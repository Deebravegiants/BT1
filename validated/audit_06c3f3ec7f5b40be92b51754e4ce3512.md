## #Title
Webhook `shop`, `topic`, and `webhook-id` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated for a given shop/topic once `Utils::HmacValidator.validate(request)` passes, but the HMAC signature only covers the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values — which are pulled straight from HTTP headers — are never part of the signed bytes, so any actor who can produce one valid (body, HMAC) pair can freely relabel it as coming from any other shop or topic.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from attacker-controllable headers with no cryptographic binding to the signed content: [2](#0-1) 

`HmacValidator.validate` verifies exactly what `to_signable_string` returns — i.e., only the body: [3](#0-2) 

`Registry.process` uses this single check as the sole gate before dispatching the handler with the unauthenticated `shop`/`topic` values: [4](#0-3) 

The identity binding that should hold is:
`bytes verified by HMAC == bytes acted upon by the handler dispatch (shop, topic, webhook_id)`

Before the request: only `raw_body` is HMAC-verified. After: `Registry.process` acts on `request.shop`, `request.topic`, `request.webhook_id` — none of which were part of the verified bytes. This is exactly the "bytes verified vs. bytes parsed/acted upon" binding failure called out for this bug class: the header fields are decoupled from the cryptographic proof, unlike `Auth::Oauth::AuthQuery`, where `shop` (and `host`, `code`, `state`) are explicitly included in `to_signable_string` and therefore are bound to the HMAC: [5](#0-4) 

### Impact Explanation
Because Shopify signs webhooks per-app (using the app's `client_secret`), any merchant who installs the app on their own (unprivileged) development/production store legitimately receives valid `(body, HMAC)` pairs for their own shop. Since the shop-domain/topic headers carry no cryptographic binding, that same attacker can capture one such valid delivery and resend it to the app's webhook endpoint with a forged `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) pointing at a different, victim shop. `Registry.process` will accept it as authentic and hand it to the registered handler labeled as coming from the victim shop — a cross-tenant identity confusion. If the host application's handler keys any session lookup, data mutation, or side effect off `WebhookMetadata#shop`/`#topic` (the intended and documented usage of this API), the attacker can trigger actions attributed to a shop they do not control, which meets the "cross-tenant access" criterion.

### Likelihood Explanation
High: no special privileges, leaked secrets, or access tokens are required — only a standard, self-service install of the app on any Shopify store (including a free development store), which yields one genuine signed webhook. Replaying and relabeling headers is trivial once the raw body and HMAC value are captured, since the gem exposes no additional check binding those headers to the signature.

### Recommendation
Do not treat `Utils::HmacValidator.validate(request)` as proof of the `shop`/`topic`/`webhook_id` values. Either:
- Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable content verified by `HmacValidator`, or
- Have `Registry.process` independently verify `request.shop` against the shop associated with the currently active/known session/install before dispatching the handler, and document clearly that `shop`/`topic` are not authenticated by the HMAC check alone.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` (no privileges beyond a normal store), triggering a real webhook delivery: body `B`, header `x-shopify-hmac-sha256: H = HMAC(client_secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: customers/create`.
2. Attacker captures this raw request (e.g., by pointing the webhook delivery at infrastructure they control).
3. Attacker resends the identical body `B` and header `x-shopify-hmac-sha256: H` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different registered `x-shopify-topic`).
4. `HmacValidator.validate` recomputes the HMAC over `B` only, matches `H`, and returns `true`.
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: "customers/create", shop: "victim.myshopify.com", body: JSON.parse(B), ...))`, and the application processes it as a legitimate event from `victim.myshopify.com`, even though it never issued this webhook.
