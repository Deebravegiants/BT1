### Title
Inconsistent, non-atomic re-reads of security-relevant `self_serve` config during a single signup allow the self-serve identity-binding trigger to be bypassed - (File: `src/plans/mod.rs`)

### Summary
The reported bug class is a stale/out-of-sync admin-controlled value: `BathPair` caches `RubiconMarketAddress` once while `BathHouse` remains the mutable source of truth, so later admin updates to the market address never propagate to `BathPair`, letting the two contracts silently diverge on a security-relevant parameter. orb-core has the analogous pattern: `orb.config` (`Arc<Mutex<Config>>`) is the single mutable source of truth for security-relevant flags such as `self_serve`, but instead of taking one authoritative snapshot for the duration of a signup, multiple independent functions inside the same signup transaction re-read `self_serve` fresh from the shared, concurrently-mutated `Config` at different points in time. Because a background task refreshes this shared config on its own timer, independent of signup lifecycle, the value observed can legitimately differ between the start and later stages of the very same signup, exactly like the `RubiconMarketAddress`/`BathHouse` desync.

### Finding Description
`self_serve` is a backend-controlled flag stored in `Config` and downloaded from the management backend (`src/backend/config.rs:50`, `src/config.rs:87`). It is periodically refreshed by a background task independent of any in-flight signup: `DefaultPlan::config_update` in `src/brokers/observer.rs:187-205` downloads a new `Config::download()` on a timer and does `*config.lock().await = new_config;`, replacing the whole shared config object wholesale, exactly like `BathHouse.setMarket()` mutating the single source of truth that `BathPair` should track.

Within a single signup, however, `self_serve` (and other trust-relevant fields) is independently re-fetched via `*orb.config.lock().await` at multiple, temporally separated points instead of being propagated from one canonical snapshot:

- `MasterPlan::run` takes one snapshot of `self_serve` at loop top (`src/plans/mod.rs:329-336`) and uses it to decide whether idle QR-scanning behaves in self-serve mode (`idle_wait_for_signup_request`, lines 394-436), a step that can block indefinitely waiting for a button press or QR scan.
- `do_signup` takes a *second, independent* snapshot of `self_serve` (`src/plans/mod.rs:497-506`) and uses it to decide whether `orb_relay_app_id` is required and whether to run `orb_relay_announce_orb_id` (lines 527-548) — this is the step that binds the companion mobile app's identity to the signup session via orb-relay.
- `proceed_with_biometric_capture` (`src/plans/mod.rs:2068-2106`) re-reads `self_serve` *yet again*, fresh from the mutex, and uses it to decide whether to gate biometric capture on receiving a `self_serve::app::v1::StartCapture` message over orb-relay (the actual identity-binding/liveness trigger from the paired app) or to skip straight to `orb.ui.signup_start()` and begin capture unconditionally.
- `detect_face` and `biometric_capture` (`src/plans/mod.rs:1093-1178`) take further independent fresh snapshots for timeout selection.

Because none of these reads share a single locked snapshot for the whole signup, and because the value they read can be mutated concurrently by the unrelated background `config_update` task at any time, the decision made in `do_signup` about whether the orb-relay app-binding/announce step is required (based on snapshot #2) can become inconsistent with the decision made moments later in `proceed_with_biometric_capture` about whether to actually wait for the app's `StartCapture` trigger (based on a later, independently-fetched snapshot #3). If `self_serve` flips from `true` to `false` between these two reads, `proceed_with_biometric_capture`'s check `if !self_serve || self_serve_app_skip_capture_trigger` becomes true, and biometric capture proceeds immediately (`orb.ui.signup_start()` then capture) without waiting for the orb-relay `StartCapture` message that is otherwise the mechanism binding the connected app/user identity to this particular capture session.

### Impact Explanation
The `self_serve_app_capture_trigger` wait step in `proceed_with_biometric_capture` is the mechanism by which the paired mobile app confirms (over orb-relay) that it is ready and associated with this specific signup before biometric capture proceeds. If the shared config's `self_serve` value flips between the time `do_signup` decided the flow requires orb-relay announcement/app binding and the time `proceed_with_biometric_capture` is actually evaluated, the trigger-wait can be silently skipped. This causes biometric capture (and downstream enrollment) to proceed without the intended app-identity confirmation step for that session, i.e., a signup can be captured/attributed without the expected in-band confirmation that ties the connected app session to the captured biometrics — a cross-stage state bleed of a security-relevant flag within one signup lifecycle.

### Likelihood Explanation
Exploiting this requires only that the operator/admin-controlled backend config value `self_serve` change while a signup is in flight — the background `DefaultPlan::config_update` task in `src/brokers/observer.rs` refreshes config unconditionally and independently of signup state, and a signup (particularly `idle_wait_for_signup_request` and the button-press wait) can legitimately span more than one config-refresh interval. No attacker action against the orb device itself is required beyond normal timing; the desynchronization is purely a consequence of the code re-reading a mutable shared value at multiple uncoordinated points rather than using one snapshot, mirroring the `RubiconMarketAddress`/`BathHouse` root cause. I was not able to fully confirm the exact `CONFIG_UPDATE_INTERVAL` value used by the top-level `Orb` broker (only `src/brokers/observer.rs` and `src/consts.rs` matches were found in the index for `CONFIG_UPDATE_INTERVAL`/`config_update_interval`) — this detail should be verified with the full source before treating this as high-likelihood versus low/theoretical.

### Recommendation
Take a single authoritative `Config` snapshot at the start of `do_signup` (or `MasterPlan::run`) and thread that same snapshot through every downstream decision point that reads `self_serve` (and related self-serve fields) for the remainder of that signup — `idle_wait_for_signup_request`, `do_signup`, `proceed_with_biometric_capture`, `biometric_capture`, `detect_face`, and `after_signup` — instead of independently re-locking and re-reading `orb.config` at each call site. If mid-signup config refresh is intentionally desired for some fields (e.g. timeouts), explicitly document and isolate which fields are safe to re-read live versus which (like `self_serve`, and anything gating identity-binding/authorization decisions) must remain fixed for the duration of a single signup transaction.

### Proof of Concept
1. Start the orb with backend config `self_serve = true`.
2. Trigger `MasterPlan::run` → `idle_wait_for_signup_request`, which (per the `self_serve` snapshot taken in `run`) enters self-serve QR-scanning flow and eventually calls `do_signup`.
3. `do_signup` re-reads config and, seeing `self_serve = true`, requires `orb_relay_app_id` and performs `orb_relay_announce_orb_id` (`src/plans/mod.rs:527-548`), establishing the orb-relay channel that is supposed to receive the app's `StartCapture` trigger.
4. Before `biometric_capture` → `proceed_with_biometric_capture` (`src/plans/mod.rs:2068-2106`) executes, the backend pushes a config update via the periodic `config_update` task (`src/brokers/observer.rs:187-205`) that sets `self_serve = false`.
5. `proceed_with_biometric_capture` re-reads config fresh, now sees `self_serve = false`, and the check `if !self_serve || self_serve_app_skip_capture_trigger` evaluates true — capture proceeds immediately via `orb.ui.signup_start()` without waiting for the app's `StartCapture` message over orb-relay, even though `do_signup` had already committed to the self-serve/app-relay flow for this signup. async fn proceed_with_biometric_capture(orb: &mut Orb) -> Result<bool> {
    let Config {
        self_serve,
        self_serve_app_skip_capture_trigger,
        self_serve_app_capture_trigger_timeout,
        ..
    } = *orb.config.lock().await;
    if !self_serve || self_serve_app_skip_capture_trigger {
        // Biometric capture not gated by a user action. Continue.
        orb.ui.signup_start();
        return Ok(true);
    }

    let orb_relay = orb.orb_relay.as_mut().expect("orb_relay to exist");

    tracing::info!("Waiting for self-serve biometric-capture trigger...");
    if let Err(e) = orb_relay
        .wait_for_msg::<self_serve::app::v1::StartCapture>(self_serve_app_capture_trigger_timeout)
        .await
    {
        if let Err(e) = orb_relay.send(self_serve::orb::v1::CaptureTriggerTimeout {}).await {
            tracing::warn!("failed to send CaptureTriggerTimeout: {e}");
        };
        orb.ui.signup_fail(SignupFailReason::Timeout);
        tracing::warn!("Self-serve biometric-capture start was not triggered: {e}");
        return Ok(false);
    };

    tracing::info!("Self-serve biometric-capture start triggered");
    orb.ui.signup_start();

    tracing::info!("Self-serve: Informing orb-relay that biometric_capture has started");
    orb_relay
        .send(self_serve::orb::v1::CaptureStarted {})
        .await
        .inspect_err(|e| tracing::error!("Relay: Failed to CaptureStarted: {e}"))?;

    Ok(true)
}

    fn config_update(&mut self, observer: &mut Observer) -> Result<()> {
        if self.before_config_update()? {
            match observer.config_update.as_mut().map(future::FutureExt::now_or_never) {
                Some(None) => return Ok(()),
                Some(Some(result)) => result??,
                None => {}
            }
            let config = Arc::clone(&observer.config);
            let ui = observer.ui.clone();
            observer.config_update = Some(tokio::spawn(async move {
                if let Ok(new_config) = Config::download().await {
                    *config.lock().await = new_config;
                    config.lock().await.propagate_to_ui(ui.as_ref());
                }
                Ok(())
            }));
        }
        Ok(())
    }
