### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so `ShopifyAPI::Utils::HmacValidator.validate` only authenticates the *body* bytes of an inbound webhook. The `shop` (and `topic`) values that `ShopifyAPI::Webhooks::Registry.process` hands to the app's business-logic handler are read straight from unauthenticated HTTP headers and are never bound to the HMAC. This mirrors the reported bug class: a value that is *acted on* (here, the tenant identity) is not covered by the cryptographic check that is supposed to bind the whole payload together.

### Finding Description
`HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, that signable string is defined as just the raw body: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from attacker-controllable HTTP headers with no cryptographic binding to the HMAC at all: [3](#0-2) 

`Registry.process` validates only the body HMAC and then forwards the unauthenticated `shop` header straight to the app's handler as the trusted tenant identity: [4](#0-3) 

The equality that should hold is: `shop claimed in the webhook == shop cryptographically bound by the HMAC`. In reality the HMAC only proves `body == HMAC(body, api_secret_key)`; it says nothing about which shop the body belongs to. Because `api_secret_key` is the app's single `client_secret`, shared across every merchant that installs the app, any merchant who has installed the app on their own (possibly free/dev) store legitimately receives a validly-signed `(body, hmac)` pair for their own shop's events. That merchant — an otherwise unprivileged actor with respect to any other tenant — can replay the exact same `body` and `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header (e.g. a victim shop's domain). `HmacValidator.validate` still succeeds because it never inspects the shop header, and `Registry.process` dispatches the handler with `shop: request.shop` set to the forged victim domain.

### Impact Explanation
This breaks the tenant-isolation guarantee the HMAC is meant to provide and lets one tenant inject data that the host application will process as if it originated from a different, victim tenant (e.g. triggering `orders/create`, `app/uninstalled`, or customer-data webhooks attributed to a shop the attacker does not own). Depending on how the host app persists or acts on `WebhookMetadata#shop` (e.g. looking up/mutating the victim's stored session or access token, deleting the victim's local records on a spoofed `app/uninstalled`), this constitutes cross-tenant access/data corruption, matching the Critical impact category (cross-tenant access) in scope for this analysis.

### Likelihood Explanation
Likelihood is significant: no secret, access token, or privileged account is required beyond installing the app on any shop the attacker controls (including a free development store), which is achievable by any unprivileged internet user for a public app. Capturing one's own genuinely-signed webhook and replaying it with a modified `Shop-Domain` header requires no cryptography to be broken — the flaw is purely the missing binding between the signed bytes and the identity field.

### Recommendation
Bind the tenant identity into the signed material, or independently authenticate it: include `shop` (and `topic`) in `to_signable_string` so the HMAC covers them, or otherwise cryptographically bind the header values to the request before trusting them in `Registry.process`/`WebhookMetadata`. At minimum, document and enforce that `request.shop` must be cross-checked against an out-of-band trusted source (e.g. the session store keyed by an already-authenticated shop) before being used for any state-changing operation.

### Proof of Concept
1. Install the target app on an attacker-owned (e.g. free trial) Shopify store `attacker-shop.myshopify.com`.
2. Trigger any subscribed webhook topic (e.g. `orders/create`) on that store; capture the raw POST body and its genuine `X-Shopify-Hmac-Sha256` header — both are valid and pass `HmacValidator.validate` because they were computed by Shopify with the app's real `api_secret_key`.
3. Replay that exact `(body, hmac)` pair to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` instead of the attacker's own domain.
4. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` (it only checks the body), and `ShopifyAPI::Webhooks::Registry.process` invokes the app's handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, causing the host application to process attacker-supplied data under the victim's tenant identity.
