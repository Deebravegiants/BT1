### Title
Webhook `shop`, `topic`, `webhook-id` and `api-version` fields are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` in `Registry.process` cryptographically verifies nothing but the body bytes. [1](#0-0)  The `shop`, `topic`, `api_version`, and `webhook_id` values are read directly from HTTP headers and are never included in the signed string, yet `Registry.process` uses them, unverified, to select the handler and to construct the `WebhookMetadata` that is handed to app code as the source of truth for which tenant the event belongs to. [2](#0-1) [3](#0-2) 

### Finding Description
The identity binding that should hold is: `bytes verified by HMAC == bytes the app trusts for tenant identity (shop)`. Here that equality is broken — `HmacValidator.validate` only checks `hmac == HMAC(body, api_secret_key)`, using `verifiable_query.to_signable_string`, which for `Request` is just `@raw_body`. [4](#0-3) [1](#0-0)  The `shop`, `topic`, `webhook_id`, and `api_version` accessors read straight from headers with no relation to the signed payload. [2](#0-1) 

`Registry.process` raises `InvalidWebhookError` only if the HMAC (of the body) fails, then dispatches based on `request.topic` and constructs `WebhookMetadata.new(topic: request.topic, shop: request.shop, ..., webhook_id: request.webhook_id)`, passing this struct to the app-supplied handler as the authoritative tenant/topic context. [3](#0-2)  Any party who can obtain one validly-signed webhook body for a given topic (e.g., a merchant who has the app installed on their own store and receives a legitimate webhook whose HMAC is computed on the body they possess) can replay that unmodified body while substituting the `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, or `x-shopify-api-version` headers. Because none of these headers are covered by the signature, `HmacValidator.validate` still returns `true`, and `Registry.process` will happily route the request under the attacker-chosen `shop`/`topic`/`webhook_id`.

### Impact Explanation
If the body content for a given topic is generic enough to be replayed across shops (or an attacker can trigger/capture a webhook with attacker-controlled body content on their own store, e.g. `orders/create` with fields they control), the app will process that body attributing it to an arbitrary victim shop domain of the attacker's choosing, since `WebhookMetadata#shop` is the only tenant identifier the handler receives and it is not authenticated. This is a cross-tenant integrity issue: data belonging to one merchant can be injected into another merchant's records/state inside the host app, without requiring the app's `client_secret`, `api_secret_key`, or any privileged credential from the attacker.

### Likelihood Explanation
Exploitability requires the attacker to already possess one validly-HMAC-signed webhook body for the relevant topic — achievable by any merchant who installs the app (an "unprivileged internet user" with respect to other tenants) and receives their own legitimate webhook traffic, then replays it with modified headers to the app's public webhook endpoint. No secret material or elevated privilege is needed beyond normal app installation, and the header substitution itself is trivial (plain HTTP headers, no cryptographic material involved).

### Recommendation
Include the security-relevant identity fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signed payload used for HMAC verification, or otherwise cryptographically bind them to the verified body (e.g., derive/verify them from a source that is itself authenticated) before they are trusted by `Registry.process` and surfaced to handlers via `WebhookMetadata`. At minimum, document that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are unauthenticated header values and must be cross-checked by the host application against a known/expected shop before being used for any tenant-scoped operation.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST: headers + `raw_body`, including the valid `x-shopify-hmac-sha256` value computed by Shopify over `raw_body`.
2. Replay the exact same `raw_body` to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim.myshopify.com` (and optionally alter `x-shopify-topic` / `x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` (via `Request#to_signable_string` at [1](#0-0) ) — validation succeeds because `raw_body` is unmodified.
4. The handler registered for the topic receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` at [5](#0-4)  and the host app processes the (attacker-supplied) body as if it belonged to `victim.myshopify.com`.
