### Title

Accrued debt-value overflow permanently freezes an oversized lending market - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary

A permissionless `update_indexes` call can permanently freeze a sufficiently large, highly utilized market because accrual computes `borrowed_scaled * borrow_index` in the `i128` domain before applying the borrow-index ceiling. [1](#0-0) [2](#0-1)  Once the represented debt exceeds `i128::MAX`, `scaled_to_original` raises `MathOverflow`, and every market operation that accrues first—including `update_indexes`, `repay`, `withdraw`, and liquidation—reverts. [3](#0-2) [4](#0-3) [5](#0-4)  The in-repository test confirms that this condition can occur before `MAX_BORROW_INDEX_RAY` and blocks withdrawals and repayments. [6](#0-5) 

### Finding Description

Every accrual step calls `scaled_to_original(env, borrowed, borrow_index)` to calculate utilization. [7](#0-6)  `scaled_to_original` delegates to `Ray::mul`, which computes `scaled * index / RAY`. [8](#0-7)  Although the intermediate multiplication is widened to `I256`, the final value must fit in `i128`; otherwise the arithmetic raises `GenericError::MathOverflow`. [9](#0-8) [3](#0-2) 

This creates an additional bound that is independent of the configured borrow-index cap: `borrowed_scaled * borrow_index / RAY <= i128::MAX`. [10](#0-9)  For example, scaled debt representing `10^36` RAY asset units can tolerate a borrow index of only about `170 * RAY`, whereas the configured index ceiling is `10^36`. [11](#0-10) [12](#0-11)  At a steep configured rate and high utilization, the index can cross that lower value-based limit before reaching the protocol ceiling. [13](#0-12) 

The controller exposes user-facing `supply`, `borrow`, `withdraw`, `repay`, and `liquidate` entrypoints that route into pool operations, while the pool’s `update_indexes` implementation runs `interest::global_sync` before committing market state. [14](#0-13) [15](#0-14) [5](#0-4)  Because the panic occurs inside the mandatory accrual phase, a later successful entry cannot skip the overflowing valuation. [4](#0-3) [16](#0-15) 

### Impact Explanation

This is a permanent market freeze and can permanently freeze supplier funds. [6](#0-5)  Once `borrowed * borrow_index` exceeds the `i128` result domain, borrowers cannot repay, suppliers cannot withdraw, liquidators cannot resolve the position, and index updates cannot complete. [16](#0-15) [4](#0-3) [5](#0-4) 

The pool design accrues before every market mutation, so there is no ordinary unprivileged exit path after the threshold is crossed. [17](#0-16)  Even an oversized repayment or withdrawal cannot bypass accrual, because the pool rejects before it reaches the position-resolution logic. [18](#0-17) 

### Likelihood Explanation

Likelihood is limited by the need for a market near the admitted RAY-domain ceiling and sustained high utilization for enough time for the borrow index to multiply that scaled debt past `i128::MAX`. [10](#0-9)  The protocol nevertheless admits caps up to approximately 170 billion whole tokens, and the checked cap only ensures that the initial token-to-RAY conversion fits; it does not ensure that accrued values remain representable. [19](#0-18) [20](#0-19) 

A single unprivileged borrower can push an existing large market toward high utilization through the public `borrow` path if it has sufficient collateral and remains within configured caps. [21](#0-20) [22](#0-21)  Thereafter, an ordinary index update triggers the fatal accrual, so exploitation does not require privileged parameters, oracle manipulation, leaked keys, or malformed token behavior. [5](#0-4) [23](#0-22) 

### Recommendation

Enforce the stricter represented-value bound before indexes advance, not merely the token-input cap. [19](#0-18) [24](#0-23)  The accrual path should detect `scaled * projected_index / RAY > i128::MAX` and clamp the projected index or reject further borrowing before crossing the bound, while still allowing repayments and withdrawals to operate on the last representable index. [25](#0-24)  Add invariant tests asserting that, under every admitted cap and index combination, accrual never reaches a state where debt or supply unscaling panics before the configured index ceiling. [6](#0-5) 

### Proof of Concept

The existing integration test demonstrates the state transition using an 18-decimal market, a billion whole tokens of supply, and a 98% borrow. [26](#0-25)  The same conditions can be produced against an existing market through public controller calls:

```rust
let debt_asset = HubAssetKey {
    hub_id: spoke_hub_id,
    asset: big_asset.clone(),
};

// 1. Seed or use existing supplier liquidity in `big_asset`.
controller.supply(
    attacker.clone(),
    0,
    spoke_id,
    vec![&env, (debt_asset.clone(), 1_000_000_000 * 10_i128.pow(18))],
);

// 2. Supply sufficient collateral, then borrow about 98% of the market.
controller.supply(
    attacker.clone(),
    0,
    spoke_id,
    vec![&env, (collateral_asset.clone(), required_collateral)],
);

controller.borrow(
    attacker.clone(),
    account_id,
    vec![&env, (debt_asset.clone(), 980_000_000 * 10_i128.pow(18))],
    Some(attacker.clone()),
);

// 3. After the borrow index grows enough, call the permissionless index update.
controller.update_indexes(vec![&env, debt_asset]);
```

At that point `accrue_step` evaluates `scaled_to_original(borrowed, borrow_index)` and panics with `MathOverflow`. [16](#0-15) [2](#0-1) [3](#0-2)  The repository’s regression test verifies that this happens below `MAX_BORROW_INDEX_RAY`, after which both `withdraw` and `repay` fail with the same error. [27](#0-26)

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"

/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}

/// Panics with `CollateralError::AssetDecimalsTooHigh` if `asset_decimals`
/// exceeds `RAY_DECIMALS`, or with `CollateralError::InvalidBorrowParams` if
/// `cap` exceeds the value returned by `max_cap_for_decimals`.
pub fn require_cap_within_asset_domain(env: &Env, cap: i128, asset_decimals: u32) {
    if RAY_DECIMALS.checked_sub(asset_decimals).is_none() {
        panic_with_error!(env, CollateralError::AssetDecimalsTooHigh);
    }
    assert_with_error!(
        env,
        cap <= max_cap_for_decimals(asset_decimals),
        CollateralError::InvalidBorrowParams
    );

    env: &Env,
    caller: &Address,
    account_id: u64,
    borrows: &Vec<HubPayment>,
    to: Option<Address>,
) {
    validation::require_authorized_caller(env, caller);

    let mut account = storage::get_account(env, account_id);

        &account,

    let restamped = enforce_post_pool_solvency(env, &mut cache, &mut account);
    let sides = if restamped {
        PositionSides::Both
    } else {
        PositionSides::Debt
    };
