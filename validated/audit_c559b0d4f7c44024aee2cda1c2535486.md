Confirmed: `CallDispatcher` is a single shared, stateless contract (`evm/src/utils/CallDispatcher.sol`) with no access control on `dispatch()` beyond requiring `to` be a contract — it holds no per-order accounting of whose funds are inside it. `IntentGatewayV2.placeOrder`'s predispatch path sweeps the dispatcher's **entire current token balance**, not just the amount produced by this order's own predispatch call.

### Title
Any user calling `placeOrder` with predispatch calldata can sweep other users' stray tokens sitting in the shared `CallDispatcher` - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder`'s predispatch flow reads the shared `CallDispatcher`'s full token balance and transfers **all of it** back to the gateway, rather than only the amount generated by the caller's own predispatch execution. If tokens end up sitting on the `CallDispatcher` — from a prior transaction that left a remainder, from a stuck/partial swap, or from anyone directly (accidentally) transferring tokens to that address — the next `placeOrder` caller whose order references that token can capture the entire balance under their own order, analogous to the `rescueERC20` bug where a function drained tokens without validating who they actually belonged to.

### Finding Description
In `evm/src/apps/IntentGatewayV2.sol`, the predispatch branch of `placeOrder` (lines 235-311) does the following per input token: [1](#0-0) 

```
uint256 balance = IERC20(token).balanceOf(dispatcher);
if (balance < requiredAmount) revert InvalidInput();
transferCalls[i] = Call({
    to: token, value: 0,
    data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
});
balancesBefore[i] = IERC20(token).balanceOf(address(this));
```

It reads `IERC20(token).balanceOf(dispatcher)` — the *entire* current balance of that token on the shared `CallDispatcher` — and constructs a transfer call moving the *entire balance* back to the gateway, not just the amount the caller's own `order.predispatch.call` was expected to produce. `CallDispatcher` itself (`evm/src/utils/CallDispatcher.sol`) is a bare, stateless relay with no ownership bookkeeping: [2](#0-1)  — it executes whatever `Call[]` it's given and has no concept of which caller's funds are inside it.

The subsequent accounting only measures the *net increase* in the gateway's own balance (`received = balanceOf(this) - balancesBefore[i]`), and any amount above what this order needs is emitted as `DustCollected` and effectively becomes protocol-owned dust: [3](#0-2) 

This means: whatever residual balance the `CallDispatcher` was holding for token `T` before this `placeOrder` call — regardless of its origin — gets fully swept and attributed to the current caller's order (as extra escrow up to `order.inputs[i].amount`, and the remainder as dust). The `CallDispatcher` is a single global contract shared by every `placeOrder`/`fillOrder`/cross-chain token-transfer caller across the whole IntentGatewayV2/HyperFungibleToken ecosystem (it's also used by `HyperFungibleToken`/`WrappedHyperFungibleToken`'s `onAccept` calldata execution and `IntentsBase._execute`), so any transaction that leaves tokens stranded on it — a reverted/partial multi-call sequence in a separate transaction, a mis-targeted direct transfer, or dust left by another order's predispatch/postdispatch sweep timing — is up for grabs by the next caller who places an order with a matching input token.

### Impact Explanation
An unprivileged caller can construct a `placeOrder` transaction whose `predispatch.call` does nothing (or a no-op) and whose `order.inputs` reference a token they suspect has a stray balance sitting on the `CallDispatcher`. As long as `balanceOf(dispatcher) >= requiredAmount`, the entire dispatcher balance for that token is pulled into the gateway and credited to the attacker's own escrowed order (up to `order.inputs[i].amount`) with any surplus emitted as protocol dust rather than returned to whoever's tokens they actually were. This is a permanent loss of funds for the original owner of the stranded tokens and a direct value transfer to the attacker (their order gets filled/backed by tokens they never contributed), matching the "theft of accidentally transferred tokens" bug class.

### Likelihood Explanation
Requires tokens to actually be resident on the `CallDispatcher` at the time of the attacker's `placeOrder` call. This can arise from: (a) a legitimate user's own predispatch/postdispatch call leaving residual balance between transactions (the contract holds no invariant preventing balance from persisting across calls), (b) any third party mistakenly sending tokens directly to the known, publicly-deployed `CallDispatcher` address (its `receive()` and lack of access control make this trivial), or (c) timing windows in cross-chain flows where `HyperFungibleToken`/`IntentsBase` route mint-then-execute through the same dispatcher. Because the dispatcher address is public infrastructure reused by many flows, an attacker can simply monitor its balance and front-run with a matching `placeOrder`.

### Recommendation
Scope the predispatch sweep to only the amount actually produced by the caller's own `predispatch.call`, e.g. by snapshotting the dispatcher's balance immediately before executing `order.predispatch.call` and only sweeping `balanceAfter - balanceBefore` (bounded to `requiredAmount`), rather than the dispatcher's total balance. Alternatively, deploy a fresh, single-use `CallDispatcher` instance per order (e.g., via `CREATE2` scoped to the commitment) so no shared, cross-order balance can ever accumulate.

### Proof of Concept
1. Some token `T` balance ends up on the shared `CallDispatcher` (e.g., user A's earlier `placeOrder` predispatch swap left 5 `T` as slippage residue, or someone directly transfers 5 `T` to the dispatcher address by mistake).
2. Attacker calls `placeOrder` with `predispatch.call` set to a harmless call (e.g., calling `T.balanceOf(address(this))`, which is a valid contract call and succeeds), `predispatch.assets` empty of that token, and `order.inputs[0] = {token: T, amount: 5}`.
3. In the sweep loop, `balance = IERC20(T).balanceOf(dispatcher)` reads the stray `5 T`; `requiredAmount = 5` so the check passes; the transfer call moves all `5 T` to the gateway.
4. `received = 5`, which equals `order.inputs[0].amount`, so it is escrowed entirely under the attacker's order commitment — the attacker now has an order backed by tokens that belonged to someone else, and can redeem/cancel it to receive real value or fill against a solver, effectively stealing the stranded funds.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
