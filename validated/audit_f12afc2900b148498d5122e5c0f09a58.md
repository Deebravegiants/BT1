### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the `shop` attribute — the tenant identifier that host applications are documented to rely on — is read unauthenticated from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates only that the body is HMAC-valid, then passes the untrusted header-derived `shop` value straight into the handler's `WebhookMetadata`. This breaks the intended identity binding: `HMAC(shop, body) == HMAC(body)` — the shop is acted upon but never covered by the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `hmac` is read from the `hmac-sha256` header: [2](#0-1) 

while `shop` is read from a separate, unsigned header: [3](#0-2) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string` (the raw body) and compares it to the received HMAC — it never incorporates the shop header: [4](#0-3) 

`ShopifyAPI::Webhooks::Registry.process` validates only this body-HMAC, then constructs `WebhookMetadata` using the unauthenticated `request.shop`, and forwards it to the app's handler: [5](#0-4) 

The gem's own documentation instructs app developers to trust `data.shop` as the tenant key for further processing (e.g., enqueuing per-shop jobs): [6](#0-5) 

Because the shop identifier is never bound to the HMAC, any request bearing a body/HMAC pair that is valid for the app's secret (which an attacker can obtain legitimately, e.g. by installing the app on their own store and capturing a real Shopify-sent webhook) can be replayed with an arbitrary `X-Shopify-Shop-Domain` header. The signature check still passes because it only verifies the raw body, and the handler receives `data.shop` set to whatever domain the attacker chose — spoofing a webhook as if it originated from a different (victim) tenant.

### Impact Explanation
This crosses the tenant boundary the gem is documented to protect: an attacker-controlled `shop` value reaches app business logic as if it were an authenticated identity claim from Shopify. Any host application that follows the documented pattern of keying per-shop side effects (data updates, job dispatch, redaction handling for `shop/redact` etc.) off `data.shop` can be tricked into acting on behalf of, or against, a shop the attacker does not own — a cross-tenant access/data-confusion vulnerability rooted entirely in this gem's verification logic, not the host app's misuse.

### Likelihood Explanation
Exploitability requires only one non-privileged capability: the ability to obtain any body+HMAC pair valid under the app's secret — trivially available to any merchant who installs the app on their own store and observes a legitimate webhook delivery (bodies for many topics, e.g. `app/uninstalled`, `shop/redact`, are shop-domain-agnostic or attacker-controllable in effect). The header can then be freely modified before replay to the app's public webhook endpoint, since nothing else authenticates it.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signable content that's cryptographically bound to the HMAC, or independently verify that `X-Shopify-Shop-Domain` matches a shop already known/authorized for the referenced webhook subscription before handing it to `WebhookMetadata`/the handler. At minimum, document that `data.shop` is unauthenticated and must not be used as a sole tenant-scoping key.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and captures a legitimate webhook HTTP request Shopify sends to the app (body `B`, header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`).
2. Attacker resends this exact body `B` and HMAC header to the app's webhook endpoint but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches the received HMAC — validation succeeds because the shop header was never part of the signed content [1](#0-0) .
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [7](#0-6) , and the app performs shop-scoped actions believing this event genuinely originated from `victim-shop.myshopify.com`.
