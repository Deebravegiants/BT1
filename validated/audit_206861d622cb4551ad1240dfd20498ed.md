### Title
Webhook `shop` identity not bound to HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` (used by `Webhooks::Registry.process`) authenticates *only* the body bytes. The `shop` value (`shopify-shop-domain`/`x-shopify-shop-domain` header) that identifies which tenant the webhook belongs to is never included in the signed data, so it can be freely altered by anyone submitting a request, while the HMAC still validates.

### Finding Description
`HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac` [4](#0-3) . For a `Webhooks::Request`, `to_signable_string` is defined as just `@raw_body` [2](#0-1) , while `shop` is read straight from an attacker-controlled header with no cryptographic linkage to the HMAC [1](#0-0) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body authenticity) before invoking the handler with `request.shop` as the trusted tenant identifier [3](#0-2) .

This is structurally the same class of bug as the reported `EmissaryLib._getEmissaryConfig` issue: a value that must be included in an authenticated hash to enforce an identity/authorization binding (there, `sponsor`; here, `shop`) is silently excluded from what is actually verified, so the binding "verified-shop == acting-shop" collapses to "verified-body == acting-shop", which anyone can violate.

### Impact Explanation
Because `shop` is not covered by the HMAC, an attacker who can obtain any single genuinely-Shopify-signed webhook body+HMAC pair (trivial: install the target app on their own free/dev store and let Shopify deliver a real webhook to the app's endpoint) can resend that exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header for an arbitrary victim shop. `Registry.process` will validate the HMAC (it only checks the body) and hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop [5](#0-4) . Per the gem's own documentation, host apps are expected to trust `data.shop` as "the shop domain of the webhook" [6](#0-5)  and to rely on `Registry.process` to "verify the request did indeed come from Shopify" [7](#0-6) . This directly enables cross-tenant confusion: a fabricated event (e.g. `app/uninstalled`, `shop/redact`, `orders/create`) can be attributed to a shop that never sent it, corrupting per-shop state, triggering unauthorized data deletion/redaction, or injecting forged order/customer data into another merchant's records — all without any credential belonging to the victim or the app.

### Likelihood Explanation
Exploitation requires no privileged access: any internet user can create a free Shopify development store, install the target app, and trigger any webhook topic the app subscribes to, thereby obtaining a validly-HMAC-signed `(body, hmac)` pair for that topic. Replaying it against the same public webhook endpoint with a different `shopify-shop-domain` header is a trivial HTTP request. Every app built on this gem's webhook handling is affected identically, since the flaw is in the shared `Request`/`HmacValidator`/`Registry` code path rather than any particular host app's usage.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie them to the verified payload, e.g.:

```ruby
sig { override.returns(String) }
def to_signable_string
  "#{shop}\n#{topic}\n#{@raw_body}"
end
```

with a corresponding fix on the signing/verification side so the concatenation cannot be re-partitioned (use fixed-length/escaped fields or a struct-hash rather than naive concatenation, to avoid boundary-shifting ambiguities). At minimum, document and enforce that `Registry.process` must additionally verify `shop` against a caller-supplied expected shop, rather than trusting the header outright.

### Proof of Concept
1. Attacker signs up for a free Shopify partner/dev store `attacker-shop.myshopify.com` and installs the victim's app, which is registered for `app/uninstalled` (or any topic) via `ShopifyAPI::Webhooks::Registry.add_registration`.
2. Attacker uninstalls the app on their own store, causing Shopify to send a legitimately HMAC-signed webhook to the app's public endpoint:
   ```
   POST /webhooks/app_uninstalled
   x-shopify-topic: app/uninstalled
   x-shopify-hmac-sha256: <valid-signature-for-body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: {}
   ```
   The attacker captures this exact `(body, hmac)` pair (e.g. via a proxy they control, since it is delivered to their own server).
3. Attacker resends the identical request to the same public endpoint, changing only the header:
   ```
   POST /webhooks/app_uninstalled
   x-shopify-topic: app/uninstalled
   x-shopify-hmac-sha256: <same valid-signature-for-body>
   x-shopify-shop-domain: victim-shop.myshopify.com
   Body: {}
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unchanged) body against the (unchanged) HMAC [8](#0-7) .
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", ...)` [9](#0-8) , causing the host app to act (e.g. delete stored data, revoke access) against `victim-shop`, a shop the attacker never legitimately controls.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
