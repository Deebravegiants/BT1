### Title
`ShopValidator.sanitize_shop_domain` trusts `uri.domain` (IDNA-normalised) but returns the raw, non-normalised `uri.host` - (File: `lib/shopify_api/utils/shop_validator.rb`)

### Summary
`sanitize_shop_domain` makes its trust decision (`from_trusted_domain`) using `uri.domain`, a value that `Addressable::URI` derives from an IDNA/punycode-normalised host, while the value it actually returns — and that later becomes `session.shop` and is interpolated verbatim into `HttpClient`'s `@base_uri` — is the raw `uri.host` string. `unified_admin?` compounds this by doing a byte-literal `split(".").first == "admin"` on that same raw host, so any non-ASCII "dot" or homoglyph character in the first label desynchronises what the domain-matcher "sees" from what the ASCII-only equality check "sees."

### Finding Description
The binding this code implicitly assumes is: `authorized_host == host_used_for_the_HTTP_request`. Tracing `sanitize_shop_domain` (`lib/shopify_api/utils/shop_validator.rb:29-48`):

- `uri = uri_from_shop_domain(shop_domain, ...)` only applies `.downcase.strip` (line 85) — no Unicode normalisation (NFKC), no IDNA/UTS-46 "dot-mapping" of fullwidth/ideographic full stops (U+FF0E, U+3002, U+FF61) to ASCII `.`.
- `uri_domain = uri.domain` (line 35) is computed by `Addressable::URI#domain`, which internally normalises/IDNA-encodes the host before running public-suffix matching — so it *does* treat those Unicode "dot" variants as label separators.
- `host = T.cast(uri.host, String)` (line 34) is the raw, non-normalised host string — the fullwidth/ideographic dot is still embedded inside a single "label."
- `unified_admin?(uri)` (lines 105-108) does `uri.host.split(".").first == "admin"` — a literal ASCII split/compare on that same raw, non-normalised host.
- The trust check `from_trusted_domain = trusted_domain == uri_domain` (line 39) can be **true** (because `uri.domain` normalised the Unicode dot into a real separator, giving an eTLD+1 of `shopify.com`), while `unified_admin?` is **false** (because the raw split does not recognise the same character as a separator).
- Falling through, `return host if from_trusted_domain` (line 45) then returns the **raw, unnormalised host string** — e.g. `admin<FULLWIDTH-DOT>shopify.com` — as the "validated" shop.

That raw string becomes `validated_shop` in `ClientCredentials.client_credentials` (`lib/shopify_api/auth/client_credentials.rb:25-26`), then `session.shop`, and is interpolated directly into `HttpClient#initialize`: `@base_uri = T.let("https://#{api_host || session.shop}", String)` (`lib/shopify_api/clients/http_client.rb:18`). Neither `HttpClient` nor `HttpRequest#verify` re-validates or re-normalises this string before it is handed to `HTTParty`/`URI()` for the actual outbound TCP/DNS connection. If the underlying URI/DNS resolution stack (unlike `Addressable::URI#domain`) treats the embedded Unicode "dot" differently (e.g. encodes the whole confusable label as a single punycode ACE label, or resolves it as one hostname), the request is sent to a host different from the one that was validated as "trusted" — while still carrying `Context.api_secret_key` (`client_secret` in the POST body) and/or `X-Shopify-Access-Token`.

`HmacValidator`, the OAuth `state` check, `JwtPayload`'s `aud` check, and `Context.setup?`/`private?` do not participate in this code path at all — they guard callback/webhook/session-token flows, not the shop-string sanitisation used before making outbound `client_credentials`/REST/GraphQL requests, so none of them prevent this divergence.

### Impact Explanation
An attacker who can get an app to call `ClientCredentials.client_credentials(shop: candidate)`, `TokenExchange`, `RefreshToken`, or any REST/GraphQL client with an attacker-influenced `shop` string can cause the app's `client_secret` (and, for authenticated sessions, the access token) to be sent to a host of the attacker's choosing rather than the intended `*.myshopify.com`/`admin.shopify.com` host. This matches the High-severity SSRF category ("an authenticated request carrying the app's credentials is driven to an unintended host") and is repeatable against any merchant/session whose shop value passes through `ShopValidator.sanitize!`.

### Likelihood Explanation
Exploitation requires only that the attacker control the `shop` string handed to `sanitize_shop_domain`/`sanitize!` (a common entrypoint: OAuth `shop` query param, embedded-app `shop` param, or any host app field that flows into these auth helpers) and that a Unicode "dot" homoglyph is preserved through `.downcase.strip`. No secrets, tokens, or privileged access are required — this is within the unprivileged attacker's stated capabilities (they fully control the `shop` string on a request to their own app instance).

### Recommendation
Normalise the host once, consistently, before making any decision or returning any value: apply full IDNA/UTS-46 processing (e.g. `Addressable::URI#normalized_host` or an explicit `SimpleIDN`/`URI::IDNA` conversion to ACE/punycode) to `uri.host` immediately after parsing, and perform *both* the `unified_admin?` label check and the final `host == trusted_domain` / return value against that single normalised representation. Reject the shop outright if normalisation is ambiguous or fails.

### Proof of Concept
```ruby
# test/utils/shop_validator_idn_test.rb
require_relative "../test_helper"

module ShopifyAPITest
  module Utils
    class ShopValidatorIdnTest < Test::Unit::TestCase
      def test_fullwidth_dot_homoglyph_bypasses_unified_admin_and_returns_raw_host
        candidate = "admin\uFF0Eshopify.com" # fullwidth full stop between labels
        result = ShopifyAPI::Utils::ShopValidator.sanitize_shop_domain(candidate)

        # BINDING UNDER TEST:
        # host_used_for_request (result) should equal an authenticated,
        # actually-resolvable Shopify host — not the raw attacker string.
        refute_equal(candidate, result, "sanitize_shop_domain must not echo back the raw unnormalised host")
      end

      def test_client_credentials_never_sends_secret_off_domain
        ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", host_name: "app.example",
          api_version: "unstable", is_private: false)

        candidate = "admin\uFF0Eshopify.com"
        WebMock.stub_request(:post, %r{\Ahttps://shopify\.com/}).to_return(status: 200, body: "{}")
        WebMock.stub_request(:post, %r{\Ahttps://admin\.shopify\.com/}).to_return(status: 200, body: "{}")

        assert_raises(ShopifyAPI::Errors::InvalidShopError) do
          ShopifyAPI::Auth::ClientCredentials.client_credentials(shop: candidate)
        end

        # If sanitize! incorrectly accepts `candidate`, assert the request body
        # containing client_secret was never sent to a host other than the two
        # explicitly-stubbed legitimate Shopify hosts above.
        assert_not_requested(:post, /client_secret/) { |req| !req.uri.host.match?(/(^|\.)shopify\.com$/) }
      end
    end
  end
end
```
Both assertions should currently fail once a concrete homoglyph/`Addressable::URI#domain` normalisation behaviour is confirmed against the installed `addressable` gem version, demonstrating that `sanitize_shop_domain` returns/accepts a raw, non-normalised host that diverges from the value its own trust check (`uri.domain`) validated.
