### Title
Permanent freeze of message delivery due to impossibility of correcting a state machine commitment after a source-chain reorg - (File: `modules/ismp/core/src/handlers/consensus.rs`, `evm/src/core/HandlerV2.sol`)

### Summary
Both the Substrate ISMP host's `update_client` handler and the EVM `HandlerV2` consensus-update path permanently lock in the *first* state commitment recorded for a given `(state_machine_id, height)` pair. Neither path allows a later, corrected consensus proof to overwrite a previously stored commitment at the same height — even when that height's content changes because of a legitimate reorg on the source/counterparty chain. This mirrors the reported OptimismPortal bug class: a proof tied to a specific index/height cannot be "re-proven" once a competing/incorrect version of that index/height has already been accepted, permanently stranding messages that were actually included under the corrected fork.

### Finding Description
On the Substrate side, `update_client` iterates the intermediate states returned by `verify_consensus` and stores each one only if the height is not already committed: [1](#0-0) 

```
// Only allow heights greater than latest height
if previous_latest_height > commitment_height.height { continue; }
// Skip duplicate states
if host.state_machine_commitment(state_height).is_ok() { continue; }
...
host.store_state_machine_commitment(state_height, commitment_height.commitment)?;
```

The "skip duplicate states" check only tests *whether a commitment exists* at that height — it never compares the new commitment's `state_root`/`overlay_root` to the one already stored. If a relayer submits a consensus proof for height `H` before a reorg on the source chain, and later submits a second, correct consensus proof for the same height `H` after the reorg (because the source chain replaced the block at `H`), the second submission is silently dropped, leaving the stale/incorrect root permanently canonical for `H`. [2](#0-1) 

The pallet's own code comments confirm this design choice ("ISMP does not allow duplicate state updates so we don't have an overwrite path"), and the test suite explicitly documents that a height below the current latest height can never be resubmitted, even after the stale commitment is removed via veto: [3](#0-2) 

On the EVM side, `HandlerV2`'s consensus-update loop is even stricter — it only stores an intermediate state if its height is *strictly greater* than the currently recorded latest height, so any resubmission at or below the latest height (including one intended to correct a prior, reorg-invalidated commitment) is dropped outright: [4](#0-3) 

The only mechanism capable of clearing a bad commitment is `veto_state_commitment` in `pallet-fishermen` (Substrate) or `deleteStateMachineCommitment` (EVM), both restricted to the active collator set / handler: [5](#0-4) [6](#0-5) 

But even that path does not fix the underlying problem: once a height is deleted and the chain's `latest_commitment_height`/`latestStateMachineHeight` has already advanced past it, the consensus-update handlers' "only accept heights greater than the latest" rule permanently prevents that height from ever being resubmitted with the corrected content — exactly the scenario documented by the test `vetoed_height_that_cannot_be_resubmitted_evicts_as_a_noop`.

### Impact Explanation
Any Post/Get request or response that was included in the block at the affected height — under the correct, post-reorg fork — becomes permanently unprovable: `HandlerV2.handlePostRequests`/`handleGetResponses` (EVM) and pallet-ismp's message handlers rely on `stateMachineCommitment(height)`/`state_machine_commitment(height)` to obtain the trie root used for membership/non-membership proofs. If that root is stale (reflecting a discarded fork) or missing (post-veto, pre-resubmission-block), no relayer can ever deliver those messages, and no user can ever finalize a cross-chain action (e.g., a token bridge mint/burn, an intent settlement, or a fee/reward claim) that depended on inclusion at that height. This is a permanent freeze of funds/message-delivery route, matching the required "route unable to deliver messages" / "permanent freezing of funds" impact bar, and is High severity because it can be triggered by ordinary chain reorg behavior on any of the many supported consensus clients (BSC, Tendermint, Pharos, GRANDPA/BEEFY-relayed L2s, sync-committee) without any malicious actor being required.

### Likelihood Explanation
Reachability is via a single unprivileged relayed transaction: any relayer can call `update_client`/`updateConsensusState` with a consensus proof for a height that was previously committed. Chains without full BFT/instant finality guarantees (e.g., BSC's PoSA, or L2 chains where a previously-accepted dispute-game/output-root claim is later overturned) can legitimately produce a different canonical block at a height that has already been recorded on Hyperbridge. Because the store logic keys strictly on height rather than on height+content, this is a realistic, non-malicious operational scenario, not merely a theoretical edge case — the report's own framing ("the trustless operator scenario is just a general blocks reorg case") applies directly here.

### Recommendation
Change the duplicate/height-gating checks in both `update_client` (`modules/ismp/core/src/handlers/consensus.rs`) and `HandlerV2`'s consensus-update loop (`evm/src/core/HandlerV2.sol`) so that a new commitment for the same height can supersede a previous one when it differs and the previous one has not yet been consumed for a finalized withdrawal/message beyond the challenge period, or, at minimum, provide a permissionless/cryptographically-verifiable path for correcting a specific height's commitment (rather than only the collator-gated `veto_state_commitment`) — analogous to the recommended fix of comparing against the *current* on-chain state at that index/height rather than a strict "already exists" check.

### Proof of Concept
1. A relayer submits `update_client` (Substrate) or the equivalent `HandlerV2` call (EVM) with a valid consensus proof asserting state commitment `C1` for `StateMachineHeight { id, height: H }` for a counterparty chain that does not have instant/absolute finality at submission time (e.g., BSC, or an L2 whose output root/dispute game has not yet passed its challenge window).
2. `host.store_state_machine_commitment` stores `C1`; `latest_commitment_height`/`latestStateMachineHeight` advances to `H` (or beyond, as later heights are also committed).
3. A reorg occurs on the counterparty chain: the block at height `H` is replaced, producing a different, now-canonical state root `C2` for the same height, in which a user's cross-chain request/response is included (in the new canonical block, not the discarded one).
4. A relayer submits a second, valid consensus proof attesting `C2` at height `H`.
5. In `update_client`, `host.state_machine_commitment(state_height).is_ok()` returns `true` (a commitment for `H` already exists), so the update is skipped via `continue` — `C2` is never stored. Equivalently, on the EVM side, `intermediate.height > latestHeight` is false, so the `storeStateMachineCommitment` call is never made.
6. The user's request, which only exists under `C2`, can never be proven against the on-chain commitment for `H` (which permanently remains `C1`), so the message can never be delivered — a permanent freeze, with no user-triggerable recovery path other than a collator veto, which itself cannot re-open height `H` once the chain has advanced past it (per `vetoed_height_that_cannot_be_resubmitted_evicts_as_a_noop`).

fn vetoed_height_that_cannot_be_resubmitted_evicts_as_a_noop() {

	ext.execute_with(|| {
		let host = Ismp::default();
		let id = queue_test_state_machine();
		let store = |height: u64| {
			host.store_state_machine_commitment(
				StateMachineHeight { id, height },
				queue_test_commitment(),
			)
			.unwrap();
			host.store_latest_commitment_height(StateMachineHeight { id, height }).unwrap();
		};

		pallet_ismp::Pallet::<Test>::update_commitment_caps(
			RuntimeOrigin::root(),
			BTreeMap::from([(id, 2)]),
		)
		.unwrap();

		store(10);
		store(11);

		// its queue entry stays behind as a stale index. The latest height is

    /**
     * @dev Delete the state commitment at given state height.
     */
    function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
        StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
        // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
        if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
            _latestStateMachineHeight[height.stateMachineId] = 1;
        }

        // track the fisherman responsible for rewards on hyperbridge through state proofs
        _vetoes[height.stateMachineId][height.height] = fisherman;

        emit StateCommitmentVetoed({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId),
            stateCommitment: stateCommitment,
            height: height.height,
            fisherman: fisherman
        });
    }
