## Title
Premature full-escrow release when multiple order inputs share the same token address in `_fillSameChain` - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

## Summary
`_orders` escrow storage is keyed only by `(commitment, token address)`, aggregating the escrowed balance for *all* input entries that reference the same ERC-20 (or native) token in a multi-input order. [1](#0-0)  `_fillSameChain`'s escrow-release calculation, however, is done per-output-index `i` and assumes a strict 1:1 correspondence between `order.inputs[i]` and `order.output.assets[i]`. [2](#0-1)  When an output leg is fully satisfied (`amountFilled == totalRequired`), the code releases the *entire remaining stored balance* for that input's token — `_orders[commitment][token]` — rather than only that leg's proportional share:

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
``` [3](#0-2) 

## Finding Description
This "full-fill sweeps remaining balance" pattern is exactly the mitigation Beanstalk/Basin adopted for the analogous constant-function-AMM bug (`Well::removeLiquidityOneToken` releasing the exact remaining balance on last withdrawal to avoid rounding-dust reverts). The Basin report notes that when quantities that should sum to a fixed total (LP supply, or here, escrowed token balance) are split into several truncating-division computations across separate legs/solvers, the arithmetic will not exactly reconcile, and only the *last* leg to complete should be given "whatever remains" rather than another computed fraction — otherwise dust is either permanently locked (protocol insolvency for the depositor) or, if miscomputed, an *earlier* leg can walk off with more than its share, starving a later leg and causing a valid, otherwise-fillable transaction to underflow/revert (the `UnknownOrder`/subtraction-underflow condition in `_withdraw`). [4](#0-3) 

The Hyperbridge analog manifests the second, more severe failure mode. `Order.inputs` and `Order.output.assets` are independent, index-parallel arrays with no uniqueness constraint enforced on `inputs[i].token`. If two output legs (say index 0 and index 2) are both funded, at least in part, by input entries that resolve to the *same token address* (e.g. the order specifies the same USDC input twice, split across two output legs, or two different `order.inputs[]` entries happen to reference the same ERC-20), `_orders[commitment][token]` holds the combined escrow for both legs. As soon as the *first* of the two legs to reach `amountFilled == totalRequired` fires, it reads and releases the aggregate remaining balance for that token — which includes funds that are still meant to back the *other*, not-yet-filled leg — rather than only its own portion.

Consequences:
1. The solver completing the first leg receives tokens that rightfully belong to the escrow backing the second leg (a direct value-transfer/theft vector against the user placing the order, or against whichever solver later tries to complete the second leg).
2. The second leg's later completion (or the user's cancellation via `_cancelSameChain`, which also reads `_orders[commitment][token]` per input index and assumes it represents only that input's remaining escrow) will find `_orders[commitment][token]` already drained to zero or to a value lower than expected, causing `_withdraw`'s `if (escrowed == 0) revert UnknownOrder();` check to fire on a legitimate fill/cancel, or `escrowed - amount` to underflow and revert. [5](#0-4) 

This is structurally the same class of bug flagged in the Basin report: state (`totalSupply`/escrow ledger) is expected to track a per-leg accounting invariant, but the code takes a shortcut ("sweep the whole remaining pool on completion") that is only valid when there is a strict bijection between the accounting key and the release unit — a bijection that isn't actually enforced here.

## Impact Explanation
This breaks a core Hyperbridge invariant for `IntentGatewayV2`/`IntrinsicIntents`: escrowed input tokens must be released strictly in proportion to the output actually delivered, and the sum of all releases for an order must never exceed what was originally escrowed for that specific input allocation. A violation lets a solver claim more escrow than it is entitled to (direct fund theft from the user/other legitimate solver) and/or causes a later, otherwise-valid fill or cancel operation to permanently revert because the escrow ledger for the shared token has already been zeroed out (freezing of funds / broken settlement) — matching the report's "protocol insolvency, valid liquidity removal reverts" impact class. This is reachable by any user placing a same-chain multi-input/multi-output order and any solver calling `fillOrder`, with no privileged role required.

## Likelihood Explanation
Reachability requires only that a placed `Order.inputs` array contain two entries with the same token address (or that two output legs are backed, index-parallel, by inputs of the same token) — nothing in `placeOrder`/`_fillSameChain`/`_cancelSameChain` validates uniqueness of `order.inputs[i].token` across indices. Since orders are fully user/solver constructed calldata, and the fill logic processes each output index independently without ever checking overlap of input tokens across indices, this is trivially triggerable by a single crafted order and a sequence of two fills (or one fill plus a cancel of the remaining leg).

## Recommendation
Track escrow accounting per `(commitment, input index)` rather than per `(commitment, token address)`, or, if aggregating by token address is intentional (e.g. for gas), compute each leg's `escrowedAmount` release strictly as a bounded pro-rata share of that leg's *own* originally-escrowed amount (tracked separately per input index) instead of reading the whole current `_orders[commitment][token]` balance on a "full fill" of any single output leg. Alternatively, validate at `placeOrder` time that `order.inputs[i].token` values are unique across `i`, eliminating the possibility of shared-token legs entirely, and add an invariant check (analogous to the Basin `checkInvariant` recommendation) asserting that the sum of all `escrowedAmount` released across an order's lifetime never exceeds the amount originally escrowed for each individual input entry.

## Proof of Concept
Conceptual sequence (same-chain order, two input legs on the same ERC-20 token `T`, two independent output legs on token `T'`/native ETH):
1. `placeOrder`: `order.inputs = [{token: T, amount: 600}, {token: T, amount: 400}]`, `order.output.assets = [{token: X, amount: 100}, {token: Y, amount: 50}]`. Escrow ledger: `_orders[commitment][T] = 1000` (600+400 combined, since `_orders` is keyed only by token address).
2. Solver A fully fills output leg 0 (`solverAmount = 100 == totalRequired`): `amountFilled == totalRequired` branch triggers, so `escrowedAmount = _orders[commitment][T]` — i.e. **1000**, not the intended 600 tied to `inputs[0]`. Solver A receives the full 1000 `T`, and `_orders[commitment][T]` is zeroed by `_withdraw`.
3. Solver B (or the user via `_cancelSameChain`) attempts to fill/cancel output leg 1, which expects the remaining 400 `T` escrow: `_orders[commitment][T]` reads 0, so `_withdraw` reverts with `UnknownOrder`, or (if a smaller residual existed) the release amount silently comes up short — the second leg's promised token allocation has already been stolen by the first filler.

This confirms the root cause via the exact code path cited above; full dynamic exploitation would need to be verified with a Foundry reproduction against `IntentGatewayV2SameChainTest.sol`, which was not run as part of this analysis.
