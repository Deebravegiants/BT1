### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by verifying the HMAC over the raw request body, but the `shop` identity that is handed to the application's webhook handler is read from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, which is **not** covered by the HMAC signature. An attacker who legitimately installs the app on their own shop (an unprivileged, self-service action) can capture a genuine, correctly-signed webhook delivered to their own endpoint and replay the identical body/HMAC pair to the victim host application's webhook endpoint while substituting the `shop-domain` header for a different (victim) shop. The signature check still passes because it never covers that header, so the host application processes attacker-controlled webhook data under the identity of an arbitrary shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate_signature` computes/compares the HMAC exclusively against this signable string: [2](#0-1) 

Meanwhile, `shop` is derived independently from a header that is never mixed into the signed material: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and the parsed body) as the authenticated identity of the shop the data belongs to when dispatching to the app's handler: [4](#0-3) 

The equality the gem is implicitly supposed to guarantee is:
`shop asserted in header == shop that the HMAC-covered body actually originated from`

Because the HMAC never binds the `shop-domain` header, this equality is not enforced. Any party who can obtain one valid `(raw_body, hmac)` pair — trivially available to any merchant who installs the app on their own store and receives a real webhook — can present that same pair to the app's public webhook endpoint with an arbitrary `shop-domain` header value. `Utils::HmacValidator.validate` returns `true` (the body and HMAC still match each other), and `Registry.process` forwards the forged `shop` value straight into `WebhookMetadata`, which the host application's handler will use as the tenant identifier for whatever side effect the webhook triggers (e.g., updating order/product data, billing state, or shop-scoped records).

### Impact Explanation
This breaks the tenant-identity binding at the trust boundary of an unprivileged, internet-reachable endpoint (the webhook receiver). An attacker with only their own (legitimately installed) shop can inject data that is processed as if it came from a different, victim shop — a cross-tenant confusion/access primitive that matches the Critical "cross-tenant access" impact category, since the receiving application has no gem-level guarantee that `shop` corresponds to the authenticated body.

### Likelihood Explanation
Exploitation requires no secrets: the attacker only needs a self-service app installation (any merchant can install most public/embedded apps) to obtain a genuinely signed webhook body+HMAC pair, and then a single forged HTTP POST with a modified `shop-domain` header to the app's public webhook URL. No access token, `client_secret`, or privileged account is required, and the gem's `Registry.process`/`HmacValidator` API provides no mechanism for host apps to detect the mismatch.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`api-version`) header value into the HMAC-covered signable content, or otherwise cryptographically bind the shop claim to the payload before trusting it. At minimum, `Utils::VerifiableQuery`/`Webhooks::Request#to_signable_string` should incorporate the shop header (matching how Shopify signs webhooks) so that the HMAC check fails if the header is altered independently of the raw body.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook at their configured endpoint (`x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker.myshopify.com`, body `B`).
2. Attacker replays a POST to the app's public webhook route with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes the HMAC over `B` only (`Request#to_signable_string` at [1](#0-0) ) and finds it matches `H` — validation succeeds.
4. `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` ( [5](#0-4) ) and invokes the host app's handler, which processes attacker-controlled data under the victim shop's identity.
