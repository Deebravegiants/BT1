### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, never the shop-identifying headers: [1](#0-0) 

Meanwhile `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read straight from unauthenticated HTTP headers: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `verifiable_query.to_signable_string` (i.e., the body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` validates that body-only signature and then unconditionally trusts `request.shop` (and the other header-derived fields) as the tenant identity, forwarding it to the host application's handler: [4](#0-3) 

This is exactly the bug class from the external report generalized to an identity-binding check: a field that is *acted on* (the `shop` used as the tenant key delivered to the app) is *not covered* by the cryptographic check (the HMAC only covers the body). The broken equality is:

```
shop-header-value == shop-that-produced-this-signed-body
```

The gem enforces `hmac(body) == received_hmac`, but never enforces that `shop-domain header` is bound to that same signed body. Since Shopify computes a single app-wide webhook HMAC secret (`Context.api_secret_key`) shared across all shops that install the app, any legitimate merchant who installs the app can capture one of their own validly-signed webhook deliveries (same HMAC secret, same body) and resend it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header swapped to a victim merchant's domain. `HmacValidator.validate` still succeeds because it only checks the (unchanged) body against the (unchanged) HMAC; `Registry.process` then hands the attacker-chosen `shop` value to the host app's webhook handler as if it were authentic.

### Impact Explanation
Most Shopify host applications (e.g., via `WebhookMetadata#shop`) use the webhook's `shop` value as the tenant key to look up sessions/access tokens or to write data scoped to that shop. Because this gem provides no binding between the signed payload and the `shop` header, an attacker with a legitimate account for the shared app can forge webhook deliveries claiming to originate from any other merchant, leading to cross-tenant data injection/corruption in host applications that trust `WebhookMetadata#shop` as delivered by this gem. This matches the Critical "cross-tenant access" impact category, since the identity boundary (`shop` as tenant/session key) is crossed using only a webhook secret the attacker already legitimately possesses for their own store.

### Likelihood Explanation
Likelihood is high for any developer/merchant with access to the shared app (a normal, unprivileged merchant install): they need no leaked credentials, no access token, and no TLS interception — only a legitimately received webhook body/HMAC pair for their own shop, and the ability to send an HTTP POST with modified headers to the app's public webhook endpoint. `Registry.process` performs no additional binding check, so exploitation requires no gem or host-application misconfiguration beyond using the gem as documented.

### Recommendation
Bind the `shop` (and ideally `topic`) to the signed payload before trusting it as tenant identity — e.g., by including the shop identifier in `to_signable_string`, or by requiring host applications to cross-check the `shop` header against a value contained in/derived from the shop's own registered session before invoking the handler. At minimum, document loudly that `WebhookMetadata#shop` is not covered by the HMAC and must not be used as a sole tenant key without corroboration against a known/registered shop domain.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and captures a legitimate webhook delivery, e.g.:
```
POST /webhooks
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: <valid-hmac-of-body>
X-Shopify-Shop-Domain: attacker-shop.myshopify.com
X-Shopify-Webhook-Id: ...
Body: {"id": 123, ...}
```
2. Attacker resends the identical body and `X-Shopify-Hmac-Sha256` value, but replaces the header:
```
X-Shopify-Shop-Domain: victim-shop.myshopify.com
```
3. `ShopifyAPI::Utils::HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb:13) succeeds because it only checks the untouched body/HMAC pair.
4. `ShopifyAPI::Webhooks::Registry.process` (lib/shopify_api/webhooks/registry.rb:189-200) calls the app's handler with `shop: "victim-shop.myshopify.com"`, even though the payload never originated from that shop — demonstrating the header/body identity binding is not enforced by this gem.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
