### Title
Unbounded-depth `T::RuntimeCall::decode` in `pallet-hyper-fungible-token`'s `on_accept` allows stack-exhaustion crash on message delivery - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
CVE-2015-8985 is a glibc crash caused by unbounded internal stack growth while parsing an attacker-supplied structure. The structural analog here is SCALE-decoding an attacker-controlled, arbitrarily-nestable enum (`RuntimeCall`) without a recursion-depth limit, which can exhaust the native call stack and abort/panic the node process during transaction/message execution.

### Finding Description
`Pallet::<T>::on_accept` in `modules/pallets/hyper-fungible-token/src/module.rs` is the `IsmpModule` handler invoked when a cross-chain token-transfer `PostRequest` is delivered through `handle_incoming_message`/`HandlerV2` dispatch. After decoding the ABI `Message` body, if `message.data` is non-empty it decodes `SubstrateCalldata` and then decodes the embedded, fully attacker-controlled bytes directly into a `RuntimeCall`: [1](#0-0) [2](#0-1) 

This call uses plain `Decode::decode`, with **no recursion-depth bound**, unlike the sibling pallet `pallet-call-decompressor`, which decodes an equally attacker-controlled `RuntimeCall` using `decode_all_with_depth_limit(MAX_EXTRINSIC_DECODE_DEPTH_LIMIT, ...)` specifically to defend against this class of bug: [3](#0-2) [4](#0-3) 

The codebase's own regression test for `pallet-call-decompressor` demonstrates the underlying primitive: 1000 levels of `RuntimeCall::Sudo(Call::sudo{ call: Box<...> })` nesting is enough to trip the decode-depth guard, and the comment explicitly documents that this is a "stack exhaustion" vector: [5](#0-4) 

The HFT (`hyper-fungible-token`) `on_accept` path decodes the exact same `T::RuntimeCall` type from exact same category of attacker payload, but without any depth limit, meaning the protection that was deliberately added for the decompressor's entry point is missing on this second entry point into `RuntimeCall::decode`.

### Impact Explanation
`on_accept` is reached purely by delivering a cross-chain `PostRequest` from any source contract that is registered in `ContractToAsset` (a normal, permissionless token-bridge transfer with calldata attached) — no privileged relayer, governance, or admin action is required beyond a standard relayed message. A crafted `message.data` containing a deeply self-nested `RuntimeCall` (e.g., repeated boxed variants, mirroring the `pallet_sudo::Call::sudo` nesting shown in the existing regression test) can drive `Decode::decode` into unbounded recursion during message handling, exhausting the thread/call stack. In a Substrate/WASM runtime this manifests as an abort/trap during block execution — a full node crash / consensus-halting denial of service for any collator/validator that processes the malicious message, i.e., "a route unable to deliver messages" and worse, a chain-halting DoS reachable by an unprivileged token bridger.

### Likelihood Explanation
High reachability, but exploitation is gated on: (1) the destination pallet actually being configured with a `RuntimeCall` enum whose variants recurse (boxed inner calls, e.g. via `pallet_utility`/`pallet_sudo`/nested batch-style calls) — this is a runtime-configuration-dependent condition I could not fully confirm was present in the shipped `nexus`/`gargantua` runtimes, since a grep for `pallet_sudo`/`pallet_utility` in `parachain/**/runtime/**` returned no matches; and (2) the source-contract-to-asset mapping (`ContractToAsset`) already being configured to accept transfers from the attacker's contract, which is a normal integration step, not a privileged gate. Given the uncertainty about whether the deployed runtimes include recursively-nestable call variants, likelihood is assessed as Medium.

### Recommendation
Replace the unbounded `T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)` call in `on_accept` with `T::RuntimeCall::decode_all_with_depth_limit(MAX_DEPTH, &mut &*substrate_data.runtime_call)`, using the same (or a comparably small) depth bound already established in `pallet-call-decompressor`, and add a regression test mirroring `decompress_stack_exhaustion_poc` that submits an `on_accept` message with a deeply nested `runtime_call` payload and asserts a clean `Err` rather than a crash.

### Proof of Concept
1. Register a source EVM contract in `ContractToAsset` for some `local_asset_id` (standard bridge setup).
2. Construct an ISMP `PostRequest` `Message` (ABI-encoded per `Message::abi_decode`) whose `data` field is a `SubstrateCalldata` (SCALE-encoded) containing a `runtime_call: Vec<u8>` that is itself the SCALE encoding of a deeply self-nested `RuntimeCall` variant (analogous to the ~1000-deep `Sudo(sudo{ call: Box<...> })` chain used in `decompress_stack_exhaustion_poc` at [6](#0-5) ), if such recursive variants exist in the deployed runtime's `RuntimeCall`.
3. Deliver this as a normal relayed `PostRequest` through `handle_incoming_message`, reaching `Pallet::<T>::on_accept`.
4. `T::RuntimeCall::decode` at `modules/pallets/hyper-fungible-token/src/module.rs:189` recurses without a depth cap and exhausts the stack, aborting the runtime — versus the depth-limited decode in `call-decompressor` which cleanly returns `ErrorDecodingCall` for the identical nesting depth.
