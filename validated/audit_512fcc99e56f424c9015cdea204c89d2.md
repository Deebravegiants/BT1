## Title
Webhook `shop`, `topic`, `webhook-id`, and `api-version` are trusted from unauthenticated headers while the HMAC only covers the raw body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` proves nothing about the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers that `Registry.process` later trusts and hands to the app's webhook handler.

### Finding Description
`Request#to_signable_string` is defined as just `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes/compares the HMAC solely against `to_signable_string`: [2](#0-1) 

`Registry.process` gates on that HMAC check, then builds `WebhookMetadata` using `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` — all of which are pulled straight from HTTP headers, not from the signed payload: [3](#0-2) [4](#0-3) 

The identity binding that breaks is: `HMAC-validated(raw_body)` ≠ `shop header used by handler`. Because a merchant's `client_secret`/`api_secret_key` is shared across every shop that installs the same app, an unprivileged attacker can:
1. Install the target app on their own (attacker-controlled) shop — this is a normal, unprivileged action any internet user can take.
2. Receive a genuine webhook for their own shop, which carries a body and HMAC signed with the app's shared secret.
3. Replay that exact body/HMAC pair to the app's webhook endpoint, but swap the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header to reference a victim shop.
4. `HmacValidator.validate` still succeeds (body/HMAC pair untouched), so `Registry.process` calls the handler with `shop: <victim-shop>`, `body: <attacker's own data>`.

This lets an attacker forge/inject webhook events attributed to any other shop using the same app, since nothing in the request binds the header-derived shop/topic identity to the signed bytes.

### Impact Explanation
This crosses the tenant boundary explicitly called out as in-scope: an app relying on `WebhookMetadata#shop` (as documented/intended usage in `docs/usage/webhooks.md`) to route data per-tenant can be made to attribute attacker-controlled payloads to a victim shop, or to falsely trigger `shop/redact`, `app/uninstalled`, etc. handlers for a shop the attacker doesn't own — cross-tenant data injection/access via a credential the attacker legitimately possesses only for their own tenant.

### Likelihood Explanation
Requires only that the attacker be able to install (or otherwise be a legitimate merchant of) the target app to obtain one authentic HMAC/body pair, then replay it with modified headers to the app's public webhook endpoint — no access to the app's `client_secret`, no privileged account, and no interaction with the victim shop is required.

### Recommendation
Bind the tenant/topic identity into the signed material, or otherwise avoid trusting header values that aren't covered by the HMAC:
- Include `shop`, `topic`, `webhook_id`, and `api_version` in `to_signable_string` (or verify them against fields embedded in the JSON body where Shopify includes them), and/or
- Cross-check `request.shop` against the shop associated with the currently active session/webhook registration before dispatching to a handler.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com`; app subscribes attacker's shop to `orders/create`.
2. Shopify sends webhook: body `B`, `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker resends the identical `B` and HMAC to the same endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns true (body unchanged). `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the handler with `shop: "victim.myshopify.com"`, causing the app to process attacker-supplied data as though it originated from the victim tenant.
