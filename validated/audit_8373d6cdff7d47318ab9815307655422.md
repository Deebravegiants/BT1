### Title
Unrestricted swap-route contracts can execute token transfers under the caller’s authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` forward caller-supplied opaque route bytes to the configured router without protocol-side venue restrictions. [1](#0-0)  A malicious route venue can therefore run contract code below the caller’s root authorization and add unexpected token-transfer children to that authorization tree. [2](#0-1) 

### Finding Description
`swap_collateral` authorizes the caller, verifies account ownership, and passes the supplied `swap` bytes into the withdrawal-and-swap path. [3](#0-2)  The shared swap path snapshots balances, authorizes only one exact input transfer from the controller to the configured router, and invokes `execute_strategy` with the opaque route. [4](#0-3)  The helper’s authorization only constrains the controller’s own `token_in.transfer(controller, router, amount)` invocation and does not constrain unrelated transfers requested deeper in the transaction. [5](#0-4)  Because route venue addresses are caller-controlled and unallowlisted, an attacker can provide a route whose venue contract calls a token contract with `transfer(victim, attacker, amount)`. [6](#0-5)  Simulation records that transfer as a child of the victim’s `swap_collateral` authorization, and it executes if the victim signs the poisoned tree. [7](#0-6) 

### Impact Explanation
A successful malicious route can steal wallet tokens unrelated to the collateral being swapped, exceeding the routed amount and bypassing the controller’s measured-output and solvency checks. [8](#0-7)  The regression demonstrates a victim losing an entire unrelated token balance while still receiving the expected swap output and completing `swap_collateral`. [9](#0-8) 

### Likelihood Explanation
The attacker cannot invoke another user’s protected account operation without that user’s authorization, so exploitation requires the victim to submit or sign an attacker-influenced route. [3](#0-2)  The likelihood is still material because ordinary integrations consume opaque `routeXdr`, simulation presents the malicious transfer inside the same authorization tree, and neither positive swap output nor final account health reveals the unrelated wallet transfer. [2](#0-1) 

### Recommendation
Enforce a protocol-controlled allowlist of venue contracts and token addresses before executing a route, or change the route format so the router can invoke only registered adapters and verified venue addresses. [10](#0-9)  Clients should additionally reject any signed authorization tree except the expected input transfer, but wallet-side validation should not be the only defense because the protocol currently permits arbitrary route-selected code below caller authorization. [5](#0-4) 

### Proof of Concept
1. Deploy `RogueHopPool` with `(victim, unrelated_token, attacker, victim_balance)`. [11](#0-10) 
2. Construct route bytes naming that contract as a hop venue while retaining a fair `token_out` payment. [12](#0-11) 
3. Have the victim invoke `swap_collateral(victim, account_id, current_usdc, amount, new_eth, malicious_route)`. [13](#0-12) 
4. The controller authorizes the expected input transfer and calls `execute_strategy(controller, amount, malicious_route)`. [1](#0-0) 
5. During the route, the malicious pool calls `unrelated_token.transfer(victim, attacker, victim_balance)`. [14](#0-13) 
6. Simulation attaches that token transfer to the victim’s `swap_collateral` authorization; if the victim signs that recorded tree, the swap succeeds and the victim’s unrelated wallet balance reaches the attacker. [15](#0-14)

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
