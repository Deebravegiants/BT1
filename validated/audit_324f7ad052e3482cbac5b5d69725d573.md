## Analysis

The external report's core bug class is: a security-critical field is *acted upon* by the code but is *not covered by the integrity check* that gates that action (`msgHash`/action byte not actually inside the HMAC-equivalent payload span that was verified). The directly analogous pattern in this Ruby gem is the webhook verification path, where the `shop` identity is trusted from an HTTP header that is never included in the HMAC-signed bytes.

### Root cause

`ShopifyAPI::Webhooks::Request` reads the `shop` from a raw header, but its `to_signable_string` — the bytes that actually get HMAC-verified — is only the raw request body: [1](#0-0) [2](#0-1) 

`HmacValidator.validate` computes and compares the signature only over `to_signable_string` (the body), using the app's single global `Context.api_secret_key`: [3](#0-2) 

`Registry.process` checks the HMAC and then unconditionally hands `request.shop` to the app's handler as the authenticated tenant identity, with no cross-check that `shop` was bound to the verified bytes: [4](#0-3) 

Because `api_secret_key` is a single app-wide secret shared across every shop that installs the app (there is no per-shop secret in this gem), any merchant who legitimately installs the app can capture a validly-signed `(body, hmac)` pair for their own store's webhook, then replay it to the app's webhook endpoint with the `x-shopify-shop-domain`/`shopify-shop-domain` header swapped to a victim shop's domain. `HmacValidator.validate` still succeeds because the digest never covered the shop header — only the body. `Registry.process` then invokes the handler with `WebhookMetadata` carrying the attacker's forged `shop` value: [5](#0-4) 

This breaks the intended identity binding: `shop value trusted by the handler == shop value that produced the valid HMAC`. In reality, the HMAC only proves "some shop that has installed this app produced this body," not "this specific `shop` header is authentic."

### Title
Webhook shop-domain identity is not bound to the HMAC-verified bytes, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body, while `shop` is read from an unauthenticated header. `Registry.process` verifies the HMAC and then trusts `request.shop` as the tenant identity passed to the app's webhook handler, without binding `shop` to the verified content.

### Finding Description
The gem's webhook flow validates authenticity via `Utils::HmacValidator.validate(request)`, which hashes only `@raw_body` [2](#0-1) . The `shop` accessor is derived purely from the `shop-domain`/`x-shopify-shop-domain` header [1](#0-0) , which is not part of the signed payload. Since `Context.api_secret_key` is a single secret shared by the app across all installing shops (it is not shop-specific), any merchant who installs the app can obtain a legitimately signed `(body, hmac)` pair for their own webhook deliveries, then resend that exact body/hmac pair to the app's webhook endpoint with the shop-domain header changed to any other tenant. `HmacValidator.validate` still passes because it never inspected the shop header, and `Registry.process` forwards the (attacker-chosen) `shop` value straight to the registered handler [4](#0-3) . Host applications built on top of this gem's documented API — that key their tenant lookups, deduplication, or authorization decisions off `WebhookMetadata#shop` because it "passed HMAC validation" — will process attacker-controlled data attributed to the wrong tenant.

### Impact Explanation
This crosses a tenant boundary: an attacker who is a legitimate but unprivileged tenant (any merchant who installs the app) can cause the app to process forged data under a victim shop's identity, since the identity field is unauthenticated relative to what was actually cryptographically verified. This matches the Critical impact category of cross-tenant access, since the shop identity binding the request is not what the signature verifies.

### Likelihood Explanation
Any user able to install the app on a shop they control (a normal, unprivileged action, no special credentials needed beyond what any merchant already has) can capture a real webhook delivery for their own store and replay it with a modified shop header to the same public webhook endpoint. No access to `api_secret_key`, tokens, or the app's infrastructure is required.

### Recommendation
Bind `shop` to the verified bytes: include the shop-domain header value inside the HMAC-signable string (or otherwise cryptographically bind it), or require callers/handlers to cross-check `request.shop` against a shop-specific secret/session before trusting it as the tenant identity. At minimum, document that `WebhookMetadata#shop` is not itself authenticated by the HMAC and must not be used as a sole tenant key.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a legitimate webhook, e.g. `orders/create`.
2. Attacker captures the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent for that delivery (valid signature over that body, computed with the app's single shared secret).
3. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [6](#0-5) , which succeeds because it only checks the body's HMAC.
5. The handler receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"` and attacker-controlled body content, even though the signature never certified that shop value [5](#0-4) .

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
