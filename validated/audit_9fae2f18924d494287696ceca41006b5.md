### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) header is trusted for tenant identification while the HMAC only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then dispatches the handler using a `shop` value taken from an HTTP header that is never included in that HMAC computation. This is the same class of bug as the reported `SmartVaultV3` issue: one value (`euroCollateral()`, built from `tokenToEurAvg()`) is used for the security-relevant check while a *different, unbound* value (`tokenToEur()`) is used for the actual state-changing action. Here, the HMAC verifies `raw_body` but the tenant-identifying `shop` field used by every downstream `WebhookHandler` is taken from an unauthenticated header.

### Finding Description
`Utils::HmacValidator.validate` computes/verifies the signature over `verifiable_query.to_signable_string`. For webhook requests, this is defined as: [1](#0-0) 

i.e. the HMAC is computed only over `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` values are all pulled straight from HTTP headers with no HMAC coverage: [2](#0-1) 

`Registry.process` validates the HMAC and, if it passes, immediately builds `WebhookMetadata` — which carries `shop` — from these unauthenticated header values and hands it to the app-supplied handler: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` field with no relation to any signed value: [4](#0-3) 

The identity binding that is broken (using the terms of the rules) is:
`shop_bound_by_hmac == shop_acted_on_by_handler`
In this code, the left side does not exist at all — no header is bound by the HMAC — so the equality trivially fails: the gem verifies `HMAC(raw_body)` but *acts* on `shop` (and `topic`/`webhook_id`) taken from headers outside that verification.

### Impact Explanation
Any unprivileged internet user who can obtain one genuinely-signed webhook body+HMAC pair for topic X (e.g., by installing a free trial of the target app on their own shop, or observing/replaying any real Shopify webhook delivered to an endpoint they control) can resubmit that exact `raw_body`/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value naming a *different* shop. Because `HmacValidator` only checks `raw_body`, the forged request passes validation, and `Registry.process` calls the app's handler with `WebhookMetadata#shop` set to the attacker-chosen shop. Any app that uses `data.shop` to look up per-tenant session/store state (the documented and expected usage pattern, per `docs/usage/webhooks.md`) will process the replayed payload under the wrong tenant's identity — i.e. cross-tenant data injection/processing. This matches the "cross-tenant access" Critical-impact category in the rules, since the HMAC's job is exactly to bind body-and-source-shop together and it does not.

### Likelihood Explanation
The attack requires only network access to the target app's webhook endpoint plus one legitimately-obtained body/HMAC pair (which is not secret — HMACs and bodies from a self-owned trial shop are freely available to any developer/attacker). No access token, `client_secret`, or privileged credential is needed, satisfying the "unprivileged internet user" requirement in the rules. This is a straightforward, low-skill request-forgery, not a timing or volatility-dependent condition.

### Recommendation
Include the tenant-identifying header (`shopify-shop-domain`/`shop-domain`) — and ideally `topic` and `webhook-id` — inside the signed material that `HmacValidator` verifies, or otherwise cryptographically bind the shop domain to the payload (e.g., verify it against a value embedded in the JSON body, or require callers to pass the shop obtained from a source that Shopify itself authenticates, such as the registered webhook subscription lookup) before constructing `WebhookMetadata` and invoking the handler.

### Proof of Concept
1. Attacker installs the app on their own store `attacker-shop.myshopify.com`, triggers a webhook (e.g. `orders/create`), and captures the raw POST body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (computed with the app's `client_secret`, which the attacker never needs to know — Shopify computed it for them).
2. Attacker replays the exact same `B`/`H` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H` — validation passes (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's own order data>, ...)` and calls the app's handler (`lib/shopify_api/webhooks/registry.rb:188-199`), causing the app to process attacker-controlled data as if it belonged to `victim-shop.myshopify.com`.
