### Title
Webhook `shop-domain` Header Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The gem's webhook verification computes the HMAC signature over the raw request body only, while the `shop-domain` (tenant identifier) header is read unverified and handed to the app's webhook handler as the authoritative tenant. Any party capable of sending an HTTP request to the app's public webhook endpoint (e.g. a merchant who has genuinely installed the app on their own shop, receiving legitimate webhook deliveries with valid HMACs for their own body content) can replay a valid `body + hmac` pair while substituting an arbitrary `x-shopify-shop-domain`/`shopify-shop-domain` header, since that header is never part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

`shop` is read straight from an HTTP header with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` verifies the signature purely against `to_signable_string` (the raw body): [3](#0-2) 

`ShopifyAPI::Webhooks::Registry.process` only checks this body-only HMAC, then trusts `request.shop` (an unauthenticated header) as the tenant identifier passed to the application's handler: [4](#0-3) 

The identity binding that is broken is:

`shop authenticated by HMAC` == `shop used by the handler to select the tenant/session`

but in reality the HMAC binds only the body bytes, and the `shop` value used for tenant selection comes from an entirely separate, unauthenticated header. Because the same `api_secret_key` is shared across every shop that has installed the app, a body+HMAC pair that is valid for one tenant's webhook delivery is *also* a valid HMAC for that identical body when replayed with a different `shop-domain` header — the signature check has no way to detect the substitution.

### Impact Explanation
This is a cross-tenant confusion vector: an attacker who legitimately operates (or has ever received webhook traffic from) one shop under a multi-tenant app can capture a genuine `raw_body`/`hmac` pair and re-POST it directly to the app's public webhook endpoint with the `shop-domain` header changed to a victim shop's domain. `Registry.process` will accept the HMAC (it never validated the header) and dispatch `WebhookMetadata` carrying the victim's shop identifier together with attacker-chosen body content to the app's handler. Depending on how the host application persists webhook data keyed by `shop`, this enables writing attacker-influenced data into another tenant's records — a cross-tenant integrity/access violation.

### Likelihood Explanation
Webhook endpoints are plain public HTTP endpoints with no additional authentication besides the HMAC; any internet user can send a POST to them. Obtaining a valid `body`+`hmac` pair requires only being a legitimate (even free/trial) merchant of the app, receiving one real webhook delivery for their own store — no possession of `api_secret_key` or any victim credentials is required. This is a low-effort, unprivileged attack path.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook-id`) header into the signed material, or otherwise cryptographically tie the header value to the verified payload before it is trusted as the tenant identifier — e.g., include the header value in the string that is HMAC-verified in `Webhooks::Request#to_signable_string`, or have `Registry.process` cross-check `request.shop` against a shop value embedded in the (HMAC-covered) body/topic query when available.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and lets a real webhook (e.g. `orders/create`) fire, capturing the raw POST: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the shared `api_secret_key`), and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker crafts a new POST to the same webhook endpoint with the *same* body `B` and *same* `hmac` header `H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (only `B`) — this matches `H`, so validation passes.
4. `request.shop` returns `"victim.myshopify.com"` (unauthenticated header), and `WebhookMetadata.new(shop: request.shop, body: request.parsed_body, ...)` is dispatched to the app's handler as if it were a legitimate event belonging to the victim shop, using attacker-supplied body content.
