## Finding: Unchecked `U256`→`u64` Conversion in SP1 BEEFY Proof Decoding Causes a Panic-DoS on Crafted Proof Input

### Title
Unrestricted conversion of attacker-controlled ABI-decoded proof fields causes a runtime panic (DoS) — (File: `evm/rust/src/conversions.rs`)

### Summary
`CVE-2016-1182` is a class of bug where a component fails to properly restrict/validate configuration-like input before processing it, letting crafted input crash or corrupt the handler. The Hyperbridge analog is in the SCALE/ABI proof conversion layer used by the BEEFY SP1 consensus path: `U256` fields decoded from an attacker-supplied ABI proof are converted to `u64`/native integers with `.expect(...)` rather than a checked, error-returning conversion, so a crafted proof value outside `u64` range panics the runtime.

### Finding Description
`modules/pallets/beefy-consensus-proofs/src/lib.rs::verify_and_apply` accepts a raw proof byte-blob, ABI-decodes it into `ismp_abi::sp1_beefy::SP1Beefy::SP1BeefyProof`, and converts it into the internal SCALE type via `.into()`: [1](#0-0) 

That `Into` implementation lives in `evm/rust/src/conversions.rs` and blindly `.expect()`s the conversion of two attacker-supplied `U256` values (`blockNumber`, `validatorSetId`) into `u64`: [2](#0-1) 

The sibling `RelayChainProof → MmrProof` conversion in the same file has the identical pattern for `leafIndex`: [3](#0-2) 

Because the proof bytes are attacker/relayer-controlled input to `verify_and_apply` (submitted before any cryptographic verification takes place — the conversion runs prior to calling `handlers::handle_incoming_message`), a submitter can set `commitment.blockNumber` (or `validatorSetId`, or `latestMmrLeaf.leafIndex`) to a `U256` value greater than `u64::MAX`. The `.try_into().expect("block number out of bounds")` call then panics instead of returning a typed error.

This is the same bug class as CVE-2016-1182: input that should be validated/restricted before being fed into processing logic is instead accepted as-is, and a crafted value causes abnormal termination of the handler (Struts: XSS/DoS via unrestricted Validator config; Hyperbridge: runtime panic via unrestricted numeric field in a proof).

The codebase's own recent hardening history shows this exact bug class has already been fixed in several sibling locations — e.g. the BEEFY MMR leaf-index panic (`modules/consensus/beefy/verifier/src/lib.rs`), the GRANDPA header-lookup panic, the Pharos proof-depth panic, and the `as_utf8_string` RPC panic that "crashed the production node": [4](#0-3) [5](#0-4) 

But the `evm/rust/src/conversions.rs` conversions for `Sp1BeefyProof`/`MmrProof` were not brought in line with this pattern.

### Impact Explanation
A panic inside on-chain execution triggered by an unsigned/permissionless proof submission halts block production or aborts the extrinsic execution context, denying the ability to deliver further BEEFY/SP1 consensus updates and, transitively, any ISMP messages that depend on that consensus client's liveness (a "route unable to deliver messages" condition). This satisfies the required impact bar of the prompt.

### Likelihood Explanation
High: the field is a raw `U256` decoded straight from attacker-supplied calldata/proof bytes with no upstream range check, and only a single out-of-range integer is needed to trigger the panic. No special privileges are required — this is exactly the kind of "single relayed proof" input path the validation rules call out as in-scope.

### Recommendation
Replace all `.expect(...)` conversions of proof-derived `U256` fields (`blockNumber`, `validatorSetId`, `leafIndex`) in `evm/rust/src/conversions.rs` with checked conversions that return a typed `Error` (e.g. `try_into().map_err(|_| Error::...)?`), consistent with the fix pattern already applied in `modules/consensus/beefy/verifier/src/lib.rs` and `modules/utils/serde/src/lib.rs`.

### Proof of Concept
1. Craft an SP1 BEEFY proof blob where `SP1BeefyProof.commitment.blockNumber` (or `validatorSetId`) is set to a `U256` value `> u64::MAX`.
2. Submit it as the `proof` argument via the reachable entry point that invokes `beefy-consensus-proofs::verify_and_apply` (e.g. through the relayer-facing extrinsic that wraps this call).
3. `ismp_abi::sp1_beefy::SP1Beefy::SP1BeefyProof::abi_decode_params` succeeds (ABI decoding places no upper bound on the numeric value).
4. The subsequent `.into()` conversion executes `value.commitment.blockNumber.try_into().expect("block number out of bounds")`, which panics because the value doesn't fit in `u64`.
5. The panic propagates out of the dispatchable before any cryptographic proof verification occurs, aborting execution.

Note: I was unable to fully trace, within the available iterations, the exact top-level dispatchable/extrinsic name that calls `verify_and_apply` (the code shown establishes it is reachable from a permissionless proof-submission entry point in `pallet-beefy-consensus-proofs`, but I could not confirm the call's origin type — unsigned vs. signed-but-permissionless — before running out of tool calls). A Devin session with full repository access would be needed to confirm the exact dispatch origin and produce a complete end-to-end PoC transaction.
