### Title
Webhook `shop` identity is not covered by HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (tenant identifier) exclusively from the `shop-domain` HTTP header, while the HMAC signature that `Registry.process` verifies only covers the raw request body. Because the tenant-identifying field is not part of the signed content, an attacker who possesses one valid, signed webhook payload (e.g., from their own Shopify store) can replay it against the host application while swapping the `shop-domain` header to any other tenant. The library reports this as an authenticated, HMAC-verified webhook for the victim shop, breaking the equality `shop_bound_by_hmac == shop_used_for_tenant_identification`.

### Finding Description
`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` and verifies the HMAC against that string: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body: [2](#0-1) 

But `shop` — the value used to identify which tenant the webhook belongs to — is read straight from the `shop-domain` HTTP header, which is never included in the signed material: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then dispatches to the handler using `request.shop`, `request.topic`, and `request.parsed_body`, none of which are cryptographically bound to each other except the body content itself: [4](#0-3) 

Because `hmac-sha256` is computed by Shopify over the JSON body alone (as documented and reflected in the tests), and the `shop-domain`/`topic` headers travel unsigned, the equality the gem should be enforcing — `hmac_signed_content == (shop, topic, body)` — actually only holds for `body`. An attacker who owns Shop A (or has otherwise obtained one valid webhook body+HMAC pair, which is trivial to obtain as any unprivileged store owner) can resend the exact same body/HMAC pair to the target host application's webhook endpoint while setting `shop-domain` to Shop B. `Utils::HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` proceeds to invoke the handler with `shop: "shop-b.myshopify.com"` and attacker-controlled body content, exactly mirroring the reported bug class of a value ("stackId"/tenant reference) that is acted upon but not covered by the authorization/signature check.

### Impact Explanation
This allows any unprivileged store owner (or anyone who can trigger/capture one legitimate webhook and its HMAC for their own shop) to inject attacker-controlled data into another merchant's tenant context inside the host application, since the library's webhook processing pipeline treats `request.shop` as trustworthy purely because the HMAC "passed." This is a cross-tenant identity-binding break consistent with the Critical "cross-tenant access" impact category — a host app relying on `ShopifyAPI::Webhooks::Request#shop`/`Registry.process` for tenant attribution can be made to apply Shop A's webhook payload to Shop B's data.

### Likelihood Explanation
Likelihood is High: the attacker only needs a single valid webhook (readily obtainable for their own store, e.g., by triggering `orders/create` or any subscribed topic) and a way to POST to the app's webhook endpoint with modified headers — no access token, `api_secret_key`, or privileged account is required. The header check in the constructor only verifies presence of the header, not that it is bound to the signed body.

### Recommendation
Include the `shop-domain` (and ideally `topic`) header values in the signable string used for webhook HMAC verification, or otherwise cryptographically bind the tenant identifier to the signature (e.g., verify `shop` against a value derived from the signed payload or from the registered webhook's known shop) before dispatching to handlers in `Registry.process`.

### Proof of Concept
1. As the owner of `attacker-shop.myshopify.com`, trigger a subscribed webhook topic (e.g. `orders/create`) so the app receives a valid request with headers `x-shopify-hmac-sha256`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, and body `B`.
2. Capture that request (`hmac = HMAC(secret, B)`, valid because `to_signable_string` only returns `B`).
3. Resend the identical body `B` and `hmac` to the app's webhook endpoint, but replace the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) returns `true` because it only checks `B` against `hmac`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the handler with `shop: "victim-shop.myshopify.com"`, causing the host application to process attacker-controlled data under the victim's tenant context.

          received_signature = verifiable_query.hmac
