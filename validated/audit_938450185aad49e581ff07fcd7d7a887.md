### Title
Solver venue pricing trusts manipulable Uniswap V4 spot price (`sqrtPriceX96`) with only a static deviation guard, allowing sandwich extraction of solver funds - (File: `sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts`)

### Summary
The Hyperbridge intents solver ("simplex") prices cross-asset intent legs against Uniswap V4 pools using the pool's raw current-tick spot price, read live from `slot0`/`getSlot0` via `UniswapV4LiquidityState.refresh()`, and never a time-weighted average. The only defense is a static `maxDeviationBps` reference-price guard, which bounds *where* the price can be relative to a fixed reference but does nothing to prevent a single-block manipulation from moving the spot price anywhere within that band. This is the same bug class as the reported `getQuoteAtTick()`/`slot0()` manipulation issue: an unprivileged actor can push the pool's instantaneous price with a large swap (optionally flash-loaned) immediately before the solver quotes/fills an intent, extracting value from the solver.

### Finding Description
`UniswapV4LiquidityState.refresh()` fetches `getSlot0` for each configured pool and stores `sqrtPriceX96`/`tick` directly as live state: [1](#0-0) 

This spot price is fed straight into `UniswapV4FundingPlanner.computeDirectPoolPriceUsd`, which derives the exotic token's USD price directly from `sdkPool.token0Price`/`token1Price` (both derived from `sqrtPriceX96`) — the highest-liquidity pool's *current* price, not a TWAP: [2](#0-1) 

The documented flow confirms this price is used to set the solver's bid/ask rate for cross-asset pairs, and that the only mitigation, `checkPriceGuard`, only rejects fills whose spot price is more than `maxDeviationBps` away from a *static* `referencePrice` — it does not detect or defend against manipulation *within* that band, nor does it account for the fee/impact of sourcing inventory through the same pool: [3](#0-2)  and [4](#0-3) .

This is structurally identical to the reported issue: the Real-Wagmi `Factory.getQuoteAtTick()` read `IUniswapV3Pool.slot0()` (spot tick) with no TWAP protection; here the solver's `UniswapV4LiquidityState`/`UniswapV4FundingPlanner` read `slot0`/`getSlot0` (spot `sqrtPriceX96`) with no TWAP protection, the difference being a static-band guard rather than none at all — which caps the damage per manipulation but does not eliminate the vulnerability class.

### Impact Explanation
An attacker who observes an intent about to be filled by the solver (or who front-runs the solver's own price refresh right before it plans/executes a fill) can swap in the underlying Uniswap V4 pool to move `sqrtPriceX96` to the edge of the allowed `maxDeviationBps` band in the direction favorable to the attacker. The solver then computes `computeDirectPoolPriceUsd` from this manipulated tick and fills the intent order at a distorted rate, transferring value from the solver's escrowed liquidity to the attacker (classic sandwich against an oracle-dependent quoting bot). Because the solver's Uniswap V4 positions are the funding source for real cross-chain fills, this is a direct path to loss of solver funds, which is the resource ultimately backing user cross-chain intents.

### Likelihood Explanation
Moving a spot price is cheap and requires only a single swap transaction (potentially flash-loaned) in the target pool, and the solver's `refresh()` is called immediately before both quoting (`getExoticTokenPrice`) and before planning a withdrawal (`planWithdrawalForToken`), so the window between "read slot0" and "act on it" is only the solver's processing/relay latency, not a mempool-safe TWAP window. The `checkPriceGuard`/`maxDeviationBps` reference bounds the maximum exploitable deviation per fill but does not require the manipulation to be undone, and repeated or larger fills against the same pool while it's held at the edge of the band compound the extractable value.

### Recommendation
Replace or supplement the direct `slot0`/`getSlot0` spot price with a Uniswap V4 (or V3) time-weighted average price (TWAP) over a meaningful window before using it in `computeDirectPoolPriceUsd`, and tighten `checkPriceGuard` to compare against the TWAP rather than (or in addition to) a static `referencePrice`. Consider also factoring in the execution cost/fee tier when sizing fills sourced from the same pool that priced them, since `computeLegPolicyOutput` currently extends the raw mid linearly with no size/impact term.

### Proof of Concept
1. Configure a solver with a `[vault.uniswapV4]` pair priced against a pool with modest liquidity (per docs, pool pricing is used whenever `bidPriceCurve`/`askPriceCurve` are omitted).
2. Attacker submits a large swap (optionally via flash loan) against that Uniswap V4 pool, shifting `sqrtPriceX96`/tick toward the edge of the configured `maxDeviationBps` band around `referencePrice`.
3. Attacker (or an unrelated user) submits an intent order that the solver fills using `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd`, which reads the manipulated `slot0` state via `UniswapV4LiquidityState.refresh()` [5](#0-4) .
4. `checkPriceGuard` passes because the manipulated price is still within the static band, and the solver plans/executes a fill (`planWithdrawalForToken`) priced off the manipulated tick, crediting the attacker more than the true market rate.
5. Attacker reverses the initial swap, netting the difference at the solver's expense.

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

	/**
	 * Computes the USD price of the non-stable token in a pool.
	 * Returns null if neither currency is USDC/USDT on this chain.
	 */
	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

```
resolveLegRates(...)

    -> venuePriceMemo() -> getVenueUsdPrice(chain, token1)
         -> UniswapV4FundingPlanner.getExoticTokenPrice
              picks the position with the largest pool liquidity
              -> computeDirectPoolPriceUsd -> sdkPool.token0Price / token1Price
    -> checkPriceGuard(...)   reject if outside maxDeviationBps of the static reference
    -> rate = 1 / venueUsd
  otherwise -> the pair's ask/bid curve at the leg's notional
```

`computeDirectPoolPriceUsd` returns the **raw pool mid** derived from `sqrtPriceX96`. The pool's
fee tier is read and stored on the hydrated position (`pos.fee`) but never applied to the price,
and there is no size or impact term — `computeLegPolicyOutput` extends the mid linearly across the
whole priced quantity. `checkPriceGuard` is the only defense on this path, and it checks deviation
from a static reference, not execution cost. A venue-priced pair that has to swap through its own
pool to source inventory pays a fee tier it never quoted against.

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```
