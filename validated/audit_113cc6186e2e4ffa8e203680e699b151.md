### Title
Unbounded `order.inputs`/`order.output.assets` array length in IntentGatewayV2 enables gas-exhaustion DoS that permanently freezes escrowed funds - (File: evm/src/apps/intentsv2/IntentsBase.sol, evm/src/apps/IntentGatewayV2.sol)

### Summary
`placeOrder()` in `IntentGatewayV2.sol` accepts an `Order` whose `inputs` and `output.assets` arrays have no upper-bound check — only `order.inputs.length == 0` is rejected. Every downstream function that must process the order (`fillOrder` → `_fillSameChain`/`_fillCrossChain`, `cancelOrder` → `_cancelSameChain`/`_cancelFromSource`/`_cancelFromDest`, and `_withdraw`) iterates over these attacker/user-controlled arrays with `for` loops whose cost scales linearly with array length, exactly mirroring the HiFi `BalanceSheetV2` "unbounded collateral" bug class: a single unprivileged transaction (`placeOrder`) can create state that later causes any function depending on it to run out of gas, permanently freezing the escrowed funds.

### Finding Description
In `placeOrder()` [1](#0-0) , the only length validation is:
```solidity
if (order.inputs.length == 0) revert InvalidInput();
```
There is no `maxInputs`/`maxOutputs` cap analogous to `Fintroller.maxBonds` in the HiFi report. The function then loops over `order.inputs` (and `order.output.assets`, `order.predispatch.assets`) multiple times performing external calls (`safeTransferFrom`, `balanceOf`) per element [2](#0-1) .

Because escrow is credited per-token in a mapping (`_orders[commitment][token]`), fulfilling or cancelling the order later requires iterating that same unbounded list again:

- `_fillSameChain`/`IntrinsicIntents.sol` fill loop iterates `order.inputs`/`order.output.assets` per output pair, doing ERC20 transfers per iteration [3](#0-2) .
- `_cancelSameChain` iterates all `order.inputs` to build the refund list [4](#0-3) .
- `_cancelFromSource` (cross-chain cancel path) iterates `order.inputs` to validate existence before dispatching the GET request [5](#0-4) .
- `_withdraw`, the terminal step for both fill-settlement and refund/cancel-settlement (called from `onAccept` for `RedeemEscrow`/`RefundEscrow`), loops over `body.tokens` doing a `safeTransfer` per token [6](#0-5) .

A user can call `placeOrder` with an `inputs` array (and matching `output.assets`) containing hundreds or thousands of distinct token entries (duplicates across inputs are rejected, but `output.assets`/`inputs` can still be sized arbitrarily large with unique dummy token addresses since there is no cap on distinct tokens, only a check against zero-amount/duplicate). Every one of those loops performs at least one `SLOAD`/`SSTORE` and, in most paths, an external call per element. Once the array is large enough, every function that must fully process the order (`fillOrder`, `cancelOrder`, and the `onAccept` `_withdraw` triggered by Hyperbridge settlement/refund messages) will exceed the block gas limit and revert deterministically, regardless of who calls it or how much gas they supply.

### Impact Explanation
This is a direct on-chain analog to the reported bug class: unbounded iteration driven by a value an unprivileged party fully controls, reachable via a single dispatched transaction (`placeOrder`), causing functions that must succeed to run out of gas. Concretely:
- The order's escrowed input tokens can never be released to a solver (`fillOrder`/`_withdraw` always reverts on OOG) and can never be refunded via `cancelOrder`/`_cancelSameChain`/`_withdraw`.
- For cross-chain orders, the Hyperbridge relayed `onAccept` call (RedeemEscrow/RefundEscrow) for that commitment will also revert every time it's replayed, since `_withdraw` iterates the same oversized `body.tokens` list — meaning the settlement message can never be delivered/executed even though authorized and correctly proven.
- The escrowed tokens (any user funds transferred in at `placeOrder`) become permanently locked in the `IntentGatewayV2` contract with no recovery path — meeting the "permanent freezing of funds" and "route unable to deliver messages" bars in the validation criteria.

This is a self-inflicted DoS from the perspective of the order creator's own funds, but it is also a griefing/DoS vector against the protocol's liveness guarantees for that class of orders, and it demonstrates the same missing invariant (no upper bound on iterable collection size controlled by an unprivileged caller) that the cited HiFi report flags as Medium/High severity.

### Likelihood Explanation
Likelihood is High for triggering the condition (any address can call `placeOrder` with an arbitrarily long `inputs`/`output.assets` array — no permission or governance gate), though the attacker/victim is generally the order creator themselves (self-DoS) since they bear the gas cost of `placeOrder` growing with array size too. The more severe angle is that this also DoSes the Hyperbridge-relayed settlement callback (`onAccept`) for cross-chain orders of this shape, which cannot be worked around by any relayer, since `_withdraw`'s loop bound is fixed by the order's own array length at creation time and cannot be split into smaller batches by an external caller.

### Recommendation
Add an explicit upper bound (e.g., `MAX_ORDER_ASSETS`) checked in `placeOrder()` against `order.inputs.length`, `order.output.assets.length`, and `order.predispatch.assets.length`, sized so that the worst-case gas cost of the largest per-order loop (`_withdraw`, fill loop, cancel loop) stays comfortably under the block gas limit with margin for gas-price volatility. This mirrors the `maxCollaterals` mitigation adopted in the referenced HiFi fix (commit b6a9a63) and should be validated at order placement time so that no order can ever be created that later becomes unprocessable.

### Proof of Concept
1. Attacker (or any user) crafts an `Order` with, e.g., 2,000 unique dummy ERC20 token entries in `order.inputs` (each with `amount = 1`) and a matching 2,000-entry `order.output.assets` list.
2. Calls `placeOrder(order, graffiti)` on `IntentGatewayV2`. This succeeds because there is no length cap — only the loops in `placeOrder` itself execute (still within gas limits since it's a single top-level tx that can be sized to just barely fit).
3. Later, when a solver attempts `fillOrder(order, options)` or the user attempts `cancelOrder(order, options)` (same-chain path calling `_cancelSameChain` → `_withdraw`), the transaction must iterate all 2,000 `body.tokens` entries doing an `SLOAD`, `SSTORE`, and `IERC20.safeTransfer` per entry — this exceeds the block gas limit and reverts unconditionally.
4. For a cross-chain order, the equivalent failure occurs inside `onAccept` when Hyperbridge relays the `RedeemEscrow`/`RefundEscrow` message and it hits the same `_withdraw` loop — the message can never be successfully processed no matter how it's retried, and the escrowed tokens remain stuck in the contract indefinitely.

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
