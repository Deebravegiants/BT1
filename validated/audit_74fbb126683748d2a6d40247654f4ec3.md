### Title
`ConnectedOrigins.setAutoApprove`/`add`/`connect` accept an attacker-supplied `origin` with no verification that it matches the caller's real origin - (File: `features/connected-origins/module/connections.js`)

### Summary
The `connected-origins` module manages the list of dApp origins a user has authorized and whether they are auto-approved for signing requests. Its public API (`connectedOriginsApi`, exposed over the extension/SDK RPC surface) takes `origin` as a plain caller-supplied string parameter rather than deriving it from the trusted transport/sender context. Any connected dApp can therefore call `setAutoApprove`, `add`, `connect`, `setFavorite`, or `updateConnection` while passing a *different* origin string than its own, mutating trust/auto-approve state for another website's connection.

### Finding Description
`ConnectedOrigins#setAutoApprove` writes the `autoApprove` flag keyed purely by the `origin` argument, with no check that the RPC caller *is* that origin: [1](#0-0) 

The same pattern - trusting a caller-supplied `origin` field - is used throughout the class for `add`, `connect`, `disconnect`, `setFavorite`, and `updateConnection`: [2](#0-1) [3](#0-2) 

These methods are exposed unmodified on the public API surface that is wired into the RPC layer used by injected/inpage providers: [4](#0-3) 

Nowhere in `ConnectedOrigins`, `connectedOriginsApi`, or the plugin wiring is the `origin` argument cross-checked against the transport-level sender/frame origin (e.g. `sender.origin` from the browser-extension messaging channel) — the plugin only observes the atom and clears data on lock, it performs no origin binding: [5](#0-4) 

This mirrors the reported bug class exactly: `proposeSetConsensusTargetRate` let any caller pass an arbitrary `protocolId`/`chainId` to mutate global state for *another* protocol because the target identifier was taken from caller input with no binding to the caller's own identity/permissions. Here, `origin` plays the same role as `protocolId`/`chainId` — it identifies *whose* trust record is being mutated, and it is taken from caller input with no binding to the actual DOM/tab origin that issued the RPC call.

### Impact Explanation
If the RPC/messaging bridge that exposes this API to web pages does not independently bind requests to the sender's real origin (which is the pattern this module itself does not enforce, and no enforcement was found in the plugin or api layer), a malicious or compromised connected dApp (`evil.com`, itself already `trusted` in some minimal capacity for the wallet to route its messages) can call `connectedOrigins.setAutoApprove({ origin: 'victim-dapp.com', value: true })` or `connectedOrigins.add({ origin: 'victim-dapp.com', trusted: true, autoApprove: true, walletAccount, assetNames })`. This would silently grant `victim-dapp.com` (or any arbitrary origin string, including one the user never actually visited/approved) `autoApprove` status, causing future signing/connection requests attributed to that origin to bypass the user's manual approval prompt — a direct authorization-bypass / cross-origin privilege bleed affecting wallet transaction/message signing, which is the kind of concrete unauthorized-signing impact this analysis is scoped to accept.

### Likelihood Explanation
Exploitability depends entirely on whether the outer RPC transport (the browser-extension background/content-script bridge, `libraries/browser-extension-rpc`) enforces sender-origin binding before invoking these API methods, or whether it forwards the `origin` field verbatim from the calling page's JSON-RPC parameters. I was not able to fully verify this cross-boundary enforcement layer within the available index/context (the RPC transport code itself does not appear to perform semantic validation of business parameters — it is a generic JSON-RPC exposer per `libraries/sdk-rpc/src/rpc.ts`), so likelihood cannot be confirmed as certain from the indexed code alone; it is architecture-dependent on the extension's messaging bridge, which was not fully visible in this scan.

### Recommendation
Bind all `connectedOrigins` mutation methods (`add`, `setAutoApprove`, `setFavorite`, `connect`, `disconnect`, `updateConnection`) to the origin of the actual RPC sender rather than a caller-supplied `origin` argument — i.e., derive `origin` server-side from the trusted message/tab context (similar to how `onlyMsc` was added to bind the caller identity in the referenced fix) instead of trusting the value passed in the RPC payload.

### Proof of Concept
Given the current code, any party able to invoke the `connectedOriginsApi` RPC methods (e.g., a connected dApp) can run:
```js
// Attacker-controlled page (origin: evil.com) calls the exposed wallet API
await exodus.connectedOrigins.setAutoApprove({
  origin: 'victim-dapp.com', // arbitrary target, not evil.com
  value: true,
})
```
Per `ConnectedOrigins#setAutoApprove` [1](#0-0) , this unconditionally flips `autoApprove` for the record matching `victim-dapp.com`, with no verification that the calling context is actually `victim-dapp.com`.

    connectedAssetName,
    origin,
    name,
    icon,
    assetNames = [],
    trusted,

  }) => {
    const value = await this.#getOrigin({ origin })

          name: name ?? value.name,

          assetNames: [...allConnectedAssetNames],

      origin,
      icon,
      name,
      connectedAssetName,
      trusted,
      favorite,

    })
  }

  connect = async ({ id, origin }) => {
    const value = await this.#getOrigin({ origin })

    if (!value) return

    const activeConnections = value.activeConnections || []
    const newConnection = { id, createdAt: Date.now() }
    const newConnections = uniqBy([...activeConnections, newConnection], 'id')

    await this.#setAttributes({ origin, attributes: { activeConnections: newConnections } })
  }

  disconnect = async ({ id, origin }) => {
    const value = await this.#getOrigin({ origin })

    if (!value) return

    const activeConnections = value.activeConnections || []
    const newConnections = activeConnections.filter((connection) => connection.id !== id)

    await this.#setAttributes({ origin, attributes: { activeConnections: newConnections } })
  }

const createConnectedOriginsPlugin = ({
  port,
  connectedOrigins,
  connectedOriginsAtom,
  enabledWalletAccountsAtom,
}) => {
  const connectedOriginsAtomObserver = createAtomObserver({
    port,
    atom: connectedOriginsAtom,
    event: 'connectedOrigins',
  })

  let unsubscribe

  const onLoad = ({ isLocked }) => {
    if (isLocked) return

    connectedOriginsAtomObserver.start()
  }

  const onUnlock = async () => {
    connectedOriginsAtomObserver.start()
    unsubscribe = enabledWalletAccountsAtom.observe(connectedOrigins.updateConnectedAccounts)
  }

  const onClear = async () => {
    await connectedOrigins.clear()
  }

  const onStop = () => {
    connectedOriginsAtomObserver.unregister()
    unsubscribe?.()
  }

  return { onLoad, onUnlock, onClear, onStop }
}
