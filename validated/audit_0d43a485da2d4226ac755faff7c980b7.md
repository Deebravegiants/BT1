This confirms the root cause: the gem's own documentation (`docs/usage/webhooks.md:125`) explicitly states `Registry.process` "will verify the request did indeed come from Shopify" based on the HMAC, and instructs developers to trust `data.shop` from `WebhookMetadata` (`docs/usage/webhooks.md:14`, `lib/shopify_api/webhooks/webhook_handler.rb:8`) as an authenticated field. But the HMAC only signs the raw body.

### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely via HMAC over the raw request body, then passes the `shop` value — taken from an unauthenticated HTTP header — to the app's handler as a trusted tenant identifier. An unprivileged internet user who can obtain one valid `(body, hmac)` pair (e.g., from a webhook Shopify legitimately sent them for their own installed/dev shop) can replay it while substituting the `shop-domain` header for a victim shop, and the gem will report it as validated and originating from the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts `shop` from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [1](#0-0) 

But `to_signable_string`, which is what actually gets HMAC-verified, is defined as just the raw body — the shop header is never part of the signed material: [2](#0-1) 

`Registry.process` calls `Utils::HmacValidator.validate(request)` (which validates `hmac` against `to_signable_string`, i.e., body only) and, if it passes, forwards `request.shop` straight into `WebhookMetadata` given to the app's handler as the authenticated tenant identifier: [3](#0-2) [4](#0-3) 

The equality the gem implicitly claims to hold is:
`shop value validated by HMAC == shop value delivered to the handler`

In reality: HMAC covers `raw_body` only; `shop` is read from a separate, unauthenticated header. So the true equality that holds is only `hmac(raw_body) == hmac(raw_body)` — nothing binds `shop` to that signature. The library's own secret (`Context.api_secret_key`) is shared across all shops/tenants of the app (it is the app's client secret, not a per-shop secret), so a valid HMAC over some body proves only "signed by an entity with the app's secret" — not "for this shop." Any attacker who obtains one legitimate `(body, hmac)` pair from Shopify (trivially available: install the app on their own shop and capture a webhook sent to them) can replay the same body/hmac to the app's webhook endpoint while setting the `shop-domain` header to any victim shop's domain. `HmacValidator.validate` still returns true, and `Registry.process` forwards `shop: <victim shop>` to the handler, which — per the gem's own documented usage — is presumed authenticated: `docs/usage/webhooks.md:14` and `docs/usage/webhooks.md:125` explicitly tell integrators the `shop` field is verified and the handler should key data storage/side effects (e.g. `perform_later(topic:, shop_domain: data.shop, ...)`) by it. Since the gem exposes no shop-bound verification and the documented contract implies one, the vulnerability lives in the gem itself, not merely in a hypothetical host-app misuse.

### Impact Explanation
This crosses a tenant boundary: an attacker-controlled webhook body (with attacker-controlled resource IDs/data for events they can trigger on their own shop, e.g. `orders/create`, `products/update`) can be attributed to a victim shop that the attacker has no access to. Any app that follows the gem's documented pattern of trusting `data.shop` for record scoping, cache keys, background job routing, or triggering shop-scoped side effects (re-sync, notifications, order processing) will act on a victim tenant using attacker-supplied content — a cross-tenant integrity/confidentiality violation.

### Likelihood Explanation
Low complexity: the attacker only needs to install the target app on any shop they control (or otherwise observe one legitimate webhook delivery, which Shopify sends to all installed shops), capture the raw body + `x-shopify-hmac-sha256` header, and replay it with a forged `x-shopify-shop-domain` header to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only an unprivileged/self-service shop install, which any internet user can obtain.

### Recommendation
- Short term: bind `shop` to the signed payload — e.g., require/validate the `shop` (and ideally `webhook_id`/topic) against the value embedded in Shopify's signed body/GraphQL-registered destination, or include the shop domain in the HMAC computation (`to_signable_string`) so header tampering invalidates the signature.
- Long term: for HTTP webhook delivery, cross-check the incoming `shop-domain` against a shop for which the app has an active, registered webhook subscription (tracked server-side per shop), rejecting webhooks for shops with no matching registration, in addition to the raw-body HMAC check.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`) via the app's normal registration flow.
2. Shopify delivers a legitimate webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`. Attacker captures `B` and `H` (they own this shop, so they can log/inspect the raw request, e.g. via a debug proxy they control).
3. Attacker sends a new HTTP POST to the same webhook endpoint with:
   - body = `B` (unchanged)
   - `x-shopify-hmac-sha256` = `H` (unchanged)
   - `x-shopify-shop-domain` = `victim-shop.myshopify.com` (forged)
4. `ShopifyAPI::Webhooks::Request.new` parses this into `shop = "victim-shop.myshopify.com"`, `to_signable_string = B`.
5. `Registry.process` calls `HmacValidator.validate`, which recomputes `HMAC-SHA256(api_secret_key, B)` and compares to `H` — it matches, since `shop` was never part of the signed input: [4](#0-3)  and [2](#0-1) .
6. `Registry.process` invokes the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`: [3](#0-2) .
7. The app, following the gem's documented pattern of trusting `data.shop`, performs a shop-scoped action (e.g., enqueues `perform_later(shop_domain: data.shop, webhook: data.body)`) against the victim tenant using attacker-controlled content.
