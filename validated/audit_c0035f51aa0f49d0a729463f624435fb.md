### No vulnerability found for this question.

Looking at `validateBtcBech32Address` in `packages/intents-sdk/src/lib/validateAddress.ts`, the code explicitly guards against exactly the attack described: after decoding via `bech32.decode` or falling back to `bech32m.decode`, it records whether the encoding used was bech32m (`isBech32m`), then explicitly rejects witness version 0 programs encoded as bech32m: [1](#0-0) 

Specifically, `if (witnessVersion === 0) { if (isBech32m) return false; ... }` rejects any v0 witness program encoded with bech32m, and `if (witnessVersion === 1) { if (!isBech32m) return false; ... }` requires bech32m for v1 (Taproot). This is precisely the BIP-350 encoding/version cross-check that the question's exploit hypothesis assumes is missing. The address given in the question, `bc1pqar0srrr7xfkvy5l643lydnw9re59gtzz5t0h9d`, decodes (if valid at all) with first data word `p` (=1), meaning it would be interpreted as witness version 1, which requires bech32m and a 32-byte program — inconsistent with the shorter v0-style program length of the address, so it would fail the `progLen === 32` check for v1, or fail decoding/checksum entirely. Either way, `validateBtcAddress` returns `false` for any address violating the version/encoding pairing rule.

There's also an existing test suite in `packages/intents-sdk/src/lib/validateAddress.spec.ts` (lines 71–144) confirming valid/invalid bech32/bech32m cases are exercised, including that mismatched encoding is rejected. [2](#0-1) 

Since `validateAddress` for Bitcoin never returns `true` for a v0 program encoded with bech32m (or a mismatched version/encoding pair), the premise of the question — that such a malformed string reaches `deriveOmniWithdrawIntentParams` / `createWithdrawalIntents` and gets forwarded unchanged to `omni.bridge.near` — does not hold. The equality between the user-supplied `destinationAddress` and the payout account is preserved because the malformed string is filtered out before any intent construction occurs.
