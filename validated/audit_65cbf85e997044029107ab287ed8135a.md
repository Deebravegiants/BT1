## Finding

### Title
Webhook `shop`/`topic` identity headers are trusted by the handler but excluded from HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC to the raw request body only. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are read directly from unauthenticated HTTP headers and handed to the application's webhook handler as if they were verified, once `Utils::HmacValidator.validate` succeeds.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` treats a successful HMAC check as proof that the *entire request*, including the shop identity, is authentic: [1](#0-0) 

But the HMAC is only computed over `@raw_body`: [2](#0-1) 

while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from attacker-influenceable HTTP headers with no binding to the signature: [3](#0-2) 

The `HmacValidator.validate` call only re-derives and compares the HMAC of `to_signable_string` (the body), never incorporating `shop`, `topic`, or `webhook_id`: [4](#0-3) 

The broken identity binding, expressed as an equality that should hold but does not:
`HMAC-verified-bytes == bytes acted upon by the handler`
In reality: `HMAC-verified-bytes = raw_body`, while `bytes acted upon = raw_body + shop-domain header + topic header + webhook-id header`.

The documented usage pattern for this gem confirms that host applications key their business logic (session/store lookup, job enqueueing) directly off `data.shop`, trusting it as an authenticated identity field once the handler is invoked: [5](#0-4) 

### Impact Explanation
Any unprivileged internet user who can install the app on their own shop (a normal, unprivileged onboarding flow) legitimately receives real webhook deliveries — bodies with valid HMAC signatures generated using the shared `client_secret` for *their own* shop's events. Because the `x-shopify-shop-domain`/`x-shopify-topic` headers are not covered by the HMAC, that same attacker can resend/replay the identical `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain (or an arbitrary domain of a shop that also has the app installed). `Registry.process` will accept the request as valid and invoke the handler with `data.shop` set to the attacker-chosen value, causing the host application to process attacker-controlled webhook data as if it originated from the victim tenant. This is a cross-tenant confusion primitive: attacker-controlled data is attributed to another tenant's identity, matching the "cross-tenant access" High/Critical impact category, since downstream apps built per this gem's own documented pattern will store or act on the spoofed shop identity.

### Likelihood Explanation
Likely, for apps that expose an internet-reachable webhook endpoint (as required by this gem's design) and follow the documented handler pattern of trusting `data.shop`/`data.topic`. The only prerequisite is that the attacker has (or creates) a store where the app is installed, which is an ordinary unprivileged action, not a privileged credential.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the value covered by the HMAC comparison, or otherwise cryptographically bind them to the body before trusting `request.shop`/`request.topic` in `Registry.process`. At minimum, document and/or enforce that `data.shop` must be cross-checked against a known, previously-established session/store record before being used for any authorization or data-routing decision.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a benign event (e.g., `orders/create`), capturing the resulting webhook POST: raw body `B` and header `x-shopify-hmac-sha256: H` (a valid HMAC of `B` using the app's `client_secret`), per [6](#0-5) .
2. Attacker resends the same body `B` and hmac `H` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or a different `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (== `B`) and matches `H`, per [7](#0-6) , so validation passes.
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)`, per [8](#0-7) , causing the app to process attacker-controlled data under the victim shop's identity.
