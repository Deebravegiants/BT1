### No vulnerability found for this question.

The claimed exploit requires the on-chain intents contract to accept a `public_key`/`signer_id` that does not match the actual key that produced the `signature`. Standard ed25519 verification performed by the contract checks that `signature` is valid for the exact `public_key` field submitted; an attacker's signature produced with their own private key over `signature.signedData.message` will not verify against a victim's public key (`ed25519:${userInfo.userAddress}`) unless the attacker also controls that private key. Since `transformED25519Signature` just passes through the raw signature bytes without any recovery step [1](#0-0) , and `prepareSwapSignedData` for the `SOLANA` case only asserts chain-type equality, not key equality, before constructing the payload [2](#0-1) , the client-side function can indeed be made to emit a mismatched `public_key`/`signature` pair. However, this divergence is caught by the intents contract's own cryptographic signature verification, which is outside this repo's code path but is explicitly the trust boundary that prevents exploitation — a forged `public_key` claim cannot pass verification without the corresponding private key, so no funds move and the relayer/contract would simply reject the intent. `publishIntent` forwards this payload directly to `publishIntents` for broadcast [3](#0-2) , but broadcasting an unverifiable signed_data does not constitute fund movement or a successful state change — it is rejected before any transitive effect on `signer_id`-gated funds.

Additionally, in the legitimate SDK call flow, `userInfo.userAddress` is derived from the caller's own connected wallet state rather than being an arbitrary attacker-supplied string reachable by an unprivileged counterparty; the scenario in the question requires the calling integrator to deliberately construct `userInfo` with someone else's address, which is a misuse of the API rather than a flaw reachable by an ordinary NEAR Intents user or counterparty as scoped by the rules.
