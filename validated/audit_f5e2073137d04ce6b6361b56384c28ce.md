## Analog Assessment

The library's OAuth (`AuthQuery`), Token Exchange (`JwtPayload`) and shop-domain flows (`ShopValidator.sanitize!`) all bind the acted-upon `shop` value into either the HMAC-signed query string or the HS256-signed JWT payload, and forging either requires the app's `api_secret_key` (out of scope per the rules). Those paths are not exploitable by an unprivileged internet user.

The webhook path, however, breaks exactly the identity-binding pattern the rules call out: **"a field acted on but not covered by the HMAC."**

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing tenant spoofing on replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) . `HmacValidator.validate` computes the HMAC over that signable string only [2](#0-1) . The `shop` value, read from the `shopify-shop-domain`/`x-shopify-shop-domain` header [3](#0-2) , is never included in the signed payload, yet `Registry.process` trusts it directly and passes it to the app's handler as the identity of the shop that sent the webhook: [4](#0-3) .

### Finding Description
`Registry.process` validates only that the HMAC of the raw body is correct for the app's secret: [5](#0-4) . It then constructs `WebhookMetadata` using `request.shop`, which is taken verbatim from an HTTP header that is not part of the signed content: [6](#0-5) .

The identity binding the gem should enforce is:
`hmac_signed_bytes == bytes_that_determine_the_tenant`

What is actually enforced is:
`hmac_signed_bytes == raw_body` while `tenant == shop-domain header` (unsigned)

Because the body and the shop header are independently controllable by whoever sends the HTTP request to the app's public webhook callback URL, any party capable of obtaining one legitimately-signed `(raw_body, hmac)` pair for the app (e.g., by installing/using the app on their own shop and capturing a real webhook delivery) can replay that exact body and HMAC to the same callback endpoint while substituting a different value in the `shop-domain` header. The HMAC still validates (it only covers the body), and the handler receives `data.shop` set to the attacker-chosen value while trusting it as the originating shop.

The library's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" [7](#0-6)  and that `data.shop` is "The shop domain of the webhook" [8](#0-7) , implying host applications are expected to trust `data.shop` as authenticated — which it is not.

### Impact Explanation
This is a cross-tenant identity confusion: a webhook whose body was legitimately signed for shop A can be replayed with the `shop` field forged to shop B. Any host application that uses `data.shop` from `WebhookMetadata` to look up per-tenant session/access tokens, apply data to a tenant's records, or make authorization decisions (a documented and expected usage pattern) will act on shop B's identity using data that actually originated from (or was crafted for) shop A. Depending on the webhook topic and body content this can range from data written to the wrong tenant, to processing of `customers/redact`/`shop/redact` compliance webhooks against the wrong shop, satisfying the "cross-tenant access" Critical impact bucket.

### Likelihood Explanation
Exploitation requires only:
1. Knowledge of the app's public webhook endpoint (routine, as it's a URL the app owner configures and Shopify calls).
2. One captured legitimate `(body, hmac)` pair, obtainable by any unprivileged actor who installs the target app on a shop they control and observes/logs a delivered webhook.
3. Sending a raw HTTP POST with that same body/HMAC but an attacker-chosen `shop-domain` header — no `api_secret_key` or other Shopify credential is needed.

No privileged access, TLS interception, or secret leakage is required, which keeps this within scope of the stated exclusions.

### Recommendation
Include the shop-domain (and ideally topic and webhook-id) in the HMAC-signed material, or otherwise cryptographically bind `request.shop` to the signature verified by `HmacValidator`, so that `to_signable_string` cannot be satisfied by a replayed body under a different `shop-domain` header. Alternatively, require registry consumers to cross-check `request.shop` against the shop associated with the specific webhook subscription/session rather than trusting the header value implicitly.

### Proof of Concept
```ruby
# Attacker step 1: install target app on their own shop, capture a real webhook delivery,
# e.g. an "orders/create" POST with body B and a valid
# X-Shopify-Hmac-Sha256 header H = HMAC-SHA256(api_secret_key, B).

# Attacker step 2: replay to the same public webhook endpoint, unmodified body/HMAC,
# but with a different shop-domain header:
POST /callback/orders/create HTTP/1.1
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: <H>              # unchanged, still valid for body B
X-Shopify-Shop-Domain: victim-shop.myshopify.com   # forged
X-Shopify-Webhook-Id: anything
X-Shopify-Api-Version: 2024-01

<B>   # unchanged raw body

# Server-side:
request = ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds because it only signs B.
# Registry.process calls handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))
