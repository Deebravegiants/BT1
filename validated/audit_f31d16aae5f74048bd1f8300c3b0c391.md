### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (and `topic`) values used by the application to route and process the webhook are taken from unauthenticated HTTP headers. Any attacker who can obtain one genuine, HMAC-valid webhook body (e.g., by owning a shop that installs the app and triggers a webhook for itself) can replay that exact body to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a victim shop. The HMAC still validates (it authenticates only the body bytes), but the shop identity binding is broken, letting the attacker inject attacker-controlled webhook data as if it belongs to another tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from request headers, none of which are included in the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC strictly against `to_signable_string`, i.e. the raw body — it has no visibility into headers at all: [3](#0-2) 

`Registry.process` trusts this validation result and then dispatches the handler using `request.shop`, which came straight from the unauthenticated header: [4](#0-3) 

The binding that should hold is: `shop asserted to the handler == shop the HMAC was computed for`. Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app, an HMAC computed over a given body is valid for that body regardless of which shop it originated from. Any attacker controlling a shop that has installed the app (or who can otherwise obtain one valid `(body, hmac)` pair, e.g. via their own test store) can:
1. Trigger a webhook from their own shop A, capturing the exact `raw_body` and its valid `X-Shopify-Hmac-Sha256` value.
2. Replay that identical body + hmac to the victim app's webhook endpoint, but with `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) rewritten to target shop B.
3. `HmacValidator.validate` succeeds (body+secret match), so `Registry.process` invokes the handler with `WebhookMetadata.shop == "shop-B"` and attacker-chosen `body`.

This crosses the tenant boundary: application code that trusts `request.shop` (e.g., to look up shop B's session/store to act on) now processes attacker-supplied data under shop B's identity.

### Impact Explanation
This is a cross-tenant identity break enabled entirely by this gem's webhook verification design — the `shop` field that host applications use to select the tenant is asserted via an unauthenticated header while only the body is HMAC-protected. Depending on how the host app's webhook handler uses `WebhookMetadata.shop`, this can lead to cross-tenant data corruption, cross-tenant reads/writes via the shop's stored access token, or injection of attacker-controlled payloads attributed to a different merchant — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Medium-to-High: the attacker needs one valid `(body, hmac)` pair, which is trivial to obtain by installing the app themselves (as any developer/merchant can) and triggering any webhook topic they control (e.g., `app/uninstalled`, `orders/create` on their own store), then replaying it with a modified shop header to any other shop domain. No secrets or privileged access are required beyond ordinary use of the app as an installed merchant.

### Recommendation
Include the shop domain (and ideally topic) in the HMAC-signed material, or otherwise cryptographically bind the header-derived identity to the verified body — e.g., require the host app to independently confirm that the `shop-domain` header value corresponds to a shop with an active webhook registration/session before trusting it, or extend `to_signable_string` to incorporate the relevant headers so that a valid signature is tied to a specific shop context rather than being replayable across tenants with only the body forged/reused.

### Proof of Concept
```ruby
# Step 1: Attacker installs the app on their own shop "attacker.myshopify.com"
# and captures a legitimate webhook delivery, e.g. body = '{"id":1}'
# hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, body)
# (api_secret_key is the same client_secret for every installed shop)

# Step 2: Attacker replays the same body/hmac to the victim app's webhook
# endpoint, forging the shop header:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac), # valid, since body is unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: '{"id":1}', headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body-only signature matches)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The app now processes attacker-controlled data under the victim shop's identity.
``` [4](#0-3)
