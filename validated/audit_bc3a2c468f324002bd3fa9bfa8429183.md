### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies the authenticity of an incoming webhook using only the raw JSON body against the `X-Shopify-Hmac-Sha256` header, but the `shop-domain` header (along with `topic`, `api-version`, and `webhook-id`) is never included in the signed content. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` after HMAC validation succeeds and forwards it, unauthenticated, to the app's handler via `WebhookMetadata`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` simply reads the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to that value: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string`, i.e. the raw body, and compares it to the provided signature: [3](#0-2) 

`Registry.process` gates on this HMAC check and then immediately uses `request.shop` — a value that was never part of the signed content — to dispatch the webhook to the registered handler: [4](#0-3) 

The identity binding that should hold is: `shop header == shop cryptographically bound to the signed payload`. Because the `shop-domain` header sits outside `to_signable_string`, this equality is never enforced. Since a single app's `api_secret_key` is shared across every shop that installs the app, any shop owner (an unprivileged internet user who can install the target app on their own store) legitimately receives HMAC-valid webhook payloads for their own shop. That same `(raw_body, hmac)` pair remains valid under the identical secret regardless of which `shop-domain` header accompanies it. An attacker who controls the webhook delivery endpoint traffic to the app (e.g., by replaying a captured payload with a substituted `X-Shopify-Shop-Domain` header) can therefore present a request that: (a) passes `Utils::HmacValidator.validate`, and (b) causes `Registry.process` to hand off `WebhookMetadata` claiming to be a victim shop, to the app-provided handler.

### Impact Explanation
This breaks the shop-identity boundary the HMAC check is meant to enforce. Any application logic that trusts `WebhookMetadata#shop` to select which merchant's session/access token/store data to act on (a normal and expected usage pattern per this gem's own webhook handler contract) can be tricked into operating under a victim shop's identity using only a body+signature pair the attacker legitimately obtained for their own (attacker-controlled) shop. This is a cross-tenant identity-confusion vector rooted entirely in this gem's `HmacValidator`/`Webhooks::Request` design, not merely a host-application misuse, since the gem is the one responsible for authenticating "this shop said this" and it never actually authenticates the shop field.

### Likelihood Explanation
Moderate-to-high: the prerequisite is only that the attacker can install the target app on their own Shopify store (or otherwise obtain one valid webhook body+HMAC pair) and can deliver a forged HTTP request to the app's public webhook endpoint with a different `shop-domain` header — both are within reach of an ordinary, unprivileged internet user, requiring no leaked credentials, no `api_secret_key`, and no access token.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the data covered by the HMAC verification, or otherwise cryptographically bind the shop identity to the signed request, so that `Registry.process` cannot dispatch a payload under a `shop` value that was not part of the authenticated content.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; capture a legitimate webhook delivery `(raw_body, X-Shopify-Hmac-Sha256)` pair for it.
2. Replay that exact `(raw_body, hmac)` to the app's webhook endpoint, replacing `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` invokes the app handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` (`lib/shopify_api/webhooks/registry.rb:188-200`), despite the payload never having been signed for that shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
