Audit Report

## Title
CORS Allowlist Bypass via Improper Suffix Matching in Gateway Wildcard Origin Validation - (File: core/services/gateway/network/httpserver.go)

## Summary
The Chainlink Gateway HTTP server's `isAllowedOrigin` function validates wildcard CORS entries (e.g. `*.ethereum.org`) using `strings.HasSuffix(originHost, allowedHost)` without requiring a domain-label boundary (a preceding `.`). An attacker who registers a domain that merely ends with the configured allowed suffix (e.g. `evilethereum.org` when the allowlist contains `*.ethereum.org`) can have their origin falsely validated, causing the Gateway to echo that malicious origin back via `Access-Control-Allow-Origin`.

## Finding Description
In `isAllowedOrigin`, the wildcard branch strips the `*.` prefix and performs a raw suffix check:

```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if strings.HasSuffix(originHost, allowedHost) {
        return true
    }
}
``` [1](#0-0) 

This does not verify that the match is preceded by a `.` label separator, so `"evilethereum.org"` incorrectly satisfies `strings.HasSuffix("evilethereum.org", "ethereum.org")`. The result feeds directly into `handleRequest`, which echoes the raw `Origin` header into `Access-Control-Allow-Origin` when `isAllowedOrigin` returns true: [2](#0-1) 

There is no other validation, normalization, or label-boundary check applied before or after this call — the existing exact-match check at line 181 (`originHost == allowedHost`) does not mitigate the flawed wildcard branch, and the existing test suite only covers a case that does not end with the suffix at all (`ethereum.remix.org` vs `ethereum.org`), not the boundary-less-suffix bypass case (`evilethereum.org` vs `ethereum.org`).

## Impact Explanation
This allows an attacker-controlled origin to pass the Gateway's CORS allowlist check whenever the operator uses a wildcard entry, causing the Gateway to set `Access-Control-Allow-Origin` to the attacker's origin. This is a genuine allowlist bypass in an internet-facing component, falling within the "allowlist bypass" / "cross-user response corruption" impact category, since it lets an attacker's browser page make and read cross-origin CORS-enabled requests to the Gateway that should have been restricted to genuine subdomains of the trusted domain.

## Likelihood Explanation
Exploitation requires the Gateway operator to have configured at least one wildcard entry in `CORSAllowedOrigins` (a supported, documented configuration option, not a misuse), and the attacker need only register any domain name string that literally ends with the configured suffix (e.g., `evilethereum.org`), which is trivially achievable without any special access, credentials, or node/network compromise. This is reachable by a fully unprivileged remote actor.

## Recommendation
Enforce a proper label boundary in the suffix check:
```go
if strings.HasSuffix(originHost, allowedHost) &&
    (originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)) {
    return true
}
```

## Proof of Concept
1. Configure Gateway with `CORSAllowedOrigins = ["https://*.ethereum.org"]` and `CORSEnabled = true`.
2. Send an HTTP request to the Gateway endpoint with header `Origin: https://evilethereum.org`.
3. `isAllowedOrigin` splits `allowedHost` to `"ethereum.org"` and evaluates `strings.HasSuffix("evilethereum.org", "ethereum.org")` as `true`.
4. `handleRequest` sets `Access-Control-Allow-Origin: https://evilethereum.org` in the response, confirmable by inspecting `resp.Header.Get("Access-Control-Allow-Origin")` in a Go test modeled on the existing `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` test at [3](#0-2) , but using origin `https://evilethereum.org` instead of `https://ethereum.remix.org`.
