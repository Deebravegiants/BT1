### Title
Webhook shop identity spoofing via `shop-domain` header not covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant identity) is read from the `X-Shopify-Shop-Domain` header, which is never included in the signed bytes. `Utils::HmacValidator` validates the signature using the app's single, shop-agnostic `Context.api_secret_key`, so the check only proves "this body was sent/signed by someone who knows the app's client secret" — it says nothing about which shop the body belongs to.

### Finding Description
`Registry.process` validates a webhook by calling `Utils::HmacValidator.validate(request)` [1](#0-0) , which in turn calls `validate_signature`, comparing `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` using `Context.api_secret_key` [2](#0-1) .

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [3](#0-2) , while `shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, entirely outside the signed content [4](#0-3) . After HMAC validation succeeds, `Registry.process` forwards `request.shop` unmodified into `WebhookMetadata`, which is handed to the app's handler as the tenant identifier for the event [5](#0-4) .

Because `Context.api_secret_key` is the single client secret for the entire app (not a per-shop secret), it is identical across every store that installs the app [6](#0-5) . This breaks the intended equality binding `hmac(body, api_secret_key) == valid  ⇒  shop == body's true owner`. In reality the equality that holds is only `hmac(body, api_secret_key) == valid ⇒ body was produced/known by an app-secret holder`, with **no cryptographic binding between `body` and the `shop` header value** used to key sessions/tenant data downstream.

An attacker who operates their own store (Shop A) and has installed the app receives genuine, correctly-HMAC-signed webhook deliveries for Shop A (same shared `api_secret_key` as every other install of the app). The attacker can replay that exact `raw_body` + `hmac-sha256` header to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with Shop B's domain. `HmacValidator.validate` still succeeds (it never inspected the shop header), and the handler receives `WebhookMetadata` claiming `shop: "shop-b.myshopify.com"` with attacker-chosen body content that was never actually sent for Shop B.

### Impact Explanation
If a host application uses `webhook_id`/`shop` from `WebhookMetadata` to look up sessions, deduplicate work, or write per-tenant data (a documented and expected usage pattern of `Registry.process`), this allows a single malicious merchant to inject arbitrary, "verified" webhook payloads under any other shop's identity — a cross-tenant data-integrity/confusion attack that requires no privileged credentials from the target shop, only the attacker's own legitimate app installation. This satisfies the Critical "cross-tenant access" impact category, since it lets one tenant's data cross into another tenant's context using only the shared app secret that the attacker legitimately possesses for their own store.

### Likelihood Explanation
Likelihood is high for any app that relies on `Registry.process`/`WebhookMetadata.shop` as the trusted tenant key (this is the primary documented way to consume webhooks in this gem). The attacker only needs to install the app on a store they control — an ordinary, unprivileged action — and capture one legitimate delivery to obtain a valid `(raw_body, hmac)` pair signed with the shared secret. No access to `api_secret_key` itself, access tokens, or any other shop's credentials is required.

### Recommendation
Include the tenant-identifying fields (at minimum `shop-domain`, ideally `topic` and `webhook-id`) in the signed/verified material, or otherwise cryptographically bind the header-derived `shop` to the signed body (e.g., require the host app to independently verify that the shop has an active session/webhook registration matching the claimed shop before trusting `WebhookMetadata.shop`). Document explicitly that `request.shop` is not covered by the HMAC and must not be treated as authenticated on its own.

### Proof of Concept
1. Install the app on attacker-controlled Shop A; wait for a real webhook delivery, capturing `raw_body`, `X-Shopify-Hmac-Sha256`, and other headers.
2. Send an HTTP request to the app's webhook endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256` value, but replace `X-Shopify-Shop-Domain` with `shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes the HMAC over `raw_body` using the shared `Context.api_secret_key` and finds it matches [7](#0-6) .
4. The registered handler is invoked with `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: <attacker-controlled JSON>, ...)` [8](#0-7) , even though Shop B never sent this webhook.
