### Title
Webhook `shop`/`topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook replay - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used downstream for tenant identification and routing are read straight from unauthenticated HTTP headers. `Registry.process` validates only that the body's HMAC is correct and then trusts these header-derived fields as-is, breaking the binding `HMAC_valid(body) == shop_header authenticated`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled directly from headers, none of which are part of the signed content: [2](#0-1) 

`Registry.process` validates the request via `Utils::HmacValidator.validate(request)`, which only calls `verifiable_query.to_signable_string` (i.e. the body) through `compute_signature`/`OpenSSL.secure_compare`: [3](#0-2) 

After that single check passes, `Registry.process` forwards the unauthenticated `request.shop` and `request.topic` header values into `WebhookMetadata`, which is what host applications use to attribute the payload to a specific merchant/tenant: [4](#0-3) 

Because the shop/topic headers are never part of the HMAC-signed data, any party who possesses one validly-signed `(body, hmac)` pair for the app's shared `client_secret` (e.g., a malicious merchant who legitimately installed the app and receives correctly-signed webhooks for their own shop) can replay that exact body+HMAC to the same webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header to claim a different shop or topic. `HmacValidator.validate` will still return `true` because it never inspects those headers, and the host application's handler will process the payload as if it legitimately originated from the spoofed shop/topic.

### Impact Explanation
This breaks the intended identity binding between "HMAC signed by the app's secret" and "the shop the payload is attributed to." A party with access to one legitimately-signed webhook (their own shop's webhook traffic, or any leaked/logged payload) can attribute the body's content to an arbitrary other shop known to be using the same app, resulting in cross-tenant data injection into per-shop business logic (e.g., mis-attributing an `orders/create` payload to another merchant's shop record). This matches the "cross-tenant access" High-impact category.

### Likelihood Explanation
Exploitation requires only capturing one valid webhook payload+signature for the shared app secret (trivially available to any merchant who has installed the app, since all shops of an app share the same `client_secret`/HMAC key) and re-posting it to the webhook endpoint with a modified `shop-domain`/`topic` header — no possession of `client_secret`, access tokens, or privileged access is needed. The header-spoofing step is entirely within an unprivileged internet user's control since the gem performs no header authenticity check.

### Recommendation
Include the identity-critical headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signable string (mirroring Shopify's actual webhook HMAC scope) or, at minimum, require the host application to bind the resolved `shop` to a known, previously-authorized session/tenant before trusting `WebhookMetadata#shop` for any tenant-specific processing. Reject requests where the claimed shop cannot be correlated with an existing installation record.

### Proof of Concept
1. App "MyApp" is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, sharing one `client_secret`.
2. Shopify sends a legitimately signed webhook to the attacker's shop endpoint:
   `headers = {"x-shopify-topic"=>"orders/create", "x-shopify-hmac-sha256"=>H, "x-shopify-shop-domain"=>"attacker-shop.myshopify.com"}`, body `B`, where `H = HMAC(secret, B)`.
3. Attacker captures `(B, H)` and replays it to the app's webhook endpoint with `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or a different topic header), keeping body `B` and hmac header `H` unchanged.
4. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)`, which still equals `H`, so validation succeeds (`lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to process attacker-controlled order data under the victim shop's tenant context.
