**Analysis:**

The premise misidentifies where the custody boundary actually sits. `NativeStateCommitter::apply` in `storage/aptosdb/src/native_state_committer.rs` is a storage-layer commit routine that consumes `(StateKey, WriteOp)` pairs already produced by validated transaction execution — it is not a Move-callable or otherwise attacker-reachable entrypoint. Its only check [1](#0-0)  exists to catch internal wiring bugs (making sure only `Position` keys land in the position bucket), not to perform authorization — that is done far upstream.

The actual write path is:

1. Move code calls `native_position::set_position`/`delete_position`, which first calls `trading_native_capability::assert_valid(cap)` before invoking the native, and derives `exchange` from the capability itself rather than from caller-supplied input: [2](#0-1) 
2. A `TradingNativeCapability` can only be minted via `get_capability`, gated by `assert_active`, which requires the exchange address to be governance-registered and not denied: [3](#0-2) 
3. The native functions `native_set_position`/`native_delete_position` just stage the key/value into the per-transaction `NativePositionContext`; they take `exchange`/`account`/`market` as plain arguments and rely entirely on the Move-level capability check having already run: [4](#0-3) 
4. Staged writes only reach `native_position_iter()` / `apply` after full transaction execution and commit, i.e., only writes the Move VM already authorized (via a valid, non-denied `TradingNativeCapability`) ever arrive at `apply`: [5](#0-4) 

There is no way for an unprivileged attacker to invoke `NativeStateCommitter::apply` directly with a crafted `StateKey`/`WriteOp` pair — the only path into it is through the validator's own execution pipeline, which only ever hands it writes produced by Move code that already passed `assert_valid(cap)`. The `account`/`market` fields are business data controlled by the registered exchange (this is by design, analogous to an exchange managing user margin positions under its own capability, not requiring the position owner's individual signature per write) — the actual authority boundary is "does the caller hold a valid, non-denied exchange capability," and that boundary is enforced in `trading_native_capability.move`, not in the storage committer. `apply`'s "sole guard" being a type-shape check rather than an authorization check is expected, because authorization is not this function's responsibility and is already closed off upstream.

    /// Abort unless `addr` is currently allowed to write: `TRADING_NATIVE`
    /// enabled, registered, and not denied.
    fun assert_active(addr: address) acquires ExchangeRegistry {
        assert!(
            features::is_trading_native_enabled(),
            error::permission_denied(EFEATURE_DISABLED),
        );
        let registry = borrow_global<ExchangeRegistry>(@aptos_experimental);
        assert!(
            registry.registered.contains(&addr),
            error::permission_denied(EEXCHANGE_NOT_REGISTERED),
        );
        assert!(
            !registry.denied.contains(&addr),
            error::permission_denied(EEXCHANGE_DENIED),
        );
    }
