### Title
Webhook shop/topic/webhook-id metadata is not covered by the HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, so `ShopifyAPI::Utils::HmacValidator.validate` only authenticates the request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are read directly from unauthenticated HTTP headers and are never part of the signed payload, yet they are trusted as the tenant identity passed to the app's webhook handler.

### Finding Description
`Registry.process` validates a webhook exclusively via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` to build the HMAC input. [1](#0-0) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the HMAC: [3](#0-2) 

After HMAC validation passes, `Registry.process` builds `WebhookMetadata` using `request.shop` — the unauthenticated header value — and hands it to the app's handler as the tenant identity: [1](#0-0) 

The identity binding that should hold is: `shop attested by HMAC == shop trusted by the handler`. Because the HMAC only covers `raw_body`, this equality does not hold — the `shop` (and `topic`/`webhook_id`) value can be changed independently of the signature that "authenticates" the request.

### Impact Explanation
This breaks the cross-tenant boundary the HMAC is meant to enforce: an attacker who obtains any single valid `(raw_body, hmac)` pair signed with the app's `client_secret` (e.g., by triggering an event on their own dev/test store, which they legitimately control) can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `Utils::HmacValidator.validate` will still succeed, since it only checks the body bytes, and `Registry.process` will invoke the app's handler believing the payload originated from the attacker-chosen shop. Any app logic that trusts `WebhookMetadata#shop` to scope data access, update per-shop records, or key session/tenant lookups can be manipulated into acting on/for a shop the attacker does not control — a cross-tenant integrity issue reachable purely with a normal, non-privileged webhook delivery the attacker owns.

### Likelihood Explanation
Any merchant/developer can install the app on a test store they control and capture a legitimate webhook delivery (body + `x-shopify-hmac-sha256`) for that store — no access token, `client_secret`, or session leak is required. They can then replay that exact body/signature to the same public endpoint with a forged `x-shopify-shop-domain` (and/or `x-shopify-topic`) header. Because the HMAC never binds these headers, the replayed request is indistinguishable from a legitimate one from the gem's perspective.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signable content, or otherwise cryptographically bind them to the HMAC — e.g., only trust `request.shop`/`request.topic` if Shopify includes them in the signed body, or require the app to independently correlate the header-provided shop with a shop known from the webhook subscription itself, rather than exposing them as unauthenticated header-derived attributes from `Webhooks::Request`.

### Proof of Concept
1. Register a webhook and receive one legitimate delivery for `shop-a.myshopify.com`, capturing `raw_body` and the `x-shopify-hmac-sha256` header value (computed by Shopify with the app's `client_secret`).
2. Replay the identical `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but set `x-shopify-shop-domain: shop-b.myshopify.com` (a shop the attacker does not own/administer).
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged shop header; `Utils::HmacValidator.validate` computes the HMAC over `raw_body` only and it matches, so `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)`, even though the HMAC was never computed with that shop in mind.
