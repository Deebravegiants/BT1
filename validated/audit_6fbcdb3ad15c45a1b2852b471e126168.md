## Title
Webhook `shop` (and `topic`) identity is not bound by the HMAC signature, enabling cross-tenant webhook replay — (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then dispatches the handler using the `shop` (and `topic`) values read from unsigned HTTP headers. Because those routing/identity fields are never included in the signed payload, a valid signature obtained for one tenant's webhook can be replayed with a forged `shop-domain` header to make the app process data as if it belonged to a different, victim tenant.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) 

`hmac` is derived from the `hmac-sha256` header, and `to_signable_string` returns only `@raw_body`. Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from unsigned headers via `shopify_header`: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then builds `WebhookMetadata` — which the handler uses to determine *which merchant* the payload is for — from those unsigned headers: [3](#0-2) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. it proves the *body* wasn't tampered with, but proves nothing about `shop`: [4](#0-3) 

The security invariant the code implicitly assumes is:
`HMAC-verified(raw_body) == identity-bound(shop-domain header)`

but the actual invariant enforced is only:
`HMAC-verified(raw_body)`

These are not equal — the `shop` (and `topic`) used to route/process the webhook is never covered by the cryptographic check, breaking the binding between "authenticated bytes" and "the tenant the app believes sent them."

### Impact Explanation
Any actor who can obtain one legitimately signed `(raw_body, hmac)` pair — trivially available to any merchant who installs the app on their own store and triggers an event (e.g., `orders/create`) — can replay that exact body and HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for a different, victim shop. `Registry.process` will accept it (the HMAC still matches the unmodified body) and hand the handler a `WebhookMetadata` claiming the data belongs to the victim tenant. Any app logic keyed off `data.shop` (e.g., updating per-shop records, triggering per-shop side effects, writing to the victim's stored data) executes under the wrong tenant — this is cross-tenant access/data corruption via a boundary the app believed was authenticated.

### Likelihood Explanation
Likelihood is realistic: webhook endpoints are public HTTP(S) endpoints by design, the attacker does not need the app's `client_secret` or any privileged account beyond a free/self-service app install to obtain a valid `(body, hmac)` sample for their own shop, and no additional secret material is needed to replay it with altered headers.

### Recommendation
Bind the tenant/routing identity to the signed material: include `shop`, `topic`, and `webhook_id` in the HMAC-covered signable string (or otherwise cryptographically bind them, e.g. by validating the `shop` header against the shop associated with the session/access token that registered the webhook), and reject the webhook if these fields cannot be verified against the signed content. At minimum, document and enforce that `request.shop` must not be trusted as an authenticated value unless it is checked against an independent, verified source (e.g., the app's own shop/session store) before being used for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` (self-service, no privileged access required) and triggers a webhook event, e.g. `orders/create`, causing the app to receive:
   - body: `{"id":1,...}` 
   - headers: `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC over body>`
2. Attacker captures this exact `(body, hmac)` pair (it is delivered straight to their own endpoint/logs).
3. Attacker sends a new POST to the app's webhook endpoint with the identical body and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `to_signable_string` (`@raw_body`) against the HMAC — this passes because the body/HMAC pair is untouched. [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes the attacker's data as belonging to the victim tenant. [6](#0-5)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
