### Title
Fee-only failed transactions under-report `loaded_accounts_data_size` when `define_ltds_fee_only_semantics` is disabled, causing actual block-cost accounting to under-charge real work performed - ([File: svm/src/rollback_accounts.rs])

### Summary
When a transaction fails during `load_transaction_accounts` (e.g. exceeds the loaded-accounts-data-size limit or hits an invalid/missing program), `load_transaction` produces a `FeesOnlyTransaction`. With `define_ltds_fee_only_semantics` disabled, its `loaded_accounts_data_size` is set to `RollbackAccounts::data_size()` — the byte length of only the fee payer/nonce accounts — rather than the actual bytes read while loading the transaction up to the point of failure. This value is later reused, unmodified, as the "actual" loaded-accounts-data-size when the executed cost is recomputed and applied to the block `CostTracker` after commit, allowing real work (loading of large accounts prior to the failure) to go unaccounted for.

### Finding Description
`load_transaction` in `svm/src/account_loader.rs` computes `loaded_accounts_data_size` for the `FeesOnly` branch as: [1](#0-0) 
This falls back to `tx_details.rollback_accounts.data_size()` when `define_ltds_fee_only_semantics` is not active, per `RollbackAccounts::data_size()`: [2](#0-1) 
which only sums the data length of the fee payer (and nonce, if present) — it ignores every other account that was loaded by `load_transaction_accounts` before the failure occurred (e.g., large program accounts, other writable accounts counted toward `loaded_tx_data_size` in `load_transaction_accounts`, `svm/src/account_loader.rs:522-620`).

This value flows through `ProcessedTransaction::FeesOnly` → `loaded_accounts_data_size()`: [3](#0-2) 
into `TransactionLoadedAccountsStats.loaded_accounts_data_size`, and then into the post-commit "actual cost" recomputation used to update the live `CostTracker`: [4](#0-3) 
`get_transaction_costs` calls `CostModel::calculate_cost_for_executed_transaction` with `committed_tx.loaded_account_stats.loaded_accounts_data_size` as the "actual" bytes, and this feeds `check_block_cost_limits`/`try_add` on the cost tracker: [5](#0-4) 

The existing test `fee_only_loaded_transaction_data_size` in `svm/tests/integration_test.rs` explicitly demonstrates this discrepancy: for the `old_fee_only` (`define_ltds_fee_only_semantics = false`) case, both the "exceeds limit" and "invalid program id" failure paths report `loaded_accounts_data_size == 0` even though large accounts (512–8192 bytes each, growing up to several accounts) were loaded before the failure was detected: [6](#0-5) 
This 0 (or otherwise small, fee-payer-only sized) value is later used as the "actual" data size fed into the post-commit cost-tracker update, meaning the accounted work is far smaller than the real work the leader/validator performed loading those accounts.

An unprivileged attacker exploits this by:
1. Constructing a transaction that references several large accounts (or a large nonce account) as writable, with a small `set_loaded_accounts_data_size_limit` or an invalid/unknown program ID as the final instruction, guaranteeing a load-time failure after the account-loading loop already accessed the large accounts.
2. Because the fee payer/nonce rollback accounts themselves are small (e.g., a plain system account), `RollbackAccounts::data_size()` returns a tiny value (often 0), regardless of how much actual account data was scanned.
3. The failing transaction is still committed as `ProcessedTransaction::FeesOnly`, charging the (correctly pre-computed, unrelated) fee, but under `define_ltds_fee_only_semantics = false` the block cost tracker's "actual" data-size cost update uses the artificially small value, systematically under-counting the true resource consumption of the failed load for cost-tracking/block-packing purposes.

No existing sanitization catches this: the fee itself is fixed earlier and unaffected (so no direct lamport theft), but the *cost model invariant* that "actual" accounting must reflect real work done is broken specifically in the disabled-feature path, which is `svm/src/rollback_accounts.rs`'s explicitly documented legacy compatibility shim ("This function will be removed by the fee-payer data size amendment to SIMD-186").

### Impact Explanation
This is a materially under-priced execution/cost-accounting bug: an unprivileged attacker can craft many failing transactions that touch large account data during loading but report near-zero loaded-accounts-data-size for the *actual* cost-tracker update (as opposed to the pre-execution estimate, which is unaffected). This lets the attacker's transactions consume more real account-loading I/O/CPU per unit of tracked block cost than the cost model assumes, undermining the invariant that cost-model actual-cost accounting upper-bounds/matches real work. This falls under the "materially underpriced execution reachable from an ordinary transaction" bounty category — it is a resource-accounting/cost-model integrity issue in the SVM's fee-only failure path, not a lamport-theft bug (the fee charged, in lamports, is unaffected since fee details are computed before `load_transaction` runs).

### Likelihood Explanation
This is trivially reachable by any unprivileged user submitting an ordinary transaction — no privileged role or config is needed beyond the (currently likely-inactive) `define_ltds_fee_only_semantics` feature being disabled on the cluster, which is the pre-SIMD-186 legacy behavior and thus the default/current mainnet state unless/until the feature is activated. The precondition (large writable accounts loaded prior to a load-time failure, small fee payer/nonce rollback accounts) is easy to construct deterministically, and the existing test suite in the repo already demonstrates the exact discrepancy (`0` vs actual size) for this configuration.

### Recommendation
Remove the `define_ltds_fee_only_semantics`-gated fallback to `RollbackAccounts::data_size()` (as the code comment already signals is planned) and always use the actual `LoadedTransactionDataSize` computed during `load_transaction_accounts`/`load_transaction`, capped at the requested limit, for `FeesOnlyTransaction::loaded_accounts_data_size`, independent of the feature flag. If the migration must remain feature-gated for consensus reasons, ensure the legacy fallback value is only used for state-accounting purposes not for actual-cost tracker updates (i.e., have `get_transaction_costs` fall back to the estimated cost when the feature is inactive rather than reusing the undercounted actual value), so the invariant that recorded/tracked cost never under-represents real work performed is preserved regardless of feature-gate state.

### Proof of Concept
Extend the existing integration test `fee_only_loaded_transaction_data_size` (`svm/tests/integration_test.rs:3624`) with an assertion on the cost-tracker path:
```rust
#[test_case(false; "old_fee_only")]
#[test_case(true; "simd186_fee_only")]
fn fee_only_actual_cost_never_undercounts(define_ltds_fee_only_semantics: bool) {
    // Reuse setup from fee_only_loaded_transaction_data_size: large writable
    // accounts + a failing instruction (missing program / exceeded LTDS limit).
    // ...
    // After execution, compute the "actual" cost as done by
    // runtime::transaction_execution::get_transaction_costs, using
    // committed_tx.loaded_account_stats.loaded_accounts_data_size.
    let actual_reported_size = output.processing_results[i]
        .as_ref()
        .unwrap()
        .loaded_accounts_data_size();

    // Assert the reported size used for actual cost accounting is never
    // smaller than the real bytes touched while loading the accounts
    // (sum of all large account sizes + fee payer size).
    let real_bytes_touched = loaded_fee_payer_size + other_accounts_size;
    assert!(
        actual_reported_size >= real_bytes_touched,
        "define_ltds_fee_only_semantics={define_ltds_fee_only_semantics}: \
         reported size {actual_reported_size} underestimates real work {real_bytes_touched}"
    );
}
```
Expected result: this assertion **fails** when `define_ltds_fee_only_semantics = false` (reported size is `0`, per the existing test's own assertions at lines 3743-3768), confirming the actual-cost-tracker input is undercounted relative to real account-loading work, while it **passes** when the feature is enabled (reported size equals `loaded_fee_payer_size + other_accounts_size`).

// Get actual transaction execution costs from transaction commit results
fn get_transaction_costs<'a, Tx: TransactionWithMeta>(
    bank: &Bank,
    commit_results: &[TransactionCommitResult],
    sanitized_transactions: &'a [Tx],
) -> Vec<Option<TransactionCost<'a, Tx>>> {
    assert_eq!(sanitized_transactions.len(), commit_results.len());

    commit_results
        .iter()
        .zip(sanitized_transactions)
        .map(|(commit_result, tx)| {
            if let Ok(committed_tx) = commit_result {
                Some(CostModel::calculate_cost_for_executed_transaction(
                    tx,
                    committed_tx.executed_units,
                    committed_tx.loaded_account_stats.loaded_accounts_data_size,
                    &bank.feature_set,
                ))
            } else {
                None
            }
        })
        .collect()
}
