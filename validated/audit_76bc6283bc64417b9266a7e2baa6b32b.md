### Title
Unbounded royalty + commission extraction in `token_offer::settle_payments` can abort mid-settlement and permanently strand escrowed sale proceeds - (File: aptos-move/move-examples/marketplace/sources/token_offer.move)

### Summary
`token_offer.move`'s `settle_payments` extracts a royalty amount and then a commission amount sequentially from a fixed-size `Coin<CoinType>` pool (`coin_offer.coins`, sized exactly to `item_price`) without ever re-checking or capping the second extraction against the coin value remaining after the first. This mirrors the Sherlock `Collateral.liquidate` bug class: a value used to debit a balance is computed from a stale/independent base amount rather than the balance actually available after a prior debit, so the debit call can abort due to insufficient value in the underlying resource.

### Finding Description
In `aptos-move/move-examples/marketplace/sources/token_offer.move`, `settle_payments` (lines ~360-407) does:
```
let coins = coin::extract(&mut coin_offer.coins, price);
let royalty_charge = price * royalty_numerator / royalty_denominator;
let royalties = coin::extract(&mut coins, royalty_charge);
...
let commission_charge = fee_schedule::commission(fee_schedule, price);
let commission = coin::extract(&mut coins, commission_charge);
```
Both `royalty_charge` and `commission_charge` are computed independently from the same base `price`, and `commission_charge` is not bounded by `coin::value(&coins)` (i.e., `price - royalty_charge`) before it's extracted [1](#0-0) . If `royalty_charge + commission_charge > price` (achievable whenever a token's royalty percentage plus the fee schedule's commission percentage together exceed 100%, or when royalty percentage alone is high and commission is a flat/derived fee), `coin::extract` on the second call will assert/abort due to insufficient coin value.

Contrast this with the sibling module `collection_offer.move`, which handles the exact same computation but explicitly bounds the second extraction to the coins actually remaining:
```
let commission_charge = fee_schedule::commission(fee_schedule, price);
let actual_commission_charge = math64::min(commission_charge, coin::value(&coins));
let commission = coin::extract(&mut coins, actual_commission_charge);
``` [2](#0-1) 

`token_offer.move`'s version omits this `math64::min` clamp entirely [3](#0-2) , which is precisely the corrected pattern the external Sherlock report recommends (re-derive/cap the value against the actual post-debit balance before extracting). The root cause is identical: a fee amount is calculated from a base quantity (`price`) instead of the balance that remains after a prior, related debit has already been applied to the same pool.

Because `sell_tokenv1`/`sell_tokenv2` first perform `object::transfer` (or `tokenv1::withdraw_token`/`direct_deposit_with_opt_in`) of the token itself before calling `settle_payments`, and Move transactions are atomic, an abort inside `settle_payments` reverts the entire transaction, including the token transfer. This makes `sell_tokenv1`/`sell_tokenv2` permanently unusable (a persistent denial of the settlement path) for any `TokenOffer` whose royalty/commission configuration triggers the underflow, since the escrowed `CoinOffer` and the seller's token can never be exchanged through this code path.

### Impact Explanation
This breaks the custody-critical settlement path connecting an object-held/escrowed `Coin<CoinType>` (in `CoinOffer`) with an owned `Token`/`TokenV2` object. While the buyer can eventually reclaim escrowed funds via `cancel`, the seller is permanently unable to consummate the sale offer through the intended path whenever the fee configuration crosses the threshold, effectively bricking the marketplace's core custody-transfer guarantee for that offer (an "accounts will not be liquidated/settled when they are meant to be" analog). This qualifies as a custody-accounting corruption in the underlying value-extraction invariant, matching the same bug class as the seed report (fee derived from stale/independent totals rather than the balance actually available post-debit).

### Likelihood Explanation
Reachable whenever a `FeeSchedule`'s commission percentage plus a token's royalty percentage (both attacker/creator-configurable within the collection or fee-schedule setup) sum to more than 100% of `price`, which is plausible in a permissionless marketplace where royalty numerators/denominators are set by token creators independently of the marketplace operator's fee schedule. No privileged access is required to trigger it — any buyer/seller pair interacting with such an offer hits the abort.

### Recommendation
Mirror `collection_offer.move`'s fix in `token_offer.move`: bound `commission_charge` (and defensively `royalty_charge`) to the coin value actually remaining in `coins` before each `coin::extract` call, e.g. `let actual_commission_charge = math64::min(commission_charge, coin::value(&coins));` prior to extraction, so settlement always completes with best-effort fee distribution instead of aborting.

### Proof of Concept
1. Deploy a `FeeSchedule` with `commission` set (via `fee_schedule::commission`) to, e.g., 60% of `price`.
2. Create/use a `TokenV2` whose `royalty` numerator/denominator represent 50% of `price`.
3. Buyer calls `init_for_tokenv2_entry` to create a `TokenOffer` with this fee schedule and this token, depositing `price` into `CoinOffer`.
4. Seller calls `sell_tokenv2`. Inside `settle_payments`: `royalty_charge = 0.5 * price`, extracted successfully leaving `0.5 * price` in `coins`; then `commission_charge = fee_schedule::commission(...) = 0.6 * price`, and `coin::extract(&mut coins, commission_charge)` aborts because only `0.5 * price` remains.
5. The entire `sell_tokenv2` transaction reverts, including the token transfer, so the sale can never complete through this function for this offer — confirming the DoS/settlement-lock, exactly analogous to the seed report's stuck `liquidate`.
