### Title
Simplex FX solver prices intent fills off the manipulable Uniswap V4 pool spot price - ([File: sdk/packages/simplex/src/strategies/fx.ts])

### Summary
The Simplex intent-solver's `FXFiller` strategy prices "curveless" cross-asset pairs (e.g. USDC↔cNGN) directly from the live Uniswap V4 pool mid price derived from `sqrtPriceX96`/current tick, rather than from a manipulation-resistant TWAP. This is the same bug class as Sherlock H-15 (`MavEthOracle.getPriceInEth`): a same-block spot price read from an AMM pool is trusted as ground truth for pricing/valuing a position, and can be pushed away from fair value with a flash-swap before being consumed.

### Finding Description
`resolveLegRates` in `sdk/packages/simplex/src/strategies/fx.ts` prices any pair with no configured bid/ask curves ("curveless") straight from the venue quote when the pair's `token0` is a USD-stable: [1](#0-0) 

That venue quote comes from `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd`, which is documented as returning the **raw pool mid** derived from `sqrtPriceX96`, with the pool's fee tier stored but never applied to the price, and no size/impact term: [2](#0-1) 

The only defense on this path is `checkPriceGuard`, which compares the live quote against a **static** `referencePrice` within `maxDeviationBps`: [3](#0-2) 

Critically, this guard is optional and off by default — `referencePrice`/`maxDeviationBps` are not required fields, and validation only enforces that if one is set the other must be too: [4](#0-3) 

The same unguarded (or band-tolerant) spot price is also used to size order-notional-based reorg/confirmation depth in `referenceRate`, compounding the impact of a manipulated quote: [5](#0-4) 

This mirrors the reported H-15 root cause precisely: reading a pool's *current* reserve/tick-derived price and trusting it as an oracle, with no time-weighting, letting an attacker swap in the same pool immediately before interacting with the price-consuming component, then reverse the swap afterward, all within a single attacker-controlled block/flash-loan window. Here, the "consumer" is the solver's own quoting/filling logic instead of an on-chain LMPVault, but the exploitable primitive — spot-price trust with a static-only sanity check and no TWAP/impact accounting — is identical, and it is reachable by any unprivileged party who can (a) move the configured Uniswap V4 pool's price and (b) place/trigger an order the FXFiller will price against that pool, both permissionless actions.

### Impact Explanation
An attacker can:
1. Flash-swap the configured Uniswap V4 pool (e.g. USDC/cNGN) to push its spot price up or down, while staying within any configured `maxDeviationBps` band (or entirely unconstrained if no guard is configured, which is the default/valid state).
2. Immediately place an intent order that the FXFiller prices via `resolveLegRates`'s venue path, causing the solver to compute bid/ask amounts off the manipulated spot price rather than fair value.
3. Reverse the swap to restore the pool, having caused the solver to either overpay the exotic token to the attacker or under-price its own withdrawal from V4 LP funding positions.

This can drain solver-held liquidity (the Uniswap V4 LP positions or wallet funds used to fill orders) — a direct funds-loss vector for the operator running the FXFiller strategy, consistent with the "concrete theft" criterion.

### Likelihood Explanation
Likelihood is high for any deployment that (a) enables Uniswap V4 pool-based pricing for a pair (a documented, supported configuration) and (b) does not configure the optional price guard, or configures a guard whose band is wide enough to admit a profitable manipulation relative to the pool's liquidity depth — which the code never checks (no size/impact term is applied). No privileged access is required; only the ability to swap in the referenced pool and to submit/trigger an intent order, both of which are open to any user.

### Recommendation
- Replace the raw `sqrtPriceX96`/mid-price read with a TWAP (time-weighted average, e.g. Uniswap V4 oracle observations) for venue pricing in `computeDirectPoolPriceUsd`/`getExoticTokenPrice`.
- Make the price guard (`referencePrice`/`maxDeviationBps`) mandatory whenever venue pricing is enabled, rather than optional.
- Apply a size/impact-aware price rather than extending the mid price linearly across the whole quantity (`computeLegPolicyOutput`), and apply the pool's fee tier to the quote as already noted in the internal flow docs.
- Consider requiring the quote to be sourced from multiple blocks/observations before being trusted for fills above a materiality threshold.

### Proof of Concept
1. Configure `[vault.uniswapV4]` with a position for a curveless pair (e.g. USDC/cNGN) and no `referencePrice`/`maxDeviationBps` guard, matching a supported/documented configuration in `docs/content/developers/evm/simplex/pricing.mdx`.
2. Attacker performs a large swap in the underlying Uniswap V4 pool to move `sqrtPriceX96` favorably (e.g. inflating cNGN price in USD terms).
3. Attacker submits an IntentGatewayV2 order matching this pair; the FXFiller's `canFill`/fill-sizing path calls `resolveLegRates` → `venueUsdPrice` → `computeDirectPoolPriceUsd`, which reads the now-manipulated spot price and prices the fill accordingly (`sdk/packages/simplex/src/strategies/fx.ts:1443-1465`).
4. Attacker reverses the initial swap, restoring the pool to its prior price, having captured the mispriced fill from the solver's Uniswap V4 LP-funded inventory. [6](#0-5)

	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

	/**
	 * Minimum-size reference rate (token1 per token0) for a leg's pair: the
	 * bid curve at 0 (the side token1-input legs trade at), falling back to the
	 * ask curve, then the live venue quote for venue-priced pairs.
	 */
	private async referenceRate(
		leg: ResolvedLeg,
		venueUsdPrice: (chain: string, token1Address: string) => Promise<Decimal | null>,
	): Promise<Decimal | null> {
		const policy = leg.pair.bidPricePolicy ?? leg.pair.askPricePolicy
		if (policy) {
			const rate = policy.getPrice(new Decimal(0))
			return rate.gt(0) ? rate : null
		}
		// Venue-priced pair: token0 is USD-stable (constructor invariant), so the
		// venue's USD-per-token1 quote inverts straight into token1-per-token0.
		const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
		if (!venueUsd) return null
		const venueRate = new Decimal(1).div(venueUsd)
		// Same guard as trade pricing: this rate sizes the order's USD notional
		// for confirmation depth, and a manipulated pool understating the value
		// would shrink the reorg protection — the exact attack the guard exists
		// to stop. Refusing to size skips the order, consistent with pricing.
		if (!this.checkPriceGuard(undefined, leg.token1Chain, venueRate)) return null
		return venueRate
	}

	private async resolveLegRates(
		orderId: string | undefined,
		leg: ResolvedLeg,
		cappedPairNotional: Decimal,
		venueUsdPrice: (chain: string, token1Address: string) => Promise<Decimal | null>,
	): Promise<LegRates | null> {
		// Explicitly configured curves always win — the venue only prices pairs
		// with no curves at all (and never same-token pairs, where a venue quote
		// would just be the asset's own USD price, not a spread).
		const curveless = !leg.pair.bidPricePolicy && !leg.pair.askPricePolicy
		if (curveless && !isSameTokenPair(leg.pair) && USD_STABLE_SYMBOLS.has(normalizeSymbol(leg.pair.token0))) {
			const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
			if (venueUsd) {
				// Guard compares the venue's token1-per-USD quote against the static reference.
				if (!this.checkPriceGuard(orderId, leg.token1Chain, new Decimal(1).div(venueUsd))) {
					return null
				}
				// A pool mid is ONE price, not a book: there is no opposite side
				// to report a round-trip margin against. The price guard above is
				// the venue-specific defense.
				const venueRate = new Decimal(1).div(venueUsd)
				return { rate: venueRate, oppositeRate: null, priceSource: "venue" }
			}

# Venue pricing (Uniswap V4 funded pairs)

Verified 2026-08-19.

```
resolveLegRates(...)
  curveless pair && token0 is a USD stable
    -> venuePriceMemo() -> getVenueUsdPrice(chain, token1)
         -> UniswapV4FundingPlanner.getExoticTokenPrice
              picks the position with the largest pool liquidity
              -> computeDirectPoolPriceUsd -> sdkPool.token0Price / token1Price
    -> checkPriceGuard(...)   reject if outside maxDeviationBps of the static reference
    -> rate = 1 / venueUsd
  otherwise -> the pair's ask/bid curve at the leg's notional
```

`computeDirectPoolPriceUsd` returns the **raw pool mid** derived from `sqrtPriceX96`. The pool's
fee tier is read and stored on the hydrated position (`pos.fee`) but never applied to the price,
and there is no size or impact term — `computeLegPolicyOutput` extends the mid linearly across the
whole priced quantity. `checkPriceGuard` is the only defense on this path, and it checks deviation
from a static reference, not execution cost. A venue-priced pair that has to swap through its own
pool to source inventory pays a fee tier it never quoted against.
