## Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-validating the raw request body, then trusts an HTTP header (`X-Shopify-Shop-Domain`) that is *not* part of the signed material to determine which tenant the payload belongs to. An attacker who controls any Shopify store that has this app installed can capture a legitimately-signed webhook for their own shop and replay it against the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop, and the HMAC check will still pass.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)` — which internally calls `verifiable_query.to_signable_string` (the raw body only) — and then, once that check passes, hands the *header-derived* `request.shop` straight to the app's webhook handler as authoritative tenant identity: [3](#0-2) [4](#0-3) 

This is exactly the bug class from the reference report: a value that is *acted upon* (here, `shop`, used to attribute the webhook payload to a tenant) is not covered by the same authentication mechanism (HMAC) that guards the rest of the message. The equality the gem implicitly claims — "HMAC-valid body ⇒ `shop` header is trustworthy" — does not hold, because the two are verified independently: the body's authenticity is proven, but the header's binding to that body is not.

### Impact Explanation
Any unprivileged internet user who owns (or trials) a Shopify store where the target app is installed can:
1. Trigger a real webhook event (e.g. `orders/create`) for their own shop, receiving a request with a valid `X-Shopify-Hmac-Sha256` for the body.
2. Replay that exact body/HMAC pair to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` with a victim shop's domain.
3. `Registry.process` will validate the (unchanged) HMAC successfully and dispatch the payload to the handler tagged with the victim's shop, since `WebhookMetadata.shop` comes straight from the spoofed header: [5](#0-4) 

Depending on how the host application keys its data/logic off `WebhookMetadata#shop` (which the gem presents as the validated tenant identifier post-HMAC-check), this enables cross-tenant data injection/corruption — writing or triggering side effects against a shop the attacker does not own. This satisfies the "cross-tenant access" Critical impact category, since the trust boundary the gem is supposed to enforce (HMAC-authenticated webhook ⇒ trustworthy shop attribution) is broken.

### Likelihood Explanation
High — the app's webhook signing secret (the API secret key) is shared across all shops using the app, and the webhook HMAC never binds the shop/topic/webhook-id headers. Any merchant/developer who can install the app on a test store and observe/trigger a webhook, or who can otherwise cause the app to receive a webhook for their store, can perform this attack without any privileged credentials, tokens, or TLS interception — only control of the HTTP request reaching the app's public webhook endpoint (which the request layer of this gem, not the transport, is responsible for authenticating).

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind the shop domain to the signed body (e.g., by having `to_signable_string` incorporate the headers as Shopify's official signing scheme intends the body to be paired with headers only over a channel Shopify itself controls end-to-end). At minimum, document that `WebhookMetadata#shop` is unauthenticated header data and must not be trusted by the host application for authorization decisions — but the safer fix is at the gem level: verify that the header-derived shop is consistent with any HMAC-covered value, since currently no HMAC-covered value for shop exists at all.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" with the app installed.
# 1. Attacker triggers a webhook (e.g. orders/create) for their own shop and
#    captures the real request: raw_body B, valid HMAC H = HMAC_SHA256(secret, B).

# 2. Attacker replays the same body/HMAC to the app's public webhook endpoint,
#    but swaps the shop-domain header to the victim's shop:
headers = {
  "x-shopify-topic"          => "orders/create",
  "x-shopify-hmac-sha256"    => H,                       # unchanged, still valid for body B
  "x-shopify-shop-domain"    => "victim-shop.myshopify.com", # spoofed
  "x-shopify-webhook-id"     => "any-id",
  "x-shopify-api-version"    => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation passes (it only checks body B against H).
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The app now processes attacker-controlled data as if it belongs to the victim shop.
```
