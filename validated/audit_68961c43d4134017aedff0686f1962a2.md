### Title
Unchecked ERC20 `transfer` return value in `IntentGatewayV2.withdraw`/`SweepDust` causes silent transfer failure and permanent escrow-fund lock - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2` (Tron variant) uses raw low-level `.call` to invoke `IERC20.transfer` when paying out escrowed order funds and transaction fees, but only checks the `success` boolean of the external call — it never decodes/checks the ABI-encoded `bool` return value that `transfer` yields. This is the same bug class as the reported `dispatcher.add` issue in Factory.sol: a function that can return `false` to signal failure is treated as if any non-reverting call means success, so a "soft failure" is silently accepted and internal accounting is updated as though the transfer succeeded.

### Finding Description
In `withdraw()`: [1](#0-0) 
and again for fee payout: [2](#0-1) 
and in `SweepDust` handling: [3](#0-2) 

all three sites do:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
`success` only reflects whether the call reverted, not whether `transfer` returned `true`. Non-standard/legacy ERC-20 tokens (e.g., tokens that return `false` on insufficient balance/blacklist instead of reverting) will make this call succeed (`success == true`) with a `false` return payload, meaning no tokens actually moved. Despite that, `_orders[body.commitment][token] -= amount;` (and the analogous fee/escrow debits) unconditionally decrement escrow accounting as if the payout happened, and `_filled[body.commitment]` is marked as settled.

Note that elsewhere in the same contract, deposits correctly use `SafeERC20.safeTransferFrom`, which reverts on a `false` return — only the payout/withdraw/sweep paths use the unchecked raw `.call`, making this an inconsistency rather than a deliberate design choice.

### Impact Explanation
This is reachable by any intent solver/filler or the original order placer through the normal order lifecycle (fill → `withdraw`, or cross-chain cancellation → `onGetResponse` → `withdraw`), i.e. a single relayed GET response or a solver-triggered withdrawal path — no privileged role required. If a non-standard token is configured as an order input (or if a future token upgrade/blacklist causes a `false` return), the beneficiary receives zero tokens while the contract's internal `_orders` mapping is decremented and the order is marked `_filled`. The tokens remain physically locked in the `IntentGateway` contract with no accounting path left to reclaim them (the commitment is already marked filled/cancelled), constituting a permanent freezing of escrowed user funds.

### Likelihood Explanation
Likelihood depends on the token used as an order's input asset behaving non-standard (returning `false` instead of reverting on transfer failure), which is a known, common pattern among older/legacy ERC-20 implementations (and can also be deliberately created by a malicious token deployed by an attacker as bait to grief specific fillers/solvers). Since `IntentGatewayV2` is a general cross-chain intents settlement contract not restricted to a token allowlist visible in this snippet, the risk is realistic wherever arbitrary ERC-20 addresses can be specified as order inputs.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` handler with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the deposit-side `safeTransferFrom` usage elsewhere in the contract, so that both a reverting call and a `false` boolean return are treated as failure.

### Proof of Concept
1. An order is placed with an ERC-20 input token that implements `transfer` to return `false` (rather than revert) when, e.g., the caller is blacklisted or balance is insufficient — a pattern seen in real-world non-standard tokens.
2. A solver fills the order or the order is cancelled/timed-out, routing to `withdraw()`.
3. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` with encoded `false` payload; the check `if (!success) revert TransferFailed();` passes.
4. `_orders[body.commitment][token] -= amount;` executes and `_filled[commitment]` is set, marking the order permanently settled even though `beneficiary` received 0 tokens.
5. The escrowed tokens remain stuck in the `IntentGateway` contract balance with no remaining code path to move them to the rightful beneficiary. [4](#0-3)
