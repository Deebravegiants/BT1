### Title
Webhook shop-domain spoofing due to HMAC covering only the raw body, not the `shop` header used for tenant identification - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value straight from the unauthenticated `x-shopify-shop-domain` HTTP header, while `to_signable_string` (the value that is actually HMAC-verified) contains only the raw request body [1](#0-0) . `Utils::HmacValidator.validate` only proves that the body bytes were signed with the app's shared `api_secret_key` — it never binds that signature to the `shop` (or `topic`/`webhook-id`) header [2](#0-1) . `Registry.process` then trusts `request.shop` unconditionally to build `WebhookMetadata` and dispatches it to the app's handler [3](#0-2) .

### Finding Description
The identity binding that should hold is:
`shop_header_used_for_tenant_routing == shop_that_the_HMAC_signature_actually_authenticates`

That equality does not hold here. `hmac` is computed as `HMAC-SHA256(api_secret_key, raw_body)` — only the body bytes are inside the signable string [4](#0-3) . The `shop`, `topic`, and `webhook-id` values are read straight off HTTP headers with no cryptographic tie to the signature [5](#0-4) .

Because the app's `api_secret_key` (`client_secret`) is shared across **every** shop that installs the app — it is not shop-specific — any merchant who installs the app (a normal, unprivileged action for a public app) legitimately receives real webhook deliveries for their own shop, each with a valid `(raw_body, hmac)` pair signed with that same shared secret. Such a merchant can then replay that exact `raw_body`/`hmac` pair directly to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header (and optionally `x-shopify-topic`) with an arbitrary victim shop's domain. `HmacValidator.validate` will still succeed, because it only checks the body signature, and `Registry.process` will hand the forged `shop` value straight to the registered handler as if it genuinely came from the victim tenant [3](#0-2) .

This is the same bug class as the "missing ownership check" in the external report: a field that is *acted upon* (here, the tenant/shop used to route and process the webhook) is not covered by the authenticity check (here, the HMAC), letting an attacker substitute an object (shop identity) they don't own for one that passes verification.

### Impact Explanation
Any host application that uses `request.shop` from `WebhookMetadata` to select which merchant/session record to read or mutate (the normal, documented usage pattern for this gem) can be made to apply attacker-supplied webhook body data against a different, victim tenant's session/data. This is a cross-tenant data-integrity/confusion issue reachable by any user who can install the app on a shop they control and can send arbitrary HTTP requests to the app's public webhook endpoint — no access token, refresh token, or `api_secret_key` disclosure is required.

### Likelihood Explanation
Requires only: (1) an attacker-controlled shop that has installed the target app (normal, often self-serve action for public apps) and thus received at least one legitimately-signed webhook, and (2) the ability to send an HTTP POST to the app's public webhook endpoint with modified headers, which is a standard capability of any internet client. No credential leakage or privileged access is needed.

### Recommendation
Include the identifying headers (`shop`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed content used for verification, or otherwise cryptographically bind them (e.g., verify the signature per-shop rather than per-app, or require the host application to independently re-validate the `shop` value against its own record of active installations before trusting it) instead of relying on the header value alone in `to_signable_string`.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled shop `evil.myshopify.com`.
2. Trigger any webhook subscription (e.g., `orders/create`) so Shopify delivers a real webhook to the app's endpoint with a valid `x-shopify-hmac-sha256` header computed over the raw JSON body using the app's shared `api_secret_key`.
3. Capture the exact `raw_body` and `x-shopify-hmac-sha256` value from that request.
4. Replay an HTTP POST to the same webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` (only body bytes are checked) [2](#0-1) , and `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"` and the attacker's body content [3](#0-2) .

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
