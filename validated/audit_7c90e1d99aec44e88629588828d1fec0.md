### Title
`WrappedHyperFungibleToken.send()` dispatches the pre-fee `params.amount` instead of the actual tokens locked, allowing fee-on-transfer/deflationary underlying tokens to drain the destination-side reserve - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` and its upgradeable counterpart `WrappedHyperFungibleTokenUpgradeable.send()` lock the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` but never verify how many tokens were actually received. The cross-chain message body is built with the caller-supplied `params.amount`, not the measured balance delta. If the underlying token charges a transfer fee (either natively or via a future upgrade, mirroring the exact USDC-upgrade scenario cited in the reference report), the contract locks less than `params.amount` yet instructs the destination chain to release/unlock the full `params.amount` from its own underlying reserve.

### Finding Description
In `send()`:
```solidity
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
...
bytes memory body = abi.encode(HyperFungibleToken.Message({
    from: abi.encodePacked(msg.sender),
    to: params.to,
    amount: params.amount, // <-- not the actually received/locked amount
    data: params.data
}));
``` [1](#0-0) [2](#0-1) 

On the receiving chain, `onAccept()` unconditionally pays out `message.amount` from its own pool of locked underlying tokens:
```solidity
IERC20(_underlying).safeTransfer(beneficiary, message.amount);
``` [3](#0-2) 

The same pattern exists in the upgradeable variant: [4](#0-3) [5](#0-4) 

This is the same bug class flagged in the reference report (blindly trusting a `transferFrom`-stated amount instead of measuring actual balance change for potentially fee-on-transfer/upgradeable tokens). Notably, the codebase's own `IntentGatewayV2.placeOrder()` already defends against exactly this class of bug by measuring balances before/after the transfer and mutating the recorded amount to the actual received value:
```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
``` [6](#0-5) 

`WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` were not given this same protection, despite implementing an analogous lock-based cross-chain bridging function.

### Impact Explanation
Any unprivileged caller can invoke `send()` with an underlying token that has (or is later upgraded to have) a transfer fee. Each such call causes the contract to lock `amount - fee` tokens while committing to release the full `amount` on the destination chain's reserve. Repeated sends progressively decouple the source-side locked balance from the cumulative amount promised to be unlocked on the destination side. Since the destination-side reserve is shared collateral funded by all users bridging that asset, this results in insolvency of the underlying token reserve — later legitimate unlock/withdraw calls for other users can fail or drain reserves meant for others, i.e., permanent freezing/loss of funds for the protocol's locked collateral pool. This matches "concrete theft or permanent freezing of funds" / "unbacked mint" criteria, since more tokens are unlocked on the destination than were ever actually locked on the source.

### Likelihood Explanation
Likelihood depends on whether a fee-on-transfer or upgradeable-fee token is configured as `_underlying` for a given deployment. Since `configure()` is owner-controlled and token selection is a deployment/governance decision, this is not guaranteed to be exploitable for every deployment, but for any deployment wrapping a token capable of taking a transfer fee (deflationary tokens, or an upgradeable stablecoin like USDC that later adds fee-on-transfer, exactly as described in the reference report), exploitation requires only a single ordinary `send()` call — no privileged access needed.

### Recommendation
Measure the underlying token balance before and after `safeTransferFrom` in `send()`, and use the delta (actual received amount) as `params.amount` when building the dispatch message, consistent with the fee-on-transfer handling already implemented in `IntentGatewayV2.placeOrder()`. Apply the same fix to both `WrappedHyperFungibleToken.sol` and `WrappedHyperFungibleTokenUpgradeable.sol`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` configured with an underlying ERC20 that charges a 1% transfer fee (e.g., the `FeeOnTransferToken` test helper already present in the repo's test suite, used in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`).
2. Call `send({amount: 1000e18, ...})`. `safeTransferFrom` moves only 990e18 tokens into the contract (10e18 burned as fee), verified via `IERC20(_underlying).balanceOf(address(this))`.
3. The dispatched `Message.amount` is still `1000e18`.
4. On the destination chain's `WrappedHyperFungibleToken.onAccept()`, `IERC20(_underlying).safeTransfer(beneficiary, 1000e18)` is executed — paying out 1000e18 real underlying tokens even though only 990e18 were ever locked on the source chain, creating a 10e18 deficit in the bridge's real backing per such transfer.
