### Title
Batch withdrawal status matched only by `assetId`, misreporting completion/tx hash across same-token withdrawals in a batch - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` and the shared `findMatchingWithdrawal` helper in `internal-utils` identify a specific withdrawal within a POA Bridge response solely by `assetId` (i.e. `near_token_id`), ignoring the withdrawal's index, destination address, and amount. This is analogous to the reported bug class: an on-chain outcome (status/hash) is looked up using a key (asset id) that does not uniquely identify the specific transition/withdrawal it is meant to describe when a single NEAR transaction contains a batch with more than one withdrawal of the same asset.

### Finding Description
`describeWithdrawal` fetches all withdrawals for a NEAR tx hash and then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which does: [1](#0-0) 

The matching function itself only compares `near_token_id` to the requested `assetId` and returns the first hit; it does not compare destination address, amount, or position/index: [2](#0-1) 

The code comment explicitly acknowledges this limitation: "Currently only matches by assetId (near_token_id). This means multiple withdrawals of the same token in a single transaction are not supported." [3](#0-2) 

The SDK's batch withdrawal API (`processWithdrawal`/`signAndSendWithdrawalIntent` with `WithdrawalParams[]`) does not appear to reject or dedupe multiple entries that share the same `assetId` but differ in `destinationAddress` or `amount`. If such a batch is submitted through the POA route, `describeWithdrawal` is later called once per withdrawal index, each with the identical `assetId`. Since the underlying matcher ignores index/destination/amount, every call returns the same (first-found) withdrawal record from the POA Bridge response — i.e., the same `status` and `transfer_tx_hash` — regardless of which of the two withdrawals is actually being queried.

This breaks the equality "status/txHash reported for withdrawal N corresponds to the on-chain outcome for withdrawal N": a caller polling completion for withdrawal #1 (destined for address B) can receive "completed" with the destination tx hash that actually corresponds to withdrawal #0 (destined for address A).

### Impact Explanation
If an integrator uses `describeWithdrawal`/`waitForWithdrawalCompletion` per-withdrawal status to decide when to credit a user or mark a leg as settled, a batch of two same-asset withdrawals with different destinations/amounts could cause the integrator to attribute the wrong destination-chain transaction hash to a withdrawal, or report both withdrawals as "completed" once only one of the two POA-side legs has actually settled. This matches the listed High impact category: "a status or hash misreport making an integrator credit or refund twice." The severity depends on real-world usage of batching same-asset withdrawals to different destinations via the POA route, which I could not fully confirm — I did not find code in `sdk.ts` that prevents or deduplicates same-`assetId` entries in a batch `withdrawalParams` array.

### Likelihood Explanation
Likelihood is limited by two mitigating factors I could observe but not conclusively rule out:
1. The bug requires a batch of ≥2 withdrawals sharing the exact same `assetId` within a single NEAR withdrawal transaction routed through `PoaBridge`.
2. The code and its own comments treat this as a known, documented limitation rather than a silent flaw, suggesting it may be a recognized product constraint rather than an actively exploited condition.

I was not able to verify (within index limits) whether `sdk.ts`/`shared-types.ts` enforce a "one entry per assetId" constraint on batch withdrawal parameters before dispatching to `PoaBridge`; if such validation exists, this finding would be moot for the POA route.

### Recommendation
- Enforce (or explicitly document and validate) that batch withdrawals routed through `PoaBridge` cannot contain multiple entries with the same `assetId`, rejecting such requests at `createWithdrawalIntents`/`processWithdrawal` time.
- Alternatively, extend `findMatchingWithdrawal` to disambiguate by destination address and amount (or an index/ordinal hint from POA) in addition to `near_token_id`, so each `describeWithdrawal` call for a given index is guaranteed to reference the correct on-chain leg.

### Proof of Concept
Not independently reproducible from the indexed context alone — I could not confirm whether the SDK permits submitting a batch with duplicate `assetId` withdrawals through the POA route from `sdk.ts`. The vulnerable matching logic itself is directly demonstrable: [4](#0-3) 
Given a POA response containing two withdrawals for the same `near_token_id` (different destinations/amounts), calling `findMatchingWithdrawal` (and therefore `PoaBridge.describeWithdrawal`) for either index returns the same first match, demonstrating the collision.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
