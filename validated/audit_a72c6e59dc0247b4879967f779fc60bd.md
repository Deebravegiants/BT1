### Title
Webhook tenant (`shop`) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before invoking the app's webhook handler with the shop identity attached to the payload. In reality, the HMAC signature only binds the raw request body — the `shop`, `topic`, `webhook_id`, and `api_version` values (all taken from unauthenticated HTTP headers) are never included in the signed material, yet `shop` is trusted and handed to the app's handler as the tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` (and `topic`, `webhook_id`, `api_version`) are read straight from HTTP headers with no cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely over `to_signable_string` (i.e., the raw body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` gates handler execution solely on this body-only HMAC check, then forwards the unauthenticated `request.shop` header straight to the app's handler as the tenant identity: [4](#0-3) 

The equality the gem implicitly claims is: `shop used to authorize/attribute the webhook == shop covered by the HMAC`. In fact `shop` is never part of the signed string, so this equality does not hold — any request whose *body* carries a valid HMAC (e.g., a body genuinely signed by Shopify for the attacker's own shop) will pass validation regardless of what `shop` header accompanies it. The docs explicitly state that `process` "will verify the request did indeed come from Shopify," which overstates what is actually verified: [5](#0-4) 

### Impact Explanation
An unprivileged internet user who legitimately installs the target app on their own shop (no special privileges required) will receive genuine Shopify webhooks — real body+HMAC pairs signed by the app's `api_secret_key` — for their own shop and topics. They can then replay that exact body/HMAC pair directly to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with any arbitrary value, including another (victim) shop's domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` calls the app's handler with `shop: <attacker-chosen value>` and the replayed body content. Any host application that uses `data.shop` (as the docs instruct: `perform_later(shop_domain: data.shop, ...)`) to route data, update per-tenant records, or authorize actions will attribute attacker-controlled data to an arbitrary shop, i.e., cross-tenant data injection/confusion.

### Likelihood Explanation
High likelihood of exploitability once an attacker has any account on the platform capable of receiving real webhooks (a normal, unprivileged action — installing the app on a shop they control). No credentials, access tokens, or `api_secret_key` are required from the attacker; they simply need to capture one legitimate body+HMAC pair generated for their own tenant and replay it with modified headers.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`) values into the signed material that `HmacValidator` verifies, or independently verify that `request.shop` corresponds to a shop with an active session/installation known to the app before trusting it as the tenant identity. At minimum, update `to_signable_string` in `lib/shopify_api/webhooks/request.rb` to include the shop domain, and update the documentation in `docs/usage/webhooks.md` to accurately describe that only body integrity is verified, not header authenticity.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (normal, unprivileged flow).
2. Shopify sends a legitimate webhook to the app's registered endpoint: body `B`, header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same request to the app's webhook endpoint but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and/or alters `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes the HMAC over `B` only and matches — validation passes.
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's original payload>, ...)`, causing the host app to process attacker-controlled data under the victim shop's identity.

          received_signature = verifiable_query.hmac

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
