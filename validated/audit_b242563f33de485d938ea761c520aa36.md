## Title
Unrestricted `CallDispatcher.dispatch()` allows anyone to steal ETH/tokens stranded in the shared dispatcher contract - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is deployed once and shared across `IntentGatewayV2`, `HyperFungibleToken` and `WrappedHyperFungibleToken` to execute arbitrary user-supplied `Call[]` batches (predispatch/postdispatch swaps, cross-chain calldata execution) while temporarily holding the assets being routed. Its `dispatch()` function has **no access control** — any address can call it directly, at any time, and instruct it to move out whatever ETH or ERC-20 balance the contract currently holds. [1](#0-0)  This mirrors the `PeripheryPayments.refundETH()` bug class: a contract that is not supposed to retain funds, but has an unauthenticated public entry point capable of moving out whatever balance happens to be resting on it.

### Finding Description
`CallDispatcher` accepts ETH via a permissionless `receive()` and exposes `dispatch(bytes memory encoded)` with zero caller restriction — it is not gated to the intent gateway, the host, or any registered app:
```solidity
receive() external payable {}
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    if (!success) revert CallFailed(to, result);
}
``` [2](#0-1) 

`IntentGatewayV2` relies on this contract to temporarily hold funds mid-flow: predispatch assets are pushed to `dispatcher`, an arbitrary swap `Call[]` is dispatched, and only the tokens explicitly listed in `order.inputs`/`order.output.assets` are swept back with dust accounting: [3](#0-2)  and [4](#0-3) . `HyperFungibleToken`/`WrappedHyperFungibleToken` similarly route minted or unwrapped tokens through the same shared `dispatcher` and its calldata: [5](#0-4) . The docs explicitly acknowledge tokens are held there "temporarily" and warn about exact-amount approvals precisely because of this exposure. [6](#0-5) 

Because the sweep logic only recovers the exact declared input/output tokens (`order.inputs[i].token` / `order.output.assets[i].token`), any additional token or native-ETH residue produced by a user- or solver-supplied `predispatch.call`/`output.call` (e.g., router refunds, reward tokens, rounding remainders, or ETH sent to the dispatcher's open `receive()`) is left stranded on `CallDispatcher`. Since `dispatch()` has no caller restriction, this residue — or any ETH/tokens that land on the shared dispatcher from any app's in-flight operation — can be drained by an unrelated third party who simply calls `CallDispatcher.dispatch()` with a `Call[]` transferring the current balance to themselves, exactly analogous to front-running an open `refundETH()`.

### Impact Explanation
Any excess ETH or ERC-20 tokens that transiently rest on the shared `CallDispatcher` (from intent-gateway predispatch/postdispatch swaps, or HFT calldata execution) can be permanently stolen by any unprivileged address, since ownership of the "leftover" balance is never enforced at the point where it is claimable — this is a direct loss-of-funds vector for order placers, solvers, and cross-chain transfer recipients relying on the shared dispatcher.

### Likelihood Explanation
`CallDispatcher` is deployed as a single, address-referenced, shared utility across multiple production apps, and its `dispatch()` and `receive()` functions are both fully public. Any residual balance — however it arises (dust from a DEX swap, a reward token, a mis-sized approval, or an errant transfer) — is instantly and trivially exploitable by any address monitoring the dispatcher's balance, with no special privileges, no proof, and no timing constraints beyond outracing the legitimate sweep.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a caller allowlist (e.g., only the registered `IntentGatewayV2`/`HyperFungibleToken`/`WrappedHyperFungibleToken` instances configured at deployment), or make dispatcher instances per-caller/per-order rather than a shared singleton so no unrelated party can ever invoke `dispatch()` against another party's in-flight funds. Additionally, ensure sweep logic in `_execute`/predispatch handling captures the dispatcher's *full* balance of any token that could plausibly be produced by the executed calldata, not just the tokens explicitly declared in `order.inputs`/`order.output.assets`.

### Proof of Concept
1. A user calls `IntentGatewayV2.placeOrder` with `predispatch.call` that swaps ETH for `DAI` via the shared `CallDispatcher`, but the swap router returns a small amount of a bonus/reward token, or leftover native ETH, that is not one of `order.inputs`.
2. `IntentsBase`/`IntentGatewayV2` sweeps back only the declared `order.inputs` token balances from `dispatcher`; the extra token/ETH remains on `CallDispatcher`.
3. An attacker, watching the mempool or simply polling `CallDispatcher`'s balances, calls `CallDispatcher.dispatch(abi.encode(calls))` directly with a `Call` that transfers the stranded token/ETH balance to their own address — this succeeds because `dispatch()` has no access control.
4. The excess funds are permanently lost to the legitimate order participant.

     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
