### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted for tenant routing but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#hmac` is verified against `to_signable_string`, which returns only `@raw_body` [1](#0-0) . However, the `shop`, `topic`, `webhook_id`, and `api_version` values consumed by `Registry.process` and handed to the app's `WebhookHandler` are all pulled from unauthenticated HTTP headers, never included in the HMAC-signed material [2](#0-1) .

### Finding Description
`Utils::HmacValidator.validate` calls `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac` [3](#0-2) . For webhook requests, `to_signable_string` is defined as simply the raw request body, and `hmac` is read from the `hmac-sha256` header [4](#0-3) [1](#0-0) . This correctly proves that the *body bytes* were signed by Shopify with the app's `client_secret`. But `Registry.process` uses `request.topic`, `request.shop`, and other header-derived values — none of which are part of the signed payload — to route the callback and populate `WebhookMetadata` that the merchant's app trusts as the tenant identity for the event: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))` [5](#0-4) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all pulled from the `shopify-*`/`x-shopify-*` headers with no cryptographic binding to the HMAC-verified body [2](#0-1) .

This is precisely the identity-binding gap described in the analog rule: "a field acted on but not covered by the HMAC." The equality that should hold is:
`hmac_verified_bytes == (headers used for tenant/topic routing)`
but in this implementation:
`hmac_verified_bytes == raw_body only`, while `shop/topic/webhook_id/api_version (unverified headers) != raw_body`.

Because Shopify's real webhook delivery always sends consistent headers and body together, this gap is not exploitable through Shopify itself. It is only reachable if the host application exposes the raw HMAC-validation primitive to attacker-influenced input (e.g., a test/proxy endpoint, a queue consumer that reconstructs `Request` from separately-sourced header/body data, or any component that lets an unprivileged caller supply headers independently of the signed body) — which is a host-application design decision, not something this gem enforces or guards against.

### Impact Explanation
If an integrator ever separates the header values from the signed body (e.g., across a message queue, a webhook relay, or a batching layer) — a legitimate use given `Registry.process` accepts a `Request` object constructed from `raw_body:` and `headers:` independently — an attacker who can influence only the headers (not the body) could cause a webhook payload validly signed for one shop to be attributed to a different `shop` value, since `shop` is never part of the HMAC input. This would let webhook data be mis-routed/misattributed across tenants (cross-tenant confusion) within the app's webhook-handling code, without needing the `client_secret` itself.

### Likelihood Explanation
Low-to-moderate. Direct exploitation strictly through Shopify's own webhook delivery endpoint is not possible, since Shopify controls both headers and body together and signs consistently. The exposure exists only when the host application's own architecture (queueing, relaying, multi-step processing) reconstructs a `ShopifyAPI::Webhooks::Request` from headers and body sourced separately — which the gem's API implicitly permits since `initialize(raw_body:, headers:)` takes them as independent parameters with no cross-validation. This is an architectural weakness in the gem's trust model for `Request`, not a "host ignoring documented API" issue, because the gem itself performs the HMAC check and then trusts unrelated header fields without documenting that they carry no integrity guarantee.

### Recommendation
Bind the tenant/topic-identifying fields into the HMAC-verified surface, or explicitly document/enforce that `shop`, `topic`, `webhook_id`, and `api_version` are unauthenticated and must not be used for authorization or tenant-isolation decisions without additional verification (e.g., cross-checking `shop` against a known/authorized shop list per topic before invoking the handler). At minimum, `Registry.process` should re-verify that the `shop` header matches an expected/allow-listed shop domain for the current app installation before dispatching to `WebhookHandler#handle`.

### Proof of Concept
1. Take a legitimate webhook body and its Shopify-computed `hmac-sha256` header value for `shop-a.myshopify.com`.
2. Construct `ShopifyAPI::Webhooks::Request.new(raw_body: <same body>, headers: { "shopify-hmac-sha256" => <same hmac>, "shopify-topic" => "orders/create", "shopify-shop-domain" => "shop-b.myshopify.com", ... })` — i.e., keep the body and HMAC identical but swap in a different `shop-domain` header.
3. Call `ShopifyAPI::Webhooks::Registry.process(request)`. `Utils::HmacValidator.validate(request)` passes because it only checks the raw body against the HMAC [6](#0-5) , and the handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` even though the payload was only ever signed in the context of `shop-a` [7](#0-6) .

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
