### Title
Unvalidated route bytes let a swap venue invoke arbitrary contract calls inside the signer's authorization tree, draining unrelated wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_tokens` forwards caller-supplied `swap` bytes verbatim to the router and wraps the whole `execute_strategy` call inside the caller's `require_auth` tree (`swap.rs:34-38`). The route XDR names the venue contracts it hops through, and the controller imposes no venue allowlist — it only measures `token_in` spend and `token_out` receipt (`swap.rs:40-54`). A malicious venue contract invoked by the route can therefore request additional `require_auth` sub-invocations (e.g., `token.transfer(victim, attacker, x)` on any token the victim holds), which Soroban simulation records under the victim's `swap_collateral`/`swap_debt`/`multiply`/`repay_debt_with_collateral` auth entry. The route still pays a fair `token_out` amount, so every controller check passes and the theft appears as just another sub-invocation the wallet asks the user to sign — the direct analog of a crafted terminal link passed unvalidated to `shell.openExternal` and detonated by one click.

### Finding Description
In `swap_tokens`, the controller:
1. Reads the configured router (`storage::get_swap_aggregator`, `swap.rs:25`).
2. Authorizes exactly one input transfer (`authorize_transfer_as_current`, `swap.rs:34`).
3. Calls `router.execute_strategy(&controller, &amount_in, swap)` under `with_flash_guard` (`swap.rs:36-38`), where `swap` is raw attacker-influenceable `Bytes` supplied to `swap_debt` / `swap_collateral` / `multiply` / `repay_debt_with_collateral` (see `SwapDebtParams.swap` at `strategies/swap_debt.rs:23` and the pass-through at `swap_debt.rs:65-72`).
4. Validates only `in_after <= in_before`, `actual_spent <= amount_in`, and `received > 0` on the output token (`swap.rs:41-54`, `swap.rs:75-84`).

Nothing in the controller inspects which contracts the route invokes. The in-repo adversarial test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves the consequence end-to-end: a `RoutedSwap` payload naming an attacker-deployed `RogueHopPool` causes `token.transfer(alice, attacker, WALLET_BALANCE)` on a token the protocol never listed, and the recorded auth tree attaches that transfer beneath Alice's `swap_collateral` entry (`rogue_hop_pool_transfer_joins_caller_auth_tree.rs:194-227`). In enforcing mode, once Alice signs the simulation-derived tree, the transfer executes and her entire balance of the unrelated token is stolen (`rogue_hop_pool_transfer_joins_caller_auth_tree.rs:258-268`), while her `swap_collateral` still completes with the fair output (`assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH)`).

### Impact Explanation
Theft of user funds: any token balance (or other auth-gated action) belonging to the signer can be drained in the same transaction that performs a legitimate-looking strategy swap. The victim only sees and signs an authorization tree produced by simulation of a `swap_collateral` call that returns exactly the expected output — the malicious transfer is hidden inside opaque route bytes the controller never decodes or validates. A malicious quote/route provider (or any attacker who can get a victim to submit crafted `swap` bytes) gains arbitrary invocation capability scoped to the victim's signature, mirroring the electerm bug where a crafted URI reaches `shell.openExternal` and detonates on a single click.

### Likelihood Explanation
Reachable by a single unprivileged interaction: the victim calls `swap_collateral`/`swap_debt`/`repay_debt_with_collateral`/`multiply` with route bytes obtained from an untrusted source. The route produces honest swap output, so on-chain result, simulation, and all controller invariants look correct; exploitation requires only that the victim sign the recorded auth tree — analogous to the single link click in the report. Because route bytes are opaque packed XDR built off-chain and passed "untouched" to the contract, the signer has no practical way to see the rogue pool address embedded in the payload, and the extra `transfer` sub-invocation appears in the auth tree only as a routine-looking token call.

### Recommendation
Constrain what route execution can request under the user's auth. Options:
- Have the router enforce a governance-managed venue allowlist (or venue-code allowlist) so payloads cannot name arbitrary contracts.
- In `swap_tokens`, additionally snapshot the caller's (and controller's) balances of all relevant tokens — or better, isolate route execution from the caller's auth context so route hops run under the router's own authority only, making victim-targeted `transfer` requests impossible to satisfy.
- At minimum, document and surface the auth-tree risk: reject payloads whose execution records sub-invocations beyond the single expected `token_in` transfer authorization.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` is a working exploit: `route_through_pool_stealing` builds a `RoutedSwap` whose `hop_pool` is an attacker contract (`RogueHopPool`) preloaded with `(victim, wallet_token, attacker, amount)`. `UnlistedPoolRouter.execute_strategy` pulls `token_in`, invokes `hop_pool.swap()`, and returns the fair `min_out`. The `swap_collateral` call succeeds; in recording mode the rogue `transfer` is attached under Alice's controller auth entry (`lines 194-227`), and in enforcing mode signing that tree moves the full `WALLET_BALANCE` to the attacker while Alice receives the correct ETH output (`lines 258-268`). The benign control (amount 0) and the honest-tree rejection (`lines 233-256`) isolate the flaw to unvalidated route venues, not auth mechanics.
