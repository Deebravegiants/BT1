### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied `shop` header straight to the app's handler as the trusted tenant identifier. Because the `shop-domain` header is never included in the HMAC-signed material, an attacker who can obtain one validly-signed webhook body/HMAC pair (e.g. by installing the app on their own store and receiving a real webhook) can replay that same body+HMAC to the app's webhook endpoint with an arbitrary `shop-domain` header, and the library will report it as an authenticated webhook for that arbitrary shop.

### Finding Description
`Webhooks::Request` builds a `VerifiableQuery` whose signable content is only the raw HTTP body: [1](#0-0) [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are not part of `to_signable_string`, so they are attacker-controllable on any request whose `raw_body` matches a value that was previously HMAC-signed by Shopify for the app's `api_secret_key`.

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as full authentication of the entire `request`, including `request.shop`, and forwards that unverified `shop` value straight into the handler's trusted metadata: [4](#0-3) 

The identity binding that should hold is:
`HMAC-verified bytes == all fields the handler treats as authenticated (including shop)`

but the actual binding is:
`HMAC-verified bytes == raw_body only`, while `shop` (and `topic`/`webhook_id`) are parsed from unauthenticated headers and passed through as if verified.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` (from `Registry.process`) to select which merchant's session, access token, or database record to act on is vulnerable to cross-tenant impersonation: an attacker who legitimately installs the app on their own store obtains at least one genuine `(raw_body, hmac)` pair signed with the app's shared `api_secret_key` (the key is the same across all shops using the app, only the body differs, but is capturable via a replayable payload such as a no-op `shop/redact`-shaped body or any single webhook the attacker can trigger against their own store). Replaying that identical body+HMAC to the app's webhook endpoint with the `shop-domain` header set to a victim shop passes `Utils::HmacValidator.validate`, causing the handler to execute with `data.shop` set to the victim's domain — enabling cross-tenant data corruption/impersonation without any credential belonging to the victim.

### Likelihood Explanation
The attacker only needs to be able to install the target app on their own shop (an ordinary, unprivileged merchant action) to capture a valid webhook body/HMAC pair, and needs no knowledge of `api_secret_key` beyond what Shopify itself provides via a legitimate delivery. Reachability requires only unauthenticated HTTP access to the app's public webhook endpoint, matching the "unprivileged internet user" threat model.

### Recommendation
Bind the authenticated headers (`shop`, `topic`, `webhook_id`) into the signable content verified by `HmacValidator`, or otherwise cryptographically tie `request.shop` to the verified payload before it is passed to `WebhookMetadata`, so the HMAC check attests to the full tuple `(shop, topic, body)` rather than the body alone.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and receives (or triggers) any webhook delivery, capturing the raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (computed by Shopify with the app's `api_secret_key`).
2. Attacker POSTs to the app's webhook endpoint with headers `X-Shopify-Topic: <same topic>`, `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: victim-shop.myshopify.com`, and body `B` unchanged.
3. `Webhooks::Request.new` parses these headers [5](#0-4)  and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H` [6](#0-5) .
4. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, even though the request was never sent by or for that shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
