### Title
`Webhooks::Request` binds shop/topic identity to unauthenticated headers instead of the HMAC-verified body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`HmacValidator.validate` only authenticates `@raw_body` against the app secret via `to_signable_string`; it never covers the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Webhooks::Request#shop`/`#topic`/`#webhook_id` read those headers directly and `Registry.process` passes them, unauthenticated, into `WebhookMetadata`, which the host app uses to decide whose tenant data to mutate. An attacker who obtains one validly-signed webhook body (e.g., for their own development shop) can resubmit the identical body with a forged `shop-domain`/`topic` header and it will still pass HMAC validation.

### Finding Description
The invariant that should hold is: `shop_identity_used_by_handler == shop_identity_covered_by_hmac`. Tracing the code shows this is false.

- `to_signable_string` returns only `@raw_body` [1](#0-0) .
- `HmacValidator.validate_signature` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac` header; it never folds in any other header [2](#0-1) .
- `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are all read straight from attacker-supplied HTTP headers with no cross-check against the signed body [3](#0-2) .
- `Registry.process` validates the HMAC, then builds `WebhookMetadata` purely from these header-derived, unauthenticated values plus `request.parsed_body` (itself just `JSON.parse(@raw_body)`, i.e., the same signed bytes) [4](#0-3) .

Because Shopify apps typically share a single `client_secret` (`Context.api_secret_key`) across all merchants that install the app, any shop the attacker controls can legitimately trigger a webhook delivery and thereby obtain a body+HMAC pair that is valid under the shared secret. Since the signature covers only the body bytes, the attacker can replay that exact body to the host app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to a victim shop's domain (and/or the `X-Shopify-Topic` header to a different registered topic). `HmacValidator.validate` still returns `true` because it never inspects headers, so `Registry.process` dispatches the handler with `WebhookMetadata#shop` equal to the forged victim domain and/or a forged topic, while the actual authenticated payload is the attacker's own shop's data.

No existing guard closes this gap: `ShopValidator.sanitize!`, `JwtPayload`'s `aud` check, and `Context.setup?`/`private?`/`embedded?` apply to OAuth/session-token flows, not to the webhook `Request`/`Registry` path, which has no equivalent binding of headers to the signed payload.

### Impact Explanation
The host app's webhook handler receives a `WebhookMetadata#shop` value that does not correspond to the shop whose data was actually signed. Any handler logic keyed off `data.shop` (looking up the merchant's stored `access_token`/session, writing order/customer/product records, or triggering `shop/redact` / `app/uninstalled` cleanup) can be made to act on a victim merchant's identity using attacker-supplied body content, or vice versa — cross-tenant data confusion. If the handler uses the (forged) `shop` to fetch and then use/return that merchant's stored Admin API access token (a common pattern, e.g., re-issuing API calls in response to a webhook), the attacker can trigger operations against the victim's store using the victim's token, which is the mechanism by which the token's authority is effectively stolen/misused. This is repeatable against any victim shop domain known to the attacker (shop domains are not secret) and against any topic registered by the host app.

### Likelihood Explanation
Preconditions: the host app must be a normal ShopifyAPI-gem-based app with at least one registered webhook handler (default usage). Attacker cost: create/use one development shop, install the app, trigger any webhook event to capture one valid `(raw_body, hmac)` pair signed under the shared app secret, then replay that body to the app's public webhook endpoint with a forged `shop-domain`/`topic` header. No secrets, no session, and no privileged access are required — only knowledge of the app's public webhook URL and a victim shop domain, both of which are not confidential. This is fully repeatable per victim/topic combination.

### Recommendation
Bind the shop and topic identity cryptographically to the verified request instead of trusting headers post-hoc: include `shop-domain`, `topic`, and `webhook-id` in the HMAC-signable string (or otherwise verify them against a value obtained from an authenticated source, e.g. cross-checking against the registered subscription/session for that shop) before constructing `WebhookMetadata`, so `Registry.process` cannot dispatch header-derived shop/topic values that weren't part of what Shopify actually signed.

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (new test)
test "shop and topic headers are not authenticated by the HMAC and can be replayed for a different tenant/topic" do
  ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)

  raw_body = '{"id":1,"note":"attacker shop order"}'
  hmac = OpenSSL::HMAC.hexdigest(OpenSSL::Digest.new("sha256"), "secret", raw_body)
  hmac_b64 = Base64.encode64(Digest.hexdecode(hmac))

  handler_orders = ... # registered for "orders/create"
  handler_victim = ... # registered for some other topic, e.g. "shop/update"

  # Attacker's legitimately-signed body for their own shop, topic "orders/create"
  attacker_request = ShopifyAPI::Webhooks::Request.new(
    raw_body: raw_body,
    headers: {
      "x-shopify-hmac-sha256" => hmac_b64,
      "x-shopify-topic" => "orders/create",
      "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
      "x-shopify-webhook-id" => "1",
      "x-shopify-api-version" => "2023-10",
    },
  )
  ShopifyAPI::Webhooks::Registry.process(attacker_request) # succeeds normally

  # Replay identical signed body, forging shop-domain to victim + topic unchanged/different
  forged_request = ShopifyAPI::Webhooks::Request.new(
    raw_body: raw_body,
    headers: {
      "x-shopify-hmac-sha256" => hmac_b64,          # same signature, still valid
      "x-shopify-topic" => "orders/create",
      "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
      "x-shopify-webhook-id" => "1",
      "x-shopify-api-version" => "2023-10",
    },
  )

  assert ShopifyAPI::Utils::HmacValidator.validate(forged_request) # HMAC still passes

  # WebhookMetadata built with the forged victim shop despite body being signed only for attacker's shop
  ShopifyAPI::Webhooks::Registry.process(forged_request)
  # assert handler_orders received data.shop == "victim-shop.myshopify.com"
  # even though the signed content was attacker-controlled and never authenticated for that shop
end
```
