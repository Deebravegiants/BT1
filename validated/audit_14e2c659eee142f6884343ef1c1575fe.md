### Title
Zero-token Emporium path bypasses all signature/UTXO-ownership proof and skips the balance equation, allowing theft of pooled ETH/tokens held by the Emporium external action - (File: `contracts/CircomDataBuilder.sol`, `contracts/Hinkal.sol`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When a `transact()` call targets the Emporium external action with `erc20TokenAddresses.length == 0`, the contract switches to a minimal public-input set that omits the EdDSA signature check, the Merkle-root/nullifier logic, and — critically — the on-chain balance accounting loop that would normally bound how much value an external action is allowed to move. This lets any unprivileged EOA submit a trivially self-satisfiable proof and drive the Emporium contract into executing an arbitrary low-level call with an arbitrary `value`, draining the Emporium's pooled ETH/token balance (funds belonging to other users' shielded UTXOs) with zero authorization.

### Finding Description
`CircomDataBuilder.formInputForCircom` chooses a stripped-down public-input builder whenever the external action is Emporium and no ERC20 tokens are listed: [1](#0-0) 

`formInputEmporiumMin` produces only `[emporiumMessage, timeStamp, calldataHash]`, matching `MainEVMCircuitMin`, which has no `SignatureVerifier`, no nullifier check, and no Merkle-root check at all — it merely commits `message = Poseidon(messageSeed)`: [2](#0-1) 

Because `messageSeed` is a private input fully chosen by the prover, and `emporiumMessage`/`calldataHash`/`timeStamp` are hashed/derived by the prover off-chain from data they also fully control, **any EOA can construct a valid Groth16 proof for this path without owning any prior UTXO, without any spending key, and without any signature** — the circuit imposes no ownership constraint whatsoever when `tokenCount == 0`.

`Hinkal.transact()` still calls `hinkalHelper.performHinkalChecks` (which only checks `calldataHash` integrity and dimensions — trivially satisfiable) and `rootHashExists` (vacuous since `rootHashHinkal` isn't bound to anything meaningful for this path), then dispatches to `_externalTransact`, which for `erc20TokenAddresses = []` produces an **empty** `deltaAmountChanges` array and calls `runAction` directly: [3](#0-2) 

The subsequent balance-equation check in `Hinkal.transact` (`balanceDif == amountChanges[i] + utxoAmount`) iterates only over `circomData.erc20TokenAddresses`, which is empty — so **no balance check is performed at all** for this transaction: [4](#0-3) 

Inside `EmporiumUpgradeable.runAction`, the attacker fully controls `externalActionMetadata` (decoded into `EmporiumStack`). By setting `signerAddress = address(0)`, `verifyWallet` skips ECDSA verification entirely (that branch exists only for the wallet-signed EIP-712 case): [5](#0-4) 

With `stack.signerAddress == 0` and `op.invokeWallet == false`, the "stateless" branch executes an attacker-chosen low-level call directly from the Emporium contract, forwarding an attacker-chosen `op.value` of the Emporium's own ETH balance to an attacker-chosen endpoint: [6](#0-5) 

The post-call accounting loop that is meant to catch unauthorized balance decreases (`balanceChange < 0` reverts) only iterates over `circomData.erc20TokenAddresses`, which the attacker set to `[]`, so this safety net never runs: [7](#0-6) 

This is exactly the "value moved by Hinkal or an external action but not counted in the balance equation" bug class: the equality `Σ(balance change) == Σ(amountChanges) + Σ(utxoAmount)` that is supposed to bound every external action's value flow is never evaluated because the token list used to compute both sides is empty, while the actual value flow (the ETH sent via `op.value` in the raw `.call`) is unconstrained by `deltaAmountChanges` or by any circuit-verified UTXO amount.

### Impact Explanation
Critical — direct theft of pooled shielded funds. The Emporium contract holds ETH/ERC20 balances on behalf of many users' shielded deposits/UTXOs (it is a shared pool, per `getBalancesForArray`/UTXO tracking used elsewhere in the same contract). An attacker with no shielded balance, no spending key, and no valid signature can drain the entire ETH balance the Emporium contract currently holds by directing an arbitrary `.call{value: X}(...)` to an address they control, with `X` bounded only by the Emporium's current ETH balance, not by any amount the attacker is entitled to.

### Likelihood Explanation
High. Generating a proof for `MainEVMCircuitMin` requires no secret material — any party who can run the prover (a fully public, permissionless operation) can produce a valid proof for arbitrary `messageSeed`/`emporiumMessage`/`calldataHash`. No relayer, admin, or backend cooperation is needed; the only precondition is that the Emporium contract holds a non-zero ETH balance at call time, which is the normal operating state of a pooled shielded-funds contract.

### Recommendation
- Reject `formInputEmporiumMin` / zero-token-count Emporium transactions unless `op.value == 0` for every stateless operation, or otherwise ensure ETH/ERC20 value moved by `runAction` is always constrained by a circuit-verified `deltaAmountChanges`/UTXO amount.
- Do not allow `stack.signerAddress == address(0)` (skipping the EIP-712 signature check) to be combined with non-zero `op.value` in the stateless branch of `EmporiumUpgradeable.runAction`.
- Ensure the top-level balance/slippage equation in `Hinkal.transact` and the balance-change check in `EmporiumUpgradeable.runAction` cannot be bypassed by supplying an empty `erc20TokenAddresses` array while still allowing value-moving low-level calls.

### Proof of Concept
1. Attacker computes any `messageSeed`, sets `message = Poseidon(messageSeed)`, and derives `emporiumMessage`, `timeStamp`, `calldataHash` consistent with a `CircomData` struct where:
   - `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`
   - `externalActionData = { externalAddress: EmporiumUpgradeable, externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalActionMetadata: abi.encode(EmporiumStack({ signerAddress: address(0), ops: [ { endpoint: attackerContract, invokeWallet: false, value: <EmporiumETHBalance>, callData: "" } ], maxFee:0, deadline:0, v/r/s: 0 })) }`
2. Attacker generates a Groth16 proof for `MainEVMCircuitMin` satisfying only `message === Poseidon(messageSeed)` (trivial, no secret key needed).
3. Attacker calls `Hinkal.transact(a,b,c,dimensions,circomData)`. `performHinkalChecks` passes (calldata hash matches by construction), `verifyProof` passes (trivial circuit), `rootHashExists` passes with any valid current root/index (unrelated to ownership).
4. `_externalTransact` calls `EmporiumUpgradeable.runAction` with `deltaAmountChanges = []`.
5. `verifyWallet` skips signature check (`signerAddress == address(0)`), the stateless branch executes `attackerContract.call{value: EmporiumETHBalance}("")`, transferring the Emporium's entire ETH balance to the attacker.
6. No balance check in `runAction` or in `Hinkal.transact` reverts, because both iterate over the empty `erc20TokenAddresses` array.
