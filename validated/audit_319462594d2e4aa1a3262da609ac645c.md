### Title
Webhook shop attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the identity of the shop that a webhook belongs to purely from the unauthenticated `shopify-shop-domain` HTTP header, while the HMAC signature that `Utils::HmacValidator` checks covers only the raw request body. This breaks the binding: `signature verifies body` != `signature verifies (body, shop)`. Because the signing secret (`Context.api_secret_key`/`client_secret`) is shared across every shop that installs the app, anyone who can obtain one valid `(raw_body, hmac)` pair — e.g., by installing the app on their own store — can replay that exact body to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header, and `HmacValidator.validate` will still report success.

### Finding Description
The signable content for a webhook request is defined as just the raw body: [1](#0-0) 

The shop, topic, API version and webhook id are all pulled straight from headers and are never mixed into `to_signable_string`: [2](#0-1) 

`HmacValidator.validate` computes an HMAC over `to_signable_string` (the body only) and compares it to the `hmac` header value using the app's single, shop-agnostic `api_secret_key`: [3](#0-2) 

`Registry.process` then trusts `request.shop` unconditionally once the (body-only) HMAC check passes, and forwards it straight into the handler as the tenant identifier: [4](#0-3) 

The binding the code implicitly assumes is:
`valid_hmac(body) == true` implies `shop_header == originating_shop`

but that equality does not hold, because `shop_header` is not part of the signed material and the secret used to compute the HMAC is identical for every shop that has the app installed. Any attacker who legitimately receives (or triggers) one webhook delivery — for instance by installing the (public) app on a shop they control — obtains a `(raw_body, hmac)` pair that is valid under the app's shared secret regardless of which shop domain is attached to it. They can then POST that same body/HMAC pair to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to name a victim shop. `HmacValidator.validate` still succeeds because it never inspects the shop header, and `Registry.process` dispatches the (attacker-authored) payload to the handler tagged as belonging to the victim shop.

### Impact Explanation
This is a cross-tenant confusion vulnerability: data that the app's webhook handlers treat as authoritative for shop A can actually be attacker-supplied content attributed to shop B. Depending on how a host application's webhook handlers use `WebhookMetadata#shop` (e.g., updating per-shop billing state, honoring `app/uninstalled`, `shop/redact`, or `customers/data_request` for compliance workflows), this allows an unprivileged party with access to any single shop's webhook stream to inject spoofed events for other tenants of the same app, i.e., cross-tenant access, which is explicitly listed as a Critical-impact category.

### Likelihood Explanation
The prerequisite is only having a valid `(body, hmac)` pair signed with the app's secret; because the secret is shared by every install of the app rather than per-shop, any user who installs a public app on their own store (or otherwise has a legitimate webhook delivery captured) satisfies this without needing any elevated privilege or leaked secret material. The rest of the attack is a straightforward direct HTTP POST to the app's public webhook endpoint with a modified header.

### Recommendation
Bind the shop identity into the material that is actually verified. Options:
- Have applications cross-check `request.shop` against the shop associated with the webhook subscription/registration (i.e., only accept the shop id embedded in server-side registration metadata, not the header value), or
- Where feasible, incorporate the shop domain into the value verified against the signature (e.g., require and validate that the destination/topic registration used to receive the webhook matches the claimed shop before trusting `request.shop`), and document to consumers of `ShopifyAPI::Webhooks::Request`/`Registry.process` that `shop` is unauthenticated header data and must not be used as a sole tenant key without an additional binding check.

### Proof of Concept
1. Attacker installs the target (public) app on their own store `attacker.myshopify.com`, obtaining a valid webhook delivery, e.g. for `orders/create`, with body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC_SHA256(client_secret, B)`.
2. Attacker crafts a POST directly to the app's webhook endpoint using the exact same body `B` and header `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. Server calls `ShopifyAPI::Webhooks::Registry.process(request)`, which invokes `Utils::HmacValidator.validate(request)`: [5](#0-4) 
   This succeeds because the check only verifies `B` against `H`, not the shop header.
4. `WebhookMetadata` built from `request.shop` reports `victim-shop.myshopify.com`, and the handler processes attacker-controlled data as if it originated from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
