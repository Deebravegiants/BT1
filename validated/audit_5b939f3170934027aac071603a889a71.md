## Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook forgery via replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while `shop`, `topic`, and `webhook_id` are read directly from unauthenticated headers and handed to the app's webhook handler as trusted tenant-identifying data. `HmacValidator` only checks that the body's HMAC is valid for the configured secret; it never binds the `shop`/`topic` fields into that check, so any request carrying a *previously observed valid (body, HMAC)* pair can be replayed with an arbitrary `shop-domain`/`topic` header and will still pass validation.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are read straight from headers with no cryptographic tie to the signature: [2](#0-1) 

`HmacValidator.validate` verifies only `verifiable_query.to_signable_string` (i.e., the raw body) against the received HMAC: [3](#0-2) 

`Registry.process` trusts `request.shop` and `request.topic` as authenticated tenant/event identity once `HmacValidator.validate` succeeds, and forwards them unmodified to the app's handler: [4](#0-3) 

This breaks the intended identity binding: **HMAC(secret, bytes verified) == bytes the app treats as identifying the tenant/event**. In reality the equality only holds for the raw body; the `shop` and `topic` fields the host application relies on to route data per-tenant are outside the signed bytes.

Any unprivileged internet user can obtain a legitimately-signed `(raw_body, hmac)` pair simply by owning/operating their own development or trial Shopify store and registering a webhook that this app also subscribes to (e.g., `orders/create`). Shopify will deliver a validly HMAC-signed payload to the app's endpoint for that user's own shop. The user can then capture that exact `raw_body` + `hmac-sha256` header and replay it to the app's webhook endpoint while substituting the `shop-domain` header (and/or `topic` header) with an arbitrary victim shop domain / topic. `HmacValidator.validate` will still return `true`, because it only checks the untouched raw body against the secret-derived HMAC, and `Registry.process` will dispatch the handler with `shop: <victim-shop>`.

### Impact Explanation
This is a cross-tenant data-integrity issue: an attacker who legitimately controls only their own shop can cause the app to process fabricated webhook data attributed to a different (victim) shop, because the shop/topic identity used by the host application is not bound to the same authentication check as the payload. Depending on how the host app uses the webhook body together with `shop` (e.g., updating per-shop order/inventory/customer records, triggering emails, revoking access, or overwriting shop-scoped state), this can lead to cross-tenant data corruption or unauthorized state changes scoped to a shop the attacker does not own — matching the "cross-tenant access" class of impact.

### Likelihood Explanation
Likelihood is high for any app that (a) trusts the gem's parsed `WebhookMetadata#shop`/`#topic` as the tenant key without independent verification, and (b) processes webhook topics whose payload shape is attacker-influenceable via the attacker's own shop (e.g., `orders/create`, `app/uninstalled`, `customers/data_request`, etc., where the attacker fully controls the body content by acting on their own store). No secret, access token, or victim-side credential is required — only capture-and-replay of a self-obtained signed webhook with a header swap.

### Recommendation
Bind the tenant/event identity into the authenticated signature surface, not just the body:
- Include `shop`, `topic`, and `webhook_id` in the string that is HMAC-verified (or verify them via a side channel that is itself authenticated, e.g., cross-check `shop` against the session/shop the delivery URL is scoped to).
- Alternatively, require apps to register per-shop distinct webhook endpoints (path-embedded shop) and validate that the path-derived shop matches the header-derived shop before trusting either.
- At minimum, document prominently that `Request#shop`/`#topic` are unauthenticated and must not be used as an authorization boundary without additional verification (e.g., confirming the shop has an active, stored session/access token in the host app before acting on the payload).

### Proof of Concept
1. Attacker registers/owns `attacker-shop.myshopify.com` and enables the app to receive a subscribed webhook topic (e.g., `orders/create`).
2. Shopify delivers a request to the app's webhook endpoint with:
   - `x-shopify-hmac-sha256: <valid HMAC of raw_body under the app secret>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-topic: orders/create`
   - body: attacker-controlled order JSON (attacker can place any order content they want in their own store).
3. Attacker captures `raw_body` and `x-shopify-hmac-sha256` verbatim.
4. Attacker sends a new HTTP request to the same app endpoint, reusing the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13`) computes the HMAC over `raw_body` only and it matches — validation passes.
6. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188`) builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and dispatches to the app handler, which now processes attacker-crafted order data as if it belongs to `victim-shop.myshopify.com`.
