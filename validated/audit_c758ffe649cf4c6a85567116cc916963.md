### Title
Empty-token Emporium Min proof lets any caller drain Emporium's balance via unaccounted arbitrary call - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol / contracts/CircomDataBuilder.sol)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only proves `message == Poseidon(messageSeed)` — a value any caller can freely choose, requiring no secret or authorization tied to any other user. This lets an unprivileged attacker submit a trivially-satisfiable proof while supplying an arbitrary `EmporiumStack` with `signerAddress == address(0)`, which both bypasses the EIP-712 signature check in `verifyWallet` and routes every op through the unrestricted "stateless" call branch (`op.endpoint.call{value: op.value}(op.callData)`), while the balance accounting loop in `runAction` (and the outer one in `Hinkal.transact`) iterates zero times because it is keyed off the same empty `erc20TokenAddresses` array.

### Finding Description
The claimed broken equality is: **assets Emporium can move in a tx == assets accounted in `balancesBefore`/`balancesAfter`**. This equality fails when `erc20TokenAddresses.length == 0`.

Path:
1. `Hinkal.transact` calls `hinkalHelper.performHinkalChecks`, which calls `CircomDataBuilder.formInputForCircom` [1](#0-0) . Since `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputEmporiumMin` is used, whose only public inputs are `emporiumMessage`, `timeStamp`, `calldataHash` [2](#0-1) .
2. The corresponding circuit `MainEVMCircuitMin` only constrains `message <== Poseidon(1)([messageSeed])` [3](#0-2) . `messageSeed` is a private input the attacker freely chooses — no nullifier, no root, no ownership check is enforced in this path.
3. `getHashedCalldata`/`getHashedCalldata1` include `circomData.externalActionData` (i.e., the whole `EmporiumStack` payload) in `calldataHash` [4](#0-3) , but this is merely a keccak consistency check between calldata and the passed-in hash, computed on-chain from attacker-supplied plaintext data — it is **not** an authorization or ownership proof over the `EmporiumStack` contents.
4. In `Hinkal.transact`, the outer balance accounting loop (`oldBalances`/`newBalances`, `balanceDif` checks) is indexed by `circomData.erc20TokenAddresses`, so with an empty array it performs zero iterations and enforces nothing [5](#0-4) .
5. Inside `EmporiumUpgradeable.runAction`, `balancesBefore`/`balancesAfter` are likewise computed over `circomData.erc20TokenAddresses` [6](#0-5)  and the same array drives the post-op accounting loop [7](#0-6)  — again zero iterations when empty.
6. `verifyWallet` is called before the ops execute; if `stack.signerAddress == address(0)` it returns immediately with **no signature check at all**, only marking `emporiumMessage` used [8](#0-7) .
7. The ops loop then executes each `EmporiumOperation`. Because `stack.signerAddress == address(0)`, the condition `op.invokeWallet && stack.signerAddress != address(0)` is false for every op, so execution always falls into the "stateless" branch: `op.endpoint.call{value: op.value}(op.callData)` [9](#0-8) . The only restriction is blocking the `callHinkalWallet`/`doSendToRelay` selectors; there is no restriction on the target `endpoint` address or on what function is invoked on it.

Exploit: the attacker crafts `op.endpoint = <any ERC20 token held by Emporium>`, `op.callData = transfer(attacker, balance)` (or a call into any router/helper that trusts `msg.sender == Emporium`), sets `signerAddress = address(0)`, `erc20TokenAddresses = []`, generates a trivial Min proof from a self-chosen `messageSeed`, and calls `Hinkal.transact`. `runAction` executes the transfer using Emporium's own token/ETH balance as `msg.sender`, and since `erc20TokenAddresses` is empty, neither `Hinkal.transact`'s balance/slippage checks nor `runAction`'s `balancesBefore`/`balancesAfter`/`BalanceChangeShouldBePositive` checks observe or constrain this movement at all.

Existing guards do not prevent this:
- `performHinkalChecks`'s `dimensionsCheck`/`checkOnchainCreation` operate on dimensions/nullifiers, not on `externalActionMetadata` contents or on preventing an empty token array for the Emporium action.
- `rootHashExists`/`insertNullifiers` are irrelevant to the Min path since no nullifiers are proven or required.
- `onlyAllowedRecipient` on `runAction` only checks `msg.sender == Hinkal`, not the contents of the stack.
- `verifyWallet`'s signature check is the one guard meant to authorize the ops, and it is explicitly skipped for `signerAddress == address(0)`.

### Impact Explanation
Any unprivileged attacker who can call `Hinkal.transact` with a self-generated trivial Min-circuit proof can direct `EmporiumUpgradeable` to execute an arbitrary external call as itself and drain any ERC20/ETH balance currently held by the Emporium contract to themselves, with zero on-chain accounting of the movement. This is direct theft of funds sitting in Emporium (e.g., residual balances, in-flight funds mid multi-step operation, dust from fee rounding, or ETH sent via the contract's `receive()`), matching the Critical severity category "direct theft of shielded or in-flight user funds." The attack is repeatable every time Emporium holds a nonzero balance and each `emporiumMessage` value can only be used once (`usedMessages`), but the attacker can pick a fresh `emporiumMessage`/`messageSeed` for each attempt at negligible cost (just gas + a locally-generated Groth16 proof for `MainEVMCircuitMin`).

### Likelihood Explanation
Preconditions: Emporium must hold a nonzero balance of some asset at the time of the attack (whether from normal protocol operation, dust, a prior partially-settled multi-op transaction, or accidental transfer). No privileged role, victim key, or relayer cooperation is required — the attacker only needs to be able to call `Hinkal.transact` directly and generate a proof for the trivial `MainEVMCircuitMin` circuit locally. This is a low-cost, highly feasible, and repeatable attack whenever Emporium's balance is nonzero.

### Recommendation
- Do not allow the `EmporiumMin` (empty `erc20TokenAddresses`) code path to skip balance accounting for ops that make stateless external calls; require `runAction`'s balance loop to track *all* tokens/ETH actually touched by the ops (not only the caller-supplied `erc20TokenAddresses` list), or forbid stateless (non-wallet) calls entirely when `signerAddress == address(0)` and `erc20TokenAddresses.length == 0`.
- Restrict the "stateless interaction" branch so that `op.endpoint` cannot be an arbitrary attacker-chosen address capable of moving Emporium's own held assets — e.g., disallow direct token contract calls, or require every op with `signerAddress == address(0)` to be reconciled against a non-empty, explicitly declared token list that is enforced by the circuit.
- Ensure `verifyWallet`'s no-signature short-circuit (`signerAddress == address(0)`) is only reachable when the transaction's own accounting (via non-empty `erc20TokenAddresses`/`amountChanges`) fully constrains every asset movement performed by the ops.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (as a registered external action with `HINKAL_EMPORIUM_ACTION_ID`), and a test ERC20 token.
2. Fund the Emporium contract directly with, e.g., 1000 test tokens (simulating residual/in-flight balance) — `token.transfer(emporiumAddress, 1000e18)`.
3. As an unprivileged attacker EOA, build `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and `externalActionMetadata` encoding an `EmporiumStack{ signerAddress: address(0), ops: [ { endpoint: token, invokeWallet: false, value: 0, callData: abi.encodeCall(token.transfer, (attacker, 1000e18)) } ] }`.
4. Generate a real Groth16 proof for `MainEVMCircuitMin` locally with attacker-chosen `messageSeed`, computing `calldataHash` consistently with `CircomDataBuilder.getHashedCalldata`.
5. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from the attacker address.
6. Assert: `token.balanceOf(emporium) == 0` and `token.balanceOf(attacker) == 1000e18` after the call — i.e., Emporium's pre-existing balance is fully drained despite `balancesBefore == balancesAfter == []` (both empty arrays, i.e., "accounted" delta is trivially zero on both sides of the equality while the real balance delta is -1000e18), proving the equality "assets moved == assets accounted" is violated.
