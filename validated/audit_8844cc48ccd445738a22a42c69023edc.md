Webhook shop-domain identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers that are never included in the HMAC computation. `Registry.process` trusts `request.shop` as the tenant identity for the webhook handler after only validating the body's HMAC, so the equality "shop bound by HMAC" == "shop used by handler" does not hold.

### Finding Description
`Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 
i.e. it signs only `@raw_body`.

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers, entirely outside the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` against `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` performs exactly this check and then immediately trusts `request.shop` as the tenant identity handed to the app's webhook handler: [4](#0-3) 

So the binding the gem is supposed to enforce — *"HMAC-signed shop" == "shop delivered to the handler"* — is broken: the HMAC proves only that Shopify (holder of `api_secret_key`) produced this exact JSON body at some point; it says nothing about which shop the body belongs to. Any bytes previously signed for one shop remain validly signed regardless of which `shopify-shop-domain` / `x-shopify-shop-domain` header value accompanies them, because that header is never part of `to_signable_string`.

### Impact Explanation
This is a cross-tenant confusion vector: a party that has ever legitimately received one webhook delivery (e.g., an owner of their own trial/dev store, or someone who intercepts one delivery over an insecure channel/logging system) possesses a raw-body + HMAC pair that remains valid forever for that exact body. By re-submitting that same body/HMAC pair to the app's webhook endpoint with a different `shopify-shop-domain` header (attacker-chosen victim shop), `HmacValidator.validate` still succeeds, and `Registry.process` calls the handler with `WebhookMetadata.new(shop: request.shop, ...)` pointing at the victim's shop instead of the real originating shop. Any host application that uses `data.shop` from the gem to select the record/tenant to write to (a documented, intended usage of `WebhookMetadata`) will process attacker-controlled data under another tenant's identity — a cross-tenant access/data-integrity break, without needing the app's `client_secret` or any privileged account.

### Likelihood Explanation
Exploitation only requires the ability to make one legitimate webhook delivery occur (trivial for anyone who can install the app on their own store or observe one delivery) and the ability to POST to the app's public webhook endpoint with modified headers — no access token, secret, or privileged account is required. The vulnerability is entirely in this gem's `Request`/`Registry`/`HmacValidator` design, not a host-app misuse of an documented contract, since the gem itself exposes `request.shop` as the authenticated tenant identifier post-`HmacValidator.validate`.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed material verified by `HmacValidator`, or otherwise cryptographically bind them to the body (e.g., verify shop against a separately-authenticated channel, or reject/replace the design so that `to_signable_string` is not the sole source of truth for tenant identity). At minimum, document that `request.shop` from headers is not authenticated by the library's HMAC check, and require host apps to independently verify shop ownership before trusting it.

### Proof of Concept
1. Capture one legitimate webhook delivery for `shop-a.myshopify.com`: raw body `B` with header `shopify-shop-domain: shop-a.myshopify.com` and valid `shopify-hmac-sha256` computed over `B`.
2. Replay to the app's webhook endpoint with the same body `B` and same HMAC header, but `shopify-shop-domain: shop-victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: replayed_headers)` builds successfully; `to_signable_string` returns `B` unchanged. [1](#0-0) 
4. `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` with `Context.api_secret_key` and matches the unchanged HMAC header — validation passes. [5](#0-4) 
5. `Registry.process` invokes the app's handler with `shop: "shop-victim.myshopify.com"` even though the body actually originated from `shop-a`. [4](#0-3)
