### Title
LDAP Authentication Bypass via Unauthenticated (Empty-Password) Simple Bind - (File: `core/sessions/ldapauth/ldap.go`)

### Summary
The LDAP authentication provider forwards the user-supplied `SessionRequest.Password` directly to `conn.Bind()` without ever validating that it is non-empty. Per RFC 4513 §5.1.2, an LDAP simple bind with a zero-length password is defined as an "unauthenticated bind" — many directory servers return a **success** result for this bind without actually validating credentials. Because chainlink treats any successful `Bind()` call as a fully authenticated login, an attacker who supplies a known/enumerable email and an **empty** password can be granted a valid node session, exactly analogous to the root cause of CVE-2014-8088 (Zend `Zend_Ldap`), where a password that effectively became empty (there, via null-byte truncation) triggered an unauthenticated bind that the application mistook for a successful, credentialed login.

### Finding Description
In `core/sessions/ldapauth/ldap.go`, `CreateSession` performs the login flow entirely from unprivileged, unauthenticated client input (`sessions.SessionRequest` from the `/sessions` login endpoint): [1](#0-0) 

```go
func (l *ldapAuthenticator) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
    conn, err := l.ldapClient.CreateEphemeralConnection()
    ...
    escapedEmail := ldap.EscapeFilter(strings.ToLower(sr.Email))
    searchBaseDN := fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())
    if err = conn.Bind(searchBaseDN, sr.Password); err != nil {
        ...
        returnErr = errors.New("unable to log in with LDAP server. Check credentials")
    }
    ...
```

There is no check anywhere in this path (or in `TestPassword`, which has the identical pattern) that `sr.Password` is non-empty before it is handed to `conn.Bind`. The same missing-validation pattern occurs in `TestPassword`: [2](#0-1) 

If `sr.Password == ""`, the request reaching the upstream LDAP server is a simple bind with a zero-length password for the DN constructed from the attacker-controlled `sr.Email`. Per LDAP protocol semantics this is an "unauthenticated bind," which many LDAP server configurations (OpenLDAP, AD in default configurations, etc.) will report as `err == nil` (bind success) without validating that the caller actually knows the account's password. The chainlink code treats `err == nil` from `conn.Bind` as proof of a successful, credentialed authentication, then immediately calls `l.FindUser` to fetch the role and creates a persisted `ldap_sessions` row granting the caller an authenticated session with that user's mapped role: [3](#0-2) 

Nowhere in the request-binding path (`core/web/sessions_controller.go`) is an empty-password check enforced either — `ShouldBindJSON` only requires the JSON fields be present, and Go's `string` zero-value `""` is a fully valid, bindable value for `SessionRequest.Password`: [4](#0-3) 

The `VerifyPasswordComplexity` / `MinRequiredLen` check in `core/utils/password.go` exists but is only invoked on password *creation/change* flows (e.g., `UpdatePassword`, `SetPassword`), never on the login (`CreateSession`) path, so it provides no protection here.

### Impact Explanation
If the configured upstream LDAP/AD server allows unauthenticated binds (the RFC default, and a common real-world misconfiguration that is often invisible to node operators who only configure chainlink's LDAP client, not the directory's bind policy), an unprivileged remote attacker can:
- Authenticate as any known/guessed email address present in the directory (e.g. `admin@example.com`) without knowing that user's password.
- Be assigned that user's mapped RBAC role (potentially `UserRoleAdmin`), gaining full node API authorization for job management, key management, and other administrative endpoints.

This is a full authentication bypass / role escalation reachable purely from an unauthenticated HTTP client hitting the node's `/sessions` login endpoint — the exact class of "unauthenticated actor bypasses authentication" described in the report.

### Likelihood Explanation
Exploitability is conditioned on the upstream LDAP server's bind policy (whether it permits unauthenticated/anonymous binds for the target DN), which chainlink does not control or verify. However, chainlink's own code contains no defense-in-depth check to reject empty passwords before delegating to the directory, so the vulnerability is squarely rooted in the application layer, matching how CVE-2014-8088 was scored (a client-library-level failure to reject a bind that resolves to zero-length credentials). Given LDAP unauthenticated binds are a well-known, frequently overlooked default in many directory deployments, likelihood is Medium.

### Recommendation
In `ldapAuthenticator.CreateSession` and `ldapAuthenticator.TestPassword` (`core/sessions/ldapauth/ldap.go`), explicitly reject empty (or whitespace-only) passwords before calling `conn.Bind`, e.g.:
```go
if sr.Password == "" {
    return "", errors.New("password must not be empty")
}
```
This should be enforced immediately upon entry to both functions, mirroring the fix pattern used to remediate CVE-2014-8088 (explicit rejection of degenerate/empty credentials prior to bind), independent of whatever anonymous-bind policy the upstream directory enforces.

### Proof of Concept
1. Configure chainlink with LDAP auth pointed at a directory server that permits unauthenticated binds (default/common OpenLDAP/AD behavior unless explicitly disabled via `disallow bind_anon` or Group Policy restricting anonymous binds).
2. Send an unauthenticated login request to the node:
```
POST /sessions
{"email": "admin@example.com", "password": ""}
```
3. `ldapAuthenticator.CreateSession` calls `conn.Bind("uid=admin@example.com,ou=Users,dc=example,dc=com", "")`.
4. The directory server returns a successful unauthenticated bind (`err == nil`).
5. chainlink proceeds to call `FindUser`, obtains the admin's mapped role, creates an `ldap_sessions` row, and returns a valid, authenticated session cookie to the caller — without the caller ever having supplied the admin's real password.

func (l *ldapAuthenticator) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	conn, err := l.ldapClient.CreateEphemeralConnection()
	if err != nil {
		return "", errors.New("unable to establish connection to LDAP server with provided URL and credentials")
	}
	defer conn.Close()

	var returnErr error

	// Attempt to LDAP Bind with user provided credentials
	escapedEmail := ldap.EscapeFilter(strings.ToLower(sr.Email))
	searchBaseDN := fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())
	if err = conn.Bind(searchBaseDN, sr.Password); err != nil {
		l.lggr.Infof("Error binding user authentication request in LDAP Bind: %v", err)
		returnErr = errors.New("unable to log in with LDAP server. Check credentials")
	}

	// Bind was successful meaning user and credentials are present in LDAP directory
	// Reuse FindUser functionality to fetch user roles used to create ldap_session entry
	// with cached user email and role
	foundUser, err := l.FindUser(ctx, escapedEmail)
	if err != nil {
		l.lggr.Infof("Successful user login, but error querying for user groups: user: %s, error %v", escapedEmail, err)
		returnErr = errors.New("log in successful, but no assigned groups to assume role")
	}

	isLocalUser := false
	if returnErr != nil {
		// Unable to log in against LDAP server, attempt fallback local auth with credentials, case of local CLI Admin account
		// Successful local user sessions can not be managed by the upstream server and have expiration handled by the reaper sync module
		foundUser, returnErr = l.localLoginFallback(ctx, sr)
		isLocalUser = true
	}

	// If err is still populated, return
	if returnErr != nil {
		return "", returnErr
	}

func (sc *SessionsController) Create(c *gin.Context) {
	defer sc.App.WakeSessionReaper()
	ctx := c.Request.Context()

	session := sessions.Default(c)
	var sr clsessions.SessionRequest
	if err := c.ShouldBindJSON(&sr); err != nil {
		jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("error binding json %w", err))
		return
	}

	// Does this user have 2FA enabled?
	userWebAuthnTokens, err := sc.App.AuthenticationProvider().GetUserWebAuthn(ctx, sr.Email)

		jsonAPIError(c, http.StatusInternalServerError, errors.New("internal Server Error"))
		return
	}

	// If the user has registered MFA tokens, then populate our session store and context
	// required for successful WebAuthn authentication
	if len(userWebAuthnTokens) > 0 {
		sr.SessionStore = sc.sessions
		sr.WebAuthnConfig = sc.App.GetWebAuthnConfiguration()
	}

	sid, err := sc.App.AuthenticationProvider().CreateSession(ctx, sr)
	if err != nil {
		jsonAPIError(c, http.StatusUnauthorized, err)
