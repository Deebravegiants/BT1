### Title
Message/Transaction signing accepts a caller-supplied `WalletAccount` object without validating it against the registered `walletAccountsAtom` - ([File: features/message-signer/src/module/message-signer.ts])

### Summary
The external report's bug class is: a state-changing/privileged function trusts that the caller is a legitimate registered entity (`RuyuiShop.purchaseShopItem`/`purchaseBattlePass` never checked `hasSignedUp(msg.sender)` before granting purchase-linked state and referee commissions). The Hydra analog is `MessageSigner#signMessage` (and the structurally identical `TransactionSigner#signTransaction` / `transactionSignerApi`), which only validates a `walletAccount` against the source-of-truth `walletAccountsAtom` when it is passed as a **string** name. When a `WalletAccount` **object/instance** is passed instead, it is used as-is to derive signing key material, with no check that this account was ever `create()`-d, is `enabled`, or matches any entry the wallet actually tracks.

### Finding Description
In `MessageSigner#normalizeWalletAccount`: [1](#0-0) 
only the `typeof walletAccount === 'string'` branch looks up `this.#walletAccountsAtom.get()` and asserts the instance exists. If `opts.walletAccount` is already an object, it is returned unchanged and immediately fed to `#getMessageSigner` and then to `signer.signMessage`, which derives the signing key from `walletAccount.seedId`/`walletAccount.index` (seed-based) or `requireDeviceFor(walletAccount)` (hardware): [2](#0-1) 

The public API type explicitly allows either form: [3](#0-2) 

The exact same pattern exists in the transaction-signing path: `TransactionSignerApi` only resolves-and-validates the account when a string name is given, otherwise passes the object straight through: [4](#0-3) [5](#0-4) 

This mirrors the report's root cause: the "purchase" (here, "sign") function assumes the caller-supplied identity/state object is authoritative, instead of re-deriving/confirming it from the canonical registered records (`walletAccountsAtom`, populated only via `WalletAccounts.create()`/`createMany()` in `features/wallet-accounts/src/module/wallet-accounts.ts`). Just as `RuyuiShop` skipped `hasSignedUp()`, `MessageSigner`/`TransactionSigner` skip an equivalent `assert(walletAccounts[walletAccount.toString()])` check whenever an object is supplied.

### Impact Explanation
If any call site (API consumer, UI code, or a future dApp/RPC bridge integration) constructs a `WalletAccount` object from data it does not fully trust or has not cross-checked against the enabled/registered account set (e.g., re-hydrating from a message, deep link, or IPC payload), signing will proceed for accounts that were never legitimately created, are disabled, or belong to state the rest of the wallet does not recognize (analogous to bypassing "sign-up"). Because `keychain.signBuffer`/`getPublicKey` only validate that the `seedId` was previously loaded into the keychain (not that the specific `WalletAccount` was ever registered by the user) — see `#getPrivateHDKey`'s checks: [6](#0-5)  — an attacker-influenced `WalletAccount` object (e.g. with a manipulated `index`, `compatibilityMode`, or hardware `id`/derivation-affecting fields) can cause the wallet to produce a valid signature for a derivation path/account that was never part of the user's enabled `walletAccounts` set, silently bypassing the registration invariant the rest of the codebase relies on (enabled-check, uniqueness-check, compatibility-mode consistency enforced in `createMany`). This is a state/authorization-bypass class defect, structurally identical to skipping the sign-up check before a privileged action.

### Likelihood Explanation
Exploitability depends entirely on whether any reachable caller constructs a `WalletAccount` object from external/untrusted input rather than always using the atom-validated string form. I was not able to fully confirm, within the available index, which production call sites (if any) pass an object built from external/RPC/dApp-controlled data into `messageSigner.signMessage` or `transactionSignerApi.signTransaction` — the visible callers in this index (tests, `sdks/headless` tests) all pass either atom-derived instances or trusted string names. This is a real gap in the defense-in-depth of the signer modules (missing the registration check present for the string path), but I could not verify a concretely reachable untrusted-input path to it within the indexed code, so likelihood is uncertain/lower-confidence pending confirmation of all callers of these signer APIs, especially the RPC/web3 provider bridges (`docs/web3-providers/*`) whose implementation was not found in the index.

### Recommendation
Make `#normalizeWalletAccount` (and the equivalent logic in `tx-signer/src/api/index.ts`) always resolve/verify against `walletAccountsAtom` regardless of whether the input is a string or an object, e.g.:
```ts
const walletAccounts = await this.#walletAccountsAtom.get()
const instance = walletAccounts[typeof walletAccount === 'string' ? walletAccount : walletAccount.toString()]
assert(instance, `wallet account ${walletAccount} not found`)
return instance
```
This ensures signing only ever proceeds for accounts that are actually part of the registered/enabled `walletAccounts` set, closing the same class of "acted without verifying registration/authorization" gap identified in the external report.

### Proof of Concept
Not independently reproducible from the indexed files alone (no test harness was found that supplies an unregistered/attacker-controlled `WalletAccount` object to `messageSigner.signMessage`). Conceptually:
```ts
// walletAccountsAtom only contains "exodus_0"
const forgedAccount = new WalletAccount({ source: 'exodus', index: 999, seedId: primarySeedId })
// bypasses the atom-lookup/assert path entirely because it's an object, not a string:
await messageSigner.signMessage({
  baseAssetName: 'ethereum',
  walletAccount: forgedAccount,
  message: { rawMessage: Buffer.from('hello world') },
})
// -> signs successfully for an index/account that was never created via walletAccounts.create()
```
This directly parallels the report's demonstrated pattern of calling a privileged function while skipping the prerequisite registration check.

    walletAccount: WalletAccount | string
  ): Promise<WalletAccount> => {
    if (typeof walletAccount === 'string') {
      const walletAccounts = await this.#walletAccountsAtom.get()
      const instance = walletAccounts[walletAccount]
      assert(instance, `wallet account ${walletAccount} not found`)

      return instance
    }

    return walletAccount
  }
