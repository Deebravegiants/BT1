### Title
Webhook `shop` (and `topic`) attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then dispatches to the app's handler using the `shop`, `topic`, and `webhook_id` values taken directly from unauthenticated HTTP headers. None of those header-derived fields are part of the signed material, so the equality the handler relies on (`request.shop == "the shop this event legitimately belongs to"`) is never actually checked.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` field of the query object [1](#0-0) .

For webhooks, `to_signable_string` is defined to return only the raw HTTP body: [2](#0-1) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` performs exactly one check — the HMAC over the body — and then immediately trusts the header-derived `shop`/`topic`/`webhook_id` to build the object handed to the app's business logic: [4](#0-3) 

The resulting `WebhookMetadata` struct — which carries `shop` as the tenant identifier the host application is expected to key its multi-tenant logic on — is populated straight from that unauthenticated header: [5](#0-4) 

This is structurally the same class of bug as the Carapace report: the code validates one attribute (there, the token/lending-contract/time triple; here, the raw body via HMAC) while a materially significant attribute that downstream logic acts on (there, the protection amount; here, the `shop` tenant identifier) is left completely unchecked. The equality that should hold is:

`shop header value` == `shop that produced/owns the HMAC-signed body`

but the gem never enforces this — it only enforces `HMAC(body)` validity, which is agnostic to which shop's secret-independent header claims accompany it. Since all shops of a given app share the same `api_secret_key`, any body signed with that shared secret is valid regardless of which shop's header is attached.

### Impact Explanation
An attacker who controls one shop where the target app is installed (a legitimate but unprivileged user of a multi-tenant Shopify app) can:
1. Trigger a webhook delivery to their own installation with attacker-influenced body content (e.g., by creating/editing a resource that fires a subscribed webhook topic), obtaining a body + valid HMAC pair signed with the app's shared `api_secret_key`.
2. Replay that exact `body`/`hmac` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) header with a victim shop's domain.
3. Because `Registry.process` only re-validates the HMAC over the body — which is unaffected by header changes — the forged request passes validation and the handler executes with `WebhookMetadata#shop` claiming to be the victim shop, injecting attacker-controlled data into another tenant's context.

This is a cross-tenant boundary break driven entirely by this gem's webhook processing logic (not by the host app ignoring documented behavior), matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the attacker to be an installed user of a multi-tenant app (not requiring the app's `client_secret` or a stolen access token), and requires the app to actually key business decisions off `WebhookMetadata#shop` (which is the documented and expected usage per the gem's webhook handler contract). Any Shopify app author following the gem's intended pattern of trusting `data.shop` for tenant routing is exposed.

### Recommendation
Do not treat header-derived identity fields as trusted merely because the body HMAC validates. At minimum:
- Cross-check the `shop` header against the shop associated with the webhook subscription/registration (e.g., verify a session/store record exists for that shop and that the app instance registered that specific webhook id for that shop) before invoking the handler.
- Consider incorporating the shop domain into the value used to look up per-shop webhook secrets/registrations rather than relying on a single shared `api_secret_key` HMAC that is indifferent to header content.
- Document explicitly that `WebhookMetadata#shop`/`topic` are unauthenticated fields and must be re-validated by the host application against known, registered webhook subscriptions before being trusted for tenant-sensitive operations.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com", app is installed there.
# Step 1: Attacker triggers an action producing a webhook delivery to their own
# app endpoint, capturing the legitimate raw body + valid HMAC signed with the
# app's shared api_secret_key, e.g.:
raw_body = '{"id":1,"note":"payload attacker fully controls via their own store"}'
hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# Step 2: Attacker resends body+hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to the victim shop.
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, unauthenticated
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# HMAC validation succeeds because it only checks raw_body against the shared secret;
# it never checks that "victim-shop.myshopify.com" is the shop that actually produced this body.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body, ...))
```
Note: I was unable to fully verify how a specific downstream host application (outside this gem, e.g. `shopify_app`) additionally hardens this path, since that logic lives outside `lib/shopify_api/**`; this analysis is scoped strictly to the guarantees this gem itself provides via `Webhooks::Registry`/`Webhooks::Request`/`Utils::HmacValidator`.
