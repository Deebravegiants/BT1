## Analysis

CVE-2017-5937 is a class of bug where a component computes state from a value assumed to always be well-formed/consistent (a format descriptor), and a crafted input breaks that assumption, causing an unguarded pointer/arithmetic operation to fail catastrophically (NULL dereference/DoS). The alt.fun analog is a broken invariant between the bonding curve's *stored* virtual token reserve and the pair's *live* ERC20 balance, reachable via plain token donations — exactly the "direct ERC20 transfers of a launched Token ... into ... Pair" surface called out in scope.

### Title
Donation-induced invariant break causes permanent arithmetic-revert DoS of `Router._computeBuy`'s overflow cap - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy` assumes `_pool.tokenReserve` (the stored virtual reserve) always exceeds `Pair.tokenBalance()` (the pair's live ERC20 balance) by the constant `LP_RESERVE` gap [1](#0-0) . Any unprivileged wallet can shrink or invert that gap for free-of-charge-in-code (but capital-costly) by repeatedly buying tokens through the curve and donating them straight back to the `Pair` via a plain `IERC20.transfer`, since `Token` is an unrestricted ERC20 and `Pair.tokenBalance()` reads the live `balanceOf`, not the swap-tracked reserve [2](#0-1) . Once the invariant inverts, the next large buy that hits the overflow-cap branch underflows/reverts instead of gracefully capping — permanently disabling the supply-trigger graduation path and any large buy on that token.

### Finding Description
`Pair.swap` only mutates `_pool.tokenReserve`/`_pool.assetReserve` on router-mediated buys/sells [3](#0-2) . `Pair.tokenBalance()` is instead a live `balanceOf` read, independent of `_pool.tokenReserve` [2](#0-1) . `Token` is a standard, unrestricted `ERC20Upgradeable` clone with no transfer hooks or allowlist [4](#0-3) , so anyone holding launched tokens (bought normally off the curve) can `transfer()` them directly to the `Pair` address at any time.

The protocol's own invariant (`test_inv_virtualReserveAlwaysExceedsRealBalance`) asserts `tokenBalance() < tokenReserve` holds "at every state of the curve" and that this is what keeps `Router._computeBuy`'s `cappedReserveToken == 0` branch unreachable [5](#0-4) . That invariant is derived purely from the fixed launch-time gap (`totalSupply − curveSupply = 250M = LP_RESERVE`) under the assumption that `tokenReserve` and `tokenBalance()` only ever move together through `swap()`. Donations break that assumption: an attacker can (1) buy `tokensOut` tokens through the curve — which decrements *both* `_pool.tokenReserve` and the real `tokenBalance()` by `tokensOut` via `swap`/`transferToken` [6](#0-5)  — then (2) `transfer()` those same tokens straight back to the `Pair`, which restores `tokenBalance()` but leaves `_pool.tokenReserve` permanently reduced. Repeating this cycle monotonically shrinks (and can invert) the `tokenReserve − tokenBalance()` gap, entirely with transactions an unprivileged trader can submit.

Once `tokenBalance() ≥ tokenReserve`, the next buy whose uncapped `tokensOut` exceeds `tokenBalance()` enters the capping branch:
```solidity
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut; // underflows if realBalance >= reserveToken
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    ...
}
``` [7](#0-6) 
This either reverts on arithmetic underflow or hits the explicit `OverflowCapDegenerate()` guard. Both are unconditional reverts with no recovery path in `Router.sol` — the exact "crafted input breaks an unchecked invariant assumption → unguarded failure" shape as the CVE's crafted `VIRGL_CCMD_CLEAR` breaking `util_format_is_pure_uint`'s assumption.

### Impact Explanation
The overflow-cap branch is the sole mechanism by which the supply-side graduation trigger (`IPair.tokenBalance() == 0`) can ever fire, per the documented dual-trigger design [8](#0-7) . Degrading it into an unconditional revert permanently strands that token: any buy large enough to attempt draining the remaining real supply reverts instead of capping and graduating, so a token whose LT never appreciates enough to cross the USD trigger can never graduate via the supply path. This freezes the `LP_RESERVE` (250M) tokens parked in `Bonding` and denies traders/LPs the graduated HyperSwap market, and also DoSes any subsequent large buy attempt on that curve — a concrete, low-cost, permanent-freezing griefing vector reachable purely through `Zap.buy`/direct `Token.transfer`.

### Likelihood Explanation
The attack requires only standard transactions available to any wallet — buying via `Zap.buy` (or directly via an allowlisted router) and a plain ERC20 `transfer` to the `Pair` — no privileged role is needed. The capital cost is bounded by the cost of cycling through the curve's modest virtual liquidity (opens at ~$3K, graduates around $9K per `docs/contracts-scope.md`), making it economically feasible for a motivated griefer, and the resulting DoS is silent (no explicit revert reason surfaces until the victim buy attempts to cap).

### Recommendation
Do not trust `Pair.tokenBalance()` (a raw `balanceOf`) as the ground truth for the overflow-cap math. Either (a) cap `tokensOut` using `min(uncapped tokensOut, _pool.tokenReserve)` derived purely from the swap-tracked reserve rather than live balance, or (b) explicitly reconcile/quarantine externally-donated tokens (mirroring the LT-donation handling already done for `Router.graduate`) before they can be read into the cap calculation, and add a defensive `require`/saturating-subtraction so `cappedReserveToken` computation can never underflow regardless of external donations.

### Proof of Concept
1. Launch a token; curve seeds `_pool.tokenReserve = 1_000_000_000e18`, real `tokenBalance() = 750_000_000e18` (gap = `LP_RESERVE = 250_000_000e18`), matching `_deployAndSeed`/`Router.addInitialLiquidity` seeding [9](#0-8) .
2. Attacker repeatedly calls `Zap.buy(token, usdcAmount, 0, address(0))` for modest `tokensOut`, then `IERC20(token).transfer(pairAddr, tokensOut)` — each cycle leaves `tokenBalance()` roughly restored while `_pool.tokenReserve` (via `swap`) is permanently decremented by `tokensOut`.
3. Repeat until `tokenBalance() >= tokenReserve` (shrinking the initial 250M-token gap to ≤0); this requires cycling through capital roughly equal to buying most of the curve's real supply, bounded by the curve's total USD depth.
4. Any subsequent buy whose unclamped `tokensOut` (from `_computeBuy`'s constant-product formula) exceeds the now-inflated `realBalance` triggers `cappedReserveToken = reserveToken - tokensOut`, which underflows/reverts (or explicitly reverts via `OverflowCapDegenerate()` at exact equality), per `Router.sol` lines 140–147, permanently blocking further large buys and the supply-trigger graduation path for that token.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

    ///      `pair.tokenBalance() < pair.tokenReserve()` a hard property at
    ///      every state of the curve. This invariant is what makes the
    ///      `cappedReserveToken == 0` branch in `Router._computeBuy`
    ///      unreachable; if it ever ceased to hold, that branch would
    ///      revert with `OverflowCapDegenerate` rather than over-pay.
    function test_inv_virtualReserveAlwaysExceedsRealBalance() public {
        (address tokenAddr, address pairAddr) = _launchNoSeed();

        // Right after launch.
        assertTrue(IPair(pairAddr).tokenBalance() < _reserve0(pairAddr), "post-launch invariant");

        // After a series of buys the property must continue to hold while
        // the curve is still trading.
        for (uint256 i = 0; i < 10; i++) {
            if (!bonding.isTrading(tokenAddr)) break;
            _buy(tokenAddr, trader, 100 ether);
            if (bonding.isTrading(tokenAddr)) {
                assertTrue(IPair(pairAddr).tokenBalance() < _reserve0(pairAddr), "invariant must hold after every buy");

        }
