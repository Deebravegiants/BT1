## Analysis

I was unable to fully confirm the exact weight formula used in `weight()` (in `modules/pallets/ismp/src/weights.rs`) before running out of iterations, so I cannot definitively state whether the extrinsic weight scales per-message. Based on what I did confirm — `#[pallet::weight(weight())]` takes no arguments related to the `messages: Vec<Message>` parameter — the weight annotation appears to be a fixed/generic weight rather than one computed from `messages.len()` or per-message-type cost, which is the key uncertainty in this analog.

### Title
Unbounded/uncharged iteration over attacker-supplied message batch in `pallet-ismp::handle_unsigned` - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`handle_unsigned` is a fee-less, permissionless (`ensure_none`) unsigned extrinsic that accepts an arbitrary `Vec<Message>` and passes it straight to `Pallet::<T>::execute`, which iterates over every message and, for each, runs full cryptographic/proof verification (consensus signature/MMR/BLS/merkle-proof checks, membership/non-membership trie proofs, and module dispatch) with no explicit cap on batch size and (as observed) a weight annotation, `weight()`, that does not appear to take the message count as an argument.

### Finding Description
`execute()` maps over the whole `messages` vector unconditionally: [1](#0-0) 

and `handle_unsigned` is the unsigned, permissionless dispatch entrypoint for this: [2](#0-1) 

Critically, this same unbounded `execute()` call also runs inside `validate_unsigned`, meaning the *full* cost of verifying every message in the batch (BEEFY/GRANDPA/BSC/sync-committee/Tendermint/Pharos signature checks, MMR/merkle multi-proofs, trie non-membership proofs) is paid **twice** for every node that merely validates a gossiped unsigned transaction, before it is ever included in a block: [3](#0-2) 

This is structurally identical to the reported bug class: a block-processing hot path (`SafeApplyFuncOnAllActiveEpochEndingTopics`, called every `EndBlocker`) that loops over an attacker/user-influenced collection whose size is not properly bounded relative to the weight/gas charged, risking a mismatch between declared cost and actual computational cost. Here, the collection is the `messages: Vec<Message>` batch submitted by any unprivileged relayer in a single unsigned extrinsic — reachable exactly as required ("a relayed proof" / "dispatched request"). Each `Message::Consensus` variant alone can trigger expensive BLS aggregate-signature verification and MMR/merkle-multi-proof verification (e.g. `verify_mmr_update_proof`, `verify_sync_committee_attestation`, `verify_bsc_header`), so a batch of many such messages multiplies actual CPU cost per submitted transaction while the declared `weight()` does not appear to scale with the number/type of messages.

### Impact Explanation
If the per-call weight is not properly scaled to the number and type of messages in the batch, a relayer (unprivileged, since `handle_unsigned` requires no signature/fee) can construct a single transaction whose declared weight fits comfortably under the block weight limit but whose actual execution time (running dozens/hundreds of consensus/proof verifications) is dramatically higher than budgeted. Because `execute()` is also invoked inside `validate_unsigned` — which every full node runs to admit the transaction into its pool/gossip — this cost is imposed on all validating nodes even before inclusion, and can be repeated across resubmissions. This can slow down transaction pool processing and block production across the network, mirroring the "slow ABCI method" impact described in the source report (topic/consensus data getting out of date, degraded block production, and in the worst case a chain halt).

### Likelihood Explanation
The path is reachable by any unprivileged party submitting a single unsigned extrinsic (`handle_unsigned`) with a large `Vec<Message>`; there is no fee to disincentivize large batches (that is the pallet's stated purpose — free execution of valid proofs), and I found no explicit maximum-batch-size bound (`BoundedVec`/`MaxMessages`) enforced before iteration in `execute`. The main uncertainty is whether `weight()` (in `modules/pallets/ismp/src/weights.rs`, not fully inspected) already scales per-message/per-type; if it does not, likelihood of a real DoS is high given how cheap it is for a relayer to craft a large but individually-valid batch of consensus/request/response messages.

### Recommendation
- Bound `messages` in `handle_unsigned` to a configurable maximum length (e.g. `BoundedVec<Message, T::MaxMessages>`).
- Compute the declared extrinsic weight as a function of the batch's actual composition (number and type of consensus/request/response/timeout messages), reflecting the true worst-case cost of the cryptographic verification routines each type triggers (BLS aggregation, MMR/merkle multi-proof, trie non-membership proofs), rather than a single fixed/generic `weight()`.
- Consider skipping or cheaply pre-filtering the full `execute()` verification inside `validate_unsigned` (or caching results) to avoid double-paying the full proof-verification cost for pool admission and block execution.
- Add benchmarks that specifically stress large heterogeneous batches to ensure declared weight tracks worst-case execution time.

### Proof of Concept
Not independently reproduced — this finding is based on static analysis of `handle_unsigned` → `execute` and `validate_unsigned` control flow together with the absence of an observed per-message-scaled weight or explicit batch-size cap; the actual weight formula in `modules/pallets/ismp/src/weights.rs` should be inspected/benchmarked to confirm whether it already accounts for `messages.len()` and message-type cost before treating this as conclusively exploitable.
