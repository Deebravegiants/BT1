### Title
Fee-on-Transfer token deposits/swaps mint LP tokens and price swaps against nominal transfer amounts instead of actual vault-received amounts, causing insolvent pool accounting - (File: program/src/processor.rs)

### Summary
`process_deposit`, `process_swap_base_in`/`_out` (and their `_v2` variants) compute LP-mint amounts and swap-output amounts using the nominal amount the caller intends to transfer (`deduct_coin_amount`, `deduct_pc_amount`, `swap.amount_in`/`swap_in_after_add_fee`) combined with the vault balances read *before* the transfer, then call `Invokers::token_transfer` for that nominal amount without ever re-reading the vault's post-transfer balance to confirm it actually increased by that amount.

### Finding Description
In `Processor::process_deposit` (`program/src/processor.rs:1174-1340`), `total_coin_without_take_pnl`/`total_pc_without_take_pnl` are derived from `amm_coin_vault.amount`/`amm_pc_vault.amount` read once at the top of the instruction [1](#0-0) . `mint_lp_amount` is then computed from `deduct_coin_amount`/`deduct_pc_amount` against that pre-transfer total [2](#0-1) , and only afterward are the coin/pc tokens actually moved into the vaults via `Invokers::token_transfer` [3](#0-2) , which is a thin wrapper around `spl_token::instruction::transfer` with no balance-delta check [4](#0-3) .

The same pattern occurs in the swap paths: `process_swap_base_in`/`process_swap_base_in_v2`/`process_swap_base_out`/`process_swap_base_out_v2` compute `swap_amount_out` (or `swap_in_after_add_fee`) from the pre-transfer vault balances and the nominal `swap.amount_in`/`swap.amount_out`, then transfer the input in and the output out with no verification that the input side actually credited the vault by the assumed amount [5](#0-4) [6](#0-5) .

If `coin_vault_mint` or `pc_vault_mint` is configured (at pool creation via `Initialize2`, which is a permissionless pool-creator-reachable instruction) as a fee-on-transfer token, the vault will receive strictly less than the nominal amount used in every downstream calculation, exactly mirroring the root cause described in the referenced report: the program accounts for the "amount sent" rather than the "amount actually received" by the destination.

### Impact Explanation
- **Deposit path**: LP tokens are minted proportional to the nominal (pre-fee) deposit amount while the vault only receives the post-fee amount. This mints LP shares that are not fully backed by pool assets, diluting/underpaying existing LPs on withdrawal (insolvent pool accounting / unbacked LP minting) — matching the "insolvent pool accounting, unbacked LP minting" impact bar.
- **Swap path**: `swap_amount_out` is computed as if the pool's coin/pc reserve increased by the full nominal `amount_in`, but the vault only gains the post-fee amount. The pool pays out an output amount sized for a larger input than it actually received, permanently transferring value from LPs to the swapper on every trade of the fee-on-transfer side — a repeatable value-extraction/drain vector, not merely a revert.
- **Withdraw path** is comparatively safe because `coin_amount`/`pc_amount` are derived from real vault balances read fresh at withdrawal time [7](#0-6) , so it does not compound the error further, but it inherits the mis-accounted (inflated) `lp_amount` from the deposit step.

### Likelihood Explanation
Reachable from a single permissionless deposit or swap transaction with attacker-chosen accounts (any user-supplied token accounts matching the pool's fixed `coin_vault_mint`/`pc_vault_mint`) once a pool is created (via the permissionless `Initialize2` instruction, explicitly in scope) with a fee-on-transfer coin or pc mint. No privileged signer or non-default build is required; the exploit is a normal SPL Token transfer with a token program that charges a transfer fee.

### Recommendation
Read `amm_coin_vault`/`amm_pc_vault` balances again immediately after the inbound `Invokers::token_transfer` calls in `process_deposit` and all four swap handlers, and use the actual balance delta (post-transfer minus pre-transfer) — not the nominal `deduct_coin_amount`/`deduct_pc_amount`/`swap.amount_in` — for `mint_lp_amount` and `swap_amount_out` calculations. Alternatively, explicitly reject pool creation (`Initialize2`) for mints that are fee-on-transfer/have a transfer hook that can reduce the delivered amount.

### Proof of Concept
1. Attacker (or any pool creator) calls `Initialize2` to create a pool where `coin_vault_mint` is a fee-on-transfer SPL token (e.g., a Token-2022 mint with `TransferFeeConfig`, or a custom fee-charging wrapper accepted by the deployed `spl_token` program instance) charging, say, 10% fee.
2. A user calls `Deposit` intending to deposit `deduct_coin_amount = 100` nominal coin tokens. `process_deposit` computes `mint_lp_amount` from `deduct_coin_amount = 100` against the current pool ratio [2](#0-1) .
3. `Invokers::token_transfer` moves the SPL transfer instruction for `100`, but the vault's real balance only increases by `90` due to the token's fee-on-transfer logic [8](#0-7) .
4. `amm.lp_amount` and the user's minted LP balance now represent a claim on `100` coin-equivalent units while only `90` are actually held by the vault, understating the true backing ratio for all LPs.
5. Repeating deposits (or performing a swap using the fee-on-transfer mint as `user_source`) compounds the shortfall, and at withdrawal the last LPs to redeem cannot receive their proportional share because the vault is short the fee amount, effectively transferring value to earlier depositors/swappers at the expense of later ones — an insolvent-pool-accounting condition.
