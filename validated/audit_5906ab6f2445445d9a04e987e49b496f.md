## Title
Missing `return` after email-extraction failure allows OIDC session creation to proceed with an empty identity - (File: core/sessions/oidcauth/oidc.go)

## Summary
In `handleTokenExchange`, when the `email` claim type-assertion fails at [1](#0-0) , the handler logs an error and writes an HTTP 500 body via `c.String(...)` but does not `return`, unlike every other error branch in the same function (e.g. [2](#0-1)  and [3](#0-2) ). Execution falls through and continues to compute the RBAC role, insert a new `oidc_sessions` row with `user_email=''`, audit-log a successful login, and finally set the session cookie and return HTTP 200 `Success: true`.

## Finding Description
The flow is: verify ID token → parse claims → extract role claim (`ExtractIDClaimValues`) → extract `email` claim → map role (`IDClaimsToUserRole`) → insert `oidc_sessions` row → save session → respond 200. The email-extraction branch is the only one in this function missing a `return` statement after writing an error response, confirmed by direct inspection of the current source: [4](#0-3) . Since `ok` is false when the assertion fails, `email` retains its zero value `""`, and this empty value is what gets persisted (`strings.ToLower(email)`) into the `oidc_sessions` table and used for the audit log entry, while the handler still proceeds to a successful 200 response with a valid session cookie set via `ginSession.Save()`. Note the error message log at line 228 also references the stale `err` variable from the prior `ExtractIDClaimValues` call rather than any error related to the failed type assertion, compounding the confusion in this branch.

## Impact Explanation
This is an authentication/session-integrity defect on the OIDC callback path (`handleTokenExchange`): a step that is supposed to fail hard instead silently continues and mints a working, cookie-backed session tied to an empty `user_email`. This falls into the node API authentication/role-bypass impact category, since a legitimate role (derived from `IDClaimsToUserRole`) can be attached to a session with no verifiable email identity, potentially confusing any downstream logic (`FindUser`, session lookup by email) that assumes `user_email` is non-empty for an authenticated session, and it pollutes the `oidc_sessions` table with sessions lacking a real identity.

## Likelihood Explanation
Exploitation requires a configured OIDC IdP whose ID token passes signature verification (`oi.provider.Verifier(...).Verify`) and contains the RBAC group/role claim (so `IDClaimsToUserRole` succeeds) but omits the top-level `email` claim. This is plausible for real-world IdPs where the `email` claim is optional, misconfigured, or omitted, and does not require the attacker to forge signatures or bypass token verification — only to complete a normal OAuth2 code exchange against a node with OIDC enabled. No operator/admin privileges are needed beyond having a valid account with the IdP, which is the expected caller of this unprivileged, internet-facing callback endpoint.

## Recommendation
Add the missing `return` statement immediately after `c.String(http.StatusInternalServerError, "Failed to get email from claims")` at [1](#0-0)  so the handler aborts before role mapping and session creation, matching the pattern used elsewhere in the function. Also correct the log statement to not reference the unrelated stale `err` variable, and consider fixing the similar pattern at the `oidc_sessions` insert error branch (line 257-260), which also lacks a `return` after `c.String(...)`.

## Proof of Concept
1. Configure a Chainlink node with OIDC authentication enabled against a test/mock IdP.
2. Have the mock IdP issue a valid, verifiable ID token that includes the configured RBAC claim (e.g., `AdminClaim`) but does not include an `email` claim.
3. Drive the OAuth2 authorization code flow to completion against the node's OIDC token-exchange endpoint (`handleTokenExchange`).
4. Observe server-side: `claims["email"].(string)` assertion fails, `c.String(http.StatusInternalServerError, ...)` is written, but execution continues to `IDClaimsToUserRole`, the `INSERT INTO oidc_sessions` call with `user_email=''`, `ginSession.Save()`, and the final `c.JSON(http.StatusOK, {"success": true})`.
5. Confirm the client receives HTTP 200 with `Success: true` and a valid session cookie, and that the `oidc_sessions` table contains a row with `user_email=''` — demonstrating the failed validation step did not prevent session creation.
