### Title
Webhook HMAC signature does not cover the `shop-domain` (or `topic`/`webhook-id`) header, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` (and `topic`, `webhook_id`, `api_version`) purely from unauthenticated HTTP headers, while the HMAC signature that `Utils::HmacValidator` validates covers only the raw request body. Any party who can produce one valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` — trivially obtainable by installing the app on their own shop and capturing a genuine webhook delivery — can replay that same body/HMAC pair to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header and have it accepted as coming from a different, victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from attacker-controllable headers, independent of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` only checks the signature against `to_signable_string` (i.e., the body), never against the headers: [3](#0-2) 

`Webhooks::Registry.process` then trusts `request.shop` as the tenant identity once the (body-only) HMAC passes, and dispatches it to the app's handler as authoritative: [4](#0-3) 

This breaks the intended identity binding: `hmac_valid(bytes) == true` is treated as equivalent to `shop_header == true_originating_shop`, but the two are independent — the HMAC only proves "this body was signed with our `api_secret_key`", not "this body came with these particular headers from this particular shop." Since a single `api_secret_key` is shared across every shop that installs the app, any merchant (an unprivileged, self-service Shopify user) can install the app on their own store, capture one legitimate webhook (body + `x-shopify-hmac-sha256`), and replay it to the app's public webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header rewritten to name a victim shop. The signature still validates because the header values were never part of the signed content.

### Impact Explanation
This is a cross-tenant identity confusion: the host application built on this gem will process the forged request as authentic data/events for the victim shop (e.g., triggering `app/uninstalled`-style session teardown, injecting fabricated order/customer data attributed to another tenant, or bypassing per-shop authorization checks in the handler). This matches the "Critical - cross-tenant access" impact category since it lets one tenant's traffic be misattributed to another tenant purely by header manipulation, without needing the victim's credentials.

### Likelihood Explanation
Medium-to-High: exploitation requires no privileged access, no TLS interception, and no leaked secrets — only that the attacker be a legitimate (even free/trial) merchant of the target app so they can capture one valid webhook body+HMAC pair for their own shop, then POST it directly to the app's public webhook endpoint with a modified shop header.

### Recommendation
Bind the tenant-identifying headers into the signed payload verification path: include `shop`, `topic`, and `webhook_id` (or otherwise cryptographically bind them, e.g. by re-deriving/confirming the shop from a server-side registration/session lookup rather than trusting the header) as part of `to_signable_string`, or require the host application to independently corroborate `request.shop` against a known, previously-established session/store record before processing the webhook payload.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook (e.g. `orders/create`) and capture the raw POST: headers (`x-shopify-topic`, `x-shopify-hmac-sha256`, `x-shopify-shop-domain: attacker.myshopify.com`) and raw JSON body.
2. Send a new POST to the app's webhook endpoint with the identical raw body and identical `x-shopify-hmac-sha256` value, but replace `x-shopify-shop-domain` with `victim.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks the (unchanged) body against the (unchanged) HMAC — the shop header is never covered — see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:12-31`.
4. `Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches `WebhookMetadata` with `shop: "victim.myshopify.com"` to the app's handler, which processes/stores it as if it legitimately originated from the victim shop.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
