### Title
Webhook `shop` identity is taken from an unauthenticated header, not from the HMAC-covered payload - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop` (tenant identity) is read from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, which is not part of the signed material. `Registry.process` validates the HMAC and then hands `request.shop` — an unauthenticated field — to the host app's webhook handler as the tenant identifier.

### Finding Description
`HmacValidator.validate` computes and compares the signature against `verifiable_query.to_signable_string`. For webhooks, that method is defined as: [1](#0-0) 

Only `@raw_body` is signed. The `shop` accessor, however, is derived from a header rather than the signed body: [2](#0-1) 

`Registry.process` validates the HMAC over the body, then immediately trusts `request.shop` (header-derived) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The identity binding that should hold is: `shop value verified by HMAC == shop value delivered to the handler`. Here, the HMAC only proves the body's integrity/authenticity for *some* shop that legitimately owns the `client_secret` used to sign that body; it says nothing about which shop domain header accompanies the request. An attacker who can replay or forward a legitimately-signed webhook body (e.g., a webhook payload from their own store, or a captured payload) can pair it with an arbitrary `x-shopify-shop-domain` header, since the header is never checked against the HMAC. The gem performs no comparison between the header-provided shop and any value embedded in (and covered by) the signed body.

### Impact Explanation
This breaks the tenant/shop binding for webhook delivery: `Registry.process` will hand the host application a `WebhookMetadata.shop` value that the attacker fully controls independent of the HMAC-authenticated body. If the host application uses `request.shop` (as documented and expected by this gem) to select which merchant's DB record, session, or access token to operate on, an attacker with a validly-HMAC-signed payload from any shop can impersonate a different tenant by swapping the shop-domain header, causing the handler to act on/behalf of the wrong tenant. This matches the "cross-tenant access" Critical-impact class: a webhook payload cryptographically authenticated for tenant A can be attributed to arbitrary tenant B purely via header manipulation.

### Likelihood Explanation
Exploitation requires the attacker to already possess one HMAC-valid webhook body (trivial: any legitimate webhook to the attacker's own store, which any unprivileged merchant/dev partner can generate, or any captured/replayed webhook payload) and the ability to set the shop-domain header when delivering the HTTP request to the app's webhook endpoint — both are attacker-controlled inputs at the HTTP layer, requiring no secrets. The impact depends on how strongly the host app relies solely on `request.shop`/`WebhookMetadata.shop` without independently cross-checking the body's own shop-identifying fields (many payloads do include their own `shop_id`/domain in JSON, but the gem does not enforce or expose that cross-check), so real-world exploitability is host-app-dependent, but the gem itself provides no protection against this mismatch and no API to validate the two are consistent.

### Recommendation
Bind the `shop` used for tenant identification to the HMAC-covered signable material, not to an unauthenticated header. At minimum, the gem should document (or enforce) that the shop-domain header must not be trusted for tenant selection unless independently corroborated by data inside the signed body (e.g., a `shop_id`/`myshopify_domain` field present in the payload JSON validated by the app), or the library should expose a helper that cross-validates `request.shop` against the parsed body's own shop-identifying fields before constructing `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers/receives a legitimately Shopify-signed webhook (e.g., `orders/create`) with a valid `x-shopify-hmac-sha256` for the raw body.
2. Attacker resends this exact raw body and valid HMAC header to the app's webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `HmacValidator.validate(request)` succeeds because it only checks the (unmodified) `@raw_body` against the HMAC: [4](#0-3) 
4. `Registry.process` proceeds to call the handler with `shop: request.shop` = `"victim-shop.myshopify.com"`: [5](#0-4) 
5. If the host app trusts this `shop` value to select tenant-specific records/tokens, the attacker has caused the app to attribute attacker-controlled data to `victim-shop.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
