Audit Report

## Title
Stale reward index causes permanently lost rewards when a pool's `total_tokens_staked` is zero - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards`'s `reward_per_token()` short-circuits and returns the unchanged `reward_per_token_stored` whenever `pool_info.total_tokens_staked.is_zero()`, while `update_pool_rewards()` unconditionally advances `last_update_block` to the current block regardless of whether the accumulator was actually updated. This causes reward emissions accrued during any zero-stake window to be permanently skipped from the accumulator and effectively stranded in the pool's reward account.

## Finding Description
`reward_per_token()` returns the stale, unchanged value when stake is zero: [1](#0-0) . The subsequent `update_pool_rewards()` call still advances `last_update_block` to `current_block_number()`: [2](#0-1) . Because `last_update_block` moves forward without any corresponding accumulator increment, the next call to `reward_per_token()` only computes elapsed blocks *after* this new `last_update_block`, permanently excluding the elapsed window from the reward calculation.

This code path is reachable through the pallet's unprivileged, public extrinsics: `stake` and `unstake` both call `Self::update_pool_and_staker_rewards(&pool_info, &staker_info)` before mutating `total_tokens_staked` [3](#0-2) [4](#0-3) , as does `harvest_rewards` [5](#0-4) . Since `unstake` allows a staker to fully withdraw their tokens, bringing `total_tokens_staked` to zero, and any subsequent `stake`/`unstake`/`harvest_rewards` call by any staker (including into a still-zero-staked pool) triggers `update_pool_rewards` with the stale index, the bug is triggerable entirely by ordinary unprivileged users through real extrinsics, with no admin or governance action required.

There is no existing guard that freezes `last_update_block` while stake is zero, nor any mechanism that redirects or accounts for the reward-rate emission during the zero-stake window; `cleanup_pool` only returns the pool's *entire* remaining balance and only when there are zero stakers at teardown time, which is not a substitute accounting path for the specific lost-emission amount [6](#0-5) .

## Impact Explanation
Reward tokens pre-funded into a pool's dedicated account at `reward_rate_per_block` become unrecoverable for any block range in which the pool has zero total stake — they are not distributed to any staker (since none existed during that window) and are not returned to the admin through any normal mechanic; only a full pool teardown via `cleanup_pool` reclaims the (undifferentiated) remaining balance. This is an accounting/fund-loss defect in the pallet's own reward-index bookkeeping, not a mocked path, admin-only issue, or purely theoretical scenario, and does not require a compromised or privileged actor.

## Likelihood Explanation
Reaching a zero-stake window is a normal, expected condition: any staker(s) can fully unstake via the unprivileged `unstake` extrinsic, and pools are commonly created with a running `reward_rate_per_block` before the first staker joins via `create_pool`. No special privileges, governance intervention, or unrealistic assumptions are needed — a single staker unstaking fully and a later new staker joining is sufficient to reproduce lost accrual for the intervening idle period.

## Recommendation
When `total_tokens_staked` is zero, avoid advancing `last_update_block` while leaving `reward_per_token_stored` unchanged. Either (a) do not update `last_update_block` past the point where stake became zero so a later computation still correctly measures the frozen window, or (b) explicitly track the un-distributable emission (`reward_rate_per_block * elapsed_blocks_at_zero_stake`) and provide a recovery path (e.g., returning it to the pool admin) instead of leaving it permanently unaccounted for in the pool's reward account.

## Proof of Concept
1. Admin calls `create_pool` with a nonzero `reward_rate_per_block` and funds the pool account via `deposit_reward_tokens`.
2. A staker calls `stake` to join the pool, then later calls `unstake` for the full amount, bringing `total_tokens_staked` to `0`. At this point `update_pool_and_staker_rewards` → `update_pool_rewards` sets `last_update_block` to the current block while `reward_per_token()` returned the stale, unchanged `reward_per_token_stored` (due to the zero-stake short circuit).
3. `N` blocks pass with `total_tokens_staked == 0`.
4. A new staker calls `stake`. The next `reward_per_token()` computation only counts blocks elapsed since the updated `last_update_block`, permanently omitting `reward_rate_per_block * N` from the accumulator — this amount remains in the pool's reward account with no accounting path to recover it short of a full `cleanup_pool` teardown (which requires zero stakers and returns the undifferentiated total balance, not the specific stranded amount).

		pub fn unstake(
			origin: OriginFor<T>,
			pool_id: PoolId,
			amount: T::Balance,
			staker: Option<T::AccountId>,
		) -> DispatchResult {
			let caller = ensure_signed(origin)?;
			let staker = staker.unwrap_or(caller.clone());

			// Always start by updating the pool rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);

			let staker_info = PoolStakers::<T>::get(pool_id, &staker).unwrap_or_default();
			let (mut pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			// Check the staker has enough staked tokens.
			ensure!(staker_info.amount >= amount, Error::<T>::NotEnoughTokens);

			// Unfreeze staker assets.
			T::AssetsFreezer::decrease_frozen(
				pool_info.staked_asset_id.clone(),
				&FreezeReason::Staked.into(),
				&staker,
				amount,
			)?;

			// Update Pools.
			pool_info.total_tokens_staked.ensure_sub_assign(amount)?;
			Pools::<T>::insert(pool_id, pool_info);

			// Update PoolStakers.
			staker_info.amount.ensure_sub_assign(amount)?;

			if staker_info.amount.is_zero() && staker_info.rewards.is_zero() {
				PoolStakers::<T>::remove(&pool_id, &staker);
			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
			}

			// Emit event.
			Self::deposit_event(Event::Unstaked { caller, staker, pool_id, amount });

			Ok(())
		}

		#[pallet::call_index(8)]
		pub fn cleanup_pool(origin: OriginFor<T>, pool_id: PoolId) -> DispatchResult {
			let who = ensure_signed(origin)?;

			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			ensure!(pool_info.admin == who, BadOrigin);

			let stakers = PoolStakers::<T>::iter_key_prefix(pool_id).next();
			ensure!(stakers.is_none(), Error::<T>::NonEmptyPool);

			let pool_balance = T::Assets::reducible_balance(
				pool_info.reward_asset_id.clone(),
				&pool_info.account,
				Preservation::Expendable,
				Fortitude::Polite,
			);
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&pool_info.admin,
				pool_balance,
				Preservation::Expendable,
			)?;

			if let Some((who, cost)) = PoolCost::<T>::take(pool_id) {
				T::Consideration::drop(cost, &who)?;
			}

			Pools::<T>::remove(pool_id);

			Self::deposit_event(Event::PoolCleanedUp { pool_id });

			Ok(())
		}
