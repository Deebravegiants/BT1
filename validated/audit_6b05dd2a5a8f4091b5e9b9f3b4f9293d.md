### Title
Webhook `shop` domain is not bound to the HMAC signature, enabling cross-tenant webhook shop-spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC that covers only the raw request body, then trusts the `X-Shopify-Shop-Domain` header — which is not covered by that HMAC — to identify which merchant the payload belongs to. Any party who can obtain one validly-signed webhook body (e.g., by installing the app on their own store, which any unprivileged internet user can do) can replay that same body+HMAC while substituting an arbitrary `shop-domain` header value, and the library will hand the handler a `WebhookMetadata` claiming the payload originated from a different shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read from a plain HTTP header that is entirely independent of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC and, once it passes, forwards the request's `shop` (and `topic`, `webhook_id`, `api_version`) straight to the registered handler without any check that binds `shop` to the signed body: [3](#0-2) 

`Utils::HmacValidator.validate` / `validate_signature` compute the HMAC purely over `verifiable_query.to_signable_string`, i.e. the raw body for webhooks — again, `shop` never enters the computation: [4](#0-3) 

The identity binding that should hold is:
`HMAC(body, api_secret_key) valid ⇒ shop header == shop that Shopify actually sent this body for`

But the code only proves `HMAC(body, api_secret_key)` is valid; it never proves the second half of that equality. Concretely:
- **Before**: Attacker installs the target app on their own (attacker-owned) shop `attacker.myshopify.com`. Shopify sends a real webhook: body `B`, headers `{shop-domain: attacker.myshopify.com, hmac: H}` where `H = HMAC(B, secret)`.
- **Attacker's request**: Attacker POSTs the exact same body `B` and `hmac: H` to the app's webhook endpoint, but sets `shop-domain: victim.myshopify.com`.
- **After**: `HmacValidator.validate` recomputes `HMAC(B, secret) == H` → passes (body unmodified). `Registry.process` then builds `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)` and invokes the host app's handler as if `victim.myshopify.com` produced payload `B`.

This is exactly the class of bug flagged in the report: the field that downstream logic acts on (`shop`) is not the field actually protected by the cryptographic check (`body`), so verified-bytes and acted-upon-identity diverge — analogous to `totalGlobalShares` being mutated by paths that the exchange-rate function does not account for.

### Impact Explanation
Any handler that trusts `WebhookMetadata#shop` to select which tenant's data/record to update, create, or delete (the documented and expected use of that field) can be tricked into applying another merchant's webhook data — or an attacker's own crafted body content — under a victim shop's identity. This is a cross-tenant confusion/cross-tenant access vector achievable by any user capable of installing the app on a shop they control, which is the normal, unprivileged installation flow for a public Shopify app. No access token, `client_secret`, or leaked credential is required — only a legitimately-received webhook of the attacker's own.

### Likelihood Explanation
Likelihood is meaningful but bounded: the attacker needs at least one legitimately signed webhook body for a topic/handler the app registers (trivial — install the app on an attacker-controlled dev store, which triggers real webhooks such as `app/uninstalled`, `shop/update`, etc.), and the impact depends on host applications keying persistence/actions off `WebhookMetadata#shop` without independent shop verification, which is the documented, expected usage pattern shown in this gem's webhook handler examples.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie the header set to the body before trusting it — e.g., include the relevant headers in the signable string, or require the caller to separately re-verify that the shop in the metadata matches a shop with an active, stored session/installation before acting on the payload. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for authorization decisions without additional verification.

### Proof of Concept
1. Install the target app on `attacker.myshopify.com` and capture one real webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H`.
2. Replay to the app's webhook endpoint:
   ```
   POST /webhooks
   x-shopify-topic: <same topic>
   x-shopify-hmac-sha256: H
   x-shopify-shop-domain: victim.myshopify.com
   x-shopify-webhook-id: <any>
   x-shopify-api-version: <any>

   <body B, byte-for-byte>
   ```
3. `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(B, secret) == H`.
4. `Registry.process` invokes the registered handler with `WebhookMetadata(shop: "victim.myshopify.com", body: B, ...)`, i.e., the host application processes attacker-controlled body content under the victim shop's identity.
