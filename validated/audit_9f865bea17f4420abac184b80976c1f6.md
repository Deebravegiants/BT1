### Title
Stale `EditAssetInSpoke` can re-freeze a listing after its scheduled relaxation - ([File: contracts/controller/src/config/asset.rs](contracts/controller/src/config/asset.rs))

### Summary
A ready `EditAssetInSpoke` operation carries absolute `paused`, `frozen`, and `no_seize` values but is not bound to the listing's flags epoch, while `RelaxSpokeAssetFlags` is epoch-bound. [1](#0-0)  Because `governance.execute` may be called by anyone with `executor = None`, a stranger can deliberately execute a stale flag-tightening edit immediately after a relaxation clears the same flags. [2](#0-1) 

### Finding Description
`edit_asset_in_spoke` validates the proposed flags only against their current stored values: a `false -> true` transition passes the flag ratchet, while a `true -> false` transition reverts. [3](#0-2) [4](#0-3)  The relaxation endpoint has a stronger freshness rule and rejects execution when `expected_epoch` differs from the live flags epoch. [5](#0-4) 

The governance resolver includes `expected_epoch` in `RelaxSpokeAssetFlagsArgs`, but `SpokeAssetArgs` has no comparable epoch field and is scheduled verbatim. [1](#0-0)  Once scheduled, an `EditAssetInSpoke` containing a tightening flag remains executable even though a later flag write has changed the listing's epoch. [6](#0-5) 

### Impact Explanation
Re-executing the stale edit can set `paused`, `frozen`, or `no_seize` again after governance has cleared them. [7](#0-6)  A re-applied `paused` flag can block ordinary exits and selected repayments, while `no_seize` can block the collateral leg of pro-rata liquidation until another delayed relaxation succeeds. [8](#0-7)  This is therefore temporary freezing of user funds and liquidation functionality rather than a permanent freeze. [9](#0-8) 

### Likelihood Explanation
The sequence is realistic during incident handling: an edit proposed while a listing is paused may legitimately copy `paused = true`, after which governance schedules and executes a relaxation. [10](#0-9)  At that point any unprivileged address can submit the still-ready stale edit with `executor = None`, because `authorize_executor` performs no authentication or role check for `None`. [11](#0-10)  The attacker cannot create the privileged proposal, but can choose to execute an already-authorized stale payload at the harmful point in the ordering. [12](#0-11) 

### Recommendation
Bind every scheduled `EditAssetInSpoke` that writes halt flags to the listing's flags epoch, as `RelaxSpokeAssetFlags` already does. [13](#0-12)  For example, add `expected_epoch` to `SpokeAssetArgs` or to a dedicated edit-flags operation, reject the edit if it differs from `get_spoke_flags_epoch`, and then write the new configuration. [5](#0-4) 

### Proof of Concept
1. The guardian pauses a listing through `set_spoke_asset_flags(spoke_id, hub_asset, paused = true, frozen = false, no_seize = false)`, producing flags epoch `E`. [14](#0-13) 
2. A proposer schedules `AdminOperation::EditAssetInSpoke` with otherwise valid `SpokeAssetArgs` that retain `paused = true`. [15](#0-14) 
3. Governance proposes `RelaxSpokeAssetFlags(expected_epoch = E, paused = false, frozen = false, no_seize = false)` and executes it after its delay, clearing `paused` and advancing the epoch. [16](#0-15) [5](#0-4) 
4. An unauthenticated attacker calls `governance.execute(None, controller, "edit_asset_in_spoke", stale_args, zero_predecessor, salt)` once the stale edit is ready. [2](#0-1) 
5. The controller's ratchet accepts `paused = false -> true`, stores `paused = true`, and advances the flags epoch again. [17](#0-16) [7](#0-6) 
6. A user attempting an affected exit or repayment then receives `SpokeAssetPaused`, and the listing remains unusable for those flows until a fresh delayed relaxation is proposed and executed. [18](#0-17) [19](#0-18)

```markdown
### ADR-0008: Independent halt flags

The `frozen`, `paused`, and `no_seize` flags control different actions. Entry
checks paused/frozen, ordinary exits check paused, and collateral seizure
checks no_seize. A paused debt leg does not block repayment of another selected
```

```markdown
A listing pause applies to one spoke, while the market's pool serves its whole
hub. Borrowers in the paused listing cannot repay, but another spoke that lists
```

```markdown
## Review pending operations

Do this immediately after the flags are set.

A listing edit proposed before the freeze cannot clear it: the controller
rejects an edit that turns a set flag off. A relaxation proposed before the
freeze cannot clear it either, because every flag write advances the listing's
flags epoch and the old relaxation names the old epoch. Other pending
operations, such as `Unpause`, still execute as proposed.

1. The verb prints every operation recorded in `configs/ops/<network>/` with its
   live state. `make <network> listOps` prints the same list. An operation
   proposed without a record there does not appear.
2. Cancel each `Waiting` or `Ready` operation that must not run during the
   incident: `make <network> cancelOp <op-id> SIGNER=<canceller>`. A pending
   edit of the frozen listing that names the old flags reverts at execution;
   cancel it too.
```

```markdown
## Clear the flags

    make <network> relaxAssetFlags <config-spoke-id> <asset> <flags> SIGNER=<proposer>

1. `<flags>` is a comma list of the flags to clear. The verb reads the live
   listing and its flags epoch, keeps every flag not named, and schedules
   `RelaxSpokeAssetFlags` bound to that epoch. It refuses a flag that is not set.
2. The verb waits for the delay, then executes the operation. With
   `AUTO_EXECUTE=0` it only schedules; run `make <network> executeOp <op-id>`
   after the delay. If any flag write lands first, the operation reverts with
   `SpokeFlagsEpochMismatch`; run the verb again.
3. Read the listing again with
   `make <network> getSpokeAsset <config-spoke-id> <asset>`.

`editAssetInSpoke` refuses a config that sets a live flag to `false` and names
this verb instead.
```
