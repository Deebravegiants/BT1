## Title
Permissionless `CallDispatcher.dispatch()` allows anyone to steal residual funds temporarily held by the shared executor - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` is a fully public function with no caller restriction, no ownership tracking of the funds it forwards, and no reentrancy guard. It is used as a **shared, singleton** utility contract by multiple unrelated protocol flows (`HyperFungibleToken`, `WrappedHyperFungibleToken`, `IntentGatewayV2`, `IntentsBase`/`ExtrinsicIntents`) to execute arbitrary calldata while temporarily custodying user/solver funds mid-transaction. Any balance that ends up sitting in this contract outside the narrow set of tokens the calling app explicitly sweeps back (e.g. from fee-on-transfer tokens, DeFi reward/airdrop side-effects of a predispatch/postdispatch call, or any other accounting edge case) is permanently exposed: since `dispatch()` has zero access control, anyone can call it directly with an arbitrary `Call[]` that moves that balance to themselves.

### Finding Description
`CallDispatcher.dispatch()` decodes an attacker-supplied `Call[]` and executes each entry with the `CallDispatcher` contract itself as `msg.sender`, without checking who invoked `dispatch()`: [1](#0-0) 

This contract is treated by several apps as a trusted, temporary custodian during multi-step "swap-then-escrow" / "fill-then-sweep" flows. Funds are pushed to `dispatcher` first, arbitrary calldata is executed, and only the tokens explicitly enumerated by the calling app (`order.inputs`, `order.output.assets`, or the HFT `Message.data` calldata) are swept back: [2](#0-1) [3](#0-2) 

Because the same `CallDispatcher` address is shared across every deployment/app that uses it (`HyperFungibleToken.onAccept`, `WrappedHyperFungibleToken.onAccept`, `IntentGatewayV2`/`IntentsBase` predispatch and postdispatch), any token balance it ends up holding that is *not* part of the enumerated sweep set (for example, a reward/airdrop token produced by a DeFi call embedded in `order.predispatch.call`/`order.output.call`, dust from rounding, or a stuck transfer from a failed downstream step) is not recoverable by the protocol logic and instead sits in a contract that anyone can drain, since `dispatch()` performs no `msg.sender`/authorization check at all. [4](#0-3) 

### Impact Explanation
Any value left in the shared `CallDispatcher` contract — belonging either to the protocol (accounted as "dust") or transiently to a user/solver mid-flow — can be permanently stolen by an unprivileged third party simply by calling `CallDispatcher.dispatch()` directly with calldata that transfers the balance out. This is a direct, unprivileged theft-of-funds primitive reachable from a single external transaction, matching the "concrete theft ... of funds" impact bar, since the singleton dispatcher is depended upon by every intent/token-bridge flow in the codebase.

### Likelihood Explanation
The precondition (residual balance sitting in the dispatcher) is only guaranteed to be zero when the calling app's sweep loop covers every token type that could end up there. Because the sweep set is fixed to `order.inputs`/`order.output.assets` (or the HFT message body) and the arbitrary calldata executed via `dispatch()` can interact with any external protocol (DEXes, lending markets, reward-bearing contracts per the docs' own examples), any deviation between what the predispatch/postdispatch call actually produces and what the app explicitly sweeps back creates an exploitable window. Given `dispatch()` itself has no access control, exploitation requires nothing more than observing a non-zero balance on the `CallDispatcher` address and submitting one transaction.

### Recommendation
Restrict `CallDispatcher.dispatch()` to be callable only by the authorized set of apps that are meant to use it (e.g. an allowlist of caller addresses set at construction, or per-app dedicated dispatcher instances instead of one global singleton), and/or ensure the contract never retains a persistent balance between transactions by requiring a `require(address(this).balance == 0)` / full-balance-sweep invariant at the end of every `dispatch()` call for all tokens touched.

### Proof of Concept
1. A user places/fills an `IntentGatewayV2` order whose `predispatch.call` or `output.call` routes through a third-party protocol that pays out an extra token not listed in `order.inputs`/`order.output.assets` (e.g., a liquidity-mining reward token, or dust from a swap route) — this token remains on the shared `CallDispatcher` contract after `_execute`'s sweep loop finishes, since the sweep only iterates over `outputsLen`/`inputsLen` token entries.
2. Anyone monitoring the chain calls `CallDispatcher.dispatch(abi.encode([Call{to: rewardToken, value: 0, data: transfer(attacker, balance)}]))` directly — no `IntentGatewayV2`/`HyperFungibleToken` involvement required, since `dispatch()` has no caller restriction.
3. The reward token balance is transferred to the attacker, permanently removing it from the protocol/user that was entitled to it. [1](#0-0)

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
