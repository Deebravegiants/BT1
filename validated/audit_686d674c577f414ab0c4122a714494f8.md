### Title
Missing storage gaps in `IntentsBase`/`ExtrinsicIntents` risk corrupting the hardcoded `_filled` storage slot relied on for cross-chain escrow verification - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2` is a UUPS-upgradeable contract (deployed behind an `ERC1967Proxy`, upgraded via `ExtrinsicIntents.upgradeToAndCall`) that inherits from `IntentsBase` and `ExtrinsicIntents` [1](#0-0) . Neither `IntentsBase` nor `ExtrinsicIntents` declares a `uint256[N] private __gap;` storage-gap reservation, unlike `SimplexPaymaster`, which does include `uint256[48] private __gap;` [2](#0-1) . Meanwhile `IntentsBase` hardcodes an absolute storage slot (`FILLED_SLOT_BIG_ENDIAN_BYTES = 0x...02`) for the `_filled` mapping that cross-chain cancel/escrow-release proofs depend on [3](#0-2) .

### Finding Description
`IntentGatewayV2`'s upgrade path is reachable purely from cross-chain governance messages relayed through Hyperbridge: `ExtrinsicIntents.upgradeToAndCall` is called from `onAccept` under `onlyHost`, and delegatecalls `ERC1967Utils.upgradeToAndCall(newImplementation, data)` to swap the implementation and optionally run migration calldata in the same transaction [1](#0-0) . Tests confirm and pin the exact slot dependence: `testFilledMappingStaysAtSlotTwo` asserts `_filled` sits precisely at storage slot 2, and comments explicitly note "The cross-chain cancel proof (FILLED_SLOT_BIG_ENDIAN_BYTES) depends on this exact slot" [4](#0-3) .

Because `IntentsBase` (the abstract contract declaring `_filled` and other shared state) has no trailing storage-gap array, any future upgrade that adds a new state variable to `IntentsBase` or to any contract earlier in the inheritance chain than where `_filled` is declared will shift `_filled` off slot 2. Since `FILLED_SLOT_BIG_ENDIAN_BYTES` is a compile-time constant baked into the contract and used to construct the storage-proof key for the cross-chain cancel/redeem flow, a slot shift silently breaks that proof construction — proofs would either fail to verify (freezing legitimate escrow releases) or, in a worse case, resolve to attacker-influenced storage if the shifted layout happens to alias with other mapping/array slots, since Solidity mapping slots are `keccak256(key, baseSlot)`-derived and any baseSlot collision from an inheritance-order/layout change can be exploited to read/forge different data than intended.

This differs from the general "any future incorrect upgrade could brick the protocol" framing in the source audit report: here the exposure is more concrete because the contract *itself* hardcodes and depends on a fixed slot number (`FILLED_SLOT_BIG_ENDIAN_BYTES`) for a security-critical mapping consumed by unprivileged, permissionless proof submission in the intents escrow flow, and the base contracts holding that mapping have no gap reservation to guarantee the slot survives additive changes made by later, unrelated upgrades.

### Impact Explanation
If a future upgrade to `IntentGatewayV2` adds a new state variable anywhere in `IntentsBase`/`ExtrinsicIntents` (or reorders/adds inherited contracts) without accounting for the missing gaps, the `_filled` mapping's actual slot moves while `FILLED_SLOT_BIG_ENDIAN_BYTES` stays hardcoded at slot 2. Any cross-chain cancel/redeem-escrow proof built against that constant would then verify against the wrong storage slot — permanently freezing legitimate escrowed funds tied to `_filled`/`_orders` state (unable to redeem or cancel via valid proofs) or, in the worst case, allowing a forged proof to be accepted against unrelated storage content, resulting in unauthorized escrow release. This qualifies as concrete permanent freezing of funds / forged message verification once triggered by an otherwise legitimate governance upgrade.

### Likelihood Explanation
The likelihood is low-to-moderate: it requires a future upgrade (not the current deployed version) to add fields to the base contracts. However, the codebase's own extensive testing and comments (`testFilledMappingStaysAtSlotTwo`, "must depend on this exact slot") show the developers are already relying on manual slot-pinning discipline rather than structural gap protection, which is exactly the fragile pattern OZ recommends storage gaps to prevent. Given `IntentGatewayV2` is under active development (already at `VERSION = 2` with a documented migration history, `ExtrinsicIntents`/`IntentsBase` diamond inheritance, and a live mainnet proxy that is upgraded periodically per the test suite), further additive upgrades are a realistic and expected event, and there is no automated protection against inheritance-order layout drift beyond the single pinned test for slot 2.

### Recommendation
Add explicit storage-gap reservations (e.g., `uint256[50] private __gap;`) at the end of `IntentsBase` and `ExtrinsicIntents`, matching the pattern already used in `SimplexPaymaster` [2](#0-1) . Additionally, add a CI-level storage-layout diff check (e.g. via `forge inspect IntentGatewayV2 storage` compared against a committed snapshot) so any upgrade that would shift `_filled` off slot 2 fails automated checks before deployment, rather than relying solely on the existing hand-written `testFilledMappingStaysAtSlotTwo` regression test.

### Proof of Concept
1. `IntentsBase` declares `_filled` (and other state) with no `__gap` reservation; `FILLED_SLOT_BIG_ENDIAN_BYTES` hardcodes slot 2 as a compile-time constant [3](#0-2) .
2. `ExtrinsicIntents.upgradeToAndCall`, reachable only via a Hyperbridge-sourced `Execute` governance message delivered through `onAccept`/`onlyHost`, delegatecall-swaps the implementation and optionally runs migration calldata [1](#0-0) .
3. Suppose a future implementation adds one new state variable to `IntentsBase` before the `_filled` declaration (a plausible, ordinary maintenance change given there's no gap to preserve layout). After the upgrade, `_filled`'s true slot becomes 3, but `FILLED_SLOT_BIG_ENDIAN_BYTES` (used by the cross-chain cancel proof construction) still points at slot 2.
4. Any subsequent cancel/redeem-escrow proof submitted by a relayer/user, built off `FILLED_SLOT_BIG_ENDIAN_BYTES`, now verifies against the wrong slot content — `testFilledMappingStaysAtSlotTwo`'s invariant (`evm/tests/foundry/IntentGatewayV2Test.sol:4124-4134`) would fail, evidencing the layout break, and in production this manifests as either failed valid redemptions (frozen escrow) or a forged/unintended value being read as the "filled" record for a commitment.
