### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop-identity spoofing in `Registry.process` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` (and `topic`/`webhook_id`) values consumed by `Registry.process` are read from unauthenticated HTTP headers. This breaks the intended binding `HMAC-verified bytes == bytes acted on`, letting an attacker who possesses one valid `(body, hmac)` pair replay it with a forged `x-shopify-shop-domain` header to make the host application process the webhook under a different tenant's identity.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

only the `@raw_body` is included in the signable string used to compute/verify the HMAC. The `shop`, `topic`, and `webhook_id` values are pulled straight from headers without any cryptographic binding to the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then trusts `request.shop`, `request.topic`, and `request.webhook_id` from the headers to build the `WebhookMetadata` passed to the host app's handler: [3](#0-2) 

`HmacValidator.validate` simply calls `verifiable_query.to_signable_string` and compares against the computed HMAC using the app's `api_secret_key`: [4](#0-3) 

Because the HMAC is only a function of the body, `HMAC(body)` is identical regardless of which `shop-domain`/`topic`/`webhook-id` headers accompany the request. This is exactly the "field acted on but not covered by the HMAC" analog: the equality that should hold is `hmac == HMAC(body, shop, topic, webhook_id)`, but the implementation only enforces `hmac == HMAC(body)`, so `shop_verified != shop_acted_on` once an attacker swaps headers on a replayed body+hmac pair.

### Impact Explanation
An attacker who legitimately receives even one webhook for their own shop (e.g., they install the app in their own dev/partner store) captures a valid `(raw_body, hmac)` pair. They can replay that exact body/hmac to the app's webhook endpoint while setting `x-shopify-shop-domain` to a victim shop's domain (and optionally change `x-shopify-topic`/`x-shopify-webhook-id`, none of which affect the HMAC). Because `Registry.process` only checks the HMAC against the body and unconditionally trusts the header-derived `shop`, the host application's `WebhookHandler#handle` will execute business logic (e.g., data deletion for GDPR topics, order/customer processing, cache invalidation, triggering side effects tied to a specific merchant) attributed to the wrong shop. This is a cross-tenant identity confusion at the point where this gem hands control back to the host app, satisfying the "cross-tenant access" impact class. The severity depends on what the host's `WebhookHandler` implementation does with `data.shop`, but the gem itself provides no way to trust the tenant binding.

### Likelihood Explanation
The main constraint is that the attacker needs at least one legitimately-signed webhook payload from Shopify (trivially obtainable by installing the app in a shop they control, or from any topic subscribed with a static/predictable body such as `shop/redact`, whose body content may be uninformative but still carries a valid HMAC over that body). Replaying that fixed body against the app's public webhook endpoint with a spoofed `shop-domain` header requires no secrets and no privileged access — an unprivileged internet user (any shop owner able to install the target app) can mount this.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string, or otherwise cryptographically bind them to the verified payload before trusting them in `Registry.process`. At minimum, `to_signable_string` should incorporate the same header fields that `WebhookMetadata` later exposes to handlers, matching Shopify's actual webhook HMAC contract (which Shopify computes over the raw body, but the header values should be treated as untrusted/informational only, or the host app should be warned not to rely on `shop` from `WebhookMetadata` as an authorization boundary without additional validation e.g. against a known/installed shop list).

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; capture a real webhook delivery, e.g. `POST /webhooks` with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`), and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Replay the identical request to the same endpoint, changing only:
   `X-Shopify-Shop-Domain: victim.myshopify.com`
   (body `B` and `X-Shopify-Hmac-Sha256: H` unchanged).
3. In `lib/shopify_api/webhooks/registry.rb` (`Registry.process`), `Utils::HmacValidator.validate(request)` succeeds because it only ever hashes `request.to_signable_string` == `B`.
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop: "victim.myshopify.com"` and passed to the host's `WebhookHandler#handle`, causing the handler to act as though the webhook genuinely originated from the victim shop.
