### Title
Missing zero-address check on ETH transfer destinations allows permanent loss of bridged funds - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`, `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
Multiple Hyperbridge contracts forward native ETH to a destination address derived from cross-chain message data or user-supplied `beneficiary` fields using a raw low-level `call{value: amount}("")`, without checking that the destination is non-zero. Because a `.call` to `address(0)` (or any address with no code) with a value payload returns `success == true`, a zero (or malformed) beneficiary silently burns the transferred ETH — this is the exact bug class reported against `AvailBridge::receiveETH()`.

### Finding Description
The pattern `(bool sent,) = dest.call{value: amount}(""); if (!sent) revert(...)` is used across the codebase to move native ETH to a destination decoded from message payloads without validating that `dest != address(0)`:

- `WrappedHyperFungibleToken.onAccept()` decodes `message.to` from a verified cross-chain `PostRequest` body and calls `beneficiary.call{value: message.amount}("")` when unwrapping WETH to native ETH, with no zero-address check on `beneficiary`. [1](#0-0) 
The same pattern also exists in `onPostRequestTimeout()` for refunds: [2](#0-1) 
and identically in the upgradeable variant: [3](#0-2) 

- `IntentsBase._sendValue()`, used to release escrowed native-token order inputs/outputs to a `beneficiary` decoded from `body.beneficiary` (a `bytes32` cast via `address(uint160(uint256(...)))`), performs the same unchecked call: [4](#0-3) 
called from `_withdraw()` when releasing escrow for a fill or refund: [5](#0-4) 

- The Tron variant `IntentGatewayV2.withdraw()` and its `SweepDust` handling repeat the same unchecked pattern: [6](#0-5) [7](#0-6) 

In all these cases, `dest`/`beneficiary` originates either from a `bytes` field decoded out of a relayed cross-chain message (`message.to`, `body.beneficiary`) or from an order field supplied at order-placement time. None of these paths validate that the resulting address is non-zero before dispatching value via `.call`. Since a `.call{value}("")` to `address(0)` succeeds (it behaves like a transfer to an uninitialized/EOA-like address), any zero or malformed beneficiary silently consumes the ETH with no revert and no recovery path.

### Impact Explanation
A zero/malformed beneficiary causes the transferred native ETH to be irrecoverably lost — for `WrappedHyperFungibleToken`, this is the bridged principal from a cross-chain token transfer; for the Intents escrow path, this is the escrowed order input/output value released on fill or refund. This matches the Medium-severity classification of the original AvailBridge finding: permanent loss of funds due to an omitted zero-address check on a value-bearing low-level call.

### Likelihood Explanation
Reachable from a single, ordinary cross-chain operation by an unprivileged actor: a token bridger calling `send()` on `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` with `to` encoding to a zero/degenerate address, or an intent creator/solver whose order `beneficiary` resolves to `address(0)` (e.g. due to encoding mistakes, truncation bugs, or malicious construction of the `to`/`beneficiary` bytes on the source chain). No governance or admin privilege is required, and the destination-side contract has no way to detect or reject the zero destination since the `.call` reports success.

### Recommendation
Add an explicit `require(dest != address(0))` / custom revert check immediately before every `dest.call{value: amount}("")` in `WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout` (and the upgradeable twin), `IntentsBase._sendValue`, and `IntentGatewayV2.withdraw`/`SweepDust` handling, so malformed beneficiaries revert (allowing retry/refund) instead of silently burning the transferred ETH.

### Proof of Concept
1. On the source chain, call `WrappedHyperFungibleToken.send()` with `params.to` encoding to 20 zero bytes (or a value that decodes via `_toAddr` to `address(0)`).
2. The message is relayed and delivered to the destination `WrappedHyperFungibleToken` via `onAccept()`.
3. `beneficiary = _toAddr(message.to) == address(0)`; `IWETH(_underlying).withdraw(message.amount)` unwraps WETH to native ETH held by the contract.
4. `(bool sent,) = beneficiary.call{value: message.amount}("")` — this call succeeds (`sent == true`) because a value-call to `address(0)` does not revert.
5. The unwrapped ETH is now permanently locked/burned in the sense that it cannot be recovered by anyone — no `Received` recipient exists, and the WETH has already been unwrapped and lost.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleTokenUpgradeable.Message memory message =
            abi.decode(request.body, (HyperFungibleTokenUpgradeable.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({from: message.from, to: beneficiary, source: string(request.source), amount: message.amount});
