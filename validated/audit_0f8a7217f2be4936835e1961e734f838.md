### Title
Stale `ExtrinsicWeightReclaimed` value leaks across extrinsics, causing over-reclaim of `BlockWeight` - ([File: substrate/frame/system/src/extensions/weight_reclaim.rs])

### Summary
`Pallet::reclaim_weight` (invoked from `WeightReclaim::post_dispatch_details`/`bare_post_dispatch` and identically from `CheckWeight::post_dispatch_details`) computes `accurate_reclaim = already_reclaimed.max(unspent)` where `already_reclaimed` comes from the single, non-keyed storage item `ExtrinsicWeightReclaimed`. This value is written with `put(accurate_reclaim)` at the end of an extrinsic's post-dispatch but is never explicitly killed/reset before the next extrinsic in the block runs its own post-dispatch. If the current extrinsic's own `unspent` is smaller than the previous extrinsic's stored value, the stale, larger value is used, over-reducing `BlockWeight` for the current extrinsic.

### Finding Description
`reclaim_weight` is defined to reconcile two sources of "how much weight can be given back": the benchmark-based `unspent = post_info.calc_unspent(info)`, and a possibly more-accurate value that another extension in the same transaction-extension pipeline (e.g. the storage-proof-size reclaim extension) may have written into `ExtrinsicWeightReclaimed` earlier in the *same* extrinsic's post-dispatch chain. The unit tests in this file demonstrate the exact mechanics: [1](#0-0) 

Here `ExtrinsicWeightReclaimed` is seeded with `accurate_refund` before `post_dispatch_details` runs, and after the call the storage item still holds `accurate_refund` — i.e. the value is *not* cleared by `reclaim_weight`, it is written back via `put()`: [2](#0-1) 

The "less precise" test confirms the `.max()` combination logic explicitly (the smaller seeded value is discarded in favor of the larger `calc_unspent` result), which is the direct evidence for the `already_reclaimed.max(unspent)` formula described in the question.

Both `CheckWeight` and `WeightReclaim`'s `prepare`/`do_prepare` functions (executed at the *start* of every extrinsic, before dispatch) only touch `BlockSize`/`BlockWeight` — neither resets `ExtrinsicWeightReclaimed`: [3](#0-2) [4](#0-3) 

Because `ExtrinsicWeightReclaimed` is a plain `StorageValue` (not keyed by extrinsic index) and no reset call was found in the `validate`/`prepare` paths of either extension, the value written by extrinsic *N*'s post-dispatch (`ExtrinsicWeightReclaimed::put(accurate_reclaim_N)`) remains in storage when extrinsic *N+1* runs its own `reclaim_weight`. In `reclaim_weight`, `already_reclaimed` is read as this stale value and combined via `.max()` with the current extrinsic's own `unspent`. If `accurate_reclaim_N > unspent_{N+1}`, `BlockWeight` is reduced by the larger, unrelated, stale amount instead of the true `unspent_{N+1}`, systematically under-accounting the true weight consumed by extrinsic *N+1*.

Note: I could not directly inspect `frame_system::Pallet::reclaim_weight`'s full body or `note_extrinsic` in `substrate/frame/system/src/lib.rs` within the available tool budget, so I cannot 100% rule out an explicit reset elsewhere in the per-extrinsic initialization path. However, none of the code paths that run at the start of each extrinsic (`CheckWeight::do_prepare`, `WeightReclaim::prepare`, and their `validate` counterparts) reset the value, and the test suite in this file never exercises or asserts a reset between two sequential extrinsics — it only exercises single-extrinsic seeding-then-reclaim scenarios. This is a meaningful test gap consistent with the described exploit.

### Impact Explanation
An attacker crafting a sequence of extrinsics in one block can make an early extrinsic report a large legitimate `unspent`/`actual_weight` gap (large `already_reclaimed` gets stored), then follow it with extrinsics whose own true `unspent` is smaller. The later extrinsics' post-dispatch reclaim will use the inflated stale credit, subtracting more weight from `BlockWeight` than was truly saved. This lets a block accept more actual computational work than the weight limit should allow — an underpriced execution / block weight limit bypass, directly matching the scoped impact.

### Likelihood Explanation
No privileged access is required — any signed account (or account routed through proxy/multisig/XCM Transact) submitting an ordinary sequence of extrinsics in a block can trigger this, since it only depends on ordering and on the natural variance of `actual_weight` reported by different pallets/calls. It is fully reproducible and deterministic given a controlled extrinsic sequence and requires no race condition, making it a fairly high-likelihood accounting bug if the reset is indeed missing.

### Recommendation
Explicitly reset (`kill()`) `ExtrinsicWeightReclaimed` at the very start of each extrinsic's processing (e.g. in `CheckWeight::do_prepare`/`WeightReclaim::prepare`, or in `note_extrinsic`) before any `unspent`/`already_reclaimed` value for that extrinsic is computed, so that no state from a previous extrinsic can influence the current one's reclaim calculation.

### Proof of Concept
Rust integration test in `substrate/frame/system/src/extensions/weight_reclaim.rs` (or `check_weight.rs`) test module:
1. Extrinsic A: `info.call_weight = 512`, `post_info.actual_weight = Some(10)` (large legitimate unspent = 502). Call `post_dispatch_details` for A; assert `ExtrinsicWeightReclaimed::<Test>::get() == 502`.
2. Without resetting `ExtrinsicWeightReclaimed`, run extrinsic B with `info.call_weight = 100`, `post_info.actual_weight = Some(90)` (true unspent = 10). Call `post_dispatch_details` for B.
3. Assert `BlockWeight::<Test>::get()` reflects a reduction of only `10` (B's true unspent), not `502` (A's stale value).
4. Currently, due to `already_reclaimed.max(unspent)` reading the un-reset `ExtrinsicWeightReclaimed`, the test would show `BlockWeight` reduced by `502` instead of `10`, proving the over-reclaim; the fix should make this assertion pass with the correct `10` reduction and cumulative `BlockWeight` equal to sum of true weights of A and B.
