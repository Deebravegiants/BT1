### Title
Gas-griefing via unbounded return data from attacker-controlled cross-chain beneficiary in `WrappedHyperFungibleToken.onAccept` / `onPostRequestTimeout` - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.onAccept` and `onPostRequestTimeout` (and their upgradeable twin `WrappedHyperFungibleTokenUpgradeable.sol`) execute a low-level, attacker-influenced call `beneficiary.call{value: message.amount}("")` where `beneficiary`/`refundee` is decoded directly from the cross-chain message body without any restriction that the target be a "safe" address. This mirrors the audited Hubble finding: a user-controlled recipient contract can consume the caller's gas by returning an arbitrarily large amount of data on the low-level `.call`, since Solidity's ABI decoding of the `(bool, bytes memory)` tuple copies the returned bytes into memory regardless of whether the caller uses the bytes value.

### Finding Description
In `onAccept`:
```solidity
IWETH(_underlying).withdraw(message.amount);
(bool sent,) = beneficiary.call{value: message.amount}("");
if (!sent) {
    IWETH(_underlying).deposit{value: message.amount}();
    IERC20(_underlying).safeTransfer(beneficiary, message.amount);
}
``` [1](#0-0) 

`beneficiary` is derived from `message.to`, a field fully controlled by the sender of the cross-chain transfer on the source chain:
```solidity
HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
address beneficiary = _toAddr(message.to);
``` [2](#0-1) 

The same pattern occurs in `onPostRequestTimeout` for `refundee`:
```solidity
IWETH(_underlying).withdraw(message.amount);
(bool sent,) = refundee.call{value: message.amount}("");
``` [3](#0-2) 

Because `beneficiary`/`refundee` is an address the attacker deploys their own contract at (any EVM contract can be placed there since the message-sender fully controls the `to`/`from` field of the ISMP message they dispatch), the attacker can make that contract's `receive()`/`fallback()` return an unbounded blob of data (e.g., via `assembly { return(0, N) }` for large `N`) whenever it receives the native-token push. `onAccept`/`onPostRequestTimeout` are executed by `EvmHost` when a relayer submits a valid proof for the incoming POST request or timeout — i.e., this code path is triggered by an unprivileged relayer processing a message that the attacker (an unprivileged sender) fully controls the content of. The relayer, not the attacker, pays for the memory expansion cost of copying the returned bytes into memory, exactly as in the referenced Hubble `VUSD.processWithdrawals` report where `withdrawal.usr` (attacker-controlled) can bloat `data` returned from `.call`.

The upgradeable version has the identical vulnerable pattern:
```solidity
IWETH(_underlying).withdraw(message.amount);
(bool sent,) = beneficiary.call{value: message.amount}("");
``` [4](#0-3) 

### Impact Explanation
Unlike the original report where the unbounded data was additionally emitted in an event, this instance still causes the caller (the relayer executing `onAccept`/`onPostRequestTimeout` via `EvmHost`) to pay quadratic gas costs for memory expansion proportional to attacker-chosen return-data size, entirely at the attacker's discretion, for every WETH-style token bridged with a malicious beneficiary address. If the returned data is large enough, it can push the relayer's execution over available gas within a batched `handlePostRequests`/`handleGetResponses` call, causing that message (and potentially the surrounding batch of requests/proofs) to fail to be delivered, or forcing relayers to burn disproportionately high gas to service a single malicious transfer. This is a griefing/DoS vector against relayers with no attacker cost beyond deploying a trivial contract and initiating a transfer of arbitrary (even tiny) amount.

### Likelihood Explanation
High likelihood: any unprivileged user can call `send()` on the source-chain `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` with `to` set to a malicious contract they control on the destination chain, and can similarly force a timeout by never fulfilling the message. No privileged role or governance action is required — only a normal cross-chain transfer dispatch that is later delivered (or times out) by any relayer.

### Recommendation
Avoid capturing/propagating unbounded return data from low-level calls to attacker-controlled addresses. Either:
- Use a fixed, minimal gas stipend and hard-cap the returndata size read (e.g., via `excessivelySafeCall`/assembly with `returndatacopy` limited to 0 bytes), or
- Do not perform a native-ETH push to an arbitrary attacker-controlled `beneficiary`/`refundee` at all — always deliver via the safer `IERC20.safeTransfer` path for WETH-style tokens, removing the raw `.call{value: ...}("")` branch, or
- Wrap the low-level call in a bounded-gas execution and explicitly discard/ignore all return data using inline assembly so no memory copy of arbitrary-length data occurs.

### Proof of Concept
1. Attacker deploys `EvilReceiver` on the destination chain with:
```solidity
receive() external payable {
    assembly { return(0, 1000000) }
}
```
2. Attacker calls `send()` on the source-chain wrapped token contract with `to = address(EvilReceiver)` and a small `amount`.
3. A relayer submits the proof and `EvmHost` invokes `WrappedHyperFungibleToken.onAccept`, which executes `beneficiary.call{value: message.amount}("")`.
4. `EvilReceiver.receive()` returns 1,000,000 bytes; Solidity's ABI decoding of the call's `(bool, bytes memory)` result copies this into memory, charging the relayer's transaction quadratic memory-expansion gas, disproportionate to the tiny amount transferred, and can cause out-of-gas failures for batched message delivery.     function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
