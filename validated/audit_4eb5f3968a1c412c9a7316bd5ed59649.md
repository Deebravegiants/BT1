## #Vulnerability found

### Title
Division-by-zero panic in `calc_take_pnl`/`calc_x_power` permanently freezes deposits and withdrawals when a pool side reaches zero balance - (File: `program/src/processor.rs`, `program/src/math.rs`)

### Summary
`Calculator::calc_x_power` and the surrounding logic in `Processor::calc_take_pnl` perform unchecked (`.unwrap()`) divisions by the current pool balances `x1`/`y1`. These values are derived directly from the AMM vault balances minus the not-yet-withdrawn PnL (`total_pc_without_take_pnl` / `total_coin_without_take_pnl`), which are attacker-influenceable through ordinary swap, deposit and withdraw traffic. If either side reaches exactly zero while the pool still has outstanding LP supply, every subsequent `Deposit`, `Withdraw`, or `WithdrawPnl` instruction that touches this pool will panic instead of returning a graceful error, permanently freezing LPs' ability to withdraw their funds from that pool.

### Finding Description
`calc_take_pnl` is invoked from three unprivileged-reachable instruction handlers — `process_deposit` [1](#0-0) , `process_withdraw` [2](#0-1) , and `process_withdrawpnl` [3](#0-2)  — each of which computes `x1`/`y1` by normalizing `total_pc_without_take_pnl`/`total_coin_without_take_pnl`, themselves derived from live vault balances minus `need_take_pnl_pc`/`need_take_pnl_coin`: [4](#0-3) 

Inside `calc_take_pnl`, these `x1`/`y1` values are passed as `current_x`/`current_y` into `Calculator::calc_x_power`, and the resulting `x2` is then divided by `x1` with no zero-check: [5](#0-4) 

`calc_x_power` itself divides by `current_y` unconditionally: [6](#0-5) 

If `x1` (or `current_y`) is `0`, `checked_div` returns `None` and `.unwrap()` panics, aborting the transaction. Because the on-chain state (vault balances, `need_take_pnl_pc/coin`, `calc_pnl_x/y`) that produced the zero condition is not altered by a failed/panicking transaction, this is not a one-off failure — it is a deterministic, persistent condition: every future `Deposit`/`Withdraw`/`WithdrawPnl` call against the pool will recompute the same zero `x1`/`y1` and panic again, effectively bricking the pool for LP withdrawals.

Reaching `total_pc_without_take_pnl == 0` (or the coin side) does not require any privileged action. `need_take_pnl_pc`/`need_take_pnl_coin` are incremented by ordinary `calc_take_pnl` calls that fire on every deposit/withdraw as pool price drifts from the last recorded `target_orders.calc_pnl_x/y` due to swap activity [7](#0-6) , while the raw vault balance is driven down by ordinary swaps. An attacker who fully controls the sequence and sizes of swaps and deposit/withdraw calls in a single crafted transaction (or a short deterministic sequence) can engineer `pc_vault.amount - need_take_pnl_pc == 0` (or the analogous coin-side condition) exactly, since all the arithmetic involved is deterministic given the attacker's chosen `amount_in`/`amount_out`/`deposit`/`withdraw` parameters.

This mirrors the referenced audit finding's core bug class ("multiple divisions by zero... system may become temporarily or fully blocked") but manifests here through unprivileged instruction flow (swap→deposit/withdraw) rather than a privileged `cage`/`mold` call.

### Impact Explanation
Once triggered, the pool permanently loses the ability to process `Deposit`, `Withdraw`, and `WithdrawPnl` instructions — every call panics deterministically given the frozen on-chain state. Since `Withdraw` is the only way for LPs to redeem their LP tokens for underlying coin/pc, this permanently freezes LP funds in the pool (funds remain in the vaults but become permanently inaccessible through the AMM program). This satisfies "permanent freezing of user or LP funds."

### Likelihood Explanation
Exploitation requires an attacker to precisely drive `total_pc_without_take_pnl` or `total_coin_without_take_pnl` to exactly `0` via a specific, deterministic sequence of swap/deposit/withdraw amounts, which is feasible for a sophisticated attacker who can simulate the exact on-chain arithmetic off-chain (all inputs — vault balances, fee parameters, `calc_pnl_x/y` — are readable on-chain) and then submit a crafted transaction sequence. It requires no privileged signer and no non-default configuration, but it does require careful computation, making it a High-difficulty but realistically achievable griefing/freezing attack.

### Recommendation
- Replace `.unwrap()` on the divisions in `Calculator::calc_x_power` (`program/src/math.rs:57`) and in `calc_take_pnl`'s `y2` computation (`program/src/processor.rs:208`) with checked operations that return `AmmError::CheckedDivOverflow` (or a dedicated error) instead of panicking.
- Add explicit guards in `calc_take_pnl` to short-circuit (return `Ok` with zero deltas, or a clear error) when `x1 == 0` or `y1 == 0`, mirroring the existing `pc_pnl_amount != 0 && coin_pnl_amount != 0` guard already present later in the function.
- Consider bounding `need_take_pnl_pc`/`need_take_pnl_coin` growth relative to live vault balances so `total_*_without_take_pnl` cannot reach exactly zero while LP supply remains outstanding.

### Proof of Concept
Conceptual reproduction path (values are illustrative; exact amounts must be computed against the pool's live state to hit `0` precisely):
1. Attacker observes pool state: `pc_vault.amount`, `coin_vault.amount`, `need_take_pnl_pc`, `target_orders.calc_pnl_x/y`, fee parameters.
2. Attacker issues a sequence of `SwapBaseIn`/`SwapBaseOut` instructions that move the pool price away from `calc_pnl_x/y` and drain `pc_vault.amount` down toward a small value `k`, respecting the per-swap invariant `swap_amount_out < total_pc_without_take_pnl` (each swap only guarantees the local `total_*_without_take_pnl` stays `>= 1` at that call, not across calls after `need_take_pnl_pc` is later increased).
3. Attacker then issues a `Deposit` or `Withdraw` instruction; inside `calc_take_pnl`, the computed `pc_pnl_amount` is engineered (via the price divergence created in step 2) to equal exactly `k`, so `total_pc_without_take_pnl = k - k = 0` is committed transiently in that call — but this doesn't itself panic (it's a subtraction, and later `pc_amount==0` returns a graceful `InvalidInput` error, reverting state).
4. Because reverted transactions don't persist state, the attacker must instead directly cause `pc_vault.amount - need_take_pnl_pc == 0` to hold at the *start* of a call (i.e., persist state across transactions): after a prior successful `Deposit`/`Withdraw`/`WithdrawPnl` transaction commits an increment to `need_take_pnl_pc` that makes it equal to the *current* `pc_vault.amount`, the *next* transaction's initial `x1 = normalize_decimal_v2(total_pc_without_take_pnl=0, ...)` is `0`. Calling `calc_take_pnl` with `x1=0` then panics at `program/src/processor.rs:208` (`checked_div(x1).unwrap()`), aborting every subsequent `Deposit`/`Withdraw`/`WithdrawPnl` on this pool.

A Devin agent with repo access could add a Rust unit test analogous to `test_calc_take_pnl` in `program/src/processor.rs` (lines 3057-3088) that calls `Processor::calc_take_pnl` with `total_pc_without_take_pnl = 0` (or `total_coin_without_take_pnl = 0`) to directly demonstrate the panic.

```rust
    pub fn calc_x_power(last_x: U256, last_y: U256, current_x: U256, current_y: U256) -> U256 {
        // must be use u256, because u128 may be overflow
        let x_power = last_x
            .checked_mul(last_y)
            .unwrap()
            .checked_mul(current_x)
            .unwrap()
            .checked_div(current_y)
            .unwrap();
        x_power
    }
```

```rust
    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
```
