### Title
Webhook shop/topic/webhook-id headers are not covered by the HMAC signature, allowing cross-tenant impersonation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0)  which is the only data the HMAC in `Utils::HmacValidator.validate` verifies [2](#0-1) . However, `Registry.process` extracts `topic`, `shop`, `webhook_id`, and `api_version` straight from unauthenticated HTTP headers and hands them, unverified, to the app's `WebhookHandler` as trusted tenant-identifying metadata [3](#0-2) .

### Finding Description
`ShopifyAPI::Webhooks::Request#shop`, `#topic`, and `#webhook_id` are all read from the `shopify-*`/`x-shopify-*` headers [4](#0-3) . None of these fields are part of `to_signable_string`, which is the exact byte string fed into `OpenSSL::HMAC.hexdigest` for verification [5](#0-4) . `Registry.process` calls `Utils::HmacValidator.validate(request)` — which only checks the body's HMAC — and then constructs `WebhookMetadata` directly from `request.shop`, `request.topic`, and `request.webhook_id` [6](#0-5) . The `WebhookMetadata` struct is documented as the app's source of truth for "The shop domain of the webhook" [7](#0-6) , and the official usage doc explicitly tells implementers to key application logic (e.g. `shop_domain: data.shop`) off this unauthenticated field [8](#0-7) .

This breaks the intended identity binding:
`shop header value == shop that the HMAC-authenticated body actually originated from`

Because every shop installed on a given app shares the same `client_secret`/`api_secret_key` (the HMAC key is per-app, not per-shop), any merchant who has legitimately installed the app can capture a genuine, validly-signed webhook delivered to their own store, then replay that exact body (whose HMAC remains valid) to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or topic/webhook-id) header to name a different, victim shop. `HmacValidator.validate` still passes because it only checks the body bytes, and the handler receives `WebhookMetadata` claiming the victim's shop domain.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker-controlled, HMAC-valid payload can be attributed to an arbitrary victim shop domain that the app has never actually sent that payload from. Any app that uses `data.shop` to select which merchant's database record, install, or session to act on (the pattern the gem's own documentation recommends) can be tricked into writing/queuing attacker-supplied webhook data under a different tenant's identity, or into processing spoofed lifecycle events (e.g. mandatory `shop/redact`, `customers/redact`) for a shop the attacker doesn't own. This matches the Critical "cross-tenant access" category, since the gem's own verification primitive is the thing failing to bind the field the interface documents as authoritative.

### Likelihood Explanation
Likelihood is high for any app that installs the gem's stock `ShopifyAPI::Webhooks::Registry.process` flow exactly as documented in `docs/usage/webhooks.md`. The prerequisite is only that the attacker be a legitimate (even free/trial) merchant of the target app — no secret material, TLS interception, or privileged access is required, and the exploit is a direct HTTP replay with one header changed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC verification (or otherwise cryptographically bind them, e.g. verify `shop` against the value returned by Shopify's separate webhook subscription confirmation, or require correlating the delivered `webhook_id`/`shop` pair against the app's own registration/session store) before constructing `WebhookMetadata` and invoking the handler. At minimum, document prominently that `data.shop`/`data.topic`/`data.webhook_id` are unauthenticated and must not be used to select tenant-scoped resources without additional server-side verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with a valid `X-Shopify-Hmac-Sha256` header computed over the raw body using the app's shared `api_secret_key`.
2. Attacker resends the identical raw body and `X-Shopify-Hmac-Sha256` header to the same webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally a fresh `X-Shopify-Webhook-Id`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present) [9](#0-8) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only and succeeds because the body/HMAC pair is genuinely valid [10](#0-9) .
5. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, and the app (following the documented pattern) records/queues the attacker's payload as if it originated from `victim.myshopify.com` [11](#0-10) .
