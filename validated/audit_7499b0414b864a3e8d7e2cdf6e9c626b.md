### Title
Webhook shop/topic attribution is not covered by the HMAC signature, enabling cross-tenant webhook forgery via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the HMAC only over the raw request body, while the `shop`, `topic`, and `webhook_id` values used by `ShopifyAPI::Webhooks::Registry.process` to route and attribute the webhook are taken from unsigned HTTP headers. This breaks the binding `HMAC-verified bytes == bytes acted upon`: the signature proves the body came from Shopify (using the app's secret), but it proves nothing about which shop or topic the body should be attributed to.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop`/`#topic`/`#webhook_id` are read directly from HTTP headers without any cryptographic binding to the body or to each other [2](#0-1) . `HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` [3](#0-2) , so it validates the body bytes but never the `shop-domain`, `topic`, or `webhook-id` headers.

`Registry.process` then trusts these unsigned headers directly to select the handler and construct the metadata passed to app code: [4](#0-3) 

The identity binding that should hold is:
`HMAC_valid(body) ⇒ (shop, topic, webhook_id) are authentic`

but the actual code only guarantees:
`HMAC_valid(body) ⇒ body is authentic`, while `(shop, topic, webhook_id)` are taken verbatim from attacker-controllable headers on any POST reaching the webhook endpoint.

Because the webhook HTTP endpoint is a public route on the host application, anyone can send a POST request to it directly (this is not a MITM or credential-theft scenario — it only requires reaching the app's public webhook URL, which is how Shopify itself delivers webhooks). An unprivileged user who legitimately owns/installs the app on their own store (a normal merchant, not a privileged operator) can trigger any webhook event in their own shop (e.g. `app/uninstalled`, `customers/redact`, `shop/update`) and receive from Shopify a valid `(raw_body, hmac)` pair signed with the app's real secret. Since the signature covers only the body and not the shop/topic headers, this same valid `(body, hmac)` pair can be replayed to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` and/or `x-shopify-topic` header value pointing at a different (victim) shop. `Registry.process` will pass HMAC validation (the body signature is genuinely valid) and will hand the handler a `WebhookMetadata` claiming the event came from the victim shop/topic [5](#0-4) .

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who only controls their own shop's webhook events can cause the app to process a forged event attributed to another merchant's shop. Depending on the handler logic (which is entirely driven by `data.shop` per the documented contract in `docs/usage/webhooks.md`), this can be used to desynchronize or corrupt another tenant's app state — e.g. forging an `app/uninstalled` event for a victim shop to make the app locally purge/deactivate that victim's stored session/access token, or forging GDPR-style redact events against a victim shop's records. This crosses a tenant boundary using only the attacker's own legitimately-issued webhook credentials, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is limited by the fact that the attacker must operate/own a shop that has the app installed to obtain a validly-signed `(body, hmac)` pair for at least one webhook topic, and must be able to directly POST to the app's public webhook endpoint with custom headers (bypassing normal delivery from Shopify's IPs, which is possible since the gem performs no header/IP-based delivery-source check — only the HMAC-over-body check). No secret, access token, or privileged account is required beyond normal app installation, which is available to any merchant. The severity of the achievable forgery is bounded by what body content the attacker's own shop's webhook naturally produces for a given topic.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, and ideally `webhook_id`/`api_version`) in the signed material verified by `HmacValidator`, or independently verify that the `shop-domain` header matches the shop context expected for the registered handler/session before acting on the webhook. At minimum, `Request#to_signable_string` should not be the sole basis for trusting `Request#shop`/`#topic`; the `shop` used for downstream authorization decisions should be cross-checked against an authenticated session/store record rather than trusted from a header that sits outside the HMAC's coverage.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers/receives (or otherwise triggers) a webhook for a sensitive topic (e.g. `app/uninstalled`).
2. Shopify delivers a POST to the app's webhook endpoint with headers `x-shopify-topic: app/uninstalled`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`, `x-shopify-shop-domain: attacker.myshopify.com`, and a JSON body.
3. Attacker captures the raw body and the valid HMAC value (both plaintext, no secret required to reuse them).
4. Attacker sends a new POST directly to the same public webhook endpoint, reusing the identical raw body and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` passes because it only checks the body bytes [6](#0-5) .
6. `Registry.process` invokes the registered handler with `shop: "victim.myshopify.com"` and `topic: "app/uninstalled"`, even though the event never originated from the victim's shop [7](#0-6) .

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
