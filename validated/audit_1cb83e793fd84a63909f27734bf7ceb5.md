### Title
Non-standard ERC20 transfer semantics break WrappedHyperFungibleToken escrow accounting, enabling drain/insolvency of locked funds - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken.send()` trusts the caller-supplied `params.amount` as the amount actually locked in the contract, instead of measuring the real balance delta like the sibling `IntentGatewayV2` contract does for the same class of tokens.

### Finding Description
In `send()`, the contract does: [1](#0-0) 

`IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` is called, but the actual number of tokens the contract received is never measured. `_buildDispatchPost(params)` then embeds the unmodified `params.amount` as `message.amount` in the cross-chain `Message`: [2](#0-1) 

On the destination chain, `onAccept()` unconditionally releases `message.amount` of the underlying token from the contract's own custody pool to the beneficiary: [3](#0-2) 

If `_underlying` is any token with non-1:1 transfer semantics (deflationary/fee-on-transfer, rebasing, or a token with an accounting bug such as the GPU token's self-transfer amplification), the amount actually escrowed on the source chain differs from `message.amount` promised to the destination chain. Because a single `WrappedHyperFungibleToken` deployment maintains one shared custody pool for the underlying token across *all* users, this creates a systemic accounting mismatch: every `send()` call either under-collateralizes (fee-on-transfer/deflationary token — the contract locks less than what it promises to release on the destination) or over/under-mints backing depending on the token's quirk.

This is directly analogous to the reported bug class: code that assumes a token's transferred amount equals the amount actually credited/held, without verifying via balance snapshots. The codebase itself demonstrates awareness of this exact risk — `IntentGatewayV2.placeOrder()` explicitly snapshots `balanceOf` before and after every ERC20 transfer and mutates `order.inputs[i].amount` to the actually-received amount: [4](#0-3) 

`WrappedHyperFungibleToken.send()` (and its upgradeable twin `WrappedHyperFungibleTokenUpgradeable.sol`) omits this same balance-diff check, showing the fix pattern already exists elsewhere in the codebase but was not applied here.

### Impact Explanation
Each cross-chain send with a non-standard underlying token compounds a mismatch between what is actually escrowed on the source chain and what has been promised/released on the destination chain's custody pool. Over repeated transfers this either:
- Drains the shared custody pool faster than it is replenished, causing later legitimate `onAccept()` calls (or timeout refunds) to revert due to insufficient balance — permanent freezing of other users' funds, or
- Allows a party who repeatedly bridges the non-standard token to extract more value from the destination pool than they actually locked, at the expense of other users sharing that pool — theft of escrowed funds.

Both outcomes are consistent with "concrete theft or permanent freezing of funds" for a token-bridging function reachable by any unprivileged user via `send()`.

### Likelihood Explanation
The condition depends on the specific ERC20 token wired as `_underlying` for a given `WrappedHyperFungibleToken` deployment (configured once via `configure()`), and it is not user-selectable per transaction — any user who bridges an already-deployed instance backed by a fee-on-transfer, deflationary, rebasing, or otherwise non-standard token would trigger the mismatch automatically, without needing to craft anything adversarial. Deflationary and fee-on-transfer tokens are common on BNB Chain and other EVM chains the SDK explicitly targets, so this is a realistic deployment/token-choice scenario rather than a purely theoretical one.

### Recommendation
Mirror the `IntentGatewayV2` pattern in `WrappedHyperFungibleToken.send()` (and the upgradeable variant): snapshot `IERC20(_underlying).balanceOf(address(this))` before and after `safeTransferFrom`, and use the measured delta — not `params.amount` — both for the amount actually escrowed and for the `message.amount` encoded into the dispatched cross-chain message, so that the destination chain never promises to release more (or less) than what was truly locked.

### Proof of Concept
Not independently executable from the available index (no on-chain reproduction was run); the flaw is demonstrated by code inspection contrasting `WrappedHyperFungibleToken.send()` (no balance-diff check) against `IntentGatewayV2.placeOrder()`'s already-tested fee-on-transfer handling (`evm/tests/foundry/IntentGatewayV2SameChainTest.sol` lines 2440-2686), which shows the codebase's own test suite validates the *absence* of this exact class of bug in `IntentGatewayV2` but no equivalent test exists for `WrappedHyperFungibleToken.send()`.

            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
