## Confirmed vulnerability: webhook shop-domain header is not covered by the HMAC signature

### Title
Webhook shop-domain spoofing via HMAC that only signs the raw body — cross-tenant webhook attribution bypass (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header — which is **not part of the signed material** — to determine which tenant (`shop`) the event belongs to. This breaks the intended binding "the shop the HMAC authenticates" == "the shop the host application stores/acts on," because the HMAC only ever authenticates `@raw_body` while `shop` is read straight from an unauthenticated header.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header, completely outside the signable string: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` (which calls `request.to_signable_string`, i.e. only the body) and then immediately hands `request.shop` to the caller's handler as the trusted tenant identifier, with no cross-check that the header's shop matches anything cryptographically bound to the body: [3](#0-2) 

`HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to `verifiable_query.hmac` — it never touches `shop`: [4](#0-3) 

The equality that should hold is:
`shop asserted by the HMAC-covered payload == shop the host application attributes the webhook event to`

Instead what holds is:
`shop stated in an unauthenticated header == shop the host application attributes the webhook event to`, while `HMAC == f(raw_body only)`.

**Exploitation path (no privileged credentials required):** An unprivileged internet user who has any means of triggering a legitimately-signed webhook delivery for a body they control (e.g., they install the same public app on their own low-privilege/free development store, or otherwise obtain one valid `(raw_body, hmac)` pair for a webhook whose body content doesn't itself encode the shop, e.g. `shop/redact`, `app/uninstalled`, or any topic whose JSON body doesn't strictly bind the originating shop) can replay that exact `raw_body` + `hmac-sha256` value to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value for a different, victim shop. `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` pointing at the attacker-chosen victim shop.

### Impact Explanation
This is a cross-tenant identity-binding break: an attacker who is not authorized for the victim shop can make the gem attest that a webhook event (with attacker-controlled or replayed body content) originated from that victim shop. Any host application that uses `WebhookMetadata#shop` to select which tenant's records to mutate (e.g. GDPR redaction handlers, uninstall/deauthorization cleanup, order/customer sync) will act on the wrong tenant's data based on a value this gem presents as verified but is not. This satisfies the "Manipulation ... resulting in cross-tenant access" class of impact defined by the assessment criteria — the gem's own `process` method is the point of failure, not host-app misuse of undocumented behavior, because `process` explicitly asserts validity ("Invalid webhook HMAC.") while not validating the one field (`shop`) the handler relies on for tenant scoping.

### Likelihood Explanation
Moderate-to-high. The precondition (obtaining at least one valid `raw_body`/`hmac` pair) is trivially satisfiable by any user who can install the app on any shop they control (even a free development store) and capture one webhook delivery, or by using a topic whose body is static/predictable across shops (e.g., `shop/redact`, `app/uninstalled`, mandatory compliance topics) so the same signed payload is reusable verbatim. No access token, `client_secret`, or elevated privilege is needed — only network access to the app's public webhook endpoint and a header value that the app itself never validates.

### Recommendation
Bind `shop` (and ideally `topic`, `api_version`, `webhook_id`) into the HMAC-verified material, or otherwise cryptographically tie the header-derived shop to the signed body — e.g., include the shop domain in `to_signable_string`, or require the host application to independently confirm the destination shop against a value derived from an authenticated source (such as a per-shop webhook signing check or a lookup keyed by an already-authenticated session/access-token record) before trusting `WebhookMetadata#shop`. At minimum, document prominently that `request.shop` is unauthenticated and must not be used as the sole tenant-scoping key without additional verification.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own (attacker-controlled) shop "attacker.myshopify.com"
#    and receives one legitimate webhook, e.g. topic "app/uninstalled":
raw_body = '{"some":"static-or-attacker-controlled-json"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), real_api_secret_key, raw_body)
valid_hmac_b64 = Base64.encode64(hmac)   # this is a genuinely valid signature for raw_body

# 2. Attacker replays the exact same raw_body/hmac but swaps the shop-domain header
#    to point at a victim shop the attacker does NOT control:
headers = {
  "shopify-topic" => "app/uninstalled",
  "shopify-hmac-sha256" => valid_hmac_b64,
  "shopify-shop-domain" => "victim-shop.myshopify.com",   # <-- forged, unauthenticated
  "shopify-webhook-id" => "attacker-chosen-id",
  "shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# 3. Registry.process only checks the body HMAC, which still validates,
#    then dispatches the handler believing the event is authentically from victim-shop:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(topic: "app/uninstalled",
#                                              shop: "victim-shop.myshopify.com", ...))
```
`Utils::HmacValidator.validate(request)` returns `true` because it only recomputes the HMAC over `raw_body`; `request.shop` is taken verbatim from the forged header, as shown in [2](#0-1)  and [3](#0-2) .
