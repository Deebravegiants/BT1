### Title
Webhook `shop` (and `topic`) identity fields are not covered by the HMAC signature, allowing cross-tenant spoofing of verified webhook requests - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before dispatching webhook data to the app's handler, but the HMAC it validates only covers the raw request body. The `shop` (and `topic`) values used to identify the tenant are taken from unauthenticated HTTP headers and are never bound into the signed material, so they can be swapped independently of the verified body.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors instead read directly from caller-supplied headers with no relation to the signed body: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC strictly over `verifiable_query.to_signable_string`, i.e. the body only: [3](#0-2) 

`Registry.process` raises `InvalidWebhookError` only if the HMAC over the body fails, and otherwise immediately forwards `request.shop` (an unauthenticated header) to the app's handler as the tenant identity for the event, with no additional check binding `shop` to the verified body: [4](#0-3) 

The gem's own documentation asserts this call "will verify the request did indeed come from Shopify," which is inaccurate: it verifies only that the *body bytes* were signed with the app secret at some point — not that the accompanying `shop`/`topic` headers on *this* request are the ones originally signed: [5](#0-4) 

This is a direct instance of "a field acted on but not covered by the HMAC": `request.shop` is the field consumed by `WebhookMetadata` and handed to the merchant's handler as the tenant-scoping identity, yet it is excluded from the signed bytes that `HmacValidator` checks.

### Impact Explanation
Any unprivileged internet user who operates their own Shopify store with the target app installed can capture a legitimate `(raw_body, hmac)` pair produced by Shopify for one of their own real webhook deliveries (e.g., by running a public endpoint or a proxy/logger in front of their own webhook URL). Because the shop-domain header is not part of the signed payload, that same valid `(body, hmac)` pair can be resent with an arbitrary `x-shopify-shop-domain` header value (e.g., a victim tenant's domain) to the app's webhook endpoint. `Registry.process` will validate the HMAC successfully (it never inspects `shop`) and hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop while carrying attacker-controlled body content. If the host application trusts `WebhookMetadata#shop` for tenant scoping (as the library's own documentation implies is safe once `process` succeeds), this results in cross-tenant data injection/misattribution — writing or triggering actions against another merchant's tenant record using attacker-controlled payload data.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple merchant shops (any public Shopify app): the attacker only needs their own (or a trial) shop installation to legitimately receive one signed webhook, then replay it with a forged `shop` header — no access to `api_secret_key`, access tokens, or any other credential is required, and no host-application misuse beyond following the library's documented `Registry.process` contract is needed.

### Recommendation
Bind the tenant/topic identity into the verified material before trusting it: include `shop`, `topic`, and `webhook_id` in the signable string checked by `HmacValidator`, or otherwise cross-validate the header-derived `shop`/`topic` against out-of-band trusted state (e.g., the merchant record that actually has this app installed, or Shopify's documented "cross-check webhook shop against known installed shops" guidance) inside `Registry.process` before constructing `WebhookMetadata`. At minimum, update `docs/usage/webhooks.md` to stop asserting the header-derived identity is verified.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and stands up a reverse proxy in front of their webhook endpoint (or simply captures traffic they control).
2. Shopify delivers a real webhook: `POST /webhook` with `x-shopify-hmac-sha256: <valid HMAC of body B>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, body `B`.
3. Attacker resends the identical `body: B` and `x-shopify-hmac-sha256` header, but swaps `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` (lib/shopify_api/webhooks/registry.rb:189-199) calls `Utils::HmacValidator.validate`, which passes because it only checks `body` against the HMAC (lib/shopify_api/utils/hmac_validator.rb:12-31; lib/shopify_api/webhooks/request.rb:35-38).
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)`, and any host logic that trusts this `shop` value for tenant scoping now processes attacker data under the victim tenant's identity.
