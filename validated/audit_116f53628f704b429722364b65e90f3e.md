### Title
Webhook HMAC only signs the raw body, allowing the `shop`/`topic` headers to be swapped for cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body alone, while the `shop`, `topic`, `webhook_id`, and `api_version` values used downstream come from HTTP headers that are never part of the signed material. `Registry.process` trusts these unsigned headers to route and label the webhook payload, breaking the intended binding between "bytes verified" and "shop acted on."

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by computing `OpenSSL::HMAC` over `to_signable_string` and comparing it to the `hmac` field using `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers and are not covered by this signable string at all: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then unconditionally trusts `request.shop` and `request.topic` (unsigned) to dispatch the handler and build `WebhookMetadata`: [3](#0-2) 

This is the exact bug class from the report generalized: `getTotalBoostedForVault[vault]` was updated using `feiDebt` (a value not actually corresponding to what was withdrawn/verified), causing the *thing acted upon* to diverge from the *thing that was checked*. Here, the checked/verified quantity is `raw_body` (HMAC-covered), but the thing acted upon — the `shop` identity used to attribute and process the payload — is taken from a header that is completely outside the verified bytes. The binding that should hold is:

`shop_used_for_dispatch == shop_that_actually_produced(and-was-authorized-to-produce)_the_HMAC-verified_body`

but the code only enforces `HMAC(raw_body) == received_hmac`; it never ties `shop-domain` (or `topic`) to that verified body.

### Impact Explanation
An attacker who controls their own Shopify store with the vulnerable app installed will legitimately receive genuine, correctly-signed webhook deliveries (valid `raw_body` + valid `x-shopify-hmac-sha256`, since Shopify itself signs them with the app's `client_secret`). Because the signature covers only the body, the attacker can replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header with a victim shop's domain. `HmacValidator.validate` still succeeds (body unchanged), and `Registry.process` will invoke the handler with `WebhookMetadata.new(shop: <victim shop>, body: <attacker-controlled/attacker-shop body>, ...)`. Any host application that uses `WebhookMetadata#shop` to select the tenant record to update (the officially documented pattern shown in this gem's own webhook usage) will write or act on the attacker's payload under the victim's tenant — a cross-tenant data/processing confusion crossing an authentication/tenant boundary, consistent with the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any unprivileged internet user can install the target app on a store they control (a normal, free onboarding flow for most Shopify apps) to obtain at least one genuinely-signed webhook body/HMAC pair, then forge the surrounding HTTP headers when POSTing to the app's public webhook callback endpoint. No access token, `client_secret`, or `api_secret_key` is required — only a normal HTTP client capable of setting headers. This requires no signature forgery, only header substitution around an already-signed body, making the likelihood high wherever the host app dispatches based on `WebhookMetadata#shop`/`#topic` without independent verification.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the HMAC-signed material, or otherwise cryptographically bind them to the verified body (e.g., compute the HMAC over a canonical string that concatenates body + shop + topic, mirroring the `less()` fix pattern of moving the trusted-value computation before/inside the verified operation rather than trusting an out-of-band value after the fact). At minimum, document and enforce in `Registry.process` that `request.shop` must be cross-checked against a shop known to have installed the app (e.g., an existing stored session) before dispatching, so that unsigned headers can never redirect a verified payload to an unrelated tenant.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com`.
2. Attacker triggers an event so Shopify sends a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the identical body `B` and HMAC header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb) succeeds because it only checks `B` against the unchanged HMAC.
5. `Registry.process` (lib/shopify_api/webhooks/registry.rb#L188-200) invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, causing any tenant-keyed logic in the host app to act on attacker-controlled data as if it originated from the victim shop.
