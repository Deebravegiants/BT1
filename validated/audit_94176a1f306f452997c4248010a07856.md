### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted for tenant/handler dispatch but are not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, and `webhook_id` values used for tenant identification and handler dispatch are read directly from unauthenticated HTTP headers. `Registry.process` verifies the HMAC over the body, then hands the header-derived `shop` field to the app's webhook handler as trusted tenant data, breaking the equality that "HMAC-verified bytes" == "bytes acted upon."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all parsed straight from HTTP headers with no cryptographic binding to the request: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the raw body) against the HMAC header, using the app's secret: [3](#0-2) 

`Registry.process` runs this validation and then immediately trusts `request.shop` and `request.topic` to build the `WebhookMetadata` passed to the app's handler, without any further check that the `shop` header corresponds to the same request the HMAC was computed for: [4](#0-3) 

`WebhookMetadata.shop` is a `String` field that handler code is expected to use as the authoritative tenant identifier: [5](#0-4) 

Because the HMAC only signs the raw body bytes, an attacker who can obtain one legitimate webhook delivery for a shop they control (e.g., by installing the app on their own store and triggering a webhook event) possesses a `(raw_body, hmac)` pair that will pass `HmacValidator.validate` regardless of which `shop-domain`/`topic`/`webhook-id` headers accompany it. The attacker can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `Registry.process` will validate successfully (the body is unchanged) and dispatch to the handler with `data.shop` set to the attacker-chosen value, while `data.body` remains whatever content was in the attacker's own original webhook.

### Impact Explanation
This breaks the identity binding `shop asserted in HMAC-protected bytes == shop acted upon by the handler`. If a host application uses `WebhookMetadata#shop` to decide which merchant's data to create/update/delete (which is exactly the field's documented purpose), this analog allows an unprivileged internet user who merely operates their own Shopify store (unprivileged relative to any other merchant) to inject attacker-controlled webhook body content tagged as belonging to a victim shop — a cross-tenant write facilitated entirely by this gem's webhook-processing code, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires: (1) the attacker to install the target app on a shop they control and trigger/capture one legitimate webhook (a normal, unprivileged action any merchant can perform), and (2) the app's webhook endpoint to be internet-reachable, which webhook endpoints inherently are (Shopify itself delivers webhooks over the open internet). No possession of `client_secret`, access tokens, or other privileged material is required — only a standard webhook delivery the attacker already legitimately receives. The main mitigating factor is that this depends on how strictly the host application trusts `data.shop`, but the gem's own `WebhookMetadata` struct offers no alternative signal and documents `shop` as the tenant field, so the trust is squarely placed on this unauthenticated value.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC verification (or otherwise cryptographically bind them, e.g., by deriving them only from a signed payload rather than headers), so that `HmacValidator.validate` fails if any of these header values are altered relative to what was originally signed by Shopify.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`) with some `raw_body`.
2. Shopify sends headers `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, and body `raw_body`; `H` is a valid HMAC computed only over `raw_body`, per `to_signable_string`: [6](#0-5) 
3. Attacker replays the same `raw_body` and `H` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only and it matches `H`, so validation passes: [7](#0-6) 
5. `Registry.process` dispatches to the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"` and `body` equal to the attacker's original payload, despite the request never having been produced or signed for `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
