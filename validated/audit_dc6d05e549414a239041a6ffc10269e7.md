### Title
Aliased-balance token entries let two `erc20TokenAddresses` slots pass independent `balanceDif` checks for a single real transfer, minting shielded value without backing - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact` snapshots balances per index with `getBalancesForArray(circomData.erc20TokenAddresses)` and then verifies, per index `i` independently, that `balanceDif[i] == amountChanges[i] + utxoAmount[i]`. Neither this per-index check, `getERC20OrETHBalance`, nor `dimensionsCheck`/`checkOnchainCreation` in `HinkalHelper.sol` requires that the addresses in `erc20TokenAddresses` be distinct, independently-backed balances. An attacker who deploys a token whose `balanceOf` merely proxies another real token's balance (while its own `transferFrom` is a no-op) can insert that alias as a second array entry, causing the delta produced by one real transfer to satisfy two independent per-index equalities.

### Finding Description
The claimed equality is: **net tokens entering Hinkal == sum(amountChanges) + sum(minted on-chain UTXO amounts)**.

Trace in `contracts/Hinkal.sol`:
- `oldBalances = getBalancesForArray(circomData.erc20TokenAddresses)` is taken once, before any transfer, for the *whole array* [1](#0-0) .
- `_internalTransact` then loops per index and, for a deposit leg (`deltaAmountChange > 0`), calls `transferERC20TokenFromOrCheckETH(circomData.erc20TokenAddresses[i], externalAddress, address(this), amountChanges[i])`, i.e. it calls `transferFrom` on whatever contract sits at that specific index [2](#0-1) .
- `newBalances = getBalancesForArray(circomData.erc20TokenAddresses)` is taken again for the whole array after all legs ran [3](#0-2) .
- The per-index check `balanceDif == (onChainCreation ? 0 : amountChanges[i]) + utxoAmount` is evaluated independently for each `i`, using only `newBalances[i] - oldBalances[i]` [4](#0-3) .
- `getERC20OrETHBalance` simply calls `IERC20(addr).balanceOf(address(this))` with no verification that distinct addresses correspond to independent storage/state [5](#0-4) .

Root cause: the contract assumes each entry in `erc20TokenAddresses` represents an independently-tracked balance, but nothing enforces this. If the attacker deploys `TokenB` such that `TokenB.balanceOf(hinkal)` simply forwards to `RealToken.balanceOf(hinkal)` (i.e., aliases the same real balance) while `TokenB.transferFrom` is a no-op that returns `true` without moving any value, then:
- Attacker calls `transact` with `erc20TokenAddresses = [RealToken, TokenB]`, `amountChanges = [100, 100]`, both legs marked as deposits (`onChainCreation=false`), with the circuit-side commitments crediting 100 shielded units to each token slot (per-token circuit constraint `inTotal + amountChanges === outTotal` is enforced *per token index* and has no notion that index 0 and index 1 alias the same underlying value — the circuit only sees two "different" token identifiers as public inputs).
- `_internalTransact` executes leg 0: `RealToken.transferFrom(sender, hinkal, 100)` — 100 real tokens move in.
- `_internalTransact` executes leg 1: `TokenB.transferFrom(sender, hinkal, 100)` — no real value moves (no-op).
- `oldBalances = [X, X]` (both alias same real balance before), `newBalances = [X+100, X+100]` (both alias the same real balance after, which only moved once).
- `balanceDif[0] = 100 == amountChanges[0]` ✓; `balanceDif[1] = 100 == amountChanges[1]` ✓ — both independent checks pass, even though only one real transfer of 100 tokens occurred.

Net result: 200 units of shielded value are credited to the two token slots while only 100 real tokens entered the vault, violating the stated invariant. `checkOnchainCreation` and `dimensionsCheck` only validate array-length consistency and onChainCreation/amountChanges relationships, not token-address uniqueness or balance independence [6](#0-5) . `performProoflessDepositChecks` (used for `HinkalWrapper.prooflessDeposit`) likewise never restricts or deduplicates addresses beyond array length equality [7](#0-6) ; the proofless deposit path itself is separately protected by exact `balanceAfter - balanceBefore == amount` checks per unique deduplicated token in `_handleTransfersFromProoflessDeposit` and `_calcTokenChangesForProoflessDeposit`, which do correctly merge duplicate *addresses* into a single amount [8](#0-7) , so the proofless-deposit-specific double counting the question describes does not directly apply there — the real exploitable surface is `Hinkal.transact`, which uses per-index (not per-unique-address) balance snapshots and has no deduplication/aliasing defense at all.

### Impact Explanation
This mints shielded UTXO value with no backing asset for the aliased portion — a direct protocol-insolvency bug matching the "minting shielded value without backing" Critical category. Each call using a freshly deployed alias token can repeat this to mint unlimited unbacked shielded balance, since the attacker fully controls the alias token's `balanceOf`/`transferFrom` behavior and can reuse the pattern with any real token index already present in `erc20TokenAddresses` for that same call (or across calls with the same combination). The attacker gains real, redeemable shielded UTXOs backed by tokens that were never actually deposited, i.e. theft from the collectively-backed vault when other users later withdraw.

### Likelihood Explanation
Preconditions: attacker needs only to deploy an ordinary ERC20-like contract they fully control (no privileged role required), and must be able to produce a valid Circom proof for their own UTXOs where the second "token" index credits shielded value against the alias address — this is fully within an unprivileged user's proof-generation capability since the circuit does not appear to constrain the *meaning* of token identifiers beyond their numeric value being consistent between `erc20TokenAddresses[i]` and the per-index public inputs. Attacker cost is just gas plus one real deposit of any small amount for the "real" leg; the "aliased" leg costs nothing extra. This is fully repeatable per transaction and does not require any special tree state, ordering, or timing beyond crafting `CircomData` as normal.

### Recommendation
- In `Hinkal.transact`, reject `circomData.erc20TokenAddresses` arrays containing duplicate entries or any entries that cannot be shown to be economically independent; more robustly, require the sum of independent transfers be individually reconciled per distinct token address using a per-transferFrom-call-observed delta rather than trusting `balanceOf` snapshots that assume address-to-balance independence.
- Alternatively/additionally, use a strict allowlist/registry of known tokens (as hinted at by references to `erc20TokenRegistryAddress` in `IHinkal.ConstructorArgs`) so that only vetted, non-aliasing ERC20 contracts can appear in `erc20TokenAddresses`, closing the ability for attackers to introduce arbitrary alias contracts.
- Add an explicit uniqueness `require` over `circomData.erc20TokenAddresses` in `dimensionsCheck`/`performHinkalChecks`.

### Proof of Concept
Foundry plan:
1. Deploy `RealToken` (standard ERC20) and mint attacker 100 tokens; deploy `AliasToken` whose `balanceOf(address who)` returns `RealToken.balanceOf(who)` and whose `transferFrom` always returns `true` without state changes.
2. Register both in a `Hinkal` instance's flow (no privileged action needed — just pass them as `circomData.erc20TokenAddresses`).
3. Approve `RealToken` spend by Hinkal for 100 tokens; craft `CircomData` with `erc20TokenAddresses = [RealToken, AliasToken]`, `amountChanges = [100, 100]`, `onChainCreation = [false, false]`, generate a locally valid proof whose out-commitments credit 100 shielded units against each token index.
4. Call `Hinkal.transact(...)`.
5. Assert: `RealToken.balanceOf(hinkal) - balanceBefore == 100` (only 100 real tokens entered), but `amountChanges[0] + amountChanges[1] == 200` and shielded commitments were inserted crediting 200 total value — i.e. `netTokensIn (100) != sum(amountChanges) + sum(mintedUtxoAmounts) backed by real assets (200)`, confirming the equality is broken and value was minted unbacked.

    function _handleTransfersFromProoflessDeposit(
        TokenWithAmount[] memory uniqueTokens,
        uint256 uniqueCount
    ) private {
        for (uint256 i = 0; i < uniqueCount; i++) {
            address erc20Address = uniqueTokens[i].erc20Address;
            uint256 amount = uniqueTokens[i].amount;

            uint256 balanceBefore = getERC20OrETHBalance(erc20Address);
            if (erc20Address == address(0)) balanceBefore -= msg.value;

            transferERC20TokenFromOrCheckETH(
                erc20Address,
                msg.sender,
                address(this),
                amount
            );

            uint256 balanceAfter = getERC20OrETHBalance(erc20Address);

            require(
                balanceAfter - balanceBefore == amount,
                "proofless deposit balances must be equal"
            );
        }
    }

    function getERC20OrETHBalance(
        address _erc20TokenAddress
    ) internal view returns (uint256) {
        if (_erc20TokenAddress == address(0)) {
            return address(this).balance;
        } else {
            IERC20 outToken = IERC20(_erc20TokenAddress);
            return outToken.balanceOf(address(this));
        }
    }
