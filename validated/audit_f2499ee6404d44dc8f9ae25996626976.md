### Title
Emporium "Min" path lets an unprivileged EOA drain native ETH held by `Hinkal`/`EmporiumUpgradeable` without any signature, nullifier, or root-hash binding - (File: contracts/CircomDataBuilder.sol, contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When a Hinkal `transact` call targets the Emporium external action with `circomData.erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes proof-input generation to `formInputEmporiumMin`, which is verified against the minimal circuit `MainEVMCircuitMin.circom`. That circuit only constrains `message = Poseidon(messageSeed)` together with `outTimeStamp` and `calldataHash` - it contains **no** signature check, **no** nullifier check, and **no** Merkle root binding at all. Combined with `EmporiumUpgradeable.verifyWallet` short-circuiting (returning immediately, without any ECDSA check) when `stack.signerAddress == address(0)`, and with `runAction`'s balance-conservation loop iterating only over `circomData.erc20TokenAddresses` (empty in this path), an attacker can supply an empty token array while still instructing `op.endpoint.call{value: op.value}(...)` to send arbitrary amounts of the contract's native ETH balance to an address they control. No equality in the protocol (proof public inputs, calldata hash binding to ownership, or balance-diff check) actually authenticates that the caller owns any of that ETH.

### Finding Description
The security of every "normal" Hinkal transaction rests on the `MainEVMCircuit` proving that the prover knows a `spendingPublicKey`/`eddsaSignature` for the nullified UTXOs and that the claimed `inNullifiers`/`outCommitments`/`amountChanges` are consistent with a real Merkle path against `rootHashHinkal` [1](#0-0) . This is the "equality" (ownership of spent UTXOs = right to move funds) the system relies on.

However, when `circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `circomData.erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` switches to `formInputEmporiumMin`, whose only public inputs are `emporiumMessage`, `timeStamp`, and `calldataHash`: [2](#0-1) 

The matching circuit, `MainEVMCircuitMin.circom`, proves nothing about ownership of funds - it only proves knowledge of a `messageSeed` whose Poseidon hash equals the public `message`/`emporiumMessage`: [3](#0-2) 

`HinkalHelper.performHinkalChecks` only re-checks that the on-chain `CircomData` hashes to `circomData.calldataHash` (self-consistency of attacker-supplied data, not ownership) and validates dimensions/onchain-creation flags — it performs no ownership check either [4](#0-3) . `relayerIsValid` is a no-op when `relay == address(0)` [5](#0-4) , and `performHinkalChecks`'s `originalSender` rule is satisfiable by any EOA acting as its own relay.

`Hinkal.transact` separately validates `rootHashHinkal` via `rootHashExists`, but any *existing* root in the tree satisfies this - the min-circuit path never binds `rootHashHinkal` to anything, so an attacker can pass any valid historical root [6](#0-5) .

Inside `EmporiumUpgradeable.runAction`, `verifyWallet` is called; when `stack.signerAddress == address(0)` it just marks the message used and returns, with **no** signature verification at all: [7](#0-6) 

The op loop then executes the "Stateless Interaction" branch, performing `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract using its own (potentially other-users'-backed) ETH balance, with only a whitelist check against `callHinkalWallet`/`doSendToRelay` selectors, not against arbitrary value transfer: [8](#0-7) 

Because `circomData.erc20TokenAddresses.length == 0` is a precondition of this entire path, `getBalancesForArray` (both in `runAction` and in the post-call check in `Hinkal.transact`) operates on an empty array, so the balance-conservation equality that normally catches unauthorized ETH movement never fires: [9](#0-8) [10](#0-9) 

`getERC20OrETHBalance`/`transferERC20TokenOrETH` treat `address(0)` as native ETH, meaning ETH deposited into Hinkal/Emporium under shielded UTXOs backed by `address(0)` sits as `address(this).balance` in the same contract that this Emporium op can freely siphon: [11](#0-10) [12](#0-11) 

This breaks the exact class of equality flagged by the analog: "value moved by Hinkal or an external action but not counted in the balance equation." No `CircomData` field involved in the movement (`op.value`, `op.endpoint`) is bound to `calldataHash`/`signedMessageHash`/the public-input vector in a way that ties it to ownership of any shielded funds, and the balance-diff equality in `Hinkal.transact` is trivially vacuous (`0`-length loop) for this path.

### Impact Explanation
This is a direct theft of shielded/in-flight user funds (Critical): any unprivileged EOA can drain the entire native-ETH balance held by the Emporium/Wallet contracts — ETH that backs other users' still-valid shielded UTXO commitments/leaves in the Merkle tree — to an address of their choosing, without owning any nullifier, signature, or private key tied to those funds. The affected users' commitments remain unspent (their nullifiers were never even touched), but the backing ETH is gone, leaving those legitimate withdrawals to permanently fail once attempted (double impact: theft + freezing).

### Likelihood Explanation
High. The attacker needs no special role: `relay = address(0)` and `originalSender = msg.sender` satisfy `performHinkalChecks`; the Groth16 proof for `MainEVMCircuitMin` requires only a self-chosen `messageSeed` (no secret belonging to any other party); `rootHashHinkal` can be any historical root read directly from public storage (`roots`/`getRootHash`); and the `EmporiumUpgradeable` op simply needs `invokeWallet=false`, `endpoint=<attacker address>`, `value=<contract's ETH balance>`, `callData=""`. All of the required inputs are either public or trivially attacker-computable.

### Recommendation
- Do not allow the Emporium "min" (`erc20TokenAddresses.length == 0`) path to authorize any `op.value`-bearing call. Either require `op.value == 0` for every operation whenever the min-circuit path is used, or forbid the min-circuit path entirely when any `op.value > 0`.
- Ensure `EmporiumUpgradeable.runAction`'s and `Hinkal.transact`'s balance-conservation checks always include native ETH (`address(0)`) exposure regardless of whether `erc20TokenAddresses` includes it — e.g., always check `address(this).balance` deltas against a bound `amountChanges`/`slippageValues`-like accounting for value-bearing ops, not only for tokens explicitly listed by the (attacker-controlled) `circomData.erc20TokenAddresses`.
- Require `verifyWallet` to enforce an actual signature/ownership binding even when `stack.signerAddress == address(0)`, or disallow value-transferring/arbitrary-endpoint ops entirely in that unauthenticated branch.

### Proof of Concept
1. Attacker (any EOA, no prior deposit) calls `Hinkal.transact(a, b, c, dimensions, circomData)` with:
   - `dimensions = {tokenNumber: 0, nullifierAmount: 0, outputAmount: 0}`
   - `circomData.erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, `onChainCreation = []`, `slippageValues = []`
   - `circomData.relay = address(0)`, `circomData.originalSender = msg.sender`
   - `circomData.rootHashHinkal` = any currently valid root read from `Merkle.getRootHash()`/`roots`
   - `circomData.externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`
   - `circomData.externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: attackerAddr, invokeWallet: false, value: address(EmporiumContract).balance, callData: ""})], maxFee: 0, deadline: type(uint256).max}))`
   - `circomData.calldataHash` computed per `CircomDataBuilder.getHashedCalldata` over the above fields
   - `circomData.messageSeed`/`emporiumMessage` freely chosen by the attacker; a Groth16 proof `(a,b,c)` generated locally for `MainEVMCircuitMin` proving `message = Poseidon(messageSeed)`.
2. `verifyProof` succeeds (attacker legitimately knows the seed for their own chosen nonce).
3. `rootHashExists` succeeds (root is a real historical root, unrelated to attacker's non-existent funds).
4. `_externalTransact` dispatches to `EmporiumUpgradeable.runAction`; `verifyWallet` returns immediately (no signature required since `signerAddress == 0`); the loop executes `op.endpoint.call{value: op.value}("")`, sending the contract's full ETH balance to `attackerAddr`.
5. Post-call balance checks in both `runAction` and `Hinkal.transact` iterate over the empty `erc20TokenAddresses` array and never notice the ETH outflow.
