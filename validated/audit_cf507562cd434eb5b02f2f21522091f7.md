### No vulnerability found for this question.

The scenario described is the intended, documented behavior of `BindingAuthorized`, not a bypass. The precondition states the attacker's `bind` grant on `clusterrole/super-role` is cluster-scoped (`Namespace=''`), which in RBAC means the grant is not restricted to any single namespace — it applies everywhere, exactly as documented in the code comment: "this allows delegation to bind particular clusterroles in rolebindings within particular namespaces, and to authorize binding a clusterrole across all namespaces in a clusterrolebinding." [1](#0-0) 

`BindingAuthorized` builds an `authorizer.AttributesRecord` with `Verb: "bind"`, `Namespace: bindingNamespace` (the namespace where the RoleBinding is actually being created), and the `roleRef` resource/name, then calls the authorizer to check if the user is allowed to `bind` that specific ClusterRole in that specific namespace. [2](#0-1)  Since the attacker's RBAC grant for `bind` on `clusterrole/super-role` was itself defined with an empty namespace (i.e., granted via ClusterRoleBinding, applicable cluster-wide), the RBAC authorizer will correctly return `Allow` when the request's namespace is namespace B, because that's exactly what a cluster-scoped grant means — it is valid in every namespace, including B. This is not the attacker escalating from namespace A into namespace B; the attacker never had a namespace-A-scoped grant in this precondition — they had a cluster-wide grant.

This exact scenario (a `bind` permission scoped to a namespace only allowing bind in that namespace, versus scoped cluster-wide allowing bind in any namespace, including via RoleBinding) is already covered by existing integration tests distinguishing `any-rolebinding-writer-namespace` (namespace-scoped bind, restricted) from `any-rolebinding-writer` (cluster-scoped bind, works in any namespace). [3](#0-2)  The `RoleBinding` storage layer calls `BindingAuthorized` with the actual target namespace pulled from the request context, and there's no code path where a namespace-A-only bind grant is checked against but succeeds for namespace B. [4](#0-3) 

There is no flaw in `BindingAuthorized`'s namespace handling — it correctly scopes the authorization check to `bindingNamespace`, and the described "escalation" is simply the correct consequence of the attacker legitimately holding a cluster-wide `bind` grant, which is precisely the delegation model RBAC's `bind` verb is designed to support.

func BindingAuthorized(ctx context.Context, roleRef rbac.RoleRef, bindingNamespace string, a authorizer.UnconditionalAuthorizer) bool {
	if a == nil {
		return false
	}

	user, ok := genericapirequest.UserFrom(ctx)
	if !ok {
		return false
	}

	attrs := authorizer.AttributesRecord{
		User: user,
		Verb: "bind",
		// check against the namespace where the binding is being created (or the empty namespace for clusterrolebindings).
		// this allows delegation to bind particular clusterroles in rolebindings within particular namespaces,
		// and to authorize binding a clusterrole across all namespaces in a clusterrolebinding.
		Namespace:       bindingNamespace,
		ResourceRequest: true,
	}

	// This occurs after defaulting and conversion, so values pulled from the roleRef won't change
	// Invalid APIGroup or Name values will fail validation
	switch roleRef.Kind {
	case "ClusterRole":
		attrs.APIGroup = roleRef.APIGroup
		attrs.APIVersion = "*"
		attrs.Resource = "clusterroles"
		attrs.Name = roleRef.Name
	case "Role":
		attrs.APIGroup = roleRef.APIGroup
		attrs.APIVersion = "*"
		attrs.Resource = "roles"
		attrs.Name = roleRef.Name
	default:
		return false
	}

	decision, _, err := a.Authorize(ctx, attrs)
	if err != nil {
		utilruntime.HandleError(fmt.Errorf(
			"error authorizing user %#v to bind %#v in namespace %s: %v",
			user, roleRef, bindingNamespace, err,
		))
	}
	return decision == authorizer.DecisionAllow
