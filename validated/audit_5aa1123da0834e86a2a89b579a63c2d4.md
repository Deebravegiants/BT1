### Title
Buffered and promise-yield receipts carrying attached deposits are silently dropped during state dump - ([File: core/primitives/src/state_record.rs])

### Finding Description
`StateRecord::from_raw_key_value_impl` only special-cases a subset of trie columns: `ACCOUNT`, `CONTRACT_DATA`, `CONTRACT_CODE`, `ACCESS_KEY`, `RECEIVED_DATA`, `POSTPONED_RECEIPT_ID`, `PENDING_DATA_COUNT`, `POSTPONED_RECEIPT`, and `DELAYED_RECEIPT_OR_INDICES`; every other column, including `col::BUFFERED_RECEIPT` (14) and `col::PROMISE_YIELD_RECEIPT` (12), falls through the catch-all `_ => { println!(...); None }` arm. [1](#0-0) 

Both `BUFFERED_RECEIPT` and `PROMISE_YIELD_RECEIPT` store real `Receipt`/`ReceiptOrStateStoredReceipt` values that can carry an attached deposit through a `Transfer` or `FunctionCall` action, exactly like the receipts stored under `DELAYED_RECEIPT_OR_INDICES` and `POSTPONED_RECEIPT` (which *are* correctly decoded). `BufferedReceipt` is the outgoing-receipt buffer used whenever a receiving shard is congested (`ShardsOutgoingReceiptBuffer` / `OutgoingReceiptBuffer`, keyed by `TrieKey::BufferedReceipt`), and `PromiseYieldReceipt` is the parked receipt created by `promise_yield_create` while awaiting a `resume` callback. [2](#0-1) 

These are ordinary, currently-enabled protocol features reachable by any account: sending transactions/receipts toward a congested shard causes the runtime to buffer the outgoing receipt in the trie instead of forwarding it immediately (`ReceiptSinkV2::buffer_receipt`), and this buffered receipt keeps its attached deposit until it is eventually forwarded. [3](#0-2) 

`tools/state-viewer/src/state_dump.rs::iterate_over_records` iterates the full trie and converts every entry through `StateRecord::from_raw_key_value`; entries that decode to `None` are simply skipped and never reach the `callback`, and `total_supply` is only accumulated from `StateRecord::Account` entries. [4](#0-3) 

Because `BUFFERED_RECEIPT` and `PROMISE_YIELD_RECEIPT` fall to `None`, any receipt sitting in those columns — including its attached deposit — is completely absent from the exported `records`/genesis file produced by `state_dump`, `print_recursive_leaves`, and `get_state_stats_group_by` (all of which rely on `StateRecord::from_raw_key_value`). [5](#0-4) 

### Impact Explanation
This is a state-divergence / supply-accounting bug: funds that are logically still owned by the protocol (parked in an outgoing buffer or a yielded promise) are not reflected anywhere in the `StateRecord` stream produced for state dumps, genesis regeneration (`neard view-state dump-state`), or `fork-network`. If such a dump is later used to bootstrap a new chain/genesis (a real, supported near-tooling workflow), the attached deposit is permanently lost — it is neither credited to any account nor represented as a receipt to be replayed. It also breaks any supply-conservation audit that compares a live-trie sum against the dumped `StateRecord` sum, since buffered/yielded-receipt deposits vanish from the second side of the comparison. This matches NEAR's "state divergence / accounting failure" bounty class rather than a direct double-spend, since the underlying live trie and consensus state are unaffected — only the exported/reconstructed representation is wrong.

### Likelihood Explanation
No privileged access is required. An ordinary account only needs to:
1. Send a transaction/receipt with an attached deposit (`Transfer` or `FunctionCall` with `deposit`) toward a shard that is congested enough that the outgoing receipt gets buffered instead of forwarded immediately (`ReceiptSinkV2::forward_or_buffer_receipt` → `buffer_receipt`), or
2. Use `promise_yield_create` with an attached deposit so the parked receipt is stored under `col::PROMISE_YIELD_RECEIPT`.

Both paths are exercised by normal, permitted user activity (congestion is a routine, expected condition covered by NEP-539/bandwidth-scheduler docs) rather than any exploit of validation logic, so this is trivially reproducible in a testnet/localnet with induced congestion or a yield/resume contract.

### Recommendation
Add explicit match arms in `StateRecord::from_raw_key_value_impl` for `col::BUFFERED_RECEIPT` and `col::PROMISE_YIELD_RECEIPT` (decoding via `ReceiptOrStateStoredReceipt`/`Receipt` similarly to `DELAYED_RECEIPT_OR_INDICES`/`POSTPONED_RECEIPT`), introducing new `StateRecord` variants (e.g. `BufferedReceipt`, `PromiseYieldReceipt`) so `state_dump`/`fork-network`/`state-viewer` preserve these funds-bearing entries. Additionally, replace the silent `_ => None` default with an explicit, audited list of "known balance-free" columns (`POSTPONED_RECEIPT_ID`, `PENDING_DATA_COUNT`, `PROMISE_YIELD_INDICES`, `PROMISE_YIELD_TIMEOUT`, `BUFFERED_RECEIPT_INDICES`, `BANDWIDTH_SCHEDULER_STATE`, `BUFFERED_RECEIPT_GROUPS_QUEUE_*`, `GLOBAL_CONTRACT_CODE`/`NONCE`, `PROMISE_YIELD_STATUS`, `YIELD_ID_TO_DATA_ID`, `DATA_ID_TO_YIELD_ID`) so that any newly introduced column triggers a compile-time or CI failure (similar to the existing `normalization_covers_every_column` guard in `tools/fork-network/src/metrics.rs`) instead of silently dropping data.

### Proof of Concept
Integration/differential test plan:
1. Set up a two-shard test cluster (or use `runtime/runtime/src/tests/apply.rs` congestion-buffering scaffolding, e.g. `generate_delegate_actions`) so that an action receipt carrying an attached deposit for a remote shard gets buffered via `ShardsOutgoingReceiptBuffer`/`OutgoingReceiptBuffer::push_back` (as already exercised in the existing buffering test). [6](#0-5) 
2. After applying the chunk, iterate the resulting trie's `disk_iter()` for the shard and call `StateRecord::from_raw_key_value(key, value)` on every entry, mirroring `iterate_over_records`.
3. Assert that the key with `key[0] == col::BUFFERED_RECEIPT` produces `Some(StateRecord::...)` containing the deposit amount — this assertion currently **fails**, since it returns `None`.
4. Separately, sum `account.amount() + account.locked()` over all `StateRecord::Account` entries plus the deposit carried by the dropped buffered receipt, and compare it against the pre-buffering total; show the `StateRecord`-derived total is short by exactly the buffered receipt's deposit, while a direct trie/`CongestionInfo` sum (`buffered_receipts_gas`/deposit tracking) still accounts for it — demonstrating the divergence between live state and its `StateRecord` export.
5. Repeat with a `promise_yield_create` call carrying an attached deposit, confirming the `col::PROMISE_YIELD_RECEIPT` entry is likewise dropped.

    fn buffer_receipt(
        &mut self,

        size: u64,
        gas: Gas,
        state_update: &mut TrieUpdate,
        shard: ShardId,
        use_state_stored_receipt: bool,

        let receipt = match use_state_stored_receipt {
            true => {
                let metadata =
                    StateStoredReceiptMetadata { congestion_gas: gas, congestion_size: size };
                let receipt = StateStoredReceipt::new_owned(receipt, metadata);
                let receipt = ReceiptOrStateStoredReceipt::StateStoredReceipt(receipt);
                receipt
            }
            false => ReceiptOrStateStoredReceipt::Receipt(std::borrow::Cow::Owned(receipt)),
        };

        self.own_congestion_info.add_receipt_bytes(size)?;
        self.own_congestion_info.add_buffered_receipt_gas(gas)?;

        if receipt.should_update_outgoing_metadatas() {
            self.outgoing_metadatas.update_on_receipt_pushed(
                shard,
                ByteSize::b(size),
                gas,
                state_update,
            )?;
        }

        self.outgoing_buffers.to_shard(shard).push_back(state_update, &receipt)?;
        self.stats.buffered_receipts.entry(shard).or_default().add_receipt(size, gas);
