## Title
Excess native ETH sent to `EvmHost.dispatch()`/`fundRequest()` for fee-token swaps is refunded to the Host contract, not the caller, permanently stranding user funds - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept `msg.value` and swap it via Uniswap V2's `swapETHForExactTokens` for an exact amount of `feeToken()`. This mirrors the reported bug class exactly: a prefunded/attached value is spent against a capped/exact target amount, and any leftover is not returned to the original payer — it is refunded to whichever address is `msg.sender` from the router's point of view, which here is `EvmHost` itself, not the user who dispatched the message.

### Finding Description
In each of the three functions, the pattern is identical: [1](#0-0) [2](#0-1) [3](#0-2) 

`swapETHForExactTokens(amountOut, path, to, deadline)` is a standard Uniswap V2 router function that computes `amounts[0]` (the exact ETH input needed to buy `amountOut` of `feeToken()`), performs the swap, and refunds any leftover ETH (`msg.value - amounts[0]`) via `TransferHelper.safeTransferETH(msg.sender, leftover)`. Critically, from the router's perspective `msg.sender` is whoever called the router — here that is `EvmHost` itself (`IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(...)`), not the original transaction sender (`_msgSender()`/user) who sent the overpaid `msg.value` to `EvmHost.dispatch(...)`.

This is structurally the same defect as the reported Lido issue: a user sends a value intended to cover an exact target amount; the underlying integration caps/consumes only the exact amount needed; the excess is not routed back to the depositor. In the Lido case the excess WETH sits unrefunded in the adapter; here the excess ETH lands back in `EvmHost`'s own balance (since the router sends the refund to the caller, which is `EvmHost`), with no code path in `dispatch`/`fundRequest` to forward that refund on to the user. Any user (an unprivileged message dispatcher calling `dispatch{value: msg.value}(post)` directly, or any `HyperApp`-derived contract relaying user-sent native value for `dispatchWithFeeToken`'s native-payment sibling path) who overestimates the native fee — which is expected, since `quote()` is only an off-chain estimate subject to slippage/price movement between quoting and execution — loses the difference permanently to the `EvmHost` contract's balance.

### Impact Explanation
This is a fund-loss issue reachable by any unprivileged user dispatching a message with native-token fee payment: whenever `msg.value` supplied exceeds the exact `post.fee`/`get.fee`/`amount` priced by the router at execution time (routine due to price movement between `quote()` and the transaction, or a user simply overpaying for safety margin), the excess ETH is not returned to them but instead accumulates in `EvmHost`. There is no user-facing recovery mechanism for this stranded value in the reviewed dispatch/fundRequest code paths. Given how frequently native-fee dispatch is used across the message-dispatcher/relayer/token-bridge integration surface (any `HyperApp`-based app, direct SDK dispatches, `fundRequest` top-ups), this is a recurring value leak rather than an edge case, meeting the bar of concrete permanent loss of user funds.

### Likelihood Explanation
Likelihood is high: any caller supplying `msg.value` to `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest` where the actual Uniswap-computed input (`amounts[0]`) is less than `msg.value` triggers the bug — this happens on essentially every call unless the caller sends the exact wei amount the router will consume at execution time, which is generally unknowable in advance (AMM price can move between quoting and inclusion). No adversarial conditions or special timing are required.

### Recommendation
After the `swapETHForExactTokens` call, explicitly capture the returned `amounts` array and forward any leftover native balance received by `EvmHost` back to `_msgSender()` (or `post.payer`/`get.payer`, consistent with existing fee-payer semantics), mirroring the refund pattern already implemented elsewhere in the codebase for `IntentGatewayV2` (e.g. `_sendValue(msg.sender, msgValue)` refunds for overpaid native input on `placeOrder`/`fillOrder`). Apply the same fix uniformly to `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`.

### Proof of Concept
1. Caller calls `quote(post)` to estimate the ETH cost for `post.fee` in `feeToken()`, getting value `X`.
2. Caller calls `EvmHost.dispatch{value: X + slack}(post)` where `slack > 0` is added for safety margin (or the AMM price shifts favorably between the `quote()` call and the `dispatch()` transaction being mined, making the actual required input less than `X`).
3. Inside `dispatch`, `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: X + slack}(post.fee, path, address(this), block.timestamp)` executes: it computes the exact `amountIn` needed (say `Y <= X`), performs the swap, and refunds `(X + slack) - Y` in ETH to the caller of the router — which is `EvmHost`, not the original message dispatcher.
4. `EvmHost`'s ETH balance increases by `(X + slack) - Y`; the original caller receives nothing back and has no way to reclaim this amount through `dispatch`/`fundRequest`/any other function shown in the reviewed code.
5. Repeating this over many dispatches accumulates stranded ETH inside `EvmHost` indefinitely.

    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                post.fee, path, address(this), block.timestamp
            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }
