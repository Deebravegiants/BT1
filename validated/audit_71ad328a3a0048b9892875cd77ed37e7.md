### Title
Credit-mode self-seizure leaves a negative supply position on the liquidated account when the receiver equals the target — (File: contracts/controller/src/positions/liquidation/apply.rs)

### Summary
`apply_liquidation_share_credit` first debits the full seized share amount `S` from the liquidated account, then credits `S - fee` to the receiver account. The only cross-account check is `receiver.spoke_id == account.spoke_id`; nothing prevents the liquidator from naming the liquidated account itself as the receiver (`SeizeMode::Credit(target_account_id)`). Like the raid0 `pers->free` clearing `mddev->private` that reshape had already repopulated, the debit leg "tears down" state on an object the credit leg then reuses, leaving `scaled_amount = -fee_scaled` when the seizure covers the entire position.

### Finding Description
In `apply_liquidation_share_credit` (`contracts/controller/src/positions/liquidation/apply.rs:147-206`), for each seized entry:

1. `position.scaled_amount = position.scaled_amount.checked_sub(env, seized_scaled)` (line 178) removes `S` from the target account's stored supply position; `update_or_remove_supply_position` deletes the map entry if it reaches zero (`contracts/controller/src/account.rs:190-199`).
2. `credit_supply_shares` (lines 217-236) then credits `liquidator_scaled = S - fee_scaled` into `receiver`. The guard at lines 165-169 only asserts the receiver's spoke matches the liquidated account's spoke — the target account trivially satisfies this.

If the liquidator passes the target's own `account_id` as the Credit receiver, the same account is debited `S` and re-credited `S - fee_scaled`. With a full seizure (`seized_scaled == position.scaled_amount`) and any nonzero `liquidation_fees`, the position reloads as `None` (it was removed by the zero-check), `get_or_create_supply_position` recreates it, and the result is a stored position with `scaled_amount = -fee_scaled`.

Downstream, `check_bad_debt_after_liquidation` (lines 300-315) removes the account only when `borrow_positions.is_empty()` and `account.is_empty()`; a negative supply entry keeps the map non-empty, so the corrupted account survives with negative scaled shares. A negative `scaled_amount` poisons any later unscale/merge on that leg (`scaled_amount.checked_add`/`checked_sub`, spoke usage accounting in `apply_spoke_exit`, and `pool` share withdrawals reading `ScaledPositionRaw`), and the earlier in-loop assertion `seized_scaled.checked_sub(env, liquidator_scaled) == fee_scaled` cannot catch the self-credit because it only validates the split, not the identities.

### Impact Explanation
A negative supply share on a live account corrupts that spoke's supply-side accounting: `apply_spoke_exit(UsageSide::Supply, -fee_scaled)` was never applied for the re-credited leg while the debit path already removed `S`, so spoke `supplied_scaled_ray` diverges from real scaled holdings. Subsequent operations on the account/leg (supply merges, withdrawals, further liquidations, bad-debt cleanup) operate on a negative balance that can underflow or mint unbacked claims, producing permanent accounting drift and potential protocol insolvency / frozen positions on the affected spoke.

### Likelihood Explanation
Reachable by a single unprivileged address calling `liquidate` with `SeizeMode::Credit` pointing at the victim's own account id on an account that is liquidatable and fully seizable with a nonzero `liquidation_fees` stamp. The liquidator funds the repayment leg normally, so the call is economically self-contained. Uncertainty: I could not confirm the outer `liquidate` entrypoint (`positions/liquidation/mod.rs`) doesn't reject `receiver == target` before reaching `apply_liquidation_share_credit`; no such check is visible in the application layer itself, and the code comments treat the receiver purely as "the liquidator's account," suggesting the self-target case was not considered.

### Recommendation
Reject `SeizeMode::Credit` where the receiver account id equals the liquidated `account_id` (and ideally any receiver owned by the same account) at plan validation time, alongside the existing spoke-match assertion in `apply_liquidation_share_credit` lines 165-169. Alternatively, net the debit and credit before storage writes so a self-credit collapses to only the fee deduction rather than a remove-then-recreate sequence.

### Proof of Concept
1. Attacker's account A supplies a single collateral leg with `liquidation_fees > 0` and borrows to just below HF 1 (or waits for a price move).
2. Call `liquidate(caller=attacker, account_id=A, repaid=[...full debt leg...], seized=[SeizeEntry covering the full collateral scaled amount], mode=SeizeMode::Credit(A))`.
3. In `apply_liquidation_share_credit`: debit removes `S` (entry deleted at zero); `credit_supply_shares` reloads a `None` position and creates one with `scaled_amount = S - fee - S = -fee_scaled`.
4. `check_bad_debt_after_liquidation` sees an empty borrow map but non-empty supply map; account A persists holding `scaled_amount = -fee_scaled` on the seized hub asset, while spoke usage was reduced by `fee_scaled` only — a permanently corrupted share balance reachable in one transaction.
