### Title
Shared singleton Emporium's `msg.sender` identity lets any attacker hijack another user's external-protocol position (e.g., steal staking rewards accrued to a victim's earlier `stake()` call) - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable` is deployed once as a shared, stateful singleton (its storage lives at a fixed ERC-7201 slot and it is used as the `allowedRecipient`/external-action target for all users), yet its CASE 2 "stateless" branch performs `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract itself with completely attacker-controlled `endpoint`/`callData`. Because every user's CASE 2 call shares the exact same `msg.sender` identity (`address(Emporium)`), any third-party contract that records `msg.sender` as an owner/staker (e.g., a staking contract's `stake()`) will treat all Hinkal users as the *same* principal, letting an attacker call `getReward()`/`claim()` on a victim's position and either redirect rewards to themselves via an explicit recipient parameter, or let `handleOut`'s before/after balance-diff sweep mint the harvested tokens as their own output UTXO.

### Finding Description
Equality that should hold: `staking_contract.owner(position) == msg.sender_of_stake_call`, and later `reward_recipient` for that position should resolve back to the same principal that originally staked (the victim's stealth identity). In this design that never holds, because the "principal" as seen by any external contract is always `address(Emporium)`, a fixed, shared address, not something per-user.

Code path:
- `runAction` CASE 1 ("Stateful Interaction") routes through a **per-user** `HinkalWallet` (`stack.signerAddress`), so `msg.sender` as seen by the external endpoint is the victim's unique wallet address — this path is safe. [1](#0-0) 
- CASE 2 ("Stateless Interaction") calls `op.endpoint.call{value: op.value}(op.callData)` directly from `EmporiumUpgradeable` itself, with only a check that the selector isn't `callHinkalWallet`/`doSendToRelay`. Any other endpoint/selector is permitted. [2](#0-1) 
- `EmporiumUpgradeable` is a single upgradeable contract with storage at a fixed slot — it is not deployed per-user, so its address is the same for every caller/session. [3](#0-2) 
- `handleOut` computes ownership of any positive balance delta purely from the current transaction's own `balancesBefore`/`balancesAfter` diff and mints a UTXO to `circomData.stealthAddressStructure` — i.e., whoever is running the current `runAction`, with zero linkage to who actually caused the underlying position/reward to exist. [4](#0-3) 
- Contrast with `HinkalWallet.callHinkalWallet`, which is gated by `onlyEmporium` and is unique per user (`address public immutable emporium` is fixed but the wallet itself is per-signer), demonstrating the protocol's own intended isolation model for stateful positions — a model CASE 2 completely bypasses by calling out from the shared Emporium address instead of a per-user wallet. [5](#0-4) 

Attacker's exact call: the attacker crafts their own `CircomData.externalActionData.externalActionMetadata` decoding to an `EmporiumStack` with `signerAddress == address(0)` (forcing CASE 2) and one `EmporiumOperation` whose `endpoint` is the same staking contract the victim previously staked through via Emporium, and whose `callData` is `getReward()`/`claim()` (optionally with a `recipient` parameter set to the attacker's own address, if the staking contract supports one). Because the staking contract's internal bookkeeping keyed the victim's earlier `stake()` call to `msg.sender == address(Emporium)`, this new call from the same `address(Emporium)` succeeds and is authorized to claim/redirect those exact rewards.

Exploit flow:
1. Victim runs a Hinkal transaction whose CASE 2 op calls `stakingContract.stake(amount)`. `msg.sender` recorded by the staking contract is `address(Emporium)`.
2. Time passes; rewards accrue to the `Emporium`-keyed position.
3. Attacker runs their own Hinkal transaction with a CASE 2 op calling `stakingContract.getReward()`/`claim()` (optionally specifying attacker's own address as reward recipient). This succeeds because it's authorized as `address(Emporium)`, the same identity the victim's stake is recorded under.
4. If the reward token is transferred to `msg.sender` (Emporium) rather than a caller-specified recipient, the attacker simply lists that token in their own `circomData.erc20TokenAddresses`; `handleOut` sees `balancesAfter > balancesBefore` for that token and mints a fresh output UTXO of that amount to the attacker's own `stealthAddressStructure`, with zero corresponding UTXO burn or deposit backing it.

Why existing guards fail: `performHinkalChecks`/`dimensionsCheck`/`verifyProof`/`onlyAllowedRecipient` only validate that Emporium is a legitimate external-action target and that the proof's declared balance deltas are self-consistent for the *current* transaction — none of them constrain who is entitled to the pre-existing balance/position sitting behind a third-party contract that treats Emporium as its caller. The circuit's `inTotal + amountChanges === outTotal` constraint is satisfied trivially because the "input" side is simply absent (no UTXO nullified) while the harvested reward becomes a brand-new legitimately-verified output.

### Impact Explanation
Critical — direct theft of a victim's earnings that were legitimately routed through the protocol. The attacker gains the entire reward amount accrued on the victim's external staking position, backed by no burn of the attacker's own UTXOs and no interaction with the victim's shielded balance/nullifiers at all. This is repeatable against any external contract that lets rewards/positions be claimed by whoever calls as the recorded `msg.sender`, for every victim who ever used a Emporium CASE 2 `stake()`-like op, and can be repeated every time new rewards accrue.

### Likelihood Explanation
Preconditions: any external contract used via CASE 2 that (a) records ownership/eligibility by `msg.sender`, and (b) allows claiming/redirecting rewards later by the same `msg.sender` — a very common pattern for ERC-20 staking/reward contracts (e.g., Synthetix-style `StakingRewards`). No privileged role is needed; the attacker only needs to observe (via on-chain state of the staking contract, keyed to the well-known `Emporium` address) that a reward balance is claimable, then submit their own ordinary Hinkal transaction with a crafted `EmporiumStack`. Cost is a single transaction plus normal Hinkal proof generation for depositing/withdrawing their own funds; fully repeatable and automatable by simply monitoring the public `Emporium` address's positions across all integrated staking protocols.

### Recommendation
CASE 2 stateless calls must never let the shared `Emporium` singleton itself be the caller identity for state-mutating interactions with third-party contracts that key ownership by `msg.sender`. Route all such calls (not just CASE 1) through a per-user proxy/wallet (as already done via `HinkalWallet`), or deploy Emporium per-user (e.g., via CREATE2 salted by user identity) so `msg.sender` seen by external protocols is unique per user rather than a fixed, shared address. Alternatively, restrict CASE 2 to a strict allowlist of endpoints/selectors known to be stateless (view-safe or non-custodial), and require any custodial/position-creating interactions to always go through the per-user wallet path.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable` (singleton), a `MockStakingRewards` contract with `stake(uint256)` recording `balanceOf[msg.sender] += amount` and pulling tokens from `msg.sender`, and `getReward()` paying `rewardToken.transfer(msg.sender, earned[msg.sender])`.
2. Simulate victim's Hinkal `runAction`: build `CircomData` with `EmporiumStack{signerAddress: address(0), ops: [{endpoint: stakingContract, invokeWallet: false, callData: abi.encodeCall(stake, (amount))}]}`; assert `stakingContract.balanceOf(address(Emporium)) == amount` and `Emporium`'s own token wasn't returned as a UTXO (since balance decreased, not increased, in that call - deposit was pre-funded via `deltaAmountChanges`).
3. `vm.warp` forward so rewards accrue: assert `stakingContract.earned(address(Emporium)) > 0`.
4. Simulate attacker's Hinkal `runAction` with their own `CircomData` (`circomData.erc20TokenAddresses` including `rewardToken`, `stealthAddressStructure` = attacker's own) and `EmporiumStack{signerAddress: address(0), ops: [{endpoint: stakingContract, callData: abi.encodeCall(getReward, ())}]}`.
5. Assert: `outUtxo.amount == earnedRewardAmount` and `outUtxo` uses the attacker's `stealthAddressStructure` — i.e. `reward_recipient == attacker != stealthAddress(staker=victim)` — while no nullifier belonging to the attacker (or victim) was spent to back this UTXO, and `stakingContract.earned(address(Emporium))` is now `0` (rewards drained on victim's behalf).

    function handleOut(
        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
    ) internal returns (UTXO memory outUtxo) {
        // total change can be less than zero if there was some balance before the call -> that's why we have <=
        if (balanceChange <= 0) {
            return outUtxo;
        }

        transferERC20TokenOrETH(
            circomData.erc20TokenAddresses[i],
            msg.sender,
            uint256(balanceChange)
        );

        outUtxo = UTXO(
            uint256(balanceChange),
            circomData.erc20TokenAddresses[i],
            circomData.stealthAddressStructure,
            circomData.timeStamp
        );
    }
