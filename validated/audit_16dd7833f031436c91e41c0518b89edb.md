### Title
Unbounded slippage on `swapETHForExactTokens` fee payment lets a flash-loan sandwich strand the caller's native token in `EvmHost` - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all let an unprivileged caller pay the protocol fee with native ETH by routing it through a live Uniswap V2 pool via `swapETHForExactTokens`, using `block.timestamp` as the deadline and the caller's entire `msg.value` as the input cap, with no minimum-output/maximum-input slippage guard of its own. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`swapETHForExactTokens` refunds any unspent ETH to whoever calls the router — here that is `EvmHost` itself, since `EvmHost` calls the router with `{value: msg.value}`. Unlike `IntentGatewayV2.placeOrder`, which explicitly tracks `msgValue` and calls `_sendValue(msg.sender, msgValue)` to return unspent native tokens to the user after its own `swapETHForExactTokens` call, none of the three `EvmHost` functions that perform this same swap (`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, `fundRequest`) ever forward the router's ETH refund back to `_msgSender()`. Any ETH left over after the swap is trapped inside `EvmHost` with no accounting of who is owed it.

Because the pool price used to compute the required ETH input is the live spot price of a Uniswap V2 pool, it is directly the kind of state the external report's flash-loan class of bug targets: an attacker can manipulate the WETH/feeToken pool reserves with a flash loan immediately before a victim's `dispatch`/`fundRequest` transaction (or the victim sends more ETH than needed as a buffer against normal slippage, which is the common pattern for this call since no `amountInMax` is exposed to the caller). Whatever ETH the router refunds to `EvmHost` — whether from ordinary price movement or from an attacker's price manipulation widening the gap between the amount consumed and `msg.value` — is not returned to the user and is not tracked by any state variable, i.e. it becomes permanently stuck/donated to the contract with no withdrawal path visible in this file.

### Impact Explanation
This is a concrete loss-of-funds bug for any unprivileged caller of `EvmHost.dispatch`/`fundRequest` who supplies native ETH: the difference between `msg.value` and the actual ETH consumed by the manipulated-price swap is permanently unrecoverable by that caller. A flash loan skewing the pool price magnifies the amount left over that gets stranded, which is exactly the bug class flagged in the external report (flash-loan-driven price manipulation causing an unintended loss on a spot-priced trade). Severity is Medium: it does not compromise consensus, mint tokens, or forge messages, but it is a reachable, unprivileged fund-loss path on the core dispatch entrypoint.

### Likelihood Explanation
Every relayer, application, or end-user that dispatches a POST/GET request or funds a pending request with native ETH (rather than the fee token directly) goes through this code path — it is the default, advertised way to pay fees per the function's own NatSpec ("Payment for the request can be made with either the native token or the feeToken... it will perform a swap under the hood"). No special privileges are required; only a thin/manipulable Uniswap V2 WETH/feeToken pool and a caller sending `msg.value` are needed.

### Recommendation
Track the actual ETH consumed (via the `amounts[0]` return value of `swapETHForExactTokens`, as `IntentGatewayV2.placeOrder` already does) in all three `EvmHost` functions, and refund `msg.value - amounts[0]` to `_msgSender()` after the swap. Additionally consider exposing a caller-supplied `amountInMax`/slippage bound rather than implicitly using all of `msg.value`, so a manipulated pool price causes a revert instead of a silent overspend.

### Proof of Concept
1. Attacker observes a pending user transaction (or front-runs their own) calling `EvmHost.dispatch(DispatchPost)` with `msg.value = X` ETH intended to cover `post.fee` fee-tokens via the WETH/feeToken Uniswap V2 pool.
2. Attacker takes a flash loan and swaps into the pool to shift the WETH/feeToken price so that acquiring `post.fee` tokens requires more WETH than before, then reverses the trade after the victim's tx lands in the same or an adjacent block (classic sandwich enabled by the unbounded `swapETHForExactTokens{value: msg.value}` call with `block.timestamp` deadline).
3. `swapETHForExactTokens` consumes only what is needed for `post.fee` output at the manipulated price and refunds the rest of `X` ETH to `EvmHost`. [1](#0-0) 
4. `dispatch` proceeds to build and emit the `PostRequest` without ever returning the refunded ETH to `_msgSender()` — no `_sendValue`/refund call exists anywhere in `EvmHost.sol` for this leftover balance, unlike `IntentGatewayV2.placeOrder`'s explicit `_sendValue(msg.sender, msgValue)` refund. [4](#0-3) 
5. The stranded ETH remains in `EvmHost` with no per-user accounting, permanently unrecoverable by the caller who supplied it.

        if (msg.value > 0) {
            address[] memory path = new address[](2);

            path[0] = IUniswapV2Router02(uniswapV2).WETH();

            );

        }
