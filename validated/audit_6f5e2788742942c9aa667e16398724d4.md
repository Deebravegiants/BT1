### Title
Wallet Unlock Passphrase Cached in Plaintext via `PassphraseCache` - ([File: features/application/src/modules/passphrase-cache.ts])

### Summary
The external report describes `price-feeder` storing a keyring password in plaintext in an on-disk configuration file with no permission checks. The equivalent bug class in this codebase is the `PassphraseCache` module, which caches the user's wallet-unlock passphrase in plaintext in the injected `storage` adapter (aliased to `sessionStorage`) with no encryption of the cached value, for up to a configurable TTL (default 60 minutes).

### Finding Description
`PassphraseCache.set()` writes the raw passphrase string directly to storage under the key `PASSPHRASE_KEY = 'passphrase'` with no encryption: [1](#0-0) [2](#0-1) 

`PassphraseCache.get()` reads that same plaintext value back out and is used by `Application#autoUnlock` and `Application#unlock` to auto-unlock the wallet: [3](#0-2) 

The storage backing `PassphraseCache` is explicitly aliased to `sessionStorage`, not any encrypted storage implementation: [4](#0-3) 

In the browser-extension environment, `sessionStorage` is just the `unsafe-storage` wrapper (no encryption) around `chrome.storage.session`, falling back to plain in-memory storage if unavailable: [5](#0-4) [6](#0-5) 

By contrast, the seed itself is stored using `seedStorage`/`secure-container`-based encryption (scrypt + AES-GCM), showing the codebase clearly distinguishes "safe" encrypted storage from "unsafe" storage elsewhere: [7](#0-6) 

The passphrase cached here is the same secret that decrypts the seed (`seedStorage.set(seed, { passphrase })`), so leaking it is equivalent to leaking the keyring password in the price-feeder report — it grants an attacker the ability to unlock/decrypt the wallet.

### Impact Explanation
Whoever can read the plaintext `sessionStorage` value (extension storage inspection, another privileged extension/content script with storage access, a local/forensic reader of the browser profile, or a future bug granting storage read access) obtains the exact passphrase needed to unlock the wallet and decrypt the encrypted seed via `seedStorage`/`secure-container`. This is a direct wallet-compromise/secret-disclosure vector, matching the "attacker with access to the configuration file... could steal the user's keyring information and hijack the... instance" impact in the original report, translated to "attacker with access to session storage could steal the passphrase and decrypt the wallet seed."

### Likelihood Explanation
This is enabled only when `cachePassphrase` config is turned on (opt-in feature, `application({ cachePassphrase: true })`), and the passphrase remains in plaintext for up to `passphraseCacheMaxTtl` (default 60 minutes) until inactivity-based expiry clears it: [8](#0-7) [9](#0-8) 
Since it depends on this feature being enabled and on an attacker having read access to the extension's session storage (not simply any unprivileged web page), likelihood is moderate rather than trivially remote-exploitable — but the underlying design flaw (storing a plaintext, wallet-unlocking secret with no encryption layer) directly mirrors the reported bug class.

### Recommendation
- Encrypt the cached passphrase at rest (e.g., wrap it with a derived, ephemeral encryption key held only in memory) rather than storing it as plaintext in `sessionStorage`.
- Document the security tradeoffs of enabling `cachePassphrase` clearly for integrators, similar to the recommendation to document risks of storing keyring passwords in config files.
- Consider reducing the default TTL and clearing the cache proactively on any signal of increased risk (e.g., extension update, permission change).

### Proof of Concept
1. Configure the SDK with `application({ cachePassphrase: true })`.
2. Call `exodus.application.unlock({ passphrase })`; this invokes `Application#unlock`, which calls `this.#passphraseCache.set(opts.passphrase)`: [10](#0-9) 
3. Inspect the underlying `chrome.storage.session` (or fallback in-memory store) — the value stored under key `passphrase` is the raw plaintext wallet passphrase, retrievable by anything with read access to that storage namespace, as shown by `PassphraseCache.set`/`get`: [11](#0-10) 
4. That passphrase can then be used directly against `wallet.unlock({ passphrase })` / `seedStorage.get(key, { passphrase })` to decrypt the seed, fully compromising the wallet.

    this.#logger.log('caching passphrase')
    const ttl = await this.#getTtl()

  async get() {
    const [passphrase, addedAt, inactiveAt, ttl] = (await this.#storage.batchGet([
      PASSPHRASE_KEY,
      ADDED_AT_KEY,
      INACTIVE_AT_KEY,
      TTL_KEY,
    ])) as [string, number, number, number]

    if (passphrase) {
      if (inactiveAt) {
        if (inactiveAt + ttl > Date.now()) {
          this.#logger.log('fetched cached passphrase, in activity period')
          return passphrase
        }
      } else if (addedAt + this.#maxTtl > Date.now()) {
        this.#logger.log('fetched cached passphrase')
        return passphrase
      }

      this.#logger.log('fetched expired passphrase, clearing and preventing unlock')
      void this.clear()
    }

  }
