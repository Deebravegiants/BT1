## Title
PoA Bridge `describeWithdrawal()` misreports status/tx-hash for batched same-asset withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal()` resolves the on-chain outcome of a specific withdrawal (identified by `index` within a NEAR transaction) by calling `findMatchingWithdrawal()`, which matches API results **only by `assetId`**, ignoring the `index` that was passed in. If a single NEAR transaction contains more than one withdrawal intent for the same token (a batch of same-asset withdrawals, e.g. to two different destination addresses/amounts), every `describeWithdrawal()` call for that transaction returns the **first** matching record from the PoA bridge API, regardless of which `index` was actually requested.

### Finding Description
`waitForWithdrawalCompletion` / `createWithdrawalCompletionPromises` in the SDK track each withdrawal by `index`, promising `promises[i]` corresponds to `withdrawalParams[i]` [1](#0-0) . For PoA-bridge-routed withdrawals, the actual on-chain status lookup ignores this index: [2](#0-1) 

The matching helper explicitly documents that it can't distinguish multiple same-token withdrawals in one transaction: [3](#0-2) 

Because `Array.prototype.find` returns the first array element satisfying the predicate, if a NEAR tx contains withdrawal index 0 (token X → address A, amount 100) and index 1 (token X → address B, amount 200), calling `describeWithdrawal({index: 1, ...})` returns the **same** `withdrawal` record (index 0's) as `describeWithdrawal({index: 0, ...})` — same `status` and same `data.transfer_tx_hash`. This is confirmed by the test file itself, which asserts "matches withdrawal by assetId, not by index" [4](#0-3)  — the test only covers the case of two *different* assets, not two same-asset withdrawals in one tx, which is the actually broken case per the function's own doc comment.

This breaks the equality the SDK is supposed to guarantee: **status/txHash reported for withdrawal `i` == the on-chain outcome of withdrawal `i`.** Instead, for a batch of same-token withdrawals, all indices resolve to the outcome of whichever record the unordered API response lists first.

### Impact Explanation
An integrator that polls `describeWithdrawal`/`waitForWithdrawalCompletion` per index to decide when to credit/refund a specific batched withdrawal could:
- Mark withdrawal `index: 1` as `"completed"` with a `txHash` that actually belongs to withdrawal `index: 0` (or vice versa), before/without the real withdrawal for index 1 landing on-chain — a **hash/status misreport that can cause a double credit** (crediting a destination based on a transaction hash that doesn't correspond to that specific withdrawal), or crediting a withdrawal as complete while its real destination transfer is still pending or failed.
- This falls under the accepted "High" impact category: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
Triggering this requires an ordinary, unprivileged user (or integrator building the intent) to submit multiple `ft_withdraw` intents for the **same PoA token** within a single signed NEAR transaction — a normal batched-withdrawal use case explicitly supported by the SDK's batch APIs (`createWithdrawalCompletionPromises`). No malicious relayer, admin, or bridge-operator behavior is needed; the bug is purely in client-side result matching against the PoA bridge's unordered API response.

### Recommendation
Match withdrawals using more than `assetId`: include `destinationAddress` and `amount` (and/or an ordering/dedup strategy sorted deterministically on both sides, as the code comment itself suggests) so that each `index` deterministically maps to its own on-chain record. At minimum, when multiple withdrawals with the same `assetId` are detected in a batch, the SDK should refuse to resolve status per-index rather than silently returning a possibly-wrong record.

### Proof of Concept
1. Build and sign a NEAR intent containing two `ft_withdraw` primitives for the same PoA token (e.g., `nep141:btc.omft.near`) with different destination addresses/amounts, submitted in a single transaction.
2. Call `bridge.createWithdrawalIdentifier({ withdrawalParams: paramsForIndex1, index: 1, tx })` then `bridge.describeWithdrawal(...)`.
3. Mock/observe the PoA bridge `getWithdrawalStatus` response containing two `COMPLETED` withdrawal records for that `assetId` (as in the existing test at lines 1054-1111, but with both records sharing the same `near_token_id`).
4. Observe that `describeWithdrawal` for `index: 1` returns the same `status`/`transfer_tx_hash` as `index: 0`, per `findMatchingWithdrawal`'s `.find()` on `assetId` alone [5](#0-4) .

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
