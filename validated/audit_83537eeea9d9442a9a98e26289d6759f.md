Based on the codebase, I found a genuine structural analog to the "conditional flag gates essential verification" bug class described in the report.

### Title
Signup success is granted without backend enrollment/uniqueness verification when `user_centric_signup` is true - (File: `src/plans/mod.rs`)

### Summary
In the GLP report, `shouldBuyGLP` is a flag that, when false, causes the strategy to skip a step (buying more GLP with pending rewards) that is required for withdrawals to succeed reliably. In orb-core's `do_signup` flow, an analogous pattern exists: a flag combination (`user_centric_signup` from the QR/app data, gated by the orb config `ignore_user_centric_signups`) causes the orb to skip the step that performs actual backend-side enrollment/verification (`enroll_user`), and instead grants signup success purely from local, in-process signals.

### Finding Description
In `MasterPlan::do_signup`, after the biometric pipeline runs and (attempted) fraud detection completes, the orb branches on `user_centric_signup` and the config flag `ignore_user_centric_signups`: [1](#0-0) 

When `user_centric_signup` is `true` and `ignore_user_centric_signups` is `false` (the default, see `Config::ignore_user_centric_signups`), the code **never calls `enroll_user`** — the plan that actually talks to the backend to submit the signup and poll for verification/uniqueness results: [2](#0-1) 

Instead, success is derived solely from the locally computed `signup_reason`, which itself depends on the on-orb `detect_fraud` step. In this build, that step is explicitly neutered: [3](#0-2) 

Compare this to the case where `enroll_user` *is* called — it submits the signup to the backend and polls for a `Completed` response, where a `success: false` result explicitly represents "Backend duplicates", "Backend inflight matches", or "Backend detected fraud": [4](#0-3) 

So the backend-side duplicate/uniqueness detection that `enroll_user` provides is entirely bypassed for the `user_centric_signup` path, mirroring the GLP bug class where a boolean flag gates a step whose absence removes a safety/correctness guarantee (there: sufficient GLP for withdrawal; here: backend duplicate/fraud verification for enrollment).

The `user_centric_signup` value itself originates from signed app data returned by the backend/app during QR scanning: [5](#0-4) 

### Impact Explanation
If `user_centric_signup` is true for a given signup (set by the app/backend-signed QR data) and the orb's `ignore_user_centric_signups` config is false (default), the orb marks the signup as `Success` without ever submitting it to the backend enrollment endpoint that performs cross-signup duplicate/fraud matching. Combined with the local `detect_fraud` being a no-op in this build, a signup can be recorded as successful — and its personal custody package uploaded — without any actual server-side dedup/fraud verification ever having occurred. This is a concrete "unauthorized or misattributed signup" class impact: the backend never gets to reject a duplicate or fraudulent enrollment because the orb-side branch never calls it in the first place.

### Likelihood Explanation
This path is reachable whenever the backend/app marks a user QR-code payload as `user_centric_signup: true`, which is a backend-controlled, non-privileged-user-triggerable condition — the same likelihood class as the original report's "flag set by the owner"; here it's set/returned by backend-issued/signed data rather than requiring any exploit of trust boundaries by an unprivileged party, but it directly determines whether backend verification is bypassed for a given signup.

### Recommendation
Do not treat `user_centric_signup` as a bypass for backend verification. Either:
1. Always route signups through `enroll_user` (backend `signup_post`/`signup_poll`) regardless of `user_centric_signup`, using the result to gate success, or
2. If a user-centric flow must skip the classic enrollment endpoint, ensure an equivalent backend round-trip verification (uniqueness/fraud check) is mandatorily performed and its result — not just local pipeline signal — is required for `success = true`.

### Proof of Concept
1. Backend/app returns `orb_qr_link::UserData { user_centric_signup: true, .. }` for a QR-code scan (`src/backend/user_status.rs`).
2. Orb config has `ignore_user_centric_signups = false` (default).
3. In `do_signup` (`src/plans/mod.rs:639-645`), since `detect_fraud` always returns `false` (line 1390-1406) and `pipeline` is `Some`, `signup_reason == SignupReason::Normal`.
4. `success = true` is set without ever calling `enroll_user::Plan::run`, so the backend `signup_post`/`signup_poll` duplicate/fraud check (`src/plans/enroll_user.rs:146-176`) never executes for this signup, yet the signup is recorded as successful and its PCP uploaded.

    async fn enroll_user(
        &mut self,
        orb: &mut Orb,
        debug_report: &mut debug_report::Builder,
        capture: &biometric_capture::Capture,
        pipeline: Option<&biometric_pipeline::Pipeline>,
        signup_reason: SignupReason,
    ) -> enroll_user::Status {
        orb.set_phase("User enrollment").await;
        let t = Instant::now();
        let status = Box::pin(
            enroll_user::Plan {
                signup_id: debug_report.signup_id.clone(),
                operator_qr_code: debug_report.operator_qr_code.clone(),
                user_qr_code: debug_report.user_qr_code.clone(),
                s3_region_str: self.s3_region_str.clone(),
                capture,
                pipeline,
                signup_reason,
            }
            .run(orb),
        )
        .await;
        dd_timing!("main.time.signup.user_enrollment", t);

        debug_report.enrollment_status(status.clone());
        status
    }
