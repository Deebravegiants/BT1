### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated once `Utils::HmacValidator.validate(request)` succeeds, but the HMAC only signs the raw request body. The `shop` (tenant) attribute that the library extracts from the `X-Shopify-Shop-Domain`/`Shopify-Shop-Domain` header and hands to the app's handler is never included in the signed content, so it can be freely set by anyone able to produce one valid body+HMAC pair for the app (e.g. a merchant who has installed the app on their own store).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` returns the decoded `hmac-sha256` header value: [1](#0-0) 

`shop` is read straight from an unauthenticated header: [2](#0-1) 

`Registry.process` validates the HMAC and then forwards `request.shop` directly to the app's handler as the identity of the tenant the webhook belongs to: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` only ever checks `verifiable_query.to_signable_string` (the raw body) against the HMAC secret — the shop header plays no part in the signature: [4](#0-3) 

This breaks the identity binding: `shop header verified == shop header used to attribute the event`. In reality, the gem only proves *"this body was HMAC-signed with this app's secret"*; it does not prove *"this body came from the shop named in this header."* Because a single app typically shares one `api_secret_key` across every shop that installs it, any user who legitimately installs the app on their own store (an unprivileged tenant) can capture one valid `(raw_body, hmac)` pair for their own shop's webhook delivery and replay it to the app's webhook endpoint with an arbitrary `Shopify-Shop-Domain` header, since that header is not part of the signed payload. The HMAC will still validate because the body/HMAC pair is legitimately signed with the shared secret, but `request.shop` — and therefore `WebhookMetadata#shop` delivered to the app handler — can be forged to any target shop domain.

The library's own documentation confirms that `data.shop` is meant to be trusted by the handler as the identifying tenant, and that `Registry.process` is expected to "verify the request did indeed come from Shopify": [5](#0-4) [6](#0-5) 

Yet the verification step never binds the shop identity to the signature, so any host application following the documented pattern (using `data.shop` to route/attribute webhook side effects, exactly as shown in the docs' own example `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) inherits a cross-tenant spoofing hole purely from this gem's verification logic.

### Impact Explanation
This allows cross-tenant confusion/attribution: a legitimate but unprivileged installer of the app can cause the app to process a webhook body while it believes the event originated from a different, victim shop. Depending on what the host app does with `data.shop` (e.g. looking up the victim's stored session/access token to react to the "event", updating victim-shop records, triggering victim-scoped side effects), this can lead to cross-tenant data corruption or actions being taken against another merchant's store context using the attacker-controlled body content. This matches the Critical "cross-tenant access" impact category since the binding between an authenticated payload and the tenant it is attributed to is broken.

### Likelihood Explanation
High. The attacker does not need the app's `api_secret_key`, an access token, or any privileged access — only a normal, legitimate installation of the target app on their own shop (any merchant can install a public app), from which they can capture one valid webhook delivery (raw body + `hmac-sha256` value) and replay it to the app's public webhook endpoint with a forged `Shopify-Shop-Domain` header. This is fully reachable through this gem's own documented `Registry.process`/`Request` API.

### Recommendation
Bind the shop identity into the verified data instead of trusting an unauthenticated header:
- Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed content, or
- After validating the body HMAC, cross-check the `Shopify-Shop-Domain` header against a shop that the app already has an active, previously-established session/webhook registration for that specific `webhook_id`/topic combination, rather than blindly trusting the header value, or
- At minimum, document prominently that `Request#shop` is NOT covered by the HMAC and must not be used by host applications as a trusted tenant identifier without additional verification (e.g. matching against `session.shop` used at registration time).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers a registered webhook topic (e.g. `orders/create`) legitimately, capturing the raw POST body and the `Shopify-Hmac-Sha256` header Shopify sent to the app's callback endpoint.
2. Attacker resends that exact same raw body and `Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged shop header; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the shared secret — the shop header was never part of the signature.
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the host app to process the attacker's webhook content as if it originated from the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
