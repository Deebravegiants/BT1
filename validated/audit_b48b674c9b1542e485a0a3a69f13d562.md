## Title
Webhook shop identity spoofing via HMAC that only covers the body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
The gem's webhook processing validates the Shopify HMAC signature only over the raw request body, while the `shop` (tenant identity) delivered to the app's webhook handler is taken from an HTTP header that is never included in the signed bytes. This breaks the identity binding `hmac(body) == hmac(body)` versus the actually-trusted value `shop_header == shop_claimed`, letting anyone who can obtain one legitimately-signed webhook payload (e.g. from their own shop) replay it against a victim shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signable string at all: [2](#0-1) [3](#0-2) 

`ShopifyAPI::Webhooks::Registry.process` validates only the HMAC over the body, then constructs the handler payload directly from the unauthenticated header value: [4](#0-3) 

The HMAC secret (`Context.api_secret_key`) is shared across every shop the app is installed on — it is not per-tenant. Since `shop-domain` is excluded from `to_signable_string`, a given `(raw_body, hmac)` pair remains valid no matter which `shop-domain` header accompanies it. This is the exact "field acted on but not covered by the HMAC" identity-binding break: the equality that should hold is `verified(shop) == trusted(shop)`, but what is actually verified is only `verified(body)`, while `shop` is trusted unconditionally.

### Impact Explanation
An attacker who legitimately installs the target app on their own store (or otherwise receives one authentic webhook delivery, which merely requires an ordinary, unprivileged install — not the app's `client_secret` or any merchant token) obtains a valid `(raw_body, hmac)` pair signed with the app's shared secret. They can replay this exact body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for any victim shop domain. `Registry.process` will accept it as authentic and dispatch `WebhookMetadata` claiming to be from the victim's shop, with attacker-controlled body content. Any host application that trusts the `shop` field from `WebhookMetadata` to look up/act on tenant-specific data (the intended and documented use of this field) is now driven by an attacker-controlled tenant identity — a cross-tenant access primitive.

### Likelihood Explanation
Any developer or user able to install the app on an unprivileged shop of their own can generate valid `(body, hmac)` pairs at will (e.g. by triggering webhook-eligible events on their own store), and only needs to alter one HTTP header on replay. No secret material, token theft, or privileged access is required — only the standard client-facing surface of the gem's webhook receiver.

### Recommendation
Bind the tenant identity into the signed material, or otherwise cryptographically tie the `shop-domain` header to the same secret used for the HMAC before trusting it, e.g. include `shop`/`topic`/`webhook-id` in `to_signable_string` (matching what is actually verified), or independently confirm the `shop` value returned by `Registry.process` corresponds to a session/shop that the recipient app expects for this specific webhook subscription before dispatching to the handler.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger a webhook event and capture the raw POST body and its `X-Shopify-Hmac-Sha256` header — both are valid because they are signed with the app's shared `api_secret_key`.
2. Replay the request to the app's webhook endpoint, keeping the body and HMAC identical, but replacing `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(raw_body, secret)`: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and the attacker-controlled body, even though the request never originated from Shopify for that shop.
