The OAuth `AuthQuery` correctly includes `shop` in `to_signable_string` (line 35-41 above), but the webhook `Request` class does **not** — its `to_signable_string` only returns the raw body, excluding `shop`, `topic`, `webhook_id`, and `api_version` from the HMAC-covered bytes.### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` when computing the HMAC digest that `Utils::HmacValidator.validate` checks against the `X-Shopify-Hmac-Sha256` header. The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read straight from unauthenticated HTTP headers and are never included in the bytes that are HMAC-verified, yet they are passed directly into `WebhookMetadata` and handed to the host app's `WebhookHandler#handle`.

### Finding Description
`Utils::HmacValidator.validate` verifies a request by recomputing `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` with the app's `client_secret` and comparing it (via `OpenSSL.secure_compare`) to the `hmac` accessor: [1](#0-0) 

For OAuth callbacks, `Auth::Oauth::AuthQuery#to_signable_string` correctly folds `shop` into the signed payload alongside `code`, `host`, `state`, `timestamp`: [2](#0-1) 

But `Webhooks::Request`, which also implements `Utils::VerifiableQuery`, only signs the raw body: [3](#0-2) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers that are merely checked for *presence*, never bound to the signature: [4](#0-3) [5](#0-4) 

`Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to build `WebhookMetadata` and dispatch to the registered handler: [6](#0-5) 

`WebhookMetadata` carries `shop` as a plain, unauthenticated `String` field that host applications use as the tenant identifier for the incoming webhook: [7](#0-6) 

This breaks the intended binding: `HMAC-verified bytes == bytes the handler trusts as this shop's data`. In reality, `HMAC-verified bytes (body only) != identity-bearing bytes (shop header) that the handler treats as authoritative`. Because Shopify signs webhooks with the app's single `client_secret` shared across all shops installing that app, any body+HMAC pair that is valid for one shop is *also* a valid HMAC for the identical body regardless of which `X-Shopify-Shop-Domain` header accompanies it — the signature says nothing about which shop the payload belongs to.

### Impact Explanation
An unprivileged internet user who can capture (or otherwise obtain) one legitimately-signed webhook delivery (body + valid HMAC) for any shop using the target app — e.g., by installing/uninstalling a trial/dev store connected to the same app, or intercepting/observing a webhook whose body content is shop-independent (such as `app/uninstalled`, `shop/redact`, or any webhook with an identical/predictable JSON body) — can replay that exact body and HMAC to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` header to name a different, victim shop. `HmacValidator.validate` will accept it because the signature only covers the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the victim shop's identity. If the host application's handler uses `data.shop` to look up the session/tenant record and act on it (the documented, expected usage pattern of this gem), this results in cross-tenant webhook injection — the classic case of "shop authenticated versus the shop trusted downstream" not being equal. This is a cross-tenant access vector as scoped by the rules.

### Likelihood Explanation
Exploitability depends on the attacker being able to obtain at least one validly-signed body/HMAC pair for some shop connected to the same app (e.g., by installing the target app on their own free/dev store, which is realistically available to any unprivileged user for public apps), and on webhook bodies that don't intrinsically encode the true shop identity elsewhere that the handler independently checks. Many mandatory/compliance webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) and lifecycle webhooks (`app/uninstalled`) have small, attacker-observable bodies, making this a realistic and low-effort path once the attacker controls one app installation.

### Recommendation
Include the identity-bearing headers (`shop`, and ideally `topic`/`webhook_id`) in the HMAC-signed payload, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` into its signature. Since Shopify's actual HMAC computation for webhooks is body-only by protocol, the gem should not silently expose `shop`/`topic` as unauthenticated, trusted accessors on a class that implements `VerifiableQuery` (implying "verified") — at minimum, the gem's documentation and `WebhookMetadata` should make explicit that `shop`/`topic`/`webhook_id` are unauthenticated header values, and host apps must independently verify that the claimed `shop` actually has this app installed / matches an existing session before acting on webhook data keyed by it.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store (`attacker-shop.myshopify.com`), which is possible for any public app.
2. Attacker triggers a webhook with a small, content-independent body, e.g. `app/uninstalled`, and captures the raw request: body `{}` (or similar) and its valid `X-Shopify-Hmac-Sha256` value, computed by Shopify using the app's real `client_secret`.
3. Attacker resends this exact body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Request.new` accepts the forged headers (only checks presence, not authenticity) — [8](#0-7) .
5. `Utils::HmacValidator.validate` succeeds because it only hashes `@raw_body`, which is unchanged — [3](#0-2) .
6. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and invokes the host app's handler as if Shopify itself reported that `victim-shop` uninstalled the app — [6](#0-5) .
