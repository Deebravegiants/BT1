Audit Report

## Title
`Pallet::payout` unconditionally rejects any account that already carries a `pallet_vesting` schedule, letting a user (or a third-party griefer) permanently trap an already-approved purchase payout - ([File: polkadot/runtime/common/src/purchase/mod.rs])

## Summary
`payout` re-checks `T::VestingSchedule::vesting_balance(&who).is_none()` before crediting a purchaser, and this check occurs before the `Accounts::<T>::try_mutate` block that finalizes the purchase. Because `pallet_vesting::vested_transfer` is a normal, unprivileged extrinsic that can target any account, an attacker (including the victim's own account, or an unrelated third party) can create a vesting schedule on the target account between the time `update_balance` fixes the entitlement and the time `PaymentAccount` calls `payout`, permanently blocking `payout` until that unrelated vesting schedule is cleared via a separate `vest`/`vest_other` call.

## Finding Description
The purchase flow is `create_account` -> `update_validity_status` -> `update_balance` -> `payout`, with `payout` restricted to the fixed `PaymentAccount` origin. [1](#0-0) 
`create_account` checks for an absent vesting schedule at account-creation time. [2](#0-1) 
However, neither `update_validity_status` nor `update_balance` re-verifies this condition. [3](#0-2) 
`payout` performs the same `vesting_balance(&who).is_none()` guard again, and this `ensure!` executes before the `Accounts::<T>::try_mutate` block that transfers funds and sets `status.validity = AccountValidity::Completed`. [4](#0-3) 

Since `pallet_vesting::vested_transfer` is an ordinary signed extrinsic with no origin restriction tying it to the purchase pallet, any account can create a `Vesting` storage entry for the target `who` in the window between `update_balance` and `payout` being called (a separate, later transaction executed by `PaymentAccount`). Because `vesting_balance` returns `Some(_)` for any account holding a `Vesting` entry — regardless of whether the computed locked amount is currently zero — and that entry is only removed by an explicit `vest`/`vest_other` call once fully elapsed, the account can be kept perpetually "vesting" by an attacker choosing an appropriately long schedule, or simply left unresolved by anyone failing to call `vest`. There is no code path in the purchase pallet allowing `PaymentAccount` or `ConfigurationOrigin` to force through the payout or clear this externally created state.

## Impact Explanation
This is an in-scope griefing/DoS vulnerability against the purchase pallet's core guarantee that an approved and funded participant will eventually receive their payout. The `free_balance`/`locked_balance` recorded in `Accounts<T>` remains stuck (validity never reaches `Completed`) for as long as an attacker-controlled `Vesting` entry exists on the target account, and this state is fully reachable using an ordinary unprivileged `vested_transfer` targeting any account, not just the caller's own. This matches a legitimate self-DoS/third-party-griefing impact class rather than a purely theoretical issue, since the check sequence, the lack of any bypass, and the externally-triggerable precondition are all clearly present in the code as cited.

## Likelihood Explanation
The attack requires no privileged access: `pallet_vesting::vested_transfer` only needs a signed origin and satisfying `MinVestedTransfer`. The purchase-side steps (`create_account`, `update_validity_status`, `update_balance`) are performed by `ValidityOrigin` as part of the normal onboarding flow, and `payout` is a distinct later transaction, giving a realistic window for an attacker to insert a `vested_transfer` in between. No race at the block level or special privilege is needed — an attacker (or an aggrieved user seeking to self-sabotage, or any third party wanting to block another user's payout) can trigger this deterministically and repeatably by choosing a sufficiently long vesting schedule.

## Recommendation
Do not treat pre-existing vesting schedules as an unconditional hard blocker inside `payout`. Reasonable fixes include: removing the redundant `vesting_balance` check from `payout` and having `add_vesting_schedule` merge with (rather than error on) any pre-existing schedule using the currency's existing multi-schedule support; transferring the `free_balance` portion unconditionally regardless of vesting state and only gating the locked/vesting portion on the check; or exposing an explicit call (self-service or privileged) that allows re-attempting/merging the payout once a schedule exists, so a legitimately owed balance is never left gated behind unrelated, externally controlled pallet state.

## Proof of Concept
1. `ValidityOrigin` calls `create_account`, `update_validity_status(who, ValidLow)`, and `update_balance(who, free, locked, vat)` for `who`.
2. Any account (e.g. `who` itself, or an unrelated attacker) calls `Vesting::vested_transfer(origin, who, VestingInfo::new(min_transfer, 1, current_block))`, creating a `Vesting` entry for `who`.
3. `PaymentAccount` calls `Purchase::payout(origin, who)`.
4. The call fails with `Error::<T>::VestingScheduleExists` per the check at `polkadot/runtime/common/src/purchase/mod.rs` lines 312-316, and `Accounts::<T>::get(who)` retains its pre-payout state (`validity` not `Completed`, unchanged `free_balance`/`locked_balance`).
5. Repeating `payout` continues to fail until the externally created vesting entry is cleared via a separate `vest`/`vest_other` call, which is outside the purchase pallet's control and can be delayed arbitrarily by the schedule parameters chosen in step 2.

		pub fn payout(origin: OriginFor<T>, who: T::AccountId) -> DispatchResult {
			// Payments must be made directly by the `PaymentAccount`.
			let payment_account = ensure_signed(origin)?;
			let test_against = PaymentAccount::<T>::get().ok_or(DispatchError::BadOrigin)?;
			ensure!(payment_account == test_against, DispatchError::BadOrigin);

			// Account should not have a vesting schedule.
			ensure!(
				T::VestingSchedule::vesting_balance(&who).is_none(),
				Error::<T>::VestingScheduleExists
			);

			Accounts::<T>::try_mutate(
				&who,
				|status: &mut AccountStatus<BalanceOf<T>>| -> DispatchResult {
					// Account has a valid status (not Invalid, Pending, or Completed)...
					ensure!(status.validity.is_valid(), Error::<T>::InvalidAccount);

					// Transfer funds from the payment account into the purchasing user.
					let total_balance = status
						.free_balance
						.checked_add(&status.locked_balance)
						.ok_or(Error::<T>::Overflow)?;
					T::Currency::transfer(
						&payment_account,
						&who,
						total_balance,
						ExistenceRequirement::AllowDeath,
					)?;

					if !status.locked_balance.is_zero() {
						let unlock_block = UnlockBlock::<T>::get();
						// We allow some configurable portion of the purchased locked DOTs to be
						// unlocked for basic usage.
						let unlocked = (T::UnlockedProportion::get() * status.locked_balance)
							.min(T::MaxUnlocked::get());
						let locked = status.locked_balance.saturating_sub(unlocked);
						// We checked that this account has no existing vesting schedule. So this
						// function should never fail, however if it does, not much we can do about
						// it at this point.
						let _ = T::VestingSchedule::add_vesting_schedule(
							// Apply vesting schedule to this user
							&who,
							// For this much amount
							locked,
							// Unlocking the full amount after one block
							locked,
							// When everything unlocks
							unlock_block,
						);
					}

					// Setting the user account to `Completed` ends the purchase process for this
					// user.
					status.validity = AccountValidity::Completed;
					Self::deposit_event(Event::<T>::PaymentComplete {
						who: who.clone(),
						free: status.free_balance,
						locked: status.locked_balance,
					});
					Ok(())
				},
