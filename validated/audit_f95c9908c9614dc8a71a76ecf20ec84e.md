### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, while the HMAC signature that `Utils::HmacValidator` verifies only covers the raw request body. Because the app's `client_secret` (via `Context.api_secret_key`) is the same across all shops installed on the app, any actor who can obtain one genuine `(raw_body, hmac)` pair (e.g. from their own store's webhook deliveries) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, and the registry will treat the request as an authenticated webhook from the spoofed shop.

### Finding Description
`Request#hmac` and `Request#to_signable_string` only operate on `@raw_body`: [1](#0-0) 

but `Request#shop` is read straight from the header and is never included in the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC of the body and, on success, unconditionally trusts `request.shop` as the tenant for the handler: [3](#0-2) 

This breaks the identity binding: `hmac == HMAC(secret, raw_body)` is verified, but the tenant field consumed by the application (`request.shop`, exposed to the handler as `WebhookMetadata.shop`) is **not** part of what was verified. Since `Context.api_secret_key` is a single per-app secret shared across every shop that installs the app (not a per-shop secret), a valid `(raw_body, hmac)` pair computed for one shop remains valid when replayed with a different `shop-domain` header — the signature check in `Utils::HmacValidator.validate_signature` has no way to detect the mismatch: [4](#0-3) 

### Impact Explanation
Any unprivileged party who can trigger a webhook to their own installed shop (trivial — install the app on a test/dev store and let Shopify send any webhook) obtains a genuine `(raw_body, hmac)` pair signed with the app's shared secret. They can then replay that identical body/HMAC to the app's webhook endpoint while setting `x-shopify-shop-domain` to any other victim shop domain known to be using the app. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` claiming to be from the victim shop, with attacker-controlled body content. Any host application that uses `WebhookMetadata.shop` to select which tenant's data to update (a documented, intended use of this field) can be made to write/act on a different tenant's records — this is cross-tenant access driven entirely by an identity field this gem fails to bind to its own signature check.

### Likelihood Explanation
The only prerequisite is having the app installed on any store (including the attacker's own), which is the normal, unprivileged way any merchant obtains app access — no leaked secrets, tokens, or privileged access are required. Getting one legitimate webhook delivery and replaying it with a modified header is straightforward and repeatable for any topic/body shape the attacker wants to construct on their own store first.

### Recommendation
Include the shop domain (and ideally webhook id/topic) inside the signed payload verification, or otherwise cryptographically bind `Request#shop` to the HMAC-verified content instead of trusting the header value independently. At minimum, document prominently that `WebhookMetadata.shop`/`Request#shop` is unauthenticated header data and must never be used by host applications as the sole tenant selector without additional verification (e.g., cross-checking against a shop this app installation is known to be registered for).

### Proof of Concept
1. Install the target app on `attacker.myshopify.com`; trigger any webhook topic the app subscribes to. Capture the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent — this HMAC is `HMAC-SHA256(app_client_secret, raw_body)`, and `app_client_secret` is identical for every shop using this app installation.
2. Replay the exact same HTTP request to the app's webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` unchanged, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, raw_body)` — unaffected by the header change — and passes: [5](#0-4) 
4. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-chosen `body`, despite the request never being generated for or authorized by `victim-shop`.
