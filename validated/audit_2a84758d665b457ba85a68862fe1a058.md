### Title
`deposit()` can silently mint zero shares for a non‑zero deposit, permanently freezing the depositor's principal - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and sibling vault contracts `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`)

### Summary
Every Zest v2 vault's `deposit()` function computes the shares to mint via `convert-to-shares-preview`, which performs plain proportional division `amount * total-supply / total-assets` with no minimum-output guard. Unlike `redeem()`, which explicitly asserts `(> inkind u0) ERR-OUTPUT-ZERO`, `deposit()` has no equivalent check, so a deposit whose computed share amount rounds down to `0` still executes successfully as long as `min-out` is `0`, permanently absorbing the depositor's underlying assets into the vault without minting any `zft` shares in return.

### Finding Description
`convert-to-shares-preview` in each vault (e.g. `v0-vault-usdc.clar`) computes: [1](#0-0) 

```
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
```

This is floor division with no mantissa/precision scaling: once the share price (`ta / ts`) exceeds `1`, any deposit `amount` smaller than the share price in base units yields `inkind = 0`.

`deposit()` then only validates: [2](#0-1) 

```
(define-public (deposit (amount uint) (min-out uint) (recipient principal))
    (let (
      ...
      (inkind (convert-to-shares-preview amount)))
    (asserts! (not (get deposit states)) ERR-PAUSED)
    (asserts! (var-get initialized) ERR-INIT)
    (asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)
    (asserts! (>= inkind min-out) ERR-SLIPPAGE)
    (asserts! (<= (+ current-assets amount) CAP-SUPPLY) ERR-SUPPLY-CAP-EXCEEDED)

    (try! (receive-underlying amount account))
    (try! (ft-mint? zft inkind recipient))
    (var-set assets (+ current-assets amount))
    ...
    (ok inkind)))
```

There is no `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)`. If the caller supplies `min-out = 0` (the default when no explicit minimum is desired), the `>= inkind min-out` check passes trivially even when `inkind` is `0`. The vault then: transfers the underlying `amount` into the contract via `receive-underlying`, mints `0` shares to `recipient` via `ft-mint? zft inkind recipient`, and increases `assets` by the full deposited `amount`.

Contrast this with `redeem()` in the same file, which does defensively check for a zero output: [3](#0-2) 

```
  (asserts! (>= current-assets inkind) ERR-INSUFFICIENT-ASSETS)
  (asserts! (not (get redeem states)) ERR-PAUSED)
  (asserts! (> amount u0) ERR-AMOUNT-ZERO)
  (asserts! (> inkind u0) ERR-OUTPUT-ZERO)
  (asserts! (>= inkind min-out) ERR-SLIPPAGE)
```

This asymmetry means the withdrawal path is protected from a silent zero-value transfer while the deposit path is not — this is exactly the bug class described in the referenced report: division that can zero out the number of shares/tokens owed to a depositor because the conversion lacks a floor/output-zero guard.

The value identity broken is:
```
sum(user shares) * (total-assets / total-supply) == total-assets deposited by users
```
After a zero-share deposit of `amount > 0`, `total-assets` increases by `amount` but `total-supply` (and the depositor's share balance) does not increase. The depositor's `amount` is absorbed into the vault's asset pool with no corresponding `zft` claim — a permanent, unrecoverable loss of that user's principal, and a proportional windfall to all existing shareholders' redemption value.

### Impact Explanation
This qualifies as **High – temporary/permanent freezing of funds**: a depositor's underlying assets become permanently unclaimable (no shares exist to redeem them) whenever the share price (`total-assets / total-supply`) has risen enough (post interest accrual) that a deposit amount rounds down to zero shares under `mul-div-down`. Because none of the vault deposit paths clamp `min-out` to a nonzero default, and nothing in the public interface forces `min-out > 0`, this can occur silently in normal operation for any user (or wallet/integration) that does not explicitly set a nonzero slippage floor, especially on lower-decimal underlying assets such as `sbtc` (8 decimals) or `ststxbtc`.

### Likelihood Explanation
The likelihood is moderate: it requires (a) the vault to have accrued enough interest that share price exceeds 1 base unit of the underlying, and (b) a depositor/integration to call `deposit` with `min-out = 0` and an `amount` smaller than the current share price. Both conditions are realistic over the lifetime of an interest-bearing vault, and many front ends/scripts default `min-out` to `0` for convenience, making accidental triggering plausible without any special privilege.

### Recommendation
Add an explicit zero-output guard to `deposit()` symmetric to the one already present in `redeem()`:
```
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed alongside the existing `ERR-SLIPPAGE` check in every vault contract (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`), so that a deposit whose computed shares round to zero always reverts instead of silently absorbing the depositor's principal.

### Proof of Concept
1. Let a vault accrue interest such that `total-assets-preview() / total-supply-preview() > 1` (price per share > 1 base unit), e.g. `ta = 150`, `ts = 100` (price = 1.5).
2. A user calls `deposit(amount=1, min-out=0, recipient=user)`.
3. `convert-to-shares-preview(1) = mul-div-down(1, 100, 150) = floor(100/150) = 0`.
4. `deposit()` checks: `amount(1) > 0` ✔, `inkind(0) >= min-out(0)` ✔ (passes because min-out is 0), supply cap check ✔.
5. `receive-underlying` pulls `1` unit of underlying from the user into the vault; `ft-mint? zft 0 recipient` mints zero shares; `assets` is incremented by `1`.
6. The user now holds `0` additional `zft` shares but has permanently transferred `1` unit of underlying into the vault's `assets`, which is unrecoverable by them and inflates the redemption value for all other shareholders. [2](#0-1) [3](#0-2)
