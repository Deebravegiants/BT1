### Title
Cross-tenant webhook confusion: `shop`, `topic`, and `webhook_id` in `Webhooks::Request` are not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating that `Utils::HmacValidator.validate(request)` succeeds, then trusts `request.shop`, `request.topic`, and `request.webhook_id` — all sourced from HTTP headers — to dispatch the payload to the handler as the tenant identity. However, the HMAC signature only covers the raw request body, not these header-derived fields.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version`, by contrast, are read straight from unauthenticated headers (`x-shopify-shop-domain`, `x-shopify-topic`, etc.), with no cryptographic binding to the signed body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` uses this single check as the sole gate before trusting the header-derived `shop` value and handing it to the app's handler as the tenant identity: [4](#0-3) 

The broken identity binding, stated as an equality that should hold but doesn't:
`shop` authenticated by the HMAC (none — HMAC only covers body bytes) ≠ `shop` used by the app to key per-tenant state (`WebhookMetadata#shop`, taken from the `x-shopify-shop-domain` header).

Because the HMAC secret (`Context.api_secret_key` / `client_secret`) is shared across all shops that install a given app (it's per-app, not per-shop), any unprivileged internet user who legitimately installs the target app on their own store receives real webhook deliveries with valid `(raw_body, hmac)` pairs for their own shop. Nothing in this gem prevents that same person from replaying that valid `(raw_body, hmac)` pair to the app's webhook endpoint while substituting a different value in the `x-shopify-shop-domain` header (and/or `x-shopify-topic`/`x-shopify-webhook-id`). `Utils::HmacValidator.validate` still succeeds (it never looks at those headers), and `Registry.process` passes the forged `shop`/`topic` straight into `WebhookMetadata`, which the app's handler is expected to trust to select the correct tenant record to mutate.

### Impact Explanation
This breaks the shop-authenticated vs. shop-used-as-tenant-key binding described in the rules, enabling cross-tenant data confusion: an attacker with only their own (legitimate) app installation can cause the app to process a webhook body under a victim shop's identity, or spoof the topic/webhook id fields for a payload the app never actually issued for that topic. Depending on how the host application persists/acts on webhook data keyed by `shop`, this can lead to writing or triggering actions against another merchant's tenant state — a cross-tenant access impact.

### Likelihood Explanation
Requires only an internet-reachable webhook endpoint (which by design is unauthenticated aside from the HMAC) and a legitimate install of the target app by the attacker on any shop to obtain one valid `(body, hmac)` pair to replay with altered headers. No access to `client_secret`, access tokens, or any Shopify-side secret is needed — only capturing/replaying traffic that legitimately reaches the attacker's own installation.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the signed material verified by `HmacValidator`, or otherwise independently authenticate the shop domain against the session/shop the webhook was registered for before dispatching to `WebhookMetadata`. At minimum, `Webhooks::Request#to_signable_string` should not be limited to `@raw_body`; the identity headers used downstream for tenant routing must be part of what the HMAC check validates, or the gem should document/enforce that consumers cross-check `shop` against known installed shops before trusting it.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store (`attacker-shop.myshopify.com`) and enables webhook delivery for some topic (e.g. `orders/create`).
2. Attacker captures one legitimate webhook POST from Shopify to their app endpoint, including the raw body and the `X-Shopify-Hmac-Sha256` header (a valid `(raw_body, hmac)` pair, since they own the endpoint/proxy).
3. Attacker resends this exact `raw_body` and `X-Shopify-Hmac-Sha256` value to the same app endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and optionally alters `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `Utils::HmacValidator.validate(request)` in [5](#0-4)  still succeeds because only `raw_body` is checked.
5. `Registry.process` [6](#0-5)  dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` to the app's handler with the forged `shop`, which the host app is designed to trust as the tenant identity for this payload.
