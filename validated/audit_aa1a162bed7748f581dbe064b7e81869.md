### Title
Webhook tenant identity (`shop` header) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header as the tenant identity handed to the app's handler. Any party who can obtain one genuine `(body, hmac)` pair signed with the app's `api_secret_key` — trivially available to any merchant who installs the app on their own store — can replay that exact body/HMAC pair while substituting an arbitrary victim shop domain in the header, and the gem will report it as a validated webhook for the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [4](#0-3) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read directly from unauthenticated HTTP headers, independent of the signed content: [5](#0-4) 

`Registry.process` performs exactly one check — `Utils::HmacValidator.validate(request)`, which computes `HMAC(api_secret_key, to_signable_string)` i.e. `HMAC(api_secret_key, raw_body)` and compares it to the `hmac-sha256` header — and then immediately builds `WebhookMetadata` from the unauthenticated header fields, including `shop: request.shop`, and dispatches it to the app's registered handler: [2](#0-1) [6](#0-5) 

This is precisely the analog of the reported bug class: the code assumes that a successful HMAC check binds *every* field consumed downstream (here, the tenant identity `shop`) to the signer's intent, but the HMAC only covers the body — never the `shop` field acted on by `Registry.process`/the handler. The binding the code implicitly relies on is:

`hmac_valid(body) == true` ⇒ `shop_header is authentic`

but the actual equality holds only for:

`hmac_valid(body) == true` ⇒ `body is authentic`

The `shop` header carries no cryptographic binding to the body or to the signature at all. The gem's own documentation confirms `data.shop` is meant to be trusted as "the shop domain of the webhook" and shown being used directly as a tenant key (`shop_domain: data.shop`) in the sample handler in `docs/usage/webhooks.md:24-27`, so this is not a case of the host app ignoring the documented API — it is following it exactly as documented, and the gem's own `process` method is what hands over the spoofable value.

### Impact Explanation
This is a cross-tenant identity-binding break with Critical impact per the report's own criteria: an unprivileged internet user (any current or newly-signed-up merchant of the app, requiring no `api_secret_key`, access token, or privileged account) can:
1. Install the app on their own store to receive one legitimate webhook delivery (any topic, e.g. `app/uninstalled` or any subscribed topic) with a genuine `hmac-sha256` header computed over a known/predictable raw body.
2. Replay the identical raw body and `hmac-sha256` header value to the app's public webhook endpoint, while setting `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) to an arbitrary victim shop's domain.
3. `Registry.process` reports the request as HMAC-valid (correctly — the body they control is unchanged) and dispatches `WebhookMetadata` with `shop` set to the victim's domain to the app's handler.

Any handler logic that is scoped by `data.shop` (looking up the victim's session/access token, queuing shop-specific background work, applying webhook content to the victim's records, or triggering compliance/redact flows for the wrong shop) executes against the victim tenant using attacker-supplied body content, i.e. cross-tenant access/data corruption without ever needing the victim's credentials.

### Likelihood Explanation
High. The prerequisite ("obtain one genuine signed webhook") requires nothing more than installing the target app on any store the attacker controls — a normal, unprivileged action available to anyone. Crafting the replay request with a modified header is trivial; no secret material or elevated privileges are needed at any step.

### Recommendation
Include the tenant-identifying headers (`shop`, and ideally `topic`/`webhook_id`) in the HMAC-signable content, or otherwise cryptographically bind the shop domain to the request before trusting `request.shop` — e.g., have `Registry.process` cross-check the header's shop domain against a shop the app actually has an active session/webhook registration for, rather than passing it through unauthenticated to the handler. At minimum, update `VerifiableQuery`/`HmacValidator` so that any field consumed for tenant identification is included in `to_signable_string`.

### Proof of Concept
1. As an attacker, install the target Shopify app on `attacker-shop.myshopify.com`. Trigger a webhook (e.g. by performing the action tied to a registered topic). Capture the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` from the delivery — `H = HMAC-SHA256(api_secret_key, B)`, valid regardless of shop.
2. Send a new HTTP POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256`: `H` (unchanged)
   - Header `X-Shopify-Shop-Domain`: `victim-shop.myshopify.com` (attacker-chosen)
   - Header `X-Shopify-Topic`: same or different registered topic
3. The app calls:
   ```ruby
   ShopifyAPI::Webhooks::Registry.process(
     ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)
   )
   ```
4. `Utils::HmacValidator.validate(request)` returns `true` (per `lib/shopify_api/utils/hmac_validator.rb:12-31`, only `B` is checked against `H`).
5. The registered handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` (per `lib/shopify_api/webhooks/registry.rb:198-199`) and performs shop-scoped work for `victim-shop.myshopify.com` using attacker-supplied body content, despite the victim never having sent this webhook.
