## Title
Missing MMR-leaf-freshness check in `EcdsaBeefy.verifyMmrUpdateProof` allows replay of a stale MMR leaf, permanently bricking authority-set rotation - (File: `evm/src/consensus/EcdsaBeefy.sol`)

### Summary
`EcdsaBeefy.sol` is one of Hyperbridge's three BEEFY consensus-client implementations (Solidity ECDSA, Solidity SP1/zk, and the shared Rust verifier used by the pallet). The Rust verifier and `SP1Beefy.sol` both explicitly pin the submitted MMR leaf to the commitment's block number (`parent_number + 1 == block_number` / `parentNumber + 1 == blockNumber`), because an MMR is append-only and any historical leaf still verifies against a newer, validly-signed MMR root. `EcdsaBeefy.sol`'s `verifyMmrUpdateProof`/`verifyMmrLeaf` never performs this check, so it accepts *any* leaf that merkle-proofs into the signed root, regardless of how old it is.

### Finding Description
`verify()` in `EcdsaBeefy.sol` only rejects proofs whose commitment `blockNumber` is not newer than the trusted `latestHeight`: [1](#0-0) 

It then calls `verifyMmrUpdateProof`, which verifies the supermajority signature over the commitment and the authority merkle-multi-proof, then calls `verifyMmrLeaf` to prove *some* leaf is included under the new `mmrRoot`: [2](#0-1) [3](#0-2) 

Nowhere is `relay.latestMmrLeaf.parentNumber + 1 == blockNumber` (or equivalent) enforced. Because an MMR is append-only, *every* historical leaf remains provable against any later root, so an attacker/relayer can pair a fresh, validly supermajority-signed commitment for a high `blockNumber` with an old `latestMmrLeaf` (e.g. one whose `nextAuthoritySet` is stale/already-retired). The contract will:
- Advance `trustedState.latestHeight = latestHeight` (the new, high block number),
- But skip or apply a stale authority-set rotation, since `relayProof.latestMmrLeaf.nextAuthoritySet.id` from the old leaf will not be `> trustedState.nextAuthoritySet.id` in the common case, or in the crafted case can itself replay an already-superseded rotation.
- Return `headsRoot = relayProof.latestMmrLeaf.extra`, i.e. the parachain-heads-root of the *old* leaf, which is then used to validate `IntermediateState`s via `verifyParachainHeaderProof`.

This is exactly the bug class the codebase's own authors already identified and fixed twice elsewhere — in the shared Rust verifier: [4](#0-3) 

and in `SP1Beefy.sol`: [5](#0-4) [6](#0-5) 

`EcdsaBeefy.sol` is the one BEEFY variant where this specific fix was never applied.

### Impact Explanation
`EcdsaBeefy` is a production `IConsensusV2` implementation invoked by `HandlerV2.handleConsensus`, which is reachable by any unprivileged relayer submitting a consensus message: [7](#0-6) 

By advancing `latestHeight` while replaying a stale leaf, an attacker can:
1. **Strand parachain-heads verification against a stale `headsRoot`** — `verifyParachainHeaderProof` will validate intermediate states against an old parachain-heads merkle root rather than the one actually committed at the new height, letting stale `IntermediateState`s (old `StateCommitment`s) be accepted as if freshly finalized, as long as their recorded height is still greater than the currently-stored `latestStateMachineHeight` for that state machine (checked in `HandlerV2.handleConsensus`, lines 156-164). This can cause the bridge to persist stale/incorrect state-machine commitments, which downstream `handlePostRequests`/response handling treats as trusted roots for message and state-proof verification.
2. **Suppress or desynchronize authority-set rotation** — since the leaf's `nextAuthoritySet` is decoupled from the actual block height, the on-chain authority bookkeeping can diverge from the real relay chain's rotation schedule. Once the real chain's authority set moves past what the client holds as `current`/`next`, later genuine commitments whose `validatorSetId` matches neither stored id will be rejected with `UnknownAuthoritySet`, permanently freezing the consensus client and thus the route — i.e., "a route unable to deliver messages," one of the explicitly in-scope impacts.

This is a Medium-severity, single-message-reachable integrity bug in the on-chain light client that mirrors the Verge-style "accept a stale/alternate history as if it were the freshest one," causing unsound state commitments and potential permanent loss of liveness for the affected route.

### Likelihood Explanation
Any relayer (unprivileged) can call `HandlerV2.handleConsensus` with an `EcdsaBeefy`-formatted proof. Constructing the malicious payload only requires reusing a previously-observed, validly-signed BEEFY commitment for a later block together with an MMR leaf from an earlier block for which the relayer already possesses a valid MMR inclusion proof (all publicly observable on the relay chain) — no validator collusion or private key compromise is required, only public historical relay-chain data. This significantly lowers the bar for likelihood versus the 51%-attack analog, since exploitation does not require majority hash power, only a discrepancy between what the two Solidity BEEFY variants enforce.

### Recommendation
Add the same leaf-freshness check that already exists in `SP1Beefy.sol` and the Rust verifier to `EcdsaBeefy.verifyMmrLeaf`/`verifyMmrUpdateProof`:
```solidity
if (uint256(relay.latestMmrLeaf.parentNumber) + 1 != latestHeight) revert StaleMmrLeaf();
```
placed before (or alongside) the existing MMR inclusion-proof check, mirroring `SP1Beefy.sol` line 125.

### Proof of Concept
1. Observe a historical, finalized BEEFY commitment/leaf pair `(commitment_A, leaf_A)` at `blockNumber_A`, with a valid MMR inclusion proof against `mmrRoot_A` (all public data).
2. Wait for/obtain a later valid supermajority-signed commitment `commitment_B` at `blockNumber_B > blockNumber_A` with root `mmrRoot_B` (also public, since MMR roots are cumulative and any earlier leaf still proves against later roots via an updated MMR proof for `mmrRoot_B`).
3. Submit `RelayChainProof { signedCommitment: commitment_B, latestMmrLeaf: leaf_A, mmrProof: proof_of_leaf_A_against_mmrRoot_B, proof: authority_multiproof }` to `EcdsaBeefy.verify`.
4. `verifyMmrUpdateProof` passes: signature/authority checks succeed against `commitment_B`; `verifyMmrLeaf` succeeds because `leaf_A` is still provably included under `mmrRoot_B` (MMR append-only property) — there is no check tying `leaf_A.parentNumber` to `blockNumber_B`.
5. Result: `trustedState.latestHeight` becomes `blockNumber_B`, but `headsRoot` and any authority-rotation data returned are those of the stale `leaf_A`, decoupling the client's advancing height from its actual rotation/parachain-heads state.
