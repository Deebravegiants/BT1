### Title
Unrefunded excess native token (`msg.value`) permanently lost in tron `IntentGatewayV2.placeOrder` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The tron port of `IntentGatewayV2.sol` implements `placeOrder` as a `payable` function that accepts native ETH (or ERC20) for order inputs and, optionally, native token as payment for solver fees (swapped to fee token via Uniswap). It tracks the running unspent balance in a local `msgValue` variable throughout escrow and fee-collection logic, but — unlike the canonical `evm/src/apps/IntentGatewayV2.sol` implementation — never sends the leftover `msgValue` back to `msg.sender` at the end of the function.

### Finding Description
`placeOrder` in `evm/tron/contracts/apps/IntentGatewayV2.sol` begins with `uint256 msgValue = msg.value;` [1](#0-0)  and decrements `msgValue` as native-token inputs are escrowed or swapped for fee-token payment of `order.fees` [2](#0-1) . After the fee-escrow block, the function proceeds directly to emitting `OrderPlaced` and returns, with no code path that forwards any remaining `msgValue` back to the caller [3](#0-2) .

This is in stark contrast to the canonical EVM implementation of the same function, which explicitly refunds unspent native tokens: `// Refund any unspent native tokens to the user. if (msgValue > 0) { _sendValue(msg.sender, msgValue); }` [4](#0-3) . A test in the test suite for the canonical version confirms this refund behavior is expected: `testPlaceOrder_RefundsExcessNativeToken` asserts that overpaid native ETH is refunded and only the required escrow amount is retained by the gateway [5](#0-4) .

Because `placeOrder` is `payable` and accepts both ERC20 token inputs and native-token fee payment in the same call, any user who: (a) funds an order purely with ERC20 input tokens but also attaches `msg.value` (e.g., mistakenly including gas-fee style value, or overestimating the native amount needed for `order.fees`), or (b) overpays the native amount required to cover `order.fees` via the Uniswap swap, will have the excess native token permanently stranded in the tron `IntentGatewayV2` contract with no function to reclaim it.

### Impact Explanation
This is a fund-loss bug reachable by any ordinary user placing an order — no privileged role is required. The excess ETH becomes indistinguishable "donated" balance sitting in the gateway contract; there is no `sweepDust`-style admin path shown in this snippet that credits it back to the specific user, and no user-facing function exists to reclaim it. This matches the classic pattern from the referenced report: `msg.value` is accepted but not fully accounted for/refunded, causing permanent loss of user funds. Given `placeOrder` is a routine, frequently-invoked entry point for intents (a core Hyperbridge product), the aggregate loss across many orders and any accidental overpayment (e.g., naive fee-quote rounding, front-end miscalculation of `nativeValue` per the SDK docs) could be significant.

### Likelihood Explanation
Likelihood is elevated because the SDK documentation for order fee payment explicitly instructs users to send `nativeValue` extra wei on the placement transaction when paying fees in native token, and states "unused native is refunded" as the expected behavior [6](#0-5)  — this refund guarantee is exactly what the tron variant fails to implement, so ordinary, spec-compliant usage patterns (slight overestimation of `nativeValue`, or Uniswap swap consuming less than the full `msg.value`) will trigger fund loss on the tron deployment without requiring any unusual or adversarial behavior.

### Recommendation
Add the same unspent-native-token refund logic present in the canonical implementation to the tron `IntentGatewayV2.placeOrder`: after the fee-escrow block, check `if (msgValue > 0) { (bool sent,) = msg.sender.call{value: msgValue}(""); if (!sent) revert InsufficientNativeToken(); }` (or reuse the `_sendValue` helper used elsewhere in the same file) before emitting `OrderPlaced`.

### Proof of Concept
1. User calls `placeOrder` on the tron `IntentGatewayV2` with `order.inputs` consisting solely of an ERC20 token (e.g., USDC) and `order.fees > 0` payable in native token.
2. User sends `msg.value` intentionally larger than needed to cover `order.fees` via the Uniswap `swapETHForExactTokens` call (e.g., due to slippage buffer or a naive client calculation), consistent with the documented SDK flow at `evm/tron/contracts/apps/IntentGatewayV2.sol:471-488`.
3. `swapETHForExactTokens{value: msgValue}(order.fees, ...)` only consumes as much ETH as needed to obtain exactly `order.fees` fee-token amount; the router refunds any leftover ETH from the swap to the calling contract (the gateway), not to the original `msg.sender`, per standard Uniswap V2 router semantics.
4. Function reaches `emit OrderPlaced(...)` and returns without ever forwarding the leftover balance sitting in the gateway to the user.
5. The excess ETH remains stuck in the `IntentGatewayV2` contract balance indefinitely, with no reclaim function for the affected user.
