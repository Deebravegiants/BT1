### Title
Webhook `shop`/`topic` fields are not covered by the HMAC signature, allowing cross-tenant spoofing of webhook origin - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then dispatches to the handler using `shop`, `topic`, `webhook_id`, and `api_version` values that are read directly from HTTP headers and are never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `api_version`, and `webhook_id` are all parsed straight out of unauthenticated headers: [2](#0-1) 

`Registry.process` validates only the HMAC of that signable string (the body) and then immediately trusts `request.shop`/`request.topic` to build the handler payload: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` confirm this — the comparison is computed only over `verifiable_query.to_signable_string`, which for webhooks is the raw body, never the shop or topic headers: [4](#0-3) 

This breaks the intended identity binding `hmac_valid(request) == shop_header_is_authentic`. Because the HMAC is computed with the app's single shared `client_secret` (not a per-shop secret) over the body only, any entity that can obtain one legitimately-signed webhook body/HMAC pair for shop A (e.g., by installing the app on an attacker-controlled shop, which is the normal, low-privilege installation flow) can replay that exact body+HMAC to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) with a victim shop's domain. The HMAC still validates because the body did not change, and `Registry.process` will hand `WebhookMetadata.new(shop: <attacker-chosen-value>, ...)` to the registered handler, which will act as if the event belongs to the spoofed shop.

### Impact Explanation
Any host application whose webhook handler uses `data.shop` to select which merchant's session/access token/store data to operate on (the intended and documented usage — see `WebhookMetadata`) can be tricked into performing actions or returning data scoped to a shop the attacker does not own. This is a cross-tenant authentication/authorization boundary break rooted entirely in this gem's `Registry.process`/`Request` implementation, since the gem presents `shop` as "verified" webhook data once `HmacValidator.validate` passes, when in fact `shop` was never covered by the signature.

### Likelihood Explanation
Exploitation only requires the attacker to be a legitimate, unprivileged merchant who has installed the app on their own store (a normal, low-privilege action available to any developer/merchant), enabling them to capture a validly-signed webhook body/HMAC for a topic of interest, then replay it with a forged shop header to the app's public webhook endpoint. No access token, refresh token, or `client_secret` is required — only observation of one's own legitimately delivered webhook traffic, which is trivial.

### Recommendation
Include the shop domain (and ideally topic) in the signed material used for webhook verification, or perform an independent, out-of-band check binding the `x-shopify-shop-domain` header to a shop known to have a currently registered/active webhook subscription for that specific `webhook_id`/topic before dispatching to handlers. At minimum, document prominently that `shop`/`topic` are unauthenticated and must be independently re-validated (e.g., by looking up the webhook_id against Shopify's API for the claimed shop) before being trusted for tenant-scoping decisions.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers/receives a legitimate webhook (e.g., `orders/create`) with body `B` and headers including `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared secret) and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker crafts a new HTTP POST to the app's webhook endpoint with the identical body `B` and identical `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate(request)` succeeds because it only re-computes the HMAC over `B` (the raw body), which is unchanged. [3](#0-2) 
4. `Registry.process` dispatches to the app's handler with `shop: "victim.myshopify.com"`, `topic`, and `body` from the attacker's shop, even though the data was never validated as belonging to `victim.myshopify.com`. If the handler uses `data.shop` to load the victim's session/access token or write victim-scoped state, this results in cross-tenant data corruption or leakage.

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
