## Title
Tron IntentGatewayV2 lacks the relayer allowlist gate, allowing any relayer to forge escrow settlement and drain open orders' escrow - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The EVM `IntentGatewayV2` deployment gates every `onAccept` and `onGetResponse` delivery behind an authorized-relayer check (`_checkRelayer`), added specifically to stop an unbound relayer from forging escrow-releasing message delivery [1](#0-0) . The Tron variant of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, implements `onAccept` and `onGetResponse` without this relayer check at all [2](#0-1) [3](#0-2) .

### Finding Description
On the canonical EVM `IntentGatewayV2` (via `ExtrinsicIntents.sol`), both `onAccept` and `onGetResponse` call `_checkRelayer(incoming.relayer)` before decoding and acting on the request body: [4](#0-3) 

This gate was deliberately introduced (per the project's own changelog) because escrow redemptions and refunds must only be honored when delivered by the single authorized relayer stored at `_relayer` — any relayer being able to trigger delivery would let a malicious message get processed [1](#0-0) .

The `evm/tron/contracts/apps/IntentGatewayV2.sol` file is a separate, parallel implementation of the same gateway for Tron. Its `onAccept` calls `authenticate(incoming.request)` for `RedeemEscrow`/`RefundEscrow` kinds but never calls any relayer-allowlist check: [5](#0-4) 

Its `onGetResponse` similarly omits the check present in the mainline contract: [6](#0-5) 

Both functions are `onlyHost`-gated, so the host (ISMP) contract is still the caller — but `onlyHost` only restricts *who calls the function*, not *which relayer's delivery is honored*. On the mainline gateway, `onlyHost` plus `_checkRelayer` together ensure only a specific, governance-approved relayer's message delivery mints/withdraws funds. The Tron gateway keeps `onlyHost` but drops the second, purpose-built check — meaning any relayer permitted to deliver ISMP messages through the host (which for post requests and get-responses is any relayer that can produce a valid consensus/state proof, not a governance-approved allowlist) can trigger `withdraw()`, releasing escrowed input tokens to whatever `beneficiary` the corresponding cross-chain request names.

### Impact Explanation
This is directly analogous to the Bisq v1 report's bug class: a verification step in the trade/settlement protocol was skippable, letting an unauthorized party drain escrowed funds from open offers. Here, the missing relayer allowlist check in the Tron `IntentGatewayV2.onAccept`/`onGetResponse` means escrow release/refund authorization relies solely on host-level message authentication (`onlyHost` + `authenticate`), not on the intended relayer-restriction control that the rest of the codebase treats as mandatory security-critical defense-in-depth. Any relayer able to route a `RedeemEscrow`/`RefundEscrow` request or `GetResponse` through the host to this gateway can cause escrowed input tokens on Tron to be released to an attacker-controlled beneficiary — direct theft of escrowed order funds, matching "drain from open offers."

### Likelihood Explanation
Medium-High: this requires only that a relayer other than the intended one deliver a request/response through the ISMP host to the Tron `IntentGatewayV2` — the same operational capability every relayer already has for legitimate delivery. No admin/governance compromise, no consensus break, and no malicious-node assumption is needed; it is purely a missing authorization check on an unprivileged, reachable code path (message delivery from a relayer to an app contract), which the rules explicitly count as in-scope (`EvmHost`/`HandlerV2` dispatch and delivery paths).

### Recommendation
Add the same `_checkRelayer`/relayer-allowlist gate used in `evm/src/apps/intentsv2/ExtrinsicIntents.sol` to `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `onAccept` and `onGetResponse`, storing an authorized `_relayer` and rejecting any delivery whose `incoming.relayer` does not match, consistent with the mainline EVM implementation.

### Proof of Concept
1. Deploy/observe the Tron `IntentGatewayV2` with an order escrowed on Tron (source chain) awaiting settlement from a destination-chain fill.
2. An arbitrary relayer (not the one intended by protocol operators) constructs and submits, through the ISMP host, a `RedeemEscrow` or `RefundEscrow` `PostRequest` (or a `GetResponse` for `onGetResponse`) that passes host-level `authenticate`/proof checks (i.e., a legitimately-proven cross-chain message, but delivered by an unintended relayer).
3. `IntentGatewayV2.onAccept` (or `onGetResponse`) executes without any relayer-identity check, calling `withdraw()` and releasing the escrowed tokens to the named beneficiary — since there is no `_checkRelayer` call to reject the delivery based on the relayer's identity, unlike the mainline gateway at [7](#0-6) .

Note: I was not able to fully verify within the available context whether Tron's ISMP host restricts *which* relayers can successfully deliver proven messages at the host level (which could mitigate this gap) — this would need to be confirmed by inspecting the Tron host/handler contracts, which were not surfaced in my searches.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        _checkRelayer(incoming.relayer);
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            _authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return _withdraw(body, kind == RequestKind.RefundEscrow, true);
        }

        // only hyperbridge is permitted to perform these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
        if (kind == RequestKind.NewDeployment) {
            _addDeployment(abi.decode(incoming.request.body[1:], (Deployment)));
        } else if (kind == RequestKind.UpdateParams) {
            _updateParams(abi.decode(incoming.request.body[1:], (ParamsUpdate)));
        } else if (kind == RequestKind.SweepDust) {
            _sweepDust(abi.decode(incoming.request.body[1:], (SweepDust)));
        } else if (kind == RequestKind.Execute) {
            Address.functionDelegateCall(ERC1967Utils.getImplementation(), incoming.request.body[1:]);
        }
    }
