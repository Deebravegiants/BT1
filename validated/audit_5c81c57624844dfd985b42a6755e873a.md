Audit Report

## Title
Bridge OutgoingToken (external adapter credential) exposed in plain text to view-only users via `/v2/bridge_types` REST and GraphQL `bridge`/`bridges` queries - (File: core/web/presenters/bridges.go)

## Summary
`BridgeType.OutgoingToken`, a long-lived credential the Chainlink node uses to authenticate itself to an external adapter, is stored in plaintext in the DB and returned unconditionally (no `omitempty`, no redaction) by `presenters.NewBridgeResource` <cite repo="Alyssadaypin/chainlink--025" path="core/web/presenters/bridges.go" start="10="21" /> [1](#0-0) . The `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` routes are registered without any role-gating wrapper, unlike `Create`/`Update`/`Destroy` which require `auth.RequiresEditRole` [2](#0-1) , meaning any authenticated `UserRoleView` (the lowest privilege tier, one step below `RequiresRunRole`'s minimum bar) can retrieve it [3](#0-2) . The same value is exposed via the GraphQL `bridge`/`bridges` queries as non-null `outgoingToken: String!`, resolved straight from the DB record [4](#0-3) .

## Finding Description
`BridgeType.OutgoingToken` is generated once at bridge creation as a static secret meant to authenticate the node to its configured external adapter [5](#0-4) , and stored as plaintext in the `bridge_types` table via the `db:"outgoing_token"` tag [6](#0-5) .

`BridgeResource`, used by both `Index` and `Show` handlers of `BridgeTypesController`, marshals `OutgoingToken` as a mandatory JSON field, in contrast to `IncomingToken` which uses `omitempty` and is explicitly documented as "only provided when creating a Bridge" [7](#0-6) . The `Index`/`Show` handlers build this resource directly from the stored ORM record with no filtering by caller role [8](#0-7) .

Critically, the router wires `GET /bridge_types` and `GET /bridge_types/:BridgeName` with no `auth.RequiresEditRole`/`RequiresRunRole`/`RequiresAdminRole` wrapper — bare `authv2.GET(...)`, contrasted directly against the `POST`/`PATCH`/`DELETE` routes which are wrapped in `auth.RequiresEditRole` [2](#0-1) . Since `authv2` only requires a valid authenticated session (any role, including `UserRoleView`) and `RequiresRunRole`/`RequiresEditRole` are the only role gates in this codebase (`view` is strictly weaker than `run`, which is weaker than `edit`) [9](#0-8) , a `view`-role session can call these GET endpoints and receive `outgoingToken` in the response, as the presenter test fixture confirms it's rendered unconditionally [10](#0-9) .

The same exposure exists in GraphQL: `Bridge.outgoingToken` is declared `String!` (non-nullable, unconditionally returned) and both `bridge`/`bridges` queries resolve it directly from the DB record with no role-based field filtering, as shown in both the schema and the passing test `Test_Bridges`/`Test_Bridge` [11](#0-10) .

By contrast, `ExternalInitiator.OutgoingToken` — a structurally similar credential for a related feature — is exposed via `ExternalInitiatorResource` in the same unconditional (non-`omitempty`) fashion [12](#0-11) , suggesting this is a broader, intentional design pattern within the codebase for the `OutgoingToken` field across both Bridge and ExternalInitiator resources — the outgoing token, since it's the node's own credential for calling out to adapters (not the caller's credential for authenticating into the node), appears to be treated as static configuration data rather than a caller-facing secret whose disclosure creates a privilege boundary violation on its own.

## Impact Explanation
This does allow a `UserRoleView` session (the lowest privilege role) to read the plaintext `OutgoingToken` for every configured bridge via a simple GET or GraphQL query, which is a real credential disclosure to a user who should only have read-only dashboard visibility, not adapter credentials. Whether this is a "critical" security vulnerability depends on the deployment: `OutgoingToken` is provided by the node to the external adapter operator so the adapter can verify it's actually the node calling (not third parties), and many Chainlink deployments treat external adapters as trusted infrastructure operated by the same node operator, in which case the "escalation" from view-role to adapter-caller identity has limited practical value since the operator already controls both the node and the adapter. However, in deployments where view-role sessions are handed to less-trusted parties (e.g., dashboard-only monitoring users) while adapters are locked down to require this token, this constitutes a genuine credential leak enabling an under-privileged party to impersonate the node against the external adapter.

## Likelihood Explanation
High: exploitation requires only a standard authenticated `view`-role session and a single unauthenticated-role-gated GET request or GraphQL query; no race conditions, timing, or additional preconditions apply.

## Recommendation
Apply the same `omitempty`/restricted-disclosure treatment already used for `IncomingToken` to `OutgoingToken` in `BridgeResource` (and `ExternalInitiatorResource`), and/or gate `GET /v2/bridge_types*` and the GraphQL `bridge`/`bridges` queries' `outgoingToken` field behind `edit`/`admin` role rather than allowing any authenticated `view`-role user to read it.

## Proof of Concept
1. Provision a user with `sessions.UserRoleView` and authenticate a session, following the pattern in `TestRBAC_Routemap_ViewOnly` [13](#0-12) .
2. Send `GET /v2/bridge_types` or `GET /v2/bridge_types/<name>` — reachable per the router wiring with no role wrapper [2](#0-1) .
3. Observe the JSON response includes `attributes.outgoingToken` in plaintext, per the presenter test fixture [10](#0-9) .
4. Equivalently issue `{ bridges { results { outgoingToken } } }` via GraphQL as a `view`-role user; it succeeds and returns the plaintext token, as validated by `Test_Bridges` [11](#0-10) .

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// 'edit'

	return func(c *gin.Context) {

// Index lists Bridges, one page at a time.
func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))
	for _, bridge := range bridges {
		resources = append(resources, *presenters.NewBridgeResource(bridge))
	}

	paginatedResponse(c, "Bridges", size, page, resources, count, err)
}

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
