### Title
POA Bridge withdrawal status matched only by `assetId`, causing status/hash misattribution across withdrawals in the same batch - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` matches the bridge's withdrawal status response to the caller's withdrawal solely by `assetId`, ignoring the `index` that uniquely identifies the actual withdrawal within a batch intent. When a batch withdrawal contains two or more withdrawals of the same asset (same `assetId`), the lookup can bind the wrong on-chain outcome (status/txHash) to a given withdrawal, breaking the equality between "the withdrawal an integrator is polling" and "the on-chain outcome actually reported."

### Finding Description
`createWithdrawalIdentifier` builds a `WithdrawalIdentifier` that carries both an `index` (assigned per-bridge-route position in the batch, see `createWithdrawalIdentifiers` in `packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`) and the full `withdrawalParams`. [1](#0-0) 

However, `describeWithdrawal` explicitly abandons the `index` for matching and instead looks up the withdrawal purely by `assetId`: [2](#0-1) 

The inline comment even documents the design rationale ("Response list is unsorted, so we match by assetId instead of index") — but this only correctly disambiguates withdrawals when each `assetId` appears at most once within a batch. If a caller submits a batch withdrawal with two entries sharing the same `assetId` (e.g., two USDC withdrawals with different `destinationAddress`/`amount`, which `waitForWithdrawalCompletion` / `createWithdrawalCompletionPromises` explicitly support per `withdrawalParams[]`), `findMatchingWithdrawal` will return the same underlying bridge record (or an incorrect one, depending on list order) for both `describeWithdrawal` calls. Each of the two independent polling promises (`promises[0]`, `promises[1]` from `createWithdrawalCompletionPromises`) could then resolve with the wrong `txHash`/`status`, i.e. the second withdrawal's completion could be reported using the first withdrawal's transaction hash, or vice versa — an integrator loop (per `docs/design/rfc-batch-withdrawal-granular-control.md:235-257`) that saves `handledIndexes` and marks each index "handled" upon promise resolution would record a fabricated completion for a withdrawal that has not actually settled. [3](#0-2) 

This is directly analogous to the `VetoProposal` bug class: the veto contract counted a valid vote against the wrong constraint (no per-voter uniqueness) so a single input satisfied the threshold multiple times; here, a single bridge response record can satisfy the "is this withdrawal complete" check for multiple distinct withdrawal indices because the uniqueness key used (`assetId`) is not the correct discriminator (`index`/nonce).

### Impact Explanation
If exploited (intentionally or by natural usage patterns like withdrawing the same token to two different addresses in one batch), an integrator relying on `describeWithdrawal`/`waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` could:
- Mark a withdrawal as "completed" with a `txHash` belonging to a different withdrawal (status misreport not matching the true on-chain outcome for that specific withdrawal), potentially causing the integrator to release funds, mark an invoice paid, or stop watching a withdrawal that never actually landed at its destination.
- Conversely, cause duplicate crediting bookkeeping if a downstream system uses the (wrong) txHash as an idempotency key shared between two logically distinct withdrawals.

This falls under "a status or hash misreport making an integrator credit or refund twice" (High), since the deliverable to the end user is unaffected by the bridge itself (funds are still sent correctly on-chain), but the SDK's reported completion status/hash for a specific withdrawal entry can be wrong when `assetId` collides within a batch.

### Likelihood Explanation
Likelihood is moderate: it does not require any malicious actor — merely a legitimate batch withdrawal containing two or more withdrawals with the same `assetId` (a case explicitly supported by the batch-withdrawal APIs, e.g. RFC "batch withdrawals" and `withdrawalParams: WithdrawalParams[]`), which is a realistic usage pattern for consolidators or split-payout accounts.

### Recommendation
Match POA bridge withdrawal status responses using a unique identifier for each entry — the `index` (or a stable field returned by the POA API that maps 1:1 to the caller's positional withdrawal, e.g. sorting by creation timestamp with `assetId` as a tie-break within same-asset groups), rather than relying on `assetId` alone in `findMatchingWithdrawal`. At minimum, when multiple withdrawals in `response.withdrawals` share the caller's `assetId`, the bridge should either disambiguate by additional fields (`destinationAddress`, `amount`) that are still unique enough, or explicitly document/reject batches with duplicate `assetId` entries to avoid silent misattribution.

### Proof of Concept
1. Submit a batch withdrawal intent with two withdrawal entries having the same `assetId` (e.g., `nep141:usdc.omft.near`) but different `destinationAddress`/`amount` — `index` 0 and `index` 1 within the POA route bucket.
2. Call `sdk.createWithdrawalCompletionPromises({ withdrawalParams: [w0, w1], intentTx })`, which internally calls `PoaBridge.describeWithdrawal` for each `WithdrawalIdentifier` (index 0 and 1), both carrying the same `assetId`.
3. Inside `describeWithdrawal`, `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` is called for both index 0 and index 1 lookups against the same unsorted `response.withdrawals` list that may contain both withdrawal records for that asset. Because matching uses only `assetId`, both calls can resolve to the same withdrawal record (or the wrong one relative to caller intent).
4. `promises[0]` (meant to track withdrawal 0) can resolve with the txHash/status that actually belongs to withdrawal 1, and vice versa, before the second withdrawal has actually settled on-chain — demonstrating a status/hash misreport not reflecting the true per-withdrawal on-chain outcome. 	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
