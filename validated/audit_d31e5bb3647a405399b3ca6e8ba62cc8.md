### Title
Unvalidated `Call.value` forwarding in `CallDispatcher.dispatch` lets a malicious order creator strand solver-funded ETH in a Uniswap-like router and steal it - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch` blindly forwards the caller-supplied `Call.value` to an arbitrary target with `to.call{value: call.value}(call.data)`, with no check that the value actually matches what the target function consumes. [1](#0-0) 
The `Call[]` array executed here is not protocol-controlled — for `IntentGatewayV2`/`IntentsBase`, it is the `order.output.call` (postdispatch) supplied by whoever places the order, and it is executed against tokens/ETH that the *solver* deposits into the dispatcher at fill time. [2](#0-1) 
This is the same bug class as the Arkis `CommandSafeExecutor` finding: an untrusted, user-supplied `value` is forwarded verbatim to an external operator (e.g. a Uniswap router) without validating that the call actually consumes it, enabling native tokens to be stranded in the router and later stolen by anyone.

### Finding Description
`ICallDispatcher.Call` carries an attacker-chosen `to`, `value`, and `data`. [3](#0-2) 
`CallDispatcher.dispatch` executes each entry with `to.call{value: call.value}(call.data)` and only checks that `to` has code — it never verifies that `call.value` is actually required/consumed by `call.data`, nor restricts `to` to a known-safe target set. [1](#0-0) 

In `IntentGatewayV2`/`IntentsBase`, order fulfillment routes solver-provided output tokens through the dispatcher and then executes the order's postdispatch `call` (`order.output.call`), which is set by the order's creator at `placeOrder` time — an unprivileged, arbitrary end user: [4](#0-3) 
The docs confirm this design: "The `call` field in `PaymentInfo` contains calldata to execute *after* the order is filled... output tokens received from the solver are routed through a DeFi protocol before reaching the beneficiary," using the same unrestricted `Call{to, value, data}` structure forwarded straight to `CallDispatcher`. [5](#0-4) 

Because `Call.value` is fully attacker-controlled and un-validated, a malicious order creator can craft `order.output.call` so that a `Call` targets a Uniswap-V2-style router with `value` set to the full amount of native ETH the solver deposited into the dispatcher, while `data` invokes a function that does not consume `msg.value` (e.g. an ERC20-for-ERC20 swap or an exact-output swap where the router doesn't refund unused ETH sent as `value`). Uniswap-style routers accept arbitrary `msg.value` on payable functions regardless of whether the function logic uses it, and any ETH left in the router after the call is not tied to a specific depositor — it can be swept by any third party in a follow-up transaction sent directly to the router (outside Hyperbridge). This mirrors exactly the exploit primitive described in the source report: value transferred by an untrusted, user-controlled `Call` into a Uniswap-family router is not refunded and becomes stealable by anyone.

The dust-sweep logic in `_execute()` only sweeps balances remaining on the `dispatcher` itself back to the gateway; it cannot recover funds that the postdispatch call has already pushed out to an external router. [6](#0-5) 

### Impact Explanation
This lets an unprivileged order-placer divert a solver's deposited output tokens (native ETH) into an external router where they become claimable by any address, including the attacker. This is direct theft of third-party (solver) funds triggered from a single `placeOrder`/`fillOrder` transaction pair — no privileged role or governance action is required. Severity scales with the size of orders solvers are willing to fill; solvers cannot detect this risk without simulating every possible postdispatch payload against every possible router-like target.

### Likelihood Explanation
Any user can call `placeOrder` and freely set `order.output.call` to an arbitrary `Call[]`, including a target address and value of their choosing, as confirmed by the composable "route through DEXes... as part of filling an order" design intent. [7](#0-6) 
No allow-list of targets or validation that `Call.value` matches what the target function actually spends exists in `CallDispatcher.dispatch`. [1](#0-0) 
The only defense is that solvers must voluntarily choose to fill an order with a malicious postdispatch payload — but solvers are economically incentivized by the offered swap output and cannot practically audit arbitrary calldata/value combinations for router-specific fund-leak edge cases before filling, especially for routers with known idiosyncrasies.

### Recommendation
- In `CallDispatcher.dispatch`, disallow forwarding `msg.value`-style `Call.value` to functions that are not expected to consume it, or require an explicit allow-list of `(target, selector)` pairs that are vetted for the value-forwarding pattern.
- Alternatively, have `IntentsBase._execute` measure the ETH balance held by the dispatcher immediately before and after each individual `Call` in `order.output.call`/`order.predispatch.call`, and revert (or refuse to proceed to distribute funds to the beneficiary) if a call sends more value than the dispatcher balance-delta shows was consumed, forcing calldata authors to structure calls so unspent value is returned to the dispatcher rather than stranded externally.
- Document/enforce that only routers verified not to strand `msg.value` (i.e., those that revert or fully refund unused ETH) may be targeted with nonzero `Call.value` in user-supplied `PaymentInfo.call`/`DispatchInfo.call`.

### Proof of Concept
1. Solver deposits `X` ETH-equivalent output tokens into the `CallDispatcher` while filling an order whose `order.output.call` was crafted by the attacker (order creator) at `placeOrder` time.
2. `IntentsBase._execute` calls `ICallDispatcher(dispatcher).dispatch(order.output.call)`, which contains `Call{to: uniswapV2Router, value: X, data: <ERC20-for-ERC20 swap or exact-output swap selector that does not consume msg.value>}`. [2](#0-1) 
3. `CallDispatcher.dispatch` forwards `X` ETH to the router unconditionally via `to.call{value: X}(data)`. [8](#0-7) 
4. Because the invoked router function does not use `msg.value`, the `X` ETH remains stranded in the router's balance, unassociated with any user's escrowed position.
5. The attacker (or any third party) sends a direct, out-of-band transaction to the router (e.g., `swapExactETHForTokens` using `address(router).balance` as the swap-in amount) to claim the stranded ETH, completing the theft of the solver's deposited funds.

        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;

            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

```text
Orders support arbitrary calldata execution at two points in the lifecycle — before escrow (predispatch) and after fill (postdispatch). Both are executed through the `CallDispatcher` contract, which takes an ABI-encoded `Call[]` array:

```solidity
struct Call {
    address to;      // Target contract (must have code, reverts with NotContract otherwise)
    uint256 value;   // ETH to send with call
    bytes data;      // Calldata to execute
}
```

The `CallDispatcher` executes each call sequentially and reverts the entire batch if any call fails.

### Predispatch

The `predispatch` field in `Order` contains calldata to execute *before* escrowing inputs. The predispatch assets specified in `DispatchInfo.assets` are transferred to the `CallDispatcher`, the encoded calls are executed, and the resulting tokens are transferred back to the gateway for escrow. This enables swap-then-escrow patterns — for example, a user sends ETH which the `CallDispatcher` swaps to DAI on Uniswap, and the resulting DAI is escrowed as the order input.

### Postdispatch

The `call` field in `PaymentInfo` contains calldata to execute *after* the order is filled. This enables fill-then-act patterns — for example, output tokens received from the solver are routed through a DeFi protocol before reaching the beneficiary.
