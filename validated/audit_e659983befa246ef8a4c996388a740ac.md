### Title
Webhook HMAC signature does not bind the `shop-domain` header, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC that `Utils::HmacValidator` verifies covers the body but never the `shop-domain` header that `Registry.process` extracts and hands to app handlers as the tenant identifier. Any actor who possesses one valid `(body, hmac)` pair produced with the app's shared `client_secret` — e.g. a merchant who has installed the app on their own store and received a legitimate webhook for it — can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. The signature check still passes because the header is outside the signed data, so the app processes attacker-controlled event data as if it originated from a different, victim shop.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which only returns `@raw_body`, and `shop` is read straight from an attacker-controllable header without being part of the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC using `verifiable_query.to_signable_string` (body only) against the `hmac` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as full authentication of the request and then forwards `request.shop` (the unauthenticated header value) directly to the app's handler as the tenant identity: [4](#0-3) 

This is exactly the "field acted on but not covered by the HMAC" pattern: the equality the gem is supposed to guarantee is `hmac == HMAC(secret, body ‖ shop)` (or at minimum `shop` bound to some signed value), but the implementation only guarantees `hmac == HMAC(secret, body)`. Because the app's `client_secret` (and therefore the HMAC key) is shared across every shop that installs the app, any merchant/tenant of the same app can generate one legitimate `(body, hmac)` pair using a webhook delivered to their own store, then re-POST it to the shared webhook controller with a forged `shopify-shop-domain` (or `x-shopify-shop-domain`) header naming a different, victim shop. `Registry.process` will accept it as valid and invoke the handler with `WebhookMetadata.new(... shop: request.shop ...)` pointing at the victim shop.

The library's own documentation encourages host apps to trust this exact flow without extra validation, presenting `Registry.process` as sufficient to "verify the request did indeed come from Shopify": [5](#0-4) 

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce: `Request#shop` is the value host applications are expected to use to identify which merchant a webhook event belongs to, but it is never cryptographically bound to the authenticated payload. An attacker who is a legitimate (even free/trial) tenant of the app can forge events attributed to any other shop the app serves, leading to cross-tenant access/data confusion (e.g., triggering app-side state changes — subscription downgrades, data deletion, order processing — against a victim shop's account). This matches the "cross-tenant access" Critical impact category, since the vulnerability lets one tenant act as another purely by controlling headers on a public-facing endpoint the gem hands request data to.

### Likelihood Explanation
Exploitability only requires: (1) being an installed tenant of the target app (readily achievable, e.g., a free dev/trial store), (2) triggering any webhook event in one's own store to obtain a valid `(body, hmac)` pair, and (3) POSTing that pair to the app's public webhook route with a modified `shop-domain` header — no access token, secret key, or privileged access is needed. This is a purely internet-facing, credential-free attack surface as required.

### Recommendation
Bind the shop to the signed material actually verified, or otherwise assert `request.shop` against a value that cannot be forged by the caller. Concretely: include the `shop-domain` (and ideally `topic`/`webhook-id`) values in `to_signable_string`, or require callers of `Registry.process` to supply/verify the expected shop out-of-band (e.g., compare against a shop resolved independently, such as one already associated with a known session) before dispatching to the handler.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) to receive a legitimate delivery with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Construct a new HTTP POST to the app's webhook controller route with:
   - body: `B` (unchanged)
   - header `X-Shopify-Hmac-Sha256: H` (unchanged)
   - header `X-Shopify-Shop-Domain: victim.myshopify.com` (forged)
   - header `X-Shopify-Topic`, `X-Shopify-Webhook-Id` as needed
3. `ShopifyAPI::Webhooks::Registry.process` computes `HmacValidator.validate(request)` using only `@raw_body`, matches `H`, and proceeds to call the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` as shown in `lib/shopify_api/webhooks/registry.rb:188-200`, even though the event data actually originated from the attacker's own store.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
