## Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is trusted for tenant routing without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from only the raw request body, while the `shop`, `topic`, and `webhook_id` fields used to identify the tenant and route processing are taken from unauthenticated HTTP headers. `Registry.process` validates only the HMAC over the body and then trusts these header-derived fields to build `WebhookMetadata`, breaking the binding between "the bytes that were HMAC-verified" and "the identity fields that are acted on."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from HTTP headers, which are never included in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts the header-derived `shop` (and `topic`, `webhook_id`) to build the metadata handed to the app's webhook handler: [3](#0-2) 

The HMAC verification (`OpenSSL.secure_compare(computed_signature, received_signature)`) only proves the body bytes were signed with `Context.api_secret_key`; it says nothing about which shop that signed body was originally intended for: [4](#0-3) 

This mirrors the report's bug class exactly: a value ("half of min position size") is used in one code path but a *different* invariant ("max with min position size") is enforced in the function that actually performs the security-relevant computation, so the checked quantity and the acted-upon quantity diverge. Here, the checked quantity is "body + secret" (HMAC), while the acted-upon quantity is "shop header, topic header, webhook-id header" — none of which are part of what was checked. The identity binding broken is:

`shop authenticated by HMAC` ≠ `shop used as tenant key in WebhookMetadata`

Because the same `api_secret_key` is shared across all shops installing a given app, any merchant who has legitimately installed the app (and therefore can capture a genuinely-HMAC-valid `(body, hmac)` pair from their own store's webhook deliveries) can replay that exact body+hmac to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. Validation succeeds (the body/HMAC pair is genuinely valid), and the host app's handler receives `WebhookMetadata` claiming the event belongs to a shop the attacker doesn't control.

### Impact Explanation
This is a cross-tenant confused-deputy vector: an unprivileged (but app-installing) attacker can cause the host application to process webhook data — and any state transitions it triggers (e.g., marking another shop's subscription as cancelled, toggling feature flags, updating billing/plan state, invalidating another shop's session) — under the identity of a shop they do not own, purely by controlling one header on a replayed, otherwise-legitimate request. This falls under the Critical "cross-tenant access" bucket in the given impact categories, since the binding between the cryptographically verified payload and the tenant that verification is applied for is missing.

### Likelihood Explanation
Likelihood is Medium: the attacker needs at least one legitimately signed `(body, hmac)` pair, which they can always obtain by installing the app on a shop they control (a normal, unprivileged action) and capturing any webhook delivery for a topic whose body content is either static/predictable or shop-content-independent (e.g. `app/uninstalled`, `shop/redact`, or any topic whose body the attacker doesn't need to control, only the header). No access to `api_secret_key` or any privileged credential is required — only the ability to install the app once as an ordinary merchant.

### Recommendation
Include the identity-bearing headers in the signable material, or otherwise cryptographically bind them to the HMAC:
- Extend `Request#to_signable_string` (or add a companion check in `Registry.process`) to incorporate `shop`, `topic`, and `webhook_id` into what is verified against the HMAC, or
- Require the host application to cross-check the `shop` header against a known/expected shop for the delivery (e.g., correlate with `webhook_id` uniqueness/idempotency and origin) before trusting it for tenant-scoped side effects, and document this requirement prominently since the gem currently offers no such binding.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook for a topic whose body is static or attacker-known (e.g. `app/uninstalled`).
2. Capture the resulting `x-shopify-hmac-sha256` header and raw body — this is a genuinely valid `(body, hmac)` pair for the shared `api_secret_key`.
3. Replay the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (and, if desired, a different `x-shopify-webhook-id`).
4. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the secret: [5](#0-4) 
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to act on behalf of `victim-shop`.
