### Title
Webhook shop/topic identity fields are trusted for tenant routing despite not being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats an incoming webhook request as authenticated once `Utils::HmacValidator.validate(request)` returns true, and then forwards `request.shop`, `request.topic`, and `request.webhook_id` to the app's handler as trusted `WebhookMetadata`. However, the HMAC signature computed by `Request#to_signable_string` only covers the raw request body, not the `shop-domain`, `topic`, or `webhook-id` headers that identify the tenant and event type. This breaks the identity binding: `verified(hmac) == verified(body)`, not `verified(hmac) == verified(shop)`.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers that are not part of the signed content: [3](#0-2) 

`Registry.process` validates the HMAC (of the body only) and then unconditionally trusts `request.shop` and `request.topic` to build the `WebhookMetadata` passed to the app-defined handler: [4](#0-3) 

So the gem's own `process` method effectively asserts "this webhook, including its shop attribution, is authentic" by only checking `hmac == HMAC(secret, body)`. The `shop-domain` header — the field host apps use to determine which merchant's data to act on — is never bound to that signature.

### Impact Explanation
Any party who has legitimately received one webhook (e.g., by installing the app on their own low-privilege dev/test store, which requires no special access) obtains a valid `(raw_body, hmac)` pair signed with the app's own `api_secret_key`-derived signature. Because `shop-domain` is not part of the signed content, that same `(body, hmac)` pair remains valid when replayed to the app's public webhook endpoint with an attacker-modified `x-shopify-shop-domain` header. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` claiming the event belongs to a different (victim) shop. If the host application uses `data.shop` (as intended/documented) to select which tenant record to update, this results in cross-tenant data corruption/injection — an app process attributing attacker-supplied webhook data to an arbitrary victim shop without ever needing that shop's credentials.

### Likelihood Explanation
Exploitability requires only: (1) the ability to install/register the target app on some Shopify store to receive one genuine signed webhook of a topic the app has registered a handler for (a normal unprivileged action, since anyone can create a shop/dev store and install a public app), and (2) sending a forged HTTP request to the app's public webhook endpoint with the same body/HMAC but a different `shop-domain` header. No access token, `client_secret`, or privileged account of the victim is required — only interaction with the gem's own `Registry.process`/`Request` verification path, which is squarely in scope.

### Recommendation
Include `shop`, `topic`, and `webhook_id` header values in the signable content verified by `HmacValidator`, or otherwise cryptographically bind the shop-domain claim to the signature (e.g., verify a shop-scoped webhook is only accepted if `request.shop` matches an entry that was independently registered for that topic/shop pair). At minimum, document clearly that `WebhookMetadata#shop` is unauthenticated and must not be used by host apps as the sole tenant-identification source without corroborating it against out-of-band knowledge (e.g., the shop associated with the webhook subscription id).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers to receive a webhook, e.g. `orders/create`.
2. Shopify sends a legitimate webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures `B` and the valid `hmac` header value.
4. Attacker sends a new HTTP request to the same public webhook endpoint with the identical body `B` and `hmac` header, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, B)` and finds it matches the (replayed, still-valid) `hmac` value — validation passes.
6. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: parsed(B), ...)`, even though this data never actually originated from `victim.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
