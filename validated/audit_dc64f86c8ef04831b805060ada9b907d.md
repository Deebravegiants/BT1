### Title
Token Exchange accepts non-admin (checkout) session tokens to mint full merchant access tokens - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` performs the OAuth token-exchange grant using only the `aud` claim of a session token as proof of trust. It never checks that the token's `iss` claim identifies it as an **admin** session token before exchanging it for an access token. Because `ShopifyAPI::Auth::JwtPayload` also accepts and fully decodes checkout UI extension tokens (issued to unauthenticated storefront customers) signed with the same `api_secret_key`/`aud`, a customer holding a checkout session token can drive `exchange_token` to obtain a full merchant `OFFLINE_ACCESS_TOKEN`.

### Finding Description
`ShopifyAPI::Auth::JwtPayload` decodes any HS256 token signed with `Context.api_secret_key` whose `aud` matches `Context.api_key`, regardless of the token's origin: [1](#0-0) 

It even distinguishes token provenance internally via `admin_session_token?`, checking that `iss` ends with `/admin`: [2](#0-1) 

This distinction exists because checkout UI extension tokens (issued to customers during checkout, `iss` ending in `/checkouts`) are explicitly supported and decoded the same way as admin tokens, as shown in the test fixtures: [3](#0-2) [4](#0-3) 

However, `TokenExchange.exchange_token` never calls or checks `admin_session_token?` (a private method, not exposed for callers to check either). It only validates context setup/embedded status, then unconditionally uses whatever `dest` shop is in the token to perform a token-exchange grant with the app's `client_secret`, requesting either an online or **offline** access token: [5](#0-4) 

The intended binding is: `token used for exchange.iss == "*/admin"` (i.e., only App-Bridge-issued admin session tokens should be exchangeable). The actual check performed is only `token.aud == Context.api_key`, which is also satisfied by checkout-context tokens. This is exactly the “JWT claim trusted without being bound” class: the code decodes and could distinguish `iss`, but never binds/enforces it before performing the sensitive exchange.

### Impact Explanation
Any unauthenticated storefront customer who starts a checkout on the shop can obtain a checkout UI extension session token that is legitimately signed by Shopify with the app's `api_secret_key` and `aud == api_key` (this is standard behavior documented for checkout UI extensions using this same library, per the `CHANGELOG.md` entry adding checkout ui extension support and the `JwtPayload` test fixtures). If the app calls `exchange_token` (as documented in `docs/usage/oauth.md`) without first confirming the token is an admin token, that customer-controlled token can be exchanged for a full-scope, merchant-level **offline access token** for the shop — an access token intended only to be obtainable via a legitimate merchant-authorized admin OAuth/token-exchange flow. This is theft/exfiltration of a merchant access token by an untrusted party, matching the Critical impact category.

### Likelihood Explanation
Likelihood is high for any app that (a) uses checkout UI extensions and (b) reuses the same `exchange_token` entry point for whatever bearer token it receives without first checking `iss`/`admin_session_token?`. Since the library's own `JwtPayload` API doesn't expose `admin_session_token?` publicly and doesn't gate `exchange_token` internally, host apps have no straightforward, documented way within this gem to reject non-admin tokens before calling `exchange_token`.

### Recommendation
In `ShopifyAPI::Auth::TokenExchange.exchange_token`, after decoding the `JwtPayload`, explicitly reject tokens whose `iss` does not end in `/admin` (i.e., raise `Errors::InvalidJwtTokenError` unless the token is an admin session token), mirroring the internal `admin_session_token?` check already used for `shopify_user_id`. Optionally expose `admin_session_token?` publicly on `JwtPayload` so host apps can also perform this check themselves.

### Proof of Concept
1. Attacker becomes a customer and begins checkout on the target shop; Shopify issues a checkout UI extension session token: `{ iss: "https://shop.myshopify.com/checkouts", dest: "https://shop.myshopify.com", aud: <app_client_id>, sub: "gid://shopify/Customer/...", exp: ... }`, signed with the app's `api_secret_key`.
2. Attacker extracts this token from the client-side checkout extension network traffic.
3. Attacker (or a compromised low-privilege component of the app) calls:
```ruby
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: stolen_checkout_token,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
```
4. `JwtPayload.new` accepts the token (only `aud` is checked), `dest_shop` is derived, and `exchange_token` posts to `/admin/oauth/access_token` with the app's `client_secret`, returning a valid merchant-level offline access token for the shop, as shown by `lib/shopify_api/auth/token_exchange.rb:29-63`.

        def exchange_token(session_token:, requested_token_type:, shop: nil)
          unless ShopifyAPI::Context.setup?
            raise ShopifyAPI::Errors::ContextNotSetupError,
              "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise ShopifyAPI::Errors::UnsupportedOauthError,
            "Cannot perform OAuth Token Exchange for private apps." if ShopifyAPI::Context.private?
          raise ShopifyAPI::Errors::UnsupportedOauthError,
            "Cannot perform OAuth Token Exchange for non embedded apps." unless ShopifyAPI::Context.embedded?

          # Validate the session token and use the shop from the token's `dest` claim
          jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
          dest_shop = jwt_payload.shop

          if shop
            ShopifyAPI::Logger.deprecated(
              "The `shop` parameter for `exchange_token` is deprecated and will be removed in v17. " \
                "The shop is now always taken from the session token's `dest` claim.",
              "17.0.0",
            )
          end

          shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
          body = {
            client_id: ShopifyAPI::Context.api_key,
            client_secret: ShopifyAPI::Context.api_secret_key,
            grant_type: TOKEN_EXCHANGE_GRANT_TYPE,
            subject_token: session_token,
            subject_token_type: ID_TOKEN_TYPE,
            requested_token_type: requested_token_type.serialize,
          }

          if requested_token_type == RequestedTokenType::OFFLINE_ACCESS_TOKEN
            body.merge!({ expiring: ShopifyAPI::Context.expiring_offline_access_tokens ? 1 : 0 })
          end
