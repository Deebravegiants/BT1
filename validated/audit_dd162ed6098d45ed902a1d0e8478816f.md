### Title
Webhook shop/topic identity forged via headers not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then trusts the `shop-domain` and `topic` HTTP headers — which are **not included in the signed material** — to route the webhook and to attribute the payload to a tenant (`shop`). This breaks the intended binding: `shop header used for tenant attribution == shop authenticated by the signature`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors are read straight from HTTP headers with no cryptographic binding to that signature: [2](#0-1) .

`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` field — for a `Webhooks::Request`, this is exactly `HMAC(secret, raw_body)`, nothing else: [3](#0-2) .

`Registry.process` performs exactly this check and, once it passes, immediately trusts `request.topic` (to pick the handler) and `request.shop` (passed straight into `WebhookMetadata` and handed to the app's handler as the tenant identifier) without any further verification that these header values are the ones Shopify actually associated with that signed body: [4](#0-3) .

Consequently, `HMAC(secret, body)` is a valid signature for *any* combination of `shop-domain`/`topic`/`webhook-id`/`api-version` headers sent alongside that same body — the signature is not bound to which shop or topic it is "for." An unprivileged internet user who can obtain one legitimate signed webhook body/HMAC pair (e.g., by installing the target app on their own free/dev store and receiving a real webhook, which any internet user can do for a public app) can resubmit that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `shop-domain` header (and/or `topic`, `webhook-id`) for a different shop or topic. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` will then treat the forged headers as authentic, invoking the handler with an attacker-chosen `shop` value.

This matches the report's bug class precisely: a field that is *acted on* (`shop`, used to route/attribute data to a tenant) is not covered by the same integrity check (`HMAC`) that is used to authenticate the request as coming from Shopify.

### Impact Explanation
Any host application built on this gem's documented `Webhooks::Registry.process` flow (as shown in `docs/usage/webhooks.md`) receives an unauthenticated `shop` value for every otherwise-"verified" webhook. If the host application uses `data.shop` to key session/token lookups, write to per-tenant storage, or make authenticated Admin API calls on behalf of "the shop," an attacker can inject falsified data (or replay another shop's data) under an arbitrary victim shop identifier — a cross-tenant data confusion/injection primitive, achievable purely by an internet user with no privileged credentials, satisfying the Critical "cross-tenant access" impact bucket.

### Likelihood Explanation
Likelihood is bounded by the requirement to obtain at least one valid `(raw_body, hmac)` pair for the target app. For any embeddable/public Shopify app, an attacker can trivially get this by installing the app on their own store and capturing the webhooks Shopify sends to the registered endpoint — this requires no special access, no leaked credentials, and no privileged account, only ordinary use of the (typically public) app-install flow. Given that pair, forging the `shop-domain`/`topic` headers on a replayed POST is trivial for anyone who can reach the app's public webhook URL.

### Recommendation
Bind the tenant/topic identity to the same integrity check used for the body: verify a full signable string that includes at minimum `shop-domain`, `topic`, and `webhook-id`/`api-version` alongside the raw body when computing/comparing the HMAC (or otherwise cryptographically bind the header values to the signature, e.g. by including them in `to_signable_string`), rather than trusting header-derived values that are excluded from HMAC coverage. At minimum, document/require that host applications independently validate that the shop in the webhook belongs to a shop that installed the app with a currently-active session before acting on the payload, and never trust `data.shop` alone as an authentication signal.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a webhook subscription (e.g., `orders/create`), causing Shopify to POST a body `B` to the app's webhook endpoint with headers:
   - `X-Shopify-Topic: orders/create`
   - `X-Shopify-Hmac-Sha256: HMAC(secret, B)` (base64)
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
2. Attacker captures `B` and the `Hmac-Sha256` value (both attacker-observable, since it's their own shop's traffic to their own subscribed endpoint, or replayed via any request logging they control).
3. Attacker crafts a new POST to the same public webhook endpoint with the *same* body `B` and *same* `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `raw_body` — this succeeds using the same `api_secret_key` [5](#0-4) [6](#0-5) .
5. The handler is invoked with `WebhookMetadata` carrying the attacker-controlled `shop: "victim-shop.myshopify.com"` [7](#0-6) , even though the signed body never originated from, nor was ever associated with, `victim-shop.myshopify.com`.
