### Title
CatFee API Key/Secret Logged in Plaintext at Info Level - (File: tesseract/messaging/tron/src/lib.rs)

### Summary
`TronClient::new` logs the entire `CatFeeConfig` struct — including the plaintext `api_key` and `api_secret` used to authenticate the relayer's CatFee bandwidth-purchasing account — at `info` log level via `{:#?}` Debug formatting, exactly mirroring the CWE-532 class described in GHSA-rpq8-q44m-2rpg (credential secrets exposed in service logs at the Information log level).

### Finding Description
`CatFeeConfig` is declared with a blanket `#[derive(Debug, Clone)]` and stores the CatFee API credentials as plain `String` fields with no redaction: [1](#0-0) 

When a TRON relayer chain is configured with CatFee credentials (used to purchase TRON energy/bandwidth before submitting transactions), `TronClient::new` builds this config and logs it wholesale at `info` level: [2](#0-1) 

Because `CatFeeConfig`'s `Debug` implementation is the default derived one (no `#[debug(skip)]`, no custom masking, unlike the pattern used elsewhere in the repo, e.g. `maskToml`/`maskSecret` in the simplex SDK), the `{:#?}` formatting call prints `api_key` and `api_secret` in cleartext into whatever log sink the relayer operator has configured (stdout, file, log aggregator, etc.) at the default `info` verbosity — the exact condition the advisory calls out as impacted ("Logging Level: Logs are generated at the information level" + "Client secret" credential description).

### Impact Explanation
Any party with read access to the relayer's info-level logs (log aggregation services, misconfigured log retention, shared hosting, CI artifact logs, support bundles, etc.) recovers the CatFee `api_key`/`api_secret` pair. Since `generate_signature` derives every request's HMAC-SHA256 authentication directly from `api_secret`, an attacker holding it can forge authenticated CatFee API calls as the relayer, potentially purchasing/rerouting TRON energy paid for by the relayer's CatFee account or draining any CatFee account balance — a concrete funds-loss/DoS vector for the relayer's transaction-submission pipeline on TRON (which depends on purchased energy to keep fee costs down and deliver messages).

### Likelihood Explanation
This triggers unconditionally and automatically whenever a TRON chain is configured with `catfee_api_key`/`catfee_api_secret` and the relayer runs at the (very common, often default) `info` log level — no attacker interaction with the protocol is required, only log access, which matches the same low-bar exposure pattern rated Medium in the original advisory.

### Recommendation
Do not log the raw `CatFeeConfig`; implement a custom `Debug` (or a wrapper newtype) that redacts `api_key` and `api_secret`, or log only non-sensitive fields (`api_base`, `timeout`) explicitly instead of `{:#?}` on the whole struct. Apply the same masking discipline already used in `sdk/packages/simplex/src/services/server/setup-api.ts`'s `maskToml`/`maskSecret` helpers.

### Proof of Concept
1. Configure a TRON chain block with `catfee_api_key = "REAL_KEY"` and `catfee_api_secret = "REAL_SECRET"`.
2. Run the relayer with default/info logging.
3. Observe the startup log line `"CatFee integration enabled: {:#?}"` at `tesseract/messaging/tron/src/lib.rs:257`, which prints the full `CatFeeConfig` Debug output including `api_key: "REAL_KEY"` and `api_secret: "REAL_SECRET"` in cleartext.
4. Anyone with access to those logs can reconstruct valid `CF-ACCESS-SIGN` HMAC signatures per `generate_signature` in `tesseract/messaging/tron/src/catfee.rs:93-101` and impersonate the relayer to CatFee's API.
