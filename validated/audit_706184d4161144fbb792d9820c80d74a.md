Confirmed: the gem's own documentation explicitly tells host apps to trust `data.shop` as "The shop domain of the webhook" and use it for tenant identification (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), while `HmacValidator.validate` only signs/verifies the raw body, not the shop-domain, topic, webhook-id, or api-version headers.

### Title
Webhook HMAC does not cover the `shop`, `topic`, `webhook_id` and `api_version` headers, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC solely against that body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers — all of which are exposed to the host application via `WebhookMetadata` and documented as trustworthy identity fields — are never included in the signed payload.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

`to_signable_string` returns only `@raw_body`, so `HmacValidator.validate_signature` computes the HMAC exclusively over the body bytes: [2](#0-1) 

`Registry.process` accepts the request purely based on that body-only HMAC, then constructs `WebhookMetadata` directly from the request's unauthenticated headers (`request.shop`, `request.topic`, `request.webhook_id`, `request.api_version`): [3](#0-2) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers with no cryptographic binding to the signed body: [4](#0-3) 

The gem's own documentation instructs host applications to use `data.shop` as the authoritative tenant identifier for the webhook (e.g. `shop_domain: data.shop`), reinforcing that this field is treated as an authenticated identity claim: [5](#0-4) 

This breaks the identity binding: **`hmac-verified(raw_body)` ⇏ `authenticated(shop-domain header)`**. Any party who can obtain one genuine Shopify-signed webhook delivery (e.g., an attacker who installs the app on their own store and triggers an event) possesses a `(raw_body, hmac)` pair that remains valid under `HmacValidator.validate` regardless of what `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, or `x-shopify-api-version` headers are attached to it. The attacker can freely rewrite these headers before POSTing to the app's webhook endpoint, and the gem will treat the request as authentic.

### Impact Explanation
This is a cross-tenant identity confusion: the host application receives a *validated* webhook whose `shop` claim was never actually checked against the signature. An attacker (any unprivileged Shopify merchant who installs the target app) can cause the host app to process attacker-supplied webhook body content while attributing it to an arbitrary victim `shop` domain, or relabel a legitimate topic (e.g. `orders/create`) as a security-sensitive topic (e.g. `app/uninstalled`, `shop/redact`) recognized by a different handler. Since apps commonly key their persisted data/session lookups by `data.shop` as directed by this gem's docs, this can lead to data being written to, or actions being taken against, the wrong merchant's tenant record — a cross-tenant access condition.

### Likelihood Explanation
Exploitability only requires the attacker to install the app on a shop they control (a normal, low-privilege action available to anyone who can install a public/development Shopify app) and to be able to POST arbitrary headers to the app's own publicly reachable webhook endpoint, which is the intended entry point for `ShopifyAPI::Webhooks::Registry.process`. No secrets, tokens, or elevated access are needed.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the verified body before they are surfaced to host-application handlers via `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), receiving a request with a valid `x-shopify-hmac-sha256` computed over the raw body using the app's `client_secret`.
2. Attacker replays this exact `(raw_body, hmac)` pair to the app's webhook endpoint but swaps the `x-shopify-shop-domain` header to `victim-shop.myshopify.com` (and/or changes `x-shopify-topic`/`x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the raw body against the HMAC — `#validate_signature` in `lib/shopify_api/utils/hmac_validator.rb` never inspects headers.
4. The host app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes attacker-controlled body content as if it were an authentic event from the victim shop.
