### Title
Permanent market freeze when accrued RAY value overflows `i128` before the index cap - ([File: common/src/rates/simulate.rs]) [1](#0-0) 

### Summary
A sufficiently large market can reach a state where every accrual panics while calculating `scaled * index / RAY`, even though the borrow index remains below `MAX_BORROW_INDEX_RAY`. [2](#0-1) [3](#0-2) 

### Finding Description
`global_sync` runs before market mutations and evaluates every elapsed accrual chunk. [4](#0-3) [5](#0-4) 

Each chunk first derives utilization by unscaling total borrowed and supplied shares with `scaled_to_original`, which is implemented as fallible half-up multiplication. [6](#0-5) [7](#0-6) 

The resulting RAY value is not bounded by the global index ceiling: an index can remain below `1e36` while `borrowed * borrow_index / RAY` or `supplied * supply_index / RAY` exceeds `i128::MAX`, causing `GenericError::MathOverflow`. [8](#0-7) [9](#0-8) 

The public path is permissionless: an authenticated caller may invoke `controller.update_indexes(caller, assets)`, which forwards the selected `HubAssetKey` list to `pool.update_indexes`. [10](#0-9) [11](#0-10) 

Because `last_timestamp` is only marked after all accrual chunks succeed, the same overflowing chunk repeats on every subsequent call to the market. [5](#0-4) 

### Impact Explanation
Once the market crosses this boundary, withdrawals, repayments, liquidations, bad-debt processing, flash loans, and any other operation that syncs the market revert before their protective logic or recovery path can run. [12](#0-11) [13](#0-12) 

Even governance's parameter-replacement path accrues under the old model before updating parameters, so it cannot bypass the panic. [14](#0-13) 

The in-repository stress test demonstrates this exact state: after repeated yearly accruals on a billion-token, 98%-utilized market, `update_indexes` fails with `MathOverflow`, the stored borrow index is still below `MAX_BORROW_INDEX_RAY`, and subsequent withdraw and repay calls also revert. [15](#0-14) 

This permanently freezes supplier principal and accrued yield and prevents repayment or liquidation of outstanding debt, which can leave the pool unable to operate and can convert otherwise recoverable debt into protocol insolvency. [15](#0-14) 

### Likelihood Explanation
The trigger requires an unusually large balance, high sustained utilization, and enough elapsed time for the index to grow beyond the market-specific representable-value ceiling. [16](#0-15) 

However, no privileged role is needed for the final state transition: any authenticated account can call `update_indexes` with the affected `HubAssetKey`, and ordinary users create the prerequisite exposure through supply and borrow. [10](#0-9) 

The protocol's documented cap is insufficient because it bounds only the index, not the product `scaled shares * index`; the test proves the representable-value cliff is reached first. [3](#0-2) [17](#0-16) 

### Recommendation
Compute utilization and accrued debt/supply values in a wider type, or saturate only the utilization inputs without allowing a market-wide panic. [18](#0-17) 

Additionally, enforce a market-specific safe index ceiling derived from current `borrowed` and `supplied` shares before accrual, so index growth stops before either unscaling multiplication can exceed `i128::MAX`. [19](#0-18) 

The fix should preserve recovery paths: repayment, withdrawal, liquidation, parameter updates, and recapitalization must remain callable after the relevant ceiling is reached. [12](#0-11) 

### Proof of Concept
The checked-in scenario supplies `1_000_000_000` whole 18-decimal tokens, borrows 98% of that market, advances time one year per iteration, and then calls `update_indexes`. [20](#0-19) 

At the cliff, `update_indexes` returns `MathOverflow`, `borrow_index < MAX_BORROW_INDEX_RAY`, and both `withdraw` and `repay` fail with the same error. [21](#0-20) 

A user-level reproduction is therefore:

```text
supply(18_decimal_asset, 1_000_000_000 whole units)
supply(collateral_asset, sufficient collateral)
borrow(18_decimal_asset, 980_000_000 whole units)
wait until index growth makes scaled_total * index / RAY exceed i128::MAX
update_indexes(caller, [HubAssetKey { hub_id, asset }])
withdraw(...amount = 1...)  // reverts during accrual
repay(...amount = 1...)     // reverts during accrual
```

The decisive overflow occurs at `scaled_to_original(borrowed, borrow_index)` or `scaled_to_original(supplied, supply_index)` inside `accrue_step`, before the index cap has an opportunity to stop growth. [2](#0-1)

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }

    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);

pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
