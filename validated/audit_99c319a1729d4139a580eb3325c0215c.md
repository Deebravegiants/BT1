Audit Report

## Title
CORS wildcard allowlist bypass via naive suffix match allows malicious origin impersonation - ([File: core/services/gateway/network/httpserver.go])

## Summary
`isAllowedOrigin` in the Gateway's user-facing HTTP server incorrectly validates wildcard CORS origin entries (e.g. `https://*.ethereum.org`) using a bare `strings.HasSuffix(originHost, allowedHost)` check without requiring a `.` domain-separator boundary. This allows an attacker who registers a domain that merely ends with the allowed suffix (e.g. `evilethereum.org` for allowed suffix `ethereum.org`) to have their origin treated as a trusted subdomain, and have it reflected verbatim into `Access-Control-Allow-Origin`.

## Finding Description
The `isAllowedOrigin` function strips the `*.` prefix from a wildcard config entry and then does a raw suffix comparison: [1](#0-0) . Because `strings.HasSuffix` performs no separator check, `strings.HasSuffix("evilethereum.org", "ethereum.org")` evaluates `true`, incorrectly classifying `evilethereum.org` as a subdomain of `ethereum.org`.

The result feeds directly into `handleRequest`, which reflects the attacker-supplied `Origin` header value verbatim into `Access-Control-Allow-Origin`, along with permissive `Access-Control-Allow-Methods` and `Access-Control-Allow-Headers`: [2](#0-1) . There is no additional origin-boundary check anywhere else in the file — `splitURL` only extracts scheme/host/port via `net/url` and `net.SplitHostPort`, it performs no domain-label validation: [3](#0-2) . The scheme and port checks preceding the host comparison do not mitigate this, since an attacker fully controls the scheme/port of their own malicious domain to match the victim's configured values.

## Impact Explanation
This is an in-scope gateway request impersonation / allowlist bypass. An operator configuring `CORSAllowedOrigins = ["https://*.ethereum.org"]` intends to trust only genuine subdomains of `ethereum.org` (e.g. `remix.ethereum.org`), consistent with the existing test asserting this exact scenario is allowed: [4](#0-3) . Due to the missing separator check, any unrelated attacker-registered domain ending in the same suffix (`evilethereum.org`) is also granted CORS trust, letting a malicious web page issue authenticated cross-origin requests to the Gateway's user-facing endpoint and read the JSON response — an origin-allowlist bypass enabling request impersonation against the internet-facing Gateway.

## Likelihood Explanation
Exploitation requires only registering an inexpensive domain name whose string ends with the configured wildcard suffix — no privileged access, credentials, node compromise, or victim interaction beyond visiting the attacker's page is needed. This is reachable by any unprivileged external client against `UserServerConfig` whenever `CORSEnabled = true` and a wildcard entry is configured, which is an example configuration shown in the integration test suite: [5](#0-4) .

## Recommendation
Require a proper subdomain boundary after stripping the `*.` prefix, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```
This ensures `evilethereum.org` is rejected while `remix.ethereum.org` (which ends with `.ethereum.org`) is still correctly allowed.

## Proof of Concept
1. Configure `UserServerConfig` with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. Send `POST /user` with header `Origin: https://evilethereum.org`.
3. In `isAllowedOrigin`, `allowedHost` becomes `ethereum.org`; `strings.HasSuffix("evilethereum.org", "ethereum.org")` returns `true`, so the function returns `true`.
4. Server response includes `Access-Control-Allow-Origin: https://evilethereum.org`, confirming the bypass. This can be added as a unit test analogous to the existing `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` test but asserting rejection of `https://evilethereum.org`, which currently fails.

		}

	}

}
