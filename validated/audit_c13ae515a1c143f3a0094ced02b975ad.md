### Title
Webhook shop-domain header is trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then passes the unauthenticated `shop-domain` header straight to the app's handler as the tenant identifier. Because the `shop` value is never included in the HMAC-signed material, an attacker who possesses one genuine `(body, hmac)` pair (e.g. from a webhook delivered to their own trial/dev store) can replay it to a victim app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header, and the signature check will still pass — causing the handler to process attacker-supplied data under a victim shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` returns only the raw request body: [1](#0-0) [2](#0-1) 

`Registry.process` validates authenticity purely with `Utils::HmacValidator.validate(request)`, which internally calls `to_signable_string` (the raw body only) and HMACs it with `Context.api_secret_key`: [3](#0-2) [4](#0-3) 

After the HMAC check passes, `request.shop` (parsed from the `x-shopify-shop-domain`/`shopify-shop-domain` header, entirely outside the signed bytes) is forwarded verbatim into `WebhookMetadata` and handed to the app's registered handler as the authoritative tenant identifier: [5](#0-4) [6](#0-5) 

The gem's own documentation instructs consumers to key business logic (job enqueuing, data association) directly off `data.shop`: [7](#0-6) 

This reproduces the tbtc bug class exactly: the value that is *acted on* (`shop`, used to bind the webhook payload to a tenant) is not the value that was *verified* (only the raw `body` is HMAC-covered). The equality the code implicitly assumes — `verified_bytes(hmac) == acted_on_identity(shop)` — does not hold, because `shop` is parsed from an unauthenticated header while the HMAC only binds `body`.

### Impact Explanation
This breaks the tenant/shop identity binding that host applications rely on to route and attribute webhook data (order updates, GDPR redact requests, uninstall notifications, etc.) to the correct merchant. An attacker who can obtain any single valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` — trivially available to them by operating their own installed/dev shop and capturing one of their own legitimate webhook deliveries — can replay that exact body/HMAC pair to the app's public webhook endpoint while forging the `shop-domain` header to name a victim shop. The `Registry.process` HMAC check still succeeds (it only checks the body), and the handler is invoked believing the payload originated from, and pertains to, the victim shop. Depending on the handler's use of `data.shop` (e.g. selecting which merchant record to write order/customer data against, or triggering `shop/redact` / `customers/redact` compliance flows for a targeted shop), this enables cross-tenant data confusion/injection using only the attacker's own valid webhook credentials against another tenant's identity — a cross-tenant boundary break within this gem's own verification code path.

### Likelihood Explanation
Exploitation only requires: (1) the attacker's own instance of the app receiving one legitimate webhook (already true for any attacker who installs a Shopify app that uses this pattern), and (2) network access to POST to the app's public webhook route with attacker-chosen headers, which is inherent to any internet-exposed webhook endpoint. No access token, `client_secret`, or privileged access is needed — the whole point of this report path is that `api_secret_key`/HMAC secrecy is preserved yet the binding still fails because the identity field is simply never part of the signed content.

### Recommendation
Include the shop-domain (and ideally topic and webhook-id) inside the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` value to the signed body before it is exposed to `WebhookHandler#handle`. At minimum, `Utils::VerifiableQuery#to_signable_string` for `Webhooks::Request` should incorporate the `shop-domain` header (matching how `Auth::Oauth::AuthQuery#to_signable_string` already binds `shop` into its signed string), and `Registry.process`/`HmacValidator` should reject requests where the authenticated shop does not match the tenant the app expects for that delivery.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook delivery, capturing the raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (both signed with the shared `api_secret_key`).
2. Attacker sends a POST to the victim app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid because it only signs `B`)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - Header `X-Shopify-Topic`: chosen to match a registered handler
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`; since it only HMACs `request.to_signable_string` (== `B`), validation succeeds. [8](#0-7) 
4. The handler's `handle(data:)` is invoked with `data.shop == "victim-shop.myshopify.com"` even though the payload actually originated from, and was signed for, the attacker's own shop — the app processes attacker data under the victim's tenant identity.
