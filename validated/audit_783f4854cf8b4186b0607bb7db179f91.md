### Title
IntentGatewayV2 (Tron) credits escrow by requested amount, not actual token balance increase, causing insolvent escrow accounting for non-standard ERC20 inputs - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron port of `IntentGatewayV2.placeOrder` escrows ERC20 inputs with a plain `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then credits `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is derived from the *requested* `order.inputs[i].amount`, not from any measured balance change. This is the exact `_depositAmount` bug class from the referenced report: the contract never checks whether the ERC20 transfer actually delivered the amount it assumes.

### Finding Description
In `placeOrder`, `reducedInputs` (used for the commitment hash and the escrow credit) is computed from `order.inputs[i].amount` *before* any tokens are moved: [1](#0-0) 

Later, in the non-predispatch escrow branch, the ERC20 leg is pulled with a raw `safeTransferFrom` and the escrow ledger is bumped by `reducedInputs[i].amount`, with no comparison to the contract's actual balance delta: [2](#0-1) 

The predispatch branch has the same defect — it computes `dust = balance - requiredAmount` against `order.inputs[i].amount`/`requiredAmount`, and always credits `reducedInputs[i].amount` regardless of what was actually swept from the dispatcher: [3](#0-2) 

This is a regression relative to the mainline EVM `IntentGatewayV2.sol`, which was explicitly hardened against this exact class of bug: it snapshots the balance before `safeTransferFrom`, and overwrites `order.inputs[i].amount` with the *actual* balance increase before computing protocol fees, escrow credit, and the commitment hash: [4](#0-3) 

The presence of dedicated `FeeOnTransferToken` regression tests for the mainline contract confirms the project already treats "transferred amount != requested amount" as a real threat model that must be measured post-transfer, not assumed: [5](#0-4) [6](#0-5) 

The Tron variant of `IntentGatewayV2.sol` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) does not carry this fix, so its escrow bookkeeping (`_orders[commitment][token]`) can permanently diverge from the actual token balance the contract holds whenever the input token doesn't transfer the full nominal amount (fee-on-transfer, deflationary/rebasing, or any non-strictly-compliant ERC20).

### Impact Explanation
Because `_orders[commitment][token]` is credited with more than the contract actually received, the aggregate escrow liabilities recorded across all orders denominated in that token can exceed the contract's real balance of that token. When `withdraw()` is later invoked (via `RedeemEscrow`/`RefundEscrow` on fill/cancel, or via `onGetResponse` for cross-chain cancellation), it pays out `body.tokens[i].amount` via a raw low-level `token.call(...)` and only guards against `_orders[commitment][token] == 0`, not against the contract's real balance: [7](#0-6) 

The result is a shared shortfall: whichever order's beneficiary/solver withdraws first drains real tokens the ledger says are still owed to other orders, so later, legitimate withdrawals for the same token can fail or come up short — a permanent freezing/loss of user or solver funds. This is consistent with the "protocol leakage" classification the original report and its judge assigned, and meets the Medium-risk bar (concrete freezing/loss of escrowed funds) requested by the rules.

### Likelihood Explanation
Any ERC20 token registered as an order input that doesn't deliver the exact requested amount on `transferFrom` (fee-on-transfer, deflationary, rebasing, or a token with any quirky transfer hook) triggers this on every `placeOrder` call by an ordinary, unprivileged user placing an intent — no special privileges, governance, or race condition needed. Likelihood is directly tied to which tokens get listed as intent inputs on the Tron deployment, but the code path itself is trivially reachable by any user submitting an order with such a token.

### Recommendation
Mirror the fix already applied to `evm/src/apps/IntentGatewayV2.sol`: snapshot `IERC20(token).balanceOf(address(this))` before each `safeTransferFrom`, overwrite `order.inputs[i].amount` with the post-transfer balance delta, and only then compute `protocolFeeBps`, `reducedInputs`, and the commitment hash. Apply the same balance-delta measurement to the predispatch sweep-from-dispatcher path, so `_orders[commitment][token]` is always credited with tokens the contract actually possesses.

### Proof of Concept
1. Admin/governance registers a fee-on-transfer ERC20 (e.g., 1% fee) as a valid intent input token on the Tron `IntentGatewayV2` deployment.
2. User A calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000}`. The contract actually receives only 990 tokens via `safeTransferFrom`, but `_orders[commitment][FOT]` is credited with `reducedInputs[0].amount` (≈1000 minus protocol fee), i.e., more than the 990 tokens actually held.
3. User B places a second order with the same `FOT` token, again under-crediting the real balance the same way; the contract's cumulative escrow ledger for `FOT` now exceeds its actual `balanceOf(this)`.
4. When both orders are filled/cancelled and `withdraw()` is called for each commitment in turn, the second `withdraw()` call attempts to `token.call(transfer.selector, beneficiary, amount)` for an amount that, combined with the first payout, exceeds the contract's real `FOT` balance — the transfer fails/reverts (or, since the code doesn't decode the ERC20 return value, silently under-pays if the token returns `false` rather than reverting), leaving that beneficiary's escrow permanently unredeemable.

/// @dev ERC20 with a configurable transfer fee (in basis points).
contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
