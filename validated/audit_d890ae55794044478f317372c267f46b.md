Based on my research, I found a concrete analog. The relevant bug class from the CVE — an **unvalidated subtraction that underflows and corrupts control flow** — maps onto alt.fun's own `assetReserve - virtualLtReserve` arithmetic, which is reachable by ordinary trader transactions and is not defended anywhere in the codebase I found.

### Title
Rounding-favorable sells can drive `assetReserve` below `virtualLtReserve`, causing a permanent underflow-revert DoS of `Bonding.buy` / `canGraduate` - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.canGraduate` and `Bonding._prepareGraduationLiquidity` both compute `realLtRaised`/`ltFromPair` as `assetReserve - virtualLtReserve`, an unchecked (Solidity-0.8-checked, i.e. Panic-reverting) subtraction that assumes `assetReserve >= virtualLtReserve` always holds. `Router._computeSell`'s floor-division rounding, combined with `Pair.swap`'s `+1` K-invariant slack, lets a trader extract slightly more LT per sell than the exact curve formula allows. Round-tripping buys/sells back to `tokenReserve == totalSupply` (i.e. zero real tokens outstanding) can therefore leave `assetReserve` a hair below `virtualLtReserve`, and every future call to `canGraduate` — which `_executeBuy` calls unconditionally at the end of every buy — permanently reverts with an arithmetic Panic, bricking the bonding curve.

### Finding Description
`Bonding.canGraduate` reads: [1](#0-0) 

and `_prepareGraduationLiquidity` (called from `_enterGraduating`, itself called at the end of every buy via `_executeBuy`) computes: [2](#0-1) 

Both subtractions assume `assetReserve >= virtualLtReserve` (the invariant "real LT raised is never negative"). `virtualLtReserve` is recovered as `Pair.k() / Token.TOTAL_SUPPLY()`, an immutable value fixed at mint: [3](#0-2) 

The invariant is only exactly true under continuous (real-number) constant-product math. `Router._computeSell` uses floor division when computing `assetOut`, which is systematically favorable to the seller by up to 1 wei per call: [4](#0-3) 

`Pair.swap`'s K-invariant check adds `+1` to both reserves before comparing against `k`, explicitly tolerating a small downward drift in the true product on every swap: [5](#0-4) 

Because `Router.sell`/`Router.buy` compute their own `newReserveAsset`/`newReserveToken` and pass them straight into `Pair.swap`, the `+1` slack in `Pair.swap` never actually blocks Router's already-rounding-favorable-to-trader values — it simply confirms them. A trader can therefore perform a sequence of buys followed by sells that returns `tokenReserve` to exactly `totalSupply` (i.e. zero real tokens outstanding on the curve, which is the state where the exact-math invariant requires `assetReserve == virtualLtReserve`), while the accumulated floor-rounding on the sell leg has extracted slightly more LT than deposited, leaving `assetReserve` a few wei below `virtualLtReserve`.

Once that happens, `assetReserve - virtualLtReserve` underflows. `canGraduate` is called unconditionally at the end of `_executeBuy` for every single future buy: [6](#0-5) 

so the Panic revert from the underflow propagates out of `Bonding.buy` itself, not just out of a view helper — the curve becomes permanently unbuyable through `Zap.buy`/`Bonding.buy`. `Bonding.triggerGraduation` (permissionless) hits the same underflow via `canGraduate`, so there is no rescue path either — the token is stuck in `Lifecycle.Curve` forever, unable to trade forward or graduate.

### Impact Explanation
This is a permanent freeze of the bonding curve for the affected token: no further `Zap.buy`/`Bonding.buy` calls can succeed (they all revert on the `canGraduate` Panic at the end of `_executeBuy`), and `triggerGraduation` cannot rescue it either since it calls the same reverting `canGraduate`. Any LT already raised on the curve, and the 250M `lpReserve` tokens parked in `Bonding` for graduation, are stranded — the token can never reach `finalizeGraduation` and its holders/creator lose their exit path via the curve (sells that don't need `canGraduate` may still partially work, but the token can never graduate to the HyperSwap LP, permanently freezing the creator's and any remaining holders' upside and the reserved LP tokens).

### Likelihood Explanation
Reachable by any single unprivileged trader using only `Zap.buy`/`Zap.sell` (or `Bonding.buy`/`Bonding.sell` directly if allowlisted as a router) — no privileged role required. The per-trade rounding drift is at most ~1 wei, so the attack requires driving `tokenReserve` back to exactly `totalSupply` via a carefully constructed sequence of buys/sells (each of which is a normal, permitted operation), which is gas-costly but requires no special access and no cooperation from any other party; it is purely a function of the rounding directions in `Router._computeBuy`/`_computeSell`, which the codebase itself flags as an area of subtlety (`docs/contracts-scope.md`'s "Virtual token reserve" and "Parabola invariant" sections, and the `+1` K slack noted in `Pair.swap`).

### Recommendation
Use a saturating subtraction (matching the pattern already used defensively in `finalizeGraduation`'s `protectedLT` computation) for both `canGraduate`'s `realLtRaised` and `_prepareGraduationLiquidity`'s `ltFromPair`, e.g. `assetReserve > virtualLtReserve ? assetReserve - virtualLtReserve : 0`, so a rounding-induced dip below the virtual floor degrades gracefully to "nothing raised yet" instead of permanently reverting every future buy. Additionally, tighten `Router._computeSell`/`_computeBuy` rounding so it never favors the trader beyond the pair's own `+1` K tolerance, eliminating the drift that can push `assetReserve` below `virtualLtReserve` in the first place.

### Proof of Concept
1. Launch a token via `Zap.createToken` (standard seed buy), leaving `Bonding` in `Lifecycle.Curve` with `tokenReserve == totalSupply - curveSupplySeed`, `assetReserve == virtualLtReserve + seedRealLt`.
2. As an unprivileged trader, repeatedly call `Zap.buy` then `Zap.sell` (or a single buy followed by a full sell of the exact tokens received) in a loop sized so that after each round trip `tokenReserve` returns closer to `totalSupply` (i.e. sell back slightly more real tokens than were net-added), exploiting `Router._computeSell`'s floor-division favorability each time.
3. After enough iterations, the cumulative 1-wei-per-trade favorable rounding on sells pushes `assetReserve` to `virtualLtReserve - 1` (or lower) while `tokenReserve == totalSupply` (no real tokens net outstanding).
4. Call `Bonding.buy` (via `Zap.buy`) once more, or call `Bonding.triggerGraduation`: `_executeBuy`/`canGraduate` computes `assetReserve - virtualLtReserve`, underflows, and the whole transaction reverts with an arithmetic Panic — permanently, since `assetReserve`/`virtualLtReserve` cannot be repaired by any external call. The token's curve is now permanently frozen: no future `Bonding.buy` or `Bonding.triggerGraduation` call can ever succeed for this token.

        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 assetOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
