## Title
Signed calldata authorization in `pallet-hyper-fungible-token` omits transfer context, allowing beneficiary-signed `RuntimeCall`s to be dispatched detached from the bridged amount/asset/source-chain that was supposed to gate them - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The Steam report showed that a whitelisted third-party embed (codepen) was trusted to run arbitrary code inside a privileged client context, because the "trust" check (is this provider on the whitelist?) was disconnected from what the embedded content actually did. `pallet-hyper-fungible-token`'s cross-chain calldata feature has the analogous structural flaw: it authenticates *who* may dispatch a `RuntimeCall` (via a signature over `(nonce, runtime_call)`), but never binds that authorization to *what bridge transfer* it rides on. Any unprivileged party who can call the peer contract's `send()` (e.g. `HyperFungibleToken.send`) supplies the `amount`, `local_asset_id`/source chain, and `beneficiary`; none of that is covered by the beneficiary's signature, so the same signed authorization can be attached to a transfer whose value/asset/origin differs from what the beneficiary actually signed for.

### Finding Description
In `on_accept`, when `SubstrateCalldata.signature` is present, the module verifies it over `(nonce, substrate_data.runtime_call)` only: [1](#0-0) 
and then dispatches `runtime_call` with `RawOrigin::Signed(beneficiary)`: [2](#0-1) 

The `amount`, `local_asset_id` (i.e. which token), and `source` (which chain sent it) are all determined earlier in `on_accept` from attacker/sender-controlled `PostRequest`/`Message` fields, and are never mixed into the signed payload: [3](#0-2) 

On the EVM side, `params.amount`, `params.to` (beneficiary) and `params.data` (which embeds the beneficiary's signature + runtime call) are all supplied by whoever calls `send()` — any unprivileged account: [4](#0-3) 

Because the signed message is only `(nonce, runtime_call)`, a beneficiary's signature — once it becomes known to a third party (e.g. shared off-chain for one intended transfer, or observed in a prior on-chain event/extrinsic) — can be repackaged by any unprivileged sender into a `send()` call carrying a different `amount`, a different registered asset/source chain, or an unrelated bridging leg, and the pallet will still dispatch the exact same privileged `RuntimeCall` as the beneficiary, gated only by their nonce being unconsumed. This decouples "the beneficiary authorized this call" from "in the context of this specific bridged value," letting an unprivileged relayer/sender trigger an unauthorized app action as the beneficiary under conditions the beneficiary never approved.

This mirrors the report's root cause: trust is established at the wrong granularity (whitelisted provider / valid signature) while the thing actually executed (arbitrary embedded code / arbitrary `RuntimeCall`) is unconstrained by the context that was supposed to scope it.

### Impact Explanation
`runtime_call.dispatch(RawOrigin::Signed(beneficiary))` executes with the beneficiary's full signed origin, subject only to the runtime's `BaseCallFilter`: [5](#0-4) 
Since the call itself is attacker-supplied (via SCALE-encoded `substrate_data.runtime_call`) and can be *any* dispatchable not filtered out, and its execution is untethered from the actual bridged value/asset/chain, this is an unauthorized-app-action primitive: a beneficiary's authorization intended for one bridging context can be triggered by an unrelated transfer of arbitrary amount/asset, at a time chosen by an unprivileged party, achieving code-injection-style abuse of a privileged execution channel. This satisfies the "unauthorized app action" acceptance criterion.

### Likelihood Explanation
Exploitation requires no special privilege — any account able to call `send()` on the peer `HyperFungibleToken`/`WrappedHyperFungibleToken` contract can trigger the destination pallet's calldata path with a `substrate_data.signature` obtained by any means (a beneficiary who signs off-chain for one legitimate purpose, or a signature captured from a previous on-chain event, since neither this pallet nor the docs indicate the signature or its payload is kept confidential). The main constraint is a fresh/matching nonce, which is satisfiable whenever the beneficiary account hasn't yet used the nonce the signature commits to (e.g., a freshly funded account at nonce 0, or between signing and normal use).

### Recommendation
Include the transfer context in the signed payload — at minimum `local_asset_id`/`source` chain identifier, `message.amount`, and ideally a domain separator (e.g. genesis hash or the pallet's own `PALLET_ID`) — so a beneficiary's signature is cryptographically bound to the specific bridged value/asset/chain it was meant to gate, not just to an arbitrary `(nonce, call)` pair that can be replayed under any qualifying transfer.

### Proof of Concept
1. Beneficiary `B` signs `(nonce_B, call_X)` off-chain for a specific intended purpose (e.g., they expect a large qualifying transfer to authorize `call_X`).
2. Attacker `A` (any unprivileged account) observes/obtains this `(signature, call_X)` pair.
3. `A` calls `HyperFungibleToken.send()` with `params.to = B`, an arbitrary (e.g., minimal) `params.amount`, and `params.data` containing `SubstrateCalldata { signature: Some(sig), runtime_call: call_X }` — see `HyperFungibleToken.sol` `send`/`_buildDispatchPost`. [6](#0-5) 
4. On the destination chain, `on_accept` mints the (attacker-chosen, possibly minimal) `amount` to `B`, verifies the signature over `(nonce_B, call_X)` only — with no check on `amount`/`local_asset_id`/`source` — and dispatches `call_X` as `RawOrigin::Signed(B)`. [7](#0-6) 
5. `call_X` executes as `B` in a context (transfer size/asset/source chain) that `B` never authorized, demonstrating unauthorized app action detached from the signed transfer's intended scope.

    /**
     * @dev Builds the DispatchPost from SendParams.
     */
    function _buildDispatchPost(SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }

    /**
     * @dev Burns `params.amount` from the caller and sends an ISMP POST request to the
     * destination chain. Fees can be paid in native tokens (via msg.value) or in the
     * host's fee token (pulled from msg.sender).
     * @param params The send parameters including destination, recipient, amount, and optional calldata
     */
    function send(SendParams calldata params) external payable whenNotPaused {
        _burn(msg.sender, params.amount);
        DispatchPost memory request = _buildDispatchPost(params);

        bytes32 commitment;
        if (msg.value > 0) {
            commitment = IDispatcher(_host).dispatch{value: msg.value}(request);
        } else {
            commitment = dispatchWithFeeToken(request);
        }

        emit Sent({
            from: msg.sender,
            to: params.to,
            dest: string(params.dest),
            amount: params.amount,
            commitment: commitment
        });
    }
