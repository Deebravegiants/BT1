### Title
Fee-on-transfer / deflationary tokens break pool solvency in Deposit and Swap (unbacked LP minting and reserve drain) - (File: program/src/processor.rs)

### Summary
`process_deposit`, `process_swap_base_in`, and `process_swap_base_out` (and their V2 counterparts) assume that the amount transferred into a vault via `Invokers::token_transfer` is fully credited to that vault. If the coin or pc mint is a fee-on-transfer/deflationary SPL token, the vault actually receives less than the nominal amount, but all downstream accounting (LP minting math, pnl deltas, and the constant-product invariant used to size the counter-asset payout) is computed from the nominal, pre-fee amount.

### Finding Description
In `process_deposit`, `total_coin_without_take_pnl`/`total_pc_without_take_pnl` are snapshotted from the vault balances before any transfer occurs [1](#0-0) . `deduct_coin_amount`/`deduct_pc_amount` are then derived purely from the caller-supplied `deposit.max_coin_amount`/`deposit.max_pc_amount` and the invariant ratio, not from any post-transfer measurement [7](#0-6) . The program transfers `deduct_coin_amount`/`deduct_pc_amount` from the user to the vaults [3](#0-2) , mints `mint_lp_amount` LP tokens computed from those same nominal deduct amounts [8](#0-7) , and updates `target_orders.calc_pnl_x`/`calc_pnl_y` using the nominal `deduct_pc_amount`/`deduct_coin_amount` as well [9](#0-8) . If the coin/pc mint charges a transfer fee, the vault's actual balance increase is smaller than `deduct_coin_amount`/`deduct_pc_amount`, but LP tokens are minted as if the full amount arrived — this is an unbacked LP mint.

The same root cause affects every swap path: `swap.amount_in` (base-in) or `swap_in_after_add_fee` (base-out) is transferred into the input vault via `Invokers::token_transfer` [10](#0-9) , but `swap_amount_out` on the opposite side is computed from the constant-product invariant using the nominal `amount_in`, not the amount the vault actually received [11](#0-10) . A fee-on-transfer input token therefore lets the pool pay out more of the other asset than the input side actually backs, silently draining real reserves on every such swap.

`Invokers::token_transfer`/`token_transfer_with_authority` are raw `spl_token::instruction::transfer` CPI wrappers with no balance-delta verification [12](#0-11) , so nothing in the call chain detects or compensates for a transfer fee.

### Impact Explanation
This is a direct analog of the reported bug class ("Bonding doesn't work with fee-on-transfer tokens" / measuring pre/post balance instead of assuming full amount received), but here the impact is stronger than a simple revert: for Deposit it results in unbacked LP token minting (diluting/insolvent pool accounting), and for Swap it results in one side of the pool being drained relative to what the counter-asset actually backs — both are concrete fund-safety issues, not just a DoS. Every LP or trader interacting with a pool whose coin or pc mint has a transfer fee is affected, and other LPs' redeemable share of the pool is permanently reduced.

### Likelihood Explanation
Reachable by any unprivileged user submitting a single `Deposit`, `SwapBaseIn`/`SwapBaseInV2`, or `SwapBaseOut`/`SwapBaseOutV2` instruction with attacker-chosen token accounts, provided the pool's coin or pc mint implements a transfer fee (a legitimate, permissionless SPL/Token-2022-style token feature). No privileged signer or non-default build is required; the program itself never validates that the mint is fee-free before initializing or trading a pool.

### Recommendation
Measure the vault's token balance immediately before and immediately after each `Invokers::token_transfer` call and use the observed delta (not the nominal instruction amount) for all subsequent accounting: `mint_lp_amount`/`calc_pnl_x`/`calc_pnl_y` in `process_deposit`, and the invariant-based `swap_amount_out`/`swap_in_after_add_fee` calculations in the swap handlers. Alternatively, explicitly reject mints that report a non-zero `TransferFeeConfig` (or any transfer-hook that can reduce the transferred amount) during `Initialize2`.

### Proof of Concept
1. Create a pool via `Initialize2` where the pc (or coin) mint is a standard fee-on-transfer SPL token that deducts, e.g., 5% on every `Transfer`.
2. A user with `max_coin_amount`/`max_pc_amount` calls `Deposit`. The program computes `deduct_pc_amount` from the full nominal amount and calls `Invokers::token_transfer` for that amount [13](#0-12) ; the pc vault only receives 95% of `deduct_pc_amount` due to the token's fee.
3. `mint_lp_amount`, computed from the full nominal `deduct_pc_amount`/`deduct_coin_amount` [14](#0-13) , is minted to the depositor's LP account regardless of the shortfall — the pool's LP supply now overstates the actual backing assets.
4. Repeating deposits with the fee-on-transfer token progressively dilutes existing LPs' redemption value on `Withdraw`, since withdrawal payouts (`process_withdraw`) are computed from `amm.lp_amount` share of the (now under-collateralized) vault balances [15](#0-14) .
5. Equivalently, calling `SwapBaseIn` with a fee-on-transfer coin mint transfers `swap.amount_in` nominally into `amm_coin_vault` while the vault actually receives less; `swap_amount_out` is still paid out from `amm_pc_vault_info` based on the full nominal `amount_in` [16](#0-15) , draining pc reserves beyond what the coin side actually backs.

    pub fn swap_token_amount_base_in(
        amount_in: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_out;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_out = pc - coin * pc / (coin + amount_in)
                // => amount_out = ((pc * coin + pc * amount_in) - coin * pc) / (coin + amount_in)
                // => amount_out =  pc * amount_in / (coin + amount_in)
                let denominator = total_coin_without_take_pnl.checked_add(amount_in).unwrap();
                amount_out = total_pc_without_take_pnl
                    .checked_mul(amount_in)
                    .unwrap()
                    .checked_div(denominator)
                    .unwrap();
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)
                let denominator = total_pc_without_take_pnl.checked_add(amount_in).unwrap();
                amount_out = total_coin_without_take_pnl
                    .checked_mul(amount_in)
                    .unwrap()
                    .checked_div(denominator)
                    .unwrap();
            }
        }
        return amount_out;
    }
