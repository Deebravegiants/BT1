### Title
Webhook shop/topic/webhook-id identity fields are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)`. The `shop`, `topic`, `webhook_id`, and `api_version` fields that the handler actually acts on are read from unauthenticated HTTP headers and are never included in the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers that are not part of the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then dispatches the handler using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [3](#0-2) 

The HMAC secret (`Context.api_secret_key`) is the app's single API secret, shared across every shop/tenant that has the app installed — it is not shop-specific: [4](#0-3) 

This breaks the intended binding `hmac == HMAC(secret, body)` ⇒ `(shop, topic, webhook_id)` are also authentic. In reality the equality only proves the body bytes were signed by the app's secret at some point for some webhook; it says nothing about which shop, which topic, or which webhook the signature was meant for.

### Impact Explanation
A merchant who installs the app on their own store (an ordinary, unprivileged action requiring no special credential) receives genuine webhook deliveries with a valid `X-Shopify-Hmac-Sha256` signature over their own payload. Because `shop-domain`, `topic`, and `webhook-id` headers are outside the signed content, that same attacker can replay the identical raw body and valid signature to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim tenant and/or the `X-Shopify-Topic`/`X-Shopify-Webhook-Id` headers for a different topic/webhook. `Registry.process` will still accept it (`Utils::HmacValidator.validate` only checks the body signature) and will invoke the registered handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ..., webhook_id: request.webhook_id)`, i.e., attacker-controlled, unauthenticated identity fields. If the host application trusts `shop`/`topic`/`webhook_id` from this metadata (as the gem's own documentation instructs apps to do) to look up per-tenant sessions or take shop-scoped action, this results in cross-tenant data injection/impersonation — the app processes forged data believing it originates from a different, victim shop.

### Likelihood Explanation
Any developer/merchant can install the app for free on a store they control and capture at least one genuinely signed webhook body/signature pair, then replay it with modified `shop-domain`/`topic`/`webhook-id` headers — no privileged credential, access token, or `api_secret_key` knowledge is required. The `Registry.process` code path performs no additional verification of these headers, so the attack is straightforward and repeatable for every registered handler.

### Recommendation
Include the identity-critical fields (`shop`, `topic`, and ideally `webhook_id`) in the signable content that is HMAC-verified, or otherwise cryptographically bind them to the signature (e.g., by validating the shop against a known, previously-established session/store record before dispatching to a handler, and rejecting any header-derived shop/topic/webhook_id that isn't independently corroborated). At minimum, document that host applications must not fully trust `WebhookMetadata#shop`/`#topic`/`#webhook_id` without additional binding, or add a check within `Registry.process` that cross-validates the header-derived shop against session data known to the app before invoking handlers.

### Proof of Concept
1. Install the target app on a test/dev store you control (`attacker.myshopify.com`), triggering a real webhook, e.g. `orders/create`.
2. Capture the raw request body and the valid `X-Shopify-Hmac-Sha256` header sent by Shopify for that webhook (both are computed only from the body and the app's `client_secret`, which is identical across all shops using the app).
3. Replay the exact same raw body and HMAC header to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com` (and/or change `X-Shopify-Topic`/`X-Shopify-Webhook-Id` to a different registered topic/id).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `Digest.hexencode(...) == HMAC(secret, raw_body)` — see: [3](#0-2) 
5. The handler is invoked with `WebhookMetadata` carrying the attacker-chosen `shop`/`topic`/`webhook_id`, even though those values were never authenticated.
