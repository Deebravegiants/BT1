### Title
`PoaBridge.describeWithdrawal()` matches batch withdrawal results by `assetId` only, causing status/txHash misreport for same-asset withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal()` looks up the on-chain withdrawal result using `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, matching purely on `assetId` and ignoring the withdrawal's `index`, `destinationAddress`, or `amount`. When a batch of intents contains more than one withdrawal for the same `assetId` (e.g., two BTC withdrawals to different destination addresses in a single NEAR transaction), each call to `describeWithdrawal()` for a different `index` can resolve to the same matched record, reporting one withdrawal's completed status/`txHash` for another withdrawal that may still be pending, failed, or refunded.

### Finding Description
`describeWithdrawal` is defined as: [1](#0-0) 

The relevant matching call passes only `args.withdrawalParams.assetId` (no `index`, no `destinationAddress`, no `amount`) to `findMatchingWithdrawal`, and the code comment even states the API response list is "unsorted, so we match by assetId instead of index" — explicitly acknowledging that `index` is not used for disambiguation. This is confirmed by the existing repo test, which documents the behavior "matches withdrawal by assetId, not by index": [2](#0-1) 

The `Bridge.describeWithdrawal` interface contract is a "One-shot status check for a withdrawal" keyed by a `WithdrawalIdentifier` that includes `index`: [3](#0-2) 

If a caller processes a batch withdrawal (the SDK explicitly supports batches, see `sdk.ts`/README batch examples) with two or more withdrawals sharing the same `assetId` (e.g., withdrawing the same token to two different destination addresses, or a retry that produces multiple PoA withdrawal records for the same asset within one NEAR tx), `findMatchingWithdrawal` has no way to disambiguate them by `index`. The lookup can therefore return the wrong record — reporting `status: "completed"` with the wrong `txHash` for a withdrawal index that is actually still `PENDING` or has `FAILED`/`REFUNDED`, while the withdrawal that actually completed may be reported as pending or matched to the wrong `txHash`.

This breaks the equality "status/txHash reported for withdrawal N == actual on-chain outcome for withdrawal N," which is exactly the class of bug flagged in the external report's rules ("a status reported that is not the on-chain outcome").

### Impact Explanation
An integrator (e.g., a custodial service or exchange) that credits or releases funds to a user based on `describeWithdrawal()` reporting `status: "completed"` for a specific batch index could credit/release for a withdrawal that has not actually completed, or misattribute one destination's `txHash` to another destination's withdrawal record — resulting in a double credit/refund or premature release of funds on the assumption that a specific leg of the batch settled. This matches the "High" impact bucket: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This requires no malicious actor — it triggers under ordinary usage whenever a batch of withdrawals contains two or more entries with the same `assetId` (same token) processed through the PoA bridge, which is a normal and explicitly supported usage pattern (batch withdrawals, described in the README). The bug is deterministic given the described matching logic and is not dependent on adversarial input, RPC misbehavior, or third-party trust assumptions excluded by the rules.

### Recommendation
Change `findMatchingWithdrawal` (and the call in `describeWithdrawal`) to disambiguate by additional fields available in the withdrawal record — at minimum `destinationAddress`/`account_id` and `amount`, and ideally a stable per-withdrawal identifier from the PoA API — rather than by `assetId` alone, so that each `index` in a batch resolves to its own distinct on-chain record.

### Proof of Concept
Given the existing repo test `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.test.ts:1054-1111` ("matches withdrawal by assetId, not by index"), the following scenario demonstrates the misreport potential without any adversarial actor:
1. Submit a batch NEAR intent containing two `ft_withdraw` withdrawals for the same `assetId` (`nep141:btc.omft.near`) to two different destination BTC addresses (index 0 and index 1).
2. The PoA API returns two withdrawal records for `near-tx-hash`, one `COMPLETED` and one still `PENDING`, both for `nep141:btc.omft.near`.
3. Call `bridge.describeWithdrawal({ index: 1, withdrawalParams: { assetId: "nep141:btc.omft.near", ... }, tx: { hash: "near-tx-hash" } })`.
4. Because `findMatchingWithdrawal` filters by `assetId` only (as shown in the cited test, which selects the first/only matching-asset record regardless of `index`), the call for index 1 (whose real withdrawal is `PENDING`) can return the `COMPLETED` record intended for index 0 — reporting `status: "completed"` and the wrong `txHash` for an index that has not actually settled.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
