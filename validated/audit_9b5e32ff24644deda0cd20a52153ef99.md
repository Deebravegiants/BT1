### Title
Unchecked ERC20 `transfer` return value in `IntentGatewayV2.withdraw`/`SweepDust` (Tron) can silently fail while escrow state is finalized, permanently freezing/burning escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed order funds and sweeps dust using a raw low-level `call` to the ERC20 `transfer` selector, but only checks that the *call itself* did not revert (`success`). It never decodes/validates the ABI-encoded boolean return value of `transfer`. For non-reverting-on-failure ERC20 tokens (e.g. ZRX-style tokens that return `false` instead of reverting), `success` will be `true` even though zero tokens were actually moved, while the contract still finalizes escrow state as fulfilled and decrements internal accounting.

### Finding Description
In `withdraw()`, escrowed tokens are released to a beneficiary via: [1](#0-0) 

and transaction fees are paid out with the same unchecked pattern: [2](#0-1) 

The same pattern is used in `SweepDust` handling inside `onAccept`: [3](#0-2) 

In all three cases, the code only checks `success` from the low-level `.call`, never decoding the returned `bytes` to verify the ERC20 contract actually returned `true`. A token that returns `false` on failure (rather than reverting) will make `success == true` at the EVM-call level, so the `if (!success) revert TransferFailed();` guard never triggers.

`withdraw()` is reached from `onAccept()` when handling `RequestKind.RedeemEscrow` / `RequestKind.RefundEscrow`, gated only by `authenticate(incoming.request)` — i.e., delivery of a relayed, proof-verified ISMP message, not a privileged caller: [4](#0-3) 

Critically, `withdraw()` unconditionally marks the order as filled and decrements the escrow ledger regardless of whether the token transfer actually succeeded: [5](#0-4) 

This means for a misbehaving/non-standard ERC20 asset, `_filled[body.commitment]` is set and `_orders[body.commitment][token]` is decremented even though the beneficiary received nothing — the escrowed tokens remain stuck in the contract with no remaining accounting path to reclaim them, since the order is already marked filled/refunded.

Note: the primary (non-Tron) `evm/src/apps/IntentGatewayV2.sol` and `intentsv2/IntentsBase.sol` consistently use `SafeERC20.safeTransferFrom`/`safeTransfer` (confirmed at `evm/src/apps/IntentGatewayV2.sol:250,321` and the input-taking paths reviewed), so this defect is isolated to the Tron contract variant.

### Impact Explanation
This is a permanent freezing-of-funds bug: escrowed order funds can be marked as released/refunded (updating internal accounting and `_filled` state) without the underlying ERC20 tokens actually leaving the contract for tokens that return `false` on failed transfers instead of reverting. Once marked filled, there is no retry or reclaim path, so the funds become permanently stuck/unbacked in the ledger. This matches the report's core class (unchecked ERC20 return values leading to loss of funds) at High/Medium severity for an intents/escrow bridge component.

### Likelihood Explanation
Requires the deployment to support (or be tricked into interacting with) an ERC20 token that returns `false` rather than reverting on transfer failure — a known, real-world token behavior class (e.g., legacy tokens like ZRX). Any relayer can trigger `withdraw()` by delivering a valid `RedeemEscrow`/`RefundEscrow` message once such a token is used as an order asset, so exploitation likelihood depends on token whitelisting/listing practices for the Tron deployment rather than any special privilege.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer`/`safeTransferFrom` (already imported and used elsewhere in the same file), which correctly reverts on both call failure and a `false` return value.

### Proof of Concept
1. Whitelist/accept a non-standard ERC20 token (returns `false` on failed `transfer`, does not revert) as an order input asset on the Tron `IntentGatewayV2` deployment.
2. Create/fill an order such that the token becomes insufficient at payout time (e.g., contract balance manipulated to be less than requested, or token enters a paused/restricted state causing `transfer` to return `false`).
3. Relayer delivers a `RedeemEscrow`/`RefundEscrow` ISMP message; `onAccept` → `withdraw()` executes: 
   - `token.call(...)` returns `success = true` (call succeeded) with encoded `false` payload.
   - `if (!success) revert TransferFailed();` does not trigger.
   - `_orders[body.commitment][token] -= amount;` executes and `_filled[body.commitment] = beneficiary;` is set.
4. Beneficiary received 0 tokens, yet the order is marked filled with escrow decremented — funds are now stranded in the contract with no accounting path to recover them.
