### Title
Third-party `supply` into a victim's account injects an unverified collateral leg that permanently fails the victim's solvency gate - (File: contracts/controller/src/account.rs)

### Summary
The DTLS bug class — a peer that failed verification is still allowed to feed the data plane — maps onto `load_or_create_account` with `AccountGuard::Supply`: any unprivileged address may supply collateral into an account it does not own, and that foreign position then binds every subsequent solvency check on the victim's account. The position was never authorized by the account owner, yet it participates fully in the post-operation risk gates, including the sub-3-decimal whole-unit collateral floor. A dust leg supplied by a stranger makes `require_post_pool_risk_gates` fail for the victim on `withdraw` and `borrow`, temporarily freezing the victim's funds.

### Finding Description
`load_or_create_account` applies three guards. `AccountGuard::Migrate` and `AccountGuard::Multiply` call `require_owner_or_delegate`, but `AccountGuard::Supply` only calls `require_spoke_match` — no ownership or delegate check: [1](#0-0) 

So `controller.supply(caller=attacker, account_id=victim_id, supplies=[(hub_asset_of_low_decimal_asset, 1)])` mints a scaled supply position into the victim's account map. `caller.require_auth()` authenticates only the payer, not the account owner — the position's "verification" (who owns the account it lands in) is skipped, yet the position still drives the account's risk outcome, exactly the shape of the Pion bug.

The trap closes in `require_post_pool_risk_gates`, which runs on `withdraw` and `borrow` for any account carrying debt: [2](#0-1) 

Its tail calls `require_whole_unit_collateral_floor`, which iterates **every** supply leg and demands `MIN_WHOLE_UNIT_COLLATERAL` whole units in any leg whose `asset_decimals < MIN_BORROWABLE_ASSET_DECIMALS`: [3](#0-2) 

The attacker's dust leg fails that assert with `MinBorrowCollateralNotMet`. Because the panic aborts the transaction, the victim cannot withdraw (the gate runs post-mutation), cannot borrow, and cannot remove the foreign leg without passing the same gate — the debt must first be repaid to zero so `account.debt_free()` short-circuits the checks at line 30. `validate_bulk_position_limits` only limits *count*, not *who* added the position, so it does not prevent the injection.

### Impact Explanation
Temporary freezing of funds: a victim account holding debt plus an uninvited sub-3-decimal dust supply leg has every `withdraw` and `borrow` revert with `CollateralError::MinBorrowCollateralNotMet` until the victim fully repays debt (which itself may be impractical if collateral is locked) or the attacker withdraws their dust — which only the attacker can do, since `withdraw` requires owner/delegate auth. The attacker risks only the dust amount; the victim's exit is blocked at the cost of an attacker-controlled release or a full debt repayment the victim may not be able to make. The same mechanism lets an attacker grief by filling the victim's remaining supply-position slots (`new_positions_count` in `validate_bulk_position_limits`), blocking the victim's own intended supplies.

### Likelihood Explanation
Reachable by any unprivileged address via the public `supply` entrypoint; requires a listed market whose `asset_decimals < MIN_BORROWABLE_ASSET_DECIMALS` and a victim with nonzero debt. Both are ordinary market configurations (the whole-unit floor exists precisely because such assets are listed). The attacker loses only the dust leg, which is refundable to them afterward.

### Recommendation
Require the caller to be the account owner or an active delegate for `supply` into a non-zero `account_id` (apply `require_owner_or_delegate` in `AccountGuard::Supply`), or exempt foreign-initiated legs from `require_whole_unit_collateral_floor`/`validate_bulk_position_limits` by tracking position provenance. The minimal fix is aligning `Supply` with `Migrate`/`Multiply` so no third party can bind unverified collateral to an account's solvency evaluation.

### Proof of Concept
1. Admin lists market `(hub=1, asset=X)` with `asset_decimals < MIN_BORROWABLE_ASSET_DECIMALS`.
2. Victim supplies collateral in asset Y and borrows, leaving the account with debt (`account.debt_free() == false`).
3. Attacker calls `controller.supply(caller=attacker, account_id=victim, spoke_id=victim_spoke, supplies=[((1, X), 1)])`. `AccountGuard::Supply` passes with only `require_spoke_match`; the dust position lands in `victim.supply_positions`.
4. Victim calls `withdraw` (or `borrow`) on any leg. Post-pool mutation, `require_post_pool_risk_gates` → `require_whole_unit_collateral_floor` hits the attacker's 1-unit leg, `units < MIN_WHOLE_UNIT_COLLATERAL`, and panics with `MinBorrowCollateralNotMet`.
5. Every subsequent `withdraw`/`borrow` reverts identically until the victim repays all debt — funds are frozen at an attacker's discretion.

Uncertainty note: I verified `AccountGuard::Supply` omits the owner check in `load_or_create_account` and that the floor check iterates all supply legs, but I did not read the `supply` entrypoint in `lib.rs`/`payments.rs` to rule out an additional upstream owner check; the guard enum's design (distinct guards for `Supply` vs `Migrate`/`Multiply`) strongly suggests none exists.

```rust
fn require_whole_unit_collateral_floor(env: &Env, cache: &mut Context, account: &Account) {
    for (hub_asset, position) in iter_typed_positions(&account.supply_positions) {
        let decimals = cache.cached_price(&hub_asset.asset).asset_decimals;
        if decimals >= MIN_BORROWABLE_ASSET_DECIMALS {
            continue;
        }
        let supply_index = cache.cached_market_index(&hub_asset).supply_index;
        let units = position
            .scaled_amount
            .mul(env, supply_index)
            .to_asset_floor(env, decimals);
        assert_with_error!(
            env,
            units >= MIN_WHOLE_UNIT_COLLATERAL,
            CollateralError::MinBorrowCollateralNotMet
        );
    }
```
