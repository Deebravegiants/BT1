### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's HMAC and then hands the caller-supplied `shop` (and `topic`, `webhook_id`, `api_version`) to the app's handler as if they were verified, but the HMAC only signs the raw body — the shop-identifying header is completely outside the signed data.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values are all read straight from HTTP headers with no cryptographic binding to the body: [2](#0-1) .

`Registry.process` calls `Utils::HmacValidator.validate(request)`, which only verifies `hmac` against `to_signable_string` (i.e., the body) via `validate_signature`: [3](#0-2) . Once that body-only check passes, `process` immediately forwards the unverified `request.shop` into `WebhookMetadata` and invokes the handler: [4](#0-3) .

The equality the gem implicitly claims to guarantee is: `bytes covered by HMAC == bytes the handler treats as authenticated (including shop)`. In reality: `bytes covered by HMAC (raw_body only) != data.shop (from an unsigned header)`. Because Shopify apps share a single `api_secret_key` across every shop that installs them, any body+HMAC pair legitimately delivered to one tenant remains a valid signature regardless of which `shop-domain` header accompanies it. An unprivileged party who has installed the app on their own shop (or who otherwise observes one legitimate webhook delivery) can capture a valid `raw_body`/`hmac` pair and replay it with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. `HmacValidator.validate` still returns `true` because it never inspects the shop header, and the handler executes believing the event originated from the victim tenant.

The gem's own documentation reinforces this false guarantee, stating that `Registry.process` "will verify the request did indeed come from Shopify" without qualifying that only the body — not the shop attribution — is verified: [5](#0-4) , and documents `data.shop` as a trustworthy field for the handler to key off of: [6](#0-5) .

### Impact Explanation
A handler that uses `data.shop` to look up a session, apply per-tenant business logic, or persist data (exactly as the documented example does — `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be tricked into attributing a webhook's body/action to an arbitrary victim shop chosen by the attacker. This is a cross-tenant confusion: the attacker fully controls which tenant's context consumes body content they crafted (via their own legitimately-installed instance of the app), breaking the identity binding between the cryptographically verified bytes and the shop the framework claims sent them.

### Likelihood Explanation
Any merchant who installs the app receives real webhook deliveries with valid HMACs for arbitrary topics they subscribed to, giving them body+HMAC pairs signed with the app's single shared `api_secret_key`. No access token, `api_secret_key`, or privileged access is needed — only a normal, unprivileged installation of the target app, or interception of any single legitimate delivery. The header can then be freely rewritten and replayed against the app's webhook endpoint.

### Recommendation
Bind the shop (and other request-identifying fields such as topic/webhook_id) into the HMAC-signed content, or otherwise cross-check the header-derived `shop` against a store's actual known/authorized shop (e.g., verify it corresponds to a shop with an active session/installation) before passing it to handlers. At minimum, `Utils::HmacValidator`/`Request#to_signable_string` should not allow the framework's documentation to imply that headers like `shop-domain` are verified when they are not part of the signed payload.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g., `orders/create`) so Shopify sends a legitimately-signed webhook: `raw_body = B`, header `X-Shopify-Hmac-Sha256 = HMAC(secret, B)`, `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Replay the exact same request to the app's webhook endpoint, but replace the header with `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes the HMAC over `raw_body` only — unchanged — so validation succeeds: [7](#0-6) .
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and body `B`, and performs whatever action the app implements (e.g., enqueue a job attributing `B` to `victim.myshopify.com`), even though `victim.myshopify.com` never sent this data.
