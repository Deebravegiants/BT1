## Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before invoking the app's handler with a `shop` value the app is expected to trust. In reality, the HMAC signature only covers the raw request body, while the `shop` field the handler receives comes from an unauthenticated header. An attacker who is a genuine, installed merchant on the app can generate a real webhook (with a correctly signed body for their own shop) and then re-send the same body/HMAC pair while substituting the `x-shopify-shop-domain` header for a victim shop, and the gem will accept it as valid.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `Webhooks::Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed data at all: [2](#0-1) 

`Registry.process` validates only the HMAC over that signable string, then forwards `request.shop` unchecked into the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` compute the digest strictly from `verifiable_query.to_signable_string` (i.e. body only) and compare it against the received HMAC — the `shop` header is never mixed into that computation: [4](#0-3) 

The library's own documentation instructs apps to treat `data.shop` from `Registry.process` as the authenticated tenant identifier and to use it directly (e.g. to enqueue per-shop jobs), while stating that `process` "will verify the request did indeed come from Shopify": [5](#0-4) [6](#0-5) 

The identity binding that should hold is: `shop authenticated by HMAC == shop delivered to the handler`. Because the HMAC secret (`Context.api_secret_key`) is shared across all shops installed on a single app (it is not a per-shop secret), any installed shop can produce a validly-signed body/HMAC pair for itself, then relabel the `shop-domain` header to name a different, victim shop. The signature still validates (it only checks the body bytes), so the forged request is accepted and dispatched to the handler as if it originated from the victim shop.

### Impact Explanation
This breaks the tenant boundary between shops installed on the same multi-tenant app — a malicious merchant can make the app process fabricated webhook data attributed to an arbitrary other shop. Any app logic keyed off `data.shop` (job routing, per-shop database writes, session lookups, audit logs, cache invalidation, etc., as shown in the gem's own usage example) can be manipulated cross-tenant. This falls under the Critical "cross-tenant access" category, since it lets one tenant's traffic corrupt or influence another tenant's application state through the gem's own trusted `WebhookMetadata#shop` field.

### Likelihood Explanation
Likelihood is high for any app that has more than one shop installed (the typical SaaS deployment model for Shopify apps). No secrets beyond what a normal installed merchant already legitimately possesses are required — the attacker only needs to trigger one genuine webhook to their own shop (trivial, e.g. by updating a product) and replay it with a modified `shop-domain` header value against the app's public webhook endpoint.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the HMAC-protected signable string, or otherwise cryptographically bind them to the verified payload, so that a valid signature for one shop's webhook cannot be replayed while claiming a different shop identity. At minimum, document prominently that `data.shop` is unauthenticated and must be cross-checked by the app against a known/installed shop list before being trusted.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com` (same `api_secret_key`).
2. Attacker controls `shop-a` and triggers a real Shopify webhook (e.g. `products/update`), capturing the genuine `raw_body` and its `x-shopify-hmac-sha256` value computed by Shopify.
3. Attacker POSTs to the app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only hashes `raw_body`: [7](#0-6) 
5. `Registry.process` calls the handler with `shop: "shop-b.myshopify.com"` even though the payload actually originated from `shop-a`: [8](#0-7) 
6. The app performs shop-b-scoped actions using attacker-controlled body content, violating tenant isolation.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
