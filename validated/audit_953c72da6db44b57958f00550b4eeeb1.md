### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the HMAC-verified bytes solely from the raw request body, while the `shop` (tenant) identity is read from an unauthenticated HTTP header. `ShopifyAPI::Webhooks::Registry.process` trusts this header value and hands it to the app's webhook handler as the authoritative tenant identifier, breaking the equality `shop authenticated == shop bound by HMAC`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of the signed payload: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. the body — the `shop` header plays no role in the cryptographic check: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then unconditionally trusts `request.shop` when constructing `WebhookMetadata`, which is passed to the host application's handler as the authenticated tenant: [4](#0-3) 

`WebhookMetadata#shop` is a plain `String` field with no cryptographic binding to the HMAC-signed body: [5](#0-4) 

**Broken equality:** `shop_bound_by_hmac == shop_delivered_to_handler` does not hold — the HMAC binds only the request body, not the `shop-domain` header, yet the gem forwards the header value as the trusted tenant identity (`WebhookMetadata.shop`) with the same trust level as the HMAC-verified body.

**Attack path:**
1. Attacker installs the app on their own store (`attacker.myshopify.com`), a fully legitimate, unprivileged action requiring no leaked credentials.
2. Attacker triggers a webhook whose signed body content they control or can predict (e.g., an `orders/create` or `products/update` topic where they control the resource content in their own store).
3. Shopify legitimately signs the resulting HTTP webhook request using the app's real `api_secret_key` (the attacker never needs to know this secret — Shopify computes and sends it).
4. Attacker intercepts the outbound webhook delivery to their own endpoint (which they fully control since it's addressed to their own app) and replays the exact same body + HMAC header to the app's webhook endpoint, but swaps the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`.
5. `HmacValidator.validate` still succeeds because the signature only covers the untouched raw body.
6. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled-content>, ...)`.
7. Any host application logic that keys off `data.shop` (e.g., looking up the victim's stored session/access token to process the event, writing to the victim's tenant record, invalidating/updating victim tenant state) now processes attacker-controlled data under the victim's tenant identity.

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is supposed to enforce: an app is expected to trust `WebhookMetadata.shop` as the authenticated origin of the event, since the gem is the one performing "HMAC validation" as its security guarantee. Because the shop identity is not cryptographically bound to the signed payload, an unprivileged app installer (any merchant, not a privileged/admin actor) can present arbitrary body content as belonging to any other tenant of the same app, i.e., cross-tenant data injection/spoofing — one of the explicitly in-scope Critical/High impact categories ("cross-tenant access").

### Likelihood Explanation
The likelihood is bounded by real-world constraints not verifiable from the gem's code alone (Shopify's edge infrastructure and delivery mechanisms, whether app hosts additionally validate the shop domain against their own installed-shop allowlist before trusting `data.shop`, and whether replay/timestamp checks exist upstream). The gem itself provides no defense — no header, timestamp, or shop binding is part of `to_signable_string` — so any host application relying solely on the documented `ShopifyAPI::Webhooks::Registry.process` → `WebhookMetadata.shop` contract inherits this gap.

### Recommendation
Bind the shop identity to the HMAC-verified data, e.g., by including the `shop-domain` header (and ideally `webhook-id`/timestamp) as part of `to_signable_string`, or by cross-checking `request.shop` against an app-known list of shops that have valid, non-revoked sessions/access tokens before invoking the handler, and reject events where the header cannot be corroborated against the signed body/session store.

### Proof of Concept
```ruby
# Legitimate webhook the attacker receives for their own store "attacker.myshopify.com"
raw_body = '{"id":1,"note":"hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # <-- attacker swaps this header
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# HMAC still validates because it only covers raw_body, not the shop header
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process will invoke the handler believing this event is from victim-shop.myshopify.com
ShopifyAPI::Webhooks::Registry.process(request)

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
