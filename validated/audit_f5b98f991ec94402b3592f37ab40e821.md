### Title
Emporium stateless op path allows attacker to invoke `LifiExternalAction.runAction` with fabricated `deltaAmounts`, sweeping any token balance sitting in `LifiExternalAction` into attacker's shielded UTXO - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction`'s "Case 2: Stateless" branch executes `op.endpoint.call(op.callData)` with an attacker-fully-controlled `endpoint`/`callData` and, when `stack.signerAddress == address(0)`, performs zero signature verification on the ops list [1](#0-0) . Because the attacker generates their own ZK proof for their own top-level `transact()` call, they can freely craft this ops list, including a call into any `isAllowedRecipient`-listed action such as `LifiExternalAction.runAction` with a second, self-fabricated `CircomData`/`deltaAmounts` pair that is never checked against the real `deltaAmountChanges` Hinkal computed for the outer call.

### Finding Description
The broken equality is: **tokens leaving `LifiExternalAction` during a `runAction` call must equal `-deltaAmounts[0]`/the real amount deposited into it by that caller for that specific call** — but `ExternalActionSwap.swap` never verifies this. It simply trusts `deltaAmounts[0]` supplied by the caller to compute `inputAmount`, uses `approveUnlimited`+`router.call` to execute the swap, and forwards whatever balance change results to `msg.sender` [2](#0-1) [3](#0-2) . There is no balance-before/after self-check inside `ExternalActionSwap`/`LifiExternalAction` comparable to the one `EmporiumUpgradeable.runAction` performs on itself.

Call path: `Hinkal.transact` → `_externalTransact` (top-level circomData targets `EMPORIUM_ID`) → `EmporiumUpgradeable.runAction` → (Case 2, `stack.signerAddress == address(0)`, no signature check) `op.endpoint.call(callData)` where `endpoint = LifiExternalAction`, `callData = runAction(craftedCircomData, deltaAmounts)` [4](#0-3) . `LifiExternalAction.runAction` only checks `onlyAllowedRecipient` (msg.sender = Emporium, which per the stated precondition is allowlisted) [5](#0-4) , then sweeps whatever balance `LifiExternalAction` currently holds of the attacker-chosen input token via the router, and sends the swap output to `msg.sender` = `Emporium`.

Back in the outer `EmporiumUpgradeable.runAction`, the swept output token shows up as a positive `balanceChange` for that token in Emporium's own before/after balances. Since the attacker's *top-level* `deltaAmountChanges[i]` for that output token is `0` (they declared no real deposit), the code does not subtract anything and treats the whole swept amount as legitimate profit, calling `handleOut` to mint a UTXO to the attacker's own `stealthAddressStructure` [6](#0-5) . `Hinkal`'s own global conservation check only verifies that Hinkal's own balance delta equals `amountChanges[i] + utxoAmount`, which is trivially satisfied because the created UTXO amount equals the balance delta actually received [7](#0-6) . `calldataHash`/`verifyProof` do not stop this because the attacker computes the hash and proof themselves over their own crafted data — these are self-consistency checks, not authorization checks against a third party's data [8](#0-7) .

The root cause is that `EmporiumUpgradeable` acts as a generic, arbitrary-call proxy toward any `isAllowedRecipient`-listed action, and none of the nested actions (`LifiExternalAction`/`ExternalActionSwap`) independently verify that the `deltaAmounts` they're given actually corresponds to value transferred in for that specific call — they rely solely on the outermost caller's balance-diff check, which cannot distinguish "value from the attacker's real deposit" from "value already sitting in the nested action from an unrelated source."

### Impact Explanation
If `LifiExternalAction` (or any other `isAllowedRecipient`-listed action reachable this way) holds any non-zero ERC20/ETH balance not currently accounted for by an in-flight top-level call (e.g., dust from a prior swap, a stuck approval-based pull, or funds mistakenly sent to the contract), an attacker can drain that balance into their own shielded UTXO with zero real deposit backing it. This is theft of protocol/other-users' residual funds and effectively mints shielded value the attacker never deposited, repeatable every time such a balance exists, matching Critical/High severity.

### Likelihood Explanation
The attack requires (1) `LifiExternalAction` (or a similarly integrated action) to be listed as an allowed recipient of another action it calls into (stated precondition) and (2) that target action to be holding a non-zero balance not otherwise accounted for at call time. The attacker only needs their own valid UTXOs and their own ZK proof — no privileged role, no victim signature or key, since Emporium's stateless path skips signature checks entirely and the "signed" path can be self-signed by the attacker acting as their own `signerAddress`. The exploit mechanism itself (arbitrary `op.endpoint`/`callData` in `EmporiumUpgradeable.runAction`, chained into any `IExternalActionV2.runAction` with attacker-fabricated `deltaAmounts`) is fully attacker-controlled and reproducible; the only external dependency is the existence of a sweepable balance in the target action.

### Recommendation
- In `LifiExternalAction`/`ExternalActionSwap.swap`, verify the caller actually transferred in the declared `inputAmount` for this call (e.g., record balance before/after around the pull, or require the caller to be `Hinkal` itself / restrict `isAllowedRecipient` to Hinkal only for swap actions).
- Restrict `EmporiumUpgradeable`'s stateless op path so `op.endpoint` cannot be another `IExternalActionV2` contract, or require that any nested `runAction` call carry deltaAmounts cryptographically tied back to the outer circomData's own `deltaAmountChanges`/`amountChanges`, not an independently fabricated struct.
- Do not allow `stack.signerAddress == address(0)` to fully skip authorization of the ops list when the ops target other privileged/allowlisted contracts; at minimum constrain reachable `op.endpoint` values to a vetted allowlist distinct from generic external calls.

### Proof of Concept
Hardhat fork test:
1. Deploy `Hinkal`, `EmporiumUpgradeable` (registered as `EMPORIUM_ID`), `LifiExternalAction`; add `Emporium` to `LifiExternalAction`'s allowed recipients.
2. Seed `LifiExternalAction` with a non-zero `RESIDUAL_TOKEN` balance (simulate leftover dust, e.g. direct `transfer` to the contract, standing in for the stated "prior user's slippage-bounded swap" residue).
3. Attacker deposits/owns their own UTXO(s) unrelated to `RESIDUAL_TOKEN`; builds a top-level `CircomData` with `externalActionId = EMPORIUM_ID`, `erc20TokenAddresses` including the swap-output token with `amountChanges[i] = 0`, `slippageValues[i] <= 0`, and `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and one op: `{endpoint: LifiExternalAction, callData: abi.encodeCall(runAction, (craftedCircomData, [-residualBalance, 0]))}` where `craftedCircomData.erc20TokenAddresses = [RESIDUAL_TOKEN, outputToken]`.
4. Generate a locally-produced valid proof for attacker's own UTXOs/circomData and call `Hinkal.transact`.
5. Assert: (a) `LifiExternalAction`'s `RESIDUAL_TOKEN` balance goes to 0; (b) a new UTXO is credited to attacker's `stealthAddressStructure` for `outputToken` equal to the swapped amount; (c) `circomData.amountChanges[outputTokenIndex] == 0` and no nullifier/UTXO in the transaction accounts for a real deposit backing that credited amount — i.e., `balanceDif == amountChanges[i] + utxoAmount` holds in `Hinkal` only because `utxoAmount` itself equals the un-backed swept value, not because any real value was deposited.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
