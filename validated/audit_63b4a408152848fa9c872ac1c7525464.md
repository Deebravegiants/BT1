## Title
Webhook shop-domain header is trusted for tenant identification but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` authenticates only the raw request *body* via HMAC, while the `shop` value used by the handler to attribute the webhook to a tenant is read from an HTTP header that is completely excluded from the signed payload. An attacker who legitimately owns any shop that has the app installed can capture one of their own validly-signed webhook deliveries and replay it to the app's public webhook endpoint with the `shop-domain` header changed to a victim shop, causing the app to process attacker-controlled data under the victim's tenant identity.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `Request#shop` is read straight from an unauthenticated header: [2](#0-1) 

`Registry.process` validates the HMAC over the signable string (the body only) and then hands `request.shop` straight to the handler as the tenant identity, with no additional binding between the signed body and the shop header: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` only ever operate on `verifiable_query.to_signable_string` (the body), never on the shop header: [4](#0-3) 

This reproduces the report's bug class exactly: a field that is *acted on* (the shop used to attribute/route the webhook data) is not covered by the value that is cryptographically verified (the HMAC only covers the body). The equality the gem implicitly assumes — "the shop whose webhook secret produced this HMAC" == "the shop named in the `shop-domain` header" — does not actually hold, because the header is never part of the signed material.

### Impact Explanation
Because the shop attribution is unauthenticated, a merchant/attacker who has the app installed on their own store (an unprivileged party from the app's perspective, since installing the app themselves requires no special privilege) can:
1. Receive a genuine, validly HMAC-signed webhook for their own shop (any topic the app subscribes to, with attacker-controlled body content where the shop is a merchant-controllable store, e.g. product/order data on their own store).
2. Replay that exact body + HMAC value directly to the app's public webhook endpoint, but with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header rewritten to a victim shop domain.
3. `Utils::HmacValidator.validate` still succeeds (it only checks the body against the secret), and `Registry.process` invokes the handler with `shop: <victim shop>` and attacker-controlled `body`.

This is a cross-tenant access / tenant-confusion vulnerability: data that the host application believes originated from, and should be stored/acted on for, the victim shop is actually attacker-controlled. Depending on how the host app's webhook handler persists/acts on this data (order creation, product updates, GDPR data-request topics, etc.), this can lead to cross-tenant data corruption or disclosure.

### Likelihood Explanation
High. The attacker only needs their own installation of the app (a normal, unprivileged action any developer/merchant can perform) to obtain a validly signed webhook body, and the webhook endpoint is by definition a public, unauthenticated HTTP endpoint that must accept POSTs from the internet. No access token, `client_secret`, or privileged credential is required — only the ability to install the app on a store they control and to send an HTTP POST with a forged header, both of which are available to any unprivileged internet user.

### Recommendation
Bind the shop identity into the value that is actually verified, e.g., include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in `to_signable_string`, or otherwise cryptographically bind the header claim to the signed body (for example by requiring the host application to independently confirm that the shop domain in the payload/header matches a shop the app has genuinely installed for, cross-checked against stored session data) so the HMAC verification also guarantees the header's shop value.

### Proof of Concept
1. Attacker installs the app on their own store `attacker-shop.myshopify.com` and receives (or triggers) a legitimate webhook delivery, capturing the raw body `B` and the valid `X-Shopify-Hmac-Sha256` header `H = HMAC-SHA256(secret, B)`.
2. Attacker sends a POST directly to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
3. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Utils::HmacValidator.validate(request)` succeeds because it only checks `B` against `H` per [5](#0-4) .
4. `Registry.process` calls the registered handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, per [6](#0-5) , causing the host application to process attacker data as belonging to the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
