This confirms the mismatch: `Registry.process` at [1](#0-0)  validates the HMAC over `request.to_signable_string` (which is just `@raw_body`, per `lib/shopify_api/webhooks/request.rb` line 36-38) but then trusts `request.shop`, sourced from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header, as the tenant identity handed to the app's webhook handler. This exactly matches the allowed bug class: "a field acted on but not covered by the HMAC."

However, exploiting this requires the attacker to produce a body whose HMAC validates — and that HMAC uses `Context.api_secret_key` (the app's `client_secret`), per [2](#0-1) . Since the `client_secret` is shared across all shops that install the same app (not shop-specific), an unprivileged user who has installed the app on their **own** shop can receive a legitimately-HMAC-signed webhook from Shopify for their own shop, then replay/forward that exact `raw_body` (bit-for-bit) to the app's webhook endpoint while spoofing the `x-shopify-shop-domain` header to a victim shop's domain. Because the HMAC check only covers `raw_body` (line 36-38) and never binds the shop header, the forged request passes `Utils::HmacValidator.validate` and is routed to the handler tagged with the attacker-chosen `shop` value, per `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` at [3](#0-2) .

This breaks the identity binding: `HMAC-verified-bytes(raw_body) == raw_body-that-was-actually-signed` holds, but `request.shop (used as tenant key) == shop-that-actually-produced-the-signed-body` does not hold, letting one tenant's legitimately-signed webhook body be misattributed to another tenant if the host app trusts `WebhookMetadata#shop` as an authoritative tenant identifier (which is exactly the documented intended use, per [3](#0-2) ).

### Title
Webhook tenant identity (`shop`) is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its verifiable signature only over the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` identity consumed by `Registry.process` and handed to webhook handlers is read directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the HMAC digest.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC-SHA256(Context.api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` header value, per [4](#0-3) . For webhook requests, `to_signable_string` is defined as just `@raw_body`, per [5](#0-4) , meaning the shop-domain header is completely outside the authenticated bytes. `Registry.process` validates this HMAC and then unconditionally trusts `request.shop` — sourced from the header, at [6](#0-5)  — as the tenant identity passed to the handler, at [7](#0-6) .

Since a single app's `client_secret` (`Context.api_secret_key`) is shared across every shop that installs the app, any shop owner who has installed the app can legitimately receive a validly-signed webhook body for their own shop and then replay the exact bytes to the app's webhook endpoint while altering only the `shop-domain` header to name a different, victim shop. The HMAC still validates (it only covers the body), so the forged `shop` value flows unchecked into `WebhookMetadata`.

### Impact Explanation
This breaks the tenant-identity binding the host application relies on: `shop` is meant to identify which merchant a webhook payload belongs to, but that field is not covered by the same authentication mechanism (`HMAC`) that protects the payload. An app that uses `WebhookMetadata#shop` to look up per-shop credentials, scope data access, or route side effects (the intended and documented usage of this field) can be tricked into associating one merchant's legitimate webhook data with another merchant's tenant record — a cross-tenant data integrity/confusion issue.

### Likelihood Explanation
Exploitation requires the attacker to be a legitimate, unprivileged user of the app on their own shop (able to receive real Shopify webhooks for that shop) and requires the host application to trust `WebhookMetadata#shop` without independently verifying it against known/expected shop identifiers — which is exactly how the gem's own registry documentation presents the field.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed material, or otherwise cryptographically bind the `shop` header to the signed body before trusting it as tenant identity in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on their own shop (`attacker-shop.myshopify.com`) and receives a legitimate webhook, e.g. `orders/create`, with body `B` and a valid `x-shopify-hmac-sha256` computed over `B` using the app's shared `client_secret`.
2. Attacker resends the exact same raw body `B` and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the HMAC only ever covered `B`, per [5](#0-4) .
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, per [3](#0-2) , causing the app to process the attacker's own webhook data under the victim's tenant identity.
