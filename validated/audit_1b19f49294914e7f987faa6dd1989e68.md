### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC over the raw request body, then hands the caller-supplied `shop-domain` header — unauthenticated — to the app's handler as the tenant identity. The identity binding that should hold is: `shop used to route/act on the webhook == shop whose secret produced the HMAC`. In this implementation the HMAC never covers the `shop` (or `topic`/`webhook-id`) header at all, so that equality is never actually checked.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor is read straight from the (attacker/replay-controllable) `shopify-shop-domain` / `x-shopify-shop-domain` header, independent of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `verifiable_query.to_signable_string` (the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Webhooks::Registry.process` gates purely on that HMAC check and then constructs `WebhookMetadata` using the unauthenticated `request.shop` value, which is exactly the field host applications use as the tenant/session key to look up per-shop state (access tokens, data) when handling the webhook: [4](#0-3) 

Because `api_secret_key` is shared by the app across *all* installed shops (it is not per-shop), any merchant who has installed the app can legitimately receive a genuinely-signed `(raw_body, hmac)` pair from Shopify for their own shop, then replay that exact body+hmac to the app's webhook endpoint while substituting a different `shop-domain` header naming a victim shop. Since the header is never part of the signed content, `HmacValidator.validate` still succeeds, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` equal to the victim shop, even though the payload actually belongs to the attacker's own shop.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook processing: an unprivileged app-installing merchant can make the host application process attacker-controlled webhook data under a different shop's identity, i.e., cross-tenant confusion/access via a component whose entire purpose is proving "this came authentically from shop X." This matches the Critical impact category of cross-tenant access.

### Likelihood Explanation
Any user who can install the app on their own shop (a normal, unprivileged action) can obtain a validly-HMAC'd webhook body/signature pair from Shopify and replay it with a forged `shop-domain` header against the app's webhook endpoint, since nothing in `Registry.process` or `Request` cross-checks the header against the signed payload or against Shopify's origin. No secrets, tokens, or elevated access are required — this is reachable purely through this gem's own webhook-processing code path (`Registry.process` → `HmacValidator.validate` → `Request#shop`).

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) values into the signed material, or otherwise cryptographically verify the shop identity, before trusting `request.shop`/`WebhookMetadata#shop`. At minimum, document that `HmacValidator` only proves body integrity/authenticity for *the app*, not per-shop origin, and require callers to cross-check `request.shop` against a shop the app has actually installed via a registered webhook subscription id, rather than trusting the header directly as the tenant key.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, giving Shopify the app's `client_secret`-derived HMAC key (shared across all installs of this app).
2. Attacker triggers a real webhook event (e.g., `orders/create`) on their shop and captures the genuine `raw_body` and `x-shopify-hmac-sha256` value sent by Shopify.
3. Attacker POSTs that exact `raw_body` and `hmac` to the victim app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes HMAC only over `raw_body` and succeeds (per `lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/utils/hmac_validator.rb`).
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)`, causing the host app to process attacker-supplied data as if it originated from `victim-shop.myshopify.com`.
