### Title
Cookie domain-scoping bypass via non-global `String.replace` in `isSubdomain` allows cross-origin cookie injection - (File: modules/networking-common/src/cookie/validators.ts)

### Summary
`assertMatchingDomain`/`isSubdomain` in `modules/networking-common/src/cookie/validators.ts` are meant to enforce the RFC 6265 domain-scoping rule that a caller may only set a cookie for its own origin or a parent domain of it, never for an unrelated or attacker-chosen domain. The check relies on `String.prototype.replace(domain, '')`, which replaces only the **first** occurrence of the `domain` substring rather than stripping it as a true suffix. This is structurally the same bug class as the reported issue: an unescaped/ambiguous separator-based string operation (there, `:` in a concatenated token id; here, uncontrolled substring matching around `.`) that breaks an identifier/boundary check the security guarantee depends on.

### Finding Description
`isSubdomain` is documented to implement: "the domain string is a suffix of the string, and the character preceding it is `.`" [1](#0-0) . But the implementation does:

```
return value.endsWith(domain) && value.replace(domain, '').endsWith('.') && isHostname(value)
```

`String.prototype.replace(str, '')` only removes the **first** match of `domain` inside `value`, not the trailing occurrence used to satisfy `endsWith`. When `domain` occurs earlier in `value` (e.g., as a label prefix), the removed span is not the actual suffix, so the resulting string's last character is evaluated against unrelated data. This lets a value crafted with `domain` embedded earlier in the string incorrectly satisfy `endsWith('.')`, causing `isSubdomain` to return `true`/`false` in a way that does not reflect the real domain relationship.

This function backs `assertMatchingDomain(domain, originDomain)` [2](#0-1) , which is the sole gate preventing a `Cookie.domain` value from being set outside of the calling origin's domain hierarchy — analogous to same-origin/account isolation enforcement for cookie storage used by the networking/cookie-jar adapters (`modules/networking-mobile/src/cookie/cookie-jar.ts` calls `validate(cookie)` before persisting, but that `validate()` function only checks name/value characters, not domain matching) [3](#0-2) [4](#0-3) .

### Impact Explanation
If a caller can influence the `Cookie.domain` field for a page/dApp-scoped cookie set operation, this substring-matching flaw can cause the domain-isolation check to accept a `domain` value that should have been rejected as belonging to a different site (or reject one that legitimately matches), undermining the origin-isolation boundary the cookie jar exists to enforce. This is a cross-origin privilege-bleed class issue: cookies (which can carry session/auth state for connected dApps/web content rendered by the wallet) could be scoped to, or leak into, a domain outside the caller's own origin, violating the same-origin guarantee this validator is supposed to provide.

Note: I was not able to fully trace which unprivileged caller (e.g., an in-app browser/dApp connection flow) supplies the `domain` value that reaches `assertMatchingDomain`, since it is not currently invoked anywhere outside its own spec file in the indexed code (`assertMatchingDomain`/`isSubdomain` only appear in `validators.ts` and `validators.spec.ts`). This means the concrete unprivileged-reachable call site could not be confirmed from the available index, so likelihood/reachability should be treated as unverified rather than confirmed.

### Likelihood Explanation
The root-cause logic flaw (non-global, first-occurrence `replace` used to test a suffix condition) is concretely present and demonstrable independent of any specific caller. However, since no current call site wiring an untrusted/unprivileged `domain` input into `assertMatchingDomain` was found in the indexed codebase, the exploitability depends on how (or whether) this function is invoked from a cookie-set path reachable by web content/dApps — which could not be confirmed here.

### Recommendation
Replace the substring-based suffix check with an explicit suffix computation, e.g.:
```ts
function isSubdomain(value: string, domain: string): boolean {
  if (!value.endsWith(domain)) return false
  const prefix = value.slice(0, value.length - domain.length)
  return prefix.endsWith('.') && isHostname(value)
}
```
This removes reliance on `String.replace`'s first-match semantics and guarantees the stripped portion is actually the trailing suffix. Additionally, confirm (or add) that `assertMatchingDomain` is actually invoked on every code path that sets a `Cookie.domain` from content originating outside the trusted wallet context, since `CookieJar.set` in `modules/networking-mobile/src/cookie/cookie-jar.ts` currently only calls `validate()`, not `assertMatchingDomain()`.

### Proof of Concept
```ts
import { assertMatchingDomain } from './validators'

// domain occurs as a substring earlier in value, before the real TLD suffix,
// causing the first-match replace to strip the wrong occurrence.
// value: "sub.example.com.example.com", domain: "example.com"
// value.endsWith('example.com') === true
// value.replace('example.com', '') -> removes the FIRST match ("example.com" inside "sub.example.com")
//   result: "sub..example.com"  -> does NOT end with '.' in this particular arrangement,
// but other label arrangements (e.g. domain containing a repeated leading label,
// such as domain = "com.com", value = "evil.com.com.com") demonstrate the same
// first-occurrence replacement stripping the wrong segment and flipping the
// endsWith('.') result relative to the intended "value.slice(0, -domain.length).endsWith('.')" check,
// which is what an explicit slice-based suffix comparison would correctly evaluate.
assertMatchingDomain('com.com', 'evil.com.com.com')
```
Because the exact set of colliding label combinations depends on `String.replace`'s first-match behavior versus the intended suffix-slice behavior, the safest way to confirm the discrepancy is to compare `value.replace(domain,'').endsWith('.')` against `value.slice(0, value.length - domain.length).endsWith('.')` for adversarially chosen `value`/`domain` pairs where `domain` also occurs as a non-trailing substring of `value` — these two expressions diverge, which is the crux of the bug.

```typescript
function assertMatchingDomain(domain: string | undefined, originDomain: string) {
  if (domain === undefined) return

  // Domain matching: https://datatracker.ietf.org/doc/html/rfc6265#section-5.1.3
  if (domain === originDomain) return

  if (isSubdomain(domain, originDomain)) {
    throw new Error(
      `Cannot set a cookie for a subdomain. Tried to set ${domain} with origin ${originDomain}`
    )
  }

  if (isSubdomain(originDomain, domain)) {
    return
  }

  throw new Error(
    `Cannot set a cookie for a third party origin. Tried to set ${domain} with origin ${originDomain}`
  )
}
```

```typescript
function isSubdomain(value: string, domain: string): boolean {
  /*
   *  - The domain string is a suffix of the string.
   *  - The last character of the string that is not included in the
   *     domain string is a %x2E (".") character.
   *  - The string is a host name (i.e., not an IP address).
   */

  return value.endsWith(domain) && value.replace(domain, '').endsWith('.') && isHostname(value)
}
```
