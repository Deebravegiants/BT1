### Title
Attacker-triggered Aquarius LP price outage permanently blocks liquidation and bad-debt cleanup of their own account - (File: contracts/price-aggregator/src/providers/aquarius.rs)

### Summary
A borrower who supplies even a dust position of an Aquarius LP share token as collateral can, after borrowing, withdraw their own liquidity from that Aquarius pool until its total value falls below the configured `min_pool_value_wad`. The price aggregator then fails with `InsufficientAquariusLiquidity` on every read. Because the controller computes account risk totals with strict (fail-closed) price reads over *all* supply legs, every path that needs the account's valuation — `liquidate`, `clean_bad_debt`, and `force_socialize_bad_debt` — reverts. The account's debt becomes permanently unliquidatable and unsocializable while the attacker keeps the borrowed funds.

### Finding Description
`aquarius::read` derives the LP fair price and then rejects the observation when the whole pool's WAD value is below `lp.min_pool_value_wad` (aquarius.rs:118-122). This is a state the attacker controls directly as a liquidity provider: withdrawing reserves drops `pool_value_wad` below the floor.

On the controller side, `process_liquidation` calls `plan::build_liquidation_plan` and `risk::calculate_account_risk_totals` over the victim's full supply book (mod.rs:58, 105-110); `clean_bad_debt_standalone` and `process_force_socialize_bad_debt` both go through `socialize_bad_debt`, which computes the same strict totals before admitting cleanup (mod.rs:222-237). A single collateral leg whose price reverts therefore poisons every valuation of the account. `supply` itself needs no price, so the attacker can add the dust LP leg *after* borrowing, or hold it from the start.

Sequence (all unprivileged, allowed actions):
1. `supply` — create account, supply ordinary collateral plus a dust amount of the Aquarius LP token the attacker is an LP in.
2. `borrow` — borrow up to the limit.
3. Withdraw the attacker's own liquidity from the Aquarius pool so `price_wad * total_shares / share_unit < min_pool_value_wad`.
4. Let the position drift (or push collateral price down) to HF < 1. Any `liquidate` or `clean_bad_debt` call now reverts inside the oracle read / risk-total computation.

### Impact Explanation
The attacker retains the full borrowed amount while the protocol can never seize collateral or socialize the debt — a direct theft of lender funds and permanent freezing of the bad debt on the book. Unlike ordinary oracle staleness (which self-heals when feeds update), this outage is attacker-maintained: the pool stays below the floor as long as the attacker doesn't re-add liquidity, and the attacker can even re-enter and repeat. It also defeats the owner-only `force_socialize_bad_debt` fallback, since that path reads the same strict totals.

### Likelihood Explanation
Requires the attacker to be a liquidity provider in an Aquarius pool whose LP token is a listed collateral hub asset, and enough LP share to pull the pool below `min_pool_value_wad`. Both are permissionless conditions; the cost is the dust collateral leg plus temporarily parking liquidity out of the pool. Medium likelihood where a listed LP token corresponds to a shallow pool.

### Recommendation
- In liquidation and bad-debt paths, treat an unpriceable *supply* leg as zero-value collateral (or skip it) rather than aborting the whole valuation, so a poisoned dust leg cannot shield the rest of the book.
- Alternatively, add a permissionless/semi-permissionless path that seizes all collateral legs at a bounded haircut when any leg is unpriceable, or allow bad-debt cleanup to bypass collateral valuation entirely and socialize debt against only the priceable residue.

### Proof of Concept
1. Governance lists hub asset `LP_X` (Aquarius share token, `min_pool_value_wad = V`) and a borrow asset `D`.
2. Attacker calls `supply(caller, 0, spoke, [(HUB_A, collateral), (LP_X, dust)])` → `account_id = A`.
3. Attacker calls `borrow(caller, A, [(D, max_borrow)])`.
4. Attacker withdraws their LP position from the Aquarius pool; `fair pool value < V` ⇒ `aquarius::read` returns `InsufficientAquariusLiquidity` (aquarius.rs:120-121).
5. Collateral price moves so `HF(A) < 1` per remaining priceable legs.
6. Liquidator calls `liquidate(liq, A, payments, SeizeMode::Transfer)` → reverts during `build_liquidation_plan`/`calculate_account_risk_totals` on the LP leg.
7. Anyone calls `clean_bad_debt(caller, A)` → reverts in `socialize_bad_debt` at `calculate_account_risk_totals` (mod.rs:222-235).
8. Owner calls `force_socialize_bad_debt(A)` → same revert. Debt persists indefinitely.

Uncertainty: I verified the fail-closed LP read and that both liquidation and cleanup compute strict risk totals, but did not trace `calculate_account_risk_totals`/`build_liquidation_plan` line-by-line to confirm there is no leg-level error tolerance; the threat-model entry DoS.1 in docs/explanation/threat-model.md corroborates that a price outage on one leg blocks liquidation and cleanup.
