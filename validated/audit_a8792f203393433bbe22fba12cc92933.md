Confirmed: the gem's own documented usage pattern (`docs/usage/webhooks.md`) tells apps to trust `data.shop` (i.e., `request.shop`, sourced purely from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header) for tenant routing (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`), while `ShopifyAPI::Webhooks::Registry.process` only validates the HMAC over the raw body via `Utils::HmacValidator.validate(request)` and `Request#to_signable_string` returning `@raw_body`. The shop-domain header is never included in the signed material, so an attacker who owns a legitimate installed shop can replay one of their own genuinely-signed webhook deliveries (valid body + valid HMAC) at the app's public webhook endpoint while substituting the `shop-domain` header to any other shop domain known to be a customer of the app, and the request passes HMAC validation. This lets an attacker inject cross-tenant events attributed to a victim shop.

### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant event forgery via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only (`to_signable_string` returns `@raw_body`), but the `shop` (and `topic`, `webhook_id`, `api_version`) values consumed by `ShopifyAPI::Webhooks::Registry.process` and handed to the application's `WebhookHandler` come exclusively from HTTP headers that are never part of the signed content.

### Finding Description
The equality the gem is supposed to enforce is: `shop attributed to the webhook event == shop that the HMAC signature actually authenticates`. In reality:

- `Utils::HmacValidator.validate(request)` recomputes the HMAC over `request.to_signable_string`, which is defined as `@raw_body` only [1](#0-0) .
- `request.shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, with no cryptographic binding to the body or the HMAC [2](#0-1) .
- `Registry.process` validates only the HMAC, then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler [3](#0-2) .
- The gem's own documentation instructs integrators to key their downstream processing off `data.shop` (e.g. `shop_domain: data.shop`) precisely because it is presented as an authenticated part of the payload [4](#0-3) .

Since the HMAC never covers the shop-domain header, any attacker who can obtain one genuinely-signed webhook body+HMAC pair (trivially available to them for their *own* installed shop, since Shopify signs their own webhooks with the app's shared secret) can replay that exact body/HMAC pair to the app's public webhook endpoint while swapping the `shop-domain` header to name a different, victim shop that also uses the app. `HmacValidator.validate` will report the signature as valid because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop.

This is the same class of bug as the analog report: a field that is acted upon (`maxAmount`/priority flag there; `shop` here) is not covered by the authentication check (`recoverSigner` there; HMAC over body here), so the value can be supplied/substituted by an unprivileged party without breaking verification.

### Impact Explanation
This breaks the tenant-isolation boundary the gem is meant to provide for webhook processing. An attacker (any user who can install the app on their own shop, i.e., a normal merchant) can forge webhook events that appear to originate from any other shop that has the app installed, as long as they can guess or observe that shop's domain (shop domains are effectively public: `something.myshopify.com`). Depending on how the host application acts on `data.shop`/`data.body` (as the gem's own docs recommend), this enables cross-tenant data confusion, forged order/customer/GDPR events attributed to a victim store, or state corruption keyed by shop domain — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker needs at least one legitimately-signed webhook body from their own shop (easy: install the app themselves, trigger any subscribed webhook topic) and knowledge of a target shop's `.myshopify.com` domain (routinely public/guessable). No credentials, access tokens, or `client_secret` are required — only observation of a signed webhook that the gem itself delivers to the attacker's own endpoint. This is directly reachable through the gem's public, documented `Registry.process`/`Request.new` API with no additional application-side mistake required.

### Recommendation
Include the shop domain (and ideally `topic`, `webhook_id`, `api_version`) inside the HMAC-covered signable content, or otherwise cryptographically bind them to the body before trusting them, e.g. by requiring the host app to independently verify that `request.shop` corresponds to a shop with an active session/installation and matches metadata already known for that specific `webhook_id`/delivery, rather than treating the header value as authenticated purely because the body-only HMAC passed. At minimum, document clearly that `shop`, `topic`, and `webhook_id` are unauthenticated header values and must not be trusted for tenant-sensitive decisions without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a subscribed webhook topic (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent to the app's webhook endpoint. This HMAC is valid because Shopify computed it with the app's shared secret over that body.
2. Attacker replays that exact `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint again, but changes the `X-Shopify-Shop-Domain` header to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`@raw_body`, unchanged) and finds it matches — validation succeeds [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: ..., ...)`, and the host application (following the gem's documented pattern) processes/queues this as an authentic event for `victim.myshopify.com` [6](#0-5) .
