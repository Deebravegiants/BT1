## Finding

Real vulnerability class found: an unauthenticated field is trusted for tenant identity while only *part* of the message is covered by the HMAC.

### Title
Webhook `shop` (and `topic`) values are trusted from unauthenticated headers even though only the raw body is HMAC-verified - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body [1](#0-0) , yet the `shop`, `topic`, `api_version`, and `webhook_id` values that `ShopifyAPI::Webhooks::Registry.process` hands to the app's webhook handler are read straight from unauthenticated HTTP headers [2](#0-1) . `Registry.process` only checks `Utils::HmacValidator.validate(request)`, which validates `request.to_signable_string` (the raw body) against `request.hmac` (also derived from a header) [3](#0-2) ; it never binds the `shop-domain` header into the signed payload.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to `verifiable_query.hmac` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) , and `hmac` is read from the `hmac-sha256` header [5](#0-4) . The `shop` accessor is read from the `shop-domain` header [6](#0-5) , which is not part of the signed string at all.

`Registry.process` uses this unauthenticated `shop` value directly to build the `WebhookMetadata` that is passed to the host application's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [3](#0-2) . The equality the library implicitly promises is `hmac_signed_bytes == authenticated_bytes`, but in reality `hmac_signed_bytes` (raw body only) ≠ `bytes_used_for_tenant_routing` (`shop`, `topic`, `webhook_id`, `api_version` headers). This is exactly the "bytes verified versus bytes parsed" / "shop authenticated versus shop used" identity-binding break.

Because the request body and its HMAC together are valid for *any* shop that could produce that exact body (e.g., the attacker's own low-privilege development/trial store receiving a real webhook, or any publicly observable webhook payload), an unprivileged attacker can:
1. Trigger or capture one legitimate `(raw_body, hmac)` pair from Shopify for a webhook topic whose body content they control or can predict (e.g. a webhook for their own store, or a topic with attacker-influenced/static body content).
2. Replay that exact body and HMAC value to the app's webhook endpoint, but with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain (and/or a different `X-Shopify-Topic`).
3. `HmacValidator.validate` still succeeds (it never looked at the shop/topic headers), and `Registry.process` calls the handler with `data.shop` set to the attacker-chosen victim shop domain.

Any host application that uses `data.shop` from the handler to key its per-tenant data store, look up access tokens, or perform any tenant-scoped side effect (which is exactly the documented usage pattern in `docs/usage/webhooks.md`: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) is exposed to cross-tenant confusion driven purely by an attacker-controlled, unauthenticated header value that the library asserts is "verified" once `process` succeeds.

### Impact Explanation
This breaks a tenant identity binding (`shop` used for downstream/tenant-scoped action vs. `shop` actually authenticated by the HMAC), qualifying as cross-tenant access under a Critical-severity impact category, without requiring any credentials, `api_secret_key`, or access tokens — only network access to the app's public webhook endpoint and one legitimate/observable `(body, hmac)` pair.

### Likelihood Explanation
Exploitability depends on the attacker being able to produce or observe at least one valid `(raw_body, hmac)` pair (trivial if the attacker installs the app on their own dev/trial store and receives a real webhook, since `hmac` is a deterministic function of body and the shared `api_secret_key` known only to Shopify — but the attacker doesn't need to know the secret, only to *replay* a body+hmac pair they legitimately received). This makes the attack straightforward for any developer/tester with access to their own store's webhooks, and the impact is amplified by the library's documentation explicitly encouraging apps to key downstream logic off `data.shop`.

### Recommendation
Bind the `shop` (and ideally `topic`, `api_version`, `webhook_id`) header values into the HMAC-covered signable string for `Webhooks::Request`, or otherwise cryptographically verify them, so that `Registry.process` cannot be tricked into dispatching a validly-signed body under an attacker-chosen shop/topic. At minimum, document prominently that `data.shop`/`data.topic` are not covered by the HMAC and must not be trusted for tenant-scoping without additional verification (e.g., cross-checking against a shop-to-access-token store established via OAuth).

body = '{"id":1}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, body)
# (attacker doesn't need api_secret_key; they just capture this pair from a real webhook they received)

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end

# typed: strict

module ShopifyAPI
  module Utils
    module HmacValidator
      extend T::Sig

      class << self
        extend T::Sig

        sig { params(verifiable_query: VerifiableQuery).returns(T::Boolean) }
        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(signable_string: String, secret: String).returns(String) }
        def compute_signature(signable_string, secret)
          OpenSSL::HMAC.hexdigest(
            OpenSSL::Digest.new("sha256"),
            secret,
            signable_string,
          )
        end
      end
    end
  end
end
