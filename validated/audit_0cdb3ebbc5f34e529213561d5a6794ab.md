Based on my research, I found a strong analog in the `pallet-intents-coprocessor` module's phantom order generation mechanism, which assumes a fixed `PhantomOrderInterval` has elapsed between generations, mirroring the exact bug class from the Zivoe report (a fixed-period assumption not strictly tied to actual elapsed time).

### Title
Phantom order generation interval check uses last-generation height as a fixed period boundary rather than actual elapsed time, causing incorrect scheduling drift - (File: `modules/pallets/intents-coprocessor/src/lib.rs`)

### Summary
The `on_initialize` hook of `pallet-intents-coprocessor` generates a new phantom order once `PhantomOrderInterval` blocks have passed since `LastPhantomGeneration`, similar to how `ZivoeYDL::earningsTrancheuse()` assumed `daysBetweenDistributions` had elapsed exactly. Because block production is not on a fixed clock and the hook only runs opportunistically (subject to weight/queue conditions and chain congestion), the actual elapsed interval between successive phantom order generations can silently drift longer than the configured interval, without the arithmetic self-correcting for the delay [1](#0-0) .

### Finding Description
The benchmarking harness for `generate_phantom_order` explicitly documents that the hook reads `LastPhantomGeneration`/`PhantomOrderInterval` "to decide whether an interval has elapsed" [2](#0-1) . This is structurally the same pattern flagged in the Zivoe finding: a period-based calculation (`daysBetweenDistributions` there, `PhantomOrderInterval` here) that is checked against a "last update" timestamp/height, but the downstream consumers (fillers bidding on phantom orders) treat the resulting order's window as if it started exactly on schedule.

Compounding this, the SDK/simplex changelog for phantom orders confirms that in practice, "phantom orders" have a narrow, block-denominated bid window and that pollers/schedulers can fall behind — the same "delay after the deadline mark" issue described in the Zivoe report, where `distributeYield()` might be called well after `lastDistribution + daysBetweenDistributions*86400` has passed [3](#0-2) . The docs explicitly state the lag "grew monotonically" and describe a scenario where a filler is "3,448 blocks behind" for nine hours, with the phantom-order generation cursor never catching up to compensate for the missed interval [4](#0-3) .

### Impact Explanation
If `on_initialize` in `pallet-intents-coprocessor` treats `PhantomOrderInterval` as a strict, un-drifting boundary (rather than tracking actual elapsed blocks/time robustly), phantom orders can be generated later than intended relative to the deadline height read from the destination chain (`pallet_ismp::LatestStateMachineHeight`) at hook-execution time [5](#0-4) . This shortens the effective bid window fillers have to respond, or causes deadlines to be computed off a stale height, degrading the phantom-order/pool-bidding mechanism's fairness and potentially causing systemic underparticipation — directly analogous to the "less yield distributed" impact in the Zivoe finding, but here manifesting as "fewer/late phantom orders processed correctly," which is a route-availability/fairness degradation rather than fund loss.

### Likelihood Explanation
Likelihood is comparable to the original: it requires the on-chain hook or its downstream consumers to experience delay beyond the nominal interval (network congestion, block production variance, or `on_initialize` weight/queue contention), which — per the accepted Zivoe judgment precedent — is considered a realistic, non-network-liveness scenario worth medium severity when the resulting mis-timed windows cause measurable, non-trivial degradation.

### Recommendation
Anchor phantom order deadlines/intervals to the actual current block/height read at the time `on_initialize` executes (as is already partially done via `pallet_ismp::LatestStateMachineHeight`) rather than assuming a fixed nominal interval since `LastPhantomGeneration`. Where a strict interval must gate generation, compute the next generation's window bounds using `current_height - LastPhantomGeneration` (actual elapsed blocks) rather than the configured `PhantomOrderInterval` constant, so that a delayed hook execution does not silently shrink the resulting order's usable bid window.

# 2026-09-03 — Stop bidding on phantom orders whose window has closed

A mainnet filler (`0xb98306ac…`, Hyperbridge `12KyapjPpm2fK62gepzZKEEk3xP9vzEJdWBspagx8DxZaj2k`) spent nine hours
bidding on phantom orders that had expired hours earlier. Its bids landed, nothing errored, and it backed no pool
the whole time: the indexer shows 0 `PoolBidder` rows against 692 balance rows, the newest of which stops at
03:03 while healthy fillers keep writing them.

The lag grew monotonically — 4 blocks behind the order it bid on, then 147, 1611, 2228, 2765, 3448 — which is the
signature of a cursor that cannot catch up rather than a one-off stall. `pollPhantomOrders` advances the cursor
by at most `maxBlocksPerPoll` (10) per tick and never skips ahead, so a deficit accumulated while ticks were lost
(a scan overrunning the 15s interval, or the rate-limit backoff sitting out up to 8 ticks) is only repaid if the
sustained rate beats the chain's. Below that, the filler stays behind forever, and every order it then sees is
already dead: the bid window is tens of blocks.

Two fixes, at the two places the delay can come from:

- The SDK's poll now abandons a backlog older than one generation cycle rather than walking it, and the scanner
  logs each skip: a filler that keeps skipping is one falling behind the chain.
- `handlePhantomOrders` drops events older than the pallet's own bid window (read from chain, plus a 2-block
  margin) against one head read per batch. That also covers the delay the scanner cannot see — the global queue this runs on, and the
  quoting inside `preparePhantomBid` — and turns a silent outage into a warning naming the lag. A failed head
  read keeps every event: one flaky endpoint must not stop the filler bidding.

Neither is a substitute for the other: the first stops the backlog forming, the second refuses to act on one that
does.
