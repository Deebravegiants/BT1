## Finding

### Title
`IntentGatewayV2.withdraw` (Tron) ignores the ERC20 `transfer` return value, permanently marking escrow as settled even when the payout silently fails - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Sherlock report flags `AccountFacet.withdraw` for not verifying the caller has enough balance before paying out, so the call can fail after consuming gas. The reachable analog in Hyperbridge is the Tron `IntentGatewayV2.withdraw` function, which similarly fails to verify that a payout actually succeeded before finalizing escrow accounting — except here the consequence is not wasted gas but permanent loss of the user's/solver's bridged funds.

### Finding Description
`withdraw()` is the internal handler invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` messages relayed cross-chain, and from `onGetResponse` for source-chain cancellations [1](#0-0) . For ERC20 payouts it uses a raw low-level `.call()` and only checks that the *call itself* succeeded, not the boolean return value of `transfer()`: [2](#0-1) 

The escrow-sufficiency check is also weak — it only verifies `_orders[commitment][token] != 0`, not that `amount <= _orders[commitment][token]` — but that particular gap is self-correcting because Solidity 0.8's checked arithmetic on `_orders[body.commitment][token] -= amount;` reverts on underflow. The real gap is the unchecked `transfer` return value: for any ERC20 token that returns `false` on failure instead of reverting (a well known non-standard-but-common behavior, e.g. contract insufficiently funded for that specific token, or a token pausing transfers to blacklisted beneficiaries), `success` from `.call()` is `true` even though no tokens moved. Execution then proceeds to mark the order filled and decrement the escrow ledger:
- `_filled[body.commitment] = beneficiary;` is set unconditionally before the loop [3](#0-2) 
- `_orders[body.commitment][token] -= amount;` zeroes the accounted escrow regardless of whether `transfer` actually returned `true` [4](#0-3) 

By contrast, the mainline (non-Tron) `IntentsBase._withdraw` uses OpenZeppelin's `SafeERC20.safeTransfer`, which reverts if the token returns `false`, keeping the mint/escrow state atomic with the actual transfer [5](#0-4) . The Tron variant regressed this safety property with a manual `.call()` pattern that ignores the `transfer` boolean.

The same unchecked pattern also appears in `SweepDust` handling in the same contract [6](#0-5) .

### Impact Explanation
Once `_filled[commitment]` is set and `_orders[commitment][token]` is decremented, the order is permanently considered "settled" — `UnknownOrder()` will trip on any retry attempt since the escrow balance is now recorded as zero, and there is no other withdrawal path. If the actual token transfer silently failed, the escrowed funds remain stuck in the contract forever, unclaimable by the intended beneficiary (user on refund, or solver on redeem). This is a permanent freezing/loss of user funds, reachable by any relayer delivering a legitimately-authenticated cross-chain `RedeemEscrow`/`RefundEscrow` message or GET response for a token that doesn't strictly follow EIP-20's revert-on-failure convention.

### Likelihood Explanation
Exploitation requires an input/output token used in an intent order to be a non-reverting, boolean-returning-false-on-failure ERC20 (a known real-world token category, distinct from fully compliant tokens), or a scenario where the contract's balance of that specific token is insufficient at withdrawal time for other reasons (e.g., accounting mismatch, prior partial dust sweep, blacklist/pause). Delivery of `RedeemEscrow`/`RefundEscrow` is a normal, permissionless relayed action in the intents flow, so likelihood is governed entirely by token selection rather than by any privileged action — a realistic and externally reachable trigger for chains/tokens deployed with the Tron `IntentGatewayV2`.

### Recommendation
Replace the raw `.call()` + `success`-only check with `SafeERC20.safeTransfer` (as already done in the mainline `IntentsBase.sol`), or explicitly decode and check the ERC20 `transfer` return value in addition to the low-level call success, before mutating `_filled` and `_orders`. Apply the same fix to the `SweepDust` branch.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron) with an input/output token that implements `transfer` to return `false` on failure instead of reverting (or contrive a state where the contract's balance of that token is less than `amount` while `_orders[commitment][token]` is still non-zero due to an accounting mismatch).
2. Place and fill/cancel an order so a `RedeemEscrow`/`RefundEscrow` message is dispatched and delivered via `onAccept`.
3. In `withdraw()`, `token.call(...transfer...)` returns `success = true` (the call didn't revert) even though the token's internal `transfer` logic returned `false` and moved no funds.
4. `_filled[commitment]` is set and `_orders[commitment][token]` is decremented to zero, but the beneficiary's token balance is unchanged.
5. Any subsequent attempt to reclaim the escrow reverts with `UnknownOrder()` since `_orders[commitment][token] == 0` — the funds are now permanently stuck in the contract.
