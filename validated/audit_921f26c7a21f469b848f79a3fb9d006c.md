### Title
Webhook `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers to build the `WebhookMetadata` passed to the host app's handler. Because the HMAC signature never covers these headers, an attacker who can obtain any validly-signed webhook body for the app (trivially available, since the same `client_secret`/`api_secret_key` is used to sign webhooks for *every* shop that installs the app) can replay that body with a forged `shop-domain` header pointing at a victim shop, and the signature will still validate.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` performs authentication like this: [1](#0-0) 

The HMAC check delegates to `Utils::HmacValidator.validate`, which in turn calls `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw body: [3](#0-2) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, none of which are included in the signed string: [4](#0-3) 

After the HMAC check passes, `request.shop` (an unauthenticated header value) is used verbatim as the tenant identifier handed to the host application's handler: [5](#0-4) [6](#0-5) 

The identity binding that should hold is:
`hmac_signed_bytes == bytes_the_app_acts_on`

but in reality:
`hmac_signed_bytes (raw body only) != bytes_the_app_acts_on (raw body + shop-domain/topic/webhook-id/api-version headers)`

The `api_secret_key` used to compute/verify this HMAC is the app's `client_secret`, shared across *every* shop that installs the app — it is not a per-shop secret. Any unprivileged internet user can install the target app on their own free development store, receive a webhook with a genuine, correctly-computed HMAC over some body, and then replay that exact body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with an arbitrary victim shop's domain. Because the signature never covers that header, `HmacValidator.validate` still succeeds, and the app's handler receives a `WebhookMetadata` claiming the event originated from the victim tenant.

### Impact Explanation
This breaks the tenant-authentication boundary the HMAC is meant to provide: an attacker with no access to the victim shop can make the host application process attacker-controlled data (of a topic/body they can freely choose, subject to matching a topic they can generate a genuine signature for) under the identity of a different, victim shop. Depending on how the host app's webhook handler uses `data.shop` (e.g., to look up and mutate per-shop records, to trigger side effects such as data sync, order processing, or uninstall/GDPR flows), this can lead to cross-tenant data corruption or spoofed events attributed to a victim merchant — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app built on this gem that trusts `WebhookMetadata#shop` for tenant scoping (the documented and intended use of this field) without independently re-verifying the shop against a known/expected value. The prerequisite — installing the target app on an attacker-controlled store to obtain a genuinely-signed webhook body/HMAC pair — requires no privileges beyond being an ordinary internet user with a free Shopify development store, and topic bodies for common webhook topics (e.g. `app/uninstalled`, `customers/data_request`, generic resource webhooks with attacker-influenced fields) are easy to obtain.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, and ideally `topic`/`webhook-id`/`api-version`) inside the signed/verified payload rather than only the raw body, or, at minimum, require the host application to independently authenticate/authorize the `shop` value against its own webhook registration records before trusting `WebhookMetadata#shop`. If Shopify's own webhook HMAC scheme genuinely only ever signs the body (matching Shopify's documented behavior), then `ShopifyAPI::Webhooks::Registry`/`Request` should not present `shop` as though it were authenticated data — the gem should clearly document that `shop` is untrusted header data and/or offer a mechanism to cross-check it against the shop that the webhook subscription was registered for.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, receiving a legitimate webhook, e.g. for `app/uninstalled`:
   ```
   POST /webhooks
   X-Shopify-Topic: app/uninstalled
   X-Shopify-Hmac-Sha256: <valid signature over body B>
   X-Shopify-Shop-Domain: attacker.myshopify.com
   Body: B
   ```
2. Attacker replays the identical request to the same endpoint, only changing the shop header:
   ```
   POST /webhooks
   X-Shopify-Topic: app/uninstalled
   X-Shopify-Hmac-Sha256: <same valid signature over body B>
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   Body: B
   ```
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `to_signable_string` (`B`) using the app's `api_secret_key`, which matches, so validation passes.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and invokes the host app's handler, which now processes an uninstall (or other topic) event as if it came from the victim shop.
