### Title
Webhook HMAC Does Not Cover `shop-domain`/`topic` Headers, Enabling Cross-Tenant Webhook Injection - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only, while `topic`, `shop-domain`, `webhook-id`, and `api-version` are read directly from unauthenticated headers and are never included in the signed payload. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop` and `request.topic` to build the `WebhookMetadata` passed to the app's handler, breaking the binding between "bytes verified" (raw body) and "bytes acted on" (headers used to select tenant/topic).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors read straight from HTTP headers with no cryptographic binding to the signed content: [2](#0-1) 

`HmacValidator.validate` only ever hashes `verifiable_query.to_signable_string` (i.e., the raw body) against the received `hmac`: [3](#0-2) 

`Registry.process` checks that HMAC, then immediately trusts `request.shop` and `request.topic` (both unauthenticated headers) to dispatch to the handler: [4](#0-3) 

The equality the code should enforce but does not is:
`shop_header == shop_bound_by_hmac`

Since the HMAC signature only proves "this `api_secret_key` holder produced this body," but not "for this shop," any party who legitimately receives one valid signed webhook body (e.g., because they run their own installed shop of the same app) can replay that exact body with a forged `x-shopify-shop-domain` (and/or `x-shopify-topic`) header pointing at a different shop. `Registry.process` will pass HMAC validation (body unchanged) and hand the handler a `WebhookMetadata` claiming the data came from the victim shop: [5](#0-4) 

Any host application that uses `data.shop` from `WebhookMetadata` to key data updates (the exact intended usage pattern of this field, since it's the only tenant identifier surfaced by the gem for webhook handling) will attribute attacker-controlled body content to another merchant's tenant.

### Impact Explanation
This is a cross-tenant data-integrity/authentication issue: an unprivileged attacker who is merely another legitimate installer of the same app can inject data attributed to a victim shop into the host application's webhook processing pipeline, without possessing the `api_secret_key`, an access token, or any victim credential. This matches the "cross-tenant access" Critical impact category, since the gem itself provides no way for consuming code to detect that the `shop`/`topic` values were not actually covered by the signature.

### Likelihood Explanation
Exploitation requires only: (1) the attacker installs the app themselves (or otherwise obtains one legitimately signed webhook body/HMAC pair, which Shopify sends to every installed shop), and (2) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with attacker-chosen headers — both are available to any unprivileged internet user, since webhook endpoints are public HTTP endpoints and headers are attacker-controlled input to `Request.new`.

### Recommendation
Include `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) in the HMAC-signed payload verification, or otherwise cryptographically bind the shop identity to the signature before it is trusted downstream. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are NOT covered by HMAC verification and must not be trusted as tenant identifiers without additional verification by the host application.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a legitimate webhook POST with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker replays the exact same request to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com` (and/or `x-shopify-topic` to any registered topic), keeping body `B` and header `H` unchanged.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and compares it to `H` — the check passes because the body is unmodified: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: <attacker's body>, ...)`, and any host application that stores/updates per-shop data keyed by `data.shop` will now apply attacker-controlled data to the victim tenant's record.
