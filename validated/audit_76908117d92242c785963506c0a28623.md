Audit Report

## Title
Internal Vault JWT AuthToken Logged in Full at Debug Level - (File: core/services/gateway/handlers/vault/handler.go)

## Summary
`HandleJSONRPCUserMessage` logs the entire `jsonrpc.Request[json.RawMessage]` struct—including the `Auth` field carrying the caller's raw JWT bearer token—at `Debug` level before authorization occurs, via `h.lggr.Debugw("handling vault request", "method", req.Method, "requestID", req.ID, "request", req)`. [1](#0-0)  Elsewhere in the same file and in `authorizer.go`, the code deliberately avoids logging the raw token, using `"hasAuth", req.Auth != ""` instead, confirming the developers treat `Auth` as sensitive and that line 403 is an inconsistent redaction gap. [2](#0-1) 

## Finding Description
The `req` parameter is a `jsonrpc.Request[json.RawMessage]` populated from the incoming gateway message, and its `Auth` field is confirmed (via production/test usage patterns cited in the report, e.g. `req.Auth != ""`, `req.Auth == ""`) to carry the JWT bearer token used for authorization. [3](#0-2)  Because `logger.Debugw` serializes struct arguments in full, passing `req` directly (rather than a redacted projection) causes the token to be written to the log stream whenever debug-level logging is enabled, and this occurs unconditionally, before `h.requestProcessor.ProcessRequest` is even invoked to authorize the request. [4](#0-3)  No redaction, custom `MarshalLogObject`, or filtering exists for this call site — the codebase's own convention of logging `"hasAuth", req.Auth != ""` at other call sites (line 432 in this file, and in `core/capabilities/vault/authorizer.go`) demonstrates that the omission at line 403 is not intentional but a gap.

## Impact Explanation
This is a real secret-in-logs defect (CWE-532 class) that mirrors the CVE-2021-3528 root cause: an internal auth token intended to authorize sensitive Vault operations (create/update/delete/list secrets) is captured verbatim in application logs rather than redacted. Anyone with read access to gateway debug logs can harvest a live JWT and replay it to impersonate the legitimate workflow owner for Vault secret operations within the token's validity window. This is a legitimate confidentiality/integrity impact on the Vault capability's authorization boundary.

## Likelihood Explanation
Exploitation requires two things beyond an unprivileged Vault client request: (1) the gateway operator has enabled `Debug`-level logging (a supported but non-default logging configuration), and (2) the attacker (or a compromised log pipeline) has read access to the resulting log output. The vulnerable code path itself is triggered by an entirely ordinary, unprivileged Vault JSON-RPC request — no node compromise or malicious-peer capability is needed to *cause* the token to be logged. However, actually *harvesting* the token requires access to log storage/aggregation, which is a real but non-trivial secondary precondition and is the kind of environment/log-access dependency that bounty programs often scope carefully (it is not "leaked credential" exclusion since the vulnerability is the application causing the leak, not a pre-existing leaked credential).

## Recommendation
Remove `"request", req` from the debug log at `core/services/gateway/handlers/vault/handler.go:403`, or replace it with an explicit redacted projection such as `"hasAuth", req.Auth != ""`, `"method", req.Method`, `"requestID", req.ID` (consistent with the pattern already used at line 432 and in `authorizer.go`), so the raw JWT is never serialized into logs. Consider implementing a `MarshalLogObject`/`String()` override on the shared `jsonrpc.Request` type in `chainlink-common` that redacts `Auth` by default, to prevent this class of bug from recurring at other call sites.

## Proof of Concept
1. Configure the gateway with `Debug` log level enabled.
2. Send a valid Vault JSON-RPC request (e.g., `vault.secrets.list`) with a valid JWT `Auth` bearer token to the gateway's `HandleJSONRPCUserMessage` entry point.
3. Inspect log output at line 403 (`"handling vault request"`); observe the fully serialized `req` object including the raw `Auth` JWT string, logged before the authorization check in `h.requestProcessor.ProcessRequest` runs.
4. As a unit test: construct a `jsonrpc.Request[json.RawMessage]` with a non-empty `Auth` field, call `HandleJSONRPCUserMessage` with a `Debug`-level test logger/observer (e.g. zap's `zaptest/observer`), and assert that the captured log entries do not contain the raw `Auth` string.

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		// Arbitrary limit to prevent abuse
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	h.lggr.Debugw("handling vault request", "method", req.Method, "requestID", req.ID, "request", req)
	if req.Method == vaulttypes.MethodPublicKeyGet {
		// Public key requests don't require authorization,
		// Let's process this request right away.
		// Note we cache this value quite aggressively so don't need to worry about DoS.
		publicKeyResponseBytes, cachedPublicKey := h.getCachedPublicKey()
		if cachedPublicKey == nil {
			// Not found in cache. Fetch from nodes.
			ar, err := h.newActiveRequest(req, callback)
			if err != nil {
				h.lggr.Errorw("failed to create new activeRequest", "error", err)
				return err
			}
			return h.handlePublicKeyGet(ctx, ar)
		}
		h.lggr.Debugw("returning cached public key response")
		return h.handlePublicKeyGetSynchronously(ctx, req, publicKeyResponseBytes, callback)
	}

	if !vaulttypes.IsGatewaySecretsMethod(req.Method) {
		return h.sendImmediateUserResponse(ctx, req, callback, api.UnsupportedMethodError, errors.New("this method is unsupported: "+req.Method))
	}

	_, cachedPublicKey := h.getCachedPublicKey()
	authorized, err := h.requestProcessor.ProcessRequest(ctx, &req, cachedPublicKey)
