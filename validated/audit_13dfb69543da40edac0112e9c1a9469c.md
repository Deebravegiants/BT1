## Analysis

The reported DODO bug (`MarginTrading.executeOperation` accepting attacker-controlled `approve()` targets because the entry point isn't restricted to the intended caller) maps to a real, unrestricted "arbitrary call executor" pattern in this codebase: `CallDispatcher.dispatch()`.

### Title
Unauthenticated `CallDispatcher.dispatch()` lets anyone drive arbitrary `approve`/`transfer` calls, draining tokens the dispatcher transiently holds - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch(bytes memory encoded)` is a public `external` function with **no access control** at all. It decodes an arbitrary `Call[]` and executes `to.call{value: call.value}(call.data)` for each entry with no restriction on `to`, `value`, or `data`. [1](#0-0) 

This contract is used as a shared, stateless intermediary that briefly custodies tokens on behalf of `IntentGatewayV2.placeOrder`, `HyperFungibleToken.onAccept`, and `WrappedHyperFungibleToken.onAccept`. In `IntentGatewayV2.placeOrder`, when an order specifies a `predispatch` call, tokens are moved to `dispatcher` *before* the (attacker-supplied) predispatch call is executed, and the gateway only pulls them back afterward: [2](#0-1) 

Because `dispatch()` itself has no caller restriction, any address that observes tokens sitting in the `CallDispatcher` balance (e.g. between the `safeTransferFrom(msg.sender, dispatcher, amount)` and the follow-up `dispatch(abi.encode(transferCalls))` sweep-back, or tokens minted to it via `HyperFungibleToken.onAccept`'s calldata-execution feature) can front-run/directly call `CallDispatcher.dispatch()` themselves with a crafted `Call[]` such as `approve(attacker, type(uint256).max)` or `transfer(attacker, balance)` on that token, stealing funds that were never meant to be reachable by them.

### Finding Description
`ICallDispatcher.dispatch` is documented as "dispatch untrusted call(s)", implying the untrusted part is the *content* of the calls, not the *caller* of `dispatch` itself: [3](#0-2) 

However the concrete implementation exposes `dispatch` with no `onlyX` modifier, no `msg.sender` check, and no reentrancy/ownership tracking of which caller "owns" the tokens currently sitting in the contract: [1](#0-0) 

The intended flow assumes only the app contract that just funded the dispatcher (e.g. `IntentGatewayV2`) will call `dispatch()` immediately afterward with its own `predispatch.call`/`transferCalls`. But since `dispatch()` is a plain `external` function on a standalone deployed contract, nothing stops a completely unrelated address from calling it directly, at any time, with any `Call[]` — including one that `approve()`s itself or `transfer()`s out whatever ERC20 balance the dispatcher happens to be holding at that moment (funds belonging to another user's in-flight `placeOrder` predispatch, or dust/mint balances from `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata execution flows).

The documentation for the HFT calldata-execution feature already acknowledges the dispatcher "holds tokens temporarily during execution" and recommends exact (not unlimited) approvals in the `Call[]` payload — but this only mitigates the amount an attacker-supplied call *inside a legitimate flow* could pull, not the fact that a third party can call `dispatch()` directly and sweep whatever is currently held. [4](#0-3) 

### Impact Explanation
Any ERC20 tokens transiently custodied by `CallDispatcher` — tokens escrowed by an `IntentGatewayV2.placeOrder` caller for a predispatch swap, or tokens minted to the dispatcher during `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata-execution deliveries — are at risk of being approved or transferred to an attacker via a direct, unauthenticated call to `CallDispatcher.dispatch()`. This is concrete theft of user/protocol funds reachable from a single unprivileged transaction, matching the "concrete theft of funds" bar.

### Likelihood Explanation
`dispatch()` requires no privilege, no proof, and no special timing beyond racing (front-running) a legitimate flow or hitting a window where the dispatcher holds a non-zero balance. Given `CallDispatcher` is a shared, long-lived, non-reentrancy-guarded contract referenced by multiple apps (`IntentGatewayV2._params.dispatcher`, `HyperFungibleToken._dispatcher`, `WrappedHyperFungibleToken._dispatcher`), any transient balance is an exploitable target; an attacker only needs to monitor mempool/chain state for a nonzero token balance on the `CallDispatcher` address and submit a `dispatch()` call ahead of or in place of the legitimate follow-up call.

### Recommendation
1. Restrict `CallDispatcher.dispatch()` to be callable only by an authorized/allow-listed set of caller contracts (e.g. `onlyOwner`/an allowlist of registered app contracts), or
2. Make `CallDispatcher` non-shared: deploy a fresh, single-use dispatcher instance per order/message (e.g. via `CREATE2` from the app contract) so no other party can ever observe or interact with tokens it holds, or
3. Have `IntentGatewayV2`/`HyperFungibleToken` perform the escrow-transfer-in and sweep-back atomically via `delegatecall`-free internal accounting that never leaves attacker-observable token balances on an externally callable shared contract between transactions.

### Proof of Concept
1. Attacker watches for a pending `IntentGatewayV2.placeOrder` transaction (or any other event) that will call `IERC20(token).safeTransferFrom(msg.sender, dispatcher, amount)` targeting the shared `CallDispatcher` address, per [5](#0-4) .
2. Once that transfer lands (dispatcher now holds `amount` of `token`), before the legitimate `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` / sweep-back call executes, the attacker submits their own transaction calling `CallDispatcher.dispatch(abi.encode([Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)})]))` directly, per [6](#0-5) .
3. Since `dispatch()` has no caller check, this succeeds, granting the attacker an unlimited allowance over the dispatcher's `token` balance, which they then drain with `transferFrom`.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
