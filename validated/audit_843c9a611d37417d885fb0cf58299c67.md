### Title
Emporium Min-proof path lets any attacker execute arbitrary, unauthorized, unaccounted calls that drain Emporium's held funds - (File: `contracts/CircomDataBuilder.sol`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only constrains `message`, `timeStamp`, and `calldataHash` [1](#0-0) . This "Min" proof requires no balance/token declarations, yet `EmporiumUpgradeable.runAction` still executes every op in the attacker-supplied `EmporiumStack` unconditionally, and when `signerAddress == address(0)` `verifyWallet` performs **no signature check at all** [2](#0-1) . Combined with the fact that both Hinkal's and Emporium's balance-accounting loops iterate `circomData.erc20TokenAddresses` (length 0 here), any funds Emporium happens to hold can be moved out via `op.endpoint.call{value: op.value}(op.callData)` with zero accounting or authorization.

### Finding Description
The invariant that should hold is: *assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter`*.

- `formInputForCircom` selects `formInputEmporiumMin` whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0` [3](#0-2) . This min-circuit input array contains only `emporiumMessage`, `timeStamp`, `calldataHash` — nothing about `amountChanges`, tokens, or `ops` content beyond the opaque `calldataHash` binding (which the attacker, as their own prover, fully controls).
- `dimensionsCheck` only enforces that `erc20TokenAddresses.length == dimensions.tokenNumber` (i.e. 0), and never restricts `EmporiumStack.ops.length` or content when `erc20TokenAddresses` is empty [4](#0-3) .
- In `Hinkal.transact`, since `circomData.erc20TokenAddresses.length == 0`, the loop that computes `balanceDif` and enforces `balanceDif == amountChanges + utxoAmount` never executes [5](#0-4) ; `_externalTransact`'s deposit-into-Emporium loop is likewise empty [6](#0-5) .
- Inside `EmporiumUpgradeable.runAction`, the ops loop executes regardless of `erc20TokenAddresses.length`: `op.endpoint.call{value: op.value}(op.callData)` is a raw call made **as Emporium**, drawing `op.value` from Emporium's own ETH balance and able to invoke any function (e.g. `IERC20.transfer`) on any `op.endpoint` [7](#0-6) . The post-loop balance/UTXO accounting loop again iterates `circomData.erc20TokenAddresses`, so with length 0 it does nothing [8](#0-7) .
- Critically, `verifyWallet` only enforces a signature when `stack.signerAddress != address(0)`; for `signerAddress == address(0)` it just marks the message used and returns, meaning **no cryptographic authorization gates the ops at all** in this branch [2](#0-1) .

Exploit flow: an unprivileged attacker generates their own valid Min-circuit proof (trivial — they choose their own `messageSeed`/`calldataHash`), calls `Hinkal.transact` with `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, and `externalActionData.externalActionMetadata` ABI-encoding an `EmporiumStack{ signerAddress: address(0), ops: [{ endpoint: <token or receiver>, invokeWallet: false, value: <Emporium's ETH balance>, callData: <transfer(attacker, balance) or empty> }] }`. This reaches `EmporiumUpgradeable.runAction`, which executes the op as Emporium with no signature check and no balance accounting, moving out whatever ETH/tokens Emporium currently holds (e.g., transient/in-flight balances left from other users' Emporium operations, rounding dust, or fee remainders) directly to the attacker.

None of the existing guards stop this: `performHinkalChecks`/`dimensionsCheck` only validate array-length consistency, not op semantics; `verifyProof` only proves the trivial Min statement; the balance/slippage `require`s in `Hinkal.transact` and `runAction` are vacuously satisfied because they iterate an empty array.

### Impact Explanation
Any ETH or ERC20 balance sitting in the Emporium contract — whether from in-flight multi-step user operations, protocol fee remainders, or dust — can be stolen by any unprivileged party with no signature or balance justification. This is direct theft of funds routed through Hinkal's Emporium external action, matching Critical severity (direct theft of shielded or in-flight user funds). The attack is repeatable indefinitely whenever Emporium holds any residual balance.

### Likelihood Explanation
The only precondition is that Emporium holds a nonzero balance of some asset at call time (as the question's own suggested fast-validation approach states: "fund Emporium, run min-path op stealing that balance"). No privileged role, relayer cooperation, or victim action is required — the attacker supplies their own proof, own calldata, and own `EmporiumStack`. Cost is a single transaction plus proof generation for the trivial Min circuit statement.

### Recommendation
Do not allow `EmporiumUpgradeable.runAction` to execute arbitrary `ops` when `erc20TokenAddresses.length == 0`/Min-path is used unless `signerAddress != address(0)` and a valid signature authorizes the exact `ops` (as already done for the non-zero-signer branch). Alternatively, forbid the Min-circuit path entirely for the Emporium action when `stack.ops.length > 0`, restricting Min proofs to genuinely message-only interactions, and require the min circuit's public inputs to also bind/attest that no value-moving `ops` are present (e.g., constrain `ops` to be empty or `value == 0` and `callData` non-state-changing when `erc20TokenAddresses.length == 0`).

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` per existing test harness; register Emporium as the external action for `HINKAL_EMPORIUM_ACTION_ID`.
2. Fund Emporium directly with ETH (simulating leftover/in-flight balance) via `vm.deal(address(emporium), 10 ether)`.
3. As an attacker EOA with no special role, construct `CircomData` with `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `amountChanges = []`, `onChainCreation = []`, `slippageValues = []`, and `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({ signerAddress: address(0), ops: [EmporiumOperation({endpoint: attacker, invokeWallet: false, value: 10 ether, callData: ""})], maxFee: 0, deadline: type(uint256).max }))`.
4. Generate a valid Min-circuit proof locally for `message = Poseidon(messageSeed)`, `timeStamp`, `calldataHash` matching the crafted `CircomData` (attacker fully controls `messageSeed`).
5. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from the attacker address.
6. Assert: `attacker.balance` increases by `10 ether` and `address(emporium).balance` goes to `0`, while `require(balanceDif >= slippageValues[i])` and `require(balanceDif == amountChanges[i] + utxoAmount)` in `Hinkal.transact` never executed (array length 0), and `BalanceChangeShouldBePositive` in `EmporiumUpgradeable.runAction` never reverted (array length 0) — confirming the equality "assets moved == assets accounted" was 10 ether ≠ 0.
