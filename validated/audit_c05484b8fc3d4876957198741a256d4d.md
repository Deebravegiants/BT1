This confirms the finding: `WebhookMetadata.shop` (documented and used by host apps for tenant identification, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)` in `docs/usage/webhooks.md`) is populated purely from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, while the HMAC only authenticates the raw request body.

### Title
Webhook `shop` domain is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate`, whose signable content is defined by `Request#to_signable_string` as just `@raw_body` [1](#0-0) . The `shop` (and `topic`, `webhook_id`, `api_version`) values, however, are read directly from HTTP headers and are never included in the HMAC-signed content [2](#0-1) . `Registry.process` still forwards this unauthenticated `shop` value straight into `WebhookMetadata`, which host apps use as the tenant identifier [3](#0-2) [4](#0-3) .

### Finding Description
The identity binding that should hold is: `hmac-verified(shop)` == `shop delivered to the handler`. In this gem it instead holds: `hmac-verified(raw_body)` != `shop header value`.

- `HmacValidator.validate` computes/compares HMAC only over `verifiable_query.to_signable_string` [5](#0-4) .
- For webhooks, `to_signable_string` returns only `@raw_body`; `shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) and are not part of the signed material at all [6](#0-5) .
- `Registry.process` validates the HMAC, then immediately trusts `request.shop` (header-derived) to build `WebhookMetadata`, which is the object host applications use to route work to a specific merchant/tenant, as shown in the gem's own documentation (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [7](#0-6) .

Because the HMAC is computed only from the JSON body and the app's `api_secret_key` is fixed per app (shared across all shops that install the app), the value of `hmac` for a given raw body is identical regardless of which shop actually triggered the webhook. Consequently, any party who can obtain one legitimate `(raw_body, hmac)` pair from Shopify — trivially achievable by installing the app on their own free/dev store and receiving one real webhook — can replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) headers with an arbitrary value, e.g., a victim merchant's domain. `HmacValidator.validate` will still pass because it only checks the body against the HMAC, never the headers. The forged request is then handed to the registered handler as if it genuinely originated from the victim shop.

### Impact Explanation
This breaks the tenant/shop identity boundary that host applications rely on `WebhookMetadata.shop` to enforce (Critical: cross-tenant access). An attacker can inject arbitrary webhook events attributed to any shop domain they choose (e.g., forge `app/uninstalled`, `orders/create`, `customers/data_request`, etc., for a shop they don't operate), causing the host application to perform tenant-scoped side effects (data writes, session/session-state changes, compliance actions) against a shop the attacker does not control. Because the identity check that binds "verified sender" to "acted-upon shop" is absent, this is a genuine cross-tenant authentication-adjacent bypass reachable by any unprivileged internet user who can install the app on a shop they control (a normal, unprivileged action) and then craft raw HTTP requests to the app's public webhook endpoint.

### Likelihood Explanation
High likelihood: no secrets beyond a single legitimately-delivered webhook body+HMAC pair (obtainable by any attacker who installs the app on their own store, which every app must allow) are needed. Crafting an HTTP POST with modified headers is trivial and requires no privileged access, TLS interception, or knowledge of `api_secret_key`.

### Recommendation
Bind the identity fields into the HMAC-verified material, or otherwise cryptographically/authoritatively verify the `shop` value before trusting it: e.g., include `shop`, `topic`, and `webhook_id` in the signable string computed for webhook HMAC verification (mirroring how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop` in the OAuth HMAC check), or reject/require that the delivered `shop` be cross-checked against a known/registered shop for the specific webhook subscription (e.g., by looking up the webhook by `webhook_id` via the Admin API and confirming it belongs to the claimed shop) before invoking the handler.

### Proof of Concept
1. Attacker installs the target app on their own Shopify dev store `attacker.myshopify.com` and receives one legitimate webhook delivery, e.g. body `{"id":1}` with a valid `X-Shopify-Hmac-Sha256` header (call it `H`) computed by Shopify using the app's `api_secret_key`.
2. Attacker sends a POST to the app's webhook endpoint with:
   - Body: the exact same `{"id":1}`
   - `X-Shopify-Hmac-Sha256: H` (unchanged, still valid for this body)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - `X-Shopify-Topic: app/uninstalled` (or any registered topic)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` and compares to `H` — validation succeeds [8](#0-7) .
4. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to process the event as though it came from the victim shop [9](#0-8) .
