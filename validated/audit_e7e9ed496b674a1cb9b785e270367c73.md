### Title
Webhook HMAC signature does not cover the `shop` (tenant) identifier, allowing shop-header spoofing / cross-tenant webhook confusion - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, never the `shopify-shop-domain` header. `Utils::HmacValidator.validate` therefore only proves that the *body* was signed with the app's secret — it says nothing about which shop the request claims to be from. Yet `Webhooks::Registry.process` unconditionally trusts `request.shop` (parsed straight from the unauthenticated header) and forwards it as the tenant identifier to the app's webhook handler. This is the same class of bug as the LayerZero refund-address issue: the value that is cryptographically bound/verified (the raw body bytes) is not the same value that is later acted upon as the identity/tenant key (the `shop` header).

### Finding Description
- `Request#hmac` reads the `shopify-hmac-sha256` header, and `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) [2](#0-1) 
- `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic binding to the signature at all: [3](#0-2) 
- `HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it against the `hmac` field — for a `Webhooks::Request` this is `HMAC(secret, raw_body)`, i.e., the shop header is never part of the signed material: [4](#0-3) [5](#0-4) 
- `Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity passed to the app's handler, with no secondary check that the shop matches anything bound to the signature: [6](#0-5) 

The identity-binding equality that should hold is: `shop-that-is-cryptographically-verified == shop-that-is-acted-upon`. Here, the verified quantity is only `raw_body`; the acted-upon quantity is the unauthenticated `shop` header. Because every shop installed on the same app shares the same `api_secret_key`, an attacker who controls one tenant (e.g., installs the app on their own store, or otherwise causes a webhook to fire for a body they know) can capture a validly-signed `(raw_body, hmac)` pair and replay it with an arbitrary `shopify-shop-domain` header value substituted in. `HmacValidator.validate` will still return `true` because it only re-hashes `raw_body`, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the spoofed shop.

### Impact Explanation
This breaks the shop/tenant identity binding that host applications rely on to route webhook data to the correct merchant's records. Depending on how the host app uses `WebhookMetadata#shop` (most `shopify_app`-style integrations key session/storage lookups off exactly this field), an attacker-controlled body can be attributed to another (victim) shop, i.e., cross-tenant confusion/injection of attacker-chosen data into another tenant's data path. This matches the "cross-tenant access" Critical impact category, since the identity used to decide "whose data is this" is not the identity that was actually authenticated.

### Likelihood Explanation
Requires the attacker to have legitimate access to at least one installation of the target app (e.g., their own store) so they can obtain one validly-signed body/HMAC pair for a topic/payload they control, then replay the raw body + same HMAC header while forging the `shopify-shop-domain` header (headers are fully attacker-controlled in a raw HTTP request the app receives). No access token, `client_secret`, or privileged account for the *victim* shop is required — only participation as any tenant of the same app. This is a realistic scenario for any multi-tenant Shopify app, matching the "unprivileged internet user" threat model.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`) into the signed material that is checked, or otherwise cross-validate the header-derived shop against a value that is cryptographically tied to the signature (Shopify's own webhook signature is only ever documented/guaranteed over the raw body, so in practice the gem should require host apps to independently authorize `shop` against a shop they already know is installed, e.g., look up `Registration`/session storage for that specific shop and reject if it is not one they previously registered a webhook subscription for), rather than trusting the header value implicitly for identity-sensitive routing.

### Proof of Concept
1. App has two installations: attacker's shop `attacker.myshopify.com` and victim shop `victim.myshopify.com`, both webhooks signed with the same `api_secret_key`.
2. Attacker triggers/observes a webhook delivery to their own shop and records `raw_body` and the `shopify-hmac-sha256` value.
3. Attacker sends a forged HTTP request to the app's webhook endpoint using the same `raw_body` and `shopify-hmac-sha256`, but sets `shopify-shop-domain: victim.myshopify.com`.
4. `Webhooks::Request.new(raw_body:, headers:)` builds a request object; `HmacValidator.validate(request)` recomputes `HMAC(secret, raw_body)` — identical to step 2's HMAC — and returns `true`.
5. `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: parsed_body, ...))`, i.e., attacker-controlled body is delivered under the victim shop's identity, despite `victim.myshopify.com` never having produced this webhook.           received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
