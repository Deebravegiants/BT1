### Title
Off-chain output commitments accept unauthenticated `encryptedOutputs`, permanently freezing recipient's shielded balance - (File: `contracts/HinkalHelper.sol`)

### Summary
For off-chain (private) outputs, the only channel through which a recipient learns the secret note data (`outAmounts[i][j]`, the ephemeral point `H0Ax/H0Ay`, `outTimeStamp`) needed to later reconstruct `inAmounts`, `inH0Ax`, `inH0Ay`, `inTimeStamps` and re-derive the nullifier for spending is `circomData.encryptedOutputs[i][j]`. The dimension/validity checks in `HinkalHelper.sol` only assert that each `encryptedOutputs[i][j]` is non-empty; they never bind its plaintext content to the on-chain `outCommitments[i][j]` value that the circuit already proved is correctly formed. A malicious sender can therefore construct a fully valid proof/commitment (satisfying the circuit's balance equality) while sending the victim a garbage or mismatched `encryptedOutputs[i][j]` blob, exactly analogous to the Monero report's manipulation of `ecdhInfo` — the recipient's wallet cannot reconstruct the private inputs for that leaf and can never spend/sweep the value it represents.

### Finding Description
In `MainEVMCircuit.circom`, the output commitment equality is: [1](#0-0) 
`outCommitments[i][j]` is a Poseidon hash of `(outAmounts[i][j], erc20TokenAddress, outPublicKeys[i][j], outTimeStamp)`, per `OriginalCommitmentCalculator`: [2](#0-1) 
`outPublicKeys[i][j]` itself is derived from a secret ephemeral point `H0Ax/H0Ay` known only to the sender at proof time (`StealthAddressCalculator`): [3](#0-2) 

None of `outAmounts`, `outPublicKeys`'s underlying `H0Ax/H0Ay`, or how the recipient should nullify the note are part of `calldataHash` or the public-input vector — they exist purely as private witness values. The only avenue by which they reach the recipient is the sidecar `encryptedOutputs[i][j]` byte blob emitted alongside the commitment. On-chain validation of this blob is limited to a non-zero length check: [4](#0-3) 

There is no Poseidon/commitment binding proof, MAC, or circuit constraint that ties `encryptedOutputs[i][j]`'s plaintext to `outAmounts[i][j]`/`H0Ax`/`H0Ay`/`outTimeStamp` used to build `outCommitments[i][j]`. Compare this with the on-chain deposit path, where the full plaintext `UTXO` struct (amount, erc20Address, full `StealthAddressStructure`, timestamp) is emitted directly in the `NewCommitment` event regardless of the (unchecked) `onChainEncryptedOutput` content: [5](#0-4) 
— so on-chain leaves remain spendable even with a garbage encrypted blob because the needed data is public anyway. For off-chain leaves, however, there is no such public fallback: `outAmounts`/`H0Ax`/`H0Ay` never appear in calldata or events, so if `encryptedOutputs[i][j]` does not correctly decrypt to those values, the leaf inserted into the merkle tree (`insertCommitments`, `contracts/HinkalBase.sol:72-133`) is a real, value-backed commitment (it satisfies the circuit's `inTotal + amountChanges === outTotal` balance equation and gets counted against the sender's balance) that the recipient can never scan, decrypt, or construct spend inputs for.

This breaks the equality the report's bug class targets: a value-bearing leaf the tree legitimately produced becomes permanently unspendable because the value that should reach the recipient through `encryptedOutputs` was never checked against the balance-changing equation the circuit enforced.

### Impact Explanation
This qualifies as permanent freezing of user funds (Critical, per the provided impact list): the sender's shielded balance is correctly debited and a corresponding commitment is inserted into the merkle tree, meaning the value "exists" in the total supply accounting, but the intended recipient has no cryptographic means to recover the note's amount/keys and can never nullify or spend it. The attack requires no relayer, admin, or privileged key — any unprivileged sender interacting normally through `transact()` can trigger it against any recipient's known stealth address, mirroring the "attacker needs only the victim's public address" precondition in the original Monero report.

### Likelihood Explanation
Likelihood is high: any user submitting a normal shielded transfer to a known recipient stealth address can substitute a malformed `encryptedOutputs[i][j]` (or one encrypted under the wrong key/format) while keeping a valid proof, since the check in `HinkalHelper.sol` performs no plaintext validation beyond `length > 0`. This does not require breaking cryptography — it just requires omitting/corrupting the encryption step that current SDK code presumably performs faithfully.

### Recommendation
Add an on-chain (or circuit-level) binding between `encryptedOutputs[i][j]` and the private witness values used to build `outCommitments[i][j]`, e.g., include a Poseidon commitment/tag over `(outAmounts[i][j], H0Ax, H0Ay, outTimeStamp)` derived inside the circuit as a public output, and require `keccak256`/hash-based tag verification against a portion of `encryptedOutputs[i][j]` on-chain, so a mismatched encrypted payload cannot be paired with a validly proved commitment.

### Proof of Concept
1. Attacker (sender) constructs a valid shielded transfer via `transact()` targeting victim's known stealth address, with correct `outAmounts[i][j]`, `H0Ax/H0Ay`, and `outTimeStamp` fed into the circuit so that `outCommitments[i][j]` and the balance equation `inTotal + amountChanges[i] === outTotal` (`circuits/MainEVMCircuit.circom:168`) hold and the proof verifies.
2. Instead of correctly encrypting `(outAmounts[i][j], H0Ax, H0Ay, outTimeStamp)` under the victim's key, attacker submits arbitrary/garbage bytes as `circomData.encryptedOutputs[i][j]` — only constraint enforced is non-empty length (`contracts/HinkalHelper.sol:144-149`).
3. `transact()` succeeds: sender's on-chain balance is debited by `amountChanges[i]`, the valid commitment leaf is inserted (`contracts/HinkalBase.sol:72-133`), and `NewCommitment` is emitted with the garbage `encryptedOutputs[i][j]` as payload.
4. Victim's wallet scans `NewCommitment` events but cannot decrypt the payload to recover `outAmounts[i][j]`/`H0Ax`/`H0Ay`/timestamp, so it can never construct the private inputs (`inAmounts`, `inH0Ax`, `inH0Ay`, `inTimeStamps`) required by `MainEVMCircuit` to spend that leaf — the funds represented by that commitment are permanently frozen from the victim's perspective, even though they were debited from the sender and are provably part of the shielded pool total.

```text
template OriginalCommitmentCalculator() {
  signal input amount;
  signal input erc20TokenAddress;
  signal input publicKey;
  signal input timeStamp;
  signal output out;

  component calcIsAmountZero = IsZero();
  calcIsAmountZero.in <== amount;

  component calcCommitment = Poseidon(4);
  calcCommitment.inputs[0] <== amount;
  calcCommitment.inputs[1] <== erc20TokenAddress;
  calcCommitment.inputs[2] <== publicKey;
  calcCommitment.inputs[3] <== timeStamp;

  out <== calcCommitment.out * (1 - calcIsAmountZero.out);
```
