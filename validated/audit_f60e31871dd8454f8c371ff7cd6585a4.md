### Title
Webhook `shop` Field Is Not Covered by HMAC Verification, Enabling Cross-Tenant Shop Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#shop` is read directly from the `x-shopify-shop-domain` HTTP header, but `HmacValidator.validate` only verifies the HMAC over the raw request body (`to_signable_string`), never over the `shop` header. An attacker who can deliver (or replay) any body that carries a valid HMAC for the configured `client_secret` can freely set the `shop-domain` header to any shop, and `Registry.process` will pass that attacker-controlled shop value straight to the host application's webhook handler as an authenticated tenant identifier.

### Finding Description
The equality this gem is supposed to enforce is: `shop value trusted by the handler == shop value that was part of the HMAC-signed data`. In practice:
- `HmacValidator.validate_signature` computes the signature only from `verifiable_query.to_signable_string`, i.e., `@raw_body` [5](#0-4) [2](#0-1) .
- `Request#shop` is populated purely from the header value, completely outside the signed content: [3](#0-2) .
- `Registry.process` verifies only the HMAC of the body, then immediately forwards `request.shop` into `WebhookMetadata`, which the host app's handler is meant to trust as "the shop this webhook is about": [1](#0-0) .

Because the header is not part of what's cryptographically bound, the same signed body (e.g., from a webhook the attacker's own shop legitimately receives, or any payload whose HMAC an attacker can obtain) can be replayed with the `shop-domain` header rewritten to point at a different, victim shop domain. Any host application that uses `WebhookMetadata#shop` to look up which merchant's session/access token to act on (the common integration pattern documented in `docs/usage/webhooks.md`) will be tricked into associating the attacker-controlled shop identity with a webhook payload it did not actually originate for that shop.

### Impact Explanation
This breaks the tenant boundary the gem is expected to guarantee for webhook processing: `shop` is used by host applications as the multi-tenant key to select the appropriate stored session/access token, but it is not authenticated by the HMAC the gem itself checks. This can enable cross-tenant data confusion in the host application's webhook handling — a High-severity outcome per the specified impact classes (cross-tenant access via a scope/identity check that answers permissively).

### Likelihood Explanation
Exploitability depends on the attacker being able to produce, capture, or replay any request body/HMAC pair valid for the target app's `client_secret` (e.g., a webhook payload the attacker's own shop legitimately triggers) and then re-deliver it to the app's webhook endpoint with a modified `shop-domain` header, since the gem performs no host/origin binding for that header nor any comparison against a registered/expected shop before invoking the handler.

### Recommendation
`Request`/`Registry.process` should not treat the `x-shopify-shop-domain` header as trustworthy on its own. At minimum, the gem should document/enforce that host applications cannot rely on `WebhookMetadata#shop` as an authenticated value unless it's cross-checked against other bound data (e.g., verifying the webhook's `topic`+`shop` pairing via a follow-up API call, or requiring TLS-terminated per-shop endpoints). Ideally, Shopify's webhook signing should be extended to cover critical headers like `shop-domain`, and this gem should reject requests where the signed body's implied resource cannot be cryptographically tied to the claimed shop.

### Proof of Concept
1. Obtain any raw body + valid `x-shopify-hmac-sha256` pair computed with the app's `client_secret` (e.g., from a legitimately delivered webhook for shop `attacker.myshopify.com`).
2. Re-issue an HTTP request to the app's webhook endpoint using the same raw body and HMAC header, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `Registry.process` at [1](#0-0)  calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unmodified) body.
4. The handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the host application to process/act upon data under the wrong shop's identity.
