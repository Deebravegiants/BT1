Found a clear analog: `TokenExchange.exchange_token` sends the app's `client_secret` to a host derived from the JWT `dest` claim without validating that host against the trusted Shopify domain list, unlike every sibling method in the same module.

### Title
`client_secret` sent to unvalidated host derived from JWT `dest` claim in `TokenExchange.exchange_token` - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` takes the `shop` used to build the HTTP request host directly from the session token's `dest` claim via `jwt_payload.shop`, and never passes it through `Utils::ShopValidator.sanitize!`, unlike `client_credentials`, `refresh_token`, and `migrate_to_expiring_token`, which all call `Utils::ShopValidator.sanitize!(shop)` before constructing the session used for the request host.

### Finding Description
`JwtPayload#shop` simply strips the scheme from the `dest` claim with no domain allow-listing: [1](#0-0) 

`exchange_token` uses this unvalidated value directly to build the session whose `shop` becomes the request host for the token-exchange call that carries `client_id`/`client_secret`: [2](#0-1) 

`Clients::HttpClient` builds the outbound base URI directly from `session.shop` with no further validation: [3](#0-2) 

Contrast this with the other three OAuth flows in the same file/module family, which all call `Utils::ShopValidator.sanitize!(shop)` — an allow-list check against `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) — before constructing the session used to build the request host: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

The identity binding that should hold is: `host that receives the client_secret == a Shopify-trusted domain (validated by ShopValidator)`. For every other credential-bearing flow in this gem that binding is enforced explicitly at the call site. For `exchange_token`, the binding is instead: `host that receives the client_secret == raw dest claim string, unvalidated`.

While the JWT itself is HMAC-verified against `Context.api_secret_key` (so an attacker cannot forge a session token from scratch), `JwtPayload#initialize` only checks `aud == Context.api_key` and does not check that `dest`/`iss` correspond to a trusted Shopify domain: [8](#0-7) 

This means `exchange_token`'s host-safety relies entirely on Shopify (the token issuer) never producing a `dest` claim outside the trusted domain set, with no defense-in-depth in this gem — a materially different (and weaker) posture than the sibling methods, which enforce the allow-list even though their `shop` argument is developer-supplied and presumably already trusted by the host app. If `dest` is ever influenced by app-controlled data (e.g., a custom/proxied `iss`/`dest` issuer configuration, a multi-tenant reverse-proxy setup, or any future/alternate token issuance path that reuses `JwtPayload`), the missing allow-list check on `TokenExchange.exchange_token`'s request host would let `client_secret` and `client_id` be POSTed to that unvalidated host.

### Impact Explanation
If the host derived from `dest` can be influenced to point off the `*.myshopify.com`/trusted domain set, the gem will POST the app's `client_id` and `client_secret` (and the raw session token) to that host — direct SSRF carrying the app's `client_secret`, and potential credential exfiltration to an attacker-controlled server. This matches the report's bug-class hint: a value (`dest`) is consumed to select the destination without being re-validated in the same way parallel code paths validate it, breaking the "host validated == host that receives `client_secret`" binding maintained everywhere else in the library.

### Likelihood Explanation
Low-to-moderate: exploitation requires a path by which the `dest` claim's value diverges from the trusted Shopify domain set while still passing HMAC verification with the app's own `api_secret_key` (e.g., because `iss`/`dest` are asserted by an unusual/relayed token issuer, or a future code path constructs `JwtPayload` from a token not exclusively minted by Shopify's own domain). Under the pure standard Shopify App Bridge flow, Shopify itself is trusted to only issue tokens with `dest` set to the real shop's domain, so the practical risk today is defense-in-depth being absent rather than a directly demonstrated remote trigger from an anonymous internet user.

### Recommendation
Apply `Utils::ShopValidator.sanitize!(dest_shop)` (or an equivalent allow-list check) to the `dest`-derived shop in `TokenExchange.exchange_token` before constructing `shop_session`, exactly as is already done in `client_credentials`, `refresh_token`, and `migrate_to_expiring_token`. Optionally, add the same check inside `JwtPayload` itself so all consumers benefit uniformly.

### Proof of Concept
1. Obtain (or, in a hypothetical relayed/alternate-issuer configuration, cause to be produced) a JWT correctly HMAC-signed with the app's `api_secret_key`, with `aud` equal to the app's `api_key` and `dest` set to `https://attacker-controlled-host.example`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: forged_or_relayed_token, requested_token_type: ...)`.
3. `jwt_payload.shop` returns `attacker-controlled-host.example` unchanged (no `ShopValidator` check).
4. `Clients::HttpClient` builds `@base_uri = "https://attacker-controlled-host.example"` and POSTs a body containing `client_id` and `client_secret` to `https://attacker-controlled-host.example/admin/oauth/access_token`, leaking the app's OAuth credentials to the attacker's host.
