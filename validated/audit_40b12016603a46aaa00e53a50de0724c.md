### Title
Webhook shop/topic/webhook-id headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop`, `topic`, and `webhook_id` are read directly from unauthenticated HTTP headers [2](#0-1) . `Utils::HmacValidator.validate` only verifies the HMAC over `to_signable_string` (the body) [3](#0-2) , so the header fields that identify *which shop* a webhook belongs to are never bound to the cryptographic signature. `Webhooks::Registry.process` passes these unauthenticated header values straight into `WebhookMetadata` and the app's handler [4](#0-3) , and `WebhookMetadata.shop`/`.topic`/`.webhook_id` are declared as trusted, verified fields of the abstraction returned by this gem [5](#0-4) .

This is the analog of the report's "bytes verified versus bytes parsed / field acted on but not covered by the HMAC" bug class: the gem verifies the *body* bytes but the app-facing identity field (`shop`) is parsed from bytes that were never verified.

### Finding Description
Compare this to the gem's own OAuth callback verifier, `Auth::Oauth::AuthQuery`, which correctly folds `shop` into the signable string that is HMAC-verified: `code`, `host`, `shop`, `state`, and `timestamp` are all included [6](#0-5) . The webhook path does not follow this pattern: `Webhooks::Request#to_signable_string` signs only `@raw_body`, excluding `shop`, `topic`, and `webhook_id`, even though these header-derived fields are handed to the app as authenticated metadata via `WebhookMetadata` [7](#0-6) .

The equality that should hold but doesn't:
`shop` (bound inside the HMAC-verified payload) == `shop` (the field the app actually acts on in `WebhookMetadata#shop`).

Because `shop` is sourced from `shopify-shop-domain`/`x-shopify-shop-domain` header text rather than from the signed body, an attacker who obtains any single valid `(raw_body, hmac)` pair for one shop — e.g. their own development store, which Shopify itself sends to them legitimately — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting a different `shop`, `webhook-id`, or `topic` header. `HmacValidator.validate` will still succeed, because it only recomputes the HMAC over the unchanged raw body [8](#0-7) , and `Registry.process` will invoke the merchant's handler with the attacker-chosen `shop` field marked as HMAC-validated [9](#0-8) .

### Impact Explanation
Apps built on this gem are expected to trust `WebhookMetadata#shop` as the authenticated tenant identifier once `HmacValidator.validate` returns true (that is the entire purpose of `Registry.process`'s HMAC check before dispatch [10](#0-9) ). Since `shop` is not actually bound by the signature, an attacker who possesses one legitimately-signed webhook body (e.g. from their own shop) can relabel it as belonging to a victim shop, causing the app to process, store, or act on attacker-controlled data under the victim's tenant context — a cross-tenant data confusion/injection primitive that is directly enabled by this gem's verification design.

### Likelihood Explanation
Any merchant/developer running the same app the attacker is a legitimate user of can obtain one valid `(body, hmac)` pair for their own store trivially (Shopify sends it to their own endpoint or test harness), then replay it with a modified `shop-domain` header against the app's public webhook receiver. No access to `api_secret_key` is required — only re-use of a previously observed valid HMAC/body pair, which is not attacker-secret-dependent. This does not depend on the host application ignoring documented behavior; the vulnerability is that `WebhookMetadata.shop`, a field this gem itself documents and constructs as validated output of `Registry.process`, is not actually covered by the HMAC check the gem performs.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signable representation for webhooks, mirroring `AuthQuery#to_signable_string`, or otherwise cryptographically bind these header values before constructing `WebhookMetadata`. At minimum, document that `shop`/`topic`/`webhook_id` are unauthenticated and must not be trusted for tenant-identification purposes, or restructure `HmacValidator.validate`/`to_signable_string` so the signature covers the full set of fields exposed via `WebhookMetadata`.

### Proof of Concept
1. Attacker's own dev shop `attacker.myshopify.com` receives a legitimate webhook: raw body `B`, headers include `x-shopify-hmac-sha256: H` (valid HMAC of `B`), `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
2. Attacker sends a new HTTP request to the victim app's webhook endpoint with the same raw body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Webhooks::Request.new` accepts the request (all required headers present) [11](#0-10) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`= B`) only, and it matches `H` [12](#0-11) , [3](#0-2) .
5. The app's handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` [13](#0-12) , despite the payload never having been generated or signed for `victim.myshopify.com`.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
