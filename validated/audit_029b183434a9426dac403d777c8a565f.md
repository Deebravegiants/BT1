### Title
DestinationAddressMatchesTokenAddressError bypass via un-normalized address comparison — funds sent to token contract address are unrecoverable - (File: packages/intents-sdk/src/lib/compareAddresses.ts)

### Summary
`compareAddresses` is the equality guard used across every bridge's `validateWithdrawal` to block a withdrawal whose `destinationAddress` resolves to the token's own contract address [1](#0-0) . For most chains it degrades to a raw `a === b` string compare [2](#0-1) , while `validateAddress` (the format check gating the same call) accepts multiple textual encodings of the identical underlying account for at least Bitcoin Cash (CashAddr with/without the `bitcoincash:` prefix, mixed case) [3](#0-2) . This is structurally the same bug class as the goldmark advisory: a security check (equality/dangerous-URL check) is performed on the raw/un-normalized form while a sibling check (format validation/entity decoding) accepts a normalized-equivalent form, letting an attacker choose the encoding that satisfies validation but slips past the equality guard.

### Finding Description
Every bridge's `validateWithdrawal` performs the same two-step check:
1. `validateAddress(destinationAddress, chain)` — format validity only, and for BCH this explicitly normalizes case and injects the missing prefix before validating [4](#0-3) [5](#0-4) .
2. `compareAddresses(tokenAddress, destinationAddress, chain)` — must return `true` to reject a self-transfer to the token's contract. For Bitcoin Cash (grouped with Near/Bitcoin/Zcash/Dogecoin/Litecoin/Solana/XRPL/Cardano/Aleo/Dash) it is plain `a === b` [2](#0-1) , with no CashAddr decoding/normalization equivalent to what `validateAddress`/`validateBchCashAddr` performs.

Because CashAddr addresses are valid with or without the `bitcoincash:` prefix and are case-insensitive (the encoding function itself lowercases and prepends the prefix before verifying the checksum) [3](#0-2) , two different strings can denote the exact same BCH account. `validateAddress` will accept both forms as valid; `compareAddresses` will only recognize them as equal if the byte strings are identical.

This is used in every bridge implementation to prevent withdrawing to the token's own address: `direct-bridge.ts` [6](#0-5) , `hot-bridge.ts` [7](#0-6) , `omni-bridge.ts` [8](#0-7) , and `poa-bridge.ts` [9](#0-8) . In `poa-bridge.ts`, the canonical token address (`tokenInfo.origin_chain_address`) comes from an external API response and its exact textual form (prefixed/lowercased or not) is not guaranteed to match whatever equivalent form a caller supplies as `destinationAddress`.

### Impact Explanation
If the reference token address and the attacker-supplied destination address are equivalent-but-textually-different CashAddr encodings (e.g., one has the `bitcoincash:` prefix and/or mixed case, the other doesn't), `validateAddress` accepts the destination as well-formed, but `compareAddresses` returns `false`, so `DestinationAddressMatchesTokenAddressError` is never thrown. The withdrawal then proceeds and funds are sent on-chain to the token contract's own BCH address. This falls squarely under "funds delivered to a wrong address/chain/contract with no recovery" — tokens sent to a bridge/token contract address on the destination chain are generally not recoverable through the normal withdrawal flow.

### Likelihood Explanation
Exploitability depends on whether an integrator/attacker can supply an arbitrary-cased or unprefixed CashAddr as `destinationAddress` while the compared token/origin address is stored in a different canonical form (verified for the PoA bridge's `origin_chain_address`, sourced from an external, not-necessarily-normalized API response). I could not fully verify from static reading whether the actual `origin_chain_address` values returned by the PoA API are always already normalized to the exact same encoding `compareAddresses` would need to match; that runtime data dependency limits certainty on real-world reachability, but the code path itself contains no normalization step to prevent it, so the equality guarantee is not structurally enforced.

### Recommendation
Make `compareAddresses` decode/normalize Bitcoin Cash (and any other chain whose valid encodings are not byte-identical, e.g., re-check Bitcoin bech32/Zcash TEX/XRPL classic-vs-X-address for the same class of issue) the same way `validateBchCashAddr` does — decode both addresses to their canonical 21-byte payload (version + hash160) and compare the decoded bytes, mirroring the pattern already used for TON and Tron in the same file [10](#0-9) .

### Proof of Concept
1. Suppose the PoA/omni bridge reports the BCH token's `origin_chain_address` as `bitcoincash:qpm2qsznhks23z7629mms6s4cwef74vcwvn0h829pq` (lowercase, prefixed).
2. Caller requests withdrawal with `destinationAddress = "QPM2QSZNHKS23Z7629MMS6S4CWEF74VCWVN0H829PQ"` (uppercase, unprefixed) — the same underlying CashAddr account.
3. `validateAddress(destinationAddress, Chains.BitcoinCash)` → `validateBchCashAddr` lowercases and adds the `bitcoincash:` prefix before checksum validation, so it returns `true` [5](#0-4) .
4. `compareAddresses(originAddress, destinationAddress, Chains.BitcoinCash)` hits the `a === b` branch and returns `false` because the strings differ in case/prefix [2](#0-1) .
5. `DestinationAddressMatchesTokenAddressError` is not thrown; the withdrawal proceeds to send funds to the token's own BCH address.

// Tron addresses are represented either as base58check (T...) or as hex
// (41...); both encode the same 21-byte version+hash160 payload.
function compareTronAddress(a: string, b: string): boolean {
	const payloadA = decodeTronAddress(a);
	const payloadB = decodeTronAddress(b);
	if (payloadA === null || payloadB === null) return false;

	return bytesEqual(payloadA, payloadB);
}

function decodeTronAddress(address: string): Uint8Array | null {
	const base58Payload = decodeTronBase58Address(address);
	if (base58Payload !== null) return base58Payload;

	return decodeTronHexAddress(address);
}

function decodeTronBase58Address(address: string): Uint8Array | null {
	try {
		const decoded = base58.decode(address);
		if (decoded.length !== 25) return null;

		// version (1) + hash160 (20) + checksum (4)
		const payload = decoded.subarray(0, 21);
		const checksum = decoded.subarray(21, 25);
		const expectedChecksum = sha256(sha256(payload)).subarray(0, 4);
		for (let i = 0; i < 4; i++) {
			if (checksum[i] !== expectedChecksum[i]) return null;
		}

		return payload[0] === 0x41 ? payload : null;
	} catch {
		return null;
	}
}

function decodeTronHexAddress(address: string): Uint8Array | null {
	try {
		const decoded = hex.decode(address);
		if (decoded.length !== 21) return null;
		return decoded[0] === 0x41 ? decoded : null;
	} catch {
		return null;
	}
}

		return true;

function validateBchCashAddr(address: string): boolean {
	// Normalize the address
	let normalized = address.toLowerCase();

	// Add prefix if missing
	if (!normalized.includes(":")) {
		normalized = `bitcoincash:${normalized}`;
	}

	// Must start with bitcoincash:
	if (!normalized.startsWith("bitcoincash:")) {
		return false;
	}

	const payload = normalized.slice("bitcoincash:".length);

	// Must start with q (P2PKH) or p (P2SH)
	if (!payload.startsWith("q") && !payload.startsWith("p")) {
		return false;
	}
