### Title
Division-by-zero in `InvariantToken::exchange_coin_to_pc`/`exchange_pc_to_coin` can panic-revert `process_deposit` when a pool's non-PNL reserve on one side has been fully swept into `need_take_pnl_*` - ([File: program/src/math.rs])

### Summary
`process_deposit` computes the counter-side deposit amount via `InvariantToken::exchange_coin_to_pc` / `exchange_pc_to_coin`, which divide by `total_coin_without_take_pnl` or `total_pc_without_take_pnl` respectively. These totals are derived by subtracting `need_take_pnl_coin`/`need_take_pnl_pc` from the raw vault balances. If `calc_take_pnl` (invoked from `process_deposit`, `process_withdraw`, and `process_withdrawpnl`) accrues enough PNL that one side's `total_*_without_take_pnl` reaches exactly zero while `amm.lp_amount` remains non-zero, any subsequent `Deposit` instruction on that base side will hit an unchecked `checked_div(0).unwrap()` and panic-abort the transaction, unlike the analogous `RiskEngine` bug in the report which similarly reverts on a reachable, non-privileged-triggered arithmetic edge case.

### Finding Description
`InvariantToken::exchange_coin_to_pc` divides by `self.token_coin` and `exchange_pc_to_coin` divides by `self.token_pc`: [1](#0-0) 

In `process_deposit`, `total_coin_without_take_pnl` / `total_pc_without_take_pnl` are computed by `calc_total_without_take_pnl_no_orderbook`, then further reduced by `calc_take_pnl`, and fed directly into `InvariantToken` as `token_coin`/`token_pc` without a nonzero check before the division-bearing exchange call: [2](#0-1) [3](#0-2) 

`calc_take_pnl` unconditionally subtracts the computed PNL amounts from the running totals with `checked_sub(...).unwrap()`, with no floor/guard preventing the result from reaching exactly zero: [4](#0-3) 

This mirrors the reported bug class: an unchecked division whose denominator can be driven to zero through normal, permissionless protocol state transitions (repeated swaps generating fee-based PNL accrual over time, since `calc_take_pnl` runs on every deposit/withdraw/withdrawpnl call), causing a legitimate, reachable user action (`Deposit`) to hard-panic instead of failing gracefully.

### Impact Explanation
If `total_coin_without_take_pnl` (or `total_pc_without_take_pnl`) reaches zero while `amm.lp_amount > 0` — i.e., nearly the pool's entire raw vault balance on one side has accrued into `need_take_pnl_*` and is pending owner withdrawal via `WithdrawPnl` — any unprivileged user's `Deposit` instruction on the corresponding `base_side` will panic instead of returning a controlled error. This blocks new liquidity deposits into the pool at that state (a denial-of-service on a core user-facing instruction), and depending on runtime panic-handling behavior can also mask the real error surface for integrators/bots that rely on program-error codes rather than raw panics for handling. Unlike `process_withdraw`, which uses `InvariantPool` (dividing by `lp_amount`, not by the reserve amount) and is therefore not exposed to this exact zero-denominator path, `process_deposit`'s use of `InvariantToken` is directly exposed.

### Likelihood Explanation
Reaching `total_*_without_take_pnl == 0` requires the PNL numerator/fee accrual (`pnl_numerator`/`pnl_denominator`, `swap_fee_numerator`/`_denominator`) to consume the entire non-PNL portion of one reserve, which under standard default fee configuration (e.g., `pnl_numerator/denominator = 12/100`) accumulates gradually across many swaps and is bounded far above zero relative to total pool value in typical configurations. This makes the precise "exactly zero" edge case low likelihood under default parameters, though it is not structurally prevented by any explicit check, and pools with unusual/extreme lifetime trading volume-to-liquidity ratios, or long-lived low-liquidity pools, could approach this boundary. This is a lower-confidence, edge-case analog compared to the original report's cleanly reachable single-transaction trigger.

### Recommendation
Add an explicit guard in `process_deposit` (and any other caller constructing `InvariantToken`) rejecting deposits (with a clear `AmmError`, not a panic) when `total_coin_without_take_pnl == 0` or `total_pc_without_take_pnl == 0`. Additionally, harden `InvariantToken::exchange_coin_to_pc`/`exchange_pc_to_coin` to use `checked_div` returning `None` (as the `Option<u64>` return type already supports) instead of `.unwrap()`, so a zero denominator surfaces as `AmmError::CalculationExRateFailure` via the existing `.ok_or(...)` call sites rather than an unhandled panic.

### Proof of Concept
Not independently verified with a runnable test; this is derived analytically from the code paths cited above. A concrete PoC would require: (1) creating a pool, (2) driving `need_take_pnl_coin` (or `need_take_pnl_pc`) via repeated swaps/`calc_take_pnl` accrual until `total_coin_without_take_pnl` (or `total_pc_without_take_pnl`) equals exactly the vault balance leaving zero remainder, then (3) calling `Deposit` with `base_side` matching the zeroed reserve, and observing a Rust panic (`attempt to divide by zero`) instead of a program error, mirroring the `stdError.divisionError` assertion pattern used in the original report's PoC.
