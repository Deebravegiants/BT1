### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity used by webhook handlers directly from the unauthenticated `shopify-shop-domain` HTTP header, while the HMAC signature verified by `Utils::HmacValidator` only covers the raw request body. This breaks the identity binding `shop_used_by_handler == shop_covered_by_hmac`, letting anyone who has captured one legitimately signed webhook body/HMAC pair from the target app (e.g. by installing the app on their own store) replay it against the app's webhook endpoint while spoofing the `shop-domain` header to point at a different, victim tenant.

### Finding Description
`Request#to_signable_string` returns only the raw request body: [1](#0-0) 

`Request#shop` is read straight from a header, with no relation to the signed content and no sanitation through `Utils::ShopValidator`: [2](#0-1) 

`Utils::HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` (the body only) and compares it to the received `hmac`: [3](#0-2) 

`Registry.process` validates only that body-HMAC, then immediately trusts `request.shop` to build the metadata passed into the app's handler: [4](#0-3) 

Because `shop` is never part of the signed material, the equality the library implicitly relies on — "the shop this webhook is attributed to" equals "the shop whose secret produced this HMAC" — does not hold. Any request whose body+HMAC pair is valid for the app (regardless of which shop it was originally sent for) will be accepted, and the `shop` value attached to it can be set to anything by the caller.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who has one valid `(raw_body, hmac)` pair signed by the target app's `api_secret_key` — obtainable by installing the (often public) app on a store they control and triggering any webhook event — can resend that exact body and HMAC to the app's public webhook endpoint while setting `x-shopify-shop-domain` (or `shopify-shop-domain`) to a different, victim shop that also uses the app. `Registry.process` will pass this forged `shop` straight to the app's webhook handler as authentic, since the gem performs no additional binding check. Downstream handlers that key their storage/business logic off `WebhookMetadata#shop` (the standard usage pattern) will apply attacker-controlled webhook data to the victim tenant's records — i.e., cross-tenant data injection/corruption without ever needing the victim's or the app's credentials.

### Likelihood Explanation
Likelihood is high: the only prerequisite is a single legitimately-signed webhook from the target app, which is trivial to obtain by installing a public app on any free/trial store and triggering an event. No access token, `client_secret`, or privileged account for the victim is required, and the manipulation (swapping one HTTP header before replay) requires no cryptography.

### Recommendation
Bind the `shop` identity into the value that is cryptographically verified, e.g. by having `Webhooks::Request#to_signable_string` incorporate the `shop-domain` header (matching how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` into its signed string), or by requiring/validating that the delivered `shop` corresponds to a shop with an existing, previously-established session/registration before invoking the handler, rather than trusting the header value on its own.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled development store `attacker.myshopify.com` and trigger any subscribed webhook event to capture a valid raw body `B` and its `x-shopify-hmac-sha256` value `H` (both signed with the app's real `api_secret_key`).
2. Send a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid because it only signs `B`), and header `x-shopify-shop-domain: victim.myshopify.com` (or any other real shop using the app).
3. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`.
4. `Registry.process` invokes the registered handler with `WebhookMetadata(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data under the victim shop's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
