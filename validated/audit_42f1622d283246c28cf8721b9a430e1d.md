## Analog Found: Delegator rewards can become permanently stuck in a vote account with zero active stake

### Title
Unprivileged `DepositDelegatorRewards` deposit becomes permanently stuck when a vote account has zero active stake - (File: `programs/vote/src/vote_state/mod.rs`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
The `DepositDelegatorRewards` vote instruction (SIMD-0123) lets **any signer** transfer lamports into a vote account and unconditionally increments `pending_delegator_rewards`, with no check on whether the vote account currently has any delegated stake. When the epoch-boundary block-reward calculation later tries to split `pending_delegator_rewards` among delegators, it does so proportionally to `stake / total_active_stake`; if `total_active_stake == 0` for that vote account, the function short-circuits and returns `0` for every stake account. The lamports that were transferred into the vote account remain there, contributing to `pending_delegator_rewards`, but are never distributable and are further protected from withdrawal by the withdraw-floor check — mirroring exactly the EsEMBR pattern where `receive()` accepts ETH that contributes to `totalEthPerEsembr` but, when `totalSupply == 0`, is never actually creditable to anyone and becomes stuck.

### Finding Description
`deposit_delegator_rewards` performs a real system-program transfer of lamports into the vote account and then unconditionally records the amount: [1](#0-0) 

Nothing in this path validates that the vote account has any active/delegated stake before accepting the deposit — any signer with a system account can call it via `VoteInstruction::DepositDelegatorRewards`: [2](#0-1) 

At the epoch reward boundary, `calculate_block_reward` computes each stake account's share of that vote account's `pending_delegator_rewards`, keyed off `total_active_stake` looked up from `reward_epoch_delegated_stakes`: [3](#0-2) 

If `total_active_stake == 0` (vote account with no active delegations — the direct analog of `totalSupply == 0` in EsEMBR), the function unconditionally returns `0`, meaning no stake account will ever be credited any portion of the deposited lamports for that period.

Compounding this, `pending_delegator_rewards` is also used as a floor that blocks withdrawal of the vote account down to zero: [4](#0-3) 

So the deposited lamports (a) can never be paid out to a delegator, because the reward calculation always yields zero when there is no active stake, and (b) cannot be withdrawn out from under `pending_delegator_rewards` by the authorized withdrawer either, since `withdraw` treats `pending_delegator_rewards` as an untouchable reserve. The lamports are functionally stranded in the vote account.

### Impact Explanation
Any unprivileged user can lock lamports into an arbitrary vote account (their own or someone else's, since the instruction only requires the sender to sign, not the vote account owner) by calling `DepositDelegatorRewards` while that vote account has no active delegated stake (e.g., a freshly created vote account, or one whose stakers have fully deactivated/withdrawn). This causes real economic value loss with no recovery path: the deposited lamports are neither burnable/reclaimable by the sender, nor distributable to any delegator, nor withdrawable by the vote account's authorized withdrawer. This is a concrete, permanent loss of value analogous to the EsEMBR `receive()` bug, occurring in the bank's epoch-reward/vote-program commit path.

### Likelihood Explanation
The precondition (a vote account with `total_active_stake == 0` at the time of deposit and reward calculation) is a normal, easily reachable state — newly created vote accounts before any delegation, or vote accounts whose stakers have fully undelegated. No special validator/operator privilege is required to trigger the deposit; it is a standard permissionless instruction callable by any keypair holding lamports.

### Recommendation
- Reject `DepositDelegatorRewards` (or make it a no-op / return funds) when the target vote account currently has zero active delegated stake, similar to the report's recommendation that `receive()` should revert when `totalSupply == 0`.
- Alternatively, track deposits made while `total_active_stake == 0` separately so they can be reclaimed by the depositor or correctly credited once stake becomes active, instead of silently stranding them behind the `pending_delegator_rewards` withdrawal floor.

### Proof of Concept
1. Create (or select) a vote account that currently has no active stake delegations (`total_active_stake == 0` for that vote pubkey in `reward_epoch_delegated_stakes`).
2. As any funded account, submit a `DepositDelegatorRewards` instruction transferring lamports to that vote account, per the flow in `deposit_delegator_rewards`. [5](#0-4) 
3. At the next epoch boundary, `calculate_block_reward` is invoked for every stake delegation to this vote account (if any exist) or none at all; because `total_active_stake == 0`, the function returns `0`, so the deposited amount is never allocated to any staker. [6](#0-5) 
4. The authorized withdrawer later attempts to withdraw the vote account balance; `withdraw` enforces `remaining_balance >= min_rent_exempt + pending_delegator_rewards`, permanently reserving the deposited amount without any way to release it. [7](#0-6) 

Note: I was unable to fully trace, within the available search budget, whether `pending_delegator_rewards` is decremented elsewhere in the codebase once a stake-account's `total_active_stake` becomes non-zero later (i.e., whether the stuck condition is permanent or merely delayed until stake is (re)delegated to that vote account). This should be verified in the actual repository before finalizing severity, since if stake is later delegated the reserved funds may eventually become distributable.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
