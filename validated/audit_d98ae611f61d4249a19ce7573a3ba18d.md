This confirms the finding. The `ShopifyAPI::Webhooks::Request` class computes its HMAC only over the raw request body (`to_signable_string` returns `@raw_body`) while the `shop` attribute (used to attribute the webhook to a tenant) is read directly from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the signed bytes. Since Shopify apps typically share a single `api_secret_key` across all installed shops, this creates a cross-tenant identity-binding break analogous to the "field acted on but not covered by the HMAC" pattern from the report.

### Title
Webhook cross-tenant spoofing via unauthenticated `shop-domain` header not covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value that is handed to app webhook handlers from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. Because the app's `api_secret_key` is shared across every shop that installs the app, any holder of one genuine, previously-delivered `(body, hmac)` pair can replay that exact body to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, and the gem will report the request as validly signed and attribute it to the attacker-chosen shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop` is read straight from the unauthenticated header with no cross-check against the signed bytes: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then constructs `WebhookMetadata` (the object passed to the app's own `handle` method) using this unauthenticated `shop` value directly: [3](#0-2) 

`HmacValidator.validate` computes the HMAC solely from `verifiable_query.to_signable_string` (the body) against `Context.api_secret_key`: [4](#0-3) 

The identity binding that should hold is:
`hmac_valid(body, secret) == true` should imply `shop_header == shop_that_produced(body, secret)`.

In this gem, that equality does not hold: `hmac_valid(body, secret)` is true for *any* request carrying a body/HMAC pair genuinely produced by Shopify for the shared app secret, regardless of the `shop-domain` header value supplied alongside it. Because the identical `api_secret_key` is used for every shop installed on a multi-tenant app (per `ShopifyAPI::Context.setup`, which stores one process-wide `api_secret_key`), a webhook body legitimately generated for Shop A remains validly signed when replayed with Shop B's domain in the header. The documented usage pattern shows apps trusting `data.shop` directly to route/attribute webhook processing: [5](#0-4) 

### Impact Explanation
This breaks the tenant/shop identity binding for the app's own trusted metadata, matching the "Cross-tenant access" Critical impact category: an entity that can obtain (or is itself a party to) one legitimately signed webhook body for their own shop can cause the app to process that payload as if it originated from a different merchant's shop, because the gem hands the handler an unauthenticated `shop` value alongside a body whose signature check says nothing about which shop it belongs to. Any app that uses `data.shop` from `WebhookMetadata` (as the gem's own documentation instructs) to select the tenant/session/database record to update is directly exposed to cross-tenant data corruption or disclosure through this gem's own code path (`Webhooks::Request` → `HmacValidator.validate` → `Registry.process` → `WebhookHandler#handle`).

### Likelihood Explanation
Exploitation requires only the ability to send an HTTP POST with attacker-controlled headers to the app's webhook endpoint plus one genuine `(raw_body, hmac)` pair — attainable by any merchant with an app installed (an "unprivileged" actor relative to other tenants) simply by capturing their own legitimate webhook deliveries, which is normal operation. No access to `api_secret_key`, access tokens, or the app's infrastructure is needed. The gem does not offer any way to bind the `shop` field into the signature check, so every consumer of this library inherits the gap.

### Recommendation
Include the `shop-domain` header (and ideally `topic`/`webhook-id`) in the bytes protected by the HMAC check, or otherwise cryptographically bind `request.shop` to the verified payload before constructing `WebhookMetadata`, e.g. by having `HmacValidator`/`Request#to_signable_string` incorporate the shop header, or by requiring callers to supply the expected shop and rejecting mismatches inside `Registry.process`.

### Proof of Concept
1. App has one shared `api_secret_key` and is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com`.
2. Attacker (an authorized user for `shop-a`, or anyone who intercepts a legitimate delivery) records a genuine webhook delivery: `raw_body = '{"id":1,...}'` with header `X-Shopify-Hmac-SHA256: <valid-for-body>` and `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
3. Attacker POSTs the identical `raw_body` and `X-Shopify-Hmac-SHA256` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request whose `to_signable_string` is unchanged (`raw_body`), so:
   ```ruby
   ShopifyAPI::Utils::HmacValidator.validate(request) # => true
   ```
   even though `request.shop == "shop-b.myshopify.com"`.
5. `ShopifyAPI::Webhooks::Registry.process(request)` passes validation and invokes the app's handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: <shop-a's data>, ...)`, corrupting/leaking Shop A's data into Shop B's context.
