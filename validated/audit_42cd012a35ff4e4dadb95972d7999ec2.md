Audit Report

## Title
CORS wildcard-origin allowlist bypass via unanchored suffix match - (File: core/services/gateway/network/httpserver.go)

## Summary
The gateway's public HTTP server validates CORS origins against an operator-configured allowlist supporting wildcard entries like `*.example.com`. The wildcard branch in `isAllowedOrigin` strips the `*.` prefix and checks `strings.HasSuffix(originHost, allowedHost)` without verifying a domain-label boundary (`.`) precedes the matched suffix, so an attacker-controlled host like `evilethereum.org` incorrectly satisfies an allowlist entry `*.ethereum.org`.

## Finding Description
`isAllowedOrigin` in `core/services/gateway/network/httpserver.go` (lines 157-193) performs, for wildcard entries: `allowedHost = allowedHost[2:]` followed by `strings.HasSuffix(originHost, allowedHost)` [1](#0-0) . This is a raw string suffix comparison rather than a label-aware comparison — it does not require the character immediately preceding the matched suffix in `originHost` to be a `.`. Consequently, `evilethereum.org` (which is not a subdomain of `ethereum.org`, has no separating dot) also satisfies `strings.HasSuffix("evilethereum.org", "ethereum.org")`. This function is called directly and unconditionally from `handleRequest` for every request when `CORSEnabled` is true, before any other authentication/authorization occurs [2](#0-1) , and the origin is reflected verbatim into the `Access-Control-Allow-Origin` response header. No other check in the code path (scheme match, port match, exact host match) mitigates the wildcard suffix flaw, since exact/scheme/port checks pass trivially when the attacker fully controls their own domain and uses the correct scheme/port to match the allowlist entry.

## Impact Explanation
When an operator enables CORS with a wildcard allowlist entry, an attacker registering a lookalike domain (e.g., `evilethereum.org` for `*.ethereum.org`) can have a page on that domain issue authenticated cross-origin browser requests to the gateway and receive `Access-Control-Allow-Origin` reflecting their origin. This defeats the intended Same-Origin Policy protection of the allowlist, allowing a malicious webpage to read the gateway's JSON-RPC responses that the browser would otherwise withhold from a foreign origin — an in-scope allowlist-bypass / cross-user response exposure impact for the gateway's request handling.

## Likelihood Explanation
Exploitation only requires (1) an operator using a documented, tested wildcard CORS entry (this is a normal supported configuration, not a misuse of the feature) and (2) the attacker registering a cheap lookalike domain sharing the suffix string. No credentials, privileged roles, or victim-side social engineering beyond visiting an attacker page are needed, and the bypass is deterministic and trivially reproducible.

## Recommendation
Anchor the wildcard suffix match to a domain-label boundary, e.g., compare against `"."+allowedHost` (keeping the leading dot) or verify `originHost == baseDomain || strings.HasSuffix(originHost, "."+baseDomain)` so `evilethereum.org` no longer satisfies `*.ethereum.org`.

## Proof of Concept
1. Start the gateway HTTP server with `CORSEnabled: true`, `CORSAllowedOrigins: []string{"https://*.ethereum.org"}` (mirrors `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go`) [3](#0-2) .
2. Send a request with header `Origin: https://evilethereum.org`.
3. Observe the response includes `Access-Control-Allow-Origin: https://evilethereum.org`, confirming the bypass, whereas the existing negative test suite (`TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards`) never exercises this unanchored-suffix lookalike case [4](#0-3) .
