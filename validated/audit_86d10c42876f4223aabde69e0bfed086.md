### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` authenticates the body content but never authenticates the `shop-domain` header. `Webhooks::Registry.process` nonetheless trusts `request.shop` (read straight from that unauthenticated header) and hands it to the app's handler as the tenant identifier. Any party able to obtain one valid `(body, hmac)` pair signed with the app's shared secret can replay it with a forged `shop-domain` header and have it accepted as a webhook from an arbitrary shop.

### Finding Description
`Request#hmac`/`#to_signable_string` bind the HMAC only to `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers that are excluded from `to_signable_string` entirely: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e. the body, using the single shared `Context.api_secret_key`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards the unauthenticated `request.shop` to the app-supplied handler as the authoritative tenant identifier: [4](#0-3) 

This breaks the intended binding `shop_verified_by_HMAC == shop_delivered_to_handler`. Before the request: Shopify signs `(body, shop=A)` with the app's client secret and delivers it to the app's single shared webhook endpoint. After an attacker's replay: the same `(body, hmac)` pair is resubmitted with `shop-domain: victim-shop.myshopify.com`. `HmacValidator.validate` still returns `true` (it only checks the body against the secret), so `Registry.process` calls the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's own event body>, ...)`. The gem provides no mechanism to bind the `shop` header to the signature, leaving that responsibility entirely — and silently — to the host application.

Because the app's `client_secret`/webhook secret is shared across every shop that installs the app (not shop-specific), any shop owner who legitimately installs the app can, using their own access token, register/observe webhook deliveries for their own shop, capture a valid `(body, hmac)` pair, and replay it against the app's webhook endpoint with a different `shop-domain` header to impersonate another tenant.

### Impact Explanation
This enables cross-tenant data injection/impersonation: a malicious installer of the app can cause the app to process attacker-controlled webhook payloads attributed to a victim shop it does not control, corrupting or forging that victim's per-tenant state (orders, inventory, GDPR events, etc., depending on what the host app's handler does with `data.shop`). This matches the "Critical — cross-tenant access" impact category, since it crosses the tenant identity boundary via a field (the shop header) that is acted upon but not covered by the cryptographic verification.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on a shop the attacker controls (a normal, low-privilege action for any internet user for apps with open/free installation), and (2) the ability to replay an HTTP POST with modified headers to the app's known webhook endpoint. No leaked credentials, `api_secret_key`, or access tokens belonging to the victim are needed — only the attacker's own legitimately-issued webhook traffic. This makes the likelihood realistic for any app that keys tenant identity off `request.shop` without independent verification.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signable material, or otherwise cryptographically bind the shop to the specific installation (e.g., verify `request.shop` against a per-shop secret/session record before invoking the handler) rather than trusting the `x-shopify-shop-domain` header purely because the body-only HMAC passed. At minimum, document prominently that `Registry.process`'s HMAC check does not authenticate the `shop` header and that host applications must independently verify the shop is a known/expected installation before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and, via the shop's own webhook subscription (using their legitimate admin access token), captures a real webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(app_client_secret, B)`.
2. Attacker sends a POST to the app's webhook endpoint with the same body `B`, the same `X-Shopify-Hmac-Sha256: H`, but header `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` recomputes the HMAC over `B` only and it matches `H`, so validation succeeds: [5](#0-4) 
4. The registered handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <parsed B>, ...)`, causing the host application to process attacker-controlled data as if it originated from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
