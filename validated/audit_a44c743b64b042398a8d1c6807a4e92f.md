### Title
Webhook `shop-domain` and `topic` are read from unauthenticated HTTP headers, not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` and `topic` attributes used by the app's webhook handler entirely from HTTP headers (`shopify-shop-domain`, `shopify-topic`) that are never included in the HMAC-signed payload. `Utils::HmacValidator.validate` only proves that the request *body* was signed with the app's `api_secret_key`; it says nothing about which shop the event belongs to. This breaks the identity binding `shop authenticated == shop attributed to the event`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` and `topic` are pulled straight from headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates the HMAC of the request and then dispatches the handler using the unauthenticated `request.shop` and `request.topic`: [3](#0-2) 

The HMAC secret (`api_secret_key`) is a single, app-wide secret shared across every installing shop — it is not per-tenant: [4](#0-3) 

Because the signature covers only the raw body, any two webhook deliveries that happen to carry an identical body (e.g. attacker triggers a webhook on their own shop, e.g. `app/uninstalled`, or any topic whose body content the attacker fully controls/can predict) will produce the same valid HMAC regardless of which shop or topic header accompanies it. An unprivileged internet user who installs the app on their own store (a normal, unprivileged action available to any developer) can:
1. Trigger a real webhook delivery to their own callback endpoint and capture a valid `(raw_body, hmac)` pair.
2. Replay that exact `raw_body` + `hmac` header to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with a victim's shop domain (and/or the `shopify-topic` header with a different registered topic).
3. `Utils::HmacValidator.validate` succeeds because it only checks the body against the secret; `Registry.process` then invokes the merchant's handler with `WebhookMetadata.new(shop: <victim shop>, topic: <attacker-chosen topic>, body: <attacker-controlled body>, ...)`.

Per the gem's own documented usage, host applications are expected to trust `data.shop` and `data.topic` directly to route/persist per-tenant work (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), as shown in the gem's own docs: [5](#0-4) 

This lets an attacker forge webhook events that appear to originate from — and are attributed to — a shop they do not control, since the gem itself provides no verification tying the `shop`/`topic` header values to the signed body.

### Impact Explanation
This is a cross-tenant identity-binding failure: the value the app trusts as "which shop this event is for" is never covered by the cryptographic proof that "Shopify signed this." An attacker can inject fabricated events attributed to a victim merchant's tenant (topic + body of the attacker's choosing, shop of the attacker's choosing), which can corrupt per-tenant data, trigger tenant-scoped side effects (inventory sync, order processing, notifications, billing-related webhooks like `app_subscriptions/update`) against a shop the attacker doesn't own, or desynchronize app state for a shop they have no authorization over — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Likelihood is high for any host app that follows the documented pattern of trusting `WebhookMetadata#shop`/`#topic` (as the gem's own docs recommend). The attacker only needs: (a) their own shop with the app installed to obtain one valid `(body, hmac)` pair for a topic/body they control, and (b) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with custom headers — both trivially available to any unprivileged internet user/app installer. No access token, `api_secret_key`, or privileged account is required.

### Recommendation
Include `shop`, `topic`, and any other header-derived fields used for authorization/routing decisions in the HMAC-signed payload verification (e.g., verify against Shopify's documented webhook headers as an authenticated tuple, or additionally validate the `shop` against the set of shops actually registered/installed for this app, and validate `topic` against the registration the webhook was delivered to that specific path for). At minimum, document and/or enforce that host applications cannot use `shop`/`topic` for tenant-scoping decisions without independently verifying the shop is an installed, known tenant of the app.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" with the app installed.
# 1. Attacker triggers any registered webhook (e.g. app/uninstalled) on their own store,
#    or otherwise obtains a raw_body + valid HMAC for a body they control.
raw_body = '{"id":1,"note":"attacker-controlled"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), Context.api_secret_key, raw_body)

# 2. Attacker POSTs to the app's public webhook endpoint, replaying the same body/hmac
#    but forging the shop-domain (and optionally topic) headers to target a victim shop.
forged_headers = {
  "shopify-topic" => "orders/create",                 # attacker-chosen topic
  "shopify-hmac-sha256" => Base64.encode64(hmac),      # valid, but only proves body integrity
  "shopify-shop-domain" => "victim-shop.myshopify.com" # NOT covered by hmac
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body/hmac match),
#    handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: ...))
#    is invoked, attributing attacker-controlled data to the victim's tenant.
```
