### Title
Missing Shopify-domain validation on JWT `dest` claim before sending `client_secret` in `TokenExchange.exchange_token` - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the request host for the token-exchange call directly from the unsanitized `dest` claim of the session token, and sends the app's `client_secret` (plus the raw session token as `subject_token`) to that host, while every sibling credential-sending code path in the gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) runs the shop value through `Utils::ShopValidator.sanitize!` first.

### Finding Description
The equality that should hold is: *the host that the HTTP client sends the `client_secret` to* == *a host validated to be a trusted Shopify domain*.

In `exchange_token`, the shop used to build the request is taken straight from the JWT payload: [1](#0-0) 

`dest_shop` comes from `JwtPayload#shop`, which is simply `@dest.gsub("https://", "")` with no domain-format or trusted-domain check: [2](#0-1) 

This unsanitized value is used to build the `Session` that seeds `Clients::HttpClient`, and `HttpClient` sets `@base_uri` directly from `session.shop`: [3](#0-2) 

The `client_secret` (and the raw `subject_token`) is placed in the POST body sent to that host: [4](#0-3) 

By contrast, every other place in the gem that sends `client_secret` to a shop-derived host explicitly validates the shop against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (`myshopify.com`, `myshopify.io`, `shopify.com`, `spin.dev`, `shop.dev`) before use: [5](#0-4) [6](#0-5) 

The presence of the sanitize call is confirmed for the sibling `migrate_to_expiring_token` method by its dedicated test, which asserts `InvalidShopError` for a non-Shopify domain: [7](#0-6) 

No analogous test exists for `exchange_token` rejecting a non-Shopify `dest`, and no `ShopValidator` call appears in its implementation. `ShopValidator` itself is defined at: [8](#0-7) 

### Impact Explanation
This maps to the listed analog category "a host validated versus the host that receives the access token or `client_secret`." If the `dest` claim of a session token can ever end up set to a non-`*.myshopify.com` value while the token still verifies (HS256 against `Context.api_secret_key`), `exchange_token` will POST the app's `client_id`, `client_secret`, and the raw session token to that attacker-influenced host — matching the "SSRF with the app's credentials" / credential-leakage High-severity impact category.

### Likelihood Explanation
The likelihood is limited by the fact that the JWT signature is verified with the shared `api_secret_key` (`JwtPayload#initialize`, `decode_token`), so producing a validly-signed token with an attacker-chosen `dest` normally requires knowledge of `api_secret_key`, which is out of scope per the rules. I was not able to find, within this gem's own code, a concrete unprivileged path (no secret, no privileged account) that lets an attacker cause a validly-signed session token to carry an arbitrary/non-Shopify `dest` value. This is therefore a real, demonstrable *inconsistency* in defense-in-depth (missing validation compared to three sibling functions) rather than a confirmed end-to-end unprivileged exploit — the exploitability depends on host-application or Shopify-side behavior outside this gem's own source, which I could not verify with the available tools.

### Recommendation
For consistency with `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`, call `Utils::ShopValidator.sanitize!(dest_shop)` on the value extracted from `jwt_payload.shop` in `TokenExchange.exchange_token` before constructing `shop_session`/`Clients::HttpClient`, raising `Errors::InvalidShopError` for any `dest` that does not resolve to a `TRUSTED_SHOPIFY_DOMAINS` host.

### Proof of Concept
Could not be fully constructed within this gem's own attack surface: exploitation requires demonstrating that a validly HS256-signed session token (against the app's real `api_secret_key`) can carry a `dest` claim pointing to a non-Shopify host, which was not achievable using only the code available in `lib/shopify_api/**`. The finding is reported as a code-level inconsistency with exact supporting lines above; confirming real-world exploitability would require testing how Shopify (or any code outside this gem) issues/propagates the `dest` claim.
