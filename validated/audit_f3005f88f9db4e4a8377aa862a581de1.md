### Title
Attacker-deployed "wrapped native" token mirroring `address(this).balance` lets a single real ETH inflow be double-credited across the `address(0)` entry and the fake wrapped-token entry in `Hinkal.transact`'s balance check, minting shielded UTXO value without backing - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact` snapshots balances for every attacker-supplied `erc20TokenAddresses[i]` via `getBalancesForArray`/`getERC20OrETHBalance`, giving `address(0)` special `+msg.value` treatment while every other address is trusted to return an independent balance via `balanceOf`. Because the circuit's only cross-token guard (`distinctErc20AddressChecks`) merely checks that the addresses are pairwise *different values*, an attacker can list `address(0)` and a self-deployed ERC20 whose `balanceOf` simply returns `address(this).balance`, causing a single real ETH inflow produced during an Emporium `runAction` call to be counted twice - once for the native entry and once for the fake "wrapped" entry - letting the attacker mint two shielded UTXOs worth the same real ETH.

### Finding Description
Broken equality: `sum(real net ETH received by Hinkal) == sum(amountChanges/utxoAmount credited across all token slots that represent that ETH)`. The code makes this false when two entries in `circomData.erc20TokenAddresses` alias the same underlying balance.

Path:
1. `Hinkal.transact` calls `getBalancesForArray(circomData.erc20TokenAddresses)` before and after `_externalTransact`: [1](#0-0) 
2. For each token slot the balance delta is computed, with `address(0)` getting `+msg.value` added on top of the raw balance delta, while any other address is trusted via `getERC20OrETHBalance` → `IERC20(...).balanceOf(address(this))`: [2](#0-1)  and [3](#0-2) 
3. The only on-chain/circuit guard against duplicate/aliased token slots is `distinctErc20AddressChecks`, which only forces the raw address *values* to differ - it has no notion that two different addresses might represent the same economic balance: [4](#0-3) 
4. During `_externalTransact` → `EmporiumUpgradeable.runAction`, proceeds from arbitrary attacker-crafted ops are sent back to `msg.sender`, which at that call frame is the `Hinkal` contract itself (since `Hinkal` is the direct caller of `runAction`), via `handleOut`: [5](#0-4) . This genuinely increases `address(this).balance` of `Hinkal` between the `oldBalances`/`newBalances` snapshots taken in `transact`.
5. The attacker deploys a token `T` whose `balanceOf(a)` simply returns `a.balance` (i.e., mirrors whatever address is queried, in particular `Hinkal`'s ETH balance) and lists `[address(0), T]` in `erc20TokenAddresses`. Because `T != address(0)`, the circuit's distinctness check passes trivially, and nothing in `Hinkal.sol`/`HinkalHelper.sol`/`EmporiumUpgradeable.sol` validates that a listed ERC20 is economically independent from the native asset.
6. When the swap/op inside `runAction` yields `X` real ETH back to `Hinkal`, both the `address(0)` slot (`balanceDif = ΔETH + msg.value`) and the `T` slot (`balanceDif = balanceOf(Hinkal)_after - balanceOf(Hinkal)_before = ΔETH`) observe the same `ΔETH = X`. The attacker crafts `amountChanges`/on-chain UTXO amounts for both slots (self-generated proof, fully attacker-controlled `CircomData`) to each claim `X`, satisfying the per-token equality check independently for each slot: [6](#0-5) . The circuit constraint `inTotal + amountChanges[i] === outTotal` is enforced per-token in isolation and has no knowledge that token slot `i=T` and `i=address(0)` reference the same underlying value, so it is trivially satisfiable by the attacker's own proof for their own UTXOs.

Net effect: one real ETH inflow of `X` is credited as `2X` of shielded value (one UTXO under `address(0)` worth `X`, one UTXO under fake token `T` worth `X`), even though the vault only holds `X` in additional real assets. Both UTXOs remain independently redeemable later (each redemption again just moves/reads the same shared ETH balance), so the protocol becomes undercollateralized by `X` per exploit run.

Why guards don't stop it: `performHinkalChecks`/`dimensionsCheck` only check array-length consistency and role/relay/root validity, not token semantic independence; `verifyProof` only checks internal circuit consistency (each token slot balanced independently); `onlyAllowedRecipient` restricts who can call `runAction` but Emporium is a legitimately whitelisted external action, so an ordinary user routing through it satisfies this; nothing in the traced code calls out to an oracle or enforces that a listed "ERC20" is a real, independent asset from `address(0)`.

The "6 decimals" framing in the question does not materially change the analysis: no decimal-scaling/conversion logic was found anywhere in `Hinkal.sol`, `Transferer.sol`, or `EmporiumUpgradeable.sol` - all balances and amounts are handled as raw `uint256` token units, so the vulnerability is not decimals-dependent; the attacker's mirror-token contract can be given any decimals metadata without affecting the exploit.

### Impact Explanation
This lets an unprivileged attacker mint shielded UTXO value not backed by real deposited assets — classified as Critical (minting shielded value without backing / protocol insolvency) per the rules. Each run of the attack (one Emporium action that yields ETH proceeds back to the vault) can double-count that proceeds amount `X`, and is repeatable at will by any user who can route funds through an Emporium op returning ETH to the vault and who deploys their own mirror-balance "token" contract for the `erc20TokenAddresses` array.

### Likelihood Explanation
Preconditions: attacker must deploy a trivial ERC20-like contract (`balanceOf` returning `a.balance`), be able to route an Emporium `runAction` whose ops yield net ETH proceeds back to `Hinkal` (achievable with any endpoint the attacker controls or a real swap), and generate a self-consistent proof for their own UTXOs claiming both slots — all explicitly within the stated attacker capabilities (deploy tokens/hooks, craft `CircomData`, generate proofs for own UTXOs). No privileged role, relay, or victim funds are required. Cost is limited to gas and deploying one contract; the technique is fully repeatable.

### Recommendation
Do not allow the same underlying value to be represented by two entries in `erc20TokenAddresses`. Concretely: (1) explicitly forbid `address(0)` from co-existing with any other address whose `balanceOf` cannot be independently attested (e.g., disallow arbitrary user-supplied tokens from being combined with native ETH unless whitelisted), or (2) snapshot balances using a trusted, hardcoded list of canonical wrapped-native addresses matched against `address(0)`, or (3) require `msg.value` accounting only for the `address(0)` slot and independently verify, via a whitelist/registry, that any other listed ERC20 address is a genuine, code-verified token contract (not attacker-deployed) before trusting its `balanceOf` return value in the solvency check.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable` (registered as external action), and a `MirrorToken` contract with `balanceOf(address a) returns (a.balance)`.
2. Fund an EOA (attacker) with ETH; craft `CircomData` with `erc20TokenAddresses = [address(0), address(MirrorToken)]`, `externalActionData` pointing at Emporium, and an `EmporiumStack` whose op performs a controlled action that results in `handleOut` sending `X` ETH back to `Hinkal` (e.g., an endpoint that simply forwards `X` ETH to `msg.sender` which resolves to `Hinkal`).
3. Set `amountChanges = [X, X]` (or corresponding on-chain UTXO amounts) and generate a locally-produced proof satisfying the circuit's per-token equation independently for each slot.
4. Call `Hinkal.transact(...)`.
5. Assert: `address(this).balance` of `Hinkal` only increased by `X` (real backing), but two UTXOs were inserted (`insertCommitments`) with combined value `2X` — i.e., `vault balance delta (X) < total credited UTXO value (2X)`, confirming the broken invariant `net tokens entering Hinkal == sum(amountChanges) + sum(on-chain UTXO amounts minted)`.

    function getERC20OrETHBalance(
        address _erc20TokenAddress
    ) internal view returns (uint256) {
        if (_erc20TokenAddress == address(0)) {
            return address(this).balance;
        } else {
            IERC20 outToken = IERC20(_erc20TokenAddress);
