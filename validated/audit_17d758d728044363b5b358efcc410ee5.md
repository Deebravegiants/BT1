### Title
Fraud detection gate is permanently disabled, allowing all signups (including fraudulent ones) to bypass fraud enforcement - (File: src/plans/mod.rs, src/plans/fraud_check.rs)

### Summary
The orb-core signup pipeline calls `detect_fraud` to decide whether a completed biometric capture should be flagged as fraudulent and rejected. This function is hardcoded to always return `Ok(false)`, and its backing `fraud_check::Report` type has zero fraud checks defined (`N_FRAUD_CHECKS = 0`), so no fraud signal can ever propagate to a `true` result [1](#0-0) [2](#0-1) .

### Finding Description
In the disclosed report, the vulnerability was a governance quorum constant (`GovernorVotesQuorumFraction(4)`) that silently undercut the intended 25% enforcement threshold, letting proposals execute far below the required voting power. The analog root cause here is structurally the same: a value/config that is supposed to gate a sensitive workflow decision (allow/deny) has been effectively neutralized, but the surrounding code still treats it as if enforcement is active.

Concretely:
- `Plan::detect_fraud` in `src/plans/mod.rs` is explicitly annotated `// FOSS: WE HAVE DELETED ALL FRAUD CHECKS` and unconditionally returns `Ok(false)`, regardless of the biometric pipeline output passed to it [3](#0-2) .
- The `fraud_check::Report` struct is empty (`pub struct Report {}`), and `N_FRAUD_CHECKS` is set to `0`, meaning `fraud_checks()`, `enabled_checks_from_config()`, and `feedback_messages()` all return empty arrays [4](#0-3) [5](#0-4) .
- As a consequence, `Report::fraud_detected()` (`self.fraud_checks_strict().iter().any(|&v| v)`) can never be `true` because it iterates over a zero-length array [6](#0-5) .
- The calling site in the signup flow computes `fraud_detected` and uses it to set `SignupReason::Fraud` vs `SignupReason::Normal`, which downstream determines whether the user is enrolled and whether biometric data upload / enrollment proceeds as a legitimate signup [7](#0-6) .

Just as the quorum bug allowed a proposal to be treated as "passed" despite failing to meet the intended threshold, this code allows a signup to always be treated as "not fraudulent" despite the biometric pipeline producing (or being expected to produce) legitimate fraud signals such as contact lenses, occlusion, multiple faces, or underage detection — all of which are still enumerated as feedback message types that can never actually be triggered [8](#0-7) .

### Impact Explanation
Because `detect_fraud` always yields `false`, no signup can ever be rejected for fraud through this mechanism, and `SignupReason::Fraud` is unreachable. This maps to the "fraud/liveness bypass" impact category: an unprivileged user's fraudulent biometric capture (e.g. spoofed capture, occluded face, contact lenses, underaged subject) is always classified as `SignupReason::Normal`, permitting enrollment and biometric data upload to proceed as if the capture were fully legitimate.

### Likelihood Explanation
This is not a rare edge case — it is the deterministic, always-on behavior of the code path for every single signup that reaches the fraud-detection stage, since `detect_fraud` has no conditional logic and always short-circuits to `Ok(false)` [9](#0-8) .

### Recommendation
Restore functional fraud checks in `fraud_check::Report`/`FraudChecks::run` (or otherwise validate biometric-pipeline fraud signals) instead of returning an unconditional empty/false result, and ensure `Plan::detect_fraud` actually evaluates the fraud-check report produced by the biometric pipeline before deciding `SignupReason`.

### Proof of Concept
1. Trigger any signup where the biometric pipeline would normally produce fraud signals (e.g., contact lenses, face occlusion, underaged subject, multiple faces).
2. Observe that `Plan::detect_fraud` (`src/plans/mod.rs:1392-1406`) is invoked and unconditionally returns `Ok(false)` without inspecting the `pipeline` argument.
3. Observe that even if `fraud_check::Report` were populated, `Report::fraud_detected()` (`src/plans/fraud_check.rs:112-114`) iterates over a `0`-length array (`N_FRAUD_CHECKS = 0`), so it can never return `true`.
4. Confirm downstream in `signup_reason` computation (`src/plans/mod.rs:563-571`) that `fraud_detected == false` forces `SignupReason::Normal`, allowing enrollment to proceed regardless of the actual fraud state of the capture.
