## Analog Found

### Title
IntentGatewayV2 `_cancelFromDest` finalizes the order before the cross-chain refund is confirmed, permanently stranding escrow if the RefundEscrow message never completes - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
This mirrors the SolverVaults bug class: a destructive/finalizing state write happens in step 1, while the actual asset payout is delegated to a separate, fallible step 2. In `ExtrinsicIntents._cancelFromDest`, the order is irreversibly marked `_filled[commitment]` — permanently blocking any future fill — before the cross-chain `RefundEscrow` message that is supposed to release the escrowed input tokens on the source chain is even dispatched, let alone confirmed delivered.

### Finding Description
`_cancelFromDest` is reachable by anyone after the order deadline (or by the order owner before it): [1](#0-0) 

It writes `_filled[commitment] = order.user` locally on the destination chain — the same flag documented as meaning "the order has been finalized and cannot be filled again": [2](#0-1) 

— and only afterward dispatches the `RefundEscrow` post request via `_post`, which uses `timeout: 0` (i.e., the request never expires and has no automatic fallback path): [3](#0-2) 

The actual release of the user's escrowed input tokens only happens later, on the source chain, inside `onAccept` → `_withdraw`, when the `RefundEscrow` message is delivered and accepted: [4](#0-3) [5](#0-4) 

If that delivery permanently fails to be accepted (e.g. `_authenticate` mismatch from a misconfigured/unregistered `_instances` mapping for the reverse direction, a decode failure, or `_withdraw`'s `revert UnknownOrder()` if the escrow accounting for that commitment/token is already zero for any reason), there is no code path that reverts or resets the local `_filled[commitment]` flag on the destination chain. The destination-side finalization is unconditional and irreversible, while the actual fund recovery depends entirely on a decoupled cross-chain message succeeding — exactly the SolverVaults pattern of burning the claim before the payoff is guaranteed.

### Impact Explanation
Once `_filled[commitment]` is set by `_cancelFromDest`, the order can never be filled by a solver (the entrypoint gateway logic checks this flag to reject fills). If the paired `RefundEscrow` message is never successfully processed on the source chain, the user's escrowed input tokens remain permanently locked in the source `IntentGatewayV2`/`ExtrinsicIntents` contract with no remaining code path to release them — the user ends up with neither a filled order nor their escrowed funds, a permanent freezing of funds.

### Likelihood Explanation
`cancelOrder` targeting the destination-chain path is callable by any account after the order deadline expires, making this reachable without any privileged role. The trigger condition (permanent failure of `onAccept`/`_withdraw` on the source chain for a `RefundEscrow` message, e.g. via stale/unregistered gateway instance mappings, decode edge cases, or escrow-accounting desync) is a realistic operational failure mode in a cross-chain relayed system, not a contrived edge case, and the `timeout: 0` setting removes even the possibility of a timeout-triggered fallback.

### Recommendation
Do not treat the order as finalized on the destination chain until the source chain confirms the escrow was actually released. Options: (1) only mark `_filled[commitment]` after receiving a confirmation callback from the source chain (i.e. invert the flow so escrow release happens first, or is confirmed before blocking future fills), or (2) give the `RefundEscrow`/`RedeemEscrow` messages a genuine timeout and an explicit `onPostRequestTimeout` handler that unmarks `_filled[commitment]` (or otherwise makes recovery possible) so a permanently undeliverable message doesn't leave escrow stranded forever.

### Proof of Concept
1. User places a cross-chain order; input tokens are escrowed on the source chain, `_orders[commitment][token] = amount`.
2. Order deadline passes without a solver filling it.
3. Anyone calls `cancelOrder` on the destination chain → `_cancelFromDest` sets `_filled[commitment] = user` and dispatches a `RefundEscrow` `DispatchPost` with `timeout: 0`.
4. A relayer attempts delivery to the source chain's `onAccept`; suppose `_authenticate` fails permanently (e.g., the destination's registered `_instances[order.destination]` address doesn't match the gateway instance that actually dispatched the message, due to a prior `UpdateParams`/`NewDeployment` reconfiguration) — every delivery attempt reverts.
5. `_filled[commitment]` on the destination remains permanently set (no fill possible), and `_orders[commitment][token]` on the source chain is never decremented/paid out — escrow is stuck forever, and the user recovers nothing.

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        _post(
            order, _body(RequestKind.RefundEscrow, commitment, order.inputs, order.user), options.relayerFee, msg.value
        );
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
