### Title
Missing check for active L2 Sequencer in `SimplexPaymaster._getOraclePrice` - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster` prices ERC-20 gas payments and fee-recycling swaps using Chainlink `AggregatorV3Interface` feeds, and is explicitly deployed to L2s such as Arbitrum, Optimism, and Base (OP-stack chains) alongside BSC and Ethereum mainnet. `_getOraclePrice` only validates that the answer is positive and not older than `maxOracleAge`; it never checks an L2 sequencer-uptime feed, so a sequencer outage/restart can be exploited to consume a stale-but-"fresh" price.

### Finding Description
`_getOraclePrice` fetches `latestRoundData()` and only guards against non-positive answers and staleness relative to `maxOracleAge`: [1](#0-0) 

There is no call to a Chainlink L2 sequencer-uptime feed (e.g., the `SequencerUptimeFeed`) anywhere in the contract, confirmed by the absence of any "sequencer" references in the EVM contracts (only unrelated Arbitrum-client/consensus code elsewhere in the repo uses that term): [2](#0-1) 

The deploy script and comments confirm this paymaster is intended for L2 deployments with sub-24h Chainlink heartbeats (Base/Ethereum, BSC, and by extension Arbitrum/Optimism, per the SDK's Chainlink feed address registry covering `EVM-42161` (Arbitrum) and `EVM-10` (Optimism)): [3](#0-2) [4](#0-3) 

`_getOraclePrice` is reached from the fully unprivileged ERC-4337 validation path `_fetchDetails` (invoked for every submitted UserOperation) and from the pricing helper `_tokenPrice`, both of which any bundler/UserOp sender triggers without any privilege: [5](#0-4) 

It is also used by `swapAndDeposit` to derive the minimum-out for a Uniswap V2 swap of accrued fees: [6](#0-5) 

Because Chainlink price feeds on Arbitrum/Optimism/Base stop updating whenever the L2 sequencer is unavailable, `updatedAt` simply freezes at the last on-chain update, and the L2's own `block.timestamp` freezes with it (no new L2 blocks are produced). The staleness check (`block.timestamp - updatedAt > maxOracleAge`) can therefore stay "fresh" for an arbitrarily long real-world outage, and — critically — once the sequencer resumes and processes the backlog, a burst of L2 blocks can be produced in quick succession before the price feed's own updater posts a new round. Any UserOp (or the treasury's `swapAndDeposit`) submitted in that recovery window is priced against a real-world-stale but timestamp-fresh answer, since the maintainers themselves acknowledge oracle freshness/staleness is not otherwise bounded per-transaction (this exact class of risk was explicitly deferred, not fixed): [7](#0-6) 

### Impact Explanation
A stale price consumed right after a sequencer outage/restart lets a UserOp sender pay a mispriced amount of the stablecoin for gas (under- or over-charging relative to true market rate), and lets `swapAndDeposit`'s slippage-bounded swap execute against a stale expected price, causing the treasury-recycled funds to be swapped at an unfavorable, manipulable rate. This is a concrete loss-of-funds vector for the paymaster's treasury/surplus, consistent with the Medium severity of the original DODO finding.

### Likelihood Explanation
L2 sequencer downtime is an operationally realistic, recurring event on Arbitrum, Optimism, and Base (the very chains this contract's deploy tooling and Chainlink feed registry target), and the exploit window (the recovery burst right after resumption) requires no special access — any UserOp sender or the treasury operator's routine `swapAndDeposit` call is sufficient to realize the mispricing.

### Recommendation
Add a Chainlink `SequencerUptimeFeed` check (per-chain, configurable like `nativeOracle`) in `_getOraclePrice`, reverting (or applying a grace period after the sequencer comes back up, per Chainlink's documented pattern) when the sequencer is reported down or has been up for less than the recommended grace period, before trusting `latestRoundData()` on any L2 deployment.

### Proof of Concept
1. Deploy `SimplexPaymaster` on Arbitrum/Optimism/Base per `DeploySimplexPaymaster.s.sol`.
2. Simulate an L2 sequencer outage: Chainlink feed's `updatedAt` and the chain's `block.timestamp` both stop advancing during the outage.
3. Sequencer resumes and processes a backlog of transactions/blocks quickly; the price feed's updater has not yet pushed a new round.
4. Within this window, submit a UserOp (or call `swapAndDeposit`) — `_getOraclePrice` passes both the `answer <= 0` and `block.timestamp - updatedAt > maxOracleAge` checks because the L2 clock only just resumed advancing, so the transaction executes against a real-world-stale price, as shown by the unguarded logic at: [8](#0-7)

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```

```markdown
# 2026-08-19 — Not adopted: soft-failing the prefund, and oracle-derived validity bounds (#1071)

Rejected: returning `prefunded = false` instead of reverting in the mode-2 `_prefund`. Upstream advises it to protect bundler reputation, but reading EntryPoint v0.8 shows both outcomes are `revert FailedOp` — AA33 for a paymaster revert, AA34 for a sig-failure — so both revert `handleOps` identically. The change would trade the `Permit2Failed(token, reason)` diagnostic, which carries Permit2's own revert data, for no bundle-level benefit.

Also deferred at the maintainer's direction: bounding `validationData`'s `validUntil` by oracle freshness so bundlers drop soon-to-be-stale ops instead of building bundles that revert. Sound in principle and would have made stale-oracle failures expire cleanly, but it touches every pricing path and was out of scope for this pass.
```
