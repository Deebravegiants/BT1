This confirms the vulnerability: `Registry.process` validates the HMAC over the request via `Utils::HmacValidator.validate(request)`, but `HmacValidator.validate_signature` computes the signature only over `verifiable_query.to_signable_string`, and `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) . Meanwhile `request.shop` is read from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header [2](#0-1) , which is never part of the signed bytes. `Registry.process` then trusts `request.shop` and passes it straight into the `WebhookMetadata` handed to the app's handler after only checking the HMAC of the body [3](#0-2) .

### Title
Webhook `shop` header is not covered by HMAC verification, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body via `Utils::HmacValidator.validate(request)` [4](#0-3) . The `Webhooks::Request#to_signable_string` method used as the HMAC input only returns `@raw_body` [1](#0-0) , but the `shop` value that identifies the tenant is read separately from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not included in the signed bytes at all [2](#0-1) .

### Finding Description
The intended identity binding is: `shop attributed to the webhook == shop the HMAC signature actually authenticates`. In practice this equality does not hold. `HmacValidator.validate` computes `computed_signature = compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac-sha256` header [5](#0-4) . Because `to_signable_string` is just the raw body, the `shop-domain` header can be freely modified by anyone relaying (or replaying) a legitimately-signed webhook body without invalidating the signature. `Registry.process` then builds `WebhookMetadata` directly from `request.shop`, `request.topic`, and `request.parsed_body` and forwards it to the app-registered handler as if it were the authenticated source-of-truth for which merchant/tenant the payload belongs to [6](#0-5) . Any handler that keys look-ups (e.g., loading the merchant's session/access token, or writing data) by `WebhookMetadata#shop` without independently re-verifying the shop is operating on attacker-controlled, unauthenticated tenant identity while believing it passed HMAC verification.

### Impact Explanation
This crosses a tenant boundary: an unprivileged internet user who has observed or captured one validly-signed webhook payload (e.g., their own store's webhook, which Shopify sends to a public HTTPS endpoint) can resubmit it with an arbitrary `shopify-shop-domain` header while keeping the original valid HMAC signature intact. Any consuming application that trusts `WebhookMetadata#shop`/`request.shop` as an authenticated tenant identifier — which is the documented and expected use, since the gem exposes `shop` precisely for that purpose — will process the payload under the wrong shop, leading to cross-tenant data confusion (e.g. writing/deleting data attributed to shop B while it actually came from shop A, or triggering `shop/redact` / `customers/redact` handlers for the wrong tenant).

### Likelihood Explanation
Likelihood is high for any app relying on this gem's webhook verification helper as designed: `Registry.process` is the gem's own dispatch entry point, and it hands `request.shop` to handlers immediately after HMAC validation succeeds, with no additional binding of the header to the signed payload [3](#0-2) . No secret, access token, or privileged access is required — only a copy of one previously delivered (or otherwise obtained) valid webhook body/HMAC pair to replay with a modified shop header, entirely within the gem's public API surface.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) in the HMAC-signed input, or otherwise cryptographically bind `request.shop` to the verified payload before it is exposed to handlers. At minimum, `to_signable_string` should not silently omit fields (`shop`, `topic`) that the gem itself exposes as trusted request attributes post-verification.

### Proof of Concept
1. Capture a legitimately Shopify-signed webhook HTTP request (raw body `B`, headers including `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: shop-a.myshopify.com`).
2. Resend the request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but replacing `x-shopify-shop-domain` with `shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: modified_headers)` is constructed; `to_signable_string` still returns `B` [1](#0-0) .
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because the signature only covers `B`, not the shop header [7](#0-6) .
5. The handler is invoked with `WebhookMetadata.new(..., shop: "shop-b.myshopify.com", ...)`, causing the app to process shop-a's authenticated payload as belonging to shop-b [6](#0-5) .
