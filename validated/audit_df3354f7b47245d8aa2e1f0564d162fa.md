## Title
Webhook `shop`, `topic`, and `webhook-id` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, then hands the caller a `WebhookMetadata` object built from `request.shop`, `request.topic`, and `request.webhook_id` — none of which are included in the signed material.

### Finding Description
The binding that should hold is:

`bytes verified by HMAC == bytes used to determine tenant identity (shop) and semantics (topic, webhook_id)`

That binding is broken. `ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic tie to the signed body: [2](#0-1) 

`HmacValidator.validate` only ever hashes `verifiable_query.to_signable_string` (i.e., the body) against the secret: [3](#0-2) 

`Registry.process` performs exactly this body-only check and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to construct the metadata passed to the host application's handler: [4](#0-3) 

The gem's own documented usage pattern instructs host apps to build `WebhookMetadata` this way, i.e. to treat `request.shop` as the authenticated origin shop for the payload: [5](#0-4) 

Because the `client_secret`/API secret key is shared across **all** shops that install a given app, any merchant who installs the app (an unprivileged internet user w.r.t. other tenants) legitimately receives real, correctly-HMAC-signed webhook bodies for their own store. That attacker can capture one such valid `(body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` reports the forged shop/topic to the handler as if Shopify itself sent that data for the victim shop.

### Impact Explanation
This breaks the tenant-identity binding the HMAC is supposed to enforce: verifying "this body was produced by someone holding the app's secret" is conflated with "this body belongs to shop X." A malicious merchant can inject attacker-controlled webhook payloads that the host application will process under another tenant's identity (cross-tenant data injection), since the shop attribution is unauthenticated. This matches the Critical "cross-tenant access" category.

### Likelihood Explanation
Any app developer that installs the app on their own shop (a normal, unprivileged action) can obtain a genuinely signed webhook body/HMAC pair for arbitrary registered topics of their choosing, then replay it against the shared webhook endpoint with a forged shop-domain header. No access token, `client_secret`, or privileged access is required — only participation as an ordinary merchant of the app.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-covered material, or otherwise cryptographically bind them to the verified body (e.g., derive/confirm the shop identity from a value that is itself covered by the signature, or require an out-of-band verified association between the shop and its previously-issued webhook subscription rather than trusting the header verbatim in `Request#shop`).

### Proof of Concept
1. App developer installs the target app on `attacker-shop.myshopify.com`; app registers `orders/create` webhook.
2. Shopify sends a legitimate webhook: body `B`, headers include `x-shopify-hmac-sha256: H` (valid HMAC of `B`), `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the same request to the app's webhook controller, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates `H` against body `B` only and succeeds: [6](#0-5) 
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: B, ...)`, and the host app processes attacker-controlled data under the victim's tenant.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
