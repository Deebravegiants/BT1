### Title
Unrefunded excess native token overpayment permanently lost in `EvmHost.dispatch()`/`fundRequest()` - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` accept native token (`msg.value`) as an alternative payment method, swapping it for the exact `feeToken` amount via `IUniswapV2Router02.swapETHForExactTokens`. The router refunds any unused ETH to its caller (`msg.sender` of the swap call), which is `EvmHost` itself, not the original user who called `dispatch()`. Any native token sent in excess of what the swap actually consumes is captured by the `EvmHost` contract and never returned to the user.

### Finding Description
In `EvmHost.dispatch(DispatchPost memory post)`: [1](#0-0) 

and the analogous `dispatch(DispatchGet)` and `fundRequest()`: [2](#0-1) [3](#0-2) 

all call `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. The standard UniswapV2Router `swapETHForExactTokens` implementation refunds `msg.value - amounts[0]` back to `msg.sender`, but since `EvmHost` is the direct caller of the router (not the end user), the refund lands in `EvmHost`'s own balance instead of being returned to the original caller. There is no `receive()`/refund forwarding logic in `dispatch()` to pass this leftover ETH back to `_msgSender()`, and no sweep/withdraw function exists in `EvmHost.sol` to recover it for the affected user.

This mirrors exactly the reported bug class: because there is no reliable way for a caller to know the *exact* native-token cost in advance (the docs explicitly warn against calling `quote()` on-chain due to sandwich-attack risk, and recommend off-chain estimation with a buffer — as demonstrated by `HyperbridgeLzEndpoint.quote()` applying a 2x buffer), users are expected to send more ETH than strictly required. Unlike `dispatch()`/`fundRequest()`, other, newer parts of the codebase have already recognized and fixed this exact pattern by explicitly refunding unspent `msg.value` to `msg.sender`: [4](#0-3) [5](#0-4) 

Both of these explicitly compute `msgValue -= amounts[0]` (or similar) and call `_sendValue(msg.sender, msgValue)` to return the leftover. `EvmHost.dispatch()`/`fundRequest()` lack this same safeguard, despite performing the identical ETH→feeToken swap pattern.

Any `IApp`/user calling `IDispatcher(host).dispatch{value: msg.value}(post)` directly — including `HyperFungibleTokenUpgradeable.send()` and `HyperbridgeLzEndpoint.send()` — inherits this vulnerability, since they simply forward `msg.value` to `EvmHost.dispatch()` without any refund path back to the end user. [6](#0-5) 

### Impact Explanation
Any user or application dispatching a POST/GET request or funding a request with native token, who sends slightly more ETH than the exact swap requires (which is the expected/recommended usage pattern per the SDK/docs buffer guidance), permanently loses that excess ETH. It is absorbed into the `EvmHost` contract's balance with no mechanism in `EvmHost.sol` to return it to the affected user. This is a direct, unrecoverable loss of user funds reachable by any unprivileged caller of the core dispatch path — impacting every application built on `IDispatcher.dispatch()`/`fundRequest()` that pays with native token.

### Likelihood Explanation
High. Overpayment is the expected behavior encouraged by the protocol's own documentation and SDK (buffer/slippage guidance, `quote()`'s sandwich-attack warning discouraging on-chain exact quoting), so essentially every native-token dispatch that isn't perfectly precise triggers this loss. No special conditions or privileged access are required — a single ordinary `dispatch{value: ...}()` call with a slightly generous `msg.value` is sufficient.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture the `amounts[0]` (actual ETH spent) returned by `swapETHForExactTokens` and refund the difference (`msg.value - amounts[0]`) back to `_msgSender()`, following the same pattern already implemented in `IntentGatewayV2._placeOrder` and `ExtrinsicIntents._fillCrossChain`.

### Proof of Concept
1. A user calls `IDispatcher(host).dispatch{value: 5 ether}(post)` where `post.fee` (in feeToken) is worth roughly `0.1 ether` at current AMM pricing, intentionally overpaying to guard against slippage/price movement as recommended by the docs.
2. Inside `EvmHost.dispatch()`, `swapETHForExactTokens{value: 5 ether}(post.fee, path, address(this), block.timestamp)` is called; the router swaps only ~0.1 ETH worth and refunds the remaining ~4.9 ETH to `msg.sender` of the swap call — i.e., to `EvmHost`, not the user.
3. `EvmHost.dispatch()` proceeds to emit `PostRequestEvent` and return the commitment; the ~4.9 ETH refund is now stranded in the `EvmHost` contract's balance.
4. There is no function in `EvmHost.sol` allowing the user (or anyone) to reclaim this ETH — it is permanently lost from the user's perspective, contrasting with `IntentGatewayV2SameChainTest.testPlaceOrder_FeeSwap_RefundsExcessNativeToken` and `testPlaceOrder_RefundsExcessNativeToken`, which verify the correct refund behavior exists elsewhere but is absent in `EvmHost`'s own dispatch functions.
