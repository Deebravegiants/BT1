### Title
Reverting LT.exchangeRate() bricks both buy and sell for every curve on that LT, contradicting the documented sell-always-open design - (File: packages/contracts/src/Bonding.sol)

### Summary
`Bonding.canGraduate()` unconditionally calls the external, BounceTech-controlled `IBounceLeveragedToken(info.ltAddress).exchangeRate()`. Both the buy path (`_executeBuy`, called from `Bonding.buy`) and the sell path (`Bonding.sell`) call `canGraduate()` on every trade. If the paired LT's `exchangeRate()` reverts — through a pause, blacklist, upgrade, bug, or hack of the externally-controlled BounceTech LT, the same failure-mode class described in the referenced M-16 report — every buy and every sell on every curve paired to that LT reverts, freezing user funds with no recovery path from within the protocol.

### Finding Description
`canGraduate` is called unconditionally inside both trading entry points: [1](#0-0) [2](#0-1) 

`canGraduate` itself makes a live external call to the LT: [3](#0-2) 

The protocol's own documentation explicitly accepts a narrower version of this failure — an LT `mint()` pause — and treats it as tolerable *specifically because sells keep working through `redeem`*: [4](#0-3) 

That design assumption does not hold for an `exchangeRate()` revert. Unlike `mint`, `exchangeRate` is read on the sell path too (via `canGraduate` inside `Bonding.sell`), so a reverting `exchangeRate()` freezes both buy and sell simultaneously for every curve paired to that LT — the exact "sell-only market is preferable to freezing both sides" invariant the codebase says it relies on is violated. There is no owner/governance override, circuit breaker, or fallback that lets `canGraduate` degrade gracefully (e.g. treat a reverting call as "not graduatable" and let the trade proceed) — a `try/catch` around the external call, analogous to `BasketHandler.quantity`'s `try assetRegistry.toColl(...) catch { return FIX_ZERO; }` pattern in the referenced report's remediation, is absent here.

The root cause mirrors M-16 exactly: a plugin/AMM assumes a single external collateral-like asset (`exchangeRate()`) will always answer, and hard-wires that call into the critical path of both core trading functions with no unregister/replace/bypass mechanism, and no isolation between the "trade" concern and the "graduation-check" concern.

### Impact Explanation
Any curve whose paired LT's `exchangeRate()` reverts becomes completely frozen for both buying and selling: traders cannot exit their positions (no sell), cannot enter (no buy), `triggerGraduation` also reverts (same call), and `finalizeGraduation` can never be reached because `_enterGraduating` is never called. Funds already deposited in that curve's `Pair` (real LT raised, unsold tokens) become permanently stuck with no path to redemption via the in-scope contracts — this satisfies "permanent freezing of trader ... funds." Because `ltAddress` is set once at `launch` and is not owner-replaceable, there is no admin remediation path either.

### Likelihood Explanation
This requires the external BounceTech LT (an out-of-protocol dependency already acknowledged as a trust boundary in the code's own comments about pause/retirement) to revert on `exchangeRate()`. This is realistic given BounceTech LTs are described as pausable, upgradeable, and subject to their own admin/keeper actions; a pause, blacklist, or bug in a widely-integrated LT is a foreseeable single point of failure, matching the "hack/upgrade/freeze" scenarios the original report enumerates. No privileged action or unusual capital is needed from the attacker/trigger side — this is purely a dependency-availability risk baked into every trade.

### Recommendation
Wrap the external `exchangeRate()` (and any other LT call inside `canGraduate`) in a `try/catch`, defaulting to "not graduatable" (or some safe non-reverting fallback) on failure, so a misbehaving LT degrades graduation-detection gracefully instead of reverting the entire buy/sell path. At minimum, decouple the sell path from `canGraduate` entirely (sells should never depend on a view used only to gate buy-side graduation), restoring the "sell always available" guarantee the codebase's own comments assume holds.

### Proof of Concept
1. Launch a token via `Bonding.launch` paired to LT `L` (mirrors real deployment).
2. Trader buys some `tokenAddress` via `Zap.buy` — succeeds normally, `Bonding.buy` → `_executeBuy` → `canGraduate` → `L.exchangeRate()` returns fine.
3. `L` (an external BounceTech contract, outside this protocol's control) is paused / blacklists the `Bonding` contract / is upgraded to a version whose `exchangeRate()` now reverts (same fact pattern as the M-16 self-destructed cUSDP scenario).
4. Trader calls `Zap.sell(tokenAddress, amount, 0)` → `Bonding.sell` → `canGraduate(tokenAddress)` → `L.exchangeRate()` reverts → the entire `sell` call reverts.
5. Any other trader's `Zap.buy` on the same curve also reverts at `_executeBuy`'s trailing `canGraduate` check.
6. No function in `Bonding`, `Router`, `Zap`, or `Factory` allows replacing `ltAddress` for an already-launched token or bypassing the `canGraduate` check, so the curve (and any real LT/tokens locked in its `Pair`) is permanently unreachable.

    function canGraduate(
        address token_
    ) public view returns (bool) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return false;
        if (info.lifecycle != Lifecycle.Curve) return false;

        address pair = info.pair;
        if (IPair(pair).tokenBalance() == 0) return true;

        (, uint256 assetReserve) = IPair(pair).getReserves();
        uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
        uint256 valueUsd = (realLtRaised * IBounceLeveragedToken(info.ltAddress).exchangeRate()) / 1e18;
        return valueUsd >= $.graduationThresholdUsd;
    }
