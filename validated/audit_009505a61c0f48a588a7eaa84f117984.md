### Title
Webhook shop/topic attribution headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop`, `topic`, and `webhook_id` values used to route and attribute the webhook to a specific merchant come from separate, unsigned HTTP headers. This breaks the identity binding `bytes verified == bytes acted on`: the signature verifies the body, but the tenant identity used by the application (`request.shop`) is taken from headers outside the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers, none of which are part of the signed material: [2](#0-1) 

`Registry.process` validates only the HMAC over the body via `HmacValidator.validate(request)`, then immediately trusts `request.shop` and `request.topic` (from headers) to route/attribute the webhook to a handler and merchant: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` compute the HMAC purely from `verifiable_query.to_signable_string` (the raw body for webhooks), and compare it against the `hmac` header value: [4](#0-3) 

Because Shopify signs webhook bodies with the same `api_secret_key` for every shop that installs the app, any merchant who legitimately installs the app can capture a genuinely-signed `(body, hmac)` pair delivered to their own shop, then replay that exact body+hmac to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header to name a *different* victim shop. `HmacValidator.validate` will still succeed (since it only checks the body bytes against the signature), and `Registry.process` will pass the attacker-chosen `shop` value into `WebhookMetadata`, which the host application's handler will treat as authentic data belonging to that shop.

This satisfies the "field acted on but not covered by the HMAC" analog: the equality that should hold is `shop_header == shop_bound_by_signature`, but in this implementation `shop_header` is never part of `to_signable_string`, so the equality is never enforced.

### Impact Explanation
This allows cross-tenant confusion: an attacker who can obtain one valid signed webhook body (by having a shop of their own install the app) can make the host application process arbitrary attacker-controlled webhook payloads as if they originated from a shop they do not own/control. Depending on how the host app's webhook handlers use `data.shop` (e.g., writing to per-shop billing state, order records, inventory, or subscription state, or triggering per-shop side effects), this can lead to cross-tenant data corruption or unauthorized actions performed against another merchant's data — a High/Critical-adjacent cross-tenant boundary break, matching the "cross-tenant access" impact category.

### Likelihood Explanation
Moderate-to-high. It requires the attacker to first obtain at least one genuinely signed `(body, hmac)` pair — trivial to do by installing the target app on their own free development store and capturing any webhook the app receives (e.g., `app/uninstalled`, `orders/create` with attacker-controlled order data on their own store). No access to `api_secret_key`, access tokens, or the victim's credentials is required; only the ability to intercept/replay HTTP requests to the app's public webhook endpoint (a capability any unprivileged internet user or app-installing merchant has).

### Recommendation
Include the identity/routing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable string, or otherwise cryptographically bind them to the body before verification — e.g., construct `to_signable_string` as a canonical concatenation of these header values plus the raw body, rather than the raw body alone. Alternatively, cross-check the shop domain embedded in the payload (if present) against the header value, and reject mismatches.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. App receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker replays a POST request to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged, still valid because only `B` is signed)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic: orders/create` (unchanged or forged)
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`.
5. `ShopifyAPI::Webhooks::Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` and dispatches it to the app's handler, which now believes the (attacker-controlled) data belongs to `victim-shop.myshopify.com`.
