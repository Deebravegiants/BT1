### Title
`Registry.process` trusts the unsigned `shop-domain` header, not covered by the HMAC, to route webhook data to a tenant - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`Webhooks::Registry.process` validates a webhook's authenticity with `Utils::HmacValidator.validate(request)` [1](#0-0) , but the HMAC signature only ever covers the raw request body (`to_signable_string` returns `@raw_body`) [2](#0-1) . The `shop-domain` header, which the gem exposes via `Request#shop` and which is handed to the app's handler as the tenant identifier, is read directly from an HTTP header and is never included in the signed material [3](#0-2) .

### Finding Description
`Utils::HmacValidator.validate` recomputes an HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` value using `OpenSSL.secure_compare` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` is simply `@raw_body`, and `hmac` is decoded from the `X-Shopify-Hmac-Sha256` header [5](#0-4) . Only the body bytes are bound to the signature — the `shop`, `topic`, `api_version`, and `webhook_id` fields are parsed straight out of HTTP headers with no cryptographic binding at all [6](#0-5) .

`Registry.process` then does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [1](#0-0) 

This is the exact "field acted on but not covered by the HMAC" pattern: the gem treats a signed request as fully authenticated and then forwards `request.shop` (an unsigned header) to the merchant-facing handler as the trusted tenant identifier for that payload. The equality the code implicitly assumes but never enforces is:

`shop_header == shop_that_actually_produced(raw_body_signed_with_hmac)`

Nothing in `Request` or `Registry` checks that equality; the gem simply parses the header and passes it along.

### Impact Explanation
Any entity capable of obtaining a validly-signed webhook for **their own shop** (an unprivileged internet user who installs the app on a shop they control) can capture the `(raw_body, hmac)` pair, which remains valid for that body forever regardless of which `shop-domain` header accompanies it. By replaying that body with a different `X-Shopify-Shop-Domain` header value (e.g. a victim's shop domain), the request still passes `HmacValidator.validate` — the signature check only looks at the body — while `Registry.process` reports the payload to the handler as if it belongs to the victim shop. Any app logic keyed off `WebhookMetadata#shop` (e.g. updating merchant records, triggering data sync, or de-provisioning/redacting a "shop/redact" webhook for a shop the attacker doesn't own) can be misdirected into acting on the wrong tenant — a cross-tenant integrity issue reachable purely through this gem's own webhook-processing API.

### Likelihood Explanation
Requires: (1) the ability to trigger at least one genuinely-signed webhook for a shop the attacker controls (trivial — install the app, perform an action that fires a webhook), (2) the ability to deliver an HTTP POST to the app's webhook endpoint with attacker-chosen headers (typically satisfied since the endpoint is a public HTTP receiver) and (3) the app relying on `Request#shop`/`WebhookMetadata#shop` (the field this gem itself surfaces) to select the tenant to act on — which is exactly the documented and only way this library exposes shop identity for webhooks. No leaked secret, TLS interception, or privileged account is required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the signed material, or independently verify that the header-derived `shop` corresponds to a shop the app has an active installation/session for before dispatching to the handler. At minimum, document/require that consuming apps re-validate `WebhookMetadata#shop` against their own installation records rather than trusting it as authenticated by the HMAC check performed by this gem.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any subscribed webhook topic (e.g. `orders/create`), capturing the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H` (valid, since `HmacValidator.validate` only checks `HMAC(secret, B) == H`).
2. Attacker resends the identical body `B` and header `H` to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` accepts the request (all three required headers present) [7](#0-6) .
4. `Registry.process(request)` calls `HmacValidator.validate(request)`, which passes because it only checks `B` against `H` [8](#0-7) .
5. `handler.handle` is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [9](#0-8)  — the app now processes attacker-supplied data under the identity of a shop the attacker does not control/own, a signature check that never validated that binding.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
