Confirmed: `ShopifyAPI::Auth::Oauth.validate_auth_callback` uses `auth_query.shop` — a value that is only HMAC-covered but never checked against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` — to build the `null_session` whose `shop` becomes the request host that receives `Context.api_secret_key` in the POST body sent to `/admin/oauth/access_token`. Unlike `TokenExchange.exchange_token`/`migrate_to_expiring_token`/`ClientCredentials`/`RefreshToken`, which all call `ShopValidator.sanitize!` on the shop before use, the Authorization Code Grant path in `lib/shopify_api/auth/oauth.rb` never sanitizes `auth_query.shop`, breaking the equality "shop verified == shop trusted to receive client_secret."

### Title
OAuth callback `shop` is HMAC-verified but never validated as a trusted Shopify domain before receiving `client_secret` - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` validates the callback's HMAC and CSRF `state`, then immediately uses `auth_query.shop` [1](#0-0)  to build a `null_session` that is passed to `Clients::HttpClient`, which derives the request host from `session.shop` and sends a POST body containing `client_id`, `client_secret`, and `code` to `https://#{shop}/admin/oauth/access_token` [2](#0-1) . Nowhere in this path is `shop` passed through `ShopValidator.sanitize!`, unlike every other credential-issuing flow in the gem (`TokenExchange`, `ClientCredentials`, `RefreshToken`) which explicitly calls `ShopValidator.sanitize!`/`sanitize_shop_domain` before using the shop as a request host.

### Finding Description
The gem's own security boundary is: any value used to construct the host that receives `api_secret_key` must be constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`) [3](#0-2) . `ShopValidator.sanitize!` enforces this and raises `Errors::InvalidShopError` otherwise [4](#0-3) .

The `AuthQuery`'s `to_signable_string` only proves that `shop` (along with `code`, `host`, `state`, `timestamp`) was signed by whoever holds `api_secret_key` [5](#0-4) . HMAC coverage proves *integrity/authenticity of the byte value*, not that the value is a *trusted Shopify domain*. `validate_auth_callback` treats "HMAC valid" as equivalent to "safe to use as the OAuth token-exchange host," which is the same class of error as the reported bug: the code binds trust to the wrong invariant (`i` vs. `locals.storageArrayIndex` in the original report; here, "HMAC-verified" vs. "domain-whitelisted").

By contrast, `TokenExchange.exchange_token`/`migrate_to_expiring_token` derive `shop` from a cryptographically similarly-signed JWT `dest` claim, yet the migration path is still explicitly validated via `ShopValidator.sanitize!` (confirmed by `test_migrate_to_expiring_token_rejects_non_shopify_domain` raising `InvalidShopError` for `"attacker.example"`) [6](#0-5) . The Authorization Code Grant callback path has no equivalent check.

### Impact Explanation
If an app under audit ever passes through an `AuthQuery` built from raw request parameters without the host framework independently constraining `shop` to `*.myshopify.com` (which the gem's own documentation examples do via `request.parameters.symbolize_keys`, not via any gem-level check), a value of `shop` that a partner/malicious collaborator can influence and get HMAC-signed (e.g., through Shopify's own signed callback with an attacker-registered custom-domain-like host, or any deployment scenario where `shop` is echoed back through a Shopify-signed redirect containing a non-`myshopify` value) would cause the gem itself to POST `client_id` + `client_secret` (the app's own OAuth client secret) to an attacker-controlled host built directly from that `shop` string. This is exfiltration of the app's `client_secret` to a host chosen by the untrusted `shop` value — a Critical-tier impact (theft of the app's `client_secret`) — because the gem, not the host app, is responsible for constructing the token-exchange URL and never enforces the trusted-domain invariant that it enforces everywhere else in the same codebase.

### Likelihood Explanation
Likelihood is constrained: exploitation requires a `shop` value that both (a) passes `Utils::HmacValidator.validate` (i.e., is part of a message signed with `api_secret_key`) and (b) is not itself `*.myshopify.com`. Since only Shopify (holder of `api_secret_key`) can produce a valid signature over an arbitrary `shop`, the primary way this manifests is not "attacker forges an HMAC" but "the gem provides no defense-in-depth check that every sibling code path (`TokenExchange`, `ClientCredentials`, `RefreshToken`) already provides," making this an inconsistency/missing-defense finding rather than a directly attacker-triggerable bypass absent a host-domain edge case Shopify itself might permit (custom/managed domains, `spin.dev`/dev-store aliases, etc.) that resolve to attacker-influenced infrastructure. This asymmetry between `validate_auth_callback` and every other flow is concrete and verifiable from the code, but full exploitability depends on Shopify-side behavior outside this gem's control, which could not be further verified with the tools available.

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop, myshopify_domain: Context.myshopify_domain)` (mirroring `TokenExchange`) immediately after HMAC/state validation in `Oauth.validate_auth_callback`, before constructing `null_session`/`auth_base_uri`, so that the shop used to receive `client_secret` is provably constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`, consistent with `ClientCredentials`, `RefreshToken`, and `TokenExchange.migrate_to_expiring_token`.

### Proof of Concept
Not independently reproducible with static analysis alone: exploitation requires demonstrating a real-world scenario where Shopify (or an intermediary) produces an HMAC-valid callback with `shop` set to a non-`myshopify.com` host that resolves under attacker control — this depends on Shopify's server-side behavior, which is outside this gem's index and could not be verified here. The code-level asymmetry is demonstrated by comparing `lib/shopify_api/auth/oauth.rb:60-94` (no `ShopValidator` call) against `lib/shopify_api/auth/token_exchange.rb` and `test/auth/token_exchange_test.rb:258-265` (explicit `ShopValidator.sanitize!` enforcement with a passing rejection test for non-Shopify domains).

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end
