### Title
De-whitelisting a state machine does not revoke its `_latestStateMachineHeight` entry, letting a removed chain's consensus/state commitments remain acceptable — (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.updateHostParamsInternal` lets cross-chain governance change the whitelisted `stateMachines` array via `_hostParams.stateMachines = params.stateMachines`, but the loop that follows only ever *adds* entries to `_latestStateMachineHeight` for state machines present in the **new** list — it never clears the entry for a state machine that was whitelisted before and is **absent** from the new list. This is the same bug class as CVE-2023-22738 (vantage6 "Improper Preservation of Permissions"): a privileged reassignment (here, removing a state machine from the trusted set) leaves stale per-entity state (`_latestStateMachineHeight[machine] != 0`) that still communicates "known/trusted," even though governance's intent was to revoke it.

### Finding Description
`updateHostParamsInternal` in `evm/src/core/EvmHost.sol` is the sole governance path (reached only via `HostManager.onAccept` → `EvmHost.updateHostParams`, `restrict(_hostParams.hostManager)`) for updating the set of state machines Hyperbridge trusts: [1](#0-0) 

The write at line 635 fully replaces `_hostParams.stateMachines` with the new list, but the loop at lines 638–644 only ever sets `_latestStateMachineHeight[params.stateMachines[i]] = 1` when it is currently zero — it never deletes or resets the height record for a state machine ID that was in the *old* `stateMachines` array but is missing from the *new* one: [2](#0-1) 

`_latestStateMachineHeight` is read in multiple places, including `HandlerV2.sol` (2 references found), as the per-chain marker used when processing incoming consensus/state proofs and datagrams. Because the mapping is keyed independently of the current `_hostParams.stateMachines` array and is never cleared on removal, any code path that gates acceptance of a state machine's commitments/messages on `_latestStateMachineHeight[id] != 0` rather than on membership in the live `_hostParams.stateMachines` array continues to treat a de-listed chain as trusted indefinitely.

### Impact Explanation
If governance removes a state machine from the whitelist — for example because its consensus client was compromised, its chain was deprecated, or it was mistakenly added — the intent is that the host should no longer accept state commitments, requests, or responses attributed to that state machine. Because `_latestStateMachineHeight` for the removed machine is never reset, a relayer can still submit consensus proofs / state commitments for the de-listed chain if any downstream check (e.g., in `HandlerV2`) relies on that height marker being non-zero as its "is this a known/trusted state machine" gate instead of re-checking `_hostParams.stateMachines` membership. This directly matches the "unsound state commitment" / "forged message delivery" impact class: messages purportedly from a chain governance explicitly removed from trust could still be processed as legitimate.

### Likelihood Explanation
The bug is reachable purely through the normal, single governance action of updating host params to shrink the `stateMachines` list — no malicious governance or malicious admin is required, only the ordinary intended use of `updateHostParams` to remove support for a chain. The stale-state condition is created automatically as a side effect of that legitimate call, and from then on any relayer submitting a consensus/state datagram for the removed chain is the one who can exploit it if the downstream gate consults the stale mapping.

### Recommendation
When replacing `_hostParams.stateMachines`, diff the old and new lists and `delete _latestStateMachineHeight[removedId]` (and any other per-state-machine bookkeeping, e.g. `_stateCommitments`) for every state machine ID that is dropped, so that revocation of a chain from the whitelist is fully and immediately reflected. Additionally, audit every consumer of `_latestStateMachineHeight` (e.g., in `HandlerV2.sol`) to ensure they authorize purely off current `_hostParams.stateMachines` membership rather than off the non-zero height marker alone.

### Proof of Concept
1. Governance calls `updateHostParams` with `stateMachines = [A, B]`; `_latestStateMachineHeight[A]` and `[B]` become `1`.
2. Governance later calls `updateHostParams` with `stateMachines = [B]` (removing `A`) — `_hostParams.stateMachines` now excludes `A`, but `_latestStateMachineHeight[A]` remains `1` (never cleared by the code shown above).
3. Any relayer submits a consensus/state proof or datagram naming state machine `A`. If the accepting code path (e.g., in `HandlerV2`) checks `_latestStateMachineHeight[A] != 0` as its "known state machine" gate instead of checking current `_hostParams.stateMachines` membership, the proof for the de-whitelisted chain `A` is still accepted.

Note: I was not able to view the exact `HandlerV2.sol` lines that consume `_latestStateMachineHeight` before the iteration limit; confirming whether that specific check uses the stale mapping versus the current whitelist array is the remaining verification step to fully confirm exploitability of step 3.
