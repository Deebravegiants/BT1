### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC verified by `Utils::HmacValidator.validate` binds nothing but the payload bytes. [1](#0-0) 
The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are read directly from attacker-controllable HTTP headers and are never included in the signed string. [2](#0-1) 
Yet `Registry.process` treats `request.shop` as a trusted tenant identifier and hands it straight to the app's webhook handler after only checking the HMAC (which never covered `shop`). [3](#0-2) 

### Finding Description
The identity binding that should hold is:
`shop asserted to the handler (request.shop) == shop that actually produced this signed payload`

Because `Utils::HmacValidator.validate` only verifies `verifiable_query.to_signable_string`, and for webhooks that string is exactly `@raw_body` (nothing else), the HMAC does not bind the `shop-domain` header at all. [4](#0-3) [1](#0-0) 

The app's `api_secret_key` is shared across *all* shops/tenants that install the same app (it is a per-app secret, not a per-shop secret) — confirmed by the fact that `HmacValidator` always signs/verifies with `Context.api_secret_key`, with no per-shop key material anywhere in the flow. [4](#0-3) 

Consequently, any merchant who can install the app on their own store (an "unprivileged internet user" with respect to any other tenant of the app) can trigger a legitimate webhook for their own shop, capture the resulting `(body, hmac-sha256)` pair — which is valid under the app's single shared secret — and then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header (or `x-shopify-shop-domain`) with any other merchant's real store domain. `Registry.process` will accept it, because the HMAC check only validates the body, and will call the handler with `WebhookMetadata` claiming the event came from the victim shop. [3](#0-2) 

This is the same bug class as the BigBang finding: a value (`shop`) is *acted upon downstream* (used as the tenant key passed into the handler) but is not covered by the cryptographic check that is supposed to guarantee its integrity — analogous to USDO being minted/transferred based on an unverified/uncovered accounting step.

### Impact Explanation
This crosses a tenant boundary: an attacker who is a legitimate (but unprivileged, non-victim) merchant of the app can forge webhook events that the host application attributes to a different, arbitrary shop. Depending on how the host app's `WebhookHandler` uses `data.shop` (e.g., looking up/mutating that shop's records, billing, orders, GDPR data-request flows, app-uninstall handling), this enables cross-tenant data injection or state corruption without any credential belonging to the victim shop — matching the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
The prerequisite is trivial for a public app: install the app once on any store (including a free development store), receive one real webhook, capture its raw body and `hmac-sha256`/`shop-domain` headers, then send a raw HTTP POST with the same body/HMAC but a different `shop-domain` value. No secrets, tokens, or elevated privileges are required, and the vulnerable code path (`Utils::HmacValidator.validate` + `Registry.process`) is the exact validation logic shipped by this gem and documented as the entry point for verifying/dispatching webhooks (`docs/usage/webhooks.md`).

### Recommendation
Bind the shop identity to the signature check, not just the body:
- Do not treat `request.shop` (or `topic`/`webhook_id`) as trusted purely because the body HMAC validated.
- Require host applications (and provide a library-level helper) to cross-check `request.shop` against an existing, previously-established session/shop record before dispatching to the handler, rather than exposing it in `WebhookMetadata` as if it were verified.
- Where feasible, incorporate the shop domain into a secondary verification step (e.g., confirm the shop has an active app installation/session) before invoking `handler.handle`.

### Proof of Concept
1. Attacker installs the app on their own store `attacker-shop.myshopify.com` and triggers any subscribed webhook topic, capturing the raw POST body `B` and header `shopify-hmac-sha256: H` (valid because it's HMAC-SHA256(`B`, app's shared `api_secret_key`)).
2. Attacker sends a new POST to the app's webhook endpoint with:
   - body: `B` (unchanged)
   - `shopify-hmac-sha256: H` (unchanged, still valid since it only signs the body)
   - `shopify-shop-domain: victim-shop.myshopify.com` (attacker-supplied, arbitrary)
   - `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`: attacker-supplied values of choice.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `body` against `H`. [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is `victim-shop.myshopify.com`, even though that shop never sent this webhook. [6](#0-5)
