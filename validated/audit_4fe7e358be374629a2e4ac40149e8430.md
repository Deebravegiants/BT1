### Title
Webhook `shop-domain` header is trusted for tenant attribution without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies the HMAC over the raw body only, but exposes `shop` (and `topic`) from unauthenticated headers. `ShopifyAPI::Webhooks::Registry.process` passes this unauthenticated `shop` value straight into `WebhookMetadata` that is handed to the app's webhook handler as if it were an authenticated tenant identifier, without any check that binds the header to the signed bytes.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares an HMAC only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw request body: [2](#0-1) 

Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.), none of which are part of the signed content: [3](#0-2) 

`Registry.process` validates the HMAC (which only proves the body was produced with the app's shared `client_secret`) and then unconditionally trusts `request.shop` to identify the tenant the event belongs to, forwarding it to the app's handler: [4](#0-3) 

This is the same class of bug as the oracle report: a value used for a security-relevant decision (`getTokenValueOfEth` trusting `latestAnswer` without checking freshness/validity) is accepted without verifying that it is bound to the thing that was actually authenticated. Here, the equality that should hold is:
`shop-domain header == shop that produced/authorized the signed webhook body`
but the gem only proves:
`HMAC-SHA256(body, client_secret) == received signature`
It never proves the header-derived `shop` is the origin of that body. Since a single Shopify app shares one `client_secret` (and thus one HMAC key) across every installed merchant, any merchant/tenant that has installed the app can capture a legitimately-signed webhook (body + valid HMAC) delivered to their own endpoint, and resubmit it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a different, victim shop. The HMAC still validates (it only covers the body), so `Registry.process` accepts it and calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` (as returned by `Registry.process`) to select which merchant's session/data to operate on — which is exactly the documented usage pattern shown in `docs/usage/webhooks.md` — can be tricked into attributing a shop's webhook payload to another tenant. This is a cross-tenant boundary violation: an attacker-controlled shop can inject data, trigger side effects, or corrupt records that get associated with an arbitrary victim shop, purely by replaying a validly-signed webhook with a forged header. This matches the Critical "cross-tenant access" impact category in scope.

### Likelihood Explanation
Likelihood is high for any real-world usage of this gem's webhook API: obtaining a validly-signed body+HMAC pair only requires being a legitimate (even trial) merchant of the app — no secret leakage or privileged access is required. Modifying an HTTP header before resubmitting the webhook is trivial. The vulnerable code path (`Registry.process` → `Utils::HmacValidator.validate` → `WebhookMetadata`) is the gem's only supported mechanism for webhook verification, so any app following the documented pattern is exposed.

### Recommendation
Bind the shop (and ideally the topic) into the signed material, or otherwise cryptographically/authoritatively tie the header value to the verified request:
- Include `shop-domain` (and `topic`) in the HMAC-signed payload, or require the caller to separately verify that `request.shop` matches a shop with an active, previously-established session/webhook registration before trusting it.
- At minimum, document prominently (and enforce in `Registry.process`) that `request.shop`/`WebhookMetadata#shop` is unauthenticated header data and must be cross-checked by the host application against a known, previously provisioned shop record before being used for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (a normal, permitted installation).
2. Shopify sends a legitimate webhook to the app: body `B`, header `X-Shopify-Shop-Domain: attacker.myshopify.com`, header `X-Shopify-Hmac-Sha256: HMAC(B, client_secret)`.
3. Attacker captures this request and resends it to the app's webhook endpoint, replacing only the header:
   `X-Shopify-Shop-Domain: victim.myshopify.com`, keeping body `B` and the same valid `X-Shopify-Hmac-Sha256` value.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Utils::HmacValidator.validate` succeeds because it only checks `B` against the HMAC, per: [5](#0-4) 
5. `Registry.process` accepts the forged request and invokes the app's handler with `WebhookMetadata#shop == "victim.myshopify.com"`, even though the payload was never generated for that shop: [6](#0-5)
