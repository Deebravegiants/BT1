### Title
Webhook `shop` identity is trusted from an unauthenticated header while HMAC only covers the body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is handed to the host application's webhook handler from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `Registry.process` verifies only covers the raw request body. This breaks the identity binding `authenticated_bytes == identity_used_by_app`, since the `shop` value used to route/attribute the webhook is never part of the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)` before dispatching to the registered handler: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` computes the HMAC exclusively over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [3](#0-2) 

Meanwhile `shop` (and `topic`, `webhook_id`, `api_version`) are read directly from HTTP headers that are never included in the signed bytes: [4](#0-3) 

That unauthenticated `shop` value is then propagated as trusted tenant identity into `WebhookMetadata`, which is exactly what the host handler receives and is expected to key its per-merchant logic on: [5](#0-4) [6](#0-5) 

The identity binding the gem should enforce is: `hmac_valid(secret, body) == true` implies `shop == the shop that produced body`. Instead the gem's guarantee collapses to `hmac_valid(secret, body) == true` implies only `body` is authentic; `shop` is taken on faith from the header. Any two requests with identical bodies but different `X-Shopify-Shop-Domain` headers pass verification identically, so the binding `shop_authenticated == shop_used_by_app` does not hold.

### Impact Explanation
Because the app's `client_secret`/`api_secret_key` is shared by Shopify across every shop that has installed the app, a merchant who has legitimately installed the app on their own store can generate a validly-HMAC-signed webhook body (e.g. by creating/updating a product, order, or customer with attacker-chosen field values) and capture the resulting `X-Shopify-Hmac-Sha256` header. Since that signature depends only on body bytes, the attacker can replay the identical body/HMAC to the app's webhook endpoint while substituting a different `X-Shopify-Shop-Domain` header naming a victim shop. `Registry.process` will accept it (HMAC matches) and hand the host application a `WebhookMetadata` whose `shop` claims to be the victim tenant while `body` is fully attacker-controlled. Any host logic that uses `data.shop` to select the tenant/session under which to persist or act on `data.body` (the pattern this gem's own docs/tests recommend, e.g. `test/webhooks/registry_test.rb`) will cross the tenant boundary, letting one merchant inject or corrupt data attributed to another merchant's store. This matches the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (even trial/free) installer of the target app on their own shop — no privileged credentials, secrets, or social engineering are needed. Triggering a webhook with attacker-chosen body content on one's own store and replaying it with a modified shop header is straightforward and fully reachable through this gem's public `Webhooks::Request`/`Webhooks::Registry.process` API.

### Recommendation
Bind the trusted shop identity to the signed payload instead of an unauthenticated header: include the shop domain in the signable string used for HMAC computation (if Shopify's signature scheme allows it), or require the host application to independently verify that `request.shop` corresponds to a shop with an active, previously-established session/installation before trusting `WebhookMetadata.shop`, and document this requirement prominently since the gem currently presents `shop` as if it were verified.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a store they control), obtaining legitimate access.
2. Attacker triggers a webhook event (e.g. `products/update`) with a body they fully control (product title/price/etc.), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends — this HMAC is valid because it is computed only over the body with the shared `api_secret_key`.
3. Attacker resends this exact body and HMAC header to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [7](#0-6) , which passes because it only checks `request.to_signable_string` (the body) — the `shop` header value is never included in the check.
5. The handler receives `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim-shop.myshopify.com"` and `body` fully attacker-controlled, and the host app processes attacker data under the victim tenant's identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
