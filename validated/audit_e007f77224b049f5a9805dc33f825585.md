### Title
User-controlled swap route executes attacker-chosen contract calls inside the signer's authorization tree, draining wallet funds beyond the routed amount - (File: contracts/controller/src/strategies/swap.rs)

### Summary
CVE-2024-55662 is a code-injection flaw: a normal user can submit content (`ExtensionCode.ExtensionClass` description) that the platform evaluates as a program with elevated (`programming`) rights. The analog in XOXNO Lending is the `swap`/`swap_xdr` argument accepted by the controller strategy entrypoints (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`): an opaque, user-supplied program that the swap router executes literally, dispatching calls to whatever pool/token addresses the payload names. Because those venue calls run while the caller's `require_auth` tree is active, a route can name an attacker-controlled "pool" that issues `token.transfer(victim, attacker, amount)` against any token the victim holds — recorded as a legitimate child of the victim's signed authorization and executed if the victim signs the simulated tree.

### Finding Description
`swap_collateral` accepts a raw `StrategySwap` blob from the caller and forwards it verbatim: `require_authorized_caller` only proves the caller owns/delegates the account, and the `swap` bytes are never inspected before being handed to the router ( [1](#0-0) ). `swap_tokens` authorizes exactly one input transfer to the router and calls `router.execute_strategy(&controller, &amount_in, swap)` under the flash guard, with no validation of which addresses the route will invoke ( [2](#0-1) ). The only post-execution checks are measured controller balance deltas (`RouterOverspend`, `NoSwapOutput`) — nothing bounds what payload-named contracts do elsewhere in the call tree ( [3](#0-2) ).

The threat model states the exposure explicitly: "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization. A token transfer that such code makes from the caller is recorded by an honest simulation as a child of the caller's authorization entry, and it executes if the caller signs that tree. The loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" ( [4](#0-3) ). The test harness contains a working exploit: `RogueHopPool.swap` calls `token.transfer(alice → attacker, WALLET_BALANCE)`, and `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` proves the stolen transfer is recorded under Alice's `swap_collateral` auth entry and executes, leaving `wallet(alice) == 0` while the strategy itself still returns a fair output and passes all risk gates ( [5](#0-4) , [6](#0-5) ).

### Impact Explanation
Theft of user funds. Any token in the victim's wallet (not just the swap input or the position's collateral) can be transferred to the attacker within the same transaction, sized up to the victim's full balance. The strategy output is fair and the account ends healthy, so no on-chain check (`SlippageExceeded`, `RouterOverspend`, `NoSwapOutput`, final HF) detects or bounds the loss. All strategy entrypoints that take a route (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`) and the standalone `execute_strategy` path share the exposure.

### Likelihood Explanation
An unprivileged attacker needs only to get a victim to sign a strategy transaction carrying a poisoned `routeXdr` — e.g., via a malicious quoting frontend, a spoofed route in a shared "compose this swap" payload, or any off-chain channel that delivers routes. On-chain everything is permitted by design: there is no venue allowlist, no payload introspection, and the injected transfer appears as a normal child authorization that simulation produces automatically. The only mitigation is client-side discipline (decode the route and refuse auth trees with unexpected children), which the codebase itself documents as an obligation the contracts do not enforce. Likelihood hinges on victim signing behavior rather than any protocol gate, but the reachable loss is unbounded relative to the routed amount.

### Recommendation
Treat the route as untrusted code and constrain what it can do with the caller's authority:
- In `swap_tokens`, scope the authorization surface so nothing outside the declared `token_in`/`token_out` can ride the caller's auth tree where the controller is `sender` — the controller path already self-authorizes only the input transfer, but the direct `execute_strategy` path and any contract that is `sender` should never sign a tree containing children it did not pre-declare.
- Enforce a venue/pool allowlist or hash-pin approved adapter targets in the router so payload-named addresses cannot be arbitrary contracts (the "unallowlisted route venues" design is what makes the injection possible).
- In SDK/wallet integrations, hard-require `verifyRoutePayload`-style checks: decode `swap_xdr`, enumerate every `assets` entry and invoked contract, and reject any simulated auth tree whose root has children beyond the single input `transfer`.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`. Attacker deploys `RogueHopPool` whose `swap()` executes `token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount)` ( [7](#0-6) ). A route naming that pool is submitted to `controller.swap_collateral(alice, account_id, USDC, SWAP_IN, ETH, route)`; simulation records `token.transfer(alice, attacker, WALLET_BALANCE)` as a child of Alice's `swap_collateral` auth entry; once she signs that tree, the transfer executes and her unrelated wallet token is fully drained while she still receives `FAIR_OUT_ETH` collateral and the account passes its risk check ( [8](#0-7) ).

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
