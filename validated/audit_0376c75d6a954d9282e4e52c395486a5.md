### Title
Excess native token sent to `EvmHost.dispatch()`/`fundRequest()` is not refunded to the caller and becomes permanently locked - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept native token payment and swap it for the exact `feeToken` amount needed via Uniswap V2, but none of them forward the unused native-token change back to the original caller — mirroring the M-12 "excess ETH not refunded" bug class.

### Finding Description
In `dispatch(DispatchPost memory post)`, when `msg.value > 0` the host swaps the entire `msg.value` for an exact amount of `feeToken` (`post.fee`) using the local Uniswap V2 router, with the swap output recipient set to `address(this)`: [1](#0-0) 

The standard `IUniswapV2Router02.swapETHForExactTokens` implementation refunds any unused ETH to `msg.sender` of that call. Here, the caller of the router is `EvmHost` itself (`address(this)`), not the end user who invoked `dispatch()`. Consequently, any ETH sent in excess of what the swap consumes for `post.fee` is refunded into `EvmHost`'s own balance rather than back to the original dispatcher/module. There is no subsequent code in `dispatch()` that computes leftover ETH and forwards it to `_msgSender()` or `post.payer`.

The identical pattern is repeated in `dispatch(DispatchGet memory get)`: [2](#0-1) 

and in `fundRequest(bytes32 commitment, uint256 amount)`: [3](#0-2) 

By contrast, other payable entry points in this same codebase (e.g. `IntentGatewayV2.placeOrder`/`fillOrder`, `ExtrinsicIntents._cancelFromSource`) explicitly track `msgValue` and call `_sendValue(msg.sender, msgValue)` to refund unspent native tokens: [4](#0-3) [5](#0-4) 

`EvmHost`'s three payable dispatch/fund entry points lack this same refund logic despite doing an identical "swap for exact output, may leave dust" operation.

### Impact Explanation
Any unprivileged caller (an app module dispatching a POST/GET request, or anyone funding a pending request) who overestimates the ETH needed to cover the Uniswap swap for `feeToken` will have the excess permanently locked inside `EvmHost`. Since fee estimation in production must rely on off-chain quotes (the docs explicitly warn against calling `quote()` on-chain due to sandwich risk) and Uniswap prices move between quote time and execution time, users are practically forced to send a buffer above the exact required amount, guaranteeing dust loss on every native-token dispatch. There is no user-facing withdrawal path for this stranded ETH in `EvmHost`; it is not tracked per-user and can only be recovered, if at all, by protocol governance sweeping the host's balance — not by the depositor. This is a concrete permanent freezing-of-funds condition affecting a core, frequently used, unprivileged code path (every native-token-paid POST/GET dispatch and fee top-up).

### Likelihood Explanation
High. This affects the default/common flow documented as "Native Token Payment" for dispatching messages, and every call where `msg.value` isn't matched exactly to the Uniswap-quoted amount triggers the loss. Given price volatility and the explicit guidance to overestimate off-chain, overpayment is the expected common case, not an edge case.

### Recommendation
In `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, capture `EvmHost`'s native balance before and after the `swapETHForExactTokens` call (or use `getAmountsIn` to compute the exact ETH needed and revert on mismatch is not sufficient by itself), and forward any residual ETH back to `_msgSender()` (or `post.payer`) via a safe ETH transfer, consistent with the refund pattern already used in `IntentGatewayV2` and `ExtrinsicIntents`.

### Proof of Concept
1. A user (or app contract) calls `dispatch(post)` with `msg.value = X` where `X` exceeds the ETH amount required to swap for `post.fee` units of `feeToken` (e.g., due to slippage buffering recommended by the docs, or a price move between off-chain quoting and on-chain execution).
2. Inside `dispatch`, `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` executes; the router computes `amounts[0] < msg.value`, performs the swap, and refunds `msg.value - amounts[0]` ETH to its caller, i.e., `address(this)` (`EvmHost`).
3. `dispatch()` returns without ever inspecting or forwarding this refunded ETH; `EvmHost`'s native balance permanently increases by the difference, with no way for the original caller to reclaim it.
4. Repeating this for every native-token dispatch/fundRequest call accumulates locked ETH inside `EvmHost` indefinitely.

```text
    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                post.fee, path, address(this), block.timestamp
            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }
```
