## Title
Missing `erc_decimals >= local_decimals` enforcement in `pallet-hyper-fungible-token::send` enables unbacked-mint on the destination EVM token - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token` defines an error variant `ErcDecimalsBelowLocal` documented as "Configured ERC decimals are less than the local asset's decimals; precision conversion requires erc_decimals >= local_decimals" [1](#0-0) , but the decimal-conversion helpers used by `send()` silently rely on `saturating_sub` rather than enforcing that invariant.

### Finding Description
The scaling helper used when a user calls `send()` to bridge tokens out to an EVM `HyperFungibleToken` contract is: [2](#0-1) 

`10u128.pow(erc_decimals.saturating_sub(local_decimals))` becomes `10^0 = 1` whenever `erc_decimals <= local_decimals`, instead of down-scaling the amount. In `send()`, the pallet escrows/burns `params.amount` denominated in the *local* asset's decimals [3](#0-2) , then computes `erc20_amount = convert_to_erc20(amount, erc_decimals, decimals)` and puts that raw value straight into `Message.amount`, which is dispatched to the destination chain [4](#0-3) .

On the EVM side, `HyperFungibleToken.onAccept` performs **no decimal rescaling at all** — it decodes `Message.amount` and mints it verbatim: `_mint(beneficiary, message.amount)` [5](#0-4) .

The system is documented to work correctly only when the EVM side has *more* decimals than the local asset (e.g., "BRIDGE is 12 decimals on nexus... pallet scales by 10^6" with an 18-decimal EVM contract) [6](#0-5) . If `register_token`/`update_token` (both `CreateOrigin`-gated) ever configure a `(local_asset, chain)` pair whose recorded EVM `erc_decimals` is *less than or equal to* the local asset's decimals — whether by governance misconfiguration or because the local asset's decimals are later changed via `pallet-assets` — `convert_to_erc20` stops down-scaling. The full, un-scaled `local_amount` (denominated in the finer local precision) is then interpreted by the EVM contract as if it were already in the coarser `erc_decimals` precision and minted 1:1. Since the escrow/burn on the source chain is for the correctly-scaled local amount but the destination mint uses the un-scaled raw integer, the destination contract mints `10^(local_decimals - erc_decimals)` times more tokens than were actually locked/burned — a straightforward unbacked-mint, directly analogous to Haven Protocol's range-proof-validation gap that let mint amounts exceed what was actually escrowed.

Unlike the analogous `HftError::ErcDecimalsBelowLocal` error variant that exists in the codebase (signaling the authors were aware of this precision-direction hazard), no code path in `send()`, `on_accept`, or `on_timeout` in `modules/pallets/hyper-fungible-token/src/module.rs`/`lib.rs` actually returns or checks that error before calling `convert_to_erc20`/`convert_to_balance` — it appears to be declared but unused (confirmed only via `grep` on the error name landing solely inside its own `lib.rs` declaration; I could not fully confirm inside the remaining iteration budget whether a check exists elsewhere in the crate, e.g. in `register_token`/`update_token`, since I ran out of tool calls before reading those functions in full).

### Impact Explanation
If reachable (i.e., if no check on `erc_decimals >= local_decimals` exists in `register_token`/`update_token`), this is a direct unbacked-mint / permanent value-freezing bug: any user can call the unprivileged, signed `send()` extrinsic and cause the destination `HyperFungibleToken` contract to mint many orders of magnitude more tokens than were escrowed/burned on the source chain, draining the peer contract's backing value and inflating supply — the same class of impact as Haven Protocol's incident (unbacked mint from a validation gap).

### Likelihood Explanation
Reachability depends entirely on governance (`CreateOrigin`) registering or updating a `(asset, chain)` precision pair with `erc_decimals <= local_decimals`. This requires either: (a) a configuration mistake by the operator (plausible, since decimals values are attacker-independent metadata entered by a privileged but fallible party, not protected by any on-chain sanity check I could locate), or (b) the local asset's `decimals()` (read dynamically via `fungibles::metadata::Inspect` for non-native assets) being changed after `Precisions` was set for a smaller value. Because I could not conclusively verify (in the remaining budget) whether `register_token`/`update_token` reject such configurations, likelihood is **uncertain** — it hinges on a code path I was unable to fully inspect before running out of iterations.

### Recommendation
- Enforce `erc_decimals >= local_decimals` at the point `Precisions` is written (in `register_token` and `update_token`), returning `Error::<T>::ErcDecimalsBelowLocal` instead of leaving the check unused.
- Alternatively/additionally, make `convert_to_balance`/`convert_to_erc20` fallible and return an explicit error (rather than silently saturating to a no-op scale factor) whenever `erc_decimals < local_decimals`, so a misconfiguration cannot silently produce an over-mint.
- Add a regression test mirroring `BridgeTokenTest.t.sol`'s decimal-scaling tests but for the `erc_decimals < local_decimals` case, asserting the call is rejected rather than producing an inflated mint.

### Proof of Concept
1. Governance calls `register_token`/`update_token` to register a non-native local asset with `local_decimals = 18` (via `pallet-assets`) and sets `Precisions::<T>::insert(asset_id, dest_chain, 6)` (misconfigured/erc_decimals lower than local).
2. A user calls `send(SendParams { asset_id, destination: dest_chain, amount: 1_000 * 10^18, .. })`. The pallet burns `1000 * 10^18` local units [7](#0-6) .
3. `convert_to_erc20(1000 * 10^18, erc_decimals=6, local_decimals=18)` computes `10u128.pow(6u8.saturating_sub(18) as u32) = 10^0 = 1`, so `erc20_amount = 1000 * 10^18` unchanged [2](#0-1) .
4. The message is dispatched with `amount = 1000 * 10^18` to the destination `HyperFungibleToken` contract, which — regardless of its own `decimals()` — calls `_mint(beneficiary, 1000 * 10^18)` verbatim [8](#0-7) , minting `10^12` times more raw token units than the 1000-token amount actually escrowed/burned on the source chain.

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
