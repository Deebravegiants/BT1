The cooldown-bypass bug class ("a field is acted on but never covered by the integrity check, so it can be manipulated independently of what was verified") maps directly onto how `ShopifyAPI::Webhooks::Registry` and `ShopifyAPI::Webhooks::Request` treat the `shop` identity field.

### Title
Webhook `shop` identity is trusted for tenant attribution but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `Utils::HmacValidator.validate` verifies the signature exclusively against that body. The `shop`, `topic`, `webhook_id`, and `api_version` fields are all read straight from unauthenticated HTTP headers and are never included in the signed material, yet `Registry.process` forwards `request.shop` unchanged into `WebhookMetadata`, which the gem's own documentation instructs apps to use as the tenant/shop identifier for all downstream processing.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` value. For webhook requests, `to_signable_string` is defined as: [1](#0-0) 
This means the HMAC binds only the raw JSON body — not the `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, or `x-shopify-api-version` headers, which are parsed unauthenticated here: [2](#0-1) 

`Registry.process` validates only this body HMAC, then immediately trusts `request.shop` (a header value) to construct the metadata passed to the app's handler: [3](#0-2) 

The equality that should hold is: *shop bytes covered by the HMAC == shop bytes acted upon by the handler*. Instead, the shop byte acted upon (`request.shop`, a header) is disjoint from the byte range actually covered by the HMAC (`@raw_body` only). The gem's own documentation explicitly instructs integrators to treat `data.shop` as the authoritative shop/tenant identifier for routing work (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), reinforcing that this field is meant to be trusted as an identity binding, not just informational: this guidance lives in the gem's shipped docs, not host-app-specific logic. [4](#0-3) 

### Impact Explanation
An unprivileged user who legitimately controls Shop A can trigger a real Shopify event (e.g. create an order) to receive an authentically HMAC-signed webhook POST for Shop A. Because the signature covers only the raw body, that same signed body/HMAC pair remains valid if replayed to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to Shop B (a victim tenant). `Utils::HmacValidator.validate` will still return `true` (body unchanged), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to Shop B while carrying Shop A's payload. Any app that follows the gem's documented pattern of keying tenant-scoped work (session/access-token lookup, data writes, job dispatch) off `data.shop` performs those actions against the wrong tenant — a cross-tenant confusion driven entirely by an unauthenticated header value.

### Likelihood Explanation
Exploitation only requires an attacker who already owns/operates one shop that installed the app — no access token, `api_secret_key`, or leaked credential is needed. Generating a genuine signed webhook is trivial (perform an ordinary action on their own store) and replaying it with a modified header is a single HTTP request.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material, or independently cross-check the header `shop` against a shop identifier embedded in the verified body/payload before treating it as authoritative for tenant routing. At minimum, document prominently that `data.shop` is unauthenticated header data and must not be used alone for tenant-sensitive lookups.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com`, app installed there.
2. Attacker performs an action that triggers a real webhook; captures the raw body `B` and the valid `X-Shopify-Hmac-Sha256` header `H` computed over `B` with the app's `api_secret_key`.
3. Attacker POSTs to the app's webhook endpoint with body `B`, header `H` unchanged, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `B`/`H`: [5](#0-4) 
5. `Registry.process` invokes the app handler with `shop: "victim-shop.myshopify.com"` and the attacker's own body, causing any tenant-keyed logic to operate against the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
