Audit Report

## Title
Missing `return` after failed email-claim extraction in OIDC token exchange allows session creation to proceed despite unverified/missing email - (File: `core/sessions/oidcauth/oidc.go`)

## Summary
`oidcAuthenticator.handleTokenExchange` type-asserts `claims["email"].(string)` and, on failure, logs an error and writes a 500 response body but does not `return`, unlike every other error branch in the function. Execution falls through, maps a role from group claims, inserts a new `oidc_sessions` row with `user_email=""`, sets the session cookie, and overwrites the response with a 200 success JSON, granting a fully authenticated session despite the missing email claim.

## Finding Description
In `handleTokenExchange` (`core/sessions/oidcauth/oidc.go:163-276`), all prior failure checks (`ShouldBindJSON`, state mismatch, `Exchange`, missing `id_token`, `Verify`, `Claims`, `ExtractIDClaimValues`) correctly `return` after writing an error response. The `email, ok := claims["email"].(string)` check at line 226 breaks this pattern: on `!ok` it calls `c.String(http.StatusInternalServerError, ...)` but has no `return`, so execution continues to `IDClaimsToUserRole` (role derived from `idClaims`, independent of `email`), the `INSERT INTO oidc_sessions` with `strings.ToLower(email)` (empty string), `ginSession.Set(webauth.SessionIDKey, clSession.ID)`, `ginSession.Save()`, and the final `c.JSON(http.StatusOK, ExchangeTokenResponse{Success: true})`, which overwrites the earlier 500 status/body. The identity-verification failure signal is checked and logged but never enforced.

## Impact Explanation
A completed, legitimately signed OIDC login whose ID token simply omits the `email` claim (common unless the `email` scope/claim is explicitly configured) still results in a valid, cookie-backed `oidc_sessions` row and a 200 success response, with role determined solely by group claims (potentially Admin). `AuthorizedUserWithSession` will authenticate this session and return a `User{Email: "", Role: <mapped role>}`, which is then used for node API authorization — an authentication logic bypass where the email-identity check is effectively unenforced. Additionally, because `user_email=""` is shared across all users hitting this path, `ClearNonCurrentSessions` keyed on `lower(user_email)` could delete unrelated users' sessions, causing cross-user session disruption.

## Likelihood Explanation
Any unprivileged client that can complete the standard OIDC redirect/exchange handshake against the configured IdP can trigger this deterministically whenever the IdP's ID token claims lack `email` — no malicious IdP, network-layer, or privileged access required. This is a purely deterministic, missing-`return` control-flow bug.

## Recommendation
Add `return` immediately after writing the error response in the `!ok` branch, matching all other error branches in the function:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```
Also consider explicitly rejecting `email == ""` before persisting the `oidc_sessions` row to prevent multiple users sharing the same empty-email key.

## Proof of Concept
1. Configure Chainlink OIDC auth against an IdP/test provider whose signed ID token includes a group claim satisfying `AdminClaim()`/`EditClaim()` etc. but omits the `email` claim.
2. As an unprivileged client, initiate the OIDC login flow, complete the provider redirect, and POST to the token-exchange endpoint backing `handleTokenExchange` with the resulting `code`/`state`.
3. Observe: `claims["email"].(string)` fails (`ok=false`), a 500 body is written but not returned; `IDClaimsToUserRole` succeeds from group claims; a row is inserted into `oidc_sessions` with `user_email=''`; `ginSession.Save()` persists a valid session cookie; final response is `200 OK` `{"success": true}`.
4. Using the returned session cookie, call any node API endpoint gated by `AuthenticateBySession`/`AuthorizedUserWithSession` and confirm it authorizes with the mapped role despite the empty/unverified email.
