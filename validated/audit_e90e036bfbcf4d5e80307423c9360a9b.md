This closes the loop: `computeIntentHashHashBytes` in `packages/intents-sdk/src/intents/intent-hash.ts` hashes the exact `signed.payload` string that was actually signed (for webauthn, the raw `payload` string produced by `makeWebAuthnMultiPayload`), not a re-parsed/re-derived version, and there is a test with a `café` (non-ASCII) memo confirming the hash matches the byte-exact signed string. [1](#0-0) [2](#0-1) 

## Analysis of the claimed vulnerability

The question hypothesizes that `JSON.stringify(payload, null, 2)` (pretty-print, used for ERC-191/TON/Tron/Stellar in `makeSwapMessage`) versus compact `JSON.stringify(payload)` (used by `IntentSignerViem`/`IntentSignerNEP413`, and also computed as `payloadSerialized` for WEBAUTHN in the same function) could produce two different byte representations for the same logical payload, letting a wallet-displayed JSON diverge from what's hashed/executed.

This does not hold. `JSON.stringify`'s `indent` parameter only inserts additional *insignificant whitespace* between structural tokens (after `:`, `,`, `{`, `[`); it does not alter how characters inside string values are escaped. Quotes, `\n`, `\u2028`, and other special characters within a string value are escaped identically by the JSON spec regardless of the `space` argument. This is directly confirmed in the repo's own tests: in `packages/internal-utils/src/utils/messageFactory.test.ts`, both the compact `NEP413` message and the pretty `ERC191`/`STELLAR`/`TON_CONNECT`/`TRON` messages for the identical `innerMessage`/`payload` decode to byte-identical field values — only whitespace differs. [3](#0-2) [4](#0-3) 

Concretely, for `WEBAUTHN`, the SDK signs `payload: payloadSerialized` (compact `JSON.stringify(payload)`), and separately exposes `parsedPayload: payload` for UI convenience — but the signature and challenge are computed strictly over `payloadSerialized`, and `makeWebAuthnMultiPayload` simply forwards `signature.signedData.payload` unchanged into the `MultiPayload` that gets hashed/verified. [5](#0-4) [6](#0-5) 

For `IntentSignerViem`/`IntentSignerNEP413`, the same `JSON.stringify(...)` call both produces the signed message and is what gets parsed by the contract and by `computeIntentHash`; there is no second, differently-formatted serialization step anywhere in that path. [7](#0-6) [8](#0-7) 

`computeIntentHash`/`computeIntentHashHashBytes` operate on the already-signed string/object fields of the `MultiPayload` (e.g., `computeSignedNep413Hash` re-Borsh-serializes using `payload.message` verbatim, and the ERC-191 test case includes a non-ASCII `café` memo and reproduces the exact same hash the contract itself would compute via `simulate_intents`), so there is no divergence between what's displayed, what's signed, what's hashed, and what the contract parses. [9](#0-8) 

No vulnerability found for this question.

export function makeWebAuthnMultiPayload(
	userInfo: { userAddress: string; userChainType: AuthMethod },
	signature: WebAuthnSignatureData,
): MultiPayload {
	assert(
		userInfo.userChainType === "webauthn",
		"User chain and signature chain must match",
	);

	const { curveType, publicKey } = parsePublicKey(userInfo.userAddress);

	return {
		standard: "webauthn",
		payload: signature.signedData.payload,
		public_key: formatPublicKey(publicKey, curveType),
		signature: formatSignature(
			extractRawSignature(signature.signatureData.signature, curveType),
			curveType,
		),
		client_data_json: new TextDecoder("utf-8").decode(
			signature.signatureData.clientDataJSON,
		),
		authenticator_data: base64urlnopad.encode(
			new Uint8Array(signature.signatureData.authenticatorData),
		),
	};
}

export async function computeSignedNep413Hash(
	signed: Extract<MultiPayload, { standard: "nep413" }>,
): Promise<Uint8Array> {
	// For NEP-413, we need to reconstruct the original message that was hashed
	const payload = signed.payload;

	return hashNEP413Message({
		message: payload.message,
		recipient: payload.recipient,
		nonce: Array.from(base64.decode(payload.nonce)),
		callback_url: payload.callbackUrl,
	});
}
