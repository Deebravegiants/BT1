### Title
`describeWithdrawal` reports `completed` status without verifying `withdrawal.data.amount` matches the signed withdrawal amount - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` matches a withdrawal from the PoA bridge indexer purely by `assetId` via `findMatchingWithdrawal`, and once `withdrawal.status === "COMPLETED"` it unconditionally returns `{ status: "completed", txHash: withdrawal.data.transfer_tx_hash }` without ever comparing `withdrawal.data.amount` to `args.withdrawalParams.amount`. The same pattern exists in the sibling implementation `waitForWithdrawalCompletion` in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`, which also returns success on `COMPLETED` status without any amount check.

### Finding Description
The broken equality is: **reported amount delivered == amount signed in the withdrawal intent (`args.withdrawalParams.amount`)**. In `describeWithdrawal` (poa-bridge.ts:313-343), the matching logic is: [1](#0-0) 

The withdrawal is located solely with `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` — a lookup keyed only on `assetId` (via `near_token_id`) — and once `status === "COMPLETED"`, the function returns `completed` with `withdrawal.data.transfer_tx_hash` as the sole payload. There is no read of `withdrawal.data.amount`, and no comparison against `args.withdrawalParams.amount` anywhere in this function or in its caller chain (`waitForWithdrawalCompletion` in `sdk.ts`, `createWithdrawalCompletionPromises`, etc.). The same gap exists in `waitForWithdrawalCompletion` (internal-utils), which returns `{ destinationTxHash, chain }` on `COMPLETED` status without checking amount either: [2](#0-1) 

None of the existing guards intercept this: `validateAddress`/`compareAddresses` only run at withdrawal-creation time in `validateWithdrawal`, not at status-polling time; `supports()` only screens `assetId`/`routeConfig`; there is no `FeeExceedsAmountError` or `getUnderlyingFee` check on the read path; and `matchesRequest`/the `assert` sanity checks in this file only validate `assetInfo != null`, never the payout amount. The bridge/indexer response is treated as authoritative for "completed" status with no reconciliation against the amount that was actually signed and intended.

### Impact Explanation
An integrator that relies on `sdk.processWithdrawal` → `waitForWithdrawalCompletion` → `describeWithdrawal` returning `status: "completed"` to mark a user's withdrawal as fully paid has no signal that the delivered amount (`withdrawal.data.amount`/effective payout implied by `transfer_tx_hash`) is less than `args.withdrawalParams.amount`. This is a status/hash misreport that can cause the integrator to credit the withdrawal as fully settled when only a partial amount was actually transferred, matching the "status or hash misreport making an integrator credit or refund twice" High-severity category (here materializing as under-crediting/failure to detect a shortfall, which for a user is effectively a loss of the un-reported difference). This is repeatable for every withdrawal processed through the PoA bridge route, since the amount field is simply never consulted in the completion-detection path.

### Likelihood Explanation
No attacker action against the SDK itself is required — the scenario needs the PoA bridge's off-chain indexer to report a `COMPLETED` withdrawal whose `data.amount` differs from what was signed (e.g., partial fill). This is plausible under normal operational conditions (partial relayer payouts, relayer bugs) and does not require exploiting any other SDK validation, since none of `validateWithdrawal`, `supports()`, or the intents contract's nonce/signature checks operate on this read/poll path at all — they only matter at creation time. Once the mismatched `COMPLETED` entry appears, every caller of `describeWithdrawal`/`waitForWithdrawalCompletion` for that withdrawal will silently accept it as fully completed, with 100% reproducibility given the described precondition.

### Recommendation
In `describeWithdrawal` (poa-bridge.ts) and `waitForWithdrawalCompletion` (internal-utils), after finding a `COMPLETED` withdrawal, compare `withdrawal.data.amount` (parsed as `BigInt`) against the amount actually expected/signed (`args.withdrawalParams.amount`, net of relayer fee as applicable). If they don't match, throw a dedicated invariant error (e.g., extending `PoaWithdrawalInvariantError`) instead of returning `status: "completed"`, so integrators are not misled into treating a partial payout as a full completion.

### Proof of Concept
```ts
// vitest, mocking only HTTP (poaBridge.httpClient.getWithdrawalStatus)
it("reports completed status even when payout amount is less than signed amount", async () => {
  const signedAmount = 100000n;
  const partialAmount = 50000n;

  vi.spyOn(poaBridge.httpClient, "getWithdrawalStatus").mockResolvedValue({
    withdrawals: [
      {
        status: "COMPLETED",
        data: {
          near_token_id: "usdt.omft.near",
          amount: partialAmount.toString(),
          transfer_tx_hash: "0xdeadbeef",
          chain: "eth",
        },
      },
    ],
  });

  const bridge = new PoaBridge({ envConfig, xrplRpcUrls: [] });

  const result = await bridge.describeWithdrawal({
    withdrawalParams: {
      assetId: "nep141:usdt.omft.near",
      amount: signedAmount, // the amount actually signed
      // ...other required fields
    },
    index: 0,
    tx: { hash: "sometxhash" },
  });

  // BEFORE fix: passes — status reported as "completed" despite amount mismatch
  expect(result.status).toBe("completed");

  // Equality under test (should hold but doesn't get checked):
  // withdrawal.data.amount (50000n) !== withdrawalParams.amount (100000n)
  // yet result carries no indication of this mismatch to the caller.
  expect(result).not.toHaveProperty("amount"); // no amount field exposed at all
});
```
