## Analog Found: Webhook Shop Identity Spoofing via HMAC Scope Gap

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines `to_signable_string` to return **only** the raw HTTP body: [1](#0-0) 

None of the identifying headers — `shop`, `topic`, `api_version`, `webhook_id` — are part of the signed content. Yet `shop` is read straight from an attacker-controllable HTTP header: [2](#0-1) 

`Registry.process` validates the HMAC over the request, then immediately trusts `request.shop` to build the tenant identity passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes/compares the signature purely against `verifiable_query.to_signable_string` (i.e. the body) using the app's single, shop-independent `Context.api_secret_key`: [4](#0-3) 

Because the same `api_secret_key` authenticates webhooks for *every* shop that has the app installed, and the `shop-domain` header is outside the HMAC scope, **any merchant who has legitimately installed the app** can capture a genuine `(raw_body, hmac)` pair from their own store's webhook traffic and replay it to the app's public webhook endpoint with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header rewritten to name a **different, victim** shop. `Utils::HmacValidator.validate(request)` still returns `true` (the body/HMAC pair is authentic), so `Registry.process` dispatches the handler with `shop: <victim-shop>` while the body content is attacker-controlled data from the attacker's own store.

**Identity binding broken:** `shop asserted in the unauthenticated header == shop cryptographically bound by the HMAC`. The gem enforces "HMAC(body) is valid" but never enforces "HMAC(body) was computed for *this* shop", so any authenticated body can be relabeled to any tenant.

### Impact Explanation
This lets an unprivileged app-installing merchant inject arbitrary webhook events/data that the host application will process as if it came from a different tenant, causing cross-tenant data confusion/injection in any app that partitions storage or business logic by `WebhookMetadata#shop` — matching the Critical "cross-tenant access" bar. No `api_secret_key`, access token, or privileged access is required beyond ordinary app installation, which any internet user can do by installing the app on a store they control.

### Likelihood Explanation
High: installing a public/dev Shopify app and receiving at least one real webhook is a normal, unprivileged action. Capturing a valid `(body, hmac)` pair and replaying it with a different `shop-domain` header against the app's public webhook endpoint requires no additional secrets — only a basic HTTP client. This mirrors exactly the "field acted on but not covered by the HMAC" analog class.

### Recommendation
Bind the shop identity into the signed material or otherwise cryptographically tie it to the verified body — e.g., require host applications to cross-check `request.shop` against a store of shops that are known to have valid, active sessions/installations before trusting `WebhookMetadata#shop`, and document this requirement prominently, since the gem's `HmacValidator` cannot itself validate header-shop consistency without Shopify including it in the signature.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, triggering a genuine webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared `api_secret_key`), `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the exact same body `B` and HMAC `H` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers/body normally.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(B) == H`.
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, causing the host app to process attacker-controlled `B` under the victim tenant's identity.
