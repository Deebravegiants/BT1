### Title
Unauthenticated `CallDispatcher.dispatch()` lets anyone drain any native/token balance the shared dispatcher happens to hold - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch()` has no caller restriction whatsoever and executes attacker-supplied `Call[]` (arbitrary `to`/`value`/`data`) using whatever native ETH or ERC20 balance the dispatcher contract currently holds. The same `CallDispatcher` instance is shared across multiple apps (`IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken` — a single deployment is listed per chain on the contract-addresses pages), each of which transiently parks user/solver funds on it mid-transaction before sweeping them back. Because `dispatch()` is fully permissionless, this mirrors the CVE-2023-41899 bug class: a component meant to be invoked only by a trusted caller for a narrow purpose instead exposes an unauthenticated pass-through that lets an unprivileged actor reach and manipulate a resource (here, the dispatcher's live balance and approvals) it should never be able to touch directly.

### Finding Description
`CallDispatcher.dispatch()` is declared `external` with no modifier: [1](#0-0) 

Any address can call it directly, decode an arbitrary `Call[]`, and force the dispatcher to `call{value: call.value}(call.data)` to any contract with code, using the dispatcher's own balance (native or via `transferFrom`/pre-existing allowances on ERC20s it holds). There is no check that the caller is `IntentGatewayV2`, `HyperFungibleToken`, or `WrappedHyperFungibleToken`.

The dispatcher is used as a shared escrow-in-transit account by several apps:
- `IntentGatewayV2.placeOrder` transfers predispatch assets to `dispatcher`, invokes `dispatch(order.predispatch.call)`, then sweeps balances back with a second `dispatch(...)` call: [2](#0-1) 
- `IntentsBase._execute` similarly routes solver output through the dispatcher for postdispatch calldata and sweeps residual "dust" afterward: [3](#0-2) 
- `HyperFungibleToken.onAccept` forwards `message.data` to the same dispatcher after minting tokens: [4](#0-3) 

The project's own documentation flags the risk of this shared, stateful intermediary explicitly: *"Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution."* This confirms the dispatcher is expected to (and does) hold live, spendable balances/approvals between the moment funds land on it and the moment they are swept out.

Because `dispatch()` has no access control, any of the following windows can be exploited by an unprivileged party:
1. **Residual/dust balance**: any ETH or ERC20 dust left on the dispatcher (fee-on-transfer tokens, rounding, a partially-successful swap, or a transaction that reverts *after* funds land on the dispatcher but the revert doesn't apply — e.g., cross-app interleaving) is directly drainable by calling `dispatch()` with a `Call` that transfers the dispatcher's balance to an attacker address.
2. **Lingering ERC20 approvals**: if any `Call.data` in a legitimate flow sets an approval (e.g., `approve(router, amount)`) that is not fully consumed by the same-transaction swap (partial fill, slippage, or leftover allowance from a prior transaction), an attacker can call `dispatch()` with a `Call` that has the approved spender call `transferFrom(dispatcher, attacker, amount)` using the dangling allowance.
3. **Cross-app confusion**: because the dispatcher is a single shared singleton (not scoped per-app or per-call), a call originating from one app (e.g., `IntentGatewayV2`) that leaves the dispatcher holding value can be drained by an attacker racing a transaction that targets a completely different, unrelated app's flow, since `dispatch()` does not verify which app/context initiated the funding.

This is the same root cause as the CVE: a forwarding surface that is supposed to be reachable only by a trusted internal caller for a specific narrow action instead accepts and executes arbitrary attacker-controlled payloads against a resource (funds/approvals) it holds, with no verification of caller identity or intended scope.

### Impact Explanation
If the dispatcher ever holds a non-zero balance or a live/unused allowance between the funding step and the sweep step of any of the apps that use it (`IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`), any unprivileged actor can permanently steal those funds with a single `dispatch()` call. Given multiple integrated apps push tokens through the same dispatcher and the docs explicitly warn about "unlimited allowances," realistic operational conditions (partial swaps, fee-on-transfer tokens, slippage, race conditions between concurrent orders sharing the same dispatcher instance) create theft-of-funds exposure. This satisfies "concrete theft ... of funds" from the validation criteria.

### Likelihood Explanation
Reachable from a single, unprivileged, permissionless transaction — `dispatch()` takes no special role and any EOA/contract can call it at any time it detects (or can induce) a non-zero balance/approval on the dispatcher. No governance, admin, or relayer privilege is required; the attacker only needs to monitor the dispatcher's balance/allowances (trivially observable on-chain) and front-run/race with a `dispatch()` call.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a caller allowlist (e.g., `onlyRole`/`onlyOwner`-gated set of authorized gateway addresses), or make the dispatcher single-use/ephemeral per call (deploy a fresh minimal-proxy dispatcher per operation, or require the calling gateway to pass and verify a commitment tying the dispatch to its own in-flight transaction). At minimum, ensure the dispatcher never has a non-zero balance/allowance outside of the atomic call it services, and add reentrancy protection so a nested call cannot re-enter `dispatch()` mid-flow.

### Proof of Concept
1. Monitor the shared `CallDispatcher` deployment address (listed on `docs/content/developers/evm/contract-addresses/{mainnet,testnet}.mdx`) for a non-zero ETH/ERC20 balance or an outstanding ERC20 allowance resulting from any `IntentGatewayV2.placeOrder`/`fillOrder`, `HyperFungibleToken.onAccept`, or `WrappedHyperFungibleToken.onAccept` execution that left dust or an unconsumed approval (e.g., due to fee-on-transfer tokens or partial swap slippage).
2. As an unrelated, unprivileged address, call `CallDispatcher.dispatch(abi.encode(calls))` directly, where `calls` is a single `Call{ to: <token or approved spender>, value: 0, data: transfer/transferFrom(attacker, dust_amount) }` or `Call{ to: attacker, value: <eth_dust>, data: "" }`.
3. Because `dispatch()` performs no caller check, the call succeeds and the funds/allowance are transferred to the attacker, with no on-chain requirement that the caller be `IntentGatewayV2`, `HyperFungibleToken`, or any other legitimate integrator. [1](#0-0)

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
