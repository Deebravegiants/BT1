## Analysis Result

The `pallet-hyper-fungible-token` module exhibits the same bug class as the reported issue: an amount is converted using a scaling factor read from mutable on-chain storage, but the factor used at message dispatch time can differ from the factor read at message finalization time if that storage is updated while the cross-chain message is in flight. ### Title
Precision (`Precisions`/decimals) update mid-flight causes incorrect mint/refund amount in `pallet-hyper-fungible-token` - (File: `modules/pallets/hyper-fungible-token/src/module.rs`, `modules/pallets/hyper-fungible-token/src/lib.rs`)

### Summary
`pallet-hyper-fungible-token::send` converts a local balance into the ERC20-denominated amount that gets embedded in the dispatched ISMP message, using the `Precisions` storage entry and the local asset's decimals *at dispatch time*. However, `on_accept` (and `on_timeout`) on the *receiving* side re-derive the conversion factor by reading `Precisions::<T>::get(local_asset_id, source)` and the local asset decimals *at delivery time*, rather than using a factor fixed at the time the corresponding funds were locked/burned. If `update_token` (or `register_token`) changes a chain's configured `decimals` for an asset while a message is still in flight, the amount minted/unlocked to the beneficiary on finalization (or refunded on timeout) will not match the amount that was actually escrowed/burned when the transfer was initiated.

### Finding Description
In `send`, `erc_decimals` and local `decimals` are read once and baked into the encoded ERC20 amount that is dispatched: [3](#0-2) 

But the EVM side (`HyperFungibleToken.onAccept`/`send`) treats the transferred amount as already-scaled ERC20 units with no further conversion, so the EVM leg is safe. The vulnerable direction is EVM → Substrate: `on_accept` decodes the raw ERC20 `message.amount` and converts it to the local balance using storage read live at finalization time: [4](#0-3) 

The same live-read pattern also occurs in the timeout refund path, which reads `Precisions::<T>::get(local_asset_id, dest)` and current local decimals to compute the refund amount, rather than the values that applied when the original transfer was dispatched: [5](#0-4) 

The `CreateOrigin`-gated `update_token` extrinsic can change `Precisions` for a `(asset_id, chain)` pair at any time, including while requests dispatched under the old precision are still pending delivery or timeout on Hyperbridge: [6](#0-5) 

Because `convert_to_balance` divides the raw ERC20 `U256` value by `10^(erc_decimals - local_decimals)`, a precision change between dispatch and delivery directly scales the resulting balance: [7](#0-6) 

- If `erc_decimals` is **increased** after a message was dispatched under the old (lower) value, `on_accept`/`on_timeout` will divide the fixed on-wire amount by a larger power of ten than the amount actually reflects, under-crediting the beneficiary/sender — a fund-freezing loss for the user.
- If `erc_decimals` is **decreased** after dispatch, the pallet will divide by a smaller factor than intended, over-crediting the beneficiary — an unbacked mint (for non-native/burn-mint assets) or an over-release of escrowed native/local funds beyond what was actually locked on the source chain, breaking the 1:1 backing invariant across the bridge.

### Impact Explanation
This breaks the fundamental invariant of the bridge: the amount released/minted on one side must equal the amount escrowed/burned on the other side. A precision update landing between `send` (EVM) and `on_accept`/`on_timeout` (Substrate) — which can plausibly happen for entirely legitimate reasons such as correcting a misconfigured chain's decimals or onboarding a new chain configuration for an asset already in-flight — causes either silent value loss for a legitimate user (funds effectively frozen/lost) or an unbacked mint / over-release of pooled/escrowed assets that dilutes backing for all other holders of that asset on the chain. Both are concrete fund-safety violations reachable from a single relayed message, without any attacker needing special privileges beyond normal governance/CreateOrigin operations that the protocol is expected to perform routinely (registering new chains, correcting precision).

### Likelihood Explanation
Likelihood is moderate: it requires a `CreateOrigin`-gated `update_token`/`register_token` call to touch the `Precisions` entry for an asset/chain pair that has transfers in flight. This is a realistic operational scenario (fixing a misconfigured decimal value, or reconfiguring a chain) rather than a purely adversarial one, and the time window is the full ISMP relay + finality window (which can be significant across L1/L2/consensus proofs), making unintentional collision plausible during active bridge usage.

### Recommendation
Bind the conversion factor to the message itself instead of re-reading mutable storage at finalization time: encode the source-side decimals (or the fully-converted local amount, analogous to how `send` already does the ERC20-side conversion) directly into the dispatched `Message` body, and have `on_accept`/`on_timeout` use that embedded value rather than looking up `Precisions`/`decimals` live. Alternatively, snapshot the precision used per commitment at dispatch time and require any precision update to only apply to messages dispatched after the update.

### Proof of Concept
1. Asset `X` is registered with `Precisions::<T>::insert(X, EvmChain, 18)`, local asset decimals = 12.
2. User A calls `send` on the EVM `HyperFungibleToken` for asset `X`, burning `1000 * 10^18` ERC20 units and dispatching a POST request to the Substrate pallet with `message.amount = 1000 * 10^18`.
3. Before this request is delivered, `CreateOrigin` calls `update_token` for asset `X` on `EvmChain`, changing `Precisions` from `18` to `24` (e.g., to correct a misconfiguration for a different, not-yet-used integration).
4. The relayer delivers the request; `on_accept` reads the *new* `erc_decimals = 24` and computes `amount = message.amount / 10^(24-12) = 1000 * 10^18 / 10^12 = 1000 * 10^6`, instead of the correct `1000 * 10^6 * 10^6` (using the original `18`), under-crediting the beneficiary by a factor of `10^6`.
5. Symmetrically, decreasing `erc_decimals` after dispatch causes the beneficiary to be over-credited relative to what was actually burned/escrowed on the EVM side, minting/releasing more than backed.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
