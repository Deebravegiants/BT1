Confirmed: `ShopValidator` (`lib/shopify_api/utils/shop_validator.rb`) is never invoked in the webhook processing path (`Registry.process` / `Webhooks::Request`) — it only validates domain *format*, and isn't called from the webhook flow at all. There is no mechanism binding the `shop-domain` header to the HMAC-covered bytes.

### Title
Webhook shop/topic/webhook-id/api-version identity is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `ShopifyAPI::Webhooks::Registry.process` accepts the request as authentic based solely on that HMAC check. However, `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all of which are read from HTTP headers — are passed unverified into `WebhookMetadata` and handed to the app's handler. The gem's own documentation claims `process` "will verify the request did indeed come from Shopify," but the tenant-identifying `shop` field is not part of that verification.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from attacker-controllable headers, but they are excluded from `to_signable_string`, so `Utils::HmacValidator.validate` never covers them: [3](#0-2) 

`Registry.process` treats a passing HMAC check as full authenticity, then constructs `WebhookMetadata` directly from the unverified `request.shop`/`topic`/`webhook_id`/`api_version`: [4](#0-3) 

This breaks the identity binding: `shop authenticated (by valid HMAC over body) == shop attributed to the event (unauthenticated header)`. Both sides must be evaluated: before the request, Shopify HMACs a `(body, secret)` pair for a specific merchant's webhook delivery; after an attacker's crafted request, the same `(body, hmac)` pair still validates, but the `shop-domain`/`topic`/`webhook-id`/`api-version` headers can be swapped to any value the attacker chooses, and the handler is invoked believing the event originated from that (possibly victim) shop. `ShopValidator` (`lib/shopify_api/utils/shop_validator.rb`) exists in the gem but is never called from the webhook path, so there is no secondary check that ties the header's shop to anything trustworthy.

### Impact Explanation
An attacker who installs the app on their own store (an ordinary, unprivileged action available to anyone) will legitimately receive genuine `(raw_body, hmac)` pairs for their own shop's webhook events, since Shopify signs webhooks per-app (not per-shop) using the app's `client_secret`. By replaying that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`/`X-Shopify-Api-Version`) header with an arbitrary victim shop domain, the attacker causes `Registry.process` to accept the request as valid and dispatch it to the handler as if it originated from the victim shop. Depending on how the host app keys off `WebhookMetadata#shop` (session lookup, GDPR data actions, uninstall cleanup, order/product ingestion, etc.), this enables cross-tenant event injection/impersonation — e.g. forging `shop/redact`, `customers/redact`, `customers/data_request`, or `app/uninstalled` against a shop the attacker does not own, or feeding attacker-controlled webhook bodies into a victim tenant's data pipeline.

### Likelihood Explanation
Any Shopify merchant/developer can install a public app to receive genuine signed webhooks for their own shop, then trivially rewrite the `shop-domain`/`topic`/`webhook-id` headers when replaying the captured request to the app's webhook endpoint — no knowledge of `api_secret_key` is required, since the body/HMAC pair is reused unmodified. The only constraint is that the replayed webhook body must match a topic/shape the attacker already legitimately received, which is not a meaningful barrier for common topics (e.g. the mandatory GDPR/uninstall topics that every installed app receives).

### Recommendation
Include `shop`, `topic`, and (if used for dedup/routing) `webhook_id`/`api_version` in the HMAC-covered signable string (mirroring how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop`, `host`, etc.), or otherwise cryptographically bind the header claims to the verified body before calling `handler.handle`. At minimum, document that host applications must independently verify `request.shop` corresponds to a shop that legitimately has this specific webhook subscription/app install before trusting it, since the HMAC alone does not vouch for `shop`.

### Proof of Concept
1. Install the target Shopify app on attacker-owned shop `attacker.myshopify.com`; trigger a subscribed webhook topic (e.g. `app/uninstalled` or `shop/redact`) so Shopify sends a genuine POST with headers `X-Shopify-Hmac-Sha256: <valid_hmac>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: app/uninstalled`, and body `B`.
2. Capture `B` and the `X-Shopify-Hmac-Sha256` value unchanged.
3. Replay a POST to the same app webhook endpoint with the identical body `B` and identical `X-Shopify-Hmac-Sha256`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` only checks `B` (`lib/shopify_api/webhooks/request.rb:35-38`).
5. `handler.handle(data: WebhookMetadata.new(shop: "victim.myshopify.com", topic: "app/uninstalled", ...))` is invoked — the host app now processes an `app/uninstalled` (or other) event as if it came from `victim.myshopify.com`, even though that shop never sent it.
