Confirmed: the safety check for `amount_out` vs. pool reserves is performed *after* the underflowing subtraction, not before.

### Title
Unchecked `amount_out`-driven integer-underflow panic in `swap_token_amount_base_out` allows single-instruction DoS - (File: `program/src/math.rs`, `program/src/processor.rs`)

### Summary
`Calculator::swap_token_amount_base_out` (used by both `process_swap_base_out` and `process_swap_base_out_v2`) computes `denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap()` (or the coin equivalent) using an attacker-supplied `swap.amount_out` *before* the program ever validates that `amount_out` is smaller than the pool's reserves.

### Finding Description
In `Calculator::swap_token_amount_base_out`, for `SwapDirection::Coin2PC` the code does: [1](#0-0) 
`total_pc_without_take_pnl.checked_sub(amount_out).unwrap()` — if `amount_out >= total_pc_without_take_pnl`, `checked_sub` returns `None` and `.unwrap()` panics. The analogous `PC2Coin` branch has the same pattern: [2](#0-1) 

In `process_swap_base_out`, this function is invoked with the raw, unvalidated `swap.amount_out`: [3](#0-2) 

Only *after* this call — and after further fee arithmetic and log emission — does the processor check `if swap.amount_out >= total_pc_without_take_pnl { return Err(...) }`: [4](#0-3) [5](#0-4) 

The same ordering (compute first, bound-check later) exists in `process_swap_base_out_v2`: [6](#0-5) [7](#0-6) [8](#0-7) 

This is the direct analog of the reported `LeqGadget` issue: a numeric comparison/subtraction operation is exercised with a value outside its supported range because the range check is applied too late (or not at all before the arithmetic), causing an unconditional panic (`unwrap()` on `None`) instead of a graceful, checked error path.

### Impact Explanation
Any unprivileged caller of `SwapBaseOut` / `SwapBaseOut V2` can set `amount_out` ≥ the relevant pool reserve (`total_pc_without_take_pnl` or `total_coin_without_take_pnl`), causing `checked_sub(...).unwrap()` to panic inside `swap_token_amount_base_out` before the processor's own `InsufficientFunds` guard is reached. On Solana, a program panic aborts and reverts the *current* transaction only — it does not corrupt persistent pool state, does not crash the validator, and does not result in theft, permanent freezing, unbacked LP minting, or insolvent accounting for other users. Every downstream instance found (`swap_token_amount_base_out` call sites in both swap-out code paths) exhibits the same "unwrap after compute, guard after that" ordering, but in all cases the effect is limited to the attacker's own transaction failing with a panic message instead of a clean `AmmError`. No state-changing token transfer occurs before the panic (both `Invokers::token_transfer` calls happen after the bound checks), so pool funds and other users' balances remain unaffected.

### Likelihood Explanation
Trivial to trigger deterministically — a single `SwapBaseOut`/`SwapBaseOutV2` instruction with `amount_out` set at or above the current pool reserve reaches the vulnerable subtraction on every invocation. However, this only affects the initiating transaction, not the on-chain pool state.

### Recommendation
- Short term: reorder the checks so `amount_out < total_pc_without_take_pnl` / `amount_out < total_coin_without_take_pnl` are validated in the processor *before* calling `Calculator::swap_token_amount_base_out`, and replace `.unwrap()` in `swap_token_amount_base_out`/`swap_token_amount_base_in` with `checked_sub(...).ok_or(AmmError::CheckedSubOverflow)?` so out-of-range inputs produce a controlled program error instead of a panic.
- Long term: audit all other `.unwrap()` usages on `checked_*` arithmetic in `program/src/math.rs` and `program/src/processor.rs` that consume attacker-controlled instruction data (`swap.amount_in`, `swap.amount_out`, `withdraw.amount`, deposit amounts) and convert them to propagate `AmmError` variants, consistent with the "range check before compute" pattern already used in `calc_total_without_take_pnl_no_orderbook`.

### Proof of Concept
1. Fund a pool normally and note `total_pc_without_take_pnl` (derived from `amm_pc_vault.amount - need_take_pnl_pc`).
2. Submit a `SwapBaseOut` (or `SwapBaseOutV2`) instruction with `swap_direction = Coin2PC` and `amount_out = total_pc_without_take_pnl` (or any larger value), holding a `user_source` token account (need not even hold sufficient balance, since the panic occurs before the `InsufficientFunds`/balance checks).
3. Execution reaches `Calculator::swap_token_amount_base_out` → `total_pc_without_take_pnl.checked_sub(amount_out)` returns `None` → `.unwrap()` panics, aborting the transaction with a runtime panic instead of the intended `AmmError::InsufficientFunds`.

Because the underflow is caught by Solana's transaction abort before any vault transfer executes, the practical effect is limited to the caller's own failed transaction and a wasted compute-budget/DoS on that single call, not a pool-wide fund-safety violation — this should be weighed when triaging severity relative to the original high-severity validator-crash report it is modeled after.
