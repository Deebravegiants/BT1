### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signable string from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields used by `ShopifyAPI::Webhooks::Registry.process` to dispatch the webhook to the app's handler are read directly from unauthenticated HTTP headers. The equality the gem should enforce — "HMAC-verified bytes == bytes the handler acts on for tenant attribution" — is broken: the header-derived `shop` is acted on (used to build `WebhookMetadata#shop`) but is not part of what the HMAC actually authenticates.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled straight from HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, etc.) with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Registry.process` validates only the body HMAC, then trusts `request.shop`/`request.topic` to build the `WebhookMetadata` passed to the app's registered handler: [3](#0-2) 

`WebhookMetadata#shop` is the tenant identifier the handler will act on (persist data under, dispatch business logic for, etc.): [4](#0-3) 

`HmacValidator.validate` only proves that `to_signable_string` (the raw body) was signed with the app's shared secret — it says nothing about which shop or topic the signature was intended for: [5](#0-4) 

Because Shopify's webhook secret is per-app (shared across all shops that install the app), any shop that installs the app can trigger a webhook and legitimately obtain a `(body, hmac)` pair signed with the app's own `api_secret_key`. An attacker who controls one installed shop can replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header to name a different, victim shop. `Utils::HmacValidator.validate` will still pass because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the victim shop.

This is the same bug class as the referenced Besu RLP issue: a bounds/identity check is performed on one representation of the data (the raw body bytes) while a different, unchecked representation (the header-derived shop/topic) is what downstream code actually consumes and trusts.

### Impact Explanation
This breaks the tenant boundary the gem is expected to preserve for webhook processing: an app built on this gem cannot rely on `request.shop` inside a validated webhook to be the shop the payload actually originated from. Depending on how the app's `WebhookHandler#handle` uses `data.shop` (e.g., looking up the shop's `Session`/access token, writing data keyed by shop, or triggering shop-scoped side effects), this enables cross-tenant data confusion/spoofing — an unprivileged installer of the app can cause the app to process arbitrary attacker-chosen bodies as if they belong to a shop they do not control.

### Likelihood Explanation
Any merchant who installs the app is an "unprivileged internet user" relative to other tenants of the same app, and merely needs to trigger one real webhook event on their own store to obtain a valid `(body, hmac)` pair for the app's shared secret. No access to `api_secret_key`, access tokens, or the victim's credentials is required — only a normal HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header.

### Recommendation
Include the tenant/topic identity in the HMAC-verified signable string, or otherwise cryptographically bind `shop`/`topic` to the signed payload before they are trusted (e.g., verify the `shop` against the session/access-token registered for that shop's webhook subscription, or use Shopify's per-webhook payload fields that already embed the shop id in the JSON body and validate consistency between the JSON body and the header before dispatch). At minimum, `Registry.process` should not treat header-derived `shop`/`topic` as authenticated data equivalent to what the HMAC covers.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and triggers any subscribed webhook topic (e.g. `orders/create`), capturing the raw body `B` and the resulting `x-shopify-hmac-sha256` header value `H` — both legitimately signed by the app's shared secret.
2. Attacker sends a POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Headers: `x-shopify-hmac-sha256: H` (unchanged), `x-shopify-topic: orders/create` (unchanged), `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds a request whose `hmac` method reproduces `H`, and `Utils::HmacValidator.validate` succeeds because it only re-signs `B`. [3](#0-2) 
4. `Registry.process` builds `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed_body, ...)` and invokes the app's handler, which now processes attacker-controlled data attributed to `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
