### Title
Route-supplied contract calls can inject unauthorized token transfers into the caller’s signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
Controller strategies accept caller-supplied `swap` bytes and execute them through the configured router while the caller’s root authorization remains active for the transaction. [1](#0-0) 

Because route venues are not restricted by the controller, a malicious route can execute attacker-controlled contract code that requests an unrelated token transfer from the caller; if the caller signs the authorization tree produced by simulation, the injected transfer succeeds even though it is unrelated to the requested collateral or debt swap. [2](#0-1) 

### Finding Description
`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` all forward caller-provided strategy bytes without binding them to a fixed pool set or independently validating the encoded external calls. [3](#0-2) 

For example, `swap_collateral` authenticates `caller`, verifies account ownership, withdraws the selected collateral, and then passes the supplied `swap` bytes into `withdraw_and_swap_from_supply`. [4](#0-3) 

`swap_tokens` subsequently invokes the configured router with the controller as `sender`, `amount_in`, and the unmodified `swap` payload. [5](#0-4) 

The controller authorizes only the expected input-token transfer from itself to the router, but that restriction does not prevent route-selected code from making a separate `require_auth` request against the original caller elsewhere in the transaction. [6](#0-5) 

Post-route checks measure only the router’s effect on the controller’s input balance and require a positive output balance; they do not inspect or reject additional operations performed under the caller’s authorization tree. [7](#0-6) 

### Impact Explanation
A crafted route can cause a malicious pool contract to transfer any unrelated spendable token held by the victim to an attacker while still returning enough output for the strategy’s measured-output and account-risk checks to pass. [8](#0-7) 

This permits theft of user wallet assets beyond the collateral or debt amount intentionally committed to the strategy. [9](#0-8) 

The injected child authorization is visible during transaction simulation, so a wallet or client that verifies the authorization tree can block the transfer; one that signs the simulated tree without inspecting children cannot distinguish it from an expected nested call. [10](#0-9) 

### Likelihood Explanation
Exploitation requires the victim to invoke a strategy containing an attacker-supplied route and to sign the resulting poisoned authorization tree. [4](#0-3) 

The attacker cannot directly select another account because `require_owner_or_delegate` rejects callers that are not the account owner or delegate. [11](#0-10) 

The practical exposure is therefore a malicious quote, route, frontend, or composed transaction that induces the victim to sign authorization containing an unexpected token-transfer child. [12](#0-11) 

### Recommendation
Do not allow lending strategies to execute routes containing arbitrary venue or pool addresses; bind routes to a governance-controlled pool allowlist or another authorization-safe route representation. [5](#0-4) 

Clients and wallets should independently decode the submitted `swap` payload, reject routes naming unexpected contracts, and refuse to sign an authorization tree containing any token transfer other than the expected strategy input transfer. [13](#0-12) 

### Proof of Concept
1. A victim holds collateral in a lending account and also holds an unrelated wallet token. [14](#0-13) 
2. An attacker provides `swap` bytes whose venue hop resolves to an attacker-deployed contract rather than a legitimate pool. [15](#0-14) 
3. The victim submits `swap_collateral(caller, account_id, current, amount, new, swap)` using that route. [15](#0-14) 
4. The controller authenticates the victim, checks account ownership, withdraws `current`, and invokes the configured router with the supplied bytes. [4](#0-3) 
5. During route execution, the malicious contract calls `TOKEN.transfer(victim, attacker, wallet_balance)`. [10](#0-9) 
6. Simulation places that transfer beneath the victim’s `swap_collateral` authorization; if the victim signs that tree, the malicious transfer executes while the router’s measured output and the controller’s final risk checks still pass. [7](#0-6)

pub(crate) fn swap_tokens(
    env: &Env,
    refund_to: &Address,
    token_in: &Address,
    amount_in: i128,
    token_out: &Address,
    swap: &StrategySwap,
) -> i128 {
    require_positive_amount(env, amount_in);
    assert_with_error!(env, !swap.is_empty(), GenericError::InvalidPayments);

    let controller = env.current_contract_address();
    let router_addr = storage::get_swap_aggregator(env);
    let router = SwapAggregatorClient::new(env, &router_addr);
    let token_in_client = token::Client::new(env, token_in);

    // Snapshot before router execution to measure its spend and output.
    let in_before = token_in_client.balance(&controller);
    let out_before = token::Client::new(env, token_out).balance(&controller);

    // Authorize only this token transfer to this router for this exact amount.
    authorize_transfer_as_current(env, token_in, &controller, &router_addr, amount_in);

    storage::with_flash_guard(env, || {
        let _ = router.execute_strategy(&controller, &amount_in, swap);
    });

    // Reject input gains or overspending; refund only this swap's unused input.
    let in_after = token_in_client.balance(&controller);
    assert_with_error!(env, in_after <= in_before, StrategyError::RouterOverspend);
    let actual_spent = in_before - in_after;

    }

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
