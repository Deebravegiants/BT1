Audit Report

## Title
Unverified ERC20 transfer amounts allow fee-on-transfer/rebasing tokens to desynchronize XCM holding credits from actual checking-account balance - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` only inspect the boolean return value of an ERC20 `transfer` call and then credit/move the exact requested `amount` into/out of XCM holding, without ever reading back the actual balance delta of the `TransfersCheckingAccount` or beneficiary. For a fee-on-transfer or rebasing ERC20 contract, this desynchronizes the amount recorded in XCM holding (`Erc20Credit(amount)`) from what is actually held in the checking account, and `ERC20Matcher`/`IsLocalAccountKey20` impose no allow-list, so any permissionlessly deployed `pallet-revive` contract matching an `AccountKey20` location is treated as a valid asset by this transactor.

## Finding Description
In `withdraw_asset_with_surplus`, the transactor calls `IERC20::transferCall` to move `amount` to the mapped `checking_address`, and on a decoded `true` return value it unconditionally mints `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` for the full requested `amount`, without checking the checking account's actual `balanceOf` before/after the call [1](#0-0) . Symmetrically, `deposit_asset_with_surplus` transfers `amount` from the checking account to the beneficiary and treats a decoded `true` return as complete success, again with no balance verification [2](#0-1) . A `grep` across the file confirms there is no `balanceOf`/balance read-back logic anywhere in `erc20_transactor.rs` — the only checks performed are on the boolean `transfer` return value and revert status.

The `ERC20Matcher` type is defined as `MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>`, and `IsLocalAccountKey20::contains` matches **any** `Location` of the form `(0, [AccountKey20 { .. }])` with no contract-address whitelist [3](#0-2) . This `ERC20Transactor` (parameterized with `assets_common::ERC20Matcher`) is wired into Asset Hub Westend's `AssetTransactors` tuple, which is used by the XCM executor for asset handling [4](#0-3) .

Because `pallet-revive` contract deployment is permissionless, any account can deploy a contract whose `transfer` implementation deducts a fee (or rebases) while still returning `true`, and that contract's address will be accepted by `ERC20Matcher` as a valid fungible asset location without any whitelist gate.

## Impact Explanation
Every successful withdraw against such a non-conformant ERC20 mints an XCM holding credit (`Erc20Credit(amount)`) that is larger than what is actually received into `TransfersCheckingAccount`. Repeated operations cause the checking account's real on-chain balance to drift below the sum of credits already represented in the XCM system, eventually causing `deposit_asset_with_surplus` (or subsequent withdraw operations for other users of the same token) to fail once the shortfall surfaces, since the checking account can no longer cover previously "issued" credits. This is a genuine accounting/backing invariant break inside the SDK's own asset-transactor code, not merely a display bug, and it is reachable by any user of `pallet_xcm::execute` — a permissionless, unprivileged path.

## Likelihood Explanation
Both the contract deployment (`pallet-revive`) and the exploitation path (`pallet_xcm::execute` invoking `WithdrawAsset`/`DepositAsset` against `ERC20Transactor`) are available to ordinary, unprivileged accounts, and `ERC20Matcher`/`IsLocalAccountKey20` apply no contract whitelist, matching any `AccountKey20` location. No governance, admin, or relayer privilege is required, and the flaw is deterministic and repeatable for any fee-on-transfer or rebasing ERC20 deployed under `pallet-revive`.

## Recommendation
After each `transfer` call in `withdraw_asset_with_surplus`/`deposit_asset_with_surplus`, read back the checking/beneficiary account's actual balance delta (via a `balanceOf` call before/after, or by validating an emitted `Transfer` event amount) and mint/move an `AssetsInHolding` credit reflecting the *actual* amount moved rather than the requested `amount`. Alternatively, restrict `ERC20Matcher`/`IsLocalAccountKey20` to an explicit allow-list of verified, standard-conformant ERC20 contracts before treating arbitrary `AccountKey20` locations as XCM-recognized fungible assets.

## Proof of Concept
1. Deploy a minimal ERC20-like contract via `pallet-revive` whose `transfer` function deducts a fee (e.g., 1%) but still returns `true`.
2. Use `pallet_xcm::execute` with a program containing `WithdrawAsset` for this contract's `AccountKey20` location with amount `100`, followed by `DepositAsset` to a different local beneficiary.
3. Observe that `withdraw_asset_with_surplus` mints `Erc20Credit(100)` into XCM holding even though the checking account's real `balanceOf` only increased by `99` [5](#0-4) , and the subsequent `deposit_asset_with_surplus` attempts to move `100` out of the checking account [6](#0-5) , which will eventually fail once accumulated shortfalls exceed the checking account's real balance — demonstrating under-collateralization relative to credits already issued.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
