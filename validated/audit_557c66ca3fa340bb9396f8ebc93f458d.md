### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing tenant-identity spoofing in `ShopifyAPI::Webhooks::Registry.process` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` (tenant) attribute delivered to the webhook handler is read from an unsigned HTTP header. This breaks the identity binding `shop_verified_by_hmac == shop_used_by_handler`, letting anyone in possession of one valid (body, HMAC) pair relabel it as belonging to a different shop.

### Finding Description
`Utils::HmacValidator.validate` verifies the signature exclusively against `to_signable_string`, which for webhook requests returns just the raw body: [1](#0-0) 

The `shop` accessor, however, comes straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signed payload: [2](#0-1) 

`Registry.process` only checks the HMAC of the body before dispatching to the registered handler, and forwards the unauthenticated `shop` value straight into `WebhookMetadata` that the handler receives as the tenant identifier: [3](#0-2) 

`HmacValidator.validate` itself only compares the HMAC over `verifiable_query.to_signable_string`, so it cannot detect that the `shop` header was altered, since `shop` isn't part of that string for webhook requests: [4](#0-3) 

Because the app-level `api_secret_key` (client secret) is shared across every shop that has installed the app, a valid `(raw_body, hmac)` pair only proves "this request was produced by someone holding the app's shared secret" — it says nothing about *which* installed shop it came from. Any shop that has legitimately installed the app can capture a real webhook delivery it received (valid body + valid HMAC) and simply retransmit it to the app's webhook endpoint with the `shop-domain` header swapped to a different, victim shop that also installed the app. The signature still validates, so `Registry.process` will call the handler with `WebhookMetadata#shop` set to the victim shop, i.e., the equality "shop the HMAC was actually generated for" == "shop delivered to the handler" no longer holds.

### Impact Explanation
This crosses the tenant boundary that `ShopifyAPI::Webhooks::Registry` is meant to enforce: application code that trusts `WebhookMetadata#shop` (e.g., to select which merchant's stored session/data to act on) can be made to act on/attribute data to the wrong shop using only a replayed, header-modified copy of a webhook the attacker legitimately received for their own store. This matches the "cross-tenant access" impact category since the gem hands the host application an unauthenticated tenant identifier under the guise of a verified one.

### Likelihood Explanation
Exploitation requires only that the attacker control (or have received a webhook for) any single shop that has the target app installed — no `api_secret_key`, access token, or other privileged credential is needed, and no interaction with Shopify's own infrastructure is required beyond replaying an HTTP POST to the app's own public webhook endpoint. This is realistically achievable by any unprivileged merchant/tester of a multi-tenant app.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-covered payload, or otherwise cryptographically bind the asserted `shop` to the signed body (for example, deriving/confirming the shop from a per-shop secret or from Shopify's registered subscription metadata) before exposing `WebhookMetadata#shop` to handlers. At minimum, the library should document prominently that `WebhookMetadata#shop` is unauthenticated and must be cross-checked by the host application against a known, previously-authorized shop/session before being trusted for tenant-scoped actions.

### Proof of Concept
1. Attacker's own shop `attacker.myshopify.com` has the app installed and receives a legitimate webhook: raw body `B`, header `x-shopify-hmac-sha256: H` (valid for the app's shared `api_secret_key`), `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker POSTs the same raw body `B` and the same valid `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged header; `Utils::HmacValidator.validate` succeeds because it only checks `H` against `B` (see `to_signable_string` returning `@raw_body`), independent of the `shop` header. [3](#0-2) 
4. `Registry.process` invokes the registered handler with `WebhookMetadata#shop == "victim.myshopify.com"`, even though the payload actually originated from `attacker.myshopify.com`'s installation.
