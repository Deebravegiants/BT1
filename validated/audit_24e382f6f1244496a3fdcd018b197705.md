### Title
Webhook shop/topic identity not covered by HMAC signature allows cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string from the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then immediately dispatches the handler using these unauthenticated header values as the tenant/topic identity, breaking the binding `shop authenticated == shop acted on`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

All the other request attributes — `shop`, `topic`, `webhook_id`, `api_version` — are parsed exclusively from headers and are never included in the HMAC-signed material: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (i.e., the raw body) against the shared `api_secret_key`: [3](#0-2) 

`Registry.process` checks that HMAC and then dispatches the handler using `request.shop` and `request.topic` straight from the unauthenticated headers, without any additional binding to the signed body: [4](#0-3) 

Because `api_secret_key` is the app's single shared client secret used for **every** shop that installs the app (not a per-shop secret), any merchant who installs the public app receives legitimately-signed webhooks for their own store, where the HMAC is valid for the raw body under the app's shared secret. Since headers are excluded from the signature, that same merchant can replay the identical `raw_body`/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain`, `x-shopify-topic`, or `x-shopify-webhook-id` header values. `Registry.process` will still consider the HMAC valid (body content unchanged) and will invoke the registered handler with the forged `shop`/`topic`, which is exactly the "bytes verified vs. bytes parsed" divergence called out in the report: the bytes cryptographically verified (raw body) are not the bytes acted upon for tenant/topic identification (headers).

This is the direct structural analog of the audited finding: an identity-critical field (`shop`) is *acted upon* by downstream logic (`handler.handle(shop: request.shop, ...)`) but is *not covered* by the authentication primitive (`HMAC` over `raw_body` only).

### Impact Explanation
An app author who trusts `WebhookMetadata#shop` (as documented/intended usage) to key session/data lookups can have data intended for shop A attributed to a payload actually generated for shop B (or a forged topic causing the wrong handler logic to run against attacker-controlled but validly-signed body content). Since all shops installing a given app share the same `api_secret_key`, one merchant (an unprivileged, self-service installer of the app) can forge webhook deliveries claiming to be a different tenant. This is cross-tenant data confusion arising purely from calling this gem's own `Registry.process`/`HmacValidator` as documented, not from any host-application misuse.

### Likelihood Explanation
Requires only that the attacker be able to install the target app on any shop (self-serve, no special privilege) to obtain a legitimately-signed webhook body/HMAC pair, and the ability to send arbitrary HTTP requests to the app's public webhook endpoint with modified headers — no access token, `client_secret`, or victim credentials are needed.

### Recommendation
Bind the header-derived identity fields into the signed material, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the verified payload (e.g., require the app to independently confirm the `shop` against a previously-established session/webhook registration before trusting it), rather than relying solely on a raw-body-only HMAC while trusting unauthenticated headers for routing/tenant identification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook with `x-shopify-hmac-sha256` valid for `raw_body` under the app's shared `api_secret_key`, and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays this exact `raw_body` to the app's webhook endpoint but rewrites `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and/or changes `x-shopify-topic`).
4. `ShopifyAPI::Webhooks::Registry.process` computes `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` — see [5](#0-4) .
5. The registered handler executes with `shop: "victim-shop.myshopify.com"`, even though that shop never sent or authorized this webhook.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
