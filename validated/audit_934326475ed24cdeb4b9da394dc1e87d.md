### Title
Relayer fee withdrawal permanently zeroes the `Fees` balance on dispatch acceptance, before destination-side disbursement succeeds - ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
`Pallet::withdraw` in `modules/pallets/relayer/src/withdrawal.rs` reads a relayer's accumulated `Fees` balance, dispatches an ISMP POST request instructing the destination chain to pay it out, and then unconditionally zeroes the `Fees` entry once `dispatch_request` returns `Ok`. This mirrors the `BalancedVault.claim()` bug class: state is marked "settled" (balance zeroed) based on successful *submission* of the payout, not on successful *delivery/execution* of the payout, and the outbound request is configured with `timeout: 0` (never expires), so there is no fallback path such as a timeout-triggered credit reversal.

### Finding Description [1](#0-0) 

The flow:
1. `available_amount = Fees::<T>::get(dest_chain, address)` reads the relayer's claimable balance.
2. A `DispatchPost` is built with `timeout: 0` (no timeout, so it can never be retried/refunded via the normal ISMP timeout mechanism) targeting either `HYPERBRIDGE_MODULE_ID` (substrate) or the destination's `host_manager` (EVM), carrying `WithdrawalParams { beneficiary_address, amount: available_amount, token }`.
3. Immediately after `dispatcher.dispatch_request(...)` succeeds (i.e., the message is merely *accepted into the outbound queue*), `Fees::<T>::insert(dest_chain, address, U256::zero())` unconditionally zeroes the balance — before the message has been relayed, proven, or executed on the destination chain.

This is the same root-cause pattern as the reported `BalancedVault.claim()` issue: the accounting entry that represents a user's/relayer's entitlement is cleared based on an *optimistic* action (successful dispatch) rather than a *confirmed* one (successful execution/settlement on the paying side). If the destination-side handler for `WithdrawRelayerFees`/`WithdrawalParams` cannot fully honor the payout — e.g., insufficient balance in the destination's fee-holding account (`RELAYER_FEE_ACCOUNT` on substrate, or the equivalent EVM host manager fee-token balance), a reverting transfer, or any other execution failure on the destination — the relayer's claim is already gone on Hyperbridge with no mechanism to re-credit it. Because `timeout: 0` means the request never times out, there is also no automatic timeout-refund flow that could restore the zeroed balance.

### Impact Explanation
If the destination-side payout can fail or only partially succeed relative to `available_amount` (e.g., the `RELAYER_FEE_ACCOUNT`/host-manager fee-token reserve is momentarily below the relayer's claim, due to concurrent withdrawals or fee-token accounting drift across many relayers), the relayer permanently loses the difference: the source-of-truth balance (`Fees` on Hyperbridge) has already been zeroed, and the destination side has no compensating credit-back logic tied to failed disbursement. This is a permanent freezing/loss of relayer reward funds — the exact class of impact ("loss of user funds," analogous to under-collateralized pro-rated claims never being recoverable) called out in the source report.

### Likelihood Explanation
Reachability is low-privilege: any relayer can trigger this by calling `withdraw_fees` (an unsigned extrinsic gated only by signature verification over the withdrawal payload) whenever `available_amount` exceeds the minimum withdrawal threshold — no special permissions are required. Whether the destination side can actually fail to fully honor the amount (e.g., `RELAYER_FEE_ACCOUNT` insolvency, concurrent draining by many relayers, EVM host-manager fee-token balance shortfall) could not be fully verified in this pass — the destination-side handlers (`RefundingRouter`/`WithdrawRelayerFees` decode-and-transfer logic in `pallet-ismp`'s dispatcher, and the EVM host manager's withdrawal-params handling) were not found in the indexed portion of the codebase available to this search, so I cannot confirm from the code itself whether that account is guaranteed always-solvent by protocol invariant, or whether it can be under-collateralized in practice. This uncertainty is the main gap in fully proving the severity.

### Recommendation
- Do not zero `Fees` on successful dispatch alone. Instead, zero (or decrement) the balance only after receiving a confirmed acknowledgment that the destination side fully executed the disbursement (e.g., via a callback/response message), or
- Give the outbound `DispatchPost` a real timeout (not `0`) and implement an `on_timeout` handler for the relayer-fee withdrawal request that re-credits `Fees` on the source chain, and
- On the destination side, ensure the handler for `WithdrawRelayerFees`/`WithdrawalParams` either fully succeeds or explicitly reverts/responds with failure in a way that is observable and reconcilable on Hyperbridge, rather than silently under-paying.

		if available_amount <

				.unwrap_or(MinWithdrawal::get())
		{
			Err(Error::<T>::NotEnoughBalance)?
		}

		let dispatcher = <T as Config>::IsmpHost::default();

		Nonce::<T>::try_mutate(address.clone(), withdrawal_data.dest_chain, |value| {
			*value += 1;
			Ok::<(), ()>(())
		})
		.map_err(|_| Error::<T>::ErrorCompletingCall)?;

		let beneficiary_address = withdrawal_data.beneficiary.clone().unwrap_or(address.clone());
		let (to, body) = match withdrawal_data.dest_chain {
			s if s.is_substrate() => (
				HYPERBRIDGE_MODULE_ID.to_vec(),
				Message::WithdrawRelayerFees(WithdrawalRequest {
					amount: available_amount.low_u128(),
					account: AccountId32::try_from(&beneficiary_address[..])
						.map_err(|_| Error::<T>::InvalidPublicKey)?,
				})
				.encode(),
			),
			_ => {
				let HostParam::EvmHostParam(params) =
					HostParams::<T>::get(withdrawal_data.dest_chain)
						.ok_or_else(|| Error::<T>::MissingMangerAddress)?;

				let body = WithdrawalParams {
					beneficiary_address: beneficiary_address.clone(),
					amount: available_amount.into(),
					token: params.fee_token,
				}
				.abi_encode()
				.map_err(|_| Error::<T>::InvalidPublicKey)?;

				(params.host_manager.0.to_vec(), body)
			},
		};

		let post = DispatchPost {
			dest: withdrawal_data.dest_chain,
			from: MODULE_ID.to_vec(),
			to,
			body,
			timeout: 0,
		};

		// Account is not useful in this case
		dispatcher
			.dispatch_request(
				DispatchRequest::Post(post),
				FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() },
			)
			.map_err(|_| Error::<T>::DispatchFailed)?;

		Fees::<T>::insert(withdrawal_data.dest_chain, address.clone(), U256::zero());

		Self::deposit_event(Event::<T>::Withdraw {
			address: sp_runtime::BoundedVec::truncate_from(address.clone()),
			beneficiary_address: sp_runtime::BoundedVec::truncate_from(beneficiary_address),
			state_machine: withdrawal_data.dest_chain,
			amount: available_amount,
		});

		Ok(())
