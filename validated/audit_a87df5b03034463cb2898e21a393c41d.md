### Title
JWT Replay-Protection Check-Then-Act Race Allows Reuse of a Single-Use Authentication Token - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` is meant to guarantee that each JWT `jti` can be redeemed (used to authenticate an HTTP-trigger request) exactly once, mirroring the "burn" semantics of the referenced report. Instead of atomically checking-and-marking the token as used, it performs two separate, non-atomic operations — `isReplay()` then, much later, `recordUsage()` — with signer/authorization validation in between. Just like the flash-governance `burnFlashGovernanceAsset()` bug where the "burn" step failed to actually consume the resource, this "burn" of a JWT ID can be bypassed by concurrent requests, allowing a supposedly single-use token to authenticate more than one request.

### Finding Description
`Authorize()` is the entry point used to authenticate unprivileged, internet-facing HTTP trigger requests to a workflow: [1](#0-0) 

The sequence is:
1. Verify the JWT signature/claims (`utils.VerifyRequestJWT`).
2. Check replay via `h.jwtCache.isReplay(claims.ID)`.
3. Look up workflow authorized keys and verify the signer is authorized.
4. Only at the very end, call `h.jwtCache.recordUsage(claims.ID)` to actually mark the `jti` as consumed.

Because the check (`isReplay`) and the mark-as-used (`recordUsage`) are two independent calls on the `jwtReplayCache` (guarded internally by its own mutex per call, not by a single atomic check-and-set), two concurrent `Authorize()` calls carrying the identical JWT can both pass step 2 (`isReplay` returns false for both) before either has reached step 4 (`recordUsage`). This is the same class of defect as the Solidity report: the "burn" step (`recordUsage`) does not happen atomically with — or gate — the authorization decision, so the "balance" (single-use token) is not actually deducted before it can be spent again. [2](#0-1) 

The `jwtReplayCache` struct only stores `jti -> timestamp`; nothing in the `Authorize` flow prevents the classic TOCTOU (time-of-check-to-time-of-use) race between the `isReplay` read and the `recordUsage` write.

### Impact Explanation
A JWT that is meant to authenticate a single HTTP-trigger call to a workflow (via the internet-facing gateway `HandleJSONRPCUserMessage` / trigger path) can be replayed concurrently, letting an unprivileged client (or a leaked/observed token) trigger the same workflow execution multiple times using one credential, defeating the intended single-use guarantee of the replay cache and enabling duplicate workflow runs / request impersonation for the duration of the race window.

### Likelihood Explanation
The window is small (network round trips for JWT verification and workflow authorized-key lookup happen between the check and the mark), but it is entirely reachable by an unprivileged client that simply fires the same signed request twice in parallel — no privileged access or malicious node/peer behavior is required, matching the analog scope constraints.

### Recommendation
Make the check-and-mark operation atomic: acquire the `jwtReplayCache` mutex once and, in a single critical section, check whether `jti` is present/expired and, if not, insert it immediately (rejecting concurrent duplicates) — i.e., merge `isReplay` + `recordUsage` into one atomic `checkAndRecord` method, and call it before performing authorization work, not after.

### Proof of Concept
1. Obtain (or generate) one valid signed JWT for an authorized workflow signer.
2. Fire two concurrent HTTP requests to the gateway trigger endpoint using the identical JWT (`jti`).
3. Both goroutines execute `Authorize()`; both call `h.jwtCache.isReplay(claims.ID)` before either has reached `h.jwtCache.recordUsage(claims.ID)`.
4. Both requests pass authorization and the workflow is triggered twice with a token intended to be single-use.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
