### Title
Webhook shop/topic identity spoofing via unsigned headers — HMAC covers only the request body, not the shop or topic used for dispatch and attribution - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate(request)` authenticates solely the raw body bytes [2](#0-1) . The `shop`, `topic`, `api_version`, and `webhook_id` values are read straight from HTTP headers via `shopify_header` [3](#0-2)  and are never part of the signed content, yet `Registry.process` uses `request.topic` to select the handler and forwards `request.shop` into `WebhookMetadata` as the shop of record for the payload [4](#0-3) , which the host app's `WebhookHandler#handle(data:)` then trusts to attribute the body to a tenant [5](#0-4) .

### Finding Description
The intended identity binding is: `hmac-verified bytes == the shop/topic the handler acts on`. In this implementation that equality does not hold — HMAC verification only proves "these body bytes were signed with the app's secret," it says nothing about which shop or topic the signer intended, since headers are outside the signature.

Because the app's `client_secret` is shared across every shop that installs the app, any tenant of a multi-tenant app can legitimately receive a validly-signed webhook body for their own shop and topic (e.g. by triggering an event that produces a webhook they control, or by capturing one their own store receives). That attacker can then replay the exact same raw body and HMAC header to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` headers with a victim shop's domain or with a different registered topic. `Utils::HmacValidator.validate(request)` still succeeds because it only recomputes the signature over `@raw_body`, which is unchanged. `Registry.process` then dispatches to the handler for the attacker-chosen topic and constructs `WebhookMetadata` carrying the attacker-chosen `shop`, even though that shop/topic pairing was never actually signed by Shopify for that combination.

### Impact Explanation
This breaks the tenant boundary the host application relies on: a webhook payload can be attributed to a shop domain that never actually generated or received that event. Depending on how the host app's `WebhookHandler` implementations use `data.shop` (e.g., to look up records, delete data on `shop/redact`/`app/uninstalled`, or process `customers/data_request`), this enables cross-tenant data manipulation or disclosure driven entirely by unauthenticated header values, which lands in the Critical "cross-tenant access" category defined for this scan.

### Likelihood Explanation
Exploitation requires no privileged credentials — the attacker only needs a validly-signed webhook body for any topic/shop pair (trivially obtainable for their own installed shop, since a valid HMAC only proves origin from someone in possession of the app's secret, and normal Shopify-delivered traffic already satisfies this) and the ability to send an HTTP request with modified headers to the app's public webhook endpoint. No interaction with `api_secret_key` beyond what the gem already computes is needed.

### Recommendation
Include the `shop`, `topic`, `api_version`, and `webhook_id` values in `to_signable_string` (or otherwise bind them cryptographically to the payload) so `Utils::HmacValidator.validate` authenticates the full identity tuple, not just the raw body. At minimum, document that host applications must not trust unsigned webhook headers for tenant attribution without additional verification (e.g., cross-checking `shop` against a known/registered shop list before dispatch).

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook, e.g. topic `orders/create`, with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and some JSON `raw_body`.
2. Attacker captures this exact raw body and HMAC header value.
3. Attacker crafts a new HTTP request to the app's webhook endpoint using the identical `raw_body` and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`@raw_body` only, per `lib/shopify_api/webhooks/request.rb` line 36-38) — validation passes because the body is untouched.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: <attacker's parsed body>, ...)`, causing the app to process attacker-controlled data under the victim shop's identity.
