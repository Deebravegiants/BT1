### Title
Webhook HMAC signature does not bind the `shop-domain` (or `topic`/`webhook-id`) header, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable payload from the raw HTTP body only, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers that are never included in the HMAC-verified data. `Registry.process` trusts these header-derived fields (in particular `shop`) once the body-only HMAC check passes, breaking the identity binding `hmac_covers(shop) == shop_trusted_by_handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors instead read straight from caller-supplied HTTP headers with no cryptographic binding: [2](#0-1) .

`Utils::HmacValidator.validate` verifies the signature strictly against `to_signable_string` (the raw body) and the received `hmac` value: [3](#0-2) . Because Shopify computes the webhook HMAC over the body only (this gem mirrors that), the signature is mathematically independent of the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers.

`Registry.process` performs the HMAC check and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` for dispatch to the registered handler without any further validation that these values belong to the shop that actually produced the signed body: [4](#0-3) . The handler receives a `WebhookMetadata` struct whose `shop` field is taken as ground truth by host applications: [5](#0-4) .

This matches the report's bug class: a field acted on (`shop`) is not covered by the value that is cryptographically bound (the HMAC only covers `raw_body`).

### Impact Explanation
Any party capable of relaying an HTTP request to the host application's webhook endpoint (i.e., any internet user reaching that endpoint) can take a legitimate signed webhook body/HMAC pair — captured from any tenant, including from their own low-privilege shop where they are a merchant — and resubmit it with the `shop-domain` header rewritten to a victim shop's domain. Because the HMAC only signs `@raw_body`, the forged request passes `HmacValidator.validate`, and `Registry.process` will call the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop. Any host application logic keyed on that trusted `shop` (e.g. updating per-shop settings, revoking data, triggering `shop/redact`/`customers/redact` flows, or writing to a per-shop record identified by `shop`) can be attributed to, or executed against, a different tenant than the one that actually sent the payload. This is a cross-tenant identity-binding bypass.

### Likelihood Explanation
The attack only requires the attacker to control (or observe) one valid webhook delivery for any shop with the app installed — for many topics the JSON body is generic/small (e.g. `{}` for mandatory topics, or predictable payload shapes for topics an attacker's own test shop can trigger), so producing a body+HMAC pair to replay is straightforward for an unprivileged internet user who can install a free/dev copy of the app on their own shop. No `api_secret_key`, access token, or privileged account is needed to exploit this once one legitimate webhook has been captured — the attacker never needs to know or compute the secret themselves.

### Recommendation
Include the shop domain (and ideally topic/webhook id/api version) in the HMAC-covered signable string, or otherwise cryptographically bind the `shop-domain` header to the request signature (e.g., verify it against a value derived from Shopify's TLS-terminated request context rather than trusting the header alone). At minimum, document that `WebhookMetadata.shop`/`topic` are unauthenticated headers and host apps must independently confirm the shop against their own installed-shop registry before acting on webhook content.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook delivery, e.g.:
   - headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <validHMACofBody>`, `x-shopify-shop-domain: attacker.myshopify.com`
   - body: `{"id":123, ...}`
2. Attacker resends the identical `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` succeeds because it only checks the HMAC of `raw_body`, which was untouched: [6](#0-5) .
4. `Registry.process` dispatches to the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`: [7](#0-6) , causing the host application to act on data attributed to `victim-shop.myshopify.com` even though the payload never originated from Shopify on behalf of that shop.
