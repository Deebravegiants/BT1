### Title
Webhook `shop` (and other Shopify-* headers) are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate`. The `shop` (and `topic`, `api_version`, `webhook_id`) values that identify *which tenant* the event belongs to are read straight from HTTP headers and are never included in the signed material. This breaks the identity binding: `hmac_valid(body) == true` is treated as proof that `shop_header == actual_owning_shop`, but the two are independent.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` and defines: [1](#0-0) 

`to_signable_string` returns only `@raw_body`; `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from headers that are excluded from the signature entirely: [2](#0-1) 

`HmacValidator.validate` then only recomputes/compares the HMAC of `to_signable_string` (the body), never the headers: [3](#0-2) 

`Registry.process` uses that body-only HMAC check as the sole gate before trusting `request.shop` and dispatching to the app's handler with that (unauthenticated) shop value: [4](#0-3) 

So the equality the gem is implicitly asserting is:

`hmac_valid(raw_body, client_secret) == true  ⇒  request.shop is the true origin shop`

but the actual binding enforced is only `hmac_valid(raw_body, client_secret) == true`, with `request.shop` coming from an attacker-controllable header (`x-shopify-shop-domain` / `shopify-shop-domain`) that is never part of the signed bytes. This is the same class of defect as the external report (H06): an operation is executed against an identity taken from an unverified field instead of the one actually bound by the cryptographic/authorization check.

### Impact Explanation
In a multi-tenant app that shares a single webhook endpoint and a single `client_secret` across all installed shops (the standard integration pattern documented for this gem), any merchant who has genuinely installed the app can capture one legitimately HMAC-signed webhook delivery for their own shop (body + `x-shopify-hmac-sha256`), then replay that exact body/HMAC pair to the same endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a victim shop. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will invoke the app's `WebhookHandler` with `WebhookMetadata#shop` set to the attacker-chosen victim shop. Depending on the topic (e.g. `app/uninstalled`, `shop/redact`, `customers/redact`, `shop/update`), this lets an unprivileged attacker trigger tenant-scoped side effects (session/token deletion, data redaction, cache invalidation, state changes) attributed to a shop they do not own — a cross-tenant access/integrity violation.

### Likelihood Explanation
Exploitation only requires: (1) being a legitimate but unprivileged installer of a multi-shop app that uses this gem's shared webhook endpoint, and (2) capturing one of your own valid webhook deliveries (trivial, since it's delivered to you). No access to `api_secret_key`, tokens, or the victim's credentials is needed — the only "secret" (HMAC) is satisfied by replaying an attacker's own legitimately-signed payload. This is realistically reachable wherever an app built on this gem uses one shared HTTP endpoint for all shops' webhooks, which is the common/documented pattern.

### Recommendation
Bind the tenant identity into the verified material instead of trusting an unauthenticated header:
- Include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified (or validate them against a shop-scoped secret/session lookup after body-HMAC validation), or
- At minimum, cross-check `request.shop` against an expected/allow-listed shop for the resolved session before dispatching to `handler.handle`, and reject/replay-protect using `webhook_id`/timestamp so a captured payload cannot be replayed with a different shop header.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - Body: `{"id": 123, ...}`
2. Attacker resends the identical body and identical `x-shopify-hmac-sha256` value to the app's shared webhook endpoint, but changes the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes HMAC over the (unchanged) body only and returns `true`: [5](#0-4) 
4. `Registry.process` proceeds and calls the app handler with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"`: [6](#0-5) 
5. The app now processes attacker-controlled webhook content under the victim shop's tenant context, with the gem providing no verification that the `shop-domain` header actually matches the shop whose secret produced the HMAC.

          received_signature = verifiable_query.hmac
