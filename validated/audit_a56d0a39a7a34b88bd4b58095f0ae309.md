### Title
Escrow release performs external token transfers before updating accounting state, violating checks-effects-interactions - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the internal `withdraw()` function releases escrowed funds to a beneficiary via a raw external `.call()` **before** decrementing the corresponding `_orders[commitment][token]` accounting entry, and only guards against a fully-zeroed escrow slot rather than validating that the requested `amount` does not exceed the actually escrowed balance. This is the same root-cause class flagged in the external report — funds are moved based on state that has not yet been validated/updated for the exact amount being paid out — but manifests here as a Checks-Effects-Interactions violation instead of a raw negative-value underflow.

### Finding Description
`withdraw()` is reachable from an unprivileged, permissionless entrypoint: `cancelOrder()` for same-chain orders calls it directly at [1](#0-0) , and it is also invoked from `onAccept`/`onGetResponse` for cross-chain redemptions/refunds.

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;
        ...
``` [2](#0-1) 

Two problems compound here:
1. **Interactions before effects**: the native-value `.call{value:}` and the ERC20/TRC20 `.call(transfer(...))` (both of which forward all remaining gas and can execute arbitrary attacker-controlled code — either via a malicious beneficiary contract for native transfers, or a malicious token contract used as one of `order.inputs`) execute *before* `_orders[body.commitment][token] -= amount` updates the escrow ledger.
2. **Weak guard**: the only validation is `_orders[body.commitment][token] == 0` (i.e., "has *some* escrow"), not `amount <= _orders[body.commitment][token]`. The correct pattern, used in the canonical (non-Tron) implementation in `IntentsBase.sol`, reads the escrowed balance, updates it, and only *then* performs the transfer:
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;
if (token == address(0)) {
    _sendValue(beneficiary, amount);
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
``` [3](#0-2) 

This is a direct behavioral divergence between the Tron deployment and the audited/tested EVM contract, and it is user-reachable: any address can call `placeOrder` with an attacker-authored ERC20/TRC20 token as one of `order.inputs`, then call `cancelOrder` (same-chain path) to trigger `withdraw()`, handing execution control to attacker code mid-function while `_orders[commitment][token]` still reflects the pre-payout value.

### Impact Explanation
Performing external calls to attacker-influenced code before updating escrow accounting is a High-severity reentrancy surface in funds-custody logic. While the `_filled[commitment]` flag (set at the top of `withdraw`) blocks the most direct same-function re-entry into `cancelOrder`/`withdraw` for the identical commitment, the fundamental safety invariant — "accounting must reflect the payout before or atomically with the transfer" — is broken, and the amount-vs-escrow validation is too weak (checks non-zero, not sufficiency). This is exactly the class of "value moved based on an accounting variable not properly checked/updated" bug identified in the source report, applied to escrowed-fund release rather than a yield-provider redemption. This pattern also makes the contract fragile to future refactors (e.g., multi-token withdrawal bodies, partial fills) where the missing sufficiency check could permit paying out more than is actually escrowed for a given commitment/token.

### Likelihood Explanation
Reachable with a single unprivileged action sequence (`placeOrder` with an attacker-controlled token, followed by `cancelOrder`), no privileged role required. The main mitigating factor is the `_filled` early-set guard blocking the most obvious duplicate-redemption reentry path through `cancelOrder` itself; likelihood is rated High for the underlying CEI violation existing in live/deployed escrow-release code, though a complete end-to-end fund-drain chain depends on additional call paths that share `_orders[commitment][token]` state during the reentrant window.

### Recommendation
Refactor `withdraw()` to follow checks-effects-interactions, matching the canonical `IntentsBase.sol::_withdraw` implementation:
1. Read `escrowed = _orders[body.commitment][token]`.
2. Validate `amount <= escrowed` (not just `escrowed != 0`).
3. Update `_orders[body.commitment][token] = escrowed - amount` **before** making any external call.
4. Only then perform the native/ERC20 transfer, ideally via `SafeERC20.safeTransfer` instead of raw low-level `.call()`.

### Proof of Concept
1. Attacker deploys `MaliciousToken`, an ERC20 whose `transfer()` implementation can execute arbitrary reentrant logic.
2. Attacker calls `placeOrder` with `order.inputs = [{token: MaliciousToken, amount: X}]`, escrowing `X` malicious tokens: `_orders[commitment][MaliciousToken] = X` [4](#0-3) .
3. Attacker calls `cancelOrder(order, options)` on the same chain, which invokes `withdraw(body, true)` with `body.tokens = order.inputs` [1](#0-0) .
4. Inside `withdraw`, the check `_orders[commitment][MaliciousToken] == 0` passes (it equals `X`), and `token.call(transfer(beneficiary, X))` is invoked *before* `_orders[commitment][MaliciousToken] -= X` executes [5](#0-4) .
5. During this external call, `MaliciousToken.transfer()` executes attacker logic while `_orders[commitment][MaliciousToken]` still equals `X` (not yet decremented), demonstrating that state-dependent invariants relied upon elsewhere in the contract during this window are unsound — the accounting ledger and actual token movement are transiently inconsistent, contrary to the safe pattern used in the canonical `IntentsBase.sol::_withdraw`.
