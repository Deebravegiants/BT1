### Title
Budget-capped rebalance swap fails to correct extreme hostile pre-seed ratios, opening the graduated LP materially off the curve-close price - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._swapBudget` caps the pre-seed rebalance swap at 99% of the available inventory side, and `_noFeeSwapInput` clamps its closed-form optimal swap size to that budget. This mirrors the DBI CVE-2026-14739 pattern: a fix engineered to defend against a bounded/"typical" attack magnitude (the earlier CVE-2026-10879-style placeholder overflow, here: earlier `_requirePairEmpty` and the general hostile-mint-preseed defense) does not scale its allocated correction capacity to an extreme instance of the same attack shape, so the defense silently degrades instead of fully closing the gap.

### Finding Description
`_seedUniswapV2Direct` / `_seedRebalancing` defend against an attacker who front-runs `finalizeGraduation` by calling `factory.createPair` + `transfer` + `pair.mint(attacker)` to seed the HyperSwap V2 pool at a hostile (TOKEN, LT) ratio (documented in `packages/contracts/AGENTS.md` "HyperSwap Pre-Seed Defense", Regime 3). The correction mechanism computes the swap input needed to rebalance the pool to the curve-close ratio via `_noFeeSwapInput`: [1](#0-0) 

but the swap is capped at 99% of the available side's inventory via `_swapBudget`, explicitly to avoid a total-inventory-exhaustion brick: [2](#0-1) 

When the hostile pre-seed ratio is extreme enough that the *unconstrained* optimal swap (`_noFeeSwapInput`'s closed-form `sqrt(reserveIn·reserveOut·targetN/targetD) − reserveIn`) exceeds this 99% budget, the rebalance swap only partially corrects the ratio. `_routerDepositAndDispose` then deposits the remaining (still off-ratio) inventory at the post-swap price, so the pool opens materially away from the curve's last trading price — this is a first-class impact type explicitly listed as acceptable in this scan's validation criteria ("an LP seeded away from the curve close price"). This residual is reproduced directly in the test suite: [3](#0-2) 

The 200x LT-rich pre-seed in the test causes the pool to open at more than 1.2x the curve-close price (`(((ltFromPair * 1e18) / tokensForLP) * 12) / 10` bound), i.e., the earlier fix's allocated "correction budget" (a fixed 99%-of-inventory cap) was never re-derived against how far an attacker can actually skew the ratio, so an extreme pre-seed pushes the defense past its designed capacity — exactly the DBI pattern of a fix sized for the wrong order of magnitude.

### Impact Explanation
Any unprivileged address can permissionlessly front-run `finalizeGraduation` by pre-creating the HyperSwap V2 TOKEN/LT pair and minting a sufficiently lopsided dust-cost LP position before phase 2 runs. This forces the finalized LP to open at a price meaningfully divorced from the bonding curve's last trade price. That price gap is then extracted by arbitrage against the newly seeded pool — an economic loss borne by the protocol/LP (the pool's post-graduation reserves, and hence future traders/LPs), even though the attacker's own directly-deposited LP share nets non-positive per the accompanying analysis. A mispriced LP open is a concrete, protocol-level fund-freezing/mispricing defect distinct from attacker profit.

### Likelihood Explanation
The attack path requires only: (1) permissionless `factory.createPair`, (2) an ERC20 `transfer` of TOKEN/LT to the pair, and (3) `pair.mint(attacker)` — all callable by any unrelated wallet with no special privileges, exactly matching the in-scope reachable paths ("pre-creating or pre-seeding the HyperSwap V2 TOKEN/LT pair before graduation"). The only requirement is sizing the pre-seed ratio extreme enough (as demonstrated by the 200x test case) to exceed the fixed 99% swap budget — an attacker fully controls the ratio and can iterate cheaply since only dust-level token/LT amounts are needed.

### Recommendation
Re-derive `_swapBudget`'s cap (or make it dynamic) against the actual worst-case achievable skew ratio rather than a static 99%-of-inventory heuristic, or add a secondary rebalancing pass / iterative correction so the deposit-time price gap is bounded to an acceptable bps tolerance regardless of how extreme the pre-seed ratio is, rather than accepting an unbounded "materially off curve-close" residual for sufficiently large attacks.

### Proof of Concept
The existing regression test demonstrates the residual directly: `test_hostilePreSeed_budgetCappedSwap_isNotProfitable` stages a pre-seed with `reserveToken = tokensForLP / 100` and `reserveLt = ltFromPair * 200`, confirms the unconstrained optimal swap exceeds the 99%-of-`tokensForLP` budget, calls `finalizeGraduation`, and asserts the resulting pool price is more than 20% off the curve-close ratio: [4](#0-3)

```text
    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }
```

```text
    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
```

```text
    ///         TOKEN-side rebalance swap exhausts its full budget (~99% of
    ///         `tokensForLP`) without reaching the cached ratio, so the pool
    ///         deposits materially off curve-close. Finalize must still succeed
    ///         (no brick), the over-funded LT side must be confiscated to the
    ///         owner, and the pre-seeder must end net-negative.
    function test_hostilePreSeed_budgetCappedSwap_isNotProfitable() public {
        (address tokenAddr,) = _launchToken();
        _enterGraduating(tokenAddr);

        (uint256 tokensForLP, uint256 ltFromPair,,) = bonding.pendingGraduation(tokenAddr);

        // Extreme LT-rich shape: TOKEN side at 1% of target, LT side at 200x.
        // The optimal TOKEN-in swap to reach the cached ratio is ~1.4x
        // `tokensForLP`, so the 99%-of-`tokensForLP` budget cap binds and the
        // pool stays ~2x off curve-close after the swap.
        uint256 reserveToken = tokensForLP / 100;
        uint256 reserveLt = ltFromPair * 200;

        // M-02 precondition: the optimal swap exceeds the budget (this is the
        // budget-capped regime, distinct from the swap-rounds-to-zero fallback
        // covered by the dust tests above).
        assertGt(
            _noFeeSwapInputUncapped(reserveToken, reserveLt, tokensForLP, ltFromPair),
            (tokensForLP * 99) / 100,
            "setup: optimal rebalance swap must exceed the per-side budget (M-02 regime)"
        );

        deal(tokenAddr, griefer, reserveToken);
        address hyperPair = _grieferMintPreSeed(tokenAddr, reserveToken, reserveLt);
        uint256 grieferLp = MockHyperswapPair(hyperPair).balanceOf(griefer);
        uint256 ownerLtBefore = lt.balanceOf(bonding.owner());

        bonding.finalizeGraduation(tokenAddr);
        assertTrue(bonding.isGraduated(tokenAddr), "finalize must succeed despite an unrecoverable pre-seed");

        // The accepted residual: no bounded swap can correct a 200x LT-rich
        // pre-seed, so the pool opens materially off curve-close.
        assertGt(
            _poolPriceLtPerToken(hyperPair, tokenAddr),
            (((ltFromPair * 1e18) / tokensForLP) * 12) / 10,
            "M-02 regime: pool opens materially off curve-close"
        );
```
