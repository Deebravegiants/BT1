Confirmed: the docs explicitly instruct app developers to trust `data.shop` from `WebhookMetadata` as the tenant identifier for processing webhook side-effects (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), while the gem's own HMAC check only covers the raw body.

### Title
Webhook `shop` field is not covered by the HMAC signature, allowing shop/tenant spoofing in `Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate`, which calls `verifiable_query.to_signable_string` [1](#0-0) . `Request#to_signable_string` returns only `@raw_body`, and none of the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, or `shopify-api-version` headers are included in the signed bytes [2](#0-1) . Despite this, `Registry.process` passes `request.shop` straight through to the handler as an authenticated tenant identifier after only checking the HMAC [3](#0-2) .

### Finding Description
This is the same bug class as the external report: a field that the application logic treats as trust-bound but that is not actually covered by the cryptographic check protecting the request — an identity-binding gap. In the report, `fullWeightDuration` was mutable outside the binding that should have constrained it (an active election); here, `shop` is delivered outside the binding that should constrain it (the HMAC signature).

Concretely:
- `HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` value [4](#0-3) .
- For webhooks, `to_signable_string` is defined as just the raw JSON body [2](#0-1) , and `shop` is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header, entirely outside the signed bytes [5](#0-4) .
- `Registry.process` raises only if the HMAC over the body is invalid, then immediately constructs `WebhookMetadata.new(... shop: request.shop ...)` and dispatches it to the app's handler [3](#0-2) .
- The gem's own documentation instructs integrators to treat `data.shop` as the authoritative tenant/shop identifier for downstream processing (e.g. enqueuing background jobs keyed by shop domain) [6](#0-5) .

Because the `api_secret_key` is a single shared secret for the app across all its installed shops (not per-shop), an unprivileged attacker who has installed the same app on their own store can:
1. Receive one legitimately-HMAC-signed webhook from Shopify for their own store (any topic), or otherwise obtain any raw body/HMAC pair valid for the app's shared secret.
2. Replay that exact body + HMAC to the app's webhook endpoint, but substitute a victim's real `shopify-shop-domain` value in the header.
3. The HMAC check still passes, because the header is not part of the signed bytes — only the body is checked.
4. `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain, which per the gem's own documented usage pattern is trusted by downstream app code as the tenant to act upon.

### Impact Explanation
This breaks the equality `authenticated_shop == shop_used_for_tenant_dispatch`: the HMAC authenticates only `body`, but the app-facing API surfaces `shop` as if it were equally authenticated. This enables cross-tenant confusion/access — an attacker-controlled webhook body can be attributed to an arbitrary victim shop domain, causing the app to process, store, or act on attacker data under another merchant's tenant context. This matches the Critical "cross-tenant access" impact category, since the gem's public API (`Registry.process` → `WebhookMetadata`) is the sole authentication boundary host apps rely on per the documented usage.

### Likelihood Explanation
Likelihood is high for any app that installs the library as documented: no access token, `client_secret`, or privileged access is required — only the ability to install the app on an attacker-owned store (a normal, unprivileged action) to obtain one valid HMAC/body pair, and the ability to send an HTTP POST to the app's public webhook endpoint with a forged shop-domain header.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the value verified against the HMAC, or independently verify that the shop asserted in the header corresponds to a shop with an active, valid installation/session before dispatching to the handler, rather than passing the raw header value through as `WebhookMetadata#shop` unauthenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw JSON body and its valid `x-shopify-hmac-sha256` value signed by the app's shared `api_secret_key`.
2. Attacker POSTs to the app's webhook endpoint with the same raw body and same HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC successfully (it only checks the body) [7](#0-6) , then invokes the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"` [8](#0-7) .
4. The app, following the documented pattern of trusting `data.shop` for tenant-scoped processing [9](#0-8) , processes attacker-controlled data under the victim shop's tenant context.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
