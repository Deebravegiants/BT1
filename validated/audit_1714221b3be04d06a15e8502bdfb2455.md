Confirmed: `Router._computeBuy` (`packages/contracts/src/Router.sol:127-148`) has no guard against `pair.tokenBalance() > reserveToken`. `Bonding.previewLtUntilGraduation` was patched with an explicit `if (realBalance >= reserveToken) return ltUntilThreshold;` guard [1](#0-0) , but `Router._computeBuy`'s own identical cap-branch arithmetic was never given the same guard [2](#0-1) .

### Title
Unrelated-wallet Token donation permanently DoSes the curve's overflow-cap buy path in `Router._computeBuy` - (File: packages/contracts/src/Router.sol)

### Summary
Any unrelated wallet can `transfer()` the launched `Token` directly into its `Pair` to inflate `pair.tokenBalance()` above the pair's stored `reserveToken`. `Router._computeBuy` — the function `Router.buy` uses on every curve buy, and the one that engages whenever a buy is large enough that the naive constant-product quote would exceed the pair's real token balance — subtracts the (now-inflated) capped `tokensOut` from `reserveToken` without checking that `reserveToken >= tokensOut`. Once the donation makes `tokenBalance() > reserveToken`, any buy whose uncapped quote would exceed the real balance underflows this subtraction and reverts, permanently bricking every large/closing buy on that curve.

### Finding Description
`Router._computeBuy` computes the naive AMM quote, then caps it at the pair's live `tokenBalance()` when that quote would exceed real supply:
```solidity
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;   // underflows if tokensOut > reserveToken
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
    amountInUsed = cappedReserveAsset - reserveAsset;
}
``` [2](#0-1) 

`tokenBalance()` is a live `IERC20.balanceOf` read on the pair (see the same pattern in `Bonding.canGraduate`) [3](#0-2) , and it is exactly the value an attacker inflates by donating `Token` directly to `Pair` — the codebase's own donation-attack regression test proves this is reachable, staging `realBalance > reserveToken` via a plain `Token.transfer(pairAddr, donatedTokens)` from an unprivileged wallet [4](#0-3) , and confirming the broken invariant with `assertGt(realBalance, reserveToken)` [5](#0-4) .

The engineers already recognized this exact underflow shape and patched it — but only in `Bonding.previewLtUntilGraduation`'s mirrored supply-leg arithmetic:
```solidity
// Donation-inflated `realBalance`: supply trigger unreachable, defer to USD leg.
if (realBalance >= reserveToken) return ltUntilThreshold;

uint256 cappedReserveToken = reserveToken - realBalance;
``` [6](#0-5) 

`Router._computeBuy` performs the identical `reserveToken - tokensOut` subtraction (with `tokensOut` capped to `realBalance`, so functionally the same as `reserveToken - realBalance` once the cap binds) but has no equivalent guard. Once a donation pushes `tokenBalance() > reserveToken`, any buy whose naive quote exceeds `realBalance` — i.e. any buy that would otherwise legitimately cap and drain the remaining curve supply, including the graduation-triggering closing buy — reverts with Solidity's arithmetic-underflow panic instead of completing.

The existing test `test_donation_zapBuyStillSucceeds` only exercises a small, non-cap-triggering buy after the donation [7](#0-6) ; it never drives a buy large enough to hit the `tokensOut > realBalance` branch in `Router._computeBuy` post-donation, so the underflow revert path is untested and unguarded.

### Impact Explanation
Once triggered, every subsequent buy sized to exceed the (attacker-inflated) real balance reverts unconditionally — there is no way for `Zap.buy` or a direct `Bonding.buy` caller to complete a cap-binding/closing buy on that curve ever again, since the underlying arithmetic panics before any state changes. This freezes the supply-side graduation trigger for that token: if the USD trigger also can't be reached (e.g. a flat or declining LT exchange rate, the exact "flat/bear markets" scenario the supply trigger exists for per the project's own documentation) [8](#0-7) , the token can become permanently stuck on the curve, unable to graduate and unable to accept large buys, for a one-time donation cost of the token amount required to push `tokenBalance()` past `reserveToken` (achievable, per the project's own regression test setup, with a drain-and-donate sequence costing roughly the launch's initial virtual LT reserve). This is a permanent freezing of the curve's trading functionality and of any capital that depends on the curve reaching graduation, satisfying the "permanent freezing of trader, creator or LP funds" bar.

### Likelihood Explanation
The precondition (`Token.transfer` of a launched token into its own `Pair`) is explicitly listed as an in-scope, permissionless, unrelated-wallet action, and the codebase's own test suite already demonstrates the exact state (`realBalance > reserveToken`) is reachable cheaply by any wallet without special privileges — no admin role, no timing dependency, no reentrancy required. The only additional step needed to realize this specific bug (as opposed to the already-patched `previewLtUntilGraduation` path) is that a large-enough buy must land afterward, which happens naturally on any actively-traded curve nearing sellout or graduation.

### Recommendation
Add the same guard used in `Bonding.previewLtUntilGraduation` to `Router._computeBuy`: if `realBalance >= reserveToken` (or equivalently `tokensOut >= reserveToken` after capping), the supply-side cap is degenerate and the function should either fall back to treating the buy as fully absorbed at `amountInUsed = amountIn` (since there is no real supply distinction left to compute against) or revert with a clear, intentional error rather than an arithmetic panic — mirroring the intent already expressed by `OverflowCapDegenerate` for the `cappedReserveToken == 0` case, extended to cover `cappedReserveToken` underflowing rather than merely equaling zero.

### Proof of Concept
1. Launch a token via `Bonding.launch` / `Zap.createToken` normally.
2. An unrelated wallet drains a large slice of the curve via direct `bonding.buy` calls (bypassing Zap) sized so `tokensOut` crosses the `250_000_000e18` LP-reserve floor, exactly as `_stageDonationAttack` does [4](#0-3) .
3. That same wallet transfers the tokens it just bought straight back to the `Pair` address via a plain ERC20 `transfer`, inflating `pair.tokenBalance()` above `reserveToken` (proven by `test_donation_realBalanceExceedsReserveToken`) [5](#0-4) .
4. Any subsequent buyer submits a buy sized so the naive constant-product quote (`tokensOut = reserveToken - k/newReserveAsset`) exceeds the now-inflated `realBalance` — this is the exact condition that trips the `tokensOut > realBalance` branch in `_computeBuy`.
5. `cappedReserveToken = reserveToken - tokensOut` underflows (`tokensOut` is now `realBalance`, which exceeds `reserveToken`), and the call reverts with Solidity's `Panic(0x11)` instead of completing the buy — bricking that curve's overflow-cap/closing-buy path for every future oversized buy attempt.

    function _stageDonationAttack(
        address tokenAddr
    ) internal returns (uint256 drainLtSpent, uint256 donatedTokens) {
        address pairAddr = bonding.getTokenInfo(tokenAddr).pair;
        address drainer = makeAddr("donationDrainer");
        // Size the drain so `tokensOut > 250M` (the LP-reserve floor) under
        // any `VIRTUAL_LIQUIDITY_USD`. Constant-product math gives
        // `tokensOut = TOTAL_SUPPLY × ltIn / (virtual + ltIn)`, which crosses
        // 250M (= ¼ of TOTAL_SUPPLY) when `ltIn = virtual / 3`. Spending the
        // full opening virtual reserve lands `tokensOut = 500M` — plenty of
        // headroom to push `realBalance > reserveToken` after the donation.
        drainLtSpent = _initialVirtualLt();
        lt.mintDirect(drainer, drainLtSpent);
        if (!bonding.isRouter(drainer)) bonding.addRouter(drainer);
        vm.startPrank(drainer);
        lt.approve(address(curveRouter), drainLtSpent);
        bonding.buy(drainLtSpent, tokenAddr, 0, drainer);
        vm.stopPrank();
        donatedTokens = Token(tokenAddr).balanceOf(drainer);
        vm.prank(drainer);
        Token(tokenAddr).transfer(pairAddr, donatedTokens);
    }
