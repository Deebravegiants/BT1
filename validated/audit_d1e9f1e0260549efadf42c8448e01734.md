Audit Report

## Title
Missing balance verification when transferring ERC20 tokens in `ERC20Transactor` - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` credit/debit the XCM holding register with the caller-supplied `amount` based solely on the ERC20 `transfer()` call's revert status and boolean ABI return, without confirming via a `balanceOf` before/after check that the checking account or beneficiary actually received/lost that exact `amount`. [1](#0-0) [2](#0-1)  This mirrors the class of ERC20 non-standard-transfer accounting bugs (fee-on-transfer/rebasing tokens) described in the Sudoswap/Qubit precedent, and is wired live into Asset Hub Westend's `AssetTransactors`. [3](#0-2) 

## Finding Description
In `withdraw_asset_with_surplus`, the transactor sends `IERC20::transferCall` from the user's account to `TransfersCheckingAccount`, then on `Ok(return_value)` with no revert and `abi_decode_returns_validate` returning `true`, unconditionally constructs `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` — crediting the XCM holding register with the full requested `amount` regardless of what the checking account actually received. [4](#0-3)  Symmetrically, `deposit_asset_with_surplus` transfers `amount` from `TransfersCheckingAccount` to the beneficiary and treats `Ok(true)` from `transferCall` as full success without checking the beneficiary's actual balance delta. [5](#0-4)  Neither function calls `balanceOf` before/after the transfer, so the only guards are contract-revert detection and the boolean return value decode — both of which a compliant-but-non-standard ERC20 (fee-on-transfer, rebasing, or deflationary token) can satisfy while moving a different amount than requested. This is wired into Asset Hub Westend's live `AssetTransactors` tuple used by `xcm_executor::Config`. [3](#0-2)  The existing test `non_existent_erc20_will_error` demonstrates that arbitrary `AccountKey20` addresses can be used directly as ERC20 asset ids in `WithdrawAsset`/`DepositAsset` XCM instructions without any privileged registration step, confirming this path is reachable by an unprivileged signed origin via `PolkadotXcm::execute`. [6](#0-5) 

## Impact Explanation
`TransfersCheckingAccount` is a single shared pot for all ERC20 XCM transfers on the chain. If a user deploys a fee-on-transfer or rebasing ERC20 contract and uses it as the asset in a `WithdrawAsset`/`DepositAsset` XCM sequence, the runtime's holding-register accounting (based on the nominal `amount`) diverges from the checking account's real token balance for that contract. Repeated use could desynchronize accounting relative to real balances of that specific token held by the checking account, but any resulting loss is confined to token deployed/controlled by the attacker themselves and interacts only with the shared checking account's balance of that same non-standard token — it does not permit draining unrelated assets or native Balances, since each ERC20 contract's balance ledger is independent per-token. The affected value is bounded by whatever amount of that specific non-standard token flows through the checking account, and the attacker is generally the one supplying/controlling the divergent token behavior.

## Likelihood Explanation
Triggerable by any unprivileged account able to submit `WithdrawAsset`/`DepositAsset` XCM instructions referencing an `AccountKey20`-addressed ERC20 asset, with no privileged role required, matching the code path demonstrated in `non_existent_erc20_will_error`. [6](#0-5)  It requires deployment of a non-standard ERC20 contract (fee-on-transfer/rebasing) by the attacker and interaction limited to that specific token's balance in the shared checking account.

## Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, query `balanceOf` on the relevant account before and after the `transfer()` call, and use the observed balance delta — rather than the caller-supplied `amount` — to construct the `AssetsInHolding` credit and to determine deposit success. Reject or adjust accounting if the observed delta does not match the requested amount.

## Proof of Concept
1. Deploy an ERC20 contract on pallet-revive whose `transfer()` deducts a fee (e.g., transfers `amount * 99 / 100` while returning `true`).
2. Submit an XCM message via `PolkadotXcm::execute` with `WithdrawAsset` referencing that contract as an `AccountKey20` asset with `amount = 100`, following the pattern in `non_existent_erc20_will_error`. [7](#0-6) 
3. Observe that `withdraw_asset_with_surplus` credits the holding register with the full `100` despite the checking account only receiving `99`. [4](#0-3) 
4. Follow with `DepositAsset`; `deposit_asset_with_surplus` will attempt to move `100` out of the checking account per the holding register's belief, progressively depleting the checking account's real balance of that token relative to the runtime's accounting. [8](#0-7)
