### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `ShopifyAPI::Utils::HmacValidator` verifies only covers the raw request body. The `shop` value handed to the host application's webhook handler is therefore never actually authenticated, breaking the binding `hmac-verified bytes == bytes the app trusts as the tenant identity`.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` recomputes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field: [2](#0-1) 

For a webhook `Request`, `to_signable_string` returns only `@raw_body`, while `shop` is read straight from the (attacker-supplied) `shop-domain` header, entirely outside the signed content: [3](#0-2) 

The `shop` value derived this way is passed unchanged into `WebhookMetadata` and forwarded to the host application's `WebhookHandler#handle`, i.e. it becomes the tenant identity the app acts on: [4](#0-3) [5](#0-4) 

Because `api_secret_key` is a single app-wide client secret (not per-shop), any merchant who has installed the app on their own store can obtain a legitimately-signed `(raw_body, hmac)` pair from a real webhook delivery to their own shop. Since the header carrying the tenant identity is outside the HMAC scope, that same `(raw_body, hmac)` pair can be replayed to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain, and `HmacValidator.validate` will still accept it — the equality the app implicitly relies on, `hmac_verified(raw_body) == shop_is_authentic`, does not hold.

### Impact Explanation
This breaks the tenant-identity binding for a Critical-severity outcome: cross-tenant access. A host application that uses `WebhookMetadata#shop` (as documented/intended by this gem) to key data lookups, updates, or deletions will process attacker-chosen body content under a victim's shop identity — e.g. injecting fake order/customer data, triggering `shop/redact` or `customers/redact`-style side effects, or overwriting per-shop configuration for a shop the attacker does not own — without ever needing the victim's access token or the app's `client_secret`.

### Likelihood Explanation
Likelihood is moderate-to-high for any attacker capable of installing the target app on a shop they control (a very low bar for public apps), since that gives them a genuinely-signed `(body, hmac)` pair they can freely replay with a forged `shop-domain` header against the same publicly reachable webhook endpoint.

### Recommendation
Bind the tenant identity into the signed material, or otherwise authenticate the `shop-domain` header, e.g.:
- Include `shop-domain` (and `topic`/`webhook-id` if relevant) in `to_signable_string`, matching Shopify's actual webhook signing behavior only if Shopify also signs those headers server-side; otherwise
- Cross-check the `shop-domain` header against a shop that is independently known to have a valid, active installation/session for this app before trusting it in `WebhookMetadata`, and document that host apps must not treat `shop` as authenticated without this check.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook subscribed by the app (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends — a valid `(raw_body, hmac)` pair signed with the app's `api_secret_key`.
2. Attacker replays this exact `raw_body` and `hmac` header to the same app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` compute the check purely from headers/body that omit `shop-domain`, so `Utils::HmacValidator.validate` returns `true`: [3](#0-2) 
4. `Registry.process` accepts the request and calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to process attacker-controlled data under the victim's tenant identity: [1](#0-0)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
