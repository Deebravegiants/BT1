Based on my investigation, I found a concrete analog that matches the reserved bug class: **a field acted on but not covered by the HMAC**.

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC covers exclusively the JSON body [1](#0-0) . The `shop` identity, however, is read directly and unauthenticated from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header [2](#0-1) . `Registry.process` validates only the body's HMAC, then dispatches the handler using this unauthenticated `shop` value as the tenant identity [3](#0-2) .

### Finding Description
The equality the app relies on is: `HMAC-authenticated bytes == tenant identity acted upon`. In this gem that equality is broken: `Utils::HmacValidator.validate(request)` cryptographically authenticates only `@raw_body` (via `to_signable_string`) using the app's single, shared `client_secret` — the same secret is valid for webhooks from *every* shop that has installed the app, since Shopify webhook HMACs are not per-shop-secret but per-app-secret. The `shop` attribute passed downstream to `WebhookMetadata` (`request.shop`) comes straight from an HTTP header with no cryptographic binding to the signed body or to the HMAC itself.

Any unprivileged internet user who can install the app on their own (attacker-controlled) shop can legitimately receive a validly-HMAC-signed webhook payload for a given topic (e.g. `orders/create`, `customers/data_request`) generated by their own store activity. Because the header value carrying the shop identity is excluded from the signable string, that same valid `(body, hmac)` pair can be replayed to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to point at a **different, victim shop**. `HmacValidator.validate` will still return `true` because it only checks the body/secret pair, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event happened for the victim's shop [4](#0-3) .

### Impact Explanation
This is a cross-tenant data/identity confusion: an attacker can cause the host application's webhook handlers to process attacker-supplied data attributed to a shop they do not control (e.g. injecting fabricated order/customer records, or triggering GDPR `customers/redact`/`shop/redact` handlers) under an arbitrary victim shop's identity, since nothing in this gem binds the `shop-domain` header to the signed payload.

### Likelihood Explanation
Any party able to install the app on a shop they control (a normal, unprivileged onboarding flow requiring no special credentials) can capture one legitimate `(body, hmac)` pair and replay it against the shared webhook endpoint with an arbitrary `shop-domain` header value, since HMAC verification never inspects that header.

### Recommendation
Bind the shop identity into the signable material, or otherwise cryptographically verify that the shop header corresponds to a shop session/registration the app itself created (e.g. requiring the `webhook-id` returned by the Admin GraphQL registration for that specific shop to be checked), instead of trusting the unauthenticated `shopify-shop-domain` header as the sole tenant identifier in `Webhooks::Request#shop` and `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, obtaining a validly-signed webhook delivery: body `B`, header `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same body `B` and `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` (`B`) with the app's shared `client_secret` and succeeds [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the host app to process attacker-controlled data as if it originated from `victim-shop.myshopify.com` [6](#0-5) .
