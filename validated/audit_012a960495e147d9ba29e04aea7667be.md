Audit Report

## Title
`queued_bytes` desynchronizes from real page sizes across the v5→v6 storage migration, letting senders bypass the delivery-fee escalation threshold - (File: cumulus/pallets/xcmp-queue/src/migration/v6.rs)

## Summary
`unversioned::UncheckedMigrateV5ToV6::on_runtime_upgrade` hard-codes the new `queued_bytes` field to `0` for every existing outbound channel during the translate closure, regardless of whether that channel already has non-empty pages between `first_index` and `last_index` in `OutboundXcmpMessages` [1](#0-0) . Since `send_fragment` only ever adds to `queued_bytes` via `saturating_add` and never resyncs against actual stored page contents [2](#0-1) , any channel with a pre-migration backlog keeps an understated byte counter until it fully drains.

## Finding Description
The migration's `translate` closure copies `recipient`, `state`, `signals_exist`, `first_index`, and `last_index` from the v5 struct but sets `queued_bytes: 0` unconditionally, without inspecting or summing the actual `OutboundXcmpMessages` pages that already exist for that channel [3](#0-2) . After the upgrade, `send_fragment` is the code path exercised by any unprivileged `send_xcm` call; it only increments `queued_bytes` for newly appended fragments/pages and never recomputes it from the real page lengths [2](#0-1) . The fee-escalation check compares this drifting counter against `threshold = max_total_size / THRESHOLD_FACTOR` to decide whether to call `increase_fee_factor` [4](#0-3) , so an understated counter delays or suppresses the intended fee escalation. The only place `queued_bytes` is forced back to a value consistent with reality is when the channel fully drains (`first_index == last_index`), confirming the counter is not otherwise self-correcting while backlog remains queued. The v6→v7 migration contains the identical zero-seeding pattern with an explicit acknowledging comment ("Corrects itself over time."), confirming this is a recognized characteristic of the migration's accounting rather than a one-off oversight, and the same gap applies unremarked to `UncheckedMigrateV5ToV6`.

## Impact Explanation
For any HRMP channel with non-empty outbound pages at the moment of the v5→v6 upgrade, `queued_bytes` starts at `0` instead of the true backlog size. Ordinary, unprivileged `send_xcm` calls into that channel keep the counter understated relative to actual occupancy, so `increase_fee_factor` is not triggered when it should be, weakening the anti-congestion delivery-fee mechanism for as long as the pre-existing backlog persists. This does not cause fund loss or double-spend; the impact is a temporary weakening of an economic congestion-pricing control, self-limiting because it corrects once the channel fully drains.

## Likelihood Explanation
The precondition (upgrading from storage v5 to v6 while a channel has queued pages) is a common, realistic operational state for any busy production parachain, not a contrived edge case. No governance or privileged action is needed to trigger the drift post-upgrade — any account issuing `send_xcm` exercises `send_fragment` and perpetuates the understated counter. The divergence is deterministic and reproducible.

## Recommendation
When performing the v5→v6 (and v6→v7) translation, compute `queued_bytes` by summing the encoded lengths of existing `OutboundXcmpMessages` pages for `first_index..last_index` per channel instead of hard-coding `0`, so the invariant `queued_bytes == sum(page lengths)` holds immediately after migration.

## Proof of Concept
1. Set `StorageVersion` to 5 and use the `v5::OutboundXcmpStatus` storage alias to insert an `OutboundChannelDetails` for a sibling `ParaId` with `first_index = 0`, `last_index = 3`.
2. Insert three non-trivial pages directly into `OutboundXcmpMessages::<Test>` for indices `0..3`, simulating a pre-existing backlog.
3. Run `UncheckedMigrateV5ToV6::<Test>::on_runtime_upgrade()`.
4. Assert `status_for(sibling).queued_bytes == 0` while the actual summed page length is `> 0`, proving desync exists immediately post-migration.
5. Call `send_xcm::<XcmpQueue>(...)` repeatedly and confirm `queued_bytes` remains offset from the real total by the original backlog amount.
6. Drain the channel via `XcmpQueue::take_outbound_messages` until `first_index == last_index`, and observe `queued_bytes` is only forced to a correct value (`0`) at that point, confirming the counter is wrong for the entire time the pre-migration backlog exists.
