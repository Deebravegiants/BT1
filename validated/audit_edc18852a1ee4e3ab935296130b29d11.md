### Title
Webhook `shop-domain` (and `topic`/`api-version`/`webhook-id`) Headers Are Not Covered by the HMAC, Allowing Tenant Spoofing of Otherwise-Valid Webhooks - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw JSON body for HMAC verification, while the shop identity (`shop-domain`), `topic`, `api-version`, and `webhook-id` are taken verbatim from HTTP headers that are excluded from the signature. `Registry.process` validates the HMAC and then unconditionally trusts these unauthenticated header values to attribute the webhook to a tenant and dispatch it to the host application's handler.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac` [1](#0-0) . For webhooks, `Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` is decoded from the `hmac-sha256` header [2](#0-1) [3](#0-2) . However `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read directly from separate, un-signed headers [4](#0-3) .

`Registry.process` validates only the HMAC (which covers the body bytes) and then immediately trusts `request.shop`, `request.topic`, etc. to build the `WebhookMetadata` handed to the host application's handler, without any additional binding between the verified bytes and the shop identity: [5](#0-4) .

This breaks the expected identity binding: `shop attributed to handler == shop that the HMAC actually authenticates`. Since Shopify's HMAC only proves "this body came from Shopify," but says nothing about which header values accompanied it, any two request contexts that carry the same raw body (e.g., a webhook payload that is topic/shop-agnostic, replayed, or captured and retransmitted with substituted headers) get an identical valid signature regardless of which shop-domain, topic, or webhook-id headers are attached. The test suite in `test/webhooks/request_test.rb` confirms header values are read independently of body/HMAC and are never cross-checked against the signed content [6](#0-5) .

### Impact Explanation
An application that dispatches per-shop side effects (e.g., updating merchant-specific records, revoking access, deleting data for GDPR topics) keyed off `WebhookMetadata#shop` as returned by this gem can be made to act on the wrong tenant if a validly-HMAC'd body is delivered/replayed with an attacker-controlled `shopify-shop-domain` header, since this gem provides no guarantee binding the header to the signed bytes. This is a cross-tenant data integrity issue rooted entirely in this gem's verification contract.

### Likelihood Explanation
Exploitation requires the attacker to possess a validly-signed raw body (e.g., via webhook capture/replay or a topic where body content is shop-independent) and to control or manipulate the delivery headers reaching the host app's endpoint — a realistic scenario for any HTTP-delivered webhook proxy, load balancer, or replay path outside Shopify's own delivery infrastructure, since this gem does no header-to-signature binding to prevent it.

### Recommendation
Include the security-relevant header values (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material, or otherwise cryptographically bind them to the request before trusting `request.shop` for tenant attribution in `Registry.process`. At minimum, document that host applications must independently verify shop identity via other authenticated means (e.g., cross-referencing an existing offline session for that shop) rather than relying solely on `WebhookMetadata#shop`.

### Proof of Concept
1. Shopify (or an attacker with network position between Shopify and the app, or replay of a captured request) sends a webhook with `raw_body = B` and a correct `shopify-hmac-sha256` computed over `B` using the app's secret.
2. The attacker/proxy retransmits the same `raw_body = B` and the same valid `hmac-sha256` header, but substitutes `shopify-shop-domain: victim-shop.myshopify.com` for the original shop header value (and/or a different `topic`).
3. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` because it only checks `B` against the HMAC — `lib/shopify_api/utils/hmac_validator.rb` lines 12-31 — and never inspects the shop header.
4. `Registry.process` proceeds to invoke the host handler with `shop: request.shop` set to the attacker-chosen value — `lib/shopify_api/webhooks/registry.rb` lines 188-200 — causing the host application to process the payload as if it belonged to `victim-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end
