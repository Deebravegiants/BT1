### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant shop-attribution spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` attribute passed to webhook handlers directly from the `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature validated by `Utils::HmacValidator` only ever covers the raw request body. This breaks the identity binding `HMAC-verified-bytes == data-acted-on`, letting a party that legitimately possesses a validly-signed webhook body (any merchant/tenant using the shared app secret) relabel which shop that payload is attributed to when replaying it to the app's webhook endpoint.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the (attacker-controllable) headers hash, independent of that signed body: [2](#0-1) 

`HmacValidator.validate` verifies the signature exclusively against `to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` checks the HMAC and then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed into the app's handler, with no additional binding of the shop field to the signature or to any registered subscription record: [4](#0-3) 

Because the HMAC secret (`api_secret_key`) is shared across all shops that install the same app, any tenant/shop that receives a legitimately-signed webhook for its own store can capture that request and re-POST it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) headers rewritten to name a different shop. `HmacValidator.validate` will still succeed, because the signature only certifies the JSON body — not the headers used to attribute that body to a tenant. The equality that should hold, `hmac_signed_bytes == tenant_identity_used_by_handler`, is broken: the signed bytes bind only the payload content, while the tenant identity (`shop`) is taken from unauthenticated header bytes.

### Impact Explanation
Any app built on this gem that relies on `WebhookMetadata#shop` (as delivered by `Registry.process`) to decide which tenant's records to update/read is exposed to cross-tenant data confusion: a legitimate but malicious/compromised merchant can cause the app to process their own valid webhook body under another shop's identity. Depending on how the host app persists webhook data, this can result in cross-tenant data corruption or disclosure — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires the attacker to already be an authorized user of the target app on at least one shop (so they can receive a genuinely-signed webhook), and requires the host application to trust the `shop` field from `WebhookMetadata` without an independent binding to the specific webhook subscription/shop record (e.g., cross-checking `webhook_id` against a per-shop registration table). The gem itself provides no such binding and exposes `shop` as if it were an authenticated field, making misuse by an integrating app straightforward and not clearly called out as unsafe in the gem's own webhook processing API.

### Recommendation
Do not treat header-derived `shop`/`topic` values as authenticated. Either (a) include the relevant headers (shop domain, topic, webhook id) in the HMAC-signed material (bind them into `to_signable_string`), or (b) require/encourage `Registry.process` callers to independently correlate `webhook_id` to a previously-registered, shop-scoped subscription before trusting `WebhookMetadata#shop`, and document that the header-derived `shop` is not cryptographically bound to the HMAC signature.

### Proof of Concept
1. App is installed on Shop A and Shop B, both processed by the same `ShopifyAPI` app instance (shared `api_secret_key`).
2. Shopify sends a legitimately HMAC-signed webhook to the app for Shop A: body `B`, headers include `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
3. An operator with access to Shop A's webhook delivery (e.g., via Shopify's webhook resend feature, or a proxy capturing the request) resends the exact same body `B` and HMAC header to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `shop-b.myshopify.com`.
4. `HmacValidator.validate` recomputes `HMAC(secret, B)` — unchanged — and returns `true` per `hmac_validator.rb:26-31`.
5. `Registry.process` builds `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)` per `registry.rb:198-199` and invokes the app handler, which now processes Shop A's payload as if it belonged to Shop B.

Note: I was unable to fully verify how downstream host applications typically consume `WebhookMetadata#shop` (that logic lives outside this gem), so the concrete data-confusion impact depends on integrator behavior; the root-cause identity-binding gap within this gem's own code is confirmed by the citations above.
