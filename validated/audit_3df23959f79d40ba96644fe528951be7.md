### Title
DepositOnChainUtxos/Emporium on-chain UTXO minting can be double-counted via a "mirror" ERC20 whose `balanceOf` aliases another listed token's real balance, minting shielded value without real backing - (File: contracts/Hinkal.sol :: transact)

### Summary
`Hinkal.transact` validates each `erc20TokenAddresses[i]` independently by snapshotting `balanceOf` before/after the external action and requiring `balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount` [1](#0-0)  The only proof that two entries in `erc20TokenAddresses` represent distinct value is a circuit check that the two address *values* differ, not that their underlying balances are independent [2](#0-1) . An attacker can deploy a "mirror" token `B` whose `balanceOf` reads the real balance of a legitimate token `A` (so `oldBalances`/`newBalances` for index B always equal those for index A) while `B.transferFrom` is either a no-op (on deposit) or forwards to `A`'s real transfer (on withdrawal). This lets one real token movement satisfy the balance equation twice - once for `A` and once for `B` - so `DepositOnChainUtxosExternalAction` (or `Emporium` in its stateless/unsigned path) mints two on-chain UTXOs from a single real deposit, and a later withdrawal of the fake "B" UTXO can be coded to drain real `A` tokens from the shared vault balance backing other users.

### Finding Description
The broken equality is: **real tokens entering the vault for index i == `utxoAmount` credited for index i**, checked per-index in `Hinkal.transact`:
```
balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount
``` [3](#0-2) 

This check relies on `getBalancesForArray` returning *independent* balances per token address [4](#0-3) . Nothing in the contracts or circuit enforces that two distinct addresses in `circomData.erc20TokenAddresses` correspond to distinct real value stores - the circuit's `distinctErc20AddressChecks` only forces the numeric address *values* to differ [2](#0-1) , and there is no on-chain token registry/whitelist consulted anywhere in `HinkalHelper` (`grep` for `TokenRegistry`/`isRegistered`/`allowedToken` shows no active enforcement).

Exploit flow (using `DepositOnChainUtxosExternalAction`, but the same reasoning applies to `Emporium` with `signerAddress == address(0)`, which runs the unsigned/stateless op path `op.endpoint.call{value: op.value}(op.callData)` [5](#0-4)  and performs the identical balance-snapshot bookkeeping in `runAction` [6](#0-5) ):

1. Attacker deploys real token `A` (or uses an existing one) and a malicious contract `B` where `B.balanceOf(x) = A.balanceOf(x)` and `B.transferFrom` is a stub returning `true` without moving value.
2. Attacker calls `transact` with `erc20TokenAddresses = [A, B]`, `onChainCreation = [true, true]`, `amountChanges = [0, 0]`, zero `inputNullifiers` for both (required by `checkOnchainCreation` [7](#0-6) ), `externalActionId` pointing at `DepositOnChainUtxosExternalAction`, `externalActionMetadata` encoding `utxoAmounts = [[100],[100]]`.
3. `_externalTransact` calls `runAction`, which for `i=0` transfers 100 real `A` tokens from user to `Hinkal` (increasing real balance by 100), and for `i=1` calls `B.transferFrom(...)` which is a no-op (no real movement) [8](#0-7) . Both a `UTXO(100, A, ...)` and `UTXO(100, B, ...)` are returned.
4. Back in `transact`, `oldBalances=[S0,S0]` and `newBalances=[S0+100, S0+100]` (index 1 mirrors index 0's real change because `B.balanceOf` == `A.balanceOf`). Both per-index checks pass: `balanceDif[0]=100=utxoAmount[0]`, `balanceDif[1]=100=utxoAmount[1]` [1](#0-0) .
5. Two on-chain commitments are inserted into the tree: 100 units of "token A" and 100 units of "token B", although only 100 real tokens ever entered the vault.
6. Later, the attacker withdraws the fake "B" UTXO via an internal transact (`externalActionId == 0`) with `amountChanges=[-100]`, `erc20TokenAddresses=[B]`. `_internalTransact` calls `transferERC20TokenOrETH(B, attacker, 100)` → `B.transfer(attacker, 100)`, which the attacker codes to internally call `A.transfer(attacker, 100)` [9](#0-8) . This pulls 100 *real* `A` tokens out of the pooled vault balance that also backs every other depositor's legitimate `A`-denominated shielded UTXOs.

Existing guards fail because: (a) `performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation` only validate array-length and zero-nullifier/zero-amountChanges preconditions for `onChainCreation`, never that addresses map to independent balances [7](#0-6) ; (b) `verifyProof`/circuit constraints never see or constrain the actual on-chain UTXO amounts minted by an external action - those come entirely from the external action's return value and are only checked against Solidity `balanceOf` snapshots, which the attacker's mirror contract can trivially satisfy; (c) `rootHashExists`, `insertNullifiers`, `nonReentrant` are irrelevant to this bookkeeping bug.

### Impact Explanation
The attacker mints shielded value ("token B", 100 units) with zero real backing, then can redeem it by draining real `A` tokens from the shared vault - which is the pooled balance backing *all* other users' legitimate `A` UTXOs. This is theft of other users' shielded funds / protocol insolvency, matching the **Critical** severity category ("minting shielded value without backing"). It is fully repeatable per attacker-deployed mirror token and scales with the size of the pooled vault balance for the aliased token.

### Likelihood Explanation
Preconditions are entirely within an unprivileged attacker's control: deploying arbitrary token contracts (including custom `balanceOf`/`transferFrom` logic), choosing `erc20TokenAddresses` ordering/values, and crafting `externalActionMetadata` for `DepositOnChainUtxosExternalAction` or an `Emporium` stateless op. No signature, relay, or admin role is needed for the deposit step (relay is optional per `performHinkalChecks`, and the attacker can act as `originalSender` directly with `relay == address(0)`) [10](#0-9) . Only proof generation for the (trivial, zero-input, zero-amountChanges) circuit computation is required, which is straightforward since `onChainCreation[i]=true` forces `inTotal=outTotal=0` for that index in-circuit, unrelated to the actual minted UTXO amount.

### Recommendation
Do not trust per-address `balanceOf` snapshots as the sole backing proof for on-chain UTXO minting. Either (1) maintain Hinkal-internal per-token accounting (a `mapping(address => uint256) internalReserve`) updated only through vetted transfer paths instead of relying on external `balanceOf` calls that an attacker-controlled token can spoof, (2) require `erc20TokenAddresses` to be members of a governance-controlled token registry/allowlist before they can be used as on-chain UTXO labels, and/or (3) constrain on-chain UTXO amounts inside the ZK circuit (bind `outCommitments`/`outAmounts` for `onChainCreation` indices to the actual minted amount) rather than deriving them purely from an external action's return value checked only via a Solidity balance diff.

### Proof of Concept
Foundry test plan:
1. Deploy `MockA` (standard ERC20, mint 1000 to attacker, `approve` Hinkal's `DepositOnChainUtxosExternalAction`).
2. Deploy `MirrorB` with `balanceOf(addr) => MockA.balanceOf(addr)` and `transferFrom(...) => return true` (no state change).
3. Craft `CircomData` with `erc20TokenAddresses=[A,B]`, `onChainCreation=[true,true]`, `amountChanges=[0,0]`, zero `inputNullifiers`, `externalActionData.externalActionId` = registered id for `DepositOnChainUtxosExternalAction`, `externalActionMetadata = abi.encode([[100],[100]])`. Generate a valid proof locally for this trivial (zero in/out per index) circuit instantiation.
4. Call `Hinkal.transact(...)`. Assert it does **not** revert, and that two `NewCommitment`/on-chain leaves are inserted (100 for A, 100 for B).
5. Assert: `MockA.balanceOf(hinkal) - balanceBefore == 100` (only 100 real tokens moved) while `sum(onchain UTXO amounts minted) == 200` - violating `net tokens entering Hinkal == sum(amountChanges) + sum(on-chain UTXO amounts minted)`.
6. (Optional extension) Implement `MirrorB.transfer` to call `MockA.transfer` internally, then perform a second `transact` spending the "B" UTXO via `_internalTransact` with `amountChanges=[-100]`, and assert `MockA.balanceOf(hinkal)` decreases by 100 real tokens, confirming real-value drain from the shared pool backing other users' `A` UTXOs.

    function _internalTransact(CircomData calldata circomData) private {
        bool hasPaidToRelay = false;
        for (uint64 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            int256 deltaAmountChange = _calculateDeltaAmount(circomData, i);

            if (deltaAmountChange > 0) {
                require(
                    circomData.externalActionData.externalAddress == msg.sender,
                    "Deposit should come from the sender"
                );
                transferERC20TokenFromOrCheckETH(
                    circomData.erc20TokenAddresses[i],
                    circomData.externalActionData.externalAddress,
                    address(this),
                    uint256(circomData.amountChanges[i])
                );
            } else {
                uint256 sumAbs = uint256(-deltaAmountChange);
                uint256 relayFee = 0;
                if (circomData.relay != address(0)) {
                    uint256 flatFee = circomData.feeStructure.feeToken ==
                        circomData.erc20TokenAddresses[i]
                        ? circomData.feeStructure.flatFee
                        : 0;

                    require(
                        sumAbs >= flatFee,
                        "Relay Fee is over withdraw amount"
                    );

                    uint256 recipientAmount = ((10000 -
                        circomData.feeStructure.variableRate) *
                        (sumAbs - flatFee)) / 10000;

                    relayFee = sumAbs - recipientAmount;

                    if (relayFee > 0) {
                        transferERC20TokenOrETH(
                            circomData.erc20TokenAddresses[i],
                            circomData.relay,
                            relayFee
                        );
                    }
                    hasPaidToRelay = true;
                }
                if (sumAbs - relayFee > 0) {
                    transferERC20TokenOrETH(
                        circomData.erc20TokenAddresses[i],
                        circomData.externalActionData.externalAddress,
                        sumAbs - relayFee
                    );
                }
            }
        }
        require(
            circomData.relay == address(0) || hasPaidToRelay,
            "relay not paid"
        );
    }
