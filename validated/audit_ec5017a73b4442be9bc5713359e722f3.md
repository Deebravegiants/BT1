### Title
Stale `Precisions` lookup in `on_timeout`/`on_accept` causes fund loss or over-refund on `pallet-hyper-fungible-token` when EVM-side decimals are reconfigured mid-flight - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet-hyper-fungible-token` encodes a cross-chain transfer amount at `send()` time using the `Precisions` storage value in effect at that moment, but never carries that conversion factor with the in-flight ISMP request. When the request later times out (`on_timeout`) or, for symmetry, when the equivalent reverse decoding happens on `on_accept`, the pallet re-reads whatever `Precisions` value is *currently* stored for that `(asset_id, chain)` pair rather than the value used to encode the message. If a `CreateOrigin` (`update_token`) legitimately updates that precision (e.g. correcting a decimals misconfiguration, or re-pointing to a redeployed contract) while a request is in flight, the amount conversion silently uses a different scaling factor than the one embedded in the original message, producing an incorrect refund/mint amount. This is directly analogous to the ECO L1/L2 bridge `inflationMultiplier` two-step update bug: a mutable, non-versioned scaling factor is read at two different points in time for the same logical transfer.

### Finding Description
`send()` computes the outgoing `erc20_amount` using the precision on file at dispatch time: [1](#0-0) 

The `Message` body dispatched over ISMP carries only the raw scaled `amount` (`alloy_primitives::U256`) — it does not carry the `erc_decimals`/`decimals` pair that produced it: [2](#0-1) 

`update_token` allows `CreateOrigin` to change the recorded EVM-side decimals for an `(asset_id, chain)` pair at any time, in place, with no coordination with requests that are already dispatched and pending: [3](#0-2) 

When the request later times out, `on_timeout` re-derives the refund amount by reading `Precisions` *again*, at refund time, and using whatever decimals are currently stored, then converts back to local balance: [4](#0-3) 

The underlying conversion helper divides (or multiplies) by `10^(erc_decimals - local_decimals)` with `saturating_sub`, so if `erc_decimals` was raised between send and timeout the refund is scaled down and can floor to zero (funds burned/frozen); if `erc_decimals` was lowered, `saturating_sub` clamps the exponent to zero and the refund is minted without any division, over-crediting the beneficiary from pallet escrow (insolvency / unbacked release of custodied funds): [5](#0-4) 

The same stale-read pattern also affects `on_accept`, which independently re-reads `Precisions` for the source chain at delivery time rather than using any value fixed at request-creation time: [6](#0-5) 

### Impact Explanation
Because the amount-scaling factor is a single mutable storage cell read independently at encode-time and at decode-time (send vs. timeout/accept), any legitimate re-registration or decimals correction via `update_token` while requests are in flight can:
- Freeze user funds on timeout: the refund computed via `convert_to_balance` floors to less than what was escrowed/burned (in the extreme, to zero), permanently trapping the difference in the pallet's escrow account or destroying it via the earlier burn.
- Cause an unbacked release: if precision is lowered, the refund's division is skipped entirely (`saturating_sub` → 0), releasing/minting far more than what was originally escrowed for that transfer, draining the pallet's custody account to the benefit of one user at the expense of others' escrowed balances.

This satisfies "concrete theft or permanent freezing of funds" / "unbacked mint" thresholds for Medium-High severity, matching the class of the source report exactly (stale, unsynced two-step multiplier used across a bridge boundary).

### Likelihood Explanation
The trigger does not require a malicious actor: `update_token` is an ordinary maintenance call (e.g. fixing a decimals typo, or re-registering a contract on a chain after a redeploy) that any `CreateOrigin` may perform as routine operations, and there is nothing in the flow that checks for or blocks in-flight requests before doing so. Any chain with active bridge traffic and periodic configuration maintenance is exposed; the window of exposure is the full ISMP request timeout period, which can be minutes to hours.

### Recommendation
Do not re-derive the scaling factor from live storage at decode time. Instead:
- Encode the `erc_decimals` (or the full scaling factor) used at `send()` time directly into the `Message` body (or into a per-commitment side-storage keyed by the request commitment), and use that captured value in `on_timeout`/`on_accept` decoding instead of re-reading `Precisions`.
- Alternatively, disallow `update_token` from mutating `Precisions` for a chain while any request dispatched under the old precision is still outstanding (e.g. require a full pause/drain of in-flight commitments for that asset/chain, or version the precision so each request pins the version it was encoded with).

### Proof of Concept
1. Register asset `X` with `local_decimals = 6`, `Precisions[X, ChainA] = 6`.
2. Alice calls `send()` with `amount = 1_000_000` (i.e. 1 token, 6 decimals). `convert_to_erc20(1_000_000, erc_decimals=6, local_decimals=6)` scales by `10^0` → `erc20_amount = 1_000_000` embedded in the dispatched `Message`; Alice's balance is burned/escrowed for `1_000_000`.
3. Before the request is delivered or times out, `CreateOrigin` calls `update_token` to correct `Precisions[X, ChainA]` from `6` to `18` (a legitimate maintenance action, e.g. matching the real ERC20 contract's decimals that were misconfigured at registration).
4. The request times out. `on_timeout` reads the *current* `Precisions[X, ChainA] = 18` and calls `convert_to_balance(value=1_000_000, erc_decimals=18, local_decimals=6)`, dividing by `10^12`. Since `1_000_000 < 10^12`, the result truncates to `0`.
5. Alice's escrowed/burned `1_000_000` units are never refunded — a full loss of funds caused purely by the timing of an unrelated, legitimate precision-correction call relative to her pending transfer.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
