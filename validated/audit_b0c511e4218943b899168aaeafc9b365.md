Confirmed: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read directly from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header [2](#0-1) . `Registry.process` validates only the HMAC-over-body via `HmacValidator.validate(request)` and then forwards `request.shop` straight into `WebhookMetadata` passed to the app's handler, with no cross-check that the body/topic actually originated for that shop [3](#0-2) . `HmacValidator` computes the signature purely from `to_signable_string`/`secret` [4](#0-3) .

### Title
Webhook shop-domain header not covered by HMAC allows cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` binds the trust decision to `shop` (`x-shopify-shop-domain` header) but the HMAC signature that `Registry.process` validates is computed solely over the raw request body, never over the shop header. Any attacker who can obtain one validly-signed webhook body+HMAC pair from Shopify (trivially available by installing the app on their own free/dev/partner shop and triggering any subscribed topic) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary victim shop domain in the header.

### Finding Description
The equality that should hold is: `shop-that-produced-this-signed-payload == shop-the-handler-is-told-it-came-from`. Because `to_signable_string` only returns `@raw_body` [1](#0-0) , the shop identity is never part of what `HmacValidator.validate_signature` authenticates [4](#0-3) . `Registry.process` treats a valid HMAC as sufficient proof of authenticity for the whole request, then trusts `request.shop` unconditionally when building `WebhookMetadata` for the handler [5](#0-4) . An attacker who is a legitimate (even free-tier) merchant of the app can capture one authentic `(raw_body, hmac)` pair for their own shop and shop domain, then send an HTTP request to the app's public webhook endpoint with the same body/HMAC but an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` still returns true because it only checks the body, so the forged shop identity is delivered to the app's handler as if it were authentic.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook consumers: the shop field, which every downstream `WebhookHandler#handle` implementation is expected to use for tenant-scoped operations (updating records, triggering side effects, `shop/redact`, `customers/redact`, `customers/data_request`, etc.), is attacker-controlled while the signature check gives host applications false confidence that it is a Shopify-authenticated statement of shop identity. This can lead to cross-tenant access/manipulation (e.g., an attacker-owned shop's order/product data being falsely attributed to and processed against a victim shop's tenant record, or GDPR-mandatory redact/data-request webhooks executing against the wrong shop).

### Likelihood Explanation
Exploitation requires no privileged credentials: any user able to install the target app on their own (even free development) Shopify store obtains a validly HMAC-signed webhook payload for arbitrary topics they can trigger, and the webhook endpoint is public-facing by design. Reissuing the captured request with a modified header is trivial.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed material, or independently verify that `request.shop` corresponds to a shop the app actually has an active session/installation for before trusting it, rather than relying on header-only unauthenticated identity alongside a body-only HMAC.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com` and subscribe to any webhook topic (or use a mandatory topic).
2. Capture the resulting POST request: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(secret, B)`, per `to_signable_string` in `lib/shopify_api/webhooks/request.rb`).
3. Replay the request to the app's webhook endpoint with the same body `B` and header `H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which passes because only `B` is verified [6](#0-5) ; the handler then receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes attacker-controlled body content as if it belongs to the victim tenant.
