### Title
Reentrancy via checks-effects-interactions violation in `withdraw` — escrow decremented after external token/ETH transfer - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of the IntentGateway's internal `withdraw` function performs the external token transfer (native `.call{value:}` or ERC20 `.call(transfer)`) to the beneficiary **before** decrementing the corresponding `_orders[commitment][token]` escrow balance, and similarly transfers the transaction fee before deleting `_orders[commitment][TRANSACTION_FEES]`. This is the same checks-effects-interactions violation pattern described in the reported `CollateralEscrowV1` finding.

### Finding Description
In `withdraw(WithdrawalRequest memory body, bool isRefund)`: [1](#0-0) 

the loop iterates over `body.tokens`, checks `_orders[body.commitment][token] == 0`, then immediately performs the external interaction (`beneficiary.call{value: amount}("")` for native tokens, or `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` for ERC20s) and only afterward executes `_orders[body.commitment][token] -= amount;`. The same pattern repeats for the transaction-fee payout: the fee token transfer happens before `delete _orders[body.commitment][TRANSACTION_FEES];`.

This differs from the CEI-compliant sibling implementation in the main EVM app, `IntentsBase._withdraw`, which decrements `_orders[body.commitment][token]` **before** making the external transfer: [2](#0-1) 

The accompanying reentrancy regression test suite (`IntrinsicIntentsReentrancyTest.sol`) documents that the main EVM contract was previously vulnerable to exactly this class of bug and was patched by setting `_filled[commitment]` before the loop and reordering effects before interactions: [3](#0-2) 

The Tron contract's `withdraw` does set `_filled[body.commitment] = beneficiary;` before the loop, which blocks re-entrant calls into `withdraw` itself for the same commitment via a fresh `onAccept`/`onGetResponse` dispatch (since `_filled` gating would need to be checked upstream). However, the per-token escrow balance (`_orders[commitment][token]`) is still mutated after the external call within the *same* `withdraw` invocation's loop, so any reentrant call that can reach state depending on `_orders[commitment][token]` (for the token not yet decremented in this same loop, or the fee balance not yet deleted) sees stale, unspent escrow accounting during the callback window.

### Impact Explanation
If the token being transferred is a malicious/reentrant ERC20 (e.g. ERC777-style hooks, or a token contract that calls back into the gateway or another integrated contract during `transfer`) or if the beneficiary is a malicious contract receiving native token via `.call`, the callback executes while `_orders[commitment][token]` for later tokens in the same withdrawal and `_orders[commitment][TRANSACTION_FEES]` still show the pre-payout escrowed balance. Any code path that reads these mappings during that window (directly or via an external view/query triggered by the reentrant call, e.g. cross-chain cancellation `onGetResponse` storage-proof flows that query `_filled`/`_orders` state, or future integrations) can be misled into believing funds are still escrowed or into re-using them. This is a permanent-fund-accounting-risk class of bug: escrowed user/solver funds intermediating a token bridge/intents settlement path.

### Likelihood Explanation
Reachability: `withdraw` is invoked by `onAccept` (for `RedeemEscrow`/`RefundEscrow` requests, authenticated but driven by relayer-submitted cross-chain messages) and by `onGetResponse` (also relayer-driven, based on submitted state proofs). Both are attacker-adjacent entry points reachable by any relayer/prover submitting valid but adversarially-timed proofs, and the beneficiary/token addresses in `WithdrawalRequest` originate from data set at `placeOrder`/`fillOrder` time by ordinary users, so an attacker can register a malicious ERC20 or malicious beneficiary contract as part of a legitimate order and then trigger settlement, giving it control of the callback during `withdraw`. The severity is tempered because `_filled[commitment]` is set first (blocking exact-same-commitment double-withdrawal reentry through the two host-gated entry points), so full exploitation depends on identifying a reachable secondary effect that reads/uses the not-yet-decremented `_orders` mapping during the callback — this requires further investigation to construct a concrete fund-draining PoC, but the code violates CEI in a security-sensitive escrow-release path exactly as flagged in the analog report.

### Recommendation
Apply the same fix already used in `IntentsBase._withdraw`: decrement `_orders[body.commitment][token]` (and delete the `TRANSACTION_FEES` entry) **before** performing the external `.call`/`transfer`, for every branch in `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `withdraw` function. Consider also using `SafeERC20.safeTransfer` instead of raw low-level `.call` for consistency with the main EVM app, and add a reentrancy guard consistent with `IntentGatewayV2.placeOrder`'s `nonReentrant` modifier if external hooks are a supported design point.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];

            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();

        }
