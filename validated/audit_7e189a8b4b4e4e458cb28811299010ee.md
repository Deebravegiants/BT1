### Title
Accrual-time RAY-value overflow permanently freezes an overlarge debt market - ([File: common/src/rates/simulate.rs](rs-lending-xlm--012/common/src/rates/simulate.rs))

### Summary

A sufficiently large borrowed position can grow until `borrowed * borrow_index` no longer fits in `i128`, after which every state-changing operation on that market panics during mandatory interest accrual, permanently freezing withdrawals, repayments, liquidations, and further index updates. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description

`accrue_step` computes utilization by first unscaling `borrowed` and `supplied` shares through `scaled_to_original`. [4](#0-3)  `scaled_to_original` performs a half-up `Ray` multiplication, which raises `MathOverflow` when the product is unrepresentable rather than clamping to the protocol's index ceiling. [5](#0-4) [6](#0-5) 

The borrow-index cap is applied only after these value calculations, so a market can reach the RAY-value ceiling while `borrow_index` remains below `MAX_BORROW_INDEX_RAY`. [7](#0-6) [8](#0-7) 

Every pool mutation loads the market through `synced_market`, `renewed_market`, or `load_leg`, each of which runs `global_sync` before the requested operation. [2](#0-1)  Standalone `update_indexes` follows the same path through `ops::market::accrue`. [9](#0-8) 

An unprivileged user can create the precondition through ordinary `controller::supply` and `controller::borrow` calls, after which `controller::update_indexes` is callable to advance the market into the overflow state. [10](#0-9) [11](#0-10)  Because the failing accrual runs before state is committed, `last_timestamp` does not advance and every subsequent attempt repeats the same panic. [12](#0-11) [13](#0-12) 

### Impact Explanation

The affected market becomes permanently unable to settle funds: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot seize collateral, and keepers cannot advance indexes. [14](#0-13) [15](#0-14) [16](#0-15) 

This is more than fail-closed input validation: after the threshold is crossed, even risk-reducing operations and administrative parameter updates begin by performing the same failing accrual. [17](#0-16) [2](#0-1) 

The repository's stress test demonstrates the state directly: after `update_indexes` fails with `MathOverflow`, both withdrawal and repayment also fail with `MathOverflow` while the borrow index remains below its configured maximum. [18](#0-17) 

### Likelihood Explanation

The attack requires no privileged role, leaked key, malformed parameter, oracle manipulation, or third-party contract; it uses ordinary `supply`, `borrow`, and `update_indexes` entrypoints. [10](#0-9) [11](#0-10) 

The practical barrier is substantial capitalization and sustained high utilization: the existing proof uses one billion 18-decimal tokens supplied and approximately 98% borrowed, backed by collateral in another market. [19](#0-18)  Interest then grows the RAY-denominated debt until multiplication crosses `i128::MAX` before the index cap engages. [20](#0-19) 

Accordingly, the issue is realistically Medium: it produces permanent freezing of a market, but it depends on an extremely large position and prolonged high-utilization accrual rather than a small immediate transaction. [21](#0-20) [22](#0-21) 

### Recommendation

Make accrual saturate rather than panic when scaled debt or supply value exceeds the representable RAY domain, or enforce market caps that keep `scaled_shares * index / RAY` representable for the maximum configured index. [23](#0-22) [7](#0-6) 

A safer boundary is to compare `borrowed` against `i128::MAX * RAY / borrow_index` before unscaling and cap the borrow index before the next accrual would cross that value. [24](#0-23)  Similar protection is needed for `supplied * supply_index`, `supplied * new_supply_index`, and `borrowed * new_borrow_index` inside `update_supply_index`, `supply_index_reward_shortfall`, and `calculate_supplier_rewards`. [25](#0-24) [26](#0-25) 

### Proof of Concept

1. Create or select an 18-decimal market with an aggressive but admitted interest-rate curve and high caps. [27](#0-26) 
2. Through `controller::supply`, deposit approximately `1_000_000_000 * 10^18` base units into that market. [28](#0-27) 
3. Through `controller::borrow`, use sufficient separate collateral to borrow approximately 98% of that liquidity. [29](#0-28) 
4. Allow sustained high-utilization interest to accrue and call `controller::update_indexes` for the market. [30](#0-29) 
5. Once `borrowed * borrow_index / RAY` exceeds `i128::MAX`, `accrue_step` panics in `scaled_to_original` before reaching the borrow-index cap. [24](#0-23) [8](#0-7) 
6. Subsequent `withdraw` and `repay` calls fail identically because both paths accrue before applying their operations. [2](#0-1) [31](#0-30)

pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

        return old_index;

    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
