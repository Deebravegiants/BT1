**Basis for rejection:** The claimed identity break does not hold. In `system-repay`, when `amount >= debt` (full repayment, i.e., `capped-amount = debt`), the reduction is computed as: [1](#0-0) 

`calc-principal-ratio-reduction(capped-amount, scaled-principal, debt) = mul-div-down(capped-amount, scaled-principal, debt)`. Since `capped-amount` equals `debt` exactly (both are the *same* variable value when repaying in full), this reduces to `mul-div-down(debt, scaled-principal, debt)`, which is `floor(debt * scaled-principal / debt) = scaled-principal` **exactly**, with zero rounding error, regardless of how `debt` itself was rounded relative to the originally borrowed `amount`. [2](#0-1) 

Tracing the exact numeric example: with `idx=3`, `INDEX-PRECISION=2`, borrowing `amount=5` gives `scaled-amount = ceil(5*2/3) = 4`, so `principal-scaled = 4`. `debt = calc-cumulative-debt(4,3) = ceil(4*3/2) = 6` (indeed `> amount`, confirming the double round-up the question describes). Calling `system-repay(6)` (i.e., repaying exactly `debt`) gives `capped-amount = min(6,6) = 6`, `principal-reduction = floor(6*4/6) = 4`, `capped-reduction = min(4,4) = 4`, so `updated-scaled-principal = 4 - 4 = 0` — **exactly zero, no dust**. [3](#0-2) 

Additionally, `principal-repaid = mul-div-down(6, 5, 6) = 5` and `interest-paid = 6 - 5 = 1`, which is credited to `assets` — i.e., the extra unit from the double round-up is paid *by the attacker to the LPs*, not extracted from them. This is the opposite of the claimed impact: the attacker bears a small extra cost, LPs gain, and `principal-scaled` returns exactly to zero on full repayment. The self-canceling design (using the identical `debt` value as both numerator input and denominator in `calc-principal-ratio-reduction`) prevents any dust accumulation described in the question, so the round/loop PoC would show `principal-scaled` returning to `0` after each full borrow+repay cycle rather than growing.
