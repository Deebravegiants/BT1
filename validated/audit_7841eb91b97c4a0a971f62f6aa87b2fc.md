### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` are trusted from unauthenticated headers while the HMAC only signs the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by checking only that the raw request body was HMAC-signed with the app's shared secret. It then trusts the shop domain, topic, webhook id, and API version straight from HTTP headers that are never covered by that signature, and uses the unauthenticated `topic` header to select which registered handler runs and the unauthenticated `shop` header as the tenant identity passed to that handler.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes the fields Shopify sends with a webhook: [1](#0-0) 

Only `to_signable_string` (`@raw_body`) is used as the signed payload; `hmac`, `topic`, `shop`, `webhook_id`, and `api_version` are all read directly from HTTP headers, none of which are part of the signable string.

`Utils::HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` using the app's `Context.api_secret_key` and constant-time-compares it to the received `hmac`: [2](#0-1) 

`Registry.process` uses this check as the sole authentication gate, then dispatches based on the *unauthenticated* `topic` header and forwards the *unauthenticated* `shop` header as the tenant identity to the handler: [3](#0-2) 

Because the app's webhook signing secret (`Context.api_secret_key`) is shared across every shop that has the app installed — it is not per-shop — a valid `(raw_body, hmac)` pair captured from a legitimate webhook delivered to *any* shop (including one the attacker legitimately controls, e.g. their own free development/trial installation of the target app) remains a cryptographically valid pair regardless of which `shop-domain`, `topic`, `webhook-id`, or `api-version` headers are attached to it. The binding that should hold is:

`shop/topic used by the handler == shop/topic that was actually HMAC-authenticated`

but the code instead enforces only:

`raw_body == HMAC-authenticated bytes`, and separately trusts `shop`/`topic` from the request headers with no cryptographic tie to that HMAC.

### Impact Explanation
An attacker who has legitimately received (or can trigger) any webhook delivery for their own shop can capture a valid `(body, hmac)` pair, then replay it to the app's public webhook endpoint with:
- an arbitrary `shopify-shop-domain` header, so `WebhookMetadata#shop` names a victim tenant the attacker does not control, and/or
- an arbitrary `shopify-topic` header, so `Registry.process` (`@registry[request.topic]&.handler`) dispatches the body to a completely different handler than the one the body was originally signed for.

This lets an unprivileged internet user inject attacker-crafted data into another merchant's tenant data path (cross-tenant access) or trick a handler into processing a body it never expected under a false topic, since the app receiving `WebhookMetadata` from this library has no way to detect the forgery — the library already told it the HMAC was valid. This matches the report's core failure mode (an identity/authorization check that answers permissively because the acted-upon field is not covered by the signature that was actually verified), qualifying as Critical (cross-tenant access) per the stated impact categories.

### Likelihood Explanation
Exploitation requires only a single legitimately-signed webhook body from any shop where the app is installed (trivially obtainable by installing/trialing the target app on the attacker's own store, which any internet user can do) plus the ability to send an arbitrary HTTP POST with custom headers to the app's public webhook URL. No access to `api_secret_key`, access tokens, or privileged accounts is required.

### Recommendation
Bind the tenant/topic identity into the authenticated payload before trusting it: e.g. include `shop`, `topic`, and `webhook_id` in the signable string (if Shopify's signing scheme is extended to support this), or, more practically, require host applications to cross-check the header-derived `shop` against a shop for which they already hold a valid access token/session before acting on the webhook, and treat `topic`/`shop` headers as untrusted routing hints rather than authenticated identity. At minimum, document prominently that `Utils::HmacValidator.validate` for webhooks only proves body integrity/origin from the shared app secret, and does **not** authenticate `shop`, `topic`, `webhook_id`, or `api_version`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store (`attacker-shop.myshopify.com`) and receives a legitimate webhook, e.g. `carts/update`, with body `B` and a valid `X-Shopify-Hmac-Sha256: H` computed by Shopify with the app's shared secret.
2. Attacker crafts a new POST to the app's webhook endpoint reusing the exact same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: orders/create` (or whatever topic/handler the attacker wants to trigger)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` (still `B`) and succeeds, since the shared secret and body are unchanged — see `lib/shopify_api/webhooks/registry.rb:190` and `lib/shopify_api/utils/hmac_validator.rb:12-31`.
4. `Registry.process` looks up the handler for the attacker-supplied `orders/create` topic and invokes it with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to process attacker-controlled data as if it originated from, and belongs to, the victim tenant.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
