## Title
Webhook Shop-Domain Header Not Covered by HMAC Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-verifying the raw request body, but the `shop` value it forwards to the app's handler as the trusted tenant identifier comes from the `X-Shopify-Shop-Domain` header, which is never included in the signed payload. This breaks the identity binding `authenticated_body == shop_the_body_is_attributed_to`, letting an attacker who controls their own legitimate install of the app replay a genuinely-signed webhook body while claiming it belongs to a different (victim) shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shop-domain` header, which is not part of that signable string: [2](#0-1) 

`Registry.process` verifies only this body-only HMAC and then hands `request.shop` directly to the app's handler as the authoritative tenant identity: [3](#0-2) 

The documented usage pattern confirms apps are expected to trust `data.shop` as the shop the webhook pertains to (e.g. to key session lookups or background jobs): [4](#0-3) 

Because `api_secret_key` is shared by the app across every shop that installs it, any attacker who installs the app on their own store legitimately receives Shopify-signed webhooks (valid `raw_body` + valid `hmac-sha256`) for that store. Nothing in `to_signable_string` or in `Registry.process` binds that signature to the shop the attacker actually owns. The attacker can therefore resend the exact same `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with an arbitrary victim shop domain; `HmacValidator.validate` still succeeds because it only checks the body against the shared secret, and `Registry.process` will invoke the handler with `shop: <victim-domain>`.

### Impact Explanation
This is a cross-tenant identity confusion: the gem exposes an unauthenticated field (`shop`) as if it were authenticated, letting one tenant (an app installer) forge webhook events attributed to any other tenant. Depending on how the host app uses `WebhookMetadata#shop` (session lookup, data deletion for mandatory compliance topics like `shop/redact`/`customers/redact`, revoking access on `app/uninstalled`, etc.), this can trigger destructive or data-disclosing actions against a shop the attacker does not control — a cross-tenant access/action vulnerability.

### Likelihood Explanation
Exploitation requires only an unprivileged internet user with their own (potentially free/dev) shop where the target app is installed — no access token, `client_secret`, or victim credentials are needed. Capturing a valid `(raw_body, hmac)` pair for their own shop's traffic and replaying it with a modified header is straightforward HTTP request forgery, well within reach of a standard attacker per the threat model.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` value to the verified body before it is passed to `WebhookMetadata`/the handler, so that a valid signature can only ever be attributed to the shop it was actually generated for.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, a legitimate shop they control.
2. Shopify sends a real webhook, e.g. `orders/create`, to the app with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and some `raw_body`.
3. Attacker captures this `(raw_body, hmac)` pair (their own traffic, no interception needed).
4. Attacker sends a new POST to the app's webhook endpoint with the same `raw_body` and `X-Shopify-Hmac-Sha256`, but with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate(request)` in `Registry.process` succeeds (body unchanged), and `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))` is invoked, causing the app to act on the attacker-controlled body as if it originated from `victim-shop.myshopify.com`.
