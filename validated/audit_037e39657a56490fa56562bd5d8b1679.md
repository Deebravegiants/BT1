Audit Report

## Title
Unauthenticated remote panic in gateway HTTP trigger handler via negative `strings.Repeat` count in `normalizeHex` - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

## Summary
`validateHexInput` (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go` L267-283) does not require the `0x` prefix and only checks `len(input) <= expectedLength`, so a maximum-length, prefix-less hex string passes validation. That same value is later passed into `normalizeHex` (L333-340), which computes `expectedHexLength - len(hexStr)` (`length-2` minus the full unstripped length) and feeds it to `strings.Repeat`, which panics on a negative count. This is reachable pre-authorization from `resolveWorkflowID` (L342-366), which is invoked from `HandleUserTriggerRequest` (L95-109) before `authorizeRequest`.

## Finding Description
`validateHexInput` enforces lowercase, `len(input) <= expectedLength` (42 for `workflowOwner`, 66 for `workflowID`), and that `strings.TrimPrefix(input, "0x")` decodes as hex via `hex.DecodeString`. It never requires the `0x` prefix to actually be present. A 42-character, all-lowercase-hex string with no `0x` prefix (e.g., `workflowOwner`) satisfies all three checks: it's lowercase, its length (42) is `<= 42`, and it decodes fine as hex (even length, valid hex chars).

That same string then flows into `resolveWorkflowID` → `normalizeHex(workflowOwner, workflowOwnerLength)`. Inside `normalizeHex`, `hexStr := strings.TrimPrefix(input, "0x")` does nothing (no prefix present), so `hexStr` remains 42 characters. `expectedHexLength := length - 2` is 40. `strings.Repeat("0", expectedHexLength-len(hexStr))` becomes `strings.Repeat("0", -2)`, which panics per Go's documented behavior (`strings.Repeat` panics if `count < 0`).

This call chain (`HandleUserTriggerRequest` → `resolveWorkflowID` → `normalizeHex`) executes before `authorizeRequest` is called, so no authentication/authorization gate is passed before the panic is triggered. The entry point `HandleJSONRPCUserMessage` in `core/services/gateway/handlers/capabilities/v2/http_handler.go` (L392-402) calls `h.triggerHandler.HandleUserTriggerRequest` synchronously with no `recover()` wrapper at that call site, so the panic is not caught within this file's code path. ## Impact Explanation
This is a legitimate logic bug that causes an unrecovered panic reachable pre-authorization via a normal, unprivileged request path (`workflows.execute` JSON-RPC method to the gateway). Whether this results in a crash of a single request-handling goroutine versus taking down the whole gateway process depends on whether some outer layer (e.g., the network/websocket read loop, or a `recover.WrapRecover`/`recover.HandleFn` call in `core/recovery/recover.go`) wraps the call chain leading into `HandleJSONRPCUserMessage`. I found the `recovery` package (`WrapRecover`, `HandleFn`) exists in the codebase but could not confirm within the index whether it (or an equivalent recover boundary) actually wraps the goroutine that processes incoming user JSON-RPC messages for this handler. If such a wrapper exists, the blast radius is limited to a single failed request (logged and safely dropped); if it does not, the panic could crash the gateway process, which would be a genuine availability impact (denial of service to the gateway node). This uncertainty is material to severity: the underlying bug is real and exploitable pre-auth, but the actual availability impact scope (single-request failure vs. full process crash) is unverified in this review.

## Likelihood Explanation
High reachability: any unauthenticated caller able to send a JSON-RPC `workflows.execute` request to the gateway can trigger this by supplying a `workflowOwner` (or `workflowID`) field that is exactly the maximum allowed length and lacks the `0x` prefix, with no valid credentials, signature, or prior state required, since the panic occurs before `authorizeRequest` runs. [5](#0-4) 

## Recommendation
- In `validateHexInput`, require a `0x` prefix (or consistently strip it before length-checking) and validate length against `expectedLength-2` hex characters after stripping, not against the full prefixed length.
- In `normalizeHex`, guard against `expectedHexLength < len(hexStr)` and return an error instead of assuming `hexStr` is always shorter.
- Verify whether the goroutine/loop invoking `HandleJSONRPCUserMessage` is wrapped in a `recover()` boundary (e.g., via `core/recovery/recover.go`'s `WrapRecover`/`HandleFn`); if not, add one so a single malformed request cannot crash the gateway process.

## Proof of Concept
Send an unauthenticated `workflows.execute` JSON-RPC request to the gateway with a 42-character, all-lowercase-hex `workflowOwner` value (no `0x` prefix), e.g.:
```json
{
  "jsonrpc": "2.0",
  "id": "req-1",
  "method": "workflows.execute",
  "params": {
    "workflow": {
      "workflowOwner": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
      "workflowName": "test",
      "workflowTag": "test"
    },
    "input": {}
  }
}
```
This passes `validateWorkflowOwner`/`validateHexInput` and then panics inside `normalizeHex` via `resolveWorkflowID`. A Go unit test calling `normalizeHex("aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa", workflowOwnerLength)` directly reproduces the panic (`strings: negative Repeat count`) and would confirm the fix once `normalizeHex`/`validateHexInput` are patched.

func validateHexInput(input string, expectedLength int) error {
	if input != strings.ToLower(input) {
		return errors.New("must be lowercase")
	}

	if len(input) > expectedLength {
		return fmt.Errorf("hex string too long: expected at most %d characters, got %d", expectedLength, len(input))
	}

	hexStr := strings.TrimPrefix(input, "0x")
	_, err := hex.DecodeString(hexStr)
	if err != nil {
		return errors.New("must be a valid hex string")
	}

	return nil
}

// normalizeHex normalizes a hex string by stripping 0x prefix, padding with leading zeros, and adding 0x prefix back
func normalizeHex(input string, length int) string {
	hexStr := strings.TrimPrefix(input, "0x")
	// length-2 because we'll add "0x" prefix
	expectedHexLength := length - 2
	paddedHex := strings.Repeat("0", expectedHexLength-len(hexStr)) + hexStr
	return "0x" + paddedHex
}

func (h *httpTriggerHandler) resolveWorkflowID(ctx context.Context, triggerReq *jsonrpc.Request[gateway_common.HTTPTriggerRequest], requestID string, callback handlers.Callback) (string, error) {
	h.lggr.Debugw("resolving workflow ID", "workflowID", triggerReq.Params.Workflow.WorkflowID, "workflowOwner", triggerReq.Params.Workflow.WorkflowOwner, "workflowName", triggerReq.Params.Workflow.WorkflowName, "workflowTag", triggerReq.Params.Workflow.WorkflowTag, "requestID", requestID)
	workflowID := triggerReq.Params.Workflow.WorkflowID
	if workflowID != "" {
		workflowID = normalizeHex(workflowID, workflowIDLength)
		_, found := h.workflowMetadataHandler.GetWorkflowReference(workflowID)
		if !found {
			h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, fmt.Sprintf("Workflow not found. 'workflowID' %s is not a valid workflow ID", workflowID), callback)
			return "", errors.New("workflow not found")
		}
		return workflowID, nil
	}
	workflowOwner := normalizeHex(triggerReq.Params.Workflow.WorkflowOwner, workflowOwnerLength)
	workflowName := "0x" + hex.EncodeToString([]byte(workflows.HashTruncateName(triggerReq.Params.Workflow.WorkflowName)))
	workflowID, found := h.workflowMetadataHandler.GetWorkflowID(
		workflowOwner,
		workflowName,
		triggerReq.Params.Workflow.WorkflowTag,
	)
	if !found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "Workflow not found. Provide either a valid 'workflowID' or a valid combination of 'workflowOwner', 'workflowName', and 'workflowTag'", callback)
		return "", errors.New("workflow not found")
	}
	return workflowID, nil
}
