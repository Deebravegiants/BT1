### Title
Webhook shop/topic identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, but then dispatches the handler using `shop`, `topic`, `webhook_id`, and `api_version` values that are read from unauthenticated HTTP headers and are never included in the signed payload. The binding the gem implicitly relies on — "the tenant (`shop`) that the HMAC authenticates" == "the tenant the handler is told to act on" — does not actually hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

All the identity/tenant fields the app uses to route and process the webhook are pulled straight from headers, outside the signature: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (i.e., the body) against the HMAC — it never verifies the headers: [4](#0-3) 

`Registry.process` uses this same validator and then trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` to build the data handed to the merchant's handler: [5](#0-4) 

Because a single app has one `Context.api_secret_key` shared across every installed shop, any legitimately installed merchant of the app already possesses a body+HMAC pair that Shopify signed as valid (received from their own store's real webhook traffic, or from a webhook endpoint the merchant points at infrastructure they control). Nothing in `Request`, `HmacValidator`, or `Registry.process` stops that merchant from replaying the exact same body/HMAC pair while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with a different shop's domain. `HmacValidator.validate` still returns `true` because it only re-derives the HMAC from `@raw_body`, and `Registry.process` will happily hand the forged `shop` value to the app's `WebhookHandler`.

This is the direct analog of the report's root cause: a value that is *acted on* by downstream logic (there: royalty split window/claim amounts; here: the tenant identity used to route/process webhook data) is not actually *covered* by the cryptographic check that is supposed to authenticate the request (there: `incrementWindow`/`claim` accounting; here: the HMAC signature).

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` (or `#topic`/`#webhook_id`) to decide which tenant's data to create, update, or delete is exposed to cross-tenant data corruption/injection: a webhook whose body legitimately belongs to shop A can be delivered to the app's endpoint labeled as belonging to shop B, and the gem's own validation layer offers no protection against this because the identity fields are never part of the signed content. This matches the Critical "cross-tenant access" impact category, since the tenant boundary that `HmacValidator`/`Registry` are meant to enforce is not actually authenticated.

### Likelihood Explanation
Exploitation requires no access token, no `api_secret_key`, and no privileged account — only the ability to obtain one genuinely-signed body/HMAC pair (trivial for any of the app's own installed merchants, who receive real webhooks signed with the app's shared secret) and to send a crafted HTTP request with a substituted shop header to the app's public webhook endpoint. This is well within the "unprivileged internet user" threat model defined for this analysis.

### Recommendation
Bind the tenant-identifying headers into the authenticated payload before dispatching to handlers: e.g., include `shop`, `topic`, and `webhook_id` in the string used for HMAC verification (or independently verify `shop` against a value already associated with a stored, provisioned session/access token for that shop), rather than trusting raw, unsigned headers for routing.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and on `victim-shop.myshopify.com`, both using the same app `client_secret`.
2. Attacker configures (or intercepts) a webhook delivery to their own endpoint for `attacker-shop.myshopify.com`, capturing the raw body `B` and the valid `x-shopify-hmac-sha256` header `H` that Shopify computed over `B` using the shared `api_secret_key`.
3. Attacker sends a POST to the target app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged shop header without issue (`lib/shopify_api/webhooks/request.rb:1-73`).
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `B` and returns `true` (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
6. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from `attacker-shop.myshopify.com`'s data (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the app to process attacker-controlled data under the victim's tenant identity.
