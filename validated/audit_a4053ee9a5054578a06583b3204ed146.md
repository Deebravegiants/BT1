### Title
Webhook shop/topic attribution not covered by HMAC, allowing cross-tenant webhook spoofing via header substitution - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` fields that `Registry.process` hands to the app's `WebhookHandler` are parsed from HTTP headers that are excluded from the signature. This breaks the binding: `hmac-verified-bytes == raw_body` but `attributed-shop == shopify-shop-domain header`, i.e. the tenant identity used by the handler is not the tenant identity actually covered by the signature.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (the body) and compares it to the `hmac` header: [3](#0-2) [4](#0-3) 

Once the body's HMAC checks out, the header-derived `shop` and `topic` are trusted as-is and forwarded into `WebhookMetadata`, which is the only tenant identifier passed to the host app's `handle(data:)` implementation: [5](#0-4) 

Because `shopify-hmac-sha256` only signs the JSON body, an attacker who has legitimately received (or can otherwise obtain) any single valid `(body, hmac)` pair — for example from their own shop's webhook deliveries, which they are entitled to receive — can resend that exact body/hmac pair to the app's public webhook endpoint while freely substituting the `shopify-shop-domain` and `shopify-topic` headers to any value of their choosing. The signature remains valid because those headers were never part of the signed content, so `HmacValidator.validate` still returns `true`, and the app's handler receives attacker-chosen `shop`/`topic` values it did not actually originate from.

### Impact Explanation
This is a violation of the equality `signed-bytes == attributed-tenant`. If a host application's `WebhookHandler#handle` uses `data.shop` to select which merchant's session/record to update (the documented and expected usage pattern), an attacker can force the app to process a legitimately-signed payload under an arbitrary victim shop domain, achieving cross-tenant data confusion/corruption without ever possessing the app's `client_secret` or any victim credentials — only a single valid webhook body+hmac pair the attacker is entitled to receive from their own installation. This matches the High-impact category of credential/tenant-boundary crossing enabled by a field (the shop attribution) that is validated as present but not bound to the HMAC that is supposed to authenticate the request's origin.

### Likelihood Explanation
Exploitation requires an attacker to control an installed instance of the app (trivial for any developer who installs a public app on their own test shop) and be able to send arbitrary HTTP headers to the app's public webhook endpoint (trivial, since webhook endpoints are internet-reachable by design). No secrets, tokens, or elevated access are needed beyond a normal app installation.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` (or at minimum `shop` and `topic`) in the signable string that `HmacValidator` verifies, or independently cross-check the header-derived `shop`/`topic` against a value looked up from the app's own session store using an identifier that is itself bound to the signed body, before constructing `WebhookMetadata` and dispatching to `WebhookHandler#handle`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), legitimately receiving a POST with body `B` and a valid header `x-shopify-hmac-sha256: H` (where `H = HMAC(secret, B)`).
2. Attacker resends the same request to the app's webhook endpoint, keeping `x-shopify-hmac-sha256: H` and body `B` unchanged, but replacing `x-shopify-shop-domain: attacker-shop.myshopify.com` with `x-shopify-shop-domain: victim-shop.myshopify.com` and/or altering `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) only — validation passes because `B` and `H` are unchanged: [6](#0-5) 
4. `request.shop` now returns `"victim-shop.myshopify.com"` (from the attacker-controlled header), which is placed into `WebhookMetadata#shop` and delivered to the app's `WebhookHandler#handle`, causing the app to process attacker-supplied data attributed to the victim shop.
