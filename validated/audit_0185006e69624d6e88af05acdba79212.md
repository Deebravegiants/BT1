### Title
Buy-then-donate breaks the `Router._computeBuy` overflow-cap invariant, causing a permanent revert (DoS) that freezes a curve's raised LT and unsold tokens - (File: packages/contracts/src/Router.sol)

### Summary
`Router._computeBuy` assumes the hard invariant `pair.tokenBalance() ("real balance") < pair.getReserves().reserveToken` documented and asserted in `test/GraduationInvariants.t.sol` (`test_inv_virtualReserveAlwaysExceedsRealBalance`). Any unprivileged trader can violate this invariant with a plain buy + ERC20 donate sequence, after which any subsequent buy that lands on the overflow-cap branch causes an arithmetic underflow `Panic`, permanently reverting instead of gracefully capping. Because the overflow-cap branch is precisely the mechanism the supply-side graduation trigger depends on (draining the curve to `tokenBalance() == 0`), this can permanently strand the curve's raised LT and remaining unsold tokens in `Lifecycle.Curve` when the USD trigger doesn't otherwise fire.

### Finding Description
`Router._computeBuy` caps `tokensOut` at the pair's real token balance whenever the uncapped constant-product output would exceed it, then back-calculates `amountInUsed`: [1](#0-0) 

```
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;   // reserveToken - realBalance
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    ...
}
```

This subtraction is only safe because the protocol relies on the invariant `realBalance < reserveToken`, which the test suite explicitly claims holds "at every state of the curve": [2](#0-1) 

That invariant is broken by a buy-then-donate sequence: an unprivileged trader (or the `Zap`/`Bonding.buy` router path any wallet can reach) buys a large slice of tokens off the curve — which decreases both the stored `reserveToken` and the real `tokenBalance()` by the same amount via `Pair.swap` — and then sends those tokens straight back to the pair with a plain ERC20 `transfer`. The donation increases only the live `tokenBalance()` (read via `IERC20.balanceOf`), not the stored `reserveToken`, so `realBalance` can now exceed `reserveToken`. This exact scenario is reproduced by the test harness's `_stageDonationAttack` helper: [3](#0-2) 

The repo already recognizes and partially patched the fallout of this specific inversion, but only inside the *view* function `Bonding.previewLtUntilGraduation`: [4](#0-3) 

```
// Donation-inflated `realBalance`: supply trigger unreachable, defer to USD leg.
if (realBalance >= reserveToken) return ltUntilThreshold;
```

No equivalent guard exists in `Router._computeBuy`, which is the function actually executed by every real `buy()` call. When `realBalance > reserveToken` and a buy's uncapped `tokensOut` exceeds `realBalance` (which happens for any moderately large or "closing" buy — exactly the kind needed to drain the curve for the supply-side graduation trigger, or the kind a legitimate large trader would submit), `cappedReserveToken = reserveToken - tokensOut` underflows and the call reverts with an unhandled `Panic(0x11)` instead of the intended graceful cap.

### Impact Explanation
Once the invariant is inverted, no buy can ever land exactly at `tokenBalance() == 0` through the cap-branch (which is required whenever the uncapped math would overshoot remaining supply), so the supply-side graduation trigger in `canGraduate` — `IPair(pair).tokenBalance() == 0` — becomes practically unreachable for that curve. If the LT's `exchangeRate()` never appreciates enough to satisfy the USD trigger (the flat/bear-market case the supply trigger exists specifically to cover, per `docs/contracts-scope.md`), the token is permanently stuck in `Lifecycle.Curve`: the creator's remaining unsold tokens and every trader's raised LT sitting in the pair can never reach graduation/LP seeding, and any trader who submits a large enough buy to hit the cap branch has their transaction revert (Panic), denying them the trade. This is a permanent freezing-of-funds condition reachable by a single unprivileged wallet, matching the CVE's DoS/availability-impact class mapped onto alt.fun's bonding-curve buffer (real-balance-vs-virtual-reserve) accounting.

### Likelihood Explanation
Low complexity, fully unprivileged, and requires only a standard `Zap.buy`/`Bonding.buy` call followed by a plain ERC20 `transfer` of the purchased tokens back to the pair — both are ordinary transactions any address can submit, with no special timing, roles, or races required. The test suite's own `_stageDonationAttack` helper demonstrates the invariant break is trivially reachable with off-the-shelf buy sizing (`ltIn = virtual/3` crosses the 250M/`tokensOut` threshold).

### Recommendation
Add the same `realBalance >= reserveToken` guard used in `Bonding.previewLtUntilGraduation` to `Router._computeBuy` (and any other site subtracting `realBalance` from `reserveToken`), treating a donation-inverted state as "already at/above the real-balance cap" rather than performing an unchecked subtraction. Alternatively, resolve the inversion at the root by having `_prepareGraduationLiquidity`/graduation-adjacent code burn or reconcile excess real balance eagerly rather than only at graduation time, so the `realBalance < reserveToken` invariant the whole overflow-cap design depends on is actually maintained by every code path that can move tokens into or out of the pair, not just router-mediated swaps.

### Proof of Concept
1. Launch a token normally (`Zap.createToken`), leaving it in `Lifecycle.Curve`.
2. As any unprivileged wallet, submit a `Zap.buy`/`Bonding.buy` sized so `tokensOut` crosses roughly a quarter of `TOTAL_SUPPLY` (e.g. spend LT ≈ `virtualLtReserve / 3`), as done in `_stageDonationAttack` (`test/Zap.t.sol:944-965`).
3. `transfer` the purchased tokens directly back to the `Pair` address (a plain ERC20 transfer, not a swap) — this raises `Pair.tokenBalance()` without touching the stored `reserveToken`, reproducing `test_donation_realBalanceExceedsReserveToken` (`test/Zap.t.sol:967-977`), which asserts `realBalance > reserveToken` afterward.
4. Submit any subsequent buy sized so the uncapped constant-product `tokensOut` exceeds the now-inflated `realBalance` (e.g. an oversized buy analogous to `test_inv_overflowCap_refundsLt`'s `oversizedBuy = 1_000_000_000 ether`, `test/GraduationInvariants.t.sol:330-351`, but now against the donation-attacked pair).
5. `Router._computeBuy`'s `cappedReserveToken = reserveToken - tokensOut` underflows since `tokensOut == realBalance > reserveToken`, reverting the transaction with `Panic(0x11)` instead of capping — the curve can no longer be drained to `tokenBalance() == 0`, blocking the supply-side graduation trigger and freezing the curve's raised LT/unsold tokens whenever the USD trigger cannot independently fire.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

    function _stageDonationAttack(
        address tokenAddr
    ) internal returns (uint256 drainLtSpent, uint256 donatedTokens) {
        address pairAddr = bonding.getTokenInfo(tokenAddr).pair;
        address drainer = makeAddr("donationDrainer");
        // Size the drain so `tokensOut > 250M` (the LP-reserve floor) under
        // any `VIRTUAL_LIQUIDITY_USD`. Constant-product math gives
        // `tokensOut = TOTAL_SUPPLY × ltIn / (virtual + ltIn)`, which crosses
        // 250M (= ¼ of TOTAL_SUPPLY) when `ltIn = virtual / 3`. Spending the
        // full opening virtual reserve lands `tokensOut = 500M` — plenty of
        // headroom to push `realBalance > reserveToken` after the donation.
        drainLtSpent = _initialVirtualLt();
        lt.mintDirect(drainer, drainLtSpent);
        if (!bonding.isRouter(drainer)) bonding.addRouter(drainer);
        vm.startPrank(drainer);
        lt.approve(address(curveRouter), drainLtSpent);
        bonding.buy(drainLtSpent, tokenAddr, 0, drainer);
        vm.stopPrank();
        donatedTokens = Token(tokenAddr).balanceOf(drainer);
        vm.prank(drainer);
        Token(tokenAddr).transfer(pairAddr, donatedTokens);
    }

    function test_donation_realBalanceExceedsReserveToken() public {
        address tokenAddr = _createToken(0);
        address pairAddr = bonding.getTokenInfo(tokenAddr).pair;

        (, uint256 donated) = _stageDonationAttack(tokenAddr);
        assertGt(donated, 250_000_000 ether, "Drain must yield > 250M tokens to break the gap");

        uint256 realBalance = IPair(pairAddr).tokenBalance();
        (uint256 reserveToken,) = IPair(pairAddr).getReserves();
        assertGt(realBalance, reserveToken);
    }
