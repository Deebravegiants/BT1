## Title
Webhook `shop` (and `topic`) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (`File: lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) purely from the unauthenticated `x-shopify-shop-domain` HTTP header, while `Utils::HmacValidator` only verifies the HMAC over the raw request body. The shop identity that the rest of the library treats as trusted (and hands off to the host application's webhook handler) is never bound to the cryptographic signature that is supposed to authenticate the request.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` and `topic` are read directly from HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC solely over `verifiable_query.to_signable_string` and compares it to the `hmac` header: [3](#0-2) 

`Webhooks::Registry.process` accepts the request once `HmacValidator.validate(request)` passes, then trusts `request.shop` (and `request.topic`) to build `WebhookMetadata` and dispatch to the registered handler for that topic/shop: [4](#0-3) 

The identity binding that should hold is:
`hmac_header == HMAC(secret, raw_body)` **and** `shop_header` is authenticated by that same signature.

In reality only the first half holds — `shop_header` is never part of the signed material. Since HMAC-SHA256 over the body is computed with the app's `client_secret`, any actor who legitimately receives a valid webhook (e.g., by installing their own copy of the app on their own store) obtains a raw body + HMAC pair that is valid *for that body*, but the HMAC says nothing about which shop it came from. Replaying that exact body while substituting the `x-shopify-shop-domain` header for a victim shop still passes `HmacValidator.validate`, because validation never inspects the header. If the app's handler logic keys off `WebhookMetadata#shop` (e.g., to update a specific tenant's record, uninstall flag, subscription state, etc.), this constitutes a break of the shop-tenant identity binding and can be used to inject spoofed events attributed to a victim shop.

### Impact Explanation
This crosses the tenant boundary: an attacker-controlled request (with an attacker-obtained valid HMAC over attacker-controlled body content, from the attacker's own store) can be relabeled to appear as though it originated from any other shop merely by changing an unauthenticated header, since the identity field acted upon (`shop`) is never covered by the signature that is meant to authenticate the whole request. This matches the "field acted on but not covered by the HMAC" identity-binding break category and results in cross-tenant data/webhook confusion in the host application, which is a Critical-class impact per the taxonomy (cross-tenant access).

### Likelihood Explanation
Exploitation requires the attacker to be able to trigger at least one genuine webhook delivery to their own account/app install (trivial — any developer/merchant can install a public app or trigger their own store's webhooks) and to be able to send that raw body plus HMAC to the app's webhook endpoint with a forged `x-shopify-shop-domain` header. No secrets, tokens or privileged access are required beyond controlling one's own shop/app installation — an unprivileged internet-capable actor.

### Recommendation
Include the shop domain (and topic) in the signed/verified material, or otherwise cryptographically bind the header-derived identity to the HMAC-validated payload before it is trusted downstream (e.g., cross-check `shop` against a value embedded in the signed body, or require the webhook subscription's expected shop to match a value that was established during OAuth for that specific installation rather than trusting the header value at process time).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers/receives a webhook (e.g. `orders/create`) with `raw_body` and a valid `x-shopify-hmac-sha256` header signed with the app's `client_secret`.
2. Attacker POSTs that exact `raw_body` and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and (optionally) forges `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-hashes `raw_body` — validation succeeds.
4. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host application to process attacker-supplied webhook content as if it came from the victim shop. [4](#0-3) [5](#0-4)

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic

      end

      sig { returns(String) }

        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
