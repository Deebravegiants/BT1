Confirmed: `CallDispatcher.dispatch()` is a fully public, unauthenticated function with zero access control — no `onlyGateway`/`msg.sender` check whatsoever [1](#0-0) . This single `CallDispatcher` instance is shared as `_params.dispatcher` across `IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `BridgeToken` deployments on a chain [2](#0-1) [3](#0-2) , and it is used as a transient holding account: callers first push tokens/ETH into it, then invoke `dispatch()` (arbitrary user-supplied calldata) to route through it, then sweep whatever balance remains back out via a second `dispatch()` call [4](#0-3) .

### Title
Unauthenticated `CallDispatcher.dispatch()` lets anyone drain any balance stranded in the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a single, chain-wide singleton contract used by `IntentGatewayV2.placeOrder`/`_execute`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` as an intermediate holding/execution point for predispatch and output calldata. Its `dispatch(bytes)` function is `external` with no caller restriction: it only checks that the target has code, never that `msg.sender` is a registered app contract [1](#0-0) . Whenever the dispatcher ends up holding a token or ETH balance that is not swept to zero within the same atomic transaction that placed it there, that balance is claimable by anyone, exactly like the DODO GSP bug where tokens sent to a shared pool contract could be claimed by any subsequent caller because ownership of the deposit was never tracked.

### Finding Description
`IntentGatewayV2.placeOrder` (and the tron variant, and `_execute` in `IntentsBase.sol`) use the dispatcher as follows:
1. Transfer `order.predispatch.assets` tokens from `msg.sender` into `dispatcher` [5](#0-4) .
2. Call `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` — fully user-controlled calldata, executed with the dispatcher as `msg.sender` against arbitrary "to" contracts (as long as they have code) [1](#0-0) .
3. Sweep back only the tokens explicitly listed in `order.inputs`, using `balanceOf(dispatcher)` (the *entire* current balance, not a delta attributable to this call) [6](#0-5) .
4. `_execute` (used when filling an order's output call) performs the same pattern with `order.output.call`, sweeping only the declared `order.output.assets` tokens [7](#0-6) .

Because `dispatch()` has no access control, and because the sweep logic in every caller only recovers tokens it explicitly enumerates (`order.inputs` / `order.output.assets`), any token or ETH that a user's predispatch/output call produces or leaves behind but does *not* declare in that enumeration remains sitting in the dispatcher after the transaction completes — unowned, untracked, and freely withdrawable by any third party who simply calls `CallDispatcher.dispatch()` directly with a `Call{to: token, data: transfer(attacker, balance)}` (or `Call{to: attacker, value: balance}` for ETH). This is functionally identical to the reported GSP issue: the shared pool/dispatcher contract accumulates value with no per-depositor bookkeeping, and possession of the funds is determined purely by "whoever calls next," not by who deposited them.

Realistic ways balance gets stranded in the dispatcher, all of which are reachable by a single unprivileged `placeOrder`/fill call:
- A `predispatch.call` (e.g., unwrapping an LP token, or any multi-output DeFi action) produces more than one output token, but `order.inputs` only lists one of them — the un-listed output token is never swept and sits in the public `CallDispatcher`.
- `_execute`'s `order.output.call` performs a swap/route that leaves dust in a token not enumerated among `order.output.assets`.
- Any actor (not necessarily going through the gateway at all) directly sends tokens/ETH to the well-known `CallDispatcher` address (it is published in deployment configs/docs) by mistake.

### Impact Explanation
Any value stranded at the shared `CallDispatcher` — belonging to a user's order, to the protocol's own dust collection, or to a mistaken direct transfer — can be permanently and unconditionally stolen by any address, since `dispatch()` performs the withdrawal call with the dispatcher's own balance and no ownership check. This is a direct theft-of-funds vector reachable from an ordinary `placeOrder`/order-fill transaction (predispatch or output calldata composability is an explicitly supported, user-controlled feature), satisfying the "concrete theft of funds" bar. Given the dispatcher is shared across multiple deployed apps (`IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`, `BridgeToken`) on the same chain, exposure compounds across all of them.

### Likelihood Explanation
Predispatch/output calldata composability is a core, documented, unprivileged feature of `IntentGatewayV2` — solvers and users are expected to route through DEXes and other DeFi primitives via this mechanism [8](#0-7) . Any order whose predispatch/output call touches more tokens than are declared in `order.inputs`/`order.output.assets` (which is easy to construct, intentionally or accidentally, e.g. a Uniswap route that dust-outputs a second token, or an LP-unwrap producing two assets when only one is declared) leaves a balance in the dispatcher that a bot can drain on the very next block since `dispatch()` requires no permission at all. No governance or privileged role is required to trigger or exploit this.

### Recommendation
- Restrict `CallDispatcher.dispatch()` to a caller allow-list (e.g., only the registered app contracts that were given this dispatcher address at `configure`/`initialize` time), or require the caller to be `msg.sender == <the app that funded this specific dispatch>`.
- Prefer per-order/per-call ephemeral dispatchers (e.g., deploy via `CREATE2`/minimal proxy and `SELFDESTRUCT`-style cleanup, or route funds directly without an intermediary contract) so no residual balance can ever persist across transactions.
- In `IntentGatewayV2.placeOrder`/`_execute`, sweep the *full* balance of the dispatcher for *any* token touched by the predispatch/output call (not just tokens explicitly enumerated in `order.inputs`/`order.output.assets`), crediting excess as protocol dust rather than leaving it unclaimed at a public address.
- Add reentrancy/ownership bookkeeping (e.g., a `lastCaller`/`pendingOwner` guard) around dispatcher balance so that a sweep cannot be front-run or hijacked by an unrelated caller.

### Proof of Concept
1. A user calls `IntentGatewayV2.placeOrder` with a `predispatch.call` that swaps token A for tokens B and C (e.g., via a router that returns two outputs), but `order.inputs` only declares token B (a single input, as is typical for a simple order).
2. `dispatch(order.predispatch.call)` executes the swap; the dispatcher now holds both B and C.
3. The sweep loop (`for i in inputsLen`) only builds a `transferCalls` entry for B, using `IERC20(B).balanceOf(dispatcher)`; token C is never touched and remains at `CallDispatcher` [9](#0-8) .
4. `placeOrder` completes; the transaction ends with token C sitting in `CallDispatcher`.
5. Any third party (no special role required) calls `CallDispatcher.dispatch(abi.encode([Call{to: C, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, IERC20(C).balanceOf(dispatcher))}]))` directly — this succeeds because `dispatch()` performs no caller check [1](#0-0) , and token C is transferred to the attacker.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
