## Title
Webhook shop-domain header is not cryptographically bound to the HMAC signature, enabling cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/registry.rb], [File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic once `Utils::HmacValidator.validate` succeeds, but the HMAC signature only covers the raw request body, never the `shop` identity. The `shop` value handed to the app's handler is read directly and unauthenticated from the `X-Shopify-Shop-Domain` header, so any request whose body/HMAC pair is valid for the app's shared `client_secret` can carry an arbitrary `shop` value, breaking the identity binding: `hmac_valid(body) == true` is treated as equivalent to `shop_header == actual_owning_shop`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop` accessor is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no relation to the signed content: [2](#0-1) .

`HmacValidator.validate` computes and compares the HMAC only over `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) .

`Registry.process` accepts the request purely based on that body-only HMAC check and then forwards `request.shop` verbatim to the app-supplied handler as the tenant identity: [4](#0-3) .

Since the webhook HMAC secret is the app's single shared `client_secret` (not a per-shop secret), any shop that has legitimately installed the app can generate a genuinely-signed webhook payload for itself (e.g. by creating an order in its own store) with a valid `hmac-sha256` header for a given raw body. Because the shop-domain header is not part of the signed content, that same valid `(body, hmac)` pair can be replayed against the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `Registry.process` will pass the HMAC check and invoke the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain, per the documented handler contract: [5](#0-4) . Any host application that uses `data.shop` as the tenant key to look up sessions/records — exactly as the gem's own documented example does — will act on attacker-supplied data under a victim shop's identity: [6](#0-5) .

### Impact Explanation
This crosses the tenant boundary the report describes by analogy: a value used to authenticate/authorize the request (the HMAC) does not cover the field (`shop`) that downstream code — including the gem's own documented handler pattern — uses to identify *which* tenant's data to update. An attacker who is merely an unprivileged, legitimately-installed shop owner (no `client_secret`, no access token, no privileged account) can cause cross-tenant confusion in the app: their own valid webhook traffic can be relabeled as belonging to any other shop, enabling injection of attacker-controlled data (order/product/customer payloads) tagged with a victim's shop domain.

### Likelihood Explanation
Likelihood is meaningfully constrained: the attacker must (a) be able to install the app on their own store to receive genuinely-signed webhook traffic, and (b) be able to send an arbitrary HTTP POST with custom headers to the app's public webhook endpoint (trivial, since these are public callback URLs by design) while reusing a captured `(body, hmac)` pair. Both conditions are realistic for any "unprivileged internet user" who signs up as a merchant for the target app, which is the normal, expected way to interact with a public app.

### Recommendation
Bind the shop identity into the authenticated material, or otherwise verify the shop header out-of-band: e.g. only accept `request.shop` values that match a shop for which the app currently holds a stored session/registration for the given webhook `topic`/`webhook_id`, and reject requests where the shop header does not correspond to a shop the app knows to have registered that webhook. At minimum, document prominently (and enforce in `Registry.process`) that consumers must independently verify `data.shop` against their own session store before trusting it, since the HMAC provides no such guarantee.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`.
2. Trigger any subscribed webhook topic (e.g. `orders/create`) on that store; Shopify sends a POST with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Capture `(B, H)`.
4. Replay a POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid), but `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb:13-22) returns `true` since only `B` is checked; `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` (lib/shopify_api/webhooks/registry.rb:198-199), and any host logic keyed on `data.shop` now processes attacker data as if it originated from the victim tenant.

          received_signature = verifiable_query.hmac
