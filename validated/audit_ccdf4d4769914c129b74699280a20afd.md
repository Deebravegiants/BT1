### Title
Stale vote/stake accounts remain in `StakesCache` after owner reassignment, corrupting stake-weighted consensus data - (File: `runtime/src/stakes.rs`)

### Summary
`StakesCache::check_and_store` (the agave analog of the reported `BaseWrapper._cachedVaults` staleness bug) updates its cache only for the branches where the *current* account owner is the vote program or the stake program. If a previously-cached vote or stake account's owner is changed away from `solana_vote_program`/`stake_program` (while lamports remain non-zero), neither branch executes, and the function returns without touching the cache, leaving the old `VoteAccount`/`StakeAccount` entry (and its contribution to `delegated_stakes`) in `Stakes<StakeAccount>` indefinitely.

### Finding Description
`check_and_store` explicitly documents this gap itself: [1](#0-0) 

The logic is: if `lamports == 0`, evict from cache based on `owner` (correct); otherwise, if `owner` is the vote program, upsert/evict the vote-account cache; else if `owner` is the stake program, upsert/evict the stake-account cache. There is **no `else` branch** to handle the case where an account was previously cached (as a vote or stake account) but its current `owner` is neither program while `lamports != 0`. In that case, the function does nothing — the cached `VoteAccount`/`StakeAccount` entry from a prior slot survives untouched in `Stakes::vote_accounts` / `Stakes::stake_delegations`, exactly mirroring the yearn-vaults pattern where `_cachedVaults`' old prefix is never refreshed when the source (`registry`) changes.

This is the same root cause class as the external report: a cache keyed by "did we see a state update for this entity" fails to invalidate stale entries when the entity's classification (registry set / account owner) changes rather than being explicitly zeroed out.

### Impact Explanation
`Stakes<StakeAccount>` backs `EpochStakes`, vote-account stake weighting, and `delegated_stakes` used for calculating leader schedules and vote/stake-weighted consensus decisions. If a stale, no-longer-owned-by-stake/vote-program account's delegation/stake persists in the cache, subsequent activated-stake calculations (`calculate_activated_stake`, `refresh_delegated_stakes`, `upsert_stake_delegation`'s diffing against `old_stake_account`) would use out-of-date information: a stake account whose owner has changed should no longer be tracked as a delegation, yet `delegated_stakes` and `vote_accounts` stake totals would continue to reflect it. This can cause cross-node divergence if some nodes reach this code path differently, or (more critically) an inflated/incorrect stake-weight bookkeeping that persists across epochs since `check_and_store` is the only synchronization point between accounts-db state and the in-memory stakes cache.

### Likelihood Explanation
This is gated on whether the SVM/runtime actually permits an account's `owner` field to change from the stake program or vote program to a different program while lamports remain non-zero (i.e., without the account being fully closed to zero lamports first, which is already handled by the `lamports == 0` branch). I was not able to conclusively verify, within available context, whether Solana's account-owner-change enforcement (in `svm/src/transaction_account_state_info.rs` and related SVM account-saving checks) permits a non-zero-lamport owner reassignment away from the stake/vote program without draining lamports to zero — normally in Solana, only the current owning program can call `system_instruction::assign`/CPI-based owner reassignment, and such reassignment is typically only permitted when the account's data is fully zeroed, not necessarily when lamports are zero. Given the note also carries a 2022 upstream TODO with a linked (unresolved) discussion, the underlying edge case is acknowledged by the maintainers as real but narrow, so likelihood is assessed as **low-to-moderate** — the code path is reachable only in a specific ownership-transition edge case that needs to be proven against the current owner-change validation rules for stake/vote accounts.

### Recommendation
Add an `else` branch to `check_and_store` that evicts any pre-existing cached entry for `pubkey` from both `vote_accounts` and `stake_delegations` whenever the current `owner` is neither the vote program nor the stake program (matching the existing `remove_vote_account`/`remove_stake_delegation` calls used in the zero-lamport path), so the cache can never retain state inconsistent with the authoritative account owner in accounts-db. This resolves the TODO already present at [2](#0-1) .

### Proof of Concept
Not able to construct a concrete PoC without confirming that the SVM permits changing an account's owner away from the stake/vote program while lamports remain non-zero (this determines whether the vulnerable code path in `check_and_store` is reachable in practice). This would require tracing the owner-change authorization logic in `svm/src/transaction_account_state_info.rs` and the account-commit path in `bank.rs`/`accounts_db.rs`, which was not fully explored due to iteration limits.

    pub(crate) fn check_and_store(
        &self,
        pubkey: &Pubkey,
        account: &impl ReadableAccount,
        new_rate_activation_epoch: Option<Epoch>,
        use_fixed_point_stake_math: bool,
    ) {
        // TODO: If the account is already cached as a vote or stake account
        // but the owner changes, then this needs to evict the account from
        // the cache. see:
        // https://github.com/solana-labs/solana/pull/24200#discussion_r849935444
        let owner = account.owner();
        // Zero lamport accounts are not stored in accounts-db
        // and so should be removed from cache as well.
        if account.lamports() == 0 {
            if solana_vote_program::check_id(owner) {
                let _old_vote_account = {
                    let mut stakes = self.0.write().unwrap();
                    stakes.remove_vote_account(pubkey)
                };
            } else if stake_program::check_id(owner) {
                let mut stakes = self.0.write().unwrap();
                stakes.remove_stake_delegation(
                    pubkey,
                    new_rate_activation_epoch,
                    use_fixed_point_stake_math,
                );
            }
            return;
        }
