### Title
Stale `QrCodes::Both` cached state bypasses re-verification of user identity binding on signup retry - (File: src/plans/mod.rs)

### Finding Description
In `scan_remaining_qr_codes` (src/plans/mod.rs:788-868), the first match arm handles the case where `qr_codes` is already `QrCodes::Both { operator_data, user_qr_code, user_data, user_qr_code_string }`: [1](#0-0) 

The only freshness check performed is `operator_data.timestamp.elapsed() < operator_qr_expiration_time` — i.e. whether the *operator* QR is still valid. There is no re-check of the `user_qr_code`/`user_data`/`user_qr_code_string` themselves, and no re-verification that a user QR was scanned in the current, present interaction. If this cached `QrCodes::Both` value is fed into a subsequent call of `scan_remaining_qr_codes` (e.g. because the caller retains the `qr_codes` variable across a signup attempt that was aborted before biometric capture began), the function immediately returns the stale `ResolvedQrCodes` without any new QR interaction, and the caller proceeds straight into biometric capture using that stale identity binding. Whichever face is physically presented to the camera next would be captured and bound to the previously-resolved (and never re-confirmed) `user_data`.

By contrast, the other arms (`QrCodes::Operator` and the fallback `_` arm) always re-invoke `scan_user_qr_code` before proceeding, which re-establishes the identity-to-QR binding for the current physical interaction.

### Impact Explanation
If reachable, this would allow a wrong-identity binding: biometrics of person B get enrolled/associated with the WLD identity claim scanned by person A in a prior, aborted attempt, within the `operator_qr_expiration_time` window. This maps to a "wrong identity binding" / cross-signup state bleed impact category.

### Likelihood Explanation
I was unable to fully confirm, within the available indexed context, whether the caller of `scan_remaining_qr_codes` actually preserves a `QrCodes::Both` value across two independent signup attempts (i.e., whether the surrounding signup loop resets `qr_codes` to `QrCodes::None`/`Operator`-only when a signup is aborted before biometric capture, or whether it is only ever re-entered with `Both` for legitimate same-user retries after a processing failure). The `MasterPlan` struct and the outer signup-orchestration loop that owns and threads the `qr_codes` variable across iterations were not fully visible in the retrieved code, so I could not verify the exact caller-side reset semantics or confirm whether an independent liveness/presence check elsewhere in the pipeline (e.g., face detection gating before capture) would catch/reject a "different person" substitution. This is a material gap: the vulnerability's exploitability hinges entirely on whether the outer loop resets `qr_codes` on an aborted-before-capture signup, which I could not confirm from the code excerpts obtained.

### Recommendation
Given the uncertainty above, I cannot assert this as a fully confirmed, reproducible vulnerability without tracing the caller of `scan_remaining_qr_codes` and confirming the exact lifecycle of the `qr_codes` variable across aborted vs. completed signups. A Devin session with full repository access should verify: (1) where `qr_codes` is declared/owned in the signup loop calling `scan_remaining_qr_codes`, (2) whether it is reset when a signup is aborted prior to biometric capture, and (3) whether any independent presence/liveness re-check exists between QR resolution and biometric capture that would prevent binding a different physical person's capture to stale `user_data`.

### Proof of Concept
Cannot be finalized without confirming outer-loop state ownership; recommend an integration test in the signup orchestration module that: (a) drives `qr_codes` to `QrCodes::Both` via a first signup attempt, (b) aborts before biometric capture, (c) starts a second signup within `operator_qr_expiration_time` with a different simulated face, and (d) asserts that `scan_user_qr_code` is invoked again (i.e., the `QrCodes::Both` fast-path is not taken) before biometric capture proceeds.
