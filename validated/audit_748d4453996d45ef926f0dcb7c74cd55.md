### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) fields are not covered by the HMAC signature, allowing tenant/topic spoofing in `ShopifyAPI::Webhooks::Request` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields are read directly from unauthenticated HTTP headers. Any header value that differs from what Shopify actually signed will still pass HMAC validation as long as the raw body and the `hmac-sha256` header are untouched, breaking the binding `shop_authenticated == shop_that_actually_sent_the_webhook`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the signature purely against `to_signable_string` (the raw body) using `Context.api_secret_key`: [3](#0-2) 

Since the same app secret (`Context.api_secret_key`) is shared across all shops/tenants that install the app, any webhook payload that legitimately arrived from Shopify for shop A (with a body/hmac pair that validates) can be replayed at the app's webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header rewritten to shop B. `HmacValidator.validate` will still return `true` because it only checks the raw body against the shared secret, and `Registry.process` (confirmed by test usage) passes `data.shop`/`data.topic` straight to the registered handler without any additional cross-check: [4](#0-3) 

This proves the root cause: the gem's own `to_signable_string` implementation for `Webhooks::Request` deliberately excludes `shop`, `topic`, `webhook_id`, and `api_version` from the signed material (unlike `Auth::Oauth::AuthQuery#to_signable_string`, which does include `shop`, `state`, `host`, etc. in the signed string): [5](#0-4) 

### Impact Explanation
Host applications built on top of this gem are documented to use `Webhooks::Request#shop` as the authenticated tenant identifier for dispatching the payload to per-shop business logic (e.g., looking up that shop's stored access token/session, updating that shop's local records, or triggering shop-scoped side effects). Because `shop` is not part of the signed material, a holder of any one valid (body, hmac) pair from Shopify — trivially obtainable by installing the app on their own shop and capturing one of their own webhooks — can forge the `shop` header to impersonate a different, victim shop. This is a cross-tenant confusion vulnerability: the app processes attacker-controlled data as though it originated from another merchant's shop.

### Likelihood Explanation
Exploitation requires only an unprivileged attacker who can install the app on their own shop (a normal Shopify merchant, no special privilege) to obtain one valid signed webhook body+hmac, and the ability to send arbitrary HTTP requests with custom headers to the app's public webhook endpoint. No access token, `client_secret`, or `api_secret_key` disclosure is needed, since the gem's `HmacValidator` never binds `shop` into the signature it checks.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signed material used for webhook HMAC validation, or otherwise cryptographically bind these header-derived identity fields to the verified payload before they are exposed to registered handlers via `Registry.process`. At minimum, document/enforce that host applications must not trust `Webhooks::Request#shop` as an authenticated tenant identifier unless independently corroborated (e.g., against a shop-specific webhook secret or a separately verified session).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives (or triggers) a legitimate webhook: raw body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the shared `api_secret_key`), and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays this exact request to the same app endpoint but rewrites the header to `x-shopify-shop-domain: victim.myshopify.com` (body `B` and hmac `H` left untouched).
3. `ShopifyAPI::Webhooks::Registry.process` constructs a `Webhooks::Request`; `HmacValidator.validate` recomputes the HMAC over `to_signable_string` (`= B`) and it matches `H`, so validation passes: [6](#0-5) 
4. The registered handler receives `data.shop == "victim.myshopify.com"` even though the request never originated from Shopify on behalf of that shop, as illustrated by the test asserting `data.shop` is taken verbatim from the `shopify-shop-domain` header: [7](#0-6)

        end
