## Analog Found

### Title
Permissionless `Initialize2` pool creation can be front-run using the same `market` seed with dust amounts, permanently squatting/DoS'ing the pool for that market - (File: `program/src/processor.rs`)

### Summary
`Process::process_initialize2` derives every pool-defining account (`amm_target_orders`, `amm_lp_mint`, `amm_coin_vault`, `amm_pc_vault`, `amm_info`) deterministically from the caller-supplied `market_info.key`, which the code explicitly treats as "Just a seed for AMM account. Can be any account." Any signer can invoke `Initialize2` for an arbitrary `market` pubkey with attacker-chosen `init_pc_amount`/`init_coin_amount`, with no restriction tying the caller to a privileged initiator of that market's pool. This mirrors the Connext `prepare` griefing pattern: the "invariant data" (here, the `market` pubkey used for address derivation) is public/predictable, and an attacker can front-run a pending legitimate `Initialize2` transaction with the exact same accounts but a trivially small deposit amount.

### Finding Description
`Self::generate_amm_associated_spl_token`, `generate_amm_associated_spl_mint`, and `generate_amm_associated_account` derive the coin/pc vaults, LP mint, `AmmInfo`, and `TargetOrders` addresses purely from `program_id`, `market_account.key`, and fixed seeds (`COIN_VAULT_ASSOCIATED_SEED`, `PC_VAULT_ASSOCIATED_SEED`, `LP_MINT_ASSOCIATED_SEED`, `TARGET_ASSOCIATED_SEED`, `AMM_ASSOCIATED_SEED`): [1](#0-0) 

Each helper only checks that the derived-address account's `owner` is still the system program before allocating it; if it is already owned by the program, it unconditionally returns `AmmError::RepeatCreateAmm`: [2](#0-1) 

`process_initialize2` requires only that `user_wallet_info.is_signer` — there is no check that the caller is the intended/legitimate initializer of the pool for that market, and `market_info` itself is documented as "Can be any account": [3](#0-2) [4](#0-3) 

Because the `market` pubkey a legitimate user intends to use is visible in their pending (unconfirmed) transaction, and it fully determines every account address, an attacker can copy that transaction's `market` pubkey into their own `Initialize2` call with a minimal `init_pc_amount`/`init_coin_amount` and submit it first. The only floor on the attacker's contribution is the LP-mint-amount subtraction used to prevent zero-liquidity pools: [5](#0-4) 

which just requires `sqrt(pc*coin) > 10^lp_decimals` — trivially satisfiable with a tiny amount for high-decimal tokens, or a modest amount otherwise.

### Impact Explanation
Once the attacker's dust-funded `Initialize2` transaction lands, all pool-defining accounts for that `market` are permanently owned by the program, so every subsequent `Initialize2` call for the same `market` (including the legitimate user's original transaction) hits `AmmError::RepeatCreateAmm` in `generate_amm_associated_spl_token`/`generate_amm_associated_account`. Since `market` is an external, typically immutable identifier (e.g., an OpenBook/Serum market) that the legitimate creator cannot swap out, this is a **permanent denial of service**: that market can never get a "real" Raydium pool created with the intended reserves/price. In addition, the attacker becomes the de-facto first depositor of a pool with an artificial, attacker-chosen initial ratio and dust liquidity, exposing later depositors/swappers on that pool to price-ratio manipulation and skewed LP-share issuance — a direct economic griefing/value-extraction vector against LP funds, not merely a wasted-gas nuisance.

### Likelihood Explanation
The attack requires only observing a pending `Initialize2` transaction in the mempool (all needed data — `market`, mint accounts — is included in the transaction) and submitting a copy with tiny amounts and higher priority fee/compute unit price, which is straightforward front-running on Solana. No privileged role, special accounts, or non-default build/config is required; this is reachable by any unprivileged actor with a wallet.

### Recommendation
Bind pool creation authorization to the actual initiator rather than relying solely on account-derivation from a public `market` pubkey — e.g., require the `market` account to be validated as a genuine OpenBook/Serum market whose creator/authority matches an expected signer, or add a permissioned "reserve" step (analogous to adding `initiator`/checking `msg.sender` in the Connext fix) so that only the party who reserved the market can complete `Initialize2` with their intended amounts. At minimum, enforce a meaningful minimum initial liquidity relative to token decimals so dust-squatting is not economically trivial, and consider requiring `create_fee_destination`/config-level allow-listing of who may initialize a pool for a given market.

### Proof of Concept
1. Legitimate user Alice broadcasts an `Initialize2` transaction for `market = M` with `init_coin_amount = 1_000_000`, `init_pc_amount = 1_000_000` intending to seed pool `M` at a fair price.
2. Attacker Bob observes Alice's pending transaction, extracts `market = M`, and immediately submits his own `Initialize2` transaction with the same `M` (and same derived `amm_target_orders`, `amm_lp_mint`, `amm_coin_vault`, `amm_pc_vault`, `amm_info` addresses per [1](#0-0) ), but `init_coin_amount = 1`, `init_pc_amount = large_skewed_value` (subject only to the `sqrt` LP floor check at [5](#0-4) ), with a higher fee to land first.
3. Bob's transaction succeeds, taking ownership of all pool accounts for market `M`.
4. Alice's original transaction now fails at `generate_amm_associated_account`/`generate_amm_associated_spl_token` with `AmmError::RepeatCreateAmm` [6](#0-5) , permanently, since `M` cannot be changed.
5. The market is now permanently stuck with Bob's skewed-price, dust-liquidity pool, and any subsequent deposit/swap activity is exposed to the manipulated initial ratio.
