### Title
Webhook shop attribution is unauthenticated — HMAC binds only the body, not the `shop-domain` header, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body. The `shop` value that is subsequently used to attribute the event to a tenant is read from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is never included in the signed material. Because the webhook signing secret (`api_secret_key`) is the app's secret, shared across every shop that installs the app, any shop owner can legitimately obtain a validly-signed `(body, hmac)` pair for their own store and then replay it to the app's webhook endpoint with a forged `shop-domain` header naming a different, victim shop. The HMAC check still passes, and the handler is invoked with attacker-chosen `topic`/`body` attributed to the victim shop.

### Finding Description
The identity binding that should hold is:
`shop authenticated by the signature == shop used as the tenant key for the webhook`

In this gem that equality is broken:

- `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `#shop` is read straight from an unauthenticated header, independent of the signature: [2](#0-1) 
- `Utils::HmacValidator.validate_signature` only compares the HMAC over `to_signable_string` (the body), never touching the shop header: [3](#0-2) 
- `Registry.process` validates only that body-HMAC, then immediately trusts `request.shop` as the tenant identifier passed to the handler: [4](#0-3) 

Since `api_secret_key` is per-app (not per-shop), any merchant/tester who installs the app on their own store can generate a body+HMAC pair that Shopify would have sent for their own shop, then submit that exact `(raw_body, hmac)` to the app's webhook endpoint while substituting the `shop-domain` header with an arbitrary target shop's domain. `HmacValidator.validate` still returns `true` because the header is not part of the signed data, and `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-controlled header value, invoking the host app's handler as if the event genuinely originated from the victim shop.

### Impact Explanation
This crosses a tenant boundary using only a signature the attacker legitimately possesses (from their own store's webhook traffic), without needing the app's `client_secret`, an access token, or any privileged credential. Depending on how a host application keys its local state off `data.shop` in the webhook handler (e.g. `app/uninstalled`, `shop/redact`, order or customer events), this allows an unprivileged internet user to inject fabricated events attributed to a victim shop — corrupting per-tenant state, triggering false uninstall/redact flows, or otherwise achieving cross-tenant interference. This matches the Critical "cross-tenant access" category.

### Likelihood Explanation
Likelihood is high: the attacker only needs their own (potentially free/dev) store with the target app installed to harvest a valid `(body, hmac)` pair, and the webhook endpoint is a public HTTP endpoint by design. No secret material, session, or elevated privilege is required — only the ability to install the app once and then send a crafted HTTP request with a substituted header.

### Recommendation
Bind the shop identity into the material that is HMAC-verified, or otherwise cryptographically tie the `shop-domain` header to the verified body before it is trusted as a tenant key:
- Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) in the signed string that `HmacValidator` verifies, e.g. by extending `VerifiableQuery#to_signable_string` for `Webhooks::Request` to canonically include these header values alongside the body, and reject requests where they are absent/mismatched.
- Where possible, cross-check the header-derived shop against server-side registration/session state for the topic before invoking the handler.
- Add negative tests asserting that a valid body-HMAC combined with a mismatched/forged `shop-domain` header is rejected.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) shop `attacker.myshopify.com`.
2. Attacker triggers a real webhook event (e.g., updates an order) so Shopify sends a legitimately-signed payload: `raw_body`, `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes HMAC over `raw_body` only, matches `H`, and returns `true` (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` proceeds and calls the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker's event data>)` (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the host application to process attacker-controlled data as if it belonged to the victim shop.
