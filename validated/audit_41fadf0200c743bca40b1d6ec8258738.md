### Title
Escrow Credited With Unverified Requested Amount Instead of Actual Tokens Received in `IntentGatewayV2.placeOrder` (Tron) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
In the Tron deployment of `IntentGatewayV2`, `placeOrder()` credits the `_orders` escrow ledger with the protocol-fee-reduced version of the *caller-specified* input amount (`reducedInputs[i].amount`) instead of the amount the contract actually received from `safeTransferFrom`. Any user placing an order with a fee-on-transfer, rebasing, or otherwise non-1:1 ERC20 token as input can cause the gateway's internal accounting to exceed its real token balance, exactly mirroring the reported bug class of recording an intended/expected amount as "locked funds" without validating it against what was actually transferred.

### Finding Description
`placeOrder()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` computes `reducedInputs[i].amount` purely from the order's declared `order.inputs[i].amount` minus the protocol fee percentage: [1](#0-0) 

In the no-predispatch branch, tokens are pulled with `safeTransferFrom` but the actual received amount is never measured — the code simply calls `transferFrom` and then unconditionally adds `reducedInputs[i].amount` to escrow: [2](#0-1) 

If the input token deducts a transfer fee (deflationary/fee-on-transfer token) or otherwise delivers less than `order.inputs[i].amount`, the gateway's actual token balance increases by less than the amount credited to `_orders[commitment][token]`. This is the exact root cause pattern from the external report: the queuing/escrow step trusts a declared amount rather than verifying the funds actually locked, so the "loss"/shortfall is not accounted for.

This directly contradicts the fix already present in the canonical EVM contract, which measures balance-before/balance-after and mutates `order.inputs[i].amount` to the actually-received amount before computing fees and commitments: [3](#0-2) 

The Tron contract's `withdraw()` function then blindly trusts this inflated `_orders` ledger and transfers out the full recorded amount without ever checking the contract's actual token balance: [4](#0-3) 

Because escrow accounting is a shared per-token pool across all commitments, an inflated `_orders` entry for one order silently consumes real token balance that belongs to other users' legitimately-escrowed orders in the same token.

### Impact Explanation
This is a High severity issue reachable by any unprivileged user submitting a single `placeOrder` transaction with a deflationary/fee-on-transfer token:
- The internal escrow ledger (`_orders`) becomes systematically over-stated relative to the contract's real token balance.
- Later legitimate withdrawals/redemptions (`withdraw()`, called from `onAccept` cross-chain settlement or `onGetResponse` refunds) for other orders in the same token can revert due to insufficient actual balance — a race-dependent, permanent freezing of funds for whichever user's withdrawal executes last.
- In aggregate this creates protocol insolvency for the affected token pool: the sum of all promised escrow balances exceeds what the contract actually holds.

### Likelihood Explanation
Likelihood is high: `placeOrder` is a fully permissionless, single-transaction entry point, no governance or privileged role required, and the only precondition is that the input token asset is a fee-on-transfer/deflationary ERC20 (a token property fully controlled by the order creator, who can choose any input token address).

### Recommendation
Mirror the fix already implemented in `evm/src/apps/IntentGatewayV2.sol`: measure the contract's token balance immediately before and after each `safeTransferFrom` call, use the *actual delta* as the amount that is mutated into `order.inputs[i].amount`, and derive `reducedInputs`/escrow crediting from that measured amount rather than the caller-declared amount, for both the predispatch and non-predispatch code paths in the Tron contract.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 token (e.g., 1% fee burned on every transfer) and register it as a supported input asset.
2. User A calls `placeOrder` with `order.inputs[0].amount = 1000` of this token, no protocol fee. The contract's actual balance only increases by `990` (1% fee taken), but `_orders[commitmentA][token]` is credited with `1000`.
3. Separately, User B places a normal order in the same token for `500`, actually transferring `500` real tokens into the contract (assume User B's token is a standard ERC20 or the same FOT token, contract balance now `990 + 495 = 1485` actual vs. ledger total `1000 + 500 = 1500`).
4. When both orders are filled/settled and `withdraw()` is invoked for both commitments, total ledger claims (`1500`) exceed the actual contract balance (`1485`), causing the second `withdraw()` call to revert (`TransferFailed`), permanently freezing that user's/solver's rightful escrow redemption.
