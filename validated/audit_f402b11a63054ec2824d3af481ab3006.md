### Title
Flash-loan-manipulable spot pool price used unguarded (by default) as the trade/funding price for intent fills - ([File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts])

### Summary
Simplex's FX filler strategy prices curveless, venue-funded pairs directly from a Uniswap V4 pool's current `sqrtPriceX96` (spot price), with no TWAP, and with the only defense (`checkPriceGuard`/`referencePrice`+`maxDeviationBps`) being an *optional* per-position config that is disabled ("unguarded") unless the operator explicitly sets it. This is the same bug class as the AutoShark Finance incident: a single-block price manipulation of an on-chain AMM pool (e.g. via a flash loan) that a protocol trusts as its price source for real fund movement.

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` / `computeDirectPoolPriceUsd` reads the pool's live tick/`sqrtPriceX96` via `StateView.getSlot0` and derives `sdkPool.token0Price`/`token1Price` as the "USD price" of the exotic token, with no TWAP or size/impact term: [1](#0-0) [2](#0-1) 

This raw pool mid feeds `FXFiller.resolveLegRates`/`referenceRate`, which is used both to price the actual fill amount (`rate = 1/venueUsd`) and to size the order for confirmation depth: [3](#0-2) [4](#0-3) 

The only mitigation is `checkPriceGuard`, driven by an operator-supplied `referencePrice`/`maxDeviationBps` pair per position — and it is explicitly optional: "The two fields must be set together; omit both to leave the chain unguarded," confirmed by the corresponding test that shows the rate is used unmodified ("sizes unguarded") when no reference is configured: [5](#0-4) [6](#0-5) 

Even when the guard IS configured, the accompanying flow doc explicitly documents that it "checks deviation from a static reference, not execution cost," and the pool read has "no size or impact term" — meaning an attacker can still move the spot price within the allowed `maxDeviationBps` band in one block and profit, since there is no TWAP smoothing: [7](#0-6) 

### Impact Explanation
This maps directly onto the report's bug class (Medium-severity flash-loan spot-price manipulation): whoever controls the pool's spot price for one block controls the price Simplex uses to fill a submitted intent order, and Simplex withdraws liquidity from its own Uniswap V4 LP position to fund that fill atomically with the manipulated quote: [8](#0-7) 
An attacker who manipulates the target pool downward (e.g. flash-loan-funded dump of the exotic token) causes `getExoticTokenPrice` to under-report the exotic token's USD value; this inflates `rate = 1/venueUsd`, causing the filler to pay out disproportionately more of the exotic token per unit of USD-stable input than fair value — the intent solver's escrowed/vault funds are drained at a manipulated rate, exactly the mechanism (AMM price crash via flash loan → protocol pays out at the crashed price) described in the AutoShark Finance report.

### Likelihood Explanation
This is reachable from a single unprivileged action: any user can submit an intent order that FXFiller will attempt to fill for a curveless, USD-stable/exotic pair configured under `[vault.uniswapV4]`; combined with a same-block/adjacent manipulation of the referenced pool (which needs no privileged access — any market participant, including via a flash loan, can move a thin pool's spot price), the filler's pricing and funding logic consumes the manipulated quote directly. Likelihood is reduced only where an operator has both configured `referencePrice`/`maxDeviationBps` for every position AND kept `maxDeviationBps` tight relative to pool depth/manipulation cost — neither of which is enforced by the code; the guard is opt-in per position, so any misconfigured or newly-added pair is exposed by default.

### Recommendation
- Make the price guard mandatory (not opt-in) for any venue-priced position, or refuse to venue-price a pair when no guard is configured, rather than defaulting to "unguarded."
- Replace/augment the spot `slot0` read with a TWAP (time-weighted average, e.g. Uniswap V3/V4 observation-based oracle) so a single-block manipulation cannot move the price used for fills.
- Incorporate the pool's fee tier and a size/impact term into `computeDirectPoolPriceUsd`/`computeLegPolicyOutput` so quoted rates reflect realistic execution cost rather than an unweighted mid.
- Tighten `maxDeviationBps` bounds and/or add a minimum reference-price liquidity/depth check before trusting `getExoticTokenPrice`.

### Proof of Concept
1. Operator configures a curveless pair (e.g. `USDC/CNGN`) funded via `[vault.uniswapV4]`, without setting `referencePrice`/`maxDeviationBps` on the position (per docs, this is valid/"unguarded").
2. Attacker manipulates the target Uniswap V4 pool's spot price in one block (e.g. flash-loan swap dumping the exotic token), depressing `sdkPool.token1Price`/`token0Price`.
3. Attacker (or an accomplice) submits an intent order matching this pair while the manipulated price is live.
4. `FXFiller.resolveLegRates` → `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` returns the manipulated USD price with no guard rejecting it (`checkPriceGuard` short-circuits true when no reference configured, per `fx.price-guard.test.ts`'s "sizes unguarded" case).
5. `computeLegPolicyOutput` computes the fill output at the manipulated `rate`, and Simplex withdraws Uniswap V4 LP liquidity to fund the resulting over-generous payout, which the attacker can arbitrage on the real market for profit — draining the solver's vault position, mirroring the AutoShark Finance flash-loan/price-crash exploit.

	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

	private async referenceRate(
		leg: ResolvedLeg,
		venueUsdPrice: (chain: string, token1Address: string) => Promise<Decimal | null>,
	): Promise<Decimal | null> {
		const policy = leg.pair.bidPricePolicy ?? leg.pair.askPricePolicy
		if (policy) {
			const rate = policy.getPrice(new Decimal(0))
			return rate.gt(0) ? rate : null
		}
		// Venue-priced pair: token0 is USD-stable (constructor invariant), so the
		// venue's USD-per-token1 quote inverts straight into token1-per-token0.
		const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
		if (!venueUsd) return null
		const venueRate = new Decimal(1).div(venueUsd)
		// Same guard as trade pricing: this rate sizes the order's USD notional
		// for confirmation depth, and a manipulated pool understating the value
		// would shrink the reorg protection — the exact attack the guard exists
		// to stop. Refusing to size skips the order, consistent with pricing.
		if (!this.checkPriceGuard(undefined, leg.token1Chain, venueRate)) return null
		return venueRate
	}

			if (venueUsd) {
				// Guard compares the venue's token1-per-USD quote against the static reference.
				if (!this.checkPriceGuard(orderId, leg.token1Chain, new Decimal(1).div(venueUsd))) {

				// to report a round-trip margin against. The price guard above is
				// the venue-specific defense.

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```

# Venue pricing (Uniswap V4 funded pairs)

Verified 2026-08-19.

```
resolveLegRates(...)
  curveless pair && token0 is a USD stable
    -> venuePriceMemo() -> getVenueUsdPrice(chain, token1)
         -> UniswapV4FundingPlanner.getExoticTokenPrice
              picks the position with the largest pool liquidity
              -> computeDirectPoolPriceUsd -> sdkPool.token0Price / token1Price
    -> checkPriceGuard(...)   reject if outside maxDeviationBps of the static reference
    -> rate = 1 / venueUsd
  otherwise -> the pair's ask/bid curve at the leg's notional
```

`computeDirectPoolPriceUsd` returns the **raw pool mid** derived from `sqrtPriceX96`. The pool's
fee tier is read and stored on the hydrated position (`pos.fee`) but never applied to the price,
and there is no size or impact term — `computeLegPolicyOutput` extends the mid linearly across the
whole priced quantity. `checkPriceGuard` is the only defense on this path, and it checks deviation
from a static reference, not execution cost. A venue-priced pair that has to swap through its own
pool to source inventory pays a fee tier it never quoted against.
