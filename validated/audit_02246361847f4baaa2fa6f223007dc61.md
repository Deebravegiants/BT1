### Title
Webhook HMAC covers only the raw body, not the `shop`/`topic` identity headers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw HTTP body. The `shop` and `topic` values that `ShopifyAPI::Webhooks::Registry.process` uses to select a handler and to populate `WebhookMetadata.shop` (the tenant identity passed to the app) come from HTTP headers that are excluded from the HMAC computation entirely.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `api_version`, and `webhook_id` by reading the `x-shopify-*`/`shopify-*` headers directly: [1](#0-0) 

But `to_signable_string`, which is what `Utils::HmacValidator.validate` actually verifies, returns only `@raw_body`: [2](#0-1) 

`Registry.process` validates the HMAC over the body, then dispatches based on `request.topic`, and forwards `request.shop` unchanged as the tenant identity to the app's handler: [3](#0-2) 

The identity binding that should hold is: `shop header value == shop that the HMAC-signed body was actually generated for`. Because the HMAC signable string only contains the body bytes, the `shop-domain` and `topic` headers are never bound to the signature. Since the HMAC secret (`api_secret_key`) is shared by the app across every shop that installs it, any shop that can trigger a genuine webhook for itself possesses a valid `(body, hmac)` pair signed with the app's own secret. That merchant can then resend the identical body/HMAC to the app's webhook endpoint while substituting the `shop-domain` (and/or `topic`) header for a different, victim shop. `HmacValidator.validate` still passes because it never inspects the headers, and `Registry.process` hands the handler a `WebhookMetadata` claiming to be from the victim shop.

### Impact Explanation
This is a cross-tenant identity break: an unprivileged party who has installed the app on their own shop can cause the host application to process attacker-controlled webhook content under a different shop's identity (`data.shop`). Any app logic that keys persistence, authorization, or side effects off `WebhookMetadata#shop` without independent verification will attribute attacker data to another tenant, which matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
The attacker only needs to be a legitimate (even free-trial) installer of the app to obtain one valid `(raw_body, hmac)` pair for their own shop, then replay it with a rewritten `shop-domain`/`topic` header — no possession of `api_secret_key` or any privileged access is required. The gem's own webhook processing method offers no protection against this because header values are structurally excluded from what the signature covers.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook_id`) in the HMAC-signable payload used by `ShopifyAPI::Webhooks::Request#to_signable_string`, or otherwise cryptographically bind them to the signed body, so that a webhook cannot be replayed under a different shop/topic without invalidating the signature.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers an event that produces a genuine webhook; Shopify sends `raw_body B` with header `x-shopify-shop-domain: attacker.myshopify.com` and a valid `x-shopify-hmac-sha256: H`, where `H = HMAC(api_secret_key, B)`.
2. Attacker resends the exact same `raw_body B` and `hmac H` to the app's webhook endpoint, but replaces the header with `x-shopify-shop-domain: victim.myshopify.com` (and/or changes `x-shopify-topic`).
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` recomputes `HMAC(api_secret_key, B)`, which still equals `H`, so validation passes: [4](#0-3) 
4. `Registry.process` invokes the topic handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed_body, ...)`, causing the app to process attacker-controlled data under the victim shop's identity.

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
