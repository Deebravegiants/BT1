### Title
Governance can zero out `OutboundRequestDeliveryReward` / `OutboundConsensusDeliveryReward` after a relayer has already delivered, permanently forfeiting the relayer's earned-but-unclaimed reward - (File: modules/pallets/relayer/src/outbound_request.rs, modules/pallets/relayer/src/outbound_consensus.rs)

### Summary
The Hyperbridge relayer pallet pays outbound-delivery rewards to relayers who have already performed the delivery work on a destination chain, but the reward amount is *looked up at claim time* rather than being fixed/escrowed at the time the eligible action (message/consensus delivery) occurred. If the reward for a `module_id` or destination `StateMachine` is reduced to zero after a relayer has delivered the request/consensus update but before the relayer submits its claim, the claim is rejected and the reward is permanently lost — mirroring the reported Sherlock issue where removing a reward token from `SingleSidedLiquidityVault` causes users to permanently lose already-accrued, unclaimed rewards.

### Finding Description
For hyperbridge-originated request delivery rewards, `process_outbound_request_delivery_claim` fetches the reward from mutable storage at claim time and reverts if it is zero: [1](#0-0) 

The reward for a `module_id` can be changed (including to zero, which the pallet treats as "not on the allowlist") at any time via the governance-only extrinsic: [2](#0-1) 

The identical pattern exists for the mandatory-consensus-rotation delivery reward: `process_outbound_consensus_delivery_claim` reads `OutboundConsensusDeliveryReward::<T>::get(destination)` and rejects the claim if it is zero, even though the relayer already performed the on-chain delivery that is being proven via a valid state proof: [3](#0-2) 

This reward, too, can be changed by governance at any time: [4](#0-3) 

In both flows, a relayer's eligibility to be paid is not fixed at the moment the qualifying event happens (successful delivery, attributable via `RequestReceipts`/`EvmHost._epochs[set_id]`), but is instead re-evaluated against present-day, mutable reward-configuration storage when the claim is later submitted. There is no snapshotting of the reward amount at delivery time and no grace period/timelock before a reward reduction takes effect. This is the same root cause as the external report: a value that should be locked in at the time work is performed can instead be zeroed out by a subsequent, unrelated, non-malicious governance update, permanently forfeiting the relayer's entitlement, since `OutboundRequestsClaimed`/`OutboundConsensusRotationsClaimed` provide no mechanism to "grandfather" already-delivered work under the reward rate that was active when the work was done.

Contrast this with the ordinary relayer fee flow (`Fees` map, `pallet_ismp_relayer::accumulate`/`withdraw`), where the amount owed is derived from the fee actually escrowed with the original request/response (proved via state proof) and stored in a per-relayer balance — that amount can't be revoked by a later parameter change. The two allowlisted "outbound delivery reward" claim types deviate from that safer pattern by re-deriving the payable amount from a mutable, governance-controlled map at claim time.

### Impact Explanation
An unprivileged relayer can perform real, valuable work (deliver a hyperbridge-originated cross-chain request, or deliver a mandatory consensus authority-set rotation proof) in good faith based on the currently configured reward. If governance subsequently adjusts (in particular, zeroes) `OutboundRequestDeliveryReward[module_id]` or `OutboundConsensusDeliveryReward[destination]` — an entirely ordinary, non-malicious governance operation to disable/adjust future rewards — the relayer's claim for delivery it has already completed will unconditionally revert with `OutboundRequestNoRewardConfigured` / `OutboundNoRewardConfigured`. Because the commitment/rotation was already proven-deliverable on the destination chain (its receipt/epoch is fixed and immutable there), the relayer has no way to "re-deliver" for a different reward; the entitlement for that specific delivery is permanently and irrecoverably lost. This is a real loss of expected relayer earnings and an unfair/broken reward-accounting invariant — a Medium-severity permanent-freezing/loss-of-funds issue in the relayer reward accounting, matching the severity class of the original report.

### Likelihood Explanation
This requires only ordinary, expected governance activity (adjusting per-module or per-chain reward rates, which the code explicitly supports via `set_outbound_request_delivery_reward` / `set_outbound_consensus_delivery_reward`) combined with normal operational latency between "relayer completes delivery" and "relayer submits its claim" (the relayer must first wait for/obtain a state proof of the destination receipt and construct/sign the claim). Any reward-rate change or module deallowlisting during that window triggers the loss — this is not a contrived attack path but a foreseeable consequence of routine reward-parameter tuning.

### Recommendation
Snapshot the reward amount at the time the qualifying delivery is durably recorded (e.g., store the applicable reward alongside the receipt/commitment, or key a `PendingReward(commitment) -> amount` entry at request-dispatch or receipt time) rather than re-reading a mutable, governance-controlled reward map at claim time. Alternatively, add a timelock/grace period so that reward reductions only take effect for requests dispatched/rotations occurring after the change, and continue honoring the old reward for deliveries already completed under the previous configuration.

### Proof of Concept
1. Governance calls `set_outbound_request_delivery_reward(module_id = "X", amount = R > 0)`, enabling the allowlist entry (`modules/pallets/relayer/src/lib.rs:96-109`).
2. Module `X` dispatches a hyperbridge-originated `PostRequest` to a destination chain; a relayer delivers it, and the destination records the relayer in its receipt trie (e.g. `RequestReceipts[commitment]` on an EVM destination).
3. Before the relayer submits `claim_outbound_request_delivery_reward`, governance calls `set_outbound_request_delivery_reward(module_id = "X", amount = 0)` (a routine reward-schedule update, not an attack).
4. The relayer now submits a fully valid `OutboundRequestDeliveryClaim` with a correct state proof of the destination receipt and a correct signature (`modules/pallets/relayer/src/outbound_request.rs:119-197`).
5. `OutboundRequestDeliveryReward::<T>::get(&module_id)` returns `0`; the `ensure!(reward > BalanceOf::<T>::default(), Error::<T>::OutboundRequestNoRewardConfigured)` check at `outbound_request.rs:148-149` reverts the claim.
6. Since `commitment` was already delivered and consumed on the destination (the receipt is immutable there) and `OutboundRequestsClaimed` is never set (the transaction reverted), the relayer has no path to ever collect the reward for that already-completed delivery — the reward is permanently lost. The identical sequence applies to `claim_outbound_consensus_delivery_reward` via `OutboundConsensusDeliveryReward` (`outbound_consensus.rs:174-176`).
