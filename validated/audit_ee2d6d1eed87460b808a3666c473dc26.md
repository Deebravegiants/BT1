## Analysis Result

The analog vulnerability class from the external report (payable/receiving functions with no path to recover funds on failure) has a genuine, reachable root cause in `multisig-factory/src/lib.rs`.

Unlike its sibling factory contracts — `staking-pool-factory/src/lib.rs` and `lockup-factory/src/lib.rs` — which both attach an `on_..._create` callback to detect promise failure and refund the attached deposit back to the caller [1](#0-0) [2](#0-1) , `MultisigFactory::create` has no such callback and no refund logic at all [3](#0-2) .

### Title
Permanent Loss of Attached NEAR Deposit on Failed Account Creation in `MultisigFactory::create` - (File: multisig-factory/src/lib.rs)

### Summary
`MultisigFactory::create` is a `#[payable]` public entrypoint that batches `create_account`, `deploy_contract`, `transfer`, and `function_call` into a single promise, but never attaches a callback to check whether the batch succeeded, and never refunds the caller's attached deposit if it fails.

### Finding Description
`MultisigFactory::create` is defined as: [4](#0-3) 

Any unprivileged caller attaches NEAR and invokes `create`, which schedules `Promise::new(account_id).create_account().deploy_contract(...).transfer(env::attached_deposit())...`. If this promise batch fails for any reason reachable by an unprivileged caller — most notably the target `account_id` already existing (e.g., because another caller, or the attacker themselves front-running, already created `name.<factory>`), or the requested `name` being invalid — the entire receipt fails atomically. In that case, `env::attached_deposit()` is never transferred out of the factory contract, and it also is never returned to the original caller, because there is no `on_..._create`-style callback (as exists in `staking-pool-factory` and `lockup-factory`) to detect the failure and issue a refund `Promise`.

Since `MultisigFactory` has no other state, no owner, and no withdrawal method, the attached deposit becomes permanently stuck on the factory contract's balance with no code path to ever move it out.

### Impact Explanation
This matches the "Permanent freezing, unrecoverable lock, or irrevocable loss of user or protocol funds in ... factory refund ... flows" impact category. A user's attached NEAR deposit (which, per `staking-pool-factory`, is expected to be in the tens of NEAR range for storage costs) is irrecoverably lost whenever the underlying account-creation promise fails.

### Likelihood Explanation
Likelihood is realistic and does not require any privileged role: an unprivileged attacker can front-run a victim's `create` call with the same `name` argument (a valid, low-cost NEAR transaction), or simply reuse the same `name` themselves after a first attempt, causing `create_account()` for `name.<factory>` to fail on the victim's or their own later call while their attached deposit is consumed by the batched transaction and never refunded.

### Recommendation
Add an `on_multisig_create`-style callback method (analogous to `on_staking_pool_create` / `on_lockup_create`) that is invoked via `.then(...)` after the account-creation promise, checks `is_promise_success()`, and issues `Promise::new(predecessor_account_id).transfer(attached_deposit)` when creation failed.

### Proof of Concept
1. User A calls `multisig-factory.create({name: "team", members: [...], num_confirmations: 2})` attaching, e.g., 5 NEAR, in transaction T1.
2. Attacker (unprivileged) submits a competing transaction T2 calling `create({name: "team", ...})` (or simply calls `create` first for the same `name`), which is included in an earlier block/receipt so that `team.<factory>` already exists by the time T1's `create_account()` executes.
3. T1's batched promise (`create_account` + `deploy_contract` + `transfer` + `function_call`) fails atomically because the account already exists.
4. Because there is no callback verifying success or refunding the deposit (unlike `staking-pool-factory::on_staking_pool_create` and `lockup-factory::on_lockup_create`), User A's 5 NEAR remains on the `multisig-factory` account balance permanently, with no method in `MultisigFactory` (which has an empty struct and only the `create` method [5](#0-4) ) available to recover it.

    /// Callback after a lockup was created.
    /// Returns the promise if the lockup creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
