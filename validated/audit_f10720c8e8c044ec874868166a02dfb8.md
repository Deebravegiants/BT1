Audit Report

## Title
Legacy Web API Trigger Handler Callback Overwrite Enables Cross-Client Response Misdelivery - (File: `core/services/gateway/handlers/capabilities/handler.go`)

## Summary
`HandleLegacyUserMessage` stores the per-request callback in the shared `h.savedCallbacks` map keyed only by the caller-controlled `msg.Body.MessageID`, with no uniqueness/collision check before the write, unlike the newer v2 HTTP trigger handler which explicitly rejects duplicate in-flight request IDs. A second concurrent request using the same `MessageID` silently overwrites the first request's registered callback, and `handleWebAPITriggerMessage` later delivers the DON's response to whichever callback is currently stored for that `MessageID`, causing cross-client response misdelivery.

## Finding Description
`ProcessRequest` in `core/services/gateway/gateway.go` (lines 221-295) decodes an incoming JSON-RPC/legacy request, validates the message via `msg.Validate()`, and routes it to `h.HandleLegacyUserMessage(ctx, msg, callback)` without ever checking whether `msg.Body.MessageID` is already in use by another in-flight request. [1](#0-0) 

Inside `HandleLegacyUserMessage`, after payload/timestamp/method validation, the handler registers the caller's callback keyed purely by `msg.Body.MessageID`, with no existence check before overwriting: [2](#0-1) 

This is unlike the newer v2 HTTP trigger handler, which explicitly detects and rejects duplicate in-flight request IDs with a `"in-flight request"` conflict error, confirming that a fix pattern already exists elsewhere in the codebase: [3](#0-2) 

When a DON node later responds, `handleWebAPITriggerMessage` looks up and deletes the callback purely by `MessageID` and forwards the response to whatever is currently registered: [4](#0-3) 

`MessageID` originates from the JSON-RPC request `ID`/legacy message body, which is fully attacker-supplied; test helpers throughout the codebase (e.g. `newSignedLegacyRequest`, `invoke_trigger.go`) confirm `MessageID` is a free-form client-chosen string with no server-side uniqueness enforcement in this handler. [5](#0-4) [6](#0-5) 

Signature validation (`msg.Validate()`, `msg.Sign`) authenticates the sender's identity/authorization to submit a trigger message but does not bind or reserve `MessageID` uniqueness across different callers; it merely proves the message came from a holder of a given key. There is no session/requester binding tied to the `savedCallbacks` map entry, so two distinct signed messages from two different keys can collide on the same `MessageID` and one legitimately overwrites the other's callback.

## Impact Explanation
If two concurrent legacy `web_api_trigger` requests use the same `MessageID`, the second overwrites the first's saved callback in `h.savedCallbacks`. When a DON node responds, `handleWebAPITriggerMessage` delivers the response to whichever callback is currently registered, meaning the response intended for the first caller can be delivered to the second caller instead, and the first caller's callback is orphaned (their `ProcessRequest` call blocks until `callback.Wait(ctx)` times out, since nothing will ever resolve it, yielding a request-timeout error to that caller). This maps to the "cross-user response corruption" and "gateway request impersonation" impact classes called out as in-scope. The severity is bounded by what the observation-source pipeline returns (e.g., HTTP bridge fetch results) being delivered to an unintended party, or a legitimate caller silently failing to receive its response.

## Likelihood Explanation
Any client capable of submitting a legacy `web_api_trigger` request to the gateway (e.g., through an external initiator) can choose an arbitrary `MessageID`; this requires no elevated privilege, only the ability to sign a message with any keypair, since signature checks only validate sender identity, not `MessageID` uniqueness. Because `MessageID` is short-lived (only exists for the duration the request is in-flight, pruned after `CallbackMaxAgeSec`, default 120s) and there is no per-caller namespace, an attacker who is able to observe or guess a victim's `MessageID` (or simply chooses to collide with their own concurrent requests to test/verify the race) can reliably trigger the overwrite. This is a straightforward, repeatable race condition rather than a purely theoretical one.

## Recommendation
Bind `savedCallbacks` entries to the requester's identity/session in addition to `MessageID`, e.g., by namespacing the map key with the sender's authenticated address/public key, or by rejecting a `HandleLegacyUserMessage` call when `msg.Body.MessageID` is already present in `h.savedCallbacks` (mirroring the "duplicate request ID" check already implemented in `httpTriggerHandler.HandleUserTriggerRequest`). Additionally, validate on response delivery that the node's response actually corresponds to the original registered caller (e.g., compare sender/workflow context) before invoking `SendResponse`.

## Proof of Concept
1. Craft two distinct signed legacy `web_api_trigger` messages (from different private keys, simulating Client A and Client B) both using `MessageID = "X"`, per `newSignedLegacyRequest`/`triggerRequest` test helper patterns.
2. Concurrently call `gateway.ProcessRequest` (or directly `handler.HandleLegacyUserMessage`) for A's request, then B's request before A's callback is resolved — this is directly testable as a Go unit test extending `TestHandlerReceiveHTTPMessageFromClient` in `core/services/gateway/handlers/capabilities/handler_test.go`, asserting that after both `HandleLegacyUserMessage` calls, `h.savedCallbacks["X"]` holds B's callback, not A's.
3. Simulate a node response for `MessageID = "X"` via `handler.HandleNodeMessage`, and assert that B's callback receives the response (via `cb.Wait`) while A's callback never resolves (times out), directly analogous to the existing `TestHandlerReceiveHTTPMessageFromClient` "happy case" test but with a second colliding registration inserted between callback setup and node response delivery.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

// Legacy requests embed
func newSignedLegacyRequest(t *testing.T, messageID, method, donID string, payload []byte) []byte {
	msg := &api.Message{
		Body: api.MessageBody{
			MessageID: messageID,
			Method:    method,
			DonID:     donID,
			Payload:   payload,
		},
	}
	privateKey, err := crypto.GenerateKey()
	require.NoError(t, err)
	require.NoError(t, msg.Sign(privateKey))
	codec := api.JSONRPCCodec{}
	rawRequest, err := codec.EncodeLegacyRequest(msg)
	require.NoError(t, err)
	return rawRequest
}
