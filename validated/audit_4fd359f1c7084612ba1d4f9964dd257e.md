### Title
Unbounded `order.inputs` / `output.assets` arrays in `IntentGatewayV2.placeOrder` can be weaponized to permanently freeze escrow and brick solver payouts via out-of-gas in `_withdraw` - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2.placeOrder` accepts an `Order` whose `inputs` and `output.assets` arrays have no maximum length, mirroring the reported `MarginAccount.provideERC721` class of bug where a user unboundedly grows an array tied to their own account that a later, gas-metered, all-or-nothing loop must fully process. That array is later iterated in full inside `_withdraw` (escrow release/refund) and in the per-input fill accounting loop, both of which are triggered by parties other than the order creator (solvers filling the order, or relayers delivering the cross-chain GET/RefundEscrow response). A malicious order creator can size these arrays so the iteration exceeds the destination or source chain's block gas limit.

### Finding Description
`placeOrder` (`evm/src/apps/IntentGatewayV2.sol:194` and the Tron variant `evm/tron/contracts/apps/IntentGatewayV2.sol:338`) only checks `order.inputs.length == 0` and rejects duplicate output tokens — there is no upper bound on `order.inputs.length` or `order.output.assets.length`. [1](#0-0) 

This attacker-controlled array is later iterated to completion, unconditionally, in `_withdraw`, which releases/refunds escrow token-by-token: [2](#0-1) 

The same array size drives the per-input fill/escrow accounting loop that a solver's `fillOrder`/`_fill` call must execute in full before it can succeed (seen in `IntrinsicIntents.sol` and `ExtrinsicIntents.sol`), and the cross-chain cancel/refund path also loops over `order.inputs` when building the `WithdrawalRequest` and verifying escrow existence: [3](#0-2) [4](#0-3) 

Just like `MarginAccount.provideERC721` letting a user push unbounded NFTs into an array later fully iterated by `ModularSwapRouter.liquidate`, here a user pushes an unbounded number of `TokenInfo` entries into `order.inputs`/`order.output.assets` at `placeOrder` time, and that array is later fully iterated by code paths triggered by other parties (solvers filling, relayers delivering GET responses/RefundEscrow messages) that cannot skip or partially process it.

### Impact Explanation
If the array is large enough that the full loop in `_withdraw` (or the fill-accounting loop) cannot complete within a block's gas limit:
- The `RefundEscrow`/GET-response delivery that is supposed to release escrow back to the order creator can never succeed — `EvmHost.dispatchIncoming` swallows the revert and simply leaves the request permanently retryable-but-failing (`evm/src/core/EvmHost.sol:794-818`), so the escrowed input tokens become permanently stuck in the contract with no way to unlock them.
- Worse, if a solver has already delivered outputs on the destination chain in good faith and the fill's `_withdraw` call (releasing the solver's earned input-token escrow) hits this same unbounded loop and runs out of gas, the solver's payout is unrecoverable even though they already paid out the order — a direct loss of solver funds triggered entirely by data the order creator controls.
This satisfies the "permanent freezing of funds" bar for a valid analog, reachable purely by an unprivileged user submitting a single `placeOrder` transaction (an order/intent), matching the allowed "intents escrow and bids" attack surface.

### Likelihood Explanation
High: `placeOrder` is fully permissionless and unprivileged (any address can call it), the array length is entirely attacker-supplied with no cap, and no privileged role is required to trigger the exploit — an attacker only needs to craft one order with a sufficiently large `inputs`/`output.assets` array and either let it sit uncancellable (self-freeze, weaponizable as griefing/spam) or get a solver to fill it and then have the solver's payout release fail.

### Recommendation
Enforce a maximum length on `order.inputs` and `order.output.assets` (and `predispatch.assets`) in `placeOrder`, sized so that the worst-case `_withdraw`/fill-accounting loop is guaranteed to fit well within the block gas limit on every supported destination chain, mirroring the fix recommended for `MarginAccount` (cap the array, reject orders exceeding it).

### Proof of Concept
1. Attacker calls `IntentGatewayV2.placeOrder` with `order.inputs` containing N (e.g., several thousand) distinct `TokenInfo` entries with tiny/dust amounts and a correspondingly large `output.assets` array; `placeOrder`'s only check (`order.inputs.length == 0`) passes.
2. `placeOrder` escrows all N inputs (transfers can be structured to be cheap, e.g., reusing a low-decimals dust token or wrapped native repeated with different dummy addresses acting as `token` fields), successfully creating the order.
3. Either:
   a. After `order.deadline`, anyone calls `cancelOrder`/triggers the cross-chain GET proof and `_withdraw` is invoked on source chain to refund escrow — the loop over N inputs exceeds the block gas limit and the transaction (or the `dispatchIncoming` callback) always fails, permanently freezing the escrow, or
   b. A solver fills the order, delivers outputs on the destination chain, and the corresponding `_withdraw` call that pays the solver from source-chain escrow hits the same unbounded loop and runs out of gas, permanently losing the solver's expected payout.

**Note:** Due to index size limits, some file contents (in particular the full body of `IntrinsicIntents.sol`/`IntentsBase.sol` beyond the cited ranges, and any potential array-length validation elsewhere in the constructor/params) could not be fully retrieved. A Devin session with full repo access should verify there is no length cap elsewhere (e.g., in `_params` validation or a modifier) before treating this as unmitigated.
