### Title
Unsafe token transfer without return-value check causes silent fund loss / stuck escrow in `IntentGatewayV2` (Tron) - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2` (Tron variant) settles escrowed intent funds — order fills, refunds, dust sweeps, and protocol fee payouts — using raw low-level `.call()` invocations of `transfer()` and only checks that the call did not revert, never decoding the ABI-encoded boolean return value. Any ERC20-compatible token that signals failure by returning `false` instead of reverting will make these transfers silently no-op while the contract still marks the escrow as redeemed, permanently losing the underlying funds for the beneficiary.

### Finding Description
In `withdraw()` (called from `onAccept` for `RedeemEscrow`/`RefundEscrow` requests) and in the `SweepDust` branch of `onAccept`, ERC20 transfers are performed like this: [1](#0-0) 

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```

and [2](#0-1) 

Here `success` only reflects whether the external call reverted at the EVM/TVM level — it does **not** decode the returned `bytes` to check the boolean result the ERC20 standard requires `transfer()` to return. Tokens that return `false` on failure instead of reverting (the exact ZRX-style class of token cited in the referenced Fei Protocol report) will make `success == true` even though no tokens moved.

This is functionally identical to the M04 bug class: the contract elsewhere consistently uses OpenZeppelin's `SafeERC20` (`using SafeERC20 for IERC20;`, and `safeTransferFrom`/`safeTransfer` calls throughout `placeOrder`/`fill`), confirming the intended pattern [3](#0-2)  — but the settlement paths (`withdraw`, `SweepDust`, and the fee payout) bypass `SafeERC20` and use raw `.call` with only a shallow success check.

Critically, in `withdraw()`, escrow accounting is decremented unconditionally after the unchecked transfer: [4](#0-3) 

If the token silently fails, `_orders[body.commitment][token]` is still decremented and `_filled[body.commitment]` is set, so the order is marked as settled/filled/refunded — the beneficiary never receives the tokens and there is no valid path afterward to retry the withdrawal (the commitment is now considered resolved).

### Impact Explanation
This can cause a permanent loss of escrowed user or solver funds:
- On `RedeemEscrow`/`RefundEscrow` delivery, the recipient (user being refunded, or solver being paid for a fill) receives nothing while the order/commitment state is marked as finalized, permanently freezing/losing the escrowed tokens.
- On `SweepDust`, protocol-owned dust can be lost identically.
- The fee payout path (`feeToken.call(...)`) can silently fail to pay the beneficiary while `_orders[body.commitment][TRANSACTION_FEES]` is deleted, losing the fee funds.

This matches "concrete theft or permanent freezing of funds" for tokens exhibiting the false-return-on-failure behavior, reachable purely via the normal relayed cross-chain message delivery path (`onAccept`) that any relayer can trigger once a valid ISMP proof is submitted.

### Likelihood Explanation
The vulnerability triggers deterministically whenever the intent gateway is configured (or a user places an order) with an ERC20 token that returns `false` instead of reverting on transfer failure (e.g., insufficient balance edge cases, blacklist-style tokens, or non-standard tokens like ZRX). Given IntentGatewayV2 accepts arbitrary tokens specified by users in `Order.inputs`/`output.assets`, an attacker or unaware integrator can cause this path to be exercised, and once triggered the loss is irreversible since escrow state is already marked settled.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` handler with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the rest of the contract (`placeOrder`/`fill` already use `safeTransferFrom`). This ensures both call-revert and false-return failure modes cause the transaction to revert, before any escrow accounting or `_filled` state is mutated.

### Proof of Concept
1. A user places an order (or a `SweepDust`/fee-token configuration references) a hostile ERC20 `T` whose `transfer()` returns `false` on failure without reverting (e.g. simulating insufficient allowance edge case or a deliberately malicious token contract deployed on the destination chain).
2. A relayer submits a valid ISMP proof for a `RedeemEscrow`/`RefundEscrow`/`SweepDust` request referencing token `T`.
3. `onAccept` → `withdraw()` executes `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))`; token `T.transfer` returns `false` but does not revert, so `success == true`.
4. `_orders[body.commitment][token]` is decremented and `_filled[body.commitment]` is set as if funds were paid out, while `beneficiary`'s balance of `T` is unchanged — the escrowed tokens remain stuck in the `IntentGatewayV2` contract with no accounting path to reclaim them.
