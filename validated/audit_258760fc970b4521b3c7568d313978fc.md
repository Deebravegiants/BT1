### Title
Vault gateway handler logs entire JSON-RPC request — including the JWT `Auth` credential — at DEBUG level before authorization (`core/services/gateway/handlers/vault/handler.go`)

### Summary
The Kafka advisory describes `NetworkClient` emitting full authentication-related requests/responses (e.g. `SaslAuthenticateRequest`) at DEBUG level, leaking credentials into logs. The Vault gateway handler in this codebase has the same bug class: `HandleJSONRPCUserMessage` logs the complete inbound `jsonrpc.Request` object — before any authorization or redaction — at DEBUG level, and that request carries an `Auth` field used as the bearer/JWT credential for the gateway's Auth0-based authorizer.

### Finding Description
In `core/services/gateway/handlers/vault/handler.go`, every inbound user request is logged in full immediately on receipt: [1](#0-0) 

This happens for *all* methods, prior to `h.requestProcessor.ProcessRequest` (the authorization step), and prior to any params sanitization. The struct being logged is the full `jsonrpc.Request[json.RawMessage]`, which includes an `Auth` field — the same field later checked for presence during authorization-failure logging (`"hasAuth", req.Auth != ""`): [2](#0-1) 

That `Auth` field is consumed by the JWT-based authorizer (`core/capabilities/vault/jwt_based_auth.go`, `core/capabilities/vault/authorizer.go`) as the bearer credential used to authenticate the caller to the Vault gateway. Because the zap/logger `%v`/structured encoding of the request struct includes this field verbatim, enabling DEBUG logging on the gateway process causes every caller's raw bearer token (and raw, unvalidated params, which for `secrets.create`/`secrets.update` may include encrypted secret payloads and identifiers) to be written to the log stream.

The codebase clearly treats this as a known risk pattern — a companion, narrower Debug log for *invalid params* was later fixed to stop echoing raw params, and a regression test was added specifically to prove that fix, while explicitly carving out the pre-existing whole-request Debug log as still present: [3](#0-2) 

That comment ("Observed at Info level so the pre-existing whole-request Debug log is excluded") confirms the line-403 whole-request Debug log is a known, still-existing gap distinct from the fixed invalid-params log.

The equivalent pattern also exists in the sibling handler `core/capabilities/vault/gw_handler.go`, which logs the full node-received request at Debug and the full response at Info: [4](#0-3) [5](#0-4) 

### Impact Explanation
If DEBUG logging is enabled on a Vault gateway/handler node (an operational choice, analogous to Kafka's DEBUG toggle), any unprivileged, unauthenticated client can trigger this log line simply by sending a JSON-RPC request to the vault gateway endpoint — authorization is checked *after* the log statement, so even rejected/unauthorized requests get their `Auth` token written to disk. This satisfies "key/secret disclosure" and "authentication bypass adjacent" criteria: an operator or anyone with log access could harvest bearer tokens submitted by legitimate users and replay them to impersonate those users against the Vault gateway (request impersonation), directly analogous to the Kafka `SaslAuthenticateRequest`/`SaslAuthenticateResponse` credential leakage.

### Likelihood Explanation
Requires DEBUG log level to be enabled on the affected component, same precondition as the Kafka CVE. Given that Chainlink nodes commonly enable DEBUG logging for troubleshooting in staging/production incident response, and that the trigger requires no privilege (just sending a request to the public gateway endpoint), likelihood is moderate — consistent with the Medium severity of the original Kafka advisory.

### Recommendation
- Remove or redact the `req` field from the DEBUG log at `handler.go:403` (and the analogous logs in `gw_handler.go:182` and `:231`) before authorization, at minimum stripping `Auth` and `Params`.
- Follow the pattern already applied to the invalid-params fix (log only `method`/`requestID`, never the raw request body or its `Auth` token) and extend the existing `TestVaultHandler_InvalidParamsDoesNotLogRawParams`-style regression test to cover the whole-request Debug log path.

### Proof of Concept
1. Configure the gateway/vault handler logger at DEBUG level (a supported, documented log-level setting).
2. As any unauthenticated external client, POST a JSON-RPC request to the vault gateway's `secrets.create`/`secrets.list`/etc. endpoint with a crafted `Auth` bearer token.
3. Observe the emitted log line `"handling vault request" method=... requestID=... request=<full struct including Auth>` at `core/services/gateway/handlers/vault/handler.go:403`, which occurs before `ProcessRequest` authorization runs — i.e., even for requests that fail authorization, the submitted credential is persisted to logs.
