Found a genuine identity-binding break in the webhook path.

### Title
Webhook `shop` and `topic` used for routing/dispatch are read from unauthenticated HTTP headers, not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies the request's HMAC over the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` fields used by the registry to select the handler and to build the `data.shop` value passed into the caller's handler are read straight from HTTP headers with no cryptographic binding to that HMAC.

### Finding Description
`to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes the signature purely from that signable string against `Context.api_secret_key` [2](#0-1) . Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from request headers via `shopify_header`, entirely outside the HMAC's coverage [3](#0-2) . This mirrors the report's bug class: "a field acted on but not covered by the HMAC" — the equality that should hold is `hmac_verified_bytes == bytes_the_handler_trusts_for_shop_identity`, but here `hmac_verified_bytes == raw_body` while `shop_used_by_handler == headers["shopify-shop-domain"]`, an entirely different, unauthenticated channel.

Compare this to `Auth::Oauth::AuthQuery`, where `shop` **is** included in `to_signable_string` alongside `code`, `host`, `state`, `timestamp` [4](#0-3) , so the OAuth callback's shop identity is properly bound to the signature. The webhook path lacks this equivalent binding for `shop`.

### Impact Explanation
An attacker who can reach the app's webhook endpoint (which is by design a public, unauthenticated HTTP endpoint) can send an arbitrary `shopify-shop-domain` header alongside a body/topic they don't control the signature for — but if the host application (or any code trusting this gem's parsed `Request#shop`) ever uses `request.shop` for tenant-scoped side effects before/independent of full body-content validation, or if the raw body's HMAC was captured/replayed from one webhook and paired with a forged header for a different shop, the shop attribution is spoofable because the gem does not bind `shop` to the signature. This is a cross-tenant-facing weakness in the identity binding this gem provides to the host app, since `ShopifyAPI::Webhooks::Registry.process` uses `request.shop` to build `data.shop` passed to handlers [5](#0-4) .

### Likelihood Explanation
Moderate: exploitation requires an attacker to control or replay a raw body whose HMAC is valid for the configured `api_secret_key` (i.e., a genuine past webhook payload from Shopify) while substituting the `shop`/`topic` headers, since headers are not covered by the signature. This does not require the `api_secret_key` itself, satisfying the scope's exclusion of credential-requiring findings, and it breaks a tenant-identity binding (shop attribution) rather than merely being a best-practice nit.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or otherwise cryptographically bind the header-derived shop identity) into the value verified by `HmacValidator`, or have `Registry.process` re-derive/cross-check the shop against another authenticated source before dispatching to handlers, mirroring the pattern already used in `AuthQuery#to_signable_string`.

### Proof of Concept
1. Capture a legitimate Shopify webhook `raw_body` and its `shopify-hmac-sha256` header (this pair is valid and passes `HmacValidator.validate` because the signature only covers `raw_body`).
2. Replay the request to the app's webhook endpoint, replacing `shopify-shop-domain` with a different tenant's shop domain and/or `shopify-topic` with a different registered topic.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses `shop`/`topic` from the attacker-controlled headers [3](#0-2) ; `Registry.process` finds a handler by the forged `topic` and invokes it with `data.shop` set to the forged shop [5](#0-4) , since `HmacValidator.validate(request)` still returns true — it only checked `raw_body` against the secret [6](#0-5) .
