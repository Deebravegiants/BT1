### Title
`SystemInstruction::CreateAccount` permanently DoS'd by attacker pre-funding the target address with lamports - (File: programs/system/src/system_processor.rs)

### Summary
`create_account()` in the native System Program rejects the whole `CreateAccount` instruction with `SystemError::AccountAlreadyInUse` whenever the destination account already holds any lamports (`to.get_lamports() > 0`), before any ownership/data check is even relevant to the intent of the caller. Because Solana account addresses used for `CreateAccount` are frequently deterministic (PDAs, `create_with_seed` derived addresses, or otherwise publicly known addresses computed off-chain before the transaction lands), any unprivileged user can front-run or simply race the legitimate creation transaction by sending a trivial system `Transfer` of 1 lamport to that address. Since the target address is fixed by seeds/derivation and cannot be changed by the legitimate protocol, the `CreateAccount` instruction — and any program logic that unconditionally depends on it succeeding — is permanently and irrecoverably blocked. This directly mirrors the reported `AddLiquidityETH` bug class: an attacker manipulates state associated with an address the protocol controls/expects to initialize from a clean slate, permanently breaking a downstream, otherwise-automatic operation that has no fallback path.

### Finding Description
The vulnerable check lives in `create_account`: [1](#0-0) 

```rust
fn create_account(...) -> Result<(), InstructionError> {
    // if it looks like the `to` account is already in use, bail
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        if to.get_lamports() > 0 {
            ic_msg!(invoke_context, "Create Account: account {:?} already in use", to_address);
            return Err(SystemError::AccountAlreadyInUse.into());
        }
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    transfer(from_account_index, to_account_index, lamports, invoke_context, instruction_context)
}
```

This is confirmed by the existing regression test that specifically documents the "already has lamports" rejection path: [2](#0-1) 

The check treats "has any lamports" as equivalent to "is in use", but an attacker who is not privileged over the account (and has no signing authority over it) can trivially put lamports into it via a normal `SystemInstruction::Transfer`, which requires no signature from the destination: [3](#0-2) 

Because `transfer_verified`/`transfer` only require the *source* to sign, and the destination account is credited unconditionally, any address — including a PDA or `create_with_seed` address that a protocol will later try to `CreateAccount` into — can be pre-funded with 1 lamport by anyone who knows the address in advance. Solana Core acknowledges this exact griefing pattern: it recently introduced `SystemInstruction::CreateAccountAllowPrefund`, gated by the `create_account_allow_prefund` feature, whose explicit purpose is to allow account creation "where account has already had rent paid in whole or in part before creation": [4](#0-3) 

This confirms the root cause is real and already recognized by the core team, but the mitigation is opt-in per instruction/feature — the original `CreateAccount` path (still the default and most widely used by CPI-based programs, PDAs, escrow/vault initializations, associated-account patterns, etc.) remains permanently exploitable for any address that is deterministic ahead of time.

### Impact Explanation
Any unprivileged attacker can permanently deny the ability to `CreateAccount` at a specific, deterministic address that a protocol/program plans to initialize (e.g., a PDA computed from known seeds, or a `create_with_seed` derived address published/predictable before the creating transaction lands). Because the address is fixed, there is no retry-with-a-different-address workaround for callers relying on deterministic addressing — the exact analog of the reported bug's permanently-stuck `_graduate()` call. Depending on how the calling program handles the resulting `AccountAlreadyInUse`/`InstructionError`, this can permanently brick account initialization flows for any unprivileged Solana program that has not adopted `create_account_allow_prefund` or does not otherwise tolerate a pre-funded (but uninitialized/system-owned) destination account. This is a concrete availability/DoS impact reachable purely by an unprivileged user, requiring only a single low-value `Transfer` instruction.

### Likelihood Explanation
Likelihood is high: the required action is a normal, permissionless `SystemInstruction::Transfer` of 1 lamport to a known/derivable address, requiring no special privileges, no race beyond simple front-running, and no elevated compute or fees. Any protocol using deterministic addresses (PDAs, seeded accounts) for later `CreateAccount` calls is affected unless it has explicitly moved to `CreateAccountAllowPrefund`.

### Recommendation
Consider hardening the legacy `CreateAccount` path itself (not only via an opt-in new instruction) so that presence of lamports alone does not block account creation — instead gate on owner/data-length (i.e., only reject if the account is owned by a non-system program or already has non-empty data), mirroring the semantics already implemented for `create_account_allow_prefund`. At minimum, broadly document and encourage migration of native/CPI callers (and downstream ecosystem programs) toward `create_account_allow_prefund` to close this griefing vector for existing/legacy call sites that cannot be changed to check for prefunding before invoking `CreateAccount`.

### Proof of Concept
1. Attacker (unprivileged) computes/derives the PDA or `create_with_seed` address `X` that some program `P` intends to initialize via `system_instruction::create_account` in a subsequent, otherwise-legitimate transaction.
2. Attacker submits `SystemInstruction::Transfer { lamports: 1 }` from any funded wallet to `X` (no signature from `X` required, per `transfer`/`transfer_verified`).
3. When `P`'s legitimate transaction later invokes `create_account(..., to_account_index=X, ...)`, the check `to.get_lamports() > 0` is now true, and the instruction fails with `SystemError::AccountAlreadyInUse`, permanently, since the address `X` is fixed and cannot be re-derived elsewhere for this protocol flow.
4. This matches the existing unit test `test_create_already_in_use` (`programs/system/src/system_processor.rs:1014-1040`), which validates that an account "that already has lamports" always causes `CreateAccount` to fail, regardless of who funded it.

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}

fn transfer_verified(
    from_account_index: IndexOfAccount,
    to_account_index: IndexOfAccount,
    lamports: u64,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    let mut from = instruction_context.try_borrow_instruction_account(from_account_index)?;
    if !from.get_data().is_empty() {
        ic_msg!(invoke_context, "Transfer: `from` must not carry data");
        return Err(InstructionError::InvalidArgument);
    }
    if lamports > from.get_lamports() {
        ic_msg!(
            invoke_context,
            "Transfer: insufficient lamports {}, need {}",
            from.get_lamports(),
            lamports
        );
        return Err(SystemError::ResultWithNegativeLamports.into());
    }

    from.checked_sub_lamports(lamports)?;
    drop(from);
    let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
    to.checked_add_lamports(lamports)?;
    Ok(())
}
