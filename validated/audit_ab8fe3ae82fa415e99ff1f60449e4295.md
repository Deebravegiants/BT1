### Title
Unauthenticated Emporium-Min proof lets any address execute arbitrary calls from Emporium's identity with zero balance accounting - (`contracts/CircomDataBuilder.sol`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only proves `message == Poseidon(messageSeed)` [1](#0-0)  and a matching `MainEVMCircuitMin` template that constrains nothing else [2](#0-1) . This lets an attacker submit a trivially-satisfiable proof together with an attacker-chosen `EmporiumStack` whose `signerAddress == address(0)`, which skips all signature verification in `verifyWallet` and unconditionally executes arbitrary `endpoint.call{value}(callData)` from Emporium's own address, while the token-balance accounting loop is a no-op because `erc20TokenAddresses` is empty.

### Finding Description
The broken equality is: **assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter`**. Because `erc20TokenAddresses.length == 0` is required to select the min-proof path, `getBalancesForArray` returns empty arrays on both sides of `runAction`, and the reconciliation loop `for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++)` never executes [3](#0-2) . Meanwhile the ops loop is fully attacker controlled: `EmporiumStack` is decoded straight from `circomData.externalActionData.externalActionMetadata` [4](#0-3) , and when `stack.signerAddress == address(0)`, `verifyWallet` returns immediately without any ECDSA check [5](#0-4) . With `signerAddress == 0`, `op.invokeWallet && stack.signerAddress != address(0)` is always false, so every op falls into "CASE 2: Stateless Interaction", executing `op.endpoint.call{value: op.value}(op.callData)` as a raw external call made from Emporium's own address [6](#0-5) . This can target any token Emporium holds (direct `transfer`) or any endpoint (e.g. a LiFi router) that Emporium has previously approved, using attacker-supplied calldata that consumes that standing approval to move funds.

Upstream, `Hinkal.transact` never blocks this: `dimensionsCheck` only requires `erc20TokenAddresses.length == dimensions.tokenNumber` (attacker just sets `tokenNumber = 0`) [7](#0-6) , and `rootHashExists` only requires a valid *historic* root/index pair, which any public root satisfies since no nullifiers or UTXOs are involved [8](#0-7) . With empty `erc20TokenAddresses`, all balance/slippage checks and nullifier/commitment insertions in `Hinkal.transact` degenerate to no-ops [9](#0-8) . The attacker's exact call: craft `CircomData` with `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `dimensions.tokenNumber = 0`, `externalActionMetadata = abi.encode(EmporiumStack{signerAddress:0, ops:[{endpoint: token/router, callData: attacker-crafted, value: 0}], ...})`, and a trivially generated proof for `message = Poseidon(messageSeed)`. Submit via `Hinkal.transact`.

### Impact Explanation
Any funds resting in the Emporium contract's balance (in-flight swap proceeds, dust from partial fills, ETH sent for stateful ops, or ERC20 allowances Emporium has standing with routers such as LiFi) can be drained by an unprivileged attacker directly to an address of their choosing, with zero UTXOs spent and zero accounting. This is repeatable for every fresh `emporiumMessage` (only constrained to be unused) and requires no capital or valid deposit from the attacker. This matches Critical: direct theft of shielded or in-flight user funds.

### Likelihood Explanation
Preconditions: Emporium contract must hold a nonzero balance or standing token approval at call time (plausible whenever swaps/routes are mid-flight or leave residual approvals/dust). Attacker cost is a single transaction with a trivially-computable Min-circuit proof (no real secret/UTXO knowledge required) and any historic Merkle root. No privileged role, relay, or victim cooperation needed. Feasibility is high and the attack is fully repeatable.

### Recommendation
Do not allow `signerAddress == address(0)` (or, more generally, unauthenticated stacks) to execute stateless calls to arbitrary attacker-chosen `endpoint`/`callData`. At minimum: require signature verification regardless of `signerAddress`, restrict endpoints to a Emporium allowlist for the unauthenticated path, and/or forbid entering `runAction` via the min-proof path unless `erc20TokenAddresses.length > 0` so balance accounting is always enforced, or independently track/require balance deltas to be zero when the min-proof/empty-token path is used.

### Proof of Concept
Foundry test plan:
1. Deploy Hinkal stack, fund `EmporiumUpgradeable` with test ERC20 tokens (simulating in-flight/leftover balance) and/or grant it an approval to a mock router.
2. As an unprivileged EOA (no deposits, no owned UTXOs), build `CircomData` with `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `dimensions.tokenNumber = 0`, `emporiumMessage = Poseidon(messageSeed)`, and `externalActionMetadata` encoding an `EmporiumStack{signerAddress: address(0), ops: [{endpoint: token, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, emporiumBalance), value: 0}], maxFee: 0, deadline: type(uint256).max}`.
3. Generate the trivial `MainEVMCircuitMin` proof locally (only `messageSeed` as private witness) and use any existing on-chain Merkle root for `rootHashHinkal`/`rootHashHinkalIndex`.
4. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from the attacker EOA.
5. Assert: `token.balanceOf(Emporium)` before == `emporiumBalance`, after == 0; `token.balanceOf(attacker)` increases by `emporiumBalance`; no nullifiers inserted, no commitments inserted, transaction succeeds — demonstrating assets moved with zero entries in `balancesBefore`/`balancesAfter` accounting.
