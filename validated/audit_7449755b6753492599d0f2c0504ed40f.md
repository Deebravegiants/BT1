### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers — none of which are included in the signed content. This breaks the intended identity binding `HMAC-verified bytes == bytes acted on`, letting anyone who possesses one valid `(raw_body, hmac)` pair (trivially obtainable by installing the public app on their own shop and capturing a legitimate webhook) replay it against the same endpoint with the `x-shopify-shop-domain` header swapped for a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read directly from headers and are never mixed into the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the received `hmac`, so it only proves the *body* bytes are authentic — it says nothing about which shop the body belongs to: [3](#0-2) 

`Registry.process` then does exactly that: it validates the HMAC and, immediately after, builds `WebhookMetadata` using `request.shop` (the unauthenticated header) and hands it to the app's handler: [4](#0-3) 

The identity binding that should hold is:
`shop attributed to the event == shop that the HMAC-covered bytes actually originated from`

but the code only enforces:
`HMAC(secret, raw_body) == received_hmac` (says nothing about `shop`)

Because Shopify apps share a single `api_secret_key` across every merchant installation, a valid `(raw_body, hmac)` pair generated for one shop's webhook is equally "valid" when replayed with a different shop's domain in the header — `HmacValidator` will accept it since it never inspects `shop`.

### Impact Explanation
This is a cross-tenant identity-binding break in the gem's own webhook-authentication code path: `Registry.process` (the function apps are documented to call to dispatch verified webhooks) passes the caller's `WebhookHandler#handle` a `WebhookMetadata.shop` value that was never bound to the HMAC-authenticated payload. Any consuming app that uses `data.shop` from a processed webhook (e.g., to select the tenant record to look up/store data for, per the gem's own webhook usage pattern) can be made to attribute a payload to the wrong merchant. An attacker only needs to be an ordinary, unprivileged installer of the target's public app (no access token, no `api_secret_key`, no TLS interception) — install the app on their own store, capture one legitimate webhook `(raw_body, hmac)`, and replay it at the app's webhook endpoint with the `x-shopify-shop-domain`/`shopify-shop-domain` header rewritten to a victim's `*.myshopify.com` domain. This falls under cross-tenant access.

### Likelihood Explanation
Moderate-to-high likelihood: the attacker only needs to install a target app on their own shop (which is generally open to any Shopify merchant/developer), capture a single legitimate webhook delivery, and replay it with one header value changed. No secrets, tokens, or privileged access are required, and the victim's shop domain is guessable/public.

### Recommendation
Bind the header-derived fields (`shop`, `topic`, `webhook_id`, `api_version`) into the value that is HMAC-verified — e.g., include them (canonicalized) in `to_signable_string`, or otherwise cryptographically tie the `shop` claim to the signed body — so that `Utils::HmacValidator.validate` fails if any of these headers are altered relative to what Shopify actually sent for that specific body.

### Proof of Concept
1. Attacker installs the target public app on their own shop `attacker.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Shopify delivers a legitimate webhook to the app's endpoint with body `raw_body` and header `x-shopify-hmac-sha256: hmac`, `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the exact same request to the same endpoint but sets `x-shopify-shop-domain: victim.myshopify.com` (and, if desired, a different `x-shopify-webhook-id`).
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` still succeeds because it only checks `raw_body` against `hmac`, which are unchanged.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)` and invokes the app's handler as if the event genuinely originated from `victim.myshopify.com`.
