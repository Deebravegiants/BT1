Based on the investigation, there is a valid analog to the reported blocklist-order bug in this repo: an incomplete-matching bug where a withdrawal's on-chain outcome is attributed to the wrong batch entry when multiple withdrawals of the same token exist in a single NEAR transaction.

### Title
Batch withdrawal status/hash misattributed when multiple withdrawals share the same asset - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`, `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`)

### Summary
`PoaBridge.describeWithdrawal` and `waitForWithdrawalCompletion` locate a specific withdrawal in the POA bridge's unsorted status-list response using only the `assetId`, never validating the match against the withdrawal's `index`, `amount`, or `destinationAddress`. When a single intent contains two or more withdrawals of the same token (a supported case per the SDK's batch withdrawal API), the first list entry matching that `assetId` is returned regardless of which entry actually corresponds to the caller's specific withdrawal.

This is structurally the same class of bug as the `committee::execute_blocklist` report: an equality check (matching a specific list entry to a specific expected entity) is performed with an incomplete/ambiguous key, so when list ordering or contents don't align 1:1 by that key, the wrong entry is matched and returned as "the" result — here, the wrong `transfer_tx_hash`/status is returned for a given withdrawal index/destination in a batch containing repeated assets.

### Impact Explanation
If an intent contains two withdrawals of the same `assetId` to different destination addresses/amounts (the SDK's own design doc for granular batch-withdrawal tracking assumes this is a normal, supported scenario — see `docs/design/rfc-batch-withdrawal-granular-control.md`), `describeWithdrawal`/`waitForWithdrawalCompletion` can report the `COMPLETED` status and `transfer_tx_hash` belonging to a *different* withdrawal entry in the batch, since matching disregards `index`, `amount`, and `destinationAddress`. An integrator relying on this to know when a specific withdrawal (e.g., index 1) has settled could see it marked "completed" with a hash that actually belongs to a different withdrawal (e.g., index 0), or vice versa — a status/hash misreport. Per the impact taxonomy, this falls under High: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This requires no malicious actor — it triggers whenever a normal user submits a batch intent with two+ withdrawals of the same underlying token to different destinations/amounts, and the POA bridge API returns its withdrawal list in an order that doesn't match the caller's expected index (the code comment itself states "Response list is unsorted"). This is a naturally occurring, unprivileged condition, not one requiring an admin/relayer to misbehave.

### Recommendation
Extend `WithdrawalCriteria`/`findMatchingWithdrawal` (in both `poa-bridge.ts` and `waitForWithdrawalCompletion.ts`) to disambiguate by additional fields beyond `assetId` — e.g., `destinationAddress`, `amount`, or a stable per-withdrawal identifier if the POA API exposes one — and only fall back to plain `assetId` matching when there is a single withdrawal of that asset in the batch. If no additional identifying data is available from the API, the SDK should refuse to report a definitive status for ambiguous batches (same asset repeated) rather than returning a possibly-mismatched entry.

### Proof of Concept
1. User submits a single NEAR intent with two withdrawals of `nep141:usdc.omft.near`: withdrawal A (index 0) to `destA` for `100`, withdrawal B (index 1) to `destB` for `50`.
2. Caller invokes `describeWithdrawal` (or `waitForWithdrawalCompletion`) for index 1 / `destB` withdrawal.
3. The POA bridge API returns both withdrawal statuses in an order where withdrawal A's record appears first with `status: COMPLETED` and `transfer_tx_hash: "txA"`, while withdrawal B is actually still pending.
4. `findMatchingWithdrawal` matches on `assetId` alone and returns withdrawal A's record.
5. The caller for withdrawal B (index 1, `destB`) is told status `completed` with `txHash: "txA"` — a transaction that actually paid `destA`, not `destB` — leading a downstream integrator to credit/settle withdrawal B based on the wrong on-chain transaction.

		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(

			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

				txHash: withdrawal.data.transfer_tx_hash,

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
