## Title
`ExchangeToken` builds the OAuth token-exchange request host from the unvalidated JWT `dest` claim, sending `client_secret` to it without the `ShopValidator` domain check applied elsewhere - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` takes the shop used to build the token-exchange request host directly from `JwtPayload#shop` (the `dest` claim), and never runs it through `Utils::ShopValidator.sanitize!`, unlike the sibling `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token` flows, which both call `Utils::ShopValidator.sanitize!(shop)` before constructing the session used to build the request host.

### Finding Description
`exchange_token` decodes the caller-supplied `session_token` via `ShopifyAPI::Auth::JwtPayload.new(session_token)` and takes `dest_shop = jwt_payload.shop`, which is nothing more than `@dest.gsub("https://", "")` [1](#0-0)  with no suffix/domain check. `token_exchange.rb` then builds `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)` and passes it straight to `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")`, together with a body containing `client_secret: ShopifyAPI::Context.api_secret_key` [2](#0-1) . `HttpClient#initialize` uses `session.shop` verbatim to build the request host: `@base_uri = "https://#{api_host || session.shop}"` [3](#0-2) , so whatever string is in `dest` becomes the destination that receives the POST containing the app's `client_secret`.

By contrast, the two other credential-issuing flows explicitly sanitize the shop against `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before it is used to build the request host:
- `ClientCredentials.client_credentials`: `validated_shop = Utils::ShopValidator.sanitize!(shop)` [4](#0-3) 
- `RefreshToken.refresh_access_token`: `validated_shop = Utils::ShopValidator.sanitize!(shop)` [5](#0-4) 

`token_exchange.rb` has no equivalent call to `Utils::ShopValidator` anywhere in the method [6](#0-5) .

The equality that should hold is: *host that receives `client_secret` == a validated, trusted `*.myshopify.com`/`myshopify.io`/etc. domain*, as enforced in the two sibling flows via `ShopValidator.sanitize!`. In `exchange_token` this equality is broken: the host is instead *whatever string comes out of the JWT `dest` claim, unchecked*.

### Impact Explanation
Whether this is actually exploitable hinges entirely on whether the `dest` claim can ever contain attacker-influenced content while still passing JWT signature verification against `Context.api_secret_key` (`JwtPayload#initialize` verifies `aud == Context.api_key` but performs no check that `dest`/`iss` are restricted to Shopify-controlled domains) [7](#0-6) . Session tokens are minted and signed by Shopify's own infrastructure with the shared `api_secret_key`; I could not verify from this repository alone whether any legitimate Shopify-issued token type (e.g., checkout/POS extension tokens, custom-domain storefronts) can carry a `dest`/`iss` value outside the standard `*.myshopify.com` family while still validating. If such a token type exists, an unprivileged holder of it could redirect the OAuth token-exchange POST - carrying the app's `client_secret` in the body - to an attacker-influenced host (SSRF with credential exfiltration, Critical impact category). If no such token type exists, this is a defense-in-depth gap rather than an independently exploitable bug, since forging an arbitrary `dest` still requires the `api_secret_key`.

### Likelihood Explanation
Low-to-moderate confidence. The asymmetry with `client_credentials.rb` and `refresh_token.rb` (both of which explicitly validate the shop before it's used to build the credential-bearing request host) strongly suggests the sanitization in `token_exchange.rb` was intentionally omitted based on an assumption that `dest` is always trustworthy because it's JWT-signed — but that assumption is exactly the missing binding: signature validity proves the token was issued by Shopify, not that the domain inside it is restricted to Shopify's own hosts. I was not able to fully confirm within this gem's code alone whether any Shopify-issued, `Context.api_key`-audienced token can carry a non-`myshopify` `dest` value; this would need to be confirmed against Shopify's token-issuance behavior, which is outside the code of this gem.

### Recommendation
Apply `Utils::ShopValidator.sanitize!(dest_shop, myshopify_domain: ...)` to the shop derived from `jwt_payload.shop` in `TokenExchange.exchange_token` before constructing `shop_session`/`HttpClient`, mirroring the treatment already applied in `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, so that the host receiving `client_secret` is always bound to the same trusted-domain allowlist regardless of entry point.

### Proof of Concept
Could not be constructed with certainty: exploitation depends on obtaining a session token whose `dest` claim is a non-Shopify-controlled domain yet still validates against `Context.api_secret_key`/`Context.api_key`, which requires knowledge specific to Shopify's token-issuance rules that is outside this gem's codebase and outside what I could verify here.
