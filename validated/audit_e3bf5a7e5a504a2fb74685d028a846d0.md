### Title
Silent U128→u64 truncation in `swap_token_amount_base_out` fee math lets an attacker drain pool funds by paying a truncated (near-zero) `amount_in` for a large `amount_out` - (File: `program/src/processor.rs`, `program/src/math.rs`)

### Summary
`process_swap_base_out` computes the required `amount_in` for a user-chosen `amount_out` using `Calculator::swap_token_amount_base_out`, then converts the U128 result to u64 with the raw, non-checked `.as_u64()` cast instead of the codebase's own safe `Calculator::to_u64()` (which uses `try_into` and errors on overflow). When the swap denominator is driven to a minimal value by the attacker's chosen `amount_out`, the computed `amount_in` (and its subsequent fee-adjusted value) can exceed `u64::MAX` while still fitting in U128. The unchecked `.as_u64()` cast then silently truncates this value to a small, essentially attacker-controllable number. That truncated value is what gets transferred *from* the user, while the full, large `amount_out` is still transferred *to* the user, draining the pool.

### Finding Description
In `program/src/math.rs`, two casting helpers exist: [1](#0-0) 
`to_u64` uses `try_into`, which safely errors on overflow. But the swap math functions instead use the raw `.as_u64()` accessor of the `U128`/uint-crate type, which truncates to the low 64 bits without any error: [2](#0-1) 

In `process_swap_base_out` (`SwapBaseOut` instruction, reachable by any unprivileged swapper with a single transaction): [3](#0-2) 

`swap.amount_out` is fully attacker-controlled instruction data. The only prior validation is that `amount_out < total_pc_without_take_pnl` (checked *after* the amount_in computation, at line 2593): [4](#0-3) 

By choosing `amount_out = total_pc_without_take_pnl - 1` (Coin2PC direction), the internal `denominator = total_pc_without_take_pnl.checked_sub(amount_out)` in `swap_token_amount_base_out` becomes `1`: [5](#0-4) 

This makes `amount_in = total_coin_without_take_pnl * amount_out / 1`, a product of two u64 pool balances that can land well above `u64::MAX` while still fitting inside U128 (max u64 * max u64 ≈ 2^128). That value is then multiplied by `swap_fee_denominator` and divided by `(swap_fee_denominator - swap_fee_numerator)` — still comfortably inside U128 range for realistic pool sizes — and finally truncated with `.as_u64()` at line 2570, discarding the high bits and yielding a small, effectively attacker-steerable `swap_in_after_add_fee`.

That truncated (tiny) value is subsequently used for:
- the `user_source.amount < swap_in_after_add_fee` solvency check (line 2581),
- the slippage check against attacker-supplied `swap.max_amount_in` (line 2584),
- the actual token amount transferred **from** the user into the vault (line 2602/`swap_in_after_add_fee`),

while the full, near-total-vault-balance `swap.amount_out` is transferred **out** to the user (line 2612). The attacker thus pays a negligible truncated amount and receives almost the entire pool's `pc` (or `coin`) reserve.

### Impact Explanation
This is a direct theft/drain of pool (LP) funds reachable from a single transaction with attacker-chosen instruction data (`amount_out`, `max_amount_in`) and no privileged accounts required — only the standard `SwapBaseOut` accounts (source/destination token accounts owned by the attacker, and the pool's own vaults/state). Because the truncated `amount_in` can be made arbitrarily small by choosing `amount_out` to make the fee-math denominator near-1, the attacker can extract nearly the full pool reserve of one side for almost nothing, causing insolvent pool accounting and permanent loss of LP funds. This exceeds the severity of the referenced report (which describes locked funds); here the analogous truncation bug enables outright fund theft.

### Likelihood Explanation
High likelihood: the attacker only needs to submit one `SwapBaseOut` transaction with a crafted `amount_out` value close to (but below) the pool's total un-PNL'd balance on one side, and a `max_amount_in` set to accept the truncated result. No special permissions, timing, or race conditions are required — this is a deterministic, single-transaction exploit against normal AMM pool state.

### Recommendation
Replace the unchecked `.as_u64()` truncating casts in `swap_token_amount_base_out` (and any other place converting large U128 fee/amount computations back to u64, e.g. lines 2570, 2192 in `processor.rs`) with the existing safe `Calculator::to_u64()` helper, which uses `try_into` and returns an error on overflow instead of silently truncating. Additionally, validate `amount_out` against a sane bound before computing `amount_in`, and ensure the fee/amount pipeline rejects (rather than truncates) any value that would not round-trip through u64.

### Proof of Concept
1. Pool state: `total_pc_without_take_pnl = P`, `total_coin_without_take_pnl = C` (real u64 vault balances).
2. Attacker submits `SwapBaseOut` with `swap.amount_out = P - 1` (Coin2PC direction) and `swap.max_amount_in` set to a value large enough to pass slippage after truncation.
3. Inside `swap_token_amount_base_out`: `denominator = P - (P-1) = 1`; `amount_in = C * (P-1) / 1 ≈ C*P`, which for realistic pool sizes exceeds `u64::MAX` but fits in U128.
4. `swap_in_after_add_fee = (amount_in * swap_fee_denominator / (swap_fee_denominator - swap_fee_numerator)).as_u64()` truncates this huge U128 value to a small u64 (`program/src/processor.rs:2559-2570`).
5. Checks at lines 2581/2584 pass because `swap_in_after_add_fee` is small.
6. `Invokers::token_transfer` moves only the tiny truncated amount from the attacker into the vault (line 2597-2603), while `Invokers::token_transfer_with_authority` sends `swap.amount_out ≈ P` (almost the entire pc reserve) to the attacker (line 2605-2613). [4](#0-3) [5](#0-4)

    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)

                // => amount_in = coin * pc / (coin - amount_out) - pc
                // => amount_in = (coin * pc - pc * coin + pc * amount_out) / (coin - amount_out)
                // => amount_in = (pc * amount_out) / (coin - amount_out)
                let denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_pc_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
        }
        return amount_in;
    }
