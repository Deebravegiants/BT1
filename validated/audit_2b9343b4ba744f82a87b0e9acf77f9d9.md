### Title
Webhook HMAC signature does not bind the `shop-domain` header, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop` is read directly from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` header. `Utils::HmacValidator.validate` only checks the HMAC over this signable string, so the `shop` value that `Webhooks::Registry.process` hands to the app's handler is never covered by the signature. Since a single `client_secret` is shared across every shop installed on an app, any merchant who can trigger a legitimately-signed webhook for their own store can replay that same body/HMAC pair to the app's webhook endpoint with a forged `shop-domain` header, causing the receiving application to process attacker-controlled data under a victim shop's identity.

### Finding Description
The equality that should hold for a webhook to be safely attributed to a tenant is:

`shop value trusted by the handler (request.shop) == shop value the HMAC signature actually authenticates`

In this gem that equality does not hold: [1](#0-0) 

`shop` is parsed straight from the `shopify-shop-domain` header, but `to_signable_string`, which is the only material fed into HMAC verification, returns solely `@raw_body`. [2](#0-1) 

`HmacValidator.validate` calls `validate_signature`, which computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the received `hmac`. Because `to_signable_string` never includes the shop domain, the HMAC check is blind to which shop header value is presented. [3](#0-2) 

`Registry.process` validates the HMAC, then immediately builds `WebhookMetadata` using `request.shop`, `request.parsed_body`, etc., and dispatches it to the host application's handler — the handler receives an *authenticated body* paired with an *unauthenticated shop claim*.

**Attack path:** The `client_secret`/`api_secret_key` used to sign webhooks is per-app, not per-shop. Any user who installs the app on their own development/test store can generate a real webhook (e.g. `orders/create`) with a body of their choosing and a correctly computed HMAC signed by the app's shared secret. Because the HMAC never covers the shop header, the attacker can intercept or resend that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (body and secret are unchanged), and `Registry.process` forwards `shop: <victim shop>` to the handler together with the attacker-chosen body content.

### Impact Explanation
This breaks the tenant isolation boundary the gem is expected to enforce for webhook delivery: an unprivileged, unauthenticated-with-respect-to-the-victim-shop actor can make the host application believe attacker-controlled webhook data originated from a different merchant's shop. Depending on how the host app keys stored state off `WebhookMetadata#shop` (order sync, inventory updates, uninstall/GDPR flows, etc.), this enables cross-tenant data confusion/corruption, which falls under the Critical "cross-tenant access" category.

### Likelihood Explanation
Likelihood is high for any app that exposes a public webhook endpoint (the standard integration pattern) and where an attacker can install the app on their own store — which is the normal, permissionless install flow for public Shopify apps. No access token, leaked credential, or privileged account is required; the attacker only needs a store where they can trigger any webhook topic supported by the app.

### Recommendation
Bind the shop identity into the material that is cryptographically verified, or otherwise cross-check `request.shop` against a value that is authenticated independently (e.g., verifying via the Admin API that the webhook actually originates from that shop, or including the shop domain in the signable string if Shopify's webhook signing were changed to support it). At minimum, document that `request.shop` is not authenticated by `HmacValidator.validate` and require host applications to treat it as untrusted input rather than a verified tenant identifier, or reject webhooks where the `shop` header does not match an expected/allow-listed value before invoking the handler.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook event (e.g. updates an order), receiving a POST with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker replays the exact same POST to the app's webhook endpoint, keeping `B` and `H` unchanged but setting `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged shop header; `HmacValidator.validate` computes `HMAC-SHA256(client_secret, B)` (same `B`) and it matches `H`, so validation passes: [4](#0-3) 
4. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)` and invokes the host handler as if the event came from `victim.myshopify.com`: [5](#0-4)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
