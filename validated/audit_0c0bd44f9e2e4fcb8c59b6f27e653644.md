### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC over the raw request body only, but then dispatches the handler using the `shop` value taken from an **unsigned HTTP header** (`x-shopify-shop-domain`). Because the app's single `client_secret` signs webhooks for every shop that installs the app, any unprivileged user who installs the app on their own store can capture a validly-signed `(raw_body, hmac)` pair and replay it with a forged `shop-domain` header claiming to be a different (victim) shop, causing the app to process an "authenticated" webhook as belonging to a tenant it does not actually come from.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all parsed from HTTP headers that are never included in the signed material: [2](#0-1) 

`Registry.process` validates the HMAC (which only binds the body bytes) and then immediately uses the unauthenticated `request.shop` to build the `WebhookMetadata` passed to the app's own handler: [3](#0-2) 

`WebhookMetadata.shop` is documented and intended to be trusted by the handler as "the shop domain of the webhook" for tenant-scoped processing: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:
`bytes verified by HMAC (== raw_body)` **should equal** `bytes the app treats as authenticated tenant identity (shop header used for dispatch)`.

That equality does not hold — the HMAC only proves "this body was produced with the app's `client_secret`" but says nothing about which shop the request is for. Since the same `client_secret` is shared across all shops that install a given app, an attacker who installs the app on their own (unprivileged) test/dev store receives genuine Shopify-signed webhooks for their own shop. They can capture the `(raw_body, hmac)` pair from one of these legitimate webhooks and resend it to the app's webhook endpoint with the `x-shopify-shop-domain` (and `x-shopify-topic`, `x-shopify-webhook-id`) headers rewritten to name a victim shop. `Utils::HmacValidator.validate` will still pass because it only recomputes the HMAC over the (unchanged) body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop with attacker-controlled body content.

### Impact Explanation
This is a cross-tenant identity confusion: the app processes a request as belonging to a shop the attacker does not own and has no credentials for, using only a legitimately-obtained signature from their own tenant. Depending on how the app's webhook handler uses `data.shop` (e.g., looking up the merchant's session/store record, updating merchant-scoped state, triggering merchant-scoped side effects), this can let one merchant inject fabricated "webhook events" attributed to another merchant, or at minimum corrupt per-shop data/state keyed by the trusted `shop` field. This matches the Critical "cross-tenant access" impact category, since the trust boundary (per-shop tenant isolation via webhook shop identity) is broken using only a signature obtained through the attacker's own legitimate installation — no leaked credentials, access tokens, or `client_secret` knowledge are required.

### Likelihood Explanation
Likelihood is moderate-to-high for apps that use the shop value from `WebhookMetadata` for tenant-scoped logic (which is the documented, expected usage pattern shown in `docs/usage/webhooks.md`). The only prerequisite is that the attacker can install the target app on any shop (a normal, unprivileged action for any Shopify merchant/developer, including via free/dev stores), observe one webhook delivery for their own shop, and replay it against the app's public webhook endpoint with modified headers. No secret material, tokens, or elevated access is needed.

### Recommendation
Bind the shop (and, ideally, topic/webhook id) identity into the authenticated material, or otherwise verify it independently before trusting it:
- Include the `shop` (and other identity-bearing headers) in the string that is HMAC-verified, not just the raw body, OR
- After validating the HMAC, cross-check the `shop` header against an expected/registered value (e.g., verify that a session/subscription exists for that shop and that this specific `webhook_id` was actually registered for it) before dispatching to the handler, OR
- Document explicitly and loudly that `WebhookMetadata#shop` is not cryptographically bound to the signed payload and must not be trusted for tenant-scoped authorization without additional verification by the consuming app.

### Proof of Concept
1. Attacker registers the target app on `attacker-shop.myshopify.com` (a normal, unprivileged install).
2. Attacker registers a webhook topic (e.g. `orders/create`) so Shopify sends real webhook deliveries to the app's endpoint, signed with the app's shared `client_secret`:
   - Headers include `x-shopify-hmac-sha256: <HMAC of raw_body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
3. Attacker intercepts this legitimate delivery (e.g., via a proxy they control, or by pointing the webhook to their own endpoint first) and records the exact `raw_body` and `x-shopify-hmac-sha256` value.
4. Attacker sends a new POST to the app's public webhook endpoint with the **same** `raw_body` and `x-shopify-hmac-sha256`, but with `x-shopify-shop-domain` rewritten to `victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only and it matches, so `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) proceeds and calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's own order data>, ...)`.
6. The app's handler processes attacker-supplied data under the identity of `victim-shop.myshopify.com`, violating tenant isolation.

Note: I could not fully verify how downstream consumers (e.g., the `shopify_app` reference implementation) further validate `data.shop` against registered webhook subscriptions, since that logic lives outside this gem; the vulnerability described here is specific to this gem's failure to bind `shop` into the authenticated payload before exposing it as trusted metadata to handlers.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
