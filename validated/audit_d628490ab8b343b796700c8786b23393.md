## Finding: Webhook shop/topic identity not covered by HMAC signature

The bug-class hint ("result not checked / value not bound") maps cleanly onto an identity-binding break in this gem's webhook processing: the HMAC signature is computed only over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values that the application uses to attribute the payload to a tenant are taken from unauthenticated HTTP headers.

### Title
Webhook shop/topic identity spoofing via HMAC that only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC of the raw body, then hands the caller's `topic` and `shop` header values — which are never included in the signed content — to the app's handler as trusted identity fields.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers and are not part of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC (over the body only) and then immediately trusts `request.topic` and `request.shop` to select the handler and build the metadata object passed to application code: [3](#0-2) 

Because the HMAC secret (`Context.api_secret_key`) is a single, app-wide client secret shared across every installed shop, any tenant that has legitimately received one authentic webhook (any topic, any shop, any body) possesses a valid `raw_body` + `hmac` pair signed with that same app secret. Since the header fields `shop`, `topic`, `webhook_id`, and `api_version` are never bound into the signature, an attacker who controls one such legitimate pair can resubmit the same body/HMAC to the app's webhook endpoint while freely rewriting the `x-shopify-shop-domain` and `x-shopify-topic` headers to any value. `HmacValidator.validate` will still succeed because it only checks `verifiable_query.to_signable_string` (the body) against the secret: [4](#0-3) 

The binding that should hold is:
`HMAC-verified(raw_body) == identity(shop, topic) used by the handler`
but the gem instead verifies `HMAC-verified(raw_body)` and separately trusts `identity(shop, topic)` from unauthenticated headers — an equality that is never checked.

### Impact Explanation
This breaks the shop/tenant identity binding for webhook processing. A merchant/tenant who has installed the app (and can therefore trigger at least one legitimate Shopify webhook to be delivered) can capture a valid `(raw_body, hmac)` pair and replay it against the app's webhook controller with a forged `shop-domain` header naming a different shop, and/or a forged `topic` header to route the body into a different handler than Shopify actually generated it for. Any application built on this gem's documented `Registry.process` API (as shown in the gem's own webhook docs) will process this as authentic data for the impersonated shop, since the gem asserts that HMAC validation is sufficient proof of authenticity for `request.shop`/`request.topic`. This enables cross-tenant data injection/confusion in the host application without needing the app's `client_secret`, `access_token`, or any other credential — only participation as one of the app's own installed shops.

### Likelihood Explanation
Any regular merchant who installs the app qualifies as an "unprivileged" actor relative to other tenants, and receiving at least one real webhook delivery from Shopify is the normal, expected behavior of any installed app — this is not a privileged or hard-to-reach precondition. Replaying an HTTP POST with modified headers requires no special access, TLS interception, or social engineering.

### Recommendation
Include the identity-relevant fields (`shop`, `topic`, and ideally `webhook_id`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the body signature. At minimum, `Registry.process` should independently verify that `request.shop` corresponds to a shop that is actually expected/authorized for the given payload (e.g., by requiring the consuming application to supply the expected shop and comparing it) rather than treating header-derived `shop`/`topic` as implicitly authenticated once the raw-body HMAC passes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering Shopify to deliver a legitimate webhook (e.g., `orders/create`) to the app's endpoint with a valid `x-shopify-hmac-sha256` header computed over the raw body using the app's shared `api_secret_key`.
2. Attacker captures the raw body and its valid HMAC value.
3. Attacker resends an HTTP POST to the same webhook endpoint with the identical raw body and HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: customers/create` (or any registered topic).
4. `HmacValidator.validate` succeeds (it only checks the body/HMAC pair) at `lib/shopify_api/utils/hmac_validator.rb:13-22`, and `Registry.process` invokes the handler with `WebhookMetadata` carrying the forged `shop`/`topic` values at `lib/shopify_api/webhooks/registry.rb:198-199`, causing the host application to process attacker-controlled data as if it originated from `victim-shop.myshopify.com`.
