## Title
Mutable `_underlying` token address in `WrappedHyperFungibleToken.configure()` causes wrong-asset payouts and permanent fund freezing for in-flight transfers - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.configure()` locks the `_host` address after its first assignment but allows `_underlying` (the wrapped ERC20 being bridged) to be changed on every call, with no restriction and no accounting for tokens already locked under the previous underlying token. `send()`, `onAccept()`, and `onPostRequestTimeout()` all read the *current* `_underlying` at call time rather than the token that was actually locked when a given transfer was initiated. This is the exact bug class described in the Connext `setWrapper`/`canonicalToAdopted` report: a legitimate reconfiguration of a wrapper/underlying mapping leaves stale references pointing at the wrong asset for pre-existing in-flight operations, breaking correctness for anyone with a pending cross-chain transfer.

### Finding Description
`configure()` unconditionally overwrites `_underlying`: [1](#0-0) 

Only `_host` has "set-once" protection; `_underlying`, `_dispatcher`, and `_isWeth` can be freely reconfigured by the owner at any time, as documented: [2](#0-1) 

Meanwhile, `send()` locks whatever token is currently configured as `_underlying`: [3](#0-2) 

But `onAccept()` (destination-side delivery) and `onPostRequestTimeout()` (source-side refund on failure) both resolve the asset to move using the *current* `_underlying` value, not the token that was actually escrowed for that specific request: [4](#0-3) [5](#0-4) 

There is no per-request record of which token was locked/expected — no `mapping(bytes32 commitment => address token)` or similar — so once the owner reconfigures `_underlying` (e.g., to fix a misconfigured deployment, migrate to a new token version, or switch WETH implementations), any request that is still in flight (dispatched before the change, but delivered/timed-out after it) will be settled against the new token instead of the one that was actually locked. The identical unrestricted-overwrite pattern and identical settlement-time resolution exist in the upgradeable variant: [6](#0-5) [7](#0-6) [8](#0-7) 

This directly mirrors the Connext finding: `setupAsset` records `canonicalToAdopted` pointing at the wrapper deployed at setup time, but `setWrapper` can later swap the wrapper contract without updating that mapping, leaving stale references that settle against the wrong token for pre-existing assets.

### Impact Explanation
Two concrete, fund-affecting outcomes follow directly from the stale `_underlying` reference:

1. **Permanent freezing of the original locked asset.** A user calls `send()` while `_underlying = A`, locking `amount` of token A in the contract via `safeTransferFrom`. If that transfer later times out (any relayer submits the timeout proof to `onPostRequestTimeout`, permissionlessly callable via the host) after the owner has reconfigured `_underlying = B`, the refund path transfers token **B**, not token A, to the refundee. The user's original token A remains stuck in the contract with no function referencing it any longer — permanent loss/freezing of funds for that user.
2. **Unbacked payout / theft of the new underlying token.** The refund/delivery in this same scenario pays out `message.amount` of token B to the refundee/beneficiary even though no corresponding deposit of token B was ever made for that request. If the contract holds any balance of token B (e.g., deposited by other users through legitimate `send()` calls made after reconfiguration), that balance can be drained to settle requests that were never backed by token B — an unbacked withdrawal that can be triggered by any relayer submitting a valid (but now-mismatched) timeout or delivery proof for a pre-existing in-flight request.

Both outcomes satisfy the required impact bar: permanent freezing of funds and unbacked/forged-value settlement of an unrelated asset.

### Likelihood Explanation
The trigger requires only an owner-level `configure()` call — which is a normal, expected maintenance operation (fixing a wrong deployment address, migrating to a new token contract, changing WETH wiring), not malicious governance intent, exactly as in the original Connext scenario where `setWrapper` is a routine, non-malicious admin action. Any in-flight request that straddles the reconfiguration (dispatched before, settled after) is affected, and settlement is triggered by an ordinary unprivileged relayer submitting the timeout or delivery proof through the ISMP host — no special privileges needed to realize the impact once the stale state exists. Given that timeouts commonly take on the order of the configured `timeout` window plus finalization delays, the window for an admin update to race an in-flight request is realistic in normal operational cadence.

### Recommendation
Snapshot the token address used for a given transfer at `send()` time (e.g., store `token` per commitment/nonce in a mapping) and use that snapshotted value in `onAccept()` and `onPostRequestTimeout()` instead of re-reading the mutable `_underlying` storage variable. Alternatively, make `_underlying` set-once like `_host`, and require deploying a new wrapper contract (with its own isolated balance) for any token migration, following the same immutability guarantee already applied to `_host`.

### Proof of Concept
1. Owner deploys `WrappedHyperFungibleToken` and calls `configure()` with `underlying = TokenA`.
2. Alice calls `send()` with `amount = 100`, locking 100 TokenA in the contract (`sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol:266-273`).
3. Before the request is delivered/times out, owner calls `configure()` again, this time with `underlying = TokenB` (a routine reconfiguration, no host address change since host is set-once).
4. Bob calls `send()` with `amount = 50`, locking 50 TokenB in the contract.
5. Alice's original request eventually times out. Any relayer submits the timeout proof; `onPostRequestTimeout` executes `IERC20(_underlying).safeTransfer(refundee, message.amount)` where `_underlying` now resolves to TokenB (`sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol:344-365`). Alice receives 100 TokenB she never deposited, draining Bob's locked TokenB, while her original 100 TokenA remains permanently stuck in the contract.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);

            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
