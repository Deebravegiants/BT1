Raydium's constant-product AMM does not have a direct analog to `UniswapImplementation.beforeSwap()`'s "auto-swap pending fees at spot price," since Raydium's swap math (`swap_token_amount_base_in`/`_out`) always operates on the pool's actual current reserves, which is standard/expected CPMM behavior with no separate TWAP-vs-spot distinction to exploit [1](#0-0) . However, there is a structurally analogous bug class in the PNL-skimming logic, `Processor::calc_take_pnl`, which is reachable from the unprivileged `Deposit` and `Withdraw` instructions.

### Title
Manipulable spot-price PNL skimming in `Processor::calc_take_pnl` permanently misallocates LP pool funds - (File: `program/src/processor.rs`)

### Summary
`calc_take_pnl` decides how much of the pool's reserves are permanently diverted from the LP-shared pool into `need_take_pnl_pc`/`need_take_pnl_coin` (claimable only by the privileged `pnl_owner`) [2](#0-1) . This split is computed using the pool's *current, instantaneous* reserves (`x1`, `y1`), not a TWAP, exactly the bug class described in the external report where an internal accounting operation is priced off manipulable spot state rather than a time-weighted value.

### Finding Description
`calc_take_pnl` computes `x2_power = last_x * last_y * current_x / current_y` via `Calculator::calc_x_power`, then `x2 = sqrt(x2_power)`, `y2 = x2 * current_y / current_x` [3](#0-2) . This re-expresses the last checkpointed invariant (`target.calc_pnl_x * target.calc_pnl_y`) at the *current* price ratio `current_x/current_y`, then treats `diff_x = current_x - x2`, `diff_y = current_y - y2` as the "fee growth" to skim into `need_take_pnl_*` [4](#0-3) .

Because this split is a function of the live `current_x/current_y` ratio, it is directly manipulable: an attacker composes, in one transaction, (1) a large swap that skews the pool ratio, (2) a `Deposit` or `Withdraw` call — both of which unconditionally invoke `calc_take_pnl` with the just-manipulated reserves as `x1`/`y1` [5](#0-4) [6](#0-5) , and (3) a reverse swap to restore the original price. Since `need_take_pnl_pc/coin` are subtracted from `total_pc_without_take_pnl`/`total_coin_without_take_pnl` for the remainder of that call and permanently increment the owner-only claimable balance [7](#0-6) , the attacker controls the magnitude of value permanently removed from the LP-shared pool on each triggerable call, independent of genuine trading-fee accrual.

### Impact Explanation
This produces insolvent/unfair pool accounting: LPs' proportional claim on `total_pc_without_take_pnl`/`total_coin_without_take_pnl` is diminished based on an attacker-chosen instantaneous price rather than real accrued fees, while the diverted amount becomes locked into a privileged-only claimable bucket (`need_take_pnl_*`, withdrawable via `process_withdrawpnl` only by `pnl_owner`) [8](#0-7) . This is a permanent, attacker-triggerable transfer of value out of the LP pool, and an unprivileged actor can force this privileged-benefiting effect at a magnitude they control, without pnl_owner's action or consent.

### Likelihood Explanation
Both `Deposit` and `Withdraw` are permissionless, user-callable instructions, and both call `calc_take_pnl` on every invocation once the pool has enough accrued k growth to pass the sanity check (`pool_pc*pool_coin >= calc_pnl_x*calc_pnl_y`) [9](#0-8) . Composing a swap immediately before/after a deposit or withdraw within a single Solana transaction is straightforward and requires no special privileges, flash loans, or off-chain coordination — matching the reachability profile of the original report's attack (price-skew then act at the skewed price then unwind).

### Recommendation
Compute the fee-growth/pnl split using price data that cannot be manipulated within a single transaction — e.g., a checkpointed/TWAP-style price, or decouple the pnl-skim ratio from the live price ratio entirely (mirroring Uniswap V2's protocol-fee formula, which depends only on `sqrt(k)` growth and not on the current price ratio). Alternatively, restrict `calc_take_pnl` triggering to epoch/time-gated calls rather than every user-initiated deposit/withdraw, and/or require the split calculation to use reserves sampled before the same-transaction swap.

### Proof of Concept
1. Attacker submits one transaction containing: `SwapBaseIn`/`SwapBaseOut` that heavily skews `amm_coin_vault`/`amm_pc_vault` reserves in one direction.
2. In the same transaction, attacker (or any account) calls `Deposit` or `Withdraw`, which invokes `Calculator::calc_total_without_take_pnl_no_orderbook` followed immediately by `Processor::calc_take_pnl` using the just-skewed `amm_coin_vault.amount`/`amm_pc_vault.amount` as `x1`/`y1` [5](#0-4) .
3. `calc_take_pnl` computes `diff_x`/`diff_y` at the skewed ratio, and moves an attacker-influenced amount into `need_take_pnl_pc`/`need_take_pnl_coin`, permanently reducing `total_pc_without_take_pnl`/`total_coin_without_take_pnl` available to LPs [7](#0-6) .
4. Attacker's final instruction in the transaction reverses the initial swap, restoring the pool to its original price, having paid only swap fees on the round-trip while the skim amount (now stuck in owner-only `need_take_pnl_*`) was determined by the manipulated intermediate price rather than the pool's real, unmanipulated state.

        // must be use u256, because u128 may be overflow
        let x_power = last_x
            .checked_mul(last_y)
            .unwrap()
            .checked_mul(current_x)
            .unwrap()
            .checked_div(current_y)
            .unwrap();
        x_power
    }

        swap_direction: SwapDirection,

        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_out = pc - coin * pc / (coin + amount_in)
                // => amount_out = ((pc * coin + pc * amount_in) - coin * pc) / (coin + amount_in)

                    .checked_mul(amount_in)
                    .unwrap()
                    .checked_div(denominator)
                    .unwrap();
            }

                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)

                    .unwrap()
                    .checked_div(denominator)
                    .unwrap();
            }
        }
        return amount_out;
