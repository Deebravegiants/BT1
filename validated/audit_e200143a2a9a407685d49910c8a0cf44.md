## Finding

The report's bug class ("data trusted by core logic without being cryptographically bound to the verification mechanism") maps directly onto how `ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Webhooks::Registry` handle the `shop` field of an incoming webhook.

### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0)  and `Registry.process` validates that body against the HMAC header via `Utils::HmacValidator.validate(request)` [2](#0-1) , but the `shop` value handed to the app's handler is read straight from the unauthenticated `shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the signed payload [3](#0-2) .

### Finding Description
`HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, raw_body)` and compares it to the `X-Shopify-Hmac-Sha256` header [4](#0-3) . The `api_secret_key` is a single per-app secret shared across every shop that has installed the app — it is **not** shop-specific. The identity binding that the library implicitly relies on is:

`shop asserted in the "shop-domain" header == shop that produced the HMAC-signed body`

but nothing enforces this equality: the HMAC only proves "this body byte-string was signed by an entity holding the app's `api_secret_key`" — it says nothing about which shop the header claims to be from. `Registry.process` forwards `request.shop` straight into `WebhookMetadata` and the app-supplied handler as the trusted tenant identifier [5](#0-4) , and the shipped documentation instructs consuming apps to key business logic (e.g. `shop_domain: data.shop`) directly off this unauthenticated field [6](#0-5) .

Because the same `api_secret_key` is valid for every shop using the app, any merchant who has legitimately installed the app can capture one authentic, HMAC-valid webhook delivered to their own endpoint (e.g. `app/uninstalled`, `customers/redact`, `shop/redact`) and replay the identical body + HMAC header while substituting the `x-shopify-shop-domain` header with a different, victim shop's domain. `Utils::HmacValidator.validate` will still pass (it never inspects the header), and the handler will process the request believing it originates from the victim shop.

### Impact Explanation
This breaks tenant isolation for any app that trusts `WebhookMetadata#shop` (as the gem's own documentation instructs). Depending on the handler's logic this enables cross-tenant actions such as: falsely triggering `APP_UNINSTALLED` cleanup (deleting another shop's stored sessions/access tokens), or forging GDPR `customers/redact` / `shop/redact` events against a shop the attacker does not control. This is a cross-tenant access vulnerability rooted entirely in this gem's webhook-processing code, matching the Critical impact category.

### Likelihood Explanation
Any user who can install the target app on a shop they control (a normal, unprivileged merchant/developer sign-up — no special credentials, no access token, no `api_secret_key` needed) can capture a real webhook delivery to their own endpoint and replay it with a modified `shop-domain` header. No privileged access, TLS interception, or leaked secret is required.

### Recommendation
Do not treat the `shop-domain` header as a trusted tenant identifier on its own. Either:
- Include the shop domain in the HMAC-signable material (not possible unilaterally, since Shopify controls the signing scheme), or
- Require the consuming application to cross-check `request.shop` against a shop it already has a stored, previously-authenticated session/access token for before acting on the webhook, and make this an explicit, enforced step in `Registry.process` rather than leaving it to documentation, or
- Bind webhook processing to the specific `webhook_id`/registration created for a known shop rather than trusting the header value blindly.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers an event (e.g. uninstalls the app), causing Shopify to POST a legitimately HMAC-signed `app/uninstalled` webhook to the app's endpoint with headers including `x-shopify-hmac-sha256: <valid hmac>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures this raw body and HMAC header.
3. Attacker resends the identical body and HMAC header to the app's webhook endpoint, replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes the HMAC over the (unchanged) body using the app's shared `api_secret_key` and it matches [7](#0-6) ; `Registry.process` proceeds and calls the handler with `shop: "victim-shop.myshopify.com"` [8](#0-7) .
5. The app's handler executes `app/uninstalled` cleanup logic against `victim-shop`'s stored session/data, even though `victim-shop` never uninstalled anything.
