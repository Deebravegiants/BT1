Based on my investigation, I have enough evidence to write up the finding.

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, but the `shop` value that is subsequently trusted and handed to the application's webhook handler is taken from an unauthenticated HTTP header. The identity binding "HMAC-valid request == request genuinely originating for shop X" does not hold, because `shop` is never part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines the signable content as the raw body only: [1](#0-0) [2](#0-1) 

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

`shop` is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic linkage to the body or the HMAC: [3](#0-2) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. it verifies `HMAC(secret, raw_body)`, never anything derived from `shop`: [4](#0-3) 

`Registry.process` performs this HMAC check and then immediately forwards `request.shop` — the unauthenticated header value — to the application's handler as the tenant identifier, alongside the (authenticated) body: [5](#0-4) 

The resulting `WebhookMetadata` struct binds `shop` and `body` together as if both were verified, but only `body` is actually covered by the signature: [6](#0-5) 

The broken identity equality is:
`HMAC(secret, raw_body) valid` ⇏ `shop-domain header == shop that produced raw_body`

Any unprivileged internet user who can obtain one genuine `(raw_body, hmac)` pair generated by Shopify for the app's webhook endpoint (e.g., by triggering an event on their own store where they have installed the target app, and capturing the delivery to the app's public webhook URL) can replay that exact `raw_body`/HMAC to the same public endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header value. `HmacValidator.validate` still succeeds because it never inspects the shop header, and `Registry.process` dispatches the handler with the attacker-chosen `shop` value paired with the captured body.

### Impact Explanation
Applications built on this gem are documented to trust `request.shop` (surfaced via `WebhookMetadata#shop`) as the authenticated tenant for the webhook — e.g., to look up that shop's session/access token or write data scoped to that shop, per the library's own webhook usage example. Since `shop` is not bound to the signed payload, an attacker can cause the host application to process webhook data under an arbitrary victim shop's identity, resulting in cross-tenant data confusion/injection (e.g., data belonging to the attacker's own store being attributed to and stored against a victim merchant's tenant record, or mandatory-topic handlers such as `shop/redact`/`app/uninstalled` firing for the wrong shop).

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one legitimately-HMAC-signed `(body, signature)` pair addressed to the target app's webhook endpoint — achievable by any user who can install the app on a store they control (a normal, unprivileged action for many public/free apps) and capture that store's outbound webhook delivery. No knowledge of `api_secret_key` or any access token is required, since the attacker reuses a valid signature rather than forging one. The header substitution itself requires nothing but a normal HTTP client capable of POSTing to the app's public webhook route.

### Recommendation
Bind the shop identity to the authenticated material: either include the shop domain as part of the string that is HMAC-verified, or cross-check `request.shop` against a shop value embedded in the verified JSON body (most Shopify webhook payloads or the `X-Shopify-Shop-Id`/domain can be corroborated against body-level fields), and reject the webhook if they disagree. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must be independently corroborated (e.g., against the app's known shop/session records) before being used to select tenant-scoped credentials or storage.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled development store; trigger a webhook event (e.g., `orders/create`) so Shopify POSTs a genuine `(raw_body, X-Shopify-Hmac-Sha256)` pair to the app's public webhook endpoint, and capture it (e.g., via a debugging proxy on the attacker's own infrastructure sitting in front of the endpoint, or any means of observing outbound traffic to the attacker's own account).
2. Replay the exact captured `raw_body` and `X-Shopify-Hmac-Sha256` value to the same endpoint, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13`) succeeds because it only checks `HMAC(secret, raw_body)`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's own order data>, ...)`, causing the application to act as if the payload originated from the victim tenant.

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
