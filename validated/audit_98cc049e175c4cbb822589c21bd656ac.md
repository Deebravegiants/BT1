### Title
Webhook shop-domain header not covered by HMAC allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the `X-Shopify-Shop-Domain` header is never included in the HMAC computation that `Utils::HmacValidator` verifies. Yet `ShopifyAPI::Webhooks::Registry.process` trusts this unauthenticated header as the tenant identifier passed to the app's handler. Since a single app's `api_secret_key` is shared across every shop that installs it, a valid `(body, hmac)` pair obtained from one tenant's own webhook traffic remains cryptographically valid when replayed with a different `shop-domain` header, letting one merchant forge webhook events that the host application will attribute to a different merchant/tenant.

### Finding Description
`HmacValidator.validate` verifies `OpenSSL::HMAC` over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as only the raw body: [2](#0-1) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic binding to the body or HMAC: [3](#0-2) 

`Registry.process` validates the HMAC (over body only) and then hands the unauthenticated `shop` value straight to the app's handler as the tenant identifier: [4](#0-3) 

The documented usage pattern shows apps trusting `data.shop` to route/attribute webhook data per tenant (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [5](#0-4) 

**The broken identity binding**: the gem verifies `hmac == HMAC(body)` but the application-level identity binding it needs is `hmac ⟹ (body, shop)`. Because `shop` is excluded from the signed content, `HMAC(body)` computed for tenant A's own webhook traffic is equally valid when the `shop-domain` header is swapped to tenant B — the equality `verified_bytes == parsed_identity` does not hold.

### Impact Explanation
Since the app's `api_secret_key` (the HMAC key) is the same across all shops that install a public/multi-tenant app, any merchant who has installed the app can generate genuine `(body, hmac)` pairs by triggering ordinary events (e.g. `orders/create`, `app/uninstalled`, `customers/data_request`) in their own store, capture the resulting webhook request, and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim tenant's domain. The HMAC check still passes because it never covered the shop header, and the handler will process attacker-controlled body content as if it originated from the victim shop. Depending on how the host application keys its business logic off `data.shop` (order ingestion, GDPR/compliance webhooks, uninstall/deauthorization flows, subscription state, etc.), this enables cross-tenant data injection or corruption — satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate, unprivileged merchant with the app installed on their own shop (a normal "unprivileged internet user" from the perspective of any other tenant) — no access to `api_secret_key`, access tokens, or other tenants' credentials is needed. They only need to observe or predict the byte content of a webhook body they can trigger themselves and know the target's shop domain (publicly discoverable, e.g. `victim.myshopify.com`). This is directly reachable through the gem's own public webhook-processing API (`Registry.process` / `Request`), not a misuse of undocumented behavior.

### Recommendation
Include the shop-domain (and topic/webhook-id, ideally) in the value verified for integrity, or otherwise cryptographically bind the shop identity to the payload before it is trusted by the handler. At minimum, `Request#to_signable_string` should not be the sole basis for trusting `Request#shop`; the library should document/enforce that `data.shop` cannot be relied upon as an authenticated tenant boundary unless additional binding (e.g., verifying the shop against an active session/webhook subscription record, or requiring shop-scoped webhook secrets) is performed by the consuming application. Ideally, extend the HMAC-verified string to incorporate the shop/topic headers so any tampering with those headers invalidates the signature.

### Proof of Concept
1. App `MyApp` is installed on `attacker.myshopify.com` and `victim.myshopify.com`, sharing one `api_secret_key`.
2. Attacker triggers an `orders/create` event in their own shop, capturing the raw webhook POST: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`), and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker replays the exact same body `B` and header `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, B)`, which still equals `H` (body unchanged), so validation succeeds: [6](#0-5) 
5. `Registry.process` calls the handler with `WebhookMetadata(shop: "victim.myshopify.com", body: B, ...)`, and the host application processes attacker-supplied data as if it came from `victim.myshopify.com`: [7](#0-6)
