### Title
Webhook HMAC only covers the raw request body, allowing the `shop`, `topic`, and `webhook_id` identity fields to be forged/replayed across tenants - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `api_version`, and `webhook_id` are all read from unauthenticated HTTP headers and are never bound into the value that `HmacValidator` verifies. `Registry.process` validates only this body-only HMAC and then hands the header-derived `shop` value straight to the app's webhook handler as the tenant identifier, breaking the intended binding `hmac(body) == hmac(body)` with the assumed-but-false binding `shop_header == shop_bound_by_signature`.

### Finding Description
`Webhooks::Request` derives its identity fields directly from HTTP headers: [1](#0-0) 

Crucially, `to_signable_string` — the value `HmacValidator` verifies against the `x-shopify-hmac-sha256`/`shopify-hmac-sha256` header — is only the raw body: [2](#0-1) 

`HmacValidator.validate` performs a constant-time comparison of the computed HMAC of that signable string against the received HMAC, using `Context.api_secret_key`: [3](#0-2) 

`Registry.process` relies solely on this check before dispatching the event, and it forwards `request.shop`, `request.topic`, and `request.webhook_id` — none of which are covered by the signature — to the app's handler as the tenant/event identity: [4](#0-3) 

Because the signature only binds the body bytes, any request with a *valid* body+HMAC pair (which is delivered to every merchant that installs the app, since Shopify signs webhooks per-body, not per-header) can be replayed with the `shop-domain` (and `topic`/`webhook-id`) headers rewritten to claim a different shop, topic, or webhook id, and it will still pass `Utils::HmacValidator.validate` unchanged. This is exactly the "field acted on but not covered by the HMAC" class of bug from the report: `beforeWithdraw`/`totalReleasedAssets` used an untracked value the same way `WebhookMetadata` uses an unsigned `shop` header as if it were authenticated.

By contrast, the OAuth callback path does correctly fold `shop` into the signed payload, so it is not affected: [5](#0-4) 

### Impact Explanation
Host applications built on this gem are documented to use `WebhookMetadata#shop` (constructed from `request.shop`) to identify which tenant a webhook event belongs to. Since that field is not covered by the signature, an attacker in possession of a single genuine `(raw_body, hmac)` pair for their own shop — trivially obtainable by installing the app once — can retarget it to any other shop domain and it will still validate as authentic. This lets the attacker inject fabricated events (e.g., `app/uninstalled`, `shop/redact`, `customers/data_request`, order/product mutation webhooks) attributed to an arbitrary victim shop into the app's processing pipeline, i.e., cross-tenant data/action injection without holding any credential for the victim tenant. This meets the Critical bar of cross-tenant access via a broken identity binding.

### Likelihood Explanation
Requires no privileged access, no `api_secret_key`, and no interception: any user who can install the app on one shop (a normal, unprivileged action) receives real, validly-signed webhook bodies and can immediately replay them with arbitrary header values against the app's public webhook endpoint. The only defense would need to be added by the host application, but the gem's own API surface (`WebhookMetadata`, `Registry.process`) offers no way for the host to know that `shop`/`topic`/`webhook_id` are unauthenticated, making the misuse straightforward and likely for any app that trusts `data.shop` for tenant scoping as the gem's structure implies it should.

### Recommendation
Bind the header-derived identity fields into the value verified by the HMAC. Concretely, change `Webhooks::Request#to_signable_string` (or `HmacValidator`) to incorporate `shop`, `topic`, and `webhook_id` in the signed material to verify, or — since Shopify's wire protocol only signs the body — require the caller to cross-check `request.shop` against session storage before trusting it, and expose that requirement explicitly (e.g., raise unless the resolved shop exists in the app's session store) so `Registry.process` cannot dispatch events for shops it hasn't independently authenticated.

### Proof of Concept
1. App merchant "attacker-shop.myshopify.com" installs the app and receives a legitimate webhook POST with body `{"id":1}` and header `x-shopify-hmac-sha256: <valid-hmac-of-body>` (computed by Shopify over the body only).
2. Attacker resends the exact same body and HMAC header to the app's webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com` and/or `x-shopify-topic` with `app/uninstalled`.
3. `Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` (`to_signable_string`), unaffected by the header changes shown in: [2](#0-1) 
4. The handler is invoked with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...)` as if Shopify itself had sent this event for the victim shop: [4](#0-3)

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
