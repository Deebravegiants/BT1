### Title
`borrow` lets a user accumulate debt in assets not held as collateral, which `get-notional-evaluation` silently excludes from the health check — undercollateralised, uninsured debt (`mainnet/contracts/market/v0-4-market.clar:514`, `mainnet/contracts/market/v0-4-market.clar:1238`)

### Summary
`get-notional-evaluation` folds over an `assets` list that is built exclusively from the **collateral** bits of the user's mask (`get-assets` → `mask-to-list-collateral`, never `mask-to-list-debt`). Consequently any debt entry whose asset-id is not also present in the user's collateral bitmap is skipped entirely by the fold and contributes `u0` to `debt-total`, while the actual scaled debt is still recorded (and grows) in `v0-market-vault`'s `debt` map. Repeated `borrow` calls for assets the caller never posts as collateral let debt accumulate that is never counted by the LTV health check, letting an attacker post minimal collateral once and drain arbitrarily many under-collateralised loans.

### Finding Description
Identity that should hold for every `borrow` call:
```
debt-total(position) ⊇ Σ_over_debt_entries(scaled_i * index_i / PRECISION * price_i)   for ALL entries in position.debt
```
i.e. every entry present in `debt` (the position's debt list returned by `v0-market-vault.get-position`) must contribute to the `debt-total` used by the LTV/health check.

Code path:
- `get-position` (market wrapper, `mainnet/contracts/market/v0-4-market.clar:466-468`) calls `v0-market-vault.get-position account mask`, which builds `debt` via `lookup-debt user-id mask MAX-U128` (`mainnet/contracts/market/v0-market-vault.clar:317-333`) — **all** debt bits in the user's mask are returned, unfiltered by the enabled bitmap.
- The `assets` list used to price/evaluate the position is produced by `get-assets` (`mainnet/contracts/market/v0-4-market.clar:482-492`), which calls `mask-to-list-collateral safe-mask` only — this only inspects mask positions `0..63` (the collateral bit range). It never calls `mask-to-list-debt`, so an asset whose *debt* bit (offset `+64`, see `DEBT-OFFSET`) is set but whose *collateral* bit is unset never appears in `assets`.
- `get-notional-evaluation` (`mainnet/contracts/market/v0-4-market.clar:514-542`) folds `calculate-asset-notional-value` over `assets`, and for each asset looks up `find-debt-scaled debt-list asset-id` (`mainnet/contracts/market/v0-4-market.clar:544-574`). If an asset-id present in `debt-list` never occurs in `assets` (because its collateral bit is unset), the fold simply never visits it — it contributes `u0` to `debt-total` even though `debt-scaled > u0`.

Exploit flow via `borrow` (`mainnet/contracts/market/v0-4-market.clar:1238-1314`), fully attacker-controlled, unprivileged:
1. Attacker posts a small amount of collateral in asset `X` only (collateral bit `X` set, no debt yet).
2. Attacker calls `borrow` for asset `Y` (`Y != X`, no collateral in `Y`). At this point `mask` (pre-borrow) only has `X`'s collateral bit, so `get-assets(mask)` = `[X]`; `get-notional-evaluation` correctly returns `debt-total = 0` for existing debt. The newly borrowed amount is priced separately via `get-asset-value asset amount true` (line 1281) and added as `debt-increase`, so this first borrow's own health check is correctly enforced against `X`'s collateral. After success, `debt-add-scaled` sets the debt bit for `Y` at mask offset `Y+64` (`mainnet/contracts/market/v0-market-vault.clar:442-471`).
3. Attacker calls `borrow` again for a *different* asset `Z` (`Z != X, Z != Y`, no collateral in `Z`). Now `mask` = `X`'s collateral bit + `Y`'s debt bit (offset). `get-assets(mask)` still returns only `[X]` (mask-to-list-collateral ignores offset bits ≥64). `get-notional-evaluation` therefore computes `debt-total` **without any contribution from `Y`'s outstanding debt** — that debt entry is simply never visited by the fold. The pre-check `is-healthy collateral-value debt-value current-ltvb` (line 1272) and the post-check `is-healthy-with-mask collateral-value debt-post-increased future-mask` (line 1287) both evaluate health using a `debt-value`/`debt-post-increased` that omits `Y`'s debt entirely, only accounting for `Z`'s freshly-added increase.
4. Repeat step 3 for further distinct assets `W`, `V`, … — each new borrow's health check only "sees" the collateral in `X` and the *current* borrow's own increase; all previously accumulated debt in assets not held as collateral is invisible to every subsequent health check.

Root cause: `get-assets` builds the priced asset universe strictly from the *collateral* mask, while debt bits live in a disjoint bit range (`+64` offset) and are never merged into that universe, so `get-notional-evaluation`'s fold structurally cannot price debt for an asset that isn't also collateral for that user.

Existing guards that fail to prevent this:
- `is-healthy` / `is-healthy-with-mask` operate purely on the (already wrong) `collateral-value`/`debt-value` inputs — they cannot detect the omission.
- `check-impl-auth` in `v0-market-vault` only gates who can call `debt-add-scaled`, not whether the caller's own health accounting was correct; the market contract itself is the authorized `impl`, so it always passes.
- No cross-check exists comparing `debt-list` entries against `assets` entries to assert full coverage.

### Impact Explanation
Each additional distinct-asset borrow is completely unconstrained by the debt already outstanding in other non-collateral assets: the attacker can keep borrowing new asset types against a single minimal collateral deposit, with each loan's own increase checked against collateral but all prior loans invisible to the check. This directly produces uncollateralised debt recorded in `v0-market-vault`'s `debt` map (and in `total-borrowed`/vault accounting) that is never backed by adequate collateral value, i.e. protocol insolvency: the vault's real token outflows (`vault-system-borrow`) exceed what the collateral guarantees can cover. The loss is borne by depositors/lenders in the underlying vaults whose liquidity is drained; the divergence is repeatable per new distinct debt asset and scales with the number of distinct assets available in the market (bounded by `ITER-UINT-64`, i.e. up to ~64 assets), each borrow further compounding the shortfall. This matches Immunefi Critical — protocol insolvency through uncollateralised debt.

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged attacker's control: deposit a small amount of any enabled collateral asset, then call `borrow` for several other assets in sequence, each time targeting an asset different from any currently held as collateral. No oracle manipulation, no flashloan, no privileged role, and no reliance on any other contract's misbehavior are required — this is a direct logic flaw reachable through the public `borrow` entrypoint with ordinary calls. Capital cost is just the single small collateral deposit; the borrowed amounts vastly exceed what that collateral would allow under correct LTV accounting. The bug is deterministic and repeatable for every additional distinct-asset borrow.

### Recommendation
Build the priced `assets` list for `get-notional-evaluation` from the union of the user's collateral **and** debt bits (i.e., also run `mask-to-list-debt` on the mask, or merge the debt-derived asset-ids into the list before calling `get-status-multi`/pricing), so every entry present in `position.debt` is guaranteed to have a matching `assets` row and is priced into `debt-total`. Alternatively, change `calculate-asset-notional-value`'s iteration to fold over the union of `collateral-list` and `debt-list` asset-ids rather than solely over the externally-supplied `assets`, and assert (or `unwrap-panic`) that every debt/collateral asset-id has a corresponding priced entry, failing the transaction otherwise instead of silently contributing zero.

### Proof of Concept
Clarinet/vitest simnet test plan (illustrative, using existing test asset ids/vaults from the local-testing setup):
1. Setup: enable assets `X`, `Y`, `Z` for both collateral and debt in `v0-assets`/`v0-egroup`, fund their vaults with liquidity from other users.
2. Attacker deposits a small amount of `X` as collateral via `collateral-add`, e.g. `X_amount` sized so its notional value at oracle price barely covers a single small loan.
3. Attacker calls `borrow` for asset `Y` with an amount at the max the LTV allows against `X` alone. Assert success, and record `debt-map[Y] = scaled_Y`, `notional-debt-total ≈ Y`'s value (matches expectations — baseline correct).
4. Attacker calls `borrow` again for asset `Z`, again sized at the max LTV allows against `X` alone (ignoring `Y`'s debt). Before the call, compute expected `debt-total` if `Y` were correctly included (`= value(Y) + value(Z)`) versus what the contract will actually compute (`= value(Z)` only, since `Y` is excluded from `assets`).
5. Assert the call succeeds (health check passes) even though `value(X_collateral) < value(Y) + value(Z)` — i.e., real aggregate LTV exceeds the configured `LTV-BORROW` threshold, proving the health check was bypassed.
6. Assert on-chain state: `v0-market-vault.get-debt` for both `Y` and `Z` shows nonzero scaled debt for the attacker, while `is-healthy` as computed by the contract at each step returned `true`; independently recompute the correct aggregate notional debt (summing all of the attacker's `debt` map entries priced at oracle rates) and show it exceeds `collateral-value * LTV-BORROW / BPS`, breaking the intended solvency invariant.
7. Optionally, repeat borrowing a third distinct asset `W` to show the divergence compounds, and confirm the attacker's net token balance change from the borrows is strictly positive (received borrowed tokens) while posted collateral value remains fixed — demonstrating extractable, uncollateralised value. (define-private (calculate-asset-notional-value
          (asset-entry {
              id: uint, addr: principal, decimals: uint,
              oracle: { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint },
              collateral: bool, debt: bool, price: uint })
          (acc { clist: (list 64 { aid: uint, amount: uint }),
                  dlist: (list 64 { aid: uint, scaled: uint }),
                  coll-total: uint,
                  debt-total: uint }))
  (let ((asset-id (get id asset-entry))
        (price (get price asset-entry))
        (decimals (get decimals asset-entry))
        (collateral-list (get clist acc))
        (debt-list (get dlist acc))
        (coll-amount (find-collateral-amount collateral-list asset-id))
        (coll-notional (if (> coll-amount u0)
                           (normalize (* coll-amount price) decimals false)
                           u0))

        (debt-scaled   (find-debt-scaled debt-list asset-id))
        (debt-notional (if (> debt-scaled u0) ;; use cache instead here
                           (let ((cached (unwrap-panic (accrue-and-cache asset-id)))
                                 (ib (get index cached))
                                 (actual (mul-div-up debt-scaled ib INDEX-PRECISION)))
                             (normalize (* actual price) decimals true))
                           u0)))

    { clist: collateral-list,
      dlist: debt-list,
      coll-total: (+ (get coll-total acc) coll-notional),
      debt-total: (+ (get debt-total acc) debt-notional) }))

(define-read-only (lookup-debt (id uint) (mask uint) (enabled-mask uint))
  (let ((init { id: id, result: (list), enabled-mask: enabled-mask })
        (iter (mask-to-list-debt mask))
        (out (fold iter-lookup-debt iter init)))
    (get result out)))

(define-read-only (get-position (account principal) (enabled-mask uint))
  (match (map-get? reverse account)
    id (let ((obligation (lookup id))
             (user-id (get id obligation))
             (mask (get mask obligation))
             (is-collateral (lookup-collateral user-id mask enabled-mask))
             (is-debt (lookup-debt user-id mask MAX-U128)))
         (ok (merge obligation { collateral: is-collateral, debt: is-debt })))
