## Title
Unbounded SCALE-decode allocation in `pallet_ismp::handle_unsigned`'s GRANDPA consensus payload lets a fee-less relayer force large, uncapped memory allocation during transaction-pool validation - (File: `modules/consensus/grandpa/primitives/src/lib.rs`, `modules/consensus/grandpa/primitives/src/justification.rs`, `modules/ismp/clients/grandpa/src/consensus.rs`, `modules/ismp/core/src/messaging.rs`)

### Summary
`pallet_ismp::handle_unsigned` is an unsigned, fee-less extrinsic that "permits anyone execute ISMP messages for free" [1](#0-0) . Its `Message::Consensus(ConsensusMessage)` variant carries an opaque `consensus_proof: Vec<u8>` with no length bound in the type itself [2](#0-1) . For the GRANDPA consensus client, this blob is SCALE-decoded directly into `ConsensusMessage` (`StandaloneChain`/`Polkadot`/`Relaychain`), whose `FinalityProof<H>` contains an unbounded `unknown_headers: Vec<H>` [3](#0-2)  and whose nested `GrandpaJustification<H>` contains an unbounded `votes_ancestries: Vec<H>` [4](#0-3) , plus (for relay messages) an unbounded `parachain_headers: BTreeMap<H256, ParachainHeaderProofs>` each carrying its own `state_proof: Vec<Vec<u8>>` [5](#0-4) .

This is the same bug class as the reported pypdf issue: a structure that legitimately only ever needs to be small (real XMP metadata / a real GRANDPA justification only needs the header sub-chain and precommit ancestry actually used) has no explicit cap on the number of entries an attacker can submit, so a single submission forces the node to allocate memory proportional to attacker-chosen quantities before any semantic rejection occurs.

### Finding Description
`GrandpaConsensusClient::verify_consensus` decodes the untrusted `proof: Vec<u8>` into a `ConsensusMessage` with a bare `codec::Decode::decode`, with no cap on the number of headers or ancestry entries [6](#0-5) . `verify_grandpa_finality_proof` then builds an `AncestryChain` from the fully-decoded `unknown_headers` and further decodes `finality_proof.justification` into a `GrandpaJustification`, whose `votes_ancestries` field is likewise an unbounded `Vec<H>` [7](#0-6) . All of this decoding and the `BTreeMap`/`BTreeSet` construction in `AncestryChain::new` and `GrandpaJustification::verify_with_voter_set` happens before any cryptographic signature check on individual precommits reduces the accepted set, meaning the allocation cost is driven entirely by how many header/ancestry entries the attacker chooses to include [8](#0-7) .

Crucially, `pallet_ismp::handle_unsigned`'s `validate_unsigned` implementation calls `Self::execute(messages.clone())` directly in the transaction-pool validation path, meaning this decode-and-partially-verify cost is paid for **every unsigned submission that reaches the pool**, not just ones that are eventually included in a block [9](#0-8) . This is structurally identical to the zstd-bomb pattern the codebase already defends against in `pallet_call_decompressor`, where the fix note explicitly says the unsigned mempool path let "a fee-less attacker ... have a tiny zstd 'bomb' expanded to gigabytes during transaction-pool validation, before any size check" [10](#0-9) . Unlike that pallet and unlike `pallet_beefy_consensus_proofs` (which explicitly caps its proof at `BoundedVec<u8, MaxProofSize>` before any expensive work, verified by its own regression test) [11](#0-10) , the GRANDPA `ConsensusMessage` path has no analogous cap on the number of headers/ancestry entries relative to what a legitimate justification requires.

### Impact Explanation
An unprivileged party can submit a `handle_unsigned` extrinsic (fee-less, unsigned, permissionless) whose GRANDPA `consensus_proof` blob contains a large number of `unknown_headers` and `votes_ancestries` entries. Each submission forces full-node transaction-pool validators to SCALE-decode and materialize this data (headers, `BTreeMap`/`BTreeSet` ancestry structures) in memory before rejection can occur, and this validation re-runs on every re-broadcast/resubmission attempt across the network's mempools — a resource-exhaustion vector consistent with CWE-770, matching the Medium severity of the referenced pypdf advisory. This does not directly cause theft of funds, but it degrades the availability of message delivery/relaying for the affected consensus client, which the scan's validation criteria explicitly accept ("a route unable to deliver messages").

### Likelihood Explanation
Likelihood is moderate: the attack requires no special privileges, no fee, and no valid signatures — only that the byte blob SCALE-decodes into the `ConsensusMessage` enum shape, since header/ancestry entry counts are unconstrained at decode time and rejection (signature/ancestry-consistency checks) only happens after the full structure is materialized. The overall extrinsic is still bounded by the substrate node's default max-extrinsic/max-block-length settings, which limits amplification versus a true compression bomb, but no explicit application-level bound exists analogous to `MaxProofSize`/`MaxCallSize` used elsewhere in this codebase for exactly this class of risk.

### Recommendation
Add explicit upper bounds on `FinalityProof::unknown_headers`, `GrandpaJustification::votes_ancestries`, and `RelayChainMessage::parachain_headers` (and their nested `state_proof` vectors) before or during decode of the GRANDPA `consensus_proof`, mirroring the `BoundedVec<u8, MaxProofSize>` pattern already used in `pallet_beefy_consensus_proofs` and the `MaxCallSize` gate in `pallet_call_decompressor`. Reject any GRANDPA `ConsensusMessage` whose header/ancestry counts exceed a configurable maximum before running `AncestryChain::new`/`GrandpaJustification::verify`, so the unsigned mempool validation path cannot be forced to allocate memory proportional to attacker-chosen counts.

### Proof of Concept
1. Construct a valid-shaped `ismp_grandpa::messages::ConsensusMessage::Relaychain(RelayChainMessage)` whose `finality_proof.unknown_headers` and nested `GrandpaJustification.votes_ancestries` contain a very large number of syntactically valid (but otherwise junk/duplicate) `SubstrateHeader` entries, and whose `parachain_headers` `BTreeMap` contains many entries each with a large `state_proof: Vec<Vec<u8>>`, sized up to the node's max extrinsic/block length.
2. Wrap this in `ismp::messaging::ConsensusMessage { consensus_proof: <encoded blob>, consensus_state_id: <GRANDPA client id>, signer: vec![] }` and submit as `pallet_ismp::Call::handle_unsigned { messages: vec![Message::Consensus(...)] }` via an unsigned transaction, as already exercised for other message types in `parachain/simtests/src/pallet_ismp.rs` [12](#0-11) .
3. Observe that `ValidateUnsigned::validate_unsigned` decodes and processes the full structure (headers, ancestry `BTreeSet`s) before rejecting it for an invalid justification signature, repeating this cost on every node's mempool and on every resubmission — the same "cheap trigger, uncapped materialize-before-reject" pattern as the pypdf XMP advisory.
