## Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" [1](#0-0)  before invoking the app's handler with a `WebhookMetadata` struct that includes `shop` [2](#0-1) . However, the HMAC that gates this verification is computed only over the raw request body, never over the `shop-domain` header, so the "authenticated" shop identity is actually unauthenticated attacker-controlled input.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [3](#0-2)  while `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to that value: [4](#0-3)  and [5](#0-4) .

`HmacValidator.validate` verifies `verifiable_query.hmac` against `HMAC(api_secret_key, verifiable_query.to_signable_string)` [6](#0-5) , so for webhooks it only proves the body bytes were signed by someone holding the app's `api_secret_key` — the same key shared by Shopify across **every shop that has installed the app**. It never proves which shop the request is for.

`Registry.process` only checks this body HMAC before dispatching to the handler with the unauthenticated `shop` field: [2](#0-1) .

This is asymmetric with how the gem handles OAuth: `Auth::Oauth::AuthQuery#to_signable_string` explicitly folds `shop` into the signed string so the shop claim *is* cryptographically bound to the signature [7](#0-6) . The webhook path lacks the equivalent binding — i.e. the equality that should hold, `hmac_signed_identity == shop_acted_on`, does not hold for webhooks.

### Impact Explanation
Because the app's `api_secret_key` is shared across all merchants that install the app (it is not shop-specific), any merchant who legitimately receives a genuine Shopify webhook for their own store also possesses a valid `(body, hmac)` pair signed with that shared secret. Nothing prevents them from replaying that exact body+HMAC pair to the app's webhook endpoint while spoofing the `x-shopify-shop-domain` header to name a different, victim shop. `Registry.process` will accept it as authentic (`Errors::InvalidWebhookError` is only raised on HMAC mismatch of the body) and hand the host app a `WebhookMetadata` claiming the data belongs to the victim shop [8](#0-7) . Any handler logic keyed off `data.shop` (looking up sessions, updating shop-scoped records, enqueuing shop-scoped jobs, as shown in the gem's own documented handler example) is thus poisoned with cross-tenant, attacker-controlled data — a cross-tenant integrity/access violation.

### Likelihood Explanation
Requires the attacker to control (or install the app on) at least one shop to obtain a genuine, validly-signed webhook payload — a low bar for any SaaS app with open/self-serve installation. No knowledge of `api_secret_key` itself is needed, only capture-and-replay of a webhook they legitimately received for their own store, with a forged shop-domain header. This is fully exploitable purely through this gem's public `Webhooks::Request`/`Webhooks::Registry` API as documented.

### Recommendation
Bind the shop identity to the verified signature for webhooks, e.g. include the `shop-domain` header value in `to_signable_string` (or independently verify the shop domain against the session/webhook subscription associated with the `webhook_id`) before constructing `WebhookMetadata`, mirroring the approach already used for `Auth::Oauth::AuthQuery`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a genuine webhook, e.g. body `{}`, with header `x-shopify-hmac-sha256: <valid-hmac-of-{}>` (valid because `HMAC(api_secret_key, "{}")` only depends on the app-wide secret and the body).
2. Attacker resends the identical body and HMAC to the app's webhook endpoint but replaces `x-shopify-shop-domain: attacker-shop.myshopify.com` with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this successfully [5](#0-4) , and `Registry.process` accepts it because `HmacValidator.validate` only checks the body signature [9](#0-8) .
4. The host app's handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)` and performs shop-scoped actions attributing attacker-supplied data to the victim tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|

            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
