### Title
Webhook shop/topic/webhook-id headers are trusted but excluded from the HMAC signature, allowing cross-tenant webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers that are never included in the HMAC-signed bytes. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts these unauthenticated header values to route and identify the "shop" for the event, breaking the intended binding: `bytes verified == bytes parsed`.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 
Only `@raw_body` is fed into the HMAC computation. The `shop`, `topic`, `webhook_id`, and `api_version` accessors read straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` computes the signature only over `to_signable_string` (the body): [3](#0-2) 

`Registry.process` checks this body-only HMAC, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because the `api_secret_key` is shared across all shops that install the app, any merchant who installs the app receives their own genuinely-signed webhook (valid `raw_body` + valid HMAC over that body). That attacker-merchant can capture this legitimate `body`/`hmac` pair and replay it against the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header for a victim shop. Since none of these headers are part of the signed content, `HmacValidator.validate` still returns `true`, and `Registry.process` will invoke the handler with `WebhookMetadata` claiming the event belongs to the victim shop. The documented handler pattern explicitly keys downstream processing off `data.shop`: [5](#0-4) 

This is the same identity-binding class as the reported bug: a field that is acted upon (`shop`) is not covered by the value that was cryptographically verified (the HMAC over `raw_body` only), so the equality `verified_identity == acted_upon_identity` does not hold.

### Impact Explanation
This breaks the shop-authentication boundary the HMAC is supposed to provide, letting one tenant (an attacker who is a legitimate merchant/installer of the app) inject events that the host application will process and persist as belonging to a different, victim shop. Any app that uses `data.shop` from `WebhookMetadata` to select tenant context, write to shop-scoped storage, or gate business logic (as the gem's own documented usage example does) is exposed to cross-tenant data corruption/injection. This matches the Critical "cross-tenant access" impact category since the shop/tenant identity is spoofed despite HMAC verification succeeding.

### Likelihood Explanation
The prerequisite is only that the attacker be able to install the target app on their own (attacker-controlled) shop — a normal, unprivileged action requiring no special credentials, access tokens, or knowledge of the app's `client_secret`. Once installed, they receive real webhook deliveries with valid bodies and HMACs signed by Shopify with the app's shared secret, which they can freely replay with a forged `shop-domain` header against the app's public callback URL. This requires no interception of TLS, no leaked secrets, and no privileged access — likelihood is high for any app that relies on `Registry`/`Request` as documented.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value verified by the HMAC, or otherwise cryptographically/logically tie the `x-shopify-shop-domain` header to the specific installation the request claims to be for (e.g., cross-check it against the shop associated with the target subscription/webhook id via a lookup keyed by the topic+webhook subscription id registered for that shop, rather than trusting the header value directly). At minimum, document that `data.shop` returned by `Registry.process` is not authenticated by the HMAC and must not be used to select tenant/session context without additional verification (e.g., confirming the shop has an active, matching webhook registration for that `webhook_id`).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers for topic `orders/create`.
2. Shopify sends a legitimately signed webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`
   - Body: `{"id": 1, ...}`
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value.
4. Attacker sends a new POST to the same public webhook endpoint with the identical `raw_body`/`x-shopify-hmac-sha256`, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because it only checks `raw_body` against the HMAC.
6. `ShopifyAPI::Webhooks::Registry.process` in `lib/shopify_api/webhooks/registry.rb` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "orders/create", body: {...}, ...)`, causing the host app to process/store attacker-controlled data under the victim shop's tenant context.
