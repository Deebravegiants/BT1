### Title
Reachable panic (`unwrap()` on `checked_sub`) in `calc_take_pnl` causes permanent denial-of-service on Deposit/Withdraw/Swap - (File: `program/src/processor.rs`)

### Summary
The CVE describes a crafted input causing an unhandled assertion/`assert` failure in `ReplaceImageInList`, aborting the whole application. The equivalent bug class here is an unguarded `.unwrap()` on an arithmetic operation that a normal, permissionless user can drive into a failing branch, causing the Solana program to panic. Because the panicking computation, `Processor::calc_take_pnl`, is invoked on every `Deposit`, `Withdraw`, and both swap paths, a state that triggers the panic once will keep triggering it on every subsequent call, freezing the pool.

### Finding Description
`Processor::calc_take_pnl` [1](#0-0)  computes, when current pool value is judged `>=` the previously recorded target value:

```
let x2 = x2_power.integer_sqrt();
let y2 = x2.checked_mul(y1).unwrap().checked_div(x1).unwrap();
let diff_x = U128::from(x1.checked_sub(x2).unwrap().as_u128());
let diff_y = U128::from(y1.checked_sub(y2).unwrap().as_u128());
``` [2](#0-1) 

`x2` is derived from `Calculator::calc_x_power`, which itself performs `last_x * last_y * current_x / current_y` using integer (floor) division [3](#0-2) , followed by an `integer_sqrt()`. The invariant `x2 <= x1` and `y2 <= y1` only holds algebraically for real numbers; with integer truncation in `calc_x_power`, `integer_sqrt`, and the subsequent multiply/floor-divide for `y2`, rounding error can push `x2` or `y2` to exceed `x1`/`y1` by one or more units in edge cases (e.g., extreme decimal normalization ratios between `pc_decimals`/`coin_decimals` and `sys_decimal_value`, or very small/large pool ratios reachable by repeated attacker-chosen swaps that move `total_pc_without_take_pnl` / `total_coin_without_take_pnl`). When that happens, `x1.checked_sub(x2)` or `y1.checked_sub(y2)` returns `None` and `.unwrap()` panics, aborting the transaction with a Rust panic rather than a handled `ProgramError`.

Crucially, `target.calc_pnl_x` / `target.calc_pnl_y` (the values compared against `x1`/`y1`) are only updated on the *success* path of `calc_take_pnl` and its callers — see the update sites in `process_deposit` [4](#0-3) , `process_withdraw` [5](#0-4) , and `process_withdrawpnl` [6](#0-5) . Since a panicking transaction is not committed, `TargetOrders.calc_pnl_x/y` on-chain remains at the value that caused the panic. Every future `Deposit`, `Withdraw` (unless status is `WithdrawOnly`, which skips the call — see `process_withdraw` gate at [7](#0-6) ), and `SwapBaseIn`/`SwapBaseOut` v1/v2 that reach `calc_take_pnl` with the same stuck `target` state and similar vault ratios will re-trigger the same panic, permanently denying service on that instruction path for the pool.

### Impact Explanation
Once the pool's vault balances land in the narrow region that produces `x2 > x1` (or `y2 > y1`), `Deposit` and default-status `Withdraw`/`Swap` calls into `calc_take_pnl` will panic and abort every time, since the on-chain `TargetOrders` state that determines `x1`/`x2` is not mutated by a failed (panicked) transaction. This is a permanent freezing-of-funds condition for LPs/users relying on those instructions, matching the CVE's "denial of service via crafted input causing assertion failure" bug class, but on-chain and with fund-freezing consequences rather than a one-off crash.

### Likelihood Explanation
Reaching the panic requires an attacker (or even an ordinary user through pool activity) to drive the vault-derived `total_pc_without_take_pnl` / `total_coin_without_take_pnl` and the stored `target.calc_pnl_x/y` into a specific numerical relationship where integer rounding in `calc_x_power`/`integer_sqrt`/floor-division causes `x2` or `y2` to exceed `x1`/`y1`. This is entirely reachable through normal `SwapBaseIn`/`SwapBaseOut` calls with attacker-chosen `amount_in`/`amount_out`, which are unprivileged, single-transaction operations — no special account or off-chain access is required. However, I was not able to fully derive or numerically confirm a concrete adversarial swap sequence within the available investigation depth; confirming exact trigger values (decimals, sys_decimal_value, and vault ratio) would require running the arithmetic (or a fuzz/property test) against `Calculator::calc_x_power` / `integer_sqrt` to find a boundary case, which is not something I can execute from static code review alone.

### Recommendation
Replace the `.unwrap()` calls on `x1.checked_sub(x2)` and `y1.checked_sub(y2)` in `calc_take_pnl` (and the analogous `checked_sub().unwrap()` chains that consume `delta_x`/`delta_y` in `process_deposit`, `process_withdraw`, and `process_withdrawpnl`) with saturating subtraction or explicit `AmmError`-returning fallbacks (e.g., clamp `x2`/`y2` to `x1`/`y1` when rounding pushes them over, or return `AmmError::CalcPnlError` instead of panicking). This converts an unrecoverable panic/DoS into a graceful, recoverable error path and prevents the pool from becoming permanently stuck in a bad `TargetOrders` state.

### Proof of Concept
Not independently verified with concrete numeric inputs; the mechanism is established by code inspection of `calc_take_pnl`'s unwrap chain [2](#0-1)  and its unconditional invocation from `process_deposit`/`process_withdraw`/swap paths [8](#0-7) [7](#0-6) . A concrete PoC would require constructing an `AmmInfo`/`TargetOrders` state and a sequence of `SwapBaseIn`/`SwapBaseOut` calls (varying `pc_decimals`, `coin_decimals`, `sys_decimal_value`, and vault balances) that drives `calc_x_power`'s integer truncation to produce `x2 > x1`, which I could not execute in this read-only environment.

    pub fn calc_x_power(last_x: U256, last_y: U256, current_x: U256, current_y: U256) -> U256 {
        // must be use u256, because u128 may be overflow
        let x_power = last_x
            .checked_mul(last_y)
            .unwrap()
            .checked_mul(current_x)
            .unwrap()
            .checked_div(current_y)
            .unwrap();
        x_power
    }
