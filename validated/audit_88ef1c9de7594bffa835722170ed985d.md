### Title
Webhook Shop Identity Spoofing via Unsigned `shop-domain` Header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant identity) is read from an unsigned HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates only the body HMAC and then hands the unauthenticated `shop` value straight to the application's handler as trusted tenant identity, breaking the binding `shop_verified_by_hmac == shop_acted_on`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not included in the signed content at all: [2](#0-1) 

`Utils::HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` against the computed signature: [3](#0-2) 

`Registry.process` validates that single HMAC and then immediately forwards `request.shop` to the application handler as the authoritative tenant identity, with no cross-check that the body was actually generated for that shop: [4](#0-3) 

Because Shopify webhooks for a given app are all signed with the same app-level `api_secret_key` (it is not shop-specific), any user who can get the target app installed on a shop they control (e.g. a free dev store) can capture a genuine `(raw_body, valid-hmac)` pair produced for their own shop, then replay that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary victim shop domain in the `shop-domain` header. `HmacValidator.validate` still returns `true` because it never inspects the header, so `Registry.process` calls the handler with `shop` == the forged victim domain and `body` == attacker-controlled content.

### Impact Explanation
This breaks the equality `shop_bound_by_signature == shop_delivered_to_handler`. Any application that uses the `shop` field from `WebhookMetadata` to select which merchant's data to update (the intended and documented usage pattern) can be made to apply attacker-chosen webhook payloads under an arbitrary victim shop's identity — a cross-tenant data injection/attribution bypass, satisfying the Critical "cross-tenant access" category.

### Likelihood Explanation
Any unprivileged internet user can obtain a valid `(body, hmac)` pair by installing the target public app on a shop they control and triggering a webhook of their choosing (e.g. creating an order/product with attacker-controlled field values), since the app's webhook secret is shared across all installations. No access token, `api_secret_key`, or privileged account is required — only a normal, uncontrolled installation of the target app.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the signed payload considered by `to_signable_string`, or otherwise cryptographically bind the `shop-domain` header value to the verified request before exposing it via `WebhookMetadata`. At minimum, document prominently that `Request#shop` is unauthenticated and must not be trusted for tenant routing without an additional out-of-band check (e.g. verifying the shop is one the app is actually installed on with a matching webhook registration).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (any unprivileged user can do this for a public app).
2. Attacker triggers a webhook event with attacker-chosen resource content (e.g. updates an order note) and captures the resulting HTTP request: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` — this validates via `Utils::HmacValidator.validate` per `lib/shopify_api/utils/hmac_validator.rb` lines 26-31.
3. Attacker replays a POST to the victim app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but header `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into `shop = "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/request.rb` lines 20-23) while `to_signable_string` still equals `B` (lines 35-38).
5. `ShopifyAPI::Webhooks::Registry.process` (lines 188-199) confirms `HmacValidator.validate(request)` succeeds and calls the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker-controlled body, ...)`, causing the host application to process attacker-chosen data under the victim's tenant identity.
