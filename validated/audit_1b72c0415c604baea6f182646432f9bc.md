### Title
Unchecked arithmetic overflow in `Calculator::calc_x_power` can permanently freeze LP/PNL funds - (File: `program/src/math.rs`, `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` calls `Calculator::calc_x_power`, which chains three `U256` multiplications and a division, all guarded only with `.unwrap()` on `checked_mul`/`checked_div` rather than a safe fallback. [1](#0-0)  This function is invoked from `Processor::calc_take_pnl`, which is executed on every `Deposit`, `Withdraw`, and `WithdrawPnl` instruction — all reachable by unprivileged LPs. [2](#0-1) 

### Finding Description
`AmmInfo::initialize` derives `sys_decimal_value` as `10^max(coin_decimals, pc_decimals)`, using the SPL mint decimals supplied by whoever creates the pool via `Initialize2` (an unprivileged, permitted action): [3](#0-2) 

`Calculator::normalize_decimal_v2` then converts raw vault/token amounts (up to `u64::MAX`) into this "normalized" `sys_decimal_value` scale: [4](#0-3) . When one side of the pool has a low native decimal count (e.g. 0) and the other has a high decimal count (up to 19, the largest value for which `10^decimals` still fits in `u64`), the normalized value for the low-decimal token can grow to nearly `U128::MAX` in magnitude (raw `u64` amount × `10^19`).

These normalized values (`x1`, `y1`, and the previously stored `target.calc_pnl_x` / `calc_pnl_y`) are fed into `calc_take_pnl`, which calls `calc_x_power(last_x, last_y, current_x, current_y)`:
```
last_x.checked_mul(last_y).unwrap().checked_mul(current_x).unwrap().checked_div(current_y).unwrap()
``` [5](#0-4) 
With each operand potentially close to `U128::MAX` (~3.4e38), the product of three such values (~1e77-1e114) can exceed `U256::MAX` (~1.15e77), causing `checked_mul` to return `None` and the subsequent `.unwrap()` to panic. This code path is reached by `process_deposit`, `process_withdraw`, and `process_withdrawpnl` — all callable by ordinary users/LPs. [6](#0-5) [7](#0-6) [8](#0-7) 

Because `total_pc_without_take_pnl` / `total_coin_without_take_pnl` (derived from live vault balances) and `target_orders.calc_pnl_x` / `calc_pnl_y` (persisted state that only grows/updates through deposits/withdrawals) are structurally intertwined, once the pool's normalized values reach the overflow threshold, **every future** `Deposit`, `Withdraw`, and `WithdrawPnl` call for that pool will panic and abort, since `calc_take_pnl` is unconditionally invoked in all three code paths.

### Impact Explanation
A panic inside `calc_take_pnl` causes the enclosing transaction to fail. Since this function is called unconditionally on `Deposit`, `Withdraw`, and `WithdrawPnl`, once the overflow condition is reached there is no way for LPs to withdraw their liquidity or for the protocol to withdraw accrued PNL — this is a permanent freeze of LP funds and pool PNL, satisfying the "permanent freezing of user or LP funds" bar. Swap instructions do not call `calc_take_pnl` (they use `calc_total_without_take_pnl_no_orderbook` and `swap_token_amount_base_in/out` directly), so swapping may remain possible, but exit paths (Deposit/Withdraw/WithdrawPnl) for that pool are bricked.

### Likelihood Explanation
Triggering this requires an adversarial or careless pool creator to mint tokens with an extreme decimals mismatch (e.g., 0 vs 19) and to grow vault balances (via large deposits, which is a normal permitted action) until normalized values approach `U128::MAX`. This is a large but not impossible value range on Solana, since SPL mints can be created with arbitrary decimals up to 255 (and `10^decimals` for `u64` sys_decimal_value is only checked to not overflow `u64` itself, capping decimals at ≤19, still large enough to produce this overflow). There is no validation in `process_initialize2` bounding `coin_decimals`/`pc_decimals` to safer values, so a pool creator (an explicitly in-scope actor) can set up the preconditions in a single `Initialize2` call, then reach the overflow via subsequent large `Deposit` calls.

### Recommendation
- Bound `coin_decimals`/`pc_decimals` accepted in `AmmInfo::initialize`/`process_initialize2` to conservative values (e.g., ≤9), consistent with real-world SPL token norms, to prevent `sys_decimal_value` and normalized values from approaching the upper bounds of their integer types.
- Replace `.unwrap()` in `Calculator::calc_x_power` (and `normalize_decimal_v2`/`restore_decimal`) with proper `ok_or(AmmError::...)` propagation so any overflow condition returns a controlled program error rather than panicking, and ideally add an alternate calculation path (e.g., dividing before multiplying, or using intermediate scaling) that avoids needing the full triple-product magnitude in `U256`.
- Add regression tests exercising pools with maximal decimal skew and near-`u64::MAX` vault balances to ensure the pnl/deposit/withdraw paths behave predictably instead of panicking.

### Proof of Concept
1. Pool creator calls `Initialize2` with `coin_mint.decimals = 0` and `pc_mint.decimals = 19`, so `sys_decimal_value = 10^19` per `AmmInfo::initialize`. [3](#0-2) 
2. Creator (or subsequent LPs) repeatedly calls `Deposit` to grow `coin_vault.amount` toward `u64::MAX`. Each `Deposit` calls `Calculator::normalize_decimal_v2(coin_amount, coin_decimals=0, sys_decimal_value=10^19)`, producing a normalized `y1` value approaching `coin_amount * 10^19` (up to ~1.8e38, near `U128::MAX`). [4](#0-3) 
3. On a subsequent `Deposit`/`Withdraw`/`WithdrawPnl` call, `Processor::calc_take_pnl` is invoked with these large `x1`/`y1` values along with the persisted `target_orders.calc_pnl_x`/`calc_pnl_y` of similar magnitude. [2](#0-1) 
4. Inside `calc_take_pnl`, `Calculator::calc_x_power(target.calc_pnl_x, target.calc_pnl_y, x1, y1)` computes `last_x * last_y * current_x`, whose magnitude (product of three ~1e38 values ≈ 1e114) exceeds `U256::MAX` (~1.15e77), causing `checked_mul(...).unwrap()` to panic and abort the transaction. [5](#0-4) 
5. Because every `Deposit`, `Withdraw`, and `WithdrawPnl` for this pool unconditionally calls `calc_take_pnl`, the pool becomes permanently unable to process withdrawals or PNL collection, freezing all LP funds in the pool.

Note: I was not able to execute this scenario end-to-end (no test harness/runtime access in this environment) to empirically confirm the exact numeric threshold at which the overflow triggers; the analysis is based on static bounds of the integer types involved (`u64`, `U128`, `U256`) and the code paths shown above.

    pub fn calc_x_power(last_x: U256, last_y: U256, current_x: U256, current_y: U256) -> U256 {
        // must be use u256, because u128 may be overflow
        let x_power = last_x
            .checked_mul(last_y)
            .unwrap()
            .checked_mul(current_x)
            .unwrap()
            .checked_div(current_y)
            .unwrap();
        x_power
    }
