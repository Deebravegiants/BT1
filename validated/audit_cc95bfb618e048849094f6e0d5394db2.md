### Title
Webhook shop identity spoofing via unauthenticated `Shop-Domain` header not covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an inbound webhook entirely from the `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `Registry.process` validates covers only the raw request body. Because the shop identifier is not bound to the signature, any bytes that produced a validly-signed body for one shop can be replayed with a forged `shop-domain` header naming a different shop that shares the same app (and therefore the same `api_secret_key`), and `Registry.process` will accept it as authentic for the spoofed shop.

### Finding Description
`Registry.process` authenticates a webhook solely via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` computes/verifies the HMAC exclusively over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [3](#0-2) 

Yet `shop` (and `topic`, `webhook_id`, `api_version`) are read directly from HTTP headers that are never included in the signed bytes: [4](#0-3) 

`Registry.process` then uses this unauthenticated `request.shop` value as the tenant identity passed to the app's handler: [1](#0-0) 

This breaks the equality that should hold: `shop bound by the HMAC signature == shop the handler acts upon`. Instead, only `raw_body == raw_body` is verified; `shop-domain header` is free for an attacker to set to any value. Since Shopify apps share one `client_secret` (`api_secret_key`) across all shops that install them, an attacker who controls their own shop installation of a multi-tenant app can obtain a validly-HMAC-signed webhook body (by triggering any webhook delivery to their own endpoint, or via the app's own webhook subscription), then replay that same body+HMAC to the victim app's webhook endpoint while substituting an arbitrary victim `shop-domain` header. The signature check passes because it never covered the header, and the handler executes with `WebhookMetadata#shop` set to the attacker-chosen victim shop.

### Impact Explanation
This is a cross-tenant identity binding bypass: an unprivileged holder of one shop's webhook traffic (which the attacker owns) can impersonate any other shop known to the same app for webhook processing purposes. Depending on the handler logic (e.g., `shop/redact`, `app/uninstalled`, `customers/data_request`, or custom fulfillment/order handlers keyed by `shop`), this enables cross-tenant data corruption, unauthorized data deletion/redaction, or state confusion attributed to a victim merchant — matching the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own legitimate installation of the target app on any shop (to obtain one validly-signed body/HMAC pair), and (2) the ability to send an arbitrary HTTP request to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header — both are unprivileged, internet-reachable actions requiring no access token, `api_secret_key`, or social engineering.

### Recommendation
Bind the shop (and topic/webhook_id) into the signed material, or otherwise cryptographically tie the header-derived shop to the signature — e.g., require `to_signable_string` to include the shop domain header value (matching Shopify's documented practice of verifying `X-Shopify-Shop-Domain` against the resolved/expected shop for that endpoint) rather than trusting it as a bare unauthenticated header. At minimum, document and enforce that consuming apps must independently verify `request.shop` corresponds to a shop with an active, expected installation before acting on the webhook payload.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and receives (or triggers) a legitimate webhook delivery, capturing `raw_body` and the `X-Shopify-Hmac-Sha256` header Shopify computed with the app's shared `client_secret`.
2. Attacker sends this exact `raw_body` and `hmac` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the forged header [4](#0-3) .
4. `Utils::HmacValidator.validate` verifies successfully because it only checks `raw_body` [5](#0-4)  against `to_signable_string` [3](#0-2) .
5. `Registry.process` invokes the handler with `shop: request.shop` = `"victim.myshopify.com"` [1](#0-0) , causing the app to act on behalf of the victim shop using attacker-supplied body content.
