### Title
Unbounded message-batch loop in `pallet-ismp::handle_unsigned` allows a free unsigned extrinsic to exceed block weight and DoS message delivery - ([File: modules/pallets/ismp/src/lib.rs])

### Summary
The reported bug (`DyadXPv2.initialize()`) is an unbounded `for` loop whose iteration count is driven by external, ever-growing state, causing the call to exceed the block gas limit and become permanently un-callable. The same root cause — a loop whose length is controlled by data an unprivileged caller supplies in a single dispatched call, with no explicit cap — is reachable in Hyperbridge's core message-dispatch path: `pallet_ismp::Pallet::handle_unsigned`.

### Finding Description
`handle_unsigned` is a permissionless (`ensure_none`), unsigned, fee-free extrinsic that accepts an arbitrary `Vec<Message>` and immediately calls `Self::execute(messages.clone())`: [1](#0-0) 

Each `Message` variant itself wraps another attacker-controlled `Vec` (`RequestMessage.requests`, `ResponseMessage.requests`, `PostRequestTimeoutMessage`/`GetTimeoutMessage.timeouts`, etc.), and the handlers for these iterate over the full length of that vector with no upper bound enforced anywhere in the pallet or in `ismp-core`: [2](#0-1) [3](#0-2) 

Critically, `pallet_ismp`'s `ValidateUnsigned::validate_unsigned` does not do a cheap, size-independent check before admitting the transaction to the pool — it runs the *entire* `Self::execute(messages.clone())` (the same unbounded loops shown above) synchronously during mempool validation: [4](#0-3) 

The dispatch call is annotated with a call-level `#[pallet::weight(weight())]` rather than a weight computed from `messages.len()` / the size of each embedded `requests`/`timeouts` vector, so the declared weight does not scale with the actual number of loop iterations the call (and its mempool-validation twin) will perform. Combined with `handle_unsigned` costing the caller nothing (it is unsigned and free — by design, per the pallet's own documentation: "all cross-chain messages received are executed for free as unsigned transactions"), an attacker can submit a single extrinsic carrying a very large `Vec<Message>` (or one `Message` with a very large inner request/response/timeout array). Because signature/proof checks for a batch are amortized (one membership proof covers the whole batch, per `state_machine.verify_membership(host, commitments, state, &msg.proof)`), an attacker only needs one valid membership proof over a huge synthetic set of leaves to make the per-request loop body (module lookup, receipt read/write, callback dispatch) run tens of thousands of times, both during `validate_unsigned` (mempool) and, if it slips through the pool's block-weight accounting, during actual block execution.

This mirrors the reported class exactly: an externally-reachable entry point iterates over a collection whose size the caller controls, with no bound, so the real gas/weight cost is not the cost the runtime assumes it is going to be.

### Impact Explanation
If the batch is large enough that its true execution weight exceeds the block's weight/proof-size limit, the extrinsic can never be successfully included — but because `validate_unsigned` fully executes the messages before that block-inclusion weight check ever applies, the cost is instead paid by every collator/validator that re-validates the extrinsic in its transaction pool, for free, repeatedly, with no signer to slash or fee to charge. This can be used to (a) grief collators (excess unpaid computation per validation pass) and (b) construct message batches that pass proof/logic validation but can never actually be included in a block because their true weight exceeds the block limit, i.e., a "route unable to deliver messages" condition for the requests bundled in that oversized batch — directly matching the accepted impact criteria (route unable to deliver messages / unpaid computation DoS surface), which is a Medium-severity finding analogous to the original.

### Likelihood Explanation
High. Nothing beyond crafting a batch (or a single `RequestMessage`/`ResponseMessage`/timeout message with an inflated inner vector) plus one valid MMR/state proof covering that batch is required. `dedup_requests` prevents trivial identical-copy padding but does not cap the *number* of distinct entries, so an attacker who controls or replays enough distinct historical requests/responses (or crafts them) can still build an arbitrarily large, individually-valid batch. The call is explicitly unsigned/free and reachable by anyone submitting to the network.

### Recommendation
- Enforce an explicit, governance-configurable maximum on `messages.len()` in `handle_unsigned`, and on the length of each embedded `requests`/`timeouts` vector inside `RequestMessage`, `ResponseMessage`, `TimeoutMessage`, and `GetRequestsWithProof`, rejecting oversized batches before any proof verification or loop processing begins (both in `pre_dispatch`/`validate_unsigned` and in `execute`).
- Make the declared `#[pallet::weight(...)]` for `handle_unsigned` a function of the actual batch size (as is already done in `WeightFeeHandler::on_executed`, which sums weights, but this happens *after* validation/execution, too late to bound cost) so `CheckWeight`/block-weight accounting can reject over-large batches before `validate_unsigned` fully executes them.
- Consider cheapening `validate_unsigned` for pallet-ismp so it doesn't need to run the full `execute()` (including all per-request callback dispatch) just to admit a transaction to the pool, mirroring the size/complexity check that `pallet-call-decompressor` and the EVM `HandlerV2` batch handlers perform up front.

### Proof of Concept
No PoC was executed (Ask-only mode, no filesystem/terminal access). A Devin agent with test-environment access could reproduce this analogous to the original report by:
1. Standing up `pallet_ismp` in the existing test runtime (`modules/pallets/testsuite`).
2. Constructing a `RequestMessage` (or `Vec<Message>`) whose `requests` vector contains a large number (e.g., several thousand) of distinct valid `PostRequest`s covered by one MMR/membership proof.
3. Measuring the weight/time consumed by `ValidateUnsigned::validate_unsigned` and `Pallet::execute` for this batch versus the statically declared `weight()` for `handle_unsigned`, and checking whether it exceeds the runtime's configured block weight limit while `pre_dispatch` still returns `Ok(())`.
