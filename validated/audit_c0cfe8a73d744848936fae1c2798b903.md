### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before dispatching to the app's handler, but the HMAC signature it validates only covers the raw request body. The `shop` field — which the app uses to identify which tenant/store the webhook event belongs to — is taken from an unauthenticated HTTP header and is never bound to the signature.

### Finding Description
`Registry.process` gates webhook handling entirely on `Utils::HmacValidator.validate(request)`: [1](#0-0) 

The HMAC is computed and verified only over `to_signable_string`, which returns the raw body, not any header: [2](#0-1) 

Meanwhile, `shop` (along with `topic`, `webhook_id`, `api_version`) is read directly from an HTTP header with no cryptographic binding to the signed payload: [3](#0-2) 

That unauthenticated `shop` value is what gets forwarded to the app-supplied handler as the tenant identifier for the event: [4](#0-3) [5](#0-4) 

The documented contract explicitly tells integrators that `process` verifies Shopify origin and that `data.shop` is "The shop domain of the webhook," implying it is a trusted, authenticated value: [6](#0-5) [7](#0-6) 

The broken identity binding, stated as an equality that should hold but doesn't:
`shop authenticated by HMAC == shop delivered to handler` — the right-hand side is attacker-controllable via the `x-shopify-shop-domain`/`shopify-shop-domain` header, while the left-hand side (the HMAC) never touches that header at all.

### Impact Explanation
Since a single app installation uses one `client_secret`/`api_secret_key` to sign webhooks for *every* shop that installs it, any attacker who has installed the app on their own (attacker-controlled) shop can capture a genuine, validly-signed `(body, hmac)` pair generated by Shopify for their own store. Because the signature never covers the `shop-domain` header, the attacker can replay that same valid body+HMAC to the app's webhook endpoint while substituting the `shop-domain` header for a victim tenant. `HmacValidator.validate` will still pass (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event originates from the victim shop. Any app logic that trusts `data.shop` for tenant-scoped actions (writing to the victim's records, triggering emails/notifications, updating cached per-shop data, invoking privileged per-tenant operations) can be manipulated into acting on/for the wrong tenant — a cross-tenant data-confusion vector achieved without ever needing the victim's access token, session, or the app's `client_secret`.

### Likelihood Explanation
Any developer who installs the target app on a store they control (a normal, unprivileged action available to any Shopify merchant) can obtain a legitimately-signed webhook body/HMAC pair for arbitrary registered topics, then freely forge the `shop-domain` header on replay. No secret material or elevated privilege is required beyond installing the app once, which is the same barrier any legitimate customer of the app would cross.

### Recommendation
Bind the shop (and ideally topic/webhook_id/api_version) to the HMAC verification, e.g. include the relevant headers in the signed payload used for validation, or require the caller to additionally verify that the resolved `shop` matches an app-tracked, previously-authenticated tenant for that specific webhook subscription (e.g. cross-check against the shop associated with the `webhook_id` at registration time) before invoking the handler. At minimum, update documentation to clarify that `data.shop` is unauthenticated and must not be trusted for tenant-scoping decisions without additional verification by the integrating application.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, obtaining webhook deliveries signed with the app's shared `api_secret_key`.
2. Attacker registers/receives a webhook (e.g., `orders/create`) and captures the exact `raw_body` and its `x-shopify-hmac-sha256` value — this pair is validly signed per `Utils::HmacValidator.validate_signature`: [8](#0-7) 
3. Attacker POSTs this captured body with the same HMAC header to the app's public webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `Registry.process` verifies the HMAC (passes, since only the body is checked) and invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though the payload never originated from or for that shop: [4](#0-3) 
5. Any app logic keyed on `data.shop` now operates under the false belief that this event is authentic for `victim-shop.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
