### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC solely against that body/secret pair. The `shop` identity (taken from the `X-Shopify-Shop-Domain` header) is never included in the signed content, yet it is trusted downstream as the tenant identifier for the webhook payload.

### Finding Description
`Request#hmac` and `Request#to_signable_string` bind the signature only to `@raw_body`: [1](#0-0) . The `shop` accessor simply reads the unauthenticated `shop-domain` header with no cryptographic tie to the signature: [2](#0-1) .

`Registry.process` validates the HMAC and, once it passes, forwards `request.shop` unchanged to the app's webhook handler as the tenant identity for the delivered payload: [3](#0-2) .

The identity binding that should hold is:
`shop header used by handler == shop that Shopify actually signed the body for`

Because `shop-domain` is outside `to_signable_string`, this equality is never enforced by `HmacValidator.validate`: [4](#0-3) . Any bytes on the wire pass validation as long as `raw_body` and `hmac` match — the `shop` header can be swapped for a different value without invalidating the signature.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged internet user who is able to legitimately install the app on their own shop (self-serve/public app install, no special privilege required) will receive genuine webhook deliveries — each a valid `(raw_body, hmac)` pair signed with the app's `client_secret`. Because `shop-domain` is not part of the signed content, that same attacker can replay the identical `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header (e.g., a victim tenant's domain). `HmacValidator.validate` still succeeds (it only checks body vs. secret), and `Registry.process` hands the app's handler a `WebhookMetadata` claiming to be from the victim shop: [5](#0-4) . Any app logic that uses this `shop` value to select tenant records, provision, deprovision, or route business-critical webhook effects (e.g., `shop/redact`, `app/uninstalled`, order/inventory updates) can be tricked into acting on/for the wrong tenant — a cross-tenant access/data-integrity break.

### Likelihood Explanation
Moderate-to-high: it requires the attacker to have received at least one legitimately signed webhook from Shopify (trivial for any public app that can be self-installed), and the ability to POST directly to the app's public webhook endpoint with modified headers (which is exactly how the endpoint is designed to be reached, per `Request.new(raw_body:, headers:)`). No `api_secret_key`, access token, or privileged account is needed — only observation of one's own legitimate webhook traffic.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed content, or otherwise cryptographically bind the `shop-domain` header value to the verified payload before it is handed to the handler, rather than trusting an unauthenticated header field as tenant identity.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com` (a normal, unprivileged self-serve install).
2. Capture a legitimate webhook delivery: raw body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` and the app's secret), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Replay the request to the app's public webhook endpoint with the same body `B` and header `H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [6](#0-5) .
5. `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` even though the payload/HMAC never originated for that shop [5](#0-4) .
