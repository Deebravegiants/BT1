## Title
Webhook HMAC Validates Only the Request Body While `shop`, `topic`, and Other Identity Headers Are Unauthenticated, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` proves nothing more than "this body was HMAC-signed with the app's shared `api_secret_key`." The `shop`, `topic`, `api_version`, and `webhook_id` values — all read from unauthenticated HTTP headers — are handed directly to the host application's handler via `WebhookMetadata` without ever being covered by the signature. Because Shopify uses a single `api_secret_key` per app (not per shop), any merchant who installs the app on their own store can capture a validly-signed `(body, hmac)` pair from their own webhook deliveries and replay it to the app's webhook endpoint with a forged `shop-domain` (and/or `topic`) header naming a different, victim shop. The signature still validates, and the handler processes the request as if it legitimately originated from the victim shop.

### Finding Description
The identity binding that should hold is:
`shop_that_produced_the_valid_HMAC == shop_the_handler_trusts_and_acts_on`

In this gem that equality is broken:

- `Request#to_signable_string` signs only `@raw_body`: [1](#0-0) 
- `Request#shop`, `#topic`, `#api_version`, `#webhook_id` are all pulled straight from HTTP headers, never included in the signed string: [2](#0-1) 
- `Registry.process` validates only the HMAC of the body and then trusts the header-derived `request.shop`/`request.topic` to route and construct `WebhookMetadata` passed to the app's handler: [3](#0-2) 
- `HmacValidator.validate` calls `verifiable_query.to_signable_string`, which for webhook requests is just the raw body — the shop/topic headers are outside the signed material: [4](#0-3) 

Because the app's `api_secret_key` (see `Context.api_secret_key` used above) is shared across all shops that install the app — it is not a per-shop secret — a signature computed for a webhook delivered to shop A is cryptographically indistinguishable from a signature for the same body content delivered to shop B. An attacker who legitimately installs the app on a shop they control (any unprivileged internet user with a Shopify dev/trial store) can:

1. Trigger a real webhook delivery to their app endpoint (e.g. `orders/create`, `app/uninstalled`, `customers/data_request`) and capture the raw body + `x-shopify-hmac-sha256` value.
2. Replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint, but substitute the `x-shopify-shop-domain` header with a target/victim shop's domain (and optionally change `x-shopify-topic`).
3. `Utils::HmacValidator.validate` still returns `true` because it only checks `raw_body` against the shared secret — the substituted `shop`/`topic` headers are never covered.
4. `Registry.process` looks up the handler by the (attacker-controlled) `topic` header and calls it with `shop: request.shop` set to the victim's domain, i.e., `WebhookMetadata` reports the victim shop even though the payload was generated by, and signed for, the attacker's own store.

The test suite documents this exact behavior: the same `hmac`/body is reused across `x-shopify-` and `shopify-` header formats without shop binding, and a `test_process_hmac_validation_fails` test only exercises the case of an invalid hmac string, never a case where the hmac is valid for the body but the shop header is inconsistent with it: [5](#0-4) 

### Impact Explanation
This crosses a tenant boundary: an unprivileged app installer (attacker) can cause the host application to process attacker-supplied webhook data under the identity of an arbitrary victim shop domain (as long as they know or guess it — `myshopify.com` subdomains are frequently discoverable/public). Depending on how the host app's webhook handlers use `WebhookMetadata#shop` (e.g., to update stored session data, mark a shop as uninstalled and purge its access token, respond to GDPR `customers/redact` or `shop/redact` mandatory webhooks, or otherwise mutate per-shop state keyed only by the `shop` string), this can lead to cross-tenant data corruption, forced session/token invalidation for a victim shop, or spoofed mandatory-compliance webhooks — all without possessing the victim's access token or any privileged credential. This matches the "cross-tenant access" class under Critical impact.

### Likelihood Explanation
Likelihood is High: exploitation requires only that the attacker be able to install the target app on a store they control (a normal, unprivileged capability for any Shopify app that is publicly installable, including free development stores) and send a crafted HTTP POST with a substituted header to the app's public webhook endpoint. No access token, `client_secret`, or other privileged credential is needed — only knowledge of the app's public webhook URL and a guessed/known victim shop domain.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header into the material that is HMAC-verified, or otherwise cryptographically tie the header claims to the signed body (e.g., require the host app to independently confirm that `request.shop` matches a shop for which a session/access token was already established via OAuth/token-exchange before trusting the webhook). At minimum, document prominently that `Utils::HmacValidator.validate` for webhooks authenticates the body only and that consuming applications must not treat `WebhookMetadata#shop` as an authenticated field.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a benign webhook (e.g. by creating an order), capturing:
   - raw body `B`
   - header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared `Context.api_secret_key`)
2. Attacker sends:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: H
x-shopify-shop-domain: victim-shop.myshopify.com
x-shopify-webhook-id: attacker-chosen-id

B
```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `H` against `B` — this succeeds because the header substitution did not change `B`: [6](#0-5) 
4. The registered handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, believing the (attacker-controlled) payload legitimately originated from `victim-shop.myshopify.com`.
