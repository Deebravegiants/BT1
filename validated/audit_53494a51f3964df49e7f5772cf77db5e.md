### Title
Signup Outcome (`SignupReason`) Sent Unsigned Alongside a Signature That Doesn't Bind It, Allowing Tampering To Bypass On-Device Fraud/Liveness Detection - (File: src/plans/enroll_user.rs, src/backend/signup_post.rs)

### Summary
The TSS report's root cause is that the data needed to credit/settle an action (the slashing report) contained nothing unique to the legitimate submitter, so the message could be copied and resubmitted by someone else, decoupling the cryptographically-meaningful payload from the field the backend used to make its decision (`msg.sender`). The same *structural* flaw exists in orb-core's signup submission: the on-device signature (`make_signature`) binds only the user id and iris code/version bytes, but the multipart form field that actually tells the backend the on-device fraud/liveness verdict (`signup_reason` / `reason`) is sent as a separate, unsigned form field. Anyone able to alter the outbound request before it reaches the backend can change that field without invalidating the signature, exactly as in the TSS bug where the reward-critical field was decoupled from any authenticated, sender-unique data.

### Finding Description
`make_signature` computes a SHA-256 digest and signs it with the secure element: [1](#0-0) 

The digest covers `ORB_ID`, `user_qr_code.user_id`, and the iris/mask codes and versions for both eyes — nothing else. It notably excludes:
- `signup_reason` (Normal / Failure / Fraud) — the exact field that reflects whether the orb's own fraud/liveness pipeline flagged the capture,
- `signup_id`,
- `distributorId` / `region` / GPS coordinates.

That signature is then attached to the multipart form built in `signup_post::request`, where `reason` is inserted as a plain, unsigned text field alongside it: [2](#0-1) 

The reason is computed earlier in the flow based on the fraud-detection result and pipeline availability: [3](#0-2) 

and is later used by `report_signup_reason` purely for local telemetry/UI bookkeeping — the actual enrollment decision travels to the backend inside this same unsigned `reason` field: [4](#0-3) 

Because the signature does not cover `reason`, the cryptographic proof-of-authenticity ("this iris data really came from this orb+user capture") and the enrollment-outcome field are decoupled — mirroring the TSS pattern where the slashing payload lacked any binding to the entity that should be credited, letting a third party swap in different attribution data while keeping the same underlying claim valid. Here, an entity with access to the outbound request (e.g., a compromised proxy, debug tooling, or any component sitting between orb-core and the HTTPS client boundary) can substitute `reason=FRAUD` with `reason=NORMAL` (or vice versa) without breaking the SHA-256/secure-element signature, since that signature never included the reason field to begin with.

### Impact Explanation
If the `reason` field can be altered post-signature, the backend's enrollment path can be forced to treat a signup that the orb's own fraud/liveness pipeline flagged (`SignupReason::Fraud`) as a normal, successful signup (`SignupReason::Normal`), or vice versa. This is a concrete fraud/liveness-bypass and misattributed-signup impact: the cryptographic attestation that should tie the biometric payload to a specific, verified outcome is incomplete, so the "verified" claim (iris data is authentic) and the "trusted" claim (this signup passed fraud/liveness checks) are not jointly authenticated. Since `enroll_user::Plan::run` and the backend rely on this reason field to decide enrollment success/failure, an unauthorized enrollment can be produced despite the orb having internally detected fraud.

### Likelihood Explanation
Exploitation requires interception/modification of the outbound signup POST prior to backend verification (e.g., abuse of debug/proxy tooling, a compromised intermediary, or any code path that can touch the request after signing but before transmission). The application uses `orb_security_utils::reqwest::http_client_builder()` over HTTPS, which limits pure network-path MITM without additional compromise, but the root cause is architectural: the signature was never designed to cover the reason field, so likelihood depends entirely on gaining any write access to the request between signing and transmission — a lower bar than defeating TLS outright, and directly analogous to the "copy and resubmit" primitive in the original TSS bug.

### Recommendation
Include `signup_reason` (and ideally `signup_id`) inside the SHA-256 digest signed in `make_signature`, so the backend can verify that the reported enrollment outcome is the exact one attested by the secure element at capture time, not a value that can be altered independently of the biometric payload it travels with.

### Proof of Concept
1. Orb performs a capture; on-device fraud detection flags fraud, setting `signup_reason = SignupReason::Fraud` at `src/plans/mod.rs:567-571`.
2. `enroll_user::Plan::run` computes `signature = make_signature(&user_qr_code, &pipeline)` (`src/plans/enroll_user.rs:74-89`), which hashes only `ORB_ID`, `user_id`, and iris/mask codes — not `signup_reason`.
3. `signup_post::request` builds the multipart form with the valid `signature` field and a separate `reason` field set to `"FRAUD"` (`src/backend/signup_post.rs:125-133`).
4. An entity with write access to this outbound request (e.g., intercepting proxy/debug tooling) changes the `reason` field from `"FRAUD"` to `"NORMAL"` before it leaves the device/network boundary.
5. The `signature` field remains valid (it never covered `reason`), so backend-side signature verification of the iris payload succeeds, and the backend processes the signup as `SignupReason::Normal`, resulting in an unauthorized/misattributed successful enrollment despite the orb's own fraud detection having flagged it.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}

        if signup_reason == SignupReason::Failure {
            tracing::info!("User enrollment failed due to a failure in the pipeline");

            tracing::info!("User enrollment failed due to fraud");
            debug_report.signup_fraud();
