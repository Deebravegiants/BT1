### Title
Webhook shop/topic/webhook-id headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw JSON body, while `ShopifyAPI::Utils::HmacValidator.validate` computes/verifies the HMAC exclusively over that string. The `shop`, `topic`, `webhook_id`, and `api_version` values — all taken from HTTP headers and passed unverified into `WebhookMetadata` for handler processing — are never included in the signed material.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
returning `@raw_body` only. `HmacValidator.validate_signature` computes the HMAC over exactly that string and compares it to the `hmac-sha256` header: [2](#0-1) 

Meanwhile, `Registry.process` trusts `request.topic`, `request.shop`, and `request.webhook_id` to route and label the payload for the handler: [3](#0-2) 

and those accessors read straight from unauthenticated headers: [4](#0-3) 

The identity binding broken is: **bytes verified (raw body only) ≠ bytes/fields acted on (body + shop + topic + webhook_id headers)**. Because the header values are outside the HMAC's scope, any party capable of relaying or re-presenting a validly-signed body (e.g., a proxy, a shared/multi-tenant receiving endpoint, or a request-forwarding bug in the host app) can attach a different `x-shopify-shop-domain` (or `x-shopify-topic`/`webhook-id`) header without invalidating the signature check, since `HmacValidator.validate` only ever re-hashes `@raw_body`.

### Impact Explanation
This breaks the shop-authenticated-vs-shop-acted-on binding: `Registry.process` will accept the forged headers as authentic and hand `WebhookMetadata` with an attacker-chosen `shop` to the app's handler, `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))`. In multi-tenant host applications that key data storage/side effects off `data.shop` (as intended by this gem's design, see `docs/usage/webhooks.md`), this enables cross-tenant data confusion — data legitimately signed for shop A being attributed to shop B — meeting the Critical "cross-tenant access" bar, since the gem itself provides no binding between the verified bytes and the tenant identifier it hands to the app.

### Likelihood Explanation
Exploitation requires the attacker to control or influence the headers reaching `ShopifyAPI::Webhooks::Request.new` for an otherwise-valid signed body (e.g., a header-rewriting proxy in front of the webhook endpoint, or any component between Shopify and the app that does not itself pin the header set to the signed payload). This is a real but non-trivial precondition, not merely a host-app documentation-ignoring issue — it stems directly from the gem's own signable-string implementation omitting header fields that are otherwise treated as authenticated.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` (or otherwise validate that the app-derived shop matches the shop implied by the merchant's registered webhook subscription) within the signed material check, or validate the `shop` header against a trusted list of shop identifiers registered by the app before dispatching to the handler.

### Proof of Concept
1. Capture a legitimate Shopify webhook request `POST /webhooks` with body `B` and a valid `x-shopify-hmac-sha256` computed over `B` for shop A, `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Replay/forward the same body `B` and the same valid HMAC header, but alter `x-shopify-shop-domain` to `shop-b.myshopify.com` (and/or a different `x-shopify-webhook-id`).
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` still returns `true` because `to_signable_string` only reads `@raw_body`, which is unchanged. [1](#0-0) 
4. `Registry.process` proceeds and invokes the handler with `WebhookMetadata` carrying `shop: "shop-b.myshopify.com"`, misattributing shop A's webhook body to shop B. [3](#0-2)
