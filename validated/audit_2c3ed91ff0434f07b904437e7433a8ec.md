### Title
Cross-chain replay of `SubstrateCalldata` signatures in `pallet-hyper-fungible-token` due to missing chain/domain binding - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet-hyper-fungible-token` is deployed on multiple Substrate runtimes in this monorepo (both `parachain/runtimes/gargantua` and `parachain/runtimes/nexus`), and lets a cross-chain HFT transfer carry optional `SubstrateCalldata` that is dispatched as `RawOrigin::Signed(beneficiary)` when the recipient's signature verifies. The signed payload is only `(account_nonce, runtime_call)` — it contains no chain/network identifier, no reference to the specific pallet instance, no source-chain binding, and no "action" discriminator. This is exactly the class of gap the external ChainPort report calls out: a signed authorization that is not bound to a `networkId`/domain can be replayed on a different chain that shares the same nonce/account state and call encoding.

### Finding Description
In `on_accept` [1](#0-0) , when incoming HFT calldata carries a `signature`, the pallet builds the signed message as:

```rust
let nonce = frame_system::Pallet::<T>::account_nonce(beneficiary.clone());
let payload = (nonce, substrate_data.runtime_call.clone()).encode();
``` [2](#0-1) 

For ECDSA it further wraps this in the generic Ethereum personal-sign prefix with no other domain data [3](#0-2) . None of the three signature branches (Ed25519, Sr25519, Ecdsa) include:
- a chain/genesis identifier or `StateMachine` (source or destination),
- the pallet's module id (`PALLET_ID`) or the specific asset/contract this transfer targets,
- any "action" tag distinguishing this dispatch context from any other signer-controlled payload.

Only `account_nonce` and `runtime_call` bind the signature, and the nonce is incremented only after a successful dispatch on that specific chain [4](#0-3) . Documentation confirms replay protection is claimed to rely solely on this nonce increment, with no chain-domain separation mentioned: "If a signature is provided, it is verified against the beneficiary's account nonce and the runtime call before dispatch... The account nonce is incremented after dispatch to prevent replay." [5](#0-4) 

Because the pallet is wired into more than one runtime in the same codebase (`gargantua` and `nexus`, both referencing `pallet_hyper_fungible_token::PALLET_ID`), an account that shares the same public key across chains (a routine setup for ECDSA-derived accounts, and possible for Ed25519/Sr25519 keys reused by convenience) and that has the same `frame_system` nonce on both chains can have a single signed `SubstrateCalldata` payload replayed as a valid `Signed` dispatch on the other chain, as long as the SCALE-encoded `runtime_call` bytes also happen to decode to a valid call there (which is plausible for common pallets like `pallet-balances::transfer` if call indices align, since these runtimes share pallet dependencies). This mirrors the ChainPort issue precisely: the payload lacks a `networkId`-equivalent field, so a signature crafted for one chain can be replayed on another chain running the identical module.

### Impact Explanation
A successful replay causes `runtime_call.dispatch(RawOrigin::Signed(beneficiary))` to execute an unintended, previously-authorized call against the beneficiary's account on a different chain than the signer intended [6](#0-5) . Depending on the call encoded (e.g., an asset transfer, an approval, a governance vote, or any call reachable via `BaseCallFilter`), this is an unauthorized app action executed under the victim's signed origin without their consent on that specific chain — a forged-authorization / unauthorized-action class impact reachable purely by a token bridger submitting an HFT cross-chain transfer with attacker-supplied `call_data` containing a previously-observed signature (e.g., harvested from a legitimate transfer on the sibling chain).

### Likelihood Explanation
Triggering requires: (1) the same account (same public key with matching nonce) exists and is meaningfully funded/privileged on both HFT-integrated chains, and (2) the raw SCALE-encoded `runtime_call` bytes are valid on both chains (true for calls from pallets shared across the two runtimes with the same call indices, which is likely for common infra pallets in a single-team monorepo). This is a real but conditional replay risk rather than a universally-triggerable exploit, since it depends on cross-chain account/nonce/call-encoding overlap that an attacker cannot always control, but can observe and target. It is nonetheless a documented protocol design gap: the signing scheme provides no cryptographic chain separation at all, unlike EIP-712-style domains, so any future addition of another HFT-integrated chain, or any account reuse pattern among users, silently reintroduces this exposure.

### Recommendation
Bind the signed payload to a chain- and pallet-specific domain, mirroring the ChainPort recommendation: include the `StateMachine`/genesis hash of the destination chain, the HFT `PALLET_ID`, and ideally the source chain and/or an explicit "action" discriminator (e.g., a fixed context string like `b"hft-calldata-v1"`) in the signed message, in addition to `(nonce, runtime_call)`. Document explicitly what properties the signature is intended to provide (non-repudiation of a specific call on a specific chain) and why each field is required, so this scheme cannot silently degrade if the pallet is deployed to additional chains.

### Proof of Concept
Conceptual PoC (not executed, since this requires two live runtime instances):
1. Deploy `pallet-hyper-fungible-token` on both `gargantua` and `nexus` runtimes (as the code already does), registering the same token/contract mapping on both.
2. A user with account `A` (nonce = `N` on both chains) signs `SubstrateCalldata { signature: Some(sig over keccak256((N, call).encode())), runtime_call: call_bytes }` intending it to execute on chain `gargantua` only, embedded in an HFT `send` call.
3. An attacker who observes this signed payload (e.g., from a public mempool/indexer) re-submits an HFT cross-chain transfer to `nexus` carrying the identical `SubstrateCalldata` bytes, targeting the same beneficiary account which also has nonce `N` on `nexus`.
4. `on_accept` on `nexus` verifies the signature successfully (no chain-binding field to reject it) and dispatches `call_bytes` under `RawOrigin::Signed(A)` on `nexus`, executing an action the user never authorized on that chain.
