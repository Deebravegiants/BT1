### Title
Unvalidated route venues let a payload-named contract drain the signer's wallet beneath the strategy auth tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The DataImportHandler UNC-path flaw is a bug class where an attacker-supplied value is used, unvalidated, to place an external call that leaks value belonging to the trusting party. The analog lives in the controller's swap strategies: `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` all accept a caller-supplied `StrategySwap` XDR and forward it to the configured router inside `swap_tokens`, which the router executes by `invoke_contract` against whatever pool and token addresses the payload names — with no allowlist anywhere in the pipeline. A route crafted by an attacker (e.g., served by a malicious quote endpoint) can name a rogue "pool" contract whose code runs `token.transfer(victim, attacker, victim_balance)` on an unrelated token. Because the call sits below the victim's `require_auth` entry, Soroban's recording mode attaches that transfer as a child of the victim's `swap_collateral` authorization, and in enforcing mode it executes the moment the victim signs the simulated tree. The protocol's own test harness proves the theft end-to-end.

### Finding Description
In `contracts/controller/src/strategies/swap.rs:13-55`, `swap_tokens` authorizes exactly one input transfer to the router (`authorize_transfer_as_current` at line 34) and calls `router.execute_strategy(&controller, &amount_in, swap)` at line 37. It bounds only the controller-side balances: input spend is capped by `RouterOverspend` checks (lines 42-48) and output must be a positive measured delta (`verify_router_output`, lines 75-84). Nothing validates the contents of `swap` — the venue pool addresses and token addresses inside the XDR are whatever the payload says, and neither the controller nor the router keeps an allowlist of them.

The router dispatches each hop to the payload-named address, putting attacker-chosen contract code on the call stack beneath the user's authorization entry. That code can call `token.transfer(victim, attacker, amount)` on any token the victim holds. The host attaches the `require_auth` demand to the victim's `swap_collateral` (or `execute_strategy`) root, and if the victim signs the tree the simulation produced, the transfer executes. `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:194-268` demonstrates exactly this: a `RogueHopPool` whose `swap` moves Alice's entire `WALLET_BALANCE` of a token the protocol never listed to the attacker, while the route still pays a "fair" output so every protocol-side check passes. The threat model acknowledges the mechanism at `docs/explanation/threat-model.md:154-165` ("a route can put third-party code on the call stack below the caller's authorization... The loss is then the caller's wallet, not the routed amount") but the contract enforces nothing against it — the only defense is each client decoding the route and refusing extra auth children, which nothing in-protocol guarantees.

### Impact Explanation
Theft of user funds. A victim who signs an attacker-supplied route loses arbitrary balances of arbitrary tokens in their wallet — unbounded by `amount_in`, by the payload's `min_out`, or by the controller's risk gates, since the stolen transfer is a sibling of the strategy call rather than part of the measured settlement. The test shows the victim's unrelated-token balance going from `WALLET_BALANCE` to zero while the swap itself completes normally.

### Likelihood Explanation
Any unprivileged address can deploy a rogue pool contract and craft a route XDR naming it; the trigger is any in-scope strategy entrypoint (`swap_collateral` shown, `swap_debt`, `repay_debt_with_collateral`, `multiply` equivalent). Exploitation requires a user to sign a route they did not build — the standard flow for aggregator-served quotes — so the practical bar is a malicious or compromised route source plus a wallet that signs the simulated auth tree without decoding it. Rating: High (strong impact, social-engineering-dependent likelihood, confirmed by an executable test).

### Recommendation
Add a venue/pool allowlist or venue-pinned pool resolution so payloads can only reference governed-registered pool addresses, and/or validate that every token and pool address in the decoded route belongs to a protocol-approved set before dispatch. At minimum, restrict hop targets to addresses resolvable from governance-registered market data rather than raw payload `assets` indices. Documenting the risk for clients does not remove the contract-level exposure for direct `execute_strategy` callers and strategy users.

### Proof of Concept
1. Attacker deploys `RogueHopPool` (as in the test at `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:51-72`), whose `swap` entrypoint calls `token.transfer(victim, attacker, victim_balance)` on an unlisted wallet token.
2. Attacker serves a route XDR for `swap_collateral` naming that contract as the hop pool, with a `min_out` the attacker's liquidity actually satisfies.
3. Victim calls `swap_collateral`; simulation records the rogue transfer as a child of the victim's auth root (test lines 194-227), and under enforcing auth the signed tree executes it (lines 229-269): victim's `wallet_token` balance goes to 0, attacker receives `WALLET_BALANCE`, while the swap itself returns the fair output and all controller checks (`RouterOverspend`, `NoSwapOutput`, risk gates) pass.

Caveat: this exposure is explicitly described in `docs/explanation/threat-model.md:154-165` as a client-side responsibility, so a reviewer may treat it as a documented design choice; the contract nonetheless contains no technical mitigation and the theft path is reachable from the listed unprivileged entrypoints.
