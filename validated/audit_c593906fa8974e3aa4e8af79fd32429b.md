### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity via `Utils::HmacValidator.validate(request)`, but the HMAC signature only ever covers the raw request body. The `shop` (from the `shop-domain` header), `topic`, `webhook_id`, and `api_version` headers are read directly from unauthenticated HTTP headers and are never included in the signed content, yet `Registry.process` trusts `request.shop` as the tenant identity when dispatching to the app's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely over `to_signable_string` (the body) and compares it to the `hmac-sha256` header value: [3](#0-2) 

`Registry.process` then validates the HMAC and, on success, unconditionally forwards `request.shop` (the unauthenticated header) to the app's webhook handler as the tenant/store identity, along with the body: [4](#0-3) 

The identity binding that should hold is: `shop identity used by the handler == shop cryptographically bound to the signed bytes`. Instead, the equality that actually holds is only `HMAC(body) == signature`; `shop` is completely decoupled from the signature. Because every shop installing the same app shares the single `api_secret_key`, a valid `(raw_body, hmac)` pair generated from real traffic on one tenant (e.g., a merchant triggering an `orders/create` event on their own shop, capturing the legitimate webhook payload and its valid HMAC) remains cryptographically valid when replayed to the same endpoint with the `shop-domain` header rewritten to a different, victim shop domain. `HmacValidator.validate` still returns `true` because it never inspected the header, and `Registry.process` will hand the victim shop's identity plus the attacker-controlled body to the app's handler.

### Impact Explanation
This breaks the tenant boundary the host application relies on: `Registry.process` and any consuming app implicitly trust `request.shop` as an authenticated indicator of which merchant/store the payload belongs to, purely because HMAC validation "passed." An attacker who is a merchant on the app (i.e., can generate legitimate webhook traffic for their own shop, which requires no special privilege beyond installing the free/trial app) can forge webhook deliveries that appear to originate from any other shop using the app, injecting attacker-controlled body content associated with the victim's tenant identity. Depending on how the consuming app persists/acts on webhook data (order creation, GDPR data requests, inventory updates, uninstall events, etc.), this can lead to cross-tenant data corruption or unauthorized actions performed against another merchant's store context inside the host application — a cross-tenant access impact.

### Likelihood Explanation
The attacker only needs: (1) the app's public webhook endpoint URL (typically the same fixed callback path registered for all shops), and (2) the ability to generate at least one legitimate webhook for their own shop by installing the app and triggering any subscribed event — both readily achievable by any internet user who installs a public/development version of the app. No access token, `client_secret`, or privileged account is required; only ordinary usage of the app as an installed merchant.

### Recommendation
Bind the shop identity into the verified signable content, or otherwise cryptographically tie the `shop-domain` header (and ideally `topic`/`webhook_id`) to the HMAC check — e.g., include these headers in `to_signable_string`, or have `HmacValidator`/`Registry.process` independently re-validate that `request.shop` matches an expected/registered shop associated with the session used to originally register that specific webhook subscription, rather than trusting the header verbatim once body-only HMAC validation succeeds.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a subscribed webhook event (e.g., update a product) so Shopify sends a legitimate webhook to the app's fixed callback URL with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`, and some `raw_body`.
2. Capture the exact `raw_body` and `x-shopify-hmac-sha256` value from that request.
3. Replay an HTTP POST to the same callback URL, reusing the identical `raw_body` and `x-shopify-hmac-sha256`, but replace the `x-shopify-shop-domain` header with `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully (all required headers present), `Utils::HmacValidator.validate(request)` returns `true` (body/HMAC pair still matches, since headers aren't part of `to_signable_string`), and `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: <attacker body>, ...)` — the app now processes attacker-controlled data under the victim shop's identity.
