## Title
Malicious application's `onGetResponse` callback can reenter `HandlerV2.handleGetResponses` to steal other responses' relayer fees and force the honest relayer's batch to revert - (File: `evm/src/core/HandlerV2.sol`, `evm/src/core/EvmHost.sol`)

### Summary
`HandlerV2.handleGetResponses` iterates over a batch of GET responses, verifies a single Merkle-Mountain-Range proof for the whole batch, and then dispatches each response to its destination module by an external, un-reentrancy-guarded call chain that ends in `EvmHost.dispatchIncoming(GetResponse,...)`, which pays the relayer fee in the same transaction. A malicious destination application, upon receiving its `onGetResponse` callback, can reenter the handler with a second, independently-constructed but equally valid proof covering other pending responses in the same batch (destined for other apps), claim itself as the delivering relayer, and collect their relayer fees immediately. When control returns to the original relayer's loop, the now-already-recorded receipts cause an unconditional `revert DuplicateMessage()`, reverting the entire original batch transaction and wasting all of the honest relayer's gas. This is structurally the same "hook reenters the claim path to steal fees owed to someone else" pattern described in the PoolTogether report (M-5), just implemented via `onGetResponse`/`onAccept` app callbacks instead of PoolTogether prize hooks.

### Finding Description
`handleGetResponses` verifies the whole batch's inclusion proof once, then loops and dispatches each leaf individually: [1](#0-0) 

For each leaf it does a hard, unconditional check-then-revert for duplicates (no try/catch), then calls `host.dispatchIncoming`:
```solidity
if (host.responseReceipts(leaf.response.request.hash()).relayer != address(0)) revert DuplicateMessage();
host.dispatchIncoming(leaf.response, _msgSender());
``` [2](#0-1) 

`dispatchIncoming(GetResponse,...)` records the receipt, makes a raw `.call` into the destination app's `onGetResponse`, and — only if that call succeeds — immediately pays out the relayer fee to whichever address was passed in as `relayer` (i.e. `_msgSender()` of whoever called `handleGetResponses`): [3](#0-2) 

Because `handleGetResponses`/`dispatchIncoming` have no reentrancy guard, and the MMR/overlay-root proof data needed to build a valid sub-proof for *any* pending response is public (it is just a merkle proof against an already-stored, public state commitment), a malicious destination contract can:

1. Wait for an honest relayer to submit `handleGetResponses` with a batch `[A(honest app), M(malicious app), B(honest app), C(honest app)]`.
2. When the loop reaches `M`, `dispatchIncoming` calls `M.onGetResponse(...)`.
3. Inside that callback, `M` reenters `IHandlerV2(handler).handleGetResponses(host, ownMessage)` with an independently constructed valid proof for `B` and `C` (still undelivered, still in the MMR) — `_msgSender()` inside this nested call is `M` itself, so `M` is recorded as `relayer` for `B` and `C`, and the relayer fee tokens for `B` and `C` are transferred to `M` instantly.
4. Control returns to the original transaction's loop; when it reaches `B`, `host.responseReceipts(B).relayer != address(0)` is now true, so the entire original relayer transaction reverts with `DuplicateMessage`.

Net effect: `M` steals the relayer fees earmarked for delivering `B` and `C` at essentially zero marginal cost (it only pays gas for its own small reentrant call, which the honest relayer's larger transaction subsidizes by having already paid for proof verification/state access in the same block), while the honest relayer's entire batch (including the legitimate delivery+fee for `A`) reverts and its gas is wasted. This mirrors the PoolTogether report exactly: a value-receiving party uses a callback hook to reenter the "claim" function and skim fees intended for the party who did the actual work of assembling/submitting the delivery.

### Impact Explanation
This directly results in theft of relayer fee tokens (ERC-20 `feeToken` transferred via `safeTransfer` in `dispatchIncoming`) that belong to the relayer who performed the delivery work, and it forces complete reverts of otherwise-valid relayer batches, which is a denial-of-service on the relayer's economics and, at scale, on message delivery throughput (since batching is how the relayer amortizes gas cost across many messages). Any application dispatching a GET request that is bundled by relayers alongside other pending responses is exposed to this: a single malicious app anywhere in a batch can hijack the fee income and abort delivery for every other response in that batch. This is a concrete, permissionless fund-theft and griefing vector against Hyperbridge's incentivized relayer economics.

### Likelihood Explanation
The attack requires only deploying a malicious IApp-compatible contract that dispatches at least one GET request (or is the target of one) and implements a hostile `onGetResponse` that reenters `handleGetResponses`. The proof data needed for the malicious sub-batch is public once the state commitment is on-chain (same MMR root the honest relayer used), so no special relayer infrastructure or private information is needed — permissionless `handleGetResponses` explicitly allows "callable by anyone." No admin/governance/consensus-forgery step is needed; this is reachable from a single relayed message batch by any unprivileged application contract.

### Recommendation
Add a reentrancy guard around `handleGetResponses`/`handlePostRequests`/`dispatchIncoming` (or a host-level lock) so an app's `onAccept`/`onGetResponse`/`onPostRequestTimeout` callback cannot re-enter the handler mid-batch. Alternatively, defer relayer fee payouts until after the entire batch's external calls have completed (checks-effects-interactions), and/or make the duplicate-receipt check tolerant (skip instead of revert) so a race does not brick the rest of an honest relayer's batch.

### Proof of Concept
1. Relayer submits `HandlerV2.handleGetResponses(host, msg)` where `msg.responses = [respA, respM, respB, respC]`, all currently undelivered and included under `host.stateMachineCommitment(msg.proof.height).overlayRoot`.
2. Loop processes `respA` normally (fee paid to relayer, `responseReceipts[A].relayer = relayer`).
3. Loop processes `respM`; `dispatchIncoming` calls `M.onGetResponse(...)`.
4. Inside `onGetResponse`, `M` calls `IHandlerV2(handler).handleGetResponses(host, ownMsg)` where `ownMsg.responses = [respB, respC]`, built with a fresh MMR multiproof against the same public `overlayRoot`/`leafCount`. This succeeds because `MerkleMountainRange.VerifyProof` only requires correct leaf/position data, not exclusive knowledge.
5. `dispatchIncoming` records `responseReceipts[B].relayer = M` and `responseReceipts[C].relayer = M`, and pays `M` the relayer fees for `B` and `C` from `_requestCommitments[...].fee`.
6. `M.onGetResponse` returns success; `dispatchIncoming` for `respM` also pays `M` its own fee.
7. Control returns to the original relayer loop at `respB`: `host.responseReceipts(B).relayer != address(0)` → `revert DuplicateMessage()`. The whole original transaction (including the successful `respA` delivery/payment) is rolled back, and the relayer's gas is spent for nothing while `M` retains the stolen `B`/`C` fees from its own successful nested transaction.

    function handleGetResponses(IHost host, GetResponseMessage calldata message) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(message.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 responsesLength = message.responses.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](responsesLength);

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // don't check for timeouts because it's checked on Hyperbridge

            // known request? also serves as source check
            FeeMetadata memory meta = host.requestCommitments(leaf.response.request.hash());
            if (meta.sender == address(0)) revert UnknownMessage();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.response.hash());
        }

        bytes32 root = host.stateMachineCommitment(message.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, message.proof.multiproof, leaves, message.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // duplicate response?
            if (host.responseReceipts(leaf.response.request.hash()).relayer != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.response, _msgSender());
        }
    }

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
