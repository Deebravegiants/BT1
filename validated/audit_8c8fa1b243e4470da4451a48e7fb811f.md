### Title
Race condition: `mmr-gadget` offchain canonicalization can read/write under a stale prefix and miscompute `first_mmr_block` before `ResetMmrTree` migration (v0→v1) completes - ([File: modules/pallets/mmr/gadget/src/offchain_mmr.rs])

### Summary
The Zebra bug fixed a state-upgrade race where a node could read sprout/history tree data using stale key assumptions before the versioned state upgrade finished applying, causing a panic/incorrect read. Hyperbridge has an analogous versioned migration, `ResetMmrTree` (`pallet_mmr_tree::migrations::ResetMmrTree`, v0→v1), which clears `NumberOfLeaves`, `RootHash`, `InitialHeight`, and `Nodes` on-chain and switches the offchain key namespace to a new `INDEXING_PREFIX` (`b"ISMP-mmr-v2"`). The `mmr-gadget` (`OffchainMmr` in `modules/pallets/mmr/gadget/src/offchain_mmr.rs`) is an asynchronous, out-of-consensus offchain worker that independently tracks `first_mmr_block`/`best_canonicalized` state and reacts to finality notifications concurrently with block import/runtime-upgrade execution. [1](#0-0) [2](#0-1) 

### Finding Description
`ResetMmrTree` is a `VersionedMigration` gated on the pallet's on-chain `StorageVersion` (0→1), applied during runtime upgrade at block execution time. It clears the on-chain `Nodes`/`NumberOfLeaves`/`RootHash`/`InitialHeight` state so subsequent MMR leaves accumulate fresh under the new `INDEXING_PREFIX`, while explicitly leaving legacy offchain-DB entries (written under the old prefix) unreachable/orphaned.

The `mmr-gadget` runs as an independent async task that consumes finality notifications and asynchronously reads chain state (via `MmrRuntimeApi`, e.g. `mmr_leaf_count`, `fork_identifier`) to decide what to canonicalize/prune in the offchain DB, using `first_mmr_block`, `best_canonicalized` and a `handle_potential_pallet_reset` check driven by `pallet_genesis()`. Because this offchain worker is decoupled from the exact block at which the runtime-upgrade extrinsic/migration executes, there is a window where:
- The gadget can observe `parent_hash`/`header.hash` runtime-API state straddling the migration block (one side pre-reset, one side post-reset), computing `parent_leaf_count`/`current_leaf_count` from inconsistent on-chain views, and
- It may still act on/persist offchain keys derived from the *old* `INDEXING_PREFIX` for blocks whose on-chain `NumberOfLeaves`/`Nodes` were just reset, or fail to detect the reset promptly and mis-canonicalize/mis-prune leaves at the wrong pos across the reset boundary. [3](#0-2) [4](#0-3) 

This mirrors the Zebra root cause: an out-of-band/async reader (there, the state-service tree cache; here, the `mmr-gadget` offchain worker) computing tree/leaf positions from a mix of pre- and post-upgrade on-chain data during the upgrade window, rather than atomically gating on the completed migration.

Note: I could not fully inspect `handle_potential_pallet_reset()`'s exact detection logic or `lib.rs`'s gadget-driving loop in this session (tool read failures on the final iteration), so the precise mechanics of how/whether the gadget already guards against this race (e.g., via `pallet_genesis()` change detection) are **unverified**. The migration code itself explicitly acknowledges orphaned legacy offchain keys as "harmless," which suggests the developers considered stale-key exposure but the cross-component timing guarantee between the on-chain migration block and the gadget's asynchronous processing of surrounding blocks is not established by the code inspected.

### Impact Explanation
If the gadget canonicalizes/prunes leaves using leaf-count/position data spanning the reset boundary, offchain MMR leaf storage for consensus digest verification (`ConsensusDigest.mmr_root` in `pallet_ismp` `on_finalize`) could become inconsistent with what light clients/relayers expect to fetch and prove against, potentially causing valid MMR leaf proofs to be unavailable (temporary freezing of message delivery/proof generation) or incorrect leaves to be served under canonical keys. This affects the message relay path since MMR leaves back ISMP request/response commitments used by relayers to prove delivery.

### Likelihood Explanation
This is a Medium-likelihood, narrow-timing issue: it requires a runtime upgrade that includes `ResetMmrTree` transitioning from v0→v1 while the gadget is concurrently finalizing/canonicalizing blocks around the exact upgrade block — a one-time, operator-triggered event (not attacker-triggered), and only relevant for chains still on storage version 0. It's not exploitable by an arbitrary unprivileged actor on demand; it is analogous to the original Zebra finding, which likewise depended on a specific state-upgrade timing window rather than a directly attacker-controlled input.

### Recommendation
Verify (and if necessary harden) `OffchainMmr::handle_potential_pallet_reset` and `canonicalize_branch`/`canonicalize_catch_up` so that:
- The gadget explicitly detects the storage-version transition (or `INDEXING_PREFIX` change) at the exact migration block and flushes/resets its internal `best_canonicalized`/`first_mmr_block` state atomically with the on-chain reset, rather than relying purely on leaf-count deltas which can be computed inconsistently across the reset boundary.
- Add an explicit try-runtime / integration test that runs the `ResetMmrTree` migration concurrently with in-flight gadget canonicalization across the migration block, asserting no leaves are mis-attributed to a canonical key computed against a stale leaf-count baseline.

### Proof of Concept
Not independently reproduced — I was unable to execute code or fully trace `handle_potential_pallet_reset()` before this session ended (tool errors on `read_file`). A concrete PoC would require: (1) a test runtime upgrade from `pallet-mmr-tree` StorageVersion 0→1 while blocks are being finalized, (2) the `mmr-gadget` running concurrently processing finality notifications for blocks on both sides of the upgrade block, and (3) asserting whether `canonicalize_branch`/`prune_branch` produce leaf-count-derived node positions (`nodes_added_by_new_leaves`) that are inconsistent with the post-reset on-chain `NumberOfLeaves`.

	impl<T, I> UncheckedOnRuntimeUpgrade for InnerResetMmrTree<T, I>
	where
		T: Config<I>,
		I: 'static,
		HashOf<T, I>: Into<H256>,

		fn on_runtime_upgrade() -> Weight {
			// `Nodes` is a `CountedStorageMap`, so `count()` is the exact number
			// of entries to scan — no overshoot.
			let nodes_count = Nodes::<T, I>::count();

			NumberOfLeaves::<T, I>::kill();
			RootHash::<T, I>::kill();
			InitialHeight::<T, I>::kill();
			let _ = Nodes::<T, I>::clear(nodes_count, None);

			log::info!(
				target: "pallet-mmr",
				"ResetMmrTree migration: cleared {} on-chain MMR nodes; new leaves will accumulate under the new offchain prefix",
				nodes_count,
			);

			// 1 read for `Nodes::count()`, 3 kills + `nodes_count` removals.
			T::DbWeight::get().reads_writes(1, 3u64 + u64::from(nodes_count))
		}

	fn canonicalize_branch(&mut self, block_hash: B::Hash) {
		let action = "canonicalize";
		let header = match self.header_metadata_or_log(block_hash, action) {
			Some(header) => header,
			_ => return,
		};

		// Don't canonicalize branches corresponding to blocks for which the MMR pallet
		// wasn't yet initialized.
		// Or headers less than the best canonicalized
		if header.number < self.first_mmr_block || header.number <= self.best_canonicalized {
			return;
		}

		let parent_hash = header.parent;
		let parent_leaf_count = match self.client.runtime_api().mmr_leaf_count(parent_hash) {
			Ok(Ok(leaf_count)) => leaf_count,
			_ => {
				debug!(target: LOG_TARGET, "Failed to fetch mmr leaf count for {:?}", parent_hash);
				return;
			},
		};

		let current_leaf_count = match self.client.runtime_api().mmr_leaf_count(header.hash) {
			Ok(Ok(leaf_count)) => leaf_count,
			_ => {
				debug!(target: LOG_TARGET, "Failed to fetch mmr leaf count for {:?}", header.hash);
				return;
			},
		};

		let fork_identifier = match self.client.runtime_api().fork_identifier(header.hash) {
			Ok(Ok(fork_identifier)) => fork_identifier,
			_ => {
				debug!(target: LOG_TARGET, "Failed to fetch  fork_identifier at {:?}", header.hash);
				return;
			},
		};

		// We "canonicalize" the leaves associated with the provided block
		// and all the nodes added by those leaves.
		let to_canon_nodes = self.nodes_added_by_new_leaves(
			header.number,
			action,
			parent_leaf_count,
			current_leaf_count,
		);

		for pos in to_canon_nodes {
			let temp_key = self.node_temp_offchain_key(pos, fork_identifier);
			if let Some(elem) =
				self.offchain_db.local_storage_get(StorageKind::PERSISTENT, &temp_key)
			{
				let canon_key = self.node_canon_offchain_key(pos);
				self.offchain_db.local_storage_set(StorageKind::PERSISTENT, &canon_key, &elem);
				self.offchain_db.local_storage_clear(StorageKind::PERSISTENT, &temp_key);
				// if it's a leaf node, also clear the duplicate that was added to no_op storage
				if let Ok(DataOrHash::Data(leaf)) =
					pallet_mmr_tree::mmr::Node::<Keccak256, Leaf>::decode(&mut &*elem)
				{
					let pre_image = leaf.preimage();
					let commitment = keccak_256(&pre_image);
					let duplicate_key = pallet_ismp::offchain::leaf_default_key(commitment.into());
					self.offchain_db.local_storage_clear(StorageKind::PERSISTENT, &duplicate_key);
				}
				debug!(
					target: LOG_TARGET,
					"Moved elem at pos {}, fork_identifier {:?} header_hash {:?} to canon key {:?}",
					pos,
					fork_identifier,
					block_hash,
					canon_key
				);
			} else {
				debug!(
					target: LOG_TARGET,
					"Couldn't canonicalize elem at pos {}, fork_identifier {:?} header_hash {:?}", pos, fork_identifier, block_hash
				);
			}
		}
		if self.best_canonicalized != header.number.saturating_sub(One::one()) {
			warn!(
				target: LOG_TARGET,
				"Detected canonicalization skip: best {:?} current {:?}.",
				self.best_canonicalized,
				header.number,
			);
			// If a block has been skipped canonicalize all blocks in between
			self.canonicalize_catch_up(header.parent);
		}
		self.best_canonicalized = header.number;

	/// Move leafs and nodes added by finalized blocks in offchain db from _fork-aware key_ to
	/// _canonical key_.
	/// Prune leafs and nodes added by stale blocks in offchain db from _fork-aware key_.
	pub fn canonicalize_and_prune(&mut self, notification: FinalityNotification<B>) {
		// Update the first MMR block in case of a pallet reset.
		self.handle_potential_pallet_reset(&notification);

		// Run catchup to just to be sure no blocks are skipped
		self.canonicalize_catch_up(notification.hash);

		trace!(target: LOG_TARGET, "Got new finality notification {:?}, Best Canonicalized {:?}", notification.hash, self.best_canonicalized);
		let mut block_nums = vec![];
		for hash in notification.tree_route.iter().chain(std::iter::once(&notification.hash)) {
			match self.header_metadata_or_log(*hash, "canonicalize") {
				Some(header) => {
					block_nums.push(header.number);
				},
				_ => {},
			};
		}

		trace!(target: LOG_TARGET, "Canonicalizing Blocks{block_nums:?}");
		// Move offchain MMR nodes for finalized blocks to canonical keys.
		for hash in notification.tree_route.iter().chain(std::iter::once(&notification.hash)) {
			self.canonicalize_branch(*hash);
		}
		self.write_gadget_state_or_log();

		// Remove offchain MMR nodes for stale forks.
		let stale_hashes: Vec<_> = notification.stale_blocks.iter().map(|sb| sb.hash).collect();
		let stale_forks = match self.client.expand_forks(&stale_hashes) {
			Ok(forks) => forks,
			Err(e) => {
				warn!(target: LOG_TARGET, "{:?}", e);
				return;
			},
		};
		for hash in stale_forks.iter() {
			self.prune_branch(hash);
		}
	}
