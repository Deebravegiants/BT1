Audit Report

## Title
Missing per-sender validation on user-supplied `MessageID` in `savedCallbacks` allows cross-user response hijacking - ([File: core/services/gateway/handlers/capabilities/handler.go])

## Summary
`HandleLegacyUserMessage` stores pending callbacks in a single global map keyed solely by the caller-supplied `msg.Body.MessageID`, with no check that the ID is unique or bound to the requesting sender. A second caller who submits a request reusing an in-flight `MessageID` silently overwrites the first caller's callback registration, so the DON's response to the first requester is routed to the second requester's callback instead.

## Finding Description
`HandleLegacyUserMessage` unconditionally inserts the callback keyed only by `MessageID`: [1](#0-0) 

`Message.Validate()` only checks length and null-byte suffix constraints on `MessageID`, and derives `Body.Sender` from the ECDSA signature over the message — but this sender value is never used to scope or protect the `savedCallbacks` map key: [2](#0-1) 

When a DON node responds, `handleWebAPITriggerMessage` looks up and deletes the entry purely by `MessageID`, with no cross-check against the original sender or request payload, and delivers the response to whichever callback is currently registered: [3](#0-2) 

The codebase itself acknowledges this gap is unresolved — the handler's own test suite contains an explicit TODO calling out that sender validation is pending: [4](#0-3) 

There is also an explicit `// TODO: apply allowlist and rate-limiting here` in `HandleLegacyUserMessage`, confirming no allowlist currently restricts which unprivileged senders can submit requests: [5](#0-4) 

Because any client can sign a `Message` with its own key and choose an arbitrary `MessageID` string, two distinct, unprivileged senders can produce independently valid signed messages sharing the same `MessageID`. The second submission overwrites the map entry before the first requester's DON response arrives, redirecting that response to the second (attacker) requester.

## Impact Explanation
If an attacker can predict, observe, or collide a victim's `MessageID` within the pending window (`CallbackMaxAgeSec`, default 120s), the DON's response intended for the victim is delivered to the attacker's callback instead — a concrete cross-user response corruption/hijack, potentially exposing data intended for another user or denying the legitimate response to the original requester. This maps to the in-scope "cross-user response corruption" impact category for gateway request handling.

## Likelihood Explanation
Exploitability is gated on the attacker's ability to guess or observe an in-flight `MessageID` belonging to another sender before the DON responds — no allowlist or per-sender ownership check currently exists to block this (confirmed by the outstanding TODOs in the code), and only unprivileged, sender-controlled input (a signed `Message` with an arbitrary chosen `MessageID`) is required to trigger the overwrite. If client-generated IDs are low-entropy or predictable, likelihood is realistic; if IDs are high-entropy random values, likelihood is lower, but the root cause — lack of sender binding on the correlation key — is a genuine, demonstrable gap in the code today, not merely theoretical, since the overwrite-on-insert behavior can be shown directly via a unit test invoking `HandleLegacyUserMessage` twice with the same `MessageID` and different signer keys.

## Recommendation
- Scope `savedCallbacks` keys by `(sender, MessageID)` instead of `MessageID` alone, and reject insertion when the key is already in-flight under a different sender.
- Implement the currently-TODO’d allowlist/rate-limiting and sender validation referenced in the code and test comments.
- Consider having the gateway mint the correlation ID itself, or cryptographically binding it to the sender to prevent cross-sender collisions.

## Proof of Concept
Extend the existing `TestHandlerReceiveHTTPMessageFromClient` test harness in `handler_test.go`: call `handler.HandleLegacyUserMessage` twice with identical `MessageID` but two different signing keys/callbacks, then assert that `handler.savedCallbacks[MessageID]` now points to the second callback; subsequently invoke `handler.HandleNodeMessage` with a response for that `MessageID` and confirm it is delivered to the second (attacker) callback rather than the first (victim) callback that originally registered it.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
