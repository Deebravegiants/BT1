### Title
Webhook `shop-domain` (and `topic`) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop` (and `topic`) values used by `ShopifyAPI::Webhooks::Registry.process` to identify the tenant and dispatch the handler are read from unauthenticated HTTP headers that are never part of the signed bytes.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing `OpenSSL::HMAC.hexdigest(secret, verifiable_query.to_signable_string)` and comparing it to the `hmac` field with `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be only the raw request body: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers, with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` validates the HMAC over the body, but then trusts `request.shop` and `request.topic` — values that were never covered by that signature — to route and label the payload as belonging to a specific merchant: [4](#0-3) 

This breaks the identity binding that `hmac(raw_body)` is supposed to guarantee: the equality the gem should enforce is `shop_header == shop_that_the_secret-holder_(Shopify)_actually_signed_this_body_for`, but no such binding exists — `shop_header` is fully attacker-controlled independent of the HMAC check. Any party who can obtain one validly-signed webhook body/HMAC pair for their own shop (e.g., their own app installation triggering a real webhook, which is a completely unprivileged action) can replay that exact body and HMAC to the app's webhook endpoint while substituting the `shop-domain` header of a different, victim tenant. `Utils::HmacValidator.validate` still returns `true` because it only checks the body bytes, and `WebhookMetadata` is constructed with the attacker-chosen `shop` value: [5](#0-4) 

Host applications built on this gem (e.g., using the `shopify_app` reference implementation) rely on `WebhookMetadata#shop` as an already-authenticated tenant identifier once `Registry.process` succeeds, since the whole point of validating the HMAC is to establish that the request came from Shopify for that shop. Because the gem does not bind `shop`/`topic` into the signed payload, this trust is misplaced and cross-tenant confusion is possible entirely through this gem's own webhook-processing API, without needing the app's `client_secret` or any privileged credential — only a legitimately delivered webhook to any one (even the attacker's own) shop.

### Impact Explanation
This is a cross-tenant access vector: an attacker who legitimately receives a signed webhook for their own shop can forge the identity of another tenant when replaying it to the same app endpoint, causing the host application to process/store data as if it came from the victim shop. This matches the Critical "cross-tenant access" category, since the identity binding (`shop` field vs. HMAC-covered bytes) that the gem is expected to enforce is broken entirely within `lib/shopify_api/webhooks/**`.

### Likelihood Explanation
Any actor capable of triggering (or intercepting) one legitimate, Shopify-signed webhook delivery — a routine, unprivileged occurrence for any shop that installs the app — can replay the identical body/HMAC pair with a modified `shop-domain` header. No access token, `api_secret_key`, or elevated privilege is required; only knowledge of the app's public webhook endpoint and one genuine (body, hmac) pair, which is trivial to obtain as an ordinary merchant.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values in the signable string used for webhook HMAC validation, or otherwise cryptographically bind them to the verified payload, so `Utils::HmacValidator.validate` fails if any of these attacker-reachable header values are altered relative to what Shopify actually signed for.

### Proof of Concept
1. App installs the library's webhook handler using `ShopifyAPI::Webhooks::Registry.process`.
2. Attacker's own shop (`attacker-shop.myshopify.com`) receives a legitimate webhook from Shopify: raw body `B` and header `x-shopify-hmac-sha256` computed over `B` with the app's real `api_secret_key`.
3. Attacker resends the same raw body `B` and the same valid `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present).
5. `Utils::HmacValidator.validate(request)` returns `true` because it only hashes `@raw_body` (`B`), which is unchanged.
6. `Registry.process` dispatches `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` to the app's handler, which now processes attacker-supplied data under the victim shop's identity.
