This confirms the vulnerability: `ShopifyAPI::Webhooks::Request#shop` (from `shop-domain` header) is explicitly documented as a trusted field passed to the handler (`docs/usage/webhooks.md` lines 12-14, 25-26), yet it is excluded from the HMAC signature computation in `Request#to_signable_string`, which returns only `@raw_body` [1](#0-0) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` against this signable string before forwarding `request.shop` to the app's handler [2](#0-1) .

### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw request body alone, never incorporating the `shop-domain` (or `topic`) header. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` and forwards it unchanged to the app's `WebhookHandler` as `WebhookMetadata#shop`, which the library's own documentation instructs developers to use as the tenant identifier for the webhook (e.g., `shop_domain: data.shop`). This breaks the intended binding `hmac_valid(body) == shop_is_authentic`.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only [3](#0-2) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers [4](#0-3) . `HmacValidator.validate` only checks that the computed HMAC over `to_signable_string` (the body) matches the header's HMAC [5](#0-4) . `Registry.process` gates entirely on this check, then constructs `WebhookMetadata` directly from `request.shop`, `request.topic`, etc., with no further binding to the verified body [2](#0-1) .

Because Shopify's webhook HMAC is computed only over the raw JSON body using the app's `client_secret` (a value never available to any merchant/attacker), any webhook payload legitimately delivered to the app for one shop (shop A, which an attacker fully controls as a merchant) carries a raw-body/HMAC pair that remains valid regardless of the `shop-domain`/`topic` header values sent alongside it. An attacker who operates a shop can capture a legitimately-signed webhook body from their own shop and replay it to the app's public webhook endpoint with a forged `shop-domain` header naming a victim shop (or a forged `topic` header). Since the header values are never part of the signable string, `HmacValidator.validate` still returns `true`, and the app's handler receives `data.shop` = victim shop / `data.topic` = arbitrary topic paired with attacker-controlled body content.

This is the "field acted on but not covered by the HMAC" identity-binding break called out in the report class: the equality the library implies — `verified_hmac(body) ⇒ shop header is authentic` — does not hold, because `shop` (and `topic`) are parsed from headers that sit entirely outside the signed bytes.

### Impact Explanation
This is a cross-tenant integrity/confusion vulnerability: an attacker who is a legitimate merchant of the target app can cause the app to process attacker-supplied JSON body content while attributing it to a different, victim shop (or a different topic than what was actually signed). Depending on how the host app's handler uses `data.shop` (e.g., to look up the shop's session/access token and perform actions, or to write data into per-shop tables), this can lead to cross-tenant data corruption or actions being taken against the wrong merchant's data store — matching the "cross-tenant access" impact category.

### Likelihood Explanation
The webhook endpoint is a public, unauthenticated HTTP endpoint by design (Shopify calls it from the internet), and the library's documented usage pattern is to pass `request.headers.to_h` straight into `ShopifyAPI::Webhooks::Request.new` [6](#0-5) , without any independent shop/topic authentication. Any developer using this gem as documented is exposed. The only requirement for the attacker is possessing a valid signed webhook body from their own shop (trivial for any developer/merchant account) and the ability to send a crafted HTTP request to the app's public webhook URL with modified headers.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC verification (or otherwise cryptographically bind them to the verified body), so that spoofing any of these headers invalidates the signature. Short of that, `Registry.process` should independently corroborate `request.shop` against a shop known to be associated with the specific `webhook_id`/subscription before dispatching to the handler.

### Proof of Concept
1. Attacker registers/owns shop `attacker.myshopify.com` and subscribes the target app to a webhook topic (or captures a legitimately delivered webhook).
2. Shopify delivers a webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: HMAC(B, client_secret)`; since `HmacValidator` only signs `B`, this HMAC value is valid for `B` regardless of what shop/topic headers accompany it.
3. Attacker replays the exact same body `B` and HMAC header to the app's public webhook endpoint, but overwrites `x-shopify-shop-domain` to `victim.myshopify.com` (and optionally `x-shopify-topic` to a more sensitive topic already registered by the app).
4. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which passes because it only checks the body [7](#0-6) .
5. The app's handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled `body`, and processes it as if Shopify itself sent legitimate data for the victim shop [8](#0-7) .
