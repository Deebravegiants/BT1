### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)`. However, the `shop` identity used to route the payload to the merchant-specific handler is read from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, which is never included in the HMAC-signed material.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
and `HmacValidator.validate_signature` computes/compares the HMAC exclusively against that signable string: [2](#0-1) 

Meanwhile `Registry.process` uses `request.shop` — sourced from the unauthenticated header via `shopify_header("shop-domain")` — to build the `WebhookMetadata` that is handed to the app's handler: [3](#0-2) [4](#0-3) [5](#0-4) 

The equality the code implicitly assumes is: `shop (header, unauthenticated) == shop (that produced the signed body)`. This is never checked. Since HMAC covers only the body bytes, any party who possesses one valid `(raw_body, hmac)` pair — trivially obtainable by installing the app on their own store and capturing Shopify's genuine webhook delivery — can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. The HMAC still validates (it only ever checked the body), and the handler receives `WebhookMetadata` claiming the victim shop as the source.

### Impact Explanation
Apps built on this gem typically use `data.shop` from `WebhookMetadata` to look up the merchant's stored session/access token or to determine which tenant's records to create, update, or delete in response to the webhook (e.g. `orders/create`, `app/uninstalled`, `customers/redact`). Because the shop identity is not bound to the HMAC-authenticated payload, an attacker can trigger handler logic that is misattributed to an arbitrary victim shop domain — a cross-tenant identity confusion. Depending on the handler's implementation, this can result in cross-tenant data corruption, spurious mandatory-compliance actions (e.g. forging `customers/redact`/`shop/redact` against a victim's data), or state desynchronization for a store the attacker doesn't control.

### Likelihood Explanation
Exploitation requires only: (1) attacker-controlled installation of the app on their own development/trial store to capture one genuine `(raw_body, hmac)` pair for a chosen topic, and (2) the app's webhook endpoint being internet-reachable (a documented requirement for Shopify webhook delivery). No access to `api_secret_key` or any privileged credential is needed — the attacker is an ordinary, unprivileged merchant who can install the target app. This is realistic and directly reachable through the gem's documented `Registry.process` API.

### Recommendation
Bind the shop identity to the authenticated payload instead of trusting the header in isolation:
- Include the `shop-domain` header (and ideally `topic`, `api-version`, `webhook-id`) in the HMAC-signable string (`to_signable_string`), matching them against the parsed body's own `shop`/`domain`/`myshopify_domain` field where the topic's payload contains one; or
- Cross-check `request.shop` against a shop value embedded in `raw_body` before constructing `WebhookMetadata`, rejecting mismatches.
- At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted by handlers without additional verification against the signed body content.

### Proof of Concept
1. Install the target app on attacker-owned store `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST: body `B` and header `x-shopify-hmac-sha256: H` (valid, computed by Shopify with the real `api_secret_key` over `B`).
2. Replay the request to the same app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but replacing `x-shopify-shop-domain: attacker.myshopify.com` with `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `H` against `HMAC(secret, B)` — this still passes: [6](#0-5) 
4. The registered handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com", body: parsed(B) ...)`, causing the app to act on victim-shop data/session using attacker-controlled content, despite no genuine webhook having been sent by Shopify for `victim.myshopify.com`.
