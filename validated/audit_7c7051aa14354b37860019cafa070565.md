Based on the investigation, there is a solid analog to the MessageProcessor issue in the webhook verification code, where the shop identity field is not covered by the HMAC that is verified.This confirms the finding: `WebhookMetadata.shop` (and `topic`, `webhook_id`, `api_version`) are trusted tenant/routing identifiers handed straight to the app's handler, yet none of them are covered by the HMAC that `HmacValidator.validate` checks.

### Title
Webhook HMAC verification excludes the `shop-domain`, `topic`, and `webhook-id` headers, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers [2](#0-1) . `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC over `to_signable_string` only [3](#0-2) , so a valid signature only proves the body's authenticity — not the `shop-domain`, `topic`, or `webhook-id` values that `Registry.process` uses to route the request and identify the tenant [4](#0-3) .

### Finding Description
`Registry.process` treats `request.shop`, `request.topic`, and `request.webhook_id` as trustworthy identifiers and forwards them unmodified into `WebhookMetadata`, which the app's `WebhookHandler#handle` uses to key its tenant-specific logic (e.g., "which shop is this data for?") [5](#0-4) [6](#0-5) .

The identity binding that should hold is:
`shop header used to compute/verify the HMAC == shop header trusted by WebhookMetadata.shop`

But `to_signable_string` only ever equals `@raw_body`, so the shop, topic, and webhook_id headers are never part of the signed material [7](#0-6) . Since a single Shopify app has one `api_secret_key` shared across every merchant shop that installs it, any merchant (an ordinary, unprivileged app installer — not a privileged account) legitimately receives webhooks whose bodies are HMAC-signed with that same shared secret. That merchant can capture one of their own valid `(body, hmac)` pairs and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain (and/or the `topic`/`webhook-id` headers altered). `HmacValidator.validate` still returns `true` because it only checks the untouched body against the untouched HMAC header [8](#0-7) ; `Registry.process` then dispatches the handler believing the data belongs to the victim shop [5](#0-4) .

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: an attacker who is a legitimate installer for the app (no `api_secret_key`, access token, or privileged account required) can make the host application process attacker-controlled webhook data under a victim shop's identity — a cross-tenant access condition, matching the report's underlying bug class (a value acted upon that is not bound by the cryptographic check meant to authenticate it).

### Likelihood Explanation
Any developer/merchant capable of installing the target app on a store they control can trigger and capture a legitimate webhook and its valid HMAC, then simply edit the `shop-domain` header value and resend the HTTP request to the app's public webhook endpoint — no secrets, tokens, or elevated privileges are needed beyond ordinary app installation.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the material that is HMAC-verified (e.g., bind them into `to_signable_string`, or perform a separate authenticated binding of `shop`/`topic` to the signed body), rather than trusting them as bare, unauthenticated HTTP headers in `Registry.process`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and enables an HTTP webhook (e.g. `orders/create`).
2. Shopify delivers a webhook request to the app with a valid `x-shopify-hmac-sha256` computed over the raw body using the app's shared `api_secret_key`, plus `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays this exact HTTP request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com` (the body and HMAC header are untouched).
4. `ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` are unaffected by the header change [9](#0-8) ; `HmacValidator.validate` returns `true` [8](#0-7) .
5. `Registry.process` invokes the app's handler with `WebhookMetadata.shop == "victim.myshopify.com"` and attacker-controlled `body`, even though the data never originated from the victim shop [5](#0-4) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          received_signature = verifiable_query.hmac
