### Title
Stranded/residual token balance in `EmporiumUpgradeable` can be swept into an attacker's own shielded UTXO via arbitrary, unrestricted `ops` - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` measures the value it pays out purely as a balance snapshot delta (`balancesAfter[i] - balancesBefore[i]`, adjusted by `deltaAmountChanges[i]`), and the `EmporiumOperation[]` that produce that delta are fully attacker-controlled arbitrary calls with no signature check when `stack.signerAddress == address(0)`. Any ERC20/ETH value that is sitting in the `EmporiumUpgradeable` contract at the start of a call (dust from a prior partial swap/multi-hop leftover, an under-consumed input, or other stranded balance) is included in `balancesBefore`, but nothing prevents a subsequent caller from crafting `ops` that route that pre-existing balance together with their own deposit into an output token, after which `handleOut` pays 100% of the positive delta to `msg.sender` and it is minted as the caller's own shielded UTXO. The invariant "tokens leaving the action in a tx == `-deltaAmountChanges` Hinkal sent it" is broken whenever the action already held tokens the caller didn't deposit.

### Finding Description
The claimed invariant is:
`sum(handleOut payouts for tx T) == sum(-deltaAmountChanges[i] for tx T)` (i.e., the value the Emporium action returns to a caller in a given `Hinkal.transact` call should equal exactly the value that same call deposited into it).

In `runAction` [1](#0-0) , `balancesBefore` is a live on-chain snapshot taken at the top of the call — it does not distinguish between "just deposited by this caller" and "stranded from before". The `ops` executed between the snapshots are attacker-supplied `EmporiumStack.ops`, and when `stack.signerAddress == address(0)` no signature is verified at all [2](#0-1) , so the caller freely chooses `op.endpoint` and `op.callData`, including chaining an `approve` + a swap/router call that consumes the *entire* current balance of a token held by the contract (their own deposit plus any residual) [3](#0-2) .

After the ops run, `balanceChange` is computed purely from the before/after snapshot and `deltaAmountChanges[i]`, and any positive delta for a token index is paid entirely to `msg.sender` via `handleOut`, with no check that the payout is bounded by what the caller actually contributed: [4](#0-3) .

The outer `Hinkal.transact` balance-diff check does not catch this either: it only verifies that Hinkal's own balance movement equals `amountChanges[i] + utxoAmount`, where `utxoAmount` is whatever `handleOut` reported — this is tautological with respect to the actual token flow and never independently bounds the payout to the caller's own deposit: [5](#0-4) . `msg.sender` inside `EmporiumUpgradeable` is always the `Hinkal` contract (it calls `runAction` from `_externalTransact`) [6](#0-5) , so the swept value flows back into Hinkal and is minted as a legitimate shielded UTXO under the attacker's own `stealthAddressStructure`, spendable later with a normal proof.

Any mechanism that leaves value in `EmporiumUpgradeable` without it being consumed the same call it arrives (interim/multi-hop tokens outside the current `erc20TokenAddresses` set, partial fills, rounding, ETH refunds, or a prior transaction that legitimately left dust) becomes fair game for the next caller whose `ops` happen to target that token.

### Impact Explanation
Any unprivileged attacker who observes (or engineers, e.g. via their own two-step sequence within a block) a nonzero token balance sitting in `EmporiumUpgradeable` can construct `ops` (no signature required, `signerAddress = address(0)`) that sweep that balance together with a nominal deposit of their own, and have the full swept amount credited to them as a valid shielded UTXO via `handleOut`. This is theft of shielded/in-flight or stranded protocol funds that never belonged to the attacker's own `-deltaAmountChanges`, matching Critical severity ("direct theft of shielded or in-flight user funds," and effectively minting shielded value without matching backing since the extra value did not come from the attacker's own proven UTXO input). It is repeatable any time the action ends up holding a balance it did not fully sweep in the depositing transaction.

### Likelihood Explanation
- Preconditions: `EmporiumUpgradeable` must hold a nonzero balance of some ERC20/ETH at the start of a `runAction` call that is not attributable to the calling transaction's own `deltaAmountChanges` (e.g., leftover from a multi-hop swap, partial fill, someone else's unswept output, or the attacker's own prior transaction in the same block deliberately leaving dust).
- Attacker cost: one transaction with self-crafted `EmporiumStack` (`signerAddress = address(0)`, no signature needed), and, if orchestrating the residual themselves, one prior transaction in the same block to create it.
- Feasibility: fully unprivileged — `runAction` is only gated by `onlyAllowedRecipient`, which allows `Hinkal` itself to call it, and `Hinkal.transact` is callable by anyone with a valid proof for their own UTXOs; the `ops` content and its target tokens are entirely attacker-chosen.
- Repeatable: yes, on every occurrence of stranded balance.

### Recommendation
Do not rely on a raw pre/post balance snapshot of the whole contract as the source of truth for payout. Instead:
- Track and consume only the amount actually deposited by the current call (e.g., pass the deposited amount explicitly through the op execution context, or require `ops` to only ever increase/decrease balances by amounts traceable to the current transaction's `deltaAmountChanges`).
- Alternatively, enforce that `EmporiumUpgradeable` never holds a balance at rest between transactions: revert if `balancesBefore[i] != 0` for any token not currently being deposited, or sweep/attribute any un-deposited residual to a protocol-controlled recovery path instead of `handleOut`.
- Restrict `op.endpoint`/token targets so arbitrary tokens outside the declared, deposit-tracked `erc20TokenAddresses` cannot be swept by `ops`.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, a mock ERC20, and a mock swap/router contract.
2. Seed residual: have `EmporiumUpgradeable` end up holding e.g. 100 tokenA with no matching UTXO obligation (simulate by directly minting tokenA to the Emporium contract address, representing dust from an interim/untracked hop, or run one crafted `runAction` call that intentionally leaves it via a multi-hop op touching a token not included in that call's `erc20TokenAddresses`).
3. Attacker deposits a small amount (e.g. 1 tokenA) via `Hinkal.transact` with a valid proof for their own UTXO, `erc20TokenAddresses = [tokenA]`, `deltaAmountChanges[0] = -1`.
4. Craft `EmporiumStack.ops` with `signerAddress = address(0)`: op1 = `tokenA.approve(mockRouter, type(uint256).max)`, op2 = `mockRouter.swap(tokenA, outputToken, allBalance)` sending output back to `EmporiumUpgradeable`, consuming the full 101 tokenA balance.
5. Assert: `outUtxo.amount` returned/committed for `outputToken` == value corresponding to all 101 tokenA (i.e., strictly greater than `-deltaAmountChanges[0]` = 1), proving `payout != -deltaAmountChanges` sent that tx.
6. Assert the attacker can later spend that minted UTXO via a normal `Hinkal.transact` withdrawal, confirming realized theft of the 100-token residual that was never theirs.
