### Title
Webhook shop/topic/webhook-id identity is trusted from unauthenticated HTTP headers not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body [1](#0-0) , but the `shop`, `topic`, `webhook_id`, and `api_version` values that the handler receives and acts on are all read directly from HTTP headers, which are never part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [2](#0-1) . `Utils::HmacValidator.validate` computes the HMAC exclusively over that signable string [3](#0-2) . Meanwhile `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all parsed straight from the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, and `shopify-api-version` HTTP headers [4](#0-3) , none of which are covered by the HMAC.

`Registry.process` checks only `Utils::HmacValidator.validate(request)` and then forwards `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` verbatim into `WebhookMetadata` given to the app's handler [1](#0-0) .

Since the app's `api_secret_key` is shared across all shops that install the app (it is not shop-specific), any user who installs the app on their own store receives genuine Shopify webhooks with a body/HMAC pair that is valid under the app's single secret. That user can capture one of their own legitimate webhook deliveries (raw body + valid `hmac-sha256` header) and replay it to the app's webhook endpoint while substituting the `shopify-shop-domain` (and optionally `shopify-topic`/`shopify-webhook-id`) header to name a different, victim shop. `Registry.process` will still report `Utils::HmacValidator.validate` as `true` (because it only checks the untouched body) and will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop [5](#0-4) .

This breaks the intended identity binding: `HMAC-verified payload origin == shop the handler believes sent it`. The equality that should hold (`hmac_verified_body's shop == request.shop used by handler`) does not, because `shop` is never part of the signed bytes.

### Impact Explanation
Any host application that uses `request.shop` (as most apps do, per the documented `WebhookMetadata` contract) to key data lookups, credential/session retrieval, or tenant-scoped mutations will process attacker-supplied data under an arbitrary victim shop's identity. This is a cross-tenant confusion: sensitive mandatory webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) [6](#0-5)  or ordinary business webhooks (`orders/create`, etc.) can be forged to name any shop, letting an attacker inject fabricated events (e.g., a fake `customers/redact` or forged order data) attributed to a victim tenant, or manipulate shop-scoped state the app maintains keyed by `shop`. This crosses a tenant boundary using only knowledge obtainable from the attacker's own legitimate installation — no `api_secret_key`, access token, or privileged account is required beyond installing the app on the attacker's own store.

### Likelihood Explanation
Requires only that the attacker (1) install the app themselves (a normal unprivileged action any Shopify merchant can take) to receive at least one genuine webhook with a valid body/HMAC pair, and (2) resend that exact body to the app's public webhook endpoint with a modified `shop`/`topic` header. No cryptographic secret needs to be recovered because the header fields simply aren't part of what's verified.

### Recommendation
Bind the tenant/topic/webhook identity into the signed material, or otherwise re-derive it from data that is cryptographically covered:
- Extend `VerifiableQuery`/`to_signable_string` (or a webhook-specific canonical string) to include `shop`, `topic`, and `webhook_id`, and validate the HMAC over that combined string instead of the raw body alone, or
- Independently confirm the `shop` header value against the shop embedded in the JSON body payload (Shopify webhook payloads generally include shop-identifying fields), rejecting mismatches, and document to consuming apps that `request.shop` must not be trusted unless cross-checked.

### Proof of Concept
1. Install the target app on an attacker-controlled development store; the attacker's server receives a genuine webhook, e.g.:
```
POST /webhooks
shopify-topic: orders/create
shopify-hmac-sha256: <valid-hmac-for-body>
shopify-shop-domain: attacker-shop.myshopify.com
shopify-webhook-id: <id>
Body: {"id": 1, ...}
```
2. Attacker resends the identical body and `hmac-sha256` value to the same endpoint, only changing the shop header:
```
POST /webhooks
shopify-topic: orders/create
shopify-hmac-sha256: <same-valid-hmac-for-body>
shopify-shop-domain: victim-shop.myshopify.com
shopify-webhook-id: <same-or-arbitrary-id>
Body: {"id": 1, ...}   # unchanged, so HMAC still validates
```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which returns `true` because it only hashes `@raw_body` [2](#0-1) [7](#0-6) .
4. The registered handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: ..., ...)` [5](#0-4) , causing the app to act as if `victim-shop.myshopify.com` sent this order data, even though the payload actually originated from the attacker's own store.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

        end
