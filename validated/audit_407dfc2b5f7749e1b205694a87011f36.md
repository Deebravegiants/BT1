### Title
`move_claim` unconditionally remaps `Preclaims` to `new` even when the `old` claim was already consumed, corrupting the preclaim linkage with no error signaled - (File: polkadot/runtime/common/src/claims/mod.rs)

### Summary
`Pallet::move_claim` performs the `Claims`/`Vesting`/`Signing` migration from `old` to `new` using `Option::map`, which silently no-ops when `old` has already been claimed. However, the `Preclaims` remap for `maybe_preclaim` is executed unconditionally, independent of whether the `Claims::<T>::take(&old)` actually returned `Some`. This can leave a `Preclaims` entry pointing at `new`, an Ethereum address that has no corresponding `Claims` balance, while the call still returns `Ok(Pays::No.into())` with no error or event indicating the failed migration.

### Finding Description
In `move_claim`: [1](#0-0) 

- `Claims::<T>::take(&old).map(|c| Claims::<T>::insert(&new, c))` — if `old` has no claim (e.g. already consumed), this is a no-op; nothing is inserted for `new`.
- The `Preclaims` mutation is gated only on `maybe_o == Some(old)`, **not** on whether the `Claims`/`Vesting`/`Signing` migration actually succeeded. If the `preclaim` account's `Preclaims` entry still equals `old` (because it was never cleared), it gets rewritten to `new` regardless of whether `new` now has an actual claim behind it.

The `old` claim can be consumed before `move_claim` executes via the unsigned `claim` extrinsic: [2](#0-1) 
`claim` takes `origin: None` and only requires a valid ECDSA signature recovering to the Ethereum address; it does not touch `Preclaims` at all, and does not require that the caller be the account associated via `Preclaims`. In contrast, `attest` (which does use `Preclaims`) removes the `Preclaims` entry only *after* a successful `process_claim`, and only on the success path: [3](#0-2) 

So the race is: whoever holds/knows the valid `ethereum_signature` for `old` (this is visible in the public mempool once broadcast, since `claim`/`claim_attest` are unsigned extrinsics with the signature embedded as a call parameter) submits `claim(dest, sig)` in the same block or an earlier block than a pending `move_claim(old, new, Some(preclaim_account))`. This drains `Claims::<T>` for `old` via `process_claim`, which removes `Claims`, `Vesting`, `Signing` for `old` but does **not** touch `Preclaims` (that storage map is untouched by `claim`/`claim_attest`, only by `attest`). When `move_claim` then executes:
- `Claims::<T>::take(&old)` returns `None` → nothing is created for `new`.
- The `Preclaims` mutate for `preclaim_account` still finds `Some(old)` (since `claim()` never cleared it) and unconditionally rewrites it to `Some(new)`.

Result: `preclaim_account`'s `Preclaims` entry now points to `new`, but `Claims::<T>::get(new)` is empty. The call returns `Ok(Pays::No.into())` — no error, no event — so the caller (a privileged `MoveClaimOrigin`) has no signal that the remap silently failed to move any funds while still corrupting the `Preclaims` linkage. A subsequent `attest` by `preclaim_account` will hit `process_claim`'s `SignerHasNoClaim` error via `?`, which means `Preclaims::<T>::remove(&who)` is never reached, leaving the account permanently stuck with a `Preclaims` entry pointing at a non-existent claim (`new`) until another privileged `move_claim`/`mint_claim` intervention.

### Impact Explanation
The intended new recipient (whoever is bound via `Preclaims` to the `preclaim_account`) loses the ability to attest/claim under the expected mapping: their `Preclaims` entry is rewritten to reference `new`, which has no backing `Claims` balance, and `move_claim` gives the calling authority no failure signal that the migration didn't actually move any value. This is a state-consistency defect: `Preclaims` and `Claims` can diverge, and the divergence is invisible at the point it is introduced. No direct fund theft occurs (the attacker who called `claim()` only receives funds that were already assigned to `old`'s signature holder), but it enables grief/DoS of the intended claim-migration process for the `preclaim_account` holder.

### Likelihood Explanation
Requires: (1) a claim exists for `old` with a `Preclaims` entry for some account pointing to `old`; (2) a privileged `MoveClaimOrigin`/Root actor has a pending `move_claim(old, new, Some(preclaim))` extrinsic; (3) an unprivileged party who has access to a valid `ethereum_signature` for `old` (visible once broadcast in the public mempool for an unsigned `claim`/`claim_attest` call) submits `claim`/`claim_attest` for `old` so it executes first. This is feasible whenever a `claim`/`claim_attest` transaction for `old` and a `move_claim` for the same `old` are both in-flight — a realistic race during any claims-migration operation, since front-running an unsigned extrinsic already present in the mempool requires no special privilege, only correct call construction (copying signature/dest from the observed pending transaction, or the true key holder self-racing the migration).

### Recommendation
Make `move_claim`'s `Preclaims` remap conditional on the actual migration of the claim, e.g. only rewrite the `Preclaims` entry if `Claims::<T>::contains_key(&new)` after the take/insert (or track whether `Claims::<T>::take(&old)` returned `Some` and short-circuit/skip the `Preclaims` mutation and/or return an error such as `Error::<T>::SenderHasNoClaim`/a new dedicated error if `old` no longer has a claim at call time), so the call fails explicitly instead of silently leaving `Preclaims` pointing at a claim that doesn't exist.

### Proof of Concept
Rust unit test in `polkadot/runtime/common/src/claims/tests.rs` (or an added test module):
1. Set up genesis/mock with a claim for `old` (`Claims::<T>::insert(old, amount)`) and `Preclaims::<T>::insert(preclaim_account, old)`.
2. Call `Claims::claim(RawOrigin::None.into(), attacker_dest, valid_sig_for_old)` — assert `Ok` and that `Claims::<T>::get(old)` is now `None` and `attacker_dest`'s balance increased.
3. Call `Claims::move_claim(RawOrigin::Root.into(), old, new, Some(preclaim_account))` — assert it returns `Ok(Pays::No.into())` (no error surfaced).
4. Assert `Preclaims::<T>::get(preclaim_account) == Some(new)` while `Claims::<T>::get(new)` is `None` — demonstrating the corrupted, unbacked linkage.
5. Call `Claims::attest(RawOrigin::Signed(preclaim_account).into(), statement)` and assert it returns `Err(Error::<T>::SignerHasNoClaim)`, and that `Preclaims::<T>::get(preclaim_account)` is still `Some(new)` afterward (never cleaned up), proving the account is permanently stuck.
