### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header to identify which merchant the event belongs to. Because the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret` shared across every installed shop — not a per-shop secret — an attacker who has installed the app on their own store can capture a legitimate, validly-signed `(raw_body, hmac)` pair from their own shop's webhook traffic and replay it against the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. The signature still validates because the header is never part of the signed content, so the app processes attacker-controlled data as if it came from an arbitrary victim tenant.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC using `verifiable_query.to_signable_string`, and for webhooks that string is defined as just the raw body: [1](#0-0) [2](#0-1) 

The `shop` accessor, however, is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is never included in the signable string: [3](#0-2) 

`Registry.process` validates only the HMAC, then unconditionally forwards `request.shop` (the header value) into `WebhookMetadata` passed to the app's handler: [4](#0-3) [5](#0-4) 

The documented usage pattern explicitly tells integrators to key their tenant/job dispatch off `data.shop`: [6](#0-5) 

The identity-binding equality that should hold is: `hmac == HMAC(secret, raw_body || shop)` (i.e., the tenant identifier must be cryptographically bound to the same secret that authenticates the payload). Instead the gem enforces only `hmac == HMAC(secret, raw_body)` while treating `shop` as trusted, which breaks that equality. Since `secret` (`Context.api_secret_key`) is the app's single `client_secret`, identical across all shops, any shop that installs the app can produce a validly-signed `(raw_body, hmac)` pair (from their own legitimate webhook deliveries) and then re-submit it to the app's webhook endpoint with a different `shop-domain` header value, satisfying `Utils::HmacValidator.validate` while the `shop` field is fully attacker-chosen.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem's own webhook-authentication contract is "if the HMAC validates, the event data — including which shop it belongs to — can be trusted," but the `shop` field used to route/attribute the webhook is outside the signed data. A host application following the gem's documented pattern (dispatch work keyed on `data.shop`) can be made to process or store attacker-supplied webhook bodies under an arbitrary victim shop's identity, i.e., cross-tenant data injection/confusion using only the attacker's own (non-privileged) app installation.

### Likelihood Explanation
Any merchant/unprivileged internet user can install a public app on their own store, which is a normal, unauthenticated action requiring no special access to the app's `client_secret`, access tokens, or other shops. Once installed, they legitimately receive HMAC-signed webhook deliveries for their own shop and can replay the body+HMAC with a modified `shop-domain` header. No secret material or privileged credential is required beyond what a normal app-install grants; the only work needed is capturing one's own webhook traffic and re-POSTing it with a changed header, which is straightforward.

### Recommendation
Bind the shop identifier into the HMAC-validated payload rather than trusting an unauthenticated header:
- Include `shop-domain` (and ideally `topic`/`webhook-id`) in `to_signable_string`, or independently verify the header value against a value derived from the signed body/registration (e.g., cross-check against Shopify's separately-fetched webhook subscription record) before constructing `WebhookMetadata`.
- At minimum, document prominently that `data.shop` is not authenticated by the HMAC and must not be used as a sole tenant key without additional verification (e.g., confirming the shop has an active, matching session/webhook registration).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged action).
2. Shopify sends the attacker's shop a legitimate webhook, e.g. `orders/create`, to the app's callback URL with headers `x-shopify-hmac-sha256: <valid_hmac>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, and some `raw_body`.
3. Attacker captures `raw_body` and `x-shopify-hmac-sha256` from this legitimate delivery.
4. Attacker POSTs to the same webhook endpoint again, reusing the identical `raw_body`/`x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(api_secret_key, raw_body)` — this still matches since `raw_body` is unchanged (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), and the host application — following the gem's documented pattern — attributes/queues the attacker-controlled webhook body to the victim tenant.
