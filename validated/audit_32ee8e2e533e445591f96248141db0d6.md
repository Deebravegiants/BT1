### Title
Webhook Tenant Identity (Shop Domain) Not Bound to HMAC Signature — Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity used for routing and processing (`shop`, `topic`, `webhook_id`) entirely from unauthenticated HTTP headers, while `Utils::HmacValidator` only verifies the raw request body. Any party holding one valid `(body, hmac)` pair for the app's shared `client_secret` — e.g., a legitimate webhook delivered to their own installed shop — can resubmit that same body/HMAC pair to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header, and the signature check will still pass.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

but the values that identify *which tenant* the webhook belongs to — `shop`, `topic`, and `webhook_id` — are read directly from headers that are never included in the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)`, and then unconditionally trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes/compares the signature purely from `to_signable_string`, i.e. the body bytes, with no binding to headers: [4](#0-3) 

This breaks the intended identity binding `HMAC(body) == HMAC(body, shop)`: the signature only proves the body was produced by an entity holding the app's `client_secret` for *some* delivery, not that it was produced *for the shop named in the header*. Because a single app-wide `client_secret` signs webhooks for every shop that installs the app, an unprivileged merchant/attacker who legitimately installs the app receives real, validly-signed webhooks for their own shop. They can capture one `(raw_body, X-Shopify-Hmac-Sha256)` pair and replay it against the same endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header rewritten to a victim shop. The HMAC check still succeeds, and `Registry.process` invokes the registered handler believing the event originates from the victim shop, with attacker-controlled body content.

### Impact Explanation
This is a cross-tenant boundary break: the value used to scope a webhook event to a merchant/tenant (`shop`) is not bound to the cryptographic proof of authenticity. A single attacker who is merely an installer of the app (no elevated privileges, no access token, no `client_secret`) can forge webhook events that the host application will attribute to a different, arbitrary shop, injecting attacker-controlled data (order/product/customer payloads, GDPR-topic payloads, etc.) into another tenant's processing pipeline. Depending on how the host app uses webhook data (e.g., updating local per-shop records, triggering fulfillment, deleting/redacting customer data for `customers/redact`), this can lead to cross-tenant data corruption or unauthorized actions performed "on behalf of" another shop.

### Likelihood Explanation
Requires only that the attacker be able to install the target app on their own shop (or otherwise obtain one legitimately-signed webhook delivery), then send a crafted HTTP request to the app's public webhook endpoint with a substituted shop-domain header and the captured body/HMAC — no access token, no `client_secret`, and no interaction with the victim shop needed.

### Recommendation
Bind the tenant/topic identity into the verified signable content, or otherwise cryptographically tie the `shop`/`topic` headers to the signature before trusting them (e.g., have the gem's `HmacValidator`/`Request` API require callers to separately confirm the `shop-domain` against a known/expected value per installation, or document explicitly that the header is untrusted and must be cross-checked by the host app against session/install records before being used for tenant-scoped side effects).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook delivery with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(client_secret, B)`).
2. Attacker resends a request to the same webhook endpoint with:
   - Body: `B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (changed)
   - `X-Shopify-Topic`: unchanged or changed to any registered topic
3. `Utils::HmacValidator.validate(request)` recomputes `HMAC(client_secret, B)`, matches `H`, and returns `true` — see [5](#0-4)  and [1](#0-0) .
4. `Registry.process` proceeds and calls the registered handler with `shop: request.shop` set to `victim-shop.myshopify.com`, even though the payload actually originated for `attacker-shop.myshopify.com` — see [3](#0-2) .
