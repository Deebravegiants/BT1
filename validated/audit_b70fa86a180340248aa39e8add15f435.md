### Title
Webhook `shop` (and `topic`) identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only, while the `shop` (and `topic`) values used by the host application come from separate, unsigned HTTP headers. Any party who can obtain one validly-HMAC-signed webhook payload (e.g., by installing the app on their own store) can replay that same body/HMAC pair while substituting the `shopify-shop-domain` header for a different, victim shop, causing the host application to process attacker-controlled data as if it belongs to another tenant.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` verifies a `VerifiableQuery`'s HMAC by computing `OpenSSL::HMAC.hexdigest` over `to_signable_string` with the app's `api_secret_key`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only the raw request body: [2](#0-1) 

However, `Request#shop` and `Request#topic` are derived from separate HTTP headers (`shopify-shop-domain`, `shopify-topic`) that are **not** included in the signable string: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then trusts `request.shop` and `request.topic` directly, passing them into the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

This breaks the identity binding: `hmac(body) == valid` is meant to prove "Shopify (holder of `api_secret_key`) vouches for this webhook for shop X," but the gem lets an attacker supply any `shop` value independent of what was actually signed, i.e. `verified_body != claimed_shop`.

### Impact Explanation
An unprivileged internet user can install the target app on their own store (a normal, unprivileged action) and receive a legitimately Shopify-signed webhook for that store — obtaining a valid `(raw_body, hmac)` pair. They can then replay that exact body and HMAC to the app's webhook endpoint while changing only the `shopify-shop-domain` (and optionally `shopify-topic`) header to name a different, victim shop. Because `HmacValidator.validate` only checks the body against the secret, the forged request passes validation, and `Registry.process` calls the handler with `data.shop` set to the victim shop even though the body/HMAC never attested to that shop. Any host application logic keyed on `data.shop` (e.g., updating shop-scoped records, uninstall/GDPR handlers, billing state, or triggering the app's own webhook-driven mutations) can be tricked into acting on/against a different tenant than the one that actually produced the signed payload — a cross-tenant identity confusion. This matches the Critical-impact category "cross-tenant access."

### Likelihood Explanation
Likelihood is high: no leaked secret is required, only the ability to install the app on an attacker-owned store (a normal onboarding flow) to harvest one valid `(body, hmac)` pair per topic, plus simple header manipulation on replay — both well within the reach of an unprivileged internet user described in the rules.

### Recommendation
Bind the identity fields to the signature: include `shop`/`shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) in the HMAC-signable string (as Shopify does for OAuth `AuthQuery` via `to_signable_string`), or otherwise cryptographically bind the header-derived shop to the signed body before trusting it in `Registry.process`/`WebhookMetadata`. At minimum, document/require that consuming applications independently verify `data.shop` against their own installed-shop records rather than trusting it implicitly as HMAC-verified.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook, capturing the genuine request: `raw_body = B`, `headers["shopify-hmac-sha256"] = H` (valid for `B` under the app's `api_secret_key`), `headers["shopify-shop-domain"] = "attacker-shop.myshopify.com"`.
2. Attacker resends to the app's webhook endpoint with the same `raw_body = B` and `shopify-hmac-sha256 = H`, but sets `shopify-shop-domain: "victim-shop.myshopify.com"`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H`: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled body content as belonging to `victim-shop`.
