## Title
Withdraw slippage protection (`min_coin_amount`/`min_pc_amount`) is entirely optional and silently skipped when omitted - (File: `program/src/processor.rs`)

### Summary
The `Withdraw` instruction accepts `min_coin_amount` and `min_pc_amount` as `Option<u64>` fields that a caller can simply choose not to include in the instruction data. When either is absent, `process_withdraw` skips the slippage check entirely and pays out whatever `coin_amount`/`pc_amount` the current pool ratio yields, mirroring the reported bug class of passing a `0`/no minimum to a liquidity-removal call.

### Finding Description
The `WithdrawInstruction` struct defines the minimum-amount fields as optional, and the unpacker only populates them if 16 extra trailing bytes are present in the instruction data, defaulting to `None` otherwise: [1](#0-0) 

In `process_withdraw`, the resulting `coin_amount`/`pc_amount` (computed from the pool's current, run-time vault balances) is only compared against the minimums when **both** `min_coin_amount` and `min_pc_amount` are `Some`: [2](#0-1) 

If a caller constructs the instruction without the optional trailing bytes (a valid, unpack-accepted instruction), `withdraw.min_coin_amount` and `withdraw.min_pc_amount` are `None`, and the `if withdraw.min_coin_amount.is_some() && withdraw.min_pc_amount.is_some()` guard is `false`, so the code proceeds straight to transferring `coin_amount`/`pc_amount` with **no slippage check whatsoever**, regardless of how the pool ratio has moved since the transaction was built: [3](#0-2) 

This is directly analogous to the reported Curve issue where `remove_liquidity_one_coin` is called with `_min_amount = 0`: the withdrawer has no on-chain guarantee about the amount received, and can be sandwiched by another party executing a swap immediately before the withdraw (skewing `total_pc_without_take_pnl`/`total_coin_without_take_pnl`) to reduce `coin_amount`/`pc_amount` paid out, then reversing the swap afterward to capture the difference.

### Impact Explanation
An LP withdrawing liquidity without the optional minimums (which is a fully valid, program-accepted instruction encoding, not an error condition) can be sandwiched by an attacker's swap in the same block/transaction ordering window, causing the LP to receive fewer coin/pc tokens than the pool's balance actually entitles them to at submission time. This is a direct loss of user (LP) funds via price manipulation, matching the required impact bar (concrete theft of LP funds).

### Likelihood Explanation
Any unprivileged actor can construct and submit a `Withdraw` instruction with the trailing minimum bytes omitted (this only requires standard SPL/RPC client behavior; wallets/SDKs that don't always populate the optional fields, or intentionally malicious builders, can produce this instruction), and any other unprivileged actor can front-run it with `SwapBaseIn`/`SwapBaseOut` in the same or an adjacent transaction to manipulate `amm_coin_vault.amount`/`amm_pc_vault.amount` before the withdraw executes. Both paths (`Withdraw`, `SwapBaseIn`) are explicitly in-scope, reachable from a single submitted transaction with attacker-chosen data.

### Recommendation
Make slippage protection mandatory rather than optional for `Withdraw`: require `min_coin_amount` and `min_pc_amount` to always be present (or enforce a sane default that at least floors the acceptable payout), and reject the instruction if only one of the two is supplied instead of silently disabling the check. Alternatively, always evaluate the check for whichever bound is provided instead of requiring both to be `Some` simultaneously.

### Proof of Concept
1. Attacker observes a pending `Withdraw` transaction from victim LP in the mempool/leader schedule, built without the optional `min_coin_amount`/`min_pc_amount` bytes (16-byte suffix), which is a valid encoding per the unpacker at `program/src/instruction.rs:372-386`.
2. Attacker submits a `SwapBaseIn`/`SwapBaseOut` transaction ahead of the victim's withdraw to skew `amm_coin_vault.amount`/`amm_pc_vault.amount`.
3. Victim's `Withdraw` executes: since `min_coin_amount`/`min_pc_amount` are both `None`, the guard at `program/src/processor.rs:1780` never triggers, and the victim receives `coin_amount`/`pc_amount` computed off the manipulated vault balances (`program/src/processor.rs:1756-1761`), which can be less favorable than the un-manipulated ratio.
4. Attacker reverses the swap afterward, netting the difference extracted from the victim's withdrawal.
