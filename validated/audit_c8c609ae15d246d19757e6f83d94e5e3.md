### Title
Beneficiary-controlled revert in `IntentGatewayV2.withdraw`/`onAccept` can DoS relayer delivery of `RedeemEscrow`/`RefundEscrow`/`SweepDust` messages - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.onAccept` handles `RedeemEscrow`, `RefundEscrow` and `SweepDust` ISMP messages by calling an internal `withdraw()` function (or an inline loop for `SweepDust`) that pays out native ETH to a `beneficiary`/`req.beneficiary` address taken directly from the message body via a raw `.call{value: amount}("")`, and immediately `revert`s the entire `onAccept` call if that transfer returns `false`. [1](#0-0) [2](#0-1)  Because `beneficiary`/`order.user` is attacker-controlled data embedded in the intent (set at order creation time by the order's own user, who is an unprivileged actor), a beneficiary address can be a contract whose `receive()`/fallback intentionally reverts (or consumes excess gas / returns huge `returndata`), causing the whole incoming ISMP message delivery to fail and revert. This matches the report's bug class: a low-level `.call` payout that can be forced to fail by the payee, causing the entire transaction (and the relayer's delivery, plus any other unrelated payouts batched in the same loop, e.g. other `SweepDust` outputs) to be reverted.

### Finding Description
`onAccept` in `IntentGatewayV2.sol` is invoked by the host for `RedeemEscrow`/`RefundEscrow` messages and dispatches to `withdraw()`: [3](#0-2) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    ...
    if (token == address(0)) {
        (bool sent,) = beneficiary.call{value: amount}("");
        if (!sent) revert InsufficientNativeToken();
    }
    ...
``` [1](#0-0) 

`beneficiary` is `order.user` (the original order creator, an unprivileged party who submits the intent), so any user placing an order can set it (or, for `RedeemEscrow`, the filler-derived path) to a smart contract designed to revert on receiving native tokens. When the relayer delivers the corresponding proof to `onAccept`, the transfer fails, `withdraw()` reverts with `InsufficientNativeToken`, and the entire `onAccept` call (and hence the whole message-delivery transaction) reverts.

The same pattern repeats in the `SweepDust` branch, which loops over multiple `TokenInfo` outputs and pays each one out with the same unguarded `.call{value: amount}("")`/`revert` pattern inside the loop: [2](#0-1) . If even one `req.beneficiary` in that batch is a griefing contract, the entire batch of dust sweeps reverts, DoS-ing payouts to all other beneficiaries in the same message.

This mirrors the analog report's root cause: use of an unrestricted low-level `.call` whose failure unconditionally reverts the whole transaction, letting an unprivileged party (the order's own beneficiary/user, analogous to the "operator" in the report) hold hostage the withdrawal/settlement of escrowed funds for themselves and, in the `SweepDust` case, for other unrelated parties batched in the same call.

### Impact Explanation
For `RedeemEscrow`/`RefundEscrow`: a griefing beneficiary can permanently block redemption or refund of their own escrowed order by having their beneficiary address always revert on `receive()`. While this only self-DoS's their own funds directly, it can be leveraged to freeze escrowed input tokens indefinitely (since `_filled[commitment]` is set before the transfer in `withdraw()`, retries of the same commitment would behave inconsistently/permanently fail since state is already marked filled), leading to a stuck order and frozen escrow funds. For `SweepDust`: because multiple beneficiaries are processed in a single `onAccept` call, one malicious beneficiary can revert the entire batch, denying dust-sweep payouts to every other beneficiary included in that message and forcing the relayer's proof-submission transaction to fail repeatedly (grief/DoS against relayer gas and against other legitimate beneficiaries' redemption of dust). This is a fund-freezing / message-delivery-DoS issue reachable from a single unprivileged intent/order submission, satisfying "permanent freezing of funds" / "route unable to deliver messages" criteria.

### Likelihood Explanation
High: any user creating an order (unprivileged, permissionless) fully controls the `beneficiary`/`user` field embedded in the order, and deploying a fallback-reverting contract is trivial and costs nothing beyond normal transaction gas. No special privileges, front-running, or race conditions are required — the attacker simply sets their beneficiary/refund address to a reverting contract before the relayer submits the redeem/refund/sweep proof.

### Recommendation
Replace the direct `.call{value: amount}("")` + `revert` pattern in `withdraw()` and the `SweepDust` branch with a payout mechanism that cannot block the rest of the message:
- Use a low-level call restricted to zero/minimal `returndata` (e.g. via inline assembly capturing only enough gas to prevent return-bomb gas griefing), and
- On failure, do not `revert` the entire message; instead credit the beneficiary a claimable/pull-based balance (or emit an event and continue processing remaining outputs) so a single malicious/broken beneficiary cannot block their own or others' payouts.
- In particular, for the `SweepDust` loop, isolate each transfer's failure so one bad beneficiary does not revert the whole batch.

### Proof of Concept
1. Attacker creates an escrow order via `IntentGatewayV2` with `order.user` set to a contract `Griefer` whose `receive() external payable { revert(); }`.
2. The order source-chain input tokens are escrowed as normal.
3. On fill/expiry, Hyperbridge dispatches a `RedeemEscrow`/`RefundEscrow` POST request back to the source chain's `IntentGatewayV2`.
4. When the relayer delivers this proof, `onAccept` → `withdraw()` executes `beneficiary.call{value: amount}("")` against `Griefer`, which reverts.
5. `withdraw()` reverts with `InsufficientNativeToken`, reverting the entire `onAccept` transaction — the escrow can never be redeemed/refunded, and (for `SweepDust`) any other outputs batched in the same message also fail to be paid out. [4](#0-3)
