### Title
Webhook HMAC only authenticates the raw body, not the `shop` header, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook exclusively via `Utils::HmacValidator.validate(request)`, which HMACs `request.to_signable_string`. For `Webhooks::Request`, that signable string is the raw HTTP body only, while the `shop` value that is handed to the application's webhook handler is read from the `x-shopify-shop-domain` header, a value the HMAC never covers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate_signature` computes the HMAC purely over that signable string and compares it to the `hmac` field: [2](#0-1) 

`Registry.process` accepts the request once that body-only HMAC checks out, then forwards `request.shop` (sourced from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header) straight into the handler: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `HMAC-verified bytes == bytes the handler trusts as belonging to a specific shop`. Here that equality fails — the HMAC binds only the body, but the handler's tenant-identifying field (`shop`) is parsed from a separate, unsigned header. This is the same class of bug as the `transfer()` report: a field that downstream logic acts on (`vendor`/`shop`) is not actually covered by the mechanism (gas forwarding/HMAC) that is supposed to make it trustworthy.

### Impact Explanation
The `api_secret_key` for an app is shared across every shop that installs it. A malicious merchant who has installed the app therefore legitimately receives real, validly-HMAC-signed webhook deliveries from Shopify for their own shop. Because the HMAC signs only the JSON body and not the shop domain, that same captured `(body, hmac)` pair remains valid if replayed to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to name a different, victim shop. The app will treat the forged request as an authentic event "from" the victim shop (cross-tenant), running the registered handler logic (`handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))`) with attacker-supplied body content attributed to another tenant. Depending on what the host application's handlers do with `shop` (e.g., look up/create tenant records, trigger uninstall/GDPR flows, update billing state, or write order/product data keyed by shop), this can lead to cross-tenant data corruption or spoofed tenant-scoped actions — matching the "cross-tenant access" impact bucket.

### Likelihood Explanation
Exploitation requires only that the attacker be an existing (even trial/free) installer of the target app — no special privilege beyond normal merchant self-service install is needed, and no access token, `api_secret_key`, or credential leak is required, since the attacker reuses a webhook payload Shopify itself validly signed for their own shop. Capturing and replaying an HTTP request with modified headers is straightforward.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook-id`) values in the signable string used for webhook HMAC verification, or otherwise cryptographically bind the shop domain to the verified payload before it is trusted, e.g., by validating that the shop domain is expected/known for this integration and rejecting mismatches, or verifying it against Shopify's per-shop webhook secret registration if available.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook (e.g., `orders/create`) with headers including `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-raw-body>`, and some JSON body `B`.
2. Attacker intercepts this request (their own webhook, so this is trivial) and replays `POST /webhooks` to the app with the same raw body `B` and same `x-shopify-hmac-sha256`, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`, which HMACs `request.to_signable_string` (`= B`, unchanged) — validation succeeds.
4. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, so the app processes attacker-controlled data as if it originated from `victim-shop.myshopify.com`.
