### Title
Remote config update reports `{ success: true }` even when the persisted write to `remoteConfigAtom` fails - (File: `features/remote-config/module/index.ts`)

### Summary
`RemoteConfig.update()` in `features/remote-config/module/index.ts` mirrors the reported StakingRewards bug class: an operation whose write to durable storage can fail asynchronously is not awaited/verified, yet the function still reports success and mutates in-memory state that downstream consumers treat as authoritative. [1](#0-0) 

### Finding Description
In `update()`, once a new remote config is fetched and detected to differ from the current value, the module immediately updates its in-memory `#current` value and fires the persistence write without awaiting it: [2](#0-1) 

```js
if (changes) {
  this.#current = this.#freeze(config)
  this.#logger.debug('updated config with changes from remote')

  void this.#remoteConfigAtom.set({
    config,
    lastModified,
    remoteConfigUrl: this.#remoteConfigUrl!,
  })
}

this.#resolveLoaded!()
return { success: true }
```

The `void` on `this.#remoteConfigAtom.set(...)` explicitly discards the promise. Because this call is not awaited, any rejection from the underlying storage atom write (I/O error, quota exceeded, serialization failure, etc.) is not caught by the enclosing `try/catch` (which only wraps the synchronous portion of the function and the awaited calls above it) - it becomes an unhandled promise rejection. Regardless of whether the write actually lands in durable storage, `update()` unconditionally returns `{ success: true }` and resolves `#resolveLoaded`, and `#current` (the value returned by `get()`/`getAll()` to the rest of the app) has already been mutated to the fetched value. This is the same root cause as the report: a side-effecting write's success/failure is decoupled from the "operation succeeded" accounting update, letting bookkeeping diverge from the actual persisted state.

### Impact Explanation
If the fire-and-forget persistence write to `remoteConfigAtom` fails, the in-memory `#current` still reflects the new remote config for the remainder of the session (all consumers of `remoteConfig.get()`/`getAll()` see the "new" values), while the persisted atom retains stale data. On the next app restart, `#current` is reinitialized from the atom's persisted (stale) value. Whether this rises to a wallet-compromise-level impact depends entirely on what specific keys/flags are distributed via remote config (e.g., feature kill-switches, security-relevant toggles, asset/contract allow-lists). I could not find in the available index any consumer of remote config that gates a signing, authentication, or origin-isolation decision directly on this data, so I cannot confirm a concrete "unauthorized signing / secret disclosure / auth bypass / cross-origin privilege bleed" outcome from this specific code path. [3](#0-2) 

### Likelihood Explanation
The failure mode requires the underlying storage write to fail after a successful fetch, which is a plausible but not everyday occurrence (storage full, IPC/atom backend failure, corruption). Because the rejection is unhandled (`void`), there's also a secondary risk of an unhandled promise rejection crashing/restarting the process in environments that terminate on unhandled rejections, compounding the inconsistency between `#current` and the persisted atom on subsequent loads.

### Recommendation
Await the `remoteConfigAtom.set(...)` call inside the existing `try/catch`, and only update/report success once persistence is confirmed; if persistence fails, do not treat the update as successful (revert `#current` or surface the error) so callers relying on `get()`/`getAll()` aren't left in a state inconsistent with what's actually durably stored:
```js
if (changes) {
  await this.#remoteConfigAtom.set({
    config,
    lastModified,
    remoteConfigUrl: this.#remoteConfigUrl!,
  })
  this.#current = this.#freeze(config)
  this.#logger.debug('updated config with changes from remote')
}
```

### Proof of Concept
1. Instantiate `RemoteConfig` with a `remoteConfigAtom` whose `set()` rejects (e.g., mock storage that throws on write, simulating disk-full/IPC failure).
2. Call `update()` with a `fetch` mock returning a new config different from the current one.
3. Observe: `update()` resolves with `{ success: true }`, `getAll()`/`get()` now return the new fetched config (in-memory `#current` updated), but the unhandled rejection from `#remoteConfigAtom.set` is never surfaced, and a subsequent process restart would load the old, unpersisted config from the atom - demonstrating the same "operation reports success while the underlying write silently fails" divergence described in the source report.
