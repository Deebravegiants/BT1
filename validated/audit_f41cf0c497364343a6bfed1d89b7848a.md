### Title
Webhook HMAC only signs the raw body, allowing shop/topic header spoofing on replay — cross-tenant webhook confusion - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over that same signable string, then trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all of which come straight from unauthenticated HTTP headers — to build the `WebhookMetadata` passed to the app's handler. Nothing in the signature binds the shop/topic identity to the signed bytes, so a valid `(body, hmac)` pair captured from one legitimate webhook delivery can be replayed with a different `shop-domain` or `topic` header and will still pass HMAC validation.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled directly from headers with no cryptographic binding: [3](#0-2) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, i.e. the raw body only: [4](#0-3) 

`Registry.process` checks only this body-only HMAC, then immediately trusts the unauthenticated header-derived `request.shop`/`request.topic`/`request.webhook_id` to construct `WebhookMetadata` and dispatch to the app's handler: [5](#0-4) 

The binding that should hold is: `shop/topic authenticated by the signature == shop/topic acted on by the handler`. Because the signature only covers the body bytes, this equality does not hold — an attacker who has legitimately received one webhook (with a valid body+HMAC pair, e.g. for their own shop) can resend that exact same HTTP request to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a different shop the app has installed, or substituting `x-shopify-topic` for a different registered topic. `HmacValidator.validate` still passes because it never inspects those headers, and `Registry.process` will hand the (unmodified) body content to the handler under the spoofed shop/topic identity.

### Impact Explanation
This breaks tenant isolation between the app's merchants: a handler that uses `WebhookMetadata#shop` to determine which merchant's records to update (a documented, expected usage pattern, since `WebhookMetadata` explicitly carries `shop` for that purpose) can be made to apply another shop's legitimate webhook payload to an unrelated shop's tenant context, or to dispatch a payload intended for one topic into the handler registered for a different topic. This is a cross-tenant data-integrity issue reachable by any unprivileged internet user who can capture one legitimate `(body, hmac)` pair (e.g., from their own store's outbound webhook, which is normal, non-privileged access) and replay it against the app's public webhook endpoint with forged headers.

### Likelihood Explanation
Webhook endpoints are public HTTP endpoints by design (Shopify calls them over the internet), so no credentials or privileged access are needed to reach `Registry.process`. Obtaining one valid `(body, hmac)` pair only requires being a normal merchant/user of the app on any shop — a low bar. Constructing the replay request with modified headers is trivial once a valid pair is captured.

### Recommendation
Include the shop domain, topic, and webhook id in the signed material (or otherwise cryptographically bind the header values used for dispatch), e.g., by having `to_signable_string` incorporate `shop`, `topic`, and `webhook_id` alongside the raw body, so that `HmacValidator.validate` fails if any of those headers are altered relative to what Shopify originally signed for.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com`, topic `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC_SHA256(secret, B)` (per `lib/shopify_api/webhooks/request.rb` line 36-38 and `lib/shopify_api/utils/hmac_validator.rb` line 26-31).
2. Attacker (any user who can trigger/observe this webhook, e.g. on their own store) replays the exact same request to the app's public webhook endpoint but changes `x-shopify-shop-domain` to `shop-b.myshopify.com` (a different shop installed on the same app) and/or changes `x-shopify-topic` to another topic the app has registered.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (the unchanged body `B`) and successfully matches `H` (per `lib/shopify_api/utils/hmac_validator.rb` line 27-31), because the headers are never part of the signed bytes.
4. `Registry.process` looks up the handler for the (possibly attacker-chosen) `request.topic` and invokes it with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the spoofed header values (per `lib/shopify_api/webhooks/registry.rb` line 190-199), causing the app to process shop-A's payload under shop-B's identity (or under the wrong topic handler).
