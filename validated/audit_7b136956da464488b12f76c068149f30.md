## Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
The reported bug class is a broken identity/authorization binding: an action (`close()`) is permitted without checking a value (accrued interest) that should have gated it. The same "acted-on-but-unverified" pattern exists in this gem's webhook processing: the `shop` used to dispatch webhook payloads to app handlers is read from an HTTP header that is **not** part of the HMAC-signed payload, so it can be swapped without invalidating the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string`: [3](#0-2) 

`Registry.process` validates that HMAC, then immediately trusts `request.shop` (sourced from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is entirely outside the signed material) to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

The identity binding that should hold is: `shop-domain header == tenant the signed body actually belongs to`. Because only `raw_body` is signed, this equality is never checked — the header can be replaced with any value while the HMAC still validates, as long as the attacker has *any* valid `(raw_body, hmac)` pair signed with the app's `api_secret_key`. Any merchant that installs the app can trivially obtain such a pair for their own store's webhooks (the HMAC secret is the app-wide `client_secret`, identical across all tenants, not shop-specific). That merchant can then replay the same body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header of a victim shop, and `Registry.process` will dispatch the payload to the handler as if it genuinely originated from the victim tenant.

### Impact Explanation
This breaks the tenant boundary the whole webhook system is meant to enforce: `WebhookMetadata#shop` — which app code uses to route/apply webhook data to the correct merchant's session/records — can be attacker-controlled by any existing (even free/unprivileged) merchant of a multi-tenant app, without any credential beyond having installed the app once. That is cross-tenant data injection/corruption, matching the "cross-tenant access" critical-impact category.

### Likelihood Explanation
Any user who can install the app (a normal signup, no special privileges) can capture a legitimately-signed webhook body/HMAC for their own shop and replay it to the same public webhook endpoint with a forged shop-domain header. No secrets beyond what is inherently disclosed to any tenant are required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material verified against the tenant context, or independently authenticate `request.shop` against the resolved session/tenant before dispatching to handlers, so the HMAC check and the tenant-attribution check bind to the same data.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com`; trigger any webhook (e.g. `orders/create`) to capture `raw_body` and the corresponding `x-shopify-hmac-sha256` value sent by Shopify.
2. Replay that exact `raw_body` + HMAC header to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC.
4. `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and calls the app's handler, which processes attacker-controlled data as if it belongs to `victim.myshopify.com`.
