### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant shop spoofing via webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only, while the `shop` (merchant identity) is taken from a separate, unsigned HTTP header. `Registry.process` verifies the HMAC and then dispatches to the app's handler using this unverified `shop` value, breaking the equality "shop authenticated == shop acted upon."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which plays no part in the signable string: [2](#0-1) 

`Registry.process` calls `Utils::HmacValidator.validate(request)`, which only verifies `request.to_signable_string` (the body) against `request.hmac`: [3](#0-2) [4](#0-3) 

After the HMAC check passes, `process` builds `WebhookMetadata` directly from `request.shop` (the unverified header) and hands it to the app's `handler.handle`: [5](#0-4) [6](#0-5) 

Contrast this with `Auth::Oauth::AuthQuery`, where the analogous identity field `shop` *is* included in the signed string: [7](#0-6) 

Because a single `api_secret_key` is shared across every shop that installs the same app, any merchant (an unprivileged internet user with respect to other tenants) that installs the app receives genuine, correctly-signed webhooks for their own shop. Since the HMAC only binds the body, that attacker can capture a valid `(raw_body, hmac)` pair from their own real webhook and replay it to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` will still pass (it only checks the body/secret), and `WebhookMetadata#shop` will be poisoned with the attacker-chosen value that the app's `handler.handle` trusts for tenant identification.

### Impact Explanation
This breaks the binding "the shop that produced a signature == the shop the payload is attributed to," letting one tenant's genuine webhook be attributed to a different tenant. Applications built on this gem (and the gem's own `Registry` dispatch) use `WebhookMetadata#shop` as the tenant key when applying webhook data (e.g., updating shop records, order/inventory data, GDPR/compliance webhooks). A malicious merchant can therefore inject spoofed but "HMAC-valid" events for another shop, i.e., a cross-tenant write/access using only credentials to their own installed instance of the same app. This matches the "Critical - cross-tenant access" impact bucket.

### Likelihood Explanation
Any account holder who installs the app on a real Shopify store (unprivileged relative to other tenants, no access to `api_secret_key` needed) can trigger a real webhook from their store, capture the raw body and header, and replay it to the app's public webhook endpoint with a modified `shop` header — a straightforward, low-effort attack with no special access required.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the HMAC-signable material, or otherwise cryptographically bind the shop identity used for dispatch to the value that was authenticated, mirroring what `Auth::Oauth::AuthQuery#to_signable_string` already does for the OAuth callback. At minimum, `Request#to_signable_string` should incorporate the shop-domain header so `HmacValidator.validate` fails if that header is altered independently of the body/signature.

### Proof of Concept
1. App developer configures a single `api_secret_key`/`client_secret` for their multi-tenant Shopify app.
2. Attacker installs the app on their own shop `attacker.myshopify.com`, and Shopify sends a real webhook: body `B`, `x-shopify-hmac-sha256: H` (valid HMAC of `B`), `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays this exact request to the app's webhook endpoint but changes only the header:
   `x-shopify-shop-domain: victim.myshopify.com`
   keeping body `B` and `x-shopify-hmac-sha256: H` unchanged.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates `H` against `B` and the shared `api_secret_key` — this still passes because `to_signable_string` never included the shop header. [8](#0-7) 
5. `Registry.process` constructs `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body:, ...)` and invokes the app's `handler.handle`, which now processes attacker-controlled data as if it belonged to `victim.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
