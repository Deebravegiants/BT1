### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic for a given shop once `Utils::HmacValidator.validate` succeeds, but the HMAC only ever signs the raw request body — never the `shop` value that the same request carries and that gets handed to the app's handler as the tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request#shop` is read straight from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` HTTP header, with no cryptographic binding to the rest of the request: [1](#0-0) 

The value that is actually HMAC-verified is only the raw body, via `to_signable_string`: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the body) and the app's shared `api_secret_key`: [3](#0-2) 

`Registry.process` performs exactly that body-only HMAC check and then, on success, forwards `request.shop` — the unauthenticated header value — into `WebhookMetadata` for the app's handler to act on: [4](#0-3) 

The identity binding the library implicitly claims to enforce is:
`HMAC_valid(request) == (body_authentic AND shop_authentic)`

but the actual binding enforced is only:
`HMAC_valid(request) == body_authentic`

`shop` is a field acted on (passed to the handler as the tenant key) but not covered by the HMAC.

Because `api_secret_key` is the single shared secret for the app across **all** shops that install it (not per-tenant), any merchant who installs the app in their own store can trigger an event, capture the resulting valid `(raw_body, hmac)` pair delivered to their own endpoint, and then replay that exact body+signature to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header (e.g., a victim tenant's domain). `HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` will dispatch the forged payload to the handler tagged with the victim shop, producing cross-tenant data injection/impersonation.

### Impact Explanation
This breaks a tenant identity boundary: an attacker-controlled (but validly-signed) webhook can be attributed to any other shop of the same app, causing the app to record, act on, or leak data under a different tenant's identity — cross-tenant access, matching the Critical impact category.

### Likelihood Explanation
Any unprivileged user who installs the app in their own Shopify store (a normal, unprivileged action) can capture a legitimately-signed webhook and replay it with a forged shop header — no access to `api_secret_key`, access tokens, or the target tenant is required. This is directly reachable through the gem's own documented webhook-processing API (`Registry.process`); no host-application misuse is required, since the library's method signature and validation logic never surface or bind the `shop` header at all.

### Recommendation
Include the tenant-identifying header(s) (`shop`, and ideally `topic`/`webhook-id`) in the value that is HMAC-verified, or alternatively require callers to supply the list of currently-installed shop domains and have `Registry.process` reject any request whose header `shop` is not in that allow-list. At minimum, document prominently that `request.shop` is unauthenticated and must be cross-checked by the host application against its own session/install store before being trusted, since `HmacValidator.validate` provides no such guarantee.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` (legitimate, unprivileged install).
2. Attacker triggers a webhook event (e.g., `orders/create`) in their own store; Shopify delivers a POST to the app with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `B` and the valid HMAC value.
4. Attacker (or a colluding party) sends a new POST to the same app webhook endpoint with the identical body `B` and identical HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` only look at the body, so `Utils::HmacValidator.validate` returns `true` (per `lib/shopify_api/utils/hmac_validator.rb` lines 12-31).
6. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-200) invokes the handler with `shop: "victim-shop.myshopify.com"`, causing the app to process/store attacker-controlled data as though it came from the victim tenant.

        def validate(verifiable_query)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
