## Finding

### Title
Unauthenticated `CallDispatcher.dispatch` allows anyone to drain any funds or exploit standing allowances held by the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
The SushiSwap PoC's root cause is a router that executes an attacker-supplied, unchecked instruction blob (`route`) without verifying that the entity invoking privileged internal logic (the swap callback) is an authorized counterparty — letting the attacker make the router itself act as an unwitting party in a transfer. The direct analog here is `CallDispatcher.dispatch`, the shared execution primitive used by `IntentGatewayV2`'s predispatch/postdispatch calldata feature, which has **no caller restriction whatsoever**.

### Finding Description
`CallDispatcher.dispatch` is declared `external` with no modifier and no `msg.sender` check: [1](#0-0) 

`IntentGatewayV2.placeOrder` uses this single, shared dispatcher instance (`_params.dispatcher`) for every order in the protocol: it pushes user-supplied `predispatch.assets` to the dispatcher, calls `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` to run arbitrary attacker-crafted `Call[]` (target/value/data, fully user controlled), and only afterward sweeps the dispatcher's token/ETH balance back into escrow: [2](#0-1) 

Because `dispatch()` itself enforces no access control, **any address — not just `IntentGatewayV2`** — can call it directly at any time with any `Call[]` payload, executing calls "as" the `CallDispatcher` contract. The contract also has an unrestricted `receive()`: [3](#0-2) 

This is the same class of bug as the SushiSwap PoC: a shared, funds-adjacent dispatcher trusts caller-supplied instructions without checking that the caller is the authorized module (`IntentGatewayV2`) that is supposed to be the only legitimate driver of its balance. Any ETH or ERC20 balance that transiently or residually sits in the `CallDispatcher` — dust from fee-on-transfer tokens, unswept remainders, funds sent directly to its `receive()`, or tokens mid-flight between the two `dispatch()` calls in `placeOrder`/`fillOrder`'s postdispatch path — is drainable by an arbitrary third party who simply calls `dispatch()` themselves with a `Call{to: token, data: transfer(attacker, balance)}` or `Call{to: attacker, value: balance}`.

### Impact Explanation
The `CallDispatcher` is a single, protocol-wide singleton reused across every `placeOrder` predispatch and every `fillOrder`/postdispatch execution for the entire `IntentGatewayV2` deployment. Any value it holds between the two internal `dispatch()` calls, or any dust/leftover balance from fee-on-transfer tokens or partial swaps, is unauthorized-third-party-drainable. This is concrete theft of user/escrow-adjacent funds reachable from a single unprivileged transaction — exactly the class of impact required (concrete theft of funds via an unauthenticated dispatch primitive).

### Likelihood Explanation
High. No proof, no consensus, no relayer permission is required — a plain EOA transaction calling `CallDispatcher.dispatch(...)` directly is sufficient. The only precondition is that the dispatcher hold a non-zero balance at some point outside the atomic swap-then-sweep window of a single `placeOrder`/`fillOrder` call, which is realistic given fee-on-transfer token rounding (already acknowledged and tested in the codebase, e.g. `testPlaceOrder_FeeOnTransferToken_Predispatch`), the unrestricted `receive()`, and any operational funds transfer to the dispatcher.

### Recommendation
Restrict `CallDispatcher.dispatch` to only be callable by the registered `IntentGatewayV2` (or whichever contract is configured as its owner/caller in `_params.dispatcher`), e.g. via an immutable "gateway" address set at construction and an `onlyGateway` modifier, mirroring the caller-restriction pattern already used elsewhere in the codebase (`onlyHost`, `_checkRelayer`). Alternatively, ensure the dispatcher never custodies value outside a single atomic call by sweeping to zero-balance at the end of `dispatch()` and disallowing external triggering entirely.

### Proof of Concept
1. Deploy/observe the shared `CallDispatcher` used by `IntentGatewayV2`.
2. Wait for (or induce, e.g. via a fee-on-transfer input token as already tested in `testPlaceOrder_FeeOnTransferToken_Predispatch`) a nonzero residual token or ETH balance to remain on the `CallDispatcher` after a legitimate `placeOrder`/`fillOrder` completes.
3. As an arbitrary unprivileged address, call `CallDispatcher.dispatch(abi.encode([Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, CallDispatcher_balance)})]))` directly — no `IntentGatewayV2` involvement required since `dispatch()` has no caller check.
4. The dispatcher executes the transfer as itself, sending the residual balance to the attacker. [4](#0-3)

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
