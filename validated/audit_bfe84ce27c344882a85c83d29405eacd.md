Based on my analysis, the Zest `market.clar` liquidation function replicates the same structural flaw as the Tapioca H-2 report: a liquidator-controlled repayment size (`debt-amount`) determines whether the "shrink reward for insufficient collateral" branch is triggered, rather than that check being based on the position's total exposure.

### Title
Liquidator can bypass bad-debt-proportional-shrink protection by chunking `liquidate()` calls with minimal `debt-amount`, extracting full bonus while worsening the position's true collateralization - (File: `local-testing/contracts/market/market.clar` / `mainnet/contracts/market/v0-4-market.clar`, function `liquidate`)

### Summary
The `liquidate` function computes a graduated maximum liquidatable amount (`max-debt-usd`) from the position's current LTV via `calc-liquidation-params`, but the liquidator freely chooses any smaller `debt-amount`. The "shrink reward when collateral is insufficient" logic in `calc-final-liquidation-amounts` only activates when the *requested* liquidation's expected collateral (`coll-expected`, sized to the liquidator-chosen `debt-amount`) exceeds the user's *entire* remaining collateral balance. By choosing arbitrarily small repayment chunks, a liquidator can keep `coll-expected` under `user-coll-balance` indefinitely, extracting full liquidation bonus on every call and never triggering the proportional-shrink branch that is supposed to make the liquidator absorb bad debt.

### Finding Description
In `liquidate` [1](#0-0) , the liquidator supplies `debt-amount`, which is capped only by `max-debt-usd` (the theoretical full graduated-liquidation ceiling), not floored by any minimum. `process-collateral-asset` then computes `coll-usd-expected = calc-liq-collateral-repay(debt-actual-usd, liq-penalty)` and caps it against `user-coll-balance` [2](#0-1) . The reward-shrinking mechanism in `calc-final-liquidation-amounts` only recalculates `debt-final-usd` downward when `coll-actual < coll-expected` [3](#0-2)  — i.e., only when the *chosen* small repayment's required collateral+bonus exceeds the *whole* remaining collateral balance.

For an under-collateralized position (`total-collateral-usd < total-debt-usd × (1+liq-penalty)`), each liquidation event that goes through uncapped (`coll-actual == coll-expected`) strictly worsens the position's `debt/collateral` ratio, because collateral is drained at rate `(1+penalty)` per unit of debt repaid while debt only drops by that unit. Algebraically, `LTV_after ≤ LTV_before` only if `collateral ≥ debt×(1+penalty)`; when that's false, every liquidation — however small — increases the LTV. By repeatedly calling `liquidate` with the smallest possible non-zero `debt-amount` (only guarded by `(asserts! (> debt-amount u0) ERR-AMOUNT-ZERO)` [4](#0-3) ), a liquidator keeps each call's `coll-expected` tiny enough to stay under the shrinking threshold, capturing full uncapped bonus every time while draining collateral disproportionately faster than debt reduction — worse than if the same total debt had been repaid in one properly-capped call.

The only safeguard against leftover dust is the `remaining-debt-to-repay` check [5](#0-4) , which only sweeps all remaining collateral if the leftover, valued at `liq-penalty-max`, would round down to zero repayable debt tokens — a dust-level threshold that does not prevent gradual over-extraction of collateral relative to debt across many transactions before that point is reached.

### Impact Explanation
This allows liquidators to systematically extract more collateral value in bonuses than the protocol's graduated liquidation design intends for under-collateralized positions, leaving larger unsocialized bad debt behind (protocol insolvency risk) compared to a single properly-capped liquidation of the same borrower. This matches the "protocol insolvency" impact category, since the difference is ultimately borne by depositors/LPs when bad debt is eventually socialized via `socialize-debt-asset` [6](#0-5) .

### Likelihood Explanation
Any liquidator can trigger this by simply calling `liquidate` with the minimum non-zero `debt-amount` repeatedly instead of the graduated maximum; no special privileges or races are required, only awareness of the pricing/reward mechanics, which are fully on-chain and computable.

### Recommendation
Enforce that the reward-shrink comparison and/or a minimum viable `debt-amount` reflect the position's *full* liquidatable exposure (`max-debt-usd`) rather than the liquidator's arbitrarily chosen smaller amount — e.g., require `coll-expected` to be evaluated against `max-debt-usd`'s theoretical collateral requirement (not the chosen `debt-amount`'s) when deciding whether to shrink, or enforce a minimum repay size proportional to `max-debt-usd` so a liquidator cannot indefinitely stay below the shrink threshold via chunking.

### Proof of Concept
1. Borrower position: `total-debt-usd = D`, `total-collateral-usd = C`, where `C < D × (1+liq-penalty)` (already past the point where any liquidation increases LTV) but `current-ltv` is between `ltv-liq-partial` and `ltv-liq-full` so liquidation is permitted.
2. Liquidator calls `liquidate(borrower, ..., debt-amount = 1)` repeatedly (smallest allowed unit). Each call: `debt-actual-usd` tiny → `coll-usd-expected` tiny → `coll-actual == coll-expected` (uncapped, since `user-coll-balance` still much larger than the tiny requirement) → no shrink branch triggered in `calc-final-liquidation-amounts`.
3. Each iteration seizes `coll-final-raw = debt_repaid × (1+liq-penalty)` in collateral value while only reducing debt by `debt_repaid` — worsening `D/C` each round instead of improving it, unlike what a single call liquidating up to `max-debt-usd` would enforce (which would trigger the shrink branch and cap the liquidator's reward proportionally to available collateral).
4. Repeating drains collateral toward zero while debt remains largely unrepaid, only triggering the dust-sweep/bad-debt-socialization path once collateral is effectively exhausted — after the liquidator has already extracted disproportionate bonus value across many small transactions.
