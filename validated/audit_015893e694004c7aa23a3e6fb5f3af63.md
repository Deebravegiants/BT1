## Title
Predictable, Unsigned Session Identifiers Enable Cross-Tenant Session Hijacking - (File: `lib/shopify_api/utils/session_utils.rb`)

## Summary
`ShopifyAPI::Utils::SessionUtils` derives the session identifier that non-embedded apps use to look up a merchant's stored access token directly and deterministically from the public shop domain, with no secret, random, or signed component. Because the identifier is fully computable by anyone who knows a target shop's `.myshopify.com` domain (public information), an attacker can present that identifier as their own session cookie value to make the host application load and use another tenant's stored access token — breaking the binding "shop authenticated == shop whose session is retrieved."

## Finding Description
`SessionUtils.current_session_id` is the gem's documented entry point for non-embedded apps to resolve "who is this request for" from cookies: [1](#0-0) 

For the cookie path it simply forwards the raw, unauthenticated `Cookie` header value: [2](#0-1) 

Crucially, the value that is meant to be stored in that cookie (`SessionCookie#value`) is not a random token — it is generated as a deterministic function of the shop domain: [3](#0-2) 

This is exactly the value written into the cookie after OAuth completes, per `Auth::Oauth.validate_auth_callback`: [4](#0-3) 

So the "session id" that host applications are told to use as the lookup key into their session store (`MyApp::SessionRepository.store_session(auth_result[:session])`, keyed by `session.id`) is nothing more than the literal string `offline_#{shop}` or `#{shop}_#{user_id}`. Neither string contains any secret, nonce, or HMAC — it is entirely reconstructible by anyone who knows (or guesses) the shop's domain.

This breaks the identity binding the rules describe as "a session id derived from unauthenticated bytes": the true authentication event is the OAuth code exchange that produced a real access token for shop A, but the key under which that token is later retrievable is a plain, guessable string with no cryptographic tie back to an authenticated browser session. Any raw HTTP client (not a browser, so same-origin/HttpOnly restrictions on `document.cookie` are irrelevant — a `Cookie:` header can be set on any direct HTTP request) can send `Cookie: shopify_app_session=offline_shop-a.myshopify.com` to the app and have `current_session_id` faithfully return that identifier, which the host app then uses to load shop A's real, previously-issued access token from its session store.

## Impact Explanation
This is a cross-tenant access vector: an unprivileged internet user who knows or enumerates a victim shop's public `.myshopify.com` domain can construct the exact non-secret session identifier for that shop's stored offline (or online, if the numeric Shopify user id is known/guessable) session, and use it to retrieve and act with that shop's persisted Shopify access token via the app built on this gem's documented session-lookup contract.

## Likelihood Explanation
Likelihood is high for offline sessions: shop domains are routinely public (storefront URLs, app listings, partner directories), and the offline session id has no other component besides `"offline_" + shop`. An attacker only needs network access to the target app's endpoints and knowledge of the shop domain — no credentials, tokens, or social engineering required.

## Recommendation
Do not use a deterministic, publicly-derivable string as the bearer session identifier. Generate cryptographically random session ids (or sign/HMAC the shop+user identity with the app's secret) so that the session cookie value cannot be reconstructed from public information alone, and validate that the id presented actually originated from this app's own issuance before using it to look up a session/access token.

## Proof of Concept
1. App A installs the merchant app for `victim-shop.myshopify.com` via the offline authorization-code grant; `Auth::Oauth.validate_auth_callback` returns a session with `id == "offline_victim-shop.myshopify.com"` and sets that value as the `shopify_app_session` cookie (see `lib/shopify_api/auth/oauth.rb` lines 100-110). The host app persists the real access token keyed by this id.
2. Attacker, knowing only the public domain `victim-shop.myshopify.com`, computes the identical string `offline_victim-shop.myshopify.com` (per `SessionUtils.offline_session_id`, `lib/shopify_api/utils/session_utils.rb` lines 63-66).
3. Attacker sends a direct HTTP request to the app's server-rendered (non-embedded) endpoint with header `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`.
4. The app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` unchecked (`lib/shopify_api/utils/session_utils.rb` lines 19-37, 68-71).
5. The host app loads the session/access token for that id from its store and uses it to make authenticated Shopify API calls — the attacker now operates with `victim-shop`'s real access token, without ever completing OAuth for that shop.
