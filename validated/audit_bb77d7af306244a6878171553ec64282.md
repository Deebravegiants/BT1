### Title
`CallDispatcher.dispatch()` has no caller restriction, letting any unprivileged address drain native/ERC20 balances held by the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a canonical, shared utility contract referenced by `HyperFungibleToken`, `WrappedHyperFungibleToken`, `HyperFungibleTokenUpgradeable`, `WrappedHyperFungibleTokenUpgradeable` and `IntentGatewayV2` to execute attacker/solver/order-supplied `Call[]` batches on top of tokens or native value it is holding for the duration of a bridge delivery or order fill/placement. [1](#0-0)  Unlike every other cross-chain entrypoint in the same codebase (`onAccept`, `onPostRequestTimeout`, `dispatch(DispatchPost)`, etc.), which are gated by `onlyHost`/`restrict` modifiers, `CallDispatcher.dispatch(bytes memory encoded)` is a completely unauthenticated `external` function: any address can call it directly, at any time, and instruct it to forward `call.value` of its own native balance (and its own token approvals it may hold) to any address it specifies. [2](#0-1)  This mirrors the reported TOFT bug's root cause: a shared contract forwards its own held native balance based on caller-supplied `(to, value)` parameters, with no check that the caller is the legitimate orchestrating contract or that the value being forwarded is scoped to the caller's own deposit.

### Finding Description
`CallDispatcher` accepts arbitrary ETH via `receive() external payable {}` and is used as a transient custody point by multiple apps: 
- `HyperFungibleToken.onAccept`/`WrappedHyperFungibleToken.onAccept` mint/unlock tokens (or unwrap WETH to native ETH) to a recipient that can be set to the `CallDispatcher` address, then immediately call `ICallDispatcher(_dispatcher).dispatch(message.data)` using attacker-controlled `data` (the sender of a bridge `send()` fully controls the `Call[]` payload). [3](#0-2) 
- `IntentGatewayV2`/`IntentsBase._execute` push predispatch/postdispatch assets to the same dispatcher, call `dispatch()` with order-supplied calls, then issue a follow-up `dispatch()` call to sweep back whatever balance remains. [4](#0-3) [5](#0-4) 

The `dispatch()` function itself performs no `msg.sender` check whatsoever:
```solidity
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    if (!success) revert CallFailed(to, result);
}
``` [6](#0-5) 

Because the contract is a single shared deployment (the docs explicitly point to canonical, reused `CallDispatcher` addresses across apps) [7](#0-6) , any native ETH or ERC20 balance that ends up sitting on the dispatcher — whether from direct `receive()` deposits, rounding/dust left over after an incomplete sweep, or any transient balance parked there between the "push funds" and "sweep funds" `dispatch()` calls within a single transaction that an attacker can reenter into via a malicious `Call.to` target — can be swept out to an attacker-chosen address by anyone, at any time, simply by calling `dispatch()` directly with `Call({to: attackerContract, value: currentBalance, data: ""})`. This is exactly the analog of the original bug class: an unprivileged caller forwards the contract's own balance to a caller-controlled destination because the intermediate "trusted" hop performs no authorization or amount-scoping check.

### Impact Explanation
Any native token or ERC20 balance accumulated on the shared `CallDispatcher` — from any of the HFT, WrappedHFT, or IntentGatewayV2 flows across all chains reusing that deployment — is not protected by any access control and can be stolen outright by a single unprivileged transaction. This is a direct theft-of-funds vector against a shared, protocol-critical utility contract.

### Likelihood Explanation
`dispatch()` is `external` with no modifier, callable by anyone with a plain transaction; exploitation requires no privileged role, no governance, no relayer collusion, and no cross-chain proof — only that the dispatcher is holding a non-zero balance at the moment of the call (e.g., because a previous call's sweep didn't fully zero it out, direct ETH transfer via `receive()`, or reentrancy through an attacker-controlled `Call.to` target invoked from within the same dispatcher). Given the dispatcher is a long-lived, address-pinned singleton reused by many independent bridge/order flows, the window and probability of it holding a nonzero balance at some point is realistic and reachable from a single unprivileged transaction.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the set of authorized app contracts that are meant to use it (e.g., an `onlyAuthorizedCaller` modifier populated by the apps' owners, or make each app deploy/own its own `CallDispatcher` instance instead of sharing one canonical address). Additionally, ensure that any custody window on the dispatcher zeroes out atomically at the end of each app-level operation (no dust left in storage/balance between the push and sweep `dispatch()` calls), and consider having `dispatch()` require that the caller be the specific app contract that funded the transient balance, not an arbitrary address.

### Proof of Concept
1. Wait for (or induce, e.g. via a malicious `Call.to` target that reenters, or via direct `receive()` deposit) a nonzero native ETH balance to accumulate on the canonical `CallDispatcher` address used by `HyperFungibleToken`/`WrappedHyperFungibleToken`/`IntentGatewayV2`.
2. As any unprivileged address, call:
```solidity
Call[] memory calls = new Call[](1);
calls[0] = Call({ to: attackerContract, value: address(callDispatcher).balance, data: "" });
callDispatcher.dispatch(abi.encode(calls));
```
3. `CallDispatcher.dispatch()` performs no caller check and forwards the entire current balance to `attackerContract` via `to.call{value: call.value}(call.data)`, completing the theft. [6](#0-5)

import {ICallDispatcher, Call} from "@hyperbridge/core/interfaces/ICallDispatcher.sol";

/**
 * @title The CallDispatcher
 * @author Polytope Labs (hello@polytope.technology)
 *
 * @notice This contract is used to dispatch calls to other contracts.
 */
contract CallDispatcher is ICallDispatcher {
    /**
     * @dev error thrown when the target is not a contract.
     */
    error NotContract(address target);

    /**
     * @dev error thrown when a call fails.
     */
    error CallFailed(address target, bytes result);

    /**
     * @dev Receive function to accept ETH transfers
     */
    receive() external payable {}

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
}

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
