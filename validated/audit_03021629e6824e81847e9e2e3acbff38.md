### Title

Permanent interest-accrual overflow can freeze a whale-sized lending market - (File: common/src/rates/index.rs)

### Summary

An attacker can place an extreme amount of supply and debt in a high-interest market and let interest accrue until fixed-point market-value multiplication overflows. Afterward, every pool mutation for that market first executes `interest::global_sync`, so repayments, withdrawals, liquidations, bad-debt cleanup, recapitalization, and explicit index updates revert with `MathOverflow`. This leaves market funds permanently frozen and debt permanently collectible only in storage, not economically recoverable through the contract. The borrow-index ceiling does not prevent the fault because debt-value multiplication can overflow before the configured index bound is reached. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description

Every mutation leg loads a `Cache` and calls `interest::global_sync`; `load_leg` is shared by repayment, withdrawal, and net-settlement flows, while `update_indexes` calls the same accrual routine for each selected market. [4](#0-3) [5](#0-4) 

`global_sync` repeatedly evaluates `accrue_step` for the elapsed interval and then writes the new indexes and revenue shares. [6](#0-5) [7](#0-6) 

During accrual, `calculate_supplier_rewards` computes `borrowed * old_borrow_index` and `borrowed * new_borrow_index` as `Ray` values. These products are `i128`-bounded fixed-point operations and can overflow when a market contains very large scaled debt and the index has grown substantially. [2](#0-1) 

The borrow index is capped only after `old_index.mul(interest_factor)` produces a new index; therefore the index ceiling bounds the multiplier but does not bound `borrowed * index`. [8](#0-7) [3](#0-2) 

Once `borrowed * borrow_index` exceeds the `i128` fixed-point domain, all subsequent sync attempts fail before any operation-specific escape logic runs. `repay` invokes `ops::load_leg`, which accrues before resolving and burning debt. [9](#0-8)  Withdrawal likewise invokes `ops::load_leg` before burning supply or debiting cash. [10](#0-9) 

Because all state in the failed transaction rolls back, `last_timestamp` and the indexes remain at their last successful values; each later call repeats the same overflowing accrual rather than advancing past it. [6](#0-5) [11](#0-10) 

### Impact Explanation

This is permanent freezing of market funds and an effectively inoperable market. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate positions tied to the market, and governance-triggered index updates cannot recover it because each path syncs the same market first. [9](#0-8) [10](#0-9) [5](#0-4) 

The failure is worse than a temporary revert: the overflowing quantity derives from stored `borrowed` and the monotonically increasing `borrow_index`, neither of which can be corrected after accrual itself becomes the first executed operation. [8](#0-7) [1](#0-0) 

Severity is Medium: the impact is severe for the affected market, but the attack requires exceptional principal, an admitted market whose caps and rate parameters permit sufficient debt, and enough accrual for the index to reach the unsafe product range. [12](#0-11) [2](#0-1) 

### Likelihood Explanation

An unprivileged borrower can create the dangerous state through ordinary controller `supply` and `borrow` calls: supply collateral in one market, borrow an extremely large position in the vulnerable market, and leave it outstanding. The attacker does not need a privileged role, leaked key, malformed token, external service failure, or contract upgrade. [13](#0-12) [4](#0-3) 

The practical constraints are capital intensity and configuration. The market must allow enough supply and borrow capacity, the borrower must provide sufficient collateral, and the configured curve must grow the index enough that the stored scaled-debt product approaches the `i128` bound. The explicit index ceiling is `10^36` raw units, far above an index at which a sufficiently large scaled debt can overflow. [3](#0-2) 

The repository’s own long-horizon harness demonstrates this exact state transition: a billion-token, 18-decimal market under a steep rate curve fails `update_indexes`, followed by failed withdrawal and repayment, while the borrow index remains below `MAX_BORROW_INDEX_RAY`. [14](#0-13) 

### Recommendation

Bound the product, not merely the index. During accrual:

1. Detect `borrowed * new_borrow_index` and `supplied * supply_index` overflow before performing `Ray::mul`.
2. Prefer saturating the affected market index and clamping derived revenue rather than reverting.
3. If economic correctness requires a revert, add a governance-recoverable path that caps accrued indexes and explicitly writes off unrealizable interest without first recomputing the overflowing product.
4. Enforce a deployment-level invariant such as `max_scaled_debt * MAX_BORROW_INDEX_RAY <= i128::MAX`, using supply/borrow caps and token decimals to prevent the unsafe domain from being reached.
5. Add regression coverage proving that repayment, withdrawal, liquidation, and `update_indexes` remain callable at the maximum admitted debt/index boundary. [8](#0-7) [2](#0-1) [4](#0-3) 

### Proof of Concept

1. Governance has admitted two markets:
   - `COL`: ordinary collateral.
   - `BIG18`: an 18-decimal asset with a steep admitted rate curve, large supply/borrow caps, and a permissive utilization limit.
2. An attacker supplies a very large `BIG18` balance so the market has borrowable liquidity.
3. Using a sufficiently collateralized account, the attacker calls controller `borrow` for most of that `BIG18` liquidity. This creates large stored scaled debt through the pool’s owner-gated `borrow` path. [15](#0-14) 
4. The attacker does not repay. Interest accrual repeatedly raises `borrow_index` through `global_sync`/`accrue_step`. [16](#0-15) 
5. Once `borrowed * borrow_index` exceeds the `i128` fixed-point domain, `calculate_supplier_rewards` reverts inside accrual. [2](#0-1) 
6. Calls to controller `update_indexes`, `repay`, `withdraw`, `liquidate`, or `clean_bad_debt` for that market fail before their operation-specific logic because every market mutation syncs interest first. [4](#0-3) [5](#0-4) 
7. The checked state remains below `MAX_BORROW_INDEX_RAY`, confirming that the index ceiling did not prevent the value-product overflow. [3](#0-2) [17](#0-16)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);
}

pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {
    let (mut cache, position) = ops::load_leg(env, action);
    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);
    let net_repay = amount
        .checked_sub(overpayment)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));
    assert_with_error!(
        env,
        net_repay == 0 || burned.raw() > 0,
        GenericError::RepayRoundsToZeroShares
    );

    let position = position.checked_sub(env, burned);
    cache.burn_debt(burned);

    cache.credit_cash(net_repay);

    let snapshot = cache.commit();

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
