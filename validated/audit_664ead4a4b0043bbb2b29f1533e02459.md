Found the analog. It's confirmed by `ShopValidator` being applied in `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`, but **not** in `lib/shopify_api/auth/oauth.rb`'s authorization-code-grant flow — the exact place where `client_secret` is transmitted.

### Title
OAuth authorization-code callback sends `client_secret` to an unsanitized `shop` host taken from the HMAC-verified query, bypassing `ShopValidator` trusted-domain checks - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the access-token request using `auth_query.shop` directly as the destination host for a POST that carries the app's `client_secret`, without ever routing it through `ShopifyAPI::Utils::ShopValidator.sanitize!`. Every other privileged-credential flow in the gem (`token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`) explicitly validates/sanitizes the shop domain before using it to build the request host, but the classic Authorization Code Grant path does not.

### Finding Description
`validate_auth_callback` verifies the HMAC over `code`, `host`, `shop`, `state`, `timestamp` via `Utils::HmacValidator.validate(auth_query)` [1](#0-0) . This proves the *bytes* of `auth_query.shop` are unmodified and legitimately signed by Shopify with the app's `api_secret_key`, but it says nothing about whether `shop` is actually a `myshopify.com`/trusted domain — HMAC validity and host trust are two different bindings, and the code conflates them.

That unsanitized `shop` value is then used to build a `null_session` and issue an HTTP POST containing `client_secret` in the body: [2](#0-1) 

Inside `Clients::HttpClient#initialize`, the destination host is built directly from `session.shop` with no domain validation: [3](#0-2) 

Compare this to the other OAuth-adjacent flows, which all call `ShopValidator.sanitize!`/`sanitize_shop_domain` before constructing a session/host from a caller-supplied or claim-derived `shop` value: [4](#0-3) [5](#0-4) 

The binding that is broken is:
`host authenticated by HMAC(shop) == host that receives client_secret`

should imply `host ∈ TRUSTED_SHOPIFY_DOMAINS`, but the code only checks the former, not the latter. `begin_auth` also passes the raw, un-sanitized `shop` parameter straight into `auth_base_uri(shop)` to build the redirect URL [6](#0-5) , so if the host application forwards a query-string `shop` value unchanged into `begin_auth` (a very common integration pattern, since the gem's own docs show `shop` coming from a request parameter), an attacker who controls that `shop` value controls where the eventual callback's `client_secret`-bearing POST is sent.

### Impact Explanation
If a merchant (or attacker acting as one) is able to influence the `shop` value used to initiate OAuth (e.g., via a `shop=` query parameter that the host app passes to `begin_auth` without pre-validating against `ShopValidator`), the resulting `/oauth/authorize` redirect and, more critically, the subsequent `access_token` POST containing the app's `client_id`/`client_secret` will be sent to an attacker-controlled host instead of `*.myshopify.com`. This is a direct SSRF-with-credentials / `client_secret` exfiltration path, matching the "High" impact category (credential leakage / SSRF carrying the app's credentials).

### Likelihood Explanation
Exploitability depends on the host application passing an unsanitized `shop` value through to `begin_auth`/`validate_auth_callback`, which the gem's own oauth.rb design does not itself prevent or warn against, unlike the newer `token_exchange`/`client_credentials`/`refresh_token` paths that defensively sanitize. Given this is the classic, still-documented Authorization Code Grant flow, and the gem provides no internal guard, likelihood is Medium: it requires the integrating app to omit shop validation, but the gem gives no structural protection where its sibling flows do.

### Recommendation
Call `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) inside `Oauth.begin_auth` and `Oauth.validate_auth_callback` before using `shop`/`auth_query.shop` to construct `auth_base_uri` or the `Auth::Session` passed to `HttpClient`, mirroring the validation already present in `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`.

### Proof of Concept
1. Host application exposes `GET /login?shop=<value>` and calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/callback")` without sanitizing `shop`.
2. Attacker sends a victim merchant to `/login?shop=evil.example.com`.
3. `auth_base_uri("evil.example.com")` produces `https://evil.example.com/admin/oauth/authorize?...&client_id=...` [7](#0-6) , leaking `client_id` and redirecting the merchant's browser to the attacker's server.
4. If the attacker's server further completes a crafted callback whose `shop` parameter matches (and, in setups where the app doesn't strictly bind `shop` to the initiating request), `validate_auth_callback` will build `null_session` for that `shop` and POST `client_secret` to it via `Clients::HttpClient` [2](#0-1) [3](#0-2) , exfiltrating the app's `client_secret` to the attacker-controlled host.
