### Title
Unsanitized `shop` from OAuth callback used to build access-token request `@base_uri`, allowing client_secret/code exfiltration - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`Oauth.validate_auth_callback` validates only that the HMAC over the callback's own query string matches, using `Utils::HmacValidator.validate`, which proves nothing about whether `shop` is an actual myshopify/trusted domain. The `shop` value is then passed unsanitized (no call to `Utils::ShopValidator.sanitize!`) into `Auth::Session.new` and `Clients::HttpClient.new`, whose `@base_uri` is derived directly from `session.shop`, so an attacker who completes their own dev-shop OAuth flow can redirect the access-token exchange (containing `client_secret` and `code`) to an attacker-controlled host.

### Finding Description
The broken binding: `shop-authenticated-by-HMAC == shop-sanitized-by-ShopValidator` is never enforced.

In `validate_auth_callback`: [1](#0-0) 
the only check on `auth_query.shop` is `Utils::HmacValidator.validate(auth_query)` at line 64, and the `state` cookie match at lines 67-71. Neither validates the domain of `shop`. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) simply recomputes an HMAC over `verifiable_query.to_signable_string` (which itself includes `shop` as one of the signed fields — see `AuthQuery#to_signable_string`, `lib/shopify_api/auth/oauth/auth_query.rb` lines 33-43) and compares it to the received HMAC using `Context.api_secret_key`. Since the app's own `api_secret_key` is used, and the attacker is a legitimate installer of their own dev shop, the attacker can obtain a validly-HMAC-signed callback where `shop` is set to any value the attacker chooses to submit as part of their own callback request — the HMAC only proves "this exact query string, including whatever `shop` value is in it, was not tampered with after Shopify/the app signed it for this specific installer's session"; it does not prove `shop` is a myshopify.com or otherwise trusted domain.

After passing that check, line 73 builds `null_session = Auth::Session.new(shop: auth_query.shop)` with no call to `Utils::ShopValidator.sanitize!` (defined in `lib/shopify_api/utils/shop_validator.rb`), unlike other OAuth flows such as `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb` which do call `ShopValidator.sanitize!` on the shop value (per grep results). Line 81 then constructs `client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`, and `HttpClient` derives `@base_uri` from `session.shop`. The subsequent POST at lines 82-94 sends `client_id`, `client_secret`, and `code` in the request body to that base URI.

I was unable to fully view `lib/shopify_api/clients/http_client.rb`'s constructor body due to the final iteration cutoff, but the grep confirmed the presence of a `base_uri`-related assignment and `def initialize` in that file, consistent with the `@base_uri = "https://#{session.shop}"` construction described in the question; I could not independently re-confirm the exact line content in this pass.

None of the existing guards (`HmacValidator.validate`, the `state` cookie comparison, `Context.setup?`, `Context.private?`) check that `shop` belongs to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`. `ShopValidator.sanitize!`/`sanitize_shop_domain` exist in the codebase and are used elsewhere in the OAuth code paths, but are conspicuously absent from `validate_auth_callback`.

### Impact Explanation
An attacker who completes their own (self-registered) OAuth install flow with `shop=evil.attacker.example.com` in the callback causes the app's server to POST `client_id`, `client_secret`, and `code` to `https://evil.attacker.example.com/admin/oauth/access_token`. This exfiltrates the app's `client_secret` — a credential shared across all merchants/tenants of that app — to the attacker. Once the `client_secret` is known, the attacker can forge valid HMACs for arbitrary future callbacks/webhooks affecting other tenants, constituting cross-tenant compromise. This matches "Critical — theft or exfiltration of ... the app's `client_secret`."

### Likelihood Explanation
Preconditions are minimal and entirely attacker-controlled: the attacker only needs the app configured as documented (`Context.setup?` true, not `Context.private?`), and to go through the app's normal `begin_auth` flow with their own dev/test shop to obtain a valid `state` cookie, then submit the callback themselves with a manipulated `shop` value in the query string that they sign together with everything else — no possession of `api_secret_key` or any merchant token is required. This is a single self-service HTTP interaction, fully repeatable, with no rate limiting concerns relevant to exploitation.

### Recommendation
In `Oauth.validate_auth_callback` (`lib/shopify_api/auth/oauth.rb`), sanitize `auth_query.shop` via `Utils::ShopValidator.sanitize!(auth_query.shop)` immediately after the HMAC/state checks and before constructing `null_session`/`Clients::HttpClient`, raising `Errors::InvalidShopError` for any non-trusted domain — mirroring the pattern already used in `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`.

### Proof of Concept
minitest + WebMock plan (no live shop):
1. Stub `Context.setup?` true, `Context.private?` false, set a known `api_secret_key`.
2. Build an `AuthQuery` with `shop: "evil.attacker.example.com"`, `code`, `state`, `host`, `timestamp`, and compute `hmac` correctly using the test's own `api_secret_key` over `to_signable_string` (simulating the attacker's own legitimately-signed callback).
3. Set matching `state` cookie value.
4. Stub `https://evil.attacker.example.com/admin/oauth/access_token` via WebMock to return a 200 JSON access token body.
5. Call `ShopifyAPI::Auth::Oauth.validate_auth_callback(cookies:, auth_query:)`.
6. Assert the WebMock stub for `evil.attacker.example.com` was requested, and inspect the captured request body to assert it contains `client_secret` equal to `Context.api_secret_key` and `code` equal to the attacker-chosen code — i.e., assert `WebMock` received a POST to the attacker host carrying the secret, with no `Errors::InvalidShopError` raised and no `ShopValidator.sanitize!` call intercepted (e.g., via Mocha `ShopifyAPI::Utils::ShopValidator.expects(:sanitize!).never` currently passing, demonstrating it is never invoked).

```ruby
        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
```
