### Title
Division-by-zero panic in `calc_take_pnl` due to decimal-normalization truncation freezes Deposit/Withdraw/WithdrawPnl - ([File: program/src/processor.rs])

### Summary
`Processor::calc_take_pnl` performs an unguarded `checked_div(x1).unwrap()` where `x1` is the sys-decimal-normalized pool "pc" reserve. Because `Calculator::normalize_decimal_v2` truncates (integer division) when rescaling from native token decimals to the internal `sys_decimal_value` precision, a non-zero but very small native pc reserve can normalize to exactly `0`. Any subsequent call into `calc_take_pnl` (invoked from `process_deposit`, `process_withdraw`, and `process_withdrawpnl`) then divides by that zero value and panics, aborting the transaction. This mirrors the FAAD2 CVE pattern: a specific, reachable numeric edge case (here, `x1 == 0` after truncation) is not defensively handled the way sibling operations are (compare with `calc_total_without_take_pnl_no_orderbook`, which uses `checked_sub(...).ok_or(...)`  instead of `.unwrap()`).

### Finding Description
`Calculator::normalize_decimal_v2` rescales a native u64 amount into the AMM's internal `sys_decimal_value` precision using floor division: [1](#0-0) 

`process_swap_base_in`/`process_swap_base_in_v2` (Coin2PC direction) only forbid `swap_amount_out >= total_pc_without_take_pnl`, i.e. they allow the native pc reserve to be driven down to a very small positive residual (as low as `1`) through repeated attacker-issued swaps: [2](#0-1) 

When `pc_decimals > 0` and `sys_decimal_value` is small relative to `10^pc_decimals` (e.g. `pc_decimals = 9`, `sys_decimal_value = 10^6`, as used throughout the initialization/test code), a native residual of `1` normalizes to `0`:
```
normalize_decimal_v2(1, 9, 1_000_000) = (1 * 1_000_000) / 10^9 = 0
```
This zero value (`x1`) is then fed into `calc_take_pnl`, which unconditionally divides by it without a zero-check: [3](#0-2) 

`calc_take_pnl` is reached from every unprivileged LP entrypoint that mutates pool accounting: Deposit, Withdraw (unless status is `WithdrawOnly`), and WithdrawPnl: [4](#0-3) [5](#0-4) [6](#0-5) 

Once `x1` normalizes to `0` and the branch guard `pool_pc_amount * pool_coin_amount >= calc_pc_amount * calc_coin_amount` is satisfied (trivially true once `x1=0` collapses the left side toward 0 alongside a correspondingly small `calc_pnl_x`), `calc_x_power` computes `x2_power = 0`, so `x2 = 0`, and then:
```
let y2 = x2.checked_mul(y1).unwrap().checked_div(x1).unwrap();
```
divides `0 / 0`, which returns `None` from `checked_div`, and `.unwrap()` panics, aborting the instruction. This is analogous to the referenced CVE class: a mathematically "trivial" edge case (0/0, or the LONG_START_SEQUENCE branch in FAAD2) is not special-cased even though the general-purpose arithmetic silently mishandles it.

### Impact Explanation
Once the pool is driven into this state, every future Deposit, Withdraw, or WithdrawPnl transaction that reaches `calc_take_pnl` will panic and revert, since the underlying vault balance ratio persists until liquidity/reserves are rebalanced by an external, uncontrolled event (further swaps, or an admin/owner action changing AMM status to `WithdrawOnly` to bypass the `calc_take_pnl` call in `process_withdraw`). Until such intervention, LPs cannot withdraw liquidity via the normal SwapOnly/OpenBook status, and the pnl owner cannot claim accrued pnl — a denial-of-service that effectively freezes LP and pnl funds in the pool. This is reachable purely by an unprivileged swapper issuing successive `SwapBaseIn`/`SwapBaseIn_V2` transactions against a pool with unfavorable `pc_decimals`/`sys_decimal_value` ratios, requiring no special privileges, leaked keys, or off-chain component compromise.

### Likelihood Explanation
Triggering requires: (1) a pool where `pc_decimals` is large enough relative to `sys_decimal_value` that a small native residual normalizes to `0` (very common: `sys_decimal_value` is fixed at `10^6` in the standard initializer while `pc_decimals` for common SPL tokens is `6`–`9`), and (2) an attacker able to repeatedly swap Coin2PC to drain the pc side down near its floor, bounded only by the strict `>=` check on `swap_amount_out`. Both conditions are attacker-controllable within a single or a short sequence of standard swap transactions using attacker-chosen `amount_in`, making this practically reachable without any special permissions.

### Recommendation
- In `Calculator::calc_take_pnl` (and any other spot performing `checked_div` on decimal-normalized reserves), explicitly guard against `x1 == 0` (and `y1 == 0`) before dividing, returning a controlled `AmmError` (as already done in `calc_total_without_take_pnl_no_orderbook`) instead of relying on `.unwrap()`.
- Replace the remaining raw `.unwrap()` calls inside `calc_take_pnl` (e.g. the `checked_sub` calls at math.rs) with `.ok_or(AmmError::...)?` so all pnl-path errors return recoverable `ProgramError`s rather than panicking and reverting unpredictably.
- Consider enforcing a minimum-reserve floor (beyond `swap_amount_out < total_pc_without_take_pnl`) high enough that normalized (`sys_decimal_value`-scaled) reserves cannot truncate to zero.

### Proof of Concept
1. Initialize an AMM pool where `pc_decimals` (e.g. 9) is large relative to `amm.sys_decimal_value` (fixed at `10^6` by `Processor::process_initialize2` / `AmmInfo::initialize`), such that `normalize_decimal_v2(residual_pc, pc_decimals, sys_decimal_value)` truncates to `0` when `residual_pc` is small (e.g. `residual_pc = 1`).
2. As an unprivileged swapper, repeatedly call `SwapBaseIn`/`SwapBaseInV2` with `swap_direction = Coin2PC`, choosing `amount_in` on each call so that `swap_amount_out` approaches `total_pc_without_take_pnl - 1` (allowed since only `swap_amount_out >= total_pc_without_take_pnl` is rejected — see `program/src/processor.rs:2000-2004`). Iterate until the on-chain `amm_pc_vault.amount - amm.state_data.need_take_pnl_pc` (native units) is `1`.
3. Call `Deposit`, `Withdraw` (status not `WithdrawOnly`), or `WithdrawPnl`. Inside, `Calculator::normalize_decimal_v2(1, pc_decimals, sys_decimal_value)` yields `x1 = 0` (`program/src/math.rs:106-116`), which is passed into `calc_take_pnl` (`program/src/processor.rs:1145-1173`), triggering `x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()` (`program/src/processor.rs:208`) to divide by zero and panic, reverting the transaction.
4. All subsequent Deposit/Withdraw/WithdrawPnl transactions against this pool similarly panic while the reserve ratio persists, freezing LP withdrawals and pnl claims until an administrative status change (e.g., to `WithdrawOnly`) circumvents the affected code path.
