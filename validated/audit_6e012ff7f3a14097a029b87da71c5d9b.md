### Title
Webhook `shop` field is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value purely from the unauthenticated `x-shopify-shop-domain` HTTP header, while the HMAC signature that `Registry.process` validates covers only the raw request body. Because the app's `api_secret_key` is a single, shared secret across every shop that installs the app, any shop that has installed the app can obtain a genuinely valid `(body, hmac)` pair and then replay it against the app's webhook endpoint with the `shop-domain` header rewritten to a different, victim shop. The HMAC check passes because it never touches the header, so the handler is invoked believing the data originated from the victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes and compares an HMAC over `verifiable_query.to_signable_string` [4](#0-3) . For webhook requests, `to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all pulled straight from HTTP headers that are never mixed into the signed string [5](#0-4) .

`Registry.process` relies exclusively on this HMAC check before dispatching to the registered handler, and it passes `request.shop` (the unauthenticated header value) straight through as the tenant identity in `WebhookMetadata`:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

The binding that is supposed to hold is: `hmac_signed_bytes == bytes_that_determine_tenant`. In this implementation that equality is broken — `hmac_signed_bytes = raw_body` but `bytes_that_determine_tenant = shop-domain header`, two disjoint inputs. Because Shopify apps use one `api_secret_key` for all installs, an attacker who has legitimately installed the app on their own shop can:
1. Register a webhook subscription (or use a mandatory webhook such as `app/uninstalled`) pointed at infrastructure they control, capturing a real `(raw_body, x-shopify-hmac-sha256)` pair signed with the shared `api_secret_key`.
2. Replay that exact body and HMAC to the app's real webhook endpoint, substituting the `x-shopify-shop-domain` header with a victim shop's domain (and any other header, like `topic`, since those are unauthenticated too).
3. `HmacValidator.validate` still succeeds because the body is unmodified, and `Registry.process` invokes the handler believing the event is `topic`/`shop` = victim, with attacker-controlled `body`.

### Impact Explanation
This breaks the tenant isolation the HMAC check is meant to guarantee, enabling cross-tenant access/action: an app built on this gem cannot distinguish "this genuinely came from shop X" from "this came from any installer of the app, relabeled as shop X." Depending on how the host app's `WebhookHandler` uses `data.shop` (e.g., looking up per-shop session/state or acting on `data.body` keyed by the asserted shop), this can be used to inject forged data, trigger mandatory GDPR webhook handling (`customers/redact`, `shop/redact`) for a shop the attacker doesn't control, or otherwise pollute/act on another tenant's records — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Any user who can install the app on their own shop (a normal, unprivileged flow for public apps) can obtain valid `(body, hmac)` pairs, since the same `api_secret_key` signs webhooks for every shop. No possession of the victim's credentials, the app's `client_secret`/access tokens, or any elevated privilege is required — only network access to POST to the app's public webhook endpoint with modified headers.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is actually verified, e.g., include the `x-shopify-shop-domain` header (and topic) in `to_signable_string`, or independently verify that the asserted shop is one for which the app holds an active session/installation before trusting `WebhookMetadata#shop`. At minimum, document and enforce that host applications must not treat the header-derived `shop` as authenticated unless it is cross-checked against a known/authorized shop list.

### Proof of Concept
```ruby
require "openssl"
require "base64"

secret = ShopifyAPI::Context.api_secret_key # shared across ALL shops that installed this app

# Step 1: attacker installs the app on their own shop "attacker-shop.myshopify.com"
# and captures a genuine webhook delivery, e.g. for topic "customers/data_request"
raw_body = '{"customer":{"id":1},"orders_requested":[299938]}'
hmac_digest = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, raw_body)
valid_hmac_b64 = Base64.encode64(hmac_digest)

# Step 2: attacker replays the SAME body+hmac but swaps the shop-domain header
# to a victim shop that also installed the app
forged_headers = {
  "x-shopify-topic" => "customers/data_request",
  "x-shopify-hmac-sha256" => valid_hmac_b64,   # still valid: body untouched
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unauthenticated
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Step 3: passes HMAC validation because the check never covers `shop`
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle is invoked with data.shop == "victim-shop.myshopify.com"
#    even though the request never originated from Shopify on behalf of that shop.
```
