## Analysis Summary

I reduced the SukukFi bug to this custody invariant: **a value/security-state should be evaluated at the time the protective condition is triggered, not pinned to a stale reference captured before the protection existed** (in SukukFi, PPS locked at fulfillment ignores subsequent state; the "protection" for late acters becomes wrong once the underlying environment changes).

I searched Aptos-native multisig, delegation-pool, vesting, and object-ownership flows for an analogous stale-reference custody break. The delegation pool and vesting modules use continuous, per-operation synchronization (`calculate_stake_pool_drift`) and don't exhibit this pattern — pending withdrawals are correctly re-priced against synchronized totals at execution. `object.move`'s `LinearTransferRef`/ownership transfer correctly re-validates `object.owner == self.owner` at transfer time.

The strongest candidate is in `aptos-move/framework/aptos-framework/sources/multisig_account.move`, which (in this repo) has a `MultisigAccountTimeLock` feature added on top of the standard multisig flow. The timelock's elapsed-time gate is computed as: [1](#0-0) 

```
inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
    if (exists<MultisigAccountTimeLock>(multisig_account)) {
        ...
        let pending_transaction = get_transaction(multisig_account, sequence_number);
        let elapsed = now_seconds() - pending_transaction.creation_time_secs;
        (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
    } else {
        true
    }
}
```

`elapsed` is computed from `pending_transaction.creation_time_secs`, a field fixed at `create_transaction`/`create_transaction_with_hash` time — before any `MultisigAccountTimeLock` resource exists on that account. This is invoked from `validate_multisig_transaction` (the VM prologue check gating execution): [2](#0-1) 

I was not able to fully inspect the `upsert_timelock` implementation in the time available (it appears further in the file but I could not retrieve it before running out of tool calls), so I cannot 100% confirm whether it resets `creation_time_secs` for already-pending transactions when a timelock is newly configured. Given the field is a per-transaction, creation-time snapshot, and the visible logic only branches on `exists<MultisigAccountTimeLock>`, the code as shown does not re-baseline existing pending transactions.

### Title
Multisig timelock uses stale `creation_time_secs`, letting pre-existing pending transactions bypass a newly-imposed delay - (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

### Summary
`can_execute_with_timelock` gates execution using `elapsed = now_seconds() - pending_transaction.creation_time_secs`, where `creation_time_secs` is captured once, at transaction creation. If a `MultisigAccountTimeLock` is added or tightened *after* a transaction was created (e.g., owners add a timelock in response to a suspected compromised key or as a security hardening step), the elapsed time computed against the transaction's original (pre-timelock) creation timestamp can already exceed the newly required `timelock_period`. The transaction becomes immediately executable the moment quorum is met, with zero actual delay — defeating the entire purpose of the timelock, which is to give the remaining owners a reaction window before a malicious/compromised approval set can move custody-held assets.

### Finding Description
The timelock feature is meant to be a custody safeguard: even after `num_signatures_required` approvals are collected, execution must wait `timelock_period` (unless `override_threshold` approvals are reached) so other owners can detect and reject a bad transaction. This is analogous to the SukukFi report's core flaw: a state that should be evaluated relative to *when the protective mechanism was engaged* is instead pinned to a stale prior timestamp/value (PPS at fulfillment vs. current NAV; here, transaction creation time vs. timelock activation time).

Because `creation_time_secs` is fixed at `create_transaction`, and `can_execute_with_timelock` never checks when the `MultisigAccountTimeLock` resource itself was created/updated, any transaction created before the timelock existed (or before it was updated to a longer duration) is checked against a clock that started ticking long before the protection was live. If enough real-world time has already passed since that stale creation timestamp (which is likely for any transaction sitting in the queue for a while), the timelock condition (`elapsed >= timelock`) is trivially satisfied on the very next approval, regardless of the current owners' intent to impose a fresh delay.

### Impact Explanation
This directly affects custody control of multisig-owned assets: APT, fungible-asset stores, resource-account signer capabilities, and code-object upgrade/ownership authority routed through a multisig account rely on the timelock as a last line of defense against a compromised or malicious minority of owners reaching quorum. A stale `creation_time_secs` baseline lets an attacker who already has (or will soon have) enough approvals execute a malicious payload — e.g., draining a resource account's fungible-asset store, reassigning object ownership, or rotating the multisig auth key — the instant the newly-added timelock is deployed, with no actual waiting period. This is a broken custody invariant because it silently nullifies a control that owners/admins believe is protecting their funds.

### Likelihood Explanation
Likelihood is moderate to high in any realistic operational scenario: multisig owners commonly add or tighten a timelock *after* observing suspicious activity, exactly the situation where a malicious transaction is already sitting in the pending queue with an old `creation_time_secs`. Any transaction created even `MIN_TIMELOCK_PERIOD` (1 hour) worth of time before the timelock is configured already satisfies `elapsed >= timelock`, so the racing window for exploitation is broad. I was unable to fully verify `upsert_timelock`'s implementation to see if it retroactively invalidates or resets outstanding transactions' timestamps; if it does, this finding would be mitigated, so this should be verified against the actual `upsert_timelock` body before treating this as confirmed.

### Recommendation
- When `upsert_timelock` establishes or changes the timelock configuration, either (a) invalidate/require re-creation of all currently pending transactions, or (b) re-baseline the elapsed-time check against `max(pending_transaction.creation_time_secs, timelock_config.effective_from_secs)` so no transaction can satisfy a timelock that did not exist while it was pending.
- Add an explicit "timelock activation timestamp" to `MultisigAccountTimeLock` and require `elapsed_since_max(activation, creation) >= timelock_period`.

### Proof of Concept
1. Owners create a multisig account with 2-of-3 approval, no timelock configured.
2. Owner A calls `create_transaction` with a malicious payload (e.g., transfer of the resource account's FA store to an external address). `creation_time_secs = T0`.
3. Time passes normally (e.g., 2 hours) without approval.
4. At `T0 + 2h`, remaining owners, worried about a leaked key, call `upsert_timelock(multisig_signer, timelock_period = 3600, override_threshold = none)` to add protection going forward.
5. Attacker (owner A, or a colluding second owner) immediately gets the second approval.
6. `validate_multisig_transaction` → `can_execute_with_timelock` computes `elapsed = now_seconds() - T0 = 7200s >= 3600s`, returning `true` — the transaction executes instantly, even though the timelock was only just configured and the owners intended a fresh 1-hour delay window before any transaction (old or new) could execute.

(Note: step 4's exact call signature for `upsert_timelock` could not be verified in this session; the PoC assumes it does not reset or invalidate pre-existing pending transactions' `creation_time_secs`, which should be confirmed directly against the function body.)

    /// Return true if the transaction with given transaction id can be executed immediately, or it has to wait
    /// for the timelock to expire.
    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }
