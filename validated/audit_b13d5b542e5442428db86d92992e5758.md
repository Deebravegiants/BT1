Based on my analysis, I found a valid analog to the reported bug class in this gem's webhook verification code.

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing tenant identity spoofing on otherwise-valid webhook requests - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly and unauthenticated from HTTP headers [2](#0-1) . `Utils::HmacValidator.validate` only checks the HMAC against `to_signable_string`, i.e. the body [3](#0-2) . `Registry.process` accepts the request once that body HMAC checks out, and then forwards `request.shop` — the unauthenticated header — straight to the app's handler as the trusted tenant identity [4](#0-3) .

### Finding Description
The identity binding that should hold is:

`shop` (used by the handler as the tenant to act on) == `shop` that Shopify actually signed the webhook body for

But the HMAC computed by `compute_signature`/`validate_signature` in `HmacValidator` is over `verifiable_query.to_signable_string`, which for webhooks is just `@raw_body` [5](#0-4) . The `shop-domain` header used to populate `WebhookMetadata#shop` [6](#0-5)  is never part of the signed material. Any attacker who can obtain one validly-HMAC-signed body/HMAC pair for their own tenant (trivial — they simply run the app on their own Shopify store and let a real webhook be delivered) can replay that exact `raw_body` + `hmac` header to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still passes because it never looks at the shop header, and `Registry.process` dispatches to the handler with `shop: "victim-shop.myshopify.com"` even though the signed body was never produced for that shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to guarantee to consuming applications: a webhook payload that passed HMAC verification is documented/expected to be "an authentic message from the named shop." Because the shop identity is not bound to the signature, an attacker can make an app process attacker-controlled webhook content under a victim shop's identity — a cross-tenant data-integrity/confidentiality issue for any handler that uses `WebhookMetadata#shop` to select which tenant's records to read, write, or delete (e.g., a mandatory `customers/redact` or `orders/create`-style handler keyed by `data.shop`).

### Likelihood Explanation
Likelihood is realistic for any attacker who can install the target app on a store they control (the normal, unprivileged install flow) — no leaked `api_secret_key`, access token, or victim credentials are required. They only need to capture one legitimately-signed webhook delivery for their own shop and replay it with a modified header to the app's public webhook endpoint.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material that `HmacValidator` verifies, or otherwise cryptographically tie the header values to the signed body (e.g., include them in the HMAC input, or require the consuming host application to independently confirm the header's shop against session/install records before trusting `WebhookMetadata#shop`). At minimum, document clearly that `request.shop` is unauthenticated header data and must not be trusted as tenant identity on its own.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` (ordinary, unprivileged install).
2. Attacker triggers a real webhook (e.g. `orders/create`) with attacker-chosen body content; Shopify delivers it with headers including `x-shopify-hmac-sha256: <valid HMAC over body>` and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker resends the identical raw body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates only `@raw_body` against the HMAC and succeeds [7](#0-6) .
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker body>, ...)` [6](#0-5) , causing the app to process attacker-controlled data under the victim's tenant identity.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
