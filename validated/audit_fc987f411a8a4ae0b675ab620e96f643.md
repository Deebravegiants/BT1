### Title
`add`/`updateConnection` silently overwrite `icon`/`name` of an already-trusted origin without re-consent - (File: features/connected-origins/module/connections.js)

### Summary
`ConnectedOrigins#add` and `ConnectedOrigins#updateConnection` merge caller-supplied `icon`/`name` into an existing origin record via `#setAttributes` purely by matching the `origin` string key, with no comparison against the previously-stored/approved `icon`/`name` and no re-consent gate. Because `trusted` and `autoApprove` are preserved (`trusted: trusted ?? value.trusted` in `add`, and `updateConnection` doesn't touch them at all), an already-trusted, auto-approved origin can have its displayed `icon`/`name` silently changed on every call.

### Finding Description
`add` (features/connected-origins/module/connections.js:140-185) looks up the existing record by `origin` and, if found, calls `#setAttributes` with `icon: icon ?? value.icon` and `name: name ?? value.name`, while carrying over `trusted: trusted ?? value.trusted`. `updateConnection` (features/connected-origins/module/connections.js:275-291) is even more permissive: it takes only `{ origin, icon, connectedAssetName }` and unconditionally sets `attributes.icon = icon` whenever a truthy `icon` is supplied, then calls `#setAttributes`.

`#setAttributes` (features/connected-origins/module/connections.js:51-64) does a blind object spread merge (`{ ...connection, ...attributes }`) keyed only on `origin` — it performs no diff against the previously stored `icon`/`name`, and no check of whether the origin is `trusted`/`autoApprove` before allowing metadata mutation. There is no code path that requires fresh user consent (e.g., a popup approval) before `icon`/`name` are updated on a record that already has `trusted: true`/`autoApprove: true`.

The tests confirm this behavior is intentional current behavior, not merely theoretical: `updateConnections should update icon` (features/connected-origins/module/__tests__/connections.test.js:504-511) shows `updateConnection({ origin, icon: 'b' })` freely overwrites `icon` on an existing record with no trust/consent check performed at all in the test setup.

I could not find, within the indexed codebase, the exact call site that wires `senderMetadata.icon`/`title` (produced in `libraries/browser-extension-rpc/src/metadata.js`, using page-controlled `og:site_name`/`<title>`/`favicon` values) directly into `connectedOrigins.add`/`updateConnection`. The `senderMetadata` is attached by `Channel#onMessage`/`onCall` in `libraries/browser-extension-channels/channel.js:31-73` to `sender.metadata`, and it is up to consuming background-script handlers (not present in the indexed subset) to pass that into `connectedOrigins.add`/`updateConnection`. Given the module's public API (`features/connected-origins/api/index.js`) directly exposes both `add` and `updateConnection`, and the README states the module "stores... metadata such as the name and icon of the website" that is meant to reflect the connecting dapp, it is highly likely such a call site exists elsewhere in the full (non-indexed) codebase, but I cannot confirm the exact integration point with certainty.

### Impact Explanation
If a call path exists that lets the connecting origin (or content script running on that origin's page) supply `icon`/`name` on every reconnect (which is a normal, expected part of the "eager connect" flow described in `docs/web3-providers/solana-provider-api.md`), then an origin that is already `trusted: true` and `autoApprove: true` can rebrand its displayed identity (icon/name) at will, without any new user prompt. Since `trusted`/`autoApprove` persist unchanged, this origin continues to receive auto-approved future connect/sign requests. If the wallet UI relies on `icon`/`name` (rather than the raw `origin` string) to communicate to the user which site it's interacting with, this enables identity-spoofing (e.g., a previously-approved malicious/unknown dapp domain could rebrand itself to display trusted branding) while retaining elevated trust/auto-approve privileges — a privilege-retention + identity-spoofing combination scoped to future auto-approved requests.

### Likelihood Explanation
Preconditions: an origin must already be `trusted`/`autoApprove`d once (via normal, legitimate user consent) — no privileged state or leaked keys required. After that, the attacker only needs to control the content served from that same origin (title/meta/favicon, which is trivial and entirely within an ordinary web author's control) and trigger any reconnect/update flow that calls `add`/`updateConnection` with new `icon`/`name` values. This is fully reachable from unprivileged, ordinary dapp behavior and is repeatable on every visit/reconnect. The main uncertainty is whether the wallet UI actually renders `icon`/`name` as the primary trust signal instead of the bound `origin` string — I was not able to locate or verify the UI rendering logic within the indexed code to confirm end-user-visible impact.

### Recommendation
In `features/connected-origins/module/connections.js`, gate identity-affecting updates (`icon`, `name`) for already-trusted/auto-approved origins behind explicit re-consent:
- In `#setAttributes`/`add`/`updateConnection`, detect when `icon` or `name` differ from the currently stored values for a `trusted`/`autoApprove` origin.
- When such a change is detected, do not silently apply it — instead require a fresh approval flow (reset `autoApprove` to `false` and/or surface a re-approval prompt) before persisting the new `icon`/`name`, or store the new metadata as a separate "pending" field until confirmed.
- Alternatively, treat `icon`/`name` as immutable once `trusted: true`, only allowing changes via an explicit user-initiated "update site info" action, not automatically from connect/update calls.

### Proof of Concept
Unit test to add to `features/connected-origins/module/__tests__/connections.test.js`:
```js
test('does not silently change icon/name of trusted+autoApprove origin without re-consent', async () => {
  await connectedOrigins.add({
    origin: 'exodus.com',
    name: 'Exodus',
    icon: 'exodus_icon',
    connectedAssetName: 'solana',
    trusted: true,
  })
  await connectedOrigins.setAutoApprove({ origin: 'exodus.com', value: true })

  // Attacker-controlled content on the same already-trusted origin changes its
  // displayed identity to impersonate a different brand.
  await connectedOrigins.updateConnection({
    origin: 'exodus.com',
    icon: 'spoofed_trusted_brand_icon',
  })

  const origins = await connectedOriginsAtom.get()
  const record = origins.find((o) => o.origin === 'exodus.com')

  // EXPECTED (fails today): identity change should require re-consent,
  // e.g. by resetting autoApprove or rejecting the icon change outright.
  expect(record.icon).toBe('exodus_icon') // should still be original icon
  expect(record.autoApprove).toBe(false) // or trust downgraded pending re-approval
})
```
Currently, `record.icon` becomes `'spoofed_trusted_brand_icon'` and `record.autoApprove` remains `true`, demonstrating the silent overwrite without re-consent.
