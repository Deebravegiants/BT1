### Title
Deposit precision truncation lets a minority depositor's contribution be minted as zero shares, silently diluting them into existing holders - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and equivalent vault contracts)

### Summary
Zest's ERC4626-style vaults compute shares to mint on deposit as `amount * totalSupply / totalAssets` using floor division, and only guard against slippage via a caller-supplied `min-out`, without an explicit "output must be non-zero" check like the one present on the redeem path. As `totalAssets` grows relative to `totalSupply` (normal, expected behavior for a yield-bearing vault as interest accrues), a small deposit can round down to `inkind = 0`, meaning the depositor's underlying is pulled and added to vault assets while the depositor is minted zero shares. This breaks the `shares minted == value contributed / share price` identity for that depositor and permanently transfers their contribution's value to existing shareholders. This mirrors the C4 "Migration total supply reduction" bug class (M-10): value contributed by a minority participant is truncated to zero by an unguarded division against the pooled total, silently removing that participant's economic interest.

### Finding Description
`convert-to-shares-preview` computes minted shares with `mul-div-down`, i.e. floor division: [1](#0-0) 

`deposit` uses this value (`inkind`) directly as the amount to mint, and only validates it against caller-supplied `min-out` via a slippage check — there is no explicit `inkind > u0` requirement, unlike the symmetric `redeem` path which does enforce `ERR-OUTPUT-ZERO`: [2](#0-1) [3](#0-2) 

If `min-out` is left at `0` (the natural default for a caller not anticipating this edge case), a deposit whose `amount * totalSupply` is less than `totalAssets` will pass the `(>= inkind min-out)` check with `inkind = 0`. The deposit still: (1) pulls the full `amount` of underlying from the depositor via `receive-underlying`, (2) mints `0` shares to the depositor, and (3) increases `assets` (the vault's asset accounting) by the full `amount`. This breaks the equation `totalSupply_after / totalAssets_after == totalSupply_before / totalAssets_before` for that depositor's contribution — the depositor's value is absorbed into the pooled `totalAssets`, increasing the redemption value of every other shareholder's existing shares while the depositor receives nothing.

The root numerical cause is structurally identical to the referenced C4 finding: a ratio-based mint that divides a user's contribution by a pooled total using floor division, with no floor/minimum-output enforcement on the mint path, allows a legitimate but unlucky (or manipulated) ratio to zero out a minority participant's issued balance while their contributed value remains locked in the pool.

Unlike a classic ERC4626 "inflation attack" (which requires an attacker to donate/inflate raw token balance), here `total-assets` is a pure bookkeeping variable (`var-get assets` plus computed accrued interest) rather than the vault's live token balance, so a third-party donation cannot manipulate it directly. However, `total-assets` grows autonomously and monotonically for any active vault purely from interest accrual over time (each `accrue` call increases `debt`, hence `total-assets`, while only the treasury reserve fraction of that growth is matched by new share minting). This means the vulnerable ratio condition arises naturally as the vault ages and interest compounds — no attacker action against another user is even required for the depositor to be harmed; only the depositor's own inattention to `min-out` protection.

### Impact Explanation
This is a real, permanent value-freeze/loss for the affected depositor: assets are moved into the vault's tracked balance, but the corresponding shares are minted as zero, so the depositor has no claim (via `redeem`) on the value they contributed. That value permanently accrues to existing shareholders proportionally. This satisfies the "permanent freezing of funds" / "theft of principal" impact bar, since the depositor's principal is unrecoverably folded into other holders' claims with no compensating share balance minted back to them.

### Likelihood Explanation
Likelihood depends on the token's decimal precision and how mature/high-yield the vault is at the time of deposit (larger `totalAssets`/`totalSupply` ratio increases the minimum deposit size that avoids truncation) and on whether the depositing integration/user supplies a protective non-zero `min-out`. For low-decimal underlying assets (e.g. sBTC/BTC-denominated vaults with 8 decimals) and long-lived, high-yield vaults, a modest deposit amount could realistically truncate to zero shares. Because `min-out` is caller-supplied and not enforced to be non-zero by the protocol itself, any integrator or user who defaults it to `0` (a very common, easy mistake, and the value an unaware caller would naturally pass) is exposed. This is a Medium-likelihood, implementation-detail-dependent issue, matching the judged severity of the original C4 finding.

### Recommendation
Add an explicit check on the deposit path mirroring the one already present on redeem:
```
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed before minting, in every vault contract (`v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, and their `local-testing` counterparts). This guarantees the deposit reverts rather than silently minting zero shares while consuming the depositor's underlying, closing the truncation window regardless of the `min-out` value supplied by the caller.

### Proof of Concept
1. Let a vault have accrued significant interest over time such that `total-assets-preview() = TA` and `total-supply-preview() = TS`, with `TA/TS` (share price) large relative to the underlying's smallest unit.
2. A depositor calls `deposit(amount, min-out: u0, recipient: depositor)` with a small `amount` such that `floor(amount * TS / TA) == 0`.
3. `convert-to-shares-preview` in [1](#0-0) 
returns `inkind = u0`.
4. In `deposit`: [4](#0-3) 
the check `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` passes trivially since `u0 >= u0`; `receive-underlying` pulls the full `amount` from the depositor; `ft-mint? zft inkind recipient` mints `0` shares; `assets` is incremented by the full `amount`.
5. Result: the depositor has paid `amount` of underlying and received zero shares — the equivalent value is now embedded in `total-assets` and accrues only to existing shareholders on future `redeem` calls, permanently freezing the depositor's contributed principal from their own claim.

  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))

        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
