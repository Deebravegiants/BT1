## Title
Webhook `shop`, `topic`, `api_version`, and `webhook_id` fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers that are never included in the HMAC computation. `Registry.process` validates only the body-vs-HMAC binding and then forwards the unauthenticated `shop`/`topic` header values straight to the application's webhook handler. This breaks the identity binding that a host application relies on: `shop_bound_by_hmac == shop_delivered_to_handler`.

### Finding Description
The HMAC validation in `Registry.process` is: [1](#0-0) [1](#0-0) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

And `Request#to_signable_string` returns only `@raw_body`, never the headers: [3](#0-2) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are parsed straight from unauthenticated headers and passed into `WebhookMetadata` given to the application handler: [4](#0-3) 

So the equality that should hold — "the shop/topic the HMAC was computed for" equals "the shop/topic acted upon by the handler" — does not hold. The HMAC only proves the body bytes were produced by holders of `api_secret_key` (i.e., Shopify, when delivering to *some* shop that installed the app); it proves nothing about which shop or topic the body is attributed to at delivery time.

An unprivileged attacker can exploit this without any of the disallowed prerequisites (`api_secret_key`, stolen tokens, TLS interception, etc.) simply by installing the target app on their **own** development/trial store, which is an ordinary, unprivileged action:
1. Install the app on their own store; Shopify delivers a real webhook to the app's registered endpoint with a valid `X-Shopify-Hmac-Sha256` computed with the app's real `api_secret_key` over some JSON body (e.g., `orders/create`).
2. Capture that `(raw_body, hmac)` pair.
3. Replay the identical `raw_body` and `hmac` to the app's webhook endpoint, but substitute `X-Shopify-Shop-Domain` with a victim shop's domain and/or `X-Shopify-Topic` with a different registered topic (e.g., `app/uninstalled`, `customers/redact`, `shop/update`).
4. `HmacValidator.validate` still succeeds because it only checks `raw_body` against `hmac` — it never touches the `shop`/`topic` headers.
5. `Registry.process` dispatches to the handler for the attacker-chosen topic with `WebhookMetadata#shop` set to the victim's domain, and the attacker-supplied body.

### Impact Explanation
Because most host applications key their persisted sessions/access tokens and business logic off of `WebhookMetadata#shop` (this is the documented contract — see `webhooks/registry_test.rb`, `data.shop` is what handlers act on), this allows an attacker to make the library assert to the application "this authentic Shopify-signed event belongs to shop X" for an arbitrary shop X of the attacker's choosing, while fully controlling the JSON body. Depending on which topic/body the app is willing to accept for that body shape, this enables cross-tenant data confusion/corruption (e.g., forging `customers/redact`, `shop/update`, or order-lifecycle events attributed to a shop the attacker does not control), which is a cross-tenant access impact — matching the Critical impact category defined for this assessment.

### Likelihood Explanation
The attack requires no privileged credentials — only the ability to install the app on an attacker-controlled store (a normal, unprivileged flow every third-party app must support) and the ability to POST to the app's public webhook endpoint, which is publicly reachable by design. The replay is trivial once one legitimate webhook is captured.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, and ideally `webhook-id`/timestamp) in the signed/verified material, or otherwise cryptographically bind them to the payload before dispatch — e.g., require and verify the `X-Shopify-Webhook-Id` for idempotency plus cross-check the `X-Shopify-Shop-Domain` against the shop that legitimately owns the currently active session/token before invoking the handler, rejecting mismatches. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are **not** cryptographically bound to the HMAC and that consuming applications must independently validate that the shop is a currently-installed tenant before trusting the payload.

### Proof of Concept
```ruby
# Step 1: attacker installs the app on their own store and captures a real webhook delivery
raw_body = '{"id":1}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Step 2: attacker replays the SAME body/hmac but swaps shop-domain + topic headers
forged_headers = {
  "x-shopify-topic"       => "app/uninstalled",          # attacker-chosen topic
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),        # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # attacker-chosen shop
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HMAC validation passes because it only checks raw_body vs hmac
ShopifyAPI::Webhooks::Registry.process(request)
# => handler invoked with data.shop == "victim-shop.myshopify.com", data.topic == "app/uninstalled"
```
