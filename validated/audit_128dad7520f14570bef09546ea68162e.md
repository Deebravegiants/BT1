### Title
Withdrawal to unfunded XRP account skips `requireDestinationTag` check, risking stuck funds after account activation - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`validateWithdrawal` in `PoaBridge` special-cases XRP withdrawals to accounts that don't yet exist on the XRPL ledger, swallowing the `XrplAccountNotFundedError` and skipping the `requireDestinationTag`/`depositAuth` checks entirely. If the destination account is later activated with `requireDestinationTag=true` and the withdrawal carries no `destinationMemo`, the transfer can arrive without the required tag.

### Finding Description
The broken equality is: **the destination-tag requirement observed at validation time** (none, because the account lookup throws `XrplAccountNotFundedError` before `account_flags.requireDestinationTag` can be read) **≠ the requirement that may exist at execution/settlement time** (`requireDestinationTag=true`, once a third party funds and configures the account before the POA relayer settles the withdrawal).

Code path: [1](#0-0)  shows that for `assetInfo.blockchain === Chains.XRPL`, the function calls `xrpl.httpClient.getAccountInfo(args.destinationAddress, xrplConfig)`, then reads `accountInfo.account_flags.requireDestinationTag` to enforce `XrplDestinationTagRequiredError` when `!args.destinationMemo`. However, if `getAccountInfo` throws before returning (because the account is unfunded), the `catch` block only re-throws when `!(isXrp && error instanceof xrpl.httpClient.XrplAccountNotFundedError)` — i.e., for an XRP asset (`assetInfo.contractId === "xrp.omft.near"`) hitting this specific error, the error is swallowed and `validateWithdrawal` resolves normally, never reaching the `requireDestinationTag` logic.

An unprivileged caller fully controls `destinationAddress` and `destinationMemo` as ordinary SDK inputs (via `WithdrawalParams`). They can supply any syntactically valid, currently-unfunded XRP address with no memo. `validateWithdrawal` passes; the withdrawal intent is created via `createWithdrawalIntents` [2](#0-1)  and gets signed/settled through the POA bridge relayer, independent of any further tag check in this repo.

Existing guards (`validateAddress`, `compareAddresses`, minimum-amount checks) validate address format and token-address collisions but do not perform any destination-tag or funded-state re-check right before settlement; there is no re-validation point in this codebase between `validateWithdrawal` passing and the relayer executing the transfer.

### Impact Explanation
No funds custodied by the SDK/integrator are misdirected to an attacker-controlled address (funds still travel to the address the caller specified). The impact is that a legitimately-intended withdrawal, once signed and submitted, can land on an XRPL account that subsequently enables `RequireDestTag` before settlement completes, causing the transfer to fail/park on the ledger per XRPL rules — requiring manual intervention (matching the "withdrawal stuck until manual intervention" High-severity category). This affects the withdrawing user's own funds; it is repeatable per XRP withdrawal to any not-yet-funded destination account, and the outcome depends on the third-party account owner's later choice to enable `RequireDestTag`, which the caller/integrator cannot control at validation time.

### Likelihood Explanation
Preconditions: an XRP (`xrp.omft.near`) withdrawal to a destination address that is unfunded (no ledger entry) at validation time; no `destinationMemo` supplied by the caller; the destination account gets funded and reserve-activated with `RequireDestTag` enabled sometime between validation and actual on-chain settlement by the POA relayer. This is a plausible race — unfunded XRP addresses are common (e.g., freshly generated addresses, exchange deposit addresses not yet activated), and settlement latency through the relayer creates a window for the account state to change. The attacker (or just an unlucky legitimate user) does not need any special access — this can happen purely through normal usage/timing, not deliberate exploitation, though it could also be deliberately engineered by a caller who withdraws to an address they know will soon require a tag, to grief themselves or a downstream integrator's status reporting.

### Recommendation
Do not treat "account not funded" as safe-to-skip for the destination-tag check. Options: (1) require callers to always supply a `destinationMemo`/tag for XRP withdrawals to unfunded accounts, or refuse the withdrawal until the account is funded and its flags can be verified; (2) re-validate `requireDestinationTag` and `depositAuth` immediately before/at settlement time (as close to execution as possible) rather than only at initial `validateWithdrawal`; (3) surface a clear warning/error to the integrator that the destination-tag requirement is unknown for unfunded accounts, rather than silently passing validation.

### Proof of Concept
```ts
import { describe, it, expect, vi } from "vitest";
import { xrpl } from "@defuse-protocol/internal-utils";
import { PoaBridge } from "./poa-bridge";

describe("PoaBridge.validateWithdrawal - XRP unfunded account tag bypass", () => {
  it("skips requireDestinationTag check when destination account is unfunded", async () => {
    const bridge = new PoaBridge({ envConfig: /* mock env with poaTokenFactoryContractID */, xrplRpcUrls: ["https://mock-xrpl"] });

    // Mock getSupportedTokens to return valid tokenInfo for xrp.omft.near
    vi.spyOn(bridge as any, "getCachedSupportedTokens").mockResolvedValue({
      tokens: [{ intents_token_id: "nep141:xrp.omft.near", origin_chain_address: "native", min_withdrawal_amount: "0" }],
    });

    // Mock getAccountInfo to reject with XrplAccountNotFundedError
    vi.spyOn(xrpl.httpClient, "getAccountInfo").mockRejectedValue(
      new xrpl.httpClient.XrplAccountNotFundedError("rUNFUNDEDADDRESS")
    );

    // Left side of equality: requireDestinationTag as observed by validateWithdrawal => never read (undefined/skipped)
    // Right side: assume the account will later be funded with requireDestinationTag = true

    await expect(
      bridge.validateWithdrawal({
        assetId: "nep141:xrp.omft.near",
        amount: 1000n,
        destinationAddress: "rUNFUNDEDADDRESS",
        destinationMemo: undefined, // no tag supplied
        skipMinAmountValidation: true,
      })
    ).resolves.toBeUndefined(); // validation passes despite unknown/future requireDestinationTag=true

    // Demonstrates: XrplDestinationTagRequiredError was never thrown because getAccountInfo
    // threw XrplAccountNotFundedError first, and the requireDestinationTag branch was
    // never reached (getAccountInfo mock only called once, no further account_flags access).
    expect(xrpl.httpClient.getAccountInfo).toHaveBeenCalledTimes(1);
  });
});
```
This shows both sides of the equality diverge: at validation time the tag requirement is treated as "not required" (silently), while nothing in the code path re-checks it later if the account becomes funded with `requireDestinationTag=true` before settlement.
