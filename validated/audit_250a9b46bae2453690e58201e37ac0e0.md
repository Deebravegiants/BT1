### Title
Webhook `shop`, `topic`, `webhook-id`, and `api-version` fields are trusted from unauthenticated HTTP headers while `HmacValidator` only signs the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands the caller's handler a `shop` identifier that was read from an HTTP header never covered by that signature. This breaks the identity binding `HMAC(secret, signed_bytes) == signature` versus the actual bytes the application acts on, allowing a rogue app-installer who controls one tenant's genuine webhook traffic to relabel that traffic as belonging to a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes and compares the HMAC exclusively over that signable string: [2](#0-1) 

Meanwhile, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers, which are never part of the signed bytes: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards the *header-derived, unauthenticated* `request.shop` value to the caller's handler as the tenant identity for that webhook payload: [4](#0-3) 

Because the app's `api_secret_key` is a single secret shared across every shop that has the app installed (it is not a per-shop key), any legitimate merchant who has installed the app can trigger a genuine, correctly-signed webhook for their own shop (e.g., by creating an order), capture the raw body and its valid `X-Shopify-Hmac-Sha256` value, and then resend that exact body/signature pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and, if desired, `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a victim shop's domain. `HmacValidator.validate` still succeeds, because it never inspects those headers — it only re-computes the HMAC over the body. `Registry.process` therefore accepts the forged request and calls the handler with `shop: <victim shop>` while `body` is the attacker's own (fully attacker-controlled) payload.

This is the same class of defect as the reported `giveLoan()` issue: a value that determines *whose* state the code mutates (there, the loan's lender/debt; here, the tenant the webhook is attributed to) is not cryptographically bound to the authenticated data, letting an unprivileged party redirect the effect of an authenticated action onto a different identity.

### Impact Explanation
This crosses a tenant boundary: an attacker with only their own (attacker-controlled) shop installation can make the app process attacker-chosen webhook content under a different merchant's `shop` identity. Any downstream application logic that keys off `WebhookMetadata#shop` (session/store lookup, data writes, cache invalidation, order/customer sync, uninstall handling for `app/uninstalled`, GDPR data-request/erasure handlers, etc.) can be tricked into applying attacker-controlled data to another tenant's session/store. This matches the "cross-tenant access" high/critical impact category, since the `shop` claim used to select the tenant is not covered by the integrity check meant to authenticate the entire message.

### Likelihood Explanation
Likelihood is realistic for any app that has at least one other installer besides the attacker: the attacker only needs their own working installation (to obtain a validly-signed body/HMAC pair) and network access to POST to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header — no access token, secret, or privileged account is required, satisfying the "unprivileged internet user" constraint.

### Recommendation
Bind the tenant/topic identity into the authenticated data rather than trusting headers independently of the signature:
- Include `shop`, `topic`, and `webhook_id` in the bytes covered by `to_signable_string`/`HmacValidator`, or
- After HMAC validation, independently verify that `request.shop` corresponds to a shop for which the app actually has an active installation/session before invoking any handler, and reject webhooks whose header-derived shop cannot be corroborated.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers an event so Shopify sends a genuine webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's single shared `api_secret_key`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker replays the request to the same app's webhook endpoint, keeping body `B` and header `H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`B`) only, and it matches `H` — validation passes: [4](#0-3) 
4. The handler is invoked with `WebhookMetadata` whose `shop` is `"victim-shop.myshopify.com"` but whose `body` is entirely attacker-controlled content from step 1, demonstrating the broken binding between the authenticated payload and the tenant it is attributed to.
