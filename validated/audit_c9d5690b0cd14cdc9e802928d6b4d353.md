### Title
Webhook shop-domain identity not covered by HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` bind the HMAC only to the raw request body, while the shop identity (`shop-domain` header, exposed via `Request#shop`) that the host application uses to route the webhook to a specific tenant is never included in the signed content.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate`/`validate_signature` computes/compares the HMAC solely against that signable string [2](#0-1) . The `shop` value is read from a separate, unauthenticated header (`shopify-shop-domain` / `x-shopify-shop-domain`) [3](#0-2) [4](#0-3) . `Registry.process` validates the body HMAC and then immediately trusts `request.shop` to construct `WebhookMetadata`, which is handed to the app's handler as the tenant identifier [5](#0-4) [6](#0-5) .

The identity binding that should hold is: `HMAC(shop-domain, body) == HMAC(api_secret_key, raw_body)`, i.e., the field the app acts on for tenant routing (`shop`) should be covered by the same integrity check as the body. Here the equality actually enforced is only `HMAC(body) == valid`, with `shop` supplied out-of-band. This is confirmed directly by the test suite, which builds a valid HMAC purely from the body (`"{}"`) and freely varies the `shopify-shop-domain` header value without affecting HMAC validity [7](#0-6) .

### Impact Explanation
An unprivileged internet user who has their own Shopify store using the same app (or who can otherwise obtain one genuine webhook delivery — e.g., via their own dev/test store, since the app's `api_secret_key` is shared across all installs) receives a request with a body+HMAC pair signed with the app's shared secret. Because `shop` is not part of the signed content, that same body+HMAC can be replayed to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header value naming a *different* victim shop. `HmacValidator.validate` still returns `true` (it only checks the body), and `Registry.process` forwards `WebhookMetadata` with the attacker-chosen `shop` to the handler [8](#0-7) . Any host app that uses `data.shop` to look up per-tenant state, credentials, or to trigger tenant-scoped side effects (as the gem's own documented handler pattern does — `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) would process attacker-controlled body content while misattributing it to a victim tenant, i.e., a cross-tenant confusion/injection primitive.

### Likelihood Explanation
Requires the attacker to possess one genuine app-signed webhook body/HMAC pair (obtainable by installing the app on their own shop, which is realistic for any publicly-installable app) and to be able to POST to the app's webhook endpoint with modified headers — both are low-effort, unprivileged actions reachable purely over the internet, no leaked secret or access token required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the signable content verified by `HmacValidator`, or independently verify that the `shop-domain` header value is bound to the shop that legitimately owns the current app installation/session before trusting `WebhookMetadata#shop` for tenant routing (e.g., derive/cross-check shop identity from the registered subscription rather than solely from the caller-supplied header).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, obtains a genuine webhook delivery with raw body `B` and valid header `shopify-hmac-sha256 = HMAC(api_secret_key, B)`.
2. Attacker replays a POST to the app's webhook endpoint using the same body `B` and same HMAC value, but sets `shopify-shop-domain: victim.myshopify.com`.
3. `HmacValidator.validate` succeeds (as shown by `test_process_with_new_format_headers`, which validates purely against body content regardless of shop header value) [7](#0-6) .
4. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed_body, ...)` [9](#0-8) , causing the app to process attacker-supplied content under the victim tenant's identity.
