### Title
Blacklist-vulnerable USDC creator balance in `FeeVault` can be permanently frozen with no recovery path - ([File: packages/contracts/src/FeeVault.sol])

### Summary
`FeeVault` accumulates each token creator's share of the 0.75% Alt Fun trading fee in a per-address scalar (`creatorBalance[creator]`) that is only ever paid out via `claim()`, which unconditionally `safeTransfer`s to `msg.sender`. If a creator address becomes blacklisted by USDC (a real, documented risk for USDC — the exact scenario the C4 judge accepted for M-04), every future `claim()` call from that address reverts permanently, and — unlike `FeeVault.feeTo` (which the owner can rotate via `setFeeTo`) — there is no admin function that can redirect, sweep, or reassign a stuck `creatorBalance[creator]` to a new address. The funds are frozen forever with zero on-chain remediation.

### Finding Description
`FeeVault.claim()` pays out strictly to `msg.sender`: [1](#0-0) 

Fees accrue to `creator` via `accrue()`, called by `Zap._accrueFee` on every buy/sell with `bonding_.creatorOf(tokenAddress)` (attribution can be updated going forward via `Bonding.transferCreator`, but only for future accruals — it does not touch the already-accrued `creatorBalance[oldCreator]` scalar in the vault): [2](#0-1) [3](#0-2) 

The vault's `usdc` is a fixed, immutable ERC20 set once at `initialize` (real USDC on mainnet — a token that Circle can and does blacklist addresses on): [4](#0-3) 

Contrast this with the protocol-side balance: `claimProtocol()` pays a rotatable `feeTo` address, and the owner has `setFeeTo` to redirect the *entire* outstanding balance to a fresh address if the current recipient becomes unable to receive USDC: [5](#0-4) [6](#0-5) 

No equivalent exists for `creatorBalance`. There is no `setCreator`, no `migrateBalance`, no owner-sweep-and-reissue path in `FeeVault.sol`. Once `usdc.safeTransfer(creator, amount)` reverts because `creator` is blacklisted, `claim()` for that creator reverts every time it is retried, for any amount, forever — the SafeERC20 wrapper (per the `MultiRewardDistributor.sendReward` analog in the referenced report) guarantees the revert propagates and blocks the entire claim, not just the blacklisted portion.

This maps directly onto the referenced bug class: a shared/permanent balance denominated in a real-world censorable token (USDC ≈ the report's "emissionToken"), where a single address becoming untransactable permanently freezes value that the protocol's own admin cannot recover — because, unlike the protocol-fee side, the creator side of `FeeVault` was never given a rotation/rescue mechanism.

### Impact Explanation
Any token creator's lifetime, unclaimed 0.25% creator-fee share (`creatorBalance[creator]`) becomes permanently and irrecoverably locked in `FeeVault` the moment their address is blacklisted by USDC issuer sanctions/compliance action. Because creators can accumulate fees across every token they've ever launched (`claim()` pays "their pooled USDC balance across every token they've launched" per the design doc), the frozen amount can be substantial for an active creator. There is no owner override, no timelock rescue, no alternate claim path — the funds are permanently stuck as unbacked USDC sitting in the vault (inflating its balance without any corresponding claimable path), a genuine freezing-of-funds bug matching the accepted severity class of the referenced finding (medium: real, non-hypothetical censorship risk on a token the protocol chose to rely on, with no admin mitigation for one specific balance type).

### Likelihood Explanation
USDC blacklisting is a documented, real-world occurrence (used precisely as the counter-example in the original report's judged discussion — "USDC and USDT are both censorable"). Any creator who accrues meaningful fees and is later sanctioned, compromised (e.g., linked to an OFAC-listed exploit, mixer interaction, or Circle compliance action), or otherwise blacklisted will trigger this permanently, with no attacker action required — it is a pure design gap (missing admin remediation), analogous to the original report's "admin cannot un-poison already-accrued rewards" finding, except here the missing remediation is asymmetric: it exists for `feeTo` but was omitted for `creatorBalance`.

### Recommendation
Add an owner-gated recovery path for stuck creator balances, mirroring the protocol-fee side's flexibility, e.g.:
- An `onlyOwner` function `reassignCreatorBalance(address from, address to)` that moves `creatorBalance[from]` to `creatorBalance[to]` (with appropriate event emission), so a creator confirmed to control a new address can migrate a frozen balance.
- Alternatively, wrap the `claim()` transfer in `try/catch`, and on failure, escrow the amount under a separate "claimable-by-signature" or admin-assisted path rather than reverting the whole call.
- At minimum, document the risk explicitly and provide a governance escape hatch, matching the treatment already given to `feeTo`.

### Proof of Concept
1. Creator `C` launches a token via `Zap.createToken`, and the token trades, accruing fees so that `FeeVault.creatorBalance(C) > 0` (via `accrue()` calls from `Zap._accrueFee` on buys/sells).
2. USDC issuer blacklists address `C` (simulate by deploying/using a `MockERC20` whose `transfer`/`_update` reverts when `to == C`, mirroring real USDC's blacklist `_beforeTokenTransfer` check).
3. `C` calls `FeeVault.claim()`. `amount = creatorBalance[C]` is nonzero, so the function proceeds to `$.usdc.safeTransfer(C, amount)`, which reverts because `C` is blacklisted.
4. Every subsequent retry of `claim()` from `C` reverts identically. There is no `FeeVault` function available to `C` or to `owner()` that can redirect, sweep, or otherwise recover `creatorBalance[C]` — confirmed by inspecting `FeeVault.sol`'s complete function surface (`accrue`, `claim`, `claimProtocol`, `sweepDonations`, `addDepositor`, `removeDepositor`, `setFeeTo`), none of which touch an individual creator's balance except `claim()` itself.
5. The corresponding USDC remains locked in the vault's balance indefinitely, unreachable by any on-chain call.

        $.totalAccruedCreator -= amount;
