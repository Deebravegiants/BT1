## Analysis

The Solidity bug pattern — an overflow guard that only protects the *multiplication* step while a later unguarded narrowing cast can still silently wrap and produce a bogus small value — has a direct analog in this codebase's `U128`/`U256` math helpers. [1](#0-0) 

`U128`/`U256` are generated by `uint::construct_uint!`, whose `.as_u64()` **does not** panic on overflow — it silently truncates to the low 64 bits. The codebase is aware of this and defines a *safe* conversion path, `Calculator::to_u64`, which uses `TryInto` and returns `AmmError::ConversionFailure` on overflow: [2](#0-1) 

However, the LP-mint/withdraw ratio helpers bypass this safe path and call `.as_u64()` directly on the raw `U128` result: [3](#0-2) 

This `InvariantPool::exchange_token_to_pool` function is exactly what computes the LP tokens minted on deposit: [4](#0-3) 

Here `pool_total_amount = amm.lp_amount` (existing LP supply, a u64) is multiplied by `token_input = deduct_coin_amount` (attacker-controlled deposit amount, up to u64::MAX) and divided by `token_total = total_coin_without_take_pnl` (the pool's real coin balance, which an attacker can drive to a very small value via a large prior swap, since swaps do not change `lp_amount`). If the quotient exceeds `u64::MAX`, `.as_u64()` silently truncates instead of erroring — unlike swap math, whose output is provably bounded by an already-valid u64 pool balance and thus not exploitable this way. [5](#0-4) 

The truncated (attacker-influenced) `mint_lp_amount` is then unconditionally credited via `token_mint_to` and added to `amm.lp_amount`, with no re-validation against the real deposit ratio — enabling unbacked LP minting.

### Title
Unchecked `U128::as_u64()` truncation in `InvariantPool`/`InvariantToken` allows unbacked LP‑token minting during Deposit - (File: `program/src/math.rs`, `program/src/processor.rs`)

### Summary
`InvariantPool::exchange_token_to_pool` / `exchange_pool_to_token` and `InvariantToken::exchange_coin_to_pc` / `exchange_pc_to_coin` compute a `U128` ratio and cast it to `u64` with `.as_u64()`. Unlike `Calculator::to_u64`, which uses a checked `TryInto` and returns `AmmError::ConversionFailure` on overflow, `uint::construct_uint!`'s `.as_u64()` silently truncates to the low 64 bits on overflow. This mirrors the reported Solidity issue: an unguarded narrowing conversion after arithmetic that can exceed the target type's range, producing a wrong value instead of failing safely.

### Finding Description
In `Processor::process_deposit`, `mint_lp_amount` is derived from `amm.lp_amount * deduct_coin_amount / total_coin_without_take_pnl` (or the pc-side equivalent) via `InvariantPool::exchange_token_to_pool`. `amm.lp_amount` and `deduct_coin_amount` are each up to `u64::MAX`, so their product can reach ~2^128. If `total_coin_without_take_pnl` (the pool's real, unpnl'd coin balance) is small — which an unprivileged swapper can engineer by first performing a large swap that drains most of one side of the pool without changing `lp_amount` — the resulting quotient can exceed `u64::MAX`. `.as_u64()` then truncates instead of reverting, yielding an attacker-shapeable `mint_lp_amount` that has no relation to the actual value deposited.

### Impact Explanation
An attacker can craft `deduct_coin_amount` (via the `Deposit` instruction's `max_coin_amount`/`base_side` parameters) so that the truncated low-64-bit result is a large, favorable LP amount. Real deposited tokens (`deduct_coin_amount`, `deduct_pc_amount`) are transferred at the amount the attacker chooses, but the LP minted is decoupled from the true pool ratio, allowing unbacked LP minting. The attacker can then redeem the inflated LP balance via `Withdraw`, draining coin/pc reserves that back other depositors' legitimate LP tokens — resulting in insolvent pool accounting and theft of LP funds.

### Likelihood Explanation
Requires: (1) driving the pool's `total_coin_without_take_pnl` (or pc side) low relative to `amm.lp_amount` via ordinary swap instructions (unprivileged, single-transaction reachable), and (2) issuing a `Deposit` with a large `max_coin_amount`/`max_pc_amount` to trigger the overflow in the ratio multiplication. Both steps use only standard, permissionless instructions (`SwapBaseIn`/`SwapBaseOut`, `Deposit`) with attacker-chosen accounts/data, making this practically reachable, though it requires a specific pool state (very skewed reserve vs. lp supply) to trigger the overflow threshold.

### Recommendation
Replace the raw `.as_u64()` calls in `InvariantPool::exchange_token_to_pool`, `exchange_pool_to_token`, and `InvariantToken::exchange_coin_to_pc`, `exchange_pc_to_coin` (program/src/math.rs) with the checked `Calculator::to_u64` conversion (or equivalent `try_into` with explicit error propagation) so that any ratio computation exceeding `u64::MAX` causes the instruction to fail with `AmmError::ConversionFailure` rather than silently minting/returning a truncated amount.

### Proof of Concept
1. Create a pool via `Initialize2` with attacker-controlled mints and an initial ratio giving a sizable `lp_amount` (e.g. `sqrt(init_pc_amount * init_coin_amount)`).
2. Perform a large `SwapBaseIn`/`SwapBaseOut` (coin→pc) to drain most of the coin-side reserve, driving `total_coin_without_take_pnl` down toward a small value while `amm.lp_amount` remains unchanged (see `process_swap_base_in`, `program/src/processor.rs:1940-2048`).
3. Call `Deposit` with `base_side = 0` and a large `max_coin_amount` (bounded only by the attacker's own token balance) such that `amm.lp_amount * deduct_coin_amount / total_coin_without_take_pnl` (computed in `InvariantPool::exchange_token_to_pool`, `program/src/math.rs:456-477`, invoked at `program/src/processor.rs:1243-1250`) exceeds `u64::MAX`.
4. Observe `mint_lp_amount` is the truncated low-64-bit remainder rather than a `ConversionFailure` error, and is minted to the attacker via `Invokers::token_mint_to` (`program/src/processor.rs:1341-1350`).
5. Attacker calls `Withdraw` with the inflated LP balance to redeem a disproportionate share of pool coin/pc reserves.
