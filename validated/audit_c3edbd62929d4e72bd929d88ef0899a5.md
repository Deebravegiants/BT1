Predictable, unsigned `offline_<shop>` session cookie enables cross-tenant session/token theft in non-embedded apps - (File: lib/shopify_api/utils/session_utils.rb + lib/shopify_api/auth/oauth.rb)

### Summary
For non-embedded (or embedded-without-JWT) apps, `SessionUtils.current_session_id` trusts the raw `shopify_app_session` cookie value as the session id with no cryptographic binding to `Context.api_secret_key`, and that value is itself deterministically derived as `"offline_#{shop}"` from public shop-domain information. Any attacker who knows a victim's `*.myshopify.com` domain can send an HTTP request with a forged `Cookie: shopify_app_session=offline_<victim-shop>` header and have the host app resolve and use the victim's stored offline access token.

### Finding Description
The claimed binding is: `session id used to key SessionStorage == bytes authenticated under Context.api_secret_key`. Tracing the code shows this binding never holds for the cookie path.

- `SessionUtils.current_session_id(shopify_id_token, cookies, online)` in non-embedded mode (`Context.embedded? == false`) or embedded-without-id-token skips JWT entirely and calls `cookie_session_id(cookies)`. [1](#0-0) 
- `cookie_session_id` just returns `cookies[SessionCookie::SESSION_COOKIE_NAME]` verbatim — no HMAC, no signature, no server-side secret involved. [2](#0-1) 
- `HmacValidator.validate` (which does use `Context.api_secret_key` via `OpenSSL.secure_compare`) is only invoked inside OAuth's `validate_auth_callback` to validate the *initial* Shopify redirect query string; it is never called on the runtime session cookie. [3](#0-2) [4](#0-3) 
- Critically, for offline sessions the cookie value set by `validate_auth_callback` is literally `session.id`, i.e. `offline_#{shop}` — a value derived only from `shop`, a public identifier (the store's `myshopify.com` domain), with no random/secret component. [5](#0-4) [6](#0-5) 
- Test fixtures confirm this exact derivation: `expected_session = Session.new(id: "offline_#{@shop}", ...)` and `expected_cookie = SessionCookie.new(value: "offline_#{@shop}", ...)`. [7](#0-6) 

Because the value returned by `current_session_id` is passed by the host app directly into `SessionStorage.load_session(id)` (per documented usage), an attacker who supplies a forged `Cookie` header containing `offline_<victim-shop>.myshopify.com` causes the app to load and use the victim's stored session/access token — with no check that the value was ever produced by, or authenticated against, this app's `api_secret_key`. None of the existing guards apply here: `HmacValidator.validate` is scoped to the OAuth callback query string, not the session cookie; `JwtPayload`'s `aud`/`iss` checks only apply to the embedded-JWT branch, which this path bypasses entirely; `ShopValidator.sanitize!` and `Context.setup?`/`private?` checks are unrelated to session-cookie authenticity.

### Impact Explanation
An attacker who knows or guesses a victim shop's domain (often public/discoverable) can, without ever touching `api_secret_key`, cause the app to treat their forged request as an authenticated request for the victim's offline session — leading to disclosure/use of the victim's offline access token and cross-tenant data access. This is repeatable against any shop whose domain is known, with no per-victim secret required, matching the Critical category (cross-tenant access / theft of merchant access token).

### Likelihood Explanation
Preconditions: app is non-embedded (or embedded without JWT/id-token support), uses the gem's documented `SessionUtils.current_session_id` + cookie flow, and stores offline sessions using the default `offline_#{shop}` id scheme. Attacker cost is minimal: no secrets needed, only the target shop domain (`*.myshopify.com`), which is typically discoverable (storefront URL, marketing links, webhook `X-Shopify-Shop-Domain` header structure, etc.). No XSS, MITM, or physical access is required — the attacker directly crafts an HTTP request/`Cookie` header with an HTTP client they control; browser same-origin cookie restrictions are irrelevant since the attacker is not relying on a victim's browser to leak the cookie.

### Recommendation
Do not use a deterministic, secret-free value as the session cookie/session id for non-embedded flows. Bind the cookie's session id value to a per-installation secret (e.g., HMAC-sign the cookie value with `Context.api_secret_key`, or use a cryptographically random session id stored server-side and validated on every use) so that `cookie_session_id` cannot be forged from public shop-domain knowledge alone, and validate that binding in `SessionUtils.current_session_id` before returning the id to be used as a `SessionStorage` lookup key.

### Proof of Concept
Minitest + WebMock/Mocha test plan:
1. Set `ShopifyAPI::Context.stubs(:embedded?).returns(false)`.
2. Build `cookies = { "shopify_app_session" => "offline_victim-shop.myshopify.com" }` (no id-token, no HMAC).
3. Call `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` and assert it returns `"offline_victim-shop.myshopify.com"`.
4. Assert `ShopifyAPI::Utils::HmacValidator.expects(:validate).never` across the whole call, proving no HMAC check against `Context.api_secret_key` ever occurs on this path.
5. Stub `ShopifyAPI::Auth::Session::SessionStorage` (or the app-level `load_session`) to return a fixture session keyed by `"offline_victim-shop.myshopify.com"` containing a fake victim access token, and assert the returned session/access token equals the victim's stored one — demonstrating that an attacker-supplied cookie derived purely from public shop-domain knowledge resolves to another tenant's credentials.
