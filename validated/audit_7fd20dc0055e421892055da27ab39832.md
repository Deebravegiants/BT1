### Title
Overpaid native-token fees for POST/GET dispatch are permanently stranded in `EvmHost` instead of being refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` accept `msg.value` as native-token payment for the ISMP relayer fee and swap it via Uniswap V2's `swapETHForExactTokens`, but forward the *entire* `msg.value` into the swap and never account for or refund the leftover ETH that the swap does not consume. Any application or user calling these payable entrypoints with more native token than the swap actually needs permanently loses the difference, mirroring the "Lack of refund mechanism for overpayment" report against `Bridge.sol#deposit`.

### Finding Description
Both dispatch entrypoints follow the same pattern: [1](#0-0) [2](#0-1) 

`IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` only spends what is required to buy exactly `post.fee` units of the fee token and refunds unspent ETH — but that refund goes to `msg.sender` of the *router call*, which is `EvmHost` itself (since `EvmHost` is the caller of the router), not the original transaction sender. There is no code path in `EvmHost` that forwards this leftover ETH back to `_msgSender()`/`post.payer`, and no sweep/withdraw function exists on the contract (confirmed absent via search for `receive()`/`withdraw`/`sweep` in `EvmHost.sol`). The excess simply accumulates as stray ETH balance on `EvmHost` with no accounting or recovery mechanism.

This is not a purely theoretical/accidental-overpayment scenario: the SDK's own fee-quoting logic pads the native amount sent with `dispatch()` by 1–5% specifically to absorb Uniswap slippage between quote and execution time, e.g. the 1% buffer in `OrderCanceller.quoteCancelFromSource` and `tokenGateway.quoteNative`: [3](#0-2) [4](#0-3) 

So under normal, SDK-recommended usage, callers routinely send more native token than the swap consumes, and that padding is silently lost to `EvmHost` on every dispatch. Contrast this with `IntentGatewayV2.placeOrder`, which performs the identical fee-swap-via-native pattern but explicitly tracks the unspent `msgValue` and refunds it to the caller: [5](#0-4) 

`HyperFungibleToken.send` and `WrappedHyperFungibleToken.send` also forward `msg.value`/the fee remainder straight into `IDispatcher(_host).dispatch{value: ...}(request)` without any downstream refund once inside `EvmHost`: [6](#0-5) 

### Impact Explanation
Any single call to `EvmHost.dispatch(DispatchPost)` or `dispatch(DispatchGet)` with native-token payment permanently strands the unswapped ETH remainder inside `EvmHost`, with no path for the payer to reclaim it. Because this is the core dispatch entrypoint used by every app on the chain (token bridging, HFT sends, GET-based cancellations, etc.), and the SDK itself intentionally overprovisions native value for slippage protection, this loss occurs routinely rather than only via user error, resulting in a continuous drain of user funds into the host contract with no recovery mechanism.

### Likelihood Explanation
High reachability: this happens on every native-token-funded `dispatch()` call made by any unprivileged caller/app through the standard, documented, SDK-recommended flow (padding native value for slippage). No special privileges, timing, or adversarial conditions are required — it is triggered by ordinary usage of the messaging fee-payment path.

### Recommendation
In `EvmHost.dispatch(DispatchPost)` and `dispatch(DispatchGet)`, capture the actual amount spent by `swapETHForExactTokens` (e.g., via its returned `amounts[0]` or a balance-before/after ETH check) and refund any leftover `msg.value` to `_msgSender()`, following the same pattern already implemented in `IntentGatewayV2.placeOrder`'s `_sendValue(msg.sender, msgValue)` refund.

### Proof of Concept
1. Attacker/user calls `EvmHost.dispatch(DispatchPost)` (or any app such as `HyperFungibleToken.send`) supplying `msg.value` intentionally or per SDK-recommended slippage buffer higher than the exact amount `swapETHForExactTokens` needs to acquire `post.fee` units of `feeToken`.
2. `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` executes, consuming only the exact ETH needed and refunding the rest to `msg.sender`, which is `EvmHost`.
3. `EvmHost`'s ETH balance increases by the unspent amount; the original caller never receives it back, and no `EvmHost` function exists to withdraw or reallocate it to the rightful payer.
4. Repeating this across dispatches accumulates stranded ETH in `EvmHost` indefinitely.
