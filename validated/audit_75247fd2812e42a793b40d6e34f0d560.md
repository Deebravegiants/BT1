## Analog Found: Missing `from` validation on privileged `IntentGatewayV2.onAccept` governance branch

### Title
Unauthorized governance actions (dust sweep, params/instance hijack) via `IntentGatewayV2.onAccept` due to missing `from` (module id) check on Hyperbridge-sourced messages - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.onAccept` gates its `RedeemEscrow`/`RefundEscrow` branch with a peer-authentication call (`authenticate(incoming.request)`), but the governance branch (`NewDeployment`, `UpdateParams`, `SweepDust`) is gated only by checking that `incoming.request.source` equals the Hyperbridge coprocessor chain id — it never checks `incoming.request.from`, i.e. which module/pallet on that chain actually dispatched the message.

### Finding Description
In `onAccept`: [1](#0-0) 

the `RedeemEscrow`/`RefundEscrow` path calls `authenticate(incoming.request)` before touching escrowed funds, but the privileged branch that follows only checks: [2](#0-1) 

`incoming.request.source` is the *state machine identifier* of the sending chain (i.e., "this message came from the Hyperbridge chain"), not an identifier of the specific pallet/module that dispatched it. There is no comparable `authenticate`/module-id check for the governance kinds. As a result, any ISMP module on the Hyperbridge chain capable of dispatching a `PostRequest` addressed to this `IntentGatewayV2` instance can trigger:

- `NewDeployment` — silently overwrite `_instances[stateMachineId]`, hijacking which contract this gateway trusts as its peer on a given chain: [3](#0-2) 
- `UpdateParams` — rewrite `_params` (including `surplusShareBps`, `protocolFeeBps`, `priceOracle`) and per-destination fee overrides: [4](#0-3) 
- `SweepDust` — transfer arbitrary amounts of any ERC-20 or native balance held by the contract to an attacker-chosen `beneficiary`: [5](#0-4) 

This mirrors the Ghost CVE's root cause pattern: a privileged code path trusts an insufficiently-scoped identifier (there: file path/type; here: source chain rather than source module), letting attacker-influenced data reach a sensitive sink (arbitrary fund transfer / trust-anchor rewrite) without the same authentication rigor applied to the sibling code path in the same function.

### Impact Explanation
If exploitable (see Likelihood caveat), `SweepDust` allows direct, permanent theft of all tokens/ETH held by the `IntentGatewayV2` contract (escrowed user funds, accumulated fees) to an attacker-controlled address — concrete theft of funds. `NewDeployment` allows an attacker to register a malicious contract as the trusted peer gateway for a state machine, which would let subsequent `RedeemEscrow`/`RefundEscrow` proofs constructed against that "instance" be treated as authentic, enabling forged settlement/escrow release. `UpdateParams` can be abused to zero out protocol fees or redirect the price oracle, degrading protocol economics.

### Likelihood Explanation
This finding's exploitability is contingent on something I could not fully verify with the tools available: whether the pallet-ismp dispatch path on the Hyperbridge/nexus chain restricts the `from` field of a dispatched request to the dispatching pallet's own fixed module id (which would mean only the specific intended governance pallet, e.g. `intents-coprocessor`, can produce a message with `source == hyperbridge`), or whether some other permissionless/less-privileged pallet on that chain can also dispatch arbitrary Post requests to `IntentGatewayV2` with `source == hyperbridge`. I found the `intents-coprocessor` pallet types referencing `NewDeployment`/`UpdateParams`/`SweepDust` [6](#0-5) , suggesting this is meant to be governance-issued from a single dedicated pallet, but I was not able to confirm in the remaining iterations whether `onAccept`'s omission of a `from`-equality check against that specific module id is intentional (relying on chain-level trust because only one Hyperbridge-side pallet ever dispatches to this address) or a genuine gap that any Hyperbridge-side dispatcher could exploit. This is the key uncertainty and should be verified directly against `modules/pallets/intents-coprocessor/src/lib.rs` and the pallet-ismp dispatch implementation before treating this as confirmed-exploitable.

### Recommendation
Add an explicit `from` (module id) check in the governance branch of `onAccept`, comparable to the `authenticate()` call used for `RedeemEscrow`/`RefundEscrow`, so that `NewDeployment`, `UpdateParams`, and `SweepDust` are only accepted when `incoming.request.from` matches the specific, hardcoded governance module id on Hyperbridge — not merely when `incoming.request.source` is the Hyperbridge chain.

### Proof of Concept
Conceptual (pending confirmation of dispatch-side `from` control):
1. Attacker controls or compromises any pallet on the Hyperbridge/nexus chain capable of invoking `IsmpDispatcher::dispatch_request` with `dest` set to the EVM chain hosting `IntentGatewayV2` and `to` set to the gateway's address.
2. Attacker crafts a body: `bytes1(RequestKind.SweepDust) || abi.encode(SweepDust{ outputs: [...all held tokens...], beneficiary: attacker })`.
3. Message is relayed and delivered via the standard ISMP handler; `IntentGatewayV2.onAccept` checks only `request.source == hyperbridge()`, which is true, and executes the sweep, transferring all matching token balances to the attacker. [5](#0-4)
