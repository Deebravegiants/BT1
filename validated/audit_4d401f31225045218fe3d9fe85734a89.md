### Title
Unbounded in-memory bid cache growth in the intents mempool watcher enables memory-exhaustion denial of service - (File: modules/pallets/intents-coprocessor/rpc/src/lib.rs)

### Summary
`BidCache`, the in-memory structure that backs the `intents_getBidsForOrder` RPC and `intents_subscribeBids` subscription, stores every observed `place_bid` extrinsic keyed by order commitment with no bound on the number of distinct commitments tracked nor on the number of bid entries per commitment. Any unprivileged bandwidth purchaser / intent filler can submit signed `place_bid` transactions into the transaction pool of any Hyperbridge node running the intents RPC service to grow this map without limit, exactly mirroring the CVE-2016-6580 `priority` library flaw where a peer could assign priority state for every possible stream ID and force unbounded memory allocation.

### Finding Description
`run_bid_watcher` subscribes to the transaction pool's `import_notification_stream` and, for every ready transaction that decodes to a `pallet_intents_coprocessor::Call::place_bid`, calls `bid_cache.insert(commitment, filler, user_op)`: [1](#0-0) 

`BidCache::insert` unconditionally creates a new `OrderBids` entry for any never-before-seen commitment, and pushes a new `BidEntry` for any never-before-seen filler under that commitment: [2](#0-1) 

The underlying store is an unbounded `HashMap<H256, OrderBids>` where `OrderBids.entries` is an unbounded `Vec<BidEntry>`: [3](#0-2) 

The only cleanup mechanism is a periodic timer that evicts entries whose `first_seen` exceeds a TTL: [4](#0-3) 

This eviction runs only once per `cleanup_interval` tick in the same `tokio::select!` loop as insertion, so a burst of transactions arriving faster than the cleanup cadence — or transactions that use distinct, attacker-chosen `commitment` values that never correspond to real on-chain orders and are never included in a block — accumulate in memory for a full TTL window regardless of validity. Unlike the on-chain query path in `get_bids_for_order`, which explicitly caps the number of on-chain bids read via `MAX_ON_CHAIN_BIDS = 30`, the mempool-derived side of the cache has no analogous cap on either the number of distinct commitments or bids per commitment: [5](#0-4) 

`extract_bid` only requires the extrinsic to decode as a signed `place_bid` call; it does not verify the `commitment` corresponds to a real, extant order before it is cached, so an attacker can mint arbitrary distinct `H256` commitments and arbitrary filler byte-strings to maximize the number of `HashMap`/`Vec` entries created: [6](#0-5) 

### Impact Explanation
Every full node running this RPC service watches its own transaction pool and independently builds this unbounded cache, so a single attacker can target the memory of any/all Hyperbridge nodes serving `intents_getBidsForOrder`/`intents_subscribeBids` by flooding the pool with cheap, distinct `place_bid` transactions (or transactions that are valid enough to enter the ready pool but never get included). Sustained growth of the `HashMap`/nested `Vec` can exhaust node memory, degrading or crashing the RPC/intents infrastructure that intent solvers and bandwidth purchasers rely on to discover bids, which can make the intents route for order fulfillment unavailable — directly analogous to the reachable-impact category of "a route unable to deliver messages" for the intents domain.

### Likelihood Explanation
The `place_bid` call is a normal signed extrinsic, so an attacker only pays ordinary transaction fees to get an entry into the ready pool; fees do not bound the number of distinct commitment keys or filler entries that can be minted, since `commitment` and `filler` values are attacker-controlled and are cached before any state validity check (no relation to a real order is enforced by `extract_bid`/`BidCache::insert`). Because caching happens on ready-pool observation rather than on inclusion/finalization, the attack does not require blocks to actually execute the calls, making it cheap and fast to mount from an unprivileged account.

### Recommendation
Bound `BidCache` the same way the on-chain path already is: cap the total number of distinct commitments tracked, cap the number of bid entries per commitment (mirroring `MAX_ON_CHAIN_BIDS`), and evict/reject new insertions once bounds are hit (e.g., LRU eviction of oldest commitments/bids) instead of only relying on time-based TTL cleanup. Additionally, validate that a `commitment` corresponds to a real on-chain order (or at least rate-limit per source account) before caching a bid from the mempool.

### Proof of Concept
1. Run a Hyperbridge node with the intents RPC/bid-watcher enabled.
2. From an unprivileged account, repeatedly submit signed `place_bid(commitment, user_op)` extrinsics using freshly randomized `commitment: H256` values and distinct `filler`/`user_op` payloads, faster than `cleanup_interval`.
3. Observe `run_bid_watcher` calling `BidCache::insert` for every distinct commitment/filler pair, growing the process-wide `HashMap<H256, OrderBids>` and its per-commitment `Vec<BidEntry>` without bound until node memory is exhausted, as shown by the unconditional insertion logic in `BidCache::insert` (lines 111-129) with no cap analogous to the `MAX_ON_CHAIN_BIDS` guard used elsewhere in the same file (lines 233-257).

	pub fn insert(
		&self,
		commitment: H256,
		filler: Vec<u8>,
		user_op: Vec<u8>,
	) -> Result<(), String> {
		let entry = BidEntry { filler: filler.clone(), user_op };

		let mut bids = self.bids.write().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		let order = bids
			.entry(commitment)
			.or_insert_with(|| OrderBids { first_seen: Instant::now(), entries: Vec::new() });
		if let Some(existing) = order.entries.iter_mut().find(|e| e.filler == filler) {
			*existing = entry;
		} else {
			order.entries.push(entry);
		}
		Ok(())
	}

pub fn extract_bid<T, Extra>(encoded: &[u8]) -> Option<(H256, Vec<u8>, Vec<u8>)>
where
	T: pallet_intents_coprocessor::Config,
	T::RuntimeCall: frame_support::traits::IsSubType<pallet_intents_coprocessor::Call<T>>
		+ DecodeWithMemTracking,
	T::AccountId: Encode + From<[u8; 32]> + DecodeWithMemTracking,
	Extra: DecodeWithMemTracking,
{
	let xt = sp_runtime::generic::UncheckedExtrinsic::<
		sp_runtime::MultiAddress<T::AccountId, ()>,
		T::RuntimeCall,
		sp_runtime::MultiSignature,
		Extra,
	>::decode(&mut &encoded[..])
	.ok()?;

	let filler = match &xt.preamble {
		sp_runtime::generic::Preamble::Signed(address, _, _) => match address {
			sp_runtime::MultiAddress::Id(id) => id.encode(),
			_ => return None,
		},
		_ => return None,
	};

	match xt.function.is_sub_type()? {
		pallet_intents_coprocessor::Call::place_bid { commitment, user_op } =>
			Some((commitment.clone(), filler, user_op.to_vec())),
		_ => None,
	}
}
