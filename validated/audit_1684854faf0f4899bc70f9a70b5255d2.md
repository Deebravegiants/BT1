### Title
Webhook `shop-domain` header is trusted by `Registry.process` without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `HmacValidator.validate` checks the `hmac-sha256` header against `to_signable_string` (the body) only, then `Registry.process` unconditionally trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler. This is structurally identical to the reported bug class: a value that drives downstream accounting/identity decisions (`shop`) is not bound by the same integrity check (`hmac`) that is presented as proof of authenticity for the whole message — exactly the "field acted on but not covered by the HMAC" pattern called out in scope.

### Finding Description
- `Request#to_signable_string` is defined as just `@raw_body` [1](#0-0) .
- `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the body or to each other [2](#0-1) .
- `HmacValidator.validate` computes/compares the signature purely over `verifiable_query.to_signable_string` (i.e., the body) [3](#0-2) .
- `Registry.process` gates on `HmacValidator.validate(request)` and then immediately trusts `request.shop` to construct `WebhookMetadata`, which is handed to the app's handler as the tenant identity for the event [4](#0-3) .

**Broken equality:** the gem implicitly asserts `hmac_valid(body) == shop_is_authentic`, but the real invariant should be `hmac_valid(body ∥ shop ∥ topic ∥ webhook_id) == event_is_authentic_for_that_shop`. Because `shop` (and `topic`/`webhook_id`) sit outside the signed payload, any request with a body/HMAC pair that is valid for *some* shop can have its `shop-domain` header (and `topic`/`webhook_id`) freely rewritten to a different shop, and `Registry.process` will accept it and forward it as if it originated from the victim shop.

### Impact Explanation
A merchant who has legitimately installed the app on their own store receives real, correctly-HMAC'd webhooks for their shop. Because the HMAC only covers the raw body, that attacker can capture such a webhook and replay it against the app's webhook endpoint with the `shopify-shop-domain` (and optionally `shopify-topic`/`shopify-webhook-id`) header rewritten to a different, victim tenant that also uses the app. `HmacValidator.validate` still passes (it only checks the untouched body), and `Registry.process` builds `WebhookMetadata` with the attacker-chosen `shop`, causing the host app to process/store data under the wrong tenant. Any app logic that uses the webhook's `shop` field to select which shop record/session/access-token to update, or to trigger further Admin API calls using that shop's stored token, is exposed to cross-tenant data corruption or being made to act with a different tenant's credentials — meeting the "cross-tenant access" bar for Critical severity.

### Likelihood Explanation
No secret material is required beyond having legitimate access to the app as an ordinary (even low-trust) merchant tenant — the exact "unprivileged internet user" scenario in scope, since any merchant who installs the app can generate arbitrarily many genuinely-signed webhooks for their own shop and freely relabel the `shop-domain`/`topic` headers before forwarding them. The only prerequisite is that the host application trusts `WebhookMetadata#shop`/`#topic` (a documented, standard usage pattern of this gem, not host misconfiguration) to select the tenant context.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the value covered by `to_signable_string` (or otherwise cryptographically bind them to the verified body, e.g., by deriving them only from a signed envelope, or additionally comparing them against Shopify's canonical value obtained via an authenticated channel) so that `HmacValidator.validate` fails whenever any of these header-derived identity fields have been altered relative to what was actually signed by Shopify.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a real webhook, e.g. `orders/create`, with headers:
   - `x-shopify-topic: orders/create`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC of raw_body>`
   - body: `{"id": 1, ...}`
2. Attacker resends the identical raw body and HMAC header to the app's webhook endpoint, but changes only `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present) [5](#0-4) .
4. `Registry.process` calls `HmacValidator.validate(request)`, which succeeds because it only checks the (unmodified) body [6](#0-5) .
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)` [7](#0-6) , causing the host app to process attacker-controlled data as if it belongs to the victim tenant.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
