## Title
Webhook HMAC validation covers only the raw body, not the `shop-domain` header — allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity solely by HMAC-validating the raw request body. The `shop` identity that is subsequently handed to the app's webhook handler is read from the `X-Shopify-Shop-Domain` HTTP header, which is **not** included in the signed payload. Since the app-wide `api_secret_key` used to compute/verify the HMAC is shared across every merchant install of the app (not per-shop), any attacker who can obtain one valid `(raw_body, hmac)` pair (e.g., by installing the app on their own store and receiving a real webhook) can replay that exact body/HMAC to the app's public webhook endpoint while swapping the `shop-domain` header to a victim shop. The signature still validates, and the app processes the event attributing it to the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is derived from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes the expected signature purely from `to_signable_string` (i.e., the body), never touching the shop header: [3](#0-2) 

`Registry.process` validates the HMAC and then trusts `request.shop` (the header value) to build the `WebhookMetadata` passed to the app's handler, with no cross-check that the shop matches whatever the signed body actually pertains to: [4](#0-3) 

Because `Context.api_secret_key` is one shared secret for the entire app across all installed shops (see `HmacValidator.validate`, which signs/verifies with the single app secret, optionally falling back to `old_api_secret_key`): [5](#0-4) 

...any merchant who has the app installed on their own store can generate a legitimately-HMAC-signed webhook body (by triggering a real event, e.g. placing an order to receive an `orders/create` webhook). That `(raw_body, hmac)` pair remains valid regardless of which shop header accompanies it, because the header is never part of the signed content. The attacker can then POST that same body+HMAC directly to the app's public webhook receiver URL with the `X-Shopify-Shop-Domain` header rewritten to any other tenant shop domain that also has the app installed. `Registry.process` will accept it as authentic and dispatch it to the handler tagged with the victim's `shop`, breaking the equality: `shop_the_HMAC_was_actually_generated_for == shop_the_handler_believes_it_is_for`.

### Impact Explanation
This is a cross-tenant access vulnerability (Critical): an unprivileged attacker (any merchant who can install the app once) can inject forged, signature-valid webhook events attributed to a victim tenant's shop domain. Depending on how the host app's `WebhookHandler` implementations key off `shop` (e.g., account state changes, data deletion for `shop/redact`/`customers/redact`/`customers/data_request`, feature toggles, billing state, order/product synchronization), this can corrupt or exfiltrate data cross-tenant, or trigger privileged operations against a shop the attacker does not control.

### Likelihood Explanation
Likelihood is high for any app that: (a) uses this gem's webhook `Registry`/`Request` implementation as documented, and (b) allows the attacker to become one of the app's own installed tenants (which is typically self-service for any Shopify app). No knowledge of `api_secret_key` is required — only capture of one legitimate raw webhook body plus its HMAC header from the attacker's own installation, both of which are delivered directly to the attacker by Shopify.

### Recommendation
- Bind the `shop` (and ideally `topic`, `api_version`) into the value that is HMAC-verified, e.g., include the shop domain in `to_signable_string`, or independently verify that the shop asserted in the header matches an expected/authorized value (such as a shop recorded for that specific webhook subscription/session) before dispatching to handlers.
- At minimum, document/require host applications to cross-check `request.shop` against the shop context of the currently active session/webhook subscription rather than trusting the header value outright.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and enables an HTTP webhook (e.g. `orders/create`).
2. Attacker places a test order, causing Shopify to POST a legitimately HMAC-signed webhook to the app's webhook endpoint; attacker captures the raw body and the `X-Shopify-Hmac-Sha256` value from this delivery (they control the receiving endpoint or can intercept it via a proxy they run).
3. Attacker replays this exact `(raw_body, hmac)` to the same app's webhook endpoint, but sets the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com` (a different, real tenant of the same app).
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) succeeds because it only checks `raw_body` against the secret.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the handler with `shop: "victim-shop.myshopify.com"`, even though the signed content actually originated from the attacker's own shop — demonstrating the cross-tenant identity confusion.
