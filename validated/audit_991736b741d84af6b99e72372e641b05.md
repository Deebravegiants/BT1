### Title
Escrowed funds permanently frozen when the beneficiary (solver or original order maker) is blacklisted by the escrowed ERC20 - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw`, invoked by `ExtrinsicIntents.onAccept` (and mirrored by `withdraw` in `evm/tron/contracts/apps/IntentGatewayV2.sol` / `sdk/packages/core/contracts/apps/IntentGatewayV2.sol`), unconditionally pushes escrowed ERC20 tokens to a `beneficiary` address that is fixed at order-creation/fill time and can never be changed. If that token has a blacklist (e.g. USDC) and the beneficiary is later blacklisted, the transfer reverts every time the withdrawal message is delivered, and there is no mechanism to redirect or otherwise release the escrow, permanently freezing the funds.

### Finding Description
`_withdraw` releases escrow to a `beneficiary` decoded straight from the cross-chain `WithdrawalRequest`: [1](#0-0) 

and forwards accumulated protocol fees to the same address: [2](#0-1) 

This is called from `ExtrinsicIntents.onAccept` for both `RedeemEscrow` (pays the solver who filled the order) and `RefundEscrow` (refunds the original order maker): [3](#0-2) 

Crucially, when `onAccept` reverts, `EvmHost.dispatchIncoming` does **not** revert the whole delivery — it just deletes the request receipt "so it can be retried": [4](#0-3) 

This retry mechanism assumes transient failures. But a blacklist condition on the beneficiary is not transient: `IERC20(token).safeTransfer(beneficiary, amount)` (or `IERC20(feeToken()).safeTransfer(beneficiary, fees)`) will revert identically on every retry, forever. Since `beneficiary` is embedded in the order/withdrawal body dispatched from the source chain and there is no admin/governance path in `IntentsBase`/`ExtrinsicIntents` to change it or sweep a specific commitment's escrow to a different address (only `SweepDust`, a governance-only global dust sweep unrelated to a specific order's escrow), the escrowed input tokens (for a refund) or output redemption (for a solver) become permanently unretrievable.

The identical pattern exists in the non-refactored gateway variants, which perform the same direct low-level `transfer` to `beneficiary` without any fallback: [5](#0-4) 

### Impact Explanation
This results in permanent freezing of user/solver funds: any order maker who is later blacklisted by the input token's issuer (before their `RefundEscrow`/`RedeemEscrow` delivers) can never recover their escrowed tokens, and any solver who fills an order and is later blacklisted before the `RedeemEscrow` message is delivered can never claim their earned input tokens or protocol fee payout. Because delivery is asynchronous and can be delayed indefinitely (relayer failure, congestion, or intentional griefing by re-submitting the failing message), the window in which a blacklisting event can occur before finalization is unbounded, and once it occurs, there is no recovery path. This satisfies the "permanent freezing of funds" impact bar for the intents escrow path.

### Likelihood Explanation
Any solver or order maker interacting with a blacklistable ERC20 (USDC, USDT, and other common stablecoins used as intent input/output assets) is exposed. No privileged or malicious actor is required — a legitimate real-world blacklisting event (e.g., regulatory/compliance action against the beneficiary address) triggers the freeze automatically, and the ISMP delivery/retry design guarantees the failure is permanent rather than one-off.

### Recommendation
Add a pull-based/claim fallback for `_withdraw` (and its counterpart in `IntentGatewayV2.sol`): on transfer failure, credit the beneficiary's owed amount to an internal claimable balance (keyed by beneficiary+token) instead of reverting the whole `onAccept`, and expose a separate `claim`/`withdrawTo` function that lets the beneficiary (or an owner-designated alternate recipient) pull the funds to a different, non-blacklisted address. Alternatively, allow the beneficiary to pre-register/rotate an alternate payout address before finalization, analogous to a position-ownership-transfer mechanism.

### Proof of Concept
1. A solver fills a cross-chain order for output token USDC, becoming the `beneficiary` recorded for a `RedeemEscrow` withdrawal request (see `_fillCrossChain` in `ExtrinsicIntents.sol`).
2. Before the `RedeemEscrow` message is relayed and delivered on the source chain, Circle blacklists the solver's address in USDC.
3. A relayer delivers the `RedeemEscrow` POST request; `HandlerV2.handlePostRequests` → `EvmHost.dispatchIncoming` → `ExtrinsicIntents.onAccept` → `IntentsBase._withdraw` executes `IERC20(USDC).safeTransfer(beneficiary, amount)`, which reverts due to the blacklist.
4. `EvmHost.dispatchIncoming` catches the failure, deletes the receipt, and returns normally — the message is now "pending retry" forever.
5. Every subsequent relay attempt of the same message hits the same blacklist revert; the escrowed USDC amount recorded in `_orders[commitment][token]` remains locked in the `IntentsBase` contract with no function available to redirect it to another address, permanently freezing the solver's funds.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
