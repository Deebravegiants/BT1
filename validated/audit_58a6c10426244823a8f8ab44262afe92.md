## Finding

### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values are taken verbatim from unauthenticated HTTP headers. `Registry.process` validates only the body HMAC and then dispatches to the app's handler using these unauthenticated header values, so the "shop that produced a validly-signed payload" is never bound to the "shop attributed to the event."

### Finding Description
`Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

All other identifying fields are parsed straight from headers with no cross-check against the signed content: [2](#0-1) 

`Registry.process` validates the HMAC (which, per above, only proves the body was signed with the app's shared `api_secret_key`) and then immediately trusts `request.shop` and `request.topic` to route and construct the handler payload, without ever validating the shop domain against `ShopifyAPI::Utils::ShopValidator` or any registered/expected shop list: [3](#0-2) 

Because Shopify signs webhooks with the app's single `api_secret_key` (shared across every shop that installed the app, not a per-shop secret), a party who can obtain one validly-signed `(raw_body, hmac)` pair — e.g. by installing the app on their own shop and receiving a legitimate webhook — can resend that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and `x-shopify-topic`) header. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) will still return `true` because it only recomputes the HMAC over `raw_body`: [4](#0-3) 

This breaks the identity binding: **shop attested by the HMAC (none — the signature covers only the body bytes) ≠ shop the handler is told to act on (`request.shop`, taken from an unauthenticated header)**. The gem exposes `WebhookMetadata` with this unverified `shop` field as the authoritative tenant identifier for the handler, so any host app that follows the documented pattern of using `data.shop` to select a tenant/session is misled into acting on another merchant's behalf.

### Impact Explanation
An attacker who controls one legitimate shop installation (a low-privilege, unprivileged-relative-to-other-tenants actor) can forge webhook events that the gem will report as originating from a different, victim shop, since shop identity is never bound to the signature nor validated against a trusted domain list before being handed to the handler. This is a cross-tenant identity confusion in the gem's own webhook-processing path (`Registry.process`), not merely a host-application oversight, because the gem itself never verifies the field it hands off as the trusted tenant identifier.

### Likelihood Explanation
Any app that registers HTTP webhooks and exposes the corresponding endpoint publicly (as required for Shopify to deliver webhooks) is reachable by any internet host that can reach that URL. Obtaining one valid `(body, hmac)` pair only requires installing the app on an attacker-owned development shop, which is trivial for public/self-serve apps.

### Recommendation
Bind the shop (and topic) into the verified signable content, or independently validate `request.shop` against `ShopifyAPI::Utils::ShopValidator.sanitize!`/an expected-shop allowlist (and, ideally, verify the shop against session/tenant records) before dispatching to `WebhookHandler#handle` in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on shop `attacker.myshopify.com`, receiving a real webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the shared `api_secret_key`), `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker POSTs the same `B` and `H` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `HmacValidator.validate` recomputes HMAC over `B` only and returns `true` (per `lib/shopify_api/utils/hmac_validator.rb` lines 26-31 and `lib/shopify_api/webhooks/request.rb` lines 35-38).
4. `Registry.process` (lib/shopify_api/webhooks/registry.rb lines 188-200) invokes the handler with `shop: "victim.myshopify.com"`, even though that shop never sent this event.
