### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, and `webhook_id` are read straight from unauthenticated HTTP headers. `Registry.process` verifies the HMAC over the body only and then forwards the header-derived `shop` value, unauthenticated, to the app's webhook handler. Any user who legitimately receives a genuine, signed webhook for one shop can replay it against the app's endpoint with a forged `shopify-shop-domain` header, and the app will process it as if it came from an arbitrary other shop.

### Finding Description
The binding that should hold is: *the shop asserted in the request equals the shop the HMAC actually authenticates*. In this gem that equality is broken.

`Request#hmac` decodes the `hmac-sha256` header and `to_signable_string` returns `@raw_body` only: [1](#0-0) [2](#0-1) 

`shop` is a plain header read with no cryptographic tie to the body or signature: [3](#0-2) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` (i.e. the raw body) against the app's single, shop-independent `api_secret_key`, and then immediately forwards `request.shop` to the handler: [4](#0-3) [5](#0-4) 

Because Shopify's webhook HMAC is computed with the single app-level `Context.api_secret_key` over the raw body only (not per-shop, not including the `shop-domain` header), the signature over a given body is identical no matter which installed shop it was originally sent for. Any principal who operates a store that has the app installed will receive genuinely-signed webhooks from Shopify for their own store's events. Because the signature never binds to `shop`, that same signed body/HMAC pair remains valid when replayed to the app's webhook endpoint with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header rewritten to name a different, victim shop.

Before the attack: `shop` (as attributed to the handler) == shop that actually produced/owns the signed payload.
After the attack: `shop` (attacker-controlled header) != the shop whose secret/signature actually authenticated the payload — yet `HmacValidator.validate` still returns `true`, and `Registry.process` still dispatches the (forged-attribution) event to the handler as if it were legitimately from the victim shop.

### Impact Explanation
This crosses a tenant boundary: an attacker who is merely one of the app's installers (an unprivileged multi-tenant user, not a privileged operator) can cause the app's webhook handler to process fabricated data under the identity of an arbitrary other shop, without needing to know `api_secret_key` or steal any access token. Depending on what the handler does with `WebhookMetadata#shop` (e.g., trigger uninstall cleanup, mutate billing/subscription state, invalidate sessions, or otherwise act on data keyed by shop), this enables cross-tenant data corruption/impersonation — matching the "Critical: cross-tenant access" impact bucket.

### Likelihood Explanation
High for any app that has more than one installer. The only precondition is that the attacker's own shop has the app installed and receives at least one real webhook (which happens automatically once installed and available topics fire, e.g. `app/uninstalled`). No secret material, no social engineering, and no privileged account are required — only replaying an HTTP request with a modified header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise authenticate the shop out-of-band (e.g., by only accepting `shop` values previously registered/known-installed for this app, or by requiring the raw signed payload from Shopify to include shop identity that is checked). At minimum, document prominently that `Webhooks::Request#shop` is not authenticated by the HMAC check and must not be trusted for authorization decisions without an independent shop allow-list check by the consuming application.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and on `victim-shop.myshopify.com`.
2. Shopify sends the attacker a legitimately signed webhook for their own shop, e.g. body `{"id":1}` with headers:
   - `x-shopify-hmac-sha256: <valid HMAC over the body using the app's api_secret_key>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-topic: app/uninstalled`
3. Attacker resends the exact same body and HMAC header to the app's webhook endpoint, only replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` which recomputes the HMAC over `@raw_body` only and matches — validation passes, per: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, per: [7](#0-6) 
   causing the app to act on victim-shop's behalf using attacker-controlled webhook data.
