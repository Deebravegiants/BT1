### Title
Stale inbound payloads remain permissionlessly replayable after `setEidMapping` revokes a source chain - (File: `sdk/packages/lz-endpoint/contracts/HyperbridgeLzEndpoint.sol`)

### Summary
`HyperbridgeLzEndpoint` validates that an inbound ISMP request originates from a currently-trusted source chain only inside `onAccept`, at the moment the message is first delivered. If the destination OApp's `lzReceive` reverts, the payload is cached in `_inboundPayloadHashes` for later recovery. The permissionless recovery function `retryPayload` never re-checks that the originating chain (`origin.srcEid` / the state machine it was mapped from) is still a trusted/configured source at the time of retry — it only checks that the supplied `(guid, message)` matches the previously stored hash. This is the same bug class as the Venus `BaseXVSProxyOFT` finding: trust validation happens on first receipt but not on retry, so revoking a compromised or unwanted remote does not stop previously failed messages from that remote being executed later.

### Finding Description
In `onAccept` (lines 355–396), the contract checks the source state machine against `_stateMachineToEid` (the owner-configured trust mapping) before advancing the inbound nonce and attempting delivery: [1](#0-0) 

If the OApp's `lzReceive` reverts, the payload hash is stored keyed only by `(receiver, srcEid, sender, nonce)` — with no further linkage back to the live `_stateMachineToEid` trust mapping: [2](#0-1) 

The owner can revoke or repoint a source chain at any time via `setEidMapping`, which deletes the reverse mapping for the previous state machine: [3](#0-2) 

However, `retryPayload` is fully permissionless and only validates the stored payload hash — it performs no check against `_stateMachineToEid`/`_eidToStateMachine` at all: [4](#0-3) 

This mirrors the reported Venus bug exactly: `_nonblockingLzReceive`/`onAccept` validates the trusted remote at delivery time, `retryMessage`/`retryPayload` retries a previously-failed message without re-validating that the remote is still trusted, and `removeTrustedRemote`/`setEidMapping` is the admin action that revokes trust but leaves already-stored failed messages fully replayable.

### Impact Explanation
If a source chain/adapter is later discovered to be compromised (e.g., its ISMP consensus client is frozen, or the deployed `HyperbridgeLzEndpoint` instance on that chain is compromised) and the owner calls `setEidMapping` to disable it, any message from that chain that failed in `onAccept` (deliberately or otherwise, e.g. a message crafted to revert once so it lands in the recovery cache and is retried after revocation) can still be delivered to the OApp via `retryPayload` after revocation. Since `retryPayload` calls `ILayerZeroReceiver(receiver).lzReceive(...)` directly on the destination OApp exactly as `onAccept` would have, this results in unauthorized/forged execution of application logic (e.g., minting, state updates) attributable to a source the operator has explicitly disowned — a forged message delivery / unauthorized app action, which can lead to theft or unbacked minting depending on the receiving OApp's logic.

### Likelihood Explanation
Medium-to-High. `retryPayload` is deliberately permissionless ("anyone may push a stuck payload through"), so no special privilege is required to trigger the replay — only that a payload from the now-untrusted source previously failed and was cached. This is a realistic operational sequence: an operator discovering a compromised remote chain's adapter would naturally call `setEidMapping` to stop new traffic, but the code gives no guarantee that already-cached failed deliveries from that remote are also invalidated.

### Recommendation
`retryPayload` (and `clear`/`skip`/`nilify`/`burn` where relevant) should re-validate that `origin.srcEid` still corresponds to a currently trusted/configured state machine (i.e., `_eidToStateMachine[origin.srcEid].length != 0` and/or `_stateMachineToEid[keccak256(_eidToStateMachine[origin.srcEid])] == origin.srcEid`) before replaying the cached payload. Alternatively, `setEidMapping` should purge or nilify all pending `_inboundPayloadHashes` entries associated with the revoked `srcEid` so stale, now-untrusted payloads cannot be resurrected.

### Proof of Concept
1. Chain A's `HyperbridgeLzEndpoint` is configured as a trusted source via `setEidMapping(eidA, stateMachineA)`.
2. An inbound message from Chain A is delivered through ISMP to `onAccept`; the destination OApp's `lzReceive` reverts (e.g., a message designed to fail temporarily), so `_inboundPayloadHashes[receiver][eidA][sender][nonce]` is populated.
3. The operator discovers Chain A's endpoint/consensus is compromised and calls `setEidMapping(eidA, "")`, clearing `_eidToStateMachine[eidA]` and the reverse `_stateMachineToEid` entry — new messages from `eidA` are now rejected by `onAccept`'s `UnknownSource` check.
4. Any user calls `retryPayload(receiver, origin, guid, message)` with the originally cached `(guid, message)`. `retryPayload` only checks the stored hash match and executes `ILayerZeroReceiver(receiver).lzReceive(...)` — succeeding despite Chain A no longer being a trusted source, delivering the "forged"/now-untrusted message to the OApp.

Note: this analysis is based on static review of `HyperbridgeLzEndpoint.sol` and its recovery API; I did not find a test in `HyperbridgeLzEndpointConfigTest.sol`/`HyperbridgeLzEndpointTest.sol` that exercises retry-after-revocation, so I cannot confirm whether this scenario is intentionally out of scope for the current design — but no code path re-validates trust on retry.

    /**
     * @notice Registers a bidirectional mapping between a LZ eid and an ISMP state machine ID.
     * @dev Pass empty `stateMachineId` to disable the EID. Re-mapping an EID clears the prior
     * state machine's reverse entry so revoked sources cannot keep impersonating the EID.
     * @param lzEid The LayerZero endpoint ID
     * @param stateMachineId The ISMP state machine identifier (e.g., StateMachine.evm(1))
     */
    function setEidMapping(uint32 lzEid, bytes calldata stateMachineId) external onlyOwner {
        if (lzEid == 0) revert InvalidEid();
        bytes memory previous = _eidToStateMachine[lzEid];
        if (previous.length != 0) {
            delete _stateMachineToEid[keccak256(previous)];
        }
        _eidToStateMachine[lzEid] = stateMachineId;
        if (stateMachineId.length != 0) {
            _stateMachineToEid[keccak256(stateMachineId)] = lzEid;
        }
    }

     * @notice Retries an inbound delivery whose OApp `lzReceive` previously reverted in {onAccept}.
     * @dev Mirrors {onAccept}'s direct call to the OApp (the adapter is the caller, so the OApp's
     * `onlyEndpoint` check still passes). Permissionless: anyone may push a stuck payload through
     * once it is executable again. On success the stored payload hash is cleared; if delivery
     * reverts again the whole call reverts and the payload remains recoverable.
     * @param receiver The destination OApp
     * @param origin The (srcEid, sender, nonce) of the stored payload
     * @param guid The original message guid
     * @param message The original message payload (must match the stored hash)
     */
    function retryPayload(
        address receiver,
        Origin calldata origin,
        bytes32 guid,
        bytes calldata message
    ) external payable {
        bytes32 stored = _inboundPayloadHashes[receiver][origin.srcEid][origin.sender][origin.nonce];
        if (stored == bytes32(0) || stored == NIL_PAYLOAD_HASH || stored != keccak256(abi.encode(guid, message))) {
            revert InvalidPayloadHash();
        }

        // Clear first; if the retry reverts, this deletion rolls back with the rest of the tx and
        // the payload remains recoverable.
        delete _inboundPayloadHashes[receiver][origin.srcEid][origin.sender][origin.nonce];

        ILayerZeroReceiver(receiver).lzReceive{value: msg.value}(origin, guid, message, msg.sender, "");
        emit InboundPayloadResolved(receiver, origin.srcEid, origin.sender, origin.nonce);
    }
