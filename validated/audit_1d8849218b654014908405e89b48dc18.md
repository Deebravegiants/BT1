### Title
Off-chain UTXO commitments lack a per-output nonce, letting a sender freeze a recipient's shielded funds via nullifier collision - (File: `circuits/OriginalCommitmentCalculator.circom`, `circuits/NullifierCalculator.circom`, `contracts/HinkalBase.sol`)

### Summary
The off-chain commitment formula `Poseidon(amount, erc20TokenAddress, publicKey, timeStamp)` [1](#0-0)  has no random/unique salt. `timeStamp` for off-chain outputs is the single circuit-wide public signal `outTimeStamp`, which is provided by the transacting party as `circomData.timeStamp` and is never checked against `block.timestamp` anywhere in `Hinkal.sol`/`HinkalBase.sol` for a normal `transact()` call. The nullifier is derived purely from the commitment value: `nullifier = Poseidon(commitment, Poseidon(nullifyingPrivateKey, commitment))` [2](#0-1) [3](#0-2) , with no binding to the leaf's Merkle index. Consequently two distinct output leaves sharing (`amount`, `erc20TokenAddress`, `publicKey`, `outTimeStamp`) produce an identical commitment and, once spent by the owning key, an identical nullifier - permanently blocking the spend of the second, otherwise-valid leaf.

### Finding Description
`MainEVMCircuit.circom` computes each output commitment as:
```
calcOutCommitment[i][j].amount <== outAmounts[i][j];
calcOutCommitment[i][j].erc20TokenAddress <== erc20TokenAddresses[i];
calcOutCommitment[i][j].publicKey <== outPublicKeys[i][j];
calcOutCommitment[i][j].timeStamp <== outTimeStamp;
calcOutCommitment[i][j].out === outCommitments[i][j];
``` [4](#0-3) 

`outTimeStamp` is a single value shared by every output in the call, and it is forwarded on-chain from `circomData.timeStamp` as a plain public-input element with no freshness/uniqueness check against `block.timestamp`: `input[index++] = circomData.timeStamp;` [5](#0-4) . A search for `block.timestamp` in `Hinkal.sol`/`HinkalBase.sol` shows it is only used by external-action modules (`ExternalActionSwap`, `EmporiumUpgradeable`) and by `DepositOnChainUtxosExternalAction` for on-chain UTXOs - not for the generic off-chain `transact()` path, confirming that a sender fully controls this value.

Since `amount`, `erc20TokenAddress`, `outPublicKeys[i][j]` (the recipient's stealth public key) and `outTimeStamp` are all attacker/sender-chosen, a sender can produce two separate output leaves with byte-for-byte identical `(amount, token, publicKey, timeStamp)` tuples, targeting the same victim recipient (e.g., paying the same stealth address twice, either in one `transact()` call with `outputCount ≥ 2` or across two separate calls using the same chosen `outTimeStamp`). Both leaves get distinct Merkle positions but the same commitment value, and `insertCommitments` inserts them as ordinary leaves with no uniqueness check [6](#0-5) .

When the victim later spends the first of these leaves, `NullifierCalculator` produces `nullifier = Poseidon(commitment, Poseidon(nullifyingPrivateKey, commitment))`, which depends only on `commitment` and the recipient's own `nullifyingPrivateKey` - not on Merkle index/siblings. Because the second leaf has the identical commitment, spending it computes the identical nullifier. `insertNullifiers` then reverts on the second spend because the nullifier is already recorded in the global mapping:
```
require(!nullifiers[inputNullifiers[i][j]], "Nullifier cannot be reused");
``` [7](#0-6) 

This mirrors the External Report's root cause exactly: identical inputs collapse to an identical hash (there `txHash`, here `nullifier`), and once one instance is "consumed," any later legitimate instance with the same hash is permanently blocked - except here the analog breaks a security-relevant equality (one nullifier per spendable value unit) rather than a scheduling convenience, so the second UTXO's value becomes permanently unspendable while the sender's balance-conservation equation in `transact()` still balanced correctly at mint time.

### Impact Explanation
This is a permanent freezing of a *victim's* (the recipient's) shielded funds, not the attacker's own balance: the attacker (payer) can force this collision at zero cost to themselves by choosing the `outTimeStamp`/`amount` values of their own outgoing payment, while the loss lands on the recipient, who cannot ever redeem the second, colliding UTXO because its nullifier is already marked "used" by the first spend. Per the scan rubric this falls under "a nullifier reusable or a value-bearing leaf left unspendable," rated Critical (permanent freezing of user funds).

### Likelihood Explanation
Likelihood is moderate-to-high for adversarial or even accidental occurrence: any unprivileged EOA calling `transact()` fully controls `outAmounts`, `outPublicKeys`, and the shared `outTimeStamp` signal for all outputs in a call (and across separate calls, since there is no on-chain enforcement tying `outTimeStamp` to `block.timestamp`). No relayer, admin, or oracle assumption is required - a single crafted `transact()` call with two outputs to the same recipient stealth address, same token, same amount, and the default (frequently repeated, e.g. `0`) timestamp value is sufficient to plant the collision.

### Recommendation
Bind each output commitment to a value that is guaranteed unique per leaf - e.g., include the resulting leaf index / insertion counter, or a fresh random blinding factor supplied per output, in the `OriginalCommitmentCalculator` hash, and likewise fold the leaf's Merkle path/index into the nullifier derivation in `NullifierCalculator`/`Signature`, so identical `(amount, token, publicKey, timeStamp)` tuples cannot collapse to the same nullifier.

### Proof of Concept
1. Attacker A calls `transact()` with `tokenCount=1`, `outputCount=2`, `erc20TokenAddresses=[TOKEN]`, both `outAmounts[0][0] == outAmounts[0][1] == X`, both `outPublicKeys[0][0] == outPublicKeys[0][1] == victimStealthPubKey`, and a single shared `outTimeStamp = T` (fully attacker-chosen, no `block.timestamp` binding for normal `transact()`), producing two out commitments `c0 == c1` [4](#0-3) .
2. `Hinkal.transact()` verifies the proof and calls `insertCommitments`, which inserts both identical leaves at two distinct tree indices with no duplicate check [6](#0-5) .
3. Victim later spends leaf #0 using their `nullifyingPrivateKey`: circuit computes `nullifier N = Poseidon(c0, Poseidon(nullifyingPrivateKey, c0))` [2](#0-1) [3](#0-2) ; `insertNullifiers` marks `nullifiers[N] = true`.
4. Victim attempts to spend leaf #1 (a distinct, still-unspent value-bearing leaf with a valid Merkle proof to the current root). Because `c1 == c0`, the circuit computes the same nullifier `N`. `Hinkal.transact()`'s `insertNullifiers` call reverts with `"Nullifier cannot be reused"` [8](#0-7) , permanently freezing the victim's second `X`-sized UTXO.

    function insertCommitments(
        uint256[][] memory offChainCommitments,
        bytes[][] memory offChainEncryptedOutputs,
        OnChainCommitment[] memory onChainCommitments,
        bool[] memory onChainCreation
    ) internal {
        // 1) Total Length of Commitments
        uint256 length = 0;
        for (uint256 i = 0; i < offChainCommitments.length; i++) {
            for (uint256 j = 0; j < offChainCommitments[i].length; j++) {
                if (onChainCreation[i]) break;
                length += offChainCommitments[i][j] != 0 ? 1 : 0;
            }
        }
        length += onChainCommitments.length;

        if (length > 0) {
            // 2) Flattening leaves array
            uint256[] memory leaves = new uint256[](length);
            uint256 index = 0;
            for (uint256 i = 0; i < offChainCommitments.length; i++) {
                for (uint256 j = 0; j < offChainCommitments[i].length; j++) {
                    if (onChainCreation[i] == true) break;
                    if (offChainCommitments[i][j] != 0) {
                        leaves[index++] = offChainCommitments[i][j];
                    }
                }
            }
            for (uint256 i = 0; i < onChainCommitments.length; i++) {
                leaves[index++] = onChainCommitments[i].commitment;
            }

            // 3) Inserting Leaves
            uint256[] memory insertedIndexes = insertMany(leaves);

            // 4) Emitting Commitments/EncryptedOutputs
            index = 0;
            for (uint256 i = 0; i < offChainEncryptedOutputs.length; i++) {
                for (uint256 j = 0; j < offChainEncryptedOutputs[i].length; j++) {
                    if (onChainCreation[i] == true) break;
                    if (offChainCommitments[i][j] != 0) {
                        emit NewCommitment(
                            leaves[index],
                            int256(insertedIndexes[index]),
                            offChainEncryptedOutputs[i][j]
                        );
                        index++;
                    }
                }
            }
            for (uint256 i = 0; i < onChainCommitments.length; i++) {
                emit NewCommitment(
                    leaves[index],
                    -1 * int256(insertedIndexes[index++]),
                    abi.encode(
                        onChainCommitments[i].utxo,
                        onChainCommitments[i].onChainEncryptedOutput
                    )
                );
            }
        }

**File:** contracts/HinkalBase.sol (L135-152)

    function insertNullifiers(
        uint256[][] calldata inputNullifiers,
        bool[] calldata onChainCreation
    ) internal {
        for (uint256 i = 0; i < inputNullifiers.length; i++) {
            for (uint256 j = 0; j < inputNullifiers[i].length; j++) {
                if (onChainCreation[i] == true) break;
                if (inputNullifiers[i][j] != 0) {
                    require(
                        !nullifiers[inputNullifiers[i][j]],
                        "Nullifier cannot be reused"
                    );
                    nullifiers[inputNullifiers[i][j]] = true;
                    emit Nullified(inputNullifiers[i][j]);
                }
            }
        }
    }
