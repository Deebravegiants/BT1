### Title
POA Bridge withdrawal status matched only by `assetId`, causing hash/status misreport for batched same-asset withdrawals - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
Both `PoaBridge.describeWithdrawal()` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and the standalone `waitForWithdrawalCompletion()` in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` locate the withdrawal record to report on using `Array.prototype.find()` keyed **only** on `assetId` (via `near_token_id`). When a single NEAR intent transaction contains more than one withdrawal of the same token (a scenario the SDK explicitly supports through batch/multi-withdrawal APIs), `find()` always returns the first matching entry in the POA API's response array — regardless of which of the several same-asset withdrawals within that transaction the caller is actually asking about.

### Finding Description
`findMatchingWithdrawal` is documented as intentionally simplistic: [1](#0-0) 

It is invoked from `describeWithdrawal`, which reports `completed`/`pending`/`failed` plus a `transfer_tx_hash` based solely on this asset-keyed lookup, with no use of `index`, `amount`, or `destinationAddress` to disambiguate between multiple withdrawals of the same asset: [2](#0-1) 

The identical pattern exists in the standalone helper: [3](#0-2) 

`describeWithdrawal` is called once per withdrawal index by the SDK's batch-withdrawal orchestration (`createWithdrawalCompletionPromises` / `waitForWithdrawalCompletion` in `sdk.ts`), which explicitly maintains per-index polling for each withdrawal in a batch: [4](#0-3) [5](#0-4) 

Because `findMatchingWithdrawal` ignores `index`/`amount`/`destinationAddress`, if withdrawal #0 and withdrawal #2 in the same intent both send the same token (e.g., two USDT payouts to different recipients in a batch payroll/settlement), both `describeWithdrawal({index:0,...})` and `describeWithdrawal({index:2,...})` calls resolve to the **same** matched record — typically the first one in the array — and thus report the **same** `transfer_tx_hash`/status for both, even though they are genuinely different on-chain transfers to different destinations.

This breaks the equality that "the status/hash reported for withdrawal N corresponds to the on-chain outcome of withdrawal N." Instead, the reported hash is that of some other of the batch's same-asset withdrawals.

### Impact Explanation
This falls under "a status or hash misreport making an integrator credit or refund twice" (High impact category):
- If an integrator (e.g., an exchange, custodian, or payment processor using this SDK for withdrawal orchestration) uses `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` to confirm completion of individual withdrawals in a batch of same-token payouts, one withdrawal (say, to attacker's address) reporting "completed" with a tx hash actually belonging to a *different* withdrawal (say, to a legitimate different recipient) can cause the integrator to mark the wrong withdrawal as settled.
  - This can cause double-crediting internal ledgers (the completed withdrawal's proceeds get attributed to two withdrawal records), or cause a withdrawal that is actually still pending/failed to be marked complete based on another withdrawal's hash, leading to premature release of dependent funds/flows on the integrator side.
  - Conversely a withdrawal that failed could be falsely reported as "completed" via a match with a different, successfully completed same-asset withdrawal, which the "status ... not the on-chain outcome" clause of the rules directly targets.

### Likelihood Explanation
Likelihood is realistic, not purely theoretical:
- The SDK explicitly advertises multi-withdrawal batch processing ("Batch Processing: Process multiple withdrawals at a time") and exposes `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` accepting arrays of `WithdrawalParams`.
- Withdrawing the same POA-bridged token (e.g., USDT/BTC/ETH via `.omft.near`) to multiple destinations within one intent transaction is an ordinary, non-adversarial usage pattern (e.g., batch payouts), not requiring any malicious actor.
- The bug triggers deterministically any time ≥2 same-asset POA withdrawals exist in one intent tx — no race condition or external cooperation is needed.

### Recommendation
Disambiguate matching using more than `assetId`. Since the POA API result order is unsorted but per-withdrawal `amount` and `address`/`destinationAddress` are available in both the withdrawal params and the API response, match using a composite key of `(assetId, destinationAddress, amount)`, or — as the code's own comment suggests — sort both the API results and the local withdrawal params consistently (e.g., by amount) for same-asset entries so that same-asset withdrawals are paired positionally rather than via first-match `find()`. At minimum, when multiple same-asset withdrawals are detected in the API response, the code should refuse to report status for any of them (return `pending`/throw) rather than silently returning a possibly-wrong match.

### Proof of Concept
1. Build and sign a NEAR intents transaction containing two POA-bridge withdrawal intents of the *same* token (e.g., `nep141:usdt.tether-token.near`) to two different destination addresses, submitted as a single `intentTx`.
2. Call `sdk.waitForWithdrawalCompletion({ withdrawalParams: [withdrawal0, withdrawal1], intentTx })` (or `createWithdrawalCompletionPromises`), which internally calls `PoaBridge.describeWithdrawal` once per index.
3. Assume the POA bridge relayer settles `withdrawal0` first (COMPLETED with `transfer_tx_hash: "0xhash0"`), while `withdrawal1` is still `PENDING`.
4. `findMatchingWithdrawal(withdrawals, "nep141:usdt.tether-token.near")` for **both** index-0 and index-1 calls returns the same first matching array entry (`withdrawal0`'s COMPLETED record), because it filters only by `nep141:${near_token_id} === assetId` and ignores index/amount/destination.
5. As a result, the promise tracking `withdrawal1` (still pending on-chain) also resolves as `{ hash: "0xhash0" }` — the tx hash of a *different* withdrawal — falsely signaling completion of `withdrawal1` to the caller.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
