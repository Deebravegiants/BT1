### Title
Unchecked ERC20 transfer return value in Tron IntentGatewayV2 escrow withdrawal permanently drops user/solver funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed order tokens (fill settlement, refunds, and dust sweeps) using a raw low-level `.call()` encoding `IERC20.transfer`, and only checks that the *call itself* did not revert (`success`). It never decodes and checks the ABI-encoded `bool` return value that `transfer()` is supposed to return. This is the exact "unchecked return value" bug class described in the source report (`Cooler.sol`), reproduced here for a live escrow-settlement path reachable by any solver or user completing/cancelling an intent order.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` releases escrowed input tokens to the beneficiary (solver on fill, user on refund/cancel) and pays out accumulated transaction fees: [1](#0-0) 

For every non-native token it does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
and immediately after (inside the same loop) unconditionally decrements the internal escrow accounting:
```solidity
_orders[body.commitment][token] -= amount;
```

The same unchecked pattern is used in the governance-triggered dust sweep path (`SweepDust`) inside `dispatchIncoming`/`onAccept`: [2](#0-1) 

`success` here only reflects whether the external call reverted at the EVM/TVM level — it says nothing about the ABI-encoded return data. TRC20/ERC20-style tokens that return `false` on failure instead of reverting (a documented pattern, analogous to ZRX on Ethereum, and common among TRC20 tokens on Tron) will make `token.call(...)` return `success == true` even though no tokens moved. The contract then proceeds to zero-out `_orders[body.commitment][token]` (or otherwise treat the withdrawal as complete) despite the transfer having silently failed.

This directly contrasts with the audited, non-Tron `IntentGatewayV2`/`IntentsBase._withdraw` path, which correctly uses OpenZeppelin's `SafeERC20.safeTransfer` (which reverts on both call failure and `false` return): [3](#0-2) 

The Tron fork appears to have replaced `safeTransfer`/`safeTransferFrom` with a hand-rolled low-level call that omits the return-data boolean check, reintroducing the exact vulnerability class the report describes.

### Impact Explanation
`withdraw()` is invoked from `onAccept()` for `RequestKind.RedeemEscrow`/`RefundEscrow` (settlement messages authenticated as coming from a peer `IntentGateway` instance) and from `onGetResponse()` for source-chain cancellations. Both are core, unprivileged, reachable paths in the intents escrow lifecycle — every solver fill and every user cancellation goes through this code.

If the escrowed token silently returns `false` on transfer (e.g., paused, blocklisted-recipient, or non-standard TRC20/ERC20 semantics):
- The escrow accounting (`_orders[commitment][token]`) is decremented/deleted and the order is marked filled/refunded, even though the beneficiary received nothing.
- The tokens remain permanently stuck in the `IntentGatewayV2` contract, unreachable by any recovery path since the accounting no longer reflects an outstanding balance.
- This is a permanent freezing/loss of user or solver funds with no way to retry or reclaim them — the on-chain state says "settled" while the actual tokens sit un-swept in the contract.

This satisfies "concrete theft or permanent freezing of funds" for the token bridge/escrow class explicitly in scope.

### Likelihood Explanation
No privileged role is required to trigger this — every normal fill settlement (`RedeemEscrow`), refund (`RefundEscrow`), or GET-response-driven cancel refund goes through `withdraw()`. The only requirement is that one of the order's input/output tokens be a non-standard ERC20/TRC20 implementation that returns `false` instead of reverting on failure (paused token, blocklist, insufficient allowance edge cases in some non-standard implementations, etc.) — a realistic condition on Tron given TRC20 tokens' well-known inconsistent adherence to the standard return-value convention.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` handler with OpenZeppelin's `SafeERC20.safeTransfer`, mirroring what `evm/src/apps/intentsv2/IntentsBase.sol` already does. This reverts on both call failure and a `false` return value, preventing state changes (escrow decrement / order finalization) from proceeding on a failed transfer.

### Proof of Concept
1. Place a cross-chain (or same-chain) order on the Tron `IntentGatewayV2` deployment using an input token `T` that implements `transfer()` returning `false` on failure without reverting (e.g., paused state, or the token owner blocklists the beneficiary right before settlement).
2. Trigger settlement: a solver fills the order on the destination chain, producing a `RedeemEscrow` message that Hyperbridge relays back to the Tron source chain, invoking `onAccept()` → `withdraw()`.
3. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `(true, <abi-encoded false>)` because `T.transfer` returns `false` but does not revert.
4. `success == true`, so the code does not revert; `_orders[commitment][token] -= amount` executes and `_filled[commitment] = beneficiary` is set, finalizing the order as settled.
5. `beneficiary`'s token balance never increased — the tokens remain locked in `IntentGatewayV2` with no accounting entry left to reclaim them.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
