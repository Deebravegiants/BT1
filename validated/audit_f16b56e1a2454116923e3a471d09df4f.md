### Title
Webhook `shop` (tenant identifier) is trusted from an unsigned HTTP header while the HMAC only signs the body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the `X-Shopify-Shop-Domain` / `Shopify-Shop-Domain` HTTP header, but the HMAC signature that the gem validates only covers the raw request body. Any attacker who possesses one legitimately-signed webhook body (e.g., from their own shop's installation of the app, which shares the same `client_secret` across all tenants) can re-deliver that body directly to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop, and the signature will still validate.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, which callers use to identify which merchant/tenant the webhook belongs to, is read straight from an HTTP header and is never included in the signed content: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` verifies `computed_signature(verifiable_query.to_signable_string, secret)` against the received HMAC, using the same `client_secret` shared by every shop installing the app: [4](#0-3) 

Because `to_signable_string` returns only the body, the `shop`, `topic`, and `webhook_id` headers are entirely outside the cryptographic binding. The equality the system implicitly relies on is:

`shop_used_for_tenant_lookup == shop_that_actually_generated_the_signed_body`

but nothing enforces this equality — `shop` is parsed from attacker-controllable bytes that were never verified.

### Impact Explanation
Any merchant/tenant using the shared app (an "unprivileged internet user" relative to other tenants) legitimately receives, for their own shop, a webhook payload correctly HMAC-signed with the app's `client_secret`. That signature remains valid for the *body* regardless of which `shop-domain` header accompanies it. By replaying that same signed body directly to the app's webhook endpoint (bypassing Shopify's own delivery infrastructure) while substituting a victim shop's domain in the header, the attacker can make the host application process/attribute webhook data to a tenant they do not own — a cross-tenant confusion/injection that does not require the `api_secret_key`, an access token, or any privileged credential beyond having their own shop's normal webhook traffic. This satisfies the Critical impact category of cross-tenant access.

### Likelihood Explanation
Likelihood is Medium-High: it only requires (a) being a legitimate (even unprivileged) installer of the target app to obtain one genuinely signed webhook body, and (b) sending an HTTP request directly to the app's public webhook endpoint with a modified `shop-domain` header — no credential theft, TLS interception, or social engineering needed. Whether the impact is realized end-to-end depends on the host application trusting `Request#shop` for tenant lookup without additional binding, which is the documented/intended usage pattern of this API in the gem (see `SessionUtils` and typical Rails engine usage where `request.shop` selects the session/tenant).

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed payload verification path, or otherwise cryptographically tie the header-derived shop to the signed body — for example, by having `to_signable_string` incorporate the shop domain, or by requiring verification callers to cross-check the header-derived shop against a value embedded in the JSON body itself before using it as a tenant key. At minimum, document that `Request#shop` is unauthenticated and must not be used as the sole tenant-selection key by host applications without additional verification.

### Proof of Concept
1. Attacker registers/installs the shared app on `attacker-shop.myshopify.com` and captures a legitimately delivered webhook: raw body `B` and header `Shopify-Hmac-Sha256: H`, where `H = HMAC(client_secret, B)`, plus header `Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker sends a new HTTP POST directly to the app's webhook endpoint with the identical body `B` and identical `Shopify-Hmac-Sha256: H`, but replaces `Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim-shop.myshopify.com` from the header: [2](#0-1) 
4. `HmacValidator.validate` still succeeds because it only checks `to_signable_string` (the unchanged body `B`) against `H`: [5](#0-4) 
5. The host application, trusting `request.shop`, processes/stores the webhook data under `victim-shop.myshopify.com`'s tenant context — a cross-tenant data injection despite full HMAC "verification" success.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
