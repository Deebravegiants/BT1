## Analysis

The reported bug class is: a state-mutating function (`Pool.lockUnits`) trusts a caller-supplied "who does this belong to" parameter with no proof that the caller (or the entity acting) is actually authorized to bind/claim that identity — letting any unprivileged actor attribute another party's resource to themselves.

The reachable analog in `orb-core` is in the **user QR-code validation and signup-enrollment flow**. The Orb determines *whose* biometric enrollment/account a signup belongs to solely from the `user_id` embedded in a scanned QR code, and the only check performed is that the QR code's hash matches data the backend has on file for that `user_id` — there is no check that the physical person being biometrically captured is the actual holder/owner of that `user_id`.

- `qr_scan::user::Data::try_parse` decodes a `user_id` (and optional `user_data_hash`) straight from the QR-code string with no binding to the person in front of the Orb: [1](#0-0) 
- `backend::user_status::request` validates only that the QR-code's `user_data_hash` matches backend-stored `user_data` for that `user_id` — proving the QR *token* is a valid backend-issued token, not that the bearer is its rightful owner: [2](#0-1) 
- Once "valid", `do_signup` takes `user_id` directly from the scanned QR code and uses it as the identity for the entire enrollment, PCP encryption, and upload pipeline: [3](#0-2) [4](#0-3) 
- That same `user_id`/QR string is what gets submitted to the backend signup endpoint as the authoritative "userId" for the captured biometrics: [5](#0-4) 
- Personal-custody-package encryption keys and `id_commitment` (identity binding) come from `UserData` resolved purely from that same unauthenticated `user_id`/hash check: [6](#0-5) 

### Title
Unauthenticated User QR-code Binding Allows Misattribution of Biometric Signup to Arbitrary Victim Account - (File: `src/plans/mod.rs`, `src/backend/user_status.rs`, `src/plans/qr_scan/user.rs`)

### Summary
The Orb determines which account (`user_id`) a biometric signup/enrollment belongs to based solely on a QR code presented to the camera. The only verification performed (`user_data.verify(user_data_hash)`) checks that the QR code is a backend-issued token for that `user_id`; it never verifies that the person whose iris/face is being captured is the actual owner of that `user_id`. Any unprivileged party who obtains a copy of another user's QR code (e.g., screenshot, photo, shared link/deep-link) can present it to the Orb and have their own biometric capture attributed to the victim's account.

### Finding Description
`qr_scan::user::Data::try_parse` extracts `user_id` and `user_data_hash` purely from the content of the scanned QR code, with no cryptographic or physical proof linking the presenter to that identity [7](#0-6) . `verify_user_qr_code`/`backend::user_status::request` treat the QR-code as valid once the backend confirms the hash matches stored `user_data` for that `user_id` [8](#0-7) . This is an integrity check on the *token*, not an authorization/ownership check on the *bearer*. Downstream, `do_signup`/`enroll_user` and the personal-custody-package pipeline use this unauthenticated `user_id` as the ground truth for whose identity commitment, encryption keys, and iris/face biometrics are recorded and uploaded [9](#0-8) [10](#0-9) . This mirrors the `Pool.lockUnits` pattern: a caller/attacker (the person standing at the Orb) can supply an identity token belonging to someone else and have the system's state-mutating operation (issuing/binding a World ID signup) act on that victim's account without proving the caller is authorized to act as that account holder.

### Impact Explanation
An attacker who obtains a copy of a victim's user QR code (screenshots are trivial to capture, replay, or intercept since the code itself, not a live signed physical-presence proof, is the sole credential) can complete an iris/face biometric signup that gets bound to the victim's `id_commitment`/account. This is a misattributed signup: the victim's World ID account becomes associated with the attacker's biometrics (or the attacker's iris data lands in packages encrypted under keys tied to the victim's identity commitment), which can enable account takeover of the victim's World ID, denial of the victim's ability to enroll (identity already "claimed"), or biometric-data leakage/binding to the wrong subject.

### Likelihood Explanation
Likelihood is significant given the enrollment app QR-code is meant to be short-lived per session, but nothing in this code path cryptographically binds the presenting human to the QR-derived `user_id` beyond the backend integrity hash check; any bearer of a valid QR string (screenshot, shoulder-surfed photo, or shared link before it's consumed/expired) satisfies the entire check performed here.

### Recommendation
Bind the scanned QR-derived `user_id` to the physical subject being biometrically captured through a mechanism that cannot be transferred by copying the QR content — e.g., requiring the QR to encode/prove a freshly-generated, single-use, short-TTL session secret that is verified end-to-end with the app session, and/or requiring an additional liveness/possession factor (e.g., app-side confirmation over the already-authenticated `orb_relay` channel) before treating `verify_user_qr_code`'s success as authorization to enroll biometrics under that `user_id`.

### Proof of Concept
1. Victim generates their `user_id` QR code in the companion app for a signup session.
2. Before the victim scans it at the Orb, attacker obtains a copy of the QR code (screenshot/photo/shared link).
3. Attacker presents the copied QR code to a different Orb (or the same one) and undergoes the standard biometric capture flow.
4. `backend::user_status::request` succeeds because the hash matches backend records for `user_id` [2](#0-1) .
5. `do_signup` proceeds using `qr_codes.user_qr_code.user_id` (the victim's id) as the identity for the attacker's captured iris/face data, uploading the resulting personal-custody-package under the victim's account [9](#0-8) .
