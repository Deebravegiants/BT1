## Title
Webhook shop attribution is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (and `topic`) used to route and process the webhook are read from unauthenticated HTTP headers. Because a single app-level `api_secret_key` signs webhooks for *every* shop that installs the app, a body+HMAC pair that is valid for one tenant remains cryptographically valid when replayed with a forged `x-shopify-shop-domain` header pointing at a different tenant.

### Finding Description
`Utils::HmacValidator.validate` verifies the HMAC by recomputing over `verifiable_query.to_signable_string` and comparing to the received signature: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw request body, never the shop domain: [2](#0-1) [3](#0-2) 

`shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic link to the signed body: [2](#0-1) 

`Registry.process` only checks the HMAC on the body, then forwards `request.shop` (the unauthenticated header) straight to the handler as the tenant identity for the event: [4](#0-3) 

This breaks the identity binding: `shop authenticated by HMAC` should equal `shop the payload is attributed to`, but the gem only proves `HMAC(secret, body) == received_hmac`; it never proves the header-derived `shop` is the one the signature was generated for. Since `api_secret_key` is shared by the app across all of its installed shops (it is not shop-specific), a valid `(body, hmac)` pair captured from a legitimate webhook to Shop A's endpoint remains a valid `(body, hmac)` pair when resent with `x-shopify-shop-domain: shop-b.myshopify.com`, because the HMAC check never inspects the shop header at all.

### Impact Explanation
Host applications built on this gem (per the documented `WebhookMetadata` contract) key their per-shop actions off `data.shop` — e.g., updating shop-scoped records, revoking/deleting data on `app/uninstalled` or GDPR `shop/redact` topics, or writing incoming data into the wrong tenant's records. An attacker who has (or previously had) their own legitimate install of the app can capture valid `(body, hmac)` pairs from webhooks Shopify sends to their own store, then replay that request to the app's public webhook endpoint with a forged shop-domain header for a victim shop. Because the HMAC only proves "this body was signed with the app's secret," not "this event belongs to shop X," the handler executes the event believing it originates from the victim tenant — a cross-tenant integrity violation reachable by any actor who has installed the app once.

### Likelihood Explanation
Webhook endpoints are public HTTP endpoints exposed to the internet by design, and headers are fully attacker-controlled inputs at the HTTP layer; the only genuine authentication in this flow is the body HMAC, which per `HmacValidator`/`Webhooks::Request` never binds the shop identity. No credentials, TLS interception, or privileged access are needed — only a legitimate (even free/trial) install of the app to harvest one valid signed payload.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-covered signable content for webhooks, or otherwise cryptographically bind the header-derived shop to the specific signature (e.g., verify that the resolved shop matches an out-of-band trusted store, such as the shop associated with the session/access token used to originally register that specific webhook subscription) before dispatching to handlers.

### Proof of Concept
1. Install the app on `shop-a.myshopify.com` and capture a legitimate webhook POST (raw body + `x-shopify-hmac-sha256` header) delivered by Shopify.
2. Replay the exact same body and HMAC header to the app's webhook endpoint, but set `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `body` against `hmac` (see `Webhooks::Request#to_signable_string` returning `@raw_body`): [3](#0-2) 
4. The handler is invoked with `WebhookMetadata.new(..., shop: request.shop, ...)` where `request.shop` is `"shop-b.myshopify.com"`, even though the payload was never generated for that shop: [5](#0-4)
