### Title
Low default Polygon confirmation depth in Simplex's cross-chain confirmation policy exposes solver capital to reorg-based fund loss - (File: `sdk/packages/simplex/src/config/interpolated-curve.ts`)

### Summary
Simplex (Hyperbridge's intent-filling SDK) gates cross-chain order fills on a `ConfirmationPolicy` curve that determines how many source-chain block confirmations must elapse before the solver commits capital on the destination chain [1](#0-0) . The built-in default for Polygon (`chainId 137`) requires only 2–5 block confirmations, recently lowered from a 32-block ceiling to a 5-block ceiling [2](#0-1) . This mirrors the reported LooksRare/Chainlink-VRF issue: an insufficient confirmation depth on a chain prone to multi-block reorgs lets a reorg invalidate the observed event after capital has already been committed based on it.

### Finding Description
`handleNewOrder` in `filler.ts` computes `requiredConfirmations` from the `ConfirmationPolicy` curve keyed by the order's source chain and USD value, then waits for that many confirmations on the source-chain deposit transaction before treating the cross-chain order as safe to fill on the destination chain [3](#0-2) . For Polygon, the built-in default curve caps confirmations at 5 blocks even for a $100k order, and as low as 2 blocks for smaller orders [2](#0-1) . The changelog documents this reduction from a 32-block default down to 5, based on average finality assumptions of ~5 seconds, rather than a safe worst-case reorg depth [4](#0-3) .

This is architecturally identical to the referenced VRF `minimumRequestConfirmations` issue: the protocol treats an event as final and irreversible after only a handful of blocks, but Polygon is documented (in the referenced report) to regularly reorg beyond 3 blocks, and even more so during network stress or validator misbehavior. Because the solver (Simplex) reads the source-chain `OrderPlaced`/deposit event through its own RPC quorum and, once "confirmed," unconditionally commits capital on the destination chain via `executeOrder`, a reorg that removes the source-chain deposit after the confirmation threshold is met but before the reorg risk is actually exhausted allows an attacker to walk away with the destination-chain payout while the source-chain escrow deposit is rolled back.

### Impact Explanation
If a source-chain reorg exceeds the configured confirmation depth (2–5 blocks for Polygon, all well below realistic reorg depths for a chain with imperfect finality guarantees), the solver's assumption that the source-side deposit is immutable becomes false. The solver has already dispatched destination-chain funds (`executeOrder`) based on the "confirmed" event [5](#0-4) . If the reorg removes or alters the underlying order/escrow, the solver has paid out real capital for an order that no longer canonically exists — a direct, unrecoverable loss of solver funds. This is unbacked-value creation from the solver's perspective and a concrete theft vector for anyone able to trigger or benefit from a reorg (including MEV/validator actors on Polygon).

### Likelihood Explanation
Reachable by any ordinary user submitting a cross-chain intent order — no privileged access needed. The threshold is a configuration default shipped as-is unless operators override it, and the documented rationale for lowering it (5s average finality) does not account for the reorg risk the confirmation depth is nominally meant to defend against. Polygon reorgs deeper than a handful of blocks are a known, recurring event on that network, making exploitation plausible without requiring an attacker to have unusual capabilities beyond timing a reorg or benefiting from one.

### Recommendation
Raise Polygon's (and other L2/PoS chains') confirmation defaults to reflect worst-case observed reorg depth rather than average finality time, or better, gate fills on Polygon's actual finality signal (e.g., checkpointed/milestone finality) instead of a fixed low block count. Consider making the curve value configurable with a documented safe floor and warning if operators set it below a chain-specific safe minimum.

### Proof of Concept
1. Operator runs Simplex with default `confirmationPolicies` for Polygon (`chainId 137`), i.e. 2–5 blocks depending on order USD value [2](#0-1) .
2. A user places a cross-chain order sourced on Polygon, depositing into escrow.
3. The Simplex filler detects the `OrderPlaced` event, waits until `getTransactionConfirmations` reports ≥ `requiredConfirmations` (as low as 2 blocks, ~4 seconds) [6](#0-5) , then dispatches destination-chain funds via `executeOrder`.
4. A reorg on Polygon deeper than the confirmation window reverts the block containing the deposit transaction (the transaction disappears or the escrow deposit changes), while the destination-chain payout has already been sent.
5. The solver has permanently lost the destination-chain funds paid out against a source-chain deposit that no longer exists.

					try {
						canFillCache.set(strategy, await strategy.canFill(order))
					} catch (err) {
						this.logger.error({ orderId: order.id, strategy: strategy.name, err }, "Error checking canFill")
						canFillCache.set(strategy, false)
					}
				}

						if (stratValue != null) {
							inputUsdValue = Decimal.max(baseInputUsd, stratValue.inputUsd)
							break

					} catch (err) {

							{ orderId: order.id, strategy: strategy.name, err },
							"Error getting strategy-specific inputUsdValue",

					}
				}

				let requiredConfirmations = 0
				if (isCrossChain) {
					const fillableStrategies = [...canFillCache].filter(([, canFill]) => canFill)

				// The AbortController lets evaluateOrder cancel the confirmation
				// loop early when the order turns out to be unprofitable.
				const abortController = new AbortController()

				// Single-provider setups keep the tight 300ms poll; quorum setups
				// fan every poll out to all providers, so poll less aggressively
				// to stay within their rate limits.
				const confirmationPollMs = sourceQuorumClient.size > 1 ? 1000 : 300

					// rejects the surrounding Promise.all and drops the order.

							backoffMs: 250,

						},

						"Order confirmation requirements",

					while (currentConfirmations < requiredConfirmations) {

						if (abortController.signal.aborted) return

								}),
							{
								maxRetries: 3,
								backoffMs: 250,
								logMessage: "Failed to get transaction confirmations",
							},
						)
						this.logger.debug({ orderId: order.id, currentConfirmations }, "Order confirmation progress")

					this.logger.info({ orderId: order.id, currentConfirmations }, "Order confirmed on source chain")

				const [, evaluationResult] = await Promise.all([

					this.evaluateOrder(order, canFillCache).then((result) => {
						if (!result) abortController.abort()
						return result
					}),
				])
				const confirmDurationSec = (Date.now() - confirmStartMs) / 1000
				this.monitor.emit("orderTiming", {

					phase: "confirmation",

				})

						order,
						evaluationResult.strategy,
						solverSelectionActive,
						inputUsdValue,
						evaluationResult.profitability,
					)

# 2026-09-08 — Polygon's confirmation ceiling drops from 32 blocks to 5

Seun reports Polygon finalizes in ~5s on average, so the built-in default's 32-block ceiling
(~64s at ~2s blocks) held $100k orders far longer than the chain needs. The max point is now 5
blocks, ~10s, which leaves headroom over the observed finality without the old minute-long wait.
The min point (2 blocks at $1k) is unchanged, and every value between the two still interpolates.
Only the built-in default moved; a user `[confirmationPolicies."137"]` entry still overrides it.
