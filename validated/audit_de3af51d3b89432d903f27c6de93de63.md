## Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is handed to the app's webhook handler purely from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` HTTP header, but the HMAC signature that `Registry.process` verifies only covers the raw request body. The `shop` field that the rest of the pipeline relies on to route/attribute webhook data is never part of the signed material, so it can be swapped independently of a still-valid signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an attacker-controllable HTTP header with no cryptographic binding to that body: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` (which calls `to_signable_string`, i.e. only `raw_body`) and then immediately forwards `request.shop` to the handler as the tenant identifier, with no additional check that the header matches anything inside the verified body: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string`: [4](#0-3) 

This is exactly the bug class in the external report: a field that is *acted on* (`shop`, used for tenant attribution/dispatch) is not covered by the HMAC that is supposed to prove authenticity of the request. The binding that should hold is:

`hmac_verified(raw_body) == true` should imply `shop_used_for_dispatch == shop_that_generated(raw_body)`

But because `shop` is taken from a header outside the signed scope, an attacker who possesses one valid `(raw_body, hmac)` pair (trivial to obtain: install the app on their own shop and let Shopify deliver a real webhook to the app's public webhook endpoint) can resend that same `(raw_body, hmac)` pair with a different `X-Shopify-Shop-Domain` header value. The HMAC check still passes (it only checks the body), yet `WebhookMetadata.shop` now reports a different tenant than the one whose secret/body actually produced the signature.

### Impact Explanation
Because a single app's `client_secret` is shared across all merchants that installed it, any merchant that has installed the app can generate a validly-signed webhook body for their own shop and then relabel it as belonging to any other shop by changing only the unauthenticated `shop-domain` header. Host applications built on this gem are expected to trust `WebhookMetadata#shop` (and only that field) to know "who this webhook is about" once `Registry.process` returns success — but that value can be forged independent of the signature. This enables cross-tenant data confusion: an attacker-controlled merchant can inject data (or trigger processing) that the host app attributes to a victim shop, e.g. writing attacker-supplied body content into the victim's persisted app state, or triggering mandatory GDPR-type webhook handlers (`shop/redact`, `customers/redact`, `customers/data_request`) against a shop they don't control. This is a cross-tenant access issue.

### Likelihood Explanation
Webhook endpoints are, by design, public unauthenticated HTTP(S) endpoints — the HMAC is the *only* mechanism meant to authenticate the sender/content. Any user who can install the app on a shop they control (a normal, unprivileged action) can obtain a genuine `(body, hmac)` pair from real Shopify deliveries and replay it toward the app's webhook endpoint with a forged `shop-domain` header, since nothing in `lib/shopify_api/webhooks/**` binds the header to the signature.

### Recommendation
Bind the shop identity into the material that is verified, e.g. include `shop` (and/or `topic`) in `to_signable_string`, or independently verify that the header-derived `shop` corresponds to a shop for which the app holds a valid installation/session before dispatching to handlers. At minimum, document/require host applications to cross check `request.shop` against a known/authorized shop list rather than trusting it implicitly once `HmacValidator.validate` succeeds.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com`; Shopify delivers a legitimate webhook to the app's public endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid over `B` with the app's real `client_secret`), plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker captures `(B, H)` and resends the exact same request to the same endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` (`B`) — it still matches `H`, so validation succeeds: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: request.parsed_body, ...)`, so the host app processes attacker-controlled body content as if it came from `victim.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
