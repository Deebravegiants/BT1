Based on my research, I found a genuine analog to the reported bug class in the PoA bridge withdrawal-status matching logic, not in the excluded DoS/loop category.

### Title
PoA Bridge withdrawal status matches only by `assetId`, causing status/hash misattribution for batched same-asset withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain completion status of a specific withdrawal by matching entries returned from the PoA indexer using only `assetId` (`near_token_id`), ignoring the withdrawal's `index`, `amount`, or `destinationAddress`. When a batch withdrawal contains multiple withdrawals of the same asset, every one of them can be matched to the same (first) API record, so the reported `txHash`/status for one withdrawal gets attributed to a different, unrelated withdrawal.

### Finding Description
`describeWithdrawal` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which does a simple `.find()` on the asset identifier alone: [1](#0-0) 

The `WithdrawalIdentifier.index` value produced by `createWithdrawalIdentifiers` (which distinguishes multiple withdrawals of the same route/asset in a batch) is never used inside `findMatchingWithdrawal`: [2](#0-1) 

The equivalent matcher in `internal-utils` documents this exact limitation explicitly in its own comment: "Currently only matches by assetId (near_token_id). This means multiple withdrawals of the same token in a single transaction are not supported": [3](#0-2) 

This is confirmed as intended matching semantics by the test suite (matching "by assetId, not by index"): [4](#0-3) 

The equality that breaks: the `txHash`/status reported for withdrawal #N to the caller is not guaranteed to be the on-chain outcome of withdrawal #N — it can be the outcome of a different withdrawal #M (same asset, different destination/amount) inside the same batch.

### Impact Explanation
When `sdk.processWithdrawal`/`waitForWithdrawalCompletion` is used for a batch of `WithdrawalParams[]` containing two or more withdrawals of the same `assetId` (e.g., two USDT withdrawals to different addresses), `watchWithdrawal` for each `WithdrawalIdentifier` polls `describeWithdrawal`, which can return the same PoA API record (same `transfer_tx_hash`) for both. An integrator relying on this status to mark a specific withdrawal request as completed and release funds/credit downstream could:
- Report withdrawal A as "completed" with a `txHash` that actually corresponds to withdrawal B's on-chain transfer, and vice versa.
- Potentially double-credit or falsely confirm completion of a withdrawal that never actually settled to its intended destination.

This matches the "status or hash misreport making an integrator credit or refund twice" High-impact criterion from the rules.

### Likelihood Explanation
This requires no malicious actor — any legitimate user/integrator issuing a batch withdrawal (`WithdrawalParams[]`) with two or more entries sharing the same `assetId` via the PoA bridge route will trigger the collision, since `findMatchingWithdrawal` has no way to disambiguate. Batch withdrawals are a documented, supported SDK feature (`README.md` "Batch Processing: Process multiple withdrawals at a time"), so the precondition is easily reached in normal usage without any protocol-level state manipulation.

### Recommendation
Disambiguate matching using more than `assetId`: also filter/sort by `amount` and `destinationAddress` (and destination memo when present) as suggested in the internal-utils comment, or track already-consumed API records per batch call so the same PoA withdrawal record cannot be matched to more than one `WithdrawalIdentifier`.

### Proof of Concept
1. Call `sdk.processWithdrawal` / `sdk.signAndSendWithdrawalIntent` with `withdrawalParams` = two entries, both `assetId: "nep141:usdt.omft.near"`, but different `destinationAddress` values (A and B), in a single batch.
2. Both withdrawals produce `WithdrawalIdentifier`s with the same `assetId` but different `index`.
3. When polling completion, `PoaBridge.describeWithdrawal` is invoked once per identifier; `findMatchingWithdrawal` in each call performs `withdrawals.find(w => nep141:${w.data.near_token_id} === assetId)`, returning the same PoA API withdrawal object (whichever the indexer lists first) for both calls.
4. Both withdrawal-completion results report the identical `transfer_tx_hash`, even though only one of them actually corresponds to that hash — the caller cannot tell which withdrawal (to address A or B) genuinely landed at that hash. [1](#0-0)

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
