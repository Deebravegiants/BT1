### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw HTTP body only, while the `shop` (tenant) identity is read from an unauthenticated header. `Registry.process` verifies the body HMAC but then hands the handler a `shop` value that was never part of what was verified, breaking the equality `shop authenticated by HMAC == shop acted upon by the handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header with no cryptographic binding to that body: [2](#0-1) .

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e., the body only) and compares it against the received `hmac` value using `OpenSSL.secure_compare`: [3](#0-2) .

`Registry.process` performs exactly this body-only HMAC check, and — once it passes — immediately trusts `request.shop` (the unauthenticated header) to build the `WebhookMetadata` object that is dispatched to the app's handler: [4](#0-3) 

Because `api_secret_key` is a single app-wide secret (not per-shop), any merchant who has legitimately installed the app can capture a genuine `(raw_body, hmac)` pair that Shopify sent for their own shop's webhook. Since the header `shopify-shop-domain` is excluded from the signable string, that same valid `(raw_body, hmac)` pair remains valid when replayed with a different `shopify-shop-domain` header value claiming to be any other shop using the app. The signature check in `HmacValidator.validate`/`validate_signature` still succeeds because it only re-derives the HMAC over the body, never over the shop field: [5](#0-4) .

This is the same bug class as the report: a security check (HMAC / try-catch state assumption) validates one thing (body integrity / "leave succeeded"), while a different, unguarded value (the `shop` tenant identity / staked-balance state) is what downstream logic actually acts on — breaking an implicit identity/state binding that the rest of the system relies on.

### Impact Explanation
`WebhookMetadata.shop` is the field host applications are documented to use for tenant routing (looking up the shop's record, disabling installs, purging data for GDPR topics like `shop/redact` or `customers/redact`, etc.). Because this value is not covered by the HMAC, a merchant who has installed the app (an unprivileged, non-Shopify actor from the app's perspective) can forge webhook deliveries to the app's public webhook endpoint that are cryptographically valid yet falsely attributed to a different, victim shop. This is a cross-tenant identity confusion that can cause the host app to act on/against another merchant's tenant data using attacker-controlled webhook content, which maps to the "Critical – cross-tenant access" impact tier.

### Likelihood Explanation
Requires only: (1) the attacker's own legitimate app installation to obtain one real `(body, hmac)` pair for any topic, and (2) the ability to POST directly to the app's public webhook endpoint with a forged `shop`-domain header — both are unprivileged, internet-reachable actions with no need for the app's `client_secret`, access tokens, or TLS interception. This is fully within scope and does not depend on the host app ignoring documented behavior; the gem's own `Registry.process`/`Request` classes are what expose the unauthenticated `shop` field to the handler after a body-only HMAC check.

### Recommendation
Do not treat `request.shop` as trusted merely because the body HMAC validated. Either (a) include the shop domain (and ideally topic/webhook-id) in the signable string used for HMAC computation, or (b) have `Registry.process` cross-check `request.shop` against an independently-verified/registered shop for the topic before constructing `WebhookMetadata`, and document clearly that callers must not use the header-derived `shop` for tenant lookups without additional verification.

### Proof of Concept
1. App has a single `api_secret_key` shared by all shops that install it.
2. Attacker installs the app on their own shop and triggers any webhook (e.g., `orders/create`), capturing the exact raw body Shopify sent and the corresponding `shopify-hmac-sha256` value.
3. Attacker POSTs that identical raw body and HMAC header directly to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (== the unchanged raw body) and finds it matches — validation passes: [6](#0-5) .
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` and the host app processes it as a genuine event for the victim shop.

          received_signature = verifiable_query.hmac
