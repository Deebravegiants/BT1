### Title
Underpriced send-fee for ML-DSA-65 `TransferToGasKey` actions due to unscaled public-key length - (File: runtime/runtime/src/config.rs)

### Summary
The gas fee charged for transmitting a `TransferToGasKey` action is computed from the length of the attached public key. For post-quantum ML-DSA-65 keys, the code currently uses the wrong (much smaller) length value for this fee, mirroring the Caviar `flashFee`/`changeFee` bug class where one code path scales a value correctly while another path uses the same value unscaled/incorrectly, resulting in a drastically underpriced fee.

### Finding Description
`gas_key_send_pk_len` in `runtime/runtime/src/config.rs` decides which byte-length to use when pricing the *send* fee of a gas-key action: [1](#0-0) 

```rust
fn gas_key_send_pk_len(config: &RuntimeConfig, public_key: &PublicKey) -> usize {
    if config.wasm_config.fix_ml_dsa_cost_charging {
        // This is the proper value - send fee should be based on how many bytes
        // the key occupies on the wire, not in storage.
        public_key.len()
    } else {
        // Preserve the (incorrect) existing behavior if the fix is not enabled.
        // Otherwise, we would break protocol consensus.
        public_key.trie_id_len()
    }
}
```

This length feeds directly into the per-byte send fee for `TransferToGasKey`: [2](#0-1) 

and into `gas_key_transfer_send_fee`, which multiplies the per-byte fee (`ActionCosts::gas_key_byte`) by this length: [3](#0-2) 

An ML-DSA-65 public key is `1952` bytes on the wire (`ML_DSA_65_PUBLIC_KEY_LENGTH`), but `trie_id_len()` for that key type returns only the `32`/`33`-byte SHA3-256 hash used as its on-trie identifier: [4](#0-3) 

As long as `wasm_config.fix_ml_dsa_cost_charging == false` (its current genesis/mainnet value, per the runtime-config diff that flips it to `true` only at a future protocol version), the send-fee-relevant length used for an ML-DSA-65 `TransferToGasKey` action is the 32/33-byte hash instead of the true ~1952-byte wire payload — a ~60x underscaling, exactly analogous to `flashFee` returning `changeFee` unscaled while `changeFeeQuote` correctly scales the same value. This is confirmed by the developers' own changelog note describing the pending fix: [5](#0-4) 

### Impact Explanation
Because `total_send_fees` computes the gas that is *burnt immediately* at transaction conversion (this is the gas that is supposed to cover network bandwidth/transmission cost for the bytes actually sent), pricing it off the 32-byte hash instead of the 1952-byte real key size means the sender pays gas calibrated for a tiny payload while actually transmitting/consensus-including a ~60x larger one. This is a concrete underpriced-execution/bandwidth issue: an attacker can submit ML-DSA-65-keyed `TransferToGasKey` actions cheaply relative to their real resource cost, letting them push disproportionate bytes through the network/chunk bandwidth budget for the fee of a much smaller action — a spam/congestion vector directly reachable from a normal, unprivileged submitted transaction.

### Likelihood Explanation
This requires no special privilege — any account can submit a transaction containing a `TransferToGasKey` action with an ML-DSA-65 public key as soon as post-quantum signatures/gas keys are enabled, and the underpricing is unconditional as long as `fix_ml_dsa_cost_charging` remains `false` for the active protocol version, which is the fix's pre-activation default described in the config diff itself.

### Recommendation
Backport/activate the `fix_ml_dsa_cost_charging` correction (or an equivalent immediate fix) so `gas_key_send_pk_len` always uses `public_key.len()` (true wire length) for the send fee, matching how `changeFeeQuote`-style correct scaling should be mirrored across all fee computation sites, and ensure the exec-side (`trie_id_len()`-based) fee and send-side (`len()`-based) fee are each computed against the appropriate—but individually correct—length rather than allowing a config flag to silently keep the underpriced legacy behavior live on any deployed protocol version.

### Proof of Concept
1. On a network where `wasm_config.fix_ml_dsa_cost_charging == false` (current default), craft a transaction with a `TransferToGasKey` action whose `public_key` is an ML-DSA-65 key (1952 raw bytes).
2. `total_send_fees` → `gas_key_transfer_send_fee` computes the per-byte component using `gas_key_send_pk_len`, which returns `public_key.trie_id_len()` (32/33 bytes) instead of `public_key.len()` (1952 bytes). [1](#0-0) 
3. The resulting burnt gas for the send fee is calculated as if the key were 32/33 bytes, roughly 60x cheaper than the true wire cost, while the transaction still carries/propagates the full 1952-byte key.
4. Repeating this with many `TransferToGasKey` actions lets an attacker consume network/chunk bandwidth well beyond what they are charged for.

```rust
/// Send fee for TransferToGasKey / WithdrawFromGasKey actions.
/// Based on the public key length (what the sender sees).
pub fn gas_key_transfer_send_fee(
    cfg: &RuntimeFeesConfig,
    sender_is_receiver: bool,
    public_key_len: usize,
) -> GasKeyTransferFee {
    let base = cfg.fee(ActionCosts::gas_key_transfer_base).send_fee(sender_is_receiver);
    let per_byte = cfg
        .fee(ActionCosts::gas_key_byte)
        .send_fee(sender_is_receiver)
        .checked_mul(public_key_len as u64)
        .unwrap();
    GasKeyTransferFee { base, per_byte }
}
```
