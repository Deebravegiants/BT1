### Title
Malformed/Missing Fraud-Signal Data Causes Fraud Checks to Silently Skip Instead of Failing Safe - (File: `fraud-engine/src/pipeline.rs`)

### Summary
The Balancer report describes a class of bug where malformed/empty encoded data (`userData = ""`) is silently decoded into an *unintended but "valid-looking" default variant*, causing the intended operation to be skipped/broken rather than erroring loudly, resulting in the security guarantee (safe withdrawal) never being enforced. The analogous pattern in `orb-core` is in the fraud-engine pipeline: when a fraud-check rule cannot extract its operand from the serialized signup/biometric data (missing field, wrong path, malformed structure), the failure is silently swallowed into `None` rather than being surfaced as an error or being conservatively treated as "fraud detected." This causes individual fraud checks to be effectively disabled whenever their input data is malformed or incomplete, mirroring the "malformed data → unintended silent path → protection never triggers" root cause of the referenced report.

### Finding Description
`Rule::evaluate` returns `Result<bool>` and legitimately errors when an operand path cannot be resolved in the serialized JSON data: [1](#0-0) 

`Pipeline::run` calls `check.rule.evaluate(...)` for every configured check, but instead of propagating this error (which would halt/flag the whole pipeline run) it converts the error into `None` via `result.ok()` and stores it in the check's `CheckResult`: [2](#0-1) 

This means that if the serialized fraud-check input for a given signup is malformed, truncated, or has a field missing (e.g. an agent that failed to populate a field, a schema mismatch after an app/orb version change, or unexpected null/empty values as seen in `serde_to_evalexpr_value`'s handling of `Value::Null` → `evalexpr::Value::Empty`), the corresponding check silently becomes `None` (i.e., "not evaluated") rather than being flagged as failed/fraudulent or erroring the pipeline outright: [3](#0-2) 

This is structurally identical to the reported bug class: malformed/incomplete data is fed into a decode/evaluate path that has multiple possible outcomes, and instead of failing loudly (which would force remediation), it resolves to a "valid" but unintended state (`None`/skipped) that quietly neutralizes the intended protection (fraud detection) rather than blocking it.

### Impact Explanation
If a `Report`'s fraud-detection status is computed only from checks whose result is `Some(true)`, then any check whose input data is malformed/missing degrades to `None` and is excluded from the fraud determination. An attacker or a buggy/incompatible upstream agent that produces malformed or incomplete data for a specific field referenced by a fraud rule can cause that specific fraud check to be silently skipped for the entire signup, without the failure being surfaced anywhere except a debug/info-level trace log. This is a fraud-detection bypass: the very data anomaly that should raise suspicion (malformed/incomplete signal data) instead disables the check meant to catch it.

### Likelihood Explanation
This does not require crafting a Balancer-style low-level byte payload; it only requires the fraud-check input JSON to be missing/malformed for a field referenced by `operand_mapping` in any configured `Rule` — something that is plausible whenever data pipelines evolve, an agent fails partially, or fields are optional/nullable. The failure mode is silent (`tracing::info!` only, no alerting) and pipeline execution continues normally, which increases the likelihood that such bypasses go unnoticed in production. I was not able to inspect `fraud-engine/src/report.rs` to confirm exactly how `CheckResult.result == None` is aggregated into the final `fraud_detected()` verdict, so the precise severity of the bypass (single-check bypass vs. whole-report bypass) is not fully confirmed with this level of access — this should be verified directly in that file.

### Recommendation
- In `Pipeline::run`, do not silently convert rule-evaluation errors to `None`; either propagate the error out of `run` (failing the whole pipeline, forcing an explicit decision on unresolvable data) or treat an unresolvable/malformed operand as `Some(true)` (fail-closed/conservative fraud flag) rather than `Some(false)`/`None`.
- Add explicit alerting/metrics whenever a check's rule fails to evaluate, so malformed-data-driven check skips are visible and actionable rather than only present in debug traces.
- Audit `fraud-engine/src/report.rs`'s aggregation logic (`fraud_detected()`) to ensure `None` check results cannot be conflated with "no fraud detected."

### Proof of Concept
1. Configure a `Pipeline` with a `Check` whose `Rule::operand_mapping` references a path (e.g. `"group_a.suspicious_flag"`) that is expected to always be present in the serialized fraud-signal struct.
2. Have the serialized data for a particular signup omit or nest that field incorrectly (simulating malformed/incomplete data from an upstream agent), so `extract_value_from_serialized_data` returns `None`: [4](#0-3) 
3. `Rule::evaluate` returns `Err(...)`; `Pipeline::run` converts this via `result.ok()` into `CheckResult { result: None, .. }` instead of erroring the whole run or flagging fraud: [5](#0-4) 
4. The check for that signup is effectively skipped/neutralized, and the pipeline proceeds as if that fraud signal never fired, with only an info-level log line as a trace.

fn extract_value_from_serialized_data<'a>(
    path: &str,
    serialized_data: &'a serde_json::Value,
) -> Option<&'a serde_json::Value> {
    let mut current_value = serialized_data;
    for key in path.split('.') {
        current_value = current_value.get(key)?;
    }
    Some(current_value)
}

fn serde_to_evalexpr_value(serde_value: &serde_json::Value) -> Result<evalexpr::Value> {
    match serde_value {
        serde_json::Value::Null => Ok(evalexpr::Value::Empty),
        serde_json::Value::Bool(bit) => Ok(evalexpr::Value::Boolean(*bit)),
        serde_json::Value::Number(num) => {
            if num.is_f64() {
                Ok(evalexpr::Value::Float(
                    num.as_f64().ok_or_else(|| eyre!("failed to extract f64"))?,
                ))
            } else if num.is_u64() {
                Ok(evalexpr::Value::Int(
                    num.as_u64().ok_or_else(|| eyre!("failed to extract u64"))?.try_into()?,
                ))
            } else {
                Ok(evalexpr::Value::Int(
                    num.as_i64().ok_or_else(|| eyre!("failed to extract i64"))?,
                ))
            }
        }
        serde_json::Value::String(string) => Ok(evalexpr::Value::String(string.clone())),
        serde_json::Value::Array(arr) => {
            let mut tuple = evalexpr::TupleType::with_capacity(arr.capacity());
            for serde_value in arr {
                tuple.push(serde_to_evalexpr_value(serde_value)?);
            }
            Ok(evalexpr::Value::Tuple(tuple))
        }
        serde_json::Value::Object(_) => Err(eyre!(
            "conversion failed: {} is not a fundamental data-type",
            serde_value.to_string()
        )),
    }
}

    pub fn run<T: Serialize>(&self, data: &T) -> Result<Report> {
        let serialized_data = serde_json::to_value(data)?;
        let mut check_results = HashMap::with_capacity(self.checks.len());

        for check in &self.checks {
            let result = check.rule.evaluate(&serialized_data);
            tracing::info!("{}: {:?}", check.identifier, result);

            if check_results
                .insert(check.identifier.clone(), CheckResult {
                    enabled: check.enabled,
                    result: result.ok(),
                })
                .is_some()
            {
                return Err(eyre!(
                    "pipeline checks with the same identifier \"{}\" found.",
                    check.identifier
                ));
            }
        }

        Ok(Report { check_results })
    }
