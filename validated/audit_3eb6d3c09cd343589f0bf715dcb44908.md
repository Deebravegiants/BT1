### Title
Webhook `shop`/`topic` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC verification performed by `ShopifyAPI::Utils::HmacValidator.validate` never covers the `shop`, `topic`, `webhook_id`, or `api_version` values that the registry later trusts as the tenant/dispatch identity for the webhook.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts `shop`, `topic`, `webhook_id`, and `api_version` straight from HTTP headers: [1](#0-0) 

but the value that is actually HMAC-signed is only the raw body: [2](#0-1) 

`HmacValidator.validate` computes the signature exclusively over `to_signable_string` (i.e. the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` accepts the request once that body-only HMAC check passes, and then unconditionally trusts `request.shop` and `request.topic` — values that were never part of the signed data — to route and tag the payload: [4](#0-3) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop the webhook payload is attributed to`

Because the HMAC secret (`Context.api_secret_key`) is a single, shop-independent app secret, any legitimately observed (body, hmac) pair — e.g. one an attacker obtains by installing the app on their own store and triggering a real webhook, or intercepting any of the app's own webhook traffic without any TLS interception, purely by controlling the shop side of an install — remains cryptographically valid for that body forever, on any shop. Since `shop`, `topic`, `webhook_id`, and `api_version` are not part of the signed bytes, an attacker can replay the exact same body+hmac to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and/or `x-shopify-topic`) header. The signature still verifies, and `Registry.process` hands the handler a `WebhookMetadata` claiming the payload belongs to a shop it never actually came from.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: `bytes verified` (the body) diverges from `bytes/identity acted on` (`shop`, `topic`). An app that uses `data.shop` to write/query per-tenant records (as its own documentation and webhook handler pattern encourages — see `WebhookMetadata.new(topic:, shop:, body:, ...)`) will attribute or apply a replayed payload to the wrong merchant's tenant, i.e. cross-tenant data injection/confusion, without requiring the attacker to know the app's `client_secret`.

### Likelihood Explanation
Any party who can legitimately install the app on a store they control (a normal, unprivileged action for any internet user relative to other tenants) can capture one valid (body, hmac) pair from their own genuine webhook traffic, then freely replay it against the app's public webhook endpoint with a forged shop/topic header. No secret material, TLS interception, or existing session is required — only knowledge of one previously observed signed body.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string (or otherwise bind them cryptographically to the HMAC, matching what Shopify's own webhook signing actually covers) instead of relying on the raw body alone, and reject a request if these header values do not match what was authenticated.

### Proof of Concept
1. Install the app on `shop-a.myshopify.com` and trigger any registered webhook topic; capture the raw body `B` and the `X-Shopify-Hmac-Sha256` header `H` that Shopify sent (this is a legitimate, correctly-signed pair for the app's real secret).
2. Send a new HTTP request directly to the app's webhook endpoint with the same body `B` and header `H`, but set `X-Shopify-Shop-Domain: shop-b.myshopify.com` (a different tenant) and/or a different `X-Shopify-Topic`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop-b.myshopify.com` as `request.shop`; `Utils::HmacValidator.validate(request)` succeeds because it only hashes `B`, which is unchanged.
4. `Registry.process` dispatches the handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)`, causing the app to process shop-a's data under shop-b's identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
