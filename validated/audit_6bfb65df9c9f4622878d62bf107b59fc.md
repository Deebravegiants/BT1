### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the request body, then trusts the unauthenticated `shop-domain` header as the tenant identifier passed to the app's handler. Because the `client_secret`/`api_secret_key` used to sign webhooks is shared across every shop that installs the app, any merchant who installs the app can capture a validly-signed webhook from their own shop and replay it with a forged `shop-domain` header pointing at a victim shop, causing the host application to process attacker-controlled data under the victim's tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, by contrast, is read straight from the (attacker-controlled, non-signed) HTTP header: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes and compares the HMAC only against `verifiable_query.to_signable_string`, i.e. the raw body — the `shop`, `topic`, `webhook_id`, and `api_version` headers are never part of the signed material: [3](#0-2) 

`Registry.process` uses this same HMAC check as the sole authentication gate, and then forwards the unauthenticated `request.shop` value directly into `WebhookMetadata`, which the host application is documented to use as the tenant/shop identifier: [4](#0-3) [5](#0-4) 

The gem's own documentation instructs consumers to key their per-shop processing off `data.shop` without qualification: [6](#0-5) [7](#0-6) 

The identity binding broken is: `hmac_valid(raw_body, api_secret_key) == true` is treated as proof that `request.shop == <the shop the body actually originated from>`, when in fact `shop` is never covered by the HMAC. Since `api_secret_key` (`Context.api_secret_key`) is a single, app-wide secret shared by all installing merchants (confirmed by `HmacValidator.validate` comparing against the same global `Context.api_secret_key`/`old_api_secret_key`), any installed merchant possesses the ability to produce a validly-signed body/HMAC pair and can freely relabel which shop it claims to be for. [8](#0-7) 

### Impact Explanation
This is a cross-tenant access vulnerability: a malicious but legitimately-installed merchant (an unprivileged actor with respect to other tenants) can forge webhook deliveries that the gem reports as authenticated for a shop they do not control. Any host application that (per the gem's documented contract) uses `data.shop` from `WebhookMetadata` to route webhook processing, update per-shop records, or trigger shop-scoped side effects will act on attacker-supplied data while believing it originated from the victim shop — a direct cross-tenant boundary violation.

### Likelihood Explanation
Likelihood is high for any app with more than one merchant installation: exploitation requires only (1) installing the app on an attacker-controlled shop to receive a legitimately HMAC-signed webhook, and (2) resending that request to the app's public webhook endpoint with the `shop-domain` (or `x-shopify-shop-domain`) header changed to the victim's domain, and optionally the topic/body value crafted to whatever the attacker's own shop naturally produces. No secrets, tokens, or victim credentials are required.

### Recommendation
Do not treat `Request#shop` as authenticated by `HmacValidator.validate` alone. Either:
- Include the shop domain (and topic) in the signed material used to compute/verify the webhook HMAC, or
- Require callers of `Registry.process` to supply the expected shop (e.g., resolved from the URL path or an out-of-band mapping) and assert `request.shop == expected_shop` before dispatching to the handler, or
- Explicitly document that `data.shop` is unauthenticated header data and must be independently cross-checked by the host application against a known/installed shop list before being trusted for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, obtaining the app's shared `api_secret_key` in the form of validly-signed webhooks (e.g. `orders/create`) delivered by Shopify.
2. Attacker captures one such webhook HTTP request, including its correctly computed `x-shopify-hmac-sha256` header for a given raw body.
3. Attacker resends the identical body/HMAC pair to the app's webhook endpoint, but rewrites the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` computes `HmacValidator.validate(request)` over `request.to_signable_string` (the raw body only) — validation succeeds because the body/HMAC pair is genuinely valid. [9](#0-8) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes the attacker's body as if it came from the victim, per the documented usage pattern. [7](#0-6)
