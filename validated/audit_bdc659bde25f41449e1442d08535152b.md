### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are trusted for tenant routing without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers [2](#0-1) . `HmacValidator.validate` only ever checks the signature over `to_signable_string` (the body) [3](#0-2) , and `Registry.process` uses the unverified `request.shop` value to build the `WebhookMetadata` that is handed to the app's handler for tenant-specific processing [4](#0-3) .

### Finding Description
The binding that should hold is: `shop_header == shop_bound_by_hmac`. In this gem it does not — the HMAC only binds the body bytes, not the `shop-domain` header used for tenant identification.

Because Shopify apps typically share a single `api_secret_key` across every merchant that installs the app, any unprivileged user who runs their **own** shop and installs the app can receive genuine webhook deliveries for their own store, each with a valid `X-Shopify-Hmac-SHA256` signature computed over the body only. Since the header set (`shop-domain`, `topic`, `webhook-id`, `api-version`) is completely excluded from the signed content, that attacker can replay the exact same body + HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` will still return `true`, because the signature check never inspects the header. `Registry.process` then dispatches the payload to the app's handler tagged with the attacker-controlled `shop` value [4](#0-3) , allowing spoofed webhook events to be attributed to a shop the attacker does not control.

This mirrors the report's root cause class: a field that is acted upon by the protocol (here, the tenant-identifying `shop` header) is not covered by the cryptographic binding (the HMAC), letting an unprivileged party manipulate it independently of the authenticated payload — analogous to the report's unguarded `approve` call bypassing an expected safety wrapper, but here the unguarded field is the tenant identity itself.

### Impact Explanation
This crosses a tenant boundary: an attacker who only controls their own (unprivileged) shop installation can cause the host application to process a forged webhook event as if it originated from a different, victim merchant, since the shop identity is not authenticated by the HMAC. Depending on how the host app's webhook handler uses `data.shop` (e.g., to look up/modify per-merchant state), this can lead to cross-tenant data corruption or unauthorized actions being recorded against another merchant's account — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only: (1) installing the app on an attacker-controlled shop to legitimately receive at least one valid webhook body+HMAC pair (no special privilege beyond being a merchant using the app), and (2) POSTing that same body/HMAC to the app's public webhook endpoint with a forged `shop-domain` header. No access to `api_secret_key`, tokens, or TLS interception is required, so likelihood is realistic for any multi-tenant app built on this gem that trusts `WebhookMetadata#shop` for tenant-scoped effects.

### Recommendation
Bind the identity headers into the signed content, or independently verify them:
- Include `shop`, `topic`, and `webhook_id` in the HMAC-covered string (this would require a coordinated change with Shopify's webhook signing scheme), or
- At minimum, have `Registry.process`/the host app cross-check the incoming `shop-domain` header against an out-of-band trusted source (e.g., confirm the shop is an existing, installed tenant with a stored session before trusting `data.shop`) rather than trusting the header verbatim once the body HMAC passes.
- Document explicitly in `docs/usage/webhooks.md` that `WebhookMetadata#shop`, `#topic`, and `#webhook_id` are **not** authenticated by the HMAC check and must be independently validated by the consuming application before being used for tenant-scoped actions.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, receiving a legitimate webhook delivery, e.g. body `{"id":123}"` with header `X-Shopify-Hmac-Sha256: <valid-hmac>` computed by Shopify using the shared `api_secret_key`.
2. Attacker crafts a new HTTP POST to the app's webhook endpoint using the **same** raw body and the **same** valid HMAC header, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`; internally `Utils::HmacValidator.validate(request)` recomputes the signature over `request.to_signable_string` (the unchanged body) and it matches, so validation succeeds [5](#0-4) .
4. The registered handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` [6](#0-5)  and processes the forged event as if it came from the victim shop.
