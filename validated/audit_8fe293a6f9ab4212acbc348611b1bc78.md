This confirms the asymmetry: for OAuth's `AuthQuery`, `shop` is included in `to_signable_string` (the HMAC-covered payload) [1](#0-0) , but for webhooks, `Request#to_signable_string` returns only `@raw_body` while `shop` is read from an unsigned header and passed straight into `WebhookMetadata` [2](#0-1) [3](#0-2) .

### Title
Webhook `shop` domain is trusted from an unsigned header while HMAC only covers the raw body, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and is validated by `Utils::HmacValidator.validate`, but the HMAC only covers `@raw_body` — the `shop` domain, which is used as the tenant identity passed to the app's webhook handler, is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header and is never part of the signed bytes.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only [4](#0-3) . `Request#shop` is derived purely from an HTTP header with no cryptographic binding to the body or its HMAC [5](#0-4) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., the body signature) and then forwards `request.shop` unchanged into `WebhookMetadata`, which is the tenant-identifying field handed to the app's `WebhookHandler#handle` [3](#0-2) . Because every shop installed on a given app shares the same `client_secret`/`api_secret_key`, an attacker who installs the app on their own store (an ordinary, unprivileged action) receives genuine webhook deliveries with a body and HMAC that are valid under that shared secret. The attacker can replay that exact `raw_body`+HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks `raw_body` against the secret [6](#0-5) , so `Registry.process` accepts the forged request and dispatches it to the handler labeled with the victim's shop. This contrasts with `Auth::Oauth::AuthQuery`, where `shop` is explicitly folded into `to_signable_string` and thus cryptographically bound to the HMAC [1](#0-0) .

### Impact Explanation
This breaks the binding `shop_verified_by_hmac == shop_used_by_handler`: the tenant identity acted upon by the application (`WebhookMetadata.shop`) is not the identity actually authenticated by the HMAC (which only authenticates the body bytes, tenant-agnostic). Any host application that uses `data.shop` from `WebhookHandler#handle` to select which merchant's records to update, upsert, or trust (a documented and expected usage pattern for this gem) can be made to apply attacker-supplied webhook content to an arbitrary victim shop's data, i.e., cross-tenant data injection.

### Likelihood Explanation
Requires only that the attacker install the target app on their own (or any) shop — an action available to any unprivileged internet user with a Shopify account — to obtain a validly-HMAC-signed body under the shared per-app secret, and then replay it with a modified shop-domain header against the app's public webhook endpoint.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-covered payload, or otherwise cryptographically verify that the shop header matches the shop that Shopify actually signed for, e.g., by having `to_signable_string` include the shop domain header alongside the raw body, or by validating the shop against a separately-authenticated channel (mutual TLS, per-shop webhook secrets, or comparing against session state) before trusting `WebhookMetadata.shop`.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop `attacker.myshopify.com`; Shopify sends a genuine webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` plus `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays this exact request to the same endpoint but rewrites `x-shopify-shop-domain` to `victim.myshopify.com`, keeping `B` and the HMAC header unchanged.
3. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` from `to_signable_string` (body only) and it matches, so `Registry.process` does not raise `Errors::InvalidWebhookError` [7](#0-6) .
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker-controlled body `B`, causing the app to process/apply attacker content as if it originated from the victim's store.
