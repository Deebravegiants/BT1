### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, but the `shop` value it then hands to the host application's handler is read from the unauthenticated `X-Shopify-Shop-Domain` header, which is never included in the HMAC-signed payload. Because a single app's `api_secret_key` is shared across every shop that installs it, any merchant who has installed the app can obtain a validly-signed webhook body and body-only HMAC for their own store, then replay that body with a forged shop-domain header to make the host app believe the event originated from an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` returns only the raw HTTP body: [1](#0-0) 

The `shop` accessor, however, is taken straight from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header and is not part of the signed material: [2](#0-1) [3](#0-2) 

`Registry.process` verifies the HMAC using `Utils::HmacValidator.validate(request)` — which computes `HMAC(secret, raw_body)` and compares it to the `hmac-sha256` header — and, once that passes, forwards the *unverified* `request.shop` value into `WebhookMetadata` that is delivered to the app's `WebhookHandler`: [4](#0-3) 

`Utils::HmacValidator` only ever signs/verifies `verifiable_query.to_signable_string` (the raw body for webhooks), never the shop header: [5](#0-4) 

This breaks the identity binding `HMAC-authenticated bytes == bytes the handler trusts as the tenant identity`. In equality terms: the gem verifies `HMAC(secret, raw_body) == received_hmac`, but the handler subsequently trusts `header["x-shopify-shop-domain"]` as the authenticated tenant, even though `header["x-shopify-shop-domain"] ⊄ raw_body`. Since `secret` (the app's `api_secret_key`) is identical for every shop that installs the same app, an attacker who controls one installation (their own store) can compute a valid HMAC over an arbitrary body and then swap the shop-domain header to any other shop that has also installed the app, producing a webhook request that passes signature verification while claiming to originate from a victim tenant.

### Impact Explanation
This is a cross-tenant access vulnerability (Critical per the reward criteria). Any Shopify app built on this gem that uses `WebhookMetadata#shop` to select the tenant/session/store the event applies to (a standard, documented usage pattern) can be tricked into processing forged events — e.g., fake `orders/create`, `customers/create`, `app/uninstalled`, or `shop/redact` — attributed to a shop the attacker does not own or control, purely by an unprivileged user who has installed the same public app on their own store. No access token, `client_secret`, or privileged credential is required — only participation as an ordinary merchant/installer of the target app.

### Likelihood Explanation
Likelihood is moderate-to-high: the attacker only needs to install the same (often public) app on a store they control to legitimately receive a validly-signed webhook body/HMAC pair, then replay it against the app's webhook endpoint with a modified `X-Shopify-Shop-Domain` header pointed at any other shop known to use the app. No secret material needs to be extracted; the shared-secret design of the HMAC scheme combined with the header being unauthenticated is sufficient.

### Recommendation
Bind the `shop` (and `topic`/`webhook_id`, if used for authorization decisions) into the HMAC-verified material, or otherwise cross-check the header-derived `shop` against a value independently known to be associated with the specific installation before trusting it (e.g., validate the header shop against the session lookup keyed by webhook_id/topic, or require Shopify's newer verification schemes that bind headers). At minimum, document that `WebhookMetadata#shop` is unauthenticated header data and must not be used as a sole tenant identifier without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers (or waits for) any webhook, e.g. `customers/create`, and captures the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H = HMAC-SHA256(secret, B)` sent to the app's webhook endpoint.
3. Attacker resends the exact same body `B` and header `H` to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and finds it equals `H` — validation passes because the shop header is never part of `to_signable_string`: [6](#0-5) 
5. The handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` and processes the attacker-controlled body as if it were an authentic event from `victim-shop.myshopify.com`, achieving cross-tenant event injection.
