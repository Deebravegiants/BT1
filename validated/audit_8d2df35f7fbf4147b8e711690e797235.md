### Title
Reentrancy in Tron `IntentGatewayV2.fillOrder` native-token fill path lacks the reentrancy guard applied to the canonical EVM contract - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The canonical EVM `IntentGatewayV2` (`evm/src/apps/IntentGatewayV2.sol`, backed by `IntrinsicIntents.sol` / `ExtrinsicIntents.sol`) was hardened against reentrancy: `placeOrder` and `fillOrder` are marked `nonReentrant` via `ReentrancyGuardTransient`, and `_filled[commitment] = msg.sender` is now set at the very top of `_fillSameChain`/`_fillCrossChain` (Checks-Effects-Interactions) before any native-token `.call` to the solver-supplied `beneficiary` address [1](#0-0) [](fillOrder nonReentrant) [2](#0-1) [3](#0-2) . This fix is explicitly regression-tested in `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`, which demonstrates that a malicious `beneficiary` re-entering `fillOrder` during the ETH transfer is now blocked [4](#0-3) .

The separate Tron deployment of the same protocol, `evm/tron/contracts/apps/IntentGatewayV2.sol`, is a monolithic, independently-maintained fork of the same order-fill logic. It does **not** inherit `IntrinsicIntents`/`ExtrinsicIntents`/`ReentrancyGuardTransient`, and its `placeOrder` is declared without the `nonReentrant` modifier present on the mainline contract [5](#0-4) [6](#0-5) . Grepping the file confirms it independently re-implements `fillOrder`, `_filled[commitment] = ...` assignment, native-value `.call`/`_sendValue` to the beneficiary — i.e., the same reentrancy-sensitive code path that was patched in the mainline contract — but as a distinct, unguarded copy.

### Finding Description
The upstream bug class (Trader `executeTrade` calling into a user-controlled `makeOrder.market` before finalizing state) maps directly onto the Intent Gateway's fill flow: `fillOrder` sends native ETH to an attacker-controlled `beneficiary` address (a solver-facing, permissionless input from the placed `Order`) and only afterward finalizes escrow/fill-state bookkeeping. The Hyperbridge team already recognized and fixed this exact class in the canonical Solidity contract by (a) adding `nonReentrant` to `placeOrder`/`fillOrder`, and (b) moving `_filled[commitment] = msg.sender` before any external call (CEI).

The Tron fork of `IntentGatewayV2` duplicates the vulnerable fill/escrow logic without adopting either mitigation: no `ReentrancyGuardTransient`, no `nonReentrant` modifier on `placeOrder` (and, by the matching code pattern, likely `fillOrder`), and a codebase independently maintained from the audited/tested mainline `src/apps/intentsv2/*` implementation. Because the fix was implemented and tested only against the mainline EVM contracts (`IntrinsicIntentsReentrancyTest.sol` targets `evm/src/apps/IntentGatewayV2.sol`, not the Tron variant), there is no evidence the Tron deployment received equivalent protection.

### Impact Explanation
If the Tron contract's fill path sends native value (or performs external token transfers) to `beneficiary` before marking the order filled/updating escrow, an attacker-controlled beneficiary contract can re-enter `fillOrder` (or a related state-mutating function) during that transfer to double-claim escrowed inputs or drain protocol/transaction fees — the same theft primitive described in the original report and confirmed exploitable pre-fix in the mainline contract's now-removed vulnerable pattern. This is a direct theft-of-funds vector against user escrow and solver payouts on the Tron deployment.

### Likelihood Explanation
Reachable by any solver/filler submitting a single `fillOrder` transaction with a malicious contract as `order.output.beneficiary` — no privileged role required, matching the "unprivileged... intent solver" reachability criterion. Likelihood is high if the Tron contract is deployed and live, since the attack requires no proof forgery, governance, or off-chain trust assumptions — only a contract-controlled beneficiary address, exactly the historical attack surface already fixed elsewhere in the codebase.

### Recommendation
Bring `evm/tron/contracts/apps/IntentGatewayV2.sol` to parity with the hardened mainline contract:
1. Add a reentrancy guard (`nonReentrant`) to `placeOrder`, `fillOrder`, and any other externally-callable state-mutating entry points that move value to user-controlled addresses.
2. Apply Checks-Effects-Interactions: set `_filled[commitment]` (and any partial-fill/escrow bookkeeping) before performing native-value transfers or external calls to `beneficiary`.
3. Add regression tests mirroring `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol` against the Tron contract to confirm the fix and prevent future drift between the two codebases.
