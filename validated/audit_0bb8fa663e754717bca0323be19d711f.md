## Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC that covers only the raw request body, then trusts the unauthenticated `shop-domain` header as the tenant identity passed to the app's handler. An attacker who can obtain any validly-signed webhook body/HMAC pair (trivially, by installing the app on their own store and triggering a webhook) can replay that exact body+HMAC while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header value. The HMAC check still passes because the header is never part of the signed payload, so the handler executes believing the event originated from a different, victim merchant.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

- `hmac` reads the `hmac-sha256` header.
- `to_signable_string` returns only `@raw_body`.
- `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated headers, with no cryptographic binding to the HMAC.

`Utils::HmacValidator.validate` computes the signature strictly over `to_signable_string` (i.e., the body) and compares it to the received HMAC: [2](#0-1) 

`Registry.process` validates only this body-bound HMAC, then immediately trusts `request.shop` (the header) as the tenant identity forwarded to the app's webhook handler: [3](#0-2) 

The broken identity binding, expressed as an equality that should hold but doesn't:

```
shop_authenticated_by_HMAC (over raw_body only)  !=  shop_used_by_handler (request.shop, from unauthenticated header)
```

Because the `shop-domain` header is not part of the signed bytes, any attacker who possesses one valid `(raw_body, hmac)` pair — which they can generate legitimately for their own store by installing the app and firing a webhook (e.g., `orders/create`) with attacker-chosen body content — can replay that exact body and HMAC to the app's webhook endpoint while changing only the `shop-domain` header to a victim merchant's domain. `HmacValidator.validate` will still succeed (it never inspects the header), and `WebhookMetadata.shop` will be set to the victim's domain, so the app processes attacker-controlled data as if it came from the victim tenant — a cross-tenant spoofing vector at the gem's core webhook trust boundary.

### Impact Explanation
This is a cross-tenant integrity/authentication issue: the gem hands the host application data tagged with an arbitrary, attacker-chosen shop identity while claiming it passed cryptographic verification. Any app that uses `WebhookMetadata#shop` (as documented/intended, e.g., to route order/customer/GDPR events per-tenant, update per-shop state, or key idempotent storage) can be made to attribute attacker-controlled webhook payloads to a different merchant's tenant, meeting the "cross-tenant access" bar via data poisoning of the receiving tenant's webhook-driven state.

### Likelihood Explanation
Medium-to-High: the only prerequisite is the ability to generate one legitimately-signed webhook (trivial for any developer/attacker who installs the app on a store they control, since Shopify will sign and deliver the webhook with the app's real secret) and the ability to POST an HTTP request to the app's public webhook endpoint with a modified header — both are unprivileged-internet-user actions requiring no access token, `client_secret`, or leaked credential.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the HMAC-verified signable content, or otherwise cryptographically tie the header-derived tenant identity to the signed body (e.g., include the shop domain in the string that's HMAC'd, or require the caller to additionally verify the header against a separately-authenticated channel such as a per-shop shared secret or the API's webhook subscription id). At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted for tenant attribution without additional verification (e.g., cross-checking against a shop already known to be installed with a matching webhook subscription id from the GraphQL Admin API).

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and trigger any webhook topic the app subscribes to (e.g. `orders/create`), capturing the exact raw request body Shopify sends and its `x-shopify-hmac-sha256` header value. This HMAC is valid because Shopify signs it with the app's real `client_secret`.
2. Replay this exact captured request to the app's public webhook endpoint, keeping the body and `x-shopify-hmac-sha256` header identical, but changing the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the unchanged raw body) and successfully matches the replayed HMAC header — see `lib/shopify_api/webhooks/registry.rb` line 190 and `lib/shopify_api/utils/hmac_validator.rb` lines 12-31.
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `request.shop` now returns `"victim-shop.myshopify.com"` — see `lib/shopify_api/webhooks/registry.rb` lines 198-199 and `lib/shopify_api/webhooks/request.rb` lines 20-23. The app processes attacker-controlled data attributed to the victim tenant, despite the HMAC check having "passed."

          received_signature = verifiable_query.hmac
