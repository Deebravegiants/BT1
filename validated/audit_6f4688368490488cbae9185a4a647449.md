### Title
Webhook HMAC only covers the request body, not the `shop-domain` header — the `shop` field is unauthenticated and can be spoofed cross-tenant - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking `Utils::HmacValidator.validate(request)`, but the HMAC only authenticates the raw request body. The `shop` (tenant identity) that is handed to the app's `WebhookHandler` comes from a separate, unauthenticated HTTP header and is never bound to the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e. the body) and compares it to the `hmac` header: [2](#0-1) 

The `shop` accessor, however, is read straight from the `shop-domain`/`x-shopify-shop-domain` header, which is completely outside the HMAC's coverage: [3](#0-2) 

`Registry.process` validates the HMAC and then forwards `request.shop` — the unauthenticated header value — directly into `WebhookMetadata`, which is the tenant-identifying field the host application's handler will use (e.g., to look up which shop's session/data to mutate): [4](#0-3) [5](#0-4) 

This is structurally identical to the H-7 bug class: two values that must be bound together for a security decision (the signed payload and the tenant/shop identity attached to it) are computed/verified independently, and the check that is performed (`hmac == HMAC(body, secret)`) does not establish the equality that the code actually relies on (`request.shop == shop that produced this body`).

**Exploitation path:** Any merchant who has installed the app (i.e., an "unprivileged" party with respect to *other* tenants of the same app, but a legitimate account with respect to their own shop) can trigger ordinary webhook-firing actions (e.g. create/update an order or product) on their own store. Shopify will POST a body plus a valid `X-Shopify-Hmac-SHA256` computed with the app's shared `client_secret`, together with an `X-Shopify-Shop-Domain` header identifying the attacker's own shop. Because the HMAC never covers the shop header, the attacker can capture this genuinely-signed `(body, hmac)` pair and replay it directly to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body against the shared secret), so `Registry.process` accepts the forged request and calls the handler with `WebhookMetadata.shop == victim_shop`, even though the payload was never actually produced for that shop.

### Impact Explanation
This breaks the identity binding `shop_authenticated_by_hmac == shop_used_for_tenant_scoping`. If the host application relies on `WebhookMetadata#shop` (as the gem's own documentation and webhook usage pattern encourages) to select which tenant's stored session/data the webhook payload should be applied to, an attacker with a legitimate install on their own shop can inject cross-tenant events — writing or corrupting data under another merchant's identity, or triggering business logic (order/fulfillment/customer-redaction handlers) against a shop that never sent the payload. This is a cross-tenant integrity issue rooted entirely in this gem's webhook verification design (`Request`/`HmacValidator`/`Registry`), not a misuse of a documented API by the host app.

### Likelihood Explanation
Any shop with the app already installed can produce this attack using only ordinary store actions plus a generic HTTP client capable of setting custom headers — no access to `api_secret_key`, tokens, or privileged accounts is required, and no host-application misconfiguration is needed, since the vulnerable code is exactly how the gem parses and forwards `shop`.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) values in the data that is HMAC-verified, or otherwise cryptographically bind them to the signed body (e.g., derive them only from a payload field that is itself covered by the signature, or require the host to independently confirm the shop via a signed source such as the session/token before trusting `WebhookMetadata#shop`). At minimum, document clearly that `shop` in `WebhookMetadata` is unauthenticated and must not be used for tenant-scoping decisions without additional verification.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Perform an action that fires a subscribed webhook topic (e.g. `orders/create`), capturing the raw POST body `B` and the resulting valid header `X-Shopify-Hmac-SHA256: H = HMAC-SHA256(secret, B)` sent by Shopify to the app's webhook endpoint.
3. Replay a new POST to the same app webhook endpoint with:
   - Body: `B` (unchanged)
   - `X-Shopify-Hmac-SHA256: H` (unchanged, still valid since it only covers `B`)
   - `X-Shopify-Shop-Domain: victim.myshopify.com` (forged)
   - `X-Shopify-Topic` / `X-Shopify-Webhook-Id` left as desired.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which passes because it only checks `B` against `H`, per `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <parsed B>, ...)`, per `lib/shopify_api/webhooks/registry.rb:198-199`, causing the host application to process attacker-supplied data under the victim shop's identity.
