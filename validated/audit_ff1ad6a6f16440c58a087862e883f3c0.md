### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` for HMAC verification, while `ShopifyAPI::Webhooks::Registry.process` trusts the separate, HMAC-unprotected `shop-domain` header as the tenant identity passed to the app's handler. This breaks the intended identity binding: `shop header used by handler == shop bound by HMAC`.

### Finding Description
`Request#hmac` and `Request#to_signable_string` only cover the raw webhook body: [1](#0-0) 

`Request#shop` simply reads the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` (which signs/verifies `to_signable_string`, i.e. only the body) and then unconditionally forwards `request.shop` — the unauthenticated header — to the app's webhook handler as the tenant identity: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` confirms that the HMAC computed over `to_signable_string` (body only) matches, with no reference to the shop header at all: [4](#0-3) 

The handler contract (`WebhookMetadata#shop`) exposes this unauthenticated value as the shop identity for the app's business logic: [5](#0-4) 

Because the app's `client_secret`/webhook secret is shared across all shops installing the app (it is not shop-specific), an unprivileged user who installs the app on their own shop can obtain a legitimately-signed webhook (valid `raw_body` + valid HMAC) for an event they trigger themselves. They can then replay that exact `raw_body`/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still passes (body/HMAC are genuine and untouched), but `request.shop` — and therefore `WebhookMetadata#shop` delivered to the app's handler — now reports the victim's domain. This is precisely the "field acted on but not covered by the HMAC" analog described in the report: the storage/binding key used by the consumer (`shop`) is not the same one authenticated by the signature (`raw_body`), just as the audit finding used the `NAV` key where `LAST_HARVEST_PERFORMANCE_FEE_TIME` was required.

### Impact Explanation
This crosses the shop/tenant boundary: it allows an attacker who legitimately installs the app (unprivileged, no leaked credentials required) to inject attacker-controlled webhook payloads that are processed by the merchant application as if they originated from an arbitrary victim shop. Depending on how the host application implements the handler (e.g., using `data.shop` to look up sessions, update shop-scoped records, or process mandatory GDPR webhooks like `shop/redact`), this can lead to cross-tenant data corruption, spoofed events, or triggering shop-scoped actions against a shop the attacker does not control — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
High likelihood of exploitability by any unprivileged internet user with their own (even free/dev) shop that has installed the app: they can trigger any subscribed webhook topic on their own store to obtain a validly-signed `raw_body`/HMAC pair, then simply POST that captured body with a different `shop-domain` header value to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only participation as a normal merchant.

### Recommendation
Bind the `shop-domain` (and other trust-relevant headers such as `webhook-id`/`api-version`, if they influence handler behavior) into the signed material, or otherwise cryptographically tie the header to the verified body — e.g., include the shop domain in `to_signable_string`, or independently confirm the shop domain against a value stored during OAuth for the API key. At minimum, document and enforce that consumers must correlate `data.shop` with a known/authorized shop record rather than trusting it as-is post-HMAC validation, and consider only accepting `shopify-shop-domain` when it matches shops already registered for the API key/session store.

### Proof of Concept
1. As an unprivileged developer, install the app on `attacker.myshopify.com`.
2. Trigger a subscribed webhook topic (e.g., `orders/create`) on `attacker.myshopify.com`; Shopify sends a POST with a genuine `raw_body`, `X-Shopify-Hmac-Sha256`, and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Capture `raw_body` and the valid `X-Shopify-Hmac-Sha256` value.
4. Replay a POST to the app's webhook endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)` — which passes because it only checks `raw_body` against the HMAC — then invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled parsed body>, ...)`, causing the app to process attacker-controlled data under the victim shop's identity.         def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac

        end
