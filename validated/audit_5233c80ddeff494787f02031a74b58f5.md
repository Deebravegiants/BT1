Confirmed identity-binding break: the webhook `shop` used to route/authenticate the callback is **not part of the HMAC-signed material**.

### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing HMAC replay across shops - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and the shop identity comes from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in that signable string. `Utils::HmacValidator.validate` only checks the HMAC against the raw body, so the `shop` value handed to the host application's webhook handler is unauthenticated with respect to the signature.

### Finding Description
`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)` [1](#0-0) , which computes `HMAC(secret, request.to_signable_string)` and compares it to the `hmac` header [2](#0-1) . `Request#to_signable_string` is defined to be exactly `@raw_body` [3](#0-2) , while `Request#shop` is read straight from the `shopify-shop-domain` header with no cryptographic binding to that HMAC [4](#0-3) . The identity equality that should hold is: `shop_bound_by_hmac == shop_used_by_handler`. Here, `shop_used_by_handler` (the header value passed into `WebhookMetadata` and to the app's handler) is **not** derivable from or checked against anything the HMAC covers — only the body bytes are authenticated [5](#0-4) .

Because Shopify signs webhooks with a single per-app secret shared across all shops installed on that app, any unprivileged actor who can trigger (or replay) one legitimately-signed webhook delivery for any shop (e.g., their own installed dev store, or a captured webhook payload with an HMAC that happens to validate for a given body) can resend it with the `shopify-shop-domain` header rewritten to a different, victim shop. The gem will treat the request as authentic for the attacker-chosen shop because the header is never covered by the signature.

### Impact Explanation
This is a cross-tenant identity-binding failure: the `shop` value that host applications use to look up sessions/tokens for that tenant (per the library's documented pattern of `WebhookMetadata#shop`) can be forged independent of the HMAC. If the host app uses this untrusted `shop` field to select which merchant's data/session to act on (which is the intended and documented use of `WebhookMetadata.shop`), an attacker can cause cross-tenant data operations to be attributed to/executed against a shop they don't own, without needing that shop's credentials.

### Likelihood Explanation
Exploitation requires only that the attacker possess one validly-HMAC'd request body/signature pair (trivial for any shop the attacker controls, since app secrets are shared across all installs of the same app) and the ability to send an HTTP request with attacker-controlled headers to the host application's webhook endpoint — no special privilege, TLS interception, or credential theft is needed. This satisfies the "unprivileged internet user" bar.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook-id`) values in the signable material verified by the HMAC, or otherwise cryptographically bind the shop-domain header to the signed body before it is trusted for tenant-scoped decisions. At minimum, `Request#to_signable_string` should not rely solely on `@raw_body` when downstream consumers use header-derived fields (like `shop`) as tenant identity for privileged actions.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they legitimately control) and captures a real webhook delivery: raw body `B` and its valid `shopify-hmac-sha256` header `H = HMAC(secret, B)`.
2. Attacker replays a POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` from `to_signable_string` (`= @raw_body = B`) [3](#0-2)  and it matches `H`, so validation passes [6](#0-5) .
4. `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is `"victim-shop.myshopify.com"` from the forged header [5](#0-4) , even though the HMAC never authenticated that value.
