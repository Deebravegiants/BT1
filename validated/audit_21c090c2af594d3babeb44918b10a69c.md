### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity is trusted from unauthenticated headers while only the raw body is HMAC-verified, allowing cross-tenant webhook shop-spoofing via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` by signing only `@raw_body` in `to_signable_string`, while `shop`, `topic`, `api_version`, and `webhook_id` are all read from unauthenticated HTTP headers via `shopify_header`. `Registry.process` validates the HMAC over the body only, then dispatches `request.shop` straight to the app's webhook handler as the tenant identifier, breaking the binding `shop authenticated == shop acted on`.

### Finding Description
`Utils::HmacValidator.validate` calls `to_signable_string` on the `VerifiableQuery` and computes/compares an HMAC against it: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body bytes: [2](#0-1) 

But the `shop`, `topic`, `api_version`, and `webhook_id` accessors used by the rest of the library are pulled straight from HTTP headers that are never part of the signed payload: [3](#0-2) [4](#0-3) 

`Registry.process` validates the HMAC (over body only), then immediately trusts `request.shop` (from the unsigned header) as the tenant identity passed to the app's handler: [5](#0-4) 

This means the equality the library implicitly claims — "HMAC-verified request == shop the payload is attributed to" — does not hold. The bytes that are cryptographically verified (raw body) are disjoint from the field (`shopify-shop-domain` header) that determines which merchant/tenant the webhook data is attributed to when passed to `WebhookMetadata`.

### Impact Explanation
Because the shop header is outside the HMAC's coverage, any party who can produce one validly-signed webhook body+HMAC pair for topic X (e.g. by legitimately receiving one webhook delivery, or via a replay/relay of a previously captured legitimate request) can resubmit it to the app's webhook endpoint with an arbitrary `shopify-shop-domain` (or `x-shopify-shop-domain`) header value while keeping the same body and HMAC — since `HmacValidator.validate` only checks the raw body, the forged request still passes validation. The app's handler then processes attacker-chosen data under a shop identity of the attacker's choosing, causing cross-tenant data misattribution (e.g., writing "shop B's" webhook data into shop A's tenant records, or vice versa) — a cross-tenant access issue, matching the "shop authenticated versus shop stored/acted on" binding-break pattern in the analog rules.

### Likelihood Explanation
Exploitation likelihood is Low: it requires the attacker to already possess one valid `(raw_body, hmac)` pair signed by Shopify (e.g. from a previously delivered webhook to the same app, since `client_secret` is never exposed to an unprivileged attacker), then replay it with a spoofed shop header at the app's webhook endpoint before/without any nonce or timestamp/replay protection in this gem's `Webhooks::Request`/`Registry` code (no `webhook-id` uniqueness or freshness check is enforced by the library itself).

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed payload, or otherwise cryptographically bind them to the raw body (e.g., verify a per-request nonce and require the app to check `webhook_id` uniqueness/freshness). At minimum, document clearly that `Registry.process`'s HMAC validation does not authenticate the shop/topic headers, and provide a way to reject to replayed webhook IDs so that host applications don't unknowingly trust `request.shop` as an authenticated tenant identifier.

### Proof of Concept
1. Attacker obtains one legitimate webhook delivery to the target app (body `B`, `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: shop-a.myshopify.com`), where `H = HMAC_SHA256(client_secret, B)`.
2. Attacker replays the same request to the app's webhook endpoint but sets `x-shopify-shop-domain: shop-b.myshopify.com` (or any other shop string), keeping body `B` and hmac `H` identical.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely over `request.to_signable_string` (i.e., `B`) — this succeeds because the body/hmac pair is unchanged. [6](#0-5) 
4. `request.shop` returns `shop-b.myshopify.com` from the spoofed header, and `WebhookMetadata` is built with this unverified shop value, which the app's handler treats as the authenticated tenant for the delivered body `B`. [7](#0-6)
