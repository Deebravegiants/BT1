### Title
Unsafe raw `token.call` transfers without codesize/return-value checks in Tron `IntentGatewayV2.withdraw` and `SweepDust` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron port of `IntentGatewayV2` escrows input tokens using OpenZeppelin's `SafeERC20.safeTransferFrom` (which validates the target has code and checks the boolean return value), but releases escrowed funds in `withdraw()` and `SweepDust` handling using raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` calls that only check `success`, never the returned boolean nor contract existence. This is the same bug class as the referenced report ("Lack of codesize check" / unchecked ERC20 return data on solmate's `safeTransferLib`), applied to fund-release paths triggered by permissionless relayer message delivery.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` is invoked from `onAccept` for `RequestKind.RedeemEscrow`/`RefundEscrow` after `authenticate(incoming.request)` succeeds — i.e. any relayer can deliver a validly-signed/verified cross-chain message that triggers release of escrowed input tokens to a beneficiary: [1](#0-0) 

For each token the code does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
and unconditionally decrements `_orders[body.commitment][token] -= amount;` regardless of whether the token's `transfer()` actually moved funds. The same unsafe pattern is used for the transaction-fee payout and in the `SweepDust` branch: [2](#0-1) 

By contrast, the same file uses the codesize/return-value-safe `SafeERC20` library when *escrowing* tokens on `placeOrder`: [3](#0-2) 

A raw `.call` to a token that returns `false` instead of reverting on failure (a well-documented ERC20 non-compliance pattern, e.g. tokens with paused/blacklist logic that return `false`), or to an address with no deployed code, will report `success == true` (empty returndata, non-reverting), even though no tokens were actually transferred. The code treats this as a successful payout and permanently deletes the escrow accounting (`_orders[...] -= amount`, `delete _orders[...][TRANSACTION_FEES]`), so the beneficiary (solver or user) never receives the tokens and there is no way to re-claim them through the intended path — the balance is stuck in the gateway and only recoverable via a `SweepDust` governance action (which pays the amount to a governance-chosen beneficiary, not the original solver/user).

### Impact Explanation
This breaks the fund-release guarantee of the intents escrow: a solver who correctly filled an order, or a user awaiting refund/cancellation, can have their escrow marked as released/refunded while the underlying tokens never leave the contract, resulting in a permanent loss of funds for the legitimate beneficiary. This is reachable through the core cross-chain intent settlement path (`RedeemEscrow`/`RefundEscrow` via `onAccept`), not through any privileged/admin function, matching a Medium/High severity fund-freezing/loss class.

### Likelihood Explanation
The trigger token/asset is chosen by the order creator when the order is placed, and once the token was accepted for escrow (it must be a real ERC20 contract to succeed via `safeTransferFrom` at deposit time), a wide range of already-deployed, non-fully-ERC20-compliant tokens (returning `false` rather than reverting on failed transfers) are common enough in production DeFi ecosystems that this is a realistic risk for any token whose `transfer` can return `false` under specific conditions (e.g., paused, blacklist, insufficient allowance edge-cases handled non-standardly). No privileged actor is required — normal relayer delivery of a legitimately verified cross-chain message triggers the vulnerable code path.

### Recommendation
Replace the raw `token.call(...)` patterns in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer` (already imported and used elsewhere in the same file for `safeTransferFrom`), which enforces both contract-existence and ERC20 boolean-return-value checks, consistent with the escrow deposit path.

### Proof of Concept
1. A user creates an order whose input token is a real ERC20 contract that is capable of returning `false` on `transfer()` under some (even rare) condition instead of reverting (e.g. paused/blacklist logic), and places it via `placeOrder` (escrow succeeds via `safeTransferFrom`).
2. A solver fills the order on the destination chain; the source `IntentGatewayV2` (Tron) receives the authenticated `RedeemEscrow` request and calls `withdraw()`.
3. If the token's `transfer()` call returns `false` (without reverting) at that moment (e.g., beneficiary temporarily blacklisted, or any non-standard failure condition), `token.call(...)` still returns `success == true`.
4. `withdraw()` proceeds to decrement `_orders[commitment][token]` and emits `EscrowReleased`, but the solver's balance never increased — the tokens are stuck in the gateway with no code path to return them to the solver.
