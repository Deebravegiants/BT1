### Title
Zero-output sell rounds a trader's token amount away without reverting, permanently burning tokens for zero LT - (File: packages/contracts/src/Router.sol)

### Summary
`Router._computeSell` truncates the constant-product output with plain integer division and `Router.sell` never checks that the computed `assetOut` is non-zero before pulling the trader's tokens into the pair. Because the pair's `reserveToken` is a huge virtual reserve (1B tokens, 18-dp), a small enough `amountIn` can floor `k / newReserveToken` to the same value as `k / reserveToken`, making `assetOut == 0`. The trader's tokens are still transferred into the pair and burned from their balance, but they receive `0` LT back — the exact rounding-to-zero pattern the external Lido report flags (a user "burns" their input for zero output) with no guard preventing it.

### Finding Description
`Router.sell` only guards against a zero *input*, not a zero *output*: [1](#0-0) 

`_computeSell` computes `assetOut = reserveAsset - (k / newReserveToken)` with floor division; there is no `require(assetOut > 0)`. Given the production seeding described in `docs/contracts-scope.md`, `reserveToken` is seeded at the full `1_000_000_000e18` virtual reserve (`Bonding._deployAndSeed`) even though only 750M tokens are real/sellable: [2](#0-1) 

With `reserveToken` on the order of `1e27` and `k` scaled accordingly, `k / newReserveToken` and `k / reserveToken` land on the same floored integer for sufficiently small `amountIn` (dust-sized token sells), so `assetOut` computes to `0`. `Router.sell` still executes `IERC20(token).safeTransferFrom(to, pairAddr, amountIn)` before computing `assetOut`, consuming the trader's tokens unconditionally, then calls `IPair(pairAddr).transferAsset(to, 0)` and `IPair(pairAddr).swap(amountIn, 0, 0, 0)` — both succeed as no-ops on the LT leg.

`Bonding.sell` (the only caller with `BONDING_ROLE`) forwards `assetOut` straight into the caller-supplied `amountOutMin` check: [3](#0-2) 

If the trader (or `Zap.sell`, which is the actual unprivileged entry point) passes `amountOutMin = 0` — which `Zap._sellInternal` does when routing to `_sellOnCurve`: [4](#0-3) 

—then `assetOut < amountOutMin` (`0 < 0`) is false, so the transaction does not revert on the slippage check. `Zap._sellInternal` then proceeds to call `IBounceLeveragedToken(lt).redeem(address(this), 0, 0)` and continues the sell path, ultimately either reverting later on `BelowMinAmount` (if the LT/USDC floor check catches it) or emitting a `Sell` event with `usdcOut == 0` while the trader's `tokenAmount` has already been irrevocably transferred into the curve pair.

### Impact Explanation
A trader who sells a small enough quantity of a launched token (dust relative to the 1B virtual reserve) has those tokens pulled into the `Pair` and effectively burned from their control, while receiving zero LT and — after fees/floor checks — potentially zero USDC. This is a direct loss of trader funds with no recovery path: the tokens sit in the `Pair` contract, are not returned, and the only exit for that value is via later trades against the curve (benefiting other traders, not the victim). This matches the "Medium" bug class in the source report: rounding permits value to be destroyed/donated with no protective check, satisfying the "concrete theft or permanent freezing of trader funds" acceptance criterion.

### Likelihood Explanation
The trigger is a single unprivileged call: `Zap.sell(tokenAddress, tokenAmount, minUsdcOut=0)` with `tokenAmount` sized so that `k / (reserveToken + tokenAmount) == k / reserveToken` under floor division. Given `reserveToken` is on the order of `1e27` wei (1B tokens × 1e18), the "dead zone" of `amountIn` values that round to zero output can be non-trivial in absolute token-wei terms even though it is economically tiny (a small fraction of a token). This can happen accidentally (e.g., a UI computing a partial-sell amount, or a user attempting to sell a tiny leftover balance) or be deliberately exploited to grief other users' balances into the pool with no benefit to the attacker beyond forcing dust losses. It requires no special privileges, no pre-conditions besides holding any non-zero token balance and calling `Zap.sell` with `minUsdcOut = 0` (the default UI slippage value for the graduation-trigger branch, and a value any caller may freely choose otherwise).

### Recommendation
Add an explicit zero-output guard in `Router._computeSell`/`Router.sell` (mirroring the existing `ZeroAmount` guard on input), e.g. `if (assetOut == 0) revert ZeroAmount();`, so any sell that would round to zero LT reverts before tokens are pulled into the pair. Apply the same defensive check to `_computeBuy`'s `tokensOut` for symmetry, even though the buy path is less exposed due to `Zap`'s LT-floor pre-check.

### Proof of Concept
1. Launch a token via `Bonding.createToken`/`Zap.createToken` so the pair is seeded with `virtualReserveToken = 1_000_000_000e18`, `realTokenAmount = 750_000_000e18` (per `Bonding._deployAndSeed`, `packages/contracts/src/Bonding.sol:470-480`).
2. Acquire a small token balance (e.g., via a buy) and compute the smallest `tokenAmount` such that `k / (reserveToken + tokenAmount) == k / reserveToken` (floor-division dead zone); at `reserveToken ≈ 1e27` this dead zone spans a range of wei-level `tokenAmount` values.
3. Call `Zap.sell(tokenAddress, tokenAmount, 0)` (or directly `Bonding.sell(tokenAmount, tokenAddress, 0, trader)` through an allow-listed router).
4. Observe: `IERC20(token).safeTransferFrom` succeeds and removes `tokenAmount` from the caller's balance and moves it into the `Pair`; `Router._computeSell` returns `assetOut == 0`; `Bonding.sell`'s `assetOut < amountOutMin` check (`0 < 0`) does not revert; the trader's tokens are gone and they received no LT/USDC in return, confirmed by comparing `Token(tokenAddress).balanceOf(trader)` and `lt.balanceOf(trader)`/USDC balance before and after the call — this reproduces the "burn for zero output" rounding condition from the source report, adapted from Lido's `Lido.sol#L522` `burnShares`-rounds-to-zero pattern onto alt.fun's curve-sell path.

    /// @notice Tokens in → LT out.
    function sell(
        uint256 amountIn,
        address token,
        address to
    ) external onlyRole(BONDING_ROLE) returns (uint256 tokensIn, uint256 assetOut) {
        if (amountIn == 0) revert ZeroAmount();

        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        tokensIn = amountIn;

        IERC20(token).safeTransferFrom(to, pairAddr, amountIn);

        assetOut = _computeSell(pairAddr, amountIn);

        IPair(pairAddr).transferAsset(to, assetOut);

        IPair(pairAddr).swap(amountIn, 0, 0, assetOut);
    }

    function _computeSell(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 assetOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        uint256 newReserveToken = reserveToken + amountIn;
        assetOut = reserveAsset - (k / newReserveToken);
    }

    /// @notice Sell tokens on the curve. Router-only.
    function sell(
        uint256 amountIn,
        address tokenAddress,
        uint256 amountOutMin,
        address trader
    ) external onlyRouter nonReentrant returns (uint256) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.creator == address(0)) revert TokenNotTrading();
        if (info.lifecycle == Lifecycle.Graduating) revert TokenIsGraduating();
        if (info.lifecycle != Lifecycle.Curve) revert TokenNotTrading();
        // A graduatable curve token must graduate, not sell back below the
        // threshold. The user-facing router triggers graduation up front via
        // `triggerGraduation`; rejecting here stops any router that skipped
        // that step from un-ripening a ready graduation.
        if (canGraduate(tokenAddress)) revert TokenIsGraduating();

        (, uint256 assetOut) = $.router.sell(amountIn, tokenAddress, msg.sender);
        if (assetOut < amountOutMin) revert SlippageExceeded();

        (uint256 newCurveSupply, uint256 newLtReserve) = _getCurveState(tokenAddress);
        emit Trade(tokenAddress, trader, false, assetOut, amountIn, newCurveSupply, newLtReserve);
        return assetOut;
    }
