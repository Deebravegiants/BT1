### Title
Webhook shop-domain header is not covered by HMAC validation, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop` (and `topic`/`webhook_id`) values used to attribute and dispatch the webhook are read from unauthenticated HTTP headers. `Registry.process` validates only the body signature and then hands the header-derived `shop` straight to the app's webhook handler, so the "shop" identity that the HMAC check certifies and the "shop" identity the handler acts on are never bound to each other.

### Finding Description
`Request#to_signable_string` returns solely `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `webhook_id`, `api_version`) are pulled directly from HTTP headers, none of which are part of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC over the body via `Utils::HmacValidator.validate(request)` and then constructs `WebhookMetadata` using `request.shop`, which was never checked against the signature: [3](#0-2) 

`HmacValidator.validate` only recomputes and compares the signature over `to_signable_string` (the raw body), never over headers: [4](#0-3) 

The broken identity binding, stated as an equality: the gem treats `hmac_valid_for(raw_body) == true` as proof that `shop_header == originating_shop`, but these are independent facts — HMAC validity only proves the body wasn't tampered with by someone lacking `api_secret_key`; it says nothing about which shop the body actually belongs to.

Concretely: any merchant who installs the app on their own store (an unprivileged, non-credentialed action relative to this gem) legitimately receives real webhook deliveries with valid `X-Shopify-Hmac-Sha256` signatures for their own shop's body. Because the signature never covers `X-Shopify-Shop-Domain`, that same (body, hmac) pair remains valid if replayed to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop. `Utils::HmacValidator.validate` still returns `true` (it only checks the body), and `Registry.process` dispatches to the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook authenticity: an app built on this library, relying on `request.shop`/`WebhookMetadata#shop` from `Registry.process` as an authenticated tenant identifier, can be made to process attacker-supplied event data under a victim shop's identity — i.e., cross-tenant data injection/corruption (e.g., triggering shop-scoped side effects, uninstall/GDPR-style flows, or business logic keyed by `shop`) without ever possessing the victim's credentials. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that trusts `WebhookMetadata#shop` from this library as the sole tenant identifier (which is the documented usage pattern — `Registry.process` is the library's canonical entry point for webhook handling). The attacker only needs to be able to install the app on an arbitrary/free shop to obtain one valid `(raw_body, hmac)` pair, then replay it with a different `shop-domain` header value; no secret key, access token, or elevated privilege is required.

### Recommendation
Bind the shop identity into the signed material, or otherwise cross-check it against a trusted source before dispatch:
- Include `shop-domain` (and ideally `topic`/`webhook-id`) in the HMAC-covered content, or
- After signature validation, require the caller/handler to confirm `request.shop` matches a shop the app has an active, previously-established session/installation for, rather than trusting the header value implicitly.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook event, capturing the raw POST body `B` and the valid `X-Shopify-Hmac-Sha256` header `H` Shopify sent.
2. Replay a request to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim.myshopify.com", hmac-sha256: H...})` is built; `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`.
4. `ShopifyAPI::Webhooks::Registry.process` invokes the app handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: JSON.parse(B), ...)`, causing the app to act as if the event originated from `victim.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
