### Title

Unvalidated route pool invokes attacker code under the swapper’s authorization - (File: contracts/swap-aggregator/src/execute/mod.rs)

### Summary

The swap router treats each route-supplied pool address as a trusted venue endpoint and invokes it without checking a venue/pool allowlist. During that invocation, attacker-controlled pool code can request additional token transfers from the swapper; transaction simulation records those transfers as children of the swapper’s signed authorization tree, so a poisoned route can drain unrelated wallet tokens if the generated tree is signed. [1](#0-0) [2](#0-1) 

### Finding Description

`execute_strategy` requires sender authorization, decodes caller-provided `StrategyPayload`, resolves the route’s token and minimum-output entries, and executes every packed instruction. [3](#0-2) 

For each swap instruction, `idx_a` becomes `hop.pool` directly from the route’s `assets` registry, and the hop is dispatched solely according to the caller-selected venue enum. [4](#0-3) 

The dispatch selects an adapter by venue but performs no check that `hop.pool` belongs to that venue or appears in a trusted pool registry. [5](#0-4) 

Venue adapters then invoke that attacker-selected contract; for example, Phoenix invokes `hop.pool.swap`. [6](#0-5) 

The controller-facing path has the same exposure: `swap_tokens` passes caller-provided `swap` bytes to the configured router while authorizing only the controller’s expected input transfer. [7](#0-6) 

A regression test demonstrates that a rogue pool can call `token.transfer(victim, attacker, amount)` during the route and that Soroban simulation attaches this unexpected transfer beneath the victim’s `swap_collateral` authorization. [8](#0-7) [9](#0-8) 

### Impact Explanation

This is an on-chain SSRF analogue: user-controlled route data causes protocol code to invoke an arbitrary contract under a transaction where the swapper’s authorization is active. The malicious venue can satisfy the router’s positive-output checks while simultaneously adding an unrelated transfer from the swapper to the attacker, causing theft of wallet funds beyond the declared swap input. [10](#0-9) [11](#0-10) 

The measured-output checks protect routed token accounting, but they do not bound unrelated authorization children introduced by third-party route code. [12](#0-11) [13](#0-12) 

### Likelihood Explanation

An unprivileged attacker can deploy a malicious contract, encode its address as a pool in an otherwise valid route, and distribute that route through a quote UI or payload-sharing flow. Execution requires the victim to sign the expanded authorization tree produced by simulation, so the attack depends on insufficient authorization-tree inspection rather than compromising a privileged account. [14](#0-13) [15](#0-14) 

### Recommendation

Bind each venue opcode to an explicitly approved pool registry or immutable venue deployment, and reject route-supplied pool addresses outside that registry before dispatch. If arbitrary pools must remain supported, the router should prevent user-auth-dependent calls from executing under the sender’s authorization context, and all signing clients must enforce that the authorization tree contains only the expected input transfer. [5](#0-4) [13](#0-12) 

### Proof of Concept

1. The attacker deploys a contract implementing the selected venue’s swap ABI and stores `(victim, unrelated_token, attacker, amount)` as its theft plan. [16](#0-15) 
2. The attacker constructs route bytes whose `assets` registry contains the malicious contract as the hop pool and normal listed assets as `token_in`/`token_out`. [17](#0-16) 
3. The victim invokes the composed path through `swap_collateral`, or calls `execute_strategy` directly; the router invokes the route-selected pool while executing the swap. [7](#0-6) [4](#0-3) 
4. During the venue call, the malicious contract invokes `unrelated_token.transfer(victim, attacker, amount)`, and simulation records that call as a child of the victim’s swap authorization. [18](#0-17) 
5. If the victim signs that simulated tree, enforcement permits the child transfer; the repository test shows the unrelated wallet balance decreasing to zero and the attacker receiving `WALLET_BALANCE` while the swap still produces fair output. [11](#0-10)

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other

    /// Decodes `swap_xdr` as a `StrategyPayload` and runs it for `sender`.
    ///
    /// Requires `sender` authorization. Pulls `total_in` of the input token, runs the
    /// instruction stream, applies fees, checks the minimum output, and returns the amount
    /// delivered to `sender`. Panics with `Error::InvalidRouteXdr` if the XDR does not decode.
    fn execute_strategy(env: Env, sender: Address, total_in: i128, swap_xdr: Bytes) -> i128 {
        renew_instance(&env);
        let payload = StrategyPayload::from_xdr(&env, &swap_xdr)
            .unwrap_or_else(|_| panic_with_error!(&env, Error::InvalidRouteXdr));
        execute::run(env, sender, total_in, payload)
