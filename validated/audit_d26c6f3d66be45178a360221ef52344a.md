### Title
Webhook `shop-domain` header is trusted as tenant identity but is not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` only proves that `raw_body` was signed by an app that knows `Context.api_secret_key` [1](#0-0) . The `shop-domain` header, which `Registry.process` hands to the consumer as the authoritative tenant identifier, is read straight from an attacker-controllable HTTP header and is never included in the signed material [2](#0-1) .

### Finding Description
The identity binding this code implicitly claims is: `hmac verified ⇒ (body, shop) both authentic for this app`. In reality the binding only holds for the body:

- `HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` field [3](#0-2) .
- For `Webhooks::Request`, `to_signable_string` is just `@raw_body`; `shop`, `topic`, and `webhook_id` are pulled from headers and are outside the signed string [4](#0-3) .
- `Registry.process` only checks `Utils::HmacValidator.validate(request)` and then immediately forwards `request.shop` (the unverified header) into `WebhookMetadata` that the app's handler uses to attribute the event to a tenant [5](#0-4) .

So the check performed ("bytes verified") is `HMAC(secret, body)`, but the value acted on ("bytes parsed/trusted") includes `shop-domain`, which is a completely independent, unauthenticated field. Any party that has ever obtained one genuine `(body, hmac)` pair signed with the app's secret — trivially available to any merchant who has installed the app, since every webhook delivered to their own shop is HMAC-valid — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` will still return `true` (it never looks at the header), and `Registry.process` will dispatch the payload to the handler tagged with the attacker-chosen `shop`, exactly mirroring the report's pattern of "a field acted on but not covered by the HMAC."

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as documented/intended by this gem) to look up the tenant record, update per-shop data, or key any tenant-scoped side effect, an unprivileged actor who is merely a merchant/installer of the app (not an admin of the victim shop) can inject webhook data attributed to a different shop of their choosing. This is a cross-tenant data-integrity/confusion issue: the library asserts to the caller that `shop` is HMAC-verified alongside the body, when it is not. This maps to the Critical "cross-tenant access" impact category, since the app's own trusted verification primitive (`HmacValidator.validate`) is the thing giving false assurance over the `shop` value.

### Likelihood Explanation
Exploitation requires only: (1) being any merchant who has installed the app (to legitimately receive one valid `(body, hmac)` webhook pair — no access to `api_secret_key` or the victim's credentials is needed), and (2) POSTing that captured pair to the app's public webhook endpoint with a modified `shopify-shop-domain` header. No TLS interception, no privileged account on the target shop, and no leaked secret are required, so this satisfies the "unprivileged internet user" bar, though it does depend on the host application trusting `WebhookMetadata#shop` for tenant-scoped actions rather than performing an additional independent shop check.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC verification (or otherwise cryptographically bind them to the body), so that `HmacValidator.validate` fails if any of those header-derived fields are altered relative to what Shopify actually signed. At minimum, document prominently that `WebhookMetadata#shop` is not covered by the HMAC and must not be used as a sole tenant-authorization signal by consuming applications.

### Proof of Concept
```ruby
# Attacker is a legitimate merchant of shop "attacker-shop.myshopify.com" with the app installed.
# Shopify sends them a genuine webhook, e.g. orders/create with body '{"id":1}'.
# The attacker records the valid headers, including:
#   shopify-hmac-sha256: <valid signature for body '{"id":1}'>
#   shopify-shop-domain: attacker-shop.myshopify.com
#   shopify-topic: orders/create

# Attacker replays the exact same body + hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to the victim's shop:
headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => "<the same valid signature, unchanged>",
  "shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: '{"id":1}', headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) still returns true, because it only hashes @raw_body.
# The handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
# even though Shopify never sent this event for victim-shop.
