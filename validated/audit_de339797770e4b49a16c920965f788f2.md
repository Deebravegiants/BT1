### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, while the `shop` identity that the gem hands to the app's handler is read from an HTTP header that is never included in that signature. This breaks the intended binding `hmac_signed_bytes == authenticated_identity`, letting an attacker who possesses one legitimately-signed webhook body (from their own shop's install of the app) relabel it as belonging to a different shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (from the header) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`, i.e., the body, and compares it with `OpenSSL.secure_compare`: [4](#0-3) 

Because the signature never covers the shop-domain header, the binding the gem is supposed to enforce — "the shop this webhook is attributed to" == "the shop the HMAC was computed for" — does not actually hold. The documentation instructs app authors to use `data.shop` directly to key business logic (e.g., dispatching background jobs by shop domain): [5](#0-4) 

An attacker who has installed the app on their own (attacker-controlled) shop receives real, validly-HMAC-signed webhook deliveries from Shopify for that shop. Because the signature covers only the JSON body, the attacker can capture one such delivery and replay it to the app's webhook endpoint, substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Utils::HmacValidator.validate` still succeeds (it never inspects the header), so `Registry.process` will dispatch the webhook to the handler with `shop: "victim-shop.myshopify.com"` while the body is fully attacker-controlled.

### Impact Explanation
Any app that follows the gem's documented pattern of using `WebhookMetadata#shop` to key shop-scoped operations (looking up a stored session for that shop, updating shop-owned records, enqueuing shop-scoped jobs, etc.) can be tricked into acting on behalf of a different merchant/tenant using attacker-supplied body content. This is a cross-tenant identity-binding failure reachable by any unprivileged internet user who can install the app on their own store (a normal, unprivileged action for embedded Shopify apps) — no access to `api_secret_key`, tokens, or Shopify's private signing material is required.

### Likelihood Explanation
Moderate-to-high: exploitation only requires (1) installing the target app on an attacker-owned/free development store to receive a real signed webhook, and (2) sending a forged HTTP request to the app's public webhook endpoint with a spoofed shop-domain header and the captured body/HMAC pair. No secrets need to be extracted; the HMAC value from a genuine delivery is reused verbatim, since the identity attribute it's being reused for (the shop header) is outside its coverage.

### Recommendation
Bind the `shop` domain into the value that is actually verified, e.g., by requiring the `shop-domain` header to be a subset of the HMAC-signable content (as Shopify already does for OAuth's `AuthQuery`, whose `to_signable_string` explicitly includes `shop`), or by validating that the shop present in the raw JSON body payload matches the header-derived shop before trusting it. At minimum, document prominently that `WebhookMetadata#shop` is not itself HMAC-authenticated and must not be used as the sole tenant-scoping key without additional verification (e.g., cross-checking against a shop that is independently known, such as one derived from the webhook subscription/session lookup).

### Proof of Concept
1. Install the vulnerable app on an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a real webhook event (e.g. `orders/create`) — Shopify sends:
   - Headers: `x-shopify-hmac-sha256: <valid-hmac-for-body>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`
   - Body: attacker-controlled JSON (order fields the attacker set on their own store).
3. Capture the raw body and the valid `x-shopify-hmac-sha256` value.
4. Replay an HTTP POST to the app's webhook endpoint with the same body/HMAC but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` succeeds because it only checks the body: [6](#0-5) 
6. `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body: [3](#0-2) 
7. Any app logic keyed on `data.shop` (per the documented usage pattern) now operates on the victim tenant using attacker-chosen data.
