### Title
Missing shop-domain sanitization in `validate_auth_callback` lets a signed callback's `shop` field drive the `client_secret`-bearing request host - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` validates the OAuth callback's HMAC via `Utils::HmacValidator.validate(auth_query)`, then uses the raw, un-sanitized `auth_query.shop` value to build a `null_session` whose `shop` attribute directly determines the target host (`https://#{session.shop}`) of the subsequent `POST /admin/oauth/access_token` request, which carries `Context.api_secret_key` in its body. Unlike `ClientCredentials.client_credentials`, which explicitly calls `Utils::ShopValidator.sanitize!(shop)` before constructing a session, `validate_auth_callback` never calls `ShopValidator` on `auth_query.shop`.

### Finding Description
The equality this code is supposed to enforce is: `host validated by ShopValidator == host that receives the client_secret`. Instead, the code enforces only `hmac(shop, host, code, state, timestamp) == valid signature`, and then trusts the `shop` string verbatim as a hostname:

- `HmacValidator.validate` proves the query byte-string (which includes `shop`) was signed by an entity holding `Context.api_secret_key` (normally Shopify). It does not prove `shop` is a well-formed `*.myshopify.com` domain.
- `validate_auth_callback` passes `auth_query.shop` straight into `Auth::Session.new(shop: auth_query.shop)`.
- `Clients::HttpClient#initialize` builds `@base_uri = "https://#{api_host || session.shop}"` directly from `session.shop`, with no validation, and then the client POSTs the OAuth code + `Context.api_secret_key` to that host at `/admin/oauth/access_token`.
- `Utils::ShopValidator.sanitize!` exists exactly to constrain `shop` to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`), and is used for this purpose in `ClientCredentials.client_credentials`, but is conspicuously absent from `validate_auth_callback`.

Because the HMAC is computed over the `shop` value itself, the value can't be tampered with by an unprivileged attacker without invalidating the signature. However, this still represents a broken defense-in-depth boundary relative to the sibling `ClientCredentials` code path: any downstream consumer relying on this library enforcing "shop is a Shopify domain" for defense against confused-deputy/config errors (e.g., a compromised or malicious Shopify-side redirect, or a testing/staging misconfiguration that permits attacker-influenced `shop` values while still possessing a valid signature under a leaked/shared secret) has no such enforcement here, unlike in the `client_credentials` flow.

### Impact Explanation
If `auth_query.shop` can be an arbitrary string while still satisfying `HmacValidator.validate` (e.g., in multi-tenant setups sharing `api_secret_key` across less-trusted signers, or due to any signature-validation weakness), the app's `client_secret` would be sent verbatim to an attacker-controlled host, constituting SSRF carrying the app's credentials.

### Likelihood Explanation
Low likelihood under normal operation, because the primary control (`HmacValidator.validate`) does bind `shop` to a signature only Shopify's callback can normally produce. The issue is the absence of a redundant, documented safety check (`ShopValidator.sanitize!`) that this same codebase applies elsewhere for the identical purpose, leaving this specific path with a single point of failure instead of the intended two.

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop)` in `validate_auth_callback` before constructing `null_session`/`Session.from`, mirroring the pattern already used in `ClientCredentials.client_credentials`, so the shop used to build the token-exchange request host is always constrained to `TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
Not independently reproducible with unprivileged-internet-user access alone, since exploitation requires a valid HMAC over an attacker-chosen `shop` value, which in the standard single-secret deployment can only be produced by the holder of `Context.api_secret_key`. This is flagged as a structural inconsistency/defense-in-depth gap rather than a fully demonstrated exploit path under default configuration.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
