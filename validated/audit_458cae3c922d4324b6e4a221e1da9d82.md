### Title
Arbitrary-recipient calldata in EmporiumUpgradeable's stateless `runAction` path drains another user's residual vault position parked under Emporium's shared identity - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction`'s "stateless" execution branch performs `op.endpoint.call{value: op.value}(op.callData)` with `EmporiumUpgradeable` itself as `msg.sender` for every user, and only blacklists two specific function selectors (`callHinkalWallet`/`doSendToRelay`). Any unprivileged attacker who submits their own (even zero-value) Hinkal transaction can supply arbitrary `callData` to any `endpoint`, so they can call a lending/vault contract's `withdraw`/`redeem` function with themselves as `receiver` while the vault's shares/position were credited to `msg.sender == Emporium` from an earlier, unrelated user's stateless deposit.

### Finding Description
Broken equality: *the set of assets Emporium's on-chain identity is entitled to move* (a vault position keyed to `msg.sender == address(EmporiumUpgradeable)`, created by an earlier legitimate depositor) **≠** *the set of assets `circomData.erc20TokenAddresses` / `deltaAmountChanges` in the attacker's own transaction attribute to the attacker*.

In the stateless branch of `runAction`: [1](#0-0) 
the contract only checks that the call's selector is not `callHinkalWallet`/`doSendToRelay`; any other `endpoint`/`callData`/`value` triple supplied by the caller in `circomData.externalActionData.externalActionMetadata` is executed with `msg.sender == EmporiumUpgradeable` for every Hinkal user. This is confirmed by the wiki's own description of the "Stateless Direct Call" mode, which explicitly states the external protocol sees `msg.sender` as the shared `EmporiumUpgradeable` contract, and contrasts it with the "Stateful HinkalWallet Invocation" mode that exists precisely to give each user a distinct identity (`HinkalWallet`) via `onlyEmporium`-gated `callHinkalWallet`.

Because many DeFi vault/lending integrations authorize withdrawals solely by `msg.sender == depositor`, any earlier stateless deposit op made through Emporium (by any legitimate user) leaves the position permanently keyed to Emporium's shared address. The post-execution accounting in `runAction`: [2](#0-1) 
only measures the delta of `circomData.erc20TokenAddresses` balances on the `EmporiumUpgradeable` contract itself, before vs. after **the current call**. It does not, and cannot, verify that the funds moved during the current call's external calls actually originated from the current caller's own declared deposits (`deltaAmountChanges`). Two exploit variants follow from this:
1. Attacker sets `op.callData` to `vault.withdraw(shares, receiver=attacker_EOA, owner=Emporium)`. Funds go straight from the vault to the attacker's EOA, bypassing Emporium's balance snapshot entirely (`balancesBefore`/`balancesAfter` never see it) - a "silent" real-asset theft that leaves no trace in the shielded UTXO accounting.
2. Attacker sets `op.callData` to `vault.withdraw(shares, receiver=Emporium, owner=Emporium)` while declaring the underlying token in `circomData.erc20TokenAddresses` with `deltaAmountChanges[i] >= 0` (i.e., contributing none of their own funds). The redeemed value increases `balancesAfter[i]`, `balanceChange > 0`, and `handleOut` (line 146-151) mints a fresh UTXO for that amount to the attacker via their own `circomData.stealthAddressStructure` - laundering another user's vault position into the attacker's shielded balance.

Existing guards do not catch this:
- `onlyAllowedRecipient` only checks that `msg.sender` calling `runAction` is `Hinkal.sol` itself, not that the `endpoint`/`callData` are legitimate for the current UTXO owner. [3](#0-2) 
- `verifyWallet`/EIP-712 signature checking in Emporium only guards the *stateful* (`invokeWallet`, `signerAddress`) path; the stateless path (`signerAddress == address(0)`) skips signature verification entirely aside from nonce replay protection. [4](#0-3) 
- `BalanceChangeShouldBePositive` only bounds the aggregate delta from going negative; it does not verify the delta's provenance.
- The circuit (`SignatureVerifier.circom`, `MainEVMCircuit.circom`) binds `calldataHash`/`externalActionMetadata` to prevent tampering by a relayer, but it never constrains the *semantic content* of `callData` (target function, recipient argument) to the attacker's own funds - the attacker is free to encode any legitimate `withdraw(..., attackerAddress, ...)` call and produce a valid proof over their own (even zero-value) UTXOs.

### Impact Explanation
Direct theft of another user's funds that are parked in an external vault/lending position under Emporium's shared on-chain identity - Critical severity, matching "direct theft of shielded or in-flight user funds" and "executing calls or moving assets a wallet owner or prover never authorised." The attack is repeatable against every subsequent legitimate stateless deposit left un-redeemed at Emporium, and against any residual dust/receipt-token balance accidentally stranded on the Emporium contract from any incomplete stateless flow (e.g., a receipt/share token not included in a depositor's own `erc20TokenAddresses`).

### Likelihood Explanation
Requires only that some other legitimate user execute a stateful/deposit-style DeFi interaction (e.g. `vault.deposit(...)`) through Emporium's **stateless** mode without redeeming/consuming it in the same transaction, leaving a withdrawable position keyed to `msg.sender == Emporium`. The attacker needs no privileges beyond normal Hinkal usage: they submit their own transaction with a self-generated proof over their own (possibly zero-value) UTXOs and freely-crafted `externalActionMetadata`. Given that Emporium is explicitly documented as supporting "arbitrary" stateless calls to any `endpoint` and only guards two specific wallet-hijack selectors, this is a design-level gap rather than a corner case, and is monitorable/exploitable opportunistically by watching for any un-redeemed vault position sitting under the Emporium contract address.

### Recommendation
Restrict the stateless direct-call path to actions that cannot leave persistent state attributable to `msg.sender == Emporium` (e.g., atomic swaps only), or require that any op targeting a protocol which records positions by `msg.sender` be routed exclusively through a per-user `HinkalWallet` (stateful mode) with EIP-712 authorization, never the shared Emporium identity. Additionally, add a strict allow-list of `(endpoint, selector)` pairs vetted for statelessness for the direct-call branch, and/or require `runAction`'s balance accounting to enforce that any balance increase in a token not explicitly deposited by the current caller (`deltaAmountChanges[i] <= 0`) cannot be attributed/paid out to that caller as a new UTXO unless the source of the increase is provably this transaction's own deposit.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a mock ERC4626-style vault (`MockVault`) that mints shares to `msg.sender` on `deposit` and burns shares/sends `receiver` the assets on `withdraw(assets, receiver, owner)` checking only `owner == msg.sender`.
2. As "User A", call Hinkal `transact` with `externalActionMetadata` encoding a stateless `EmporiumOperation` to `MockVault.deposit(amount, Emporium)`; assert `MockVault` records the position under `address(EmporiumUpgradeable)` and Emporium's own vault-share balance increases, while the underlying token leaves User A's shielded UTXOs. Do not redeem in this transaction.
3. As "Attacker", generate a proof over attacker's own (zero-value) UTXOs, craft `externalActionMetadata` with a stateless op calling `MockVault.withdraw(sharesOfUserA, attacker, address(EmporiumUpgradeable))` (or `receiver = Emporium` + declaring the underlying token with zero `deltaAmountChanges`), call `transact`.
4. Assert: attacker's EOA balance (variant 1) or attacker's new shielded UTXO (variant 2) equals User A's deposited amount, while User A never authorized or participated in this second transaction - proving the equality "Emporium's movable assets == attacker's declared assets" is broken.
