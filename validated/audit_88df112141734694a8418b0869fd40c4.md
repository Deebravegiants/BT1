Confirmed. `WebhookMetadata.shop` is a plain `String` const populated directly from `request.shop`, with no independent verification tying it to the authenticated bytes.

### Title
Cross-Tenant Webhook Shop Spoofing via Header Fields Not Covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`), routing (`topic`), and dedup (`webhook_id`) fields from raw HTTP headers, while `Utils::HmacValidator` (via `to_signable_string`) authenticates only the raw request body. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose body HMAC validates, then hands `request.shop` straight to the app's handler as trusted tenant identity — breaking the equality: **shop authenticated by the HMAC ≠ shop consumed by the handler**.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are read straight from headers, independent of that signed body: [2](#0-1) 

`HmacValidator.validate` only ever checks the `hmac` field against `to_signable_string`, i.e. the body bytes — it never touches the shop/topic headers: [3](#0-2) 

`Registry.process` accepts the request once that body-only HMAC passes, then constructs `WebhookMetadata` using the unauthenticated `request.shop` header as the tenant identifier passed to the app's handler: [4](#0-3) [5](#0-4) 

The gem's own documentation instructs developers to treat `data.shop` as the authoritative tenant identifier for downstream work (e.g. queuing jobs keyed by shop): [6](#0-5) 

Because `api_secret_key` is a single, app-wide secret shared across *every* merchant who installs the app (not a per-shop credential), any unprivileged merchant who installs the app on their own store receives legitimate webhook deliveries whose body+HMAC pair is validly signed with that shared secret. That merchant can capture one such valid `(raw_body, hmac)` pair from their own store's webhook traffic and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header with a victim shop's domain. `HmacValidator.validate` still succeeds — it never inspected the header — so `Registry.process` calls the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"` even though the payload actually originated from, and was signed for, the attacker's own shop.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker with no privileges beyond "any merchant who installed the app" can make the app process attacker-supplied webhook bodies under a victim shop's identity. Depending on how the host app trusts `data.shop` (as documented), this can drive per-shop side effects (e.g. GDPR `customers/redact`/`shop/redact` handling, data indexing/lookup keyed by shop, `app/uninstalled` cleanup) against a victim tenant using attacker-controlled body content — a cross-tenant access/data-integrity break attributable entirely to this gem's failure to bind the authenticated bytes to the claimed shop.

### Likelihood Explanation
Requires only that the attacker be able to install the target app on their own (or a throwaway) Shopify store — a normal, unprivileged action available to any internet user for public apps — plus basic ability to capture and replay an HTTP request with a modified header. No access token, `client_secret`, or leaked credential is needed.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material, or otherwise cross-check the header-derived shop against server-side state established during OAuth (e.g. verify the shop header matches a shop this specific webhook subscription/session was registered for) before exposing it in `WebhookMetadata`. At minimum, document prominently that `data.shop`/`data.topic` are unauthenticated header values and must not be trusted for authorization decisions without additional server-side verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`; app registers e.g. `orders/create` webhooks.
2. Shopify delivers a legitimate webhook: body `B`, headers include `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures `(B, HMAC(secret,B))` and resends it to the app's public webhook endpoint, replacing only `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully; `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes HMAC over `B`.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, i.e. attacker-chosen body processed under the victim's tenant identity.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
