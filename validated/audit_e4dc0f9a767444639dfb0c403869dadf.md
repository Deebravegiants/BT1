### Title
Webhook Shop Domain Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers and passed straight into the handler. This breaks the intended identity binding `verified_bytes == acted_upon_bytes`, since the tenant-identifying `shop` field is never part of the HMAC-signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from headers with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely from `to_signable_string` (the body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof of authenticity for the *entire* request, then forwards the unauthenticated `request.shop` value straight to the handler as the tenant identifier: [4](#0-3) 

Because the HMAC secret is the app's single `client_secret` shared across every shop that installs the app, any two webhook deliveries with identical bodies produce identical valid HMAC digests regardless of which shop they originated from. An entity that controls a shop where the app is installed (an unprivileged installer, not a privileged Shopify employee) can capture a legitimate, validly-signed webhook delivery for their own store and then replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header rewritten to a victim shop's domain. `HmacValidator.validate` still passes (body/hmac pair is untouched), but `WebhookMetadata.shop` now reports the victim's domain to the handler.

### Impact Explanation
Applications built on this gem rely on `WebhookMetadata#shop` (populated from `request.shop`) to route processed data to the correct tenant record/session. Spoofing this field lets an attacker impersonate a different shop's webhook traffic, potentially injecting attacker-controlled data (e.g., forged `app/uninstalled`, `orders/create`, or `customers/data_request` payloads) attributed to a victim tenant — a cross-tenant confusion/injection primitive, which is Critical-severity per the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is Low–Medium: exploitation requires the attacker to (a) install the app on a shop they control to obtain at least one validly-signed webhook, and (b) be able to deliver a crafted HTTP request to the app's public webhook endpoint with a modified shop header — both realistic for any developer/merchant who can install the third-party app, without needing the `api_secret_key`, an access token, or any privileged account.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed material (or otherwise cryptographically bind them to the verified body), so `Utils::HmacValidator.validate` fails whenever these header-derived fields are altered. At minimum, document and encourage host apps to cross-check `request.shop` against the shop associated with the specific webhook subscription/session rather than trusting the header value implicitly.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw body `B`, and header `shopify-hmac-sha256: H` where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker resends the identical `B`/`H` pair to the app's webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` succeeds because it only checks `B` against `H` [5](#0-4) .
4. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, so the app processes attacker-supplied data under the victim's tenant identity [6](#0-5) .
