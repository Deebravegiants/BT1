### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `ShopifyAPI::Webhooks::Registry.process` to build `WebhookMetadata` come from HTTP headers that are excluded from the HMAC-signed content [1](#0-0) . Since Shopify signs webhooks using the app's single shared `api_secret_key` for every shop that installs the app (not a per-shop secret), any unprivileged user who installs the app on their own shop can legitimately receive a `(body, hmac)` pair signed with that shared secret, then replay that exact body+hmac to the app's webhook endpoint with a forged `shop-domain` header pointing at a victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC only over `to_signable_string`, which for `Webhooks::Request` is `@raw_body` alone [2](#0-1) [3](#0-2) . The `shop`, `topic`, and `webhook_id` accessors read directly from attacker-controllable headers (`shopify-shop-domain`/`x-shopify-shop-domain`, etc.) with no cryptographic binding to those values [4](#0-3) .

`Registry.process` validates only the HMAC of the body, then constructs `WebhookMetadata` directly from these unauthenticated header values and dispatches it to the app's handler: [5](#0-4) 

This breaks the intended identity binding: `hmac == HMAC(secret, body)` is verified, but the equality that actually matters for tenant isolation — `request.shop == shop that produced body` — is never checked. Because the same `api_secret_key` is shared across all shops that install the app, an attacker who installs the app on their own (unprivileged, free development) store can capture a genuinely-signed `(body, hmac)` pair from their own webhook traffic, then POST that identical body/hmac to the app's webhook endpoint while substituting the `shop-domain` header (and/or `topic`/`webhook_id`) for a target/victim shop domain. `HmacValidator.validate` still succeeds because it only checks the body, and the handler processes the replayed payload under the spoofed victim shop identity.

### Impact Explanation
This allows an unprivileged app-installer to make the host application ingest attacker-controlled webhook bodies attributed to an arbitrary other shop (cross-tenant confusion), e.g., injecting fabricated `orders/create`, `customers/data_request`, or `app/uninstalled` events tagged as coming from a victim shop. Depending on how the host app's handler acts on `data.shop` (e.g., writing to per-shop records, revoking access, triggering GDPR data flows, enqueuing per-tenant jobs), this can lead to cross-tenant data corruption or unauthorized actions taken against a shop the attacker does not control, satisfying the "cross-tenant access" impact bar.

### Likelihood Explanation
Likelihood is high for any attacker willing to install the app on their own store (free, no privilege required) to harvest a validly-signed body/hmac pair, since the signing secret is shared across all installs. Forging the header alone (with no valid body/hmac at all) is not sufficient — the attacker needs a real signed body, but obtaining one requires nothing more than being a normal, unprivileged Shopify merchant/developer who installs the app.

### Recommendation
Include the identity-relevant fields (`shop`, `topic`, `webhook_id`, `api_version`, and ideally a timestamp/nonce) in the signed payload, or otherwise cryptographically bind the shop domain to the HMAC before trusting it to route/attribute webhook data. At minimum, downstream consumers should be required to cross-check `request.shop` against a shop they already have an active, verified session/installation record for, rather than trusting it as an authenticated identity purely on the strength of the body-only HMAC.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (an ordinary, unprivileged development/partner store).
2. Attacker triggers or waits for a legitimate webhook (e.g., `orders/create`) to their own store; captures `raw_body` and the `X-Shopify-Hmac-Sha256` header — both signed with the app's shared `api_secret_key`.
3. Attacker POSTs the exact same `raw_body` and `hmac` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (optionally also `X-Shopify-Topic`).
4. `Utils::HmacValidator.validate(request)` returns `true` because validation only checks `raw_body` against the hmac [6](#0-5) .
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and invokes the registered handler, which processes attacker-controlled data as if it originated from the victim shop [7](#0-6) .
