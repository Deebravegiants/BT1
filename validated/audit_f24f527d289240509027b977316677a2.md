### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content only from the raw HTTP body, while the shop-identifying header (`x-shopify-shop-domain`) is read separately and trusted without being part of the HMAC-signed material. `Registry.process` validates only that the body's HMAC is correct, then dispatches to the app's handler using the header-derived `shop` value as the tenant identity. A request whose body+HMAC pair was legitimately produced for one shop can be replayed with the `shop-domain` header rewritten to a different shop, and it will still pass validation, causing the webhook body to be processed as if it belonged to the attacker-chosen tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor reads the `shop-domain` header independently of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC over the `Request` object (i.e. over the body only) and, once it passes, forwards `request.shop` — the unauthenticated header value — as the tenant identity to the app's handler: [3](#0-2) 

The binding that should hold is: `hmac_signed_bytes == bytes_that_determine_tenant`. Here, `hmac_signed_bytes = raw_body` but `tenant_identity = header["shop-domain"]`, which is disjoint from `raw_body`. Any two requests sharing the same `raw_body`/`hmac` pair but differing only in the `shop-domain` header will both pass `HmacValidator.validate`, yet resolve to different tenants in `WebhookMetadata`.

### Impact Explanation
This is a cross-tenant identity-confusion vector: a party who legitimately receives a valid signed webhook for their own shop (e.g., by installing the app on a shop they control) can capture that exact `raw_body` + `hmac-sha256` header pair and resend it to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop. `Registry.process` will accept it as valid and the handler will process the payload under the victim's tenant context (`WebhookMetadata.shop`), since nothing cryptographically ties the shop-domain header to the signed body. Depending on how the host app keys data/side effects off `WebhookMetadata#shop` (very likely, since that's the field's whole purpose), this can lead to writing/mutating another merchant's data or triggering tenant-scoped actions under the wrong tenant — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only: (1) being able to legitimately receive at least one valid webhook of a reused/replayable topic (trivial for anyone who installs the app on their own store, which is an unprivileged action), and (2) sending an arbitrary HTTP request to the app's public webhook endpoint with a forged `shop-domain` header — no knowledge of `api_secret_key` is needed since the original HMAC is reused verbatim. This is squarely reachable by an unprivileged internet user.

### Recommendation
Bind the shop identity into the signed material, e.g. include the `shop-domain` header value in `to_signable_string` (mirroring the pattern already used for `AuthQuery`, where `shop` is part of the signable string), or otherwise cryptographically verify that the header-derived shop matches an expected/registered value before dispatching to the handler.

### Proof of Concept
1. Install the app on Shop A (attacker-controlled) and capture a legitimate webhook request Shopify sends to the app: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for secret key, since Shopify signed it), plus `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
2. Replay the request to the app's webhook endpoint with the same body `B` and same `H`, but change the header to `X-Shopify-Shop-Domain: shop-b.myshopify.com` (victim).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`= B`) — unchanged — so validation succeeds: [4](#0-3) 
4. The handler receives `WebhookMetadata.new(topic:, shop: "shop-b.myshopify.com", body: parsed(B), ...)`, processing Shop A's payload under Shop B's tenant identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
