### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing shop impersonation in `Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-signing only the raw HTTP body, while the `shop-domain` header — which the gem passes on to app handlers as the authoritative tenant identifier — is never included in the signed material. Anyone who can obtain one validly-signed webhook body from the target app (e.g., by installing the same public app on their own store) can replay that body under a forged `x-shopify-shop-domain` header and have it accepted as an authentic event for a different shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` and compares it to the `hmac-sha256` header: [2](#0-1) 

`Webhooks::Registry.process` validates only that HMAC, then forwards `request.shop` — parsed straight from the unauthenticated `shop-domain`/`x-shopify-shop-domain` header — to the app's handler as the tenant identity for the event: [3](#0-2) 

`Request#shop` simply reads the header verbatim, with no cryptographic binding to the signed body: [4](#0-3) 

This reproduces the bug class from the external report: a field that is *acted upon* (`shop`, used by the app to select which tenant's data the webhook payload applies to) is not part of the data covered by the integrity check (only `@raw_body` is signed). The equality that should hold — `shop-domain header == shop implied by the HMAC-protected content` — is never enforced; the gem lets the two diverge silently.

Because Shopify webhook HMACs are computed with the app's single `client_secret`/`api_secret_key`, which is shared across every shop that installs the app (not a per-shop secret), any unprivileged user who installs the same (e.g. public) app on a store they control receives events with a validly-computed signature over a body they fully control. Nothing stops them from re-POSTing that exact `raw_body` + `hmac-sha256` pair to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. `Registry.process` will validate the HMAC successfully (since it only checks the body) and hand the attacker-controlled body to the handler tagged with the victim's shop.

### Impact Explanation
If the host app's webhook handler uses `WebhookMetadata#shop` to select the tenant record to update (a common, encouraged pattern, since the gem exposes `shop` specifically for that purpose), an attacker can inject or manipulate data attributed to a shop they do not control — a cross-tenant access/write primitive achieved without ever possessing the victim's access token or the app's `client_secret`.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target app on an attacker-controlled shop (trivial for public apps), which yields a legitimately-signed webhook body, and (2) sending an HTTP POST to the app's public webhook endpoint with a modified `shop-domain` header. No secrets, tokens, or privileged access are needed — only interaction available to any unprivileged internet user who can install the app once.

### Recommendation
Bind the shop identity into the value that is cryptographically verified: either include the shop/topic/webhook-id in the signed payload comparison, or require the caller to independently confirm that `request.shop` corresponds to a shop with an active, matching installation/session before trusting it, rather than only validating the raw body's HMAC.

### Proof of Concept
1. Install the target public app on an attacker-owned development store `attacker.myshopify.com`, triggering a webhook (e.g. `app/uninstalled`) that Shopify signs with the app's shared `client_secret`.
2. Capture the raw POST body and its `X-Shopify-Hmac-Sha256` header — both valid.
3. Replay the identical body and HMAC header to the same app endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which succeeds because it only checks the (unchanged) body against the (unchanged) HMAC — see `lib/shopify_api/webhooks/request.rb` line 36-38 and `lib/shopify_api/utils/hmac_validator.rb` line 26-31.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)` and, if it trusts `shop` to select the tenant, processes attacker-controlled data as if it originated from the victim's shop.
