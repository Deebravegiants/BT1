### Title
Missing length validation on `message.from` in `hyper-fungible-token`'s `on_accept` panics the destination chain runtime - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`HyperFungibleToken::on_accept`, the `IsmpModule` callback invoked when `pallet-ismp` processes an incoming cross-chain POST request via the permissionless `handle_unsigned` extrinsic, decodes the attacker/source-chain-supplied `Message` ABI payload and later slices/copies `message.from` without validating its length, unlike the sibling `on_timeout` handler in the same file which explicitly validates `from_bytes.len()` and returns `HftError::InvalidSenderLength` on mismatch.

### Finding Description
In `on_accept`, when the decoded `message.data` carries a `SubstrateCalldata` with no `signature`, the code computes the dispatch origin from `message.from` directly: [1](#0-0) 

```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
```

- If `from_bytes.len() < 20` and `source.is_evm()`, the subtraction `from_bytes.len() - 20` underflows a `usize`. This panics with an arithmetic overflow in checked-arithmetic builds, or wraps to a huge value causing an out-of-bounds slice index panic in wrapping builds.
- If `source` is not EVM and `from_bytes.len() != 32`, `copy_from_slice` panics directly on the length mismatch.

Contrast this with the length handling that already exists for the exact same field, `message.from`, in `on_timeout` in the same file: [2](#0-1) , and for `message.to` in `on_accept` itself: [3](#0-2) . Both of those paths defensively check length and return a typed `HftError` instead of indexing/copying blindly. The `on_accept` no-signature branch for `message.from` is the one path that was never given this guard, which is a clear internal inconsistency indicating a missed validation rather than an intentional design decision.

`on_accept` is reached when `pallet-ismp`'s unsigned `handle_unsigned` extrinsic validates and executes a relayed message — this call is `ensure_none` (unsigned) and callable by anyone with a valid proof: [4](#0-3) . `message.data` is entirely attacker/relayer-controlled bytes from the source-chain contract's payload, and the internal `Message` structure it decodes (including `.from`) is defined and consumed with no length check at this call site: [5](#0-4) .

### Impact Explanation
A panic during extrinsic execution inside `IsmpModule::on_accept`, dispatched from within pallet-ismp's transactional call, aborts/reverts the transaction, but because `handle_unsigned` is validated via `ValidateUnsigned::validate_unsigned` — which itself calls `Self::execute(messages.clone())` during transaction-pool validation (off-chain, before inclusion) — a panic here can be triggered merely by submitting the extrinsic to the pool, i.e. before block inclusion: [6](#0-5) . A Rust panic raised inside WASM runtime execution during off-chain transaction-pool validation crashes/traps the executing node's runtime worker (this mirrors exactly the reported bug class: malformed payload causes an unhandled crash rather than a clean validation error), which is a route/liveness impact for the affected parachain node rather than a benign rejection.

### Likelihood Explanation
Reaching this exact code path is bounded by the requirement that `ContractToAsset::<T>::get(source, &from)` (keyed on the ISMP-level `PostRequest.source`/`from`, i.e. the registered/trusted contract address on the source chain) succeeds, meaning the message must appear to originate from an already-registered `HyperFungibleToken`-family contract, and that message must carry a valid ISMP proof of inclusion on that source chain. Whether an entirely unprivileged party (a normal user of the legitimate source contract, not a malicious admin/governance actor) can control the raw bytes placed into `message.from` on the source side could not be conclusively verified in the time available — I was not able to locate and read the `send()`/message-construction logic of `HyperFungibleToken.sol` / `HyperFungibleTokenUpgradeable.sol` before running out of tool budget, so I cannot confirm whether `from` is always derived internally as `msg.sender` (fixed 20 bytes, making this unreachable under honest source contracts) or whether it can be influenced by a caller-supplied parameter (making it directly reachable by any user of the bridge). This is a material open question that should be verified before treating this as a confirmed, fully unprivileged-reachable vulnerability.

### Recommendation
Add an explicit length check on `message.from` in `on_accept`'s no-signature branch, mirroring the existing pattern in `on_timeout` and for `message.to`, e.g.:
```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    if from_bytes.len() < 20 {
        Err(HftError::InvalidSenderLength(from_bytes.len()))?
    }
    T::EvmToSubstrate::convert(H160::from_slice(&from_bytes[from_bytes.len() - 20..]))
} else {
    if from_bytes.len() != 32 {
        Err(HftError::InvalidSenderLength(from_bytes.len()))?
    }
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
```
This converts a potential panic into a graceful `DispatchError`, consistent with how the rest of the module already handles malformed lengths.

### Proof of Concept
1. Register a source contract/state machine pairing in `ContractToAsset` as would occur for a normal `HyperFungibleToken` deployment (standard setup, not requiring admin misbehavior beyond normal bridge configuration).
2. Craft (or, if confirmed reachable from the source contract's public interface, induce) a source-chain `PostRequest.body` that ABI-decodes into a `Message` whose `.data` decodes to a `SubstrateCalldata` with `signature = None`, and whose `.from` field is fewer than 20 bytes (for an EVM source) or not exactly 32 bytes (for a non-EVM source).
3. Relay this message with a valid state/consensus proof and submit it via `Ismp::handle_unsigned`.
4. During either transaction-pool validation (`validate_unsigned`) or in-block execution, `on_accept` panics at the `from_bytes.len() - 20` subtraction or the `copy_from_slice` length mismatch, crashing the executing node process instead of returning a typed error.

Note: step 2's exact reachability from an untrusted caller depends on the source-side contract logic, which I could not verify within the available tool budget — this should be checked directly against `HyperFungibleToken.sol`/`HyperFungibleTokenUpgradeable.sol` `send()` implementation before treating likelihood as fully confirmed.
