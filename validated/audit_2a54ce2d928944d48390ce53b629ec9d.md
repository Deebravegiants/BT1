Based on my analysis, the premise of this question does not hold up under the actual code paths.

## Analysis

`HinkalWrapper.prooflessDeposit` calls `IHinkal(hinkal).prooflessDeposit(...)` [1](#0-0) , which is a **completely separate function** from `Hinkal.transact`. `Hinkal.prooflessDeposit` never invokes `verifyProof`, `_internalTransact`, `_externalTransact`, or the `balanceDif` accounting logic that lives inside `Hinkal.transact` [2](#0-1) . There is no code path by which a `prooflessDeposit` call routes through `Hinkal.transact`'s `balanceDif` check — the two functions do not call each other at all.

Instead, `Hinkal.prooflessDeposit` has its own, separate balance-accounting guard in `_handleTransfersFromProoflessDeposit`, which uses **strict equality**, not `>=`: [3](#0-2) 

This means if the token is fee-on-transfer (delivers less than `amount`), `balanceAfter - balanceBefore` will be strictly less than `amount`, and the require will revert the whole transaction — no under-collateralized UTXO can be minted this way, since a proofless deposit's on-chain commitment always uses the caller-supplied `amounts[i]` value [4](#0-3) , but that commitment is only inserted after the transfer's exact-amount check already succeeded.

For `Hinkal.transact` itself (not reachable from `prooflessDeposit`), the `balanceDif` check also uses strict equality (not `>=`) for the core invariant [5](#0-4) , so a fee-on-transfer token that delivers less than `amountChanges[i]` during `_internalTransact`'s `transferERC20TokenFromOrCheckETH` call [6](#0-5)  would cause `balanceDif < amountChanges[i]`, failing the equality check and reverting — it does not silently pass.

Regarding reentrancy: both `Hinkal.transact` and `Hinkal.prooflessDeposit` carry the `nonReentrant` modifier from a shared `ReentrancyGuard` inherited once via `HinkalBase` [7](#0-6) , [8](#0-7) , [9](#0-8) . Even if an ERC777 hook fired during `HinkalWrapper._pullAndApproveDepositTokens` (before Hinkal's guard is engaged) attempted to call into `Hinkal.transact`, that call itself would proceed under its own separate lock acquisition (since Hinkal's guard hadn't yet been entered) — but this reentrant `transact` call would be an entirely independent transaction context with its own `oldBalances`/`newBalances` snapshot and its own proof requirement (`verifyProof` must pass with a valid attacker-generated proof for attacker-owned UTXOs). It does not let the attacker corrupt the `prooflessDeposit`'s own accounting, and it does not let the attacker mint UTXOs unbacked by value inside `transact` because that function's own strict-equality balance check independently governs correctness for that call.

In short, there is no mechanism by which a fee-on-transfer/ERC777 token routed through `HinkalWrapper.prooflessDeposit` can make `Hinkal.transact`'s `balanceDif == ... + utxoAmount` check pass while under-delivering value — the two code paths are disjoint, and each has its own strict (not `>=`) balance-equality guard that reverts on short delivery.

    function _handleTransfersFromProoflessDeposit(
        TokenWithAmount[] memory uniqueTokens,
        uint256 uniqueCount
    ) private {
        for (uint256 i = 0; i < uniqueCount; i++) {
            address erc20Address = uniqueTokens[i].erc20Address;
            uint256 amount = uniqueTokens[i].amount;

            uint256 balanceBefore = getERC20OrETHBalance(erc20Address);
            if (erc20Address == address(0)) balanceBefore -= msg.value;

            transferERC20TokenFromOrCheckETH(
                erc20Address,
                msg.sender,
                address(this),
                amount
            );

            uint256 balanceAfter = getERC20OrETHBalance(erc20Address);

            require(
                balanceAfter - balanceBefore == amount,
                "proofless deposit balances must be equal"
            );
        }
    }
