### Title
Cross-User Response Confusion via Unauthenticated `MessageID` Reuse in Legacy WebAPI Capability Handler - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
`handler.HandleLegacyUserMessage` stores the client's callback in `h.savedCallbacks` keyed only by the client-supplied `msg.Body.MessageID`, with no check for whether that ID already has an in-flight request/callback registered. `handler.handleWebAPITriggerMessage`, which is invoked once a DON node responds, looks up and delivers the response purely by `MessageID`, without any binding to the specific user/session that submitted the original request. This mirrors the audit finding's root cause — trusting an attacker-influenced value to route a privileged callback instead of verifying the true initiator/owner of the operation.

### Finding Description
`HandleLegacyUserMessage` unconditionally overwrites any existing entry for the same `MessageID`: [1](#0-0) 

The only validation performed on `MessageID` is a length/format check in `Message.Validate()` — there is no uniqueness or ownership constraint: [2](#0-1) 

The gateway's top-level HTTP entrypoint enforces only a length cap (200 chars) on the request/message ID before dispatch, again with no anti-collision or per-session binding: [3](#0-2) 

When a DON node later returns a `MethodWebAPITrigger` response, the handler looks up `savedCallbacks[msg.Body.MessageID]`, deletes it, and delivers the response to whatever `Callback` is currently stored under that ID — accepting "first response wins" with no re-validation that the response corresponds to the requester who originally registered that callback: [4](#0-3) 

`HandleNodeMessage` does verify that the *node* responding is a legitimate signer (`msg.Body.Sender != nodeAddr`), but this only authenticates the DON member, not which end user's request the payload belongs to: [5](#0-4) 

Attack flow:
1. User A submits an HTTP request through the gateway with `MessageID = X`. `HandleLegacyUserMessage` saves `savedCallbacks[X] = <UserA's callback>` and forwards the request to all DON members.
2. Before the DON responds, Attacker submits another request reusing the same `MessageID = X` (nothing prevents choosing an arbitrary/observed ID — the gateway's dedupe/duplicate-request protection that exists in the newer v2 `httpTriggerHandler` (`"duplicate request ID"` / `"in-flight request"` checks) is absent from this legacy code path). This overwrites `savedCallbacks[X] = <Attacker's callback>`, silently discarding User A's registration.
3. When a DON node responds to the original request for `X` (which still carries User A's trigger data/results), `handleWebAPITriggerMessage` delivers that response to whichever callback is currently registered under `X` — the Attacker's — because the lookup has no way to verify the response's payload actually belongs to the same session as the currently-stored callback.

This is the same class of bug as the reported `to.onFlashLoan()` issue: a security-sensitive callback dispatch that trusts a value the initiator does not strongly bind/verify (there, `to`; here, the reusable `MessageID`), enabling one untrusted party to redirect output intended for another.

### Impact Explanation
An unprivileged HTTP caller of the gateway can hijack another concurrent user's in-flight WebAPI trigger response by racing to register a callback under the same `MessageID`. Depending on payload contents (workflow trigger results, secrets returned in the payload, etc.), this results in cross-user response confusion / unauthorized disclosure of another user's response data, and denial of service for the victim (whose original callback silently vanishes and eventually times out).

### Likelihood Explanation
Exploitability requires the attacker to guess or observe another user's chosen `MessageID` and win a narrow race window between request submission and DON response delivery. `MessageID` is client-chosen and not namespaced per-session/per-caller, so if IDs are ever predictable, sequential, or observable (e.g., shared clients, logging, or low-entropy IDs chosen by legitimate integrators), the race is straightforward to win. This lowers likelihood somewhat versus a fully passive attack, but the complete absence of a duplicate/in-flight check (unlike the newer v2 handler which explicitly guards against this) makes it a real, reachable weakness in a still-shipped, unprivileged, internet-facing code path.

### Recommendation
- In `HandleLegacyUserMessage`, reject (or otherwise safely handle) registration of a new callback when `savedCallbacks[msg.Body.MessageID]` already exists and is not expired, mirroring the "duplicate request ID"/"in-flight request" protection already implemented in `httpTriggerHandler.HandleUserTriggerRequest` (v2).
- Bind the saved callback to a stronger, non-reusable identifier (e.g., include a gateway-generated nonce or the original caller's signature/session ID) rather than relying solely on an untrusted, caller-controlled `MessageID`.
- Alternatively, scope `savedCallbacks` per-connection/per-caller instead of a single shared, cross-user map keyed by an attacker-influenced string.

### Proof of Concept
Conceptual PoC (Go, using existing test harness patterns in `handler_test.go`):
1. Send request R1 via `handler.HandleLegacyUserMessage` with `MessageID = "shared-id"` and callback `cb1`.
2. Before any DON node responds, send request R2 via `handler.HandleLegacyUserMessage` with the same `MessageID = "shared-id"` and callback `cb2`. Observe `h.savedCallbacks["shared-id"]` now points to `cb2`, silently overwriting `cb1` — no error is returned to the second registrant.
3. Simulate a DON node response for `MessageID = "shared-id"` via `handler.HandleNodeMessage`. Observe that `cb2.Wait()` receives the response (intended for R1's requester), while `cb1.Wait()` never resolves (times out), demonstrating that R1's originator never receives its own response and R2's originator instead receives R1's data.

Note: I was unable to fully confirm whether the outer `gateway.ProcessRequest`/legacy DON-config wiring adds any additional per-caller isolation before reaching `HandleLegacyUserMessage` in production deployments (index coverage limits on some wiring/config files); the described race is demonstrable purely within the `handler` struct's own state as shown above.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
