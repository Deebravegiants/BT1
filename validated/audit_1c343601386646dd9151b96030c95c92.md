### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `x-shopify-shop-domain` header as the tenant identity passed to the app's handler. Any party who can obtain one genuinely-signed webhook payload (e.g. by installing the app on their own store) can replay that exact body to the app's webhook endpoint with a different `shop-domain` header and have it accepted as coming from another shop, because the shop field is never part of the signed data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

The `shop` accessor is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header, entirely outside the signed payload: [2](#0-1) 

`Registry.process` validates the webhook using `Utils::HmacValidator.validate(request)`, which in turn calls `validate_signature`, comparing the computed HMAC of `to_signable_string` (i.e. the body only) against the received signature: [3](#0-2) 

After this check passes, `Registry.process` immediately builds `WebhookMetadata` using `request.shop` — the unauthenticated header value — and dispatches it to the app's registered handler as the tenant identity for the event: [4](#0-3) [5](#0-4) 

The identity binding that should hold — *the shop whose secret produced this HMAC* == *the shop the handler is told the event belongs to* — is broken: the HMAC is computed with the app's single shared `client_secret` (identical for every installed shop), and the `shop` field used by the handler is never bound to that signature at all.

### Impact Explanation
This is a cross-tenant identity-binding break (`Impact: Critical - cross-tenant access`). An attacker who is an unprivileged merchant with the app legitimately installed on their own store receives real webhook deliveries for their own shop, each with a valid HMAC computed from the shared `client_secret`. Because `to_signable_string` never incorporates the shop domain, the attacker can replay that exact body (and therefore the exact valid HMAC) directly to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for any victim shop domain. `Registry.process` will accept the forged request as authentic and hand the handler a `WebhookMetadata` claiming the event originated from the victim shop, letting the attacker inject or spoof data (orders, app-uninstall notices, GDPR events, etc.) attributed to a tenant they do not control.

### Likelihood Explanation
Requires only that the attacker be able to install the app on any shop they control (a normal, unprivileged merchant capability) and send an HTTP request directly to the app's public webhook endpoint — no access token, secret, or privileged account is needed. This is a realistic and low-effort attack path.

### Recommendation
Bind the shop identity to the authenticated payload rather than trusting the header alone: include the shop domain in the HMAC-signed material (or require the consuming application, and ideally the gem's own `Request`/`Registry.process` API, to cross-check `request.shop` against a shop that is independently known/authorized, e.g. an already-stored session for that shop) before dispatching `WebhookMetadata` to handlers. At minimum, document prominently and enforce in `Registry.process` that `request.shop` must be validated against the app's known/installed shop list, since it is not itself authenticated by the HMAC.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, receiving a legitimate webhook such as `orders/create` with body `B` and a valid `X-Shopify-Hmac-SHA256` header computed as `HMAC(client_secret, B)`.
2. Attacker sends a POST directly to the app's webhook endpoint with the same body `B`, the same valid HMAC header, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` [6](#0-5)  which passes because it only checks `B` against the signature, ignoring the shop header.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and processes the attacker-controlled body as if it were genuinely sent by/about `victim.myshopify.com`.
