### Title
Webhook `shop`, `topic`, and `webhook_id` values are trusted from unauthenticated HTTP headers while only the raw body is HMAC-verified - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC of the raw request body only, then dispatches to the handler using `shop`, `topic`, `api_version`, and `webhook_id`, all of which are read from HTTP headers that are never covered by that HMAC. This breaks the identity binding `hmac-verified bytes == data acted upon`, letting an attacker who possesses any one validly-signed webhook body (e.g., from a webhook delivered to a store they control) resubmit it with a forged `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header to make the host application process/attribute that payload to a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all parsed directly from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (i.e., only the body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` performs this HMAC check and then immediately trusts the unauthenticated header-derived `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` to build `WebhookMetadata` and dispatch to the app's handler: [4](#0-3) 

The identity binding that is broken:
`hmac_valid(raw_body) == true` is treated as equivalent to `shop header == the shop that produced raw_body`, but the two are independent — the HMAC says nothing about which shop, topic, or webhook_id the body belongs to.

Because any Shopify merchant can install an app and receive legitimately-signed webhooks addressed to their own store, an attacker who is a merchant of the app (an "unprivileged internet user" relative to other tenants) can capture a validly-signed webhook body+HMAC for their own shop, then replay that exact body+HMAC to the app's webhook endpoint while substituting a different `shop-domain` (and/or `topic`/`webhook_id`) header value naming a victim shop. Since the header is never part of the signed content, `HmacValidator.validate` still returns `true`, and `Registry.process` dispatches the payload to the handler labeled with the attacker-chosen shop.

### Impact Explanation
This is a cross-tenant data-integrity/confusion vector: the host application's webhook handler (`WebhookHandler#handle`) receives `WebhookMetadata.shop` set to an attacker-controlled value while processing another tenant's real event body, or vice versa — an attacker's own webhook body can be attributed to a victim shop. Any host app that keys persistence, authorization, or side effects (e.g., "update order data for `shop`", "delete customer data for `shop`" for GDPR topics) off `WebhookMetadata.shop` without an independent shop-membership check can have data written, deleted, or leaked under the wrong tenant. This matches the Critical "cross-tenant access" impact category, since it lets one tenant's request path cause the app to act on/attribute data belonging to a different tenant.

### Likelihood Explanation
Requires the attacker to be able to send arbitrary HTTP requests to the app's public webhook endpoint (an unprivileged internet capability) and to have obtained at least one validly-signed webhook body (trivially available to any merchant who installs the app on their own store, since they receive real webhooks addressed to themselves). No access to `api_secret_key`, access tokens, or any privileged credential is required — only a raw body + hmac pair that Shopify itself already delivered to the attacker's own tenant. This makes the likelihood realistic for any host application that trusts `WebhookMetadata.shop`/`topic`/`webhook_id` without further verification, which is the documented and expected usage pattern of this gem's webhook API.

### Recommendation
Bind the header-derived identity fields into the signed material, or otherwise cryptographically verify them against the caller's known configuration:
- Extend `to_signable_string` (or add a second verification step) to incorporate `shop`, `topic`, and `webhook_id`/`api_version` into the HMAC computation, matching the raw body concatenation Shopify actually signs, so tampering with any of these headers invalidates the signature.
- At minimum, document and/or enforce that `Registry.process` verify `request.shop` corresponds to a shop the app has an active, stored session/installation record for before dispatching to the handler, closing the gap where header values are trusted purely on the strength of a body-only HMAC.

### Proof of Concept
```ruby
require "openssl"
require "base64"

secret = ShopifyAPI::Context.api_secret_key
body = '{"id":123,"note":"legit order for attacker-owned-shop.myshopify.com"}'

# Attacker legitimately receives this webhook for their own shop:
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body)
encoded_hmac = Base64.encode64(hmac)

# Attacker replays the same signed body but swaps the shop-domain header
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => encoded_hmac,      # still valid: body unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, unauthenticated
  "x-shopify-webhook-id" => "attacker-controlled-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

# Passes: HmacValidator only checked the body, not the shop header
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle is invoked with WebhookMetadata.shop == "victim-shop.myshopify.com"
#    even though the signed payload actually originated from the attacker's own shop.
```

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)

        end
