### Title
Webhook shop-domain/topic identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop`, `topic`, `webhook_id`, and `api_version` values that identify *which tenant and event* the webhook belongs to are taken from unauthenticated HTTP headers and passed straight into the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read directly from headers with no cryptographic binding to the signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)`, then immediately builds `WebhookMetadata` using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`, and dispatches it to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) and the shared `api_secret_key`: [4](#0-3) 

The identity binding the gem implicitly relies on is: `HMAC-verified bytes == (shop, topic, webhook_id)` used to route/attribute the event. In fact the equality only holds for the body; the header-derived shop/topic/webhook_id are never part of the signed material, so:

`HMAC-verified bytes (body only) ≠ tenant-identifying fields (shop, topic, webhook_id) delivered to the handler`

An unprivileged party who can obtain any single genuinely-Shopify-signed webhook body (e.g. a merchant who installed the app and receives their own legitimate webhooks) can replay that exact body with the same valid HMAC, while substituting the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers for a different (victim) shop or a different topic. `HmacValidator.validate` will still return `true` because it only checks the body against the secret, and `Registry.process` will hand the forged `shop`/`topic`/`webhook_id` to the app's `WebhookHandler#handle`, which per the gem's own documentation is expected to key persistence/business logic (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) off these exact fields: [5](#0-4) 

This is the same bug class as the reported "unrwap parameter not covered by the guard" issue: a value that is *acted upon* (shop attribution, topic routing) is not covered by the authenticity check (HMAC) that is supposed to protect the whole trust decision.

### Impact Explanation
Because `data.shop` and `data.topic` are trusted without being bound to the HMAC-verified payload, an attacker-controlled webhook can be misattributed to a different, victim tenant (shop) inside apps that rely on the gem's documented `WebhookMetadata#shop`/`#topic` to select which merchant's records to update. This is a cross-tenant data-integrity/confusion issue in a multi-tenant Shopify app — the strongest applicable impact bucket here is "Critical – cross-tenant access," since the forged `shop` value can cause writes/enqueued jobs to be associated with, or executed against, a different merchant's account than the one that actually produced the signed payload.

### Likelihood Explanation
Exploitation requires the attacker to already possess at least one validly-signed webhook body for the shared `api_secret_key` (trivial for any merchant who has installed the app, since they legitimately receive webhooks) and the ability to POST arbitrary headers to the app's public webhook endpoint (any internet-reachable HTTP client). No access token, refresh token, or `client_secret` needs to be exfiltrated — only reuse of a header-and-body combination the attacker's own tenant already legitimately received. This makes the likelihood moderate-to-high for any app that keys internal logic off `WebhookMetadata#shop`/`#topic` as instructed by the gem's own documentation.

### Recommendation
Bind the tenant/event-identifying headers into the HMAC-signed material (e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string`, or independently verify `shop`/`topic` against Shopify's webhook-registration records / an authenticated channel) before constructing `WebhookMetadata` and invoking the handler in `Registry.process`.

### Proof of Concept
```ruby
# Attacker is a merchant with the app installed; legitimately receives a webhook:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => VALID_HMAC_FOR_BODY,   # computed by Shopify using the shared api_secret_key
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
  "x-shopify-webhook-id" => "real-id",
  "x-shopify-api-version" => "2024-01",
}
body = '{"id": 1, "note": "hello"}'

# Attacker replays the identical body + valid HMAC but swaps the shop header:
forged_headers = headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) still returns true (only body is checked),
# and the app's handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
# even though Shopify never sent this event for victim-shop.
```

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
