### Title
Fee-on-transfer tokens desynchronize escrow accounting from actual balances in Tron `IntentGatewayV2.placeOrder` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits escrow using the user-declared `order.inputs[i].amount` (minus protocol fee) via `safeTransferFrom`, without verifying the amount actually received by the contract. If the input token charges a transfer fee (e.g. USDT-style fee-on-transfer, which can be toggled on for TRC20/ERC20-compatible tokens on Tron), the contract will credit more escrow than it actually holds, breaking the core invariant that escrowed accounting must be backed 1:1 by real token balances.

### Finding Description
In the no-predispatch branch of `placeOrder`: [1](#0-0) 

the contract calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is derived purely from the pre-transfer, user-declared `order.inputs[i].amount` (only reduced by the protocol fee basis points), not from any measured balance delta.

This is in stark contrast to the audited/fixed main EVM contract `evm/src/apps/IntentGatewayV2.sol`, which explicitly measures `balBefore`/`balanceOf` deltas around `safeTransferFrom` specifically to defend against fee-on-transfer tokens: [2](#0-1) 

The code comment in the main contract even states: "For fee-on-transfer tokens, the gateway receives less than the requested amount. We mutate order.inputs to reflect actual received so the commitment and escrow are consistent with what the gateway holds." — confirming this exact bug class was identified and remediated in the primary EVM deployment but the fix was not ported to the Tron deployment.

The predispatch branch of the same Tron contract does perform balance/dust accounting via `IERC20.balanceOf(dispatcher)` checks and `DustCollected` events: [3](#0-2) 

but this only measures dust in the *dispatcher-to-gateway sweep* step (assuming the initial `safeTransferFrom(msg.sender, dispatcher, amount)` into the dispatcher was received in full); it does not correct for fee loss on the very first `safeTransferFrom` into the dispatcher either, and the simple (non-predispatch) path has no accounting at all.

### Impact Explanation
`_orders[commitment][token]` is the ledger used later to pay out solvers via `RedeemEscrow`/withdrawal and refund flows. If it is inflated relative to the gateway's actual token balance (because a fee-on-transfer token skimmed part of the transfer), then honoring escrow redemptions for this or other orders will attempt to pay out more tokens than the contract holds. This is either an outright insolvency (later legitimate redemptions revert/fail, permanently freezing other users' funds) or, if enough surplus previously accumulated from other sources exists, a direct value leak from the protocol/other users' escrow to whoever redeems first — matching "concrete theft or permanent freezing of funds" from a single `placeOrder` call by any unprivileged user.

### Likelihood Explanation
Reachable by any external, unprivileged caller placing an order (`placeOrder` is `public payable`, no access control) using a fee-on-transfer token as an input asset. USDT's fee-on-transfer switch is dormant today but can be activated by Tether at any time without contract changes, and other fee-on-transfer tokens (which the intent-gateway does not appear to whitelist against) could be used deliberately by a malicious order-placer to desynchronize accounting. This mirrors exactly the reported analog bug class (fee-on-transfer breaking a 1:1 deposit/credit invariant), and the maintainers' own fix in the sibling EVM contract confirms the root cause is real and previously acknowledged for this codebase family.

### Recommendation
Port the balance-delta measurement pattern already used in `evm/src/apps/IntentGatewayV2.sol` (lines 312-329) to the Tron `IntentGatewayV2.placeOrder`: for each ERC20 input in both the predispatch and non-predispatch paths, record `balanceOf(address(this))` before and after `safeTransferFrom`, use the actual delta as the received amount for computing `reducedInputs`/escrow credit and the commitment hash, and emit `DustCollected` for any positive difference between declared and received amounts.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with an input token that implements a fee-on-transfer (e.g. 1% fee), analogous to USDT with fees enabled.
2. User calls `placeOrder` with `order.inputs[0] = {token: feeToken, amount: 1000e6}` and no predispatch.
3. `safeTransferFrom(msg.sender, address(this), 1000e6)` executes, but due to the 1% fee, the gateway's actual balance only increases by `990e6`.
4. `_orders[commitment][feeToken]` is nonetheless credited with `reducedInputs[0].amount` computed from the full `1000e6` (minus only the protocol fee bps), e.g. `990e6` if protocol fee is 1%, or `1000e6` if protocol fee is 0 — in either case potentially exceeding the `990e6` actually held.
5. When a solver fills the order and later a `RedeemEscrow` request instructs the gateway to pay out `_orders[commitment][feeToken]` to the filler, the transfer either reverts (freezing the filler's legitimate payout and any co-mingled escrow in the same token) or succeeds by drawing down unrelated escrowed balances of other orders in the same token, socializing the loss across other users' funds.
