## Title
Webhook shop identity not covered by HMAC signature enables cross-tenant webhook injection - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw request body only, while the `shop` value that the host application uses to route/attribute the webhook payload to a specific merchant tenant comes from an HTTP header that is never included in the signed content. Any user who can obtain one valid `(body, hmac)` pair — e.g., by owning a store that installed the app and receiving a legitimate webhook for their own shop — can replay that exact body/HMAC pair while substituting the `shop-domain` header to any other shop that also uses the app. `Utils::HmacValidator.validate` will still report the signature as valid, and `Webhooks::Registry.process` will hand the payload to the app's handler tagged with the attacker-chosen `shop`, i.e. wrong-tenant data injection.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` (and `topic`, `webhook_id`, `api_version`) are read straight from HTTP headers and never enter the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` uses the result of that validation as the sole authenticity gate, then immediately trusts `request.shop` (the unauthenticated header) to build the `WebhookMetadata` handed to the host app's handler: [4](#0-3) 

The broken identity binding, stated as an equality that the gem fails to enforce:
`shop bytes verified by HMAC == shop bytes used to attribute/act on the webhook payload`

In truth: `shop bytes verified by HMAC == "" (nothing — shop is not part of the signed string)`, while `shop bytes used to act on the payload == request.shop` (header-derived, attacker-controllable in a replay). This is exactly the "bytes verified vs. bytes parsed / field acted on but not covered by the HMAC" class of bug called out for this scan.

### Impact Explanation
Any tenant of a multi-tenant app built on this gem (an "unprivileged internet user" relative to other merchants) can capture a legitimate webhook delivered for their own shop (body + valid `hmac-sha256` header, both attacker-visible since they control the receiving endpoint or can intercept their own store's webhook deliveries) and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to a victim shop domain. Because `HmacValidator.validate` never covers the shop header, the forged request passes validation, and `Registry.process` invokes the host app's handler with `WebhookMetadata#shop` set to the victim's domain and the attacker's own webhook body. If the host application uses that `shop` value to key its per-tenant data store (the common and documented pattern for consuming `ShopifyAPI::Webhooks`), this results in cross-tenant data injection/corruption — writing attacker-controlled data (e.g., fake order/customer/inventory events) into a different merchant's tenant record, satisfying the "cross-tenant access" Critical impact bar.

### Likelihood Explanation
High for any app that has at least one merchant install (trivial to obtain as an unprivileged user by installing the app to their own store), since:
- Obtaining a valid `(body, hmac)` pair requires no privileged access — any merchant using the app receives such webhooks for their own store.
- Forging the header on replay requires no cryptographic material at all — `api_secret_key` is never needed by the attacker.
- The gem's `Registry.process` performs no additional binding between the verified bytes and the `shop` header before dispatching to the handler.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the bytes that are HMAC-verified, or otherwise cryptographically bind the header-derived `shop` to the signed payload before it is trusted. At minimum, `Webhooks::Request#to_signable_string` should incorporate the `shop-domain` header value, and `HmacValidator`/`Registry.process` should reject a request if the shop asserted by headers cannot be tied to the verified signature. Documentation/host-app guidance should also explicitly warn that `WebhookMetadata#shop` is derived from an unauthenticated header and must not be trusted for tenant routing without additional verification (e.g., cross-checking against a known/authorized shop list).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and captures a legitimately delivered webhook: raw body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared secret, computed by Shopify).
2. Attacker replays the exact same HTTP request to the app's webhook endpoint, changing only:
   - `x-shopify-shop-domain: victim.myshopify.com`
   - keeping raw body `B` and header `x-shopify-hmac-sha256: H` unchanged.
3. Server-side, the app calls `ShopifyAPI::Webhooks::Registry.process(request)`:
   - `Utils::HmacValidator.validate(request)` recomputes HMAC over `request.to_signable_string` (`== B`), matches `H`, returns `true` — see [5](#0-4) 
   - `Registry.process` proceeds and calls the handler with `shop: request.shop`, which now returns `"victim.myshopify.com"` — see [6](#0-5) 
4. The host application's handler processes attacker-controlled body `B` as if it were an authentic event for `victim.myshopify.com`, resulting in cross-tenant data injection.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
