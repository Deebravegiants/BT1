### Title
Emporium `signerAddress == address(0)` + zero-token dimensions bypasses all authorization and balance checks, allowing theft of Emporium's ETH — (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `Dimensions.tokenNumber == 0` and `CircomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID`, `Hinkal.transact` routes to the "Emporium-min" proof path (`formInputEmporiumMin`) which emits zero UTXO/nullifier/root constraints, and `EmporiumUpgradeable.runAction` skips the EIP-712 signature check entirely when `EmporiumStack.signerAddress == address(0)`. Combined with an empty `erc20TokenAddresses` array (which makes every balance-conservation loop in both `Hinkal.transact` and `EmporiumUpgradeable.runAction` iterate zero times), an attacker can execute an arbitrary `EmporiumOperation` that sends Emporium's ETH balance to any address with no on-chain or in-circuit check that the value ever left.

### Finding Description
The broken equality is value conservation: tokens leaving an action must equal `-deltaAmountChangesForThatAction`. Here `deltaAmountChanges` is the empty array (since `circomData.erc20TokenAddresses.length == 0`), so the constrained "value moved" is `0`, while `op.value` (real ETH) actually leaves the Emporium contract.

Path:
1. `Hinkal.transact` calls `hinkalHelper.performHinkalChecks`, which calls `dimensionsCheck` [1](#0-0) . All the length checks pass trivially for `tokenNumber=0` since every array involved (`erc20TokenAddresses`, `amountChanges`, `onChainCreation`, `slippageValues`, `inputNullifiers`) is empty. There is no minimum-`tokenNumber` requirement anywhere in `HinkalHelper.sol` or `Dimensions.sol` [2](#0-1) .
2. `CircomDataBuilder.formInputForCircom` detects `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0` and calls `formInputEmporiumMin`, which produces only 3 public inputs (`emporiumMessage`, `timeStamp`, `calldataHash`) [3](#0-2) .
3. `MainEVMCircuit(tokenCount=0,...)` has its entire per-token loop (nullifier checks, root-hash checks, `inTotal+amountChanges===outTotal`) skipped because it iterates `for (var i=0; i<tokenCount; i++)` with `tokenCount=0` [4](#0-3) . The proof only needs a self-consistent EdDSA signature over the attacker's own freshly generated keypair — it proves nothing about ownership of any UTXO or of the Emporium's funds.
4. `Hinkal.transact` computes `oldBalances`/`newBalances` and the balance-diff/slippage/UTXO-amount checks only over `circomData.erc20TokenAddresses`, which is empty, so this loop never executes [5](#0-4) .
5. `_externalTransact` builds `deltaAmountChanges` as an empty array (also looping over the empty `erc20TokenAddresses`) and calls `EmporiumUpgradeable.runAction` [6](#0-5) .
6. Inside `runAction`, `balancesBefore`/`balancesAfter` are computed over the same empty array, so the entire `for` loop that checks `balanceChange < 0` and enforces `handleOut` never runs [7](#0-6) .
7. `verifyWallet` is called with `stack.signerAddress == address(0)`; it marks `emporiumMessage` used and returns immediately, performing **no** ECDSA verification of `stack.ops`, `endpoint`, or `value` [8](#0-7) .
8. The stateless branch then executes `op.endpoint.call{value: op.value}(op.callData)` with attacker-supplied `endpoint`/`value`/`callData`, draining ETH held by the Emporium contract to the attacker's endpoint [9](#0-8) .

No guard catches this: `dimensionsCheck`/`checkOnchainCreation` only validate array-length consistency, not `tokenNumber > 0`; `performHinkalChecks`'s `calldataHash` check only ensures self-consistency of the calldata that was submitted by the attacker (it commits to `externalActionData`, but that only proves the attacker didn't tamper with their own submitted call — it grants no authorization over funds); the circuit constrains nothing about `op.value`/`ops` because `tokenCount=0` disables the whole per-token loop; and `verifyWallet` explicitly no-ops when `signerAddress==address(0)`.

### Impact Explanation
Critical — direct, permissionless theft of ETH held by the `EmporiumUpgradeable` contract, which is funded by other users' shielded/in-flight deposits from prior legitimate transacts. Repeatable for every `emporiumMessage` nonce (each drain requires one fresh `emporiumMessage`), and each call can steal the entire current ETH balance of Emporium in one transaction.

### Likelihood Explanation
Preconditions are minimal and attacker-controlled: Emporium must hold nonzero ETH (a normal, expected steady state given prior user activity), and the attacker needs only their own keypair to generate a trivially satisfiable `tokenCount=0` proof plus a deployed contract to receive the ETH. No privileged role, victim key, or special timing is required — the attack is a single, ordinary call to `Hinkal.transact` and fully repeatable whenever Emporium holds a balance.

### Recommendation
- Reject `runAction` calls where `stack.signerAddress == address(0)` unless `stack.ops` is provably empty or every `op.value == 0`, since the address-zero branch is meant only for value-neutral/prepaid-via-UTXO cases.
- For the Emporium-min (`tokenCount==0`) path, require that the sum of `op.value` across all `stack.ops` equals zero unless it is explicitly accounted for by a verified value-in/value-out mechanism (e.g., require `erc20TokenAddresses` to include `address(0)` whenever any `op.value > 0`, so the existing balance-conservation loop actually executes).
- Alternatively, always compute Emporium's ETH balance before/after `runAction` regardless of whether `address(0)` is present in `erc20TokenAddresses`, and revert if the balance decreased without a matching, signed authorization.

### Proof of Concept
Hardhat/Foundry fork test:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, register Emporium under `HINKAL_EMPORIUM_ACTION_ID` via `registerExternalAction`.
2. Victim performs a normal `transact` with `tokenNumber>=1`, `externalActionId=HINKAL_EMPORIUM_ACTION_ID`, positive `deltaAmountChange` for `address(0)` (ETH), and a signed `EmporiumStack` (`signerAddress != 0`) depositing ETH into Emporium. Assert `address(emporium).balance` increased by the deposit amount.
3. Attacker deploys a receiver contract `AttackerSink` with a payable `receive()`.
4. Attacker builds `CircomData` with `erc20TokenAddresses=[]`, `dimensions.tokenNumber=0`, `externalActionData.externalActionId=HINKAL_EMPORIUM_ACTION_ID`, `externalActionMetadata = abi.encode(EmporiumStack({v:0,r:0,s:0,signerAddress:address(0), ops:[EmporiumOperation({endpoint: address(AttackerSink), invokeWallet:false, value: uint128(address(emporium).balance), callData: "0x"})], maxFee:0, deadline:type(uint256).max}))`, and a fresh `emporiumMessage`.
5. Generate a valid `MainEVMCircuitMin0` proof using attacker's own random EdDSA keypair (no relation to victim's UTXOs), matching `formInputEmporiumMin`'s public inputs (`emporiumMessage`, `timeStamp`, `calldataHash`).
6. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from the attacker EOA.
7. Assert: (a) call succeeds without revert, (b) `address(emporium).balance` before minus after equals `address(AttackerSink).balance` gain, and (c) `circomData.amountChanges`/`deltaAmountChanges` remained the empty array throughout, proving `0 != op.value` — the broken equality.
