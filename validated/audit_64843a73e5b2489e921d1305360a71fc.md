### Title
Accrued RAY-valued debt can overflow `i128` and freeze a high-utilization market - ([File: common/src/rates/index.rs](common/src/rates/index.rs))

### Summary
XOXNO does not multiply a principal by `10^(collateral_decimals + principal_decimals)`, but it has the analogous representability failure: RAY-scaled debt shares are multiplied by the growing borrow index and the result must fit in `i128`. [1](#0-0)  A sufficiently large, highly utilized market can therefore reach a state where the next accrual panics with `MathOverflow` before `MAX_BORROW_INDEX_RAY` can protect later accounting. [2](#0-1) 

### Finding Description
`calculate_supplier_rewards` computes both `borrowed * old_borrow_index / RAY` and `borrowed * new_borrow_index / RAY` through `Ray::mul`. [1](#0-0)  `Ray::mul` uses an overflow-safe `I256` intermediate but still converts the final result back to `i128`, panicking when that result is unrepresentable. [3](#0-2)  The decimal-rescaling cap only guarantees that the original asset amount fits after conversion to RAY; it does not guarantee that the accrued share value still fits after index growth. [4](#0-3) 

A borrower can create the large debt through `borrow`, while any caller can later advance the market through `update_indexes`. [5](#0-4) [6](#0-5)  Pool accrual delegates each elapsed chunk to `accrue_step`, which reaches the overflowing debt-value calculation. [7](#0-6) [8](#0-7)  Once the overflow threshold is crossed, withdrawals and repayments hit the same accrual panic, and liquidation cannot rescue the position because liquidation also operates after market synchronization. [9](#0-8) 

### Impact Explanation
All supplier funds in the affected market become frozen, borrower repayment is impossible, and liquidation or bad-debt processing cannot proceed through the ordinary accrual path. [9](#0-8)  This is a permanent freezing of funds under the deployed code, subject only to a privileged contract upgrade or other out-of-band remediation. [10](#0-9) 

### Likelihood Explanation
The attack requires a very large market and enough collateral to borrow a substantial fraction of it, then sustained index growth until `scaled_debt * borrow_index / RAY` exceeds `i128::MAX`. [1](#0-0)  Listing caps admit up to roughly `i128::MAX / 10^(27 - decimals)` base units, equivalent to about 170 billion whole tokens regardless of supported decimals, so the cap bound does not by itself bound the post-accrual value. [11](#0-10)  The in-repository reproduction uses a one-billion-token, 18-decimal market at 98% utilization and demonstrates that `update_indexes`, `withdraw`, and `repay` all revert with `MathOverflow`. [12](#0-11) 

### Recommendation
Bound admitted market exposure by the maximum accrued RAY value, not merely by the amount that can be converted from asset units to RAY. [13](#0-12)  In particular, enforce `scaled_supply * MAX_SUPPLY_INDEX_RAY / RAY <= i128::MAX` and `scaled_debt * MAX_BORROW_INDEX_RAY / RAY <= i128::MAX`, or store accrued totals in a wider representation before converting individual payable amounts back into the supported domain. [1](#0-0)  Accrual should also clamp or otherwise safely handle the index before calculating an unrepresentable total debt value. [2](#0-1) 

### Proof of Concept

```rust
// Preconditions:
// - `debt_asset` is a listed 18-decimal market with approximately 1e9 whole
//   tokens supplied by users.
// - `collateral_asset` is listed collateral in the same spoke.
// - The attacker has enough collateral value to borrow ~98% of `debt_asset`.

let account_id = controller.supply(
    attacker,
    0,
    spoke_id,
    vec![(collateral_key, sufficient_collateral)],
);

controller.borrow(
    attacker,
    account_id,
    vec![(debt_key, roughly_98_percent_of_pool_liquidity)],
    Some(attacker),
);

// After sustained high-utilization accrual:
controller.update_indexes(attacker, vec![debt_key]);
// -> GenericError::MathOverflow

// Every subsequent synchronized exit path hits the same panic:
controller.repay(attacker, account_id, vec![(debt_key, 1)]);
controller.withdraw(
    supplier,
    supplier_account_id,
    vec![(debt_key, 0)],
    Some(supplier),
);
```

The existing reproduction constructs this state with `1_000_000_000 * 10^18` supplied units and a 98% borrow, then asserts `MathOverflow` from `update_indexes`, `withdraw`, and `repay`. [12](#0-11)

pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
