No vulnerability found for this question.

**Analysis:** The premise requires a "later change to collection burnability settings" after minting, but no such mutator exists. The `AptosCollection.tokens_burnable_by_creator` field is set once in `create_collection_object` at collection creation [1](#0-0)  and there is no entry function, setter, or mutator_ref that ever writes to this field afterward — unlike `mutable_description`/`mutable_uri` which have dedicated `set_collection_description`/`set_collection_uri` functions gated by their own flags [2](#0-1) .

Since `tokens_burnable_by_creator` is immutable for the lifetime of the collection, `mint_internal`'s read of `collection.tokens_burnable_by_creator` at mint time [3](#0-2)  always reflects the collection's one true, permanent policy. Consequently, `is_burnable`'s report — which simply checks whether the per-token `burn_ref` is `option::some` [4](#0-3)  — always matches the token's actual burnability, and `burn` independently re-validates `burn_ref.is_some()` before burning [5](#0-4) . There is no code path by which an unprivileged caller (or even the creator) can toggle this setting after tokens exist, so the described "corruption" scenario cannot be constructed against production custody logic.
