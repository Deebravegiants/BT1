Audit Report

## Title
Proxy `InstanceFilter` restriction is not propagated when a proxied call is wrapped in `Multisig::as_multi_threshold_1`, because that pallet dispatches the inner call on a freshly constructed origin - (File: substrate/frame/proxy/src/lib.rs, substrate/frame/multisig/src/lib.rs)

## Summary
`Proxy::do_proxy` attaches an `InstanceFilter`-based closure to a `RawOrigin::Signed(real)` origin via `origin.add_filter(...)` and dispatches the outer call on that origin [1](#0-0) . When the outer call is `Multisig::as_multi_threshold_1`, that function calls `ensure_signed(origin)` to recover `who`, derives a new account `id = Self::multi_account_id(&signatories, 1)`, and dispatches the inner call via `call.dispatch(RawOrigin::Signed(id.clone()).into())` — a brand-new `RuntimeOrigin` value that only carries the default `BaseCallFilter`, not the closure `do_proxy` pushed onto the original origin object [2](#0-1) . This is confirmed by `origin.add_filter` being a per-value operation on `RuntimeOrigin` (it wraps the existing closure and stores it on that specific `RuntimeOrigin` struct instance) [3](#0-2) , and a freshly-constructed `RawOrigin::Signed(id).into()` starts with the default filter rather than inheriting any filter chain from the caller's origin object.

## Finding Description
The root cause is architectural: `OriginTrait::add_filter` mutates a specific `RuntimeOrigin` value in place; it is not something that is regenerated deterministically from an `AccountId`. `pallet_multisig::as_multi_threshold_1` and `Pallet::<T>::operate` (used by `as_multi`/`approve_as_multi`) both construct a brand-new origin — `RawOrigin::Signed(id).into()` — to represent the multisig account, and dispatch the inner call on that new value [4](#0-3) [5](#0-4) . This is unlike `pallet_utility::batch_all`, which explicitly clones and re-filters the *same* origin (`origin.clone()` plus an additional `add_filter`) before dispatching nested calls, thereby preserving the caller's filter chain [6](#0-5) .

Confirmed behavior: `multisig_filters` test shows that only the pallet's static `BaseCallFilter` (blocking things like `set_code`) still applies to the inner call — it does not test or demonstrate that a caller-supplied dynamic filter (such as the one `do_proxy` attaches) is preserved [7](#0-6) . This is consistent with the claim that the proxy's `InstanceFilter` closure specifically (as opposed to the runtime's static `BaseCallFilter`) is lost across the multisig account-changing dispatch.

One correction to the claim's PoC: `as_multi_threshold_1` requires `other_signatories` to be non-empty (`ensure!(!other_signatories.is_empty(), Error::<T>::TooFewSignatories)`) [8](#0-7) , so the exact PoC step using `other_signatories: vec![]` would fail before reaching the dispatch. This does not invalidate the core finding — an attacker can simply supply one arbitrary other signatory account and the underlying mechanism (fresh, unfiltered `RawOrigin::Signed(id)`) is unchanged — but it shows the submitted PoC as literally written is not directly reproducible and needed correction.

## Impact Explanation
The security-relevant fact acknowledged in the report itself is correct and important: the resulting inner-call dispatch happens as `Signed(multi_account_id(&signatories, 1))`, a deterministic pseudonym account derived from `real` (and any chosen extra signatories), not as `real` itself. This is a materially different origin than the one `real`'s primary account operates under, and it holds no privileges or balance unless something has specifically funded/authorized that derived account. The proxy `InstanceFilter` is designed to restrict what a delegate can do "as `real`"; this pseudonym-account redirection means the specific privileged call executes under an account that is, by default, unfunded and without prior state, so there is no guaranteed concrete loss of `real`'s assets or privileges from this alone. The report is honest about this bound, framing the guaranteed impact as "filter-bypass/unauthorized dispatch" rather than "guaranteed fund drain," and notes the impact only becomes concrete if that specific pseudonym account happens to hold state (e.g., due to a prior legitimate multisig operation by `real`).

## Likelihood Explanation
The mechanism itself is real, deterministic, and requires no privileged access — any account holding proxy delegate rights over `real` with a `ProxyType` that permits `RuntimeCall::Multisig(..)` could invoke this pattern. This is a plausible configuration in general.

## Recommendation
As given in the original report: pallet_proxy's filter closures (or `InstanceFilter::filter` implementations) should recursively unwrap known origin-redirecting composite calls (`Multisig::as_multi`, `Multisig::as_multi_threshold_1`) before deciding whether to permit them, or restrictive `ProxyType`s should not blanket-permit `RuntimeCall::Multisig(..)`. Alternatively, `pallet_multisig` could be changed to propagate/re-apply the calling origin's filter chain onto the derived multisig origin before dispatching the inner call, analogous to how `pallet_utility::batch_all` re-filters rather than reconstructing the origin from scratch.

## Proof of Concept
Corrected version of the submitted PoC (which as-submitted uses an invalid empty `other_signatories` argument that would be rejected by `Error::<T>::TooFewSignatories`):
1. Configure a mock `ProxyType::NonTransfer` whose `filter()` returns `false` for a privileged call type but `true` for `RuntimeCall::Multisig(..)`.
2. `Proxy::add_proxy(real, delegate, ProxyType::NonTransfer, 0)`.
3. Confirm directly that `ProxyType::NonTransfer.filter(&RuntimeCall::Privileged(...))` is `false`.
4. Call `Proxy::proxy(delegate_origin, real, None, Box::new(RuntimeCall::Multisig(pallet_multisig::Call::as_multi_threshold_1 { other_signatories: vec![some_other_account], call: Box::new(privileged_call) })))`.
5. Observe that the inner call executes under `Signed(multi_account_id(&[real, some_other_account], 1))` and is not evaluated by `def.proxy_type.filter(c)`, in contrast to a direct `Proxy::proxy(delegate_origin, real, None, privileged_call)` which is correctly filtered.
6. Note that because the effective origin is the derived pseudonym account (not `real`'s primary account), demonstrating a concrete state-change impact additionally requires that pseudonym account to hold relevant balance/state — this should be included in the test to establish concrete impact rather than a bypass on an empty account.

		// This is a freshly authenticated new account, the origin restrictions doesn't apply.
