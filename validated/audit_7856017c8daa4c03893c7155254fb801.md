### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` (tenant) identifier that is subsequently trusted and handed to the app's handler is read from an HTTP header that is never included in the signed payload. This breaks the intended binding `hmac == HMAC(secret, body + shop)`; in reality `hmac == HMAC(secret, body)` only.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled directly from unauthenticated HTTP headers via `shopify_header`: [2](#0-1) [3](#0-2) 

`Registry.process` verifies only the HMAC of the body, then immediately trusts `request.shop` (along with `topic`/`webhook_id`) and forwards it to the registered handler as authenticated tenant context: [4](#0-3) 

Because the `shop` header is not part of `to_signable_string`, an attacker who has captured any one valid `(raw_body, hmac)` pair produced by Shopify for their own store (a normal, unprivileged webhook delivery visible to that store's own operator/app instance) can replay that exact body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` / `Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body: [5](#0-4) 

The forged request is then dispatched to the handler as `WebhookMetadata` carrying the attacker-chosen `shop` value, with no re-validation. Notably, the OAuth path in this same gem does perform host/shop trust validation via `ShopValidator.sanitize_shop_domain` before trusting a shop value: [6](#0-5) 
but no equivalent binding exists for webhook processing — the gem's own `Registry.process`/`Request` never checks that the signed body actually originated for the claimed `shop`.

### Impact Explanation
This allows an unprivileged actor (any merchant/store operator using the app) to inject webhook events that are attributed to a shop/tenant they do not own, since `shop` is the field host applications rely on to select per-tenant data, credentials, or record scoping. Any app that keys writes/state changes off `WebhookMetadata#shop` returned by this gem — which explicitly presents it as validated data after `Registry.process` succeeds — is exposed to cross-tenant data corruption/injection. This matches the High-severity class "cross-tenant access" achieved purely through this gem's own signature-verification logic.

### Likelihood Explanation
Exploitation requires the attacker to have legitimately obtained one valid `(raw_body, hmac)` pair, which any store owner with the app installed can obtain from their own genuine webhook traffic (e.g., by controlling a proxy/logging endpoint in front of their own webhook receiver, or observing their own app's logs). No access to `api_secret_key` or another tenant's credentials is required — only a header rewrite before the (unchanged) body is replayed to the shared webhook endpoint.

### Recommendation
Bind the shop identity into the signed material actually verified, or otherwise cryptographically tie `shop`/`topic` to the HMAC-covered payload. At minimum, `Webhooks::Request#to_signable_string` should incorporate the `shop`, `topic`, and `webhook_id` headers (as Shopify's webhook signature contract intends them to be immutable per-delivery), and/or `Registry.process` should independently validate that the shop domain is a trusted `myshopify.com` domain (reusing `Utils::ShopValidator`) and reject replays with mismatched shop/topic/webhook_id metadata.

### Proof of Concept
1. Attacker owns `attacker.myshopify.com`, which has the app installed and receives a legitimate webhook: `POST /webhooks` with body `{"id":1}` and headers `X-Shopify-Hmac-Sha256: <valid-hmac-for-body>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`.
2. Attacker captures this exact `(body, hmac)` pair (e.g., from their own server logs/proxy in front of their webhook receiver).
3. Attacker replays the identical body and HMAC to the same app endpoint but changes the header to `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body`: [7](#0-6) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes the attacker-controlled payload as if it came from the victim tenant.

        extend T::Sig

        sig do

            shop_domain: String,

        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end
