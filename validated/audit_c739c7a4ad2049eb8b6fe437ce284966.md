### Title
Webhook `shop` Domain Is Not Bound to the HMAC Signature, Enabling Cross-Tenant Shop Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from unauthenticated HTTP headers and are never included in the signed content. `Registry.process` validates only that the HMAC matches the raw body, then passes the caller-supplied `shop` header straight through to the app's webhook handler as the trusted tenant identifier. Any party who can obtain one validly-signed webhook body/HMAC pair (trivially, by installing the app on their own store) can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header, and the signature check will still pass.

### Finding Description
The identity binding that should hold is: `shop value trusted by the host application == shop value actually authenticated by the HMAC`. This binding is broken here because the `hmac` and `to_signable_string` methods on `Request` only cover the JSON body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers supplied with the request, completely outside the HMAC's coverage: [2](#0-1) 

`HmacValidator.validate` computes the signature strictly from `to_signable_string` (i.e., the body only), using the app's single shared `Context.api_secret_key`, which is identical for every shop that has the app installed: [3](#0-2) 

`Registry.process` raises only if the HMAC over the body fails, then forwards `request.shop` unchanged as the tenant identifier into `WebhookMetadata`, which the host application is documented to trust as "The shop domain of the webhook": [4](#0-3) [5](#0-4) 

The docs also explicitly promise that `Registry.process` "will verify the request did indeed come from Shopify," implying the whole record (including `shop`) is authenticated: [6](#0-5) 

Since the HMAC secret is shared across every shop that installs the app (it is the app's `client_secret`, not a per-shop secret), and `shop-domain` is not part of the signed payload, an unprivileged attacker can:
1. Install the target app on their own (attacker-owned) shop, legitimately triggering Shopify to send a real webhook with a valid `X-Shopify-Hmac-Sha256` value computed over some body `B`.
2. Capture that `(B, hmac)` pair.
3. POST directly to the app's public webhook endpoint with body `B`, the captured `hmac`, and an arbitrary `shopify-shop-domain` header set to a victim shop.
4. `HmacValidator.validate` succeeds (it only checks `B` against `hmac`), and the handler receives `WebhookMetadata` claiming the (attacker-controlled) body belongs to the victim shop.

If the host application uses `data.shop` to select which merchant's records/session to update (which is exactly what the field is documented for), this results in cross-tenant data confusion/injection — attacker-controlled webhook content is attributed to a victim shop.

### Impact Explanation
This breaks the shop-authentication binding at the core of the gem's webhook verification promise, allowing an attacker to inject forged data attributed to an arbitrary victim shop without needing the app's `client_secret` or any victim credentials — this is a cross-tenant integrity issue, matching the "cross-tenant access" impact category.

### Likelihood Explanation
Any developer/merchant able to install the target Shopify app on a shop they control (a normal, unprivileged action) can obtain a legitimately-signed body/HMAC pair and then freely relabel it as belonging to any other shop when posting to the app's public webhook endpoint. No secrets, tokens, or special access are required beyond the standard, unprivileged app-installation flow.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`, `api_version`) in the value that is HMAC-verified, or otherwise cryptographically bind the shop domain to the signed payload before trusting it in `WebhookMetadata`. At minimum, document that `Registry.process` does not authenticate the `shop` header and instruct integrators to cross-check `data.shop` against a shop for which they have an active, previously-established session/webhook registration before trusting the payload.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, causing Shopify to send a legitimate webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` (computed as `HMAC-SHA256(client_secret, B)`).
2. Attacker captures `B` and `H` (e.g., via their own server logs, since it's their own installation).
3. Attacker sends a new POST request directly to the same public webhook URL with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged, still valid since only body is signed)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic`: same topic as before
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `H` against `B`: [7](#0-6) 
5. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)`, and the host application processes attacker-controlled data as if it originated from the victim shop.

          received_signature = verifiable_query.hmac
