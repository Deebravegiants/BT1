### Title
Unchecked `i128` RAY-value overflow during interest accrual permanently freezes a whale market - ([File: common/src/rates/index.rs](common/src/rates/index.rs))

### Summary
The pool computes market-wide debt and supply values as `scaled_shares * index` inside `i128`-bounded RAY arithmetic. For sufficiently large supplied/borrowed totals, ordinary interest accrual can overflow the RAY-value domain before `MAX_BORROW_INDEX_RAY` is reached. Because `update_indexes`, `supply`, `borrow`, `withdraw`, `repay`, liquidation settlement, revenue claims, and recapitalization all synchronize the market first, one successful overflow leaves every subsequent operation on that market reverting.

### Finding Description
`Controller::update_indexes` is permissionless and forwards caller-selected `HubAssetKey`s to the pool through `markets::update_indexes` and `pool_update_indexes_call`. The pool then calls `ops::market::accrue`, which loads each market and invokes `interest::global_sync`.

`global_sync` calls `accrue_step`. That function first calculates:

```rust
let borrowed_original = scaled_to_original(env, borrowed, borrow_index);
let supplied_original = scaled_to_original(env, supplied, supply_index);
```

`scaled_to_original` is implemented as `scaled.mul(env, index)`, whose multiplication returns a checked `i128` fixed-point result. `calculate_supplier_rewards` repeats the same checked multiplication using the old and capped new borrow indexes:

```rust
let old_total_debt = borrowed.mul(env, old_borrow_index);
let new_total_debt = borrowed.mul(env, new_borrow_index);
```

Although `update_borrow_index` caps the index at `MAX_BORROW_INDEX_RAY`, it does not cap the product `borrowed * borrow_index`. A sufficiently large scaled debt can therefore overflow before the index cap applies. The same issue exists for `supplied * supply_index` in `update_supply_index`.

The repository's own long-horizon test demonstrates the concrete boundary: one billion 18-decimal tokens at sustained 98% utilization reaches a `MathOverflow` inside accrual while `borrow_index` remains below `MAX_BORROW_INDEX_RAY`. The test then confirms both `withdraw` and `repay` revert with the same error.

### Impact Explanation
This is permanent freezing of funds and protocol insolvency risk for the affected `(hub_id, asset)` market:

- Suppliers cannot withdraw deposited tokens.
- Borrowers cannot repay debt.
- Liquidators cannot execute liquidation paths because those paths synchronize the market first.
- `claim_revenue` cannot access accrued protocol revenue.
- `recapitalize` cannot rescue the market because it also loads an interest-synced cache.
- Bad-debt cleanup and other settlement flows cannot progress for that market.

The underlying token balance remains in the pool contract, but all state-changing routes that can release or account for it panic during mandatory accrual.

### Likelihood Explanation
Triggering the condition requires an unusually large market and enough elapsed time or a steep configured rate for the index to multiply the scaled total past `i128::MAX`. An unprivileged caller cannot directly choose the stored totals, but can reach the failure by calling:

```text
update_indexes(caller, vec![HubAssetKey { hub_id, asset }])
```

once the market's stored `borrowed`, `supplied`, and indexes cross the arithmetic boundary. Any borrower or supplier can also encounter it through normal `repay`, `withdraw`, `borrow`, `supply`, or liquidation calls after sufficient accrual time.

This is not merely an input-validation failure on an impossible amount: the test uses accepted `supply` and `borrow` operations to establish the state, then advances time and calls `update_indexes`. However, exploitation depends on a listed asset having enough token supply and protocol capacity to admit approximately RAY-domain-limit scale values, which constrains the likelihood.

### Recommendation
Represent market totals in a wider type throughout accrual, or detect and bound the RAY-value product before multiplication.

Concretely:

- Calculate `borrowed * borrow_index` and `supplied * supply_index` through `I256` intermediate value helpers rather than `Ray::mul`.
- Return or propagate saturated/clamped totals only where saturation is explicitly safe; do not silently cap user claims.
- Enforce an admitted-size invariant such that `scaled_total * MAX_*_INDEX` remains representable.
- Alternatively, add a market-level scaled exposure ceiling derived from `i128::MAX / MAX_*_INDEX`, not merely an asset-unit cap.
- Add regression coverage around the existing whale-market test asserting that accrual stops safely before permanent accrual failure, while withdrawals and repayments remain executable.

### Proof of Concept
A minimal attack path is:

1. Identify a listed market whose admitted scaled supply/debt is large enough that future index growth can make `scaled * index > i128::MAX`.
2. Supply a large amount through `Controller::supply` and establish high utilization through `Controller::borrow`, subject to ordinary collateral checks.
3. Wait until the next accrual step moves the scaled value beyond the `i128` RAY-value domain.
4. Call permissionless `Controller::update_indexes(caller, [hub_asset])`.
5. The call panics with `MathOverflow`; subsequent `withdraw`, `repay`, liquidation, `claim_revenue`, and `recapitalize` calls panic at the same mandatory synchronization point.

The in-repository reproduction is `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-356`. It supplies one billion 18-decimal units, borrows 98%, advances time until `update_indexes` fails, verifies `borrow_index < MAX_BORROW_INDEX_RAY`, and verifies that both withdrawal and repayment subsequently fail with `MATH_OVERFLOW`.
