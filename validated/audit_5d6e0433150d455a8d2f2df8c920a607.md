### Title
Webhook `shop-domain` Header Is Not Covered by the HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` treats the `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers as trusted, authenticated data, but the HMAC signature computed by `HmacValidator` only ever covers the raw request body. Any actor who can obtain one genuine `(raw_body, hmac)` pair from Shopify (trivially done by installing the app on their own store and triggering a webhook) can replay that exact body/signature to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header, and `Registry.process` will accept it as an authentic webhook "from Shopify" for the spoofed shop.

### Finding Description
`Registry.process` validates a webhook solely via: [1](#0-0) 

which calls `Utils::HmacValidator.validate(request)`. The validator only recomputes the signature over `to_signable_string`: [2](#0-1) 

and `Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 

Meanwhile `Request#shop`, `#topic`, and `#webhook_id` are read directly and unauthenticated from HTTP headers: [4](#0-3) 

After the HMAC check passes, `Registry.process` forwards `request.shop` straight into `WebhookMetadata`, which the app's handler is documented to treat as "the shop domain of the webhook": [5](#0-4) [6](#0-5) 

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," implying `data.shop` is trustworthy — but the equality that is actually enforced is:

`hmac(raw_body) == expected_hmac(raw_body)`

whereas the equality the host application relies on (and that the docs imply) is:

`request.shop == "the shop that produced this signed body"`

These two are not the same binding: `shop-domain` is never included in the signed payload, so it can be swapped freely on any valid `(raw_body, hmac)` pair without invalidating the signature.

### Impact Explanation
An attacker who has legitimately received one signed webhook for their own (or any) shop can replay the identical body+signature to the victim app's webhook endpoint with the `shop-domain` header changed to a target shop. `Registry.process` will accept it as authentic and dispatch it to the app's handler tagged with the attacker-chosen shop identity. Depending on how the host app keys data/session lookups off `data.shop` (as the gem's own documentation recommends: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), this allows an unprivileged actor to inject attacker-controlled webhook payloads that are processed and stored under a different tenant's identity — a cross-tenant data-integrity/confusion issue. It can also be used to trigger mandatory-topic side effects (e.g. spoofing `shop/redact` or `customers/redact` for a victim shop) since these topics are dispatched the same way.

### Likelihood Explanation
Likelihood is significant: no privileged credentials, `api_secret_key`, or access token is required. The attacker needs only (a) one genuine webhook delivery they legitimately received (trivial to obtain by installing any publicly-installable app on their own development store) and (b) the ability to POST to the target app's public webhook URL, which is inherently internet-reachable by design. Swapping the `shop-domain` header requires no cryptographic work since it is outside the signed payload.

### Recommendation
Bind the shop identity into what is authenticated: e.g., include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in the signable string used for HMAC validation, or have `HmacValidator`/`Registry.process` separately verify that `request.shop` matches an expected/registered shop for the session context before dispatching to the handler. At minimum, update documentation to explicitly warn that `data.shop`/`data.topic` are not covered by the HMAC and must be independently corroborated (e.g., against a known installed-shop list) by the host application before being trusted for tenant-sensitive operations.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com` and receive a real webhook delivery, capturing the raw body `B` and the valid `x-shopify-hmac-sha256` header `H` (correctly computed by Shopify over `B` using the app's secret).
2. POST to the app's public webhook endpoint with:
   - `x-shopify-hmac-sha256: H`
   - `x-shopify-topic: <same or attacker-chosen registered topic>`
   - `x-shopify-shop-domain: victim.myshopify.com` (spoofed)
   - body: `B` (unchanged)
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `Registry.process` calls `HmacValidator.validate`, which recomputes `HMAC-SHA256(secret, B)` and compares it to `H` — this succeeds because `B` and `H` are unmodified and genuinely matching, regardless of the spoofed `shop-domain`.
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, and the host app processes attacker-controlled data as if it originated from the victim shop.
