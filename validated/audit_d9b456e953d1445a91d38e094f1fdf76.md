## Title
Webhook shop-domain header is trusted for tenant identification but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches the handler using the `shop` value taken from an HTTP header that is never included in the signed content. This breaks the binding "shop verified by HMAC == shop the handler is called with," letting an attacker who controls a validly-signed webhook body (e.g. from their own installed shop) relabel it as belonging to any other shop.

### Finding Description
`Webhooks::Request` derives everything the handler receives from raw HTTP headers/body, but only the body is part of the signable content: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`; `shop` comes from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of that string.

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, and, if it matches, immediately trusts `request.shop` (the unsigned header) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` to compute the expected signature: [4](#0-3) 

Because `to_signable_string` for a webhook `Request` is just the raw body, the HMAC check equals: "does this body match this HMAC?" It never equals: "does this shop-domain header match this HMAC?" The identity binding the app relies on — `hmac_valid(body) == owns(shop)` — does not hold; `shop` is fully attacker-controlled independent of the signature check.

This differs from the OAuth/AuthQuery flow in the same codebase, where `shop` (and `host`) are explicitly part of `to_signable_string` and therefore covered by the HMAC: [5](#0-4) 

For webhooks there is no equivalent binding of `shop` into the signed payload.

### Impact Explanation
An unprivileged internet user who legitimately installs the target app on their own shop will receive genuine, correctly-HMAC-signed webhook deliveries from Shopify for that shop (e.g., `app/uninstalled`, `orders/create`, etc.). Because the HMAC only covers the body, the attacker can resend that exact `raw_body` + `hmac-sha256` value to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `Registry.process` will validate successfully (body+hmac match) and hand the handler a `WebhookMetadata` claiming to be from the victim shop. Any app logic keyed on `data.shop` (session lookup, per-tenant state changes, deletion/uninstall handling, etc.) will act on the wrong tenant — this is cross-tenant access/data corruption caused entirely by trusting an unauthenticated identity field.

### Likelihood Explanation
Exploitation only requires the attacker to install the target app on a shop they control (which is normal, unprivileged usage for any public app) and to be able to replay an HTTP request with modified headers to the app's own public webhook endpoint — no access token, `client_secret`, or privileged account is required. This is realistic and directly reachable through the gem's documented webhook-processing API (`ShopifyAPI::Webhooks::Registry.process`).

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-covered content, or otherwise validate `request.shop` against a set of shops actually expected to be sending this payload (e.g., cross-check against a known/installed-shop store) before trusting it for tenant-scoped processing. At minimum, document and enforce that consumers must independently verify `WebhookMetadata#shop` is a shop with an active session/install before acting on the payload, and add a fatal check when the domain is not recognized.

### Proof of Concept
1. Attacker installs the vulnerable app onto `attacker-shop.myshopify.com`, obtaining `raw_body` and a valid `hmac-sha256` value for a real webhook delivery (e.g. `orders/create`).
2. Attacker sends the identical `raw_body` and `hmac-sha256` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. The app's handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's own order data>, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) and performs shop-scoped operations against the victim tenant using attacker-controlled body content.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
