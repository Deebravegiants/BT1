Based on my investigation, I found a concrete analog to the report's bug class ("bytes verified versus bytes parsed") in this gem's session-token handling.

### Title
Session ID collision via unbound shop-domain parsing in `JwtPayload#shop` - ([File: lib/shopify_api/auth/jwt_payload.rb])

### Summary
`ShopifyAPI::Auth::JwtPayload#shop` derives the "shop" identity used to key sessions by naively stripping a literal `"https://"` prefix off the JWT `dest` claim, rather than parsing/validating it as a URL and checking it against Shopify's known domain suffixes (the way `ShopifyAPI::Utils::ShopValidator.sanitize!` does elsewhere in the same gem). The signature over the JWT covers the raw `dest` string, but the *parsed* value used downstream as a tenant identifier is produced by an unvalidated, ad-hoc transformation of that string, so bytes that are cryptographically verified are not the same bytes that get bound to the session/tenant identity.

### Finding Description
`JwtPayload#shop` is implemented as: [1](#0-0) 
This value (`payload.shop`) is then used directly, with no additional format validation, as the tenant key for session identity: [2](#0-1) 
and again in `TokenExchange.exchange_token`, where it becomes both the session's `shop` and part of the outbound token-exchange request: [3](#0-2) 

Elsewhere in the same gem, shop domains that arrive from less-trusted origins (OAuth callback `shop` query parameter) are explicitly parsed with `Addressable::URI` and checked against `TRUSTED_SHOPIFY_DOMAINS` via `ShopValidator.sanitize!`: [4](#0-3) 
No equivalent check is applied to the `dest`/`shop` value extracted from a session token in `JwtPayload`. The `gsub("https://", "")` only removes a literal prefix; it does not validate that the remaining string is a well-formed `*.myshopify.com` (or other trusted) hostname, does not strip a `http://` scheme, and does not reject values containing paths, ports, userinfo, or unexpected characters. This is the identity-binding gap analogous to the "bytes verified versus bytes parsed" class from the report: the signature (JWT HMAC) verifies the exact `dest` string, but the code that turns that string into the shop-domain identity used for session partitioning does its own unvalidated parsing, rather than reusing the strict validator that exists for this exact purpose elsewhere in the codebase.

### Impact Explanation
If `JwtPayload#shop` (or `dest`) can ever be produced with an unexpected/ambiguous format, differing consumers within the same app (or across the ecosystem) that assume `ShopValidator`-level guarantees are not necessarily true for JWT-derived shop values, weakening the shop==session-key binding this gem is meant to preserve. In this codebase specifically, this value is consumed to build session IDs (`jwt_session_id`, `offline_session_id`) that key access-token storage — if two structurally different `dest` strings could stem-collide after the naive strip (e.g., different casing, trailing slash, or `http://` prefix not stripped), the resulting session ID collisions could allow one tenant's session identity to overwrite or be confused with another's.

### Likelihood Explanation
Low. `dest` is inside the JWT payload and is covered by the JWT's own HMAC signature (verified in `decode_token` before any of these claims are trusted) [5](#0-4) , so an unprivileged internet user cannot forge an arbitrary `dest` value without the app's `api_secret_key`. This limits the practical exploitability compared to the ENS report (where the input was fully attacker-controlled), which is why this is flagged as a hardening/defense-in-depth gap rather than a directly exploitable cross-tenant bypass, consistent with the report's own downgrade to "note" once it required an already-malformed input.

### Recommendation
Route the `dest` value through the same strict domain validation used for OAuth callback shops (`ShopifyAPI::Utils::ShopValidator.sanitize!`) inside `JwtPayload#shop`/`#shopify_domain`, rejecting tokens whose `dest` does not parse to a trusted `myshopify.com`/`myshopify.io`/`spin.dev`/`shop.dev` (or configured) domain, instead of relying on a bare string `gsub`.

### Proof of Concept
Conceptually, in `test/auth/jwt_payload_test.rb` style, craft a payload where `dest` is a value that the gem's own `ShopValidator` would reject (e.g. `"httpshttps://evil.com"`, or a value containing embedded userinfo/path such as `"https://real-shop.myshopify.com@evil.com"`), sign it with the (test-known) `api_secret_key`, and observe that `JwtPayload#shop` returns a string that would fail `ShopValidator.sanitize!` yet is accepted and used unchanged as a session-partitioning key by `SessionUtils.session_id_from_shopify_id_token` and `TokenExchange.exchange_token`, with no independent domain-format check performed.

        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end
