### Title
Shallow, denylist-based body/query redaction in the web request logger exposes secrets in Debug logs - (File: `core/web/router.go`)

### Summary
The Chainlink node's web request logging middleware (`loggerFunc`) logs every authenticated API request's URL query parameters and JSON body at `Debug` level. Redaction of sensitive values is performed by `redact()`/`readSanitizedJSON()`, which only inspect **top-level** JSON keys/query keys against a tiny, hardcoded denylist containing only password-like key names. Any sensitive value that is nested one level deep, embedded inside a larger string blob, or simply named something other than "password" (tokens, secrets, API keys embedded in URLs, job TOML specs, GraphQL `variables`) is logged unredacted. This mirrors the root cause of CVE-2023-39951: sensitive payload content ends up verbatim in observability output because the filtering logic used an overly narrow, structurally shallow rule instead of properly scoping what is safe to record.

### Finding Description
`loggerFunc` reads and re-buffers the full request body, then logs it via `readBody`/`readSanitizedJSON`, and logs the query string via `redact`: [1](#0-0) 

`readSanitizedJSON` unmarshals the body into a flat `map[string]any` and only redacts a value if its **top-level** key matches the blacklist; it does not recurse into nested objects/arrays, and it does not inspect string values that themselves contain embedded secrets (e.g., a URL with `?token=...`, or a raw TOML job spec): [2](#0-1) 

The blacklist itself only covers password-shaped keys: [3](#0-2) 

`redact()` for query parameters has the same denylist limitation, only matching key names, not values: [4](#0-3) 

This middleware is installed globally on the authenticated API router group, so it runs for essentially every `/v2/...`/`/query` request handled by the node (job creation, bridge creation, key management, sessions, etc.): [5](#0-4) 

Concrete leak vectors from an authenticated, unprivileged (any role) client:
- Job specs are submitted as a raw TOML string under a single field (e.g. `{"toml": "..."}`) via `POST /v2/jobs`. Any credentials embedded in that TOML (RPC endpoint URLs with API keys, external adapter URLs with query-string tokens, etc.) are stored inside one string value that never matches a "password"-named key, so it is logged in full at Debug.
- Any JSON body whose sensitive field is nested (e.g., `{"data":{"attributes":{"secret": "..."}}}` — a common shape for JSON:API-style request bodies used throughout this router) bypasses redaction entirely, because `isBlacklisted` is only ever evaluated against the outer key (`"data"`), never against the nested key holding the actual secret.
- Query parameters named `token`, `secret`, `apiKey`, `accessKey`, etc. are not redacted at all — only variants containing the substring "password" are.

This is directly analogous to the OTel/AWS SES CVE: a debug/telemetry-facing logging path applies an insufficiently scoped filter (there, `url.path` unconditionally included raw SES POST params; here, a shallow top-level key denylist) and ends up recording sensitive request content that was never intended to be exposed to the logging/telemetry backend.

### Impact Explanation
If Debug-level node logs are shipped to a centralized logging/telemetry backend (a common operational practice, and explicitly anticipated by the codebase's own audit/telemetry pipelines), any secret embedded in a request body field that isn't literally password-shaped, or nested under a wrapper key, or embedded inside a string blob (job specs, URLs), will be persisted in that log store in plaintext. This can expose bridge/EI-related credentials, API keys embedded in job pipeline configuration, or other request secrets to anyone with access to the log backend — a broader, less-privileged audience than intended (log/telemetry consumers vs. the node operator). This is a confidentiality-only issue (no integrity/availability impact), consistent with the CVSS profile of the reference CVE.

### Likelihood Explanation
Debug-level logging must be enabled for the leak to manifest, which limits default exposure. However, the logger runs unconditionally on the shared middleware chain for the entire authenticated API surface, so the moment Debug logging is turned on (a routine operational/debugging action, not a special "insecure" flag), every request — including ones carrying secrets in job specs or nested attributes — is captured. No attacker action beyond making a normal authenticated API call is required to place the secret into the log stream; the risk is realized whenever operators forward Debug logs off-box.

### Recommendation
- Replace the shallow, key-name denylist with either (a) a recursive redaction pass over nested JSON structures and known secret-bearing fields, or (b) an allowlist approach where only vetted, non-sensitive fields are ever logged.
- Extend the denylist to cover general secret-shaped key names (`token`, `secret`, `key`, `authorization`, etc.), and apply the same recursive logic to `redact()` for query parameters.
- For freeform string blobs known to potentially contain credentials (e.g., job TOML specs), exclude the raw value from Debug logs entirely or apply pattern-based scrubbing (e.g., strip query strings/credentials from any embedded URLs) before logging.
- Consider gating full body/query logging behind an explicit, separately documented "insecure debug" flag rather than the general `Debug` log level, given how easily wide log-level changes are made in production.

### Proof of Concept
1. Enable `Debug` level logging on a running Chainlink node.
2. As any authenticated API user, submit `POST /v2/jobs` with a TOML spec whose observation source references an external adapter URL containing an API key/token in its query string, e.g.:
```
type = "webhook"
schemaVersion = 1
observationSource = """
ds [type=http method=GET url="https://example-adapter.com/data?apikey=SUPER_SECRET_KEY"];
"""
```
3. Observe the node's Debug log output produced by `loggerFunc`: the `body` field will contain the full JSON payload including the raw TOML string with `apikey=SUPER_SECRET_KEY` unredacted, because the top-level JSON key (`toml`) does not match the password-only blacklist in `isBlacklisted`. func loggerFunc(lggr logger.Logger) gin.HandlerFunc {
	return func(c *gin.Context) {
		buf, err := io.ReadAll(c.Request.Body)
		if err != nil {
			lggr.Error("Web request log error: ", err.Error())
			// Implicitly relies on limits.RequestSizeLimiter
			// overriding of c.Request.Body to abort gin's Context
			// inside io.ReadAll.
			// Functions as we would like, but horrible from an architecture
			// and design pattern perspective.
			if !c.IsAborted() {
				c.AbortWithStatus(http.StatusBadRequest)
			}
			return
		}
		rdr := bytes.NewBuffer(buf)
		c.Request.Body = io.NopCloser(bytes.NewBuffer(buf))

		start := time.Now()
		c.Next()
		end := time.Now()

		lggr.Debugw(fmt.Sprintf("%s %s", c.Request.Method, c.Request.URL.Path),
			"method", c.Request.Method,
			"status", c.Writer.Status(),
			"path", c.Request.URL.Path,
			"ginPath", c.FullPath(),
			"query", redact(c.Request.URL.Query()),
			"body", readBody(rdr, lggr),
			"clientIP", c.ClientIP(),
			"errors", c.Errors.String(),
			"servedAt", end.Format("2006-01-02 15:04:05"),
			"latency", fmt.Sprintf("%v", end.Sub(start)),
		)
	}

func readSanitizedJSON(buf *bytes.Buffer) (string, error) {
	var dst map[string]any
	err := json.Unmarshal(buf.Bytes(), &dst)
	if err != nil {
		return "", err
	}

	cleaned := map[string]any{}
	for k, v := range dst {
		if isBlacklisted(k) {
			cleaned[k] = "*REDACTED*"
			continue
		}
		cleaned[k] = v
	}

	b, err := json.Marshal(cleaned)
	if err != nil {
		return "", err
	}
	return string(b), err
}

func redact(values url.Values) string {
	cleaned := url.Values{}
	for k, v := range values {
		if isBlacklisted(k) {
			cleaned[k] = []string{"REDACTED"}
			continue
		}
		cleaned[k] = v
	}
	return cleaned.Encode()
}

// NOTE: keys must be in lowercase for case insensitive match
var blacklist = map[string]struct{}{
	"password":             {},
	"newpassword":          {},
	"oldpassword":          {},
	"current_password":     {},
	"new_account_password": {},
}

func isBlacklisted(k string) bool {
	lk := strings.ToLower(k)
	if _, ok := blacklist[lk]; ok || strings.Contains(lk, "password") {
		return true
	}
	return false
}
