### Title
Rounding slack in `Pair.swap`'s K-invariant check lets repeated dust sells drain `assetReserve` below the immutable virtual-LT floor, causing `_prepareGraduationLiquidity` to permanently revert and brick graduation - ([File: packages/contracts/src/Pair.sol])

### Summary
`Pair.swap`'s K-invariant check uses a `+1` slack on both reserves, and `Router._computeSell` derives `assetOut` via floor division. Both biases systematically favor the seller by a small, non-zero amount on every sell. An unprivileged trader repeating small `Bonding.sell` calls can compound this bias to push the pair's stored `assetReserve` below the token's immutable launch-time virtual LT reserve (`Pair.k() / Token.TOTAL_SUPPLY()`). Once that happens, `Bonding._prepareGraduationLiquidity`'s unchecked subtraction `assetReserve - virtualLtReserve` underflows and reverts under Solidity 0.8's checked arithmetic, permanently blocking both the USD-trigger and supply-trigger graduation paths for that token, freezing all curve-raised LT and the 250M `LP_RESERVE` tokens that are supposed to seed the HyperSwap pair.

### Finding Description
`Pair.swap` enforces the constant-product invariant with a `+1` slack on each side: [1](#0-0) 

```
(newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k → revert
```

This permits the true product `newTokenReserve * newAssetReserve` to fall below `k` by up to `newTokenReserve + newAssetReserve + 1`. On top of that, `Router._computeSell` computes `assetOut` via `reserveAsset - (k / newReserveToken)` — an integer floor division that rounds `assetOut` up in the seller's favor by up to 1 wei on every call: [2](#0-1) 

Both biases are small per-call but strictly one-directional (always favor the seller), so an unprivileged trader who repeatedly calls `Bonding.sell` with small amounts can compound the drift over many transactions, gradually reducing the pair's stored `assetReserve` relative to what a pure, unbiased constant-product curve would leave.

Graduation math depends on `assetReserve` never dropping below the launch-time virtual LT reserve: [3](#0-2) 

`ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr)` is an unchecked (Solidity-0.8-checked) subtraction. `_launchTimeVirtualLtReserve` is recovered from immutable identities (`Pair.k() / Token.TOTAL_SUPPLY()`), so it is a fixed floor for the life of the token: [4](#0-3) 

If the rounding drift from repeated sells drives the stored `assetReserve` below this floor, `_prepareGraduationLiquidity` reverts with a Panic (arithmetic underflow) instead of computing `ltFromPair`. This function is called from both graduation entry points:

- `_enterGraduating`, invoked inline at the end of every threshold-crossing `Bonding.buy` via `_executeBuy`: [5](#0-4) 
- `triggerGraduation`, the permissionless standalone phase-1 entry point: [6](#0-5) 

Both the USD trigger and the supply trigger route through the same `_prepareGraduationLiquidity` call, so once the underflow condition is reached, **every** future graduation attempt for that token — whether fired by a buy crossing the USD threshold or by the supply hitting zero — reverts identically. The token is permanently stuck in `Lifecycle.Curve`, `finalizeGraduation` is unreachable, and the curve-raised LT plus the 250M `LP_RESERVE` tokens held by `Bonding` for LP seeding can never be deployed or recovered, since `Bonding` has no rescue path outside the graduation flow.

### Impact Explanation
This is a permanent freeze of funds: all LT raised on the curve for the affected token, plus the 250M reserved LP tokens sitting in `Bonding`, become permanently unreachable because the only exit path (`finalizeGraduation`, gated by the one-shot `LPLock.recordLock`) can never be entered. Traders can still buy/sell on the (now-degraded) curve, but the token can never graduate to the HyperSwap V2 pool, and the protocol's designed LP-seeding invariant is permanently broken for that token. This matches the CVE's "hang/repeatable crash" class mapped onto alt.fun's shape: a reachable, unprivileged-caller code path that permanently denial-of-services a core state transition and traps funds.

### Likelihood Explanation
Exploitation requires a large number of low-value sells to accumulate enough rounding drift to cross the (typically large, ~1e18-scaled) floor gap between `assetReserve` and `virtualLtReserve` — this is gas-expensive and slow, which is why the CVSS analog is Medium rather than High. However, every sell is available to any unprivileged holder with `Bonding.sell`, requires no special privilege, and the bias direction is deterministic (always in the seller's favor), so it is a reliable, patient griefing/self-inflicted vector rather than a probabilistic one. No mint-floor or transaction-size gate blocks tiny sells at the `Bonding`/`Router` layer (only `Zap`'s USDC path enforces a BounceTech LT `minTransactionSize`; direct `Bonding.sell` calls with an already-held LT balance are unrestricted at this layer).

### Recommendation
Replace the unchecked subtraction in `_prepareGraduationLiquidity` with a saturating computation (clamp `ltFromPair` to zero when `assetReserve <= virtualLtReserve`) so that rounding drift can never revert graduation; additionally, tighten `Pair.swap`'s K-check slack (or account for the accumulated rounding bias directly in `_computeSell`/`_computeBuy`) so `assetReserve` cannot legitimately dip below `virtualLtReserve` over the life of the curve.

### Proof of Concept
1. Launch a token via `Bonding.launch`/`Zap.createToken`, buy a moderate stake with `Bonding.buy`.
2. Repeatedly call `Bonding.sell` with the smallest possible non-zero token amount thousands of times (an unprivileged actor can script this against `Router._computeSell`'s floor-division bias and `Pair.swap`'s `+1` K slack).
3. Read `Pair.getReserves()` after each batch; observe `assetReserve` trending below what an unbiased constant-product curve at the same `tokenReserve` would imply, eventually falling below `Pair.k() / Token.TOTAL_SUPPLY()`.
4. Trigger a buy or call `Bonding.triggerGraduation` once a trigger condition is met; observe the transaction revert with an arithmetic underflow Panic inside `_prepareGraduationLiquidity`, and confirm this revert reproduces on every subsequent qualifying buy/`triggerGraduation` call, permanently preventing graduation.

*(Note: precisely quantifying the number of sells needed to cross the floor requires numeric simulation against the live `k`/`virtualLtReserve` values for a given token, which was not run as part of this analysis — the underflow mechanism and its permanence, however, follow directly from the cited code.)*

    function swap(
        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }

    function _computeSell(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 assetOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        uint256 newReserveToken = reserveToken + amountIn;
        assetOut = reserveAsset - (k / newReserveToken);
    }

    /// @notice Permissionless trigger for phase 1 of graduation. Same flow as
    ///         the inline post-buy trigger inside `_executeBuy`, but callable
    ///         without any buy. Closes the case where `canGraduate` is true
    ///         (LT appreciation pushed the curve past the USD threshold) but
    ///         the closing buy on the curve would mint below the BounceTech
    ///         LT mint floor and revert with `BelowMinTransactionSize`,
    ///         making the token un-graduatable via `Zap.buy`.
    /// @dev    `_enterGraduating` reads pair reserves and the launch-time
    ///         virtual reserve only — it does not depend on a buy having
    ///         just landed, so the same logic is safe to expose as a
    ///         standalone entry point. The lifecycle pre-checks mirror
    ///         `Bonding.buy`; the launch trading delay is intentionally
    ///         not enforced because `canGraduate` already requires either
    ///         the USD threshold or full curve sellout, both of which are
    ///         unreachable from a fresh launch within the delay window.
    function triggerGraduation(
        address tokenAddress
    ) external nonReentrant {
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (info.creator == address(0)) revert TokenNotTrading();
        if (info.lifecycle == Lifecycle.Graduating) revert TokenIsGraduating();
        if (info.lifecycle != Lifecycle.Curve) revert TokenNotTrading();
        if (!canGraduate(tokenAddress)) revert NotGraduatable();
        _enterGraduating(tokenAddress);
    }

    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }

    /// @dev Recovers the launch-time virtual LT reserve from immutable
    ///      identities: `Pair._pool.k = tokenReserve_init * assetReserve_init
    ///      = TOTAL_SUPPLY * virtualLtReserve_init` is set ONCE in
    ///      `Pair.mint` and never modified by `Pair.swap` (swap only
    ///      mutates `tokenReserve` / `assetReserve` and asserts K-floor).
    ///      So `Pair.k() / Token.TOTAL_SUPPLY()` returns the exact
    ///      `virtualLtReserve` that was passed to `addInitialLiquidity` at
    ///      launch — for any pair, in any phase, with no storage of our own.
    ///
    ///      Going through this derivation rather than a stored mirror
    ///      eliminates an admin-writable economic-state slot and makes the
    ///      donation-immunity property a pure consequence of the pair's
    ///      already-immutable accounting. The `TOTAL_SUPPLY`-equality check
    ///      in `setTokenImplementation` keeps the divisor consistent across
    ///      impl rotations, so tokens launched under different
    ///      `tokenImplementation` versions still derive the same way.
    function _launchTimeVirtualLtReserve(
        address token_,
        address pair_
    ) internal view returns (uint256) {
        return IPair(pair_).k() / Token(token_).TOTAL_SUPPLY();
    }
