### Title
Webhook tenant identity (`shop-domain`) is not covered by the HMAC, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body [4](#0-3) . The tenant identity (`shop`) that the handler receives and acts on is read from the `x-shopify-shop-domain` header, a value that is never included in the signed bytes computed by `HmacValidator` [5](#0-4) [1](#0-0) . This breaks the intended identity binding: `shop used for tenant attribution == shop covered by the signature` does not hold; only `body used for tenant attribution == body covered by the signature` holds.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` field via constant-time comparison [6](#0-5) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`; none of the HTTP headers — including `shop-domain` — participate in the signature [1](#0-0) . Yet `shop` is exposed as a first-class attribute (`request.shop`) read straight from that unsigned header [2](#0-1) , and `Registry.process` passes it directly into `WebhookMetadata` given to the app's handler after only checking the body HMAC [3](#0-2) .

Because the signature is a function of the body bytes alone, any valid `(raw_body, hmac)` pair generated by Shopify for one shop remains a valid pair for any other value of the `shop-domain` header — the gem's `process` method will accept it and report a validated, "from Shopify" webhook. An unprivileged attacker who legitimately installs the target app on their own shop will receive genuine `(raw_body, hmac)` pairs signed with the same `Context.api_secret_key` used by the target app instance for every shop (the secret is per-app, not per-shop). Replaying that untouched `(raw_body, hmac)` pair while spoofing the `x-shopify-shop-domain` header to a victim's shop passes `HmacValidator.validate` unchanged, since the header is not part of `to_signable_string`. The handler then receives `WebhookMetadata` claiming the victim shop while the body content belongs to the attacker's own shop, breaking the `shop` identity binding that `Registry.process` is documented to guarantee ("This will verify the request did indeed come from Shopify…") [7](#0-6) .

### Impact Explanation
This is a cross-tenant identity confusion at the point where the gem attributes webhook data to a shop: the shop the handler is told to act on is not the shop the signature actually covers. Any app that uses `WebhookMetadata#shop` (as documented) for tenant-scoped storage or business logic will mix data/actions between tenants when fed a replayed body with a forged `shop-domain` header, which matches the Critical class of "cross-tenant access."

### Likelihood Explanation
Exploitation only requires being able to install the target app on any shop (an ordinary, unprivileged action available to any Shopify merchant/developer) to obtain genuine `(raw_body, hmac)` pairs, plus the ability to POST a crafted HTTP request with an altered header to the app's webhook endpoint — no access token, `client_secret`, or privileged access is required.

### Recommendation
Bind the `shop` (and other tenant-identifying headers such as `webhook-id`, `topic`, `api-version`) into the signed material verified by `HmacValidator`, or independently authenticate the `shop-domain` header against the shop associated with the specific `webhook_id`/subscription server-side before dispatching to the handler, so that the identity acted upon is provably the identity that was signed.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`, triggering a webhook (e.g., `orders/create`) that Shopify signs and delivers with headers `x-shopify-hmac-sha256: <valid-hmac-of-body>` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker captures the exact `raw_body` and `x-shopify-hmac-sha256` value.
3. Attacker POSTs the identical `raw_body` and `x-shopify-hmac-sha256` to the app's webhook route, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present) [8](#0-7) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and matches, since the header was never part of the signed content [4](#0-3) .
5. The handler executes with `WebhookMetadata.shop == "victim.myshopify.com"` while the body is attacker-controlled content, achieving cross-tenant data/action confusion.
