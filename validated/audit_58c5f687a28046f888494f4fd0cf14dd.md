Found a concrete analog: HOT Bridge's API-fallback status resolution reports a withdrawal as `"completed"` with a transaction hash without checking the `chain_id` or `verified_withdraw` fields that the HOT API itself returns alongside the hash.

### Title
HOT Bridge API fallback reports withdrawal as completed without validating `chain_id` or `verified_withdraw` - (File: packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts)

### Summary
`HotBridge.fetchWithdrawalHashFromApi()` parses the HOT API response with `HotApiWithdrawalResponseSchema`, which defines `verified_withdraw: boolean` and `chain_id: number` fields on each withdrawal entry, but the matching logic only compares `nonce` and validates that the `hash` is hex before returning it as the authoritative destination transaction hash.

### Finding Description
`fetchWithdrawalHashFromApi` finds the withdrawal entry solely by nonce equality: [1](#0-0) 
and the schema explicitly carries `verified_withdraw` and `chain_id` per entry: [2](#0-1) 
Neither field is consulted before the caller treats the API's hash as ground truth. `describeWithdrawal()` calls this fallback and, on any non-null result, immediately reports `{ status: "completed", txHash: formatTxHash(apiHash, args.landingChain) }`, formatting the hash for `args.landingChain` (the chain the SDK/caller expects) rather than confirming it corresponds to `chain_id` from the API response: [3](#0-2) 
and in the non-EVM/Stellar/TON branch: [4](#0-3) 

This breaks the equality that the *status reported* ("completed", with a specific txHash) must equal *the verified on-chain outcome*. Two independent checks the HOT API itself provides to gate that equality — `verified_withdraw` (whether HOT has confirmed the withdrawal actually landed) and `chain_id` (which network the hash belongs to) — are dropped on the floor. The bridge-indexer fallback (`fetchWithdrawalHashBridgeIndexer`) has the analogous gap: it matches by `nonce` only and returns any non-empty `hash` field without an equivalent verification flag check: [5](#0-4) 

### Impact Explanation
If the HOT API (an off-chain, attacker/relayer-adjacent service already treated as a semi-trusted data source by this integration) returns an entry with the correct `nonce` but `verified_withdraw: false` or a `chain_id` that does not match the chain the withdrawal is destined for, the SDK will still report the withdrawal as `"completed"` with that hash. An integrator/caller consuming `describeWithdrawal()` (e.g., to mark a withdrawal settled and release downstream funds/credit) would credit based on a status that does not reflect the true on-chain outcome — matching the "status or hash misreport making an integrator credit or refund twice" High-impact category, since a not-yet-verified or wrong-chain hash could later be superseded or invalidated.

### Likelihood Explanation
No malicious relayer/HOT-operator action is required to trigger this from the SDK's perspective beyond the already-considered untrusted API response; this is purely a client-side omission of an existing, schema-defined safety field. It fires on the normal fallback path (bridge indexer failure → HOT API fallback), which per the code comments is an expected, non-exceptional occurrence for EVM/Stellar/TON chains.

### Recommendation
In `fetchWithdrawalHashFromApi`, reject (or continue polling instead of returning) any matched withdrawal whose `verified_withdraw !== true`, and cross-check `chain_id` against the expected `args.landingChain` (mapped to HOT's network id) before returning the hash as `"completed"`.

### Proof of Concept
1. A NEAR withdrawal transaction produces `nonce = N` destined for chain `Ethereum`.
2. Bridge indexer lookup fails (network hiccup), triggering the HOT API fallback: `fetchWithdrawalHashFromApi(txHash, N, logger)`.
3. HOT API returns `{ withdrawals: [{ hash: "0xabc...", nonce: "N", near_trx: txHash, verified_withdraw: false, chain_id: 137 }] }` (i.e., an unverified entry, or one actually belonging to Polygon `chain_id: 137` rather than Ethereum).
4. `fetchWithdrawalHashFromApi` only checks `w.nonce === nonce.toString()` and that the hash is hex — it returns `"abc..."` regardless of `verified_withdraw` or `chain_id`.
5. `describeWithdrawal()` returns `{ status: "completed", txHash: formatTxHash("abc...", Chains.Ethereum) }`, misreporting a withdrawal as completed on Ethereum even though HOT has not verified it (or it actually settled on a different chain).
