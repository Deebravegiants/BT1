### Title
Attacker-controlled Aquarius LP liquidity withdrawal can permanently block liquidation and bad-debt cleanup - (File: contracts/price-aggregator/src/providers/aquarius.rs)

### Summary
A borrower can collateralize an Aquarius LP token, borrow against it, and then withdraw their own liquidity from the referenced Aquarius pool until its configured `min_pool_value_wad` check fails. Because the controller resolves prices for every supply and debt position before liquidation or bad-debt cleanup, the deliberately broken LP price causes both recovery paths to revert. This is attacker-triggered availability loss rather than an ordinary external oracle outage, and it can strand borrowed assets as unrecoverable bad debt.

### Finding Description
The Aquarius provider derives an LP price from the pool's reserves and total shares, computes the resulting pool value, and returns `InsufficientAquariusLiquidity` when that value is below `lp.min_pool_value_wad`. [1](#0-0) 

The aggregator's strict `prices` entry point resolves each requested key through `engine::resolve`, which panics when the resulting outcome is unusable. [2](#0-1) [3](#0-2) 

On liquidation, `build_liquidation_plan` is called before any repayment is applied. [4](#0-3)  The common risk calculation loads prices and indexes for the union of the account's supply and debt positions, so one deliberately unusable LP collateral price aborts valuation of the entire account. [5](#0-4) 

The same all-position valuation is performed again after liquidation and is also the admission check for standalone `clean_bad_debt`. [6](#0-5) [7](#0-6) 

`supply` permits the account owner to add any listed, unpaused and unfrozen collateral; there is no rule preventing an Aquarius LP token whose pool liquidity is controlled by that same borrower. [8](#0-7) [9](#0-8) 

### Impact Explanation
The borrower can retain the borrowed assets while making their position impossible to value. Any `liquidate` call fails before repayment because liquidation planning must load the failing LP price, and `clean_bad_debt` likewise fails before it can socialize the debt. If the borrower keeps the Aquarius pool below the configured liquidity floor, this becomes a permanent liquidation and cleanup block, allowing borrowed principal to become protocol bad debt rather than being recovered through collateral seizure.

This is more than a generic fail-closed condition: the account owner can intentionally induce the condition after obtaining borrow proceeds, and the resulting loss is borne by suppliers when the debt cannot be liquidated or cleaned up.

### Likelihood Explanation
An unprivileged borrower can execute the sequence whenever an Aquarius LP token is accepted as collateral and the borrower controls enough pool liquidity to reduce measured pool value below `min_pool_value_wad`. The attacker needs only their own LP share/liquidity and a normal borrow; no privileged role, leaked key, malicious parameter change, or third-party oracle dishonesty is required. The attack is most practical where one liquidity provider controls a large fraction of the referenced pool or where `min_pool_value_wad` is close to normal pool value.

### Recommendation
Do not allow a collateral position whose price resolution fails to make the entire account non-liquidatable. Liquidation and cleanup should isolate an unavailable collateral leg, value the remaining positions, and permit debt repayment plus seizure of healthy priced collateral where the resulting action does not worsen protocol solvency. Alternatively, add a dedicated emergency cleanup path that can exclude an irrecoverable LP leg after explicit governance authorization, and consider rejecting collateral sources whose referenced Aquarius pool liquidity can be materially controlled by the borrower.

### Proof of Concept
1. Governance lists hub asset `LP = { hub_id: H, asset: aquarius_lp_token }` in spoke `S`, with its price configured as `PriceSource::AquariusLp` or `AquariusStableLp` and a positive `min_pool_value_wad`.
2. The attacker calls `Controller::supply(caller = attacker, account_id = 0, spoke_id = S, assets = [(LP, attacker_lp_amount)])`, creating account `A`. The owner-controlled path permits this new listed collateral position. [10](#0-9) 
3. The attacker calls `Controller::borrow(caller = attacker, account_id = A, borrows = [(DEBT, amount)], to = Some(attacker))`, where `DEBT` is another listed hub asset and the LP collateral satisfies the normal risk gates.
4. Through the Aquarius pool's normal withdrawal function, the attacker withdraws their own liquidity until `reserve_a`, `reserve_b`, or resulting fair pool value causes `pool_value_wad < lp.min_pool_value_wad`.
5. A liquidator calls `Controller::liquidate(liquidator, A, [(DEBT, repay_amount)], SeizeMode::Transfer)`. The plan path requests prices for all of `A`'s supply and debt assets, the LP leg returns `InsufficientAquariusLiquidity`, `prices` panics, and no repayment or seizure occurs. [5](#0-4) 
6. A caller invokes `Controller::clean_bad_debt(caller, A)`. The same price fetch fails before `is_socializable_bad_debt` can be evaluated, so the insolvent account cannot be removed. [11](#0-10) 
7. While the attacker maintains the pool below the configured floor, every liquidation and cleanup attempt reverts; the borrowed assets remain outside the pool while the LP collateral cannot be seized through the controller.

fn socialize_bad_debt(env: &Env, account_id: u64, gate: BadDebtGate) {
    let mut cache = Context::new(env);
    let account = storage::get_account(env, account_id);

    assert_with_error!(
        env,
        !account.borrow_positions.is_empty(),
        CollateralError::DebtPositionNotFound
    );

    let totals = risk::calculate_account_risk_totals(
        env,
        &mut cache,
        &account.supply_positions,
        &account.borrow_positions,
    );

    let admits = match gate {
        BadDebtGate::DustCapped => {
            is_socializable_bad_debt(totals.total_debt, totals.total_collateral)
        }
        BadDebtGate::InsolventOnly => totals.total_debt > totals.total_collateral,
    };
    assert_with_error!(env, admits, CollateralError::CannotCleanBadDebt);

    bad_debt::execute_bad_debt_cleanup(env, &mut cache, account_id, &account, &totals);
