### Title
Webhook HMAC verification covers only the raw body, not the `shop-domain` header — allowing shop-identity spoofing via signed-payload replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies webhooks using only the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` fields — all of which are consumed by `ShopifyAPI::Webhooks::Registry.process` and handed to the application's webhook handler as trusted tenant-identifying metadata — come straight from unauthenticated HTTP headers and are never covered by the HMAC signature. This breaks the identity binding `shop_that_produced_the_signed_body == shop_delivered_to_the_handler`.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `Request#shop` is read verbatim from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no relation to the signed bytes: [2](#0-1) 

`Utils::HmacValidator.validate` computes/verifies the signature purely over `to_signable_string` (the body): [3](#0-2) 

`Registry.process` checks the HMAC of the body, then immediately trusts `request.shop` (the header) to build the `WebhookMetadata` passed to the app's handler, with no cross-check that the shop belongs to the body that was actually signed: [4](#0-3) 

The gem's own documentation instructs apps to key business logic (e.g. job queues, session lookups) directly off `data.shop`: [5](#0-4) 

Because the shop domain is outside the HMAC's protection scope, any party who has ever received one legitimately signed webhook body (e.g., from installing the app on their own store) can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` will still pass (it only checks the body bytes), and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` is attacker-chosen while the `body` is the original, unrelated, but validly-signed payload. This is exactly the report's bug class — “extra flexibility/looseness allowed on a value that a signature is supposed to pin down” — mapped onto the identity-binding rule “a field acted on but not covered by the HMAC.”

### Impact Explanation
This crosses a tenant boundary: an attacker who legitimately controls one installation of the app (their own shop) can cause the app to process a signed webhook under a victim shop's identity. If the handler uses `data.shop` to look up a stored session/access token (the documented pattern) or to route/queue per-tenant work, the attacker can inject cross-tenant events, pollute another merchant's processing pipeline, or trigger handler logic that acts on the victim's stored credentials using attacker-supplied (but validly-signed-for-a-different-shop) body content. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood requires the attacker to first obtain one valid `(body, hmac)` pair, which any shop that installs the app naturally receives via ordinary webhook delivery. No `api_secret_key`, access token, or privileged access is needed — only a normal, low-privilege installation and the ability to POST to the app's public webhook endpoint with a modified header. This is straightforward for anyone able to install the target app on a test/free store.

### Recommendation
Bind the shop identity (and topic/webhook id) into the value that is actually verified. Concretely:
- Include `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) in `Request#to_signable_string`, or
- Require the application layer to independently verify that `request.shop` matches a shop for which a session/subscription is expected before trusting it, and document this requirement prominently, since currently `Registry.process` performs no such check.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com` and capture one legitimately delivered webhook: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's secret).
2. Replay the exact same request to the app's webhook endpoint, keeping `raw_body = B` and `X-Shopify-Hmac-Sha256 = H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) builds `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker's captured body, and invokes the app's handler as if Shopify delivered this event for the victim shop.
