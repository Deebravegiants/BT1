### Title
`getConnectedAccounts` throws when `activeWalletAccountAtom` points to a wallet account not yet present in `connectedAccountsAtom` - ([File: features/connected-origins/module/connections.js])

### Summary
`ConnectedOrigins#getConnectedAccounts` unconditionally does `pick(accounts[activeWalletAccount].addresses, assetNames)` without checking that `accounts[activeWalletAccount]` exists. `connectedAccountsAtom` is refreshed only by the async `updateConnectedAccounts` handler, which is wired to fire on changes to `enabledWalletAccountsAtom`, not on changes to `activeWalletAccountAtom`. A newly created/enabled wallet account can be set as active before the corresponding async refresh completes, producing a window where `accounts[activeWalletAccount]` is `undefined` and the call throws.

### Finding Description
`getConnectedAccounts` reads `activeWalletAccount` from `this.#activeWalletAccountAtom.get()` and `accounts` from `this.#connectedAccountsAtom.get()` independently [1](#0-0) , then does `pick(accounts[activeWalletAccount].addresses, assetNames)` with no guard for a missing key.

The two atoms are updated through completely different, unsynchronized triggers:
- `connectedAccountsAtom` is only refreshed by `updateConnectedAccounts`, which is subscribed via `enabledWalletAccountsAtom.observe(connectedOrigins.updateConnectedAccounts)` [2](#0-1) . `enabledWalletAccountsAtom` is a `compute` derivation of `walletAccountsAtom` (fires when the wallet-account map changes, e.g., account creation/enable/disable) [3](#0-2) . `updateConnectedAccounts` itself is `async` and performs several awaited steps (`#enabledWalletAccountsAtom.get()`, diff check, `#connectedOriginsAtom.get()`, `#getAccounts()` which derives addresses per asset) before finally calling `#connectedAccountsAtom.set(...)` [4](#0-3) .
- `activeWalletAccountAtom` is a separate, independently-backed atom set directly via `WalletAccounts#setActive` [5](#0-4) ; setting it does not itself trigger `updateConnectedAccounts`.

Consequence: if a new wallet account is created/enabled and then immediately set active (e.g., right after account creation flow calls `walletAccounts.createMany(...)` then `setActive(newName)`), `enabledWalletAccountsAtom`'s observer fires the async `updateConnectedAccounts`, but this may not have completed (and thus `connectedAccountsAtom` not yet populated for the new account) by the time `activeWalletAccountAtom` already reflects the new account. Any trusted-origin dapp calling `getConnectedAccounts` in that window hits `accounts[activeWalletAccount]` === `undefined`, and `undefined.addresses` throws a `TypeError` before `pick` is even invoked.

Note: contrary to the "silently return addresses for the wrong/previous account" branch in the question, the code throws immediately when accessing `.addresses` on `undefined`; it does not silently return stale/incorrect address data, since the non-active entries in the loop are always keyed and labeled correctly by their own `name`.

### Impact Explanation
The exploitable outcome is a crash/exception (`TypeError`) surfaced to the RPC caller during `getConnectedAccounts`, i.e., a localized denial-of-service for that RPC call during account-switch windows. It does not appear to cause wrong-account address disclosure (the code throws rather than mixing up entries), so it does not rise to unauthorized signing, secret disclosure, or wrong-account exposure — it is limited to disrupting the connected-accounts RPC response during a narrow timing window.

### Likelihood Explanation
Requires: (1) the origin already being a trusted/connected dapp (able to call `getConnectedAccounts` at all, gated by `isTrusted`) [6](#0-5) , and (2) the wallet performing an account creation+switch in quick succession while the dapp polls `getConnectedAccounts` rapidly. The window is bounded by the async chain in `updateConnectedAccounts` (multiple `await`s plus per-asset address derivation), so it is narrow but non-zero and can be widened by increasing the number of connected assets/origins. A malicious/compromised connected dapp can increase the chance of hitting the window by polling frequently, but cannot itself trigger the account switch — it depends on normal user/wallet UI action happening concurrently.

### Recommendation
In `getConnectedAccounts`, guard against a missing `accounts[activeWalletAccount]` entry — e.g., fall back to deriving the addresses on demand (similar to `#getWalletAccountAddresses`) or skip/await a refresh (`updateConnectedAccounts`) before reading `connectedAccountsAtom` when the active account is not present in it, rather than assuming presence.

### Proof of Concept
Integration test (Jest) using the existing test harness in `features/connected-origins/module/__tests__/connections.test.js`:
1. Set up `connectedOrigins` with `enabledWalletAccountsAtom` initially containing `exodus_0` only, and a trusted origin connected with `assetNames: ['solana']`.
2. Without awaiting completion, concurrently:
   - Update `enabledWalletAccountsAtom` to add `exodus_1` (simulating account creation), and
   - immediately `await activeWalletAccountAtom.set('exodus_1')` (simulating an immediate switch), **before** calling/awaiting `connectedOrigins.updateConnectedAccounts()`.
3. Call `await connectedOrigins.getConnectedAccounts({ origin })`.
4. Assert that this throws a `TypeError` (`Cannot read properties of undefined (reading 'addresses')`), demonstrating the crash instead of a controlled response — proving `accounts[activeWalletAccount]` can be `undefined` at call time.
