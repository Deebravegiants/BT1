### Title
Webhook tenant identity (`shop`) is taken from an unauthenticated HTTP header instead of the HMAC-verified body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`Webhooks::Request#to_signable_string` binds the HMAC signature only to `@raw_body`, while `Webhooks::Request#shop` (and `topic`, `api_version`, `webhook_id`) are read directly from HTTP headers that are never included in the signable string and therefore never covered by the HMAC check. `Registry.process` accepts the request as valid once `HmacValidator.validate(request)` succeeds on the body, then unconditionally forwards the header-derived, unauthenticated `request.shop` value to the host application's webhook handler as the tenant identifier.

### Finding Description
This mirrors the `AntiSandwichHook._getTargetOutput` bug class: a value that is *acted upon* as if it were verified (the negative `int128` cast to `uint128`) is not actually range/sign-checked before use. Here, the field acted upon for tenant binding — `shop` — is not covered by the cryptographic check that is supposed to authenticate the request.

- `Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `shop`, `topic`, `api_version`, and `webhook_id` are all sourced from headers, outside the signed material: [2](#0-1) 
- `HmacValidator.validate` calls `verifiable_query.to_signable_string` (i.e., only the body) and `verifiable_query.hmac` (parsed from the `hmac-sha256` header) — it never touches the `shop-domain` header: [3](#0-2) 
- `Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop` as the tenant for the handler call: [4](#0-3) 

The binding that should hold is:
`shop authenticated by HMAC == shop used by the handler to scope tenant data`

But what actually holds is:
`shop-domain header (unauthenticated) == shop used by the handler to scope tenant data`

Because the HMAC only proves the *body* bytes came from someone holding the app's shared secret — not that the header-supplied `shop-domain` is the shop that produced that body. An attacker who installs the app on their own shop (Shop A) receives legitimate, correctly-HMAC-signed webhook deliveries for Shop A. Since the signature is computed purely over `raw_body` and never incorporates the `shop-domain` header, the attacker can replay/relay that exact request to the victim application's webhook endpoint while rewriting only the `X-Shopify-Shop-Domain` header to Shop B's domain. `HmacValidator.validate` still returns `true` (the body/HMAC pair is unchanged and valid), but `Registry.process` now hands the handler a `WebhookMetadata` claiming `shop: "shop-b.myshopify.com"` while the body content actually belongs to Shop A.

### Impact Explanation
This breaks the tenant isolation boundary the gem is supposed to enforce for webhook processing. If a host application uses `WebhookMetadata#shop` (as documented/intended) to select which merchant's `Session`/data store record to write against, an attacker can inject their own webhook payload (e.g., fake order/customer data, or a crafted `shop/redact`/`customers/redact` compliance payload) into another tenant's data scope — i.e., cross-tenant data corruption/injection using only their own legitimate app installation, no access token or `client_secret` required. This matches the "Critical – cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that installs on more than one shop (any public/multi-tenant app): the attacker only needs their own legitimate install (a normal, unprivileged merchant) to receive valid signed webhook bodies, then can freely modify the `shop-domain` header on replay since it is not part of the signed payload. No secrets, tokens, or privileged access are needed — only the ability to send an arbitrary HTTP request to the app's own publicly reachable webhook endpoint with a header of the attacker's choosing.

### Recommendation
Include the shop-identifying header (and ideally topic/api-version/webhook-id) in the HMAC-signed material, or otherwise cryptographically bind the `shop-domain` header to the signature verification, e.g. by having `to_signable_string` incorporate the header value, or by requiring host apps to cross-check `request.shop` against an already-authenticated session/shop the app expects for that delivery before trusting it as a tenant key.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (a normal, unprivileged action, no special credentials needed beyond running their own shop).
2. Attacker triggers an event (e.g., `orders/create`) on their own shop, causing Shopify to deliver a webhook POST to the app's webhook endpoint with headers:
   `X-Shopify-Hmac-Sha256: <valid HMAC over raw_body>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, body `raw_body`.
3. Attacker intercepts/replays this exact request but rewrites only `X-Shopify-Shop-Domain` to `victim.myshopify.com`, leaving `raw_body` and `X-Shopify-Hmac-Sha256` untouched.
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (== unchanged `raw_body`) and compares to the unchanged `hmac` header — validation passes. [5](#0-4) 
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's order data>, ...)` and, if it uses `shop` to look up/scope tenant records, processes attacker-controlled data under the victim's tenant.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
