### Title
Native-token escrow release reverts entirely if `beneficiary` rejects Ether, permanently blocking `onAccept`/`onGetResponse` delivery and freezing all escrowed funds for that order - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw()`, used by `IntentGatewayV2`'s `onAccept` (for `RedeemEscrow`/`RefundEscrow`) and `onGetResponse` (for cancellation refunds), pushes native-token escrow to `beneficiary` via `_sendValue`, which does a raw `.call{value:...}("")` and reverts the whole transaction if the transfer fails. Because `beneficiary` is attacker-controlled input from the original order (`order.output.beneficiary`), an attacker can place/fill an order whose beneficiary is a contract that rejects plain Ether transfers, causing the ISMP message delivery (`onAccept`) to permanently revert and the escrowed funds for that commitment to become unrecoverable, mirroring the reported Gitcoin `sendValue`/`_grantAddress` DOS pattern.

### Finding Description
`_withdraw` in [1](#0-0)  iterates over the withdrawal's token list and, for the native-token leg, calls `_sendValue(beneficiary, amount)`: [2](#0-1) 

`_sendValue` reverts the entire call with `InsufficientNativeToken` if the low-level call fails — i.e., if `beneficiary` is a contract without a payable `receive`/`fallback`, or one that intentionally reverts.

`_withdraw` is reached from `IntentGatewayV2.onAccept` when the incoming ISMP POST body decodes to `RequestKind.RedeemEscrow`/`RefundEscrow` (analogous logic exists in the Tron variant at [3](#0-2) , and via `onGetResponse` for the cross-chain cancel-refund path (see `_cancelFromSource`/`onGetResponse` flow in `ExtrinsicIntents.sol`). `body.beneficiary` is taken from `order.output.beneficiary`, which is set by the order creator/filler and never validated as capable of accepting native Ether.

Because `onAccept` is invoked by the trusted host during ISMP message delivery (a single relayed proof / dispatched request path), a revert there causes the incoming POST request handling to fail. Since the beneficiary address is fixed at order-placement time and cannot be changed after the fact (there is no rescue/redirect path, unlike `WrappedHyperFungibleToken.onAccept`, which explicitly falls back to wrapping ETH into the ERC-20 form on failed native push — see [4](#0-3) ), the escrowed native tokens for that specific order commitment can never be released: every retry of delivery for the same commitment will hit the same reverting beneficiary.

Note: `IntrinsicIntents.sol`'s same-chain fill path already guards against this for the *fill* leg using an inline check-and-revert pattern documented as "this loop is at the via-ir stack limit" ( [5](#0-4) ) but that still reverts on failure rather than falling back, so the same class of issue exists there for the initial fill, and it can be avoided by the filler simply choosing not to fill a bad order — the escrow release path in `_withdraw`, however, is *not* avoidable since it is driven by protocol/relayer message delivery against attacker-chosen order data.

### Impact Explanation
If a user (or colluding solver) sets `order.output.beneficiary` to a contract that rejects Ether, the redeem/refund path for that specific order's escrowed native-token input becomes permanently non-deliverable: `onAccept` always reverts for that commitment, so `withdraw`/`_withdraw` can never succeed, and the escrowed value is permanently frozen in the `IntentGatewayV2` contract (classified High per the rules: "permanent freezing of funds"). This is scoped to the specific attacker-created order's escrow rather than a global DoS of the gateway (each commitment/order is processed independently), but it is a concrete permanent loss of funds for that order — either the user's original input tokens (refund path) or the solver's expected output token redemption (redeem path).

### Likelihood Explanation
Likelihood is high: any unprivileged user can place an order with `order.output.assets` including the native token and `order.output.beneficiary` set to a non-payable/reverting contract, or can select a colluding beneficiary. No special privileges or timing are required — a single `placeOrder`/`fillOrder` interaction is sufficient to set up the condition, and the subsequent relayed `onAccept` delivery is unavoidable since it's the only path to release escrow.

### Recommendation
Do not let a failed native-token push to an untrusted `beneficiary` revert the entire withdrawal/`onAccept` flow. Options:
- Use a "push, then pull" pattern: attempt `_sendValue`, and on failure, credit the beneficiary's amount to an internal claimable balance (pull-based withdrawal) instead of reverting.
- Alternatively, mirror the fallback pattern already used in `WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout` (wrap failed native pushes into the ERC-20/WETH form and transfer that instead) so delivery always succeeds and funds are not stuck at a specific commitment.
- Ensure this applies uniformly to `_withdraw` (`IntentsBase.sol`), the Tron `withdraw` function, and the inline native-fill push in `IntrinsicIntents.sol`.

### Proof of Concept
1. Attacker deploys `RejectEther`, a contract with no `receive()`/payable `fallback()`.
2. Attacker calls `placeOrder` (or arranges a fill) on `IntentGatewayV2` with an order whose `output.assets` includes the native token (`address(0)`) and `output.beneficiary = address(RejectEther)`.
3. Order proceeds normally through escrow/fill; a `RedeemEscrow` (or `RefundEscrow`, after expiry/cancel) message is dispatched cross-chain.
4. When the relayer delivers the message and the host calls `IntentGatewayV2.onAccept`, execution reaches `_withdraw` → `_sendValue(beneficiary, amount)` → the low-level call to `RejectEther` fails → `revert InsufficientNativeToken()` propagates, reverting `onAccept`.
5. Every subsequent relay attempt for the same commitment hits the identical reverting beneficiary; the escrowed native token amount for that commitment is permanently locked in the gateway with no code path to redirect it.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
