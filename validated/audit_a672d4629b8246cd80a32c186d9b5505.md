### Title
Direct token donations to a curve `Pair` can permanently brick the overflow-cap safety valve, freezing the curve's remaining supply and blocking graduation - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy` relies on an invariant — `reserveToken > realBalance` at every point on the curve — to safely cap the final oversized buy. That invariant is guaranteed only under swap-only trading, but a launched `Token` is a plain ERC20 that anyone can `transfer` directly into its `Pair`. A donation of the launched token to the `Pair` increases `tokenBalance()` without touching the tracked `_pool.tokenReserve`, shrinking the gap the cap logic depends on. Once the gap is driven to zero, the branch that is supposed to gracefully cap the last buy instead reverts with `OverflowCapDegenerate()`, permanently blocking any buy large enough to trip the cap — including the buy that would otherwise drain the curve and trigger supply-based graduation.

### Finding Description
`Router._computeBuy` computes the uncapped `tokensOut` from the constant-product formula, then, if it exceeds the pair's real balance, caps it and back-derives `amountInUsed`: [1](#0-0) 

The critical line is `uint256 cappedReserveToken = reserveToken - tokensOut;` followed by `if (cappedReserveToken == 0) revert OverflowCapDegenerate();`. Since in this branch `tokensOut` is set to `realBalance` (`pair.tokenBalance()`), `cappedReserveToken` is exactly `reserveToken - realBalance` — the gap between the virtual token reserve tracked in `Pair._pool.tokenReserve` and the pair's *actual* ERC20 balance of the launched token.

At launch this gap is fixed at `LP_RESERVE = 250,000,000e18` (`virtualReserveToken = totalSupply` vs `realTokenAmount = curveSupply = 75%`), and the test suite proves it is preserved through ordinary buys/sells: [2](#0-1) 

That invariant test only exercises `_buy`/`_sell` through `Router`/`Bonding` — it never exercises a plain ERC20 `transfer(pair, amount)` of the launched `Token`. `Pair.swap` (called only by the `Router`) updates `_pool.tokenReserve` in lockstep with real token movements, but `Pair.tokenBalance()` is a live `balanceOf` read: [3](#0-2) [4](#0-3) 

Nothing in `Pair.sol` or `Router.sol` prevents a third party from transferring the launched `Token` (a standard, unrestricted ERC20 minted 1:1 to buyers) directly to the `Pair` address. Docs explicitly acknowledge donation to the pair is possible and is only cleaned up at graduation time (`_prepareGraduationLiquidity` burns leftover/donated tokens *after* the curve has already closed) — nothing defends the *live* curve against it: [5](#0-4) 

**Attack construction:** an attacker (any unprivileged holder of the token, obtainable simply by buying via `Zap.buy`) repeatedly:
1. Buys `X` tokens through the normal curve (`Zap.buy` → `Bonding.buy` → `Router.buy`). This leaves `reserveToken - realBalance` unchanged (both drop by `X`).
2. Sends those `X` tokens directly to the `Pair` via `Token.transfer(pair, X)` (no curve interaction). This increases `realBalance` by `X` while `reserveToken` (in `_pool`) is untouched, shrinking `cappedReserveToken = reserveToken - realBalance` by `X`.

Repeating this until the cumulative donated amount equals the current gap (bounded by `LP_RESERVE`, 250M tokens, but the attacker only needs to close the *remaining* gap at the moment they want to trigger the DoS — not necessarily the full 250M, since the gap only needs to reach zero for the specific residual-supply buy an honest trader is about to make) drives `cappedReserveToken` to `0`. From that point on, **any buy whose uncapped `tokensOut` exceeds `realBalance`** — i.e. any buy attempting to consume the remaining curve supply — hits `revert OverflowCapDegenerate()` instead of completing at the capped amount.

### Impact Explanation
This breaks the exact mechanism `AGENTS.md`/`docs/contracts-scope.md` describe as load-bearing ("Overflow buy protection... `Router.buy` caps `tokensOut`... so the last buy cannot exceed remaining supply"). Once bricked:
- Legitimate traders can no longer buy the last chunk of curve supply; every such buy reverts.
- The supply-based graduation trigger (`IPair.tokenBalance() == 0`) can never fire again through ordinary trading, since the buy that would zero out `tokenBalance()` always reverts in the degenerate branch.
- If the paired LT's `exchangeRate()` never independently pumps the USD trigger past threshold, the token is permanently stuck in `Lifecycle.Curve` — trading is effectively capped below full depletion forever, the creator/traders can never complete the intended bonding-curve lifecycle, and the 250M `lpReserve` tokens held in `Bonding` plus the curve-raised LT never reach `Bonding.finalizeGraduation`/HyperSwap LP, permanently freezing that value from ever seeding an LP or being distributed as intended.
- This is a griefing attack that costs the attacker only the (relatively cheap, near-empty-curve) LT spent buying and permanently donating tokens — no privileged role required, matching the CVE's "unprivileged trigger → permanent halt of expected processing" bug class (reachable assertion / DoS), remapped here onto a fund-freezing on-chain equivalent.

### Likelihood Explanation
Medium. The attack requires the attacker to accumulate and donate a meaningful fraction of curve supply (up to the 250M-token virtual gap) which costs real LT to buy from the curve — but the price per token is cheapest early in the curve's life (market cap opens near $3K), and the attacker does not need to close the *entire* 250M gap, only enough to zero out `cappedReserveToken` relative to the *current* `reserveToken - realBalance` gap at the time an honest large/final buy is attempted. Because this is a pure ERC20 transfer with no special permissions, any unprivileged wallet holding the launched token can execute it, and the invariant-breaking mechanics are not caught by any existing on-chain guard or by the documented invariant tests (which only test swap-only trading paths).

### Recommendation
Do not derive `cappedReserveToken` from the live `tokenBalance()` combined with the immutable virtual `reserveToken` without reconciling donation-inflated balances first. Options:
- Track a `donationsExcluded` real-balance accounting in `Pair` (mirroring the LT-side approach already used for `assetReserve` vs. `assetBalance()`), so `_computeBuy`'s cap logic uses the curve-tracked real balance rather than a raw `balanceOf` read that is vulnerable to donations.
- Alternatively, replace the `revert OverflowCapDegenerate()` branch with a floor at `cappedReserveToken = 1` (or otherwise handle the zero case gracefully) so a griefed gap cannot brick buy execution outright, and separately sweep/burn any pre-graduation token donations to keep `tokenBalance()` in sync with the swap-tracked reserve.
- Add a Pair-level `skim`/`sync` style permissionless donation-cleanup entry point (burn excess token balance beyond `reserveToken`'s accounting) usable *during* active trading, not just at graduation.

### Proof of Concept
1. Launch a token via `Bonding.launch`/`Zap.createToken` (virtual `reserveToken = 1e9e18`, `realBalance = 7.5e8e18`, gap = `2.5e8e18`).
2. Attacker repeatedly: `Zap.buy(token, usdcAmt, 0, ref)` to acquire `X` tokens from the curve, then `Token.transfer(pair, X)` directly (bypassing `Zap`/`Router`) to donate them back — repeat until the current `reserveToken - pair.tokenBalance()` gap (read via `Router`'s internal state, observable off-chain from `Pair.getReserves()` and `Pair.tokenBalance()`) reaches `0`.
3. Any subsequent large buy whose unconstrained `tokensOut` (via `Router._computeBuy`'s `reserveToken - (k / newReserveAsset)`) exceeds `pair.tokenBalance()` now computes `cappedReserveToken = reserveToken - realBalance = 0` and reverts `OverflowCapDegenerate()`, matching the check at: [6](#0-5) 

This can be validated by extending `test/GraduationInvariants.t.sol`'s `test_inv_virtualReserveAlwaysExceedsRealBalance` (packages/contracts/test/GraduationInvariants.t.sol:362-377) to interleave a direct `token.transfer(pairAddr, X)` donation between buys and show the invariant `tokenBalance() < reserve0` is violated, followed by an oversized buy reverting with `OverflowCapDegenerate` instead of completing/graduating.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

    ///      `pair.tokenBalance() < pair.tokenReserve()` a hard property at

    function swap(
        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }
