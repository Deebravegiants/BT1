### Title
Emporium relay-fee destination and fee token are not covered by the EIP-712 signature, letting any caller redirect wallet-owner funds - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.verifyWallet` only binds the signer's EIP-712 signature to `emporiumMessage`, the hash of `stack.ops`, `stack.maxFee`, and `stack.deadline`. Neither `circomData.relay` (the fee recipient) nor `circomData.feeStructure.feeToken` (the token the fee is paid in) are part of the signed payload, yet `payRelayFees`/`sendToRelayFromWallet` uses exactly these unsigned fields to pull funds out of the signer's `IHinkalWallet` via `doSendToRelay`.

### Finding Description
The invariant the audit question asks to check is: `(assets leaving the wallet, their destination) == (ops, maxFee) the owner signed`. Tracing the code:

- `verifyWallet` (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:302-349) recomputes `hashedMessage` from `EMPORIUM_SIGNATURE_TYPEHASH` over `circomData.emporiumMessage`, `_hashEmporiumOps(stack.ops)`, `stack.maxFee`, `stack.deadline` only [1](#0-0) . The only fee-related check is `feeStructure.flatFee > stack.maxFee` [2](#0-1) , which bounds the *amount* but never touches `circomData.relay` or `circomData.feeStructure.feeToken`.
- After `runAction` executes the signed `ops`, it calls `payRelayFees(circomData, stack.signerAddress, deltaAmountChanges)` [3](#0-2) .
- In `payRelayFees`, when `signerAddress != address(0)` (i.e., exactly the case that went through the signature check), `relayFee = flatFee` (bounded by `maxFee`), and it is sent via `payRelay(circomData.relay, signerAddress, relayFee, erc20TokenAddress)` [4](#0-3) .
- `payRelay` -> `sendToRelayFromWallet` -> `IHinkalWallet(signerAddress).doSendToRelay(relay, relayFee, feeToken)` [5](#0-4) , which pulls `relayFee` of `feeToken` straight out of the signer's Hinkal wallet to `relay`.

Both `relay` and `feeToken` come from `circomData`, which is supplied by whoever submits the `Hinkal.transact` call (the prover/relayer), not by the wallet owner who only signed `EmporiumSignature(message, ops, maxFee, deadline)`. `CircomData` (contracts/types/CircomData.sol:23-45) shows `relay` and `feeStructure` as independent top-level fields, disconnected from the `EmporiumStack` signature payload defined in contracts/external-actions/emporium/EmporiumStack.sol:11-18.

Consequently, an unprivileged attacker who obtains (or replays, before it is used) a validly signed `EmporiumStack` for a given `emporiumMessage`/`ops`/`maxFee`/`deadline` can submit the transaction with `circomData.relay = <attacker address>` and/or `circomData.feeStructure.feeToken = <any token the wallet holds>`, keeping `flatFee <= maxFee` so `verifyWallet` passes, while the wallet's `doSendToRelay` call sends the fee to the attacker's own address in a token of the attacker's choosing instead of the intended relay/token. `runAction`'s `onlyAllowedRecipient` modifier only restricts which contract (i.e. `Hinkal`) can call `EmporiumUpgradeable.runAction`; it does not constrain the content of `circomData` supplied by the original transaction caller.

None of the existing guards close this gap: `dimensionsCheck`/`checkOnchainCreation`/`rootHashExists` validate UTXO/tree consistency, not fee routing; the flatFee-vs-maxFee check bounds only the amount, not the destination or token.

### Impact Explanation
This lets an unprivileged attacker (any address that can call `Hinkal.transact` with a captured valid `EmporiumStack` signature and craft its own `CircomData`) redirect the wallet owner's relay-fee payment — pulled directly from the owner's `IHinkalWallet` via `doSendToRelay` — to an address and/or token the owner never approved. This is "executing calls / moving assets a wallet owner … never authorised," matching the **High** severity category. It is repeatable for every `EmporiumStack` signature the attacker can observe/relay before it is consumed (each `emporiumMessage` can only be used once due to `usedMessages`, but every fresh signed stack is equally exploitable).

### Likelihood Explanation
Preconditions: the attacker needs access to a validly signed, not-yet-used `EmporiumStack` (e.g., because relayer infrastructure typically transmits these off-chain before submission, or the owner's own signed message is otherwise observable) and the ability to submit the `Hinkal.transact` call with attacker-chosen `circomData.relay`/`feeStructure.feeToken`. No special role is required beyond normal `Hinkal.transact` usage; this is fully within the described unprivileged attacker capabilities (craft every field of `CircomData`). Cost is a single transaction; feasibility is high since the signature scheme structurally omits `relay`/`feeToken`.

### Recommendation
Include `relay` and `feeStructure.feeToken` (and ideally the full `feeStructure`, including `variableRate`) inside the `EMPORIUM_SIGNATURE_TYPEHASH` payload that the wallet owner signs, and verify them in `verifyWallet` against `circomData.relay`/`circomData.feeStructure` before executing `ops` or paying fees. Alternatively, restrict `relay` to protocol-whitelisted addresses via an on-chain allowlist check independent of the signature.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a mock `IHinkalWallet`, and register the test `Hinkal` contract as an allowed recipient.
2. Owner signs an `EmporiumStack` (`ops`, `maxFee = flatFee`, `deadline`) for `emporiumMessage = M` per `EMPORIUM_SIGNATURE_TYPEHASH`.
3. Call `runAction` (as the allowed `Hinkal` caller) with `circomData.emporiumMessage = M`, `circomData.feeStructure.flatFee = maxFee`, but set `circomData.relay = attacker` (different from the relay the owner/relayer infrastructure intended) and/or `circomData.feeStructure.feeToken = <token B>` instead of the originally intended fee token.
4. Assert `verifyWallet` does not revert (signature still validates because `relay`/`feeToken` aren't part of the hash).
5. Assert `doSendToRelay` is invoked with `relay == attacker` and/or `feeToken == tokenB`, i.e., assert `(actual fee destination/token) != (relay/feeToken the owner intended when they authorized ops/maxFee)`, proving the equality `(assets leaving wallet, destination) == (ops, maxFee) signed` is broken.
