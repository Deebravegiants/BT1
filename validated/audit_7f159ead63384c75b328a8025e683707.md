### Title
Non-embedded `cookie_session_id` trusts an unsigned cookie value as a storage key with no shop cross-check, enabling cross-tenant session hijacking - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
`SessionUtils.cookie_session_id` returns `cookies[SESSION_COOKIE_NAME]` verbatim and this value is used directly as the session-storage lookup key [1](#0-0) . For non-embedded apps this cookie is the *only* credential (`current_session_id` skips the JWT branch entirely) [2](#0-1) , and the value the gem itself writes into that cookie at OAuth completion is the raw, deterministic session id (`offline_#{shop}` or `#{shop}_#{user_id}`) with no signature or MAC applied by the gem [3](#0-2) [4](#0-3) .

### Finding Description
The binding that should hold is: `session_loaded_by(cookie_session_id(cookies)).shop == shop_authenticated_for_this_request`. In the non-embedded path there is no independent authenticated shop for the request — the *entire* identity of the request (which shop, which user) is derived solely from the string inside `cookies['shopify_app_session']`, which `cookie_session_id` hands back unmodified [5](#0-4) . Nothing in this gem cryptographically binds that string to the browser session that legitimately received it: `SessionCookie` is a plain `T::Struct` with `name`/`value`/`expires`, containing no HMAC or signature field [6](#0-5) , and the value set into it is exactly `session.id`, i.e. `#{shop}_#{user_id}` for online sessions or `offline_#{shop}` for offline sessions — both fully deterministic and reproducible by anyone who knows the target shop domain and a small numeric user id [7](#0-6) [4](#0-3) .

An attacker who has installed the app on their own development shop can observe the exact format of the session id (e.g. `attacker-shop.myshopify.com_12345`). Because the format is `#{shop}_#{user_id}` with no per-installation secret or nonce, the attacker can construct the id for a different (victim) shop by substituting the victim's shop domain (public knowledge) and iterating small staff user ids. Setting their own browser's `shopify_app_session` cookie to this forged value and calling into the app causes `cookie_session_id` to return the forged id verbatim; whatever storage lookup consumes it (`SessionStorage.load_session`, `session.shop`, `session.access_token`) will load and act on the victim's session with no re-check that `session.shop` matches anything the request actually proved. The OAuth-time state check in `validate_auth_callback` (`state == auth_query.state`) is a one-time, short-lived control for the *login handshake cookie* and does not apply to the long-lived `shopify_app_session` cookie read later by `cookie_session_id` [8](#0-7) . No other guard (`HmacValidator.validate`, `ShopValidator.sanitize!`, `JwtPayload`'s `aud` check, `Context.embedded?`) applies to the non-embedded cookie path, since those all belong to the JWT/embedded branch which is bypassed entirely when `Context.embedded?` is false [9](#0-8) .

### Impact Explanation
Successful exploitation lets an unprivileged attacker load and use another merchant's (or another staff member's) session, including its stored access token, purely by presenting a guessed/forged cookie value — this is cross-tenant/cross-user access and access-token exposure, matching the Critical impact category (cross-tenant access, theft of a merchant access token). It is repeatable against any shop/user id pair the attacker can enumerate, and the blast radius spans every shop using the same non-embedded app installation, not just the attacker's own tenant.

### Likelihood Explanation
Preconditions: app configured `is_embedded: false` (so the cookie is the sole credential) and the host storing the cookie value as delivered by this gem (a plain string with no additional application-level signing). Attacker cost is low: knowledge of the victim shop's domain (public) and a small integer user id (guessable within a limited range for online sessions, or none at all for offline sessions where the id is simply `offline_#{victim-shop}`). No secrets, tokens, or privileged access are required — fully consistent with the unprivileged attacker model.

### Recommendation
Do not use the raw, predictable session id as an unauthenticated, unsigned cookie value. Either (a) sign/HMAC the cookie value with a server-side secret and verify the signature inside `cookie_session_id` before returning it, or (b) generate an unguessable opaque token per session (unrelated to shop/user id) to use as the cookie value and map it server-side to the real session id, and (c) after loading the session, assert that the session's `shop` matches an independently-verified shop for the request (e.g., a `shop` query parameter validated via `ShopValidator`) before trusting it.

### Proof of Concept
```ruby
# test/utils/session_utils_forged_cookie_test.rb
require "test_helper"

class SessionUtilsForgedCookieTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(
      api_key: "key", api_secret_key: "secret", scope: "scope",
      host_name: "host", is_embedded: false, api_version: "unstable",
    )
  end

  def test_forged_cookie_returns_victim_session_id_verbatim
    victim_session_id = "victim-shop.myshopify.com_1" # attacker guesses small user id
    cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => victim_session_id }

    result = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)

    # BROKEN BINDING: nothing asserts result's implied shop == attacker's authenticated shop
    assert_equal victim_session_id, result
    assert_not_equal "attacker-shop.myshopify.com", result.split("_").first
  end
end
```
This demonstrates that `cookie_session_id`/`current_session_id` return an attacker-forged victim session id verbatim with no shop cross-check, confirming the storage-key/consumer divergence described.

      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
