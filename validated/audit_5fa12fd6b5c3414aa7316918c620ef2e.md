## Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) headers are trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the webhook HMAC signature over the raw request body only, but the `shop` field that identifies which merchant/tenant the webhook belongs to is read from an HTTP header that is never included in the signed payload. `ShopifyAPI::Webhooks::Registry.process` verifies the HMAC and then unconditionally hands the header-derived `shop` value to the app's handler, so the "which shop this webhook is for" binding is not authenticated by the HMAC at all.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, independent of the body: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e. the raw body) and secure-compares it to the `hmac` field: [3](#0-2) 

`Registry.process` validates that HMAC, then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` object dispatched to the app's handler, with no cross-check that the shop the HMAC-signed body actually belongs to matches the shop asserted in the unauthenticated header: [4](#0-3) 

The binding that should hold is:
`hmac_signed_bytes == (raw_body ⊕ shop_header ⊕ topic_header)`

but in reality it is only:
`hmac_signed_bytes == raw_body`

So `shop` (the field the handler acts on to select/scope tenant data) is not bound by the signature at all — this is exactly the "field acted on but not covered by the HMAC" identity-binding break called out as an acceptable analog class.

### Impact Explanation
Any unprivileged internet user can install the target app on a shop they control (or on any Shopify development/trial store, which is free and requires no privileges) and thereby obtain genuinely-signed webhook deliveries — Shopify signs these using the app's shared `client_secret`, so the resulting HMAC over the body is valid and produced legitimately, without the attacker ever needing to know the secret. Because the signature only covers the body, the attacker can replay that exact HTTP request to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header with a victim shop's domain. `HmacValidator.validate` still succeeds (body unchanged), and `Registry.process` passes the attacker-chosen `shop` value straight to the app's handler as if it were an authenticated fact about the victim tenant. Depending on how the host app's handler uses `shop` (e.g., to look up/update per-shop records, trigger uninstall/reinstall logic, or write body data under a shop key), this enables cross-tenant data confusion or forged tenant-scoped events — a High-severity identity-binding bypass reachable purely from within this gem's webhook-processing code path.

### Likelihood Explanation
Obtaining a validly-signed webhook body requires nothing more than installing the app on any shop (including free development stores), which is trivially available to any unprivileged internet user. Replaying the HTTP request to the app's public webhook URL with a modified `shop-domain` header requires no secret material and no privileged access — only basic HTTP tooling. The vulnerable code path (`Request#shop`, `HmacValidator.validate`, `Registry.process`) is exercised on every webhook delivery, making this readily reachable.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, and ideally `topic`, `webhook-id`) in the signable string used for HMAC validation, or otherwise cryptographically bind them to the signed body (e.g., compute HMAC over `shop + topic + raw_body`) so that `Registry.process` cannot be fed a body/shop pair that was not jointly authenticated by Shopify.

### Proof of Concept
1. Attacker creates a free Shopify development store and installs the target app, registering a webhook subscription for a topic the app handles.
2. Shopify delivers a webhook to the app: body `B`, headers include `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures this request and replays it to the same app endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com` (body `B` and the HMAC header are left untouched).
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes `HMAC(secret, B)`, which still matches, so validation passes.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches the handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body `B`, even though Shopify never generated this shop/body pairing for the victim.
