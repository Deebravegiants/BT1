The Zest Protocol vaults are Clarity contracts (Stacks), not Solidity — there is no `Locke.sol` here, so this is treated purely as a bug-class hint, per the rules. Searching for the same rounding-to-zero pattern in `ts.tokens`/`streamAmt`-style accounting, I found the closest structural analog in the vault deposit/redeem pair, which is present identically across all vault instances (`v0-vault-usdc.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`, and their `local-testing` counterparts).

### Title
Deposit mints zero shares for value transferred, breaking the share-to-backing identity - (File: `mainnet/contracts/vault/v0-vault-usdc.clar`, and identically in `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`)

### Summary
`deposit` computes `inkind` (shares to mint) via `convert-to-shares-preview` but never asserts `inkind > 0` before transferring the user's underlying and minting shares, unlike `redeem`, which explicitly guards against a zero output with `ERR-OUTPUT-ZERO`. [1](#0-0) 

### Finding Description
`convert-to-shares-preview` performs a floor division `mul-div-down amount ts ta`: [2](#0-1) 

(see the shared helper, e.g. `local-testing/contracts/vault/vault-sbtc.clar:310-317`): [3](#0-2) 

Once the vault has accrued interest (`ta > ts`, i.e., price-per-share > 1), any deposit `amount` smaller than the current price-per-share floors `inkind` to `u0`. In `deposit`, the only zero-guard is on the raw `amount`: [4](#0-3) 

There is no equivalent `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` check. As a result the transaction proceeds: `receive-underlying` pulls the user's tokens, `ft-mint? zft inkind recipient` mints zero shares, and `assets` is still credited by the full deposited `amount`: [5](#0-4) 

This breaks the identity that should hold for every deposit: `value transferred in == value represented by shares minted`. Instead, the depositor's underlying is absorbed into the vault's `assets` accounting and effectively redistributed to all other existing shareholders (raising `total-assets/total-supply` for everyone else) while the depositor receives nothing in return — a silent, permanent loss of principal, not merely a temporary revert as in the analog report.

Compare with `redeem`, which correctly guards the symmetric case: [6](#0-5) 

### Impact Explanation
This is a direct, permanent loss of a user's principal (their deposited underlying is absorbed by the vault with zero shares minted in return) — categorized as theft/permanent freezing of user funds at rest, which is Critical/High impact under the accepted rubric. Low-decimal underlying tokens (e.g., a hypothetical 4-6 decimal token) or vaults that have accrued substantial interest (raising price-per-share) make this far easier to trigger unintentionally, mirroring the "low decimal + accrued duration" conditions from the analog report, except the effect here is fund loss rather than a temporary block.

### Likelihood Explanation
Likelihood is moderate: it requires the vault's price-per-share (`ta/ts`) to exceed the deposited `amount` in the underlying's smallest unit. This becomes increasingly likely over the vault's lifetime as interest accrues (raising `ta` relative to `ts`), and is more easily reachable for underlying assets with fewer decimals (e.g., 6-decimal USDC-like assets) where "1 unit" represents a comparatively larger value. A user (or a UI/integration bug) submitting a very small `amount` after the vault has accrued meaningful interest would trigger silent value loss without any error being raised.

### Recommendation
Add a zero-output guard to `deposit`, symmetric to the one already present in `redeem`:
```clarity
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed alongside the existing `(asserts! (> amount u0) ERR-AMOUNT-ZERO)` check in every vault's `deposit` function, so that a deposit which would mint zero shares reverts instead of silently forfeiting the depositor's underlying.

### Proof of Concept
1. Vault starts with `index`/`lindex` at `INDEX-PRECISION` (1:1), some initial deposits exist, `total-assets-preview` (`ta`) and `total-supply-preview` (`ts`) are equal.
2. Time passes and interest accrues via `accrue`, causing `ta > ts` (price-per-share > 1) — see `total-assets-preview`/`debt-preview` computation: [7](#0-6) 
3. A user calls `deposit` with `amount = 1` (smallest unit of the underlying). `convert-to-shares-preview(1)` computes `mul-div-down(1, ts, ta)`, which floors to `0` because `ta > ts`.
4. `deposit` passes all its `asserts!` (only `amount > u0` is checked, and `1 > 0`), pulls `1` unit of underlying from the user via `receive-underlying`, mints `0` shares via `ft-mint? zft u0 recipient`, and increments `assets` by `1`.
5. The user has permanently lost their `1` unit of underlying with zero compensating shares; the value is absorbed into the vault, proportionally benefiting all other existing shareholders.

(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
