### Title
Escrow credited from dispatcher's raw token balance instead of the delta actually produced by the predispatch call, allowing theft of other orders' dust/residue - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`placeOrder`'s predispatch path in the Tron `IntentGatewayV2` measures how much a given input token the shared `CallDispatcher` holds by reading `IERC20(token).balanceOf(dispatcher)` directly, with no "before" snapshot subtracted. This is the same bug class as the reported `morphoUrdClaim` issue: an amount (here, the swept/dust amount, and the gate that determines whether the order's `requiredAmount` was satisfied) is derived from a total balance rather than from the balance delta produced by the current call. If the dispatcher already holds a balance of that token from any other source — a prior order's leftover dust in the same dispatcher, a donation, or any other order's predispatch flow sharing the same dispatcher contract — that pre-existing balance is silently absorbed into the current order's accounting.

### Finding Description
In `placeOrder`, when an order carries `predispatch.call` and `predispatch.assets`, the contract transfers predispatch assets to `_params.dispatcher`, executes the call, and then sweeps the resulting balance back:

```solidity
for (uint256 i; i < inputsLen;) {
    address token = address(uint160(uint256(order.inputs[i].token)));
    uint256 requiredAmount = order.inputs[i].amount;
    uint256 balance;

    if (token == address(0)) {
        balance = address(dispatcher).balance;
        if (balance < requiredAmount) revert InsufficientNativeToken();
        transferCalls[i] = Call({to: address(this), value: balance, data: ""});
    } else {
        balance = IERC20(token).balanceOf(dispatcher);
        if (balance < requiredAmount) revert InvalidInput();
        transferCalls[i] = Call({
            to: token,
            value: 0,
            data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
        });
    }

    uint256 dust = balance - requiredAmount;
    if (dust > 0) emit DustCollected(token, dust);

    // Store reduced amount (after protocol fees) in escrow
    _orders[commitment][token] += reducedInputs[i].amount;
    ...
}
```

`balance` here is the dispatcher's total balance of the token after the predispatch call, not the balance produced by this specific predispatch call (i.e., not `balanceAfter - balanceBefore`). The `requiredAmount` check (`balance < requiredAmount`) is therefore satisfiable using any tokens that happen to already sit on the shared `_params.dispatcher` contract — a single dispatcher instance used by all orders — regardless of whether the current order's predispatch call actually produced that amount. Additionally, the "dust" swept to the gateway (and the `DustCollected` event) includes any such pre-existing residue, misattributing it to the current order.

This is fixed correctly in the sibling EVM implementation, which snapshots `balancesBefore[i]` prior to the sweep and computes `received = balanceAfter - balancesBefore[i]`: [2](#0-1) 

The Tron contract lacks this before/after delta pattern entirely for the predispatch branch.

### Impact Explanation
Because the `requiredAmount` gate can be satisfied by dispatcher residue rather than tokens actually produced by the placer's own predispatch call, an order placer can under-fund the predispatch call (e.g. supply a smaller swap output than declared in `order.inputs`) as long as the shared dispatcher happens to hold leftover balance of that token from any other party's activity. The contract will still credit `_orders[commitment][token] += reducedInputs[i].amount` — the full nominal reduced amount the placer declared — into escrow. This escrow entry is later redeemable by a solver via `fillOrder`/`RedeemEscrow`, meaning the gateway pays out real tokens against an escrow credit that was never actually backed by the current order's own funds, draining the gateway's token balance that legitimately belongs to other orders/users. This is a real fund-theft/fund-drain path, satisfying "concrete theft of funds."

### Likelihood Explanation
`_params.dispatcher` is a single shared `CallDispatcher` contract used by every order that uses the predispatch feature; any leftover token dust from a previous predispatch call (which is a realistic occurrence given the surrounding contract's own dust-handling/`DustCollected` semantics), or a trivial small donation transfer to the known dispatcher address by an attacker, is sufficient to trigger the flawed accounting. The bug is reachable from a single, unprivileged `placeOrder` transaction with `predispatch.call`/`predispatch.assets` populated — no special privileges, governance, or multi-step setup required.

### Recommendation
Snapshot each input token's (and native) balance on the dispatcher immediately before dispatching predispatch calls, and compute the swept/escrowed/dust amounts strictly from `balanceAfter - balanceBefore`, mirroring the pattern already used in `evm/src/apps/IntentGatewayV2.sol` (`balancesBefore[i]` / `received = balanceAfter - balancesBefore[i]`). This ensures escrow crediting and dust accounting reflect only value actually produced by the current order's predispatch execution, not any balance incidentally present on the shared dispatcher beforehand.

### Proof of Concept
1. Attacker (or anyone) sends a small amount of `TokenX` directly to the known `_params.dispatcher` address (or relies on residue left by any prior predispatch call for the same token).
2. Attacker calls `placeOrder` with `order.inputs[0] = {token: TokenX, amount: requiredAmount}` and a `predispatch.call`/`predispatch.assets` that intentionally produces less than `requiredAmount` of `TokenX` on the dispatcher (e.g., a minimal or no-op call).
3. In the sweep loop, `balance = IERC20(TokenX).balanceOf(dispatcher)` includes the pre-existing residue, satisfying `balance >= requiredAmount` even though the current predispatch call under-delivered.
4. `_orders[commitment][TokenX] += reducedInputs[0].amount` credits the full nominal escrow amount, and the full `balance` (including the unrelated residue) is swept to the gateway.
5. A colluding/attacker-controlled solver later calls `fillOrder` and redeems the escrow via `RedeemEscrow`, receiving tokens the attacker never actually deposited for this order — draining value that belonged to the dispatcher/other orders.
