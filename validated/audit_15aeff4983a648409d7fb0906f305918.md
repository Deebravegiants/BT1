### Title
Webhook `shop` domain is trusted for tenant identification without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, while the HMAC that `Registry.process` validates only covers the raw request body. This breaks the identity binding: `hmac == HMAC(secret, raw_body)` is verified, but `shop` (the tenant identifier passed on to webhook handlers) is never part of that signed material, so `shop` can be set to any value independently of what the signature actually authenticates.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from a header that is not part of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC over `request.to_signable_string` (i.e. only the body), and then unconditionally forwards `request.shop` to the handler as the tenant identity for the event: [3](#0-2) 

`HmacValidator.validate_signature` confirms the check is solely `OpenSSL.secure_compare(computed_signature, received_signature)` against `verifiable_query.to_signable_string` (the body), never touching headers such as `shop-domain`: [4](#0-3) 

Because every shop that installs a given app shares the same `api_secret_key`, any body+HMAC pair that is valid for one shop's webhook delivery remains a valid (body, HMAC) pair regardless of which `shop-domain` header accompanies it. An attacker who has legitimate access to their own installed shop (an unprivileged, non-Shopify-employee "merchant" account) receives real webhook deliveries with a valid HMAC computed from the shared app secret. That attacker can replay the exact same raw body and HMAC to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value (e.g., a victim shop's domain). `HmacValidator.validate` still returns `true` because it only checks the body bytes, yet `Registry.process` forwards the attacker-chosen `shop` value into `WebhookMetadata` and the app's handler, which uses `shop` as the tenant key for its business logic (e.g. crediting an event, updating a database row, uninstalling data, etc., depending on the handler).

This is the same class of flaw as the referenced report: a value trusted to identify the acted-upon entity ("shop"/tenant) is not the value actually bound by the cryptographic check ("hmac over raw_body"), so an attacker can substitute the identity while keeping the check green — analogous to following a deleted/different profile because the handle check doesn't bind to the actual profile id.

### Impact Explanation
This is a High severity issue: it allows cross-tenant confusion/injection in webhook processing. An attacker who legitimately controls one shop instance of the app can forge webhook events that the app's handler will process as if they belong to a different (victim) shop, because the `shop` field used for tenant identification is never bound to the signature that the gem validates. Depending on what the consuming application does with `WebhookMetadata#shop` (e.g., write to per-shop tables, trigger billing/fulfilment actions, or determine session/credential lookups), this can lead to cross-tenant data corruption or actions being attributed to the wrong merchant.

### Likelihood Explanation
Any user who can install the app on their own store (a normal, unprivileged action) automatically gets legitimately-signed webhook bodies delivered to the app's public endpoint. Replaying that body with a different `shop-domain` header requires no secrets, no privileged access, and no interaction with Shopify's servers beyond normal app installation — only the ability to send an HTTP POST to the app's own publicly reachable webhook URL, which by design must be reachable from the internet.

### Recommendation
Bind the trusted tenant identity to the value that is authenticated. At minimum, when validating a webhook request, the shop that will be used for business logic must be cross-checked against a shop that is otherwise known to be trusted for that specific webhook subscription (e.g., correlate `webhook_id` or a per-shop signing context rather than trusting the header value as-is), or compute/verify the HMAC over a signable string that includes the `shop-domain` header value in addition to the raw body, so a mismatched `shop` header invalidates the signature the same way a mismatched body would.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged action supported by the app).
2. Shopify sends a legitimate webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`, and some `raw_body`.
3. Attacker captures this `raw_body` and `hmac` value.
4. Attacker sends a new POST request to the same public webhook endpoint with the identical `raw_body` and `hmac`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because it only checks `raw_body` against the shared `api_secret_key`.
6. `ShopifyAPI::Webhooks::Registry.process` in `lib/shopify_api/webhooks/registry.rb` calls the registered handler with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from `attacker-shop.myshopify.com`'s webhook delivery, demonstrating the tenant/identity confusion.
