### Title
Webhook `X-Shopify-Shop-Domain` (and topic/webhook-id) headers are not covered by the HMAC signature, allowing cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` only proves the request *body* was produced with the app's secret key. The `shop`, `topic`, `webhook_id`, and `api_version` values are read from HTTP headers that are never included in the signed data, so they can be modified freely by anyone relaying the request without invalidating the HMAC check.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates authenticity solely via: [1](#0-0) 

`Utils::HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` is defined as the raw body only: [3](#0-2) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight from headers with no cryptographic binding to the HMAC: [4](#0-3) 

After validation succeeds, `request.topic` selects the handler and `request.shop` is passed into `WebhookMetadata` and handed to the app's handler as the identity of the shop the event belongs to: [1](#0-0) 

The broken identity binding is:
`HMAC-verified bytes (raw_body only)` ≠ `shop/topic/webhook_id header values acted upon by the handler`

Because the signature covers only the body, any party that has ever received one legitimate, validly-signed webhook body from Shopify (e.g., by installing the app on their own store and receiving a routine webhook such as `orders/create` or `app/uninstalled`) can replay that exact `raw_body` + `hmac` pair while substituting an arbitrary `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header. `HmacValidator.validate` will still return `true` because it never inspects those headers, and `Registry.process` will hand the attacker-chosen `shop` value to the host application's webhook handler as if the event genuinely originated from that shop.

### Impact Explanation
Host applications built on this gem rely on `WebhookMetadata#shop` (sourced from `request.shop`) to determine which tenant a webhook event applies to (e.g., updating billing/subscription state, processing GDPR `customers/redact` or `shop/redact` payloads, deactivating a shop on `app/uninstalled`, syncing order/product data). Because the shop identity is not bound to the cryptographic proof of authenticity, an attacker who legitimately receives any single valid webhook can forge events attributed to a different, victim shop, causing the host app to write/act on the victim's tenant record with attacker-supplied body content. This is a cross-tenant identity-binding break reachable by any unprivileged party that can install the app on a store they control (a standard, non-privileged flow) and can send HTTP requests to the app's public webhook endpoint — no access to `api_secret_key`, access tokens, or the merchant's credentials is required.

### Likelihood Explanation
Requires only: (1) installing the target app on an attacker-controlled Shopify store (trivial, unprivileged, and normal usage of the platform) to obtain one legitimate `raw_body`+`hmac` pair, and (2) sending a crafted HTTP request to the app's public webhook callback URL with the captured body/HMAC but a spoofed shop-domain (and optionally topic) header. No secret material or victim credentials are needed, making this practically exploitable by any internet user against apps that trust `WebhookMetadata#shop`/`#topic` for tenant-scoped actions.

### Recommendation
Bind the shop, topic, and webhook-id to the HMAC-verified data instead of trusting bare headers:
- Include the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` header values in the string that is HMAC-verified (analogous to how `Auth::Oauth::AuthQuery#to_signable_string` folds `shop`, `state`, etc. into the signed payload), or
- Independently corroborate `request.shop` against the shop associated with the session/tenant record the webhook claims to target before acting on it, and reject mismatches.

### Proof of Concept
```ruby
# Attacker installs the app on their own store "attacker.myshopify.com" and captures
# a legitimately signed webhook (raw_body + valid X-Shopify-Hmac-Sha256).
raw_body = '{"id":123,"email":"attacker@example.com"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# Attacker replays the SAME body/hmac but swaps the shop-domain header to the victim shop.
forged_headers = {
  "x-shopify-topic" => "customers/redact",
  "x-shopify-hmac-sha256" => valid_hmac,       # still valid: body unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unverified
  "x-shopify-webhook-id" => "attacker-chosen-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (only raw_body is checked),
#    handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
#    even though the body/HMAC never originated from that shop.
```

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end
