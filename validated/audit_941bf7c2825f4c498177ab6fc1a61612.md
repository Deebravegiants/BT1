### Title
Webhook `shop` field is trusted but not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value used for tenant attribution from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature computed by `Utils::HmacValidator` only covers the raw request body, never the shop header. This breaks the binding `hmac_verified_bytes == data_acted_on`, letting anyone who possesses one legitimately-signed webhook payload relabel it for a different shop and have it accepted as authentic.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` calls `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only `@raw_body`: [2](#0-1) 

However, the `shop` accessor — which is passed straight into `WebhookMetadata` and handed to the app's handler as the tenant identifier — is read from a separate, unsigned header: [3](#0-2) [4](#0-3) 

So the equality the code implicitly relies on — "bytes verified by HMAC" == "bytes the handler treats as this shop's data" — does not hold: the HMAC signs the body, but the shop attribution comes from an out-of-band header that is never part of `to_signable_string`.

### Impact Explanation
An attacker who controls (or has installed) the app on **shop A** can capture one legitimately-signed webhook request Shopify sends to their own endpoint (a normal, unprivileged action — no `api_secret_key` needed). They can then resend that exact `raw_body`/`hmac-sha256` pair to the same webhook endpoint while substituting `x-shopify-shop-domain: shop-b.myshopify.com`. `HmacValidator.validate` still succeeds because it only checks the body against the HMAC; `Registry.process` then dispatches the handler with `shop: "shop-b.myshopify.com"` and the attacker-chosen body, having the host application record/act on data as if it originated from shop B. Any host application that uses `WebhookMetadata#shop` to route to per-tenant storage, look up the tenant's session, or gate business logic will process forged data under a foreign tenant's identity — a cross-tenant data-integrity/access break attributable to this gem's `shop` binding.

### Likelihood Explanation
The prerequisite (having received one valid webhook for one's own shop) is trivial for any developer/merchant that installs the app, which is an ordinary, unprivileged path — no leaked secrets, no TLS interception, and no reliance on host misconfiguration; the gem's own `Request`/`Registry.process` API is used exactly as documented.

### Recommendation
Include the `shop`/`shop-domain` header (and ideally `topic`, `api-version`, `webhook-id`) in the value returned by `to_signable_string`, or independently verify that the `shop` header matches a shop the receiving handler expects/owns before trusting it, so the HMAC binds the full set of fields the application acts on.

### Proof of Concept
1. Install the app on `shop-a.myshopify.com`; capture a real webhook POST (raw body `B`, header `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: shop-a.myshopify.com`).
2. Replay the same request to the webhook endpoint, changing only `x-shopify-shop-domain` to `shop-b.myshopify.com`, keeping body `B` and header `H` unchanged.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes HMAC over `B` only [5](#0-4)  — validation succeeds.
4. The handler receives `WebhookMetadata.new(... shop: "shop-b.myshopify.com" ...)` [4](#0-3)  and processes attacker-controlled data as belonging to shop B.
