### Title
Webhook HMAC validation does not bind the `shop-domain` header to the signed payload, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the raw body only, then passes the header-derived `request.shop` straight to the app's webhook handler as the tenant identifier, without that value ever being covered by the signature.

### Finding Description
The webhook signature verification path is:
- `ShopifyAPI::Webhooks::Request#hmac` reads `shopify-hmac-sha256` from headers. [1](#0-0) 
- `#to_signable_string` — the bytes the HMAC actually authenticates — is just `@raw_body`. [2](#0-1) 
- `#shop`, `#topic`, `#webhook_id`, `#api_version` are all pulled from headers, which are never included in the signable string. [3](#0-2) 
- `Registry.process` validates the HMAC (`Utils::HmacValidator.validate(request)`, which computes `HMAC(secret, to_signable_string)` i.e. `HMAC(secret, raw_body)`), then immediately forwards `request.shop` (and `request.topic`) — unauthenticated header values — to the app's handler as the trusted tenant/topic identity. [4](#0-3) 

The binding that is broken is:
`shop authenticated by HMAC (over raw_body only)` ≠ `shop the handler trusts (request.shop header, unsigned)`.

Because the header is not part of the signed material, anyone who can obtain one valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` — which any unprivileged merchant can obtain simply by installing the app on their own store and receiving a genuine webhook for their own shop — can replay that exact `raw_body`/`hmac` pair while substituting an arbitrary `shop-domain` header. `HmacValidator.validate` will still pass because it only checks `raw_body` against the secret; the app handler, however, will process the event as if it came from the victim shop specified in the forged header.

### Impact Explanation
This breaks the shop-authentication boundary between tenants (cross-tenant access): a merchant who has legitimately installed the app can forge webhook deliveries that the app's handler will attribute to a different (victim) shop, since `WebhookMetadata.shop` is populated straight from the unauthenticated header value passed by `Registry.process`. Depending on how the host application keys data by `data.shop` (e.g. GDPR redact/data-request handling, order sync, inventory updates), this can cause cross-tenant data corruption, unauthorized redaction, or processing actions against another merchant's records — a Critical-class cross-tenant boundary violation per the accepted impact set.

### Likelihood Explanation
Exploitation requires only an "unprivileged internet user" capability already granted by the app model: install the app (or otherwise trigger a legitimate webhook delivery) to capture one valid `(raw_body, hmac)` pair, then replay it to the app's public webhook endpoint with a forged `shopify-shop-domain` header. No access to `api_secret_key`, access tokens, or the victim's credentials is required.

### Recommendation
Include the shop domain (and ideally topic) in the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop`/`topic` values to the verified payload before they are handed to the application handler (e.g., verify that the merchant's installed session/access token actually corresponds to the shop asserted in the header, or require the shop identity to be embedded in and validated as part of the signed body rather than trusted from headers alone).

### Proof of Concept
1. Install the target app as an unprivileged merchant on `attacker-shop.myshopify.com` and capture one legitimate webhook POST, e.g. body `{"id":1}` with headers:
   - `x-shopify-hmac-sha256: <valid HMAC of body with app's api_secret_key>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-topic: shop/redact`
2. Replay the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but change the header:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, raw_body)` — unchanged — so validation succeeds. [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the request was never authenticated for that shop, and the app processes it as a genuine event from the victim tenant.
