### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats `request.shop` as a trusted, Shopify-verified tenant identifier once `Utils::HmacValidator.validate(request)` succeeds. In reality the HMAC only signs the raw request body — the `shop` value comes from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is never included in the signed material. Because the app's `api_secret_key` is shared across every shop that has installed the app, a valid HMAC over a given body proves only "this body was produced by someone who knows the app secret and controls a webhook feed for the app" — it proves nothing about which shop the payload is "for". An attacker who can trigger a genuinely signed webhook (e.g., by installing the target app on their own store) can therefore replay that signed body with a forged `shop` header naming a different tenant.

### Finding Description
`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, and for webhooks that string is defined as the raw body only: [1](#0-0) [2](#0-1) 

The `shop` accessor is read straight from the (attacker-controllable) header and is never fed into the signature computation: [3](#0-2) 

`Registry.process` performs only the HMAC check and topic lookup, then hands the unauthenticated `shop` value straight to the app's handler as if it were verified: [4](#0-3) 

This breaks the equality the app author is entitled to assume: `hmac_valid(body, api_secret_key) == true` should imply `request.shop == the tenant that produced this signed payload`. In fact `request.shop` is disjoint from anything the signature covers, so the equality never held — it only appeared to hold because in the common case the header matches the originating shop. Because `api_secret_key` is a single shared secret for the whole app (not per-shop), any shop that has installed the app can produce a validly-signed body and pair it with a spoofed `shop` header naming any other tenant of the same app, and `Registry.process`/`WebhookMetadata` will pass that forged identity on to the handler unchanged.

### Impact Explanation
This is a cross-tenant identity-binding bypass: the gem exposes `WebhookMetadata#shop` to app developers as the authenticated source of the webhook, and the developer-facing tests in this repo confirm the intended contract that handlers key off `data.shop` for tenant-specific processing. [5](#0-4) 
Any downstream logic (session/data lookups, entitlement decisions) keyed on `data.shop` inherits a spoofable value despite an HMAC check having "passed," which is exactly the cross-tenant class of impact called for by the rules.

### Likelihood Explanation
Exploitation requires only: (1) being able to install the target app on an attacker-controlled shop (no special privilege beyond being a merchant), which yields legitimately signed webhook deliveries under the shared `api_secret_key`; and (2) POSTing a captured/regenerated raw body plus its valid HMAC to the app's public webhook endpoint with an altered `shop` header. No access token, `api_secret_key` leakage, or privileged account is needed — the app's webhook endpoint is by design internet-reachable and unauthenticated apart from the HMAC check.

### Recommendation
Bind the `shop` (and ideally `topic`) into the material that is actually verified against Shopify's expectations rather than trusting the raw header outright: at minimum, `Registry.process`/`WebhookMetadata` should document/require that consuming apps independently confirm `request.shop` corresponds to a shop with an active installation/session before using it for tenant-scoped decisions, and the gem should not present `shop` as if it were HMAC-verified. Where possible, prefer deriving tenant context from a source that is cryptographically bound to the request (e.g., validating against a known/installed shop list) rather than an unauthenticated header field.

### Proof of Concept
1. Install the target Shopify app on attacker-owned store `attacker.myshopify.com`; register/observe a legitimate webhook delivery, capturing `raw_body` and its `x-shopify-hmac-sha256` value (both are visible to the attacker as the destination of their own webhook endpoint, or replayable via a network intermediary the attacker controls).
2. Send an HTTP request to the app's public webhook endpoint with the same `raw_body` and the same `x-shopify-hmac-sha256`, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(raw_body, api_secret_key)`; see [6](#0-5) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, so the app processes attacker-supplied data under the victim shop's identity, per [7](#0-6) .
