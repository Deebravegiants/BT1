**Analysis:**

The premise conflates two unrelated checks. `verify_constant_data` in `move-bytecode-verifier/src/constants.rs` only validates that a constant's byte encoding can be deserialized into a value of its declared `SignatureToken` type — e.g., for `SignatureToken::U64` it checks the data is exactly 8 bytes and decodes to *some* `u64` value [1](#0-0) . There is no concept of an "out-of-range" `u64` value here — every 8-byte little-endian sequence decodes to a value within the full valid `u64` range `[0, 2^64-1]`. The verifier's job is type/format well-formedness, not business-logic bounds checking.

The actual custody invariant (split amount ≤ source balance) is enforced at runtime via explicit `assert!` statements inside every split/merge implementation examined, regardless of where the amount value originated (constant, argument, or computed value):
- `token.move::split`: `assert!(dst_token.amount > amount, ...)` before subtracting [2](#0-1) 
- `fungible_asset.move::extract`: `assert!(self.amount >= amount, error::invalid_argument(EINSUFFICIENT_BALANCE))` [3](#0-2) 
- Example `MultiToken.move::split` / `NFT.move::split_out`: `assert!(token.balance >= amount, ...)` [4](#0-3) [5](#0-4) 

These assertions execute at interpretation time via the Move VM's normal instruction dispatch, e.g. how `LdConst` merely pushes a deserialized value onto the operand stack [6](#0-5)  — the subsequent arithmetic and comparisons in the split/merge function bodies are unaffected by whether the amount came from a module constant or any other source. There is no code path where a crafted constant bypasses these runtime bounds checks; if `amount` exceeds `balance`, the transaction aborts before any subtraction occurs, so underflow of the source balance cannot happen. Since the custody-invariant check is enforced independently of constant verification, this scenario does not cross a real custody boundary.
