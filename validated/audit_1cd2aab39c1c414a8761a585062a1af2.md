### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop` and `topic` as plain HTTP-header reads, while the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body (`to_signable_string` returns `@raw_body`). `Registry.process` accepts any request whose body-HMAC is valid and then trusts the unauthenticated `shop` header to build `WebhookMetadata`, which is the identity a consuming application uses to attribute the webhook to a tenant.

### Finding Description
`Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the signed content: [2](#0-1) 

`HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac` header, i.e. it only proves "this body was signed by someone holding the app's client secret" — it says nothing about which shop the header claims to be from: [3](#0-2) 

`Registry.process` then does exactly one check (`HmacValidator.validate(request)`) before dispatching to the handler with `shop: request.shop` taken from the unauthenticated header: [4](#0-3) 

The identity binding that should hold is:
`hmac-covered bytes == bytes that determine which shop/topic the webhook is attributed to`

but in this gem it is actually:
`hmac-covered bytes == raw_body` while `shop (tenant identity) == unauthenticated header value`

Because a single Shopify app has one `api_secret_key` shared across every shop that installs it, `HMAC(secret, body)` is identical for identical body bytes regardless of which shop originated the request. An unprivileged user who has their own store with the app installed (or who otherwise obtains one valid `body` + `hmac-sha256` pair, e.g., from their own webhook deliveries) can capture that legitimate webhook and resend it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header rewritten to a victim shop. `HmacValidator.validate` still passes because it never inspects the shop header, and `Registry.process` forwards `shop: request.shop` (the attacker-controlled value) straight to the host application's handler as if it were verified.

### Impact Explanation
The host application's `WebhookHandler#handle` implementations are expected to trust `WebhookMetadata#shop` as the tenant identity, since the whole point of HMAC verification is to let handlers skip separately authenticating the caller. Because `shop` is not bound to the signature, an attacker can cause the handler to process attacker-supplied body content under a victim shop's identity — e.g., writing/deleting data keyed by `shop`, marking a victim's app installation as uninstalled/updated, or triggering shop-scoped side effects — resulting in cross-tenant access/manipulation. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any user who can install the app on their own shop (a completely unprivileged action available to any merchant) automatically obtains valid `(body, hmac)` pairs signed with the app's real secret. Replaying that pair with a modified `shop-domain` header requires no access to `api_secret_key`, tokens, or TLS interception — only a normal HTTP client — making this readily reachable by an ordinary internet user acting as a self-service merchant.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-covered signable content, or otherwise cryptographically bind the header-derived `shop` value to the verified payload before it is handed to `WebhookHandler#handle`. At minimum, document that host applications must independently verify `WebhookMetadata#shop` against a known/installed-shop list before trusting it, since `Registry.process` currently only validates the body's HMAC.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and receives a legitimate webhook delivery: body `B`, header `X-Shopify-Hmac-Sha256: H = HMAC(secret, B)`, `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker replays the exact same request to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim.myshopify.com` (and/or `X-Shopify-Topic` if desired, since neither is signed).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches `H` — validation succeeds because the shop header was never part of the signed input: [5](#0-4) 
4. The registered `WebhookHandler#handle` is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the host app to act on behalf of the victim shop using attacker-controlled body content, even though the victim never sent this webhook.
