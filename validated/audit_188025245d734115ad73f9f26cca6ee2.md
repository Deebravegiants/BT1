### Title
Signed `maxFee` cap for HinkalWallet relay payments can be exceeded because `relay` is unsigned and `flatFee` is validated once but paid per matching token leg - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.payRelayFees` walks `circomData.erc20TokenAddresses` and, for every index whose `deltaAmountChanges[i] < 0` that matches `feeStructure.feeToken`, calls `payRelay` → `sendToRelayFromWallet` → `IHinkalWallet(signerAddress).doSendToRelay(relay, flatFee, feeToken)`. Because the same fee token can legitimately appear more than once in `erc20TokenAddresses` (multiple negative-delta legs of one token), `flatFee` is charged once per matching leg instead of once per operation, while `verifyWallet` only checks `feeStructure.flatFee > stack.maxFee` a single time. Additionally, the `relay` address that receives these funds is not part of the EIP-712 hash signed by the wallet owner (`EMPORIUM_OPERATION_TYPEHASH`/`EMPORIUM_SIGNATURE_TYPEHASH` only cover `endpoint, invokeWallet, value, callData`), so whoever submits the transaction chooses where the (possibly duplicated) fee goes.

### Finding Description
The invariant that should hold is: *total relay fee taken from a signed Emporium operation ≤ `stack.maxFee`, and paid only to the relay the signer intended*. This is violated:

1. `verifyWallet` bounds only the per-occurrence `flatFee` against `maxFee`: [1](#0-0) 
2. `payRelayFees` iterates every token index with a negative delta and re-evaluates `isFeeToken`/`flatFee` per index, invoking `payRelay` for each match: [2](#0-1) 
3. Each match ultimately reaches `HinkalWallet.doSendToRelay`, which trusts the `relay` argument forwarded by the Emporium contract with no additional check besides `onlyEmporium`: [3](#0-2) 
4. `relay` is a `CircomData` field, not part of the signed `EmporiumOperation`/`EmporiumSignature` payload: [4](#0-3) 

So a transaction submitted with a valid, previously-signed `EmporiumOperation` stack for the victim's own wallet, but with the fee token repeated across two (or more) negative-delta legs of `circomData.erc20TokenAddresses`, causes `doSendToRelay` to be invoked multiple times for `flatFee`, sending a multiple of the signed fee cap out of the wallet — and the submitter can freely set `circomData.relay` to any address since it isn't bound by the signature, redirecting these payments away from the intended relay.

Note: `doSendToRelay`/`callHinkalWallet` themselves are correctly restricted to `onlyEmporium`, and `invokeWallet` calls still require `stack.signerAddress`'s EIP-712 signature over the `ops` array, so an attacker cannot forge a wallet's participation from scratch — they need a validly signed stack for that wallet. This limits the attack to the signer's *own* wallet or to a case where the signer authorized an operation without anticipating that the relay-fee leg could be duplicated/redirected.

### Impact Explanation
- The extra `flatFee` payments and the unsigned `relay` field together allow moving funds from the HinkalWallet beyond what the owner authorized (`maxFee`) and to a recipient the owner never picked. This matches "High: executing calls or moving assets a wallet owner ... never authorised" and "theft ... of relay fees."
- It does **not** amount to draining the wallet's entire arbitrary balance as framed in the question, because (a) `doSendToRelay` can only be triggered through a validly signed `EmporiumOperation` stack for that specific wallet — an attacker cannot forge this for a victim wallet without the victim's signature, and (b) the overcharge is bounded by `(occurrences of feeToken - 1) * flatFee`, not the wallet's full balance.

### Likelihood Explanation
- Requires the wallet owner (attacker's own wallet, or a careless integrator/signer) to sign an `EmporiumOperation` stack whose corresponding `circomData.erc20TokenAddresses` includes the fee token in more than one negative-delta leg — a pattern the protocol appears to support architecturally (multiple output legs of the same token), so it is plausible but not guaranteed to be reachable for every operation type.
- The transaction submitter (who need not be the signer or a whitelisted relay) fully controls `circomData.relay`, `circomData.erc20TokenAddresses` ordering, and `deltaAmountChanges` layout at submission time as public circuit inputs, making the redirection trivial to attempt once a matching signed stack + proof exists.
- I could not verify from the available files whether `performHinkalChecks`/`dimensionsCheck` in `HinkalHelper` (not fully inspected) forbid duplicate token entries in `erc20TokenAddresses` for the Emporium path, so the exact reachability of a duplicated fee-token leg is not fully confirmed.

### Recommendation
- Include `relay` (and `feeStructure`) inside the EIP-712 typed data signed by `stack.signerAddress` so the owner explicitly authorizes the fee recipient.
- In `payRelayFees`, accumulate the total flat fee actually paid across all matching legs and compare that cumulative total (not the per-occurrence value) against `stack.maxFee`, or restrict `flatFee` to be charged at most once per operation regardless of how many legs match `feeStructure.feeToken`.

### Proof of Concept
Not fully reproducible from the indexed files alone: confirming whether `HinkalHelper.performHinkalChecks`/`dimensionsCheck` permit a duplicate fee-token entry in `circomData.erc20TokenAddresses` (and generating a matching valid proof) requires inspecting `HinkalHelper.sol` and the circuit constraints in full, which were only partially available in this pass. A Foundry/Hardhat test would need to:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, and a `HinkalWallet` for a signer, fund the wallet.
2. Sign an `EmporiumOperation[]` stack with `maxFee == feeStructure.flatFee`.
3. Craft `CircomData` with the fee token appearing twice among `erc20TokenAddresses` with negative `deltaAmountChanges`, and `circomData.relay` set to an attacker address.
4. Generate a locally valid proof for this input vector and call `Hinkal.transact`.
5. Assert `attackerRelayBalanceAfter - attackerRelayBalanceBefore == 2 * flatFee > stack.maxFee`, proving the signed cap was exceeded and funds went to an address never included in the signed hash.
