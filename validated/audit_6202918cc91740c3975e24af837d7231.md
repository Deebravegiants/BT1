Audit Report

## Title
Cross-workflow response cache confusion via workflow-owner-scoped-only cache key - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

## Summary
The gateway's `responseCache` keys cached outbound HTTP action responses solely by `gateway.OutboundHTTPRequest.Hash()`, which the package's own test suite proves incorporates `WorkflowOwner` but explicitly excludes `WorkflowID`. This means two distinct workflows registered under the same owner address that issue an HTTP action with an identical method/URL/headers/body will collide on the same cache entry, causing one workflow to silently receive another workflow's previously cached response — directly contradicting the documented "workflow ID scoped" isolation guarantee in the handler's `README.md`.

## Finding Description
`responseCache.Fetch` and `responseCache.Set` both key cache entries using `req.Hash()` alone: [1](#0-0) [2](#0-1) 

The struct comment states the hash is derived from "method, URL, headers, body, workflowOwner" — notably omitting `WorkflowID`: [3](#0-2) 

This is confirmed as actual runtime behavior (not just a stale comment) by the package's own test suite, which has a dedicated test asserting identical hashes for requests differing only in `WorkflowID`, alongside a test confirming that differing `WorkflowOwner` does change the hash: [4](#0-3) [5](#0-4) 

This contradicts the documented design intent in the handler's README, which explicitly states cache entries are keyed by "workflow ID and request hash" and that "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage": [6](#0-5) 

The cache is populated and consulted directly from unmarshaled, node-supplied `OutboundHTTPRequest` data in `makeOutgoingRequest`, with no additional per-workflow namespacing applied on top of `Hash()`: [7](#0-6) 

No other code path re-introduces `WorkflowID` into the cache key or otherwise segregates the map by workflow before lookup/storage, so any two workflows sharing a `WorkflowOwner` and issuing structurally identical HTTP action requests will read/write the same `cachedResponse` entry.

## Impact Explanation
This is a genuine data-isolation defect: a workflow author who registers multiple workflows under one owner address (a normal, permissionless action) can have one workflow's HTTP action response — potentially stale, attacker-influenced, or simply unrelated data — silently substituted into a sibling workflow's execution when both issue the same request shape within the cache TTL (`CacheSettings.MaxAgeMs`, documented default up to 10 minutes). Since CRE workflow decision logic can act on HTTP action results (including driving downstream job execution or fund-moving decisions), this constitutes a legitimate cross-workflow response corruption/isolation-bypass issue, matching the "cross-user response corruption" impact class. Severity is bounded by the requirement that colliding workflows share the same owner and identical request parameters, and by the TTL window, but it is not a hypothetical: the discrepancy between the documented design (`WorkflowID`-scoped) and actual implementation (`WorkflowOwner`-only) is verified by the codebase's own tests.

## Likelihood Explanation
No privileged or operator access is required — only the ability to author/register more than one workflow under the same owner address and have both issue HTTP actions with matching method/URL/headers/body within the TTL, which is a standard, unprivileged workflow-authoring capability. The dedicated regression test (`"having different workflowID results in same Hash"`) confirms this is the actual, currently shipping behavior rather than a theoretical edge case.

## Recommendation
Include `WorkflowID` in `OutboundHTTPRequest.Hash()` (and consider `ExecutionID`/`ReferenceID` if per-execution isolation is also desired), or explicitly namespace the `responseCache` map/key by `WorkflowID` in addition to the request hash within `response_cache.go`, so the implementation matches the "workflow ID scoped" isolation guarantee documented in `README.md`.

## Proof of Concept
1. Register two workflows `wfA` and `wfB` under the same `WorkflowOwner`.
2. `wfA` issues an HTTP action `GET https://example.com/api` with `CacheSettings.Store=true`; the gateway executes the request and caches the response under `req.Hash()` via `responseCache.Set`/`Fetch`.
3. `wfB` issues the identical `GET https://example.com/api` HTTP action (same headers/body) within `MaxAgeMs`.
4. `wfB` receives `wfA`'s cached response without the gateway executing `wfB`'s own request, as proven by `TestRequestHash`'s `"having different workflowID results in same Hash"` subtest: [4](#0-3)  — combined with `TestFetch`'s cache-hit-returns-stored-response behavior in the same file.

### 3.2 Caching Behavior

- **Cacheable Responses**: 2xx (success) and 4xx (client error) status codes.

- **Cache Invalidation**: Time-based expiration with periodic cleanup
- **Cache Strategy**: All cacheable responses are cached; Non-zero `CacheSettings.MaxAgeMs` determines whether to return a cached value or make a fresh request
