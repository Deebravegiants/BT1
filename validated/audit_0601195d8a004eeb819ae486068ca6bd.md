### Title
Webhook Shop-Domain Header Not Bound to HMAC Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw request body only, never incorporating the `shopify-shop-domain` (or `x-shopify-shop-domain`) header. `ShopifyAPI::Webhooks::Registry.process` relies on `Utils::HmacValidator.validate(request)` to authenticate the webhook, then trusts `request.shop`, taken straight from the header, to attribute the payload to a tenant when invoking the registered handler.

### Finding Description
The identity binding that should hold is:
`shop authenticated by HMAC == shop passed to handler`

In this gem it does not, because:
- `HmacValidator.validate` recomputes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field [4](#0-3) .
- For webhook requests, `to_signable_string` is simply `@raw_body` [1](#0-0) .
- `shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers that are never mixed into that signed string [2](#0-1) .
- `Registry.process` validates the HMAC and then immediately forwards `request.shop` (header value) to the handler as the tenant identity, with no secondary check that this shop matches the shop the HMAC/secret was actually issued for [3](#0-2) .

Because Shopify apps use a single, app-wide `client_secret` (not a per-shop secret) to sign all webhooks for all shops that installed the app, any body that legitimately produces a valid HMAC for one tenant produces the exact same valid HMAC for every tenant, since the signature depends only on body bytes and the shared secret — never on the shop. Any actor who can install the app on their own store (an "unprivileged internet user" from the app's perspective) receives genuine, validly-signed webhooks for topics whose bodies are static, predictable, or otherwise reproducible independent of shop identity (the test suite itself demonstrates this with an empty-body `"{}"` webhook payload producing a valid signature [5](#0-4) ). That attacker can capture the resulting `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `shopify-shop-domain` header for an arbitrary victim shop. `HmacValidator.validate` still returns `true` (the body/HMAC pair is genuinely valid), and `Registry.process` calls the handler with `shop: request.shop` set to the attacker-chosen victim shop [6](#0-5) .

### Impact Explanation
This breaks tenant isolation: the host application's webhook handler receives data it believes was authenticated as originating from Shop B, when it was actually forged by an attacker who only controls Shop A. Depending on how the host app's handler is written (which is the gem's documented extension point, `Handler#handle`, receiving `WebhookMetadata` with the spoofed `shop`), this can be leveraged for cross-tenant data confusion or to trigger shop-keyed side effects (e.g., cache invalidation, state changes, or session bookkeeping keyed by `shop`) attributed to a shop that never sent the event. This falls under the Critical "cross-tenant access" bucket because the root cause — an identity field asserted outside the cryptographic envelope — sits entirely inside this gem's `Webhooks::Request`/`Registry` code, not in host-application misuse.

### Likelihood Explanation
Exploitability requires only that the attacker be able to install the target app on their own Shopify store (a normal, unprivileged action any merchant can take) and know or predict a webhook body that Shopify will send them — trivially true for topics with empty or otherwise attacker-known bodies. No access token, `client_secret`, or privileged credential is required from the attacker's side; they only replay a webhook that Shopify itself already signed for them, aimed at a different shop's endpoint.

### Recommendation
Bind the shop identity (and ideally the other headers used for dispatch) into the HMAC-covered signable content, e.g. by including `shop`, `topic`, and `webhook_id` alongside the raw body in `to_signable_string`, or by independently verifying that the `shop` header corresponds to a shop with a known, active installation/session before dispatching to handlers, so that a valid HMAC for one shop cannot be replayed to spoof another.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, granting Shopify permission to send it webhooks signed with the app's single `client_secret`.
2. Shopify sends the attacker a genuine webhook whose body is static/predictable, e.g. `raw_body = "{}"`, with headers `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: <valid signature over "{}">` — mirroring the exact fixture used in the gem's own test suite [5](#0-4) .
3. Attacker replays this exact `raw_body` and `shopify-hmac-sha256` value to the app's webhook endpoint, but rewrites the `shopify-shop-domain` header to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the body against the shared secret [7](#0-6) .
5. The registered handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", ...)` [8](#0-7) , causing the host app to process an event as if it legitimately came from the victim shop.
