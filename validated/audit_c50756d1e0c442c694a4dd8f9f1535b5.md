### Title
Reentrancy in same-chain order cancellation via `withdraw()`'s post-transfer state finalization — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
In the Tron variant of `IntentGatewayV2.sol`, the same-chain cancellation path (`cancelOrder` → `withdraw`) sends native ETH/TRX and ERC-20 tokens to the order's `beneficiary` via raw low-level `.call` *before* the per-token escrow accounting is fully drained and while `_filled[commitment]` is set only once, using the entire loop's balance state rather than being finalized atomically ahead of the external calls in a strict checks-effects-interactions manner comparable to the already-fixed `IntrinsicIntents.sol`/`IntentsBase.sol` contracts used on standard EVM chains.

### Finding Description
The canonical, hardened `IntentsBase.sol._withdraw` (used by the mainline EVM `IntentGatewayV2`) sets `_filled[body.commitment] = beneficiary` at the very top of the function, before any external call, and the accompanying `IntrinsicIntentsReentrancyTest.sol` documents this exact CEI fix was needed after a prior vulnerability where `_filled` was only set inside `_withdraw(finalize=true)`, allowing an attacker to reenter `fillOrder`: [1](#0-0) 

The Tron contract's `withdraw()` function, however, performs the escrow decrement (`_orders[body.commitment][token] -= amount`) *after* the external `.call` transfer for each token, inside the same loop, for both native and ERC-20 assets: [2](#0-1) 

Although `_filled[body.commitment] = beneficiary` is set at the top of `withdraw()` (line 693) — which blocks a reentrant re-fill of the *same* order — the per-token escrow balance (`_orders[commitment][token]`) is only decremented *after* the token/native transfer completes. Since `withdraw()` iterates over `body.tokens` and calls out to arbitrary `token.call(...)`/`beneficiary.call{value}("")` for each entry before decrementing that entry's escrow, a malicious `beneficiary` contract (native-token case) or a malicious/hooked ERC-20 token can reenter mid-loop. Because the check `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` for a *given token slot* has not yet been zeroed out when the external call fires (it only becomes zero after the current iteration's decrement executes), a reentrant call into `cancelOrder` for the **same commitment but referencing a different token entry not yet processed**, or into `onGetResponse`/`onAccept` for the same commitment with different token lists, can drain a token's escrow balance multiple times before the loop's `-= amount` line executes, since `_filled` being non-zero only blocks re-invocation paths that check `_filled` up front (`cancelOrder`, `fillOrder`) but this contract's `withdraw` is also reachable via `onGetResponse` and `onAccept`, and there is no reentrancy guard (`nonReentrant`) protecting `withdraw` or the outer entry points at all.

Additionally, native-token and ERC-20 transfers in this file use raw low-level `.call` (not `safeTransfer`) with a boolean success check but no `nonReentrant` modifier anywhere in the contract, unlike the OpenZeppelin `ReentrancyGuard` usage pattern recommended by the report and unlike ecosystem best practice. Combined with the escrow decrement occurring after the transfer, this file structurally repeats the same class of bug the `IntrinsicIntentsReentrancyTest.sol` regression suite was written to prevent on the mainline contract.

### Impact Explanation
Successful exploitation drains escrowed user/solver funds (native TRX/ETH and ERC-20 tokens) held by the `IntentGatewayV2` Tron deployment beyond what is legitimately owed, resulting in direct, permanent loss of escrowed assets for other order participants — a Critical-severity theft-of-funds condition reachable from a single order cancellation/fill transaction by an unprivileged solver/beneficiary.

### Likelihood Explanation
The attack is triggerable by any user who can be designated as `order.user`/beneficiary of an order with multiple escrowed token entries (a normal, permissionless action via `placeOrder`), and then trigger `cancelOrder` (same-chain path) or has a bidding-eligible reentry via `onAccept`/`onGetResponse` for cross-chain redemptions, requiring only a malicious contract as the beneficiary/receiving token address — a realistic and low-cost setup requiring no privileged role.

### Recommendation
Apply the same checks-effects-interactions pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol._withdraw`: decrement `_orders[commitment][token]` (and any other relevant state) fully before performing any external call, and additionally add a `nonReentrant` guard (OpenZeppelin `ReentrancyGuard`) to `withdraw`, `cancelOrder`, `onAccept`, and `onGetResponse` in `evm/tron/contracts/apps/IntentGatewayV2.sol`, mirroring the mainline gateway's already-patched behavior and its reentrancy regression tests in `IntrinsicIntentsReentrancyTest.sol`.

### Proof of Concept
1. Attacker places an order (or is designated beneficiary of an order) with two escrowed input tokens: `TOKEN_A` (a malicious ERC-20 with a transfer hook, or the entry is native TRX) and `TOKEN_B` (a standard ERC-20), both escrowed under the same `commitment`.
2. Attacker triggers `cancelOrder` (same-chain path) with `beneficiary` set to a malicious contract.
3. `withdraw()` sets `_filled[commitment] = beneficiary` once, then begins the token loop: on the native/`TOKEN_A` iteration, the `.call{value: amount}("")` (or malicious token's `transfer` hook) reenters the gateway.
4. Because `_orders[commitment][TOKEN_A] -= amount` has not yet executed at the time of reentrancy, and `_filled` only prevents re-invoking the *outer* `cancelOrder`/`fillOrder` entry points (not a differently-shaped reentrant call path such as directly hitting `onGetResponse`/`onAccept` for the same commitment with a stale/duplicated `WithdrawalRequest`), the attacker can cause the escrow for `TOKEN_A` or `TOKEN_B` to be paid out more than once before the loop's decrement executes, exceeding the actual escrowed balance and draining the contract.     function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
