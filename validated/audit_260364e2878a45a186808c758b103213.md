## Title
Webhook shop/topic identity spoofing due to HMAC covering only the body, not the tenant-identifying headers — (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before dispatching a webhook to the app's handler, but the HMAC it checks only covers the raw request body. The tenant-identifying fields the gem hands to the handler — `shop`, `topic`, `webhook_id`, `api_version` — are read directly from unauthenticated HTTP headers and are never bound into the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` and compares it to the `hmac` header: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from headers that are *not* part of the signed string: [3](#0-2) 

`Registry.process` treats a passing HMAC check as authorization to trust these header-derived fields, and forwards `request.shop` (attacker-controlled header, not covered by the HMAC) straight into the handler's metadata: [4](#0-3) 

The binding the gem implicitly claims to enforce is:
`shop_the_HMAC_authenticates == shop_attributed_to_the_webhook`

but the actual binding enforced is only:
`body_bytes_signed_by_app_secret == body_bytes_received`

Because `api_secret_key` is shared across every shop that installs the app, any merchant who installs the app receives genuine Shopify webhooks for their own store with a valid HMAC over their own body content. Nothing in `Request` or `HmacValidator` ties that HMAC to the `shop-domain`, `topic`, or `webhook-id` headers. An attacker who controls one installed shop can therefore replay the exact `raw_body`/`hmac` pair they legitimately received while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a victim shop or a more sensitive topic (e.g. a mandatory GDPR/`app/uninstalled` topic). `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will happily hand the forged `shop`/`topic` to the host application's handler as if it had been verified — exactly the documented promise in `docs/usage/webhooks.md`: [5](#0-4) 

This is analogous to the reported bug class: a downstream consumer treats a check ("HMAC validated") as proof of an invariant ("this shop/topic is authentic") that the check never actually establishes — the field acted on (`shop`, `topic`) is not covered by the HMAC that gates trust.

### Impact Explanation
This breaks the tenant boundary the whole webhook subsystem is meant to enforce: `Registry.process` hands a `WebhookMetadata` whose `shop` field is attacker-controlled to the app's handler, enabling cross-tenant confusion/spoofing — an attacker-controlled shop can cause the host application to act on behalf of, or attribute state changes to, a different (victim) shop, or trigger a different topic's handler than the one that was actually signed. This maps to the "cross-tenant access" Critical impact category since the shop identity used by handlers for tenant/session lookup is not authenticated.

### Likelihood Explanation
Any actor who can install the app on a shop they control (self-serve installs are the norm for Shopify apps) can obtain a genuinely-signed webhook body/HMAC pair and then simply replay it to the app's public webhook endpoint with modified `x-shopify-shop-domain`/`x-shopify-topic` headers — no access token, `client_secret`, or privileged access is required.

### Recommendation
Include the tenant-identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the verified body, so that `HmacValidator.validate` actually authenticates the shop/topic attribution before `Registry.process` dispatches to a handler.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a real webhook, e.g. for `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker POSTs the same body `B` and same `hmac` header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally changes `x-shopify-topic` to a different registered topic).
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (required headers all present).
4. `Utils::HmacValidator.validate` returns `true` because it only recomputes the HMAC over `B`, which matches `H` — the shop/topic headers are never checked.
5. `Registry.process` dispatches to the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: <attacker-chosen-topic>, ...)`, and the host application acts on this forged shop attribution as if Shopify had verified it.
