### Title
Local enrollment bypass skips backend duplicate/fraud verification for `user_centric_signup` - (File: `src/plans/mod.rs`)

### Summary
When a scanned user QR-code resolves to `user_data.user_centric_signup == true` (and the orb's `ignore_user_centric_signups` config flag is not set), the signup-success branch in `do_signup` never calls the backend enrollment plan (`enroll_user::Plan::run`), which is the only code path that submits the signup to the backend and polls for backend-side duplicate/fraud verification. Instead, success is derived purely from the on-orb `signup_reason`, which — in this build — is essentially always `Normal` because all on-device fraud checks are stubbed out.

### Finding Description
In `src/plans/mod.rs`, `do_signup` computes `signup_reason` from the (no-op) local fraud pipeline: [1](#0-0) 

It then branches on the client/backend-reported flag `user_centric_signup`: [2](#0-1) 

If `user_centric_signup` is true, the code directly sets `debug_report.enrollment_status` from the locally computed `signup_reason` and treats the signup as successful without ever invoking `self.enroll_user(...)`. The `enroll_user` path is the only one that performs the backend round trip (`signup_post::request` + `signup_poll::request` polling), which is where the backend performs duplicate detection, inflight-match detection, and backend fraud checks: [3](#0-2) 

Meanwhile, the on-orb fraud detection that feeds `signup_reason` in this FOSS build is a stub that always returns `false` ("no fraud"): [4](#0-3) [5](#0-4) 

This mirrors the report's bug class: a critical verification/state-update step (`_checkpoint` in the original finding; here, the backend enrollment/fraud "checkpoint") is conditionally skipped based on an unrelated boolean flag, without ensuring the check still happens through another path.

### Impact Explanation
For any signup where the backend marks `user_centric_signup = true`, the orb reports the signup as successful and uploads the PCP without ever asking the backend to validate/deduplicate the identity via `signup_post`/`signup_poll`. Since local fraud checks are entirely disabled in this build, this effectively removes the only remaining anti-fraud/anti-duplicate gate for that signup path, allowing a misattributed or duplicate signup to be accepted as successful from the orb's perspective.

### Likelihood Explanation
Likelihood depends entirely on the backend response value `user_centric_signup` in `UserData`: [6](#0-5) 
and the orb-side config toggle `ignore_user_centric_signups`: [7](#0-6) 
The condition is reachable whenever the backend sets that flag for a given user/app, which appears to be an intended app-centric flow rather than an attacker-controlled input — so likelihood of a genuinely malicious trigger is uncertain without further backend context.

### Recommendation
Ensure the backend anti-fraud/duplicate "checkpoint" (the `enroll_user` call, or an equivalent lightweight backend verification call) is always executed regardless of the `user_centric_signup` branch, or explicitly document/verify that the backend independently re-validates user-centric signups out-of-band before treating them as final. At minimum, do not set `result.success = true` / `enrollment_status = Success` purely from local `signup_reason` without any backend round trip.

### Proof of Concept
1. Backend returns `UserData { user_centric_signup: true, .. }` for a scanned user QR code.
2. Orb config has `ignore_user_centric_signups = false` (default-ish).
3. Biometric pipeline succeeds (`pipeline.is_some()`), and `detect_fraud` always returns `false` (stubbed).
4. `signup_reason == SignupReason::Normal`.
5. In `do_signup`, the `if user_centric_signup && !ignore_user_centric_signups` branch sets `enrollment_status = Success` and `success = true` without any call to `signup_post::request`/`signup_poll::request`, i.e., without backend duplicate/fraud verification. [2](#0-1)
