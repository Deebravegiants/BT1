Webhook shop-domain identity is trusted from an unsigned HTTP header while the HMAC only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then reads the tenant identity (`shop`), `topic`, `webhook_id`, and `api_version` from HTTP headers that are never included in the signed material. The binding "HMAC-verified bytes == bytes the handler acts on" is broken: the signature proves the body wasn't tampered with, but says nothing about which shop, topic, or webhook the payload belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) .

`Registry.process` validates the HMAC and then immediately trusts `request.shop`/`request.topic`/`request.webhook_id`/`request.api_version` to construct the `WebhookMetadata` passed to the app's handler: [3](#0-2) .

The equality that should hold but doesn't: `HMAC-verified-bytes == identity-bytes-acted-on`. Here, `HMAC(secret, raw_body)` only certifies `raw_body`; it does not certify `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. Any party capable of relaying/replaying a validly-HMAC'd request body (e.g. a proxy, a webhook forwarding intermediary, or anyone able to influence headers on the path to the app, or replaying a previously observed legitimate payload with body content generic enough to fit another shop, such as `{}` in the mandatory `shop/redact` payload) can change the `shop-domain` header to point the payload at a different tenant, and the gem's validation code offers no protection because it never checks that the signed body content matches the claimed shop.

### Impact Explanation
Because the gem hands the (unauthenticated) `shop` value directly to the app's webhook handler as the trusted tenant identifier, cross-tenant confusion is possible for any downstream application that keys its processing off `data.shop`. For topics whose body doesn't inherently redundantly encode the acting shop (e.g., mandatory compliance webhooks `shop/redact`, `customers/redact`, `customers/data_request`, which can have generic/empty-ish bodies), an attacker who can influence or replay one HMAC-valid webhook delivery can effectively cause a handler to execute logic (e.g., data deletion, redaction) against a shop identity of their choosing while the gem still reports the HMAC as "valid." This matches the "cross-tenant access" impact category since the shop the app trusts and the shop whose data was actually signed/verified are not proven equal.

### Likelihood Explanation
This requires an attacker to have some ability to modify or replay HTTP headers between Shopify and the app (e.g., a misconfigured reverse proxy, a webhook-forwarding relay, load balancer normalization quirks, or a party that captured one valid HMAC'd delivery and can resend it with a different `shop-domain` header value) — it does not require the app's `api_secret_key`. It is a design gap in the library's own verification logic (`to_signable_string` excluding identity headers) rather than something the host app can fix by "following the docs" — the docs (`docs/usage/webhooks.md`) instruct developers to trust `data.shop` from the handler.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification (or otherwise cryptographically bind them), so that `Utils::HmacValidator.validate` fails if any of these fields are altered independently of the body.

### Proof of Concept
1. Attacker (or a compromised/misconfigured intermediary) captures a legitimate webhook delivery for `shop-a.myshopify.com` with topic `shop/redact` and body `{}` (mandatory topic bodies are minimal/generic), including its valid `x-shopify-hmac-sha256` header computed over `{}`.
2. Attacker resends the exact same body `{}` and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the HMAC only covers `{}` [4](#0-3) .
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop: "shop-b.myshopify.com"` and handed to the app's handler as an authenticated webhook for shop-b [5](#0-4) , even though shop-b never sent this webhook.
