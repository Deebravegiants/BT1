### Title
Legacy user QR-code format accepted without any cryptographic hash binding, enabling QR replay and misattributed signup - ([File: src/plans/qr_scan/user.rs])

### Summary
The Babylon report describes a bug class where a user-supplied identifier (`unbondingTxHash`) is trusted as a unique key without the service verifying that it actually corresponds to the data it claims to represent, letting an attacker plant another user's key and disrupt that user's legitimate operation. Orb-core's user-QR parsing has the same class of defect: the legacy QR-code format (`QR_CODE_V2` / `from_v2`) is accepted and used to drive a signup with **no cryptographic hash or signature binding it to the actual user data**, unlike the newer `decode_qr` format which carries a `user_data_hash` used to authenticate the backend-returned identity data.

### Finding Description
`Data::try_parse` in [1](#0-0)  attempts three parsing strategies in order: the modern `decode_qr` (which returns a `user_data_hash` used later to authenticate the identity data returned by the backend), the legacy `QR_CODE_V2` regex format (`from_v2`), and (behind a feature flag) the signup-extension format.

The legacy `from_v2` path builds a `Data` struct with `user_data_hash: None`, i.e., it carries **no hash or signature** at all: [2](#0-1) .

Downstream, `user_status::request` uses `qr_code.user_id` directly as the key sent to the backend to fetch identity/session status: [3](#0-2) . When the backend responds without `backend_keys`/`authenticated_app_data` (the "old QR-code format" branch), the orb only checks that `user_data_hash` wasn't unexpectedly present, then unconditionally accepts the session as valid and proceeds with signup using no `id_commitment` and no verification that the physical presenter of the QR code is the legitimate owner of that `user_id`: [4](#0-3) .

Because the plaintext QR payload (`userid:<uuid>:<data_policy>`) contains nothing but the bare identifier and is not bound by any hash/signature to the presenting device or biometric session (contrast with the `decode_qr`/`user_data.verify(user_data_hash)` path at [5](#0-4) ), anyone who captures or copies that QR content (e.g., photographing a victim's screen) can present it to a different orb and drive a full biometric signup under the victim's `user_id`, exactly mirroring the Babylon flaw where an unauthenticated user-supplied key is trusted to represent another party's legitimate record.

### Impact Explanation
A successful replay lets an attacker's iris/face biometrics be submitted and attributed to another person's `user_id`/session — a misattributed-signup scenario. Depending on backend session semantics, this can also consume/poison a legitimate user's pending session, preventing that user from completing their own signup with their own biometrics, analogous to the original bug where a legitimate unbonding request became unusable because the key was already occupied.

### Likelihood Explanation
Exploitation only requires capturing the plaintext QR content (no signature or hash) of a legacy-format QR code and presenting it to any orb before the victim does, or in parallel; the format itself provides no defense against replay since `user_data_hash` is always `None` for this code path. This is a low-effort attack requiring no privileged access, hardware tampering, or operator/node compromise.

### Recommendation
Deprecate/remove acceptance of the legacy hash-less `QR_CODE_V2` format in production, or require every accepted user QR code to carry a `user_data_hash` (or equivalent signature) that is cryptographically verified against backend-issued identity data before proceeding with a signup, exactly as already done for the modern `decode_qr` path (`user_data.verify(user_data_hash)`).

### Proof of Concept
1. Victim's app displays their legacy QR code `userid:<victim-uuid>:<data_policy>`.
2. Attacker photographs/copies this string.
3. Attacker approaches a (different) orb and presents the copied string as their own user QR-code.
4. `Data::try_parse` accepts it via `from_v2` with `user_data_hash: None`, so no hash check is ever performed in `user_status::request`'s old-format branch.
5. If the backend still reports the session as `valid` (e.g., session not yet consumed), the orb proceeds to run a full biometric signup, submitting the attacker's iris/face data tagged with the victim's `user_id`, or otherwise consuming/poisoning the victim's session before the victim can use it themselves.

        if let Ok((user_id, user_data_hash)) = decode_qr(code) {
            return Some(Self {
                user_id: user_id.hyphenated().to_string(),
                signup_extension: false,
                signup_extension_config: None,
                user_data_hash: Some(user_data_hash),
            });
        }
        if let Some(captures) = QR_CODE_V2.captures(code) {
            return Some(Data::from_v2(&captures));
        }
        #[cfg(feature = "internal-data-acquisition")]
        if let Some(captures) = QR_CODE_SIGNUP_EXTENSION.captures(code) {
            return Some(Data::from_signup_extension(&captures));
        }
        None
    }
