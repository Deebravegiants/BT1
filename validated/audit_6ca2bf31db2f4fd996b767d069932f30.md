### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and `Utils::HmacValidator.validate` is the only integrity check performed before a webhook is dispatched to an app's handler. However, `Request#to_signable_string` returns only `@raw_body`, so the HMAC binds solely to the webhook body. The `shop` field (`request.shop`, sourced from the `x-shopify-shop-domain`/`shopify-shop-domain` header) is read and forwarded into `WebhookMetadata` unauthenticated, even though it is the field the handler uses to determine *which tenant* the webhook data belongs to.

### Finding Description
`Webhooks::Registry.process` does: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the HMAC using `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` only returns the raw JSON body — the `shop`, `topic`, `webhook_id`, and `api_version` headers are excluded from the signed content: [3](#0-2) 

Yet `shop` (parsed straight from the `x-shopify-shop-domain` header, with zero format/domain validation) is exactly the attribute passed into `WebhookMetadata` and handed to the app's `WebhookHandler#handle`: [4](#0-3) [5](#0-4) 

This is the exact class of bug the report describes: an attacker-controlled binding is enforced on the wrong entity. The identity binding the gem should provide is:
`hmac == HMAC(secret, body || shop || topic || webhook_id)`
but the gem only verifies:
`hmac == HMAC(secret, body)`

Because the `shop` (tenant) identity is not part of the signed payload, any request carrying the same `body`/`hmac` pair that Shopify legitimately generated for one shop can be replayed with an arbitrary `x-shopify-shop-domain` header pointing to a different shop, and `Registry.process` will still accept it as valid — attributing the payload to the attacker-chosen tenant. By contrast, in this same codebase the OAuth `AuthQuery` does this correctly, including `shop` in the signed string: [6](#0-5) 
which highlights that the webhook path is the inconsistent, unprotected one.

### Impact Explanation
An unprivileged internet user who has network access to an app's public webhook endpoint (the intended, unauthenticated ingress point for Shopify webhooks) can obtain one valid `(body, hmac)` pair — trivially, by installing the app on their own store and capturing the webhook Shopify sends them — then replay that exact HTTP request to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. Because `Request#hmac` still validates (it only checks the body), `Registry.process` invokes the app's handler with `WebhookMetadata#shop` set to the victim's domain. Any app logic that uses `data.shop` to select the tenant record/session to act on (a documented, expected usage pattern for webhook handlers) will perform actions or store attacker-controlled data against the wrong tenant — i.e., cross-tenant data confusion/injection, achieved purely through this gem's failure to bind `shop` to the HMAC.

### Likelihood Explanation
Likelihood is credible but conditioned on typical usage: any unprivileged actor can become a legitimate installer of the target app (obtaining one authentic body/HMAC pair for their own shop) and can freely target the app's public webhook URL, which requires no credentials, secret, or elevated network position. The only requirement is that the app relies on `WebhookMetadata#shop` (as intended by the gem's own API) rather than independently re-deriving/verifying the shop, which is the documented and expected pattern.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the HMAC-signed content for webhooks, matching Shopify's actual signing scheme, or otherwise cryptographically bind the shop-domain header to the payload before exposing it via `WebhookMetadata`. At minimum, `Request#to_signable_string` should incorporate the shop-domain header (and other Shopify headers used as identity) so `HmacValidator.validate` covers every field the handler is permitted to trust.

### Proof of Concept
1. Attacker installs the app on their own development store `attacker-shop.myshopify.com` and registers a webhook subscription.
2. Shopify legitimately delivers a webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(secret, B)`.
3. Attacker replays the exact same request to the app's webhook endpoint but changes only the header:
   `x-shopify-shop-domain: victim-shop.myshopify.com`
4. `Webhooks::Request.new` parses headers, `HmacValidator.validate` recomputes `HMAC(secret, B)` (body unchanged) and it still matches `H`, since `to_signable_string` only returns `@raw_body`: [7](#0-6) 
5. `Registry.process` calls `handler.handle` with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)`, and the app processes attacker-controlled data as if it originated from `victim-shop`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
