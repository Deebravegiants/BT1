### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `request.shop` is read directly from the unsigned `X-Shopify-Shop-Domain` HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only and then hands `request.shop` straight to the app's handler as the trusted tenant identifier. Because the app's `client_secret` (used to compute the HMAC) is shared across every shop that has installed the app, any merchant who installs the app can capture one of their own legitimately-signed webhook deliveries and replay it to the app's webhook endpoint with the `shop-domain` header swapped to a victim shop, producing a request that still passes HMAC validation but is attributed to the wrong tenant.

### Finding Description
The identity binding that should hold is:
`shop_the_HMAC_authenticates == shop_the_handler_acts_on`

In this gem that equality is broken:
- `to_signable_string` only returns `@raw_body`: [1](#0-0) 
- `shop` is read from the `shop-domain` header, entirely outside the signed material: [2](#0-1) 
- `Registry.process` validates only `Utils::HmacValidator.validate(request)` (which validates `to_signable_string`, i.e., the body) and then immediately trusts `request.shop` when constructing `WebhookMetadata` passed to the app's handler: [3](#0-2) 
- `HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, so it never incorporates the shop header: [4](#0-3) 

Because the `api_secret_key` used to sign webhooks is a single per-app secret (not per-shop/per-tenant), a webhook body+HMAC pair that is valid for shop A's install of the app is *also* valid for shop B's install, since the signature never binds to the shop. An attacker who installs the target app on their own store (an ordinary, unprivileged action available to any merchant) receives real, validly-signed webhooks for their own shop. They can then replay that exact `raw_body`/HMAC pair to the app's webhook callback URL while substituting `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) with a victim shop's domain. `Registry.process` will accept it as authentic and deliver `WebhookMetadata` with `shop: <victim-shop>` to the app's handler.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook consumers: the handler receives forged data falsely attributed to a shop the attacker doesn't own or operate. Depending on how the host app uses `data.shop` (e.g., to look up/update per-shop records, sync inventory, or trigger per-tenant side effects), this enables cross-tenant data injection/corruption using another merchant's identity, without possessing that merchant's credentials — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any consumer relying on this gem's documented webhook flow (`ShopifyAPI::Webhooks::Registry.process` + `ShopifyAPI::Webhooks::Request`) as shown in the gem's own docs. Any user who can install the app (a normal, unprivileged flow for a public/multi-tenant app) can capture one authentic signed webhook and replay it with a different `shop-domain` header value; no secret material, privileged access, or the app's own `client_secret` need be known to the attacker.

### Recommendation
Bind the shop identity into the signed material used for HMAC verification, or otherwise cryptographically tie the `shop-domain` header to the payload before trusting it — e.g., include the shop domain (and/or webhook id) in `to_signable_string`, or require the caller to independently verify that `request.shop` corresponds to a shop with an active, known installation/session before acting on webhook data.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger any subscribed webhook topic and capture the raw POST: headers `X-Shopify-Hmac-Sha256`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic`, and the raw body.
2. Replay the identical raw body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (the raw body only) using the shared `Context.api_secret_key` — this matches, since the body/HMAC pair is unchanged. [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)`, i.e., `shop: "victim.myshopify.com"`, even though the request was never sent by Shopify on behalf of that shop. [6](#0-5)
