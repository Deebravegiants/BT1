### Title
Webhook `shop-domain` header is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers with no cryptographic tie to that signature [2](#0-1) . `Registry.process` validates only the body's HMAC and then hands the unauthenticated `shop` header straight to the app's webhook handler as the tenant identity [3](#0-2) .

### Finding Description
The identity binding that should hold is: `HMAC-authenticated content == shop identity acted upon`. Here it doesn't. `HmacValidator.validate` computes `HMAC(api_secret_key, raw_body)` and compares it to the `hmac-sha256`/`x-shopify-hmac-sha256` header [4](#0-3) . Since the signature covers only the JSON body bytes, any request with a raw body/HMAC pair that is valid for the shared `api_secret_key` will pass validation *regardless of what shop-domain header accompanies it*. `Registry.process` then trusts `request.shop` (taken from the `shopify-shop-domain`/`x-shopify-shop-domain` header) as the authenticated tenant and forwards it, unmodified, to the registered `WebhookHandler#handle` via `WebhookMetadata#shop` [5](#0-4) . The library's own documentation instructs apps to key business logic off `data.shop` (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), reinforcing that host apps rely on this value as the trusted tenant identifier [6](#0-5) .

Because the `api_secret_key` is shared by the app across every merchant/shop that installs it (it is not per-tenant), any merchant who has installed the app can capture a genuine, validly-signed webhook body from their own store (e.g. by triggering `orders/create`) and replay that exact `raw_body` + `hmac-sha256` header pair to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. The HMAC check still succeeds because the header is not part of the signed content, and the handler executes believing the payload originated from the victim tenant.

### Impact Explanation
This breaks tenant isolation: an attacker who is merely another (unprivileged, non-victim) merchant using the same app can make the app process arbitrary attacker-supplied JSON under a victim shop's identity. Depending on how the host app's `WebhookHandler#handle` uses `data.shop` (e.g., to look up per-shop records, trigger mandatory GDPR webhook processing such as `customers/redact`/`shop/redact`, or update shop-scoped state), this results in cross-tenant access/action — data intended to be scoped to one merchant can be attributed to, or made to affect, a different merchant's tenant context.

### Likelihood Explanation
Any user who can install the app on their own store (an ordinary Shopify merchant, i.e., an "unprivileged internet user" relative to other tenants of the same app) can generate a valid body/HMAC pair without ever needing the app's `client_secret`/`api_secret_key` in plaintext — they just need to receive one legitimate webhook from Shopify to their own shop and replay its body+signature with a forged `shop-domain` header. No credential theft, TLS interception, or privileged access is required.

### Recommendation
Include the shop/topic/webhook identity in the signed content Shopify computes (not possible to change server-side, since Shopify's HMAC header format is fixed to sign only the body), or — more practically — cross-check the `shop-domain` header against a shop the app has actually installed/has an active session/access token for before trusting it, and avoid using the raw header value for authorization-sensitive actions. At minimum, document prominently that `WebhookMetadata#shop` is not itself an authenticated value and that host applications must independently verify the shop is one with a currently valid, stored access token/session before acting on webhook data for that shop.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged merchant action).
2. Attacker triggers a webhook (e.g. updates a product) and captures the raw POST body and `x-shopify-hmac-sha256` header Shopify sent — this is a validly-signed pair for the app's shared `api_secret_key`.
3. Attacker resends the identical raw body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` succeeds at `lib/shopify_api/webhooks/registry.rb:190` because it only checks `HMAC(secret, raw_body)`, which is unchanged. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, so the app processes attacker-controlled data as if it belongs to `victim-shop.myshopify.com`.
