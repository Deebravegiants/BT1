### Title
POA bridge `describeWithdrawal` conflates multiple same-asset withdrawals in one transaction, misreporting completion status/hash - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain status of a specific withdrawal (identified by `WithdrawalIdentifier.index`) by calling `findMatchingWithdrawal`, which matches purely on `assetId`, ignoring `index`, `destinationAddress`, and `amount`. When a single NEAR intent transaction contains more than one withdrawal of the same asset (a supported scenario per `createWithdrawalIdentifiers` / `createWithdrawalCompletionPromises`, which assigns each withdrawal a distinct `index`), every one of those withdrawals resolves to the *same* matched record from the POA API response.

### Finding Description
`findMatchingWithdrawal` in [1](#0-0)  selects the first withdrawal in the API response whose `near_token_id` matches the requested `assetId`, with no distinction by `index`/destination/amount. `describeWithdrawal` at [2](#0-1)  uses that single match to report `status`/`txHash` for the withdrawal identified by `args`. The comment in the code even acknowledges the limitation explicitly: "multiple withdrawals of the same token in a single transaction are not supported."

However, the SDK's withdrawal-orchestration layer does support batching multiple withdrawals — including same-asset withdrawals — from one NEAR transaction, assigning each a unique `index` per bridge route in `createWithdrawalIdentifiers` ( [3](#0-2) ) and polling each independently via `createWithdrawalCompletionPromises` ( [4](#0-3) ). This creates a mismatch: the orchestration layer treats each same-asset withdrawal as a distinct entity to be independently confirmed, while the POA bridge's status lookup cannot actually distinguish between them.

The equality broken is: *the status/txHash reported for withdrawal index N* should equal *the on-chain outcome of withdrawal index N specifically*, but instead it equals *the on-chain outcome of whichever same-asset withdrawal happens to appear first in the API response* (index 0, regardless of which index/destination was actually queried).

### Impact Explanation
If a user or integrator issues two withdrawals of the same asset in a single batched transaction to two different destination addresses (e.g., withdrawal index 0 → address A, index 1 → address B), `watchWithdrawal`/`waitForWithdrawalCompletion` for index 1 will report `completed` with the `transfer_tx_hash` that actually belongs to withdrawal index 0's transfer to address A, as soon as index 0 completes — even if the withdrawal to address B is still pending, failed, or hasn't even been processed by the relayer yet. An integrator relying on this status to credit/confirm delivery for the second withdrawal would incorrectly believe funds were delivered to address B (or would double-count/misattribute a single destination transfer as fulfilling two distinct withdrawal obligations), matching the "status or hash misreport making an integrator credit or refund twice" impact category (High).

### Likelihood Explanation
Requires a user/integrator to submit ≥2 POA-bridge withdrawals of the same underlying asset within a single NEAR intent transaction — a state reachable purely through normal SDK usage (`createWithdrawalIdentifiers` explicitly supports and indexes multiple withdrawals per bridge route), with no malicious actor or privileged party needed. The trigger is a common batching pattern (e.g., splitting one logical withdrawal into two destinations, or a user submitting two withdrawal intents together), making likelihood moderate-to-high for integrators that batch withdrawals.

### Recommendation
Disambiguate `findMatchingWithdrawal` by more than `assetId` alone — for example, sort/match candidates by `(assetId, amount, destinationAddress)` in a stable, index-consistent order relative to the requested withdrawals, or (preferably) have the POA bridge API return the withdrawal identifier submitted by the caller so status lookups can bind to the exact withdrawal (mirroring the pattern used by HOT bridge, which binds by `nonce` derived per `index`). At minimum, until API support exists, `describeWithdrawal` should refuse to report `completed` when more than one same-asset withdrawal is outstanding for the same tx/index set, rather than silently returning another withdrawal's result.

### Proof of Concept
1. User submits one NEAR transaction containing two POA-bridge withdrawal intents for the same `assetId` (e.g., `nep141:btc.omft.near`): index 0 → destination A (amount 100000), index 1 → destination B (amount 200000).
2. `createWithdrawalIdentifiers` assigns `index: 0` and `index: 1` for the two `WithdrawalIdentifier`s under `RouteEnum.PoaBridge` ( [5](#0-4) ).
3. The POA relayer completes withdrawal 0 first (to destination A) and the API's `getWithdrawalStatus` response contains one `COMPLETED` entry with `near_token_id: "btc.omft.near"` and `transfer_tx_hash: "hashA"`; withdrawal 1 (to destination B) is still `PENDING` or not yet indexed.
4. Caller polls `describeWithdrawal` for the `WithdrawalIdentifier` with `index: 1` (destination B). `findMatchingWithdrawal` ( [1](#0-0) ) matches on `assetId` alone, finds the `COMPLETED` record for destination A's transfer, and `describeWithdrawal` returns `{ status: "completed", txHash: "hashA" }` — even though the withdrawal to destination B never completed.
5. An integrator watching withdrawal index 1 via `watchWithdrawal`/`waitForWithdrawalCompletion` incorrectly concludes destination B received funds and credits accordingly, while the actual `hashA` transfer only ever went to destination A.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
