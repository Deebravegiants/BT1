### Title
Reentrancy in Tron IntentGatewayV2 `withdraw()` allows draining escrowed funds via external transfer before state update - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron deployment of `IntentGatewayV2` performs the token/native transfer to the beneficiary *before* decrementing the `_orders[commitment][token]` escrow accounting, violating the checks-effects-interactions pattern that the canonical EVM version (`evm/src/apps/intentsv2/IntentsBase.sol`) correctly follows. This mirrors the class of bug behind the Terraport incident: a contract path that lets an external call reach out (and potentially re-enter) before internal balance/liquidity accounting is settled, letting an attacker extract more value than they are entitled to.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` is reached from `onAccept()` (for `RedeemEscrow`/`RefundEscrow` requests delivered via ISMP) and from `onGetResponse()` (for source-chain cancellation after a destination storage proof). Its body: [1](#0-0) 

only checks that `_orders[body.commitment][token] != 0` (non-zero), then performs the raw `.call` transfer of `amount` to `beneficiary` for either native token or ERC20 (using low-level `.call` rather than `SafeERC20`), and only *afterwards* subtracts `amount` from `_orders[body.commitment][token]`.

Contrast this with the canonical EVM implementation in `IntentsBase._withdraw`, which decrements escrow *before* transferring: [2](#0-1) 

Because the Tron variant transfers first, a beneficiary that is a contract (or a malicious/ERC777-style token with transfer hooks) can re-enter the gateway during the `.call`. Since the escrow decrement for that `(commitment, token)` pair has not yet been applied, a nested call path that reaches `withdraw()` again for the same commitment (e.g., another `RedeemEscrow`/`RefundEscrow` delivery, or an `onGetResponse` cancellation proof processed in the same call context) would still see the pre-decrement escrow balance and pay out again, draining more than what was actually escrowed for that order — analogous to Terraport's liquidity being emptied through a flawed contract accounting path. Neither `onAccept` nor `withdraw`/`onGetResponse` carry a `nonReentrant` guard in this file, unlike other gateway paths (e.g., `placeOrder` uses `nonReentrant` in the EVM version).

### Impact Explanation
This is a High-severity bug class: unauthorized/duplicated withdrawal of escrowed user funds directly maps to "concrete theft ... of funds" from the Intent Gateway's escrow, reachable by a single relayed ISMP message (`RedeemEscrow`/`RefundEscrow`) or GET-response delivery — exactly the reachable-by-unprivileged-relayer criteria in scope. If exploitable, it can drain escrowed liquidity for in-flight orders on the Tron deployment, paralleling the Terraport LUNC/USTC/TERRA liquidity drain caused by a flawed contract-level fund-release path.

### Likelihood Explanation
Likelihood depends on whether a reentrant call path actually exists back into `withdraw()`/`onAccept()`/`onGetResponse()` from within the external `.call`/ERC20 transfer — these are gated by `onlyHost`, so a directly attacker-controlled reentrant call would need the host itself to be re-entered and dispatch a second accepted request in the same transaction, or the ERC20 token used for escrow to have transfer callbacks that route back into the gateway (unlikely for standard ERC20/TRC20, but the code accepts arbitrary escrowed tokens). I could not fully confirm an end-to-end reentrant call graph through the `HyperApp`/host contract within the available tool iterations, so this should be validated by tracing `onlyHost`'s implementation and the ISMP host's message-processing loop for TRON to see if nested `onAccept` calls are possible within one external call. Given the missing CEI ordering and missing reentrancy guard regardless of confirmed reachability, this is at minimum a definite code-quality/security regression relative to the audited EVM contract, and a real risk if any escrowed token or native-transfer path allows re-entry.

### Recommendation
- Apply checks-effects-interactions in `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `withdraw()`: decrement `_orders[body.commitment][token]` by `amount` before performing the native/ERC20 transfer, matching `IntentsBase._withdraw`.
- Add a `nonReentrant` guard to `onAccept` and `onGetResponse` (or to `withdraw` itself) for defense in depth.
- Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern with `SafeERC20.safeTransfer` for consistency and correctness with non-standard/fee-on-transfer TRC20 tokens.
- Add a Foundry test that attempts reentrant withdrawal via a malicious beneficiary contract/token during `withdraw()` to confirm the fix closes any real reentrancy window.

### Proof of Concept
Conceptual PoC (requires confirming a reentrant call path into `onAccept`/`onGetResponse` is reachable in the Tron host implementation, which was not verified in this pass):
1. Attacker escrows tokens via `placeOrder`, becomes both order beneficiary and a malicious contract.
2. Attacker arranges for two independent `RedeemEscrow`/`RefundEscrow` deliveries (or a `RedeemEscrow` delivery plus a `RefundEscrow`/cancellation `onGetResponse`) referencing the same `commitment`/`token`, timed so that the second is processed as a nested call triggered from the malicious beneficiary's fallback/receive hook during the first `withdraw()`'s external transfer, i.e., before `_orders[commitment][token] -= amount` executes.
3. Both deliveries pass the `_orders[commitment][token] != 0` check because the decrement from the first delivery hasn't yet applied, so the attacker receives `amount` twice for a single escrowed balance, draining the gateway of tokens beyond what was actually deposited for that order. [3](#0-2)

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
