**The claimed divergence does not exist.** Both call sites compute `actualAmount` with the identical formula:

`packages/intents-sdk/src/sdk.ts` `createWithdrawalIntents`: [1](#0-0) 

`packages/intents-sdk/src/sdk.ts` `_estimateWithdrawalFee`: [2](#0-1) 

Both use `feeInclusive ? amount - fee.amount : amount` — for `feeInclusive: false` (the scenario in the question), **no fee subtraction happens in either function**. `actualAmount` equals the raw `amount` in both places, so the min-withdrawal check inside `PoaBridge.validateWithdrawal` (`args.amount < minWithdrawalAmount`) is evaluated against the exact same value in both entrypoints: [3](#0-2) 

The premise "amount above the token's `min_withdrawal_amount` but below it after fee subtraction" cannot occur for `feeInclusive: false`, since there is no fee subtraction in that branch anywhere in the code.

**On the fee-added-back-on-top mechanism**: `PoaBridge.createWithdrawalIntents` adds `relayerFee` on top of `actualAmount` to form the signed `ft_withdraw` amount: [4](#0-3) 

For `feeInclusive: false`, this yields signed `amount = amount + relayerFee`, i.e., `sum(debits) == amount + fee`, and the destination receives `amount` (the relayer keeps the added fee). Both sides of the invariant hold: `sum(debits) == amount + (feeInclusive ? 0 : fee)` and `destination receives amount - (feeInclusive ? fee : 0)`.

**On the missing `FeeExceedsAmountError` guard in `createWithdrawalIntents`** (only present in `_estimateWithdrawalFee`, `packages/intents-sdk/src/sdk.ts` lines 421-425): this only matters for `feeInclusive: true` with `amount <= fee.amount`. In that case `actualAmount` underflows to a negative BigInt, but `validateWithdrawal`'s min check (`args.amount < minWithdrawalAmount`) still catches it and throws `MinWithdrawalAmountError` before any signing occurs, since a negative amount is always less than any positive minimum: [5](#0-4) 

So no unchecked negative/underflowed amount reaches `bridge.createWithdrawalIntents` for signing.
