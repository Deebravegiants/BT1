### Title
Cross-seed public key cache collision in `MemoizedKeychain` due to missing `seedId` in cache key - (File: `features/keychain/module/memoized-keychain.js`)

### Summary
`MemoizedKeychain` caches exported public key/xpub data using only `stableStringify(keyId)` as the cache key, without including `seedId` in the derived cache key. In a multi-seed wallet where two different seeds share a structurally identical `keyId` (same `derivationPath`/`keyType`/`derivationAlgorithm`/`assetName`), `exportKey` for the second seed will incorrectly return the first seed's cached public key data.

### Finding Description
The cache key is computed as: [1](#0-0) 

and used in both read and write paths without any seed-scoping: [2](#0-1) 

The public `exportKey` method only checks `opts?.exportPrivate` before consulting the cache, and looks up/stores using `keyId` alone — `opts.seedId` (which is passed alongside `keyId` per the `Keychain.exportKey(keyId, opts)` contract, as seen in `cached-sodium-encryptor.ts`'s `keychain.exportKey({ keyId, seedId, exportPrivate })` call) is never incorporated: [3](#0-2) 

A `KeyIdentifier` object itself carries no `seedId` field — its identity is `keyType`/`derivationAlgorithm`/`derivationPath`/`assetName` only, as confirmed by `getCacheKey` in the sibling `cached-sodium-encryptor` feature which explicitly concatenates `seedId` together with those `KeyIdentifier` fields specifically *because* the identifier alone is not seed-unique: [4](#0-3) 

This shows the codebase itself recognizes that `keyId` fields alone are insufficient to scope a cache key across seeds — that pattern was correctly applied in `cached-sodium-encryptor` but not in `MemoizedKeychain`, which is the canonical `keychain` module implementation wired into the IOC container: [5](#0-4) 

Consequently, for a wallet supporting multiple seeds (e.g., after importing a second seed, both producing identical derivation-path conventions for the same asset/account index — a very common occurrence since standard derivation paths like `m/44'/0'/0'` are identical across seeds), calling `exportKey(keyId, { seedId: A })` populates `#publicKeys[stableStringify(keyId)]`, and a subsequent `exportKey(keyId, { seedId: B })` for a *different* seed will hit that same cache entry and silently return seed A's `xpub`/`publicKey` data for seed B.

### Impact Explanation
This causes cross-seed/cross-account state confusion: an unprivileged caller (dapp/API/internal feature) requesting the public key or xpub for seed B's wallet account can receive seed A's public key material instead. This can lead to wrong address exposure/display, incorrect fund destination for receive flows, and broken account isolation — an origin-agnostic wallet-integrity defect that maps to Hydra's "wrong-account access / storage integrity" impact category.

### Likelihood Explanation
Requires a multi-seed wallet (a supported and increasingly common configuration, e.g. via seed import features) where two seeds happen to produce a `keyId` with identical `derivationPath`/`keyType`/`derivationAlgorithm`/`assetName` — which is the normal case for identical account indices under a shared derivation standard (e.g., both seeds deriving `m/44'/0'/0'` for bitcoin). No privilege is needed beyond triggering ordinary `exportKey` calls (public-key-only, non-private export) for two seedIds, which is a normal, unprivileged wallet operation (address/xpub derivation). This is deterministic and fully repeatable.

### Recommendation
Include `seedId` (from `opts.seedId`) as part of the cache key in `#getCachedKey`/`#setCachedKey`, e.g. `keyIdToCacheKey({ seedId, keyId })` similar to the approach already used in `getCacheKey` of `features/cached-sodium-encryptor/module/cache.ts`, ensuring cache entries are strictly scoped per seed.

### Proof of Concept
Integration test in `features/keychain/module/__tests__/`:
1. Instantiate `MemoizedKeychain` with in-memory storage.
2. Add two seeds, `seedA` and `seedB`, with different underlying entropy but the wallet configured such that both derive a `KeyIdentifier` with the same `derivationPath`/`keyType`/`derivationAlgorithm`/`assetName` (e.g., `m/44'/0'/0'`, secp256k1, bitcoin).
3. Call `exportKey(keyId, { seedId: seedA })` — capture `xpub`/`publicKey` A.
4. Call `exportKey(keyId, { seedId: seedB })` — capture returned `xpub`/`publicKey`.
5. Assert `xpubB !== xpubA` and `publicKeyB !== publicKeyA` (derive expected values via `super.exportKey` bypass or a plain `Keychain` instance for comparison).
6. Expected (buggy) result: the assertion fails because the cached entry for seedA is returned for seedB, demonstrating the cross-seed collision.

export const getCacheKey = ({ keyId, seedId }: CacheParams) => {
  const components = [
    seedId,
    keyId.keyType,
    keyId.derivationAlgorithm,
    keyId.derivationPath,
    keyId.assetName,
  ]

  return components
    .filter(Boolean)
    .map((component) => encodeURIComponent(component!))
    .join('/')
}
