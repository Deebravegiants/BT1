## Custody Analog Found: Reserve-Balance Donation Manipulates LP Minting in `swap::liquidity_pool`

### Title
Live fungible-store balance used as AMM reserve enables donation-based LP share dilution/theft in `liquidity_pool::mint` - (File: `aptos-move/move-examples/swap/sources/liquidity_pool.move`)

### Summary
The external report's root custody invariant is: *a permissionless, direct transfer into a custody-tracking pool can inflate the pool's perceived value/price-per-share independent of legitimate deposit accounting, and downstream logic that computes shares/health from that live, manipulable value gets corrupted.* The Aptos-native analog exists in the `swap` move-example's `liquidity_pool::mint` function, which computes LP-token issuance directly from the live `fungible_asset::balance()` of the pool's reserve stores rather than from an internally-tracked, deposit-gated reserve variable.

### Finding Description
In `liquidity_pool.move`, `mint()` reads reserves directly from the store objects: [1](#0-0) 

```
let reserve_1 = fungible_asset::balance(store_1);
let reserve_2 = fungible_asset::balance(store_2);
...
let token_1_liquidity = math64::mul_div(amount_1, (lp_token_supply as u64), reserve_1);
let token_2_liquidity = math64::mul_div(amount_2, (lp_token_supply as u64), reserve_2);
```

`fungible_asset::deposit`/`unchecked_deposit` in the framework is permissionless — any signer can deposit `FungibleAsset` into any known `Object<FungibleStore>` address without being the store owner (confirmed via `dispatchable_fungible_asset::deposit` and `fungible_asset::deposit_sanity_check` flows, which check store validity, not caller identity). This mirrors the "direct transfer of funds to the Controller inflates share price" primitive from the external report — except here the corrupted value is `reserve_1`/`reserve_2`, and the custody boundary broken is: LP token issuance should reflect *only* value actually paid in exchange for shares, not incidental balance changes.

Because `store_1`/`store_2` addresses are public (they are fields of the `LiquidityPair`/pool object, discoverable on-chain), an attacker can front-run a victim's `mint()` call by directly depositing extra fungible assets into `store_1` (or `store_2`) just before the victim's transaction executes. This inflates `reserve_1` read at mint time without increasing `lp_token_supply`, so `token_1_liquidity = amount_1 * lp_token_supply / reserve_1` rounds down for the victim — the victim's deposit still increases the pool's real balance, but they receive disproportionately fewer LP shares than the pool's constant-product accounting implies. The donated value plus the under-minted differential accrues to existing LP-share holders (i.e., the attacker, if they already hold LP shares or immediately mint a large LP position right after the victim, capturing the inflated reserve pro-rata).

This is structurally identical to the reported bug class: a permissionless external balance mutation is fed directly into a share-price/health calculation that assumes the balance only changes through gated, share-issuing paths — exactly the `pricePerShare()`/`balanceOf()` anti-pattern the original report calls out and recommends avoiding.

### Impact Explanation
This allows an attacker to systematically dilute other liquidity providers' custody claim on pooled fungible assets (APT/FA reserves held in `store_1`/`store_2` `FungibleStore` objects) by sandwiching `mint()` calls with direct store deposits, extracting value from victim depositors into their own LP position. This is a supply/custody accounting corruption that moves value to the wrong holder, matching the "Custody Impact Gate" criteria (asset/ownership control corruption tied to fungible-asset token objects). Because `liquidity_pool` is a reusable move-example pattern (also duplicated verbatim in `testsuite/benchmark-workloads/.../liquidity_pool.move`), any protocol instantiating it — including the `bonding_curve_launchpad`'s graduation flow, which creates real pools on this exact `swap` module — inherits the flaw with live mainnet-relevant funds.

### Likelihood Explanation
Likelihood is high wherever this pattern is deployed with real value: the donation is a single permissionless `fungible_asset::deposit` call requiring no special privilege, and sandwiching/front-running a `mint()` transaction is standard MEV behavior on Aptos (transactions are visible pre-execution to block proposers/searchers). No oracle, governance, or privileged assumption is needed — it is a direct, unprivileged root cause in `mint()`'s reserve computation.

### Recommendation
Do not source AMM reserves from the live `fungible_asset::balance()` of the pool's stores at mint/swap time. Instead, maintain internally-tracked reserve fields (as `bonding_curve_launchpad::liquidity_pairs::LiquidityPair.fa_reserves`/`apt_reserves` already correctly do) that are updated only inside gated mint/swap/burn logic, and reconcile any excess store balance (donations) into the pool via an explicit, permissioned `sync()`/`skim()` function that mints/attributes value fairly rather than implicitly during a victim's `mint()` calculation.

### Proof of Concept
1. Attacker observes a pending `liquidity_pool::mint(victim, fa_1, fa_2, is_stable)` transaction in the mempool for an existing pool with `lp_token_supply > 0`.
2. Attacker submits (and gets ordered before the victim's tx) a plain `fungible_asset::deposit(store_1, donated_fa)` transferring extra token_1 directly into the pool's `store_1`, without calling `mint()`.
3. Victim's `mint()` executes: `reserve_1 = fungible_asset::balance(store_1)` now includes the attacker's donation, inflating `reserve_1`. `token_1_liquidity = amount_1 * lp_token_supply / reserve_1` computes a lower LP amount than the fair-market-value ratio would allow.
4. Attacker then calls `mint()` themselves with a matching deposit, receiving LP shares priced against the now-diluted-for-victim, attacker-inflated reserve — capturing a share of both the victim's underpriced deposit and their own earlier donation.

*Note: I could not fully trace whether `fungible_asset::deposit`'s sanity check in this codebase version enforces any store-frozen/owner restriction beyond metadata dispatch checks (the `unchecked_deposit` implementation body itself was not retrievable via the index in the final iteration) — this should be verified in a live session before treating the PoC as fully confirmed, since the index has size limits and some file contents (e.g., the exact body of `fungible_asset::unchecked_deposit`) may not be available. A Devin session with full repo access would be needed to confirm the exact deposit-authorization semantics and finalize a runnable Move test.*
