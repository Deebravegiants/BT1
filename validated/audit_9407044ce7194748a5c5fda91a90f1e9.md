### Title
A single failing `IsmpModule::on_accept`/`on_response`/`on_timeout` invalidates and drops an entire batch of unrelated messages - ([File: modules/pallets/ismp/src/impls.rs])

### Summary
`pallet-ismp`'s message-execution pipeline aggregates the per-request dispatch results of an entire `handle_unsigned` batch into a single `Result`, so that one destination module rejecting its own request (a normal, expected outcome per the ISMP design docs) causes the whole batch — including all other unrelated, valid requests bundled in the same call — to be treated as an invalid message and dropped, both in the transaction-pool validation path and in the on-chain dispatch path.

### Finding Description
`Pallet::<T>::execute` dispatches every `Message` in the batch via `handle_incoming_message`, then flattens all per-request events from every message and calls `.collect::<Result<Vec<_>, _>>()` on them: [1](#0-0) 

Because `.collect::<Result<Vec<_>, _>>()` short-circuits to `Err` on the *first* error it encounters, a single failing request anywhere in the batch turns the whole `execute()` call into `Err(Error::<T>::InvalidMessage)` — discarding the events (and, since the call is `#[frame_support::transactional]`, reverting the storage side effects) produced by every *other* successfully-processed message in the same batch: [2](#0-1) 

Per the protocol's own documentation, a destination module returning an error from `on_accept` (e.g. because it wants the request to time out and be replayed, or because the payload is invalid for that particular module) is an expected, non-exceptional outcome: [3](#0-2) 

The `handlers::request::handle` function reflects this by collecting per-request results into a `Vec<Result<Event, Error>>` rather than short-circuiting at the per-message level: [4](#0-3) 

However `execute()` re-introduces short-circuiting at the *batch* level. This same aggregated result feeds `ValidateUnsigned::validate_unsigned`, which maps any `Err` from `execute()` directly to `InvalidTransaction::BadProof`, causing the transaction pool to reject the entire unsigned extrinsic: [5](#0-4) 

This is the direct analog of the reported CrossL2Inbox issue: a destination application ("any contract/module with flow-control privileges") can, simply by returning an error from its own `on_accept`/`on_response`/`on_timeout` callback for a request addressed to it, cause the Supervisor-equivalent (the runtime's message-validity check) to mark the *entire* transaction as invalid and exclude it from block inclusion — even though that error only concerns one request and was never intended to invalidate the rest of the batch. Any application module (even an honestly-implemented one that legitimately rejects malformed or business-logic-invalid payloads) becomes an involuntary DoS vector against every other message a relayer happens to batch alongside it.

### Impact Explanation
A relayer that batches multiple independent requests/responses/timeouts (destined for different applications/users) into one `handle_unsigned` call loses all of them if just one is rejected by its destination module. In the mempool this manifests as outright rejection (`InvalidTransaction::BadProof`) of the whole extrinsic; on-chain, the `#[frame_support::transactional]` dispatch reverts all state changes for the batch. This blocks delivery of otherwise-valid, unrelated cross-chain messages — a "route unable to deliver messages" condition — until the relayer manually identifies and excludes the offending message, which itself may be adversarially and repeatedly recreated by an attacker who controls (or can force failure in) a destination module.

### Likelihood Explanation
No privileged access is required. Any account can dispatch a `PostRequest`/`GetResponse` targeting a module whose `on_accept`/`on_response`/`on_timeout` implementation returns an error under attacker-chosen conditions (a very common pattern, since the design docs explicitly endorse modules returning `Err` to trigger timeout/replay semantics). Relayers that batch requests for throughput (the normal, encouraged mode of operation, since `RequestMessage`/multi-proof batching exists precisely to amortize proof-verification costs) are the ones exposed, and an attacker only needs to get one bad request accepted into the same batch as targeted victim requests.

### Recommendation
Do not let a single request/response/timeout failure invalidate the whole batch. Persist and finalize the state changes/events for messages that succeeded, and report failures for the individual failing messages only (e.g. return a partial success/failure report from `execute()`, or split failed messages out of the transactional scope so their revert does not roll back unrelated, successful messages in the same call). At minimum, `validate_unsigned` should not reject the entire unsigned extrinsic when only a subset of contained messages are invalid at the application level.

### Proof of Concept
1. Deploy/identify a registered `IsmpModule` (via `IsmpRouter::module_for_id`) whose `on_accept` returns `Err` for a request the attacker controls (e.g. by sending a malformed payload it is designed to reject, as shown by `ErrorModule` in the test router: [6](#0-5) ).
2. A relayer batches this request together with N other unrelated, valid `PostRequest`s targeting other modules/users into a single `Message::Request(RequestMessage)` (or several `Message`s within one `handle_unsigned` call), as is normal practice to amortize the shared membership proof.
3. Submit the batch via `handle_unsigned`. In `Pallet::execute`, `handle_incoming_message` succeeds for all N valid requests but returns an `Err` event for the malicious one; the subsequent `.collect::<Result<Vec<_>, _>>()` in `impls.rs` turns the aggregate result into `Err(Error::InvalidMessage)`.
4. If submitted as an unsigned transaction, `validate_unsigned` propagates this as `InvalidTransaction::BadProof`, and the transaction pool drops the entire batch — none of the N valid requests get delivered. If it somehow reaches dispatch, the `#[frame_support::transactional]` `handle_unsigned` call reverts all state changes for the batch, again preventing delivery of the N valid requests.

A relayer will construct the `RequestMessage` which holds a batch of new `PostRequest`s, as well as a _multi-proof_<sup>[1]</sup> of their existence on the source chain. The handler will perform the following operations

- Assert that the state machine's consensus client is not frozen
- Assert that the configured `challenge_period` for the `StateCommitment` has elapsed
- Assert that the requests have not been previously processed
- Assert that the requests have not timed out
- Assert that the membership proof for the requests verify
- Finally dispatch the requests to the relevant `IsmpModule::on_accept` and store a receipt for each request to prevent requests from being replayed.

<Callout title={'Danger'} type={"warn"}>
It's important to note that if the `IsmpModule::on_accept` does not return `Ok`, the receipt of this request will not be persisted, allowing the request to be **replayed**. Consequently, the `IsmpModule` is responsible for maintaining all invariants before modifying it's internal state to prevent partial state changes that could result in critical vulnerabilities in their request handler. This model ensures that if a request cannot be executed successfully on a destination state machine, it can time out gracefully on the source.
