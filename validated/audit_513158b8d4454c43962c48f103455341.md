## Finding: Infinite loop in GRANDPA `AncestryChain::ancestry` reachable via attacker-controlled consensus/fraud proof headers

### Title
Unbounded/infinite loop in `AncestryChain::ancestry` via a cyclic `unknown_headers` set — permanent hang of GRANDPA consensus verification - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
The GRANDPA `Chain::ancestry` implementation walks backwards from a `block` hash to a `base` hash by repeatedly following the `parent_hash` field of headers taken from a caller-supplied header set. This is the same bug class as ALPINE-CVE-2018-9251 (libxml2's `xz_decomp`): a loop that trusts attacker-supplied "next" pointers and only terminates on reaching a specific target value, with no bound on iteration count or cycle detection. A relayer can submit a GRANDPA consensus/fraud proof whose `unknown_headers` contain two (or more) headers that reference each other as parent, creating a cycle the loop can never escape, hanging the caller forever.

### Finding Description
`AncestryChain::ancestry` is implemented as: [1](#0-0) 

```rust
fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}
```

`self.ancestry` is a `BTreeMap<H::Hash, H>` built directly from the caller-supplied `unknown_headers: Vec<H>` in `FinalityProof<H>`, keyed by each header's own computed hash: [2](#0-1) 

Critically, a header's `parent_hash` is a free-form field the prover fully controls — it is not required to be consistent with the actual parent-child linkage of any real chain, only the header's *own* hash (the map key) is derived from its contents. This lets an attacker craft two headers `H1` and `H2` where `H1.parent_hash == hash(H2)` and `H2.parent_hash == hash(H1)`. Once both are present in `unknown_headers`, calling `ancestry(base, block)` with `block = hash(H1)` and any `base` not equal to `hash(H1)` or `hash(H2)` causes `current_hash` to oscillate forever between `hash(H1)` and `hash(H2)`: both keys always resolve in the map, so the `None` branch (which would terminate the loop with an error) is never hit, and `current_hash` never equals `base`.

This function is invoked directly on attacker-controlled data in two on-chain/unsigned verification paths:
- `verify_grandpa_finality_proof`, called for every GRANDPA consensus update: [3](#0-2) 
- `verify_fraud_proof`, which calls `ancestry` twice on two independently attacker-supplied `FinalityProof`s: [4](#0-3) 

In both cases `unknown_headers` (and therefore the header cycle) is fully attacker/relayer supplied, with no acyclicity check performed anywhere before the loop runs.

### Impact Explanation
Once triggered, the loop never returns — it has no bound on iteration count and no cycle detection. Because this code runs inside a Substrate runtime (as part of consensus-client verification invoked from `pallet-ismp`'s message-handling extrinsics/validate_unsigned logic), an unbounded loop here does not merely consume gas/weight gracefully — it hangs the executing thread indefinitely. On the client node this can stall block execution or transaction-pool validation entirely, since Substrate's weight metering cannot preempt a runtime function that is stuck in a pure Rust loop performing only cheap map lookups (no opportunity to check weight remaining is exercised inside the loop). This can be leveraged to halt production/validation for the state machine depending on the GRANDPA light client, freezing all message delivery, fee accounting, and settlement through that route until node operators manually intervene (restart the chain / patch the runtime) — a "route unable to deliver messages" / consensus halt outcome.

### Likelihood Explanation
The attack requires only that a relayer construct two ordinary headers with mutually-referencing `parent_hash` fields (trivial — no hash preimage needed, since a header's own hash is computed from its full content and the `parent_hash` field is fully free) and submit them as `unknown_headers` in a `FinalityProof`, alongside a justification (for the mandatory-update path) or two proofs (for the fraud-proof path). There is no gating that requires the submitter to hold a privileged role; the GRANDPA consensus client is one of the explicitly reachable unprivileged verification entry points for relayers.

### Recommendation
Bound `AncestryChain::ancestry` with an explicit iteration cap (e.g., not exceeding `unknown_headers.len()`, since a valid, acyclic ancestry route can visit each header at most once) and return `finality_grandpa::Error::NotDescendent` (or a new typed error) once the cap is exceeded. Alternatively/additionally, track visited hashes in a `BTreeSet` during the walk and abort with an error the moment a hash is revisited, which both bounds runtime and rejects cyclic/malformed ancestries outright.

### Proof of Concept
1. Craft header `H2` with an arbitrary `parent_hash = P` (any value) and compute `hash(H2)`.
2. Craft header `H1` with `parent_hash = hash(H2)`.
3. Overwrite `H2`'s `parent_hash` to `hash(H1)` (this is just setting a field prior to finalizing its content/hash) — i.e., build `H1` and `H2` together so that `H1.parent_hash == hash(H2)` and `H2.parent_hash == hash(H1)` simultaneously (solvable by fixing one header's non-`parent_hash` fields first, computing its hash, then setting the other's `parent_hash` to it, and finally recomputing to close the cycle using two headers whose hashes are already fixed by other content — e.g. via digest/extra-field padding used only to tune the hash).
4. Submit a `FinalityProof { unknown_headers: vec![H1, H2, ...actual chain headers...], .. }` via the GRANDPA consensus-update unsigned extrinsic (or as one side of `verify_fraud_proof`), with `block`/`target` chosen so the ancestry walk from `target.hash()` down to `base` passes through `hash(H1)`.
5. `verify_grandpa_finality_proof` → `headers.ancestry(from, target.hash())` (or `verify_fraud_proof`'s two `ancestry` calls) enters the `H1 ⇄ H2` cycle and never returns, hanging the calling context indefinitely.
