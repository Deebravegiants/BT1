### Title
Tron `IntentGatewayV2.onAccept` UpdateParams applies `protocolFeeBps`/`destinationFeeBps` with no upper-bound validation - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron port of `IntentGatewayV2` handles `RequestKind.UpdateParams` in `onAccept` by decoding the `ParamsUpdate` and writing `_params`/`_destinationProtocolFees` directly, with no equivalent of the mainline EVM contract's `_validateParams`/bounds check on `protocolFeeBps` and `destinationFeeBps`.

### Finding Description
The canonical EVM `IntentsBase.sol` enforces strict bounds before any fee parameter is committed: [1](#0-0) 

`_validateParams` requires `surplusShareBps <= 10_000` and `protocolFeeBps < 10_000`, and `_updateParams` additionally requires every `destinationFeeBps < 10_000` before writing to `_destinationProtocolFees`, reverting with `InvalidInput` otherwise.

The Tron variant of the same contract, however, implements `onAccept`'s `UpdateParams` branch without calling any validation routine at all — it directly overwrites `_params` and `_destinationProtocolFees[stateMachineId]` with attacker/governance-supplied values: [2](#0-1) 

There is no `_validateParams`-equivalent function present in this file, and no check that `feeBps < 10_000` (i.e., < 100%) is enforced anywhere in the Tron UpdateParams path, unlike the Solidity mainline. This means a `ParamsUpdate` cross-chain governance message that legitimately reaches this contract (dispatched from Hyperbridge, matching the intended `onAccept` authorization: `keccak256(incoming.request.source) == keccak256(IDispatcher(host()).hyperbridge())`) can set `protocolFeeBps` or any per-destination `destinationFeeBps` to any value including ≥10,000 (100%) or larger, with no cap.

### Impact Explanation
Since fee bps values feed directly into order-fee computations in `placeOrder`/fill flows (fee = `amount * feeBps / 10_000`), an unbounded `protocolFeeBps`/`destinationFeeBps` set at or above 10,000 effectively confiscates 100% or more of a user's escrowed input tokens on every order routed to/through that destination, or can create arithmetic conditions (fee > input amount) that either lock/under-refund user funds or break settlement math, causing concrete loss of user assets. This is functionally identical to the reported analog (unbounded royalty in `FootiumPlayer`): a governance-controlled numeric parameter that should be capped is left unbounded in one contract variant despite an existing, working reference implementation (`IntentsBase.sol`) that already enforces the cap, indicating this omission is a real regression/inconsistency rather than by design.

### Likelihood Explanation
Triggering requires only a single legitimate cross-chain governance dispatch of `RequestKind.UpdateParams` sourced from Hyperbridge (the same authorized path used for all normal fee updates on this contract); no additional privilege escalation, chain compromise, or malicious insider action is required beyond the normal operational flow of updating fees. A simple operator mistake (e.g., typo entering `15000` instead of `1500` bps) or a front-run of a fee update transaction (as in the original report) is sufficient to trigger unbounded fee extraction from users placing orders through this deployment, matching the exact bug class in the source report.

### Recommendation
Port the `_validateParams` bounds checks from `evm/src/apps/intentsv2/IntentsBase.sol` (specifically `surplusShareBps <= 10_000`, `protocolFeeBps < 10_000`) into the Tron `IntentGatewayV2.onAccept` `UpdateParams` handler, and enforce `destinationFeeBps < 10_000` for every entry in the destination-fee loop before writing to `_destinationProtocolFees`, reverting with `InvalidInput` otherwise — mirroring the mainline contract exactly.

### Proof of Concept
1. Hyperbridge governance (or a compromised/careless operator) dispatches a `PostRequest` with `body = abi.encodePacked(RequestKind.UpdateParams, abi.encode(paramsUpdate))` where `paramsUpdate.params.protocolFeeBps = 10000` (100%) or `paramsUpdate.destinationFees[0].destinationFeeBps = 20000` (200%).
2. The Tron `IntentGatewayV2.onAccept` (evm/tron/contracts/apps/IntentGatewayV2.sol lines 644-660) authenticates only that the request source is Hyperbridge, then unconditionally sets `_params = update.params;` and `_destinationProtocolFees[stateMachineId] = feeBps;` with no bound check.
3. A subsequent `placeOrder` for that destination computes the protocol fee using the now-unbounded `feeBps`, taking 100% (or effectively all) of the user's escrowed input tokens as protocol fee, whereas the mainline EVM contract would have reverted this update with `InvalidInput` at the `_validateParams`/loop-bound check.

    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
    }

    /**
     * @dev Updates the gateway's configuration parameters and per-destination protocol fees.
     * Called by Hyperbridge governance to modify fee settings, host address, dispatcher,
     * price oracle, and other operational parameters.
     *
     * Validates all params before applying. Emits ParamsUpdated with the old and new params,
     * then iterates over any destination-specific fee overrides and applies them to
     * `_destinationProtocolFees`.
     *
     * @param update The parameter update containing new params and destination fee overrides.
     */
    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }
