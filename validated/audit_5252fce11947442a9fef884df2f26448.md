## Title
Webhook Cross-Tenant Shop Spoofing — HMAC Covers Only the Body, Not the `shop-domain` Header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` attribute used to attribute an inbound webhook to a specific merchant is read from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is never part of the HMAC-signed material. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts this unauthenticated header to build the `WebhookMetadata` that is handed to the app's handler.

### Finding Description
`Request#to_signable_string` binds the HMAC only to `@raw_body`: [1](#0-0) 

`shop` is a completely separate accessor pulled straight from headers, outside the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC (of the body only) and then immediately forwards `request.shop` — the unauthenticated header value — to the handler as the tenant identifier, with no cross-check against the body or against any registered/expected shop: [3](#0-2) 

Because every shop that installs the same app shares the same `api_secret_key`, a valid HMAC only proves "this body was signed with *this app's* secret" — it does not bind the request to a particular tenant. The gem's own documentation asserts a stronger guarantee than what is actually implemented: it tells developers that `Registry.process` "will verify the request did indeed come from Shopify," implying the resulting `data.shop` is trustworthy. [4](#0-3) [5](#0-4) 

The broken identity binding, stated as an equality that the gem fails to enforce:
`shop authenticated by HMAC (= "any shop with access to this app's shared secret")` ≠ `shop used as the tenant/session key (= request.shop, an unsigned header)`.

### Impact Explanation
An attacker who installs the target app on their own (unprivileged) Shopify store obtains a valid HMAC signature for arbitrary webhook bodies they can influence (e.g. by setting a product/customer field, generating an `orders/create` event, etc., on their own store). Because the HMAC signable string is `@raw_body` alone, that exact `(body, hmac)` pair remains valid for any `shop-domain` header value. The attacker can replay that pair directly to the app's public webhook endpoint while substituting a victim shop's domain in the `shop-domain` header. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` claiming the (attacker-controlled) body belongs to the victim shop — a cross-tenant data/identity confusion that lets one merchant's traffic be attributed to another merchant's tenant record inside the host application. This maps to the "Critical - cross-tenant access" impact category defined in scope.

### Likelihood Explanation
Exploitation requires only an unprivileged internet user with a normal Shopify store installing the target app (a standard, low-privilege action any attacker can perform) and the ability to POST to the app's already-public webhook endpoint — no access token, `client_secret`, or privileged account is required. The webhook controller pattern shown in the gem's own docs accepts POSTs from the open internet by design. [6](#0-5) 

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the HMAC-signed material verified by `HmacValidator`, or otherwise cryptographically bind the header-derived shop to the signed body (e.g., include the header values in the signable string, or require the caller to supply/verify an expected shop per registration) before constructing `WebhookMetadata`. At minimum, document prominently that `request.shop` is unauthenticated and must be cross-checked by the host app against a shop that is actually known to be registered for that webhook/topic.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (any unprivileged install).
2. Attacker triggers a webhook event on their own store whose body content they can influence (e.g. update a product note, or use `customers/data_request`), causing Shopify to POST a legitimately-HMAC-signed `(raw_body, hmac)` pair to the app's webhook endpoint, with header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker crafts a new HTTP POST to the same app webhook endpoint using the identical `raw_body` and `hmac` header captured/reproduced from step 2, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only and succeeds since the body is unchanged.
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic:, shop: request.shop, body: request.parsed_body, ...))` with `shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own store — demonstrating cross-tenant attribution using a body the attacker fully controls.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
```

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
