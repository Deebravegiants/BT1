### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers that are excluded from the signed material. `Utils::HmacValidator.validate` only checks that the body's HMAC matches, then `Registry.process` trusts `request.shop` from the unsigned header to attribute the webhook to a tenant.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

`to_signable_string` returns `@raw_body` only — the `shop-domain` header (`Request#shop`, line 20-23) is never included in the signable string. `HmacValidator.validate` recomputes the HMAC over `to_signable_string` and compares it to the `hmac` from the header: [3](#0-2) 

`Registry.process` then uses the (unauthenticated) `request.shop` to build the tenant-identifying `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The identity binding broken is: **shop authenticated by HMAC (over body only) ≠ shop attributed to the webhook (from an unsigned header)**. Because the `api_secret_key` is shared across every shop that has installed the app, a fully valid HMAC can be produced for *any* shop the attacker controls (e.g. their own free/dev store where the app is installed) and that same signed `(body, hmac)` pair remains valid when the `x-shopify-shop-domain` header is swapped to a victim shop's domain — the signature check still passes because the header was never part of the signed content.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged user who has legitimately installed the app on their own shop can capture one genuine webhook delivery (body + valid HMAC), then replay it against the app's webhook endpoint with the `shop-domain` header changed to any other shop that also has the app installed. The handler will process it as if it came from the victim shop (`WebhookMetadata#shop`), potentially triggering shop-scoped side effects (e.g. state changes keyed by shop, GDPR/`shop/redact`-style handling, cache/session invalidation, `app/uninstalled` handling) attributed to a tenant the attacker does not control. This satisfies the Critical "cross-tenant access" bar since the shop-scoping guarantee the gem is supposed to provide (webhook is provably from Shopify *for that shop*) is broken.

### Likelihood Explanation
Requires only: (1) the ability to install the same (often public) app on an attacker-controlled shop — something any unprivileged internet user can do by creating a free Shopify development store, and (2) the ability to send an HTTP request to the app's webhook endpoint with attacker-chosen headers, which is trivial once one legitimate `(body, hmac)` pair is observed. No knowledge of `api_secret_key`, access tokens, or any other credential is required — this exactly mirrors the H-01 bug class of "a field acted upon but not covered by the integrity check."

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook_id`, `api_version`) values in the signed/verified material, or bind the trusted shop identity to something Shopify itself certifies to be tied to that HMAC (e.g., only trust `shop` values that are independently confirmed against a session/store lookup keyed by a value the app controls, not a client-supplied header). At minimum, document that `request.shop` is unauthenticated and must not be used as an authorization boundary without an additional binding check.

### Proof of Concept
1. Install the target app (assume it's a public/dev-store-installable app) on attacker-owned store `attacker-shop.myshopify.com`.
2. Trigger any webhook topic the app subscribes to; capture the raw body and the `x-shopify-hmac-sha256` header Shopify sends — this HMAC is valid because it's computed with the same `api_secret_key` the app uses for every shop.
3. Replay the exact same body and HMAC header to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (only body is checked), `Registry.process` invokes the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, causing the app to perform shop-scoped logic against the victim tenant using attacker-supplied body content.
