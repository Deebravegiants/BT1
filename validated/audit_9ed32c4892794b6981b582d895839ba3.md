### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body, but dispatches to the merchant's handler using the `shop` (and `topic`) values taken from unauthenticated HTTP headers. This breaks the intended binding `authenticated(shop) == acted_on(shop)`, mirroring the reported analog class where a field acted upon (`ERC20Method`) is not covered by the validated/signed data (the transfer payload's method check).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates only the HMAC over the raw body via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` and `request.topic` (unauthenticated headers) to look up the handler and build the `WebhookMetadata` passed to merchant-authored handler code: [3](#0-2) 

`HmacValidator.validate` computes the HMAC strictly over `to_signable_string` (the raw body only), never over `shop` or `topic`: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` field forwarded verbatim to the handler as the tenant identifier for the event: [5](#0-4) 

Because the HMAC only proves "this body was produced/authorized using the app's secret for *some* webhook," and not "this body belongs to shop X" or "this body is for topic Y," an attacker who is a merchant of the very app (i.e., can install the app on their own store and legitimately receive webhooks with a valid HMAC for their own shop) can capture such a valid `(body, hmac)` pair and replay it with the `shop-domain` (and/or `topic`) header rewritten to point at a different, victim shop. `Registry.process` will accept the HMAC (it only checks the body) and will hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop, while the actual signed content is the attacker's own data.

This is the same root-cause pattern as the reported analog: a field used to route/act on the transaction (`ERC20Method` there, `shop`/`topic` here) is decoded/read but never verified as being covered by the security check (a `TRANSFER` assertion there, an HMAC there here).

### Impact Explanation
Any app whose webhook handler uses `WebhookMetadata#shop` to select which merchant/tenant's records to create, update or credit (a common and encouraged pattern — this is literally the field's purpose) can be made to apply an attacker-supplied body under a victim shop's identity. Depending on the handler's logic (e.g., `orders/create`, `app/uninstalled`, `shop/update`), this enables cross-tenant data injection or state corruption, satisfying the "cross-tenant access" criterion for Critical/High impact in this program.

### Likelihood Explanation
Exploitability requires only that the attacker be able to install the target app on a store they control (a normal, unprivileged action for any Shopify merchant testing/installing a public or unlisted app) and can then observe the HMAC and body of webhooks legitimately delivered to their own endpoint. No access to the app's `client_secret`, access tokens, or any privileged credential is required — the attacker only replays their own previously-received, validly-signed webhook body while altering unauthenticated headers. This is directly reachable through the gem's own `Webhooks::Registry.process`/`Webhooks::Request` API as documented for standard app usage.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-signable content, or otherwise cryptographically bind them to the request (e.g., verify `shop` against an independently known session/shop-scoped secret, or require the webhook body itself to carry and cross-check the `shop_domain`/`shop_id` field that Shopify includes in most webhook payloads) before dispatching to handlers. At minimum, document prominently that `WebhookMetadata#shop` and `#topic` are unauthenticated and must not be trusted as tenant identifiers without additional verification.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook event (e.g., `orders/create`) and capture the raw POST body and the `X-Shopify-Hmac-Sha256` header — this HMAC is valid because `HmacValidator.validate` only signs `raw_body`, per [1](#0-0) .
3. Replay the identical body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (and/or a different `X-Shopify-Topic`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the body/HMAC pair is untouched: [6](#0-5) .
5. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, applying attacker-controlled body content under the victim's tenant identity: [7](#0-6) .
