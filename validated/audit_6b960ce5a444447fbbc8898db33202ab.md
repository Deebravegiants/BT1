## Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, but the `shop` value that is subsequently handed to the application's webhook handler is read from the `x-shopify-shop-domain` HTTP header, which is never included in the signed content. This breaks the intended identity binding: `hmac_valid(body) == true` is treated as equivalent to `shop_header == authentic_shop_that_generated_body`, but these are two different things.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic relationship to the signed body: [2](#0-1) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` — i.e., HMAC over `to_signable_string` (the body) — and then constructs `WebhookMetadata` using `request.shop` (the unauthenticated header) before dispatching to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes and compares HMAC strictly against `verifiable_query.to_signable_string`: [4](#0-3) 

The identity binding that should hold is: `shop_the_handler_trusts == shop_that_actually_produced_this_signed_body`. Instead the gem only proves `hmac_valid == true` for the body bytes, and separately trusts an unauthenticated header for `shop`. Because all shops installed under one app share the same `api_secret_key` used to compute the webhook HMAC, any tenant that can trigger a webhook on their own store (e.g., by creating an order in their own, legitimately-installed shop) obtains a `(raw_body, hmac)` pair that is valid under the app's secret. That attacker-controlled tenant can then resend the exact same body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `Utils::HmacValidator.validate` will still return `true` (it never looks at the header), and the handler receives `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"` with attacker-chosen body content.

Compare to `AuthQuery`, which correctly includes `shop` inside the signed content: [5](#0-4) 

The webhook path deliberately/accidentally omits this binding — `shop` is a field acted upon by downstream logic (any code keying data storage or business logic off `WebhookMetadata#shop`) but is not covered by the HMAC.

### Impact Explanation
This allows a merchant/tenant of a multi-tenant Shopify app (an unprivileged, ordinary app user — not requiring `api_secret_key`, stolen credentials, or TLS interception) to inject attacker-controlled webhook payloads that are misattributed to an arbitrary victim shop domain. Any host application that follows the gem's documented contract (trusting `WebhookMetadata#shop` from a "verified" webhook) can be tricked into writing/mutating/deleting data under a victim tenant's identity — a cross-tenant access/data-integrity violation directly caused by this gem's incomplete authentication of the webhook shop field.

### Likelihood Explanation
Requires only: (1) the attacker installs the app on their own shop (this is a normal, unprivileged onboarding action available to anyone), (2) they trigger any webhook event to observe a valid `(body, hmac)` pair, and (3) they replay it with a spoofed `shop-domain` header. No secrets, no privileged accounts, and no TLS interception are needed — the webhook HMAC and shop header are both attacker-observable/attacker-settable over a normal HTTP POST to the app's public webhook endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to the signed body — e.g., include the `x-shopify-shop-domain` header (and other identifying headers) in `to_signable_string`, or require the caller to separately verify that `request.shop` matches an expected/registered shop before trusting `WebhookMetadata#shop`. At minimum, document explicitly that `shop` in `WebhookMetadata` is unauthenticated and must not be used for tenant-scoping decisions without additional verification.

### Proof of Concept
1. Attacker installs app on their own shop `attacker.myshopify.com` and triggers an event so Shopify sends the app a real webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, B)`), header `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the exact same request to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and matches `H` — validation passes. [6](#0-5) 
4. `WebhookMetadata.new(shop: request.shop, ...)` is built with `shop = "victim.myshopify.com"` and dispatched to the handler, which trusts it as the authentic tenant for body `B` — despite `B` never having been produced by or for `victim.myshopify.com`.
