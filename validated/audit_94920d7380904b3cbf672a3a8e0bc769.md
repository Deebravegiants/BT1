Audit Report

## Title
Attacker-controlled `MessageID` collision in gateway `WebAPIHandler.HandleLegacyUserMessage` allows cross-user response hijacking / loss of trigger callback - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
The gateway's legacy WebAPI trigger flow (`handler.HandleLegacyUserMessage`) stores a caller's response callback in a shared, gateway-wide map keyed solely by the client-supplied `msg.Body.MessageID`, with no check for whether that ID is already in use by another (potentially different) caller. [1](#0-0)  When any DON node later reports a `web_api_trigger` result for that `MessageID`, `handleWebAPITriggerMessage` looks the ID up in the map, deletes it, and forwards the response to whichever caller's callback is currently stored there — with no verification that the responding callback belongs to the request that produced that node response. [2](#0-1) 

## Finding Description
`Message.Validate()` enforces format constraints on `MessageID` (length, no trailing null bytes) and derives `Body.Sender` from the ECDSA signature, but it never checks that `MessageID` is unique or bound to the sender. [3](#0-2)  Since the signature only proves who signed a given message, not that the `MessageID` chosen inside it is exclusive to that signer, two different unprivileged callers (Attacker A and victim B) can independently sign and submit legacy `web_api_trigger` requests using the identical `MessageID`.

`h.savedCallbacks[msg.Body.MessageID] = &savedCallback{...}` unconditionally overwrites any existing entry for that ID. [1](#0-0)  If B's request is stored first and A's request with the same ID arrives before a DON node responds to B, A's callback silently replaces B's in the map. When a DON node's `web_api_trigger` response for that `MessageID` subsequently arrives at `handleWebAPITriggerMessage`, the handler pops whatever callback currently sits at that key and delivers the response to it — it does not compare the response against the original requester's identity. [2](#0-1)  `HandleNodeMessage`'s sender check only verifies that the *node* sending the response matches the expected `nodeAddr`; it performs no binding to which user's request the response corresponds to. [4](#0-3) 

This is a real, demonstrated gap in the codebase: the newer v2 HTTP trigger handler (`httpTriggerHandler.setupCallback`) explicitly guards against exactly this problem by rejecting a request whose ID is already in-flight ("requestID has already been used... Ensure the requestID is unique for each request") [5](#0-4) , and this behavior is explicitly covered by a "duplicate request ID" test. [6](#0-5)  The legacy `capabilities/handler.go` path used by `web_api_trigger`, however, has no equivalent check, confirming the flagged behavior is a genuine, unmitigated gap rather than a misunderstanding of intended design. This legacy handler is still actively wired into the gateway via `handler_factory.go` and reachable from any unauthenticated (only self-signed) HTTP client through `gateway.ProcessRequest` → `HandleLegacyUserMessage`. [7](#0-6) 

## Impact Explanation
An unprivileged, unauthenticated-to-the-gateway caller can pick an arbitrary `MessageID` and, by colliding with a concurrent legitimate caller's ID, either (a) silently drop the legitimate caller's in-flight trigger response — a denial of service that leaves the victim's HTTP request to hang until the gateway's callback timeout — or (b) potentially receive a `web_api_trigger` response object that was intended for a different caller, if timing allows the attacker's entry to still occupy the slot when the DON node's response for that `MessageID` arrives. This maps to the "cross-user response corruption" impact category in scope, since it involves the gateway trust boundary directly reachable by unprivileged clients.

## Likelihood Explanation
Exploitability requires only that the attacker guess or observe a `MessageID` in concurrent use by another caller. The repo's own example script (`core/scripts/gateway/web_api_trigger/invoke_trigger.go`) defaults to a fixed, predictable ID (`"12345"`) [8](#0-7) , which indicates that non-random, easily-collided `MessageID`s are realistic in practice for clients built off this reference tooling, and a malicious client can also deliberately race a known/target ID with no authentication or ownership check standing in the way. This is moderate-to-high likelihood for any deployment where clients reuse deterministic/default ID generation, and the attack requires no elevated privileges — only the ability to sign and send a legacy gateway message, which any client can do.

## Recommendation
Bind each `savedCallbacks` entry to the identity of the request's signer (e.g., key on `(Sender, MessageID)` rather than `MessageID` alone), and/or reject a legacy request whose `MessageID` collides with an existing in-flight entry — mirroring the "in-flight request ID" duplicate-detection already implemented in the v2 `httpTriggerHandler.setupCallback`. Consider deriving the storage key server-side instead of trusting the client-supplied value verbatim.

## Proof of Concept
1. User B signs and sends a legacy `web_api_trigger` message with `MessageID = "shared-id"`; the gateway stores B's callback at `h.savedCallbacks["shared-id"]` and dispatches the request to all DON members. [9](#0-8) 
2. Before any DON node responds, Attacker A signs and sends a second legacy `web_api_trigger` message, also using `MessageID = "shared-id"`, from a different private key; the gateway overwrites the map entry with A's callback.
3. When a DON node's `web_api_trigger` result for `MessageID = "shared-id"` arrives, `handleWebAPITriggerMessage` pops the current entry (now A's callback) and delivers the response to A. [2](#0-1) 
4. B's original HTTP request to the gateway never receives a response and stalls until `callback.Wait` times out in `gateway.ProcessRequest`. [10](#0-9) 

A minimal Go unit test can reproduce this deterministically against `capabilities.handler` by: constructing two signed `api.Message`s with identical `MessageID` and distinct private keys, calling `HandleLegacyUserMessage` for both with separate `handlers.Callback` instances, then invoking `HandleNodeMessage` with a single node response for that `MessageID` and asserting that only the second (attacker's) callback receives a response while the first (victim's) callback never resolves.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
