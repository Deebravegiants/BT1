## Analog Found

### Title
Refund path for timed-out cross-chain transfers is blocked while `HyperFungibleToken`/`WrappedHyperFungibleToken` are paused, permanently freezing burned/locked user funds - (File: `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`)

### Summary
`HyperFungibleToken.send()` burns the sender's tokens up-front and dispatches an ISMP `PostRequest`; the tokens are only restored to the sender if the request either lands (`onAccept` on the destination) or times out and `onPostRequestTimeout` is invoked on the source. Both `onAccept` and `onPostRequestTimeout` carry the `whenNotPaused` modifier [1](#0-0) , and the flow is confirmed in the maintainers' own design notes: `onAccept` and `onPostRequestTimeout` "run `onlyHost` and `whenNotPaused`" [2](#0-1) . This is the same bug class as the VaultController report: a state-mutating recovery path (repaying / reclaiming funds) is disabled by `pause()`, while an independent, time-driven process (interest accrual there; timeout-clock expiry here, driven by `HandlerV2`/`IsmpHost`, which do not check the destination app's `Pausable` state) keeps advancing regardless of the pause.

### Finding Description
`send()` burns tokens immediately and dispatches a request via the host: [3](#0-2) . The only two ways to make the sender whole are `onAccept` (destination arrival) or `onPostRequestTimeout` (source-side refund after expiry). Both callbacks are gated by `whenNotPaused` in addition to `onlyHost` [4](#0-3) , and the same pattern exists in `WrappedHyperFungibleToken` [5](#0-4) .

The timeout clock itself is not controlled by the token contract: `HandlerV2.handlePostRequestTimeouts` (invoked by any relayer, permissionlessly) checks the request's timeout against the host's timestamp and calls `host.dispatchTimeOut(...)`, which in turn calls the app's `onPostRequestTimeout` [6](#0-5) . Neither `EvmHost`'s `notFrozen` modifier nor `HandlerV2`'s `notFrozen(host)` modifier checks the destination *application's* `Pausable` state — they only check the host-level `FrozenStatus` [7](#0-6) . This means:

1. A user calls `send()`, burning their tokens and committing a `PostRequest` with a finite `timeout`.
2. Before the request is delivered (`onAccept`), the token owner calls `pause()` on `HyperFungibleToken` — for whatever emergency or migration reason (documented as an intended, legitimate operator action) [8](#0-7) .
3. The request's timeout elapses. Because the timeout window is a wall-clock deadline tracked by the ISMP host/handler independent of the app's pause state, the request becomes eligible for `onPostRequestTimeout` regardless of the token being paused — analogous to interest accruing in `pay_interest()` regardless of `VaultController` being paused.
4. Any relayer attempts to deliver the timeout via `HandlerV2.handlePostRequestTimeouts` → `host.dispatchTimeOut` → `HyperFungibleToken.onPostRequestTimeout`, but the call reverts because the token is paused. There is no retry mechanism once the on-chain timeout window and destination delivery race have both closed and been consumed — the burned tokens are stuck with zero recovery path while the pause remains in effect.
5. If the pause persists (deliberately, or because of an incident that also prevents `unpause()`, e.g. compromised/unavailable owner key, prolonged emergency response), the user's principal is frozen indefinitely with no way to reclaim it — worse than the VaultController case, where the user only faced accruing interest risk, not outright loss of principal.

This exactly mirrors the reported bug class: a `Pausable`-gated recovery function (`onPostRequestTimeout` ≈ `repayUSDi`) is blocked by `pause()`, while a background, time-based mechanism outside the pausable app's control (the ISMP timeout clock ≈ interest accrual) continues to run and eventually renders the user unable to recover funds through the normal path.

### Impact Explanation
Funds sent via `send()` are burned atomically and can be permanently unrecoverable if the token is paused at/after request timeout, since the only recovery function (`onPostRequestTimeout`) is itself blocked by the same pause. This is a concrete, permanent-freezing-of-funds risk reachable by any ordinary token bridger performing a routine cross-chain transfer, with no counterparty or admin fault required beyond a legitimate pause. Given `HyperFungibleToken` and `WrappedHyperFungibleToken` are the burn/mint and lock/unlock token bridge primitives explicitly in scope, this is Medium/High severity depending on how long pauses are expected to last operationally.

### Likelihood Explanation
Pausing is a normal, documented operational action (emergency response, migrations) [8](#0-7) , and cross-chain timeouts are a routine and expected occurrence for any relayed message (network congestion, relayer downtime, destination chain issues). The overlap window — pause active while a pending send's timeout has elapsed — is realistically likely, especially since pauses are most likely to be triggered exactly during periods of relayer/network stress that also cause timeouts to accumulate.

### Recommendation
Do not gate `onPostRequestTimeout` (the refund/recovery path) with `whenNotPaused`. Pausing should stop new burns (`send`) and new mints (`onAccept`), but must not block returning already-committed-and-timed-out funds to their original owner. If the `whenNotPaused` gate on `onPostRequestTimeout` was added specifically to prevent forged-timeout-proof mints per the design decision [9](#0-8) , that protection should instead rely on the existing `onlyHost` + proof-verification guarantees rather than `Pausable`, since it creates the freezing risk described above.

### Proof of Concept
1. User A calls `HyperFungibleToken.send({dest: chainB, amount: X, timeout: T, ...})`; `X` tokens are burned from A [10](#0-9) .
2. Owner calls `pause()` before the request is relayed/accepted on chain B [11](#0-10) .
3. Time `T` elapses without delivery (relayer downtime, congestion, etc.).
4. A relayer submits the timeout batch via `HandlerV2.handlePostRequestTimeouts`, which calls `host.dispatchTimeOut(...)` → `HyperFungibleToken.onPostRequestTimeout(...)`.
5. The call reverts with `Pausable: paused`, since `onPostRequestTimeout` carries `whenNotPaused` [4](#0-3) .
6. User A's `X` tokens remain burned with no route to re-mint until `unpause()` is called — and if the pause is never lifted (or the timeout-delivery window for retries is otherwise exhausted), the funds are permanently frozen.

## Pausability

Both contracts inherit from OpenZeppelin's `Pausable`. The owner can pause and unpause all operations:

```solidity lineNumbers
IHyperFungibleToken(tokenAddress).pause();
IHyperFungibleToken(tokenAddress).unpause();
```

When paused, `HyperFungibleToken` blocks all ERC20 transfers (`transfer` and `transferFrom`) in addition to cross-chain `send()` and `onAccept()`. This is a full stop on all token movement — use it for emergency situations or during migrations.
