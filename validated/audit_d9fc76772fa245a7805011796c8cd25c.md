### Title
Webhook shop-domain header not covered by HMAC integrity check enables cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an HTTP header that is never included in the HMAC-signed data. `Utils::HmacValidator` only verifies the raw request body against the signature, so the `shop-domain` header can be swapped without invalidating the HMAC check, breaking the equality `hmac-verified bytes == bytes acted upon (topic + body + shop)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` are all read straight from headers, independent of what is HMAC-verified: [2](#0-1) 

`Registry.process` validates only the HMAC of the request, then immediately trusts `request.shop`/`request.topic` to dispatch to a handler and build `WebhookMetadata`: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) and compares it with `OpenSSL.secure_compare`: [4](#0-3) 

Because the signature never covers the `shop-domain` header, a caller who possesses one valid `(body, hmac)` pair — for example from a webhook legitimately delivered to a shop the attacker controls, or any shop event triggerable by an unprivileged merchant/tester — can resubmit the identical body/HMAC to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` header. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop. This is structurally identical to the reported bug class: a field that is acted upon (`shop`, the tenant-binding attribute, analogous to `Lock.end` driving governance power) is not covered by the integrity check that is supposed to bind the whole record (the HMAC, analogous to the `MAXTIME` restriction enforced elsewhere but skipped on the merged path).

### Impact Explanation
If a host application uses `WebhookMetadata#shop` (as delivered by this gem) to select which tenant's data to update/delete/credit — the intended and documented use of this field — an attacker can force the app to process attacker-controlled but seemingly-verified webhook data under a victim shop's identity, i.e. cross-tenant access/data corruption without ever possessing the victim's credentials or the app's `api_secret_key`. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The attacker only needs to obtain one legitimately-signed `(body, hmac)` webhook pair — trivially available by installing/using the app on a shop they control (unprivileged) and capturing its own webhook deliveries — then replay it against the endpoint with a forged `shop-domain` header. No access to `api_secret_key`, TLS interception, or privileged accounts is required, so likelihood is high wherever the host trusts `request.shop`/`WebhookMetadata.shop` for tenant scoping, which is the gem's documented usage pattern.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the value that is HMAC-verified (or otherwise cryptographically tie them to the signed body), so `HmacValidator.validate` fails whenever any of these header-derived, tenant-identifying fields are altered relative to what Shopify originally signed. At minimum, document/enforce that consumers must independently verify `request.shop` corresponds to a session/shop they already trust before acting on webhook data, since the header itself carries no integrity guarantee today.

### Proof of Concept
1. App owner (or an unprivileged attacker who installs the app on shop `attacker.myshopify.com`) triggers a webhook event; Shopify sends a POST with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker captures this request, then resends it to the same webhook endpoint but changes only the header to `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the new headers; `Utils::HmacValidator.validate` recomputes the signature from `@raw_body` only (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`) — identical to step 1 — so validation passes.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls the registered handler with `WebhookMetadata(shop: "victim.myshopify.com", body: B, ...)`, causing the host app to act on shop `B`'s payload as if it belongs to `victim.myshopify.com`.
