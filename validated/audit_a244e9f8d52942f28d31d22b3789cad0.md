### Title
Webhook shop/topic identity spoofing via HMAC coverage gap — `Registry.process` trusts unauthenticated headers - ([File: lib/shopify_api/webhooks/registry.rb](lib/shopify_api/webhooks/registry.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , so the HMAC computed by `Utils::HmacValidator.validate` only authenticates the body bytes, never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers [2](#0-1) . Yet `Registry.process` forwards those unauthenticated header values straight into the handler as trusted identity data after validation succeeds [3](#0-2) .

### Finding Description
The identity binding that should hold is: `hmac_valid(raw_body) == true` implies `shop header == the shop that produced raw_body`. That equality does not hold here, because the HMAC signature only commits to `@raw_body`:

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all parsed straight from HTTP headers with no cryptographic tie to the body or to each other [4](#0-3) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` — i.e., "is this body's HMAC correct for *some* valid webhook" — and, if so, unconditionally trusts `request.shop` and `request.topic` when constructing the data handed to the app's handler:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

This is documented as verifying "the request did indeed come from Shopify," giving downstream integrators (e.g. `shopify_app`) false confidence that `data.shop` is authenticated [5](#0-4) .

Because any app has at least one shop it controls (its own dev/test install), an attacker who is a legitimate merchant/installer of the target app can obtain a genuinely-signed `(raw_body, hmac)` pair for their own shop from Shopify (by triggering any webhook topic on their own store), then replay that exact body/HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to name a victim shop. `HmacValidator.validate` still passes because it only checks the body against the secret; `Registry.process` then calls the handler with `shop: "victim-shop.myshopify.com"` and the attacker-supplied body content, breaking the shop-to-body identity binding.

### Impact Explanation
This crosses a tenant boundary: the handler is invoked believing data legitimately originated from the victim shop, when in fact both the body content and the triggering timing are attacker-controlled while only the `shop` label is forged. Any application logic keyed on `WebhookMetadata#shop` (e.g., writing order/customer data, updating the merchant's stored state, GDPR/redact workflows for `shop/redact`, `customers/redact`, `customers/data_request`) can be poisoned with attacker-chosen content attributed to another tenant — this is cross-tenant data injection, which the rules classify as Critical impact.

### Likelihood Explanation
The only prerequisite is that the attacker controls (or can install the app on) at least one shop capable of generating any real webhook — a normal, unprivileged capability for anyone who installs a public Shopify app. No access to `api_secret_key`, tokens, or the target's credentials is required; only network-level ability to POST to the app's public webhook endpoint with modified headers.

### Recommendation
Include the identity fields (`shop`, `topic`) in the signed data — or, more practically, require the host application to cross-check the `shop-domain` header against the shop that owns the currently-active webhook subscription (looked up via `webhook_id` or an out-of-band registry) before trusting it. At minimum, the library should compute/verify signatures over a canonical string that binds `shop` and `topic` to the body, not the raw body alone, and the documentation should explicitly warn that `WebhookMetadata#shop`/`#topic` are not covered by the HMAC.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any subscribed webhook topic (e.g. `orders/create`), capturing the genuine request Shopify sends: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC-SHA256(secret, B)`).
2. Attacker replays the request to the app's webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes the HMAC over `@raw_body` (`B`) [6](#0-5) .
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [7](#0-6) , causing the app to act on attacker-controlled body content as if it belonged to the victim shop.
