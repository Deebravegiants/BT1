Unbounded price-impact swap in `UniV3UniswapV2Wrapper.swapETHForExactTokens` allows frontrun/sandwich of `IntentGatewayV2.placeOrder` fee-swap - (File: evm/src/utils/uniswapv2/UniV3UniswapV2Wrapper.sol)

### Summary
`UniV3UniswapV2Wrapper.swapETHForExactTokens` (`evm/src/utils/uniswapv2/UniV3UniswapV2Wrapper.sol:114-156`) builds a Uniswap V3 `ExactOutputSingleParams` with `sqrtPriceLimitX96: 0` [1](#0-0) , exactly the pattern flagged in the external report for `InfiltrationPeriphery.heal`. This wrapper is deployed as the protocol's `uniswapV2Router()` on chains where the native UniswapV2 router is unavailable (per `evm/script/DeployUniV3Wrapper.s.sol:21-33`, which writes the wrapper's address into the `UNISWAP_V2` config slot read by `IDispatcher.uniswapV2Router()`) [2](#0-1) . `IntentGatewayV2.placeOrder` unconditionally calls this function whenever an unprivileged user pays `order.fees` with native ETH: [3](#0-2) .

### Finding Description
When a user places an order and elects to pay the solver fee in native ETH (`msgValue > 0`), `IntentGatewayV2.placeOrder` calls `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), block.timestamp)` [4](#0-3) . If `uniswapV2Router()` resolves to `UniV3UniswapV2Wrapper` (the deployment path used to give a V2-compatible interface backed by Uniswap V3 on chains lacking a canonical V2 deployment), the actual swap executed is `SWAP_ROUTER.exactOutputSingle` with `sqrtPriceLimitX96` hardcoded to `0` [5](#0-4) .

The only bound on execution price is `amountInMaximum: msg.value`, i.e. the user's own `msgValue` (the leftover native ETH not consumed by input escrow) — this is analogous to `heal`'s `amountInMaximum: msg.value` in the audit report. Because `sqrtPriceLimitX96` is `0` (inactive), the V3 pool can be pushed to any tick before the trade executes, up to the limit of `amountInMaximum`. A searcher observing the pending `placeOrder` transaction in the mempool can:
1. Frontrun with a large swap in the same direction (buying `feeToken` with WETH) to move the pool price up.
2. Let the victim's `exactOutputSingle` execute at the worse post-manipulation price, consuming most/all of the user's supplied `msgValue` to obtain `order.fees` worth of `feeToken`.
3. Backrun to restore the pool price and capture the extracted value.

The victim is any unprivileged user submitting `placeOrder` with `msgValue > 0` for the fee payment — no special privilege is required to trigger this path, and no frontend-supplied slippage/price-limit parameter exists to protect them, since `heal`'s companion `costToHeal`-style quoting problem — the design gives the caller no ability to bound tick price. This mirrors the report's root cause precisely: the swap wrapper's zero `sqrtPriceLimitX96` disguises an unprotected-price trade behind a refund mechanism (`if (spent < msg.value) { refund }`), just like `heal`'s `if (msg.value > amountIn) { refundETH }` [6](#0-5) .

The same zero-`sqrtPriceLimitX96` pattern also appears in `swapExactTokensForETH` [7](#0-6)  and in the quoting helpers `getAmountsIn`/`getAmountsOut` [8](#0-7) , which — like `costToHeal` in the original report — will not reflect adverse execution-time market conditions.

### Impact Explanation
Users paying the `IntentGatewayV2` solver fee in native ETH on a chain where `uniswapV2Router()` points to `UniV3UniswapV2Wrapper` can be sandwiched, losing up to the full difference between the fair market price and their supplied `msg.value` for the fee-token leg of `placeOrder`. Because `amountInMaximum` equals the entire leftover `msgValue`, a sufficiently funded attacker can extract essentially all of that value in the worst case, a concrete loss of user funds triggered by ordinary, expected use of the intent-placement flow — meeting the Medium severity bar (loss of funds for an unsuspecting, unprivileged caller via price manipulation, not a low/no-impact issue).

### Likelihood Explanation
Any `placeOrder` call with `order.fees > 0` paid in native ETH is affected whenever the underlying `uniswapV2Router()` is the V3-backed wrapper. This is a standard, permissionless, singleton user action (no special role needed) and the MEV/sandwich technique against a public mempool transaction with a known exact-output target and zero price limit is well understood and cheap to execute, making exploitation practically certain once such a transaction is visible pre-confirmation.

### Recommendation
Add a caller-supplied (or oracle/TWAP-derived) `sqrtPriceLimitX96` bound to `UniV3UniswapV2Wrapper.swapETHForExactTokens` and `swapExactTokensForETH`, threaded through from `IntentGatewayV2.placeOrder`'s fee-swap path (e.g., let the caller pass a max acceptable price or compute one from a short TWAP observation of the pool before swapping), instead of hardcoding `0`. Alternatively, tighten `amountInMaximum` using a fresh on-chain quote with a bounded slippage tolerance rather than relying on the user's entire `msgValue`, and revert if the quoted price deviates materially from a TWAP reference.

### Proof of Concept
1. Deploy `UniV3UniswapV2Wrapper` and configure it as `uniswapV2Router()` on the `EvmHost`/dispatcher, per `evm/script/DeployUniV3Wrapper.s.sol`.
2. A user calls `IntentGatewayV2.placeOrder` with `order.fees > 0` and sends `msg.value` covering both the input assets and the fee-swap, causing the gateway to call `swapETHForExactTokens{value: msgValue}(order.fees, [WETH, feeToken], address(this), block.timestamp)` [9](#0-8) .
3. An attacker observes this pending transaction and frontruns it with a large WETH→feeToken swap on the same V3 pool, pushing the pool price up.
4. The victim's `exactOutputSingle` executes with `sqrtPriceLimitX96 = 0` (no protection) [1](#0-0) , consuming a much larger portion of `msg.value` than fair value to obtain `order.fees` of `feeToken`, up to the full `amountInMaximum`.
5. The attacker backruns by reversing the swap, capturing the spread as profit while the victim's refund (if any) is reduced or eliminated [6](#0-5) .
