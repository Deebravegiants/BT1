The `Webhooks::Request#to_signable_string` (which is HMAC-verified) covers only `@raw_body`, while `Webhooks::Request#shop` is read directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header and is never included in the signed payload. ### Title
Webhook tenant identity spoofing via unsigned `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value used for tenant routing from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature verified by `Utils::HmacValidator.validate` only covers the raw request body (`to_signable_string` returns `@raw_body`). The header carrying the tenant identity is never part of the signed bytes, so it can be freely modified without invalidating the HMAC check.

### Finding Description
`Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)` and then immediately trusts `request.shop` for tenant identification, forwarding it into the handler as `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)`. [1](#0-0) 

The signable string used for HMAC verification is defined as just the raw body, excluding all headers (including `shop-domain`, `topic`, `webhook-id`, `api-version`): [2](#0-1) 

Because the Shopify app's `client_secret`/webhook signing secret is shared across *all* shops that install the app (it is not per-shop), any merchant who installs the app on their own store legitimately receives Shopify-signed webhooks (raw body + valid HMAC) for their own shop's events. That merchant can capture such a `(raw_body, hmac)` pair and replay it to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. Since the equality actually enforced is:

`HMAC(raw_body, secret) == received_hmac`

...and the identity ultimately acted upon by the host application is `request.shop` (unauthenticated header), the check silently answers permissively for a forged tenant: `shop_verified (not checked) != shop_acted_upon (header value)`. The webhook is accepted and dispatched to the handler as if it originated from the victim shop, with attacker-influenced body content.

### Impact Explanation
This breaks the tenant boundary the whole webhook subsystem is meant to enforce: an app's webhook handler (per the library's documented contract) uses `WebhookMetadata#shop` to select/act on a specific merchant's data (e.g., updating that shop's local records, deleting data, provisioning access). An attacker who is merely a legitimate merchant of the app can inject a forged event that the host application will process under the identity of a different, unrelated shop — a cross-tenant data-integrity/confusion vulnerability, matching the "Critical - cross-tenant access" bar without needing the app's `client_secret`, any access token, or any privileged account.

### Likelihood Explanation
Any developer/merchant who has the target app installed on their own store can trivially receive genuine signed webhooks for that store, and webhook endpoints are typically a single shared public HTTPS URL for a multi-tenant app. Forging the header on replay requires no cryptographic material beyond the observed valid request, making this easy to execute and requiring only an ordinary merchant account — not a privileged one.

### Recommendation
Include the shop/tenant identity (and other routing-critical headers such as `topic`) inside the signed payload used for verification, or otherwise cryptographically bind `shop-domain` to a value that is authenticated per request (e.g., verify the shop domain against a known list of shops that installed the app with a stored per-shop secret/session), so that `to_signable_string` covers everything the application acts upon rather than only `@raw_body`.

### Proof of Concept
1. Merchant `M` installs the app on `attacker-shop.myshopify.com`. Shopify sends a legitimate webhook to the app's shared endpoint:
   ```
   X-Shopify-Topic: products/update
   X-Shopify-Hmac-Sha256: <valid-base64-hmac-of-body>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: {"id":1,"title":"..."}
   ```
2. `M` captures the exact raw body bytes and the `X-Shopify-Hmac-Sha256` value.
3. `M` replays the identical body and HMAC header to the same endpoint, only changing:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls: [3](#0-2) 
   `Utils::HmacValidator.validate(request)` passes because it only checks `raw_body` against the secret; `request.shop` now returns `"victim-shop.myshopify.com"`.
5. The host application's handler executes business logic (e.g. data mutation, redaction, entitlement changes) believing the event is authentic for `victim-shop.myshopify.com`, achieving cross-tenant impact.
