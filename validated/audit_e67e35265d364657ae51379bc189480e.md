Webhook `shop` identity field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC only over the raw request body, while the `shop` (tenant identity), `topic`, `webhook_id`, and `api_version` fields are read directly from unauthenticated HTTP headers and passed straight into the handler as trusted identity data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#hmac` decodes the `hmac-sha256` header value for comparison: [1](#0-0) [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers that are never included in the signable string: [3](#0-2) 

`ShopifyAPI::Utils::HmacValidator.validate` only checks the HMAC of `to_signable_string` (i.e., the body) against the secret: [4](#0-3) 

`Registry.process` uses this "validated" request to construct `WebhookMetadata`, propagating the unauthenticated `shop` header directly to the handler as the trusted tenant identifier: [5](#0-4) [6](#0-5) 

The gem's own documentation instructs developers to trust `data.shop` as "The shop domain of the webhook" after calling `Registry.process`, reinforcing that this field is intended to be an authenticated identity binding, when in fact it is not bound to the HMAC at all: [7](#0-6) [8](#0-7) 

This breaks the equality that should hold: `shop authenticated by HMAC == shop used as tenant/session key`. Instead, the equality that actually holds is: `bytes verified (raw_body) != bytes/fields relied upon (shop, topic, webhook_id, api_version headers)`.

### Impact Explanation
Any party capable of triggering a legitimately-HMAC-signed webhook delivery from Shopify for their own shop (e.g., a merchant who has installed the app and can create resources such as orders, products, or use webhook topics whose body content is attacker-influenced or predictable/empty, such as `app/uninstalled`) can capture that valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header swapped to reference a different, victim shop. `HmacValidator.validate` will still pass because it never inspects the headers, and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the victim's domain while carrying attacker-controlled body content. Any host application following this gem's documented pattern of using `data.shop` to select the tenant session, apply per-shop data, or gate business logic will process attacker data under the victim's tenant identity — a cross-tenant identity binding bypass.

### Likelihood Explanation
Exploitability depends only on the ability to obtain one validly-signed webhook body/HMAC pair from Shopify for the attacker's own store (readily available to any merchant/developer who installs the app) and does not require the app's `api_secret_key`, an access token, or any privileged access. The attacker only needs to control the HTTP headers of the replayed request, which is trivial for any internet-facing webhook endpoint. This is a design property of this gem's `Webhooks::Request`/`Registry` classes themselves (not a misuse of a documented safer alternative), since the documented processing flow directly surfaces the unauthenticated header as trusted identity.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the HMAC-verified content, for example by including the relevant headers in `to_signable_string`, or by requiring the host app to cross-check `WebhookMetadata.shop` against session/tenant records established via OAuth before trusting it. At minimum, update `Webhooks::Request` so `hmac` verification covers the full set of identity-bearing fields consumed downstream, not just the raw body, and document that `data.shop` cannot presently be trusted as cryptographically bound to the payload.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and registers/receives an `orders/create` webhook. Shopify signs the request:
   - Headers: `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`
   - Body: `{"id":1,...}` (attacker-controlled order data, since attacker created the order).
2. Attacker replays the exact same body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses `shop` from the (forged) header value `victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` recomputes HMAC over `raw_body` only — passes, since body and HMAC are unmodified and genuinely signed by Shopify.
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker order data>, ...)` and invokes the handler, which — per this gem's documented pattern — treats `data.shop` as the authenticated tenant and processes attacker-controlled data as if it belonged to `victim.myshopify.com`.

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
