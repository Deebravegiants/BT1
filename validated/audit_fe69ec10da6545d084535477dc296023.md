### Title
Emporium `runAction` executes arbitrary calls with zero balance accounting when `erc20TokenAddresses` is empty (Min-circuit path), allowing theft of any token balance held by Emporium - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When a `transact()` call targets the Emporium external action with `circomData.erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes to `MainEVMCircuitMin`, which imposes no per-token balance, nullifier, or amount-change constraints at all [1](#0-0) . `EmporiumUpgradeable.runAction` still executes every operation in `EmporiumStack.ops` via `op.endpoint.call{value: op.value}(op.callData)` unconditionally, but its balance-accounting loop is scoped only to `circomData.erc20TokenAddresses`, so an empty array means no token's balance is ever checked before or after the calls [2](#0-1) .

### Finding Description
Broken equality: `tokens leaving Emporium via op.endpoint.call` (any `transfer`/`transferFrom` payload the attacker crafts) `!= sum(-deltaAmountChanges over erc20TokenAddresses)`, because when `erc20TokenAddresses = []` there is no entry for the target token at all, so the right side is vacuously zero/undefined regardless of what the left side does.

Code path:
1. `Hinkal.transact()` calls `hinkalHelper.performHinkalChecks` → `dimensionsCheck` requires `erc20TokenAddresses.length == dimensions.tokenNumber`, `amountChanges.length`, `onChainCreation.length`, `slippageValues.length`, `inputNullifiers.length`, `outCommitments.length` all equal `dimensions.tokenNumber` [3](#0-2) . Setting `dimensions.tokenNumber = 0` makes all these arrays empty and legally consistent.
2. `formInputForCircom` detects `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0` and calls `formInputEmporiumMin`, producing only `{emporiumMessage, timeStamp, calldataHash}` as circuit inputs [4](#0-3) .
3. `MainEVMCircuitMin` only constrains `message <== Poseidon(1)([messageSeed])` — it has zero constraints on tokens, amounts, nullifiers, or merkle roots [5](#0-4) . A valid proof is trivial to produce for any attacker since `messageSeed` is self-chosen.
4. Back in `Hinkal.transact()`, the per-token balance/slippage-diff loop iterates `circomData.erc20TokenAddresses` — with length 0 it never executes, so no check is applied on the Hinkal contract's own balances either [6](#0-5) .
5. `_externalTransact` computes `deltaAmountChanges` as an array of length `erc20TokenAddresses.length` (0) and calls `EmporiumUpgradeable.runAction` [7](#0-6) .
6. Inside `runAction`, `balancesBefore`/`balancesAfter` are computed over the (empty) `erc20TokenAddresses` array, and `verifyWallet` performs no signature check when `stack.signerAddress == address(0)` [8](#0-7) . The ops loop then executes `op.endpoint.call{value: op.value}(op.callData)` unconditionally for every op, independent of `erc20TokenAddresses` [9](#0-8) . The subsequent per-token loop that would normally revert on `balanceChange < 0` (`BalanceChangeShouldBePositive`) also only runs over the empty `erc20TokenAddresses` array, so it never inspects the token that was just moved [10](#0-9) .

Exploit call: attacker calls `Hinkal.transact()` with `dimensions.tokenNumber = 0`, `circomData.erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [{endpoint: <targetToken>, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, amount))}]}))`, and any historically valid `rootHashHinkal`/index and a trivially self-generated `MainEVMCircuitMin` proof. This drains whatever balance of `<targetToken>` (real dust from a prior `LifiExternalAction`/`DepositOnChainUtxosExternalAction`, or any other token accidentally/temporarily held by Emporium) sits at Emporium's address, with zero equality/slippage check ever applied to that token.

Note: the "fake ERC20 deployed by attacker" framing in the question understates the actual severity — the bug is not specific to a self-deployed token. It applies identically to any real ERC20 (e.g., USDC/WETH rounding dust) that happens to sit on Emporium's balance, since the vulnerability is that `erc20TokenAddresses=[]` disables all balance accounting for the Min path regardless of which token is targeted.

None of the listed guards (`onlyAllowedRecipient`, `verifyWallet` with `signerAddress=0`, `dimensionsCheck`, `rootHashExists`, circuit's `inTotal+amountChanges===outTotal`) prevent this, because they are all either bypassable by choosing `tokenNumber=0` (which is explicitly supported by `formInputForCircom`'s Min-path branch) or scoped only to the (attacker-emptied) `erc20TokenAddresses` array.

### Impact Explanation
Critical — direct theft of any ERC20 (or ETH via `value`) balance currently held by the Emporium contract, including in-flight funds left as rounding dust by legitimate prior actions (LiFi swaps, on-chain UTXO deposits) or any token accidentally sent/stuck there. The attack is repeatable for every distinct token/amount sitting at Emporium and costs only gas plus a trivially-generated zero-dimension proof.

### Likelihood Explanation
High feasibility: no privileged role, whitelisted relay, or victim cooperation is required. Preconditions are (1) Emporium holds a non-zero balance of some ERC20 (dust or otherwise) and (2) a `mainEVMCircuitMin` verifier is registered for `(tokenNumber=0, nullifierAmount=0, outputAmount=0, HINKAL_EMPORIUM_ACTION_ID)` — the repo does register such a verifier (`mainEVMCircuitMin0v4.sol`), confirming this zero-dimension Emporium path is a supported production feature, not a hypothetical dimension. Any EOA can generate the trivial proof themselves and repeat the attack whenever dust/residual balance accumulates.

### Recommendation
Do not allow `runAction`/Emporium's ops execution to bypass balance accounting: either (a) require that every ERC20 address touched/transferred by `op.callData`/`op.endpoint` be present in `circomData.erc20TokenAddresses` and enforce the existing `balanceChange` check for it, or (b) for the Min/zero-dimension path, restrict allowed `op.callData` selectors to a safe allow-list that cannot move ERC20/ETH balances (e.g. disallow `transfer`/`transferFrom`/`approve` and any `value > 0` in stateless mode), or (c) compute `balancesBefore/After` over the union of `erc20TokenAddresses` and every token address referenced in `stack.ops`, reverting on any unaccounted decrease.

### Proof of Concept
Hardhat fork test:
1. Deploy Hinkal, HinkalHelper, EmporiumUpgradeable (with a registered `mainEVMCircuitMin` verifier for tokenNumber=0), and a real/mock ERC20.
2. Simulate a legitimate flow (e.g., `DepositOnChainUtxosExternalAction`) that leaves a small residual balance of the ERC20 on the Emporium contract (dust).
3. As an unprivileged attacker EOA, generate a `MainEVMCircuitMin` proof locally (arbitrary `messageSeed`), and call `Hinkal.transact()` with `dimensions = {tokenNumber:0, nullifierAmount:0, outputAmount:0}`, `circomData.erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and one op calling `token.transfer(attacker, dustAmount)`.
4. Assert: before the call, `Emporium` balance of the token == `dustAmount`; after the call, attacker's ERC20 balance increased by `dustAmount` and Emporium's balance decreased to 0 — while `circomData.erc20TokenAddresses.length == 0` throughout, proving no equality (`op.endpoint.call` amount vs `-deltaAmountChanges`) was ever checked.
