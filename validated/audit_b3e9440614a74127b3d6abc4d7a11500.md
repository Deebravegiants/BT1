### Title
Excess native ETH sent to `EvmHost.dispatch()` for fee-token swaps is refunded to `EvmHost` instead of the caller, permanently trapping user funds - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` are `payable` functions that accept native `msg.value` as an alternative to fee-token payment. When `msg.value > 0`, they call `swapETHForExactTokens{value: msg.value}(post.fee, ...)` on the configured Uniswap V2 router but never check or account for any leftover ETH from that swap [1](#0-0) . This is the same bug class as the reported Notional issue: a function accepts `msg.value` on behalf of an external party but does not refund the unspent portion to that party, causing silent loss of funds.

### Finding Description
In `dispatch(DispatchPost)`:
```
if (msg.value > 0) {
    ...
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
}
``` [1](#0-0) 

The same pattern is repeated in `dispatch(DispatchGet)` [2](#0-1) .

Neither call captures the `amounts` return value from `swapETHForExactTokens`, nor does either function forward any leftover ETH back to `_msgSender()`. The refund behavior instead depends entirely on the downstream router. The project's own custom router wrapper, `UniV3UniswapV2Wrapper.swapETHForExactTokens`, does implement a refund — but it sends the leftover ETH to `msg.sender` of *that call*, which is `EvmHost` itself (since `EvmHost` is the direct caller of the router), not the original account that funded the `dispatch()` transaction:
```
if (spent < msg.value) {
    uint256 refund = msg.value - spent;
    IWETH(weth).withdraw(refund);
    (bool success,) = msg.sender.call{value: refund}("");
    if (!success) revert RefundFailed();
}
``` [3](#0-2) 

Because `msg.sender` in the router's context is `EvmHost`, any overpaid ETH is credited back to `EvmHost`'s own balance rather than to the account (EOA, `HyperFungibleToken`, or `WrappedHyperFungibleToken`) that supplied `msg.value` to `dispatch()`. `HyperFungibleToken.send()` and `WrappedHyperFungibleToken.send()` both forward the caller's entire `msg.value` (or the leftover after wrapping) directly into `IDispatcher(_host).dispatch{value: msgValue}(request)` [4](#0-3) , so any user who overestimates the fee (e.g., due to gas-price/exchange-rate drift between calling `quote()` and `send()`) loses the excess ETH permanently.

This is confirmable by contrast with the codebase's own correct pattern elsewhere: `IntentGatewayV2.placeOrder` / `ExtrinsicIntents` explicitly capture the swap's `amounts[0]` return value, subtract it from `msgValue`, and explicitly refund the true remainder to `msg.sender` at the end of the function:
```
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
    order.fees, path, address(this), block.timestamp
);
msgValue -= amounts[0];
...
if (msgValue > 0) {
    _sendValue(msg.sender, msgValue);
}
``` [5](#0-4) 
`EvmHost.dispatch()` does not implement this pattern at all — it has no post-swap accounting or refund step.

### Impact Explanation
Any unprivileged user or application contract that pays dispatch fees with native ETH via `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or indirectly through `HyperFungibleToken.send()` / `WrappedHyperFungibleToken.send()` will lose any ETH sent in excess of the exact amount required to purchase `post.fee`/`get.fee` fee tokens. The excess is not burned but is not returned either — it accumulates in `EvmHost`, representing a direct, permanent loss of user funds with no recovery path exposed to the depositor.

### Likelihood Explanation
High likelihood: `dispatch()` is a core externally-reachable entry point invoked on essentially every cross-chain message dispatch that opts to pay in native token, and exact fee quoting is fragile (dependent on `quote()` estimates and pool price at execution time via `swapETHForExactTokens`), so overpayment by even a small margin is common in practice (e.g. slippage buffers, gas price movement between quote and send, or users intentionally sending round ETH amounts).

### Recommendation
Capture the `amounts` array returned by `swapETHForExactTokens` in both `dispatch(DispatchPost)` and `dispatch(DispatchGet)`, compute the unspent ETH (`msg.value - amounts[0]`), and explicitly refund it to `_msgSender()` before returning — mirroring the pattern already used correctly in `IntentGatewayV2`/`ExtrinsicIntents`.

### Proof of Concept
1. User calls `HyperFungibleToken.send{value: X}(params)` where `X` is intentionally or accidentally larger than the ETH cost of buying `params.relayerFee` fee tokens.
2. `send()` forwards the entire `X` into `IDispatcher(_host).dispatch{value: X}(request)`.
3. Inside `EvmHost.dispatch`, `swapETHForExactTokens{value: X}(post.fee, ...)` swaps only the ETH needed (`spent < X`) and refunds `X - spent` to `msg.sender`, which is `EvmHost` itself, not the original user.
4. The user has permanently lost `X - spent` ETH with no way to reclaim it.
