### Title
Permanent freezing of escrowed multi-token order funds via a single reverting/blacklisting token in `IntentGatewayV2.withdraw()` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.withdraw()` (and its non-Tron counterpart `IntentsBase._withdraw()`) releases all escrowed tokens for an order commitment in a single loop over `body.tokens`. Each iteration performs a direct `transfer`/`safeTransfer` call and reverts the entire transaction (`TransferFailed`) if any single transfer fails. Because escrow release for *all* tokens in the order is bundled into one atomic call with no per-token isolation or fallback, a single non-cooperating token (e.g., an ERC20 that blacklists the beneficiary, is paused, or otherwise reliably reverts on transfer to that address) permanently blocks release of every other, perfectly healthy token escrowed for that same commitment. This mirrors the reported Gearbox `CreditManager` bug class: an operation meant to conclusively resolve/clean up a position is gated on the success of every constituent token transfer, so one broken token transfer leaves the entire position stuck forever instead of being resolved.

### Finding Description
`withdraw()` sets `_filled[body.commitment] = beneficiary` and then, for each token in `body.tokens`, performs: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    ...
    for (uint256 i; i < len;) {
        address token = ...
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();
        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }
        _orders[body.commitment][token] -= amount;
        ...
    }
    ...
}
```

Because `withdraw()` is invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` (dispatched by the destination-chain fill confirmation or a cross-chain cancellation), any revert here causes the entire cross-chain delivery to be rejected. The same atomic-all-or-nothing pattern exists in the non-Tron `IntentsBase._withdraw()`: [2](#0-1) 

Orders can escrow multiple distinct `TokenInfo` entries per commitment (the loop bounds are `body.tokens.length`), so a single order can bundle several unrelated ERC20s. If any one of those tokens has transfer semantics that can permanently fail toward the resolved beneficiary — e.g. a USDC-style blacklist that later flags the beneficiary/solver address, a pausable token that gets paused, or a token that reverts on transfers to certain addresses — every subsequent retry of the identical `RedeemEscrow`/`RefundEscrow` delivery reverts identically, because the escrow accounting (`_orders[body.commitment][token]`) for the failing token is never decremented and the beneficiary/commitment inputs are fixed by the original order. There is no mechanism to skip the broken token, partially settle, or re-route/delete the stuck order the way `_execute`'s dust-sweep path handles leftover balances. This is structurally identical to the reported issue: an all-token-success precondition gates the resolution (deletion/close) of an account/position, so one bad token transfer permanently blocks the resolution of the whole position — freezing funds that would otherwise be perfectly redeemable.

### Impact Explanation
A solver who correctly fills an order, or a depositor whose order is cancelled, can have their entire escrowed bundle of tokens permanently frozen in the `IntentGatewayV2`/`IntentsBase` contract if just one token in the bundle cannot be transferred to the resolved beneficiary. Since `_filled`/`_orders` state for that commitment is never resolved (the whole call reverts), the healthy tokens in the same order are locked indefinitely alongside the broken one — no admin sweep, retry-with-different-beneficiary, or partial-release path exists. This is a permanent freezing-of-funds condition reachable by any order creator or filler who can construct/select a multi-token order.

### Likelihood Explanation
Likelihood is moderate: it requires an order with a heterogeneous token list where at least one token can enter a state that reliably reverts transfers to the fixed beneficiary (blacklist-capable stablecoins, pausable tokens, or tokens with transfer hooks are common in production, e.g. USDC/USDT blacklisting). Since order creation permits specifying arbitrary ERC20 tokens as inputs/outputs, an order creator (malicious or not) can combine a reputable token with a fragile/blacklistable one, or a legitimate token can later become blacklisted for a specific beneficiary address independent of any bridge actor's intent — at which point the entire escrowed bundle for that commitment becomes permanently stuck via this reachable, no-privilege-required code path.

### Recommendation
Do not bundle multiple token releases into a single all-or-nothing transfer loop gated on cross-chain message replay. Options: (1) wrap each token transfer in a try/catch and, on failure, credit the amount to a per-beneficiary/per-token "claimable" balance that can be withdrawn separately later (mirroring the CreditManager fix of not blocking resolution on transfer failure), (2) allow partial finalization so failing tokens don't block the release of succeeding ones and `_filled`/escrow state for successful tokens is still updated, or (3) provide a permissioned/timed escape hatch to redirect or sweep the stuck token amount for a commitment once marked broken, so the associated healthy tokens and the order's resolution state are not held hostage by one uncooperative token.

### Proof of Concept
1. A depositor creates an order (or a solver targets an order) whose escrowed `body.tokens` list contains two tokens: TOKEN_A (a normal ERC20) and TOKEN_B (a token capable of blacklisting, e.g. USDC-style `isBlacklisted`).
2. The order is filled/cancelled normally; Hyperbridge relays the `RedeemEscrow`/`RefundEscrow` request to `onAccept`, which calls `withdraw(body, isRefund)`.
3. Before delivery (or between retries), TOKEN_B's issuer blacklists the `beneficiary` address (a legitimate, permissionless real-world event for centralized stablecoins).
4. `withdraw()` iterates the token list; the `TOKEN_A` transfer would succeed, but the loop reaches `TOKEN_B`'s `transfer` call, which reverts; the function reverts with `TransferFailed`, undoing any state changes in the call.
5. Every subsequent relay attempt of the same request reproduces the identical revert, since the message body, beneficiary, and blacklist state are unchanged — `_orders[body.commitment][TOKEN_A]` remains escrowed and unclaimable forever, alongside the now-unrecoverable `TOKEN_B` balance.
