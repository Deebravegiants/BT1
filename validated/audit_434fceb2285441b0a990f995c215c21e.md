## Title
Fee-on-transfer / deflationary underlying tokens desynchronize escrow accounting in `WrappedHyperFungibleToken.send()`, enabling insolvency of the wrapped-token bridge - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken` (and its upgradeable twin `WrappedHyperFungibleTokenUpgradeable`) locks an underlying ERC20 on the source chain and dispatches a cross-chain message that always encodes the caller-specified `params.amount`, regardless of how many tokens the contract actually received. If the underlying token charges a transfer fee or otherwise delivers less than the nominal amount (a fee-on-transfer/deflationary token), the destination chain unlocks/mints the full requested amount while the source contract only escrowed the reduced (actual) amount — creating an unbacked liability that can eventually leave the contract unable to honor legitimate withdrawals.

### Finding Description
In `send()`, the contract locks tokens via `safeTransferFrom` but never measures the resulting balance change: [1](#0-0) 

The dispatched `Message.amount` field is taken directly from `params.amount` inside `_buildDispatchPost`: [2](#0-1) 

Unlike `IntentGatewayV2`, which explicitly accounts for fee-on-transfer tokens by snapshotting balances before/after `safeTransferFrom` and mutating `order.inputs[i].amount` to the actually-received amount (see `evm/src/apps/IntentGatewayV2.sol` lines 312-328, and the corresponding fee-on-transfer test coverage), `WrappedHyperFungibleToken.send()` performs no such reconciliation. It blindly assumes 1 token requested = 1 token received = 1 token owed cross-chain.

On the receiving side, `onAccept` and `onPostRequestTimeout` also unconditionally call `safeTransfer(beneficiary, message.amount)`, again trusting the message amount rather than verifying actual balance movement: [3](#0-2) 

The identical pattern exists in the upgradeable variant: [4](#0-3) 

Because each `WrappedHyperFungibleToken` deployment is "its own bridge application" holding escrowed underlying balance per the design docs, any persistent gap between the amount promised in outgoing messages and the amount actually escrowed compounds across every send using a fee-charging or rebasing token, since a wrapped deployment could plausibly be configured against any owner-chosen `_underlying` ERC20 via `configure()`.

### Impact Explanation
If the `_underlying` token is a fee-on-transfer or deflationary token (e.g., a Tether-style token with a nonzero transfer fee, or any token with transfer-time deductions), each `send()` call escrows less than the amount that gets promised and eventually unlocked/minted on the destination chain. Over repeated transfers this depletes the contract's real token balance below its outstanding cross-chain liabilities, so later legitimate `onAccept` unlocks or `onPostRequestTimeout` refunds will revert or drain remaining honest users' funds — a permanent freezing/loss-of-funds condition for the wrapped bridge. This matches the report's "Critical/High" pattern of bookkeeping desync from non-standard ERC20 behavior, mapped here onto the wrapped-token lock/unlock bridge path rather than a generic sidechain bridge.

### Likelihood Explanation
Exploitability depends entirely on the owner configuring `_underlying` to a fee-on-transfer or rebasing token via `configure()`; with a standard, well-behaved ERC20 (as apparently intended for the currently deployed instances) this is not triggerable. However, nothing in the contract enforces or validates that `_underlying` is transfer-amount-preserving, so any future or accidental configuration to a fee-charging token immediately exposes this gap on every transfer, with no additional privilege required from the caller (any user calling `send()` triggers the underescrow).

### Recommendation
- **Short term**: Document that `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` must only wrap standard ERC20 tokens with no transfer fees or rebasing behavior, mirroring the recommendation in the referenced report.
- **Long term**: Mirror the `IntentGatewayV2` fix pattern — snapshot the contract's balance of `_underlying` before and after `safeTransferFrom` in `send()`, and encode the *actual received* amount in the dispatched `Message`, not the caller-supplied `params.amount`. Apply the equivalent fix to `WrappedHyperFungibleTokenUpgradeable.send()`.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` = a deflationary ERC20 that burns 1% on every transfer.
2. Alice calls `send({ amount: 1000e18, dest: ... })`. `safeTransferFrom` pulls 1000e18 from Alice but the contract only receives 990e18 (10e18 burned as fee).
3. `_buildDispatchPost` still encodes `amount: 1000e18` in the cross-chain `Message`, and this is what gets committed/dispatched (`sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol:238-243, 266-290`).
4. The destination `HyperFungibleToken`/`WrappedHyperFungibleToken` peer processes `onAccept`, minting/unlocking 1000e18 to the beneficiary — 10e18 more than was actually escrowed on the source chain.
5. Repeating this depletes the source contract's real underlying balance relative to its outstanding message-implied liabilities; a subsequent legitimate `onPostRequestTimeout` refund or unlock for another user can then fail or be paid out of funds that rightfully belong to others, i.e. a shortfall/freeze condition.

    function _buildDispatchPost(HyperFungibleToken.SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(HyperFungibleToken.Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }

    function send(HyperFungibleToken.SendParams calldata params) external payable whenNotPaused {
        uint256 msgValue = msg.value;
        if (_isWeth && msgValue >= params.amount) {
            msgValue = msgValue - params.amount;
            IWETH(_underlying).deposit{value: params.amount}();
        } else {
            IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
        }

        DispatchPost memory request = _buildDispatchPost(params);
        bytes32 commitment;
        if (msgValue > 0) {
            commitment = IDispatcher(_host).dispatch{value: msgValue}(request);
        } else {
            commitment = dispatchWithFeeToken(request);
        }

        emit Sent({
            from: msg.sender,
            to: params.to,
            dest: string(params.dest),
            amount: params.amount,
            commitment: commitment
        });
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
