Based on my review of the actual code, the claim is accurate: `HandleLegacyUserMessage` inserts into `h.savedCallbacks` keyed solely by `msg.Body.MessageID` with no existence check [1](#0-0) , `handleWebAPITriggerMessage` looks up/delivers to whatever callback currently occupies that key [2](#0-1) , and `api.Message.Validate()` only enforces `MessageID` length/null-byte constraints, not uniqueness — the value is fully attacker-chosen [3](#0-2) . Sibling handlers explicitly guard against this exact class of bug: `confidentialrelay`'s request-ID handling and `http_trigger_handler.setupCallback` both reject duplicate/in-flight IDs [4](#0-3) , confirming this is a known-necessary safeguard missing from the legacy capabilities handler. The gateway's `ProcessRequest` entry point routes any legacy `api.Message` (only requiring valid signature/lengths, not per-client MessageID isolation) straight into `HandleLegacyUserMessage` [5](#0-4) , so this is reachable by any unprivileged caller with signing key material able to submit a request to the gateway (i.e., any onboarded gateway client), not requiring node/operator/host access.

Audit Report

## Title
Unprivileged users can hijack another user's WebAPI trigger response via `MessageID` collision in the gateway's legacy handler - ([File: core/services/gateway/handlers/capabilities/handler.go])

## Summary
`HandleLegacyUserMessage` stores a pending user callback in the shared `h.savedCallbacks` map keyed solely by the caller-supplied `msg.Body.MessageID`, with no uniqueness/collision check before insertion. `handleWebAPITriggerMessage` later looks up and delivers the node's response to whichever callback is registered under that key, so a colliding `MessageID` from a different in-flight request results in cross-user response delivery.

## Finding Description
`HandleLegacyUserMessage` unconditionally overwrites `h.savedCallbacks[msg.Body.MessageID]` [1](#0-0) . `api.Message.Validate()` bounds `MessageID` length and disallows trailing null bytes but does not enforce uniqueness or bind it to a session/sender beyond the message signature itself [3](#0-2) . When a node response arrives, `handleWebAPITriggerMessage` matches purely on `msg.Body.MessageID`, deletes and forwards the payload to whichever callback is currently stored there, with no cross-check of requester identity [2](#0-1) . `HandleNodeMessage` only validates that the responding node matches the claimed sender of the node-originated response, not that the response is provenance-bound to a specific user request beyond the raw `MessageID` [6](#0-5) . This is a real gap relative to sibling code: `httpTriggerHandler.setupCallback` explicitly rejects a request when an entry already exists for that ID [4](#0-3) , demonstrating this duplicate-ID protection is a known-necessary safeguard that the legacy `capabilities` handler omits.

## Impact Explanation
If two concurrent legacy WebAPI trigger requests reach the same DON handler instance with the same `MessageID` (whether by accident, by predictable/reused IDs, or by a caller who can influence or observe another caller's ID), the second insertion silently overwrites the first entry in `savedCallbacks`. Whichever request's node response is delivered first is routed to whichever callback currently occupies the map slot, producing cross-user response corruption/leak — an in-scope impact class per the acceptance criteria (cross-user response corruption).

## Likelihood Explanation
Exploitation requires the attacker to submit a legacy request whose `MessageID` collides with a legitimate in-flight request's `MessageID` within the callback TTL window (`defaultCallbackMaxAgeSec` = 120s) [7](#0-6) . This requires either knowledge/prediction of another caller's `MessageID` or a caller/environment where `MessageID`s are not guaranteed to be cryptographically random/unique (e.g., sequential IDs, idempotency keys reused by client tooling, or a caller with multiple co-tenant users routed through the same DON handler). The report itself acknowledges this precondition (randomness/uniqueness guarantee of `MessageID`) was not conclusively verified beyond the length/null-byte checks in `Validate()`, and no code was found elsewhere that enforces `MessageID` uniqueness or randomness at submission time, so the vulnerability is real but its practical exploitability depends on external factors (how calling systems generate `MessageID`s) that are outside this codebase's control in the general case. Still, the structural flaw — a shared mutable map keyed by attacker-controlled input in the same handler instance used across all callers targeting a DON, with no duplicate-ID rejection — is confirmed and directly analogous to the protection already implemented in adjacent code (`confidentialrelay`, v2 `http_trigger_handler`).

## Recommendation
- Reject `HandleLegacyUserMessage` requests when a `savedCallbacks` entry already exists for the given `MessageID`, mirroring `httpTriggerHandler.setupCallback`'s duplicate-ID rejection.
- Bind the saved callback to additional provenance (e.g., sender address derived from the message signature, since `Validate()` already populates `m.Body.Sender`) rather than relying solely on the caller-supplied `MessageID` as the map key.
- Consider namespacing `savedCallbacks` keys by `(Sender, MessageID)` instead of `MessageID` alone.

## Proof of Concept
1. Craft two `api.Message` legacy WebAPI-trigger requests signed by two different keys but sharing the same `MessageID` value, targeting the same DON.
2. Call `handler.HandleLegacyUserMessage` for request A, then for request B (same `MessageID`) — confirm via `handler.savedCallbacks` that B's callback has overwritten A's entry (`core/services/gateway/handlers/capabilities/handler.go:411-414`).
3. Simulate a node response for that `MessageID` via `handler.HandleNodeMessage`; confirm the response is delivered to B's callback (`cb2`) even though A's request (`cb1`) is the one still "in flight" from the caller's perspective, verifying cross-user response confusion. This can be implemented as a Go unit test extending the existing `TestHandlerReceiveHTTPMessageFromClient` test in `core/services/gateway/handlers/capabilities/handler_test.go`.

func (h *handler) HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {

	if err != nil {
		return err
	}
	if msg.Body.Sender != nodeAddr {
		return errors.New("message sender mismatch when reading from node ")
	}
	start := time.Now()
	switch msg.Body.Method {
	case MethodWebAPITrigger:
		err = h.handleWebAPITriggerMessage(ctx, msg, nodeAddr)
	case MethodWebAPITarget, MethodComputeAction, MethodWorkflowSyncer:
		err = h.handleWebAPIOutgoingMessage(ctx, msg, nodeAddr)
	default:
		err = fmt.Errorf("unsupported method: %s", msg.Body.Method)
	}
	h.metrics.recordHandleDuration(ctx, time.Since(start), msg.Body.Method, err == nil)
	return err
}
