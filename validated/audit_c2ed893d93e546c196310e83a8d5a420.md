### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while `shop` (and `topic`, `webhook_id`, `api_version`) are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to build the `WebhookMetadata` passed to the host application's handler, so the "shop the app processes work for" is never bound to the value actually verified by the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors are parsed straight from HTTP headers with no cryptographic binding: [2](#0-1) .

`HmacValidator.validate` computes and compares the HMAC only over `verifiable_query.to_signable_string`, i.e. the raw body: [3](#0-2) .

`Registry.process` checks that HMAC, then immediately forwards `request.shop` — the unverified header — into `WebhookMetadata` delivered to the app's handler: [4](#0-3) . `WebhookMetadata.shop` is a plain `String` field with no further validation: [5](#0-4) .

This breaks the identity binding: `shop asserted in the "x-shopify-shop-domain" header == shop actually covered by the verified HMAC`. Because the app's `client_secret` (`api_secret_key`) is shared across every shop that installs the app, any merchant who installs the app can obtain a genuine `(raw_body, hmac)` pair for their own shop by triggering any real webhook event. Since the header carrying the shop domain isn't part of the signed payload, that same attacker can replay the identical body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) with a victim shop's domain. `Registry.process` will validate the HMAC successfully (it only checks the body) and hand the host app a `WebhookMetadata` claiming to be from the victim shop, carrying attacker-controlled body content.

The gem's own documentation instructs consuming apps to key business logic directly off `data.shop` (e.g. `shop_domain: data.shop`) without any additional verification, since the gem's contract implies `process` already validated the request's authenticity end-to-end: [6](#0-5) .

### Impact Explanation
This is a cross-tenant integrity issue: an attacker who is a legitimate (but malicious) merchant of the app can inject forged webhook data attributed to a different, victim shop into the host application's per-tenant processing pipeline (e.g., queued jobs keyed by `shop_domain`), because the gem never binds the header-derived `shop` to the HMAC-verified bytes. This matches the "Critical - cross-tenant access" impact category, since the root cause is entirely within this gem's `Request`/`Registry`/`HmacValidator` code, not a host-application misuse of a documented API — the documented, recommended usage pattern is exactly what's vulnerable.

### Likelihood Explanation
High. Any developer/merchant with the ability to install the app (or otherwise obtain one valid raw-body+HMAC pair, which is trivial via any legitimate webhook their own store triggers) can replay it with a modified `shop-domain` header using an off-the-shelf HTTP tool. No special privileges, secrets, or race conditions are required.

### Recommendation
Include the shop domain (and topic) in the signable string / verification step, or otherwise cryptographically bind `request.shop` to the request before it is trusted — e.g., require the app to independently confirm that a session/webhook subscription actually exists for `request.shop` before dispatching to the handler, or extend `HmacValidator`/`Request#to_signable_string` to incorporate the `shop-domain` and `topic` headers so tampering invalidates the HMAC.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers any subscribed webhook (e.g. `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header sent by Shopify — this HMAC is valid because it's computed with the app's shared `client_secret`.
2. Attacker replays this exact `raw_body` + `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which only checks the raw body against the HMAC — this succeeds: [7](#0-6) .
4. `Registry.process` then builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` using the forged `shop-domain` header value and dispatches it to the app's handler as if it genuinely originated from `victim.myshopify.com`: [8](#0-7) .
