### Title
`Webhooks::Request#shopify_header` prefers unprefixed `shopify-*` headers over `x-shopify-*`, letting an attacker forge the `shop` of an otherwise genuinely-HMAC-signed webhook - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#shopify_header` resolves `@headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]`, and `Utils::HmacValidator.validate` only checks the HMAC over `@raw_body` using the app's single, shop-agnostic `Context.api_secret_key`. Because the HMAC never binds to a specific shop, an attacker who owns a real (dev) shop with the app installed can capture a genuinely-signed webhook and replay it directly to the app's public webhook endpoint with an extra, unprefixed `shopify-shop-domain` header, causing `Request#shop` to resolve to an arbitrary victim shop domain while the HMAC still validates.

### Finding Description
The broken binding: `shop value the HMAC-holder actually owns (from Shopify's genuine x-shopify-shop-domain header) == shop value returned by Request#shop`. This must always hold for the webhook to be safely attributed to a tenant, but it does not:

- `Request#shop` calls `shopify_header("shop-domain")`, defined as:
`@headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]` [1](#0-0) 
- `#initialize` only checks that *either* `shopify-#{name}` or `x-shopify-#{name}` is present, it never rejects the case where *both* are present with different values: [2](#0-1) 
- `HmacValidator.validate`/`validate_signature` compute the HMAC solely over `to_signable_string` (`@raw_body`) using `Context.api_secret_key` (the app's single client secret, identical for every shop that has the app installed) - the shop identity is never part of the signable string: [3](#0-2) [4](#0-3) 
- `Registry.process` trusts `request.shop` directly to build `WebhookMetadata` passed to the app's handler, after only checking the HMAC (not any shop binding): [5](#0-4) 
- No `ShopValidator.sanitize!` or equivalent shop-domain/tenant check is ever applied to `Webhooks::Request#shop` (confirmed by search: `ShopValidator` is only used in OAuth/token-exchange/storefront code, never in the webhooks path).

Exploit flow: the attacker creates their own development shop, installs the app, and triggers a real webhook (e.g. `orders/create`, `app/uninstalled`, or a mandatory `shop/redact`) so Shopify sends a genuinely HMAC-signed request to the attacker's own receiving server, with headers such as `x-shopify-hmac-sha256`, `x-shopify-topic`, and `x-shopify-shop-domain: attacker-shop.myshopify.com`. Since the attacker fully controls their own server, they capture the raw body and the genuine HMAC unchanged, then send this exact body + HMAC directly to the target app's public webhook endpoint, adding one extra header: `shopify-shop-domain: victim-shop.myshopify.com`. When the app constructs `Webhooks::Request.new(raw_body:, headers:)` from this request, `shopify_header("shop-domain")` returns the unprefixed value (`victim-shop.myshopify.com`) because it is checked first, while `hmac` is unaffected (it comes from whichever HMAC header pair is used, unchanged, still valid because `@raw_body` and secret are unchanged). `HmacValidator.validate` passes because the signature only covers `@raw_body`. `Registry.process` therefore invokes the app's webhook handler believing the event is for `victim-shop.myshopify.com`, even though the actual signer/owner of that HMAC is `attacker-shop.myshopify.com`.

### Impact Explanation
This breaks cross-tenant isolation: the app's webhook handler code (built on this gem, following the gem's documented API of trusting `request.shop`) will process the attacker-originated event as if it belongs to an arbitrary victim shop of the attacker's choosing. Depending on what the handler does with `WebhookMetadata#shop`/`#body`, this can mean: injecting attacker-controlled data into a victim tenant's records, or - more severely - triggering mandatory-topic handlers like `shop/redact`, `customers/redact`, or `app/uninstalled` against a victim shop's local state (deactivating tokens, purging data) despite the attacker never having any relationship to the victim shop. This is repeatable against any victim shop identifier string the attacker chooses (Shopify never enforces that the domain in the injected header corresponds to a shop that installed the app), and it requires no leaked secret. Matches the Critical "cross-tenant access" category.

### Likelihood Explanation
Preconditions are low-cost and fully within the attacker's stated capabilities: create a free/dev Shopify store, install the target app, trigger any webhook topic, capture the genuine raw HTTP request their own server receives, and replay it with one added header to the app's public webhook URL (which is an internet-reachable endpoint by design). No credentials, secrets, or victim cooperation are required. The only host-app dependency is that it passes through the raw incoming headers to `Webhooks::Request.new` without deduplicating/rejecting header-name collisions - which is the standard, documented usage pattern shown in `docs/usage/webhooks.md`.

### Recommendation
In `Webhooks::Request#initialize`/`#shopify_header`, do not silently prefer one header form. Either: (1) only ever accept the canonical `x-shopify-*` headers (reject/ignore any unprefixed `shopify-*` variant), or (2) explicitly reject the request (raise `Errors::InvalidWebhookError`) if both `shopify-#{name}` and `x-shopify-#{name}` are present and disagree, for every field derived via `shopify_header`, not just `shop-domain`.

### Proof of Concept
```ruby
# test/webhooks/request_test.rb (new test)
def test_shopify_header_precedence_allows_shop_spoofing
  raw_body = '{"foo":"bar"}'
  headers = {
    "x-shopify-hmac-sha256" => "genuine-hmac-signed-with-app-secret",
    "x-shopify-topic" => "orders/create",
    "x-shopify-shop-domain" => "attacker-shop.myshopify.com", # genuine, HMAC-holder's real shop
    "shopify-shop-domain" => "victim-shop.myshopify.com",     # attacker-injected, unprefixed
  }

  request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

  # Broken binding demonstrated: request.shop does NOT equal the x-shopify- (genuine) value
  assert_equal "victim-shop.myshopify.com", request.shop
  refute_equal "attacker-shop.myshopify.com", request.shop

  # HMAC validation is unaffected by shop, so it would still pass with the real secret:
  ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "real_secret", ...)
  # stub compute_signature to match "genuine-hmac-signed-with-app-secret" for raw_body
  # assert Utils::HmacValidator.validate(request) == true while request.shop == victim shop
end
```
This confirms `request.shop` resolves to the attacker-injected, unprefixed value while a genuinely-computed HMAC (bound only to the shared app secret and body, not to shop identity) still validates.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
