### Title
Webhook topic/shop identity not covered by HMAC verification allows cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then trusts the unauthenticated `shop-domain` and `topic` headers to route and label the event for the host application. [1](#0-0)  The signable content computed for HMAC verification is defined as the raw body only, excluding `topic`, `shop-domain`, `api-version`, and `webhook-id`. [2](#0-1) 

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature over `verifiable_query.to_signable_string` and HMAC-compares it to the value supplied in the `hmac` accessor. [3](#0-2)  For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`; `shop`, `topic`, `api_version`, and `webhook_id` are read straight off client-supplied HTTP headers and are never part of the signed material. [4](#0-3) 

`Registry.process` treats a valid body HMAC as sufficient authentication, then immediately uses the unauthenticated `request.topic` to select a handler and forwards the unauthenticated `request.shop` into `WebhookMetadata` given to the app: [1](#0-0)  The documentation explicitly tells integrators that `data.shop` is "The shop domain of the webhook" and encourages using it directly to route work per-tenant (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), with no mention that `shop` must be independently reconciled against a known/installed shop list. [5](#0-4) 

The broken binding, stated as an equality that should hold but doesn't:
`HMAC-authenticated bytes (raw_body)` ≠ `bytes acted upon for tenant identity (shop-domain / topic headers)`.

Exploit path (no `api_secret_key`, access token, or other privileged credential required):
1. An ordinary internet user installs the target app on their own store (a normal, unprivileged action any Shopify merchant can perform).
2. Shopify sends the attacker's own app instance a legitimate webhook: `raw_body` + a correctly computed `X-Shopify-Hmac-Sha256` for that body, plus headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` and `X-Shopify-Topic: <topic>`.
3. The attacker captures this genuine `(raw_body, hmac)` pair — this requires no secret, since the attacker is a legitimate recipient of the webhook.
4. The attacker sends a new HTTP POST directly to the app's public webhook endpoint (the endpoint the app owner exposes per the gem's documented usage) with the *same* `raw_body` and `hmac`, but with `X-Shopify-Shop-Domain` swapped to a victim shop's domain (and/or a different `X-Shopify-Topic`).
5. `Utils::HmacValidator.validate` succeeds because it only checks the body against the HMAC — headers are irrelevant to the check. [6](#0-5) 
6. `Registry.process` dispatches to the handler for the attacker-chosen topic and passes `shop: request.shop` (the forged victim shop) straight to the app's business logic. [7](#0-6) 

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook authenticity: an attacker who legitimately receives one webhook for their own shop can inject fabricated webhook events attributed to an arbitrary victim shop and/or arbitrary topic, with attacker-controlled body content (since they choose which of their own real webhooks — and thus which body payloads — to replay, and can drive the body content by taking actions in their own store to trigger events of their choosing). Downstream app logic that trusts `data.shop` to select tenant-scoped resources (customer records, orders, credentials, background jobs keyed by shop) can be manipulated to write/act under the identity of a shop the attacker does not own — a cross-tenant access primitive achieved entirely through the gem's own `Request`/`Registry` code and its documented "trust `data.shop`" contract, without any credential, access token, or `client_secret`.

### Likelihood Explanation
Likelihood is high for apps following the documented pattern verbatim: the docs present `data.shop` as an implicitly trustworthy shop identifier immediately usable for tenant routing/queuing, with no guidance to reconcile it against an app's known installed-shop table. [8](#0-7)  Any user capable of installing the app on a shop they control (a low bar — any Shopify merchant) can obtain the raw ingredients (valid body+HMAC pairs) needed for the forgery, and the forged request is a single unauthenticated HTTP POST to a publicly reachable endpoint.

### Recommendation
Bind `shop`, `topic`, `api_version`, and `webhook_id` into the HMAC-signable content wherever feasible, or — since Shopify's own `X-Shopify-Hmac-Sha256` signature is computed over the body only and this cannot be changed by the gem — have `Webhooks::Request`/`Registry.process` require and expose an explicit, separate verification step so integrators are not encouraged to trust `data.shop` blindly. At minimum, update `docs/usage/webhooks.md` to state unambiguously that `data.shop` and `data.topic` are unauthenticated header values not covered by the HMAC check, and instruct integrators to always cross-check `data.shop` against their own store of shops that have completed OAuth/installed the app before acting on webhook data.

# typed: strict
# frozen_string_literal: true

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
