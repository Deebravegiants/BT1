### Title
Relay-fee bypass via zero-delta token leg breaks the "relay not paid" invariant - (File: contracts/Hinkal.sol)

### Summary
`Hinkal._internalTransact` is supposed to guarantee that whenever a caller names a `relay` in `CircomData.relay`, that relay is actually compensated out of at least one withdrawal before the transaction can succeed. The guard that enforces this, `hasPaidToRelay`, is set to `true` merely by *entering* the withdrawal branch for any token index whose `relay != address(0)` — without checking that the computed `relayFee` (or the withdrawn amount) is non-zero. A caller can therefore satisfy the "relay not paid" check with a token leg whose delta is exactly `0`, while routing all real value through the fee-free deposit branch, so the relay is compensated nothing for a transaction it submits and pays gas for.

### Finding Description
In `contracts/Hinkal.sol`, `_internalTransact` iterates every `erc20TokenAddresses[i]` and computes `deltaAmountChange = _calculateDeltaAmount(circomData, i)`: [1](#0-0) 

- If `deltaAmountChange > 0` (a deposit), no fee logic runs at all — deposits are fee-free by design.
- Otherwise (i.e. `deltaAmountChange <= 0`, including exactly `0`) the code enters the withdrawal branch, computes `sumAbs = uint256(-deltaAmountChange)` (which is `0` when the delta is `0`), and — critically — sets `hasPaidToRelay = true` unconditionally whenever `circomData.relay != address(0)`, regardless of whether `relayFee` ends up being non-zero: [2](#0-1) 

The final invariant check only verifies that the flag was raised, not that any value was actually transferred to the relay: [3](#0-2) 

`circomData.amountChanges` (and thus a `0` value for an unused index) is fully caller-chosen and is only constrained to be within `MAX_AMOUNT` bounds; there is no requirement that a "withdrawal" leg be non-zero: [4](#0-3) 

`onChainCreation` is disallowed only for internal transactions (so the "delta forced to 0" trick via `onChainCreation` doesn't add anything here), but a legitimately signed `amountChanges[i] == 0` for an extra, unrelated token index is sufficient — `checkOnchainCreation` never forbids a zero `amountChanges` entry outside the `onChainCreation` path: [5](#0-4) 

This is the same bug class as the referenced report: a party constructs a transaction with a trivial/zero-valued leg specifically to satisfy an on-chain "fee was paid" check while avoiding paying any real fee on the value that actually moves.

### Impact Explanation
This breaks the intended equality "relay named ⇒ relay is compensated from the transaction it submits." A user can deposit an arbitrary amount of a real token (fee-free by design) while padding `erc20TokenAddresses`/`amountChanges` with one extra token index whose delta is `0`, naming any `relay` address. The `0`-delta leg satisfies `hasPaidToRelay`, so the whole transaction passes with the relay receiving zero compensation despite paying gas to submit it and despite the contract's own accounting believing the relay-payment invariant held. This is theft/permanent loss of protocol relay fees the relay was entitled to for facilitating the transaction — matching the "theft or permanent freezing of protocol/relay fees" High-impact category.

### Likelihood Explanation
The attacker only needs control over the calldata they sign off-chain (spending key owner) — a normal, unprivileged capability. No admin, relay, or oracle assumptions are needed; the flat/variable fee computation and dummy-leg construction are entirely user-controlled and require no interaction with `calldataHash`/`signedMessageHash` internals beyond values the user already signs.

### Recommendation
Track whether an actual non-zero amount was transferred to the relay, not just whether the branch was entered. E.g., only set `hasPaidToRelay = true` when `relayFee > 0` (or, more strictly, only count withdrawal legs where `sumAbs > 0`), and/or require the relay's fee/compensation to be validated against a non-zero minimum, independent of how many token indices are present.

### Proof of Concept
1. User builds a `CircomData` with `erc20TokenAddresses = [TokenA, TokenB]`.
2. `TokenA`: `amountChanges[0] = +1000` (a large deposit; `externalActionData.externalAddress == msg.sender`).
3. `TokenB`: `amountChanges[1] = 0`, `onChainCreation[1] = false` — a legitimate, signable zero "withdrawal" leg.
4. `circomData.relay = relayAddress` (some third-party relay expecting compensation), `feeStructure` set normally.
5. In `_internalTransact`: index 0 goes to the deposit branch (no fee). Index 1 goes to the else branch with `sumAbs = 0`, `relayFee = 0`, but `hasPaidToRelay = true` is still set because `circomData.relay != address(0)`.
6. Final `require(circomData.relay == address(0) || hasPaidToRelay, "relay not paid")` passes.
7. Result: the relay submitted/paid gas for a transaction depositing 1000 units of TokenA and received `0` compensation, even though `circomData.relay` was set — violating the intended fee-payment guarantee.
