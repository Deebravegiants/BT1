The `handle_unsigned` extrinsic in `pallet-state-coprocessor` accepts a caller-supplied `address: Vec<u8>` field with no signature verification (it is dispatched via `ensure_none(origin)` / validated in `ValidateUnsigned::validate_unsigned`), and that raw attacker-chosen bytes are directly converted into an `AccountId` and credited with minted `ReputationAsset` tokens, proportional to the batch's verified GetResponse byte size. This is a legitimate analog: an unauthenticated caller can submit a validly-proven `GetRequestsWithProof` batch (which anyone with a real state/membership proof can construct) but freely choose *who* receives the reputation-token mint by setting `address` to any 32 bytes, including their own account or a third party's — this is exactly the "unauthenticated identity data injection into a privileged mint path" pattern the CVE describes for the Rancher webhook (attacker supplies identity data that ends up asserted as ground truth for a privileged operation).

### Title
Unauthenticated `address` field in `pallet-state-coprocessor::handle_unsigned` lets any caller redirect ReputationAsset minting to an attacker-chosen account - (File: modules/pallets/state-coprocessor/src/impls.rs)

### Summary
`GetRequestsWithProof::address` is fully attacker-controlled, unsigned data that is used, without any cryptographic binding to the message content or to the entity that produced the proofs, as the recipient identity for a reputation-token mint.

### Finding Description
`handle_get_requests` in `modules/pallets/state-coprocessor/src/impls.rs` (lines 62-186) verifies the source-chain membership proof and destination-chain storage proof for a batch of `GetRequest`s, but performs no verification whatsoever on the `address` field of `GetRequestsWithProof`. [1](#0-0) 
That struct is submitted through the pallet's `handle_unsigned` call, which only checks `ensure_none(origin)` — i.e. it is explicitly permissionless/unsigned: [2](#0-1) 
`ValidateUnsigned::validate_unsigned` re-executes `handle_get_requests` for mempool admission but likewise applies no check to `address`, only building a `provides` tag from the request hashes: [3](#0-2) 
After proof verification succeeds, the raw `address` bytes are converted directly into an `AccountId` and minted `ReputationAsset` tokens scaled by the total verified response bytes: [4](#0-3) 
Nothing ties `address` to the actual proof submitter, to a signature, or to any other authenticated identity — any account bytes the caller writes into the extrinsic become the mint recipient, provided a rate is configured and the batch contains valid proofs.

### Impact Explanation
This mirrors the CVE's bug class: an unauthenticated actor supplies identity data in an admission-path payload, and that data is trusted as ground truth for a privileged side effect (here, reputation-asset minting rather than object creation, but the same "attacker names the beneficiary of a privileged action" pattern). A relayer that legitimately delivers proofs can mint reputation to any address, including addresses it does not control being credited on its behalf, or diverting rewards away from the actual proof-fetching entity to itself. Because `pallet-messaging-incentives`' own `relayer_for` logic recovers the relayer from a *signed* `signer` field on `Message::Request`/`Message::Response` (verified via `verify_and_get_sr25519_pubkey`), the deliberate contrast shows the intended design was to cryptographically bind minting to the actual submitter — `pallet-state-coprocessor` instead trusts a bare `Vec<u8>` field with no such binding, which is the mitigating design broken here. [5](#0-4) 

### Likelihood Explanation
High reachability: `handle_unsigned` is unsigned and explicitly designed to be callable by any network participant with valid proofs (the whole point of the "unsigned/free" ISMP message design documented in the pallet). The only prerequisites are a nonzero `MintPerByte` rate (a governance-controlled but expected production configuration) and any valid `GetRequestsWithProof` batch, which any relayer already producing real traffic can construct while simply substituting an arbitrary `address`.

### Recommendation
Bind the reputation-mint recipient to a cryptographically verified identity rather than a bare unsigned field — e.g., require and verify a signature over the `GetRequestsWithProof` payload (mirroring `pallet-messaging-incentives::relayer_for`), or derive the recipient from the transaction's signed origin instead of accepting caller-supplied `address` bytes when this extrinsic is invoked unsigned.

### Proof of Concept
1. Governance sets `pallet_messaging_incentives::MintPerByte` to a nonzero rate (as intended for production reward accrual).
2. Any relayer (or any party who can construct valid source/response proofs for real GET requests) submits `pallet_state_coprocessor::Call::handle_unsigned` with a `GetRequestsWithProof` whose `requests`/`source`/`response` are all legitimately valid, but whose `address` field is set to an attacker-controlled 32-byte account of their choosing rather than the account that actually produced/paid for the proofs.
3. `handle_get_requests` (`modules/pallets/state-coprocessor/src/impls.rs:157-186`) mints `rate * total_bytes` of `ReputationAsset` to that attacker-chosen `address`, with no check that it corresponds to any authenticated submitter — demonstrated by the existing test `valid_message()` in `modules/pallets/testsuite/src/tests/pallet_state_coprocessor.rs:78-91`, which shows `address` is accepted as arbitrary bytes (`vec![0u8; 32]`) with no validation path exercised against it.

	/// Recover the relayer's account from the sr25519 signature on a
	/// `Message`'s `signer` field. Returns `None` if the message has
	/// no signer (e.g. consensus messages) or the signature is bad.
	fn relayer_for(message: &Message) -> Option<T::AccountId> {
		let (signer, signed) = match message {
			Message::Request(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			Message::Response(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			_ => return None,
		};
		Signature::decode(&mut &signer[..])
			.ok()?
			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}
