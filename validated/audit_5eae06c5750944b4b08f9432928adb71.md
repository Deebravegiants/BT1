### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook using an HMAC that is computed only over the raw HTTP body, while the `shop` value that identifies which tenant/merchant the event belongs to is read from an unsigned HTTP header. `Registry.process` trusts this unauthenticated `shop` value and hands it straight to the app's webhook handler, breaking the equality "HMAC-verified bytes == bytes the app acts on."

### Finding Description
`Utils::HmacValidator.validate` verifies the signature against `verifiable_query.to_signable_string`. For webhooks, `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is derived independently from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never included in the signable string and therefore never covered by the HMAC check: [2](#0-1) 

`Registry.process` validates the HMAC over the body, then immediately trusts `request.shop` (and other headers) to dispatch the event to the app's handler as authenticated tenant metadata: [3](#0-2) 

Because the `shop-domain` header sits outside the HMAC's protected byte range, any (body, HMAC) pair that is valid for one tenant remains cryptographically valid after the `shop-domain` header is swapped for a different tenant's domain. This is exactly the bug class described in the report: a field acted upon (`shop`) that is not covered by the integrity check (`HMAC`), so the equality "verified identity == identity acted upon" fails. The app's webhook handler receives `WebhookMetadata` built from this unauthenticated `shop`, so any per-tenant logic keyed off `data.shop` (looking up a session/store, writing merchant records, honoring `shop/redact` or mandatory GDPR topics, etc.) can be misattributed to a shop the attacker does not own.

### Impact Explanation
This breaks the shop-to-signature binding and enables cross-tenant confusion in the host application, since a request with a genuine HMAC (over some captured/legitimately-obtained body) can be relabeled to a victim shop merely by changing an unauthenticated header. Per the given severity classification, unauthorized cross-tenant access/action attribution driven through this library's own webhook verification logic is a Critical-class outcome, since apps rely on this gem to establish that a webhook's declared shop is trustworthy once HMAC validation succeeds.

### Likelihood Explanation
Exploitation requires only a network-reachable webhook endpoint (webhook endpoints are, by design, public/unauthenticated aside from the HMAC check) plus one previously valid (body, HMAC) pair — for example a webhook the attacker legitimately receives after installing the app on their own store, since the HMAC key (`api_secret_key`/`client_secret`) is shared across all shops that install the same app, not per-shop. No access to the target's credentials, session, or the app's `client_secret` is required, so this is reachable by a normal, unprivileged internet user/merchant.

### Recommendation
Bind the `shop` (and any other tenant-identifying header the app relies on) into the value that is HMAC-verified, or otherwise independently authenticate the `shop-domain` header against a set of shops for which the app holds a valid session before dispatching to a handler — mirroring the report's mitigation pattern of closing the gap between what is verified and what is subsequently trusted/acted upon.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook, capturing `raw_body` and its valid `x-shopify-hmac-sha256` value (computed by Shopify using the app's shared `client_secret`).
2. Attacker resends the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `raw_body` against the HMAC.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) dispatches to the handler with `shop: "victim.myshopify.com"` even though the payload/HMAC never originated from Shopify for that shop, causing the app to process/attribute the event as belonging to the victim tenant.
