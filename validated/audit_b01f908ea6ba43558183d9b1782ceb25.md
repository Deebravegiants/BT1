### Title
`transactionSigner.signTransaction` / `messageSigner.signMessage` sign with any `walletAccount` supplied by the caller, without verifying it belongs to the requesting/authorized context - ([File: features/tx-signer/src/api/index.ts])

### Summary
The `repayLoan` bug in the report is a class of vulnerability where a privileged operation (`safeTransferFrom`) is executed against a *caller-controllable* identity (`_loan.borrower`) instead of the actual invoking party (`msg.sender`), with no check that the two match. The direct analog in the Hydra wallet SDK is the transaction/message signing surface: `transactionSignerApi.signTransaction` and `messageSigner.signMessage` accept a `walletAccount` parameter (either a `WalletAccount` object or a plain string name) directly from the caller and use it to select the signing key, without validating that this account is the one the calling context (e.g. a connected dApp origin, or the active session) is authorized to act on behalf of.

### Finding Description
`transactionSignerApi.signTransaction` resolves the `walletAccount` parameter and forwards it straight to the signer: [1](#0-0) 

The same pattern exists in `messageSigner.signMessage`, which normalizes a string account name into a `WalletAccount` instance from `walletAccountsAtom` and signs with it — again with no origin/authorization check tying the requested account to the caller: [2](#0-1) 

Both `TransactionSigner.signTransaction` and `SeedBasedTransactionSigner.signTransaction` simply use whatever `walletAccount` is passed to derive the signing key (`walletAccount.index`, `walletAccount.seedId`), with no cross-check against the account(s) actually granted to the request's origin: [3](#0-2) [4](#0-3) 

Separately, the codebase *does* have a proper authorization/isolation primitive for dApp connections — `@exodus/connected-origins`, which tracks per-origin trust and connected accounts and is meant to gate what an origin can act as: [5](#0-4) [6](#0-5) 

However, the signing APIs (`transactionSignerApi`, `messageSignerApi`) are independent modules that do not depend on or consult `connectedOrigins`/`connectedAccountsAtom` at all — their dependency lists only include the signer and `walletAccountsAtom`: [7](#0-6) [8](#0-7) 

Because the SDK API surface flattens all feature APIs into a single namespace exposed over the RPC/multi-process bridge (`libraries/browser-extension-rpc`, `libraries/sdk-rpc`) to the UI process: [9](#0-8) 

any caller with access to that RPC surface (e.g. a compromised/malicious UI-side context, or any code path that can reach `exodus.transactionSigner.signTransaction` / `exodus.messageSigner.signMessage`) can supply an arbitrary `walletAccount` (by name or object) and obtain a signature for an account other than the one that context is actually connected/entitled to — exactly mirroring the `repayLoan` pattern of trusting a caller-supplied identity for a sensitive operation instead of validating it against the true caller's authorization.

### Impact Explanation
If the RPC/API boundary that exposes `transactionSigner`/`messageSigner` is reachable by less-privileged code (e.g. content-script/dApp-facing bridge, or any feature that itself doesn't enforce connected-origin scoping), an attacker can request signing on behalf of *any* wallet account known to the wallet (not just the one connected/consented to by the user for that origin), potentially resulting in unauthorized transaction signing or message signing that leaks funds or approves actions from an account the origin was never granted access to. This matches the report's core impact class: unauthorized action performed against an account that did not authorize the caller.

### Likelihood Explanation
Likelihood depends on how the platform-specific integration (desktop/mobile/extension) wires the RPC surface and whether it interposes its own origin-scoping/consent-UI in front of `transactionSigner`/`messageSigner` before exposing them to dApp-facing code — this wiring is not present in the Hydra monorepo excerpts examined here, so it's uncertain whether downstream consumers add this check outside of Hydra. Within Hydra itself, however, the `transactionSigner`/`messageSigner` API modules as defined have no such check, and `connectedOrigins` is a separate, optional feature that is not wired as a dependency of the signer APIs.

### Recommendation
Ensure any code path that exposes `transactionSigner.signTransaction` / `messageSigner.signMessage` to origin/session-scoped or less-trusted callers validates that the requested `walletAccount` is among the accounts the calling origin/session is actually connected to and authorized to use (e.g. cross-check against `connectedOrigins.getConnectedAccounts({ origin })` or the caller's session-bound active account) before invoking the signer, rather than trusting the `walletAccount` value supplied in the call parameters.

### Proof of Concept
Not directly executable from the indexed context — no wiring was found in this repo connecting the RPC/dApp-facing bridge to `transactionSigner`/`messageSigner` with an origin check in between (only the internal API modules were found, which accept `walletAccount` unconditionally). This is a structural/config gap analysis rather than a demonstrated exploit chain; confirming exploitability requires inspecting the platform-specific (extension background/content script) code that decides which SDK methods are exposed to which processes/origins, which is outside what the indexed Hydra monorepo content covers. If a Devin session with full repo/platform access is needed to trace this exposure end-to-end, that would need to be done outside of this ask-only analysis.

  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }

import { createRPCClient, RPC } from '@exodus/sdk-rpc'
import PortTransport from './port-transport.js'
import RPCManager from './rpc-manager.js'
import RuntimePort from './runtime-port.js'

const DEFAULT_PORT_NAME = 'app'

const createRpc = ({ port, methods, serialize, deserialize, onData }) => {
  const transport = new PortTransport({ port })
  const rpc = new RPC({ transport, serialize, deserialize })

  if (onData)
    transport.on('data', (data) => {
      onData(typeof data === 'string' ? deserialize(data) : data)
    })

  if (methods) {
    rpc.exposeMethods(methods)
  }

  return rpc
}

export const createUiRpc = ({
  name = DEFAULT_PORT_NAME,
  methods,
  serialize,
  deserialize,
  onData,
}) => {
  const port = new RuntimePort({ name })
  const rpc = createRpc({ port, methods, serialize, deserialize, onData })
  return createRPCClient(rpc)
}
