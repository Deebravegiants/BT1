### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant/handler dispatch without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are read verbatim from unauthenticated HTTP headers and passed straight into `WebhookMetadata` used by the app's handler dispatch.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, and for webhooks that method returns only `@raw_body`: [1](#0-0) [2](#0-1) 

Meanwhile `Registry.process` only validates the HMAC and then constructs `WebhookMetadata` directly from `request.shop` and `request.topic`, which are read from the `x-shopify-shop-domain` / `x-shopify-topic` headers with no cryptographic binding to the body: [3](#0-2) [4](#0-3) 

The identity binding the library implicitly claims to provide is: `shop asserted in the header == shop that actually generated/owns the signed body`. Because the HMAC only covers `@raw_body`, this equality is never checked — `hmac_valid(raw_body)` is independent of `shop_header` and `topic_header`.

**Attack path (unprivileged internet user):** Because `Context.api_secret_key` is the app's single `client_secret`, it is shared across *every* shop that installs the app (this is normal, documented Shopify OAuth/webhook behavior, not misuse of undocumented internals). Any unprivileged person can install the app on their own (e.g., free development) store and thereby legitimately receive Shopify-signed webhooks — valid `raw_body` + valid `x-shopify-hmac-sha256` pairs computed with the shared secret. That attacker can then replay the exact same `raw_body`/`hmac` pair directly to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) with a victim shop's domain or a different topic. `HmacValidator.validate` still succeeds (it only checks the body bytes), and `Registry.process` happily dispatches the forged `shop`/`topic` to the handler, causing the host application to act on data it believes originates from — and is scoped to — the victim shop, when the payload actually came from the attacker's own shop.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: a handler that keys any effect (data write, cache update, uninstall/cleanup logic, notification, feature toggle) off `WebhookMetadata#shop` can be made to act on an arbitrary victim shop's identifier using attacker-controlled (self-signed-via-shared-secret) body content. This is a cross-tenant impact class explicitly in scope of this analog exercise (the tenant/session-key binding is not verified by the signature that is supposed to authenticate the message).

### Likelihood Explanation
Requires no leaked secrets, no privileged account, and no TLS interception: any internet user can install a public Shopify app on their own store to obtain legitimately-signed webhook traffic, then directly POST a modified copy of that traffic (with a different `shop`/`topic` header) to the app's public webhook endpoint. The gem performs no additional verification tying the header values to the signed body.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signable material (or otherwise cryptographically bind them to the body, e.g. by including them in a canonical signed string), so a byte-identical replay from a different tenant/topic no longer passes validation. At minimum, document this limitation prominently and require host applications to cross-check `request.shop` against the shop they expect for the given webhook subscription rather than trusting the header outright.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`; when they perform an action that triggers a webhook, Shopify sends a request with a body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` — a valid signature because `secret` (the app's `client_secret`) is shared across all installs.
2. Attacker captures this legitimate `(B, hmac)` pair from their own store's traffic (no interception of anyone else's traffic needed).
3. Attacker POSTs to the app's webhook endpoint with the same body `B` and the same `hmac`, but headers changed to:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: <topic the attacker wants dispatched>`
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only recomputes the HMAC over `raw_body` [5](#0-4) .
5. `ShopifyAPI::Webhooks::Registry.process` proceeds to call the registered handler with `WebhookMetadata.new(topic: "<forged topic>", shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [6](#0-5) , causing the host application's business logic to execute as if the victim shop sent this event.
