## Title
Simplex venue-priced pairs trust a raw, manipulable Uniswap V4 pool mid with no size/impact term, letting a flash-loan price manipulation drain solver inventory during an intent fill - (File: `sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts`)

### Summary
When a Simplex `FXFiller` trading pair is configured without static bid/ask curves ("curveless"), it prices the pair directly off a Uniswap V4 pool's current tick via `UniswapV4FundingPlanner.computeDirectPoolPriceUsd`, using the raw `sqrtPriceX96`-derived mid with no depth/impact adjustment and no execution-cost accounting. [1](#0-0)  The only defense is an *optional* static-reference price guard (`referencePrice` / `maxDeviationBps`), which is off by default and, even when configured, only bounds deviation from a stale reference rather than validating pool depth or protecting against a transient, single-block manipulation. [2](#0-1)  An attacker who can move the pool price within the guard band (or against an unguarded chain) can submit an intent order to be filled by this solver at the manipulated rate, extracting value from the solver's on-chain inventory/LP position — directly analogous to the reported HarryPotterObamaSonic10Inu liquidity-pool price-manipulation exploit.

### Finding Description
`resolveLegRates` in `fx.ts` routes any curveless pair whose `token0` is a USD stable straight to the venue price:
```
const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
if (venueUsd) {
    if (!this.checkPriceGuard(orderId, leg.token1Chain, new Decimal(1).div(venueUsd))) return null
    const venueRate = new Decimal(1).div(venueUsd)
    return { rate: venueRate, oppositeRate: null, priceSource: "venue" }
}
``` [3](#0-2) 

That `venueUsd` value comes from `UniswapV4FundingPlanner.getExoticTokenPrice`, which iterates the configured positions and calls `computeDirectPoolPriceUsd`, returning `sdkPool.token0Price`/`token1Price` verbatim — the pool's instantaneous mid, unaffected by the pool's own fee tier or any trade-size impact:
```
if (c0 === usdc || c0 === usdt) {
    return { exoticToken: c1, priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)) }
}
``` [4](#0-3)  `computeLegPolicyOutput` then extends this single mid linearly across the whole order size, so a full order is priced at the just-quoted instantaneous rate regardless of how large it is.

The only guardrail, `checkPriceGuard`, is purely a static-reference deviation check:
```
private checkPriceGuard(orderId, chain, venueToken1PerUsd) {
    const guard = this.priceGuard?.get(chain)
    if (!guard || guard.reference.lte(0)) return true
    const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
    if (deviationBps.gt(guard.maxDeviationBps)) { ...; return false }
    return true
}
``` [2](#0-1) 

This guard is optional by design (`referencePrice`/`maxDeviationBps` must both be set, or neither) and defaults to unguarded operation. [5](#0-4)  Even when configured, an attacker only needs to move the pool price to within the allowed band (which project documentation shows configured as wide as 2%) to profit, and the guard does nothing to account for pool depth, so a thin pool can be pushed to the edge of the band cheaply. This is the same bug class as the reported incident: an attacker manipulates a DEX liquidity pool's spot price and a dependent protocol/contract consumes that manipulated spot price as ground truth to value an asset, without TWAP, depth check, or execution-cost modeling.

### Impact Explanation
A Simplex solver configured with a curveless (venue-priced) pair funds/prices trades directly from a manipulable Uniswap V4 pool mid. [6](#0-5)  An attacker can:
1. Manipulate the target pool's price (e.g., via a large swap or flash loan) so the reported mid understates the exotic token's true value (or, symmetrically, overstates the stablecoin's purchasing power).
2. Submit (or have their own filler skip, letting this solver win) an intent order that this solver fills at the manipulated rate via `quotePhantomFill`/`calculateProfitability`, both of which consume the same `resolveLegRates` venue path. [7](#0-6) 
3. Immediately restore the pool price and walk away with the spread between the manipulated fill price and the pool's honest price, funded out of the solver's wallet/LP inventory withdrawn via `UniswapV4FundingPlanner.planWithdrawalForToken`.

This is a direct, unbounded fund-extraction path against solver capital — concrete theft of solver-held liquidity — matching the Medium/High severity bucket of the referenced price-manipulation incident, gated only by an optional and coarse deviation guard.

### Likelihood Explanation
Likelihood depends on operator configuration: it only applies to fillers running curveless, venue-priced pairs (an explicitly supported, documented Simplex configuration), and is easiest against chains where the operator omitted `referencePrice`/`maxDeviationBps` (the default) or set a wide band. Given Uniswap V4 pools for exotic/illiquid tokens (the intended use case per the documentation, e.g., cNGN) are typically thin, manipulating spot price within even a 1-2% band is inexpensive relative to the notional a solver would fill. Any user able to submit an intent order (fully permissionless) can trigger the mispriced fill once the pool is manipulated.

### Recommendation
- Do not price fills off instantaneous `sqrtPriceX96`; use a TWAP/observation-based price or require corroboration from an independent oracle.
- Make the price guard mandatory (not optional) for venue-priced pairs, and size `maxDeviationBps` to the pool's liquidity depth rather than a fixed operator-chosen constant.
- Incorporate the pool's own fee tier and a size/impact term into `computeLegPolicyOutput` so a large fill is priced against realistic execution cost, not the linear extension of a point quote.
- Consider requiring same-block/same-transaction manipulation resistance (e.g., comparing against a price observed several blocks earlier) before trusting a pool quote for funding withdrawals.

### Proof of Concept
1. Configure a Simplex `FXFiller` with a curveless pair (`token0` = USDC, `token1` = an exotic token) and a `[vault.uniswapV4]` position on a thin pool, without setting `referencePrice`/`maxDeviationBps` (or with a loose band), as documented in `docs/content/developers/evm/simplex/pricing.mdx`. [8](#0-7) 
2. Attacker swaps against the pool to move `sqrtPriceX96` so `sdkPool.token0Price`/`token1Price` understate the exotic token's value (or stay within the configured band).
3. Attacker submits an intent order via `IntentGateway` requesting the exotic token for USDC at the manipulated rate.
4. `FXFiller.calculateProfitability` → `resolveLegRates` reads the manipulated venue price, passes `checkPriceGuard` (no guard, or within a loose band), and fills the order, releasing exotic tokens funded from the solver's Uniswap V4 position via `UniswapV4FundingPlanner.planWithdrawalForToken`. [9](#0-8) 
5. Attacker reverses the manipulation swap, capturing the spread between the manipulated fill price and the pool's fair value, at the solver's expense.

		}

				// the venue-specific defense.

				return { rate: venueRate, oppositeRate: null, priceSource: "venue" }
			}

## Pool-Based Pricing

When **`[vault.uniswapV4]`** lists at least one position, cross-asset pairs without curves derive bid/ask prices from **Uniswap V4 pool state** (current tick). The pool acts as the price oracle instead of a static curve. Note this yields a **single** price used in both directions — a venue-priced pair has no bid/ask spread of its own, so its margin comes from `order.fees` alone.

With Uniswap V4 positions configured, you can **omit** `bidPriceCurve` and `askPriceCurve` on the pair. Pool pricing requires the pair's `token0` to be a USD stablecoin, and same-token pairs always need their curve. The optional **`spreadBps`** field (basis points) sets the slippage tolerance for on-chain LP redemptions; defaults to `50` (0.50%).

Uniswap V4 venue pricing uses pools that pair the exotic token with **USDC or USDT** (addresses from your chain config). When multiple positions exist for the same exotic token on a chain, the most-liquid qualifying pool's price is used.

```toml lineNumbers
[assets.CNGN]
"EVM-8453" = "0x46C85152bFe9f96829aA94755D9f915F9B10EF5F"

[[pairs]]
token0 = "USDC"
token1 = "CNGN"
maxOrderSize = "5000"       # no curves — priced from the pool

[vault.uniswapV4]
spreadBps = 50  # 0.5% slippage tolerance on LP redemptions
positions = [
    { chain = "EVM-8453", tokenId = "2087350" },
]
```

<Callout type="info">
Startup validation requires a pricing source per pair: **either** bid/ask price curves, **or** at least one `[vault.uniswapV4]` position. A pair with neither fails validation.
</Callout>
```
