### Title
Truncating division in `convert_to_balance` permanently burns dust when receiving `HyperFungibleToken` cross-chain transfers - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler converts an incoming EVM-denominated transfer amount to the local asset's decimal precision using integer division that truncates toward zero. Because the EVM-side `HyperFungibleToken.send()` contract burns/dispatches the user's requested amount verbatim, with no obligation that it be an exact multiple of the decimals scaling factor, any amount whose low-order digits fall below one "local unit" is silently lost: it is burned/escrowed on the source chain but never minted/released on the destination, and there is no accounting of the shortfall anywhere in the message or in pallet storage. This is the same rounding-down-causes-less-than-requested defect described in the ERC5095 report, except here the truncated remainder isn't just under-delivery to the same user — it's an unrecoverable value leak from the whole bridge, reachable by any ordinary bridging transaction.

### Finding Description
`convert_to_balance` performs the ERC20→local conversion by plain integer division, with no remainder handling: [1](#0-0) 

It is invoked directly in `on_accept` to compute the amount credited to the beneficiary: [2](#0-1) 

That credited `amount` is then minted or released from escrow to the beneficiary, and the event records only the (already-truncated) result — the pallet never observes or stores the original, pre-truncation `message.amount`: [3](#0-2) [4](#0-3) 

On the EVM origin side, `HyperFungibleToken.send()` accepts an arbitrary `uint256 amount` from the caller, burns exactly that amount, and forwards it unscaled as `Message.amount` in the dispatched request: [5](#0-4) 

Nothing in `HyperFungibleToken.send()` (nor its interface) constrains `amount` to be an exact multiple of `10^(erc_decimals - local_decimals)`. The documentation explicitly notes that decimal scaling is handled only by the pallet on receipt, and that the TypeScript SDK is what normally "handles fee estimation, token approvals, and decimal scaling" for callers — implying the on-chain contract itself performs no such rounding/validation: [6](#0-5) 

Consequently, an unprivileged user (or any caller who bypasses the SDK, or whose amount simply doesn't align to the scale factor after fee/precision math) can call `send()` with an amount whose remainder modulo `10^(erc_decimals-local_decimals)` is non-zero. That full amount is burned on the EVM chain. When the message lands on the destination chain, `convert_to_balance` truncates the remainder away and mints/releases strictly less than what was burned. The lost remainder is not credited to the beneficiary, not returned to the sender, and not tracked in any pallet storage — it is gone permanently. This contrasts with `on_timeout`, where the refund path recomputes the same conversion on the same already-scaled `message.amount`, so no information is lost there; the loss is specific to the accept path where the *input* amount originates from an unconstrained EVM caller.

### Impact Explanation
This is a real, unbacked-token/permanent-fund-loss bug reachable by any user of the bridge in a single transaction — no privileged role required. Every cross-chain transfer whose amount isn't already decimal-aligned to the destination chain's precision burns `remainder` units of value that vanish from total supply across both chains combined: the source chain's escrow/burn accounting is decremented by the full amount, but the destination chain's mint/release is short by the truncated remainder. Depending on the decimals gap (e.g. 18 EVM decimals vs. 10 or 12 local decimals, as configured for `BRIDGE`/`pall_hft`), the lost amount per transfer can be up to `10^(erc_decimals-local_decimals) - 1` base units, and this loss compounds across every misaligned transfer, permanently reducing the economic backing of the bridged token without any way to reclaim or later account for the dust. This matches the "permanent freezing/loss of funds" acceptance criterion — worse than the referenced ERC5095 issue, because there the shortfall stayed with the same withdrawing user (an accounting nuisance); here it disappears from the system entirely with no owner.

### Likelihood Explanation
High. `send()` places no constraint on `amount` alignment, and typical bridging amounts (e.g. denominated by a user typing a human-readable quantity, or converted via a UI/SDK that doesn't defend against this specific edge, or via direct contract calls bypassing the SDK's scaling helpers) will frequently not be exact multiples of the scale factor once the pair's decimals differ (which is documented as the normal case, e.g. BRIDGE's 18 EVM decimals vs. 12 nexus decimals). Any such transfer triggers the loss automatically and silently — no attacker coordination or special conditions are needed, only ordinary use of the bridge.

### Recommendation
Reject (revert) `send()`/`on_accept` amounts that aren't exact multiples of the applicable scale factor, or explicitly track/refund the truncated remainder (e.g. return the non-representable remainder to the sender on the source chain before burning/escrowing, or accrue it in a per-asset dust pool that can be swept/redistributed) so that burned/escrowed value on one chain always equals minted/released value on the other, with no unaccounted-for leak.

### Proof of Concept
1. Configure a token pair where `erc_decimals = 18` (EVM side) and `local_decimals = 10` (substrate side), as documented for `BRIDGE`/nexus.
2. From the EVM chain, call `HyperFungibleToken.send({ amount: 1_000_000_000_000_000_001, ... })` (i.e. `10^18 + 1` wei) targeting the substrate chain. This burns exactly `1_000_000_000_000_000_001` wei from the caller (see `HyperFungibleToken.sol` burn/dispatch path).
3. The dispatched `Message.amount` (`1_000_000_000_000_000_001`) arrives unchanged at the destination pallet's `on_accept`.
4. `convert_to_balance(1_000_000_000_000_000_001, 18, 10)` computes `value / 10^8 = 10_000_000_000` (truncating the trailing `1`), so the beneficiary is minted/released the local equivalent of only `10_000_000_000 * 10^8 = 1_000_000_000_000_000_000` — one full base unit less than what was burned.
5. The truncated unit is never minted, refunded, or recorded anywhere; it is permanently lost from the combined cross-chain supply.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,

	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
