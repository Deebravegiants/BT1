### Title
Client-Attested `user_centric_signup` Flag Bypasses Backend Fraud/Duplicate Verification During Enrollment - (File: `src/plans/mod.rs`)

### Summary
In `do_signup`, when the user's authenticated app data sets `user_centric_signup = true`, the Orb determines signup success **locally** from `signup_reason` instead of calling the backend `enroll_user` flow, which normally performs the authoritative `signup_post`/`signup_poll` round trip that includes backend-side fraud, duplicate, and inflight-match detection. This is structurally analogous to the fingerprint-bypass report: a locally observed "success" signal (there, an unauthenticated `onAuthenticationSucceeded` callback; here, a locally-computed `signup_reason`) is trusted in place of a cryptographically/server-verified confirmation, letting the party that controls the input skip the authoritative check.

### Finding Description
`user_centric_signup` originates from `authenticated_app_data.user_centric_signup`, a field inside the app-supplied `UserData` payload that is authenticated only by a **self-consistency hash check** (`user_data.verify(user_data_hash)` against a hash the app itself embeds in its own QR code) rather than being independently asserted or signed by the backend's fraud engine: [1](#0-0) 

That flag flows into `QrCodes::Both.user_data.user_centric_signup` and is read in `do_signup`: [2](#0-1) 

When `user_centric_signup` is true, the success determination is:
```rust
debug_report.enrollment_status(match signup_reason {
    SignupReason::Normal => enroll_user::Status::Success,
    _ => enroll_user::Status::Error,
});
signup_reason == SignupReason::Normal
```
instead of calling `self.enroll_user(...)`, which is the path that actually POSTs the signup to the backend (`signup_post::request`) and polls `signup_poll` for backend-side confirmation, duplicate detection, and fraud flags: [3](#0-2) [4](#0-3) 

Critically, `signup_reason` itself is computed from `detect_fraud`, which in this FOSS build unconditionally returns `false` because "we have deleted all fraud checks": [5](#0-4) [6](#0-5) 

So for `user_centric_signup` flows, "success" reduces to "biometric pipeline ran without an internal agent error" — there is no equivalent of the backend's duplicate-iris / inflight-match / fraud rejection (item list documented at `src/plans/enroll_user.rs:162-168`) applied before the Orb reports/treats the signup as successful and uploads the personal custody package.

### Impact Explanation
An app/operator that can set `user_centric_signup = true` in its self-attested user data causes the Orb to locally accept a signup as successful and proceed to build and upload the Personal Custody Package (containing iris/face keys and identity data) without the backend's authoritative fraud/duplicate check ever gating the "success" outcome the Orb itself acts on. This can result in misattributed signups (bypassing the same anti-fraud logic that `enroll_user`'s POST+poll cycle is designed to enforce for normal signups) — the same class of impact called out for acceptance in the validation rules ("unauthorized or misattributed signup ... fraud/liveness bypass").

### Likelihood Explanation
Moderate. It requires control over the app-side `authenticated_app_data` payload (an unprivileged, non-operator actor in this flow) and only needs to set one boolean field consistent with its own self-generated hash — there is no separate backend attestation of `user_centric_signup` beyond this self-consistency check within the code reviewed. Reaching this path also requires a normal, non-fraud pipeline result, which in this FOSS build is trivially satisfied since fraud checks are stubbed to always return `false`.

### Recommendation
- Do not let a client/app-attested flag (`user_centric_signup`) skip the backend confirmation (`signup_post`/`signup_poll`) that performs duplicate/fraud checks. If user-centric signups must avoid persisting user PII server-side, still require a backend round trip that returns a signed/verified fraud/duplicate verdict before the Orb treats the signup as `Success`.
- Do not treat the absence of local fraud checks (`detect_fraud` stub) as equivalent to "no fraud" — either gate PCP upload/enrollment success on a real fraud verdict, or clearly ensure this FOSS default cannot be relied upon as an authoritative accept signal for `user_centric_signup` paths.
- Require `user_centric_signup` to be corroborated by a backend-issued signature/attestation tied to the operator+orb session, not merely the app's self-consistent hash.

### Proof of Concept
Conceptual reachable path (no external tooling required, unlike the Frida-based mobile PoC):
1. An app-controlled QR payload sets `authenticated_app_data.user_centric_signup = true` and includes a `user_data_hash` that is self-consistent with that payload (per `UserData::verify`).
2. The Orb parses this in `user_status::request`, setting `UserData.user_centric_signup = true` [7](#0-6) .
3. During `do_signup`, once biometric capture/pipeline complete without an internal agent error, `signup_reason` is `Normal` because `detect_fraud` always returns `false` [8](#0-7) .
4. Because `user_centric_signup` is true, the Orb sets `enrollment_status = Success` and `result.success = true` locally, entirely bypassing the `enroll_user::Plan::run` backend POST/poll cycle that would otherwise apply backend fraud/duplicate detection [9](#0-8) .

**Note:** This is a source-level analog reasoning from the reviewed FOSS orb-core code; I could not verify against the closed-source/backend fraud engine or the `orb_qr_link::UserData::verify` implementation (not present in this repo's indexed content), which may impose additional constraints not visible here.
