### Title
Predispatch input-sweep in `IntentGatewayV2.placeOrder` credits an attacker's order with the *entire* token balance of the shared `CallDispatcher`, letting anyone steal residual/misdirected funds - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`placeOrder`'s predispatch branch determines how much of an input token to escrow for an order by reading `IERC20(token).balanceOf(dispatcher)` — the balance of the single, shared `CallDispatcher` contract referenced by `_params.dispatcher` — rather than by tracking what the current transaction actually produced for the caller. An attacker who knows (or forces to zero) the required amount can set `order.inputs[i].amount` equal to the dispatcher's current balance of any token and have that whole balance credited to their own order's escrow, exactly as the `YearnProvider`/`AaveProvider` report describes: the amount returned/credited is determined by a balance measurement on a shared contract that the caller does not exclusively control, rather than by verified provenance of the funds.

### Finding Description
`_params.dispatcher` is one persistent `CallDispatcher` contract shared across every call to `placeOrder`/`fillOrder` on the gateway [1](#0-0) . `CallDispatcher` has a payable `receive()` and executes arbitrary calldata handed to it by the gateway [2](#0-1) , so its balance is not exclusively owned by whichever order is currently "in flight" — it can (and does, by design) accumulate residual dust across unrelated transactions (fee-on-transfer residues, partially-swept predispatch outputs, or plain accidental transfers, since `receive()` accepts ETH from anyone).

In the predispatch branch of `placeOrder`, for each declared input the code:
1. Reads `balance = IERC20(token).balanceOf(dispatcher)`.
2. Requires only `balance >= requiredAmount` (attacker-supplied `order.inputs[i].amount`).
3. Builds a sweep call that transfers the **whole** `balance` (not `requiredAmount`) from `dispatcher` to the gateway.
4. After the sweep, computes `received = balanceAfter - balanceBefore`, and **only escrows `order.inputs[i].amount` (the original request) if `received <= order.inputs[i].amount`** — otherwise it just emits a `DustCollected` event for the excess and leaves the requested amount as the escrowed value. [3](#0-2) 

Because the attacker fully controls `order.inputs[i].token` and `order.inputs[i].amount`, they can simply query the dispatcher's current balance for any token off-chain and set `requiredAmount` equal to it. Then `received == requiredAmount` exactly, no dust is flagged, and `order.inputs[i].amount` (the value that becomes the escrowed amount for the attacker's own order via `_orders[commitment][token] += reducedInputs[i].amount`) is set to the dispatcher's full balance — funds the attacker never actually deposited. Predispatch calldata can be a harmless no-op call (any whitelisted-by-contract-check call target with nonzero code size), so the attacker does not need to supply real predispatch logic at all; they only need the sweep-based accounting path to run.

This mirrors the reported bug class precisely: the amount credited to the caller is derived from measuring the balance of a shared/user-influenceable contract rather than from verified, attributable transfer of the caller's own funds — just as `YearnProvider`/`AaveProvider.withdraw()` let an attacker report/engineer balances so the contract sends back tokens that were never the caller's.

### Impact Explanation
Any token balance sitting on the shared `CallDispatcher` — whether native ETH sent there by mistake (its `receive()` is unconditionally payable), ERC20 dust left over from another user's predispatch execution, or protocol residuals — can be swept into an attacker-controlled order's escrow and subsequently exfiltrated by the attacker (e.g., via order cancellation/refund to `order.user`, or by self-filling a trivially satisfiable destination). This is a direct theft of funds that do not belong to the caller, reachable from a single `placeOrder` transaction by any unprivileged EOA. Severity: High, matching the reference report's "Any tokens can be stolen" classification, scoped here to whatever balance transiently or accidentally resides on the shared dispatcher.

### Likelihood Explanation
Likelihood is High for any funds that land on the dispatcher: the attacker only needs to observe `IERC20(token).balanceOf(dispatcher)` (or `dispatcher.balance`) and submit one `placeOrder` transaction with matching `requiredAmount` and a harmless predispatch call. No special permissions, races, or complex setup are required beyond the dispatcher holding a nonzero balance of some token at the time of the call — a state that is plausible given the dispatcher's payable `receive()` and its general role as an intermediary for arbitrary predispatch/output calls across all users of the gateway.

### Recommendation
Do not size the sweep transfer or the credited `order.inputs[i].amount` by the dispatcher's *total* balance. Instead:
- Capture the dispatcher's token/ETH balance immediately before executing the attacker's own predispatch call within the same transaction, and only sweep/credit the *delta* produced by that specific predispatch call (i.e., `balanceAfterPredispatch - balanceBeforePredispatch` on the dispatcher, not just on the gateway).
- Never transfer more than `requiredAmount` in the sweep call; if the delta exceeds `requiredAmount`, sweep only `requiredAmount` and leave/attribute the excess as protocol dust to be later collected by governance (as already done via the `SweepDust` path) rather than allowing it to pass through into the order's own accounting.
- Consider making the dispatcher balance-check strict equality-agnostic to pre-existing balance: require `dispatcher` balance was zero (or record/subtract a known baseline) for the specific token before honoring `requiredAmount` against it.

### Proof of Concept
1. Assume the shared `CallDispatcher` at `_params.dispatcher` currently holds `X` units of some ERC20 `T` (from dust, a stuck previous predispatch sweep, or a mistaken direct transfer — its `receive()` accepts arbitrary ETH, and ERC20 transfers directly to its address are equally unguarded).
2. Attacker calls `placeOrder` with:
   - `order.predispatch.call` = an arbitrary but harmless call to any deployed contract (only needs nonzero code size per `CallDispatcher.dispatch`), and `order.predispatch.assets` funding it with a negligible/zero-effect transfer.
   - `order.inputs[0] = TokenInfo({ token: T, amount: X })`.
3. `placeOrder` executes the predispatch branch: `balance = IERC20(T).balanceOf(dispatcher) == X`, passes the `balance >= requiredAmount` check, builds a sweep call transferring the full `X` from `dispatcher` to the gateway.
4. After the sweep, `received == X == order.inputs[0].amount`, so no dust is flagged and `order.inputs[0].amount` remains `X`.
5. `_orders[commitment][T] += X` (minus any protocol fee) is escrowed under the attacker's own order/commitment, funded entirely by tokens the attacker never transferred from their own wallet.
6. The attacker can then reclaim these funds through the standard refund/cancel-or-self-fill path available to `order.user` (the caller), completing the theft of the dispatcher's balance. [3](#0-2) [2](#0-1)

     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
