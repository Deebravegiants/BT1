### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant data misattribution via webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, and `webhook_id` values used by the application come from unauthenticated HTTP headers. `Registry.process` trusts `request.shop` to attribute the webhook to a tenant after validating only that the body's HMAC is correct, breaking the binding between "bytes verified" and "shop stored/used".

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `x-shopify-shop-domain` / `shopify-shop-domain` header without any cryptographic binding to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` only confirms that `HMAC(secret, to_signable_string)` matches the supplied `hmac` value — it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build `WebhookMetadata` passed to the app's handler: [4](#0-3) 

This is the same "bytes verified vs. bytes parsed / shop authenticated vs. shop stored" class of bug identified in the external report (TWAP calculated from data not covering the actual current value used downstream). Here, the value cryptographically authenticated (the raw body) is disjoint from the value used as the tenant identity key (the `shop-domain` header). Any request whose body was legitimately HMAC-signed for one shop can be replayed with the `shop-domain` header rewritten to a different shop, and the signature will still validate, because the header is never part of the signed content.

### Impact Explanation
This breaks the identity binding `shop_authenticated == shop_used_for_tenant_key`. An unprivileged internet user who has legitimately received (or can otherwise obtain) one raw webhook payload + its valid HMAC for a topic that is shop-agnostic in payload content (or generic body content, e.g. `{}` or a template body), can submit that same body/HMAC pair to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header value. Because `Registry.process` only checks `Utils::HmacValidator.validate(request)` (body-only) and then unconditionally forwards `request.shop` to the handler, the application will process/attribute the webhook data to a shop the attacker chooses — a cross-tenant data-integrity/confusion issue. Depending on how the consuming application (e.g., built on `WebhookMetadata.shop`) persists or acts on this data (e.g., writing "customer redacted" or "shop redacted" GDPR webhooks, or updating cached shop state), this can cause cross-tenant data corruption or spoofed events attributed to a victim shop.

### Likelihood Explanation
Exploitability depends on the attacker being able to obtain a genuinely-signed webhook body+HMAC pair at least once (e.g., as the owner of their own — unprivileged — shop installation of the app, which is normal/unprivileged access), and on there being at least one webhook topic whose body content is shop-independent or attacker-predictable (many mandatory GDPR topics like `shop/redact` and `customers/redact` have minimal/templated bodies). This does not require the app's `client_secret`, an access token, or any privileged account — only the ability to send an HTTP request to the app's public webhook endpoint with attacker-chosen headers, which any internet user can do once they possess one valid signed payload from their own tenant.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or at minimum `shop`) as part of `to_signable_string`, or otherwise cryptographically bind the header-derived identity fields to the HMAC before they are used to key any downstream tenant logic. Since Shopify's actual webhook HMAC only signs the body (matching Shopify's real webhook contract), the library should instead require applications to independently corroborate the `shop-domain` header against a known/installed shop record before trusting it (i.e., document/enforce that `WebhookMetadata.shop` must be cross-checked against the app's own session store, not treated as authenticated purely because `Registry.process` didn't raise). At minimum, update documentation and add a check that resolves/validates the shop domain against existing installed sessions before invoking the handler.

### Proof of Concept
1. App A (attacker) installs the target Shopify app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `customers/redact` with body `{}` and a valid `X-Shopify-Hmac-Sha256` header computed over `{}` with the app's shared secret (attacker can capture this from their own webhook delivery logs/dashboard — fully unprivileged, as it's their own store).
2. Attacker resends this exact `raw_body` (`{}`) and `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` (`{}`) only — this matches, since the body and HMAC are unmodified: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", ...)`, causing the app to process a spoofed redact/data event attributed to `victim-shop`, despite no cryptographic proof that Shopify (or `victim-shop`) ever sent this webhook.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
