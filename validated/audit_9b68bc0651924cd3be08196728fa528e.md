### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that gets handed to the host application's webhook handler from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `Registry.process` validates only covers the raw request body. This breaks the identity binding: `hmac == HMAC(body)` while `shop` (the value actually acted upon) is an independent, unauthenticated header. Because `Context.api_secret_key` is the same secret for every shop that has installed the app, any shop can generate a validly-signed webhook body and then relabel it as coming from a different (victim) shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an unsigned header: [2](#0-1) 

`Registry.process` validates the HMAC via `HmacValidator.validate(request)`, which internally calls `validate_signature`/`compute_signature` against `to_signable_string` only (i.e. the body), and then, once that single check passes, immediately trusts `request.shop` to build the `WebhookMetadata` object dispatched to the host app's handler: [3](#0-2) [4](#0-3) 

The identity binding the gem should enforce is:
`hmac == HMAC(secret, body ‖ shop)`
but what is actually checked is:
`hmac == HMAC(secret, body)` while `shop` is taken from `X-Shopify-Shop-Domain` unauthenticated.

Because `api_secret_key` is a single, shop-independent app secret (the same secret is used to validate OAuth HMACs and JWTs for every merchant, see `Utils::HmacValidator.validate` and `Context.api_secret_key` usage throughout `lib/shopify_api/auth/oauth.rb`), any unprivileged merchant who installs the app can:
1. Trigger a real webhook event in their own store (e.g., create an order), producing a body and a correctly computed `X-Shopify-Hmac-Sha256` header signed with the app's shared secret.
2. Replay that exact `(body, hmac)` pair to the app's webhook endpoint, but substitute `X-Shopify-Shop-Domain` with a victim shop's domain.
3. `Registry.process` re-validates the HMAC (which still matches, since only the body is signed) and constructs `WebhookMetadata.new(shop: request.shop, ...)` — where `shop` is now the attacker-chosen victim domain — and dispatches it to the host app's handler.

The host application, trusting the gem's HMAC validation as an authenticity/tenant guarantee (as documented and demonstrated in `docs/usage/webhooks.md` and `test/webhooks/registry_test.rb`), will act on the payload as if it legitimately originated from the victim shop, causing cross-tenant data confusion/write (e.g., storing attacker-controlled order/customer data under the victim's shop record, or triggering shop-scoped side effects like `shop/redact` incorrectly attributed to another tenant).

### Impact Explanation
This is a cross-tenant access issue: an unprivileged tenant (any merchant who installs the app) can forge the identity of a *different* tenant's webhook without needing that tenant's credentials, `access_token`, or the app's `client_secret`. Only the gem's own (mis-)designed identity binding is exploited. This matches the "Critical – cross-tenant access" impact bucket.

### Likelihood Explanation
Likelihood is high for any app relying solely on `ShopifyAPI::Webhooks::Registry.process`/`Request` as the authenticity+tenant source without independently validating `shop` against an installed-shop allowlist. The attack requires only: (a) being a legitimate installer of the target app on the attacker's own shop (to obtain one validly-HMAC'd body/signature pair), and (b) sending a single crafted HTTP POST to the app's public webhook endpoint with a swapped header — no access token, secret, or privileged access needed.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to the signed body (e.g., require the host app to cross-check `request.shop` against the shop that actually owns the currently-loaded session/subscription before trusting `WebhookMetadata#shop`). At minimum, document prominently that `Webhooks::Request#shop` is unauthenticated and must not be trusted as a tenant identifier without additional verification against a known list of shops that installed the app for the given webhook subscription.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has the app installed there.
# They trigger a real event, capturing a valid (body, hmac) pair delivered by Shopify:
body = '{"id":1,"note":"hi"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)
)

# Attacker replays it to the app's webhook endpoint with a forged shop header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation succeeds (it only checks `body`),
#    and the host app's handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
#    even though the payload never originated from that shop.
```
