### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers. `Utils::HmacValidator.validate` only checks the body against the HMAC, so the `shop` value that `Registry.process` hands to the app's webhook handler is never bound to the signature that "proves" the request came from Shopify.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `webhook_id`, and `api_version` as plain header reads: [1](#0-0) 

Crucially, `to_signable_string`, which is the only input used to verify the HMAC, returns just `@raw_body` — it does not include `shop`, `topic`, `webhook_id`, or `api_version`: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the body) and the app's `api_secret_key`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof the whole request — including `request.shop` — is authentic, and forwards that unauthenticated `shop` value straight to the app's handler: [4](#0-3) 

The gem's own documentation reinforces this false guarantee, stating that `Registry.process` "will verify the request did indeed come from Shopify": [5](#0-4) 
and lists `shop` as one of the trustworthy fields delivered to the handler: [6](#0-5) 

Because the same app-level `api_secret_key` is used to sign webhooks for every shop that installs the app, an attacker who installs the (public) app on their own store receives a legitimately HMAC-signed `(body, hmac)` pair. Since neither `shop` nor `topic` is part of the signed content, the attacker can replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain (and/or a different `x-shopify-topic`). `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` calls the handler with `shop: <victim shop>` but `body: <attacker-controlled data>`.

This breaks the identity binding: **shop value verified by the HMAC (none) vs. shop value acted on by the application (attacker-controlled header)**.

### Impact Explanation
This lets an unprivileged internet user (any user who can install the target public app on their own store) inject attacker-controlled webhook payloads that the host application will process as if they originated from an arbitrary victim shop. Depending on how the host app's webhook handler uses `data.shop` (e.g., to look up the shop's session/access token and perform actions, or to write data keyed by shop), this results in cross-tenant data injection/impersonation — a Critical-severity cross-tenant access issue per the impact criteria.

### Likelihood Explanation
Exploitation only requires: (1) the ability to install the target public app on an attacker-controlled store to obtain a validly-signed webhook body/HMAC pair, and (2) sending a crafted HTTP POST to the app's public webhook endpoint with a forged `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header while reusing the captured body and HMAC. No access token, `api_secret_key`, or privileged access is required, making this readily reachable by any unprivileged internet user for apps that allow public installation.

### Recommendation
Bind the shop (and ideally topic) identity to the HMAC verification instead of trusting it purely from headers. At minimum, `HmacValidator`/`Request` should incorporate the `shop-domain` (and `topic`) header into the signed content check where feasible, or `Registry.process`/the webhook handler contract should require the caller to independently corroborate `request.shop` against a known/installed-shop list before trusting it, and documentation should be corrected to not claim the entire request (including `shop`) is verified.

### Proof of Concept
1. Attacker installs the target public Shopify app on their own store `attacker-shop.myshopify.com`, triggering a legitimate webhook delivery to the app; the attacker captures the raw request body `B` and its valid header `X-Shopify-Hmac-Sha256: H` (computed by Shopify using the app's `api_secret_key` over `B` only).
2. Attacker sends a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid), but `x-shopify-shop-domain: victim-shop.myshopify.com` and any desired `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Utils::HmacValidator.validate` succeeds because it only checks `H` against `B` (`to_signable_string` returns `@raw_body`) — see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`.
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: <attacker data>, ...)` — see `lib/shopify_api/webhooks/registry.rb:188-200` — causing the app to process attacker-controlled data under the victim shop's identity.
