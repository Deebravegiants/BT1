## Title
Reverting native-ETH transfer in `_withdraw()` permanently freezes an entire order's escrow (ETH + bundled ERC20 tokens) - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw()` — the shared escrow-release routine used by both `ExtrinsicIntents.onAccept` (cross-chain `RedeemEscrow`/`RefundEscrow`) and `IntrinsicIntents` (same-chain fills/cancels) — pushes native ETH to the order's beneficiary via `_sendValue`, which `revert`s on transfer failure. Because the token loop inside `_withdraw` is atomic and processes every escrowed asset for a commitment in one call, a beneficiary that cannot accept a raw ETH push (no payable `receive`/`fallback`, or a contract that deliberately reverts) causes the *entire* withdrawal — including any bundled ERC20 legs of the same order — to fail permanently and non-retryably.

### Finding Description
`_withdraw` iterates over `body.tokens` and, for the native-token leg, calls `_sendValue`, which reverts on failure: [1](#0-0) [2](#0-1) 

This is invoked from `onAccept` on `RedeemEscrow`/`RefundEscrow` delivery: [3](#0-2) 

`EvmHost.dispatchIncoming` treats an `onAccept` revert as "keep it retryable" — it deletes the request receipt and returns without reverting the whole handler batch: [4](#0-3) 

So this specific weakness does **not** brick unrelated messages in the same relayer batch (unlike the classic push-payment report where one reverting recipient stalls the whole payout list) — that per-message isolation is already handled at the host layer. However, for the *specific* `WithdrawalRequest` whose beneficiary cannot receive ETH, the condition is permanent: every redelivery attempt re-executes the same `_sendValue` call and reverts the same way. Since `_orders[...]` state changes happen before the external call and the whole call reverts atomically, none of that order's escrow — not even the ERC20 legs bundled in the same `WithdrawalRequest.tokens` array — can ever be released, because the loop processes all tokens for the commitment in one all-or-nothing pass.

The identical pattern (revert-on-failed native push, atomic multi-token loop) exists in the Tron port's `withdraw()`: [5](#0-4) 

### Impact Explanation
This is a permanent freeze of escrowed funds, not a protocol-wide DoS: it affects only the specific order/commitment whose `beneficiary` (either the solver's chosen address for `RedeemEscrow`, or `order.user` for `RefundEscrow`) is a contract that cannot accept a bare ETH transfer. Because the token loop bundles all assets for that commitment atomically, a solver who fills an order containing both native ETH and ERC20 outputs, or a user who cancels an order with mixed-asset inputs, can have *all* of that order's escrowed value (ETH and ERC20 alike) permanently stuck if the receiving address can't accept ETH — with no retry path that can ever succeed and no pull-based recovery mechanism. This meets the "permanent freezing of funds" impact bar even though it is scoped per-order rather than protocol-wide.

### Likelihood Explanation
Triggering requires only that a solver's fill address (self-chosen) or a user's order-placement address (self-chosen) be a non-payable/reverting contract — no privileged role or governance action is needed, and it can happen accidentally (e.g., using a smart-contract wallet without a payable fallback) as easily as maliciously. Given ordinary usage patterns (contract wallets, multisigs, proxies), this is plausible without adversarial intent, though it is bounded to self-inflicted loss per affected commitment rather than a cross-party theft vector.

### Recommendation
Replace the push-and-revert native transfer in `_withdraw` (and the Tron `withdraw`) with a pull-over-push pattern: on a failed native transfer, credit an internal `ethBalance[beneficiary]` mapping instead of reverting, emit an event, and let the beneficiary call a separate `withdrawETH()` to pull funds later. Additionally, decouple per-token transfers within the same `WithdrawalRequest` so a failure on one asset does not block release of the others (e.g., process each token transfer independently and only mark the order finalized once all succeed, or track partial completion per token).

### Proof of Concept
1. User places a cross-chain order whose `output.beneficiary` (for `RedeemEscrow`, this becomes the solver's `msg.sender`) or whose `order.user` (for `RefundEscrow`) is a contract with no payable `receive`/`fallback`.
2. Order includes both a native-ETH leg and an ERC20 leg in `order.inputs`/`order.output.assets`.
3. On settlement, `onAccept` → `_withdraw` is invoked with a `WithdrawalRequest.tokens` array containing both assets.
4. `_sendValue(beneficiary, ethAmount)` reverts because the beneficiary cannot accept ETH.
5. The whole `_withdraw` call reverts; `EvmHost.dispatchIncoming` deletes the receipt so the message is retryable, but every future relayer resubmission hits the identical revert.
6. Both the ETH and the bundled ERC20 escrow for that commitment remain locked in the contract indefinitely, with no pull-based path to recover the ERC20 portion.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));

                if (!success) revert TransferFailed();
