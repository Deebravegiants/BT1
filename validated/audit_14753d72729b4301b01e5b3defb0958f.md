This confirms the vulnerability: `Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) returns only `@raw_body`, so the HMAC signature covers the request body exclusively — the `shop-domain` header is never part of the signed payload. Yet `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) passes `shop: request.shop` straight into `WebhookMetadata`, which host applications use as the tenant identity for routing/persisting webhook data (`lib/shopify_api/webhooks/webhook_handler.rb:6-12`).

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signable string from the raw body only, while the `shop` (tenant identity) is read from an unauthenticated header. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose body/HMAC pair validates and forwards the header-derived `shop` value to the app's handler without binding it to the signature, exactly the class of bug described in the report: "a field acted on but not covered by the HMAC."

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
returning only `@raw_body`. `HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, Context.api_secret_key, verifiable_query.to_signable_string)` and compares it to the received `hmac`: [2](#0-1) 
Since `to_signable_string` only includes the body, the `shop-domain` header used to populate `Request#shop` is completely outside the signed data: [3](#0-2) 
`Registry.process` validates the HMAC and then trusts `request.shop` as the tenant identity forwarded to the handler: [4](#0-3) 
`api_secret_key` (the `client_secret`) is shared across all shops that installed the app, not per-shop, so any legitimate installer of the app can generate a genuinely-signed `(raw_body, hmac)` pair for their own shop (e.g. by triggering a real webhook event), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. The signature still validates because it never covered the header, and the handler receives `WebhookMetadata` claiming the data belongs to the victim shop.

The security-relevant equality that should hold is: `shop_bound_by_signature == shop_used_for_tenant_routing`. In this implementation, no such binding exists — `shop` is parsed independently of the verified bytes.

### Impact Explanation
This breaks the tenant boundary the HMAC is meant to guarantee. A malicious app-installing merchant can forge webhook deliveries that the app attributes to a different, victim shop, causing cross-tenant data injection (e.g., fake `orders/create`, `app/uninstalled`, or GDPR-topic payloads processed under another shop's identity). Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up per-shop sessions/records or trigger per-shop side effects), this can lead to data corruption, unauthorized actions performed "as" the victim shop, or information disclosure between tenants — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any actor who can install the app on at least one shop (a minimal bar for many public/embedded apps) and can control the webhook endpoint's HTTP request (since this is a plain HTTP POST endpoint the merchant's own infrastructure — or any MITM/testing tool between Shopify and the app — can replay with modified headers). No access token, `client_secret`, or privileged credentials are required beyond the ability to trigger one genuine webhook for the attacker's own shop.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) into the signed payload, or otherwise cryptographically bind the identity fields to the HMAC before trusting them. At minimum, `to_signable_string` should incorporate the `shop-domain` header (and other identity-bearing headers) so that any header tampering invalidates the signature, e.g.:

```ruby
def to_signable_string
  "#{shop}\n#{@raw_body}"
end
```

with the corresponding change on Shopify's signing side, or — more practically since Shopify controls the signing — the gem should treat the header-derived `shop` as untrusted unless independently corroborated (e.g., cross-checked against `body["shop_domain"]` or app-registered shop sessions before dispatching to handlers), and document this clearly so host apps don't rely on `WebhookMetadata#shop` as an authenticated tenant identifier.

### Proof of Concept
1. App is installed on `attacker.myshopify.com`. Attacker triggers any subscribed webhook topic (e.g., `orders/create`) for their own shop, capturing the genuine `raw_body` and `x-shopify-hmac-sha256` header Shopify sends.
2. Attacker replays an HTTP POST to the app's webhook endpoint with the exact same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` — validation succeeds. [5](#0-4) 
4. The app's registered handler receives `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body:, ...)` and processes attacker-controlled data as if it belongs to `victim.myshopify.com`.
