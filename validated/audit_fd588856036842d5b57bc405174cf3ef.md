Confirmed: `Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `shop`, `topic`, and `webhook_id` headers are never part of the HMAC-verified bytes, and `ShopValidator` is never invoked on the webhook `shop` header.

### Title
Webhook `shop-domain` header is not covered by the HMAC, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, while the `shop-domain`, `topic`, and `webhook-id` headers are read directly from unauthenticated HTTP headers and passed straight through to the app's webhook handler. Because the app's `api_secret_key` is shared across every shop that installs the app, any merchant that has legitimately installed the app can capture a valid `(body, hmac)` pair from their own webhook deliveries and replay it against the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop, producing a webhook that passes HMAC validation but is falsely attributed to another tenant.

### Finding Description
`Webhooks::Registry.process` validates a webhook exclusively with `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` and `request.hmac`: [2](#0-1) 

`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are pulled straight from HTTP headers with no cryptographic binding to the signed bytes: [3](#0-2) 

`HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, raw_body)` and compares it to the `hmac-sha256` header using `OpenSSL.secure_compare`: [4](#0-3) 

The equality this code is supposed to enforce is:
`(shop attributed to the event) == (shop that produced the signed bytes)`

but only `(hmac-computed-from-body) == (hmac header)` is actually checked. The `shop-domain` header — which is handed to the handler as the tenant identifier via `WebhookMetadata` — is completely outside the signed payload: [5](#0-4) 

Since `api_secret_key` is a single, app-wide secret (not per-shop), a legitimate low-privilege merchant who has installed the app receives real `(body, hmac)` pairs from Shopify for their *own* shop. That attacker-controlled merchant can replay the exact same body/HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value (any `*.myshopify.com` string, or a real victim domain), and `HmacValidator.validate` will still return `true` because it never inspects the header. `ShopValidator`, which exists in the gem, is never called on the webhook `shop` header to constrain it to a value consistent with the request origin: [6](#0-5) 

### Impact Explanation
This breaks the tenant-identity binding between an HMAC-authenticated webhook and the shop it is attributed to. A shop-scoped, unprivileged internet user (any merchant who installs the app once) can produce webhook deliveries to the app's callback endpoint that pass signature verification but claim to originate from a different, victim shop domain of their choosing. Depending on how the host application's webhook handler uses `data.shop` (e.g., to select which tenant's local record to create/update/delete, e.g. on `app/uninstalled`), this enables cross-tenant data corruption or spoofing — matching the Critical "cross-tenant access" impact category, since the only thing standing between the attacker and impersonating any other shop is the unauthenticated header value.

### Likelihood Explanation
Likelihood is Medium-to-High: no leaked credentials or privileged account access are required beyond installing the app once as any merchant (which is normally free/self-service for a Shopify app), and the attacker fully controls the HTTP headers of the replayed request to the app's own publicly reachable webhook endpoint.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the signed/verified material, or otherwise cryptographically bind the shop the webhook is attributed to (e.g., by requiring the caller to also validate the shop domain via `ShopValidator` against a shop known to have that webhook subscription/registration, or by validating source IP/mTLS in addition to HMAC). At minimum, document and enforce that host applications must independently verify `data.shop` against a shop that has both installed the app and has an active subscription for the given `webhook_id`/topic before trusting it as a tenant identifier.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, and the app registers a webhook (e.g. `orders/create`) for the topic.
2. Shopify delivers a legitimate webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`, and some JSON body.
3. Attacker captures this `(body, hmac)` pair (they own the request, no secret needed).
4. Attacker resends an HTTP POST to the same webhook endpoint with the identical body and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `request.to_signable_string` (`@raw_body`) — unchanged — so validation succeeds:
`OpenSSL.secure_compare(computed_signature, received_signature) == true`
6. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the host app to act on data attributed to `victim-shop.myshopify.com` even though the payload actually came from the attacker's own shop.
