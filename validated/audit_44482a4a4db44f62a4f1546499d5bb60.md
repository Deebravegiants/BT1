### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant routing while only the raw body is HMAC-verified, enabling cross-shop webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) and event type (`topic`) used by `Registry.process` purely from HTTP headers, while `Utils::HmacValidator` only authenticates the raw request body bytes. Because the signature never binds `shop`/`topic` to the body, a party who can obtain one genuine `(raw_body, hmac)` pair from Shopify (e.g., by triggering a webhook on their own store, which any merchant/developer can freely do) can replay that exact payload to the target app's webhook endpoint while forging the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to claim it belongs to a different shop. The app has no way to detect this, since the only integrity check performed (`Utils::HmacValidator.validate`) never touches those headers.

### Finding Description
`Request#to_signable_string` returns solely the raw body: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively from `to_signable_string`, i.e. only the body: [2](#0-1) 

Meanwhile, `Request#shop` and `Request#topic` are read straight from attacker-controllable HTTP headers with no cryptographic binding to the verified body: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` and `request.topic` (both unauthenticated) to route/dispatch the event and to construct `WebhookMetadata` that host applications use as the tenant key: [4](#0-3) 

The binding that should hold is:
`hmac_valid(raw_body) == true` should imply `(raw_body, shop, topic)` were jointly produced/signed by Shopify for that specific shop and topic. Instead, the gem only proves `hmac_valid(raw_body) == true`; `shop` and `topic` are independent, unauthenticated inputs. Any `(raw_body, hmac)` pair that Shopify legitimately signs — regardless of which shop/topic it was originally sent for — will pass `HmacValidator.validate` no matter what `shop-domain`/`topic` headers are attached to the replayed request.

### Impact Explanation
This breaks the tenant boundary the whole webhook subsystem is built on. An attacker who controls or can trigger events on *any* Shopify shop (their own store, a free/dev store, or one they have any legitimate access to) can capture a validly-signed `(body, hmac-sha256)` pair from a webhook Shopify sends to any endpoint they control, then replay that exact body/HMAC to the *victim* app's webhook receiver with a forged `X-Shopify-Shop-Domain` header pointing at any target shop of the attacker's choosing. Because `Registry.process` never checks that the signed body actually corresponds to the claimed shop, the host application's handler executes as if the event genuinely occurred for that shop — this is a cross-tenant confusion: `WebhookMetadata#shop` is used by consuming apps as the authoritative session/tenant key (see `docs/usage/webhooks.md`), so data can be attributed to, or actions taken against, the wrong tenant purely off attacker-controlled headers with only a stolen/self-triggered body+HMAC to satisfy the "authentication" step. Depending on the topic (`app/uninstalled`, `shop/redact`, `customers/data_request`, billing topics, etc.) this can trigger cross-tenant data deletion, incorrect session invalidation, or forged compliance/billing events for shops the attacker has no access to — meeting the "cross-tenant access" bar without any access token, `api_secret_key`, or privileged credential of the victim.

### Likelihood Explanation
Likelihood is high for any app relying on this gem's default webhook verification: obtaining one legitimately-signed body/HMAC pair only requires the attacker to control (or transiently interact with) *some* Shopify shop capable of emitting a webhook to an endpoint they own — a routine, unprivileged action available to any developer/merchant. No secret material belonging to the target shop or the app owner is needed; only network access to POST to the app's public webhook endpoint with forged headers, which is inherent to any internet-reachable webhook receiver built on this gem's guidance.

### Recommendation
Bind `shop` and `topic` into the HMAC-covered signable content (or otherwise authenticate them, e.g. by looking up the calling shop out-of-band and rejecting the body if it deviates), so that `Utils::HmacValidator.validate` fails whenever the claimed shop/topic don't match what Shopify actually signed the payload for. At minimum, document and provide a validated way to cross-check `shop`/`topic` headers against the body content or a shop registry before dispatching to `handler.handle`.

### Proof of Concept
1. Attacker installs (or already has) any public/dev Shopify app that emits webhooks (e.g., subscribes their own `attacker-shop.myshopify.com` to a topic) and stands up a listener to receive Shopify's legitimately signed webhook: raw body `B` with header `X-Shopify-Hmac-Sha256: H` (computed by Shopify with the target app's shared secret) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker replays the identical `B`/`H` to the target app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`).
3. The app builds a `ShopifyAPI::Webhooks::Request` from these headers/body and calls `Registry.process`:
```ruby
request = ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {
  "x-shopify-hmac-sha256" => H,
  "x-shopify-topic" => "app/uninstalled",
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",
})
ShopifyAPI::Webhooks::Registry.process(request) # passes HMAC check, dispatches as victim-shop
```
4. `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes HMAC over `B`, which is unchanged. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", ...)` even though Shopify never signed anything about `victim-shop.myshopify.com` — a full cross-tenant spoof using only a self-obtained webhook.
