### Title
Emporium wallet-signed flow omits variable-rate relay fee, allowing unprivileged users to underpay relay/protocol fees - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.payRelayFees` computes the relay fee differently depending on whether `signerAddress` is set (wallet-signed flow) or not (direct flow). The direct flow correctly applies both the flat fee and the variable-rate cut via `hinkalHelper.calculateRelayFee(sumAbs, flatFee, variableRate)`, while the wallet-signed flow only ever pays `flatFee`, silently dropping the `variableRate` component of the fee.

### Finding Description
In `payRelayFees` [1](#0-0) , the two branches compute `relayFee` inconsistently:

```solidity
if (signerAddress == address(0)) {
    uint256 sumAbs = uint256(-deltaAmountChanges[i]);
    relayFee = $._hinkalHelper.calculateRelayFee(sumAbs, flatFee, feeStructure.variableRate);
} else {
    relayFee = flatFee;
}
```

`calculateRelayFee` (in `RelayStore.sol`) applies both the flat fee and a percentage cut (`variableRate`) of the remaining balance: [2](#0-1) . This is the same calculation used in `Hinkal._internalTransact` for the standard (non-Emporium) path [3](#0-2) , confirming that the intended fee model always includes the variable component.

However, when `stack.signerAddress != address(0)` — i.e., the caller routes the Emporium operation through a signed `HinkalWallet` op (`EmporiumStack.signerAddress`, set by the transacting user themselves as part of the `externalActionMetadata` they construct) [4](#0-3)  — only `flatFee` is charged to the relay, and the `variableRate` cut is never applied or transferred anywhere. `verifyWallet` only checks that `flatFee <= stack.maxFee`, never referencing `variableRate` at all [5](#0-4) . This mirrors the report's bug class: two implementations of the same fee/reserve check exist in the codebase, one of which omits a component (fee amount / variable rate) that the other correctly includes, causing the protocol to under-collect what it is owed.

### Impact Explanation
Any unprivileged EOA can choose to route calls through the Emporium wallet-signed path (`invokeWallet`/`signerAddress` set) instead of the direct path, and will only be charged `flatFee`, permanently bypassing the `variableRate` cut of relay/protocol revenue that the identical operation would incur via the non-wallet path or via `Hinkal._internalTransact`. This is a systematic underpayment (effectively theft) of protocol/relay fees, matching the "High - theft ... of protocol/relay fees" impact category.

### Likelihood Explanation
High. No privileged role is required — this fee-selection is purely a function of which parameters the caller supplies in `circomData.externalActionData.externalActionMetadata` (the `EmporiumStack.signerAddress`), fields entirely controlled by the transacting user/relayer submitting the proof and calldata. Any user electing to use the wallet-signed Emporium path will always underpay relative to the direct path for the same swap/action.

### Recommendation
Apply `calculateRelayFee` (flat fee + variable-rate cut) uniformly regardless of whether `signerAddress` is set, or explicitly document/enforce that the wallet-signed flow can only be used together with a compensating fee model, and cap `maxFee` against the full computed fee (including variable rate) rather than only `flatFee` in `verifyWallet`.

### Proof of Concept
Conceptual PoC (cannot be executed without full test harness, but derivable directly from the code):
1. User A calls `transact` with `externalActionId` = Emporium, `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` (direct call) and a swap of amount `X` of `erc20Token` with `feeStructure.variableRate = V`. Relay receives `flatFee + V% of (X - flatFee)`.
2. User B performs an economically identical operation (same `erc20Token`, same `X`, same `feeStructure`) but instead sets `EmporiumStack.signerAddress` to their own `HinkalWallet` and routes the same call via `invokeWallet = true` (stateful path) with a valid EIP-712 signature.
3. In `payRelayFees`, since `signerAddress != address(0)`, `relayFee` is set to `flatFee` only [6](#0-5) ; the `V%` variable cut that User A paid is never collected from User B, even though the relay performed the same amount of work and the fee structure specified the same `variableRate`.

**Note on uncertainty:** I could not find test files or off-chain documentation confirming whether omitting the variable-rate fee in the wallet-signed path is an intentional design decision (e.g., because the variable-rate portion depends on a post-execution balance delta unknown at signature time) versus an unintentional bug. The code itself, however, treats these as if they should be equivalent fee mechanisms (`flatFee` is checked against `stack.maxFee` in both paths), and no comment in the contract explains or justifies the asymmetry, which is why I flag it as an inconsistency analogous to the reported bug class rather than a confirmed intentional omission.

        uint256 variableRate
