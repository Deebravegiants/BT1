### Title
Webhook `shop` (and other identity headers) are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (`File: lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content as the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` fields used by the registry to route and process the webhook are read directly from unauthenticated HTTP headers. This breaks the identity binding: `hmac_valid(body)` does not imply `shop_header == shop_that_produced(body)`, so an attacker who can obtain one genuine, HMAC-valid webhook delivery (e.g., for their own shop, since the app's `client_secret`/`api_secret_key` is shared across all shop installs of the app) can resend the same signed body with a forged `X-Shopify-Shop-Domain` header to make the app process and persist data under a different tenant's identity.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all parsed straight from request headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.topic` for handler dispatch and `request.shop` as the tenant identity passed to the handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the raw body) and compares it to the `hmac` header value — it has no knowledge of, and does not cover, the `shop` header: [4](#0-3) 

The broken equality is: the library treats `hmac_valid(body, secret) == true` as authorization to trust `shop_header` as the origin tenant, when in reality the HMAC only authenticates the *body*, not the *(shop, body)* pairing. Because `api_secret_key` is the same for every shop that installs a given app, any shop's genuine webhook delivery yields a body+HMAC pair that remains valid under the same secret regardless of which shop header accompanies it.

### Impact Explanation
This is a cross-tenant identity binding failure: an attacker who legitimately installs the app on their own store (an ordinary, unprivileged action) will receive genuine, correctly HMAC-signed webhook deliveries for their own shop. They can then replay that exact body with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header changed to a victim shop's domain. `HmacValidator.validate` will still report the HMAC as valid (it never inspected the shop header), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop. Any host application that uses `request.shop`/`data.shop` from this gem to select the tenant record to update (the intended and documented use of this field) will apply attacker-controlled webhook data to the wrong tenant, i.e., cross-tenant data injection/corruption via the app's own trusted webhook pipeline.

### Likelihood Explanation
Likelihood is moderate to high: exploitation requires only that the attacker can install the target app on a shop they control (a normal merchant action, not a privileged one) and can send an arbitrary HTTP POST to the app's public webhook endpoint with copied body/HMAC and a modified shop-domain header — no access to `api_secret_key`, tokens, or the victim's infrastructure is needed.

### Recommendation
- Bind the identity fields (`shop`, `topic`, `webhook_id`, `api_version`) into the HMAC-signable string, or otherwise cryptographically verify that the `shop` header matches the shop embedded/derivable from the signed payload.
- Alternatively, require callers to supply the expected/authenticated shop (e.g., from an authenticated session or subscription lookup) and compare it against the header before trusting `request.shop`, failing closed on mismatch.
- Document and enforce that `Registry.process` must not use unauthenticated header values as tenant identifiers without an explicit secondary integrity check (e.g., confirming a matching, still-registered webhook subscription for that exact shop + topic + webhook_id).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), receiving a POST with a valid `X-Shopify-Hmac-Sha256` header computed over the JSON body using the shared `api_secret_key`.
2. Attacker resends this exact body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses `shop` as `victim-shop.myshopify.com` from the header at line 21-23 of `lib/shopify_api/webhooks/request.rb`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `@raw_body` against the HMAC secret (`lib/shopify_api/utils/hmac_validator.rb:12-31`), never inspecting the shop header.
5. The handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) and, following the gem's documented usage pattern, applies the attacker's order data to the victim's tenant record.
