### Title
Webhook `shop-domain` Header Not Covered by HMAC Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` (and `topic`) values used by `ShopifyAPI::Webhooks::Registry.process` to identify the tenant are taken from HTTP headers that are never included in the HMAC computation. An attacker who can produce (or replay) a body/HMAC pair valid for the shared `api_secret_key` can freely swap the `shop-domain` header to any target shop and have the webhook accepted as authentic for that shop.

### Finding Description
`Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 

only `@raw_body` is signed. The `shop`, `topic`, `api_version`, and `webhook_id` values are read straight from headers with no cryptographic binding: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string` (i.e., the body) and compares it with the `hmac-sha256` header: [3](#0-2) 

`Registry.process` validates only the HMAC and then dispatches the handler using the unauthenticated `request.shop`/`request.topic` values: [4](#0-3) 

Because the same `api_secret_key` is shared across all shops installed on an app, and because many webhook topics have identical or attacker-predictable bodies (e.g., `app/uninstalled` sends `{}`, and other topics can produce identical JSON payloads for different shops), the equality the gem is implicitly relying on:

`HMAC(secret, body) valid` == `body and shop-domain header both originate from Shopify for that shop`

does not hold. In truth only the body is authenticated; the `shop-domain` header is not bound to the signature at all. An attacker who operates their own store with the app installed receives genuine webhooks (with valid HMACs) from Shopify. They can capture one such valid `(body, hmac)` pair and resend it to the app's webhook endpoint with the `shop-domain` header changed to an arbitrary victim shop domain. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be for the victim shop.

### Impact Explanation
This breaks the tenant-identity binding that host applications rely on to route webhook events to the correct merchant record. Since `Registry.process` supplies `request.shop` directly to the handler without any verification that it matches the shop that actually produced the signed body, a host application using this gem's webhook pipeline can be induced into processing attacker-forged events "as" an arbitrary victim shop (cross-tenant confusion), e.g., triggering `app/uninstalled` handling, forcing token/data cleanup, or invoking other topic handlers against a store the attacker does not control.

### Likelihood Explanation
The prerequisite is modest: any user who can install the app on a store they control can obtain valid `(body, hmac)` pairs for topics with static or attacker-influenceable bodies, then replay them against the same public webhook endpoint with a forged `shop-domain` header. No secret material, TLS interception, or privileged access is required — only network access to the app's public webhook receiver.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values in the signable string used for HMAC verification, or otherwise cryptographically bind the shop identity to the signature (matching the pattern used for the `hmac`, but covering headers, not merely the body). At minimum, `Registry.process` should refuse to trust `request.shop` unless it has been verified as part of the signed payload.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a real webhook for topic `app/uninstalled` with body `{}` and header `x-shopify-hmac-sha256: <valid-hmac-for-empty-body>`.
2. Attacker resends the exact same request to the app's public webhook endpoint, keeping body `{}` and the same valid HMAC, but changing `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present), `Utils::HmacValidator.validate` returns `true` because `to_signable_string` only checks `{}` against the secret (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the registered `app/uninstalled` handler with `shop: "victim-shop.myshopify.com"`, even though this request never actually originated from Shopify for that shop.
