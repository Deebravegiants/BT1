### Title
Same-asset batch PoA withdrawals collapse to one status via `findMatchingWithdrawal`, causing double-credit misreporting - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
When a user submits a batch intent with two or more PoA-bridged withdrawals of the same `assetId` (e.g. two `nep141:btc.omft.near` legs to different destinations), `describeWithdrawal` uses `findMatchingWithdrawal`, which matches purely by `near_token_id`/`assetId` and ignores the withdrawal's `index`. Every `watchWithdrawal` call for that route/assetId therefore reports the status/txHash of the same first-matching API entry, regardless of which of the multiple legs is actually being watched.

### Finding Description
The broken equality: `watchWithdrawal(wid(index=i)).txHash` should equal the on-chain outcome of leg `i` specifically. Instead, because `findMatchingWithdrawal` in [1](#0-0)  does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)`, it always returns the array's first entry matching `assetId`, irrespective of `index`. `describeWithdrawal` at [2](#0-1)  passes only `args.withdrawalParams.assetId` to the matcher, never `args.index`.

Reachable path: `sdk.signAndSendWithdrawalIntent`/`processWithdrawal` accept a `WithdrawalParams[]` batch (see [3](#0-2) ), an ordinary user can submit N legs with the identical `assetId` and different `destinationAddress`/`amount`. `createWithdrawalIdentifiers` in [4](#0-3)  assigns increasing `index` values per bridge route but does not disambiguate withdrawals of the same asset in any way that survives into `describeWithdrawal`. `createWithdrawalCompletionPromises` in [5](#0-4)  then calls `watchWithdrawal` independently, once per leg, all reaching the same `findMatchingWithdrawal` code.

Because `Array.prototype.find` deterministically returns the first match for every call, both `watchWithdrawal` calls for index 0 and index 1 (or however many legs share the assetId) resolve to the exact same `withdrawal` object from the API response — same `status`, same `txHash` — not "swapped" per the question's phrasing, but literally identical. This means the completion promise for leg 1 reports the txHash that actually corresponds to leg 0's transfer (or vice versa, depending on which happens to be "first" in the unsorted array), while the true transfer for the other destination is never distinctly reported.

No existing guard catches this: `supports()`, `validateWithdrawal`, `compareAddresses`, `FeeExceedsAmountError` etc. all operate on individual withdrawal params pre-submission and have no visibility into duplicate-assetId batches; nothing in `createWithdrawalIdentifiers` rejects or special-cases duplicate assetId within a route. The code's own comment block (lines 409-416) explicitly acknowledges: "multiple withdrawals of the same token in a single transaction are not supported."

### Impact Explanation
An integrator relying on `createWithdrawalCompletionPromises` or `waitForWithdrawalCompletion` for a batch with duplicate-asset legs receives the same `txHash`/status for multiple distinct withdrawal identifiers. If the integrator credits/refunds a destination based on the reported txHash-to-index mapping, it can end up crediting the wrong destination address's transfer or crediting/reconciling one destination twice while leaving the other's actual transfer unaccounted for. This matches the High-severity category: "a status or hash misreport making an integrator credit or refund twice." It's repeatable on every batch submission containing duplicate PoA assetIds.

### Likelihood Explanation
Preconditions are trivial and fully attacker-controlled: any ordinary user (or an integrator forwarding user-supplied `withdrawalParams`) can construct a batch with two-or-more legs of the same PoA-supported `assetId`. No special routeConfig, solver cooperation, or contract state is needed — batch withdrawals are a first-class, documented SDK feature. Cost is a single normal intent submission.

### Recommendation
Disambiguate matching in `findMatchingWithdrawal`/`describeWithdrawal` beyond `assetId` alone — e.g. reject (throw) when `createWithdrawalIdentifiers` detects duplicate `assetId` within the PoA route until the POA bridge API supports index-based or amount-based disambiguation, as hinted in the existing code comment (sort both withdrawals and API results by amount and match positionally). At minimum, `describeWithdrawal` should not silently return identical results for distinct `WithdrawalIdentifier.index` values sharing an assetId.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
