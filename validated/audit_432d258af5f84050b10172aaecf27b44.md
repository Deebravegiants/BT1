This confirms the vulnerability: `Registry.process` dispatches to the handler using `request.shop` (from the `shopify-shop-domain` header) as the tenant identity, but `Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` is computed only from the `shopify-hmac-sha256` header — the topic, shop-domain, api-version, and webhook-id headers are never included in the HMAC-verified content.

### Title
Webhook shop-domain header is trusted for tenant identity but is not covered by HMAC verification - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands `request.shop` (parsed from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header) to the app's handler as the tenant identifier for that payload. Because the header is not part of the signed content, the binding `hmac_verified(body) == shop_attributed(payload)` does not hold.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`, which for a webhook `Request` is just the raw body [1](#0-0) . The `shop` accessor, however, is read straight from request headers and is never part of that signed string [2](#0-1) .

`Registry.process` validates the HMAC once, then trusts `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` — none of which are covered by that signature — and forwards them straight to the app-supplied handler as authenticated tenant/topic metadata: [3](#0-2) .

Since `OpenSSL::HMAC` only signs `@raw_body`, any request whose body/HMAC pair was legitimately produced by Shopify for one shop remains "HMAC-valid" no matter what value is placed in the `shopify-shop-domain` header. The equality that should hold — `hmac_covers(shop) == shop_used_for_tenant_routing` — is broken: the HMAC covers only the body, while the shop value used to route data into the host app's per-tenant handler comes from an unauthenticated header.

### Impact Explanation
An unprivileged internet user who can capture (or is themselves the recipient of, as an app-installing merchant) one legitimate webhook body+HMAC pair for shop A can resend that exact body and HMAC to the app's webhook endpoint while substituting `shopify-shop-domain: B`. `Utils::HmacValidator.validate` still returns `true` because the body and HMAC are unchanged, and `Registry.process` will invoke the handler with `shop: "B"`, causing shop A's data to be attributed to and processed under tenant B in the host application — a cross-tenant data-confusion/injection primitive delivered entirely with attacker-controlled headers and no knowledge of `api_secret_key`.

### Likelihood Explanation
Any external actor able to reach the app's public webhook endpoint can attempt this; capturing one genuine webhook (e.g., by installing the app on their own shop and recording webhooks Shopify sends them) is sufficient to obtain a valid body+HMAC pair. No secret key, session, or elevated privilege is required — only observation of one legitimate delivery and the ability to POST to the webhook route with a forged `shop-domain` header.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC-signed material (or otherwise cryptographically bind them to the verified body, e.g., via a signed envelope), so `HmacValidator.validate` fails whenever any of these fields is altered relative to what Shopify actually sent. At minimum, `ShopifyAPI::Webhooks::Request#to_signable_string` should incorporate the shop domain and topic rather than only `@raw_body`.

### Proof of Concept
1. Install the app on shop A (`a.myshopify.com`) and capture a legitimate webhook delivery: raw body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Send a new POST to the app's webhook endpoint with the same body `B` and header `shopify-hmac-sha256: H`, but set `shopify-shop-domain: victim-shop.myshopify.com` and any desired `shopify-topic`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and finds it equal to `H` [4](#0-3)  — validation passes.
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` [5](#0-4) , causing the host app to process shop A's captured payload as if it originated from `victim-shop.myshopify.com`.
