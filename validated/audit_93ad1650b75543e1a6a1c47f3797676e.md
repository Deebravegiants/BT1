Confirmed: `shop` in `ShopifyAPI::Webhooks::Request` is read purely from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header, while `to_signable_string` — the data actually covered by the HMAC — is only `@raw_body`. `Registry.process` validates the HMAC over the body only, then hands `request.shop` straight to the handler with no further check.### Title
Webhook shop attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` derives the shop that a webhook is attributed to purely from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, while the HMAC signature that `Registry.process` verifies only covers the raw request body. Because the shop identity is never bound into the signed material, any party who can produce one valid `(raw_body, hmac)` pair—simply by receiving a single legitimate webhook from Shopify for a store they control (e.g., a free/dev store where they install the app)—can replay that exact body/HMAC pair while substituting an arbitrary victim `shop-domain` header. The signature check still passes, and the registered handler receives a `shop` value that does not correspond to the tenant that actually produced the signed payload.

### Finding Description
`Request#hmac` and `Request#to_signable_string` bind the signature validation exclusively to `@raw_body`: [1](#0-0) 

`Request#shop` reads directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, a field that plays no part in `to_signable_string`: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` (which checks `to_signable_string`, i.e. `raw_body`, against `Context.api_secret_key`) and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler, with no additional binding check between the verified body and the claimed shop: [3](#0-2) 

The identity binding that should hold is:
`shop that HMAC-signed the payload == shop attributed to the WebhookMetadata handed to the app`

What actually holds is:
`HMAC(raw_body, api_secret_key) == received_hmac` AND `shop = arbitrary unauthenticated header value`

These are independent checks. The `api_secret_key` used to compute the HMAC is the same secret for **every shop** that has installed the app (it is the app's client secret, not a per-shop secret), so a valid `(raw_body, hmac)` pair captured from a webhook fired for shop A remains "valid" (in the sense that `Utils::HmacValidator.validate` returns true) no matter which shop-domain header is attached to the replayed request.

### Impact Explanation
This breaks the tenant/shop isolation that host applications rely on `ShopifyAPI::Webhooks::Registry.process` + `WebhookMetadata#shop` to enforce. An attacker who legitimately installs the target app on any shop they control (including a free development store, which requires no privileged credentials) can:
1. Trigger and capture a legitimate webhook `(raw_body, hmac, topic)` for their own store.
2. Replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim merchant's domain.
3. Have the app's registered handler process attacker-controlled body content as if it came from the victim shop — the handler receives `WebhookMetadata.shop == victim-shop` while `body` is fully attacker-chosen (from their own store data).

Depending on how the host app uses `data.shop` (e.g., looking up/mutating per-shop records, triggering mandatory `shop/redact` / `customers/redact` flows, updating billing/subscription state, or writing merchant-scoped audit data), this is a cross-tenant data-integrity/confusion issue: one merchant can inject or forge events attributed to a different merchant's tenant. This matches the "cross-tenant access" impact category, since the tenant boundary (`shop`) is not authenticated by the mechanism the library exposes for that purpose.

### Likelihood Explanation
High. No privileged credentials, leaked secrets, or social engineering are required — only the ability to install the app on any Shopify store (including a free trial/dev store) to receive at least one authentic webhook, and then to send a crafted HTTP request to the target app's public webhook endpoint with a different `shop-domain` header. This is a pure two-header-and-body HTTP replay against the gem's documented `Registry.process` entry point.

### Recommendation
Bind the shop used for `WebhookMetadata` to material that is actually covered by the HMAC, or otherwise cryptographically authenticate the shop-domain header per request. Options:
- Include the `shop-domain` (and `topic`/`webhook-id`) header values in the signable string used for HMAC verification, so any header tampering invalidates the signature.
- Alternatively, require host applications to cross-check `request.shop` against an independently-verified expectation (e.g., the shop tied to the session/subscription the webhook was registered for) before trusting it, and document this requirement explicitly, since currently `Registry.process` implicitly presents `request.shop` as verified.

```diff
 sig { override.returns(String) }
 def to_signable_string
-  @raw_body
+  "#{shop}\n#{topic}\n#{@raw_body}"
 end
```
(with the corresponding change needed server-side or a documented requirement that `shop` must be independently re-validated by the host application before use.)

### Proof of Concept
```ruby
require "shopify_api"
require "openssl"
require "base64"

secret = ShopifyAPI::Context.api_secret_key # shared across all shops using this app

# Step 1: attacker installs app on their own (attacker-controlled) shop and
# captures a legitimate webhook fired for that shop.
raw_body = '{"id": 1, "note": "legit payload from attacker-owned shop"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, raw_body)

# Step 2: attacker replays the same signed (body, hmac) pair, but swaps the
# shop-domain header to a victim's shop.
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # <-- attacker controlled, unauthenticated
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# HMAC validation still succeeds because it only checks raw_body against the shared secret.
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process will now invoke the registered handler with shop == "victim-shop.myshopify.com"
ShopifyAPI::Webhooks::Registry.process(request)
```

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
