## Title
Session ID Trusted From Unauthenticated Cookie Bytes Enables Cross-Tenant Session Hijacking - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` derives the session identifier for non-embedded (and cookie-fallback) requests directly from the raw `shopify_app_session` cookie value, with no cryptographic verification that the value actually originated from a completed OAuth flow for that shop. Combined with the fact that session IDs are deterministic, guessable strings (`"offline_#{shop}"` or `"#{shop}_#{user_id}"`), an attacker can set an arbitrary session-ID cookie and have the host application treat the request as belonging to a different, victim shop.

### Finding Description
When an app completes the Authorization Code Grant OAuth flow for a non-embedded app, `ShopifyAPI::Auth::Oauth.validate_auth_callback` builds a `SessionCookie` whose `value` is simply `session.id`: [1](#0-0) 

That `id` is deterministic and computed purely from the shop domain (and user id for online sessions): [2](#0-1) 

The `SessionCookie` itself carries no signature or MAC — it is a plain `T::Struct` with `name`, `value`, `expires`: [3](#0-2) 

Later, to identify "the current session" for a request, `SessionUtils.current_session_id` reads this cookie value back **verbatim**, with no validation that it was actually issued by this library/OAuth flow: [4](#0-3) [5](#0-4) 

Contrast this with the embedded-app path, where the session id is derived from a verified JWT (`Auth::JwtPayload`, HMAC-signed with `api_secret_key`) — a properly authenticated binding. The cookie path has no equivalent binding: the "identity" (session id) that is handed to the host application's session store lookup is taken from bytes the client fully controls, breaking the implicit equality the library is supposed to guarantee:

`session_id_returned_by_gem == session_id_of_an_OAuth-authenticated_session`

Because the id format is public and predictable (just `"offline_" + shop_domain`, and shop domains are public `*.myshopify.com` strings), any client can construct `Cookie: shopify_app_session=offline_<victim-shop>.myshopify.com` and send it to the app. `current_session_id` will happily return `"offline_<victim-shop>.myshopify.com"`, which the host application (per the documented usage pattern in `docs/getting_started.md` and `docs/usage/oauth.md`) uses as the key to fetch the victim's persisted `Session`/access token from its session repository — resulting in the requester being treated as an authenticated request for the victim shop.

### Impact Explanation
This breaks the tenant boundary between shops without any secret, access token, or privileged access being required by the attacker — only knowledge (or a guess) of the victim's shop domain. It is a cross-tenant session hijack / authentication-bypass vector: `SessionUtils.current_session_id`, the library's documented API for identifying "the session for this request," returns an unauthenticated, attacker-suppliable value as if it were an authenticated identity.

### Likelihood Explanation
The session-id format is fixed and simple to reproduce (`"offline_#{shop}"`/`"#{shop}_#{user_id}"`), and shop domains are not secrets — they are visible in URLs, App Bridge configuration, admin links, etc. No cryptographic material, access token, or TLS interception is needed to exploit this; the attacker only needs to set an HTTP cookie header on their own request to the target app.

### Recommendation
Bind the session-cookie value to an authenticated proof (e.g., sign/HMAC the cookie value with `api_secret_key`, similar to how `HmacValidator`/`JwtPayload` protect OAuth callback and session-token flows) and verify that signature inside `SessionUtils.cookie_session_id`/`current_session_id` before trusting the derived session id, rather than returning the raw cookie contents unchecked.

### Proof of Concept
1. App A (attacker-controlled) completes the non-embedded OAuth flow normally; attacker observes that their own session cookie value is `offline_shop-a.myshopify.com`, confirming the deterministic `offline_#{shop}` format used by `SessionUtils.offline_session_id`.
2. Attacker sends a request to the target app's protected endpoint with header:
   `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`
3. The host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which — per `cookie_session_id` — returns `"offline_victim-shop.myshopify.com"` unchanged, with no verification.
4. The host app looks up its session store using this id and retrieves `victim-shop`'s persisted `Session` (access token), then serves the attacker's request as if authenticated for `victim-shop`.

      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
      end
