## Title
Race condition (TOCTOU) in `ConnectedOrigins` allows cross-origin trust/connection state corruption due to non-atomic read-modify-write — (File: `features/connected-origins/module/connections.js`)

## Summary
The Sherlock report describes a reentrancy bug where `sellNFT()` lacks any concurrency guard around a multi-step read → compute → delete sequence, letting an attacker interleave calls and corrupt/wipe shared array state (the orderbook). The `@exodus/connected-origins` module in this repository has the same structural weakness: several public state-mutating methods (`connect`, `disconnect`, `untrust`, `setAutoApprove`, `setFavorite`, `updateConnection`, `clearConnections`) perform an unguarded **get-then-set** cycle over the entire `connectedOriginsAtom` array, with no mutual exclusion across these different call sites.

## Finding Description
`ConnectedOrigins` reads the full list of connected origins, computes a new array, and writes it back: [1](#0-0) [2](#0-1) 

Each of these calls (`connect`, `disconnect`, `untrust`, `setAutoApprove`, `setFavorite`, `updateConnection`, `clearConnections`) independently does `#getData()` (a snapshot read of the atom) then, after arbitrary async work, `#setData()` (a full overwrite of the atom) via `#setAttributes`: [3](#0-2) 

While the underlying atom's own `set()` primitive is internally serialized with `makeConcurrent` so that a *single* `.set(value)` call is atomic with respect to other `.set()` calls on the same atom: [4](#0-3) 

this only protects the atom's own get/set implementation detail — it does **not** make the higher-level compound operation (`getData → compute newData → setData`) atomic. If two of these methods are invoked concurrently (e.g. `connect({id, origin: 'siteA.com'})` and `disconnect({id, origin: 'siteB.com'})`, or `untrust({origin: 'siteB.com'})`), both can read the same pre-change snapshot of the origins array before either write lands. The second `set()` call then overwrites the atom with a version of the array computed from the stale snapshot, silently reverting whatever the first call did — a classic lost-update/TOCTOU race, structurally identical to the missing reentrancy guard in `sellNFT()` that let repeated deletions clobber unrelated buy orders.

## Impact Explanation
`connect`/`disconnect` and related calls are driven by web-page/dApp interactions through the wallet's Web3 provider layer (site connection/disconnection flows described in `docs/web3-providers/solana-provider-api.md` and the `connected-origins` README): [5](#0-4) 

Because there is no mutual exclusion across the whole read-modify-write sequence spanning different origins, a malicious or compromised website can race its own connect/disconnect calls (or simply flood them) at the same time legitimate operations are occurring for other origins, causing the shared `connectedOriginsAtom` to be corrupted:
- an `untrust`/`disconnect` for one origin can be silently reverted (leaving a revoked/malicious site's trust or active connection restored — an authorization/trust bypass), or
- a legitimate site's `activeConnections`/`trusted`/`autoApprove` state can be wiped out by a concurrent write from an unrelated origin's operation (a cross-origin state bleed / DoS on the connection registry), which also feeds `#connectedAccountsAtom`: [6](#0-5) 

This maps to the "cross-origin privilege bleed" category: an unprivileged web page can influence/corrupt the trust and auto-approve state governing other origins' access to wallet accounts and addresses, without any special privilege beyond normal dApp connection flow.

## Likelihood Explanation
Likelihood is moderate: it requires overlapping async operations touching the connected-origins atom (e.g., a malicious site opening/reconnecting rapidly while the user is interacting with another connected dApp, or a site issuing back-to-back connect/disconnect calls while another tab's dApp session updates state). Since browser extensions routinely have multiple tabs each with their own dApp connection to the same background wallet instance, such interleavings are realistically triggerable by a malicious/compromised website without any user action beyond normal browsing with multiple tabs open.

## Recommendation
Serialize all `ConnectedOrigins` mutation methods (`connect`, `disconnect`, `untrust`, `setAutoApprove`, `setFavorite`, `updateConnection`, `clearConnections`, `#addNewItem`) behind a single mutex (e.g. `makeConcurrent`) so the entire get-modify-set sequence is atomic, or migrate the update to use the atom's functional `set((previous) => ...)` form (already supported by the underlying atom, see `enforce-rules.ts` lines 96-106) instead of separate `#getData()`/`#setData()` calls, eliminating the TOCTOU window entirely.

## Proof of Concept
Not independently executed against the live extension; based on static analysis of the read-modify-write pattern:
```js
// Site A calls disconnect to revoke itself
connectedOrigins.disconnect({ id: 'a-conn', origin: 'siteA.com' })
//   -> #getOrigin reads current array snapshot S0
//   -> computes newConnections without 'a-conn'
//   -> awaits #setAttributes -> #getData() (async) -> ... -> #setData(newData_A)

// Concurrently, Site B calls untrust
connectedOrigins.untrust({ origin: 'siteB.com' })
//   -> reads the SAME snapshot S0 (before A's write lands)
//   -> computes newData_B = S0.filter(o => o.origin !== 'siteB.com')
//   -> writes newData_B, which does NOT contain A's disconnection change

// Result: whichever write lands last overwrites the other's change.
// If B's write lands after A's, Site A's disconnected/active connection
// entry re-appears (or is dropped) depending on ordering — attacker-controlled
// via timing of its own RPC calls.
``` [3](#0-2) [7](#0-6) 

**Uncertainty / follow-up needed:** I could not confirm from static indexing alone whether an upstream RPC/permission layer restricts which origin string can be passed to `connect`/`disconnect`/`untrust` (i.e., whether a malicious site can only ever pass its own origin, or could spoof another origin's parameter directly). If origin values are strictly bound server-side to the sender's verified origin, the race is limited to self-inflicted corruption of the attacker's own entry plus incidental lost updates against concurrent unrelated legitimate operations (still a real DoS/trust-bypass risk on the connection registry), rather than direct cross-origin spoofing. Confirming this requires tracing the RPC exposure/dependency wiring in `sdks/headless` and the dapp-facing web3 provider background handlers, which was not fully covered by the indexed context.

  untrust = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })

    if (!isTrusted) return

    const data = await this.#getData()
    const newData = data.filter((connection) => connection.origin !== origin)

    await this.#setData(newData)
  }

  isTrusted = async ({ origin }) => {
    const value = await this.#getOrigin({ origin })

    if (!value) {
      return false
    }

    // backward compatibility
    return value.trusted === undefined || value.trusted
  }

  isAutoApprove = async ({ origin }) => {
    const value = await this.#getOrigin({ origin })
    return value?.autoApprove || false
  }

  setAutoApprove = async ({ origin, value }) => {
    return this.#setAttributes({ origin, attributes: { autoApprove: value } })
  }

  setFavorite = async ({ origin, value, assetNames = [] }) => {
    return this.#setAttributes({ origin, attributes: { favorite: value, assetNames } })
  }

  connect = async ({ id, origin }) => {
    const value = await this.#getOrigin({ origin })

    if (!value) return

    const activeConnections = value.activeConnections || []
    const newConnection = { id, createdAt: Date.now() }
    const newConnections = uniqBy([...activeConnections, newConnection], 'id')

    await this.#setAttributes({ origin, attributes: { activeConnections: newConnections } })
  }

  disconnect = async ({ id, origin }) => {
    const value = await this.#getOrigin({ origin })

    if (!value) return

    const activeConnections = value.activeConnections || []
    const newConnections = activeConnections.filter((connection) => connection.id !== id)

    await this.#setAttributes({ origin, attributes: { activeConnections: newConnections } })
  }

# @exodus/connected-origins

The connected origins module maintains a list of the third-party websites that the user has authorized to interact with Exodus. It stores the authorization status and connection status, along with metadata such as the name and icon of the website.

## Usage

To use the module call the factory and pass in required dependencies

```js
import connectedOriginsAtomDefinition from '@exodus/connected-origins/atoms'
import connectedOriginsDefinition from '@exodus/connected-origins/module'

const connectedOriginsStorage = storage.namespace('connectedOrigins')
const connectedOriginsAtom = connectedOriginsAtomDefinition.factory({
  storage: connectedOriginsStorage,
})

// create connected origins
const connectedOrigins = connectedOriginsDefinition.factory({ connectedOriginsAtom })

// load connected origins
await connectOrigins.load()

// get connected origins
await connectedOriginsAtom.get()

// clear connected origins
await connectOrigins.clear()
