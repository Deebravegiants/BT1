### Title
`PoaBridge.describeWithdrawal` reports the same completed withdrawal for two distinct same-asset `WithdrawalIdentifier` indices - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` calls `findMatchingWithdrawal` which selects a withdrawal purely by `` `nep141:${w.data.near_token_id}` === assetId ``, completely ignoring `args.index` [1](#0-0) . When a single NEAR intent transaction contains two `WithdrawalParams` of the same `assetId` to two different `destinationAddress` values, both `WithdrawalIdentifier{index:0}` and `WithdrawalIdentifier{index:1}` resolve to whichever matching record the POA API returns first, so `watchWithdrawal` reports identical `{status:'completed', txHash}` for both indices even though they represent two separate on-chain payouts.

### Finding Description
The broken equality is: `(status, txHash)` reported for `describeWithdrawal({index: i})` should equal the true on-chain outcome of withdrawal `i`, for `i in {0,1}`. In `describeWithdrawal`, the withdrawal status API response is matched only by asset id: [2](#0-1) 

`findMatchingWithdrawal` iterates `withdrawals` and returns the first entry whose `nep141:${near_token_id}` equals `assetId`, with no reference to `args.index` at all: [3](#0-2) . The code comment above the function explicitly acknowledges this is a known limitation: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported." This behavior is directly covered by an existing test, `"matches withdrawal by assetId, not by index"`, in `poa-bridge.test.ts`, which sets up two `COMPLETED` withdrawals for different tokens (`eth.omft.near`, `btc.omft.near`) and shows the match is by `assetId` regardless of index.

The attacker input needed is trivial and requires no special privilege: an ordinary user (or an integrator forwarding user-supplied `withdrawalParams`) submits `withdrawalParams = [{assetId: "nep141:btc.omft.near", destinationAddress: A, feeInclusive: false, ...}, {assetId: "nep141:btc.omft.near", destinationAddress: B, feeInclusive: false, ...}]` in one NEAR intents transaction. `createWithdrawalIdentifiers` (in `withdrawal-watcher.ts`) assigns `index: 0` and `index: 1` to these two `WithdrawalParams` respectively, both routed to `PoaBridge` since it's the same route/asset [4](#0-3) . When the POA bridge processes both withdrawals and the status API eventually returns two `COMPLETED` records with `near_token_id: "btc.omft.near"` (one per payout, to A and to B respectively), calling `describeWithdrawal` for `index:0` and for `index:1` both invoke the same `findMatchingWithdrawal(withdrawals, "nep141:btc.omft.near")`, which returns the same first match for both calls — the destination-specific distinction (A vs B) is lost. `watchWithdrawal` then surfaces the same `{status:'completed', txHash: withdrawal.data.transfer_tx_hash}` for both identifiers.

No existing guard prevents this: `validateWithdrawal`, `compareAddresses`, `supports()`, and `assert` sanity checks in this file only validate a single withdrawal's parameters (destination-address format, minimum amount, XRPL-specific flags) and never cross-check for duplicate `assetId` values across the batch of `WithdrawalParams`, nor does `findMatchingWithdrawal` use `withdrawal.data.address`/`destinationAddress` to disambiguate.

### Impact Explanation
An integrator that tracks per-index completion (e.g., crediting an internal ledger, releasing custody, or marking a specific destination address as paid) based on the reported `txHash`/`status` for each `WithdrawalIdentifier` will incorrectly conclude that both withdrawal #0 (to A) and withdrawal #1 (to B) completed with the same transaction hash, when in reality only one on-chain transfer occurred to that hash (or the two are conflated/misattributed if the API ever returns them in a different order than submitted). This is a status/hash misreport that can cause an integrator to double-credit or double-clear funds without any additional on-chain event, matching the "High" impact category (status or hash misreport making an integrator credit or refund twice).

### Likelihood Explanation
The precondition is simply submitting two (or more) `WithdrawalParams` with the same `assetId` in a single batch to the POA bridge route — no special token state, no privileged access, and no interaction with a malicious relayer/API is required beyond the bridge behaving normally. Any unprivileged user or a counterparty whose withdrawal batch is forwarded by an integrator can trigger this on every call where duplicate-asset withdrawals are batched, making it fully repeatable and low-cost to trigger.

### Recommendation
Disambiguate withdrawals by more than `assetId` — e.g., additionally match on `destinationAddress` (`withdrawal.data.address`) and/or `amount`, or reject/serialize batches containing duplicate `assetId` entries for the POA route until the POA bridge API supports returning a stable per-withdrawal correlation id.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
