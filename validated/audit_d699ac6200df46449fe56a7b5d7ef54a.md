### Title
Connected-origin account disclosure ignores per-origin wallet scoping, leaking all wallet account addresses to any trusted dApp - (File: `features/connected-origins/module/connections.js`)

### Summary
`ConnectedOrigins.getConnectedAccounts` is the function that decides which wallet accounts (and their addresses) are exposed to a connecting dApp/origin. Instead of scoping the result to the specific wallet account(s) the user actually authorized for that origin, it iterates over the **entire** `connectedAccountsAtom` (built from all enabled wallet accounts) and returns every account's address for the requested asset(s), completely ignoring the per-origin `walletAccount` field that is persisted precisely to track which account was granted to that origin.

### Finding Description
The stored origin record captures a `walletAccount` field when a connection is created via `add`/`#addNewItem`: [1](#0-0) 

However, `getConnectedAccounts` — the method actually consumed to disclose account/address data to a connected dApp — never reads or filters by `value.walletAccount`. It instead reads the aggregate, wallet-wide `#connectedAccountsAtom` (populated from *all* `enabledWalletAccountsAtom` entries via `#getAccounts`) and returns addresses for every wallet account in the wallet, only reordering so the active one comes first: [2](#0-1) 

This mirrors the root cause pattern in the external report: a security/trust-boundary decision (`check_wallets_for_list` deciding "is this wallet in the tracked/active set") is made against an **aggregate** value (`investor_wallet_balance_total`) instead of the entity that should actually be checked (the individual wallet's own balance). Here, the trust-boundary decision "which accounts may this origin see" is made against the aggregate set of all enabled wallet accounts instead of the specific `walletAccount`(s) the user actually connected to that origin.

The population of the aggregate atom itself confirms it is wallet-wide, not per-origin: [3](#0-2) [4](#0-3) 

### Impact Explanation
`getConnectedAccounts` is documented as usable "while the wallet is locked" and is the API surface exposed to dApp-facing RPC consumers (e.g. `sdks/headless`) once an origin is `trusted`: [5](#0-4) 

Because the function does not filter by the connected `walletAccount`, any dApp that a user has trusted/connected with even a single account is handed the receive addresses of **every other wallet account** in the user's wallet (multi-account setups are common in this wallet, see `features/wallet-accounts`). This breaks the intended account-isolation boundary of the connected-origins trust model: an origin authorized for one account gains visibility into the address set of unrelated accounts it was never granted access to, enabling cross-account linkage/deanonymization by any connected site — a cross-account privilege bleed across the origin permission boundary, analogous to the reported wallet-list contamination bug (over-broad, aggregate-based inclusion instead of per-entity authorization).

### Likelihood Explanation
This triggers on the ordinary, expected code path: any time a trusted origin calls `getConnectedAccounts` (e.g., to enumerate wallet accounts for a dApp), which is core, always-invoked functionality of the connected-origins feature rather than an edge case — no attacker action beyond normal dApp connection is required.

### Recommendation
In `getConnectedAccounts`, filter the returned accounts to only those actually authorized for the given `origin` (i.e., the stored `value.walletAccount`, and any additional accounts explicitly added to that origin's `accounts`/authorization list), rather than iterating over the full `connectedAccountsAtom`/`enabledWalletAccountsAtom` set. The per-origin `walletAccount` field currently persisted should be the actual authorization source of truth used at read time, not just metadata.

### Proof of Concept
1. User has two wallet accounts, `exodus_0` and `exodus_1`.
2. User connects `exodus_0` to `dapp.example` via `connectedOrigins.add({ origin: 'dapp.example', walletAccount: 'exodus_0', trusted: true, connectedAssetName: 'ethereum' })`.
3. `dapp.example` calls `connectedOrigins.getConnectedAccounts({ origin: 'dapp.example' })`.
4. Per `getConnectedAccounts` (lines 249-273), the result includes **both** `exodus_0` and `exodus_1` addresses for `ethereum`, even though the user only ever authorized `exodus_0` for this origin — confirmed by the code never referencing `value.walletAccount` when building `connectedAccounts`.

  /**
   * Returns the connected accounts for a given origin with the active wallet account sorted first. Can be used while
   * the wallet is locked
   */
  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
