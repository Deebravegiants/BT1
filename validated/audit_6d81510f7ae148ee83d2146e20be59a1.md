Found the analog. The `Webhooks::Request` `shop-domain` header is used as the tenant identity fed to the handler, but it is **not part of the HMAC-signed bytes**.

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant identity spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity by HMAC-checking only the raw JSON body, then trusts the unauthenticated `shop-domain` header as the tenant identifier passed to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns solely `@raw_body`, and `#hmac` is decoded from the `hmac-sha256`/`x-shopify-hmac-sha256` header [1](#0-0) [2](#0-1) . The `shop` accessor reads directly from the `shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to that header value [3](#0-2) .

`Registry.process` calls `Utils::HmacValidator.validate(request)`, which only verifies `request.hmac` against `compute_signature(request.to_signable_string, secret)` — i.e., against the raw body bytes, never against `request.shop` [4](#0-3) . After that single check passes, the shop value is handed straight to the app's handler as the tenant identifier: `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [5](#0-4) .

This breaks the equality that should hold: `shop authenticated by HMAC == shop stored/used as tenant key`. In this gem, `hmac-verified bytes == raw_body`, whereas `shop used for downstream tenant-scoped writes == unauthenticated header value`. Any client who knows (or brute-forces/replays) a single valid `(raw_body, hmac)` pair for their own shop's genuine webhook can resend the exact same body/HMAC while substituting an arbitrary `shop-domain` header value, and `HmacValidator.validate` still returns `true` because the signed bytes (the body) are unchanged.

### Impact Explanation
Applications built on this gem's documented pattern (`docs/usage/webhooks.md`, `Registry.process`) receive `data.shop` as an already-“verified” tenant identifier and typically use it directly to look up sessions or write data scoped to that shop domain [6](#0-5) . Since the gem asserts authenticity via `HmacValidator.validate` but that check never covers the `shop` field, a caller who can produce a body/HMAC pair for shop A can attribute that payload to shop B, achieving cross-tenant data confusion/write in the host application, which is a direct consequence of this gem's verification design rather than the host app "ignoring documented behavior" — the documented API returns `data.shop` as if it were verified.

### Likelihood Explanation
Exploitability depends on an attacker being able to obtain one legitimate `(body, hmac)` pair (e.g., from their own app installation's genuine webhook, which they legitimately receive) and resend it with a forged `shop-domain` header to the app's public webhook endpoint. This requires no `api_secret_key` and no privileged access — only observing traffic to one's own shop's webhook, which is realistic for any merchant/attacker running the app on their own store. Likelihood is moderate-to-high wherever the host directly trusts `data.shop` for tenant scoping, which the gem's own documentation encourages.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body before exposing `request.shop` to `WebhookMetadata`. At minimum, document loudly that only the body is authenticated and that `shop` must be independently validated against a known/installed shop list before being trusted as a tenant key.

### Proof of Concept
```ruby
# Attacker has a genuine webhook delivered to their own shop "attacker.myshopify.com":
raw_body = '{"id":1,"note":"hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker resends the identical body+hmac to the app's webhook endpoint,
# but swaps the shop-domain header to a victim shop they don't control:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Utils::HmacValidator.validate(request) # => true, because only raw_body is signature-checked

ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The host app now processes data.body as belonging to "victim-shop.myshopify.com"
