### Title
Emporium min-circuit path allows unsigned, unaccounted arbitrary calls that drain Emporium's held funds - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only constrains `message == Poseidon(messageSeed)`, `timeStamp`, and `calldataHash` — no root/nullifier/UTXO ownership binding at all. Combined with `EmporiumUpgradeable.verifyWallet` skipping signature verification when `EmporiumStack.signerAddress == address(0)`, any unprivileged caller can force Emporium to execute an arbitrary `op.endpoint.call{value: op.value}(op.callData)` from Emporium's own identity, with zero balance accounting since both `Hinkal.transact`'s per-token loop and `EmporiumUpgradeable.runAction`'s `balancesBefore`/`balancesAfter` loop iterate over the empty `erc20TokenAddresses` array.

### Finding Description
The claimed invariant is: *assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter`*. This is broken.

Path:
1. `Hinkal.transact` → `hinkalHelper.performHinkalChecks` → `CircomDataBuilder.formInputForCircom` selects `formInputEmporiumMin` whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`: [1](#0-0) 
2. The Min circuit (`MainEVMCircuitMin`, matching `VerifierEVMMin0v4` with `inputAmount == 3`) proves nothing about `rootHashHinkal`, nullifiers, or amountChanges — only that the prover knows a self-chosen `messageSeed`: [2](#0-1) 
3. `dimensionsCheck` only requires internal array-length consistency with `dimensions.tokenNumber == 0`; it does not require ownership of funds when `tokenNumber == 0`: [3](#0-2) 
4. In `Hinkal.transact`, the balance/slippage-accounting loop iterates `circomData.erc20TokenAddresses` — with length 0, it never executes: [4](#0-3) 
5. `_externalTransact` calls `EmporiumUpgradeable.runAction` with `deltaAmountChanges` also empty (built from the empty `erc20TokenAddresses`): [5](#0-4) 
6. Inside `runAction`, the attacker-controlled `EmporiumStack` is decoded from `externalActionMetadata`. `verifyWallet` is called: if `stack.signerAddress == address(0)`, it only records `usedMessages[emporiumMessage] = true` and returns — **no ECDSA signature check at all**: [6](#0-5) 
7. In the ops loop, since `signerAddress == address(0)`, the "Stateful" branch (`op.invokeWallet && stack.signerAddress != address(0)`) is always false, so every op takes the "Stateless" branch and Emporium performs `op.endpoint.call{value: op.value}(op.callData)` directly from its own address, with the only restriction being that `callData`'s selector isn't `callHinkalWallet`/`doSendToRelay`: [7](#0-6) 
8. The `balancesBefore`/`balancesAfter` accounting that would normally catch a net-negative balance change also iterates `circomData.erc20TokenAddresses`, which is empty, so any token not in that (empty) list is never checked: [8](#0-7) 

Because of this, an attacker can craft `op = {endpoint: <token Emporium holds>, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)}` (or `approve`), submit a trivially self-generated Min proof (no real UTXO or deposit required), set `EmporiumStack.signerAddress = address(0)`, and have Emporium execute the call directly, moving out any ERC20/ETH balance Emporium holds (e.g. residual balances from prior stateless swaps, unclaimed relay fees, or dust from other users' Emporium operations) with zero on-chain accounting or authorization.

None of the existing guards stop this: `performHinkalChecks`'s `dimensionsCheck`/`checkOnchainCreation` only validate array-length consistency, not fund ownership; `verifyProof` only checks the trivial Min-circuit relation; `rootHashExists` only checks the supplied root is a historically valid Merkle root (trivially satisfiable, e.g. the initial root), not that the caller owns any leaf under it; `insertNullifiers`/`insertCommitments` operate on empty arrays and are no-ops.

### Impact Explanation
This is direct, permissionless theft of any funds held by the `Emporium` contract (protocol/relay/user-in-flight funds sitting in Emporium from unrelated stateless operations, relay fee residues, or dust), executed with Emporium's own identity via an unauthenticated ("unsigned") call path. This matches Critical: direct theft of shielded or in-flight user funds, and also "executing calls or moving assets ... never authorised" since no `EmporiumStack` signature is checked. It is repeatable for any token balance Emporium accumulates over time, at negligible attacker cost (a self-chosen `messageSeed`/proof, no real deposit needed).

### Likelihood Explanation
Preconditions: (a) an `EmporiumMin`-capable verifier must be registered for `dimensions = {0,0,0}` + Emporium's `externalActionId` (this appears to be an intended registered configuration given the dedicated `VerifierEVMMin0v4`/`MainEVMCircuitMin` artifacts), and (b) the Emporium contract must hold some balance of a token (which naturally accumulates from normal stateless-swap flows, dust, or fee residue). Both are plausible operational states, not privileged. The attacker needs no special role, no valid UTXO, no signed `EmporiumStack` — just the ability to generate a trivial Groth16 proof for the Min circuit and submit a `transact` call. This is fully repeatable each time Emporium holds a drainable balance.

### Recommendation
Do not allow `formInputEmporiumMin` (or any Min/near-empty-constraint circuit path) to authorize execution of `EmporiumUpgradeable.runAction` when `EmporiumStack.signerAddress == address(0)`. Specifically:
- Require `erc20TokenAddresses.length > 0` (i.e., disallow the Min-input path) whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and the resulting `EmporiumStack.signerAddress == address(0)`, so the stateless op path always goes through the balance-accounting loop with real tokens tracked.
- Alternatively, remove/never register a Min verifier for the Emporium action ID, or make the stateless (`signerAddress == 0`) branch require a signature/authorization equivalent to the stateful branch instead of merely marking `usedMessages`.
- Ensure Emporium never carries idle balances between transactions (sweep to zero at the end of each `runAction`), so there is nothing to steal via an unaccounted op even if the above is bypassed.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, register `EmporiumUpgradeable` as the external action for `HINKAL_EMPORIUM_ACTION_ID`, and register a verifier for `buildVerifierId({0,0,0}, HINKAL_EMPORIUM_ACTION_ID)` pointing at `VerifierEVMMin0v4`.
2. Fund `Emporium` directly with e.g. 1000 `TestERC20` tokens (simulating leftover balance from prior stateless swaps/fees).
3. As an unprivileged attacker EOA (no deposits, no UTXOs): generate a valid Groth16 proof for `MainEVMCircuitMin` using a self-chosen `messageSeed`; build `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [{endpoint: address(TestERC20), invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, 1000e18)}], ...}))`, and a valid existing `rootHashHinkal`/index.
4. Call `Hinkal.transact(a, b, c, dimensions={0,0,0}, circomData)`.
5. Assert: `TestERC20.balanceOf(attacker)` increases by 1000e18 and `TestERC20.balanceOf(Emporium)` drops to 0, with no revert, proving `assets moved != assets accounted (0)` in both `Hinkal.transact`'s per-token loop and `EmporiumUpgradeable.runAction`'s `balancesBefore/After` loop.

    function formInputEmporiumMin(

        uint16 index = 0;

        input[index++] = circomData.emporiumMessage;
