### Title
Webhook shop identity is read from an unauthenticated header not covered by the HMAC signature — cross-tenant webhook spoofing (`Webhooks::Request`) - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is used by host applications to determine which merchant/tenant a webhook belongs to, but that value is taken directly from the `X-Shopify-Shop-Domain` HTTP header, which is **not** included in the HMAC-signed payload. The HMAC only covers the raw request body, so the binding `hmac_valid == (shop header is authentic)` does not hold.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` simply reads the `shop-domain` (or `x-shopify-shop-domain`) header verbatim, with no cryptographic tie to the signed body: [2](#0-1) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (the body only) and compares it to the `hmac-sha256` header value using the app's single, shop-agnostic `api_secret_key`: [3](#0-2) 

Because the same `api_secret_key` is shared across **all** shops that install a given app, a valid `(raw_body, hmac)` pair generated by Shopify for one merchant's webhook remains cryptographically valid for that same body regardless of which `X-Shopify-Shop-Domain` header accompanies it. The header is never part of the signed bytes, so an attacker who has access to a genuine signed webhook (e.g., from their own installed shop, since webhook payloads/headers are visible to the shop owner or any TLS-terminating proxy/logging system on the receiving end) can resend the identical body+HMAC to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop's domain. `HmacValidator.validate` will still return `true` because it only checks body bytes against the secret — it never authenticates the header claiming which shop the event belongs to.

This directly matches the requested identity-binding class: **"bytes verified versus bytes parsed"** — the bytes cryptographically verified are the raw body; the bytes parsed and trusted for tenant identification (`shop`) are unauthenticated header bytes.

### Impact Explanation
If a host application (as documented/intended usage of this gem) uses `Request#shop` to look up the tenant/session context to process the webhook payload (e.g., "load session for shop X, then process this order/webhook body under shop X's data"), an attacker can inject or overwrite data across tenants by relabeling their own authentic webhook to point at a different, victim shop. This is a cross-tenant access/data-confusion primitive — the app authenticates the payload's authenticity but not its claimed tenant, satisfying the "Critical: cross-tenant access" impact bucket.

### Likelihood Explanation
Requires only that the attacker (a) run their own Shopify store with the target app installed to legitimately obtain properly signed `(body, hmac)` pairs, and (b) resend that pair to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header. No secrets, tokens, or privileged access to Shopify's infrastructure are needed — only unprivileged internet/API access to the target app's exposed webhook endpoint, matching the "unprivileged internet user" threat model.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material, or otherwise cryptographically bind the `shop-domain` header to the payload before trusting it — e.g., verify the header against a value embedded in and covered by the signed body, or require host applications to cross-check the `shop` domain against an existing session/install record rather than trusting the header outright. At minimum, the gem's documentation and `Request` class should make explicit that `shop` is **not** verified by `HmacValidator.validate` and must not be used as an authoritative tenant identifier without additional verification (e.g., matching to a previously stored, authenticated session for that shop).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, and Shopify delivers a genuine webhook: body `B`, headers include `X-Shopify-Hmac-Sha256: H` (valid for `B` under the shared `api_secret_key`) and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker crafts a new HTTP request to the app's webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. The app calls `ShopifyAPI::Utils::HmacValidator.validate(request)` — this passes because `to_signable_string` only hashes `B`, unaffected by the header change: [4](#0-3) 
4. The app then reads `request.shop` and processes `B`'s content under `victim.myshopify.com`'s tenant context, believing the HMAC check authenticated that association — but that association was never signed.

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
