### Title
Webhook `shop` identity is taken from an unauthenticated header while the HMAC only signs the raw body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's HMAC over the raw request body only, then unconditionally trusts the `shop-domain` HTTP header (exposed as `request.shop`) to identify which merchant the webhook belongs to. Because the header is never included in the signed material, an attacker who can obtain any validly-signed webhook payload (e.g. from their own shop with the app installed) can resubmit it to the app's webhook endpoint with the `shop-domain`/`x-shopify-shop-domain` header changed to a victim shop, and the request will still pass HMAC validation.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`to_signable_string` returns only `@raw_body`; the `shop` (and `topic`, `webhook_id`, `api_version`) accessors read straight from HTTP headers and are never mixed into the signable string used for HMAC computation: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the HMAC strictly against `verifiable_query.to_signable_string` (i.e. the raw body), never touching headers: [3](#0-2) 

`Registry.process` performs exactly this HMAC check and then, once it passes, hands `request.shop` straight to the app's registered handler as the tenant identity, with no further binding check between the signed body and the shop header: [4](#0-3) 

The identity-binding invariant the gem should enforce is:
`shop_header == shop_that_produced(HMAC-signed body)`

Because `shop-domain` is excluded from the signable string, this equality is never actually checked — only `HMAC(body) == received_hmac` is checked, which is independent of the header. Any two requests with the same body but different `shop-domain` headers produce identical, both-"valid" HMACs.

### Impact Explanation
Shopify computes the webhook HMAC using the app's single `client_secret`/`api_secret_key`, which is shared across every shop that has the app installed. This means:
1. An attacker installs the target app on their own (attacker-controlled) shop and receives genuine, correctly-signed webhooks for topics they can trigger (e.g. `app/uninstalled`, `orders/create`, `shop/redact`, `customers/data_request`).
2. The attacker replays that exact `raw_body` + `hmac-sha256` header pair to the victim app's webhook endpoint, but swaps `x-shopify-shop-domain` (or `shopify-shop-domain`) to point at an arbitrary victim shop.
3. `HmacValidator.validate` still succeeds because it only checks the body against the secret, and `Registry.process` dispatches the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain.

Any host application that uses the webhook `shop` field to select/act on tenant data (looking up a session by shop, deleting the shop's records for `shop/redact`, marking a shop as uninstalled, processing a fraudulent `customers/data_request`, etc.) will act on the wrong tenant — a cross-tenant access/integrity break driven entirely by this gem's failure to bind the header to the signed payload.

### Likelihood Explanation
Any external actor who can install the target app on a shop they control (which is normal, unprivileged usage of a public app) can obtain validly HMAC-signed webhook bodies for topics they trigger themselves, then freely relabel the `shop-domain` header when POSTing to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only the ability to receive one's own app webhooks and edit an HTTP header on replay, which is well within reach of an unprivileged internet user interacting with a multi-tenant app.

### Recommendation
Include the `shop-domain` header (and ideally `topic`/`webhook_id`) inside the HMAC-signed material verified by `Utils::HmacValidator`, or otherwise cryptographically bind the shop identity to the signed body before it is exposed to handlers via `WebhookMetadata`. At minimum, `Registry.process` should refuse to trust `request.shop` unless it is corroborated by the signed payload contents (many webhook payloads include the shop id/domain in the JSON body) rather than relying solely on an unauthenticated header value.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com"
# and receives a legitimate webhook for topic "app/uninstalled":
raw_body = '{"id":123}'                     # attacker's own shop's payload
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_client_secret, raw_body)

# Attacker replays it to the same app's webhook endpoint, but swaps the shop header:
headers = {
  "x-shopify-topic" => "app/uninstalled",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),  # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate succeeds (only checks raw_body against secret)
# => handler.handle is invoked with shop: "victim-shop.myshopify.com"
```
The app's registered handler now believes `victim-shop.myshopify.com` uninstalled the app (or triggered whatever topic was replayed), even though the victim shop never sent this request.
