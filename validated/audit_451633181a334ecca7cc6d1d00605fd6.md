This confirms the claim's core technical premise. `ERC20Matcher` uses `IsLocalAccountKey20` which matches **any** local `AccountKey20` location — i.e., it matches any local H160 contract address with no allow-list or curation, so any permissionlessly-deployed `pallet-revive` contract can be routed through `ERC20Transactor` as long as it's addressed as an `AccountKey20` in the XCM message. The transactor unconditionally credits the requested `amount` into `AssetsInHolding` based only on the boolean return value of `transfer`, never checking actual balance deltas, and both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` route through a single shared `TransfersCheckingAccount` for all ERC20 assets in a given runtime configuration.

Audit Report

## Title
ERC20Transactor trusts nominal `amount` and boolean `transfer` return instead of verifying actual balance change, enabling shared-checking-account shortfall DoS for non-standard ERC20 tokens - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` call the target ERC20 contract's `transfer` function and, upon a `true` boolean return, unconditionally credit/debit the caller-specified `amount` into XCM holdings or move it out of a single, globally shared `TransfersCheckingAccount`, without ever checking the checking account's or beneficiary's actual balance before/after the call. Since `ERC20Matcher` (`IsLocalAccountKey20`) matches any local H160 address with no allow-list, and `pallet-revive` contract deployment is permissionless, an attacker can deploy a non-standard ERC20 (rebasing/fee-on-transfer/share-accounting token) that returns `true` from `transfer` while moving less than the requested `value`, causing the shared checking account's real balance to fall short of what has been credited to holdings across transactions.

## Finding Description
In `withdraw_asset_with_surplus`, the transactor calls `IERC20::transferCall` moving `amount` from the user to the shared `TransfersCheckingAccount`, decodes only the boolean return value, and if `true`, credits `AssetsInHolding` with exactly the requested `amount` via `Erc20Credit(amount)` — never verifying that the checking account's real balance increased by `amount`. [1](#0-0) 

Symmetrically, `deposit_asset_with_surplus` transfers `amount` from the checking account to the beneficiary, again trusting only the boolean success flag rather than an observed balance delta. [2](#0-1) 

The `Erc20Credit` imbalance type's doc comment explicitly documents this design assumption — "the actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime" — confirming there is no runtime-level balance verification against the nominal amount. [3](#0-2) 

Critically, `ERC20Matcher` is defined as `MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>`, and `IsLocalAccountKey20` matches **any** local `(0, [AccountKey20{..}])` location — there is no allow-list restricting which contract addresses can be routed through `ERC20Transactor`. [4](#0-3) 

The `TransfersCheckingAccount` is a single, statically-configured account (`ERC20TransfersCheckingAccount`, a `PalletId`-derived account) shared across the entire `ERC20Transactor` instance for the whole runtime — i.e., across all ERC20 contracts and all users of this transactor. [5](#0-4) 

The repo's own test suite demonstrates that arbitrary, non-standard contracts (returning non-boolean values that coerce truthy, or non-ERC20 contracts entirely) are reachable through this exact XCM path and cause `FailedToTransactAsset` reverts, confirming both that arbitrary contracts are reachable and that mismatches between assumed and actual behavior surface as XCM execution failures. [6](#0-5) 

## Impact Explanation
If any ERC20 contract with rebasing/rounding/fee-on-transfer semantics is used through this path, the shared checking account's real on-chain balance will diverge downward from the cumulative amount recorded as credited across all users' XCM holdings for that token (and, because the account is shared per-transactor-instance, this bleeds into the pool used by all ERC20 tokens processed by this transactor). A later `deposit_asset_with_surplus` attempting to move the full nominal amount out of the checking account can then fail with `XcmError::FailedToTransactAsset`, trapping assets and failing execution of an unrelated, later XCM message for a different user of the same (or, since the account is shared, potentially confounded with) token. This is a genuine denial-of-service / griefing vector rather than a direct fund-theft bug, since the ERC20 contract's own state remains authoritative and no double-spend of the contract's tokens occurs.

## Likelihood Explanation
The precondition — that a permissionlessly-deployed, non-standard ERC20 contract can be routed through `ERC20Transactor` — is confirmed by the unrestricted `IsLocalAccountKey20` matcher and by `pallet-revive`'s permissionless contract deployment, and is directly exercised by the repository's existing tests using deliberately non-conforming contracts. An attacker (or an unwitting user who deploys a well-intentioned rebasing/fee token and uses it via XCM) can trigger the shortfall condition without needing any privileged role, using only ordinary `PolkadotXcm::execute` calls and contract deployment, both of which are user-accessible operations.

## Recommendation
Do not rely on the `amount` parameter or the boolean success return as proof of an exact transfer. Query the checking account's/beneficiary's ERC20 balance before and after each `transfer` call and use the observed delta to construct `Erc20Credit`/determine transferred amount, rather than trusting the nominal requested value. Additionally, consider isolating checking-account balance risk per-asset (or per-transaction escrow) instead of a single global pooled account, so that a shortfall from one non-conforming token cannot propagate into failures for unrelated users/tokens.

## Proof of Concept
1. Deploy (via `pallet-revive`, permissionless) an ERC20-like contract whose `transfer(to, value)` moves `value - 1` (or otherwise less than requested) while returning `true`.
2. Use `PolkadotXcm::execute` with a `withdraw_asset`/`deposit_asset` XCM program referencing this contract's address as an `AccountKey20` location (matched by the unrestricted `ERC20Matcher`), as shown feasible in the existing `smart_contract_does_not_return_bool_fails` and `withdraw_and_deposit_erc20s` tests.
3. Repeat withdrawals of this token to accumulate a deficit in `ERC20TransfersCheckingAccount`'s real balance relative to what has been credited into XCM holdings.
4. Trigger a subsequent `deposit_asset_with_surplus` (for this or another user's transfer of the same token) that requires the checking account's full nominal balance; observe `XcmError::FailedToTransactAsset` and trapped assets, analogous to the existing `smart_contract_does_not_return_bool_fails`/`smart_contract_not_erc20_will_error` failure patterns in the test suite. pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
