### Title
Webhook `shop` field used for tenant attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , while `shop` and `topic` are read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`) that are never part of the signed bytes [2](#0-1) . `Registry.process` validates the HMAC over the body only and then forwards the unauthenticated `request.shop` value straight into the handler as the tenant identifier [3](#0-2) .

### Finding Description
The binding that should hold is: `shop_bound_by_hmac == shop_delivered_to_handler`. Here, `Utils::HmacValidator.validate(request)` only proves that `HMAC(secret, raw_body) == received_hmac` [4](#0-3) . It proves nothing about the `shopify-shop-domain` header. Yet `Registry.process` passes `request.shop` (parsed from that unauthenticated header) as the `shop:` field of `WebhookMetadata`, which is exactly the value host applications use to determine which tenant's data the webhook body should be applied to [3](#0-2) .

This is the same bug class as the referenced report: a value used to change tenant-scoped state (there, the reserve ratio/price; here, which merchant's data the webhook payload is attributed to) is computed/read from bytes that are outside the scope of the value actually verified (there, `1e18` precision vs. `1e8` stored ratio; here, HTTP headers vs. HMAC-signed body).

### Impact Explanation
Because the shop attribution is not cryptographically bound, an unprivileged internet user who can reach the app's webhook endpoint and knows/guesses any single valid `(topic, body, hmac)` triple for their own shop can replay it while substituting an arbitrary `shopify-shop-domain` header for a different (victim) tenant. If the host application trusts `WebhookMetadata#shop` (as the library's own documented model instructs it to) to select which merchant's stored data to update/delete, this yields cross-tenant data corruption/injection without any additional secret — a boundary crossing between tenants using only knowledge of the app's public webhook signing behavior for one's own shop.

### Likelihood Explanation
The attacker still needs a valid signature for the body they send, which requires either a body they control from their own shop's genuine webhook (self-serve, since a merchant fully controls the payloads/triggers of webhooks fired for their own shop, e.g. `orders/create`) or the ability to trigger a webhook with attacker-influenceable body content, then replaying it with a spoofed shop header at the app's callback URL. This requires no `client_secret`, no access token, and no privileged account — only the attacker's own legitimately-owned test shop, which is realistic for any developer with a Shopify Partner account. Exploitability depends entirely on whether the host application relies on `WebhookMetadata#shop` (rather than independently re-deriving the shop from an already-authenticated source) — which is the pattern this gem's own `Registry.process` API surfaces and encourages via `WebhookHandler#handle(data:)`.

### Recommendation
Bind `shop` (and `topic`) to the HMAC by including them in the signed materials, or, more consistently with Shopify's actual webhook contract, document/require host apps to treat `WebhookMetadata#shop` as it is: unauthenticated header data that must never be used alone to select tenant-scoped state, and provide an API that resolves the shop from an already-authenticated source (e.g., matching against the destination path/registered callback session) rather than the raw header.

### Proof of Concept
```ruby
raw_body = '{"id":1,"note":"legit body from attacker-shop"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => Base64.encode64(hmac),
  "shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HMAC validation passes (it only checks raw_body against the attacker's own real secret-signed webhook),
# but the handler receives shop: "victim-shop.myshopify.com" in WebhookMetadata,
# even though that header was never verified.
