## Title
Webhook Shop-Domain Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` value (read from the `X-Shopify-Shop-Domain` header) is never included in the signed material. `ShopifyAPI::Webhooks::Registry.process` verifies the HMAC and then forwards the unverified `shop` header straight to the app's handler as the tenant identifier, breaking the intended binding `HMAC-verified bytes == identity used for routing`.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

`to_signable_string` returns `@raw_body` only — the `shop` (from `shopify-shop-domain`/`x-shopify-shop-domain`), `topic`, `api_version`, and `webhook_id` headers are parsed from headers but excluded from the signable string.

`Registry.process` validates the HMAC against this signable string, then immediately builds `WebhookMetadata` using the unverified `request.shop` value and dispatches it to the app's handler: [2](#0-1) 

The gem's own documentation tells integrators that calling `Registry.process` "will verify the request did indeed come from Shopify," and instructs handlers to use `data.shop` as the tenant/shop identifier (e.g., to route work or look up a session) without any additional verification: [3](#0-2) [4](#0-3) 

Because a single app's `api_secret_key` (`client_secret`) is shared across every merchant install, an HMAC computed for one shop's webhook body is valid for *any* value of the `shop-domain` header — the header is never part of the signed input. The equality the gem is supposed to guarantee — `shop identity trusted by the handler == shop identity bound by the HMAC` — does not hold; only the body is bound.

### Impact Explanation
This is a cross-tenant identity-binding break, matching the report's bug class ("a field acted on but not covered by the HMAC"). A party who can submit a syntactically valid `(raw_body, hmac)` pair signed with the app's shared secret — for example, a merchant who has the app installed on their own store and can observe/replay the genuine webhook POST that Shopify sends to the app's public webhook endpoint for their store — can resubmit that exact `raw_body`/HMAC directly to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` value naming a *different* merchant. `HmacValidator.validate` still succeeds because the signature check never touches the shop header, and `Registry.process` hands the forged shop identity straight to the app's handler as authoritative, per the documented contract. Any downstream logic that uses `data.shop` to select a tenant/session/data store (exactly as shown in the gem's own example handler) processes attacker-supplied body content under another merchant's identity — a cross-tenant data-integrity/access issue.

### Likelihood Explanation
Exploitation requires only (a) the app's public webhook endpoint, and (b) one genuine `(body, hmac)` pair obtainable by any merchant who has installed the app (they receive real Shopify webhooks addressed to that same shared endpoint). No access to `api_secret_key`, access tokens, or Shopify-side credentials is required, so this is reachable by any unprivileged merchant already granted the same class of privilege as the fork target (install the app on their own store).

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material used for HMAC verification, or otherwise require the app to independently re-validate that the `shop` header corresponds to a shop that actually has this specific webhook/topic registered (e.g., cross-check against the app's own webhook registration/session store) before trusting `WebhookMetadata#shop` for tenant routing. At minimum, update `docs/usage/webhooks.md` to clearly state that `data.shop` is **not** cryptographically bound by the HMAC and must not be trusted as an authenticated tenant identifier without additional server-side verification.

### Proof of Concept
1. App has a single shared `client_secret` across all merchant installs (standard Shopify app model).
2. Merchant A installs the app; Shopify sends a genuine webhook to the app's shared endpoint: body `B`, header `X-Shopify-Shop-Domain: shop-a.myshopify.com`, `X-Shopify-Hmac-Sha256: HMAC(secret, B)`.
3. Merchant A (attacker) captures this request (they control network traffic to their own testing tools, or simply crafts an equivalent body they know will validate) and resends it to the same webhook endpoint but with header `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes `HMAC(secret, B)` (body unchanged) and it matches, since `to_signable_string` never included the shop header — validation succeeds.
5. `Registry.process` builds `WebhookMetadata.new(..., shop: "shop-b.myshopify.com", body: B, ...)` and invokes the handler, which (per the documented usage pattern) treats `shop-b.myshopify.com` as the authenticated origin of body `B`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
