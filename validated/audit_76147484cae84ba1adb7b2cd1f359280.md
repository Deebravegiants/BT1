### Title
Commitment/nullifier collision across independent tree leaves permanently freezes one of two duplicated UTXOs - (File: circuits/PointCompressor.circom / circuits/OriginalCommitmentCalculator.circom / circuits/NullifierCalculator.circom / contracts/external-actions/DepositOnChainUtxosExternalAction.sol)

### Summary
The leaf commitment `hash4(amount, erc20TokenAddress, stealthAddress, timeStamp)` and the resulting nullifier `Poseidon(commitment, Poseidon(nullifyingPrivateKey, commitment))` are functions only of the four UTXO fields and the spender's private key — never of the Merkle tree index/position. An unprivileged attacker can read a victim's already-deposited `NewCommitment` on-chain UTXO fields (amount, token, stealth address, timestamp, all emitted in cleartext for on-chain deposits) and replay them via `DepositOnChainUtxosExternalAction`, funding a second, independent leaf whose commitment is byte-for-byte identical to the victim's. Since both leaves reduce to the same nullifier, only one can ever be spent; whichever leaf is not spent first is permanently frozen.

### Finding Description
Equality that should hold: **leaf(index_A) ↔ nullifier_A is a 1:1, injective mapping** so that TREE_TRUTH (leaf validly included with a correct root) implies SINGLE_SPEND (each leaf redeemable exactly once, independently of any other leaf). This is broken because the commitment/nullifier computation ignores tree position entirely:

- `circuits/OriginalCommitmentCalculator.circom:16-20` computes `commitment = Poseidon4(amount, erc20TokenAddress, publicKey/stealthAddress, timeStamp)` with no tree-index or randomization input.
- `circuits/NullifierCalculator.circom:11-18` computes `nullifier = Poseidon(commitment, Poseidon(nullifyingPrivateKey, commitment))`, again a pure function of `(commitment, nullifyingPrivateKey)`.
- `contracts/HinkalBase.sol:57-62` (`createOnchainCommitment`) mirrors the exact same formula: `hash4(utxo.amount, uint160(utxo.erc20Address), utxo.stealthAddressStructure.stealthAddress, utxo.timeStamp)`.

Attacker's exact call: the victim's genuine deposit (via `Hinkal.prooflessDeposit` → `_createProoflessDepositCommitments`, `contracts/Hinkal.sol:326-354`) creates a leaf with `timeStamp = block.timestamp` at block N, and emits the full `UTXO` struct in cleartext in `NewCommitment` (`contracts/HinkalBase.sol:122-131`), exposing `amount=A`, `erc20Address=T`, `stealthAddressStructure=S`. The attacker later calls `Hinkal.transact` with `externalActionData.externalActionId` pointing at `DepositOnChainUtxosExternalAction`, setting `circomData.originalSender = attacker`, `circomData.timeStamp = Tblk`, `utxoAmounts[i][0] = A`, and `circomData.stealthAddressStructure = S` (copied verbatim from the victim's leaf). In `DepositOnChainUtxosExternalAction.sol:66-72`, for `utxoIndex == 0` the created UTXO has `timeStamp = circomData.timeStamp + 0 = Tblk`, exactly matching the victim's original leaf's fields. `Hinkal.sol:126-129` then calls `createOnchainCommitment` on this UTXO, producing the identical commitment value at a brand-new tree index.

Existing guards do not catch this:
- `checkOnchainCreation` (`contracts/HinkalHelper.sol:173-202`) only enforces `amountChanges[i]==0` and `inputNullifiers[i][j]==0` for on-chain-created leaves — it never checks commitment uniqueness against existing leaves.
- `insertCommitments` (`contracts/HinkalBase.sol:72-133`) just appends leaves to the tree; there is no duplicate-commitment check.
- `performHinkalChecks` (`contracts/HinkalHelper.sol:208-236`) requires `circomData.originalSender == sender` when no relay is used, which forces the attacker to fund the duplicate deposit with their *own* tokens (`transferERC20TokenFrom(tokenAddress, userAddress=attacker, msg.sender=Hinkal, tokenTotal)` in `DepositOnChainUtxosExternalAction.sol:76-81`) — this prevents the attacker from directly draining the victim's external balance, but does not prevent the collision itself.
- `insertNullifiers` (`contracts/HinkalBase.sol:135-152`) only checks `!nullifiers[inputNullifiers[i][j]]` at spend time — the first of the two colliding leaves to be spent (by whoever holds the matching `nullifyingPrivateKey`, i.e. only the victim, since `calcInPublicKeys` in `circuits/MainEVMCircuit.circom:107-119` binds the spend to the victim's key) succeeds and marks the shared nullifier used; the second attempted spend then reverts with `"Nullifier cannot be reused"` — permanently.

### Impact Explanation
Only the victim (holder of the `nullifyingPrivateKey` matching stealth address `S`) can ever generate a valid spending proof for either leaf, so the attacker cannot steal funds directly. However, the attacker can deliberately create a second, indistinguishable-by-commitment leaf funded with the attacker's own tokens. Whichever of the two colliding leaves the victim's wallet redeems first consumes the shared nullifier; the other leaf's value becomes permanently unspendable/frozen. If a wallet or user redeems the attacker-planted duplicate before the original genuine deposit (e.g., due to FIFO-by-index redemption order, or ambiguity from indistinguishable balances), the **victim's own legitimately-deposited funds are permanently frozen** — satisfying "permanent freezing of user funds," Critical severity. This is repeatable against any victim on-chain deposit whose fields are observable (which is all on-chain UTXO creations, since they are emitted in cleartext), at a cost to the attacker of funding the duplicate with an equal amount of their own capital.

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged attacker's control: any victim `prooflessDeposit`/on-chain UTXO creation is observable via the `NewCommitment` event, which leaks `amount`, `erc20Address`, `stealthAddressStructure`, and `timeStamp` in cleartext for on-chain leaves. The attacker needs only to call `Hinkal.transact` targeting the registered `DepositOnChainUtxosExternalAction` external action, supply matching `CircomData` fields, and pay the equivalent token amount from their own balance. No privileged role, no proof forgery, and no compromise of the victim's key is required — only replaying public on-chain data. Repeatable against every on-chain UTXO creation in the protocol.

### Recommendation
Bind the commitment (and thus nullifier) to something unique per insertion, e.g., include the tree leaf index or a protocol-issued monotonically increasing nonce/salt as an additional Poseidon input in `OriginalCommitmentCalculator`/`createOnchainCommitment`, or enforce a global uniqueness check on `timeStamp` per `(stealthAddress, erc20Address, amount)` tuple (e.g., a mapping rejecting duplicate on-chain-created commitments) before insertion in `insertCommitments`/`DepositOnChainUtxosExternalAction`.

### Proof of Concept
Foundry test plan:
1. Victim calls `prooflessDeposit` with `amount=A`, `erc20Address=T`, `stealthAddressStructure=S`; record `block.timestamp` as `Tblk` and the emitted `NewCommitment` leaf/index (`indexVictim`).
2. In a later block, attacker (funded with `A` tokens of `T`) calls `Hinkal.transact` targeting `DepositOnChainUtxosExternalAction` with `circomData.originalSender = attacker`, `circomData.timeStamp = Tblk`, `circomData.stealthAddressStructure = S`, `utxoAmounts = [[A]]`, `amountChanges[i] = 0`, `onChainCreation[i] = true`, `inputNullifiers[i] = [0]`; assert a second `NewCommitment` is emitted with the same `commitment` value as the victim's leaf but a different index (`indexAttacker`).
3. Compute the expected shared nullifier via `NullifierCalculator`/`hash2` using the victim's `nullifyingPrivateKey` and confirm off-chain that it is identical for both `indexVictim` and `indexAttacker`.
4. Victim generates a valid proof and calls `Hinkal.transact` spending `indexAttacker`'s leaf (or `indexVictim`'s, to demonstrate order-independence) — assert success and `nullifiers[n] == true`.
5. Victim attempts to spend the other (remaining) leaf with a valid inclusion proof for its distinct root/index — assert revert `"Nullifier cannot be reused"`, proving that leaf's `A` tokens are now permanently unredeemable despite being validly included in the tree. template OriginalCommitmentCalculator() {
  signal input amount;
  signal input erc20TokenAddress;
  signal input publicKey;
  signal input timeStamp;
  signal output out;

  component calcIsAmountZero = IsZero();
  calcIsAmountZero.in <== amount;

  component calcCommitment = Poseidon(4);
  calcCommitment.inputs[0] <== amount;
  calcCommitment.inputs[1] <== erc20TokenAddress;
  calcCommitment.inputs[2] <== publicKey;
  calcCommitment.inputs[3] <== timeStamp;

  out <== calcCommitment.out * (1 - calcIsAmountZero.out);
}

    function insertNullifiers(
        uint256[][] calldata inputNullifiers,
        bool[] calldata onChainCreation
    ) internal {
        for (uint256 i = 0; i < inputNullifiers.length; i++) {
            for (uint256 j = 0; j < inputNullifiers[i].length; j++) {
                if (onChainCreation[i] == true) break;
                if (inputNullifiers[i][j] != 0) {
                    require(
                        !nullifiers[inputNullifiers[i][j]],
                        "Nullifier cannot be reused"
                    );
                    nullifiers[inputNullifiers[i][j]] = true;
                    emit Nullified(inputNullifiers[i][j]);
                }
            }
        }
    }

            (uint256[][])
        );
        require(
            utxoAmounts.length == tokenCount,
            "DepositOnChainUtxosExternalAction: metadata length mismatch"
        );

        utxoSet = new UTXO[](countUtxos(utxoAmounts));

        uint256 utxoIndex = 0;
        for (uint256 i = 0; i < tokenCount; i++) {
            require(
                deltaAmounts[i] == 0,
                "DepositOnChainUtxosExternalAction: Delta amount must be zero"
            );

            address tokenAddress = circomData.erc20TokenAddresses[i];
            uint256 tokenTotal = 0;

            for (uint256 j = 0; j < utxoAmounts[i].length; j++) {
                uint256 amount = utxoAmounts[i][j];
                require(
                    amount > 0,
                    "DepositOnChainUtxosExternalAction: UTXO amount must be positive"
                );
                tokenTotal += amount;

                utxoSet[utxoIndex] = UTXO({
                    amount: amount,
                    erc20Address: tokenAddress,
                    stealthAddressStructure: circomData.stealthAddressStructure,
                    timeStamp: circomData.timeStamp + utxoIndex
                });
                utxoIndex++;
            }

            if (tokenAddress != address(0) && tokenTotal > 0) {
                transferERC20TokenFrom(
                    tokenAddress,
                    userAddress,
                    msg.sender,
                    tokenTotal
