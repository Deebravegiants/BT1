### Title
Webhook `shop` identity spoofing — HMAC signature does not bind the `X-Shopify-Shop-Domain` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for a webhook event from an HTTP header that is never included in the HMAC-signed payload, while `ShopifyAPI::Webhooks::Registry.process` treats the resulting `shop` value as authenticated and hands it, unverified, to the app's webhook handler.

### Finding Description
`Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

while `shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header, completely outside the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` only ever validates `to_signable_string` (the body) against `hmac`: [3](#0-2) 

`Registry.process` accepts a request once `HmacValidator.validate(request)` succeeds, and then forwards `request.shop` straight into `WebhookMetadata` as the trusted tenant identifier for the handler, with no separate check that the header matches anything cryptographically bound to the body: [4](#0-3) 

The identity binding that should hold is: `hmac(body, client_secret) valid` ⇒ `(body, shop) pair is authentic`. In this implementation the equality actually enforced is only `hmac(body, client_secret) valid` ⇒ `body is authentic`; `shop` is never part of the equation. Because every shop installed on the same app shares the same `client_secret`, a party who legitimately receives real webhook deliveries for their own shop (any merchant who installs the app) possesses valid `(body, hmac)` pairs signed with the app's secret. They can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header naming a different, victim tenant. The signature still validates because the header is not covered by it, so `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop even though the body never came from Shopify for that shop.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: a merchant with a legitimate but low-privilege installation of the app can forge webhook events that a host application will process as belonging to an arbitrary other merchant/tenant (cross-tenant access), e.g. triggering app-side data mutation, uninstall handling, or business logic keyed off `data.shop` for a shop the attacker does not control. This matches the "High/Critical - cross-tenant access" impact class defined in scope, since the identity binding (`shop` vs. the bytes actually verified by the HMAC) is broken.

### Likelihood Explanation
Likelihood is realistic but requires the attacker to first obtain at least one genuine, validly-signed webhook body from their own shop installation (trivial — install the app on a test store and capture a delivery), and to be able to send arbitrary HTTP requests with custom headers to the app's registered webhook endpoint (also trivial, since these are plain HTTP callbacks). No access to `api_secret_key` or a Shopify access token is needed.

### Recommendation
Bind the tenant/shop identity into the signed material that `HmacValidator` verifies, or otherwise cryptographically tie `shop` to the delivery: e.g., have `Request#to_signable_string` include the shop domain (and ideally webhook id / topic) alongside the body before hashing, or independently validate that the shop named in the header matches a shop the receiving app actually has an active session/installation for before invoking the handler with that identity.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; capture a real webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC-SHA256(client_secret, B)`).
2. Construct a new HTTP POST to the app's webhook endpoint with the identical body `B` and identical `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers).hmac` still equals `H`, and `Utils::HmacValidator.validate` succeeds because it only hashes `B`.
4. `ShopifyAPI::Webhooks::Registry.process` invokes the registered handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the event body never originated from Shopify for that shop — demonstrating the shop identity spoof. [4](#0-3)
