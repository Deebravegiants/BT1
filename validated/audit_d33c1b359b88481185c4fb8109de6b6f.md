### Title
Unsafe support of non-standard ERC-20 tokens in `IntentGatewayV2.withdraw` and `SweepDust` handling — return value of `transfer` not checked - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
In the Tron variant of the intents `IntentGatewayV2` contract, escrow withdrawal (`withdraw`) and dust sweeping (`onAccept`/`SweepDust`) release tokens using a raw low-level `.call` to the `transfer` selector, checking only that the call did not revert (`success`) but never decoding/validating the boolean return value of `transfer`. Non-standard ERC-20 tokens that return `false` on failure instead of reverting will be treated as a successful transfer: escrow accounting is decremented and the order is marked filled/refunded, even though no tokens actually reached the beneficiary.

### Finding Description
`withdraw()` is the function that releases escrowed input tokens to a beneficiary after a cross-chain fill (`RedeemEscrow`) or a refund (`RefundEscrow`/GET-response path). For ERC20 tokens it does: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

Only `success` (whether the low-level call reverted) is checked; the ABI-encoded `bool` return value that `transfer` is supposed to return is discarded. The same unsafe pattern is repeated for the transaction-fee payout in `withdraw` and for the `SweepDust` handling in `onAccept`: [2](#0-1) [3](#0-2) 

By contrast, deposit-side transfers in the same file correctly use `SafeERC20.safeTransferFrom` (which does check the return value): [4](#0-3) [5](#0-4) 

showing that `SafeERC20`/`safeTransfer` is available (`using SafeERC20 for IERC20;` is declared) but simply wasn't applied to the outbound `withdraw`/`SweepDust` paths.

`withdraw` is reachable from `onAccept`, which is invoked by the ISMP host when a relayer delivers a `RedeemEscrow` or `RefundEscrow` cross-chain message, and from `onGetResponse` for the source-chain refund path: [6](#0-5) 

Since ERC20 tokens like USDT (on some deployments) or other non-standard tokens can return `false` on a failed `transfer` (e.g., due to a blacklist, paused state, or insufficient contract balance) instead of reverting, `withdraw` will not detect the failure. `_orders[body.commitment][token] -= amount` still executes, and `_filled[body.commitment] = beneficiary` is set, permanently marking the order as settled — even though the beneficiary received nothing. The escrowed tokens remain stuck in the contract with no accounting path to recover them (the order is already marked filled/refunded, so it cannot be retried), and separately the destination-chain state (order filled) has already been committed based on the assumption the escrow would be honored.

### Impact Explanation
This causes permanent freezing of the escrowed funds for the affected order/token: the beneficiary receives no tokens, but the contract's internal accounting treats the transfer as complete and the order can never be re-settled through the normal withdrawal/refund path. Given intents escrow custody of user funds across chains, this is a fund-loss/freezing bug for any listed token that doesn't strictly follow the reverting-`transfer` convention.

### Likelihood Explanation
Likelihood is moderate: exploitation/triggering requires either an integrated non-standard token that returns `false` instead of reverting, or a token that ends up in a state where `transfer` fails "quietly" (e.g., blacklisted recipient, paused token, or ERC20 with insufficient balance due to fee-on-transfer edge cases). It requires no privileged actor — it is triggered naturally by normal relayed message delivery (`onAccept`/`onGetResponse`) once such a token is used with the gateway.

### Recommendation
Replace the raw `.call` + `success`-only check with `SafeERC20.safeTransfer` (already imported and used via `using SafeERC20 for IERC20;` elsewhere in the file) in `withdraw` (both the token loop and the fee payout) and in the `SweepDust` branch of `onAccept`, so that both a reverting call and a `false` return value are treated as failures.

### Proof of Concept
1. Configure/whitelist a token whose `transfer` implementation returns `false` on failure instead of reverting (e.g., a legacy USDT-style token, or one that blacklists a recipient).
2. Create and fill a cross-chain order using that token as an input asset; the source-chain gateway escrows the tokens via `safeTransferFrom` (correctly checked).
3. On settlement, a relayer delivers the `RedeemEscrow`/`RefundEscrow` message, triggering `onAccept` → `withdraw`.
4. If the beneficiary is blacklisted (or the token otherwise fails to transfer) and the token returns `false` rather than reverting, `withdraw`'s `token.call(...)` returns `success = true` even though no tokens moved.
5. `_orders[body.commitment][token] -= amount` executes and `_filled[body.commitment]` is set, permanently closing out the order while the beneficiary got zero tokens — the escrowed balance is now stuck in the contract with no code path to reclaim it.
