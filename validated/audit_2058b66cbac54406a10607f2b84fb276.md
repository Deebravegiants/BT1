### Title
Legacy `coin::freeze_coin_store` freezes only the `CoinStore`, leaving the paired primary `FungibleStore` balance fully transferable - (File: `aptos-move/framework/aptos-framework/sources/coin.move`)

### Summary
This is the direct Aptos analog of the Morpho/Aave bug: a custody-control action taken on one representation of an asset (the Aave collateral flag / here, the legacy `CoinStore`) is not propagated to a second, economically-linked representation of the same asset (Morpho's internal accounting / here, the paired primary `FungibleStore`), so the control (seize-prevention / freeze) silently fails to cover the user's full balance.

### Finding Description
Since the coin→fungible-asset migration, a single logical balance for `CoinType` can be split across two resources for the same account: the legacy `CoinStore<CoinType>` and the paired primary `FungibleStore` (accessed via `primary_fungible_store`). `balance<CoinType>` explicitly sums both: [1](#0-0) 

The framework itself acknowledges that `frozen` semantics must stay consistent across both resources — `maybe_convert_to_fungible_store` explicitly re-applies the `CoinStore.frozen` flag onto the newly created primary `FungibleStore` during migration, with a comment stating the intent to keep "frozen semantic as consistent as possible": [2](#0-1) 

However, the legacy freeze entry points that a `FreezeCapability<CoinType>` holder actually calls to freeze/unfreeze an account only touch the `CoinStore` resource and never sync the paired `FungibleStore`: [3](#0-2) 

Additionally, the public view function `is_coin_store_frozen`, which issuers/integrators use to check an account's frozen status, only inspects `CoinStore.frozen` and has no knowledge of the paired `FungibleStore`'s frozen flag: [4](#0-3) 

Meanwhile, transfers/deposits/withdrawals on the primary fungible store (`primary_fungible_store::transfer`, `dispatchable_fungible_asset::transfer`, etc.) check only the `FungibleStore.frozen` flag via `fungible_asset::deposit_sanity_check` / `withdraw_sanity_check_impl`: [5](#0-4) 

Because a user can hold (or later receive) a balance in the primary `FungibleStore` independently of the `CoinStore` — e.g. from any counterparty using native FA transfer paths, or from a prior partial migration — calling `freeze_coin_store` does **not** freeze that FA-side balance. The corrupted control here is the `frozen` boolean: the issuer/holder of `FreezeCapability<CoinType>` believes (and `is_coin_store_frozen` reports) the account is fully frozen, while the FA-side balance for the exact same `CoinType`-paired asset remains freely transferable.

### Impact Explanation
An issuer that relies on `FreezeCapability<CoinType>` + `is_coin_store_frozen` to halt movement of a compromised, sanctioned, or otherwise flagged account's holdings (a legitimate custody/compliance control tied to a live, mainnet asset) can be silently bypassed for any portion of that account's balance sitting in the paired primary fungible store. Funds thought to be locked can still be transferred, deposited to, or withdrawn from via FA-native entry points, defeating the freeze control entirely for that portion of the balance. This is a custody/control-integrity break directly analogous to the reported bug (a protective flag on one ledger not enforced on the economically-linked ledger), not merely a display/event mismatch, since it results in unauthorized movement of an asset an authorized party intended to be immobilized.

### Likelihood Explanation
Likelihood is realistic but conditional: it requires (a) a `CoinType` that has been paired with a fungible asset (which now happens automatically/by default for most coins post fungible-asset migration), and (b) the target account holding or being able to receive a balance in its primary fungible store (trivial — any FA-native transfer to the account creates one). No privileged/social-engineering assumption beyond the `FreezeCapability` holder performing its normal, intended freeze action is required; the break is a straightforward oversight of not calling `fungible_asset::set_frozen_flag_internal` alongside `CoinStore.frozen = true`, unlike the migration code path which the framework itself proves is the correct behavior.

### Recommendation
Update `freeze_coin_store` / `unfreeze_coin_store` (and `is_coin_store_frozen`) to also set/read the frozen flag of the paired primary `FungibleStore` when a paired metadata exists, mirroring the logic already implemented in `maybe_convert_to_fungible_store`. Alternatively, deprecate the legacy freeze API in favor of a unified freeze path that always operates through `primary_fungible_store::set_frozen_flag` for both possible balance homes.

### Proof of Concept
1. Issuer creates `CoinType` with `FreezeCapability`, and pairing to fungible asset is created (`ensure_paired_metadata` / `create_pairing`), so both `CoinStore<CoinType>` and a primary `FungibleStore` can exist for the same account.
2. Victim account has a legacy `CoinStore<CoinType>` balance and separately receives/holds fungible-asset balance in its primary `FungibleStore` for the paired metadata (e.g., via `primary_fungible_store::transfer` from a third party, or partial migration).
3. Issuer calls `coin::freeze_coin_store<CoinType>(victim, &freeze_cap)`. `is_coin_store_frozen<CoinType>(victim)` now returns `true`, and any call to `coin::transfer<CoinType>` / `coin::withdraw<CoinType>` sourced purely from `CoinStore` aborts as expected.
4. Victim (or an attacker who compromised the victim's key, which is exactly the scenario a freeze is meant to mitigate) calls `primary_fungible_store::transfer` (or any FA-native entry function) moving the primary-store balance of the paired metadata out of the account. This succeeds because `fungible_asset::deposit_sanity_check`/`withdraw_sanity_check_impl` only check `FungibleStore.frozen`, which was never set by `freeze_coin_store`.
5. Result: the account's `CoinType`-denominated balance is only partially frozen; the FA-side portion moved despite the issuer's freeze and despite `is_coin_store_frozen` reporting the account as frozen.

**Caveat:** I could not fully trace the body of `coin::withdraw<CoinType>` / `coin::transfer<CoinType>` (only `calculate_amount_to_withdraw` was retrieved) to confirm whether the legacy `transfer`/`withdraw` entry points themselves also check `FungibleStore.frozen` when drawing from the primary store portion of a mixed balance; if they do, the exploitable gap is narrower (limited to FA-native transfer paths and direct `primary_fungible_store`/`dispatchable_fungible_asset` calls, not `coin::transfer`). This is due to index size limits on retrievable file content — a full review of `coin.move`'s `withdraw`/`transfer`/`deposit` bodies via a Devin session is recommended to confirm the exact blast radius before treating this as final.
