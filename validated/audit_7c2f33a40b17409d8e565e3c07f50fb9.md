### Title
Direct LT donations to a bonding-curve Pair become permanently unrecoverable after graduation - (`File: packages/contracts/src/Pair.sol`, `packages/contracts/src/Router.sol`, `packages/contracts/src/Bonding.sol`)

### Summary
Any LT sent directly to a token's curve `Pair` via `IERC20.transfer` (bypassing `Zap.buy`) is never reflected in the pair's stored `assetReserve`, and `Router.graduate` only drains the exact `ltFromPair` amount computed from stored reserves. Once the token's lifecycle passes `Curve`, nothing can ever pull the donated LT back out of the abandoned `Pair` contract — the exact "funds stuck in a strategy/pool contract because of internal accounting vs. real balance" bug class described in the reference report.

### Finding Description
`Pair.transferAsset` can only be called by an address holding `BONDING_ROLE` via `Router`, and `Router.graduate` transfers an **explicit `amount`**, not `assetBalance()`: [1](#0-0) [2](#0-1) 

During graduation, `Bonding` computes `ltFromPair = reserve1 - virtualLtReserve` from the pair's **stored** reserves (not its live balance) and drains exactly that via `Router.graduate(token, ltFromPair)`, deliberately leaving any donated LT behind: [3](#0-2) 

This is confirmed by the test suite, which explicitly asserts the donation is left in the pair after `graduate`: [4](#0-3) 

The natspec on `Router.graduate` even documents that the leftover's "lockedness" is a *trust assumption*, dependent on `BONDING_ROLE` never being granted elsewhere and `Bonding` only ever calling `graduate` from the one-time `_prepareGraduationLiquidity` path — i.e. once a token's lifecycle flips past `Curve`, that call site becomes permanently unreachable for that token: [5](#0-4) 

There is no sweep, rescue, or admin withdrawal function anywhere in `Pair`, `Router`, or `Bonding` that can move `assetBalance()` beyond the tracked `ltFromPair` out of a graduated (or even still-curving) pair. `FeeVault` has an explicit `sweepDonations()` for exactly this class of accidental-donation risk on USDC, but no equivalent exists for LT donated straight to a `Pair`: [6](#0-5) 

This mirrors the reported bug precisely: an internal accounting variable (`poolAmount` in the reference report, `assetReserve`/`ltFromPair` here) under-tracks the contract's real token balance, and the withdrawal/drain path is bounded by that internal variable rather than the live balance, permanently stranding the difference. The reference report's own framing — "user may find it easier to simply send funds to the pool address" — applies directly here: the `Pair` address is a normal, discoverable ERC20-pair-shaped contract (`getTokenInfo`/`Trade` events expose it), so a user or integrator naively doing a raw `transfer` to it instead of `Zap.buy` loses their LT permanently.

### Impact Explanation
Any LT donated directly to a curve `Pair` — whether by user mistake, a naive integration, or intentional value transfer — is permanently and irrecoverably locked once that token graduates (or indefinitely while still on-curve, since no in-lifecycle sweep exists either). This is a permanent freezing of user funds with no admin or protocol recovery path, satisfying the Medium bar of "permanent freezing of trader ... funds."

### Likelihood Explanation
Likelihood is driven by ordinary user error rather than sophisticated exploitation: any address can call `IERC20(lt).transfer(pairAddress, amount)` at any time (curve or post-graduation) with zero preconditions or privilege. The protocol's own documentation acknowledges this exact class of donation happening as an attacker-griefing vector during graduation (Regime 2/3 hostile pre-seed handling on the HyperSwap side), showing donation-to-pair is a realistic, expected occurrence — but on the bonding-curve `Pair` side, unlike `FeeVault`, no recovery mechanism was built for it.

### Recommendation
Add a permissionless (or owner-gated) sweep function on `Pair` (or a `Router`/`Bonding` wrapper) that transfers `assetBalance() - assetReserve` (and similarly for `tokenBalance() - tokenReserve`, mirroring the existing burn-on-graduation handling for token donations) to a designated recipient — analogous to `FeeVault.sweepDonations()`. This should be safe post-graduation as well, since `assetReserve`/`tokenReserve` are frozen once the pair is drained.

### Proof of Concept
1. Creator launches a token via `Zap.createToken`, producing `Pair` `P` for `(token, LT)`.
2. A user, meaning to fund/support the curve, mistakenly calls `LT.transfer(P, 1000e18)` directly instead of `Zap.buy(...)`. `P.assetBalance()` increases by `1000e18`, but `P.getReserves()`'s `assetReserve` (and thus the graduation `ltFromPair` computation) is unaffected.
3. Trading continues; eventually the token graduates via `Bonding.finalizeGraduation` (either supply or USD trigger). `_prepareGraduationLiquidity` computes `ltFromPair` from stored reserves and calls `Router.graduate(token, ltFromPair)`, draining only the curve-raised amount — the donated `1000e18` LT stays in `P`.
4. The token's lifecycle is now past `Curve`; no code path in `Bonding`, `Router`, or `Pair` can invoke `Router.graduate` (or any other `transferAsset` caller) against `P` again.
5. The `1000e18` LT is permanently stranded in `P` with no way for the user, the creator, or the protocol to recover it — confirmed by `test_graduate_leavesDonationBehind` in `Router.t.sol`, which pins exactly this "donation remains locked in pair" behavior with no follow-up recovery test or function. 1. Read `(reserve0, reserve1)` from the Pair **before** any state mutation.
2. Burn any unsold real curve tokens from the pair (`unsoldBurned`). This also burns any tokens donated to the pair via direct ERC20 transfer.
3. Recover `virtualLtReserve = Pair.k() / Token.TOTAL_SUPPLY()` and compute `ltFromPair = reserve1 - virtualLtReserve` — the real LT raised by the curve, excluding the launch-time virtual seed AND any LT donated to the pair. Drain exactly that amount via `Router.graduate(token, ltFromPair)`. Donated LT remains in the curve pair, reachable only via `Pair.transferAsset` which is gated by `Router`'s `BONDING_ROLE`.
4. Compute `tokensForLP = (ltFromPair × reserve0) / reserve1` — the unique amount that sets the LP price `ltFromPair / tokensForLP` equal to the last curve price `reserve1 / reserve0`. Capped at `lpReserveTotal` as a defensive guard (parabola math proves `tokensForLP ≤ lpReserveTotal` by construction).
5. Burn `lpReserveTotal − tokensForLP` from `Bonding`'s held reserve (`lpBurned`).
6. `addLiquidity(tokensForLP, ltFromPair)` on HyperSwap V2 → LP tokens go to `LPLock`.

    function sweepDonations() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        uint256 backed = $.totalAccruedCreator + $.protocolBalance;
        uint256 balance = $.usdc.balanceOf(address(this));
        if (balance <= backed) revert NothingToClaim();
        amount = balance - backed;
        address feeTo_ = $.feeTo;
        $.usdc.safeTransfer(feeTo_, amount);

    }
