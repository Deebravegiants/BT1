### Title
Missing freeze-authority validation on `coin_mint`/`pc_mint` in `Initialize2` allows a malicious pool creator to permanently freeze pool funds - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` only rejects a `lp_mint` that has a freeze authority set; it never checks whether the attacker-supplied `coin_mint` or `pc_mint` retain a freeze authority. Because the pool's coin/pc vaults are just ordinary SPL Token accounts of those mints, whoever controls the mint's freeze authority can freeze the AMM's own vault account (or any user's LP-related token account) at any time after liquidity has been deposited by other users, permanently blocking `Deposit`, `Withdraw`, and both swap instructions for that pool. This mirrors the `BeforeSendHook` DoS pattern in the reference report: an untrusted party retains an out-of-band mechanism to unilaterally force SPL transfers to fail, freezing funds contributed by other, unrelated users.

### Finding Description
`process_initialize2` validates several properties of the coin/pc vault accounts (owner, non-zero amount, no delegate, no close authority) and of the `lp_mint` (zero supply, `mint_authority == amm_authority`, no freeze authority): [1](#0-0) 

However, the mints of the coin/pc side of the pool — `amm_coin_mint_info` / `amm_pc_mint_info`, which are fully attacker-controlled since anyone can call `Initialize2` with arbitrary mints — are only unpacked to read `decimals`; their `freeze_authority` field is never inspected: [2](#0-1) 

The coin/pc vault accounts created for the pool are standard SPL Token accounts owned by `amm_authority` for that mint: [3](#0-2) 

Because SPL Token's `FreezeAccount` instruction can be invoked by the mint's freeze authority against *any* token account of that mint — including the AMM's vault, which the AMM program does not own the mint for — a pool creator who keeps the freeze authority on `coin_mint`/`pc_mint` can freeze the vault after other LPs have deposited real funds via `Deposit`, `Withdraw`, or swap instructions: [4](#0-3) [5](#0-4) [6](#0-5) 

All of these paths use `Invokers::token_transfer` / `token_transfer_with_authority`, which are plain SPL Token CPI wrappers with no resilience to a frozen source/destination account: [7](#0-6) 

No `is_frozen`/`AccountState::Frozen` check exists anywhere in `processor.rs`, and `InvalidFreezeAuthority` is used exactly once, for the `lp_mint` only. This confirms the coin/pc side of the pool is unprotected against this class of attack.

### Impact Explanation
Once the coin or pc vault (or a counterpart LP holder's ATA of that mint) is frozen by the mint's freeze authority:
- `Deposit` fails permanently for that pool (transfer into the frozen vault reverts).
- `Withdraw` fails permanently, so all LPs (not just the attacker) can never redeem their share of the frozen-side vault — their funds are permanently locked.
- Both swap instructions fail permanently, since every swap moves tokens in or out of the affected vault, making the pool a dead/DoS'd pool.

This is a direct permanent freezing of LP/user funds triggered unilaterally by a single privileged-but-unvetted party (the original pool creator retaining freeze authority on the token mint they chose to pair) — the same impact class (funds frozen via a transfer-blocking mechanism the attacker alone controls) as the `BlockBeforeSend` finding in the reference report.

### Likelihood Explanation
Any unprivileged user can call `Initialize2` (it is a normal, permissionless pool-creation instruction) supplying their own custom mint with `freeze_authority = Some(attacker)`. There is no check preventing this, and legitimate LPs have no signal at deposit time distinguishing such a mint from a normal one unless they manually inspect on-chain mint metadata. Likelihood is high because the exploit requires only one Initialize2 call plus a wait for other liquidity to arrive, then a single `FreezeAccount` transaction to the mint's freeze authority.

### Recommendation
In `process_initialize2`, mirror the `lp_mint` freeze-authority check for `coin_mint` and `pc_mint`: reject pool creation (return `AmmError::InvalidFreezeAuthority`) if either mint's `freeze_authority` is `Some(_)`. Additionally consider re-checking vault account frozen state (or refusing operations on frozen vaults with a clear error) in `Deposit`/`Withdraw`/swap paths as defense in depth for mints that could otherwise have their freeze authority reassigned via governance/multisig changes after pool creation.

### Proof of Concept
1. Attacker mints `coin_mint` via the SPL Token program, setting `freeze_authority = attacker_pubkey`.
2. Attacker calls `Initialize2` pairing `coin_mint` with a normal `pc_mint`, seeding initial liquidity as required by [8](#0-7) .
3. A victim LP calls `Deposit`, successfully adding coin/pc tokens to `amm_coin_vault`/`amm_pc_vault`.
4. Attacker submits a standard SPL Token `FreezeAccount` instruction (signed by the freeze authority) targeting `amm_coin_vault`.
5. Any subsequent `Deposit`, `Withdraw`, or swap instruction touching `amm_coin_vault` now fails at the `token_transfer`/`token_transfer_with_authority` CPI because the source/destination account is frozen, permanently locking the victim's deposited funds in the vault with no on-chain recovery path.

    pub fn token_transfer<'a>(
        token_program: AccountInfo<'a>,
        source: AccountInfo<'a>,
        destination: AccountInfo<'a>,
        owner: AccountInfo<'a>,
        deposit_amount: u64,
    ) -> Result<(), ProgramError> {
        let ix = spl_token::instruction::transfer(
            token_program.key,
            source.key,
            destination.key,
            owner.key,
            &[],
            deposit_amount,
        )?;
        solana_program::program::invoke_signed(
            &ix,
            &[source, destination, owner, token_program],
            &[],
        )
    }

    /// Issue a spl_token `Transfer` instruction.
    pub fn token_transfer_with_authority<'a>(
        token_program: AccountInfo<'a>,
        source: AccountInfo<'a>,
        destination: AccountInfo<'a>,
        authority: AccountInfo<'a>,
        amm_seed: &[u8],
        nonce: u8,
        amount: u64,
    ) -> Result<(), ProgramError> {
        let authority_signature_seeds = [amm_seed, &[nonce]];
        let signers = &[&authority_signature_seeds[..]];
        let ix = spl_token::instruction::transfer(
            token_program.key,
            source.key,
            destination.key,
            authority.key,
            &[],
            amount,
        )?;
        solana_program::program::invoke_signed(
            &ix,
            &[source, destination, authority, token_program],
            signers,
        )
    }
