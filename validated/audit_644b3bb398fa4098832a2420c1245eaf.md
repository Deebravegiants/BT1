### Title
Bridge Outgoing Token (webhook authentication secret) exposed to View-role users via `GET /v2/bridge_types/:BridgeName` and GraphQL `bridge` query - ([File: core/web/bridge_types_controller.go])

### Summary
The Foreman advisory describes a low-privileged, view-only authenticated actor being able to read a sensitive credential (the Proxmox password) through an API endpoint that should only expose non-sensitive host metadata. The chainlink codebase has an analogous pattern: the bridge `OutgoingToken` — a secret used to authenticate Chainlink's outgoing webhook calls to an external adapter — is returned in full to any authenticated user holding only the `View` role, via both the REST `Show` route and the GraphQL `bridge` query.

### Finding Description
`BridgeResource` (the JSON:API presenter for a bridge) includes the `OutgoingToken` field without redaction: [1](#0-0) 

`NewBridgeResource` populates this field directly from the stored `bridges.BridgeType.OutgoingToken` value: [2](#0-1) 

The router wires the `GET /v2/bridge_types/:BridgeName` route to `bt.Show` with **no role restriction** (unlike `Create`, `Update`, `Destroy`, which are wrapped in `auth.RequiresEditRole`): [3](#0-2) 

This is confirmed by the RBAC route test table, where `GET /v2/bridge_types/MOCK` is marked `viewOnlyAllowed: true` — i.e., a `View`-role user is expected to successfully retrieve this route without a 401/403: [4](#0-3) 

The `View` role is the codebase's lowest-privilege authenticated role, analogous to "view_hosts" permission in the Foreman/Proxmox report — it is only blocked from `Run`/`Edit`/`Admin`-gated actions: [5](#0-4) 

The same secret is also exposed via GraphQL: the `Bridge` type's `outgoingToken` field is a required, always-populated string, resolved by `BridgeResolver.OutgoingToken()`: [6](#0-5) [7](#0-6) 

GraphQL query-level access control for reading a bridge only requires `authenticateUser`, which grants any authenticated session (including `View` role) access — it does not require `authenticateUserCanRun`/`CanEdit`/`IsAdmin`: [8](#0-7) 

The `OutgoingToken` is a genuine secret: it is generated via `utils.NewSecret(24)` at bridge creation time and used to authenticate outbound webhook/adapter requests, functionally equivalent in sensitivity to a stored credential/password: [9](#0-8) 

This mirrors the CVE-2021-20259 root cause: a credential/secret needed only for privileged/system-level operations is surfaced through a read endpoint reachable by an authenticated actor holding only view-level permissions.

### Impact Explanation
An authenticated node user provisioned with only the `View` role (e.g., a read-only dashboard/monitoring account) can retrieve the `OutgoingToken` for any configured bridge by calling `GET /v2/bridge_types/:BridgeName` or querying the `bridge` GraphQL field. Possession of this token could allow the low-privileged actor to impersonate the Chainlink node's outgoing webhook calls to the external adapter (depending on how the adapter validates the token), or otherwise misuse a credential they should not have access to under the node's own RBAC model. This directly matches the CWE-200 (Exposure of Sensitive Information to an Unauthorized Actor) classification and the "authenticated but under-privileged actor obtains a secret via an API they can legitimately reach" pattern of the source advisory.

### Likelihood Explanation
Likelihood is high for any deployment where multiple user roles are configured (a supported, documented feature — LDAP/OIDC/local roles all support `View`), since exploitation requires nothing beyond a normal, valid low-privilege session and a single unauthenticated-role-checked GET request; no additional bypass or timing is needed.

### Recommendation
- Redact/omit `OutgoingToken` from the `BridgeResource` presenter (and GraphQL `Bridge` type) for users below `Edit`/`Admin` role, similar to how `IncomingToken` is already `omitempty` and only populated on creation.
- Alternatively, gate `GET /v2/bridge_types/:BridgeName` (and the equivalent GraphQL resolver) behind `auth.RequiresEditRole` / `authenticateUserCanEdit`, consistent with the mutating bridge routes.
- Audit other presenters/resolvers for the same "token/secret returned to any authenticated session" pattern (e.g., `ExternalInitiatorResource.OutgoingToken`, `ExternalInitiatorAuthentication`) since they use the identical unguarded-GET pattern.

### Proof of Concept
1. Provision a Chainlink node user with role `View` (e.g., via `/v2/users` as admin, or LDAP/OIDC read-claim mapping).
2. As admin, create a bridge (`POST /v2/bridge_types`) to obtain a bridge name; note the server-issued `outgoingToken`.
3. Authenticate as the `View`-role user (session cookie or API token).
4. Call `GET /v2/bridge_types/<BridgeName>`.
5. Observe the JSON:API response includes `"outgoingToken": "<secret>"` — the full, unredacted secret is disclosed to a user who cannot create, update, or delete bridges.
6. Equivalently, issue the GraphQL query `{ bridge(name: "<BridgeName>") { ... on Bridge { outgoingToken } } }` as the same `View`-role session and observe the same disclosure.

		user, ok := GetAuthenticatedUser(c)

		}

	}

	return func(c *gin.Context) {

		if !ok {
			c.Abort()

	}

// NewBridgeType returns a bridge type authentication (with plaintext
// password) and a bridge type (with hashed password, for persisting)
func NewBridgeType(btr *BridgeTypeRequest) (*BridgeTypeAuthentication,
	*BridgeType, error,
) {
	incomingToken := utils.NewSecret(24)
	outgoingToken := utils.NewSecret(24)
	salt := utils.NewSecret(24)

	hash, err := incomingTokenHash(incomingToken, salt)
	if err != nil {
		return nil, nil, err
	}

	return &BridgeTypeAuthentication{
		Name:                   btr.Name,
		URL:                    btr.URL,
		Confirmations:          btr.Confirmations,
		IncomingToken:          incomingToken,
		OutgoingToken:          outgoingToken,
		MinimumContractPayment: btr.MinimumContractPayment,
		UseConnectionManager:   btr.UseConnectionManager,
	}, &BridgeType{
		Name:                   btr.Name,
		URL:                    btr.URL,
		Confirmations:          btr.Confirmations,
		IncomingTokenHash:      hash,
		Salt:                   salt,
		OutgoingToken:          outgoingToken,
		MinimumContractPayment: btr.MinimumContractPayment,
		UseConnectionManager:   btr.UseConnectionManager,
	}, nil
}
