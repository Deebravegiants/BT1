### Title
Missing duplicate-authority-index check in BEEFY supermajority threshold allows signature replay to forge consensus finality - (File: `evm/src/consensus/EcdsaBeefy.sol` / `modules/consensus/beefy/verifier/src/lib.rs`)

### Summary
Both the Solidity (`EcdsaBeefy.sol`) and Rust (`beefy/verifier/src/lib.rs`) BEEFY consensus clients compute the 2/3+1 supermajority participation threshold from the raw count of submitted votes/signatures (`sigLen` / `signatures_length`) rather than from the count of *unique* authority indices that produced them. Unlike sibling consensus clients in the same codebase — Pharos (`verify_validator_membership`, which explicitly rejects `Error::DuplicateParticipant`) and Tendermint (`ensure_unique_addresses`) — the BEEFY verifiers contain no equivalent uniqueness check before the threshold is evaluated.

### Finding Description
`EcdsaBeefy.verifyMmrUpdateProof` reads `sigLen = relayProof.signedCommitment.votes.length` and immediately checks `checkParticipationThreshold(sigLen, authoritySet.len)` [1](#0-0)  before recovering signer addresses and merkle-verifying them against the authority set root [2](#0-1) . Nowhere in this flow is it verified that the `vote.authorityIndex` values are distinct.

The Rust equivalent has the identical structure: `signatures_length` gates `check_participation_threshold` [3](#0-2) , and the subsequent loop builds `authority_leaves`/`authority_indices` directly from `mmr.signed_commitment.signatures` without deduplication [4](#0-3) .

By contrast, the Pharos client explicitly guards this exact bug class: `verify_validator_membership` deduplicates `participant_keys` and rejects the proof with `Error::DuplicateParticipant` if the deduplicated set is smaller than the submitted list [5](#0-4) , and the Tendermint verifier calls `ensure_unique_addresses` on validator sets before trusting them [6](#0-5) . The BEEFY clients lack this defense-in-depth, so a relayer submitting a BEEFY consensus proof can pad `sigLen`/`signatures_length` with repeated valid `(authorityIndex, signature)` pairs from a small number of colluding or compromised authorities to satisfy the raw-count supermajority check, without a genuine 2/3+1 quorum of distinct authorities ever having signed the commitment.

This is directly analogous to CVE-2019-9148's root cause: a trust decision (there, "this key/identity is validly certified"; here, "this many distinct authorities attest to this commitment") is made from an unvalidated count of claims rather than from validated, deduplicated identities.

### Impact Explanation
If duplicate authority indices are accepted toward the threshold, an attacker controlling or having leaked signing keys for a minority of BEEFY authorities (fewer than 2/3+1) could still satisfy `checkParticipationThreshold` by resubmitting valid signatures under repeated indices, allowing a forged/short-quorum consensus update to be accepted. This directly affects `IConsensusV2.verify` output — the intermediate state commitments used by `EvmHost`/pallet-ismp to accept state roots for message and token-bridge proof verification — so a successful bypass forges message delivery/state commitment for the entire downstream ISMP pipeline (Medium/High severity depending on whether the underlying `MerkleMultiProof.VerifyProof` from the external `solidity-merkle-trees` library independently rejects duplicate indices at the same k-index).

### Likelihood Explanation
Exploitability hinges on whether the external `MerkleMultiProof.VerifyProof` (from `@polytope-labs/solidity-merkle-trees`, not present in this repository's indexed sources) tolerates duplicate `(index, hash)` leaf entries during proof verification. This could not be conclusively confirmed from the code available in this repository — the dependency's implementation is out of scope for this index. This uncertainty is the main caveat on likelihood; the application-layer gap (no duplicate check prior to/alongside the merkle verification) is nonetheless a clear and provable deviation from the codebase's own established pattern for this exact bug class (see Pharos and Tendermint counter-examples above).

### Recommendation
Add an explicit uniqueness check on `vote.authorityIndex` (Solidity) / `sig.index` (Rust) before or as part of the threshold check in `EcdsaBeefy.verifyMmrUpdateProof` and `beefy/verifier/src/lib.rs::verify_mmr_update_proof`, mirroring `Error::DuplicateParticipant` in the Pharos verifier [5](#0-4) , so that the supermajority threshold is computed over distinct authorities rather than raw submitted signature count.

### Proof of Concept
1. Obtain (or compromise) valid BEEFY signatures from `k < 2/3*N + 1` distinct authorities for a given `commitmentHash`.
2. Construct `relayProof.signedCommitment.votes` (or `mmr.signed_commitment.signatures`) with more than `2/3*N + 1` total entries by repeating the same valid `(authorityIndex, signature)` pairs from the `k` compromised authorities.
3. Submit to `EcdsaBeefy.verify` / `verify_consensus`. `sigLen`/`signatures_length` (the padded count) passes `checkParticipationThreshold`/`check_participation_threshold` [7](#0-6) [8](#0-7)  even though fewer than the required unique authorities actually attested.
4. If the downstream `MerkleMultiProof.VerifyProof`/`merkle_proof.verify` call does not itself reject duplicate index entries, the forged state commitment is accepted, propagating a false state root into `IntermediateState` and onward into ISMP message/state verification.

/// Verify that all participating validators are members of the trusted validator set.
fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}
