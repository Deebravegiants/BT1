Unsigned `x-shopify-shop-domain` header lets attacker impersonate any merchant on webhook delivery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC computed by `Utils::HmacValidator` covers exclusively the request body. `Webhooks::Request#shop` (backed by the `x-shopify-shop-domain`/`shopify-shop-domain` header) is never included in the signed material, so an attacker who legitimately receives one valid `(body, hmac)` pair for their own shop can resend it to the same endpoint with an arbitrary `x-shopify-shop-domain` value and have `Registry.process` accept it as authentic for a different, victim merchant.

### Finding Description
The binding that must hold is: `hmac_received == HMAC(secret, to_signable_string)` should only authenticate values that downstream code treats as trusted. In practice, `Registry.process` treats `request.shop` as trusted, authenticated tenant identity: [1](#0-0) 

But `to_signable_string` binds the signature to `@raw_body` alone: [2](#0-1) 

`request.shop` is read straight from the `x-shopify-shop-domain` header, which is completely outside that signable string: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` only ever look at `verifiable_query.hmac` and `verifiable_query.to_signable_string`; they never inspect `shop`, `topic`, `webhook-id`, or any nonce/timestamp: [4](#0-3) 

The `api_secret_key` used to compute the HMAC is the app's global client secret (shared across every merchant install), not a per-shop secret, so a signature valid for shop A's webhook is arithmetically valid for the identical body regardless of which shop header accompanies it.

Attack flow: the attacker installs the app on their own development shop and registers a webhook endpoint they control (or their own server pointed at the app's public webhook receiver). They capture one legitimately signed `(raw_body, x-shopify-hmac-sha256)` pair delivered by Shopify. They then POST that exact body and HMAC to the app's webhook endpoint again, but replace `x-shopify-shop-domain` with a victim merchant's `*.myshopify.com` domain. `HmacValidator.validate` recomputes the HMAC over `raw_body` only, which still matches, so `Registry.process` proceeds and calls the topic handler with `WebhookMetadata.new(shop: request.shop, ...)` — i.e., the victim's domain — while the payload content is whatever the attacker originally received (or, if the topic allows attacker-influenced content such as `app/uninstalled`, `shop/update`, or a custom subscribed topic, attacker-chosen data). Any handler logic keyed on `shop` (data isolation, deprovisioning, redaction, cache invalidation, billing, GDPR redact flows) now runs against the wrong tenant, or a request is treated as “from the victim shop” when it never was.

No existing guard prevents this: `ShopValidator.sanitize!`, `Context.setup?`, and `JwtPayload` checks are unrelated to webhook delivery; nothing in `Request#initialize` or `Registry.process` cross-checks `shop` against the signed body, a nonce, a timestamp, or the `x-shopify-webhook-id` header for replay/re-labelling detection.

### Impact Explanation
Any handler that trusts `WebhookMetadata#shop` as the authenticated origin of the event (which is the documented/intended use of this field) can be made to act on behalf of an arbitrary victim merchant using a body the attacker legitimately obtained for their own shop, or in the case of attacker-influenced/duplicate topics, effectively forged data. This is a cross-tenant/authentication-bypass class issue: an unprivileged attacker (their own dev shop, their own installed app instance) can cause the host app to process a request "as" a different merchant. Blast radius extends to every merchant whose `myshopify.com` domain the attacker can guess or discover (these are often predictable or discoverable), and is repeatable indefinitely since nothing expires or single-uses the captured body/HMAC pair.

### Likelihood Explanation
Preconditions are minimal and fully within the stated attacker capability: create a dev shop, install the app, register a webhook, capture one valid delivery. No secrets, no privileged access, and no interaction with the victim are required. The main variable is how much the receiving app's own webhook handler relies on `shop` for authorization/isolation decisions — that is host-app-dependent, but the gem provides no protection at all, so any host app that follows the documented `Registry.process` pattern is exposed by default.

### Recommendation
Include `shop`, `topic`, and ideally `webhook-id`/timestamp in the signable string, or independently verify that the `x-shopify-shop-domain` header matches an app-known/authorized shop before trusting it in `WebhookMetadata`. At minimum, `Webhooks::Request#to_signable_string` should not be the sole security boundary for a value (`shop`) that downstream code treats as authenticated; the header should be validated against session/install records, and delivery should be deduplicated by `x-shopify-webhook-id` to bound replay.

### Proof of Concept
minitest sketch (WebMock/Mocha), no live shop:
```ruby
def test_shop_domain_not_covered_by_signature
  body = '{"id":1}'
  secret = ShopifyAPI::Context.api_secret_key
  hmac = Base64.encode64(OpenSSL::HMAC.digest("sha256", secret, body)).strip

  req_a = ShopifyAPI::Webhooks::Request.new(
    raw_body: body,
    headers: {
      "x-shopify-topic" => "orders/create",
      "x-shopify-hmac-sha256" => hmac,
      "x-shopify-shop-domain" => "victim-shop.myshopify.com",
    },
  )
  req_b = ShopifyAPI::Webhooks::Request.new(
    raw_body: body,
    headers: {
      "x-shopify-topic" => "orders/create",
      "x-shopify-hmac-sha256" => hmac,
      "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
    },
  )

  assert ShopifyAPI::Utils::HmacValidator.validate(req_a)
  assert ShopifyAPI::Utils::HmacValidator.validate(req_b)
  refute_equal req_a.shop, req_b.shop
  # Same signature validates for two different shop identities -> proves
  # to_signable_string does not bind `shop` to the HMAC.
end
```
Assertions on both sides of the equality: `HmacValidator.validate(req_a) == true` and `HmacValidator.validate(req_b) == true` while `req_a.shop != req_b.shop`, demonstrating the signature does not authenticate the shop that `Registry.process` hands to the webhook handler.
