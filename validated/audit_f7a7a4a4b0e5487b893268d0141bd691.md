Confirmed: `WrappedHyperFungibleToken.send()` locks the underlying ERC20 with `safeTransferFrom(msg.sender, address(this), params.amount)` without measuring actual received balance, and unconditionally dispatches `params.amount` as the bridged amount [1](#0-0) . This exactly matches the reported bug class — the contract assumes the transferred amount equals the requested amount, unlike `IntentGatewayV2.placeOrder`, which explicitly measures balance-before/after and mutates the committed amount to the actual received value for fee-on-transfer tokens [2](#0-1) .

### Title
Fee-on-transfer/deflationary underlying tokens cause unbacked minting/unlocking in WrappedHyperFungibleToken - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken.send()` locks the underlying ERC20 by calling `safeTransferFrom(msg.sender, address(this), params.amount)` and then dispatches a cross-chain message encoding `params.amount` as the bridged value, without ever checking how many tokens the contract actually received [1](#0-0) . If the underlying token charges a fee on transfer (e.g., USDT-style fee tokens, rebasing/deflationary tokens), the contract's balance increases by less than `params.amount`, but the destination chain's `onAccept()` unconditionally transfers out the full `message.amount` of its own underlying token to the beneficiary [3](#0-2) .

### Finding Description
The lock-side accounting never reconciles the pre/post balance of `_underlying`:
```solidity
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
...
bytes memory body = abi.encode(HyperFungibleToken.Message({
    from: abi.encodePacked(msg.sender),
    to: params.to,
    amount: params.amount,   // <-- unverified, assumed == actually locked
    data: params.data
}));
``` [4](#0-3) [5](#0-4) 

This is the same class of bug already identified and explicitly mitigated in `IntentGatewayV2.placeOrder`, where the contract measures `balBefore`/`balAfter` around every `safeTransferFrom` and rewrites `order.inputs[i].amount` to the amount actually received before hashing the commitment and crediting escrow [2](#0-1) , and is covered by dedicated fee-on-transfer tests [6](#0-5) . `WrappedHyperFungibleToken` has no equivalent safeguard — the lock leg (`send()`) never adjusts `message.amount` to the actual transferred quantity.

On the receiving side, `onAccept()` decodes the message and unlocks/transfers the full `message.amount` of the peer's own underlying token to the beneficiary, and on WETH-mode chains it even withdraws/pushes native value equal to `message.amount` [7](#0-6) . Because each `WrappedHyperFungibleToken` deployment on every chain independently custodies its own underlying token pool, a lock of `990` (after a 1% transfer fee took `10`) but a dispatched/committed `amount` of `1000` results in the destination chain paying out `1000` units from its own reserve while the source chain's reserve only increased by `990`. Repeated over many transfers, this systematically drains the destination-side custody pool relative to what was actually locked — an unbacked value creation from the perspective of the wrapped-token invariant (total locked on source == total paid out on destination across all messages).

### Impact Explanation
This breaks the fundamental 1:1 backing invariant of a lock/unlock bridge: users (or attackers using intentionally deflationary/fee-on-transfer tokens as the configured `_underlying`) can cause the destination-chain pool to pay out more than was ever actually locked on the source chain. Over repeated transfers, this permanently drains the underlying token reserve on affected chains beyond what is deposited, which is a direct loss of pooled funds for the protocol/other users of the same wrapped-token deployment — a concrete instance of unbacked value transfer via a single submitted transaction (`send()`), reachable by any unprivileged user who configures/uses a fee-on-transfer underlying (or by the token itself later adding a fee via upgradeable/pausable fee mechanisms, if applicable to the configured underlying).

### Likelihood Explanation
Deployments that wrap tokens with any transfer-fee or deflationary mechanic (USDT-with-fee variants, some rebasing/tax tokens) are directly and trivially affected on every single `send()` call — no attacker action beyond calling `send()` normally is required; the discrepancy is baked into the token's own transfer semantics. The IntentGatewayV2 code in the same repository demonstrates the developers are aware of and actively guard against this exact class of token behavior elsewhere, indicating it is a realistic configuration risk that was simply missed in `WrappedHyperFungibleToken`.

### Recommendation
Mirror the pattern already used in `IntentGatewayV2.placeOrder`: record `_underlying` balance before and after the `safeTransferFrom` in `send()`, compute the actual received amount, and use that reconciled amount (not `params.amount`) both in the dispatched `Message.amount` and in the `Sent` event. Optionally, restrict configurable underlyings to tokens verified not to charge transfer fees, or document/reject fee-on-transfer tokens explicitly during `configure()`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` with `_underlying` set to a fee-on-transfer ERC20 charging, e.g., 1% fee on transfer (like the `FeeOnTransferToken` test helper already present in the repo's IntentGatewayV2 tests) [8](#0-7) .
2. User calls `send({..., amount: 1000e18})`. `safeTransferFrom` moves 1000 tokens from the user, but the contract only receives 990 due to the 1% fee [5](#0-4) .
3. The dispatched `Message.amount` is still `1000e18` [9](#0-8) .
4. On the destination chain, `onAccept()` transfers `1000e18` of its own underlying token to the beneficiary [10](#0-9) , i.e., 10 more tokens than were actually locked on the source chain.
5. Repeating this drains the destination pool's reserve relative to genuinely locked collateral, eventually causing insolvency (inability to honor other users' unlock/refund requests) once the pool is depleted.

contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }
}
