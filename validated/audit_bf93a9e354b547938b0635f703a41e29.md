Audit Report

## Title
Replay guard records request digest before owner-authorization validation completes, enabling DoS via replay-guard poisoning - ([File: core/capabilities/vault/authorizer.go])

## Summary
`authorizer.AuthorizeRequest` calls `replayGuard.CheckAndRecord` — which mutates state by marking the digest as "seen" — before `validateSecretOwnersMatchAuthorized` runs and passes. This means a request that ultimately fails owner-binding validation still permanently consumes its digest in the replay guard, which can be exploited to poison a specific, predictable digest and deny a legitimate future request that hashes to the same digest.

## Finding Description
`AuthorizeRequest` performs, in order: (1) delegate auth (allowlist or JWT) to get an `AuthResult` bound to an `authorizedOwner`, (2) `a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt())` — a state-mutating call that inserts the digest into the `seen` map on success, and only then (3) `validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner())`, which checks that the `owner` fields embedded in the request params match the authorized owner. [1](#0-0) 

`RequestReplayGuard.CheckAndRecord` unconditionally records the digest as soon as it is not already present — it does not roll back on a later validation failure elsewhere in the pipeline. [2](#0-1) 

The digest itself is computed over the full request (method/ID/params), including the embedded `owner` fields, via `req.Digest()` in both the allowlist path and the JWT path. [3](#0-2) [4](#0-3) 

For the allowlist path, authorization succeeds if the exact digest of the incoming request appears anywhere in the on-chain `WorkflowRegistry` allowlist, and the "authorized owner" returned is whichever address registered that digest on-chain — not necessarily the owner embedded in the request's own params. [5](#0-4) 

This confirms the reported ordering bug: an attacker who can register their *own* on-chain allowlist entry for an arbitrary digest (computed off-chain over a request whose params reference a victim's owner) will pass step 1 as themselves, cause the digest to be recorded by `CheckAndRecord`, and only then fail `validateSecretOwnersMatchAuthorized` because the params' owner doesn't match their own authorized identity. The pipeline-invariant comment in `gateway_vault_request_processor.go` documents this ordering as intentional but does not account for the digest being committed on paths later rejected. [6](#0-5) 

Existing tests (`TestAuthorizer_AllowListPath_RejectsCreateOwnerMismatch`, etc.) confirm the owner-mismatch rejection path is reached only *after* the digest would already be recorded in a real (non-mocked) replay guard, and no test exercises the sequential double-call scenario (poison-then-legitimate-retry) that would reveal the DoS. [7](#0-6) 

## Impact Explanation
The concrete impact is denial of service against a specific, predictable Vault request (create/update/delete/list secret) belonging to another workflow owner: once an attacker (who legitimately controls a digest registration under their own on-chain identity or their own valid JWT) causes a matching digest to be recorded, the legitimate owner's identical request will be rejected with `ErrRequestAlreadySeen` until the entry's `expiresAt` lapses. This is a genuine availability impact on the vault capability (blocking legitimate secret create/update/delete/list operations), matching the "unauthorized/blocked node API action" class in scope. No funds movement or key exfiltration occurs; the impact is confined to request availability for a specific victim/digest.

## Likelihood Explanation
Exploitation requires the attacker to control a digest that (a) they can get registered/authorized under their own identity (on-chain allowlist entry they self-register, or a JWT with a `request_digest` claim they control) and (b) matches the exact bytes (method + ID + params, including the victim's `owner` field) of a request the victim will legitimately send. This is feasible primarily through the allowlist path, since an attacker can compute an arbitrary digest offline (over params containing a victim's owner) and register that digest against their own address on the `WorkflowRegistry` — a self-service action requiring no privilege beyond being an onboarded workflow owner. Predicting the victim's exact request bytes (particularly `request_id` and secret `key`/`namespace`) is the main constraint on likelihood, but deterministic/well-known IDs in operational tooling make this plausible in specific scenarios rather than purely theoretical.

## Recommendation
Reorder `AuthorizeRequest` so that `validateSecretOwnersMatchAuthorized` (and any other request-content validation) completes and passes *before* `replayGuard.CheckAndRecord` mutates state. Concretely, split the replay guard into a non-mutating `Check` (used before final validation, or used first, then a mutating `Record` invoked only after all checks — including owner-binding — have passed successfully.

## Proof of Concept
1. Attacker self-registers (via `WorkflowRegistry`) an allowlist entry under their own address `0xAttacker` for a digest computed over a request `{method: vault.secrets.create, id: X, params: {owner: 0xVictim, ...}}`.
2. Attacker submits that exact request body (unauthenticated `Auth` field, using the allowlist path) to the gateway/node.
3. `authorizer.AuthorizeRequest` → `authorizeAllowListBasedAuth` succeeds (digest found on-chain, authorized owner = `0xAttacker`) → `replayGuard.CheckAndRecord(digest, expiresAt)` records the digest → `validateSecretOwnersMatchAuthorized` fails because params' owner is `0xVictim` ≠ `0xAttacker`; overall call returns an owner-binding error.
4. `0xVictim` later submits the identical legitimate request (correctly authorized as themselves); `CheckAndRecord` finds the digest already present and returns `ErrRequestAlreadySeen`, denying the victim's real request.
5. A Go unit test extending `authorizer_test.go` that calls `AuthorizeRequest` twice with the same digest/mismatched-owner request first, then a matching correctly-owned request second (using the real `RequestReplayGuard`, not just mocks), would demonstrate the second (legitimate) call incorrectly failing with `ErrRequestAlreadySeen`.

```go
func (a *authorizer) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	authResult, err := a.authorizeRequest(ctx, req)
	if err != nil {
		return nil, err
	}
	if authResult == nil {
		err = errors.New("auth mechanism returned nil auth result")
		a.lggr.Errorw("auth mechanism returned nil auth result", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "")
		return nil, err
	}
	if err := a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt()); err != nil {
		a.lggr.Debugw("replay guard rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "", "error", err)
		return nil, err
	}
	if ownerErr := validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner()); ownerErr != nil {
		a.lggr.Errorw("owner binding rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "hasAuth", req.Auth != "", "error", ownerErr)
		return nil, ownerErr
	}
	a.lggr.Debugw("request authorized", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "")
	return authResult, nil
```

```go
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
```
