### Title
XRPL X-address bypasses `compareAddresses` same-token-address guard, allowing withdrawal to the token's own account — (File: `packages/intents-sdk/src/lib/compareAddresses.ts`, `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`validateAddress` for XRPL accepts both the classic `r...` address form and the X-address form (`isValidXAddress`), which are two different textual encodings of the same underlying `(Account, DestinationTag)` pair. `compareAddresses` for XRPL only does a raw string comparison (`a === b`), without decoding either form, so if a user supplies the token's `origin_chain_address` encoded as an X-address, the same-address guard in `PoaBridge.validateWithdrawal` is bypassed even though the destination resolves to the exact same XRPL account as the token contract.

### Finding Description
The claimed invariant is: for every accepted destination `d` and token address `t` on XRPL, if `d` and `t` denote the same account, then `compareAddresses(t, d, 'xrpl:0')` must be `true`.

- `validateAddress` (`packages/intents-sdk/src/lib/validateAddress.ts:333-335`) accepts an address if `xrp_isValidClassicAddress(address) || xrp_isValidXAddress(address)` — both classic (`r...`) and X-address forms are valid formats.
- `compareAddresses` (`packages/intents-sdk/src/lib/compareAddresses.ts:48-60`) for `Chains.XRPL` (and Near/Bitcoin/Doge/etc.) simply does `return a === b;` — no canonicalization/decoding is performed for XRPL, unlike EVM (`getAddress`), TON (`tryParseTonAddress`), or Tron (base58/hex decode to a common payload).
- `PoaBridge.validateWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:207-219`) calls `compareAddresses(tokenInfo.origin_chain_address, args.destinationAddress, assetInfo.blockchain)` and throws `DestinationAddressMatchesTokenAddressError` only if it returns `true`.

Exploit flow: the attacker takes the known `origin_chain_address` (a classic `r...` address) for an XRPL-based token (e.g. an IOU token whose issuer/hot-wallet address is the token contract account) and re-encodes that exact same classic account (with an arbitrary destination tag) into the X-address format defined by `ripple-address-codec`. This string:
1. Passes `validateAddress` because `xrp_isValidXAddress` returns `true` for a well-formed X-address.
2. Fails the identity check in `compareAddresses` because the raw string differs from the stored classic `origin_chain_address`, even though it decodes to the identical account.
3. `DestinationAddressMatchesTokenAddressError` is therefore never thrown, and `validateWithdrawal` proceeds; a withdrawal intent is created sending tokens to what is, on the XRPL ledger, the token's own account (the funds become unrecoverable, matching the classic "block transfer to token's own address" bypass the code comment on `compareAddresses` explicitly says it exists to prevent).

The question's premise about `compareAddresses` "throwing internally" is not the actual mechanism here — XRPL's branch (`a === b`) can never throw, so that specific framing is inaccurate. The real, reachable divergence is the missing canonicalization between classic and X-address encodings of the same XRPL account, which produces exactly the outcome the question describes (guard bypassed, funds sent to the token's own address).

### Impact Explanation
An unprivileged user, acting as their own withdrawal requester, can craft a `destinationAddress` (a re-encoded X-address of the token's own on-chain account) that passes `validateAddress` and evades `compareAddresses`'s "destination equals token address" check in `PoaBridge.validateWithdrawal`. This results in a withdrawal intent whose `IntentPrimitive` sends real amount to the token contract's own account, which is unrecoverable — the funds move but do not reach the user or any usable wallet. This is a direct instance of "funds delivered to a wrong address/chain/contract with no recovery," matching the Critical impact category. It is trivially repeatable per withdrawal call and costs the attacker only their own funds (self-inflicted, but also usable against any counterparty/integrator that forwards attacker-controlled destination strings into `createWithdrawalIntents`/`processWithdrawal`).

### Likelihood Explanation
Preconditions: the target must be an XRPL-based POA-bridge asset with a known `origin_chain_address` (obtainable via the public `getSupportedTokens` API), and the attacker needs only to run the well-documented `ripple-address-codec` X-address encoder against that classic address with any destination tag — a trivial, low-cost, fully client-side operation requiring no special access. Since `PoaBridge.validateWithdrawal` is called directly from `IntentsSDK.processWithdrawal`/`createWithdrawalIntents` for any withdrawal request, this is reachable by any unprivileged caller of the public SDK.

### Recommendation
In `compareAddresses.ts`, add an XRPL-specific canonicalization step (analogous to `compareTonAddress`/`compareTronAddress`) that decodes both classic and X-address forms to a normalized `(classicAddress, tag)` pair using `ripple-address-codec`'s `xAddressToClassicAddress`/`classicAddressToXAddress` before comparing, instead of relying on raw string equality for `Chains.XRPL`.

### Proof of Concept
```ts
// packages/intents-sdk/src/lib/compareAddresses.xrpl-xaddress.test.ts
import { describe, it, expect } from "vitest";
import { classicAddressToXAddress } from "ripple-address-codec";
import { compareAddresses } from "./compareAddresses";
import { validateAddress } from "./validateAddress";
import { Chains } from "./caip2";

describe("XRPL address canonicalization bypass", () => {
  const tokenAddress = "rTokenIssuerAddressXXXXXXXXXXXXXXXX"; // token's origin_chain_address (classic form)

  it("accepts an X-address encoding of the same account as a valid destination", () => {
    const xAddress = classicAddressToXAddress(tokenAddress, 12345, false);
    expect(validateAddress(xAddress, Chains.XRPL)).toBe(true);
  });

  it("BROKEN: compareAddresses fails to recognize the X-address as the same account", () => {
    const xAddress = classicAddressToXAddress(tokenAddress, 12345, false);
    // Both denote the identical XRPL account -> should be true, but returns false.
    expect(compareAddresses(tokenAddress, xAddress, "xrpl:0")).toBe(false);
  });
});
```
