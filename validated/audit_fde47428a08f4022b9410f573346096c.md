### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross‑tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates an incoming webhook solely by validating the HMAC over the raw request body, while the `shop` attribute that is handed to the app's webhook handler is read from the `x-shopify-shop-domain` / `shopify-shop-domain` header, a header that is never included in the signed payload.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` is invoked in `ShopifyAPI::Webhooks::Registry.process` to authenticate a webhook request: [1](#0-0) 

The HMAC is verified against `Request#to_signable_string`, which is defined as just the raw body — nothing else: [2](#0-1) 

However, the `shop` value that gets passed downstream to the application's handler is read straight from the `x-shopify-shop-domain` (or `shopify-shop-domain`) header, which is completely outside the HMAC-covered surface: [3](#0-2) [4](#0-3) 

`Registry.process` trusts this unauthenticated header value and forwards it as the tenant identity to the handler without any additional binding check: [1](#0-0) 

The identity binding that should hold is:
```
shop_used_by_handler == shop_that_the_HMAC_actually_authenticates
```
But because the signable string is `raw_body` alone, the equality that actually holds is:
```
HMAC_valid  ⇐⇒  body_bytes_unmodified
```
with `shop` completely free for an attacker to set to any value, as long as they can supply *some* `(raw_body, hmac)` pair that is valid under the app's shared `api_secret_key`.

Critically, Shopify signs webhooks using the **app's single shared `client_secret`**, not a per-shop secret. This means any legitimate webhook delivery an attacker receives for their *own* store (they only need to install the app on a store they control to receive genuine, correctly-signed webhooks) yields a `(raw_body, hmac)` pair that remains valid under `HmacValidator.validate` regardless of what `x-shopify-shop-domain` header is attached to the replayed request. An attacker can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `Registry.process` will pass HMAC validation and hand the handler `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
If the consuming application uses `data.shop` (as demonstrated in the gem's own tests/handlers) to select which tenant's session/data store to write the webhook body into, an attacker can inject arbitrary attacker-controlled payload content into another merchant's tenant data path — i.e., cross-tenant data injection/access using only the HMAC-authenticated envelope of their own store's webhook. This satisfies the Critical "cross-tenant access" impact category: the library itself fails to bind the authenticated field (`shop`) to the HMAC-verified bytes, so any host application relying on the documented `WebhookMetadata#shop` for tenant routing inherits the cross-tenant vulnerability.

### Likelihood Explanation
Likelihood is high for any unprivileged internet user who can install the target app on a store they control (a normal, permitted action for any Shopify merchant/developer): they legitimately receive real webhook deliveries with valid `(body, hmac)` pairs, then simply replay the same body/HMAC to the target app's public webhook endpoint with a forged `shop-domain` header. No access to `api_secret_key`, tokens, or privileged accounts is required.

### Recommendation
Bind the shop identity into the signature verification surface, e.g.:
- Include the `x-shopify-shop-domain` header value in `to_signable_string` so the HMAC covers both body and shop, or
- Cross-check `request.shop` against a shop already known/authorized for the currently registered webhook subscription (e.g., compare against the session/shop that the app registered the webhook for) before dispatching to the handler.
- At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must not be used alone to select tenant context without additional verification (e.g., cross-referencing against the app's own installed-shop registry).

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the target app there.
# Shopify delivers a genuine, correctly signed webhook to the app's endpoint:
genuine_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => "<valid HMAC computed by Shopify over raw_body using the app's client_secret>",
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
}
raw_body = '{"id":1,"malicious_field":"payload"}'

# Attacker captures (raw_body, hmac) and replays it, only swapping the shop-domain header:
forged_headers = genuine_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HMAC validation still succeeds because to_signable_string only covers raw_body:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

ShopifyAPI::Webhooks::Registry.process(request)
# Handler receives WebhookMetadata with shop: "victim-shop.myshopify.com"
# even though the payload was never sent by Shopify for that shop.
```

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
