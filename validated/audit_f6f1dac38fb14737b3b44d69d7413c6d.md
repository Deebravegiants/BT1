### Title
Fee-on-transfer / rebasing underlying tokens allow unbacked minting via `WrappedHyperFungibleToken.send()` - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` caches the caller-supplied `params.amount` and dispatches it verbatim in the cross-chain `Message`, without verifying how many underlying tokens the contract actually received via `safeTransferFrom`. For fee-on-transfer or rebasing ERC20 underlyings, the contract locks less than `params.amount` but the destination `HyperFungibleToken` mints (or the peer `WrappedHyperFungibleToken` unlocks) the full, unreduced `params.amount` to the beneficiary.

### Finding Description
In `send()`:
```solidity
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
...
DispatchPost memory request = _buildDispatchPost(params); // encodes params.amount, not actual balance delta
``` [1](#0-0) 

`_buildDispatchPost` embeds `params.amount` directly into the `HyperFungibleToken.Message.amount` field that is committed and relayed cross-chain: [2](#0-1) 

There is no balance-before/after check (unlike `IntentGatewayV2.placeOrder`, which explicitly measures `IERC20(token).balanceOf(address(this))` before and after `safeTransferFrom` to compute the actual received amount for exactly this reason): [3](#0-2) 

On the destination side, `onAccept` mints the full `message.amount` to the beneficiary (in `HyperFungibleToken`) or unlocks the full `message.amount` from the peer's underlying custody (in another `WrappedHyperFungibleToken`): [4](#0-3) [5](#0-4) 

The identical unguarded pattern also exists in `WrappedHyperFungibleTokenUpgradeable.sol`: [6](#0-5) 

### Impact Explanation
If the configured `underlying` token charges a transfer fee or is a rebasing token that can decrease balances, the wrapper locks strictly less than `params.amount` while the destination side mints or releases the full `params.amount`. For the burn/mint `HyperFungibleToken` side this is a direct unbacked mint — value is created out of thin air on every cross-chain send, redeemable back to the canonical underlying, silently draining the locked reserve on the home chain over time (or immediately for a single large send relative to reserve). This is a concrete path to insolvency/theft of the locked underlying token pool, reachable by any user calling `send()` with a single transaction and no privileged role required.

### Likelihood Explanation
Likelihood is contingent on the deployer configuring `_underlying` to a fee-on-transfer or rebasing token, which the docs explicitly claim to support generically for "existing ERC20 tokens" — there is no on-chain allow-list restricting `_underlying` to fee-free, non-rebasing tokens, and `configure()` sets `_underlying` without any validation: [7](#0-6) 
Any user holding such a token can trigger the discrepancy with a normal `send()` call.

### Recommendation
Mirror the fix already applied in `IntentGatewayV2.placeOrder`: measure `IERC20(_underlying).balanceOf(address(this))` before and after the `safeTransferFrom` in `send()`, use the actual received delta as the `amount` encoded in the dispatched `Message`, and emit the amount actually locked in the `Sent` event. Apply the same fix to `WrappedHyperFungibleTokenUpgradeable.send()`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` with `_underlying` set to a fee-on-transfer token (e.g., 1% fee, as modeled in `FeeOnTransferToken` test helper used elsewhere in the repo).
2. Approve and call `send({amount: 1000e18, ...})`. `safeTransferFrom` moves only 990e18 into the contract (`balanceOf(this)` increases by 990e18) due to the fee, but `message.amount = 1000e18` is what gets dispatched.
3. On the destination `HyperFungibleToken`, `onAccept` executes `_mint(beneficiary, 1000e18)` — 1000e18 minted against only 990e18 actually locked, an unbacked 10e18 mint per transaction.
4. Repeating this (or reversing direction) progressively drains the locked underlying reserve relative to circulating minted supply, eventually leaving legitimate holders unable to redeem 1:1.

    function _buildDispatchPost(HyperFungibleToken.SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(HyperFungibleToken.Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
