### Title
Webhook shop-domain header not covered by HMAC allows cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0)  and `Utils::HmacValidator.validate` computes/compares the HMAC solely against that signable string [2](#0-1) . The `shop` identity used downstream to attribute the webhook to a tenant is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header [3](#0-2) , which is never included in the HMAC-signed bytes.

### Finding Description
`Registry.process` validates the webhook exclusively via `Utils::HmacValidator.validate(request)` [4](#0-3) , then builds `WebhookMetadata` using `request.shop`, i.e., the header value, and passes it to the app-registered handler [5](#0-4) . The equality this binding is supposed to enforce is:

`shop_bound_by_hmac == shop_acted_on_by_handler`

but in reality:

`shop_bound_by_hmac = ∅ (only raw_body is signed)` ≠ `shop_acted_on_by_handler = header["shopify-shop-domain"]`

Because the HMAC is computed with the app's single, shared `client_secret` across every shop that installs the app, any merchant who legitimately installs the app receives genuinely-signed webhooks for their own shop (valid body + valid HMAC + header `shop-domain = attacker-shop`). Since the header is not part of the signed bytes, that attacker can replay the exact same `raw_body`/HMAC pair to the app's webhook endpoint while substituting `shopify-shop-domain: victim-shop.myshopify.com`. `HmacValidator.validate` will still succeed (it only checks the body against the shared secret) [6](#0-5) , and `Registry.process` will invoke the handler with `shop: "victim-shop.myshopify.com"` [5](#0-4) , i.e., attacker-controlled body content gets attributed to a tenant the attacker does not control.

This is the same class of defect as the reported Yearn `underlying`/`token` mismatch: an identifier that downstream logic trusts and acts on (`shop`) is not the identifier actually covered by the cryptographic check (`raw_body` only).

### Impact Explanation
Any host application that keys per-tenant state (session lookup, order/customer records, inventory, billing, etc.) off `WebhookMetadata#shop` is exposed to cross-tenant data injection: an unprivileged internet user who is merely a merchant/installer of the target app can forge webhook events "as" any other shop that has installed the same app, without possessing the app's `client_secret`, an access token, or any victim credentials. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires only that the attacker install the target app on any shop they control (a normal, unprivileged onboarding flow) and replay a legitimately received webhook with a modified `shop-domain` header — no secrets, tokens, or privileged access are needed, making this readily reachable by an unprivileged internet user.

### Recommendation
Bind the shop identity into the value that is cryptographically verified: include the `shop-domain` header (and any other header this gem relies on, e.g. `topic`) in `Request#to_signable_string`, or otherwise require the host application to independently verify that `request.shop` corresponds to a shop with an active, previously-established session/installation before trusting it, rather than trusting the raw header as-is.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook: body `B`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, header `x-shopify-hmac-sha256: HMAC(secret, B)`.
3. Attacker replays this exact `B` and HMAC to the app's webhook endpoint but changes the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` computes `HMAC(secret, B)` from `to_signable_string` (which equals `B` only) [1](#0-0)  and it matches the supplied HMAC, so validation passes [2](#0-1) .
5. `Registry.process` dispatches to the handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body `B` [5](#0-4) , causing the host app to process forged data under the victim tenant's identity.
