## Title
Webhook shop identity spoofing via unsigned `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC‑validating the raw request body, while the `shop` value that is handed to the application's webhook handler is read from an HTTP header that is **not** covered by that HMAC. Any party able to produce one genuinely-signed webhook body (e.g. by installing the app on their own store and triggering an event) can replay that body/HMAC pair while substituting an arbitrary `shopify-shop-domain` header, causing the handler to process the payload as if it came from a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

but `shop` is read independently from a request header that plays no part in the signed content: [2](#0-1) 

`Registry.process` validates the HMAC over that signable string only, then immediately trusts `request.shop` (and `request.topic`) as the tenant identity passed to the registered handler: [3](#0-2) 

The equality this code implicitly relies on is:
`hmac_valid(raw_body) == true` **implies** `shop-domain header == shop that produced raw_body`

That implication does not hold. The app's `api_secret_key` (client secret) is shared across every shop that has installed the app — it is not per-tenant. Consequently:

1. An attacker installs the app on their own shop (a normal, unprivileged onboarding action) and triggers any webhook topic they control (e.g. `orders/create` by placing an order in their own store, or `app/uninstalled`). Shopify delivers a webhook to the app with a body and a valid `x-shopify-hmac-sha256` computed with the shared client secret.
2. The attacker captures that `(raw_body, hmac)` pair.
3. The attacker replays the same body and HMAC directly to the app's webhook endpoint, but sets `x-shopify-shop-domain` (or `shopify-shop-domain`) to an arbitrary victim shop domain.
4. `Utils::HmacValidator.validate` succeeds because it only checks the HMAC of `raw_body`, which is unchanged and still valid for the shared secret.
5. `WebhookMetadata.new(shop: request.shop, ...)` is built with the attacker-chosen victim shop domain, and the app's handler executes business logic (data mutation, uninstall cleanup, billing changes, etc.) believing the event originated from the victim shop.

This is the same defect class as the report’s "check that doesn't cover what it should": the check (HMAC) authenticates the wrong scope of data (only the body), while a separate, security-relevant field (the shop identity used for tenant binding) is trusted without being included in that check.

### Impact Explanation
This breaks the tenant binding `shop-domain used for dispatch == shop that authored the signed content`, letting one unprivileged, self-onboarded attacker forge webhook events attributed to any other shop that has installed the same app. Depending on what the host application does in its webhook handlers (common patterns: deleting shop data on `app/uninstalled`, updating billing/plan state, writing customer/order data keyed by `shop`), this enables cross-tenant data corruption or state manipulation — a cross-tenant access impact.

### Likelihood Explanation
Exploitation only requires the attacker to be able to install the target app on a shop they control (a standard, low-privilege action available to any Shopify merchant/developer) and to capture one legitimately delivered webhook. No access to the app's `api_secret_key`, no interception of another tenant's traffic, and no social engineering is required.

### Recommendation
Bind the shop identity into the authenticated request. Where the underlying JSON body already contains identifying fields (most Shopify webhook payloads include the shop's `id`/domain in some webhooks, or apps can maintain a mapping of registered shop → webhook secret is not available since secret is shared), a more robust fix is to require applications to cross-check `request.shop` against a known set of shops that have completed OAuth for this app (i.e., only accept webhooks for shops with a stored/active session), and document this requirement clearly, since the library's HMAC check alone cannot bind the shop header. Alternatively, incorporate a shop-scoped secret rather than a single app-wide `api_secret_key` for webhook validation if Shopify's API begins to support per-shop signing.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), receiving:
   - `raw_body = '{"id": 1, ...}'`
   - `x-shopify-hmac-sha256 = HMAC(raw_body, app_client_secret)` (valid, since attacker's own store is legitimately subscribed)
2. Attacker sends a POST to the app's webhook endpoint with the same `raw_body` and `hmac` header, but:
   - `x-shopify-topic: orders/create`
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `raw_body`: [4](#0-3) 
4. The handler executes with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)`, acting on the victim shop's tenant context using attacker-supplied data.
