## Finding

### Title
Unbounded, Unauthenticated JSON-RPC Memory Amplification via Unthrottled Body Parsing - (File: `chain/jsonrpc/src/lib.rs`)

### Summary
Like the reported issue, nearcore's public JSON-RPC HTTP endpoint fully deserializes every request body into `serde_json::Value`-backed structures before any per-method or per-caller throttling is applied, and the server has **no per-IP rate limiting and no global concurrency/parsing semaphore** at all in the RPC layer — a gap that is broader than in the referenced report (which at least rate-limited 2 of ~25 methods and had a global 1,000-request semaphore).

### Finding Description
The Axum route for the primary RPC endpoint is: [1](#0-0) 

`rpc_handler` uses the `Json<Message>` extractor, which fully parses the request body with `serde_json` into the `Message` enum (`Request`, `Batch(Vec<Message>)`, etc.) before `JsonRpcHandler::process()` is ever invoked, i.e., before any method dispatch, validation, or throttling: [2](#0-1) 

Each parsed `Request` also carries an untyped `params: Value` field, which is later deserialized a second time by `RpcRequest::parse()` in `process_method_call()`: [3](#0-2) [4](#0-3) 

The only middleware applied to the router is CORS and a request body size cap (`RequestBodyLimitLayer`) — there is no rate limiter, no per-IP throttle, and no concurrency-limiting semaphore anywhere in the `chain/jsonrpc` stack (confirmed by searching for `Semaphore`/`rate_limit`/`ConcurrencyLimit` constructs, none of which exist in this crate): [5](#0-4) 

Additionally, `Message::Batch(Vec<Message>)` allows an attacker to submit many sub-requests in a single body (bounded only by the overall body size limit), and each sub-message undergoes the same `serde_json::Value` allocation amplification (heap Strings, `Vec<Value>` with boxed enum elements, `HashMap<String, Value>` for objects) described in the report: [6](#0-5) 

Because parsing (both the `Json<Message>` extraction and the later `RpcRequest::parse()`/`serde_json::from_value` step) happens for every accepted TCP connection with no concurrency ceiling and no per-source throttling, an attacker can open many concurrent connections, each sending a body up to `json_payload_max_size`, and force the node to perform full JSON-to-`Value` tree materialization (and for batches, a `Vec<Message>` of such trees) simultaneously across all connections before any request-level backpressure (actor thread pools, tx pool checks, etc.) comes into play.

### Impact Explanation
This is a resource-exhaustion / denial-of-service vector reachable by any unprivileged network client submitting ordinary RPC requests — no validator, P2P, or privileged access is required. Sustained concurrent large/batched payloads can amplify in-memory usage well beyond the wire size of the requests, exhausting node memory and potentially crashing or stalling the RPC-serving process, which affects the availability of the query/`send_tx` path used by wallets, indexers, and users submitting transactions.

### Likelihood Explanation
The attack requires no special privileges: any client can send HTTP POST requests to `/`. The only mitigating control is the body-size limit configured via `json_payload_max_size` (default value not confirmed in this investigation — it is referenced in `RpcConfig`/`limits_config` but its exact default constant was not located within the available tool budget). There is no per-IP or global concurrency control in `chain/jsonrpc`, so parallelizing many connections (each within the body-size limit, and optionally batched) is straightforward and does not require bypassing any application-level protection, since none exists at this layer.

### Recommendation
- Add a global concurrency/semaphore limit on simultaneous JSON body parsing in `create_jsonrpc_app()` (e.g., a `tower` concurrency-limit layer) before the `Json<Message>` extractor runs.
- Add per-IP request-rate limiting (e.g., a `tower-governor`-style layer) ahead of body parsing for the `/` route.
- Consider capping the number of elements allowed in `Message::Batch` independent of the raw body size, since batch elements amplify memory disproportionately to their serialized size.
- Confirm and, if necessary, tighten the default `json_payload_max_size` in `RpcConfig`/`limits_config`, and document the recommended value for public-facing nodes.

### Proof of Concept
Conceptual reproduction (not executed against a live node):
1. Configure a `neard` node with the default/public `RpcConfig` (`chain/jsonrpc/src/lib.rs`), which enables `/` with only `RequestBodyLimitLayer` and CORS, and no rate limiting.
2. From many concurrent client connections (single or multiple source IPs — no per-IP check exists), send POST requests to `/` with a JSON-RPC batch body (`Message::Batch`) containing many sub-requests, each with a large/deeply nested `params` value, sized up to just under `json_payload_max_size`.
3. Because each connection's body is fully parsed into `serde_json::Value` trees (`Json<Message>` extractor, then a second `serde_json::from_value` per sub-request in `process_method_call`) with no global semaphore or per-IP throttle gating this work, the aggregate in-memory footprint across concurrent connections can substantially exceed the aggregate wire size of the requests, driving up node memory usage as concurrency increases.

**Note on completeness:** I was not able to confirm the exact default value of `json_payload_max_size` within the available search budget, nor whether any external reverse proxy or infrastructure-level rate limiting is assumed for production deployments outside this repository — those would need to be checked in a live/production configuration if further validation is required.

    /// A response to a Request.
    Response(Response),
    /// A notification.
    Notification(Notification),
    /// A batch of more requests or responses.

    /// The protocol allows bundling multiple requests, notifications or responses to a single

    /// This variant has no direct constructor and is expected to be constructed manually.
    Batch(Vec<Message>),
    /// An unmatched sub entry in a `Batch`.

    #[serde(skip_serializing)]

}
