### Title
Webhook shop-domain and topic headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from only the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and attribute the webhook are read directly from HTTP headers that are never included in the signed payload.

### Finding Description
`Webhooks::Registry.process` treats a request as authentic if `Utils::HmacValidator.validate(request)` succeeds: [1](#0-0) 

`HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [3](#0-2) 

But `shop`, `topic`, `webhook_id`, and `api_version` — the identity/tenant fields the host app relies on — are all pulled straight from unauthenticated HTTP headers: [4](#0-3) 

These header-derived values are then handed to the app's handler as trusted tenant identity, without ever being covered by the signature check: [5](#0-4) 

This is the same class of bug as the reported issue: a signature check (`check_signer`/`HmacValidator`) verifies one narrow set of bytes (the raw body / the `signer` account), while a separate identity field that the caller actually relies on (`shop-domain` header / `wallet_address` owner) is left completely unchecked. The equality that should hold — `verified_bytes == identity_used_downstream` — is broken: `HMAC(raw_body) == valid` says nothing about `shop-domain header == the shop that produced raw_body`.

### Impact Explanation
Any party capable of obtaining one genuine, HMAC-valid webhook body (e.g., by installing the app on their own store and triggering a webhook, which Shopify apps can freely do) can replay that exact body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for an arbitrary victim shop domain. Because the signature only certifies the body bytes, the HMAC check still passes, and `Registry.process` will hand the handler a `WebhookMetadata` object whose `shop` is the attacker-chosen victim domain. Any host application that uses `data.shop` to select which tenant's records to create, update, or delete (the intended and documented use of `WebhookMetadata#shop`) can be tricked into writing attacker-controlled data into another merchant's tenant scope — a cross-tenant integrity/confidentiality violation.

### Likelihood Explanation
The gem's own webhook processing exposes this gap unconditionally: no code path in `Request` or `Registry` ties the authenticated bytes to the header-derived shop/topic. Any unprivileged actor who can install the app on a store they control (a normal, unprivileged action within the Shopify app ecosystem) can generate a valid HMAC for a body of their choosing and then freely forge the shop-domain/topic headers, without needing `api_secret_key`, an access token, or any elevated privilege.

### Recommendation
Include the trusted identity fields (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed payload, or otherwise cryptographically bind them to the raw body before trusting them downstream, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop`, `state`, `host`, etc., into the signed string. At minimum, `Webhooks::Request#to_signable_string` should not allow header values used for tenant routing to be excluded from what `HmacValidator` verifies.

### Proof of Concept
1. Attacker installs the target app on their own development store (`attacker.myshopify.com`) and triggers any webhook, obtaining `raw_body` and its valid `hmac-sha256` signature computed with the app's shared secret.
2. Attacker resends the identical `raw_body` and `hmac-sha256` header to the app's webhook endpoint, but changes the `X-Shopify-Shop-Domain` header to `victim.myshopify.com` (and optionally the topic header).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC — validation succeeds. [6](#0-5) 
4. The registered handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"`, and any host logic keyed on that field now operates as if the data came from the victim tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          received_signature = verifiable_query.hmac

        end
