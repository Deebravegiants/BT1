### Title
Missing slippage protection in `bonding_curve_launchpad::swap` custody-transfers real APT and FA at a fully manipulable price - (File: aptos-move/move-examples/bonding_curve_launchpad/sources/bonding_curve_launchpad.move)

### Summary
The `swap` entry function in `bonding_curve_launchpad.move`, and the underlying `swap_fa_to_apt`/`swap_apt_to_fa` functions in `liquidity_pairs.move`, execute real custody transfers of APT and fungible-asset value using an on-chain, single-transaction constant-product price with **no `min_amount_out` parameter at all**. This is the same missing-slippage-check bug class as the `FRouter.sell`/`buy` finding, but here it is a true custody defect: the module holds user FA and APT in an object-owned `FungibleStore`/account, and the amount transferred out is computed and immediately paid via `aptos_account::transfer` and `fungible_asset::transfer_with_ref` inside the same function that mutates the reserves, with zero minimum-output guarantee for the caller.

### Finding Description
`bonding_curve_launchpad::swap` (lines 164-184) is a public entry function that only validates `amount_in > 0`: [1](#0-0) 

It forwards directly into `liquidity_pairs::swap_fa_to_apt` / `swap_apt_to_fa`, which compute `amount_out` from the live reserves via `get_amount_out` and immediately execute the transfer with no comparison against any caller-supplied minimum: [2](#0-1) [3](#0-2) 

Compare this to the companion `swap::router` module (used later for the graduated/external DEX), which *does* implement the recommended fix pattern — an explicit `amount_out_min` parameter checked with `assert!(fungible_asset::amount(&out) >= amount_out_min, EINSUFFICIENT_OUTPUT_AMOUNT)`: [4](#0-3) 

The `bonding_curve_launchpad`/`liquidity_pairs` bonding-curve swap path — which is the pre-graduation, most price-sensitive phase (thin reserves, virtual liquidity `INITIAL_VIRTUAL_APT_LIQUIDITY`) — has no equivalent protection anywhere in the call chain. Because the FA store and reserves are held custody-style inside the `LiquidityPair` object (`fa_store: Object<FungibleStore>`, `apt_reserves`, `fa_reserves`) and the pair signer moves real APT via `aptos_account::transfer` and real FA via `fungible_asset::transfer_with_ref` in the same call: [5](#0-4) 

any attacker who can observe a pending `swap` transaction in the mempool (or simply batch their own large swap immediately before a victim's transaction in the same block/checkpoint) can shift `fa_reserves`/`apt_reserves` to force the victim's `get_amount_out` computation to return an arbitrarily small `amount_out`, which is then unconditionally paid out — there is no on-chain mechanism for the victim to reject an unfavorable execution price.

### Impact Explanation
This directly corrupts custody value transferred out of the object-held `fa_store`/APT reserves to the wrong (attacker-favorable) amount: the victim's asset (APT or FA) is withdrawn from their account at the pre-trade price but the value received back is determined post-manipulation, with the delta captured by whoever manipulated reserves immediately before. Because `graduate()` triggers automatically once `apt_updated_reserves > APT_LIQUIDITY_THRESHOLD`, reserve manipulation on this path can also affect graduation timing/liquidity migrated to the external DEX pool. This meets the "theft… of APT, fungible assets… held value" and "supply or custody accounting corruption that moves value to the wrong holder" custody-impact criteria, since it is unprivileged (any signer calling the public entry `swap`), affects a live custody path holding user deposits and virtual/real APT reserves, and has no admin/governance precondition.

### Likelihood Explanation
High likelihood: `swap` is a public entry function callable by anyone with no minimum-out guard, the bonding-curve reserves are shallow by design (using virtual liquidity specifically to make early trades sensitive to size), and sandwich/front-running of a visible mempool transaction against an AMM-style constant-product formula is a well-established, cheap, and repeatable attack requiring no special privilege — only the ability to submit two transactions around the victim's.

### Recommendation
Add a `min_amount_out: u64` parameter to `bonding_curve_launchpad::swap` and thread it through to `liquidity_pairs::swap_fa_to_apt`/`swap_apt_to_fa`. After computing `apt_gained`/`fa_gained` via `get_amount_out`, assert `apt_gained >= min_amount_out` (or `fa_gained >= min_amount_out`) before executing `aptos_account::transfer` / `fungible_asset::transfer_with_ref`, mirroring the pattern already implemented in `swap::router::swap` (`EINSUFFICIENT_OUTPUT_AMOUNT` check).

### Proof of Concept
1. Creator launches an FA pair via `create_fa_pair`, establishing a `LiquidityPair` with virtual `apt_reserves = INITIAL_VIRTUAL_APT_LIQUIDITY` and some `fa_reserves`.
2. Victim submits `bonding_curve_launchpad::swap(account, name, symbol, /*swap_to_apt=*/false, amount_in = X)` expecting `fa_gained ≈ get_amount_out(...)` at current reserves.
3. Attacker observes the pending transaction and submits their own large `swap(..., swap_to_apt=false, amount_in = Y)` immediately before it (front-run), shifting `apt_reserves`/`fa_reserves` unfavorably for the victim.
4. Victim's transaction executes against the now-worse reserves; `swap_apt_to_fa` computes and pays out a much smaller `fa_gained` than the victim expected, with no `assert!` to reject the trade — this is confirmed by the absence of any minimum-output check in `liquidity_pairs.move` lines 269-325, in contrast to the guarded `swap::router::swap` at lines 81-92.
5. Attacker can then reverse their position (sandwich) to realize the extracted value, all executed unprivileged through the public `swap` entry function.

            liquidity_pairs::swap_apt_to_fa(name, symbol, transfer_ref, account, fa_metadata_obj, amount_in);
        };

    /// Facilitate swapping between a given FA to APT.
    public(friend) fun swap_fa_to_apt(
        name: String,
        symbol: String,
        transfer_ref: &TransferRef,
        swapper_account: &signer,
        fa_object_metadata: Object<Metadata>,
        amount_in: u64
    ) acquires Pairs, LiquidityPair {
        // Verify the liquidity pair exists and is enabled for trading.
        assert_liquidity_pair_exists(name, symbol);
        let liquidity_pair = borrow_global_mut<LiquidityPair>(get_pair_obj_address(name, symbol));
        assert!(liquidity_pair.is_enabled, ELIQUIDITY_PAIR_DISABLED);
        // Determine the amount received of APT, when given swapper-supplied amount_in of FA.
        let (fa_given, apt_gained, fa_updated_reserves, apt_updated_reserves) = get_amount_out(
            liquidity_pair.fa_reserves,
            liquidity_pair.apt_reserves,
            true,
            amount_in
        );
        // Verify the swapper holds the FA.
        let swapper_address = signer::address_of(swapper_account);
        let does_primary_store_exist_for_swapper = primary_fungible_store::primary_store_exists(
            swapper_address,
            fa_object_metadata
        );
        assert!(does_primary_store_exist_for_swapper, EFA_PRIMARY_STORE_DOES_NOT_EXIST);
        // Perform the swap.
        // Swapper sends FA to the liquidity pair object. The liquidity pair object sends APT to the swapper, in return.
        let liquidity_pair_signer = object::generate_signer_for_extending(&liquidity_pair.extend_ref);
        let from_swapper_store = primary_fungible_store::ensure_primary_store_exists(
            swapper_address,
            fungible_asset::transfer_ref_metadata(transfer_ref)
        );
        fungible_asset::transfer_with_ref(transfer_ref, from_swapper_store, liquidity_pair.fa_store, fa_given);
        aptos_account::transfer(&liquidity_pair_signer, swapper_address, apt_gained);
        // Record state changes to the liquidity pair's reserves, and emit changes as events.
        let former_fa_reserves = liquidity_pair.fa_reserves;
        let former_apt_reserves = liquidity_pair.apt_reserves;
        liquidity_pair.fa_reserves = fa_updated_reserves;
        liquidity_pair.apt_reserves = apt_updated_reserves;
        event::emit(
            LiquidityPairReservesUpdated {
                former_fa_reserves,
                former_apt_reserves,
                new_fa_reserves: fa_updated_reserves,
                new_apt_reserves: apt_updated_reserves
            }
        );
        event::emit(
            LiquidityPairSwap {
                is_fa_else_apt: false,
                gained: (apt_gained as u128),
                swapper_address
            }
        );
    }

    /// Facilitate swapping between APT to a given FA.
    public(friend) fun swap_apt_to_fa(
        name: String,
        symbol: String,
        transfer_ref: &TransferRef,
        swapper_account: &signer,
        fa_object_metadata: Object<Metadata>,
        amount_in: u64
    ) acquires Pairs, LiquidityPair {
        // Verify the liquidity pair exists and is enabled for trading.
        assert_liquidity_pair_exists(name, symbol);
        let liquidity_pair = borrow_global_mut<LiquidityPair>(get_pair_obj_address(name, symbol));
        assert!(liquidity_pair.is_enabled, ELIQUIDITY_PAIR_DISABLED);
        // Determine the amount received of FA, when given swapper-supplied amount_in of APT.
        let (fa_gained, apt_given, fa_updated_reserves, apt_updated_reserves) = get_amount_out(
            liquidity_pair.fa_reserves,
            liquidity_pair.apt_reserves,
            false,
            amount_in
        );
        // Perform the swap.
        // Swapper sends APT to the liquidity pair object. The liquidity pair object sends FA to the swapper, in return.
        // Requires the liquidity pair object's address, which is retrieved using the stored extend_ref.
        let swapper_address = signer::address_of(swapper_account);
        let liquidity_pair_address = object::address_from_extend_ref(&liquidity_pair.extend_ref);
        let to_swapper_store = primary_fungible_store::ensure_primary_store_exists(
            swapper_address,
            fungible_asset::transfer_ref_metadata(transfer_ref)
        );
        aptos_account::transfer(swapper_account, liquidity_pair_address, apt_given);
        fungible_asset::transfer_with_ref(transfer_ref, liquidity_pair.fa_store, to_swapper_store, fa_gained);
        // Record state changes to the liquidity pair's reserves, and emit changes as events.
        let former_fa_reserves = liquidity_pair.fa_reserves;
        let former_apt_reserves = liquidity_pair.apt_reserves;
        liquidity_pair.fa_reserves = fa_updated_reserves;
        liquidity_pair.apt_reserves = apt_updated_reserves;
        event::emit(
            LiquidityPairReservesUpdated {
                former_fa_reserves,
                former_apt_reserves,
                new_fa_reserves: fa_updated_reserves,
                new_apt_reserves: apt_updated_reserves
            }
        );
        event::emit(
            LiquidityPairSwap {
                is_fa_else_apt: true,
                gained: (fa_gained as u128),
                swapper_address
            }
        );
        // Check for graduation requirements. The APT reserves must be above the pre-defined
        // threshold to allow for graduation.
        if (liquidity_pair.is_enabled && apt_updated_reserves > APT_LIQUIDITY_THRESHOLD) {
            graduate(liquidity_pair, fa_object_metadata, transfer_ref, apt_updated_reserves, fa_updated_reserves);
        }
    }
