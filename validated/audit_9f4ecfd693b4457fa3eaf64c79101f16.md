Audit Report

## Title
LDAP unauthenticated ("empty password") bind allows authentication bypass in `ldapAuthenticator.CreateSession` - (File: `core/sessions/ldapauth/ldap.go`)

## Summary
`ldapAuthenticator.CreateSession` calls `conn.Bind(searchBaseDN, sr.Password)` with the raw, client-supplied password and no check that it is non-empty. Per RFC 4513 §5.1.2, a simple bind with a non-empty DN and a zero-length password is defined as an "unauthenticated bind," which many LDAP server configurations treat as successful (`err == nil`) without verifying any credential, allowing an attacker who knows a valid user's email to obtain that user's role/session by submitting an empty password.

## Finding Description
The public, unauthenticated `POST /sessions` endpoint binds the request body directly into `sessions.SessionRequest` with no validation on `Password`: [1](#0-0)  and the struct itself carries no required/length constraint on `Password`: [2](#0-1) . This route is registered without authentication middleware: [3](#0-2) .

In `ldapAuthenticator.CreateSession`, the attacker-controlled `sr.Password` is passed straight to `conn.Bind`: [4](#0-3) . If the password is empty and the upstream LDAP server permits unauthenticated binds for that DN, `Bind` returns `nil` error, `returnErr` remains unset, and the code proceeds to call `FindUser` and issue a fully valid session with the target's real role: [5](#0-4) . The identical unguarded pattern exists in `TestPassword`, used for re-authentication flows: [6](#0-5) . By contrast, the local-auth path never has this exposure because it always requires a bcrypt hash comparison rather than delegating trust to a bind call: [7](#0-6) . No code path in `CreateSession`, `SessionRequest`, or `SessionsController.Create` rejects an empty password before it reaches `conn.Bind`, so the well-documented LDAP "unauthenticated bind" pitfall is not defended against at the application layer.

## Impact Explanation
If exploitable against the deployed LDAP server, this maps directly to an in-scope "node API authentication/role bypass" impact: an unprivileged network attacker who knows or guesses a valid LDAP-mapped user's email obtains a legitimate session with that user's role (potentially `admin`), which is gated to sensitive endpoints via `RequiresAdminRole`/`RequiresEditRole`: [8](#0-7) . This would constitute full node compromise if the targeted account has admin role.

## Likelihood Explanation
This is not purely a server-side/operator misconfiguration outside chainlink's control — while the actual success of the empty-password bind depends on the upstream LDAP server permitting unauthenticated binds, RFC 4513 defines this behavior as the default outcome for a non-empty DN + empty password simple bind, and OpenLDAP historically allows it unless `disallow bind_anon` (or similar) is explicitly configured. The chainlink application code itself performs no defensive check to short-circuit this before delegating trust to the LDAP server's bind result, which is the root cause and squarely within chainlink's code (`core/sessions/ldapauth/ldap.go`), not merely a deployment misconfiguration of chainlink infrastructure. The attack requires no credentials, no prior access, and only a valid email address, which is often predictable (e.g., corporate email conventions) or obtainable, making this readily repeatable against any environment where the LDAP server exhibits the RFC-default unauthenticated-bind behavior.

## Recommendation
Reject `SessionRequest.Password` (and the `password` parameter in `TestPassword`) whenever it is empty, returning an authentication failure immediately before calling `conn.Bind`, in both `core/sessions/ldapauth/ldap.go`'s `CreateSession` and `TestPassword` functions. This eliminates trust in the LDAP server's handling of RFC 4513 unauthenticated binds regardless of server configuration.

## Proof of Concept
1. Deploy a chainlink node with LDAP auth enabled, pointed at an LDAP server configured with default OpenLDAP behavior (unauthenticated binds not explicitly disallowed).
2. As an unauthenticated attacker, send:
```
POST /sessions
Content-Type: application/json

{"email":"admin@example.com","password":""}
```
3. In `ldapAuthenticator.CreateSession`, `conn.Bind(searchBaseDN, "")` succeeds (`err == nil`) because the server treats it as an unauthenticated bind.
4. `FindUser` resolves the role, and a full session is created and returned for `admin@example.com` without knowledge of the real password — verifiable via a Go unit test that mocks `LDAPConn.Bind` to return `nil` for an empty password argument and asserts `CreateSession` returns a valid session ID.

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}
