### Title
Unchecked ERC20 transfer return value in `IntentGatewayV2.withdraw` / SweepDust allows silent fund loss on non-standard tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2` (Tron variant) releases escrowed intent funds using a raw low-level `.call()` to the token's `transfer` selector, checking only that the *call* succeeded, not that the ERC20 `transfer` function actually returned `true`. This is the same bug class as the external report's `finalizeCrowdfund` unchecked-return-value issue: a boolean success indicator from an inner call is silently discarded, so callers (here, the escrow-release logic) proceed as if the transfer succeeded even when the token reports failure.

### Finding Description
The contract imports and declares `using SafeERC20 for IERC20` [1](#0-0) , and uses `safeTransferFrom`/`safeTransferFrom` correctly for escrow deposits (e.g. in `placeOrder`) [2](#0-1) . However, the escrow-release path (`withdraw`, called from both `onAccept` for `RedeemEscrow`/`RefundEscrow` and from `onGetResponse`) and the `SweepDust` handler instead perform raw calls:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [3](#0-2) 

and identically in the dust-sweep branch:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
``` [4](#0-3) 

`success` here only reflects whether the target contract executed without reverting — it says nothing about the ABI-encoded return data. Standard-conforming ERC20 tokens revert or return `true`, so this pattern happens to work for them, but for the well-known class of non-compliant tokens that return `false` on failure without reverting (some TRC20/ERC20 tokens on Tron, proxy tokens, or blacklist-style tokens that "fail silently"), `success` will still be `true` even though no tokens were actually moved. The escrow accounting is decremented regardless (`_orders[body.commitment][token] -= amount;`) and the order is marked `_filled[body.commitment] = beneficiary;`, permanently finalizing the withdrawal as if funds were delivered.

### Impact Explanation
If any of the whitelisted intent input/output tokens (governed via `params`/`NewDeployment`/protocol-fee token updates, which are cross-chain-configurable via Hyperbridge `UpdateParams`) is a non-standard token that returns `false` instead of reverting on transfer failure (e.g., due to insufficient balance edge cases, paused/blacklist logic, or other non-compliant behavior), a solver or beneficiary would have their withdrawal marked `_filled` / escrow decremented without receiving the tokens — a permanent loss of the escrowed funds with no recovery path, since `_filled` prevents re-processing and the GET-response cancellation flow checks `_filled` to block refunds. This is a fund-freezing/loss bug reachable by any relayer delivering a `RedeemEscrow`/`RefundEscrow`/`SweepDust` request or GET response, matching the required impact bar of "permanent freezing of funds."

### Likelihood Explanation
Likelihood depends on whether the deployed/whitelisted intent tokens include any non-compliant ERC20 (common on Tron, where TRC20 implementations vary and some do not strictly follow the "revert on failure" convention). Given the contract explicitly imports `SafeERC20` for other transfer paths, this suggests the raw-call pattern in `withdraw`/`SweepDust` was inconsistent rather than intentional, increasing the chance this is a real gap versus a deliberate design choice for TRX-specific opcodes.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw` and the `SweepDust` branch with `IERC20(token).safeTransfer(beneficiary, amount)` (already imported via `SafeERC20`), consistent with the deposit-side code. This ensures both call success and the ERC20 boolean return value (when present) are validated, and non-standard tokens with missing return data are also handled correctly by `SafeERC20`.

### Proof of Concept
1. Protocol admin (via Hyperbridge `NewDeployment`/config) whitelists a token `T` whose `transfer` implementation returns `false` on certain failure conditions instead of reverting (a known real-world ERC20/TRC20 pattern).
2. A solver escrows `T` for an order; later a `RedeemEscrow` request is delivered (or a `RefundEscrow`/timeout GET response fires) under conditions where `T.transfer` to the beneficiary returns `false` (e.g., beneficiary is blacklisted, or `T` has a transient pause).
3. `withdraw()` calls `token.call(...)`; the outer call itself does not revert (no revert inside `T.transfer`), so `success == true` even though `T`'s internal return value was `false` and no tokens moved.
4. `_orders[commitment][token] -= amount;` and `_filled[commitment] = beneficiary;` execute, permanently marking the order filled/refunded.
5. The beneficiary never receives token `T`; escrowed funds are stuck with no way to re-trigger withdrawal since `_filled` blocks reprocessing.
