### Title
Registering a new IntentGateway deployment for a state machine permanently freezes escrow for in-flight orders authenticated against the old instance - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`IntentsBase`/`ExtrinsicIntents` authenticates incoming `RedeemEscrow`/`RefundEscrow` settlement messages by comparing the message's `request.from` against the *currently registered* gateway instance for the source state machine, looked up live via `_instance()`. When Hyperbridge governance re-points `_instances[chain]` to a new gateway address (via `NewDeployment`) — a routine, non-malicious redeployment/migration action, exactly analogous to updating the collateral address in the original Perennial report — any order that was escrowed and filled against the *old* instance but whose settlement message has not yet been delivered becomes permanently unauthenticatable, freezing the escrowed funds with no recovery path.

### Finding Description
`_authenticate` reads the gateway address for a given chain strictly from live storage at delivery time, not from any value pinned at order-placement or fill time: [1](#0-0) [2](#0-1) 

The registered instance is mutated in place by `_addDeployment`, driven by the `NewDeployment` action, dispatched only by Hyperbridge governance: [3](#0-2) [4](#0-3) 

The settlement path relies on this live mapping matching the address that actually sent the original message:

- On fill, the solver on the destination chain dispatches a `RedeemEscrow` POST addressed to `_instance(order.source)` from the destination gateway's own address (`request.from` on delivery is the destination gateway's address at fill time): [5](#0-4) [6](#0-5) 

- On delivery to the source chain, `onAccept` calls `_authenticate(incoming.request)`, which requires `_instance(request.source) == module` where `module` is decoded from `request.from` (the sending gateway's real, historical address): [7](#0-6) 

If governance registers a new deployment for that destination chain (`NewDeployment`) between the time an order is filled on the old destination gateway and the time the `RedeemEscrow` message is delivered, `_instance(order.source destination)` on the source side (or equivalently `_instance(request.source)` at the destination-authenticating call) now returns the *new* address, while `request.from` still carries the *old* gateway's address that actually executed the fill. `_authenticate` therefore reverts with `Unauthorized` on every delivery attempt of that message, permanently — the message can never be re-signed to originate from a different `from` address, since `from` is fixed by the contract that actually dispatched it.

The same live-lookup problem affects the source-side cancellation path: `_cancelFromSource` also reads `_instance(order.destination)` live to build the storage-proof key for the GET request: [8](#0-7) 
If the instance address changed, the GET request queries the *new* (empty) contract's storage slot instead of the old gateway's `_filled[commitment]` slot — the proof will show "not filled" even if it genuinely was filled elsewhere, or fail to resolve a valid state at all, breaking the fallback cancellation route as well.

This is structurally identical to the referenced Perennial issue: a governance-level "controller" address update (there: collateral address; here: gateway `_instances[chain]`) is applied globally and immediately, with no migration path for in-flight cross-chain messages/state that were created under the old address, causing authentication of legitimate messages to fail against the newly-updated live value.

### Impact Explanation
Any order filled on a destination chain shortly before that chain's gateway is redeployed and registered via `NewDeployment` has its `RedeemEscrow` settlement message rejected forever on the source chain: the solver who delivered output tokens to the beneficiary can never claim the escrowed input tokens on the source chain. Because `_filled[commitment]` on the destination chain is already set (order marked filled), the source-side cancellation route (`onGetResponse`) will observe a non-empty storage value and revert with `Filled()`, and the destination-side "cancel" route is blocked for the same reason (order already filled). This results in a genuine, permanent freezing of user escrow funds with no recovery mechanism — a direct violation of the "permanent freezing of funds" criterion, reachable by an ordinary solver/user transaction sequence around a legitimate governance redeployment, not requiring any malicious governance action, matching the class and severity of the referenced report.

### Likelihood Explanation
The trigger condition — a state machine's registered IntentGateway `NewDeployment` (redeployment/migration of the destination gateway) occurring while at least one order is in flight (filled but not yet settled) — is a realistic, foreseeable operational event for a live cross-chain protocol (contract upgrades that require redeployment rather than proxy upgrade, chain migrations, or gateway replacement after an incident). Given asynchronous cross-chain delivery latency (finality + relayer submission), there is a natural window during which in-flight orders exist. This requires no attacker and no malicious governance intent, only routine maintenance, making it a credible operational risk rather than a purely theoretical or adversarial-only scenario.

### Recommendation
Do not authenticate settlement messages against the live `_instances` mapping alone. Options:
- Snapshot/pin the destination gateway address used for authentication at order-placement time inside the `Order` struct (or a per-order stored mapping keyed by commitment) so that redemption authentication always checks against the address that was valid when the order was created/filled, not the live governance-controlled value.
- Alternatively, maintain a historical set of previously-valid instance addresses per chain (rather than overwriting a single value) so that `_authenticate` accepts messages from any address that was ever registered, with a governance-controlled explicit deprecation/sunset window rather than an instantaneous, unconditional swap.
- Require governance to drain/settle all in-flight orders for a chain (or provide an explicit migration message forwarding path) before finalizing a `NewDeployment` swap for that state machine.

### Proof of Concept
1. Governance registers `GatewayOld` as the IntentGateway instance for chain `B` via `NewDeployment` (`_instances[keccak256(B)] = GatewayOld`).
2. A user places a cross-chain order on chain `A` with `destination = B`, escrowing input tokens on `A`.
3. A solver fills the order on chain `B` by calling `fillOrder` on `GatewayOld`, delivering output tokens to the beneficiary; `GatewayOld` dispatches a `RedeemEscrow` POST to chain `A`, with `from = GatewayOld`.
4. Before this message is delivered/finalized on chain `A`, governance dispatches a new `NewDeployment` for chain `B` pointing `_instances[keccak256(B)]` to `GatewayNew` (e.g., due to a contract migration).
5. When the relayer delivers the `RedeemEscrow` message to chain `A`'s `onAccept`, `_authenticate` computes `module = GatewayOld` from `request.from`, but `_instance(B)` now resolves to `GatewayNew`; the check `_instance(order.source) != module` fails and the call reverts with `Unauthorized` — permanently, since resubmission cannot change `request.from`.
6. The solver cannot claim the source-chain escrow. Any attempt at cancellation-from-source is blocked by `Filled()` because `_filled[commitment]` was already set on `GatewayOld` during the fill in step 3. The escrowed input tokens on chain `A` are permanently stuck.

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            (uint256 protocolShare, uint256 beneficiaryShare) =
                _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                _sendValue(beneficiary, beneficiaryTotal);
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        // Native dispatch fee only if the solver sent enough to cover it; else the fee token.
        uint256 nativeFee = options.nativeDispatchFee;
        if (nativeFee > msgValue) nativeFee = 0;
        msgValue -= nativeFee;
        _post(
            order,
            _body(RequestKind.RedeemEscrow, commitment, order.inputs, bytes32(uint256(uint160(msg.sender)))),
            options.relayerFee,
            nativeFee
        );
