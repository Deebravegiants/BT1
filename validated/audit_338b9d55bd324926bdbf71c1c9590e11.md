## Title
Webhook Shop-Domain Header Not Covered by HMAC Enables Cross-Tenant Signature Replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook purely by validating an HMAC over the **raw body**, then trusts a separate, unauthenticated header (`x-shopify-shop-domain`) as the tenant identifier that is handed to the app's handler. Because the HMAC is computed with the app's single `Context.api_secret_key` (shared across every shop that installs the app), and the `shop` value is never included in the signed material, an attacker who controls one legitimate install of the app can replay a validly-signed webhook body while substituting the `shop` header for a victim shop, causing the app to process the payload as if it originated from the victim tenant.

### Finding Description
`Request#hmac` and `Request#to_signable_string` show that only the raw request body is signed/verified: [1](#0-0)  

```
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end
...
def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
def to_signable_string
  @raw_body
end
```

`Registry.process` validates only that HMAC, then immediately forwards the unauthenticated `request.shop` header to the app-defined handler as the tenant identity: [2](#0-1) 

```
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

`HmacValidator.validate_signature` confirms the signature is computed with the app-wide `Context.api_secret_key` over `verifiable_query.to_signable_string` (the raw body only): [3](#0-2) 

The binding the library implicitly claims to enforce is:
`shop that authorized/produced this payload == shop attributed to the webhook (data.shop)`

But what is actually verified is only:
`bytes verified (raw_body + api_secret_key) == bytes parsed (raw_body)`

The `shop` identity is a completely separate, attacker-controlled HTTP header that plays no role in the cryptographic check. Because `api_secret_key` is one single value for the whole app (not per-shop), any tenant that has legitimately installed the app can capture a body+HMAC pair sent by Shopify to their own store and resend it to the app's public webhook endpoint with the `x-shopify-shop-domain` header rewritten to any other shop, including a victim they don't own. The HMAC still validates (same secret, same body), yet the handler receives `data.shop` pointing at the victim, exactly matching the "shop authenticated versus shop stored as session key" analog described for this scan.

### Impact Explanation
This crosses a tenant boundary: an unprivileged holder of one legitimate app installation can make the app believe a captured/re-sent webhook body belongs to a different merchant. Depending on the handler's business logic (e.g., updating order/product/customer state keyed by `data.shop`, or looking up/activating a session for that shop), this enables cross-tenant data poisoning or state corruption — classified as Critical (cross-tenant access) per the scan's impact taxonomy.

### Likelihood Explanation
Moderate-to-high: requires the attacker to operate at least one legitimate installation of the target app (a normal, unprivileged merchant/dev-store action, not a privileged credential), be able to receive one of that app's real webhooks, and know/guess a victim's `myshopify.com` domain (public information). No access to `api_secret_key` or access tokens is required — the whole point is that the shared secret produces a valid signature regardless of which shop's header is attached.

### Recommendation
Bind the shop identity to the signed material, or otherwise cryptographically tie `shop` to the specific payload, rather than trusting `x-shopify-shop-domain` as an unauthenticated header. At minimum, document/require that consuming apps must independently verify `data.shop` is associated with an existing session/install before trusting it, and consider incorporating the shop domain into the signable string used by `HmacValidator`/`Request#to_signable_string`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Shopify sends a legitimate webhook to the app: body `B`, header `x-shopify-hmac-sha256: H` (HMAC of `B` with the app's `api_secret_key`), `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker resends the exact same body `B` and HMAC `H` to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (same secret + same body), `Registry.process` builds `WebhookMetadata` with `shop: "victim.myshopify.com"`, and the app's handler processes the payload attributing it to the victim tenant.
