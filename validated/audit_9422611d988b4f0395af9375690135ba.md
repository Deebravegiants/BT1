### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely via `Utils::HmacValidator.validate`, which HMACs only the raw request body. The `shop-domain` header — the field the registered handler uses to decide **which tenant** the event belongs to — is never included in the signed material, so it can be modified without invalidating the HMAC.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the HMAC exclusively over `verifiable_query.to_signable_string`: [2](#0-1) 

`Registry.process` treats a passing HMAC check as proof the webhook "did indeed come from Shopify" (per the docs) and then immediately hands `request.shop` — read straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header — to the app's handler as the tenant identifier: [3](#0-2) [4](#0-3) 

The identity binding that should hold is:
`HMAC(secret, signed_bytes) == received_hmac` **and** `shop used by handler ⊆ signed_bytes`.

In this implementation `signed_bytes = raw_body` only, so the equality the gem actually enforces is `HMAC(secret, raw_body) == received_hmac`, while `data.shop` passed to `WebhookMetadata`/the handler comes from a header that is completely outside that signed scope. The gem's own documentation states `process` "will verify the request did indeed come from Shopify," implying the whole request (including `shop`) is trustworthy, which is not what the code guarantees: [5](#0-4) 

### Impact Explanation
An attacker who legitimately owns/operates their own installed shop (an unprivileged internet user relative to any other merchant) can capture one authentic webhook delivery to their own endpoint (raw body + its valid `x-shopify-hmac-sha256`), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value for a *different, victim* shop. Because the HMAC never covers the shop header, `HmacValidator.validate` still succeeds, and `Registry.process` forwards `WebhookMetadata.new(..., shop: request.shop, body: request.parsed_body, ...)` to the app's handler with the attacker-chosen shop but the attacker's own body content. Any host application that trusts `data.shop` for tenant-scoped writes/lookups (the exact usage pattern shown in the gem's own docs) can be made to attribute forged/attacker-controlled data to another merchant's tenant — a cross-tenant integrity/confidentiality break satisfying the Critical "cross-tenant access" bar.

### Likelihood Explanation
Likelihood is moderate-to-high: any app developer who installs the app for their own shop can capture a fully valid, Shopify-signed webhook body+HMAC for that shop through ordinary use (no secret, TLS interception, or privileged access needed), then simply resend it with a different shop header, since replay of the body is not tied to any nonce/shop binding within the gem's verification path.

### Recommendation
Include the tenant-identifying header(s) (`shop-domain`, and ideally `topic`/`webhook-id`) in the signed material verified by `HmacValidator`, or otherwise cryptographically bind `shop` to the HMAC-covered payload before it is handed to `WebhookMetadata`. At minimum, `Registry.process` should not treat a body-only HMAC pass as validating the shop attribute, and documentation should not claim the full request is verified.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and captures a legitimate webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` under the app's real secret).
2. Attacker POSTs to the app's webhook endpoint with the same body `B` and same `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because only `B` is hashed. [6](#0-5) 
4. The handler receives `data.shop == "victim-shop.myshopify.com"` with attacker-controlled body `B`, even though no data ever originated from `victim-shop`.
