### Title
Missing upper-bound validation on `accountIndex` allows out-of-spec BIP32 hardened derivation paths - ([File: libraries/key-utils/src/derivation-path.js])

### Finding Description
`SeedBasedTransactionSigner.signTransaction` in `features/tx-signer/src/module/seed-signer.ts` only guards `unsignedTx.txMeta.accountIndex` with `assert(Number.isInteger(...))`, which accepts negative numbers, zero, and any integer up to `Number.MAX_SAFE_INTEGER`. [1](#0-0) 

Actual key derivation does not use `txMeta.accountIndex` at all — it uses `walletAccount.index` directly, unvalidated by this signer, and passes it into `baseAsset.api.getKeyIdentifier(...)`. [2](#0-1) 

`WalletAccount.index` itself has no numeric range constraint at construction time — it only checks `index == null` for non-custodial accounts, not that it's within a valid BIP32 account range. [3](#0-2) 

Downstream, `assertKeyIdentifierParameters` validates `accountIndex` with `isSafeNonNegativeInteger`, which only requires `value >= 0 && Number.isSafeInteger(value)` — up to `2^53-1`, far beyond the valid BIP32 hardened-index space of `0` to `2^31-1`. [4](#0-3) [5](#0-4) 

`buildDerivationPath` similarly only asserts `accountIndex >= 0` and `typeof === 'number'`, with no upper bound, before embedding it as a hardened path segment string `${accountIndex}'`. [6](#0-5) 

The resulting path string is checked only via regex (`/^\d+(')?$/`) in `assertValidDerivationPath`, which has no numeric bound check either. [7](#0-6) 

So an `accountIndex` such as `2**31` or `Number.MAX_SAFE_INTEGER` (`2**53-1`) passes every validation layer in this call chain and produces a "syntactically valid" derivation path string that is outside the legal BIP32 hardened-index range (`HARDENED_OFFSET = 0x80000000`, valid unhardened range `0..2^31-1`). Negative values, by contrast, are rejected by `isSafeNonNegativeInteger`/`buildDerivationPath` (`>= 0` checks) and cause a thrown assertion rather than silent wraparound — this is a denial-of-service path, not key confusion.

I was unable to fully trace how the native/JS BIP32 implementation (`libraries/bip32/src/hdkey.js`, `libraries/slip10/src/hdkey.js`) numerically encodes an index exceeding `2^31-1` once it reaches the actual key-derivation primitives — whether it throws (`RangeError` from a `writeUInt32BE`-style bounds check, causing denial of service) or truncates via 32-bit bitwise coercion (causing silent wraparound to an unrelated, attacker-uncontrolled-but-different key). This should be verified directly in those files before treating it as a "wrong-key" signing bug rather than solely a DoS.

### Impact Explanation
Confirmed: the validation chain (`seed-signer.ts` → `key-identifier.js` → `derivation-path.js`) allows an out-of-spec, non-BIP44-compliant hardened account index to be accepted and turned into a derivation path string. At minimum this is a crash/denial-of-service vector when the underlying HD-key derivation code enforces 32-bit bounds and throws. If the underlying derivation instead performs 32-bit truncation on the hardened index (`index + HARDENED_OFFSET`), it could derive an unintended, but still deterministic and reproducible, key/address — this specific consequence remains unverified against `hdkey.js`.

### Likelihood Explanation
Low-to-moderate. The attacker needs to control `walletAccount.index` (e.g., via an RPC-constructed `WalletAccount`/import payload/deeplink flow that ultimately calls `signTransaction`) with an out-of-range value. Reaching `signTransaction` with an attacker-influenced `walletAccount`/`txMeta.accountIndex` requires an origin/dapp or import flow that doesn't itself constrain `index` to the normal `0..N` range used by legitimate wallet UI account creation — this repo doesn't show such a caller-side clamp in the files reviewed here.

### Recommendation
- Add explicit BIP32-compliant bounds checking for `accountIndex` (and `chainIndex`/`addressIndex`) in `assertKeyIdentifierParameters` (`libraries/key-utils/src/key-identifier.js`) and `buildDerivationPath` (`libraries/key-utils/src/derivation-path.js`): reject any value `< 0` or `> 0x7fffffff` (`2^31-1`), not just "safe non-negative integer."
- Tighten `SeedBasedTransactionSigner.signTransaction`'s assert to the same bound (`Number.isInteger(x) && x >= 0 && x <= 0x7fffffff`) rather than `Number.isInteger` alone.
- Add a constructor-time range assertion on `WalletAccount.index` in `libraries/models/src/wallet-account/index.ts`.

### Proof of Concept
Unit/fuzz test plan for `libraries/key-utils/src/derivation-path.js` and `libraries/key-utils/src/key-identifier.js`:
```js
import { buildDerivationPath } from '../src/derivation-path.js'
import { assertKeyIdentifierParameters } from '../src/key-identifier.js'

const boundaryValues = [-1, 0x80000000, 2 ** 31, Number.MAX_SAFE_INTEGER]

for (const accountIndex of boundaryValues) {
  test(`rejects out-of-range accountIndex=${accountIndex}`, () => {
    expect(() =>
      buildDerivationPath({ derivationAlgorithm: 'BIP32', purpose: 44, bip44: 0x80000000, accountIndex, chainIndex: 0, addressIndex: 0 })
    ).toThrow() // currently only negative values throw; 2**31 and MAX_SAFE_INTEGER do NOT throw, demonstrating the gap
  })
}
```
Expected (fixed) behavior: all boundary values above `0x7fffffff` and below `0` throw a clear validation error; currently `2**31` and `Number.MAX_SAFE_INTEGER` pass validation, confirming the gap.
