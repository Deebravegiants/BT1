Found the vulnerability. `TokenExchange.exchange_token` (unlike its sibling methods `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token`) never calls `Utils::ShopValidator.sanitize!` on the shop value it uses to build the request URL that carries the app's `client_secret`.

### Title
SSRF / client_secret exfiltration via unvalidated `dest` claim host in `TokenExchange.exchange_token` - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`exchange_token` derives the shop host it sends the OAuth token-exchange request (including the app's `client_id`/`client_secret`) to directly from the JWT's `dest` claim, with no domain validation, unlike every other credential-bearing helper in the same module.

### Finding Description
In `exchange_token`, the shop used to build the outbound request is taken unvalidated from the session token: `dest_shop = jwt_payload.shop` [1](#0-0) . `JwtPayload#shop` simply strips `"https://"` from the `dest` claim with no format/domain checking: `@dest.gsub("https://", "")` [2](#0-1) . `dest_shop` is then used directly to build the session whose `shop` becomes the base host for the HTTP request carrying the app's `client_id`/`client_secret`: `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)` followed by `client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")` and a POST with `client_secret: ShopifyAPI::Context.api_secret_key` in the body [3](#0-2) .

By contrast, the three sibling methods in the very same file (`migrate_to_expiring_token`, and the analogous `client_credentials`/`refresh_access_token` modules) all call `Utils::ShopValidator.sanitize!(shop)` before constructing the session/request: [4](#0-3) [5](#0-4) [6](#0-5) . `ShopValidator.sanitize!` restricts the host to Shopify's trusted domain suffixes (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) [7](#0-6) .

The identity binding broken is: *host that received the app's `client_secret`* should equal *a trusted Shopify domain*, but in `exchange_token` it instead equals *whatever string is embedded in the `dest` claim of the JWT, unchecked*.

The `dest` claim itself is only checked for `aud == Context.api_key` [8](#0-7)  — there is no validation that `iss`/`dest` point to a genuine `*.myshopify.com` (or other trusted) domain anywhere in `JwtPayload` or in `exchange_token`. While a session token is normally issued by Shopify (signed with the app's secret, so a fully external attacker without the secret cannot forge one), embedding tokens (e.g., from App Bridge in the browser, or a malicious/compromised iframe context in an embedded app) are host-supplied values that reach this code path without the gem itself constraining `dest` to a Shopify domain, unlike every sibling credential-exchange path which enforces that constraint. This is a broken defense-in-depth guarantee: the gem enforces the host-trust invariant everywhere else it sends `client_secret`, but not here.

### Impact Explanation
If `dest_shop` can be influenced to a non-Shopify host, the app's `client_id` and `client_secret` are POSTed to an attacker-controlled or arbitrary host in the token-exchange request body — a High-severity SSRF-with-credentials / client_secret exfiltration scenario, consistent with the "host validated versus host that receives the access token or `client_secret`" identity-binding class in scope.

### Likelihood Explanation
Moderate: exploitation requires a session token whose `dest` claim is not itself constrained to a trusted domain to reach `exchange_token` (e.g. token relay/replay through a compromised or misconfigured embedding context), since normal Shopify-issued tokens carry a genuine `myshopify.com` `dest`. It does not require possession of `api_secret_key`, an access token, or TLS interception — the missing check is purely a gem-side omission that is inconsistently applied compared to its sibling functions.

### Recommendation
Apply the same guard used in `migrate_to_expiring_token`/`client_credentials`/`refresh_access_token`: call `Utils::ShopValidator.sanitize!(dest_shop)` in `TokenExchange.exchange_token` before constructing `shop_session` and issuing the request, e.g.:
```ruby
dest_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)
```

### Proof of Concept
1. Obtain/construct a session token whose `dest` claim value is not a Shopify-trusted domain (e.g. via a compromised embedding host or token-relay bug in the surrounding app) but which otherwise satisfies `aud == Context.api_key`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `client.request` in [9](#0-8)  is sent to the attacker-controlled `dest_shop` host with `client_id`/`client_secret` in the JSON body, whereas `migrate_to_expiring_token` with the same malicious `shop` string would raise `Errors::InvalidShopError` via `ShopValidator.sanitize!`.
