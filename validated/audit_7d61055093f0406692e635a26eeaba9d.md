### Title
Missing zero-address check on withdrawal beneficiary permits permanent loss of escrowed native tokens - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The `withdraw()` internal function (and its equivalent `_withdraw()` in `evm/src/apps/intentsv2/ExtrinsicIntents.sol` / `IntrinsicIntents.sol`) that releases escrowed order funds on `RedeemEscrow`/`RefundEscrow` never validates that the resolved `beneficiary` address is non-zero before paying it out. `beneficiary` is ultimately derived from `order.user` (for refunds/cancellations) or `order.output.beneficiary` (for fills), both of which are attacker/user-supplied fields with no zero-address check enforced anywhere in `placeOrder`. If either field is left as `bytes32(0)` — by a client-side bug, encoding mistake, or careless integration — a subsequent refund or redemption sends the escrowed native token via a raw low-level `call{value: amount}("")` to `address(0)`, which succeeds and permanently destroys the funds.

### Finding Description
`withdraw()` decodes the beneficiary directly from the incoming `WithdrawalRequest` with no validation: [1](#0-0) 

For the `RefundEscrow` path, this beneficiary traces back to `order.user`, which is copied verbatim into the refund message at cancellation time: [2](#0-1) 

For the fill/redeem path, the output beneficiary is likewise taken as-is from the order without a zero check before native value is transferred: [3](#0-2) 

Neither `placeOrder` (as far as could be located) nor `withdraw()`/`_withdraw()` reject `address(0)` as a beneficiary. Because the payout for native-token escrow uses a raw `call{value: amount}("")`, which succeeds even when the target is `address(0)`, a zero beneficiary does not revert — it silently burns the transferred value. This is the exact bug class from the reference report: a missing 0-address check in a withdrawal path lets a simple mistake destroy user funds instead of reverting safely.

### Impact Explanation
Any order whose `user` field (used as the refund beneficiary on cancellation) or `output.beneficiary` field (used as the fill payout target) is `bytes32(0)` — whether from a client bug, a malformed order builder, or a compromised/careless integration — causes the corresponding escrowed native-token amount to be sent to `address(0)` and irrecoverably lost when the order is cancelled/refunded or filled. This is a concrete, permanent loss of user funds reachable from a single `placeOrder` transaction plus the standard cancel/fill/redeem flow — no privileged role is required.

### Likelihood Explanation
Likelihood is moderate: it requires a caller (user or their tooling) to submit an order with a zero beneficiary/user field, which is an easy mistake in SDK integrations, fuzzed/malformed calldata, or a buggy order-encoding client, and the protocol performs no defensive check to catch it before funds move. Because there is no revert path, the error is silent and irreversible once the corresponding cancel/fill message is processed.

### Recommendation
Add an explicit zero-address check on the resolved `beneficiary` in `withdraw()`/`_withdraw()` (and, defensively, validate `order.user` and `order.output.beneficiary` are non-zero in `placeOrder`), reverting with a dedicated error (e.g., `InvalidBeneficiary()`) instead of allowing the native-token transfer to `address(0)` to silently succeed.

### Proof of Concept
1. User calls `placeOrder` with `order.user = bytes32(0)` (or, for the fill path, `order.output.beneficiary = bytes32(0)`), escrowing native ETH as input.
2. Order expires unfilled; anyone calls `cancelOrder` after the deadline (permitted once expired, per `_cancelFromDest`), which sets `_filled[commitment] = address(0)` and dispatches a `RefundEscrow` message carrying `beneficiary = order.user = address(0)`.
3. On the source chain, `onAccept` authenticates the message and calls `withdraw()`/`_withdraw()`, which executes `(bool sent,) = beneficiary.call{value: amount}("")` with `beneficiary == address(0)`. The call succeeds (`sent == true`), the escrow accounting is decremented, and the native ETH is permanently lost — no revert, no recovery path.
