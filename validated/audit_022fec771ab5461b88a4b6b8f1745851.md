Based on the investigation, I found a genuine analog of the reported bug class in the gateway HTTP trigger workflow-resolution path. The core issue in the original report is that some functions strictly validate input length (`addValidators`) while sibling functions accept malformed/short input that then gets silently transformed (auto-padded) to fit an expected size (`setWithdrawer` + `_getPubKeyRoot`), enabling unexpected matches. The chainlink codebase has the same pattern in workflow identity validation.

### Title
Inconsistent workflowOwner length validation allows zero-padding to bypass exact-match workflow authorization - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
`WorkflowMetadataHandler.validateAuthMetadata` (used when workflows register/push their authorization metadata) enforces an **exact** length check on `WorkflowOwner` (`!= workflowOwnerLength`) [1](#0-0) . In contrast, `httpTriggerHandler.validateWorkflowOwner`, which validates the caller-supplied `workflowOwner` on an unprivileged, internet-facing trigger request, calls `validateHexInput`, which only checks an **upper bound** (`len(input) > expectedLength`) and never rejects a too-short value [2](#0-1) . The short, caller-controlled value is then passed to `normalizeHex`, which left-pads it with zeros to the expected length before it is used to look up the workflow [3](#0-2) .

### Finding Description
`validateHexInput` is the shared helper for `workflowID` and `workflowOwner` validation in the HTTP trigger handler:
```
func validateHexInput(input string, expectedLength int) error {
	if input != strings.ToLower(input) { ... }
	if len(input) > expectedLength { ... }   // only upper bound checked
	hexStr := strings.TrimPrefix(input, "0x")
	_, err := hex.DecodeString(hexStr)
	...
}
``` [4](#0-3) 

Unlike `WorkflowMetadataHandler.validateAuthMetadata`, which requires `len(...) != workflowOwnerLength` (exact match) for the same conceptual field [1](#0-0) , the trigger-path validator accepts any hex string shorter than the expected length. The value is then passed through `normalizeHex`, which pads it with leading zeros to reach the expected length:
```
func normalizeHex(input string, length int) string {
	hexStr := strings.TrimPrefix(input, "0x")
	expectedHexLength := length - 2
	paddedHex := strings.Repeat("0", expectedHexLength-len(hexStr)) + hexStr
	return "0x" + paddedHex
}
``` [5](#0-4) 

`resolveWorkflowID` uses this normalized/padded owner (along with workflow name and tag) to look up a registered workflow via `GetWorkflowID`, and the resolved `workflowID` is then used to authorize/execute the trigger request [6](#0-5) . This mirrors the `setWithdrawer`/`_getPubKeyRoot` inconsistency in the report exactly: one code path enforces strict length while a sibling code path silently zero-pads a short, unprivileged, attacker-controlled input before using it as a lookup/identity key.

### Impact Explanation
This is a genuine unprivileged-actor confusion vector in the internet-facing gateway. An attacker submitting an `HTTPTriggerRequest` with a truncated `workflowOwner` will have it silently zero-padded rather than rejected. While practically finding a collision against a real, non-zero-prefixed workflow owner address requires the victim's owner address to legitimately have leading zero bytes (or the attacker guessing/knowing such an owner), the validation asymmetry itself is a real inconsistency: the same conceptual identifier (`WorkflowOwner`) is treated as "must be exact" in one authorization path and "may be short and auto-padded" in another, which is precisely the anti-pattern flagged in the report. This could enable cross-user response confusion / workflow request misrouting if any registered workflow owner has a short/zero-padded prefix representation, and it also weakens defense-in-depth against malformed-input abuse on the unprivileged trigger endpoint.

### Likelihood Explanation
Likelihood of a full authorization bypass is low-to-moderate, contingent on the existence of a workflow owner value whose hex form has leading zero bytes (i.e., an address numerically small enough to be produced by padding a short attacker input). The inconsistency itself, however, is unconditionally present and reachable by any unprivileged client hitting the gateway's HTTP trigger endpoint, matching the report's core recommendation: enforce exact length checks consistently rather than relying on implicit auto-padding.

### Recommendation
Make `validateHexInput` enforce an exact expected length (`len(input) != expectedLength`) for `workflowOwner` (and `workflowID`) in `httpTriggerHandler`, matching the strict check already used in `WorkflowMetadataHandler.validateAuthMetadata`. Remove reliance on `normalizeHex`'s zero-padding behavior for validation purposes; padding, if still needed for formatting, should occur only after an exact-length check has already passed.

### Proof of Concept
1. Submit a `jsonrpc.Request` with method `gateway_common.MethodWorkflowExecute` and `Workflow.WorkflowOwner = "0x1234"` (a valid hex string far shorter than `workflowOwnerLength`).
2. `validateWorkflowOwner` → `validateHexInput("0x1234", workflowOwnerLength)` passes because `len("0x1234") (6) > workflowOwnerLength` is false [7](#0-6) .
3. `resolveWorkflowID` calls `normalizeHex("0x1234", workflowOwnerLength)`, producing `"0x00000000000000000000000000000000001234"` [8](#0-7) .
4. This zero-padded value is used to look up a workflow via `GetWorkflowID`; if any registered workflow's owner hex representation happens to equal this zero-padded string, the attacker's truncated input resolves to that workflow's ID, despite never having supplied the real owner address, contrary to the exact-match validation enforced elsewhere (`validateAuthMetadata`).

func validateHexInput(input string, expectedLength int) error {
	if input != strings.ToLower(input) {
		return errors.New("must be lowercase")
	}

	if len(input) > expectedLength {
		return fmt.Errorf("hex string too long: expected at most %d characters, got %d", expectedLength, len(input))
	}

	hexStr := strings.TrimPrefix(input, "0x")
	_, err := hex.DecodeString(hexStr)
	if err != nil {
		return errors.New("must be a valid hex string")
	}

	return nil
}

func (h *httpTriggerHandler) validateWorkflowID(ctx context.Context, workflowID, requestID string, callback handlers.Callback) error {

}

// normalizeHex normalizes a hex string by stripping 0x prefix, padding with leading zeros, and adding 0x prefix back
func normalizeHex(input string, length int) string {
	hexStr := strings.TrimPrefix(input, "0x")
	// length-2 because we'll add "0x" prefix
	expectedHexLength := length - 2
	paddedHex := strings.Repeat("0", expectedHexLength-len(hexStr)) + hexStr
	return "0x" + paddedHex
}

func (h *httpTriggerHandler) resolveWorkflowID(ctx context.Context, triggerReq *jsonrpc.Request[gateway_common.HTTPTriggerRequest], requestID string, callback handlers.Callback) (string, error) {
	h.lggr.Debugw("resolving workflow ID", "workflowID", triggerReq.Params.Workflow.WorkflowID, "workflowOwner", triggerReq.Params.Workflow.WorkflowOwner, "workflowName", triggerReq.Params.Workflow.WorkflowName, "workflowTag", triggerReq.Params.Workflow.WorkflowTag, "requestID", requestID)
	workflowID := triggerReq.Params.Workflow.WorkflowID
	if workflowID != "" {
		workflowID = normalizeHex(workflowID, workflowIDLength)
		_, found := h.workflowMetadataHandler.GetWorkflowReference(workflowID)
		if !found {
			h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, fmt.Sprintf("Workflow not found. 'workflowID' %s is not a valid workflow ID", workflowID), callback)
			return "", errors.New("workflow not found")
		}
		return workflowID, nil
	}
	workflowOwner := normalizeHex(triggerReq.Params.Workflow.WorkflowOwner, workflowOwnerLength)
	workflowName := "0x" + hex.EncodeToString([]byte(workflows.HashTruncateName(triggerReq.Params.Workflow.WorkflowName)))
	workflowID, found := h.workflowMetadataHandler.GetWorkflowID(
		workflowOwner,
		workflowName,
		triggerReq.Params.Workflow.WorkflowTag,
	)
	if !found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "Workflow not found. Provide either a valid 'workflowID' or a valid combination of 'workflowOwner', 'workflowName', and 'workflowTag'", callback)
		return "", errors.New("workflow not found")
	}
	return workflowID, nil
}
