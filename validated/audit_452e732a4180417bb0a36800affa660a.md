Confirmed: `markUtxosAsBlocked()` and its use in `prooflessDeposit`/`DepositOnChainUtxosExternalAction` only ever emit the `BlockedUtxosCreated` event [1](#0-0) , with no accompanying on-chain state (mapping, flag on the UTXO/commitment, or nullifier reservation) that actually restricts spending of the underlying commitment.

### Title
"Blocked" UTXOs are not actually locked on-chain, enabling an escrow-style honeypot / rug of counterparties relying on `BlockedUtxosCreated` - (File: `contracts/Hinkal.sol`, `contracts/HinkalBase.sol`, `contracts/external-actions/DepositOnChainUtxosExternalAction.sol`)

### Summary
`prooflessDeposit`'s `createBlockedUtxos` flag and `DepositOnChainUtxosExternalAction` both advertise that a UTXO/commitment is "blocked" by emitting `BlockedUtxosCreated()`, but neither the flag nor the event has any on-chain enforcement preventing the owner of that commitment from immediately spending it via a normal `transact()` call with a valid nullifier proof. This is the exact H-2 pattern: an asset that a counterparty is led to believe is locked/reserved (the "escrow") can be drained by its owner at any time, including in the same block or right before a matching counter-transaction, leaving the counterparty with nothing.

### Finding Description
`Hinkal.prooflessDeposit()` accepts a `createBlockedUtxos` boolean and, if true, calls `markUtxosAsBlocked()`, which is a no-op besides emitting an event: [2](#0-1) [1](#0-0) 

Likewise, `DepositOnChainUtxosExternalAction.runAction` creates on-chain UTXOs and emits the same `BlockedUtxosCreated` event as a signal, again with no mapping or state marking those specific commitments as non-spendable: [3](#0-2) 

The `orderId` parameter passed alongside `createBlockedUtxos` is explicitly documented as "unused on-chain; off-chain listeners read it from calldata to match this tx to an order" [4](#0-3) . This confirms the intended design: an off-chain marketplace/relayer watches for `BlockedUtxosCreated` + `orderId` to treat a deposited UTXO as reserved for a specific buyer/order (functionally the "escrow/club" in the Footium analogy), while the actual spendability of that commitment is governed only by the standard nullifier check in `HinkalBase.insertNullifiers()`, which has no concept of "blocked": [5](#0-4) 

Because nothing in `transact()`'s balance/slippage equality or nullifier-uniqueness check consults the "blocked" status, the owner of the underlying UTXO can generate a normal proof and spend/withdraw the commitment via `_internalTransact`/`_externalTransact` at any time — including after signaling "blocked" and receiving payment/commitment from a counterparty off-chain, but before the counterparty's matching transaction lands. This breaks the implicit equality the marketplace relies on: "UTXO marked blocked ⇒ commitment remains spendable only by/for the intended buyer until order completes." No such invariant is enforced on-chain.

### Impact Explanation
A seller can list a "blocked" UTXO (e.g., via `prooflessDeposit(..., createBlockedUtxos=true, orderId)`), have a buyer act on the `BlockedUtxosCreated` signal (paying off-chain, or depositing funds expecting to atomically claim the blocked UTXO), and then front-run the settlement by spending the underlying commitment with `transact()` before the buyer's transaction is included. The buyer is left with an empty/void claim while the seller retains the funds — a direct theft of the buyer's payment/expected transferred value, matching the report's "executing calls or moving assets a wallet owner or prover never authorised" / theft-of-in-flight-funds impact category.

### Likelihood Explanation
High. This requires no privileged role — any unprivileged EOA acting as a "seller" in an OTC/marketplace flow built on top of `createBlockedUtxos`/`orderId` can execute this by simply calling `transact()` to spend their own commitment after emitting the blocking signal and before the buyer's transaction confirms (mempool front-running or same-block ordering), exactly mirroring the original Footium report's mechanics.

### Recommendation
Either remove the misleading "blocked" semantics entirely (and rely purely on off-chain trust with clear documentation that no on-chain lock exists), or implement real enforcement: mark the specific commitment/nullifier as locked in contract state when `createBlockedUtxos`/`DepositOnChainUtxosExternalAction` is used, and have `insertNullifiers`/`transact()` reject spends of locked commitments until the order is explicitly released or expires (e.g., via a buyer-claim function or an authorized unlock call), so the "blocked" state actually constrains spendability rather than being a purely informational event.

### Proof of Concept
1. Seller calls `Hinkal.prooflessDeposit(erc20Addresses, amounts, stealthAddressStructures, onChainEncryptedOutputs, createBlockedUtxos=true, orderId="order-1")`, which deposits tokens, creates an on-chain UTXO commitment, and emits `BlockedUtxosCreated()` [2](#0-1) .
2. An off-chain marketplace watching for `BlockedUtxosCreated`/`orderId` treats the UTXO as reserved for Buyer B and instructs B to send payment (on-chain or off-chain) to claim it.
3. Before B's claim transaction is mined, the seller generates a standard ZK proof for the same commitment and calls `Hinkal.transact(...)`, whose only checks are the calldata-hash integrity, proof verification, root-hash existence, and nullifier-uniqueness — none of which reference "blocked" status [5](#0-4) .
4. The nullifier is consumed and funds are withdrawn/transferred to the seller via `_internalTransact`, succeeding because no on-chain state distinguishes a "blocked" UTXO from any other spendable UTXO.
5. Buyer B's later transaction fails (nullifier already spent / commitment already withdrawn), and B has already paid or committed value based on the false assumption that the UTXO was locked.

    function insertNullifiers(
        uint256[][] calldata inputNullifiers,
        bool[] calldata onChainCreation
    ) internal {
        for (uint256 i = 0; i < inputNullifiers.length; i++) {
            for (uint256 j = 0; j < inputNullifiers[i].length; j++) {
                if (onChainCreation[i] == true) break;
                if (inputNullifiers[i][j] != 0) {
                    require(
                        !nullifiers[inputNullifiers[i][j]],
                        "Nullifier cannot be reused"
                    );
                    nullifiers[inputNullifiers[i][j]] = true;
                    emit Nullified(inputNullifiers[i][j]);
                }
            }
        }
    }

contract DepositOnChainUtxosExternalAction is Transferer, ExternalActionBaseV2 {
    event BlockedUtxosCreated();

    constructor(
        address[] memory _allowedRecipients
    ) ExternalActionBaseV2(_allowedRecipients) {}

    function runAction(
        CircomData calldata circomData,
        int256[] calldata deltaAmounts
    ) external override onlyAllowedRecipient returns (UTXO[] memory utxoSet) {
        uint256 tokenCount = circomData.erc20TokenAddresses.length;
        require(
            tokenCount > 0 && deltaAmounts.length == tokenCount,
            "DepositOnChainUtxosExternalAction: token count mismatch"
        );

        address userAddress = circomData.originalSender;
        require(
            userAddress != address(0),
            "DepositOnChainUtxosExternalAction: Invalid originalSender"
        );

        uint256[][] memory utxoAmounts = abi.decode(
            circomData.externalActionData.externalActionMetadata,
            (uint256[][])
        );
        require(
            utxoAmounts.length == tokenCount,
            "DepositOnChainUtxosExternalAction: metadata length mismatch"
        );

        utxoSet = new UTXO[](countUtxos(utxoAmounts));

        uint256 utxoIndex = 0;
        for (uint256 i = 0; i < tokenCount; i++) {
            require(
                deltaAmounts[i] == 0,
                "DepositOnChainUtxosExternalAction: Delta amount must be zero"
            );

            address tokenAddress = circomData.erc20TokenAddresses[i];
            uint256 tokenTotal = 0;

            for (uint256 j = 0; j < utxoAmounts[i].length; j++) {
                uint256 amount = utxoAmounts[i][j];
                require(
                    amount > 0,
                    "DepositOnChainUtxosExternalAction: UTXO amount must be positive"
                );
                tokenTotal += amount;

                utxoSet[utxoIndex] = UTXO({
                    amount: amount,
                    erc20Address: tokenAddress,
                    stealthAddressStructure: circomData.stealthAddressStructure,
                    timeStamp: circomData.timeStamp + utxoIndex
                });
                utxoIndex++;
            }

            if (tokenAddress != address(0) && tokenTotal > 0) {
                transferERC20TokenFrom(
                    tokenAddress,
                    userAddress,
                    msg.sender,
                    tokenTotal
                );
            }
        }

        emit BlockedUtxosCreated();
    }
