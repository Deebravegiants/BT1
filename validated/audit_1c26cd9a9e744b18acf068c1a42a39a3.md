### Title
Webhook `shop`/`topic`/`webhook_id` metadata are trusted for tenant dispatch without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers and then handed to the application's webhook handler as the tenant identity for the payload. This lets an attacker who owns any legitimate installation of the app (and can therefore obtain genuinely-signed webhook deliveries) resubmit a captured, validly-signed webhook body while swapping the `shop-domain` header to a victim shop, producing a request that passes `HmacValidator.validate` yet is dispatched to the app as if it originated from the victim tenant.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are parsed independently from headers that are not part of that signed string: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the HMAC and then forwards `request.shop`, `request.topic`, and `request.webhook_id` straight to the app-supplied handler as trusted tenant/routing metadata: [4](#0-3) 

The identity binding that should hold is:
`shop header value == shop bound inside the HMAC-signed content`

but the actual binding enforced by this gem is only:
`HMAC(raw_body) == received_hmac`

with `shop` (and `topic`/`webhook_id`) verified as *bytes present in the header* but never cross-checked against anything covered by the signature. This is the same bug class as the report's `normalizedToFull()` issue: a value that is *acted upon* (here, tenant attribution for dispatch) is derived from data that is disjoint from the data that was actually cryptographically verified.

Because Shopify signs webhooks with the app's single shared `client_secret` for *all* shops that have the app installed, any unprivileged internet user who installs the app on their own (attacker-controlled) development/trial store receives real webhook deliveries with a valid HMAC over a body they can partially or fully control (e.g., an `orders/create` payload for their own store). They can then replay that exact `raw_body` + `hmac-sha256` header pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and optionally `shopify-topic`/`shopify-webhook-id`) with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body signature, and `Registry.process` dispatches the attacker-chosen body content to the handler tagged with the victim's shop.

### Impact Explanation
This crosses a tenant boundary: it lets an attacker inject data into another merchant's webhook-processing pipeline while carrying the identity of that merchant's shop, satisfying "cross-tenant access" (Critical) as defined by the ruleset, since any host application logic that keys off `WebhookMetadata#shop` (e.g., to select which merchant's session/access token/data record to update) will act on attacker-supplied data under the wrong tenant.

### Likelihood Explanation
Requires the attacker to be able to install the app themselves (or otherwise obtain one legitimate webhook delivery) and to freely POST HTTP requests with arbitrary headers to the app's public webhook endpoint — both are unprivileged-internet-user actions with no leaked credentials or privileged account needed. The only constraint is that the injected body content is limited to whatever data a legitimate webhook of that topic/shape can carry (e.g., order/customer content on the attacker's own store), which still gives meaningful attacker control over cross-tenant-attributed data.

### Recommendation
Bind the routing/tenant metadata into the signed content, or otherwise cryptographically tie the `shop`/`topic`/`webhook_id` header values to the verified payload before using them for dispatch:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string` (matching what Shopify's HMAC actually authenticates end-to-end for the delivery), or
- After computing the raw-body HMAC, require the host application to independently corroborate the delivered `shop` against a shop that is expected/registered for that specific webhook subscription (e.g., compare against the webhook's registered callback/shop) rather than trusting the header value unconditionally in `Registry.process`.

### Proof of Concept
1. Attacker creates a Partner-owned development store and installs the target Shopify app, receiving a genuine webhook subscription (e.g., `orders/create`) signed by Shopify with the app's `client_secret`.
2. Attacker triggers an event on their own store producing an attacker-influenced JSON body `B`; Shopify sends:
   - `X-Shopify-Hmac-Sha256: H = HMAC-SHA256(client_secret, B)`
   - `X-Shopify-Topic: orders/create`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
3. Attacker replays the identical `B` and `H` to the app's public webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds successfully because header presence checks only require the three headers to exist: [5](#0-4) 
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` and compares it to `H` — this passes because `B` and `H` are both replayed unchanged: [6](#0-5) 
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body `B`, even though that body was never actually sent by Shopify for the victim shop: [7](#0-6)

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
