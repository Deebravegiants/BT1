### Title
Fee-on-Transfer Underlying Tokens Break Locked/Unlocked Accounting in `WrappedHyperFungibleToken.send()` - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` pulls the underlying ERC20 with `safeTransferFrom(msg.sender, address(this), params.amount)` and then dispatches a cross-chain message that always carries the user-specified `params.amount`, instead of the amount actually received by the contract. For fee-on-transfer tokens, the contract receives less than `params.amount`, but the destination chain unlocks/transfers the full `params.amount` to the beneficiary, causing the locked-token reserve backing the wrapper to become permanently under-collateralized.

### Finding Description
In `send()`:
```solidity
function send(HyperFungibleToken.SendParams calldata params) external payable whenNotPaused {
    uint256 msgValue = msg.value;
    if (_isWeth && msgValue >= params.amount) {
        msgValue = msgValue - params.amount;
        IWETH(_underlying).deposit{value: params.amount}();
    } else {
        IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
    }

    DispatchPost memory request = _buildDispatchPost(params);
    ...
}
``` [1](#0-0) 

`_buildDispatchPost` encodes `params.amount` verbatim into the cross-chain `Message`, with no adjustment for actual tokens received:
```solidity
bytes memory body = abi.encode(HyperFungibleToken.Message({
    from: abi.encodePacked(msg.sender),
    to: params.to,
    amount: params.amount,
    data: params.data
}));
``` [2](#0-1) 

If `_underlying` is a fee-on-transfer token, `safeTransferFrom` delivers `params.amount - fee` to the contract, but the dispatched message still commits to unlocking `params.amount` on delivery (or on timeout refund). On the receiving side, `onAccept` unconditionally transfers `message.amount` of the underlying to the beneficiary:
```solidity
} else {
    IERC20(_underlying).safeTransfer(beneficiary, message.amount);
}
``` [3](#0-2) 

The same is true of the timeout refund path, `onPostRequestTimeout`, which also refunds the full `message.amount`: [4](#0-3) 

This is the exact bug class described in the external report — the amount used downstream (dispatched/minted/unlocked) is the pre-fee requested amount rather than the actual amount received by the contract holding custody, so the deducted transfer fee is never accounted for. The sibling `IntentGatewayV2` contract explicitly guards against this by snapshotting balances before/after transfer and using the delta (see `evm/src/apps/IntentGatewayV2.sol` lines 230–329, and the corresponding test suite at `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` lines 2436–2686), confirming this is a recognized bug class in this codebase that was not addressed in `WrappedHyperFungibleToken`. [5](#0-4) 

### Impact Explanation
Each `send()` call with a fee-on-transfer underlying locks strictly less value than the amount the protocol commits to unlocking on the destination (or refunding on timeout). Repeated use drains the locked-token custody pool below what is needed to satisfy legitimate unlock/refund obligations, eventually causing later unlocks/refunds to revert (funds frozen) or, for chains that mint/transfer from a shared pool across many users, letting one user's shortfall be paid out of other users' deposits (a value-transfer/theft effect). This is a protocol-level insolvency in the wrapped-token custody accounting, directly reachable by any single unprivileged user submitting a `send()` transaction with a fee-on-transfer token configured as `_underlying`.

### Likelihood Explanation
The `configure()` owner function can set `_underlying` to any ERC20 address, and nothing in the code enforces that the token must not have a transfer fee; standard fee-on-transfer tokens are common (deflationary/tax tokens). Any user calling `send()` triggers the discrepancy — no special privileges or timing are required, only that the configured underlying charges a fee on `transferFrom`.

### Recommendation
Mirror the pattern already used in `IntentGatewayV2`: measure the actual balance received before crediting/dispatching.
```solidity
uint256 balBefore = IERC20(_underlying).balanceOf(address(this));
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
uint256 received = IERC20(_underlying).balanceOf(address(this)) - balBefore;
// use `received` (not params.amount) when building the dispatched Message
```
Apply the same actual-amount accounting to the WETH branch if `deposit()` can also incur deductions, and ensure the dispatched `Message.amount` (and thus what `onAccept`/`onPostRequestTimeout` unlock) always reflects tokens truly held in custody.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` = a 1% fee-on-transfer ERC20.
2. User calls `send({amount: 1000e18, ...})`. `safeTransferFrom` delivers only 990e18 to the contract; contract balance increases by 990e18.
3. `_buildDispatchPost` still encodes `amount: 1000e18` into the cross-chain `Message`; the ISMP request commits to unlocking 1000e18 on the destination chain (or refunding 1000e18 on timeout).
4. When the request is delivered, `onAccept` on the destination executes `IERC20(_underlying).safeTransfer(beneficiary, 1000e18)`, unlocking 10e18 more than was actually locked.
5. Repeating this drains the custody reserve, so a subsequent legitimate unlock/refund for another user reverts due to insufficient balance (frozen funds), or is paid using another user's escrowed principal.

        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
