## Finding [1](#0-0) [2](#0-1) 

### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from HTTP headers that are never included in the HMAC-signed content. `Registry.process` validates the HMAC and then trusts `request.shop` unconditionally to build `WebhookMetadata` passed to the app's handler, mirroring the reported bug class where a field is "acted on but not covered" by the integrity check — analogous to the `SwapCallLib.call()` case where a failure path let execution continue with unauthenticated state.

### Finding Description
`Utils::HmacValidator.validate(request)` computes the HMAC purely over `request.to_signable_string`, which is `@raw_body`: [3](#0-2) 

`request.shop`, however, is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to that HMAC: [4](#0-3) 

`Registry.process` validates only the body's HMAC and then forwards the unauthenticated `shop` header straight to the app's webhook handler as the tenant identity: [5](#0-4) 

Because Shopify signs webhooks with the single app-level `client_secret` (the same secret is used for every shop that has the app installed), a valid `(body, hmac)` pair is not shop-specific — it only proves "signed by holder of this app's secret," not "signed for shop X." An attacker who installs the app on their own store receives genuinely-signed webhook deliveries (valid body + HMAC, computed with the app's shared secret). They can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still passes (it never looked at the header), so `Registry.process` invokes the handler with `WebhookMetadata` claiming the victim shop, while the body content is fully attacker-controlled data captured from the attacker's own shop.

This breaks the intended identity binding: `shop authenticated == shop stored/acted upon`. The HMAC only proves data integrity of the body, not the shop-tenant binding that `Registry.process` implicitly assumes when it hands `request.shop` to application handlers.

### Impact Explanation
This is a cross-tenant confusion vulnerability: any app using this library to persist or act on webhook data keyed by `WebhookMetadata#shop` can have attacker-controlled body content misattributed to any other merchant's tenant (e.g., fake `orders/create`, `app/uninstalled`, or `shop/update` payloads processed under a victim shop id). This matches the Critical "cross-tenant access" impact category, since the boundary between tenants is enforced only by an easily-spoofed header rather than by the cryptographic signature.

### Likelihood Explanation
Exploitation requires the attacker to install the target app on a shop they control (a normal, low-barrier action for any public/embedded Shopify app) in order to harvest a legitimately-signed `(body, hmac)` pair, then replay it to the app's webhook endpoint with a modified `shop-domain` header. No access to the app's `client_secret`, access tokens, or victim credentials is required — only observation of the attacker's own webhook deliveries, which are visible to any merchant who installs the app.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`) values inside the HMAC-signed content, or otherwise cryptographically bind the claimed shop domain to the signed payload before trusting `request.shop` in `Registry.process`. At minimum, document that consuming applications must independently verify `WebhookMetadata#shop` against a known/installed-shop list rather than treating it as authenticated by `HmacValidator.validate`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify sends a webhook to the app's endpoint with a body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)` — signed with the app's single shared `client_secret`.
3. Attacker replays the exact same `B` and `H` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(client_secret, B) == H`, per `lib/shopify_api/webhooks/request.rb` line 36-38 and `lib/shopify_api/webhooks/registry.rb` line 190.
5. `Registry.process` calls the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the app to process attacker-controlled data as if it originated from the victim shop.
