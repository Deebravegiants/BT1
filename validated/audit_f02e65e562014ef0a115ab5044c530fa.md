### Title
Cross-chain replay of `RotationProofChallenge` in `rotate_authentication_key` / `rotate_authentication_key_with_rotation_capability` due to missing `chain_id` binding - (File: `aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary
The Opera-Bridge bug is a missing `chain_id`/contract-address binding in a signed message hash, allowing off-chain signatures to be replayed across chains or redeployed contracts. Aptos's own `account.move` module shows it already recognizes this exact bug class — the *offer* challenges were upgraded to `...ProofChallengeV2` specifically to add `chain_id` — but the core key-rotation challenge, `RotationProofChallenge`, was never given the same fix.

### Finding Description
`RotationProofChallenge` [1](#0-0)  is the struct signed off-chain to authorize an authentication-key rotation. It contains only `sequence_number`, `originator`, `current_auth_key`, and `new_public_key` — no `chain_id`. The doc comment claims replay is prevented "because they include the TXN's unique sequence number," but sequence numbers are per-account counters that reset to 0 on every distinct chain/genesis and are not chain-unique.

Contrast this with `RotationCapabilityOfferProofChallengeV2`, whose comment explicitly states the fix: *"This V2 struct adds the `chain_id` and `source_address` to the challenge message, which prevents replaying the challenge message."* [2](#0-1)  The same pattern is used in `multisig_account::MultisigAccountCreationMessage`, which explicitly documents `chain_id` as being "included to prevent cross-chain replay" [3](#0-2) .

Despite this precedent, `rotate_authentication_key` [4](#0-3)  and `rotate_authentication_key_with_rotation_capability` [5](#0-4)  both build the challenge from only `sequence_number`, `originator`, `current_auth_key`, and `new_public_key`, and verify it via `assert_valid_rotation_proof_signature_and_get_auth_key` [6](#0-5) , with no `chain_id` check anywhere in that path.

For `rotate_authentication_key_with_rotation_capability` in particular, the transaction is submitted by the **delegate**, not the account owner, so the only authorization for rotating the offerer's key is the captured `cap_update_table` signature over `RotationProofChallenge`. If an offerer account and a delegate account exist with identical addresses, auth keys, and sequence numbers on two different Aptos-based chains (e.g., a devnet/testnet reset sharing genesis state with mainnet, or an enterprise/L2 fork of Aptos that copies mainnet account state), a `cap_update_table` signature captured on chain A is bit-for-bit valid on chain B, and the delegate can replay it there to rotate the offerer's authentication key without any fresh authorization from the current chain-B key holder.

### Impact Explanation
A successful replay lets an unprivileged delegate take over custody of another account's authentication key on a second chain, without that chain's owner ever authorizing it there. Auth-key control is the root of custody for all APT, fungible assets, and objects owned by that account, so this is a full account takeover / unauthorized owner-reassignment scenario, matching the "Unauthorized takeover of ... resource-account control" custody-impact category.

### Likelihood Explanation
Exploitation requires a precondition: two Aptos chains (or the same chain across a fork/genesis reset) sharing identical account state (address, auth key, sequence number) for both the offerer and the delegate. This is realistic for Aptos-based devnets/testnets rehydrated from mainnet snapshots, and for enterprise/L2 deployments that fork Aptos framework code and initialize state from a mainnet-like genesis. It is not exploitable on two chains with independent, divergent account histories. Given this precondition requirement, likelihood is lower than the original Opera-Bridge case (which needed no shared state, only shared signature format), but the underlying root cause — a signed authorization struct with no `chain_id`, in a module that has already fixed the identical bug in three sibling structs — is a genuine, currently-unpatched gap in local code.

### Recommendation
Add `chain_id: u8` (and ideally the resource address, mirroring `MultisigAccountCreationMessage`) to `RotationProofChallenge`, and update `rotate_authentication_key` and `rotate_authentication_key_with_rotation_capability` to populate and verify it, consistent with the fix already applied to `RotationCapabilityOfferProofChallengeV2` and `SignerCapabilityOfferProofChallengeV2`.

### Proof of Concept
1. Deploy/observe two Aptos-based chains (chain A, chain B) that share identical genesis/account state for address `O` (offerer) and address `D` (delegate) — e.g., a testnet reset from a mainnet snapshot, or a permissioned fork.
2. On chain A, `O` legitimately offers rotation capability to `D`, and `D` submits `rotate_authentication_key_with_rotation_capability` with a `cap_update_table` signed over `RotationProofChallenge{ sequence_number, originator: O, current_auth_key, new_public_key }`.
3. Capture the `cap_update_table` bytes (e.g., from the public transaction on chain A).
4. On chain B, where `O`'s account still has the same `sequence_number`/`current_auth_key` and has (or is later given) the same rotation-capability offer to `D`, `D` submits the identical transaction with the same captured `cap_update_table` bytes.
5. `assert_valid_rotation_proof_signature_and_get_auth_key` passes because the struct contains no `chain_id`, and `O`'s authentication key on chain B is rotated to the attacker-controlled `new_public_key` without any fresh authorization on chain B.

Note: I was not able to execute this against a live network to empirically confirm the shared-genesis precondition holds for any specific currently-deployed Aptos network pair; this is a code-level analysis of the missing `chain_id` binding, consistent with the fix already present for the V2 offer-capability challenges in the same file.

    public entry fun rotate_authentication_key(
        account: &signer,
        from_scheme: u8,
        from_public_key_bytes: vector<u8>,
        to_scheme: u8,
        to_public_key_bytes: vector<u8>,
        cap_rotate_key: vector<u8>,
        cap_update_table: vector<u8>,
    ) acquires Account, OriginatingAddress {
        let addr = signer::address_of(account);
        ensure_resource_exists(addr);
        let account_resource = &mut Account[addr];
        let old_auth_key = account_resource.authentication_key;
        // Verify the given `from_public_key_bytes` matches this account's current authentication key.
        if (from_scheme == ED25519_SCHEME) {
            let from_pk = ed25519::new_unvalidated_public_key_from_bytes(from_public_key_bytes);
            let from_auth_key = ed25519::unvalidated_public_key_to_authentication_key(&from_pk);
            assert!(
                account_resource.authentication_key == from_auth_key,
                error::unauthenticated(EWRONG_CURRENT_PUBLIC_KEY)
            );
        } else if (from_scheme == MULTI_ED25519_SCHEME) {
            let from_pk = multi_ed25519::new_unvalidated_public_key_from_bytes(from_public_key_bytes);
            let from_auth_key = multi_ed25519::unvalidated_public_key_to_authentication_key(&from_pk);
            assert!(
                account_resource.authentication_key == from_auth_key,
                error::unauthenticated(EWRONG_CURRENT_PUBLIC_KEY)
            );
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        };

        // Construct a valid `RotationProofChallenge` that `cap_rotate_key` and `cap_update_table` will validate against.
        let curr_auth_key_as_address = from_bcs::to_address(account_resource.authentication_key);
        let challenge = RotationProofChallenge {
            sequence_number: account_resource.sequence_number,
            originator: addr,
            current_auth_key: curr_auth_key_as_address,
            new_public_key: to_public_key_bytes,
        };

        // Assert the challenges signed by the current and new keys are valid
        assert_valid_rotation_proof_signature_and_get_auth_key(
            from_scheme,
            from_public_key_bytes,
            cap_rotate_key,
            &challenge
        );
        let new_auth_key = assert_valid_rotation_proof_signature_and_get_auth_key(
            to_scheme,
            to_public_key_bytes,
            cap_update_table,
            &challenge
        );

    fun assert_valid_rotation_proof_signature_and_get_auth_key(
        scheme: u8,
        public_key_bytes: vector<u8>,
        signature: vector<u8>,
        challenge: &RotationProofChallenge
    ): vector<u8> {
        if (scheme == ED25519_SCHEME) {
            let pk = ed25519::new_unvalidated_public_key_from_bytes(public_key_bytes);
            let sig = ed25519::new_signature_from_bytes(signature);
            assert!(
                ed25519::signature_verify_strict_t(&sig, &pk, *challenge),
                std::error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE)
            );
            ed25519::unvalidated_public_key_to_authentication_key(&pk)
        } else if (scheme == MULTI_ED25519_SCHEME) {
            let pk = multi_ed25519::new_unvalidated_public_key_from_bytes(public_key_bytes);
            let sig = multi_ed25519::new_signature_from_bytes(signature);
            assert!(
                multi_ed25519::signature_verify_strict_t(&sig, &pk, *challenge),
                std::error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE)
            );
            multi_ed25519::unvalidated_public_key_to_authentication_key(&pk)
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        }
    }
