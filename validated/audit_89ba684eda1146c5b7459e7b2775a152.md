### Title
Webhook shop identity is unauthenticated — `shop`/`topic`/`webhook_id` headers are not covered by the HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`), `topic`, and `webhook_id` exclusively from unauthenticated HTTP headers, while its HMAC (`to_signable_string`) only covers the raw request body. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` that is handed to the application's handler, with no check that the header actually belongs to the shop whose secret produced the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are read straight from headers that are entirely outside that signable string: [2](#0-1) 

`HmacValidator.validate` only recomputes the signature over `verifiable_query.to_signable_string` (i.e. the body): [3](#0-2) 

`Registry.process` validates that HMAC, then constructs `WebhookMetadata` using `request.shop` (and `request.topic`, `request.webhook_id`) with no additional binding between the verified body and the header-derived shop: [4](#0-3) 

The identity binding that should hold is: `shop-header-authenticity == body-authenticity` (i.e. the shop the handler is told about should be provably the shop whose secret signed the payload). Instead, only `body-authenticity` is verified; `shop-header-authenticity` is `false` — the header is fully attacker-controllable independent of the HMAC. This is exactly the "field acted on but not covered by the HMAC" identity-binding break: `_accruedFeeShares` in the report used a formula that ignored a term it should have accounted for; here the gem's webhook trust model ignores that `shop` isn't part of what it cryptographically verified.

Any unprivileged internet user can trivially obtain a genuine, validly-signed `(raw_body, hmac)` pair by installing the app on a free/dev shop they control and receiving one legitimate webhook from Shopify. They can then replay that exact body+HMAC to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` for any victim `*.myshopify.com` domain (shop domains are not secret). `HmacValidator.validate` still succeeds because it never looks at that header, and `Registry.process` calls the app's handler with `WebhookMetadata#shop` set to the victim shop.

The gem's own documentation demonstrates the exact unsafe pattern host apps are told to use — persisting/acting on data keyed by `data.shop`: [5](#0-4) 
and explicitly states that `Registry.process` "will verify the request did indeed come from Shopify," which is misleading given `shop` is unverified: [6](#0-5) 

### Impact Explanation
Because `shop` (the tenant identifier) is not bound to the HMAC, an attacker who legitimately controls one shop can forge webhook deliveries that the host application will attribute to any other, unrelated shop. Following the gem's documented handler pattern, this lets the attacker inject attacker-chosen webhook bodies/topics into another tenant's data pipeline (e.g. triggering shop-scoped side effects, cache/DB writes, or business logic keyed by `data.shop`) without ever touching that victim's credentials — a cross-tenant access/data-integrity break, rated Critical per the given impact classes.

### Likelihood Explanation
High. No secrets, tokens, or privileged access to the victim are required — only a normal Shopify (dev/trial) shop the attacker owns to receive one legitimate signed webhook, and knowledge of the victim's public `*.myshopify.com` domain, which is not sensitive. The header substitution and replay require only basic HTTP tooling.

### Recommendation
Bind the tenant/topic identity into the signed payload validation instead of trusting the raw headers post-hoc:
- Include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified (or, at minimum, require the caller to supply the expected `shop` for the registered handler/session and reject if it disagrees with any independently-verified source, e.g. cross-check against the app's known list of installed shops before dispatching to the handler).
- Update `Utils::HmacValidator`/`VerifiableQuery` so `Webhooks::Request#to_signable_string` is not solely `@raw_body`, or add an explicit post-HMAC step in `Registry.process` that validates `request.shop` is one of the app's currently installed/authorized shops before invoking the handler.
- Update `docs/usage/webhooks.md` to clarify that `data.shop` is not covered by the HMAC and must be independently validated by the host application before being trusted for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on a shop they control, `attacker.myshopify.com`, and subscribes to any webhook topic (e.g. `app/uninstalled`).
2. Shopify sends a legitimate webhook to the app's endpoint:
   - Headers: `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: app/uninstalled`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - Body: `raw_body` (JSON)
3. Attacker captures this request (it is delivered to infrastructure they control).
4. Attacker resends the identical `raw_body` and `X-Shopify-Hmac-Sha256` value to the same webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses this successfully; `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only and it matches, so `Registry.process` does not raise `InvalidWebhookError`.
6. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim.myshopify.com", body: <attacker's body>, ...)` — as shown in `lib/shopify_api/webhooks/registry.rb` lines 190-199 — causing the host app (following the documented pattern of keying persistence off `data.shop`) to act on `victim.myshopify.com`'s tenant using attacker-controlled data.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
