### Title
Webhook shop/topic identity not covered by HMAC, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers to route and process a webhook, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body. Any party that can obtain one valid `(body, hmac)` pair signed with the app's shared secret — e.g. a merchant who installed the app and received a legitimate webhook to their own endpoint — can replay that body with a forged `shopify-shop-domain` (or `shopify-topic`) header and have the host application's webhook handler process it as if it came from a different shop/topic.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from headers and are never included in the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies the HMAC over `verifiable_query.to_signable_string`, i.e. the raw body: [3](#0-2) 

`Registry.process` performs this single check and then unconditionally trusts `request.shop` and `request.topic` to route the payload to a handler and construct `WebhookMetadata`: [4](#0-3) 

The equality the code implicitly relies on is:
`hmac_valid(body) == true` ⟺ `shop header is authentic for this body`

That equality does not hold: the HMAC secret (`api_secret_key`/`client_secret`) is shared across every shop that has installed the app, and the signature is computed over the body alone. Any shop/merchant that legitimately receives a webhook (and thus a valid `(body, hmac)` pair) can resend that exact body to the app's webhook endpoint with a different `shopify-shop-domain` header, and `HmacValidator.validate` will still return `true` because it never inspects the header. The resulting `WebhookMetadata.shop` handed to the app's handler is therefore an attacker-controlled, HMAC-unauthenticated value that can name any other tenant.

### Impact Explanation
This breaks the tenant boundary the gem's webhook signature check is supposed to enforce. A host application using `ShopifyAPI::Webhooks::Registry.process` and trusting `data.shop`/`data.topic` (as the documented API and generated `WebhookMetadata` encourage) can be made to apply a replayed payload to the wrong shop's records, or process a payload under a different topic than the one Shopify actually intended, all while `HmacValidator.validate` reports success. This is a cross-tenant integrity issue: one merchant of a multi-tenant app can forge webhook events attributed to another merchant, without ever needing the app's `client_secret` for the target shop (only a previously delivered, legitimately-signed body from a shop they control).

### Likelihood Explanation
Any developer/merchant who installs the app receives real webhook deliveries with valid HMACs computed against the app-wide secret. Capturing and replaying such a request with a modified `shopify-shop-domain` (and/or `shopify-topic`) header requires no special access beyond being a normal, unprivileged installer of the app — well within the "unprivileged internet user" threat model, since the check in `HmacValidator.validate` and `Registry.process` never binds shop/topic identity to the signature.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string (or otherwise cryptographically bind them to the payload) before computing/verifying the HMAC in `Utils::HmacValidator`/`Webhooks::Request`, so that any tampering with those headers invalidates the signature. At minimum, document that host applications must independently authenticate the shop associated with a webhook delivery (e.g., verify it against a shop that is actually installed/known) rather than trusting `WebhookMetadata#shop` as authenticated data.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook they control (e.g. `app/uninstalled`), capturing the raw request: body `B`, and headers including `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared secret) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same body `B` and `hmac` header `H` to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely over `B` and succeeds, since `H` matches.
4. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed(B), ...)`, causing the host app to process an attacker-forged event as if it originated from the victim shop.
