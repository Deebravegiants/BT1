### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body [1](#0-0) . The `shop` domain (and topic/api-version/webhook-id) used to build the `WebhookMetadata` handed to the app's handler is read straight from request headers and is never part of the signed content [2](#0-1) .

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [3](#0-2) , and `HmacValidator.validate` computes/compares the HMAC over that signable string only [4](#0-3) . Meanwhile, `Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no binding to the signature [5](#0-4) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler, then passes the unauthenticated `request.shop` value straight into `WebhookMetadata` given to the app: [1](#0-0) . The documented handler contract explicitly tells app authors to trust `data.shop` as "The shop domain of the webhook" and use it to route/attribute the payload [6](#0-5) .

This breaks the identity binding: `shop-header-value == shop-that-authored-the-signed-body`. Concretely: `HMAC-verified(body) == true` does **not** imply `request.shop == body-owning-shop`. An attacker who has installed the same public app on their own (self-service, no special privilege) development store will legitimately receive a validly-signed webhook for their own shop and body. Because the header carrying the shop domain is not part of the signed payload, the attacker can replay that same body+HMAC pair directly to the app's public webhook endpoint while substituting an arbitrary victim `x-shopify-shop-domain` header value. `HmacValidator.validate` still succeeds (it never inspects headers), and `Registry.process` dispatches the handler with `shop: <attacker-chosen victim domain>` and `body: <attacker's own webhook payload>` [7](#0-6) .

### Impact Explanation
Any app implementation that follows the gem's documented pattern (using `data.shop` to look up the tenant's session/config and apply `data.body` to that tenant, as shown in the gem's own example handler) can be made to process attacker-controlled webhook data under an arbitrary victim shop's identity. This is a cross-tenant confusion/data-injection vector satisfying the "cross-tenant access" Critical impact category, since no credentials belonging to the victim, TLS interception, or leaked secrets are required — only the ability to self-install the app on any shop (a normal unprivileged action for any internet user with a free/dev Shopify store).

### Likelihood Explanation
Moderate-to-high: exploitation requires only that the attacker obtain one legitimately signed webhook for a shop they control (trivial via self-installation) and then send a raw HTTP POST to the app's public webhook route with a forged shop-domain header — no interaction with or credentials from the victim are needed. It depends on the host application trusting `data.shop` per the gem's own documented contract, which is the exact behavior the library's docs instruct developers to rely on.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed material, or otherwise cryptographically bind them, e.g. change `Request#to_signable_string` to incorporate `shop`, `topic`, and `webhook_id` alongside the raw body, and update `HmacValidator`/webhook signing verification accordingly. At minimum, document prominently that `data.shop` is unauthenticated and must be cross-checked against the app's known/registered shop list (or the webhook subscription id looked up via `Registry.get_webhook_id`) before being trusted, since the current documentation instructs the opposite.

### Proof of Concept
1. Attacker installs the app on their own Shopify dev store `attacker.myshopify.com` and captures a legitimate webhook: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC-SHA256(api_secret_key, B)`).
2. Attacker POSTs to the target app's public webhook endpoint:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: H
   x-shopify-shop-domain: victim-shop.myshopify.com   <-- forged
   Body: B
   ```
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Utils::HmacValidator.validate(request)` succeeds because it only re-derives `H` from `B` [8](#0-7) .
4. `Registry.process` invokes the app handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's own order data>, ...)` [7](#0-6) , and the app (following the documented pattern) processes/attributes attacker data to the victim tenant.

Note: this analysis is based on the indexed library source; some auxiliary files (e.g., full `docs/usage/webhooks.md`, `client_credentials.rb`, `refresh_token.rb`) were only partially inspected, so if additional shop-binding logic exists elsewhere in the host integration guidance not captured here, it should be verified directly in a full checkout.
