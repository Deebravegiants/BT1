### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [2](#0-1) , while the `shop` attribute used to identify the tenant is read directly from an HTTP header that is never included in the signed material [3](#0-2) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` (which checks the body against the HMAC) and then dispatches to the handler using the unauthenticated `request.shop` value [4](#0-3) .

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, body || shop || topic)`, i.e., the shop the handler believes the webhook is "for" should be cryptographically bound to the same signature that authenticates the payload. In this implementation, that binding is broken: `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` [5](#0-4) , and for `Webhooks::Request`, `to_signable_string` is just `@raw_body` [2](#0-1) . The `shop`, `topic`, `api_version`, and `webhook_id` values are all pulled from headers (`shopify_header`) that are completely outside the signed scope [6](#0-5) .

Because any unprivileged internet user can POST directly to the app's public webhook endpoint (this is the same endpoint Shopify calls), an attacker who is able to obtain one valid `(body, hmac)` pair — for example by installing the app on their own store and capturing a genuine webhook Shopify sends them — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. `HmacValidator.validate` will still return `true`, because it never inspects the shop header [7](#0-6) , and `Registry.process` will hand the forged `WebhookMetadata` (with the victim's shop, but attacker-controlled body content) straight to the app's handler [4](#0-3) .

This directly matches the documented gem behavior/expectation that `process` "will verify the request did indeed come from Shopify" [8](#0-7)  and that `data.shop` is a trustworthy field describing "the shop domain of the webhook" [9](#0-8)  — the library's own documented contract implies shop identity is verified as part of `process`, but the implementation only authenticates the body bytes, not the shop binding.

### Impact Explanation
This is a High severity cross-tenant issue: a handler that uses `data.shop` to key persistence/session lookups (the documented and expected usage pattern, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)` shown in the docs example) can be tricked into associating a captured, HMAC-valid webhook body with an arbitrary victim shop domain. Depending on the webhook topic, this can lead to cross-tenant data corruption (e.g., forging an `app/uninstalled` event to make the app tear down a victim shop's session/data, or injecting attacker-chosen body content attributed to a victim shop).

### Likelihood Explanation
Exploitation requires the attacker to first obtain one legitimate `(raw_body, hmac)` pair signed with the app's secret. The easiest way to do this is to install the target app on an attacker-controlled shop (many apps are freely installable on any dev/trial store) and capture a webhook Shopify sends for that shop, then replay it with a forged shop header. This does not require the app's `client_secret` or a leaked access token — it only requires the ability to trigger and observe a normal webhook. This is a realistic path for an unprivileged internet user with a Shopify Partner/dev account, moderate likelihood.

### Recommendation
Bind the shop domain (and ideally topic/webhook id) into the signed material, not just the raw body — since Shopify's webhook HMAC is computed only over the body per Shopify's spec, the gem should instead require callers to independently verify that `request.shop` corresponds to a shop for which the app has an active, previously-established session/installation before trusting it, and should document this requirement prominently instead of implying `process` fully "verifies the request did indeed come from Shopify" including its shop attribution. At minimum, update the documentation to clarify that only the body is HMAC-verified and that `data.shop` must be cross-checked by the host application against known installed shops before being trusted for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and lets it register a webhook (e.g., `orders/create`).
2. Shopify sends the attacker a legitimate webhook: `raw_body = B`, header `x-shopify-hmac-sha256 = H` (valid HMAC of `B`), header `x-shopify-shop-domain = attacker-shop.myshopify.com`.
3. Attacker POSTs to the same app's public webhook endpoint with body `B`, header `x-shopify-hmac-sha256 = H` unchanged, but header `x-shopify-shop-domain = victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this successfully [10](#0-9) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which returns `true` because it only checks `B` against `H` [11](#0-10) .
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` [12](#0-11) , causing the app to process attacker-supplied body content under the victim shop's identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
