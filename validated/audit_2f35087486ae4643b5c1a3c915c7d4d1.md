### Title
Webhook `shop` (and `topic`) identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC only over the raw request body, while the `shop`, `topic`, and `webhook_id` values are read directly from unauthenticated HTTP headers and passed on to the app's handler as trusted identifiers. Nothing in the verification path binds the tenant identity (`shop`) to the signature, so a party who legitimately receives one validly-signed webhook (e.g. for their own store) can replay it with a forged `shopify-shop-domain` header and have it accepted as coming from a different merchant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and the HMAC comparison in `HmacValidator.validate_signature` is computed exclusively over that signable string: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors simply read from headers that are entirely outside the HMAC's scope: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` (and `request.topic`) to construct the `WebhookMetadata` object handed to the app's business-logic handler — there is no check that the signed body's origin actually corresponds to the claimed shop: [3](#0-2) 

The identity binding that should hold is:
`shop asserted by the HMAC-signed payload == shop the handler acts on`

But the actual binding enforced by the code is only:
`HMAC(raw_body, api_secret_key) == received_hmac`

with `shop` completely decoupled from that check. Any entity capable of triggering one legitimately-signed webhook delivery to itself (e.g., a merchant who has installed the app on their own store, or anyone who otherwise obtains a single valid `(body, hmac)` pair for a known topic) can resend that exact body/HMAC pair while substituting an arbitrary `shopify-shop-domain` header value. `Registry.process` will still accept it as authentic and dispatch it to the handler tagged with the attacker-chosen `shop`, breaking the tenant boundary the handler relies on to scope data access (e.g. looking up sessions, orders, or customer data "for that shop").

### Impact Explanation
This lets an attacker with legitimate access to at least one real, signed webhook (from their own installed store) impersonate an arbitrary other merchant to the app's webhook handler, since the only cryptographic guarantee provided by this library — the HMAC — never covers the `shop` field the handler is told to trust. Depending on what the consuming application does with `WebhookMetadata#shop` (commonly used to resolve the tenant's session/access token or to write data under that tenant), this can lead to cross-tenant data access or corruption, which maps to a Critical-tier "cross-tenant access" impact.

### Likelihood Explanation
Any actor who can get the app installed on a shop they control (a normal, low-privilege action for anyone using the Shopify App Store or a dev store) can trigger real webhook deliveries for themselves and capture a valid `(raw_body, hmac)` pair for a topic of interest. Replaying that pair with a different `shopify-shop-domain` header requires no secret material at all, since this gem's `HmacValidator` and `Registry.process` never check that the header matches the entity that produced the signed body.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the HMAC verification, e.g. include these header values as part of the signable string computed by `Request#to_signable_string`, or independently verify that the shop domain in the header corresponds to a shop with an active, matching session/installation before constructing `WebhookMetadata`. At minimum, document and enforce that `request.shop` must not be treated as authenticated unless it is cross-checked against a value that is cryptographically tied to the signed payload.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) for their own shop, capturing the request body `B` and the resulting header `x-shopify-hmac-sha256: H` (a valid HMAC of `B` under the app's shared `api_secret_key`).
2. Attacker resends this exact body `B` and header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` builds the request object from these headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(B, secret) == H` — see [4](#0-3) .
4. `Registry.process` then builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the forged `shop` value and dispatches it to the app's handler as if it were an authentic webhook for `victim-shop.myshopify.com` — see [5](#0-4) .
