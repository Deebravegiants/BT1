### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` (and `topic`, `webhook_id`, `api_version`) from unauthenticated HTTP headers, while `Utils::HmacValidator` only verifies the HMAC over the raw body via `to_signable_string`. `Registry.process` trusts `request.shop` as the tenant identity handed to the app's handler without it ever being covered by the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `shop`, `topic`, `webhook_id`, `api_version` are all read directly from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` computes the HMAC solely over `verifiable_query.to_signable_string`, i.e. the raw body for webhook requests: [3](#0-2) 

`Registry.process` then raises only if the HMAC over the body is invalid, and otherwise passes `request.shop` straight into `WebhookMetadata` as the authoritative tenant identifier delivered to the app's handler: [4](#0-3) 

The identity binding that should hold is: `HMAC-verified bytes == bytes the tenant decision is made from`. Here it is broken: the HMAC only covers the body, but the `shop` header — which the app's own documentation instructs developers to treat as "The shop domain of the webhook" and use directly to key their persistence/session lookup — is outside that signed scope: [5](#0-4) 

Because any Shopify merchant can freely create a development/trial store and receive genuinely-signed webhooks for that store (a valid HMAC over some body B, signed with the app's real `client_secret` by Shopify's own webhook delivery for that shop), an attacker who controls their own shop can capture a legitimately-signed webhook request and simply replace the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header before replaying it to the target app's webhook endpoint. Since the signature check only re-verifies the unchanged body, the forged headers pass validation, and the handler is invoked believing the event belongs to a different (victim) tenant.

### Impact Explanation
This crosses the tenant boundary: an unprivileged internet user who owns any Shopify store (no access token, no `client_secret`, no privileged account needed) can inject webhook events attributed to an arbitrary victim `shop` domain into apps that rely on `data.shop` for tenant-scoped side effects (e.g., updating a shop's local order/inventory records, triggering billing logic, revoking/granting entitlements keyed by shop). This matches the Critical bucket for cross-tenant access.

### Likelihood Explanation
Likelihood is high for any app that follows this gem's own documented pattern of trusting `data.shop` from `WebhookMetadata`: [6](#0-5)  The only prerequisite is possessing one genuinely Shopify-signed webhook (trivially obtainable by installing the target app on an attacker-owned store, or any store subscribed to the relevant topic), then replaying it with a modified `shop-domain` header — no secret or privileged credential is required.

### Recommendation
Bind the tenant-identifying headers into the signed payload verification, e.g. construct the HMAC-signable string from `shop-domain || topic || webhook-id || raw_body` (or otherwise cryptographically bind these headers to the signature check) in `Request#to_signable_string`/`HmacValidator`, so that any header substitution invalidates the HMAC. At minimum, `Registry.process` should refuse to trust `request.shop` unless it can be shown to have been covered by the verified signature.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and subscribes to a registered topic (e.g. `orders/create`).
2. Shopify delivers a genuine webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw body B>`, and body `B`.
3. Attacker captures this request and replays it to the same endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com`, leaving `raw_body` (`B`) untouched.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `to_signable_string` (`= @raw_body`) — unchanged — so validation succeeds: [7](#0-6) 
5. `Registry.process` invokes the handler with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"`, and the app performs tenant-scoped actions against the victim shop's record.
