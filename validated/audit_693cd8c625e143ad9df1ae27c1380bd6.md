## Title
Webhook `shop` (and other Shopify-supplied headers) are not covered by the HMAC signature, allowing a legitimate merchant to replay their own valid webhook payload while impersonating a victim shop - (File: `lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Request` derives `topic`, `shop`, `api_version`, and `webhook_id` from HTTP headers, but the HMAC signature that `ShopifyAPI::Utils::HmacValidator` verifies is computed **only over the raw request body**. The `shop` value that `ShopifyAPI::Webhooks::Registry.process` hands to the app's handler (and that the app uses as the tenant identifier for the event) is therefore never bound to the cryptographic proof of authenticity.

## Finding Description
`Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the HMAC exclusively from `to_signable_string`, i.e. the body: [2](#0-1) 

`Registry.process` only checks this body-bound HMAC before dispatching the event to the app-provided handler, passing `request.shop` (read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header) as the tenant identifier for the event, with no additional check that this header was itself covered by the signature: [3](#0-2) 

Because the HMAC secret (`Context.api_secret_key`) is the app's single client secret, shared across every shop that has installed the app, any merchant who has installed the app can receive real, validly-signed webhooks for their **own** store. The `hmac-sha256` header from that legitimate delivery remains valid for the same body regardless of which `shop-domain` header accompanies it, since the header is never part of the signed content.

**Identity binding broken (as equality):**
`shop_authenticated_by_hmac` (implicitly: "the shop that legitimately triggered this signed body") ≠ `shop_used_for_tenant_attribution` (`request.shop`, taken from an unsigned header and trusted directly by `Registry.process`/the app's handler).

## Impact Explanation
An unprivileged merchant who has installed the target app can:
1. Trigger a real Shopify event on their own store (e.g. `orders/create`) to receive a validly HMAC-signed webhook body from Shopify.
2. Replay that exact body (with its still-valid HMAC) to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. `Registry.process` accepts the request (`HmacValidator.validate` only checks the body) and dispatches `WebhookMetadata.new(shop: "<victim>.myshopify.com", body: <attacker's own data>, ...)` to the app's handler.

Depending on what the app's webhook handler does with `shop` (creating/upserting records, triggering fulfillment, provisioning, syncing data, etc.), this allows cross-tenant data injection/corruption attributed to a shop the attacker does not control — a cross-tenant access violation.

## Likelihood Explanation
Any merchant who has installed the app already satisfies the only precondition (a store that receives real webhooks from Shopify for the app). No access to `api_secret_key`, tokens, or the victim's credentials is required — only capturing one legitimate webhook delivery to their own shop and replaying it with a modified header, which is trivial for anyone who can install the app and control a test store.

## Recommendation
Include the identifying headers (`shop`, `topic`, `api_version`, `webhook_id`) in the signed/verified material, or independently verify that `request.shop` corresponds to a shop with a known, currently-authorized installation/session before trusting it for tenant attribution. At minimum, document/require host applications to cross-check `request.shop` against their own installed-shop record rather than trusting the header implicitly, and/or extend `to_signable_string`/`HmacValidator` to bind the shop header into the computed digest so a body signed for one shop cannot be replayed under another shop's identity.

## Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the app.
# Step 1: capture a real webhook delivery Shopify sends to the app for their own shop.
captured_body = '{"id": 1, "note": "malicious payload"}'
captured_hmac = "shopify-generated-valid-hmac-for-captured_body"  # valid for api_secret_key

# Step 2: replay the same body+hmac but swap the shop-domain header to the victim's shop.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_hmac,       # still valid: HMAC only covers raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # attacker-controlled, unsigned
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)

# HmacValidator.validate(request) returns true, because it only checks captured_body's HMAC.
ShopifyAPI::Webhooks::Registry.process(request)
# -> app's handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker's captured_body, ...)
```
