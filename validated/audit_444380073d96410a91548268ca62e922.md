### Title
Webhook shop-domain header is not bound by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` value later handed to the application's webhook handler is read from an HTTP header that is never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` (`shop-domain` header) and `topic` are separate accessors that read directly from the unauthenticated headers hash and are never mixed into `to_signable_string`: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` — which calls `verifiable_query.to_signable_string` (i.e. only the raw body) — and, once that passes, immediately constructs `WebhookMetadata` using `request.shop`, which was never covered by the signature: [4](#0-3) 

`HmacValidator.validate`/`validate_signature` compute the HMAC purely from `verifiable_query.to_signable_string` and the app's `api_secret_key`: [5](#0-4) 

Because the HMAC secret (`api_secret_key`/`client_secret`) is identical for every shop that has installed a given app, and the signature covers only the request body, an unprivileged attacker who legitimately installs the target app on their own store can capture a genuine webhook (valid body + valid HMAC) that Shopify sends to their own store's endpoint. They can then replay the exact same body and HMAC header to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` (the body/HMAC pair is genuinely valid), and `Registry.process` forwards `WebhookMetadata` with `shop: <victim shop>` to the host application's handler — an equality break between "shop whose secret authenticated the payload" (the attacker's own shop, since the key is app-wide, not shop-specific) and "shop the application believes it received data for" (`request.shop`, an unauthenticated header value).

### Impact Explanation
This breaks tenant isolation for any application logic keyed on `WebhookMetadata#shop` (e.g., writing order/customer/inventory data associated with the spoofed shop, triggering `shop/redact` or `customers/redact` GDPR flows against an arbitrary shop, or invalidating/mutating another tenant's stored state). This is cross-tenant access/data confusion driven entirely by the gem's own trust decision (treating HMAC success as authentication of `request.shop`), matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Any developer or attacker can install the app on a store they control (an "unprivileged internet user" from the platform's perspective), receive a real webhook with a valid signature, and replay it with a modified shop header to the app's internet-facing webhook endpoint. No possession of the merchant's or app's real secrets for the *victim* shop is required — only a body/HMAC pair valid under the app's single shared secret, which the attacker obtains for free via their own installation.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header into the material that is HMAC-verified, or otherwise cross-check the header-derived `shop` against an independently trusted source (e.g., validate that the shop is one the application has an active, matching installation/session for) before dispatching `WebhookMetadata` to handlers. At minimum, document and enforce that `request.shop` must not be trusted as an authenticated identity unless additional shop-specific verification is performed.

### Proof of Concept
1. Install the target Shopify app on attacker-owned store `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the raw POST: body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC-SHA256(api_secret_key, B)`).
2. Replay to the app's public webhook endpoint:
```
POST /webhooks HTTP/1.1
x-shopify-topic: orders/create
x-shopify-hmac-sha256: H
x-shopify-shop-domain: victim-shop.myshopify.com
x-shopify-webhook-id: <any>
x-shopify-api-version: <any>

B
```
3. `Utils::HmacValidator.validate` succeeds because `to_signable_string` only checks `B`/`H`. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the application to process attacker-controlled data under the victim shop's identity.         def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
