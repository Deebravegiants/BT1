### Title
Unbounded in-memory recursive collection of execution outcomes in `get_recursive_transaction_results` enables attacker-triggered high memory usage / RPC-node resource exhaustion - (File: `chain/chain/src/chain.rs`)

### Summary
`Chain::get_recursive_transaction_results` recursively walks every receipt spawned (directly or indirectly) by a transaction and pushes each `ExecutionOutcomeWithIdView` into a single `Vec` with no depth or size cap, then materializes the whole vector into a `FinalExecutionOutcomeView`/`FinalExecutionOutcomeWithReceiptView` response. This is directly analogous to the BtcPoller `Bootstrap` bug: a loop that accumulates an attacker/user-influenced amount of data into memory before ever returning/committing, with no batching or cap, driven by data that is not size-limited at the point of collection.

### Finding Description
`get_recursive_transaction_results` (`chain/chain/src/chain.rs:3190`) recurses over `outcome.receipt_ids` for every outcome found, appending each to a shared `outcomes: &mut Vec<ExecutionOutcomeWithIdView>` with no limit on the number of entries collected: [1](#0-0) 

This function is invoked by `get_final_transaction_result` and `get_partial_transaction_result_option`, both of which allocate `let mut outcomes = Vec::new();` and hand it straight to the unbounded recursive collector before returning the full result to the caller: [2](#0-1) [3](#0-2) 

These are reachable from the public, unauthenticated JSON-RPC surface via the `ViewClientActor::get_tx_status` handler (used by `EXPERIMENTAL_tx_status`/`tx` RPC methods and by `broadcast_tx_commit`/`send_tx_commit` polling), which calls `chain.get_partial_transaction_result_option` on every poll of a submitted transaction's status: [4](#0-3) 

Unlike the analogous receipt-lookup paths that were clearly hardened against unbounded growth in this codebase (e.g., `resolve_receipt_via_hint`'s explicit `remaining_budget`/`BudgetExceeded`, `view_state`'s `MAX_VIEW_STATE_PAGE_ITEMS`/byte cap, and `view_access_keys`' `access_keys_limit`), `get_recursive_transaction_results` has no analogous cap on the number of outcomes it will collect or on the depth of the receipt DAG it will traverse: [5](#0-4) [6](#0-5) 

A NEAR smart contract is able to fan out a single transaction into an arbitrarily large number of receipts via nested cross-contract calls/promises (each `FunctionCall` action can create new receipts, which in turn can create more, up to the block gas limit per block, but across many blocks a single originating transaction's receipt DAG can still grow into many thousands of nodes over its lifetime, especially when combined with yield/resume or repeated self-calls that keep spawning new receipts). Every node in that DAG, and every outcome view returned via `EXPERIMENTAL_tx_status` while the transaction is still in flight, is retained in memory in a single `Vec` per RPC call with no early cutoff — mirroring the BtcPoller pattern of accumulating everything before ever returning/limiting.

### Impact Explanation
Repeated or large `tx_status`/`broadcast_tx_commit` requests against a transaction whose promise/receipt tree is deliberately made very large (an attacker-controlled contract designed to fan out many self-calls or long receipt chains) force the RPC-serving node (`ViewClientActor`, which serves untrusted RPC/API traffic) to build and serialize an unbounded `Vec<ExecutionOutcomeWithIdView>` per request. This is a node-resource-exhaustion / potential-crash primitive reachable purely by submitting transactions and polling their status — the same class of bug as the BtcPoller `Bootstrap` OOM (unbounded accumulation before any limiting/commit step), scoped here to unprivileged transaction/RPC interaction rather than validator or P2P behavior.

### Likelihood Explanation
Likelihood is limited by real-world constraints: each block's gas limit bounds how many receipts a single chunk application can process, and honest usage rarely produces huge receipt trees for one transaction. However, an adversarial contract deployed by any account (no special privileges needed) can be crafted to intentionally maximize `receipt_ids` fan-out/depth for a transaction it controls, and then repeatedly poll `EXPERIMENTAL_tx_status`/`broadcast_tx_commit` on public RPC endpoints to force repeated unbounded collection work, making exploitation practically feasible without validator or node-operator cooperation.

### Recommendation
Bound `get_recursive_transaction_results` the same way other outcome-serving paths in this codebase were hardened: introduce a maximum outcome count (and/or maximum recursion depth) analogous to `RECEIPT_TO_TX_MAX_DEPTH` / `receipt_to_tx_max_outcomes_per_request`, and return a defined error (e.g. `TooManyOutcomes`/`DepthExceeded`) once the cap is hit rather than continuing to accumulate. Consider converting the recursive push into an iterative worklist with an explicit cap so the collected `Vec` can never grow unbounded regardless of how large the underlying receipt DAG is, and reject/paginate `tx_status`/`broadcast_tx_commit` responses beyond that cap.

### Proof of Concept
1. Deploy a contract whose method, when called, issues a `FunctionCall` receipt to itself with a callback, chained recursively (or via yield/resume) so that a single originating transaction hash accumulates a very large `receipt_ids` DAG over many blocks.
2. Submit the transaction via `broadcast_tx_async`.
3. Repeatedly call `EXPERIMENTAL_tx_status` (or `tx`/`broadcast_tx_commit`) for that transaction hash against a public RPC node while the receipt tree keeps growing; each call triggers `get_partial_transaction_result_option` → `get_recursive_transaction_results`, which walks and materializes the entire (attacker-grown) outcome set into memory with no size limit, unlike the capped `resolve_receipt_via_hint`/`view_state`/`view_access_keys` paths in the same codebase.

        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
        id: &CryptoHash,
        require_all_outcomes: bool,
    ) -> Result<(), Error> {
        let outcome = match self.get_execution_outcome(id) {
            Ok(outcome) => outcome,
            Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
        };
        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;
        for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }
