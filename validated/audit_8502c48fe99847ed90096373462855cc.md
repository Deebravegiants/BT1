### Title
Permissionless `CallDispatcher.dispatch()` allows any unprivileged caller to drain funds momentarily or residually held by the shared dispatcher contract - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch(bytes)` has no access control whatsoever — any address can call it directly to make the dispatcher execute an arbitrary, caller-supplied `Call[]` array against arbitrary targets, using the dispatcher's own identity, native-ETH balance, and any ERC20 balance it happens to be holding. This mirrors the Moonhacker root cause: a function meant to be invoked only as part of a trusted, choreographed flow (an Aave `executeOperation` callback there, an `IntentGatewayV2`/`HyperFungibleToken` predispatch/postdispatch step here) instead accepts and blindly executes attacker-controlled operation parameters with no validation of who is calling or why, letting an outsider redirect value that the contract is holding. [1](#0-0) 

### Finding Description
`CallDispatcher` is a single shared singleton contract used by `IntentGatewayV2` (predispatch/postdispatch calldata execution) and `HyperFungibleToken`/`WrappedHyperFungibleToken` (`onAccept` calldata execution) across every deployment on a chain: [2](#0-1) 

`dispatch()` decodes the `Call[]` and executes each entry with `to.call{value: call.value}(call.data)` — the only checks are that `to` has code and that the call succeeds. There is no `onlyGateway`/`onlyHost`/`msg.sender` restriction of any kind: [3](#0-2) 

The contract also has a `payable receive()`, so it explicitly accepts native ETH: [4](#0-3) 

Both `IntentGatewayV2.placeOrder` (predispatch) and `IntentsBase._execute` (postdispatch) route tokens through this dispatcher and then issue a second `dispatch()` call to sweep the resulting balance back to the gateway, based on a `balanceOf(dispatcher)` snapshot taken before the user-supplied predispatch/output calldata runs: [5](#0-4) [6](#0-5) 

The sweep logic only transfers back the balance of the specific `order.inputs`/`order.output.assets` tokens that the order declares. Any other asset that ends up sitting in the dispatcher — a reward/airdrop token returned by a DEX swap invoked from `predispatch.call`/`output.call`, a stray ERC20 the caller forgot to enumerate, excess native ETH left after a swap whose output token wasn't the one accounted for, or simply someone mistakenly sending ETH to the dispatcher's `receive()` — is never reclaimed by the gateway and instead sits in the shared, permissionless `CallDispatcher`. The documentation itself acknowledges the dispatcher "holds tokens temporarily during execution" and warns against unlimited allowances in `Call[]`, confirming the authors are aware value can transiently or residually sit there: [7](#0-6) 

Because `dispatch()` is callable by anyone, any such residual balance (native ETH or ERC20) is immediately and permanently sweepable by any unprivileged third party — they simply call `CallDispatcher.dispatch(abi.encode([Call({to: attacker, value: dispatcher.balance, data: ""})]))` for ETH, or the analogous `transfer` call for an ERC20 the dispatcher holds. This is the same class of bug as Moonhacker: a function that performs privileged, value-moving operations based purely on attacker-supplied parameters, without verifying that the caller is part of the legitimate, expected flow.

### Impact Explanation
Any native ETH or ERC20 tokens that land in `CallDispatcher` outside of the exact tokens a given order's `predispatch`/`output` step accounts for become permanently and immediately stealable by any address, since the contract is shared across all intent orders and all HFT bridge deliveries on a chain. This is a direct, unbacked loss of funds for whichever user or protocol integration caused (or was caused to cause, e.g. via a swap route returning an unexpected token/dust) the residual balance, and it also creates a race: even funds that are supposed to be swept back atomically within a transaction are only safe because Solidity execution is single-threaded within a transaction — any legitimate flow that leaves so much as a wei of an unaccounted-for asset in the dispatcher hands it to whoever calls `dispatch()` first afterward.

### Likelihood Explanation
`dispatch()` requires no privilege, no proof, and no relationship to any specific order or app — it is directly callable by any EOA or contract at any time. The likelihood of some non-zero, non-swept balance accumulating in the dispatcher is realistic given the documented dust/allowance caveat, arbitrary DEX-routing calldata solvers and users are allowed to supply in `predispatch.call`/`output.call`, and the fact that the sweep logic only targets the declared input/output token set, not "everything the dispatcher now holds."

### Recommendation
Restrict `CallDispatcher.dispatch()` to an allowlisted set of callers (the registered `IntentGatewayV2`/`HyperFungibleToken` instances that are expected to use it), or make each deployment app-specific rather than a shared singleton. Additionally, make the sweep step generic — sweep the dispatcher's full balance of every token actually touched during predispatch/postdispatch execution (not just the tokens declared in the order) back to the gateway/user before returning control, so no residual balance can ever be left behind for a third party to claim.

### Proof of Concept
1. A solver fills or a user places an order whose `predispatch.call`/`output.call` routes through a DEX that returns an unexpected reward token, or simply sends slightly more native ETH to the dispatcher than the declared output asset accounts for (e.g., a swap with rounding, or a protocol that also emits an airdrop token to the caller of the swap, which is the `CallDispatcher`).
2. `IntentGatewayV2`/`IntentsBase` sweeps back only the declared `order.inputs`/`order.output.assets` tokens; the extra token/ETH remains in `CallDispatcher`.
3. Any unrelated third party calls:
```solidity
CallDispatcher(dispatcher).dispatch(
    abi.encode([Call({to: attacker, value: address(dispatcher).balance, data: ""})])
);
```
or the ERC20 equivalent, transferring the residual balance to themselves — `dispatch()` performs no caller check and executes the call unconditionally. [3](#0-2)

/**
 * @title The CallDispatcher
 * @author Polytope Labs (hello@polytope.technology)
 *
 * @notice This contract is used to dispatch calls to other contracts.
 */
contract CallDispatcher is ICallDispatcher {
    /**
     * @dev error thrown when the target is not a contract.
     */
    error NotContract(address target);

    /**
     * @dev error thrown when a call fails.
     */
    error CallFailed(address target, bytes result);

    /**
     * @dev Receive function to accept ETH transfers
     */
    receive() external payable {}

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
