### Title
Single-step `transferCreator` can permanently strand future creator fees at an unrecoverable address - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.transferCreator` reassigns the fee-attribution role for a launched token in one irreversible call, with no acceptance step and no way to validate that the new address can actually operate on-chain.

### Finding Description
`Bonding.transferCreator` only checks for the zero address and that the new value differs from the current creator before writing `info.creator = newCreator` directly: [1](#0-0) 

This is the same "no transfer ownership pattern" bug class as the referenced report: a privileged role is moved with a single state write and no `acceptCreator()`/`pendingCreator` confirmation step. The protocol is clearly aware of this exact risk class — `FeeVault`, which is `Ownable2StepUpgradeable`, documents in its own header comment that a single-step transfer "to a fat-fingered or contract-incompatible address would otherwise brick every owner-only path on the live proxy," which is precisely why the protocol-owner role uses the two-step pattern there: [2](#0-1) 

`transferCreator`, however, was never given the same protection, even though `info.creator` is not just cosmetic — it is the sole key `FeeVault` uses to route ongoing fee accrual: [3](#0-2) 

Claims are pull-based and keyed strictly off `msg.sender`: [4](#0-3) 

Because `transferCreator` requires `msg.sender == info.creator` to call it again, once the role is moved to an address that cannot originate transactions (a typo'd address, an incompatible contract, a burn-style address, etc.) there is no path — permissioned or permissionless — to recover or redirect it. Every subsequent buy/sell on that token routes its 0.25% creator fee into `FeeVault.creatorBalance[newCreator]` for an address nobody controls, and `lifetimeCreatorEarned` for that token permanently reflects unclaimable funds.

### Impact Explanation
Once the creator role is set to an unreachable address, all past and future accrued creator fees for that token (`FeeVault.creatorBalance[newCreator]`) become permanently frozen — no owner override, no timelock/rescue path, and no way for the original or any other party to reclaim them via `Bonding.transferCreator` (since the caller-check requires the now-inaccessible address to initiate it). This is a direct, permanent freezing of creator funds, matching the report's "onlyOwner" impact but here manifesting as trapped USDC fee revenue in `FeeVault` rather than a bricked admin role.

### Likelihood Explanation
`transferCreator` is a fully permissionless, single-argument call reachable by any token creator at any time, so the only barrier to triggering the issue is human error (fat-fingering an address, pasting a non-EOA/incompatible contract, or copy-paste mistakes) — the same likelihood profile as the original finding, and a class of error that is common in practice.

### Recommendation
Convert `Bonding.transferCreator` to a two-step pattern: a `nominateCreator(token, newCreator)` call by the current creator sets a `pendingCreator[token]`, and a separate `acceptCreator(token)` call by `pendingCreator[token]` finalizes `info.creator = pendingCreator[token]`. This mirrors the `Ownable2StepUpgradeable` pattern already used elsewhere in the codebase (`FeeVault`, `Bonding`'s own admin owner) and prevents an unrecoverable mis-transfer of the fee-attribution role.

### Proof of Concept
1. Creator launches a token via `Bonding.launch`/`Zap.createToken`, accruing fees to `info.creator` in `FeeVault.creatorBalance`.
2. Creator calls `Bonding.transferCreator(tokenAddress, newCreator)` with `newCreator` mistyped or set to a contract address that cannot call `FeeVault.claim()` / `Bonding.transferCreator` again.
3. Trading continues; every subsequent `Zap.buy`/`Zap.sell` calls `FeeVault.accrue(token, newCreator, ...)`, growing `creatorBalance[newCreator]`.
4. No account can call `claim()` as `newCreator`, and no account can call `transferCreator` again (the check `msg.sender != info.creator` reverts with `NotCreator`), so the accrued and all future creator fees for this token are permanently unclaimable.

    function transferCreator(
        address tokenAddress,
        address newCreator
    ) external {
        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
    }
```

    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }
```

        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
