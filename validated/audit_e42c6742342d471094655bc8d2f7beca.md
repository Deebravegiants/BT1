## Title
Emporium `runAction` "Stateless Interaction" branch allows draining tokens that are not included in `circomData.erc20TokenAddresses`, bypassing the balance-equality check — (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` performs an unrestricted low-level call (`op.endpoint.call{value: op.value}(op.callData)`) whenever `stack.signerAddress == address(0)` (the "Stateless Interaction" case). The only guard on this call is a selector blacklist against `callHinkalWallet`/`doSendToRelay`; the target `endpoint` and `callData` are otherwise fully attacker-controlled and are only committed to by the caller's own ZK proof, not validated against any allow-list. Because the post-call solvency check only iterates over the tokens listed in `circomData.erc20TokenAddresses` for that specific transaction, any user can direct the Emporium contract to `transfer` out ERC-20 tokens that belong to other users/pending balances but are simply not named in their own `erc20TokenAddresses` array, and the theft is invisible to the balance-change accounting.

### Finding Description
In `runAction` [1](#0-0) , the "Stateless Interaction" branch performs:
```solidity
bytes4 selector = bytes4(op.callData);
if (selector == IHinkalWallet.callHinkalWallet.selector || selector == IHinkalWallet.doSendToRelay.selector) {
    revert UnauthorizedWalletCall();
}
(success, err) = op.endpoint.call{value: op.value}(op.callData);
```
`op.endpoint` and `op.callData` come from `EmporiumStack.ops`, which is `abi.decode`d from `circomData.externalActionData.externalActionMetadata` [2](#0-1) . This metadata is opaque application data — it is bound only by `calldataHash` (as part of `circomData.externalActionData`) [3](#0-2)  and is never checked against a target/selector allow-list beyond the two wallet-specific selectors.

The post-call solvency check only measures balances for the caller-supplied `circomData.erc20TokenAddresses` list:
```solidity
for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
    int256 balanceChange = int256(balancesAfter[i]) - int256(balancesBefore[i]);
    ...
    if (balanceChange < 0) revert BalanceChangeShouldBePositive();
}
``` [4](#0-3) 

Since the caller fully controls `erc20TokenAddresses` (it is just another field committed by their own proof, not derived from what tokens actually exist on the Emporium contract), an attacker can simply omit any token they intend to drain from that array. The arbitrary call in the loop can then target `TokenX.transfer(attacker, amount)` where `TokenX` is a token currently held by the Emporium contract on behalf of other users (deposited via prior legitimate transactions and not yet withdrawn/converted), while `erc20TokenAddresses` for the attacker's own transaction lists an unrelated (or empty-change) token. The balance equation `balanceChange = after - before` is never evaluated for `TokenX`, so the theft is never detected and the transaction succeeds.

This is precisely the bug class in the reference report: a privileged/pooled contract performs a low-level call with attacker-controlled target and data, and the resulting value movement escapes the equality check that is supposed to guarantee solvency — "value moved by Hinkal ... but not counted in the balance equation."

### Impact Explanation
This breaks Hinkal's core solvency invariant for the Emporium vault: any user can drain ERC-20 balances belonging to other users/pending operations held by the Emporium contract, as long as those tokens aren't listed in their own transaction's `erc20TokenAddresses`. This is direct theft of user funds held in a shared/pooled contract, and it requires nothing more than an ordinary user-generated valid proof (Critical impact per the rubric — direct theft of user funds via unauthorized asset movement).

### Likelihood Explanation
Likelihood is high: exploitation only requires being an ordinary Hinkal user able to generate a valid ZK proof for a self-owned note (or even a fresh `onChainCreation` deposit UTXO) and craft `externalActionMetadata` with a malicious `EmporiumOperation`. No special privileges, admin keys, or relayer collusion are needed — the attacker only needs the Emporium contract to be currently holding a token balance that is not part of their own `erc20TokenAddresses` list, which is a normal state of a shared pooled contract handling many users' deposits/external actions.

### Recommendation
- **Short term:** Require that every `erc20TokenAddresses`/token balance touched by an `EmporiumOperation`'s target contract be explicitly included in `circomData.erc20TokenAddresses` for that transaction (e.g., check balances of *all* tokens the Emporium contract currently holds, or restrict `op.endpoint` to a registered allow-list of protocol-approved routers/tokens rather than arbitrary user-chosen addresses).
- **Long term:** Replace the arbitrary low-level `op.endpoint.call(op.callData)` in the stateless-interaction path with a narrow, specific interface (mirroring the report's recommendation for `CallbackModule`), and never let a pooled/custodial contract execute attacker-chosen calldata against attacker-chosen targets without full accounting of every asset the contract holds.

### Proof of Concept
1. User A deposits Token X into the Emporium contract via a legitimate `transact` call (e.g., preparing a multi-step swap), leaving Token X balance sitting in the Emporium contract awaiting a follow-up action.
2. Attacker (any Hinkal user) crafts a `transact` call with `circomData.externalActionData.externalActionId` = Emporium action id, `erc20TokenAddresses = [TokenY]` (unrelated/zero-change token), and `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and one `EmporiumOperation{ endpoint: TokenX, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, TokenX_balance)) }`.
3. Attacker generates a valid proof over their own note (any nullifier they control) so `calldataHash`/proof checks in `HinkalHelper.performHinkalChecks` and `Hinkal.transact` pass.
4. `EmporiumUpgradeable.runAction` executes the stateless branch, calling `TokenX.transfer(attacker, TokenX_balance)` directly from the Emporium contract's own balance.
5. The post-call solvency loop only checks `TokenY` (`balancesAfter[TokenY] - balancesBefore[TokenY] >= 0`), which is unaffected, so the transaction succeeds and Token X is stolen from the Emporium contract undetected.
