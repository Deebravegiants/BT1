### Title
Webhook shop identity not bound to HMAC signature enables cross-tenant impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content solely from the raw request body, while the shop identity (`x-shopify-shop-domain` header) that the host application relies on for tenant attribution is taken from an unsigned HTTP header. `ShopifyAPI::Webhooks::Registry.process` verifies the HMAC over the body only, then dispatches to the app's handler using this unauthenticated `shop` value, breaking the intended binding between "the tenant whose secret produced this signature" and "the tenant the handler believes sent it."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from a header that is never included in the signed content: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (i.e. the raw body) against the HMAC: [3](#0-2) 

`Registry.process` accepts the request once this body-only HMAC check passes, then forwards the header-derived `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version` — all headers, all unsigned) straight into the handler as trusted tenant metadata: [4](#0-3) 

The binding the code implicitly assumes is:
`shop asserted in header == shop whose secret produced the HMAC over the body`

But nothing enforces this equality — the HMAC only proves "this body was signed with the app's secret" (which is true for any shop that has ever triggered any webhook to this app, since all shops share the app's single `api_secret_key`). It does not prove which shop the header claims to be. A caller who possesses one valid `(raw_body, hmac)` pair — trivially obtainable by installing the app on any shop and capturing one legitimate webhook delivery — can replay that exact body/HMAC pair while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` will still return `true` because it never looks at the header, and `Registry.process` will invoke the handler believing the payload originated from the spoofed shop.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged user who has installed the app on their own store (no special privilege, no leaked credentials, no access token needed) can cause the app to process a webhook under a different merchant's shop domain. Any host application logic that uses `WebhookMetadata#shop` to key updates (e.g., updating billing state, order records, or triggering per-shop side effects) can be tricked into applying an attacker-crafted body to a victim shop's identity, since the gem provides no mechanism binding the header-derived shop to the HMAC-verified payload.

### Likelihood Explanation
Likelihood is high for any app that trusts `WebhookMetadata#shop` without independently cross-checking it (e.g., against a known-installed-shops list or the payload body's own shop reference). Exploitation requires only: (1) installing the app once to receive one legitimate webhook with a valid HMAC, and (2) POSTing that same body/HMAC pair to the webhook endpoint with a forged shop-domain header — both achievable by any internet user without special access.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signable content, or independently verify that the shop asserted in the header actually owns an active session/install before trusting `request.shop` in `Registry.process`. At minimum, document that `WebhookMetadata#shop` is unauthenticated and host apps must validate it against their own session store before acting on it.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and capture a legitimate webhook POST, e.g. body `{"id":1}` with header `x-shopify-hmac-sha256: <valid-hmac-for-body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Replay the exact same raw body and HMAC header to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12`) succeeds because it only checks the raw body's signature.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`) invokes the handler with `shop: "victim-shop.myshopify.com"`, even though the payload was never signed by or associated with that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
