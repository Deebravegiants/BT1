### Title
Non-embedded/session-cookie fallback session ID is derived from an unauthenticated, predictable cookie value with no cryptographic binding to the shop - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` exposes two paths for resolving "which session to use": a cryptographically verified path via the Shopify ID token (JWT, HMAC-signed by Shopify with the app's `api_secret_key`), and a cookie-based fallback path that returns the raw, unverified cookie value as the session id. This breaks the intended identity binding `session_id == HMAC_or_signature_verified(shop)` that the JWT path enforces.

### Finding Description
`SessionUtils.session_id_from_shopify_id_token` derives the session id only after decoding and verifying a JWT signed with `Context.api_secret_key` [1](#0-0) , which in turn relies on `JwtPayload#initialize` performing `JWT.decode(... true, algorithm: "HS256")` [2](#0-1) . This guarantees the `shop` value embedded in the resulting session id was actually asserted by Shopify.

By contrast, the fallback path `cookie_session_id` simply returns whatever value is stored under the `shopify_app_session` cookie name, with no signature, no HMAC, and no verification of any kind: [3](#0-2) 

This value is invoked whenever no `shopify_id_token` is supplied — which is the *only* path for non-embedded apps, and a fallback path even for embedded apps [4](#0-3) .

The session id values produced during the legitimate OAuth flow are deterministic and predictable, constructed purely from the shop domain (and, for online sessions, the numeric Shopify user id): [5](#0-4) 

The OAuth callback flow sets this predictable, unsigned value directly into the browser cookie as the session-cookie's `value` (for non-embedded/offline flows) with no additional MAC: [6](#0-5) , and `SessionCookie` itself is a plain value struct with no signature field [7](#0-6) .

The identity-binding equality that should hold is: `session_id returned by SessionUtils == session_id cryptographically bound to a Shopify-issued assertion of "shop"`. For the JWT path this equality holds (bound via HMAC signature verified against `api_secret_key`). For the cookie fallback path it does not hold — the "session id" is just bytes taken verbatim from an HTTP cookie, i.e. exactly the analog called out in the rules: "a session id derived from unauthenticated bytes."

### Impact Explanation
`SessionUtils.current_session_id` is the documented, gem-provided mechanism host applications are expected to use to look up which stored `Session` (and therefore which merchant's access token) to activate for an inbound request [8](#0-7) . Because the returned identifier is (a) not cryptographically bound to any verified assertion from Shopify and (b) fully predictable/guessable (`offline_{shop}` or `{shop}_{user_id}`, both deducible from a target's publicly-known `myshopify.com` domain), an unprivileged internet user who can influence or forge the `shopify_app_session` cookie value sent to a host application built on this gem's documented `SessionUtils` API can cause the wrong tenant's session id to be resolved and used to activate another merchant's access token — a cross-tenant access condition and/or session-fixation vector, matching the "High — session fixation or forced OAuth completion" impact category.

### Likelihood Explanation
This requires the host application to rely on the cookie-fallback branch of `current_session_id` exactly as documented (no ignoring or misuse of the gem's API is required — it is a first-class, unauthenticated code path built into the gem itself, distinctly weaker than the sibling JWT path that ships in the same method). Exploitability further depends on the attacker's ability to set or predict the cookie value in the victim's or their own browser context (e.g., cookie injection via subdomain/network conditions, or simply because the value format is fully deterministic and requires no secret to construct). No `api_secret_key`, access token, or privileged access is required to construct a candidate session id string.

### Recommendation
Do not treat raw cookie bytes as a trusted session identifier. Either (a) sign/HMAC the cookie value with `Context.api_secret_key` (or a dedicated session-cookie secret) and verify that MAC in `cookie_session_id` before returning it, mirroring the verification already performed on the JWT path, or (b) make the cookie an opaque, non-predictable, server-generated token that has no direct algebraic relationship to the shop domain or user id, so that guessing or forging it does not yield a usable cross-tenant identifier.

### Proof of Concept
1. Host app built with this gem, non-embedded flow. Attacker knows victim's shop domain `victim-shop.myshopify.com` (public information).
2. Attacker computes the deterministic offline session id `offline_victim-shop.myshopify.com` per `SessionUtils.offline_session_id` [9](#0-8) .
3. Attacker sets a `shopify_app_session` cookie with that value in a request to the host app (e.g. via cookie injection on a shared/sub-domain, or a session-fixation flow where the cookie is set before authentication completes).
4. Host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns the attacker-chosen string unchanged via `cookie_session_id` [10](#0-9) [3](#0-2) .
5. If the host app's session storage (keyed by this id, as instructed in the gem's docs) already contains a stored `Session` for `victim-shop.myshopify.com` (i.e., that merchant previously installed the app), the host app activates and uses the victim's access token for the attacker's request — cross-tenant access — without the attacker ever completing OAuth or possessing any Shopify-issued credential.

        def current_session_id(shopify_id_token, cookies, online)
          if Context.embedded?
            if shopify_id_token
              id_token = shopify_id_token.gsub("Bearer ", "")
              session_id_from_shopify_id_token(id_token: id_token, online: online)
            else
              # falling back to session cookie
              raise Errors::CookieNotFoundError, "JWT token or Session cookie not found for app" unless
                cookies && cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]

              cookie_session_id(cookies)
            end
          else
            raise Errors::CookieNotFoundError, "Session cookie not found for app" unless
              cookies && cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]

            cookie_session_id(cookies)
          end
        end

        def session_id_from_shopify_id_token(id_token:, online:)
          raise Errors::MissingJwtTokenError, "Missing Shopify ID Token" if id_token.nil? || id_token.empty?

          payload = Auth::JwtPayload.new(id_token)
          shop = payload.shop

          if online
            jwt_session_id(shop, T.must(payload.sub))
          else
            offline_session_id(shop)
          end
        end

      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
      end

## Session Persistence
Session persistence is deprecated from the `ShopifyAPI` library gem since [version 12.3.0](https://github.com/Shopify/shopify-api-ruby/blob/main/CHANGELOG.md#version-1230). The responsibility of session storage typically is fulfilled by the web framework middleware.
This API library's focus is on making requests and facilitate session creation.

⚠️ If you're not using the [ShopifyApp](https://github.com/Shopify/shopify_app) gem, you may use ShopifyAPI to perform OAuth to create sessions, but you must implement your own session storage method to persist the session information to be used in authenticated API calls.
