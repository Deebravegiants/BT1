### Title
Webhook `shop` (and other identifying headers) are not covered by the HMAC signature, allowing cross-tenant shop spoofing on a validly-signed webhook - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw body only, while the merchant-identifying `shop`, `topic`, `api_version`, and `webhook_id` values are read from unauthenticated HTTP headers. `Registry.process` verifies the HMAC over the body and then trusts `request.shop` (and `request.topic`) taken from the headers to route/attribute the webhook, so a genuinely-signed body can be replayed with a different `shop-domain` header and still pass validation while claiming to belong to an arbitrary shop.

### Finding Description
`Utils::VerifiableQuery#to_signable_string` is what `HmacValidator` HMACs and compares against the `hmac-sha256` header. For webhooks, this is implemented as: [1](#0-0) 

which returns only `@raw_body`. The `shop`, `topic`, `api_version`, and `webhook_id` accessors are derived purely from HTTP headers that are never mixed into the signed string: [2](#0-1) 

`Registry.process` validates the HMAC of the body, then immediately trusts the header-derived `request.shop` and `request.topic` to build `WebhookMetadata` and dispatch to the app's handler: [3](#0-2) 

This is precisely the "bytes verified versus bytes parsed" binding break called out in the rules: the bytes that are HMAC-verified (the raw body) are not the same bytes that establish tenant identity (the `shop-domain` header parsed separately). Because the signature is only over the body, any request whose body+HMAC pair is valid for *some* shop will also pass validation if the `shop-domain` (and/or `topic`) header is altered to name a *different* shop, since altering a header does not invalidate the body-only HMAC.

### Impact Explanation
An attacker who can obtain one validly-signed webhook body/HMAC pair for their own store (trivial — they install the app on their own dev/test shop and trigger a webhook, e.g. `orders/create`) can replay that exact body+HMAC to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to point at a different, victim merchant's shop domain. `HmacValidator.validate` still returns true (it never inspects headers), and `Registry.process` will hand the attacker-controlled payload to the app's handler tagged as belonging to the victim shop (`WebhookMetadata#shop`). Any app logic that uses this shop value to look up a session/access token and act on the merchant's store, update per-shop state, or make trust decisions is now operating on attacker-supplied identity — a cross-tenant confusion that can lead to state corruption, incorrect authorization decisions, or actions taken against the wrong tenant's data/access token.

### Likelihood Explanation
The precondition (a genuinely signed body from an app the attacker can install on their own store) is easy to satisfy for any public app; installing on one's own store and capturing a legitimate webhook delivery requires no special access. Replaying with a modified header is a plain HTTP request forgery — no cryptographic secret is required since the header is unauthenticated. The only gating factor is whether the consuming app's handler makes trust decisions based on `WebhookMetadata#shop`/`#topic`, which is the documented and expected use of this metadata per this gem's API.

### Recommendation
Bind the identifying headers into the HMAC-signable string (or otherwise authenticate them), e.g. include `shop`, `topic`, and `webhook_id`/`api_version` in `to_signable_string`, or require callers to pass an expected shop and compare it against a separately-trusted source (e.g., the session used to register the webhook) rather than trusting the header verbatim once the body HMAC passes.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger any subscribed webhook (e.g. `orders/create`) and capture the raw POST: headers (including `X-Shopify-Hmac-Sha256: H` and `X-Shopify-Shop-Domain: attacker.myshopify.com`) and raw body `B`.
2. Replay the request to the app's webhook endpoint, keeping body `B` and `X-Shopify-Hmac-Sha256: H` unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac` decodes the same header value, `Utils::HmacValidator.validate` recomputes HMAC over `B` only [4](#0-3)  and it matches `H`, so validation succeeds.
4. `Registry.process` builds `WebhookMetadata` with `shop: "victim.myshopify.com"` [5](#0-4)  and dispatches to the app's handler, which now believes attacker-controlled webhook content originated from `victim.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end
