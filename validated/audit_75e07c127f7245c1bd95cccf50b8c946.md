## Title
Webhook shop/topic/api_version/webhook_id are trusted from unauthenticated headers while only the raw body is covered by the HMAC — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable material from the raw request body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers that are never included in the HMAC signature. `Registry.process` validates the HMAC and then forwards the header-derived `shop` value to the app's webhook handler as the authoritative tenant identifier, even though that value was never cryptographically bound to the signed payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are parsed directly from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e. it only ever authenticates the raw body bytes, not the headers: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then unconditionally trusts `request.shop`/`request.topic`/`request.webhook_id`/`request.api_version` (all header-derived, unauthenticated) when constructing the `WebhookMetadata` handed to the app's business logic: [4](#0-3) 

Equality that should hold but doesn't: `shop attributed to the webhook == shop that the HMAC actually authenticates`. In reality, the HMAC only proves "a body signed with this app's `api_secret_key`," while `shop` (the tenant-binding field) is taken from a header that is completely outside the signed material — exactly the "field acted on but not covered by the HMAC" pattern called out as in-scope.

### Impact Explanation
Any user who can install the app on a store they control (a normal, unprivileged action for public/installable Shopify apps) legitimately receives real webhook deliveries — valid `raw_body` + HMAC pairs — for their own shop. Because the `shopify-shop-domain` header is not part of the signed content, that same attacker can replay the captured `(raw_body, hmac)` pair to the victim app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value (e.g., a real merchant's `*.myshopify.com` domain). `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will dispatch the handler with `WebhookMetadata#shop` set to the attacker-chosen shop. Any app logic that keys off `data.shop` to look up/update per-tenant records (sessions, settings, orders, GDPR data) can be manipulated to write attacker-controlled data into another tenant's context — a cross-tenant integrity/confusion issue arising directly from an identity field left outside the HMAC's coverage.

### Likelihood Explanation
Obtaining a validly-signed webhook body only requires installing the target app once on an attacker-owned/dev store (routine, unprivileged action for any public app), then replaying the captured body+HMAC with a forged shop-domain header at the app's webhook endpoint. No access to `api_secret_key`, tokens, or any privileged account is required.

### Recommendation
Bind the shop (and ideally topic/webhook id) to the signed material, or otherwise independently verify that the shop asserted in the header corresponds to a shop for which the app currently holds an active session/installation, before trusting `WebhookMetadata#shop` in `Registry.process`. At minimum, document that consumers of this gem must not treat `Webhooks::Request#shop` as authenticated and must cross-check it against known installed shops.

### Proof of Concept
1. Install the target app on attacker-owned store `attacker.myshopify.com`; trigger a webhook (e.g. `app/uninstalled`) so Shopify sends a real `(raw_body, x-shopify-hmac-sha256)` pair to the app's endpoint.
2. Capture that `raw_body` and its valid HMAC.
3. Replay a POST to the same webhook endpoint with the identical `raw_body`/HMAC but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` passes (only `raw_body` is checked, per `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:12-22`).
5. `Registry.process` invokes the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's own webhook body>, ...)`, per `lib/shopify_api/webhooks/registry.rb:188-200` — the app now processes attacker-controlled data under the victim's tenant identity.
