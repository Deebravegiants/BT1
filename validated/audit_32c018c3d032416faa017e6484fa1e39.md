### Title
Webhook HMAC only signs the raw body, so the `shop-domain`, `topic`, `webhook-id` and `api-version` headers can be replayed unmodified against a forged tenant identity - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` computes/verifies the HMAC solely over that string. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read straight from HTTP headers that are never included in the signed material, yet `Registry.process` trusts them as the tenant/event identity passed to the app's webhook handler.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `Request#shop`/`#topic`/`#webhook_id`/`#api_version` are pulled from headers that are not part of that signable string: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC exclusively over `verifiable_query.to_signable_string` and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` gates on this body-only HMAC check and then forwards the *header-derived, unverified* `shop`, `topic`, `webhook_id`, and `api_version` straight to the registered handler as ground truth: [4](#0-3) 

The identity binding that should hold is: `hmac_signed_bytes == bytes_that_determine_the_tenant`. Here, `hmac_signed_bytes = raw_body` while `bytes_that_determine_the_tenant = shop-domain header (+ topic/webhook-id/api-version headers)`. Because the header set is disjoint from the signed body, any request whose body+HMAC pair was legitimately produced for one shop (or captured from any legitimately-received webhook) remains valid when replayed with a different `x-shopify-shop-domain` (and/or `x-shopify-topic`) header. `Registry.process` will still pass the `Utils::HmacValidator.validate(request)` check, since only the (unchanged) body is checked, and will hand the attacker-chosen `shop` value to the app's handler.

In a shared multi-tenant webhook endpoint (the normal deployment model for this gem, where one HTTP endpoint receives webhooks for every installed shop), a malicious merchant can:
1. Install the app on their own shop and trigger an event to receive a legitimate `(body, hmac)` pair signed by the app's real secret key.
2. Replay that exact `(body, hmac)` pair directly to the app's public webhook endpoint, substituting `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) with a victim shop's domain / a different topic.
3. `Registry.process` validates successfully (HMAC only checks the untouched body) and dispatches to the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain.

Any handler logic that uses `data.shop` to look up the victim's session, access token, or tenant-scoped records is manipulated into acting under the wrong tenant's identity, an unprivileged internet actor achieving cross-tenant impact without possessing the victim's or even the app's `client_secret` (they only need one prior legitimately-signed body from *any* shop, including their own).

### Impact Explanation
This crosses a tenant/authentication boundary: it lets one shop's legitimately-signed webhook payload be attributed to an arbitrary other shop (cross-tenant confusion), matching the "Critical – cross-tenant access" impact category, since the `shop` value handed to application code is not bound to the HMAC that supposedly authenticates the request.

### Likelihood Explanation
The exploit needs only one prior legitimately-delivered webhook (trivially obtainable by installing the app on one's own free development store) and the ability to POST directly to the app's public webhook endpoint with custom headers - both squarely within reach of an unprivileged internet user, requiring no `api_secret_key`, access token, or TLS interception.

### Recommendation
Include the values the application will rely on for identity/routing (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the signed body, rather than trusting them as bare headers. At minimum, document that `WebhookMetadata.shop`/`topic` are unauthenticated and must be independently corroborated (e.g., against the registered/expected shop) before being used for tenant-sensitive operations.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and provokes any webhook (e.g., `orders/create`) with body `B`, receiving a genuine `x-shopify-hmac-sha256` header `H = HMAC_SHA256(secret, B)`.
2. Attacker sends a POST directly to the app's shared webhook endpoint:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: H
   x-shopify-shop-domain: victim-shop.myshopify.com
   x-shopify-webhook-id: <any>
   x-shopify-api-version: 2024-01

   B
   ```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `B` and succeeds because `B` and `H` are unchanged. [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, even though the request body/topic originated from the attacker's own shop, letting the attacker inject fabricated events under the victim shop's identity.
