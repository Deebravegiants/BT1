## Title
Unsorted intermediate state commitments let a single consensus update skip storing lower heights while still advancing the "head" pointer, permanently orphaning those heights — (File: evm/src/core/HandlerV2.sol)

## Summary
The reported bug class is a proto-array forkchoice algorithm that collapsed two sequential sweeps ("update weights" then "update node relations/head") into a single sweep, so the head pointer could advance ahead of, or inconsistently with, the underlying per-node state, leaving a stale/incorrect head until the next sweep corrected it.

Hyperbridge's EVM handler has the same "combine what should be two ordered passes into one" defect in `_handleConsensus`, where each `IntermediateState` (one per finalized parachain/L2 header contained in a single consensus proof) is checked against, and immediately used to advance, the state machine's "head" (`_latestStateMachineHeight`) in one pass, without first sorting or separating "store the commitment" from "advance the head."

## Finding Description
`HandlerV2._handleConsensus` iterates the `intermediates` array returned by a consensus client's `verify()` and, for each entry, re-reads the *current* latest height and immediately stores the commitment if the entry's height is greater: [1](#0-0) 

`EvmHost.storeStateMachineCommitment` unconditionally sets both the per-height commitment mapping *and* the head pointer (`_latestStateMachineHeight`) in the same call, with no check that `height.height` is actually the maximum height ever seen — the caller's `intermediate.height > latestHeight` check is the only ordering guard, and it is evaluated against a "head" value that mutates within the very same loop, iteration by iteration: [2](#0-1) 

This is the single-sweep analog of the reported bug: the Rust-side consensus handler (`update_client`) treats "store each valid commitment" and "advance the head" as two separate passes — it sorts `commitment_heights` ascending, stores every entry that is `> previous_latest_height` (captured once, before the loop), and only writes `store_latest_commitment_height` after the entire per-height sweep completes: [3](#0-2) 

The EVM handler has no equivalent sort and no separation between "commit this height" and "advance the head" — it interleaves them per-entry using a head value that is already partially advanced by earlier entries in the same array. `intermediates` for a BEEFY/zkBEEFY proof is built directly from attacker/relayer-controlled proof data (`proof.parachains` / `SP1BeefyProof.headers`), with no on-chain guarantee of ascending order for repeated entries of the same `stateMachineId`: [4](#0-3) [5](#0-4) 

If a proof presents the same `stateMachineId` at height `H_high` before height `H_low` (both `> currentLatest`), the loop stores `H_high` first (advancing the head to `H_high`), then evaluates `H_low > H_high` as false and silently skips storing `H_low`'s commitment entirely — unlike the Rust path, which would still store `H_low` because it only compares against the pre-batch `previous_latest_height`, not the in-progress head.

## Impact Explanation
Once `H_low`'s commitment is skipped, it can never be (re)stored: subsequent consensus updates only ever push the head higher, and the guard `intermediate.height > latestHeight` permanently excludes any resubmission of `H_low`. Any request/response whose merkle inclusion proof is rooted at `H_low`'s `overlayRoot` becomes permanently undeliverable via `HandlerV2.handlePostRequests`/`handleGetResponses`, since `host.stateMachineCommitment(request.proof.height)` will forever revert with `StateCommitmentNotFound`: [6](#0-5) 

This is a permanent freezing of in-flight messages committed at that height — matching the "route unable to deliver messages" acceptance criterion.

## Likelihood Explanation
Exploitation requires only a single relayer-submitted consensus proof whose `intermediates` list contains the same destination `stateMachineId` more than once with a lower height following a higher one — fully controlled by whoever crafts/orders the `ParachainProof`/`SP1BeefyProof.headers` calldata, i.e. any unprivileged relayer. This does not require a malicious validator/authority set, governance, or off-protocol trust assumptions — only an ordinary relayed BEEFY/zkBEEFY consensus message.

## Recommendation
Mirror the Rust `update_client` two-pass design in `HandlerV2._handleConsensus`: for each `stateMachineId`, capture the pre-batch latest height once, sort/iterate `intermediates` so every entry greater than that pre-batch value is stored (regardless of intra-batch order), and only update `_latestStateMachineHeight` once, to the maximum height observed for that `stateMachineId` in the batch, after all per-height commitments have been persisted.

## Proof of Concept
1. Attacker/relayer submits a BEEFY (or SP1Beefy) consensus proof whose parachain-header list contains two entries for the same destination `stateMachineId`: entry A at height 200 and entry B at height 150, both greater than the currently stored `_latestStateMachineHeight` (say 100), with entry A ordered before entry B in the `parachains`/`headers` array (both entries pass their respective merkle/ZK inclusion checks against the same `headsRoot`/proof, since nothing enforces per-state-machine ordering).
2. `HandlerV2._handleConsensus` processes entry A first: `latestHeight = 100`, `200 > 100` → `storeStateMachineCommitment(200, …)` is called, setting `_latestStateMachineHeight = 200`.
3. Entry B is processed next: `latestHeight = 200` (freshly re-read), `150 > 200` is false → the commitment for height 150 is never stored.
4. Any user whose PostRequest/GetResponse proof is rooted at height 150 can never have it delivered: `handlePostRequests`/`handleGetResponses` call `host.stateMachineCommitment(StateMachineHeight{stateMachineId, height:150})`, which reverts with `StateCommitmentNotFound` permanently, since no future update can ever store height 150 again (`intermediate.height > latestHeight` will always fail for 150 once the head is beyond it).
