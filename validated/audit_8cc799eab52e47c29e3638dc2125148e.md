### Title
Webhook `shop`, `topic`, `api_version`, and `webhook_id` fields are trusted for tenant routing without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers and forwarded downstream (including into `WebhookMetadata` used to identify the merchant/tenant) without being part of the HMAC-verified payload.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes an HMAC over `verifiable_query.to_signable_string` and compares it against the `hmac` field [1](#0-0) . For webhook requests, `Request#to_signable_string` returns only `@raw_body` [2](#0-1) , whereas `shop`, `topic`, `api_version`, and `webhook_id` are all derived from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-api-version`, `shopify-webhook-id`, or their `x-shopify-` equivalents) that are never included in the signed string [3](#0-2) .

`Registry.process` validates the HMAC and, upon success, dispatches `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` straight to the registered handler via `WebhookMetadata`, with no further binding check between the header values and the signed body [4](#0-3) .

The identity binding that should hold is: `hmac == HMAC(secret, body || shop || topic || webhook_id)`. In this implementation the equality actually enforced is only `hmac == HMAC(secret, body)`; the `shop` (and other metadata) fields are unauthenticated with respect to the HMAC, i.e. `shop_used_by_handler ≠ shop_covered_by_hmac`. Any party capable of producing (or replaying) a validly-HMAC'd body for one shop can present that same body with attacker-chosen `shopify-shop-domain`/`shopify-topic`/`shopify-webhook-id` headers, and `Registry.process` will accept it and hand the forged `shop` value to the app's webhook handler as if it originated from that shop.

### Impact Explanation
This breaks the tenant-identity binding the HMAC is meant to provide for webhook delivery: the receiving application relies on `WebhookMetadata#shop` to route webhook data to the correct merchant/tenant record, but that value is not covered by the cryptographic signature. This enables cross-tenant data confusion — a webhook payload can be attributed to a different, attacker-chosen shop than the one whose secret/body actually produced the signature, since the gem provides no protection against header spoofing on the identity fields.

### Likelihood Explanation
Exploitation requires the attacker to control the raw HTTP request reaching the host application's webhook endpoint (e.g., a network position able to replay/proxy a legitimately-observed webhook body with modified headers, or a scenario where the app's webhook route is reachable with attacker-controlled headers such as behind a misconfigured proxy that forwards client-supplied `X-Shopify-Shop-Domain`). This is a real weakness in the library's own verification logic (not a misuse of a documented contract), but full exploitation is somewhat conditional on the deployment/network path, which is why it is rated as the identity-binding gap in the library rather than a directly exploitable end-to-end attack in isolation.

### Recommendation
Include the identity-critical headers (`shop`, `topic`, `webhook_id`, `api_version`) in the value used for `to_signable_string`, or otherwise independently authenticate them (e.g., re-deriving/confirming `shop` from a value that is itself covered by the HMAC) before they are used to route webhook data to a handler, mirroring how `AuthQuery#to_signable_string` incorporates `shop` into its signed parameters [5](#0-4) .

### Proof of Concept
1. Attacker observes (or is sent) a legitimate Shopify webhook: `raw_body = B`, `hmac = HMAC_SHA256(secret, B)`, `shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker resends the same `raw_body = B` and the same `hmac` value to the app's webhook endpoint, but sets `shopify-shop-domain: shop-b.myshopify.com` (and/or a different `shopify-topic`/`shopify-webhook-id`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` is unaffected by the header change [6](#0-5) .
4. The handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` even though the HMAC only ever certified the body, not this shop association [7](#0-6) .

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
