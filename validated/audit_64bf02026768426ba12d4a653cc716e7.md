### Title
Cross-tenant webhook impersonation via unauthenticated `shop-domain` header not covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` (parsed from the `shopify-shop-domain`/`x-shopify-shop-domain` header) as the tenant identity passed to the app's webhook handler, without that header ever being included in the HMAC that is validated.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac` [1](#0-0) . For webhooks, `Request#to_signable_string` is defined as just `@raw_body` [2](#0-1) , and `Request#hmac` is parsed from the `hmac-sha256` header [3](#0-2) . However `Request#shop` is read directly and unauthenticated from the `shop-domain` header [4](#0-3) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., only the body/hmac pairing) and then forwards `request.shop` straight into `WebhookMetadata` passed to the app's handler as the tenant identity: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [5](#0-4) . The equality the gem implicitly relies on is: `shop used for tenant routing == shop covered by HMAC`. That equality does not hold — `shop` is completely outside the signable string, so any bytes verified by the HMAC say nothing about which shop the request came from.

Because Shopify's webhook signature (the same design mirrored in this gem's `to_signable_string`) authenticates only the body bytes and the shared secret, not the headers, a valid `(body, hmac)` pair generated for a webhook delivered to the attacker's own shop remains valid for that same body no matter what `shop-domain` header value accompanies it. An attacker who controls a shop that has the app installed can capture a legitimate webhook delivery (or otherwise produce a body whose content is attacker-influenced/predictable, e.g. `shop/redact`, `customers/data_request`, or any topic where the body schema is fixed/guessable) together with its valid `hmac-sha256` header, then replay that exact body+hmac to the app's public webhook endpoint while substituting the `shop-domain` header for a victim shop's domain. `Registry.process` will pass HMAC validation (since only the body is checked) and hand the handler `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This breaks the tenant/shop identity binding at the point where the gem authenticates inbound webhook traffic and hands data off to the host application. Any host application that uses `data.shop` from the handler (as the gem's own documentation instructs: "the shop domain of the webhook") to key persistence, authorization, or per-tenant side effects is misled into cross-tenant data association/processing, since the gem asserts (via calling `HmacValidator.validate` successfully) that the whole request — including `shop` — was verified, when in fact `shop` was never covered by the signature. This matches a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only an unprivileged actor with a shop that has the target app installed (a normal merchant/developer account, not a privileged one), no access to `api_secret_key` or any Shopify-issued token. They need one legitimately signed webhook body from their own shop and the ability to send an arbitrary HTTP POST to the app's public webhook callback endpoint with attacker-chosen headers — both are standard, low-effort capabilities of a normal internet-facing attacker who is also an app-installing merchant.

### Recommendation
Include `shop-domain` (and `topic`/`webhook_id` if they are used for routing decisions) in the HMAC-covered signable string, or otherwise cryptographically bind the shop identity to the verified payload before it is handed to the handler, so that `Registry.process` cannot separate a validated signature from an attacker-controlled tenant claim.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com` and installs the victim app; the app registers a webhook handler for a topic such as `customers/data_request`.
2. Shopify delivers a legitimate webhook to the attacker for their own shop: body `B`, headers include `shopify-shop-domain: attacker-shop.myshopify.com` and `shopify-hmac-sha256: HMAC(secret, B)`.
3. Attacker captures `(B, HMAC(secret, B))` and replays a POST to the app's webhook endpoint, keeping body `B` and the same `hmac-sha256` value, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against `hmac` [7](#0-6) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from, and was signed for, the attacker's own shop [5](#0-4) .

          end
        end

          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @raw_body = raw_body
