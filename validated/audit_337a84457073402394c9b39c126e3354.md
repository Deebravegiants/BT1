### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs (via HMAC-SHA256) only the raw request body, while the `shop` (and `topic`/`webhook_id`) values are read from HTTP headers that are completely outside the signed payload. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then trusts the unauthenticated `shop` header to build `WebhookMetadata`, breaking the binding "shop authenticated == shop the payload is attributed to."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is pulled from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed string: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (along with `request.topic`/`request.webhook_id`, also header-derived) to construct the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the raw body) and the app's shared `api_secret_key`: [4](#0-3) 

Because `api_secret_key` is the app's single `client_secret`, shared across **every** merchant/shop that has installed the app, any shop that installed the app can legitimately obtain a body + valid HMAC pair from its own genuine webhook delivery. That merchant can then replay the identical body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a different (victim) shop's domain. The HMAC still validates (it only covers the body), but `request.shop` — the value the host application uses to decide "which tenant does this data belong to" — is now attacker-controlled and unauthenticated.

This exactly matches the hinted bug class: a field ("shop") that is acted on by the library/handler but not covered by the HMAC binding that is supposed to authenticate the message.

### Impact Explanation
This breaks the equality "shop claimed in the webhook == shop that actually generated/authorized the payload." Any application that uses `WebhookMetadata#shop` to look up a merchant's stored offline session/access token, write data, or otherwise scope an action to a tenant can be tricked into performing that action against, or attributing attacker-supplied data to, a different (victim) shop, i.e., cross-tenant contamination — one of the explicitly in-scope Critical impacts.

### Likelihood Explanation
Any developer/merchant that has installed the target app can capture a legitimate webhook (their own shop's HMAC-valid body) and replay it with a forged `shop-domain` header — no access token, no `api_secret_key`, and no privileged account is required beyond being a normal (unprivileged, from the victim's perspective) app installer. This is a low-effort, directly reachable attack through the gem's own public `Webhooks::Registry.process`/`Webhooks::Request` API, matching the "unprivileged internet user" threat model.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`) in the signed material that is validated against the HMAC, or otherwise cryptographically bind the header-derived identity fields to the signature before they are used to build `WebhookMetadata`. At minimum, document/require host applications to independently verify that the shop domain in the webhook headers corresponds to a shop for which they have an active, previously stored session, and reject webhooks whose shop is not already an installed tenant.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Shopify sends a legitimate webhook to the app: body `B`, header `x-shopify-shop-domain: attacker.myshopify.com`, and `x-shopify-hmac-sha256: HMAC(secret, B)`.
3. Attacker replays the exact same request to the app's webhook endpoint, only changing the header to `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(secret, B)` against the raw body, which is unchanged: [5](#0-4) 
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...)`: [6](#0-5) 
6. The host application, trusting `data.shop`, processes attacker-controlled data as if it originated from `victim.myshopify.com`, achieving cross-tenant data injection/attribution.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
