### Title
Optional slippage checks in `Withdraw` (and `Deposit`) allow MEV sandwich attacks on LP redemption/provision - ([File: program/src/processor.rs])

### Summary
`WithdrawInstruction` (and similarly `DepositInstruction`) allow the caller to make `min_coin_amount`/`min_pc_amount` (or `other_amount_min`) optional. When a client submits `None` for these fields (the on-chain equivalent of the `amountMin = 0` pattern from the external report), `process_withdraw` skips the slippage check entirely, letting the LP burn proceed at whatever coin/pc ratio the pool has at execution time. This reproduces the exact "reinvest with `amountMin = 0`" bug class described in the report: predictable, un-protected on-chain redemption/provision transactions that an MEV bot can sandwich.

### Finding Description
`WithdrawInstruction` defines `min_coin_amount`/`min_pc_amount` as `Option<u64>` [1](#0-0) , and the unpacking logic only populates them when the caller supplies the extra 16 bytes, otherwise both are `None` [2](#0-1) .

In `process_withdraw`, the resulting `coin_amount`/`pc_amount` (computed from the pool's current, spot on-chain ratio) are only checked against the user-supplied minimums **if both `Option`s are `Some`**:
```
if withdraw.min_coin_amount.is_some() && withdraw.min_pc_amount.is_some() {
    if withdraw.min_coin_amount.unwrap() > coin_amount
        || withdraw.min_pc_amount.unwrap() > pc_amount
    {
        return Err(AmmError::ExceededSlippage.into());
    }
}
``` [3](#0-2) 

If a client (or any wallet/integrator using the plain `Withdraw` variant without the optional fields) omits the minimums, the instruction proceeds unconditionally — there is no protocol-enforced floor. The same optional-and-unenforced pattern exists for `Deposit`'s `other_amount_min`, which is only checked `if deposit.other_amount_min.is_some()` [4](#0-3) . In contrast, the swap paths (`process_swap_base_in`/`process_swap_base_in_v2`) always enforce `minimum_amount_out` as a mandatory field, so they are not affected [5](#0-4) .

Because Raydium's AMM price (`calc_total_without_take_pnl_no_orderbook`) is derived directly from the live coin/pc vault balances at instruction execution time [6](#0-5) , an attacker who observes a pending `Withdraw` (or `Deposit`) transaction with no minimums set can front-run it with a large swap that skews the coin/pc ratio, let the victim's withdraw/deposit execute at the manipulated ratio, then back-run with an opposite swap to restore the ratio and capture the difference — a classic sandwich attack, exactly analogous to the reported `reinvest`/`amountMin=0` issue.

### Impact Explanation
A victim LP who withdraws or deposits without both minimum fields populated can receive significantly less value (fewer coin/pc tokens on withdraw, or overpay/receive fewer LP tokens on deposit) than the pool's unmanipulated state would provide, with the difference captured by the sandwiching MEV bot. This is a direct theft of user/LP funds enabled by a missing mandatory slippage guard in a reachable, unprivileged instruction path.

### Likelihood Explanation
Any unprivileged LP calling `Withdraw` or `Deposit` without supplying the optional minimum fields (or a wallet/SDK that defaults them to `None`) is exposed. Since Solana transactions and their instruction data are visible in the mempool/leader schedule before confirmation, an MEV bot can trivially detect such transactions and construct front-run/back-run swap pairs using the always-available `SwapBaseIn`/`SwapBaseOut` instructions on the same pool.

### Recommendation
Make `min_coin_amount`/`min_pc_amount` (and `other_amount_min`) mandatory fields (not `Option`) so the protocol always enforces a caller-specified floor, mirroring the mandatory `minimum_amount_out` check already used in the swap instructions, rather than allowing the check to be silently bypassed when the fields are omitted.

### Proof of Concept
1. Victim submits `Withdraw { amount, min_coin_amount: None, min_pc_amount: None }`.
2. MEV bot observes the pending transaction and front-runs with a large `SwapBaseIn`/`SwapBaseOut` that skews `amm_coin_vault`/`amm_pc_vault` balances.
3. Victim's `Withdraw` executes; since both minimums are `None`, the check at `program/src/processor.rs:1780-1786` is skipped, and `coin_amount`/`pc_amount` are computed from the skewed ratio, giving the victim less value than expected.
4. MEV bot back-runs with the opposite swap to restore the ratio and pocket the extracted value.
