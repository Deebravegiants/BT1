### Title
Fee-on-transfer output tokens let beneficiaries be paid less than the agreed amount while orders are marked fully filled - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol], [File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`IntentGatewayV2`'s `placeOrder` was explicitly hardened against fee-on-transfer/USDT-style tokens on the **input** side: it measures actual balance received via `balanceOf` deltas before trusting `safeTransferFrom` amounts [1](#0-0) , and this is verified by dedicated foundry tests [2](#0-1) . However, the corresponding **output**-side transfers performed during fill — in both the same-chain path (`_fillSameChain`) and the cross-chain path (`_fillCrossChain`) — still use a raw `safeTransferFrom(msg.sender, beneficiary, amount)` and treat the requested amount as delivered, with no balance check.

Neither function checks the beneficiary's actual balance delta after the transfer. If the order's output token deducts a fee on transfer (e.g. a USDT-style fee-enabled token, or any deflationary/fee-on-transfer ERC20), the beneficiary receives `beneficiaryTotal * (1 - fee)`, strictly less than `totalRequired`. Despite this shortfall, the code:
- Marks `amountFilled == totalRequired` and sets `isFullyFilled = true` in the same-chain path [5](#0-4) , releasing the **full** escrowed input amount to the solver via `_withdraw` [6](#0-5) .
- In the cross-chain path, unconditionally dispatches `RedeemEscrow` for the full `order.inputs` to the solver on the source chain regardless of what the beneficiary actually received [7](#0-6) .

This is the exact bug class from the external report — code assumes `transferFrom` delivers the nominal amount when the token can silently deliver less — but manifesting on the output/payout leg of the intents system rather than the input/escrow leg (which was already fixed).

### Impact Explanation
Any order whose output asset is a fee-on-transfer token results in the beneficiary permanently receiving less value than the order specifies, while the solver still collects the full escrowed input tokens as if the order were completely and correctly filled. This is a fund-loss bug reachable by any solver calling the public `fillOrder` entry point with no special privileges — the beneficiary bears the fee cost that the protocol's own escrow accounting does not account for. The order is also erroneously marked complete/filled (`_filled[commitment]`, `OrderFilled` event), foreclosing any future partial-fill correction for the shortfall on the same-chain path.

### Likelihood Explanation
Any order creator (user) who selects a fee-on-transfer token as an output asset triggers this on every fill, deterministically, with no adversarial setup needed beyond normal use of such a token. Given intents protocols must support arbitrary ERC20 outputs to be broadly usable, and the input side was already patched for exactly this token category (demonstrating the team is aware fee-on-transfer tokens are in scope), the likelihood of this being triggered in production is high.

### Recommendation
Apply the same balance-delta pattern used in `placeOrder` to the output transfers in `_fillSameChain` and `_fillCrossChain`: record `beneficiary`'s (and the protocol's) token balance before the `safeTransferFrom` call, compare against the balance after, and either (a) revert if the actual amount received by the beneficiary is less than `totalRequired`, or (b) only release proportional escrow / mark the order filled based on the amount actually received.

### Proof of Concept
1. Order creator places a same-chain order with `order.output.assets[0].token` = a fee-on-transfer ERC20 (e.g. 1% fee), `amount = 1000e18`, beneficiary = user.
2. Solver calls `fillOrder` supplying `options.outputs[0].amount = 1000e18` and approves the gateway for `1000e18`.
3. Inside `_fillSameChain`, `IERC20(token).safeTransferFrom(msg.sender, beneficiary, 1000e18)` is executed; due to the 1% fee, beneficiary actually receives only `990e18`.
4. `amountFilled == totalRequired (1000e18)` is still true, so `isFullyFilled = true`; the full escrowed input tokens are released to the solver via `_withdraw`, and `OrderFilled` is emitted as if the beneficiary was paid in full.
5. Beneficiary is short `10e18` of the promised output value, with no recourse — the order is already finalized.

The existing `FeeOnTransferToken` test contract in the test suite [8](#0-7)  can be directly reused to demonstrate this on the fill/output side, mirroring the input-side tests that already validate the (fixed) `placeOrder` behavior.

contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }
}
