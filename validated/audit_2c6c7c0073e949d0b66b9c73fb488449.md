## Title
Webhook shop-domain identity binding bypass allows cross-tenant webhook impersonation — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC that `Registry.process` verifies covers the body alone. The `shop` (and `topic`/`webhook_id`) values used to build `WebhookMetadata` and dispatch to the app's handler come from unauthenticated HTTP headers that are never part of the signed bytes. This breaks the binding `shop-that-produced-the-HMAC == shop-delivered-to-the-handler`, letting anyone who possesses one valid (body, HMAC) pair — trivially obtainable by installing the app on their own store and receiving a genuine webhook — replay it with an arbitrary `X-Shopify-Shop-Domain` header value to make the app process attacker-supplied data as if it originated from any other shop.

while `shop` is read straight from an unauthenticated header: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` verifies that HMAC, then immediately forwards `request.shop` (and `request.topic`, `request.webhook_id`) — none of which are covered by the HMAC — into `WebhookMetadata` for the registered handler: [4](#0-3) 

Because `hmac == HMAC(secret, body)` and never `HMAC(secret, body || shop)`, the equality the app implicitly relies on — `signed_shop == delivered_shop` — is never actually checked; only `signed_body == delivered_body` is checked. Any two shops sharing the same app (the normal multi-tenant case) share the same `api_secret_key`, so a (body, HMAC) pair legitimately produced for shop A's webhook remains a valid signature no matter which `shop-domain` header accompanies it.

### Impact Explanation
An unprivileged user who has installed the app on their own store (or otherwise legitimately received one real webhook delivery) can capture that request's raw body and its valid `X-Shopify-Hmac-Sha256` value, then replay it directly to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header for a victim shop. `Registry.process` will accept the HMAC (it only ever validated the body) and hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop. Any app logic that trusts `data.shop` to look up/update per-tenant records (the documented and expected usage) can be made to write or act on attacker-chosen content under another tenant's identity — a cross-tenant confused-deputy condition.

### Likelihood Explanation
Reaching this requires only: (1) a publicly reachable webhook endpoint built on this gem (the documented integration pattern), and (2) one legitimate webhook delivery to observe a valid (body, HMAC) pair — achievable by any developer who installs the app on a store they control, no `api_secret_key` or privileged access to the victim needed. This is a low-effort, directly reachable path.

### Recommendation
Include the shop domain (and topic/webhook id, if they are trusted for dispatch) in the signable bytes checked against the HMAC, or independently verify that `request.shop` corresponds to a shop session/installation the app actually expects for this specific HMAC before invoking the handler, rather than trusting `X-Shopify-Shop-Domain` as an unauthenticated header.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a real webhook (e.g. `orders/create`) with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `HMAC(secret, B)`).
2. Attacker sends a POST to the app's public webhook endpoint with the same body `B`, the same header `X-Shopify-Hmac-Sha256: H`, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` builds the request from these headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` (`B`), matching `H`.
4. `handler.handle` is invoked with `WebhookMetadata(shop: "victim.myshopify.com", body: parsed(B), ...)`, so the app processes attacker-controlled data attributed to the victim's tenant.
