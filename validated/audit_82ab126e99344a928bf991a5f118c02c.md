### Title
Webhook `shop-domain` is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only the HMAC-over-body via `Utils::HmacValidator.validate(request)` and then forwards `request.shop` straight into the handler's `WebhookMetadata` without any additional binding [3](#0-2) .

### Finding Description
The binding that should hold is: `hmac_signed_bytes == (body, shop)`. In this gem it only holds `hmac_signed_bytes == body`. The `shop` field that the app's webhook handler uses to route/attribute data (`data.shop`, per `docs/usage/webhooks.md`) [4](#0-3)  is never included in the HMAC-protected content computed in `HmacValidator.compute_signature` [5](#0-4) .

This is structurally the same class of defect as the `stNXM` `update` modifier bug: a value that gates/attributes a privileged action (`adminFees` for arNXM balance vs. `shop` for webhook data) is checked using a proxy signal (`balance`/`hmac`) that doesn't actually bind the specific unauthenticated variable that matters (`staked==0`/`shop` header) to the authorization decision.

Because the shared `client_secret` HMAC key is identical for every shop of a given app, a merchant who has installed the app on their own store can capture a legitimately-signed webhook (raw body + valid `X-Shopify-Hmac-Sha256`) delivered to their own registered endpoint, then replay that exact body/hmac pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` still passes because it only checks the body bytes against the secret [6](#0-5) , and `Registry.process` will invoke the handler believing the data originated from the spoofed `shop` [3](#0-2) .

### Impact Explanation
If the host application's handler trusts `data.shop` to key per-tenant state (e.g., updating a victim shop's order/customer records, billing status, or install state, as shown in the documented handler pattern [7](#0-6) ), an attacker who is merely an installed merchant of the app can inject attacker-chosen webhook bodies attributed to any other shop — a cross-tenant data-integrity/confusion issue. This maps to "Critical – cross-tenant access" per the rubric, since the trust boundary between tenants relies entirely on the unauthenticated `shop-domain` header.

### Likelihood Explanation
Exploitability requires only that the attacker be a legitimate merchant with the app installed (an "unprivileged internet user" relative to other tenants), able to register/receive one webhook to their own endpoint and replay it with a modified header — no access token, `client_secret`, or privileged account is needed. However, this is also inherent to how Shopify's own webhook HMAC scheme has historically worked (HMAC covers body only), so the severity in practice depends heavily on whether the consuming application additionally validates that `shop` belongs to a shop it has an active session/installation record for — something this library's docs do not explicitly instruct developers to check.

### Recommendation
Document (and ideally enforce) that consumers of `WebhookMetadata` must cross-check `data.shop` against a known/authorized shop list (e.g., an existing offline session) before using it to key any tenant-scoped state, since the HMAC in `Utils::HmacValidator` does not bind the shop identity. Alternatively/additionally, the gem could expose a helper that validates `request.shop` is one of the app's currently-installed shops as part of `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Attacker triggers the event in their own store and captures the raw POST from Shopify, including `X-Shopify-Hmac-Sha256: <hmac>` and body `<raw_body>`.
3. Attacker resends the identical `raw_body`/`hmac` pair to the app's webhook endpoint, replacing only `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses `shop` from the forged header [8](#0-7) ; `Utils::HmacValidator.validate(request)` succeeds because only `raw_body` is hashed [5](#0-4) .
5. `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` [9](#0-8) , causing the app to process attacker-controlled data as if it came from `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
