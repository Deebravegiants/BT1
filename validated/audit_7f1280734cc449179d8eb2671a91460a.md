### Title
Unchecked ERC20 return value in `CallDispatcher.dispatch` allows fake escrow credit in `IntentGatewayV2.placeOrder` predispatch path (Tron variant) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`CallDispatcher.dispatch()` only checks that the low-level `.call` did not revert; it never inspects the ABI-encoded boolean return value of `transfer`/`transferFrom` calls it forwards. In the `predispatch` branch of `IntentGatewayV2.placeOrder` (Tron variant), the escrow ledger `_orders[commitment][token]` is incremented *before* the sweep transfer from the `CallDispatcher` back to the gateway is verified against an actual balance delta. A non-reverting-on-failure ERC20/TRC20 token used as an order input lets an attacker credit themselves escrow with tokens that were never actually received by the gateway.

### Finding Description
`CallDispatcher.dispatch` executes each `Call` with a raw `.call` and only reverts if the call itself reverts: [1](#0-0) 

It does not decode/check the boolean return data of ERC20 `transfer`, so a token that returns `false` on failure (instead of reverting) will make `dispatch` report success even though no tokens moved.

In `IntentGatewayV2.placeOrder` (Tron contracts), the predispatch branch builds a sweep `Call[]` using the unchecked `IERC20.transfer.selector` pattern and — critically — increments the escrow accounting for the order **before** that sweep dispatch executes and with no post-sweep balance verification: [2](#0-1) 

Compare this to the canonical (non-Tron) `IntentGatewayV2.sol`, which correctly snapshots balances before the sweep and derives the escrowed amount from the *actual* post-sweep balance delta rather than the nominal `order.inputs[i].amount`: [3](#0-2) 

The Tron variant lacks this actual-balance reconciliation: `_orders[commitment][token] += reducedInputs[i].amount;` is set from the requested amount, not from what the gateway actually received after the `CallDispatcher` sweep at line 449. If the input token silently fails the sweep `transfer` call (returns `false`, doesn't revert), the gateway's escrow ledger is inflated with phantom balance while the real tokens remain unrecovered from the dispatcher (or never left the user in enough quantity).

### Impact Explanation
A solver observing the order fills it on the destination chain, fronting real output tokens to the beneficiary. When the solver later calls `withdraw()`/settlement to claim the source-chain escrowed input, `_withdraw` uses `safeTransfer`, which will revert once the phantom-inflated portion of `_orders[commitment][token]` exceeds the gateway's real token balance: [4](#0-3) 

This produces two directly damaging outcomes reachable from a single unprivileged `placeOrder` transaction: (1) the solver who already delivered genuine output tokens on the destination chain cannot recover the (phantom) input escrow — direct theft of solver funds; and (2) once the shared escrow ledger is desynchronized from the real token balance, other legitimate users' `withdraw()`/cancel-refund calls on the same token can revert due to insufficient real balance, permanently freezing their genuinely escrowed funds.

### Likelihood Explanation
`placeOrder` is a public, unauthenticated entry point reachable by any address in a single transaction; the only precondition is using an ERC20/TRC20 input token that returns `false` on failed transfer rather than reverting — a common token behavior class on Tron (TRC20) that the reported bug class explicitly calls out. The predispatch/calldata code path is a documented, intended feature (swap-then-escrow) rather than an edge case, making it reachable in normal usage.

### Recommendation
In `CallDispatcher.dispatch`, decode and check the boolean return value for any call whose selector matches ERC20 `transfer`/`transferFrom` (or more generally, require `result.length == 0 || abi.decode(result, (bool))`), or require callers to use `SafeERC20`-wrapped calldata. Additionally, in the Tron `IntentGatewayV2.placeOrder` predispatch branch, mirror the non-Tron implementation: snapshot gateway token balances before the sweep dispatch and set `_orders[commitment][token]` from the actual observed balance delta after `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))`, not from the nominal requested amount.

### Proof of Concept
1. Deploy/select an ERC20/TRC20 token whose `transfer` returns `false` on failure instead of reverting (e.g., balance insufficient at the `CallDispatcher`, or a token with a `transfer` bug).
2. Attacker calls `placeOrder` with `predispatch.call`/`predispatch.assets` set so tokens route through `_params.dispatcher`, and `order.inputs[0].token` = the non-reverting token.
3. In the sweep phase (`evm/tron/contracts/apps/IntentGatewayV2.sol:416-449`), the `Call` built at line 430-435 calls `token.transfer(address(this), balance)` via `CallDispatcher.dispatch`; craft conditions so this transfer returns `false` (e.g., dispatcher's balance is manipulated to be below `balance` after a reentrant/side-effect from the predispatch call, or the token enforces an internal check that returns false rather than reverting).
4. `CallDispatcher.dispatch` sees `success == true` (call didn't revert) and returns normally.
5. `_orders[commitment][token]` has already been incremented by `reducedInputs[i].amount` at line 441 regardless of the real transfer outcome — the gateway now believes it holds tokens it never received.
6. A solver fills the order cross-chain, delivering real output tokens to the beneficiary, then attempts to withdraw the phantom source-chain escrow and finds insufficient real balance (theft of solver's fronted output) or drains balance backing other users' legitimate escrows (freezing their funds).

        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
