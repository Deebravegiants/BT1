### Title
Anyone can permanently block the permissionless `clean_bad_debt` path by topping up an insolvent account's collateral above the dust threshold - (File: contracts/controller/src/positions/liquidation/curve.rs)

### Summary
`clean_bad_debt` is the only permissionless path that socializes insolvent debt. It is gated by `is_socializable_bad_debt`, which requires the account's total collateral (WAD USD) to be at or below `BAD_DEBT_USD_THRESHOLD` ($5). Because `supply` lets any third party add collateral to an existing asset slot of a foreign account, an attacker can cheaply push an insolvent account's collateral just above the threshold, making every subsequent `clean_bad_debt` call revert with `CannotCleanBadDebt`. The only remaining cleanup path is the owner-gated `force_socialize_bad_debt`, which must go through governance.

### Finding Description
The permissionless gate is defined in `is_socializable_bad_debt`: `total_debt > total_collateral && total_collateral <= BAD_DEBT_USD_THRESHOLD` (curve.rs:25-27). `process_clean_bad_debt` only requires `caller.require_auth()` and not being inside a flash loan (mod.rs:196-200); `socialize_bad_debt` with `BadDebtGate::DustCapped` then enforces the predicate and reverts otherwise (mod.rs:229-235).

Meanwhile `controller::supply` is permissionless for topping up: per `scripts/permissionless_entrypoints.txt:69`, "anyone may top up an account they do not own" as long as the account already holds a supply position in that hub asset (INV-AUTH-03 prevents opening a *new* slot, but does not prevent growing an *existing* one). An insolvent-but-not-yet-cleaned account by definition still holds residual supply positions (otherwise it would have been removed by `cleanup_account_if_empty`, apply.rs:308-310).

So the attacker calls `supply(account_id = victim, hub_asset = <asset the victim already supplies>, amount ≈ $5+)` from their own funds. The victim's `total_collateral` crosses `BAD_DEBT_USD_THRESHOLD`, `is_socializable_bad_debt` returns false forever (the attacker-controlled collateral is never withdrawn — the victim is insolvent and can't withdraw without restoring solvency), and `clean_bad_debt` reverts on every attempt.

The straddle is explicitly modeled in the protocol's own Certora spec (`certora/controller/spec/boundary_rules.rs:44-67`): "`bad_debt_straddle_blocks_dust_gate` — an attacker who raises `total_collateral` strictly above `BAD_DEBT_USD_THRESHOLD` blocks the permissionless dust-gated socialization path while staying insolvent."

### Impact Explanation
Bad debt that could be socialized immediately and permissionlessly instead remains on the books until governance schedules and executes `force_socialize_bad_debt` (owner-gated, `BadDebtGate::InsolventOnly`, mod.rs:246-248), which is a delayed/operational action. During that window the market carries a backing shortfall: the pool's supply index write-down is deferred, utilisation/rate accounting stays distorted, and suppliers' effective backing remains overstated. This is a griefing/temporary-liveness DoS on a core protocol maintenance operation, matching the report class (an unprivileged caller repeatedly/permanently suppressing a protected operation via an open state-mutating call). The attacker's cost is only ~$5 of collateral per victim account, which is seized when force cleanup eventually runs — so the cost is one-time while the blocking persists indefinitely until governance acts.

### Likelihood Explanation
Requires only: an insolvent account with collateral at or below $5 (the normal end state of liquidations, deliberately produced by the liquidation engine's residual handling) and ~$5 of an asset the account already supplies. `supply` is explicitly documented as permissionless for foreign accounts. No privileged role, oracle manipulation, or timing dependence is needed; the attacker can even front-run a pending `clean_bad_debt` transaction. Likelihood is limited mainly by the fact that the attacker donates real funds and the block is only bypassable by governance, capping severity at Medium.

### Recommendation
- Make the dust gate per-attacker-unforgeable: e.g., count only collateral the account held before it became insolvent, or snapshot collateral value at the time insolvency is detected.
- Alternatively, block third-party `supply` top-ups (INV-AUTH-03) to accounts that are currently insolvent / liquidatable, or to accounts whose collateral is near the dust band.
- A cheaper mitigation: subtract any third-party top-up amount recorded after the account first met the insolvency condition when evaluating `is_socializable_bad_debt`.

### Proof of Concept
1. Alice's account is liquidated down to residual state: `total_debt = $20`, `total_collateral = $4` (≤ `BAD_DEBT_USD_THRESHOLD`). `clean_bad_debt(alice_id)` is ready to succeed via `BadDebtGate::DustCapped`.
2. Eve calls `controller::supply` with `account_id = alice_id`, `hub_asset` = an asset Alice already supplies, `amount` worth $2, authorized with Eve's own funds. The call is permitted by INV-AUTH-03 (existing slot top-up).
3. `total_collateral` is now $6 > `BAD_DEBT_USD_THRESHOLD`; `is_socializable_bad_debt` returns false.
4. Every subsequent `clean_bad_debt(alice_id)` reverts `CollateralError::CannotCleanBadDebt` (mod.rs:235). Alice cannot withdraw Eve's collateral (insolvent; withdraw re-proves solvency). The $20 bad debt is stuck until the owner executes `force_socialize_bad_debt` — an operation an unprivileged keeper can no longer perform.
