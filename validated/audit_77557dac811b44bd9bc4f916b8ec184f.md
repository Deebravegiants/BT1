### Title
Webhook `shop` / `topic` / `webhook_id` identity fields are trusted from unauthenticated HTTP headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives its `shop`, `topic`, `webhook_id`, and `api_version` values from HTTP headers, but `Utils::HmacValidator` only verifies the HMAC over the raw request body (`to_signable_string` returns `@raw_body`). The tenant-identifying header (`shop-domain`) is never bound into the signed bytes, so `Registry.process` hands the caller-supplied, unauthenticated `shop` value to the app's webhook handler as if it were verified.

### Finding Description
`Request#to_signable_string` signs only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from headers with no cryptographic binding to that body: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header value — it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` validates the HMAC (of the body only) and then trusts `request.shop`, `request.topic`, and `request.webhook_id` directly to construct `WebhookMetadata` passed to the app's handler: [4](#0-3) [5](#0-4) 

The binding that should hold is: `hmac == HMAC(secret, shop ‖ topic ‖ webhook_id ‖ body)`, so that the tenant identity is cryptographically tied to the signature. Instead the actual binding is `hmac == HMAC(secret, body)` while `shop` is taken from an untrusted header (`Request#shop`), i.e. the equality the gem should enforce (`authenticated_shop == header_shop`) is never checked — headers are trusted wholesale once the body's HMAC checks out.

### Impact Explanation
Because the `shop-domain` header is not covered by the signature, a party capable of capturing/observing one valid `(raw_body, hmac)` pair for a webhook — e.g., a webhook delivered to their own store, or any request with a body/HMAC pair they can obtain — can replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) headers to claim it originates from a different, victim shop. `Registry.process` will pass HMAC validation (since the body is unchanged and the secret-derived signature still matches) and deliver `WebhookMetadata` labeling the payload as belonging to the attacker-chosen `shop`. Any host application that keys tenant-scoped state (e.g., resource ownership, session lookups, per-shop data mutation) off `WebhookMetadata#shop` as returned by this gem is misled into cross-tenant processing — the exact failure mode called out in the rules ("a field acted on but not covered by the HMAC" breaking a shop-identity binding).

### Likelihood Explanation
Exploitability requires the attacker to already possess at least one legitimate `(body, hmac)` pair — which they can obtain for their own store by registering/receiving webhooks on their own shop (a fully unprivileged, self-service action) — and to freely control the transport-layer headers sent to the app's webhook endpoint, both of which are realistic for an unprivileged internet actor since they don't require the app's `client_secret`, an access token, or any privileged credential.

### Recommendation
Bind the tenant/topic identity into the signed material, or otherwise cryptographically verify `shop-domain`/`topic`/`webhook-id` against the body before trusting them: incorporate these header values into `to_signable_string` (or validate them independently against Shopify's known good values, e.g., confirming the `shop` corresponds to a shop with an active session/install) instead of trusting them as bare headers once only the body's HMAC has been checked.

### Proof of Concept
1. Register a webhook handler for topic `orders/create` and receive one legitimate webhook delivery for your own store `attacker-shop.myshopify.com`; capture its `raw_body`, and the `X-Shopify-Hmac-Sha256` header value computed over that body.
2. Send a POST to the app's webhook endpoint reusing that exact `raw_body` and `X-Shopify-Hmac-Sha256` value, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and any desired `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. Using `ShopifyAPI::Webhooks::Registry.process`, this reaches: [4](#0-3) 
`Utils::HmacValidator.validate(request)` returns `true` (body/HMAC pair unchanged), and the handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though that value was never authenticated — demonstrating the header/HMAC binding break.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
