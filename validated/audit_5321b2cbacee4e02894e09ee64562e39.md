This confirms the exploitable pattern: `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) trusts `request.shop` (the `X-Shopify-Shop-Domain` header) as the tenant identity for the dispatched `WebhookMetadata`, while `Utils::HmacValidator.validate(request)` only verifies `request.to_signable_string`, which is defined as `@raw_body` — the header is never part of the signed content.

### Title
Webhook tenant identity (`shop-domain` header) is not covered by the HMAC, allowing shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` verifies solely the JSON payload bytes against `X-Shopify-Hmac-Sha256` [2](#0-1) . The `shop` (`X-Shopify-Shop-Domain`), `topic`, and `webhook_id` headers are read separately from HTTP headers and are not included in the signable string [3](#0-2) .

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identifier passed to the host app's handler via `WebhookMetadata` [4](#0-3) . Because the `shop-domain` header is never part of the signed bytes, the equality the gem implicitly claims — "the shop asserted in the HMAC-verified request equals `request.shop` used by the handler" — does not hold. An attacker who obtains any one validly-signed webhook body for a given app (bodies can be identical/predictable across shops for many topics, e.g. `shop/redact`, `app/uninstalled`, or topics with static/guessable payloads) can replay that exact body with a forged `X-Shopify-Shop-Domain` header value for a different shop, and the HMAC check in `Utils::HmacValidator.validate` will still pass, since it only recomputes the digest over `@raw_body` [5](#0-4) . Any host application that uses `WebhookMetadata#shop` to select per-tenant data, credentials, or session records (the documented intended use of this metadata) will act on the attacker-chosen shop identity while believing the request is HMAC-authenticated for that shop, breaking the tenant boundary this gem is documented to enforce with `HmacValidator`.

### Impact Explanation
This qualifies as Critical — cross-tenant access: the gem's own webhook signature verification is advertised as proof that the whole request (including which shop it originated from) is authentic, but the shop binding is not cryptographically covered. Downstream apps that key off `WebhookMetadata#shop` (as instructed by this library's public API) can be tricked into applying webhook data/actions to the wrong tenant, purely by an attacker manipulating an unauthenticated HTTP header while replaying a body they can obtain (e.g., their own valid webhook for their own shop, or any body that is not shop-specific).

### Likelihood Explanation
Requires no credentials from the victim tenant and no knowledge of `api_secret_key`: the attacker only needs to have received (or predicted) one valid signed webhook body from Shopify (trivial for their own test shop or app-uninstall/GDPR-style topics whose payload does not embed the shop), then can replay it with an arbitrary `shop-domain` header value to the app's webhook endpoint. The library performs no cross-check between the header-derived `shop` and any value inside the signed body.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or otherwise cryptographically bind them, e.g. by validating them against a value embedded in the body, or documenting/enforcing that host apps must never trust `WebhookMetadata#shop` without independent verification, e.g. against the topic's expected shop from `parsed_body`). At minimum, `Registry.process` should refuse to dispatch when the header-derived shop cannot be corroborated by data inside the HMAC-covered body.

### Proof of Concept
```ruby
# Attacker records one legitimately-signed webhook (their own shop, e.g. "attacker.myshopify.com")
raw_body = '{"id": 1}' # any real webhook payload received from Shopify for attacker's own shop
valid_hmac = "<hmac-sha256 header from the legit request>"

# Replay against the target app's webhook endpoint, changing only the shop-domain header
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,       # unchanged, still validates: signs only raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged tenant
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (only raw_body is checked)
# => handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))
# The host app's handler now processes data under the wrong/attacker-chosen tenant identity.
```

Note: I could not fully verify how a specific host application consumes `WebhookMetadata#shop` (that logic lives outside this gem), but the gem's own code path from `Registry.process` through `WebhookMetadata` unconditionally trusts the unsigned header, which is the root cause within this library's scope.
