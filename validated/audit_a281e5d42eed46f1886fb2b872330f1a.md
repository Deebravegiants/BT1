Confirmed: `ShopValidator` is used in `lib/shopify_api/auth/client_credentials.rb`, `lib/shopify_api/auth/refresh_token.rb`, and `lib/shopify_api/clients/graphql/storefront.rb`, but it is **not** used anywhere in `lib/shopify_api/auth/oauth.rb` (`begin_auth` / `validate_auth_callback`) nor in `lib/shopify_api/auth/token_exchange.rb`'s `exchange_token`. This is the analog worth reporting: the library added a "trusted domain" guard (`ShopValidator.sanitize!`) for several flows that build request hosts, but the original Authorization Code Grant flow that sends the app's `client_secret` to a caller-supplied `shop` host was left uncovered.

### Title
Unsanitized `shop` used to build OAuth access-token request host, allowing SSRF/exfiltration of `client_secret` - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` accept a `shop` string and use it directly, without going through `ShopifyAPI::Utils::ShopValidator.sanitize!`, to build the host that receives the app's `client_secret` during the OAuth access-token exchange.

### Finding Description
`begin_auth` takes a caller-supplied `shop:` and passes it straight to `auth_base_uri(shop)`, which builds `"https://#{shop}/admin"` with no domain validation [1](#0-0) . In `validate_auth_callback`, the `shop` comes from `auth_query.shop`, which is HMAC-verified as part of the callback query string [2](#0-1) [3](#0-2) , but `shop` itself is never checked against `ShopValidator.TRUSTED_SHOPIFY_DOMAINS`; it's used verbatim to build `null_session` and issue the `POST /admin/oauth/access_token` request that carries `client_secret` in its body [4](#0-3) .

Compare this to the sibling flows that were hardened: `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token` all call `Utils::ShopValidator.sanitize!(shop)` before constructing the session used to target the `/admin/oauth/access_token` endpoint [5](#0-4) [6](#0-5) [7](#0-6) . `ShopValidator.sanitize!` was purpose-built to reject non-Shopify hosts and prevent exactly this class of issue [8](#0-7) . The CHANGELOG documents this as a deliberate security addition [9](#0-8) , but `oauth.rb`'s `begin_auth`/`validate_auth_callback` and `token_exchange.rb`'s `exchange_token` (which derives `dest_shop` from the JWT and also skips sanitization before building `shop_session`) were left out of that fix [10](#0-9) .

Because `begin_auth` is explicitly documented and intended to be reachable by an unauthenticated user hitting the app's own "login" route with an attacker-supplied `shop` query parameter (per the gem's own usage docs), a value such as `evil.example.com` (or a value crafted to be treated as a hostname, e.g. containing `@`, `/`, or unexpected characters) flows unchecked into `auth_base_uri`. This breaks the intended equality `hostname the client_secret is sent to == a Shopify-trusted domain`, which is precisely the identity binding `ShopValidator` exists to enforce elsewhere.

### Impact Explanation
If `shop` is attacker-influenced (as it is by design on the "start OAuth" route, since the shop domain is supplied before any authentication has occurred), the constructed `auth_base_uri`/callback host can point outside `*.myshopify.com`/`*.myshopify.io`/etc. In the callback path this directly determines the destination of the POST carrying the app's `client_secret` for the `/admin/oauth/access_token` exchange. This matches the report's "SSRF with the app's credentials" impact class.

### Likelihood Explanation
The `shop` parameter in `begin_auth` is explicitly meant to be taken from the login route before any trust is established (per `docs/usage/oauth.md`), so this code path is reachable by any unauthenticated internet user who can influence what shop value is submitted to the app's login endpoint. The `validate_auth_callback` path requires HMAC to pass first, which is only forgeable by someone possessing `api_secret_key` — the underlying risk there is lower unless the calling application forwards an unvalidated `shop` from `begin_auth` all the way through.

### Recommendation
Apply `Utils::ShopValidator.sanitize!` (or `sanitize_shop_domain`) to the `shop` value in `Oauth.begin_auth` before calling `auth_base_uri`, and to `auth_query.shop` in `Oauth.validate_auth_callback` before constructing `null_session`/issuing the access-token request. Apply the same treatment to `dest_shop` in `TokenExchange.exchange_token` for defense in depth, consistent with `ClientCredentials`, `RefreshToken`, and `TokenExchange.migrate_to_expiring_token`.

### Proof of Concept
1. Host application exposes `/login?shop=<value>` and passes `shop` straight to `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], ...)` (the documented usage pattern).
2. Attacker requests `/login?shop=evil.example.com`.
3. `auth_base_uri("evil.example.com")` returns `"https://evil.example.com/admin"` with no domain check [11](#0-10) , and the victim's browser is redirected there with the app's `client_id` and `redirect_uri`.
4. If the host application later completes a callback for that same `shop` value (e.g., because the attacker's server can complete an OAuth-like flow that satisfies the `state` cookie check and produces an HMAC for that shop — feasible if the app is a first/embedded party under the attacker's control, or via CSRF-like flow reuse), `validate_auth_callback` will build the access-token POST target from the unvalidated `auth_query.shop`, sending `client_secret` to that host [4](#0-3) .

        def auth_base_uri(shop)

        end
