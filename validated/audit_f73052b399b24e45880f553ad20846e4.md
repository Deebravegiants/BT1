### Title
Webhook shop-tenant identity spoofing via unsigned `X-Shopify-Shop-Domain` header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The webhook HMAC verification in this gem authenticates only the raw request body bytes, never the `shop-domain` header that the host application uses as the tenant identity for the delivered event. An attacker who possesses one genuine, validly-signed webhook payload (e.g., from their own shop, which they legitimately control since they installed the app) can resend that exact body/HMAC pair to the app's webhook endpoint while substituting a different value in the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header. `HmacValidator.validate` will report success because it only recomputes the HMAC over `to_signable_string`, which is just `@raw_body`. The forged `shop` value is then handed to the host application's handler as the "verified" tenant identity for that payload — a cross-tenant identity confusion.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

- `hmac` is decoded from the `hmac-sha256` header.
- `to_signable_string` returns only `@raw_body`.
- `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers via `shopify_header`, none of which are part of the signed material.

`Utils::HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string` and compares it against `verifiable_query.hmac`: [2](#0-1) 

`Registry.process` relies on that validation as the sole authenticity gate before trusting `request.shop`: [3](#0-2) 

The equality that should hold is: `shop bound inside the HMAC-signed bytes == shop used to construct WebhookMetadata and dispatched to the handler`. In reality: `shop` is parsed from an unsigned header, while the HMAC only covers `raw_body`. Before the attacker's request: a legitimate webhook for Shop A arrives with body B, `hmac-sha256` = HMAC(secret, B), and `shop-domain` = A — all consistent. After the attacker's replay: the same body B and the same valid `hmac-sha256` are resent, but `shop-domain` header is swapped to Shop B (a victim tenant the attacker does not control). `HmacValidator.validate` still returns `true` because it only checks `B` against the HMAC; `request.shop` now returns `"B"` (victim), and `WebhookMetadata.shop` is populated with the victim's domain even though the signed payload was never associated with that shop.

### Impact Explanation
Any host application that uses `request.shop` (surfaced to handlers via `WebhookMetadata#shop`) as the tenant key for de-duplication, authorization, or data writes will process an attacker-controlled webhook body under a different, victim shop's identity. This is a cross-tenant access primitive: data ostensibly belonging to Shop A's webhook event gets attributed and applied to Shop B without B ever having triggered or consented to it. This matches the report's cross-tenant impact class, achieved purely by manipulating unauthenticated header bytes that sit outside the HMAC boundary — directly analogous to the original bug's core defect, where the actor performing an action (unstaking) is never checked for rightful ownership of the token being acted upon.

### Likelihood Explanation
The attacker needs only: (1) legitimate use of the app on their own shop, which lets them capture one authentic `raw_body` + `hmac-sha256` pair from Shopify (no `api_secret_key` or access token needed — the header/body pair alone suffices since the signature check doesn't bind the shop), and (2) the ability to POST to the app's publicly reachable webhook endpoint with a modified `shop-domain` header. No credentials, TLS interception, or social engineering are required, only unprivileged internet access to the endpoint and one prior legitimate webhook delivery.

### Recommendation
Bind the tenant identity into the verified material: either include `shop`, `topic`, and `webhook_id` in `to_signable_string` so they are covered by the HMAC comparison, or require the host application to independently correlate the signed body against a shop that it has already authenticated via its own session/subscription records rather than trusting the unsigned header value from `Webhooks::Request#shop`. At minimum, document that `Request#shop` and other header-derived attributes are not covered by the HMAC and must not be used as an authorization or tenant-routing decision on their own.

).strip
# ^ Attacker legitimately obtains this pair from their own shop's real webhook delivery.

forged_headers = {

  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # swapped from attacker's own shop
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes despite shop having been swapped, because HMAC only covers raw_body:
