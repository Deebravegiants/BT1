## Analysis

The bug class in the report is: a setter/action can be manipulated to affect an identity/tenant-scoped value that isn't actually bound by the check meant to authorize the change. Mapped onto this gem's unprivileged-internet-user surface, the strongest analog is in the webhook processing pipeline, where the `shop` field that identifies *which tenant's data a webhook belongs to* is never covered by the HMAC signature that is supposed to authenticate the request.

### Root cause

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the HMAC exclusively over that signable string: [2](#0-1) 

But `Request#shop` is read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, which is completely outside the HMAC computation: [3](#0-2) 

`Registry.process` only validates the HMAC over the body, then forwards the header-derived, unauthenticated `shop` value straight into `WebhookMetadata`, which is what the host application's handler uses to attribute the event to a tenant: [4](#0-3) [5](#0-4) 

### The broken equality

The check the gem performs is: `HMAC(secret, raw_body) == received_hmac`.
The value the gem/host actually trusts and acts on is: `header["shop-domain"]`.

These are two different things — `shop` is never an input to the HMAC computation, so:

`shop_used_for_tenant_attribution != shop_covered_by_hmac` (the latter set is empty).

### Exploitability

`api_secret_key` is shared by the app across **all** installing shops (it is not per-tenant). Any unprivileged attacker who installs the target app on their own store legitimately receives real webhook deliveries with a valid `hmac-sha256` header computed by Shopify over the body. Because the header carrying the shop identity is not part of the signed content, the attacker can capture one such legitimate `(raw_body, hmac)` pair from their own shop and replay it to the app's public webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never looked at the shop header), and the host app's handler receives `WebhookMetadata.shop` set to the victim's domain with attacker-chosen body content — a cross-tenant spoofing/data-integrity break using only the attacker's own legitimate app installation, no secrets or victim credentials required.

### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from an HTTP header that is excluded from the HMAC signature verified by `Utils::HmacValidator`. Any app installer can replay a legitimately-signed webhook body from their own shop while swapping the `shop-domain` header to impersonate another tenant, since only the body — not the shop — is authenticated.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only, and `HmacValidator.validate_signature` compares `HMAC(api_secret_key, raw_body)` to the `hmac-sha256` header. The `shop` accessor reads `shopify-shop-domain`/`x-shopify-shop-domain`, a header untouched by this computation. `Registry.process` gates only on the HMAC of the body and then forwards this unauthenticated `shop` value into `WebhookMetadata`, the struct handed to the app's `WebhookHandler#handle` implementation as the trusted tenant identifier.

Because `api_secret_key` is one shared secret for the whole app (across all shops), a legitimately-installed attacker shop possesses valid `(body, hmac)` pairs signed by Shopify. Swapping the `shop-domain` header on replay does not invalidate the HMAC check, letting the attacker control the `shop` field the host application uses for tenant attribution while the HMAC "verification" passes.

### Impact Explanation
This breaks the tenant boundary the HMAC check is meant to enforce: an attacker who is merely a legitimate installer of the app can make the library report attacker-controlled webhook data as belonging to an arbitrary victim shop, corresponding to the Critical "cross-tenant access" category (or High if the host's business logic limits the blast radius).

### Likelihood Explanation
Requires only installing the target app on an attacker-controlled shop (a normal, unprivileged action) and replaying a captured webhook request with a modified header — no access to `api_secret_key`, access tokens, or the victim's credentials is needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`/`api_version`) into the signable content, or otherwise cryptographically tie the header values to the signed body before trusting them in `WebhookMetadata`. At minimum, document/enforce that consumers must independently validate `shop` against the session/shop that legitimately registered the webhook rather than trusting the header value outright.

### Proof of Concept
1. Install the target Shopify app on attacker-owned shop `attacker.myshopify.com`.
2. Trigger any webhook (e.g., `orders/create`) and capture the raw POST: body `B` and header `x-shopify-hmac-sha256: H` (valid, computed by Shopify with the app's shared secret).
3. Replay the exact same HTTP request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `Utils::HmacValidator.validate` still returns `true` (it only checks `B` against `H`), and `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, spoofing data as belonging to the victim tenant.
