### Title
Webhook `shop` and `topic` headers are not covered by the HMAC signature, allowing cross-tenant event spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read from unauthenticated HTTP headers. `Utils::HmacValidator.validate` only checks that the body matches the signature, then `Webhooks::Registry.process` trusts the header-derived `shop`/`topic` values when dispatching to the app's handler. This breaks the intended binding: `hmac_valid(body) == true` is treated as proof that `(shop, topic, body)` as a whole is authentic, when in fact only `body` is bound to the signature.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` verifies only `to_signable_string` (i.e., the body) against the `hmac` header: [3](#0-2) 

`Webhooks::Registry.process` gates on this body-only HMAC check and then forwards the *header-derived* `shop` and `topic` (not covered by the signature) to the application's webhook handler as if they were authenticated: [4](#0-3) 

The binding that should hold is: `hmac_valid == true` implies `(shop, topic, body)` is exactly what Shopify sent. In this implementation the actual invariant is only `hmac_valid == true` implies `body` is unmodified — `shop` and `topic` can be freely substituted by anyone who can reach the webhook endpoint with a previously-observed valid `(body, hmac)` pair, since the `api_secret_key` used for HMAC is shared across all shops/installs of the app, not tied to a specific tenant. This lets a request carry a genuine signature for its body while lying about which shop and topic it represents — exactly the "field acted on but not covered by the HMAC" analog: `shop_claimed_by_header != shop_actually_bound_by_hmac`.

### Impact Explanation
Because the `client_secret`/`api_secret_key` is common to the whole app (not per-merchant), any actor who can obtain one validly-signed webhook body/HMAC pair (e.g., a merchant who has installed the app themselves, or anyone who can observe a webhook delivery) can replay it to the app's public webhook endpoint with a different `x-shopify-shop-domain` (and/or `x-shopify-topic`) header. `HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` object asserting the spoofed shop/topic. If the host application uses `request.shop` to select tenant context, update tenant-scoped records, or make trust decisions (a common and expected usage pattern for this field, as shown by the gem's own `webhooks.md` docs and test suite), this results in cross-tenant data corruption or cross-tenant action execution — one merchant's event being attributed to and processed against another merchant's account.

### Likelihood Explanation
Exploitation requires only network access to the app's public webhook endpoint plus one legitimately-signed body (trivially obtainable by installing the app on any store, since the attacker only needs to be a normal, unprivileged merchant to receive their own valid webhooks) — no access to `api_secret_key`, access tokens, or any elevated privilege is required. The gem provides no mitigation (no per-shop secret, no inclusion of `shop`/`topic` in the signable string), so likelihood is significant wherever the host app is directly reachable and trusts `WebhookMetadata#shop`.

### Recommendation
Include `shop` and `topic` (and any other header fields relied upon by handlers) in the HMAC-signable string, or otherwise cryptographically bind them to the signed payload, so that `Utils::HmacValidator.validate` authenticates the full tuple `(shop, topic, body)` rather than the body alone. At minimum, document that `request.shop`/`request.topic` are unauthenticated and must not be trusted for tenant selection without independent verification (e.g., cross-checking against the session/shop that registered the webhook).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook delivery, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker crafts a new HTTP request to the app's webhook endpoint using:
   - `x-shopify-hmac-sha256: H` (unchanged)
   - body: `B` (unchanged)
   - `x-shopify-shop-domain: victim.myshopify.com` (spoofed)
   - `x-shopify-topic: orders/create` (same or different topic string chosen by attacker)
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: spoofed_headers)` is constructed; `request.hmac` decodes `H`, and `Utils::HmacValidator.validate(request)` recomputes `HMAC-SHA256(api_secret_key, B)` and finds it matches `H` — validation succeeds.
4. `Webhooks::Registry.process(request)` calls `handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: parsed_body, ...))`, causing the host application to process attacker-supplied order data under the victim shop's identity — a cross-tenant confusion the gem's HMAC check was supposed to prevent.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
