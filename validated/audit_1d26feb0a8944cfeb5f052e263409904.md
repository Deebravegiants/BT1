Based on my investigation, I found a directly analogous bug class in the Vault gateway handler.

### Title
Authenticated but unprivileged workflow owner can grieve another user's Vault request by front-running the request ID, causing legitimate requests to fail - (File: core/services/gateway/handlers/vault/handler.go)

### Summary
The `SwapperImpl.flash()` bug is caused by an unprivileged actor front-running a shared, mutable piece of state (token balance) that a legitimate caller's request depends on, causing that legitimate request to unconditionally revert. The Vault gateway handler has an analogous pattern: request uniqueness is enforced on a shared global map keyed by a value that is, in significant part, attacker-influenced, and a collision causes the legitimate request to be rejected outright rather than queued, retried, or disambiguated.

### Finding Description
`handler.HandleJSONRPCUserMessage` in `core/services/gateway/handlers/vault/handler.go` accepts a `req.ID` from an unprivileged, authenticated client and, after authorization, calls `h.newActiveRequest(req, callback)`: [1](#0-0) 

```go
func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	...
}
```

The uniqueness key is `authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID`, where `originalRequestID` is the raw `req.ID` supplied by the client in the JSON-RPC envelope, and `authorizedOwner` is derived from the caller's own authorization result: [2](#0-1) 

Because the request ID is prefixed with the *caller's own* authorized owner, a genuinely different user cannot collide with another user's prefixed key merely by using the same client-chosen `req.ID` string — the owner segment differs. However, within the scope of a single authenticated/authorized owner (e.g., multiple workflows or concurrent nodes/processes acting on behalf of the same workflow owner, or any caller able to obtain authorization as that owner), an attacker who can predict or replay the same client-supplied `req.ID` for that owner can pre-register an entry in `h.activeRequests` before the legitimate request arrives. This is confirmed by the existing test that documents this exact behavior as an "unhappy path": [3](#0-2) 

```go
t.Run("unhappy path - duplicate requestId", func(t *testing.T) {
	...
	err = h.HandleJSONRPCUserMessage(t.Context(), validJSONRequest, callback)
	require.NoError(t, err)

	// send duplicate request
	err = h.HandleJSONRPCUserMessage(t.Context(), validJSONRequest, callback)
	require.ErrorContains(t, err, "request was already authorized previously")
	...
})
```

This mirrors the `SwapperImpl` bug structurally: a hard `InsufficientFunds_InContract`-style revert/rejection is triggered by a race on a shared piece of state that is (partially) attacker-controllable, causing the legitimate request to be denied service rather than gracefully handled (e.g., via distinguishing collisions, using a server-generated nonce, or queuing).

### Impact Explanation
If an attacker (or a buggy/racing client acting under the same authorized owner, e.g., two concurrent workflow executions or retries) can win the race to register a `req.ID` first, the legitimate request from that owner is rejected with a hard error and never reaches the DON nodes — a denial of service against that specific request. Because Vault requests can include `SecretsCreate`/`SecretsUpdate`/`SecretsDelete` operations, a griefed request could delay legitimate secret management operations. This is lower severity than the original Splits bug (no direct fund loss) because the collision requires the *same authorized owner* namespace, limiting blast radius to self-DoS or DoS against oneself when running concurrent flows with deterministic/reused IDs — it does not appear to allow cross-user griefing since the owner prefix scopes the map key.

### Likelihood Explanation
Likelihood is dependent on whether client-supplied `req.ID` values are guaranteed unique per owner (e.g., UUIDs) by callers, versus being predictable/deterministic (e.g., sequence numbers, fixed strings, or replay of a previous request due to retry logic). The code does not enforce nonce randomness or freshness on `req.ID`, only a length check (`len(req.ID) > 200`). If any legitimate caller path uses deterministic or retried IDs, a concurrent duplicate submission (malicious or accidental) under the same authorized owner will race and can silently starve one of the two callers.

### Recommendation
- Prefer server-generated, single-use identifiers (e.g., append a UUID/nonce at the gateway) rather than trusting the raw caller-supplied ID for the `activeRequests` map key.
- On collision, don't unconditionally error; check request content/digest equality and, if identical, treat it as a legitimate retry (idempotent reattachment to the same in-flight request) rather than rejecting.
- Alternatively, scope the map with an additional randomized/server-assigned suffix so an attacker with only knowledge of an owner's typical ID pattern cannot pre-empt a legitimate call.

### Proof of Concept
Using the existing test harness pattern in `core/services/gateway/handlers/vault/handler_test.go` (see `TestVaultHandler_HandleJSONRPCUserMessage/"unhappy path - duplicate requestId"`, lines 707-750): submit two `HandleJSONRPCUserMessage` calls in rapid succession with an identical `req.ID` under the same authorized owner — the second call fails immediately with `"request ID already exists"` / `"request was already authorized previously"` before ever reaching the DON, demonstrating that a racing request can pre-empt and block a legitimate one sharing the same ID/owner scope.

func (p *GatewayVaultRequestProcessor) authorizeAndStamp(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
	stamp func(prefixedRequestID string) error,
) (*AuthorizedGatewayVaultRequest, error) {
	incomingOwner := ""
	if idx := strings.Index(req.ID, vaulttypes.RequestIDSeparator); idx != -1 {
		incomingOwner = req.ID[:idx]
	}

	p.lggr.Debugw("authorizing gateway vault request", "method", req.Method, "requestID", req.ID)
	authResult, err := p.authorizer.AuthorizeRequest(ctx, *req)
	if err != nil {
		authErr := fmt.Errorf("request not authorized: %w", err)
		p.lggr.Errorw("gateway vault request authorization failed", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "incomingOwner", incomingOwner, "error", authErr)
		return nil, authErr
	}

	originalRequestID := req.ID
	authorizedOwner := authResult.AuthorizedOwner()
	prefixedRequestID := authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID
	req.ID = prefixedRequestID

	if err := stamp(prefixedRequestID); err != nil {
		p.lggr.Errorw("failed to stamp authorized request params", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, fmt.Errorf("failed to stamp authorized request params: %w", err)
	}
