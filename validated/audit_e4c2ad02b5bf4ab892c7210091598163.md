This confirms the vulnerability. The `SubstrateCalldata` signature verification in `pallet-hyper-fungible-token::module.rs` `on_accept` reads the beneficiary's *current, live* `frame_system::Pallet::<T>::account_nonce(beneficiary)` at the moment the cross-chain message is processed on the destination chain — not a nonce value the sender fixed at signing time. This is precisely the same bug class as the `EnforcedTxGateway` report: the value being signed over is a "next expected" counter that can drift between when the user signs off-chain and when the message is actually delivered/executed on-chain.

### Title
Cross-chain calldata signatures in pallet-hyper-fungible-token are signed against a live account nonce that can change before message delivery, causing legitimate signed calls to permanently fail - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` executes optional destination-chain calldata authorized by a beneficiary signature over `(nonce, runtime_call)`, where `nonce` is fetched live from `frame_system::Pallet::<T>::account_nonce(beneficiary)` at message-processing time rather than being a value fixed and delivered as part of the signed cross-chain message. [1](#0-0)  Because the beneficiary must sign this payload off-chain before the ISMP request is dispatched, relayed, and finally delivered on the destination chain, any unrelated extrinsic that increments the beneficiary's `frame_system` account nonce in that window (a normal transfer, a different pallet call, etc.) invalidates the signature, exactly the same race the `EnforcedTxGateway` report describes for the L1→L2 queue index.

### Finding Description
The flow is: (1) a source-chain sender calls `send` with `call_data` containing a `SubstrateCalldata { signature, runtime_call }`, where `signature` is produced off-chain by the beneficiary signing `keccak256((nonce, runtime_call).encode())` using *the nonce value the beneficiary read at signing time*. [2](#0-1)  (2) The ISMP request travels through consensus/relaying to the destination chain, an inherently unbounded and unpredictable delay. (3) On delivery, `on_accept` re-derives the nonce to check the signature against by calling `frame_system::Pallet::<T>::account_nonce(beneficiary.clone())` — i.e., whatever the beneficiary's `frame_system` nonce is *at execution time*, not the value that was actually signed. [3](#0-2)  If the beneficiary submits even one unrelated signed extrinsic on the destination chain between signing the calldata authorization and the cross-chain message's delivery, `frame_system`'s nonce advances, the recomputed hash no longer matches what was signed, and verification fails with `HftError::SignatureVerificationFailed` for all three signature schemes (Ed25519, Sr25519, ECDSA). [4](#0-3)  This mirrors the report's root cause precisely: a signed message binds itself to a shared, externally-mutable sequence counter instead of a value fixed by the signer and delivered with the message (a proper nonce field or the replay-protection mapping the report recommends).

Additionally, the token transfer/mint to the beneficiary happens *before* the calldata signature check in the same `on_accept` call. [5](#0-4)  Since `on_accept` returns `Err` on signature failure, the whole PostRequest handling errors out; depending on `pallet-ismp`'s transactional wrapping of `on_accept`, this either reverts the token credit (leaving the request stuck, unable to be delivered, since a resubmission with the correct calldata is not possible for an already-processed request/commitment) or, if not fully transactional, leaves tokens credited while the intended follow-on call silently fails to execute — either way the cross-chain intent (mint + authorized call) cannot be delivered as designed.

### Impact Explanation
This breaks message delivery for a documented, user-facing feature (cross-chain calldata execution) whenever there is any real-world delay between signing and delivery combined with beneficiary activity on the destination chain — a common and even adversarial-inducible condition, since anyone can grief a target beneficiary by getting them to sign literally any transaction on the destination chain (or the beneficiary may simply use their account normally) before the cross-chain message lands. The result is legitimate signed cross-chain calls becoming permanently unexecutable once in flight, since the request cannot be re-signed and resubmitted (the underlying PostRequest/commitment is already fixed). This falls under "a route unable to deliver messages" / "unauthorized app action" from an availability standpoint — the promised calldata execution silently and unrecoverably fails despite a valid, honestly-signed authorization.

### Likelihood Explanation
Likelihood is high in practice: any account that transacts even once on the destination chain between signing off-chain and cross-chain delivery — which given consensus/finality and relayer delays is essentially guaranteed for any moderately active account — will have its signature invalidated. No attacker action is even required, though a malicious actor could deliberately induce a beneficiary's other transactions to weaponize this against a specific pending cross-chain call.

### Recommendation
Do not verify against a live, externally-mutable counter. Instead:
- Have the sender's `send` call capture the beneficiary-signed nonce (or a nonce namespace scoped to this pallet, e.g. `pallet_hyper_fungible_token::Nonce::<T>::get(beneficiary)`) into the dispatched `Message`/`SubstrateCalldata` payload itself as an explicit field, and verify it against that pallet-local nonce (incrementing it after use, as is already done for `WithdrawalInputData`/`beneficiary_message` elsewhere in the relayer pallet). [6](#0-5) 
- Alternatively, adopt the report's own recommendation: replace the shared/external counter with a pallet-owned, monotonically-incrementing nonce dedicated to this signing purpose (not `frame_system`'s account nonce, which is mutated by unrelated activity), plus a deadline/expiry to bound how long a signature stays valid, matching the `nonce` + `deadline` pattern used throughout the rest of the codebase (e.g. Permit2/EIP-712 flows, `pallet-ismp-relayer` withdrawal and accumulate-fees signatures). [7](#0-6) 

### Proof of Concept
1. Beneficiary B holds `frame_system` account nonce `n` on destination chain D.
2. A user on source chain S calls `send` with `call_data` = `SubstrateCalldata { signature: Sig_B(keccak256((n, runtime_call).encode())), runtime_call }`, dispatching an ISMP PostRequest to D.
3. Before the request is relayed and delivered, B submits any ordinary signed extrinsic on D (e.g., a `balances::transfer`), advancing B's `frame_system` nonce to `n+1`.
4. The ISMP request is delivered and `on_accept` runs: it recomputes `nonce = frame_system::Pallet::<T>::account_nonce(B) = n+1` and hashes `(n+1, runtime_call)`, which does not match the signature B produced over `(n, runtime_call)`. [8](#0-7) 
5. `HftError::SignatureVerificationFailed` is returned, matching the assertion pattern in the existing test that only replays (i.e., re-submitting the *same* request after its own nonce increment) are checked, but a delayed first-time delivery hitting an already-advanced nonce fails identically — confirmed by the same code path exercised in `should_receive_asset_with_calldata`'s replay check. [9](#0-8)
