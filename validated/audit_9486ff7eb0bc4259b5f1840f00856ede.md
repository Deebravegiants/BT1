### Title
Missing fee-vs-amount validation in `createWithdrawalIntents()` allows negative `actualAmount` to be signed into a withdrawal intent - (File: packages/intents-sdk/src/sdk.ts)

### Summary
`IntentsSDK.createWithdrawalIntents()` computes `actualAmount = amount - feeEstimation.amount` when `feeInclusive` is true, but — unlike the sibling method `_estimateWithdrawalFee()` — it never asserts that `amount > feeEstimation.amount` before doing the subtraction.

### Finding Description
In `_estimateWithdrawalFee()`, before subtracting the fee from the requested amount, the SDK explicitly guards against the fee exceeding the amount: [1](#0-0) 

```
if (args.withdrawalParams.feeInclusive) {
    if (args.withdrawalParams.amount <= fee.amount) {
        throw new FeeExceedsAmountError(fee, args.withdrawalParams.amount);
    }
}
const actualAmount = args.withdrawalParams.feeInclusive
    ? args.withdrawalParams.amount - fee.amount
    : args.withdrawalParams.amount;
```

However, the public `createWithdrawalIntents()` entry point — which is the method that actually builds and signs the withdrawal intent primitives that get executed on-chain — performs the identical subtraction **without** the corresponding `FeeExceedsAmountError` guard: [2](#0-1) 

```
public async createWithdrawalIntents(args: {
    withdrawalParams: WithdrawalParams;
    feeEstimation: FeeEstimation;
    referral?: string;
    logger?: ILogger;
}): Promise<IntentPrimitive[]> {
    for (const bridge of this.bridges) {
        if (await bridge.supports(args.withdrawalParams)) {
            const actualAmount = args.withdrawalParams.feeInclusive
                ? args.withdrawalParams.amount - args.feeEstimation.amount
                : args.withdrawalParams.amount;

            await bridge.validateWithdrawal({
                assetId: args.withdrawalParams.assetId,
                amount: actualAmount,
                ...
```

This is exactly analogous to the reported bug class: a downstream signed/executed value (`actualAmount`, which flows into `ft_withdraw`/`mt_withdraw`/`native_withdraw` intents and `token_diff` computations) is derived by subtracting a fee from an amount without first checking that the subtraction cannot go negative/underflow — mirroring `EnforceClientCUsUsageInEpoch`'s unchecked arithmetic that produced a value whose sign no longer matched the intended semantics.

Because `feeEstimation` is caller-supplied input to `createWithdrawalIntents` (a caller can obtain a `FeeEstimation` from an earlier quote and pass it directly, or construct one), an attacker/integrator-controlled `feeEstimation.amount` that is `>= amount` produces a negative `bigint` for `actualAmount`. This negative amount is then passed to `bridge.validateWithdrawal()` and `bridge.createWithdrawalIntents()`.

### Impact Explanation
Whether this is actually exploitable to move funds depends on whether every bridge implementation (`omni-bridge.ts`, `direct-bridge.ts`, `poa-bridge.ts`, `hot-bridge.ts`) independently asserts `amount > 0n` before constructing the on-chain `ft_withdraw`/`token_diff` intent. I was only able to confirm the `assertAmount`-style guard pattern in a subset of files (`aurora-engine-bridge-utils.ts`, `direct-bridge-utils.ts`, `omni-bridge.ts`, `poa-bridge-utils.ts` each contain one `amount` assertion, per `grep_search`), but I was unable to view their full bodies before the iteration budget ran out, so I cannot confirm with certainty that a negative `actualAmount` is rejected in every bridge path, or trace what a negative `amount` string (e.g., `"-500"`) would do inside `token_diff`/`ft_withdraw` JSON payloads once serialized into the signed NEP-413/ERC-191 intent message. If any bridge path lacks that guard, a negative `amount` field would be serialized directly into the signed intent (`amount: actualAmount.toString()`), producing either a runtime rejection on-chain or, in the worst case, an intent whose stringified amount is malformed/negative, which would not match "amount plus fee once" semantics and could misstate the debit encoded in the user's signed payload.

### Likelihood Explanation
Exploitability requires the caller of `createWithdrawalIntents()` to supply (or be tricked into supplying) a `feeEstimation` whose `amount` is greater than or equal to the withdrawal `amount` while `feeInclusive: true`. Since `feeEstimation` is typically obtained from `estimateWithdrawalFee()` (which does have the guard) and reused within the same call site, exploiting this in the SDK's own default flow is unlikely under normal usage. However, `createWithdrawalIntents()` is a public method that accepts `feeEstimation` as a parameter independent of any freshness or origin check, so any integrator who caches, reuses, or externally constructs a `feeEstimation` object (e.g., across sessions, from a stale quote, or from a different route) can trigger the unguarded subtraction. This is a real gap in defense-in-depth even though the primary flow closes it earlier.

### Recommendation
Add the same `FeeExceedsAmountError` check present in `_estimateWithdrawalFee()` to `createWithdrawalIntents()` before computing `actualAmount`, e.g.:
```
if (args.withdrawalParams.feeInclusive && args.withdrawalParams.amount <= args.feeEstimation.amount) {
    throw new FeeExceedsAmountError(args.feeEstimation, args.withdrawalParams.amount);
}
```
This ensures the invariant `actualAmount >= 0` holds at every entry point that derives a signed withdrawal amount from a fee subtraction, not just the estimation path.

### Proof of Concept
1. Call `sdk.createWithdrawalIntents({ withdrawalParams: { amount: 100n, feeInclusive: true, ... }, feeEstimation: { amount: 150n, ... } })` directly (bypassing `estimateWithdrawalFee`/`_estimateWithdrawalFee`, e.g. using a fee estimation cached from an earlier, larger withdrawal or a manually constructed object).
2. Inside `createWithdrawalIntents()` (`packages/intents-sdk/src/sdk.ts:342-344`), `actualAmount = 100n - 150n = -50n`, with no assertion blocking this.
3. `-50n` flows into `bridge.validateWithdrawal({ amount: -50n, ... })` and `bridge.createWithdrawalIntents({ withdrawalParams: { ...args.withdrawalParams, amount: -50n }, ... })`, exactly as the report's `rewardedCU` negative value flowed unchecked into `chargeCuToSubscriptionAndCreditProvider`.

Confidence note: I could not fully verify within the remaining tool budget whether every individual bridge's `createWithdrawalIntents`/`validateWithdrawal` implementation independently rejects a negative `amount` before it reaches a signed intent payload. This should be verified by reading the full bodies of `direct-bridge.ts`, `omni-bridge.ts`, `poa-bridge.ts`, and `hot-bridge.ts` (specifically their `assert`/validation calls on `amount`) to determine whether this gap is fully mitigated downstream or is a live path to a malformed signed intent.
