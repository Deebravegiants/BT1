### Title
Session hijacking via guessable, unsigned session-ID cookie bound only to public shop domain - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` trusts the raw, unauthenticated value of the app's session cookie as the lookup key for a merchant's stored `Session` (which contains the merchant's access token), and `ShopifyAPI::Auth::Session.id`/`Oauth.validate_auth_callback` construct that same session ID deterministically from public information (`shop` domain, and for online sessions the Shopify user id). Because the ID space is predictable and the cookie value is never cryptographically bound to the browser that completed OAuth, an attacker who can place an arbitrary cookie value in a victim's browser (or who probes the app directly with a forged cookie) can cause the gem to resolve to another merchant's session.

### Finding Description
For non-embedded apps, `Oauth.validate_auth_callback` sets the session cookie's *value* to the deterministic session id: [1](#0-0) 

That id is generated in `Auth::Session.from` as `"#{shop}_#{associated_user.id}"` for online tokens or `"offline_#{shop}"` for offline tokens: [2](#0-1) 

Later, when the host application asks the gem which session is "current," `SessionUtils.current_session_id` simply reads this cookie value back out with no signature, MAC, or origin check at all: [3](#0-2) [4](#0-3) 

The identity binding that should hold is:
`session_id (used to fetch session/access token) == session_id (issued by this gem to the browser that actually completed the OAuth handshake for that specific shop)`

But because:
1. the session id is a deterministic function of public data (`shop` domain — commonly guessable/enumerable, e.g. `<name>.myshopify.com`, plus for online sessions a numeric Shopify user id which is often small/sequential or discoverable), and
2. `cookie_session_id` performs zero verification of the cookie's authenticity/origin before it is used as a session-store lookup key,

any party who can set an arbitrary cookie value in a victim's browser for the app's domain (e.g., via a subdomain cookie-tossing bug, a shared parent domain, an XSS on a sibling path, or simply by convincing the app/browser via response-splitting or a misconfigured `Set-Cookie` on a shared host) can force that browser's session id to equal `offline_<victim-shop>.myshopify.com`. The gem will then have `current_session_id` return that attacker-chosen, victim-owned identifier, and the host application will look up and use the victim merchant's stored offline access token for the attacker's subsequent requests to the app, without either the JWT/HMAC verification path (`JwtPayload`, `HmacValidator`) ever being consulted, since the cookie path is a completely independent, unauthenticated code path in `current_session_id`.

This is distinct from normal cookie tampering risk because the vulnerability is not merely "the cookie can be tampered with" — it is that the **value the gem itself chooses to store in the cookie is a low-entropy, predictable identifier tied only to public shop/user data**, so guessing or forcing that value is sufficient to select another tenant's session, with no cryptographic secret involved at any point in this cookie path.

### Impact Explanation
If exploited, an attacker can cause the library to resolve to and operate under another merchant's stored `Session`, including that merchant's OAuth access token, purely by controlling/guessing a cookie value — a cross-tenant session/access-token compromise, matching the Critical class ("cross-tenant access", theft of a merchant access token) called out in scope. No secret, no TLS interception, and no privileged access to Shopify is required — only the ability to set a cookie value in the victim's browser context for the app's domain, which is a class of unprivileged web attacker capability (subdomain cookie scope issues, shared-domain cookie tossing, or a forced/predicted value on first visit before OAuth is even completed).

### Likelihood Explanation
Exploitability depends on the host application's cookie scoping/hosting setup (shared domains, subdomains, or any mechanism letting a third party set a cookie for the app's origin) — this is a reasonably common real-world pattern for multi-tenant SaaS apps hosted on shared infrastructure (e.g., `*.herokuapp.com`, shared PaaS domains) and for apps that don't scope cookies tightly. The shop domain portion of the ID is always public (merchants routinely disclose `*.myshopify.com`), so the only real "secret" component for online sessions is the Shopify numeric user id, which is not treated as a secret by Shopify and is often observable/enumerable. The offline-session id (`offline_#{shop}`) has effectively zero secret component at all.

### Recommendation
- Never use the raw, predictable session id (`shop`/`shop_user_id`) as the cookie *value* that is later trusted as a store lookup key with no additional verification. Instead, issue a high-entropy, unguessable, unrelated session token (e.g. `SecureRandom.uuid`/`SecureRandom.hex(32)`) as the cookie value, and keep the shop-derived id as an internal storage key looked up only after the opaque cookie token is validated against server-side state.
- Sign or HMAC the cookie value with the app's `api_secret_key` (similar to `Utils::HmacValidator`) so that `SessionUtils.cookie_session_id` can reject any cookie value that wasn't issued by this gem for that specific session.
- Document/enforce that host apps must set the session cookie with `secure`, `HttpOnly`, and a tightly scoped `domain`/`path`, and reject cookies that don't match the expected format before doing any storage lookup.

### Proof of Concept
1. Host app A (using this gem, non-embedded) installs for merchant `victim-shop.myshopify.com`; per `Session.from`, the resulting offline session id is `offline_victim-shop.myshopify.com` and, per `Oauth.validate_auth_callback`, this exact string is written as the session cookie value in the victim merchant admin's browser.
2. Attacker, who can set a cookie for the app's origin in their own browser (e.g., because the app is hosted on a shared/wildcard domain, or via any cookie-scope weakness on a sibling subdomain/path under the app's control), sets:
   `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`
3. Attacker issues a normal request to the app. The host app calls `SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` verbatim with no validation (`lib/shopify_api/utils/session_utils.rb:19-37`, `68-71`).
4. The host app's session storage returns the victim merchant's `Session` object (containing their real access token) for that id, and the attacker's subsequent API calls execute using the victim's access token/tenant context.
