### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read from HTTP headers that are never included in the HMAC computation. `ShopifyAPI::Webhooks::Registry.process` verifies the HMAC and then unconditionally hands `request.shop` to the app's handler as the authenticated tenant identity, even though that value was never bound to the signature.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the received `hmac`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to return only `@raw_body`: [2](#0-1) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all sourced from HTTP headers that are outside the signed payload: [3](#0-2) 

`Registry.process` verifies the HMAC (over the body only) and then dispatches to the handler using the *unverified* `request.shop` value as the tenant identity: [4](#0-3) 

The broken identity binding is:
`shop authenticated by HMAC` (nothing — HMAC covers only `raw_body`) ≠ `shop delivered to the handler as the trusted tenant key` (`request.shop`, read straight from the `x-shopify-shop-domain` header).

Because the shared secret used for webhook HMACs is the app's single `client_secret` (identical for every shop that installs the app), any tenant that has installed the same app already possesses a stream of validly-signed `(body, hmac)` pairs for their own shop. Since the header carrying the shop identity is completely outside that signature, an attacker who controls one installation of the app can replay a genuine, validly-signed body while substituting the `x-shopify-shop-domain` (or its `shopify-shop-domain` alias) header with a victim shop's domain. `Utils::HmacValidator.validate` will still return `true` (the body/HMAC pair is untouched), and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the victim's domain, causing the host application to attribute an attacker-supplied event/body to a different tenant.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged internet user who is merely a legitimate customer/merchant of the same app can cause the app to process attacker-controlled webhook data under another shop's identity, because the shop identity is never cryptographically bound to the signature that the gem verifies. Any host application that follows the gem's documented pattern (`Registry.process` → handler keyed off `WebhookMetadata#shop`) inherits this cross-tenant exposure directly from the gem's own verification logic, not from misuse of the API.

### Likelihood Explanation
The attacker needs no credentials beyond installing the target app on a shop they control (the normal, unprivileged install flow), and needs only to relay/replay one legitimate webhook delivery with a modified header — no cryptographic secret, session, or access token is required to forge the tenant binding.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the HMAC-signable string for `ShopifyAPI::Webhooks::Request`, or otherwise cryptographically bind the shop domain to the signed payload before it is trusted in `Registry.process`/`WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` and lets Shopify deliver a genuine webhook (e.g. `orders/create`) to the app's endpoint, capturing the raw body `B` and its valid header `x-shopify-hmac-sha256: H` (computed by Shopify over `B` using the app's shared `client_secret`).
2. Attacker resends the same request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but replacing `x-shopify-shop-domain` with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`, so `Registry.process` proceeds and calls the handler with `WebhookMetadata#shop == "victim.myshopify.com"`, even though the payload actually originated from and was signed by the attacker's own shop's traffic.

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
