### Title
Webhook `shop` identity is not bound to the HMAC signature, allowing cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC over the raw request body only, then dispatches to the app's handler using the shop identity taken from the `X-Shopify-Shop-Domain` HTTP header — a field that is never included in the HMAC computation. Any party who can obtain one validly-signed webhook body (e.g., by installing the app on their own shop and triggering a webhook) can replay that exact body to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop, and the library will accept it as authentic for the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is derived purely from the (unauthenticated) `shopify-shop-domain` / `x-shopify-shop-domain` header, which is disjoint from the signed content: [2](#0-1) 

`Registry.process` validates only that the HMAC matches `to_signable_string` (i.e., the body), and then immediately trusts `request.shop` — sourced from the un-signed header — to construct the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

This breaks the identity binding: **shop authenticated (bytes verified by HMAC) ≠ shop acted on (bytes read from the header and handed to the app as the tenant identity)**. Before the attacker's request: `HMAC(secret, body) == hmac_header` proves the body is untampered and was signed by Shopify for *some* shop, but says nothing about which shop. After the attacker's request: the gem still reports `request.shop == attacker-chosen value`, while the cryptographic proof only covers the body bytes. Because the header is not part of the signable string, any body that Shopify has legitimately signed for the attacker's own shop can be resent by the attacker to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim `myshopify.com` domain, and `Utils::HmacValidator.validate(request)` (which itself only calls `verifiable_query.to_signable_string`) will still return `true`.

### Impact Explanation
This is a cross-tenant identity confusion: content that Shopify only ever certified for shop A is delivered to the app's business logic tagged as belonging to shop B. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up the session/store record to update, to trigger `app/uninstalled` cleanup, to write order/customer data, or to invalidate a shop's cached token), an attacker can inject attacker-controlled webhook payloads into another merchant's tenant context without ever needing that merchant's credentials — meeting the "cross-tenant access" bar for High/Critical impact.

### Likelihood Explanation
Exploitation only requires: (1) the attacker's own shop can install the app and receive at least one real webhook (trivial for any public app, and even for private/custom apps that allow installation on attacker-controlled dev stores), and (2) network access to POST to the app's public webhook endpoint with arbitrary headers — both are unprivileged-internet-user-level capabilities. No secrets, tokens, or TLS interception are needed, matching the "shop authenticated vs. shop used for dispatch" pattern called out in the analog rules.

### Recommendation
Include the shop domain (and ideally topic/api-version/webhook-id) in the HMAC-signed payload used by `to_signable_string`, or otherwise cryptographically bind the accepted `shop` value to the verified body (e.g., require the shop to also be embedded/verified inside the parsed JSON body against a known list of installed/authorized shops before dispatching). At minimum, document that consumers of `WebhookMetadata#shop` must independently verify the shop is one they have a valid session for before trusting the payload's shop attribution.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; capture a legitimately-signed webhook, e.g. `orders/create`, with headers `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker.myshopify.com`, and body `B`.
2. Replay the identical body `B` and HMAC `H` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) — it matches `H`, so validation succeeds.
4. `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` is invoked with `shop: "victim.myshopify.com"`, even though Shopify never signed anything for `victim.myshopify.com`. [4](#0-3) [5](#0-4)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
