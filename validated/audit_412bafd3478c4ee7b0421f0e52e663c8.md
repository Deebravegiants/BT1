## Title
Unchecked low-level `transfer` return value in Tron `IntentGatewayV2.withdraw` permanently drains/loses escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed order tokens using a raw low-level `.call()` with the `IERC20.transfer.selector`, checking only that the external call did not revert (`success`) but never validating the ABI-decoded boolean return value. This is the exact "unchecked send" class described in the report — using `transfer` without confirming success — except here it's disguised behind a low-level `call` whose `success` flag only reflects that the callee didn't revert, not that the token transfer actually happened.

### Finding Description
In `withdraw()`, escrowed tokens are released to a beneficiary via: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

The same unchecked pattern is repeated for transaction fee payout and dust sweeping in the same file: [2](#0-1) [3](#0-2) 

`success` here is only `false` if the callee reverts or the call target has no code. Any ERC20 (including many TRC20/legacy tokens on Tron that follow the "return `false` on failure instead of reverting" convention) that returns `false` without reverting will make `success == true`, so the code proceeds as if the transfer succeeded. Immediately after, the escrow accounting is decremented (`_orders[body.commitment][token] -= amount`) and — in the calling context — the order is marked `_filled[body.commitment] = beneficiary`, permanently closing the order.

Note that inbound token intake in the same contract correctly uses `SafeERC20.safeTransferFrom` (imported via `using SafeERC20 for IERC20;`), and the mainnet `evm/src/apps/intentsv2/IntentsBase.sol` `_withdraw` function correctly uses `IERC20(token).safeTransfer(beneficiary, amount)`: [4](#0-3) 

This confirms the Tron contract's raw-call pattern is an inconsistent, unsafe deviation from the safeTransfer-based design used elsewhere in the same protocol.

### Impact Explanation
If the escrowed token misbehaves (returns `false` instead of reverting on a failed transfer — e.g. due to insufficient balance edge cases, blacklists, paused states, or non-standard TRC20 implementations common on Tron), the beneficiary receives nothing, yet:
- the escrow balance is decremented as if paid out,
- the order is marked filled/refunded and can never be retried,
- for the fee payout branch, protocol/relayer fees are similarly "paid" without actually transferring funds.

This results in permanent loss of the depositor's/solver's escrowed funds with no path to recovery, satisfying the "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
This path executes for every successful order withdrawal (`RedeemEscrow`/`RefundEscrow`) processed via `onAccept`, and for every `SweepDust` operation — both are core, frequently used flows reachable by ordinary users/solvers via `placeOrder`/`fillOrder`/`cancelOrder` round trips, not by any privileged actor. The only prerequisite is a token that can return `false` without reverting, which is a well-known and common category of ERC20/TRC20 tokens (particularly relevant given this contract specifically targets the Tron/TRC20 ecosystem, which does not have as strict compliance norms as canonical OpenZeppelin ERC20).

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` occurrences in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw`'s escrow release, its fee payout, and the `SweepDust` handler) with `SafeERC20.safeTransfer`, consistent with how inbound transfers already use `safeTransferFrom` in this file and how `IntentsBase._withdraw` handles it on EVM mainnet.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron) with an escrowed token contract that returns `false` on `transfer` failure instead of reverting (a realistic TRC20/legacy ERC20 behavior).
2. A user places an order and it is filled/escrowed normally; `_orders[commitment][token]` is credited.
3. Trigger `withdraw()` (via `onAccept` for `RedeemEscrow`/`RefundEscrow`) when the token transfer to the beneficiary fails and returns `false` (e.g., token temporarily blacklists the beneficiary or contract balance is manipulated to trigger an internal `false`-return branch).
4. `success` remains `true` because the call itself didn't revert; the code does not decode/check the boolean return.
5. `_orders[body.commitment][token] -= amount` executes, and the order is marked `_filled`, even though the beneficiary never received the tokens — funds are stuck in the contract, permanently unrecoverable by the intended beneficiary.
