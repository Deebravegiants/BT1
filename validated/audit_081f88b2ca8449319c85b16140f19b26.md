### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body [1](#0-0) . The `shop` value that is handed to the host application's handler as the trusted tenant identifier is read directly from the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header, which is never included in the signed material [2](#0-1) .

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [3](#0-2) , and `HmacValidator.validate` computes/compares the HMAC exclusively against that signable string using the app's `api_secret_key` [4](#0-3) . The `shop`, `topic`, `webhook_id`, and `api_version` fields are all parsed straight from unauthenticated headers via `shopify_header` [5](#0-4) , with no cryptographic binding to the body that was actually verified.

`Registry.process` then forwards `request.shop` — the unverified header value — directly into `WebhookMetadata` as the tenant identity for the handler to act on: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [1](#0-0) . This is the exact bug class from the reference report: an identity-relevant field (`shop`) is acted upon by the code but is not covered by the integrity check (`HMAC`) that gates that action. The equality that should hold is `shop_bound_by_hmac == shop_used_by_handler`; here `shop_bound_by_hmac` is undefined (nothing shop-specific is signed) while `shop_used_by_handler` is an attacker-controllable header.

Because every shop installed on a given app shares the same `api_secret_key`, the HMAC for a given raw body is identical regardless of which shop it was generated for. An attacker who legitimately receives (or triggers) one real webhook for their own shop obtains a valid `(raw_body, hmac)` pair. They can then replay that exact body/HMAC to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header (e.g., a victim shop's domain). `HmacValidator.validate` will still succeed because it never inspects the header, and the host application's handler will receive data purportedly from the victim shop `data.shop`, exactly as instructed by the library's own documentation [6](#0-5) .

### Impact Explanation
This breaks tenant isolation (cross-tenant access): any unprivileged user who can obtain one valid webhook body/HMAC pair (e.g., by installing the app on their own store, or capturing/replaying a webhook they legitimately received) can forge webhooks that the host application will process as belonging to any other shop of their choosing, since the gem provides `shop` to the handler as if it were authenticated. Depending on how the host app uses `data.shop` (e.g., to look up records, update order/customer data, or key into per-tenant storage), this can lead to data being written to, or read under, the wrong tenant's context — a cross-tenant integrity/confidentiality violation attributable to the gem's authentication contract, since the gem explicitly documents this field as the "shop domain of the webhook" without ever validating it.

### Likelihood Explanation
Likelihood is high for any app that receives webhooks and is installed by more than one merchant (the normal case): obtaining a valid body+HMAC pair only requires installing/uninstalling the app on a shop the attacker controls, or capturing one legitimate webhook delivery, then replaying the identical payload with a forged shop header to the app's public webhook URL. No access token, secret key, or privileged account is required — only knowledge of the app's public webhook path.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, triggering a real webhook (e.g., `orders/create`) which the attacker captures, obtaining `raw_body` and the valid `X-Shopify-Hmac-Sha256` value computed with the shared app secret.
2. Attacker sends a POST directly to the app's public webhook endpoint with the exact same `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and any desired `X-Shopify-Topic`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers without validating them [7](#0-6) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the (unmodified) body against the (unmodified, still-valid) HMAC [8](#0-7) .
5. The handler is invoked with `data.shop == "victim-shop.myshopify.com"` even though the payload actually originated from, and pertains to, the attacker's own shop, allowing the attacker to inject spoofed data tagged to the victim tenant.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the material that is HMAC-verified, or otherwise cross-check the header-derived `shop` against a value obtained through an authenticated channel (e.g., verify it matches a shop with a known, registered webhook subscription/session) before trusting it in `WebhookMetadata`. At minimum, document prominently that `data.shop` is not authenticated by the HMAC and must be independently validated by the host application against its own list of installed shops before being used for any tenant-scoped operation.
