### Title
Webhook `shop-domain` header is not bound to the HMAC signature, allowing a signed payload to be replayed with a spoofed tenant identity - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity used for downstream tenant-scoped processing purely from an unauthenticated HTTP header, while `to_signable_string` — the value actually covered by the HMAC check in `Utils::HmacValidator.validate` — only includes the raw request body. This breaks the identity binding `verified(hmac) == shop_acted_on`.

### Finding Description
`Utils::HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the supplied `hmac` value using `OpenSSL.secure_compare` [1](#0-0) . For webhooks, `to_signable_string` returns only `@raw_body` [2](#0-1) , meaning the HMAC cryptographically binds only the JSON body — not the `shop`, `topic`, or `webhook_id` fields.

`Request#shop`, however, is read directly and unconditionally from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed content [3](#0-2) . `Registry.process` validates the HMAC and then immediately constructs `WebhookMetadata` using `request.shop` as the tenant identifier that gets handed to the app's handler for shop-scoped processing [4](#0-3) .

This is a real identity-binding gap versus the OAuth callback path in the same gem, where `AuthQuery#to_signable_string` explicitly includes `shop` inside the signed parameter set [5](#0-4) , so `shop` there is provably bound to the signature. No equivalent binding exists for webhooks: `hmac_valid(body) == true` does not imply `shop_header == shop_that_produced(body)`.

### Impact Explanation
If an attacker can obtain any single valid `(raw_body, hmac)` pair produced with the app's `client_secret` — for example a webhook payload the app already emitted/received for one shop — they can resend it to the app's webhook endpoint with the `shop-domain` header rewritten to a different, victim shop. `HmacValidator.validate` will accept it (the body+hmac pair is genuinely valid), and `Registry.process` will hand the handler a `WebhookMetadata` claiming to belong to the victim shop while carrying attacker/other-tenant body content. Any host application relying on `data.shop` from this gem's webhook processing API to scope the write of order/customer/inventory data to the correct tenant record can be made to attribute or apply data cross-tenant.

### Likelihood Explanation
Low-to-moderate in practice: exploitation requires the attacker to first obtain a legitimately-signed `(body, hmac)` pair for the shared `client_secret`. In a normal multi-tenant public app, all installed shops receive webhooks HMAC-signed with the same app `client_secret`, so any shop that has installed the app already possesses valid `(body, hmac)` pairs from its own webhook deliveries; nothing in this gem's `Request`/`Registry` code re-derives or checks that the `shop` header matches the shop the payload was actually generated for. No possession of `api_secret_key`, TLS interception, or local access is needed once a legitimate webhook has been observed by any tenant of the app — only the ability to POST to the app's public webhook endpoint with modified headers.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise ensure `Registry.process`/`WebhookMetadata` establishes that the shop claimed in the header actually corresponds to the shop for which the signed body was produced (e.g., by requiring the caller to supply/verify the expected shop out-of-band, or by including the shop in `to_signable_string` the same way `Auth::Oauth::AuthQuery` does).

### Proof of Concept
1. App is installed on Shop A and Shop B, both webhooks signed with the same `client_secret`.
2. Shop A's tenant captures/logs a legitimately delivered webhook `(raw_body, x-shopify-hmac-sha256)` pair for topic `orders/create` (e.g. via their own logging/proxy in front of the app, or by triggering webhooks against an endpoint they control if they operate a companion integration).
3. Attacker (Shop A tenant) replays that exact `raw_body` and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `HmacValidator.validate` succeeds because the `(body, hmac)` pair is genuinely valid for the app's secret [6](#0-5) .
5. `Registry.process` invokes the registered handler with `WebhookMetadata` whose `shop` is `"shop-b.myshopify.com"` even though the body content originated from Shop A [4](#0-3) , causing the host application to apply Shop A's data under Shop B's tenant identity.
