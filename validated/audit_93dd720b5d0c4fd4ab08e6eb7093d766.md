### Title
Webhook shop identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an HTTP header that is never included in the HMAC signature computation. `Registry.process` validates only the HMAC of the raw body and then trusts the unauthenticated `shop` header to attribute the webhook to a tenant, allowing any shop that has installed the app to replay one of its own legitimately-signed webhooks against another shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

The `shop` accessor, however, is read straight from an HTTP header supplied by the caller, with no cryptographic binding to that header: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the signature strictly over `to_signable_string` (i.e., only the raw body) against the app's `api_secret_key`: [3](#0-2) 

`Webhooks::Registry.process` checks this HMAC, and — once it passes — immediately trusts `request.shop` (the unauthenticated header value) to build the `WebhookMetadata` that is handed to the app's webhook handler, which apps use to decide which tenant's data to act on: [4](#0-3) 

This is the same class of bug as the reported issue: a field that is *acted on* (the shop/tenant identity, analogous to the vault selection) is not covered by the authentication check (HMAC, analogous to `isExecutionFeeFromLpVault`). The equality that should hold — "shop cryptographically bound in the signed payload" == "shop used to attribute/act on the webhook" — is broken: the HMAC only proves "this body was signed with the app's secret," not "this body came from shop X."

Because a single `api_secret_key` is shared across every shop that installs the same app (Shopify signs all webhooks for an app with that app's client secret, not a per-shop secret), any shop that has installed the app is an "unprivileged internet user" from the perspective of other tenants of the same app, yet can produce a validly-HMAC-signed webhook body simply by triggering an event in its own store.

### Impact Explanation
An attacker who installs the target app on their own (free) development store can:
1. Trigger a webhook event in their own store, capturing the legitimately-HMAC-signed raw body Shopify sends to the app's webhook endpoint.
2. Replay that exact body to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain.
3. `HmacValidator.validate` still succeeds (it never inspects the shop header), so `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the victim's domain.

Any app relying on `data.shop` to route webhook side effects to the correct tenant's DB row (installs, orders sync, uninstall handling, etc.) will act on the victim tenant using attacker-supplied body content — i.e., cross-tenant access/confusion, matching the "Critical: cross-tenant access" bar.

### Likelihood Explanation
Exploitation requires only: (a) the app supports installation by arbitrary Shopify stores (typical for public apps), and (b) the app trusts `WebhookMetadata#shop` for tenant routing, which is exactly the documented/intended use of this API. No possession of `api_secret_key`, access tokens, or privileged accounts is required beyond the attacker's own (free, self-service) shop installation — which is a normal "unprivileged internet user" capability for public Shopify apps.

### Recommendation
Bind the shop identity into the verified signable material, or otherwise cryptographically tie the `shop-domain` header to the specific installation before trusting it — e.g., include the shop domain (and/or webhook-id) as part of the HMAC-checked payload, or cross-check `request.shop` against the shop associated with the specific access-token/session used to register that specific webhook subscription, rejecting the webhook if the header shop does not match a known, currently-installed shop record maintained by the host app. At minimum, document prominently that `WebhookMetadata#shop` is not itself authenticated by the HMAC and must be independently verified by the host application before being used for tenant routing.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers any registered webhook topic (e.g. `orders/create`) in their own store; Shopify POSTs to the app's webhook endpoint with headers such as:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC over raw body, computed with the shared api_secret_key>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   ```
3. Attacker replays the identical raw body and HMAC header to the same endpoint, but changes the header to:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` object; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only [1](#0-0)  — validation succeeds since the body/secret pair is unchanged.
5. The registered handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)` [5](#0-4)  and the host app processes attacker-controlled data as if it originated from the victim tenant.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
