### Title
Stale `TargetOrders.calc_pnl_x`/`calc_pnl_y` snapshot vs. rounded current reserves can permanently freeze `deposit`/`withdraw`/`swap` on the pool - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` is the shared helper invoked by every state-mutating AMM instruction reachable by unprivileged users (`Deposit`, `Withdraw`, `WithdrawPnl`, `SwapBaseIn`/`SwapBaseIn_v2`, `SwapBaseOut`/`SwapBaseOut_v2`). It compares a **stored, historical** invariant snapshot (`target.calc_pnl_x * target.calc_pnl_y`, decimal-normalized) against the **freshly computed** current reserve product (`total_pc_without_take_pnl * total_coin_without_take_pnl`). If the stale snapshot is ever greater than the live value, the function hard-errors with `AmmError::CalcPnlError`, aborting the transaction. [1](#0-0) 

### Finding Description
`calc_take_pnl`'s branch condition is:
```
if pool_pc_amount.checked_mul(pool_coin_amount).unwrap()
    >= (calc_pc_amount).checked_mul(calc_coin_amount).unwrap()
{ ... } else { return Err(AmmError::CalcPnlError.into()); }
``` [2](#0-1) 

`calc_pc_amount`/`calc_coin_amount` are derived from `target.calc_pnl_x`/`calc_pnl_y`, which is a snapshot of the pool's normalized reserves recorded the last time `calc_take_pnl` (or `Withdraw`) ran — i.e., a value from a *previous* invocation, analogous to the "last known" `totalSupplyYsCvgHistories` in the referenced report. `pool_pc_amount`/`pool_coin_amount` are the *live*, freshly derived reserves for the current call.

The snapshot and the live reserves are computed through `Calculator::normalize_decimal_v2`, which performs a **floor** integer division when converting native token amounts to the internal `sys_decimal_value` scale: [3](#0-2) 

During `Withdraw`, the new `calc_pnl_x`/`calc_pnl_y` snapshot is computed as a chain of independently-rounded subtractions:
```
target.calc_pnl_x = x1
    .checked_sub(Calculator::normalize_decimal_v2(pc_amount, ...))
    .unwrap()
    .checked_sub(U128::from(delta_x))
    .unwrap()
``` [4](#0-3) 

Because `normalize_decimal_v2(a) - normalize_decimal_v2(b)` and `normalize_decimal_v2(a - b)` are not guaranteed to be equal under floor rounding, repeated `Withdraw`/`Deposit`/swap cycles (fully controllable by any unprivileged LP/swapper, since these paths take user-chosen `max_coin_amount`/`max_pc_amount`/`amount`/`amount_in` values) can accumulate rounding drift such that the recorded snapshot `calc_pnl_x * calc_pnl_y` ends up numerically *larger* than the true, live `total_pc_without_take_pnl * total_coin_without_take_pnl` computed on a subsequent call. This flips the comparison in `calc_take_pnl` to the `else` branch and returns `AmmError::CalcPnlError`.

Since `calc_take_pnl` is called unconditionally on the hot path of `Deposit` (`program/src/processor.rs:1166-1173`), `Withdraw` (`program/src/processor.rs:1719-1748`, skipped only when status is `WithdrawOnly`), `WithdrawPnl` (`program/src/processor.rs:1459-1502`), and both swap variants (`program/src/processor.rs:2342-2347`, `2533-2538`), a single successful state transition that produces this rounding drift makes **every subsequent call to any of these instructions revert**, because `target.calc_pnl_x`/`calc_pnl_y` is never independently recalibrated from the live vault balances — it only accumulates further via the same subtraction chain.

### Impact Explanation
Once the invariant `pool_pc*pool_coin >= calc_pnl_x*calc_pnl_y` is broken, `Deposit`, `Withdraw` (outside `WithdrawOnly` status), `WithdrawPnl`, and both `SwapBaseIn`/`SwapBaseOut` variants unconditionally revert for the pool. LPs can no longer withdraw their liquidity through the normal path, and swappers can no longer trade against the pool — a permanent freeze of user and LP funds in that specific pool, matching the "permanent freezing of user or LP funds" acceptance criterion.

### Likelihood Explanation
This is reachable purely through the public `Deposit`/`Withdraw`/`Swap` instructions with attacker-chosen amounts — no privileged signer is required. Triggering it reliably requires accumulating enough rounding drift across many small, adversarially-chosen deposit/withdraw/swap amounts (particularly on pools with large decimal disparities between the coin and pc mints, which amplifies `normalize_decimal_v2` truncation error), so likelihood depends on the specific token-pair decimals and pool depth, but the primitive (repeatable floor-rounding drift under fully attacker-controlled instruction data) is present in every pool.

### Recommendation
Do not accumulate `calc_pnl_x`/`calc_pnl_y` via chained, independently-rounded subtractions. Instead, recompute the post-operation snapshot directly from the freshly-normalized live reserves after each operation (i.e., snapshot = `normalize_decimal_v2(total_pc_after_op)`, `normalize_decimal_v2(total_coin_after_op)`), and/or treat a "current < snapshot" condition as a saturating no-op (skip pnl-taking for this call rather than reverting the entire user transaction), so a rounding-induced discrepancy cannot brick deposit/withdraw/swap.

### Proof of Concept
1. Attacker performs a sequence of `Deposit` and `Withdraw` calls choosing `max_coin_amount`/`max_pc_amount`/`withdraw.amount` values that maximize floor-rounding loss in `Calculator::normalize_decimal_v2` at each step (most effective on pools where `coin_decimals`/`pc_decimals` differ significantly from `sys_decimal_value`'s implied scale).
2. Each `Withdraw` call updates `target.calc_pnl_x`/`calc_pnl_y` via the subtraction chain at `program/src/processor.rs:3161-3181`, accumulating rounding error independent of the true reserve arithmetic.
3. After sufficient iterations, a subsequent `Deposit`/`Withdraw`/`Swap` call computes live `pool_pc_amount * pool_coin_amount` that is now less than the drifted `calc_pnl_x * calc_pnl_y`, causing `calc_take_pnl` at `program/src/processor.rs:190-277` to return `AmmError::CalcPnlError`.
4. From this point, every call to `Deposit`, `Withdraw` (non-`WithdrawOnly`), `WithdrawPnl`, `SwapBaseIn`, and `SwapBaseOut` on this pool reverts, freezing LP and swap access to the pool's funds.

    pub fn normalize_decimal_v2(val: u64, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**9) -> (1.23*10**6)
        //let ret:u64 = val.checked_mul(amm.sys_decimal_value).unwrap().checked_div((10 as u64).pow(native_decimal.into())).unwrap();
        let ret_mut = (U128::from(val))
            .checked_mul(sys_decimal_value.into())
            .unwrap();
        let ret = ret_mut
            .checked_div(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        ret
    }
