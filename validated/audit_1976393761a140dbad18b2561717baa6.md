## Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC over the raw request body only, while the `shop` (and `topic`/`webhook_id`/`api_version`) values that are handed to the app's handler and treated as authenticated shop-identity come from unauthenticated HTTP headers. Since the app's `api_secret_key` is shared across every shop that has installed the app (it is not per-shop), a party who legitimately receives one valid `(body, hmac)` pair for their own shop can replay that same body/HMAC to the app's webhook endpoint while swapping the `shop-domain` header to point at a different (victim) shop, and `Utils::HmacValidator.validate` will still accept it.

## Finding Description
The identity binding that should hold is:

`shop domain trusted by the app for a webhook == shop domain over which the HMAC signature was computed`

In practice this equality does not hold. `Request#to_signable_string` — the value that is fed into HMAC verification — is defined as just the raw body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to that same signature: [2](#0-1) 

`Registry.process` validates only the HMAC and then forwards the header-derived `shop` value straight into the handler's data, unmodified: [3](#0-2) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (the body) with the app's single, shared `api_secret_key`: [4](#0-3) 

Because the same `api_secret_key` is used to sign webhooks for every shop that installed the app, a valid `(raw_body, hmac)` pair generated for shop A's webhook is also a valid `(raw_body, hmac)` pair when replayed with a `shop-domain` header claiming to be shop B — the signature check has no way to detect the substitution since the header was never part of what was signed.

The library's own documentation presents `Registry.process` as verifying that "the request did indeed come from Shopify" without qualifying that the shop identity itself is unauthenticated: [5](#0-4) 

and documents `data.shop` as simply "The shop domain of the webhook" with no caveat that it is unverified: [6](#0-5) 

An app author following this documented contract at face value (using `data.shop` from a `process`-validated request as an authenticated tenant identifier, e.g. for a multi-tenant lookup or job dispatch) is doing exactly what the gem tells them is safe, and is exposed by the gem's own guarantee, not by an app-level failure to read the docs.

## Impact Explanation
This crosses the tenant boundary the report class calls for: any actor who can obtain one genuine webhook delivery for a shop they control (installing the app, then triggering any subscribed event) captures a valid `(body, hmac)` pair signed under the app-wide secret. They can replay it against the app's public webhook endpoint with an altered `shop-domain` header to impersonate a victim shop's webhook traffic. Any app logic that trusts `WebhookMetadata#shop` for tenant-scoped effects (updating that shop's local records, enqueueing shop-scoped jobs, billing/inventory sync, etc., exactly as shown in the documented example) will act on forged data attributed to the victim shop — this is a cross-tenant confusion enabled purely by this gem's verification code, matching the "Critical - cross-tenant access" impact category.

## Likelihood Explanation
The attacker only needs to be an unprivileged internet user who can install the app on any shop (including a free/dev store) to legitimately receive one signed webhook delivery, then send an ordinary HTTP POST to the target app's public webhook URL with the captured body/HMAC and a spoofed `shop-domain` header. No access token, `client_secret`, or privileged account is required, and the request path (`Registry.process` → `HmacValidator.validate` → handler) is exactly the gem's documented, expected usage.

## Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically tie the trusted headers to the verified signature, e.g. by:
- Rejecting/flagging in `Registry.process` (or `HmacValidator`) any case where the header-derived shop is not cross-checked against a shop known to have this specific webhook/app-secret relationship, or
- Documenting explicitly and loudly in `docs/usage/webhooks.md` that `data.shop` (and other headers) are **not** covered by the HMAC and must be independently corroborated (e.g., against the app's own shop/session store) before being used for any tenant-scoped action, rather than only saying `process` "will verify the request did indeed come from Shopify."

## Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` and trigger any subscribed webhook topic (e.g. `orders/create`) to legitimately receive a webhook POST with a valid `x-shopify-hmac-sha256` computed over the raw body using the app's `api_secret_key`.
2. Capture that raw body and its HMAC header.
3. Send a new HTTP POST to the app's webhook endpoint with the identical raw body and HMAC header, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. Because `Request#to_signable_string` only returns the raw body (`lib/shopify_api/webhooks/request.rb:35-38`) and `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) only checks that body against the shared `api_secret_key`, validation succeeds; `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) then calls the app handler with `shop: "victim-shop.myshopify.com"`, even though the request body/content actually originated from `attacker-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
