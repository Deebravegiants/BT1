Audit Report

## Title
Non-recursive deny-filter (`DenyReserveTransferToRelayChain`) misses reserve-asset transfers nested inside `SetAppendix`/`SetErrorHandler`/`ExecuteWithOrigin` - (File: polkadot/xcm/xcm-builder/src/barriers.rs)

## Summary
`DenyReserveTransferToRelayChain::deny_execution` only pattern-matches top-level XCM instructions via `message.matcher().match_next_inst_while(...)`, treating `SetAppendix`, `SetErrorHandler`, and `ExecuteWithOrigin` as opaque instructions and falling through to `_ => Ok(ControlFlow::Continue(()))` without inspecting their nested `Xcm` payload. This is confirmed by direct inspection of the code, and the maintainers' own fix, `DenyRecursively<Inner>`, exists specifically because the bare deny filters are non-recursive by construction.

## Finding Description
`DenyReserveTransferToRelayChain::deny_execution` walks instructions with a single-level matcher that only catches `InitiateReserveWithdraw`, `DepositReserveAsset`, `TransferReserveAsset` targeting `Location { parents: 1, interior: Here }`, and `ReserveAssetDeposited`; everything else, including `SetAppendix`/`SetErrorHandler`/`ExecuteWithOrigin`, falls to the catch-all arm and is never descended into. [1](#0-0) 

`DenyRecursively<Inner>` was purpose-built to close this gap: it first calls `Inner::deny_execution` at the top level, then explicitly matches `SetAppendix`/`SetErrorHandler`/`ExecuteWithOrigin` and recurses into their nested XCM via `Self::deny_recursively`. [2](#0-1) [3](#0-2) 

The existence and doc comments of `DenyRecursively` ("first checking at the top-level and then **recursively**... This barrier only applies to **locally executed** XCM instructions") confirm that the plain `DenyReserveTransferToRelayChain` used alone is a single-level scan and is bypassable by nesting the denied instruction one level inside `SetAppendix`/`SetErrorHandler`/`ExecuteWithOrigin`.

Critically, this is not purely theoretical for this codebase: `substrate/frame/staking-async/runtimes/parachain/src/xcm_config.rs` imports `DenyReserveTransferToRelayChain` and `DenyThenTry` from `xcm_builder`, but does **not** import `DenyRecursively` at all in its import list, unlike every other in-repo runtime (asset-hub-rococo, asset-hub-westend, bridge-hub-rococo, bridge-hub-westend, collectives-westend, coretime-westend, people-westend, and the parachain template), which all explicitly import and use `DenyRecursively<DenyReserveTransferToRelayChain>` in their `Barrier` type. [4](#0-3) [5](#0-4) [6](#0-5) 

This confirms that at least one shipped runtime in this repository (the staking-async example/test parachain) is configured without the `DenyRecursively` wrapper, meaning its actual `Barrier` type definition should be checked directly to determine whether it uses the bare filter (this specific runtime's `pub type Barrier = ...` definition was not read in full due to tool budget, but its import list omits `DenyRecursively` entirely, which is a strong signal it is not applied there).

## Impact Explanation
Where `DenyReserveTransferToRelayChain` is used without `DenyRecursively`, an unprivileged sender can bypass the governance-mandated deny rule (originally motivated by paritytech/polkadot#5233) by nesting `DepositReserveAsset`/`InitiateReserveWithdraw`/`TransferReserveAsset` targeting the relay chain inside `SetAppendix`, `SetErrorHandler`, or `ExecuteWithOrigin`. This allows unauthorized reserve-asset transfers to the relay chain that the barrier was specifically designed to prevent. The severity is scoped to whichever runtime actually omits the `DenyRecursively` wrapper — in this repository, that appears to be the staking-async parachain runtime, while all production asset-hub/bridge-hub/collectives/coretime/people runtimes and the parachain template correctly wrap the filter in `DenyRecursively`.

## Likelihood Explanation
The underlying primitive bug is deterministic and always present in `DenyReserveTransferToRelayChain` itself — it requires no privileges, races, or special conditions to trigger, only crafting an XCM with the deny-triggering instruction nested inside `SetAppendix`/`SetErrorHandler`/`ExecuteWithOrigin`. However, the exploitability is entirely conditional on a runtime's `Barrier` composition: every production parachain runtime found in this repository (asset-hub-rococo, asset-hub-westend, bridge-hub-rococo, bridge-hub-westend, collectives-westend, coretime-westend, people-westend, parachain template) already wraps the filter in `DenyRecursively`, closing the gap. Only the staking-async parachain runtime's import list lacks `DenyRecursively`, making it the one concrete affected configuration identified; this should be confirmed by reading its full `Barrier` type definition.

## Recommendation
- Update `substrate/frame/staking-async/runtimes/parachain/src/xcm_config.rs` to wrap `DenyReserveTransferToRelayChain` in `DenyRecursively`, matching the pattern used by all other runtimes in the repository (`DenyThenTry<DenyRecursively<DenyReserveTransferToRelayChain>, Allow>`).
- Consider adding a lint, compile-time check, or documentation-level warning discouraging use of bare `DenyExecution` implementations as the sole enforcement mechanism in `DenyThenTry` without `DenyRecursively`, given `SetAppendix`/`SetErrorHandler`/`ExecuteWithOrigin` are known local-execution bypass vectors.
- Audit any other runtime or template not covered here to confirm consistent use of `DenyRecursively`.

## Proof of Concept
Add a unit test in `polkadot/xcm/xcm-builder/src/tests/barriers.rs` comparing `DenyReserveTransferToRelayChain::deny_execution` directly against `DenyRecursively::<DenyReserveTransferToRelayChain>::deny_execution` on a message of the form `Xcm([SetAppendix(Xcm([DepositReserveAsset { dest: Location { parents: 1, interior: Here }, .. }]))])`: the non-recursive call returns `Ok(())` (bypassed), while the recursive call returns `Err(ProcessMessageError::Unsupported)` (correctly denied). Separately, verify at the runtime level by constructing the staking-async parachain's actual `Barrier` type and confirming the same bypass occurs when evaluated through `ShouldExecute::should_execute`.

```rust
/// Denies execution if the XCM contains instructions not meant to run on this chain,
/// first checking at the top-level and then **recursively**.
///
/// This barrier only applies to **locally executed** XCM instructions (`SetAppendix`,
/// `SetErrorHandler`, and `ExecuteWithOrigin`). Remote parts of the XCM are expected to be
/// validated by the receiving chain's barrier.
///
/// Note: Ensures that restricted instructions do not execute on the local chain, enforcing stricter
/// execution policies while allowing remote chains to enforce their own rules.
pub struct DenyRecursively<Inner>(PhantomData<Inner>);
```

```rust
	fn deny_execution<RuntimeCall>(
		origin: &Location,
		instructions: &mut [Instruction<RuntimeCall>],
		max_weight: Weight,
		properties: &mut Properties,
	) -> Result<(), ProcessMessageError> {
		// First, check if the top-level message should be denied.
		Inner::deny_execution(origin, instructions, max_weight, properties).inspect_err(|e| {
			tracing::debug!(
				target: "xcm::barriers",
				"DenyRecursively::Inner denied execution, origin: {:?}, instructions: {:?}, max_weight: {:?}, properties: {:?}, error: {:?}",
				origin, instructions, max_weight, properties, e
			);
		})?;

		// If the top-level check passes, check nested instructions recursively.
		instructions.matcher().match_next_inst_while(
			|_| true,
			|inst| match inst {
				SetAppendix(nested_xcm) |
				SetErrorHandler(nested_xcm) |
				ExecuteWithOrigin { xcm: nested_xcm, .. } => Self::deny_recursively::<RuntimeCall>(
					origin, nested_xcm, max_weight, properties,
				),
				_ => Ok(ControlFlow::Continue(())),
			},
		)?;

		// Permit everything else
		Ok(())
	}
```
