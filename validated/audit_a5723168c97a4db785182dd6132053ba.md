### Title
`SubstrateCalldata` signature in `pallet-hyper-fungible-token::on_accept` lacks binding to a specific cross-chain message, enabling front-running of a beneficiary's calldata authorization by an unrelated transfer - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` optionally executes an arbitrary `RuntimeCall` on behalf of the token beneficiary, authorized by a signature the beneficiary attaches to the cross-chain transfer. The signed payload is only `(account_nonce, runtime_call)` — it does not commit to the specific incoming ISMP message (source chain, peer contract, asset, amount, or transfer) that was meant to carry it. Because the check only compares against the beneficiary's live on-chain nonce, the exact same `(signature, runtime_call)` bytes copied from one pending/observed transfer can be delivered inside a completely different, unrelated `Message` (crafted by any unprivileged sender who can dispatch a cross-chain transfer to the same beneficiary) as long as the beneficiary's nonce has not yet advanced. This is the same missing-domain-binding root cause as the reported `CrosschainMerkleDistributor.claimBySignature` issue: a signature intended for one specific delivery context can be replayed into another context that the signer never authorized.

### Finding Description
`on_accept` verifies the calldata-execution signature like this: [1](#0-0) 

The signed message is `keccak256((nonce, runtime_call).encode())` where `nonce = frame_system::Pallet::<T>::account_nonce(beneficiary)`. There is no commitment in the signed payload to:
- the source chain (`source`) or peer contract (`from`) that delivered the message,
- the `local_asset_id` / amount being transferred,
- the destination pallet instance, or
- any per-message identifier (ISMP request nonce/commitment).

The only thing that prevents unconditional replay is the account nonce, which is incremented only after a successful dispatch: [2](#0-1) 

`Message.to` (the beneficiary) and `Message.data` (which embeds the `SubstrateCalldata { signature, runtime_call }`) are attacker-controlled fields of an entirely independent cross-chain transfer that anyone can dispatch through any registered peer contract, as documented for the multi-chain HFT deployment topology and the identical cross-chain message format shared by every EVM/Substrate deployment: [3](#0-2) 

Because the beneficiary's account nonce and the runtime call SCALE encoding are both externally observable (mempool/pending ISMP request, or even a prior successful transaction), an unprivileged actor can copy a legitimate `SubstrateCalldata` blob a beneficiary produced for one intended transfer and paste it into a new, unrelated `send()` call from any registered peer, addressed to the same beneficiary, before the original message is delivered.

### Impact Explanation
The test at `modules/pallets/testsuite/src/tests/pallet_hyper_fungible_token.rs` confirms the only replay protection is the nonce bump on successful dispatch: [4](#0-3) 

An attacker who races their own (unrelated, possibly minimal-value) transfer to the same destination pallet ahead of the beneficiary's real transfer causes:
1. The beneficiary's authorized `runtime_call` to execute under `RawOrigin::Signed(beneficiary)` as a side effect of the attacker's message rather than the beneficiary's intended one, and the account nonce to advance.
2. The beneficiary's legitimate, subsequently-delivered message to permanently fail signature verification (`HftError::SignatureVerificationFailed`) because the on-chain nonce no longer matches the one embedded in their signature, since `on_accept` returns an error and the dispatchable's storage changes are rolled back transactionally — denying/blocking the user's own transfer until the ISMP request times out and is refunded on the source chain.

This is an unauthorized app action: a third party triggers the beneficiary's signed authorization decoupled from the specific transfer/context the user intended it for, and can weaponize it to grief/deny the user's own bridging operation.

### Likelihood Explanation
Exploitability only requires: (a) observing a `SubstrateCalldata` blob before its carrying ISMP message is delivered (it is visible in the pending/undelivered request or, once delivered, is public forever and can be replayed against a still-unincremented nonce on a still-registered peer's future message), and (b) the ability to dispatch a cross-chain `send()` from any registered peer contract to the same destination pallet and beneficiary — something any unprivileged token bridger can do. No special privileges are required.

### Recommendation
Bind the signed payload to the specific incoming message and context, not just the beneficiary's nonce, e.g. include the ISMP request commitment/hash (or `(source, from, local_asset_id, amount)`) and the destination `StateMachine`/pallet identifier in the signed message: `keccak256((nonce, source, from, local_asset_id, amount, dest, runtime_call).encode())`. This mirrors the CrosschainMerkleDistributor recommendation of adding message-specific information to the signed payload so a signature cannot be lifted from one delivery context and replayed into another.

### Proof of Concept
1. Beneficiary `B` (nonce = `N` on destination chain `D`) initiates a bridge transfer from source chain `X` via registered peer `P_X`, with `data = SubstrateCalldata { signature: sign_B(nonce=N, call=C), runtime_call: C }`.
2. The ISMP request is dispatched but not yet delivered on `D` (still awaiting consensus proof/challenge period), or has just been delivered and observed on-chain.
3. Attacker `A`, who can dispatch a cross-chain transfer from any other registered peer `P_Y` to the same pallet on `D`, sends their own small transfer with `to = B`'s bytes and `data` set to the exact same `SubstrateCalldata { signature, runtime_call: C }` copied from step 1.
4. `A`'s message is delivered to `D` first; `on_accept` reads `account_nonce(B) == N`, the signature verifies, `C` is dispatched as `B`, and `B`'s nonce becomes `N+1`.
5. `B`'s original message is later delivered; `on_accept` now reads `account_nonce(B) == N+1 != N` embedded in the signature, `SignatureVerificationFailed` is returned, and (per transactional dispatch) `B`'s entire transfer — mint included — is rolled back, denying `B`'s transfer until ISMP timeout/refund.

```text
## Calldata Execution

The `call_data` field in `SendParams` allows executing arbitrary runtime calls on the destination substrate chain after the tokens are transferred. The calldata is SCALE-encoded as:

```rust lineNumbers
pub struct SubstrateCalldata {
    /// Optional SCALE-encoded MultiSignature of (account_nonce, runtime_call)
    pub signature: Option<Vec<u8>>,
    /// SCALE-encoded runtime call to execute
    pub runtime_call: Vec<u8>,
}
```

If a signature is provided, it is verified against the beneficiary's account nonce and the runtime call before dispatch. Supported signature types: Ed25519, Sr25519, ECDSA. The account nonce is incremented after dispatch to prevent replay.

If no signature is provided, the origin is derived from the sender address in the cross-chain message.
```
