### Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC only signs the raw body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` only proves that the *body bytes* were signed by Shopify with the app's single, app-wide `api_secret_key` [2](#0-1) . The `shop` value consumed by the registry, however, comes straight from the `X-Shopify-Shop-Domain` header and is never included in the signed payload [3](#0-2) . `Registry.process` validates the HMAC and then forwards `request.shop` unchanged to the handler as the tenant identifier [4](#0-3) .

### Finding Description
The binding that should hold is: `hmac_verified_bytes == bytes_that_determine_the_tenant("shop")`. In this gem it does not: the HMAC covers only `@raw_body`, while `shop` is read independently from a header that is not part of the signed content [5](#0-4) .

Because `api_secret_key` is a single per-app secret shared across every shop that installs the app (not a per-shop secret) [6](#0-5) , any merchant who installs the app on their own store can trigger events (e.g. by editing a product, updating an order, etc.) and receive a webhook delivery with a body they substantially control and a *validly-computed* HMAC for that body. Since the shop identity is carried in a separate, unsigned header, that attacker-controlled request can be replayed to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to name a different (victim) shop that also uses the app. `HmacValidator.validate` will still return `true`, because the check only recomputes the HMAC over the raw body using the shared secret — it never verifies that the claimed `shop` matches the shop that actually produced that body [7](#0-6) . `Registry.process` then dispatches to the handler with `shop: request.shop` set to the attacker's chosen victim domain and `body: request.parsed_body` containing attacker-controlled content [4](#0-3) .

This mirrors the reported bug class exactly: an identity field (`shop`) is acted upon by application logic but is not covered by the cryptographic signature that is supposed to authenticate the message, allowing an unprivileged party (any merchant who can install the app) to spoof the tenant.

### Impact Explanation
This breaks tenant isolation: host applications built on this gem naturally use `WebhookMetadata#shop`/`request.shop` to select which tenant's data/session to act on (e.g., updating the correct shop's local record store). An attacker-controlled shop can inject attacker-chosen webhook bodies attributed to a victim shop, leading to cross-tenant data corruption or processing of forged events as if they came from the victim — this maps to the "cross-tenant access" Critical impact category, since the shop-identity boundary that the gem is supposed to protect is not cryptographically enforced.

### Likelihood Explanation
Likelihood is high for any app builder who trusts `WebhookMetadata#shop` as an authenticated tenant identifier (which is the documented usage pattern of `Registry.process`/`WebhookMetadata`). The only prerequisite is installing the app on any shop (including a free development store) — no access token, `api_secret_key`, or privileged access is required, satisfying the "unprivileged internet user" constraint.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is authenticated, or otherwise cryptographically tie the header-supplied shop to the specific installation/session the request should be attributed to (e.g., verify the shop against a known, previously-established session/webhook registration for that topic instead of trusting the header value outright). At minimum, document/require that consuming apps must independently verify `request.shop` is a shop they have an active installation for before trusting it as a tenant key, and consider incorporating the shop domain into the signable string to detect spoofed headers directly inside `HmacValidator`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, obtaining a legitimate, secret-signed webhook delivery for a real event, e.g. body `{"id":1,"title":"X"}` with header `X-Shopify-Hmac-Sha256: <valid-hmac-for-that-body>` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends the identical HTTP request to the app's webhook endpoint but changes only the header `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `hmac` and `to_signable_string` are unaffected by the header change [8](#0-7) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against `Context.api_secret_key` [9](#0-8) .
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: {"id"=>1,"title"=>"X"}, ...)` [10](#0-9) , causing the host application to process attacker-supplied data as if it originated from the victim tenant.

          received_signature = verifiable_query.hmac
