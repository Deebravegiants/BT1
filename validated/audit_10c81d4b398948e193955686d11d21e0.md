### Title
`Request#shop` returns the unsigned `x-shopify-shop-domain` header while `HmacValidator` only signs the raw body, allowing shop-identity spoofing on replayed webhooks - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so the HMAC computed by `HmacValidator.validate_signature` covers nothing except the body bytes [2](#0-1) . `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read straight from attacker-controlled, unsigned headers [3](#0-2) , and `initialize` only checks that the `topic`, `hmac-sha256`, and `shop-domain` headers are *present*, never that they match what was actually signed [4](#0-3) . `Registry.process` trusts `request.shop` after HMAC validation succeeds and hands it to the app's handler as the tenant identity [5](#0-4) .

### Finding Description
The invariant the app relies on is: `shop_used_by_handler == shop_that_Shopify_actually_signed_this_payload_for`. This equality is broken because the signed material and the "shop" value are decoupled.

- `HmacValidator.validate` calls `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only `@raw_body` — no headers, including `shop-domain`, are part of the signable string [1](#0-0) [2](#0-1) .
- `Request#shop` simply reads `shopify_header("shop-domain")`, i.e. the `x-shopify-shop-domain` or `shopify-shop-domain` HTTP header, verbatim [6](#0-5) [7](#0-6) .
- `initialize` only verifies presence of the `topic`, `hmac-sha256`, and `shop-domain` headers, not their correctness or that they were part of the signed content [8](#0-7) .
- `Registry.process` gates on `HmacValidator.validate(request)` succeeding, then immediately trusts `request.shop` (and `request.topic`) to build `WebhookMetadata` passed to the app's registered handler [5](#0-4) .

Attack flow:
1. The attacker creates their own development shop, installs the app, and registers a webhook endpoint on their own server, receiving a validly-signed webhook — headers `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, and body `B`. Here `H = HMAC(secret, B)`, which is legitimate because it only ever covered `B`.
2. The attacker replays the exact same body `B` and HMAC `H` to the app's webhook endpoint, but substitutes the `x-shopify-shop-domain` (or `shopify-shop-domain`) header value with the victim merchant's domain, `victim-shop.myshopify.com`.
3. `Registry.process` calls `HmacValidator.validate(request)`. Since `to_signable_string` is still just `B`, and `H = HMAC(secret, B)` remains valid — the header tampering has no effect on this check, so validation succeeds [9](#0-8) .
4. `request.shop` now returns `victim-shop.myshopify.com`, and this value — never covered by the signature — is passed into `WebhookMetadata.shop` and delivered to the app's handler as though Shopify genuinely sent this event for the victim's shop [10](#0-9) [11](#0-10) .

No existing guard intervenes: `ShopValidator.sanitize!`, `state` comparisons, `JwtPayload`'s `aud` check, and `Context.setup?`/`private?` are all part of the OAuth/session-token paths, not the webhook path, and none of them are invoked anywhere in `Request`, `HmacValidator`, or `Registry.process`. `Sorbet` typing (`T.cast(shopify_header(...), String)`) only enforces the value is a `String`, not that it was signed or well-formed as a shop domain — there's no call to `ShopValidator.sanitize!` on `request.shop` in this webhook path at all.

### Impact Explanation
This is authentication bypass at the tenant-identity level: an unprivileged attacker who owns any real shop that installed the app can produce arbitrarily many forged "victim shop" webhook deliveries by controlling only an unsigned header, while reusing one HMAC they legitimately received for their own shop. Any app logic keyed off `WebhookMetadata#shop` — e.g., invalidating a victim's cache, triggering data deletion/redaction flows (`shop/redact`, `customers/redact`, `customers/data_request`), updating per-shop state, or triggering side effects scoped "per shop" — can be triggered against an arbitrary victim shop the attacker never installed on or was authorized for. This is a cross-tenant identity forgery: the app is made to believe an event legitimately signed for shop A was in fact issued for victim shop B. This matches "Critical - authentication bypass: a forged or unsigned request is accepted as authentic by the app," since the shop-identity claim inside an app-processed, HMAC-"verified" webhook is fully attacker-controlled and cross-tenant.

### Likelihood Explanation
Preconditions are minimal and entirely within the described attacker capability: the attacker only needs to install the target app on any shop they control (trivial via Shopify's free developer shop program) and receive one legitimately signed webhook of any topic handled by the target app. From that single captured `(body, HMAC)` pair, they can replay unlimited spoofed requests differing only in the unsigned `shop-domain` header, targeting any victim shop name (shop domains are guessable/enumerable, e.g. `<storename>.myshopify.com`). No secrets, tokens, or victim cooperation are required. This is fully repeatable and cheap.

### Recommendation
Include the shop-identifying and topic headers inside the signable material that `HmacValidator` verifies, or otherwise cryptographically bind `shop-domain`/`topic`/`webhook-id` to the HMAC (e.g., by having `to_signable_string` incorporate the normalized header values, matching Shopify's actual signing scheme if it also signs these headers upstream) rather than trusting them as separate unsigned inputs. At minimum, additionally validate `shop-domain` against `ShopValidator.sanitize!` and cross-check it against any registered/expected shop for the given webhook subscription before dispatching to the handler.

### Proof of Concept
```ruby
# test/webhooks/request_shop_spoof_test.rb
require "test_helper"

class RequestShopSpoofTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(
      api_key: "key", api_secret_key: "secret", api_version: "2022-01",
      host_name: "app.com", scope: "read_products", is_private: false,
      is_embedded: true, session_storage: ShopifyAPI::Auth::FileSessionStorage.new
    )
    @body = '{"id":1,"name":"test"}'
    @hmac = Base64.encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "secret", @body)
    ).strip
  end

  def build_request(shop_domain)
    ShopifyAPI::Webhooks::Request.new(
      raw_body: @body,
      headers: {
        "X-Shopify-Topic" => "orders/create",
        "X-Shopify-Hmac-Sha256" => @hmac,
        "X-Shopify-Shop-Domain" => shop_domain,
        "X-Shopify-Api-Version" => "2022-01",
        "X-Shopify-Webhook-Id" => "123",
      }
    )
  end

  def test_same_hmac_validates_for_two_different_shops
    attacker_request = build_request("attacker-shop.myshopify.com")
    victim_request   = build_request("victim-shop.myshopify.com")

    assert ShopifyAPI::Utils::HmacValidator.validate(attacker_request)
    assert ShopifyAPI::Utils::HmacValidator.validate(victim_request)

    refute_equal attacker_request.shop, victim_request.shop
    # Same HMAC accepted as valid for both — shop identity is not bound to the signature.
    assert_equal "attacker-shop.myshopify.com", attacker_request.shop
    assert_equal "victim-shop.myshopify.com", victim_request.shop
  end
end
```
This demonstrates that one signature (`@hmac`, computed over `@body` only) is accepted as valid by `HmacValidator.validate` for two `Request` objects whose `#shop` differ solely by the unsigned `x-shopify-shop-domain` header — violating the required "signature covers every value acted on" invariant.
