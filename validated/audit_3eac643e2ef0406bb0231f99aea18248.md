### Title
Webhook `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are not covered by the HMAC signature, allowing cross-tenant identity spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `HmacValidator.validate` cryptographically authenticates just the JSON body bytes. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers used downstream to identify the tenant and route the payload are never included in the signed material.

### Finding Description
`Registry.process` validates the request with `Utils::HmacValidator.validate(request)`, which only checks `OpenSSL.secure_compare(computed_signature, hmac)` against `to_signable_string`, defined as: [1](#0-0) 
That signable string is `@raw_body` only, never `shop`, `topic`, `webhook_id`, or `api_version`: [2](#0-1) 

After the HMAC check passes, `Registry.process` constructs `WebhookMetadata` directly from `request.shop`, `request.topic`, etc., and hands it to the app-supplied handler as the trusted tenant identity: [3](#0-2) 

The equality that should hold is: `shop_bound_by_HMAC == shop_used_for_tenant_routing`. Because the HMAC covers only `raw_body`, this equality is never enforced — `shop` (and `topic`/`webhook_id`/`api_version`) are attacker-controllable header values that ride along with an otherwise-valid signature, exactly analogous to the LPP report's pattern of "a field acted on but not covered by the [authentication] check."

An unprivileged party who is a legitimate merchant with the app installed on their own shop can trigger genuine Shopify webhooks for arbitrary body content, capturing valid `(raw_body, hmac)` pairs signed with the app's single shared `client_secret` (the same secret is used to compute HMACs for every shop that installs a given app). They can then submit a forged HTTP request directly to the app's public webhook endpoint using that captured `(raw_body, hmac)` pair, but with the `shop-domain` header changed to a victim shop's domain (and/or the `topic` header changed). `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will call the handler with `WebhookMetadata.shop` set to the victim's shop.

### Impact Explanation
This breaks the tenant-identity binding the whole webhook system relies on. Any app whose handler trusts `data.shop` (as the documented usage pattern instructs — see `docs/usage/webhooks.md` and `BREAKING_CHANGES_FOR_V15.md`, both showing handlers keyed off `data.shop`) to attribute incoming data/events to a specific merchant can be made to process attacker-supplied data under a different, victim shop's identity — a cross-tenant data-injection primitive. Because `topic` is also unauthenticated, an attacker can also relabel the event type (e.g., make an `orders/create` body get routed to a `shop/redact` or `app/uninstalled` handler), further amplifying impact depending on what the host app's handlers do with the topic/shop pairing.

### Likelihood Explanation
Requires only: (1) the attacker's own shop to have the target app installed (an ordinary merchant, i.e., an unprivileged party with respect to other tenants) so they can capture a real `(body, hmac)` pair via legitimate use, and (2) the ability to POST directly to the app's public webhook endpoint with modified headers (no TLS interception, no secrets, and no privileged account needed — the shared `client_secret` never needs to be known to the attacker). This is a realistic, moderate-effort attack path exploitable by any app-installing merchant against other tenants of the same app.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the payload before use — e.g. compute/verify the HMAC over a canonical string that concatenates the raw body with these header values, matching how `AuthQuery#to_signable_string` already includes `shop` in its signed field set. At minimum, document that `Request#shop`/`#topic` are unauthenticated and should not be used as tenant/topic routing keys without an independent check (e.g., cross-referencing against sessions the app already has on file), and consider raising `InvalidWebhookError` if the header-derived shop does not match an expected/known shop.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com`.
2. Attacker triggers a real webhook event (e.g. `customers/data_request`) with attacker-controlled body content; Shopify sends a real request to the app's webhook endpoint, signed with the app's `client_secret`:
   - `x-shopify-hmac-sha256: <valid_hmac_of_body>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-topic: customers/data_request`
3. Attacker captures `raw_body` and `x-shopify-hmac-sha256` from this legitimate request (e.g., by controlling the receiving infra they run, or intercepting their own traffic — no victim credentials needed).
4. Attacker crafts a new POST directly to the app's public webhook endpoint reusing the same `raw_body` and `x-shopify-hmac-sha256`, but replaces:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
5. `Registry.process` calls `Utils::HmacValidator.validate(request)` — which only checks `raw_body` against the HMAC, so validation succeeds:
```ruby
# lib/shopify_api/webhooks/request.rb
def to_signable_string
  @raw_body
end
```
6. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"`, and the app's handler processes attacker-supplied data as if it originated from the victim shop:
```ruby
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
```
