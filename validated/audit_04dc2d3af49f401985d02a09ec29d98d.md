### Title
Webhook `shop` identity is read from an unauthenticated HTTP header while the HMAC only covers the raw body, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before invoking the app's webhook handler, but the identity binding it actually enforces is incomplete: the HMAC signature only authenticates the request *body*, not the `shop` (tenant) that the body is attributed to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , which is what `Utils::HmacValidator.validate` uses to compute/compare the signature against the `hmac-sha256` header value [4](#0-3) . Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers with no cryptographic binding to that HMAC at all [2](#0-1) .

`Registry.process` validates only the HMAC, then immediately trusts `request.shop` and `request.topic` to build `WebhookMetadata`, which is handed to the app's handler as the tenant/topic identity for the webhook payload [3](#0-2) .

Because a given app's `api_secret_key` is shared across **every shop** that has the app installed, any merchant who installs the app (an "unprivileged internet user" relative to other tenants of the same app) can legitimately receive a validly-HMAC'd webhook delivery for their own shop, then replay that exact `(raw_body, hmac-sha256)` pair directly at the app's webhook endpoint while substituting a different value in the `x-shopify-shop-domain` (or `shopify-shop-domain`) header. `Utils::HmacValidator.validate` will still return `true`, because it never inspects the shop header — it only checks that the body matches a signature computed with the app's `api_secret_key`, which is valid for any shop of that app. The broken identity equality is:

`shop authenticated by HMAC (none — HMAC binds only to secret+body) ≠ shop declared in x-shopify-shop-domain header (fully attacker-controlled once a valid body+hmac pair is obtained)`

This lets an attacker-controlled shop's legitimate webhook be replayed as if it originated from a victim shop, and the app (which typically uses `data.shop` to select per-tenant database records/settings/access tokens for further processing, exactly as shown in this gem's own documentation example `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will process attacker-supplied data under the victim's tenant identity.

### Impact Explanation
This is a cross-tenant confused-deputy condition (Critical impact bucket: cross-tenant access) reachable purely through this gem's own webhook verification API. An app built directly on the documented `Registry.process` pattern has no way to detect the spoof, since the gem's `process` method is documented and designed to be the complete verification step ("This will verify the request did indeed come from Shopify"). Any handler that persists or acts on webhook data keyed by `data.shop` (the standard, gem-recommended pattern) will attribute attacker-supplied webhook content to an arbitrary victim shop of the attacker's choosing.

### Likelihood Explanation
Likelihood is high for any app with more than one installed shop: the attacker only needs to install the app on their own store (a normal, unprivileged action), capture one legitimate webhook delivery (body + `x-shopify-hmac-sha256`), and replay it to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header. No secret material, TLS interception, or privileged access is required — only the ability to send an arbitrary HTTP request to the app's already-public webhook receiver, which is the exact threat model `Registry.process` claims to defend against.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the authenticated signable payload — or, at minimum, cross-check `x-shopify-shop-domain` against a shop the app expects to be delivering this specific webhook (e.g. correlate against the session belonging to `webhook_id`/subscription, or require apps to validate `shop` server-side against their own list of installed shops before trusting `data.shop`). At the gem level, `Request#to_signable_string` should not be the sole trust anchor for `shop`; document explicitly (or enforce) that `data.shop` must additionally be validated by the app against its own installed-shop registry, since the current HMAC does not attest to the header set.

### Proof of Concept
1. App "Foo" is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com` (same `api_secret_key` for both, since it's per-app).
2. Attacker triggers a webhook-eligible action on their own `attacker-shop` (e.g., updates a product), and Shopify delivers a webhook to the app's endpoint with a valid `x-shopify-hmac-sha256` computed over the raw body using the app's `api_secret_key`.
3. Attacker captures this exact `(raw_body, x-shopify-hmac-sha256)` pair (e.g., via their own logging/proxy, since it was delivered to their own app instance's endpoint or a controlled webhook consumer).
4. Attacker sends a new HTTP request directly to the app's public webhook route with the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC [5](#0-4) .
6. The app's handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker's data, ...)` and processes/stores attacker-controlled data as if it came from `victim-shop`.
