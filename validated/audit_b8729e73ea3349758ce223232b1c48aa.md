### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body [1](#0-0) , while the `shop-domain` header, which is later used as the tenant identifier passed to the app's handler, is read from an HTTP header that is never included in the signed data [2](#0-1) . `Registry.process` validates only this body-based HMAC and then forwards `request.shop` straight into `WebhookMetadata` for the app's handler to act on [3](#0-2) . This is the same class of bug as the `BalancerLBPSwapper.init()` report: a value that is *acted on* (here, the tenant/shop identity) is not part of the value that is *cryptographically verified* (here, the raw-body HMAC).

### Finding Description
Shopify webhook authenticity in this gem is established by:
1. Computing `HMAC-SHA256(api_secret_key, raw_body)` and comparing to the `hmac-sha256`/`x-shopify-hmac-sha256` header via `Utils::HmacValidator.validate(request)` [4](#0-3) [5](#0-4) .
2. `Request#to_signable_string` returns only `@raw_body` — no shop, topic, or webhook-id is folded into the signed message [1](#0-0) .
3. Once the HMAC check passes, `Registry.process` trusts `request.shop` (sourced purely from the `shop-domain` header) as the tenant identity and hands it to the app's `handler.handle` via `WebhookMetadata` [6](#0-5) .

Because the `shop-domain` header sits entirely outside the signed payload, any request whose **body** matches a genuine, previously-observed `(body, hmac)` pair for the shared app secret will pass validation regardless of which `shop-domain` header accompanies it. The equality that should hold — "shop asserted in the header == shop the HMAC was computed for" — is not enforced; the only binding enforced is "hmac == HMAC(secret, body)", independent of shop.

An attacker who runs their own store with the app installed (an "unprivileged internet user" relative to other tenants) can:
- Trigger/capture a legitimate webhook delivery for their own shop, obtaining a real `(raw_body, hmac)` pair signed with the app's shared secret.
- Replay that exact body/hmac pair directly to the app's public webhook endpoint while substituting the `shop-domain` header with a victim shop's domain.
- The gem's `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop.

### Impact Explanation
This breaks the tenant/shop identity binding without requiring the app's `client_secret`, an access token, or any privileged credential — the attacker only needs a working, unprivileged installation of the app (or any means to trigger a webhook whose body they can predict, e.g. many `.../redact` payloads have simple/guessable bodies). Downstream consequences depend on the host application, but because this gem's own `WebhookMetadata.shop` is the field apps are expected to trust for per-tenant routing/authorization, a mismatch here directly enables cross-tenant processing — an app could act on, log, or persist attacker data under a victim shop's tenant record, or an attacker could trigger deletion/redaction/side effects attributed to a shop it does not own. This lands in the "Critical - cross-tenant access" bucket defined for this scan.

### Likelihood Explanation
Moderate-to-high: many Shopify webhook topics have fixed or low-entropy bodies (e.g., `shop/redact`, `customers/redact` mandatory topics, or webhooks with static/empty JSON), making it plausible for an attacker who controls their own shop to obtain a `(body, hmac)` pair that is byte-identical to what would be sent for other shops on the same topic, since the HMAC is shop-independent by construction in this gem's `to_signable_string`. No secret material or elevated privilege is required — only a direct HTTP request to the app's public webhook route with a forged `shop-domain` header.

### Recommendation
Bind the shop identity to the signed material, or otherwise verify `request.shop` against an expected/registered shop before trusting it in `WebhookMetadata`:
- Extend `Request#to_signable_string` (or add a secondary check in `Registry.process`) so it incorporates `shop-domain`, `topic`, and `webhook-id`, not just the raw body, or
- Require callers of `Registry.process` to supply the shop they expect to receive the webhook from and assert `request.shop == expected_shop` before dispatching to `handler.handle`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives (or triggers) a genuine webhook delivery for a topic with body `B`, together with the correct `x-shopify-hmac-sha256` header `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker sends a new HTTP POST to the app's webhook endpoint with:
   - body: the same bytes `B`
   - `x-shopify-hmac-sha256: H` (unchanged, still valid because HMAC only covers `B`)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - `x-shopify-topic`: same or another registered topic
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and matches `H` [7](#0-6) , so the request is accepted as valid.
4. `handler.handle` is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"` [6](#0-5) , even though the payload never originated from Shopify for that shop.
