## Finding

### Title
Batch Withdrawal Status Misattribution via Asset-Only Matching in POA Bridge - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
When an integrator submits a batch withdrawal containing two or more entries for the same NEP-141 asset (e.g., two USDC payouts to different destination addresses within one intent), `PoaBridge.describeWithdrawal` resolves each entry's completion status using `findMatchingWithdrawal`, which selects a withdrawal record purely by `assetId`, ignoring `destinationAddress`, `amount`, and `index`. `.find()` deterministically returns the first API record whose `near_token_id` matches, so multiple withdrawal identifiers with the same asset collapse onto the same record, causing one withdrawal's real on-chain outcome (tx hash / completion) to be reported for a *different* withdrawal.

### Finding Description
`PoaBridge.describeWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:313-343`) calls: [1](#0-0) 

```
const withdrawal = findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId);
```

and `findMatchingWithdrawal` is: [2](#0-1) 

The comment on the function explicitly acknowledges the limitation: "multiple withdrawals of the same token in a single transaction are not supported" [3](#0-2) . The identical pattern exists in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts:144-153` where `findMatchingWithdrawal` also matches only on `assetId` [4](#0-3) .

However, batch withdrawals with multiple entries are an officially supported, documented SDK feature — not an edge case requiring malicious input. The SDK's public API explicitly accepts `WithdrawalParams[]` for a single intent via `signAndSendWithdrawalIntent`/`processWithdrawal`/`createWithdrawalCompletionPromises`: [5](#0-4) [6](#0-5) 

Nothing in `withdrawalParams` type or SDK validation rejects two entries with the same `assetId` but different `destinationAddress`/`amount` (e.g., splitting a USDC balance between two recipients in one intent). Each entry gets its own `WithdrawalIdentifier` and independently calls `bridge.describeWithdrawal`. For the POA bridge, both calls hit the same `findMatchingWithdrawal(...).find()` against the *same* underlying withdrawals list returned for the NEAR tx, and both resolve to the *first* matching record for that asset — regardless of which destination address or amount is actually associated with which withdrawal index.

This breaks the equality: "status/txHash reported for withdrawal index N == the on-chain outcome of withdrawal index N." Instead, the tool reports "withdrawal index N is completed with tx hash H" when H in fact corresponds to a *different* withdrawal (to a different address/amount) in the same batch.

### Impact Explanation
An integrator using `createWithdrawalCompletionPromises` or `waitForWithdrawalCompletion` for a batch containing duplicate-asset withdrawals to different destinations would receive a false "completed" status with a valid-looking but mismatched `txHash` for the withdrawal that is actually still pending or failed. This matches the High-impact class "a status or hash misreport making an integrator credit or refund twice": the integrator could credit the second recipient as paid (using the first recipient's tx hash as proof) while the second payout is still outstanding, or mistakenly treat a pending/failed withdrawal as settled and skip retry/refund logic, leaving actual funds undelivered while books show it as delivered.

### Likelihood Explanation
Likelihood is limited to integrators who construct batch withdrawals with more than one entry sharing the same `assetId` (e.g., splitting proceeds among multiple destination addresses in a single intent, or amount-based payout splitting) — a usage pattern the SDK's batch API explicitly allows and does not warn against. No malicious actor or privileged access is required; it's a correctness bug triggered by ordinary use of a documented feature.

### Recommendation
Match withdrawal records against `destinationAddress` and `amount` in addition to `assetId` (or require the POA bridge/indexer API to return records sortable/matchable by withdrawal index), and reject/document that duplicate same-asset entries in a single batch cannot currently be tracked independently. At minimum, raise an explicit error rather than silently misattributing status when multiple candidate matches exist for the same asset.

### Proof of Concept
1. Submit `processWithdrawal({ withdrawalParams: [ {assetId: "nep141:usdc.omft.near", amount: 100n, destinationAddress: "0xAlice"}, {assetId: "nep141:usdc.omft.near", amount: 50n, destinationAddress: "0xBob"} ] })`.
2. NEAR intent settles, producing two POA bridge withdrawals for the same `near_token_id` but different `address`/`amount`.
3. Call `createWithdrawalCompletionPromises` and await `promises[1]` (Bob's withdrawal).
4. Because `findMatchingWithdrawal` in `poa-bridge.ts:418-427` matches only on `assetId`, it returns the first COMPLETED record found (Alice's), so `promises[1]` resolves as "completed" with Alice's `transfer_tx_hash`, even though Bob's withdrawal is still pending.

		args: WithdrawalIdentifier & { logger?: ILogger },

		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index

		);

			return { status: "pending" };

			return { status: "pending" };

				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});

			});
