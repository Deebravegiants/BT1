### Title
Webhook HMAC signs only the request body, not the `shop`/`topic`/`webhook_id` headers, allowing cross-tenant webhook replay/spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, and `HmacValidator.validate` verifies solely that this body's HMAC matches the app's `client_secret`. The `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers — which `Registry.process` trusts to route the payload to a handler and to construct `WebhookMetadata` — are never covered by the signature.

### Finding Description
`Request#to_signable_string` is defined as `@raw_body` only: [4](#0-3) 
`HmacValidator.validate_signature` computes the HMAC over `to_signable_string` (i.e. the body) and compares it to the `hmac-sha256` header: [3](#0-2) 
`Registry.process` only checks this body-HMAC before dispatching the handler using `request.topic` and building `WebhookMetadata` with `request.shop`, `request.webhook_id`: [2](#0-1) 

This breaks the intended binding: `verified(body) == authenticated(shop, topic, webhook_id)`. In reality the gem only verifies `verified(body)`, while `shop`/`topic`/`webhook_id` are unauthenticated bytes taken straight from attacker-controllable HTTP headers. Any party who has legitimately received one valid `(body, hmac)` pair from Shopify for their own store (e.g., a malicious merchant who installed the app, or anyone who has observed a webhook delivery) can replay that exact body+hmac to the app's webhook endpoint while substituting arbitrary `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` header values. `HmacValidator.validate` will still return `true` because it only checks the body, and `Registry.process` will hand the payload to the handler under the attacker-chosen `shop`/`topic` identity.

### Impact Explanation
This is a cross-tenant identity-binding bypass: the host application's webhook handler receives events falsely attributed to a victim shop it never actually came from (or a different topic than actually occurred), since the gem's only authentication check does not bind the payload to the shop or topic. Depending on how the host app's `WebhookHandler` implementations use `data.shop` (e.g., to look up/mutate that shop's session, trigger data-deletion for GDPR topics like `shop/redact`, `customers/redact`, or `customers/data_request`, or invalidate access), this can result in cross-tenant actions being performed against a shop the attacker doesn't own, purely by replaying a legitimately-obtained (body, hmac) pair with forged headers. This satisfies "cross-tenant access" impact.

### Likelihood Explanation
Any user who can install the app on their own store (fully unprivileged relative to other tenants) legitimately receives real `(body, hmac)` pairs for their own webhooks. Because headers are never covered by the signature, forging the `shop`/`topic`/`webhook_id` headers on a replayed request requires no cryptographic secret at all — it is a pure HTTP-level header substitution against the app's public webhook endpoint.

### Recommendation
Bind the shop, topic, and webhook id into the value that is HMAC-verified, or otherwise cryptographically bind them to the verified body (e.g., include them in `to_signable_string`, or independently confirm the delivered `shop`/`topic` against a value derived from the verified body/session, and reject if a given `webhook_id` was already processed for a different shop or topic).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify deliver one webhook (any topic), capturing the exact `raw_body` and the `x-shopify-hmac-sha256` header value.
2. Attacker sends a POST to the app's webhook endpoint with the identical body and `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim.myshopify.com` and `x-shopify-topic` to a mandatory topic such as `shop/redact`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the (unmodified) body against the (unmodified) hmac header: [5](#0-4) 
4. The registered handler for `shop/redact` is invoked with `WebhookMetadata` carrying `shop: "victim.myshopify.com"`, causing the host app to perform victim-shop-scoped actions triggered by data the attacker fully controls.
