Audit Report

## Title
Missing `return` After Failed Email-Claim Extraction Lets OIDC Token Exchange Silently Continue and Issue an Authenticated Session - (File: core/sessions/oidcauth/oidc.go)

## Summary
In `handleTokenExchange`, the `email, ok := claims["email"].(string)` failure branch writes an HTTP 500 body but omits the `return` statement present in every other error branch of the function, so execution continues into session creation, audit logging, and the final `200 OK` success response. The same omission occurs again at the `oidc_sessions` DB-insert error branch a few lines later.

## Finding Description
`handleTokenExchange` performs the OIDC authorization-code exchange and, on success, is expected to persist a session in `oidc_sessions`, set a session cookie, and return `ExchangeTokenResponse{Success: true}`. Every prior error condition in the function (`ShouldBindJSON`, state mismatch, `Exchange`, missing `id_token`, `Verify`, `idToken.Claims`, `ExtractIDClaimValues`, `IDClaimsToUserRole`) correctly writes an error response and returns immediately. The `email` claim check at lines 226-230 breaks this pattern — it logs and writes an error body but falls through, so `IDClaimsToUserRole`, the `oidc_sessions` INSERT (with `user_email` set to the empty string or a non-string value), `AuthLoginSuccessNo2FA` audit logging, `ginSession.Save()`, and the terminal `c.JSON(http.StatusOK, ...)` all still execute. The same defect recurs for the DB insert error at lines 257-260: a failed persistence attempt is still followed by `ginSession.Save()` and a success response. Existing checks (state validation, token verification, claims parsing) do not compensate for this specific omission, since it occurs after all of those checks have already passed.

## Impact Explanation
This is a session-integrity defect: the server can mint and hand back a valid, cookie-authenticated session while the client-visible/logged result is inconsistent with the internal error state, and the persisted `user_email` collapses to an empty/malformed value for every occurrence, creating potential identity confusion between such sessions in `oidc_sessions` lookups. The role assigned to the session is still derived independently via `IDClaimsToUserRole` from separate group claims, so this bug does not directly escalate privilege beyond what the IdP's claims otherwise grant, but it does produce an authenticated session bound to an incorrect/empty identity, and a "success" response can be returned even when session persistence itself failed (DB-insert branch).

## Likelihood Explanation
Triggering the vulnerable branch requires the OIDC identity provider to complete a legitimate authorization-code exchange but omit (or return non-string) the `email` claim in the ID token — a scenario that arises from IdP/scope misconfiguration (e.g., `email` scope not requested/granted) rather than from an anonymous attacker directly forcing this state without any trust relationship to the login flow. It is not exploitable purely by an unauthenticated network client without going through a real IdP exchange, which limits practical likelihood to misconfigured or compromised-IdP deployments rather than a straightforward remote unauthenticated bypass.

## Recommendation
Add `return` immediately after the error response in the `email` claim check:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims. error: %v", err)
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```
Add the equivalent `return` after the `oidc_sessions` INSERT error at lines 257-260 so a failed session-creation is never followed by `ginSession.Save()` and a `200 OK` response.

## Proof of Concept
1. Stand up or configure an OIDC provider/test double that completes the authorization-code exchange and ID-token verification successfully but returns claims without an `email` field (or with `email` as a non-string, e.g. `null`).
2. Drive the standard OIDC login flow against the node (`/redirect` then callback to the token-exchange endpoint backing `handleTokenExchange`) with a valid `code`/`state`.
3. Observe server logs show `"Failed to get email from claims"` yet the HTTP response is `200 OK` with `ExchangeTokenResponse{Success: true}` and a valid session cookie (`webauth.SessionIDKey`) is set.
4. Confirm the `oidc_sessions` table contains a row with `user_email = ''` and that the session cookie is usable for subsequent authenticated requests, demonstrating the fail-open behavior.
