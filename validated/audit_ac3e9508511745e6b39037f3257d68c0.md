Confirmed: `_orders` is a per-(commitment, token) accounting mapping [1](#0-0) , while the actual token custody is a single, shared, pooled ERC-20 balance held by the IntentGateway contract across every order that escrows that token — exactly the shared-pool-vs-per-user-accounting pattern the report describes.

### Title
Escrowed-Balance Accounting Desync With Rebasing Input Tokens Can Permanently Lock or Insolvency-Break IntentGateway Escrow - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2`/`IntentsBase` escrows arbitrary ERC-20 input tokens named by the user in `placeOrder`, recording the escrowed amount per `(commitment, token)` in the `_orders` mapping [1](#0-0) . All orders that escrow the same token share one physical ERC-20 balance on the gateway contract, but withdrawals are driven purely off the `_orders` bookkeeping value, not off any comparison to the contract's live `balanceOf`. If the escrowed token is a rebasing token, the gateway's actual balance can drift away from the sum of all `_orders[...][token]` entries over time, producing either stuck value or reverting withdrawals for other users sharing that token.

### Finding Description
`placeOrder` only special-cases the *initial* transfer for fee-on-transfer tokens by diffing balances immediately before/after the `transferFrom`, and stores the "received" amount as `reducedInputs[i].amount` in `_orders[commitment][token]` [2](#0-1) . This diff protects only against the single-transaction discount; it does nothing about balance changes that happen to the token's supply *while it sits in escrow* between `placeOrder` and eventual `_withdraw`.

`_withdraw` (called on fill/refund settlement) decrements the bookkeeping value and does a plain `IERC20.safeTransfer` for the recorded amount, with no check against the gateway's actual token balance:
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;
...
IERC20(token).safeTransfer(beneficiary, amount);
``` [3](#0-2) 

Because the gateway holds one pooled balance per token address across *every* open order (not a segregated escrow per order), a rebase changes the token amount actually custodied without any code path updating `_orders`:

- **Negative rebase** (token supply/balance of the holder shrinks, e.g. a slashed liquid-staking derivative): the sum of all `_orders[...][token]` entries across open orders exceeds the gateway's true `balanceOf(gateway)`. Whichever order's `_withdraw`/fill/refund executes first still succeeds, but a later order sharing the same token can have its `safeTransfer` revert because the physical balance is insufficient — permanently freezing that user's/solver's funds and blocking `RedeemEscrow`/`RefundEscrow` delivery for that order (a route that becomes unable to deliver settlement for funds it legitimately escrowed).
- **Positive rebase** (token balance grows while held, e.g. a rebasing yield token): the surplus tokens accrue on the gateway contract but are never reflected in any `_orders` entry and are not swept by the dust-collection logic (`DustCollected`/`SweepDust`), which only fires for the fee-on-transfer discrepancy measured inside `placeOrder`'s predispatch sweep [4](#0-3) . That value is permanently stuck — no function reads or releases balance beyond what `_orders` tracks.

This is reachable by any unprivileged user simply by calling `placeOrder` with `TokenInfo.token` set to a rebasing ERC-20's address; nothing in `placeOrder`/`fillOrder`/`_withdraw` validates or restricts the token to non-rebasing assets.

### Impact Explanation
This breaks the core escrow invariant that every order's recorded input amount is redeemable. A negative rebase can cause legitimate solver/user withdrawals to permanently revert (frozen funds, denial of settlement) for orders that are otherwise valid and correctly filled/cancelled — a High-severity freezing-of-funds condition on a path directly reachable from a single `placeOrder`/`fillOrder` transaction. A positive rebase causes permanent, unrecoverable value loss (stuck tokens) for the protocol/users, since there is no privileged or unprivileged path to reconcile `_orders` totals with actual balance.

### Likelihood Explanation
Likelihood depends on solver/integrator/user choosing to route a rebasing token through `IntentGatewayV2`, which is entirely permitted by the contract — there is no allowlist or check rejecting rebasing tokens in `placeOrder`, `fillOrder`, or `_withdraw`. Any market that lists a rebasing/liquid-staking-style token as tradable input triggers this whenever the token rebases while escrowed, which for tokens like stETH-style assets or elastic-supply tokens happens routinely (e.g., daily rebases), not merely under adversarial conditions.

### Recommendation
Either (a) explicitly disallow rebasing/elastic-supply tokens as valid `TokenInfo.token` inputs, or (b) segregate escrow accounting per order using shares/exchange-rate accounting instead of raw stored amounts, or (c) validate at withdrawal time that `IERC20(token).balanceOf(address(this)) >= amount` and handle shortfalls (e.g., pro-rata reduction with an explicit shortfall event) rather than allowing an unconditional `safeTransfer` to revert and permanently lock the order.

### Proof of Concept
1. User A calls `placeOrder` escrowing 1000 units of rebasing token `RBT` (input recorded as `_orders[commitmentA][RBT] = 1000`).
2. User B calls `placeOrder` escrowing 1000 units of the same `RBT` (`_orders[commitmentB][RBT] = 1000`); gateway's `balanceOf(gateway)` is now 2000.
3. `RBT` undergoes a negative rebase, reducing the gateway's actual `balanceOf` to 1500 (each order's proportional share is now ~750, but `_orders` still records 1000 each).
4. Order A is filled cross-chain; settlement `onAccept` → `_withdraw` decrements `_orders[commitmentA][RBT]` to 0 and calls `safeTransfer(solverA, 1000)`, which succeeds because 1500 ≥ 1000, draining most of the remaining balance.
5. Order B is filled; `_withdraw` attempts `safeTransfer(solverB, 1000)` against a gateway balance of only 500 — the ERC-20 transfer reverts, permanently blocking `RedeemEscrow` delivery for order B and freezing solver B's/user B's entitled tokens, even though order B was legitimately escrowed and filled.
