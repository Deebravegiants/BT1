### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC computed by `Utils::HmacValidator` binds solely to the body bytes. The `shop` (tenant identity) is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed material, yet it is passed straight through to the host application's webhook handler as the trusted tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook exclusively via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For webhooks, `to_signable_string` is defined as just the raw body: [3](#0-2) 

Meanwhile `shop` is parsed from an HTTP header that is completely outside that signed string: [4](#0-3) 

After HMAC validation succeeds, `Registry.process` forwards this unauthenticated `shop` value directly into `WebhookMetadata`, which the host app's handler treats as the authoritative tenant/shop for the event: [5](#0-4) [6](#0-5) 

The documented binding this gem promises is: *"This will verify the request did indeed come from Shopify"* (per `docs/usage/webhooks.md`), which developers reasonably read as "the whole tuple `(shop, topic, body)` reported to my handler is authentic." In reality the equality the code actually checks is:

`HMAC(secret, raw_body) == received_hmac`

but the equality the handler relies on for tenant isolation is:

`shop_header == shop_that_actually_sent_this_body`

These are not the same binding. Since `shop` (and `topic`, `webhook_id`, `api_version`) are excluded from the signable string, any request whose body+HMAC pair is valid for *some* shop (e.g. one the attacker legitimately controls, or a captured/replayed webhook payload) can have its `shop-domain` header rewritten to an arbitrary victim shop domain by an unprivileged internet user submitting directly to the app's webhook endpoint — HMAC validation still passes because it never inspected the header.

### Impact Explanation
This breaks per-tenant identity binding at exactly the multi-tenant boundary this gem's webhook processing is supposed to enforce. An app that (as the shipped example handler in the docs does) uses `data.shop` to route webhook processing to per-shop records, jobs, or database rows will process/attribute attacker-controlled data under a victim shop's identity — i.e., cross-tenant access/confusion, satisfying the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any unprivileged internet user can POST directly to the app's public webhook endpoint. They need one HMAC-valid `(body, hmac)` pair (trivially obtainable by triggering any webhook on a shop they install the app on, or reusing/replaying a previously observed webhook) and can then freely set the `shopify-shop-domain` header to any victim shop before resending it to the same endpoint — no secret material is required for the header field itself.

### Recommendation
Include the shop domain (and ideally topic/webhook id/api version) in the HMAC-signed material, or require the app to independently verify that the `shop-domain` header corresponds to a shop it has a matching webhook registration/session for. At minimum, document and enforce that `shop` from `WebhookMetadata` must not be trusted for tenant identification unless separately corroborated (e.g., cross-checked against an existing installed shop/session record) before being used to key any storage or job.

### Proof of Concept
1. Register the app on attacker's own shop `attacker.myshopify.com`, capture a legitimate webhook request Shopify sends (raw body `B` and its valid `hmac-sha256` header `H`, computed by Shopify with the app's `client_secret` over `B`).
2. Replay the exact same request to the app's public webhook endpoint, but change the `X-Shopify-Shop-Domain` header to `victim.myshopify.com` (and optionally spoof `X-Shopify-Webhook-Id`/topic if relevant), keeping body `B` and hmac header `H` unchanged.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim.myshopify.com", "x-shopify-hmac-sha256" => H, ...})` is constructed.
4. `Utils::HmacValidator.validate(request)` calls `to_signable_string`, which returns only `B`; `OpenSSL.secure_compare(HMAC(secret, B), H)` succeeds because `B` and `H` are unmodified. [7](#0-6) 
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed_body_from_attacker_shop, ...)`, and the host application (following the gem's own documented example) processes/queues this data under `victim.myshopify.com`'s identity — a full break of tenant isolation despite HMAC validation "succeeding".
