### Title
`onPostRequestTimeout` incorrectly gated by `whenNotPaused`, blocking refunds of already-burned tokens - ([File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol])

### Summary
`HyperFungibleToken` and `HyperFungibleTokenUpgradeable` guard both the entry point that starts new cross-chain transfers (`send`) and the entry point that finalizes an already-in-flight, timed-out transfer (`onPostRequestTimeout`) with the same `whenNotPaused` modifier. Pausing the contract is meant to stop new outbound/inbound transfers, but it also blocks refunding tokens that were already burned for a transfer that has since timed out, freezing user funds for the duration of the pause.

### Finding Description
`send()` burns the caller's tokens and dispatches an ISMP POST request; `onAccept()` mints tokens on the destination when the message is delivered; and `onPostRequestTimeout()` re-mints the burned tokens back to the sender if the message never gets delivered before its timeout. All three are marked `whenNotPaused`: [1](#0-0) [2](#0-1) [3](#0-2) 

The same pattern exists in the upgradeable variant: [4](#0-3) 

`onPostRequestTimeout` is invoked by the ISMP host (via `HandlerV2.handlePostRequestTimeouts` → `host.dispatchTimeOut` → `IIsmpModule.onPostRequestTimeout`) once *any* relayer submits a valid non-membership proof that the outgoing request timed out — this is a permissionless path reachable at any time after timeout, independent of whether new sends are allowed. `pause()` is documented as pausing "all cross-chain operations (send and receive)": [5](#0-4) 

However, unlike `send`/`onAccept` (which correctly gate *new* activity), `onPostRequestTimeout` completes an operation that was already committed (tokens already burned) before the pause took effect. Applying `whenNotPaused` here mirrors exactly the audit-report pattern: `is_accepting_new_orders` should only gate acceptance of *new* orders, not the execution/completion of already-pending ones; the implementation incorrectly reuses the same guard for both, blocking legitimate completion of prior commitments.

### Impact Explanation
While the token is paused (e.g. owner pauses due to an incident, an emergency, or simply as routine risk management), any user whose `send()` transfer subsequently times out cannot have their already-burned tokens refunded — `onPostRequestTimeout` reverts under `whenNotPaused`. Per the ISMP timeout-handling semantics, a reverted `on_timeout` callback leaves the request commitment intact so the timeout can be retried later, but until the contract is unpaused, the user's funds are burned and unrecoverable. This is a freezing-of-funds condition on any user with an in-flight transfer at pause time, entirely outside the affected user's control, and not necessarily short-lived (pause duration is at the owner's discretion, with no correctness invariant tying it to prevention-of-refund).

### Likelihood Explanation
Likely to trigger in the normal, non-malicious operational lifecycle of the token: any owner pausing the contract (a supported, expected admin action for security purposes) while cross-chain transfers are in flight will strand any transfer that later times out during the pause window. No malicious actor is required — it is a straightforward consequence of correct-use pausing.

### Recommendation
Do not gate `onPostRequestTimeout` (and any other function that completes/refunds a previously-committed action) with `whenNotPaused`. Reserve the pause check for functions that initiate new state (`send`, `onAccept`), consistent with how `HandlerV2`'s `notFrozen` distinguishes outgoing vs. incoming freeze states rather than blanket-blocking timeout processing.

### Proof of Concept
1. Alice calls `send()` on chain A, burning `amount` tokens and dispatching a POST request to chain B with `timeout = T`.
2. Before delivery, the owner calls `pause()` on chain A's `HyperFungibleToken` (e.g., due to an unrelated incident).
3. The message is never delivered before `T` elapses (destination congestion, liveness failure, or simply chain B being also paused).
4. A relayer submits `handlePostRequestTimeouts` with a valid non-membership proof; the host calls `onPostRequestTimeout` on chain A's token contract.
5. `onPostRequestTimeout` reverts due to `whenNotPaused`; Alice's burned tokens are not re-minted, and the request commitment is retained for retry (per `modules/ismp/core/src/handlers/timeout.rs`), but Alice remains unable to reclaim funds until the owner unpauses — an owner-controlled, indefinite freeze window.
