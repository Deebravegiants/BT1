### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` attribute from the `x-shopify-shop-domain` HTTP header, but `HmacValidator.validate` only verifies the HMAC over `to_signable_string`, which returns the raw request body alone. The `shop` header (along with `topic`, `webhook_id`, `api_version`) is never bound into the signed material, so the equality the gem implicitly asserts — "the shop that authorized/signed this payload" == "the shop attribute exposed to the handler" — does not actually hold.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated once `Utils::HmacValidator.validate(request)` passes: [1](#0-0) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw HTTP body (`@raw_body`), while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers that are not part of the signed string: [3](#0-2) [4](#0-3) 

The processed metadata object then hands this unverified `shop` value straight to the app's `WebhookHandler#handle`, as the tenant identifier the handler is expected to trust: [5](#0-4) [6](#0-5) 

This breaks the intended identity binding:
`HMAC-verified(raw_body)` == `shop attribute trusted by handler`

In reality the binding is only:
`HMAC-verified(raw_body)` while `shop` is attacker-controlled header data with no cryptographic tie to the body or to the HMAC.

Contrast this with the OAuth callback path, where `shop` **is** included in `to_signable_string` and therefore is HMAC-bound: [7](#0-6) 

The webhook path lacks this equivalent binding, which is the direct analog of the `TemporalGovernor` bug class: a field that is acted upon (here, tenant attribution) is not covered by the same authentication mechanism (here, the HMAC) that gatekeeps the surrounding operation.

### Impact Explanation
An unauthenticated internet user who possesses (or can capture) any single valid `(raw_body, hmac)` pair for a webhook topic — for example, from their own shop's outgoing webhook traffic, or from a topic whose body is not sensitive/unique per shop — can replay that exact body/HMAC pair while substituting an arbitrary `x-shopify-shop-domain` header. Because the header is not part of the signed content, `HmacValidator.validate` still returns `true`, and the app's handler receives `data.shop` set to the attacker-chosen shop domain rather than the shop that genuinely produced the payload. If the host application uses `data.shop` (as documented/intended) to select which merchant's session/data store to write into, this leads to cross-tenant data confusion — writing or acting on data attributed to a shop that never sent it. This satisfies the "cross-tenant access" Critical impact category, since the trust boundary between tenants is defined by this `shop` field and the gem presents it as verified when it is not.

### Likelihood Explanation
This does not require any of the excluded conditions — no `api_secret_key`, no access token, no privileged account, and no host-application misuse of a documented API is needed. The library's own `Registry.process`/`Request` code path is what exposes the unverified `shop` field as if it were part of the authenticated payload. Any actor able to send one legitimate/valid webhook body+HMAC to the shared callback route (e.g., their own store's webhook traffic, which they fully control and can forward or replay) can perform this attack; it does not require possessing anyone else's secret. This is a realistic and directly exploitable condition, not merely theoretical.

### Recommendation
Bind the tenant/topic identity into the HMAC verification for webhooks, analogous to the OAuth flow. Concretely: include `shop`, `topic`, and any other fields the handler is expected to trust in `Request#to_signable_string` (or require/verify that the shop domain is independently confirmed, e.g. by checking it against a shop known via an existing session before dispatching to the handler). At minimum, the gem should not present `shop` on `WebhookMetadata` as if it is authenticated when the HMAC does not cover it; documentation and code should make this explicit, or the design should be changed so verification actually spans the identity-bearing fields.

### Proof of Concept
1. Attacker controls (or observes) a store that receives real Shopify webhooks; they capture one valid webhook request: raw body `B` and header `x-shopify-hmac-sha256` computed by Shopify with the app's `client_secret` over `B`.
2. Attacker sends a forged HTTP request to the app's webhook endpoint with:
   - Same raw body `B`
   - Same valid `x-shopify-hmac-sha256` header
   - `x-shopify-shop-domain` header changed to `victim-shop.myshopify.com`
   - `x-shopify-topic` unchanged or changed as needed
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`; since `to_signable_string` only returns `B`, the HMAC still matches:
```ruby
# lib/shopify_api/webhooks/request.rb
def to_signable_string
  @raw_body
end
```
4. `Registry.process` proceeds and calls the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, i.e., the app processes the payload as if it originated from `victim-shop.myshopify.com`, even though that shop never sent it.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

      def initialize(raw_body:, headers:)

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
