### Title
Webhook Shop-Domain Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the HMAC over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and label the webhook to a specific merchant are read from unauthenticated HTTP headers that are never included in the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the HMAC solely against this signable string: [2](#0-1) 

Meanwhile, `Registry.process` uses `request.shop` (and `topic`, `webhook_id`, `api_version`) — all sourced directly from HTTP headers rather than the signed body — to build the `WebhookMetadata` handed to the host application's handler: [3](#0-2) 

The `shop` accessor reads straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic binding to the HMAC-verified body: [4](#0-3) [5](#0-4) 

This is the same bug class as the report: a field that is *acted on* (here, the `shop` identity used to attribute webhook data to a tenant) is not covered by the authenticity check (the HMAC), while a different field that *is* covered (the body) is treated as sufficient proof of the whole message's authenticity. The identity binding that should hold — `shop used by the handler == shop the HMAC-signed body actually belongs to` — is not enforced anywhere in this library.

### Impact Explanation
Because the app's webhook HMAC secret (`api_secret_key`) is shared across all shops that have installed the app, any tenant (an unprivileged merchant who installs the app, or anyone who can otherwise obtain one valid `(raw_body, hmac)` pair delivered to the app) can capture a legitimately signed webhook and replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header claiming to be a different, victim shop. `Utils::HmacValidator.validate` will still pass because it never inspects the shop header, and `Registry.process` will hand the host application a `WebhookMetadata` object asserting the (attacker-chosen) victim shop as the source of that body. If the host application uses `data.shop` to look up per-tenant state, credentials, or to trigger tenant-scoped side effects (as the library's own docs/tests show, e.g. `assert_equal(@shop, data.shop)`), this results in cross-tenant data/state confusion driven entirely by unauthenticated attacker input.

### Likelihood Explanation
Exploitation requires no privileged credentials, no access token, and no knowledge of `api_secret_key` — only one legitimately observed webhook body+HMAC pair (trivially available to any merchant that installs the app, since the app's webhook secret is shared across all shops) and the ability to send an HTTP request to the app's public webhook endpoint with a modified shop header. This is a realistic, low-effort attack path fully reachable through this gem's documented API (`Registry.process`).

### Recommendation
Bind the shop identity to the HMAC-verified payload instead of trusting the header outright: either (a) include the shop domain in the value covered by the HMAC comparison, or (b) require host applications to cross-check `request.shop` against an independently established per-installation identifier (e.g., the shop associated with the specific webhook subscription/registration ID) before trusting it, and document this requirement clearly since `Registry.process`'s current contract implies the entire `WebhookMetadata`, including `shop`, is verified.

### Proof of Concept
1. App `MyApp` is installed on `attacker.myshopify.com`. Shopify delivers a real webhook to the app with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. The attacker (the merchant on `attacker.myshopify.com`, an unprivileged actor w.r.t. other tenants) captures `B` and `H` from their own delivered webhook (no secret key needed — HMAC value is visible in the request they legitimately received).
3. Attacker sends a new POST to the app's webhook endpoint with the same body `B`, the same `X-Shopify-Hmac-Sha256: H` header, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers with `request.shop == "victim.myshopify.com"`. `Utils::HmacValidator.validate` recomputes HMAC over `@raw_body` (`B`) only, which matches `H`, so validation passes.
5. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed_body_of_B, ...)`, causing the host app to process attacker-controlled body content attributed to `victim.myshopify.com`.
