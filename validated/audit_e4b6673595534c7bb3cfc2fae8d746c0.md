### Title
Unvalidated user-supplied `beneficiary` address allows solver output tokens to be permanently stuck in `IntentGatewayV2` - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol, evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder` lets the order creator set `order.output.beneficiary` to any `bytes32`-encoded address with no validation. When a solver fills the order via `fillOrder → _fillSameChain`, the solver's output tokens are sent directly to that unchecked `beneficiary` with `IERC20.safeTransferFrom(msg.sender, beneficiary, ...)` or a raw native-value `.call`. If the user sets `beneficiary` to the gateway contract's own address (`address(this)`) — or to any other address that cannot use the funds — the solver's tokens land in the gateway itself and are not recoverable through any user-facing function, mirroring the RMM-core `withdraw()` bug where a user-supplied `recipient` could be set to the engine address itself, stranding funds.

### Finding Description
`placeOrder` (evm/src/apps/IntentGatewayV2.sol:194-415) stores `order.output.beneficiary` verbatim as part of the order and emits it in `OrderPlaced`, performing no check that it is non-zero or different from `address(this)`: [1](#0-0) 

On fill, `_fillSameChain` decodes the beneficiary and transfers the solver's output funds straight to it: [2](#0-1) 

There is no check anywhere in `placeOrder`, `fillOrder`, or `_fillSameChain`/`_fillCrossChain` that `beneficiary != address(this)` (the gateway itself) or `beneficiary != address(0)`. The cross-chain release path (`_withdraw` in `IntentsBase.sol`) has the same unconditional transfer pattern: [3](#0-2) 

If a user places an order with `output.beneficiary = address(intentGateway)` (either by mistake, or a malicious order-placer targeting an unsuspecting solver), a solver that fills the order sends its output assets to the gateway contract address itself. Unlike protocol dust (recoverable only via the host-gated `SweepDust` request), there is no mechanism for the solver or anyone else to recover these mis-routed funds — they are permanently locked in the contract's balance.

### Impact Explanation
This causes a permanent freezing of solver funds: real ERC20/native tokens transferred by an unprivileged solver during `fillOrder` become irrecoverably stuck in the `IntentGatewayV2` contract, with no owner/withdraw path available to the solver or the order placer. This satisfies the "permanent freezing of funds" bar for Medium/High severity. The order-placer side is also affected for the escrow: `_withdraw`'s `body.beneficiary` for solver-side compensation (`msg.sender`) is safe, but the destination-side beneficiary used for the *output* leg is entirely user-controlled and unchecked, so the loss falls on whichever party (solver) provides output value against a bad beneficiary. This is reachable from a single `placeOrder` + `fillOrder` transaction pair by any unprivileged user/solver — no privileged role, no governance, no p2p/consensus dependency.

### Likelihood Explanation
Likelihood is driven by user error/negligence in constructing `order.output.beneficiary` (analogous to the original report's "Alice accidentally specifies the engine address"), and it can also be deliberately exploited by a malicious order-placer who crafts an order with `beneficiary = address(intentGateway)` to bait a solver's automatic fill logic into sending it real value that gets trapped. Since solvers often fill orders programmatically based on decoded parameters without re-validating the beneficiary against a blocklist of unsafe addresses, this is a plausible and repeatable griefing vector, not merely a one-off accident.

### Recommendation
- **Short term:** In `placeOrder`, validate `order.output.beneficiary` is non-zero and not equal to `address(this)` (and not equal to any other known unsafe/gateway address for cross-chain instances), reverting with `InvalidInput` otherwise. Apply the same guard to any other user-supplied recipient fields (e.g., `order.session`, cross-chain destination gateway addresses if user-controllable).
- **Long term:** Add invariant/property-based tests (e.g., Echidna/Foundry fuzzing) asserting that `beneficiary` can never resolve to the gateway's own address across `placeOrder`/`fillOrder`/`_withdraw` paths, and that no user-reachable code path can result in tokens being sent to `address(this)` without a corresponding recovery mechanism.

### Proof of Concept
1. User calls `placeOrder(order, graffiti)` with `order.output.beneficiary = bytes32(uint256(uint160(address(intentGateway))))` and valid `inputs`/`output.assets`.
2. `placeOrder` escrows the user's inputs and emits `OrderPlaced` with the unchecked beneficiary; no revert occurs (evm/src/apps/IntentGatewayV2.sol:194-414).
3. A solver, evaluating the order off-chain (without cross-checking beneficiary against the gateway address), calls `fillOrder(order, options)`.
4. `_fillSameChain` executes `IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal)` (or the native `.call`) sending the solver's output tokens to `beneficiary == address(intentGateway)` (evm/src/apps/intentsv2/IntrinsicIntents.sol:95-106).
5. The solver's output tokens now sit in the gateway's own balance. There is no user-callable function to withdraw arbitrary balances sent this way (the only sweep, `SweepDust`, is host-gated and intended for protocol fee dust, not solver payments) — the funds are permanently stuck.
