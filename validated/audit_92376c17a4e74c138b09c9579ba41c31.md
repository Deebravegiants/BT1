### Title
Webhook shop-domain identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating that `hmac-sha256` matches a signature computed over the raw request body [1](#0-0) . The `shop-domain` header, however, is never part of the signed bytes, yet it is the value used to attribute the webhook to a tenant and is handed unchanged to every app's `WebhookHandler#handle` implementation [2](#0-1) . This breaks the identity binding `shop (authenticated) == shop (acted upon)` in the same way the ERC1155 report describes a receiver address that is used to move value without being covered by the operation's authorization check.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 

`Webhooks::Request#shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, entirely independent of that signable string: [4](#0-3) 

`Utils::HmacValidator.validate` computes and compares the HMAC only against `verifiable_query.to_signable_string`: [5](#0-4) 

So the HMAC proves "this JSON body was signed by someone holding the app's `client_secret` (Shopify)" — it proves nothing about which shop the body is attributed to. `Registry.process` nonetheless treats `request.shop` as trusted tenant identity and forwards it into `WebhookMetadata`, which host applications use to look up the shop's session/access token or to update per-shop state: [6](#0-5) [7](#0-6) 

Contrast this with the OAuth callback path, `Auth::Oauth::AuthQuery`, where `shop` **is** included in the signable string alongside `code`, `host`, `state`, and `timestamp` [8](#0-7) , so the shop identity is correctly bound to the signature there. The webhook path lacks the equivalent binding.

Any party that has legitimately received one authentic webhook for a shop with the same app installed (e.g., an attacker who installs the target app on their own store to obtain a real, correctly-signed webhook body) can capture that `(raw_body, hmac)` pair — the HMAC secret is the app's single `client_secret`, shared across all shops that install the app — and replay it to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header. `HmacValidator.validate` will still pass because it only checks the untouched body against the same secret; `Registry.process` will then hand the app's handler a `WebhookMetadata` claiming the payload came from the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding bypass: the gem asserts the shop identity of a webhook is verified when in fact only the payload bytes are verified. Depending on how the host application's `WebhookHandler` implementations use `data.shop` (e.g., to look up the target shop's session, mark `app/uninstalled`, process `shop/update`, or fulfill mandatory GDPR topics like `customers/data_request`/`customers/redact`/`shop/redact`), this permits an attacker who controls one shop instance of the app to inject falsely-attributed events for a different, victim shop — a cross-tenant impact.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app on their own shop (an "unprivileged" externally-available action for any public/installable app) to obtain one authentic, HMAC-signed webhook body, and then be able to submit an HTTP request to the app's public webhook endpoint with a modified `shop-domain` header — no access to `client_secret`, tokens, or the victim's credentials is required.

### Recommendation
- Include the shop domain (and ideally `webhook_id`/`api_version`) inside the HMAC-signed material, or otherwise cryptographically bind the shop identity to the payload, mirroring what `Auth::Oauth::AuthQuery#to_signable_string` already does for `shop`.
- If Shopify's webhook signing scheme does not cover headers, require host applications to independently corroborate `shop-domain` against a shop known from another authenticated channel (e.g., an already-stored session) before trusting it, and document this requirement prominently in `docs/usage/webhooks.md`.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com`, triggering a genuine webhook delivery to the app's callback endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body B>`, and body `B`.
2. Attacker captures `(B, valid_hmac)` (e.g., via their own proxy/logging in front of their webhook receiver, or by an app that echoes it back).
3. Attacker sends a new HTTP request to the same public webhook endpoint with the identical body `B` and identical `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` only, matches the supplied signature, and returns `true`.
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and invokes the app's handler, which acts as if the (attacker-controlled) payload genuinely originated from the victim shop.
