### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop`, `topic`, `webhook_id`, and `api_version` values consumed by the handler come from HTTP headers that are never included in the signed material.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate_signature` computes the HMAC over exactly this `to_signable_string` value and compares it against the `hmac` accessor, which is likewise read from a header (`hmac-sha256`): [2](#0-1) [3](#0-2) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from separate, unsigned HTTP headers: [4](#0-3) 

`Registry.process` validates only the HMAC over the body and then forwards the header-derived `shop` value straight into the `WebhookMetadata` passed to the app's handler, with no cross-check that this shop is the one the HMAC was actually issued for: [5](#0-4) 

Because the app's `client_secret` (used to compute the HMAC) is shared across every shop that installs a multi-tenant app, any merchant who legitimately installs the app receives real webhook deliveries with a valid HMAC for a body they control the shape of. That same merchant can replay the request, keeping the body and its valid `hmac-sha256` value intact, but substitute an arbitrary `x-shopify-shop-domain` (and/or `x-shopify-topic`) header pointing at a victim shop. The gem's `HmacValidator.validate` will report `true` because the HMAC only ever covered the (unmodified) body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

This breaks the intended identity binding:
`hmac_valid(body) == true` should imply `shop_header == shop_that_generated(body, hmac)`, but the code only enforces `hmac_valid(body) == true` while trusting `shop_header` unconditionally — i.e. the equality `shop_header == shop_bound_by_hmac` is never checked.

### Impact Explanation
If the host application's webhook handler uses `WebhookMetadata#shop` to key any privileged operation (e.g., "look up shop record, update local database, write authorization data") without an independent check that the shop was genuinely the one that installed the app and generated that payload, an attacker-controlled merchant can inject arbitrary attacker-chosen body content that is falsely attributed to a different tenant. This is a cross-tenant data integrity/confusion issue within the gem's own webhook-authentication primitive, matching the Critical "cross-tenant access" category: the shop-scoping guarantee the gem is expected to provide (an HMAC-validated webhook implies the shop header is trustworthy) does not actually hold.

### Likelihood Explanation
Exploitation requires only that the attacker be a merchant who has installed the target app (an ordinary, unprivileged install — no leaked credentials, no access to `api_secret_key`, no social engineering). They can freely craft the JSON body of their own legitimate webhook deliveries (e.g., product/order fields) and replay the delivered request with a modified `shop-domain` header, since nothing besides the raw body is protected by the signature. This is a low-effort, repeatable network-only attack against any app whose webhook handler trusts `WebhookMetadata#shop`/`topic` as authenticated.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the signed/verifiable material, or otherwise cryptographically bind them to the HMAC — for example, incorporate the `shop-domain` header into `to_signable_string`, or independently verify the header-provided shop against a shop known to be associated with the specific HMAC/webhook subscription (e.g., cross-reference against the webhook_id returned from Shopify's API) before handing it to the handler. At minimum, update documentation to explicitly and prominently warn implementers that `WebhookMetadata#shop`/`topic` are unauthenticated header values that must be independently validated by the host application before being trusted for tenant-scoped operations.

### Proof of Concept
1. App `MyApp` is a multi-tenant Shopify app; shop `attacker.myshopify.com` installs it and receives real webhook deliveries (e.g. `orders/create`) signed with the app's shared `client_secret`.
2. The attacker's own store triggers a webhook delivery with a body of their choosing (they can create orders/products with attacker-controlled field content on their own store). Shopify computes and sends a valid `x-shopify-hmac-sha256` for that body plus header `x-shopify-shop-domain: attacker.myshopify.com`.
3. The attacker intercepts/replays this request to the app's webhook endpoint, keeping the body and `x-shopify-hmac-sha256` unchanged, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers; `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only and it matches, so `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) proceeds.
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` with attacker-chosen body content, believing the data legitimately originated from `victim.myshopify.com`.
