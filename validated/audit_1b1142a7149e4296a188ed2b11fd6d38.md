### Title
Escrow release/refund loops over all order tokens without per-token isolation, letting one malicious/blacklisting ERC20 permanently freeze a multi-token order's entire escrow - (File: evm/src/apps/intentsv2/IntentsBase.sol, evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
Hyperbridge's Intent Gateway lets a user escrow multiple input tokens per order (`order.inputs` is a `TokenInfo[]`). When escrow is released — on a successful fill (`RedeemEscrow`) or a cancellation (`RefundEscrow`) — the gateway iterates over every token in the withdrawal request and transfers each one in a single, unguarded loop. If any single token in that list reverts on transfer (blacklist-capable token, pausable token, or a token an attacker deliberately makes revert), the entire withdrawal transaction reverts, blocking release of *all* other, legitimate tokens in the same order. This mirrors the OpenQ "malicious ERC20 blocks bounty claim" bug class, applied here to the intent-escrow release path.

### Finding Description
`IntentsBase._withdraw` releases escrow for a `WithdrawalRequest` by looping over `body.tokens` and calling `IERC20.safeTransfer` for each token with no isolation between iterations: [1](#0-0) 

This function is invoked as the terminal step of both:
- a fill (`IntrinsicIntents._fillSameChain` → `_withdraw(body, false, isFullyFilled)`), and
- a cancellation (`IntrinsicIntents._cancelSameChain` → `_withdraw(body, true, true)`), [2](#0-1) [3](#0-2) 

as well as the cross-chain settlement path where `onAccept` decodes a `WithdrawalRequest` for `RedeemEscrow`/`RefundEscrow` and calls the same `_withdraw`. The Tron deployment implements the equivalent logic directly with low-level `.call` + `transfer.selector`, which reverts identically on failure: [4](#0-3) 

Because `order.inputs`/`body.tokens` can contain multiple distinct ERC20 addresses in one order, a user placing an order controls exactly which tokens get escrowed together. An order creator can escrow one legitimate, valuable token (e.g., USDC) alongside a token they fully control (deployed by them, or a real token that later blacklists an arbitrary address) as a second input. Any attempt to release escrow — whether by the solver claiming after a fill, or by the user themselves cancelling — walks the full `body.tokens` array; a revert on the malicious token's `transfer`/`safeTransfer` call reverts the whole function, and since `_filled[commitment]` is set at the top of `_withdraw` only within the same atomic transaction, the revert rolls that back too, so the withdrawal state is never marked complete and can be retried — but every future retry hits the exact same revert deterministically. The escrow becomes permanently unreleasable through the normal fill/cancel code path.

Concretely for the cross-chain fill flow: the solver front-runs nothing — they deliver real output tokens to the beneficiary on the destination chain in `ExtrinsicIntents._fillCrossChain` before the `RedeemEscrow` message is even dispatched. Only after Hyperbridge delivers that message does the source chain attempt `_withdraw` to pay the solver from escrow. If the order's escrowed inputs include a token that reverts for the solver's address (e.g., attacker deploys/uses a token that blacklists whichever address ends up as `msg.sender`/beneficiary, or that reverts unconditionally after a delay), the solver has already paid out real value on the destination chain but can never redeem any of the escrowed inputs — including the otherwise-good token bundled in the same order — because the single loop has no per-token try/catch and one failing `transfer` reverts release of the entire basket.

### Impact Explanation
This is a fund-freezing / theft vector reachable by any unprivileged order creator via a single `placeOrder` transaction, matching the "route unable to deliver messages / permanent freezing of funds" acceptance criteria:
- A solver can be induced to deliver real output value cross-chain and then be permanently denied the escrowed input tokens (theft of solver-provided value / freezing of the order's escrow).
- The order's own creator can similarly freeze their own escrow to prevent legitimate fills from ever finalizing while extracting solver-provided outputs (classic "malicious depositor blocks claim" pattern from the OpenQ report), since same-chain fills first pay the beneficiary directly and only then attempt to release escrow via `_withdraw`, so a revert there strands the input tokens while the solver's outputs have already moved.
- No admin/governance action can free the specific token from that order's `body.tokens` list since the release path has no per-token skip/catch and no path exists to release a subset of tokens for a stuck commitment.

This qualifies as High severity: it is unprivileged, reachable via a single dispatched fill/cancel, and results in permanent freezing of escrowed funds (and potential loss of solver-delivered value on the counter-leg).

### Likelihood Explanation
Likelihood is high for orders containing attacker-chosen or attacker-influenced multi-token baskets: the order creator fully controls `order.inputs` (which tokens are escrowed) at `placeOrder` time, so they can trivially include a token they can make revert on demand (a custom ERC20 with an owner-toggleable pause/blacklist, or a standard blacklist token like USDC/USDT where the attacker gets the solver's or their own withdrawal address blacklisted). No special privileges, front-running, or governance access are required — only a normal `placeOrder` and `fillOrder`/`cancelOrder` sequence that any user can already perform.

### Recommendation
Isolate per-token transfer failures in `_withdraw` (and its Tron/`IntentGatewayV2.sol` `withdraw` equivalent) so that one reverting token cannot block release of the others:
- Wrap each token transfer in a try/catch (or use a low-level `call` and record failure) and, on failure, credit the amount to a per-beneficiary/per-token "pending withdrawal" balance that can be pulled separately (pull-payment pattern), instead of reverting the whole loop.
- Emit an event for skipped/failed tokens so relayers/users are aware and can retry that token individually once resolved.
- Apply the same fix consistently across `IntentsBase._withdraw`, `ExtrinsicIntents`'s cross-chain paths, and the Tron `IntentGatewayV2.withdraw`.

### Proof of Concept
1. Attacker (as order user) calls `placeOrder` with `order.inputs = [ {token: USDC, amount: X}, {token: EvilToken, amount: 1} ]`, where `EvilToken` is an ERC20 the attacker deployed that always reverts on `transfer`/`transferFrom` to addresses other than the attacker (or that the attacker can toggle to revert via an owner-controlled blacklist).
2. A solver calls `fillOrder` (same-chain or cross-chain), delivering the required output tokens directly to the order's beneficiary (`IntrinsicIntents._fillSameChain` / `ExtrinsicIntents._fillCrossChain` pay the beneficiary before touching escrow).
3. Escrow release is attempted via `IntentsBase._withdraw` (same-chain, immediately in the same tx; cross-chain, via the `RedeemEscrow` `onAccept` callback): the loop at [5](#0-4)  reaches `EvilToken` and its `safeTransfer` call reverts.
4. The whole `_withdraw` call (and, for same-chain, the whole `fillOrder` transaction) reverts, so `_filled[commitment]` is never durably set and the USDC escrow — despite being a perfectly good token — can never be paid out to the solver, while the solver has already given away the output tokens in step 2 (same-chain case) or paid the destination-chain output plus dispatch fee (cross-chain case).
5. Repeating step 3 always reverts identically since `EvilToken`'s revert condition is persistent/attacker-controlled, permanently freezing the USDC escrow and denying the solver any recovery through the protocol's own withdrawal path.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
