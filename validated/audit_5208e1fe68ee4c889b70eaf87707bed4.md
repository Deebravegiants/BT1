### Title
Webhook shop-domain header trusted for tenant identity without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC over the raw request body, but the `shop-domain` (and `topic`/`webhook-id`) headers used to identify *which merchant* the webhook belongs to are never included in the signed material. This is the same class of bug as the external report: a field that is *acted on* (the tenant identity) is not *covered by* the integrity check (the HMAC), so the two can be desynchronized by an attacker.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor simply reads the `shop-domain` header, which is not part of the signable string: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which computes the HMAC over `to_signable_string` (the body only) and compares it to the `hmac-sha256` header: [3](#0-2) [4](#0-3) 

Once the HMAC (body-only) checks out, `request.shop` — an attacker-controllable header that was never bound to the HMAC — is passed straight into `WebhookMetadata`, which is the trust boundary the host application uses to determine which merchant/tenant the webhook event applies to: [3](#0-2) [5](#0-4) 

**Binding that should hold, but doesn't:**
`hmac(raw_body, client_secret) valid ⇒ shop-domain header == shop that actually generated raw_body`

In reality: `hmac(raw_body, client_secret) valid` only proves *the raw body* was signed with the app's `client_secret` — it says nothing about which shop the header claims to be from. Because Shopify signs webhook bodies for an app using the single shared `client_secret` for *all* merchants of that app (not a per-shop secret), any legitimate webhook payload captured from *any* installation of the app (including the attacker's own store, if the app is public) carries a valid HMAC that will remain valid no matter what `shop-domain` header is attached to the replayed request.

### Impact Explanation
An unprivileged internet user who has the app installed on their own shop (or who otherwise captures one genuine webhook delivery) can take that valid `raw_body` + `x-shopify-hmac-sha256` pair and POST it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `Registry.process` will accept it as valid (body HMAC matches) and hand the host application a `WebhookMetadata` claiming the event is `shop: <victim-shop>`. If the host application (as intended/documented by this gem, see `docs/usage/webhooks.md`) uses `data.shop` to key per-tenant storage/logic — the standard, encouraged usage pattern — this results in cross-tenant data confusion/injection: an attacker-controlled payload processed under another merchant's identity. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Moderate-to-high. It requires the attacker to obtain at least one genuine `(raw_body, hmac)` pair signed with the app's shared `client_secret` — trivially achievable for any public app by installing it on a shop the attacker controls and capturing the delivered webhook (or any other topic whose body content is attacker-influenceable, e.g. `orders/create` after placing an order in their own store). No access token, `client_secret`, or privileged account is required — only normal, unprivileged use of the app as a merchant.

### Recommendation
Bind the tenant-identifying headers to the integrity check instead of trusting them independently of the HMAC:
- Include `shop-domain` (and ideally `topic`/`webhook-id`) in the signable string used for HMAC validation, or
- Cross-check the `shop-domain` header against an independently-verified source of truth (e.g., the shop associated with the specific stored webhook registration / API version fetched from Shopify) before dispatching to the handler, or
- At minimum, document prominently that `WebhookMetadata#shop` is not cryptographically bound to the payload's HMAC and must not be trusted as the sole tenant key without additional verification by the host app.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. for `orders/create`, with headers:
   - `x-shopify-hmac-sha256: <valid HMAC over body B>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - body `B` (JSON payload, content partially attacker-controlled via order fields).
2. Attacker replays the exact same body `B` and HMAC header to the app's webhook endpoint, but changes:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only (`to_signable_string`) — this still matches because the body was not altered [1](#0-0) .
4. The request is treated as authentic; the handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [6](#0-5) , even though the payload actually originated from, and was signed on behalf of, `attacker-shop.myshopify.com`.
