### Title
Unbounded, unmetered contract-storage removal loop in `DeleteAccount` allows compute-cost-free state-removal DoS - (File: `core/store/src/utils/mod.rs`, `runtime/runtime/src/actions.rs`)

### Summary
`action_delete_account` gates account deletion on `MAX_ACCOUNT_DELETION_STORAGE_USAGE` (10,000 bytes), but that cap explicitly excludes contract storage usage. The subsequent `remove_account` call then iterates and removes *every* `ContractData` trie entry belonging to the account in an unbounded loop, and this removal work is never charged any gas/compute — only gas-key nonce removal is billed. This mirrors the reported bug class of "external/expensive calls executed in an unbounded loop without per-iteration cost accounting," here materializing as unmetered trie work reachable from an ordinary, unprivileged `DeleteAccount` transaction.

### Finding Description
`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) computes the storage usage subject to the deletion-size cap by first *subtracting out* the contract storage: [1](#0-0) 

This means `MAX_ACCOUNT_DELETION_STORAGE_USAGE` — documented as "larger accounts (after subtracting contract storage) cannot be deleted" — only bounds the account record + access keys, not the account's contract data (key/value pairs written via `storage_write` during contract execution and paid for via ordinary storage staking). [2](#0-1) 

The account is then deleted via `remove_account` (`core/store/src/utils/mod.rs:504-575`), which, after removing access keys/gas-key nonces (which *are* charged compute via `storage_removes_compute`), performs a second unbounded scan and removal of all `ContractData` entries with **no compute/gas accounting at all**: [3](#0-2) 

Back in `action_delete_account`, the only compute usage added to the result is derived from `remove_result.gas_key_nonce_count` — the `RemoveAccountResult` struct doesn't even track how many contract-data keys were removed, so nothing charges for that work: [4](#0-3) [5](#0-4) 

Any unprivileged account holder can: (1) deploy a contract, (2) call it repeatedly to write a large amount of persistent state via `storage_write` (paying only the linear storage-stake deposit, which is refundable), and (3) submit a single `DeleteAccount` action signed with a full-access key. The `DeleteAccount` action itself carries only a fixed `exec_fee`/`send_fee` (`ActionCosts::delete_account`) that does not scale with the number of state entries. During `apply`, this single receipt then forces the node to iterate and remove an arbitrarily large number of trie entries within one receipt's execution, without that iteration counting against `compute_limit`/`gas_limit` the way normal state-touching host calls do.

This differs from the properly-metered receipt-processing loops elsewhere in the runtime, e.g. `process_delayed_receipts`/`process_incoming_receipts`, which check `compute_limit` and `check_proof_size_limit_exceed()` before each unit of work and defer to a delayed queue if exceeded: [6](#0-5) 
`remove_account`'s contract-data removal loop has no equivalent gas/proof-size check — it runs to completion inside a single action regardless of size.

### Impact Explanation
This is unbounded, effectively free (gas-underpriced) trie work triggerable by any unprivileged account. A user can grow an account's contract storage to an arbitrarily large size (bounded only by their willingness to lock storage-stake tokens, which are later refunded on deletion) and then trigger a single cheap `DeleteAccount` transaction that forces every validator/node applying that chunk to enumerate and remove all of that state. Because the cost is not gas-metered, this both (a) lets an attacker cause disproportionate, underpriced node CPU/IO work relative to what they paid (free/underpriced execution), and (b) risks chunk-apply time blowing past expected per-chunk budgets, which can contribute to degraded liveness/perceived chunk-processing stalls if state is large enough, since the per-receipt storage-proof/gas limits that normally bound receipt cost do not constrain this deletion path.

### Likelihood Explanation
Reachable directly from a standard transaction (`DeleteAccount` action) signed by the account's own full-access key — no validator, P2P, or privileged role is required. The only cost to the attacker is the ordinary storage-stake deposit for writing state (refunded on deletion) plus the fixed, size-independent `DeleteAccount` action fee. Building up a large amount of contract storage is a normal, permitted usage pattern (e.g., large NFT/token contracts), so the attack requires no exotic setup beyond volume.

### Recommendation
- Include contract-data (and total state) size in the `MAX_ACCOUNT_DELETION_STORAGE_USAGE` cap computation instead of excluding it, or
- Meter and charge gas/compute for every `ContractData` key removed in `remove_account` (as is already done for gas-key nonces via `storage_removes_compute`), and enforce the existing `compute_limit`/proof-size checks during that removal loop so oversized deletions are rejected or partially processed/deferred rather than executed unbounded in a single receipt.
- Add a regression test analogous to `test_delete_account_removes_gas_keys` but for large `ContractData` sets, asserting that `action_delete_account` either charges proportional compute or is rejected when contract storage exceeds a safe bound.

### Proof of Concept
1. Create account `attacker.near` and deploy a contract that supports arbitrary `storage_write` calls (e.g., a generic KV contract).
2. Submit many `FunctionCall` transactions/receipts to write N large key/value entries into `attacker.near`'s contract storage, paying the standard storage-stake deposit for each (refundable). N can be made very large (e.g., hundreds of thousands of entries) since there is no cap on total contract storage size for an account other than available balance for storage stake.
3. Submit a single `DeleteAccount` action, signed by `attacker.near`'s full-access key, with `beneficiary_id` set to itself or another account:
   - `check` in `action_delete_account` (`runtime/runtime/src/actions.rs:326-353`) computes `account_storage_usage` after subtracting contract storage, so it passes the `MAX_ACCOUNT_DELETION_STORAGE_USAGE` (10,000-byte) check regardless of how large the contract storage is.
   - `remove_account` (`core/store/src/utils/mod.rs:555-574`) then collects and removes all N `ContractData` keys in a single call, with the associated `ActionResult.compute_usage` unaffected (only gas-key nonce removal is charged, per `runtime/runtime/src/actions.rs:376-386`).
4. Observe that the single `DeleteAccount` receipt/action performs O(N) trie removal work while being billed only the fixed `ActionCosts::delete_account` fee, independent of N — demonstrating the free/unbounded compute path.

(Exact reproduction requires running the runtime test harness, e.g. extending `runtime/runtime/src/access_keys.rs`'s `test_delete_account_removes_gas_keys`-style tests with a large `ContractData` population and measuring `action_result.compute_usage` vs. the number of removed entries, which was not independently executed here — this PoC outline is derived from static code-path analysis of the cited functions.)
