The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are transport headers only — the HMAC is computed exclusively over `@raw_body` in `ShopifyAPI::Webhooks::Request#to_signable_string`, and `HmacValidator.validate` never incorporates any header value.

### Title
Webhook shop/topic identity spoofing via unauthenticated headers not covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values — which are the fields the host application uses to determine *which tenant* and *which event* the payload belongs to — are read from unauthenticated HTTP headers and are never part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the signature purely against `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` then trusts `request.shop` and `request.topic` — taken directly from headers — to route to a handler and to build the `WebhookMetadata` the host app uses as the tenant identity for the event: [4](#0-3) 

This breaks the intended identity binding: `HMAC(body) == received_signature` is verified, but the equality that actually matters for tenant isolation, `shop_header == shop_that_produced(body, hmac)`, is never checked. Any `(raw_body, hmac)` pair that is valid for one shop (a value the app itself will legitimately observe once, e.g. from a webhook fired by the attacker's own installed test store) remains a valid `(raw_body, hmac)` pair no matter what `shop-domain`/`topic`/`webhook-id` headers accompany it, since none of those headers are mixed into the signed string.

### Impact Explanation
This is a cross-tenant identity confusion: the gem passes the header-derived `shop` and `topic` through the `WebhookMetadata` struct as trustworthy, HMAC-verified data (per its own documentation, "process...will verify the request did indeed come from Shopify"), when in fact only the body content is verified. Host applications that key data lookups, session retrieval, or destructive actions (e.g. `app/uninstalled`, `shop/redact`, `customers/redact`) off `data.shop` without independently re-validating the shop are exposed to cross-tenant event injection using a replayed, still-valid signature.

### Likelihood Explanation
The attacker needs one legitimately signed `(body, hmac)` pair, which is trivial to obtain — every real webhook Shopify sends to any shop running the app (including an attacker's own free/dev store) qualifies. The attacker then only needs to change the `shop-domain` (and optionally `topic`/`webhook-id`) header on a replayed POST to the app's public webhook endpoint. No secret, token, or privileged access is required.

### Recommendation
Bind the tenant-identifying headers into the signed material, or at minimum require the host application to independently verify that the shop referenced in `data.shop` is a shop with an active installation before trusting the payload for that shop. The `to_signable_string` implementation for `Webhooks::Request` should incorporate `shop`, `topic`, and `webhook_id` (or the library should document explicitly, at the point they are exposed on `WebhookMetadata`, that they are unauthenticated and must not be used for tenant routing without separate verification).

### Proof of Concept
1. App has webhooks registered and shop A legitimately triggers an event (e.g. `orders/create`); the app's webhook endpoint receives `raw_body`, headers including `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker, who controls shop A (a store they own, e.g., a free dev store with the app installed) captures this exact `(raw_body, H)` pair from network logs (it is not secret — it traverses their own browser/webhook receiver).
3. Attacker replays the identical `raw_body` and `x-shopify-hmac-sha256: H` to the same endpoint, but sets `x-shopify-shop-domain: shop-victim.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(raw_body)` and it still matches `H`, so `Registry.process` proceeds: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "shop-victim.myshopify.com"` even though the payload actually originated from shop A, and any code that trusts this shop value for tenant-scoped effects executes cross-tenant.
