Audit Report

## Title
Cache-key collision in gateway HTTP action response cache omits WorkflowID, enabling cross-workflow response confusion - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

## Summary
The `responseCache` used by the gateway's HTTP-action handler keys cached responses purely by `OutboundHTTPRequest.Hash()`, which the test suite explicitly confirms varies by `WorkflowOwner` but is identical regardless of `WorkflowID`. This contradicts the component's own README, which states cache entries are "scoped by workflow ID to prevent cross-workflow data leakage," and allows a cached HTTP response from one workflow to be served to a different workflow under the same owner.

## Finding Description
The cache is a `map[string]*cachedResponse` keyed by `req.Hash()` in `isExpiredOrNotCached`, `Fetch`, and `Set` <cite repo="AYontt/chainlink--018" path="core/services/gateway/handlers/capabilities/v2/response_cache.go" start="46="/> [1](#0-0) . The struct's own comment says the hash covers "method, URL, headers, body, workflowOwner" — omitting `workflowID` [2](#0-1) . The test suite proves this directly: `TestRequestHash` asserts two requests differing only in `WorkflowID` produce the *same* hash, while requests differing in `WorkflowOwner` produce *different* hashes [3](#0-2) . Meanwhile the README documents "Cache Key: Generated from workflow ID and request hash" and "Workflow Isolation: Cache entries are scoped by workflow ID" [4](#0-3) , which is inconsistent with the actual implementation.

The call site in `gatewayHandler.makeOutgoingRequest` passes the full `OutboundHTTPRequest` (which does carry `WorkflowID` as a field) into `h.responseCache.Fetch`/`Set`, but since `Hash()` itself doesn't incorporate `WorkflowID`, the cache lookup/storage is effectively scoped only by owner+method+URL+headers+body [5](#0-4) . Note: `Hash()` itself is implemented in the vendored `chainlink-common` package (`gateway_common.OutboundHTTPRequest`), not in this repo, so its exact implementation could not be directly inspected here — but the test file in this repo (`response_cache_test.go`) exercises and asserts this exact behavior against the real type, which is strong, reproducible evidence of the described behavior.

## Impact Explanation
This is a legitimate cross-workflow response-confusion bug within a single workflow owner's tenancy: two distinct workflows (e.g., different `WorkflowID`s) belonging to the same owner, hitting the same URL/method/headers/body with `CacheSettings.Store`/`MaxAgeMs` set, will read/write the identical cache slot. This can cause one workflow to receive another's HTTP action response, silently corrupting the executing workflow's inputs/decisions — a loss-of-integrity condition that matches the "cross-user response corruption" impact class referenced in the rules. It is not, however, a cross-*owner* leak: `WorkflowOwner` is part of the hash, so isolation between different owners (the stronger multi-tenant boundary) is preserved.

## Likelihood Explanation
Triggerable by an unprivileged capability/workflow author: any owner who runs two workflows that both issue HTTP actions to the same endpoint with matching method/headers/body and enable caching will hit this collision through completely normal usage — no adversarial action, elevated role, or misconfiguration is required. This is a reachable, unprivileged-triggered condition backed directly by the repo's own test file.

## Recommendation
Include `WorkflowID` in the `Hash()` computation (or otherwise incorporate it into the cache key used by `isExpiredOrNotCached`/`Fetch`/`Set`) so cache entries are correctly scoped per-workflow as documented in the README. Update `TestRequestHash`'s "having different workflowID results in same Hash" test to assert the opposite (different hash), and audit other cache/dedup key derivations in the gateway/capabilities code for the same documented-vs-actual mismatch.

## Proof of Concept
1. Two workflows (`workflow-123`, `workflow-456`) under the same `WorkflowOwner` each send an `OutboundHTTPRequest` with identical `Method`, `URL`, headers, and body, both with `CacheSettings.Store = true`.
2. Workflow A's response is stored via `rc.Set`/`rc.Fetch` under `req.Hash()`.
3. Workflow B's subsequent request within TTL computes the identical hash (per `TestRequestHash` "having different workflowID results in same Hash" at `core/services/gateway/handlers/capabilities/v2/response_cache_test.go:139-149`) and is served Workflow A's cached response via `isExpiredOrNotCached`/`Fetch` at `core/services/gateway/handlers/capabilities/v2/response_cache.go:46-84`, demonstrating cross-workflow response confusion.

// in-flight until the result is stored, preventing duplicate fetches.
func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
