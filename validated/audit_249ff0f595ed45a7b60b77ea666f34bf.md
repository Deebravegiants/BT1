### Title
`rootHashHinkal` unconstrained by `MainEVMCircuitMin` allows proof-valid `transact` calls with attacker-chosen `externalActionMetadata` in the Emporium-Min path - (File: `contracts/CircomDataBuilder.sol`)

### Summary
`formInputEmporiumMin` only feeds `emporiumMessage`, `timeStamp`, and `calldataHash` into the Groth16 public-input vector for the `VerifierEVMMin0v4`/`MainEVMCircuitMin` path, matching `inputAmount == 3`. `circomData.rootHashHinkal` is never placed in that vector and `MainEVMCircuitMin.circom` has no `rootHashHinkal` signal at all, so the circuit places zero constraints on it, while `Hinkal.transact` still performs a root-existence check on that same unconstrained value.

### Finding Description
Broken equality: **root-gated authorization** (`rootHashExists(circomData.rootHashHinkal, ...)` in `contracts/Hinkal.sol:57-64`) **≠ circuit-constrained value** (the Min circuit never receives or checks `rootHashHinkal`).

Trace:
- `contracts/CircomDataBuilder.sol:150-161` (`formInputEmporiumMin`) builds `input = [emporiumMessage, timeStamp, calldataHash]` only, selected whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0` (`contracts/CircomDataBuilder.sol:139-148`). [1](#0-0) 
- `VerifierEVMMin0v4.inputAmount = 3` and it just forwards those 3 signals; it never sees `rootHashHinkal`. [2](#0-1) 
- `MainEVMCircuitMin` only declares `outTimeStamp`, `calldataHash` as public inputs and `messageSeed` as private, outputting `message <== Poseidon(1)([messageSeed])`. It has no `rootHashHinkal`, no `nullifyingPrivateKey`, no nullifier/commitment/root logic whatsoever — unlike `MainEVMCircuit` which does constrain `rootHashHinkal` via `ForceEqualIfEnabled` against the Merkle root computed from a real commitment path. [3](#0-2) [4](#0-3) 
- Meanwhile `Hinkal.transact` independently checks `rootHashExists(circomData.rootHashHinkal, circomData.rootHashHinkalIndex)`, using the raw calldata value that was never bound by the proof for this path. [5](#0-4) 
- `dimensionsCheck` (called from `performHinkalChecks`) forces `erc20TokenAddresses`, `amountChanges`, `inputNullifiers`, `outCommitments` to be empty when `dimensions.tokenNumber == 0`, so no nullifier is spent and no UTXO ownership is proven in this transaction at all. [6](#0-5) 
- `_externalTransact` then invokes `IExternalActionV2(...).runAction(circomData, deltaAmountChanges)` where `deltaAmountChanges` is an empty array (tokenNumber=0), passing through to `EmporiumUpgradeable.runAction`, which decodes `circomData.externalActionData.externalActionMetadata` into an arbitrary `EmporiumStack` of `ops` and executes them. [7](#0-6) [8](#0-7) 
- Critically, `verifyWallet` only marks `emporiumMessage` used and enforces an ECDSA check **only if `stack.signerAddress != address(0)`**; if the attacker sets `stack.signerAddress == address(0)`, `verifyWallet` returns immediately with no signature check at all. [9](#0-8) 

Attacker call: pick any nonzero root already in `roots[]` (they don't need to know any nullifying key for it — any historical root suffices), generate a trivial `MainEVMCircuitMin` proof for a self-chosen `messageSeed` (giving `emporiumMessage = Poseidon(messageSeed)`), set `dimensions.tokenNumber=0`/empty arrays, set `externalActionData` to point at the registered `Emporium` action with `externalActionMetadata` encoding an `EmporiumStack{signerAddress: address(0), ops: [...]}` containing arbitrary `endpoint.call{value}(callData)` entries. `verifyProof` passes (circuit is fully satisfied since it only checks a hash preimage), `rootHashExists` passes (root is real, just unrelated to attacker), `onlyAllowedRecipient` passes because `msg.sender` is `Hinkal` calling into the registered `Emporium`, and `runAction` executes attacker-chosen calls with no signature, no nullifier spend, no fund-source binding for that stateless branch.

Existing guards fail because: `performHinkalChecks`/`dimensionsCheck` only constrain array shapes, not values; `verifyProof` only proves knowledge of a Poseidon preimage, not spending authority; `rootHashExists` checks membership of a value the circuit never binds to anything attacker-specific; and `verifyWallet`'s stateless branch (`signerAddress == 0`) has zero authorization check.

### Impact Explanation
Any funds sitting in the `Emporium` contract's own balance (protocol/relay fees collected via `payRelayFees`/`sendToRelay`, or residual balances from prior partial operations) can be moved to attacker-chosen endpoints via arbitrary `op.endpoint.call{value: op.value}(op.callData)`, with the only gate being replay-protection on `emporiumMessage` (trivially bypassed by picking a new `messageSeed` each time) and `balanceChange >= 0` checks in `handleOut`/`Hinkal.transact`'s slippage check — which don't prevent draining Emporium-held funds outward to arbitrary contracts before any `handleOut` transfer runs. This is at minimum theft of protocol/relay fees (High) and, depending on whatever balances the Emporium accumulates from users mid-flow, potentially theft of in-flight user funds (Critical) — since the entire authorization for the stateless branch is absent and repeatable per fresh `messageSeed`.

### Likelihood Explanation
Preconditions are trivially attacker-controllable: any EOA can deposit into the tree to obtain a valid root, or reuse any existing root in `roots[]` (root doesn't need to correspond to attacker's own deposit at all since it's never checked by the circuit). Generating a `MainEVMCircuitMin` proof requires only knowledge of a self-chosen `messageSeed` — no special key material. The only remaining requirement is that the `Emporium` contract holds exploitable balance and is registered as the `externalActionId`'s address, both of which are protocol-level facts independent of the attacker. This is fully repeatable per transaction (new `messageSeed`/`emporiumMessage` each time to avoid `UsedMessage` revert).

### Recommendation
Bind `rootHashHinkal` (or otherwise cryptographically bind ownership/authorization) into the Min-path circuit's public inputs, or require `stack.signerAddress != address(0)` (mandatory signature check) whenever `dimensions.tokenNumber == 0` in the Emporium action, so that a stateless, root-unconstrained proof can never authorize arbitrary external calls that move Emporium-held balance. At minimum, remove or gate the `stack.signerAddress == address(0)` bypass in `verifyWallet` so it cannot be reached via the Min proof path.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `VerifierEVMMin0v4` (wired to a real `mainEVMCircuitMin0v4` verifier), and `EmporiumUpgradeable`, registering `HINKAL_EMPORIUM_ACTION_ID -> Emporium`.
2. Fund the `Emporium` contract with ETH (simulating accumulated protocol/relay fees).
3. Perform one legitimate deposit from a benign user to populate `roots[]` with a real root the attacker does not control the preimage of.
4. As attacker (no private key/UTXO knowledge), pick `messageSeed`, compute `emporiumMessage = Poseidon(messageSeed)`, generate a valid Groth16 proof for `MainEVMCircuitMin` locally with `snarkjs`.
5. Build `CircomData` with `dimensions.tokenNumber=0`, empty token/nullifier/outCommitment/amountChanges arrays, `rootHashHinkal` = the benign root from step 3, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionMetadata` = ABI-encoded `EmporiumStack{signerAddress: address(0), ops: [{endpoint: attackerContract, invokeWallet: false, value: X, callData: ""}]}`.
6. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from attacker EOA.
7. Assert: `transact` succeeds (`verifyProof` and `rootHashExists` both pass) and `attackerContract` balance increases by `X`, taken from `Emporium`'s pre-funded balance — demonstrating value acted on (root-gated authorization) was never constrained by the selected circuit.
