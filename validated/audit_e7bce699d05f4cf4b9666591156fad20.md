### Title
Webhook shop identity spoofing via unauthenticated header trusted as verified tenant — cross-tenant data injection ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates the incoming webhook only via an HMAC computed over the raw request body, then unconditionally trusts the `shop` (and `topic`/`webhook_id`) values taken from HTTP headers — which are never covered by that HMAC — to build the `WebhookMetadata` handed to the app's registered handler.

### Finding Description
`Registry.process` performs the authenticity check with `Utils::HmacValidator.validate(request)` and then immediately constructs the metadata that identifies which tenant the payload belongs to using `request.shop`, a value read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [1](#0-0) 

The HMAC that gates this call, however, is only computed over `@raw_body`: [2](#0-1) [3](#0-2) 

And `HmacValidator.validate` verifies exactly `verifiable_query.to_signable_string` against the received HMAC — nothing about the headers is part of that signable string for `Request`: [4](#0-3) 

The identity binding that should hold is:
`shop-in-signed-content == shop-used-to-attribute-the-webhook-to-a-tenant`

but the actual code enforces only `hmac(body) == valid`, and separately trusts `header["shopify-shop-domain"] == shop-used-to-attribute-the-webhook`. These are two independent, unlinked checks. Any bytes that pass the body-HMAC check (i.e., were legitimately signed by Shopify for *some* installation of the app, including the attacker's own store) can be replayed to the app's public webhook endpoint with an arbitrary, attacker-chosen `shop` header, and the library will report that replayed metadata to the handler as if it belonged to the spoofed shop, `topic`, and `webhook_id`.

### Impact Explanation
An attacker who installs the target app on a shop they control (a normal, unprivileged action any internet user can perform for a public app) will receive legitimately-signed webhook deliveries for their own store — a genuine `(body, hmac)` pair signed with the app's `client_secret`. Because `shop`, `topic`, and `webhook_id` are carried only in headers outside the HMAC's scope, the attacker can replay that exact body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop (and/or the `shopify-topic` header for a different topic than what was actually signed). `Utils::HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will pass the forged `shop`/`topic` straight through to the app's registered handler as trusted `WebhookMetadata`. If the host app persists or acts on this data keyed by `shop` (the intended and documented use of `WebhookMetadata#shop`), this constitutes cross-tenant data injection/corruption — writing or triggering side effects attributed to a shop the attacker does not control. This matches the Critical "cross-tenant access" impact category, since the tenant boundary (`shop`) is not actually bound to the authenticated bytes.

### Likelihood Explanation
Likelihood is meaningful but not trivial: the attacker needs at least one legitimately signed webhook body of their own (installing the app on their own store is sufficient and free for any public app), and needs the receiving application to trust `WebhookMetadata#shop`/`#topic` for authorization or storage decisions, which is exactly how the library documents and tests this API to be used (`test/webhooks/registry_test.rb`). No `client_secret`, access token, or privileged access is required — only normal use of a public app installation flow plus direct HTTP requests to the app's public webhook endpoint.

### Recommendation
Bind the tenant/topic identity to the signed payload rather than trusting header values independently of the HMAC:
- Include `shop`, `topic`, and `webhook_id` in the signable content validated by `Utils::HmacValidator`, or otherwise cryptographically bind them to the body (e.g., derive/confirm `shop` from a signed claim rather than a bare header), so a body signed for one tenant/topic cannot be replayed under another tenant/topic's identity.
- At minimum, document prominently that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are unauthenticated header values and must not be trusted by host applications without additional verification (e.g., cross-checking against a shop already known to have installed the app with a matching webhook subscription/ID on Shopify's side).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g., `orders/create`), capturing the raw POST body `B` and the legitimate `X-Shopify-Hmac-Sha256` header `H` computed by Shopify over `B` with the app's `client_secret`.
2. Attacker sends a new POST request to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid because `HmacValidator.validate` only checks body bytes — [5](#0-4) [6](#0-5) )
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (spoofed)
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which returns `true` (body signature matches), then builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and invokes the app's handler — [1](#0-0) .
4. The host application's handler processes/stores data as if `victim-shop.myshopify.com` sent this webhook, even though the payload actually originated from and was signed for `attacker-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          received_signature = verifiable_query.hmac
