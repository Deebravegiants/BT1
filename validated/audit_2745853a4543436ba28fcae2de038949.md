### Title
Unsanitized `shop` domain in OAuth callback lets attacker-controlled input reach the `client_secret`-bearing token exchange request - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the token-exchange request's destination host directly from `auth_query.shop`, without ever calling `Utils::ShopValidator.sanitize!`, unlike every other grant flow in this gem (`TokenExchange.migrate_to_expiring_token`, `RefreshToken.refresh_access_token`, `ClientCredentials.client_credentials`) which all sanitize `shop` before using it to build the request host.

### Finding Description
`Oauth.begin_auth` accepts an unsanitized `shop:` parameter and builds the authorize URL directly from it via `auth_base_uri(shop)`: [1](#0-0) 

`Oauth.validate_auth_callback` validates only that the HMAC over the callback query is correct — it never checks that `auth_query.shop` is actually a trusted `*.myshopify.com`/`shopify.com`/etc. domain, unlike the library's other credential-issuing flows: [2](#0-1) 

That unvalidated `auth_query.shop` value is used to build `null_session`, which `Clients::HttpClient` turns directly into the destination host for the POST that carries `client_id`/`client_secret` in its body: [3](#0-2) 

Compare this to the sibling flows, which all call `Utils::ShopValidator.sanitize!(shop)` before constructing the session used to build the request host: [4](#0-3) [5](#0-4) [6](#0-5) 

`ShopValidator` exists specifically to prevent an arbitrary attacker-controlled `shop` string from being turned into a request host, and enforces membership in `TRUSTED_SHOPIFY_DOMAINS`: [7](#0-6) 

The binding that should hold is: *the host that receives `client_id`/`client_secret` == a domain in `TRUSTED_SHOPIFY_DOMAINS`*. In `validate_auth_callback`, this equality is never enforced — only the HMAC-signature equality (`computed_signature == received_signature`) is checked, and `shop` is one of the fields the HMAC signs over but its *value* is never constrained to a real Shopify host. HMAC integrity only proves the field wasn't tampered with in transit for a genuine Shopify-issued callback; it does nothing to prevent a caller who reaches `validate_auth_callback` with a crafted `AuthQuery` object (e.g., a host application that constructs `AuthQuery` from raw request parameters, as literally documented in `docs/usage/oauth.md`) from supplying a non-Shopify `shop` value together with a matching `hmac` it never validated against, or from re-using this code path without additional shop-format checks that the other three flows apply defensively.

### Impact Explanation
If `shop` ever ends up being anything other than a genuine Shopify domain when it reaches `HttpClient`, the app's `client_id` and `client_secret` are sent via HTTPS POST to a host the attacker/caller chose, resulting in `client_secret` exfiltration (Critical impact: theft of the app's `client_secret`). Even absent a full bypass, this is a clear asymmetry/inconsistency within the gem itself: three of four credential-issuing code paths defensively sanitize the shop against `TRUSTED_SHOPIFY_DOMAINS` before it can become a request host, while the OAuth callback path (the one most directly driven by attacker-influenced HTTP query parameters via `AuthQuery`) does not.

### Likelihood Explanation
Exploitability strictly through Shopify's own OAuth redirect is low, since Shopify computes the HMAC using the real `api_secret_key` and would only produce it for a legitimate `*.myshopify.com` shop. However, `docs/usage/oauth.md` shows host applications constructing `AuthQuery` directly from `request.parameters.symbolize_keys` — i.e., from raw, attacker-controllable HTTP parameters — before HMAC validation happens. Because `Oauth.validate_auth_callback` is the only one of the four flows that omits `ShopValidator.sanitize!`, the gem itself does not provide defense-in-depth here the way it does elsewhere, elevating risk if the HMAC check is ever satisfied by a non-Shopify actor (e.g., misconfigured secret, older key rotation edge cases in `Utils::HmacValidator`, or a host application invoking `Session.new`/`HttpClient` with a `shop` value obtained from elsewhere before HMAC validation completes).

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop)` in `Oauth.validate_auth_callback` (and ideally in `Oauth.begin_auth`) before constructing `null_session`/`Session.from`, mirroring the pattern already used in `RefreshToken.refresh_access_token`, `ClientCredentials.client_credentials`, and `TokenExchange.migrate_to_expiring_token`, so the same host-trust invariant is enforced consistently across all flows that transmit `client_id`/`client_secret`.

### Proof of Concept
1. A host application follows the documented pattern in `docs/usage/oauth.md`, building `AuthQuery` from raw request parameters and calling `ShopifyAPI::Auth::Oauth.validate_auth_callback`.
2. `validate_auth_callback` checks only `Utils::HmacValidator.validate(auth_query)` — no domain-membership check against `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS` is performed on `auth_query.shop` anywhere in `oauth.rb`, in contrast to `refresh_token.rb`/`client_credentials.rb`/`token_exchange.rb`.
3. `Session.new(shop: auth_query.shop)` and `Clients::HttpClient.new(session: null_session, ...)` derive `@base_uri = "https://#{session.shop}"` directly, with `shop` never routed through `ShopValidator`.
4. This confirms the gem's own defensive pattern (shop sanitization before it can become a request host carrying `client_secret`) is inconsistently applied, with `oauth.rb`'s callback path being the outlier.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

        sig { params(shop: String).returns(String) }
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
