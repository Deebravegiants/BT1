## Title
Webhook HMAC does not bind `shop-domain` or `topic`, enabling cross-tenant webhook forgery / replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches the event using the `shop` and `topic` values taken directly from HTTP headers that are **not** covered by that HMAC. Any actor who has obtained one genuine `(body, hmac)` pair — trivially possible by installing the app on their own store and receiving a real webhook — can replay that exact body/HMAC pair while freely substituting the `x-shopify-shop-domain` and `x-shopify-topic` headers, and the signature check still passes. This breaks the identity binding `shop authenticated == shop the handler acts on`.

### Finding Description
The `hmac` verification path is:
- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it (constant-time) to the value from the `hmac-sha256` header. [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body — no headers are included in what is signed: [2](#0-1) 

`shop` and `topic` are read straight from headers, independent of the HMAC: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then uses the unauthenticated `request.topic` to select a handler and the unauthenticated `request.shop` as the tenant identity passed into the handler: [4](#0-3) 

Because the signature only certifies "this body was HMAC'd with `api_secret_key`" and says nothing about which shop or which event topic it belongs to, a `(body, hmac)` pair legitimately received for shop A / topic X can be replayed verbatim to the same endpoint with headers rewritten to claim shop B / topic Y, and `Utils::HmacValidator.validate` will still return `true`. This is a broken binding: the value the HMAC actually authenticates (bytes of the body) is not the value the application trusts as the tenant/action identity (`shop`, `topic` headers).

### Impact Explanation
This directly enables cross-tenant impact: an unprivileged actor who merely installs the app on their own store (a fully unprivileged action requiring no credentials, no `api_secret_key`, and no access to any victim data) can obtain a genuine signed webhook body (many webhook bodies are minimal/predictable, e.g. `{}` for topics like `app/uninstalled`). They can then forge requests to the app's public webhook endpoint attributing that same signed body to an arbitrary victim `shop-domain` and to an arbitrary registered `topic`. Depending on what the host application's webhook handlers do with `WebhookMetadata#shop` (e.g., revoke sessions, delete data, mark shop uninstalled/redacted, trigger merchant-scoped side effects), this allows a cross-tenant write/action against a shop the attacker does not control — satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for the precondition (installing the app on one's own store to obtain a valid signed body is trivial and requires no special access), and the exploit itself is a simple HTTP replay with two header values changed — no cryptographic material or `api_secret_key` is needed, since the signature never covered those fields in the first place.

### Recommendation
Include `shop`, `topic`, and `webhook_id`/API version alongside the raw body in the value that is HMAC-verified (or otherwise cryptographically bind them, e.g. by using Shopify's shop-scoped webhook verification metadata), so that a signature cannot be replayed across shops or topics. At minimum, `Registry.process` should re-derive/require an authenticated shop and topic instead of trusting caller-supplied headers unconditionally.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`; Shopify sends a genuine webhook, e.g. topic `app/uninstalled` with body `{}` and header `x-shopify-hmac-sha256: <valid_hmac_of_{}>`.
2. Attacker replays that exact request to the app's webhook endpoint, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: shop/redact` (or any topic registered by the app whose legitimate body happens to be `{}`/matching bytes)
3. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13`) recomputes the HMAC over the (unchanged) body and it matches, so validation passes.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) dispatches the handler for `shop/redact` with `shop: "victim-shop.myshopify.com"`, causing the host app's handler to act on the victim shop's tenant data despite the attacker never having any credential or relationship with that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
