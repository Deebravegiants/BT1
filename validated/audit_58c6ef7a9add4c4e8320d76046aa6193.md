### Title
Stale approvals left on the shared `CallDispatcher` persist across unrelated orders, enabling repeat token theft when it is refunded — (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2` routes both predispatch and postdispatch/output calldata through a single, protocol-wide `CallDispatcher` contract (`_params.dispatcher`), the same instance for every order placed or filled through the gateway. Order calldata is attacker-controlled `Call[]` data executed with `ICallDispatcher.dispatch()`, which can include arbitrary `approve()` calls from the dispatcher to any spender. Nothing ever revokes an approval granted by a prior order's calldata. Because the dispatcher is a shared, long-lived contract that legitimately and repeatedly receives fresh token balances from unrelated orders (predispatch assets transferred in via `IERC20(token).safeTransferFrom(msg.sender, dispatcher, amount)`, or postdispatch beneficiary funds sent by solvers), a stale approval left by one order's calldata lets its beneficiary drain a *different, later* order's funds the moment they land on the dispatcher — mirroring the Visor `transferERC721` bug where a lingering approval let the same delegatee repeatedly steal an NFT each time the vault was refilled.

### Finding Description
In `evm/src/apps/intentsv2/IntentsBase.sol`, `_execute()` (lines 498–545) calls `ICallDispatcher(dispatcher).dispatch(order.output.call)` with `dispatcher = _params.dispatcher` — a single fixed address for the whole gateway [1](#0-0) . The same shared dispatcher is used for `placeOrder`'s predispatch execution in `evm/src/apps/IntentGatewayV2.sol` (`ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`), and for the postdispatch sweep test path shown in `evm/tests/foundry/IntentGatewayV2Test.sol:1358-1363`, where an order's calldata explicitly does `IERC20.approve(uniswapRouter, type(uint256).max)` from the dispatcher [2](#0-1) .

`CallDispatcher.dispatch()` itself is a stateless pass-through that executes whatever calls it's given, with no bookkeeping of approvals it grants and no revocation step afterward [3](#0-2) . After each order's calldata runs, the gateway only sweeps *token balances* left on the dispatcher back to itself (`_execute`'s sweep loop, lines 507–533) — it never touches `allowance(dispatcher, spender)`. An approval granted by order A's calldata (e.g., `approve(attackerRouter, type(uint256).max)`) therefore survives indefinitely on the dispatcher contract.

Because the dispatcher is reused by every subsequent order — predispatch assets are transferred directly to it (`IERC20(token).safeTransferFrom(msg.sender, dispatcher, amount)` in `placeOrder`, and again for postdispatch beneficiary funds sent by solvers when `output.call.length > 0`) — any later order whose input/output token matches the previously-approved token, and which lands funds on the dispatcher before the gateway's synchronous sweep executes, is vulnerable to the earlier approval being exercised by the original spender to drain those funds before they can be swept or escrowed.

### Impact Explanation
This is a direct theft-of-funds vector against the shared intent-settlement path: an attacker can place one order with predispatch/output calldata that grants an unlimited approval from the singleton `CallDispatcher` to an address they control, then front-run or race the next legitimate order's fund transfer to the same dispatcher, calling `transferFrom` to steal the newly arrived tokens before the gateway sweeps them back into escrow/dust accounting. Given `_execute` and the predispatch flow only sweep balances and never `approve(spender, 0)`, the exposure compounds with every additional approval left behind by any order over the gateway's lifetime.

### Likelihood Explanation
Likelihood is high: placing an order with malicious predispatch/output calldata is fully permissionless (any user can call `placeOrder`/have their order filled with attacker-chosen calldata within the documented `Call[]` mechanism), and the dispatcher's role as a shared, reusable relay for every order's token flows is the intended design (per `docs/content/developers/evm/intent-gateway/overview.mdx`), not a rare edge case. The only requirement is timing the theft between a subsequent order's fund transfer to the dispatcher and the gateway's sweep-back call within the same or a following transaction.

### Recommendation
Treat the `CallDispatcher` as a strictly single-use, non-custodial relay: after every `dispatch()` invocation from `_execute()` and from `placeOrder`'s predispatch/transfer-back flow, explicitly revoke (`approve(spender, 0)`) any allowances the just-executed calldata may have granted for the tokens involved in that order, or redesign the dispatcher to be deployed per-order (e.g., via CREATE2/minimal proxy, then self-destructed or made unreachable) rather than shared as a single persistent contract across the gateway's entire lifetime.

### Proof of Concept
1. Attacker calls `placeOrder` (or fills an order) with `output.call` (or `predispatch.call`) encoding `Call({to: TOKEN, value: 0, data: approve(ATTACKER, type(uint256).max)})`, executed via `_execute`/`ICallDispatcher.dispatch` against the shared `_params.dispatcher`.
2. The order completes normally; the gateway sweeps only the *current* token balance from the dispatcher back to itself, leaving the `TOKEN` allowance from `dispatcher` to `ATTACKER` at `type(uint256).max`.
3. A later, unrelated order (any user's `placeOrder` with a `TOKEN` predispatch asset, or any solver's fill with a `TOKEN` postdispatch output) transfers `TOKEN` funds to the same `dispatcher` address as part of its normal flow (`evm/src/apps/IntentGatewayV2.sol` predispatch transfer step).
4. Before the gateway's transfer-back/sweep call executes (or if the attacker races it in the same block via a bundled transaction), `ATTACKER` calls `TOKEN.transferFrom(dispatcher, ATTACKER, balance)` using the leftover approval, draining the second order's funds.
5. Repeat for any token used by any subsequent order — the dispatcher never becomes safe again once an approval has been granted through it.

        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];

            }

            if (size == 0) {

            }
