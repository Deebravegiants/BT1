### Title
Accrued debt RAY value overflows i128 and permanently freezes the market - (File: common/src/rates/scaling.rs / contracts/pool/src/interest.rs)

### Summary
Analogous to CVE-2017-9229 (invalid internal state in a forward computation producing an invalid dereference/crash), XOXNO Lending's accrual engine computes `borrowed_scaled * borrow_index` in `scaled_to_original` without bounding the product. Once a market's accrued debt value exceeds the `i128` range — which happens *before* the `MAX_BORROW_INDEX_RAY` cap engages — `accrue_step` panics with `MathOverflow`. Every state-mutating and view path runs accrual first, so the market becomes permanently bricked: no repay, withdraw, liquidation, or `update_indexes` can ever execute again.

### Finding Description
`interest::global_sync` runs `accrue_step` on every entrypoint touch (`contracts/pool/src/interest.rs:20-53`). Inside `accrue_step`, utilization and interest are computed from `scaled_to_original(env, borrowed, borrow_index)` (`common/src/rates/simulate.rs:129-175`), which performs `borrowed.mul(index)` — `mul_div` on `i128` that panics with `GenericError::MathOverflow` when `borrowed * index / RAY > i128::MAX` (`common/src/math/fp_core.rs:148-159`, `common/src/rates/scaling.rs:85-95`).

The borrow index is capped at `MAX_BORROW_INDEX_RAY = 1e36` raw (`common/src/rates/index.rs`), but the *value* `borrowed * index` overflows long before the index reaches the cap whenever total scaled debt is large. For an 18-decimal asset, `max_cap_for_decimals(18) = i128::MAX / 10^9 ≈ 1.7e29` base units (`common/src/validation.rs:48-56`), so a debt of ~1e9 whole tokens (`1e36` RAY of scaled debt) is inside the allowed cap domain; at that size a borrow index of only ~1.7x overflows `i128::MAX ≈ 1.7e38`.

The protocol's own harness confirms this is a reachable cliff: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361` drives a 1-billion-token 18-decimal market at 98% utilization on a steep-but-valid curve (`max_borrow_rate` 175% < the 200% cap), and after a few years `try_update_indexes_for` fails with `MATH_OVERFLOW`, after which `withdraw` and `repay` both revert with the same error while `borrow_index < MAX_BORROW_INDEX_RAY`. `docs/reference/invariants.md` (INV-IDX-01) explicitly acknowledges: "Debt-value overflow can still revert accrual before that ceiling is reached."

### Impact Explanation
Permanent freezing of all funds in the affected `(hub, token)` market. Since `global_sync` runs at the head of `supply`, `borrow`, `withdraw`, `repay`, `net_settle`, `seize_positions`, `flash_loan`, `claim_revenue`, and `recapitalize` (`contracts/pool/README.md:157-168`), once `borrowed * borrow_index` exceeds `i128::MAX` every one of these entrypoints panics. Suppliers can never withdraw, borrowers can never repay, liquidators can never seize, and even `recapitalize` — the documented recovery path — reverts. `last_timestamp` is never advanced (`cache.mark_accrued` is only reached after the loop), so the overflow re-triggers on every subsequent call forever. This is not a fail-closed DoS of a single call: it is an irrecoverable loss of all tokens held in that market's pool balance.

### Likelihood Explanation
Reachable by unprivileged users on any large high-utilization market:
1. A whale supplies and a borrower draws a large position (both permissionless), e.g. ~1e9 whole tokens of an 18-decimal asset — within `max_cap_for_decimals(18)` and the market's cap parameter domain.
2. Utilization stays high (attacker can keep it there by simply not repaying; interest accrual itself pushes utilization up).
3. Time passes — permissionless `update_indexes` or any touch advances accrual. At 175% APR the index crosses the ~1.7-170x overflow threshold (per the harness, a handful of years; at the 200% `MAX_BORROW_RATE_RAY` cap, faster).

No admin action, leaked key, or invalid parameter is required: `max_borrow_rate` up to `2*RAY` is a legitimate parameter, and the debt size fits the allowed cap domain. The only gate is market scale and elapsed time.

### Recommendation
Bound the debt-value product rather than letting it panic:
- In `update_borrow_index`/accrual, clamp `borrow_index` to `min(computed, MAX_BORROW_INDEX_RAY, i128::MAX * RAY / borrowed)` so accrual saturates (no further interest) instead of overflowing — mirroring how the supply index uses `mul_div_floor_saturating` (`common/src/rates/index.rs:41`).
- Alternatively make `scaled_to_original` saturate at `MAX_RAY_VALUE` in the accrual/utilization path so the market keeps operating (charging at the rate ceiling) rather than bricking.
- Ensure the fix is applied inside `accrue_step` in `common/src/rates/simulate.rs` so `global_sync` and `simulate_update_indexes` stay bit-for-bit identical.

### Proof of Concept
Codified in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`:

```rust
let principal = BILLION * 10i128.pow(18);          // 1e9 whole tokens, 18 dec
t.supply_raw(BOB, "BIG18", principal);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98); // 98% utilization

loop { t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; } }
// → Error(Contract, #33) MathOverflow while borrow_index < MAX_BORROW_INDEX_RAY
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

On mainnet the same sequence is executed by: supply → borrow at high utilization → wait / call `update_indexes` until `borrowed * borrow_index > i128::MAX * RAY` → every subsequent market call panics permanently.
