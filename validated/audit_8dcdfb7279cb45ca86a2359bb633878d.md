### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` headers are trusted without HMAC coverage, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers and passed straight through to the app's webhook handler as trusted, tenant-identifying data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  This is the only content that `Utils::HmacValidator.validate` checks against the HMAC signature in `Webhooks::Registry.process`: [2](#0-1) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all read directly out of attacker-controllable HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) with no cryptographic binding to the HMAC-verified body: [3](#0-2) 

These unauthenticated values are then handed directly to the app's registered handler as `WebhookMetadata`, which app code is documented to treat as trusted tenant identification: [4](#0-3) 

The security-relevant equality that should hold is: `shop header value == shop that produced/authorized the HMAC-signed body`. Because `shop` is excluded from the signable string, this equality is never checked — the gem only proves "this body was HMAC'd with our secret," not "this body/shop pair was HMAC'd with our secret." Any request with a body+HMAC pair that validates (e.g., a genuine webhook the attacker legitimately receives for their own Shopify store, since app secrets are shared across all shops using a public app) can be replayed with an arbitrary `shopify-shop-domain` header, and the gem will report it as valid and pass the attacker-chosen shop value to the handler.

### Impact Explanation
This breaks the tenant identity binding the gem is expected to guarantee for its callers: an unprivileged internet user who operates their own install of the public app (a normal, unprivileged capability — installing/using a public Shopify app on their own store) can capture a legitimately HMAC-signed webhook body for their own shop, then POST that same body+HMAC to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a victim shop. `Registry.process` reports `Invalid webhook HMAC.` only if the body/HMAC pair fails validation — it never fails due to a shop mismatch, so the forged request passes validation and the handler receives `WebhookMetadata` with `shop` set to the victim's domain and the attacker's own body content. Any app that uses `data.shop` (as documented) to key data storage, enqueue background jobs, or attribute records will process attacker-supplied data under the victim tenant's identity — a cross-tenant data injection/corruption primitive achieved without needing the victim's or the app's credentials.

### Likelihood Explanation
Exploitation only requires the attacker to install the target public app on their own (attacker-controlled) Shopify store — a routine, unprivileged action — trigger any registered webhook topic to receive one legitimately signed body+HMAC pair, and replay it to the app's public webhook endpoint with a modified shop header. No access to the app's `client_secret`, TLS interception, or victim credentials is required, making this practically exploitable by any user of a public app.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-covered signable content, or otherwise cryptographically bind the header-derived tenant identity to the verified payload before it is handed to `WebhookHandler#handle`. At minimum, `Registry.process` should independently verify that the `shop` in the webhook belongs to a shop with an active, registered subscription for that exact `topic`/`webhook_id`, rather than trusting the header value outright.

### Proof of Concept
1. Attacker installs the target public Shopify app on their own store `attacker-shop.myshopify.com` and registers for the `orders/create` webhook topic.
2. Shopify sends a legitimately HMAC-signed webhook to the app's endpoint:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC of body B, signed with app's real secret>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: B
   ```
3. Attacker captures this request (e.g., via their own proxy/logging, which they legitimately control since it's their own store's traffic) and replays it to the same endpoint, changing only the shop header:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <same valid HMAC of body B>
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   Body: B
   ```
4. `ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` reconstruct the same value used in step 2 (only `raw_body` matters), so `Utils::HmacValidator.validate` returns `true` per [5](#0-4) .
5. `Registry.process` invokes the app handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's parsed body>, ...)`, per [6](#0-5) , causing the app to process attacker-controlled order data as though it belongs to the victim shop.
