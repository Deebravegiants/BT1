Audit Report

## Title
JWT replay-guard TOCTOU race in HTTP Trigger gateway allows duplicate workflow trigger execution - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
The `WorkflowMetadataHandler.Authorize` method checks JWT replay status via `jwtCache.isReplay()` and records usage via `jwtCache.recordUsage()` as two separate, non-atomic critical sections guarded by independent lock acquisitions on the same `sync.RWMutex`. This creates a genuine check-then-act race window: two concurrent requests bearing the identical signed, single-use JWT can both observe `isReplay == false` before either calls `recordUsage`, allowing the same JWT to authorize more than one workflow trigger dispatch.

## Finding Description
`isReplay` takes an `RLock`, checks map membership, and releases the lock; `recordUsage` is only called later, after authorized-key validation, under a separate `Lock()` acquisition: <cite repo="AYontt/chainlink--021" path="core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go" start="80,90" end="90,108" /> [1](#0-0) 

This is reachable directly from an unauthenticated network path: `HandleUserTriggerRequest` → `authorizeRequest` → `WorkflowMetadataHandler.Authorize`, invoked on every inbound gateway HTTP trigger request. [2](#0-1) [3](#0-2) 

The existing per-request-ID dedup in `setupCallback` (`h.callbacks[requestID]` conflict check) does not prevent this bypass, because the JSON-RPC `req.ID` is fully attacker-controlled and independent of the JWT `jti`; an attacker can send two copies of the same signed request with two different `req.ID` values, defeating that dedup while still reusing the same `jti`. [4](#0-3) 

The codebase demonstrates the correct atomic pattern in `vault.RequestReplayGuard.CheckAndRecord`, which performs the lookup-and-insert in one critical section under a single mutex: [5](#0-4)  No equivalent atomic method or concurrency test exists for `jwtReplayCache`, confirming the gap is real and not mitigated elsewhere in this file.

Additionally, `VerifyRequestJWT` binds the JWT to a specific request digest (`Digest` claim) computed from the JSON-RPC request body, so replaying the identical JWT requires resending the identical request body/digest — this doesn't prevent the race, it just defines exactly what "replay" means here (same digest, same jti, sent twice). [6](#0-5) 

## Impact Explanation
An attacker who possesses one valid signed JWT for a trigger request (the same precondition needed to trigger it once) can race two copies of that exact request to the gateway and get both dispatched to the DON before the replay cache records the `jti`, since checkers use `isReplay`(RLock)/`recordUsage`(Lock) as decoupled steps rather than one atomic check-and-record. This can cause duplicate/unauthorized workflow executions from a token intended to be single-use, mapping to the "unauthorized job run" impact category. The severity is bounded by a narrow race window (map lock hold time) and by the fact the attacker must already hold a valid, digest-bound JWT — it does not grant new capabilities beyond duplicating an already-authorized single action.

## Likelihood Explanation
Exploitation requires only sending the identical signed request concurrently over HTTP, with no privilege escalation or special network position; this is trivially achievable by any client that already has one valid trigger JWT. The race window itself is small (a lock hold time on map read/insert), so reliable exploitation may require multiple attempts or favorable scheduling, but it is a real, reproducible client-side timing bug consistent with a classic TOCTOU pattern, and the codebase's own `vault.RequestReplayGuard` (with a passing concurrency test asserting exactly one winner) shows the intended atomic behavior was known and implemented correctly elsewhere but not applied here.

## Recommendation
Combine `isReplay` and `recordUsage` into a single atomic `CheckAndRecord(jti)` method under one `Lock()` (mirroring `vault.RequestReplayGuard.CheckAndRecord`), returning an "already used" error if the `jti` exists, otherwise inserting it in the same critical section. Call it once from `Authorize` prior to key validation, and add a concurrency test analogous to `TestRequestReplayGuard_ConcurrentAccess` asserting only one of N concurrent identical-JWT requests succeeds.

## Proof of Concept
1. Obtain one valid signed JWT (`jti = X`, `digest = D`) for an HTTP Trigger workflow request.
2. Fire N (e.g., 10) concurrent goroutines each calling `WorkflowMetadataHandler.Authorize(workflowID, token, req)` with the same `token`/`jti` but distinct `req.ID` values (to bypass the unrelated per-`req.ID` callback dedup in `setupCallback`).
3. Because `isReplay` and `recordUsage` are separate lock acquisitions, assert (as a Go unit test in `workflow_metadata_handler_test.go`) that more than one goroutine returns a non-error result from `Authorize`, proving duplicate acceptance of a single-use JWT — analogous to `TestRequestReplayGuard_ConcurrentAccess` but demonstrating the *failure* of atomicity in `jwtReplayCache` instead of its success in `RequestReplayGuard`.

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
