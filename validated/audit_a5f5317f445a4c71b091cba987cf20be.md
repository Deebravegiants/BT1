## Title
Permissionless `finalizeGraduation` requires a HyperEVM "big block" (~2.5M gas) that default-configured callers cannot produce, permanently freezing curve-raised LT and 250M tokens parked on `Bonding` — ([File: packages/contracts/src/Bonding.sol])

## Summary
The Aave/Polygon incident froze ~$110M because an interest-rate-strategy contract was built with an assumption (Ethereum-style gas/opcode behavior) that didn't hold on the actual deployment chain (Polygon), and no ordinary user transaction could unfreeze the funds without a governance-voted patch. alt.fun's two-phase graduation has the same shape: phase 2 (`Bonding.finalizeGraduation`) is deliberately sized at ~2.5M gas because HyperEVM enforces a hard, protocol-level split between "small blocks" (~2M gas ceiling) and "big blocks" (~30M gas ceiling), and a wallet must explicitly opt in to big blocks via a separate Hyperliquid L1 signed action before any of its EVM transactions can exceed the small-block ceiling [1](#0-0) . That opt-in is per-wallet, off-EVM state, and is not something `finalizeGraduation`'s caller-facing contract logic can enforce or verify [2](#0-1) [3](#0-2) .

## Finding Description
Graduation is deliberately split into two transactions because a single-tx graduation (drain curve + seed HyperSwap LP + lock) would not fit HyperEVM's small-block ceiling [1](#0-0) :
- Phase 1, `Bonding._enterGraduating`, fires inline on the threshold-crossing buy and is budgeted (and tested) to stay under 1.8M gas, comfortably inside the ~2M small-block ceiling [4](#0-3) . It parks the curve-raised real LT (`p.ltFromPair`) and the unburned LP-bound tokens inside `Bonding` via `pendingGraduation[token]` and flips `lifecycle: Curve → Graduating`, freezing all further trading on that token [5](#0-4) .
- Phase 2, `Bonding.finalizeGraduation`, is explicitly documented as a "**permissionless** big-block tx (~2.5M gas)" [1](#0-0) . It reads the cached `pendingGraduation` amounts, seeds the HyperSwap LP, and flips the token to `Lifecycle.Graduated` [6](#0-5) .

HyperEVM's dual block dispatch is not a mere convenience feature — it is a hard consensus-level gas ceiling per wallet, and the mechanism to raise that ceiling (`evmUserModify`, an L1 phantom-agent EIP-712 action, distinct from any normal EVM transaction) has to be executed and confirmed **before** the wallet's `finalizeGraduation` call is submitted [2](#0-1) . Any caller that has not separately performed this opt-in — which is the default state for essentially every wallet, including the "anyone can call to rescue a stuck token" callers the natspec explicitly relies on — will have their `finalizeGraduation` transaction rejected outright with `error code -32603: exceeds block gas limit`, exactly the failure mode documented for the protocol's own deploy script [3](#0-2) .

This is structurally the same "compatibility issue" class as the reference incident: a contract module (here, `finalizeGraduation`, analogous to Aave's interest-rate-strategy contract) was engineered to a gas/behavior budget that quietly depends on infrastructure-level configuration that varies by deployment/wallet context (chain-specific block-dispatch, analogous to Ethereum-vs-Polygon incompatibility), and the protocol's contracts have no on-chain mechanism to detect the mismatch, guide the caller, or provide a fallback path. The "permissionless, anyone-can-rescue" design intent in the natspec is undermined precisely because "anyone" in practice means "anyone who has already performed a separate, non-obvious, off-EVM opt-in action for their specific wallet" — which the Cloudflare Worker keeper does, but which a generic rescuer using a wallet/dApp UI is very unlikely to know about or be able to do without bespoke tooling.

## Impact Explanation
While `Lifecycle.Graduating`, the token is fully frozen: `Zap.buy`/`Zap.sell` both revert with `TokenIsGraduating` [7](#0-6) , and the curve-raised real LT plus the unburned portion of the 250M-token LP reserve sit in `Bonding`, reachable only through a successful `finalizeGraduation` call [6](#0-5) . If the keeper is down (a Cloudflare Worker is a single centralized dependency) and no other wallet happens to already be opted into big blocks, every graduating token remains stuck — traders cannot exit the curve, cannot exit on the graduated pool, and the protocol's own claimed brick-resistance/permissionless-rescue guarantee does not hold in practice. This mirrors the reference incident precisely: funds are not stolen but become inaccessible for an indeterminate period until an out-of-band, non-obvious remediation step (opting a wallet into big blocks, analogous to Aave's patch-and-vote) is performed.

## Likelihood Explanation
This isn't a probabilistic exploit — it is the deterministic default state of the system. Any wallet that has never explicitly called `evmUserModify` (i.e., the overwhelming majority of ordinary EOAs, including anyone trying to "rescue" a stuck graduation via a block explorer's "Write Contract" tab or a generic dApp) will have their `finalizeGraduation` transaction rejected by the small-block ceiling every time phase 2's real gas cost (~2.5M, per the protocol's own budget) exceeds the ~2M small-block limit. The single point of resilience is the off-chain Cloudflare Worker keeper; any keeper downtime, misconfiguration, or decommissioning directly manifests as this freeze with no on-chain fallback.

## Recommendation
- Do not rely solely on an off-chain keeper plus an implicit "anyone can call" narrative for a function whose gas cost structurally requires a non-default, per-wallet L1 opt-in; document and/or enforce this pre-condition more defensively.
- Consider further reducing `finalizeGraduation`'s worst-case gas so it fits within the small-block ceiling (as phase 1 already does, under 1.8M), removing the dependency on big-block opt-in entirely.
- Provide an on-chain or well-publicized fallback (e.g., a permissioned or incentivized backstop, or a documented, easy-to-follow big-block opt-in flow) so that "anyone can call to rescue a stuck token" is actually true for a generic wallet, not only for wallets that have pre-opted into big blocks.

## Proof of Concept
1. A token crosses the graduation threshold via a normal `Zap.buy`; phase 1 (`_enterGraduating`) fires inline and succeeds under the small-block ceiling, leaving the token `Lifecycle.Graduating` with `pendingGraduation[token]` populated [8](#0-7) .
2. Assume the keeper Worker is offline (deployment lapse, provider outage, decommissioning, etc.) and no other wallet is currently opted into HyperEVM big blocks.
3. A third-party rescuer, using a standard wallet/dApp (not aware of, or unable to execute, the Hyperliquid `evmUserModify` L1 action described in `scripts/toggle-big-blocks.mjs`), submits `bonding.finalizeGraduation(tokenAddress)` as an ordinary transaction. Because this wallet defaults to small blocks, and `finalizeGraduation`'s real-world gas cost (~2.5M, documented in `AGENTS.md`) exceeds the ~2M small-block ceiling, the transaction is rejected by the chain with `exceeds block gas limit`, mirroring the exact failure `AGENTS.md` warns about for the deploy script [9](#0-8) .
4. The token remains stuck at `Lifecycle.Graduating` indefinitely: `Zap.buy`/`Zap.sell` continue to revert with `TokenIsGraduating`, and the curve-raised LT plus unburned LP-reserve tokens stay parked inside `Bonding`, unreachable by any caller who has not independently completed the big-blocks opt-in for their own wallet.

## Graduation — Two-Phase, Dynamic LP Seeding (Read This Before Touching Graduation Code)

This is the most bespoke piece of the protocol. Full rationale + invariants live in [`docs/contracts-scope.md`](../../docs/contracts-scope.md#graduation); the short version:

- **Two-phase split.** Graduation is split across two transactions to fit HyperEVM's small-block (~2M gas) ceiling.
  - **Phase 1: `_enterGraduating`**, fired inline by the threshold-crossing buy (~150-200k of additional gas on top of the buy). Drains the curve, computes the LP-bound amounts, caches them in `pendingGraduation[token]`, flips `lifecycle: Curve → Graduating`, freezes trading. Emits `TokenGraduating`.
  - **Phase 2: `finalizeGraduation`**, **permissionless** big-block tx (~2.5M gas). Creates the HyperSwap pair if needed, seeds liquidity across the empty, donation, and hostile mint-pre-seed regimes, locks LP, flips `lifecycle: Graduating → Graduated`. Emits `TokenGraduated`. A Cloudflare Worker keeper handles the happy path; anyone can call to rescue a stuck token.
- **Brick resistance.** Phase 2 must never revert under any pre-seed shape. Empty/donation pairs use direct pair calls; hostile mint pre-seeds use direct `pair.swap` for rebalance plus router `addLiquidity` for the canonical quote-based deposit. Tested by `test_brick_resistance_frontRun_dust_seed` in [`test/TwoPhaseGraduation.t.sol`](test/TwoPhaseGraduation.t.sol).

### HyperEVM gotchas (read this BEFORE deploying)

HyperEVM is **not** a vanilla EVM RPC — these things will burn time if you skip them:

- **Dual block dispatch.** Small blocks ≈2M gas / ~1s, big blocks ≈30M gas / ~60s. `Deploy.s.sol` includes contracts that exceed 2M gas individually (`Bonding`, `Zap`), so the broadcast WILL fail with `error code -32603: exceeds block gas limit` until you opt in. The opt-in is **per-wallet, persists**, lives on the Hyperliquid L1 (NOT EVM), and applies to **every** subsequent tx from that wallet (1s → 60s confirmations). Tooling: `scripts/toggle-big-blocks.mjs` (status / on / off) — uses Hyperliquid's `evmUserModify` L1 action with the `Agent`/phantom-agent EIP-712 signing scheme (NOT the user-signed-action scheme; do not copy from random Hyperliquid SDK examples without reading `sign_l1_action`).
- **Slow broadcasts.** With big blocks on, a full `Deploy.s.sol` is ~14–19 sequential txs × ~60s = **15–20 minutes**. Plan accordingly. Use `--slow` so forge waits for confirmations between dependent txs (it would hit nonce/state mismatches without it).
- **`--legacy` is NOT needed.** HyperEVM supports EIP-1559; the past broadcasts in `broadcast/Deploy.s.sol/999/` confirm this.

#!/usr/bin/env node
/**
 * Toggle HyperEVM "big blocks" on/off for the deployer wallet.
 *
 * HyperEVM dispatches transactions into two block sizes:
 *   - Small blocks (~2M gas, ~1s)  — default
 *   - Big blocks   (~30M gas, ~60s) — required for contract deploys
 *
 * The choice is per-wallet and lives on the Hyperliquid L1 (NOT the EVM), so
 * you flip it by signing an EIP-712 L1 action (`evmUserModify`) and POSTing
 * it to https://api.hyperliquid.xyz/exchange. There is no on-EVM way to
 * change this — `cast send` cannot help.
 *
 * Status is read via the `eth_usingBigBlocks(address)` JSON-RPC custom
 * method on any HyperEVM RPC.
 *
 * Usage:
 *   node scripts/toggle-big-blocks.mjs <on|off|status>
 *
 * Reads `.env` from this package automatically:
 *   DEPLOYER_PRIVATE_KEY=0x...
 *   HYPEREVM_RPC_URL=...
 *
 * IMPORTANT: This uses Hyperliquid's L1 action signing scheme, not the
 * simpler "user-signed action" scheme. The action is msgpack-encoded,
 * keccak-hashed with the nonce, then wrapped in a phantom-`Agent` EIP-712
 * envelope before signing. See `sign_l1_action` in
 * `hyperliquid-python-sdk/hyperliquid/utils/signing.py`.

    /// @dev `tokenHolder` is where `Router` pulls LT from / delivers tokens to
    ///      (the calling Zap). `trader` is event-only attribution (the user EOA).
    function _executeBuy(
        address tokenHolder,
        address trader,
        uint256 amountIn,
        address tokenAddress
    ) internal returns (uint256 tokensOut, uint256 amountInUsed) {
        (amountInUsed, tokensOut) = _s().router.buy(amountIn, tokenAddress, tokenHolder);

        (uint256 newCurveSupply, uint256 newLtReserve) = _getCurveState(tokenAddress);
        emit Trade(tokenAddress, trader, true, amountInUsed, tokensOut, newCurveSupply, newLtReserve);

        if (canGraduate(tokenAddress)) {
            _enterGraduating(tokenAddress);
        }
    }

    /// @dev Phase 1: drain curve, cache LP-bound amounts, freeze trading. Runs
    ///      inline at end of the threshold-crossing buy. Pinning `tokensForLP`
    ///      and `ltFromPair` here (at the last curve price) is what preserves
    ///      the zero-gap invariant across the tx split.
    function _enterGraduating(
        address tokenAddress
    ) internal {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        info.lifecycle = Lifecycle.Graduating;

        (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) =
            _prepareGraduationLiquidity(tokenAddress);

        $.pendingGraduation[tokenAddress] = PendingGraduation({
            tokensForLP: tokensForLP, ltFromPair: ltFromPair, lpBurned: lpBurned, unsoldBurned: unsoldBurned
        });

        emit TokenGraduating(tokenAddress, tokensForLP, ltFromPair, lpBurned, unsoldBurned);
    }

    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }
