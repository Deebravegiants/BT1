### Title
Cross-chain transfers can deliver 0 tokens for a non-zero locked/burned amount due to unchecked decimal-truncation in `convert_to_balance` - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler converts the ERC20-denominated amount carried in an incoming ISMP message into the local balance denomination via `convert_to_balance`, which performs an unchecked integer division. When the source chain's ERC20 decimals exceed the local asset's decimals by enough, a genuinely non-zero amount that a user burned/locked on the source chain can floor to `0` on the destination, and the pallet proceeds to mint/transfer `0` without ever detecting or rejecting this outcome — mirroring the referenced `calculateMint()` zero-mint bug in USSD.

### Finding Description
`convert_to_balance` divides the raw ERC20 `U256` value by `10^(erc_decimals - local_decimals)` with no post-conversion zero check: [1](#0-0) 

This is invoked directly in the unsigned/unprivileged message-delivery path, `on_accept`, which any relayer can trigger by delivering a valid cross-chain proof for a message that was legitimately dispatched by a user who burned/locked tokens on the EVM side: [2](#0-1) 

The resulting `amount` (potentially `0`) is passed straight into `NativeCurrency::transfer`, `Assets::transfer`, or `Assets::mint_into` with no guard, and a `TokenReceived` event with `amount: 0` is still emitted as if the transfer succeeded normally: [3](#0-2) [4](#0-3) 

The identical unguarded division exists in the `on_timeout` refund path as well, so a refund for a real, non-zero burned amount can also silently deliver `0` back to the original sender: [5](#0-4) 

Contrast this with the outbound `send()` path, which multiplies (`convert_to_erc20`) rather than divides, so precision loss/zero-flooring is specific to the inbound/refund direction: [6](#0-5) 

### Impact Explanation
Whenever `erc_decimals - local_decimals` is large enough that a legitimately small (but non-zero) transferred amount floors to zero in `convert_to_balance`, the user's principal — already burned/locked on the source EVM chain — is permanently lost: the destination pallet mints or transfers `0` and reports success. The same integer-division floor applies to timeout refunds, so even the "safety net" refund path can zero out a real balance. This is a direct, unbacked value-loss condition reachable by any ordinary token bridger without any privileged action, matching the classification of "permanent freezing/loss of funds" from token bridge mint/burn logic.

### Likelihood Explanation
Likelihood depends on the configured decimal gap (`Precisions` storage, admin-set per asset/chain) and the size of the individual transfer. For any asset pair where `erc_decimals - local_decimals` is non-trivial (e.g., 12+, common when bridging an 18-decimal EVM token to a 6-decimal Substrate asset), any user-submitted amount smaller than `10^(erc_decimals - local_decimals)` in ERC20 base units triggers the bug. This can happen accidentally (small transfers, dust) or be deliberately probed by a user/relayer, and requires no special privileges to reach — only a normal `send()` call from the EVM side followed by ordinary message relay.

### Recommendation
Add an explicit zero-check (and ideally a minimum-transfer-amount check) in `convert_to_balance`, rejecting (reverting the message handling, or dispatching a timeout/refund) any conversion that would produce a local `amount == 0` for a non-zero input `value`. This should be applied consistently in both `on_accept` and `on_timeout` in `modules/pallets/hyper-fungible-token/src/module.rs`.

### Proof of Concept
1. Admin registers an asset with `Precisions::<T>::insert(asset_id, evm_chain, 18)` (ERC20 has 18 decimals) while the local asset has `decimals = 6` (i.e., `local_decimals = 6`).
2. A user calls the EVM `HyperFungibleToken.send()` (or equivalent) to bridge a dust amount, e.g. `value = 999_999` (raw ERC20 units, i.e., `0.000000000000999999` tokens) — genuinely non-zero.
3. The pallet's `on_accept` receives the message and computes:
   `convert_to_balance(999_999, 18, 6)` → `999_999 / 10^(18-6)` = `999_999 / 10^12` = `0`.
4. `mint_into`/`transfer` is called with `amount = 0`; `TokenReceived { amount: 0, .. }` is emitted; the call returns `Ok`.
5. The user's tokens were already burned/locked on the EVM side in step 2, but they receive nothing on the destination chain — a total, permanent loss of the transferred principal with no revert or recovery path. [7](#0-6)

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
