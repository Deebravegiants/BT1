### Title
Unvalidated `unsignedTx.txMeta.keyId` in `SeedBasedTransactionSigner.signTransaction` allows cross-key signing bypass - ([File: features/tx-signer/src/module/seed-signer.ts])

### Summary
`SeedBasedTransactionSigner.signTransaction` derives the signing key from `unsignedTx.txMeta.keyId` when that field is present, only validating that it is a *well-formed* `KeyIdentifier` (via `KeyIdentifier.validate`) rather than verifying it belongs to the `walletAccount`/`baseAssetName` the user approved. Since `TransactionSigner.signTransaction` (the public entry point) only asserts `typeof txMeta === 'object'` with no allow-list, an attacker-influenced caller can supply an arbitrary `txMeta.keyId` and cause signing with a key/derivation path different from what the UI displayed.

### Finding Description
The public entry point performs only shallow type checks and does not restrict which keys `txMeta` may contain: [1](#0-0) 

That `unsignedTx` (including `txMeta`) is forwarded unchanged to `SeedBasedTransactionSigner.signTransaction`: [2](#0-1) 

The critical branch is:
```
const keyId = unsignedTx.txMeta?.keyId
...
if (!keyId) {
  const signer = await this.#getSignerForWalletAccount({ walletAccount, baseAsset })
  return signTx({ unsignedTx, signer })
}
assert(KeyIdentifier.validate(keyId), `txMeta.keyId must be a key identifier object`)
const signer = await this.#getSignerForKeyId({ seedId: walletAccount.seedId, keyId })
return signTx({ unsignedTx, signer })
``` [3](#0-2) 

`KeyIdentifier.validate` only checks structural well-formedness (valid `derivationAlgorithm`, syntactically valid `derivationPath`, supported `keyType`) — it performs no comparison against the target `walletAccount`, `baseAssetName`, or any allow-listed derivation prefix: [4](#0-3) [5](#0-4) 

Consequently, `#getSignerForKeyId` will happily derive and sign with any syntactically valid `keyId` under the same `seedId`, i.e. any account/path within the user's seed — not limited to the account/asset the UI rendered for approval: [6](#0-5) 

Separately, `accountIndex` and `compatibilityMode` in `txMeta` are only defaulted from `walletAccount` when *absent*; if the caller supplies them, they pass straight through unchanged and are asserted only to be an integer (`accountIndex`), with no equality check against `walletAccount.index`: [7](#0-6) 
These fields are then handed to the asset-specific `signTx` implementation as part of `unsignedTx`, and some assets' `signTx`/key-derivation logic use `accountIndex`/`compatibilityMode` from `txMeta` to compute derivation paths per input (e.g. Bitcoin-like multi-input signing).

I could not fully verify, within the available index, the exact code path connecting an untrusted browser-extension/RPC/deeplink dapp request all the way to this `unsignedTx.txMeta` object without any wallet-side allow-listing/sanitization in between (e.g., in `sdks`/RPC-bridge/web3-provider adapters). The web3 provider docs (`solana.signTransaction`, `bitcoin` PSBT provider) describe the dapp-facing surface, and `features/assets-feature/client/asset-client-interface.js` shows a `signTransaction({ assetName, unsignedTx, walletAccount })` pass-through to the transaction signer, but the intermediate adapter code that converts a raw dapp transaction request into the internal `unsignedTx.txMeta` object was not found in the index, so it's unconfirmed whether that adapter already strips/rebuilds `txMeta` (which would neutralize this issue) or forwards attacker-influenced fields verbatim. [8](#0-7) 

The `__proto__` prototype-pollution vector specifically was not confirmed to have exploitable impact — the code performs `typeof txMeta === 'object'` checks and property lookups (`unsignedTx.txMeta.compatibilityMode`, `.accountIndex`, `.keyId`) that are not obviously affected by a polluted prototype in the reviewed code paths.

### Impact Explanation
If the "sometimes we need a different keyId" (`txMeta.keyId`) override is reachable from an untrusted dapp/RPC/deeplink caller without wallet-side allow-listing, this would let a malicious caller instruct the wallet to sign with a different key (different account/asset key) than the one displayed in the approval UI — a scope divergence between what the user consented to and what is actually signed. That matches a cross-account/cross-key authorization bypass under signing logic.

### Likelihood Explanation
The likelihood depends entirely on whether an intermediate RPC/dapp/adapter layer allow-lists `txMeta` fields before they reach `SeedBasedTransactionSigner.signTransaction`. Within `features/tx-signer`, there is no such allow-listing: `transaction-signer.ts` performs only a generic `typeof` check, and `seed-signer.ts` trusts `txMeta.keyId`/`accountIndex`/`compatibilityMode` verbatim when present. I was unable to locate, within the indexed codebase, the exact adapter code that builds `unsignedTx.txMeta` from a raw dapp/RPC signing request, so I cannot confirm end-to-end reachability from an unprivileged dapp origin with certainty.

### Recommendation
- In `TransactionSigner.signTransaction` and/or `SeedBasedTransactionSigner.signTransaction`, enforce an explicit allow-list of permitted `txMeta` fields per call site, and require any privileged fields (`keyId`, `accountIndex`, `compatibilityMode`) that diverge from the `walletAccount`'s own derivation to be explicitly and separately authorized (e.g. only used for known/trusted internal callers such as EOS/Ripple fallback flows, never routed through the dapp/RPC-facing API surface).
- When `txMeta.accountIndex`/`compatibilityMode` are supplied by an untrusted caller, assert they equal `walletAccount.index`/`walletAccount.compatibilityMode` rather than merely checking they are present/well-typed.
- For `txMeta.keyId`, in addition to `KeyIdentifier.validate`, verify the `keyId`'s derivation path/asset is consistent with the `walletAccount`/`baseAssetName` being signed for (or restrict the override capability to an internal-only API not exposed to the public/dapp-facing `transactionSignerApi`).

### Proof of Concept
Unit test plan for `features/tx-signer/src/module/__tests__/seed-signer.test.ts`:
1. Set up a `walletAccount` for account index 0.
2. Call `seedSigner.signTransaction({ walletAccount, baseAssetName: 'bitcoin', unsignedTx: { txData: {}, txMeta: { keyId: new KeyIdentifier({ derivationAlgorithm: 'BIP32', derivationPath: "m/44'/0'/999'/0/0", keyType: 'secp256k1' }) } } })`.
3. Spy on `assets.bitcoin.api.signTx` to capture the `signer` passed in, then call `signer.getPublicKey()`/`signer.sign()` and assert it derives from the attacker-supplied `m/44'/0'/999'/0/0` path rather than the walletAccount's own account-0 path.
4. Assert this succeeds without any error and without cross-checking `keyId` against `walletAccount.index`, demonstrating the missing invariant ("signing scope must match approved walletAccount").
5. Repeat by supplying `txMeta.accountIndex = 999` and confirm the value is passed through unmodified to `signTx`'s `unsignedTx.txMeta.accountIndex` without validation against `walletAccount.index`.
