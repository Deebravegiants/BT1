### Title
Unvalidated Balance-Based Asset Sweep from a Shared, Unrestricted `CallDispatcher` Enables Theft/Griefing of Escrowed Intent Inputs - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder()`'s predispatch flow measures "tokens generated by the predispatch call" by simply reading `IERC20(token).balanceOf(dispatcher)` and sweeping the entire balance, rather than validating that the swept amount was actually produced by *this* order's predispatch execution. The `dispatcher` (`CallDispatcher`) is a single, protocol-wide shared contract whose `dispatch()` function has **no access control** whatsoever, so anyone can call it directly. This mirrors the Balancer report's root cause — assets moved/staked by a privileged operation are not validated against what should legitimately be in scope — except here the "spent assets" are an entire token balance sitting in a shared, permissionless contract.

### Finding Description
In the predispatch branch of `placeOrder`, tokens are sent to `_params.dispatcher`, arbitrary calldata is executed, and then the contract "sweeps" tokens back by reading the dispatcher's raw balance: [1](#0-0) 

The received amount is computed purely from a balance delta on the gateway side, and any balance above the required input amount is attributed as protocol "dust", while a balance below `requiredAmount` reverts: [2](#0-1) 

Critically, `CallDispatcher.dispatch()` is a fully public function with **no owner/caller restriction**, executing arbitrary `Call[]` with the dispatcher as `msg.sender`: [3](#0-2) 

Because the dispatcher is a single shared singleton (`_params.dispatcher`) reused by every `placeOrder` call across all users, and its `dispatch()` entrypoint is unrestricted, any ETH/token balance that ever sits on the `CallDispatcher` — leftover swap dust, fee-on-transfer residue, or tokens transferred there mid-flow — is not scoped to the order that put it there. Anyone monitoring the mempool can call `CallDispatcher.dispatch()` directly with a `Call` that transfers out that balance before the legitimate sweep executes, or an order's predispatch calldata can itself scoop up balance left behind by a different (unrelated) in-flight/concurrent operation on the same shared dispatcher, since the sweep step trusts `balanceOf(dispatcher)` unconditionally rather than tracking exactly what its own predispatch call produced.

### Impact Explanation
Funds routed through the shared `CallDispatcher` are not isolated per order. An attacker able to front-run or interleave calls to the permissionless `dispatch()` function can drain any token/ETH balance sitting on the dispatcher at that moment — including tokens a user has just transferred there as part of their own `placeOrder` predispatch step, or dust intentionally or unintentionally left behind by swap calldata. This can result in direct theft of user-escrowed input tokens or of protocol-collected dust, i.e., concrete loss of funds reachable from a single unprivileged `placeOrder` transaction combined with an attacker's own transaction against `CallDispatcher`.

### Likelihood Explanation
`placeOrder`'s predispatch path (arbitrary swap/unwrap calldata before escrow) is a standard, documented usage pattern of the Intent Gateway and is reachable by any unprivileged user in a single transaction. `CallDispatcher.dispatch()` requiring zero authorization makes exploitation trivial for anyone watching the mempool for predispatch transactions or for residual balances left on the shared dispatcher (e.g., from swap slippage/dust), making this a realistically and cheaply exploitable path rather than a purely theoretical one.

### Recommendation
- Restrict `CallDispatcher.dispatch()` to only be callable by the authorized `IntentGatewayV2` instance(s) (e.g., an `onlyGateway`/allow-listed caller modifier), removing the fully public access.
- Avoid relying on raw `balanceOf(dispatcher)` deltas to determine "received" amounts; instead deploy a fresh, single-use dispatcher/escrow context per order (or use a nonce-scoped accounting mechanism) so that swept amounts can only reflect what this specific predispatch call generated.
- Sweep exactly the amount produced by the predispatch call (tracked via return data or a pre/post balance snapshot taken atomically around only the user's own calls) rather than the dispatcher's full balance.

### Proof of Concept
1. User A submits `placeOrder` with `predispatch.call` that swaps ETH→TokenX via the shared `CallDispatcher`, transferring TokenX to the dispatcher and expecting the gateway to sweep it in the same transaction (`evm/src/apps/IntentGatewayV2.sol:258-289`).
2. Because `CallDispatcher.dispatch()` has no access control (`evm/src/utils/CallDispatcher.sol:44`), an attacker who observes any residual TokenX balance sitting on the shared dispatcher (whether from A's transaction not yet finished sweeping in a bundled/aggregated flow, or leftover dust from a previous order's incomplete sweep) can call `dispatcher.dispatch()` directly with a `Call{to: TokenX, data: transfer(attacker, balance)}`.
3. Because the gateway's own sweep logic trusts `IERC20(token).balanceOf(dispatcher)` unconditionally rather than verifying the balance is exclusively attributable to the current order, the attacker's direct call can extract value that legitimate order flows assumed was safely held for them, resulting in reverted/failed escrow for the victim or outright loss of the swept tokens.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
