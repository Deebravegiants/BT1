Based on my investigation, I found a genuine analog to the Exactly Protocol bug class in `Router.sol`.

### Title
Missing pair-existence check in `Router.buy` lets a malformed reserve state be operated on without the `PairNotFound` guard every sibling function enforces - (`packages/contracts/src/Router.sol`)

### Summary
The Exactly Protocol exploit succeeded because `DebtManager` failed to validate that a caller-supplied market address was a legitimate, registered market before trusting it as an authorization surrogate. The alt.fun analog is narrower but the same class of defect: `Router.buy()` is the only state-mutating trade path in `Router.sol` that omits the `if (pairAddr == address(0)) revert PairNotFound();` check that every other pair-resolving function (`sell`, `previewBuy`, `getAmountOut`, `addInitialLiquidity`, `graduate`) explicitly performs. [1](#0-0) 

### Finding Description
`Router.buy` resolves `pairAddr` via `factory.getPair(token, asset)` and immediately proceeds into `_computeBuy(pairAddr, amountIn)`, `safeTransferFrom`, `transferToken`, and `swap` without ever checking `pairAddr != address(0)`: [2](#0-1) 

Contrast with `sell`, which performs the check immediately after resolving the pair: [3](#0-2) 

And `previewBuy`/`getAmountOut`/`addInitialLiquidity`/`graduate`, which all guard identically: [4](#0-3) [5](#0-4) [6](#0-5) 

`Router.buy` is gated by `BONDING_ROLE`, held only by `Bonding`, and `Bonding.buy` is itself gated by `onlyRouter` and requires `info.creator != address(0)` for the target `tokenAddress`, i.e. the token must already have been registered through `Bonding.launch`, which always creates a corresponding `Pair` via `Factory.createPair` in the same call before `tokenInfo` is populated: [7](#0-6) [8](#0-7) 

Because `Factory.createPair` is one-shot per `(tokenA, tokenB)` pair and there is no admin path to delete or overwrite an existing `_pairs` entry, every `tokenAddress` reachable through the legitimate `Bonding → Router` call chain already has a non-zero `pairAddr` by construction. I was unable to identify any reachable code path — reachable from an unprivileged trader's transaction via `Zap.buy` / `Zap.buyWithPermit` / `createToken` — where `Bonding.buy` forwards a `tokenAddress` for which `factory.getPair(token, asset)` returns `address(0)`, because the `TokenNotTrading` check in `Bonding.buy` and the atomic launch/pair-creation in `Bonding.launch` close that gap.

### Impact Explanation
If reachable, calling into `_computeBuy(address(0), amountIn)` would attempt to decode return data from a call to an address with no code, which reverts on ABI decoding rather than silently succeeding, so even in a hypothetical zero-pair scenario, no theft or fund loss would result — it would simply be a revert (DoS), not the collateral-draining spoof seen in Exactly. This differs materially from the Exactly bug, where the missing check let the attacker substitute an arbitrary market and *successfully* execute a state-changing withdrawal that drained a victim's real collateral.

### Likelihood Explanation
Given the current wiring (`Bonding`'s `onlyRouter`/`TokenNotTrading` gate plus `Factory`'s one-shot, non-deletable pair registration), there is no demonstrated way for an unprivileged trader, token creator, or unrelated wallet to make `factory.getPair(token, asset)` return `address(0)` for a `tokenAddress` that reaches `Router.buy`. The missing check is real and inconsistent with the rest of the file, but I could not construct a concrete transaction sequence from `Zap.createToken/buy/sell` or any other unprivileged entry point that exploits it into theft or fund freezing.

### Recommendation
Add the same `if (pairAddr == address(0)) revert PairNotFound();` guard to `Router.buy` that already exists in `sell`, `previewBuy`, `getAmountOut`, `addInitialLiquidity`, and `graduate`, for defense-in-depth and consistency, even though no exploitable path was found under the current `Bonding`/`Factory` invariants. This closes the class of bug the Exactly report warns about before any future change to `Bonding`'s launch/registration flow could make the zero-pair case reachable.

### Proof of Concept
Not applicable — no concrete unprivileged-caller transaction sequence was found that drives `Router.buy` to a non-registered/zero pair address under the current contract wiring. This is a defensive/consistency gap, not a demonstrated exploit.

    function buy(
        uint256 amountIn,
        address tokenAddress,
        uint256 amountOutMin,
        address trader
    ) external onlyRouter nonReentrant returns (uint256 tokensOut, uint256 amountInUsed) {
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        // `creator == 0` means the slot was never written. `Lifecycle.Curve` is
        // the zero value, so without this an unknown token would fall through
        // and revert deep in `router.buy` with an opaque error.
        if (info.creator == address(0)) revert TokenNotTrading();
        if (info.lifecycle == Lifecycle.Graduating) revert TokenIsGraduating();
        if (info.lifecycle != Lifecycle.Curve) revert TokenNotTrading();
        _enforceLaunchDelay(tokenAddress);

        (tokensOut, amountInUsed) = _executeBuy(msg.sender, trader, amountIn, tokenAddress);
        if (tokensOut < amountOutMin) revert SlippageExceeded();
    }
