## Title
Unchecked ERC20 return value in escrow payout allows malicious order tokens to silently fail transfers and permanently trap/steal solver funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` imports and declares `using SafeERC20 for IERC20;`, and correctly uses `safeTransferFrom`/`safeTransfer` semantics for pulling tokens *into* escrow during `placeOrder`. However, the escrow-payout path (`withdraw()`) and the governance `SweepDust` handler in `onAccept` bypass `SafeERC20` entirely and instead perform raw low-level `.call()`s to `transfer()`, only checking that the call itself didn't revert — never decoding/validating the returned boolean. This is precisely the ERC20 return-value handling flaw described in the referenced Buffer report: tokens that signal failure by returning `false` (instead of reverting) are silently treated as successful transfers.

### Finding Description
In `withdraw()`:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
``` [1](#0-0) 

`success` from a low-level `.call()` only reflects whether the callee *reverted*; a token whose `transfer()` returns `false` on failure (without reverting) makes `success == true` even though no tokens moved. The contract then unconditionally decrements the escrow accounting `_orders[body.commitment][token] -= amount`, permanently marking the escrow as paid regardless of whether the beneficiary actually received anything.

The same unchecked pattern is used for the accumulated fee payout in the same function: [2](#0-1) 

and again in the `SweepDust` handler inside `onAccept`: [3](#0-2) 

This is inconsistent with the rest of the codebase, which uniformly uses OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` for the exact same purpose — e.g. the escrow release in `IntentsBase._withdraw` on other chains: [4](#0-3) 

and the input-collection side of this very Tron contract: [5](#0-4) 

The input `token` for an order is fully attacker-controlled — any address the order creator (`msg.sender`) supplies in `order.inputs[i].token` in `placeOrder`. A malicious order creator can deploy an ERC20 whose `transfer()` returns `false` (instead of reverting) whenever it is called by the gateway contract (or under attacker-chosen conditions), while behaving normally for `transferFrom` during deposit so that `placeOrder`'s `safeTransferFrom` succeeds and the order looks legitimate. `withdraw()` is reached unprivileged via:
- `cancelOrder()` same-chain branch, callable directly by the order owner: [6](#0-5) 
- `onAccept` for `RedeemEscrow`/`RefundEscrow`, triggered once a solver fills the order and the cross-chain message is delivered: [7](#0-6) 

### Impact Explanation
When a solver fills a cross-chain order whose input token is a "false-on-failure" ERC20, the solver delivers real output tokens to the user's beneficiary, but the escrow release of the input tokens to the solver silently no-ops: `success` is true, `_orders[...] -= amount` proceeds, and the solver receives zero tokens while the escrow accounting is zeroed out as "paid." The tokens remain trapped in the contract with no further code path able to claim them (the commitment is already marked filled and the per-token escrow entry is now decremented/zero), meeting the "permanent freezing of funds" bar, and constituting theft of the solver's honest output tokens by a malicious order creator. The same flaw in the fee payout and `SweepDust` handler can similarly zero-out fee/dust accounting without delivering funds.

### Likelihood Explanation
High. Any unprivileged user can place an order (`placeOrder`) using a purpose-built ERC20 as `order.inputs[i].token` that returns `false` instead of reverting under the specific call pattern used against solvers (this is not an exotic assumption — this is a documented class of ERC20 behavior, e.g. tokens with pausable/blacklist logic that "fail soft"). No special privileges, timing races, or additional preconditions are required beyond a single order placement and a solver choosing to fill it.

### Recommendation
Replace all raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` usages in `withdraw()` and the `SweepDust` branch of `onAccept` with `IERC20(token).safeTransfer(beneficiary, amount)` (the `using SafeERC20 for IERC20` directive is already imported/declared in this file but simply not used at these call sites), matching the pattern already used in `placeOrder`'s `safeTransferFrom` calls and in the sibling `IntentsBase._withdraw` implementation.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 whose `transferFrom` behaves normally (so escrow deposit succeeds) but whose `transfer()` returns `false` (does not revert) when called by the `IntentGatewayV2` contract.
2. Attacker calls `placeOrder` with `order.inputs[0].token = EvilToken`, depositing real value; `placeOrder` uses `safeTransferFrom`, so the deposit succeeds and escrow is credited (`evm/tron/contracts/apps/IntentGatewayV2.sol:459`).
3. A solver fills the order on the destination chain, delivering real output tokens to the beneficiary, then the `RedeemEscrow` message is relayed back and `onAccept` invokes `withdraw(body, false)`.
4. In `withdraw`, `EvilToken.transfer(solver, amount)` returns `false` without reverting; `success == true` from the low-level call, so `TransferFailed()` is never raised, and `_orders[commitment][token] -= amount` proceeds as if the solver was paid.
5. The solver receives zero `EvilToken`, the escrow entry is zeroed, and the tokens remain unrecoverable in the contract — the solver has permanently lost the value of the output tokens it delivered.
