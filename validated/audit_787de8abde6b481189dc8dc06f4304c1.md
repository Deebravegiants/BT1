### Title
PoA Bridge status polling matches withdrawals by `assetId` only, misattributing destination tx hash across withdrawals in the same batch - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
When multiple withdrawals of the same token are included in a single batched intent transaction, `PoaBridge.describeWithdrawal` and the underlying `findMatchingWithdrawal` helper resolve the on-chain outcome for a specific withdrawal index solely by `assetId`, ignoring the withdrawal's index/destination/amount. This lets the SDK report the wrong destination transaction hash (or wrong completion status) for a given `WithdrawalIdentifier`, which is the equality an integrator relies on to credit/refund a specific withdrawal.

### Finding Description
`PoaBridge.describeWithdrawal` looks up the on-chain withdrawal record using only the asset identifier: [1](#0-0) 

The comment on this call explicitly states the response list is "unsorted, so we match by assetId instead of index" — but `index` (the position of this withdrawal in the batch, carried in `WithdrawalIdentifier`) is never used to disambiguate. A parallel implementation of the same lookup pattern exists in `internal-utils`, with the limitation spelled out directly in its docstring: [2](#0-1) 

`createWithdrawalIdentifiers` assigns a per-bridge-route `index` to each withdrawal in a batch so that later status calls can distinguish sibling withdrawals of the same route: [3](#0-2) 

But `PoaBridge.describeWithdrawal`/`findMatchingWithdrawal` never consult that `index`, `destinationAddress`, or `amount` — only `assetId`. When a caller submits a batch of withdrawals to the PoA route with the same `assetId` but different destination addresses (or different amounts), each per-index `describeWithdrawal` poll queries the same PoA API response and returns the *first* withdrawal record found for that asset. This means:
- Two (or more) different withdrawal indices in the same batch can end up reporting the *same* `txHash`/status, even though they should each resolve to a distinct destination transaction.
- An integrator building automation on `watchWithdrawal`/`waitForWithdrawalCompletion` per withdrawal index (exactly the batch-processing flow documented in the SDK's `createWithdrawalCompletionPromises`) will therefore attribute a completed destination tx hash to the wrong index.

### Impact Explanation
This breaks the equality "the status/hash reported for withdrawal index N is the on-chain outcome of withdrawal N." Concretely: if withdrawal #0 (destination A) and withdrawal #1 (destination B) share `assetId`, `describeWithdrawal({index:0})` and `describeWithdrawal({index:1})` can both resolve to the withdrawal record actually belonging to B. An integrator that credits internal ledgers, marks invoices paid, or releases custody based on per-index `txHash`/`status` from the SDK can:
- Mark withdrawal #0 (to A) as completed using B's `transfer_tx_hash`, effectively crediting/closing A's flow based on B's transaction — a misreport that can lead to a wrong-address credit/no-recovery situation from the integrator's perspective, or
- Leave the genuinely-completed withdrawal permanently "pending" (since the matcher only returns one record per asset) requiring manual intervention — a stuck-withdrawal condition.

This matches the High-impact categories "a status or hash misreport making an integrator credit or refund twice" and "a withdrawal stuck until manual intervention."

### Likelihood Explanation
This triggers under normal, unprivileged usage — no malicious actor is required. Any legitimate batch withdrawal request with two or more entries sharing the same `assetId` on the PoA route (a common real-world case, e.g., paying out the same token to several recipients in one intent) exercises this code path. The bug is baked into the matching logic itself (not a race or edge case in an external system), so it is deterministic whenever such a batch occurs and the integrator relies on the SDK's per-withdrawal status output.

### Recommendation
Extend `findMatchingWithdrawal` (in both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) to disambiguate same-asset withdrawals within a batch — e.g., match on `(assetId, destinationAddress, amount)` tuple, or track and exclude already-claimed indices/hashes across concurrent lookups for the same `tx.hash`, so each `WithdrawalIdentifier.index` deterministically resolves to its own on-chain record. Until fixed, the SDK should explicitly reject or warn on batches containing duplicate `assetId` entries routed through PoA Bridge, consistent with the existing code comment acknowledging this is unsupported.

### Proof of Concept
1. Submit a single `signAndSendWithdrawalIntent` batch with two `withdrawalParams` entries, both `assetId: "nep141:usdt.tether-token.near"`, but `destinationAddress: A` for index 0 and `destinationAddress: B` for index 1, via `RouteEnum.PoaBridge`.
2. `createWithdrawalIdentifiers` assigns `index: 0` and `index: 1` to the two withdrawals under the PoA route (see `packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`).
3. Call `sdk.waitForWithdrawalCompletion` (or `createWithdrawalCompletionPromises`) for both indices. Each independently invokes `PoaBridge.describeWithdrawal`, which calls `getWithdrawalStatusWithRetry` (keyed only by `tx.hash`) then `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` — matching by `assetId` alone (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:313-322`).
4. Once the PoA bridge processes both transfers, the API response contains two withdrawal records with the same `near_token_id`/`defuse_asset_identifier` but different `transfer_tx_hash`/`address`. Both `describeWithdrawal({index:0})` and `describeWithdrawal({index:1})` resolve to whichever record `Array.find` returns first, so at least one index reports the wrong (or a duplicate) `txHash` as "completed," while the other stays "pending" indefinitely.

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
