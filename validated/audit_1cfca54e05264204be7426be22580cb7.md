### Title
Stale operator authorization is trusted for the full `operator_qr_expiration_time` window without re-validating that the operator is still authorized before starting a new signup - (File: `src/plans/mod.rs`)

### Summary
The external report describes `AutoRange` trusting a `positionConfigs[tokenId]` entry that was set by a *previous* owner, because `execute()` never re-checks that the configuration still corresponds to the current owner before acting on it. The same class of bug — an authorization/config artifact validated once and then reused across a security-relevant boundary without re-checking it is still current — is reachable in orb-core's operator QR-code flow.

### Finding Description
When an operator's QR code is scanned, orb-core calls the backend once via `verify_operator_qr_code`/`backend::operator_status::request` to confirm the operator is authorized, and caches the result in an `OperatorData` struct together with a `timestamp: Instant::now()`: [1](#0-0) 

That cached `OperatorData` is then reused, without ever calling the backend again, as long as `operator_data.timestamp.elapsed() < operator_qr_expiration_time`, both in `idle_wait_for_signup_request`/`idle_scan_user_qr_code` (self-serve loop) and in `scan_remaining_qr_codes`: [2](#0-1) 

`operator_qr_expiration_time` defaults to 23 hours: [3](#0-2) 

So exactly like `AutoRange.execute()` reading `positionConfigs[tokenId]` without checking whether the config still belongs to the current `tokenId` owner, `scan_remaining_qr_codes`/`idle_scan_user_qr_code` read the cached `OperatorData` (an authorization artifact obtained from a point-in-time backend check) and use it to authorize/attribute an arbitrary number of subsequent, unrelated user signups for up to 23 hours, with no re-validation that the operator's authorization is still valid at the time each new signup is attributed to them.

### Impact Explanation
If an operator's authorization is revoked by the backend (e.g., operator account disabled, distributor removed) after the initial QR validation but within the 23-hour window, the orb will still attribute every subsequent signup during that window to that operator and record their (stale) `operator_qr_code`/`location_data` in the `DebugReport`/PCP credentials: [4](#0-3) 
This causes misattributed signups — signups being recorded/paid/tracked against an operator identity that is no longer actually authorized, which is functionally the same "protocol acts on stale ownership/config data" outcome flagged in the report (there the protocol lost incentives; here signups are misattributed to a de-authorized operator for an extended window).

### Likelihood Explanation
This is reachable on the standard, non-privileged operator/user signup path with no special preconditions beyond normal operation over the (default 23-hour) `operator_qr_expiration_time` window, matching the report's own conclusion that relying on a single point-in-time check without re-validation is realistic in practice ("frontend/session checks are unreliable" argument that the judge upheld).

### Recommendation
Re-validate operator authorization (call `backend::operator_status::request` again) before starting each new signup that reuses a cached `OperatorData`, or shorten/eliminate the reuse window so that authorization state cannot silently go stale relative to the backend's source of truth, mirroring the report's mitigation of binding/re-checking ownership before consuming a previously stored authorization artifact.

### Proof of Concept
1. Operator A scans their QR code; `verify_operator_qr_code` succeeds and `OperatorData { qr_code, location_data, timestamp: Instant::now() }` is cached (`src/plans/mod.rs:775-781`).
2. Backend revokes operator A's authorization (e.g., account disabled) a few minutes later.
3. Within the remaining `operator_qr_expiration_time` (up to ~23h by default), the orb calls `scan_remaining_qr_codes`/`idle_scan_user_qr_code`, which see `operator_data.timestamp.elapsed() < operator_qr_expiration_time` and reuse the cached (now stale) `OperatorData` without calling `backend::operator_status::request` again (`src/plans/mod.rs:788-820`, `456-488`).
4. New, unrelated signups are attributed to the now-unauthorized operator A and recorded as such in the `DebugReport`/PCP credentials.

    async fn scan_initial_qr_codes(
        &mut self,
        orb: &mut Orb,
        qr_codes: &mut QrCodes,
        self_serve: bool,
        operator_qr_expiration_time: Duration,
    ) -> Result<()> {
        if self_serve
            && qr_codes
                .operator_timestamp()
                .map_or(true, |ts| ts.elapsed() > operator_qr_expiration_time)
        {
            loop {
                let qr_capture_start = Instant::now();
                let operator_qr_code =
                    self.scan_operator_qr_code(orb, None).await?.expect("to never timeout");
                let Some(operator_qr_code) =
                    self.handle_magic_operator_qr_code(orb, operator_qr_code).await?
                else {
                    continue;
                };
                let Some((_, operator_location_data)) =
                    self.verify_operator_qr_code(orb, &operator_qr_code, qr_capture_start).await?
                else {
                    continue;
                };
                *qr_codes = QrCodes::Operator {
                    operator_data: OperatorData {
                        qr_code: operator_qr_code,
                        location_data: operator_location_data,
                        timestamp: Instant::now(),
                    },
                };
                break;
            }
        }
        Ok(())
    }
