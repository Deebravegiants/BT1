### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` value that identifies which merchant/tenant the webhook belongs to is read straight from an HTTP header that is never included in the signed material. An attacker who can obtain (or predict) one validly-signed webhook body can replay it with an arbitrary `shop-domain` header and have it accepted and dispatched to the handler as if it came from a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

`shop` is parsed from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is entirely separate data that is not part of the signable string: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` (i.e. body only), and — once that check passes — trusts `request.shop` to build the `WebhookMetadata` that is handed to the app's handler: [3](#0-2) 

`HmacValidator.validate_signature` computes the HMAC purely from `verifiable_query.to_signable_string`: [4](#0-3) 

The identity binding that should hold is: `shop header value == shop covered by the HMAC`. In this code that equality never holds — the HMAC covers `body` only, while `shop` is an independent, unauthenticated header. The gem's own documentation reinforces the false assumption that HMAC validation authenticates the whole request ("This will verify the request did indeed come from Shopify and then call the specified handler for that webhook."), which is misleading with respect to the `shop` field.

Because a webhook body for topic X is frequently identical or predictable in structure across shops (and an attacker who installs the app on their own store legitimately receives correctly-HMAC-signed webhooks for their own shop), the attacker can capture a validly-signed request and resend it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. The HMAC check still passes (it only checks the body), and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: the shop identity delivered to the handler is attacker-controllable while still passing "webhook authenticity" validation. Depending on how the host app uses `data.shop` (e.g., to look up which merchant's session/store data to update, to trigger per-shop side effects, or to route data into a specific tenant's queue/store), this can result in cross-tenant data confusion or injection of forged events attributed to a shop the attacker does not control — a cross-tenant access issue.

### Likelihood Explanation
Exploitation requires the attacker to already be able to trigger and capture at least one legitimately-signed webhook for a topic (trivially achievable by installing the app on their own store, which is exactly the "unprivileged internet user" threat model), and then to replay that exact body with a different `shop-domain` header value. No access to `api_secret_key` or any victim credentials is needed. This makes the class of attack readily reachable through the gem's documented API (`Registry.process` / `Request.new`).

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signable string used for HMAC verification, or otherwise cryptographically bind `request.shop` to the validated payload, instead of trusting it as a bare, unauthenticated header value. At minimum, document prominently that `data.shop` is not authenticated by the HMAC check and must be independently verified/authorized by the host application (e.g., cross-checked against a known, previously-established session for that shop) before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) for topic X, capturing the raw body `B` and the valid `x-shopify-hmac-sha256` header computed by Shopify over `B`.
2. Attacker sends a POST to the app's webhook endpoint with:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-hmac-sha256: <the HMAC captured in step 1>`
   - Body: `B` (unchanged)
3. `ShopifyAPI::Webhooks::Request.new` parses these headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `B` and matches — validation succeeds.
4. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` and invokes the registered handler, which now processes attacker-supplied data as though it originated from `victim-shop.myshopify.com`.
