### Title
Utilization gate is skipped when a market has zero suppliers, allowing unbounded debt against donated cash - (File: contracts/pool/src/guards.rs)

### Summary
`require_utilization_below_max` returns early whenever `cache.supplied() == Ray::ZERO`, and `require_liquidation_buffer` computes the reserve from that same zero supply (`reserved = ceil(0 * BPS / BPS) = 0`). A market that holds token cash without any supply shares — reachable because anyone can transfer tokens directly to the pool contract — therefore passes both solvency gates regardless of how much debt `borrow` mints against it, and the market can carry positive `borrowed` with zero `supplied`, a state the codebase itself treats as `PoolInsolvent` in `require_supply_for_debt`.

### Finding Description
The reported Carapace issue is a degenerate-ratio bug: `leverageRatio()` returns 0 when `totalProtection == 0`, so the `leverageRatio <= ceiling` phase gate passes vacuously and the pool advances with no protection sold.

The same shape exists in `contracts/pool/src/guards.rs`:

```rust
// contracts/pool/src/guards.rs
pub(crate) fn require_utilization_below_max(env: &Env, cache: &Cache) {
    if cache.supplied() == Ray::ZERO || cache.params().max_utilization >= Ray::ONE {
        return;                       // <- gate skipped when denominator is zero
    }
    let borrowed = cache.borrowed().mul_ceil(env, cache.borrow_index());
    if borrowed == Ray::ZERO { return; }
    let supplied = cache.supplied().mul_floor(env, cache.supply_index());
    assert_with_error!(env,
        supplied > Ray::ZERO && borrowed.div_ceil(env, supplied) <= cache.params().max_utilization,
        CollateralError::UtilizationAboveMax);
}
```

Utilization is `borrowed / supplied`; when `supplied == 0` the ratio is effectively infinite, yet the guard treats it as a pass — the exact inverse of the correct handling, analogous to Carapace returning a "safe" 0 ratio for an empty denominator. Compounding this, `require_liquidation_buffer` derives its reserve from `supplied`, so with zero supply the reserve is 0 and `cash - draw >= 0` is the only constraint:

```rust
let reserved = mul_div_ceil(env, supplied, LIQUIDATION_BUFFER_BPS, BPS); // 0 when supplied == 0
assert_with_error!(env, cache.cash().saturating_sub(draw) >= reserved, ...);
```

The codebase recognizes `supplied == 0 && borrowed != 0` as `PoolInsolvent` via `require_supply_for_debt`, but that guard is not part of the borrow-time check set (`borrow.rs` invokes the utilization/liquidity guards only), so borrow reaches the degenerate state rather than reverting.

### Impact Explanation
Once a market carries debt with zero supply:

- Any subsequent `supply` enters a market that is already above `max_utilization` (infinite ratio). The new supplier's funds are instantly lent out; their `withdraw` is gated by utilization and the liquidation buffer, so supplier funds are frozen until the attacker repays — attacker-controlled temporary freezing of depositor funds.
- Operations that invoke `require_supply_for_debt` (e.g., revenue/settlement paths) panic with `PoolInsolvent` while the degenerate state persists, freezing protocol revenue flows for that market.
- The borrowed cash is drained from balances the market never accounted as claims, so the market's `backing_shortfall` accounting is skewed from inception.

### Likelihood Explanation
An unprivileged attacker needs only two steps, both in scope:

1. Donate tokens to the pool contract via a direct token transfer — `cash` rises while `supplied` stays 0 (donations do not mint shares).
2. Post collateral in any other market of the same hub (satisfying the controller-side `require_post_pool_risk_gates`, which only checks account-level LTV/HF) and call `Controller::borrow` for the donated market. Pool-side, `require_utilization_below_max` returns early and the liquidation buffer reserves nothing, so the borrow succeeds for the full donated balance.

The attacker's debt remains collateralized at the account level, so liquidation cannot repair the market-level state; the degenerate market then traps the next real supplier.

### Recommendation
Replace the early return with an explicit solvency check on the borrow path — i.e., call `require_supply_for_debt` (or equivalent) inside `require_utilization_below_max`, so `supplied == 0 && borrowed > 0` (including the post-draw state) reverts instead of passing:

```rust
if cache.supplied() == Ray::ZERO {
    assert_with_error!(env, cache.borrowed() == Ray::ZERO && draw == 0,
        CollateralError::PoolInsolvent);
    return;
}
```

Equivalently, treat a zero-supply market as utilization = +∞ rather than "skip", and exclude donated cash from borrowable liquidity (track a supply-only cash invariant or require `supplied > 0` before any draw).

### Proof of Concept
1. Fresh market `(hub, X)` with `max_utilization < RAY 1.0` configured; `supplied = 0`, `borrowed = 0`, `cash = 0`.
2. Attacker `token.transfer(pool, X, 1_000e7)` → `cash = 1_000e7`, `supplied` still 0.
3. Attacker supplies collateral in market `(hub, Y)` and calls `controller.borrow(account_id, [(hub,X; 1_000e7)], None)`.
4. Pool borrow path: `require_utilization_below_max` returns at the `supplied == Ray::ZERO` branch; `require_liquidation_buffer` computes `reserved = 0` and `cash - draw = 0 >= 0` passes → borrow mints `borrowed(X) > 0` with `supplied(X) == 0`.
5. Victim calls `supply` on market `X`. The market is already at infinite utilization; the victim's subsequent `withdraw` fails `UtilizationAboveMax`/`InsufficientLiquidity` until the attacker repays, and any `require_supply_for_debt`-guarded call reverts `PoolInsolvent` in the interim.
