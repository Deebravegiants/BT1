### Title
Webhook shop identity is taken from an unsigned header while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` returns only the raw request body, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read directly from unauthenticated HTTP headers. `Utils::HmacValidator.validate` (and therefore `Webhooks::Registry.process`) only proves that the *body bytes* were signed with the app's `client_secret`; it proves nothing about which shop the header claims the webhook came from. Since a single app has one `client_secret` shared across every merchant that installs it, any merchant who can trigger a webhook for their own store can capture a validly-HMAC'd body and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop, and the signature will still validate.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are parsed straight from headers, none of which are included in the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `to_signable_string` (the body) and compares it to the `hmac` header value — it never binds the result to `shop`: [3](#0-2) 

`Webhooks::Registry.process` accepts the request once the body HMAC checks out, then dispatches the handler using the unverified `request.shop`, `request.topic`, and `request.webhook_id`: [4](#0-3) 

The broken identity binding, expressed as an equality that should hold but doesn't:
`shop bound by HMAC signature == shop asserted in the `shopify-shop-domain`/`x-shopify-shop-domain` header`

Because the app's `client_secret` is identical for every shop that installs the app, an unprivileged attacker who installs the app on their own store (a normal, unprivileged action any internet user can take) can:
1. Trigger a webhook topic whose body is attacker-controllable or predictable (e.g., a topic with an empty/near-empty payload, or one where the attacker's own shop content matches what they want the handler to process for another shop).
2. Receive the legitimately signed `(body, hmac)` pair for their own shop.
3. Replay that exact body and `hmac` header to the app's public webhook endpoint, but substitute the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with the victim shop's domain.
4. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` runs the handler believing the event belongs to the victim shop.

This crosses the tenant boundary that the HMAC is nominally supposed to protect: `shop` — a value the handler and any downstream `SessionRepository` lookups treat as authenticated — is actually attacker-controlled.

### Impact Explanation
This maps to the Critical "cross-tenant access" category: an attacker with no privileges beyond installing the app on their own (attacker-controlled) shop can make the app process a webhook as if it originated from a different, victim shop. Depending on the handler logic (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`, or custom mandatory-compliance topics), this can cause the app to delete/redact victim data, deactivate the victim's session, or otherwise perform shop-scoped side effects attributed to the wrong tenant — all without ever touching the victim's credentials.

### Likelihood Explanation
Likelihood is limited by needing the attacker to be an installer of the app on some shop (any app in the Shopify App Store satisfies this trivially — installing an app is unprivileged) and needing a webhook topic whose body content is attacker-influenceable or topic-agnostic enough to be replayed against another shop. Many mandatory/compliance topics (`shop/redact`, `customers/redact`, `customers/data_request`) and topics like `app/uninstalled` have small, near-static payloads, making replay straightforward once the attacker captures one signed body from their own store.

### Recommendation
Bind the shop (and topic/webhook id) into the signed material that `HmacValidator` verifies, or otherwise independently authenticate the header-derived `shop` before dispatch — e.g., verify the header shop against a shop known to have this specific `webhook_id`/subscription registered, or require handlers to cross-check `shop` against an existing installed session rather than trusting the header. At minimum, document that `Webhooks::Request#shop` is not itself authenticated by the HMAC and must not be treated as tenant-binding without additional verification (e.g., confirming an active session exists for that shop before acting).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (normal signup flow, no privilege needed).
2. Attacker triggers/receives a legitimately signed webhook, e.g. for `app/uninstalled`, capturing `raw_body` and the `shopify-hmac-sha256` header.
3. Attacker POSTs the same `raw_body` and `shopify-hmac-sha256` to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully; `HmacValidator.validate(request)` returns `true` because only `raw_body` is checked: [5](#0-4) 
5. `Webhooks::Registry.process(request)` invokes the registered handler with `shop: "victim-shop.myshopify.com"`, causing the app to run victim-scoped logic (e.g., wiping the victim's stored session/data) triggered entirely by the attacker.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
