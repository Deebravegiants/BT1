## Analysis

The reported bug class is: **a fee/amount is pre-computed before an operation completes, and if the actual settled amount differs (increases) from what was pre-computed, the system fails to re-validate sufficiency of funds/limits — it just proceeds with an inconsistent state.**

The closest reachable analog in the chainlink repo is in the workflow metering/credit-spend accounting path, which governs unprivileged workflow-triggered capability calls and controls fund/credit movement (job-run cost accounting), not a mocked or operator-only path.

### Title
Metering `Settle` fails to re-validate balance when actual capability spend exceeds the pre-computed `Deduct` reservation - (File: `core/services/workflows/metering/metering.go`)

### Summary
`Report.Deduct` earmarks (reserves) a credit amount for a capability step **before** the capability actually executes, using either a fixed `ByResource` amount or a derived max (`ByDerivedAvailability`) computed from current balance/user limit/concurrency. [1](#0-0)  After the capability runs, `Report.Settle` computes the *actual* spend (`spentCredits`) from node-reported metering data and reconciles it against the earlier reservation (`step.Deduction`). [2](#0-1)  This is structurally identical to the pump-science pattern: a fee/amount is computed from an assumption made *before* the real outcome is known, and the real outcome (here, actual node spend) can diverge from that assumption.

### Finding Description
In `Settle`, the balance reconciliation is:
```go
if err := r.balance.Add(step.Deduction.Sub(spentCredits)); err != nil {
    // invariant: capability should not let spend exceed reserve
    r.lggr.Info("invariant: spend exceeded reserve")
}
r.balance.AddSpent(spentCredits)
``` [3](#0-2) 

If `spentCredits` (the actual, node-reported spend for the step) exceeds `step.Deduction` (the amount pre-computed and reserved before the capability ran), the code merely logs an informational message ("invariant: spend exceeded reserve") and continues — it does not reject the settlement, does not re-check that sufficient balance/credits remain, and does not stop further steps from being deducted against an already-violated balance. This mirrors exactly the pattern flagged in the external report: the fee/amount was computed against a pre-state assumption (`exact_in_amount`/`buy_amount_applied` before the last-buy price adjustment; here, `step.Deduction` before the capability's real resource usage is known), and when the real value diverges upward, the code does not recheck that the payer (here, the workflow's or organization's credit balance) still has sufficient funds.

The `getMaxSpendForInvocation` reservation is also based on splitting *currently available* balance across `openConcurrentCallSlots` at Deduct time [4](#0-3) , so concurrent steps can each reserve based on a stale balance snapshot; if actual spends from prior/concurrent steps come in higher than reserved, `Settle` for subsequent steps still won't re-validate against the true remaining balance beyond the same log-only invariant check.

I was not able to fully inspect `balance_store.go`'s `Add`/`AddSpent`/`Minus` implementations within the available iterations, so I cannot confirm from source whether `Add` enforces a hard floor at zero or merely returns an advisory error that the caller (as shown above) ignores. This is a gap in verification — a background agent should read `core/services/workflows/metering/balance_store.go` to confirm whether negative balances are actually possible after this code path, or whether `balance.Add`'s error already prevents underflow at the data-structure level (in which case the impact is reduced to inconsistent bookkeeping/logging only, not fund-loss).

### Impact Explanation
If `balance.Add` does not itself enforce a floor, an attacker-controlled or malfunctioning capability could report inflated `SpendValue`/`SpendValueInGasUnits` in its response metadata, causing `spentCredits` to exceed the reserved `Deduction`. Because `Settle` only logs the mismatch rather than failing the step or halting further spend authorization, subsequent `ByDerivedAvailability` calls (line 361, `getMaxSpendForInvocation`) would compute future spend limits off of a balance that no longer reflects true consumption, potentially permitting execution beyond the organization's actual paid-for credit limit (unauthorized job-run/fund consumption, similar in class to the original report's "insufficient remaining funds" concern).

### Likelihood Explanation
This is triggered purely by unprivileged workflow execution requests flowing through the standard capability invocation → metering pipeline (`Reserve` → `Deduct` → capability execution → `Settle`), with no special privilege required beyond normal workflow trigger access (e.g., via the HTTP trigger/gateway path). The only requirement is a capability response whose reported spend exceeds the pre-reserved limit, which can occur either through a buggy/malicious capability or a legitimate but larger-than-expected resource usage burst.

### Recommendation
In `Report.Settle`, when `step.Deduction.Sub(spentCredits)` is negative (i.e., actual spend exceeds the reservation), the code should not merely log and continue. It should, at minimum, re-validate the resulting balance against zero/available limits and take a defined action (e.g., switch to metering-mode fail-open explicitly, halt subsequent `Deduct` calls, or surface a hard error/deny) rather than silently absorbing the shortfall via an ignored error. This mirrors the original recommendation of rechecking actual-vs-assumed amounts and re-validating sufficiency of funds after the real value is known, rather than trusting the pre-computed figure.

### Proof of Concept
1. A workflow triggers a capability step with `Deduct("stepA", ByResource("GAS.1", "cap-1", decimal.NewFromInt(10)))`, reserving 10 credits worth of balance. [5](#0-4) 
2. The capability (or a malicious/compromised DON node in its `ResponseMetadata.Metering`) reports a `SpendValue` that converts to, e.g., 1000 credits.
3. `Settle("stepA", metadata)` computes `spentCredits = 1000`, then calls `r.balance.Add(10 - 1000)` = `r.balance.Add(-990)`. [6](#0-5) 
4. If this returns an error, it is only logged (`"invariant: spend exceeded reserve"`) — execution proceeds, and `r.balance.AddSpent(1000)` is still recorded, without any hard stop or re-check for the workflow's remaining credit sufficiency for subsequent steps.

// ByResource returns a DeductOpt that earmarks a specified amount of local universal credit balance for a given spend
// type.
func ByResource(
	spendType, capabilityID string,
	amount decimal.Decimal,
) func(string, *Report) ([]capabilities.SpendLimit, error) {
	return func(ref string, r *Report) ([]capabilities.SpendLimit, error) {
		step := ReportStep{
			CapabilityID:     capabilityID,
			Deduction:        decimal.Zero,
			AggregatedSpends: make(map[string]AggregatedStepDetail),
		}

		defer func() {
			r.steps[ref] = step
		}()

		bal, err := r.balance.ConvertToBalance(spendType, amount)
		if err != nil {
			// Fail open, continue optimistically
			r.switchToMeteringMode(fmt.Errorf("failed to convert to balance [%s]: %w", spendType, err))
		}

		step.Deduction = bal

		// if in metering mode, exit early without modifying local balance
		if r.meteringMode {
			return []capabilities.SpendLimit{}, nil
		}

		return []capabilities.SpendLimit{}, r.balance.Minus(bal)
	}
}

// ByDerivedAvailability returns a DeductOpt that derives the maximum spend limit based on the user spend limit and
// the number of open concurrent call slots.
func ByDerivedAvailability(
	userSpendLimit decimal.NullDecimal,
	openConcurrentCallSlots int,
	info capabilities.CapabilityInfo,
	config *values.Map,
) func(string, *Report) ([]capabilities.SpendLimit, error) {
	return func(ref string, r *Report) ([]capabilities.SpendLimit, error) {
		step := ReportStep{
			CapabilityID:     info.ID,
			Deduction:        decimal.Zero,
			AggregatedSpends: make(map[string]AggregatedStepDetail),
		}

		defer func() {
			r.steps[ref] = step
		}()

		limit, err := r.getMaxSpendForInvocation(userSpendLimit, openConcurrentCallSlots)
		if err != nil {
			return nil, err
		}

		if !limit.Valid {
			return []capabilities.SpendLimit{}, nil
		}

		step.Deduction = limit.Decimal

		// if in metering mode, exit early without modifying local balance
		if r.meteringMode {
			return []capabilities.SpendLimit{}, nil
		}

		return r.creditToSpendingLimits(info, config, limit.Decimal), r.balance.Minus(limit.Decimal)
	}
}

// Settle handles the actual spends that each node used for a given capability invocation in the engine,
// by returning earmarked local balance to the available to use pool and adding the spend to the metering report.
// The Deduct method must be called before Settle.
// We expect to only set this value once - an error is returned if a step would be overwritten.
func (r *Report) Settle(ref string, metadata capabilities.ResponseMetadata) error {
	r.mu.Lock()
	defer r.mu.Unlock()

	if !r.reserved {
		return ErrNoReserve
	}

	step, ok := r.steps[ref]
	if !ok {
		return ErrNoDeduct
	}

	if step.Spends != nil {
		return ErrStepSpendExists
	}

	spentCredits := decimal.NewFromInt(0)
	resourceSpends := make(map[string][]ReportStepDetail)

	// Group by resource dimension
	for _, nodeDetail := range metadata.Metering {
		resourceSpends[nodeDetail.SpendUnit] = append(resourceSpends[nodeDetail.SpendUnit], ReportStepDetail{
			Peer2PeerID:          nodeDetail.Peer2PeerID,
			SpendValue:           nodeDetail.SpendValue,
			SpendValueInGasUnits: nodeDetail.SpendValueInGasUnits,
			CRESpendValue:        decimal.Zero,
		})
	}

	// Aggregate node responses to a single number
	for unit, spendDetails := range resourceSpends {
		aggregated := AggregatedStepDetail{
			SpendUnit:  unit,
			SpendValue: decimal.Zero,
		}

		deciVals := []decimal.Decimal{}
		for idx, detail := range spendDetails {
			value, err := r.parseSpendValue(unit, detail)
			if err != nil {
				// throw out invalid values for local balance settlement. they will still be included in metering report.
				continue
			}

			if val, convertErr := r.balance.ConvertToBalance(unit, value); convertErr == nil {
				resourceSpends[unit][idx].CRESpendValue = val
			}

			deciVals = append(deciVals, value)

			if isGasSpendType(unit) && len(deciVals) > 1 {
				r.switchToMeteringMode(fmt.Errorf("multiple executions for single execution unit [%s]: %w", unit, err))
			}
		}

		// TODO: explicitly ignore RPC_EVM spend types for now -
		// this check causes TestEngine_Metering_ValidBillingClient/billing_type_and_capability_settle_spend_type_mismatch ./core/services/workflows/v2
		// to fail because the capability is returning a spend type that isn't gas or compute
		// This should be removed when we have proper support for non-gas/compute spend types
		if unit == "RPC_EVM" {
			continue
		}

		aggregated.SpendValue = medianSpend(deciVals)
		value := aggregated.SpendValue

		// if N is not set, assume 1
		if metadata.CapDON_N == 0 {
			metadata.CapDON_N = 1
		}

		// TODO: indicate in the registry config that a capability is single execution or not
		// https://smartcontract-it.atlassian.net/browse/CRE-1037
		if !isGasSpendType(unit) {
			value = value.Mul(decimal.NewFromUint64(uint64(metadata.CapDON_N)))
		}

		bal, err := r.balance.ConvertToBalance(unit, value)

		if err != nil {
			r.switchToMeteringMode(fmt.Errorf("attempted to Settle [%s]: %w", unit, err))
		} else {
			aggregated.CRESpendValue = bal
			spentCredits = spentCredits.Add(bal)
		}

		step.AggregatedSpends[unit] = aggregated
	}

	step.Spends = resourceSpends
	step.CapdonN = metadata.CapDON_N
	r.steps[ref] = step

	// if in metering mode, exit early without modifying local balance
	if r.meteringMode {
		return nil
	}

	// Refund the difference between what local balance had been earmarked and the actual spend
	if err := r.balance.Add(step.Deduction.Sub(spentCredits)); err != nil {
		// invariant: capability should not let spend exceed reserve
		r.lggr.Info("invariant: spend exceeded reserve")
	}

	r.balance.AddSpent(spentCredits)
```

func (r *Report) getMaxSpendForInvocation(
	userSpendLimit decimal.NullDecimal,
	openConcurrentCallSlots int,
) (decimal.NullDecimal, error) {
	nullCapSpendLimit := decimal.NewNullDecimal(decimal.Zero)
	nullCapSpendLimit.Valid = false

	if openConcurrentCallSlots == 0 {
		// invariant: this should be managed by the consumer (engine)
		return nullCapSpendLimit, ErrNoOpenCalls
	}

	if !r.reserved {
		return nullCapSpendLimit, ErrNoReserve
	}

	if r.meteringMode {
		return nullCapSpendLimit, nil
	}

	// Split the available local balance between the number of concurrent calls that can still be made
	spendLimit := r.balance.Get().Div(decimal.NewFromInt(int64(openConcurrentCallSlots)))

	if userSpendLimit.Valid {
		spendLimit = decimal.Min(spendLimit, userSpendLimit.Decimal)
	}

	return decimal.NewNullDecimal(spendLimit), nil
}
