## Title
Pool creator can permanently freeze LP/swapper funds by using a mint with an attacker-controlled `freeze_authority` for `coin_mint`/`pc_mint` - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` validates that the newly-created LP mint has no freeze authority, but it never validates the `freeze_authority` of the user-supplied `coin_mint`/`pc_mint` that back the pool's vaults. Since any unprivileged user can create a pool (`Initialize2`) supplying arbitrary SPL mints, an attacker can create a pool whose coin or pc mint has a freeze authority it controls. After other users deposit or swap into the pool, the attacker calls the standard SPL Token `FreezeAccount` instruction against the AMM's `coin_vault`/`pc_vault`, which permanently blocks every subsequent `Deposit`, `Withdraw`, `SwapBaseIn(V2)` and `SwapBaseOut(V2)` CPI `Transfer` from/into that vault. This is the on-chain analog of the reported ERC20 "revert on transfer" DoS: an untrusted, attacker-influenced token implementation is trusted to always allow value transfer, and there is no code path allowing a seller/LP/arbitrator-equivalent to recover funds once the token blocks transfers.

### Finding Description
During pool creation the program unpacks and stores the caller-supplied `coin_mint`/`pc_mint` without any restriction on their `freeze_authority`: [1](#0-0) 

It does check that the **LP mint** it creates itself has no freeze authority: [2](#0-1) 

but performs no equivalent check for `amm_coin_mint_info` / `amm_pc_mint_info`, which are attacker-chosen accounts. The resulting vaults (`amm.coin_vault`, `amm.pc_vault`) are simply SPL token accounts for those mints: [3](#0-2) 

All subsequent value-moving instructions (`Deposit`, `Withdraw`, `SwapBaseIn`, `SwapBaseOut`, and their V2 variants) perform unconditional `spl_token::instruction::transfer` CPIs against these vaults via `Invokers::token_transfer` / `Invokers::token_transfer_with_authority`: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

None of these instructions check the freeze state of the coin/pc mint or vault, nor does the codebase provide any way for the program (or another party) to migrate/rescue vault funds if the SPL Token program rejects the transfer because the account is frozen (freezing is enforced entirely inside the SPL Token program, which the AMM program cannot bypass). Once the attacker (holding the mint's freeze authority) issues `FreezeAccount` on `amm_coin_vault` or `amm_pc_vault` directly against the SPL Token program, every future `Transfer` sourced from or destined to that vault will be rejected by the token program, which propagates as a CPI failure and aborts the whole Raydium instruction.

### Impact Explanation
Once other unprivileged users have deposited liquidity or swapped into the pool (increasing the vault balances beyond the attacker's own stake), the attacker freezes the vault. This permanently blocks:
- `Withdraw` for every LP (their share of vault tokens is unrecoverable, since `token_transfer_with_authority` from the frozen vault always fails).
- `SwapBaseIn/Out` (V1/V2) for every trader.
- `Deposit` (destination vault transfer fails the same way).

This is a permanent freeze of user/LP funds already locked in the vault, matching the accepted impact bar ("permanent freezing of user or LP funds").

### Likelihood Explanation
The attack requires only standard, unprivileged capabilities already reachable in a single transaction plus one follow-up SPL token instruction:
1. Attacker mints a token with itself as `freeze_authority` (or reuses any token they control the freeze authority of).
2. Attacker calls `Initialize2` as an ordinary pool creator, using that mint as `coin_mint` or `pc_mint` — no check rejects this.
3. Attacker waits for other users to deposit/swap (increasing vault balance), then calls SPL Token `FreezeAccount` on the vault token account using their freeze authority key.

No privileged Raydium signer, leaked key, or malicious validator is needed — only normal pool-creator and mint-authority actions, both explicitly in scope.

### Recommendation
- In `process_initialize2`, reject mints whose `freeze_authority` is `Some(_)` for both `coin_mint` and `pc_mint`, the same way `lp_mint.freeze_authority.is_some()` is already rejected (`program/src/processor.rs` around line 904).
- Alternatively/additionally, provide a privileged or permissionless "pool status" transition (e.g., an `AmmStatus` disabling swaps/deposits and enabling only vault-agnostic accounting) plus a whitelist mechanism for approved coin/pc mints, so that pools cannot be created against tokens capable of freezing transfers.

### Proof of Concept
1. Attacker creates SPL mint `M` with `freeze_authority = attacker`.
2. Attacker calls `Initialize2` (`program/src/processor.rs` `process_initialize2`) with `coin_mint = M`, depositing an initial amount; this succeeds because only `lp_mint.freeze_authority` is checked (`program/src/processor.rs:904-906`), not `coin_mint`/`pc_mint`.
3. A victim LP calls `Deposit` to add liquidity, increasing `amm_coin_vault` balance (`program/src/processor.rs:1327-1340`).
4. Attacker directly invokes SPL Token `FreezeAccount` on `amm_coin_vault` using the `M` mint's freeze authority (outside the Raydium program, but against the vault account owned by `amm_authority`).
5. Any subsequent `Withdraw`/`SwapBaseIn`/`SwapBaseOut` touching `amm_coin_vault` now fails at the `Invokers::token_transfer_with_authority` CPI (`program/src/processor.rs:1787-1795`, `2014-2022`), because the SPL Token program rejects transfers on frozen accounts — permanently trapping the victim LP's and any swapper's funds in the pool.

    /// Issue a spl_token `Transfer` instruction.
    pub fn token_transfer<'a>(
        token_program: AccountInfo<'a>,
        source: AccountInfo<'a>,
        destination: AccountInfo<'a>,
        owner: AccountInfo<'a>,
        deposit_amount: u64,
    ) -> Result<(), ProgramError> {
        let ix = spl_token::instruction::transfer(
            token_program.key,
            source.key,
            destination.key,
            owner.key,
            &[],
            deposit_amount,
        )?;
        solana_program::program::invoke_signed(
            &ix,
            &[source, destination, owner, token_program],
            &[],
        )
    }

    /// Issue a spl_token `Transfer` instruction.
    pub fn token_transfer_with_authority<'a>(
        token_program: AccountInfo<'a>,
        source: AccountInfo<'a>,
        destination: AccountInfo<'a>,
        authority: AccountInfo<'a>,
        amm_seed: &[u8],
        nonce: u8,
        amount: u64,
    ) -> Result<(), ProgramError> {
        let authority_signature_seeds = [amm_seed, &[nonce]];

            token_program.key,
            source.key,
            destination.key,
            authority.key,
            &[],
            amount,
        )?;
        solana_program::program::invoke_signed(
            &ix,
            &[source, destination, authority, token_program],
            signers,
        )
    }
