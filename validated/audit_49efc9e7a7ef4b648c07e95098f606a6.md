### Title
Webhook `shop` (and `topic`/`webhook_id`) tenant-identifying header is not covered by HMAC verification, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` only signs/verifies the raw request body via HMAC, while the tenant-identifying `shop` header that downstream handlers rely on to attribute the webhook to a specific merchant is never part of the signed payload. This breaks the equality that should hold: `shop_used_by_handler == shop_that_was_actually_signed`.

### Finding Description
`Utils::HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string`, and `Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from HTTP headers and are never included in the signed content: [2](#0-1) 

`HmacValidator` only validates the body signature and returns a boolean; it never checks that the `shop` header is consistent with anything cryptographically bound to it: [3](#0-2) 

`Registry.process` then trusts `request.shop` (and `request.topic`) directly, only after confirming the *body* HMAC is valid, and dispatches the handler using that unverified `shop` value as the tenant identity: [4](#0-3) 

Because the signature is computed over the body alone, any `(raw_body, hmac)` pair that was legitimately produced by Shopify for **one** shop remains fully valid when replayed with a **different** `shop` header value. An attacker who operates their own store with the target app installed will legitimately receive real webhook deliveries (body + valid HMAC, computed with the app's real secret by Shopify) for their own shop. They can capture such a request and resend it to the same public webhook endpoint, substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header to name a victim shop, while keeping the original body and HMAC untouched. Verification still succeeds because the HMAC never depended on those headers.

### Impact Explanation
This crosses the tenant boundary the gem is supposed to enforce: an unprivileged party (a merchant of their own store using the same app) can make the host application process attacker-controlled webhook data under another shop's identity (`WebhookMetadata#shop`), since nothing in this library binds the header-derived `shop` to the signed content. Depending on which webhook handlers the host app registers (e.g., `app/uninstalled`, `customers/data_request`, `orders/create`), this can drive cross-tenant state changes, data injection, or data-deletion actions attributed to a shop the attacker does not own — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires no secret knowledge and no compromise of TLS or credentials — only the ability to install the target app on an attacker-controlled/dev store (a normal, unprivileged flow) to obtain one valid `(body, hmac)` pair, then a single crafted HTTP POST with a modified `shop` header to the app's public webhook endpoint. This is low-effort and fully within reach of any external app user.

### Recommendation
Include the tenant-identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the body before trusting them in `Registry.process`. At minimum, `to_signable_string` should incorporate these header values (similar to how `Auth::Oauth::AuthQuery#to_signable_string` folds multiple fields together) so a valid signature can only be produced for the exact `(shop, topic, body)` tuple Shopify actually sent.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook (e.g. `customers/data_request`) and captures the real delivery: raw body `B`, and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's real `api_secret_key`), plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the identical request to the app's public webhook endpoint, keeping `B` and `H` unchanged but replacing the shop header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes `HMAC(B, secret)` and it still equals `H`, so validation passes (`lib/shopify_api/utils/hmac_validator.rb:12-31`).
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host application to process attacker-controlled data as if it belonged to the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
