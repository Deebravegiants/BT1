## Finding

### Title
Webhook shop/topic/id headers are not covered by the HMAC signature, allowing cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request **body**. The `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's webhook handler as the trusted tenant/event identity come from HTTP **headers**, which are never included in the signed bytes. Because the same `api_secret_key` is shared across every shop that has the app installed, any unprivileged merchant who installs the app on their own store can capture a legitimately-signed `(body, hmac)` pair from their own webhook traffic and replay it with the `X-Shopify-Shop-Domain` (and/or topic/webhook-id) header swapped to a victim shop. The signature still validates because it never covered those headers, and the handler is invoked believing the event belongs to the victim tenant.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`HmacValidator.validate_signature` computes and compares the HMAC exactly over that signable string: [2](#0-1) 

`Registry.process` performs this HMAC check and then immediately trusts the header-derived `shop`, `topic`, and `webhook_id` to build the data passed into the app's handler: [3](#0-2) 

Those values are pulled straight from headers with no cryptographic binding to the body: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `hmac_signed_bytes == (shop, topic, webhook_id, body)`. Instead the gem enforces only `hmac_signed_bytes == body`, while `shop` (the tenant key the handler and, typically, the host app's session/tenant lookup will key off of) is taken from an unauthenticated header. This is precisely the "field acted on but not covered by the HMAC" bug class: the header used to select/authenticate the tenant is disjoint from the bytes the HMAC actually protects.

### Impact Explanation
Because `api_secret_key` is the same for the app regardless of which shop it originates from, a normal unprivileged merchant who installs the app on their own store obtains legitimately signed webhook traffic. By replaying that traffic with only the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to a different, victim shop that also has the app installed, the forged request passes `Registry.process`'s HMAC check unchanged and is dispatched to the app's business logic as if it originated from the victim shop. Depending on what the host app's webhook handler does with `WebhookMetadata#shop` (e.g., look up the victim's session/access token, mutate data, process uninstall/GDPR webhooks, trigger order/inventory sync), this enables cross-tenant data access or manipulation without ever needing the victim's credentials — satisfying the Critical "cross-tenant access" impact bar.

### Likelihood Explanation
High. No secret material or privileged access is required — only the ability to legitimately install the app on any shop (a self-service, unprivileged action) and capture one's own valid webhook body+signature, then replay it with a modified `shop`/`topic`/`webhook-id` header. The vulnerable code path (`Registry.process`) is the gem's only enforcement of webhook authenticity, and it is exercised on every inbound webhook the host application forwards to it.

### Recommendation
Include the tenant/event-identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) as part of the HMAC-signed material, or otherwise cryptographically bind them to the verified content (e.g., signing a canonical string of `topic|shop|webhook_id|body` instead of `body` alone), so `HmacValidator.validate` fails if any of those header values are altered after signing.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (normal, unprivileged onboarding).
2. Shopify sends a legitimate webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC of raw body>`
   - Body: `{"id": 1, ...}` (attacker's own order data)
3. Attacker replays the exact same body and `x-shopify-hmac-sha256` value, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com` (a different shop that has the app installed) and re-sends it to the app's webhook endpoint.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `request.to_signable_string` (the unchanged raw body) — validation succeeds.
5. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-supplied `victim-shop.myshopify.com` value and invokes the app's handler as if the event genuinely came from the victim shop. [6](#0-5)
