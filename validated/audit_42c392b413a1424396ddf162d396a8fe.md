Based on my research, I found a concrete integer-overflow analog to the CVE in the Pharos consensus verifier's storage-string decoder, which is on-chain, reachable-by-untrusted-data code analogous to the `aom` bug: an attacker-controlled length value drives buffer-size arithmetic without overflow protection.

### Title
Unchecked integer overflow in Pharos BLS-key string-length arithmetic can panic the on-chain consensus verifier and permanently block the Pharos route - ([File: modules/consensus/pharos/verifier/src/state_proof.rs])

### Summary
`decode_bls_key_from_string_slot` and its sibling `bls_data_slots_from_header` derive a byte length (`str_len`) directly from an untrusted Solidity storage slot value (`header_val`) proven only by a Merkle/SPV proof against the Pharos state root — the *content* of that slot is fully attacker-controlled (any staking-contract validator can set an arbitrarily large string length for their `blsPublicKey` field). This `str_len` is then used in unchecked arithmetic (`(str_len + 31) / 32`) to compute how many 32-byte storage slots to read and how large a `Vec` to allocate, exactly mirroring the `img_alloc_helper` pattern in CVE-2024-5171 where an attacker-controlled dimension drives buffer-size math without overflow checks.

### Finding Description
`decode_u256_from_storage` decodes a raw 32-byte state-proof value into a `U256` with no bound other than "not longer than 32 bytes": [1](#0-0) 

In `decode_bls_key_from_string_slot`, the long-string branch reads that value as `header_val`, computes `str_len = ((header_val - 1) / 2).low_u64() as usize`, and immediately uses it in unchecked addition to compute `slots_needed` and to size a `Vec::with_capacity`: [2](#0-1) 

The same unchecked pattern exists in the standalone helper `bls_data_slots_from_header`, used by `compute_all_storage_keys` to size the storage-key list for an entire validator set: [3](#0-2) 

`header_val` is *not* itself authenticated data with any semantic constraint — it is simply whatever bytes a Pharos staking-contract validator wrote into their own `blsPublicKey` string-length header slot. Any address that can call the staking contract's validator-registration path controls this value completely, and the SPV proof only proves that this (attacker-chosen) byte sequence is present in the tree — it proves nothing about its magnitude being sane. `str_len` can therefore be driven up to (on the `wasm32` runtime target, where `usize` is 32-bit) values close to `u32::MAX`, at which point `str_len + 31` overflows `usize`. Substrate runtimes are conventionally built with arithmetic overflow checks enabled, so this addition panics rather than silently wrapping (the surrounding pallet-ismp/runtime code has no `catch_unwind` around `ConsensusClient::verify_consensus`).

This is invoked from the on-chain `ConsensusClient::verify_consensus`/validator-set update path via `modules/ismp/clients/pharos/src/lib.rs`, which is dispatched from `pallet_ismp::Call::handle_unsigned` — the standard entry point any relayer uses to submit a Pharos consensus/state update, i.e. a single unprivileged, unsigned extrinsic.

### Impact Explanation
A panic inside `verify_consensus`/`decode_validator_set` during block execution (or unsigned-extrinsic validation) aborts that execution path. Because the corrupting length lives in the Pharos staking contract's persistent storage (tied to a specific validator's pool), every subsequent attempt to prove/update that validator epoch will hit the same panic until the malicious validator is somehow purged — effectively making the Pharos consensus route on Hyperbridge permanently unable to ingest new state updates ("a route unable to deliver messages"), since no relayer can successfully deliver a valid consensus proof for an epoch containing the poisoned record.

### Likelihood Explanation
Likelihood is moderate: it requires becoming an active validator (or delegator/pool participant) on the Pharos staking contract and setting a pathological `blsPublicKey` string length — a permissionless, staking-gated action, not an admin/governance/collator privilege. Once set, any relayer submitting the routine epoch/validator-set proof triggers the fault deterministically.

### Recommendation
Replace all unchecked `str_len + 31` / slot-count arithmetic with `checked_add`/`checked_div` (or `saturating_add` followed by an explicit sanity bound), and reject any `str_len` above a small hard maximum (e.g. 128 bytes, consistent with the expected 96–98 character BLS hex string) before doing any further slot-count or `Vec::with_capacity` computation, in both `decode_bls_key_from_string_slot` and `bls_data_slots_from_header`.

### Proof of Concept
1. On the Pharos L2, call the staking contract to register/update a validator whose `blsPublicKey` string storage slot header is a "long string" marker (`lowest_byte & 1 == 1`) encoding a length value such that `low_u64() as usize` is within `[u32::MAX - 30, u32::MAX]` (achievable by writing an arbitrarily large odd `header_val`, e.g. via a custom validator field with attacker-controlled storage, since only the header parity and magnitude matter to this decoder).
2. Wait for/trigger a Pharos epoch snapshot including this validator, then have any relayer submit the epoch validator-set proof through `pallet_ismp::Call::handle_unsigned`, which routes into `PharosConsensusClient::verify_consensus` → `decode_validator_set` → `decode_bls_key_from_string_slot`.
3. The addition `str_len + 31` in [4](#0-3)  overflows `usize` and panics (overflow-checked runtime build), aborting the extrinsic/block execution and permanently blocking further Pharos consensus updates that reference the same corrupted validator record.

pub fn bls_data_slots_from_header(header_value: &[u8]) -> Result<usize, Error> {
	let header_val = decode_u256_from_storage(header_value)?;
	let header_bytes = header_val.to_big_endian();
	let lowest_byte = header_bytes[31];

	if lowest_byte & 1 == 0 {
		// Short string - data is in the header itself
		Ok(0)
	} else {
		// Long string - header = length * 2 + 1
		let length = (header_val - 1) / 2;
		let str_len = length.low_u64() as usize;
		Ok((str_len + 31) / 32)
	}
}

/// Decode a U256 value from raw big-endian storage bytes.
pub fn decode_u256_from_storage(value: &[u8]) -> Result<U256, Error> {
	if value.is_empty() {
		return Ok(U256::zero());
	}

	if value.len() <= 32 {
		let mut padded = [0u8; 32];
		padded[32 - value.len()..].copy_from_slice(value);
		Ok(U256::from_big_endian(&padded))
	} else {
		Err(Error::StorageValueTooLarge)
	}
}
