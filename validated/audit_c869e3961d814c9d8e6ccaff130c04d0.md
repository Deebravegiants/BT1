### Title
Cross-chain order relayer fees can be permanently frozen when `EvmHost.feeToken` is updated between order placement and settlement - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2` escrows a user's relayer-fee payment in whatever `feeToken` is active on `EvmHost` at `placeOrder` time, but releases those fees at settlement by re-reading `IDispatcher(host()).feeToken()` fresh. If governance updates the host's `feeToken` via `updateHostParams` while an order is still pending, the escrow (denominated in the old token) and the release call (denominated in the new token) diverge, causing the entire settlement to revert and permanently freeze both the escrowed fee and the order's principal input/output tokens.

### Finding Description
`placeOrder` escrows the user's relayer fee using the fee token that is current *at placement time*: [1](#0-0) 

```solidity
if (order.fees > 0) {
    address feeToken = IDispatcher(hostAddr).feeToken();
    ...
    IERC20(feeToken).safeTransferFrom(msg.sender, address(this), order.fees);
    _orders[commitment][TRANSACTION_FEES] = order.fees;
}
```

`_orders[commitment][TRANSACTION_FEES]` records only an *amount*, not which token was escrowed — the token identity is implicit and tied to whatever `feeToken()` returned at that moment.

At settlement, `_withdraw` (shared by fill/redeem/cancel-refund paths) re-reads the *current* `feeToken()` instead of the token that was actually escrowed: [2](#0-1) 

```solidity
if (finalize) {
    uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
    if (fees > 0) {
        delete _orders[body.commitment][TRANSACTION_FEES];
        IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
    }
    ...
}
```

`EvmHost.updateHostParamsInternal` only guards against changing `feeToken` while *the host itself* still holds a balance of the old token — it does not know about, and cannot protect, balances escrowed by downstream `IApp` contracts like `IntentGatewayV2`: [3](#0-2) 

```solidity
address oldFeeToken = feeToken();
if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
    uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
    if (balance != 0) revert CannotChangeFeeToken();
}
...
_hostParams.feeToken = params.feeToken;
```

Consequently, governance can freely change `feeToken` (this is a normal, expected `updateHostParams` operation reachable via `HostManager.onAccept` → `SetHostParam`) as soon as the host's own balance of the old token is zero, even though `IntentGatewayV2` is holding real user fee escrows denominated in that old token. This is structurally identical to the PirexRewards defect: two independent, desynchronizable sources of truth for a "reward/fee token," where a legitimate configuration change (not malicious intent) on one component silently invalidates state recorded by another, and the affected balance is deleted/finalized on the assumption the transfer will use the *same* token that was originally escrowed.

### Impact Explanation
Because `_withdraw` decrements/deletes `_orders[commitment][TRANSACTION_FEES]` and then immediately calls `safeTransfer` on the *new* fee token, and this happens inside the same atomic call that also releases the order's principal input/output tokens and marks `_filled[commitment]`, an insufficient balance/allowance of the new token causes `safeTransfer` to revert, which reverts the entire `_withdraw` call. This means:
- The order can never be finalized (fill, redeem, or refund) again through the ordinary path — the principal escrow (potentially far larger than the fee) becomes permanently stuck in the contract, and `_filled` is never set.
- This is a genuine permanent freezing of user funds triggered by a single, reachable, non-malicious configuration update (`updateHostParams` changing `feeToken`), affecting any order placed with `order.fees > 0` that is still pending when the change occurs.

### Likelihood Explanation
`feeToken` rotation is an explicitly supported, expected governance operation (`HostParams.feeToken`, `updateHostParams`, `CannotChangeFeeToken` guard exists specifically to allow rotation once the host's own balance is drained). Any live deployment with outstanding intent orders at the time of a fee-token rotation will trip this bug — it requires no attacker, just the intersection of two legitimate, independently-reachable operations (placing an order, and later rotating the fee token), matching the "mismanagement" root cause called out in the source report.

### Recommendation
Snapshot the escrowed fee's token identity at `placeOrder` time (e.g., store it alongside the amount, or key `_orders` fee storage by the actual token address used) rather than re-deriving it from the host's current `feeToken()` at settlement time. Alternatively, have `EvmHost.updateHostParamsInternal` require that all registered `IApp` fee-token balances are drained (or provide a migration path) before permitting a `feeToken` change, so stale escrows in downstream apps cannot be orphaned.

### Proof of Concept
1. User calls `placeOrder` with `order.fees = X` while `EvmHost.feeToken() == TokenA`. Contract escrows `X` `TokenA` into `_orders[commitment][TRANSACTION_FEES]`.
2. Before the order is filled/cancelled, Hyperbridge governance dispatches a `SetHostParam` request via `HostManager.onAccept` → `EvmHost.updateHostParams` changing `feeToken` from `TokenA` to `TokenB` (allowed since the host itself holds zero `TokenA`).
3. A solver later fills the order (or the user cancels it after expiry). The settlement path calls `IntentsBase._withdraw(..., finalize: true)`, which deletes `_orders[commitment][TRANSACTION_FEES]` and calls `IERC20(TokenB).safeTransfer(beneficiary, X)`.
4. `IntentGatewayV2` holds no (or insufficient) `TokenB` for this purpose — `safeTransfer` reverts, reverting the whole `_withdraw` call, including the release of the order's principal input/output tokens and the `_filled` write.
5. The order can never be completed; its escrowed principal and fee are permanently stuck.
