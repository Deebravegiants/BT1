### Title
Webhook Shop-Domain Spoofing via HMAC Coverage Gap Enabling Cross-Tenant Webhook Injection - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (tenant identifier) from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies only covers the raw request body. This reproduces the "storage collision" bug class from the report: a field that is *acted upon* by downstream logic (`shop`) is not part of the cryptographically committed data (the HMAC-signed bytes), so the binding `shop_authenticated == shop_used_as_tenant_key` silently breaks.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the (spoofable) header, entirely independent of the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC solely via `Utils::HmacValidator.validate(request)`, which calls `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., only the body is checked — and then forwards `request.shop` unchanged into the handler payload: [3](#0-2) [4](#0-3) 

Because a single app-level `api_secret_key` is shared across *all* shops that install the app (this is standard/documented Shopify app architecture: the HMAC merely proves "this body was signed by an entity holding this app's secret," not "this body belongs to shop X"), an attacker who legitimately controls or has been granted access to one installed shop (Shop A, an unprivileged tenant relative to Shop B) can:
1. Trigger any real webhook event in Shop A (e.g. update a product), obtaining a genuinely valid `(raw_body, hmac)` pair signed with the shared `api_secret_key`.
2. Replay that exact `raw_body` and `hmac` to the app's webhook endpoint, but substitute `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `HmacValidator.validate` still returns `true`, because the header is never part of `to_signable_string`.
4. `Registry.process` hands the handler a `WebhookMetadata` claiming `shop: "shop-b.myshopify.com"` with attacker-chosen body content, even though Shop A produced it.

This is the exact analog to the report's storage-collision class: `DiamondCutStorage`/`UpgradeStorage` size mismatch let unrelated data silently alias into privileged slots; here, the `shop` field silently aliases across tenants because it sits outside the HMAC's "storage layout" (signed byte range).

### Impact Explanation
Any handler that trusts `WebhookMetadata#shop` to look up/act on per-tenant records (the intended and only documented use of this field) can be made to write, delete, or process attacker-supplied data under a victim shop's identity — a cross-tenant access/data-integrity break, without needing the victim's or the app's `client_secret`/access token. This matches the Critical "cross-tenant access" impact bucket.

### Likelihood Explanation
Exploitation requires only: (a) being an installed, even unprivileged, tenant of the same multi-tenant app (a normal merchant account, not a privileged Shopify/app-owner credential), and (b) the ability to trigger any webhook-eligible action in one's own shop and replay the HTTP request with one header rewritten. No secret material needs to be known or guessed. Likelihood is high wherever an app registers webhooks and lets handler logic key off `WebhookMetadata#shop` — which is the library's documented pattern (`handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))`).

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value verified by the HMAC, e.g., require handlers to independently confirm the shop belongs to an active `Session`/install record before trusting `request.shop`, or extend `to_signable_string` semantics so the library explicitly documents that `shop`, unlike `body`, is unauthenticated header data and must be revalidated by the consumer against known installed shops before use.

### Proof of Concept
```ruby
# 1. Attacker (merchant of shop-a.myshopify.com) captures a real webhook fired by their own store
raw_body = '{"id": 123, "note": "attacker-controlled"}'
hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# 2. Attacker replays it, swapping only the shop-domain header to a victim tenant
spoofed_headers = {
  "x-shopify-topic" => "products/update",
  "x-shopify-hmac-sha256" => hmac,
  "x-shopify-shop-domain" => "shop-b.myshopify.com", # victim tenant, not the attacker's shop
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: spoofed_headers)

ShopifyAPI::Utils::HmacValidator.validate(request) # => true, HMAC only covers raw_body
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle receives WebhookMetadata(shop: "shop-b.myshopify.com", body: attacker-controlled)
# even though the signature was produced from shop-a's genuine traffic.
```

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
