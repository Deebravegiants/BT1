### Title
Webhook `shop` identity is trusted from an HMAC-unsigned header, enabling cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body [1](#0-0) . The `shop` value that identifies which merchant/tenant the event belongs to is read straight from the `shop-domain` HTTP header and is never included in the signed payload [2](#0-1) . Because `to_signable_string` returns only `@raw_body`, the HMAC binds the body's authenticity but not the header-derived `shop`, `topic`, `api_version`, or `webhook_id` fields [3](#0-2) .

### Finding Description
The identity binding that should hold is: `shop attributed to event == shop that produced the HMAC-signed body`. Since Shopify apps typically share a single `api_secret_key` across all installed shops (not a per-shop secret), any shop that has installed the app can generate a fully valid `(raw_body, hmac)` pair for its own legitimate webhook event (e.g., by creating an order or updating a product it controls, including attacker-influenced string fields in that body). That merchant can then replay this valid body+HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value naming a *different* installed shop. `HmacValidator.validate` will pass because the body signature is untouched [4](#0-3) , yet `Registry.process` hands the handler a `WebhookMetadata` claiming the event came from the victim shop [5](#0-4) .

Before attacker action: `event.shop == body.origin_shop` holds by construction of legitimate traffic.
After attacker's crafted request: `event.shop (victim) != body.origin_shop (attacker's own shop)`, yet the gem's `process` accepts it as authentic for the victim shop, since only the body bytes are verified, not the shop binding.

### Impact Explanation
Any host application that keys per-tenant state, authorization decisions, deduplication, or data writes off `WebhookMetadata#shop` (the officially exposed field for this exact purpose) can be made to attribute attacker-controlled webhook content to an arbitrary other tenant shop of the same app. This is a cross-tenant data/state confusion vulnerability carried entirely by the app's own trusted credential (the shared `api_secret_key`), reachable by any unprivileged merchant who has installed the app on their own store — no access to the victim's credentials or any privileged access to the app's infrastructure is required.

### Likelihood Explanation
Exploitability requires only: (1) installing the target app on a shop the attacker controls (a standard, unprivileged action for any Shopify user), and (2) the ability to send an HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header, which is trivial once a valid `(body, hmac)` pair from the attacker's own shop is captured. No secret, token or elevated privilege belonging to the victim or the app operator is needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is cryptographically verified, e.g., by including the relevant headers in `to_signable_string`, or explicitly documenting/enforcing that consumers must cross-check `request.shop` against a shop known to be currently authorized/installed rather than trusting it as tenant-authenticated purely because the body HMAC passed. At minimum, `Registry.process` should not implicitly treat `request.shop` as an authenticated tenant identifier when only the body is what's HMAC-verified.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, obtaining the app's shared webhook secret behavior transparently (they never see the secret — Shopify signs their own webhook automatically).
2. Attacker triggers a real webhook event (e.g., updates a product) causing Shopify to POST a legitimately HMAC-signed `(raw_body, hmac)` to the app's webhook endpoint, with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures this valid request, then re-sends it directly to the app's webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` unchanged but replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `@raw_body` using the app's `api_secret_key` and it matches, since the body was untouched [6](#0-5) .
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: <attacker-controlled parsed body> ...)` [5](#0-4) , causing the host app to process attacker-controlled content under the victim shop's tenant identity.
