### Title
Unbounded ancestry walk in GRANDPA justification verification permits attacker-induced infinite loop - ([File: modules/consensus/grandpa/primitives/src/justification.rs])

### Summary
`AncestryChain::ancestry` in `modules/consensus/grandpa/primitives/src/justification.rs` walks a chain of `parent_hash` pointers built entirely from attacker-supplied headers (`votes_ancestries` / `unknown_headers` in a submitted GRANDPA `ConsensusMessage`), with no visited-set/loop-guard and no bound on iteration count. If the attacker-supplied header set contains a cycle that never reaches `base`, the `while current_hash != base` loop never terminates — the same bug class as CVE-2018-5818's `parse_rollei()` infinite loop from unvalidated attacker input.

### Finding Description
`AncestryChain` is constructed directly from relayed data: [1](#0-0) 

The walk that consumes it has no cycle detection: [2](#0-1) 

Each iteration only checks whether `current_hash` is present in the attacker-provided `ancestry` map; if present, it advances to that header's declared `parent_hash` and pushes it onto `route`. There is no set of already-visited hashes and no maximum-hop bound. An attacker can submit two or more headers whose `parent_hash` values point to each other, forming a cycle entirely contained within the map, such that `base` is never encountered. Every iteration finds a hit in the `BTreeMap` (`Some(current_header)`), so the loop keeps advancing around the cycle forever instead of ever returning `Err(NotDescendent)`.

This function is called from `GrandpaJustification::verify_with_voter_set` (walking `votes_ancestries` per precommit) at [3](#0-2)  and from `verify_grandpa_finality_proof` (walking `unknown_headers`) at [4](#0-3) , both of which are reached from `GrandpaConsensusClient::verify_consensus`, the entry point invoked when a relayed GRANDPA consensus proof (`ConsensusMessage::StandaloneChain`/`Relaychain`/`Polkadot`) is submitted: [5](#0-4) 

`verify_consensus` decodes the entire `ConsensusMessage` (including `votes_ancestries`/`unknown_headers`) straight from relayer-controlled bytes with only structural/decoding checks before any ancestry walk — there is no cycle validation anywhere upstream.

### Impact Explanation
Any relayer/unprivileged submitter of a GRANDPA consensus update (an externally-relayed proof processed through pallet-ismp's consensus-update path) can craft a header set with a `parent_hash` cycle and cause `verify_consensus` to spin forever. Because this executes inside the on-chain STF as part of validating/consuming a submitted consensus proof, it results in denial of service to block/transaction processing for the GRANDPA light client path — a route unable to deliver messages/consensus updates, which per the validation rules qualifies as impact (a route rendered unable to deliver messages). This blocks all IBC/ISMP traffic relying on that GRANDPA-based consensus client until intervention.

### Likelihood Explanation
High. The attacker only needs to submit a single crafted consensus proof containing a header cycle (e.g., two dummy headers `A.parent_hash = B.hash()`, `B.parent_hash = A.hash()`), which requires no signatures over the ancestry headers themselves — `AncestryChain` accepts any headers in `unknown_headers`/`votes_ancestries` regardless of whether they are cryptographically tied to real chain state at the point the ancestry walk runs (the ancestry walk happens before/alongside other checks). This is a straightforward, cheap, one-shot DoS with no privileged access required.

### Recommendation
Bound the `ancestry` walk: track visited hashes and return `Err(NotDescendent)` (or a dedicated cycle error) as soon as a hash is revisited, and/or cap the loop by `self.ancestry.len() + 1` iterations. This guarantees termination regardless of attacker-supplied `parent_hash` graphs, mirroring the fix pattern already applied elsewhere in this codebase for proof-depth bounding (e.g. `MAX_PROOF_DEPTH` in `modules/consensus/pharos/primitives/src/spv.rs`).

### Proof of Concept
1. Construct two `SubstrateHeader`s, `H1` and `H2`, with `H1.parent_hash = H2.hash()` and `H2.parent_hash = H1.hash()` (a two-node cycle), and neither hash equal to `base`.
2. Package `H1`, `H2` as `unknown_headers` in a `FinalityProof` (or as `votes_ancestries` in a `GrandpaJustification`), with a `target` header chained to `H1`/`H2` and any syntactically-valid commit/justification bytes needed to pass earlier decode/shape checks.
3. Submit this as the proof to `GrandpaConsensusClient::verify_consensus` (i.e., relay it as a GRANDPA `ConsensusMessage`).
4. `AncestryChain::new(&unknown_headers)` builds a map containing `H1`/`H2`; the subsequent `.ancestry(base, target.hash())` call in `verify_grandpa_finality_proof` (or inside `GrandpaJustification::verify_with_voter_set`) enters the `while current_hash != base` loop, cycles between `H1.hash()` and `H2.hash()` indefinitely, and never returns — hanging the calling node/runtime execution.

	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
