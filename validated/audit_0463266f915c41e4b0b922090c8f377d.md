### Title
Observable Response Discrepancy on Admin/API Login Enables Email Enumeration - (File: core/web/sessions_controller.go, core/sessions/localauth/orm.go)

### Summary
The `/sessions` login endpoint returns the raw underlying authentication error message to the unauthenticated caller. Depending on whether the submitted email exists, the response body differs ("sql: no rows in result set" / no-user error vs. `"Invalid password"`), allowing an unprivileged actor to enumerate valid Chainlink node user accounts, analogous to CVE-2023-39343 in Sulu.

### Finding Description
`SessionsController.Create` forwards the authentication provider's error verbatim to the HTTP client: [1](#0-0) 

For the local auth provider, `CreateSession` first looks up the user, then checks email and password separately, returning **different, distinguishable errors** for each failure mode: [2](#0-1) 

`FindUser` (called first) simply passes through the sqlx `GetContext` error (e.g. `sql.ErrNoRows`) when no user matches the email: [3](#0-2) 

So:
- Unknown email → error propagated from `FindUser` (distinct DB "no rows" style message)
- Known email, wrong password → `pkgerrors.New("Invalid password")` at line 161

Both are surfaced unmodified as the JSON error body via `jsonAPIError(c, http.StatusUnauthorized, err)` in `sessions_controller.go:58`, giving the client an oracle to distinguish "user exists" vs. "user doesn't exist."

The same discrepancy pattern exists in the LDAP provider's local-admin fallback path, which also returns distinct `"invalid email"` vs `"invalid password"` errors that get returned the same way when local fallback is used: [4](#0-3) 

### Impact Explanation
This is a username/email enumeration vulnerability on the node's admin login form (`POST /sessions`), reachable by any unauthenticated network client without any privileges. An attacker can iterate over candidate email addresses and determine which ones correspond to real Chainlink node operator accounts, which then become high-value targets for credential stuffing, phishing, or brute-force password attacks against the admin API. This matches CWE-204 (Observable Response Discrepancy) and the CVSS vector in the reference advisory (`AV:N/AC:L/PR:L/UI:N/C:L`), i.e., a confidentiality-only disclosure of account existence, not a full account/auth bypass.

### Likelihood Explanation
High likelihood of exploitation: no authentication or special access is required, the endpoint is unauthenticated by design (`unauth.POST("/sessions", sc.Create)` in `core/web/router.go:215`), and the differing error strings are returned directly in the JSON response body with no rate-limiting bypass needed beyond the existing unauthenticated rate limiter.

### Recommendation
Normalize the error path in `orm.CreateSession` (and the LDAP `localLoginFallback` equivalent) so that "user not found" and "password mismatch" produce the same generic error (e.g., `"invalid credentials"`) before returning to `SessionsController.Create`, and ensure timing is constant-time across both branches (similar to the existing `constantTimeEmailCompare` already used for the email check) to avoid a timing side channel replacing the message side channel. Avoid using `jsonAPIError(c, ..., err)` with the raw provider error; map to a single generic unauthorized message at the controller boundary instead.

### Proof of Concept
1. `POST /sessions` with `{"email":"unknown@nowhere.test","password":"x"}` → response body contains the raw `FindUser`/DB error (e.g., mentions no matching row).
2. `POST /sessions` with `{"email":"<real-admin-email>","password":"wrong"}` → response body contains `"Invalid password"`.
3. Compare the two responses — the differing error text (or underlying error type) lets the attacker confirm the second email is a valid, registered node user, as demonstrated by the existing test cases in `core/web/sessions_controller_test.go:39-40` which already exercise both "incorrect pwd" and "incorrect email" cases separately and could be adapted to assert response-body equality (currently they only assert status code ≥ 400, not message parity).

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}

// localLoginFallback tests the credentials provided against the 'local' authentication method
// This covers the case of local CLI API calls requiring local login separate from the LDAP server
func (l *ldapAuthenticator) localLoginFallback(ctx context.Context, sr sessions.SessionRequest) (sessions.User, error) {
	var user sessions.User
	sql := "SELECT * FROM users WHERE lower(email) = lower($1)"
	err := l.ds.GetContext(ctx, &user, sql, sr.Email)
	if err != nil {
		return user, err
	}
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		l.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return user, errors.New("invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		l.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return user, errors.New("invalid password")
	}

	return user, nil
}
