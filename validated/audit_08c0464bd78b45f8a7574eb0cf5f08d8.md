### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the HMAC over the raw request body only. The `shop-domain` header — which the gem trusts as the tenant identity and forwards to the app's handler — is never included in the signed data. Any party who can obtain one legitimately-signed `(body, hmac)` pair from Shopify (e.g. by installing the app on their own low-privilege store, since Shopify webhooks for all merchants of an app are signed with the same `api_secret_key`) can replay that pair to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header, and the signature check will still pass.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an attacker-controllable HTTP header, entirely outside the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` verifies only `verifiable_query.to_signable_string` against the HMAC, i.e. only the body: [3](#0-2) 

`Registry.process` performs this HMAC check and then immediately trusts `request.shop` as the tenant identity, forwarding it to the app's handler without any additional binding to the signed content: [4](#0-3) 

`WebhookMetadata#shop` is a plain `String` field consumed by every app-provided `WebhookHandler#handle`: [5](#0-4) 

**Identity binding broken (as an equality):** the gem implicitly assumes
`hmac_verified(body) == true` implies `shop_header == the_shop_that_shopify_actually_sent_this_body_for`.
In reality the HMAC only proves `hmac == HMAC(secret, body)`; it says nothing about which shop the body/header pair is associated with. Because Shopify signs every merchant's webhooks with the *same* app-level `api_secret_key`, a party controlling any installed instance of the app (their own, unprivileged store) can:
1. Receive a legitimate webhook `(body_A, hmac_A)` for their own shop `shop-domain: A`.
2. Replay `body_A`/`hmac_A` to the app's webhook endpoint but set `x-shopify-shop-domain: B` (a victim tenant).
3. `HmacValidator.validate` succeeds (body/hmac unchanged), `Registry.process` proceeds, and the handler executes with `shop: "B"`.

This lets an attacker with no privileges on the victim's shop inject attacker-chosen webhook content (subject to what the attacker's own store's data can contain, e.g. an `orders/create` or `customers/create` payload with attacker-controlled fields) that the app processes and persists/acts upon as if it belonged to shop B — a cross-tenant data-integrity/authentication-boundary violation.

### Impact Explanation
This crosses a tenant boundary: an app built on this gem cannot distinguish "verified body for the wrong shop" from "legitimate event for the claimed shop," because the shop identity used for record association is unauthenticated relative to the signature. Depending on what the host app's `WebhookHandler` does with `data.shop` (e.g., look up/create records keyed by shop, trigger emails, update inventory, mark orders), this can result in cross-tenant data injection or corruption. This matches the "Critical - cross-tenant access" impact category defined in scope.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target app on any store (the attacker's own, unprivileged store), which yields a valid `(body, hmac)` pair signed with the app's shared secret; and (2) the ability to send an arbitrary HTTP request to the app's public webhook receiver endpoint with a spoofed `x-shopify-shop-domain` header — something entirely within reach of an unprivileged internet user, since no access-token, TLS interception, or victim credentials are needed. Likelihood is high wherever the host app relies solely on this gem's `Registry.process`/`HmacValidator` for both authenticity and tenant attribution (which the gem's own docs and code structure encourage).

### Recommendation
Include the shop/tenant identity (and ideally topic/webhook-id) in the data that is cryptographically bound to the HMAC, or otherwise independently verify that `request.shop` corresponds to a shop for which the app holds a valid, previously-established session/installation before trusting it in `WebhookMetadata`. At minimum, document prominently that `Request#shop` is unauthenticated and must be cross-checked by the host application against known installed shops before use.

### Proof of Concept
```ruby
# Attacker installs the target app on their own shop "attacker-shop.myshopify.com"
# and captures a legitimately-signed webhook, e.g. for "orders/create":
raw_body = '{"id":1,"malicious_field":"payload"}'
hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body)
)

# Attacker replays the same body/hmac pair to the app's public webhook endpoint,
# but swaps the shop-domain header to the victim's shop:
POST /webhooks HTTP/1.1
Host: victim-app.example.com
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <hmac captured above>
x-shopify-shop-domain: victim-shop.myshopify.com   # spoofed, not covered by hmac
x-shopify-webhook-id: <any>
x-shopify-api-version: 2024-01

{"id":1,"malicious_field":"payload"}
```
`ShopifyAPI::Webhooks::Registry.process` will call `Utils::HmacValidator.validate`, which passes because it only checks `raw_body` against `hmac`: [4](#0-3) 
The handler then receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {...}, ...)`, causing the host app to process attacker-controlled data as if it originated from the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
