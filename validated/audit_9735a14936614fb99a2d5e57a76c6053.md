### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then dispatches to the app's handler using the `shop` value taken from the unauthenticated `X-Shopify-Shop-Domain` header. Because the header is not part of the signed material, an attacker who controls a shop where the app is installed (and therefore legitimately receives genuinely-signed webhooks for that shop) can replay a captured `body + hmac` pair while substituting the `shop-domain` header for a victim shop, and the request will still pass HMAC validation.

### Finding Description
The HMAC binding only covers the JSON body: [1](#0-0) 

while the tenant-identifying `shop` and other fields come from headers that are never included in the signable string: [2](#0-1) 

`HmacValidator.validate` verifies exactly the bytes returned by `to_signable_string` (the raw body) against the secret-derived signature — it says nothing about which headers accompanied that body: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof of the webhook's origin, then trusts `request.shop` (from the unauthenticated header) to route/attribute the payload to a tenant: [4](#0-3) 

The broken binding is: `HMAC-verified-bytes == raw_body` but `identity-acted-upon == shop-domain-header`, and these are not the same thing. Any party that can obtain one genuinely-signed `(raw_body, hmac)` pair for a shop they control — trivial, since anyone can install a public app on their own free/dev store and thereby receive Shopify-signed webhooks for it — can resend that exact body/HMAC pair to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header changed to a victim shop domain that also has the app installed. `HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This breaks the shop/tenant identity binding at the point where the gem hands verified data to the host application, i.e., a merchant-facing app is told "this payload with this body is authoritative data for shop V" when it is actually attacker-controlled data associated with shop A. Depending on how the host app uses the topic/body (e.g., updating order/customer state, GDPR/compliance actions, billing, uninstall/reinstall triggers), this enables cross-tenant data confusion — writing attacker-controlled content into another merchant's app state.

### Likelihood Explanation
Exploitation only requires the attacker to control a shop that has the target app installed (freely obtainable via a Shopify dev/partner store) — no access to `api_secret_key`, access tokens, or the target's credentials is needed. This is a realistic, unprivileged path, matching the "restricted function misses cases" bug class: the code trusts a field that looks bound but isn't actually covered by the verification it relies on.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-covered material, or otherwise cryptographically bind the header-derived identity to the signed body before dispatching to handlers — e.g., verify that the `shop` header matches a shop known to have an active install/session before trusting it, rather than accepting it purely because the body's HMAC validates.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they control), and Shopify sends a real webhook, e.g. `orders/create`, with a genuinely computed `X-Shopify-Hmac-Sha256` for the JSON body.
2. Attacker captures `raw_body` and its valid `hmac` value.
3. Attacker crafts a new HTTP request to the app's webhook endpoint using the same `raw_body`/`hmac`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (a real shop that also has the app installed).
4. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against the secret.
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)` and invokes the app's handler, which now processes attacker-controlled data as if it originated from the victim shop.
