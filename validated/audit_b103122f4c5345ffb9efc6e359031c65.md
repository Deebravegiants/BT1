This confirms the finding. The docs explicitly state `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md` line 125), and `data.shop` is documented as "The shop domain of the webhook" (`docs/usage/webhooks.md` line 14) — implying it is a trusted, verified value that host apps use as the tenant identifier, exactly as `WebhookHandler.handle` example does (`shop_domain: data.shop`, line 26). But the HMAC only covers the raw body, never the shop domain header.

### Title
Webhook `shop` field is not covered by HMAC signature, allowing cross-tenant shop-domain spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's HMAC over the raw request body only. The `shop` (and `topic`/`webhook_id`/`api_version`) values, which are taken directly from HTTP headers, are never included in the signed content. Any actor who can produce one legitimately-signed webhook body (e.g., a merchant who has installed the app on their own store and thus can trigger genuine, correctly-HMAC'd webhook deliveries) can replay that same body to the app's webhook endpoint with an arbitrary, attacker-chosen `X-Shopify-Shop-Domain` header, and the HMAC check will still pass.

### Finding Description
`ShopifyAPI::Webhooks::Request` builds `to_signable_string` from only the raw body: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC solely against `to_signable_string`, i.e., the raw body, using the app's `api_secret_key`: [2](#0-1) 

`Registry.process` only checks this body HMAC before dispatching to the handler, then passes the unauthenticated `request.shop` header value straight through as the tenant identifier: [3](#0-2) 

`Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the HMAC-verified content and no validation via `ShopValidator`: [4](#0-3) 

The equality that should hold is: `shop value verified by HMAC == shop value acted upon by the handler`. In this implementation, `shop value verified by HMAC` is undefined (the HMAC only binds the body), while `shop value acted upon` is an attacker-controlled header. Because the same app secret is shared across every shop that installs the app, a malicious merchant can generate a fully valid HMAC over any body they want (from their own store's genuine webhook traffic) and then freely substitute the `shop-domain` header when relaying it to the app's public webhook endpoint.

### Impact Explanation
This breaks the tenant-isolation boundary the library's own documentation promises: `data.shop`, "the shop domain of the webhook," is presented as trustworthy input for consumers (`docs/usage/webhooks.md`), and the host application typically uses it as a lookup key for the shop's session/tenant record. An attacker can cause the app to process and store attacker-supplied data (order/customer/product payloads from their own shop) under a victim shop's identity, corrupting or injecting data into another tenant's context — a cross-tenant data integrity/isolation violation.

### Likelihood Explanation
Any developer who follows the documented `WebhookHandler` pattern and trusts `data.shop` as an authenticated value (as the docs' own example implies) is exposed. Producing a validly-signed body requires nothing more than installing the app on one's own store — a routine action available to any user, not a privileged credential.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed content (or otherwise cryptographically bind them to the request), or at minimum, cross-check `request.shop` against a known/registered shop record before trusting it, and document clearly that `shop` is unauthenticated header data if it cannot be bound to the signature.

### Proof of Concept
1. App merchant "Attacker" installs the target app on `attacker-shop.myshopify.com`.
2. Shopify sends attacker a legitimately signed `orders/create` webhook: body `B`, HMAC `H = HMAC(secret, B)`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays `POST /callback/orders/create` to the app's public endpoint with the same body `B` and the same valid `hmac-sha256: H`, but changes the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) succeeds because it only checks `B` against `H`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the app's handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled body `B`, which the app persists/acts upon as if it were genuine data from the victim shop.
