### Title
Unchecked `message.from` length in `HyperFungibleToken::on_accept` causes a runtime panic (DoS) on cross-chain token transfers with calldata - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
The `IsmpModule::on_accept` handler for the hyper-fungible-token pallet decodes an ABI-encoded `Message` from an incoming `PostRequest` body and, when the message carries calldata with no signature, derives the calldata's dispatch `origin` from `message.from` without validating its length before slicing or copying it into a fixed-size buffer. This mirrors the ALPINE-CVE-2020-36229 bug class: a field from untrusted/relayed input is parsed with an implicit fixed-length assumption, and a malformed length triggers a runtime trap instead of a typed error.

### Finding Description
In the calldata-without-signature branch: [1](#0-0) 

```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
```

Two unchecked-length operations are present:
- `from_bytes.len() - 20` — if `from_bytes.len() < 20`, this subtraction underflows a `usize`. In a debug/overflow-checked build this panics directly; in a release build the wrapped huge value is then used to index `from_bytes[...]`, which panics as an out-of-bounds slice.
- `account.copy_from_slice(from_bytes)` — `copy_from_slice` panics unless `from_bytes.len()` is exactly 32.

This is the same class of defect the codebase has explicitly hardened elsewhere: `StateMachine::from_str`'s `copy_from_slice` was patched to check length first specifically because "the wasm trap [is] reachable from untrusted input", and similar unchecked-length crashes were fixed in the Ethereum trie decoder, the GRANDPA verifier, the pharos SPV verifier, and the sync-committee verifier: [2](#0-1) [3](#0-2) 

Unlike those sites, `message.from` in `hyper-fungible-token/src/module.rs` was never given an explicit length check before the slice arithmetic / `copy_from_slice`, even though `message.to` (a few lines above, lines 63-71) *is* validated for exactly 32/20 bytes with a typed `HftError::InvalidRecipientLength` before use — showing the missing check on `from` is an inconsistency/oversight rather than an intentional invariant.

`message` (including `from`) is ABI-decoded straight from the request `body`: [4](#0-3) 

`on_accept` is the pallet-ismp routed callback invoked once a relayer submits a proven `PostRequest` targeting this module; the module only authenticates the *source contract address* via `ContractToAsset`, not the byte-length of the embedded `from` field: [5](#0-4) 

### Impact Explanation
A malformed/short `from` field (reachable whenever the message's `data` is non-empty and no `signature` is supplied) causes the runtime to panic during extrinsic execution of `handle_unsigned`/message delivery, aborting the whole batch of ISMP messages being processed in that call and denying delivery of legitimate token transfers and other batched requests. This is a Hyperbridge message-delivery route becoming "unable to deliver messages" — one of the explicitly accepted high-impact outcomes for this scan.

### Likelihood Explanation
The check on `to` shows the pallet author intended to validate untrusted length fields but missed doing the same for `from`. Reaching this code only requires a submitted `PostRequest` with non-empty `data` (no signature) and a `from` field whose length is not 20 (EVM source) or not exactly 32 (non-EVM source) bytes — a low-effort, cheaply constructed payload for whichever party encodes the ABI message on the source side.

### Recommendation
Validate `message.from`'s length up front (mirroring the existing `HftError::InvalidRecipientLength` pattern used for `message.to`) and return a typed error instead of calling `copy_from_slice`/slicing when the length does not match the expected 20 or 32 bytes.

### Proof of Concept
1. Craft a `Message` (per `modules/pallets/hyper-fungible-token/src/types.rs`) with `data` non-empty, `signature = None`, and `from` set to a byte string of length ≠ 20 (e.g. 3 bytes) when the request `source` is an EVM state machine.
2. Have this `PostRequest` proven/relayed to a chain running `pallet-hyper-fungible-token` where `ContractToAsset` is registered for `(source, from-contract-address)`.
3. On `on_accept`, execution reaches `&from_bytes[from_bytes.len() - 20..]` with `from_bytes.len() = 3`, causing `3usize - 20` to underflow, which panics (directly under overflow checks, or via out-of-bounds indexing otherwise), aborting extrinsic execution of the message batch. [1](#0-0)
