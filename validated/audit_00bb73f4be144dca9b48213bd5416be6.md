### Title
Unauthenticated `IntentGatewayV2.select()` allows griefing of solver-selection fills - (File: evm/src/apps/intentsv2/IntentsBase.sol / evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.select()` is a `public` function with no caller restriction that writes an order's solver-authorization commitment into a shared, commitment-keyed transient-storage slot. Because the slot is keyed only by `commitment` and not by caller/session, any unprivileged actor who observes a pending order commitment (bids/orders are public per the Hyperbridge intent flow) can call `select()` directly to overwrite that slot before the legitimate solver's `fillOrder()` reads it in the same transaction, causing the legitimate fill to revert with `Unauthorized`. This is structurally the same bug class as the reported `checkOrder`: an externally-reachable function that mutates per-order authorization/nonce-like state with no `msg.sender` binding, letting anyone invalidate another party's pending authorized action.

### Finding Description
`select()` is exposed with no access control: [1](#0-0) 

Its implementation stores the authorization purely by `commitment`, with no binding to `msg.sender`, a nonce, or any caller-specific value that would prevent a third party from overwriting it: [2](#0-1) 

`fillOrder()` later reads that same commitment-keyed transient slot to authorize the caller: [3](#0-2) 

In the intended flow, `SolverAccount.validateUserOp()` calls `select()` during ERC-4337 validation and `fillOrder()` runs during execution of the *same* UserOperation: [4](#0-3) 

Under ERC-4337, `EntryPoint.handleOps` runs the validation phase for *all* UserOperations in a bundle before running the execution phase for any of them. Because `select()` is a plain public function anyone can call (either directly, or by packaging a throwaway UserOperation whose validation calls it), an attacker can include a call to `select(commitment, arbitrarySolver, arbitrarySignature)` for the same order commitment in the same bundle transaction. That call's `tstore` overwrite happens during the shared validation phase, before the targeted solver's `fillOrder()` executes and checks the (now-corrupted) transient slot, causing `fillOrder` to revert with `Unauthorized`.

### Impact Explanation
This lets any unprivileged party — a griefer, a competing solver, or a hostile bundler — permanently or repeatedly block a specific order from being filled by its properly-selected solver, without needing any privileged role or leaked key. Because the attack can be repeated for every new attempt, it can be used to deny a solver's fills indefinitely for a targeted order (or systematically, for any order whose commitment is publicly observable before settlement), which is a route/action-denial impact on the intents fill path — analogous to the reported `checkOrder` griefing that blocks deposit/withdraw flows.

### Likelihood Explanation
Order commitments and pending bids on Hyperbridge's intent flow are public by design (the SDK's phantom-aggregation logic explicitly notes "Anyone can submit a bid to the coprocessor"), so an attacker has everything needed to construct the colliding `select()` call: the `commitment`, and a self-signed `SelectSolver` EIP-712 signature (attacker just signs with their own key to get *some* valid recovered `sessionKey`; `ECDSA.recover` does not need to match the real session key to succeed and write to the shared slot). Submitting the griefing call only requires normal permissionless bundler/relayer access to `EntryPoint.handleOps` or the ability to call `IntentGatewayV2.select()` directly within the same transaction as the target fill, which any relayer/searcher/bundler can arrange.

### Recommendation
Bind the transient-storage authorization slot to more than just `options.commitment` — e.g., include `msg.sender`/the calling account in the key, or require `select()` to be called only through a restricted path (e.g., only from a registered `SolverAccount`/EntryPoint context), so that an unrelated third party cannot overwrite another caller's pending selection for the same commitment within the same transaction.

### Proof of Concept
1. Solver constructs a valid UserOperation `OpS` for order `order` (commitment `C`) using `SolverAccount`, to be included in bundle transaction `T`.
2. Attacker observes `C` (public bid/order data) and crafts any UserOperation `OpA` whose `validateUserOp`/account logic calls `IntentGatewayV2.select({commitment: C, solver: attacker, signature: attackerSelfSignedSig})` — a signature attacker generates with their own private key, which `ECDSA.recover` accepts and returns some `sessionKey` attacker controls.
3. Attacker submits (or colludes with a bundler to submit) transaction `T` containing both `OpS` and `OpA` via `EntryPoint.handleOps`.
4. `EntryPoint` runs the validation phase for all ops first: `OpS`'s validation calls `select()` and sets `tstore(C) = keccak256(solver=legitSolver, sessionKey=real)`; `OpA`'s validation later (same phase) calls `select()` and overwrites `tstore(C) = keccak256(attacker, attackerSessionKey)`.
5. In the execution phase, `OpS`'s `fillOrder(order, ...)` reads `tstore(C)`, computes `expectedSelectionHash = keccak256(msg.sender=legitSolver, order.session)`, finds a mismatch against the attacker-overwritten value, and reverts with `Unauthorized`, per [3](#0-2) , blocking the legitimate fill.

    function _select(SelectOptions calldata options) internal returns (address) {
        bytes32 structHash = keccak256(abi.encode(SELECT_SOLVER_TYPEHASH, options.commitment, options.solver));
        bytes32 digest = _hashTypedDataV4(structHash);
        address sessionKey = ECDSA.recover(digest, options.signature);

        bytes32 commitment = options.commitment;
        bytes32 selectionHash = keccak256(abi.encode(options.solver, sessionKey));
        assembly {
            tstore(commitment, selectionHash)
        }

        return sessionKey;
    }
