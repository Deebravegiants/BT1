### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, allowing cross-tenant spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` validates webhook authenticity via `Utils::HmacValidator.validate`, which computes the HMAC over `to_signable_string` [3](#0-2) . For webhooks, `to_signable_string` returns only `@raw_body` [4](#0-3) , while `shop` is read from an unauthenticated header (`shopify-shop-domain`/`x-shopify-shop-domain`) that is never mixed into the signed bytes [5](#0-4) . This is the exact "field acted on but not covered by the HMAC" analog: `request.shop` is trusted and forwarded into `WebhookMetadata` for the app's handler [6](#0-5) , yet nothing cryptographically binds that value to the HMAC-verified body. By contrast, the OAuth `AuthQuery#to_signable_string` correctly includes `shop` in the signed string [1](#0-0) , showing the library's own precedent for binding `shop` into HMAC-covered data — a precedent not followed for webhooks.

### Finding Description
All shops installed under a single Shopify app share the same `Context.api_secret_key` [7](#0-6) . Since the webhook HMAC is computed only over the raw body (`OpenSSL::HMAC.hexdigest(sha256, secret, raw_body)`, as shown in the test's construction of a valid header) [8](#0-7) , a webhook payload that is genuinely signed by Shopify for shop A's body is equally valid HMAC-wise if replayed with the `shop-domain` header changed to shop B. `Registry.process` only checks `Utils::HmacValidator.validate(request)` [6](#0-5)  — it never verifies that the `shop` header is consistent with anything cryptographically tied to the body, so the identity binding `verified_hmac_body == (shop, body)` is broken; only `verified_hmac_body == body` holds.

### Impact Explanation
This is a cross-tenant identity confusion at the trust boundary the gem is responsible for: the app's webhook handler receives `WebhookMetadata#shop` believing it has been authenticated by Shopify, when in fact only the body bytes were authenticated. A malicious merchant who has installed the app (an unprivileged internet user relative to other merchants) can capture their own legitimately-signed webhook deliveries (e.g., via a self-controlled webhook endpoint proxy, or by reusing delivery retries/logs) and resubmit the same signed body to the app's webhook endpoint with an arbitrary `shop-domain` header pointing at a victim shop. `HmacValidator.validate` will report success because it never inspects `shop`, and the app's handler will process attacker-supplied data as if it belonged to the victim tenant — this can lead to cross-tenant data corruption/injection (e.g., forged `orders/create`, `app/uninstalled`, or GDPR mandatory webhook data attributed to the wrong shop).

### Likelihood Explanation
Requires the attacker to control at least one shop that has installed the app (a low, "unprivileged internet user" bar — anyone can install a public Shopify app on a test/dev store) and to be able to replay/produce webhook requests directly to the app's HTTP endpoint with modified headers, which is straightforward since delivery is just an HTTP POST that Shopify (or a replaying attacker in possession of a captured valid signed request) sends to a public URL.

### Recommendation
Include the shop identity in the HMAC-signed material for webhooks, or otherwise cryptographically bind `shop` to the verified body — e.g., extend `to_signable_string` in `lib/shopify_api/webhooks/request.rb` to include the `shop` value alongside the raw body, mirroring the approach already used in `AuthQuery#to_signable_string` [1](#0-0) . At minimum, document that `request.shop` is unauthenticated and require host applications to independently confirm the shop is one they have an active session/token for before trusting webhook data, since as written the value flows straight into `WebhookMetadata` without any such binding [9](#0-8) .

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; Shopify sends a legitimately HMAC-signed webhook: body `{"foo":"bar"}`, headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body with app secret>`.
2. Attacker captures this raw body + HMAC header (e.g., via a proxy they control, or replays a previously received webhook).
3. Attacker POSTs the same raw body and the same `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers [10](#0-9) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`@raw_body` only) and matches, since `shop` was never part of the signed input [11](#0-10) .
5. The handler receives `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: {...})` and processes it as authentic data for the victim tenant.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
