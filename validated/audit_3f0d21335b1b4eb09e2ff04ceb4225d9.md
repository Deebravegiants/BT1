### Title
Sustained high-utilization accrual overflows `i128` before `MAX_BORROW_INDEX_RAY` engages, permanently freezing every market verb — (`File: common/src/rates` `scaled_to_original`, exercised via `contracts/pool/src/interest.rs::accrue_chunk`)

### Summary
The kernel bug class is an arithmetic/allocation flaw reachable by unprivileged input that crashes the system. On XOXNO Lending the analog is a reachable `i128` overflow inside interest accrual: once a market's scaled debt times the growing `borrow_index` exceeds `i128::MAX`, `global_sync` panics, and because every pool verb (and every controller verb, which accrues first) runs accrual before mutating, the market is bricked forever — no withdraw, no repay, no liquidation, no `recapitalize`.

### Finding Description
`interest::global_sync` accrues in ≤1-year chunks and calls `accrue_chunk`, which runs `accrue_step` and then unstales debt value via `scaled_to_original`/`mul_ceil` style RAY multiplies (`contracts/pool/src/interest.rs:20-53`). The bounds `MAX_BORROW_INDEX_RAY`/`MAX_SUPPLY_INDEX_RAY` at 1e36 cap the *index*, but the overflow occurs in the *value* multiply `borrowed_scaled × borrow_index` before the cap is ever reached. With an 18-decimal asset at ~1e18-scale principal and ~98% utilization on the steep segment of the rate curve, the index passes ~170× and the product overflows `i128`. The checked-arithmetic panic (`MathOverflow`, error 33) is permanent because `borrowed` and `borrow_index` never decrease.

This is not theoretical: the harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361` builds the scenario end-to-end and asserts that `update_indexes`, `withdraw`, and `repay` all panic with `MATH_OVERFLOW`, that the index cap "did not engage before the value overflow", and that "the market is frozen: no repay, no withdraw, no liquidation" — explicitly noting the documented bound in `docs/reference/formulas.md` is wrong.

### Impact Explanation
Permanent freezing of funds and contract unable to operate. All supplier and collateral value routed through that pool market becomes immovable: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate (liquidation also accrues first), and governance cannot `recapitalize` its way out since recapitalization hits the same accrual path. The controller's `update_indexes` and every position verb touching the market revert identically.

### Likelihood Explanation
Fully reachable by unprivileged addresses using only `supply` and `borrow` with large amounts (caps can be lifted by normal governance config, and even without that, whale-scale supply/borrow plus time is sufficient). No special permissions, no oracle manipulation, no flash tricks required — just capital plus time at high utilization. Cost is high (whale-scale liquidity and years of accrual), which is why this is Medium rather than Critical, but nothing in the code prevents it and the failure is irreversible.

### Recommendation
Apply the index cap before the value unscale, or saturate: in `accrue_step`, clamp `borrow_index`/`supply_index` to `MAX_*_INDEX_RAY` and skip/saturate the `scaled_to_original` products that would overflow, so accrual degrades gracefully instead of panicking. Alternatively compute utilization/debt value in widened arithmetic (e.g., via `U256`-style mul-div) inside `scaled_to_original`. Add a regression asserting the index cap engages *before* the value overflow.

### Proof of Concept
```rust
// tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-356
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98); // 98% utilization
// advance years until accrual panics:
assert_contract_error(t.try_update_indexes_for(&["BIG18"]), errors::MATH_OVERFLOW);
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
// last.borrow_index < MAX_BORROW_INDEX_RAY — the cap never engaged.
```
