### Title
Webhook shop attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (and `topic`/`webhook_id`) values used to route and attribute the webhook to a specific merchant are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC against the body but never verifies that the `shop` header is actually bound to that signature, so an attacker who can obtain one validly-signed webhook body can replay it with a forged `shop-domain` header to make the app process it as belonging to a different (victim) shop.

### Finding Description
The identity-binding equality that should hold is:
`shop the HMAC signature was computed for == shop attributed to the webhook payload by the handler`

In this library that equality is broken:

- `to_signable_string` returns only `@raw_body`, excluding all Shopify headers from the signed material: [1](#0-0) 

- `shop` (like `topic` and `webhook_id`) is read straight from an attacker-controllable header with no cryptographic binding to the signed body: [2](#0-1) 

- `Registry.process` validates only the body's HMAC, then hands the unauthenticated `request.shop` straight to the application's webhook handler as the tenant identity for the event: [3](#0-2) 

- `HmacValidator.validate` / `validate_signature` confirm this: the signature is checked exclusively against `verifiable_query.to_signable_string`, which for webhooks is the raw JSON body — nothing else: [4](#0-3) 

Because a single app has one `client_secret` shared across every merchant that installs it, any shop that installs the app can receive a legitimately Shopify-signed webhook for its own store (body + valid `x-shopify-hmac-sha256`). Since `shop-domain` is not part of the signed material, that exact body/HMAC pair can be replayed to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to point at a victim shop. `Registry.process` will accept it as valid (the HMAC over the body still checks out) and invoke the registered handler with `WebhookMetadata` claiming the victim shop, even though Shopify never signed anything binding this payload to that shop.

### Impact Explanation
This breaks the tenant boundary between shops using the same app: an attacker-controlled shop can inject a fully "HMAC-verified" webhook event that the application attributes to a different, victim merchant. Any app logic that trusts `WebhookMetadata#shop` to look up, mutate, or delete per-merchant data (order/customer records, mandatory `shop/redact`/`customers/redact` compliance flows, feature toggles, etc.) can be manipulated by an unprivileged user who merely installs the same public app on their own store. This matches the "cross-tenant access" criterion for a Critical-impact finding.

### Likelihood Explanation
Exploitation only requires an internet user to install the target app on a shop they control (a normal, unprivileged action for any public Shopify app) to obtain one valid `(body, hmac)` pair, then replay it to the app's public webhook endpoint with a modified `shop-domain` header — no access token, `client_secret`, or other privileged credential is needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material, or otherwise independently verify the shop attribution — e.g., cross-check `x-shopify-shop-domain` against a shop value embedded in the payload itself or against records of shops known to have this webhook/topic registered — before handing it to the registered handler. At minimum, document that `request.shop` from `ShopifyAPI::Webhooks::Request` is unauthenticated and must not be trusted by itself for tenant attribution.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a shop they control) and triggers a webhook topic the app registers for (e.g., `orders/create`).
2. Shopify sends the webhook to the app's endpoint with a body `B` and a valid `x-shopify-hmac-sha256` computed as `HMAC-SHA256(client_secret, B)`, plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures this request, then replays it directly to the same webhook endpoint, keeping `B` and the HMAC header unchanged but rewriting `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because it only checks `HMAC-SHA256(client_secret, B)` against `to_signable_string` (= `B`), which is unchanged.
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, even though Shopify never signed anything associating body `B` with `victim-shop.myshopify.com`. [3](#0-2) [5](#0-4)
