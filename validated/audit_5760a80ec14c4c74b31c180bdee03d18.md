## Analog Identified: Webhook `shop` identity not covered by HMAC signature

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating the HMAC over the raw request body only, then trusts the unauthenticated `x-shopify-shop-domain` (or `shopify-shop-domain`) header to attribute the webhook to a tenant. The binding `shop_the_HMAC_was_computed_for == shop_used_to_route_the_webhook_data` does not hold, because the header is never part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The HMAC validator (`ShopifyAPI::Utils::HmacValidator.validate`) recomputes the signature purely from `to_signable_string` and compares it with the `hmac-sha256` header: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` then trusts `request.shop`, which is read straight from the `shop-domain` header without any cryptographic tie to the verified body: [3](#0-2) [4](#0-3) 

Because the `shop` field is a plain HTTP header value that is *not* part of the HMAC-signed string, the equality `hmac_signed_shop == request.shop` is never actually enforced — the HMAC only proves "this body+secret pair is authentic for *some* shop that the app secret was used for," not "this body came from the shop named in this header."

### Impact Explanation
An attacker who controls (or has installed the app on) their own Shopify development store can trigger any webhook topic they're subscribed to (e.g. `orders/create`) and legitimately receive a body + valid `x-shopify-hmac-sha256` signature pair, computed with the target app's real `api_secret_key`. Because the shop header is unauthenticated, the attacker can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` will still pass (it never inspects the shop header), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data originated from the victim shop. Any app logic keyed off `data.shop` (e.g. writing order/customer records, updating per-shop state, billing, GDPR/mandatory-webhook handling) will then process attacker-supplied content under the victim's tenant identity — a cross-tenant data-integrity/confusion vulnerability requiring no access token, no `client_secret`, and no privileged account.

### Likelihood Explanation
Any developer/merchant can install the target app on their own store (fully unprivileged, self-service action) to obtain a legitimately signed webhook body+HMAC pair, then replay it against the same public webhook endpoint with a forged shop header. No secret material, TLS interception, or social engineering is required — only crafting and sending one HTTP request.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed material, or otherwise cryptographically bind the verified body to the claimed shop before dispatching to handlers. At minimum, `Webhooks::Request#to_signable_string` should incorporate the `shop`, `topic`, and `webhook_id` headers, and `HmacValidator`/`Registry.process` should reject requests where the signed shop does not match the header-declared shop.

### Proof of Concept
1. Install the target app on attacker-owned store `attacker.myshopify.com`; trigger `orders/create` to receive a legitimate webhook POST:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC over body>`, `x-shopify-shop-domain: attacker.myshopify.com`
   - Body: `{"id": 1, ...attacker-controlled order data...}`
2. Replay the identical body and `x-shopify-hmac-sha256` header to the same endpoint, changing only:
   - `x-shopify-shop-domain: victim.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only validates `@raw_body` against the HMAC — the shop header is never checked.
4. The registered handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: <attacker-controlled JSON>, ...)`, causing the host application to process attacker-controlled data as if it belongs to `victim.myshopify.com`.
