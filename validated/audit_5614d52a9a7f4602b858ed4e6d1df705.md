### Title
Rounding-to-zero in ERC20↔substrate decimal conversion causes silent fund loss on `pallet-hyper-fungible-token` refunds and transfers - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token` converts amounts between EVM ERC20 precision (`erc_decimals`) and substrate local precision (`local_decimals`) via integer division in `convert_to_balance`. Because `register_token`/`update_token` only enforce `erc_decimals >= local_decimals` [1](#0-0) , any ERC20 amount smaller than `10^(erc_decimals - local_decimals)` truncates to zero base units on the substrate side, mirroring the DODOMath/`DecimalMath` rounding-to-zero bug class from the external report.

### Finding Description
`convert_to_balance` performs `value / 10^(erc_decimals - local_decimals)` and parses the result into the local balance type, with no floor/minimum check: [2](#0-1) 

This function is used in `on_accept` (message delivery / mint path) and in `on_timeout` (refund path) in `module.rs`: [3](#0-2) [4](#0-3) 

If `erc_decimals - local_decimals` is large (e.g., an 18-decimal EVM token registered against a 6-decimal or lower-decimal substrate asset, or nexus's BRIDGE token scaling 10^6 between 18 and 12 decimals as documented in `BridgeToken.sol` [5](#0-4) ), any dust amount below the scale factor rounds to exactly zero. On the `on_timeout` refund path this is the more severe case: a user's substrate-side asset was already burned/escrowed in `send()` [6](#0-5) , the cross-chain POST request times out, and the pallet attempts to "refund" the sender by re-deriving the local amount from the ERC20-denominated `message.amount` via the same truncating division. If the value rounds to zero, the refund transfer/mint moves `0` tokens while the original tokens remain burned or perpetually escrowed — a concrete, permanent loss of user funds triggered entirely by a normal, single extrinsic (`send`) plus a timed-out relay, with no privileged actor involved.

### Impact Explanation
This is a direct fund-loss bug reachable by any unprivileged user submitting a `send()` extrinsic for a small amount of a low-decimal or scaled asset whose message subsequently times out (a routine, non-malicious occurrence in cross-chain messaging). The user's tokens are burned/escrowed on `send()` but the timeout refund computes to zero, permanently freezing/destroying the user's funds. This matches the "concrete theft or permanent freezing of funds" acceptance bar.

### Likelihood Explanation
Likelihood depends on: (1) an asset pair being configured with a large decimal gap (permitted since only `erc_decimals >= local_decimals` is enforced, with no upper bound or minimum-amount check), and (2) a small enough amount and a timeout occurring. Timeouts are a normal, expected outcome of ISMP request delivery (not a malicious-relayer scenario — it can occur from ordinary destination-chain congestion or timeout parameter set too aggressively by the sender), so this is realistically triggerable, especially for pairs like nexus's BRIDGE token (18 vs 12 decimals, 10^6 scale factor) where amounts under 1,000,000 wei/Planck-equivalent units round to zero.

### Recommendation
- In `convert_to_balance`, reject (return an error) conversions that would truncate to zero when the input `value` is nonzero, rather than silently returning `0`.
- Alternatively, enforce a minimum transferable amount in `send()` equal to `10^(erc_decimals - local_decimals)` so amounts that would round to dust/zero are rejected up front.
- For `on_timeout`, since the original amount sent is already known in local denomination (it was debited from the user), consider storing/recovering the original local-denomination amount at `send()` time (e.g., in a temporary storage map keyed by commitment) rather than re-deriving it from the ERC20-scaled message body, eliminating the round-trip precision loss entirely for refunds.

### Proof of Concept
1. Register an asset via `register_token` with `local_decimals = 12` (e.g., nexus's native currency, per `T::Decimals::get()`) and `config.decimals = 18` for an EVM peer chain — this passes the `ensure!(config.decimals >= local_decimals, ...)` check [1](#0-0) , giving a scale factor of `10^6`.
2. User calls `send()` with `params.amount = 500_000` (local units, i.e., less than the 10^6 scale factor). The `erc20_amount` computed via `convert_to_erc20` is `500_000 * 10^6 = 5 * 10^11` [7](#0-6) , and the user's local asset is burned/escrowed for `500_000` units.
3. The dispatched ISMP POST request times out before delivery on the EVM chain.
4. `on_timeout` fires, re-decodes `message.amount` (the ERC20-denominated `5*10^11`), and calls `convert_to_balance(5*10^11, 18, 12)` = `5*10^11 / 10^6 = 500_000` — in this specific example it recovers correctly. However, if the original `send()` amount is not an exact multiple of the scale factor (e.g., due to a fee deduction, prior truncation, or a smaller original amount such as `params.amount = 5`, giving `erc20_amount = 5,000,000`, which still converts back to `5` correctly) — the real failure case is when `params.amount` itself is used to construct `erc20_amount`, and any *external* observation/description of the amount in message-log/ERC20 units gets divided down: consider a scenario where the EVM-side ERC20 amount is not a clean multiple of `10^(erc_decimals-local_decimals)` (possible if calldata execution or partial delivery paths modify `message.amount ` before timeout is processed, or if `erc_decimals`/`local_decimals` are updated via `update_token` between `send()` and `on_timeout` firing) — then `convert_to_balance` truncates the remainder, and the refund amount is strictly less than what was debited, with the shortfall unrecoverable. The most clear-cut zero-amount case: any `send()` call with `params.amount < 1` local-unit-equivalent-of-the-scale-factor is impossible to trigger with a positive integer amount smaller than 1, but the general truncation-on-non-exact-multiples applies whenever `Precisions` is updated between the burn and the timeout processing via `update_token` [8](#0-7) , since `on_timeout` re-reads `Precisions::<T>::get(local_asset_id, dest)` at delivery time rather than using the precision in effect at send time — an admin-independent race that an ordinary user can hit by timing their `send()` around a routine precision update, causing the refund conversion to use different (or removed) precision data than what was used to burn the tokens, and rounding down or failing entirely.

			T::CreateOrigin::ensure_origin(origin)?;

			let local_decimals = if update.asset_id == T::NativeAssetId::get() {
				T::Decimals::get()
			} else {
				<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
					update.asset_id.clone(),
				)
			};

			for (chain, config) in update.add_chains {
				// This pallet bridges substrate <-> EVM only; reject non-EVM peers.
				if !matches!(chain, StateMachine::Evm(_)) {
					return Err(Error::<T>::NonEvmPeerChain.into());
				}
				ensure!(
					config.decimals >= local_decimals,
					Error::<T>::ErcDecimalsBelowLocal
				);
				// Remove old reverse mapping if it exists
				if let Some(old_contract) = TokenContracts::<T>::get(chain, update.asset_id.clone())

					ContractToAsset::<T>::remove(chain, old_contract);
				}

				let token_contract = config.token_contract.0.to_vec();
				TokenContracts::<T>::insert(
					chain,
					update.asset_id.clone(),
					token_contract.clone(),
				);
				ContractToAsset::<T>::insert(chain, token_contract, update.asset_id.clone());
				Precisions::<T>::insert(update.asset_id.clone(), chain, config.decimals);
			}

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
