### Title
Webhook `shop-domain` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then trusts the `shop`/`webhook_id`/`topic` values taken from unauthenticated HTTP headers to identify which tenant the webhook belongs to. Because every shop that installs the app shares the same `api_secret_key`, an attacker who controls one legitimately-installed shop (trivial — anyone can create a Shopify dev/trial store) can capture a validly-signed webhook body+HMAC pair from their own store and replay it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop, producing a webhook that passes HMAC validation but is attributed to the wrong tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors are read directly from HTTP headers, which are not part of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC and, if it passes, immediately dispatches the handler using `request.shop` (and other header-derived fields) with no additional binding check between the signed body and the shop identity: [3](#0-2) 

`Utils::HmacValidator.validate` computes/compares the signature over `verifiable_query.to_signable_string` (the body, for webhooks) using `Context.api_secret_key`, and that secret is identical for every shop that installs the app: [4](#0-3) 

The identity binding that should hold is:
`HMAC-verified(body) == HMAC-verified(body, shop)`, i.e. the signature is expected to authenticate "this body came from *this* shop," but it only authenticates "this body was produced with the app's shared secret" — the `shop` header is unauthenticated and can be swapped freely by any party that can reach the webhook endpoint with a *body they already have a valid signature for*.

### Impact Explanation
This breaks the tenant boundary the gem is meant to enforce: an unprivileged internet user who installs the app on their own (free) shop can obtain a legitimately-signed webhook (e.g. `orders/create`, `app/uninstalled`, `customers/data_request`) and replay it with an arbitrary `x-shopify-shop-domain` header value. The host application's handler (using `WebhookMetadata#shop`) will process the payload as if it originated from the victim shop — e.g. triggering app-uninstall cleanup, GDPR data deletion, order/customer state changes, or any shop-scoped side effect keyed off `data.shop` — for a tenant the attacker does not control. This is a cross-tenant access/data-integrity issue directly caused by the gem's webhook authentication design providing no protection for the `shop` field, satisfying the "Critical - cross-tenant access" impact bar.

### Likelihood Explanation
High: the prerequisite is only the ability to install the app on an attacker-owned shop (free, unprivileged) and to send an HTTP request to the app's public webhook endpoint — no possession of `api_secret_key`, tokens, or other privileged material is required. Capturing a valid `(raw_body, hmac)` pair from one's own store is straightforward (the attacker's own store legitimately receives such webhooks), and headers are trivially forgeable by any HTTP client.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) identity into the value that is cryptographically verified, or require the caller to cross-check `request.shop` against a known/expected shop (e.g., an existing session for that shop) before trusting it — the library should not hand an unauthenticated `shop` value to handlers as though it were verified. At minimum, document loudly that `WebhookMetadata#shop` is not authenticated by the HMAC and that callers must independently confirm the shop has an active session/install before acting on the payload; better, extend `HmacValidator`/`Request#to_signable_string` so the header-derived shop value is included in what's verified against Shopify's documented webhook validation, or reject requests whose `shop-domain` header doesn't match a session the app already trusts.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to (e.g. `orders/create`) and capture the raw POST: headers (`x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`) and raw body `B`.
2. Replay the exact same request to the app's webhook endpoint, only replacing the `x-shopify-shop-domain` header with `victim-shop.myshopify.com` (or any string), keeping body `B` and hmac header `H` unchanged.
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes HMAC over `B` using the shared `Context.api_secret_key`, which still matches `H` — validation succeeds (`lib/shopify_api/webhooks/request.rb` lines 35-38; `lib/shopify_api/utils/hmac_validator.rb` lines 26-31).
4. `Registry.process` proceeds to call the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` (`lib/shopify_api/webhooks/registry.rb` lines 188-200), causing the host app to act on victim-shop data/state using attacker-supplied body content.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
