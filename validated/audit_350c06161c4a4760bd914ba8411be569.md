Confirmed: the webhook `hmac` is computed over `to_signable_string`, which is only the raw request body — the `shop-domain` header used to identify the tenant is never part of the signed bytes.### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity via `Utils::HmacValidator`, but the HMAC only signs the raw request body, not the `shop-domain` header. Any party capable of producing one valid `(body, hmac)` pair for their own shop can replay that same body/hmac pair while substituting an arbitrary `shop-domain` header, and `Registry.process` will accept it as authentic and dispatch it to the app's handler tagged with the attacker-chosen shop.

### Finding Description
`Registry.process` gates all webhook processing on a single check: [1](#0-0) 

That check delegates to `Utils::HmacValidator.validate`, which computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` accessor: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, while `shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header and is never mixed into the signed bytes: [3](#0-2) [4](#0-3) 

`Registry.process` then builds the tenant-identifying metadata straight from `request.shop` (the unauthenticated header) and hands it to the app's handler: [1](#0-0) [5](#0-4) 

The binding that is expected but not enforced is: **`hmac` valid for `raw_body` ⇒ `shop-domain` header is authentic for that `raw_body`**. In reality, the HMAC only proves `hmac` valid for `raw_body`; it says nothing about which shop the header claims to be. Since `secret` (`Context.api_secret_key`) is shared across every shop/tenant that installs the app, anyone who can install the app on a shop they control (e.g. a free Shopify partner/dev store — no special privilege required) will legitimately receive real Shopify webhooks with a valid `hmac` computed over a body they can fully observe. They can then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while overwriting only the `x-shopify-shop-domain` header to name a victim shop. `HmacValidator.validate` recomputes the same HMAC over the same `raw_body` and it still matches, so the forged request is accepted and `WebhookMetadata#shop` is populated with the attacker-chosen victim domain.

### Impact Explanation
This breaks the tenant isolation the whole HMAC check exists to provide: an unprivileged, unrelated user (any merchant who installs the app on their own shop) can make the library accept a webhook while asserting it belongs to a different shop. Any application built on this gem's documented `Registry.add_registration` / `Registry.process` flow inherits this flaw automatically — it cannot be avoided by following the documented API. Depending on what data is present in shared/replayable webhook bodies (e.g. `app/uninstalled`, `shop/update`, or any webhook whose body content is attacker-influenced or reusable) and how the host maps `WebhookMetadata#shop` to stored records, this enables cross-tenant data confusion/corruption in the app's persistence layer, satisfying the "cross-tenant access" impact bar because the library itself hands the host an unauthenticated tenant identifier under the guise of an "HMAC-verified" webhook.

### Likelihood Explanation
Likelihood is high for the specific primitive (forging the `shop` field while keeping a valid HMAC) because it requires no secret material — only the ability to install the app once as an ordinary merchant and to control HTTP headers on a replayed request, both trivially available to any internet user. The severity of the downstream effect depends on host-app logic, but the root cause — `shop` not covered by the signed bytes — is entirely inside this gem.

### Recommendation
Include the tenant-identifying header (`shop-domain`, and ideally `topic`/`webhook-id`) in the bytes that are HMAC-verified, or otherwise cryptographically bind them to the signature before trusting `request.shop`. At minimum, `Webhooks::Request#to_signable_string` should incorporate the shop domain (e.g. concatenate/canonicalize headers + body) rather than relying solely on `@raw_body`, and `HmacValidator`/`VerifiableQuery` should be updated accordingly so a valid signature can only be replayed for the exact shop it was issued for.

### Proof of Concept
1. Attacker registers the target app as an unprivileged merchant on `attacker-shop.myshopify.com` (no special access required).
2. Shopify sends a legitimate webhook to the app's endpoint with headers including `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid_hmac_for_body>`, and some `raw_body`.
3. Attacker captures this exact `raw_body` + `x-shopify-hmac-sha256` pair (e.g., by controlling their own network traffic/logging) and replays an HTTP POST to the same app endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` identical but changing `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged headers; `Utils::HmacValidator.validate` recomputes HMAC over the unchanged `raw_body` and it matches, so `Registry.process` accepts the request.
5. `WebhookMetadata.new(... shop: request.shop ...)` is built with `shop: "victim-shop.myshopify.com"` and forwarded to the app's `WebhookHandler#handle`, even though Shopify never issued this webhook for `victim-shop`.
