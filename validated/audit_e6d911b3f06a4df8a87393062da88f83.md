### Title
Improper Escaping in `StateMachine::Display`/`FromStr` Round-Trip Breaks Cross-Chain Message Routing - (File: modules/ismp/core/src/host.rs)

### Summary
`StateMachine`'s string encoding (`Display`) and decoding (`FromStr`) form the untrusted-input boundary for chain identifiers submitted by unprivileged actors — most concretely the `chain` field of `BandwidthPurchaseMsg`, which `modules/pallets/bandwidth/src/abi.rs` documents as "the UTF-8 form of `StateMachine::Display` ... so EVM dapps can build it with string concat." `Display` formats `Substrate`, `Tendermint`, and `Relay` variants by directly concatenating their raw 4-byte identifiers into a `-`-delimited string without escaping the delimiter character itself, exactly the same class of bug as the reported python-ldap issue (CWE-116: improper encoding/escaping of output) — the serializer assumes its inputs never contain the separator it uses.

### Finding Description
`Display for StateMachine` builds strings like `"RELAY-{relay}-{para_id}"`, `"SUBSTRATE-{id}"`, `"TNDRMINT-{id}"` where `relay`/`id` are raw, attacker-influenced 4-byte arrays interpreted as UTF-8: [1](#0-0) 

`FromStr` reverses this purely by splitting on `-` and taking positional segments: [2](#0-1) 

Because the 4-byte identifier is never escaped before being embedded between `-` delimiters, any legitimate `StateMachine::Relay`/`Substrate`/`Tendermint` value whose raw bytes happen to contain the ASCII `-` character (0x2D) produces a string that does not parse back to the original value — `str::split('-')` shifts the field boundaries, and `values.get(1)` (or the final segment) no longer has exactly 4 bytes, so `FromStr` returns `Err`. This mirrors the reported bug precisely: `escape_dn_chars` in python-ldap fails to hex-escape a byte with special meaning to the consumer (NUL for LDAP DN parsing), so a legitimate value silently becomes unparseable by the receiving API. Here, the "escaping" helper (`Display`) fails to escape/quote the `-` byte with special meaning to its own `FromStr` counterpart.

The reachable, unprivileged entry point is `PurchaseMessage::try_from(&[u8])` in the bandwidth pallet, which decodes an EVM dapp-supplied `chain: Bytes` field (the UTF-8 `Display` string) via `StateMachine::from_str`: [3](#0-2) 

An unprivileged bandwidth purchaser (or any relayer forwarding a purchase message that already crossed a chain via `BandwidthManager.sol` -> ISMP dispatch) can construct or relay a message whose destination `chain` was encoded from a real `StateMachine::Relay{relay, para_id}`/`Substrate(id)`/`Tendermint(id)` value containing a `-` byte, causing `PurchaseMessage::try_from` to fail and the whole cross-chain purchase message to be rejected as unhandleable — after the source-chain dispatch (and its associated relayer/protocol fee) has already been paid.

### Impact Explanation
This is a message-delivery-integrity bug reachable from a single unprivileged, fee-paying dispatch (`BandwidthManager.purchase()` → ISMP `dispatch` → cross-chain `handle_unsigned`/`on_accept` decode). Per the scope rules, "a route unable to deliver messages" is an accepted impact category. The practical effect: a purchase whose `chain` string round-trips incorrectly is dispatched cross-chain, consumes dispatch/relayer fees, and is then rejected by the bandwidth pallet's decode step — the paid message can never be successfully processed on the destination, and the payer's fee for that dispatch is not refunded by this decode-time rejection path. This is a protocol-level correctness/DoS defect on the message-encoding boundary rather than a takeover or unbacked mint, consistent with Medium severity.

### Likelihood Explanation
Likelihood is constrained by how `Substrate`/`Tendermint`/`Relay` 4-byte identifiers are chosen in practice (they are usually meaningful ASCII mnemonics like `PAS0`, `CENJ`, `hybr`) — an operator or governance process assigning a consensus/relay identifier that happens to contain `-` is unlikely but not prevented by any validation in the codebase. The `FromStr` test suite explicitly checks non-4-byte and invalid-UTF8 cases but does not test or guard against a valid 4-byte, valid-UTF8 identifier that contains the `-` delimiter itself: [4](#0-3) 

This confirms the round-trip property (`Display` → `FromStr` → original value) is only tested with non-`-`-containing fixtures (`b"hybr"`, `b"CENJ"`), leaving the delimiter-collision case unguarded and unnoticed.

### Recommendation
Escape or reject the delimiter character when constructing `Display` output for `Substrate`, `Tendermint`, and `Relay` variants — e.g., reject identifiers containing `-` at the point they are set (in the same way invalid UTF-8 already degrades to `"XXXX"`), or switch to a length-prefixed/hex encoding for the byte segment so `FromStr` never relies on positional `-`-splitting of attacker/operator-supplied bytes. Add a round-trip property test that includes `-` in the raw 4-byte identifier to catch this class of encoding bug, mirroring the fix pattern used for the non-4-byte-length case already tested in `host.rs`.

### Proof of Concept
```rust
use ismp::host::StateMachine;
use core::str::FromStr;

// A legitimate Relay identifier whose raw bytes are valid ASCII and contain '-'.
let sm = StateMachine::Relay { relay: *b"CN-A", para_id: 1000 };

let s = sm.to_string();
// Produces "RELAY-CN-A-1000" — the `values.get(1)` segment on parse-back is "CN"
// (2 bytes), not the original 4-byte "CN-A".
assert_eq!(s, "RELAY-CN-A-1000");

// Round-trip fails: FromStr splits on '-' and rejects the malformed 4-byte segment.
assert!(StateMachine::from_str(&s).is_err());
```
Reachable end-to-end via `BandwidthPurchaseMsg.chain` in `modules/pallets/bandwidth/src/abi.rs`: an EVM dapp builds `chain` as `StateMachine::Relay{..}.to_string().into_bytes()` per the documented convention, dispatches the purchase cross-chain (paying dispatch fees), and the destination pallet's `PurchaseMessage::try_from` rejects the message at `StateMachine::from_str(chain_str)`, wasting the paid dispatch/fee without crediting bandwidth.
