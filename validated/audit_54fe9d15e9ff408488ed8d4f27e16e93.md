### Title
Webhook tenant identity (`shop`) is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header as the tenant identity passed to the host application's handler. Because the header is never part of the signed payload, an attacker who can produce or replay one valid `(body, hmac)` pair can attach an arbitrary `shop-domain` header and have the app process the webhook as if it originated from a different merchant.

### Finding Description
`Utils::VerifiableQuery#to_signable_string` for the webhook `Request` returns only `@raw_body`: [2](#0-1)  This is what `HmacValidator.validate` hashes and compares against the `hmac-sha256` header: [5](#0-4) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain` header without any cryptographic binding to that HMAC: [1](#0-0) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body integrity) before forwarding `request.shop` straight into the `WebhookMetadata` handed to the app's business logic: [3](#0-2) [4](#0-3) 

This is exactly the identity-binding gap described in the report's bug class: a field that is acted upon (`shop`, used by host apps to key session/tenant lookups, GDPR redaction targets, order/customer updates, etc.) is not covered by the HMAC that is supposed to authenticate the whole request. Equality that should hold but doesn't: `hmac == HMAC(secret, body || shop || topic || webhook_id)`, whereas the gem only enforces `hmac == HMAC(secret, body)`.

### Impact Explanation
Any consumer of this gem that trusts `WebhookMetadata#shop` to scope the operation to a tenant (the documented and expected usage pattern, e.g. mandatory `shop/redact`, `customers/redact`, `customers/data_request` topics) can be tricked into performing an action against the wrong merchant's data if an attacker can supply/replay a body+hmac pair while forging the shop header. This crosses the tenant boundary the gem's webhook authentication is meant to enforce, meeting the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation requires the attacker to have or produce a valid `(body, hmac)` pair — for instance by replaying a webhook they legitimately received for their own shop (a body with no `shop` field, such as `{}` for mandatory topics, works with any `shop` header) against the app's public webhook endpoint with a spoofed `shopify-shop-domain` header. Since the gem does nothing to bind the header to the signature, this is a straightforward header-only manipulation, no secrets required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string bound to the HMAC (matching Shopify's actual webhook signing scheme is body-only by protocol, so alternatively) the gem should treat the shop header as untrusted unless independently corroborated — e.g., by requiring/validating it against a known/registered shop before constructing `WebhookMetadata`, or by clearly documenting that host applications must independently authenticate `shop` before using it for tenant-scoped actions, rather than presenting it as verified data alongside a "HMAC validated" guarantee.

### Proof of Concept
1. Attacker's own store receives a legitimate mandatory webhook, e.g. `customers/redact`, with body `{}` and a correctly computed `x-shopify-hmac-sha256` header for that body.
2. Attacker replays that exact `(body="{}", hmac)` pair to the app's webhook endpoint but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` succeeds because it only checks `body` against `hmac`: [6](#0-5) 
4. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", ...)` and invokes the app handler, which acts as though Shopify authenticated a request for `victim-shop`.
