### Title
Unauthenticated `CallDispatcher.dispatch()` lets anyone impersonate the trusted cross-chain relay and drain any approvals granted to it - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is the shared contract that `HyperFungibleToken` (and other `HyperApp`s) use to execute arbitrary follow-on calls after a cross-chain transfer is delivered, enabling "transfer-and-swap" composability. Its `dispatch()` function performs blind, unauthenticated external calls to attacker-supplied target addresses, exactly mirroring the Maverick `Router.exactInput` bug class where a byte-encoded "path" of untrusted contract addresses is executed without any allow-listing.

### Finding Description
`HyperFungibleToken.send()` lets any caller attach arbitrary `params.data`, which is packed unmodified into the cross-chain `Message.data` field: [1](#0-0) 

On delivery, `onAccept` mints tokens to the beneficiary and then unconditionally forwards `message.data` to the shared `CallDispatcher`: [2](#0-1) 

`CallDispatcher.dispatch()` itself has **no access control** (`external`, no `onlyHost`/`onlyOwner` modifier) and blindly loops over an attacker-decodable `Call[]`, only checking that the target has code, then executes it with attacker-chosen value and calldata: [3](#0-2) 

This is the same root cause as the Maverick `Router.exactInput` finding: a byte-encoded sequence of "targets to call" is trusted and executed without verifying that the targets are legitimate/expected contracts, and the calling context (`msg.sender == CallDispatcher`) is what any downstream contract will see, regardless of whether the call arrived via a legitimate ISMP delivery or a direct, unauthenticated call to `dispatch()`. Because `dispatch()` is public and reachable by anyone — not just the `HyperFungibleToken`/host — any user who has granted an ERC20 `approve` to the `CallDispatcher` address (which the documented "transfer-and-swap" pattern requires them to do, so that the dispatcher can pull newly minted tokens and forward them to a router) can have those tokens stolen by an unrelated attacker who directly calls `CallDispatcher.dispatch()` with a crafted `Call[]` such as `token.transferFrom(victim, attacker, amount)`, entirely bypassing the ISMP host and any cross-chain message.

### Impact Explanation
Any address that trusts the `CallDispatcher` contract (by granting it a token allowance, as the composable "transfer-and-swap" flow depends on) is exposed to permanent theft of those approved funds. The attacker requires no relayer collusion, no consensus forgery, and no interaction with the ISMP host at all — a single unprivileged transaction to the public `dispatch()` function is sufficient. This satisfies "concrete theft of funds" from an unprivileged path, matching a Medium-severity classification analogous to the judged Maverick finding.

### Likelihood Explanation
Likelihood is high for any deployment where `CallDispatcher` is used for its advertised composability purpose (approvals granted to it for downstream swaps/actions), since exploitation requires only a single unauthenticated call with an arbitrary `Call[]` payload — no proof, no consensus interaction, and no dependency on a specific cross-chain message being in flight.

### Recommendation
Restrict `CallDispatcher.dispatch()` so it can only be invoked by the trusted calling `HyperApp`/host contract that is meant to route the decoded cross-chain payload (e.g., an `onlyAuthorizedCaller` modifier keyed to a registry of `HyperApp` instances), and/or scope any token approvals so they cannot be redirected by a call that didn't originate from a genuine, verified cross-chain delivery. At minimum, do not allow the dispatcher to be called directly by arbitrary externally-owned accounts with attacker-chosen `Call[]` data.

### Proof of Concept
1. Victim approves `CallDispatcher` to spend `amount` of `TokenX` (as required for a legitimate transfer-and-swap flow expected after a `HyperFungibleToken.send()` delivery).
2. Attacker (no privilege, no relayer role) calls `CallDispatcher.dispatch(encoded)` directly, where `encoded` decodes to `Call[]{ to: TokenX, value: 0, data: abi.encodeCall(IERC20.transferFrom, (victim, attacker, amount)) }`.
3. `dispatch()` only checks `extcodesize(TokenX) != 0` and executes the call; since `msg.sender` inside `TokenX.transferFrom` is `CallDispatcher` (the approved spender), the transfer succeeds and the victim's funds move to the attacker — with no cross-chain message, proof, or ISMP host interaction ever involved.     function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
