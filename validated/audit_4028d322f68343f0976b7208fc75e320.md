### Title
Duplicate authority votes can be padded to pass the BEEFY supermajority-participation gate without a real 2/3 signer quorum - ([File: evm/src/consensus/EcdsaBeefy.sol])

### Summary
The `AdvancedDistributor` bug is "no check that an action has already happened, so repeating it inflates a counted value (voting power) far beyond what the caller legitimately controls." The Hyperbridge BEEFY consensus verifier has the same missing-check pattern applied to signature counting instead of vote-minting: the supermajority check is computed from the *raw length* of the submitted votes array rather than the number of *distinct* authorities that actually signed, and no code path rejects a proof that repeats the same `authorityIndex`/signature pair.

`sigLen` is simply `votes.length` — there is no step anywhere in this function (nor in the mirrored Rust implementation, `modules/consensus/beefy/verifier/src/lib.rs::verify_mmr_update_proof`, which likewise computes `signatures_length = mmr.signed_commitment.signatures.len()` and feeds `authority_indices` straight into `merkle_proof.verify` without deduplication) that rejects a `votes`/`signatures` array containing the *same* `authorityIndex` (and its valid signature) more than once.

This is exactly the same root cause class as the report: the code counts an action ("this authority contributed a vote toward the 2/3 threshold") without checking whether that action was already counted, so a relayer can artificially inflate the count of signers by resubmitting a single valid signature multiple times under the same `authorityIndex`.

Notably, the codebase *does* explicitly guard against this exact class elsewhere — the Pharos consensus verifier dedupes participants before doing anything else: [2](#0-1) 

```
fn verify_validator_membership(...) -> Result<(), Error> {
    let deduped: alloc::collections::BTreeSet<&[u8]> = participants.iter().map(|k| k.as_ref()).collect();
    if deduped.len() != participants.len() {
        return Err(Error::DuplicateParticipant);
    }
    ...
}
```

The absence of an equivalent `DuplicateParticipant`/index-uniqueness check in the BEEFY ECDSA path (both Solidity and Rust) is the gap.

### Impact Explanation
BEEFY is the primary consensus client used to admit new `StateCommitment`s from Polkadot/Kusama parachains into Hyperbridge (`EvmHost`/`pallet-ismp` consensus update path). If an attacker (or a small colluding minority of validators, or a single compromised authority key) can pass `checkParticipationThreshold` by repeating one or a few valid signatures under distinct claimed vote slots, they can get a forged/unauthorized state commitment accepted as if backed by a genuine 2/3 supermajority. A forged state commitment is the root primitive for forging message delivery, membership/non-membership proofs, and ultimately token bridge mint/relayer-fee withdrawal proofs downstream — i.e., unbacked mint or unsound state commitment, which the validation rules for this exercise call out as an accepted, in-scope impact class.

### Likelihood Explanation
The consensus proof submission entry point (posting a `RelayChainProof`/BEEFY consensus message) is permissionless — any relayer can submit one. Exploitation requires possession of at least one valid authority signature over the target commitment (e.g., from a single malicious/compromised validator, or leaked signature data), which is a materially lower bar than obtaining genuine signatures from 2/3 of the authority set. I was not able to inspect the external `@polytope-labs/solidity-merkle-trees` `MerkleMultiProof.VerifyProof` implementation (it lives outside this repository's indexed contents) to confirm definitively whether it independently rejects duplicate `(index, hash)` leaf entries; if it does reject duplicates, the attack is blocked at that later step. This is a genuine gap in my verification and should be checked directly against that library before treating this as conclusively exploitable.

### Recommendation
In both `EcdsaBeefy.sol::verifyMmrUpdateProof` and `modules/consensus/beefy/verifier/src/lib.rs::verify_mmr_update_proof`, deduplicate `authorityIndex` values before computing `sigLen`/`signatures_length` and before running the participation-threshold check — mirroring the `verify_validator_membership` dedup pattern already used in the Pharos consensus verifier. Reject the proof (e.g., `DuplicateAuthorityIndex`) if any index appears more than once.

### Proof of Concept
1. Obtain (or compromise) one valid authority secp256k1 signature over a legitimate BEEFY commitment `commitmentHash`, along with that authority's Merkle-multiproof membership leaf/index in the trusted `authoritySet`.
2. Construct a `RelayChainProof.signedCommitment.votes` array that repeats this `Vote { signature, authorityIndex }` entry `N` times, where `N` is large enough that `sigLen = N` satisfies `checkParticipationThreshold(sigLen, authoritySet.len)` (i.e., `N >= 2/3 * authoritySet.len`), even though the true distinct-signer count is 1.
3. Submit this proof to `EcdsaBeefy.verify` (or the on-chain consensus-update entry point that calls it). Since `authorities[i]` is populated once per loop index regardless of duplication, and the same `(index, hash)` leaf is a legitimately valid entry in the authority-set Merkle tree, the multiproof verification step is not guaranteed to reject the duplicated entries — pending confirmation against the external `MerkleMultiProof` library, which could not be inspected here.
4. If the proof passes, the attacker forges acceptance of `relayProof.signedCommitment.commitment`'s MMR root / parachain state commitments without genuine supermajority backing, and can then bring updated `StateCommitment`s / `IntermediateState`s into Hyperbridge that were never actually finalized by 2/3 of the true validator set.

/// Verify that all participating validators are members of the trusted validator set.
fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}
