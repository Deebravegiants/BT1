### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` identity used by the application (from the `x-shopify-shop-domain` / `shopify-shop-domain` header) is read separately and never included in the signed data. `Registry.process` validates the HMAC and then hands `request.shop` straight to the app's webhook handler as the trusted tenant identifier, so the header can be swapped for any value without invalidating the signature.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from an unauthenticated header and is completely independent of the signed payload: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. it never touches the `shop` field: [3](#0-2) 

`Registry.process` accepts the request once the (body-only) HMAC is valid, and then forwards `request.shop` to the handler as the tenant identity, together with the body that was actually signed for a *different* shop: [4](#0-3) 

Because every shop that installs the app shares the same app-level `api_secret_key` (webhooks are signed with the app's secret, not a per-shop secret), any attacker who controls a shop that has the app installed can capture one of their own genuinely-signed webhook deliveries (valid `raw_body` + `x-shopify-hmac-sha256`), and then replay that exact body/HMAC pair to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds (it never inspected `shop`), and `Registry.process` calls the handler with `data.shop == "victim-shop.myshopify.com"` while `data.body` actually contains attacker-controlled/attacker's-own-shop content. This breaks the identity binding: *the shop the HMAC was computed for* ≠ *the shop the handler is told owns the payload*.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem hands the host application a `shop` value that the cryptographic signature never protected. Any host application that uses `WebhookMetadata#shop` to key per-tenant lookups, storage writes, or authorization decisions (a documented and expected usage pattern per the gem's own webhook processing example) can be made to associate attacker-supplied/attacker-controlled webhook content with an arbitrary victim shop, or vice versa. This matches the "Critical - cross-tenant access" impact category since it lets an unprivileged app-installer confuse or corrupt another tenant's webhook-driven state without possessing that tenant's credentials.

### Likelihood Explanation
Any unprivileged user who can install the app on their own store (a normal, unprivileged action) can capture a legitimately signed webhook (raw body + `x-shopify-hmac-sha256`) for their own shop, then replay it against the app's public webhook endpoint with a forged `shop-domain` header. No secrets, tokens, or privileged access are required — only observation of one's own webhook traffic, which is an ordinary capability of any app installer.

### Recommendation
Include the shop identity (and, ideally, topic/webhook-id) in the HMAC-covered signable content, or otherwise cryptographically bind the `shop-domain` header to the signed body before trusting it — e.g., require the host application to independently confirm that the `shop` reported by the webhook corresponds to a shop actually known to have installed the app for that specific webhook subscription/topic, or extend `to_signable_string` in `lib/shopify_api/webhooks/request.rb` to incorporate the shop domain and validate accordingly in `Utils::HmacValidator`.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Attacker triggers the webhook and captures the raw POST: `raw_body` and the `x-shopify-hmac-sha256` header genuinely computed by Shopify using the app's `api_secret_key`.
3. Attacker resends this exact `raw_body` + `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which only checks the HMAC over `raw_body` [1](#0-0)  — validation succeeds.
5. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)` [5](#0-4) , causing the host app to process attacker-controlled content under the victim shop's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
