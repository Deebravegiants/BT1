### Title
Hyperbridge-originated system requests dispatch with zero fee/payer and no default relayer reward, leaving system messages economically unattractive for relayers to deliver - ([File: modules/pallets/host-executive/src/lib.rs])

### Summary
This is the direct analog of the Sherlock finding "some liquidations will not be attractive for liquidators": just as some liquidation calls pay the liquidator nothing (pnl exceeds `lf`), several Hyperbridge system pallets dispatch ISMP `PostRequest`s with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` — i.e., zero fee and no payer to refund. No relayer is economically compensated for delivering these requests, so a permissionless relayer has no rational incentive to pick them up, and delivery depends entirely on altruism or a single operator self-relaying.

### Finding Description
Multiple pallets that originate ISMP requests from Hyperbridge itself dispatch with a zero `FeeMetadata`:
- `host-executive`'s `update_host_params` extrinsic: [1](#0-0) 
- `intents-coprocessor`, `token-governor`, and `pallet-relayer`'s own withdrawal-request dispatch path also use the same zero `FeeMetadata` pattern, as confirmed by grepping for `FeeMetadata { payer: [0u8; 32]...}` occurrences across `modules/pallets/host-executive/src/lib.rs`, `modules/pallets/intents-coprocessor/src/lib.rs`, `modules/pallets/relayer/src/withdrawal.rs`, and `modules/pallets/state-coprocessor/src/impls.rs`.

This zero-fee/zero-payer dispatch pattern is explicitly documented as a known, currently-live gap in `docs/outbound-request-incentivization.md`: [2](#0-1) 

The proposed remedy — `pallet-relayer`'s `OutboundRequestDeliveryReward` storage map and the `claim_outbound_request_delivery_reward`/`set_outbound_request_delivery_reward` extrinsics — exists in code: [3](#0-2) 

However, this reward is **opt-in and defaults to zero per `module_id`** (`ValueQuery`, default `0`), meaning "no reward" and "module not on the allowlist" are indistinguishable states: [4](#0-3) . I found no evidence of governance actually invoking `set_outbound_request_delivery_reward` for the `host-executive`, `intents-coprocessor`, `token-governor`, or `pallet-relayer` withdrawal module IDs in the runtime configuration I was able to inspect — the only call sites for `set_outbound_request_delivery_reward` are the pallet's own extrinsic definition and the design doc, not any runtime genesis/migration wiring.

Consequently, until (and unless) governance explicitly sets a non-zero reward for each of these module IDs, relayers have zero economic incentive to deliver: host-parameter propagation updates, host-executive fee-withdrawal instructions, intents-coprocessor cross-chain governance/oracle updates, token-governor messages, and the relayer pallet's own fee-withdrawal request to the destination `HostManager`.

### Impact Explanation
Undelivered system messages have concrete protocol-level consequences, not just user-app inconvenience:
- `pallet-relayer`'s own withdrawal request (dispatched via the same zero-fee path in `withdrawal.rs`) is how a relayer collects previously accumulated fees from `RELAYER_FEE_ACCOUNT` on the destination chain. If this specific system message stalls because no relayer values delivering an unrewarded transaction, relayer fee payouts can be permanently stuck (funds effectively frozen from the relayer's perspective) unless the relayer self-relays their own withdrawal.
- `host-executive`'s `update_host_params` is how governance-approved parameter changes (fee token, timeout, host manager rotation) propagate to destination EVM hosts. Undelivered updates leave destination chains running stale/incorrect host parameters, which can affect fee accounting or manager authority recognition on those chains.
- More generally, this creates a systemic single-point-of-failure: system message delivery is reduced to "whichever operator feels like doing it for free," undermining the permissionless relayer model Hyperbridge is built on.

This satisfies "a route unable to deliver messages" / permanent freezing of relayer-owed funds in the validation criteria.

### Likelihood Explanation
High likelihood in practice: this is not a hypothetical edge case like the liquidation report (which requires `pnl > lf`) — the zero-fee dispatch is the **default and only** code path for these system pallets today. The mitigation (`OutboundRequestDeliveryReward`) exists but is disabled by default and requires an explicit governance action per module that I could not confirm has been taken. Any period where governance has not configured a reward for a given module_id reproduces the unincentivized-delivery condition on every dispatch from that module.

### Recommendation
- Ensure governance sets a non-zero `OutboundRequestDeliveryReward` for every system module (`host-executive`, `intents-coprocessor`, `token-governor`, and the relayer pallet's own withdrawal module id) at genesis/runtime-upgrade time rather than leaving it as an opt-in post-deployment action, so there is no window where these dispatches are unincentivized.
- Consider treating "no reward configured" as a build/deploy-time invariant check (e.g., a runtime sanity test asserting all known system `module_id`s have non-zero rewards) rather than relying solely on manual governance follow-up.
- For the relayer pallet's own fee-withdrawal dispatch specifically, consider a guaranteed-delivery path (e.g., self-relay by the withdrawing relayer, or a protocol-funded minimum reward) since this path directly gates relayers' ability to collect funds owed to them — mirroring the original report's recommendation that "liquidators should have guaranteed payment."

### Proof of Concept
1. `host-executive::update_host_params` (or `intents-coprocessor`/`token-governor`/relayer withdrawal) is invoked, dispatching a `PostRequest` via `dispatch_request(DispatchRequest::Post(post), FeeMetadata { payer: [0u8;32].into(), fee: Default::default() })` — see `modules/pallets/host-executive/src/lib.rs:225-231`.
2. `pallet_ismp::child_trie::RequestCommitments` records the commitment, but no fee is escrowed since `fee == 0` and `payer` is the zero address.
3. A permissionless relayer scanning for profitable requests to deliver sees `fee = 0` and has no reason to submit the destination-chain delivery transaction (which costs real gas).
4. Unless `OutboundRequestDeliveryReward::<T>::get(module_id)` has been explicitly set to a non-zero value by governance for that specific `module_id` (verified nowhere in the runtime wiring I inspected), no relayer claim path exists either, so the request can sit undelivered indefinitely.
5. For the relayer-withdrawal case specifically, this directly blocks the relayer's own fee payout from `RELAYER_FEE_ACCOUNT`, since delivery is a precondition for the destination-side transfer.

**Note on uncertainty:** I could not access the parachain runtime genesis/migration code that would conclusively show whether `set_outbound_request_delivery_reward` has been called for these specific module IDs in a live deployment — this is based on the absence of call sites found via search across the indexed codebase, plus the documentation in `docs/outbound-request-incentivization.md` explicitly stating the zero-fee/zero-payer dispatch as an unresolved, current problem for these exact modules. If governance has, since that doc was written, wired up non-zero rewards for all four module IDs outside of what my searches covered, the practical severity would be reduced to a residual gap for any newly-added system module that is not yet allowlisted.

A regular cross-chain message that flows *through* hyperbridge has a fee attached at origin (the source chain transfers `fee.payer → RELAYER_FEE_ACCOUNT` and records `RequestPayments[commitment]` in pallet-hyperbridge's child trie). When a relayer delivers and the destination receipt lands back on hyperbridge, the existing `accumulate_fees` flow credits that fee to the relayer. That whole pipeline assumes a *user* paid at origin.

But hyperbridge itself originates requests too: host parameter propagation, host-executive updates, intents-coprocessor responses, token-governor messages, the relayer pallet's withdrawal request. Today these all dispatch with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` (see `modules/pallets/host-executive/src/lib.rs:228`, `modules/pallets/intents-coprocessor/src/lib.rs:486`, `modules/pallets/relayer/src/lib.rs:638`, and `modules/pallets/token-governor/src/impls.rs`). Zero fee, zero payer. So relayers have no economic reason to pick them up, and the only thing that keeps them flowing today is altruism.

		/// Pay the configured `OutboundRequestDeliveryReward` to the relayer
		/// that delivered a hyperbridge-originated request to the destination.
		///
		/// Unsigned. Spam-protected by `validate_unsigned` (the encoded
		/// payload becomes a unique tag, so a duplicate submission with the
		/// same `commitment` is rejected at the txpool stage).
		#[pallet::call_index(5)]
		#[pallet::weight({1_000_000})]
		pub fn claim_outbound_request_delivery_reward(
			origin: OriginFor<T>,
			claim: OutboundRequestDeliveryClaim,
		) -> DispatchResult {
			ensure_none(origin)?;
			Self::process_outbound_request_delivery_claim(claim)
		}

		/// Governance-set per-`module_id` reward for delivering a
		/// hyperbridge-originated request from that module. Setting
		/// `amount = 0` removes the module from the allowlist.
		#[pallet::call_index(6)]
		#[pallet::weight(<T as frame_system::Config>::DbWeight::get().reads_writes(0, 1))]
		pub fn set_outbound_request_delivery_reward(
			origin: OriginFor<T>,
			module_id: BoundedVec<u8, ModuleIdBound>,
			amount: BalanceOf<T>,
		) -> DispatchResult {
			T::RelayerOrigin::ensure_origin(origin)?;
			OutboundRequestDeliveryReward::<T>::insert(&module_id, amount);
			Self::deposit_event(Event::OutboundRequestDeliveryRewardUpdated {
				module_id,
				new_reward: amount,
			});
			Ok(())
		}
