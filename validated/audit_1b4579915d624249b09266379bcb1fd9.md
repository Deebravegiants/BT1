### Title
Webhook Shop/Topic Header Spoofing via HMAC That Only Covers Raw Body, Enabling Cross-Tenant Data Confusion - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` and `topic` from HTTP headers that are never included in the HMAC-signed material, while `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` as the tenant identity passed to the host application's handler. Because the same `api_secret_key` signs webhooks for every shop that installs a given app, this breaks the intended binding `hmac_verified_body == (shop, topic, body)` down to only `hmac_verified_body == body`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [4](#0-3) , and `HmacValidator.validate_signature` computes/verifies the HMAC exclusively over that string using the app's `api_secret_key` [5](#0-4) . Meanwhile `Request#shop` and `Request#topic` are read straight out of the `shopify-shop-domain` / `shopify-topic` (or `x-shopify-*`) headers with no cryptographic tie to the body [6](#0-5) . `Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching, then constructs `WebhookMetadata` using the unauthenticated `request.shop` and `request.topic` as the tenant/topic identity forwarded to the app's own webhook handler [7](#0-6) .

Because the `api_secret_key` is the same for a given app regardless of which shop installed it, a merchant who has legitimately installed the app (an "unprivileged internet user" relative to other tenants of the same app) can capture one of their own valid `body` + `X-Shopify-Hmac-Sha256` pairs (e.g., by triggering an `orders/create` webhook on their own store) and replay that exact body/HMAC to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a victim shop. `HmacValidator.validate` will pass because the body is untouched and the secret matches, yet `WebhookMetadata#shop` will report the victim's domain to the app's handler, causing the host application to misattribute (or otherwise cross-process) event data across tenants.

### Impact Explanation
This crosses the tenant boundary the gem is supposed to enforce for webhook processing: the `shop` value that applications use to route/attribute incoming webhook data is not covered by the same cryptographic check that authenticates the payload. This matches the "Critical - cross-tenant access" category, since a legitimate low-privilege installer of the app can make the library report attacker-chosen shop identity for data it forwards to the merchant's/app's own handler.

### Likelihood Explanation
Any user who can install the app on a shop (a routine, unprivileged action) can obtain a valid body+HMAC pair for their own tenant and immediately replay it against the app's public webhook URL with a different `shop-domain` header — no access to `api_secret_key`, tokens, or victim credentials is required, only network access to the endpoint the app already exposes for Shopify webhook delivery.

### Recommendation
Bind `shop` (and ideally `topic`) into the signed material actually verified, e.g., by having `Request#to_signable_string` incorporate the header values (as Shopify's own webhook signature covers only the body by design, the gem should independently validate that `shop-domain` corresponds to a session/shop that this app installation is expected to receive events for, and/or require correlation with the `webhook_id`/subscription record before trusting `request.shop` for routing) rather than passing the raw header value straight through as authenticated tenant identity.

### Proof of Concept
1. Attacker (merchant M) installs the target app and lets it register an `orders/create` webhook.
2. Attacker triggers an order to receive a legitimate webhook POST to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` valid for `H = HMAC(api_secret_key, B)`.
3. Attacker resends the identical `B`/`H` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds because `B`/`H` are unchanged and signed with the shared `api_secret_key` [8](#0-7) .
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [7](#0-6) , causing the host application to process attacker-supplied order data under the victim shop's identity.
