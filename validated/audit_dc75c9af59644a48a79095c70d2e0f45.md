### Title
`deserialize` in `public-key.ts` accepts non-hex/odd-length strings, silently producing a truncated `Buffer` instead of throwing - ([File: features/public-key-provider/module/store/formats/serialization/public-key.ts])

### Summary
`deserialize` in `features/public-key-provider/module/store/formats/serialization/public-key.ts` only asserts that `serialized` is truthy before calling `Buffer.from(serialized, 'hex')`, unlike its sibling `monero-public-key.ts` which explicitly checks `serialized.length === 2 * buffer.length` after conversion. Because Node's `Buffer.from(str, 'hex')` silently stops/truncates on invalid or odd-length hex instead of throwing, a corrupted or attacker-influenced `publicKey` string stored via the legacy storage format can be deserialized into a `Buffer` whose length/content does not correspond to the original serialized string, without any error being raised.

### Finding Description
The reachable call path is: `StorageFormatLegacyBuilder.get` (`features/public-key-provider/module/store/formats/storage/legacy.ts`, lines 74-86) returns an entry whose `publicKey` field only had to pass `assertStorageFormatLegacy`'s `serialization.publicKey.validateSerialized(publicKey)` check, which is merely `typeof serialized === 'string'` [1](#0-0) . That entry then flows into `PublicKeyStore.get` which calls `serialization.publicKey.deserialize(publicKey)` [2](#0-1) . The `deserialize` implementation itself performs no hex/length validation beyond truthiness: [3](#0-2) . Contrast this with `monero-public-key.ts`, which validates `serialized.spendPub.length === 2 * spendPub.length` etc. after conversion [4](#0-3) . Because `Buffer.from` on malformed hex (odd length, non-hex characters) truncates rather than throwing, strings like `'zz'`, `'123'`, or `'0x1234'` will produce a `Buffer` with unexpected length/content silently, and the resulting `PublicKeyBuffer` is returned to callers such as `PublicKeyProvider#exportPublic`/`getPublicKey` without further validation [5](#0-4) , and ultimately consumed for encoding/signing (e.g. `baseAsset.keys.encodePublic(publicKey, ...)` in `features/address-provider/module/address-provider.js`).

### Impact Explanation
If the persisted `StorageFormatLegacy` blob (hardware-wallet public key cache or synced/imported legacy data) is corrupted or attacker-influenced, this missing validation lets a malformed hex string pass through unnoticed as a valid `PublicKeyBuffer`, rather than failing fast. Downstream consumers that assume `PublicKeyBuffer` correctness (address derivation, `encodePublic`, signature verification) then operate on a corrupted/truncated key, which can cause address/key mismatches — receive addresses or signing keys diverging from the truly derived key. This matches a data-integrity/wrong-key persistence impact class scoped to storage compromise. Note that in the observed flow, `publicKeyStore.get` (and thus this deserializer) is primarily exercised for hardware wallets and, in dev builds, as a cache path, per `#exportPublic`'s `buildMetadata.dev || walletAccount.isHardware` gate [6](#0-5) ; in production for software wallets the key is always rederived from the keychain and not trusted from cache.

### Likelihood Explanation
Exploitation strictly requires that the attacker can already write/influence the persisted legacy storage blob (e.g., via imported backup or storage sync data), which is the explicit precondition given in the question. Given that precondition, producing a non-hex/odd-length string that passes `validateSerialized` (a bare `typeof === 'string'` check) and reaches `deserialize` is trivial and fully repeatable — no additional privilege or timing constraints apply beyond the storage-integrity assumption itself.

### Recommendation
Add the same post-conversion length/charset validation used in `monero-public-key.ts` to `public-key.ts`'s `deserialize`:
```ts
const deserialize = (serialized: PublicKey): PublicKeyBuffer => {
  assert(serialized, `publicKey was not a string`)
  const buf = Buffer.from(serialized, 'hex')
  assert(serialized.length === 2 * buf.length, `expected publicKey to be a valid hex string`)
  return buf
}
```
This ensures malformed hex throws instead of silently producing a truncated/mismatched buffer, matching the invariant already enforced in the Monero variant.

### Proof of Concept
Add a unit/fuzz test to `features/public-key-provider/module/store/__tests__/` (or a new test near `serialization/public-key.ts`):
```ts
import publicKeys from '../formats/serialization/public-key.js'

describe('public-key deserialize hex validation', () => {
  const invalidInputs = ['zz', '0x1234', '123', '']

  it.each(invalidInputs)('should throw or preserve length for %s', (input) => {
    let result
    try {
      result = publicKeys.deserialize(input)
    } catch {
      return // throwing is acceptable/expected
    }
    // if it didn't throw, length must match input length/2
    expect(result.length).toBe(input.length / 2)
  })
})
```
Currently `deserialize('zz')` returns an empty `Buffer` (length 0) without throwing and without the length matching `'zz'.length / 2 = 1`, and `deserialize('123')` truncates the trailing nibble silently — demonstrating the missing validation compared to `monero-public-key.ts`.
