### Title
Webhook `shop-domain` and `topic` are trusted from unauthenticated headers, not bound by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates an HMAC over the raw request body only. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values consumed by `ShopifyAPI::Webhooks::Registry.process` are read straight from HTTP headers that are never included in the signed payload, so the app trusts an unauthenticated claim about *which tenant* a webhook body belongs to.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are pulled directly from headers, none of which are covered by `to_signable_string`: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop` and `request.topic` to build `WebhookMetadata` and dispatch it to the app's handler: [3](#0-2) [4](#0-3) 

`HmacValidator.validate` (used both for OAuth and webhooks via the shared `VerifiableQuery` interface) only proves that `to_signable_string` was signed with `Context.api_secret_key`; it says nothing about the `shop`/`topic` headers because they are outside `to_signable_string`: [5](#0-4) [6](#0-5) 

The `client_secret` (`Context.api_secret_key`) used to compute the HMAC is a single, shared secret for the *app*, not per-shop — the same secret authenticates webhooks from every shop that has the app installed. Because the signature covers only body bytes and not the tenant identifier, two different tenants that happen to produce byte-identical bodies (which is common for topics like `shop/redact`, `customers/redact`, `app/uninstalled`, or any event with a small/templated payload) yield identical valid `(body, hmac)` pairs. An attacker who controls or operates their own shop with the app installed can capture a legitimately-signed `(raw_body, hmac)` pair from an event on their own store, then replay it to the app's public webhook endpoint with a forged `shopify-shop-domain` header pointing at a victim shop (and the matching `shopify-topic` header). `Registry.process` will accept the HMAC (it's valid for that body) and hand the handler a `WebhookMetadata` claiming `shop: <victim-shop>`, even though the victim never sent that event and the signature never bound the body to that shop.

This breaks the identity binding: `shop authenticated (by HMAC over signable bytes)` ≠ `shop acted upon (WebhookMetadata.shop, taken from an unsigned header)`.

### Impact Explanation
Any app built on this gem that keys persistence, entitlements, or side effects (e.g. marking a shop uninstalled, redacting/deleting customer data, updating subscription/billing state, writing order/customer records) off `WebhookMetadata.shop` can be made to attribute attacker-supplied, validly-signed body content to an arbitrary victim shop domain. This is a cross-tenant data/action confusion: the attacker never had the victim's access token or credentials, yet the app processes an event under the victim's tenant identity. For mandatory topics like `shop/redact` or `customers/redact`, this could trigger unwanted data deletion/redaction for a shop that never requested it; for `app/uninstalled`, it could cause an app to falsely deprovision a victim's tenant. This matches the Critical "cross-tenant access" impact category, since the trust boundary between tenants sharing one app secret is defeated.

### Likelihood Explanation
Exploitation requires only that the attacker: (1) install the target app on a shop they control (public apps are generally installable by anyone), (2) trigger or wait for a webhook event with a body identical or attacker-influenced enough to collide with a target topic/body shape, and (3) send a forged HTTP request with modified headers to the app's public webhook endpoint. No access token, `api_secret_key`, or privileged Shopify account is needed — this is reachable by an unprivileged internet user who can install a public app and reach the app's webhook route. Likelihood is elevated for topics with small/fixed-shape bodies (e.g. `shop/redact`, `customers/redact`, `app/uninstalled`) where byte-for-byte body collisions across tenants are trivial to obtain.

### Recommendation
Bind the tenant/topic identity into the signed payload rather than trusting headers outright:
- Include `shop-domain`, `topic`, and `webhook-id` in the bytes covered by `to_signable_string` (or otherwise cryptographically bind them to the body), and validate as part of HMAC verification, so a valid signature cannot be replayed against a different claimed shop/topic.
- At minimum, document/enforce that consuming apps must cross-check `WebhookMetadata.shop` against a shop this app instance has legitimate installation state for (with a recorded offline token) before trusting the payload, and reject `webhook_id` reuse (replay).

### Proof of Concept
1. App has two shops, `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both with the app installed (single shared `client_secret`/`api_secret_key`).
2. Attacker's own shop fires `shop/redact` (or any topic with a small/templated body, e.g. `{}`), and the attacker captures the raw body and the `X-Shopify-Hmac-Sha256` header Shopify sent for that request.
3. Attacker computes/observes that `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, raw_body)` — see `HmacValidator.compute_signature` — matches for any request with that exact `raw_body`, since headers play no role: [7](#0-6) 
4. Attacker POSTs the same `raw_body` + `hmac` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and `X-Shopify-Topic: shop/redact`.
5. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` and `Registry.process(request)` accept the request (`Utils::HmacValidator.validate(request)` passes because it only checks the body) and dispatch `WebhookMetadata.new(topic: "shop/redact", shop: "victim-shop.myshopify.com", ...)` to the app's handler, which performs the redact/action against `victim-shop.myshopify.com` — a shop that never requested it: [3](#0-2)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
