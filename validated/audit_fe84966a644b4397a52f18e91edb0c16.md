### Title
Unauthenticated arbitrary-call execution from Emporium combined with un-swept token approvals allows theft via leftover allowances - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When `stack.signerAddress == address(0)`, `verifyWallet` skips all signature checks on `stack.ops`, so any unprivileged caller can drive `runAction` with a fully attacker-chosen `EmporiumOperation[]` whose `op.endpoint` and `op.callData` are unrestricted (only the `callHinkalWallet`/`doSendToRelay` selectors are blocked). Combined with the min-circuit path (`erc20TokenAddresses = []`), the resulting `balancesBefore`/`balancesAfter` arrays are empty, so any asset movement triggered by the call is entirely unaccounted for. If Emporium ever has an outstanding ERC20 allowance to a router (from a prior op in any earlier transaction that approved a router but did not fully consume/revoke it), an attacker can call that router directly from Emporium in a later transaction and have it pull tokens via `transferFrom(emporium, attacker, amount)` using the stale allowance.

### Finding Description
Equality claimed broken: *the set of assets Emporium can move in a transaction* == *the set of assets accounted for in `balancesBefore`/`balancesAfter`*. In `runAction` [1](#0-0) , `balancesBefore`/`balancesAfter` [2](#0-1)  are computed exclusively over `circomData.erc20TokenAddresses`. For the min-circuit Emporium path this array is empty by design (`formInputEmporiumMin` is chosen precisely when `erc20TokenAddresses.length == 0`) [3](#0-2) , and the corresponding circuit, `MainEVMCircuitMin`, only proves knowledge of a `messageSeed` whose Poseidon hash equals an unconstrained output `message` — it carries no economic authorization at all [4](#0-3) . Thus any unprivileged EOA can trivially satisfy the proof requirement.

`verifyWallet` short-circuits with no signature check whenever `stack.signerAddress == address(0)` [5](#0-4) , meaning the entire `EmporiumOperation[]` (`endpoint`, `callData`, `value`) is attacker-chosen with zero authorization when going through CASE 2. The only defense in CASE 2 is a 4-byte selector blacklist against `IHinkalWallet.callHinkalWallet.selector`/`doSendToRelay.selector` [6](#0-5) ; it does not restrict `op.endpoint` to any allowlist, nor gate arbitrary calldata targeting third-party contracts.

Root cause: Emporium is a shared, non-per-user contract (state, including any ERC20 `allowance` it has granted to a router via a previous swap operation, persists across unrelated transactions and unrelated users), yet `runAction`'s only invariant check (`balancesBefore`/`balancesAfter` diff) is scoped to the caller-supplied `erc20TokenAddresses` array for the *current* call. Since this array is `[]` for the min-circuit flow, any asset egress driven by `op.endpoint.call(op.callData)` — including a `router.someSwap(...)` call that internally executes `token.transferFrom(emporium, attacker, amount)` against a stale allowance — is invisible to the balance/slippage machinery and never reverts via `BalanceChangeShouldBePositive`.

Attacker's exact call: submit `Hinkal.transact` with a trivial min-circuit proof, `circomData.erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and `externalActionMetadata` encoding an `EmporiumStack{ signerAddress: address(0), ops: [{ endpoint: R, invokeWallet: false, value: 0, callData: <R's swap/pull function with attacker as recipient> }] }`. `_externalTransact` routes this to `EmporiumUpgradeable.runAction` [7](#0-6) , which executes `op.endpoint.call{value: op.value}(op.callData)` with `msg.sender == Emporium` [8](#0-7) . Inside R, `transferFrom(emporium, attacker, X)` succeeds against the pre-existing allowance.

Why existing guards fail: `performHinkalChecks`/`getHashedCalldata` only bind `circomData` self-consistency (calldata-hash integrity), not authorization of ops content when `signerAddress==0` [9](#0-8) ; `rootHashExists`/nullifier logic is irrelevant since no UTXOs are spent; the selector guard only blocks two specific 4-byte values, not arbitrary third-party targets; the balance/slippage checks in both `Hinkal.transact` and `EmporiumUpgradeable.runAction` are computed only over an array the attacker controls and can set to empty.

### Impact Explanation
Critical — direct theft of protocol/shared-contract-held tokens (any allowance Emporium has extended to any external router from any prior legitimate swap that wasn't fully consumed or revoked) can be redirected to the attacker. Because Emporium is shared infrastructure, this is not limited to the attacker's own deposited funds; it can drain any stale allowance regardless of which user's transaction created it, and is repeatable for every token/router pair with a nonzero outstanding allowance until it is exhausted.

### Likelihood Explanation
Requires: (1) at least one prior legitimate Emporium operation left a nonzero ERC20 allowance to some router (a realistic byproduct of approve-then-swap patterns commonly used for DEX aggregator integration, especially with `approve(router, type(uint256).max)`-style patterns or partial-fill swaps), (2) attacker able to construct calldata against that specific router that pulls tokens to an attacker-controlled recipient (feasible for many router ABIs that accept a `to`/`recipient` parameter), and (3) attacker able to generate a valid Groth16 proof for `MainEVMCircuitMin`, which needs no privileged secret. All these preconditions are attacker-reachable without any privileged role, making this feasible whenever the allowance precondition exists.

### Recommendation
Do not allow ops to be replayed without authorization when `signerAddress == address(0)`; require `verifyWallet` to always cryptographically bind the exact `ops` array (endpoint/calldata/value) to an authorizing party regardless of signer address, or eliminate the fully-unauthenticated CASE 2 path entirely. Separately, enforce that Emporium never carries persistent allowances across transactions: always reset approvals to zero after use (`approve(router,0)` after swap), and restrict `op.endpoint` in CASE 2 to a governance-maintained allowlist of trusted routers rather than accepting arbitrary target addresses/calldata from an unauthenticated caller.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a mock `ERC20`, and a `MockRouter` that on `swap(address token, uint256 amount, address recipient)` calls `IERC20(token).transferFrom(msg.sender, recipient, amount)`.
2. Simulate a leftover approval: directly set `token.approve` from Emporium to `MockRouter` for `amount = 1000e18` (representing residual allowance from an earlier legitimate op), and mint `1000e18` tokens to Emporium (representing balance transiently present, e.g. from another concurrent op in the shared contract).
3. Craft `EmporiumStack{ signerAddress: address(0), ops: [{ endpoint: address(mockRouter), invokeWallet: false, value: 0, callData: abi.encodeCall(MockRouter.swap, (address(token), 1000e18, attacker)) }] }`.
4. Call `runAction` (or full `Hinkal.transact` with a trivially-satisfied min-circuit proof) with `circomData.erc20TokenAddresses = []`.
5. Assert: `token.balanceOf(attacker)` increases by `1000e18` and `token.balanceOf(emporium)` decreases by `1000e18`, while `balancesBefore.length == 0` and `balancesAfter.length == 0` (both sides of the claimed equality remain `[]`/unchanged), proving the transfer is completely unaccounted for and unblocked by any `require`.
