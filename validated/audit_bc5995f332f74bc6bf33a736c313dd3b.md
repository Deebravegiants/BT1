### Title
Repeated 1‑yoctoNEAR promise subsidy on zero-balance accounts allows unbounded token minting - (File: runtime/near-vm-runner/src/logic/logic.rs)

### Summary
`promise_batch_action_function_call_weight` (and its `promise_yield_create_with_id` twin) implement a `one_yocto_on_promise` exemption: if the attached amount is exactly 1 yoctoNEAR and the contract's *current* balance is zero, the deduction is skipped and the amount is instead recorded into `subsidized_amount`, which the runtime later treats as freshly minted supply. Because the balance check re-reads the same zero balance after every skipped deduction (the balance is never actually reduced or exhausted), this exemption can be triggered repeatedly within a single execution or across repeated executions from a zero-balance account, effectively minting unlimited yoctoNEAR instead of the single one-time compatibility subsidy it was designed for.

### Finding Description
The exemption logic:
```rust
// runtime/near-vm-runner/src/logic/logic.rs:3097-3112
let skip_deduct = amount == Balance::from_yoctonear(1)
    && self.config.one_yocto_on_promise
    && self.result_state.current_account_balance.is_zero();
if skip_deduct {
    self.result_state.subsidized_amount = self
        .result_state
        .subsidized_amount
        .checked_add(amount)
        .expect("subsidized_amount overflow");
} else {
    self.result_state.deduct_balance(amount)?;
}
``` [1](#0-0) 

The same pattern exists in `promise_yield_create_with_id` [2](#0-1)  and in both wasmtime-runner mirrors [3](#0-2) [4](#0-3) .

The key defect: when `skip_deduct` fires, `current_account_balance` is left untouched — it stays exactly zero. There is no counter limiting how many times this exemption may fire within one function-call execution, nor across repeated calls from the same zero-balance account. A contract with a genuinely zero NEAR balance can call `promise_batch_action_function_call` (or `promise_yield_create_with_id`) in a loop inside a single WASM execution, attaching 1 yoctoNEAR to each of many outgoing `FunctionCallAction`s targeting arbitrary receivers. Each iteration satisfies `amount == 1 && current_account_balance.is_zero()` and is subsidized — none of these deposits are ever actually debited from any account.

This is the same bug class as the reported Solidity issue: state (the “balance available to spend”) is checked once per call but never actually consumed/decremented across the loop, so the same “free” value can be reused an unbounded number of times per execution, rather than being a single one-shot exemption.

Downstream, `subsidized_amount` accumulated in the VM outcome is propagated to `ActionResult::subsidized_amount` [5](#0-4) , then summed into `BalanceStatsV1::subsidized_amount` per receipt [6](#0-5) , and finally subtracted from `total_balance_burnt` at the chain level:
```rust
// chain/chain/src/runtime/mod.rs:401-407
// Theoretically this may become negative but the subsidized amount is many orders
// of magnitude lower than the burned amount for each promise, so it should not happen.
let total_balance_burnt =
    burnt.checked_sub(apply_result.stats.balance.subsidized_amount).ok_or_else(...)?;
``` [7](#0-6) 
The doc comment on `BalanceStatsV1::subsidized_amount` explicitly states: *"Amount of balance subsidized (effectively minted) for zero-balance contracts attaching 1 yoctoNEAR to promise function calls."* [8](#0-7)  — confirming this mechanism is a real, protocol-acknowledged minting path, whose safety implicitly relies on the assumption that it fires "rarely" (once per otherwise-empty account), an assumption the loop scenario breaks.

Each subsidized 1 yoctoNEAR is attached as a genuine `FunctionCallAction` deposit in an outgoing receipt; when that receipt executes, the deposit is unconditionally added to the receiver account's real balance via `account.set_amount(outcome.balance)` in `execute_function_call`/`action_function_call`, independent of the callee's own logic [9](#0-8) . So the minted yoctoNEAR is realized as spendable balance on the receiving account, not just an internal accounting artifact.

The exemption is not restricted to any special "deterministic account" category — it applies to any contract account whose current balance happens to be zero, as confirmed by the config comment ("This lets deterministic accounts call functions like ft_transfer_call ... without needing to be seeded with balance first") and the generic implementation of `Config::one_yocto_on_promise` [10](#0-9) .

### Impact Explanation
This constitutes concrete token inflation: NEAR (in 1-yoctoNEAR increments) is created and credited to receiver accounts without ever being debited from any account's real balance. Although each individual increment is tiny (1 yoctoNEAR = 10⁻²⁴ NEAR), a single execution can invoke the vulnerable host function many times (bounded only by gas — hundreds/thousands of cheap `function_call_base`-cost promise actions fit in one ~300 Tgas transaction), and this can be repeated indefinitely across transactions/blocks by any actor who maintains a zero-balance contract account. Over time and across many transactions this is an unbounded, attacker-controlled minting primitive, matching the "concrete token inflation" acceptance criterion. It also silently corrupts the chain's balance-accounting invariant, which is exactly the mechanism the code comments acknowledge and rely on staying negligible.

### Likelihood Explanation
Reachable directly from an ordinary contract call: deploying a contract that holds a wasm binary invoking `promise_batch_action_function_call_weight` (or `promise_yield_create_with_id`) repeatedly on an account kept at zero balance, then dispatching a signed transaction that calls it, is fully within an unprivileged user's capability — no validator/node privilege needed. The only precondition is that the calling account's balance is exactly zero at the time of each call, which an attacker fully controls by deploying/using a purpose-built account they own with no NEAR balance (a "zero-balance account", explicitly a supported/first-class case per the code comments).

### Recommendation
Bound the `one_yocto_on_promise` exemption so it can only be exercised a small, fixed number of times per execution/receipt (e.g., cap it at one use per receipt, or track a monotonically-decreasing "subsidy budget" per account/epoch instead of re-checking `current_account_balance.is_zero()` on every call). Alternatively, remove the `current_account_balance.is_zero()` re-check per call and instead consume a one-shot flag in `ExecutionResultState` that is cleared after the first subsidized use, so repeated invocations within the same or subsequent receipts from the same zero-balance account do not each mint new value.

### Proof of Concept
1. Deploy a WASM contract to an account `attacker.near` and set/keep its NEAR balance at exactly 0 (a "zero-balance account", as already exercised by `setup_zba_global_contract` in the test suite [11](#0-10) ).
2. Have the contract's method loop N times, each iteration calling `promise_batch_create` for some victim receiver followed by `promise_batch_action_function_call` (or `promise_batch_action_function_call_weight`) with `amount = 1` yoctoNEAR, exactly mirroring the pattern validated in `test_one_yocto_on_promise_enabled` / `test_one_yocto_subsidy_tracked_in_stats` [12](#0-11) [13](#0-12) , but issued N times in a single call instead of once.
3. Because `current_account_balance` remains zero after each skipped deduction, every iteration satisfies `skip_deduct` and adds 1 yoctoNEAR to `subsidized_amount`, producing N outgoing `FunctionCallAction`s each carrying a genuine 1-yoctoNEAR deposit that gets credited to the receiver's real account balance once executed — with none of it ever debited from `attacker.near`.
4. Repeating this transaction across blocks accumulates unbounded minted NEAR, verifiable by observing `apply_result.stats.balance.subsidized_amount` growing without any corresponding balance decrease anywhere in the system (as tracked in the existing test `test_one_yocto_subsidy_tracked_in_stats`, which already demonstrates 2 yoctoNEAR minted from two independent zero-balance calls in one chunk) [14](#0-13) .

fn create_with_id_one_yocto_exemption_on_drained_zba() {
    use testlib::runtime_utils::alice_account;
    let (node, zba_id) = setup_zba_global_contract();
    let alice_id = alice_account();
    let balance_before = node.user().view_account(&zba_id).unwrap().amount;
    let subsidized_before = node.client.read().cumulative_subsidized;

    // Sign as alice (not zba) so that the gas reservation comes out of alice's
    // balance — keeping zba's balance untouched until the wasm runs. The gas
    // reward still goes to the receiver (zba).
    let args = drain_then_yield_args(&alice_id, balance_before, &[20u8; 32], &[6u8; 16], 1);
    let args_len = args.len() as u64;
    let res = node
        .user()
        .function_call(alice_id, zba_id.clone(), "call_promise", args, MAX_GAS, Balance::ZERO)
        .unwrap();

    assert_eq!(
        res.status,
        FinalExecutionStatus::SuccessValue(vec![]),
        "drain + 1-yocto via the exemption should succeed on a ZBA; got {res:?}",
    );

    // The exemption fires exactly once — confirm the runtime tracked it.
    let subsidized_after = node.client.read().cumulative_subsidized;
    let subsidy = subsidized_after.checked_sub(subsidized_before).unwrap();
    assert_eq!(
        subsidy,
        Balance::from_yoctonear(1),
        "expected exactly 1 yoctoNEAR of subsidy (the exemption), got {} yoctoNEAR",
        subsidy.as_yoctonear(),
    );

    // The wasm drains the entire account_balance, then the 1-yocto deduction is
    // skipped via the exemption — leaving VMLogic balance at 0. The runtime
    // sets account.amount = 0, the ZBA check lets that stand, and finally the
    // receiver gas reward is credited on top, so balance_after = reward exactly.
    let reward = contract_function_call_reward(&fee_helper(&node), &res, "call_promise", args_len);
    let view = node.user().view_account(&zba_id).unwrap();
    assert_eq!(
        view.amount, reward,
        "expected zba balance to equal exactly the gas reward (drained + subsidized + reward)",
    );
    assert!(
        view.storage_usage <= 770,
        "zba should still qualify as a ZBA after the call: storage_usage = {}",
        view.storage_usage,
    );
}

#[test]
fn test_one_yocto_on_promise_enabled() {
    let mut logic_builder = VMLogicBuilder::default();
    logic_builder.config.one_yocto_on_promise = true;
    logic_builder.context.account_balance = Balance::ZERO;
    logic_builder.context.attached_deposit = Balance::ZERO;
    let mut logic = logic_builder.build();

    let index = promise_create(&mut logic, b"rick.test", 0, 0).expect("should create a promise");

    // 1 yoctoNEAR should succeed even with zero balance
    promise_batch_action_function_call_weight(&mut logic, index, 1, Gas::ZERO, 0)
        .expect("1 yoctoNEAR should succeed with feature enabled");

    // 2 yoctoNEAR should still fail
    promise_batch_action_function_call_weight(&mut logic, index, 2, Gas::ZERO, 0)
        .expect_err("2 yoctoNEAR should fail with zero balance");

    // Transfer with 1 yoctoNEAR should still fail (feature only applies to function calls)
    let num_1u128 = logic.internal_mem_write(&1u128.to_le_bytes());
    logic
        .promise_batch_action_transfer(index, num_1u128.ptr)
        .expect_err("transfer should still fail with zero balance");

    assert_eq!(
        logic.result_state().subsidized_amount,
        Balance::from_yoctonear(1),
        "subsidized_amount should track the skipped deduction"
    );
}
