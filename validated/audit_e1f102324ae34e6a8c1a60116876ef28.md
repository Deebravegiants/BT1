### Title
Budget-capped hostile-preseed rebalance permits an LP seeded materially off curve-close price - ([File: packages/contracts/src/Bonding.sol])

### Summary
CVE-2021-28709 describes a class of bug where a hypervisor operation split into sub-steps only partially succeeds, and the caller/accounting layer treats the outcome as if it fully succeeded, producing an inconsistent final state. The analogous pattern in alt.fun is `Bonding._pairRebalance` / `_seedRebalancing`, called from the permissionless `finalizeGraduation` → `_seedUniswapV2Direct` path: the rebalance swap meant to correct a hostile pre-seeded HyperSwap pair back to the curve-close ratio is capped at `_swapBudget` (99% of the per-side inventory), and when that cap binds the swap only *partially* corrects the ratio, yet `_routerDepositAndDispose` proceeds to deposit and lock LP at the still-skewed ratio rather than escalating or retrying.

### Finding Description
`finalizeGraduation`'s Regime-3 defense (`_seedUniswapV2Direct` → `_seedRebalancing` → `_pairRebalance`) computes the no-fee swap input required to restore the pool to the cached curve-close ratio `(tokensForLP, ltFromPair)`: [1](#0-0) 

The swap input is capped at `_swapBudget`, 99% of the graduation's own inventory of the input side: [2](#0-1) 

When an attacker's mint pre-seed is lopsided enough (e.g. LT reserve 200× the curve-close target while TOKEN reserve is 1% of target), the *unconstrained* optimal rebalance swap exceeds this 99% budget, so `_pairRebalance`'s capped swap can only partially close the gap. `_seedRebalancing` does not detect or reject this "partial success" case — it proceeds straight to `_routerDepositAndDispose`, which deposits the router's `quote()`-optimal subset at whatever ratio the partially-rebalanced pool now holds and mints LP to `LPLock` at that price: [3](#0-2) 

The project's own regression test explicitly reproduces and names this as the "M-02" accepted residual: a 200× LT-rich pre-seed causes the budget-capped swap to leave the pool ~2× off curve-close, and `finalizeGraduation` still succeeds and locks LP at that skewed price: [4](#0-3) 

This is the direct P2M analog: an operation (`pair.swap` rebalance) that is executed against a budget-limited chunk (like PoD's order-split into smaller chunks) is only *partially* successful, and the surrounding logic (`_seedRebalancing`/`_routerDepositAndDispose`/`finalizeGraduation`) does not account for the shortfall — it commits the downstream, security-critical action (locking LP permanently via `LPLock.recordLock`, which "cannot skip") against the unreconciled, partially-corrected state.

### Impact Explanation
The immediate, measurable effect is that the locked, permanent HyperSwap V2 LP pool opens materially away from the bonding curve's closing price (the test asserts >20% price deviation in a realistic 200× pre-seed scenario, and the deviation scales with how lopsided the pre-seed is, up to the point the budget-capped swap consumes its full allowance). This is one of the explicitly in-scope harms per the validation criteria ("an LP seeded away from the curve close price"). A mispriced, permanently-locked LP:
- Misprices the token for every post-graduation trader routed through `Zap`/HyperSwap until arbitrage (if any) closes the gap, exposing traders to worse-than-fair execution immediately after graduation.
- Is irreversible: `LPLock` has no withdraw/rescue path in v1, so the mispriced position cannot be corrected once locked (`LPLock.recordLock` finalizes the position, as called out as a load-bearing invariant in `packages/contracts/AGENTS.md`).
- The team's own tests only assert the *pre-seeder* doesn't personally profit; they do not bound or prevent the price-integrity damage to third parties (other traders / the token's own price discovery), which is the actual harm covered by the "LP seeded away from curve close" criterion.

### Likelihood Explanation
This is reachable entirely by an unprivileged address using the documented, already-anticipated hostile-pre-seed technique:
1. Front-run `finalizeGraduation` by calling `factory.createPair(token, lt)` and `pair.mint(attacker)` with a wildly imbalanced ratio (e.g., dust TOKEN / large LT), exactly as documented in `packages/contracts/AGENTS.md`'s "HyperSwap Pre-Seed Defense" section.
2. Anyone (including the attacker) can then call the permissionless `Bonding.finalizeGraduation(token)`.
3. `_seedRebalancing`'s budget cap (`_swapBudget`, 99%) binds whenever the required corrective swap exceeds the graduation's own curve-raised inventory — a condition the project's fuzz test (`testFuzz_hostilePreSeed_neverProfitable_neverBricks`) shows is reachable for `seedMultiple` up to 1000×, i.e. any sufficiently large (but still cheap, since it's largely confiscated/burned) pre-seed.
The team is aware of this exact scenario (it is named and tested as "M-02"), and treats the price deviation as an "accepted residual" purely because the pre-seeder personally doesn't profit — but it does not evaluate or bound the damage to the LP's price integrity for other participants, which is a separate, in-scope harm class.

### Recommendation
- Detect when `_pairRebalance`'s swap is budget-capped (i.e., the unconstrained required input exceeds `maxSwap`) and, in that case, do not deposit at the residual skewed ratio. Options: (a) widen the per-side rebalance budget so it can always reach the target ratio using the full available inventory rather than capping at 99%, since mass conservation already forces disposal of the off-ratio remainder regardless; or (b) if a hard budget must remain for gas/degenerate-ratio reasons, add a second bounded iteration/second swap pass so multiple partial swaps compound toward the target before depositing, rather than depositing after a single partially-successful swap.
- Add an explicit maximum allowed post-swap price deviation from `ltFromPair/tokensForLP` before allowing `_routerDepositAndDispose` to proceed; if the deviation still exceeds a safe bound after the swap, prefer the `_seedDirectMint` fallback (which at least does not donate to a pre-existing skewed pool) or emit a distinct on-chain warning event so downstream integrators/keepers can react (e.g., pause further post-grad routing) instead of silently locking a mispriced pool.
- Extend `test/TwoPhaseGraduation.t.sol`'s M-02 coverage to also bound the *absolute* price deviation (not just pre-seeder P&L), and re-enable/re-add the removed profitability/end-to-end assertions referenced in `packages/contracts/AGENTS.md` ("This property was previously asserted directly but is no longer guarded by an automated test").

### Proof of Concept
Using the project's own existing test as the PoC (already demonstrates the vulnerable state transition):
```solidity
// packages/contracts/test/TwoPhaseGraduation.t.sol:864-917
function test_hostilePreSeed_budgetCappedSwap_isNotProfitable() public {
    (address tokenAddr,) = _launchToken();
    _enterGraduating(tokenAddr);
    (uint256 tokensForLP, uint256 ltFromPair,,) = bonding.pendingGraduation(tokenAddr);

    // Extreme LT-rich shape: TOKEN side at 1% of target, LT side at 200x.
    uint256 reserveToken = tokensForLP / 100;
    uint256 reserveLt = ltFromPair * 200;

    deal(tokenAddr, griefer, reserveToken);
    address hyperPair = _grieferMintPreSeed(tokenAddr, reserveToken, reserveLt);

    bonding.finalizeGraduation(tokenAddr); // succeeds, does NOT revert

    // Pool opens >20% off the curve-close price and is now permanently locked in LPLock
    assertGt(
        _poolPriceLtPerToken(hyperPair, tokenAddr),
        (((ltFromPair * 1e18) / tokensForLP) * 12) / 10
    );
}
```
This confirms: an unprivileged attacker, using only public calls (`factory.createPair`, `transfer`, `pair.mint`, `Bonding.finalizeGraduation`), can force a permanently-locked LP to open materially away from the bonding curve's closing price, with `finalizeGraduation`'s budget-capped rebalance swap being only partially successful and the downstream code committing the LP lock without accounting for that shortfall.

    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }

    function _pairRebalance(
        RebalanceParams memory p
    ) internal returns (bool) {
        uint256 s = _noFeeSwapInput(p.reserveIn, p.reserveOut, p.targetN, p.targetD, p.maxSwap);
        if (s == 0) return false;

        // Quote from the pair so the output tracks its live fee; a value
        // derived from a stale fee rate would trip the pair's K-check.
        uint256 expectedOut = IUniswapV2Pair(p.pair).getAmountOut(s, p.tokenIn);
        if (expectedOut == 0) return false;

        IERC20(p.tokenIn).safeTransfer(p.pair, s);
        (uint256 amount0Out, uint256 amount1Out) = p.tokenInIs0 ? (uint256(0), expectedOut) : (expectedOut, uint256(0));
        IUniswapV2Pair(p.pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
        return true;
    }

    ///         (no brick), the over-funded LT side must be confiscated to the
    ///         owner, and the pre-seeder must end net-negative.
    function test_hostilePreSeed_budgetCappedSwap_isNotProfitable() public {
        (address tokenAddr,) = _launchToken();

        (uint256 tokensForLP, uint256 ltFromPair,,) = bonding.pendingGraduation(tokenAddr);

        // Extreme LT-rich shape: TOKEN side at 1% of target, LT side at 200x.
        // The optimal TOKEN-in swap to reach the cached ratio is ~1.4x
        // `tokensForLP`, so the 99%-of-`tokensForLP` budget cap binds and the
        // pool stays ~2x off curve-close after the swap.
        uint256 reserveToken = tokensForLP / 100;
        uint256 reserveLt = ltFromPair * 200;

        // M-02 precondition: the optimal swap exceeds the budget (this is the
        // budget-capped regime, distinct from the swap-rounds-to-zero fallback
        // covered by the dust tests above).

            _noFeeSwapInputUncapped(reserveToken, reserveLt, tokensForLP, ltFromPair),

        deal(tokenAddr, griefer, reserveToken);
        address hyperPair = _grieferMintPreSeed(tokenAddr, reserveToken, reserveLt);
        uint256 grieferLp = MockHyperswapPair(hyperPair).balanceOf(griefer);
        uint256 ownerLtBefore = lt.balanceOf(bonding.owner());

        assertTrue(bonding.isGraduated(tokenAddr), "finalize must succeed despite an unrecoverable pre-seed");

        // pre-seed, so the pool opens materially off curve-close.

            _poolPriceLtPerToken(hyperPair, tokenAddr),
            (((ltFromPair * 1e18) / tokensForLP) * 12) / 10,
            "M-02 regime: pool opens materially off curve-close"
        );
