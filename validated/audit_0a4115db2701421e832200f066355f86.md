### Title
Webhook shop-domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` validates a webhook by HMAC-checking only the raw request body, while the `shop` (tenant identity) that gets dispatched to the app's `WebhookHandler` is read from an HTTP header that is never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)` [1](#0-0) , which calls `validate_signature`, computing the HMAC over `verifiable_query.to_signable_string` and comparing it against the `hmac` header value using the app's `api_secret_key` [2](#0-1) .

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [3](#0-2) . The `shop` accessor, however, is read directly from the `shop-domain` header and is *not* part of that signed string [4](#0-3) . After HMAC validation succeeds, `Registry.process` forwards `request.shop` straight into `WebhookMetadata` and into the app's handler as the tenant identifier, with no further check binding it to the signed body [5](#0-4) . `WebhookMetadata#shop` is a plain `String` field consumed by the host app's `WebhookHandler#handle` implementation for tenant-scoped logic [6](#0-5) .

This breaks the identity binding `verified_bytes == bytes acted upon`: the HMAC only authenticates the *body*, but the gem treats the unauthenticated `shop-domain` header as an authenticated tenant identity equivalent to a session key. Because a single app's `api_secret_key` is shared across every shop that installs the app, anyone who can install the app themselves (a normal, unprivileged action for a public app) receives genuinely-signed webhook deliveries for their own store. They can then replay that same body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with a victim shop's domain. `HmacValidator.validate` will still succeed (it never looks at the header), and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: the gem allows the shop identity to be forged independently of the cryptographic proof, in effect meeting the "shop authenticated versus shop used as an identity/session key" analog. Downstream app logic that trusts `WebhookMetadata#shop` for tenant-scoped operations (e.g., toggling app state, updating per-shop records, or triggering mandatory GDPR webhooks like `customers/redact`) can be made to act on/for the wrong tenant using a payload the attacker fully controls (their own webhook body) but with an arbitrary target shop.

### Likelihood Explanation
Requires only that the attacker be able to install the target app on their own store (readily available for public apps) to obtain one legitimately-signed webhook, and then send a forged HTTP POST to the app's webhook endpoint with a modified shop-domain header — no possession of `api_secret_key` or any other privileged credential is required.

### Recommendation
Include the `shop`, `topic`, and other trust-relevant headers in the HMAC-signed material (or independently verify that the shop-domain matches an active, previously-established session/installation for that shop) before dispatching to `WebhookHandler#handle`, rather than trusting the header value on its own.

### Proof of Concept
1. Attacker installs the target public Shopify app on their own store `attacker.myshopify.com`, receiving a legitimately Shopify-signed webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the shared `api_secret_key`), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends this exact `B`/`H` pair to the app's webhook endpoint but replaces the header with `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` are computed purely from `B` and the `hmac-sha256` header, so `Utils::HmacValidator.validate` returns `true` [7](#0-6) .
4. `Registry.process` builds `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: parsed_body, ...)` and invokes the app's handler believing the event genuinely originated from `victim.myshopify.com` [8](#0-7) .
