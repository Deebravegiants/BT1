### Title
Withdrawal status matched only by `assetId`, causing hash/status misreport for batched same-asset POA Bridge withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal()` resolves the completion status/tx-hash of a specific withdrawal (identified by `landingChain`, `index`, `withdrawalParams`, `tx`) by calling `findMatchingWithdrawal()`, which selects an entry from the POA Bridge API response **solely by `assetId`**, ignoring `index`, `amount`, and `destinationAddress`. If a batch of intents contains two or more withdrawals of the same token (same `assetId`) to different destinations/amounts within one NEAR transaction, the SDK can report the wrong withdrawal's completion status and `txHash` for a given `WithdrawalIdentifier`.

### Finding Description
`Bridge.describeWithdrawal()` is documented as a "one-shot status check for a withdrawal" that returns `{status, txHash}` keyed by a specific `WithdrawalIdentifier` (`landingChain`, `index`, `tx`) [1](#0-0) . Callers (e.g. `watchWithdrawal`) trust this per-identifier result to report a specific hash/status back to the integrator [2](#0-1) .

For the POA route, the matching logic is:
```
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
``` [3](#0-2) 

The comment above the function explicitly acknowledges: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported" [4](#0-3) . Yet `describeWithdrawal()` is called once per `WithdrawalIdentifier.index` for each withdrawal in a batch, without ever using `index`, `amount`, or `destinationAddress` to disambiguate:
```
async describeWithdrawal(args) {
	const response = await this.getWithdrawalStatusWithRetry(args);
	const withdrawal = findMatchingWithdrawal(
		response.withdrawals,
		args.withdrawalParams.assetId,
	);
	...
	return { status: "completed", txHash: withdrawal.data.transfer_tx_hash };
}
``` [5](#0-4) 

If the same NEAR transaction contains two `ft_withdraw` intents for the same `assetId` (e.g., two BTC withdrawals to different addresses/amounts in one batch), `Array.prototype.find` will return the **first** matching entry in the (documented as "unsorted") API response for **every** index that shares that `assetId`. Consequently `watchWithdrawal()` for withdrawal #2 could resolve with the destination `txHash` that actually belongs to withdrawal #1 (or vice versa), and could report `completed` prematurely for one leg while the other is still pending/failed.

This breaks the equality "status/hash reported == actual on-chain outcome for *this* withdrawal", the exact bug class highlighted in the CWE-284 analog (something reported as validated/true that was not actually checked against the specific request).

### Impact Explanation
An integrator that relies on `waitForWithdrawalCompletion`/`describeWithdrawal` per-withdrawal result to credit a user or release funds could:
- Credit/confirm withdrawal B as completed using the `txHash` that actually corresponds to withdrawal A (misattribution of on-chain proof), or
- Report `completed` too early for a withdrawal whose real settlement is still pending or failed, or
- Report `failed`/incorrect status for a withdrawal that in fact succeeded.

This matches the "status or hash misreport making an integrator credit or refund twice" impact category (High), since downstream systems that key off `describeWithdrawal`'s returned `txHash` to reconcile off-chain records could associate the wrong on-chain transaction with a given withdrawal request, or trigger a duplicate/incorrect settlement decision.

### Likelihood Explanation
Requires the caller of the intents-sdk to batch two or more withdrawals of the identical `assetId` (same token) in a single NEAR transaction via `createWithdrawalIntents`/`processWithdrawal` — a supported, documented feature ("Batch Processing: Process multiple withdrawals at a time") [6](#0-5) . No malicious relayer, bridge operator, or admin action is needed — this is purely a client-side data-association bug triggered by legitimate batch usage patterns (e.g., a service withdrawing the same token to multiple users in one transaction). The code comment itself confirms the authors are aware this scenario is unsupported/broken, which corroborates the finding.

### Recommendation
Disambiguate matching in `findMatchingWithdrawal` using more than `assetId`: match by `assetId` **and** `destinationAddress` **and** `amount` (and, if the API ever exposes it, an explicit per-withdrawal index/nonce). If the POA Bridge API cannot supply enough fields to uniquely identify a withdrawal, the SDK should refuse to support batching same-asset withdrawals in one transaction (throw explicitly, rather than silently mismatching), or serialize such batches into separate NEAR transactions. The `waitForWithdrawalCompletion` variant in `internal-utils` should undergo the same review, since it also matches only via `WithdrawalCriteria.assetId` [7](#0-6) .

### Proof of Concept
1. Build a batch of withdrawal intents where two entries share `assetId = "nep141:btc.omft.near"` but different `destinationAddress`/`amount` (supported per SDK batch withdrawal docs) and submit them in a single NEAR transaction.
2. Call `sdk.waitForWithdrawalCompletion` (or `PoaBridge.describeWithdrawal`) separately for `index: 0` and `index: 1` of the resulting `WithdrawalIdentifier`s, both pointing at the same `tx.hash`.
3. Because `findMatchingWithdrawal` filters only on `assetId` [8](#0-7) , both calls receive the same `withdrawals.find(...)` result (the first matching entry in the unsorted API array), regardless of `index`. Any consumer inspecting the returned `txHash` for withdrawal index 1 will actually observe the hash belonging to withdrawal index 0's on-chain settlement, misreporting the true destination/settlement of withdrawal 1.

Note: I could not fully trace how `sdk.ts`'s public batch-withdrawal orchestration (`waitForWithdrawalCompletion`, `processWithdrawal`) assigns/uses `index` across bridges within the remaining investigation budget; the `Bridge` interface and `PoaBridge` implementation confirm the `index` field is defined but unused in `describeWithdrawal`'s matching logic, which is the root cause identified here.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
