### Title
Permissionless `LockupFactory::create()` allows front-running/squatting of a target employee's deterministic lockup account, permanently blocking rightful lockup/vesting creation - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create()` is a public, unprivileged, `#[payable]` function that derives the new lockup contract's account ID **solely** from the caller-supplied `owner_account_id`, with no binding to the caller's identity, to any token/asset the caller must legitimately hold, or to any authorization from the intended owner or the NEAR Foundation. [1](#0-0) 

Because the target account ID (`sha256(owner_account_id)` prefix `.` factory account) is fully deterministic and predictable off-chain, any unprivileged user can pre-emptively call `create()` for any target `owner_account_id` with only the minimum attached deposit, permanently occupying that account. This is directly analogous to the referenced Trader Joe finding [M-03], where `createRJLaunchEvent()` let anyone with 1 Wei of `_token` claim a `getRJLaunchEvent[_token]` slot and block the rightful issuer.

### Finding Description
`create()` computes the deterministic lockup account ID from only the `owner_account_id` parameter: [2](#0-1) 

There is no check that `env::predecessor_account_id()` matches `owner_account_id`, no check that the caller is the NEAR Foundation, and no per-owner registry preventing a second (legitimate) attempt from choosing a different derivation — the address is fixed by `owner_account_id` alone. The `vesting_schedule` and `foundation_account_id` are entirely caller-supplied: [3](#0-2) 

If an unprivileged attacker calls `create()` first for a known/targeted `owner_account_id` (e.g., a known upcoming employee/investor grant recipient) with the minimum attached deposit (`MIN_ATTACHED_BALANCE = 3.5 NEAR`), a lockup contract will be deployed at the exact deterministic address that the NEAR Foundation (or legitimate funder) would later need for that same `owner_account_id`. Because NEAR account creation fails if the target account already exists, any subsequent legitimate `create()` call for the same `owner_account_id` will have its `create_account()` action fail, causing the whole promise batch to fail and the deposit to simply be refunded via `on_lockup_create`: [4](#0-3) 

The legitimate funder's transaction does not lose funds, but the rightful lockup contract (with the correct lockup amount, vesting schedule, and foundation-controlled termination rights) can never be deployed at that canonical address again — the attacker's minimally-funded, attacker-controlled contract (potentially with no `vesting_schedule`/`foundation_account_id`, stripping out the Foundation's intended termination rights) permanently squats the slot.

### Impact Explanation
This matches the in-scope impact "Permanent freezing, unrecoverable lock, or irrevocable loss of user or protocol funds in lockup release, vesting termination... flows" and "High. Unauthorized execution... state-transition bypass in ... lockup ... flows that lets an unprivileged user perform actions beyond intended authority." An unprivileged attacker can, for negligible cost, permanently prevent the NEAR Foundation from ever deploying the intended vesting/lockup contract for a specific target owner account, and/or supplant the Foundation's vesting-termination authority for that target with an attacker-chosen (or absent) `vesting_schedule`/`foundation_account_id` at the canonical, deterministic address.

### Likelihood Explanation
The `owner_account_id` values used for legitimate lockups (employees, investors) are typically knowable/guessable in advance by anyone tracking allocations, and `create()` requires only `MIN_ATTACHED_BALANCE` (3.5 NEAR) with no permission gate, per the documented design "It allows any user to create and fund the lockup contract." [5](#0-4) 

This makes the attack realistically and cheaply executable by any unprivileged actor who can predict or learn a target `owner_account_id` before the Foundation's real deployment transaction lands.

### Recommendation
Bind the derived lockup account ID to more than just the caller-suppliable `owner_account_id` (e.g., require `env::predecessor_account_id()` to be an authorized funder/foundation account for `create()`, or incorporate a nonce/whitelist check), or gate `create()` behind an allowlist of authorized funders so that only the Foundation (or its designated agents) can register a lockup for a given `owner_account_id`, closing the front-running/squatting window analogous to the recommendation in the referenced report (restrict privileged creation entrypoints).

### Proof of Concept
1. Attacker observes or learns that the NEAR Foundation intends to create a vesting lockup for `owner_account_id = "alice.near"`.
2. Attacker computes `lockup_account_id = sha256("alice.near")[:20] || "." || lockup_factory_account`.
3. Attacker calls `create(owner_account_id="alice.near", lockup_duration=..., vesting_schedule=None, ...)` on `LockupFactory`, attaching only `MIN_ATTACHED_BALANCE` (3.5 NEAR), per `lockup-factory/src/lib.rs` lines 107-122.
4. The lockup account is created and deployed at the deterministic address, with no vesting schedule/foundation termination rights.
5. When the NEAR Foundation later calls `create(owner_account_id="alice.near", ...)` with the real grant amount and vesting schedule, `create_account()` fails because the account already exists; the whole promise batch fails and the deposit is refunded per `on_lockup_create` (lines 171-198) — the legitimate vesting lockup for "alice.near" can never be deployed at the canonical address.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }

# Lockup Factory Contract

This contract deploys lockup contracts. 
It allows any user to create and fund the lockup contract.
The lockup factory contract packages the binary of the 
<a href="https://github.com/near/core-contracts/tree/master/lockup">lockup 
contract</a> within its own binary.

To create a new lockup contract a user should issue a transaction and 
attach the required minimum deposit. The entire deposit will be transferred to 
the newly created lockup contract including to cover the storage.

The benefits: 
1. Lockups can be funded from any account.
2. No need to have access to the foundation keys to create lockup.
3. Auto-generates the lockup from the owner account.
4. Refund deposit on errors.
