### Title
Stale `storageDepositFee` in cached `feeEstimation` causes user to overpay for storage that is registered before sign time - ([File: packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts])

### Summary
`estimateWithdrawalFee` computes `storageDepositFee = minStorageBalance - userStorageBalance` from a point-in-time RPC read and bakes it into `feeEstimation` (both `feeEstimation.amount`, via the `token_diff` quote, and `underlyingFees.NearWithdrawal.storageDepositFee`). `createWithdrawalIntents` later reuses that same stale `feeEstimation` object via `getUnderlyingFee(...)` without re-querying storage state, so if the destination account's NEP-141 storage is registered/topped-up between estimate and sign, the SDK still emits a non-zero `storage_deposit` field on the `ft_withdraw` intent and still deducts the equivalent value from the user via the `token_diff` intent.

### Finding Description
The claimed equality is:

`storage_deposit attached in ft_withdraw == max(0, minStorageBalance - storage_balance_of(destination))` evaluated **at execution time**, and this amount should be charged **exactly once**.

Trace:
1. `estimateWithdrawalFee` (packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts:194-268) reads current storage state via `getCachedStorageDepositValue(tokenAccountId, destinationAddress)` (line 225-229), computes `feeAmount = minStorageBalance - userStorageBalance` (line 244), gets a solver quote to cover it (`getFeeQuote`, line 246-257), and returns a `FeeEstimation` whose `amount` and `underlyingFees[NearWithdrawal].storageDepositFee` both encode this now-historical `feeAmount` (lines 259-267).
2. Later, `createWithdrawalIntents` (lines 110-149) is called with that same, now possibly-stale, `feeEstimation` object. It does **not** re-check storage state. It:
   - Emits a `token_diff` intent using `feeEstimation.quote` (lines 120-131), which deducts the swap input from the user's balance in the intents system.
   - Emits the `ft_withdraw` intent (via `createWithdrawIntentPrimitive`, `direct-bridge-utils.ts:49-60`) with `storage_deposit: getUnderlyingFee(args.feeEstimation, RouteEnum.NearWithdrawal, "storageDepositFee")` (direct-bridge.ts:137-141) — i.e., the exact stale value, not a freshly computed one.
3. `getCachedStorageDepositValue` (lines 273-300) only caches when storage is *already sufficient* (`result[1] >= result[0]`, line 295), so a "not-yet-registered" result is never cached — but that's irrelevant here, because `createWithdrawalIntents` never calls this function at all; it trusts the value carried in `feeEstimation`.

Exploit flow: An unprivileged actor (the withdrawing user, an integrator, or any third party who knows the public `destinationAddress`) can call the token contract's public `storage_deposit(account_id)` method directly to register/top-up the destination account's storage between the `estimateWithdrawalFee` call and the later `signAndSendWithdrawalIntent`/`createWithdrawalIntents` call using the cached `feeEstimation`. Because `storage_deposit` on NEP-141/NEP-145 token contracts is permissionless and callable by anyone for any `account_id`, no cooperation from the destination account is required.

At execution time, the on-chain `ft_withdraw` intent still carries `storage_deposit = feeAmount` (stale, non-zero) even though the account is now registered. Per the contract-types schema documentation for `FtWithdraw`/`IntentFtWithdraw` (`packages/contract-types/schemas/intents.schema.json:403-409`, `src/index.ts:490-494`): *"The amount will be subtracted from user's NEP-141 `wNEAR` balance. NOTE: the `wNEAR` will not be refunded in case of fail."* This confirms the wNEAR is debited from the user's intents balance unconditionally as part of processing this intent, while the on-chain `storage_deposit` call against an already-registered account will, per standard NEP-145 semantics, refund the excess NEAR to the caller (the `intents.near` contract itself), not back into the user's NEP-141 balance inside the intents system. The `token_diff` intent that paid for this (lines 120-131) already deducted the equivalent value from the user's balance in the same batch, so the user permanently loses that value with no path to recovery — it is not returned to their intents balance, and existing guards (`assert` in `withdrawalParamsInvariant`, `validateWithdrawal`, `compareAddresses`, `getUnderlyingFee`'s existence check) never re-validate storage state at sign time; they only check structural/route correctness, not staleness of the cached storage figure.

### Impact Explanation
The user's `wNEAR`-equivalent balance is debited via the `token_diff` intent (packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts:120-131) for a `storageDepositFee` that is no longer needed, and the corresponding `storage_deposit` amount attached to `ft_withdraw` (line 137-141) is refunded on-chain to `intents.near`'s own NEAR balance rather than credited back to the user. This is a fee overcharge extracted from the withdrawing user with no automatic refund mechanism visible in this SDK — matching the "fee overcharge" High-impact category. It is repeatable on every withdrawal where the timing window between estimate and sign is exploited (or simply where storage naturally becomes registered between the two calls, e.g., another concurrent withdrawal to the same destination, or a third party proactively registering storage), and does not require privileged access — any account can call the token contract's public `storage_deposit`.

### Likelihood Explanation
Preconditions: (1) the destination NEAR account is not yet registered with the token contract at estimate time (`minStorageBalance > userStorageBalance`), producing a non-zero `storageDepositFee`; (2) between `estimateWithdrawalFee` and the later sign/`createWithdrawalIntents` call using the cached `feeEstimation`, someone calls `storage_deposit` for that `destinationAddress` on the token contract. Cost to the attacker is a single trivial `storage_deposit` NEAR transaction (a few hundredths of a NEAR at most). This requires no special privilege, and is entirely feasible for any integrator flow that separates estimate and sign in time (e.g., showing a fee quote to the user before they approve/sign). Repeatable per withdrawal.

### Recommendation
Re-validate storage state (via `getCachedStorageDepositValue`) inside `createWithdrawalIntents` at sign time rather than trusting the `storageDepositFee` carried in the possibly-stale `feeEstimation`, and clamp the `storage_deposit` field and any associated `token_diff` swap amount to the freshly measured deficit (0 if already sufficient). Alternatively, invalidate/refresh the `feeEstimation` immediately before signing, or shorten/remove the "sufficient" caching path so `estimateWithdrawalFee` calls close to sign time reflect current chain state.
