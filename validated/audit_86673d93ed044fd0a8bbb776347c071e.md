### Title
Non-embedded session lookup trusts an unsigned cookie value as the session identifier - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
For non-embedded apps, `ShopifyAPI::Utils::SessionUtils.current_session_id` returns the raw value of the `shopify_app_session` cookie as the session ID used by the host application to look up a stored `ShopifyAPI::Auth::Session` (which contains the merchant's `access_token`). That cookie value is never HMAC-verified or otherwise bound to an authenticated identity by this gem.

### Finding Description
`current_session_id` branches on `Context.embedded?`. For non-embedded apps (and as a fallback for embedded apps without a JWT), it calls `cookie_session_id(cookies)`, which simply returns `cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]` verbatim: [1](#0-0) [2](#0-1) 

This value is used verbatim as the returned session ID with no cryptographic binding to the cookie's originator. Compare this with the JWT path (`session_id_from_shopify_id_token`), where the session ID is derived from `payload.shop` / `payload.sub`, both of which come from a JWT payload that is HMAC-verified against `Context.api_secret_key` before being trusted: [3](#0-2) [4](#0-3) 

For the cookie path there is no equivalent binding. `SessionCookie` is a plain struct with no signature field, and when it's set at the end of OAuth for non-embedded apps its `value` is simply `session.id` (e.g. `offline_shop.myshopify.com` or `shop.myshopify.com_12345`), sent as an ordinary `Set-Cookie`: [5](#0-4) [6](#0-5) 

The documented usage pattern instructs host apps to pass raw request cookies straight into `current_session_id`, and then use the returned string to load the session (and its `access_token`) from session storage: [7](#0-6) 

The broken identity binding is:
`session_id used to fetch the stored access_token == unauthenticated, attacker-controlled cookie bytes`

instead of the intended:
`session_id == value cryptographically derived from a verified shop/user identity`

Since session IDs for offline sessions are deterministically formatted as `"offline_#{shop}"` [8](#0-7)  and for online sessions as `"#{shop}_#{user_id}"` [9](#0-8) , these IDs are guessable/enumerable (shop domains are public, e.g. via the app's install list or `?shop=` parameter). An attacker who can set a cookie in their own browser (which is always possible — cookies are fully client-controlled unless cryptographically signed) can set `shopify_app_session=offline_victim-shop.myshopify.com` and have the host application's session storage return the victim shop's `Session` object, including its Shopify `access_token`, to the attacker's own authenticated flow.

### Impact Explanation
This is a session-fixation/cross-tenant-access primitive: an unprivileged internet user who can only control cookies sent in their own browser session can cause the host application (following the gem's documented API exactly as intended) to bind their request to a victim merchant's session and access token, since the gem never verifies that the cookie value was actually issued by itself/Shopify to that browser. This maps to "Critical - cross-tenant access, theft of a merchant access token" and to "High - session fixation."

### Likelihood Explanation
The vulnerable code path is the one explicitly documented as the intended non-embedded integration pattern [7](#0-6) , so any app following the docs is affected without any misuse of the API. Exploitation only requires the attacker to know or guess a target shop's domain (public information) and set a cookie value in their own browser — no secrets, tokens, or privileged access are required.

### Recommendation
Do not treat the raw cookie value as a trusted session identifier. Either:
- Sign/HMAC the cookie value (e.g., with `api_secret_key`) when it is set in `validate_auth_callback`, and verify that signature in `cookie_session_id` before returning it, or
- Store an opaque, unguessable, server-generated token in the cookie (unrelated to the deterministic `shop`/`user_id` session-id format) and map it server-side to the session ID, or
- At minimum, mark this behavior clearly as unsafe for host apps and require them to independently verify the cookie's authenticity (e.g., via a signed Rack session) before calling `current_session_id`.

### Proof of Concept
1. Victim installs the app for `victim-shop.myshopify.com`; the gem completes OAuth and creates offline session ID `offline_victim-shop.myshopify.com` stored with the shop's access token in the host's session storage.
2. Attacker, in their own browser, sets a cookie: `shopify_app_session=offline_victim-shop.myshopify.com` (shop domain is public/guessable).
3. Attacker sends any request to the host application; the host app (per documented usage) calls
   `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`.
4. `cookie_session_id` returns the attacker-forged value unmodified [2](#0-1) .
5. The host app loads the session for that ID from its session storage and uses it to make Shopify API calls — the attacker's request is now executed with the victim shop's access token, achieving cross-tenant access/token theft.

        def current_session_id(shopify_id_token, cookies, online)
          if Context.embedded?
            if shopify_id_token
              id_token = shopify_id_token.gsub("Bearer ", "")
              session_id_from_shopify_id_token(id_token: id_token, online: online)
            else
              # falling back to session cookie
              raise Errors::CookieNotFoundError, "JWT token or Session cookie not found for app" unless
                cookies && cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]

              cookie_session_id(cookies)
            end
          else
            raise Errors::CookieNotFoundError, "Session cookie not found for app" unless
              cookies && cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]

            cookie_session_id(cookies)
          end
        end

          raise Errors::MissingJwtTokenError, "Missing Shopify ID Token" if id_token.nil? || id_token.empty?

          payload = Auth::JwtPayload.new(id_token)
          shop = payload.shop

          if online
            jwt_session_id(shop, T.must(payload.sub))
          else
            offline_session_id(shop)
          end
        end

```markdown
#### Cookie
Cookie based authentication is not supported for embedded apps due to browsers dropping support for third party cookies due to security concerns. Non-embedded apps are able to use cookies for session storage/retrieval.

For *non-embedded* apps, you can pass the cookies into:
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)` for online (user) sessions or
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for offline (store) sessions.
```
