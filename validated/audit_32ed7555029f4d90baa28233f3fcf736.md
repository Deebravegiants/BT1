Webhook `shop` (and `topic`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw body only, while the `shop` (and `topic`) values that are handed to the app's handler as the tenant identity come from unauthenticated HTTP headers that are excluded from the signed payload. This breaks the equality that should hold between "the shop the signature was computed for" and "the shop attributed to the processed webhook data."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` and `Request#topic` are read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`) with no cryptographic binding to those values: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `computed_signature(verifiable_query.to_signable_string, secret)` against the `hmac` header — i.e., it only proves the body bytes were signed with the app's secret, not that the accompanying `shop-domain`/`topic` headers were: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then trusts `request.shop` (and `request.topic`) as-is to construct `WebhookMetadata`, which is passed to the app-provided handler as the authoritative tenant identity: [4](#0-3) [5](#0-4) 

The documented usage pattern explicitly relies on `data.shop` as the tenant key for downstream job dispatch (`shop_domain: data.shop`): [6](#0-5) 

**Broken identity binding (as an equality):**
`shop_attributed_by_gem == shop_domain_header` should equal `shop_the_hmac_was_computed_for`, but the gem only proves `hmac == HMAC(raw_body, secret)`. Since `shop-domain` (and `topic`) are excluded from `to_signable_string`, an attacker who possesses *any* validly-signed webhook body/HMAC pair for the app's secret (e.g., a webhook legitimately delivered to the app for their own, attacker-controlled shop, since merchants installing the app can trivially trigger real webhook deliveries for their own store) can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and/or `x-shopify-topic`) header value. `Utils::HmacValidator.validate` will still return `true` because it only checks the raw body against the secret, and `Registry.process` will forward the attacker-chosen `shop` value into `WebhookMetadata`, causing the host application to process/attribute the webhook payload to a shop the attacker does not control.

### Impact Explanation
This crosses the "cross-tenant access" boundary explicitly called out in scope: an attacker who can generate one legitimately-signed webhook (using their own installed instance of the app, which is a routine unprivileged action) can forge the reported `shop` identity for that payload to any other tenant string, tricking the host application into associating attacker-supplied webhook body content with a victim shop's identity in its own data model (e.g., misattributed order/product data, incorrect job queuing keyed by `shop_domain`, potential state corruption per tenant). This matches the required impact category of cross-tenant access via broken identity binding.

### Likelihood Explanation
Likelihood is significant for any app that installs on merchant stores: any store owner (an unprivileged actor relative to other tenants of the same app) can install the app, cause a real webhook to be sent (any topic they subscribe to, e.g. `orders/create`), capture the valid `(raw_body, hmac)` pair from their own webhook delivery, and replay it directly to the app's webhook endpoint with a forged `shop-domain` header. No access token, `client_secret`, or privileged credential is needed — only the ability to receive one's own webhook, which the whole point of installing an app self-serves.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the signed payload used by `to_signable_string`, or otherwise cryptographically bind them (e.g., verify `shop` against a value looked up from a session/store keyed by an authenticated identifier, not from the unauthenticated header alone) before handing them to `WebhookHandler#handle`.

### Proof of Concept
1. Install the app on shop `attacker-shop.myshopify.com` and subscribe to a webhook topic (e.g. `orders/create`).
2. Trigger the webhook (e.g., create an order in `attacker-shop`), capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify computed with the app's real `api_secret_key`.
3. Replay the exact same raw body and HMAC header to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only hashes `raw_body` per [1](#0-0)  and [7](#0-6) .
5. `Registry.process` forwards `shop: "victim-shop.myshopify.com"` (attacker-controlled) into `WebhookMetadata`, which the host application's handler treats as authoritative per the documented pattern [6](#0-5) , causing cross-tenant data attribution.
