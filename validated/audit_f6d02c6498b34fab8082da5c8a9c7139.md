### Title
Webhook `shop` header is trusted for tenant identification but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the HMAC signature over the raw request body only, while the `shop` (tenant identity) is read from a separate, unauthenticated HTTP header. The HMAC never binds the shop-domain header to the payload, so a valid signature only proves the request body originated from an app secret holder — it proves nothing about *which* shop the event belongs to.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but the `shop` accessor used downstream for tenant routing reads the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is completely outside the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.to_signable_string` against `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity passed into the handler, with no independent verification that the signed body actually belongs to that shop: [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(secret, body || shop)`, i.e. the shop the app acts on must equal the shop covered by the HMAC. Instead the actual binding is `hmac == HMAC(secret, body)` while `shop_acted_on = header["shopify-shop-domain"]` — a field acted on but never covered by the HMAC.

Since Shopify apps use a single `api_secret_key` shared across every installed shop (there's no per-shop webhook secret in this design), any party who can obtain one valid `(raw_body, hmac)` pair for a topic (e.g. by installing the app on their own store and receiving a real webhook) can resubmit that exact payload to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` will still succeed because only `raw_body` is checked, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event is from the victim shop.

### Impact Explanation
Cross-tenant impersonation: the app's webhook handler code operates on `request.shop`/`WebhookMetadata#shop` as the source of truth to look up a shop's session/access token or to key business logic (e.g., order fulfillment sync, GDPR data-request/redact handling). A holder of one valid signed webhook body can trigger the handler logic under an arbitrary victim shop's identity, causing the app to perform actions or process attacker-supplied data attributed to a tenant that never sent it. This satisfies the "cross-tenant access" criticial-impact class, since the boundary between shops (tenants) is broken using only a body/HMAC pair the attacker legitimately obtained for their own shop.

### Likelihood Explanation
Requires only: (1) the ability to install the target app on any shop (or otherwise obtain one legitimate webhook delivery, which is often just a matter of installing a public app), and (2) the ability to POST arbitrary headers/body to the app's public webhook endpoint (which is by definition internet-reachable). No access token, `client_secret`, or privileged account for the victim shop is needed — only a captured signed payload from any shop, which is realistically obtainable by any developer/attacker who installs the app once.

### Recommendation
Include the shop-domain (and/or webhook-id) as part of the signed material verified by the app, or otherwise bind the `shop` header to a value the app can independently corroborate (e.g., only trust `request.shop` after confirming a session/access-token record exists for it, never wholesale trust the header purely because the body HMAC validated). At minimum, document clearly that `request.shop` is NOT authenticated by `HmacValidator.validate`, and require handler implementations to cross-check the shop against their own stored session data before performing shop-scoped actions.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`. Shopify delivers a real webhook: body `B`, header `shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, B)`), header `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays this to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com` while keeping `B` and `H` unchanged.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac-sha256: H...})` is constructed.
4. `Utils::HmacValidator.validate(request)` returns `true` because `to_signable_string` only returns `B`, and `H` matches `HMAC(api_secret_key, B)` regardless of the shop header.
5. `Registry.process(request)` proceeds to call `handler.handle(data: WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed_body, ...))`, causing the app to process attacker-controlled webhook data under the victim shop's identity.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
