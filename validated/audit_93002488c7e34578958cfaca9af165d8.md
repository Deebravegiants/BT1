### Title
Unsigned integer wraparound in message staleness check allows bypass of the freshness/anti-replay guard - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`handler.HandleLegacyUserMessage` validates message freshness by comparing `uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec` against `uint(payload.Timestamp)`, where `payload.Timestamp` is a client-supplied `int64` field decoded from an unprivileged, internet-facing JSON payload. This mirrors the `TimeoutChecker.isTimeout` bug class: instead of validating/rejecting an out-of-range input, the code performs unsigned arithmetic/casts on a value that can be attacker-controlled and out of the expected domain, producing a wraparound that silently flips the result of the freshness check rather than reverting/erroring.

### Finding Description
The staleness check is: [1](#0-0) 

```go
if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) { //nolint:gosec // G115: comparing unix timestamps, both fit within uint
    h.lggr.Errorw("stale message")
    return callback.SendResponse(...ErrorCode: api.HandlerError...)
}
``` [2](#0-1) 

`payload.Timestamp` comes directly from the client-supplied `TriggerRequestPayload` (unmarshalled from the request body before any bound-checking), as seen in test helpers building this payload with an arbitrary `int64`: [3](#0-2) 

The code only checks `payload.Timestamp == 0` before performing the cast: [4](#0-3) 

`uint(payload.Timestamp)` converts an `int64` to `uint` (64-bit on most platforms). If a client sends a negative `Timestamp` (or one that is otherwise outside the sane window, e.g. far in the future), the conversion wraps to a very large unsigned value. Since the comparison is `uint(now)-maxAge > uint(payload.Timestamp)`, a wrapped/huge value on the right-hand side makes the inequality false, so the "stale message" branch is never taken — the same class of defect as the analog `isTimeout` bug, where `block.timestamp < timestamp` underflows instead of being explicitly rejected, producing a false (here, false-negative "not stale") result instead of a proper validation error.

### Impact Explanation
The freshness/staleness check is the only defense in this legacy handler path against replay of old or forged trigger messages before they are dispatched to all DON nodes: [5](#0-4) 
By supplying a crafted (negative or overflow-adjacent) `Timestamp`, an unprivileged external client can bypass this freshness gate entirely, allowing stale/replayed `web_api_trigger` messages to be forwarded to the DON's member nodes indefinitely, undermining the anti-replay guarantee the check is meant to provide. This does not directly cause fund loss but weakens a security control at the gateway boundary that node operators rely on to reject old/replayed requests.

### Likelihood Explanation
The `Timestamp` field is fully attacker-controlled in an unprivileged, internet-facing request (`HandleLegacyUserMessage` is invoked directly from `gateway.ProcessRequest` for messages arriving over the user-facing gateway server), and only an `== 0` sanity check is performed before the vulnerable cast. Crafting a message with a negative or otherwise out-of-range timestamp is trivial for any external caller, making this straightforward to trigger.

### Recommendation
Validate `payload.Timestamp` is within a sane, non-negative range (and not too far in the future) before performing any unsigned conversion/comparison, and perform the freshness comparison entirely in signed 64-bit arithmetic (e.g., `time.Unix(payload.Timestamp, 0)` compared via `time.Time.Before`/`Sub`) instead of casting to `uint`. Reject (return `UserMessageParseError`/`HandlerError`) rather than silently mis-evaluating when the timestamp is outside the expected domain.

### Proof of Concept
1. Craft a JSON-RPC legacy message with `payload.Timestamp = -1` (or any negative `int64`), signed correctly by a valid key, and method `web_api_trigger`.
2. Submit via the gateway's user-facing HTTP endpoint, which routes to `handler.HandleLegacyUserMessage`.
3. `uint(payload.Timestamp)` wraps to `18446744073709551615` (max uint64), which is always `> uint(now)-MaxAllowedMessageAgeSec`, so the staleness check's `>` condition is false and the "stale message" branch is skipped.
4. The message is forwarded to all DON member nodes as if freshly received, even though it carries an invalid/negative timestamp that should have been rejected.

Note: I could not directly view the `TriggerRequestPayload` struct's field type or the exact `MaxAllowedMessageAgeSec` type declaration in this session (index did not return their source), so I inferred `Timestamp` is `int64` from the test helper constructing the payload with an `int64`-parsed value; this should be independently confirmed by reading `core/capabilities/webapi/webapicap/event_trigger_generated.go` and `core/services/gateway/config` in a full checkout to verify exact types before remediation.
