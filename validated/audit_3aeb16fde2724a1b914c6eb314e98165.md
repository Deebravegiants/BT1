### Title
Webhook `shop`/`topic`/`webhook-id` identity headers are not covered by the HMAC, enabling cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`), the event `topic`, and the `webhook_id` from unauthenticated HTTP headers, while the HMAC signature that the library verifies is computed over the raw request body only. Any party able to obtain one legitimately signed `(body, hmac)` pair — trivially available to anyone who installs the app on their own store and receives a single real webhook — can replay that pair to the app's webhook endpoint while freely rewriting the `shop`, `topic`, and `webhook-id` headers, since none of them are bound by the signature check.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors read directly from HTTP headers with no cryptographic protection: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the signature purely as a function of `verifiable_query.to_signable_string` (the body) against `verifiable_query.hmac` (the `hmac-sha256` header) — it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` trusts this same HMAC check and then dispatches to the app's handler using the unauthenticated `request.topic` and `request.shop` values, treating them as the identity of the tenant/event that produced the webhook: [4](#0-3) 

Because the HMAC secret (`api_secret_key`) is shared by the app across **all** installing shops, an attacker who installs the target app on their own (unprivileged) shop can capture a real, validly-signed `(body, hmac)` pair from their own webhook traffic, then POST it to the app's webhook endpoint with the `shop-domain` header rewritten to point at a different, victim shop (and/or the `topic`/`webhook-id` headers rewritten to a different event type). The `HmacValidator.validate` check still passes because it only re-derives the signature from the untouched body, so the forged `shop`/`topic` identity is accepted and handed to the app's business logic as if it genuinely originated from the victim shop.

This is the same bug class as the reference report: a value is acted upon (`shop`/`topic`, used as the tenant/event key) that is not covered by the integrity check (the HMAC), letting the caller freely control a field the receiver believes is authenticated. Concretely, the broken identity binding is:
`shop_used_for_business_logic (request.shop, header-derived)` ≠ `shop_bound_by_signature (none — signature covers body only)`.

### Impact Explanation
This lets any party who can install the app on some shop (a low bar — matches "unprivileged internet user") impersonate webhook events for a different tenant shop, without ever needing the `api_secret_key`, an access token, or any credential belonging to the victim. Depending on how the host application keys behavior off `WebhookMetadata#shop`/`#topic` (e.g. `app/uninstalled`, `shop/redact`, GDPR/data-erasure topics, or app-specific state transitions), this can trigger cross-tenant state changes, data deletion, or false session/uninstall events for a shop the attacker does not control — a cross-tenant access impact under the given severity rubric.

### Likelihood Explanation
Moderate-to-high: the attacker only needs to (1) install the app on a shop they control to receive one legitimately signed webhook, and (2) send a crafted HTTP request replaying that body/hmac with forged `shop-domain`/`topic`/`webhook-id` headers to the app's public webhook endpoint. No secrets, tokens, or privileged access are required.

### Recommendation
Bind the identity headers into the signed material, or otherwise verify that the `shop-domain` header matches a shop known to have legitimately received that specific webhook (e.g., cross-check against the registered shop/session, not just the raw body HMAC). At minimum, document and enforce that `WebhookMetadata#shop`/`#topic` must not be trusted as authenticated identifiers unless additionally corroborated (e.g., against an active session for that shop), since the current `HmacValidator` only authenticates the body.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, triggering a real webhook (e.g., `orders/create`) to the app's webhook endpoint. Attacker captures the raw body `B` and the valid `X-Shopify-Hmac-Sha256: H` header (`H = HMAC-SHA256(api_secret_key, B)`).
2. Attacker crafts a new HTTP POST to the same webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - Header `X-Shopify-Topic: app/uninstalled` (forged, or any other registered topic)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and finds it equals `H` — validation passes because only the body is checked.
4. The app handler for the forged topic is invoked with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host application to act as though the victim shop sent this event.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
