### Title
Interest accrual can permanently freeze an oversized market before the borrow-index cap - (File: `common/src/rates/index.rs`)

### Summary
An unprivileged caller can trigger a permanent `MathOverflow` panic in market accrual once scaled debt multiplied by the next borrow index exceeds `i128::MAX`. Because the index cap is applied only after multiplication, it does not prevent the overflow. [1](#0-0) 

### Finding Description
`update_borrow_index` computes `old_index * interest_factor` before clamping the result to `MAX_BORROW_INDEX_RAY`. [1](#0-0)  Afterward, `calculate_supplier_rewards` multiplies scaled borrowed shares by both indexes to compute accrued interest, and either multiplication can exceed the RAY-scaled `i128` accounting ceiling. [2](#0-1) 

The pool applies this accrual on every market operation through `global_sync`, which loops over the elapsed time and calls `accrue_chunk`. [3](#0-2)  `accrue_chunk` calls `accrue_step` over the live `borrowed`, `supplied`, `borrow_index`, and `supply_index` values before committing new indexes. [4](#0-3) 

The strongest public trigger is `controller::update_indexes(caller, assets)` with `caller` set to the attacker and `assets` containing the affected `HubAssetKey`; the controller forwards the assets directly to the pool's `update_indexes`. [5](#0-4) 

### Impact Explanation
Once a market reaches the overflow boundary, every subsequent operation that first accrues the market reverts with `MathOverflow`. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, and bad-debt cleanup or recapitalization cannot safely recover the market without privileged code changes. The market's user funds are therefore permanently frozen under the deployed code path.

The in-repository regression test demonstrates the exact reachable state: approximately 98% utilization of a one-billion-token market reaches the RAY-value ceiling before `MAX_BORROW_INDEX_RAY`, after which both `withdraw` and `repay` panic with `MathOverflow`. [6](#0-5) 

### Likelihood Explanation
Likelihood is low because reaching the overflow boundary requires an extremely large market, sustained high utilization, and enough elapsed accrual for the debt-index product to approach `i128::MAX`. An attacker can supply and borrow through normal unprivileged flows, but doing so requires substantial collateral and capital. Nevertheless, no privileged action is needed to trigger the resulting failure: once the state exists, any address can call `update_indexes` and push the market over the boundary. [5](#0-4) 

### Recommendation
Bound scaled market totals to a safe multiple of `i128::MAX / MAX_BORROW_INDEX_RAY`, rather than only bounding raw token caps and indexes independently. Accrual should also pre-check whether `borrowed * new_borrow_index` and `supplied * new_supply_index` fit in the accounting domain; if not, clamp both the index and derived debt/value calculation before multiplication instead of allowing an uncatchable arithmetic panic. The same bound should be enforced in market configuration and share-mint paths so the unsafe state cannot be entered.

### Proof of Concept
1. Create or use a market with sufficiently high decimals and caps to admit a very large balance.
2. Through `controller::supply`, deposit `1_000_000_000 * 10^18` base units of the market token.
3. Supply enough collateral in another market and call `controller::borrow` for approximately 98% of that balance.
4. Leave the market at high utilization until the accrued borrow index makes `borrowed_scaled_ray * new_borrow_index / RAY` exceed `i128::MAX`.
5. Call `controller::update_indexes(attacker, vec![HubAssetKey { hub_id, asset }])`.
6. The pool accrual panics with `GenericError::MathOverflow` before the borrow-index cap can make the market safe.
7. Subsequent `withdraw` and `repay` calls panic at the same accrual step, as demonstrated by the regression test. [7](#0-6)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
