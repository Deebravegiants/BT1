### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop-identity forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the HMAC-signable content solely from the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Registry.process` validates only the body's HMAC and then trusts `request.shop` when constructing `WebhookMetadata` passed to the app's handler. This breaks the identity binding: `shop_that_produced_the_signed_bytes == shop_the_app_attributes_the_data_to`.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers, none of which are part of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` — which only checks `to_signable_string` (the body) against the secret — and then unconditionally forwards `request.shop` (an unauthenticated header) to the app's handler as the tenant identifier: [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. it authenticates the body bytes, never the `shop` header: [4](#0-3) 

Because a single app installation shares one `api_secret_key` (`Context.api_secret_key`) across *all* merchant shops that install it, and the shop identity is carried in a header outside the signed content, an entity with a legitimately signed webhook body (obtained from Shopify by controlling any shop where the app is installed, or from any leaked/replayed legitimate delivery) can present that same signed body with an arbitrary `shop-domain` header value. `Registry.process` and the downstream handler will accept it as valid and attribute the (attacker-influenced) body content to the victim shop named in the header, since nothing checks that the header's shop matches the shop that actually produced/owns the signed body.

This is the same "identity checked ≠ identity acted on" pattern in the referenced report (limit checked on `msg.sender`/bridge rather than the real depositor): here the HMAC authenticates only the body, but the field the application actually keys tenant-scoped effects on — `shop` — is taken from unauthenticated bytes.

### Impact Explanation
An app built on this gem processes webhooks keyed by `WebhookMetadata#shop` to route data to the correct merchant's tenant (e.g., updating/deleting records, triggering per-shop side effects). Because `shop` isn't bound to the HMAC-covered bytes, a malicious party can cause the library to hand off attacker-influenced data under a victim shop's identity to the host application's webhook handler — a cross-tenant data-attribution issue at the point where this gem hands trust boundaries to the app. This matches the Critical criterion "cross-tenant access" since the shop-domain claim carries no cryptographic binding to the payload it accompanies.

### Likelihood Explanation
Requires the attacker to be a legitimate merchant/tenant of the target app (to obtain at least one genuinely-signed webhook body/HMAC pair for the shared app secret) and to be able to submit HTTP requests to the app's public webhook endpoint with attacker-chosen headers — both are unprivileged-internet-user-reachable conditions once the app is installed by any shop, since no access token or `client_secret` disclosure is needed and the header can be freely set by any HTTP client hitting the endpoint. Real-world exploitability further depends on the host application's routing (many frameworks pass raw headers through to gem consumers unfiltered), which is consistent with how `Request.new` reads headers in this gem.

### Recommendation
Either (a) require callers/library to bind `shop` into the signed materials it validates (e.g., include the `shop-domain`, `topic`, and `webhook-id` headers in `to_signable_string` so `HmacValidator` authenticates them along with the body), or (b) document/require that `Registry.process` cross-check `request.shop` against an expected/allow-listed shop for the currently active session/tenant context before invoking the handler, rather than trusting the header outright.

### Proof of Concept
1. App installs on `shop-a.myshopify.com`; attacker controls this shop and triggers a webhook (e.g. `orders/create`), capturing the genuine Shopify-delivered `raw_body` and its valid `x-shopify-hmac-sha256` value (both computed with the app's single shared `api_secret_key`).
2. Attacker replays the same `raw_body` + valid `hmac` to the app's public webhook endpoint but sets `x-shopify-shop-domain: shop-b.myshopify.com` (the victim shop, also installed the same app).
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers as-is; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unchanged) body bytes: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: <attacker's body>, ...)` — data the app will process/store as if it legitimately originated from `shop-b`, even though it never came from Shopify for that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
