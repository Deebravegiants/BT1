## Finding

### Title
Lockup account addresses are derived only from `owner_account_id`, letting an attacker front-run and permanently squat a victim's lockup contract before the intended (vesting-protected) lockup can ever be created - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` derives the address of the to-be-deployed lockup contract deterministically from `sha256(owner_account_id)` and the factory account, with no dependency on the caller/`predecessor_account_id`, deposit, or a caller-chosen salt. Because the resulting account ID is fully public and predictable, and the factory does not verify that the caller is authorized to create a lockup for a given `owner_account_id`, an unprivileged attacker can pre-create (front-run) the deterministic lockup account for a victim with attacker-chosen (weak) parameters — e.g., no vesting schedule and zero lockup duration — using only the minimum required deposit. Once that account exists, any subsequent, legitimate `create()` call for the same `owner_account_id` (e.g. one initiated by the NEAR Foundation with a real vesting schedule) will fail at the `create_account()` step and be refunded via `on_lockup_create`, permanently preventing the intended vesting-protected lockup from ever being deployed at the canonical address for that owner. This mirrors the Astaria root cause: a deterministically pre-computable deployment address combined with no state-corruption/pre-existence guard lets an unprivileged actor permanently deny legitimate contract creation for a target address.

### Finding Description
In `create()`:
```rust
let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
let lockup_account_id =
    format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());
...
Promise::new(lockup_account_id.clone())
    .create_account()
    .deploy_contract(CODE.to_vec())
    .transfer(env::attached_deposit())
    .function_call(b"new".to_vec(), ... )
    .then(ext_self::on_lockup_create(...))
``` [1](#0-0) 

The only requirement to call `create` is `env::attached_deposit() >= MIN_ATTACHED_BALANCE` (3.5 NEAR): [2](#0-1) [3](#0-2) 

There is no check that `predecessor_account_id() == owner_account_id`, no reservation/registry preventing a second party from claiming a given owner's slot first, and no verification that the target account does not already exist before submitting the `create_account` promise. The callback `on_lockup_create` treats any failure (including "account already exists") identically to a normal creation failure and simply refunds the deposit to whoever called `create` this time:
```rust
if lockup_account_created {
    ...
    true
} else {
    ...
    Promise::new(predecessor_account_id).transfer(attached_deposit.0);
    false
}
``` [4](#0-3) 

Since `hex(sha256(owner_account_id))[..20] + "." + factory_account_id` is deterministic and public, anyone can precompute the target account for any `owner_account_id` before the intended party (e.g., NEAR Foundation) submits their transaction, exactly as the Astaria attacker precomputed the CREATE2 vault address. The attacker only needs to submit their own `create()` call first (front-run), passing the same `owner_account_id` with minimal/weak parameters (e.g., `vesting_schedule: None`, `lockup_duration: 0`), funded with just `MIN_ATTACHED_BALANCE`.

### Impact Explanation
This is a **High** severity state-transition bypass: an unprivileged user can occupy the canonical lockup address intended for a victim before the legitimate (vesting/lockup-protected) contract is created, permanently preventing the correct lockup terms from ever being established at that address (the legitimate large-deposit `create()` call will fail and be refunded, but a new account cannot be created at the same ID). This effectively bypasses the vesting/lock-up protection mechanism entirely for a targeted `owner_account_id`, letting the attacker force an owner into a contract of the attacker's choosing (or block a real one from ever forming at the deterministic address). It maps to the Allowed Impact category of "state-transition bypass ... in lockup ... flows that lets an unprivileged user perform actions beyond intended authority" and also risks "irrevocable loss/inability to set up proper vesting protection" for the intended lockup/vesting flow.

### Likelihood Explanation
Likelihood is high for any attacker who can predict or observe an intended `owner_account_id` before the legitimate lockup-creation transaction lands (e.g., by monitoring mempool/public announcements of upcoming vesting grants, or simply targeting well-known account IDs preemptively). The attack requires only a single unprivileged `create()` call and 3.5 NEAR plus gas — no special role or timing precision beyond normal transaction front-running, which is readily achievable on NEAR given visibility into pending transactions or predictable grant recipients.

### Recommendation
- Bind the derived lockup account to the caller as well as (or instead of) only `owner_account_id`, e.g., include `predecessor_account_id` or a factory-side nonce/registry in the address derivation, or require `predecessor_account_id() == owner_account_id` for self-service creation and have the Foundation use a distinct authorized flow for vesting grants.
- Before issuing the `create_account` promise, check (or track in contract state, as the staking-pool-factory does with `staking_pool_account_ids`) whether a lockup has already been created for a given `owner_account_id`, and reject/react appropriately instead of silently allowing squatting.
- Consider requiring privileged (foundation) authorization for lockups that include a `vesting_schedule`, so an attacker cannot preclude a vesting lockup by squatting the address with a vesting-less variant.

### Proof of Concept
1. Attacker observes (or predicts) that the Foundation intends to create a vesting lockup for `owner_account_id = "victim.near"`.
2. Attacker computes `lockup_account_id = hex(sha256("victim.near"))[..20] + "." + "lockup.nearnet"` off-chain — this is fully deterministic per `lockup-factory/src/lib.rs:119-121`.
3. Attacker front-runs and calls:
```
near call lockup.nearnet create '{"owner_account_id":"victim.near","lockup_duration":"0"}' --accountId attacker.testnet --amount 3.5
```
This succeeds and deploys a no-vesting, zero-duration lockup at the deterministic address, owned by `victim.near` but funded/configured by the attacker.
4. The Foundation later calls:
```
near call lockup.nearnet create '{"owner_account_id":"victim.near","lockup_duration":"...","vesting_schedule":{...}}' --accountId foundation.near --amount 1000000
```
5. The `create_account()` promise for the same deterministic `lockup_account_id` fails because the account already exists; `on_lockup_create` refunds the 1,000,000 NEAR deposit back to the Foundation, and the intended vesting-protected lockup is never created at that address. [5](#0-4)

    #[payable]
    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

        let transfers_enabled: WrappedTimestamp = TRANSFERS_STARTED.into();
        Promise::new(lockup_account_id.clone())
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                near_sdk::serde_json::to_vec(&LockupArgs {
                    owner_account_id,
                    lockup_duration,
                    lockup_timestamp,
                    transfers_information: TransfersInformation::TransfersEnabled {
                        transfers_timestamp: transfers_enabled,
                    },
                    vesting_schedule,
                    release_duration,
                    staking_pool_whitelist_account_id,
                    foundation_account_id: foundation_account,
                })
                    .unwrap(),
                NO_DEPOSIT,
                gas::LOCKUP_NEW,
            )
            .then(ext_self::on_lockup_create(
                lockup_account_id,
                env::attached_deposit().into(),
                env::predecessor_account_id(),
                &env::current_account_id(),
                NO_DEPOSIT,
                gas::CALLBACK,
            ))
    }

    /// Callback after a lockup was created.
    /// Returns the promise if the lockup creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
