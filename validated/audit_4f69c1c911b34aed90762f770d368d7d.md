### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields are read from unauthenticated HTTP headers and passed straight through to the app's webhook handler. `Utils::HmacValidator` verifies only that `hmac` matches `to_signable_string` (the raw body), never that the header-derived `shop` is bound to that HMAC. This breaks the equality that should hold: `shop used to identify the tenant == shop covered by the verified signature`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read straight from HTTP headers, none of which are part of the signed string: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` trusts this HMAC check as the sole authenticity gate, then immediately forwards the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` header values into `WebhookMetadata`, which is handed to the app's own `WebhookHandler#handle`: [4](#0-3) [5](#0-4) 

Because the client secret used to compute the HMAC is per-app (shared across every shop that has the app installed), a body+HMAC pair that is valid for the attacker's own shop (an unprivileged internet user can legitimately install the app on their own store and capture a genuine `raw_body`/`x-shopify-hmac-sha256` pair from a real webhook delivery) remains a valid `(body, hmac)` pair regardless of which `shop` header accompanies it. An attacker can replay that exact `raw_body` and `hmac` to the app's webhook endpoint while substituting `x-shopify-shop-domain` (or `shopify-shop-domain`) with a victim shop's domain. `HmacValidator.validate` still returns `true` because it never inspects the shop field, so `Registry.process` proceeds and calls the app's handler with `WebhookMetadata.new(shop: <victim-shop>, ...)`, i.e., the equality `shop authenticated by HMAC == shop acted upon by the handler` is broken — the shop is acted upon (used as the tenant key for whatever the host app does with the webhook data) but is not covered by the cryptographic binding.

### Impact Explanation
This qualifies as cross-tenant access under the High-severity bucket in scope: an unprivileged actor who legitimately controls one shop/app installation can forge a webhook payload that the app's HMAC check will accept as authentic for a different, victim shop. Any host application that trusts `WebhookMetadata#shop` to select which tenant's data to create/update (a documented, expected usage pattern of this library, since the gem explicitly hands `shop` to the handler as the tenant identifier) can be tricked into writing or acting on attacker-controlled webhook body data under the wrong shop's identity — a tenant-isolation break stemming directly from this gem's own signature-validation code rather than any host-side misuse.

### Likelihood Explanation
The prerequisite (obtaining one valid `raw_body`/`hmac` pair) is trivially available to any unprivileged user who installs the app on a store they control — the app's client secret is shared across all shops using the app, so no victim-specific secret or credential is needed. Only the ability to send an HTTP POST to the app's public webhook endpoint with attacker-chosen headers is required, which is exactly the capability an internet-facing webhook endpoint exposes.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values in the signable string used for HMAC verification, or otherwise cryptographically bind the shop domain to the payload before trusting it (e.g. verify against a known/registered shop for this delivery, or require the caller to additionally validate the delivered shop against their own webhook registration records) inside `Request#to_signable_string` / `HmacValidator.validate`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`; the app registers a webhook (e.g. `orders/create`).
2. Attacker triggers a real event so Shopify sends a legitimate webhook: `raw_body = B`, header `x-shopify-hmac-sha256 = H` (valid per `test/webhooks/registry_test.rb:284-298` pattern, computed as `OpenSSL::HMAC.digest(sha256, client_secret, B)`), header `x-shopify-shop-domain = attacker.myshopify.com`.
3. Attacker replays the exact same request to the app's public webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`, keeping `raw_body = B` and `x-shopify-hmac-sha256 = H` unchanged.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds (see `lib/shopify_api/utils/hmac_validator.rb:12-31` and `lib/shopify_api/webhooks/request.rb:35-38`).
5. `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...))` is invoked, so the host app processes attacker-controlled body content as if it came from `victim.myshopify.com`.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
