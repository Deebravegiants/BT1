Audit Report

## Title
CORS wildcard-origin allowlist uses unanchored suffix matching, letting attacker-registered domains bypass host validation - ([File: core/services/gateway/network/httpserver.go])

## Summary
`isAllowedOrigin()` in `core/services/gateway/network/httpserver.go` implements wildcard host allowlisting (`*.example.com`) using an unanchored `strings.HasSuffix` check on the raw hostname string rather than a boundary-aware subdomain match. Any attacker-registered domain that merely ends with the configured suffix (e.g., `evilremix.com` against `*.remix.com`) is treated as trusted, allowing CORS trust intended only for genuine subdomains to be granted to an unrelated attacker-controlled origin.

## Finding Description
`isAllowedOrigin` splits the incoming `Origin` header and each configured `CORSAllowedOrigins` entry into scheme/host/port via `splitURL`, then performs an exact-match check followed by the flawed wildcard fallback: [1](#0-0) 

When an entry is configured as `*.remix.com`, the `*.` prefix is stripped, leaving `allowedHost = "remix.com"`, and the code checks `strings.HasSuffix(originHost, allowedHost)` with no verification that a `.` character precedes the match or that the match begins at a DNS label boundary. Consequently, `originHost` values such as `evilremix.com`, `notremix.com`, or `attacker-remix.com` all satisfy the suffix check despite not being subdomains of `remix.com`. [2](#0-1) 

This function is invoked directly from `handleRequest` on every gateway request when `CORSEnabled` is true, using the caller-supplied, unauthenticated `Origin` header, and its boolean result directly controls whether `Access-Control-Allow-Origin` is reflected back with the attacker's own origin value: [3](#0-2) 

There is no other validation layer (no exact-suffix-with-dot check, no PSL/eTLD+1 validation) between this flawed comparison and the header being set, so the bypass is directly exploitable by any external, unauthenticated client capable of sending an HTTP request with a crafted `Origin` header.

## Impact Explanation
This maps to a cross-origin allowlist/CORS bypass: an attacker who controls a domain that is a superstring (not necessarily a subdomain) of a configured allowed suffix can cause the gateway to respond with `Access-Control-Allow-Origin: <attacker origin>`, `Access-Control-Allow-Methods`, and `Access-Control-Allow-Headers`. A malicious webpage hosted at such a domain could then have a victim's browser make credentialed/CORS-visible requests to the gateway and read the JSON-RPC style responses cross-origin, which were only meant to be exposed to genuine `*.<allowed-domain>` subdomains — an origin-validation/allowlist bypass (CWE-187/CWE-20).

## Likelihood Explanation
Exploitability requires the deployment to configure at least one wildcard entry in `CORSAllowedOrigins` (e.g., `https://*.remix.com`) with `CORSEnabled: true`. Given that precondition, any unauthenticated external attacker who registers a domain ending in the same substring (no actual subdomain relationship needed, e.g., `evilremix.com`) can trigger the bypass with an ordinary browser request — no special privileges, network position, or victim interaction beyond visiting the attacker's page is required, and the exploit is fully repeatable.

## Recommendation
Replace the raw `strings.HasSuffix` check with a boundary-aware comparison after stripping the `*.` prefix, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```
This ensures `evilremix.com` no longer matches `*.remix.com` while genuine subdomains like `foo.remix.com` still match.

## Proof of Concept
1. Configure the gateway HTTP server with `CORSEnabled: true` and `CORSAllowedOrigins: ["https://*.remix.com"]`.
2. Send an HTTP request to the gateway endpoint with header `Origin: https://evilremix.com`.
3. In `isAllowedOrigin`, `splitURL` yields `originHost = "evilremix.com"` and, after stripping `*.`, `allowedHost = "remix.com"`.
4. `strings.HasSuffix("evilremix.com", "remix.com")` evaluates to `true`, so `isAllowedOrigin` returns `true`.
5. `handleRequest` sets `Access-Control-Allow-Origin: https://evilremix.com` in the response, confirmable via `curl -H "Origin: https://evilremix.com" http://<gateway-host>:<port><path> -i` and observing the reflected header, or via a Go unit test calling `httpServer.isAllowedOrigin("https://evilremix.com")` with the above config and asserting it returns `true`.

func (s *httpServer) isAllowedOrigin(origin string) bool {
	originScheme, originHost, originPort, err := s.splitURL(origin)
	if err != nil {
		s.lggr.Debug("error parsing origin URL", err)
		return false
	}
	for _, allowed := range s.config.CORSAllowedOrigins {
		// probably better to do this once when server starts and store it in a map
		// this is an easier solution so we don't have to apply more changes to the code
		// just need to be careful when specifying allowed origins in the config file
		allowedScheme, allowedHost, allowedPort, err := s.splitURL(allowed)
		if err != nil {
			s.lggr.Debug("error parsing allowed origin URL", err)
			continue
		}
		// skip if the scheme doesn't match at all
		if originScheme != allowedScheme {
			continue
		}
		// skip if the port doesn't match at all
		if originPort != allowedPort {
			continue
		}
		// check for exact host match (e.g., remix.com)
		if originHost == allowedHost {
			return true
		}
		// check for wildcard host match (e.g., *.remix.com)
		if strings.HasPrefix(allowedHost, "*.") {
			allowedHost = allowedHost[2:]
			if strings.HasSuffix(originHost, allowedHost) {
				return true
			}
		}
	}
	return false
}
