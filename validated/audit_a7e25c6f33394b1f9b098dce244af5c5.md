### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the handler a `shop` value that is read from the `X-Shopify-Shop-Domain` header — a field that was never part of the signed material. Because the tenant identifier (`shop`) is not bound to the HMAC that is verified, an attacker who can obtain one valid `(raw_body, hmac)` pair (e.g. by legitimately triggering a webhook to their own store/app installation) can replay it with a forged `shop-domain` header for a different shop and still pass validation.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is populated independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cryptographic tie to the signed body: [2](#0-1) 

`Registry.process` verifies the HMAC and then constructs `WebhookMetadata` using `request.shop` as the tenant identity passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` recomputes the HMAC strictly over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the `hmac` header — it never incorporates `shop`: [4](#0-3) 

This is the same class of bug as the report's core issue: a field that downstream logic treats as authoritative (there, the L1 timestamp trusted by L2; here, the `shop` tenant identifier trusted by the handler) is not actually covered by the integrity check that is supposed to authenticate the whole message (there, the L2 timestamp comparison; here, the webhook HMAC). The equality that should hold — `shop bound by HMAC == shop delivered to handler` — does not hold, because the HMAC only binds the JSON body.

The gem's own documentation instructs integrators to trust `data.shop` as "The shop domain of the webhook" and use it directly as the tenant key (e.g. `shop_domain: data.shop`): [5](#0-4) 

### Impact Explanation
An attacker who can obtain one genuine `(raw_body, hmac)` pair — trivially available to anyone who can install the app on any shop they control, since Shopify sends real webhooks to the app's public callback URL for that shop — can replay that exact body/HMAC combination to the app's webhook endpoint while substituting an arbitrary victim `X-Shopify-Shop-Domain` value. `HmacValidator.validate` still succeeds because the signature check is body-only, and `Registry.process` forwards the forged `shop` straight to the host app's handler. Any handler that uses `data.shop` (as the gem's own docs recommend) to key merchant records, gate authorization, or take shop-specific action (e.g. attributing order data, or acting on `app/uninstalled`) will attribute attacker-controlled webhook content to a shop the attacker does not control — a cross-tenant data injection / impersonation vector.

### Likelihood Explanation
The prerequisite is low: obtaining one legitimately signed webhook is possible for anyone who installs the app on any store (including a store they own), since HMAC secrets are shared across all shops for a given app (`Context.api_secret_key`) rather than per-shop. No access token, refresh token, or `client_secret` leakage is required — only observation of one delivered webhook and the ability to POST to the app's existing webhook endpoint with a modified header.

### Recommendation
Bind the shop identity to the authenticated payload before trusting it: incorporate the `X-Shopify-Shop-Domain` (and ideally `X-Shopify-Webhook-Id`/topic) into the HMAC-covered signable string, or independently verify that the delivered `shop` corresponds to a shop for which this specific webhook subscription/id was registered, before invoking the handler in `Registry.process`.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; Shopify delivers a legitimate webhook POST to the app's callback URL with body `B` and header `X-Shopify-Hmac-Sha256: H` (computed as `HMAC_SHA256(api_secret_key, B)`), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker replays the identical request but changes only the header: `X-Shopify-Shop-Domain: victim-shop.myshopify.com`, keeping body `B` and HMAC `H` unchanged.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac-sha256: H})` is constructed; `Utils::HmacValidator.validate` recomputes `HMAC_SHA256(api_secret_key, B)`, which still equals `H`, so validation passes.
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled `B` as if it originated from `victim-shop.myshopify.com`.
