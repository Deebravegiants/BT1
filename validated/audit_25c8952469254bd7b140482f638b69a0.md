### Title
Missing bandwidth-gate enforcement on `on_response` allows unmetered/free GET-response delivery bypassing the paid bandwidth allowance - (File: parachain/runtimes/gargantua/src/ismp.rs)

### Summary
The bandwidth-gate mechanism (`pallet-bandwidth`) is documented and implemented to meter **every non-purchase inbound message** from a registered source chain/app pair, draining a prepaid byte allowance via `BandwidthGate::try_consume`. `ProxyModule::on_accept` correctly enforces this gate for `PostRequest`s. `ProxyModule::on_response`, however, contains a comment claiming to "mirror the request path in `on_accept`" for bandwidth billing, but never actually calls `try_consume`. This is the same bug class as the CI4MS report: an allowlist/metering check that is consistently applied on one operation (`on_accept`) is silently omitted on a parallel, reachable operation (`on_response`), letting an unprivileged actor bypass the intended gate.

### Finding Description
`pallet-bandwidth`'s gate is meant to be "consulted on every inbound request from a source chain" [1](#0-0) , draining a paid byte allowance and rejecting the message when the allowance is empty.

In `ProxyModule::on_accept`, this is implemented correctly — every non-purchase `PostRequest` triggers `pallet_bandwidth::Pallet::<Runtime>::try_consume` before further processing: [2](#0-1) 

In `ProxyModule::on_response`, the doc comment explicitly states the intent to bill bandwidth the same way ("Mirrors the request path in `on_accept`: the chain and module that produced the response pay for the bytes they deliver"), but the function body never calls `try_consume` — it only checks the destination chain and routes to the module: [3](#0-2) 

This is structurally identical to the CI4MS root cause: `saveFile`/`createFile` enforce the allowlist while `deleteFileOrFolder`/`renameFile` do not, despite sharing the same validation intent — here `on_accept` enforces the bandwidth allowlist/allowance while `on_response` does not, despite the code comment asserting parity.

### Impact Explanation
GET responses are dispatched by Hyperbridge itself via `handlers/response.rs` after a GET request the app previously issued was answered with a state proof [4](#0-3) . The response body can be arbitrarily large (bounded only by the number/size of storage values in `request.keys`), and — per the bandwidth model — the byte cost of a response is supposed to be billed to the `(source chain, app)` pair, exactly like a `PostRequest`'s bytes are billed in `on_accept`. Because `try_consume` is never invoked for responses, an app/relayer can drive an unlimited volume of GET-response traffic through the coprocessor without ever depleting (or even holding) a `pallet-bandwidth` subscription. This directly undermines the metering/DoS-protection guarantee the bandwidth gate exists to provide, allowing an unprivileged message dispatcher to consume Hyperbridge coprocessor resources for free — a route the "$"-tiered allowance model was built specifically to prevent free-riding on. This is an availability/economic-integrity impact on the messaging pipeline rather than a direct fund-theft bug, consistent with the CI4MS analog's DoS/integrity impact classification (their CVSS impact was C:N/I:H/A:H).

### Likelihood Explanation
Every GET response delivered through the `gargantua` runtime's ISMP router flows through this exact code path, and the missing check is unconditional (not gated behind a feature flag, unlike the `no-bandwidth` compile-time disable used for `on_accept`). Any relayer/user who can trigger and deliver a GET response for an app that would otherwise be gated (i.e., not on `pallet-bandwidth`'s allowlist) can exploit this immediately, with no special privilege beyond what's already required to relay a GET response (a role explicitly reachable by unprivileged relayers/message dispatchers per the threat model).

### Recommendation
Add the same bandwidth-gate enforcement to `ProxyModule::on_response` that exists in `on_accept`: compute the response's ABI-encoded byte length and call `pallet_bandwidth::Pallet::<Runtime>::try_consume(&response.get.source, &response.get.from, bytes)` before dispatching to the destination module, respecting the same `no-bandwidth` feature-flag compilation pattern already used for `on_accept`. Add a regression test asserting that `on_response` calls (or fails to call) the gate exactly like `on_accept` does, so the documented parity claim in the code comment is actually enforced.

### Proof of Concept
Concrete exploitation is not directly demonstrable from static analysis alone since it requires driving an actual GET request/response round trip through a live `gargantua` deployment. Based on code inspection:
1. An app that is **not** on the `pallet-bandwidth` `Allowlist` and has **zero** live subscription bytes issues (or is targeted by) a `DispatchGet` request whose `from` field is that app's module id.
2. The originating chain relays a `handleGetResponses`/`ResponseMessage` for this GET request through Hyperbridge's normal response-delivery pipeline (`modules/ismp/core/src/handlers/response.rs`), which is fully permissionless for any relayer holding a valid state proof.
3. `ProxyModule::on_response` is invoked with the `GetResponse`; because `try_consume` is never called (unlike in `on_accept`), the response is delivered regardless of the app's bandwidth balance, and no `BandwidthConsumed` event is ever emitted for it — confirmed by the absence of any `try_consume`/`BandwidthGate` reference in the `on_response` body [3](#0-2)  despite the identical mechanism being present and functioning in `on_accept` [5](#0-4) .

	fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
		// Bandwidth gate. Always-enforce unless the `no-bandwidth` flag
		// is set; skipped for purchase messages so the recharge flow
		// itself doesn't need bandwidth. With the flag on the gate is a
		// no-op and this block is compiled out entirely.
		#[cfg(not(feature = "no-bandwidth"))]
		if !pallet_bandwidth::Pallet::<Runtime>::is_purchase_message(&request) {
			let bytes = ismp::abi::encode_post_request(&request).len() as u32;
			<pallet_bandwidth::Pallet<Runtime> as pallet_bandwidth::BandwidthGate>::try_consume(
				&request.source,
				&request.from,
				bytes,
			)
			.map_err(|err| {
				anyhow!(
					"bandwidth gate: {err} (source={:?}, from={:x?})",
					request.source,
					request.from
				)
			})?;
		}

	fn on_response(&self, response: GetResponse) -> Result<Weight, anyhow::Error> {
		// Bandwidth gate. Mirrors the request path in `on_accept`: the chain
		// and module that produced the response pay for the bytes they
		// deliver. Compiled out when the `no-bandwidth` flag is on.
		if response.dest_chain() != HostStateMachine::get() {
			return Ok(Weight::from_parts(0, 0));
		}

		let dest = &response.get.from;

		let pallet_id = ModuleId::from_bytes(dest).map_err(|err| Error::Custom(err.to_string()))?;

		match pallet_id {
			pallet_ismp_demo::PALLET_ID =>
				pallet_ismp_demo::IsmpModuleCallback::<Runtime>::default().on_response(response),
			_ => Err(anyhow!("Destination module not found")),
		}
	}
