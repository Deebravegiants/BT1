This confirms the core binding break: `to_signable_string` returns only the raw body, and `shop`, `topic`, `webhook_id`, `api_version` come from unauthenticated headers. The docs at `docs/usage/webhooks.md` lines 12-26 explicitly instruct app developers to route business logic (`shop_domain: data.shop`, background job enqueue) using the `shop` field, confirming this is the intended/expected use of `data.shop`, which is exactly the field left outside the HMAC's protection.

### Title
Webhook HMAC only covers raw body, allowing shop/topic header forgery for cross-tenant webhook injection - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw HTTP body, while the `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's handler are read straight from unauthenticated HTTP headers. Because the app's webhook secret (`api_secret_key`) is shared across every shop/tenant that installs the app, any party who can obtain one valid `(raw_body, hmac)` pair — trivially available to anyone who installs the app on their own store — can replay that pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or topic/webhook-id) header for a different, victim tenant. The signature check still passes because those headers are never part of the signed material, so the app's handler receives attacker-chosen body content falsely attributed to another shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

All the other externally supplied, security-relevant values are parsed directly from headers with no cryptographic binding to the signed payload: [2](#0-1) 

`Registry.process` validates the request using exactly that signable string and, once it passes, trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` for constructing `WebhookMetadata` passed to the developer's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string` (the raw body) and compares it against the `hmac` header: [4](#0-3) 

The equality that should hold is: `shop header == shop cryptographically bound inside the HMAC-verified payload`. In this implementation that equality never exists — the HMAC only proves "this body was signed with the app's `api_secret_key`", not "this body belongs to shop X" or "this body is topic Y". Since `api_secret_key` is a single per-app secret shared by all merchants who install the app (not a per-shop secret), a valid `(body, hmac)` pair obtained from a webhook delivered to *any* one shop using the app is equally valid for *any other* shop, because the shop identity is carried out-of-band in a header that isn't part of the signed input.

The documented usage pattern shows apps take `data.shop` from the resulting `WebhookMetadata` at face value for business logic (job dispatch, per-tenant record updates), confirming that `shop` is treated as an authenticated tenant identifier by consumers of this gem, even though it's not: [5](#0-4) 

### Impact Explanation
This is a High-impact scope/identity check bypass leading to cross-tenant data confusion: an attacker who legitimately installs the target app on their own store (an ordinary, unprivileged action available to anyone) can capture a genuine `(raw_body, hmac)` pair for a webhook delivered to their own shop, then POST that identical pair to the app's shared webhook endpoint while spoofing the `shop-domain` (and/or `topic`/`webhook-id`) header to name a victim shop. `Registry.process` will accept it as authentic (the HMAC still matches the unmodified body) and pass attacker-controlled body content into the app's handler tagged as belonging to the victim tenant. Any app that uses `data.shop` to key per-tenant records, trigger tenant-scoped side effects, or make trust decisions (which the gem's own documentation instructs apps to do) is exposed to cross-tenant data injection/corruption originating from a fellow (non-privileged) app installer.

### Likelihood Explanation
Likelihood is realistic: obtaining a valid signed webhook body requires nothing more than installing the app on an attacker-controlled shop — something any internet user can do for a publicly listed app, no privileged credentials or secret leakage required. Forging arbitrary HTTP headers on an inbound request is trivial. The only constraint is that the injected body must be a payload the attacker can obtain signed for their own shop (e.g., `orders/create` for an order they place themselves), which still lets them control the content while claiming it belongs to another shop.

### Recommendation
Bind the tenant/topic identity into the signed material instead of trusting headers post-hoc: extend `VerifiableQuery`/`Request#to_signable_string` (or perform an independent secondary check) so that `shop`, `topic`, and `webhook_id` are verified against Shopify's known registration state for that HMAC, or at minimum reject processing unless the `shop` header matches an active session/registration the app already knows about for the webhook `topic`/`webhook_id` combination. Documented guidance should also warn that `data.shop` must be cross-checked against the app's own shop/session records before being used for tenant-scoped side effects.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (normal unprivileged action).
2. Shopify sends a legitimate webhook, e.g. `orders/create`, to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid HMAC over body>` and some JSON `raw_body` the attacker fully controls (they placed the order).
3. Attacker captures this exact `(raw_body, hmac)` pair.
4. Attacker crafts a new HTTP POST to the same app webhook endpoint, keeping `raw_body` and `X-Shopify-Hmac-Sha256` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC from `raw_body` only (`lib/shopify_api/webhooks/request.rb` line 36-38, `lib/shopify_api/utils/hmac_validator.rb` lines 26-31) — validation succeeds unchanged.
6. The app's `WebhookHandler.handle` is invoked with `data.shop == "victim-shop.myshopify.com"` and `data.body` containing the attacker's chosen JSON, despite the request never having come from Shopify on behalf of `victim-shop`.
