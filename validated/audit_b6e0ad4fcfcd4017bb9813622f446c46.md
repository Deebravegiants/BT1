### Title
Missing validation of user-supplied Curve25519 public key allows weak-key biometric encryption - ([File: src/backend/user_status.rs])

### Summary
The self-custody encryption key used to protect a user's biometric Personal Custody Package (PCP) is decoded from user/app-controlled QR-code-linked data without any cryptographic validity check beyond byte length. This mirrors the reported "missing address validation" bug class: an attacker-controlled value (here, a Curve25519 public key instead of a blockchain address) is accepted and used downstream without checking it isn't a degenerate/malicious value.

### Finding Description
`decode_public_key` in [1](#0-0)  only validates that the base64-decoded payload is exactly 32 bytes before wrapping it in a `sodiumoxide::crypto::box_::PublicKey`. It performs no check that the 32 bytes represent a non-degenerate Curve25519 point (e.g., rejecting the all-zero key or other known low-order points).

This function is used to decode `user_public_key` (the `self_custody_public_key` field) coming from `orb_qr_link::UserData`, which is derived from data supplied through the user's QR code / app flow: [2](#0-1) . That value is only checked for a matching `user_data_hash` from the scanned QR code via `user_data.verify(user_data_hash)` [3](#0-2) , but this only confirms the value matches what was embedded in the QR code — it does not confirm the key is a well-formed, safe Curve25519 point. Since the QR code and its embedded hash are attacker/user controlled inputs (produced by the app being scanned, i.e., an unprivileged user), a user can supply a degenerate key that still satisfies the hash check.

The resulting `self_custody_user_public_key` is then used directly to encrypt the tier0/tier1/tier2 biometric archives (iris, face, normalized iris images) via `encrypt()` in [4](#0-3)  and [5](#0-4) , without any additional validation at the point of use.

Note: I was unable to directly inspect the implementation of `orb_qr_link::UserData::verify` (defined in an external crate not indexed in this repository) to confirm exactly which fields are covered by the hash, nor was I able to inspect the internals of the `encrypt()` function itself (only its call sites) to verify whether `sodiumoxide`'s underlying `crypto_box` implementation performs any implicit rejection of degenerate keys. libsodium's standard `crypto_box`/`crypto_box_seal` APIs do not reject known low-order/weak public keys by default, but this could not be independently confirmed against the exact `sodiumoxide` version pinned in this repo without additional tooling.

### Impact Explanation
If a malicious or curious end user crafts a QR code with a degenerate Curve25519 public key (e.g., all-zero bytes) as their `self_custody_public_key`, the resulting encrypted PCP tiers (containing that user's own iris/face biometric captures) could be encrypted with a predictable/weak shared secret. Depending on the underlying `crypto_box` behavior, this could allow any third party intercepting the uploaded package (e.g., over network transit, S3 storage, or backend logs) to recover the user's own biometric data without needing the corresponding private key — a biometric data disclosure impact specific to that user's own signup. This does not directly compromise other users' data or allow cross-signup state bleed, limiting the blast radius to the crafting user's own submission.

### Likelihood Explanation
Exploitation requires the attacker to control their own signup's QR code/app-generated `self_custody_public_key` and matching `user_data_hash`, both of which are within reach of any end user going through a normal signup with a custom or modified client app. No special orb-side privilege is needed, making this reachable by an ordinary signup participant. However, real-world impact depends on whether `sodiumoxide`'s box implementation actually mishandles degenerate keys, which could not be confirmed here.

### Recommendation
Before accepting a user-supplied Curve25519 public key (`self_custody_public_key`, and any backend-provided keys as defense in depth), validate that it is not the identity element or a known low-order point, and/or use a `crypto_box` implementation/wrapper that performs contributory-behavior checks. At minimum, add an explicit rejection of the all-zero key and other publicly known low-order Curve25519 points in `decode_public_key` in `src/backend/user_status.rs`, returning an error that causes the QR-code/signup validation to fail rather than silently proceeding to encrypt biometric data with an unsafe key.

### Proof of Concept
Not fully verifiable without access to the `orb_qr_link` crate internals and the exact `sodiumoxide`/libsodium version's `crypto_box` key handling; a full PoC would require crafting a QR code whose `authenticated_app_data.self_custody_public_key` is a 32-byte all-zero (or other known low-order) value with a matching `user_data_hash`, feeding it through `backend::user_status::request`, and confirming `decode_public_key` accepts it and that the resulting PCP encryption in `personal_custody_package.rs` produces a predictable ciphertext.

fn decode_public_key(payload: &str) -> Result<PublicKey> {
    let bytes = BASE64.decode(payload.as_bytes())?;
    let bytes = <[u8; 32]>::try_from(bytes)
        .map_err(|x| eyre!("incompatible public key length: {}", x.len()))?;
    Ok(PublicKey(bytes))
}
