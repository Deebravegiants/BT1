### Title
Persistent third-party allowances granted by `EmporiumUpgradeable.runAction` (CASE2 arbitrary calls) can be drained by any unrelated caller - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` executes arbitrary attacker/user-supplied `op.callData` against `op.endpoint` *as the Emporium contract itself* (CASE2, `op.endpoint.call(...)` at [1](#0-0) ). One of the operations a proof-holder can encode is an ERC20 `approve(spender, amount)` call, which sets `allowance(Emporium, spender)`. Nothing in `runAction` forces that allowance to be fully consumed within the same call or revoked afterward, so it survives as ordinary persistent ERC20 state that any unrelated third party can trigger later by calling the spender directly.

### Finding Description
The equality that should hold is: **an allowance granted from Emporium to a spender during a user's proven op sequence should only ever be consumable by that same op sequence (i.e., 1:1 attributable to and atomically bound to the account/proof that authorized it)**. Instead, the allowance is materialized as ordinary ERC20 contract storage keyed only by `(Emporium, spender)`, completely decoupled from any notion of "who authorized it" once the `runAction` call returns.

Code path:
1. Victim calls `Hinkal.transact()` with `circomData.externalActionData` pointing at Emporium and an `EmporiumStack.ops` entry `{endpoint: tokenX, invokeWallet: false, callData: abi.encodeCall(IERC20.approve, (spender, amount))}`.
2. `runAction` hits CASE2 (`op.invokeWallet` false, or `signerAddress == 0`) and executes `op.endpoint.call(op.callData)` at [1](#0-0) , so `tokenX.approve(spender, amount)` runs with `msg.sender == Emporium`, setting `allowance[Emporium][spender] = amount`.
3. Because `approve()` doesn't move any balance, `balancesBefore == balancesAfter` for tokenX in the post-loop check at [2](#0-1) , so the victim's transaction completes normally with no revert and no on-chain signal that a dangling allowance now exists.
4. There is no code anywhere in `runAction`, `handleOut`, or `Transferer`/`TransfererBase` that resets or checks the final allowance to zero after the op loop; `unsafeApproveERC20Token`/`approveERC20Token`/`approveUnlimited` are only used by the contract's own internal helper calls, not applied to arbitrary op-driven approvals [3](#0-2) [4](#0-3) .
5. Any unrelated party (the attacker) can now call `spender.deposit(amount, attacker)` (or any standard `deposit(assets, receiver)`-style function, e.g. the common ERC4626 pattern, which lets the caller name an arbitrary `receiver`) *directly on-chain, without ever going through Hinkal, without a proof, without `onlyAllowedRecipient`*. The spender pulls `tokenX` via `transferFrom(Emporium, spender, amount)`, which succeeds purely on ERC20 allowance semantics, and mints/credits shares to the attacker's own address.

`onlyAllowedRecipient` only gates who may call `runAction` on Emporium (i.e. it must be the Hinkal contract) at [5](#0-4)  — it does nothing to protect allowances left behind in third-party ERC20 contracts once `runAction` returns. `performHinkalChecks`, `verifyProof`, nullifier/root checks, and the circuit's `inTotal + amountChanges === outTotal` constraints all bind only the *victim's own* balance delta for the tokens the victim chose to list in their own `circomData.erc20TokenAddresses`; none of them constrain or track state changes that happen in a wholly separate later transaction initiated by an unrelated address with no Hinkal proof at all. The theft happens entirely outside of Hinkal's transact/proof pipeline, so no per-proof authority check can catch it.

### Impact Explanation
The victim's real, previously-shielded tokenX value (moved into Emporium's balance to be later deposited into a yield/vault position) is diverted to an attacker-chosen recipient at a spender contract, with the attacker paying nothing beyond gas. This is a direct theft of user funds resulting from Emporium's persistent, unrevoked ERC20 allowance combined with common "deposit(assets, receiver)"-style external contracts — it does not require a "buggy" third party, just a standard recipient-flexible deposit function (e.g., ERC4626 vaults, Aave `deposit(asset, amount, onBehalfOf, ...)`). Every leftover, non-fully-consumed approve op ever executed via Emporium is a standing, repeatable theft vector until the allowance is exhausted or separately revoked; multiple attackers/bots can race to drain it. This matches "theft of shielded... user funds" / "executing calls or moving assets a wallet owner or prover never authorised."

### Likelihood Explanation
Requires only: (1) some user's `EmporiumStack` op sequence performs an `approve()` to a spender that is not fully and atomically consumed within the same `runAction` call (a natural pattern for multi-step/session-based DeFi interactions, or simply an approve for more than the immediately-used amount, or an approve executed in isolation to be used by a later, separate transact), and (2) the spender is any contract with a standard flexible-recipient deposit/mint entrypoint (extremely common). No privileged role, no relayer collusion, no compromised dependency is needed — the attacker only needs to observe on-chain allowance state and call the spender directly. This is highly feasible and requires no interaction with Hinkal's proof system at all.

### Recommendation
Do not let arbitrary `EmporiumStack` ops leave standing allowances on behalf of the shared Emporium contract. After executing the op loop in `runAction`, explicitly reset the allowance of every token/spender pair touched by an `approve`-type call back to zero (or require ops to use a "approve-exact-amount-and-consume-in-same-call" pattern enforced by checking that the final allowance for any spender approved during the loop is zero before returning). Alternatively, disallow raw `approve` calldata in CASE2 ops entirely and instead route approvals through an internal helper that atomically pairs an approval with its consuming call and revokes any leftover allowance at the end of `runAction`.

### Proof of Concept
Foundry test outline:
1. Deploy `Hinkal`, `EmporiumUpgradeable` (registered as allowed recipient), a mock ERC20 `tokenX`, and a mock `SpenderVault` implementing `deposit(uint256 amount, address receiver)` that calls `tokenX.transferFrom(msg.sender==Emporium, address(this), amount)` and credits `shares[receiver] += amount`.
2. Victim deposits `tokenX` into Hinkal/Emporium, then submits a CASE2 `transact()` whose `EmporiumStack.ops` contains one op: `{endpoint: tokenX, invokeWallet: false, callData: approve(spenderVault, amount)}`. Assert `IERC20(tokenX).allowance(emporium, spenderVault) == amount` after the tx, and that the victim's tx succeeded without reverting.
3. As attacker (no Hinkal interaction, no proof), call `spenderVault.deposit(amount, attacker)` directly.
4. Assert `IERC20(tokenX).allowance(emporium, spenderVault) == 0`, `tokenX.balanceOf(emporium)` decreased by `amount`, and `spenderVault.shares(attacker) == amount` while `spenderVault.shares(victim) == 0` — proving the allowance authorized by the victim's proof was consumed for the attacker's unrelated benefit.
