### Title
Vote account `pending_delegator_rewards` is used to compute block-reward distributions but is never decremented after distribution, allowing repeated over-distribution of the same balance - (File: `programs/vote/src/vote_state/mod.rs`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
`VoteStateV4::pending_delegator_rewards` is credited via `deposit_delegator_rewards` (SIMD-0123) [1](#0-0)  and is read every epoch by `calculate_block_reward()` to compute each stake account's share of the vote account's pending balance [2](#0-1) . The only mutator that changes this field is `add_pending_delegator_rewards`, which only ever increments it [3](#0-2) ; no decrement/reset counterpart exists anywhere in the codebase that I could find (`vote_state/mod.rs`, `vote_processor.rs`, `handler.rs`, `calculation.rs`, `distribution.rs`).

### Finding Description
This is structurally the same bug class as the reported `InflationaryVest.vy` issue: a "claimable" quantity is computed from a running balance (`self.claimed` / `pending_delegator_rewards`) that is read on every distribution but is never updated to reflect amounts already paid out.

In agave's block-revenue-sharing path (SIMD-0123):
- `deposit_delegator_rewards` increases `pending_delegator_rewards` on the vote account whenever new block-revenue lamports are deposited into it [4](#0-3) .
- Every epoch during rewards calculation, `calculate_block_reward()` reads `vote_state.pending_delegator_rewards()` and distributes a proportional share of it to each staker based on `stake / total_active_stake`, capped at `pending_delegator_rewards` [5](#0-4) .
- The comment in the code explicitly acknowledges that "during recalculation, if stake account has already received rewards, it's possible to have `stake > total_active_stake`" and clamps the result, but this is a workaround for a symptom, not a fix: the balance being divided among stakers (`pending_delegator_rewards`) is never reduced by what has already been paid out to those stakers.
- I was unable to locate any function (`sub_pending_delegator_rewards`, `set_pending_delegator_rewards` reset to a reduced value, or similar) that decrements this field after `distribute_epoch_rewards_in_partition` / `store_stake_accounts_in_partition` credits `block_reward` to stake accounts [6](#0-5) .

As a result, on every subsequent epoch boundary where `block_revenue_sharing` is active, `calculate_block_reward()` would recompute a reward using the *original, undiminished* `pending_delegator_rewards` value, effectively re-distributing the same pool of lamports to stakers epoch after epoch — mirroring exactly the `self.claimed` omission in the reported Vypers vulnerability (a value meant to gate/limit repeated payouts is read but never advanced).

### Impact Explanation
If confirmed at runtime, this would cause block-revenue-sharing rewards to be paid out to delegators repeatedly from the same underlying `pending_delegator_rewards` balance across multiple epochs, rather than being paid out once and exhausted. Since block-reward lamports are minted into circulation via `self.capitalization.fetch_add(stake_reward_lamports_minted, ...)` in the distribution path [7](#0-6) , uncontrolled repeated distribution from a non-decreasing counter would represent unbounded/incorrect value creation, i.e., materially incorrect reward accounting, similar in class to the double-claim in the reported bug.

### Likelihood Explanation
This code path is gated entirely behind the `block_revenue_sharing` and `custom_commission_collector` / `commission_rate_in_basis_points` features (SIMD-0123/SIMD-0232/SIMD-0291), which are not yet active on mainnet as far as I can determine from the code. I could not verify at runtime (no execution environment available) whether some other mechanism outside the files I inspected resets `pending_delegator_rewards`, nor could I confirm this is not caught by an invariant/assertion elsewhere in the reward pipeline (e.g., `assert!` checks in `distribute_reward_commissions`). This uncertainty, combined with the feature being pre-activation and my search coverage being limited to what the codebase index returned, means this should be treated as a plausible but unconfirmed analog requiring direct code/test verification (e.g., writing a two-epoch test depositing once and observing whether `pending_delegator_rewards` shrinks after distribution) before being treated as a confirmed vulnerability.

### Recommendation
Verify whether `pending_delegator_rewards` is intentionally left unchanged (e.g., because the actual "distributed" amount is tracked in a separate field/sysvar not surfaced by my searches) or whether it constitutes a genuine bug. If it's the latter, `pending_delegator_rewards` must be decremented by the total `block_reward` actually distributed to all stake accounts for that vote account during `store_stake_accounts_in_partition` / `build_updated_stake_reward`, analogous to updating `self.claimed` in the reported fix, before the next epoch's `calculate_block_reward` call reads it again.

### Proof of Concept
Not independently executed. Suggested reproduction: enable `block_revenue_sharing`/`custom_commission_collector`/`commission_rate_in_basis_points` features in a test bank, call `deposit_delegator_rewards` once to set a nonzero `pending_delegator_rewards`, advance two epoch boundaries with the same stake/vote configuration, and check whether the second epoch's `calculate_block_reward` (via `test_repeated_inflation_rewards_collector`-style epoch operations [8](#0-7) ) again distributes a nonzero block-reward derived from the same undiminished `pending_delegator_rewards`, rather than 0.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}

    pub(crate) fn pending_delegator_rewards(&self) -> u64 {
        match &self.target_state {
            TargetVoteState::V4(v4) => v4.pending_delegator_rewards,
        }
    }

    pub(crate) fn add_pending_delegator_rewards(
        &mut self,
        amount: u64,
    ) -> Result<(), InstructionError> {
        match &mut self.target_state {
            TargetVoteState::V4(v4) => {
                v4.pending_delegator_rewards = v4
                    .pending_delegator_rewards
                    .checked_add(amount)
                    .ok_or(InstructionError::ArithmeticOverflow)?;
                Ok(())
            }
        }
    }
