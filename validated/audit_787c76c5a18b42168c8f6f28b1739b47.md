### Title
Missing minimum-interval / max-deviation check between successive Pyth price updates in the same transaction allows risk-free oracle arbitrage - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`v0-4-market.clar` (and its local-testing mirror `market.clar`) lets any caller submit up to 3 raw Pyth `verify-and-update-price-feeds` payloads (`write-feeds`/`write-feed`) as part of a protocol action, and then immediately resolves the price for that action (`price-resolve`/`resolve-pyth`). The only checks applied to an incoming update are (a) staleness relative to `max-staleness`, and (b) that the new `publish-time` is **not older** than the last one recorded (`oracle-timestamp-fresh`, and `is-price-update-more-recent` in `pyth-storage-v4.clar`). There is no check bounding how much the price itself may move between two *valid, fresh, monotonically increasing* Pyth updates submitted within the same block/transaction sequence. This is exactly the class of bug described in the external report: Pyth ticks every ~400ms, so an attacker can supply two different, both individually valid, price attestations in quick succession (e.g. via a wrapper contract chaining two market calls in one Stacks transaction) and have the protocol accept whichever one is more favorable for each leg of the attack.

### Finding Description
`write-feed`/`write-feeds` push arbitrary Pyth VAA byte blobs into `pyth-storage-v4` on every call: [1](#0-0) 

`pyth-storage-v4.write-batch-entry` only rejects an update if its `publish-time` is **not strictly greater** than the previous one (`is-price-update-more-recent`) or if it is stale relative to a governance threshold — it does not compare the new price to the previous price: [2](#0-1) [3](#0-2) 

The market's own price-resolution path repeats this pattern: `oracle-timestamp-fresh` only checks staleness (`<= max-staleness`) and monotonicity (`>= ts prev`), never a bound on price *movement* between consecutive updates: [4](#0-3) 

`check-confidence` only bounds Pyth's own reported confidence interval against a single price snapshot; it does not compare two different snapshots taken moments apart in the same transaction: [5](#0-4) 

Because every protocol entrypoint accepts an optional list of raw Pyth update payloads and immediately consumes the resulting stored price for its own accounting (collateral valuation, debt valuation, liquidation health-factor computation), an attacker can compose a single atomic Stacks transaction (through an intermediary contract) that:
1. Pushes Pyth update #1 (price P1, timestamp T1) and executes action A (e.g., borrow/open a position) valued at P1.
2. Pushes Pyth update #2 (price P2 > T1, still fresh, still monotonic, but a different price due to the ~400ms Pyth refresh) and executes action B (e.g., close/liquidate/withdraw) valued at P2.

Both updates pass every check in `price-resolve`/`write-batch-entry` because neither check inspects the delta between P1 and P2 — only the delta between publish-time and current wall time, and monotonic ordering. This breaks the identity that collateral value used to permit borrowing/withdrawal must equal a single, non-manipulable market price for the duration of the atomic operation; instead two different valid prices are used to value two sides of the same economic position, letting the attacker realize a risk-free profit funded by the vault/other depositors.

### Impact Explanation
An attacker exploiting the price gap between two legitimate, valid Pyth updates within one atomic transaction can borrow/withdraw against collateral valued favorably and immediately reverse/close the position at the second, more favorable price, extracting value directly from vault liquidity/other users' backing — i.e. direct theft of user funds at rest, corresponding to a Critical-severity insolvency/theft vector, mirroring the impact assessed in the original CoreDAO report (BVSS 7.0, `C:M/I:C`).

### Likelihood Explanation
The precondition (chaining two market calls with two distinct Pyth VAA payloads inside one Stacks transaction) requires no privileged access — any user can submit an arbitrary Pyth update payload as part of a call, and Hermes constantly serves new attestations every ~400ms, so obtaining two valid-but-different payloads is trivial and was empirically demonstrated on another Pyth-integrated protocol in the source report. Likelihood is Medium-High, gated only by the cost/complexity of assembling a composing contract and available liquidity/collateral limits.

### Recommendation
Add an explicit check in `price-resolve`/`write-batch-entry` (or in `oracle-timestamp-fresh`) that rejects a new price update if it deviates from the previously stored price for the same feed by more than a configurable basis-point threshold within a short time window (e.g., within the same block), in addition to the existing staleness and monotonicity checks — mirroring the remediation referenced in the report (`NLX-Protocol/nlx-synthetics` commit `a2f22a08`).

### Proof of Concept
1. Deploy a thin wrapper contract that, in one Stacks transaction:
   a. Calls a `v0-4-market.clar` action (e.g. borrow) supplying a fresh Pyth VAA payload with price P1/time T1 via the market's `feeds` parameter, which is processed by `write-feeds`/`write-feed` [1](#0-0)  and consumed by `price-resolve` [6](#0-5) .
   b. Immediately calls a second market action (e.g. liquidate/withdraw) supplying a second, real Hermes-served VAA with price P2/time T2 > T1 obtained ~400ms later, again passing both the staleness and monotonicity checks in `pyth-storage-v4.write-batch-entry` [2](#0-1) .
2. Because neither call validates the price delta between P1 and P2, the attacker profits from the price swing risk-free within the single atomic transaction, exactly as demonstrated on-chain in the referenced report's transaction (`updatePriceFeeds` invoked twice with two different prices in one tx).
