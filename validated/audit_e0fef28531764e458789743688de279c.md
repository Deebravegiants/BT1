### Title
Webhook `shop-domain`, `topic`, `webhook-id` and `api-version` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated request headers. `Utils::HmacValidator.validate` computes/verifies the HMAC exclusively over that body, so an attacker who possesses one valid `(body, hmac)` pair issued by Shopify for their own shop can replay it to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header. The HMAC still verifies (the body is unchanged), but the `shop` value handed to the app's handler is fully attacker-controlled and unbound to the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `webhook_id`, `api_version` as plain header reads: [1](#0-0) 

Only `@raw_body` is included in `to_signable_string`, which is the value actually signed/verified: [2](#0-1) 

`Utils::HmacValidator.validate_signature` recomputes the HMAC purely from `to_signable_string` and compares it to the `hmac` header — it never incorporates `shop`, `topic`, or any other header: [3](#0-2) 

`Registry.process` trusts the (unauthenticated) `request.shop` value from the same object once the body-only HMAC check passes, and forwards it straight into `WebhookMetadata` used by the app's handler to select/update tenant data: [4](#0-3) 

This breaks the intended identity binding `hmac_verified(body) == shop_attributed_to(body)`. Because the header carrying the tenant identity (`shop`) is outside the MAC scope, `shop-authenticated-by-signature != shop-used-as-tenant-key`.

### Impact Explanation
Any attacker who is themselves a legitimate merchant with the app installed (or who can capture/replay one previously delivered webhook, e.g. via browser dev tools, proxy logs, or a leaky log line) has a valid `(raw_body, hmac)` pair signed with the app's `client_secret` for their own shop. By resending that exact body to the app's webhook endpoint with `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) rewritten to point at a victim shop, the HMAC check in `HmacValidator.validate` still succeeds, since it only checks the untouched body. The handler then processes attacker-supplied body content under the victim's tenant identity — a cross-tenant write/state-corruption primitive (e.g. an `orders/create` or `app/uninstalled` style payload attributed to a shop the attacker doesn't control). This is a cross-tenant access vulnerability caused entirely by this gem's own webhook verification logic.

### Likelihood Explanation
Exploitation only requires one legitimate webhook delivery to any attacker-controlled shop (trivial to obtain by installing the app once) and the ability to send an HTTP POST with custom headers to the app's public webhook callback route — both are unprivileged-internet-user capabilities requiring no access token, no `client_secret`, and no privileged account.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable payload verified against the HMAC (or otherwise cryptographically bind them to the body), so that verification fails if any of these header values are altered relative to what Shopify originally signed.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; capture a legitimate webhook delivery (raw JSON body `B` and header `X-Shopify-Hmac-Sha256: H`), where `H = HMAC-SHA256(client_secret, B)`.
2. Replay the request to the app's webhook endpoint, keeping `body = B` and `X-Shopify-Hmac-Sha256: H` unchanged, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(client_secret, B) == H` — this succeeds because `B` and `H` are untouched: [5](#0-4) 
4. `request.shop` returns the attacker-supplied `victim-shop.myshopify.com`: [6](#0-5) 
5. The app's `WebhookHandler#handle` receives `data.shop == "victim-shop.myshopify.com"` together with the attacker's chosen body `B`, causing tenant-crossing side effects in the host application.
