### Title
Webhook `shop` (tenant identity) is trusted from an unauthenticated header while only the raw body is HMAC-verified - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC over the request body, but then dispatches the handler using a `shop` value read from the `X-Shopify-Shop-Domain` header, which is never covered by that HMAC. This is the same class of bug as the reported `partial_sha256_var_start` issue: a value that is *acted upon* (here, the tenant identity used to route/attribute the webhook) is not bound by the integrity check that is supposed to authenticate the whole message.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`. [1](#0-0) 

For webhooks, `Webhooks::Request` implements `VerifiableQuery` by using the raw HTTP body as the only signable content: [2](#0-1) 

However, the `shop`, `topic`, `api_version`, and `webhook_id` values used elsewhere are pulled straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.), none of which are included in `to_signable_string`: [3](#0-2) [4](#0-3) 

`Registry.process` validates the HMAC (which only proves the raw body was signed by the holder of `client_secret`) and then calls the handler with `request.shop` taken from the unauthenticated header: [5](#0-4) 

The binding that should hold is:
`hmac_signed_bytes == bytes_that_determine_shop`

but in this code:
`hmac_signed_bytes = raw_body` while `shop_used_by_handler = headers["x-shopify-shop-domain"]`

These are disjoint. An attacker who can influence or spoof the `X-Shopify-Shop-Domain` header on a request that carries a validly-signed body for shop A (e.g. a genuine webhook delivery replayed or forwarded through a proxy/host application that merges attacker-controlled headers, or any host app that passes through headers without pinning them to the TLS/mTLS-verified sender) can cause the handler to process the payload while attributing it to shop B. Because `WebhookMetadata.shop` is exactly what most host apps use as the tenant key to look up sessions/data (this is the intended purpose of the field, per `docs/usage/webhooks.md` and `Registry.process`), this breaks the tenant-identity binding the HMAC is supposed to enforce, and is precisely analogous to "a field acted on but not covered by the HMAC" from the rules.

### Impact Explanation
If an attacker (or a compromised/incorrectly-configured proxy/load balancer in front of the host app) can control the `X-Shopify-Shop-Domain` header independently of the HMAC-covered body, they can cause a webhook payload to be attributed to an arbitrary shop. Depending on how the host application uses `WebhookMetadata#shop` (commonly to select which merchant's session/DB row to update, e.g., for `app/uninstalled`, `shop/redact`, GDPR webhooks, or inventory/order sync), this enables cross-tenant data corruption or triggers privileged per-shop actions (e.g., forcing a `shop/redact` or `app/uninstalled` handler to run against the wrong shop), which lines up with the "cross-tenant access" Critical impact category. The severity depends on how strictly the host's reverse proxy/framework isolates the incoming HTTP headers from client influence, which this gem does not control or document any guard for.

### Likelihood Explanation
This gem is a library; the actual HTTP header ingestion happens in the host application's controller/framework layer, and many web servers/proxies do sanitize or overwrite `X-Shopify-*` headers from external input. This lowers likelihood versus a directly-exploitable bug in this repo. However, the root cause — the gem's own `Webhooks::Request`/`HmacValidator` design signing only the body while trusting headers for identity — is squarely inside this gem's code (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`), and nothing in the gem's own logic re-derives or cross-checks `shop` against the signed payload.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed content (or otherwise cryptographically bind them, e.g. by having Shopify sign a canonical string containing these header values alongside the body), or, at minimum, document/enforce that host applications must not accept these headers from any source other than a verified direct connection from Shopify. Alternatively, cross-validate the header-derived `shop` against an independent source of truth (e.g., look up the webhook subscription's expected shop via the topic/registration) before dispatching to a handler.

### Proof of Concept
Given a valid webhook body `B` signed by Shopify for shop `A` with header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`:
1. Forward the exact same body `B` and its valid HMAC header to the app's webhook endpoint, but with `X-Shopify-Shop-Domain: shop-b.myshopify.com` substituted for `shop-a.myshopify.com`.
2. `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the HMAC — see: [6](#0-5) 
3. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, body: request.parsed_body, ...))` with `shop` = `"shop-b.myshopify.com"`, even though the signed body content actually pertains to shop A — see: [7](#0-6) 

This demonstrates the identity binding `signed_bytes == identity_used_downstream` does not hold in this gem's webhook verification path.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
