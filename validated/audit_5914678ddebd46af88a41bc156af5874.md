### Title
Whale-scale debt causes a permanent `MathOverflow` panic in accrual, freezing an entire market — (`common/src/rates/compound.rs`, `common/src/rates/scaling.rs`)

### Summary
Like CVE-2019-6467 (a reachable assertion failure crashing the service), the pool's interest accrual contains a checked-arithmetic trap that any unprivileged user can push the market into: once debt value overflows `i128` inside `scaled_to_original`/`accrue_step`, **every** market operation panics with `MathOverflow` (error 33) — permanently freezing all supplied and borrowed funds in that market.

### Finding Description
Every pool mutation runs `interest::global_sync` first (`contracts/pool/src/interest.rs:20-33`), which calls `accrue_step` per ≤1-year chunk (`contracts/pool/src/interest.rs:39-53`). Accrual un-scales debt and computes interest via checked `i128`/`I256` arithmetic (`common/src/rates/compound.rs:36-49`, `common/src/rates/scaling.rs::scaled_to_original`), panicking with `GenericError::MathOverflow` on overflow (`common/src/errors.rs`, `contracts/pool/README.md:151-155`). Because `borrowed` (RAY-scaled, ×10^27) is multiplied by a growing `borrow_index`, a market holding ~1e30-token-scale debt overflows the representable value **before** the `MAX_BORROW_INDEX_RAY` cap engages. Since accrual runs first in every entrypoint, the trap becomes permanent: `supply`, `borrow`, `withdraw`, `repay`, `seize_positions`, `recapitalize`, and `update_indexes` all hit the same panic for that market — mirroring the CVE's "configuration the code cannot handle → crash on every query" shape, but here the crash bricks the market rather than just one request.

### Impact Explanation
Permanent freezing of funds and protocol insolvency for the affected (hub, token) market: no supplier can withdraw, no borrower can repay, no liquidator can seize, and no governance action can unfreeze it (the panic precedes all mutation logic; Soroban rolls back the transaction, leaving the poisoned state intact).

### Likelihood Explanation
An unprivileged address can reach it through the standard verbs: `controller.supply` a large amount, then `controller.borrow` at high utilization (caps are set per market and the test uses `with_max_utilization_disabled` / lifted caps, which is realistic for large-cap markets). The in-repo harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`) demonstrates the full chain: a 1e9·10^18-scale market at 98% utilization on the steep XLM curve panics inside `scaled_to_original` during `update_indexes`, after which `withdraw` and `repay` both revert with `MATH_OVERFLOW`. Reaching the cliff requires genuinely whale-scale positions and sustained accrual, so it is a real but edge-condition DoS rather than a cheap griefing vector — Medium/High.

### Recommendation
Clamp `accrue_step`'s debt-value growth at the representable ceiling before the checked multiply (e.g., cap `borrow_index` growth in `accrue_step`/`scaled_to_original` paths when `borrowed * index` approaches `i128::MAX`, or saturate the index at `MAX_BORROW_INDEX_RAY` earlier). Alternatively, let accrual compute in `I256` end-to-end and trap only on genuinely unrepresentable results, preserving repay/withdraw liveness.

### Proof of Concept
Reproduced by the existing harness test at `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`:
1. `supply` a whale position into a high-decimal market and `borrow` ~98% of it.
2. Advance ledger time; call `update_indexes` repeatedly.
3. `accrue_step` → `scaled_to_original` overflows `i128` → `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`.
4. Subsequent `withdraw` and `repay` both panic with `MathOverflow` — the market is permanently frozen.
