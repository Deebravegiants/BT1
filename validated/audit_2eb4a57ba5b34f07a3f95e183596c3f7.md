### Title
Unbacked Token Minting via Replayable ISMP Requests Combined with Non-Atomic State Mutation Before Fallible Calldata Dispatch - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` mints/transfers bridged tokens to the beneficiary *before* executing attacker-supplied optional calldata (`message.data`). If that calldata dispatch subsequently fails, `on_accept` returns `Err`, which causes `pallet-ismp`'s request handler to delete the just-stored request receipt, making the same ISMP request replayable by any relayer until it times out. Because the mint/transfer step already ran and is not rolled back (there is no storage-transaction wrapper around the module callback), each replay re-mints/re-transfers the same amount, producing unbacked tokens with no additional collateral locked on the source chain.

### Finding Description
`on_accept` in [1](#0-0)  performs the balance-affecting operation — minting a new asset or transferring from the pallet's escrow account to the beneficiary — unconditionally and *before* the optional-calldata block.

The optional-calldata block at [2](#0-1)  decodes attacker-controlled `message.data` into a `SubstrateCalldata { signature, runtime_call }`, derives an origin (either the beneficiary via signature, or an account mechanically derived from `message.from` when no signature is supplied), and dispatches the decoded `runtime_call` with `runtime_call.dispatch(RawOrigin::Signed(origin.clone()).into()).map_err(...)?`. Any dispatch failure (e.g., `BadOrigin`, insufficient balance, arithmetic error inside the inner call, or simply supplying a call the `BaseCallFilter` allows through but that is guaranteed to fail for the derived origin) propagates as `Err` out of the whole `on_accept`.

`pallet-ismp`'s request handler treats a module callback `Err` as "not delivered": it stores the request receipt *before* calling the module, then explicitly deletes it if the callback errors, per [3](#0-2) . The protocol's own documentation confirms the resulting semantics: "The `IsmpHost` does not store receipts for failed messages ... this effectively allows messages to be re-executed until they time out. Therefore you should ensure irreversible state changes occur only after a message effectively meets all success criteria" [4](#0-3) .

`pallet-hyper-fungible-token` violates exactly this guidance: it performs the irreversible mint/transfer *before* the fallible calldata dispatch, and there is no `#[transactional]`/`with_storage_layer` wrapper anywhere in the pallet or in the ISMP request-handling path to atomically undo the mint if the later step fails. Consequently, an attacker who controls the message's optional calldata (submitted from the registered peer contract on the source chain as part of a normal token-send with calldata) can deliberately choose a `runtime_call` that the `BaseCallFilter` permits but whose dispatch is guaranteed to fail for the derived origin (e.g., a call requiring root/council origin, so `dispatch` always returns `BadOrigin` regardless of `RawOrigin::Signed`). Every relay of that message mints/transfers tokens to the beneficiary, then deterministically fails at the calldata step, deletes the receipt, and becomes eligible for another relay — repeating until the request's timeout is reached.

### Impact Explanation
This is an unbacked-mint / fund-theft primitive reachable by any unprivileged party who can trigger a cross-chain token send with calldata from a registered peer contract (a normal user action, not requiring privileged access). Each successful relay-and-fail cycle credits the beneficiary with additional tokens/assets without any corresponding new lock/burn on the source chain, and because token receipt is asset mint or escrow-account debit, this directly drains the escrow pool or inflates the wrapped asset supply. Given `pallet-hyper-fungible-token` mediates real bridged value, this meets the "unbacked mint"/"theft of funds" bar defined in scope.

### Likelihood Explanation
Likelihood is high: the calldata field is fully attacker-controlled from the source-chain call that dispatches the HFT message; choosing a `runtime_call` that passes `BaseCallFilter::contains` but fails `Dispatchable::dispatch` for a `Signed` origin (e.g., any call gated by `EnsureRoot`/`EnsureSignedBy`/council origins, or one with a guaranteed arithmetic/`InsufficientBalance` failure for the freshly-derived origin) is straightforward and repeatable. No signature forgery, consensus break, or race condition is required — only the timeout window during which relayers can keep resubmitting the same proof/message.

### Recommendation
Reorder the logic so the mint/transfer only occurs after the optional calldata has been successfully validated and dispatched (or make both operations atomic, e.g., wrap the whole `on_accept` body in `frame_support::storage::with_transaction` and only commit if the entire function succeeds). Alternatively, decode/validate and dispatch the `runtime_call` first, and perform the token credit last, so any dispatch failure aborts before value transfer, consistent with the pattern warned about in the ISMP documentation.

### Proof of Concept
1. Register a peer HFT contract for state machine `S` and asset `A` via `ContractToAsset`.
2. From `S`, send an ISMP `PostRequest` to the HFT module encoding a `Message` with:
   - `to` = attacker's beneficiary account
   - `amount` = desired mint amount
   - `data` = ABI/SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <encoded call requiring EnsureRoot/EnsureSignedBy origin, e.g., a privileged-only extrinsic that BaseCallFilter still allows> }`
3. Relay the request; `on_accept` mints/transfers `amount` to the beneficiary, then attempts `runtime_call.dispatch(RawOrigin::Signed(beneficiary_or_derived_account))`, which fails with `BadOrigin`, causing `on_accept` to return `Err(HftError::CallDispatchError(...))`.
4. `pallet-ismp`'s request handler deletes the just-created request receipt (`modules/ismp/core/src/handlers/request.rs:123-125`), leaving the request eligible for re-processing.
5. Repeat step 3 for the same request (same proof/commitment) any number of times before the request's configured timeout elapses — each iteration mints/transfers `amount` again to the beneficiary with no new collateral locked on chain `S`.
