### Title
`ExternalInitiatorsEnabled` config flag is enforced only at registration, not at authentication/run time - ([File: core/web/auth/auth.go])

### Summary
The `JobPipeline.ExternalInitiatorsEnabled` flag is meant to act as a kill switch/feature gate for the legacy External Initiator mechanism (external, unprivileged actors that can remotely trigger job runs). It is checked when an External Initiator is *created*, but the actual authentication/run-triggering code path never re-checks it, mirroring the Illuminate `Redeemer` bug where `pauseRedemptions` blocked some redemption entry points but not `authRedeem`/`autoRedeem`.

### Finding Description
`ExternalInitiatorsController.Create` gates creation of a new external initiator credential behind the flag: [1](#0-0) 

However, the middleware that actually authenticates an inbound External Initiator request and grants it the `Run` role (used to trigger job/pipeline runs) never consults this flag: [2](#0-1) 

The `Authenticate` gin middleware simply iterates the configured `authMethod`s (including `AuthenticateExternalInitiator`) and grants access on a successful credential match — there is no check of `App.GetConfig().JobPipeline().ExternalInitiatorsEnabled()` anywhere in this authentication flow: [3](#0-2) 

Once authenticated via this method, the caller is treated as a fully privileged `Run`-role actor: [4](#0-3) 

The config documentation itself hints that the flag's enforcement is incomplete/legacy ("Unused: used to enable..."), which is consistent with the flag only gating the creation endpoint: [5](#0-4) 

### Impact Explanation
If an operator disables `ExternalInitiatorsEnabled` (e.g., in response to a suspected compromise of an external initiator's stored credentials, or simply to shut off the legacy feature fleet-wide as a precaution/incident response — analogous to calling `pauseRedemptions`), any External Initiator record that was created while the flag was previously enabled remains fully functional: it can still authenticate via `AuthenticateExternalInitiator` and trigger job/pipeline runs with the `Run` role. The intended "pause" of the feature is bypassed for any already-provisioned initiator, undermining the operator's ability to stop unwanted/ malicious job-run triggering through this vector during an incident.

### Likelihood Explanation
This requires no privilege beyond possessing (or having previously obtained) valid External Initiator access-key/secret credentials — the same unprivileged actor class assumed by the External Initiator mechanism itself. No additional exploitation complexity is needed beyond sending the normal authenticated request; the flag is simply never consulted on the request path, so the bypass is deterministic and always reachable once a credential exists.

### Recommendation
Add an explicit `ExternalInitiatorsEnabled()` check inside `AuthenticateExternalInitiator` (core/web/auth/auth.go), returning `auth.ErrorAuthFailed` (or a dedicated disabled-feature error) when the flag is off, so that disabling the feature immediately revokes the ability of all existing External Initiator credentials to authenticate and trigger runs — not just blocking the creation of new ones.

### Proof of Concept
1. Start a node with `JobPipeline.ExternalInitiatorsEnabled = true` and create an External Initiator via `POST /v2/external_initiators` (per `core/web/external_initiators_controller.go` `Create`), obtaining `AccessKey`/`Secret`.
2. Operator flips the config to `JobPipeline.ExternalInitiatorsEnabled = false` (intending to disable/pause the feature, e.g. due to a security incident).
3. Attempt to create a *new* external initiator — this correctly fails with "The External Initiator feature is disabled by configuration".
4. Using the previously obtained credentials, send a webhook job-run trigger request with the `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers to a route protected by `auth.Authenticate(..., AuthenticateExternalInitiator)` (e.g. the pipeline run creation endpoint). Because `AuthenticateExternalInitiator` (`core/web/auth/auth.go:119-149`) never checks `ExternalInitiatorsEnabled()`, the request succeeds and the job run is triggered despite the feature being "disabled".

// AuthenticateExternalInitiator authenticates an external initiator request.
//
// Implements authMethod
func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

// Authenticate is middleware which authenticates the request by attempting to
// authenticate using all the provided methods.
func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
