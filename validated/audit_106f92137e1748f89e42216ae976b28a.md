### Title
Webhook HMAC only covers the request body, not the `shop-domain`/`topic`/`webhook-id` headers, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking the HMAC over the raw body [3](#0-2) . The `Request#to_signable_string` used for that check returns only `@raw_body` [4](#0-3) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to that HMAC [5](#0-4) . The `shop` value is then passed unmodified into `WebhookMetadata` and handed to the app's handler as the tenant identity for that webhook event [6](#0-5) .

### Finding Description
The identity binding the gem is supposed to guarantee is: `shop header == shop that produced this HMAC-signed body`. In reality the equality enforced is only `HMAC(body, api_secret_key) == received_hmac`; nothing ties the `shopify-shop-domain` header (or `shopify-topic`/`shopify-webhook-id`) to that signature.

Because the app's `client_secret`/`api_secret_key` is shared across every shop that has the app installed, any shop that has legitimately installed the app can obtain a genuinely-signed `(body, hmac)` pair for itself (by triggering any webhook event on its own store, or via Shopify's webhook test feature). That attacker-controlled shop can then POST that same raw body and HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and optionally `shopify-topic`/`shopify-webhook-id`) to name a different, victim shop. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` will report the request as valid, because it only recomputes the signature over the body [7](#0-6) . `Registry.process` will then invoke the app's handler with `WebhookMetadata` carrying the forged `shop` (i.e. the victim's domain) alongside attacker-chosen `body` content [8](#0-7) .

### Impact Explanation
Because the gem's own documentation instructs app developers to key business logic (session lookup, job enqueue, data writes) directly off `data.shop` from `WebhookMetadata` — treating it as the verified tenant identity of an HMAC-authenticated request [9](#0-8)  — this break lets an attacker with a legitimate install on Shop A inject attacker-controlled webhook payloads that are processed as if they originated from Shop B (a shop the attacker doesn't control). This is a cross-tenant identity confusion at the core validation boundary the gem is documented to guarantee ("will verify the request did indeed come from Shopify").

### Likelihood Explanation
Exploitation only requires the attacker to (a) have a legitimate app installation on any shop (a normal, unprivileged merchant/tenant of the app) and (b) be able to send arbitrary HTTP requests with custom headers to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — the attacker only ever supplies its own legitimately obtained body/HMAC and forges headers, which is exactly the kind of unprivileged-internet-user analog in scope.

### Recommendation
Include the tenant-identifying fields (`shop`, and ideally `topic`/`webhook_id`) in the signed material that `HmacValidator` verifies, or otherwise cryptographically bind the header values to the HMAC (e.g., by validating that the `shop` header matches a shop known to have legitimately triggered that specific `webhook_id`, or by requiring the caller to additionally prove shop identity through a channel not solely dependent on the shared app secret). At minimum, document that `Request#shop`/`topic`/`webhook_id` are unauthenticated header values and must not be trusted for tenant-scoping decisions unless additionally cross-checked (e.g., against the shop stored for that `webhook_id`, or against the caller's IP allow-list for Shopify's webhook infrastructure).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, permitted install) and configures the app to receive `orders/create` webhooks, exactly as any legitimate merchant would.
2. Attacker triggers an `orders/create` event on `attacker-shop.myshopify.com` (e.g., creates an order), causing Shopify to POST a legitimately-signed webhook to the app's endpoint. Attacker captures `raw_body` and the `X-Shopify-Hmac-Sha256` header value from this real request (or replays it directly).
3. Attacker crafts a new POST to the app's `/callback/orders/create` endpoint using the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers since only `topic`, `hmac-sha256`, and `shop-domain` presence is checked, not any cross-binding [10](#0-9) .
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the HMAC only covers `raw_body`, which is unmodified [3](#0-2) .
6. The app's `WebhookHandler#handle` is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's order data>, ...)`, causing the host app to process attacker-controlled data as if it belonged to `victim-shop.myshopify.com`.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
