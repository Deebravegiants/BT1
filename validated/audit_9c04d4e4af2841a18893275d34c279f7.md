### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature that `Registry.process` verifies only covers the raw request body. Any actor who can obtain one legitimately-signed webhook delivery (e.g., for their own store, since the app's webhook secret is shared across every shop that installs the app) can replay that exact body/HMAC pair while swapping the `shop-domain` header to name an arbitrary victim shop. The signature check still passes, and the gem hands the forged `shop` value to the registered handler as trusted tenant data.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the (unsigned) header: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then forwards `request.shop` verbatim to the handler as the authenticated tenant identifier, with no cross-check against the payload or against any known/allowed shop: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` only ever compares `verifiable_query.to_signable_string` (i.e., the raw body for webhooks) against the computed digest — the `shop` string is never part of what is authenticated: [4](#0-3) 

The broken identity binding is:
`shop that produced a valid HMAC (implicitly, the store that actually received this exact webhook body from Shopify, signed with the app's shared client secret)` **≠** `shop trusted as the tenant key by the handler (the attacker-controlled x-shopify-shop-domain header value passed through as WebhookMetadata#shop)`.

Because the app's webhook signing secret (`Context.api_secret_key`) is identical for every shop that installs a given app, any merchant who installs the app can capture a real webhook delivery to their own store (valid body + valid HMAC), then resend that same body/HMAC combination to the app's webhook endpoint with the `shop-domain` header changed to a different, victim shop's domain. Since only the body is authenticated, this forged request passes `Registry.process`'s HMAC check unchanged, and the handler is invoked believing the event originated from the victim shop.

### Impact Explanation
If a host application (as documented/intended usage of this gem) uses `WebhookMetadata#shop` to select the tenant record, session, or store to which webhook data is applied — which is the very purpose of exposing `shop` on the metadata object — an attacker can inject fabricated events attributed to any other shop using the same app. This is a cross-tenant integrity/confidentiality violation: data belonging to shop A's real webhook can be replayed and falsely attributed to shop B, corrupting or exposing shop B's app-side state without shop B's involvement.

### Likelihood Explanation
The attacker needs no privileged credentials, no access to `api_secret_key`, and no interception of TLS: any user who installs the app on their own store automatically receives legitimately-HMAC-signed webhooks and can freely replay them against the shared endpoint with a modified `shop-domain` header. This is fully reachable through the gem's documented, public `Webhooks::Registry.process` / `Webhooks::Request` API.

### Recommendation
Bind the trusted `shop` value to something cryptographically tied to the request rather than an unsigned header — e.g., include the shop domain in the signed payload comparison, or require the host app to independently confirm the asserted shop against a known session/subscription for that specific webhook topic before trusting `WebhookMetadata#shop`. At minimum, document prominently that `shop` is not authenticated by the HMAC and must not be trusted as a tenant key without additional verification (e.g., matching against the shop associated with the specific `webhook_id`/subscription registered via the API).

### Proof of Concept
1. Attacker installs the target app on their own store (`attacker.myshopify.com`) and triggers an event so Shopify sends a real webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, header `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker captures this full request.
3. Attacker resends the exact same body `B` and HMAC header unchanged, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B)` against the header — it passes: [5](#0-4) 
5. The registered handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: B, ...)`, and any app logic keyed on `data.shop` now processes attacker-controlled data as if it belongs to `victim-shop`.
