### Title
Tokens/ETH not declared in `erc20TokenAddresses` become permanently stuck in `EmporiumUpgradeable` after arbitrary op execution - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` reconciles balances only for the tokens listed in `circomData.erc20TokenAddresses`, using a before/after balance-diff to compute the `UTXO` to return to the caller [1](#0-0) . The arbitrary calls executed inside the op loop (`op.endpoint.call{value: op.value}(op.callData)`) are not restricted to only touching those declared tokens [2](#0-1) . Any token (or ETH) balance the contract accrues that is outside the declared `erc20TokenAddresses` set is never moved out by `handleOut`, and there is no rescue/sweep function anywhere in the `Emporium`/`ExternalActionBaseUpgradeable` contracts to recover it [3](#0-2) .

### Finding Description
The balance equation the contract enforces is: for each token `i` in `circomData.erc20TokenAddresses`, `balanceChange[i] = balancesAfter[i] - balancesBefore[i]`, adjusted by `deltaAmountChanges[i]`, and any resulting positive delta is sent back to `msg.sender` via `handleOut` [4](#0-3) . This equality only covers tokens explicitly enumerated in `circomData.erc20TokenAddresses`, which is attacker/prover-supplied calldata, not something the arbitrary `op.callData` executed against `op.endpoint` is constrained to match.

Because `Emporium` is a shared, persistent contract instance used across all Hinkal users (it holds no per-user isolation — only a global balance), any interaction whose external call yields a token not present in that specific transaction's `erc20TokenAddresses` array (e.g., reward/rebate tokens from a lending/staking protocol call, referral tokens, excess `msg.value` refunded as ETH by a router, or rounding dust from a multi-hop swap) accumulates in the `Emporium` contract's balance permanently. There is no mechanism — not for the depositing user, not for other users, not even the contract owner — to withdraw tokens that were never declared in `erc20TokenAddresses` for the transaction that produced them, since `handleOut` is the only egress path and it is strictly scoped to the declared token list [5](#0-4) .

This matches the "value moved by Hinkal or an external action but not counted in the balance equation" analog class from the report: the `Stream` contract could not recover payment-token dust after stream completion; here, `Emporium` can never recover any non-declared token/ETH dust generated by its own arbitrary call execution, for the lifetime of the contract.

### Impact Explanation
Any token or ETH balance that accrues in the shared `Emporium` contract outside the declared `erc20TokenAddresses` set for a given call is permanently frozen with no recovery path for any party — this is a permanent freezing of value that flows through the protocol's own DeFi-adapter contract, satisfying the Critical "permanent freezing of user funds" bar, since `Emporium` is a shared contract serving all Hinkal users and the stuck value is not limited to the acting user's own error in isolation — it compounds across every transaction routed through this adapter over the contract's lifetime.

### Likelihood Explanation
Likelihood is significant because `Emporium`'s entire purpose is to execute arbitrary, owner-approved-endpoint DeFi calls (`op.endpoint.call`) on behalf of users [6](#0-5) ; many common DeFi interactions (claiming rewards, staking, multi-hop swaps with dust, routers refunding excess ETH) naturally produce token/ETH movements that a user or the off-chain proof-builder may not fully enumerate in `erc20TokenAddresses`, and once such value lands in `Emporium`, it is unrecoverable by design.

### Recommendation
Add an owner-gated (or otherwise permissioned) sweep/rescue function to `EmporiumUpgradeable` that can transfer out ERC20/ETH balances not currently pending as part of an in-flight, declared `erc20TokenAddresses` reconciliation — mirroring the `rescueERC20` pattern from the referenced report, but ensuring it does not conflict with tokens actively tracked by a concurrent transaction's balance-diff logic (e.g., via a reentrancy guard or per-token "in-flight" flag).

### Proof of Concept
1. A user submits a Hinkal transaction routed through `Emporium.runAction` with `circomData.erc20TokenAddresses = [tokenA]` and an `EmporiumStack` op that calls a lending protocol's `claimRewards()` function on `op.endpoint`, which pays out `tokenB` (a reward token) directly to the `Emporium` contract address.
2. `runAction` computes `balancesBefore`/`balancesAfter` only for `tokenA` [7](#0-6) ; the received `tokenB` balance is invisible to the loop and is never transferred to `msg.sender` by `handleOut`.
3. `tokenB` now sits in `Emporium`'s balance. No function in `EmporiumUpgradeable`, `ExternalActionBaseUpgradeable`, or `OwnerHinkalUpgradeable` can move `tokenB` out — future transactions can only move tokens they explicitly declare in `erc20TokenAddresses`, so `tokenB` remains stuck for the life of the contract.

    function handleOut(
        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
    ) internal returns (UTXO memory outUtxo) {
        // total change can be less than zero if there was some balance before the call -> that's why we have <=
        if (balanceChange <= 0) {
            return outUtxo;
        }

        transferERC20TokenOrETH(
            circomData.erc20TokenAddresses[i],
            msg.sender,
            uint256(balanceChange)
        );

        outUtxo = UTXO(
            uint256(balanceChange),
            circomData.erc20TokenAddresses[i],
            circomData.stealthAddressStructure,
            circomData.timeStamp
        );
    }
