### Title
RAY-scaled debt accrual overflows and permanently freezes a high-utilization market - (File: common/src/rates/index.rs)

### Summary
An unprivileged borrower can push a sufficiently large market into a state where accruing its scaled debt overflows `i128`. `Controller::update_indexes` is permissionless, while withdrawal, repayment, and liquidation paths accrue the same market before settling positions. Once `borrowed_scaled_ray * borrow_index` exceeds the representable RAY value, those operations revert with `MathOverflow`, freezing supplier and borrower funds.

### Finding Description
The analogous bug class is attacker-reachable arithmetic overflow during attacker-influenced state processing, rather than libebml’s native heap overwrite. Pool debt is stored as a RAY-scaled share amount. During accrual, `calculate_supplier_rewards` computes both `borrowed * old_borrow_index` and `borrowed * new_borrow_index`; an unrepresentable result raises `MathOverflow` rather than saturating or skipping the market. [1](#0-0) 

`update_indexes` is publicly reachable after caller authorization and forwards the selected `HubAssetKey` list to the pool. [2](#0-1) [3](#0-2)  The pool loads each market and calls `interest::global_sync`, which invokes `accrue_step` for each elapsed chunk. [4](#0-3) [5](#0-4) 

For an 18-decimal market, supplying one billion whole tokens creates `1e36` RAY-scaled shares. The representable RAY-debt ceiling is `i128::MAX`, so a borrow index above approximately `170 * RAY` makes `borrowed * borrow_index` unrepresentable. The protocol’s own long-horizon test demonstrates that a 98%-utilization market reaches this cliff before `MAX_BORROW_INDEX_RAY` and that subsequent withdrawal and repayment calls fail with `MathOverflow`. [6](#0-5) 

### Impact Explanation
This permanently freezes all funds whose settlement requires the affected market. Suppliers cannot withdraw because withdrawal performs index accrual and then unscales supply; borrowers cannot repay because repayment accrues and computes the debt’s scaled value; liquidation and bad-debt settlement likewise cannot rescue the market once the same accrual path panics. `Controller::withdraw`, `Controller::repay`, `Controller::liquidate`, and `Controller::update_indexes` all become unusable for that market. [7](#0-6) [8](#0-7) 

Direct token donations do not remove the oversized scaled debt, and recapitalization also has to operate on the accrued market. Consequently, user principal and accrued yield remain locked unless an excluded administrative upgrade changes the accounting code.

### Likelihood Explanation
The attack requires a very large configured supply/borrow domain, substantial attacker collateral, high sustained utilization, and enough elapsed time for the borrow index to cross the overflow threshold. No privileged call is required: the attacker can create their own collateral account, borrow the target asset through `Controller::borrow`, and later invoke permissionless `Controller::update_indexes`. Other suppliers are exposed whenever their funds remain in the market at the cliff.

Because the numeric threshold is far above ordinary market sizes, exploitation is capital-intensive and conditional on configured caps and market growth. The resulting failure is nevertheless deterministic once the scaled-debt/index product reaches the `i128` boundary, supporting a Medium severity.

### Recommendation
Enforce a debt-share ceiling derived from the maximum possible borrow index:

```rust
scaled_debt <= i128::MAX / (MAX_BORROW_INDEX_RAY / RAY)
```

Apply the bound when minting debt in `calculate_scaled_borrow` or the pool borrow path, so every admitted scaled-debt amount remains representable through `MAX_BORROW_INDEX_RAY`. Alternatively, make accrual explicitly saturate debt valuation at a safe market-level ceiling before multiplying, while keeping all withdrawal, repayment, liquidation, and cleanup paths able to burn shares. Add a regression test asserting that the largest admitted scaled debt can accrue to `MAX_BORROW_INDEX_RAY` without `MathOverflow`.

### Proof of Concept
1. On an 18-decimal market, a supplier deposits `1_000_000_000 * 10^18` units through `Controller::supply`, producing approximately `1e36` scaled supply/debt units at index `RAY`.
2. An attacker supplies sufficient separate collateral and calls `borrow(attacker, attacker_account, [(target_asset, 980_000_000 * 10^18)], Some(attacker))`, leaving the market near 98% utilization.
3. Ledger time advances under a steep configured interest curve until the projected borrow index exceeds roughly `170 * RAY`.
4. The attacker calls `update_indexes(attacker, [target_asset])`. `accrue_step` reaches `calculate_supplier_rewards`, where `borrowed.mul(new_borrow_index)` overflows and reverts.
5. Subsequent `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, and `recapitalize` attempts for that market hit the same accrual path and cannot settle the funds.

The repository’s long-horizon harness reproduces this sequence and observes `MathOverflow` from both the index update and later withdrawal/repayment attempts. [9](#0-8)

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
