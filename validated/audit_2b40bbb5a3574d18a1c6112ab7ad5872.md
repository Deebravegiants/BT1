### Title
Webhook shop-domain spoofing due to `shop` not covered by HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` validates a webhook's authenticity by HMAC-signing only the raw request body, while the `shop` (tenant) attribution is read from an unauthenticated header that is completely outside the signed payload. An unprivileged actor who obtains one genuine `(raw_body, hmac)` pair for a webhook delivery can replay it against the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a different shop, and `Utils::HmacValidator.validate` still reports success — because the HMAC never covered the shop value.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop`, by contrast, is derived purely from an HTTP header that is never mixed into the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature exclusively over `to_signable_string` (i.e., the raw body) and compares it against the `hmac-sha256` header, never referencing `shop`, `topic`, or `webhook-id`: [3](#0-2) 

This is the exact bug-class analog from the report: a field the application acts on (`shop`, used as the tenant/session key by any host app that calls `request.shop` after `HmacValidator.validate(request)` succeeds) is not covered by the integrity check (the HMAC), so the equality the app implicitly relies on —

`shop used to attribute/store the webhook == shop that was actually signed by Shopify with the app's secret`

— does not hold. Validating the HMAC only proves the *body* came from someone holding `Context.api_secret_key` (normally Shopify); it proves nothing about which `shop` the caller claims the payload is for, because `shop` is carried in a header that sits entirely outside the MAC.

Contrast this with `Auth::Oauth::AuthQuery`, where `shop` **is** part of `to_signable_string` and therefore is genuinely bound to the HMAC: [4](#0-3) 

No equivalent binding exists for `Webhooks::Request`.

### Impact Explanation
Any party who can obtain one legitimately signed webhook body+HMAC pair (e.g., a merchant/app-installer inspecting webhook traffic delivered to their own store, or any endpoint that logs/echoes inbound webhook requests) can resubmit that exact `(raw_body, hmac-sha256)` combination to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` (or `x-shopify-shop-domain`) header value. `HmacValidator.validate` still returns `true`, and `request.shop` returns the attacker-chosen value. Any host application that follows the documented pattern of "validate HMAC, then trust `request.shop` for tenant attribution" will process, store, or act on that webhook data under the wrong shop — a cross-tenant data-integrity/confusion issue, entirely without possession of `client_secret`, an access token, or any privileged credential.

### Likelihood Explanation
The attacker only needs one previously observed valid webhook (their own store's webhook payload is sufficient — no secret required) and the ability to POST to the app's public webhook endpoint with custom headers, both of which are available to any unprivileged internet user/merchant. No cryptographic break, credential theft, or race condition is required — only that the host app trusts `Request#shop` once `HmacValidator.validate` passes, which is exactly the usage pattern the gem's own documentation/tests encourage.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook-id`) into the value that is HMAC-verified, e.g., include the relevant Shopify headers in `to_signable_string`, or expose a combined verification that fails unless the header-derived `shop` matches a value cryptographically tied to the signed payload. At minimum, document clearly that `HmacValidator.validate` only authenticates `raw_body` and that `shop`/`topic` headers must not be trusted for tenant attribution without additional verification (e.g., cross-checking against the shop that owns the currently active session/webhook registration).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers/receives a webhook; they capture the exact `raw_body` and `X-Shopify-Hmac-Sha256` header Shopify sent (fully legitimate, no secret required — the attacker just controls a shop that has the app installed).
2. Attacker crafts a new HTTP POST to the app's webhook endpoint using the same captured `raw_body` and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. Server-side code constructs `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` and calls `ShopifyAPI::Utils::HmacValidator.validate(request)` — this returns `true` because validation only checks `raw_body` against the HMAC (`lib/shopify_api/utils/hmac_validator.rb` lines 12-31, `lib/shopify_api/webhooks/request.rb` lines 35-38).
4. The host app then reads `request.shop` (line 20-23) and gets `"victim-shop.myshopify.com"`, and proceeds to process/store the attacker's payload as if it belonged to the victim shop — a cross-tenant confusion achieved without any credential belonging to the victim or the app.
