The strongest matching analog in `orb-core` is in the biometric-capture frame-selection logic, which mirrors the reported bug-class: an error indicator is returned alongside other (possibly unusable) output fields, and the caller logs the error but does not stop using those other fields.

### Title
Face Identifier error field is logged but not enforced before using `is_valid`/`score` to select the self-custody candidate image — ([File: src/plans/biometric_capture/mod.rs])

### Summary
`face_identifier::types::IsValidOutput` (and its Python counterpart `FIIsValidOutput`) bundles an `error: Option<PyError>` field together with `is_valid: Option<bool>` and `score: Option<f64>` in the same flat struct, rather than returning a `Result` that forces callers to branch on success/failure. `handle_face_identifier` in the biometric capture plan only logs when `output.error.is_some()`, then proceeds to evaluate `output.is_valid` and `output.score` regardless of whether an error was reported.

### Finding Description [1](#0-0) defines `IsValidOutput` with `error`, `is_valid`, and `score` as independent optional fields rather than mutually exclusive states enforced by the type system (unlike a `Result<T, E>`).

In `handle_face_identifier`, the broker/plan code does: [2](#0-1) 

Specifically:
```
if output.error.is_some() {
    tracing::error!("Face self-custody frame error: {:?}", output);
}
if output.is_valid.map_or(false, |v| v) {
    ...
    self.self_custody_candidate_rgb = Some(FrameInfoSelfCustodyCandidate::new(output, frame...));
    ...
}
```
The error is logged for observability only — it is never used as a gate to skip the `is_valid`/`score` branch. If the underlying model (`is_valid` in `src/agents/python/face_identifier/mod.rs`, [3](#0-2) ) or any future/alternate implementation returns a struct where `error` is populated but `is_valid`/`score` also happen to carry stale, default, or attacker-influenced values, the frame-selection logic will still treat the output as authoritative and may select it as the "self-custody candidate" image used later to build the personal custody package (`build_pcp` in `src/plans/mod.rs`, which pulls `face_identifier_bundle.thumbnail`/`embeddings` unconditionally once the `Result` is `Ok`, at [4](#0-3) ).

This is the same bug class as the ICurve.sol issue: an error code/flag is returned by a function together with other output values, and a caller checks/logs the flag but does not use it to prevent using the other (potentially invalid) values.

### Impact Explanation
If a frame is incorrectly accepted as the self-custody candidate despite a reported face-identifier error, a poor-quality, corrupted, or manipulated RGB image/embedding could be selected and later bundled into the personal custody package that is uploaded and retained for the signup, and could also affect the biometric capture flow's frame selection (`self.face_ir`, `self.thermal` reset alongside it). This could result in the wrong or lower-integrity biometric image being retained/associated with a signup.

### Likelihood Explanation
Likelihood is limited by the current first-party Python agent implementation, which only sets `error: Some(...)` on exception paths where `is_valid`/`score` are typically left `None` (in which case `map_or(false, ...)` safely short-circuits). However, the type system does not enforce this invariant, and the check-but-ignore pattern is a latent hazard for any future model implementation, refactor, or FFI/parsing change (this is a `FromPyObject` struct pulled from a Python dict, so the guarantee that `error` and `is_valid`/`score` are mutually exclusive relies entirely on Python-side discipline, not Rust-side validation).

### Recommendation
Convert the face-identifier "is valid" output boundary to enforce error-first handling: if `output.error.is_some()`, treat the whole output as invalid and `return`/`continue` before consulting `is_valid` or `score`, rather than only logging. Consider modeling `IsValidOutput` as a `Result<IsValidData, PyError>` at the Rust boundary (as `EstimateOutput`/`PipelineOutput` do via `TryFrom` in `src/agents/python/iris/mod.rs`) so the compiler forces error handling before any downstream code can read `is_valid`/`score`.

### Proof of Concept
Not directly exploitable from the current agent implementation, but demonstrable by constructing an `IsValidOutput { error: Some(PyError{..}), is_valid: Some(true), score: Some(1.0), .. }` and feeding it through `handle_face_identifier`: the function will log the error but still select the frame as `self_custody_candidate_rgb` because the code path only branches on `is_valid`/`score`, never on `error`.
