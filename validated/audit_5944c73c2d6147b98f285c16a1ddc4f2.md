### Title
Webhook `shop`, `topic`, `api_version` and `webhook_id` metadata are trusted from unsigned HTTP headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC over the raw request body, then hands the app a `WebhookMetadata` struct whose `shop`, `topic`, `api_version`, and `webhook_id` fields are read directly from HTTP headers that are never covered by that HMAC. Any bytes an attacker controls in these headers are accepted as authenticated tenant/topic identity as long as they can present *any* valid `(body, hmac)` pair signed with the app's secret — which they can obtain legitimately by installing the app on their own store.

### Finding Description
`Registry.process` performs the only authentication check in the webhook pipeline: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`; it does not include `shop`, `topic`, `api_version`, or `webhook_id`, all of which are pulled straight from HTTP headers with no cryptographic binding to the signature: [3](#0-2) 

Those unauthenticated header-derived values are then propagated verbatim into `WebhookMetadata` and dispatched to the host app's handler as if they were verified: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `hmac-verified(shop) == shop delivered to handler`. Because `shop` (and `topic`) are never part of the signed payload, this equality does not hold — the gem verifies "bytes of `@raw_body`" but acts on "bytes of the `shop-domain`/`topic` headers," which are two disjoint inputs. This is exactly the "field acted on but not covered by the HMAC" analog: the webhook endpoint is a public, unauthenticated HTTP endpoint (by design, per Shopify's webhook delivery model), so any internet user who can reach it controls every header on the request.

Exploit path: an attacker registers their own store/app installation (an unprivileged, legitimately obtained tenant), triggers a webhook topic that produces attacker-influenced body content (e.g. `orders/create` with attacker-controlled order data on their own shop), and captures the resulting `(raw_body, X-Shopify-Hmac-Sha256)` pair — a validly signed pair for the app's `client_secret`, since Shopify computes it. The attacker then replays that exact body and HMAC value to the app's public webhook endpoint, but rewrites `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) to name a victim shop that also has the app installed. `HmacValidator.validate` still succeeds (body/HMAC unchanged), and `Registry.process` dispatches `WebhookMetadata.new(shop: "<victim-shop>", ...)` to the handler, which any host app built on this gem's documented API will use to select the tenant/session/data to act on — a cross-tenant confusion where attacker-controlled data is attributed to a victim shop's identity.

### Impact Explanation
This breaks the tenant-isolation guarantee that a `shop` value returned from `Registry.process`/`WebhookMetadata` is trustworthy proof that the payload originated from that shop. Any host application that keys off `WebhookMetadata#shop` to write data, invalidate caches, update order/customer state, or select which merchant's access token/session to use is exposed to cross-tenant data injection driven entirely by an unprivileged attacker who merely has (or creates) a store where the app is installed. This matches the Critical "cross-tenant access" impact category, since the identity boundary between shops is enforced only by an unsigned header rather than the cryptographic signature.

### Likelihood Explanation
Likelihood is moderate-to-high in gem-only terms: the webhook endpoint is intentionally public/unauthenticated (per Shopify's design), the attacker only needs their own legitimate app installation to mint one valid `(body, hmac)` pair, and no secret material belonging to the victim or the app is required — only header rewriting on a replayed request, which is fully within an "unprivileged internet user" threat model.

### Recommendation
Include the tenant-identifying and topic-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) inside the HMAC-signed payload used for verification — or, at minimum, have `Request#to_signable_string` incorporate a canonical representation combining the raw body with these header values so that `HmacValidator.validate` cryptographically binds `shop`/`topic` to the signature rather than trusting them as separate, unauthenticated header reads.

### Proof of Concept
1. App installs on Attacker's own shop `attacker.myshopify.com`; attacker triggers a webhook (e.g., `orders/create`) and captures the legitimate POST: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid, computed by Shopify using the app's real `client_secret`).
2. Attacker replays the identical request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and/or `X-Shopify-Topic` to a topic registered by the app).
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb:12-31` recomputes the HMAC over `B` only, matches `H`, and returns `true`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) proceeds to call the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: JSON.parse(B), ...)`, delivering attacker-controlled data tagged with the victim's shop identity despite no cryptographic proof that the victim shop ever sent this payload.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
