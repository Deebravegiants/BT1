## Analysis

The reported bug class — an accounting/limit check performed **before** an external token transfer, with the authoritative state update happening only **after**, unprotected by a reentrancy guard — has a concrete analog in the Tron deployment of the Intent Gateway.

The canonical EVM `IntentGatewayV2` explicitly guards `placeOrder`/`fillOrder` with `ReentrancyGuardTransient` [1](#0-0) , and its `fillOrder`/`_withdraw` flow was hardened to set `_filled[commitment]` at the very top (CEI) specifically to close a reentrancy window during ETH/ERC-20 payouts, as documented and tested in `IntrinsicIntentsReentrancyTest.sol` [2](#0-1) .

The Tron port of the same contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`) does **not** inherit any reentrancy guard — it extends only `HyperApp` and `EIP712`, with no `ReentrancyGuard`/`nonReentrant` anywhere in the file [3](#0-2) . Its `placeOrder`-equivalent escrow logic still performs `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and only afterwards updates the authoritative escrow accounting `_orders[commitment][token] += reducedInputs[i].amount` [4](#0-3) . This is the same Checks-Effects-Interactions ordering flaw as `SolverVaults.deposit()`: an external call (`safeTransferFrom`) happens before the state that tracks/limits accounting is finalized, and — unlike the EVM sibling contract — there is no reentrancy guard to close the window.

### Title
Missing reentrancy protection in Tron `IntentGatewayV2` allows escrow-accounting manipulation via hook-capable input tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2` on Tron escrows order input tokens via `safeTransferFrom` before updating the `_orders` escrow accounting, and — unlike the canonical EVM `IntentGatewayV2`, which is wrapped in `ReentrancyGuardTransient` — this contract has no reentrancy guard at all.

### Finding Description
In the EVM implementation, `IntentGatewayV2` inherits `ReentrancyGuardTransient` and applies it to `placeOrder`/`fillOrder` [1](#0-0) , and the fill/withdraw path sets `_filled[commitment]` before any external transfer specifically to prevent reentrant self-fills, as verified by `IntrinsicIntentsReentrancyTest.sol` [5](#0-4) .

The Tron port re-implements the same order-placement/escrow logic but omits any `nonReentrant` protection [3](#0-2) . Its escrow-credit step follows the exact CEI-violating shape flagged in the external report: `safeTransferFrom` (external call, can trigger a token hook on upgradeable USDT/USDC-style tokens) executes first, and `_orders[commitment][token] += reducedInputs[i].amount` (the accounting the rest of the protocol trusts for withdrawals/fills) is only updated afterward [4](#0-3) . The same pattern also appears in the predispatch branch, where dust/escrow accounting is updated after a `ICallDispatcher(dispatcher).dispatch(...)` external call [6](#0-5) .

### Impact Explanation
Hyperbridge explicitly supports USDT/USDC across many EVM-compatible chains, most of which are upgradeable proxies that can add transfer hooks. Since Tron's `IntentGatewayV2` lacks the `nonReentrant` protection that its EVM sibling relies on, a malicious/hook-bearing input token could reenter the gateway during the `safeTransferFrom` window and interleave a second `placeOrder`/`fillOrder`/withdrawal call while the outer call's escrow accounting is not yet finalized, corrupting the `_orders` escrow ledger that gates fund release to solvers and beneficiaries. This risks fund theft or the gateway's real token balance being over-committed relative to recorded escrow.

### Likelihood Explanation
Requires an input token with a transfer hook (feasible for upgraded USDT/USDC-style proxies, which the protocol explicitly targets) and requires the attacker to control or predict the order flow — a single unprivileged `placeOrder` transaction is enough to trigger the reentrant window, since no `nonReentrant` guard exists to block it.

### Recommendation
Add a reentrancy guard (matching the EVM implementation's `ReentrancyGuardTransient`) to Tron's `IntentGatewayV2`, and/or reorder the escrow logic so that `_orders[commitment][token]` accounting is finalized before any external call (`safeTransferFrom`, `ICallDispatcher.dispatch`), following strict CEI.

### Proof of Concept
1. Attacker deploys/uses an ERC-20 (or an upgraded USDT/USDC proxy with a transfer hook) as `order.inputs[0].token`.
2. Attacker calls `placeOrder` on Tron's `IntentGatewayV2`; execution reaches `IERC20(token).safeTransferFrom(msg.sender, address(this), amount)` [7](#0-6) .
3. The token's transfer hook re-enters the gateway (e.g., a second `placeOrder`/fill call) before `_orders[commitment][token] += reducedInputs[i].amount` executes for the outer call, since no `nonReentrant` modifier blocks reentry.
4. The reentrant call operates on inconsistent/incomplete escrow state, enabling corrupted accounting between escrowed tokens and the `_orders` ledger used for subsequent withdrawals.

**Uncertainty:** I could not fully inspect the Tron `fillOrder`/`_fillSameChain` implementation (beyond the `withdraw` helper, which does set `_filled[commitment]` first) within the available tool budget, so I cannot confirm whether the fill path independently reintroduces the exact self-fill/fee-theft reentrancy that was fixed on the EVM side. The confirmed root cause is the absence of any reentrancy guard combined with CEI-violating escrow updates in `placeOrder`'s token-transfer loop.
