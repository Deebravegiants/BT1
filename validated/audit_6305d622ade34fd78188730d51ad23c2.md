## Title
Webhook Shop-Domain Header Is Not Bound to the HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, yet it dispatches the webhook to the host application's handler using the `shop` (and `topic`) values taken from unauthenticated HTTP headers. Because the HMAC secret (`Context.api_secret_key`) is a single, app-wide secret shared across every shop that has the app installed — not a per-shop secret — any unprivileged user who installs the app on their own store can obtain a validly-signed webhook body and then replay that exact body while substituting the `X-Shopify-Shop-Domain` header of a different (victim) shop. The signature check still passes because it never covers the shop header, so the host application processes attacker-controlled data as if it originated from the victim's tenant.

### Finding Description
The HMAC validation logic only signs the raw body: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`, and none of `shop`, `topic`, `api_version`, or `webhook_id` (all read straight from HTTP headers) participate in the signable string.

`HmacValidator.validate` computes/compares the HMAC using only this signable string and the app-wide secret `Context.api_secret_key` (the same secret is valid for every shop that installs the app, not scoped per tenant): [3](#0-2) 

`Registry.process` then trusts the header-derived `request.shop` value once the body-only HMAC check passes, and forwards it to the handler as authoritative tenant identity: [4](#0-3) 

The broken identity binding is:
`HMAC_valid(body, api_secret_key) == true` is treated as proof that `shop_header == shop_that_produced(body)`, but the HMAC never covers `shop_header`. These two are independent values — anyone possessing one legitimately-signed body (trivial to obtain by installing the app on their own store) can pair it with an arbitrary `shop` header and still pass validation.

### Impact Explanation
This breaks the tenant/authentication boundary the HMAC check is supposed to enforce. An attacker who installs the app on Shop A (something any unprivileged internet user with a Shopify account can do for a public app) receives genuine, validly-signed webhook deliveries for Shop A. By replaying the identical raw body with the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header changed to Shop B's domain, the forged request still satisfies `Utils::HmacValidator.validate`, and `Registry.process` calls the host app's handler with `WebhookMetadata` claiming the data belongs to Shop B: [5](#0-4) 

Any host application that uses `data.shop` to select the tenant/session context to act upon (e.g., to look up the shop's session, apply order/product updates, or trigger per-shop business logic keyed by this gem's own webhook metadata) will apply attacker-controlled payload content under another tenant's identity — a cross-tenant access/data-injection condition.

### Likelihood Explanation
Likelihood is meaningful because:
- Obtaining a validly-signed body requires nothing more than installing the app on an attacker-owned store — no leaked secrets, no privileged access, no social engineering.
- The `api_secret_key` is shared across all shops for the app, so a signature valid for one tenant is valid for all tenants.
- The gem's own `Registry.process`/`Request` classes provide no cross-check between the signed body and the asserted shop, so every consumer of this library's webhook dispatch is exposed unless it independently re-validates the shop out-of-band (which the gem does not document as required, nor does it enforce).

### Recommendation
Bind the shop identity to the authenticated payload rather than trusting the unauthenticated header:
- Where possible, derive/validate the shop from data actually contained in and covered by the signed body (e.g., a `X-Shopify-Shop-Id`/resource fields cross-checked against an API call), or
- Require verification that the shop asserted in the header matches a shop for which the caller can independently prove possession (e.g., cross-reference against a known/installed shop list keyed by more than the header), or
- At minimum, document prominently that `request.shop`/`WebhookMetadata#shop` is NOT cryptographically bound to the HMAC and must not be used by host applications as a trusted tenant selector without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`, generating a real webhook subscription.
2. Shopify sends a legitimate webhook to the app's endpoint with headers:
   - `X-Shopify-Hmac-Sha256: <valid signature over raw body B>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - body `B`
3. Attacker captures `B` and the valid HMAC, then resends the exact same request but changes only:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
4. `Utils::HmacValidator.validate` recomputes the HMAC over `B` using the app's single `api_secret_key` — it matches, since the signature never included the shop header.
5. `Registry.process` proceeds, invoking the host app's handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: parsed(B) ...)`, causing the host application to act on `victim-shop.myshopify.com`'s tenant context using attacker-supplied body content.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
