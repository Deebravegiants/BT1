### Title
`isOwnAddress` falsely matches attacker-supplied address against shared `noAccountYet` sentinel for unsynced abstract-account wallets - ([File: features/address-provider/module/address-provider.js])

### Summary
For abstract-account assets (e.g. EOS), `AddressProvider.isOwnAddress` compares the caller-supplied `address` string directly against `#getMainAccountName`'s result, which falls back to `asset.noAccountYet` — a fixed, non-secret, per-asset constant — whenever `accountStates[walletAccount]?.[assetName]?.mainAccountName` has not yet been set [1](#0-0) . An attacker who supplies `address === asset.noAccountYet` for any fresh/unsynced `walletAccount` of that asset will get `isOwnAddress` to return `true`, even though this "account name" is not tied to that specific wallet account at all [2](#0-1) .

### Finding Description
`isOwnAddress` branches on `asset.api.features.abstractAccounts`; for such assets it calls `#getMainAccountName` and does a strict string equality check against the caller's `address` parameter [2](#0-1) . `#getMainAccountName` reads `accountStates[walletAccount]?.[assetName]?.mainAccountName`, and if that's falsy (unset, e.g. because the wallet hasn't synced/created an on-chain account for that abstract-account asset yet), it returns `this.#getAsset(assetName).noAccountYet` — a static placeholder value defined on the asset object itself, not derived from any account-specific secret or state [1](#0-0) . This is confirmed by the existing test suite, which shows `getReceiveAddress` also returns this exact placeholder (`assets.eosio.noAccountYet`) until `mainAccountName` is set [3](#0-2) . Since `noAccountYet` is a hardcoded, asset-level constant (not per-wallet, not secret, and shared across all wallet accounts of that asset), any caller who knows/reads it can pass it as the `address` argument and get a `true` "own address" result for any walletAccount that hasn't yet recorded a `mainAccountName`.

The API entry point `addressProviderApi.isOwnAddress` wraps `AddressProvider.isOwnAddress` behind only a lock check (`lockedAtom`) and walletAccount resolution — no per-account/address-specific validation is applied before dispatching to the module method [4](#0-3) . There is no additional guard preventing an unprivileged caller (e.g., a dapp/RPC consumer with access to this API) from invoking `isOwnAddress` with an attacker-chosen `address` value while the wallet is merely unlocked.

### Impact Explanation
This produces a false-positive "own address" result tying an arbitrary, non-owned identifier to a victim's wallet account. Any downstream logic that gates trust, auto-approval, "send to self" detection, deduplication of change addresses, or similar decisions on `isOwnAddress` could be misled into treating the sentinel value as belonging to the user, for as long as that abstract-account wallet has not yet established its `mainAccountName`. The impact is scoped to logic consumers of `isOwnAddress` and does not by itself grant signing, key disclosure, or fund transfer capability — it's a wrong-account/false-identity classification bug rather than a direct fund-loss primitive.

### Likelihood Explanation
Preconditions are narrow but realistic: the walletAccount must be for an abstract-account asset (e.g. EOS) and must not yet have a recorded `mainAccountName` in `accountStatesAtom` (i.e., a fresh, not-yet-synced/created account) [1](#0-0) . The `noAccountYet` value is a static, non-secret constant on the asset definition, so any consumer of the codebase (including a malicious dapp with RPC access) can trivially discover and supply it. The exploit requires no privileged state, no key material, and is deterministic/repeatable, matching the described unit-test PoC path.

### Recommendation
Do not treat the `noAccountYet` fallback as a valid ownership match in `isOwnAddress`. Specifically, `#getMainAccountName`'s fallback value should not be compared for equality in `isOwnAddress`; instead, `isOwnAddress` should return `false` outright when no `mainAccountName` has been recorded for the given `walletAccount`/`assetName` (i.e., check `accountStates[walletAccount]?.[assetName]?.mainAccountName` is truthy before doing the comparison, rather than reusing the same fallback-producing helper used for address-display purposes).

### Proof of Concept
Unit test in `features/address-provider/__tests__/module/seed/eos.test.js` style:
```js
it('should return false when comparing against the shared noAccountYet sentinel with no mainAccountName set', async () => {
  const { addressProvider } = await setup()
  await expect(
    addressProvider.isOwnAddress({
      walletAccount,
      assetName: 'eosio',
      address: assets.eosio.noAccountYet, // attacker-supplied, publicly known constant
    })
  ).resolves.toBe(false)
})
```
Expected (current buggy) behavior: resolves to `true` because `#getMainAccountName` falls back to `assets.eosio.noAccountYet` and `address === mainAccountName` holds. Expected (fixed) behavior: resolves to `false`, since no actual `mainAccountName` has been established for `walletAccount`.
