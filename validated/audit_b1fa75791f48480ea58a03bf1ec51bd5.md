### Title
Router.sell computes assetOut from the K-invariant without capping it against the pair's real LT balance, letting a large sell request more LT than the curve actually holds - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy` explicitly caps `tokensOut` at the pair's real token balance (`pair.tokenBalance()`) because the stored `reserveToken` is virtual and can exceed the real sellable supply [1](#0-0) . `_computeSell`, which computes the LT payout for a token sell, has no analogous cap against the pair's real LT balance (`pair.assetBalance()`), even though the stored `reserveAsset` is also partly virtual — it is seeded with a `virtualLtReserve` at `mint()` time that is never backed by real LT until buys occur [2](#0-1) [3](#0-2) .

### Finding Description
`Pair.mint` seeds `assetReserve` with a virtual LT amount while the pair's real LT balance starts at `0`; only the LT that flows in from real buys increases the real balance [4](#0-3) . This means at any point in the curve's life, `reserveAsset (stored) = virtualLtReserve + realRaisedLT`, but `assetBalance() (real) = realRaisedLT` only — a permanent deficit equal to `virtualLtReserve` exists between the stored reserve and the real balance, exactly mirrored by the `Router.graduate` comment which explicitly subtracts `virtualLtReserve` from the stored reserve to compute the real LT to pull out at graduation [3](#0-2) .

`Router.sell` computes `assetOut` purely from the constant-product formula against the stored (virtual-inclusive) `reserveAsset`, with no check that `assetOut` fits within the pair's real LT balance:
```
uint256 newReserveToken = reserveToken + amountIn;
assetOut = reserveAsset - (k / newReserveToken);
```
As `amountIn` (tokens sold) grows, `k / newReserveToken` shrinks toward `0`, driving `assetOut` toward the *full* stored `reserveAsset` — which is more LT than the pair ever actually holds, because the stored reserve always includes the un-backed `virtualLtReserve` slice [5](#0-4) .

`Router.sell` then calls `IPair(pairAddr).transferAsset(to, assetOut)` before updating reserves via `swap()` [6](#0-5) . Once `amountIn` (a large token sell, reachable by any holder who accumulated enough tokens via ordinary curve buys) crosses the threshold where the K-formula's requested `assetOut` exceeds the pair's real LT balance, `transferAsset`'s underlying `safeTransfer` reverts for insufficient balance, and the entire sell — including the `Zap._sellInternal` token pull that preceded it — reverts atomically [7](#0-6) . This is the direct structural analog of the referenced PocketMine-MP bug: neither `_computeSell` nor `Router.sell` validates the requested payout ("dropped item count") against what is actually available before attempting to move it, and only the downstream ERC20 balance check (equivalent to the crash trigger in the original bug) catches the discrepancy.

Unlike `_computeBuy`, which pre-clamps `tokensOut` to `pair.tokenBalance()` and back-derives a consistent `amountInUsed`/`newReserveAsset` pair so the trade always succeeds at a smaller size, `_computeSell` has no such clamp-and-recompute path. There is no way for a large seller to get a partial, consistently-priced sell near the tail of the curve — the transaction either succeeds at the full K-formula price or reverts outright with an opaque low-level ERC20 error, with no graceful degradation.

### Impact Explanation
This does not enable theft (the failure mode is atomic revert, not a mispriced transfer of real LT), but it produces an availability/DoS gap that is the structural counterpart of the missing-count-check class in the source advisory: sufficiently large legitimate sells near the tail of the curve (where real LT raised is small relative to the virtual seed, or where a holder has accumulated a large share of circulating supply) are unconditionally bricked with an unhandled revert instead of being safely capped/partial-filled the way buys are. Because `Router.sell` is the sole exit path for curve-stage holders (post-graduation sells route through Uniswap/HyperSwap instead), any holder who cannot exit via a capped or partial sell is forced to either split into smaller sells (if even possible) or hold until a graduation event, and in adversarial curve states this can prevent large legitimate holders from exiting at all on the curve.

### Likelihood Explanation
Reachable by any unprivileged trader through the public `Zap.sell` / `Zap.sellWithPermit` path with ordinary `sell(tokenAddress, tokenAmount, minUsdcOut)` calls [8](#0-7) ; no special role or malicious LT/HyperSwap behavior is required. Whether the threshold is reachable depends on the concrete virtual-reserve constants chosen at token launch versus the amount of tokens a single seller can accumulate, which is not fully derivable from the excerpts reviewed here.

### Recommendation
Mirror `_computeBuy`'s pattern in `_computeSell`/`Router.sell`: cap `assetOut` at `pair.assetBalance()` (or at `reserveAsset - virtualLtReserve`, tracked explicitly rather than inferred), and back-derive a consistent `amountInUsed`/reduced-fill so oversized sells settle for the maximum safely payable amount instead of reverting unconditionally.

### Proof of Concept
Not independently reproduced in this pass — reachability depends on the exact virtual-reserve constants used at `Bonding.launch`/`Router.addInitialLiquidity` time, which were not available in the reviewed excerpts. Conceptually: buy heavily into a token (or wait for the curve to raise little real LT relative to its virtual seed), accumulate a large fraction of circulating token supply, then call `Zap.sell` with that full amount; if `newReserveToken` grows enough that the K-formula's `assetOut` exceeds `IPair(pair).assetBalance()`, the transaction reverts inside `IPair.transferAsset`'s `safeTransfer`, unconditionally blocking that sell.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

    function sell(
        uint256 amountIn,
        address token,
        address to
    ) external onlyRole(BONDING_ROLE) returns (uint256 tokensIn, uint256 assetOut) {
        if (amountIn == 0) revert ZeroAmount();

        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        tokensIn = amountIn;

        IERC20(token).safeTransferFrom(to, pairAddr, amountIn);

        assetOut = _computeSell(pairAddr, amountIn);

        IPair(pairAddr).transferAsset(to, assetOut);

        IPair(pairAddr).swap(amountIn, 0, 0, assetOut);
    }
