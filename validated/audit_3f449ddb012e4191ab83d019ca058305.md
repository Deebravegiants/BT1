### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read from separate HTTP headers that are never covered by the HMAC computation. `Registry.process` validates only that the body's HMAC is correct and then trusts the header-derived `shop` value when building `WebhookMetadata` for the handler. Because Shopify's HMAC is a function of `(secret, body)` only, any `(body, hmac)` pair that is valid for one shop's webhook remains valid forever and for any shop, letting an attacker who can obtain one legitimately-signed webhook body replay it with an attacker-chosen `shop-domain` header and have the library accept it as authentic for the impersonated shop.

### Finding Description
In `lib/shopify_api/webhooks/request.rb`:
- `hmac` and `to_signable_string` are the two members required by `Utils::VerifiableQuery` [1](#0-0) .
- `to_signable_string` returns `@raw_body` only [2](#0-1) .
- `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers that are not part of the signable string [3](#0-2) .

`Utils::HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac` header, i.e., it only proves the body was signed by someone holding `api_secret_key` — it says nothing about which shop, topic, or webhook id the caller claims [4](#0-3) .

`Registry.process` then does exactly that: validate the body HMAC, and unconditionally trust the header-derived `request.shop` when constructing the object handed to the app's handler: [5](#0-4) 

The documented handler contract explicitly tells integrators to trust `data.shop` as "The shop domain of the webhook" [6](#0-5) , and the reference Rails integration in the docs passes the request straight from the public endpoint into `Registry.process` with no additional shop verification [7](#0-6) .

**Broken identity binding (as an equality):**
`hmac_valid(raw_body) == true` is treated by `Registry.process` as implying `request.shop == originating_shop`, but the equality does not hold because `shop` is not an input to the HMAC. The only invariant the HMAC actually proves is `hmac_valid(raw_body) == true ⇒ raw_body was generated using api_secret_key` — it says nothing about the `shop-domain`, `topic`, or `webhook-id` headers that accompany that body.

### Impact Explanation
An unprivileged actor who can obtain one legitimately-signed `(raw_body, hmac)` pair — e.g., by installing the app on their own store and receiving a real webhook, or by observing one on the wire — can replay that exact body and HMAC to the app's public webhook endpoint while substituting an arbitrary `shop-domain` (and `topic`/`webhook-id`) header. `HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen value. Any host application that uses `data.shop` (as the library's own documentation instructs) to key its per-tenant persistence, job dispatch, or session lookup will process and store attacker-controlled webhook content under a victim shop's identity — a cross-tenant data-injection/spoofing primitive that also enables convincing a victim's install to appear to receive events it never triggered.

### Likelihood Explanation
The webhook endpoint is by design a public, unauthenticated HTTP endpoint (that is the entire point of `Registry.process`/`Request`). Obtaining one valid `(body, hmac)` sample only requires the attacker to install the target app on their own shop (a normal, unprivileged action any developer can take) or to capture one webhook delivery. No `api_secret_key`, access token, or privileged account for the victim shop is required. Because the HMAC is content-only and never mixes in the header claims, the replay works for the lifetime of the app (HMACs don't expire).

### Recommendation
Include the shop, topic, and webhook id in the material that is authenticated, or otherwise cryptographically bind the header claims to the signed payload before trusting them:
- Compute/verify the HMAC over a canonical string that incorporates `shop-domain`, `topic`, and `webhook-id` (in addition to the body), analogous to how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop`, `state`, `host`, etc. into its signable string [8](#0-7) .
- At minimum, document prominently (and ideally enforce in `Registry.process`) that `request.shop` is unauthenticated header data and that host applications must cross-check it against a known/expected shop (e.g., the shop associated with the registered webhook id) before trusting it for tenant-scoped operations.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H` (valid, since `H = HMAC(secret, B)`).
2. Replay the exact same request to the app's public webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes `HMAC(secret, B)`, which still equals `H`, so validation succeeds [9](#0-8) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata#shop == "victim.myshopify.com"` [10](#0-9) , causing the host application to process/store attacker-supplied body content under the victim shop's identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
