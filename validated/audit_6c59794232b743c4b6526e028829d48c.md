Confirmed: `placeOrder` in `IntentGatewayV2.sol` never validates that `order.output.assets[i].amount` is non-zero — it only checks for duplicate output tokens and non-empty `inputs` [1](#0-0) . This means a user can place a cross-chain order with a zero-amount output entry for a given token.

At fill time, `ExtrinsicIntents._fillCrossChain` computes `totalRequired = order.output.assets[i].amount` and unconditionally calls `IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare)` with no `> 0` guard before the transfer, unlike other paths in the same codebase (e.g. `_withdraw` in `IntentsBase.sol` explicitly does `if (amount == 0) continue;` before transferring) [2](#0-1) [3](#0-2) .

### Title
Zero-amount output transfer in `_fillCrossChain` can permanently freeze cross-chain order escrow - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
`placeOrder` does not reject orders whose `output.assets[i].amount` is zero. When such an order is a cross-chain order, `_fillCrossChain` always calls `safeTransferFrom` for that output token, even when the transferred amount is zero. Some ERC-20 tokens (well documented class, e.g. certain deflationary/compliance tokens) revert on a zero-value `transfer`/`transferFrom`. If the output token for that leg is such a token, `fillOrder` can never succeed for that order.

### Finding Description
`placeOrder` in `IntentGatewayV2.sol` validates only `order.inputs.length != 0` and rejects duplicate output tokens; it never checks that each `order.output.assets[i].amount > 0` [1](#0-0) . The order is then escrowed and its commitment stored cross-chain.

On the destination chain, `_fillCrossChain` iterates the output assets and, for every ERC-20 output (including one with `totalRequired == 0`), unconditionally executes:
```solidity
IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
``` [4](#0-3) 

If `token` reverts on a zero-value transfer (a known non-standard ERC-20 behavior), this call always reverts, so `fillOrder` for this order can never succeed no matter who the solver is.

### Impact Explanation
Because cross-chain fills are all-or-nothing (no partial fills, per the documented Fill Flow) [5](#0-4) , the order can never be filled. The user's escrowed input tokens on the source chain remain locked in `_orders[commitment][token]` indefinitely, since the only ways to release escrow are (a) a successful fill triggering `RedeemEscrow`, or (b) cancellation. Cancellation eventually recovers funds via `cancelFromDest`/`cancelFromSource`, but if the user's `session`/authorized flow depends on the order eventually filling, or if cancel windows/relayer costs make cancellation impractical, escrowed value can be stuck for extended periods; more importantly this represents a permanent denial-of-fill vector for any order whose destination output token reverts on zero-amount transfers, directly analogous to the reported NFT-freeze bug class (unconditional zero-amount transfer blocking the only "unlock" path).

### Likelihood Explanation
This requires only that a user (or an attacker griefing a specific token/route) create a cross-chain order with a zero-amount entry in `output.assets` for a token that reverts on 0-value transfers — a single `placeOrder` call, fully reachable by any unprivileged user, with no special permissions needed. The protocol explicitly supports arbitrary ERC-20 tokens as inputs/outputs, so such tokens are within scope.

### Recommendation
In `placeOrder`, reject any `order.output.assets[i].amount == 0` (mirroring the existing zero-checks already applied to `order.inputs` and `predispatch.assets`), and/or guard the transfer call sites in `_fillCrossChain` (and `_fillSameChain`/`IntrinsicIntents.sol`) with `if (amount > 0)` before calling `safeTransferFrom`, consistent with the pattern already used in `_withdraw`.

### Proof of Concept
1. User calls `placeOrder` with `order.output.assets = [{token: T, amount: 0}]` where `T` is an ERC-20 that reverts on `transferFrom(from, to, 0)`. This succeeds because `placeOrder` has no zero-amount check on outputs [1](#0-0) .
2. Inputs are escrowed on the source chain as normal.
3. A solver attempts `fillOrder` on the destination chain. `_fillCrossChain` computes `totalRequired = 0`, and since `options.outputs[i].amount` must be `>= totalRequired` (i.e., can also be 0), `beneficiaryTotal = 0 + beneficiaryShare(0) = 0`, and the code calls `IERC20(T).safeTransferFrom(msg.sender, beneficiary, 0)` unconditionally [4](#0-3) .
4. If `T.transferFrom` reverts on a 0 amount, `fillOrder` reverts for every solver attempt, permanently preventing settlement and leaving the source-chain escrow locked outside of the cancellation path.

## Cross-Chain Swaps

Source and destination are different chains. Settlement requires cross-chain messaging through Hyperbridge. Fills are all-or-nothing — partial fills are not supported for cross-chain orders.

![Cross-Chain Swap](./images/intent-gateway-cross-chain.svg)

### Fill Flow

The solver calls `fillOrder(order, options)` on the **destination chain**. The function verifies the order hasn't expired (`order.deadline >= block.number`), confirms execution is on the correct chain, and checks the order hasn't already been filled. The solver must provide output amounts greater than or equal to the order's required amounts — any amount below the required amount reverts with `InvalidInput()`.

If the solver provides more tokens than required, the excess (surplus) is split according to `surplusShareBps`. If the order includes calldata, 100% of surplus goes to the protocol to prevent manipulation.

After delivering output tokens to the beneficiary, the contract dispatches a cross-chain `RedeemEscrow` message back to the source chain.
