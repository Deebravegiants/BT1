### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not covered by the HMAC signature, allowing cross-tenant spoofing of the webhook's shop attribution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the handler a `WebhookMetadata` struct whose `shop` field is read straight from an unauthenticated HTTP header. Any party who can obtain one genuinely-signed webhook body (e.g., the operator of any shop that has installed the app) can replay that exact body with a forged `x-shopify-shop-domain` header for a different shop, and the app will process it as if it came from the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the signature only over that signable string (`to_signable_string`), i.e. only over the raw body: [2](#0-1) 

Meanwhile, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read directly from HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, etc.) that are never part of the signed material: [3](#0-2) 

`Registry.process` verifies the HMAC and then immediately trusts `request.shop` (along with `topic`/`webhook_id`/`api_version`) to build the `WebhookMetadata` passed to the app's handler, with no further binding check between the authenticated body and the claimed shop: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `shop authenticated by the HMAC == shop the handler acts on`. Because the HMAC only signs the body, that equality never holds — the header-derived `shop` is an independent, attacker-controllable value once an attacker possesses any validly-signed body (e.g., their own webhook, received legitimately after installing the app). Since `api_secret_key` is the same for every merchant using a given app, a webhook that Shopify genuinely delivered to Shop A's endpoint carries an HMAC that remains valid no matter what shop-domain header is attached to it — the signature never covered that header in the first place. Replaying that same raw body with `x-shopify-shop-domain` rewritten to Shop B causes `Registry.process` to hand the handler a `WebhookMetadata` claiming the data belongs to Shop B, passing HMAC validation.

### Impact Explanation
Handlers built on top of this library are documented to key their session/token lookups and business-data updates off `WebhookMetadata#shop` (see `docs/usage/webhooks.md`, "Process a Webhook"). An attacker who legitimately installs the app on their own shop can capture a real, validly-signed webhook payload and resubmit it with a spoofed shop-domain header claiming to be a different, victim tenant. Downstream handlers that use `data.shop` as the session/storage key will apply attacker-controlled body content to the victim tenant's records — a cross-tenant data-integrity/confusion vulnerability, matching the report's underlying bug class ("data processed" without properly verifying who it legitimately belongs to).

### Likelihood Explanation
Any merchant/developer who can install the target app on a shop they control can trivially capture one authentic webhook (their own HTTP webhook delivery) and replay it with a modified header, since no additional binding of headers to the signed body exists. No credential leakage or privileged access is required beyond ordinary app installation, which is the normal, low-privilege path for interacting with a public Shopify app.

### Recommendation
Bind the shop (and ideally the webhook id/topic) claim to the HMAC-verified content instead of trusting a bare header:
- Extend `to_signable_string` (or an equivalent check in `HmacValidator`/`Registry.process`) to incorporate the `shop`, `topic`, and `webhook_id` header values into the signed material, or
- Cross-check `request.shop` against a shop known/expected by the caller (e.g., an active session or an allow-list) before invoking the handler, and reject processing when the header-derived shop doesn't match a value the app already trusts for that installation.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook POST with body `B` and a valid `x-shopify-hmac-sha256` header (signed by the shared `api_secret_key`).
2. Attacker resends the exact same request to the app's webhook endpoint, keeping `raw_body = B` and the original valid HMAC header unchanged, but replaces `x-shopify-shop-domain: attacker.myshopify.com` with `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unmodified) raw body against the (unmodified) HMAC: [6](#0-5) 
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, i.e., attacker-supplied body content now attributed to a tenant the attacker does not control.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
