### Title
Fee-on-transfer/deflationary tokens cause escrow over-crediting in Tron `IntentGatewayV2.placeOrder` (no post-transfer balance check) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` computes the commitment hash and the escrowed `reducedInputs[i].amount` from the user-supplied `order.inputs[i].amount` **before** performing the ERC-20 transfer, and in the simple (non-predispatch) escrow path never re-measures the actual token balance received. For rebasing/deflationary/fee-on-transfer tokens this credits the order's escrow ledger with more tokens than the gateway actually holds.

### Finding Description
In `evm/src/apps/IntentGatewayV2.sol::placeOrder`, the canonical EVM implementation explicitly protects against fee-on-transfer tokens: it snapshots the gateway's balance before the transfer and computes the actually-received amount afterward, then uses that received amount for both the commitment and the escrow crediting [1](#0-0) .

The Tron fork at `evm/tron/contracts/apps/IntentGatewayV2.sol` does **not** replicate this. `reducedInputs`/`commitment` are computed up-front from the raw `order.inputs[i].amount` supplied by the caller, prior to any transfer [2](#0-1) . In the simple (no-predispatch) escrow path, the contract calls `safeTransferFrom` for the requested amount and then blindly credits `_orders[commitment][token] += reducedInputs[i].amount` — a value derived from the pre-transfer requested amount — with no comparison against the token balance actually gained by the contract:
```solidity
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
// Store reduced amount (after protocol fees) in escrow
_orders[commitment][token] += reducedInputs[i].amount;
``` [3](#0-2) 

If `token` is a fee-on-transfer/deflationary token (or a rebasing token that can lose balance between transfer and later withdrawal), the gateway's actual token balance increase is smaller than `order.inputs[i].amount`, yet the internal accounting (`_orders[commitment][token]`) is credited as if the full pre-fee amount arrived. (Note the predispatch branch of the same function does correctly re-measure `balanceOf(dispatcher)` after the call and emits dust for any shortfall/excess, so only the non-predispatch/default escrow path is affected.) [4](#0-3) 

This is the exact bug class from the referenced report — failing to verify actual balance received before crediting internal accounting for tokens whose transferred amount can differ from the nominal amount.

### Impact Explanation
Because escrowed accounting is inflated relative to the token balance actually custodied by the contract, the sum of all `_orders[commitment][token]` entries for a fee-on-transfer/deflationary token can exceed `IERC20(token).balanceOf(address(this))`. When solvers later fill orders and the source-chain settlement path releases escrow (transferring `_orders[commitment][token]` to the solver), the contract can attempt to pay out more of that token than it holds — draining tokens legitimately escrowed by other users/orders and eventually causing transfer reverts (denial of service / frozen funds) for later orders once the shortfall is exhausted. This is a concrete accounting/fund-safety break in escrow custody reachable by any unprivileged user submitting a `placeOrder` transaction with an arbitrary ERC-20 token address, satisfying "concrete theft or permanent freezing of funds."

### Likelihood Explanation
Likelihood is moderate: it requires the deployer/market to permit a fee-on-transfer, deflationary, or rebasing token as an order input on the Tron deployment (the Tron ecosystem includes such tokens, e.g. certain TRC-20 tokens with transfer taxes). Since `placeOrder` accepts an arbitrary `token` address supplied by any caller with no allow-list enforced in the shown code, any user can trigger the bug by placing an order with such a token, with no privileged role required.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: for the non-predispatch path, snapshot `balanceOf(address(this))` before calling `safeTransferFrom`, compute the actual delta afterward, and use that measured amount (not the caller-supplied `order.inputs[i].amount`) both for computing `reducedInputs`/the commitment hash and for crediting `_orders[commitment][token]`.

### Proof of Concept
1. Deploy a fee-on-transfer TRC-20 token (e.g., 5% transfer fee) and mint balance to a user.
2. User calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs[0] = {token: fotToken, amount: 1000}`, no predispatch.
3. `safeTransferFrom` moves only 950 tokens into the contract (contract balance increases by 950), but `_orders[commitment][fotToken]` is credited with `reducedInputs[0].amount` derived from the full 1000 (minus protocol fee only), e.g. ~995 — 45 more than the gateway actually received.
4. Repeating this with multiple orders/users accumulates an internal-ledger balance exceeding the real token balance held by the contract, so a subsequent legitimate `withdraw()`/settlement for an earlier order can fail or drain balance intended for other orders. [3](#0-2)
