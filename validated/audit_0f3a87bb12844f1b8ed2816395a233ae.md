This confirms the intended and documented usage pattern: `data.shop` is explicitly documented to be used by the host application to identify **which tenant/shop** the webhook belongs to (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), making it a genuine tenant-identity binding.

### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook forgery — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, while the `shop`, `topic`, and `webhook_id` values used to route and attribute the webhook to a tenant are taken directly from unauthenticated HTTP headers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `shop`, `topic`, `webhook_id`, `api_version` are all parsed straight from HTTP headers with no cryptographic binding to that body [2](#0-1) . `Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` (i.e., only the body) against `Context.api_secret_key`, and then immediately trusts `request.shop` and `request.topic` to look up a handler and build the `WebhookMetadata` passed to the app's handler [3](#0-2) . The binding that should hold is: `bytes verified by HMAC == bytes used to determine the tenant (shop) and dispatch (topic)`. Here that equality is broken — the HMAC only covers the body, not the headers that carry the tenant identity.

Because the app's `api_secret_key` is shared across all shops that install the app, any merchant can install the app on their own store (an "unprivileged internet user" merely needs to be a shop owner, not an app operator), trigger a legitimate webhook delivery for a topic they control the body of, and thereby obtain a body + valid HMAC pair signed with the app's real secret. They can then replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `shopify-shop-domain` and/or `shopify-topic` headers to name a different (victim) shop. The HMAC check still passes because it only recomputes over the untouched body, while `Registry.process` dispatches to the handler using the forged headers — as documented, apps use `data.shop` to route/attribute persisted work per tenant [4](#0-3) .

### Impact Explanation
This lets an attacker who legitimately installed the app on their own store inject attacker-chosen webhook bodies that the host application will process as if delivered for an arbitrary victim shop, since the only cryptographic guarantee (`HmacValidator.validate`) does not cover the shop/topic identity fields that are relied upon downstream. This is a cross-tenant boundary break: the identity ("this event belongs to shop X") is not authenticated, only the payload bytes are. Per the documented usage pattern, apps commonly persist or act on data keyed by `data.shop`, so a forged shop header can cause writes/reads attributed to the wrong tenant.

### Likelihood Explanation
Requires only that the attacker be able to install the app on a store they control (a normal, low-privilege action available to any Shopify merchant) and be able to send arbitrary HTTP requests to the app's public webhook endpoint — no access to `api_secret_key`, access tokens, or the victim's credentials is needed. No replay/dedup/timestamp protection is enforced in `Registry.process` beyond the HMAC-over-body check [3](#0-2) .

### Recommendation
Extend the HMAC-verifiable signable string (or add a second binding check) to include the `shop`, `topic`, and `webhook_id` header values, or otherwise cryptographically bind the tenant identity to the payload before dispatching to handlers, so that swapping headers on an otherwise-valid signed body invalidates the request.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers for a webhook topic whose body they can influence or predict (e.g., `carts/update` or a custom metafield webhook).
2. Shopify delivers a legitimately HMAC-signed webhook: body `B`, header `shopify-hmac-sha256: H` (valid HMAC of `B` under the shared `api_secret_key`), `shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays this exact `(B, H)` pair to the same webhook endpoint but rewrites the header to `shopify-shop-domain: victim.myshopify.com` (and/or a different registered `shopify-topic`).
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed by the host controller exactly as documented [5](#0-4) ; `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [6](#0-5) ; `Registry.process` dispatches to the handler with `shop: "victim.myshopify.com"` [3](#0-2) , causing the host app to act on attacker-controlled data as though it originated from the victim's store.
