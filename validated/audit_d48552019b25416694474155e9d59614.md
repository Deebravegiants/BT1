Based on my research, I found a clear analog in the Hyperbridge intents system's native-token withdrawal path, which mirrors the BvbProtocol bug: a message-driven fund release to a hardcoded beneficiary address that can never be changed, with no fallback for a beneficiary that cannot receive native value.

### Title
Escrowed native-token withdrawals can be permanently locked when the beneficiary cannot receive ETH, with no way to redirect the payout - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw()` releases escrowed order funds to a `beneficiary` address decoded from a cross-chain `WithdrawalRequest` (via `onAccept` for `RedeemEscrow`/`RefundEscrow`, or `onGetResponse` for a get-response driven refund). For native-token legs (`token == address(0)`) it calls `_sendValue(beneficiary, amount)`, which reverts the entire transaction if the low-level call fails (`if (!sent) revert InsufficientNativeToken();`). If the `beneficiary` — the order's `user` (refund path) or the filling solver (redeem path) — is a contract without a `receive()`/payable `fallback()`, this call always reverts, and there is no mechanism anywhere in the protocol to change the beneficiary address for a stuck withdrawal.

### Finding Description
`_withdraw` is the single funds-release routine reached from `onAccept` for both `RedeemEscrow` and `RefundEscrow` requests, and from `onGetResponse` on the cancel-from-source path: [1](#0-0) [2](#0-1) [3](#0-2) 

The `beneficiary` for `RedeemEscrow`/`RefundEscrow` is taken verbatim from `order.user` (destination-initiated cancel) or from the solver address recorded when filling the order, and is baked into the cross-chain message body (`WithdrawalRequest.beneficiary`), with no field or entry point letting the affected party redirect funds to a different address: [4](#0-3) 

The native-value transfer path reverts on failure rather than degrading gracefully: [5](#0-4) [6](#0-5) 

Notably, this exact bug class is already recognized and *fixed* elsewhere in the same codebase: `WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout` explicitly re-wrap ETH into WETH and deliver an ERC-20 transfer if the native push fails, with an inline comment stating the intent is specifically to avoid "permanently lock[ing] funds for the same caller class": [7](#0-6) [8](#0-7) 

`IntentsBase._withdraw` (used by the intents/order-filling app, i.e. the "intent solver" surface named in scope) has no equivalent fallback for its native-token leg.

### Impact Explanation
If a user places an order with a native-ETH input and later cancels via `_cancelFromDest`/`_cancelFromSource` (or the corresponding Tron `IntentGatewayV2.cancelOrder`/`withdraw`), the `RefundEscrow` message that eventually arrives always calls `_withdraw` with `beneficiary = order.user`. If `order.user` is a smart-contract wallet that reverts on receiving raw ETH (multisig without a receive function, a proxy without payable fallback, or simply misconfigured), `_sendValue` reverts every time `onAccept`/`onGetResponse` is invoked for that commitment. Since the beneficiary is immutable and there is no separate "claim to a different address" function, the escrowed native tokens in `_orders[commitment][address(0)]` are permanently unreachable — the analog of the NFT being locked forever in the reported BvbProtocol issue. The same applies to the `RedeemEscrow` path if the recorded solver address cannot receive native value. This is a concrete, permanent freezing-of-funds bug affecting user or solver capital escrowed by the intents contract.

### Likelihood Explanation
Reaching this requires only a single order with a native-token input/output whose associated address (user or solver) is a non-payable contract — no privileged role, governance, or malicious relayer/collator is needed, satisfying the "unprivileged... intent solver" reachability requirement. This can occur unintentionally (a smart contract wallet without a receive function) exactly as in the original report's "honest user forgot his wallet can't receive" scenario, making the likelihood non-trivial for real, permissionless usage of the intents system.

### Recommendation
Mirror the fallback pattern already used in `WrappedHyperFungibleToken`: on a failed native `_sendValue` to `beneficiary`, do not revert the whole withdrawal — instead wrap the amount into the WETH/underlying ERC-20 and deliver it via `safeTransfer`, or record the amount in a per-beneficiary withdrawable-balance mapping with a separate `pull`-style `claim(address to)` function that lets the recorded beneficiary redirect the payout to an address of their choosing (analogous to the recommended fix of adding a `to` parameter to `withdrawToken`). This must decouple "who is authorized to claim" (the recorded beneficiary) from "where funds are sent" (attacker/mis-set-up-proof address), and must not let the whole cross-chain message delivery revert solely because of a beneficiary's inability to receive native value.

### Proof of Concept
1. Attacker/careless user deploys a contract `NoReceive` with no `receive()`/payable `fallback()` and uses it as `order.user` when calling `placeOrder` on the intents app with a native ETH input (`token == address(0)`).
2. Before the order is filled, `NoReceive` (as `msg.sender`) calls `cancelOrder`/`_cancelFromDest`, which dispatches a `RefundEscrow` `WithdrawalRequest{beneficiary: NoReceive}` per `ExtrinsicIntents._cancelFromDest`. [4](#0-3) 
3. Hyperbridge relays the request; `onAccept` decodes it and calls `_withdraw(body, true, true)`. [2](#0-1) 
4. Inside `_withdraw`, `_sendValue(NoReceive, amount)` performs a raw call that fails since `NoReceive` has no payable fallback, so `_sendValue` reverts with `InsufficientNativeToken`, reverting the entire `onAccept` transaction. [5](#0-4) 
5. Every subsequent delivery attempt of the same commitment fails identically; `_orders[commitment][address(0)]` remains non-zero and `_filled[commitment]` is never set, permanently locking the escrowed ETH inside the intents contract with no recovery path.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
