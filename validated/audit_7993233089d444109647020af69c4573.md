Found relevant code: `EvmHost.sol`'s `dispatch()` and `fundRequest()` functions both call `swapETHForExactTokens` and, unlike `IntentGatewayV2.sol`, do not check or refund leftover native token from the swap.### Title
`EvmHost` swap-based fee payments do not check `swapETHForExactTokens` return value, permanently locking excess native token sent for dispatch/GET/fundRequest fees - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all let a caller pay the relayer fee in native token by swapping the entire `msg.value` through Uniswap V2's `swapETHForExactTokens`. Unlike the analogous logic in `IntentGatewayV2.placeOrder`, which reads the swap's returned `amounts[0]` and refunds the unspent `msgValue` to the caller, `EvmHost` discards the return value entirely and never refunds the difference between `msg.value` and the actual ETH consumed by the swap.

### Finding Description
`swapETHForExactTokens(amountOut, path, to, deadline)` is an exact-output swap: it only spends as much ETH as the current pool price requires to produce `amountOut` of the fee token, and it returns `amounts[0]`, the actual ETH spent. Uniswap V2's router refunds unspent ETH to `msg.sender` (the caller of the router) at the end of the call, but here `msg.sender` from the router's perspective is `EvmHost` itself, not the original user, because `EvmHost` initiates the swap. Any refunded ETH therefore lands and stays inside `EvmHost`, since none of the three call sites check `amounts[0]` or measure `msg.value - amounts[0]` to return the difference to `_msgSender()`: [1](#0-0) [2](#0-1) [3](#0-2) 

Compare this to `IntentGatewayV2.placeOrder`, which performs the identical swap but explicitly captures the returned `amounts` array, deducts the actually-spent amount from `msgValue`, and refunds any leftover native token to `msg.sender` at the end of the function: [4](#0-3) 

`EvmHost` has no equivalent refund step after any of its three `swapETHForExactTokens` calls — the function simply proceeds to build/store the request or update fee metadata, silently accepting whatever ETH remains as a "donation" it never emits or accounts for.

### Impact Explanation
Any user who dispatches a POST/GET request or calls `fundRequest` with native token (`msg.value`) greater than what the current AMM price requires to obtain `post.fee`/`get.fee`/`amount` of the fee token will have the residual ETH permanently stuck in `EvmHost`. Since Uniswap V2 exact-output swaps virtually always leave some dust (and the caller must generally overestimate `msg.value` to guard against price movement between quote and execution, since there is no `amountInMax` parameter exposed here — the entire `msg.value` is passed as the implicit maximum), this loss occurs on essentially every native-token-funded dispatch, `dispatch(GET)`, or `fundRequest` call. This is directly reachable by any unprivileged account dispatching an ISMP request through `EvmHost`, matching the "medium, recurring rounding/slippage loss that compounds over time" characterization in the referenced Cork Protocol finding. Funds are permanently frozen with no path to recovery since `EvmHost` has no sweep/withdraw function for stray ETH tied to this flow.

### Likelihood Explanation
High likelihood: this is not a rare edge case but the expected outcome of every native-fee-funded call, since `swapETHForExactTokens` almost always leaves unspent ETH when `msg.value` exceeds the exact amount needed, and no caller can predict the exact spot price at execution time. The `IntentGatewayV2` contract in the same codebase demonstrates the team is aware of this exact class of bug and has already fixed it there, but the fix was not applied to `EvmHost`.

### Recommendation
Capture the return value of each `swapETHForExactTokens` call in `EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()`, and refund `msg.value - amounts[0]` back to `_msgSender()` (mirroring the pattern already implemented in `IntentGatewayV2.placeOrder`, lines 383–397).

### Proof of Concept
1. User calls `EvmHost.dispatch(DispatchPost)` with `post.fee = X` and `msg.value = Y` where `Y` is intentionally (or unavoidably, due to price movement) greater than the ETH actually required to buy `X` fee tokens.
2. `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: Y}(X, path, address(this), block.timestamp)` executes, spending `amounts[0] < Y` ETH and refunding `Y - amounts[0]` ETH to `EvmHost` (the router's caller).
3. `EvmHost` never reads `amounts[0]` nor forwards the refunded ETH back to the user; the request is dispatched and the function returns.
4. The `Y - amounts[0]` ETH remains permanently trapped in `EvmHost`'s balance with no accounting entry and no withdrawal mechanism for the original payer, repeating on every such call.
