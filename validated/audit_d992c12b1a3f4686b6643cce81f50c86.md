### Title
Permissionless risk restamp forces a victim's stored LTV down and gates their withdrawals - (File: contracts/controller/src/risk/params.rs)

### Summary
Each supply position stores its own LTV/LT/bonus/fee snapshot copied at creation, and borrows/withdrawals evaluate solvency against the stored values rather than the live listing. The intended protection for existing accounts is that a governance LTV/LT cut only propagates through gated paths. However, `update_account_threshold(caller, has_risks=false, account_ids)` is callable by any authenticated address on any account, and it restamps stored `loan_to_value` to the current listing value unconditionally — with no health-factor gate, because `LtvOnly` scope skips `apply_gated_liquidation_params` entirely (`refresh_supply_risk_params` always writes `position.loan_to_value = effective_config.loan_to_value` at `contracts/controller/src/risk/params.rs:35`). Since withdrawal solvency is evaluated against the lower of stored LTV and stored LT (see `docs/reference/runbooks/liqvid-listing-params.md` §10 and `enforce_post_pool_solvency` in `contracts/controller/src/positions/supply.rs:158`), a stranger can downgrade a victim's collateral factor and make the victim's previously-valid `withdraw` revert with `InsufficientCollateral`, even though the account's health factor (which reads LT, not LTV) is still ≥ 1.

The same downgrade is reachable via an unprivileged dust `supply` into the victim's existing supply market: `merge_supply_leg` calls `refresh_supply_risk_params` with `RiskRefreshScope::FullTuple` (`contracts/controller/src/positions/supply.rs:288-296`), which writes the new LTV unconditionally and only gates the LT/bonus/fee tuple. The test `poc_lt_cut_stays_sticky_when_hf_below_min` (`tests/test-harness/tests/controller/security_audit.rs:489-494`) confirms a third-party top-up restamps the victim's LTV to the cut value (7500 → 5000) even when the LT gate correctly refuses to move.

### Finding Description
- Root cause: in `refresh_supply_risk_params` (`contracts/controller/src/risk/params.rs:25-40`), the LTV write is outside the `favors_liquidator`/`clears_min_hf` gate that protects LT, bonus and fees. The gate exists because a restamp that worsens terms for an indebted account is dangerous; LTV is equally dangerous for the *withdraw* path, because the post-withdraw solvency check uses min(stored LTV, stored LT) as the collateral weight.
- Attack path 1: after any governance `edit_asset_in_spoke` that lowers a listed asset's LTV, call `update_account_threshold(attacker, false, [victim_id])`. `sync_account_thresholds` (`params.rs:149-237`) requires only `require_authorized_caller`, resolves any account id, and writes the lower LTV onto every listed supply position. The `has_risks=false` scope performs no health check at all.
- Attack path 2 (no governance dependency needed for the mechanism, only for a lower LTV): `supply(attacker, victim_id, victim_spoke, [(hub_asset, dust)])` is permissionless for markets the victim already supplies (`require_third_party_existing_supply`, `supply.rs:78-97`), and `merge_supply_leg` restamps LTV on the victim's position.
- Effect: the victim's `withdraw` now recomputes borrowing power with the reduced LTV and reverts `InsufficientCollateral`. The victim's funds are frozen until they repay debt or add collateral — and adding collateral via their own `supply` does not help lift the LTV back, since the listing value is what gets restamped. Note that without the attack the victim could have withdrawn under the grandfathered LTV, because the runbook explicitly documents that "existing positions keep their stamped terms" and refresh paths were meant to be gated.

### Impact Explanation
Temporary freezing of user funds and forced deleveraging. After a routine, timelocked governance risk-parameter reduction (a normal, expected operation — the repo ships a runbook for exactly this), any unprivileged address can selectively force the new, lower LTV onto chosen victim accounts, converting their withdraws into reverts until they reduce debt. This is griefing with real cost to the victim: they must source repayment funds or add collateral to unlock a withdrawal that the protocol's own grandfathering design intended to remain valid. It also enables targeted withdrawal-blocking of a specific large account (e.g., to keep collateral in place for a pending liquidation the attacker wants to run later, or to prevent a victim exiting ahead of a known price move).

### Likelihood Explanation
- Requires a prior governance LTV decrease on a listed asset — a routine risk operation, explicitly documented in `docs/reference/runbooks/liqvid-listing-params.md`.
- Once such a cut is live, the attack is a single permissionless call with no capital requirement (the `update_account_threshold` path) or dust cost (the `supply` path).
- The code actively confirms the behavior: `test_update_account_threshold_safe` shows the ungated LTV propagation, and `poc_lt_cut_stays_sticky_when_hf_below_min` shows a third-party `supply_to` restamping the victim's LTV. No prerequisites on victim health: HF uses LT and stays ≥ 1 even when the LTV cut blocks withdrawal.
- Severity is bounded: it is not permanent freezing (the victim can repay or withdraw partially within the new limit) and it cannot push the account into liquidation by itself, so Medium rather than High.

### Recommendation
Apply the same `favors_liquidator`-style asymmetry to LTV: only restamp `loan_to_value` downward for an indebted account when the resulting borrow-limit check still passes (i.e., run `clears_min_hf`-equivalent using min(new_LTV, stored LT), or simply never decrease stored LTV on the ungated/`LtvOnly` and third-party-supply paths for accounts with debt). At minimum, restrict `update_account_threshold` and the `merge_supply_leg` restamp so a non-owner/non-delegate caller can never lower another account's effective collateral weight below what its current debt requires.

### Proof of Concept
Extend the existing test shape in `tests/test-harness/tests/controller/security_audit.rs` / `keeper.rs`:

```rust
#[test]
fn poc_third_party_ltv_restamp_freezes_victim_withdraw() {
    let mut t = LendingTest::new().standard_two_asset_dust_disabled();

    // Victim supplies USDC and borrows ETH near its stamped LTV limit.
    t.supply(ALICE, "USDC", 10_000.0);
    t.borrow(ALICE, "ETH", 3.0);
    let victim = t.resolve_account_id(ALICE);

    // Governance (or owner in harness) cuts the USDC listing LTV.
    t.edit_asset_config("USDC", |c| c.loan_to_value = 3_000);

    // Precondition: victim can still withdraw under the grandfathered stamp.
    let ok = t.try_withdraw(ALICE, "USDC", 1_000.0);
    assert!(ok.is_ok(), "withdraw must succeed while the old LTV stamp holds");

    // Re-supply to restore the position, then the attack: a stranger restamps.
    t.supply(ALICE, "USDC", 1_000.0);
    // Path A: permissionless keeper call, has_risks = false -> LtvOnly, no HF gate.
    t.update_account_threshold_by(BOB, false, &[victim]);
    // (Equivalent path B: `t.try_supply_to_account(BOB, ALICE, "USDC", dust)`
    //  reaches the same ungated LTV write via merge_supply_leg.)

    // The victim's withdraw now reverts even though HF (LT-based) is healthy.
    let blocked = t.try_withdraw(ALICE, "USDC", 1_000.0);
    assert_contract_error(blocked, errors::INSUFFICIENT_COLLATERAL);
    t.assert_healthy(ALICE); // LT stamp untouched -> still not liquidatable
}
```
