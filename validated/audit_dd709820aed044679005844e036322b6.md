The documentation explicitly states `data.shop` ("The shop domain of the webhook") is a trusted field returned after `Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0) [2](#0-1) , yet the HMAC computation only ever covers the raw body, never the `shop-domain` header that becomes `data.shop`.

### Title
Webhook `shop` identity is not covered by the HMAC that gates webhook processing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated once `Utils::HmacValidator.validate(request)` passes, and then hands the caller `WebhookMetadata` containing `request.shop`, documented as an already-verified field. But the HMAC signable string is the raw body only; the `shop` value comes from the `X-Shopify-Shop-Domain` header, which the HMAC never touches.

### Finding Description
`Registry.process` gates on the HMAC check and then immediately trusts `request.shop` for the handler payload: [3](#0-2) 

`Request#hmac` decodes the `hmac-sha256` header, and `to_signable_string` — the data actually verified against `Context.api_secret_key` — is defined as the raw body alone: [4](#0-3) 

`HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string`: [5](#0-4) 

So the binding the gem actually proves is: `HMAC(body, api_secret_key) == received_hmac`. The binding the documentation implies and the binding the handler receives is: `shop == the tenant whose data this body belongs to`. These are not the same equality — `shop` is read from an unauthenticated header and is never mixed into the signable string, so any body/HMAC pair valid for one shop is equally "valid" if replayed with a different `shop-domain` header value.

Compare this to `ShopifyAPI::Auth::Oauth::AuthQuery`, where `shop` *is* part of `to_signable_string` and thus cryptographically bound to the HMAC: [6](#0-5) 

There is no analogous binding for webhooks.

### Impact Explanation
An unprivileged entity that is itself a legitimate merchant/installer of the app receives correctly-HMAC-signed webhook deliveries for its own shop. Because the header carrying the shop identity sits outside the signed payload, that same person can resend the identical body and HMAC to the app's webhook endpoint while substituting a different `X-Shopify-Shop-Domain` value. `Registry.process` will still report the HMAC as valid (the body it verifies is untouched) and will hand the handler `WebhookMetadata` labeling the data as belonging to the spoofed shop. Any host application that uses `data.shop` from a validated webhook to key its per-tenant datastore — exactly the pattern the gem's own documentation demonstrates (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`) — will attribute another merchant's data lineage or write path to the wrong tenant, i.e., cross-tenant data confusion, using only inputs the gem itself validated as authentic.

### Likelihood Explanation
The gem's own webhook documentation (`docs/usage/webhooks.md`) presents `data.shop` as a verified field of an authenticated request and shows a direct, unfiltered downstream use (`shop_domain: data.shop`), so most consumers built against the documented API will trust it without a second, independent shop check. The only prerequisite is possession of one real signed webhook body (trivially available to any merchant that installs the app), not the app's `client_secret` or any access token.

### Recommendation
Include the shop identity (and other identity-bearing headers such as `topic`/`webhook_id`) in the HMAC signable string, or otherwise cryptographically bind the shop-domain header to the payload before exposing `WebhookMetadata#shop`, so `Registry.process` cannot report a request as "verified" while allowing the shop label to be swapped independently of the signed body.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com`: body `B`, header `x-shopify-hmac-sha256: H` where `H = HMAC_SHA256(api_secret_key, B)`.
2. Attacker (an installer of the app for `shop-a`) resends the exact same `B` and `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "shop-b.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(api_secret_key, B)` and matches `H` — validation passes.
5. The handler receives `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: parsed(B), ...)`, i.e., data for `shop-a` is delivered to the app labeled as belonging to `shop-b`, despite `Registry.process` having reported the webhook as verified.

        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
