### Title
Unauthenticated Emporium calls via the zero-token Min-circuit path drain any standing ERC20 approval - (File: `contracts/CircomDataBuilder.sol`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only proves `message == Poseidon(messageSeed)` — a secret the attacker picks themselves, with no binding to any UTXO, root, nullifier, or ERC20 list. Combined with `EmporiumUpgradeable.runAction`'s `signerAddress == address(0)` branch, which skips the EIP-712 signature check in `verifyWallet` entirely, an attacker can submit an `EmporiumStack` whose `ops` execute an arbitrary `call` from Emporium's own address (e.g. `token.transferFrom(victim, attacker, amount)`), while the balance-accounting loop that is supposed to catch any Emporium balance change iterates zero times because `erc20TokenAddresses` is empty.

### Finding Description
The invariant that should hold is: **assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter`**. This is broken as follows.

1. `formInputForCircom` selects the minimal circuit whenever the emporium action id is used and the token array is empty: [1](#0-0) 
`formInputEmporiumMin` only emits `emporiumMessage`, `timeStamp`, `calldataHash` — matching `MainEVMCircuitMin.circom`, which only proves `message <== Poseidon(1)([messageSeed])`: [2](#0-1) 
`messageSeed` is chosen by the attacker; nothing ties this proof to `rootHashHinkal`, nullifiers, amountChanges, or any owned UTXO. `getHashedCalldata`/`calldataHash` is just a public keccak256 of caller-supplied fields, trivially reproducible without any secret.

2. `HinkalHelper.dimensionsCheck` and `checkOnchainCreation` place no additional constraint here — with `dimensions.tokenNumber == 0` all the length checks trivially pass on empty arrays: [3](#0-2) 

3. `Hinkal.transact` → `_externalTransact` builds `deltaAmountChanges` of length 0 (matching the empty `erc20TokenAddresses`) and calls `EmporiumUpgradeable.runAction`: [4](#0-3) 

4. Inside `runAction`, `balancesBefore`/`balancesAfter` are computed only over `circomData.erc20TokenAddresses`, which is empty — so this accounting tracks *nothing*: [5](#0-4) 
`verifyWallet` skips signature verification entirely when `stack.signerAddress == address(0)`: [6](#0-5) 
Then each `EmporiumOperation` is executed as a raw, unrestricted external call from Emporium's own address (only `callHinkalWallet`/`doSendToRelay` selectors are blocked): [7](#0-6) 

5. `payRelayFees` also iterates the empty token array and does nothing; setting `feeStructure.flatFee == 0` skips the only other check (`"Gas Token in Emporium is not found"`), matching the "zero effective fee" condition in the question: [8](#0-7) 

**Exploit**: attacker picks any `messageSeed`, generates a real proof for `MainEVMCircuitMin`, sets `erc20TokenAddresses = []`, `feeStructure.flatFee = 0`, and `externalActionMetadata = abi.encode(EmporiumStack{signerAddress: address(0), ops: [{endpoint: victimToken, invokeWallet: false, value: 0, callData: transferFrom(victim, attacker, amount)}], ...})`. If `victimToken` has ever granted Emporium a standing/leftover ERC20 allowance from any user (a very ordinary state resulting from normal Emporium swap/deposit ops that approve more than they consume), the attacker's call executes `token.transferFrom(victim, attacker, amount)` as Emporium, with zero balance accounting, zero UTXOs, zero slippage checks, and zero nullifiers spent. The stolen funds go directly to the attacker's wallet, bypassing every Hinkal/Emporium accounting guard.

None of `performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, `verifyProof`, `rootHashExists`, or the balance/slippage `require`s in `Hinkal.transact` catch this because they all operate over `circomData.erc20TokenAddresses`, which the attacker deliberately sets to empty, and the Min circuit intentionally has no signals to constrain the ops.

### Impact Explanation
Direct theft of another user's (or the protocol's) funds via any standing ERC20 approval ever granted to the Emporium contract, executed by a completely unprivileged, unauthenticated attacker. This satisfies the Critical severity category "direct theft of shielded or in-flight user funds" — any leftover allowance to Emporium (a plausible, ordinary residue of prior legitimate Emporium interactions such as approve-and-swap patterns) becomes fully drainable by anyone. The attack is repeatable for every distinct standing approval and every fresh `emporiumMessage` (each message can only be used once via `usedMessages`, but the attacker can generate unlimited fresh seeds).

### Likelihood Explanation
- No privileged role, relay whitelisting, or signature is required (`relay == address(0)` skips `relayerIsValid`; `signerAddress == address(0)` skips `verifyWallet`'s ECDSA check).
- The attacker only needs to compute a Poseidon hash and produce a Groth16 proof for the already-deployed `MainEVMCircuitMin` circuit — no special privileges, no valid UTXO, no deposit needed.
- The only precondition is the existence of some standing/leftover ERC20 allowance granted to the Emporium contract, which is a normal byproduct of typical approve-based swap/deposit flows using Emporium ops.
- Cost to the attacker is only gas plus proof generation; the payoff can be the full allowance amount.

### Recommendation
- Never allow `formInputForCircom`/`formInputEmporiumMin` to authorize execution of `EmporiumOperation.ops` that touch tokens outside the proven/circuit-checked set; the Min path should not be permitted to trigger arbitrary `call`s at all, or must cryptographically bind `ops`/`endpoint`/`callData` into the circuit's public inputs.
- Do not allow `verifyWallet` to fully skip authorization when `signerAddress == address(0)`; require that any executed `ops` be constrained by data proven in the ZK proof (e.g., bind `_hashEmporiumOps(stack.ops)` into `calldataHash`/circuit public inputs even for the Min path).
- Restrict `EmporiumOperation.endpoint`/`callData` in the stateless branch to a safe allow-list, or forbid calling arbitrary `transferFrom`-capable functions on tokens Emporium wasn't explicitly authorized to move in that transaction.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, register a verifier for `buildVerifierId({tokenNumber:0, nullifierAmount:0, outputAmount:0}, HINKAL_EMPORIUM_ACTION_ID)` pointing at a real `MainEVMCircuitMin` verifier, register Emporium in `externalActionMap[HINKAL_EMPORIUM_ACTION_ID]`.
2. Deploy an ERC20 mock, have `victim` call `token.approve(emporium, largeAmount)` (simulating leftover allowance from a prior legitimate Emporium op).
3. As `attacker` (unprivileged EOA), generate `messageSeed`, compute `message = Poseidon(messageSeed)`, generate a valid Groth16 proof for `MainEVMCircuitMin` with public inputs `(timeStamp, calldataHash)` and output `message`.
4. Build `CircomData` with `erc20TokenAddresses=[]`, `amountChanges=[]`, `inputNullifiers=[]`, `outCommitments=[]`, `onChainCreation=[]`, `slippageValues=[]`, `feeStructure.flatFee=0`, `relay=address(0)`, `externalActionData = {externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalAddress: emporium, externalActionMetadata: abi.encode(EmporiumStack{signerAddress: address(0), ops:[{endpoint: token, invokeWallet:false, value:0, callData: abi.encodeCall(IERC20.transferFrom,(victim, attacker, largeAmount))}], maxFee:0, deadline: block.timestamp+1})}`, `emporiumMessage = message`.
5. Call `Hinkal.transact(a,b,c, dimensions, circomData)` from `attacker`.
6. Assert: `token.balanceOf(attacker)` increases by `largeAmount`, `token.balanceOf(victim)` decreases by `largeAmount`, while `balancesBefore == balancesAfter == []` inside `runAction` (i.e., the accounting equality is violated: real assets moved but zero assets accounted for).

    function payRelayFees(
        CircomData calldata circomData,
        address signerAddress,
        int256[] calldata deltaAmountChanges
    ) internal {
        FeeStructure calldata feeStructure = circomData.feeStructure;

        bool foundToken = false;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            // tokens deposited into Emporium are not charged
            if (deltaAmountChanges[i] >= 0) {
                continue;
            }

            address erc20TokenAddress = circomData.erc20TokenAddresses[i];
            bool isFeeToken = erc20TokenAddress == feeStructure.feeToken;

            if (isFeeToken) {
                foundToken = true;
            }

            uint256 relayFee = 0;
            uint256 flatFee = isFeeToken ? feeStructure.flatFee : 0;

            if (signerAddress == address(0)) {
                uint256 sumAbs = uint256(-deltaAmountChanges[i]);

                EmporiumStorageVars storage $ = _getEmporiumStorage();
                relayFee = $._hinkalHelper.calculateRelayFee(
                    sumAbs,
                    flatFee,
                    feeStructure.variableRate
                );
            } else {
                relayFee = flatFee;
            }

            payRelay(
                circomData.relay,
                signerAddress,
                relayFee,
                erc20TokenAddress
            );
        }

        if (!foundToken && feeStructure.flatFee != 0) {
            require(
                signerAddress != address(0),
                "Gas Token in Emporium is not found"
            );

            payRelay(
                circomData.relay,
                signerAddress,
                feeStructure.flatFee,
                feeStructure.feeToken
            );
        }
