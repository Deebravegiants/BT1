### Title
Webhook shop/topic/webhook-id headers are trusted by handlers without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the `hmac` field via `Utils::HmacValidator.validate(request)`, which only signs the raw request body [1](#0-0) [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from HTTP headers and are never included in the HMAC-signed string [3](#0-2) . Documentation explicitly tells app developers that `Registry.process` "will verify the request did indeed come from Shopify" before invoking the handler with these fields, implying they are authenticated.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) . `HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over that signable string and compares it against the `hmac` header using `OpenSSL.secure_compare` [4](#0-3) . This proves only that the *body bytes* were signed with the app's `api_secret_key`; it says nothing about the `shop`, `topic`, or `webhook_id` headers, which are read straight from `@headers` with no cryptographic binding [5](#0-4) .

`Registry.process` uses exactly this unauthenticated `shop` value to build the `WebhookMetadata` object passed to the app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [2](#0-1) . The library's own documentation tells integrators that `Registry.process` "will verify the request did indeed come from Shopify," and lists `shop` among the trusted fields handed to their handler, without noting that the `shop` header is unauthenticated [6](#0-5) [7](#0-6) .

The equality that should hold but does not: `shop_that_signed_the_HMAC == shop_delivered_to_handler`. In reality the code only proves `HMAC(body, api_secret_key) == received_hmac`; it never proves the `shop-domain` header is the one Shopify actually associated with that signed body. Since the HMAC is a keyed hash over the body only, capturing one legitimate webhook body+HMAC pair (e.g., from webhooks delivered to the attacker's own shop, which any merchant/dev of an installed app can trivially obtain) lets the pair be replayed to the same endpoint with an arbitrary `shop-domain` header substituted, since nothing binds the header to the signature.

### Impact Explanation
If a multi-tenant app's `WebhookHandler#handle` implementation trusts `data.shop` to select which merchant/tenant record to update (a very common pattern per the docs' own example, `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), an attacker who has legitimately received at least one webhook for their own store (any developer/merchant with the app installed) can replay that exact body+HMAC to the app's public webhook endpoint while spoofing the `x-shopify-shop-domain` header to point at a victim shop. This causes cross-tenant data write/confusion inside the app using another merchant's identity — this satisfies the "cross-tenant access" Critical impact category, because the app's own webhook-processing boundary (its equivalent of a tenant identity check) is bypassed using only a legitimately-obtained webhook and no possession of `api_secret_key` or any victim credential.

### Likelihood Explanation
Likelihood is bounded by the requirement that the attacker must have legitimately received (or otherwise obtained) at least one valid `(raw_body, hmac)` pair for some shop — which is trivial for any developer who installs the app on their own development store — and by the fact that many apps do rely on the delivered `shop` field to select the tenant, exactly as illustrated in this gem's own documentation example.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the signed material verified by `HmacValidator`, or otherwise cross-validate the header-derived `shop` against a known, previously-authenticated mapping (e.g., the webhook subscription id returned during registration) before handing it to the app's handler. At minimum, update `docs/usage/webhooks.md` and `WebhookMetadata` documentation to make explicit that only the request body is authenticated by `Registry.process`, and that `data.shop`/`data.topic`/`data.webhook_id` must not be trusted for tenant-selection without additional verification (e.g., matching against the shop's registered webhook_id).

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; let Shopify deliver a legitimate webhook (e.g. `orders/create`) to the app's endpoint. Capture the raw body `B` and the valid `x-shopify-hmac-sha256` header `H` (computed by Shopify over `B` using the app's `api_secret_key`).
2. Replay an HTTP POST to the same webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` passes because it only hashes `B` [1](#0-0) ; `Registry.process` invokes the app handler with `data.shop == "victim-shop.myshopify.com"` even though the payload actually belongs to `attacker.myshopify.com` [2](#0-1) , causing the app to process attacker-controlled order data under the victim shop's tenant context.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
