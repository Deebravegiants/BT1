### Title
Webhook `shop-domain` Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body [4](#0-3) . The `shop` value that the application later attributes the webhook data to is taken from the `x-shopify-shop-domain` / `shopify-shop-domain` header and is never included in the HMAC-signed payload [5](#0-4) .

### Finding Description
The identity binding the gem is supposed to enforce is: `shop attributed to webhook == shop the HMAC-signed bytes originated from`. Because `to_signable_string` returns only `@raw_body` [6](#0-5) , and `hmac` is computed by decoding the `hmac-sha256` header [7](#0-6) , the `shop-domain` header is completely outside the scope of what `Utils::HmacValidator.validate` checks [8](#0-7) . Shopify signs webhook bodies using the app's single, shop-independent `client_secret` (`Context.api_secret_key`), which is identical for every shop that has installed the app [9](#0-8) . Consequently, a party that operates (or has installed) the app on any one shop can capture a legitimately-signed `(raw_body, hmac)` pair delivered to their own shop, then replay that exact body/HMAC to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `Registry.process` will validate the HMAC successfully (it never inspected `shop`) and hand `request.shop` — now the victim's domain — straight to the registered handler as authoritative tenant identity [10](#0-9) .

### Impact Explanation
Any host application that uses `request.shop`/`WebhookMetadata#shop` (the value this gem hands back after "verifying" the webhook) to look up the tenant, update per-shop records, or gate mandatory GDPR webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) will process attacker-supplied data under a victim shop's identity. This is a cross-tenant data confusion caused entirely by this gem's verification routine only covering the body and not the tenant-identifying header it hands back as trusted, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to control/install the app on at least one shop (a normal, unprivileged action any merchant can take), capture one webhook delivery for their own shop, and replay it with a modified header to the same public webhook endpoint. No access to the app's `client_secret`, access tokens, or any other privileged credential is required — the attacker only needs the ability to receive their own webhooks, which is trivial once they add the app to a shop they control.

### Recommendation
Bind `shop` (and ideally `topic`/`api_version`/`webhook_id`) into the value that is HMAC-verified, e.g., include the `shop-domain` header in `to_signable_string` (or verify it out-of-band against a separately maintained shop→session mapping) inside `lib/shopify_api/webhooks/request.rb`, rather than trusting the raw header value once only the body's signature has been checked.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Shopify delivers a legitimate webhook to the app with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`, and some JSON body.
3. Attacker captures the raw body and HMAC header value (these are visible to them since they control the receiving shop/server, or can be inferred through side channels the app exposes).
4. Attacker crafts a new HTTP POST to the app's webhook endpoint with the identical `raw_body`/`x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses the forged headers without error (`raw_body` and `hmac` header format checks only) [11](#0-10) .
6. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes the HMAC over `raw_body` [4](#0-3) .
7. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` [12](#0-11) , and the host application processes attacker-controlled data as if it originated from the victim shop.
