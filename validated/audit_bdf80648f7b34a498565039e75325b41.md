Confirmed. The docs explicitly say `Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0)  and the example handler trusts `data.shop` to route the payload to the correct tenant [2](#0-1) , but the `shop` value is never covered by the HMAC.

### Title
Webhook `shop` identity is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which signs/verifies only the raw request body [3](#0-2) . The `shop` attribute that downstream handlers use to attribute the event to a tenant is read directly from an unauthenticated HTTP header and is never included in the signed content.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` only [4](#0-3) , while `Webhooks::Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to that header value [5](#0-4) . `Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `to_signable_string` (the body) and compares it to the `hmac` header [6](#0-5) . Since the shop header is excluded from the signed string, the HMAC check passes for any `shop-domain` header value paired with a validly-signed body — the binding "shop authenticated == shop acted upon" is broken: the gem authenticates the *body*, but `Registry.process` acts on the *header-derived* `shop` when constructing `WebhookMetadata` and invoking the handler [7](#0-6) .

An unprivileged attacker who installs the app on their own development/trial store receives legitimately-signed webhook deliveries for their own shop (each with a valid `hmac-sha256` header for that exact body). By replaying that same body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header (e.g. a victim's `myshopify.com` domain), the request still passes `HmacValidator.validate`, and the handler receives `WebhookMetadata` claiming the event belongs to the victim shop [8](#0-7) .

### Impact Explanation
This breaks the tenant boundary the gem is documented to enforce: "This will verify the request did indeed come from Shopify" for the specific shop implied by the payload [1](#0-0) . Any host application that trusts `data.shop` (as the gem's own documented handler example does — `perform_later(topic: data.topic, shop_domain: data.shop, ...)` [2](#0-1) ) to select which tenant's records to create/update/delete will process attacker-controlled data under a victim shop's identity — a cross-tenant data injection, satisfying the Critical "cross-tenant access" impact bar.

### Likelihood Explanation
Reachable by any unprivileged actor: obtaining a validly HMAC-signed webhook body only requires installing the app on one's own shop (a normal, unprivileged action), no `api_secret_key`, access token, or victim credentials are needed. The attack requires only calling the app's public webhook endpoint with a modified header, which is entirely within reach of an internet-based attacker who knows/guesses the app's webhook URL.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed content used for verification, or otherwise cryptographically bind the `shop-domain` header to the payload before trusting it — e.g., cross-check `request.shop` against a known/expected shop for the delivery, or require the host application to validate `shop` against its own registered shops using a channel that Shopify itself authenticates (such as looking up the webhook subscription id rather than trusting the header). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for authorization decisions without additional verification.

### Proof of Concept
1. Install the target app on an attacker-controlled development store `attacker.myshopify.com`; trigger any webhook topic the app subscribes to (e.g. `orders/create`) so Shopify delivers a request with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and some `raw_body`.
2. Capture `raw_body` and the valid `hmac-sha256` value.
3. Replay an HTTP POST to the app's webhook endpoint with the same `raw_body` and `hmac-sha256` header, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [3](#0-2) , which only checks the body HMAC and succeeds; the handler is invoked with `WebhookMetadata(shop: "victim.myshopify.com", ...)`, causing the host app to process attacker-supplied data as if it originated from the victim's shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
