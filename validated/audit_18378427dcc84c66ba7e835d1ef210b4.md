### Title
POA Bridge withdrawal status matched only by `assetId`, causing cross‑withdrawal status/hash misreport in same‑token batches - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain status of a specific withdrawal by matching PoA Bridge API results only on `assetId`, ignoring the withdrawal's index/amount/destination. When a single NEAR transaction contains more than one withdrawal intent for the same token (a supported and tested batch pattern), the SDK can report the wrong withdrawal's status and destination transaction hash for a given `WithdrawalIdentifier`.

### Finding Description
`describeWithdrawal` fetches the PoA bridge's unsorted withdrawal list and calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, explicitly matching by `assetId` alone rather than by `index`: [1](#0-0) 

The equality this code is supposed to preserve is: *"the status/txHash returned for withdrawal `wid.index` corresponds to the on-chain outcome of that specific withdrawal intent."* Because the lookup key is only `assetId`, this equality holds only when at most one withdrawal in the batch uses that `assetId`. The SDK's own architecture explicitly supports batches of multiple withdrawal identifiers sharing the same parameters/asset in one NEAR transaction — `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` accept an array of `withdrawalParams` and iterate per `index`: [2](#0-1) [3](#0-2) 

If two (or more) withdrawal intents in the same NEAR transaction target the same `assetId` (e.g., the same token withdrawn to two different destination addresses, or split into two amounts), `describeWithdrawal(index=0)` and `describeWithdrawal(index=1)` both call `findMatchingWithdrawal` with the identical `assetId`, and (per the code's own comment "Response list is unsorted, so we match by assetId instead of index") return the first PoA record found for that asset — with no secondary check against amount or destination address. The existing test at `poa-bridge.test.ts:1054` only demonstrates that matching is index-independent for *distinct* asset IDs; it does not cover (and the implementation does not guard against) two same-asset withdrawals in one batch.

### Impact Explanation
This breaks the "status reported == actual on-chain outcome" equality for a specific `WithdrawalIdentifier.index`. In a same-token batch:
- A pending/failed withdrawal for index 1 could be reported as `"completed"` with a `txHash` that actually belongs to a different withdrawal (index 0) with a different destination address/amount.
- Downstream consumers relying on `sdk.waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` (e.g., an integrator that credits a user or releases custody once a withdrawal is confirmed) could mark the wrong withdrawal as completed and release funds or mark an obligation as fulfilled based on a transaction hash unrelated to the actual withdrawal being tracked — a status/hash misreport that can cause an integrator to credit or clear an obligation incorrectly. This matches the "High" impact category in the rules: *"a status or hash misreport making an integrator credit or refund twice."*

### Likelihood Explanation
No malicious actor is required — an ordinary user or integrator batching two withdrawals of the same token (a legitimate, tested usage pattern per `sdk.createWithdrawalCompletionPromises.test.ts`) into a single NEAR transaction reaches this code path. The only requirement is that PoA Bridge's withdrawal list contains ≥2 entries sharing `defuse_asset_identifier`, which happens naturally whenever the same token is withdrawn more than once in the same transaction.

### Recommendation
Match withdrawals in `findMatchingWithdrawal` using a compound key: `assetId` plus `destinationAddress` (and ideally `amount`), or use the withdrawal's positional/near-side identifying data if the PoA API exposes it, instead of relying on `assetId` alone.

### Proof of Concept
1. Construct a NEAR transaction with two `ft_withdraw` intents for the same `assetId` (e.g., `nep141:eth.omft.near`) but different `destinationAddress` values, submitted via the SDK's batch withdrawal APIs (as exercised in `sdk.createWithdrawalCompletionPromises.test.ts`).
2. Call `sdk.waitForWithdrawalCompletion` with the array of both `withdrawalParams` and the shared `intentTx`.
3. Mock (or observe in production) the PoA Bridge `getWithdrawalStatus` response containing two withdrawal records for that same `assetId`, one `"COMPLETED"` and one `"PENDING"`/different destination.
4. Observe that `describeWithdrawal` for `index=0` and `index=1` both resolve based on whichever record `findMatchingWithdrawal` finds first by `assetId`, independent of which destination/amount corresponds to which index — i.e., the reported `txHash`/status for one index can belong to the other withdrawal.

Note: I could not fully inspect the internal implementation of `findMatchingWithdrawal` (its exact matching predicate) due to tool-call limits reached before retrieving its full body; the call site in `poa-bridge.ts` confirms only `assetId` is passed as the matching criterion, but I was unable to verify definitively whether any additional implicit disambiguation exists inside `findMatchingWithdrawal` itself. This should be verified directly in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` (function `findMatchingWithdrawal`) before remediation.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
