Audit Report

## Title
`assigned_slots::TemporarySlots`/`TemporarySlotCount` desync via `paras_registrar::deregister` on a not-yet-leased temporary slot - (File: polkadot/runtime/common/src/assigned_slots/mod.rs)

## Summary
`assign_temp_parachain_slot` inserts a `TemporarySlots` entry and increments `TemporarySlotCount` unconditionally, but only actually leases the para (via `configure_slot_lease`, which drives `ParaLifecycle` toward `Parachain`) when `SlotLeasePeriodStart::Current` is chosen and the current period's active-slot cap is not yet reached. [1](#0-0)  When neither condition holds, the para's `ParaLifecycle` remains `Parathread`, so `paras_registrar::do_deregister`, which only checks lifecycle, permits the manager to deregister the para while `assigned_slots` still holds a live `TemporarySlots` entry and inflated `TemporarySlotCount`. [2](#0-1) 

## Finding Description
`assign_temp_parachain_slot` builds a `temp_slot` and only calls `Self::configure_slot_lease` — the call that actually turns the para into a lease-holding parachain — under the condition `lease_period_start == SlotLeasePeriodStart::Current && ActiveTemporarySlotCount::<T>::get() < T::MaxTemporarySlotPerLeasePeriod::get()`. [3](#0-2)  Regardless of whether that branch executes, `TemporarySlots::<T>::insert(id, temp_slot)` and `TemporarySlotCount::<T>::mutate(|count| count.saturating_inc())` always run. [4](#0-3) 

Meanwhile, `paras_registrar::do_deregister` gates solely on `paras::Pallet::<T>::lifecycle(id)`, allowing deregistration when the lifecycle is `Parathread` or `None`, with no reference to `assigned_slots` state at all. [2](#0-1)  The `deregister` extrinsic is reachable by the para's manager via `ensure_root_para_or_owner`, which permits a signed origin matching `para_info.manager` (subject only to the para not being locked). [5](#0-4) 

The only place that decrements `TemporarySlots`/`TemporarySlotCount`/`ActiveTemporarySlotCount` is `unassign_parachain_slot`, which is a distinct, `AssignSlotOrigin`-gated call in `assigned_slots` itself — `do_deregister` never invokes it or any equivalent hook. [6](#0-5)  The permanent-slot path is not exploitable this way, since `assign_perm_parachain_slot` unconditionally calls `configure_slot_lease` before inserting into `PermanentSlots`, immediately flipping `ParaLifecycle` away from `Parathread` and causing `do_deregister` to fail with `NotParathread`. [7](#0-6) 

## Impact Explanation
When a temporary slot is assigned with `SlotLeasePeriodStart::Next`, or when the current period's active-slot cap is already saturated, the para stays a `Parathread` while `assigned_slots` bookkeeping already accounts for it as an assigned temporary slot. The manager can then deregister the para through the ordinary, unprivileged `deregister` extrinsic, leaving a stale `TemporarySlots` entry for a nonexistent `ParaId` and an un-decremented `TemporarySlotCount` against the governance-set `MaxTemporarySlots` cap. This permanently strands capacity in the temporary-slot pool and causes `allocate_temporary_slot_leases` to keep considering the orphaned entry, wasting weight for a `ParaId` that no longer exists. The impact is an accounting/resource-management bug limited to the `assigned_slots` pallet's bookkeeping and periodic allocation logic — no funds are stolen and no consensus-critical state is corrupted.

## Likelihood Explanation
The precondition (assignment with `SlotLeasePeriodStart::Next`, or the active-slot cap already reached at assignment time) is a normal governance/root operational choice, not a rare edge case. Once that precondition is set by the `AssignSlotOrigin`, any para manager can trigger the desync deterministically with a single `deregister` call, requiring no special privileges beyond being the para's manager.

## Recommendation
`paras_registrar::do_deregister` should reject deregistration of a para that still has an `assigned_slots::TemporarySlots` or `PermanentSlots` entry, or `assigned_slots` should expose a cleanup routine (mirroring `unassign_parachain_slot`'s storage mutations) that `do_deregister` invokes to remove/decrement the corresponding entries when a para with an assigned slot is deregistered.

## Proof of Concept
1. Register a para as an on-demand parathread via the registrar.
2. Call `AssignedSlots::assign_temp_parachain_slot(RuntimeOrigin::root(), id, SlotLeasePeriodStart::Next)`; verify `TemporarySlots::<Test>::get(id).is_some()`, `TemporarySlotCount::<Test>::get() == 1`, and the para's lifecycle is still `Parathread` (lease not yet active).
3. As the para's signed manager, call `paras_registrar::Pallet::deregister(RuntimeOrigin::signed(manager), id)`; observe it returns `Ok(())`.
4. Verify `paras::Pallet::<Test>::lifecycle(id).is_none()` (para fully deregistered).
5. Verify the desync: `TemporarySlots::<Test>::get(id).is_some()` (stale entry) and `TemporarySlotCount::<Test>::get() == 1` (not decremented).

	/// Deregister a Para Id, freeing all data returning any deposit.
	fn do_deregister(id: ParaId) -> DispatchResult {
		match paras::Pallet::<T>::lifecycle(id) {
			// Para must be a parathread (on-demand parachain), or not exist at all.
			Some(ParaLifecycle::Parathread) | None => {},
			_ => return Err(Error::<T>::NotParathread.into()),
		}
		polkadot_runtime_parachains::schedule_para_cleanup::<T>(id)
			.map_err(|_| Error::<T>::CannotDeregister)?;

		if let Some(info) = Paras::<T>::take(&id) {
			<T as Config>::Currency::unreserve(&info.manager, info.deposit);
		}

		PendingSwap::<T>::remove(id);
		Self::deposit_event(Event::<T>::Deregistered { para_id: id });
		Ok(())
	}
