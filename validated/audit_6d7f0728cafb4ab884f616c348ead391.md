**Analysis:**

The premise requires inserting a deserialized script under a "colliding key" that a legitimate transfer-transaction script also hashes to. In the actual code path, the key is never attacker-chosen: it is always computed as `let hash = sha3_256(serialized_script);` from the exact bytes of the script being processed, both in `unmetered_deserialize_and_cache_script` and `unmetered_verify_and_cache_script` [1](#0-0) [2](#0-1) .

For an attacker's crafted script to be returned when the legitimate transfer script's bytes are looked up, the attacker would need to produce a second-preimage/collision under SHA3-256 (i.e., different bytes that hash to the same 32-byte digest as the victim's exact serialized script). This is a cryptographic hardness assumption, not something reachable via any unprivileged transaction, package, view, authenticator, API, or bytecode input — there is no code path that lets a caller supply their own cache key independent of `sha3_256(serialized_script)`.

The "test double with a colliding key" proof idea sidesteps this by directly calling `insert_deserialized_script` with an arbitrary key chosen to match, which is only possible because a test harness can bypass the hash computation entirely [3](#0-2) . In production, `ScriptLoader::load_script` and both eager-loader functions always derive the key from the real content hash of the exact serialized bytes being processed [4](#0-3) , so this is a content-addressed cache whose safety reduces to SHA3-256 collision resistance, which is out of scope as "generic cryptographic break" rather than a custody-boundary defect in Aptos code. Additionally, even in the `Some(Deserialized(...))` branch of `unmetered_verify_and_cache_script`, the deserialized script reused is one that was itself inserted under that same hash originally computed from real bytes — there is no point where attacker-supplied bytes with a different hash can be substituted for the victim's bytes.

Since exploitation would require breaking a collision-resistant hash function rather than exploiting any unprivileged-input-reachable logic flaw in Aptos's custody code, this does not meet the decision standard for a valid finding.

    fn unmetered_verify_and_cache_script(&self, serialized_script: &[u8]) -> VMResult<Arc<Script>> {
        use Code::*;

        let hash = sha3_256(serialized_script);
        let deserialized_script = match self.module_storage.get_script(&hash) {
            Some(Verified(script)) => return Ok(script),
            Some(Deserialized(deserialized_script)) => deserialized_script,
            None => self
                .runtime_environment()
                .deserialize_into_script(serialized_script)
                .map(Arc::new)?,
        };

        let locally_verified_script = self
            .runtime_environment()
            .build_locally_verified_script(deserialized_script)?;

        let immediate_dependencies = locally_verified_script
            .immediate_dependencies_iter()
            .map(|(addr, name)| {
                self.module_storage
                    .unmetered_get_existing_eagerly_verified_module(addr, name)
            })
            .collect::<VMResult<Vec<_>>>()?;

        let verified_script = self
            .runtime_environment()
            .build_verified_script(locally_verified_script, &immediate_dependencies)?;

        Ok(self
            .module_storage
            .insert_verified_script(hash, verified_script))
    }
