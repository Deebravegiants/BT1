## Title
Webhook shop-domain identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic for a given shop as long as `Utils::HmacValidator.validate(request)` passes, and then dispatches the handler using `request.shop`, which is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header [1](#0-0) . However `ShopifyAPI::Webhooks::Request#to_signable_string` — the value that is actually HMAC-verified — only returns the raw body, never the shop, topic, webhook_id or api_version headers [2](#0-1) . The HMAC validator itself only ever signs/verifies `verifiable_query.to_signable_string` [3](#0-2) .

### Finding Description
The binding the code should enforce is: `shop used for tenant dispatch == shop that produced the HMAC-signed payload`. In reality, the gem only checks `HMAC(raw_body, api_secret_key) == received_hmac` [4](#0-3) , while the `shop`, `topic`, `api_version`, and `webhook_id` fields that `Registry.process` passes on to the app's handler as `WebhookMetadata` are taken verbatim, unauthenticated, from request headers [5](#0-4) [1](#0-0) .

Because `api_secret_key` is a single app-wide shared secret (not per-shop), any merchant who has installed the app can obtain a legitimately-signed webhook (valid `hmac` + `raw_body` pair) for their own shop. That merchant can then replay the same body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop. `HmacValidator.validate` will still pass (it never inspects the shop header), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-controlled) body belongs to the victim shop [6](#0-5) .

The docs for this exact API explicitly claim this call "will verify the request did indeed come from Shopify," implying full authenticity of shop attribution, which is not actually enforced [7](#0-6) .

### Impact Explanation
Any downstream app logic that trusts `data.shop` from `WebhookMetadata` to select per-tenant state, look up a stored access token, or write into per-tenant records can be tricked into acting on a victim shop's identity with attacker-supplied body content — a cross-tenant confusion primitive triggered purely by an unprivileged merchant/internet user who can obtain one valid signed webhook for their own shop.

### Likelihood Explanation
Any shop with the app installed will receive normal webhooks with a valid HMAC over a body they control indirectly (e.g., by editing their own products/orders to control body content). Forging the shop header on the replay requires no secret knowledge, since the header is not covered by the signature.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material, or independently verify that the `shopify-shop-domain` header corresponds to a shop with an active app installation/session before trusting it for dispatch — i.e., change `Request#to_signable_string` in [8](#0-7)  so the shop-identifying headers are bound to the signature, not just the raw body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a legitimate webhook, e.g. `orders/create`, with body `B` and `shopify-hmac-sha256` header `H = HMAC(app_secret, B)`.
2. Attacker captures `B` and `H`, then sends a new POST to the app's webhook endpoint with the same `raw_body=B` and `shopify-hmac-sha256=H`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` recomputes `HMAC(app_secret, B)`, which still matches `H` (body unchanged), so validation passes [3](#0-2) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [6](#0-5) , causing the host app to process attacker-controlled data under the victim shop's identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
