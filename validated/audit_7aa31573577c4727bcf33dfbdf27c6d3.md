### Title
Emporium Min-proof path allows unauthenticated arbitrary calls that drain Emporium's own token/ETH balance with zero on-chain accounting - (File: `contracts/CircomDataBuilder.sol`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`, `contracts/Hinkal.sol`)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only constrains `emporiumMessage`, `timeStamp`, and `calldataHash` — nothing about the actual `EmporiumOperation[]` payload, target addresses, or value moved [1](#0-0) . Setting `EmporiumStack.signerAddress == address(0)` additionally skips the EIP-712 signature check in `verifyWallet` [2](#0-1) , so the ops loop executes fully attacker-controlled low-level calls from Emporium's own identity [3](#0-2)  while every balance-accounting loop in both `runAction` and `Hinkal.transact` iterates the (empty) `erc20TokenAddresses` array and therefore records zero movement [4](#0-3) [5](#0-4) .

### Finding Description
The invariant that should hold is: **assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter` (and in Hinkal's `oldBalances`/`newBalances`/`slippageValues`/`utxoAmount` checks)**. This equality is broken on the Min path.

Path:
1. `Hinkal.transact` calls `hinkalHelper.performHinkalChecks`, which calls `CircomDataBuilder.formInputForCircom` [6](#0-5) . When `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`, it selects `formInputEmporiumMin`, producing only 3 public signals: `emporiumMessage`, `timeStamp`, `calldataHash` [1](#0-0) . Per the main circuit, `message <== Poseidon([messageSeed])` — the attacker just needs any self-chosen `messageSeed` [7](#0-6) . No nullifier, UTXO, root-hash, or ops content is constrained by the proof.
2. `calldataHash` is checked with a plain on-chain equality (`getHashedCalldata(circomData) == circomData.calldataHash`) [8](#0-7) , which the attacker trivially satisfies since they compute the hash of their own crafted `circomData`.
3. `Hinkal.transact` dispatches to `_externalTransact` → `EmporiumUpgradeable.runAction`. `onlyAllowedRecipient` only checks `msg.sender == Hinkal` (the registered external action caller), not the legitimacy of the payload [9](#0-8) .
4. `runAction` decodes `EmporiumStack` from attacker-controlled `externalActionMetadata`. With `signerAddress == address(0)`, `verifyWallet` returns immediately without any signature check [2](#0-1) .
5. The ops loop then executes `op.endpoint.call{value: op.value}(op.callData)` for every attacker-supplied op, from `msg.sender == Emporium contract` [10](#0-9) . The only restriction is blocking `callHinkalWallet`/`doSendToRelay` selectors — an attacker can instead call `ERC20(token).transfer(attacker, amount)` directly, moving any token balance Emporium currently holds to themselves.
6. `balancesBefore`/`balancesAfter` and the resulting `utxoSet` are computed by iterating `circomData.erc20TokenAddresses`, which is empty by construction of the Min path, so this loop runs zero times — no `BalanceChangeShouldBePositive` check, no UTXO creation, and an empty `utxoSet` is returned [11](#0-10) .
7. Back in `Hinkal.transact`, `oldBalances`/`newBalances` are likewise computed over the empty array, and the entire balance/slippage/`utxoAmount` reconciliation loop (lines 97-147) also runs zero times [5](#0-4) . `insertNullifiers`/`insertCommitments` operate on empty arrays consistent with the Min path, so no leaf is spent or created.

Net result: real value leaves the Emporium contract to the attacker, while every on-chain accounting structure (`balancesBefore/After`, `oldBalances/newBalances`, `balanceDif`, `slippageValues`, `utxoAmount`, nullifiers, commitments) shows zero change. None of the existing guards (`performHinkalChecks`, `verifyProof`, `rootHashExists`, `onlyAllowedRecipient`, `verifyWallet` when `signerAddress==0`) constrain the ops' target, calldata, or value — they only gate proof validity for signals that the Min path deliberately excludes.

### Impact Explanation
Any ERC20 or native ETH balance currently held by the `EmporiumUpgradeable` contract (funds parked mid-flow by other users, or protocol-held balances awaiting further Emporium operations) can be drained to an attacker-chosen address in a single transaction, with a proof that costs nothing to generate (no real UTXO ownership, no signature, no deposit). This is direct theft of in-flight/parked user or protocol funds routed through Hinkal — Critical severity. The attack is repeatable for as long as Emporium holds a nonzero balance of any token, each `emporiumMessage` value can only be reused once due to `usedMessages`, but the attacker can pick a fresh `messageSeed`/`emporiumMessage` each time at negligible cost.

### Likelihood Explanation
Preconditions: (1) `EmporiumUpgradeable` must hold some balance (a normal state given its purpose of holding parked balances between operations), and (2) a verifier must be registered for `buildVerifierId` with `tokenNumber == 0` and `externalActionId == HINKAL_EMPORIUM_ACTION_ID` (this Min-path verifier's existence is implied by the deliberate `formInputEmporiumMin` code path being shipped for legitimate "no deposit/withdraw" Emporium ops). Given that, the attacker needs no privileged role, no victim key, and no capital beyond gas — this is a fully unprivileged, deterministic, repeatable exploit.

### Recommendation
Do not allow the Min-path (`erc20TokenAddresses.length == 0`, `signerAddress == 0`) to execute arbitrary low-level calls with no balance accounting. Either: (a) require `verifyWallet` to enforce a signature check regardless of `signerAddress`, binding `ops` to an authenticated identity even in the "stateless" case, or (b) require that `erc20TokenAddresses` (and thus the balance-accounting loops in both `EmporiumUpgradeable.runAction` and `Hinkal.transact`) always cover every token/ETH address touched by any op in the stack, and reject the Min proof path unless the circuit also constrains the op set (e.g., via a hash of `ops` included in the `message` binding) tying the proof to the exact operations executed. At minimum, remove the ability for stateless (non-wallet) ops to target arbitrary endpoints/calldata when no accounted token list is present.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (proxy), register a Min-path verifier for `(tokenNumber=0, nullifierAmount=0, outputAmount=0, externalActionId=HINKAL_EMPORIUM_ACTION_ID)` that accepts a trivially-generated proof of `message = Poseidon(messageSeed)`.
2. Fund `EmporiumUpgradeable` with `1000 TOKEN` (simulate parked balance from an unrelated legitimate flow).
3. As an unprivileged attacker EOA, build `circomData` with `erc20TokenAddresses = []`, `externalActionData = {externalAddress: EmporiumUpgradeable, externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalActionMetadata: abi.encode(EmporiumStack{signerAddress: address(0), ops: [EmporiumOperation{endpoint: TOKEN, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, 1000e18))}], maxFee: 0, deadline: block.timestamp + 1})}`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, `onChainCreation = []`, `slippageValues = []`.
4. Generate the trivial Min proof and call `Hinkal.transact(a, b, c, dimensions, circomData)`.
5. Assert:
   - `TOKEN.balanceOf(EmporiumUpgradeable) == 0` (before: 1000e18) — value moved.
   - `TOKEN.balanceOf(attacker) == 1000e18` — attacker gain.
   - No `Nullified` event emitted, no `NewCommitment` event emitted (accounting arrays empty) — proving `utxoAmount == 0` while real value moved, confirming the broken equality.

    function formInputEmporiumMin(

        uint16 index = 0;

        input[index++] = circomData.emporiumMessage;

    ///@dev Check if transacaction is valid before making it
    ///@param circomData circom data

    function performHinkalChecks(
        CircomData calldata circomData,
        Dimensions calldata dimensions,
        address sender
    ) external view returns (uint256[] memory) {
        require(
            (circomData.originalSender == address(0) &&
                circomData.relay != address(0)) ||
                (circomData.originalSender == sender &&
                    circomData.relay == address(0)),
            "invalid value for originalSender"
        );

        require(
            CircomDataBuilder.getHashedCalldata(circomData) ==
                circomData.calldataHash,
            "Calldata Hash Integrity Check Failed"
        );
        relayerIsValid(circomData.relay);
        dimensionsCheck(circomData, dimensions);
        checkOnchainCreation(circomData);

        return
            CircomDataBuilder.formInputForCircom(
                block.chainid,
                hinkalAddress,
                circomData
            );
    }
