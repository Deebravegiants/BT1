### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header not covered by HMAC signature allows cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and attribute the webhook are all sourced from unauthenticated HTTP headers that are excluded from that signature. `Registry.process` validates the HMAC and then trusts these header-derived fields, including `shop`, when constructing `WebhookMetadata` passed to the app's handler.

### Finding Description
`Registry.process` validates a webhook by calling `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` computes the expected signature strictly from `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [3](#0-2) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.), which are not part of the signed content: [4](#0-3) 

`Registry.process` then forwards `request.shop` unchanged into `WebhookMetadata`, which is the struct handed to the host application's `WebhookHandler#handle`: [1](#0-0) [5](#0-4) 

This breaks the identity binding: `shop authenticated (i.e., covered by a signature verified with the app's shared secret) == shop used as the tenant key by the handler`. In this gem, only the request body is authenticated; the `shop` (and `topic`/`webhook_id`) are not. Since every shop installed on a given app shares the same `client_secret`/HMAC key, any party who can obtain one valid `(raw_body, hmac)` pair for *any* shop on the app (e.g., from their own store's webhook deliveries, which a merchant fully controls and can inspect/capture) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. The HMAC check still passes because it only verifies the body, and the registry attributes the payload to the attacker-chosen shop.

### Impact Explanation
This is a cross-tenant vulnerability: a legitimate, unprivileged webhook sender for one tenant (their own shop) can cause the app to process an authenticated-looking webhook as if it originated from a different, arbitrary shop. Depending on how the host application implements `WebhookHandler#handle` (which the gem's `WebhookMetadata.shop` is designed to be trusted for tenant routing), this can lead to writing or acting on data under another merchant's tenant context, satisfying the "cross-tenant access" criterion for Critical severity.

### Likelihood Explanation
Likelihood is Medium: the attacker must control (or previously capture) at least one valid raw-body/HMAC pair from a legitimate webhook delivery to the same app (trivial for a merchant who installed the app, since they receive their own webhooks), and then must be able to send a crafted HTTP request to the app's public webhook endpoint with a forged `shopify-shop-domain` header — both are within reach of an unprivileged internet user / app-installing merchant, with no access token, `client_secret`, or privileged account required.

### Recommendation
Include the identity fields that determine trust/routing — at minimum `shop`, and ideally `topic` and `webhook_id` — in the HMAC-signed payload used by `to_signable_string`, or otherwise cryptographically bind them to the signed body before they are exposed via `WebhookMetadata`. Alternatively, document that `WebhookMetadata.shop`/`topic` are unauthenticated header values and require host applications to independently re-verify shop ownership (e.g., against known/registered shops) before trusting webhook attribution.

### Proof of Concept
1. Capture a legitimate webhook delivery for `shop-a.myshopify.com` (available to any merchant who installs the app), consisting of `raw_body` and the header `shopify-hmac-sha256: <valid HMAC of raw_body>`.
2. Replay the exact same `raw_body` and `shopify-hmac-sha256` value to the app's webhook endpoint, but replace the header `shopify-shop-domain: shop-a.myshopify.com` with `shopify-shop-domain: shop-b.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the signature over `to_signable_string` (`raw_body` only) — matching the captured HMAC — and passes.
4. `WebhookMetadata.shop` is set to `shop-b.myshopify.com` and delivered to the app's handler, which will process the request as belonging to `shop-b`, despite the payload/HMAC having actually been produced for `shop-a`.
