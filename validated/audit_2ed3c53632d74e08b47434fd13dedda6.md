### Title
Webhook shop/topic/webhook_id attribution is not covered by HMAC, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by the app to attribute and route the event come from HTTP headers that are never included in that signable string. `ShopifyAPI::Webhooks::Registry.process` validates only that the body bytes match *some* valid Shopify-signed payload, then trusts the header-derived `shop` for tenant attribution.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from attacker-controllable HTTP headers with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC over the body via `Utils::HmacValidator.validate(request)`, and — on success — dispatches to the handler using `request.shop` (header-derived) for tenant identification, alongside `request.topic` and `request.parsed_body`: [3](#0-2) 

`HmacValidator.validate` only ever calls `verifiable_query.to_signable_string` (the raw body) against `verifiable_query.hmac` (the header-derived HMAC digest) — it has no notion of `shop`: [4](#0-3) 

The broken identity binding, stated as an equality that fails to hold: `shop_that_HMAC_authenticates == shop_used_for_tenant_attribution`. In this gem, the left side is undefined (no shop bytes are ever hashed), while the right side is `request.shop`, taken verbatim from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header.

**Attack sequence**: an attacker who operates a legitimate Shopify shop and has installed the target app receives a genuine webhook from Shopify for their own shop — a real, validly-signed `(raw_body, hmac)` pair. They replay this exact HTTP POST to the app's webhook endpoint, but rewrite the `X-Shopify-Shop-Domain` header (and, if desired, `X-Shopify-Topic`) to name a different, victim shop. Because `HmacValidator.validate` recomputes the HMAC solely from `raw_body` using the app's `api_secret_key` — a value the attacker never needed and never touches — the recomputed signature still equals the one supplied in the (unmodified) `hmac` header, and validation succeeds. The handler is invoked with `WebhookMetadata.shop` set to the victim's domain and the attacker's forged body content, even though the true owner of that body is the attacker's own shop.

### Impact Explanation
This lets an unprivileged, minimally-privileged attacker (any merchant who installs the app) inject arbitrary webhook events attributed to an arbitrary victim shop domain into the host application, since the header-derived `shop` used for all downstream per-tenant processing (data ingestion, job dispatch, cache invalidation, etc., per the documented `data.shop` usage in `docs/usage/webhooks.md`) is completely outside the scope of what the HMAC actually authenticates. This is a cross-tenant confusion/injection primitive: the app cannot distinguish "this event genuinely originated from shop X" from "this event's body is authentic (for the sender's own shop) but has been relabeled as shop X."

### Likelihood Explanation
Any user able to install the app on their own store (a routine, unprivileged action) can trivially capture one authentic webhook and replay it with a modified `shop-domain` header using a basic HTTP client — no access token, `client_secret`, or TLS interception is required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signable content (or otherwise cryptographically bind them to the body), or independently verify the shop by cross-referencing it against a known, previously-established session/shop record before dispatching to handlers, rather than trusting the raw header value once body-only HMAC validation passes.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing the genuine `raw_body`, `X-Shopify-Hmac-Sha256`, and `X-Shopify-Topic` values Shopify sent.
2. Attacker POSTs the identical `raw_body` and `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. The app calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body:, headers:))` exactly as documented in `docs/usage/webhooks.md`.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only, matches the supplied HMAC, and returns `true`. [5](#0-4) 
5. The handler executes with `data.shop == "victim-shop.myshopify.com"` and the attacker-controlled `data.body`, despite the payload never having been produced by, or authorized for, the victim shop.
