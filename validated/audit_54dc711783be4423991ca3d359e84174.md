### Title
Webhook `shop`, `topic`, and `webhook_id` headers are trusted for tenant dispatch despite not being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `ShopifyAPI::Webhooks::Registry.process` dispatches to handlers and constructs `WebhookMetadata` using the `shop`, `topic`, `api_version`, and `webhook_id` values taken straight from unauthenticated HTTP headers. The HMAC never binds these header values to the payload, so any attacker who can obtain one validly-signed `(body, hmac)` pair (e.g., a webhook delivered to their own store, which they legitimately control) can replay it with arbitrary `x-shopify-shop-domain` and `x-shopify-topic` header values and have the app process it as if it were a legitimate webhook for a different topic and a different, victim merchant.

### Finding Description
`Request#hmac`/`Request#to_signable_string` compute/verify the signature purely over `@raw_body`: [1](#0-0) 

`HmacValidator.validate` only checks that the HMAC matches `to_signable_string` (the body), and says nothing about the headers: [2](#0-1) 

`Registry.process` then uses the unauthenticated header-derived accessors (`request.topic`, `request.shop`, `request.api_version`, `request.webhook_id`) to select the handler and build the metadata passed to it: [3](#0-2) 

The identity binding that should hold is: *the shop/topic that the HMAC-signing party (Shopify) intended for this payload* == *the shop/topic the handler is told it is processing*. Because `shop`, `topic`, `webhook_id`, and `api_version` are read from headers that are never included in the signed bytes, that equality is not enforced — only the body bytes are authenticated, not the routing metadata attached to them.

### Impact Explanation
An attacker who legitimately owns a Shopify store (an unprivileged internet user with respect to the target app/other merchants) can trigger any webhook delivery to their own endpoint (e.g., by installing the app, placing a test order, or triggering any subscribed topic), capture the resulting `(raw_body, x-shopify-hmac-sha256)` pair, and then replay that exact body/HMAC to the app's webhook endpoint while substituting:
- `x-shopify-shop-domain` with a victim merchant's domain, and/or
- `x-shopify-topic` with a different registered topic (e.g. `app/uninstalled`, `shop/redact`, `customers/redact`).

Because the gem never validates that these header values are consistent with the signed body, the request passes `HmacValidator.validate` and is dispatched to the handler for the attacker-chosen topic with `WebhookMetadata.shop` set to the victim shop. If the host application relies on `WebhookMetadata.shop`/`topic` (as the gem's documented contract implies it should) to decide which tenant's data/session to mutate (e.g., marking an install revoked, purging data for GDPR `redact` topics, invalidating sessions), this allows cross-tenant action against a shop the attacker does not control — satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
High. No secret, access token, or privileged account is required — only the ability to receive one legitimate webhook to a store the attacker owns (trivial, since installing/using the app on any store is normal, unprivileged merchant activity) and the ability to replay an HTTP request with modified headers, which is trivial for anyone controlling their own webhook receiver/proxy.

### Recommendation
Include the routing-critical headers (`shop`, `topic`, `api_version`, `webhook_id`) in the signed material, or otherwise cryptographically/contextually bind them to the verified body (e.g., require the body's own `shop_domain`/`shop_id` fields to match the header before trusting header-derived shop/topic, and reject mismatches). At minimum, document and enforce that `WebhookMetadata.shop`/`topic` must never be used for tenant-sensitive actions without cross-checking against the authenticated payload contents.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and captures a real webhook delivery, e.g. body `{"id":1}` with header `x-shopify-hmac-sha256: <valid-hmac-of-body>`.
2. Attacker replays the exact same body and HMAC to the app's webhook endpoint, but sets:
   - `x-shopify-shop-domain: victim.myshopify.com`
   - `x-shopify-topic: app/uninstalled` (or any topic the app has registered a handler for)
3. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which succeeds because it only checks the body bytes: [4](#0-3) 
4. The handler registered for `app/uninstalled` is invoked with `WebhookMetadata.shop == "victim.myshopify.com"`, even though Shopify never issued this event for that shop.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
