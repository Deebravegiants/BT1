This confirms the vulnerability: `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `#shop` is read directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header [2](#0-1) . `Registry.process` validates only the HMAC over the raw body via `Utils::HmacValidator.validate(request)` and then dispatches to the handler passing `request.shop` as the tenant identifier, with no cross-check that the header's shop matches any shop bound into the signed payload [3](#0-2) .

### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook impersonation — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC-SHA256 signature over the raw request body, computed via `Utils::HmacValidator.validate(request)` [4](#0-3) . The `Request#to_signable_string` method used for this HMAC computation returns only `@raw_body` [1](#0-0) . However, `Request#shop`, the value passed to the handler as `WebhookMetadata#shop` and used by the host app to attribute the payload to a merchant/tenant, is read straight from the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) HTTP header, which is completely outside the HMAC's signed content [2](#0-1) .

### Finding Description
This breaks the identity binding: `shop header verified == shop header used to attribute the payload` should hold, but instead `shop header (unauthenticated) != shop bound inside the HMAC-signed bytes (body only)`.

Any unprivileged internet user who has ever received (or intercepted) a legitimately signed webhook body for their own shop — trivial to obtain, since they control their own store and can register a webhook endpoint elsewhere to capture the payload and its valid `X-Shopify-Hmac-Sha256` value — can replay that exact `raw_body` + `hmac` pair to the victim app's webhook endpoint while substituting an arbitrary value (e.g., a victim shop's domain) in the `X-Shopify-Shop-Domain` header. `Registry.process` recomputes the HMAC only over `@raw_body`, which is unchanged and therefore validates successfully, and then calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))`, passing the attacker-chosen `shop` straight through [5](#0-4) . Any host application that trusts `data.shop` from `WebhookMetadata` (e.g., to look up which tenant's data/session to update, per the gem's own documented usage) will process attacker-controlled body content under an arbitrary victim tenant's identity.

### Impact Explanation
This allows cross-tenant data injection/impersonation: a webhook whose HMAC is validly signed for shop A's payload can be attributed to shop B merely by forging an HTTP header, since the header carrying the tenant identity is never authenticated. Depending on how the host app processes the given topic (e.g., `app/uninstalled`, `customers/redact`, order or fulfillment updates), this can lead to a cross-tenant state corruption — matching the "cross-tenant access" impact class, since the trust boundary between two independent Shopify tenants is broken purely because the gem allows an unauthenticated field to be treated as verified.

### Likelihood Explanation
High feasibility: any user can be a legitimate Shopify merchant, register a webhook subscription on their own store pointing to a listener they control, capture one genuine signed webhook body/HMAC pair, and then replay it to the target app's public endpoint with a modified shop-domain header — no `api_secret_key`, access token, or privileged access is required.

### Recommendation
Bind the shop identity into the HMAC-verified signable content (or independently authenticate the `shop-domain` header, e.g. by requiring it to be included in the signed payload as Shopify's other verifiable queries do — compare `Auth::Oauth::AuthQuery#to_signable_string`, which explicitly includes `shop` in the signed string [6](#0-5) ). At minimum, document that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant attribution without additional verification (e.g., cross-checking against an active session for that shop).

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com` and registers a webhook (e.g., `orders/create`) pointing to a listener under their control.
2. Attacker triggers the event and captures the raw POST body and the `X-Shopify-Hmac-Sha256` header — both valid for the app's `client_secret` since Shopify signed them.
3. Attacker POSTs the identical body and HMAC header to the victim app's webhook endpoint, replacing `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` accepts the forged headers [7](#0-6) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because the body is byte-identical and correctly signed [4](#0-3) .
5. The registered handler receives `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON parsed from the captured body>, ...)`, causing the host app to process attacker-supplied data attributed to the victim tenant [8](#0-7) .
