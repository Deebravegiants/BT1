## Finding

### Title
Excess native ETH sent to `EvmHost.dispatch()`/`fundRequest()` for fee-swap is permanently locked in the contract instead of being refunded to the payer - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept native ETH via `msg.value` and forward the *entire* value to `IUniswapV2Router02.swapETHForExactTokens` with `to = address(this)`. Uniswap's router only spends the exact amount needed for the requested fee and refunds any unused ETH — but it refunds it to `msg.sender` of the swap call, which is `EvmHost` itself, not the original caller/payer. `EvmHost` never captures or forwards this refund back out, so any ETH sent above the exact required fee becomes permanently stuck in the contract.

### Finding Description
In `EvmHost.dispatch(DispatchPost)`: [1](#0-0) 

the call `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` is made without capturing the returned `amounts` array and without any subsequent refund logic. The same pattern is repeated in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

Uniswap V2 Router's `swapETHForExactTokens` computes the exact input needed (`amounts[0]`) and only refunds the dust `msg.value - amounts[0]` to `msg.sender` — which, in this call context, is `EvmHost`, not the transaction's original `_msgSender()`/`post.payer`. Because `EvmHost` never re-forwards that refunded dust to the caller, it accumulates unclaimed inside `EvmHost`'s balance with no user-facing recovery path.

This is confirmed to be a known bug class the project is otherwise aware of and has fixed elsewhere: `IntentGatewayV2.placeOrder` performs the identical swap pattern but explicitly tracks `amounts[0]` and refunds the remainder: [4](#0-3) 

and `ExtrinsicIntents._fillCrossChain` likewise explicitly refunds leftover `msgValue` to `msg.sender`: [5](#0-4) 

`EvmHost.dispatch`/`fundRequest`, the most fundamental and most-used entry points for dispatching cross-chain messages and funding relayer fees, lack this same refund logic that its own sibling contracts implement.

### Impact Explanation
Any unprivileged message dispatcher — any app or user calling `IDispatcher(host).dispatch{value: msg.value}(post)` or `fundRequest{value: msg.value}(...)` with native ETH — will lose any ETH sent above the exact fee amount required for the Uniswap swap. The project's own documentation confirms native-token fee estimation is inherently imprecise: "Fee Calculation | Approximate (subject to slippage)" and explicitly warns off-chain `quote()` estimates should be used, meaning overpayment (to account for slippage/safety margin) is the expected common case, not an edge case: [6](#0-5) 

Since `dispatch` and `fundRequest` are the base primitives used by essentially every app built on Hyperbridge (`HyperFungibleToken.send`, `HyperbridgeLzEndpoint`, custom `HyperApp` contracts, etc. all forward `msg.value` straight into `IDispatcher.dispatch`), this is a widely reachable freezing-of-funds bug affecting ordinary users on every native-fee-paying dispatch, not a contrived scenario.

### Likelihood Explanation
High. Any caller using native-token payment via `dispatch()`/`fundRequest()` and sending even slightly more ETH than the exact quoted fee (routine due to slippage buffers, gas price fluctuation between quote and execution, or a deliberate safety margin) permanently loses the excess. No malicious actor is required — this occurs under normal, expected usage patterns as documented by the project itself.

### Recommendation
Capture the `amounts` return value from `swapETHForExactTokens` in `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, and refund `msg.value - amounts[0]` back to `_msgSender()` (or the designated payer), mirroring the pattern already implemented in `IntentGatewayV2.placeOrder` and `ExtrinsicIntents._fillCrossChain`.

### Proof of Concept
1. User calls `EvmHost.dispatch{value: 1 ether}(post)` where `post.fee` (in feeToken) only requires 0.9 ETH worth of input to swap via Uniswap, intentionally sending extra ETH as a slippage buffer (as the docs recommend estimating off-chain, which is inherently imprecise).
2. Inside `dispatch`, `swapETHForExactTokens{value: 1 ether}(post.fee, path, address(this), block.timestamp)` executes: the router spends `amounts[0] = 0.9 ether` and refunds `0.1 ether` back to `msg.sender` of the swap call, i.e., `EvmHost`.
3. `EvmHost.dispatch` returns without ever forwarding that `0.1 ether` back to the user; it remains stuck in `EvmHost`'s balance with no callable function that lets the original payer reclaim it.

```text
### Payment Method Comparison

| Feature | Native Token | FeeToken (Recommended) |
|---------|-------------|------------------------|
| **Gas Cost** | Higher (includes swap) | Lower (no swap) |
| **Slippage** | Yes (Uniswap swap) | No |
| **Fee Calculation** | Approximate (subject to slippage) | Exact |
| **Token Approval** | Not required | Required  |
| **User Convenience** | High (users have native tokens) | Low (users need feeToken) |
| **Best For** | One-off transactions, user-facing apps | Frequent dispatches, cost optimization |
```
