### Title
Emporium's `runAction` only reconciles balances for tokens explicitly listed in `circomData.erc20TokenAddresses`, letting any op drain untracked token balances held by the Emporium contract - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` snapshots and reconciles balances only for the tokens present in the caller-supplied `circomData.erc20TokenAddresses` array, and `deltaAmountChanges` is sized to exactly match that array by construction in `Hinkal._externalTransact`. Because the attacker fully controls both `erc20TokenAddresses` and the `EmporiumStack.ops` (via `externalActionMetadata`) for their own proof/transaction, they can execute an arbitrary low-level call to any token contract that Emporium already holds a balance of, moving that token out, while never listing it in `erc20TokenAddresses` - so no `balanceChange`/`deltaAmountChanges` check ever fires for it.

### Finding Description
The broken equality is: *"the set of tokens whose Emporium balance can change during `runAction` == the set of tokens present in `circomData.erc20TokenAddresses`"*. The code enforces this only for indices `0..erc20TokenAddresses.length-1`: [1](#0-0) 

`stack.signerAddress == address(0)` makes `verifyWallet` a no-op (only replay-marking the message, no signature check), so the "Stateless Interaction" branch is reachable by an unprivileged EOA with no wallet contract at all: [2](#0-1) 

In that branch, `op.endpoint.call{value: op.value}(op.callData)` is a fully attacker-controlled arbitrary call, blocked only for the `callHinkalWallet`/`doSendToRelay` selectors: [3](#0-2) 

After all ops run, reconciliation only iterates `circomData.erc20TokenAddresses.length`: [4](#0-3) 

`deltaAmountChanges` is created with exactly `erc20TokenAddresses.length` entries in `Hinkal._externalTransact` — there is no independent constraint tying the array length/content to what `ops` actually touch: [5](#0-4) 

Because `erc20TokenAddresses`, `amountChanges`, and `externalActionData` (which contains the `EmporiumStack`/`ops`) are all attacker-chosen fields committed to by the attacker's own proof (via `calldataHash` in `getHashedCalldata1`), the zk circuit never cross-checks that every token an op moves is included in `erc20TokenAddresses`: [6](#0-5) 

Exploit flow: an attacker crafts `circomData.erc20TokenAddresses = [tokenA]` and an `EmporiumStack.ops` array whose second (or only) op is `op.endpoint = tokenB`, `op.callData = abi.encodeCall(IERC20.transfer, (attacker, amount))`, with `stack.signerAddress = address(0)`. Since the low-level call is made *from* the Emporium contract, `msg.sender` inside `tokenB.transfer` is Emporium itself, so no approval is needed - only a pre-existing Emporium balance of `tokenB`. Such a balance can already exist in the shared, multi-tenant Emporium contract from dust/rounding left over by any earlier transaction (from the attacker or any other user) whose own `erc20TokenAddresses` didn't fully cover every token its `ops` touched, or from any other stray transfer into the contract. `handleOut`/`balanceChange` guards (lines 132-151) never see `tokenB` because it is outside the loop bound, so the transfer succeeds unconditionally and is never reverted by `BalanceChangeShouldBePositive`.

### Impact Explanation
Any balance of an ERC20 token resting in the shared `EmporiumUpgradeable` contract that is not included in the current caller's `erc20TokenAddresses` list can be permanently and unconditionally exfiltrated by any unprivileged EOA who crafts an op targeting that token directly. Because Emporium is a shared relay used across many users' external actions, and nothing in the contract or circuit ever audits/sweeps all token balances it may hold — only the caller-declared subset — this is a direct, repeatable theft vector against value that Hinkal never priced into `deltaAmountChanges`/`balanceChange`. This matches the Critical category (direct theft of in-flight/shielded funds) whenever the stranded balance originated from another user's shielded funds routed through Emporium.

### Likelihood Explanation
Preconditions: Emporium must hold some balance of a token not declared by the attacker's `erc20TokenAddresses`. This is highly plausible in practice — any swap/DEX external action leaving rounding dust, partial fills, or a caller (malicious or careless) who under-declares `erc20TokenAddresses` relative to what their own `ops` manipulate leaves the residue permanently in Emporium, since no other code path ever forces Emporium's balance of an "unlisted" token back to zero. Attacker cost is a single self-generated proof/transaction with `signerAddress == address(0)` (no signature, no wallet, no privileged role) and one crafted op — fully within the declared unprivileged-EOA capabilities. The attack is repeatable indefinitely as new dust accumulates.

### Recommendation
Enforce that `EmporiumStack.ops` cannot target/move balances of tokens outside `circomData.erc20TokenAddresses`, e.g. by restricting `op.endpoint` from being an ERC20 contract that isn't in the declared list (or by snapshotting/reconciling balances for *all* tokens Emporium could plausibly hold, not just the caller-declared subset), and/or by adding a global sweep/zero-balance invariant so Emporium never carries residual token balances across transactions.

### Proof of Concept
Foundry test outline:
1. Deploy `EmporiumUpgradeable`, `ERC20 tokenA`, `ERC20 tokenB`.
2. Seed Emporium with a `tokenB` balance (simulate leftover dust from a prior transaction, e.g. `tokenB.transfer(emporiumAddress, amount)` directly, representing stranded prior-user funds) — do NOT go through any accounted flow.
3. Build `circomData` with `erc20TokenAddresses = [tokenA]`, `amountChanges`/`deltaAmountChanges` sized 1, and `externalActionData.externalActionMetadata` encoding `EmporiumStack{ signerAddress: address(0), ops: [ {endpoint: tokenB, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer,(attacker, amount))} ] }`.
4. Call `runAction(circomData, deltaAmountChanges)` from the allowed-recipient (`Hinkal`) context.
5. Assert: `tokenB.balanceOf(emporium)` decreases by `amount`, `tokenB.balanceOf(attacker)` increases by `amount`, while `circomData.erc20TokenAddresses` and `deltaAmountChanges` contain no entry for `tokenB`, and the transaction does not revert with `BalanceChangeShouldBePositive`.
