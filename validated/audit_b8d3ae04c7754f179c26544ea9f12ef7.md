## Finding: Webhook shop/topic headers are not covered by the HMAC signature, enabling cross-tenant webhook forgery

### Title
Webhook `shop`, `topic`, and `webhook-id` are trusted for dispatch but excluded from HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, then dispatches to a handler using the `topic` and `shop` values taken directly from HTTP headers — values that are never included in the signed material. Any party who can obtain one valid `(raw_body, hmac)` pair (e.g. from a webhook Shopify delivers to their own store) can replay it against the app's endpoint with an arbitrary `shop-domain`, `topic`, or `webhook-id` header and have it accepted as authentic for a different merchant/topic.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body — none of the identifying headers: [2](#0-1) 

`Registry.process` validates that HMAC and then immediately trusts `request.topic` (to select the handler) and `request.shop` (propagated into `WebhookMetadata` and handed to the app) without any cryptographic binding between those fields and the signature that was just verified: [3](#0-2) 

This is the same bug class as the reported analog: a value that is *acted upon* (here, `shop`/`topic`/`webhook_id`, used for tenant/handler dispatch) is not covered by the integrity check (`hmac`) that gates the action. The equality the code implicitly assumes — `verified_bytes == acted_upon_identity (shop, topic)` — does not hold, because `verified_bytes` is only `raw_body`, while `acted_upon_identity` is read from unauthenticated headers.

Contrast this with the OAuth callback path, where `shop`, `host`, `code`, `state`, and `timestamp` are all explicitly included in `AuthQuery#to_signable_string` and therefore covered by the HMAC: [4](#0-3) 
The webhook path lacks this equivalent binding for `shop`/`topic`.

### Impact Explanation
An unprivileged internet user who owns any store where the app is installed (a normal, self-serve action — no special privilege required) can trigger the app to receive a genuine webhook for their own shop, capture the exact `(raw_body, hmac)` pair Shopify sent, and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and/or `X-Shopify-Webhook-Id` headers for a different (victim) shop/topic. Because `Registry.process` only checks the HMAC of the body and never ties it to those headers, the forged request passes validation and is dispatched to the handler as `WebhookMetadata.new(topic: <attacker-chosen>, shop: <attacker-chosen>, ...)`. Depending on how the host application keys its persisted state off `data.shop`, this enables cross-tenant data confusion/corruption — writing or acting on data attributed to a shop the attacker does not control.

### Likelihood Explanation
Moderate-to-high: exploitation requires only capturing one legitimate webhook delivery from the attacker's own store (trivial — install the app, perform an action that fires a webhook, and intercept it with any HTTP proxy) and replaying it with modified headers. No knowledge of `api_secret_key` or any Shopify-side credential is required.

### Recommendation
Bind the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) into the signed material verified by `Utils::HmacValidator`, or otherwise cryptographically tie the verified body to the shop/topic before dispatch (e.g., cross-check `shop` against a known/registered shop record, and validate `topic` against the body's semantic content rather than the header alone). At minimum, document this gap so host applications independently verify shop identity out-of-band before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) shop `attacker.myshopify.com` and triggers an event (e.g., creates an order) so Shopify sends a legitimate webhook with a valid `hmac` for the raw body.
2. Attacker intercepts this HTTP request (their own traffic, no secret needed) and notes the exact `raw_body` and `x-shopify-hmac-sha256` value.
3. Attacker resends the identical `raw_body`/`hmac` pair to the app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com` (and/or a different `x-shopify-topic`).
4. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against `hmac` (`lib/shopify_api/webhooks/request.rb#to_signable_string`, `lib/shopify_api/utils/hmac_validator.rb#validate`).
5. `Registry.process` dispatches the handler with `shop: "victim.myshopify.com"`, causing the host application to process attacker-controlled data as if it originated from the victim shop.
