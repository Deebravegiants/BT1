## Analysis

The Gearbox bug class is: a shared/reusable component (an "adapter") can be swapped out from under multiple dependent consumers without any check that those consumers are still safely bound to it, silently changing their behavior.

nearcore has a structurally identical pattern in **global contracts referenced by account id**. A contract deployed with `GlobalContractDeployMode::AccountId` is addressed by the deploying account's id rather than by its code hash [1](#0-0) . Any other account can "subscribe" to it via `UseGlobalContractAction` / `action_use_global_contract`, which stores only the reference `AccountContract::GlobalByAccount(id)` — not a pinned code hash — into the consuming account [2](#0-1) .

Because the binding is purely by `AccountId` and not by ownership identity or code hash, whoever controls that account id at code-load time controls the code that runs for every consuming account:

- `action_deploy_global_contract` allows (re)deploying code under the same `AccountId` identifier at any time, with no check that the deployer is the "original" owner of the semantic identity — it only checks the account can afford storage [3](#0-2) .
- `use_global_contract` re-resolves the current global contract code under that identifier at usage-time (`TrieKey::GlobalContractCode { identifier: contract_identifier }`), with no versioning/pinning back to what was live when the consumer opted in [4](#0-3) .
- Accounts can be fully deleted (`action_delete_account`/`remove_account`), which removes the `Account`, local `ContractCode`, keys, and data — but does **not** touch `TrieKey::GlobalContractCode` entries keyed by `AccountId` [5](#0-4) [6](#0-5) . Sub-accounts (and top-level accounts once vacated) can later be recreated by any predecessor satisfying `action_create_account`'s rules [7](#0-6) .

This is the near-analog of the Gearbox report: the "adapter" (global contract identity) is shared by multiple "contracts" (consuming accounts with `AccountContract::GlobalByAccount`), and the system's own docs confirm the update-for-everyone behavior is by design for the *legitimate* deployer ("This allows the owner to update the contract for all its users" [8](#0-7) , exercised in `test_global_contract_update` [9](#0-8) ) — but there is no check anywhere that the entity redeploying under that `AccountId` is still the same actor the consumers trusted when they called `UseGlobalContractAction`. If the deploying account is deleted and its id later recreated by a different, potentially malicious actor, that new controller can silently push arbitrary code that will execute under every consumer account that still references `GlobalByAccount(that_id)` — no re-confirmation, no check that "this adapter is not in use by others" is ever performed, mirroring exactly the recommendation in the source report ("add a check that removed adapter is not used in other contracts").

### Title
Global contract identity hijack via account-id recycling breaks/takes over dependent `GlobalByAccount` consumers - (File: `runtime/runtime/src/global_contracts.rs`)

### Summary
A global contract deployed in `AccountId` mode is referenced by consuming accounts purely via the deployer's `AccountId` (`AccountContract::GlobalByAccount`), re-resolved at every call. There is no binding to the identity/session that deployed the code the consumer originally opted into, and no protection preventing the underlying account id from being deleted and later recreated by an unrelated party who can then redeploy contract code that silently takes effect for all existing consumers.

### Finding Description
`use_global_contract` stores only `AccountContract::GlobalByAccount(id)` in the consumer's account, and code resolution always reads the *current* value at `TrieKey::GlobalContractCode { identifier: AccountId(id) }` [10](#0-9) . `action_deploy_global_contract` lets whoever currently controls account `id` write new code under that identifier at any time, with no ownership continuity check [3](#0-2) . Meanwhile, `action_delete_account`/`remove_account` deletes the account but leaves the `GlobalContractCode`/nonce trie entries for that `AccountId` identifier untouched [6](#0-5) [5](#0-4) , and a new account with the same id can subsequently be created (sub-account creation is permitted for any predecessor matching the naming rule; a vacated top-level id is likewise creatable subject to registrar rules) [7](#0-6) . This lets a new controller of that account id redeploy a global contract under the same `GlobalContractIdentifier::AccountId`, and every account that had previously called `UseGlobalContractAction` against that identifier will transparently execute the new (potentially malicious) code on their next call — exactly the "shared component removed/swapped out from under dependents" bug class described in the source report.

### Impact Explanation
Consuming accounts unknowingly execute code chosen by a party they never authorized, which can lead to unauthorized state mutation, drained balances (a malicious global contract can implement arbitrary logic, including funneling attached deposits or approving transfers), or broken/DoS'd functionality for every account that adopted the shared contract — satisfying "unauthorized state or balance change" criteria.

### Likelihood Explanation
Exploitation requires the attacker to obtain control of a specific account id after its original owner deletes it (or to pre-register a throwaway sub-account, get others to `UseGlobalContractAction` against it, then delete+recreate it themselves) — feasible for sub-accounts, which any predecessor can create following the naming rule, making the attack self-inflictable and fully reachable via ordinary `DeleteAccount` / `CreateAccount` / `DeployGlobalContract` / `UseGlobalContractAction` transactions with no privileged access required.

### Recommendation
Bind `GlobalByAccount` references to something that cannot be silently transferred — e.g., pin to the code hash observed at `UseGlobalContractAction` time (falling back to `AccountId::Global(hash)` semantics), or track a monotonically-increasing "generation"/creation nonce for the underlying account and invalidate/require re-confirmation of `GlobalByAccount` references when the backing account is deleted and recreated, analogous to the report's recommendation to verify a shared component is not still relied upon by other consumers before it can be repointed.

### Proof of Concept
1. Account `shared.near` deploys a global contract in `AccountId` mode (`DeployGlobalContractAction{ deploy_mode: AccountId }`), as in `test_global_contract_update` [11](#0-10) .
2. Accounts `A` and `B` call `UseGlobalContractAction{ contract_identifier: AccountId(shared.near) }`, binding their `AccountContract` to `GlobalByAccount("shared.near")`.
3. `shared.near` is deleted via `DeleteAccountAction` (the `GlobalContractCode` keyed by `AccountId("shared.near")` remains in the trie, per `remove_account`).
4. A different actor creates a new account `shared.near` (if it is a sub-account whose parent permits it, or once naming/registrar constraints allow) and calls `DeployGlobalContractAction{ deploy_mode: AccountId }` with malicious code.
5. On `A`'s and `B`'s next `FunctionCall`, `AccountContract::GlobalByAccount("shared.near")` resolves to the new malicious code, executing it under `A`'s/`B`'s security context without either account having re-consented.

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())
