This confirms the design: `VerifiableQuery#to_signable_string` is the only content that HMAC covers, and for the webhook `Request` class that content is `@raw_body` alone — no headers are included in the signable string. [1](#0-0) 

### Title
Cross-tenant webhook spoofing via unsigned `shop` header — HMAC verifies only the body, not the shop identity used for dispatch ([File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `Request#shop` is read from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header. `Registry.process` validates the HMAC against the body and then forwards `request.shop` unchecked into the handler. Because a single app-wide `client_secret` signs webhooks for every shop that installs the app, any merchant who has the app installed (an unprivileged actor with respect to other tenants) can capture a legitimately-signed webhook delivered to their own store and replay it against the app's webhook endpoint with the `shop` header rewritten to any victim shop domain. The HMAC still validates (it only covers the body bytes), but the shop identity the app trusts for tenant attribution is forged.

### Finding Description
The identity binding that should hold is:
`shop value trusted by the handler == shop that the HMAC-signed bytes were actually generated for`

In this gem that binding is broken:
- `Request#to_signable_string` signs only `@raw_body`: [2](#0-1) 
- `Request#shop` is read from a header that is excluded from the signed content: [3](#0-2) 
- `Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` and, on success, passes `request.shop` straight through to the handler without re-checking it against anything else: [4](#0-3) 
- `HmacValidator.validate_signature` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the body) and secure-compares it to the `hmac` header — it never touches `shop`: [5](#0-4) 

Because Shopify apps use one `client_secret` for all merchant installs, a merchant who has legitimately installed the app receives real webhooks (e.g. `orders/create`) signed with that same shared secret for their own shop. That merchant can capture such a webhook and resend it to the app's endpoint with the `shopify-shop-domain` header swapped to a different, victim shop domain. The HMAC check in `HmacValidator.validate` still passes because it only verifies the body bytes match the secret — it says nothing about which shop the request claims to be from. `Registry.process` then dispatches the (attacker-controlled) body attributed to the victim's `shop` value to the topic handler.

This is the same bug class as the `retryMessage()` finding referenced: a validation is performed on one artifact (HMAC over the body / `proofReceipt`-style status check) while the code proceeds to act on a *different*, unchecked artifact (`shop` header / banned-address or suspended-message state) that is assumed — incorrectly — to still be consistent with what was validated.

### Impact Explanation
This crosses a tenant boundary: an app built on this gem, using `Registry.process` as documented, will process attacker-supplied webhook data under an arbitrary victim shop's identity, purely on the strength of a header the gem never authenticates. If the host application uses `WebhookMetadata#shop` to look up per-shop state (sessions, order records, fulfillment triggers, etc.), the attacker can inject or corrupt data belonging to a merchant they do not control — a cross-tenant access/data-injection issue, which the rubric classifies as Critical.

### Likelihood Explanation
Exploitation requires only an unprivileged actor who can install the app on their own store (or otherwise obtain one validly-signed webhook payload for a topic they control) and can send arbitrary HTTP requests to the app's public webhook endpoint with a modified header — no access token, `api_secret_key`, or other privileged credential is needed. The victim shop domain need not even be a real merchant known to the attacker in advance for the request to pass validation.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed content, or independently authenticate the `shop` header against a value looked up from a store the app controls (e.g., match it against the shop associated with the specific webhook subscription/registration) before trusting it in `WebhookMetadata`. At minimum, `Request#to_signable_string` should not omit any field that downstream code (`Registry.process`, `WebhookMetadata`) treats as verified.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and configures/triggers a webhook (e.g. `orders/create`), receiving a real, validly-signed request:
   - Headers: `x-shopify-hmac-sha256: <valid HMAC of body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
2. Attacker replays this exact request to the app's public webhook endpoint, only changing the header:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC from `request.to_signable_string` (the unmodified body) and the shared `client_secret` — validation succeeds because the body and secret are unchanged.
4. `Registry.process` invokes the topic handler with `WebhookMetadata.new(... shop: request.shop ...)`, where `request.shop` is now `"victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own store.
