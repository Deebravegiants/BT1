### Title
Webhook shop/topic attribution not bound by HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, then dispatches business logic using the `shop-domain`, `topic`, and `webhook-id` HTTP headers taken verbatim, without those fields ever being part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) 

`to_signable_string` returns only `@raw_body`, while `shop`, `topic`, and `webhook_id` are read directly from HTTP headers (`shop-domain`, `topic`, `webhook-id`) that are never included in the signed string. `Utils::HmacValidator.validate` only recomputes and compares the HMAC over `to_signable_string`: [2](#0-1) 

`Registry.process` trusts this validation, then uses the unauthenticated header values to build the dispatched metadata: [3](#0-2) 

The identity binding the gem should be enforcing is: `shop header == shop cryptographically bound to this exact webhook payload`. Instead the gem enforces only `HMAC(raw_body) == signature`, leaving `shop`, `topic`, and `webhook_id` completely outside the authenticated boundary. Because the app's `client_secret` (used to compute webhook HMACs) is shared across every shop that installs the app, any two genuine webhook deliveries produced by Shopify for the same app share the same signing key. An attacker who has legitimately installed the app on their own store (an "unprivileged" party with respect to any other tenant of the same app) receives real, validly-signed webhooks for their own shop. They can take a captured `(raw_body, hmac)` pair from one of their own real deliveries and replay it to the app's public webhook endpoint while substituting the `shop-domain` (and/or `topic`/`webhook-id`) header with a different, victim shop's domain. `Utils::HmacValidator.validate` still passes because it never inspected those headers, and `Registry.process` will invoke the registered handler with `shop: <victim shop>` and the attacker-controlled body, causing the app to process/attribute the event to a tenant that never sent it.

### Impact Explanation
This breaks the identity binding between the authenticated bytes (`raw_body` + HMAC) and the tenant identifier the application acts on (`shop` header), allowing a low-privilege actor (any merchant who can install the app once) to inject or misattribute webhook events for arbitrary other shops using the same app. Depending on the handler logic, this enables cross-tenant data injection or spoofed lifecycle events (e.g., forging `shop/redact`, `app/uninstalled`, order/customer events) attributed to a shop the attacker does not control — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-controlled store to receive at least one genuine webhook, and (2) sending a crafted HTTP request with swapped headers to the app's public webhook endpoint. No access to `api_secret_key`, access tokens, or privileged accounts is required, making this reachable by any ordinary internet user who can install a public app.

### Recommendation
Include the identifying fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed/verified material, or independently verify that the `shop-domain` header corresponds to a shop with a stored, previously-issued session/access token before trusting it for dispatch, rather than trusting header values that fall outside the HMAC's coverage.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook to the app's endpoint:
   - Headers: `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC of body>`
   - Body: `{"id": 1, ...}`
3. Attacker replays this exact body and HMAC header to the same endpoint but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and optionally `X-Shopify-Topic` to another registered topic supported by the app).
4. `Utils::HmacValidator.validate(request)` in [4](#0-3)  passes because it only checks `raw_body` against the unchanged HMAC.
5. `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"`, causing the app to process a forged event as if it originated from the victim tenant.
