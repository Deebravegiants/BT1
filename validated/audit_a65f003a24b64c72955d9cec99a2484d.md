### Title
Unchecked subtraction panic in `swap_token_amount_base_out` allows an attacker to crash a swap-base-out transaction before slippage/liquidity checks run - ([File: program/src/math.rs])

### Summary
`process_swap_base_out` (and the `_v2` variant) computes the required input amount by calling `Calculator::swap_token_amount_base_out` **before** it validates that `swap.amount_out` is actually less than the pool's available liquidity. Inside that math routine, the denominator is computed with `total_pc_without_take_pnl.checked_sub(amount_out).unwrap()` (or the coin equivalent), which panics whenever the attacker-supplied `amount_out` is greater than or equal to the pool reserve, instead of returning a controlled `AmmError`.

### Finding Description
In `swap_token_amount_base_out`:

This function is invoked from `process_swap_base_out`/`process_swap_base_out_v2` with `swap.amount_out` taken directly from the instruction data, before the existing safety check `if swap.amount_out >= total_pc_without_take_pnl { return Err(AmmError::InsufficientFunds) }` is reached:

...
program/src/processor.rs:2593   if swap.amount_out >= total_pc_without_take_pnl { ... }
``` [2](#0-1) 

Because `checked_sub` returns `None` (rather than a valid, negative "fragment size") when `amount_out >= total_pc_without_take_pnl`, and the code immediately `.unwrap()`s that `Option`, the calculation aborts the whole transaction with a Rust panic/`unwrap` failure rather than a graceful program error. This mirrors the CVE-2021-29264 bug class: an attacker-influenced value drives an unchecked arithmetic subtraction that can go out of range, and the resulting invalid value is consumed further down the pipeline without validation, leading to a crash rather than controlled error handling. The out-of-order check placement (compute-first, validate-second) is the direct root cause — the existing bounds check exists in the code but is placed *after* the vulnerable subtraction.

### Impact Explanation
Any unprivileged swapper can submit a single `SwapBaseOut`/`SwapBaseOut2` transaction with an `amount_out` greater than or equal to `total_pc_without_take_pnl` (or `total_coin_without_take_pnl` for the reverse direction). This causes the on-chain program to panic during instruction execution instead of returning a normal `ProgramError`. On Solana, a panic inside program execution is caught by the runtime and simply fails the transaction (no state corruption, no funds lost, no validator crash), so the practical effect is a failed transaction with a less user-friendly failure mode (a raw panic/log instead of a typed `AmmError`), not permanent freezing of funds, theft, or insolvent accounting.

### Likelihood Explanation
Trivial to trigger — a single transaction with attacker-chosen `amount_out` reaches this path unconditionally for the swap-base-out instructions, with no privileged signer or special state required.

### Recommendation
Move the `swap.amount_out >= total_pc_without_take_pnl` / `total_coin_without_take_pnl` bounds check before calling `Calculator::swap_token_amount_base_out`, or change the internal `checked_sub(...).unwrap()` calls to propagate a proper `AmmError` (e.g., `ok_or(AmmError::InsufficientFunds)?`) instead of panicking.

### Proof of Concept
1. Create/observe a pool with `total_pc_without_take_pnl = P`.
2. Submit `SwapBaseOut` with `swap_direction = Coin2PC` and `swap.amount_out = P` (or greater).
3. `process_swap_base_out` calls `Calculator::swap_token_amount_base_out` first, which executes `total_pc_without_take_pnl.checked_sub(amount_out)` → `None` → `.unwrap()` panics, aborting the transaction before the existing `InsufficientFunds` guard at `program/src/processor.rs:2593` is ever reached.

Note: I was unable to fully confirm within the available iterations whether this panic path could be chained with any other state to produce a stronger, funds-impacting effect (e.g., permanent freezing via repeated forced panics in a particular pool state); based on the code reviewed, the observable effect is a failed transaction, which does not meet the required bar of concrete theft, permanent freezing, unbacked LP minting, or insolvent accounting.
