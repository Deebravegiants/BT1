### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) fields are trusted but not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers and passed straight to the app's webhook handler. This breaks the intended binding: `hmac_valid == true` should imply the header-derived shop/topic identity is trustworthy, but in this implementation `hmac_valid` only proves the raw body is untampered, not that the `shop` header matches the shop that produced that body.

### Finding Description
`Registry.process` verifies the webhook solely via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` calls `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only `@raw_body`: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled directly from request headers with no cryptographic binding to the signed body: [3](#0-2) 

These unauthenticated fields are then forwarded verbatim to the app's registered handler as trusted identity data: [4](#0-3) 

Because `shop` is "a field acted on but not covered by the HMAC," any party who can produce (or replay/capture) one valid `(raw_body, hmac)` pair signed with the app's secret can resubmit that same body with an arbitrary `X-Shopify-Shop-Domain` header value, and the gem will report it as a validated webhook for that attacker-chosen shop. For a multi-tenant app that keys per-shop side effects (order processing, data writes, entitlement changes) off `WebhookMetadata#shop`, this is a cross-tenant identity confusion: data legitimately produced for shop A can be attributed to shop B purely by header manipulation, with no invalidation of the HMAC check.

### Impact Explanation
This maps to the Critical "cross-tenant access" category: the shop identity that the host application relies on (`data.shop` in the handler) is not bound to the cryptographic proof (`hmac`) that the gem reports as valid. An app built on the documented `ShopifyAPI::Webhooks::Registry.process` / handler API has no way to detect the mismatch, since the gem's own validation step returns success.

### Likelihood Explanation
Exploitation requires the webhook endpoint to be reachable and a valid `(body, hmac)` pair for the target app's secret (e.g., captured from any one legitimate webhook delivery, which travels over plain HTTP headers/body distinguishable from the header set) to be replayable with a modified shop-domain header. This is a realistic scenario for apps that expose a single shared webhook endpoint across many installed shops, which is the common multi-tenant pattern this gem's `Webhooks` module is designed for.

### Recommendation
Include `shop` (and ideally `topic`) in the value that is verified, or otherwise cryptographically/contextually bind the header-derived shop to the specific installation before dispatching to the handler—for example, by validating that `request.shop` corresponds to a session/shop the app actually has on record for the delivered `webhook_id`/topic, in addition to the raw-body HMAC check.

### Proof of Concept
1. Capture one legitimate webhook delivery for `shop-a.myshopify.com`: raw body `B` and its valid header `X-Shopify-Hmac-Sha256` computed over `B` with the app's `api_secret_key`.
2. Replay a POST to the app's webhook endpoint with the identical body `B` and identical HMAC header, but set `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `shop-b.myshopify.com`; `Utils::HmacValidator.validate` succeeds because it only checks `B` against the HMAC (`to_signable_string` returns `@raw_body`, per `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: parsed(B), ...)`, causing the app to process shop A's webhook payload as if it belonged to shop B.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
