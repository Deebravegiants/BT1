### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` (tenant identity), `topic`, and `webhook_id` fields are read straight from HTTP headers that are never included in the signed content. `Registry.process` accepts any request whose body-only HMAC validates and then hands the caller-supplied `shop` header directly to the app's `WebhookHandler#handle` via `WebhookMetadata`, without ever validating that the `shop` value is bound to the signed payload.

### Finding Description
The webhook verification flow is:

1. `HmacValidator.validate(request)` computes `HMAC(secret, request.to_signable_string)` and compares it to the `hmac-sha256`/`x-shopify-hmac-sha256` header value. [2](#0-1) 
2. `Request#to_signable_string` returns only `@raw_body` — it never includes `shop`, `topic`, or `webhook_id`. [3](#0-2) 
3. `Request#shop` is read directly and unverified from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header. [4](#0-3) 
4. `Registry.process` only checks `Utils::HmacValidator.validate(request)` (a body-only check) before dispatching to the handler with `request.shop` as the trusted tenant identifier. [5](#0-4) 

This breaks the intended identity binding: `HMAC-verified bytes == authenticated shop`. In reality, `HMAC-verified bytes == raw_body only`, and `shop` is an attacker-controllable header that rides along unauthenticated. Any unprivileged internet user who can obtain one *valid* signed webhook body/HMAC pair for **any** shop/topic combination they control (e.g., their own free development/partner test store, which anyone can create and freely install the app on to generate legitimate webhook deliveries) can replay that exact body+HMAC to the app's public webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. The HMAC check passes (it only covers the unchanged body), and the app's handler receives `WebhookMetadata#shop` populated with the victim shop's domain, causing the application to process a forged event as if it originated from the victim tenant.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker-controlled request can cause an app to attribute webhook data/events to a shop the attacker does not control and was never sent by Shopify for that shop. Depending on how the host app uses `WebhookMetadata#shop` (e.g., topics like `app/uninstalled`, `shop/update`, `customers/data_request`, or generic topics with static/predictable bodies such as empty `{}` payloads), this can drive the app into taking tenant-scoped actions (deleting session/shop records, marking a shop uninstalled, triggering data-erasure flows, etc.) against a victim shop's data using only a replayed body that was legitimately signed for a different (attacker-owned) shop. This matches the "cross-tenant access" high-impact category since the shop identity binding that the app relies on from this gem is not actually authenticated by the gem.

### Likelihood Explanation
Likelihood is realistic but not trivial: the attacker needs at least one genuine `(raw_body, hmac)` pair, which they can readily obtain by installing the app on their own free Shopify development store and observing/capturing any webhook delivery (many webhook topics, including the mandatory `shop/redact`, `customers/redact`, `customers/data_request`, produce very generic or empty bodies, making this attainable). No `client_secret` or access token is required — the attacker only needs network access to the app's public webhook endpoint and a self-controlled Shopify store to source a valid signature.

### Recommendation
Do not treat `Request#shop`, `#topic`, or `#webhook_id` header values as authenticated. Either:
- Include the `shop`, `topic`, and `webhook_id` header values in the signed material used for signature computation/verification (this would require matching Shopify's actual signing scheme, so at minimum this should be verified against Shopify's own documented behavior), or
- Explicitly document that consuming applications must independently verify `WebhookMetadata#shop` against their own list of currently-installed/authorized shops before acting on the delivered data, and consider raising/flagging when the header-derived shop cannot be corroborated.

### Proof of Concept
1. Install the target app on an attacker-owned Shopify development store `attacker-shop.myshopify.com`; trigger/capture a webhook delivery for a topic with a static or empty body, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: customers/data_request
   x-shopify-hmac-sha256: <valid-hmac-for-body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: {}
   ```
2. Replay the exact same body and `x-shopify-hmac-sha256` value, but change the shop header to the victim:
   ```
   POST /webhooks
   x-shopify-topic: customers/data_request
   x-shopify-hmac-sha256: <same-valid-hmac-for-body>
   x-shopify-shop-domain: victim-shop.myshopify.com
   Body: {}
   ```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-computes the HMAC over `request.to_signable_string` (`@raw_body`, unchanged) — validation succeeds. [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(topic: "customers/data_request", shop: "victim-shop.myshopify.com", ...)`, i.e., the app processes a forged data-request/redaction-style event as if Shopify sent it for the victim shop. [7](#0-6)
