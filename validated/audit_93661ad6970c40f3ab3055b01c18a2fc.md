### Title
Webhook shop identity not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop` (tenant) identity that the dispatcher trusts and hands to the app's webhook handler is read from an HTTP header that is never included in that signed content. Since `Utils::HmacValidator` only proves that *the body* was signed with the app's shared `api_secret_key`, it proves nothing about which shop the request claims to be from. Any party who can obtain one validly-signed webhook delivery for the app (e.g., by installing the app on their own store) can replay that exact body/HMAC pair while substituting an arbitrary `x-shopify-shop-domain` header, causing the app to process the event as if it came from a different, victim tenant.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop` is populated straight from the `shop-domain` header with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC strictly against `to_signable_string` (i.e., the body), never the headers: [3](#0-2) 

`Registry.process` treats a passing HMAC check as authorization to trust the entire `request`, including `request.shop`, and forwards it as the authoritative tenant identity to the app-supplied handler: [4](#0-3) 

The identity binding this code implicitly assumes is: `hmac_valid(body) == shop_header_is_authentic`. That equality does not hold — the same app uses one shared `api_secret_key` across all of its installed shops (this is the OAuth `client_secret`, not a per-shop secret), so any tenant who has legitimately triggered a webhook to their own installation possesses a body+HMAC pair that is valid for *any* shop, and can re-submit it with a different `shop-domain` header value. The gem performs no check that the header-derived `shop` is consistent with anything cryptographically tied to the signature.

### Impact Explanation
This breaks the cross-tenant boundary the gem is expected to enforce for webhook processing: an app relying on `WebhookMetadata#shop` (as built in `registry.rb`) to select which tenant's data to mutate, delete, or act upon can be tricked into performing that action against a different, arbitrary shop, since the "authenticated" request's shop attribution is forgeable by any party who can produce one valid signed body for the app (trivially available to any merchant/attacker who installs the app on their own store or reuses a leaked/observed prior delivery). This is a cross-tenant access primitive — Critical impact per the defined criteria.

### Likelihood Explanation
Likelihood is meaningful but not universal: exploitation requires the attacker to already have one valid (body, HMAC) pair for the target app (obtainable by installing the app themselves and capturing/replaying their own webhook delivery, or observing a previously delivered webhook), and requires the app's webhook handling logic to key its downstream side effects primarily off `WebhookMetadata#shop` rather than independently re-deriving/confirming tenant context. Given that the library's own documented `WebhookMetadata` explicitly exposes `shop` as a trusted field to handlers, and many topics (e.g., `app/uninstalled`, or any generic/empty-body topic) have body content that carries no shop-specific data, this is a realistic replay scenario without needing the `api_secret_key` to be otherwise leaked.

### Recommendation
Bind the shop identity to the HMAC verification: include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) headers in the value that is HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to the signed payload, before it is trusted and handed to `handler.handle`. At minimum, document loudly that `request.shop` is unauthenticated header data and must not be used by host applications as a sole tenant-selection key without additional verification (e.g., cross-checking it against the shop tied to the offline access token used to look up session/context for that webhook).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, obtaining the app's normal webhook flow.
2. Attacker triggers/observes a legitimately delivered webhook whose body is generic (e.g. an empty-body test topic or a topic like `app/uninstalled` with shop-agnostic body), capturing the exact `raw_body` and its valid `x-shopify-hmac-sha256` value (computed by Shopify using the app's shared `client_secret`).
3. Attacker resends this exact `raw_body` + `x-shopify-hmac-sha256` pair to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` at [3](#0-2)  passes because it only checks the body's HMAC.
5. `Registry.process` at [4](#0-3)  dispatches to the handler with `shop: "victim.myshopify.com"`, causing the app to act on the victim tenant using attacker-controlled body content.
