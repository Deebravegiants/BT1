### Title
Webhook shop-domain header not bound by HMAC, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the raw request body against the `X-Shopify-Hmac-Sha256` header, but the tenant identifier (`shop`) that the handler receives and acts on is taken from a separate, unsigned header (`X-Shopify-Shop-Domain`). Because the HMAC only covers the body bytes, any request carrying a validly-signed body can be paired with an attacker-chosen shop domain header and will still pass validation, letting the host application process the webhook under the wrong tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, entirely independent of the signed payload: [2](#0-1) 

`Registry.process` verifies the HMAC and, if valid, immediately builds `WebhookMetadata` using `request.shop` (the unsigned header) as the tenant identifier passed to the handler: [3](#0-2) 

`WebhookMetadata.shop` is the only tenant-scoping field handed to the app's `WebhookHandler#handle`: [4](#0-3) 

The identity binding that should hold is:
`shop header value used for tenant routing == shop covered by the HMAC-signed bytes`

Instead, the code only checks:
`HMAC(raw_body, api_secret_key) == received_hmac`

with no cryptographic tie between `raw_body` and `shop`. Consequently:
- Before the attacker's action: a legitimate webhook delivery for shop A has `raw_body` (signed) and header `shop-domain: A.myshopify.com` (unsigned).
- After the attacker's action: the same `raw_body` + valid `hmac` is replayed to the app's public webhook endpoint with `shop-domain: B.myshopify.com` substituted.
- `HmacValidator.validate` still returns `true` (it only checks `raw_body`), and `Registry.process` dispatches to the handler with `shop: "B.myshopify.com"`, `body` unchanged.

Any entity that can install the app on their own store (an "unprivileged" party from the app's perspective — no special credentials beyond installing a public app) receives real, validly-HMAC-signed webhook deliveries for their own shop's events. They can then replay that exact signed body to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header for a victim shop's domain, since this gem performs no binding between the two.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook processing: an attacker can make the host application believe attacker-controlled, validly-signed webhook content originated from a different, victim merchant's shop. Depending on how the host app's `WebhookHandler` uses `WebhookMetadata#shop` (e.g., looking up the shop's session/access token, writing records keyed by shop, or triggering shop-scoped side effects), this enables cross-tenant data confusion/write using the attacker's own signed traffic — a cross-tenant access issue directly caused by an identity field (`shop`) not being covered by the cryptographic authenticity check.

### Likelihood Explanation
Any user who can install the app on their own shop (the normal, unprivileged installation flow for a public app) can capture one legitimate signed webhook body+HMAC pair for their own store and immediately reuse it against the shared webhook endpoint with an arbitrary victim shop-domain header. No access token, `client_secret`, or privileged access is required — only receipt of one webhook for their own tenant, which is trivial to trigger (e.g., updating one of their own orders).

### Recommendation
Bind the shop identity into the value that is actually authenticated. Options:
- Include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in `to_signable_string` so the HMAC covers them, if Shopify's webhook signing scheme allows a canonicalized string combining headers and body; or
- After HMAC validation, cross-check `request.shop` against an expected/allow-listed shop for the receiving endpoint (e.g., validate it corresponds to a shop with a stored session before dispatching), rather than trusting the header verbatim; or
- Document explicitly (and enforce in `Registry.process`) that `request.shop` must never be used as an authorization/tenant-scoping key without an independent lookup tied to a stored, previously-authenticated session for that shop.

### Proof of Concept
1. Attacker installs the target public app on their own store `attacker.myshopify.com` and triggers a real event (e.g., updates an order) so Shopify delivers a legitimate webhook to the app's endpoint with headers:
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - `X-Shopify-Hmac-Sha256: <valid HMAC of raw_body>`
   - `raw_body: <JSON payload>`
2. Attacker intercepts/replays this exact HTTP request to the same public endpoint, only changing the header to:
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
3. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against `hmac` — both unchanged and still valid: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's payload>, ...)` and processes it as if it were an authentic event for `victim.myshopify.com`.

          unless handler

        end
