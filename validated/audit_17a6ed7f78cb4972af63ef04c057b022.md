### Title
Emporium's `signerAddress != address(0)` path in `payRelayFees` skips variable-rate relay-fee scaling, letting any attacker permanently underpay protocol fees - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`payRelayFees` charges `relayFee = $._hinkalHelper.calculateRelayFee(sumAbs, flatFee, feeStructure.variableRate)` only when `signerAddress == address(0)`, but simply sets `relayFee = flatFee` (no variable-rate component at all) when `signerAddress != address(0)`. Because `stack.signerAddress` is fully attacker-controlled — any unprivileged EOA can deploy their own `IHinkalWallet`-compliant contract and self-sign the `EMPORIUM_SIGNATURE_TYPEHASH` message with their own key — an attacker can always choose the non-zero-signer path to withdraw arbitrarily large `sumAbs` amounts through `runAction` while paying only the flat fee, indefinitely avoiding the volume-proportional relay fee.

### Finding Description
The broken equality is:
`relayFee_expected(sumAbs) = flatFee + variableRate * sumAbs` (as enforced in the `signerAddress == address(0)` branch via `calculateRelayFee` at [1](#0-0) )
vs.
`relayFee_charged = flatFee` when `signerAddress != address(0)`.

`runAction` calls `verifyWallet(stack, circomData)` which, for a non-zero `signerAddress`, only validates that the EIP-712 signature over `EMPORIUM_SIGNATURE_TYPEHASH` recovers to `stack.signerAddress`, that the deadline hasn't passed, and that `feeStructure.flatFee <= stack.maxFee` [2](#0-1) . There is no check that `signerAddress` corresponds to a protocol-deployed or whitelisted wallet, nor any check on `variableRate`. `IHinkalWallet` is a bare interface (`callHinkalWallet`, `doSendToRelay`, `isValidSignature`) [3](#0-2) , and the reference implementation `HinkalWallet.sol` shows nothing more than an `onlyEmporium`-gated relay/pass-through contract that any attacker could redeploy for themselves and control the ECDSA key of [4](#0-3) . Nothing in `runAction`/`payRelayFees`/`verifyWallet` restricts `signerAddress` to any pre-registered or trusted contract — it's simply whatever address the attacker signs for and deploys.

Attacker flow: deploy a minimal `IHinkalWallet` contract, sign `EMPORIUM_SIGNATURE_TYPEHASH` with their own EOA key (`stack.signerAddress` = their own contract/EOA), submit a `circomData`/`deltaAmountChanges` that withdraws a large `sumAbs` from Emporium with `feeStructure.variableRate > 0`. In `payRelayFees`, `isFeeToken` is true, `signerAddress != address(0)` so `relayFee = flatFee` only (line 236), and `payRelay` → `sendToRelayFromWallet` → `IHinkalWallet(signerAddress).doSendToRelay(...)` sends only `flatFee` regardless of `sumAbs` [5](#0-4) .

None of the guards mentioned in the audit checklist (`performHinkalChecks`, `verifyProof`, `rootHashExists`, nullifier insertion, circuit constraints) touch relay-fee computation; the divergence is a pure Solidity fee-schedule branch defect, not a proof/circuit issue.

### Impact Explanation
This causes permanent underpayment of protocol/relay fee revenue. The fee owed under the intended fee schedule scales with withdrawal size via `variableRate`, but any attacker can route unlimited withdrawal volume through the `signerAddress != address(0)` path and pay only the fixed `flatFee`, regardless of `sumAbs`. This matches the "High" impact category (theft or permanent freezing of protocol/relay fees) and is fully repeatable per-transaction with no bound on `sumAbs`.

### Likelihood Explanation
The attacker needs only to: (1) deploy a trivial contract implementing `IHinkalWallet`, (2) sign the `EMPORIUM_SIGNATURE_TYPEHASH` message with their own private key (self-authorized, no third party involved), and (3) set `feeStructure.variableRate > 0` and `flatFee <= maxFee`. All of these are fully within the capabilities of an unprivileged EOA as defined by the ruleset. There is no cost or gate preventing this beyond normal gas/deployment cost, and it can be repeated for every Emporium withdrawal.

### Recommendation
Apply the same `calculateRelayFee` (flat + variable-rate scaling on `sumAbs`) regardless of whether `signerAddress` is zero or not, i.e., unify the fee computation in `payRelayFees` so the `signerAddress != address(0)` branch also computes `relayFee = $._hinkalHelper.calculateRelayFee(sumAbs, flatFee, feeStructure.variableRate)` before dispatching via `sendToRelayFromWallet`.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a fee-token ERC20, a `RelayStore`/relay address, and a minimal attacker-controlled `IHinkalWallet` contract with a known EOA-controlled signer key.
2. Fund Emporium/attacker UTXO path so two functionally identical large withdrawals of `sumAbs` (e.g., 1,000,000 tokens) can be executed, with `feeStructure.variableRate` set to a nonzero value and identical `flatFee` in both cases.
3. Test A: call `runAction`/`transact` with `stack.signerAddress = address(0)`; record relay's fee-token balance delta — assert it equals `calculateRelayFee(sumAbs, flatFee, variableRate)` (flat + variable component).
4. Test B: call `runAction`/`transact` with `stack.signerAddress` = attacker's self-deployed wallet contract and a valid self-signature over `EMPORIUM_SIGNATURE_TYPEHASH`; record relay's fee-token balance delta — assert it equals only `flatFee`.
5. Assert `deltaB < deltaA` for the same `sumAbs`/`variableRate`, proving the variable-rate portion is skipped entirely in the signer-controlled path.

    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }

        if (block.timestamp > stack.deadline) {
            revert SignatureExpired();
        }

        if (circomData.feeStructure.flatFee > stack.maxFee) {
            revert FeeExceedsSignedMax();
        }
    }

contract HinkalWallet is Transferer, IHinkalWallet {
    address public immutable emporium;

    event EthReceivedOnWallet(address indexed sender, uint256 amount);

    error NotAllowedToCallWallet();

    constructor(address _emporium) {
        emporium = _emporium;
    }

    modifier onlyEmporium() {
        if (msg.sender != emporium) {
            revert NotAllowedToCallWallet();
        }
        _;
    }

    function callHinkalWallet(
        address endpoint,
        bytes calldata data,
        uint value
    ) external onlyEmporium returns (bool success, bytes memory err) {
        (success, err) = endpoint.call{value: value}(data);
    }

    function doSendToRelay(
        address relay,
        uint256 actualAmount,
        address erc20TokenAddress
    ) external onlyEmporium {
        sendToRelay(relay, actualAmount, erc20TokenAddress);
    }
