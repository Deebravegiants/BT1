Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, and `ShopifyAPI::Utils::HmacValidator.validate` only checks that HMAC against the body. The `shop` (`x-shopify-shop-domain`/`shopify-shop-domain`) header, which `ShopifyAPI::Webhooks::Registry.process` treats as the authenticated tenant identifier passed to the host app's handler, is never included in the signed material. This breaks the intended equality `hmac_verified_bytes == bytes_the_app_trusts_for_tenant_identity`.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

`to_signable_string` returns only `@raw_body`. `shop` is read straight from the `shop-domain` header with no cryptographic binding to the HMAC: [2](#0-1) 

`HmacValidator.validate` verifies the signature strictly against `to_signable_string` (i.e., the body), never against headers: [3](#0-2) 

`Registry.process` accepts any request whose body-HMAC checks out, then forwards `request.shop` (attacker-controlled header, unverified) as the trusted tenant identity to the app's `WebhookHandler#handle`: [4](#0-3) 

`WebhookMetadata.shop` is the field host applications use to look up/act on tenant data: [5](#0-4) 

Equality that should hold but doesn't: `shop_bound_by_hmac == shop_delivered_to_handler`. In reality, `shop_bound_by_hmac` is undefined (the HMAC binds nothing about shop), while `shop_delivered_to_handler` is taken verbatim from an attacker-settable header.

### Impact Explanation
An unprivileged internet user who controls (or has installed the app on) any Shopify store receives genuine webhooks for their own shop, each with a valid HMAC computed over that specific body. Because the signature covers only the body and not the `shop-domain` header, the attacker can replay the exact same body + HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds (body unchanged), so `Registry.process` dispatches the webhook to the app's handler with `WebhookMetadata#shop` set to the victim's domain. Any host application that uses this library's `shop` field as the tenant key (the documented, intended usage) will process attacker-supplied data/events under the wrong tenant — a cross-tenant confusion/injection primitive (e.g., triggering `customers/redact`-style data deletion, order/inventory updates, or app-state mutations against a shop the attacker doesn't own). This matches the High-impact "cross-tenant access" criterion, since it crosses a tenant boundary using only a header the gem fails to authenticate.

### Likelihood Explanation
Requires no secrets, tokens, or privileged access — only the ability to install the target app on any (even a free/dev) store to obtain one legitimately-signed webhook body/HMAC pair, and the ability to POST to the app's public webhook endpoint with a modified header. This is fully reachable by an unprivileged internet user through the gem's own webhook-processing API (`Registry.process`), not by the host app misusing/ignoring documented behavior — the gem itself hands back an unauthenticated `shop` value labeled as verified metadata.

### Recommendation
Include the shop-domain (and ideally topic/api-version) in the HMAC-signed material, or otherwise cryptographically bind the shop identity to the signed payload before exposing it via `WebhookMetadata`. Short term, document that `Request#shop`/`WebhookMetadata#shop` is not currently covered by the HMAC and must not be trusted as an authenticated tenant identifier without additional verification (e.g., cross-checking against a known/installed shop list). Long term, extend `to_signable_string` (or add a parallel signed-headers check) so that `HmacValidator.validate` fails if the shop header has been tampered with relative to the originally signed request.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (any store, no privileges beyond normal merchant signup) and triggers an event that fires a registered webhook topic (e.g., `orders/create`).
2. Attacker's endpoint (or a proxy they control) captures the raw POST: body `B`, and headers including `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's real secret) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker crafts a new POST to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. Server-side, the app calls `ShopifyAPI::Webhooks::Registry.process(request)`. `Utils::HmacValidator.validate(request)` passes because it only checks `H` against `B` per: [6](#0-5) 
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)`, per: [7](#0-6) 
6. The host app, trusting `data.shop` as verified (as documented/intended), performs an action against `victim-shop.myshopify.com`'s tenant data using attacker-controlled body content — a cross-tenant write/action performed without any credential belonging to the victim.
