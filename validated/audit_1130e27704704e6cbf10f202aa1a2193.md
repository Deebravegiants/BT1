## Analysis

I searched extensively across `packages/intents-sdk/src`, `packages/internal-utils/src`, and `packages/crosschain-assetid/src` for equality-breaking bugs analogous to the reported truncated-counter bug (signed payload tampering, amount/fee mismatches, wrong-address delivery, bridge mis-selection, replayed signatures, and status/hash misreporting). The reachable finding is a status-matching flaw in `PoaBridge.describeWithdrawal`.

### Title
Withdrawal status/tx-hash misattribution when multiple same-asset withdrawals are batched in one NEAR transaction - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` matches the PoA bridge's withdrawal status response to a specific withdrawal **by `assetId` alone**, not by the withdrawal's `index`, because the API's response list is unsorted: [1](#0-0) 

### Finding Description
`describeWithdrawal` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` to locate the withdrawal record corresponding to a given `WithdrawalIdentifier`. The comment explicitly states: "Response list is unsorted, so we match by assetId instead of index." When a single NEAR transaction contains **two or more withdrawals of the same asset** (e.g. `createWithdrawalIdentifiers` assigns separate `index` values per bridge/route for a batch of withdrawal intents, as seen in `withdrawal-watcher.ts`), each `WithdrawalIdentifier` for that asset differs only by `index`/`destinationAddress`/`amount`, but the lookup key passed to the PoA bridge is only the `assetId`. If the matching function returns the first (or any single) result for that asset, both `describeWithdrawal` calls (for index 0 and index 1) can return the identical `status`/`txHash`, even though they refer to two different, independent transfers.

This breaks the "status reported equals the actual on-chain outcome for *that specific withdrawal*" invariant: a caller (integrator, watcher, ledger) polling withdrawal B's status via `watchWithdrawal` could receive withdrawal A's `completed` status and `txHash`, incorrectly concluding that B's funds have landed when in fact A's did (or B's is still pending/failed).

### Impact Explanation
An integrator relying on `describeWithdrawal`/`watchWithdrawal` per-withdrawal status to decide when to credit a user, release escrow, or mark a batch entry complete could be induced to treat a still-pending or distinct withdrawal as completed with a borrowed `txHash`. This matches the allowed High-impact class: "a status or hash misreport making an integrator credit or refund twice." No malicious actor input is required — an ordinary user submitting two same-asset withdrawals in one tx (a supported, unprivileged flow via `createWithdrawalIdentifiers`) can trigger the misattribution.

### Likelihood Explanation
Requires: (1) a batch of withdrawals containing ≥2 entries with the same `assetId` routed through the PoA bridge, and (2) the underlying PoA API returning an unsorted/ambiguous list where `findMatchingWithdrawal` cannot disambiguate by `index`. This is plausible in normal SDK usage since `IntentsSDK`/`createWithdrawalIdentifiers` explicitly supports multiple withdrawals per transaction and assigns sequential indices without asserting per-route asset uniqueness.

### Recommendation
Disambiguate matching in `findMatchingWithdrawal` using additional fields available on both the `WithdrawalIdentifier` and the PoA response (e.g., `destinationAddress`, `amount`, and the withdrawal's position/order) instead of `assetId` alone, or require the PoA API to return records taggable by a unique per-withdrawal identifier so each `index` maps deterministically to exactly one record.

### Proof of Concept
Note: I could not view the full body of `findMatchingWithdrawal` (only its call site and the disambiguation comment were available in the indexed context), so I cannot show the exact matching logic that causes duplicate returns; this should be verified directly in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` (both reference `findMatchingWithdrawal`) before treating this as fully confirmed. Conceptually:
1. Submit a NEAR transaction with two `ft_withdraw` intents for the same `assetId` (e.g., `nep141:btc.omft.near`) to two different destination addresses.
2. `createWithdrawalIdentifiers` assigns `index: 0` and `index: 1` to the two `WithdrawalIdentifier`s for the `PoaBridge` route.
3. Call `describeWithdrawal` for both identifiers while only one of the two underlying transfers has completed on the PoA side.
4. If `findMatchingWithdrawal` returns the same (first) record for both calls (since it keys only on `assetId`), both `describeWithdrawal` invocations report `{ status: "completed", txHash: <same hash> }`, even though only one withdrawal actually completed. [2](#0-1)

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
