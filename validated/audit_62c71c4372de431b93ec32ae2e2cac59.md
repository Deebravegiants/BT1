### Title
Session hijacking via predictable, unauthenticated session-cookie-derived session ID — ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` derives the session identifier used to look up a merchant's stored `Session` (containing the access token) directly from the raw, unauthenticated `shopify_app_session` cookie value, for both the embedded-cookie-fallback path and the entire non-embedded flow. That cookie value is never a random secret — it is set, at OAuth completion, to the deterministic, publicly-derivable session ID string (`offline_<shop>` or `<shop>_<associated_user_id>`), and it is trusted verbatim with no HMAC/signature check binding it to the actual completed OAuth exchange.

### Finding Description
The binding that should hold is:
`session_id trusted by the host app == session_id cryptographically proven to have completed OAuth for that shop`

In this gem, that equality is broken:

- On `validate_auth_callback` completion, the non-embedded cookie is created as `SessionCookie.new(value: session.id, ...)` [1](#0-0)  where `session.id` for offline sessions is the fully deterministic string `"offline_#{shop}"`, and for online sessions `"#{shop}_#{associated_user.id}"` [2](#0-1) .
- Later, `SessionUtils.current_session_id` reads this identifier straight back out of the incoming request's cookies with **no cryptographic verification** of the cookie's authenticity — it is neither HMAC-signed nor tied to any server-side secret: [3](#0-2) 
- The raw lookup is performed by `cookie_session_id`, which just echoes back `cookies[SESSION_COOKIE_NAME]` verbatim: [4](#0-3) 

Because the ID format (`offline_<shop>` / `<shop>_<user_id>`) is documented and predictable, and the cookie carrying it is not signed by this gem, any client can set this cookie to an arbitrary value of that form. Host applications are expected to use the value returned by `current_session_id` as the lookup key into their own persistent session store (per the gem's documented `SessionRepository` pattern) to retrieve the corresponding `Session` object — including its `access_token` — for use in subsequent authenticated API calls. The gem provides no mechanism to prove that the party presenting the cookie is the same party for whom that session was created; it treats "bytes present in an incoming cookie" as equivalent to "proof of a completed OAuth handshake for that shop."

### Impact Explanation
An unprivileged internet user (e.g., someone who has installed the app on their own throwaway shop, or simply crafts an HTTP request with a forged cookie) can set the `shopify_app_session` cookie to `offline_<victim-shop>.myshopify.com` (or `<victim-shop>.myshopify.com_<user_id>` for online tokens, where user IDs are small integers or otherwise enumerable). If the host application's session storage is keyed exactly by this identifier — as the gem's documented pattern intends — the attacker's request will resolve to the victim shop's stored `Session`, and any authenticated API call made using that session will run with the victim's `access_token`. This is a cross-tenant session hijack / token theft, since it exposes another merchant's access token and permits acting on their store data. This satisfies the Critical bar: cross-tenant access and theft of a merchant access token.

### Likelihood Explanation
Likelihood is high wherever a host app follows the gem's documented cookie/session-id pattern faithfully (the flow shown in `docs/usage/oauth.md`), since:
- The session ID format is not a secret — it's derived purely from the shop domain (and possibly a low-entropy numeric user ID), both of which are typically public or easily guessable.
- No part of this gem signs, encrypts, or otherwise authenticates the cookie value before treating it as trusted input.
- Exploitation needs no access token, no `client_secret`, and no elevated privileges — only the ability to set an arbitrary cookie value on a request to the host app, which is trivially available to any internet user.

### Recommendation
`SessionUtils` should not treat the raw cookie payload as a trustworthy, semantically meaningful session identifier. Either:
1. Bind the cookie value to the session via an HMAC computed with `Context.api_secret_key` (similar to `Utils::HmacValidator`) and verify that HMAC in `cookie_session_id`/`current_session_id` before returning the ID, or
2. Replace the deterministic `offline_<shop>` / `<shop>_<user_id>` scheme with a non-deterministic, high-entropy session ID (e.g. `SecureRandom.uuid`, which `Session#initialize` already supports) and always issue that as the cookie value rather than the predictable one used in `Session.from`.

### Proof of Concept
1. Deploy an app using this gem's documented offline OAuth flow for shop `victim-shop.myshopify.com`; the app completes OAuth and, per `oauth.rb`, sets cookie `shopify_app_session=offline_victim-shop.myshopify.com` in the victim's browser, and the host app's `SessionRepository` stores the resulting `Session` (with `access_token`) keyed by `offline_victim-shop.myshopify.com`.
2. As an unrelated, unprivileged user, send a request to the same app with the cookie header `shopify_app_session=offline_victim-shop.myshopify.com` manually set (no prior OAuth performed by the attacker).
3. The app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, {"shopify_app_session" => "offline_victim-shop.myshopify.com"}, false)` [3](#0-2) , which returns `"offline_victim-shop.myshopify.com"` unchanged, with no signature check.
4. The host app looks this ID up in its session storage per the documented pattern, retrieves the victim's stored `Session` object (including `access_token`), and the attacker's subsequent request is served using the victim shop's credentials — a full cross-tenant session hijack.
