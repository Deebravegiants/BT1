### Title
Unprotected `initialize()` on `HyperFungibleTokenUpgradeable` / `WrappedHyperFungibleTokenUpgradeable` allows front-run takeover of the bridge admin (owner) role - ([File: sdk/packages/core/contracts/apps/HyperFungibleTokenUpgradeable.sol])

### Summary
`HyperFungibleTokenUpgradeable.initialize()` and `WrappedHyperFungibleTokenUpgradeable.initialize()` are guarded only by the bare OpenZeppelin `initializer` modifier, with no caller restriction, unlike the other upgradeable contracts in this codebase (`EvmHost`, `IntentGatewayV2`, `SimplexPaymaster`), which explicitly close this hole with an `onlyFresh`/admin-checked initializer plus an atomic CREATE2 deployment or a host-gated `migrate` path.

### Finding Description
`HyperFungibleTokenUpgradeable.initialize(string name, string symbol, address initialOwner)` sets `initialOwner` as the `Ownable` owner via `__Ownable_init(initialOwner)`, with `initialOwner` supplied entirely by whoever calls `initialize()`: [1](#0-0) 

`WrappedHyperFungibleTokenUpgradeable.initialize(address initialOwner)` has the identical pattern: [2](#0-1) 

Compare this to the codebase's own established pattern for closing exactly this class of bug: `IntentGatewayV2.initialize()` uses an `onlyFresh` modifier (reverts unless `_getInitializedVersion() == 0`) and relies on the raw implementation being deployed via CREATE2 with init data bound atomically at deployment, plus a host-only `migrate()` for any proxy left un-initialized after an upgrade: [3](#0-2) 

`SimplexPaymaster` follows the same `onlyFresh` + host-gated `migrate` design: [4](#0-3) 

The project's own design-decision notes explicitly document why an initializer with "no caller restriction" is dangerous unless the proxy is initialized atomically at deployment: [5](#0-4) 

`HyperFungibleTokenUpgradeable` and `WrappedHyperFungibleTokenUpgradeable` do not follow this pattern: their `initialize()` has no `onlyFresh`-style check and no owner/admin check, only the standard `initializer` guard which prevents double-initialization but does not restrict *who* is allowed to run it first. If these upgradeable contracts are deployed as a bare proxy (`new ERC1967Proxy(impl, "")`) followed by a separate `initialize()` call — the common two-step proxy deployment pattern, and distinct from the atomic CREATE2 constructor-initialization used elsewhere in this repo (e.g. the non-upgradeable `HyperFungibleToken`, which sets owner in its constructor) — any unprivileged address can front-run the legitimate deployer's `initialize()` transaction and set itself as `initialOwner`.

### Impact Explanation
Owning the contract grants full control over `configure()` (sets `_host`/`_dispatcher`, gated only by `_host == address(0)` so it's still settable by the attacker-owner on first call), `addChain()`/`removeChain()` (which registers the trusted peer module ID per chain used to validate/mint on incoming ISMP messages), and `pause()`/`unpause()`: [6](#0-5) 

Since this contract "is both the token and the bridge in one contract" and mints new supply upon incoming cross-chain messages from configured peers, an attacker who wins this race can configure `_host`/`_dispatcher` and peer module IDs to values it controls, then dispatch spoofed incoming messages that mint tokens to itself with no real cross-chain backing — an unbacked-mint outcome. This is a direct token/bridge takeover, not merely griefing.

### Likelihood Explanation
Exploitability depends entirely on the deployment pattern used for the proxy. If the deployer initializes atomically (init data passed to the proxy constructor in the same transaction as proxy creation, as documented for the CREATE2 non-upgradeable `HyperFungibleToken`), the window does not exist. However, nothing in the reachable contract code enforces atomic initialization for the Upgradeable variants — the pattern is left entirely to deployment tooling/scripts, and no atomic-deployment script for these particular Upgradeable contracts was found in the indexed portion of the repo (only the CREATE2 constructor-init pattern for the non-upgradeable `HyperFungibleToken`/`BridgeToken` was found). This is a plausible medium-likelihood configuration/deployment-time issue rather than a confirmed live exploit, since I could not verify from the indexed files whether any current deployment script instantiates these Upgradeable contracts via a non-atomic two-step proxy pattern.

### Recommendation
Add the same `onlyFresh`-equivalent protection used elsewhere in this codebase: require `_getInitializedVersion() == 0` won't help alone since that's already implied by `initializer`; the real fix is to bind `initialOwner`/config to the deployer via a constructor-level immutable admin check (as `IntentGatewayV2` and `SimplexPaymaster` do with `_owner`/`onlyHost`), or mandate/document that these Upgradeable token contracts must only ever be deployed with `initialize()` calldata passed atomically into the proxy constructor, and add an explicit deployment script enforcing that pattern, consistent with the rest of the repo's initializer hardening work.

### Proof of Concept
1. Deployer deploys `HyperFungibleTokenUpgradeable` implementation and an `ERC1967Proxy` pointing to it with empty init data (two-step deployment).
2. Before the deployer's `initialize(name, symbol, deployerAddr)` transaction is mined, an attacker submits `initialize(name, symbol, attacker)` with higher gas, which is accepted since `initializer` only checks it hasn't run yet, not who the caller is: [7](#0-6) 
3. Attacker is now `owner`; the deployer's transaction reverts (`InvalidInitialization`).
4. Attacker calls `configure()` with a malicious `_host`/`_dispatcher`, and `addChain()` to register itself as a trusted peer: [8](#0-7) 
5. Attacker then triggers `onAccept` (via the malicious host it controls) to mint tokens to itself, unbacked by any real bridged funds.

    /// @dev The `Initializable` version this implementation lands a proxy on, through `initialize`
    /// or `migrate`. Bumped by the next implementation that needs a migration.
    uint64 private constant VERSION = 2;

    /// @dev `initialize` is for a bare proxy only. A proxy that an upgrade left below `VERSION` is
    /// taken there by the host-only `migrate`; without this, anyone could `initialize` it.
    modifier onlyFresh() {
        if (_getInitializedVersion() != 0) revert InvalidInitialization();
        _;
    }

    /**
     * @dev One-time init of a bare proxy: registers the peers, each bound to `address(this)`,
     * stores the params, arms the relayer gate, and lands at `VERSION`. Refused on any proxy
     * already at a version, see `onlyFresh`.
     * @param p The initial gateway configuration parameters.
     * @param peerChains State-machine ids of the cross-chain peers to register, each bound to this
     * gateway's own address so no peer address is carried in the proxy's init data.
     * @param relayer The only relayer whose deliveries are accepted. Zero leaves the gate open.
     */
    function initialize(Params memory p, bytes[] memory peerChains, address relayer)
        public
        onlyFresh
        reinitializer(VERSION)
    {
        uint256 peersLength = peerChains.length;
        for (uint256 i = 0; i < peersLength; i++) {
            Deployment memory deployment = Deployment({chain: peerChains[i], gateway: address(this)});
            _addDeployment(deployment);
        }
        _validateParams(p);
        _params = p;
        _setRelayer(relayer);
    }

    /// @param params_  Initial pricing and treasury parameters
    /// @param tokens_  Initially supported ERC-20 tokens
    /// @param oracles_ token/USD feed for each entry in tokens_
    /// @param relayer_ The only relayer whose governance deliveries are accepted; zero leaves
    ///                 the gate open
    function initialize(
        address host_,
        Params memory params_,
        address[] memory tokens_,
        AggregatorV3Interface[] memory oracles_,
        address relayer_
    ) external onlyFresh reinitializer(VERSION) {
        if (host_ == address(0) || host_.code.length == 0) revert InvalidHost();
        if (tokens_.length != oracles_.length) revert LengthMismatch();

        _hostAddr = host_;
        _setParams(params_);

        for (uint256 i = 0; i < tokens_.length; i++) {
            _registerToken(tokens_[i], oracles_[i]);
        }
        _setRelayer(relayer_);

# 2026-09-05 — `initialize` only on a bare proxy, rather than a version check in the upgrade path

Chosen: `initialize` is refused unless the proxy is at version 0. `migrate` is the only entry to
`VERSION` for a proxy that already has one, and it is host-only.

The hole both options close: `initialize` has no caller restriction, because a bare proxy is
initialized atomically in its constructor. An `UpgradeContract` that installs this implementation
on a version-1 proxy without `migrate` calldata would leave the proxy below `VERSION` with
`initialize` callable by anyone, who could then set the params and the relayer.
