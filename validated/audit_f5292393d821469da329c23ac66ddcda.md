This codebase contains a strong analog to the Mango Markets oracle-manipulation pattern (which caused the UXD Protocol loss): Hyperbridge's Simplex intent-filler prices "venue" trading pairs directly off a live Uniswap V4 pool's spot price, with no TWAP and an easily-bypassed/optional deviation guard.

### Title
Intent solver prices fills off manipulable Uniswap V4 spot price with no TWAP or size-impact model, enabling Mango-style price-manipulation drain of solver funds - ([File: sdk/packages/simplex/src/strategies/fx.ts])

### Summary
For any pair configured without static bid/ask curves, `FXFiller` prices intent orders from the *instantaneous* `sqrtPriceX96` of a Uniswap V4 pool the solver holds liquidity in, rather than a manipulation-resistant TWAP. The only defense, `checkPriceGuard`, is optional (a chain can be left "unguarded"), and even when configured it only checks static deviation from a hand-set reference — it does nothing about trade-size price impact or same-block manipulation, and the resulting price is applied linearly to the entire order regardless of pool depth.

### Finding Description
`resolveLegRates` in [1](#0-0)  prices a curveless, USD-stable-anchored pair by calling `venueUsdPrice`, which resolves through `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd`, defined in [2](#0-1) . That function derives the price straight from `sdkPool.token0Price` / `token1Price`, which are computed from the pool's live `sqrtPriceX96` read via `getSlot0` in [3](#0-2)  — an unmodified spot price, not a time-weighted average.

The only safeguard is `checkPriceGuard`, in [4](#0-3) , which compares the quote against a static `referencePrice` and rejects only if it drifts more than `maxDeviationBps`. Per the docs, this guard is optional per chain ("omit both to leave the chain unguarded") — [5](#0-4)  — and even when configured it is a coarse band around a manually maintained reference, not a manipulation-resistance mechanism (no multi-block confirmation, no liquidity-depth/size-impact check). The project's own internal flow notes make this explicit: [6](#0-5)  states the mid price has "no size or impact term" and `checkPriceGuard` "checks deviation from a static reference, not execution cost."

This is structurally the same bug class as the Mango Markets exploit referenced in the external report: a protocol trusts a single spot price from a thin/controllable venue as ground truth for valuing an asset, and that price directly drives fund movement (there, borrow/mint against inflated collateral; here, the amount of the exotic token the solver delivers, or the rate at which the solver accepts inventory into its own vault, per leg via `computeLegPolicyOutput`).

### Impact Explanation
An attacker who can move the pool's `sqrtPriceX96` (e.g., via a large swap or flash-loan-funded swap against the exact pool the solver's Uniswap V4 position sits in) — while staying inside `maxDeviationBps`, or on any chain left "unguarded" per the documented config option — causes `resolveLegRates`/`referenceRate` to return a manipulated `venueUsd` price. This price feeds `computeLegPolicyOutput`, which extends it linearly across the entire ordered quantity with no size-impact correction. An intent order submitted while the pool is in this manipulated state causes the solver to either overpay the exotic token relative to its true market value or accept an under-priced deposit into inventory — a direct value transfer out of the solver's escrowed capital and Uniswap V4-backed vault, matching the "concrete theft ... of funds" criterion.

### Likelihood Explanation
The attack requires no privileged role: any unprivileged intent submitter/taker can manipulate a public Uniswap V4 pool (subject to available liquidity/capital) and, in the same block or bundle, submit or trigger the fill of an intent order priced off that pool. The guard being optional per chain, and even the configured guard covering only static deviation (not per-trade impact or staleness against fast-moving state), leaves a real window; the docs explicitly warn "Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote," confirming this is a known, reachable weakness rather than a hypothetical one.

### Recommendation
Replace or supplement the spot-price read with a TWAP over a manipulation-resistant window before using it in `computeDirectPoolPriceUsd`/`getExoticTokenPrice`. Make the price guard mandatory (not opt-out) for every venue-priced chain, and extend it to account for trade size versus pool liquidity (apply an execution-cost/slippage model in `computeLegPolicyOutput` rather than a flat linear extension of the mid), and consider bounding order size relative to on-chain pool depth for venue-priced pairs.

### Proof of Concept
1. Solver configures a curveless pair (e.g., USDC/CNGN) priced solely from a Uniswap V4 position, per [7](#0-6) , with no `referencePrice`/`maxDeviationBps` guard (an explicitly supported configuration) or with a wide-enough guard.
2. Attacker executes a large swap (optionally flash-loan funded) against that same Uniswap V4 pool, moving `sqrtPriceX96` such that `token0Price`/`token1Price` diverge sharply from the pool's normal equilibrium, while remaining inside any configured `maxDeviationBps`.
3. In the same block/bundle, attacker submits an intent order on the affected pair. `FXFiller.resolveLegRates` → `getVenueUsdPrice` → `computeDirectPoolPriceUsd` returns the manipulated spot price; `checkPriceGuard` passes (guard absent or band wide); `computeLegPolicyOutput` linearly applies this bad rate to the full order size.
4. The solver's fill transaction delivers tokens at the manipulated rate, and the attacker reverses the pool manipulation trade afterward, pocketing the difference extracted from the solver's inventory/vault — directly analogous to how the Mango Markets attacker used a manipulated oracle price to over-borrow against inflated collateral.

	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

	/**
	 * Computes the USD price of the non-stable token in a pool.
	 * Returns null if neither currency is USDC/USDT on this chain.
	 */
	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```
