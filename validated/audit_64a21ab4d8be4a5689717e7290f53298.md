### Title
Webhook `shop-domain` Header Is Not Covered by HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, while the `shop-domain` header that identifies *which merchant* the webhook belongs to is never included in the signed content. Because the app's HMAC secret (`api_secret_key`) is shared across every shop that has the app installed (it is not per-shop), any user who controls one shop that has installed the app can obtain a validly-signed `(body, hmac)` pair and replay it directly to the app's public webhook endpoint with an arbitrary `shop-domain` header, causing the host application's webhook handler to process the data as if it belonged to a different (victim) shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` verifies the HMAC exclusively against `verifiable_query.to_signable_string`, i.e. only the body bytes — never the `shop`, `topic`, or `webhook_id` headers: [2](#0-1) 

`Registry.process` gates on that body-only HMAC check, then forwards the *unauthenticated* `request.shop` header straight into `WebhookMetadata`, which is handed to the app's webhook handler as the tenant identity for the event: [3](#0-2) 

`Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signed body: [4](#0-3) 

The identity binding that should hold is: `shop header == shop that the signed body was generated for`. Because `api_secret_key` is a single per-app secret shared by all shops that install the app (not per-shop), any merchant who has installed the app can trigger a real webhook on their own store, capture the genuinely-signed `(body, hmac)` pair, and re-POST it to the app's webhook endpoint with the `shop-domain` header rewritten to a different, victim shop that also has the app installed. The HMAC check still passes (it only verifies the body was signed with the app's secret — which it was), but the shop attribution used by the handler is now attacker-controlled and decoupled from the signed data.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for inbound webhook data: an unprivileged app user (any merchant who installed the app) can cause the host application to process arbitrary attacker-supplied event data attributed to another merchant's shop identity. Depending on the handler's use of `WebhookMetadata#shop` (e.g., keying database writes, triggering shop-scoped actions, or fulfilling mandatory GDPR topics like `customers/redact`/`shop/redact`), this enables cross-tenant data corruption or cross-tenant action injection — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is high for any installation with multiple shops sharing one app secret (the normal, documented deployment model for a public/custom Shopify app): the attacker needs no secrets, only the ability to install the app on their own shop (or observe an existing webhook delivery to their shop) and to send an HTTP request directly to the app's public webhook endpoint.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook_id`) header into the value that is HMAC-verified, or otherwise cryptographically/contextually verify that the shop in the header matches the shop the signed payload was actually generated for (e.g., look up the expected shop via a registered webhook id, or require the host application to cross-check `shop` against a known/authorized session before trusting it). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for authorization decisions without additional verification.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any subscribed webhook topic (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker sends this exact `(body, hmac)` pair directly to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (a different shop that has the same app installed).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(body, api_secret_key) == received_hmac` — this passes because the body/hmac pair is genuinely valid for the shared app secret. [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, even though the payload was never actually generated for that shop.
