### Title
Webhook `shop` identity is unauthenticated (not covered by HMAC) allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely via `Utils::HmacValidator.validate(request)`, which checks the HMAC over `to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only the raw request body — none of the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) are covered by the signature. After this check passes, the code dispatches to the host application's handler using `request.shop` (an unauthenticated header value) as the tenant identifier in `WebhookMetadata`.

### Finding Description
- `Webhooks::Request#to_signable_string` returns `@raw_body` only. [1](#0-0) 
- `Webhooks::Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic binding to the body or HMAC. [2](#0-1) 
- `HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e., body bytes only) and compares it against the `hmac` header. [3](#0-2) 
- `Registry.process` treats a passing HMAC check as full authentication of the request, then forwards the unauthenticated `request.shop` value straight into `WebhookMetadata`, which the host application uses to identify/route the tenant. [4](#0-3) [5](#0-4) 

The identity binding broken is: `shop authenticated == shop used for tenant dispatch`. The HMAC only binds the **body**; the **shop** field that downstream handlers rely on for tenant scoping is never part of the signed content. Since a single app's webhook HMAC secret (`api_secret_key`) is shared across every shop that installs the app, any unprivileged user who installs the app on their own store receives legitimately-signed webhook deliveries (body + valid HMAC) for their own shop. They can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `Registry.process` will accept it as valid (HMAC only checks the body) and hand the attacker-controlled `shop` value to the handler, causing the host app to process/attribute data as if it came from the victim shop — a cross-tenant confusion made possible purely by this gem's validation logic not binding the identifying header to the signature.

### Impact Explanation
This enables cross-tenant data confusion/injection: an attacker with a legitimate (self-owned) installation of the target app can forge webhook events "from" a different shop, causing the host application to write/act on data under a victim tenant's identity. This satisfies the Critical bar of cross-tenant access, since it directly breaks the shop-to-request identity binding that the library is expected to provide via `Utils::HmacValidator`.

### Likelihood Explanation
Requires only that the attacker install the target Shopify app on any shop they control (unprivileged action available to any merchant) and be able to send arbitrary HTTP requests to the app's public webhook endpoint — no access token, `api_secret_key`, or other Shopify-side credential is needed. The `Webhooks::Request` header-parsing code makes it trivial to also satisfy `topic`, `hmac-sha256`, `shop-domain` header presence checks with only the header value swapped. [6](#0-5) 

### Recommendation
- Short term: Include the `shop-domain` (and ideally `topic`, `webhook-id`) header value in the signed material validated by `HmacValidator`, or otherwise cryptographically bind the shop header to the HMAC before trusting `request.shop` for tenant dispatch.
- Long term: Document explicitly for consumers of `WebhookMetadata.shop` that it is unauthenticated with respect to the HMAC, or change `Registry.process` to fail closed unless the shop identity is independently verified (e.g., cross-checked against a known/installed shop list) rather than trusted implicitly post-HMAC-check.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, obtaining legitimate webhook deliveries signed with the app's `api_secret_key`.
2. Attacker captures one such delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`).
3. Attacker POSTs to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `B` — it matches, so validation passes. [7](#0-6) 
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body, ...)` and the host application processes the payload as if it originated from the victim's shop. [8](#0-7)

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
