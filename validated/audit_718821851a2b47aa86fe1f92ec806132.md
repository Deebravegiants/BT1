### Title
Unsafe raw `.call` ERC20 payout in `withdraw`/`SweepDust` allows silent transfer failure with escrow permanently marked released - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol` imports and uses `SafeERC20` (`using SafeERC20 for IERC20;`) for pulling tokens into escrow (`safeTransferFrom` in `placeOrder`), but the token *payout* paths — `withdraw()` and the `SweepDust` branch of `onAccept()` — bypass `SafeERC20` and instead use a raw low-level `.call` with only a `success` (call-did-not-revert) check, never inspecting the returned boolean data.

### Finding Description
In `withdraw()`: [1](#0-0) 
Each token payout is done via:
```
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
and the escrow accounting (`_orders[body.commitment][token] -= amount;`) is decremented and `_filled[body.commitment] = beneficiary` is set *regardless* of whether the token's `transfer` call actually returned `true`. The same unsafe pattern is used for the fee payout in the same function and for the dust sweep in `onAccept`'s `SweepDust` branch: [2](#0-1) 

This is precisely the bug class from the referenced report: the contract checks only that the external call did not revert, not that the token's own success flag (return value) is `true`. Tokens that follow the "return false instead of reverting on failure" pattern (a known category of legacy/non-standard ERC20/TRC20 tokens, which is exactly why this Tron-specific fork exists as a separate file from the standard EVM `IntentGatewayV2.sol` that consistently uses `safeTransfer`/`safeTransferFrom` throughout) will cause `success == true` while `beneficiary` receives nothing.

Notably, the standard EVM version at `evm/src/apps/intentsv2/IntentsBase.sol` uses `IERC20(token).safeTransfer(beneficiary, amount)` consistently for the same withdrawal logic: [3](#0-2) 
confirming the Tron variant's `withdraw()`/`SweepDust` diverged from this safe pattern and reintroduced the vulnerability that `SafeERC20` is designed to prevent.

### Impact Explanation
`withdraw()` is the function that releases escrowed user/solver funds after a cross-chain settlement message is authenticated (`RedeemEscrow`/`RefundEscrow` via `onAccept`) or after a same-chain fill/cancel. If the escrowed token silently returns `false` on transfer (e.g., due to insufficient allowance/edge conditions or a non-standard token implementation), the contract still marks the order filled/cancelled and decrements escrow state as if funds were delivered. The beneficiary receives nothing, and the tokens become permanently stuck/unrecoverable in the contract since `_orders[...]` is already zeroed and `_filled[...]` is already set — this is a direct, permanent loss of escrowed user funds, matching "concrete theft or permanent freezing of funds."

### Likelihood Explanation
This triggers on ordinary settlement flow (`fillOrder` → cross-chain `RedeemEscrow` message → relayer delivers → `onAccept` → `withdraw`, or same-chain `cancelOrder`) for any token whose `transfer` implementation returns `false` instead of reverting on failure — a well-documented legacy ERC20/TRC20 behavior class, particularly relevant on Tron where non-standard TRC20 tokens are common. No malicious/privileged actor is required; the relayer only needs to deliver a legitimate proof for the flow to execute against such a token.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout patterns in `withdraw()` and the `SweepDust` branch with `SafeERC20.safeTransfer`, consistent with the rest of the contract (`placeOrder`'s `safeTransferFrom`) and with the standard EVM `IntentsBase.sol` implementation.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with an ERC20/TRC20 token whose `transfer(address,uint256)` returns `false` on failure instead of reverting (e.g., insufficient internal balance edge case, blacklist, or any legacy token implementing the pre-EIP20-strict return semantics).
2. User calls `placeOrder` escrowing that token; escrow is recorded via `safeTransferFrom` (which works fine because `safeTransferFrom` correctly reverts on failure at deposit time).
3. Solver fills the order; a `RedeemEscrow` message is delivered and `onAccept` → `withdraw()` executes.
4. Craft/trigger conditions where the token's `transfer` call returns `false` without reverting (e.g., a token pausable/blacklist state that flips between deposit and withdraw, or a token that returns `false` on transfer to a particular address) — `success` from the low-level `.call` is `true` (the call itself didn't revert), so `TransferFailed()` is never triggered.
5. `_orders[commitment][token]` is decremented to 0 and `_filled[commitment]` is set, but `beneficiary` never received the tokens — the escrowed funds are now permanently unreachable through this contract's accounting. [4](#0-3)
