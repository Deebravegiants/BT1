This confirms the vulnerability. The webhook HMAC validation (`Utils::HmacValidator.validate(request)` at `lib/shopify_api/webhooks/registry.rb:190`) only signs `@raw_body` via `Webhooks::Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`), while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unsigned HTTP headers (`lib/shopify_api/webhooks/request.rb:15-33`) and passed straight into the handler at `Registry.process` (`lib/shopify_api/webhooks/registry.rb:198-199`) without any binding to the HMAC-covered body.

### Title
Webhook tenant identity (`shop`) not covered by HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body (`to_signable_string` returns `@raw_body`), but the `shop-domain`, `topic`, `webhook-id`, and `api-version` values used by the host application's handler are taken from unauthenticated HTTP headers that are never included in the signed payload.

### Finding Description
`Registry.process` validates the webhook solely via `Utils::HmacValidator.validate(request)` [1](#0-0) , which in turn calls `compute_signature(verifiable_query.to_signable_string, secret)` [2](#0-1) . For webhook requests, `to_signable_string` is defined to return only `@raw_body` [3](#0-2) , meaning the HMAC binds nothing but the JSON body. Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) that are entirely outside the HMAC's coverage [4](#0-3) .

The identity binding that should hold is: `shop header == shop cryptographically bound to this body`. Because the HMAC only proves "this body was signed by Shopify for some webhook," and not "this body was signed by Shopify for shop X," any request carrying a body+HMAC pair that once validated for one shop will also validate successfully with a different `shop-domain` header value substituted in, since `validate_signature` never inspects `shop` [5](#0-4) . The resulting `WebhookMetadata` handed to the app's handler therefore carries an attacker-controlled, unauthenticated `shop` value that the host application will treat as an authenticated tenant identifier [6](#0-5) .

### Impact Explanation
An unprivileged actor who can capture or replay any single legitimate webhook delivery (e.g., a webhook delivered to their own trial/test store, or one leaked in logs/proxies) can resend the identical body+HMAC to the app's webhook endpoint while altering only the `shopify-shop-domain` header to point at a victim's shop. Since this gem's HMAC validation never checks that the shop matches the signed content, the request passes validation, and the handler is invoked with `data.shop` set to the victim's domain and `data.body` set to attacker-influenced content — cross-tenant data confusion in the app's webhook processing pipeline, which is the class of "cross-tenant access" impact.

### Likelihood Explanation
Likelihood is moderate to high: it requires only one previously observed valid webhook payload+HMAC pair (which any merchant installing the app receives) and standard HTTP tooling to replay it with a modified header — no possession of `api_secret_key` or access tokens is needed, satisfying the in-scope unprivileged-attacker constraint.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` values in the signed payload used for HMAC verification (e.g., bind them into `to_signable_string` or require the host app to independently correlate `shop` with a known webhook subscription/topic before trusting it), so that tampering with these headers invalidates the signature.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(secret, B)`.
2. Attacker resends the exact same request to the app's webhook endpoint, keeping `body=B` and `x-shopify-hmac-sha256=H`, but changes `x-shopify-shop-domain` to `shop-b.myshopify.com` (a victim shop the attacker does not control).
3. `Registry.process` calls `HmacValidator.validate(request)`, which only recomputes HMAC over `B` and compares to `H` — validation succeeds because `to_signable_string` never included the shop header [3](#0-2) .
4. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: parsed_body, ...)`, causing the host app to process/act on data as if it authentically originated from `shop-b.myshopify.com` [6](#0-5) .
