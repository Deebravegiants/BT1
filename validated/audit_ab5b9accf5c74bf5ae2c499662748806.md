## Title
Multisig transaction execution can bypass payload-approval binding when full payload is stored on-chain - ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
The external report's custody invariant reduces to: *a system must not execute a privileged custody-affecting action using externally-supplied data that was never actually validated/approved by the authorizing party.* In TOKI, the callback payload executed on the destination chain is not bound to anything the relayer/user actually vetted. The Aptos-native analog I found is in `multisig_account::validate_multisig_transaction`, which is the VM-invoked gate that decides whether an owner-approved multisig transaction is allowed to execute.

### Finding Description
When an owner calls `create_transaction`, the full transaction payload is stored on-chain in `MultisigTransaction.payload` [1](#0-0) . Other owners vote on that specific transaction id via `vote_transanction`/`approve_transaction` [2](#0-1) , believing they are approving the payload that was stored at creation time.

At execution time, `validate_multisig_transaction` is invoked by the VM with an executor-supplied `payload: vector<u8>` argument [3](#0-2) . The function only cross-checks the supplied `payload` against what owners approved in two cases:
1. If the transaction was created via `create_transaction_with_hash` (`payload_hash.is_some()`), the hash is checked.
2. If the transaction was created with a full payload (`transaction.payload.is_some()`), the match is checked **only when `features::abort_if_multisig_payload_mismatch_enabled()` is true** (from the doc-derived implementation, mirrored in source around line ~1375-1381, matching the pattern I confirmed in `doc/multisig_account.md` lines 3679-3702) [4](#0-3) .

If that feature flag is not enabled, an executing owner can supply an arbitrary `payload` argument at execution time that differs from the `transaction.payload` the other owners actually approved, and the quorum/timelock checks (`num_approvals >= num_signatures_required`, `can_execute_with_timelock`) will still pass because they only count votes against the sequence number, not against the payload content actually executed [5](#0-4) . This breaks the core multisig custody invariant that "the exact payload approved by k-of-n owners is the payload that gets executed as the multisig (resource) account," potentially allowing an executor with sufficient standing (any owner, once quorum on *a* transaction id is reached) to redirect APT/fungible-asset transfers, reassign object/code-object ownership, or otherwise act with the multisig account's authority using unapproved instructions.

### Impact Explanation
The multisig account is itself a resource account holding real custody authority over APT, fungible assets, and any objects/code it owns. If an executor can substitute the payload actually run, this is a direct authority break enabling theft or reassignment of multisig-controlled assets — squarely inside the custody-impact gate (multisig control takeover, and asset transfer to an unapproved holder).

### Likelihood Explanation
This is **conditional and I could not fully verify it independently** within available tool calls:
- The gap is explicitly feature-flag-gated (`abort_if_multisig_payload_mismatch_enabled`), and the very existence/naming of this flag strongly suggests it was already introduced specifically to close this exact gap. I was unable to confirm from the index whether this flag is enabled by default on mainnet today.
- I was also unable to fully trace the Rust-side VM prologue/execution path (`aptos-vm/src/aptos_vm.rs`, `types/src/transaction/multisig.rs`) to conclusively confirm that the `payload` bytes actually executed by the VM are the caller-supplied argument rather than always being re-derived from the stored `MultisigTransaction.payload`.
- Because the impact gate explicitly excludes findings that depend on "privileged governance or admin assumptions" (i.e., a feature flag not being turned on), and because I cannot confirm this flag's current default/mainnet state or fully confirm the VM data flow, I **cannot assert with confidence that this is an unprivileged, currently-live root cause** independent of configuration.

### Recommendation
If independently confirmed (via a Devin session with full repo/tooling access) that (a) the flag defaults to disabled on live networks, and (b) the VM executes the caller-supplied `payload` rather than the stored one when the flag is off, then the mismatch check in `validate_multisig_transaction` should be made unconditional (not feature-gated) so that any multisig transaction with a full on-chain payload always requires the executed payload to match the approved one, byte-for-byte, regardless of feature-flag state.

### Proof of Concept
Not constructed — this finding requires confirming the two open questions above (feature flag default state and VM payload-execution binding) before a concrete PoC transaction sequence can be built. Given the uncertainty, I recommend a dedicated Devin session with full codebase/tooling access to definitively trace `aptos-vm/src/aptos_vm.rs` and `types/src/transaction/multisig.rs` for the actual execution-time payload binding before treating this as a confirmed vulnerability.

    /// Generic function that can be used to either approve or reject a multisig transaction
    /// Retained for backward compatibility: the function with the typographical error in its name
    /// will continue to be an accessible entry point.
    public entry fun vote_transanction(
        owner: &signer, multisig_account: address, sequence_number: u64, approved: bool) {
        assert_multisig_account_exists(multisig_account);
        let multisig_account_resource = borrow_global_mut<MultisigAccount>(multisig_account);
        assert_is_owner_internal(owner, multisig_account_resource);

        assert!(
            multisig_account_resource.transactions.contains(sequence_number),
            error::not_found(ETRANSACTION_NOT_FOUND),
        );
        let transaction = multisig_account_resource.transactions.borrow_mut(sequence_number);
        let votes = &mut transaction.votes;
        let owner_addr = address_of(owner);

        if (votes.contains_key(&owner_addr)) {
            *votes.borrow_mut(&owner_addr) = approved;
        } else {
            votes.add(owner_addr, approved);
        };

        emit(
            Vote {
                multisig_account,
                owner: owner_addr,
                sequence_number,
                approved,
            }
        );
    }
