### Title
Attacker-crafted GRANDPA header cycle causes an infinite loop in `AncestryChain::ancestry`, hanging block execution — ([File: modules/consensus/grandpa/primitives/src/justification.rs])

### Summary
`AncestryChain::ancestry` walks parent hashes from `block` to `base` using a `while current_hash != base` loop, with no visited-set/cycle guard and no bound on iterations. The `ancestry` map it walks is built directly from `unknown_headers` submitted inside a GRANDPA consensus proof/justification — fully attacker-controlled data. Since a header's hash is a deterministic function of its own encoded fields (including `parent_hash`), an attacker can construct two headers whose `parent_hash` fields point at each other, forming a genuine 2-cycle that is internally hash-consistent. If `ancestry()` is asked to walk from a block inside that cycle to a `base` that is never reached, the loop never terminates.

### Finding Description
`ancestry()` is defined in `modules/consensus/grandpa/primitives/src/justification.rs`: [1](#0-0) 

It is called from two permissionless, attacker-reachable entry points:
1. `GrandpaJustification::verify_with_voter_set` (per-precommit ancestry walk during justification verification): `ancestry_chain.ancestry(base_hash, signed.precommit.target_hash)` [2](#0-1) 
2. `verify_grandpa_finality_proof` (top-level consensus-update verification): `headers.ancestry(from, target.hash())` and the base/latest-hash ancestry check [3](#0-2) 

Both call sites build the `AncestryChain` directly from `finality_proof.unknown_headers` / `self.votes_ancestries`, i.e. header lists supplied wholesale inside the submitted consensus message: [4](#0-3)  and [5](#0-4) .

None of these headers are validated against any external, trusted source before the ancestry walk runs — that's the entire point of the function (they are the "unknown headers" being proven). Because a header's hash is computed over its own SCALE-encoded fields (including `parent_hash`), an attacker can pick two header bodies `H1`, `H2` and set `H1.parent_hash = hash(H2)` and `H2.parent_hash = hash(H1)`; both hashes are then fully self-consistent, since the hash function has no external anchor forcing acyclicity. Once such a pair is included in `unknown_headers`/`votes_ancestries`, and the ancestry walk is started at a block in the cycle with a `base` that the cycle never reaches, the `while current_hash != base` loop alternates between the two hashes indefinitely — `self.ancestry.get(&current_hash)` always succeeds for both, so the `_ => return Err(...)` arm is never hit.

This directly parallels the CVE-2021-43545 bug class: a permissionless, single-message-triggered operation entering an unbounded loop with no anti-hang safeguard, causing the executing process (here, the runtime/validator processing the block) to hang.

### Impact Explanation
GRANDPA consensus proof verification runs inside pallet-ismp's consensus-update dispatch, which executes during normal block execution/weight-metered dispatch on the Hyperbridge chain (and any consuming parachain using this GRANDPA client). An infinite loop inside this code path means the extrinsic never returns, so:
- The node executing/importing the block hangs indefinitely (no watchdog interrupts a pure CPU loop mid-instruction the way network timeouts do).
- Because Substrate's weight metering only checks weight *before* and *after* dispatch of a call, not during a tight in-memory loop, the call cannot be pre-empted, and the block can never be finalized — a permissionless route that is unable to deliver messages and can halt chain progress, i.e. a Medium/High denial-of-service against consensus updates for the affected state machine's IBC connection.

### Likelihood Explanation
The `unknown_headers`/`votes_ancestries` fields are attacker-supplied wire data with no relationship-to-a-real-chain check performed before the ancestry walk. Constructing a 2-header cycle only requires computing two hashes that reference each other, which is mechanically simple (no cryptographic signature is required over the header content itself — only the GRANDPA precommit signatures over the *justification*, which reference target hashes, not full acyclicity of the ancestry set). This is submittable in a single consensus-update message by any relayer/unprivileged submitter, making the likelihood high once such a message decodes and reaches the ancestry walk.

### Recommendation
Add a cycle/visited-set guard and/or a maximum iteration bound to `AncestryChain::ancestry`, e.g. track visited hashes in a `BTreeSet` and return an error (e.g. `Error::AncestryCycle`) if a hash is revisited before `base` is reached, or bound the loop to `self.ancestry.len() + 1` iterations. This preserves correctness for legitimate ancestry chains (which are acyclic paths of length ≤ number of submitted headers) while eliminating the infinite-loop possibility for maliciously crafted header sets.

### Proof of Concept
1. Construct two SCALE-encodable headers `H1`, `H2` (arbitrary otherwise-valid field values) such that:
   - `H1.parent_hash = Blake2::hash(H2.encode())`
   - `H2.parent_hash = Blake2::hash(H1.encode())`
   This is solvable by iterating over cosmetic fields (e.g. `state_root`, `extrinsics_root`, digest logs) of each header until the mutual-hash equations hold (birthday-bound search, feasible offline).
2. Include both headers in `finality_proof.unknown_headers` (or `votes_ancestries`) of a submitted GRANDPA consensus/justification message, with `target` set to `H1` and `base`/`from` set to a hash not present in `{H1, H2}` (e.g. the currently trusted `consensus_state.latest_hash`).
3. Submit this consensus message through the normal permissionless consensus-update path into pallet-ismp's GRANDPA client.
4. `verify_grandpa_finality_proof` calls `headers.ancestry(from, target.hash())` (or the per-precommit call inside `verify_with_voter_set`), which enters `while current_hash != base { ... }` and toggles between `H1`'s and `H2`'s hashes forever, hanging the executing node.

Note: I was not able to fully verify whether any upstream size/format check (e.g. maximum extrinsic size, or a header-count cap in the runtime config) would prevent submission of exactly two headers — such checks would not need to be large to admit this cycle, since only 2 headers are required. I was also unable to trace whether the `tesseract-consensus/grandpa` (off-chain relayer) daemon path performs any pre-validation before submission, but per the scope rules that daemon path is out of scope; the on-chain verifier itself contains no cycle protection, which is the root cause.

	/// Initialize the ancestry chain given a set of relay chain headers.
	pub fn new(ancestry: &[H]) -> AncestryChain<H> {
		let ancestry: BTreeMap<_, _> = ancestry.iter().cloned().map(|h: H| (h.hash(), h)).collect();

	}

	pub fn header(&self, hash: &H::Hash) -> Option<&H> {
		self.ancestry.get(hash)

impl<H: HeaderT> finality_grandpa::Chain<H::Hash, H::Number> for AncestryChain<H>
where
	H::Number: finality_grandpa::BlockNumberOps,
{
	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
