### Title
Webhook cross-tenant shop spoofing - HMAC signs only the raw body, not the `shop-domain`/`topic`/`webhook-id` headers passed to the handler ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` fields — read from unauthenticated HTTP headers — are trusted and forwarded to the host application's handler as authenticated metadata.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from HTTP headers and are **not** part of the signed string: [3](#0-2) 

After successful HMAC validation, `Registry.process` builds a `WebhookMetadata` struct directly from these unauthenticated header fields and hands it to the app's handler as trusted, authenticated data: [4](#0-3) [5](#0-4) 

The binding that is broken is: `shop header verified-by-HMAC == shop header acted-upon-by-handler`. In reality only `raw_body` is covered by the HMAC; `shop`, `topic`, `webhook_id`, and `api_version` are asserted but never bound cryptographically. Because the same `client_secret`/webhook secret is shared across every shop that installs the app, any unprivileged merchant who has installed the app on their own store can capture a legitimately-signed webhook (valid `body` + `hmac`) delivered to their own shop, then replay that exact `body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header naming a different, victim shop. `HmacValidator.validate` still succeeds because it only checks the body's signature, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
This crosses a tenant boundary: an attacker can make the host application process attacker-controlled webhook data (order/customer/product content they choose, from their own store) under the identity of an arbitrary other shop, since `shop` is unauthenticated relative to the cryptographic proof. Any host application that uses `WebhookMetadata#shop` to key its per-tenant storage, authorization, or business logic (which is the intended and documented use of this field) would attribute/apply attacker-controlled data to a shop the attacker does not control — i.e., cross-tenant data corruption/injection.

### Likelihood Explanation
Requires only that the attacker install the target app on a shop they control (a normal, unprivileged action any merchant can do) and be able to trigger at least one webhook topic that is also registered by the target app, then replay it with a modified header set. No `api_secret_key`, access token, or privileged account is needed — the attacker uses their own legitimately-signed webhook.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed payload (or otherwise cryptographically bind them, e.g., derive/verify shop identity from the access-token/session store rather than trusting the header), so `to_signable_string` cannot be satisfied by a signature computed over the body of an unrelated shop/topic.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook subscribed by the app (e.g. `orders/create`), receiving from Shopify a POST with headers `x-shopify-hmac-sha256`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, and a JSON body — the HMAC is valid for that exact body under the shared `client_secret`.
2. Attacker resends the same raw body and the same `x-shopify-hmac-sha256` value to the host app's webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (only checks presence, not authenticity) [6](#0-5) ; `Registry.process` calls `HmacValidator.validate(request)`, which passes because it only re-hashes `@raw_body` [7](#0-6) .
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)` and processes it as authentic data for the victim shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
