## Title
Unrestricted `CallDispatcher.dispatch` combined with persistent ERC20 approvals lets any user steal tokens temporarily routed through the shared dispatcher - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher` is a single, shared, permissionless contract used by `HyperFungibleToken.onAccept`, `WrappedHyperFungibleToken.onAccept`, and `IntentGatewayV2`/`IntentsBase._execute` (predispatch and output-call flows) to execute attacker/user-supplied `Call[]` payloads that arrive embedded in cross-chain messages and orders. Exactly like the `PrivatePool.flashLoan`/`execute` bug (approvals granted by one controller of a shared vault surviving a transfer of control and later being exploited by a permissionless caller), an ERC20 `approve()` issued through one message's calldata persists on the `CallDispatcher` forever, and because `dispatch()` has **no access control whatsoever**, anyone can invoke it directly at any later time to exploit that leftover allowance against whatever balance the dispatcher happens to be holding for a completely unrelated user's in-flight transfer or order.

### Finding Description
`CallDispatcher.dispatch` is `external` with no caller restriction and executes each `Call` with the dispatcher itself as `msg.sender`: [1](#0-0) 

It is invoked as a shared singleton by multiple products:
- `HyperFungibleToken.onAccept` forwards attacker/user-controlled `message.data` straight to it after minting tokens to the beneficiary (which can be set to the dispatcher's own address): [2](#0-1) 
- `IntentsBase._execute` dispatches `order.output.call` (attacker/user supplied) through the same dispatcher during order fills, then sweeps only *balances* back afterward — never allowances: [3](#0-2) 

The project's own documentation flags the exact risk but only recommends developer discipline, not an on-chain guard: "Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution." [4](#0-3) 

Because `dispatch()` is callable by anyone, any user can submit a bridging `send()` (or an intent order with `predispatch.call`/`output.call`) whose embedded `Call[]` approves an attacker-controlled spender for `type(uint256).max` on some token, targeting the `CallDispatcher` as the approving party. That approval is permanent — nothing in the codebase ever revokes it. Afterward, whenever *any other* user's legitimate cross-chain transfer or order routes the same token through the dispatcher (minted/unlocked to `CALL_DISPATCHER` per the documented pattern, or sitting there mid-execution of a multi-call swap), the attacker can call `CallDispatcher.dispatch()` themselves — completely independent of, and not requiring any interaction with, the legitimate flow — to run `token.transferFrom(dispatcher, attacker, balance)` against the standing approval and steal the funds before the legitimate call sequence completes its sweep.

This mirrors the referenced report precisely: a permissionless entity (previous approver / any caller of `dispatch`) can drain funds legitimately owned by the current expected beneficiary because approvals outlive their intended single-use context and the vulnerable function (`flashLoan` there, `dispatch` here) is reachable by anyone with attacker-chosen call targets.

### Impact Explanation
Any ERC20 token routed through the shared `CallDispatcher` — via `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata-execution bridging or `IntentGatewayV2` predispatch/output composability — can be permanently drained by any user who has ever left (or intentionally planted) a standing approval through a prior malicious message. Since `dispatch()` enforces no `msg.sender` check and no allowance-revocation ever occurs, this is a direct, unbounded theft vector against the shared dispatcher's balance, reachable by an ordinary unprivileged token bridger or intent-order creator/solver in a single transaction.

### Likelihood Explanation
High: `dispatch()` requires zero privilege and zero coordination with the victim transaction — an attacker plants the approval once (a normal `send()`/`placeOrder()` call with `data`/`predispatch.call`/`output.call`), then waits and calls `dispatch()` whenever the dispatcher next holds a nonzero balance of the approved token. The composable/calldata-execution feature is explicitly documented and encouraged for normal use (Uniswap swap examples), making the attack surface broad and easy to trigger without any special conditions.

### Recommendation
Add an access-control or scoping mechanism to `CallDispatcher.dispatch`, e.g. restrict callers to a fixed allowlist of authorized invokers (`HyperFungibleToken`, `WrappedHyperFungibleToken`, `IntentGatewayV2`), or deploy a fresh, ephemeral dispatcher (e.g., via `CREATE2`/clone) per message/order rather than sharing one singleton contract across all users. Additionally, revoke any allowance granted during a `dispatch()` call before returning control (reset `approve(spender, 0)` for any token touched), so no approval outlives the single execution it was created for.

### Proof of Concept
1. Attacker calls `HyperFungibleToken.send()` (or places an intent order with `predispatch.call`) with `data` encoding `Call[]{ to: TOKEN, data: approve(ATTACKER_SPENDER, type(uint256).max) }`, targeting the shared `CallDispatcher`. This lands as a legitimate cross-chain message; `onAccept` executes it, leaving `TOKEN.allowance(dispatcher, ATTACKER_SPENDER) = max`. [2](#0-1) 
2. Later, a legitimate user bridges `TOKEN` cross-chain with `to = CALL_DISPATCHER` (the documented pattern for calldata execution), or an order's predispatch/output flow momentarily deposits `TOKEN` on the dispatcher: [5](#0-4) 
3. Attacker calls `CallDispatcher.dispatch()` directly (no access control) with a `Call` to `TOKEN.transferFrom(dispatcher, attacker, balance)` from `ATTACKER_SPENDER`, draining the victim's tokens before their intended calls execute. [1](#0-0)

            }

                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
