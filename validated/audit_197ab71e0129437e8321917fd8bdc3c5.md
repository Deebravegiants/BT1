## Title
Phantom-order price snapshot lets a solver flash-manipulate its on-chain token balance to set the published pool exchange rate used to price real intent orders - (File: `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts`)

### Summary
The reported bug class — using a flash-loanable balance to pass a threshold/weighting check and trigger an economically privileged action within a single transaction — has a direct analog in Hyperbridge's phantom-order price-discovery pipeline. A solver's bid price is weighted in the `weightedMedian` calculation by a *live* `eth_call` read of its output-token balance (`getTotalSolverBalance` / `getBalance`), rather than by an escrowed, staked, or otherwise irreversible deposit. Because the balance read is a point-in-time RPC call rather than a locked commitment, a solver (or anyone impersonating one via the solver's delegated key) can inflate its measured "inventory" for the single read that decides the published price, then immediately move the funds back out — the same "borrow → pass check → trigger privileged effect → return funds" pattern as the EarlyExecution flashloan report, except the "privileged effect" here is setting the on-chain exchange rate (`LiquidityPool.sellRate`/`buyRate`) that `IntentGatewayV2.quoteIntent`'s default `indexed_rates` strategy uses to price real user orders.

### Finding Description
`aggregatePhantomBids` (`sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts:1261-1566`) weights every solver's phantom quote by `getBalance(destUrl, chain, outputToken, solver)` — an `eth_call` `balanceOf`/`maxWithdraw` read taken with a `blockTag` (`getTotalSolverBalance`, lines 1022-1037), defaulting to `"latest"` when no explicit tag is supplied. `weightedMedian` (lines 709-724) then *selects* one bidder's exact quoted price verbatim as the leg's `medianPrice` whenever that bidder's weight covers ≥50% of total weight — this is a selection, not a blend, so a solver holding a transient majority of weight sets the price outright.

That leg-level `medianPrice` flows unmodified into `PhantomOrderPriceSnapshotV2` and then into `updateLiquidityPools` (`sdk/packages/indexer/src/services/liquidityPool.service.ts:449-518`), which merges it into `LiquidityPool.sellRate`/`buyRate` — the exact field that `IntentGateway.quoteIntent`'s default `indexed_rates` strategy (`sdk/packages/sdk/src/protocols/intents/quote/indexedRates.ts`) uses to compute `amountIn`/`amountOut` for constructing real, fund-moving `IntentGatewayV2` orders (per `docs/content/developers/sdk/api/intent-gateway.mdx:181-234` and the 2026-08-25 changelog making indexed rates the default pricing strategy).

The weighting mechanism is explicitly balance-based rather than stake/escrow-based: "the solver's balance of that leg's OUTPUT token on the destination chain" (`docs/ai/flows/phantom-price-snapshot-to-pool-rates-phantombidwindowexhausted.md:11`). Nothing locks that balance for the duration of the bid window or the aggregation read — the code comment on `memoizedSolverBalance` even documents that the read is "a point-in-time read either way" and ignores "balance changes within the run." A solver can therefore:
1. Submit a phantom bid quoting an attractive price on a leg.
2. Immediately before (or during) the window in which the indexer processes `PhantomBidWindowExhausted` and calls `aggregatePhantomBids`, flash-borrow (or otherwise transiently acquire) a large balance of the leg's output token on the destination chain.
3. Have that inflated balance observed by the `eth_call` `balanceOf` read, which gives the solver's quote majority weight and therefore lets `weightedMedian` select its price verbatim as the published `medianPrice`.
4. Return/repay the borrowed tokens immediately after — the aggregation has already captured and persisted the inflated weight.

This mirrors the report's core defect: a decision with real economic consequences (published exchange rate, analogous to "early execution" of a governance action) is gated on a balance check that is trivially satisfiable with borrowed capital held for only an instant, because the system conflates "currently holds tokens" with "durably backs this quote."

### Impact Explanation
The manipulated `sellRate`/`buyRate` is not merely informational telemetry — it is the *default* pricing source (`indexed_rates` strategy) for `quoteIntent`, which computes the `amountIn`/`amountOut` used to construct real `IntentGatewayV2` orders that escrow and release real user funds on Hyperbridge's intent-based cross-chain swap system. An attacker who skews the published rate can cause the SDK to construct orders that either (a) let the attacker's own solver later fill at a rate favorable to the attacker (extracting value from users relying on the quote), or (b) mis-price legitimate users' orders such that they escrow more input than the market rate justifies, or receive less output than a fair rate would produce — a form of unbacked/unfair value extraction from users who trust the indexed rate as ground truth. This satisfies the "unbacked mint" / "unsound state commitment" class insofar as the published `LiquidityPool` rate is a state commitment other on-chain economic decisions (order construction and fund escrow amounts) rely on without any additional verification.

### Likelihood Explanation
Likelihood is moderate-to-high for a well-resourced solver operator: the balance check is a simple `eth_call` against a standard `balanceOf`/`maxWithdraw` selector, at a `blockTag` that defaults to `"latest"` for the phantom-aggregation run (not a value pinned to the moment the bid was placed). Any EVM chain with flash-loanable liquidity for the relevant output token (a stablecoin such as USDC/cNGN/USDT, which is exactly the class of token these pools price) provides ample capital for a same-block manipulation. The main mitigating factor is that the exact block the indexer executes `aggregatePhantomBids` (in response to `PhantomBidWindowExhausted`) is not perfectly deterministic to the attacker in advance, requiring the attacker to hold the inflated balance across a short window rather than a single atomic transaction — this raises cost/risk versus the original report's single-transaction attack but does not eliminate it, since the bid window and indexing latency are both bounded and observable quantities the attacker can budget for.

### Recommendation
Weight phantom bids by a durable, non-flash-loanable commitment rather than a live spot balance: require solvers to escrow or lock the output-token amount they are quoting (mirroring the `intents-coprocessor` pallet's existing bid-deposit/reserve pattern used for the substrate-side `place_bid`), or require the balance to be observed as a time-weighted average / minimum-over-window rather than a single point-in-time read. At minimum, pin the balance read to a block from *before* the bid window closes (e.g., the block the bid was submitted in) rather than "latest" at aggregation time, so a balance acquired after bidding cannot retroactively inflate weight, and consider requiring balance persistence across multiple blocks before it counts toward `weightedMedian` weight.

### Proof of Concept
Conceptual PoC (no on-chain harness available in this review):
1. Attacker runs (or compromises) a solver account registered as a valid phantom bidder (`isVerifiedSolverBid` passes with a correctly signed `PackedUserOperation`).
2. Attacker submits a phantom bid on the leg they wish to manipulate, quoting a favorable-to-them price (e.g., inflated `medianPrice` for a token they intend to later trade against, or a price that will let their own solver capture the surplus on a subsequent real fill).
3. Near the end of the phantom bid window (`Intents::phantom_bid_window`), attacker flash-borrows a large amount of the leg's output token on the destination chain (any DEX/lending flashloan primitive on that chain) and holds it in the solver's account.
4. The Hyperbridge node emits `PhantomBidWindowExhausted`; the indexer's `handlePhantomOrderPrices` calls `aggregatePhantomBids`, which reads the solver's `balanceOf` via `eth_call` at `"latest"` (`getTotalSolverBalance`, `phantom-aggregation.ts:1022-1037`), observing the inflated balance and assigning it majority weight in `weightedMedian`.
5. `weightedMedian` selects the attacker's quoted price verbatim as `medianPrice`; `updateLiquidityPools` writes it into `LiquidityPool.sellRate`/`buyRate`.
6. Attacker repays the flashloan in the same or a subsequent transaction, having only needed to hold the balance across the observation window.
7. Any consumer of `IntentGateway.quoteIntent()` using the default `indexed_rates` strategy now prices orders off the manipulated rate until the next phantom window refreshes it, allowing the attacker's solver to profit off users' subsequently constructed and escrowed orders.
