### Title
`make_signature` omits `signup_id` from the signed digest, enabling attestation replay across signup sessions - ([File: src/plans/enroll_user.rs])

### Finding Description
`make_signature` builds the SHA256 context that is passed to `secure_element::sign` using only `ORB_ID`, `user_qr_code.user_id`, and the iris/mask pipeline codes (`ir_net_version`, `iris_version`, and per-eye `iris_code`/`mask_code`/`iris_code_version`) — it never mixes in the `signup_id` for the current session [1](#0-0) . The `signup_id` is only used afterward as the HTTP URL path segment when submitting the signup (`/api/v2/signups/{signup_id}`) and is completely decoupled from the signature value itself [2](#0-1) .

Because iris/mask code extraction from the biometric pipeline is deterministic for a given physical input, an attacker who can present the exact same face/eyes to the Orb's cameras across two distinct signup sessions (using their own `user_id`, an allowed physical-scene input) will cause `make_signature` to compute an identical SHA256 digest and therefore an identical `secure_element::sign` output on both occasions. The resulting base64 `signature` string sent in `signup_post::request` for `signup_id = A` is byte-identical to the one sent for `signup_id = B`. Nothing in `enroll_user::Plan::run` or `signup_post::request` checks the signup_id-to-signature binding, computes a fresh nonce, or otherwise prevents this — the signature is a static function of biometric + user identity only.

### Impact Explanation
This breaks the intended invariant that the secure-element attestation is unique per signup transaction. A signature meant to attest "these specific iris codes were produced by this hardware's secure element for this signup" can be replayed verbatim across multiple signup_ids for the same user, since orb-core itself supplies no cryptographic binding to `signup_id`. Whether the backend independently re-derives/re-verifies signup uniqueness is outside this repository's scope, but the orb-side attestation-integrity control the code purports to implement (binding a hardware signature to a distinct signup event) does not actually do so, which is a genuine deviation from the stated invariant of the audited function.

### Likelihood Explanation
High feasibility given the stated preconditions: no privileged access, no key/token leakage, and no MCU tampering required — only the ability to present the same face twice (allowed physical-scene input) and to reuse one's own known `user_id`. The pipeline's iris/mask code extraction is deterministic for identical input images, so repeatability is straightforward as long as the same QR user_id and same captured images are used across sessions.

### Recommendation
Mix `signup_id` (and ideally a server-issued nonce/challenge) into the `Context` before calling `secure_element::sign`, e.g. `ctx.update(signup_id.as_bytes())` in `make_signature`, and update the call site in `Plan::run` to pass `signup_id` into `make_signature`. This cryptographically binds the attestation to the specific signup transaction and prevents replay across sessions.

### Proof of Concept
Unit test in `src/plans/enroll_user.rs`:
```rust
#[test]
fn signature_is_not_bound_to_signup_id() {
    let user_qr_code = /* construct fixed qr_scan::user::Data */;
    let pipeline = /* construct fixed Pipeline with identical iris/mask codes */;

    // Simulate what would happen if signup_id were incorporated (it currently is not):
    let sig_a = make_signature(&user_qr_code, &pipeline).unwrap();
    let sig_b = make_signature(&user_qr_code, &pipeline).unwrap();

    // Demonstrates the vulnerability: identical inputs across two different
    // signup sessions (signup_id A vs B, never passed into make_signature)
    // yield identical signatures.
    assert_eq!(sig_a, sig_b, "signature is independent of signup_id — replay possible");
}
```
Pair with an integration-level check on `signup_post::request`: call it twice with the same `signature` value but different `signup_id` strings and confirm the request layer does not reject or alter the `signature` field based on prior use — `signup_post::request` at src/backend/signup_post.rs:100-161 shows no such check exists client-side, and the escaping of the digest binding was already shown to be missing in `make_signature`.

```rust
fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
```
