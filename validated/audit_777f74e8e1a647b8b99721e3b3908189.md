### Title
Unchecked ERC-20 return data on escrow withdrawal/refund allows silent transfer failure with escrow permanently decremented - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.withdraw()` and the `SweepDust`/fee-redemption branches of `onAccept()` release escrowed ERC-20 tokens using a raw low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check the boolean `success` returned by the call (i.e., whether the call reverted), without decoding and checking the ABI-encoded return data that ERC-20's `transfer` is supposed to return.

### Finding Description
In `withdraw()`, escrowed token amounts are released to a beneficiary via:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
``` [1](#0-0) 

The same unchecked pattern is repeated for fee redemption:
```solidity
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
delete _orders[body.commitment][TRANSACTION_FEES];
``` [2](#0-1) 

and in the `SweepDust` handler:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
``` [3](#0-2) 

Per the ERC-20 standard, `transfer` must return a `bool` indicating success. Some tokens (and any non-standard/malicious token registered as an escrow asset) return `false` in the ABI-encoded output data on failure instead of reverting the call. A low-level `.call` only reports `success = true` when the call itself did not revert; it does not verify the decoded boolean result. Because this code checks only `success` and ignores the returned data, a `transfer` that returns `false` (silently failing to move funds) is treated identically to a successful transfer. `withdraw()` is reachable from `onAccept()` for `RequestKind.RedeemEscrow`/`RefundEscrow`, which is invoked by the host when relaying a `RedeemEscrow`/`RefundEscrow` message (with source authenticated via `authenticate()`) after IntentGatewayV2 fills or refunds an order on the counterpart chain — i.e., reachable through the normal cross-chain message-delivery path driven by relayer-submitted proofs. [4](#0-3) 

Elsewhere in the same file, safer patterns are used (`IERC20(token).safeTransferFrom(...)` via OpenZeppelin's `SafeERC20`), which do check the returned boolean, showing the raw `.call` sites are an inconsistency/regression rather than an intentional design choice. [5](#0-4) 

### Impact Explanation
If a non-standard-compliant ERC-20 (one that returns `false` rather than reverting on failure — this can occur for tokens with blacklists, paused states, insufficient allowance/balance edge cases, or deliberately malicious tokens registered for an order) is escrowed:
- `withdraw()` will decrement `_orders[commitment][token]` and emit `EscrowReleased`/`EscrowRefunded` even though the beneficiary never received the tokens, permanently freezing/losing those funds (the escrow accounting says the funds are gone, but they remain stuck in the contract with no further code path to redeem them).
- Fee redemption can similarly mark fees as paid (`delete _orders[...][TRANSACTION_FEES]`) while the relayer/fee recipient receives nothing.
- `SweepDust` can mark dust as swept via `DustSwept` event while tokens remain in the contract.

This is a genuine loss/freezing-of-funds vector rather than a purely cosmetic issue, since accounting state changes irreversibly regardless of transfer success.

### Likelihood Explanation
Likelihood depends on whether the escrowed token is a standard OpenZeppelin-style ERC-20 (which reverts on failure, making this benign) versus a non-standard token that returns `false`. Since `IntentGatewayV2` is a generic intents/token-bridging escrow that can accept arbitrary tokens specified in `TokenInfo.token` for any order, the contract cannot assume the registered token always reverts on failure. This is a realistic risk for any deployment supporting non-canonical ERC-20 tokens.

### Recommendation
Replace all `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only checks in `withdraw()`, the fee-redemption block, and the `SweepDust` handler with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the `safeTransferFrom` usage already present elsewhere in the same contract. This decodes and validates the returned boolean (or absence of return data, per EIP-20 tolerance) and reverts on failure, ensuring escrow state is only decremented when the transfer actually succeeds.

### Proof of Concept
1. Register/escrow a token `T` for an order such that `T.transfer` can return `false` without reverting (e.g., a token with a blacklist check that returns `false` for a blacklisted recipient, or a deliberately crafted "fail-silently" ERC-20).
2. Have the counterpart-chain gateway dispatch a `RedeemEscrow` message for a commitment holding `T`.
3. `onAccept` → `withdraw()` calls `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))`; `T.transfer` executes without reverting but returns `false` (beneficiary is blacklisted, balance insufficient in a way that returns false instead of reverting, etc.).
4. `success == true` is observed by the low-level `.call`, so `TransferFailed()` is not raised; `_orders[body.commitment][token] -= amount` executes and `EscrowReleased` is emitted.
5. The beneficiary never received tokens `T`, yet the escrow record shows the amount as withdrawn — the tokens remain stuck in `IntentGatewayV2` with no remaining code path referencing that now-zeroed-out escrow entry, permanently freezing the funds.
