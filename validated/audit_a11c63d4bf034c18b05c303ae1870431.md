### Title
`terminate_vesting_contract()` is permanently blocked if any shareholder's (or beneficiary's) `CoinStore` is frozen - (File: `aptos-move/framework/aptos-framework/sources/vesting.move`)

### Summary
`vesting.move` implements an APT vesting/staking contract where an admin can call `terminate_vesting_contract()` to stop future vesting and eventually reclaim all remaining stake via `admin_withdraw()`. Before doing anything else, `terminate_vesting_contract()` unconditionally calls `distribute()`, which loops over every shareholder and pushes their withdrawable coins via `aptos_account::deposit_coins`. If the `CoinStore` of any single shareholder (or their designated beneficiary) is frozen, the whole atomic transaction aborts, permanently preventing termination — the exact same custody-DoS pattern as the referenced Sherlock `cancel()`/USDC-blacklist bug, but native to Aptos coin freeze capabilities instead of an ERC-20 blacklist.

### Finding Description
`terminate_vesting_contract()`: [1](#0-0) 

calls `distribute()` first (line 775) before changing `vesting_contract.state` to `VESTING_POOL_TERMINATED`. `distribute()` iterates over `shareholders` and, for each one, resolves a `recipient_address` via `get_beneficiary()` and calls `aptos_account::deposit_coins(recipient_address, share_of_coins)`: [2](#0-1) 

`coin::deposit`/`aptos_account::deposit_coins` aborts with `EFROZEN` if the destination `CoinStore` is frozen, per the coin module's own error definitions and formally-specified invariant: [3](#0-2) [4](#0-3) 

Any coin type that has an active `FreezeCapability` (which `AptosCoin` itself supports via `coin::freeze_coin_store`) lets whoever holds that capability freeze an arbitrary account's `CoinStore`. If a shareholder (or a beneficiary they set via `update_beneficiary`) has a frozen `CoinStore` for the relevant coin, `deposit_coins` inside the `for_each_ref` loop aborts. Because Move transactions are atomic, this single failure reverts the entire `distribute()` call — and therefore also aborts `terminate_vesting_contract()`, since `distribute()` is called unconditionally at its very start, before any state is mutated.

This mirrors the Sherlock bug's root cause exactly: a privileged "cancel/terminate" custody-control operation is entangled with an unconditional push-payment to a party whose receiving capability an attacker (or any freeze-capability holder) can disable, thereby holding the entire flow hostage.

### Impact Explanation
This blocks admin control over the vesting contract's staked funds indefinitely:
- The admin cannot terminate the contract, so `vesting_contract.remaining_grant` is never zeroed and the stake is never unlocked.
- `admin_withdraw()` requires `state == VESTING_POOL_TERMINATED` and therefore can never be called either: [5](#0-4) 
- All shareholders in the same pool are collectively locked out, not just the one whose store got frozen, since `distribute()` fails as a whole atomic loop.
- This is a permanent, non-recoverable loss/lock of value custody-controlled by the vesting contract (APT stake and rewards) for the admin/all shareholders, satisfying the "Permanent lock or non-recoverable loss of ... resource-account-held value" custody-gate criterion.

### Likelihood Explanation
Likelihood is scenario-dependent: it requires that the coin type used for vesting have an active freeze capability holder distinct from the vesting admin (for `AptosCoin` this is the framework/governance-controlled freeze cap; for custom coins used in employee-vesting style contracts it could be the token issuer). Any such coin-freeze authority — legitimate or compromised — can trigger this DoS on any active vesting contract by freezing one shareholder's or beneficiary's store. Given `update_beneficiary` lets a shareholder redirect distributions to an arbitrary address they don't fully control the freeze status of, this can also be self-inflicted or externally forced without admin cooperation.

### Recommendation
Decouple `terminate_vesting_contract()` from `distribute()`'s per-shareholder push payments:
- Have `terminate_vesting_contract()` skip or catch failures in individual per-shareholder deposits (e.g., accumulate undistributed amounts into a claimable/pull-based balance per shareholder rather than pushing in a loop that can revert the whole batch).
- Alternatively, make distribution failure-tolerant per shareholder (try/skip pattern is not natively available in Move without restructuring, so consider moving to a pull-based `claim()` model similar to the Sherlock recommendation: store amounts owed and let the shareholder/beneficiary claim later), so that termination and stake unlocking are not gated on any specific recipient successfully receiving funds immediately.

### Proof of Concept
1. Admin creates a vesting contract with shareholders `[A, B]` via `create_vesting_contract`.
2. The coin type used for vesting (or `AptosCoin` if governance/framework performs a freeze) has its `FreezeCapability` used to call `coin::freeze_coin_store(B_address, &freeze_cap)`, freezing B's `CoinStore`.
3. Time passes; stake becomes withdrawable. Admin calls `terminate_vesting_contract(admin, contract_address)`.
4. Internally this calls `distribute(contract_address)`, which loops through shareholders `[A, B]`. When it reaches B and calls `aptos_account::deposit_coins(B_address, share_of_coins)`, the call aborts with `EFROZEN` (`coin.move` line 58-59) because B's `CoinStore.frozen == true`.
5. The abort propagates up through `distribute()` and `terminate_vesting_contract()`, so the transaction reverts entirely — `vesting_contract.state` is never set to `VESTING_POOL_TERMINATED`, `remaining_grant` is never zeroed, and stake is never unlocked, for both A and B.
6. Every subsequent retry of `terminate_vesting_contract` on this contract fails identically as long as B's store remains frozen, permanently locking the admin out of terminating/reclaiming the vesting contract's stake.

Note: I could not fully verify at what point in the mainnet lifecycle (or via which specific governance/coin-issuer flows) `AptosCoin`'s `FreezeCapability` is actually held/used in practice versus custom coins used for vesting; this affects real-world likelihood but not the validity of the code-level custody-invariant break itself.

    /// Distribute any withdrawable stake from the stake pool.
    public entry fun distribute(contract_address: address) acquires VestingContract {
        assert_active_vesting_contract(contract_address);

        let vesting_contract = borrow_global_mut<VestingContract>(contract_address);
        let coins = withdraw_stake(vesting_contract, contract_address);
        let total_distribution_amount = coin::value(&coins);
        if (total_distribution_amount == 0) {
            coin::destroy_zero(coins);
            return
        };

        // Distribute coins to all shareholders in the vesting contract.
        let grant_pool = &vesting_contract.grant_pool;
        let shareholders = &grant_pool.shareholders();
        shareholders.for_each_ref(|shareholder| {
            let shareholder = *shareholder;
            let shares = pool_u64::shares(grant_pool, shareholder);
            let amount = pool_u64::shares_to_amount_with_total_coins(grant_pool, shares, total_distribution_amount);
            let share_of_coins = coin::extract(&mut coins, amount);
            let recipient_address = get_beneficiary(vesting_contract, shareholder);
            aptos_account::deposit_coins(recipient_address, share_of_coins);
        });

        // Send any remaining "dust" (leftover due to rounding error) to the withdrawal address.
        if (coin::value(&coins) > 0) {
            aptos_account::deposit_coins(vesting_contract.withdrawal_address, coins);
        } else {
            coin::destroy_zero(coins);
        };

        emit(
            Distribute {
                admin: vesting_contract.admin,
                vesting_contract_address: contract_address,
                amount: total_distribution_amount,
            },
        );
    }

    /// Terminate the vesting contract and send all funds back to the withdrawal address.
    public entry fun terminate_vesting_contract(admin: &signer, contract_address: address) acquires VestingContract {
        assert_active_vesting_contract(contract_address);

        // Distribute all withdrawable coins, which should have been from previous rewards withdrawal or vest.
        distribute(contract_address);

        let vesting_contract = borrow_global_mut<VestingContract>(contract_address);
        verify_admin(admin, vesting_contract);
        let (active_stake, _, pending_active_stake, _) = stake::get_stake(vesting_contract.staking.pool_address);
        assert!(pending_active_stake == 0, error::invalid_state(EPENDING_STAKE_FOUND));

        // Unlock all remaining active stake.
        vesting_contract.state = VESTING_POOL_TERMINATED;
        vesting_contract.remaining_grant = 0;
        unlock_stake(vesting_contract, active_stake);

        emit(
            Terminate {
                admin: vesting_contract.admin,
                vesting_contract_address: contract_address,
            },
        );
    }
