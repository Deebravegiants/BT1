I found a concrete analog of this bug class, but it is a genuinely important finding: `evm/tron/contracts/apps/IntentGatewayV2.sol` (the Tron variant of the IntentGateway) contains exactly the same "unset default value silently equals a legitimate sentinel/self value" flaw that the Anchor `Program<T>` advisory describes, and unlike the LayerZero endpoint adapter (`sdk/packages/lz-endpoint/contracts/HyperbridgeLzEndpoint.sol`), which has already been patched for this exact class of bug (`expectedEid == 0` explicit rejection added, per the `testOnAcceptRejectsSrcEidZeroFromUnregisteredSource` regression test), the Tron gateway's `instance()`/`authenticate()` pair still has the unfixed collapse.

### Title
Unregistered-instance default collapses to `address(this)`, allowing spoofed cross-chain message authentication - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.instance()` on the Tron deployment returns `address(this)` whenever no peer gateway is registered for a given `stateMachineId`, rather than reverting like the canonical EVM implementation does. `authenticate()` then compares the incoming request's `from` field against this fallback value, so a message whose `from` field is set to the local gateway's own address is treated as coming from "itself" — passing authentication for any `stateMachineId` that was never explicitly registered as a peer.

### Finding Description
The canonical EVM `IntentGatewayV2` reverts with `UnknownInstance` when no deployment is registered for a `stateMachineId`: [1](#0-0) 

The Tron variant instead silently substitutes `address(this)` as a default: [2](#0-1) 

That default is then used directly as the trust anchor in `authenticate()`, which is the sole gate protecting `onAccept`/`onGetResponse` from forged deliveries: [3](#0-2) 

This is structurally identical to the Anchor `Program<T>` bug: a generic/unset case (`T = ()`, `stateMachineId` never registered) is defaulted to a sentinel value (`Pubkey::default()`, `address(this)`) that also happens to be a *legitimate, trusted value* in the same comparison (the System program id / the gateway's own address). Any caller who can get a message accepted by the local ISMP host with `request.from == address(gateway)` and `request.source` set to *any state machine the gateway operator never explicitly registered as a peer* passes `authenticate()`, because `instance(unregistered_source)` resolves to `address(this)` which trivially equals `module` when `request.from` is the gateway's own address.

In this same file, `HyperbridgeLzEndpoint.sol` demonstrates the fixed version of this exact bug class (a reverse-map default of `0` colliding with a legitimate `srcEid = 0`), and its regression test explicitly documents the "pre-fix" collapse and the fix (`expectedEid == 0` check) — confirming the project's own engineers recognize this failure mode as a genuine, previously-exploited vulnerability class: [4](#0-3) [5](#0-4) 

The Tron `IntentGatewayV2.sol` was not brought in line with this fix.

### Impact Explanation
`authenticate()` gates `onAccept`/`onGetResponse`, which release escrowed funds (`RedeemEscrow`), refund funds (`RefundEscrow`), and apply governance-configured parameters (`UpdateParams`, `NewDeployment`, `SweepDust`) sent as ISMP `PostRequest`/`GetResponse` bodies from a "trusted peer gateway." Because any state machine ID that the operator has not yet explicitly registered via a `NewDeployment` action resolves to `address(this)`, an unprivileged attacker who can dispatch or relay an ISMP message whose `from` field equals the Tron gateway's own address (spoofing the sender field, which is attacker-controlled bytes at the ISMP layer for an unregistered source chain) can forge a `RedeemEscrow`/`RefundEscrow`/`SweepDust` action and drain escrowed order funds, or forge `UpdateParams`/`NewDeployment` to hijack gateway configuration. This is concrete theft/permanent freezing of escrowed intent funds, matching the "unauthorized app action" / "unsound message delivery" impact bar.

### Likelihood Explanation
Reachable by a single relayed message from an unprivileged relayer — no admin, governance, or validator compromise required. The only precondition is that the destination `stateMachineId` used in the forged request has not yet been explicitly registered as a peer deployment (true for any chain the gateway operator hasn't onboarded yet, which is the common case for a newly deployed or partially-configured gateway, and is permanently true for any state machine the operator never intends to onboard but that ISMP still permits routing from).

### Recommendation
Change `instance()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to revert (e.g. with `UnknownInstance`) when `_instances[keccak256(stateMachineId)] == address(0)`, matching the canonical `evm/src/apps/intentsv2/IntentsBase.sol::_instance` behavior, instead of silently returning `address(this)`. Add a regression test mirroring `testOnAcceptRejectsSrcEidZeroFromUnregisteredSource` that asserts a request from an unregistered `stateMachineId` with `from == address(this)` is rejected.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with peer deployments registered only for chains A and B (never for chain C).
2. Attacker (any unprivileged relayer) submits/relays an ISMP `PostRequest` to the local ISMP host with:
   - `source = <encoding of chain C>` (unregistered)
   - `from = abi.encodePacked(address(gateway))` (the gateway's own address on Tron)
   - `body` = an encoded `RedeemEscrow` (or `SweepDust`) request targeting attacker-controlled beneficiary/commitment.
3. The host calls `IntentGatewayV2.onAccept`, which calls `authenticate(request)`.
4. `instance(request.source)` looks up `_instances[keccak256(chain C)]`, finds it unset (`address(0)`), and returns `address(this)` per: [6](#0-5) 
5. `module == address(bytes20(request.from)) == address(this) == instance(request.source)`, so the `Unauthorized` check is bypassed and the forged `RedeemEscrow`/`SweepDust` body is executed, releasing escrowed tokens to the attacker.
