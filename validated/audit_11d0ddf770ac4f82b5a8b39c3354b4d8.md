### Title
Webhook shop-domain/topic headers are not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body alone, while the `shop`, `topic`, `webhook_id`, and `api_version` values that the gem hands to application webhook handlers as trusted identity metadata come from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` only validates that the body was signed with the app's `api_secret_key`; it never binds that signature to the `shop-domain` header it forwards to the handler. This breaks the identity binding `hmac(body, api_secret_key) == valid ⇒ shop header == originating shop`, which does not hold.

### Finding Description
`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string`. [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw request body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, which are entirely outside the HMAC computation: [3](#0-2) 

`Registry.process` checks the HMAC and then dispatches the handler using the unauthenticated `request.shop` and `request.topic` values as trusted identity for the event: [4](#0-3) 

`WebhookMetadata.shop` is documented and consumed by host apps as "The shop domain of the webhook" and is expected to be trustworthy for routing/tenant-scoping decisions: [5](#0-4) [6](#0-5) 

Because `api_secret_key` (the app's `client_secret`) is the same value for every merchant that has the app installed, any merchant who has installed the app can trigger a genuine webhook from Shopify to their own account and legitimately obtain a valid `body`/HMAC pair signed with the shared secret. That attacker can then replay the exact same body and HMAC to the app's webhook endpoint while altering the `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) headers to claim the event belongs to a different shop. `HmacValidator.validate` will still pass, because it never inspects the headers, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the spoofed shop, with a body the attacker fully controls (their own store's data).

This is precisely the analog of the reported bug class: a field (`shop`/`topic`) that is acted upon downstream (tenant/shop-scoped business logic, `perform_later(topic:, shop_domain:, webhook:)` as shown in the docs example) but is not bound by the cryptographic check that gates trust in the request.

### Impact Explanation
This crosses a tenant boundary: an attacker with a legitimate but unprivileged Shopify account and merely app-installation privileges (no `api_secret_key`, no access token, no elevated privilege) can inject attacker-controlled webhook payloads that are misattributed to an arbitrary other shop. Any host application that uses `WebhookMetadata#shop` to key data updates, cache invalidation, notifications, billing triggers, or any tenant-scoped side effect (exactly as illustrated in the gem's own documented usage example) would apply attacker-controlled data under a victim shop's identity. This satisfies the "cross-tenant access" criterion for a Critical/High-impact finding, since it lets one tenant impersonate another tenant's identity within the app's own webhook-processing trust boundary that this gem establishes.

### Likelihood Explanation
Likelihood is high for any app built directly on this gem's documented API and webhook flow (as shown in `docs/usage/webhooks.md`) with no additional out-of-band verification: any user who can install the app to a store (a normal unprivileged onboarding action) can trigger a real Shopify webhook to obtain a fresh, valid `body`/HMAC pair, then simply resend it to the app's public webhook endpoint with modified `shop`/`topic` headers. No secrets, tokens, or privileged access are required beyond the attacker's own store.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable content, or otherwise cryptographically bind the shop/topic to the verified payload before exposing them via `WebhookMetadata`. At minimum, `Registry.process` should independently confirm that the `shop` claimed in the headers is one that legitimately has (or previously had) this webhook registered/expected, rather than trusting the header value outright once only the body's HMAC has been checked.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged action).
2. Attacker triggers a real webhook event in their own store (e.g., updates a product), causing Shopify to POST a JSON body `B` to the app's webhook endpoint with header `x-shopify-hmac-sha256 = HMAC_SHA256(app_secret, B)` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures `B` and the valid HMAC value.
4. Attacker resends `B` with the same valid HMAC header but with `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`) directly to the app's public webhook endpoint.
5. `Utils::HmacValidator.validate` (via `lib/shopify_api/utils/hmac_validator.rb`, called from `Registry.process` in `lib/shopify_api/webhooks/registry.rb:190`) passes, because it only checks `B` against the secret.
6. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: B, ...)`, causing the host application to process attacker-controlled data under the victim shop's identity.
