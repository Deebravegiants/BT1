### Title
Unbounded rounding leak in `Router._computeSell`/`_computeBuy` lets an unprivileged trader erode a curve pair's `assetReserve` below the virtual seed, causing an unrecoverable arithmetic-underflow revert that permanently bricks buys and graduation - (File: `packages/contracts/src/Router.sol`, `packages/contracts/src/Bonding.sol`)

### Summary
CVE-2023-37017 is a class of bug where a value that is implicitly assumed to always be present/consistent is missing or malformed, and the code hits an unchecked assertion that crashes the process on every subsequent message. Alt.fun has a structural analog: `Bonding.canGraduate` and `Bonding._prepareGraduationLiquidity` both compute `assetReserve - _launchTimeVirtualLtReserve(...)` with no floor/guard, assuming the pair's stored `assetReserve` can never fall below the immutable launch-time virtual seed [1](#0-0) . That assumption is only true if every swap preserves the constant-product invariant exactly. It does not: `Router._computeSell` and `Router._computeBuy` use floor division when deriving the post-trade reserve, which rounds strictly in the trader's favor on every single trade [2](#0-1) [3](#0-2) . Over enough permissionless round-trip trades this steadily erodes `assetReserve` below the exact K-preserving value; `Pair.swap`'s own K check only rejects gross violations (`(newTokenReserve+1)*(newAssetReserve+1) < k`), not this rounding drift [4](#0-3) . Once `assetReserve` drops below `_launchTimeVirtualLtReserve`, the unchecked subtraction underflows (Solidity Panic 0x11) inside `canGraduate`, which is called unconditionally at the end of every buy via `Bonding._executeBuy` [5](#0-4) , permanently reverting every future buy on that token — an unrecoverable, remotely-triggerable DoS analogous to the repeatedly-triggerable MME assertion crash in the CVE.

### Finding Description
`canGraduate` and `_prepareGraduationLiquidity` derive the "real LT raised" by subtracting the recovered launch-time virtual reserve from the pair's stored `assetReserve`:

```solidity
uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
``` [6](#0-5) 

and

```solidity
ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
``` [7](#0-6) 

Both assume `assetReserve >= virtualLtReserve` always holds as a mathematical invariant of the curve. That invariant depends on `Router`'s swap math being exact, but it is not:

- `_computeSell` sets the post-trade `newReserveAsset` implicitly to `floor(k / newReserveToken)`, and pays out `assetOut = reserveAsset - floor(k / newReserveToken)`, which is always `>=` the exact real-valued amount a perfect constant-product curve would pay — i.e. it rounds in the trader's favor by up to just under 1 wei per call [2](#0-1) .
- `_computeBuy`'s capped-overflow branch performs a similar ceiling/floor combination that also leaks sub-wei value on the boundary case [3](#0-2) .
- `Pair.swap`'s only defense is a coarse K-floor check with a `+1` slack on both reserves, which is far looser than "no rounding drift" and does not catch this erosion [8](#0-7) .

Because `sell`/`buy` are reachable by any unprivileged trader through `Bonding.buy`/`Bonding.sell` (and their `Zap` wrappers), and because trading a token back and forth (small buy immediately followed by a small sell of the tokens received) is a legitimate, permissionless, repeatable action, an attacker can drive `assetReserve` down by ~1 wei per round trip with no economic loss beyond gas and the protocol fee, until `assetReserve` falls below `virtualLtReserve`. At that point:

- Every future `Bonding.buy` reverts with an unhandled `Panic(0x11)` (arithmetic underflow) inside `canGraduate`, called unconditionally from `_executeBuy` [9](#0-8) .
- `Bonding.triggerGraduation` and `previewLtUntilGraduation` hit the same unguarded subtraction and also revert [10](#0-9) [11](#0-10) .
- The token is permanently stuck in `Lifecycle.Curve`: it can never graduate (the buy that would flip it always panics before completing), and holders can only ever sell into whatever LT remains in the curve, which never recovers because no further buys can land.

This is the direct structural analog of the CVE: an unbounded assumption ("assetReserve always dominates the virtual seed" ≈ "S1Setup Request always carries Global eNB ID") that isn't runtime-validated, and whose violation triggers an unhandled low-level assertion/panic reachable by an ordinary, unprivileged remote party, repeatedly, with no recovery path.

### Impact Explanation
Once tripped, the bug permanently freezes the curve for that token: no further buys can execute (every one panics before completing), the token can never reach graduation (so it can never seed the HyperSwap LP or unlock the funds parked for graduation), and any LT already raised by traders is trapped in the curve pair with no route out except partial sells until liquidity runs dry. This is a permanent freezing-of-funds outcome for every trader and the creator of that token, and it is triggerable by any single unprivileged wallet.

### Likelihood Explanation
The mechanism (per-trade rounding drift favoring the caller) is deterministic and always present, but the magnitude per round trip is at most a few wei against reserves denominated in 18-decimal LT amounts on the order of thousands of tokens. Reaching the underflow condition purely through this leak therefore requires a very large number of automated round-trip transactions (bounded only by gas cost, not by any protocol-enforced limit), making this a low-cost-per-step but high-transaction-count attack rather than a one-shot exploit. Likelihood is Medium: it is fully permissionless, requires no special conditions or races, and is bounded only by attacker patience/gas budget, but is not a single-transaction trigger like the original CVE.

### Recommendation
- Add an explicit invariant check in `Router._computeSell`/`_computeBuy` (or in `Pair.swap`) that rejects any swap whose resulting `assetReserve`/`tokenReserve` would go below the values implied by exact (non-floored) constant-product math, rather than relying on the loose `+1` slack check.
- Alternatively/additionally, replace the unguarded subtractions in `Bonding.canGraduate`, `Bonding.previewLtUntilGraduation`, and `Bonding._prepareGraduationLiquidity` (`assetReserve - _launchTimeVirtualLtReserve(...)`) with a saturating subtraction (as is already done defensively for `ltBalance - p.ltFromPair` in `finalizeGraduation`, see `packages/contracts/src/Bonding.sol:1019-1020`) so a violated invariant degrades gracefully (`realLtRaised = 0`) instead of reverting every future call.
- Round all `Router` sell/buy math consistently against the trader (ceil the amount taken from the trader / floor the amount paid to the trader) so the invariant `assetReserve >= virtualLtReserve` is provably monotonic rather than merely "expected."

### Proof of Concept
1. Launch a token via `Zap.createToken` with a modest seed buy, establishing a `Pair` with `assetReserve = virtualLtReserve` initially.
2. From an unprivileged wallet, repeatedly call `Zap.buy(token, minUsdcAmount, ...)` followed immediately by `Zap.sell(token, tokensJustReceived, 0)` (or the underlying `Bonding.buy`/`Bonding.sell` directly if bypassing the USDC/LT layering) in a loop.
3. Each `sell` round trip pays out `assetOut = reserveAsset - floor(k / newReserveToken)` per `Router._computeSell` (`packages/contracts/src/Router.sol:172-182`), which is `>=` the exact curve amount; repeated over enough iterations this strictly decreases `assetReserve` relative to the exact invariant, independent of the trader's own gains/losses on each individual trade.
4. Once accumulated drift pushes `assetReserve` below `_launchTimeVirtualLtReserve(token, pair)` (`packages/contracts/src/Bonding.sol:1114-1119`), the next `Bonding.buy` call panics inside `canGraduate`'s `assetReserve - _launchTimeVirtualLtReserve(...)` subtraction (`packages/contracts/src/Bonding.sol:691-693`), reverting with `Panic(0x11)`.
5. Confirm all subsequent `Bonding.buy`, `Bonding.triggerGraduation`, and `Bonding.previewLtUntilGraduation` calls for that token now revert unconditionally, and the token can never reach `Lifecycle.Graduating`/`Graduated`.

Note: the exact number of round trips required to trip the underflow was not empirically measured here — this would need to be validated with a Foundry fuzz/invariant test (extending `test/GraduationInvariants.t.sol`) driving thousands of alternating buy/sell calls and asserting `assetReserve >= virtualLtReserve` holds at every step, since the current test suite does not appear to cover this specific rounding-erosion invariant.

    function previewLtUntilGraduation(
        address token_
    ) external view returns (uint256) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return 0;
        if (info.lifecycle != Lifecycle.Curve) return 0;

        address pair = info.pair;
        uint256 realBalance = IPair(pair).tokenBalance();
        if (realBalance == 0) return 0;

        (uint256 reserveToken, uint256 reserveAsset) = IPair(pair).getReserves();

        uint256 ltUntilThreshold = type(uint256).max;
        uint256 exchangeRate = IBounceLeveragedToken(info.ltAddress).exchangeRate();
        if (exchangeRate > 0) {
            uint256 realLtRaised = reserveAsset - _launchTimeVirtualLtReserve(token_, pair);
            uint256 thresholdRealLt = ($.graduationThresholdUsd * 1e18 + exchangeRate - 1) / exchangeRate;
            if (realLtRaised >= thresholdRealLt) return 0;
            ltUntilThreshold = thresholdRealLt - realLtRaised;
        }

        // Donation-inflated `realBalance`: supply trigger unreachable, defer to USD leg.
        if (realBalance >= reserveToken) return ltUntilThreshold;

        uint256 cappedReserveToken = reserveToken - realBalance;
        uint256 cappedReserveAsset = (IPair(pair).k() + cappedReserveToken - 1) / cappedReserveToken;
        uint256 ltUntilSupply = cappedReserveAsset - reserveAsset;

        return ltUntilSupply < ltUntilThreshold ? ltUntilSupply : ltUntilThreshold;
    }

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
