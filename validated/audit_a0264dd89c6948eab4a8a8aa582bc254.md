## Title
Creator fee balances become permanently frozen in `FeeVault` if the creator's address is later blacklisted by the USDC contract - ([File: packages/contracts/src/FeeVault.sol])

### Summary
`FeeVault.creatorBalance` is a `mapping(address creator => uint256)` that accrues USDC fees keyed to the creator address recorded at each `_accrueFee` call. `FeeVault.claim()` always pays out to `msg.sender`, with no way to redirect the payout to an alternate address. `Bonding.transferCreator` lets a creator reassign the *future* fee-attribution address, but it never touches the already-accrued `creatorBalance` entry keyed to the old address. If USDC's issuer blocklists the old creator address (a routine, well-documented capability of the real USDC contract), the accrued balance under that address becomes permanently unclaimable, exactly mirroring the reported bug class where a `receiver` address fixed at an earlier step cannot be changed once a token contract blocks it.

### Finding Description
Fees accrue via `Zap._accrueFee`, which reads the creator from `Bonding.creatorOf(tokenAddress)` at the time of each trade and forwards USDC to `FeeVault.accrue`: [1](#0-0) 

`FeeVault.accrue` credits `creatorBalance[creator] += creatorAmount`: [2](#0-1) 

The only way to withdraw is `claim()`, which is hard-wired to pay `msg.sender` — there is no `receiver` parameter and no admin/creator override path: [3](#0-2) 

`Bonding.transferCreator` is the only mechanism to change a creator's address, but it only updates `info.creator` for *future* fee attribution — it does not move or re-key the `creatorBalance` mapping entry that has already accrued under the old address: [4](#0-3) 

Since `IERC20(usdc).safeTransfer(msg.sender, amount)` in `claim()` will revert if `msg.sender` (the old creator) is on USDC's blocklist, and since `transferCreator` cannot rescue the already-accrued balance sitting under `creatorBalance[oldCreator]`, that USDC is stuck in `FeeVault` permanently once the old creator address is blocked — with no owner-level or creator-level path to redirect it, unlike `claimProtocol`/`sweepDonations` which pay a mutable, admin-controlled `feeTo`.

### Impact Explanation
This is a permanent freeze of legitimate creator funds inside `FeeVault`, not a griefing/no-impact issue — the USDC becomes economically stranded (still backing `totalAccruedCreator`, so it can't even be swept via `sweepDonations`, which only sweeps the *unbacked* surplus). Any creator address later added to USDC's (or USDT's) blocklist loses all not-yet-claimed fee income with no recovery mechanism reachable by an unprivileged trader/creator or by the protocol owner.

### Likelihood Explanation
Reaching this state requires no privileged action and no protocol bug beyond the missing redirect mechanism: a creator simply needs to accrue fees (normal `Zap.buy`/`Zap.sell` activity on their launched token) and then be added to USDC's blocklist — a real-world event outside the protocol's control but explicitly the threat model the reported bug class addresses. Given USDC/USDT blocklisting is an established, exercised capability of the token issuers, this is a realistic Medium-likelihood scenario for any active creator.

### Recommendation
Add an owner- or creator-controlled path to reassign an *already-accrued* `creatorBalance` from one address to another (e.g., extend `transferCreator` or add a dedicated `FeeVault.reassignBalance(oldCreator, newCreator)` gated by `msg.sender == oldCreator` or protocol owner), or add a `claimTo(address receiver)` variant that lets `msg.sender` designate an alternate payout address before the transfer is attempted, mirroring the original report's recommendation of decoupling the stored beneficiary from the final transfer target.

### Proof of Concept
1. Creator `C` launches a token via `Zap.createToken`; trades accrue fees to `FeeVault.creatorBalance[C]` via `Zap._accrueFee` → `FeeVault.accrue`.
2. USDC's issuer adds `C` to its blocklist (out-of-protocol event).
3. `C` calls `Bonding.transferCreator(tokenAddress, newAddress)` to redirect *future* fees — this succeeds and updates `info.creator`, but `FeeVault.creatorBalance[C]` (the already-accrued balance) is untouched, per `Bonding.sol:738-748`.
4. `C` (or anyone acting for `C`) calls `FeeVault.claim()`. Since `msg.sender` must equal `C` to read `creatorBalance[C]`, and `IERC20(usdc).safeTransfer(C, amount)` reverts because `C` is blocklisted by USDC, the call always reverts.
5. There is no other function in `FeeVault` or `Bonding` that can move `creatorBalance[C]` to a new, unblocked address — the USDC is permanently locked in `FeeVault`.

```text
    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }
```

```text
    function claim() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
        emit CreatorFeesClaimed(msg.sender, amount);
    }
```

```text
        address tokenAddress,
        address newCreator
    ) external {
        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
```
