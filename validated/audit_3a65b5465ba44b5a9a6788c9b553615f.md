### Title
Donated LT Permanently Trapped in Curve `Pair` With No Recovery Mechanism - (File: `packages/contracts/src/Router.sol`, `packages/contracts/src/Pair.sol`, `packages/contracts/src/Bonding.sol`)

### Summary
Any address can permissionlessly send `IERC20(lt).transfer(pairAddr, amount)` directly to a bonding-curve `Pair` before graduation. That LT balance is excluded from graduation's LP-seeding math and stays in the `Pair` forever — there is no on-chain function, before or after graduation, that can move it out again. This mirrors the referenced `LiquidityReward` bug class: funds are correctly excluded from the "active" accounting path (to preserve invariants) but the protocol provides no sweep/rescue mechanism for the excluded balance, permanently freezing it in the contract.

### Finding Description
`Router.graduate()` is the only function capable of invoking `Pair.transferAsset`, which is itself gated `onlyRouter` [1](#0-0) . `graduate` is only reachable via `Bonding._prepareGraduationLiquidity`, and it drains only the *computed* `ltFromPair = storedAssetReserve - virtualLtReserve`, explicitly excluding any LT donated directly to the pair via ERC20 `transfer` [2](#0-1) .

The protocol's own natspec confirms this is permanent and unreachable once the token's lifecycle passes `Curve`: "the leftover is unreachable as long as (a) `BONDING_ROLE` is not granted to any other address, and (b) future `Bonding` upgrades preserve the lifecycle gate" [3](#0-2) . Test coverage explicitly asserts this donation remains locked post-graduation: `assertEq(IPair(pairAddr).assetBalance(), donation, "donated LT must remain locked in the curve pair")` [4](#0-3) , and `Router.t.sol` confirms `graduate` deliberately leaves any donation behind in the pair [5](#0-4) .

After graduation, `Bonding`'s only remaining privileged action toward the pair is none — `Router.graduate` cannot be called again (the lifecycle gate blocks it), and `Pair` exposes no owner/admin withdrawal function at all [6](#0-5) . The donated LT is stranded in the `Pair` contract indefinitely.

### Impact Explanation
Any LT sent directly to a `Pair` (by mistake, by a well-meaning donor, or by any third-party integration) is permanently frozen with no path to recovery for the depositor, the token creator, or the protocol. This is a genuine, irreversible loss of funds — the same "trapped liquidity" bug class as the referenced finding, just triggered by direct-transfer donations into the AMM pair rather than a stopped reward campaign.

### Likelihood Explanation
The `Pair` address is discoverable on-chain (`Factory.getPair`/`Bonding.tokenInfo`), and nothing prevents any external address, wallet, or contract from calling a standard ERC20 `transfer` to it at any time before or after graduation. This requires no special privilege — it is a fully permissionless, single-transaction action reachable by any unrelated wallet, matching the explicitly allowed reachable-path list ("direct ERC20 transfers of a launched Token or an LT into Pair").

### Recommendation
Add a permissioned or permissionless sweep function (analogous to `FeeVault.sweepDonations()`, which already exists for exactly this purpose on the fee side [7](#0-6) ) that lets the protocol owner (or anyone, routed to a fixed recipient) recover LT balance in a `Pair` beyond `assetReserve` post-graduation, mirroring the existing `_sweepLTToOwner` pattern already used for rebalance residue in `Bonding.finalizeGraduation` [8](#0-7) .

### Proof of Concept
1. `Bonding.launch(...)` creates `tokenAddr` and its `Pair`.
2. Any wallet (not the creator, not a trader) mints or holds LT and calls `IERC20(lt).transfer(pairAddr, X)` directly — no approval or router interaction needed.
3. The curve trades normally; `X` is excluded from `canGraduate`'s USD trigger (per `test_inv_donation_doesNotTrigUsdGraduation`) and excluded from `ltFromPair` at graduation (per `test_graduate_leavesDonationBehind`).
4. `Bonding.triggerGraduation` / `finalizeGraduation` complete the two-phase graduation; `X` remains in the `Pair` (`assertEq(IPair(pairAddr).assetBalance(), donation, ...)`).
5. Post-graduation, no function exists on `Pair`, `Router`, or `Bonding` that can move `X` out — `Router.graduate` is unreachable (lifecycle no longer `Curve`), and `Pair.transferAsset` has no other caller. `X` is permanently stuck.
