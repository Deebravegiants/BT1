## Finding: Webhook `shop` identity is not covered by the HMAC signature

### Title
Webhook shop-domain identity used by handlers is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands the caller a `WebhookMetadata` object built from `request.shop`, a value taken straight from the (unsigned) `shop-domain` header. Because the shop identity is never part of the signed bytes, an attacker who owns a legitimate Shopify store can capture a validly-signed webhook payload issued for their own store and replay it to the victim app's webhook endpoint with a forged `shop-domain` header, and the signature will still verify.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` performs a single check to authenticate the whole request: [1](#0-0) 

That check calls `Utils::HmacValidator.validate`, which computes/compares the signature only over `verifiable_query.to_signable_string`: [2](#0-1) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only the raw body — the `shop-domain` header used for the `shop` accessor is completely excluded from what gets signed: [3](#0-2) 

Yet `shop` is exactly the field the gem hands to the host application as the tenant identity in `WebhookMetadata`, right after the HMAC check passes: [4](#0-3) 

The gem's own documentation instructs integrators to key downstream tenant-scoped processing (job queues, `shop_domain`) directly off this unauthenticated field: [5](#0-4) 

This is the binding break: the equality the app relies on is `hmac_signed(body) == valid AND request.shop == "the shop that produced this body"`. In reality only the first half is checked — `to_signable_string` (signed) ≠ `shop-domain header` (used for identity), so nothing prevents an attacker from decoupling them.

### Impact Explanation
An attacker who registers their own (free/trial) Shopify store can trigger real webhook deliveries with attacker-controlled body content (e.g. `orders/create`, `products/update`) signed with the app's real `api_secret_key` (Shopify signs it, not the attacker). The attacker intercepts/replays that exact `raw_body` + `X-Shopify-Hmac-Sha256` pair to the target app's public webhook endpoint, but substitutes the `X-Shopify-Shop-Domain` header with a victim merchant's domain. `Utils::HmacValidator.validate` still passes because it never inspects the shop header, and the app's handler receives `WebhookMetadata` claiming the (attacker-authored) data belongs to the victim shop. Any host logic that trusts `data.shop` to select the tenant context (as the docs themselves recommend) will process/store attacker-supplied data under the victim's identity — a cross-tenant data-integrity break reachable by any unprivileged internet user who can register a store and hit the target's public callback route.

### Likelihood Explanation
High likelihood of reachability: webhook endpoints are public, unauthenticated HTTP routes by design; obtaining a signed body only requires owning any Shopify dev/partner store subscribed to the target app, which is trivial for any internet user. No secrets, tokens, or privileged access are required — only the ability to replay an HTTP request with a modified header.

### Recommendation
Bind the shop identity to the signed payload before trusting it: verify `request.shop` against the shop associated with the specific `webhook_id`/subscription that was registered (e.g., cross-check against the app's own stored registration/session for that shop), or require the host application to independently confirm that the `shop-domain` header corresponds to a shop that has an active, previously-established session/install record before acting on `data.shop`. At minimum, update the documented example and `WebhookMetadata` guidance to make clear that `shop` is unauthenticated and must not be used as a sole tenant key.

### Proof of Concept
1. Attacker creates a free Shopify development store `attacker.myshopify.com` and installs the victim app on it, subscribing to `orders/create` webhooks.
2. Attacker creates an order in their own store, causing Shopify to POST a legitimately HMAC-signed webhook to the app's callback URL with:
   - `X-Shopify-Hmac-Sha256: <valid signature over raw_body>`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - `raw_body` containing attacker-chosen order data.
3. Attacker captures this exact `raw_body` + `X-Shopify-Hmac-Sha256` pair (it is delivered to their own server, e.g. by re-pointing the webhook `path`/using a proxy configuration during their own subscription flow, or via `Registry.register` argument they control for their own store).
4. Attacker sends a new HTTP POST directly to the target app's public webhook route with the identical `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` — validation succeeds.
6. The app's handler receives `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: <attacker data>, ...)` and processes/stores the attacker's payload as if it originated from the victim shop.
