### Title
Webhook shop-tenant identity spoofable because `shop-domain` header is not covered by HMAC verification - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC verification performed in `Registry.process` proves only that the *body* was signed by Shopify with the app's shared secret — it proves nothing about the `shop-domain` (or `topic`/`api-version`/`webhook-id`) HTTP headers. `Registry.process` nonetheless takes `request.shop` (sourced solely from the unauthenticated `shop-domain` header) and hands it straight to the app's `WebhookHandler#handle` via `WebhookMetadata`, which apps use as the tenant key for the event.

### Finding Description
The identity binding that should hold is:
`shop value trusted by the handler == shop value cryptographically bound by the HMAC`

In this gem that binding is broken:
- `hmac` is computed over `to_signable_string`, which is defined as `@raw_body` only [2](#0-1) .
- `shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, a value that is never included in the signed string [1](#0-0) .
- `Registry.process` validates only the HMAC (i.e., only the body) and then constructs `WebhookMetadata` with `shop: request.shop`, passing it to the app-supplied handler [3](#0-2) .

Because the shared secret (`api_secret_key`) is the same for every shop that installs the app, any unprivileged internet user can install the target app on a shop they control (a normal, unprivileged action), trigger a real webhook event, and receive a genuinely Shopify-signed `(raw_body, X-Shopify-Hmac-Sha256)` pair. Since the header carrying the shop identity is outside the signed content, the attacker can replay that exact `raw_body`/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Utils::HmacValidator.validate(request)` still returns true (the body/HMAC pair is valid), but `request.shop` now resolves to the victim's domain, and the app's handler processes the event as if it originated from the victim tenant.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an attacker-controlled webhook body (fully attacker-influenced content, since it originates from their own shop's data/actions) gets attributed to a victim shop's tenant identity inside the app. Depending on how the host app's `WebhookHandler` implementation uses `data.shop` (e.g., to select which tenant's records to create/update/delete, or to trigger uninstall/redact flows for mandatory topics like `shop/redact`), this can lead to cross-tenant data corruption, spoofed app/uninstall lifecycle events for a shop the attacker doesn't control, or injection of attacker-controlled data into a victim's tenant record — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Likelihood is high for any unprivileged actor: obtaining a legitimately signed `(body, hmac)` pair only requires installing the target app on a shop the attacker controls (trivial, no special privilege), and then replaying it with a modified header to the app's own public webhook endpoint, since headers are not covered by the signature.

### Recommendation
Bind the shop (and other trust-relevant headers such as `topic`, `api-version`, `webhook-id`) into the signed content, or otherwise cryptographically verify the header against a value obtained through an authenticated channel (e.g., cross-check against the shop stored for the app's session/state, not solely the header). At minimum, `to_signable_string` should incorporate the `shop-domain` header (and any other header used downstream by the handler) so that `HmacValidator.validate` fails when those headers are altered independently of the body.

### Proof of Concept
1. Attacker installs the target Shopify app on a shop they control, `attacker.myshopify.com`.
2. Attacker triggers any subscribed webhook topic (e.g. `orders/create`), and captures the resulting HTTP request Shopify sends to the app's webhook endpoint: `raw_body` and header `X-Shopify-Hmac-Sha256: <valid HMAC over raw_body>`.
3. Attacker resends this exact `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but with `X-Shopify-Shop-Domain: victim.myshopify.com` substituted.
4. `ShopifyAPI::Webhooks::Request.new` builds the object; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only re-computes the HMAC over `raw_body` [4](#0-3) .
5. `handler.handle` is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, even though the event body actually originated from the attacker's own shop [5](#0-4) .
