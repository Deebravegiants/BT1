Based on my analysis of the codebase, I've identified a valid analog to the Mercurial CVE's bug class: an unbounded subtraction that "incorrectly proceeds" when an invariant it silently assumes (a floor/offset bound) is violated, rather than validating it first — surfacing here as an unguarded `uint256` subtraction that can revert with a Panic and permanently brick a curve.

### Title
Unguarded `assetReserve - virtualLtReserve` subtraction in `canGraduate` permanently DoSes buy/sell on any curve where cumulative round-down slack drains the pair below the launch-time virtual LT seed - (File: packages/contracts/src/Bonding.sol)

### Summary
`Bonding.canGraduate` computes the USD-trigger leg as `assetReserve - _launchTimeVirtualLtReserve(token_, pair)` with a plain `uint256` subtraction and no saturating guard [1](#0-0) . This silently assumes `assetReserve >= virtualLtReserve` always holds. `canGraduate` is invoked unconditionally on every buy (`_executeBuy`) and every sell (`Bonding.sell`, and again in `Zap.sell` before routing to `Bonding.sell`), and by the permissionless `triggerGraduation` [2](#0-1) [3](#0-2) . If `assetReserve` ever dips below the fixed `virtualLtReserve` (`Pair.k() / Token.TOTAL_SUPPLY()`, locked at launch and never updated by swaps [4](#0-3) ), the subtraction underflows and Solidity 0.8's overflow checks revert with a Panic — bricking every subsequent buy and sell on that curve, permanently freezing all trader funds still on the curve (no exit, no graduation, since `canGraduate`'s revert also blocks the only path to `_enterGraduating`).

### Finding Description
`Pair.swap`'s K-invariant check uses a `+1` slack on both sides: `(newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k` reverts [5](#0-4) . Combined with `Router._computeSell`'s floor-rounded `assetOut = reserveAsset - (k / newReserveToken)` [6](#0-5) , every sell can leave the real product `newTokenReserve * newAssetReserve` strictly below `k` by a small amount — i.e., each sell can hand the trader a hair more asset than the exact constant-product value, at the pool's expense. This is bounded per-call but not bounded in aggregate: an attacker (or any accumulation of ordinary buy/sell round trips, at attacker's own cost of just gas + a wei-scale of value) can repeat buy→sell cycles to monotonically ratchet `assetReserve` downward relative to what it "should" be, eventually pushing it below the immutable `virtualLtReserve` floor that `canGraduate` assumes as a lower bound.

Once that happens, `assetReserve - _launchTimeVirtualLtReserve(...)` underflows on the very next `canGraduate` call. Since `canGraduate` is called at the tail of every `_executeBuy` [7](#0-6)  and at the head of every `sell` [8](#0-7) , and `Zap.sell` also calls `bonding_.canGraduate(tokenAddress)` directly before doing anything else [9](#0-8) , the Panic reverts every trade attempt on that token going forward. Notably, the team already recognized and patched a sibling underflow in this exact reserve-arithmetic neighborhood — the "donation attack regression" fix for `Bonding.previewLtUntilGraduation`'s supply leg (`realBalance > reserveToken` underflow) — but that fix did not extend a saturating guard to `canGraduate`'s asset-side subtraction [10](#0-9) .

### Impact Explanation
Once triggered, the affected token's curve is permanently frozen: no further buys, no further sells, and no graduation (since `_enterGraduating` is only reachable through `canGraduate` returning `true`, but the function reverts before it can return anything). All LT value raised by traders on that curve, and every token holder's ability to exit or for the curve to graduate into the HyperSwap LP, is permanently stuck — a High-severity freezing-of-funds condition matching the "Impact" criteria (permanent freezing of trader/creator funds).

### Likelihood Explanation
Reaching the underflow requires accumulating enough round-down slack via repeated buy/sell round trips to erode `assetReserve` below `virtualLtReserve`; each individual round trip leaks only wei-scale value, so the number of iterations needed scales with the size of `virtualLtReserve` (`VIRTUAL_LIQUIDITY_USD`-derived) relative to the per-trip leak. This makes it gas-expensive but requires no special privilege, no price movement, and no protocol cooperation — any unprivileged trader can execute the attack purely by repeatedly calling `Zap.buy`/`Zap.sell` (or `Bonding.buy`/`Bonding.sell` via an allowlisted router) on their own funds, bounded only by gas cost. This is a Medium-likelihood, high-severity griefing/DoS vector rather than a trivial one-shot exploit.

### Recommendation
Replace the plain subtraction in `canGraduate` with a saturating subtraction (mirroring the pattern already used elsewhere in the codebase, e.g. `_ltSwapInventory`'s `bal > protectedLT ? bal - protectedLT : 0` [11](#0-10) ), so that `assetReserve < virtualLtReserve` degrades to `realLtRaised = 0` (USD trigger simply doesn't fire) instead of reverting the entire trade. The same guard should be audited into any other call site that assumes `assetReserve >= virtualLtReserve` without checking (e.g. `_prepareGraduationLiquidity`'s `ltFromPair = assetReserve - virtualLtReserve` [12](#0-11) , which — while only reachable once `canGraduate` already returned true via the supply leg — should not rely on the same unguarded assumption).

### Proof of Concept
1. Launch a token via `Zap.createToken` with the minimum seed.
2. Repeatedly, from a single unprivileged wallet: `Zap.buy(token, smallUsdcAmount, 0, address(0))` immediately followed by `Zap.sell(token, tokensOut, 0)` on the tokens just bought.
3. Each round trip leaves `Pair`'s `assetReserve` a wei-scale amount lower than an exact-curve round trip would (due to `Router._computeSell`'s floor rounding against `Pair.swap`'s `+1`-slack K-check).
4. After sufficiently many iterations, `assetReserve` drops below the fixed `virtualLtReserve = Pair.k() / Token.TOTAL_SUPPLY()`.
5. The next call to `Bonding.buy` or `Bonding.sell` (or `Zap.buy`/`Zap.sell`) triggers `canGraduate`'s `assetReserve - _launchTimeVirtualLtReserve(...)` and reverts with a Solidity Panic (0x11, arithmetic underflow), permanently bricking all further trading on that token's curve.
