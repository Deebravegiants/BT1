### Title
Decimal-mismatched minimum-liquidity burn in `process_initialize2` enables share-price inflation attacks on low-decimal-mint pools - (`program/src/processor.rs`)

### Summary
The external report's bug class is a fixed/assumed decimal base being applied to a value that is actually decimal-dependent, silently breaking the intended protection for low-decimal assets. The same class of bug exists in `process_initialize2`: the "locked/minimum liquidity" amount burned at pool creation is derived only from the coin mint's decimals, even though the liquidity value itself is a mixed function of both coin and pc decimals. For pools created against a very-low-decimal coin mint, the anti-inflation floor collapses to a negligible value, unlike a decimal-independent constant.

### Finding Description
In `process_initialize2`, the LP mint is created with `lp_decimals = coin_mint.decimals` [1](#0-0) , and pool liquidity is computed as the geometric mean of the raw (native-unit) pc and coin vault balances:

```
let liquidity = Calculator::to_u64(
    U128::from(amm_pc_vault.amount)
        .checked_mul(amm_coin_vault.amount.into())
        .unwrap()
        .integer_sqrt()
        .as_u128(),
)?;
let user_lp_amount = liquidity
    .checked_sub((10u64).checked_pow(lp_mint.decimals.into()).unwrap())
    .ok_or(AmmError::InitLpAmountTooLess)?;
...
amm.lp_amount = liquidity;
``` [2](#0-1) [3](#0-2) 

Only `user_lp_amount` tokens are actually minted to the creator, while `amm.lp_amount` (the internal total-supply accounting used for all subsequent deposit/withdraw share math) is set to the full `liquidity` value — the difference (`10^coin_decimals`) is the "locked" portion that is never minted to anyone, functioning like Uniswap V2's `MINIMUM_LIQUIDITY` burn.

The critical flaw: `liquidity = sqrt(pc_amount * coin_amount)` mixes the native decimal scales of *both* tokens, but the locked/burned floor `10^coin_decimals` is scaled using *only* the coin mint's decimals — it completely ignores `pc_mint.decimals`. This is exactly the same decimal-assumption error as the report: a value meant to defend against low-precision/low-value assets is computed using one side's decimals only, so it fails whenever the paired asset's decimals diverge (e.g., a coin mint created with 0–2 decimals paired against an 18-decimal token such as wSOL/USDC-like assets). Because `Initialize2` is a fully permissionless, single-transaction instruction where the caller supplies arbitrary coin/pc mint accounts and arbitrary initial amounts [4](#0-3) , an attacker can mint their own SPL token with very low decimals and pair it with a high-decimal token to create a pool where the burned floor (`10^coin_decimals`, e.g. `10^0 = 1` or `10^2 = 100`) is negligible relative to the actual raw liquidity value.

### Impact Explanation
With a negligible locked-liquidity floor, the classic AMM "donation/inflation" attack becomes cheap: the attacker creates the pool with minimal deposits (just enough to pass the `checked_sub` floor), receiving almost the entire (tiny) LP supply. They then directly transfer ("donate") tokens straight into the coin/pc vaults (ordinary SPL transfers, not going through `Deposit`), inflating `total_pc_without_take_pnl`/`total_coin_without_take_pnl` used by `calc_total_without_take_pnl_no_orderbook` without any matching increase to `amm.lp_amount`. Subsequent legitimate depositors calling `process_deposit` then receive rounded-down (often zero) LP tokens via `InvariantPool::exchange_token_to_pool` (`RoundDirection::Floor`) [5](#0-4) , while their deposited tokens are absorbed into the pool. This is a direct theft/permanent-loss vector against LPs. Because a fixed, decimal-independent lock (as in Uniswap V2's constant `MINIMUM_LIQUIDITY`) is not used, low-decimal coin mints are the class of pools left unprotected — precisely mirroring the reported "low-decimal-asset breaks fixed/assumed-decimal check" bug class.

### Likelihood Explanation
High: `Initialize2` is callable by any unprivileged account with any mint pair they choose, including a newly-minted SPL token with attacker-chosen (very low) decimals; no privileged signer or off-chain component is required. The only defense is the `checked_sub` floor check, which becomes trivial to satisfy for low-decimal coin mints.

### Recommendation
Decouple the anti-inflation lock from the coin mint's decimals. Use a fixed, decimal-independent minimum-liquidity constant (as Uniswap V2 does), or normalize both `pc_amount` and `coin_amount` to a common decimal base (e.g., via `Calculator::normalize_decimal_v2`, already used elsewhere in the codebase such as `program/src/processor.rs:950-959`) before computing `liquidity`/the locked amount, ensuring the burned floor reflects real economic value regardless of either mint's decimals.

### Proof of Concept
1. Attacker mints a new SPL token `LowDec` with `decimals = 0` and creates a market/mint pairing it against a normal 9/18-decimal token (`pc_mint`).
2. Attacker calls `Initialize2` with `init_coin_amount` and `init_pc_amount` chosen so `liquidity = sqrt(init_pc_amount * init_coin_amount) = 2` (just above the `10^0 = 1` floor). `user_lp_amount = 1` is minted to the attacker; `amm.lp_amount = 2` is recorded internally.
3. Attacker sends a large direct SPL `Transfer` of `pc_mint`/`LowDec` tokens straight to `amm_pc_vault`/`amm_coin_vault` (bypassing `Deposit`), inflating `amm_pc_vault.amount`/`amm_coin_vault.amount` massively while `amm.lp_amount` stays at 2.
4. A victim calls `Deposit`; `InvariantPool::exchange_token_to_pool` computes `mint_lp_amount = coin_amount * amm.lp_amount / total_coin_without_take_pnl`, which rounds to 0 for any reasonably sized deposit because `total_coin_without_take_pnl` is now enormous relative to `amm.lp_amount = 2`, causing `AmmError::InvalidInput` or the victim's deposited tokens being absorbed with no LP minted, depending on exact amounts — a share-price manipulation/fund-loss condition directly enabled by the negligible, decimals-mismatched lock computed in `process_initialize2`.
