### Title
Unbounded relayer-supplied signature array in BEEFY MMR update proof causes disproportionate ECDSA-recovery work per unsigned extrinsic - (File: modules/consensus/beefy/verifier/src/lib.rs)

### Summary
`verify_mmr_update_proof` in the BEEFY consensus-client verifier iterates over every signature in the relayer-supplied `mmr.signed_commitment.signatures` array, calling the expensive `secp256k1_recover` operation once per entry, before any hard limit on the array's size is enforced relative to the actual authority set. [1](#0-0)  This is dispatched via the unsigned, fee-free `handle_unsigned` extrinsic on `pallet-ismp`, reachable by any unprivileged relayer/message submitter. [2](#0-1) 

### Finding Description
`verify_mmr_update_proof` computes `signatures_length = mmr.signed_commitment.signatures.len()` and only checks `check_participation_threshold(signatures_length as u32, authority_set.len)` — which, from its usage, enforces a super-majority *lower bound* on participation, not an *upper bound* on how many entries the relayer may submit. [3](#0-2)  The subsequent loop then runs `H::secp256k1_recover` for every element of `mmr.signed_commitment.signatures`, regardless of whether the count exceeds the known authority set size:

```rust
for sig in mmr.signed_commitment.signatures.iter() {
    let uncompressed = H::secp256k1_recover(&commitment_hash.0, &sig.signature)...
    ...
}
``` [4](#0-3) 

Because this is invoked from the unsigned `handle_unsigned` extrinsic — callable for free by anyone, per its own doc comment "allows anyone execute ISMP datagrams for free" [5](#0-4)  — an attacker who pads the `signatures` vector with many (possibly invalid/duplicate-index) entries forces the runtime to perform many expensive elliptic-curve recovery operations in validation of a single transaction, analogous to the reported bug class where an unbounded/attacker-controlled dimension parameter drives disproportionate server-side work with no upstream limit.

### Impact Explanation
If the signature count is not bounded independent of `authority_set.len`, a malicious relayer can submit a `ConsensusMessage` with an arbitrarily large `signed_commitment.signatures` array. Each entry triggers a full secp256k1 recovery before the (unrelated) merkle multi-proof and MMR-leaf checks run, so validation cost scales with attacker-controlled input size rather than a fixed protocol constant. This could produce excessive computation during `validate_unsigned`/`execute`, which runs during block-building and transaction-pool validation, potentially stalling consensus-client processing for the affected chain — a liveness/DoS impact on the specific reachable path (message delivery route unable to process consensus updates in a timely manner).

### Likelihood Explanation
The call path is fully unprivileged: `handle_unsigned` is explicitly documented as executable by "anyone" with no signature or fee required, and a `ConsensusMessage` embedding an oversized `signatures` vector reaches `verify_mmr_update_proof` directly. Likelihood is bounded chiefly by whatever generic Substrate extrinsic/block-size limits apply to the encoded call, which are not specific to this function and were not further inspected due to time constraints.

### Recommendation
Bound `mmr.signed_commitment.signatures.len()` to at most `authority_set.len` (and reject if the count exceeds it) before performing any `secp256k1_recover` calls, mirroring the way `MAX_PROOF_DEPTH` and similar caps were added elsewhere in the codebase (e.g. the Pharos SPV proofs) specifically to prevent unbounded relayer-controlled work.

### Proof of Concept
Not independently reproduced; this report is based on static code review of `modules/consensus/beefy/verifier/src/lib.rs` lines 105–172. I was unable to confirm within the available tool budget whether `check_participation_threshold` (or an earlier/later guard I did not inspect, e.g. in `MmrProof` decoding/`BoundedVec` typing) already caps the signature count — this should be verified directly in the repository before treating this as confirmed. If `MmrProof.signed_commitment.signatures` is typed as an unbounded `Vec` (as the field access `.iter()` suggests) with no `BoundedVec` constraint in its SCALE type definition, the vulnerability as described holds.

pub fn verify_mmr_update_proof<H: Keccak256 + EcdsaRecover + Send + Sync>(
	mut trusted_state: ConsensusState,
	mmr: MmrProof,
) -> Result<(ConsensusState, H256), Error> {
	let signatures_length = mmr.signed_commitment.signatures.len();
	let latest_height = mmr.signed_commitment.commitment.block_number;

	if trusted_state.latest_beefy_height >= latest_height {
		return Err(Error::StaleHeight {
			trusted_height: trusted_state.latest_beefy_height,
			current_height: latest_height,
		});
	}

	let commitment = mmr.signed_commitment.commitment.clone();

	// Pick the authority set the commitment claims to be signed under, then judge
	// participation against that set alone.
	let authority_set = if commitment.validator_set_id == trusted_state.current_authorities.id {
		&trusted_state.current_authorities
	} else if commitment.validator_set_id == trusted_state.next_authorities.id {
		&trusted_state.next_authorities
	} else {
		return Err(Error::UnknownAuthoritySet { id: commitment.validator_set_id });
	};

	if !check_participation_threshold(signatures_length as u32, authority_set.len) {
		return Err(Error::SuperMajorityRequired);
	}
