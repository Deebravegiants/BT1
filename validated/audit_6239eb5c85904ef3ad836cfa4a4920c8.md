This confirms the vulnerability. The docs explicitly document `ShopifyAPI::Webhooks::Registry.process` as verifying "the request did indeed come from Shopify" and pass `data.shop` to the handler as an authoritative, trusted field, per `docs/usage/webhooks.md` lines 14, 125.

### Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Utils::HmacValidator` validates the HMAC exclusively against that raw body. The `shop`, `topic`, `webhook_id`, and `api_version` values that `ShopifyAPI::Webhooks::Registry.process` extracts and forwards to the app's `WebhookHandler` come directly from unauthenticated HTTP headers and are never part of the signed payload.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body bytes: [2](#0-1) 

Meanwhile `shop`, `topic`, and `webhook_id` are all read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`), which are attacker-controllable and are **not** part of the signable string: [3](#0-2) 

`Registry.process` validates only the HMAC (which is body-only), then dispatches the handler with `request.shop`, `request.topic`, and `request.webhook_id` taken from those unauthenticated headers: [4](#0-3) 

This breaks the identity binding: `authenticated(body) == authenticated(body, shop, topic, webhook_id)` does not hold — only `body` is authenticated by the app's `client_secret`-derived HMAC, but `shop` (the tenant identifier) is trusted and propagated to the handler as if it were verified. Because the same `api_secret_key`/`client_secret` is used to sign webhooks for *every* shop that has installed the app, an unprivileged attacker who controls their own shop installation of the app (a legitimate, unprivileged action) can capture one valid `(raw_body, hmac)` pair from a real webhook delivered to their own store, then replay that exact body and HMAC value to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain (and/or a different `shopify-topic`/`shopify-webhook-id`). `HmacValidator.validate` will still succeed because it only checks the untouched body bytes, and `Registry.process` will invoke the handler believing the event is authentically `shop: <victim-shop>`.

The official usage docs confirm that host applications are expected to treat `Registry.process` as sufficient to "verify the request did indeed come from Shopify" and to trust `data.shop` for actions like `perform_later(topic: data.topic, shop_domain: data.shop, ...)`: [5](#0-4) [6](#0-5) 

### Impact Explanation
This enables cross-tenant confusion: a host application that (as documented and intended) trusts `WebhookMetadata#shop` after `Registry.process` returns without error can be tricked into applying a legitimate webhook body to the wrong shop's tenant data (e.g., writing/queuing an `orders/create` payload under a victim shop's identifier, or triggering shop-scoped side effects keyed off `data.shop`). This crosses a tenant boundary using only the gem's documented API and requires no access token, `client_secret`, or privileged account — only the ability to install the app on an attacker-owned shop (an ordinary, unprivileged action) to obtain one valid signed payload.

### Likelihood Explanation
Any developer/attacker can install the target app on their own free/dev Shopify store, subscribe to any webhook topic, and observe a real `(body, hmac)` pair delivered to their own endpoint — no special access is required. Replaying that pair with a forged `shop-domain` header against the app's public webhook endpoint is straightforward for anyone who can send arbitrary HTTP requests.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed material, or alternatively require the host application to cross-check `request.shop` against the shop associated with the specific webhook subscription/session store before trusting it. At minimum, document prominently that `shop`/`topic`/`webhook_id` headers are not covered by Shopify's HMAC and must be independently validated by the consuming application against known installed shops before being used for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` (unprivileged, self-service action) and registers for topic `orders/create`.
2. Shopify delivers a real webhook to the attacker's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`, and some `raw_body`.
3. Attacker crafts a new POST request to the target app's webhook route reusing the identical `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. The app calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body:, headers:))`.
5. `Utils::HmacValidator.validate(request)` succeeds because `to_signable_string` only checks `raw_body`, per `lib/shopify_api/webhooks/request.rb` lines 35-38 and `lib/shopify_api/utils/hmac_validator.rb` lines 26-31.
6. The handler executes with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", ...)`, per `lib/shopify_api/webhooks/registry.rb` lines 198-199, causing the app to process attacker-supplied data as if it belonged to the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
