### Title

Attacker-controlled swap routes can move unrelated wallet tokens through the caller’s authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary

Controller strategy entrypoints accept caller-supplied route bytes and execute them through the configured swap router without restricting which pool contracts those routes invoke. Because the strategy call is authorized as a tree, malicious route-selected code can request additional token transfers from the caller; if the generated authorization tree is signed, those transfers can steal unrelated wallet assets while the controller’s own input/output checks still pass. [1](#0-0) [2](#0-1) 

### Finding Description

`swap_collateral` authenticates the caller and verifies account ownership or delegation, then passes the caller-supplied `swap` bytes into the router execution path. [3](#0-2)  The controller grants the router only one exact transfer of the declared input token from the controller, snapshots that token and the output token, invokes `execute_strategy`, and later rejects controller input overspending or missing output. [4](#0-3) 

The route program resolves each swap’s pool address from the payload’s `assets` registry and dispatches that address to a venue adapter. [2](#0-1)  The payload decoder bounds and structurally validates registry indices but does not require the selected pool address to be a governance-approved or venue-approved contract. [5](#0-4)  For example, the Phoenix adapter invokes `swap` on the payload-selected pool address. [6](#0-5) 

That malicious pool can issue a token transfer naming the original strategy caller as `from`. Under Soroban authorization rules, that transfer can execute when the caller signs the authorization tree containing it, even though it is unrelated to the lending swap input. [7](#0-6)  The controller’s later measurements only bound the controller’s declared swap input and require positive output; they do not inspect or reject unrelated child calls made under the caller’s broader signed authorization tree. [8](#0-7) 

### Impact Explanation

A malicious route provider can supply a route that performs a nominal or fair swap while also transferring unrelated tokens from the victim’s wallet to an attacker-controlled address. [9](#0-8)  The loss can exceed the swap input and affect assets that are not listed, supplied, borrowed, or otherwise authorized to the lending protocol. [10](#0-9) 

The resulting transaction can still satisfy the controller’s `RouterOverspend` and `NoSwapOutput` checks because those checks inspect only the controller’s declared input and output balances. [8](#0-7)  This permits theft of user funds rather than merely a poor execution price. [11](#0-10) 

### Likelihood Explanation

The attacker must persuade or trick the account owner/delegate into submitting a poisoned `swap` payload and signing the authorization tree generated for it. [12](#0-11)  This is more demanding than exploiting a standing token allowance because the malicious transfer must be present in the signed tree, but it does not require protocol admin access, a leaked key, a malicious token, or a compromised router contract. [13](#0-12) 

The exposure applies to every caller-controlled strategy path that forwards route bytes, including `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`. [14](#0-13)  Likelihood is therefore primarily a routing/wallet UX risk rather than a permissionless attacker-initiated drain. [15](#0-14) 

### Recommendation

Restrict route execution so strategy hops can invoke only deployment-approved venue pool contracts, rather than arbitrary addresses supplied in the route registry. [2](#0-1) 

If venue pools cannot be enumerated safely, enforce a contract-level authorization policy that rejects any caller-authorization child other than the expected token pull before execution. [16](#0-15)  Clients should also decode the route and reject any signed authorization tree containing transfers or calls unrelated to the declared swap input. [17](#0-16) 

### Proof of Concept

1. The victim owns a lending account and invokes `swap_collateral(caller, account_id, current, amount, new, swap)`. [3](#0-2) 
2. The supplied `swap` encodes a swap instruction whose `idx_a` selects an attacker-deployed contract from `assets`. [18](#0-17) 
3. The router resolves `assets[idx_a]` as `hop.pool` and dispatches the hop to a venue adapter. [2](#0-1) 
4. The venue adapter invokes the attacker-selected pool address. [19](#0-18) 
5. That contract calls `unrelated_token.transfer(victim, attacker, victim_balance)`, which requires caller authorization and is recorded beneath the strategy authorization tree. [20](#0-19) 
6. The victim signs the poisoned tree returned by simulation, the unrelated tokens move to the attacker, and the route can still return enough output for the controller’s positive-output check to pass. [8](#0-7)

    /// Validates every instruction's opcode, mode, and indices before execution begins,
    /// including the `Prev` chain, same-token swaps, and split-weight bounds.
    fn validate(&self, env: &Env, assets_len: u32, amounts_len: u32, weight_count: u32) {
        for i in 0..self.op_count {
            let record = self.raw(i);
            let Some(opcode) = Opcode::from_u8(record[field::OPCODE]) else {
                panic_with_error!(env, Error::InvalidRouteXdr);
            };
            let mode = Mode::from_u8(record[field::MODE]);
            let (idx_a, idx_b, idx_c) = (
                record[field::POOL] as u32,
                record[field::TOKEN_IN] as u32,
                record[field::TOKEN_OUT] as u32,
            );

            // `Prev` is a purely structural link: the predecessor must exist,
            // must have a single output, and that output must be this
            // instruction's input.
            if mode == Mode::Prev {
                if i == 0 {
                    panic_with_error!(env, Error::BrokenTokenChain);
                }
                let previous = self.raw(i - 1);
                let produced = match Opcode::from_u8(previous[field::OPCODE]) {
                    // A swap produces its `token_out`, a mint its share token.
                    Some(Opcode::Swap(_)) => previous[field::TOKEN_OUT],
                    Some(Opcode::Mint) => previous[field::TOKEN_IN],
                    // A burn releases every constituent at once.
                    _ => panic_with_error!(env, Error::BrokenTokenChain),
                };
                if idx_b != produced as u32 {
                    panic_with_error!(env, Error::BrokenTokenChain);
                }
            }
            match mode {
                Mode::Fixed(idx) if idx as u32 >= amounts_len => {
                    panic_with_error!(env, Error::InvalidRouteXdr)
                }

                    panic_with_error!(env, Error::InvalidRouteXdr)
