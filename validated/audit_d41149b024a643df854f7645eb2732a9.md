### Title
`withdraw` in the Tron `IntentGatewayV2` releases escrow via low-level `.call` before decrementing state, enabling reentrant double-withdrawal - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` transfers escrowed ETH/ERC-20 to a beneficiary via a low-level `.call` **before** decrementing the `_orders[commitment][token]` escrow balance, and this contract (unlike the mainline `evm/src/apps/IntentGatewayV2.sol`) has no reentrancy guard. This is the same class of bug as the wildcredit `_wethWithdrawTo` finding: an external call that can trigger arbitrary code (via `beneficiary.call{value: amount}("")`) happens ahead of the state update that is supposed to prevent re-use of the same escrow.

### Finding Description
In `withdraw(WithdrawalRequest memory body, bool isRefund)`: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;
        ...
```

The guard `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` only checks that the balance is non-zero, not that it equals `amount`, and the actual decrement `_orders[body.commitment][token] -= amount` happens **after** the external `.call`. When `token == address(0)`, the beneficiary is an externally-controlled address that receives control during the ETH transfer (`receive()`/`fallback()`), before `_orders[...]` has been decremented for that token.

This contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, is a separate implementation from the hardened `evm/src/apps/IntentGatewayV2.sol` used elsewhere in the repo. The hardened version composes `IntrinsicIntents`/`ExtrinsicIntents` and inherits `ReentrancyGuardTransient`, and its fill/withdraw logic was patched with a CEI fix (`_filled[commitment] = msg.sender` set before any external call), as documented extensively in `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`. The Tron variant does **not** inherit any reentrancy guard: [2](#0-1) 

```solidity
contract IntentGatewayV2 is HyperApp, EIP712 {
    using SafeERC20 for IERC20;
```

`withdraw()` is reachable by an unprivileged relayer delivering a `RedeemEscrow`/`RefundEscrow` ISMP message via `onAccept`, and also from `cancelOrder` for same-chain orders: [3](#0-2) 

```solidity
function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
    RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
    if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
        authenticate(incoming.request);
        WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
        return withdraw(body, kind == RequestKind.RefundEscrow);
    }
```

`authenticate()` only checks that the incoming request's `from` matches a registered gateway instance address for that chain — it does not restrict the *beneficiary* encoded in the `WithdrawalRequest`, which is attacker-controlled data relayed from another chain (an attacker can place an order on a source-chain instance they operate, or manipulate their own beneficiary field in a legitimate cross-chain order they placed).

### Impact Explanation
If a beneficiary is a contract with `receive()`, it can re-enter `withdraw` (indirectly, e.g. by re-entering `onAccept`/`cancelOrder`/another entry that reaches `withdraw` for the same commitment) before `_orders[commitment][token]` is decremented. Because the only guard is `_orders[...][token] == 0` (not an exact-amount check), and the decrement happens post-transfer, a reentrant call for the same `commitment`/`token` can pass the guard again and trigger a second `.call` transfer of the same escrowed amount, draining protocol-held escrow funds (ETH or ERC-20) beyond what was actually escrowed — a direct theft of funds analogous to the referenced wildcredit finding, where a reserve check performed after a low-level ether transfer could be bypassed via reentrancy.

### Likelihood Explanation
Reachable from a single relayed ISMP POST message (`RedeemEscrow`/`RefundEscrow`) delivered by any permissionless relayer, or from a same-chain `cancelOrder` call — both are unprivileged, single-transaction entry points. The attacker only needs to control the `beneficiary` address encoded in an order they placed (a normal capability of any user of the intents system) and deploy a malicious contract as that beneficiary. No governance or privileged role is required.

### Recommendation
Apply Checks-Effects-Interactions in `withdraw()`: decrement `_orders[body.commitment][token]` (and the fee balance) **before** performing the external `.call`/`safeTransfer`, mirroring the fix already applied in `IntentsBase._withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol`) and in `IntrinsicIntents`/`ExtrinsicIntents` (setting `_filled` and decrementing escrow before any external calls). Additionally, add a reentrancy guard (e.g. `ReentrancyGuardTransient`, as used in `evm/src/apps/IntentGatewayV2.sol`) to the Tron `IntentGatewayV2` contract, and change the escrow guard to check exact sufficiency (`_orders[commitment][token] >= amount`) rather than merely non-zero.

### Proof of Concept
1. Attacker places (or is party to) an order whose output/beneficiary is a malicious contract `Evil`, with `Evil.receive()` calling back into the gateway (e.g. re-invoking `cancelOrder` or waiting for a duplicate `RedeemEscrow`/`RefundEscrow` delivery for the same commitment) before the first `withdraw` call returns.
2. A relayer delivers a `RedeemEscrow`/`RefundEscrow` POST for the order's commitment; `onAccept` → `withdraw` is invoked.
3. Inside the loop, `withdraw` calls `beneficiary.call{value: amount}("")` for the native-token entry; control transfers to `Evil.receive()` while `_orders[commitment][address(0)]` is still non-zero (not yet decremented).
4. `Evil.receive()` triggers a second path into `withdraw` for the same `commitment`/token (e.g. by re-triggering a retryable delivery, since `dispatchIncoming` in `EvmHost` deletes the receipt on failure allowing retries, or via a same-chain `cancelOrder` if applicable) — the `_orders[...] == 0` check still passes because the decrement from step 3 hasn't happened yet, allowing a second transfer of the same escrowed amount.
5. After both external calls return, `_orders[commitment][token] -= amount` executes twice, potentially underflowing/over-draining the escrow relative to what was ever deposited, resulting in the contract paying out more than it collected.
