### Title
Webhook `shop-domain` header is trusted as tenant identity but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying an HMAC over the raw request body, but the `shop` value that is subsequently trusted and handed to the app's webhook handler is taken from an HTTP header that is completely outside the scope of that signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` and compares it to the `hmac-sha256` header: [2](#0-1) 

`Registry.process` treats a passing HMAC check as sufficient proof of authenticity, and then immediately trusts `request.shop`, which is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, unvalidated and unsigned: [3](#0-2) [4](#0-3) 

The `shop` field is then forwarded as the tenant identity to the app's handler via `WebhookMetadata`, and the documentation explicitly instructs developers to key their business logic (e.g., enqueuing jobs "per shop_domain") off `data.shop`: [5](#0-4) 

Unlike the OAuth callback path, which validates `shop` through `ShopValidator.sanitize!`/is bound into the HMAC-signed `AuthQuery` (`code, host, shop, state, timestamp`): [6](#0-5) 

there is no equivalent binding for webhook requests between the authenticated bytes (the raw body) and the claimed tenant (`shop-domain` header). This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the equality the code implicitly assumes is `hmac_valid(raw_body) ⇒ shop_header == originating_shop`, but the signature scheme never establishes that equality.

### Impact Explanation
Any unprivileged user who installs the app on their own store legitimately receives real webhook deliveries — i.e., a valid `(raw_body, hmac)` pair produced by Shopify using the app's shared `client_secret`. Because the `shop-domain` header is not part of the signed content, that same attacker can replay the identical `raw_body`/`hmac` pair directly to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value (e.g., a victim shop's domain). `Registry.process` will accept the request as authentic (the HMAC still validates against the unmodified body) and will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen value. Any app logic keyed on `data.shop` (session lookups, per-tenant data writes, `app/uninstalled` cleanup, order/customer ingestion, etc.) can be tricked into acting on behalf of, or writing data attributed to, a shop the attacker does not control — a cross-tenant confusion/injection primitive.

### Likelihood Explanation
Exploitation requires only: (1) the attacker be a legitimate (if unprivileged) installer of the app, in order to observe at least one genuine `(body, hmac)` pair, and (2) the ability to send an HTTP POST directly to the app's public webhook endpoint with custom headers — no interception of TLS, no access to `client_secret`, and no privileged account is required. The gem provides no built-in check tying the header to the signed payload, and the documented integration pattern (`docs/usage/webhooks.md`) encourages developers to trust `data.shop` directly.

### Recommendation
Bind the shop identity into the authenticated material before trusting it, e.g., by including `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) in `to_signable_string`, or by cross-checking `request.shop` against the shop referenced inside the (also authenticated) parsed body/webhook subscription record before dispatching to the handler. At minimum, `ShopValidator.sanitize!` should be applied to `request.shop`, and callers should be warned that the header alone must never be treated as tenant-authenticated without an out-of-band check (e.g., verifying it corresponds to a shop with an active webhook registration/session).

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Shopify delivers a legitimate webhook to the app's endpoint:
   ```
   POST /callback/orders/create
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC over raw_body using app's client_secret>
   x-shopify-shop-domain: attacker.myshopify.com
   Body: {"id": 1, ...}
   ```
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value.
4. Attacker replays the identical request directly to the app's public webhook endpoint, only changing the shop header:
   ```
   POST /callback/orders/create
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same valid HMAC, body unchanged>
   x-shopify-shop-domain: victim-shop.myshopify.com
   Body: {"id": 1, ...}    (unchanged - HMAC still verifies)
   ```
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` only checked the (unmodified) body.
6. The app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes/attributes the (attacker-supplied) event data as if it originated from the victim shop — demonstrated by `Registry.process` dispatching solely on `request.topic`/`request.shop` per [3](#0-2) .
