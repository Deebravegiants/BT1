Based on my investigation, I found a directly analogous pattern in the Intent Gateway's escrow-withdrawal logic: caller/message-supplied token amounts are used to move funds and only reconciled against the actual escrowed balance *after* the external transfer is performed, mirroring the report's core concern — logic trusts an externally supplied numeric parameter instead of deriving/enforcing it from already-known state before acting on it.

### Title
Checks-effects-interactions violation in escrow withdrawal lets a caller-supplied token amount be spent before the escrow balance is validated/decremented - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.withdraw()` (Tron variant) receives a `WithdrawalRequest.tokens[]` array — decoded from an ISMP message body — whose `amount` field is used directly to push value out of the contract via a raw `.call` to the token before the corresponding `_orders[commitment][token]` escrow accounting is decremented.

### Finding Description
`onAccept()` decodes an incoming `RedeemEscrow`/`RefundEscrow` message into a `WithdrawalRequest` and calls `withdraw(body, isRefund)`: [1](#0-0) 

The `amount` transferred is taken as-is from `body.tokens[i].amount` (attacker/relayer-controlled message payload) and is used to perform the external transfer *before* `_orders[body.commitment][token] -= amount;` runs. The only pre-transfer check is `_orders[body.commitment][token] == 0`, which does not validate that `amount` is less than or equal to the actual escrowed balance for that commitment. In the corresponding non-Tron implementation this ordering is correct — the escrow is decremented before the transfer: [2](#0-1) 

This is the same root-cause class flagged in the external report: a numeric input parameter (`amountToBuy`/`token`/`initialBid` in the GEB example, `amount` here) that should be strictly derived from/validated against existing on-chain state is instead accepted from the caller and only reconciled afterward (via Solidity's checked-arithmetic revert), rather than being validated up front with checks-effects-interactions ordering enforced.

### Impact Explanation
Because the external call (`token.call(transfer(...))`) precedes the storage decrement, a token contract configured as an order's input asset that executes a callback during `transfer` (e.g., an ERC-777-style hook, or any token with reentrant hooks) can re-enter the gateway (e.g., `cancelOrder`/`placeOrder`/fill paths) while `_orders[commitment][token]` still reflects the pre-withdrawal balance, enabling a double-spend of the same escrowed balance. This is a fund-theft primitive against the escrow pool shared by all orders denominated in that token.

### Likelihood Explanation
Exploitation requires an order be placed with a token that has transfer-time callbacks (not standard ERC-20, but this is not restricted anywhere in `placeOrder`), and requires an attacker/solver to control both the malicious token and the fill/redeem flow to trigger reentrancy during message delivery. This narrows likelihood but the path is reachable through a normal, unprivileged flow: place an order with a self-controlled hook token as input, fill it, and let the relayed `RedeemEscrow` message trigger `withdraw()`.

### Recommendation
Apply strict checks-effects-interactions ordering uniformly: validate `amount <= escrowed` and update `_orders[commitment][token]` before performing any external call/transfer, matching the pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`. Additionally, consider deriving the redemption amount solely from on-chain escrow state rather than trusting the message-supplied `amount` field, consistent with the audit recommendation to enforce strict equality/derivation from known state rather than accepting a redundant, unchecked input parameter.

### Proof of Concept
1. Attacker deploys a malicious ERC-20-like token with a `transfer()` function that calls back into `IntentGatewayV2` (e.g., invoking `cancelOrder` for the same commitment).
2. Attacker places an order using this token as the input asset, escrowing `X` tokens; `_orders[commitment][token] = X`.
3. Order is filled and a `RedeemEscrow` ISMP message is relayed back to the source chain, invoking `onAccept -> withdraw(body, false)` with `body.tokens[0].amount = X`.
4. Inside `withdraw`, the token's `transfer(beneficiary, X)` call is made — triggering the malicious token's callback — before `_orders[commitment][token] -= X` executes.
5. During the callback, the attacker reenters a path that reads/uses the still-unmodified `_orders[commitment][token] == X` (e.g., to trigger another release/refund for the same commitment), extracting more tokens than were ever escrowed for that order. [1](#0-0)

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

                ++i;
            }
        }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
