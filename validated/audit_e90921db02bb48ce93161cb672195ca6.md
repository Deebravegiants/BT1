## Finding

### Title
`Webhooks::Registry.process` trusts unauthenticated `topic`/`shop-domain` headers because HMAC only signs the raw body - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`Webhooks::Registry.process` validates a webhook exclusively via `Utils::HmacValidator.validate`, which computes the HMAC over `Request#to_signable_string` (the raw body only) and never over the `topic`, `shop-domain`, or `webhook-id` headers. Because the app-level `api_secret_key` used for HMAC is shared by every shop that installs the app, any installed merchant can capture one of their own genuinely-signed webhook deliveries and replay the identical body to the app's public callback URL with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header, and the signature still validates.

### Finding Description
The claimed binding is: `shop authenticated by signature == shop used by the handler as WebhookMetadata#shop`. Tracing the code shows this binding does not exist for webhooks:

- `Request#hmac` reads `shopify-hmac-sha256` and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `Request#topic`, `Request#shop`, and `Request#webhook_id` are read straight from HTTP headers with no cryptographic binding to the body: [2](#0-1) 
- `HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the received `hmac` header - it never touches `topic`, `shop`, or `webhook-id`: [3](#0-2) 
- `Registry.process` only calls that HMAC check, then dispatches using the unauthenticated `request.topic` and constructs `WebhookMetadata` from the unauthenticated `request.shop`: [4](#0-3) 

Root cause: the HMAC secret (`api_secret_key`) is per-app, not per-shop, and the signature protects only the body bytes. `topic`, `shop-domain`, and `webhook-id` are fully attacker-controllable headers in any request the attacker crafts to the app's public webhook endpoint.

Exploit flow: the attacker installs the app on their own development shop (as permitted), triggers a real event (e.g. `orders/create`), and lets Shopify deliver the genuine, correctly-signed webhook to the app's registered callback path. The attacker captures that exact `raw_body` + `X-Shopify-Hmac-Sha256` header. They then send a new HTTP request to the same public callback URL, keeping body and HMAC identical, but replacing `X-Shopify-Shop-Domain` with the victim shop's domain (and/or `X-Shopify-Topic` with a different registered topic). `HmacValidator.validate` still succeeds because it only checks the body, so `Registry.process` builds `WebhookMetadata.new(topic: <attacker-chosen>, shop: <victim-shop>, body: <attacker's own body>, ...)` and invokes the app's handler as if the victim shop generated that event/data. No component in the traced path (`HmacValidator`, `Request`, `Registry`) cross-checks the header-derived shop/topic against anything derived from the signature itself.

### Impact Explanation
This lets an unprivileged installed merchant cause the app's webhook handler to execute with a shop identity (`WebhookMetadata#shop`) of the attacker's choosing while supplying attacker-controlled body content, i.e., one tenant's request causes data to be attributed to/written under another merchant's shop context. Depending on the handler's use of `data.shop` (e.g., enqueuing background jobs keyed by shop, updating shop-scoped records, or handling `app/uninstalled`/`shop/redact`), this is a repeatable cross-tenant data-integrity/confidentiality issue matching "Critical - cross-tenant access." It is repeatable against any victim shop the attacker knows the domain of, at will, with no rate limiting in the gem.

### Likelihood Explanation
Preconditions: attacker must (a) install the target app on any shop they control (trivial, free), (b) know/guess the app's public webhook callback URL (typically discoverable/predictable, e.g. `/webhooks` or documented in the app), and (c) know a victim shop's `myshopify.com` domain (public/guessable). No secrets, tokens, or privileged access are required. Cost is a single legitimate app install plus replaying one captured HTTP request - low effort, fully repeatable.

### Recommendation
Bind the authenticated identity to the signed payload rather than trusting headers: include `shop-domain`, `topic`, and `webhook-id` in the signable string (or otherwise cryptographically bind them, e.g. compare against a shop stored/expected server-side for that webhook subscription), and/or require the host app to validate `request.shop` against its own session/shop registry before invoking the handler. At minimum, document that `WebhookMetadata#shop`/`topic` are unauthenticated and must be revalidated by the app before being trusted for tenant-scoped operations.

### Proof of Concept
Minitest sketch (extending `test/webhooks/registry_test.rb` / `test/utils/hmac_validator_test.rb` patterns):
```ruby
def test_hmac_does_not_bind_shop_or_topic_headers
  raw_body = '{"id":1}'
  secret = ShopifyAPI::Context.api_secret_key
  hmac = Base64.encode64(OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, raw_body)).strip

  original_request = ShopifyAPI::Webhooks::Request.new(
    raw_body: raw_body,
    headers: {
      "X-Shopify-Topic" => "orders/create",
      "X-Shopify-Hmac-Sha256" => hmac,
      "X-Shopify-Shop-Domain" => "attacker-shop.myshopify.com",
      "X-Shopify-Webhook-Id" => "wh-1",
      "X-Shopify-Api-Version" => "2024-01",
    },
  )
  assert ShopifyAPI::Utils::HmacValidator.validate(original_request)

  # Same body/hmac, forged shop + topic headers
  forged_request = ShopifyAPI::Webhooks::Request.new(
    raw_body: raw_body,
    headers: {
      "X-Shopify-Topic" => "customers/update",
      "X-Shopify-Hmac-Sha256" => hmac,
      "X-Shopify-Shop-Domain" => "victim-shop.myshopify.com",
      "X-Shopify-Webhook-Id" => "wh-1",
      "X-Shopify-Api-Version" => "2024-01",
    },
  )
  # Binding under test: shop authenticated by signature should equal shop dispatched to handler.
  assert ShopifyAPI::Utils::HmacValidator.validate(forged_request), "HMAC still valid despite forged shop/topic"
  assert_equal "victim-shop.myshopify.com", forged_request.shop
  refute_equal original_request.shop, forged_request.shop
  # => demonstrates the two sides of the binding diverge while the signature still passes.
end
```
This shows the invariant "shop authenticated by the signature == shop dispatched to the handler" is false: the signature validates identically regardless of the `shop-domain`/`topic` header values, confirming the cross-tenant dispatch vector at `ShopifyAPI::Webhooks::Registry.process`.
