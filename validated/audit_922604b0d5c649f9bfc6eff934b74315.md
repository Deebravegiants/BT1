This confirms a clear analog: `client_credentials.rb` and `refresh_token.rb` both call `Utils::ShopValidator.sanitize!(shop)` before building the `shop_session` used to construct the request host, but `token_exchange.rb` does not — it takes `dest_shop = jwt_payload.shop` straight from the JWT `dest` claim and feeds it unvalidated into `Session.new(shop: dest_shop)`, which `Clients::HttpClient` then uses verbatim as the request host: `@base_uri = "https://#{api_host || session.shop}"` [1](#0-0) .

### Title
Unvalidated JWT `dest` claim used as request host for token exchange, bypassing the app's trusted-domain check - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`TokenExchange.exchange_token` decodes the caller-supplied session token and uses the raw `dest` claim as the host to which it sends the app's `client_id`/`client_secret` and the subject token, without running it through `Utils::ShopValidator.sanitize!`, unlike the sibling `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token` flows which do sanitize the shop before use.

### Finding Description
`JwtPayload#shop` simply strips `"https://"` from the raw `dest` claim with no domain allow-listing: `@dest.gsub("https://", "")` [2](#0-1) . `JwtPayload.new` only checks the HMAC signature (with `Context.api_secret_key`), expiry/`nbf` leeway, and that `aud == Context.api_key` [3](#0-2) . It never validates that `dest` is a genuine `*.myshopify.com`/`myshopify.io`/`spin.dev`/`shop.dev` host.

`TokenExchange.exchange_token` takes this unchecked value directly:
```
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = jwt_payload.shop
...
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
``` [4](#0-3) 

`shop_session` is then passed into `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")`, and `HttpClient` builds the outbound URL straight from `session.shop`: `@base_uri = "https://#{api_host || session.shop}"` [1](#0-0) . The request body sent to that host includes the app's `client_secret` and the full `subject_token` (the session token itself) [5](#0-4) .

Contrast this with `ClientCredentials.client_credentials`, which calls `validated_shop = Utils::ShopValidator.sanitize!(shop)` before building the session [6](#0-5) , and `RefreshToken.refresh_access_token`, which does the same [7](#0-6) . `ShopValidator` exists precisely to restrict shop hosts to Shopify's trusted domain suffixes (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) [8](#0-7) , but `TokenExchange` was not updated to use it, even though the changelog for the same release explicitly says the shop for `exchange_token` is now "derived from the session token's `dest` claim" [9](#0-8) .

**Binding that should hold:** `host_that_receives(client_secret, subject_token) == trusted_shopify_domain(dest_claim)`. What actually holds: `host_that_receives(client_secret, subject_token) == raw_dest_claim` with no trusted-domain check, breaking the equality whenever `dest` is not a `*.myshopify.com`-family host.

### Impact Explanation
Whether this is exploitable by an unprivileged internet user depends on whether an attacker can get a session token whose HMAC validates against the app's `api_secret_key` but whose `dest` claim is attacker-controlled to a non-Shopify host. Session tokens are normally minted and signed by Shopify itself when the app is loaded in the Admin/App Bridge context, and Shopify is the one who sets `dest` to the actual shop's domain — so under normal operation `dest` should always be a legitimate Shopify-controlled domain, and this gap would not be reachable without Shopify itself misbehaving or without another mechanism for an attacker to obtain a validly-signed token with an arbitrary `dest`. I could not find, within this gem's code, any additional path (e.g., a public HMAC-signing oracle) that would let an unprivileged user forge or manipulate the `dest` claim of an otherwise validly-signed token. Because of this, I can't confirm a concrete unprivileged-attacker-controlled trigger for sending `client_secret`/subject token to an attacker host through this exact code path — the missing `ShopValidator` call is a genuine defense-in-depth gap and inconsistency with sibling methods, but proving it as an SSRF/credential-exfiltration primitive requires an attacker-forgeable or attacker-redirectable `dest`, which is not demonstrated by code in scope.

### Likelihood Explanation
Low-to-uncertain without a demonstrated way for an unprivileged party to control the `dest` claim of a token that still passes `JwtPayload`'s HMAC/`aud` checks. The inconsistency with `ClientCredentials`/`RefreshToken` (which do sanitize) strongly suggests the omission is unintentional, but likelihood of practical exploitation depends on factors (Shopify's token-issuance guarantees) outside this gem.

### Recommendation
Apply `Utils::ShopValidator.sanitize!` (or equivalent trusted-domain validation) to `jwt_payload.shop` in `TokenExchange.exchange_token` before using it to build `shop_session`/the request host, mirroring the pattern already used in `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`.

### Proof of Concept
Not constructible with certainty from in-scope code alone: it requires producing a session token that (a) has a valid HMAC under `Context.api_secret_key`, (b) has `aud == Context.api_key`, and (c) has a `dest` claim pointing to a non-Shopify-trusted host — none of which this gem's code shows as forgeable by an unprivileged actor. Absent that primitive, this is flagged as a code-consistency/defense-in-depth gap rather than a proven exploitable vulnerability.
