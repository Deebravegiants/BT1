Confirmed the exploit primitive. The `WebhookMetadata.shop` field, which is passed directly to the app handler as the tenant identifier, is populated straight from the `shop-domain` header — and that header is never part of the HMAC-signed bytes.

### Title
Webhook tenant identity (`shop`, `topic`) is not bound to the HMAC signature, enabling cross-tenant webhook spoofing via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its verifiable signature over the raw body only, while the `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are read unauthenticated and forwarded to the app's webhook handler as trusted tenant/routing metadata. `Registry.process` verifies only that the body's HMAC is valid, then dispatches using these unauthenticated headers.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
and `Request#shop`/`#topic`/`#webhook_id`/`#api_version` are all read straight from HTTP headers without any cryptographic binding: [2](#0-1) 

`HmacValidator.validate` verifies `verifiable_query.hmac` against `to_signable_string`, i.e. the body bytes only: [3](#0-2) 

`Registry.process` raises only if the body HMAC fails, then immediately builds `WebhookMetadata` from the unauthenticated `request.shop`/`request.topic`/`request.webhook_id`/`request.api_version` and hands it to the app's handler: [4](#0-3) 

`WebhookMetadata.shop` is a `T::Struct` field with no further validation, and is documented/typed as the trusted tenant identifier consumed by `WebhookHandler#handle`: [5](#0-4) 

The broken binding, as an equality that should hold but doesn't:
`bytes verified by HMAC` (body only) ≠ `bytes that determine the tenant` (`shop-domain` header, `topic` header).

**Before attacker action:** a legitimate webhook for shop A arrives with `raw_body = B`, `hmac = HMAC(secret, B)`, `shop-domain = A`, `topic = "orders/create"`. This is what the app is designed to trust: the header set matches what Shopify actually sent for shop A.

**Attack:** an unprivileged internet user who can generate a genuine webhook to their own endpoint (or who observes/captures a body+HMAC pair for shop A by any external means, e.g. their own webhook feed for their own store, or a shared/multi-tenant proxy) resends the exact same `raw_body` and `hmac-sha256` header to the app's public webhook endpoint, but substitutes `shop-domain: <victim-shop>.myshopify.com`. Because `HmacValidator.validate` never inspects the `shop-domain` header, the HMAC check still passes — the gem only recomputed/compared the digest of `raw_body`. `Registry.process` then constructs `WebhookMetadata` with `shop: "<victim-shop>.myshopify.com"` and calls the app's `handle` method with that value trusted as the authenticated tenant.

**After attacker action:** the app processes attacker-controlled body content while believing it originated from and pertains to the victim shop — a cross-tenant identity break with no credential belonging to the victim ever being used.

### Impact Explanation
Any consuming application that follows this gem's documented pattern of trusting `WebhookMetadata.shop` (and/or `.topic`) as the authenticated tenant context — which is the gem's only exposed way to know which merchant a webhook is "for" — can be made to write, delete, or act on data under the wrong `shop` scope. This is a cross-tenant access primitive: an unprivileged caller (anyone who can get one legitimately-HMAC'd payload, even for their own shop) can cause the receiving app to attribute/process that payload as belonging to a different merchant.

### Likelihood Explanation
Moderate-to-high: the attacker doesn't need to break the HMAC (they never forge a new signature), they only need one legitimate `(body, hmac)` pair — trivially obtainable by registering the same webhook topic on their own store, or by replaying a webhook if the endpoint is otherwise reachable/observable. Then the header can be freely modified since it's not covered by the signature. This is a design flaw in the gem's `Request`/`Registry` contract, not merely host-app misuse, because the gem itself defines and exposes `WebhookMetadata.shop`/`.topic` as fields intended to be trusted post-`process`, without documenting or enforcing that they are unauthenticated.

### Recommendation
Either (a) include `shop-domain`, `topic`, `webhook-id`, and `api-version` in the signable string used for HMAC verification (this would require Shopify-side changes as well, so more practically), or (b) clearly scope `WebhookMetadata.shop`/`.topic` as unauthenticated hints and require callers to separately confirm the `shop` against a session/store they already look up by `webhook_id`/registration, or (c) bind the webhook's `shop` to the `X-Shopify-Shop-Domain` only after checking it against a merchant record already tied to the `webhook_id`, rejecting mismatches, before invoking the handler.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and receives a legitimate webhook for it:
raw_body = '{"id":1,"note":"attacker controlled content"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker resends the same body+hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to the victim's shop:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
# Passes HMAC validation because only raw_body is checked:
ShopifyAPI::Webhooks::Registry.process(request)
# => app handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
#    with attacker-controlled body, believing it is authenticated data for the victim shop.
```
