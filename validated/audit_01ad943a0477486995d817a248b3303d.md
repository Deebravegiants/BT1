## Title
Webhook shop identity spoofing due to HMAC covering only the raw body, not the shop-domain header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator.validate` protects the integrity of the JSON body only. It does not cover the `X-Shopify-Shop-Domain` header, which is nonetheless surfaced by `Request#shop` and forwarded verbatim into `WebhookMetadata#shop` by `Registry.process`, becoming the tenant identifier the host application is expected to trust.

### Finding Description
`Registry.process` performs exactly one authenticity check before dispatching to the app's handler: [1](#0-0) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, and for webhook requests that method is defined as: [2](#0-1) 

Only `@raw_body` feeds the signature. The `shop` accessor, however, is read straight from the (uncovered) header: [3](#0-2) 

`Registry.process` then builds `WebhookMetadata` directly from `request.shop`, with no cross-check against the body or against any per-shop secret, and passes it to the app's handler: [4](#0-3) 

The gem's own documentation instructs integrators to treat `data.shop` as the trusted tenant identifier for downstream processing: [5](#0-4) 

The equality the gem implicitly claims to guarantee is:
`shop_covered_by_hmac == shop_delivered_to_handler`

In reality:
`shop_covered_by_hmac = ∅ (not part of to_signable_string) ≠ shop_delivered_to_handler = request.shop (raw header)`

Because the same app-level `api_secret_key` is used to sign webhooks for every shop that installs the app (it is not a per-tenant secret), any unprivileged internet user who can install the app on a store they control (or otherwise legitimately receive one webhook for a shop they own) obtains a genuine `(body, hmac)` pair that is valid for that body under the app's secret. Nothing in `Request` or `Registry.process` binds that pair to the `shop-domain` header, so the attacker can resend the identical body and valid HMAC to the app's public webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header value (e.g., naming a victim shop). `HmacValidator.validate` will pass, and the app will process the payload believing it originated from the victim shop.

### Impact Explanation
This breaks the identity binding between the cryptographically authenticated bytes (body) and the tenant the app associates the data with. If the host app (as the gem's own documented example demonstrates) uses `data.shop` to select which shop's session/records/queue the webhook body applies to, an attacker can inject data attributed to another merchant's shop — a cross-tenant data confusion/access primitive. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires only: (1) the attacker be able to receive at least one legitimate webhook for a shop they control (trivial — install the target app on any free/dev store), and (2) the ability to POST to the app's public webhook endpoint with custom headers (also trivial, since these endpoints are unauthenticated HTTP endpoints by design). No leaked secrets, tokens, or privileged access are required.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the signed material verified against Shopify's HMAC, or, since Shopify's real signature does not cover headers, have `Registry.process`/`Request` require the caller to supply the shop domain out-of-band (e.g., from the route/session context that received the request) rather than trusting the `X-Shopify-Shop-Domain` header value as an authenticated identity, and document this requirement prominently so integrators do not use `data.shop` as a trusted tenant key without additional verification (e.g., confirming the shop has an existing valid session/webhook registration matching the webhook_id).

### Proof of Concept
```ruby
# Attacker installs the app on shop-attacker.myshopify.com and receives a genuine webhook:
raw_body = '{"id":1,"note":"hello"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body) # computed by Shopify, delivered to attacker

# Attacker resends the exact same body+hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to a victim shop they do not own:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # attacker-controlled, not covered by HMAC
  "x-shopify-webhook-id" => "attacker-chosen-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate succeeds (raw_body signature matches),
#    and the app's handler receives data.shop == "victim-shop.myshopify.com"
``` [6](#0-5)
