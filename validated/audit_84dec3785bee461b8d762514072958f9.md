### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw request body only, while the `shop` (tenant identity) is read from a separate, unsigned HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC of the body and then dispatches the (unauthenticated) `shop` value straight to the app's webhook handler, so the value the app relies on to attribute the event to a tenant is never bound to the signature that proves the payload is genuine.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed content: [2](#0-1) 

`HmacValidator.validate` (used by `Registry.process`) only checks `verifiable_query.to_signable_string` against `verifiable_query.hmac`, i.e. only the body bytes are verified — the `shop` header is never included in that computation: [3](#0-2) 

`Registry.process` validates only that HMAC, then immediately forwards `request.shop` — an unverified field — to the app's handler as the tenant identifier: [4](#0-3) 

This breaks the intended identity binding:
`shop asserted to handler == shop that produced/authorized the signed body`

Because `shop` is not covered by the HMAC, an attacker who possesses one validly-signed webhook body/HMAC pair (trivially obtainable: any store owner or app installer receives genuine signed webhooks for their own shop) can replay that same body and HMAC while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` carrying the attacker-chosen shop value. This is precisely the "acted-on field not covered by the HMAC" class from the report (there, the ERC1155 transfer bound approvals to the wrong identity by trusting an unverified allowance path; here, the webhook consumer binds tenant data to an unverified `shop` header instead of the value cryptographically committed in the signed payload).

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` (as documented/intended, e.g. to select which merchant's session/access token or database record to update) can be tricked into associating a genuine, correctly-signed Shopify event with the wrong shop. This is a cross-tenant identity-binding bypass: data or side effects intended for shop A can be attributed to attacker-chosen shop B merely by replaying a body the attacker legitimately received once, with a doctored `shop-domain` header. This matches the "cross-tenant access" High/Critical impact category — the confidentiality/integrity boundary between tenants is broken using only a body the attacker was legitimately sent for their own shop.

### Likelihood Explanation
Likelihood is high for any app that stores/dispatches based on `WebhookMetadata.shop`: no privileged credentials are required beyond being any Shopify merchant/app installer who can trigger and capture one webhook delivery for their own store (e.g., a simple update to their own store's shop settings). The replay itself only requires re-POSTing captured bytes with a modified header value to the app's public webhook endpoint.

### Recommendation
Include the shop domain (and other routing-critical headers, e.g. topic, webhook-id/idempotency) in the HMAC-verified surface, or otherwise cryptographically bind the shop identity to the payload (e.g., derive/confirm shop from a value embedded and required inside the signed JSON body, not from a header) before trusting it in `Registry.process`/`WebhookMetadata`. At minimum, document clearly that `request.shop` is unauthenticated and must never be used by consuming apps without an independent tenant check (e.g., cross-referencing against the shop of the resource contained in `parsed_body`).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) for a small, harmless order. They capture the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent — both perfectly valid, signed with the real `api_secret_key` (which the attacker never needed to know).
2. Attacker replays the exact same raw body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this successfully (all required headers present).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`@raw_body`) only — this matches, since the body is identical to what was legitimately signed. [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker's own order payload>, ...)`. Any app logic keyed on `data.shop` (e.g., "look up victim-shop's access token/session and process this order") now operates under the wrong tenant context, using attacker-supplied data falsely attributed to the victim shop.
