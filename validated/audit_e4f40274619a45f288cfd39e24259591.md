This confirms the vulnerable pattern documented at [1](#0-0)  — the docs claim `Registry.process` "will verify the request did indeed come from Shopify," but the implementation only authenticates the request body, not the `shop-domain` or `topic` fields that the handler acts on.

### Title
Webhook `shop` and `topic` fields are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [2](#0-1) , while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers [3](#0-2) . `HmacValidator.validate` only checks the HMAC over `to_signable_string`, i.e. the body [4](#0-3) . `Registry.process` accepts the request once that body-only HMAC passes and then passes the unauthenticated `shop`/`topic` straight to the app's handler [5](#0-4) .

### Finding Description
The binding this breaks is: **shop/topic bytes acted upon by the handler == shop/topic bytes covered by the HMAC**. In this gem, only the raw body is signed; `shop-domain` and `topic` headers are excerpted verbatim and forwarded to `WebhookMetadata` without any cryptographic tie to the signature [6](#0-5) . Because every shop installed under the same Shopify app shares the same `api_secret_key` (`Context.api_secret_key`), any attacker who can obtain one valid `(body, hmac)` pair signed under that app's secret — e.g. by triggering/observing a webhook to their own store, which is legitimately signed with the same shared secret — can replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` header. `HmacValidator.validate` will still return `true` because it only verifies the body bytes [7](#0-6) , and `Registry.process` will happily dispatch the spoofed `shop`/`topic` combination to the handler as though Shopify itself sent it for that shop [5](#0-4) . The gem's own documentation states that `process` "will verify the request did indeed come from Shopify" [8](#0-7)  and that `data.shop`/`data.topic` are safe values applications should key logic on [9](#0-8) , which overstates the actual guarantee: no verification is provided for `shop` or `topic`, only for the body.

### Impact Explanation
An attacker (any merchant who has installed the app, i.e. an unprivileged internet user relative to other tenants) can forge webhook deliveries attributed to a different shop or topic, causing the host application to process attacker-controlled data as if it belonged to another merchant's shop domain — a cross-tenant confusion/spoofing vector. Depending on how the host app keys downstream logic off `data.shop` (record lookup, session association, billing actions, data writes), this can lead to cross-tenant data corruption or disclosure.

### Likelihood Explanation
Requires the attacker to already have at least one legitimately-signed webhook body+HMAC pair from the shared app secret (trivial for any installed merchant, since they receive their own genuine webhooks) and the ability to POST an HTTP request with custom headers to the app's public webhook endpoint (no elevated privilege needed). This is a realistic, low-effort attack path for any app that trusts `data.shop`/`data.topic` for tenant-scoping, which the docs encourage.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC-signable payload (or otherwise cryptographically bind them to the body signature) instead of trusting raw headers, and update `docs/usage/webhooks.md` to accurately describe what `process` actually authenticates.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a genuine webhook (e.g. `orders/create`), capturing the raw body and the valid `X-Shopify-Hmac-Sha256` header — both signed with the app's single shared `api_secret_key`.
2. Attacker replays that exact `(raw_body, hmac)` pair to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or a different `X-Shopify-Topic`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers, `HmacValidator.validate` passes because it only checks the body bytes against the shared secret [4](#0-3) , and `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` [5](#0-4) , despite the request never having originated from Shopify for that shop.
