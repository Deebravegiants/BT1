### Title
Reentrancy in Tron `IntentGatewayV2.withdraw` — escrow decrement occurs after external token transfer, with no `nonReentrant` guard anywhere in the contract - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` implements its own `withdraw()` routine that violates the Checks-Effects-Interactions pattern in exactly the way described in the external report: it performs the external token transfer via a raw low-level `.call()` and only decrements the escrow accounting (`_orders[body.commitment][token] -= amount`) afterward. Unlike the hardened mainline EVM contracts (`evm/src/apps/intentsv2/*`), which were patched to set `_filled[commitment]` before the transfer loop and additionally wrap every state-mutating entry point (`placeOrder`, `fillOrder`, `cancelOrder`) with `nonReentrant` (confirmed by the dedicated regression suite `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`), the Tron contract has **no `nonReentrant` modifier anywhere** in the file.

### Finding Description
`withdraw()` in the Tron contract: [1](#0-0) 

transfers escrowed tokens to the beneficiary using `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only afterwards executes `_orders[body.commitment][token] -= amount;`. This is directly reachable by any unprivileged user without a cross-chain proof through the same-chain cancellation path: [2](#0-1) 

`cancelOrder` (same-chain branch) is `public payable` with **no `nonReentrant` modifier**, and calls `withdraw(body, true)` synchronously using `order.inputs` — tokens fully chosen by the order creator at `placeOrder` time: [3](#0-2) 

Because the token used as an order input is attacker-selectable, an attacker can escrow a callback/hook-bearing ERC-20 (e.g. an ERC-777-style token, mirroring the `WeirdToken` PoC in the original report) as the order's input, then call `cancelOrder` to trigger `withdraw()`, whose raw `.call()` invokes the token's transfer hook mid-execution — before the escrow bookkeeping for that token is finalized.

While `_filled[body.commitment]` is set at the top of `withdraw()` (line 693) — which blocks a naive re-entrant call into `cancelOrder`/`withdraw` for the *same* commitment (the nested call reverts with `Filled()`, and since `withdraw` uses `.call()`, that revert is caught and surfaces as `TransferFailed()`, aborting the whole transaction rather than enabling silent theft for that specific vector) — the contract provides **no defense-in-depth**: every other state-mutating function (`placeOrder`, `select`, `fillOrder`) is likewise missing `nonReentrant`. This is a direct regression from the mainline contract, whose developers evidently concluded CEI ordering alone was insufficient, since they layered `nonReentrant` on top of the CEI fix across `placeOrder`, `fillOrder`, and `cancelOrder`: [4](#0-3) [5](#0-4) 

The Tron contract carries none of these protections, and the reentrant hook has multiple unguarded surfaces available (e.g. placing a fresh order, or interacting with cross-chain dispatch paths) during the token-transfer callback window, before the current withdrawal's escrow state and any surrounding balances/accounting are finalized.

### Impact Explanation
Any user can trigger `withdraw()` (via same-chain `cancelOrder`, or indirectly via the destination-chain `onAccept`/`onGetResponse` `RedeemEscrow`/`RefundEscrow` flows that are ultimately funded by this same vulnerable function) using a malicious hook-bearing token as an order input. Because escrow accounting is updated only after the external transfer completes, and because the contract has zero reentrancy protection compared to its own hardened sibling implementation, any additional cross-function reentrant surface reachable from the hook (unguarded `placeOrder`/`fillOrder`) can be abused to manipulate escrow/fee state relative to token balances actually held by the contract, resulting in theft of pooled escrow funds or fee-token balances belonging to other users' orders — a direct, unbacked-drain risk of the same class documented in the referenced Beedle `Lender.refinance` report.

### Likelihood Explanation
High. `placeOrder` and `cancelOrder` are fully permissionless, and the order creator freely chooses the input token, so no privileged setup is required — an attacker only needs to deploy one hook-bearing ERC-20 and place/cancel an order with it. The complete absence of `nonReentrant` guards (in contrast to the mainline contract, which the project's own test suite shows was patched for exactly this bug class) indicates this Tron variant did not receive the corresponding security fix.

### Recommendation
Port the same fix applied to `evm/src/apps/intentsv2/IntentsBase.sol` (`_withdraw`) to the Tron `IntentGatewayV2.sol`:
1. Decrement `_orders[body.commitment][token]` **before** performing the external transfer (Checks-Effects-Interactions).
2. Add `nonReentrant` modifiers to all state-mutating external entry points (`placeOrder`, `cancelOrder`, `fillOrder`/`select`), matching the mainline EVM contract.
3. Replace raw `.call()`-based transfers with `SafeERC20.safeTransfer`, consistent with `IntentsBase.sol`.

### Proof of Concept
1. Attacker deploys a hook-bearing ERC-20 (`WeirdToken`-style, calling back on transfer, as in the original report's PoC).
2. Attacker calls `placeOrder` on the Tron `IntentGatewayV2`, escrowing `WeirdToken` as `order.inputs[0]`.
3. Attacker calls `cancelOrder` (same-chain path) for their own order — permitted since `order.user == msg.sender`.
4. `cancelOrder` → `withdraw(body, true)` sets `_filled[commitment]`, then loops over tokens: for `WeirdToken`, it calls `token.call(transfer(...))`, which fires the token's transfer hook back into attacker-controlled code, **before** `_orders[commitment][token] -= amount` executes.
5. Inside the hook, because `cancelOrder`/`placeOrder`/`fillOrder` carry no `nonReentrant` guard, the attacker invokes `placeOrder` again (or any other unguarded state-mutating function) while the original `withdraw()` frame's escrow state for this token has not yet been finalized, corrupting the relationship between `_orders` accounting and actual token balances held by the contract — enabling excess withdrawal of pooled funds on subsequent calls.         bytes32 commitment = keccak256(abi.encode(order));

        // order has already been filled
        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

            // Same-chain: validate locally and refund immediately
