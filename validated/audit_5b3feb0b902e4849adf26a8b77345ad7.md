### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header — HMAC covers only the raw body, not the shop binding ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`), `topic`, `webhook_id`, and `api_version` entirely from HTTP headers, while `Utils::HmacValidator` only ever verifies the raw request body against those headers being untouched. The webhook processing pipeline (`Registry.process`) trusts `request.shop` as the authoritative tenant identifier for the handler without that value ever being covered by the HMAC signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0)  and `Request#hmac` reads the `hmac-sha256` header [2](#0-1) . `HmacValidator.validate` computes an HMAC over `to_signable_string` (the body only) and compares it to the supplied `hmac` header using the app's `api_secret_key` [3](#0-2) . Nothing about the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers is part of the signed content — `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are read straight from attacker-controllable headers [4](#0-3) .

`Registry.process` validates only the HMAC and then dispatches directly using the unauthenticated `request.shop`/`request.topic`/`request.webhook_id` values as the tenant/topic identity handed to the app's handler: [5](#0-4) 

Because `api_secret_key` (the app's `client_secret`) is a single value shared across **every** shop that installs the app — not a per-shop secret — a valid `(body, hmac)` pair generated for one shop's webhook is cryptographically valid for **any** shop, since the shop identity is never part of the signed content. The equality the gem should enforce is:
`hmac == HMAC(api_secret_key, body) AND shop-in-signed-content == shop-used-for-tenant-dispatch`

but only the first half is checked; the second half doesn't exist.

### Impact Explanation
An unprivileged internet user who is (or can become) a legitimate merchant installing the same app can trigger any webhook topic on their own store to obtain one real `(body, x-shopify-hmac-sha256)` pair signed by the app's shared secret. They can then replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header naming a victim shop. `Utils::HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` forwards `shop: <victim-shop>` to the app's handler together with attacker-chosen body content. This is a cross-tenant identity-binding break: data/events attributed to shop A can be injected and processed as if belonging to shop B, potentially corrupting per-tenant state, ACLs, or triggering shop-scoped side effects (e.g., app/uninstalled-style bookkeeping, order/customer data ingestion) under a victim's tenant identity.

### Likelihood Explanation
Any developer building on this gem's documented `Registry.add_registration`/`Registry.process` API and using `WebhookMetadata#shop` as the tenant key (the natural, expected usage) is exposed. The prerequisite — being able to trigger one legitimate webhook to harvest a valid body/HMAC pair — is trivially achievable by any merchant/developer who installs the app, which requires no privileged credentials, no `access_token`, and no knowledge of `api_secret_key`.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is cryptographically verified, e.g. include the `X-Shopify-Shop-Domain` header value in the signable string used by `HmacValidator`, or independently verify that the `shop` extracted from headers matches an identity that the app has previously bound to this specific `access_token`/session before dispatching to a handler. At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted as the sole tenant discriminator without additional validation (e.g., cross-checking against a shop the app already has an active offline session for).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook topic (e.g., `products/create`), receiving from Shopify a POST with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker replays the identical request to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com` (keeping body `B` and `H` unchanged).
3. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)` and compares to `H` — passes, since body was untouched [6](#0-5) .
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` with `shop == "victim.myshopify.com"` and dispatches to the app's handler [7](#0-6) , which processes attacker-controlled body content under the victim shop's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
