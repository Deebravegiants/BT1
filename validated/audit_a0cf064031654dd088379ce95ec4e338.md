Based on my investigation, I found a direct analog to the reported `setApr`/`setFundingFee` bug class in `aptos-move/move-examples/swap/sources/liquidity_pool.move`.

### Title
Unbounded `swap_fee_bps` set via `set_stable_fee`/`set_volatile_fee` bypasses the module's own `MAX_SWAP_FEES_BPS` cap - (File: `aptos-move/move-examples/swap/sources/liquidity_pool.move`)

### Summary
The `liquidity_pool` module defines a constant `MAX_SWAP_FEES_BPS: u64 = 25` (0.25%) that is clearly intended to cap the swap fee taken from every trade [1](#0-0) . However, the `fee_manager`-gated setters that mutate the fee configuration never enforce this cap.

### Finding Description
`stable_fee_bps` and `volatile_fee_bps` are stored in the shared `LiquidityPoolConfigs` resource [2](#0-1)  and are copied directly into each new pool's `swap_fee_bps` field at pool-creation time [3](#0-2) .

The setter functions that let the `fee_manager` update these values perform no bound checking whatsoever: [4](#0-3) 

They only route through `fee_manager_only_mut_liquidity_pool_configs`, which just checks the caller's identity, not the value being set. The `MAX_SWAP_FEES_BPS` constant is declared but never referenced by these setters — it is dead code with respect to enforcement. Since `FEE_SCALE = 10000` represents 100% [5](#0-4) , a `fee_manager` (malicious or "fat-fingered") can set `new_fee_bps` to any `u64` value — including values at or above `10000` (≥100% fee) or arbitrarily large values that would corrupt downstream fee-based arithmetic (e.g. `amount * fee_bps / FEE_SCALE` computations used for reserves/output-amount math), causing either:
- Pools to take up to (or beyond) 100% of swapped-in tokens as "fees" (custody/theft of trader funds diverted into `fees_store_1`/`fees_store_2`, which are later claimable by LPs via `claim_fees` [6](#0-5) ), or
- Arithmetic overflow/abort in swap fee/output computations, causing a denial-of-service for all trades against that pool (since `swap_fee_bps` is baked into each pool at creation time and is not user-adjustable per-pool).

This mirrors the original `LoanVault.setApr`/`setFundingFee` bug class exactly: a privileged but not fully-trusted role (`fee_manager` here vs. `owner` there) can set an unconstrained percentage parameter that is later used unchecked in value-transfer math, with no min/max enforcement despite the codebase itself defining an intended maximum.

### Impact Explanation
If `swap_fee_bps` is pushed near or above `FEE_SCALE` (10000), swappers can lose most or all of their input tokens to the pool's fee accounting, and those "fees" are custody-shifted to the `fees_store_1`/`fees_store_2` objects claimable by LPs — i.e., value taken from swappers and moved to the wrong economic holder, matching the "custody accounting corruption that moves value to the wrong holder" impact class. In the DoS variant, all future swaps against affected pools would be permanently blocked once created with a corrupt fee, since `swap_fee_bps` is immutable per-pool after creation.

### Likelihood Explanation
Low-to-medium: requires the `fee_manager` role (set via `set_fee_manager`/`accept_fee_manager` [7](#0-6) ) to be malicious, compromised, or to make an input mistake — same likelihood class as the original report. No exploitation by unprivileged users is possible; this is purely a missing-input-validation issue for a privileged setter.

### Recommendation
Add `assert!(new_fee_bps <= MAX_SWAP_FEES_BPS, ...)` (and any desired minimum) in both `set_stable_fee` and `set_volatile_fee` before mutating `pool_configs.stable_fee_bps`/`volatile_fee_bps`, consistent with the module's own already-declared `MAX_SWAP_FEES_BPS` constant.

### Proof of Concept
1. `fee_manager` calls `set_volatile_fee(fee_manager, 10000)` (or any value up to `u64::MAX`) — this succeeds with no error since there is no bound check [8](#0-7) .
2. A new volatile pool is created via `create(...)`, copying `configs.volatile_fee_bps` (now 10000+) into `LiquidityPool.swap_fee_bps` [9](#0-8) .
3. Any swap against this pool computes fees using this corrupted `swap_fee_bps`, resulting in either an aborting/DoS'd pool or full/near-full confiscation of swapper input as "fees" credited to LP claimants.

**Note on completeness:** I was not able to fully trace the exact swap fee application arithmetic (the function that consumes `swap_fee_bps` during a swap, likely in the same file beyond what I retrieved) within the available search budget, so I cannot cite the precise overflow/output-corruption line. I recommend a Devin session with full file access to confirm the exact downstream arithmetic effect (overflow abort vs. silent value transfer) if that level of certainty is required before filing.
