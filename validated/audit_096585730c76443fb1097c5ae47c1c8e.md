### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant shop-attribution spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while `Registry.process` trusts the unauthenticated `shop-domain` header to attribute the webhook to a merchant. This breaks the intended binding: `HMAC(body) == HMAC(body)` should imply `authenticated_shop == attributed_shop`, but the `shop` value used by the handler is never part of the signed bytes.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is attacker-controlled input at the transport layer and is not included anywhere in `to_signable_string`: [2](#0-1) 

`Registry.process` validates the request via `Utils::HmacValidator.validate(request)`, which only re-computes `HMAC(to_signable_string)` (i.e., `HMAC(raw_body)`) and compares it to the `hmac` header: [3](#0-2) 

After this check passes, `process` immediately dispatches to the app's handler using `request.shop`, which was never covered by the HMAC: [4](#0-3) 

This is the exact bug class described in the report: a field (`shop`) is acted upon by the code but is not covered by the integrity check (HMAC), so the verified bytes (`raw_body`) and the bytes trusted for identity attribution (`shop-domain` header) diverge. Compare this with the OAuth callback path, where `AuthQuery#to_signable_string` correctly includes `shop` in the signed payload, so `shop` there is bound to the HMAC: [5](#0-4) 

Because Shopify signs webhooks using a per-app shared secret (`Context.api_secret_key`) rather than a per-shop secret, any legitimate webhook payload from Shop A (whose HMAC is valid for the app) can be re-delivered to the app's webhook endpoint with the `shop-domain` header rewritten to Shop B. The HMAC still validates (it only checks the raw body against the shared app secret), and the handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` even though the payload/HMAC actually came from Shop A's event.

### Impact Explanation
This crosses a tenant boundary: it allows an unprivileged internet user (anyone who can capture or replay a validly-signed webhook payload, e.g. via a `shop/redact`, `customers/data_request`, `orders/create` webhook, or by controlling their own store to generate a validly-HMAC'd payload) to make the gem attribute that event to an arbitrary victim shop. Any host application that keys business logic (data writes, cache invalidation, redaction, entitlement checks) off `WebhookMetadata#shop` without independently cross-checking the shop against its own registration records or session store would perform actions against the wrong tenant using attacker-supplied data — i.e., cross-tenant access/data confusion driven entirely through this gem's own webhook-processing API.

### Likelihood Explanation
Medium-High. The attacker needs one validly-signed webhook body (trivially obtainable by registering their own app installation/shop and receiving any webhook, since the same `api_secret_key` signs bodies for all shops using this app) and the ability to POST to the app's public webhook endpoint with a modified `shop-domain` header — both are within reach of an unprivileged internet user with no credentials, tokens, or `client_secret` required.

### Recommendation
Include the shop-identifying header(s) (`shop-domain`, and ideally `topic`/`webhook-id`) in the HMAC-signable string, or otherwise cryptographically bind them to the body (e.g., compute the HMAC input as `shop-domain + raw_body`), so `Utils::HmacValidator.validate` fails whenever the `shop` header does not match the shop that produced the signed payload. At minimum, document that host applications must not trust `WebhookMetadata#shop` without independent verification.

### Proof of Concept
1. Attacker creates their own store `attacker.myshopify.com` and installs the target app, or otherwise obtains any validly-signed webhook delivery for the app (e.g., `orders/create` with `X-Shopify-Hmac-SHA256` computed over `raw_body` using the app's shared `api_secret_key`).
2. Attacker replays this exact `raw_body` and `hmac-sha256` header to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` — validation succeeds because the body/HMAC pair is legitimate. [6](#0-5) 
4. The registered `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's data>, ...)`, causing the host app to process attacker-controlled data as if it originated from the victim shop.
