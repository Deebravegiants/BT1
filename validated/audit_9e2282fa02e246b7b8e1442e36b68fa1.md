## Title
`Oauth.begin_auth` / `Oauth.validate_auth_callback` skip `ShopValidator` sanitization applied elsewhere in the gem, allowing an attacker-controlled `shop` value to receive the app's `client_secret` - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Utils::ShopValidator.sanitize!` is the gem's designated control for binding a caller-supplied `shop` string to a genuinely trusted Shopify host before that string is used to build a URL that the gem POSTs the app's `client_id`/`client_secret` to. It is used in `TokenExchange.migrate_to_expiring_token` [1](#0-0)  and in `ClientCredentials`/`RefreshToken`/`Storefront` client code, but it is never called in `Auth::Oauth.begin_auth` or `Auth::Oauth.validate_auth_callback` [2](#0-1) [3](#0-2) .

### Finding Description
`begin_auth(shop:, ...)` takes `shop` as a raw caller-supplied string (the gem's own usage docs show it being read straight from a request header/param, e.g. `request.headers["Shop"]`) and feeds it directly into `auth_base_uri(shop)`: [4](#0-3) 

```ruby
def auth_base_uri(shop)
  return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")
  ...
end
```

There is no call to `Utils::ShopValidator.sanitize!` anywhere in `oauth.rb`, unlike `token_exchange.rb`'s `migrate_to_expiring_token`, which explicitly does:

```ruby
validated_shop = Utils::ShopValidator.sanitize!(shop)
shop_session = ShopifyAPI::Auth::Session.new(shop: validated_shop)
``` [5](#0-4) 

The consequence is in `validate_auth_callback`, where `auth_query.shop` (a component of `AuthQuery`, HMAC-verified only insofar as it reproduces exactly the string originally sent by the OAuth authorization host) is used unvalidated to build the base URI for the access-token exchange request, which carries the app's `client_id` and `client_secret` in the POST body: [6](#0-5) 

```ruby
null_session = Auth::Session.new(shop: auth_query.shop)
body = {
  client_id: Context.api_key,
  client_secret: Context.api_secret_key,
  code: auth_query.code,
  ...
}
client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
response = client.request(
  Clients::HttpRequest.new(http_method: :post, path: "access_token", body: body, body_type: "application/json"),
)
```

The identity binding that should hold is: **`shop` string used to construct the token-exchange request host == a value that has passed `ShopValidator.sanitize!`/its trusted-domain allowlist** (exactly the binding enforced in `migrate_to_expiring_token`). In `Oauth.validate_auth_callback`, that binding does not hold — `auth_query.shop` is used as-is. `HmacValidator.validate` only proves that the HMAC in the callback matches a signature computed over `{code, host, shop, state, timestamp}` with `Context.api_secret_key` [7](#0-6) ; it does not check that `shop` is actually a `*.myshopify.com`/trusted admin domain, nor does it check that the `Host: <trusted domain>` used to build the outbound request URL is the same value protected by that signature versus a value an app developer might pass through unsanitized from `request.parameters` before HMAC verification even runs — note the documented usage pattern builds the `AuthQuery` directly from raw `request.parameters` [8](#0-7) .

### Impact Explanation
If `begin_auth`'s `shop` argument (attacker/tenant supplied, e.g. from a query/header) is not previously validated by the host app, `auth_base_uri(shop)` builds `"https://#{shop}/admin"` unchecked — an app author following the gem's own documented sample code (`shop = request.headers["Shop"]`) [9](#0-8)  gets no protection from the library itself, whereas `migrate_to_expiring_token` deliberately hardens the exact same class of input with `ShopValidator.sanitize!`, showing the library's own security model expects this check on every "shop→host" pathway. Because the OAuth callback flow's `validate_auth_callback` reuses `auth_query.shop` to construct the URL that receives the app's `client_id`/`client_secret` (High-impact category: SSRF with the app's credentials), the missing sanitize! call here is a real gap relative to the gem's own established control, and is inconsistent with the "host validated versus host that receives the client_secret" identity binding that the library enforces elsewhere.

### Likelihood Explanation
Exploitation still requires either (a) an app developer wiring unsanitized shop input into `begin_auth`/`validate_auth_callback` exactly as the gem's own docs sample, or (b) some means of getting Shopify's OAuth authorize/callback flow to sign a callback for a non-myshopify shop value. I was not able to confirm within the scope of this investigation whether Shopify's OAuth service itself would ever produce a valid HMAC for a non-`myshopify.com` `shop` value passed through `auth_query.shop`; if it does not, the practical exploitability of the `validate_auth_callback` path is reduced to the `begin_auth` open-redirect variant, which does not itself leak `client_secret` (no credential is sent in `begin_auth`). This uncertainty means I cannot assert with confidence that an unprivileged internet user can force `validate_auth_callback` to leak `client_secret` to an arbitrary host without further verification against Shopify's live OAuth server behavior, which is outside what static code review of this gem can prove.

### Recommendation
Apply `Utils::ShopValidator.sanitize!` (or an equivalent trusted-domain check) to `shop` in `Auth::Oauth.begin_auth` before constructing `auth_base_uri`, and to `auth_query.shop` in `Auth::Oauth.validate_auth_callback` before it is used to build the `Auth::Session`/`HttpClient` base path that receives `client_id`/`client_secret`, mirroring the pattern already used in `TokenExchange.migrate_to_expiring_token`.

### Proof of Concept
Not independently confirmed end-to-end against Shopify's live OAuth authorize/callback endpoints; the code-level gap (absence of `ShopValidator.sanitize!` in `oauth.rb` versus its presence in `token_exchange.rb`) is demonstrated by direct comparison of the two files cited above. A concrete PoC would require driving the OAuth callback with a Shopify-issued, validly HMAC-signed callback for a non-myshopify `shop` value (or reproducing the app's documented unsanitized-header usage in `begin_auth`) — verifying whether Shopify's servers ever permit the former was not possible within this review.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))
```

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
