### Title
RAY-scaled market value overflows `i128` inside accrual, permanently freezing the market — ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
CVE-2024-41439 is a heap buffer overflow reachable via a crafted input file, causing a Denial of Service. The XOXNO Lending analog is an `i128` overflow reachable via attacker-crafted position size: `accrue_step` unscales the whole book (`scaled_to_original(borrowed, borrow_index)` / `supplied × supply_index`) every accrual step, and `Ray::mul` panics with `GenericError::MathOverflow` once `scaled × index` exceeds `i128::MAX`. Since every verb (`supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `update_indexes`, flash paths) runs `global_sync` accrual first, one accrual panic bricks the market permanently — no exit path exists, and the `MAX_BORROW_INDEX_RAY` cap does not engage before the value cliff.

### Finding Description
`accrue_step` in `common/src/rates/simulate.rs` unconditionally computes:

- `borrowed_original = scaled_to_original(env, borrowed, borrow_index)` at line 60
- `supplied_original = scaled_to_original(env, supplied, supply_index)` at line 61

Both call `scaled.mul(env, index)` (`common/src/rates/scaling.rs:14-16`), a half-up multiply-divide that panics on overflow per `docs/reference/formulas.md` ("Unrepresentable results raise `MathOverflow`"). A scaled book of ~1e36 raw RAY (one billion whole tokens at 18 decimals) reaches the `i128::MAX` ceiling when the index grows ≈170x — well before `MAX_BORROW_INDEX_RAY` (10^36 RAY, i.e. a 1e9 index multiple) can clamp growth in `update_borrow_index` (`common/src/rates/index.rs:13-19`). The chunked accrual in `simulate_update_indexes_body` (lines 157-175) and the mutating `global_sync`/`accrue_chunk` in `contracts/pool/src/interest.rs:20-53` both hit the panic on the very first step once the cliff is crossed; because the panic aborts before `last_timestamp` advances, every subsequent call re-executes the same overflowing step forever. The repository's own harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-360`) demonstrates this end-to-end: after the cliff, `try_update_indexes_for`, `try_withdraw_raw`, and `try_repay` all revert with `MATH_OVERFLOW`, and `borrow_index < MAX_BORROW_INDEX_RAY` confirms the index cap never protects the market.

### Impact Explanation
Permanent freezing of funds for every supplier and borrower in the affected market. Once `borrowed × borrow_index` (or `supplied × supply_index`) overflows `i128`, no state-changing entrypoint on that market can succeed: `global_sync` panics before any withdraw, repay, liquidate, or bad-debt cleanup logic runs. Suppliers' deposits, borrowers' remaining collateral backing, and accrued protocol revenue are all unrecoverable. This matches the accepted "permanent freezing of funds" impact, and the DoS is not fail-closed-by-choice — the contract is mathematically unable to operate.

### Likelihood Explanation
An unprivileged attacker seeds the condition with ordinary `supply`/`borrow` calls: supply a very large principal (the test uses 1 billion whole tokens / ~1e36 raw units at 18 decimals), borrow near-maximum against it, then sustain high utilization so the index compounds. At the steep end of the XLM-style curve the index passes ~170x within a few years; once crossed, the first call to `update_indexes` (permissionless) detonates the freeze. Requirements: a market whose caps allow a RAY-scaled book within ~170x of `i128::MAX` (high-decimal assets make this easiest), sustained high utilization, and time. It is capital-heavy and slow, hence Medium rather than High, but no privileged action, oracle manipulation, or third-party cooperation is needed — the attacker fully controls the position sizes that determine `borrowed`/`supplied`.

### Recommendation
Bound the multiplication instead of letting it panic: in `accrue_step`/`global_sync`, detect that `scaled × index` would exceed `i128::MAX` and clamp `borrow_index`/`supply_index` to the largest index that keeps the unscaled value representable (or cap total scaled supply at listing time so `scaled × MAX_SUPPLY_INDEX_RAY < i128::MAX`). Alternatively, compute utilization via `mul_div` on the scaled shares with an `I256` intermediate (the same path `mul_div_floor_saturating` uses for `calculate_scaled_cap` in `common/src/rates/scaling.rs:26-33`) so accrual itself never panics, and apply the index caps before the value computation. `docs/reference/invariants.md` INV-IDX-01 already acknowledges "debt-value overflow can still revert accrual before that ceiling"; the fix is to make the value computation saturating/I256 rather than checked-panic.

### Proof of Concept
```rust
// Existing harness test reproducing the freeze:
// tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-360
let principal = BILLION * 10i128.pow(18);           // ~1e36 raw units
t.supply_raw(BOB, "BIG18", principal);              // unprivileged supply
t.borrow_raw(ALICE, "BIG18", principal * 98 / 100); // ~98% utilization

// After enough accrual, the index crosses ~170x and:
t.try_update_indexes_for(&["BIG18"])  // Err: MATH_OVERFLOW
t.try_withdraw_raw(BOB, "BIG18", 1)   // Err: MATH_OVERFLOW — funds frozen
t.try_repay(ALICE, "BIG18", 1.0)      // Err: MATH_OVERFLOW — debt stuck
// book.borrow_index < MAX_BORROW_INDEX_RAY: the cap never engaged
```

The panic originates at `scaled_to_original` → `Ray::mul` on `borrowed × borrow_index` inside `accrue_step` (`common/src/rates/simulate.rs:60`), reached through `global_sync` (`contracts/pool/src/interest.rs:39-48`) before every market operation.
