## Title
Last LP holder can never fully withdraw — permanent freezing of residual pool funds - (File: `program/src/processor.rs`, `process_withdraw`)

### Summary
`process_withdraw` rejects any withdrawal request where `withdraw.amount >= amm.lp_amount`, which means a user can never redeem the entirety of the outstanding LP supply in a single call. This is the same bug class as the Amun Basket finding: a strict "must be less than total" check prevents the last holder(s) from fully exiting, permanently locking the final slice of pooled coin/pc tokens.

### Finding Description
In `process_withdraw`:
```rust
if withdraw.amount > lp_mint.supply || withdraw.amount >= amm.lp_amount {
    return Err(AmmError::NotAllowZeroLP.into());
}
``` [1](#0-0) 

`amm.lp_amount` tracks the total outstanding LP the pool believes is redeemable, and `withdraw.amount` is the amount of LP tokens the caller wants to burn. Because the comparison uses `>=` rather than `>`, a caller can never withdraw an amount equal to the full remaining `amm.lp_amount` — only strictly less. There is no special-case carve-out for "withdraw everything," unlike, e.g., initialize which permanently burns `10^decimals` LP worth of liquidity into the first depositor's mint (see `process_initialize2`) and expects the rest of the LP supply to eventually be fully redeemable.

Concretely: whichever single LP holder ends up owning the last remaining `amm.lp_amount` (which will happen for the final unredeemed LP position, whether that's one wallet holding all remaining LP or the very last redemption needed to zero out the pool) is blocked from ever executing a withdraw for the full amount they hold, since `withdraw.amount >= amm.lp_amount` always triggers `NotAllowZeroLP`. They can only submit `withdraw.amount < amm.lp_amount`, leaving at least 1 LP token (and its proportional share of `coin_amount`/`pc_amount` in the vaults) stuck forever, since after their partial withdrawal `amm.lp_amount` decreases but is still non-zero, and the same restriction reapplies on any subsequent attempt to close it out. There is no code path that permits `amm.lp_amount` to ever reach zero, so the residual coin/pc tokens backing that last sliver of LP become permanently unrecoverable.

This directly parallels the referenced Amun report: a check meant to prevent a degenerate "empty pool" state (`NotAllowZeroLP`) instead prevents the legitimate final full exit, freezing funds instead of protecting the invariant.

### Impact Explanation
Funds equal to the value of at least 1 LP unit's worth of `coin_amount`/`pc_amount` become permanently locked in the AMM's coin/pc vaults with no instruction path able to retrieve them, since `process_withdraw` is the only redemption path and it structurally forbids `withdraw.amount == amm.lp_amount`. This is a permanent freezing of legitimate user/LP funds, matching the "Medium/High" severity bar (freezing of user funds) used by the analogous report.

### Likelihood Explanation
This is reachable by any single unprivileged LP holder simply calling `Withdraw` with `amount` equal to their full LP balance once they are the sole/last holder of the pool's outstanding LP — a completely ordinary end-of-life scenario for any AMM pool (e.g., all other LPs have exited, or a pool is being wound down). No malicious behavior, special permissions, or unusual accounts are required — it will happen deterministically whenever someone tries to fully drain the pool via LP redemption.

### Recommendation
Change the check from `withdraw.amount >= amm.lp_amount` to `withdraw.amount > amm.lp_amount`, allowing a caller to redeem the entire remaining `amm.lp_amount` in one call. If a "never let the pool hit exactly zero LP" invariant is genuinely required (to protect the constant-product math elsewhere), that invariant should be enforced at the point where it matters (e.g., only prevent withdrawal to zero when `lp_mint.supply` after burn would be zero but other LP holders still exist), not as a blanket ban on withdrawing 100% of the currently outstanding LP.

### Proof of Concept
1. Initialize a pool via `Initialize2`; user A receives `user_lp_amount = liquidity - 10^decimals` LP tokens, and `amm.lp_amount` is set to that same minted amount. [2](#0-1) 
2. Assume A is (or becomes, after all other holders redeem) the sole holder of all outstanding `amm.lp_amount` LP tokens.
3. A calls `Withdraw` with `amount == amm.lp_amount` (their full balance) to exit completely.
4. `process_withdraw` evaluates `withdraw.amount >= amm.lp_amount` → true → returns `AmmError::NotAllowZeroLP`, reverting the transaction. [3](#0-2) 
5. A can only withdraw `amm.lp_amount - 1` at most, permanently leaving `1` LP's worth of `coin_amount`/`pc_amount` locked in `amm_coin_vault`/`amm_pc_vault`, with no instruction able to ever bring `amm.lp_amount` to zero.
