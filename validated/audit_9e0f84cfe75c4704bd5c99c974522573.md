### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from unauthenticated HTTP headers, while `Utils::HmacValidator` only signs/verifies the raw request body. `Registry.process` treats HMAC success as proof the whole request "did indeed come from Shopify" (per the gem's own documentation) and hands the unverified `shop` value straight to the app's webhook handler. This breaks the binding between "bytes verified by HMAC" and "shop identity acted upon," exactly analogous to the LP-token bug where a value used by the protocol (BPT) was not covered by the safety check meant to gate what can be acted on.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers, none of which are part of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC only over `to_signable_string` (the raw body) and compares it against the `hmac-sha256` header: [3](#0-2) 

`Registry.process` uses this validation as the sole authenticity gate, then passes the unverified `request.shop` on to the app's handler as tenant identity: [4](#0-3) 

The gem's own documentation instructs `process` callers that HMAC validation "will verify the request did indeed come from Shopify," and explicitly tells app authors to use `data.shop` as the shop domain to route/act on (e.g. `shop_domain: data.shop`): [5](#0-4) [6](#0-5) 

The identity binding broken: `hmac_valid_for(raw_body) == true` is treated as `shop_header == authentic_shop`, but no equality actually exists between the HMAC-verified bytes and the `shop` value acted upon.

### Impact Explanation
An attacker who controls (or has installed) the app on their own shop legitimately receives HMAC-valid webhook deliveries for their own shop/body pairs from Shopify. Because the `shop-domain` header is excluded from the signed content, the attacker can replay that same valid `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` calls the app's handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain — enabling cross-tenant data injection/impersonation (e.g., forging `orders/create`, `app/uninstalled`, or GDPR webhooks against another merchant's tenant record) without possessing that merchant's credentials. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that follows the gem's documented pattern of trusting `data.shop`/`request.shop` for tenant routing (which the docs explicitly recommend). The attacker needs no special access beyond controlling one legitimately-installed shop instance of the target app (an "unprivileged internet user" from the app's perspective, since anyone can install a public app on their own store) and the ability to send arbitrary HTTP headers to the app's public webhook route.

### Recommendation
Include the shop domain (and ideally topic/webhook-id/api-version) in the HMAC-signed payload used for verification, or otherwise cryptographically bind the header-derived shop value to the verified body (e.g., require the shop to match an actively registered/known shop with a stored offline session before acting, and document this requirement clearly). At minimum, update `to_signable_string` / `HmacValidator` so that the `shop` header cannot be altered without invalidating the HMAC, and revise the documentation so it does not claim the full request (including headers) is verified.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and configures a webhook subscription (e.g., `orders/create`).
2. Shopify delivers a legitimate webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures this request and resends it to the same endpoint, keeping body `B` and the HMAC header unchanged, but replacing `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac` still returns the correct decoded HMAC (unaffected by header change); `HmacValidator.validate` recomputes HMAC over `@raw_body` only and it matches, so `Registry.process` proceeds.
5. The registered handler is invoked with `WebhookMetadata.shop == "victim.myshopify.com"`, letting the attacker inject fabricated webhook data attributed to a shop they do not control.

- `topic`, `String` - The topic of the webhook

- `body`, `T::Hash[String, T.untyped]`- The body of the webhook

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
