## Analog Vulnerability Found

### Title
Unauthenticated `message.from` Field Allows Arbitrary Runtime-Call Dispatch Under Any Account Identity — (`modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler executes optional calldata attached to a cross-chain token transfer by dispatching a `RuntimeCall` under an origin (`RawOrigin::Signed(origin)`). When the `SubstrateCalldata.signature` field is `None`, the origin account is derived directly from the attacker-supplied `message.from` bytes inside the ABI-decoded message body — with no cryptographic proof that the caller controls that identity. This mirrors the WeGIA pattern: an unauthenticated, attacker-controlled identity field is trusted and used directly to authorize a privileged action, instead of being bound to a verified signer.

### Finding Description
In `on_accept` [1](#0-0) , the outer `PostRequest.from`/`source` pair is checked against `ContractToAsset` to authenticate which contract on the source chain sent the message. However, the `Message` body decoded from `body` (`message.from`, `message.to`, `message.amount`, `message.data`) is fully attacker-controlled ABI-encoded payload data — it is not itself authenticated by that lookup.

When `message.data` is non-empty, the pallet decodes `SubstrateCalldata { signature, runtime_call }` and computes the dispatch `origin`: [2](#0-1) 

- If `signature` is `Some(..)`, the code verifies the signature (Ed25519/Sr25519/Ecdsa) is over `(nonce, runtime_call)` and recovers/binds the signer to `beneficiary`, which is legitimate.
- If `signature` is `None`, the origin is instead derived straight from `message.from` with **no verification whatsoever**:
```rust
} else {
    let from_bytes = message.from.as_ref();
    if source.is_evm() {
        T::EvmToSubstrate::convert(H160::from_slice(&from_bytes[from_bytes.len() - 20..]))
    } else {
        let mut account = [0u8; 32];
        account.copy_from_slice(from_bytes);
        account.into()
    }
};
```
This `origin` is then used to dispatch an arbitrary `RuntimeCall`: [3](#0-2) 

Anyone able to trigger a cross-chain HFT send (a permissionless action reachable by any bridge user, analogous to the "message dispatcher" persona in scope) can set `message.from` to an **arbitrary 20- or 32-byte identity** of their choosing, entirely independent of `beneficiary` or the true message sender, and have a `RuntimeCall` dispatched as `RawOrigin::Signed(<that arbitrary account>)`. The only mitigation present is `BaseCallFilter::contains(&runtime_call)`, which filters *which calls* are permitted, not *who* is impersonated.

### Impact Explanation
Because the "signed" branch cryptographically binds the call to a real key holder while the "unsigned" branch binds it to nothing but attacker-supplied bytes, an attacker can dispatch any call not blocked by `BaseCallFilter` under an arbitrary victim's `AccountId`. Depending on which calls remain permitted by the runtime's filter, this can enable unauthorized transfers, approvals, votes, or other state-changing dispatchables performed "as" another account — a direct analog of WeGIA's SQL injection via unauthenticated identity override, satisfying the "unauthorized app action" acceptance criterion.

### Likelihood Explanation
High. No signature is required to reach the vulnerable branch — an attacker only needs to omit `substrate_data.signature` and craft `message.from` as any address, and to have the resources to trigger an ordinary HFT cross-chain send (this pallet's core function is reachable by any user with a token to send from a recognized source contract). No relayer collusion or privileged access is required.

### Recommendation
Remove the unsigned/"trust `message.from`" branch entirely, or require that `message.from` be cryptographically verifiable (e.g., always require `substrate_data.signature` before dispatching any `runtime_call`, or restrict the unsigned path to dispatching solely under `beneficiary`, the already-validated recipient, rather than an arbitrary attacker-chosen address).

### Proof of Concept
1. Attacker sends an HFT cross-chain message from a registered/authenticated source contract (satisfies `ContractToAsset` check).
2. In the message body, set `message.to` = attacker's own beneficiary account (to satisfy the token transfer step) and `message.data` = ABI-encoded `SubstrateCalldata { signature: None, runtime_call: <arbitrary call> }`.
3. Set `message.from` = victim's `AccountId` bytes (20 or 32 bytes, attacker's free choice, not the true sender).
4. On delivery, `on_accept` dispatches `runtime_call` with `RawOrigin::Signed(victim_account)` — no signature from the victim was ever checked. Any call permitted by `BaseCallFilter` now executes as if authorized by the victim.

**Note:** I could not fully trace the Solidity/EVM-side sender logic that populates `message.from` when a `HyperFungibleToken` send is initiated (e.g., whether the source contract enforces `from == msg.sender`), because the relevant `HyperFungibleToken.sol`/`WrappedHyperFungibleToken.sol` send-path source was not retrievable in this session. The pallet-side dispatch logic shown above, however, independently and unconditionally trusts `message.from` for identity whenever no signature accompanies the calldata, which is the exploitable condition regardless of how the field was populated on submission.

		PostRequest { body, from, source, .. }: PostRequest,

		let local_asset_id = ContractToAsset::<T>::get(source, &from)

		// Decode the Message
		let message = Message::abi_decode(&body).map_err(HftError::DecodeError)?;
