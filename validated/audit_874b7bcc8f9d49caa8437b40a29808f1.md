### Title
Unvalidated `purpose` parameter in `MessageSigner.signMessage` allows signing under an unapproved BIP44 derivation path/address - (File: `features/message-signer/src/module/message-signer.ts`, `features/message-signer/src/module/seed-signer.ts`, `features/message-signer/src/module/hardware-signer.ts`)

### Summary
`MessageSigner.signMessage` forwards the caller-supplied `purpose` field verbatim from the public `SignMessageParams` down to `SeedBasedMessageSigner.#getKeyId` / `HardwareMessageSigner.#getKeyId`, where it is combined via `purpose ?? defaultPurpose` and fed directly into `baseAsset.api.getKeyIdentifier(...)` with no check against the account's actual supported purposes returned by `assetSources.getSupportedPurposes`. This lets a caller pick an arbitrary BIP44 `purpose` value, causing the signature to be produced for a derivation path/address other than the wallet account's approved default.

### Finding Description
The call chain is:
- `MessageSigner.signMessage` destructures `purpose` from the untyped-at-runtime `SignMessageParams` and passes it straight through to the internal signer without validation: [1](#0-0) 
- `SeedBasedMessageSigner.#getKeyId` fetches the list of supported purposes only to derive `defaultPurpose = purposes[0]`, but never checks that the caller-supplied `purpose` is a member of that list before using it: `purpose: purpose ?? defaultPurpose` [2](#0-1) 
- The same pattern exists in the hardware path: [3](#0-2) 
- The resulting `KeyIdentifier`/derivation path is used directly to sign (`this.#keychain.signBuffer` for seed-based, or `device.signMessage({ derivationPath: keyId.derivationPath, ... })` for hardware), meaning whatever `purpose` was supplied determines the actual key/address used to produce the signature. [4](#0-3) [5](#0-4) 

`purpose` is typed only as an optional `number` (`Purpose = number`) with no enum/allow-list enforcement at the type or runtime level: [6](#0-5) 

The `messageSignerApi` simply forwards `params` from the caller into `messageSigner.signMessage` with no additional scoping: [7](#0-6) . The README explicitly documents `purpose` as a caller-supplied parameter with example value `44`, confirming it is part of the intended external API surface reachable via the SDK (`exodus.messageSigner.signMessage(...)`): [8](#0-7) 

The `getSupportedPurposes` call result is used only to compute a fallback default, not as an allow-list, so any numeric `purpose` value bypasses the account's intended derivation scheme entirely.

### Impact Explanation
An attacker-supplied `purpose` value that differs from `assetSources.getSupportedPurposes()[0]` (or any other value from that set) will cause `getKeyIdentifier` to compute a different `derivationPath`/`KeyIdentifier` than the one associated with the wallet account normally shown to and approved by the user for that asset/account. The resulting signature is then produced under a different address than the one the user believes they are signing with — a confused-deputy signature scoped to whatever alternate path/coin-type mapping the attacker selects, provided `getKeyIdentifier` for that asset can construct a valid key for the supplied purpose (e.g., BIP44 vs. BIP49/84/86 variants, or purpose values mapping to other coin-type derivations for multi-coin assets).

### Likelihood Explanation
The precondition is simply that a caller of `signMessage` (headless SDK / dapp-facing API) supplies `purpose` — which is explicitly documented as a public, unvalidated parameter of `SignMessageParams`. No privileged state, leaked keys, or social engineering is required; it only requires the ability to invoke `exodus.messageSigner.signMessage` with attacker-chosen parameters, which the README confirms is part of the normal external API contract. The bug is deterministic and repeatable for any asset whose `getKeyIdentifier` accepts multiple purposes.

### Recommendation
Validate the caller-supplied `purpose` against the list returned by `assetSources.getSupportedPurposes({ assetName, walletAccount })` in both `SeedBasedMessageSigner.#getKeyId` and `HardwareMessageSigner.#getKeyId` before using it, rejecting (throwing) if `purpose` is not one of the returned values. Alternatively, remove `purpose` from the externally reachable `SignMessageParams`/`IMessageSigner` surface and only allow it to be set internally/by trusted UI code that already knows the approved value.

### Proof of Concept
Add a unit test in `features/message-signer/src/module/__tests__/seed-signer.test.ts` (and analogously for `hardware-signer.test.ts`):
1. Mock `assetSources.getSupportedPurposes` to return `[44]` for a given `walletAccount`/`ethereum` asset.
2. Call `seedSigner.signMessage({ baseAssetName: 'ethereum', walletAccount, purpose: 999, message: { rawMessage: Buffer.from('hello world') } })`.
3. Assert that this call either throws (expected fix behavior) or, in the current code, assert that `baseAsset.api.getKeyIdentifier` was invoked with `purpose: 999` (proving the unvalidated override) and that the resulting `KeyIdentifier`/derivation path differs from the one computed with `purpose: 44` — demonstrating the signature is produced under a different key/address than the approved default.

    const compatibilityMode = walletAccount.compatibilityMode

    const purposes = await this.#assetSources.getSupportedPurposes({
      assetName: baseAssetName,
      walletAccount: walletAccount.toString(),
    })
    const defaultPurpose: number = purposes[0]!

    const defaultPathIndexes = getDefaultPathIndexes({
      asset: baseAsset,
      walletAccount,
      compatibilityMode,
    })

      purpose: purpose ?? defaultPurpose,
      accountIndex: walletAccount.index!,
      addressIndex,
      chainIndex,
      compatibilityMode: walletAccount.compatibilityMode,
