### Title
Webhook HMAC signature does not bind the `shop`/tenant identity header, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes/verifies the HMAC only over the raw request body, while the shop identity used to attribute the webhook to a tenant (`X-Shopify-Shop-Domain`) is read from an HTTP header that is never included in the signed bytes. This breaks the equality `shop authenticated by HMAC == shop the webhook is attributed to`, allowing a merchant who has the app installed on their own store to replay a validly-signed webhook body while swapping the shop-domain header to impersonate another tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But the tenant identity (`shop`) that the rest of the pipeline trusts is pulled straight from a header, not from the signed payload: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC (which only covers the body) and then dispatches the handler using `request.shop`, `request.topic`, and `request.webhook_id`, none of which are covered by that signature: [4](#0-3) 

`HmacValidator.validate` simply HMACs `to_signable_string` (the raw body) with the app's secret and compares it to the supplied `hmac` header — it has no knowledge of, and does not cover, the shop-domain/topic/webhook-id headers: [5](#0-4) 

This is the same bug class as the report: a value that gets acted upon later (pool owner / fee-beneficiary in the report; shop/tenant attribution here) is not covered by the mechanism that is supposed to bind it (the setter's lack of downstream re-validation in the report; the HMAC signature in this gem). Concretely, the binding that should hold is:
`shop_the_body_was_signed_for == request.shop used to route/process data`
but the gem only enforces `hmac(raw_body) == received_hmac`, with `request.shop` sourced independently from an unauthenticated header.

### Impact Explanation
An attacker who is simply a legitimate (unprivileged, non-app-secret-holding) merchant with the app installed on their own store receives real, validly-HMAC-signed webhook deliveries for their own shop. They can capture one `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while altering only the `X-Shopify-Shop-Domain` header to name a victim shop. Because `Utils::HmacValidator.validate` never considers the shop header, the forged request passes verification, and `Registry.process` will hand the attacker-controlled body to the handler tagged with the victim's shop: [6](#0-5) 

Depending on what the host app's webhook handlers do with `WebhookMetadata#shop` (e.g. updating per-shop settings, triggering per-shop side effects, uninstall/redact bookkeeping), this results in cross-tenant data injection/manipulation attributed to a shop the attacker does not control — a cross-tenant access impact.

### Likelihood Explanation
Any merchant who installs the app (no special privilege, no `client_secret`, no access token) can obtain a validly signed body/HMAC pair from their own legitimate webhook traffic and immediately replay it with a different shop header value at the app's public webhook endpoint. No cryptographic secret needs to be broken; only the unauthenticated header needs to be changed.

### Recommendation
Include the tenant-identifying headers (`X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, `X-Shopify-API-Version`) in the signable material used for `Request#to_signable_string`, or otherwise cryptographically bind the shop domain to the verified payload before it is used for routing/attribution in `Registry.process`. At minimum, document and warn implementers that `request.shop` is not covered by the HMAC and must not be treated as a verified tenant identity.

### Proof of Concept
1. Attacker installs the target app on their own development/merchant store (no special access needed) and triggers a webhook subscribed via `Registry` (e.g. `orders/create`).
2. Attacker captures the raw POST body and the `X-Shopify-Hmac-Sha256` header from the legitimate delivery.
3. Attacker resends the same body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes HMAC over `@raw_body` [1](#0-0) .
5. `Registry.process` invokes the handler with `shop: request.shop` equal to `victim-shop.myshopify.com` [6](#0-5) , causing the host app to process attacker-controlled data as belonging to the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
