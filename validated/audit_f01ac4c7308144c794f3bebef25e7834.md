### Title
User-centric signups locally accepted as successful without backend fraud/duplicate verification - ([File: src/plans/mod.rs])

### Summary
The 0x report describes a class of bug where a caller relies on a local/pre-execution check (`getOrderInfo`) to decide whether an action is valid, while the authoritative execution path (`fillOrder`) can diverge from that local judgment for reasons that are never surfaced back to the caller — resulting in an outcome that is accepted/finalized even though the real backend-level validation never actually ran. `orb-core`'s `do_signup` function contains the same class of divergence: when `user_centric_signup` is `true`, the Orb marks the signup as successful purely from a *local* `signup_reason` value, entirely skipping the call to `enroll_user`, which is the only code path that consults the backend for duplicate/fraud/in-flight detection.

### Finding Description
In `Plan::do_signup`, after the biometric pipeline runs, the Orb computes `signup_reason` locally (`Normal`, `Failure`, or `Fraud`) based only on local pipeline output and local `detect_fraud` result: [1](#0-0) 

It then branches on `user_centric_signup` (a boolean supplied by the app through the QR-code-verified backend response, not backend-enforced logic executed at signup time): [2](#0-1) 

When `user_centric_signup` is `true` and `ignore_user_centric_signups` is `false`, `success` is derived solely from `signup_reason == SignupReason::Normal` — the `enroll_user` call is never invoked. Compare this to the `else` branch, which calls `enroll_user`, which POSTs to the signup backend and polls `signup_poll` for a definitive verdict. The comments in `enroll_user.rs` make explicit that this backend round trip is the *only* place where duplicate identities, legacy/in-flight signups, and backend-side fraud detection are checked: [3](#0-2) 

So for the `user_centric_signup` branch, none of "Backend duplicates", "Backend legacy signup requests", "Backend inflight matches", or "Backend detected fraud" are ever evaluated — the Orb declares `success = true` and proceeds to `report_signup_reason`/`debug_report.signup_successful()` based purely on the local pipeline outcome. This mirrors the 0x issue precisely: a pre-check (local `signup_reason`) is treated as equivalent to the authoritative validation (`fillOrder`/backend enrollment), but the code paths that can diverge (rounding error / backend duplicate-fraud checks) are undocumented and silently skipped, so the caller can end up in a state that looks "fillable"/"successful" locally while the authoritative system never confirmed it.

Additionally, in the FOSS build, `detect_fraud` unconditionally returns `Ok(false)` because all fraud checks have been removed: [4](#0-3) 

This means for `user_centric_signup` flows, `signup_reason` can essentially only end up `Normal` or `Failure` (pipeline error) — there is no local fraud detection and no backend fraud detection in this branch, so a signup can be marked `Normal`/successful and get persisted to `debug_report.signup_successful()`/reported to UI/analytics with zero server-side fraud or duplicate verification.

### Impact Explanation
A signup can be locally reported and persisted as `Normal`/successful (`debug_report.signup_successful()`, UI "complete signup" flow, `dd_incr!("main.count.signup.result.success.successful_signup")`) without the backend ever confirming: (a) the iris/identity isn't a duplicate of a previous signup, (b) there's no in-flight competing signup for the same identity, and (c) backend-side fraud detection didn't flag the attempt. This is a misattributed/unauthorized-signup class impact: the Orb's local state and telemetry claim a verified unique signup occurred, while the actual uniqueness/fraud gate that the rest of the system relies on (backend `enroll_user`/`signup_poll`) was bypassed entirely for this code path.

### Likelihood Explanation
The `user_centric_signup` flag originates from `orb_qr_link::UserData` returned by the backend `user_status::request` verification step and is not attacker-forged in the sense of bypassing signature checks (it's part of the response tied to `user_data_hash` verification) — but it is a legitimate value in the normal unprivileged self-serve signup flow (self-serve/app-centric signups are an intended product feature), meaning ordinary users go through this branch by design, not as a rare edge case. Because this is the default path for any app-centric ("self-custody"/self-serve) signup, the likelihood that a normal, unprivileged signup flow never triggers backend-side duplicate/fraud verification is high whenever `user_centric_signup` is set — this isn't a rare misconfiguration but a designed code path.

### Recommendation
Document explicitly (and enforce) that `user_centric_signup` locally-determined success is not equivalent to backend-verified enrollment: either (1) always perform a minimal backend round trip (equivalent to `enroll_user`'s duplicate/fraud check) even for user-centric signups before declaring `success`, or (2) if this bypass is intentional (backend performs deduplication asynchronously via the uploaded PCP), clearly document in-code and in the protocol/spec that `debug_report.signup_successful()` in this branch does **not** imply backend fraud/duplicate confirmation, and gate any downstream trust decisions (analytics reported as "verified", UI success feedback implying identity uniqueness) accordingly.

### Proof of Concept
1. Complete a self-serve/app-centric signup flow where the backend's `user_status::request` response sets `authenticated_app_data.user_centric_signup = true` (this is a normal supported flow for self-custody apps, not privileged access).
2. Ensure the biometric pipeline succeeds (`pipeline.is_some()`), which is achievable by any unprivileged user completing a normal capture.
3. Because `detect_fraud` in the FOSS build always returns `false` (`src/plans/mod.rs:1392-1406`), `signup_reason` becomes `SignupReason::Normal`.
4. In `do_signup`, since `user_centric_signup && !ignore_user_centric_signups`, `success = (signup_reason == SignupReason::Normal) = true` is computed at `src/plans/mod.rs:639-645` — `enroll_user` (and therefore `signup_post::request` + `signup_poll::request`, the only backend duplicate/fraud gate) is never called.
5. `debug_report.signup_successful()` is triggered and the signup is reported as successfully completed, even though the backend never confirmed the identity wasn't a duplicate or fraudulent — demonstrating that the local outcome and the authoritative backend outcome are decoupled without any documented safeguard, analogous to the `getOrderInfo`/`fillOrder` divergence in the original report.
