Position NFT seller can front-run a secondary-market sale and withdraw or borrow out the account's value before the buyer receives it - (File: contracts/position-nft/README.md, contracts/controller/src/positions/supply.rs)

### Summary
A position NFT on XOXNO Lending carries the full lending account — all supply collateral and all debt. Because ownership is resolved live through `owner_of` and nothing locks an account while its NFT is listed or approved to a marketplace, a malicious seller can front-run the buyer's purchase transaction and strip the position: withdraw all collateral (`withdraw` with amount `0` means withdraw-all) and/or max out borrows against it. The buyer's `transfer_from` still executes, delivering an emptied or max-leveraged account at an inflated price — the same honeypot shape as `FootiumAcademy::mintPlayer` claims before a club sale. [1](#0-0) [2](#0-1) 

### Finding Description
Every controller account is one NFT (`account_id == token_id`), and "transferring the token transfers the whole position… collateral and debt both move with the token" [3](#0-2) . The controller resolves ownership on every call via the NFT's `owner_of`, never caching it [4](#0-3) . `process_withdraw` requires only owner-or-delegate authorization, maps a zero amount to `WITHDRAW_ALL_SENTINEL` (withdraw-all), and pays any `to` recipient — so up to the exact ledger the transfer lands, the seller retains full power to drain the account's collateral to themselves [5](#0-4) [6](#0-5) . There is no sale hook, escrow, or timelock that freezes position mutations while an NFT approval for a marketplace is outstanding; `approve`/`transfer_from` are plain OpenZeppelin entrypoints the controller is unaware of [7](#0-6) .

### Impact Explanation
Theft of user funds: the buyer pays the agreed price expecting the collateralized position observed via `get_collateral_amount`/marketplace metadata, but receives an account with collateral withdrawn (or debt maxed against it). On a marketplace-style sale this is a pure rug — the buyer's payment is gone and the NFT is worth a fraction of the price. [1](#0-0) 

### Likelihood Explanation
Medium: it requires a secondary-market sale priced off collateral rather than an atomic bundled check, and an owner willing to front-run. Any unprivileged seller can execute it with one `withdraw` (or `borrow`) call — no privileged access, no oracle manipulation, no timing exoticism beyond submitting before the buyer's transaction. [8](#0-7) 

### Recommendation
Document for integrators that position value must be verified atomically with the transfer (e.g., a marketplace contract that re-reads `get_account_positions`/health in the same transaction as `transfer_from`, or a commit-reveal lock). Alternatively, add a controller-level "sale lock" flag the owner can set that blocks `withdraw`, `borrow`, and strategy mutations until the NFT moves — mirroring the report's timelock recommendation. [9](#0-8) 

### Proof of Concept
1. Alice supplies 10,000 USDC to `account_id = 7` (`supply(caller=alice, account_id=0, ...)`), creating NFT token 7.
2. Alice lists NFT 7 on a secondary market, priced to include the 10,000 USDC collateral, and `approve`s the marketplace contract.
3. Bob submits the marketplace purchase transaction (payment + `transfer_from(spender=market, from=alice, to=bob, token_id=7)`).
4. Alice observes Bob's transaction and front-runs it with `withdraw(caller=alice, account_id=7, withdrawals=[(hub_asset(usdc), 0)], to=Some(alice))` — the zero leg resolves to `WITHDRAW_ALL_SENTINEL` and pays out the full collateral; `require_owner_or_delegate` still passes because Alice remains `owner_of(7)` until the transfer [10](#0-9) [6](#0-5) .
5. Bob's transaction executes: NFT 7 transfers to Bob, whose account now holds zero supply positions. Alice keeps both the sale proceeds and the 10,000 USDC.
   Variant: Alice instead calls `borrow` up to the LTV limit, leaving Bob an underwater/near-liquidatable account.

```markdown
Per-token `Owner` entries renew on two schedules. Any read through `owner_of`
extends `Owner(token_id)` to the OpenZeppelin default of 30 days. `mint` and
`renew(token_id)` extend `Owner(token_id)` and the holder's `Balance` entry with
`TTL_THRESHOLD_USER` and `TTL_BUMP_USER`, a 120-day bump matching the
controller's own per-user entries. Neither call extends the enumeration
entries. `renew` requires no authorization: extending a lifetime moves no
state, cannot shorten a lifetime, and cannot move or approve a token.

If `Owner(token_id)` archives, `owner_of` no longer resolves until the entry is
restored. A caller that simulates the transaction and then submits it is not
blocked — the simulation returns the archived entry ids and the submitted
operation restores them in line, at the cost of restore rent. Liquidation
therefore still succeeds against a lapsed `Owner` entry. Only a caller that
hand-builds a footprint without simulating needs an explicit `RestoreFootprint`.
A call to the permissionless `renew(token_id)` before expiry prevents the
archival. This asymmetry is recorded as INV-STOR-02 in
[`docs/reference/invariants.md`](../../docs/reference/invariants.md).
```

```rust
pub(crate) fn process_withdraw(
    env: &Env,
    caller: &Address,
    account_id: u64,
    withdrawals: &Vec<HubPayment>,
    to: Option<Address>,
) -> Vec<HubPayment> {
    validation::require_authorized_caller(env, caller);

    let mut account = storage::get_account(env, account_id);
    require_owner_or_delegate(env, account_id, caller, &account.owner);

    let recipient = to.unwrap_or_else(|| caller.clone());
    let mut cache = Context::new(env);
    require_external_recipient(env, &mut cache, &recipient);
    let aggregated = payments::aggregate_payments(env, withdrawals, payments::ZeroLeg::MeansAll);

    let paid = settle_withdraw(env, &mut account, &recipient, &aggregated, &mut cache);
```
