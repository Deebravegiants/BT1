### Title
Stale delegate grant re-arms when a position NFT returns to its original owner, letting a former delegate drain the account - (File: contracts/controller/src/storage/account.rs)

### Summary
The follow-redirects bug class is a credential that should be scoped to one trust domain surviving a transition to another domain. In XOXNO Lending, the direct analog is the controller's `DelegateGrant`: a stored position-manager authorization keyed to a `granted_by` snapshot. Unlike every other authority layer (per-token NFT approval, `approve_for_all`, in-flight controller auth), the delegate grant is **not** cleared on NFT transfer — it merely goes dormant and re-activates if the token ever returns to the recorded `granted_by` address. A stale "credential" thus crosses an ownership boundary it should have been severed at.

### Finding Description
Per-token NFT approvals are cleared on transfer (`get_approved` returns `None` after `transfer_from`, pinned by `contracts/position-nft/src/test.rs` lines 136-158), and `permissionless_entrypoints.txt` states "the transfer clears the token approval". The controller's delegate mechanism deliberately diverges: `get_delegates` returns an empty list only because `granted_by` no longer equals the current NFT owner, while "the stale grant stays in storage and re-arms if the token returns to `granted_by`" [1](#0-0) . The deactivation is a read-time comparison in `contracts/controller/src/storage/account.rs`, not a deletion — nothing scrubs the grant at the boundary.

Because owner checks are resolved live via `owner_of` and delegates are checked against stored `granted_by`, an account's authority set silently changes the moment ownership flips back — with no `add_delegate` transaction and no signature from the new-epoch owner. The grant was authorized under ownership epoch N; it executes under epoch N+2 without fresh consent, exactly like `Proxy-Authorization` surviving a cross-domain redirect.

### Impact Explanation
Theft of user funds by an unprivileged address. A former delegate can call `withdraw`, `borrow`, `transfer`-triggering flows, or receive `SeizeMode::Credit` legs on any account the victim later reacquires, without any authorization from the victim in the new ownership epoch. Concrete sequence: attacker obtains a delegate grant on Alice's account (legitimately, e.g., as a keeper/manager, or via social engineering); Alice transfers the position NFT (sale, collateral move, marketplace listing, or even a transfer the attacker arranges); a third party later returns the token to Alice's address — including a different, freshly-funded account state. The dormant grant re-arms instantly; the attacker withdraws collateral or takes out debt against it and extracts value before Alice notices, since Alice never re-granted.

The asymmetry is the bug: a user who checks `get_delegates` post-transfer sees an empty list and reasonably concludes all delegated authority ended — the standard NFT semantic the sibling `approve` mechanism honors. The hidden re-arm makes that guarantee false.

### Likelihood Explanation
Medium. It requires (a) the victim to have granted a delegate at some point and (b) the token to return to `granted_by` while the attacker still monitors. Both are plausible in ordinary use: positions are transferable collateral (marketplace trades, OTC sales with buy-back, treasury reshuffles between a user's own addresses where an old manager grant exists), and delegate grants have no expiry and persist indefinitely in storage. No privileged role, price manipulation, or oracle assumption is needed; the attacker only submits `position-nft::transfer` (to arrange the return leg where feasible) and standard `controller::withdraw`/`borrow` calls.

### Recommendation
Invalidate delegate grants on ownership change rather than dormantly snapshotting `granted_by`:
- Store an ownership epoch or the current owner in `DelegateGrant` and treat the grant as permanently dead once mismatched — i.e., delete or tombstone grants when the NFT transfer hooks (or first post-transfer controller touch) detect `granted_by != owner`, instead of allowing re-arm.
- Alternatively, require `add_delegate` to re-stamp after any intervening `owner_of` change, so returning ownership can never resurrect authority granted under a prior epoch.
- Short of a code change, document prominently that selling/transferring a position NFT does not permanently revoke delegates, and add a `remove_delegate`-on-transfer off-chain keeper — though this does not close the atomicity gap.

### Proof of Concept
1. Alice owns account `A` (token id `T`) with collateral. Alice calls `add_delegate(account_id=T, delegate=Bob)`.
2. Alice transfers NFT `T` to Carol: `position-nft.transfer(from=Alice, to=Carol, token_id=T)`. `get_delegates(T)` now returns empty — Carol's epoch, grant dormant.
3. Carol funds/refreshes the account, then later transfers `T` back to Alice (buy-back, gift return, or Alice repurchases the position on a marketplace). No delegate transaction occurs.
4. `get_delegates(T)` still shows empty or shows Bob — either way the controller's authorization check `granted_by == owner` passes again because `granted_by` is still `Alice` in storage [1](#0-0) .
5. Bob calls `controller::withdraw(caller=Bob, account_id=T, withdrawals=[collateral], to=Bob)`. The delegate path authorizes Bob despite Alice never consenting in the current ownership epoch; Bob receives the collateral.

Note: the dormant-then-rearm behavior is documented in the position-nft README; if reviewers classify this as an accepted ADR choice rather than an oversight of the approve/transfer clearing invariant, the finding downgrades to informational. The security-relevant asymmetry — one authority layer surviving a boundary that clears every other authority layer — is nonetheless directly analogous to the `Proxy-Authorization` leak and reaches an unprivileged attacker path.
