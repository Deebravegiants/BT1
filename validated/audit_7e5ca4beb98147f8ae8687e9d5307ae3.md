### Title
Unchecked TRC20/ERC20 `transfer` return value in `IntentGatewayV2.withdraw()` allows silent escrow-release failure - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` releases escrowed input tokens and protocol fees to solvers/beneficiaries via a raw low-level `.call()` to the token's `transfer` function, checking only the call's `success` boolean and never inspecting the ABI-decoded return value. Tokens that return `false` on failure instead of reverting (a documented, common ERC20/TRC20 pattern) will make this check pass even though no tokens moved, while the contract's internal escrow accounting is unconditionally decremented as if the transfer succeeded.

### Finding Description
In `withdraw()`, escrowed tokens and fees are released with:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) 

`success` here only reflects whether the external call reverted, not whether the token's own `transfer` logic returned `true`. For non-compliant/non-reverting tokens (the "return false on failure" class described in the report, e.g. ZRX-style tokens, and common among TRC20 tokens on Tron), a failed transfer returns `abi.encode(false)` while `success` is still `true`. The code then proceeds to decrement escrow:
```solidity
_orders[body.commitment][token] -= amount;
``` [2](#0-1) 
and marks the order filled/refunded, emitting `EscrowReleased`/`EscrowRefunded`, even though the beneficiary never received the tokens.

The same pattern recurs for the transaction-fee payout in the same function: [3](#0-2) 

and in the `SweepDust` branch of `onAccept`: [4](#0-3) 

Notably, the contract already imports and uses `SafeERC20` (`using SafeERC20 for IERC20;`) for inbound transfers such as `safeTransferFrom` elsewhere in the codebase (e.g., `evm/src/apps/IntentGatewayV2.sol` and `evm/src/apps/intentsv2/IntentsBase.sol` use `safeTransfer`/`safeTransferFrom` consistently for both directions) [5](#0-4) [6](#0-5) , but the Tron variant's outbound token payouts (`withdraw` and `SweepDust`) deliberately bypass `SafeERC20` and use raw low-level calls that check only call success, exposing exactly the return-value-checking gap the external report describes.

### Impact Explanation
`withdraw()` is invoked from `onAccept()` when a relayer delivers a `RedeemEscrow`/`RefundEscrow` cross-chain message from the destination chain, and from `onGetResponse()` for cancellation refunds — both are unprivileged, relayer-driven paths triggered by ordinary solver/user intent activity, not admin actions. If the escrowed input token on Tron is one that returns `false` rather than reverting on failure (e.g., due to insufficient contract-held balance edge cases, blacklist/pausable TRC20 tokens, or other non-standard implementations), the solver/beneficiary receives no tokens, yet:
- The escrow balance is decremented (`_orders[...][token] -= amount`), permanently freezing/losing the user's or solver's claim to those funds — they cannot be re-claimed since the accounting says they were already paid out.
- The order is marked filled/refunded (`_filled[commitment] = beneficiary`), so it can never be retried or reconciled.

This is a direct path to permanent loss of escrowed user/solver funds without recourse, matching the "concrete theft or permanent freezing of funds" criterion.

### Likelihood Explanation
Likelihood depends on encountering a non-reverting-on-failure token among the tokens configured for escrow on the Tron deployment. Such token behavior is common enough among ERC20/TRC20-style tokens (this is precisely the ERC20 ambiguity the original report highlights) that any token integrated into the Intent Gateway on Tron with this property, or one that develops such a code path (e.g., a pausable/blacklisting token that returns false instead of reverting for a blacklisted beneficiary), triggers this on every relayed settlement — a normal, permissionless part of the intent-fill lifecycle, not a privileged or attacker-only trigger.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` (both the token loop and the fee payout) and in the `SweepDust` branch of `onAccept()` with `SafeERC20.safeTransfer`, consistent with the rest of the codebase (which already imports `SafeERC20` in this file). `safeTransfer` correctly reverts on both a failing low-level call and a call that succeeds but returns `false` (or returns no data, per the EIP-20 ambiguity), ensuring escrow accounting is never decremented unless tokens actually moved.

### Proof of Concept
1. Deploy/configure `IntentGatewayV2` (Tron variant) with an input token `T` whose `transfer()` implementation returns `false` on failure instead of reverting (e.g., a blacklist-style TRC20 where a blacklisted beneficiary address causes `transfer` to return `false`).
2. A user places a cross-chain order escrowing `T` as input; a solver fills it on the destination chain.
3. Hyperbridge relays the `RedeemEscrow` message; `onAccept` calls `withdraw(body, false)`.
4. Suppose the intended beneficiary (solver) address is later blacklisted by token `T`, or `T`'s `transfer` returns `false` under some contract-specific condition (e.g., paused state) instead of reverting.
5. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `(true, abi.encode(false))` — the low-level call succeeds even though the transfer failed.
6. `success` is `true`, so the code proceeds: `_orders[body.commitment][token] -= amount;` and the order is finalized (`_filled[commitment] = beneficiary`, `EscrowReleased` emitted) — but the beneficiary never received the `T` tokens, which remain stuck in the contract with no accounting path to reclaim them.
