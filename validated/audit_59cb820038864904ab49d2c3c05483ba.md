## Finding: Silent payout failure in `pallet-bounties::claim_bounty` permanently strands the bounty reward

The Sherlock report's root cause — a critical state-finalizing operation (`cancel()`) that unconditionally pushes tokens to a recipient and then commits an irreversible state change, ignoring the possibility that the transfer itself fails — has a direct structural analog in `pallet-bounties`.

### Title
Unchecked payout transfers in `claim_bounty()` allow permanent, irrecoverable loss of bounty funds - (File: `substrate/frame/bounties/src/lib.rs`)

### Summary
`claim_bounty()` deletes the on-chain bounty record and emits a "success" event *before/regardless of* whether the underlying `Currency::transfer` calls to the curator and beneficiary actually succeeded. The only safety net is `debug_assert!(res.is_ok())`, which is compiled to a no-op in release/production builds.

### Finding Description [1](#0-0) 

In `claim_bounty`, the pallet computes `final_fee` (curator payout) and `payout` (beneficiary payout) and calls:
```rust
let res = T::Currency::transfer(&bounty_account, &curator, final_fee, AllowDeath); // should not fail
debug_assert!(res.is_ok());
let res = T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath); // should not fail
debug_assert!(res.is_ok());
*maybe_bounty = None;
```
`debug_assert!` only panics in debug builds; production runtimes are compiled in release mode, so a `Err` return from either `transfer` call is silently discarded. Immediately after, `*maybe_bounty = None` deletes the bounty from storage and a `BountyClaimed` event is emitted as if the payout succeeded — this mirrors the `remainingBalance = 0` state-zeroing in the Sherlock report that happens regardless of transfer outcome.

A native `Currency::transfer` to a beneficiary/curator can genuinely fail (independent of any "blacklist" primitive) whenever the destination account does not yet exist and the transferred amount is below the existential deposit — this is standard `pallet-balances` behavior. `BountyValueMinimum` only bounds the *total* bounty `value` at `propose_bounty` time [2](#0-1) ; it does not bound `payout = value - fee` nor `final_fee` individually. Since `fee` is set independently via `propose_curator` (only constrained by `fee < bounty.value`) [3](#0-2) , and the beneficiary is freely chosen by the curator at `award_bounty` time, it is straightforward to construct a scenario where either `payout` or `final_fee` ends up smaller than the chain's existential deposit for a not-yet-existing account.

### Impact Explanation
When either transfer silently fails, the corresponding balance remains stuck in the module-owned `bounty_account_id(bounty_id)`. Because the bounty entry is deleted from `Bounties` storage in the same call, there is no remaining pointer/mechanism (no analogous "reclaim" path tied to a deleted bounty id — the existing `BountyFundsReclaimed` event only applies to funds left behind after `close_bounty`) to recover these funds. This results in permanent, irrecoverable loss of treasury/bounty funds — a strictly worse outcome than the referenced report's temporary DoS on `cancel()`.

### Likelihood Explanation
`claim_bounty` is intentionally permissionless ("anyone can trigger claim") [4](#0-3) , so the failure-triggering conditions (dust `fee`/`payout` values combined with a fresh destination account) only need to exist once for the loss to be locked in permanently — the fee and beneficiary values are set through the normal curator workflow (`propose_curator`, `award_bounty`) rather than requiring a privileged bypass, so this is reachable without exploiting any explicitly trusted-only code path.

### Recommendation
Replace the `debug_assert!`-guarded transfers with actual error propagation: either use `?`/`try_mutate` semantics so a failed transfer aborts the whole `claim_bounty` call (leaving the bounty claimable/retryable later, similar to the `PaymentState`/`retry_payment` pattern already used in `pallet-multi-asset-bounties`), or capture the residual balance before clearing storage and expose a follow-up extrinsic (analogous to `BountyFundsReclaimed`) that lets it be swept back to the treasury or reattempted by the intended recipient.

### Proof of Concept
1. Governance approves a bounty with `value` and, through `propose_curator`, sets `fee` such that `payout = value - fee` is smaller than `T::Currency::minimum_balance()`.
2. Curator accepts and calls `award_bounty` with a `beneficiary` account address that has never been used on-chain (no existential deposit, does not exist in `frame_system::Account`).
3. `claim_bounty` is called (by anyone). `T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath)` returns `Err(TokenError::ExistentialDeposit-like error)` because creating the destination account requires at least the ED.
4. In a release build, `debug_assert!(res.is_ok())` is a no-op; execution continues, `*maybe_bounty = None` deletes the bounty, and `Event::BountyClaimed` fires.
5. The `payout` amount remains stranded in `bounty_account_id(bounty_id)` with no bounty record referencing it — funds are permanently lost.
