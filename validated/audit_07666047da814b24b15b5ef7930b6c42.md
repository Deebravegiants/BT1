### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant spoofing via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` fields are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts these header-derived fields to build `WebhookMetadata`, which is handed to the app's handler as the tenant identifier. This breaks the intended binding: `hmac(raw_body) == valid` should imply `shop == the shop that produced raw_body`, but the gem's design only verifies `hmac(raw_body)`, not `hmac(raw_body, shop)`.

### Finding Description
`Request#hmac` and `Request#to_signable_string` bind only the raw body to the signature: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from headers, which are not part of `to_signable_string`: [2](#0-1) 

`Registry.process` validates only the HMAC of the request (i.e., of the body) and then immediately trusts `request.shop`, `request.topic`, etc., to construct `WebhookMetadata`, which is dispatched to the app-defined handler as the authoritative tenant/topic identity: [3](#0-2) 

`WebhookMetadata.shop` is a plain, unauthenticated `String` field: [4](#0-3) 

Because the HMAC only binds `raw_body`, the equality the gem is supposed to guarantee — `verified(hmac) ⇒ shop_header == originating_shop` — does not hold. An attacker who can capture one legitimate, validly-signed webhook body/HMAC pair (e.g. from their own store, which they legitimately receive as the store owner) can replay that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary value in the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header. `HmacValidator.validate` will still succeed because it only recomputes and compares the HMAC of `raw_body`: [5](#0-4) 

The handler then receives `WebhookMetadata` claiming to be from the victim shop, with attacker-chosen `body` content (from the original captured payload) attributed to that shop. This is directly analogous to the reported bug class: a value that participates in an important state decision (rebalance token/shop identity) is not the value actually covered by the cryptographic/consistency check that is supposed to protect it — "bytes verified" (raw body) diverges from "bytes trusted for identity" (shop header).

### Impact Explanation
This is a cross-tenant identity confusion: an app that dispatches per-shop side effects from a webhook handler based on `data.shop` (e.g., updating that shop's stored order/customer/product records, deleting local data on `shop/redact`, or triggering shop-scoped business logic) can be made to attribute an attacker-controlled webhook body to an arbitrary target shop domain, without needing that shop's access token or any credential belonging to the app. This matches the "cross-tenant access" criteria for Critical impact, since it lets an unprivileged party (anyone who can obtain one valid signed webhook, e.g. for their own shop) inject data attributed to a different, victim shop into the receiving application's webhook-processing logic.

### Likelihood Explanation
Likelihood is constrained by the fact that the attacker must first obtain at least one genuinely-signed webhook body+HMAC pair — which they can do trivially for their own store (any Shopify merchant can install the app and trigger a webhook to capture a valid `(body, hmac)` pair) — and then can freely resend that exact `(body, hmac)` while forging the shop/topic/webhook-id headers, since those are never covered by the signature. No knowledge of `api_secret_key` or any merchant's access token is required. The main variable is whether the consuming application relies on `data.shop` (rather than independently re-deriving the shop, e.g. from GraphQL admin API calls using their own stored token) to make trust decisions — which is the exact usage pattern the gem's `WebhookMetadata` API encourages.

### Recommendation
- **Short term:** Change `Request#to_signable_string` (or the HMAC validation call site in `Registry.process`) to include `shop`, `topic`, `webhook_id`, and `api_version` in the signed material, or otherwise document/require that consuming apps must independently corroborate `WebhookMetadata.shop` against their own database (e.g. verifying they registered a webhook for that shop) before trusting it for tenant-scoped operations.
- **Long term:** Since Shopify's actual HMAC computation (server-side) never included headers, an in-gem fix isn't fully possible without protocol support; the gem should at minimum document this trust boundary explicitly and encourage validating `webhook_id` uniqueness/idempotency plus a webhook-existence check against the Admin API for the claimed shop before acting on high-privilege operations (e.g., mandatory redact topics).

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own shop ("attacker-shop.myshopify.com")
#    and captures a legitimately-signed webhook delivered to their endpoint:
raw_body     = '{"id":123,"note":"malicious payload"}'
valid_hmac   = <captured "X-Shopify-Hmac-Sha256" header value, valid for raw_body>

# 2. Attacker replays the exact same body+hmac to the target app's webhook endpoint,
#    but swaps the shop-domain header to the victim's shop:
headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => valid_hmac,      # still validates raw_body!
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged, not covered by HMAC
  "x-shopify-webhook-id"   => "attacker-chosen-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true (body HMAC matches),
#    handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
#    is invoked with attacker-controlled body attributed to the victim shop.
```
