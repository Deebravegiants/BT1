### Title
Permanent freeze of escrowed native-token refunds when beneficiary cannot accept ETH - (File: evm/tron/contracts/apps/IntentGatewayV2.sol / evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
The Tron `IntentGatewayV2.withdraw()` function (and the analogous `_withdraw`/`_sendValue` path in the EVM `IntentsBase.sol`) releases escrowed native-token (ETH) order inputs to a `beneficiary` using a low-level `.call{value: amount}("")`, and **reverts the entire withdrawal** if the call fails: `if (!sent) revert InsufficientNativeToken();` [1](#0-0) . This mirrors the L1ScrollMessenger `dropMessage`/`onDropMessage` bug class: a refund path that is gated on a successful callback/transfer to an address chosen by the user (or a peer gateway message), with no fallback mechanism if that address cannot receive value.

### Finding Description
`withdraw()` is invoked from two permissionless, message-driven entry points:
- `onAccept()` for `RedeemEscrow`/`RefundEscrow` requests delivered via ISMP `onAccept` [2](#0-1) 
- `onGetResponse()` for the source-chain cancellation flow, which decodes a `WithdrawalRequest` from the GET-response context and calls `withdraw(body, true)` [3](#0-2) 

Inside `withdraw()`, for native-token (`token == address(0)`) legs, funds are pushed via `.call{value: amount}("")`; if the push fails, the function reverts with `InsufficientNativeToken()` rather than skipping/queuing the transfer [4](#0-3) . The `beneficiary` for this path is `order.user` (chosen by the order creator at `placeOrder` time) or the solver for redemption — an address that the protocol does not control and cannot verify can accept a plain ETH transfer. The same pattern exists in the EVM version's `_sendValue`, used from `_withdraw` in `IntentsBase.sol` [5](#0-4) .

Unlike `EvmHost.dispatchTimeOut`, which explicitly re-stores the request/fee commitment on callback failure so the message can be retried later [6](#0-5) , and unlike `pallet-ismp`'s timeout handler, which restores the commitment for retry when the module callback errors [7](#0-6) , the intent-gateway `withdraw()`/`onGetResponse()`/`onAccept()` path has no such retry-with-different-beneficiary or pull-based fallback. If the `beneficiary`/`order.user` address is a contract without a payable `receive`/`fallback` (or one that reverts on receiving native value, or one that runs out of gas due to the 2300-gas stipend-like constraints of a plain call — though here it's a full-gas `.call`), then:
- Every future submission of the `RefundEscrow`/`RedeemEscrow` POST request or the cancellation GET response for that exact commitment will revert identically, since the beneficiary and amount are fixed by the already-signed `Order`/`WithdrawalRequest`.
- There is no code path to change the beneficiary or fall back to an ERC20-wrapped/pull-based transfer (contrast with `WrappedHyperFungibleToken.onPostRequestTimeout`, which explicitly re-wraps to WETH and does a safe ERC20 transfer if the native push fails [8](#0-7) ).
- Because the outer message delivery itself reverts, the underlying ISMP request/response commitment is never consumed, so this becomes a permanently un-deliverable message for that specific commitment — the escrowed native ETH is locked in the `IntentGatewayV2` contract indefinitely.

### Impact Explanation
Any user who places a cross-chain (or GET-response-cancelled) order with native ETH input, using a smart-contract wallet, multisig, or intent-solver contract as `order.user`/beneficiary that cannot accept a raw ETH `call`, will have that escrowed ETH permanently frozen once a refund or redemption is attempted, since the delivery transaction that would release the funds can never succeed. This is a permanent freezing-of-funds condition (High severity under the accepted "concrete theft or permanent freezing of funds" bar), scoped strictly to the native-ETH leg of orders.

### Likelihood Explanation
Medium-High likelihood: any smart contract wallet (e.g., a Gnosis Safe without a receive function configured correctly, an intents-based solver contract, or a vault contract) used as the order beneficiary would trigger this. Given the intent-gateway explicitly supports composable/solver contracts and calldata-driven flows (predispatch/postdispatch `Call[]` execution), it is realistic that a `beneficiary` is a contract rather than an EOA. No malicious actor or privileged role is required — this is triggerable by any regular user simply by using a non-payable contract as `order.user` for a native-ETH order and later needing a refund/cancellation.

### Recommendation
For native-token legs in `withdraw()` (Tron `IntentGatewayV2.sol`) and `_withdraw`/`_sendValue` (EVM `IntentsBase.sol`), do not revert the entire settlement/refund on a failed native push. Instead:
- Fall back to a pull-based accounting model (credit an internal balance the beneficiary can withdraw later), or
- Wrap the native asset (e.g., WETH) and deliver it as an ERC20 transfer if the raw push fails, mirroring the pattern already used in `WrappedHyperFungibleToken.onPostRequestTimeout`.

### Proof of Concept
1. Deploy a `RefundableBeneficiary` contract with no `receive()`/`fallback()` (or one that always reverts).
2. Call `placeOrder()` on `IntentGatewayV2` (Tron) with a native-ETH input leg (`token == address(0)`) and `order.user` set to `RefundableBeneficiary`'s address.
3. Trigger the cancellation flow: either `cancelOrder()` from the destination chain (dispatching `RefundEscrow` back through `onAccept`) or from the source chain via `onGetResponse` after the order deadline passes unfilled.
4. Observe that `withdraw()` reaches the native branch, `beneficiary.call{value: amount}("")` returns `false`, and the function reverts with `InsufficientNativeToken()`.
5. Confirm that resubmitting the exact same ISMP message/proof always reverts identically, and there is no alternate function to redirect or pull the escrowed ETH — it remains locked in the `IntentGatewayV2` contract balance indefinitely.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
