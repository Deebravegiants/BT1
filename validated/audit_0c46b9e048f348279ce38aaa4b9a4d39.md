### Title
Webhook `shop` (and `topic`/`webhook-id`) identity fields are not covered by the HMAC, enabling cross-tenant webhook data replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` accepts a webhook only if `Utils::HmacValidator.validate(request)` succeeds, but the HMAC is computed solely over `request.to_signable_string`, which returns only the raw request body. The `shop-domain`, `topic`, `api-version`, and `webhook-id` values — all read straight from unauthenticated HTTP headers — are never included in the signed material, yet they are the exact fields the library hands to the app's handler to identify *which tenant* the payload belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are pulled directly from HTTP headers with no cryptographic binding to the HMAC digest: [2](#0-1) 

`HmacValidator.validate` computes the digest purely from `verifiable_query.to_signable_string` (the body) and compares it against the `hmac-sha256` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as authorization to dispatch `request.shop` (the unauthenticated header) straight to the app's handler as the tenant identity: [4](#0-3) 

The broken identity binding, stated as an equality that the code assumes but never enforces:
`HMAC_valid(body) == true` is treated as implying `shop_header == shop_that_Shopify_actually_signed_this_body_for`, but the signature never covers `shop_header`. Because every shop that installs the app shares the exact same public webhook receiver URL, and because the app's `api_secret_key` (used to compute the digest) is identical across all tenants, any `(body, hmac)` pair that was legitimately generated for Tenant A's data is a **valid HMAC pair regardless of which shop header accompanies it**. An unprivileged attacker who is themselves a legitimate merchant installing the app on their own store (a normal, unprivileged action any internet user can perform) will receive real webhook deliveries with valid `(body, hmac)` pairs for their own shop. They can then replay that exact body/HMAC to the app's shared webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim tenant's domain. `HmacValidator.validate` still returns `true` (it never looked at the header), and `Registry.process` forwards `WebhookMetadata.new(... shop: request.shop ...)` — the attacker-chosen victim domain — to the handler, which will process/store attacker-supplied data as if it originated from the victim's shop.

### Impact Explanation
This breaks the tenant boundary the whole HMAC check exists to enforce: passing HMAC validation is supposed to guarantee the data came from Shopify *for the claimed shop*, but the claimed shop is never authenticated. Any host application that uses `request.shop` (or the `shop` field surfaced via `WebhookMetadata`) to key persistence, deduplication, or business logic will attribute/replay attacker-controlled webhook content to another merchant's tenant — a cross-tenant data injection/corruption primitive, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high: no credentials beyond a free/self-serve app install are required, the webhook endpoint is public by design, all tenants share the identical secret and endpoint, and the only "attack" step is swapping one header value on a replayed HTTP request — no cryptographic material needs to be forged.

### Recommendation
Do not treat header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) as trusted once the HMAC check passes. Either:
1. Include these fields in the signed payload used for HMAC verification (matching what Shopify's servers actually sign), or
2. Require the host application to independently verify that `request.shop` corresponds to a shop with an active installation/session for this app before processing, rather than presenting `Registry.process` as sufficient tenant authentication.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, receiving a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the shared `api_secret_key`), header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker POSTs the same `B` and `H` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`:
   - `validate_signature` recomputes `compute_signature(request.to_signable_string, secret)` = HMAC(`B`, secret) = `H`, matching the attacker-supplied header — validation passes [5](#0-4) .
4. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` is invoked with `shop == "victim.myshopify.com"` [6](#0-5) , causing the host app to process attacker-controlled data under the victim's tenant identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
