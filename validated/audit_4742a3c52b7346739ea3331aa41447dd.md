### Title
Webhook `shop` (tenant identity) is not covered by the HMAC, allowing cross-tenant webhook impersonation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [3](#0-2) , so `Utils::HmacValidator.validate` only proves that *some* body bytes were signed with the app's `client_secret` [4](#0-3) . The tenant identity, `shop`, together with `topic` and `webhook_id`, are read straight from attacker-controllable HTTP headers [5](#0-4)  and are handed directly to the app's handler as trusted, verified data via `Registry.process` [2](#0-1) . Nothing in this gem binds the `shop-domain` header to the signature, so `request.shop` is "verified" only in the sense that the body's bytes matched a valid signature — the identity claim itself is unauthenticated.

### Finding Description
The binding that breaks is: **shop claimed in the `shop-domain` header == shop the HMAC actually authenticates**. In reality the HMAC authenticates only the byte sequence `@raw_body`; it says nothing about which shop/tenant that body belongs to. `Registry.process` trusts `request.shop` (and `request.topic`, `request.webhook_id`) unconditionally as long as `Utils::HmacValidator.validate(request)` passes, and forwards them to the host app's `WebhookHandler#handle` as the authenticated tenant identifier [2](#0-1) [6](#0-5) .

Because every shop installation of a given app shares the same `client_secret`, any merchant who installs the app (an unprivileged internet user with respect to any *other* merchant's data) can:
1. Trigger a legitimate webhook from Shopify to the app for their own shop, choosing a topic/body they control (e.g. by editing a product/order whose JSON fields they set), thereby obtaining a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the shared `client_secret`.
2. Replay that exact `raw_body` + HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) with a victim shop's domain.
3. `Utils::HmacValidator.validate` still succeeds because it only checks `raw_body` against the signature; `Registry.process` then invokes the handler with `WebhookMetadata.shop` set to the victim shop, causing the host app to process/store attacker-supplied data under the victim tenant's identity.

This is the same class of defect as the M-5 report: a value that is *acted upon* (there, the oracle price; here, the tenant/shop identity) is validated against the wrong thing (there, only `price > 0`; here, only "is `raw_body` HMAC-valid") instead of the actual binding that matters (price within Chainlink's min/max band; shop bound into the signed payload).

### Impact Explanation
This crosses a tenant boundary: data belonging to shop B can be forged/attributed by an attacker who only controls shop A's installation of the same app, without ever obtaining shop B's access token or the app's `client_secret`. Depending on the handler's logic (e.g. `app/uninstalled`, `shop/redact`, `orders/create`, billing/subscription topics), this can lead to unauthorized data being written into, or destructive actions being taken against, a completely unrelated merchant's tenant record — a cross-tenant access impact.

### Likelihood Explanation
Any developer/merchant who can install the app (no special privilege beyond being a Shopify merchant) can generate a valid signed webhook body for their own shop and then freely spoof the header fields when replaying it to the app's public webhook endpoint, since nothing in this gem ties `shop-domain` (or `topic`/`webhook-id`) to the signature. No secrets, tokens, or credentials belonging to the victim are required.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC validation, or otherwise cryptographically bind the header claims to the signed payload before trusting them in `WebhookMetadata`. At minimum, document that `WebhookMetadata#shop`/`topic`/`webhook_id` are unauthenticated and must not be trusted as tenant identifiers without additional server-side verification (e.g. cross-checking against the shop stored for the session that registered the webhook).

### Proof of Concept
```ruby
# Attacker owns shop-a.myshopify.com (installed the same app).
# Step 1: capture a legitimate webhook Shopify sent for shop-a with body they crafted, e.g. "{}"
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), Context.api_secret_key, "{}")
valid_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "shop-a.myshopify.com",
}

# Step 2: replay same body+hmac, but claim it's for the victim shop
forged_headers = valid_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: "{}", headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) still succeeds (only raw_body is signed),
#    handler.handle(data: WebhookMetadata) is called with shop == "victim-shop.myshopify.com"
```
