### Title
Webhook Shop Domain Not Covered by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` attribute consumed by handlers is read from an unauthenticated header. An attacker who can obtain one valid `(body, HMAC)` pair for their own shop can replay it with a forged `shop-domain` header to make the app attribute the payload to a different, victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is pulled straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header without any cryptographic binding to the HMAC: [2](#0-1) 

`HmacValidator.validate` only recomputes and compares the HMAC over `to_signable_string` (the body), so it never verifies that the `shop` header is authentic: [3](#0-2) 

`Registry.process` validates the HMAC and then forwards `request.shop` directly into `WebhookMetadata`, which is the tenant identifier handed to the app's business logic: [4](#0-3) 

This breaks the intended identity binding: **shop authenticated by the HMAC ≠ shop attributed to the payload**. Since Shopify's HMAC signing scheme (shared secret over the raw body) does not include the shop domain in the signed material, any body/HMAC pair is valid for that body regardless of which shop header accompanies it. A malicious merchant who has installed the app (a legitimate, unprivileged Shopify user) can:
1. Trigger a webhook for their own shop (e.g., create an order) to legitimately receive a `(body, HMAC)` pair signed with the app's shared secret.
2. Replay that exact body and HMAC to the app's public webhook endpoint, but substitute the `shopify-shop-domain` header with a victim shop's domain.
3. `HmacValidator.validate` succeeds (body and HMAC match), and `Registry.process` calls the handler with `WebhookMetadata(shop: <victim-shop>, ...)`.

The gem provides no mechanism to bind the `shop` header to the HMAC, so any host application built on top of it (using `request.shop` to route data/create records/index sessions, which is the sanctioned intended use per the gem's own `WebhookMetadata` and documentation) will process attacker-controlled data under a foreign tenant's identity.

### Impact Explanation
This is a cross-tenant confusion vulnerability: it lets one merchant (an unprivileged Shopify user) inject arbitrary attacker-chosen webhook payloads that the app will treat as coming from a different shop. Depending on how the host app keys data/state off `WebhookMetadata#shop` (which is the API's documented and expected identifier field for exactly this purpose), this can lead to cross-tenant data corruption or injection of forged data into another merchant's records, satisfying the "cross-tenant access" Critical impact category, since the attacker never needs the victim's or the app's credentials — only a legitimate install of their own.

### Likelihood Explanation
Likelihood is high for any app that exposes a single public webhook endpoint (the standard, documented integration pattern for `ShopifyAPI::Webhooks::Registry.process`). The only capability required is an unprivileged Shopify merchant account that can install the app and trigger any webhook event (e.g., placing a test order), which is trivial and requires no special privileges, secrets, or social engineering.

### Recommendation
Include the `shop` domain (and ideally `webhook-id`/`api-version`) in the signable material used for HMAC verification, or otherwise cryptographically bind the shop identity to the verified payload before it is handed to `WebhookMetadata`/handlers. At minimum, document loudly that `request.shop` is unauthenticated and must not be trusted for tenant attribution without an independent verification step (e.g., cross-checking against an app-side registered webhook-id-to-shop mapping).

### Proof of Concept
1. Install the app on Shop A (attacker-controlled) and trigger any subscribed webhook topic; capture the raw POST body and the `x-shopify-hmac-sha256` header Shopify sends — this is a valid `(body, HMAC)` pair signed with the app's `client_secret`.
2. Replay the exact same body and HMAC header to the app's webhook endpoint, replacing `x-shopify-shop-domain` with Shop B's domain (the victim, also an app installer, or even an arbitrary/nonexistent shop domain string).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks the body: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: <attacker's Shop-A body>, ...)`, causing the host app to process Shop-A's attacker-chosen data as if it originated from Shop B.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
