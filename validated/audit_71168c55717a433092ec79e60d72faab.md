### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook solely by validating the HMAC over the raw request body, but the `shop` (tenant identifier) that is subsequently trusted and dispatched to the host app's handler is taken from an HTTP header that is never included in the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Registry.process` validates the webhook exclusively via `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` to compute the HMAC and compares it against the `hmac` header [2](#0-1) . Meanwhile `Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signed body [3](#0-2) . After HMAC validation succeeds, `request.shop` is passed straight into `WebhookMetadata` and handed to the app's registered handler as the tenant identity for that webhook [4](#0-3) , and `WebhookMetadata.shop` is a plain, unauthenticated `String` field [5](#0-4) .

This breaks the intended identity binding:
`hmac == HMAC(secret, raw_body)` should equal `hmac == HMAC(secret, raw_body ∥ shop)`, but the gem only enforces the former. The `shop` header is a field acted on (used as the tenant key for dispatching to handler logic) but not covered by the HMAC.

Because Shopify signs webhooks with `HMAC-SHA256(secret, raw_body)` and the same body/HMAC pair is valid regardless of which header values accompany it, any party who can capture one legitimate webhook delivery (e.g., by installing the app on their own shop and observing an outbound webhook, or via a shared/relayed body) can resend that exact body + HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. The gem will validate the HMAC (it only checks the body) and hand the forged `shop` value to the host app's handler as if the event genuinely originated from that other shop.

### Impact Explanation
This is a cross-tenant identity binding failure: the value the host application trusts to identify "which merchant this webhook is about" is not authenticated, only the payload bytes are. Any app logic that keys off `WebhookMetadata#shop` (e.g., updating shop-specific state, triggering shop-scoped side effects, looking up/associating data per shop) can be manipulated to apply another shop's legitimately-signed event body under an attacker-chosen shop identity, or apply the attacker's own event body under a different shop's identity if the attacker can obtain any valid (topic, body, hmac) triple for their own shop and merely change the shop header. This matches the "Critical - cross-tenant access" impact category described by the analog rules, since the tenant boundary (shop) enforced downstream is not bound to the same cryptographic proof that authenticates the request.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one valid (raw_body, hmac) pair — trivially obtainable by installing the target app on a shop they control and capturing Shopify's own webhook delivery to that app (no `client_secret` or access token needed, since Shopify computes and sends the HMAC itself). The attacker then only needs to be able to send an HTTP request to the app's public webhook endpoint with a modified `shop-domain` header, which is standard unprivileged internet access. No secrets, tokens, or privileged accounts are required.

### Recommendation
Include the tenant-identifying header(s) (at minimum `shop-domain`, and ideally `webhook-id`/`api-version`) in the signed material that `to_signable_string` returns, or otherwise cryptographically bind them before trusting `request.shop` in `Registry.process`. Since Shopify's actual HMAC only signs the body, the gem should not treat `shop`/`topic`/`webhook_id` header values as authenticated identity fields; instead, if tenant-scoped behavior is required, the host app should be instructed to independently verify that the shop/webhook combination corresponds to a webhook Shopify was actually asked to deliver for that shop (e.g., cross-check against a known/registered shop list, or use the GraphQL webhook ID lookup already present in `Registry.get_webhook_id` to confirm the tuple is legitimate) rather than trusting the header directly for tenant dispatch.

### Proof of Concept
1. App developer installs the app on `attacker-shop.myshopify.com`. Shopify sends a real webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`, `x-shopify-topic: orders/create`
   - Body: `{"id": 1, "amount": 100}`
2. Attacker captures this exact `(raw_body, hmac)` pair (they control the endpoint delivery to their own shop, or intercept it on their own infrastructure).
3. Attacker crafts a new HTTP request to the same app webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` identical, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds the request; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, raw_body)` — unaffected by the header change — and passes validation per `lib/shopify_api/webhooks/registry.rb:190`.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)`, causing the host app to process an order-creation event under the victim shop's identity even though Shopify never sent this event for that shop.
