### Title
Webhook shop/topic/id identity not covered by HMAC allows cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook only by HMAC-verifying the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and process the webhook come from unauthenticated HTTP headers that are never part of the signed payload.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (i.e., the raw body) against the HMAC secret — it never incorporates the shop/topic/webhook_id headers into the signature check: [3](#0-2) 

`Registry.process` then dispatches to the handler using the *unauthenticated* `request.shop`, `request.topic`, and `request.webhook_id` values, having only validated the body's HMAC: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop passed to WebhookMetadata`. Here, the HMAC only authenticates `raw_body`, so any request with a body/HMAC pair captured from one shop's genuine webhook can be replayed to the app's public webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header substituted for a victim shop, and the signature check still passes because that header was never part of the signed content.

### Impact Explanation
A merchant who has installed the app (an unprivileged actor with no access to `api_secret_key`) receives genuine webhook deliveries with valid HMACs for their own shop's data. Because the shop identity header is not covered by the signature, they can replay the exact body+HMAC pair to the app's public webhook endpoint while substituting the `shop-domain` header for a different (victim) shop. Any host application that uses `WebhookMetadata#shop` to scope data writes, cache invalidation, or trigger shop-specific side effects (the documented and intended use of this field) will process attacker-controlled data under a victim tenant's identity — a cross-tenant integrity violation reachable purely from the gem's own webhook-processing logic.

### Likelihood Explanation
Exploitation only requires capturing one legitimately-signed webhook body/HMAC pair (trivial for any merchant with the app installed, since Shopify sends real webhooks to the app's endpoint) and resending it to the same public endpoint with a modified shop header — no secret key, TLS interception, or privileged access needed.

### Recommendation
Include the shop domain (and ideally topic/webhook_id) as part of the HMAC-signed content, or otherwise cryptographically bind the shop identity to the payload before trusting it in `WebhookMetadata`. At minimum, cross-check `request.shop` against a shop-scoped secret or a previously established session/tenant record before dispatching to handlers, rather than trusting the raw header once body-only HMAC validation succeeds.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers a real webhook (e.g., `orders/create`), capturing the raw body and the genuine `X-Shopify-Hmac-Sha256` header Shopify computed for that body.
2. Attacker POSTs the same raw body and HMAC header to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only [5](#0-4)  — it matches, since the body is unchanged.
4. `Registry.process` builds `WebhookMetadata` with `shop: request.shop` = `"victim.myshopify.com"` [6](#0-5)  and invokes the app's handler, which believes this event genuinely originated from the victim shop.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
