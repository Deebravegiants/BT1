## Title
Cross-chain replay of `hyper-fungible-token` calldata-execution signatures due to missing domain separation - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The Keystone advisory (CVE-2025-65073) is a scope-confusion bug: a signature that was only ever meant to authenticate a narrow, purpose-specific flow (`/v3/ec2tokens`/`/v3/s3tokens` AWS Signature validation) was accepted as proof of full Keystone authorization because the verifier never bound the signature to the intended audience/purpose. The `pallet-hyper-fungible-token` calldata-execution path in Hyperbridge has the analogous defect: the signed payload that authorizes a beneficiary's runtime call carries no chain/pallet/purpose binding, so a signature captured from one legitimate cross-chain transfer can be reused to authorize the same runtime call on a completely different destination chain.

### Finding Description
When an incoming `PostRequest` to `pallet-hyper-fungible-token` carries non-empty `data`, it is decoded as `SubstrateCalldata { signature, runtime_call }` [1](#0-0)  and, if a signature is present, verified this way:

```
let nonce = frame_system::Pallet::<T>::account_nonce(beneficiary.clone());
...
let payload = (nonce, substrate_data.runtime_call.clone()).encode();
let msg = sp_io::hashing::keccak_256(&payload);
``` [2](#0-1) 

The signed message is exactly `(account_nonce, runtime_call_bytes)` — nothing else. It does not include:
- the destination `StateMachine` / chain identifier,
- a genesis hash or spec version,
- the source contract/module id, or
- any pallet-specific domain tag.

By contrast, the sibling relayer-fee withdrawal flow in the same codebase *does* bind the destination chain into its signed message, and the test suite explicitly exercises "a signature the relayer would have produced for a different source chain" being replayed and rejected [3](#0-2) , i.e. the codebase's own pattern shows the authors know cross-chain replay must be defended against for this kind of user-provided signature — but that binding was not applied to the HFT calldata path.

Because `pallet-hyper-fungible-token` is meant to be deployed identically (same pallet, same ABI-compatible `Message` struct) on multiple destination substrate chains [4](#0-3) , and the same beneficiary `AccountId` and identically-encoded `runtime_call` bytes (e.g. a common `Balances::transfer_allow_death` call, which parachains built from the same runtime template will encode identically) can legitimately exist on more than one chain, a signature the user produced to authorize a call on chain A's HFT pallet is equally valid on chain B's HFT pallet as long as the nonce coincides (trivially true at `nonce = 0`, or otherwise achievable). The `data` field, and thus the signed payload, is fully public — it is embedded in the cross-chain `Message` body that any indexer/relayer can read off-chain or on-chain.

### Impact Explanation
An attacker who observes a legitimately signed `SubstrateCalldata` (nonce, runtime_call, signature) intended for delivery to one destination chain can initiate their own `send()` on the source chain targeting a *different* destination chain that also runs `pallet-hyper-fungible-token` with the same runtime call encoding, embedding the exact same `data` bytes. On the unintended destination chain, the pallet will accept the identical signature (since it never checked destination/chain binding), dispatch the beneficiary's `runtime_call` there via `RawOrigin::Signed(origin)` [5](#0-4) , and consume that chain's independent nonce. This is an unauthorized app action executed under a victim account's identity on a chain the victim never intended to interact with — matching the "unauthorized app action" and "forged message delivery" impact classes in scope, since consent for one specific delivery context is being treated as consent for an unrelated one.

### Likelihood Explanation
Exploitability requires: (1) the victim's `SubstrateCalldata` signature is visible (guaranteed — it travels in the public cross-chain message body/logs), (2) a second chain running `pallet-hyper-fungible-token` shares the runtime call encoding and the victim's beneficiary account has a matching nonce, and (3) the attacker (any unprivileged relayer/bridger) sends a `send()` with the copied `data` field to that other chain. Given Hyperbridge's explicit multi-chain, shared-runtime deployment model for this pallet, and that `nonce = 0` for a fresh account on every new chain is common, this is realistically reachable by any unprivileged user acting as sender/relayer, without needing any privileged role.

### Recommendation
Bind the signed payload to the specific delivery context before hashing, e.g.:
```
let payload = (T::Version::get() /* or genesis hash */, dest_state_machine, nonce, runtime_call).encode();
```
mirroring the domain separation already used in `pallet-relayer`'s withdrawal message construction, so a signature produced for one chain/pallet instance cannot be replayed on another.

### Proof of Concept
1. On chain A (destination), Alice bridges tokens with `call_data` authorizing `Balances::transfer_allow_death(dest, amount)` signed as `sr25519(keccak256((0u64, runtime_call).encode()))`, exactly as constructed in the existing test `should_receive_asset_with_calldata` [6](#0-5) .
2. Attacker observes this signed `SubstrateCalldata` (public in the `Message.data` field of the delivered request).
3. Attacker triggers/relays an equivalent cross-chain `send()` targeting chain B, which also runs `pallet-hyper-fungible-token` with the identical `RuntimeCall` encoding for `Balances::transfer_allow_death`, and Alice's account nonce on chain B is also `0`.
4. Chain B's `on_accept` verifies the same signature successfully (payload has no chain binding) and dispatches the call as `RawOrigin::Signed(Alice)`, moving Alice's funds on chain B without her consent for that chain.
