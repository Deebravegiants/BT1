### Title
Flash-manipulable reserve ratio used as PnL "price basis" can permanently freeze Deposit/Withdraw/WithdrawPnl - (File: `program/src/processor.rs`)

### Summary
UwuLend's exploit stemmed from using a spot, single-transaction-manipulable reserve state as the price source for a critical accounting decision (borrow vs. liquidate valuation), letting the attacker distort the price within one atomic sequence and profit off the inconsistency. Raydium AMM has a structurally analogous pattern: `Processor::calc_take_pnl` derives its "current price" directly from the live token-vault balances read at instruction time (`amm_pc_vault.amount` / `amm_coin_vault.amount`), and persists a resulting `target_orders.calc_pnl_x` / `calc_pnl_y` basis that every subsequent Deposit, Withdraw, and WithdrawPnl call must remain consistent with via a hard invariant check.

### Finding Description
In `Processor::calc_take_pnl`, the pool's "current price" is computed each call directly from `total_pc_without_take_pnl` / `total_coin_without_take_pnl`, which in turn come straight from the live SPL token vault balances read in the same instruction (`Calculator::calc_total_without_take_pnl_no_orderbook(amm_pc_vault.amount, amm_coin_vault.amount, &amm)`), see [1](#0-0) . This function is invoked from `process_deposit` [2](#0-1) , `process_withdraw` [3](#0-2) , and `process_withdrawpnl` [4](#0-3) , but critically NOT from the swap paths (`process_swap_base_in`, `process_swap_base_out`, and their `_v2` variants only call `calc_total_without_take_pnl_no_orderbook`, never `calc_take_pnl`), see [5](#0-4)  and [6](#0-5) .

`calc_take_pnl` enforces a strict solvency-style invariant before proceeding: [7](#0-6) 
```
let pool_pc_amount = U128::from(*total_pc_without_take_pnl);
let pool_coin_amount = U128::from(*total_coin_without_take_pnl);
if pool_pc_amount.checked_mul(pool_coin_amount).unwrap()
    >= (calc_pc_amount).checked_mul(calc_coin_amount).unwrap()
```
If this check fails, the function returns `AmmError::CalcPnlError`, which aborts the entire enclosing instruction (Deposit, Withdraw, or WithdrawPnl).

After a successful pass, `process_deposit` re-derives `target_orders.calc_pnl_x` / `calc_pnl_y` from the *instantaneous, potentially attacker-shifted* reserves plus the user's deposited amounts: [8](#0-7) 

Because a single atomic Solana transaction can freely combine a large `SwapBaseIn`/`SwapBaseOut` instruction (unprivileged, attacker-chosen amounts) with a subsequent `Deposit` instruction against the same pool, an attacker can:
1. Swap a large amount in one direction to momentarily skew `amm_pc_vault.amount` / `amm_coin_vault.amount` far from the pool's fee-adjusted "true" equilibrium.
2. Immediately call `Deposit` in the same transaction while the reserves are still skewed. `calc_take_pnl` computes `x1, y1` from this skewed state and `process_deposit` writes a new `target_orders.calc_pnl_x/y` basis derived from that skewed snapshot plus the deposited liquidity.
3. Reverse the swap (or let the pool arbitrage back to a normal ratio) later in the same transaction or in subsequent blocks.

Once the manipulated basis is committed to `target_orders`, any later legitimate Deposit/Withdraw/WithdrawPnl call recomputes real, un-skewed `x1, y1` and compares `pool_pc_amount * pool_coin_amount` against the now-inflated `calc_pnl_x * calc_pnl_y` recorded during the attack window. If the recorded product exceeds the genuine reserve product (which is plausible since the basis was captured mid-manipulation rather than at a fee-accumulated equilibrium), every subsequent call to `calc_take_pnl` — and therefore every Deposit, Withdraw, and WithdrawPnl — will unconditionally hit the `else` branch and return `AmmError::CalcPnlError`, see [9](#0-8) .

### Impact Explanation
This would permanently deny all liquidity providers (and the protocol's `pnl_owner`) the ability to deposit, withdraw, or collect PnL from the affected pool, since every one of those instructions unconditionally calls `calc_take_pnl` and any failure there propagates as a hard error that aborts the instruction. This constitutes a permanent freezing of LP funds in the pool — funds remain in the vaults but become unwithdrawable through the standard instruction set, matching the "permanent freezing of user or LP funds" bar in the validation criteria. Unlike UwuLend, this is not a direct fund-draining oracle attack (Raydium's swap math itself is not oracle-dependent), but the same underlying flaw — an accounting subsystem trusting a spot, single-transaction-manipulable value as a persisted basis for a later solvency check — is present.

### Likelihood Explanation
The prerequisite actions (`SwapBaseIn`/`SwapBaseOut` and `Deposit`) are both fully unprivileged, reachable by any signer with attacker-chosen amounts and accounts, and composable in one atomic transaction with no special build flags, leaked keys, or off-chain dependencies — matching all in-scope reachability constraints. However, whether the specific arithmetic (fee accrual, decimal normalization via `Calculator::normalize_decimal_v2`/`restore_decimal`) actually allows the recorded `calc_pnl_x * calc_pnl_y` to exceed the genuine post-reversion reserve product depends on exact swap/deposit sizing and decimal precision, and requires numeric simulation to confirm a concrete parameter set that triggers the permanent lock; this could not be fully verified through static review alone.

### Recommendation
Decouple the PnL "price basis" from the instantaneous vault balance read within the same instruction. Options include: (1) requiring `calc_take_pnl`'s price snapshot to be taken from a time-weighted or previous-block value rather than the same-transaction live vault balance, (2) relaxing the strict `>=` invariant to tolerate small, bounded deviations (e.g., recoverable via saturating arithmetic instead of a hard error) so a single skewed snapshot cannot permanently deny future PnL/deposit/withdraw calls, or (3) recomputing/repairing `target_orders.calc_pnl_x/y` using a safe fallback path if the invariant check fails, rather than aborting outright.

### Proof of Concept
1. Attacker submits one transaction containing: (a) `SwapBaseIn`/`SwapBaseOut` with a large `amount_in`/`amount_out` against the target pool to sharply skew `amm_pc_vault.amount` and `amm_coin_vault.amount`; (b) immediately following, a `Deposit` instruction (`DepositInstruction`) against the same pool.
2. `process_deposit` calls `Calculator::calc_total_without_take_pnl_no_orderbook` using the just-skewed vault balances [1](#0-0) , then `Self::calc_take_pnl` [2](#0-1)  to derive `delta_x`/`delta_y`, and finally writes a new `target_orders.calc_pnl_x`/`calc_pnl_y` basis built from the skewed `x1`/`y1` plus the attacker's deposited amounts [8](#0-7) .
3. Attacker unwinds the swap (or lets arbitrageurs restore the ratio), returning `amm_pc_vault.amount`/`amm_coin_vault.amount` toward the pre-attack equilibrium.
4. Any later party calling Deposit, Withdraw, or WithdrawPnl triggers `calc_take_pnl` again; if the now-recomputed `pool_pc_amount * pool_coin_amount` (real, reverted reserves) is less than the inflated recorded `calc_pnl_x * calc_pnl_y`, the function returns `AmmError::CalcPnlError` [9](#0-8) , permanently blocking all further Deposit/Withdraw/WithdrawPnl calls on the pool.
