### Title
Unchecked fixed-size buffer copy from attacker-controlled BEEFY vote signature causes panic/crash - ([File: evm/rust/src/conversions.rs])

### Summary
The `From<Vote> for SignatureWithAuthorityIndex` conversion in the BEEFY consensus-proof pipeline copies an attacker-supplied, variable-length Solidity `bytes` signature into a fixed 65-byte buffer using `copy_from_slice` without first validating that the source length equals 65. This is the same bug class as the reported libuv issue: a length assumption (`_POSIX_PATH_MAX`/fixed buffer) is not enforced against the actual data before a raw fixed-size buffer write, causing a crash when the assumption is violated.

### Finding Description
`SignatureWithAuthorityIndex::from(Vote)` converts an ABI-decoded `Vote` (from `ecdsa_beefy::Beefy::Vote`) into the internal proof type consumed by the BEEFY relay-chain proof conversion pipeline: [1](#0-0) 

The relevant lines:
```
fn from(value: Vote) -> Self {
    let sig_bytes = value.signature.to_vec();
    let mut signature: TSignature = [0u8; 65];
    signature.copy_from_slice(&sig_bytes);
    ...
```
`value.signature` is an `alloy_primitives::Bytes` — a dynamically-sized, ABI-decoded byte array with no length constraint enforced at decode time. `copy_from_slice` requires the source and destination slices to have identical lengths; Rust does not truncate or pad, it panics (`source slice length (N) does not match destination slice length (65)`) whenever `sig_bytes.len() != 65`.

This conversion is invoked as part of building `RelayChainProof`/`MmrProof` from a `Commitment`'s `votes` list, which in turn feeds `ConsensusMessage`/`BeefyConsensusProof` construction used by the BEEFY consensus verification path: [2](#0-1) 

Because the `Vote.signature` field is a raw dynamic `bytes` value populated from relayed/attacker-influenced proof data (BEEFY commitments and their per-authority votes are gathered and forwarded off-chain by relayers before being submitted for consensus verification), any vote whose signature is not exactly 65 bytes — e.g., truncated, padded, or maliciously crafted — triggers an unrecoverable panic at this conversion boundary rather than a graceful `Result::Err`.

### Impact Explanation
A panic in a consensus-proof conversion routine used on the BEEFY verification path aborts the process handling the proof (the host/relayer/prover binary invoking this conversion). This matches the "cause node process to crash" impact described in the original report: an external, unprivileged party who can influence the shape of a BEEFY vote/signature being converted can force a denial-of-service crash of the component performing consensus verification, disrupting the liveness of the BEEFY relay-chain proof path that Hyperbridge's message dispatch relies on.

### Likelihood Explanation
The trigger condition is trivial to produce — any signature byte-array whose length is not exactly 65 (e.g., 64, 66, or 0 bytes) reaches `copy_from_slice` unfiltered, since there is no `if sig_bytes.len() != 65 { return Err(..) }` guard prior to the copy, unlike other conversions in the same file that correctly use `try_into().expect(...)` with a descriptive panic message acknowledging invalid input, or the safe pattern seen in `modules/consensus/pharos/verifier/src/state_proof.rs` where lengths are validated before slicing: [3](#0-2) 

The `Vote`/signature conversion has no equivalent guard, making a malformed-length signature reach the fixed buffer copy directly.

### Recommendation
Validate `sig_bytes.len() == 65` before calling `copy_from_slice`, returning a `TryFrom`-style `Result` (or using `try_into()` on the slice) instead of an infallible `From` that can panic on attacker-controlled input, mirroring the defensive length checks already used elsewhere in the codebase (e.g., `decode_u256_from_storage`).

### Proof of Concept
1. Construct a `Vote` with `signature` set to a `bytes` value of length 64 or 66 (any length ≠ 65) instead of a valid 65-byte ECDSA signature.
2. Route this `Vote` through the BEEFY consensus proof conversion path so that `SignatureWithAuthorityIndex::from(vote)` is invoked (e.g., during construction of a `RelayChainProof`/`Commitment` from relayed vote data).
3. Observe the process panics at `signature.copy_from_slice(&sig_bytes)` in `evm/rust/src/conversions.rs`, terminating the component performing BEEFY consensus verification — analogous to the original libuv `realpath` buffer-size mismatch crash.
