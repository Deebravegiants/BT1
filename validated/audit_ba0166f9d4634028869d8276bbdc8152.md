### Title
Emporium's balance-safety check is entirely skipped when `erc20TokenAddresses` is empty, allowing arbitrary asset drain via unconstrained `ops` calls - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` only verifies that Emporium's balance did not decrease for the tokens explicitly listed in `circomData.erc20TokenAddresses`, by diffing `balancesBefore`/`balancesAfter` and reverting via `BalanceChangeShouldBePositive` [1](#0-0) . The `stack.ops` executed inside the same call are arbitrary attacker-supplied calls (`op.endpoint.call{value: op.value}(op.callData)`) that are not otherwise constrained to match `erc20TokenAddresses` [2](#0-1) . If the attacker supplies `erc20TokenAddresses = []`, the balance-check loop never executes for any asset, so an op that directly transfers out a token/ETH balance sitting in Emporium is never checked or reverted.

### Finding Description
The equality that should hold is: for every asset whose balance decreases in Emporium during `runAction`, `balanceChange >= 0` must be enforced (or the decrease must be explained/covered by `deltaAmountChanges`). In the code, this equality is only checked inside the `for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++)` loop [1](#0-0) . When `circomData.erc20TokenAddresses.length == 0`, this loop body — including the `revert BalanceChangeShouldBePositive()` guard — never executes, so the equality is never evaluated for any asset, regardless of what the `ops` actually did to Emporium's balances.

The `ops` array (`stack.ops`) is decoded from `circomData.externalActionData.externalActionMetadata` and executed unconditionally before the (potentially empty) balance-check loop [3](#0-2) . Nothing in `runAction` restricts an op's `endpoint`/`callData` to only touch tokens present in `erc20TokenAddresses` — the ops can call any external contract, including calling `transfer`/`transferFrom` directly on a token contract holding Emporium's balance, or sending raw ETH out via `op.value`.

`runAction` is gated by `onlyAllowedRecipient`, meaning it can only be invoked by the Hinkal core contract (an allowed recipient) as part of a `transact` flow with a valid ZK proof for the attacker's own UTXOs. However, `circomData.erc20TokenAddresses` and `externalActionMetadata` (hence `ops`) are public inputs supplied by the caller and merely bound into the proof via a calldata/message hash commitment — the circuit does not semantically constrain that every asset touched by `ops` must appear in `erc20TokenAddresses`. This lets an attacker submit a self-proven transaction where the declared token array is empty (or omits the target asset) while the embedded `ops` perform a direct transfer of an asset that happens to be sitting in Emporium's balance (e.g., relay fee tokens, dust/leftover balances from other users' in-flight or partially completed Emporium flows — a scenario the code comment at line 141 explicitly acknowledges: "the only case when balanceChange can be < 0, when there were some funds on emporium before the call").

Existing guards do not catch this: `performHinkalChecks`/`dimensionsCheck` validate proof structure and dimension consistency but do not force `erc20TokenAddresses` to include every asset an external action's `ops` touches; `verifyWallet` only checks the EIP-712 signature over `ops`/`maxFee`/`deadline`, not that the balance-diff array covers all tokens moved by `ops`; the circuit constraints (`inTotal + amountChanges === outTotal`, etc.) constrain UTXO accounting for the caller's own leaves, not Emporium's on-chain token balance for arbitrary ERC20s untouched by the public-input array.

### Impact Explanation
An attacker can drain any ERC20 or ETH balance held by the Emporium contract that is not listed in their submitted `erc20TokenAddresses` array, with zero revert protection, by crafting `ops` that call `transfer`/`transferFrom`/native-ETH-send directly against that asset. This is direct theft of funds routed through/held by Emporium on behalf of other users (deposits in flight, relay fees, or dust from prior operations), matching the Critical category (direct theft of shielded/in-flight user funds). It is repeatable for any asset balance that accumulates in Emporium and is not declared by the attacker.

### Likelihood Explanation
Preconditions: (1) Emporium must hold a non-zero balance of some asset (plausible from other users' multi-step flows, relay fees, or residual dust — acknowledged in the code's own comment), and (2) the attacker must be able to submit a valid self-proven `transact` call through Hinkal with `erc20TokenAddresses = []` (or omitting the target asset) while embedding an `ops` entry that calls the target token/ETH transfer. Since the attacker fully controls `CircomData`, `externalActionMetadata`, and can generate proofs for their own UTXOs, and `erc20TokenAddresses` length appears to be a free choice within the accepted dimensions, this is feasible without any privileged role. Cost is limited to a single proof generation and gas.

### Recommendation
Do not gate the balance-safety check on `erc20TokenAddresses.length`. Either (a) require `erc20TokenAddresses` to be non-empty and to enumerate every asset that could be affected by `ops` (validated at the circuit/dimension level, not just left to caller choice), or (b) track Emporium's aggregate ETH/ERC20 balances independently of the caller-supplied array (e.g., a fixed allow-list of "protocol-relevant" tokens checked unconditionally) so that any negative balance change is always caught, or (c) restrict `ops.endpoint`/`callData` so they cannot directly invoke token transfer functions on arbitrary tokens outside of the declared `erc20TokenAddresses`/allowed integrations.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a mock allowed-recipient (simulating Hinkal), and a mock ERC20 `T`.
2. Seed Emporium with a balance of `T` (simulate "funds from a legitimate flow", e.g., direct `T.mint(emporium, 100e18)`).
3. As the attacker, craft `CircomData` with `erc20TokenAddresses = []` and `externalActionData.externalActionMetadata` encoding an `EmporiumStack` with one stateless op: `endpoint = address(T)`, `callData = abi.encodeCall(T.transfer, (attacker, 100e18))`, `value = 0`.
4. Call `runAction(circomData, deltaAmountChanges = [])` from the mock allowed recipient.
5. Assert: call does not revert (specifically `BalanceChangeShouldBePositive` is never triggered), `T.balanceOf(emporium)` goes from `100e18` to `0`, and `T.balanceOf(attacker)` increases by `100e18` — demonstrating `balanceChange` for `T` (real value = -100e18) was never compared against 0 because `T` was absent from `erc20TokenAddresses`.
