### Title
Webhook `shop` domain header is trusted for tenant identification despite not being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body via `Utils::HmacValidator.validate(request)` [1](#0-0) . The `Request#to_signable_string` used for that HMAC computation is only the raw body [2](#0-1) ; the `shop` value read from the `x-shopify-shop-domain`/`shopify-shop-domain` header is never included in the signed material [3](#0-2) . After validation succeeds, that unauthenticated header value is handed to the app's handler as the tenant identity via `WebhookMetadata.new(topic: ..., shop: request.shop, body: ..., ...)` [1](#0-0) .

### Finding Description
The bug class from the external report is "a subject's guarded state is released based on one signal while other, unresolved signals for the same identity are ignored" — i.e., an equality/binding that should hold (`the identity the HMAC vouches for == the identity used to act`) is broken because one field used downstream is not actually covered by the cryptographic check that gates the whole operation.

Here the equality that should hold is:
`shop used to authorize/act on data == shop whose bytes were actually HMAC-verified`

`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the received `hmac` [4](#0-3) . For webhooks, `to_signable_string` returns only `@raw_body` [2](#0-1) . The `shop` accessor pulls straight from an HTTP header (`shopify-shop-domain`) that is not part of that signed string [3](#0-2) [5](#0-4) .

Critically, the HMAC secret (`Context.api_secret_key`) is the app's shared `client_secret`, not a per-shop secret [6](#0-5) . Any merchant that installs the app receives legitimately-signed webhooks for their own shop, computed with that same app-wide secret. Because the signature only binds the body, not the shop header, a malicious-but-otherwise-unprivileged merchant who has installed the app can capture one of their own legitimately-delivered webhooks (valid body + valid HMAC) and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to point at a victim shop. `Registry.process` will still consider the HMAC valid (it never inspected the header) [7](#0-6) , and the handler will be invoked believing the event legitimately originates from the victim shop, because `request.shop` is passed through untouched into `WebhookMetadata` [8](#0-7) .

This mirrors the report's root cause exactly: a single check (HMAC valid) is treated as sufficient to "unfreeze"/authorize an action tied to a specific subject (a shop), while another independent piece of state relevant to that subject's identity (the shop header) is left unguarded by that same check.

### Impact Explanation
If a host application built on this gem uses the webhook `shop` value from `WebhookMetadata#shop` as the tenant key (a documented, intended use of the field returned by this gem's own API) to route data — e.g., writing `orders/create` payloads under a shop record, or acting on `app/uninstalled` to revoke/rotate stored credentials for "that shop" — an attacker-merchant can forge the tenant identity of webhook events for shops they do not own. This is cross-tenant access: attacker-controlled data/events attributed to and processed against a victim tenant's data, purely by manipulating an HTTP header while riding on a legitimately-obtained HMAC for their own body. This satisfies the "cross-tenant access" Critical impact category, since the trust boundary between tenants of the same app is bypassed using only capabilities available to any merchant/attacker who has installed the app (no `api_secret_key`, no access token, no privileged account required beyond normal app installation).

### Likelihood Explanation
Likelihood is significant given:
- The app's webhook HMAC secret is shared across all installations (`Context.api_secret_key`) rather than being scoped per-shop, so any installer of the app has a valid signing oracle for arbitrary body content in the sense that they can obtain HMAC-valid deliveries for real events on their own shop.
- No code path in `Request` or `Registry` cross-checks the `shop` header against anything (no comparison to `iss`/`dest`-style bound claims, no verification the header matches a known/installed shop for this delivery).
- This is a documented, gem-exposed field (`WebhookMetadata#shop`) that app authors are expected to use to identify the originating shop, so the vulnerable usage pattern does not require the host app to "ignore" documented API — it is the direct, natural use of the exposed value.

### Recommendation
Do not treat the `shop` header as authenticated by the webhook HMAC. Either:
1. Bind the shop into the signed material the gem verifies (not possible unilaterally since Shopify controls the wire format), or
2. Have `Registry.process`/`Request` require the caller to supply the expected/registered shop(s) for the webhook and reject processing if `request.shop` does not match an application-provided allow-list, or clearly document in `WebhookMetadata` that `shop` is unauthenticated header data and must be independently verified/whitelisted by the host app against its own list of installed shop domains before being used as a trust boundary, mirroring the explicit `Utils::ShopValidator.sanitize!` pattern already used elsewhere in this gem (e.g., `ClientCredentials.client_credentials`, `TokenExchange.migrate_to_expiring_token`) to avoid trusting unauthenticated shop-like strings.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com`, and the app registers for a webhook topic (e.g., `orders/create`).
2. Shopify delivers a legitimate webhook to the app's endpoint with headers including:
   - `x-shopify-hmac-sha256: <valid HMAC over body, computed with the app's shared api_secret_key>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - body: `{"id": 1, ...}`
3. Attacker captures this exact request (they own the shop, so they can trivially receive/replay it, e.g. from their own server logs or by pointing the delivery endpoint at a proxy they control).
4. Attacker resends this same request to the app's webhook endpoint but with the header changed to:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
5. The gem's `Registry.process` runs `Utils::HmacValidator.validate(request)` [9](#0-8) , which only checks the (unchanged) body against the (unchanged) HMAC — validation succeeds.
6. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: {"id": 1, ...})` [8](#0-7) , causing the host application to process attacker-supplied order data as if it belonged to `victim-shop.myshopify.com`.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
