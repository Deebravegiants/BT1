### Title
Unbounded/cyclic ancestry traversal in GRANDPA justification verification enables infinite-loop DoS - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
`AncestryChain::ancestry()` walks attacker-supplied `votes_ancestries` headers from a target hash back to a base hash by repeatedly following `parent_hash` pointers, with no cycle detection and no bound on the number of hops [3](#0-2) . The header set backing this walk is built directly from the fully attacker-controlled `votes_ancestries: Vec<H>` field of the `GrandpaJustification`, keyed only by each header's self-declared hash [4](#0-3) . This is analogous to CVE-2018-19478, where a crafted input drives the parser into an extremely long/unbounded computation.

### Finding Description
In `GrandpaJustification::verify_with_voter_set`, `finality_grandpa::validate_commit(&self.commit, voters, &ancestry_chain)` is invoked first, before the per-precommit `check_message_signature` loop that follows it [5](#0-4) . The `finality_grandpa` crate's `validate_commit` only checks that precommit authors are members of the voter set (by ID, not signature) and computes the "ghost"/tally by tracing ancestry routes via the supplied `Chain` implementation — it performs no cryptographic signature verification itself. That means `AncestryChain::ancestry()` can be invoked with completely forged precommit target hashes and a `votes_ancestries` set containing headers whose `parent_hash` fields form a cycle (e.g., header A's parent points to header B's self-declared hash, and B's parent points back to A's), all before a single ECDSA/ED25519 signature is checked.

Because `ancestry()` has no visited-set / cycle detection and no maximum hop count, when `base_hash` is not part of the cycle, the `while current_hash != base` loop alternates forever between the cyclic headers, never terminating [6](#0-5) .

The whole path is reachable by any unprivileged party through the unsigned `handle_unsigned` extrinsic: `Pallet::execute` → `handle_incoming_message` → `GrandpaConsensusClient::verify_consensus` (decodes attacker-supplied `proof` bytes into `ConsensusMessage`, no auth) → `verify_parachain_headers_with_grandpa_finality_proof`/`verify_grandpa_finality_proof` → `GrandpaJustification::verify` [1](#0-0) . `handle_unsigned` is explicitly designed to let anyone submit consensus/message proofs for free as an unsigned transaction and is also executed inside `validate_unsigned` in the transaction pool, and inside block-authoring/import via `Self::execute` [7](#0-6) [8](#0-7) .

### Impact Explanation
An attacker needs no valid signatures, no stake, and no special privileges — only knowledge of the public current/next GRANDPA authority IDs (public information) to populate `commit.precommits[].id`, plus arbitrary crafted headers for `votes_ancestries`. Submitting this as `handle_unsigned` causes the node to enter the unterminating `ancestry()` loop:
- During transaction-pool validation (`validate_unsigned` calls `Self::execute`), this can hang the validating node's transaction-pool worker on every peer that receives and validates the gossip transaction.
- During block authoring/import, it hangs block production/import, since `Self::execute` is called unconditionally for every message in the batch with no per-message timeout.

This can render the GRANDPA-based route (and potentially the whole chain, since GRANDPA client validation is invoked broadly for any relay/parachain state machine using this client) unable to process further consensus updates or deliver messages, satisfying the "route unable to deliver messages" impact bar, and in the worst case can stall block production/import entirely — a liveness-critical, permanent-freeze-class issue reachable from a single relayed message.

### Likelihood Explanation
High. The trigger requires only public authority IDs, standard SCALE-encodable header/justification structures, and no valid cryptographic material. Any relayer or outside party can submit `Message::Consensus` via `handle_unsigned` at zero cost (unsigned, "free" per design) [9](#0-8) .

### Recommendation
- Add cycle detection in `AncestryChain::ancestry()` (e.g., track visited hashes and abort with `Error::NotDescendent` when a hash repeats) and/or bound the number of hops to `votes_ancestries.len() + 1`.
- Alternatively, verify precommit signatures (`check_message_signature`) before invoking `finality_grandpa::validate_commit`, and reject any `votes_ancestries` entries that are not reachable in a strictly decreasing block-number chain from a genuinely-signed precommit target — this both closes the DoS and matches expected trust assumptions for `Chain::ancestry`.
- Cap `votes_ancestries.len()` to a sane maximum before constructing the `AncestryChain`.

### Proof of Concept
1. Craft two headers `A` and `B` (fields otherwise arbitrary/zeroed) such that `A.parent_hash == B.hash()` and `B.parent_hash == A.hash()` (fully attacker-controlled since hashes are simply derived from header content, no external constraint).
2. Build a `GrandpaJustification` with `votes_ancestries = vec![A, B]`, and `commit.precommits` containing at least one entry whose `id` is a real, publicly-known authority from the current/next set and whose `precommit.target_hash == A.hash()` (or `B.hash()`); the `signature` field can be arbitrary garbage since it is not checked until after `validate_commit` runs.
3. Set `commit.target_hash`/`target_number` and the outer `FinalityProof.unknown_headers`/`block` so that the earlier `verify_grandpa_finality_proof` sanity checks pass and reach `justification.verify(...)`.
4. Submit this as a `ConsensusMessage::Polkadot` (or `StandaloneChain`) proof inside a `Message::Consensus` via `pallet_ismp::Call::handle_unsigned`.
5. Observe that `finality_grandpa::validate_commit` invokes `AncestryChain::ancestry(base, A.hash())`, which loops forever alternating between `A` and `B`, hanging the validating node.

## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
