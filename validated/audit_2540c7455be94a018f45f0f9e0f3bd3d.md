### Title
Duplicate `erc20TokenAddresses` entries let a single balance delta back two independent output commitments - (File: `contracts/Hinkal.sol`)

### Summary
`Hinkal.transact` computes a per-token `balanceDif` from a single before/after snapshot and then checks that value against the sum of committed UTXOs for that token index, but nothing on-chain or in the circuit constrains `circomData.erc20TokenAddresses` to contain distinct addresses. This mirrors the XST_exp2 bug class: a value that is metered once (a pool reserve in the original exploit, a token balance snapshot here) gets credited multiple times because the surrounding logic assumes one-token-per-slot without enforcing it.

### Finding Description
In `Hinkal.sol`, `oldBalances`/`newBalances` are captured once per index of `circomData.erc20TokenAddresses` via `getBalancesForArray`, and the loop that follows recomputes `balanceDif` and the matching `utxoAmount` independently for every index `i`: [1](#0-0) 

If the same ERC20 address appears twice in `circomData.erc20TokenAddresses` (say index 0 and index k), `getERC20OrETHBalance` returns the *same* global balance for both indices, so `balanceDif` at index 0 and index k are numerically identical for a single real transfer of `X` tokens into the contract. The loop then independently checks:
```
balanceDif == amountChanges[i] + utxoAmount   // for i = 0
balanceDif == amountChanges[k] + utxoAmount   // for i = k
```
Nothing prevents the prover from producing a valid proof where `utxoSet` contains two output UTXOs for that same token address — one credited against index 0 and one against index k — each satisfying the equation with the *same* `balanceDif = X`. The circuit-checked `inputForCircom` and `calldataHash` do not enforce uniqueness of `erc20TokenAddresses` either: `dimensionsCheck` in `HinkalHelper.sol` only checks array lengths against `dimensions.tokenNumber`, never distinctness of addresses: [2](#0-1) 

This is directly analogous to the XST_exp2 pattern where a single unit of value (the pair's real token balance) was made to be recognized/counted multiple times by a mechanism (repeated `skim()` calls) that never verified the underlying value hadn't already been accounted for.

### Impact Explanation
If exploitable, a user depositing a single real transfer of `X` tokens could mint two separate shielded UTXOs each nominally worth `X` (or split so that `sum(utxoAmount at index0) + sum(utxoAmount at indexk) = 2X` while only `X` was actually deposited), i.e. minting shielded value without backing — a Critical-severity outcome per the given impact classification (unbacked minting of shielded value).

### Likelihood Explanation
This requires the prover to construct a valid Circom proof with `dimensions.tokenNumber ≥ 2` and duplicate addresses in `erc20TokenAddresses`, plus a matching `utxoSet` produced by `_internalTransact`/`_externalTransact`. I was not able to fully inspect `circuits/MainEVMCircuit.circom`'s token-address handling in this pass (only grep results were reviewed, not the full uniqueness/ordering constraints in the circuit template), so it is **uncertain** whether the circuit template itself enforces distinct or sorted token addresses as part of its public-input binding. This must be verified against the full circuit before treating this as a confirmed break, since the circuit is the authority that binds `erc20TokenAddresses` into the proof's public inputs.

### Recommendation
Add an explicit on-chain (and/or circuit) check that `circomData.erc20TokenAddresses` contains strictly increasing/unique addresses, enforced in `HinkalHelper.dimensionsCheck` (mirroring similar strictly-increasing-address invariants used elsewhere in DeFi protocols to prevent double-counting).

### Proof of Concept
Not fully constructible without confirming the circuit's constraints on `erc20TokenAddresses`; the described on-chain arithmetic path is shown above (`contracts/Hinkal.sol:88-146`), but a full PoC requires generating a valid Groth16 proof with duplicate token-address public inputs, which depends on `circuits/MainEVMCircuit.circom` — a file I could not fully verify in this session for uniqueness constraints.

**Note on confidence**: Because I could not fully read the token-address-handling section of `circuits/MainEVMCircuit.circom` within the available tool budget, I cannot state with certainty whether the circuit template already rejects duplicate addresses (in which case this finding would not be exploitable). This should be verified before acting on the recommendation above.
