### Title
LimitRanger admission bypass on `/resize` subresource for pods marked for deletion - ([File: plugin/pkg/admission/limitranger/admission.go])

### Summary
`(l *LimitRanger).runLimitFunc` unconditionally returns `nil` (skipping all `LimitRange` min/max/ratio enforcement) whenever `a.GetOldObject()`'s `DeletionTimestamp` is set, with no distinction for the `resize` subresource. Since `DefaultLimitRangerActions.SupportsAttributes` explicitly allows `Update` operations on the `resize` subresource, an attacker who deletes their own pod with a grace period and then issues a resize request during the grace window can change container CPU/memory requests/limits without any `LimitRange` bound checking.

### Finding Description
`runLimitFunc` checks the old object's deletion state before applying any limit function: [1](#0-0) 

Normally this early-return is harmless because `SupportsAttributes` rejects ordinary pod `Update` operations (container specs are immutable outside creation): [2](#0-1) 

However, `SupportsAttributes` explicitly carves out an exception: `Update` requests to the `resize` subresource on a `Pod` are supported and reach `runLimitFunc`/`ValidateLimit`/`MutateLimit`: [3](#0-2) 

The `resize` subresource (`pkg/registry/core/pod/strategy.go`, `podResizeStrategy`) is precisely the code path that legitimately mutates `Containers[*].Resources`/`InitContainers[*].Resources` via `dropNonResizeUpdates` and `PrepareForUpdate`, and its own validation (`ValidatePodResize` in `pkg/apis/core/validation/validation.go`) does not reject resize requests solely because the pod has a `DeletionTimestamp` set — it only blocks static pods, Windows pods, QoS-class changes, and unsupported kubelets: [4](#0-3) 

Exploit flow: (1) attacker with pod update/patch permission issues a graceful `DELETE` on their own pod (sets `metadata.deletionTimestamp` with a grace period, object remains live in etcd); (2) before GC/kubelet removes it, attacker issues a `PATCH`/`PUT` to the pod's `/resize` subresource increasing container CPU/memory beyond the namespace `LimitRange` max; (3) `LimitRanger.Admit`/`Validate` call `runLimitFunc`, which sees `oldAccessor.GetDeletionTimestamp() != nil` and returns `nil` immediately, never calling `PodValidateLimitFunc`/`maxConstraint`; (4) the resize request is admitted and persisted since `BeforeUpdate` in `staging/src/k8s.io/apiserver/pkg/registry/rest/update.go` only preserves the deletion timestamp/grace period fields themselves, not resource bounds: [5](#0-4) 

The kubelet on the node will apply the resized cgroup limits to the still-running (terminating) pod for the remainder of the grace period, allowing consumption of resources in excess of the `LimitRange`-enforced bounds.

### Impact Explanation
This is a namespace-scoped resource-limit bypass / policy-enforcement gap (matches the "admission bypass" bounty class). During the deletion grace period the attacker's pod can consume CPU/memory beyond what the `LimitRange` permits, potentially causing node resource pressure/DoS for co-located tenants, though the impact is time-bounded to the grace period and requires the `InPlacePodVerticalScaling` feature and `resize` subresource permission to be enabled/granted.

### Likelihood Explanation
Requires only ordinary namespace-scoped RBAC to `delete` and `update` (or `patch`) the `resize` subresource of one's own pod — no elevated privileges. Requires the `InPlacePodVerticalScaling` feature gate to be enabled (default-on in current releases) and a sufficient grace period to fit the resize call within the window, which is fully attacker-controlled via `DeleteOptions.GracePeriodSeconds`. This is reliably repeatable.

### Recommendation
In `runLimitFunc`, do not blanket-skip validation for the `resize` subresource: either remove the deletion-timestamp short-circuit when `a.GetSubresource() == "resize"`, or explicitly re-check `a.GetObject()`'s own resource fields against `LimitRange` bounds regardless of the old object's deletion state for resize requests.

### Proof of Concept
Integration test in `plugin/pkg/admission/limitranger`:
1. Create namespace with a `LimitRange` capping container CPU/memory (e.g., max CPU 500m).
2. Create a pod with CPU request/limit within bounds; enable `InPlacePodVerticalScaling`.
3. Issue a graceful `DELETE` with `GracePeriodSeconds: 300` (pod remains, `DeletionTimestamp` set).
4. Issue an `UPDATE`/`PATCH` to the pod's `resize` subresource setting CPU limit to 2 (exceeding max 500m).
5. Assert current behavior: `LimitRanger.Validate`/`Admit` return `nil` and the resize is persisted with CPU=2 — demonstrating the bypass.
6. After the fix, assert the resize request is rejected with a `Forbidden` error citing the `LimitRange` max constraint.

func (d *DefaultLimitRangerActions) SupportsAttributes(a admission.Attributes) bool {
	// Handle in-place vertical scaling of pods, where users modify container
	// resources using the resize subresource.
	if a.GetSubresource() == "resize" && a.GetKind().GroupKind() == api.Kind("Pod") && a.GetOperation() == admission.Update {
		return true
	}

	// No other subresources are supported
	if a.GetSubresource() != "" {
		return false
	}

	// Since containers and initContainers cannot currently be added, removed, or updated, it is unnecessary
	// to mutate and validate limitrange on pod updates. Trying to mutate containers or initContainers on a pod
	// update request will always fail pod validation because those fields are immutable once the object is created.
	if a.GetKind().GroupKind() == api.Kind("Pod") && a.GetOperation() == admission.Update {
		return false
	}

	return a.GetKind().GroupKind() == api.Kind("Pod") || a.GetKind().GroupKind() == api.Kind("PersistentVolumeClaim")
}

func ValidatePodResize(newPod, oldPod *core.Pod, opts PodValidationOptions) field.ErrorList {
	// Part 1: Validate newPod's spec and updates to metadata
	fldPath := field.NewPath("metadata")
	allErrs := ValidateObjectMetaUpdate(&newPod.ObjectMeta, &oldPod.ObjectMeta, fldPath)
	allErrs = append(allErrs, validatePodMetadataAndSpec(newPod, opts)...)

	// static pods cannot be resized.
	if _, ok := oldPod.Annotations[core.MirrorPodAnnotationKey]; ok {
		return field.ErrorList{field.Forbidden(field.NewPath(""), "static pods cannot be resized")}
	}

	// windows pods are not supported.
	if oldPod.Spec.OS != nil && oldPod.Spec.OS.Name == core.Windows {
		return field.ErrorList{field.Forbidden(field.NewPath(""), "windows pods cannot be resized")}
	}

	specPath := field.NewPath("spec")
	if qos.GetPodQOS(oldPod) != qos.ComputePodQOS(newPod) {
		allErrs = append(allErrs, field.Invalid(specPath, newPod.Status.QOSClass, "Pod QOS Class may not change as a result of resizing"))
	}

	if !isPodResizeRequestSupported(*oldPod) {
		allErrs = append(allErrs, field.Forbidden(specPath, "Pod running on node without support for resize"))
	}
