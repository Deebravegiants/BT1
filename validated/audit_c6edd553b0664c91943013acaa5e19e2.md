### Title
Webhook shop/topic identity is not covered by the HMAC signature, allowing tenant-confused webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the raw HTTP body against the HMAC signature, then dispatches the handler using the `shop`, `topic`, and `webhook_id` values taken from unauthenticated HTTP headers. This is structurally the same bug class as the Hyperdrive report: a value is used to determine tenant/business outcome (bonds reserves / here, the acting `shop`) that is not actually covered by the same binding that was verified (governance fee amount / here, the HMAC signature). The equality that should hold — "the `shop` the HMAC authenticates" == "the `shop` the handler acts on" — is broken.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers, none of which participate in the signable string: [2](#0-1) 

`Registry.process` verifies the HMAC over that body-only string, then constructs `WebhookMetadata` (and dispatches the app's handler) using `request.shop`, `request.topic`, and `request.webhook_id` — none of which were part of the verified bytes: [3](#0-2) 

`HmacValidator.validate_signature` confirms the check is purely `HMAC(secret, to_signable_string) == received_signature`, i.e., body-only: [4](#0-3) 

This is in contrast to the OAuth callback's `AuthQuery`, which correctly folds `shop`, `host`, `code`, `state`, and `timestamp` into the signed string, so that the party performing OAuth cannot swap `shop` without invalidating the HMAC: [5](#0-4) 

For webhooks, no such binding exists: `body` + `hmac` is a valid signed pair regardless of which `shop`/`topic`/`webhook_id` header accompanies it. An attacker who obtains any one legitimately-signed `(body, hmac)` pair (e.g., by installing the target app on their own free/trial development store and capturing a webhook delivery meant for their own shop — an action requiring no privileged credentials or knowledge of `client_secret`) can resend the same `(body, hmac)` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) for a victim shop. `HmacValidator.validate` will report `true` because it only checks the body bytes, and `Registry.process` will happily invoke the app's handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`.

### Impact Explanation
This breaks the tenant boundary: the app's webhook handler is invoked believing an event was authoritatively delivered by Shopify for a specific merchant (`shop`), when in fact only the body bytes were verified, and the tenant-identifying header was fully attacker-controlled. Depending on how the host app's `WebhookHandler#handle` implementation keys off `data.shop` (a documented, intended usage per `docs/usage/webhooks.md`), this enables cross-tenant confusion — e.g., forging a `shop/redact`/`customers/redact`/`app/uninstalled` style event against a victim shop's session/data record, or injecting attacker-controlled body content into a victim tenant's processing pipeline. This matches the Critical "cross-tenant access" bucket, since the mismatch is inherent to this gem's own webhook-verification code path, not a misuse of the API by the host app.

### Likelihood Explanation
The prerequisite — obtaining one valid `(body, hmac)` pair for the target app — only requires installing the target app on any shop (including a free development store), which any unprivileged internet user can do without `api_secret_key`, an access token, or social engineering. No TLS interception or local access is needed; only a standard HTTP replay against the app's public webhook endpoint with a modified header.

### Recommendation
Bind the tenant/topic identity into the verified bytes so the equality "authenticated shop == acted-on shop" holds:
- Include `shop`, `topic`, and `webhook_id` (or at minimum `shop`) in `to_signable_string`, mirroring what Shopify's platform intends developers to trust, and reject the request if these headers were altered relative to what was signed; or
- If the header values cannot be added to the signable string (since Shopify itself only signs the raw body), the gem should not surface these header-derived fields as verified/trusted without documenting that the *body* alone is authenticated, and should encourage host apps to cross-check `shop` against an already-established session/webhook registration state before acting, rather than treating `WebhookMetadata.shop` as intrinsically authenticated.

### Proof of Concept
1. Attacker creates a free development store and installs the target Shopify app.
2. Shopify delivers a legitimate webhook to the app's endpoint: body `B`, header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, H)` (e.g., via a debugging proxy on the delivery it controls) and resends a POST to the same app webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` because only `B` is hashed ( [1](#0-0) , [4](#0-3) ).
5. `Registry.process` invokes the app's `WebhookHandler#handle` with `WebhookMetadata.shop == "victim-shop.myshopify.com"` ( [3](#0-2) ), causing the app to act on the victim's tenant context using attacker-supplied body content.
