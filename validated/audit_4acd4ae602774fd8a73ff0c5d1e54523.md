## Finding

### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is taken from unauthenticated HTTP headers while the HMAC only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` binds its HMAC signature exclusively to the raw request body, while the tenant-identifying `shop` field (plus `topic` and `webhook_id`) is read from HTTP headers that are never included in the signed bytes. `Registry#process` validates the HMAC and then hands the header-derived `shop` straight to the app's webhook handler as the trusted tenant identifier. This is the same bug class as the audit report's underlying pattern: a value that is acted upon by privileged/tenant-sensitive logic is not actually covered by the cryptographic check that is supposed to authenticate it.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

- `hmac` is decoded from the `hmac-sha256` header.
- `to_signable_string` returns only `@raw_body`.
- `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from separate HTTP headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) that are **not** part of `to_signable_string`.

`Utils::HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it against the `hmac` header: [2](#0-1) 

Since `to_signable_string` is only the raw body, the HMAC proves nothing about the `shop-domain`, `topic`, or `webhook-id` headers. `Webhooks::Registry#process` nonetheless validates the HMAC and then treats the header-derived `shop` as the authenticated tenant identity, dispatching it to the handler: [3](#0-2) 

**Identity binding broken (as an equality):**
`shop` used by the handler to scope tenant-specific side effects ≠ `shop` covered by the HMAC signature that is supposed to authenticate the request as genuinely originating from that shop.

Concretely: `HMAC-covered bytes = raw_body` while `shop_used_for_authorization = headers["shop-domain"]`, and these two are never cross-checked against each other.

### Impact Explanation
An unprivileged attacker who can observe or capture one legitimately-signed webhook body (e.g., from their own store, or a body which is otherwise not secret/unique to a shop) can resend that exact body with the same valid `hmac-sha256` header but an arbitrary `shop-domain` header. `HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry#process` will pass the attacker-chosen `shop` to the app's handler as if it were the authenticated tenant. Any host application that uses `WebhookMetadata#shop` to determine which merchant's data to update, credit, or act upon (the gem's documented usage pattern) can be made to apply another shop's legitimate webhook payload under an attacker-chosen tenant identity — i.e., cross-tenant action/data confusion, without possessing any access token, refresh token, or the app's `client_secret`.

### Likelihood Explanation
This requires no privileged material: an attacker only needs network reachability to the app's webhook endpoint and one previously-observed valid `(body, hmac)` pair (many webhook bodies are generic/non-secret, e.g., `app/uninstalled` with minimal payload, or bodies from the attacker's own shop where they legitimately receive the HMAC). No `api_secret_key`, TLS interception, or credential leakage is needed — only a replay of headers, which is squarely within the gem's own verification logic (`Webhooks::Request` / `Webhooks::Registry`), not a host-application misuse.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or independently authenticate/bind the `shop` header to the verified body (e.g., require the shop to also appear inside the signed payload/body and compare it against the header, rejecting mismatches). At minimum, document and enforce that `shop`, `topic`, and `webhook_id` must never be trusted for authorization decisions unless they are cryptographically bound to the validated bytes.

### Proof of Concept
1. Register a webhook handler that performs a tenant-scoped action keyed by `WebhookMetadata#shop` (as demonstrated in the gem's registry flow).
2. Capture one legitimate webhook delivery for `shop-domain: attacker-shop.myshopify.com` with body `B` and header `hmac-sha256: H`, where `H = HMAC(secret, B)`.
3. Replay a request to the app's webhook endpoint with the identical body `B` and header `hmac-sha256: H`, but change the `shop-domain` header to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` returns `true` (it only recomputes over `@raw_body`), so `Registry#process` proceeds and calls the handler with `shop: "victim-shop.myshopify.com"`, causing the handler to execute the body's action attributed to the victim tenant. [4](#0-3) [5](#0-4)

          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
