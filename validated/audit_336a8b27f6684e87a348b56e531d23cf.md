## Finding

### Title
Webhook `shop` and `topic` fields are trusted for tenant routing but are not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then hands the caller-supplied `shop-domain` and `topic` headers straight to the app's handler as trusted tenant-identifying metadata. Because those headers are not part of the signed material, any holder of one valid `(body, hmac)` pair can replay it with arbitrary `shop`/`topic` headers and have it accepted as an authentic webhook for a different shop or event type.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`HmacValidator.validate` computes the signature over exactly that string and compares it to the `hmac-sha256` header: [2](#0-1) 

`Registry.process` treats a passing HMAC check as sufficient authentication for the whole request, then builds `WebhookMetadata` directly from the unauthenticated `shop` and `topic` headers and dispatches it to the app's handler: [3](#0-2) 

`Request#shop` and `Request#topic` are read straight from headers with no cryptographic binding to the body/HMAC: [4](#0-3) 

The equality that should hold is: `bytes verified by HMAC == bytes acted on for tenant/topic routing`. Here, `bytes verified` = raw body only, while `bytes acted on` = raw body **plus** `shop-domain` and `topic` headers — breaking the binding. The library's own webhook doc explicitly recommends using `data.shop` to key application logic (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), reinforcing that host apps are expected to trust this value as tenant-scoping metadata.

### Impact Explanation
Any actor who has legitimately received one valid webhook delivery (e.g., by installing the app on their own free/dev shop and triggering an event) obtains a `(raw_body, hmac)` pair that stays valid forever for that body, independent of headers. They can then POST that same body/HMAC directly to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header pointing at a victim shop (and/or a different `x-shopify-topic`). `Utils::HmacValidator.validate` will accept it, and the handler will process attacker-supplied data under the identity of another tenant — a cross-tenant data-integrity break (e.g., injecting fabricated order/customer data attributed to a victim shop, or triggering a different lifecycle topic such as `app/uninstalled` semantics against an unaffected shop's records if the host app dispatches based on `data.topic`). No `api_secret_key`, access token, or TLS interception is required.

### Likelihood Explanation
Requires only: (1) the ability to obtain one legitimate `(body, hmac)` pair, achievable by any unprivileged actor who installs the app once on a shop they control, and (2) knowledge of the app's public webhook callback URL, which is typically discoverable/predictable. No secrets are needed to forge the tenant-identifying headers.

### Recommendation
Bind `shop-domain`, `topic`, and `webhook-id` into the signed material used for HMAC verification (or otherwise cryptographically bind them, e.g., by deriving/confirming the shop from a source that Shopify signs, such as validating against registrations tied to a known session/access token), rather than trusting them as free-form headers once only the body HMAC passes. At minimum, document prominently that `data.shop`/`data.topic` are unauthenticated and must not be used for authorization or tenant-scoping decisions without independent verification (e.g., cross-checking against the shop associated with the webhook subscription that was registered).

### Proof of Concept
1. Install the target app (any Shopify app using this gem for webhooks) on an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook (e.g., `orders/create`) and capture the delivered request: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC_SHA256(secret, B)`, and this is independent of any header value).
3. Send a new HTTP POST directly to the app's public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim.myshopify.com` and/or a different `x-shopify-topic`.
4. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC successfully (per `lib/shopify_api/utils/hmac_validator.rb` line 30) since it only checks `B`/`H`, then calls the registered handler with `WebhookMetadata(shop: "victim.myshopify.com", topic: <forged topic>, body: <attacker's body>)`, causing the app to act on `B` as if it were legitimate data for `victim.myshopify.com`.
