## Finding: Integer overflow / panic in Pharos BLS string-length parsing before proof verification

Root cause: in `verify_validator_set_proof`, the validator-set storage keys are recomputed from the **raw, not-yet-verified** `proof.storage_values` before `verify_all_storage_proofs` checks them against `state_root`: [1](#0-0) 

`compute_all_storage_keys` calls `bls_data_slots_from_header` on attacker-supplied `storage_values[idx]` to determine how many BLS data slots to expect, *before* any proof check has run: [2](#0-1) 

`bls_data_slots_from_header` decodes a Solidity "long string" length header and computes `(header_val - 1) / 2`, then truncates to `u64`/`usize` and adds `31`: [3](#0-2) 

Because `header_val` here comes straight from `proof.storage_values`, which is fully attacker/relayer controlled at this point (its authenticity is only checked *after* this arithmetic runs), a relayer can submit a crafted 32-byte "storage value" whose low byte is odd and whose `U256` value is very large. `length.low_u64()` truncates a 256-bit computed length down to 64 bits (silently discarding the high bits, an unchecked-narrowing bug analogous to the libarchive ISO parser's unchecked length field), and the subsequent `str_len + 31` addition is a `usize` arithmetic operation that overflows for values near `usize::MAX`. In a Substrate/pallet-ismp runtime built with `overflow-checks = true` (the norm for runtime WASM builds), this addition panics, aborting the extrinsic and denying service to any relayer trying to submit real Pharos consensus updates; if overflow checks are disabled, the wrapped result silently desyncs the derived slot count from the actual on-chain layout, corrupting the recomputed storage key list used for verification.

### Impact
A single crafted, unsigned Pharos consensus-update submission (proof/relayed message) reaches this parser before any cryptographic check occurs, matching the required "reachable from a single relayed proof, dispatched request" criterion. The result is either:
- a panic/DoS in the consensus-verification path used by `pallet-ismp`'s unsigned message handling for the Pharos light client, or
- (with overflow checks off) miscomputed storage keys that could desynchronize verification logic in unexpected ways.

### Likelihood
High for the DoS variant, since it requires only a malformed `storage_values` entry inside an otherwise well-formed `ValidatorSetProof` — no signature or state-root forgery needed, because the vulnerable arithmetic executes strictly before the proof-verification step (`verify_all_storage_proofs`) that would normally reject bogus values.

### Recommendation
Reorder `verify_validator_set_proof` so that `verify_all_storage_proofs` (or at least verification of each BLS-header slot) runs before any length is derived from `storage_values`, or make `bls_data_slots_from_header` fail safely with checked arithmetic (`checked_add`, `try_into` instead of `low_u64()` truncation) and bound `str_len` to a small sane maximum (e.g. ≤ 128 bytes for a BLS key) before using it in any addition/division.

### Proof of Concept
1. Craft a `ValidatorSetProof` where `storage_values[1]` (`activePoolSets` length) = 1, `storage_values[2]` = an arbitrary pool id, and `storage_values[3]` (the BLS header slot) is set to a 32-byte value whose lowest byte is odd and whose big-endian integer value is close to `U256::MAX` (e.g. `U256::MAX - 1`, which is odd).
2. Submit this as the unsigned Pharos consensus proof via the standard pallet-ismp consensus update path (the caller of `Pharos::verify_validator_set_proof`, `modules/consensus/pharos/verifier/src/lib.rs`, which was not fully traced in this session — I could not confirm the exact extrinsic/dispatch entry point due to remaining tool-call limits, but `verify_validator_set_proof` is the `ConsensusClient` verification routine invoked whenever a Pharos consensus message is relayed).
3. `compute_all_storage_keys` → `bls_data_slots_from_header` computes `length = (header_val - 1) / 2` (a huge `U256`), truncates via `low_u64()` to obtain `str_len`, then computes `(str_len + 31) / 32`; with `str_len` near `u64::MAX`, `str_len + 31` overflows `usize`, panicking the verification path in an overflow-checked build.

Note: I was unable to trace, within the remaining tool budget, the exact extrinsic or unsigned-transaction entry point that ultimately calls `verify_validator_set_proof` (only its definition site and callers list, not the dispatch wiring in `modules/consensus/pharos/verifier/src/lib.rs`, were inspected). If you need the precise dispatch call chain confirmed, a further pass reading `modules/consensus/pharos/verifier/src/lib.rs` and the `ConsensusClient` trait usage in `pallet-ismp` would be required.

pub fn verify_validator_set_proof<H: Keccak256 + Send + Sync>(
	state_root: H256,
	proof: &ValidatorSetProof,
	epoch: u64,
) -> Result<ValidatorSet, Error> {
	let layout = StakingContractLayout::default();

	// Recompute expected storage keys from the storage values
	let keys = compute_all_storage_keys::<H>(&proof.storage_values, &layout)?;

	// Verify each storage value against its per-key proof path.
	// Pharos uses a flat trie — storage proofs verify directly against state_root.
	verify_all_storage_proofs(&keys, &proof.storage_values, &proof.storage_proof, &state_root)?;

	// Decode the verified storage values into a ValidatorSet
	let decoded_set = decode_validator_set_from_storage::<H>(&proof.storage_values, epoch)?;

	validate_validator_set(&decoded_set)?;

	Ok(decoded_set)
}

pub fn bls_data_slots_from_header(header_value: &[u8]) -> Result<usize, Error> {
	let header_val = decode_u256_from_storage(header_value)?;
	let header_bytes = header_val.to_big_endian();
	let lowest_byte = header_bytes[31];

	if lowest_byte & 1 == 0 {
		// Short string - data is in the header itself
		Ok(0)
	} else {
		// Long string - header = length * 2 + 1
		let length = (header_val - 1) / 2;
		let str_len = length.low_u64() as usize;
		Ok((str_len + 31) / 32)
	}
}
