### Title
`computeTonConnectHash` writes UTF-16 code-unit length instead of UTF-8 byte length for `domain`, causing local hash to diverge from the TON Connect spec hash - ([File: packages/intents-sdk/src/intents/intent-hashes/ton-connect.ts])

### Summary
`computeTonConnectHash` builds the TON Connect sign-data message by writing `domain.length` (JavaScript UTF-16 code unit count) as the 4-byte big-endian length prefix, then concatenating `new TextEncoder().encode(domain)` (UTF-8 bytes). For any `domain` containing non-ASCII characters these two counts differ, so the locally computed message bytes — and therefore the SHA-256 hash — do not match the hash defined by the TON Connect `ton-connect/sign-data/` spec, which prefixes the actual UTF-8 byte length.

### Finding Description
The broken equality is:
`computeIntentHash(multiPayload)` (via `computeTonConnectHash`) `== intent_hash` returned by the relayer/contract for the same signed `ton_connect` MultiPayload.

In [1](#0-0)  the "text" branch builds the hashed message as:
```
numberToBigEndian(domain.length, 4)
new TextEncoder().encode(domain)
```
`domain.length` is the number of UTF-16 code units in the JS string, while `TextEncoder().encode(domain)` produces UTF-8 bytes. For ASCII-only domains these two values are numerically equal, so the bug is invisible in the existing test suite, which only exercises `"near.com"` [2](#0-1) . For any domain containing multi-byte UTF-8 characters (e.g. `"münchén.example"`), `domain.length` (15) is smaller than `new TextEncoder().encode(domain).length` (17, since `ü` and `é` each take 2 UTF-8 bytes but 1 UTF-16 code unit). The length prefix written into the hashed message is therefore wrong relative to the byte stream that actually follows it, producing a SHA-256 digest that differs from the correctly-spec'd hash (length prefix = UTF-8 byte length of `domain`, as documented in the function's own doc comment and the TON Connect protocol).

`computeSignedTonConnectHash` is called unconditionally from `computeIntentHashHashBytes`/`computeIntentHash` for any `standard: "ton_connect"` `MultiPayload` [3](#0-2) , with no validation anywhere in the codebase restricting `domain` to ASCII characters. There is no `assert`, `validateAddress`, or schema check on `domain`'s character set found in the repo that would prevent a non-ASCII value from reaching `computeTonConnectHash`.

### Impact Explanation
Because `computeIntentHash` is used by integrators to locally recompute the intent hash before/after publishing (e.g., to persist an expected hash in `onBeforePublishIntent` and compare it against `waitForIntentSettlement`), a wrong local hash for a non-ASCII `domain` means the SDK-computed hash will never equal the hash the actual TON Connect signing flow (and any correctly-implemented verifier) derives from the same signed payload. This breaks hash-based settlement tracking for the caller's own signed intent — the integrator's persisted "expected hash" mismatches the "actual settled hash", which per the audit's severity table constitutes a status/hash misreport that can cause a double-send or lost-track of already-signed funds.

### Likelihood Explanation
Preconditions: a `ton_connect` MultiPayload whose `domain` field contains any non-ASCII character (multi-byte in UTF-8) — e.g., an internationalized domain name rendered in native Unicode rather than punycode, or any non-ASCII string in that field. No special privilege is required: any user or app constructing a `ton_connect` signed payload with such a domain triggers the divergence on every call. It is fully repeatable and costs the attacker/affected user nothing beyond having a non-ASCII `domain` string in their own signed payload.

### Recommendation
Compute the length prefix from the actual encoded bytes rather than the JS string length:
```ts
const domainBytes = new TextEncoder().encode(domain);
...
numberToBigEndian(domainBytes.length, 4),
domainBytes,
```
and reuse `domainBytes` in the parts array instead of re-encoding `domain`.

### Proof of Concept
Vitest plan:
1. Construct two `MultiPayload` fixtures identical except `domain`: one ASCII (`"near.com"`), one non-ASCII (`"münchén.example"`), same `address`, `timestamp`, `payload: {type:"text", text:"hello world"}`.
2. Manually compute the "expected" spec-correct hash bytes by building the message with `domain_len = new TextEncoder().encode(domain).length` (i.e., the fixed logic) and compare with `sha256`.
3. Assert `computeTonConnectHash(nonAsciiPayload)` (current buggy code) `!==` the manually computed spec-correct hash — demonstrating `computeIntentHash(multiPayload) !== intent_hash` that a correct TON Connect verifier/relayer would produce for the same signed message.
4. Assert that for the ASCII-only fixture the two hashes are equal, confirming the bug is latent/undetected by existing tests and only manifests for non-ASCII domains.

export interface TonAddress {
	workchainId: number; // i32: typically 0 for base workchain, -1 for masterchain
	address: Uint8Array; // 32 bytes
}

/**
 * Convert number to big-endian byte array
 */
function numberToBigEndian(num: number, bytes: number): Uint8Array {
	const result = new Uint8Array(bytes);
	for (let i = bytes - 1; i >= 0; i--) {
		result[i] = num & 0xff;
		num >>= 8;
	}
	return result;
}

export function parseTonAddress(addressString: string): TonAddress {
	const parsed = tryParseTonAddress(addressString);
	if (parsed === null) {
		throw new Error(`Invalid TON address: ${addressString}`);
	}
	return parsed;
}
