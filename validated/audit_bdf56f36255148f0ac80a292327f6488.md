### Title
Pod Security Admission bypasses label validation and enforce-level pod re-check via Namespace `/status` (and `/finalize`) subresource updates - ([File: staging/src/k8s.io/pod-security-admission/admission/admission.go])

### Summary
`Admission.ValidateNamespace` unconditionally short-circuits to `sharedAllowedResponse` whenever `attrs.GetSubresource() != ""`, skipping all pod-security label validation and the `EvaluatePodsInNamespace` re-check. The Namespace registry strategies for the `status` and `finalize` subresources (`namespaceStatusStrategy.PrepareForUpdate` and `namespaceFinalizeStrategy.PrepareForUpdate`) reset `Spec`/`Status` back to the old values but do **not** reset `ObjectMeta` (labels/annotations), so `pod-security.kubernetes.io/*` labels submitted through a `/status` or `/finalize` update are actually persisted, unvalidated by PSA.

### Finding Description
`ValidateNamespace` begins with: [1](#0-0) 
This is intended to skip subresources such as `status`/`finalize` on the assumption that they cannot mutate metadata/labels. However, the actual namespace registry strategy does not enforce that assumption: [2](#0-1) [3](#0-2) 
Both `namespaceStatusStrategy.PrepareForUpdate` and `namespaceFinalizeStrategy.PrepareForUpdate` only overwrite `Spec` or `Status` from the old object; they leave `ObjectMeta` (including `.metadata.labels`) exactly as submitted by the client. Their `ValidateUpdate` methods (`ValidateNamespaceStatusUpdate`, `ValidateNamespaceFinalizeUpdate`) validate only status/finalizer semantics, not PSA label syntax or semantics: [4](#0-3) [5](#0-4) 

Consequently, a request such as `PUT/PATCH /api/v1/namespaces/{ns}/status` with a modified `metadata.labels` map (e.g., `pod-security.kubernetes.io/enforce: privileged` or an invalid value) reaches `ValidateNamespace` with `attrs.GetSubresource() == "status"`, hits the short-circuit at line 231-233, and is unconditionally allowed:
- No `PolicyToEvaluate` / label-format validation is performed (an attacker could even set syntactically invalid label values, since only the main-resource path invokes `invalidResponse` on decode errors).
- The `oldPolicy`/`newPolicy` comparison and `EvaluatePodsInNamespace` re-check (lines 245-306) are never executed, so lowering the enforce level does not trigger the normal warnings about existing pods violating the new/looser or stricter policy.
- Effectively the namespace's persisted PSA labels can be changed out-of-band from the "official" Update path that the rest of `ValidateNamespace` is designed to protect.

### Impact Explanation
This allows an authenticated identity holding only `update` on the `namespaces/status` (or `namespaces/finalize`) subresource of their own namespace — a narrower permission than full namespace `update` — to change the namespace's enforced Pod Security level without going through PSA's intended validation/re-check flow. This falls under Kubernetes' "Pod Security / admission bypass" bounty class: it enables silently weakening namespace-level enforcement (e.g., relaxing `enforce: restricted` to `enforce: privileged`) with no audit trail from the pods-affected re-check, and could allow subsequently creating privileged pods that would otherwise have been blocked.

### Likelihood Explanation
Exploitability requires the attacker to hold `update` verb specifically on the `namespaces/status` (or `namespaces/finalize`) RBAC resource for their namespace (a distinct RBAC resource string from plain `namespaces`). This is not granted by Kubernetes' built-in `admin`/`edit` ClusterRoles (which do not include cluster-scoped `namespaces` permissions at all), but it is a realistic configuration in self-service/namespace-as-a-service clusters that grant scoped Roles with `resourceNames: [<ns>]` on `namespaces`/`namespaces/status` to let tenants manage their own namespace metadata/finalizers, under the (incorrect) assumption that the status subresource cannot affect labels. Once such a Role exists, exploitation is deterministic and repeatable via a single API call.

### Recommendation
- In `namespace/strategy.go`, have `namespaceStatusStrategy.PrepareForUpdate` and `namespaceFinalizeStrategy.PrepareForUpdate` also reset `ObjectMeta` (labels/annotations) to the old object's values, so subresource updates cannot smuggle metadata changes.
- Defense in depth: in `Admission.ValidateNamespace`, do not blindly trust `attrs.GetSubresource() != ""`; instead compare old vs. new PSA labels regardless of subresource, or explicitly reject subresource requests that change `pod-security.kubernetes.io/*` labels.

### Proof of Concept
Integration test plan (`test/integration/apiserver/podsecurity` or `staging/src/k8s.io/pod-security-admission/admission`):
1. Create namespace `ns1` with `pod-security.kubernetes.io/enforce: restricted`.
2. Create a pod in `ns1` that would violate `enforce: privileged` semantics is not needed; instead create a privileged pod is blocked normally to confirm baseline enforcement.
3. Grant the test client a Role bound only to `update` on `namespaces/status` with `resourceNames: [ns1]` (no `namespaces` update).
4. As that client, `PATCH` (or `PUT`) `/api/v1/namespaces/ns1/status` with `metadata.labels["pod-security.kubernetes.io/enforce"] = "privileged"` (or an invalid value like `"bogus"`).
5. Assert the request succeeds (200) and `GetNamespace(ns1).Labels["pod-security.kubernetes.io/enforce"]` is now `"privileged"`/`"bogus"` — i.e., PSA did not validate or reject it via the main-resource path checks.
6. Assert no `EvaluatePodsInNamespace` warnings were returned (confirm via response `Warnings` being empty) even though existing pods would now be allowed that previously would not, demonstrating the enforcement re-check was skipped.
7. Follow up by creating a privileged pod in `ns1` and confirm it is now allowed, proving the enforce level was effectively lowered without triggering the normal namespace-update evaluation path.
