### Title
Malicious coin/pc mint at pool creation permanently freezes LP funds via atomic dual-token Withdraw - (File: `program/src/processor.rs`)

### Summary
`Initialize2` lets any unprivileged caller create a pool with two arbitrary SPL mints as `coin_mint`/`pc_mint`, with no validation that they correspond to a real market's base/quote assets. `process_withdraw` always transfers `coin_amount` and `pc_amount` atomically in the same instruction before burning LP tokens. If either mint is (or later becomes) a token that reverts on transfer, the entire `Withdraw` call reverts, and since burning LP happens only after both transfers succeed, LPs who deposited legitimate tokens alongside the malicious one can never retrieve either asset — permanently freezing their funds.

### Finding Description
`process_initialize2` unpacks `coin_mint`/`pc_mint` and only checks that they differ from each other; the `market_info` account is explicitly commented as "Just a seed for AMM account. Can be any account," so there is no on-chain check binding `coin_mint`/`pc_mint` to a real OpenBook/Serum market's base/quote assets: [1](#0-0) [2](#0-1) 

Both mints are recorded verbatim into `AmmInfo`: [3](#0-2) 

`process_withdraw` computes `coin_amount`/`pc_amount` from the LP share, then performs two `Invokers::token_transfer_with_authority` calls (one per token) followed by an LP `token_burn`, all in one instruction — if either `spl_token::instruction::transfer` invocation reverts (e.g., a malicious/upgraded token program logic that reverts on transfer to certain destinations, or a token that becomes non-transferable), the whole instruction reverts and the LP burn never happens: [4](#0-3) 

There is no alternate instruction path that lets an LP redeem only the "good" side of the pool or that lets the pool bypass the malicious token to recover the legitimate token; `process_deposit` and `process_withdrawpnl` follow the identical atomic dual-transfer pattern: [5](#0-4) [6](#0-5) 

This is the same root cause described in the report: an attacker (here, the unprivileged pool creator) pairs a legitimate token with a malicious/reverting token, and the atomic multi-token transfer logic causes any legitimate-token recovery to be blocked as long as the malicious token's transfer fails.

### Impact Explanation
Once an LP deposits into such a pool (lured by a legitimate-looking `coin` or `pc` side and a plausible/initially-working malicious counterpart), if the malicious mint starts reverting on transfer (which the token issuer fully controls, e.g. a pausable/blocklist-capable SPL-compatible token), the LP's `Withdraw` will unconditionally revert, permanently trapping both the malicious and the legitimate tokens inside the AMM vaults with no recovery instruction. This is a permanent freezing of LP funds, matching the "High" impact bar for the analog bug class.

### Likelihood Explanation
Likelihood is medium: it requires a malicious/deceptive pool creator to pick a reverting (or conditionally reverting) mint as one side of the pool at `Initialize2` time, and requires an LP to deposit without realizing the counterpart token is malicious. Since `Initialize2` performs no validation that mints correspond to a genuine market, and pool creation is fully permissionless and cheap, this is straightforward to set up as a honeypot pool.

### Recommendation
- Validate `coin_mint`/`pc_mint` against the referenced market's actual base/quote mints at `Initialize2` instead of treating `market_info` as an arbitrary seed account.
- In `process_withdraw` (and `process_withdrawpnl`), avoid a single atomically-coupled dual transfer; use low-level/CPI calls that allow partial success, or add a recovery path allowing an LP to burn LP tokens and receive only the non-malicious side's tokens if the other transfer fails.

### Proof of Concept
1. Attacker mints a normal SPL token `GOOD` and a custom token `EVIL` whose transfer instruction can be made to revert (e.g., via a frozen/close-authority-controlled account, or by using a token program variant that supports conditional transfer failure).
2. Attacker calls `Initialize2` (`program/src/processor.rs` `process_initialize2`) with `coin_mint = GOOD`, `pc_mint = EVIL`, seeding the pool with real `GOOD` liquidity and a small amount of `EVIL`; no check rejects this pairing beyond `coin_mint != pc_mint`.
3. A victim LP calls `Deposit`, adding more `GOOD`/`EVIL` in proportion, receiving LP tokens.
4. Attacker causes `EVIL` transfers to start reverting (e.g. freezes/closes the relevant token account state, or the token contract logic changes).
5. Victim calls `Withdraw`; `Invokers::token_transfer_with_authority` for the `EVIL` (pc) vault reverts, reverting the whole instruction before the LP burn — the victim's `GOOD` tokens (and LP position) are now permanently locked in the vault with no available instruction to recover them.
