### Title
POA Bridge withdrawal status matched by `assetId` only, causing status/hash misreport for batched same-token withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain status of a specific withdrawal (identified by `landingChain`, `index`, `withdrawalParams`, `tx`) by calling `findMatchingWithdrawal`, which selects the withdrawal record purely by comparing `assetId` to `nep141:${w.data.near_token_id}` — it does not use `index` or `destinationAddress`/`amount` to disambiguate. If a single NEAR intent transaction contains two or more `ft_withdraw` withdrawals of the same token (e.g., to two different destination addresses in the same batch), every `WithdrawalIdentifier` for that token resolves to the same first-matching record via `Array.prototype.find`.

### Finding Description
`findMatchingWithdrawal` in [1](#0-0)  is explicitly documented as matching by `assetId` only and not supporting multiple withdrawals of the same token in one transaction: [2](#0-1) 

`describeWithdrawal` calls this matcher without ever using `args.index` (or destination address/amount) to disambiguate between multiple same-asset withdrawals in the batch: [3](#0-2) 

The SDK's batch withdrawal API (`sdk.processWithdrawal` / `sdk.waitForWithdrawalCompletion` / `createWithdrawalCompletionPromises`) explicitly supports arrays of `WithdrawalParams` and constructs one `WithdrawalIdentifier` per entry (with distinct `index`) via `createWithdrawalIdentifiers`, then polls each independently through `watchWithdrawal`: [4](#0-3) [5](#0-4) 

Consequently, if a caller submits a batch containing two POA-bridge withdrawals of the same `assetId` (e.g., two `btc.omft.near` withdrawals to different Bitcoin addresses in one NEAR tx), both `WithdrawalIdentifier`s (index 0 and index 1) produce identical `describeWithdrawal` results — the same `status` and the same `transfer_tx_hash` — because `findMatchingWithdrawal` returns the first array element whose `near_token_id` matches, regardless of which logical withdrawal (index) is being queried. The equality broken is: *the status/txHash reported for withdrawal N must correspond to the on-chain outcome of withdrawal N*, not to whichever same-asset withdrawal happens to be first in the (explicitly documented as "unsorted") API response array (comment at line 318: "Response list is unsorted, so we match by assetId instead of index").

### Impact Explanation
An integrator building on this SDK (e.g., a custodial exchange or wallet crediting users after a "completed" withdrawal) that submits or observes a batch of same-token withdrawals would receive the *same* destination tx hash and completion status for two withdrawals that are, on-chain, two separate transfers to two separate addresses. This can lead to:
- A second withdrawal being reported "completed" with a tx hash that actually belongs to the first withdrawal, causing the integrator to credit/close out both withdrawals based on a single real on-chain event (double credit / double confirmation), even though only one of the two destination addresses actually received funds.
- If the first-matched record is `PENDING`/`FAILED` while a different, later withdrawal in the batch actually completed, the completed one could incorrectly be reported as pending/failed, potentially triggering unnecessary manual intervention or retries.

This matches the "a status or hash misreport making an integrator credit or refund twice" High-impact class, since the outcome reported for one withdrawal in a batch does not correspond to the actual on-chain event for that specific withdrawal.

### Likelihood Explanation
This is fully reachable via the public, documented batch APIs (`processWithdrawal`, `waitForWithdrawalCompletion`, `createWithdrawalCompletionPromises`) with `withdrawalParams` as an array — no malicious actor is required; a normal integrator issuing two withdrawals of the same POA-bridge asset in one batch triggers this deterministically. The code comment itself acknowledges the limitation ("multiple withdrawals of the same token in a single transaction are not supported"), confirming it is a known, real, reachable gap rather than a theoretical one — the bug is that it silently returns an incorrect but plausible-looking result instead of failing loudly or refusing to match ambiguous cases.

### Recommendation
- In `findMatchingWithdrawal`, detect ambiguity: if more than one withdrawal in `response.withdrawals` matches the given `assetId`, do not silently return the first match. Either:
  - Disambiguate deterministically (e.g., sort both the POA API's withdrawals and the batch's same-asset `withdrawalParams` by `amount`/`destinationAddress` as the existing comment suggests, and consistently map by position), or
  - Throw/return an explicit "ambiguous, cannot determine status" error/pending state so integrators do not silently miscredit funds.
- Add a runtime guard in `PoaBridge.describeWithdrawal` (or at the batch-orchestration layer in `sdk.ts`) that rejects/flags batches containing multiple POA-bridge withdrawals with identical `assetId`, until the API/matcher supports correct disambiguation.

### Proof of Concept
1. Build a batch withdrawal request with two `WithdrawalParams` for `RouteEnum.PoaBridge`, both with `assetId: "nep141:btc.omft.near"`, but different `destinationAddress` (`addrA`, `addrB`).
2. Submit via `sdk.processWithdrawal({ withdrawalParams: [w1, w2] })`, producing one NEAR intent tx with two `ft_withdraw` intents.
3. The POA bridge indexer settles both withdrawals; suppose it produces two `withdrawals` entries with different `transfer_tx_hash` (`hashA`, `hashB`) but identical `near_token_id: "btc.omft.near"`.
4. `sdk.waitForWithdrawalCompletion` calls `describeWithdrawal` for `WithdrawalIdentifier{index:0,...}` and `WithdrawalIdentifier{index:1,...}` separately.
5. Both calls invoke `findMatchingWithdrawal(withdrawals, "nep141:btc.omft.near")`, which uses `Array.prototype.find` and returns the same first record (e.g., the one with `hashA`) for both index 0 and index 1 — regardless of which one is actually `addrA`'s vs `addrB`'s completion. The test at [6](#0-5)  ("matches withdrawal by assetId, not by index") demonstrates this matching behavior directly, confirming that `index` plays no role in selecting the correct record.

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
