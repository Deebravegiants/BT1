Audit Report

## Title
Global, unauthenticated request-ID namespace in the ConfidentialRelay gateway handler lets any caller squat another user's in-flight request ID and deny their relay request - (File: core/services/gateway/handlers/confidentialrelay/handler.go)

## Summary
`HandleJSONRPCUserMessage` in the ConfidentialRelay handler performs only trivial length/emptiness validation on the caller-supplied `req.ID` before calling `newActiveRequest`, which inserts the request into a single shared `activeRequests` map keyed solely by that raw ID and rejects the insert if the key is already occupied. There is no authorization, allowlist, or ownership-binding step to scope the ID to a caller, unlike the sibling Vault handler pattern, allowing any caller reaching this method to pre-claim another party's request ID and cause their legitimate request to fail with "request ID already exists".

## Finding Description
`HandleJSONRPCUserMessage` validates only that `req.ID` is non-empty and ≤200 characters, then immediately calls `h.newActiveRequest(req, labels, callback)`: [1](#0-0) 

`newActiveRequest` locks the handler's mutex, checks whether `h.activeRequests[req.ID]` is already populated, and returns an error ("request ID already exists") if so — otherwise it inserts the new request keyed directly by the attacker-controlled `req.ID`, with no owner, workflow, or session identity mixed into the key: [2](#0-1) 

The dispatch path from the gateway's `multiHandler.HandleJSONRPCUserMessage` routes directly to this handler method based solely on the JSON-RPC `Method` field, with no intervening authorization step: [3](#0-2) 

This confirms the request-ID keyspace in `activeRequests` is a single global, first-come-first-served namespace with no per-caller scoping — any two callers whose requests share the same `req.ID` will collide, and the second to arrive is rejected outright. The project's own regression test, `TestConfidentialRelayHandler_DuplicateRequestID`, directly demonstrates this exact collision behavior: [4](#0-3) 

## Impact Explanation
This is a targeted denial-of-service: an actor who can predict or learn another party's request ID (e.g., from logs, telemetry, or execution-ID patterns) can pre-register that same ID, causing the legitimate request to be rejected before ever being fanned out to relay nodes, denying that specific relay/capability-exec request. This falls into a DoS/request-availability impact class rather than key/secret exfiltration, unauthorized fund movement, or authentication bypass — the request is denied, not hijacked, impersonated, or answered incorrectly.

## Likelihood Explanation
Exploiting this requires only reaching the gateway's ConfidentialRelay JSON-RPC methods (`MethodSecretsGet`, `MethodCapabilityExec`) and knowing or guessing the victim's `req.ID` before the victim's own request lands — the ID is a plain caller-chosen string with no cryptographic or ownership binding enforced by this handler before insertion. Whether this is exploitable by a fully unauthenticated external network attacker versus only by other authenticated/allowlisted DON participants depends on gateway-level connection authentication that occurs before user messages reach this handler; that authentication layer was not fully traceable within the available investigation, but even a semi-trusted or authenticated party lacking any specific authorization for a *particular other user's* request ID can still exploit this collision because the code shown provides no per-owner scoping regardless of how the caller connected.

## Recommendation
Scope the `activeRequests` key in the ConfidentialRelay handler to include an authenticated/authorized owner or workflow-execution identity component, rather than the raw caller-supplied `req.ID` alone — mirroring the pattern of binding request IDs to an authorized owner before insertion, as referenced for the Vault handler. At minimum, add an authorization or ownership check for `MethodSecretsGet`/`MethodCapabilityExec` so the request-ID namespace cannot be squatted by an unrelated caller.

## Proof of Concept
1. Attacker learns/guesses a request ID `X` that a legitimate workflow execution is about to submit via `MethodCapabilityExec`.
2. Attacker calls `HandleJSONRPCUserMessage` with `ID = X`; `newActiveRequest` succeeds and inserts `X` into `activeRequests`.
3. Legitimate caller's subsequent `HandleJSONRPCUserMessage` call with the same `ID = X` hits the existing-key check in `newActiveRequest` and is rejected with `"request ID already exists: X"`.
4. Reproduced directly by the existing test `TestConfidentialRelayHandler_DuplicateRequestID` in `core/services/gateway/handlers/confidentialrelay/handler_test.go` (lines 863–881), which issues the same `req.ID` twice and asserts the second call errors with "request ID already exists".

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	labels := h.extractRequestLabels(req)
	l := h.requestLogger(req, labels)
	l.Debugw("handling confidential relay request", "nodes", len(h.donConfig.Members), "f", h.donConfig.F)

	ar, err := h.newActiveRequest(req, labels, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
}

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], labels requestLabels, callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID, "executionID", labels.ExecutionID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		labels:    labels,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

func TestConfidentialRelayHandler_DuplicateRequestID(t *testing.T) {
	t.Parallel()
	h, cb, don, _ := setupHandler(t, 4)
	don.On("SendToNode", mock.Anything, mock.Anything, mock.Anything).Return(nil)

	params := json.RawMessage(`{"workflow_id":"wf1"}`)
	req := jsonrpc.Request[json.RawMessage]{
		ID:     "req-dup",
		Method: MethodCapabilityExec,
		Params: &params,
	}

	err := h.HandleJSONRPCUserMessage(t.Context(), req, cb)
	require.NoError(t, err)

	cb2 := common.NewCallback()
	err = h.HandleJSONRPCUserMessage(t.Context(), req, cb2)
	require.ErrorContains(t, err, "request ID already exists")
}
