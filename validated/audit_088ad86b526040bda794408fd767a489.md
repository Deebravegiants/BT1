### Title
Webhook shop identity not covered by HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` identity that the library extracts and hands to the app's handler is read from an HTTP header that is **not** part of the signed material. This breaks the binding: `hmac_verified(body) == true` does not imply `shop_header == shop_that_produced(body)`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The shop identity used by the rest of the pipeline is read from a header, entirely outside the signed content: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the metadata handed to the app's handler, without any additional binding between the header value and the signature: [3](#0-2) 

`HmacValidator.validate` performs `OpenSSL.secure_compare` strictly between the computed signature of `to_signable_string` (the body only) and the received signature — it has no knowledge of, and does not cover, `shop`, `topic`, `webhook_id`, or `api_version`: [4](#0-3) 

Because the `shop-domain` header is excluded from the signable string, any request bearing a **previously valid** `(body, hmac)` pair — for example a genuine webhook delivery the attacker's own shop received, which they fully control and can replay to the app's public webhook endpoint — will still pass `HmacValidator.validate`, and the attacker can freely choose the `shop-domain` header value sent alongside it. The gem passes that attacker-chosen `shop` straight through as an authenticated-looking identity to the handler:
```
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
```
This is the same class of bug described in the referenced report: an operation is gated on a check (HMAC / staticcall) that does not actually cover the field the rest of the logic treats as trusted (shop identity / storage state), so the binding `verified_bytes == acted_upon_bytes` silently fails to hold for that field.

### Impact Explanation
This is a **cross-tenant access** vector: if the host application uses `WebhookMetadata#shop` (as documented/intended) to decide which tenant's records to update, invalidate caches for, or attribute business events to, an attacker who legitimately receives webhooks for their own shop (any merchant that installs the app) can relabel those events as belonging to an arbitrary other `shop` value and have the app process them as authentic, without ever needing the app's `client_secret` or any other credential. This satisfies the "cross-tenant access" Critical impact category since no tenant-specific secret is required — only a genuine webhook the attacker already legitimately possesses for their own store.

### Likelihood Explanation
Likelihood is high for any consumer of this gem that reads `shop` off `WebhookMetadata`/`Request` post-HMAC-validation and trusts it (which is the documented usage pattern shown in the gem's own webhook docs/tests, e.g. `data.shop` in `test/webhooks/registry_test.rb`). No privileged access, TLS interception, or secret leakage is needed — only the ability to send an arbitrary HTTP request to the app's public webhook endpoint with a header value of the attacker's choosing and a body/HMAC pair the attacker already possesses from a webhook legitimately delivered to their own shop.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the signed material, or otherwise cryptographically tie the header-derived identity to the verified payload before it is trusted by handlers, e.g.:
- Since Shopify's own webhook HMAC scheme signs only the body, `Registry.process` (or `Request`) should not expose `shop`/`topic` as if they were authenticated by the HMAC check; alternatively, the library should independently confirm the `shop-domain` header against the topic's expected shop from an out-of-band, already-authenticated source (e.g., the registered session/store lookup) before dispatching, rather than passing the raw header value through untouched.
- At minimum, document prominently (and enforce where possible) that `shop`, `topic`, `api_version`, and `webhook_id` on `Webhooks::Request`/`WebhookMetadata` are **not** covered by the HMAC and must not be used for authorization or tenant-scoping decisions without additional verification (e.g., cross-checking against a known/registered shop for that specific webhook subscription).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and legitimately receives a real webhook delivery, e.g. body `{"id":123}` with a valid `x-shopify-hmac-sha256` header computed by Shopify over that body using the app's secret.
2. Attacker replays that exact `(body, hmac)` pair to the app's public webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body successfully (all required headers present).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `OpenSSL::HMAC.hexdigest(sha256, secret, raw_body)` against the supplied hmac — this still matches, since the body is unchanged.
5. `Registry.process` proceeds to call the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, i.e., the app now processes attacker-supplied data as an authentic event from `victim-shop.myshopify.com`.
