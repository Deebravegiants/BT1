### Title
Sell-side underflow in `Bonding.canGraduate` when `assetReserve` drops below the recovered virtual LT reserve — permanent freeze of curve selling ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.canGraduate` computes `realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair)` (Bonding.sol:692) with no check that `assetReserve >= virtualLtReserve`. Because `Bonding.sell` (Bonding.sol:598) calls `canGraduate(tokenAddress)` unconditionally on every single sell before executing the trade, any state where the pair's stored `assetReserve` sits below the launch-time virtual reserve turns every future sell into a reverting call, permanently bricking exit liquidity for that curve — analogous to the reported libheif bug class where an unchecked coordinate subtraction (`tile - offset`) underflows once an attacker-influenced transform (irot) pushes a value below its assumed floor.

### Finding Description
`Pair.swap` (`packages/contracts/src/Pair.sol:65-79`) enforces the K-invariant with an explicit `+1` slack on both sides:
```solidity
uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();
``` [1](#0-0) 

This slack is documented in `AGENTS.md` as an accepted design ("Pair.swap's `+1` K slack") and is what lets `Router._computeSell`/`_computeBuy`'s floor-rounded results always pass the check. The consequence is that the *actual* product `newTokenReserve * newAssetReserve` is permitted to land strictly below `k` by up to roughly `newTokenReserve + newAssetReserve`, and each sell computes `assetOut` purely from division rounding in `Router._computeSell`:
```solidity
uint256 newReserveToken = reserveToken + amountIn;
assetOut = reserveAsset - (k / newReserveToken);
``` [2](#0-1) 

`assetReserve` is only ever compared against the *launch-time* virtual reserve, recovered as `Pair.k() / Token.TOTAL_SUPPLY()` — a constant that never changes:
```solidity
function _launchTimeVirtualLtReserve(address token_, address pair_) internal view returns (uint256) {
    return IPair(pair_).k() / Token(token_).TOTAL_SUPPLY();
}
``` [3](#0-2) 

`canGraduate` subtracts this constant from the live stored `assetReserve` with no guard:
```solidity
(, uint256 assetReserve) = IPair(pair).getReserves();
uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
``` [4](#0-3) 

`previewLtUntilGraduation` performs the identical unguarded subtraction (Bonding.sol:722) and only added a guard for the *other* subtraction (`reserveToken - realBalance`, guarded at line 729) — the fix applied for the known donation-attack underflow (`test_donation_realBalanceExceedsReserveToken`) covered a different subtraction and did not extend the guard to `assetReserve - virtualLtReserve`.

Critically, `Bonding.sell` calls `canGraduate` on **every** sell, unconditionally, before the trade executes:
```solidity
if (canGraduate(tokenAddress)) revert TokenIsGraduating();
(, uint256 assetOut) = $.router.sell(amountIn, tokenAddress, msg.sender);
``` [5](#0-4) 

If `assetReserve` is ever driven below `virtualLtReserve` (via the K-invariant's `+1` slack accumulated across repeated buy/sell round-trips, or via legitimate sequences of sells that draw the stored `assetReserve` down through floor-division rounding), the subtraction at Bonding.sol:692 underflows and reverts inside `canGraduate`, which is called unconditionally at the top of every `sell`. This means **every subsequent sell on that curve reverts**, with no way to trade out — a permanent freeze of every trader's tokens on that curve. Because `canGraduate` is also invoked from `_executeBuy`'s post-trade hook (per `docs/contracts-scope.md`: "`Bonding.canGraduate()` is checked at the end of every buy"), the same underflow would also brick the buy path, freezing the entire curve.

### Impact Explanation
This is a permanent freezing of trader funds on the affected curve: once `assetReserve - virtualLtReserve` underflows, no unprivileged address can sell (or buy, since `canGraduate` is invoked post-buy too) through `Bonding`/`Zap` for that token. Tokens already bought are stuck; LT already raised on the curve becomes unreachable since graduation itself (`_prepareGraduationLiquidity`, Bonding.sol:1084) performs the exact same unguarded subtraction and would also revert, meaning the curve can neither trade nor graduate. This satisfies the "permanent freezing of trader funds" acceptance bar. Severity is High given the class-wide, permanent nature of the freeze once triggered.

### Likelihood Explanation
Reaching the specific integer state where `assetReserve` sits below the constant `virtualLtReserve` requires exploiting the intentionally-accepted `+1` K-invariant slack in `Pair.swap` across many buy/sell round trips (rounding losses accumulate on the asset side across repeated `_computeBuy`/`_computeSell` calls). All of the calls involved (`Bonding.buy`/`sell` via any allowlisted `Zap`) are reachable by any unprivileged trader; no privileged role is required. The likelihood is Medium: it depends on whether the accumulated rounding drift from the `+1` slack across realistic transaction counts is sufficient to cross the boundary before gas/economic cost makes it impractical — this was not fully provable analytically within available tools, but the code path itself is unguarded and directly reachable, unlike the previously-fixed `reserveToken - realBalance` underflow which received an explicit `>=` guard.

### Recommendation
Add the same defensive guard used for the supply leg to both `canGraduate`, `previewLtUntilGraduation`, and `_prepareGraduationLiquidity`: before computing `assetReserve - virtualLtReserve`, check `assetReserve >= virtualLtReserve` and treat any shortfall as `realLtRaised = 0` (mirroring the `realBalance >= reserveToken` guard already present at Bonding.sol:729). This eliminates the underflow revert path entirely and keeps `canGraduate`/`sell`/`buy` callable regardless of any residual K-invariant rounding drift.

### Proof of Concept
Conceptually (exact reproduction requires a Foundry harness against `Router._computeSell`/`Pair.swap`, not fully executed here due to tool constraints):
1. Launch a token via `Bonding.launch`/`Zap.createToken` with a seed buy, establishing `assetReserve == virtualLtReserve` at mint.
2. As an unprivileged trader, execute a large number of small buy-then-sell round trips through `Zap.buy`/`Zap.sell` (or directly through an allowlisted router as in `test_donation_realBalanceExceedsReserveToken`'s pattern), each of which is accepted by `Pair.swap`'s `(newTokenReserve+1)*(newAssetReserve+1) >= k` slack even though the true product may fall marginally below `k`.
3. After enough round trips, the stored `assetReserve` value drifts to just below the constant `virtualLtReserve = Pair.k()/TOTAL_SUPPLY()`.
4. Any further call to `Bonding.sell` (or a buy that lands on `canGraduate`'s post-trade check) reverts with a panic (arithmetic underflow) inside `canGraduate` at `assetReserve - _launchTimeVirtualLtReserve(...)`, permanently blocking all trading on the curve.
