### Title
Redeem drains real underlying pro‑rata to phantom interest, insolvency/freeze for last redeemer(s) - (File: `local-testing/contracts/vault/vault-*.clar`, function `redeem`, `total-assets`/`total-assets-preview`)

### Finding Description
The broken identity: `sum_i(convert-to-assets-preview(shares_i))` at each successive redeem call must satisfy `<= ubalance()` at that moment. Once a debt/borrowed gap opens (`total-debt > total-borrowed` with no real backing, per any earlier phantom‑interest trigger), this identity is violated across a sequence of redemptions.

`total-assets`/`total-assets-preview` add unbacked interest into the accounting numerator: [1](#0-0) 

`convert-to-assets-preview` uses this inflated `ta` to compute each redeemer's payout: [2](#0-1) 

`redeem` gates the payout only against the internal `assets` variable (and `assets - total-borrowed`), never against the real token balance `ubalance()`, and then unconditionally transfers real underlying via `send-underlying`: [3](#0-2) 

`get-available-assets` is likewise computed from the accounting vars `assets`/`total-borrowed`, not `ubalance()`: [4](#0-3) 

Root cause: once `interest = total-debt - total-borrowed > 0` is phantom (not backed by any real token inflow), it inflates `ta` used to price every share for every redeemer, but the `assets` variable that both the `>= current-assets inkind` guard and `var-set assets (- current-assets inkind)` bookkeeping operate on tracks only real principal-side accounting, decremented one‑for‑one by each `inkind` actually paid out in real tokens. As long as `current-assets >= inkind` holds (checked before `send-underlying`), the transfer proceeds and pays the phantom-inflated `inkind` out of the *shared, real* underlying balance. Because the phantom `interest` amount does not shrink when assets are paid out (it depends only on `total-debt`/`total-borrowed`, untouched by redemptions), successive redeemers keep pricing their shares against a `ta` that still contains the same absolute phantom component while the real `assets`/`ubalance()` pool has already shrunk. Early redeemers who happen to call first capture their full, phantom-inflated share in real tokens; the shrinking real pool combined with an undiminished phantom `interest` numerator guarantees that at some point `inkind > current-assets` for a later caller, tripping `ERR-INSUFFICIENT-ASSETS` (or, if that guard is somehow satisfied, `send-underlying`'s underlying FT/STX transfer itself fails for lack of real balance). Either way the last redeemer(s) cannot be paid: the outcome is a hard revert (freeze) for them, while earlier redeemers extracted real value the vault never actually held.

No check anywhere in `redeem`, `get-available-assets`, or `total-assets` compares against `ubalance()` to prevent this: the guards are entirely self-referential to the vault's own (corruptible) `assets`/`total-borrowed` variables, so once those variables' relationship to `total-debt` is broken by any of the earlier phantom-interest triggers, the CUSTODY invariant `sum(payouts) <= ubalance()` is not enforced by the code, only by accident of ordering (who redeems first).

### Impact Explanation
Every redeemer before the divergence point is paid in full, including a slice of the phantom interest, in real underlying tokens taken from the shared pool. This is a wealth transfer from later redeemers to earlier ones and, at the margin, either: (a) a full revert/freeze for the last redeemer(s) whose `inkind` now exceeds the depleted `current-assets`, or (b) if the accounting check happens to still pass, an underlying-token transfer failure inside `send-underlying`. In both cases the practical effect is permanent freezing of the remaining shareholders' funds/insolvency: they hold zft shares that can never be redeemed at their nominal `convert-to-assets` value because the real backing was already paid out to earlier callers. This matches Critical severity (protocol insolvency / permanent freezing of funds), and the loss is fully repeatable for however many share holders exist once the precondition gap is present; the party bearing the loss is whichever shareholder(s) redeem last.

### Likelihood Explanation
This finding is entirely contingent on the stated precondition — a `total-debt > total-borrowed` gap opened by one of the separately-scored phantom-interest triggers. Given that precondition, no additional attacker privilege or capital is required beyond being an ordinary shareholder (or several colluding/uncoordinated ones) calling the public `redeem` function in the normal way; front-running to be first in line is trivial and costs only transaction fees. The mechanism is deterministic and reproducible every time the gap exists and more than one holder attempts to redeem.

### Recommendation
Cap `total-assets`/`total-assets-preview`'s "phantom" interest component by the real token balance, i.e., bound `interest` (and therefore `ta`) so it can never imply backing beyond `ubalance()`; alternatively, enforce `(<= inkind (ubalance-minus-obligations))` as an explicit guard in `redeem` in addition to the existing `current-assets`/`available-assets` checks, so that no payout is allowed to exceed the vault's actual real token holdings regardless of what the internal accounting variables claim.

### Proof of Concept
Clarinet/vitest simnet plan:
1. Initialize vault, have holders A, B, C each deposit equal amounts, recording `ubalance()` (= real token balance) and each `convert-to-assets-preview(shares)`.
2. Trigger a `total-debt > total-borrowed` gap via any established phantom-interest trigger (e.g., a repay/accrual sequence from a prior finding that decrements `total-borrowed` without a matching decrease in `total-debt`/index, or vice versa) so `total-assets() > ubalance()`.
3. Have A call `redeem` for all of A's shares; assert the call succeeds and `send-underlying` transfers `inkind_A = convert-to-assets-preview(sharesA)` in real tokens, and assert `inkind_A` includes a portion attributable to the phantom `interest` term (i.e., `inkind_A / sharesA > (ubalance()_before / total-supply()_before)`).
4. Have B redeem next; assert B likewise receives a phantom-inflated payout.
5. Have C (last redeemer) call `redeem`; assert the transaction reverts with `ERR-INSUFFICIENT-ASSETS` (or the underlying transfer fails), while `get-balance-internal(C)` still shows unredeemed zft shares — i.e., C's funds are frozen.
6. Assert numerically that `inkind_A + inkind_B > ubalance()_genesis + any real repayments received`, proving the CUSTODY identity `sum(payouts) <= ubalance()` was violated before C's call.
