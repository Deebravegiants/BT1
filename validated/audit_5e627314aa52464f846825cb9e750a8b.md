### Title
Simplex venue pricing consumes a single-block, unguarded Uniswap V4 spot price to size intent fills - ([File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts])

### Summary
The Jimbo report is a "protocol-specific price manipulation" where an attacker flashloan-manipulates a concentrated-liquidity AMM's active bin/spot price within a single transaction and forces the protocol's own logic (`shift`/`reset`) to act on that manipulated spot state before it can revert, extracting value. The Hyperbridge/Simplex analog is `UniswapV4FundingPlanner.getExoticTokenPrice` / `computeDirectPoolPriceUsd`, which prices "curveless" cross-asset intent legs directly off a Uniswap V4 pool's live `sqrtPriceX96` (a single, current-block spot read) with no TWAP, no size/impact term, and — unless the operator opts into `referencePrice`/`maxDeviationBps` — no deviation check at all.

### Finding Description
`resolveLegRates` prices a curveless pair (no `bidPriceCurve`/`askPriceCurve`) by calling `venuePriceMemo()` → `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice`, which selects the most-liquid qualifying pool and returns `computeDirectPoolPriceUsd`, the **raw pool mid derived from `sqrtPriceX96`**: [1](#0-0) [2](#0-1) 

The flow doc explicitly confirms there is no fee-tier or price-impact adjustment, and the only defense — `checkPriceGuard` — checks deviation from a static, operator-configured reference price, not execution cost or manipulation resistance: [3](#0-2) 

Documentation further states the guard is **optional**: `referencePrice`/`maxDeviationBps` "must be set together; omit both to leave the chain unguarded." [4](#0-3) 

This mirrors the Jimbo bug class precisely: a pricing/settlement decision is derived from a live, single-transaction-manipulable AMM state variable (Jimbo's `getActiveId()`/bin reserves; here `slot0.sqrtPriceX96`), and the only mitigation (Jimbo's `triggerBin`/`anchorBin` thresholds; here the optional static reference-price guard) does not defend against a flash/same-block price move because it is either unconfigured or compares to a stale static number rather than a TWAP.

### Impact Explanation
An attacker who can move a thin/qualifying Uniswap V4 exotic↔USDC/USDT pool's spot price within one transaction (flashloan swap) and then, in the same block, gets an order filled by the Simplex solver against that manipulated `getExoticTokenPrice()` value can force the solver to price and fund a fill far off the fair market rate. Because `computeLegPolicyOutput` linearly extends the manipulated mid across the whole quantity with no size/impact term, the solver can be made to deliver far more of the exotic token than the input is worth, draining solver-held Uniswap V4 LP inventory (`planWithdrawalForToken` atomically withdraws from the position to fund the fill). This is a direct theft of solver/vault funds, reachable by any unprivileged intent submitter (the "phantom"/fill order path) without any privileged role.

### Likelihood Explanation
Likelihood is contingent on operator configuration: pairs relying on curves are unaffected, and pairs with `referencePrice`/`maxDeviationBps` configured are bounded to that deviation window (though still using a single spot read rather than a TWAP, so an attacker within the allowed deviation band can still repeatedly extract the guard's slack). Pairs configured for pool-based pricing **without** the optional guard (a state the docs explicitly allow: "omit both to leave the chain unguarded") are fully exposed to same-block manipulation, matching Jimbo's precondition (thin/controllable liquidity pool, single-tx manipulation, then protocol acts on manipulated state).

### Recommendation
- Make the Uniswap V4 price guard (`referencePrice`/`maxDeviationBps`) mandatory whenever pool-based pricing is used, rather than optional.
- Replace or supplement the instantaneous `sqrtPriceX96` spot read with a TWAP/observation-based price, or require checking against an external oracle before sizing a fill.
- Add a price-impact/liquidity-depth term to `computeLegPolicyOutput` so large fills against a given pool's depth are penalized rather than priced linearly off the mid.
- Consider bounding order size relative to the sourcing pool's available liquidity so a single order cannot be sized to profit from a feasible flash manipulation.

### Proof of Concept
Conceptual, mirroring the Jimbo PoC structure:
1. Attacker flashloans capital and swaps heavily against the exotic/USDC Uniswap V4 pool configured under `[vault.uniswapV4]` for a curveless pair, moving `sqrtPriceX96` far from fair value within the same transaction/block.
2. Attacker (or an accomplice bid) submits/triggers an intent order on the affected pair sized so that `getExoticTokenPrice` (read live via `UniswapV4LiquidityState.refresh()` at fill time) returns the manipulated price, with no `referencePrice`/`maxDeviationBps` configured (or within its slack).
3. Simplex's `FXFiller.quotePhantomFill` → `resolveLegRates` → `computeLegPolicyOutput` prices the fill at the manipulated mid and `UniswapV4FundingPlanner.planWithdrawalForToken` atomically withdraws exotic-token liquidity from the solver's LP position to fund it.
4. Attacker reverses the initial swap in the same transaction (or immediately after, since the fill is atomic within the ERC-7821 batch), realizing the price manipulation profit at the solver's expense, and repays the flashloan. [5](#0-4)

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

# Venue pricing (Uniswap V4 funded pairs)

Verified 2026-08-19.

```
resolveLegRates(...)
  curveless pair && token0 is a USD stable
    -> venuePriceMemo() -> getVenueUsdPrice(chain, token1)
         -> UniswapV4FundingPlanner.getExoticTokenPrice
              picks the position with the largest pool liquidity
              -> computeDirectPoolPriceUsd -> sdkPool.token0Price / token1Price
    -> checkPriceGuard(...)   reject if outside maxDeviationBps of the static reference
    -> rate = 1 / venueUsd
  otherwise -> the pair's ask/bid curve at the leg's notional
```

`computeDirectPoolPriceUsd` returns the **raw pool mid** derived from `sqrtPriceX96`. The pool's
fee tier is read and stored on the hydrated position (`pos.fee`) but never applied to the price,
and there is no size or impact term — `computeLegPolicyOutput` extends the mid linearly across the
whole priced quantity. `checkPriceGuard` is the only defense on this path, and it checks deviation
from a static reference, not execution cost. A venue-priced pair that has to swap through its own
pool to source inventory pays a fee tier it never quoted against.

```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```
