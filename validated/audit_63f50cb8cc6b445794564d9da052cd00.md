Audit Report

## Title
Cross-workflow HTTP response cache poisoning in gateway HTTP capability handler (missing `WorkflowID` scoping) - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

## Summary
The gateway's `responseCache` is a single map shared across all workflows served by a `gatewayHandler`, keyed only by `req.Hash()`, which per the test suite depends on `WorkflowOwner` but not `WorkflowID`. This lets any workflow sharing the same `WorkflowOwner` as a victim workflow poison or read the victim's cached outbound HTTP action responses, contradicting the documented "Workflow Isolation" guarantee.

## Finding Description
`newResponseCache` creates one `cache map[string]*cachedResponse` per `gatewayHandler` instance, shared across every workflow processed by that handler <cite repo="Alyssadaypin/chainlink--004" path="core/services/gateway/handlers/capabilities/v2/response_cache.go" start="17,31" end="24,38" />. `Set` and `Fetch` key exclusively on `req.Hash()` <cite repo="Alyssadaypin/chainlink--004" path="core/services/gateway/handlers/capabilities/v2/response_cache.go" start="110,66" end="120,77" />, and `isCacheableStatusCode` caches both 2xx and 4xx bodies [2](#0-1) . `makeOutgoingRequest` in `http_handler.go` unmarshals `OutboundHTTPRequest` directly from a node-forwarded JSON-RPC result and calls `responseCache.Fetch`/`Set` with attacker-influenced `CacheSettings` <cite repo="Alyssadaypin/chainlink--004" path="core/services/gateway/handlers/capabilities/v2/http_handler.go" start="404,433" end="411,442" />. The `response_cache_test.go` unit tests demonstrate that `Hash()` is invariant to `WorkflowID` but sensitive to `WorkflowOwner` [1](#0-0) , directly contradicting the component's own README, which claims cache keys are "Generated from workflow ID and request hash" and that entries are "scoped by workflow ID to prevent cross-workflow data leakage" [3](#0-2) . No other layer (rate limiters, mTLS handling, org resolver) re-introduces per-workflow cache partitioning — the rate limiters operate on `nodeAddr`/global scope, not per-workflow-cache [4](#0-3) , so nothing prevents the collision once method/URL/headers/body/owner match.

## Impact Explanation
This maps to cross-user response confusion: a workflow can cause another workflow (same owner) to receive a cached response it did not itself fetch, including a 4xx error body or an attacker-shaped 2xx payload, corrupting downstream workflow logic or leaking response content across otherwise logically distinct workflow deployments. This is a real, code-verifiable violation of the documented workflow-isolation guarantee, not a hypothetical one.

## Likelihood Explanation
Exploitation requires the attacker to control a workflow deployed under the same `WorkflowOwner` as the victim workflow, and to predict/match the exact outbound request shape (method, URL, headers, body) with `CacheSettings.Store=true`/`MaxAgeMs>0`. This is a realistic multi-workflow deployment scenario (one owner running several workflows, some possibly less trusted, e.g., third-party workflow code deployed under one owner address) rather than a cross-owner attack, since `WorkflowOwner` is part of the hash and does segment across owners.

## Recommendation
Include `WorkflowID` in `OutboundHTTPRequest.Hash()` (upstream in `chainlink-common`) or otherwise partition `responseCache`'s map/keys by `WorkflowID` in addition to the existing hash, so cache entries are strictly isolated per workflow as the README already documents. Update `response_cache_test.go:139-149` to assert differing `WorkflowID` produces differing hashes/cache keys, and consider excluding 4xx bodies from caching unless explicitly opted into per workflow.

## Proof of Concept
1. Deploy Workflow A and Workflow B under the same `WorkflowOwner` but different `WorkflowID`.
2. Workflow A issues `OutboundHTTPRequest{Method:"GET", URL:"https://api.example.com/data", CacheSettings:{Store:true}}`; `makeOutgoingRequest` calls `h.responseCache.Set(req, outboundResp)` keyed by `req.Hash()` [5](#0-4) .
3. Workflow B issues an identical `OutboundHTTPRequest` (same method/URL/headers/body/owner, different `WorkflowID`) with `CacheSettings.MaxAgeMs>0`; `Fetch` returns Workflow A's cached response via the same map key [6](#0-5) .
4. Confirm with a Go unit test analogous to `response_cache_test.go:139-149`, asserting that `rc.Set(reqA, respA)` followed by `rc.Fetch(ctx, reqB, ...)` (reqB differing only in `WorkflowID`) returns `respA` without invoking the fetch callback.
