### Title
Duplicate token addresses in `CircomData.erc20TokenAddresses` cause the same on-chain UTXO commitment to be inserted twice into the Merkle tree, minting unbacked shielded value - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact()` iterates `circomData.erc20TokenAddresses` and, for each index, re-scans the entire `utxoSet` returned by an external action to find matching entries by token address, accumulating `utxoAmount` and copying the matched UTXO into `onChainCommitments`. Nothing in `dimensionsCheck`/`checkOnchainCreation` (in `HinkalHelper.sol`) enforces that `erc20TokenAddresses` contains unique addresses. If the same token address appears at two indices, a single real UTXO produced by an external action gets matched and re-inserted into `onChainCommitments` twice, and both copies are written into the Merkle tree via `insertCommitments`, producing two independently spendable leaves for value that is backed by only one real token balance change.

### Finding Description
In `contracts/Hinkal.sol` (`transact`), the balance/UTXO accounting loop is: [1](#0-0) 

For index `i`, `utxoAmount` is computed by scanning the *whole* `utxoSet` for entries whose `erc20Address` matches `circomData.erc20TokenAddresses[i]`, and each match is copied into `onChainCommitments[onChainCommitmentCounter++]`. If `erc20TokenAddresses` contains the same token at two indices (e.g. index 0 and index 1), the *same* single `utxoSet[j]` entry matches at both outer iterations, so:
- `utxoAmount` at index 0 counts it once, and `utxoAmount` at index 1 counts the identical entry again.
- `onChainCommitments` receives **two separate slots** both built from the same `utxo` via `createOnchainCommitment`, one per matching outer iteration.

`HinkalHelper.dimensionsCheck` only checks array-length consistency, never uniqueness of `erc20TokenAddresses`: [2](#0-1) 

Setting `onChainCreation[i] = true` at both duplicate indices forces `amountChanges[i] == 0` (enforced in `checkOnchainCreation`), so the balance equation for each duplicate index reduces to `balanceDif == 0 + utxoAmount(i)`. Because `oldBalances`/`newBalances` are queried once for the whole transaction (not per index) via `getBalancesForArray`, `balanceDif` for both duplicate indices is identical — the single real balance change from the external action's swap: [3](#0-2) 

Since the same single `utxoSet` entry naturally satisfies `utxoAmount == balanceDif` at *both* duplicated indices, both per-index checks pass trivially, and both copies of the commitment get pushed into `onChainCommitments`, which is passed unmodified into `insertCommitments`: [4](#0-3) 

`insertCommitments` has no deduplication logic — it simply flattens `onChainCommitments` into `leaves` and calls `insertMany`, inserting **both** copies as distinct tree leaves via `insertMany`/`NewCommitment` events. Each leaf is independently valid: it hashes `(amount, erc20Address, stealthAddress, timeStamp)` via `hash4`, and both duplicate commitments carry the identical `utxo` fields (same amount, same stealth address, same timestamp), so both are separately spendable in a future `transact()` call using a proof against either leaf/root pair, as long as one of the two duplicate leaves is nullified with a distinct nullifier value chosen by the depositor for each separate future spend (the `nullifiers` mapping only prevents reuse of the *same* nullifier value, not spending two independent leaves that represent the same backing asset).

This breaks the core equality the protocol depends on: total value represented by spendable on-chain commitments must not exceed the actual token balance held by `Hinkal` corresponding to that value. Here, one real deposit of value `V` (from a swap/external action) results in **two** independently spendable leaves of value `V` each, i.e. `2V` of shielded claims backed by only `V` of real assets.

### Impact Explanation
This is unbacked minting of shielded value / effectively a double-spend of protocol-held assets: an attacker who controls (or colludes with) the external action to produce a UTXO set matching a duplicated token address can create two on-chain commitments from one real balance change, then later withdraw/spend both leaves for a combined value double the actual backing asset. This matches the "Critical" category: minting shielded value without backing / double spend.

### Likelihood Explanation
Exploitability depends on being able to route a transaction through `_externalTransact` (an external action such as a swap adapter) that returns a `utxoSet` with an entry for a token address that the attacker also duplicates in `circomData.erc20TokenAddresses`, and satisfying the ZK proof for that `CircomData` (the caller fully controls `CircomData` and must produce a valid Groth16 proof consistent with the public inputs built by `CircomDataBuilder.formInputForCircom`). Whether the circuit itself constrains `erc20TokenAddresses` to be unique per transaction could not be fully confirmed here since `circuits/**` template details for this specific transaction shape were not inspected in this pass; if the circuit does not enforce uniqueness of token addresses across indices (which appears architecturally plausible given the Solidity side performs no such check), the on-chain loop shown above provides a concrete path to double-inserting a commitment for a single backing balance change.

### Recommendation
- **Short term:** In `HinkalHelper.dimensionsCheck`, require that `circomData.erc20TokenAddresses` contains no duplicate addresses (or, in `Hinkal.transact`, ensure each `utxoSet[j]` entry is matched/consumed by at most one index `i`, e.g. by marking matched entries and skipping already-consumed ones, or by restructuring the UTXO-to-token matching to be a single pass keyed by unique token rather than re-scanning per index).
- **Long term:** Add explicit constraints in the corresponding Circom template enforcing uniqueness of token addresses within a single transaction's public inputs, and add an on-chain/off-chain invariant check that the sum of newly inserted on-chain commitment amounts per token never exceeds the actual measured balance delta for that token in the same transaction.

### Proof of Concept
1. Attacker crafts `CircomData` with `dimensions.tokenNumber = 2`, `erc20TokenAddresses = [T, T]` (same token duplicated), `onChainCreation = [true, true]`, `amountChanges = [0, 0]` (satisfying `checkOnchainCreation`'s zero-amountChanges requirement for onchain creation).
2. `circomData.externalActionData` points to an external action (e.g. a swap adapter) whose `runAction` returns a single `UTXO` for token `T` with `amount = V`, reflecting one real net balance increase of `V` in `Hinkal`'s holdings of `T`.
3. In `Hinkal.transact`, the outer loop over `erc20TokenAddresses` processes index 0: it scans `utxoSet`, finds the single UTXO for `T`, sets `utxoAmount = V`, and writes `onChainCommitments[0] = createOnchainCommitment(utxo, ...)`.
4. The loop processes index 1 (duplicate `T`): it re-scans the *same* `utxoSet`, matches the identical UTXO entry again, sets `utxoAmount = V`, and writes `onChainCommitments[1] = createOnchainCommitment(utxo, ...)` — an identical copy.
5. Both per-index balance checks (`balanceDif == 0 + utxoAmount`) pass since `balanceDif = V` (measured once globally) equals `utxoAmount` at both indices.
6. `insertCommitments(..., onChainCommitments, ...)` inserts **both** identical commitments as two distinct Merkle leaves via `insertMany`.
7. The attacker now holds knowledge of secrets for two independently spendable leaves, each provably worth `V` of token `T`, while `Hinkal` only actually received `V` of `T` from the external action — enabling a future withdrawal of `2V` total against `V` of real backing. [5](#0-4) [6](#0-5)

    function insertCommitments(
        uint256[][] memory offChainCommitments,
        bytes[][] memory offChainEncryptedOutputs,
        OnChainCommitment[] memory onChainCommitments,
        bool[] memory onChainCreation
    ) internal {
        // 1) Total Length of Commitments
        uint256 length = 0;
        for (uint256 i = 0; i < offChainCommitments.length; i++) {
            for (uint256 j = 0; j < offChainCommitments[i].length; j++) {
                if (onChainCreation[i]) break;
                length += offChainCommitments[i][j] != 0 ? 1 : 0;
            }
        }
        length += onChainCommitments.length;

        if (length > 0) {
            // 2) Flattening leaves array
            uint256[] memory leaves = new uint256[](length);
            uint256 index = 0;
            for (uint256 i = 0; i < offChainCommitments.length; i++) {
                for (uint256 j = 0; j < offChainCommitments[i].length; j++) {
                    if (onChainCreation[i] == true) break;
                    if (offChainCommitments[i][j] != 0) {
                        leaves[index++] = offChainCommitments[i][j];
                    }
                }
            }
            for (uint256 i = 0; i < onChainCommitments.length; i++) {
                leaves[index++] = onChainCommitments[i].commitment;
            }

            // 3) Inserting Leaves
            uint256[] memory insertedIndexes = insertMany(leaves);

            // 4) Emitting Commitments/EncryptedOutputs
            index = 0;
            for (uint256 i = 0; i < offChainEncryptedOutputs.length; i++) {
                for (uint256 j = 0; j < offChainEncryptedOutputs[i].length; j++) {
                    if (onChainCreation[i] == true) break;
                    if (offChainCommitments[i][j] != 0) {
                        emit NewCommitment(
                            leaves[index],
                            int256(insertedIndexes[index]),
                            offChainEncryptedOutputs[i][j]
                        );
                        index++;
                    }
                }
            }
            for (uint256 i = 0; i < onChainCommitments.length; i++) {
                emit NewCommitment(
                    leaves[index],
                    -1 * int256(insertedIndexes[index++]),
                    abi.encode(
                        onChainCommitments[i].utxo,
                        onChainCommitments[i].onChainEncryptedOutput
                    )
                );
            }
        }
    }
