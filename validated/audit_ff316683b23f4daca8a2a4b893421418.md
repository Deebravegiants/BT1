### Title
Missing relayer authorization gate in Tron `IntentGatewayV2.onAccept` allows unauthorized RedeemEscrow/RefundEscrow message delivery - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The EVM `ExtrinsicIntents.onAccept` requires `_checkRelayer(incoming.relayer)` before processing any `RequestKind`, gating who may deliver an incoming ISMP post request to the intents application [1](#0-0) . The Tron variant of the same contract, `IntentGatewayV2.onAccept`, omits this relayer check entirely and only checks `onlyHost`/source authentication before dispatching `RedeemEscrow`/`RefundEscrow` withdrawals [2](#0-1) . This is directly analogous to the "agent-mode dispatch ignoring the toolsAllow policy check" bug class in the external report: a dispatch code path exists that skips a policy/authorization gate enforced elsewhere in the same logical flow.

### Finding Description
`ExtrinsicIntents.onAccept` (the reference/EVM implementation) enforces `_checkRelayer(incoming.relayer)` as the very first authorization step after `onlyHost`, before any `RequestKind` is even decoded [1](#0-0) . Per the documented flow, "a delivery from anyone but the authorised relayer never decodes the body, never runs `_authenticate`, and leaves no receipt" [3](#0-2) . This relayer gate is a deliberate second line of defense on top of `HandlerV2`/`EvmHost.dispatchIncoming`, which itself uses `_msgSender()` as the "claimed relayer" with no cryptographic guarantee that it's the real relayer.

The Tron port of the intents application, `evm/tron/contracts/apps/IntentGatewayV2.sol`, implements the corresponding `onAccept` but never calls an equivalent relayer check — it goes straight from `onlyHost` to `RequestKind` decoding and `authenticate(incoming.request)` for the escrow paths [2](#0-1) . No `_checkRelayer`, `checkRelayer`, or `_relayer` state reference exists anywhere in that file. Since `EvmHost.dispatchIncoming` (or its Tron-host equivalent) trusts whatever address the caller supplies as `relayer` when `IApp.onAccept` is invoked, and the honest handler on EvmHost only restricts *who* can call `dispatchIncoming` (`restrict(_hostParams.handler)`) — not what relayer address is reported — the missing per-application relayer check on Tron means the `authenticate`/withdrawal path in `onAccept` is reachable by any caller who can get a message accepted by the host, without the additional relayer-authorization layer the EVM contract enforces.

### Impact Explanation
If the host's relayer-reporting mechanism on Tron can be influenced by an unprivileged party (e.g., a permissionless `handlePostRequests`-style call where `_msgSender()` becomes the reported relayer, as on the EVM `HandlerV2`), the missing gate on `IntentGatewayV2.onAccept` removes a defense-in-depth authorization check specifically designed to restrict which relayer may trigger escrow redemption/refund logic. This maps to "unauthorized app action" — a lower-trust caller performing an action (triggering `withdraw`) that the analogous EVM contract requires a specific authorized relayer for. Given intents gateways move escrowed user/solver funds, bypassing this layer weakens the guarantees around fund release.

### Likelihood Explanation
Likelihood depends on whether the Tron host's dispatch path also allows an arbitrary caller to report the relayer identity for a delivered message (as `HandlerV2`/`EvmHost` do via `_msgSender()`). Given the Tron contract is a near-verbatim port of `ExtrinsicIntents.sol` (same struct types, same `RequestKind` enum, same `authenticate`/`withdraw` flow) but is missing this one authorization line, it is highly likely an intentional check was dropped during the port rather than an intentional relaxation, since no compensating check exists elsewhere in the file.

### Recommendation
Add the same relayer-authorization gate used in `ExtrinsicIntents.onAccept` (`_checkRelayer(incoming.relayer)` or Tron equivalent) as the first check inside `IntentGatewayV2.onAccept` in `evm/tron/contracts/apps/IntentGatewayV2.sol`, before decoding `RequestKind`, so the Tron deployment matches the authorization model of the EVM reference contract.

### Proof of Concept
1. Deploy `IntentGatewayV2.sol` (Tron) bound to a host whose `dispatchIncoming`-equivalent reports the caller's `msg.sender` as the relayer (mirroring `EvmHost.dispatchIncoming` at `evm/src/core/EvmHost.sol:794-818`, which is `restrict(_hostParams.handler)` only, not gated on relayer identity).
2. An attacker (not the configured relayer) submits a valid proof through the host's handler equivalent for a `RedeemEscrow`/`RefundEscrow` post request addressed to `IntentGatewayV2`.
3. Because `IntentGatewayV2.onAccept` never calls a relayer check (unlike `ExtrinsicIntents.onAccept` line 331: `_checkRelayer(incoming.relayer);`), the request proceeds directly to `authenticate(incoming.request)` and `withdraw(...)`, letting the attacker trigger escrow withdrawal logic without holding the authorized-relayer role that the EVM contract requires.
