## Title
Missing contract-existence check before low-level token transfers in Tron `IntentGatewayV2.withdraw`/`onAccept` allows silent transfer failure and permanent loss of escrowed funds — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` releases escrowed intent funds using raw low-level `.call()` invocations of `transfer(address,uint256)` and only checks the boolean `success` return value, never whether the target token address actually contains code. This is the exact bug class described in the report: per the EVM/TVM low-level call semantics, a `call` to an address with no code returns `success = true` even though no transfer logic executed. As a result, `withdraw()` and the `SweepDust` handler in `onAccept()` can mark an order as filled/refunded and decrement internal escrow accounting while never actually moving tokens, if the order's token address is not (or is no longer) a deployed contract.

### Finding Description
`withdraw()` iterates over `body.tokens` and, for ERC20 assets, performs: [1](#0-0) 

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
There is no check that `token` is a contract before the call. The same pattern appears for the fee-token transfer at the end of `withdraw` and for `SweepDust` handling in `onAccept`: [2](#0-1) [3](#0-2) 

Both `withdraw` (triggered by `RequestKind.RedeemEscrow`/`RefundEscrow` in `onAccept`) and the `SweepDust` branch are reached directly from `onAccept`, which is called by the host after processing an authenticated relayed ISMP message — i.e., from an unprivileged relayer delivering a proof for a message that itself originates from a normal user's intent-fill/refund flow: [4](#0-3) 

Because `withdraw` unconditionally sets `_filled[body.commitment] = beneficiary` and decrements `_orders[body.commitment][token]` regardless of whether the underlying `.call()` actually executed transfer logic, a token whose contract has been destroyed or never deployed at the recorded address will cause the escrow accounting to be permanently marked as settled without any tokens leaving/entering the contract.

Notably, the non-Tron `IntentsBase.sol` used by the main `IntentGatewayV2` contract shows the codebase is aware of this class of issue and mitigates it in other paths (it contains several `code.length`/`extcodesize`-style existence checks), but this protection is absent from the Tron variant's `withdraw`/`SweepDust` low-level-call paths.

### Impact Explanation
If the escrowed token's contract becomes non-existent by the time a withdrawal/refund/sweep is relayed and delivered (e.g., a proxy that is later destroyed, a token registered but not yet deployed on Tron, or a placeholder/incorrect token address supplied in an order), `withdraw()` will:
- Mark the order as permanently filled (`_filled[commitment] = beneficiary`), preventing any future retry or refund of the escrow, and
- Decrement the internal escrow ledger as if payment succeeded,

while never delivering tokens to the beneficiary. This results in permanent freezing/loss of the escrowed funds for the affected order — the beneficiary who was owed tokens never receives them, and the order can never be re-processed because it is already recorded as filled/refunded. This satisfies the "permanent freezing of funds" impact criterion for intents escrow.

### Likelihood Explanation
Likelihood is difficulty "Low" per the class (same as the original Trail of Bits finding): it requires the referenced token contract to have no code at execution time. This can realistically occur for tokens registered by address but not yet deployed, tokens deployed via a factory pattern later destroyed, or misconfigured/incorrect asset addresses in an order — none of which require any privileged action, only a relayer delivering a legitimately authenticated withdrawal/refund/sweep message for such an order.

### Recommendation
Add an explicit contract-existence check (`token.code.length > 0`) before performing the low-level `.call()` transfers in `IntentGatewayV2.withdraw()` and the `SweepDust` branch of `onAccept()` in `evm/tron/contracts/apps/IntentGatewayV2.sol`, reverting if the token has no code — mirroring the protections already present in `evm/src/apps/intentsv2/IntentsBase.sol`. Longer term, replace the raw `.call()` transfer pattern with OpenZeppelin's `SafeERC20.safeTransfer`, which is already imported and used elsewhere in this same contract for `safeTransferFrom`.

### Proof of Concept
1. An order references a TRC20 `token` address that either has not yet been deployed or is subsequently self-destructed (or an intent references an incorrect/placeholder token address).
2. A relayer legitimately relays a `RedeemEscrow`/`RefundEscrow` message for that order commitment; `onAccept` authenticates it and calls `withdraw(body, ...)`. [5](#0-4) 
3. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` targets an address with no code; the low-level call returns `success = true` without transferring anything.
4. `withdraw` proceeds to set `_filled[body.commitment] = beneficiary` and decrement `_orders[body.commitment][token] -= amount`, permanently marking the order as settled even though the beneficiary received nothing — the escrowed value is unrecoverable.
