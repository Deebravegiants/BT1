### Title
Webhook tenant/topic spoofing via unauthenticated headers not covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the HMAC signature over the raw request body only. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values — which are read straight from attacker-controllable HTTP headers — are never included in the signed payload. `Registry.process` relies on `Utils::HmacValidator.validate` to authenticate the request, but that check only proves the body bytes are legitimate; it says nothing about which shop or topic the body belongs to.

### Finding Description
The identity binding that should hold is:
`hmac_valid(body) == true` should imply `shop header == shop that Shopify actually sent this specific webhook for` (and similarly for `topic`).

In this gem, that equality is broken:
- `hmac` is computed as `HMAC-SHA256(secret, raw_body)` [4](#0-3) .
- `to_signable_string` returns only `@raw_body`, never the headers [1](#0-0) .
- `shop`, `topic`, `webhook_id`, `api_version` are all pulled unauthenticated from headers [2](#0-1) .
- `Utils::HmacValidator.validate` only recomputes and compares against `to_signable_string`, i.e. only the body [5](#0-4) .
- `Registry.process` gates entirely on that body-only HMAC check, then forwards the unauthenticated `request.shop` and `request.topic` to the host app's handler as trusted identity fields [3](#0-2) .

Any attacker who legitimately receives one valid `(body, hmac)` pair for a given topic (e.g., by installing the app on their own shop, or subscribing to a self-controlled event that produces the same body shape) can replay that identical body+HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` header. Because those headers are outside the signed content, `HmacValidator.validate` still returns `true`, and the forged `shop`/`topic` are handed to the app's `WebhookHandler` as if Shopify itself vouched for them.

### Impact Explanation
This crosses the tenant boundary the gem is meant to enforce for webhook consumers: a request whose body was only ever authenticated for shop A can be replayed and attributed to shop B (or to a different topic than the one actually signed) purely by changing an unauthenticated header. Any host application that uses `WebhookMetadata#shop`/`#topic` (which is exactly the documented usage pattern in `webhook_handler.rb`/`registry.rb`) to key per-tenant data — the intended and only way to consume this API — can be tricked into writing or acting on data under the wrong tenant, or invoking the wrong handler logic for a topic. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitability requires the attacker to obtain at least one valid `(raw_body, hmac)` pair, which is trivial for any developer/attacker who installs the app on their own free/dev shop and receives real webhooks for it (this needs no privileged access, TLS interception, or leaked secrets — only a normal, self-controlled Shopify store using the target app). From there, forging headers on a replayed HTTP POST to the app's public webhook endpoint is straightforward. This is a design flaw in `Request`/`HmacValidator`/`Registry`, not a misuse of the API by the host application, so it doesn't depend on the host ignoring documented usage.

### Recommendation
Bind the shop/topic identity to the signature, not just the body:
- Have `to_signable_string` (or a separate check in `Registry.process`) incorporate the `shop-domain` and `topic` header values into the material that is verified, or
- Since Shopify's actual webhook HMAC is defined over the raw body per their documented scheme, at minimum cross-validate `request.shop` against the shop associated with the webhook subscription/session expected to receive it (e.g., require the caller to pass the expected shop and compare with `Digest.hexencode`-safe constant-time equality) before trusting `request.shop` for dispatch, rather than passing it through unauthenticated.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook POST with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's `client_secret`), topic `orders/create`, `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker replays the exact same request to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and/or a different `X-Shopify-Topic`), keeping body `B` and `X-Shopify-Hmac-Sha256: H` unchanged.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers [6](#0-5) , `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds since `H` still matches `B` [7](#0-6) .
4. The registered handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: ..., ...)` [8](#0-7) , causing the host app to process attacker-supplied data as if it originated from the victim shop.
