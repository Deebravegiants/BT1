### Title
Webhook HMAC Signature Does Not Cover `shop`, `topic`, or `webhook-id` Headers, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC verification performed by `Utils::HmacValidator.validate` binds solely to the byte content of `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` values — all read directly from unauthenticated HTTP headers — are never part of the signed material, yet `Registry.process` treats them as trusted identifiers and forwards them to the app's webhook handler.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
returning only `@raw_body`. Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers with no cryptographic binding: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then hands the unauthenticated `request.shop` (and `topic`, `webhook_id`, `api_version`) to the app's handler as if they were verified: [3](#0-2) 

`Utils::HmacValidator.validate` and `validate_signature` only ever operate on `verifiable_query.to_signable_string`, so any field excluded from that string is fully attacker-controllable without invalidating the signature: [4](#0-3) 

This is the same bug class as the reported `CalculateRequestHash` issue: the verification function omits a field (`shop`/`topic`/`webhook_id`) that is later used to make a trust decision, breaking the equality that should hold between "bytes verified" and "bytes/headers acted upon."

### Impact Explanation
Because the HMAC only covers the JSON body, a party who can obtain any one valid `(raw_body, hmac)` pair from the app's shared `api_secret_key` (e.g., by having the app installed on their own shop and receiving a legitimate webhook) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header. `Registry.process` will pass HMAC validation and deliver the payload to the handler tagged with the attacker-chosen `shop`, `topic`, and `webhook_id` in `WebhookMetadata`. If the host application uses `data.shop` to attribute the payload to a tenant (e.g., processing `shop/redact`, `app/uninstalled`, or order data), this enables cross-tenant data confusion/injection under the app's own trusted webhook pipeline — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Any actor who can install the app on a shop they control (a normal, unprivileged action) can capture a legitimate signed webhook body/HMAC pair, since the webhook endpoint is publicly reachable over the internet and no additional secret or privileged credential is required to forge the headers. The header-spoofing itself requires no cryptographic material at all.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (and any other header consumed by the handler) in the signable string used for HMAC verification in `Request#to_signable_string`, or independently verify these headers against values that are cryptographically bound (e.g., signed metadata from Shopify), rather than trusting raw HTTP headers once only the body HMAC has been checked.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; capture a legitimate webhook POST, including `raw_body`, `x-shopify-hmac-sha256`, and other headers.
2. Send a new POST to the app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256` (still valid since only the body is signed), but replace `x-shopify-shop-domain` with `victim.myshopify.com` and/or change `x-shopify-topic`/`x-shopify-webhook-id`.
3. `Utils::HmacValidator.validate` returns `true` (body/HMAC pair matches), and `Registry.process` dispatches the handler with `WebhookMetadata` claiming the event originated from `victim.myshopify.com`, even though the body content and headers were never jointly authenticated.

          received_signature = verifiable_query.hmac
