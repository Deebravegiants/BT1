### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) identity is trusted by handlers but not bound by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values that the app's webhook handler actually acts on are read straight from HTTP headers that are never included in the signed bytes. This breaks the identity binding `hmac_signed_bytes == bytes_the_handler_trusts_as_the_tenant_identifier`, letting anyone who can obtain one validly-signed webhook body (e.g. an attacker's own dev/test store with the app installed) relabel that payload as coming from any other shop while keeping a valid signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled directly from attacker-controllable HTTP headers, independent of the signed body: [2](#0-1) 

`HmacValidator.validate` only ever checks the signature against `to_signable_string` (i.e., the raw body), never the headers: [3](#0-2) 

`Registry.process` accepts any request that passes this HMAC check, and then dispatches to the handler using the *unsigned* `request.shop` (and `request.topic`) as the trusted tenant/topic identity: [4](#0-3) 

The equality this scheme is supposed to guarantee is:
`hmac_valid(raw_body, secret) ⇒ (shop, topic, webhook_id) in headers are authentic for that raw_body`

In reality the guarantee is only:
`hmac_valid(raw_body, secret) ⇒ raw_body was produced by someone holding client_secret`

Since every shop installing the same app shares the same `client_secret` used to sign all of that app's webhooks, an attacker who legitimately installs the app on their own store (a normal, unprivileged action) receives real webhook requests whose HMAC is valid for the body only. They can freely rewrite the `X-Shopify-Shop-Domain`/`shopify-shop-domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers on that captured request to any other shop domain/topic/id they choose and replay it — the recomputed HMAC (over the unchanged raw body) still matches, so `Utils::HmacValidator.validate(request)` still returns `true`.

### Impact Explanation
This directly enables **cross-tenant access**: the app-defined webhook handler receives `WebhookMetadata` containing an attacker-chosen `shop` value that the library asserts is verified (it passed `HmacValidator.validate`), when in fact only the body bytes were verified, not the shop binding. Any application logic that keys off `request.shop`/`WebhookMetadata#shop` to select which tenant's data to update, invalidate, resync, or delete (a common and reasonable pattern, since the library's own `process` method passes this value on as authoritative) can be manipulated into acting on/for a shop the attacker does not own, using data supplied by the attacker's own store. This satisfies the Critical "cross-tenant access" category defined in scope.

### Likelihood Explanation
Likelihood is high for any app that relies on the gem's webhook verification as an assurance of shop identity (which is the natural reading of `HmacValidator.validate`/`Registry.process` succeeding). The only prerequisite is that the attacker legitimately installs the target app on a shop they control — a normal, unprivileged action requiring no stolen credentials, TLS interception, or social engineering — and can replay HTTP requests with modified headers, which is trivial.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the HMAC-verified content, or otherwise independently authenticate the header before trusting it, e.g. by:
- Including a canonical representation of `shop-domain` (and `topic`) in `to_signable_string` in addition to the raw body, and requiring the caller to independently validate that `request.shop` corresponds to a shop with a known/installed session for this app before dispatching to a handler; or
- At minimum, documenting/enforcing in `Registry.process` that `request.shop` must be cross-checked against an existing, trusted session store keyed by validated shop domain before being passed to `WebhookMetadata`, rather than treating a passing `HmacValidator.validate` result as proof that the shop header is authentic.

### Proof of Concept
1. Attacker creates their own Shopify development store `attacker.myshopify.com` and installs the victim's app (a normal, self-service action).
2. Shopify sends a real webhook to the app's endpoint, e.g. `orders/create`, with body `B`, and headers including `X-Shopify-Hmac-Sha256: H(B, secret)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker replays this exact request to the same endpoint, but rewrites `X-Shopify-Shop-Domain` to `victim.myshopify.com` (and optionally the topic/webhook-id).
4. Because `Request#to_signable_string` only returns `@raw_body` (`B`), and `B` is unmodified, `Utils::HmacValidator.validate(request)` in `Registry.process` still succeeds: [4](#0-3) 
5. The app's handler receives `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: attacker-controlled parsed body, ...)` and, trusting the library's "verified" webhook, may process/act as if the data legitimately originated from `victim.myshopify.com`.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
