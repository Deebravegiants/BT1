Audit Report

## Title
JWT single-use replay protection has a check-then-act race allowing token reuse - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` implements JWT (`jti`) single-use replay protection using a non-atomic check-then-act pattern: `jwtReplayCache.isReplay` is checked under a read lock at the top of `Authorize`, and `jwtReplayCache.recordUsage` is only called under a separate write lock at the very end, after JWT verification and authorized-key checks. Two concurrent requests carrying the identical signed JWT can both pass the `isReplay` check before either calls `recordUsage`, allowing the same JWT to authorize multiple distinct `WorkflowExecute` dispatches to the DON.

## Finding Description
`jwtReplayCache.isReplay` and `jwtReplayCache.recordUsage` each acquire and release their own lock independently rather than sharing one critical section: [1](#0-0) 

`Authorize` calls `isReplay` immediately after JWT verification, then performs authorized-key lookups, and only calls `recordUsage` at the very end of the successful path: [2](#0-1) 

Tracing the call chain confirms there is no lock held around the entire `Authorize` invocation from the caller side either: `httpTriggerHandler.HandleUserTriggerRequest` calls `h.authorizeRequest`, which calls `h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)` directly, with no mutex acquired before or during this call. [3](#0-2) [4](#0-3)  The only synchronization present in `httpTriggerHandler`, `callbacksMu`, protects the separate `callbacks` map and is acquired later in `setupCallback`, after `Authorize` has already completed — it does not serialize `Authorize` calls and thus does not close the race window. [5](#0-4) 

As a result, two goroutines processing the same signed JWT concurrently can both observe `isReplay(claims.ID) == false` before either records usage, both pass the authorized-key checks, and both are dispatched as legitimate workflow executions — defeating the single-use guarantee the existing sequential regression tests assume: [6](#0-5) [7](#0-6) 

For comparison, `RequestReplayGuard.CheckAndRecord` (used by the Vault JWT/allowlist auth flow) correctly performs the check-and-insert atomically under a single `mu.Lock()`, demonstrating this is an established pattern elsewhere in the codebase that `jwtReplayCache` fails to follow. [8](#0-7) 

## Impact Explanation
An unprivileged HTTP-trigger caller who possesses a validly signed JWT (which is a per-request artifact, not a privileged secret held only by trusted operators) can fire duplicate copies of the same request concurrently at the gateway. If both requests are processed by racing goroutines before either records the `jti`, the anti-replay guarantee is bypassed and the same signed request triggers multiple distinct `WorkflowExecute` dispatches to the DON. This is a concrete bypass of the replay-protection mechanism on the internet-facing HTTP trigger path, resulting in duplicate/unintended workflow executions from what should be a single-use authorization token — mapping to the "unauthorized job run" / gateway request impersonation impact class.

## Likelihood Explanation
The race window is real: it spans JWT verification and the authorized-key map lookups between the `isReplay` check and the `recordUsage` call, and is fully controllable by an external caller who can send multiple copies of the same signed request concurrently to increase the chance of winning the race. It is probabilistic rather than deterministic (unlike a single-block-timestamp trigger), but it is a genuine, unmitigated concurrency bug in production code reachable by any client capable of issuing two simultaneous HTTP requests with the same JWT — no operator, admin, or elevated privilege is required.

## Recommendation
Replace the separate `isReplay`/`recordUsage` methods with a single atomic `CheckAndRecord(jti string) bool` (or similar) method on `jwtReplayCache` that performs the existence check and the insertion under one lock acquisition, mirroring `RequestReplayGuard.CheckAndRecord` in `core/capabilities/vault/request_replay_guard.go`. Call this single method once in `Authorize`, ideally immediately after JWT signature verification, so that no other goroutine can observe an unrecorded `jti` between the check and the record for the same token.

## Proof of Concept
Add a test alongside the existing sequential test at `workflow_metadata_handler_test.go:1193-1217` that instead launches two goroutines calling `handler.Authorize(workflowID, tokenString, req)` concurrently with the same JWT, synchronized via a start barrier (e.g., a channel or `sync.WaitGroup` released simultaneously), and asserts that at most one of the two calls succeeds. To make the race reliably observable, instrument `jwtReplayCache.isReplay`/`recordUsage` or insert a small artificial delay between them (or slow down the `authorizedKeys` map lookup) to widen the window; under the current implementation both goroutines can return successfully, demonstrating the bypass.

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
