### Title
Webhook HMAC signature does not cover the `shop-domain`/`topic`/`webhook-id` headers, allowing header spoofing on a validly-signed body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `topic`, `shop`, `api_version`, and `webhook_id` values are read directly from unauthenticated HTTP headers. `Utils::HmacValidator.validate` only proves that *the body* was produced by someone holding `api_secret_key`; it proves nothing about which shop or topic the caller is claiming the body belongs to. `Webhooks::Registry.process` then dispatches to the app's handler using these unauthenticated `topic`/`shop` values, breaking the intended binding `HMAC-authenticated bytes == (shop, topic) attributed to those bytes`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` verifies the HMAC strictly against `verifiable_query.to_signable_string`, i.e., the body bytes: [2](#0-1) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled from HTTP headers with no cryptographic tie to the signed body: [3](#0-2) 

`Registry.process` validates the HMAC (of the body only) and then hands the handler the unauthenticated `topic` and `shop` values as trusted identity metadata: [4](#0-3) 

Because `api_secret_key` is a single app-wide secret (not per-shop), any merchant who installs the app receives real, validly-HMAC-signed webhook deliveries for their own shop. Since the signature only covers the JSON body, that same `(body, hmac)` pair remains valid no matter what `shop-domain`, `topic`, or `webhook-id` headers accompany it. An attacker who controls their own shop (an unprivileged, non-admin actor from the perspective of other tenants) can therefore replay a validly-signed body while substituting the `x-shopify-shop-domain` header for a victim shop, or substituting `x-shopify-topic` for a different topic than what was actually sent, and the library will accept it as authentic and dispatch it to the app's handler as if it genuinely originated from that shop/topic.

### Impact Explanation
This breaks the binding between "bytes cryptographically verified" and "shop attributed to those bytes," and directly matches the Critical impact category of cross-tenant access: an app's webhook handler that keys off `WebhookMetadata#shop` (e.g., to update local records, sync app state, or trigger `GDPR`/mandatory webhook workflows for that shop) can be made to process attacker-supplied data under another tenant's identity, using only a webhook payload the attacker legitimately received for their own shop.

### Likelihood Explanation
Any merchant who installs the app can trivially capture one legitimate webhook delivery (body + `hmac-sha256` header) for their own shop, since Shopify sends real webhooks to every installed app. Replaying it with a modified `shop-domain` (and/or `topic`) header requires no secret knowledge and no privileged access — it exploits the library's `HmacValidator`/`Webhooks::Request` design, which never binds the header-derived identity fields into the signed payload.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or equivalently, verify them out-of-band against Shopify’s current, cryptographically-verified webhook headers such as the newer `X-Shopify-Hmac-Sha256` request signing that Shopify recommends binding to the full request, not just the body) in the HMAC-signable string so that spoofing any of these headers invalidates the signature. At minimum, document and/or enforce that consumers must cross-check `request.shop` against a known, previously-registered shop for the topic before trusting it, and reject webhook deliveries whose `shop` does not match an existing session/shop record.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. topic `orders/create`, with headers:
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC of raw body>`
   - `x-shopify-topic: orders/create`
2. Attacker replays the exact same raw body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only, using the app's single `api_secret_key`, and it matches (since body/HMAC pair was never altered). [5](#0-4) 
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: ...)`, causing the app to treat attacker-controlled order data as belonging to `victim-shop.myshopify.com`.
