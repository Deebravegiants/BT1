### Title
Independent, non-atomic Config reads let `MegaAgentOne` and `MegaAgentTwo` initialize with mismatched model configs during a signup - ([File: src/brokers/orb.rs])

### Summary
`MegaAgentOne` (iris, IR-Net, occlusion) and `MegaAgentTwo` (face-identifier, RGB-Net, iris) are two independently constructed Python agents that together implement the biometric pipeline for a signup. Each is built from the shared `Config` via its own, separate `From<&Config>` conversion, and each conversion takes its own independent lock on `Arc<Mutex<Config>>` at a different point in time. There is no mechanism that guarantees the two agents are constructed from the same, mutually consistent configuration snapshot - directly analogous to the reported `FathomProxyWalletOwner` issue, where several address/config fields that are "assumed to work as a completely synchronized set" are actually initialized independently and can silently diverge.

### Finding Description
`Orb::init_mega_agent_one` and `Orb::init_mega_agent_two` each independently acquire the config mutex and convert a snapshot of `Config` into the corresponding agent struct: [1](#0-0) 

```
async fn init_mega_agent_one(&mut self) -> Result<mega_agent_one::MegaAgentOne> {
    Ok((&*self.config.lock().await).into())
}

async fn init_mega_agent_two(&mut self) -> Result<mega_agent_two::MegaAgentTwo> {
    Ok((&*self.config.lock().await).into())
}
```

Each call is a separate, unsynchronized lock/unlock cycle on the same `Arc<Mutex<Config>>`. The conversions themselves pull disjoint but semantically related fields out of `Config`: [2](#0-1) [3](#0-2) 

Between these two lock acquisitions, the shared `Config` object can be atomically *replaced wholesale* (not merged) by the background config-update task, which runs every `CONFIG_UPDATE_INTERVAL` (10s) and does `*config.lock().await = new_config;`: [4](#0-3) [5](#0-4) 

If a backend config push lands between the two `init_mega_agent_*` calls, `MegaAgentOne`'s `iris`/`ir_net` models will be built from the *old* `iris_model_configs` / `ir_net_model_configs`, while `MegaAgentTwo`'s `face_identifier`/`iris` models will be built from the *new* `face_identifier_model_configs` / `iris_model_configs` / `child_threshold` - two agents that participate in the same signup's fraud/liveness decision using two different configuration generations, exactly the "obsolete version of one of the contracts" scenario described in the external report.

This divergence is compounded during the pipeline run itself: `run_update_all_configs` re-pushes only `face_identifier_model_configs` to `mega_agent_two`, but never refreshes `mega_agent_one`'s `iris`/`ir_net` model state after its initial construction: [6](#0-5) 

So even within a single pipeline run, the `Config`-derived state of `mega_agent_one` and `mega_agent_two` is guaranteed to be able to drift, since one is refreshed mid-pipeline and the other is not, and there is no versioning/consistency check tying the two together.

### Impact Explanation
`MegaAgentOne` and `MegaAgentTwo` jointly determine the biometric result for a signup: iris matching (both agents), IR-Net eye estimation, occlusion detection, RGB-Net face detection, and the face-identifier fraud/liveness check (`face_identifier_fraud_checks`) consumed in `biometric_pipeline::Plan::run`: [7](#0-6) 

If the two agents run with inconsistent model/threshold generations (e.g., a lowered `child_threshold`, a changed `fraud_check_engine_config`, or an outdated iris model version in one agent but not the other), the fraud/liveness enforcement for that signup is evaluated against a non-coherent configuration state. This can manifest as an inconsistent or bypassed fraud/liveness decision for a given signup - conceptually the same class of harm as the reported bug ("the wallet contract may work incorrectly, possibly resulting in a lock of funds"), here translated to "the pipeline may work incorrectly, possibly resulting in an incorrect fraud/liveness/enrollment decision."

### Likelihood Explanation
The race window is real but narrow and non-attacker-controlled from the unprivileged user's side: it only manifests when a backend config push (which happens routinely every 10 seconds via `config_update`) lands between the two agent-initialization lock acquisitions, or when `mega_agent_one` is enabled long before `mega_agent_two`/pipeline execution (e.g. warm boot vs. later signup) such that a config update occurs in between. Likelihood is therefore data-race/timing-dependent rather than directly exploitable by a malicious QR code or user input, and I could not fully verify (within this pass) the exact temporal distance between `enable_mega_agent_one` and `enable_mega_agent_two`/pipeline start across all code paths (e.g. `warmup::Plan`), which would materially affect how often this window is hit in practice.

### Recommendation
Read the `Config` once (single lock acquisition) and derive both `MegaAgentOne` and `MegaAgentTwo` from that single snapshot, e.g. by having `Orb` fetch `let config = self.config.lock().await.clone();` once and passing the same `&Config` value into both `From<&Config>` conversions. Additionally, ensure any mid-pipeline config refresh (`run_update_all_configs`) updates all Config-derived model state in both mega agents together (or introduce a config-generation/version tag that both agents log/report, so that any observed mismatch is detectable and can be treated as an unreliable signup indicator).

### Proof of Concept
Not directly demonstrable via a unprivileged-user PoC (this is a timing/config-consistency issue, not an input-driven exploit): it requires a config-update tick from the backend to land between the two independent lock acquisitions in `init_mega_agent_one`/`init_mega_agent_two`, or between `mega_agent_one` enablement and the later `run_update_all_configs` push to `mega_agent_two` in `biometric_pipeline::Plan::run`. This can be reproduced in a controlled test by mutating the shared `Arc<Mutex<Config>>` between the two `init_mega_agent_*` calls (e.g. via a test harness that swaps `iris_model_configs`/`face_identifier_model_configs` mid-initialization) and observing that the two agents end up with model configs derived from different `Config` generations.

    fn config_update(&mut self, observer: &mut Observer) -> Result<()> {
        if self.before_config_update()? {
            match observer.config_update.as_mut().map(future::FutureExt::now_or_never) {
                Some(None) => return Ok(()),
                Some(Some(result)) => result??,
                None => {}
            }
            let config = Arc::clone(&observer.config);
            let ui = observer.ui.clone();
            observer.config_update = Some(tokio::spawn(async move {
                if let Ok(new_config) = Config::download().await {
                    *config.lock().await = new_config;
                    config.lock().await.propagate_to_ui(ui.as_ref());
                }
                Ok(())
            }));
        }
        Ok(())
    }
