### Title
Cross-action trust escape via `EmporiumUpgradeable.runAction` allows theft of any victim's `DepositOnChainUtxosExternalAction` allowance - (File: `contracts/external-actions/DepositOnChainUtxosExternalAction.sol`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`DepositOnChainUtxosExternalAction.runAction` trusts `circomData.originalSender` as the token source for `transferERC20TokenFrom`, gated only by `onlyAllowedRecipient` (`isAllowedRecipient[msg.sender]`). Because `EmporiumUpgradeable` can be registered in that mapping and forwards attacker-supplied `op.callData` via a raw `op.endpoint.call(...)`, an attacker can construct a completely fabricated, unverified `CircomData` struct naming any victim as `originalSender` and drain the victim's standing ERC20 allowance directly into Emporium, which the attacker then converts into their own private UTXO.

### Finding Description
The broken equality is: **AUTHORITY** — `transferERC20TokenFrom`'s `_from` argument (the victim) must equal the address whose proof-verified `originalSender` was checked against the true transaction sender in `HinkalHelper.performHinkalChecks` (`contracts/HinkalHelper.sol:213-219`). That binding only applies to the *top-level* `circomData` argument of `Hinkal.transact`. It is never re-applied to any nested calldata that an external action subsequently constructs and dispatches on its own.

Path:
1. Attacker calls `Hinkal.transact` with a top-level `circomData` whose `externalActionData.externalActionId` resolves to `EmporiumUpgradeable`, and whose `originalSender` is legitimately set to the attacker's own address (satisfying `performHinkalChecks`, `contracts/HinkalHelper.sol:213-219`) since they are `msg.sender`.
2. `Hinkal._externalTransact` (`contracts/Hinkal.sol:234-261`) calls `EmporiumUpgradeable.runAction(circomData, deltaAmountChanges)`. `msg.sender` inside Emporium is `Hinkal`, which is allowed (`onlyAllowedRecipient`).
3. `EmporiumUpgradeable.runAction` decodes an `EmporiumStack` from `circomData.externalActionData.externalActionMetadata` — arbitrary attacker-chosen bytes (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:80-83`). The attacker sets `signerAddress = address(0)`, which skips all signature checks in `verifyWallet` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:314-316`).
4. For a stateless op (`invokeWallet == false`), Emporium performs a raw `op.endpoint.call{value: op.value}(op.callData)` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:103-113`), where `op.endpoint = DepositOnChainUtxosExternalAction` and `op.callData` encodes `runAction(forgedCircomData, [0])` with `forgedCircomData.originalSender = victim`. This forged struct is never passed through `Hinkal.transact`, never hashed into `calldataHash`, and never checked by `performHinkalChecks`.
5. Inside `DepositOnChainUtxosExternalAction.runAction` (`contracts/external-actions/DepositOnChainUtxosExternalAction.sol:21-86`), `onlyAllowedRecipient` only checks `isAllowedRecipient[msg.sender]` — and `msg.sender` here is `EmporiumUpgradeable`, which is allowed per the stated precondition. `userAddress = circomData.originalSender = victim`, and since `deltaAmounts[i] == 0` (attacker-supplied `[0]`), it calls `transferERC20TokenFrom(tokenAddress, victim, msg.sender /* Emporium */, tokenTotal)` (lines 75-82), pulling the victim's standing allowance directly to Emporium.
6. Back in `EmporiumUpgradeable.runAction`, the balance delta for that token (from the outer, attacker-controlled `circomData.erc20TokenAddresses`) reflects the stolen `tokenTotal`. `handleOut` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:162-184`) forwards this gain to `msg.sender` (Hinkal) and mints a `UTXO` keyed to the attacker's own `circomData.stealthAddressStructure`.
7. `Hinkal.transact`'s balance-diff check (`contracts/Hinkal.sol:134-146`) reconciles cleanly because `amountChanges[i] = 0` and `utxoAmount = tokenTotal`, so the theft is accepted and committed via `insertNullifiers`/`insertCommitments`.

Existing guards fail because: `onlyAllowedRecipient` only authenticates *which contract* is calling, not *on whose behalf/with what data*; `performHinkalChecks`'s `originalSender == sender` binding is applied solely to the outer, Hinkal-supplied `circomData`, and is bypassed entirely for the forged nested struct built inside `externalActionMetadata` and dispatched via Emporium's generic `op.endpoint.call`.

### Impact Explanation
Critical — direct theft of a victim's approved ERC20 balance. Any EOA that has ever granted (or still holds) a nonzero allowance to `DepositOnChainUtxosExternalAction` (a common pattern for a legitimate deposit, especially with `approve(..., type(uint256).max)`) can have that entire allowance pulled by an unprivileged attacker into `EmporiumUpgradeable`, and then converted into a private UTXO under the attacker's own stealth address. This is repeatable for every victim with outstanding allowance and for every token, as long as `EmporiumUpgradeable` remains registered as an allowed recipient of `DepositOnChainUtxosExternalAction`.

### Likelihood Explanation
Preconditions: (1) `EmporiumUpgradeable` registered in `DepositOnChainUtxosExternalAction`'s `isAllowedRecipient` (stated deployment precondition), (2) at least one victim with nonzero standing allowance to `DepositOnChainUtxosExternalAction`. Both are plausible/likely in a real deployment (cross-action recipient allowlisting is explicitly described as serving "VolatileTokenAction and Hinkal interactions" without restricting to only Hinkal, and infinite-approval UX is common). Attacker cost is a single `transact` call plus a self-generated proof for their own (unrelated) UTXO state — no special privileges, no victim cooperation, no signature forgery (since `signerAddress = 0` skips EIP-712 verification).

### Recommendation
Do not let `onlyAllowedRecipient` be the sole authorization for state-changing token pulls. `DepositOnChainUtxosExternalAction.runAction` (and any action relying on `circomData.originalSender`) must only trust `originalSender` when it was itself proof-verified against the true caller — e.g., require `msg.sender == hinkal` specifically for actions performing `transferFrom` keyed on `originalSender`, rather than allowing arbitrary allowlisted contracts (like Emporium) to relay it. Alternatively, `EmporiumUpgradeable` must never be allowed to forward raw, unverified `CircomData` to other Hinkal external actions; any nested `runAction` invocation reachable through Emporium ops should re-derive `originalSender` from the top-level, hash-committed `circomData`, not decode a second independent struct from attacker-supplied `callData`.

### Proof of Concept
Foundry fork test:
1. Deploy `DepositOnChainUtxosExternalAction` and `EmporiumUpgradeable`; register `EmporiumUpgradeable` address in the former's `isAllowedRecipient` (via constructor/`setAllowedRecipients`), and register `DepositOnChainUtxosExternalAction`'s ID/`EmporiumUpgradeable`'s ID in `Hinkal.registerExternalAction`.
2. Victim: `approve(DepositOnChainUtxosExternalAction, type(uint256).max)` for `TOKEN`.
3. Attacker builds top-level `circomData` with `externalActionId` = Emporium's ID, `originalSender = attacker`, `erc20TokenAddresses = [TOKEN]`, `amountChanges = [0]`, `onChainCreation=[false]`, `stealthAddressStructure` = attacker's, and `externalActionData.externalActionMetadata` = ABI-encoded `EmporiumStack{signerAddress:0, ops:[EmporiumOperation{endpoint: DepositOnChainUtxosExternalAction, invokeWallet:false, value:0, callData: abi.encodeCall(runAction, (forgedCircomData, [int256(0)]))}]}` where `forgedCircomData.originalSender = victim`, `erc20TokenAddresses=[TOKEN]`, `externalActionData.externalActionMetadata = abi.encode(uint256[][]([[tokenTotal]]))`.
4. Generate a valid snarkjs proof for the attacker's own top-level `circomData`/nullifiers (unrelated to the forged inner struct, which is never proof-checked).
5. Call `Hinkal.transact(a,b,c,dimensions,circomData)`.
6. Assert: `TOKEN.balanceOf(victim)` decreased by `tokenTotal`; attacker's resulting UTXO commitment (traceable via emitted `insertCommitments`/encrypted output for their `stealthAddressStructure`) increased by `tokenTotal`; no revert occurred despite `forgedCircomData.originalSender` never passing through `performHinkalChecks` or being bound to any proof.
