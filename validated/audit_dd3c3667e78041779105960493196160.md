### Title
Cross-chain replay of signed calldata authorizes unintended `RuntimeCall` dispatch in HyperFungibleToken bridging - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The Flowise advisory concerns a feature (`overrideConfig`) that lets an unprivileged caller inject configuration that controls execution, with insufficient scoping/authorization around what can be changed and in what context. The closest reachable analog in Hyperbridge is `pallet-hyper-fungible-token`'s optional calldata-execution feature: any user who calls `send()` on the source-chain `HyperFungibleToken`/`WrappedHyperFungibleToken` contract can attach an ABI-encoded `data` payload that, once relayed and accepted on the destination chain, gets decoded into a `RuntimeCall` and dispatched with `RawOrigin::Signed` on behalf of an account chosen by the payload — either the token beneficiary (if a signature is supplied) or the message sender (if not). This is functionally an "execute this configuration/call for me" primitive analogous to `overrideConfig`, and its authorization scoping is under-specified.

### Finding Description
In `on_accept` (`modules/pallets/hyper-fungible-token/src/module.rs:50-212`), when `message.data` is non-empty, the pallet:
1. Decodes `SubstrateCalldata { signature, runtime_call }` from the attacker-controlled `message.data` field [1](#0-0) .
2. If a signature is present, verifies it over `(nonce, runtime_call)` where `nonce = frame_system::Pallet::<T>::account_nonce(beneficiary)` — the destination chain's own local nonce for the beneficiary account [2](#0-1) .
3. Dispatches the decoded `runtime_call` as `RawOrigin::Signed(origin)` — where `origin` is either the beneficiary (signed path) or the raw sender address converted from `message.from` (unsigned path) — subject only to `BaseCallFilter` [3](#0-2) .

The signed payload `(nonce, runtime_call).encode()` contains **no domain separator**: no genesis hash, no `StateMachine`/chain identifier, no pallet/instance identifier, and no reference to the specific bridging leg (`source`, `dest`, or contract address) that produced the message. The only binding is a local `frame_system` nonce, which is independent per parachain/runtime instance.

Because many parachains can run this same pallet against the same peer EVM contracts (and the EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` template can be deployed with a CREATE2-derived identical address across chains per the docs) [4](#0-3) , a signature a user produces authorizing a specific `runtime_call` at their current nonce on one destination chain is not scoped to that chain. If the beneficiary's nonce coincidentally matches (e.g., both are `0`, common for accounts that have not yet transacted on that particular parachain, or artificially normalized nonces), the exact same `SubstrateCalldata` blob is valid input for `on_accept` on a *different* destination parachain that the user never intended to authorize a call on. Any user can re-trigger delivery of this cross-chain-replayable authorization by sending a fresh `send()` call (with attacker-chosen `to`/destination) carrying the previously observed `data` blob, since `data` travels verbatim in the message body and is not bound to a specific destination in the signed content.

This is the direct analog of the Flowise issue: an optional "inject configuration/execution into the flow" feature (here, "attach signed calldata to mint-and-execute") is exposed to any unprivileged sender, and the authorization check is insufficiently scoped (no allow-list, no context binding), so the feature can be used to trigger unauthorized app actions beyond what the signer intended.

### Impact Explanation
A successful replay dispatches an arbitrary `RuntimeCall` as `RawOrigin::Signed(beneficiary)` on a state machine the beneficiary did not intend to authorize. Because `BaseCallFilter` is the only guard (and it exists to block calls during maintenance/SafeMode, not to restrict per-app scope), the replayed call can be anything the runtime otherwise permits for a signed origin — including asset transfers, staking/governance actions, or approvals — executed without the account holder's consent on that chain. This is an "unauthorized app action" / forged-authorization class impact, meeting the required severity bar (unauthorized action on user funds/state via a message an attacker relays).

### Likelihood Explanation
Reaching this path requires only: (1) a legitimate signed `SubstrateCalldata` blob to exist at some point (obtainable from public mempool/indexer data, since this is exactly the intended, documented usage of the calldata-execution feature) [5](#0-4) , and (2) another HFT-enabled parachain (or the same chain before the beneficiary's nonce has advanced) where the beneficiary's nonce coincides. Both conditions are plausible in a multi-parachain deployment of `pallet-hyper-fungible-token`, and no privileged role is needed to trigger the replay — any address can call `send()` on the EVM side with attacker-supplied `data`.

### Recommendation
Bind the signed payload to a domain-specific context before dispatch: include the destination `StateMachine` identifier (or `T::HostStateMachine`), the source contract/chain pair, and/or the local genesis hash in the signed message, in addition to the nonce and `runtime_call`. Alternatively, derive a dedicated per-pallet-instance nonce/replay set (e.g., a message-commitment-keyed `BoundedBTreeSet`) rather than relying on the shared `frame_system` account nonce, so that a signature can never be valid outside the single delivery it was produced for.

### Proof of Concept
1. Victim signs a `SubstrateCalldata{signature, runtime_call: X}` payload intending to authorize `X` via a `send()` call to Parachain A, where their `frame_system` nonce there is `0`.
2. Attacker observes this data (it is transmitted in a public cross-chain message body / calldata) and, if Parachain B also runs `pallet-hyper-fungible-token` with the victim having nonce `0` there, submits their own `send()` call (any sender, any amount) targeting Parachain B's HFT contract, embedding the same `data` bytes as `message.data`.
3. On Parachain B, `on_accept` decodes `SubstrateCalldata`, recomputes `(nonce=0, X).encode()`, and the same signature validates against the victim's public key, since no chain-specific context is included in the signed payload.
4. `X` is dispatched with `RawOrigin::Signed(victim)` on Parachain B, an action the victim never authorized there.

**Note:** I could not verify from the indexed code whether every deployment guarantees distinct beneficiary nonces across parachains, nor examine the full `types.rs`/`lib.rs` definitions of `SubstrateCalldata` and the EVM-side `send()`/`Message` encoding logic (they were not fully returned by the index). A Devin session with full repository access would be needed to confirm the exact encoding of `message.from`/`Message` on the Solidity side and to verify there is no additional binding elsewhere (e.g., in `types.rs`) that mitigates this before treating the finding as fully confirmed.

## Calldata Execution

Both contracts support optional calldata execution on the destination chain via the `CallDispatcher`. By passing a non-empty `data` field in `SendParams`, the sender can trigger arbitrary contract calls on the destination chain immediately after tokens are minted or unlocked. This enables composable cross-chain workflows like transfer-and-swap (e.g., bridge USDC then swap to WETH via UniswapV2), transfer-and-stake, or transfer-and-deposit into a lending protocol — all in a single cross-chain operation.

The `data` field is an ABI-encoded `Call[]` array, where each `Call` specifies a target contract, a native value to forward, and the calldata to execute. On the destination chain, the HFT contract mints or unlocks tokens to the `to` address, then forwards the entire `data` payload to the `CallDispatcher`, which executes each call sequentially. If the calls need to spend the bridged tokens (e.g., approve then swap), set `to` to the `CallDispatcher` address so tokens are delivered directly to it.

For code examples, see the [HyperFungibleToken](/developers/evm/hyper-fungible-token/hyper-fungible-token#calldata-execution) and [WrappedHyperFungibleToken](/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token#calldata-execution) pages.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
