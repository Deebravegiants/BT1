### Title
Setting `order.user` to the zero address lets an order's finality marker collapse back to `address(0)`, defeating the "already filled/cancelled" guard - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`IntentsBase._filled[commitment]` is used the same way `bulls[contractId]` is used in the BvB report: `address(0)` is the sentinel meaning "not yet finalized," and any non-zero value means "finalized, do not process again." Just as the BvB bull could call `transferPosition` to push their own address back to `address(0)` and un-match an already-matched order, an IntentGateway order placer can set `order.user = bytes32(0)` so that when the order is later finalized as cancelled/refunded, the write `_filled[commitment] = address(uint160(uint256(order.user)))` stores `address(0)` — indistinguishable from "never processed" — re-opening the order to further processing.

### Finding Description
`_filled` is documented as: "A non-zero value indicates the order has been finalized and cannot be filled again." [1](#0-0) 

Both `fillOrder` and `cancelOrder` gate on this exact non-zero check: [2](#0-1) [3](#0-2) 

`_cancelFromDest` finalizes a cross-chain order by writing the order's own `user` field into `_filled`:
```solidity
function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
    if (order.deadline >= _blockNumber()) {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
    }
    _filled[commitment] = address(uint160(uint256(order.user)));
    _post(order, _body(RequestKind.RefundEscrow, commitment, order.inputs, order.user), options.relayerFee, msg.value);
}
``` [4](#0-3) 

If the order creator sets `order.user = bytes32(0)` at `placeOrder` time, then `address(uint160(uint256(order.user)))` evaluates to `address(0)`. Once the order's deadline has passed, the ownership check is skipped entirely (`if (order.deadline >= _blockNumber())` is false, so anyone may call `cancelOrder`), and the finalization write becomes `_filled[commitment] = address(0)` — exactly the "unfinalized" sentinel value. This is the same class of bug as the BvB report: a state variable meant to be write-once-nonzero is written with the attacker-chosen zero value, resetting the "already processed" guard.

The same pattern exists in the shared `_withdraw` helper used for both `RedeemEscrow` and `RefundEscrow` processing on the source chain:
```solidity
function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    if (finalize) _filled[body.commitment] = beneficiary;
    ...
``` [5](#0-4) 

Because `body.beneficiary` for a `RefundEscrow` message is populated directly from `order.user` (see `_cancelFromDest` above and the same pattern in `_cancelSameChain`), a zero `order.user` propagates the zero sentinel into the finality marker on both the destination chain (`_cancelFromDest`) and the source chain (`_withdraw` finalize branch), collapsing both sides' "finalized" state back to "not yet processed."

### Impact Explanation
Once `_filled[commitment]` reverts to `address(0)`:
- `cancelOrder` can be invoked again on the same commitment, since the top-level guard (`_filled[commitment] != address(0)`) no longer blocks it, letting an attacker re-dispatch additional `RefundEscrow` messages against an order that Hyperbridge/the protocol considers already finalized.
- `fillOrder` on the destination chain will also pass its "not already filled" check (`_filled[commitment] != address(0)`) for an order that was already cancelled, allowing a colluding/careless solver to be lured into filling a dead order and dispatching a competing `RedeemEscrow` message against escrow that the legitimate cancellation flow is concurrently trying to refund — an unsound state commitment where the on-chain "finalized" record can be forced back to "pending" by the order's own creator.
- This breaks the state-commitment invariant the whole cross-chain cancel/redeem protocol depends on (the destination `_filled` slot is what the source-chain GET-based cancellation path trusts as proof of fill status), enabling repeated/duplicated dispatches and races between `RedeemEscrow`/`RefundEscrow` for a single commitment.

This satisfies the "unsound state commitment" / "unauthorized app action" categories: the finality flag that other flows (fill-status proofs, cancel-from-source GET queries, `fillOrder`, `cancelOrder`) rely on can be forced back to its initial value by the order creator alone.

### Likelihood Explanation
This requires no special privilege beyond placing an order with `order.user = bytes32(0)` — something the contracts do not appear to reject at `placeOrder` time (not confirmed with certainty since `placeOrder`'s full body was not reviewed in this pass), and then waiting for the order's own deadline to pass, at which point `_cancelFromDest`'s ownership check is deliberately skipped for anyone to call. Every step is a normal, permissionless user action (`placeOrder`, `cancelOrder` after expiry), making this straightforward to trigger if `order.user == address(0)` is not explicitly disallowed.

### Recommendation
Reject `order.user == bytes32(0)` at `placeOrder` (and anywhere `order.user` is trusted as a beneficiary/finality marker), or, more robustly, stop overloading `address(0)` as both the "unset" sentinel and a legitimate finalization value: use a separate boolean/enum "finalized" flag distinct from the beneficiary address, matching the BvB report's own fix of forbidding `recipient == address(0)` in `transferPosition`.

### Proof of Concept
1. User places a cross-chain order with `order.user = bytes32(0)` (assuming `placeOrder` does not reject a zero `order.user`).
2. Wait until `order.deadline < block.number`.
3. Call `cancelOrder(order, options)` on the destination chain. `_cancelFromDest` skips the ownership check (deadline passed) and executes `_filled[commitment] = address(uint160(uint256(order.user))) == address(0)`, and dispatches a `RefundEscrow` post request.
4. Because `_filled[commitment]` is now `address(0)` again, call `cancelOrder` a second time (or call `fillOrder`); the top-level `if (_filled[commitment] != address(0)) revert Filled();` guard no longer blocks the call, allowing repeated dispatch of finalization messages against the same commitment.

Note: I could not verify within this pass whether `placeOrder` explicitly validates `order.user != bytes32(0)`, nor fully trace every downstream consequence at the source-chain `onAccept` handler for a duplicated `RefundEscrow`/`RedeemEscrow` race; a Devin session with full repo access would be needed to confirm `placeOrder`'s validation and the exact fund-recovery bound in `_orders` decrement paths.
