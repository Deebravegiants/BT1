### Title
Unaccounted ERC1155 deposits held by `EmporiumUpgradeable` can be drained by any attacker via a self-executed `safeTransferFrom` stateless op - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable` inherits `Transferer`'s unconditional `onERC1155Received`/`onERC1155BatchReceived` hooks, allowing it to accept any ERC1155 asset from any stateless op call it makes on behalf of a user. However, `runAction`'s accounting (`getBalancesForArray`, `deltaAmountChanges`, UTXO generation) only tracks `circomData.erc20TokenAddresses` (ERC20/ETH balances), so any ERC1155 token that lands on the Emporium contract is completely untracked and unowned at the contract-storage level. Because "Case 2: Stateless Interaction" executes `op.endpoint.call(op.callData)` directly from the Emporium contract itself, any attacker can craft an `EmporiumOperation` whose `callData` is `IERC1155(token).safeTransferFrom(address(emporium), attacker, id, amount, "")`, which succeeds because the ERC1155 standard's ownership check (`from == msg.sender`) is trivially satisfied when Emporium calls out to the token contract about its own balance.

### Finding Description
The broken equality: `ERC1155 balanceOf(Emporium, id) attributable to victim's prior stateless op == amount victim can later withdraw through Emporium accounting`. In reality this equals 0 on the right side, because Emporium's runAction bookkeeping never represents ERC1155 balances at all.

Code path:
- `Transferer.onERC1155Received`/`onERC1155BatchReceived` at [1](#0-0)  unconditionally return the ERC1155 receiver selectors for any caller/token/id/amount, with no bookkeeping of the depositor.
- `EmporiumUpgradeable.runAction` at [2](#0-1)  only measures `balancesBefore`/`balancesAfter` over `circomData.erc20TokenAddresses` (ERC20/ETH), and only that array's deltas are folded into `deltaAmountChanges`/UTXO creation via `handleOut`. ERC1155 assets are outside this array entirely; there is no counterpart bookkeeping structure.
- The "Case 2: Stateless Interaction" branch at [3](#0-2)  executes `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract's own context (`address(this)` is the caller as seen by `op.endpoint`). The only restriction is blocking the `callHinkalWallet`/`doSendToRelay` selectors; any other call, including `IERC1155.safeTransferFrom`, is permitted.
- `verifyWallet` at [4](#0-3)  only enforces the EIP-712 signature check when `stack.signerAddress != address(0)`; for stateless ops (`signerAddress == address(0)`) it only checks message replay via `usedMessages`, imposing no constraint on `op.endpoint`/`op.callData` content.

Attacker's exact call: the attacker submits their own valid Hinkal proof/UTXO for a trivial or zero-net ERC20 action (satisfying all circuit and `performHinkalChecks` constraints, which only operate over `erc20TokenAddresses`/`amountChanges`), with `externalActionMetadata` decoding to an `EmporiumStack` whose single `EmporiumOperation` has `invokeWallet=false`, `signerAddress=address(0)`, `endpoint = ERC1155TokenAddress`, and `callData = abi.encodeCall(IERC1155.safeTransferFrom, (address(emporium), attacker, id, amount, ""))`. Since this call is made by Emporium itself, the ERC1155 contract's `from == _msgSender()` check passes trivially, and the tokens are transferred to the attacker with no ERC20 accounting inconsistency being triggered (ERC1155 balance is invisible to `getBalancesForArray`).

None of the existing guards defend against this: `performHinkalChecks`, `verifyProof`, `dimensionsCheck`, `insertNullifiers`, `rootHashExists`, and the circuit's `inTotal + amountChanges === outTotal` constraint all operate solely over the ERC20/ETH `erc20TokenAddresses`/`amountChanges` universe declared in `CircomData`; they have no visibility into or constraint over the `op.endpoint`/`op.callData` bytes executed in Case 2, nor over ERC1155 balances held by Emporium.

### Impact Explanation
Any ERC1155 asset that a victim's stateless op causes to be transferred into the Emporium contract (e.g., a wrapped position or ticket minted/transferred to `address(emporium)` as a side effect of interacting with some protocol) can be fully drained by any subsequent attacker, with zero contribution required from the attacker and no on-chain record linking the deposit to the victim. This is direct theft of a shielded-linked user asset, matching the Critical severity bar. The attack is repeatable for every ERC1155 balance that ever accrues on the Emporium contract from any user's stateless interaction.

### Likelihood Explanation
Preconditions: at least one prior stateless `EmporiumOperation` (from any user) must result in an ERC1155 balance being held by the Emporium contract — plausible for any protocol interaction that mints/returns ERC1155-represented positions to the caller (Emporium). The attacker needs only the ability to submit their own valid, unprivileged Hinkal deposit/proof (a capability every user has) and to craft `externalActionMetadata`/`callData`, both of which are attacker-controlled inputs with no additional validation. No relayer, admin, or victim cooperation is required, making this highly feasible and cheap (cost limited to a normal Hinkal external-action transaction).

### Recommendation
Do not allow arbitrary `op.endpoint.call` targets/calldata in stateless Emporium operations without restricting them to a vetted allowlist of safe operations, or track and gate ERC1155/ERC721 holdings per-owner (e.g., require an explicit UTXO/ownership record before any such asset can leave the contract), and/or disable acceptance of ERC1155/ERC721 assets in `Transferer` unless the specific external action is designed and audited to account for them.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a `MockERC1155`, and wire up `Hinkal`/verifier mocks so both victim and attacker can submit trivial valid proofs.
2. Victim executes a stateless `EmporiumOperation` (endpoint = a mock "position" contract) whose side effect is `MockERC1155.safeTransferFrom(mockPositionOwner, address(emporium), id, amount, "")`, landing the ERC1155 balance on Emporium. Assert `MockERC1155.balanceOf(address(emporium), id) == amount`.
3. Attacker, in a separate transaction with their own unrelated/trivial deposit and proof, submits an `EmporiumStack` with a stateless op: `endpoint = address(MockERC1155)`, `callData = abi.encodeCall(IERC1155.safeTransferFrom, (address(emporium), attacker, id, amount, ""))`.
4. Assert `MockERC1155.balanceOf(address(emporium), id) == 0` and `MockERC1155.balanceOf(attacker, id) == amount` afterward, while the attacker's `erc20TokenAddresses`/UTXO output set shows no debit corresponding to this ERC1155 value — demonstrating the broken equality (victim's deposited value fully transferred to attacker with zero counted contribution/UTXO on the attacker's side).
