Based on my investigation, I found a genuine identity-binding gap in this gem's webhook verification logic.

### Title
Webhook shop identity not bound to HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies only that the HMAC over the raw request body matches (using the app's shared `api_secret_key`), but the `shop-domain` header used to attribute the event to a merchant is never included in the signed content. Any shop that has installed the app can capture one of its own genuine webhook deliveries and replay the same body/HMAC pair to the app's webhook endpoint while spoofing the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to name a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  The `shop` accessor is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which calls `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., HMAC-SHA256 over the body only, using `Context.api_secret_key`, which is the **app-level** secret shared across every shop that installed the app: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `hmac-verified content == content attributed to shop X`. In reality, the HMAC only proves "this body was produced with `api_secret_key`" — it says nothing about which shop the body came from, and the `shop` value handed to the handler is taken from an attacker-controllable header outside the signed scope: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [3](#0-2) 

Because `api_secret_key` is the same for all shops using the app (not a per-merchant secret), any merchant who installs the app receives genuine, validly-HMAC'd webhook deliveries for their own shop. Nothing prevents that merchant (an "unprivileged" holder of a legitimate but low-trust webhook payload) from POSTing the exact same body and HMAC to the app's webhook endpoint while substituting a victim's `shop-domain` header — the HMAC will still validate because it never covered that header. The gem's own documentation asserts this call "will verify the request did indeed come from Shopify" without noting the shop identity is unauthenticated: [5](#0-4) 

### Impact Explanation
This breaks the tenant-isolation binding `shop authenticated == shop attributed to the event`, letting one tenant inject or replay data attributed to a different tenant into the host application's business logic (e.g., orders/customers processing keyed off `data.shop`). This is a cross-tenant data-integrity/isolation violation reachable by any unprivileged party who has legitimately installed the app once and captured one webhook body (identical bodies/HMACs can also arise from templated/duplicate payloads across shops in some topics), satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Requires only that the attacker be a real (even free) merchant install of the app so they receive at least one legitimately signed webhook, then replay it to the app's public webhook endpoint with a forged `shop-domain` header — no access token, `client_secret`, or privileged account needed, and no reliance on the host ignoring documented API behavior since the gem's own `Registry.process`/`Request` classes never bind shop to the signature.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed content, or independently verify that the `shop` header corresponds to a shop with a matching, previously-registered webhook subscription/session before dispatching to the handler. At minimum, document clearly in `Registry.process` that `shop` is unauthenticated and must be cross-checked by the host application against known installed shops.

### Proof of Concept
```ruby
# Attacker owns shop "attacker.myshopify.com" and has installed the target app.
# They receive a genuine webhook delivery:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => "<valid-hmac-for-body>",   # computed by Shopify with the app's shared api_secret_key
  "x-shopify-shop-domain" => "attacker.myshopify.com",
}
body = '{"id":1,"note":"legit order"}'

# Attacker replays the identical body+hmac to the app's public webhook endpoint,
# only changing the shop-domain header to a victim shop:
forged_headers = headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation succeeds (it only checks `body`), and the handler receives
#    WebhookMetadata with shop: "victim-shop.myshopify.com", even though the
#    event never originated from that shop.
