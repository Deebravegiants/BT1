Confirmed mechanism: when `DeleteAccount(beneficiary_id)` fires, `action_delete_account` unconditionally emits `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` for the full account balance [1](#0-0) , without validating that `beneficiary_id` refers to an existing account (only `InvalidAccountId` format checks apply, per the action spec) [2](#0-1) . When that refund receipt executes, `action_transfer_or_implicit_account_creation` is invoked; since the receipt is a refund (`is_refund = true`, `predecessor_id().is_system()`), the `debug_assert!(!is_refund)` guard on the implicit-account-creation branch shows this path is deliberately never supposed to be taken for a non-existent, non-implicit account [3](#0-2) , and the code comments explicitly state "Refunds don't automatically create accounts, because refunds are free and we don't want some type of abuse" [4](#0-3) . If `beneficiary_id` is a syntactically valid but non-existent (and non-implicit-eligible) account, the refund receipt's execution fails at `check_account_existence`/`AccountDoesNotExist`, and because it is a refund, `apply_action_receipt` burns the deposit into `other_burnt_amount` instead of returning it to anyone [5](#0-4) .

This is exactly the coupling failure described in the report: `beneficiary_id` (an unprivileged, user-supplied action parameter, like `escrowPool`) is not required to be tightly coupled with a real, existing account (like `escrowPool != 0` when `escrowPortion != 0`), so an account holder who deletes their account and misconfigures/mistypes the beneficiary permanently burns their own balance instead of it being recoverable or refused up front.

### Title
Unvalidated `DeleteAccount` beneficiary permanently burns the deleted account's balance if the beneficiary account does not exist - (File: runtime/runtime/src/actions.rs)

### Summary
`DeleteAccountAction::beneficiary_id` is validated only for well-formed `AccountId` syntax, not for account existence, at both the action-validation layer and inside `action_delete_account`. If the beneficiary does not exist as an account (and is not eligible for implicit-account auto-creation), the balance-refund receipt generated for it fails execution and the entire deleted account's balance is burned rather than being lost or refunded to the deleting user.

### Finding Description
`action_delete_account` computes `account_balance = account_ref.amount()` and, if positive, unconditionally queues `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` before removing the account [6](#0-5) . There is no check anywhere in the delete-account action path that `beneficiary_id` corresponds to a live account; validation only rejects a malformed `AccountId` string [7](#0-6) .

When the resulting refund receipt is later processed, its single `Transfer` action goes through `action_transfer_or_implicit_account_creation`. Refund receipts are identified by `predecessor_id().is_system()` and are explicitly barred from implicit-account creation (`debug_assert!(!is_refund)`), per the documented rationale that "Refunds don't automatically create accounts, because refunds are free and we don't want some type of abuse" and "Account deletion with beneficiary creates a refund, so it'll not create a new account" [4](#0-3) [8](#0-7) . Consequently, if `beneficiary_id` names a non-implicit account that has never been created, `check_account_existence` fails the receipt with `AccountDoesNotExist`. Because this is a refund receipt, `apply_action_receipt` does not generate a further refund for the failure — it instead adds the full deposit to `other_burnt_amount`, i.e. it is permanently removed from total supply [5](#0-4) .

This mirrors the reported bug class exactly: two logically coupled parameters (`escrowPortion`/`escrowPool` in the report; here, "have a nonzero balance to refund" / "beneficiary_id must be a live, refundable account") are not jointly validated, so a misconfiguration silently destroys value instead of being rejected or safely handled.

### Impact Explanation
Any unprivileged account holder who submits a `DeleteAccount` action (directly, via a contract's `promise_batch_action_delete_account` host function, or via a meta-transaction) with a `beneficiary_id` that is syntactically valid but does not exist as an account (e.g., a typo, an account that was never funded/created, or a sub-account name that was never registered) irrevocably burns their entire remaining account balance. This is a concrete, permanent loss of user funds (removed from total supply as `other_burnt_amount`) with no recovery path, triggered purely by a self-inflicted but easy-to-make input error, exactly analogous to the escrow-loss scenario in the original report.

### Likelihood Explanation
The path is reachable by any account with a nonzero balance issuing a standard `DeleteAccountAction`/`promise_batch_action_delete_account` — no privileged role, validator status, or special network conditions are required. The failure mode requires only that the user (or a buggy/malicious contract acting on the user's behalf) specify a `beneficiary_id` that is not a real, existing account and not implicit-account-eligible, which is a common class of user error (e.g., typos, wrong network/testnet account names, referencing an account not yet created).

### Recommendation
Before generating the delete-account balance-refund receipt (or before accepting the `DeleteAccountAction` at validation time), verify that `beneficiary_id` corresponds to an existing account, or otherwise ensure the refund can be delivered (e.g., by supporting implicit-account creation for the delete-account refund path, or by rejecting the action outright with an explicit error such as `BeneficiaryAccountDoesNotExist` when the account cannot be verified to exist). At minimum, surface this failure mode clearly to callers so wallets/SDKs can pre-validate the beneficiary before submitting the transaction.

### Proof of Concept
1. Create account `alice.near` with a nonzero balance.
2. Have `alice.near` submit `DeleteAccountAction { beneficiary_id: "nonexistent.near" }` (or use `promise_batch_action_delete_account` from a contract with a fresh, unregistered sub-account name) where `nonexistent.near` has never been created and is not eligible for implicit-account auto-creation.
3. `action_delete_account` removes `alice.near` and queues a `Receipt::new_balance_refund("nonexistent.near", balance)` [6](#0-5) .
4. When that refund receipt executes, `check_account_existence` fails with `AccountDoesNotExist` because the refund path cannot create the account [4](#0-3) .
5. `apply_action_receipt` treats this as a failed refund and adds the entire balance to `other_burnt_amount`, permanently destroying it [5](#0-4) .

fn action_transfer_or_implicit_account_creation(
    account: &mut Option<Account>,
    deposit: Balance,
    is_refund: bool,
    action_receipt: &VersionedActionReceipt,
    receipt: &Receipt,
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    actor_id: &mut AccountId,
    epoch_info_provider: &dyn EpochInfoProvider,
) -> Result<(), RuntimeError> {
    Ok(if let Some(account) = account.as_mut() {
        let is_gas_refund = is_refund && action_receipt.signer_id() == receipt.receiver_id();
        // For gas refunds, try to refund to the gas key first. If the signer key is a gas key,
        // the refund goes to the gas key balance and we skip crediting the account balance.
        if is_gas_refund
            && try_refund_gas_key_balance(
                state_update,
                receipt.receiver_id(),
                &action_receipt.signer_public_key(),
                deposit,
            )?
        {
            return Ok(());
        }
        action_transfer(account, deposit)?;
        if is_gas_refund {
            try_refund_allowance(
                state_update,
                receipt.receiver_id(),
                &action_receipt.signer_public_key(),
                deposit,
            )?;
        }
    } else {
        debug_assert!(!is_refund);
        action_implicit_account_creation_transfer(
            state_update,
            &apply_state,
            &apply_state.config.fees,
            account,
            actor_id,
            receipt.receiver_id(),
            deposit,
            apply_state.block_height,
            epoch_info_provider,
        );
    })
