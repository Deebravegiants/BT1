### Title
Cross-tenant webhook spoofing via unbound `shop-domain` header in `Webhooks::Request` HMAC validation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from an HTTP header (`shopify-shop-domain` / `x-shopify-shop-domain`) that is never included in the HMAC-signed material. `to_signable_string` returns only the raw request body, so the signature proves the body came from an entity holding `Context.api_secret_key`, but proves nothing about which shop the header claims the event is for.

### Finding Description
`Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from unauthenticated HTTP headers: [3](#0-2) 

After successful HMAC validation, `Registry.process` passes `request.shop` (and `request.topic`) directly into `WebhookMetadata`, which the app-supplied handler uses to attribute the event to a tenant: [1](#0-0) 

This breaks the intended identity binding: **bytes verified (the raw body, keyed by the app's shared secret) ≠ bytes parsed as tenant identity (the `shop-domain` header)**. This is directly analogous to the reward-rate mismanagement bug class described in the report — a value used to drive business logic (`shop`) is not covered by the same integrity check (`HMAC`) that authenticates the payload it's paired with, so the two can be desynchronized by an attacker who controls the unauthenticated part.

Contrast this with `Auth::Oauth::AuthQuery`, where `shop` (and `host`) *are* included in `to_signable_string`, so the OAuth callback correctly binds shop identity to the signature: [4](#0-3) 

The webhook path has no equivalent binding.

### Impact Explanation
An attacker who can install the target app on their own (attacker-controlled) shop receives genuine, validly-signed webhook deliveries from Shopify for that shop (e.g., `orders/create`, `customers/data_request`, `shop/redact`, or any topic whose body content the attacker can influence, such as creating an order with attacker-chosen line-item text). Because `to_signable_string` covers only the body, the attacker can replay that exact `raw_body` + `hmac` pair to the victim app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop domain. `HmacValidator.validate` still succeeds (the body/HMAC pair is authentic and was genuinely signed by Shopify with the app's secret), and `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop. Any app logic that trusts `data.shop` for tenant-scoped writes, GDPR redaction, deauthorization, or state transitions can be manipulated into acting against a different tenant than the one that actually generated the event — a cross-tenant integrity violation reachable by any user able to install the app on a shop they control, without needing the app's `client_secret` or any privileged credential.

### Likelihood Explanation
Requires the attacker to have (or create) their own shop with the target app installed — feasible for any public/free-install app — and requires the host application to key any tenant-sensitive action off `WebhookMetadata#shop`/`#topic` without an independent cross-check (e.g., matching against a shop already known from OAuth). This is a realistic and commonly-relied-upon pattern for consumers of this gem, since the library's documented `process` API is the sole authentication step offered for webhooks. Likelihood is moderate: it needs an attacker-controlled tenant plus a host app that trusts the header-derived `shop` for privileged effects, but no secret leakage, MITM, or social engineering.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-covered material, or otherwise cryptographically tie the header-derived tenant identity to the signed body — e.g., include the `shop-domain` header value in `to_signable_string`, or require callers to cross-validate `request.shop` against a shop they already have an active, independently-established session/installation record for before acting on the webhook. At minimum, document prominently that `shop` from `Webhooks::Request` is unauthenticated and must be cross-checked against known installed shops before use.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (a shop they control).
2. Attacker triggers an event (e.g., creates an order) causing Shopify to deliver a webhook with body `B` and header `shopify-hmac-sha256: H` (a valid signature over `B` using the app's `api_secret_key`), plus header `shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the identical `B` and `H` to the app's webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com`.
4. `Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim.myshopify.com", hmac-sha256: H...})` is constructed: [5](#0-4) 
5. `Registry.process(request)` calls `HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds, because `shop` is not part of the signed string: [6](#0-5) 
6. The registered handler executes with `WebhookMetadata#shop == "victim.myshopify.com"`, even though the event actually originated from `attacker.myshopify.com`, demonstrating the cross-tenant identity break.

          received_signature = verifiable_query.hmac

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|

            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
