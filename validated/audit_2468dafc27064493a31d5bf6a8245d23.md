### Title
`FeeVault.claim()` pays only `msg.sender`, permanently freezing a creator's accrued USDC fees if that address is later blacklisted by USDC - (File: packages/contracts/src/FeeVault.sol)

### Summary
`FeeVault.claim()` has no recipient parameter: it always transfers the caller's `creatorBalance[msg.sender]` to `msg.sender` itself via `safeTransfer`. If the creator's own address is later added to USDC's blacklist, the `safeTransfer` call reverts every time `claim()` is called, and there is no on-chain path to redirect the already-accrued balance to a different, non-blacklisted address, permanently freezing that creator's fees. This is the same root-cause pattern as the referenced report: a single-recipient claim path (`msg.sender`-only) with no way to specify an alternate recipient once that address becomes untransferable for the settlement token.

### Finding Description
`claim()` is defined as: [1](#0-0) 

It reads `creatorBalance[msg.sender]`, zeroes it, and calls `$.usdc.safeTransfer(msg.sender, amount)` — the recipient is hard-coded to `msg.sender`, with no parameter to redirect the payout.

The only mechanism that changes "creator" attribution is `Bonding.transferCreator`: [2](#0-1) 

This only updates `TokenInfo.creator` in `Bonding`, which affects *future* fee attribution passed into `FeeVault.accrue(token, creator, ...)` on subsequent trades. It does **not** touch the already-accrued `FeeVault.creatorBalance[oldCreator]` mapping entry, which is keyed by the address that was `creator` at the time each `accrue` call happened: [3](#0-2) 

So once USDC accrues against a given creator address, that specific address's `creatorBalance` mapping slot is the only place those funds exist, and `claim()` can only ever pay out to that same address.

If USDC (or any blacklist-capable stablecoin used as `$.usdc`) blacklists that creator's address for any reason (KYC/AML action, false positive, sanctions list, compliance mistake, etc.), `IERC20.transfer(msg.sender, amount)` reverts unconditionally inside `safeTransfer`, because the recipient is blacklisted. Since `claim()` offers no recipient argument, there is no way for the creator — or anyone — to redirect that specific balance to a fresh, non-blacklisted address. `transferCreator` cannot help because it doesn't move the FeeVault balance, only future attribution. `claimProtocol()` and `sweepDonations()` at least route to an admin-settable `feeTo`, but the creator-facing `claim()` path has no analogous recipient flexibility and no admin override.

### Impact Explanation
This permanently freezes a creator's already-earned USDC fees (`creatorBalance[creator]`), which can grow unbounded over the token's trading lifetime (0.25% of every buy/sell for that creator's launched tokens, per `docs/contracts-scope.md:112-122`). There is no owner-level rescue: `FeeVault` has no sweep/rescue function for `creatorBalance`, no way to reassign a specific creator's already-accrued balance, and `usdc.safeTransfer` will keep reverting for that address indefinitely. This is a permanent freezing of creator funds, matching the report's impact class exactly (funds become unretrievable once a blacklist event occurs against the one hard-coded recipient address).

### Likelihood Explanation
Reaching this state requires no privileged action by the protocol — it is purely a consequence of USDC's centralized blacklist policy, which is an accepted external risk for any protocol paying out real USDC. Any creator address that accumulates fees and is later blacklisted (for any reason, valid or erroneous) triggers this permanently, on the very next and every subsequent `claim()` call. Given the protocol explicitly deals in real USDC (`FeeVault.usdc()`), and blacklisting is a known, documented behavior of centralized stablecoins, likelihood is non-trivial over the life of the protocol, though it depends on an external, out-of-protocol-control event.

### Recommendation
Add a `recipient` parameter to `claim()` (and consider one for `claimProtocol()`/`sweepDonations()` for consistency), allowing the caller to redirect payout to an alternate address they control, mirroring `NonfungiblePositionManager.collect()`'s design. Alternatively, add an owner-gated `rescueCreatorBalance(address creator, address to)` function restricted to cases where `usdc.transfer` to `creator` demonstrably fails, so legitimately blacklisted creators aren't permanently locked out of funds they've already earned.

### Proof of Concept
1. `Zap` accrues creator fees for `creator` via `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)` across many trades, growing `creatorBalance[creator]`. [3](#0-2) 
2. USDC's issuer blacklists `creator`'s address (a real, documented USDC admin capability, external to this codebase).
3. `creator` calls `Bonding.transferCreator(token, newAddress)` hoping to redirect future *and* past earnings — this only updates `TokenInfo.creator` for future accruals; `creatorBalance[creator]` in `FeeVault` is untouched. [2](#0-1) 
4. `creator` (or anyone) calls `FeeVault.claim()`. Execution reaches `$.usdc.safeTransfer(msg.sender, amount)` with `msg.sender == creator`, which is blacklisted; the transfer reverts, and the whole `claim()` transaction reverts. [1](#0-0) 
5. Every future call to `claim()` from `creator` reverts identically. `creatorBalance[creator]` remains non-zero, and its underlying USDC is permanently stranded inside `FeeVault` with no owner-level or protocol-level rescue path.

```text
    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }
```

```text
    function claim() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
        emit CreatorFeesClaimed(msg.sender, amount);
    }
```

```text
    function transferCreator(
        address tokenAddress,
        address newCreator
    ) external {
        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
    }
```
