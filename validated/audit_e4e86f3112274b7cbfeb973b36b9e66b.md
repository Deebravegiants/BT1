### Title
Permanent freezing of bridged/burned funds when the fee refund transfer reverts on `PostRequestTimeout` handling - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatchTimeOut(PostRequestTimeout, ...)` first invokes the destination app's `onPostRequestTimeout` callback (which performs a state-changing refund action, e.g. re-minting burned tokens) and then, in the same transaction, attempts to refund the relayer fee to the original `payer` via a direct `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)`. If `meta.sender` (the original dispatcher/payer) is on a token blocklist (USDC/USDT-style), this transfer reverts unconditionally, which reverts the *entire* transaction — including the app-level refund that had already succeeded — with no fallback path.

### Finding Description
`dispatchTimeOut` for `PostRequestTimeout` is: [1](#0-0) 

The function deletes the request commitment for replay protection, calls the app's `onPostRequestTimeout` via a low-level `.call`, and — critically — only guards against *that* call failing (`if (!success) { restore commitment; return; }`). It does **not** guard the subsequent fee refund:
```solidity
if (meta.fee != 0) {
    // refund relayer fee
    IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
}
```
This uses `safeTransfer`, which reverts on failure, and reverting here rolls back the *whole* `dispatchTimeOut` call — including the successful `onPostRequestTimeout` execution and the `delete _requestCommitments[commitment]`.

The `meta.sender` here is `post.payer`, set at dispatch time by the originating application (e.g. `HyperFungibleToken.send()`/`HyperFungibleTokenUpgradeable.send()` sets `payer: msg.sender`): [2](#0-1) 

The corresponding app flow burns the sender's tokens on `send()` and expects `onPostRequestTimeout` to re-mint them back if the message times out without delivery: [3](#0-2) 

Because the feeToken is configured per-host and is typically a centralized stablecoin (DAI/USDC per the docs), any dispatcher/sender whose address later becomes blocklisted on that fee token permanently cannot have their timed-out request processed: every retry of `dispatchTimeOut` will re-run `onPostRequestTimeout` (idempotently minting) but then hit the same reverting `safeTransfer`, reverting the whole call again, forever. Unlike the mirrored `GetRequestTimeout` variant which pays the same risk, this specific path directly gates recovery of previously burned/locked user funds.

### Impact Explanation
This is a permanent freezing-of-funds bug: any user whose address is later blocklisted by the fee token issuer (for reasons entirely unrelated to Hyperbridge) loses the ability to ever have their timed-out cross-chain message processed on the host contract, because the relayer-fee refund step is not isolated from the app-level refund step. Since `HyperFungibleToken`-style apps burn tokens on `send()` and rely exclusively on either successful delivery or `onPostRequestTimeout` to restore balance, a permanently-reverting timeout handler means the burned tokens are irrecoverable — a direct, permanent loss of user funds. This mirrors the reported Cooler bug class (an untouchable ERC20 transfer to a griefable/blocklistable address gating an otherwise-legitimate state transition, causing default/permanent loss).

### Likelihood Explanation
Reachable by any relayer submitting a timeout proof for any request whose original payer got blocklisted on the fee token after dispatch — a normal, permissionless operational path (timeouts are expected and routinely processed). No malicious relayer/governance action is needed; the condition is solely "payer's address is blocklisted on `feeToken()`" which can happen to any ordinary user of a blocklist-capable stablecoin (USDC/USDT) used as the fee token. Given Hyperbridge's own docs state DAI is the "typical choice ... for its decentralized properties" specifically to avoid this class of risk, the design already implicitly acknowledges the danger, indicating real awareness of the risk surface but incomplete mitigation on this specific timeout path.

### Recommendation
Decouple the relayer-fee refund from the app-level timeout callback so a reverting transfer cannot block or roll back the app's already-successful refund. Options:
- Wrap the fee refund in a try/catch (or low-level `call`) and, on failure, credit the amount to a withdrawable balance for `meta.sender` instead of a push transfer, mirroring the `IntentGatewayV2` pull-based withdrawal pattern already used elsewhere in the codebase.
- Alternatively, perform the fee refund via `.call` with a checked-but-non-reverting fallback that escrows to an internal "unclaimed fees" mapping when the push transfer fails, so the request/commitment cleanup and app callback can always finalize regardless of the state of the fee token account.

### Proof of Concept
1. `HyperFungibleTokenUpgradeable.send()` is called by `alice`, burning `amount` tokens and dispatching a POST request with `payer: alice` and non-zero `relayerFee`.
2. Before delivery, the destination fails to accept the message (or the request otherwise times out), and `alice`'s address becomes blocklisted on the host's configured `feeToken` (e.g., she is sanctioned/blocklisted by the USDC issuer for unrelated reasons).
3. A relayer submits the timeout proof; `EvmHost.dispatchTimeOut(PostRequestTimeout, meta, commitment)` is invoked.
4. `IApp(request.from).onPostRequestTimeout(timeout)` succeeds and re-mints `amount` to `alice` inside the same call frame.
5. Execution reaches `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` with `meta.sender = alice`; the fee token's `transfer` reverts because `alice` is blocklisted.
6. The entire `dispatchTimeOut` transaction reverts, undoing the re-mint from step 4 as well as the commitment cleanup.
7. Every subsequent relayer retry hits the identical revert. `alice`'s originally burned tokens can never be restored — permanent loss.

```text
    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
```

```text
    /**
     * @notice Handles timeout of a previously dispatched cross-chain transfer
     * @dev Called by the ISMP host when a sent message times out without being delivered.
     * Re-mints the burned tokens back to the original sender as a refund.
     * @param incoming The timed-out POST request and the relayer that submitted the timeout proof
     */
    function onPostRequestTimeout(PostRequestTimeout memory incoming) external override onlyHost whenNotPaused {
        Message memory message = abi.decode(incoming.request.body, (Message));
        address refundee = _toAddr(message.from);
        _mint(refundee, message.amount);
        emit Refunded({to: refundee, amount: message.amount});
    }
```
