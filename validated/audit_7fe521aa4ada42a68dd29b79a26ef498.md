### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC computed over the raw request body, but then trusts the unauthenticated `shopify-shop-domain` (or `x-shopify-shop-domain`) header as the tenant identity passed to the app's handler. The `shop` field acted upon by the handler is never included in the signed material, breaking the intended binding of "authenticated shop == shop the handler acts on."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively from `to_signable_string` (i.e., the raw body) using the app's `client_secret`, and never touches the `shop`, `topic`, or `webhook_id` headers: [2](#0-1) 

`Registry.process` validates the request via this body-only HMAC, then reads `request.shop` — sourced directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed payload — and forwards it unchanged to the app's webhook handler as the tenant identity: [3](#0-2) [4](#0-3) 

Because every shop installed on a given app shares the same `client_secret`, an attacker who controls (or has installed) their own shop on the app can capture a legitimate `(raw_body, hmac)` pair generated by Shopify for their own shop's webhook, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still succeed, because it only checks the body against the secret — the shop field is invisible to it. The app's handler, per the documented contract, receives `WebhookMetadata` (`topic`, `shop`, `body`, `webhook_id`, `api_version`) and is expected to attribute and act on the webhook using `data.shop`: [5](#0-4) 

This is exactly the bug-class pattern from the external report: a field that governs subsequent authorization/attribution logic (there, `_depositFor`; here, `shop`) is controllable by the caller and not covered by the identity check that gates the operation (there, `lastTransactionBlock`; here, the HMAC).

### Impact Explanation
This enables cross-tenant confusion: a malicious merchant/attacker with a legitimate install on the same app can forge webhook deliveries that the app attributes to a victim shop. Depending on how the host app implements its handler (e.g., updating order/customer/product state, triggering fulfillment or GDPR redaction flows keyed off `data.shop`), this can lead to state corruption or actions performed against a shop the attacker doesn't control, i.e., cross-tenant access/impact, which meets the "High/Critical - cross-tenant access" bar.

### Likelihood Explanation
Medium. It requires the attacker to control at least one legitimate app installation (a shop) that receives real webhooks from Shopify with a valid HMAC — a low bar for any developer/malicious merchant who installs a public app or a private test copy of the target app — and then to POST the captured `(raw_body, hmac)` pair to the same publicly reachable webhook endpoint with a forged shop header. No knowledge of `client_secret` or any privileged credential is required beyond controlling one's own shop's webhook traffic.

### Recommendation
Bind the trusted identity fields (`shop-domain`, `topic`, `webhook-id`) into the signed material that `HmacValidator` verifies, or otherwise cryptographically tie the `shop` header to the signed body (e.g., include it in `to_signable_string`, or independently verify shop identity against a previously established session/webhook subscription record before invoking the handler). At minimum, document prominently that `request.shop` is unauthenticated and host apps must independently verify shop ownership/subscription before trusting it for any state-changing or tenant-scoped action.

### Proof of Concept
1. Attacker registers/owns "shop-attacker.myshopify.com" on the target app and receives a legitimate webhook delivery from Shopify for topic `orders/create`:
   - `raw_body = '{"id":123}'`
   - `shopify-hmac-sha256 = <valid HMAC of raw_body using app's client_secret>`
   - `shopify-shop-domain = "shop-attacker.myshopify.com"`
2. Attacker replays the request to the app's webhook endpoint unchanged except:
   - `shopify-shop-domain = "victim-shop.myshopify.com"`
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this into a `Request` whose `hmac` and `to_signable_string` are unaffected by the header change: [6](#0-5) 
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the secret: [7](#0-6) 
5. The registered handler is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, despite the payload never having been authenticated for that shop — the app processes/attributes the webhook to the wrong tenant.
