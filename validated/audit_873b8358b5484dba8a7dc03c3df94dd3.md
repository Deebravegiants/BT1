## Title
`IntentGatewayV2.placeOrder` hardcodes the Uniswap V2 fee-swap deadline to `block.timestamp`, exposing native-fee payers to stale-price execution and sandwich attacks - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder` lets a user pay the solver fee (`order.fees`) in native token instead of the fee token. When `msg.value > 0`, the contract swaps native token for the exact fee-token amount via `IUniswapV2Router02.swapETHForExactTokens`, but passes `block.timestamp` as the `deadline` argument, which — exactly like the Venus `RiskFund` finding — provides no real deadline protection at all.

### Finding Description
In `placeOrder`, the fee-collection branch performs: [1](#0-0) 

`block.timestamp` is evaluated at the time the transaction is *mined*, not when it was signed, so it imposes no bound on how long the transaction may sit in the mempool before inclusion. This is the identical root cause described in the referenced Venus `RiskFund.swapPoolsAsset` report: users have no way to supply a real deadline, so a delayed-inclusion or MEV-sandwiched transaction executes against a stale/manipulated price with no protection from the deadline mechanism.

The same pattern is duplicated in the Tron and SDK-bundled copies of the contract: [2](#0-1) 

Unlike a plain `swapExactTokensForTokens` call with a caller-supplied `amountOutMin`, this call is `swapETHForExactTokens` where `amountOut = order.fees` is fixed and `amountInMax = msg.value`. This bounds the worst case (the router reverts with `EXCESSIVE_INPUT_AMOUNT` if the required input exceeds `msg.value`), but it does not eliminate loss: an attacker can sandwich the pending `placeOrder` transaction to push the required WETH input up to just under `msg.value`, consuming nearly the user's entire fee budget and returning little/no refund (`msgValue -= amounts[0]`, then `_sendValue` refunds only the leftover), extracting the difference as sandwich profit. Because there is no deadline, this stale/pending transaction remains sandwichable indefinitely instead of expiring safely.

### Impact Explanation
This is a direct, exploitable value-extraction vector against any user who places an order and elects to pay the solver fee in native token: an MEV bot can detect the pending `placeOrder` call, sandwich it, and capture most of the native-token buffer the user attached for the fee swap as arbitrage profit, at the user's expense. This affects the core, unprivileged, single-transaction entry point for the Intent Gateway (`placeOrder`), reachable by any ordinary intent-placer with no special privileges.

### Likelihood Explanation
Likelihood is moderate: it requires (a) the user to pay fees via native token (`msgValue > 0` path) and (b) either delayed inclusion or an MEV searcher actively monitoring the mempool for `placeOrder` calls with a swap component — a well-known and automatable MEV pattern. Because Uniswap V2 pools are public and easily manipulated within a single block, and because `placeOrder` transactions are plainly visible with their exact swap parameters in calldata, this is realistically exploitable whenever meaningful value flows through the native-fee path.

### Recommendation
Add a `deadline` parameter to the `Order`/`placeOrder` call surface (or derive a bounded deadline, e.g. `block.timestamp + maxDelay`, from a caller-supplied `maxDelay`) and pass it through to `swapETHForExactTokens` instead of `block.timestamp`, in both `evm/src/apps/IntentGatewayV2.sol` and the duplicated `evm/tron/contracts/apps/IntentGatewayV2.sol` (and any other bundled copies, e.g. under `sdk/packages/core/contracts/apps/`). This ensures a transaction that sits in the mempool past its intended execution window reverts instead of executing at a stale/manipulated price.

### Proof of Concept
1. User calls `placeOrder` with `order.fees > 0`, paying via native token (`msg.value` covering the fee swap plus buffer), per the flow shown in `evm/tests/foundry/IntentGatewayV2Test.sol` (`testPlaceOrder_FeeSwap_RefundsExcessNativeToken`, lines 3713-3752) which demonstrates the exact `swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), block.timestamp)` call path.
2. The transaction is broadcast but sits pending (low gas price, or is observed by an MEV searcher before inclusion).
3. A searcher front-runs with a large WETH→feeToken buy, inflating the feeToken price; `placeOrder`'s swap then executes needing close to `msg.value` worth of ETH to obtain `order.fees` feeTokens (bounded by `amountInMax = msg.value`, so it doesn't revert but nearly exhausts the buffer); the searcher back-runs to sell feeToken back, capturing the price differential as profit while the user's refund (`msgValue -= amounts[0]`) shrinks correspondingly.
4. Because `deadline = block.timestamp` (evaluated at inclusion time), there is no mechanism preventing this delayed/sandwiched execution.
