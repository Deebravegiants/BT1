### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is trusted for tenant identity without being covered by the HMAC signature, allowing cross-tenant spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw HTTP body, while the tenant-identifying `shop-domain` header (as well as `topic` and `webhook-id`) is read separately from unauthenticated headers and never bound into the HMAC computation. `Registry.process` accepts any request whose body HMAC validates and then propagates the *unsigned* `shop` header straight into the webhook handler as the trusted tenant identity, without any secondary check that the shop is the one Shopify actually attributed to that body.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` value from the request [1](#0-0) . For webhooks, `to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers with no cryptographic linkage to the signature [3](#0-2) .

`Registry.process` validates only the HMAC of the body and then trusts `request.shop` (and `request.topic`) as the tenant/event identity that gets forwarded to the app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) .

This breaks the identity binding `shop authenticated == shop bound to signed bytes`. Anything with a valid `(raw_body, hmac)` pair signed by the app's `client_secret` — which Shopify legitimately delivers to *any* shop that installs the app, including an attacker-controlled test store — can be replayed to the app's own public webhook endpoint with an arbitrary `shopify-shop-domain` header substituted in. Because `hmac-sha256` never covers that header, the forged header passes `HmacValidator.validate` and the app processes attacker-supplied event data (`topic`, `body`, `webhook_id`) under a victim shop's identity.

### Impact Explanation
This is a cross-tenant identity binding break: an unprivileged merchant who legitimately installs the app on their own store receives genuine, correctly-signed webhooks for their own shop's events. By capturing one such `(raw_body, hmac)` pair and replaying it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop, they can make the host application believe attacker-controlled body content originated from the victim tenant. Depending on how the host app's webhook handler uses `WebhookMetadata#shop` (e.g., to look up the victim's stored session/access token and act on their behalf, or to write attacker data into the victim's tenant records), this can result in cross-tenant data corruption or unauthorized actions taken under another merchant's identity — meeting the "cross-tenant access" bar for Critical impact.

### Likelihood Explanation
Likelihood is high for any app that relies on `ShopifyAPI::Webhooks::Registry.process`/`Request` as documented: any user can install the app on a store they control, capture a real webhook delivery (raw body + `hmac-sha256`), and replay it to the app's public webhook endpoint with a substituted `shop-domain` header. No secrets, tokens, or privileged access are required — only the ability to receive one's own app-installed webhook and issue an HTTP POST to the app's public endpoint.

### Recommendation
Bind the tenant-identifying headers into the signed material, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the validated bytes rather than trusting them as independently-parsed headers. At minimum, `to_signable_string` (or an additional validation step in `Registry.process`) should incorporate `shop-domain` (and ideally `topic`, `webhook-id`) so that a valid HMAC for one shop's payload cannot be revalidated after swapping in a different shop's identity header.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body under client_secret>`, body: `{"id": 1, ...}`.
2. Attacker crafts a new HTTP POST to the app's public webhook endpoint, keeping the exact same `raw_body` and `x-shopify-hmac-sha256` value, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `OpenSSL::HMAC.hexdigest(sha256, secret, raw_body)` against the supplied HMAC [1](#0-0)  — this still passes because the body is unchanged.
4. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: ...)` [5](#0-4) , causing the host application to process attacker-supplied data under the victim's tenant identity.
