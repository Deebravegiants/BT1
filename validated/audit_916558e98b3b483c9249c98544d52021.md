## Analysis

The gem's webhook-processing HMAC verification only signs the raw request body, not the shop-identifying header that downstream handler code trusts for tenant attribution — the same class of flaw as the referenced report (a value used to route/act, but not bound by the value that was actually authenticated).

### Title
Webhook `shop-domain` header is trusted for tenant attribution without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator.validate` binds solely to the body bytes. [1](#0-0) [2](#0-1) 
Yet `Registry.process` passes `request.shop` — parsed straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header — into `WebhookMetadata` and forwards it to the app's registered `handler.handle`, after confirming only that the HMAC over the body is valid. [3](#0-2) 

### Finding Description
The equality that should hold is: `shop_bound_by_hmac == shop_used_for_tenant_attribution`. Here it does not — `to_signable_string` (the bytes actually HMAC-verified) is just `@raw_body`, while `shop` is read independently from a header that is excluded from the signable string. [4](#0-3) 
`HmacValidator.validate_signature` compares the received `hmac` against `HMAC(secret, verifiable_query.to_signable_string)`, i.e. `HMAC(secret, raw_body)` — never incorporating `shop`, `topic`, or `webhook_id`. [5](#0-4) 
Because `Registry.process` only calls `Utils::HmacValidator.validate(request)` before dispatching, any request whose body+hmac pair is valid for *some* shop will pass validation regardless of which shop's domain is asserted in the header, and that attacker-controlled header value is what's handed to the app's handler as the authoritative tenant identifier. [6](#0-5) 

### Impact Explanation
This breaks the tenant boundary the HMAC is meant to establish: a `(topic, body, hmac)` triple that is valid because it was genuinely sent by Shopify for shop A can be replayed with the `shopify-shop-domain` header rewritten to shop B, and the gem will report it to the app's handler as an authenticated webhook for shop B carrying shop A's payload data. This is a cross-tenant integrity violation delivered through a code path in this gem (`Registry.process`), not merely a host-application oversight, since the gem itself computes and exposes `request.shop` as trustworthy metadata after "validating" the request.

### Likelihood Explanation
Any unprivileged actor who can capture or otherwise obtain one legitimately HMAC-signed webhook body (for example, from their own installed app/shop) can replay it to the app's webhook endpoint with a modified shop header; no `api_secret_key` or other app secret is required to mount the attack, only knowledge of one already-valid `(body, hmac)` pair.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the HMAC-signable string, or otherwise force callers to independently authenticate the shop before trusting `request.shop`/`WebhookMetadata#shop`, e.g. by including these fields in `to_signable_string` so `HmacValidator.validate` fails when they are altered.

### Proof of Concept
1. Attacker registers an app/shop (shop A) and receives a genuine webhook: headers include `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: shop-a.myshopify.com`, body `B`.
2. Attacker resends this exact `(B, H)` pair to the same endpoint but with `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares to `H` — this still matches because the shop header is not part of `to_signable_string`. [1](#0-0) 
4. Validation succeeds, and `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: ...)` is dispatched to the handler, so the app processes shop A's payload as if it belonged to shop B. [7](#0-6)
