### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw webhook body, excluding the `shop-domain` header from the HMAC-signed content. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over that body-only string and then trusts `request.shop` (read straight from the unauthenticated header) to build the `WebhookMetadata` passed to the host app's handler. This breaks the intended binding `shop == HMAC-authenticated tenant`, because the shop identifier acted upon by the handler is not one of the bytes verified by the signature.

`to_signable_string` returns only `@raw_body`. `Utils::HmacValidator.validate` computes and compares the HMAC exclusively over that signable string: [4](#0-3) 

`Registry.process` then raises only if that body-only HMAC fails, and unconditionally forwards `request.shop` — read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header — to the host app's handler as the tenant identifier: [5](#0-4) [6](#0-5) 

Compare this to the OAuth callback HMAC, where `shop` *is* included in the signed content: [7](#0-6) 

So for OAuth callbacks the equality `hmac-verified bytes ⊇ {shop}` holds, but for webhooks it does not: the field the handler acts on (`data.shop`) is disjoint from the field the HMAC verifies (`raw_body`). Any request body with a valid signature — for any shop — carries an attacker-controlled, unverified `shop-domain` value that the handler trusts as the tenant identity.

### Impact Explanation
An app's `client_secret` (the HMAC key) is shared by Shopify across every shop that installs the same public app; it is not shop-specific. A user who installs the app on their own (unprivileged) development/test shop legitimately receives Shopify-signed webhook deliveries for their own shop. Because the signature covers only the body, the attacker can replay that captured, validly-signed body to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value naming a different, victim tenant. `Registry.process` will validate the HMAC (it never inspected the shop header) and hand the handler a `WebhookMetadata` claiming the webhook is from the victim shop. Any host app that uses `data.shop` from the documented API (as the official docs at `docs/usage/webhooks.md` instruct: `"shop", String - The shop domain of the webhook"`) to key data storage, trigger side effects, or attribute the payload to a tenant will process attacker-supplied data under an arbitrary victim's identity — a cross-tenant data-injection/spoofing primitive, without ever needing `api_secret_key` or any credential belonging to the victim.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target app on an attacker-controlled shop (any merchant can do this — a normal, low-privilege action), (2) capturing one legitimate webhook delivery to that shop (trivial, since the attacker controls the receiving endpoint or can log the request), and (3) POSTing the identical body/HMAC to the same public webhook endpoint with a modified `shop-domain` header. No secrets, tokens, or elevated access are needed.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed content, or otherwise separately authenticate that the `shop-domain` header corresponds to a shop that has genuinely installed the app (e.g., cross-check against stored, previously-verified shop/session records) before passing it to the handler. At minimum, document prominently that `data.shop` in `WebhookMetadata` is unauthenticated and must be independently validated by the host application before being trusted as a tenant key.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com`, and triggers an event (e.g. `orders/create`) so Shopify sends a legitimately HMAC-signed webhook to the app's registered callback URL.
2. Attacker captures the raw body `B` and the `x-shopify-hmac-sha256` header value `H` (valid because `H = HMAC(client_secret, B)`, and `client_secret` is shared by the app across all shops, not tied to `attacker.myshopify.com`).
3. Attacker sends a new POST to the same webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` and `Registry.process` call `Utils::HmacValidator.validate`, which recomputes `HMAC(client_secret, B)` and matches `H` — validation succeeds because `shop-domain` was never part of the signed input: [3](#0-2) 
5. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: parsed(B), ...)`, so the host app processes attacker-chosen webhook content as if it originated from `victim.myshopify.com`.
