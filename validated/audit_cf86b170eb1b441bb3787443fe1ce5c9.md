### Title
Webhook shop-domain attribution is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC computed by `ShopifyAPI::Utils::HmacValidator.validate` authenticates the *body bytes* only. The `shop`, `topic`, `webhook_id`, and `api_version` values are all read straight from unauthenticated HTTP headers and are passed through unchanged into `WebhookMetadata`, which the gem's own documentation describes as verified data from a request that "did indeed come from Shopify."

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` gates on HMAC validation and then hands the caller's `handler.handle` a `WebhookMetadata` built directly from header-derived accessors: [1](#0-0) 

The HMAC check itself only signs the raw body: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature exclusively from `verifiable_query.to_signable_string`, so any field not included in that string is not authenticated: [4](#0-3) 

The `shop` value returned by `Request#shop` is the `shop-domain`/`x-shopify-shop-domain` header, which is outside the signable string: [5](#0-4) 

The `WebhookMetadata` struct carries that unauthenticated `shop` value forward to the handler, and the gem's documentation explicitly tells integrators that `process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook": [6](#0-5) 

Binding broken, stated as an equality that the library implicitly promises but does not enforce:
`HMAC-verified(raw_body)` ⇏ `HMAC-verified(shop_header)`, yet the API surfaces `data.shop` as if it were `HMAC-verified(shop)`.

Attack path: an unprivileged internet user who can install the target app on any shop they control (a routine, unprivileged action for any Shopify merchant) will legitimately receive genuine webhook deliveries for their own shop, including a valid `x-shopify-hmac-sha256` header computed over a given JSON body. Because the signature covers only the body — not the `x-shopify-shop-domain` header — the attacker can replay that exact captured body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with an arbitrary victim shop domain. `HmacValidator.validate` still succeeds (it never looks at the shop header), and `Registry.process` invokes the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
Any app built on this gem that uses `data.shop` from the webhook handler to select which merchant's data/session/store the incoming webhook body applies to (which is precisely the field's documented purpose) can be made to attribute attacker-controlled webhook content to another tenant. This is a cross-tenant boundary break rooted entirely in this gem's own request/verification code — `Registry.process` documents and performs "verification the request came from Shopify" but the identity field (`shop`) that downstream code relies on for tenant isolation is excluded from that verification.

### Likelihood Explanation
The attacker only needs to be able to install the target app on a shop they control — an ordinary, unprivileged action available to any Shopify user — and capture one legitimate webhook delivery from their own store. No access to the app's `client_secret`, TLS interception, or privileged account is required. The replay itself is a trivial HTTP request with one header value changed.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`/`api_version`) header values in the HMAC-signable string, or otherwise cryptographically bind the shop-domain header to the request signature (e.g., verify it against Shopify's canonical webhook payload metadata rather than a header) before constructing `WebhookMetadata`. At minimum, update the documentation to clearly state that `data.shop` is not covered by the HMAC and must not be trusted for tenant attribution without additional verification (e.g., cross-checking against a known, previously registered shop for that webhook subscription).

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com` and receives a genuine webhook POST with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker resends the identical request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but replacing `x-shopify-shop-domain: attacker-shop.myshopify.com` with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the tampered headers; `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(client_secret, B)` (body unchanged) and confirms it equals `H` — validation passes.
4. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))`, causing the app to process attacker-controlled webhook content under the victim shop's identity.
