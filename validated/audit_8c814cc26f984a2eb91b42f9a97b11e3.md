### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then unconditionally trusts the `shop-domain` header for tenant attribution. Because the `shop` field is never part of the signed content, any request whose body+HMAC pair was legitimately produced by Shopify for one shop can be replayed with an arbitrary `X-Shopify-Shop-Domain` header, and it will still pass validation — attributing the (relayed) webhook to a different, victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines the signable content as only the raw body: [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string`, i.e., `@raw_body`: [3](#0-2) 

`Registry.process` treats a valid HMAC as sufficient proof of authenticity for the entire request, including the `shop` field, and forwards it unchanged to the app's handler: [4](#0-3) [5](#0-4) 

The gem's own documentation instructs host apps to use `data.shop` directly for tenant-scoped work (e.g., enqueuing jobs "per shop"): [6](#0-5) 

This is the identity-binding equality that should hold but does not:
`hmac_verified_bytes (raw_body)` == `bytes_used_for_tenant_attribution (shop-domain header)`.

Since the `shop-domain` header sits outside the signed bytes, an attacker who is able to obtain any one validly-signed `(raw_body, hmac)` pair — for example by receiving genuine webhooks on their own store (a normal, unprivileged merchant installing the app) — can replay that exact body+HMAC to the app's webhook endpoint while substituting the `shop-domain` header (and the `webhook-id`/`api-version` headers, which are likewise unsigned) with a victim shop's domain. `HmacValidator.validate` still succeeds because the body is byte-for-byte identical to what Shopify originally signed, and `Registry.process` will hand `WebhookMetadata` carrying the attacker-chosen `shop` value to the app's handler.

### Impact Explanation
This breaks the tenant boundary the whole webhook-processing flow is meant to enforce: `shop` is the only signal host apps have to know which merchant a webhook event belongs to, yet it is fully attacker-controllable independent of the cryptographic proof of authenticity. For topics whose bodies are static or highly predictable across shops (e.g., mandatory compliance topics such as `shop/redact`, `customers/redact`, `customers/data_request`, or events with minimal/no payload), an attacker can trigger the handler logic for a shop they do not control by relaying a self-obtained signed payload with a forged shop header — leading to cross-tenant confusion such as incorrectly revoking/deactivating another shop's integration state, triggering data purges/redactions against the wrong tenant, or polluting per-shop job queues keyed by `data.shop`. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires the attacker to possess one legitimately-signed webhook body (trivially obtainable by installing the app on their own development/test store and capturing an incoming webhook, no `api_secret_key` or victim credentials needed) and the ability to POST to the app's public webhook endpoint with custom headers. No access token, `client_secret`, or privileged account for the victim is required, and the affected code path (`Registry.process` / `HmacValidator.validate`) is exercised on every webhook the host app processes.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header value in the bytes that are HMAC-verified, or otherwise cryptographically bind the shop identity to the verified payload (e.g., require the host application to independently confirm the reported `shop` against a stored, authenticated session/webhook subscription id rather than trusting the header). At minimum, document prominently that `data.shop` is not covered by the Shopify HMAC and must not be used for authorization decisions without additional verification.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and lets Shopify deliver a real webhook, e.g., topic `customers/redact` with body `raw_body` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, raw_body)`.
2. Attacker replays this exact request to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and any other desired unsigned headers) while keeping `raw_body` and `X-Shopify-Hmac-Sha256` unchanged.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request; `Utils::HmacValidator.validate(request)` recomputes the HMAC over `raw_body` only, matches `H`, and returns `true`.
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to perform the redact/uninstall/other tenant-scoped action against `victim-shop.myshopify.com` even though Shopify never sent this event for that shop.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
