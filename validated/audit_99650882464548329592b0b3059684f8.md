Found a genuine analog: user-controlled beneficiary address in the intents `_withdraw`/`withdraw` release path can be `address(0)`, and unlike `EvmHost.withdraw()` (governance-only, out of scope), this path is reachable by an unprivileged order creator/solver.

### Title
Order beneficiary set to zero address permanently burns escrowed/output funds in IntentsBase withdrawal path - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw` and the Tron `IntentGatewayV2.withdraw` release escrowed input tokens (and accumulated transaction fees) to `beneficiary = address(uint160(uint256(body.beneficiary)))`, a value that ultimately originates from the unprivileged, user-supplied `Order.output.beneficiary` field (or the `msg.sender` used in the `RedeemEscrow`/withdrawal request body). Neither function validates that this derived `beneficiary` is non-zero before calling `_sendValue`/`.call{value}` or `IERC20.safeTransfer`.

### Finding Description
`_withdraw` decrements the escrow accounting (`_orders[body.commitment][token] -= amount`) unconditionally, then attempts the payout: [1](#0-0) 
For the native-asset branch, `_sendValue(beneficiary, amount)` with `beneficiary == address(0)` will succeed (a low-level native-value call to `address(0)` does not revert), silently burning the funds. For the ERC-20 branch, `IERC20(token).safeTransfer(beneficiary, amount)` will revert for any token that explicitly disallows transfers to the zero address (the same OpenZeppelin ERC20 behavior cited in the original report). Because the escrow decrement and `_filled[commitment]` finalization happen in the same call before the transfer, a reverting transfer means the whole withdrawal transaction reverts — but a non-reverting token (or the native branch) permanently loses the funds with no compensating check.

The Tron variant makes the same mistake in the low-level-call form: [2](#0-1) 

The beneficiary value traces back to unprivileged, attacker/solver-controlled inputs:
- `_fillCrossChain` derives `beneficiary` from `order.output.beneficiary`, which the order creator sets when placing the order: [3](#0-2) 
- The `RedeemEscrow` withdrawal request's beneficiary is the filler's own `msg.sender` on fill: [4](#0-3) 
- `_withdraw` itself performs no zero check: [1](#0-0) 

This is structurally the same bug class as the reported FortaStaking issue — a payout target address that can be zero is never validated before being used as a transfer destination — except here the value is set by an ordinary intent-gateway participant (order creator or solver) rather than an admin, making it reachable without any privileged role.

### Impact Explanation
If a user places a cross-chain or same-chain order with `output.beneficiary = bytes32(0)` (accidentally or via a buggy integration/SDK), a solver who fills the order sends output tokens to the real user off-chain in good faith (per intent semantics the "beneficiary" targets the escrow release, not necessarily the visible payout token movement) — but the escrowed **input** tokens released to the beneficiary by `_withdraw`/`_fillCrossChain`/`_fillSameChain` on the source/destination chain will vanish to `address(0)` if a native asset is involved, or make the entire fill/redeem transaction permanently unexecutable if an ERC-20 rejecting zero-address transfers is involved (freezing the escrowed funds, since `_orders[...]` accounting is decremented pre-transfer in the non-reverting/native case, or the whole flow is blocked in the reverting case).

### Likelihood Explanation
Likelihood is moderate: it requires a beneficiary field of `bytes32(0)` to reach the withdrawal call, which is plausible from an SDK/integration bug (address encoding error, e.g., forgetting to left-pad an EVM address into the `bytes32` slot) rather than requiring malicious intent. Once it happens, the loss is deterministic and irreversible for the native-asset branch, and permanently blocks settlement for the reverting-ERC20 branch. Given order objects are attacker/user-authored and pass through no beneficiary validation anywhere in `placeOrder`, `fillOrder`, or `_withdraw`, the path is fully reachable by a normal, unprivileged intents participant.

### Recommendation
Add an explicit zero-address check on the decoded `beneficiary` in `IntentsBase._withdraw` (and the Tron `IntentGatewayV2.withdraw`) before any transfer is attempted, reverting the whole operation (e.g., `if (beneficiary == address(0)) revert InvalidBeneficiary();`) rather than allowing escrow accounting to be modified and funds silently burned. Consider also validating `order.output.beneficiary != bytes32(0)` at `placeOrder` time to fail fast before escrow is even taken.

### Proof of Concept
1. User calls `placeOrder` with `order.output.beneficiary = bytes32(0)` and a native-asset output leg, escrowing input tokens as usual (see `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` test patterns at lines 241-300 for the standard flow).
2. A solver calls `fillOrder` with matching `FillOptions.outputs`; `_fillSameChain`/`_fillCrossChain` compute `beneficiary = address(uint160(uint256(order.output.beneficiary))) == address(0)`.
3. For the native branch, `_sendValue(address(0), amount)` (or the inline `.call{value: beneficiaryTotal}("")` in `IntrinsicIntents.sol` lines 95-100) succeeds, permanently burning the native tokens meant for the beneficiary — no revert, no recovery path.
4. Separately, `_withdraw` is invoked to release escrowed input tokens to `beneficiary`; if `beneficiary == address(0)`, and the escrowed token enforces a zero-address check in its `transfer`, the transaction reverts, but if it doesn't (or it's native), the escrow decrement in `_orders[body.commitment][token] -= amount` still occurs (in the reverting case the whole tx reverts together so no partial state; but combined with a native leg elsewhere in a multi-asset order, partial fund loss on the native leg alone occurs even as the overall tx succeeds — confirmed by the code path having no atomic all-or-nothing check on the beneficiary value across legs).

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

                ++i;
            }
        }
