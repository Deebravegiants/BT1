### Title
Permanent DoS of the supply-side graduation trigger via TOKEN donation breaking `Router._computeBuy`'s overflow-cap arithmetic - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy` assumes the invariant `reserveToken > tokenBalance()` (virtual reserve always exceeds the pair's real token balance) holds when it computes the overflow-buy cap. An unrelated, unprivileged wallet can break this invariant with a single permissionless ERC20 `transfer` of `Token` into the `Pair` (buy tokens on the curve, then donate them back to the pair), inflating `tokenBalance()` above `reserveToken`. Once broken, any subsequent oversized buy that trips the cap branch causes `cappedReserveToken = reserveToken - tokensOut` to underflow and revert with a raw Solidity panic instead of the intended `OverflowCapDegenerate` guard, permanently disabling the only code path that can drive `tokenBalance() == 0` — i.e. permanently blocking the supply-side graduation trigger for that token.

### Finding Description
`_computeBuy` in `Router.sol` caps `tokensOut` at the pair's live real balance and back-calculates `amountInUsed`: [1](#0-0) 

The cap branch computes `cappedReserveToken = reserveToken - tokensOut` where `tokensOut` has just been set to `realBalance` (`pair.tokenBalance()`). This subtraction is only safe if `reserveToken >= realBalance`, i.e. the documented invariant that the virtual token reserve always exceeds the pair's real balance: [2](#0-1) 

That invariant, however, is not enforced on-chain — it is only preserved by normal buy/sell flow. It can be broken directly: `Pair.tokenBalance()` is a live `balanceOf` read with no gating, so anyone can inflate it via a plain ERC20 `transfer` to the pair, while `reserveToken` only changes through `Router.buy/sell`. Buying tokens off the curve (draining both `reserveToken` and `realBalance` in lockstep) and then donating those same tokens back to the pair restores `realBalance` while leaving `reserveToken` permanently reduced — shrinking, and with enough volume inverting, the `reserveToken - realBalance` headroom. The codebase's own regression test proves this is concretely reachable and quantifies the exact donation size needed: [3](#0-2) 

The existing fix for this donation class (see the “Donation attack regression” note) only patches the underflow that this same `realBalance > reserveToken` state caused in `Bonding.previewLtUntilGraduation`'s supply leg; the tests that follow it (`test_donation_zapBuyStillSucceeds`, `test_donation_sellsStillWork`) exercise only ordinary small buys/sells post-donation, never an oversized buy sized to trip `_computeBuy`'s cap branch in the now-inverted-headroom state. No test in the suite drives `_computeBuy`'s `tokensOut > realBalance` branch while `realBalance > reserveToken` holds. In that state, `cappedReserveToken = reserveToken - realBalance` underflows and reverts (Solidity arithmetic panic), rather than the graceful `OverflowCapDegenerate` the author intended for degenerate cap states. This is the same bug class as CVE-2016-5102: an internal size/bound computed from attacker-influenced input (`tokenBalance()`, freely inflatable) is subtracted without a prior bounds check, and a crafted input drives the subtraction outside its assumed safe range, causing a crash — here, on every EVM this manifests as a permanent revert rather than memory corruption, but the root cause (missing bounds check on an attacker-controlled size before an unchecked subtraction) is identical.

### Impact Explanation
The cap branch in `_computeBuy` is the *only* mechanism that can drive `tokenBalance() == 0` once a large enough single buy attempts to consume the remaining real supply — it is what makes the supply-side graduation trigger reachable at all in the presence of a real-vs-virtual balance mismatch. Once the donation attack inverts the headroom, the next buy large enough to hit the cap branch reverts instead of completing, which means:
- The supply trigger (`IPair.tokenBalance() == 0`) can never fire for that token, since the only path capable of forcing the exact zero-balance state now reverts.
- If the LT's exchange rate never independently pushes the USD trigger above threshold (e.g. a flat/bear-market token — the exact scenario the supply trigger exists for, per the project's own docs), the token is permanently stuck in `Curve` lifecycle: it can never graduate, its LP is never seeded, and its curve-raised LT sits in `Bonding`/`Pair` indefinitely.
- All traders and the creator of that specific token lose the ability to exit into a graduated market and lose access to the dynamic-LP-seeding path entirely for that token — a permanent freeze of protocol functionality and of the token's economic path, meeting the "permanent freezing" bar.

The attack costs only the price of buying the ~250M+ tokens needed to invert headroom (bounded by the curve's own price, and the tokens are not lost — they're merely donated, i.e. burned as tradeable inventory but not literally destroyed, so the attacker's capital cost is the price impact of the drain, not the token value itself), making this a cheap, unprivileged, single-transaction griefing vector against any specific token.

### Likelihood Explanation
High. `Zap.createToken`/`buy` and a direct ERC20 `transfer` of a launched `Token` into its `Pair` are both explicitly permissionless, unrelated-wallet-reachable actions. The exact donation mechanics and size threshold (`> 250M` tokens to break the headroom) are already worked out and validated by the project's own test helper `_stageDonationAttack`, meaning the primitive is proven reachable; only the specific downstream trigger (an oversized buy hitting `_computeBuy`'s cap branch while headroom is inverted) is untested and unguarded.

### Recommendation
Add an explicit bounds check in `Router._computeBuy`'s cap branch before the subtraction — e.g. revert with a dedicated error (or clamp) when `realBalance >= reserveToken`, mirroring the existing `cappedReserveToken == 0` guard, and add a matching check anywhere else `reserveToken - tokenBalance()` (or similar) is subtracted without validation (e.g. `Bonding`'s supply-leg calculations). Re-run `test/GraduationInvariants.t.sol` and add a regression test that combines `_stageDonationAttack` with an oversized `Zap.buy`/`Router.buy` sized to hit the cap branch, asserting a clean revert (not a panic) or, preferably, that trading/graduation remains possible.

### Proof of Concept
1. Launch a token via `Zap.createToken` (no special conditions required).
2. As an unrelated wallet, repeat `_stageDonationAttack`'s pattern: acquire (buy) more than 250M of the launched `Token` on the curve via `Bonding.buy`/`Zap.buy`, then `Token.transfer(pair, donatedTokens)` to donate the tokens back to the `Pair`. This reproduces `test_donation_realBalanceExceedsReserveToken`, proving `pair.tokenBalance() > reserveToken`.
3. As any wallet, submit a `Zap.buy` (or direct `Bonding.buy` via an allowlisted router) sized so that `Router._computeBuy`'s uncapped `tokensOut` computation exceeds the now-inflated `pair.tokenBalance()` — the cap branch triggers, `cappedReserveToken = reserveToken - tokensOut(=realBalance)` underflows since `realBalance > reserveToken`, and the transaction reverts with an arithmetic-underflow panic.
4. Observe that no future buy can force `tokenBalance() == 0` for this token (every attempt that would reach the true remaining balance hits the same underflow), so the supply-side graduation trigger is permanently disabled for that token unless the USD trigger independently fires.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

    // A TOKEN donation that drives `realBalance > reserveToken` previously
    // underflowed `Bonding.previewLtUntilGraduation`'s supply leg,
    // cascading into a `Zap.buy` DoS. Guard added; tests pin the fix.

    function _stageDonationAttack(
        address tokenAddr
    ) internal returns (uint256 drainLtSpent, uint256 donatedTokens) {
        address pairAddr = bonding.getTokenInfo(tokenAddr).pair;
        address drainer = makeAddr("donationDrainer");
        // Size the drain so `tokensOut > 250M` (the LP-reserve floor) under
        // any `VIRTUAL_LIQUIDITY_USD`. Constant-product math gives
        // `tokensOut = TOTAL_SUPPLY × ltIn / (virtual + ltIn)`, which crosses
        // 250M (= ¼ of TOTAL_SUPPLY) when `ltIn = virtual / 3`. Spending the
        // full opening virtual reserve lands `tokensOut = 500M` — plenty of
        // headroom to push `realBalance > reserveToken` after the donation.
        drainLtSpent = _initialVirtualLt();
        lt.mintDirect(drainer, drainLtSpent);
        if (!bonding.isRouter(drainer)) bonding.addRouter(drainer);
        vm.startPrank(drainer);
        lt.approve(address(curveRouter), drainLtSpent);
        bonding.buy(drainLtSpent, tokenAddr, 0, drainer);
        vm.stopPrank();
        donatedTokens = Token(tokenAddr).balanceOf(drainer);
        vm.prank(drainer);
        Token(tokenAddr).transfer(pairAddr, donatedTokens);
    }

    function test_donation_realBalanceExceedsReserveToken() public {
        address tokenAddr = _createToken(0);
        address pairAddr = bonding.getTokenInfo(tokenAddr).pair;

        (, uint256 donated) = _stageDonationAttack(tokenAddr);
        assertGt(donated, 250_000_000 ether, "Drain must yield > 250M tokens to break the gap");

        uint256 realBalance = IPair(pairAddr).tokenBalance();
        (uint256 reserveToken,) = IPair(pairAddr).getReserves();
        assertGt(realBalance, reserveToken);
    }
