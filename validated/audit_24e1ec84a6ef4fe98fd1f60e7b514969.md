## Title
Webhook `shop-domain` Header Is Not Covered By HMAC Validation, Allowing Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the shop identity for an incoming webhook purely from the unauthenticated `shopify-shop-domain` HTTP header, while the HMAC signature that the gem validates covers only the raw request body. This breaks the identity binding `shop (used to dispatch/act on data) == shop (attested by the HMAC)`, letting anyone who possesses one validly-signed webhook body (e.g. from their own shop) replay it with a different `shop-domain` header and have it processed by the app as if it originated from an arbitrary victim shop.

### Finding Description
`Request#shop` reads the shop straight from headers, with no cryptographic binding: [1](#0-0) 

The signable string used for HMAC verification is exclusively the raw body — `shop`, `topic`, and `webhook_id` are excluded: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` against the HMAC, i.e. only the body bytes: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build `WebhookMetadata`, which is handed to the app's handler as the authoritative tenant identity: [4](#0-3) 

Because `to_signable_string` returns only `@raw_body`, two requests with identical bodies but different `shopify-shop-domain` header values produce the *same* valid HMAC (using the app's single shared `client_secret`, which is identical for all shops of the app). This is exactly the bug-class pattern described in the reference report: a field that is acted upon (`shop`) is not covered by the "invariant" that's supposed to protect it (the HMAC), the same way an inflated vault share price isn't covered by the check meant to protect first-depositor share issuance.

### Impact Explanation
This crosses a tenant boundary: an app that operates on multiple merchants' shops can be tricked into processing a webhook payload under the wrong shop's identity. Depending on the app's webhook handler logic (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`, inventory/order sync), this can cause the app to perform actions against — or leak/attribute data belonging to — a shop other than the one that actually sent the payload, i.e. cross-tenant access/impact, which is a "Critical" category per the given impact taxonomy.

### Likelihood Explanation
Exploitation requires only:
1. The attacker to install the app on their own shop (or otherwise obtain one legitimately HMAC-signed webhook body — no `api_secret_key` needed since the signature is provided by Shopify to any installed app).
2. Replaying that same body to the app's public webhook endpoint with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header changed to the victim shop's domain.

No credentials, tokens, or secrets belonging to Shopify or the app need to be known to the attacker — only the unprivileged ability to install the app once and send arbitrary HTTP requests, matching the "unprivileged internet user" threat model.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or minimally `shop`) in the HMAC signable string, or otherwise cryptographically bind the shop domain to the payload before trusting it in `Registry.process`/`WebhookMetadata`. At minimum, document/require host applications to independently verify that `request.shop` corresponds to a shop actually installed with a matching, previously-stored access token before acting on the webhook.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: app/uninstalled
   x-shopify-hmac-sha256: <valid-hmac-of-body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: {}
   ```
2. Capture this request. `HmacValidator.compute_signature` only hashes the body `"{}"`, so the HMAC is independent of the `shop-domain` header value.
3. Replay the identical body/HMAC with the header changed:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) validates the (still-correct) HMAC over the body, then invokes the handler with `shop: "victim-shop.myshopify.com"`, causing the app to treat the forged request as authentic data/action for the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
