### Title
Webhook shop attribution is not cryptographically bound to the HMAC, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate(request)` verifies nothing but the request body bytes. The `shop` (and `topic`/`webhook_id`) values are read straight from HTTP headers that are never covered by the signature. Any actor who can obtain one valid `(raw_body, hmac)` pair for the app — trivially available to anyone who installs the app on their own store, since that requires no secret — can replay that exact body/HMAC pair to the app's public webhook endpoint while swapping the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header to an arbitrary victim shop domain. `Registry.process` accepts the request because the HMAC still matches the (unchanged) body, and hands `request.shop` — the attacker-controlled header — to the registered handler as if it were verified.

### Finding Description
The binding that should hold is:
`shop_verified_by_hmac == shop_acted_on_by_handler`

In this code, that equality never actually exists:

- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received `hmac`. [1](#0-0) 
- For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 
- `shop` is pulled from an unsigned header: [3](#0-2) 
- `Registry.process` validates the HMAC once, then immediately trusts `request.shop` and forwards it to the handler without any additional binding to the signed content: [4](#0-3) 

Because the api_secret_key is shared across all shops installed on a given app (it is the app's secret, not a per-shop secret), a valid `(body, hmac)` pair produced for *shop A*'s webhook delivery remains a *valid* HMAC pair regardless of which shop header accompanies it. An attacker only needs to be a legitimate (unprivileged) installer of the app on their own store to capture one such pair from Shopify's real webhook delivery, then POST it directly to the app's public webhook endpoint with the `shop-domain` header changed to any other shop the attacker wants to target. `Registry.process` will accept it as valid and dispatch it to the handler tagged with the forged shop, since only the body — not the shop/topic/webhook-id headers — is authenticated.

This breaks the tenant boundary the library is expected to enforce: the whole purpose of exposing `WebhookMetadata#shop` to consuming apps is to let them safely key persistence/business logic (order records, GDPR redaction, `app/uninstalled` cleanup, etc.) by shop, under the assumption that `Registry.process` already validated the request. That assumption is false for the `shop` field.

### Impact Explanation
This is a cross-tenant access vector: an attacker who is a legitimate (but unprivileged, non-victim) installer of the app can inject webhook events that the host application will process as belonging to an arbitrary *other* merchant's shop. Depending on how host apps use `WebhookMetadata#shop` (which the library's own docs and `Registration`/`WebhookHandler` API encourage them to trust once `Registry.process` succeeds), this can cause data to be written/deleted under the wrong tenant, e.g., forging a GDPR `shop/redact` or `app/uninstalled` event for a victim shop, or injecting fabricated `orders/create` payloads attributed to a shop the attacker does not control. This matches the report's "Critical - cross-tenant access" impact bucket.

### Likelihood Explanation
Likelihood is moderate-to-high: the only prerequisite is possessing one legitimately-issued `(raw_body, hmac)` pair for the app, which any unprivileged actor gets simply by installing/using the app on a store they control (no stolen secrets, tokens, or privileged access required). From there, forging the shop header on a replayed request is trivial (a single HTTP header change) and does not require breaking the HMAC at all, since the header is outside the signed scope entirely.

### Recommendation
Do not treat any header value (`shop`, `topic`, `webhook_id`, `api_version`) as trusted purely because the body HMAC validated. Either:
1. Include the shop domain (and ideally topic/webhook id) inside the signable string used for HMAC verification, or
2. Cross-check `request.shop` in `Registry.process` against an independently known set of installed/authorized shops (e.g., the shop associated with the currently active session/offline token) before dispatching to handlers, and document clearly that `WebhookMetadata#shop` is not itself authenticated by the HMAC.

### Proof of Concept
1. Install the target app on an attacker-controlled store `attacker-shop.myshopify.com`; trigger any webhook topic the app subscribes to (e.g. `orders/create`) so Shopify delivers a real request with a valid `X-Shopify-Hmac-Sha256` header for that raw body.
2. Capture the exact `raw_body` and `hmac` header from that delivery.
3. Replay a POST to the app's public webhook endpoint with the identical `raw_body` and `hmac` header, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` (it only checks the body), and `ShopifyAPI::Webhooks::Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"` — i.e., data that actually originated from the attacker's own shop is now attributed to, and processed as belonging to, the victim shop.
