Confirmed: `EvmHost` uses the real `@uniswap/v2-periphery` `IUniswapV2Router02` interface, whose `swapETHForExactTokens` implementation (per canonical Uniswap V2) refunds any unspent ETH via a raw `msg.sender.call{value:...}("")` — and since `EvmHost` is the caller of the router, that refund lands back in `EvmHost`'s own balance, not the original transaction sender's wallet. `EvmHost` never reads/uses the router's return value nor forwards any leftover ETH back to `_msgSender()`.

### Title
Unrefunded Excess Native Payment in `EvmHost.dispatch`/`fundRequest` Native-to-FeeToken Swap - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` all accept `msg.value` and swap it for the exact `feeToken` amount needed via `IUniswapV2Router02.swapETHForExactTokens`, but none of them capture the router's refund of unspent ETH and return it to the caller.

### Finding Description
In `EvmHost.dispatch(DispatchPost)`: [1](#0-0) 
the function does `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` and discards the return value entirely — no refund step follows. The identical pattern recurs in `dispatch(DispatchGet)`: [2](#0-1) 
and in `fundRequest`: [3](#0-2) 

Canonical `UniswapV2Router02.swapETHForExactTokens` (imported from `@uniswap/v2-periphery`) refunds any ETH not consumed by the swap back to `msg.sender` of that call — which is `EvmHost` itself, since `EvmHost` is the one invoking the router with `{value: msg.value}`. Because `EvmHost` neither tracks the amount actually spent (unlike the correct pattern used elsewhere in the codebase, e.g. `IntentGatewayV2._fillCrossChain` which does `msgValue -= amounts[0]` and then explicitly refunds the remainder to the caller: ` [4](#0-3) `), nor forwards the router's refund back to `_msgSender()`, any ETH sent beyond the exact swap cost for `post.fee`/`get.fee`/`amount` is silently absorbed into `EvmHost`'s own balance.

Any unprivileged caller dispatching a POST/GET request or funding a request with native token can overpay (e.g. by supplying a generous `msg.value` because the exact Uniswap output amount is difficult to predict precisely on-chain, or due to price movement between quote and execution) and permanently lose the difference — the contract provides no accounting or withdrawal path that returns this specific excess to the original payer.

### Impact Explanation
This directly mirrors the `mintFromReserve` excess-ether issue: users interacting with `EvmHost.dispatch`/`fundRequest` with native token payment (a primary, documented payment path — see `docs/content/developers/evm/messaging/post-requests.mdx` "Native Token Payment" section) who send `msg.value` greater than what the swap actually needs lose that excess permanently, with no mechanism to reclaim it. Since exact swap costs are only knowable after execution (subject to slippage/liquidity), overpayment is a realistic and likely occurrence for any dApp or user not meticulously computing `getAmountsIn` immediately before the transaction. This is a direct, unrecoverable loss of user funds — a Medium severity issue per the same class of finding in the original report.

### Likelihood Explanation
High for a common user flow: any app or EOA calling `dispatch{value: msg.value}(post)` or `fundRequest{value: msg.value}` with `msg.value` set to a safety-margin amount (standard practice for native-swap-based fee payments, as recommended in the docs' "Estimating Fees" section) will trigger this every time the estimate exceeds the actual swap cost.

### Recommendation
Capture the `amounts` array returned by `swapETHForExactTokens` in all three call sites (`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, `fundRequest`), compute `msg.value - amounts[0]` as done in `ExtrinsicIntents._fillCrossChain` and `IntentGatewayV2.placeOrder`, and refund the remainder to `_msgSender()` via a low-level call, reverting on failure.

### Proof of Concept
1. Caller invokes `EvmHost.dispatch{value: 1 ether}(post)` where `post.fee` only requires `0.1 ether` worth of swap input.
2. `swapETHForExactTokens{value: 1 ether}(post.fee, path, address(this), block.timestamp)` executes; the router spends `~0.1 ether` and refunds `~0.9 ether` back to `address(this)` (`EvmHost`), per lines [1](#0-0) .
3. `EvmHost` never forwards this `~0.9 ether` back to the caller; it remains stuck in the `EvmHost` contract's balance, with no accounting entry or withdrawal function tied to the original caller.
4. The caller has permanently lost `~0.9 ether` for a `0.1 ether` fee payment.
