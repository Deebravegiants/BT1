### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, but the `shop` and `topic` values that the library hands to the app's handler — and that the app uses as the tenant/event identity — come from unauthenticated HTTP headers. The signature is not bound to those values, breaking the identity equality `verified(bytes) == claimed(shop, topic)`.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`. Its `to_signable_string` returns only the raw body: [1](#0-0) 

But `shop` and `topic` are read straight from HTTP headers (`x-shopify-shop-domain` / `shopify-shop-domain`, `x-shopify-topic` / `shopify-topic`), which are never included in `to_signable_string`: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body relationship, then passes the unauthenticated `request.shop` and `request.topic` straight to the app's handler as the trusted tenant/event identity: [3](#0-2) 

`WebhookMetadata.shop` is explicitly documented as "The shop domain of the webhook" and the sample handler code uses it directly as the per-tenant key (`shop_domain: data.shop`) to route/persist data: [4](#0-3) 

Because the HMAC only binds the body bytes, the same `(raw_body, hmac)` pair remains valid for the app's endpoint regardless of what `shop-domain` or `topic` header accompanies it. The gem's own `process` method — not merely "host misuse" — performs the trust decision and identity extraction this way, so this is a defect inside the gem's documented API surface, not host misapplication of it.

### Impact Explanation
An attacker who operates their own (unprivileged) shop installation of the app can capture one legitimate webhook delivery for their own shop (a normal HMAC-signed `(body, headers)` pair that Shopify sent them, which they are entitled to receive) and replay it to the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim's shop domain (and/or the `shopify-topic` header changed to a different registered topic). `HmacValidator.validate` still returns `true` because it only checks the HMAC against `@raw_body`, and `Registry.process` will invoke the registered handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain and/or an attacker-chosen topic. Any app that uses `data.shop`/`data.topic` to look up or update per-tenant records (as shown in the gem's own documentation example) will attribute the attacker's forged event/body to another merchant's tenant — a cross-tenant data-injection/corruption primitive achievable without the app's `client_secret`, an access token, or any privileged account. This satisfies the Critical "cross-tenant access" bar.

### Likelihood Explanation
The attacker only needs to be a legitimate (even trial) merchant of the target app to obtain one valid `(raw_body, hmac)` pair for their own shop (e.g., by triggering any subscribed webhook topic on their own store), then issue a normal HTTP POST to the app's public webhook endpoint with forged headers — no cryptographic material or secret access is required. This is a low-effort, no-privilege attack reachable purely through the gem's documented `Registry.process`/`Request` flow.

### Recommendation
Bind the authenticated identity to the signature: either (a) include `shop`, `topic`, and `webhook_id` in the signable payload used for HMAC verification, or (b) after validating the body HMAC, cross-check the claimed `shop` header against an independently-trusted source (e.g., require the app to supply the expected shop for the given delivery and compare), and reject processing when they don't match. At minimum, document prominently that `request.shop`/`request.topic` are unauthenticated headers and must not be trusted as tenant identifiers without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a normal webhook (e.g. `orders/create`) to the app's registered callback. Attacker captures the raw HTTP request: body `B`, and headers including `x-shopify-hmac-sha256: H` (valid HMAC of `B`), `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
2. Attacker resends the exact same body `B` and `hmac-sha256: H` to the same callback URL, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `H` against `B` — this still passes: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though Shopify never sent this webhook for that shop, letting the attacker inject/forge data attributed to the victim tenant.
