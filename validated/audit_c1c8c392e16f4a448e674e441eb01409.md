### Title
Webhook `shop-domain` header is trusted but not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw JSON body via `Utils::HmacValidator.validate`, then hands the handler a `shop` value taken from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header — a field that is never included in the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from an HTTP header, independent from the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC (over the body) before dispatching to the handler with the header-derived `shop`: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute and compare the HMAC solely against `verifiable_query.to_signable_string` (i.e., the body), never touching `shop`: [4](#0-3) 

This breaks the identity binding: `shop (HMAC-verified)` should equal `shop (used by the handler as the tenant key)`, but here `shop` is never part of the HMAC-covered bytes at all — the equality never holds by construction. Any request whose body+HMAC pair is valid for the app's shared `client_secret` (a pair the requester can legitimately obtain from a webhook fired by their own store, since a public app's webhook-signing secret is shared across all installing shops) can be replayed with an arbitrary `x-shopify-shop-domain` header. `Registry.process` will accept it and pass that attacker-chosen `shop` value to the handler as `WebhookMetadata#shop`, which host applications commonly use as the per-tenant identity/lookup key.

### Impact Explanation
This allows an attacker who controls their own shop installation of a multi-tenant app (an unprivileged capability — anyone can install a public app) to forge webhook deliveries "as" a victim shop: capture a valid `(body, hmac)` pair generated by an action in their own store, then replay it to the app's webhook endpoint with `x-shopify-shop-domain` set to the victim's domain. Since the shop is not bound to the signed bytes, the gem provides no defense against this and the consuming application will process attacker-controlled data under another tenant's identity, resulting in cross-tenant data injection.

### Likelihood Explanation
Likelihood is limited by the need to first obtain at least one legitimate `(body, hmac)` pair, which requires the attacker to have installed the app in their own store (a normal, unprivileged action available to any Shopify user) and observe one webhook delivery. Given the shared `client_secret` signs all shops' webhooks identically, this is straightforward to achieve for any public app.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header value in `to_signable_string`, or otherwise cryptographically bind the shop domain to the request before validation, so the HMAC check fails if the header does not match the shop that actually triggered the webhook.

### Proof of Concept
1. Attacker installs a multi-tenant Shopify app in their own store `attacker.myshopify.com` and triggers an event (e.g., creates an order) so Shopify sends a webhook with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker captures `(B, H)`.
3. Attacker sends `POST /webhooks` to the app's endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid), but header `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B`/`H` against `client_secret`: `lib/shopify_api/webhooks/registry.rb:188-190`.
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` even though the payload actually originated from the attacker's own store, letting the attacker inject data attributed to the victim tenant.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
