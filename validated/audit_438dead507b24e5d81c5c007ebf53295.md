This is a genuine finding: the `shopify-shop-domain` header used to identify the tenant (`shop`) in `ShopifyAPI::Webhooks::Registry.process` is never covered by the HMAC signature verification.

### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `#shop` is read directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC of the body but then forwards `request.shop` to the app's handler as trusted tenant data.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by calling `Utils::HmacValidator.validate(request)`, which computes an HMAC over `request.to_signable_string` and compares it to `request.hmac`: [1](#0-0) 

`Request#to_signable_string` returns only `@raw_body`, while `#shop` is derived from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header, which is never included in the signed bytes: [2](#0-1) 

The HMAC binds "the shop this webhook came from" to only the body bytes, not to the shop header. After the signature check passes, `Registry.process` calls the app's `handler.handle` using `request.shop` from that unauthenticated header, without any further validation that the header matches the shop that actually holds the API-secret-signed body: [1](#0-0) 

Because HMAC verification here only proves "these exact body bytes were signed by someone holding `api_secret_key`" and not "this body was signed together with shop X," an attacker who has legitimately received one valid, correctly-signed webhook body for shop A (e.g., from a real Shopify webhook delivery for their own installed shop, which they fully control and can replay) can resend the exact same signed body while substituting a different `shopify-shop-domain` header value for shop B. The HMAC will still validate because the header is not part of `to_signable_string`, but `request.shop` now falsely reports shop B to the host application's handler. This breaks the binding: `shop-header-claimed-by-request == shop-actually-verified-by-hmac`.

### Impact Explanation
This is a cross-tenant identity confusion at the gem layer: the library asserts (via HMAC pass) that a webhook payload is authentic, and simultaneously hands the app a `shop` value that was never covered by that same proof. Any app that uses `WebhookMetadata#shop` (populated straight from `request.shop`) to key per-tenant data access, without independently cross-checking it against the payload's own tenant identifiers, can be made to write/attribute webhook-driven data to the wrong merchant/tenant. This matches the Critical "cross-tenant access" bucket, since the identity binding failure occurs entirely within this gem's own verification method (`Utils::HmacValidator.validate` / `Registry.process`), not because the host app misuses a documented API.

### Likelihood Explanation
The attacker must possess at least one validly-signed webhook body (obtainable from their own shop's genuine webhook deliveries, which any merchant/app installer receives) and must control (or intercept/replay to) an endpoint that calls `ShopifyAPI::Webhooks::Registry.process` directly with attacker-influenced headers. Because `shop` is sourced purely from an HTTP header and is trivial to overwrite in a raw HTTP request, and no part of the gem cross-validates it against the signed body, exploitation only requires header manipulation plus body replay — no cryptographic material is needed.

### Recommendation
Include the shop domain (and topic/webhook-id, if they are meant to be trusted) in the HMAC-signed payload used by `Request#to_signable_string`, or explicitly document/enforce that `Registry.process` must verify `request.shop` against a shop already known to be associated with the delivered `raw_body` (e.g., by requiring the host app to pass the expected shop and comparing it before invoking the handler). At minimum, `Registry.process` should not treat `request.shop` as trusted merely because the HMAC over the body validated.

### Proof of Concept
```ruby
# Attacker has one legitimately-signed webhook body from their own shop (shop-a.myshopify.com)
raw_body = '{"id":123}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker resends the same body, same hmac, but with a different shop-domain header
forged_headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "shopify-shop-domain" => "victim-shop.myshopify.com", # unauthenticated substitution
  "shopify-webhook-id" => "any-id",
  "shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HMAC validation passes (it only checks raw_body), and the handler receives
# WebhookMetadata with shop: "victim-shop.myshopify.com" despite the payload
# never having been signed together with that shop identity.
```
