Found it: `WorkflowMetadataHandler.GetWorkflowID` and `httpTriggerHandler.resolveWorkflowID` resolve a workflow purely from a **10-byte truncated hash** of the attacker-controlled `WorkflowName` string, combined with `WorkflowOwner` and `WorkflowTag`, with no re-verification against the full name once the mapping is stored.

### Title
Workflow lookup relies on a 10-byte truncated-hash workflow name, enabling collision-based cross-workflow impersonation via HTTP trigger requests - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go, core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
The gateway's HTTP trigger path resolves a target workflow by `(workflowOwner, HashTruncateName(workflowName), workflowTag)` instead of the full 32-byte `WorkflowID`. `HashTruncateName` produces only a 10-byte (80-bit) digest of the user-supplied workflow name [1](#0-0) , and this truncated hash is the sole distinguishing key stored in the `workflowRefToID`/`workflowIDToRef` maps used to route unprivileged HTTP trigger requests to a specific workflow [2](#0-1) . This is structurally the same defect flagged in the external report: relying on a short, brute-forceable hash prefix as the *only* discriminator for routing/authorization, instead of validating full, collision-resistant identity.

### Finding Description
`resolveWorkflowID` in `httpTriggerHandler` accepts an unauthenticated/unprivileged-triggered HTTP request specifying `WorkflowOwner`, `WorkflowName`, and `WorkflowTag`. When no explicit `WorkflowID` is given, it computes `workflowName := "0x" + hex.EncodeToString(workflows.HashTruncateName(triggerReq.Params.Workflow.WorkflowName))` and looks up the workflow via `h.workflowMetadataHandler.GetWorkflowID(workflowOwner, workflowName, workflowTag)` [3](#0-2) .

`HashTruncateName` only keeps 10 bytes (80 bits) of the hash of the name — this is explicitly documented as "the receiver hashes/truncates it internally" in a related contract-facing config comment [4](#0-3) , and the same primitive is reused across multiple places for on-chain/off-chain workflow identity binding [5](#0-4) .

Because the workflow lookup key is `(owner, truncated-name-hash, tag)` and not the full name, two different workflow names belonging to the *same owner* and using the *same tag* that happen to produce the same 10-byte truncated hash are indistinguishable to the gateway's routing table. An attacker who controls a workflow under a given owner address (workflow registration is not privileged — any address can register a workflow name via the on-chain WorkflowRegistry) can brute-force a workflow name whose `HashTruncateName` output collides with the truncated hash of a victim's already-registered, already-authorized workflow name (same owner, same tag). Once registered, the metadata handler's `workflowRefToID`/`workflowIDToRef` maps [6](#0-5)  can no longer disambiguate between the two names for that (owner, tag) pair — later name-based HTTP trigger lookups resolve to whichever entry is currently stored, allowing request/response confusion between the victim's workflow and the attacker's colliding one.

This mirrors the report's root cause exactly: a fixed, short hash prefix is trusted as a unique identifier for routing/validation purposes without any additional context check (the report's recommended fix was "validate the address that emits the event as well" — i.e., don't rely solely on the truncated hash). Here, the equivalent missing check would be validating against the full name (or increasing/verifying full context) before treating a truncated-hash match as authoritative for routing an unprivileged trigger request.

### Impact Explanation
An attacker who registers a workflow under an owner they control can trigger a birthday-style collision search over the workflow-name space to obtain a `HashTruncateName` collision with another workflow registered under the same owner and tag. If exploited, HTTP-triggered requests intended for one workflow could resolve to — and be executed against — a different workflow, or the workflow-ID resolution used for gateway routing/authorization could become ambiguous, leading to cross-workflow response/request confusion. The name-hash truncation to 80 bits is far weaker than the underlying 256-bit `WorkflowID`, making a birthday attack on this specific derived identifier meaningfully more tractable than an attack on `WorkflowID` itself.

### Likelihood Explanation
Likelihood is limited by the requirement that owner and tag also match, which narrows the practical exploitation window (an attacker generally needs to already control the owner account whose workflow they want to collide with, or convince/wait for a shared owner/tag scenario). This differs from the original Optimism report, where any attacker-deployed contract could collide with the trusted function selector regardless of caller identity. Nonetheless, the primitive itself (`HashTruncateName`) is reused broadly for workflow identity across the codebase, and any code path that trusts the truncated name hash as a full identifier — without also comparing the full name or `WorkflowID` — inherits this weakness.

### Recommendation
Do not use the 10-byte `HashTruncateName` output as the primary/sole key for workflow lookup or authorization decisions. Where full `WorkflowID` (32 bytes) is available, always route/authorize by `WorkflowID` and use the truncated name hash only when the full ID is genuinely unavailable, with the full workflow name stored and re-verified when possible. When resolving via `(owner, name, tag)` in `GetWorkflowID`/`resolveWorkflowID`, retain the full plaintext name alongside the truncated hash in the reference table and reject/flag lookups where the full name does not match a colliding truncated hash before treating the mapping as authoritative.

### Proof of Concept
1. Register workflow A under owner `O` with tag `T` and name `nameA`; the gateway stores `workflowRefToID[{O, HashTruncateName(nameA), T}] = idA` [6](#0-5) .
2. Under the same owner `O` and tag `T`, brute-force a `nameB != nameA` such that `HashTruncateName(nameB) == HashTruncateName(nameA)` (80-bit search space, feasible with sufficient compute/time or via any weakness in the underlying hash truncation).
3. Register workflow B with `nameB`; the gateway's `workflowRefToID`/`workflowIDToRef` maps now collide on the same truncated-hash key used for lookups in `resolveWorkflowID` [3](#0-2) .
4. Send an HTTP trigger request specifying `WorkflowOwner=O`, `WorkflowName=nameA`, `WorkflowTag=T` (or `nameB`); demonstrate that resolution is ambiguous/incorrect due to the collision, causing the request to be routed to the unintended workflow.

func (h *httpTriggerHandler) resolveWorkflowID(ctx context.Context, triggerReq *jsonrpc.Request[gateway_common.HTTPTriggerRequest], requestID string, callback handlers.Callback) (string, error) {
	h.lggr.Debugw("resolving workflow ID", "workflowID", triggerReq.Params.Workflow.WorkflowID, "workflowOwner", triggerReq.Params.Workflow.WorkflowOwner, "workflowName", triggerReq.Params.Workflow.WorkflowName, "workflowTag", triggerReq.Params.Workflow.WorkflowTag, "requestID", requestID)
	workflowID := triggerReq.Params.Workflow.WorkflowID
	if workflowID != "" {
		workflowID = normalizeHex(workflowID, workflowIDLength)
		_, found := h.workflowMetadataHandler.GetWorkflowReference(workflowID)
		if !found {
			h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, fmt.Sprintf("Workflow not found. 'workflowID' %s is not a valid workflow ID", workflowID), callback)
			return "", errors.New("workflow not found")
		}
		return workflowID, nil
	}
	workflowOwner := normalizeHex(triggerReq.Params.Workflow.WorkflowOwner, workflowOwnerLength)
	workflowName := "0x" + hex.EncodeToString([]byte(workflows.HashTruncateName(triggerReq.Params.Workflow.WorkflowName)))
	workflowID, found := h.workflowMetadataHandler.GetWorkflowID(
		workflowOwner,
		workflowName,
		triggerReq.Params.Workflow.WorkflowTag,
	)
	if !found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "Workflow not found. Provide either a valid 'workflowID' or a valid combination of 'workflowOwner', 'workflowName', and 'workflowTag'", callback)
		return "", errors.New("workflow not found")
	}
	return workflowID, nil
