### Title
Missing relayer-allowlist gate on `onAccept` allows forged-relayer governance/escrow actions on the Tron `IntentGatewayV2` fork - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The mainline EVM `IntentGatewayV2` (`evm/src/apps/IntentGatewayV2.sol` / `evm/src/apps/intentsv2/ExtrinsicIntents.sol`) was hardened on 2026‑09‑03 with a relayer allowlist: `onAccept` and `onGetResponse` now call `_checkRelayer(incoming.relayer)` *before* decoding the message body, so escrow redemption/refund and every governance action (`NewDeployment`, `UpdateParams`, `SweepDust`, `Execute`) can only be actioned by the single relayer address recorded in `_relayer`. That fix (and its `setRelayer`/`_relayer` machinery) was never ported to the Tron fork of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`. This is the same class of bug as the reference report: a sensitive, fund-moving code path is missing an access-control check that an equivalent, audited implementation elsewhere in the same protocol already enforces.

### Finding Description
`evm/tron/contracts/apps/IntentGatewayV2.sol` declares no `_relayer` storage slot and no `_checkRelayer`/`setRelayer` functions — its state section only has `_filled`, `_nonce`, `_params`, `_admin`, etc. [1](#0-0) 

Its `onAccept` handler goes straight from decoding `RequestKind` to processing `RedeemEscrow`/`RefundEscrow` (which release escrowed tokens) and to the governance branch handling `NewDeployment`, `UpdateParams`, `SweepDust`, with no per-relayer check anywhere in the function: [2](#0-1) 

Compare this with the mainline `ExtrinsicIntents.onAccept`, which runs `_checkRelayer(incoming.relayer)` immediately after the `onlyHost` gate and before the `RequestKind` is even read, so every action — escrow release included — is gated on the authorized relayer: [3](#0-2) 

The project's own documentation explains why this gate exists: the relayer field reported to `onAccept` (`incoming.relayer`) is only as trustworthy as the host's configured `handler` contract, which itself can be replaced through governance (`HostManager` → `EvmHost.updateHostParams`). The relayer allowlist is explicit defense-in-depth against a compromised/misrouted handler being able to attribute a delivery to an untrusted party and thereby trigger governance or escrow-draining actions: [4](#0-3)  and [5](#0-4) 

The changelog for that fix lists every file touched by the hardening (`contracts/apps/IntentGatewayV2.sol`, `evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, associated tests) — `evm/tron/contracts/apps/IntentGatewayV2.sol` is conspicuously absent, confirming the Tron deployment never received the fix. [6](#0-5) 

### Impact Explanation
On any chain where this Tron variant is deployed as the live `IntentGatewayV2`, any relayer able to get a delivery attributed to it through `EvmHost.dispatchIncoming`/`HandlerV2` (or through a future handler swap/misconfiguration) can trigger `RedeemEscrow`/`RefundEscrow` and drain escrowed user/solver funds, or apply forged `UpdateParams`/`NewDeployment`/`SweepDust` governance actions, without the same-relayer restriction the rest of the protocol relies on as a second line of defense. This is concrete theft-of-funds / unauthorized-app-action risk on the intents escrow, matching the reference report's "sensitive setter functions with no meaningful access control" pattern, just missing on a specific deployment target instead of missing everywhere.

### Likelihood Explanation
This requires either (a) a compromised/misrouted `handler` on the host reporting an incorrect relayer for an otherwise-legitimate message, or (b) any future bug in how the relayer parameter is derived/propagated to `onAccept`. The mainline contracts treat this as sufficiently likely/serious to warrant an explicit fix and dedicated regression tests, so the Tron fork's omission of that same fix constitutes a real, currently-unmitigated regression on that deployment target — the underlying trust assumption (`onlyHost` implies `incoming.relayer` is trustworthy) was reviewed and rejected everywhere else in the codebase.

### Recommendation
Port the 2026‑09‑03 relayer-allowlist fix to `evm/tron/contracts/apps/IntentGatewayV2.sol`: add a `_relayer` storage slot, a host-gated `setRelayer`, and a `_checkRelayer(incoming.relayer)` call at the top of `onAccept`/`onGetResponse`, mirroring `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, and add the same regression tests (`testOnAcceptRejectsUnlistedRelayer`, `testFreshProxyIsOpenUntilGovernanceArmsIt`, etc.) against the Tron build.

### Proof of Concept
Not independently exploitable through the indexed context alone — full confirmation requires reviewing the Tron file's complete `onAccept`/`onGetResponse` bodies and the Tron-side host/handler wiring, which were only partially retrievable here (lines ~120–630 of `evm/tron/contracts/apps/IntentGatewayV2.sol` were not fully inspected). Based on the retrieved storage section (no `_relayer`), the retrieved `onAccept` body (no relayer check before acting on `RedeemEscrow`/`RefundEscrow`/governance kinds), and the changelog's explicit file list excluding this path, the missing gate is a documented, high-confidence but not fully code-walked finding. Recommend a Devin session with full repository access to confirm there is no equivalent gate elsewhere in the Tron contract or its Tron-specific host/handler before treating this as fully verified.

# 2026-09-03 — Governance deliveries to `HostManager` gated on the same relayer

Closes the route around the app-level gates: `HostManager.onAccept` accepted `SetHostParam` from
any relayer, and that request can replace the host's handler, the contract every app trusts to
report the relayer address. `HostManager` now holds `_relayer`, set by the host admin through
`setRelayer`, and `onAccept` reverts with `UnauthorizedRelayer` for any other relayer, zero
included. Only governance traffic reaches this contract, so ordinary relaying is unaffected.
No file in this package changed; the entry is here because the delivery flow documented in
`Flow.md` is what it corrects.

# 2026-09-03 — Relayer allowlist on the intent gateway

The gateway now accepts `onAccept` and `onGetResponse` deliveries only from a single authorised
relayer stored at `_relayer` (slot 13, packed behind `_paused`). The check runs before the message
body is decoded, so escrow redemptions, refunds and every governance action, upgrades included, are
covered. A refused delivery reverts, which the host records as undelivered, so the authorised
relayer can submit the same message later. `setRelayer(address)` is callable by the immutable
`_owner` and by the host; the host branch exists so a governance `UpgradeContract` can carry the
call as its migration calldata and arm the relayer in the upgrade transaction (`upgradeToAndCall`
delegatecalls that calldata with the host still as `msg.sender`).

The interface gains `RelayerUpdated(address previous, address current)` and `setRelayer`, keeping
its declarations identical to `IntentsBase`. The unused `_paused` getter was dropped from the gateway
to stay under the EIP-170 size limit; it was never declared here.

`evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`,
