Based on my investigation, I found a concrete equality-breaking analog in `PoaBridge.describeWithdrawal` / `findMatchingWithdrawal`.

### Title
Withdrawal status/tx-hash misreport when a batch contains multiple withdrawals of the same token via POA Bridge - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`findMatchingWithdrawal` matches a withdrawal entry only by `assetId`, not by index, amount, or destination address, when a NEAR intent transaction produces multiple POA-bridge withdrawals of the *same token* (a batch withdrawal with two entries for the same `assetId` but different destinations/amounts).

### Finding Description
`describeWithdrawal` fetches all withdrawals tied to the intent tx hash and calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` [1](#0-0) [2](#0-1) . `Array.prototype.find` returns the **first** matching element regardless of which of the `N` batch entries actually corresponds to a given `withdrawalParams`/`index`. When the response API returns multiple withdrawals sharing the same `near_token_id` (i.e., a batch withdrawal sends the same token to two different destination addresses, or in two different amounts, within one intent), both `createWithdrawalCompletionPromises` calls to `describeWithdrawal` (one per withdrawal index, per `withdrawalParams.map((_, index) => ...)` in `sdk.ts`) [3](#0-2)  will independently invoke `findMatchingWithdrawal` with the *same* `assetId` and get the *same first match* — so both promises resolve to the same `txHash`/status, even though they represent distinct on-chain withdrawals with different `destinationAddress` and `amount`.

The code even documents this gap explicitly: *"Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported."* [4](#0-3) . There is no assertion or runtime guard that rejects such batches — `createWithdrawalIdentifiers` and `PoaBridge.supports`/`validateWithdrawal` do not detect or reject duplicate-assetId batch withdrawals [5](#0-4) .

This breaks the equality: *the status/tx-hash reported for withdrawal index `i` must correspond to the on-chain outcome of withdrawal `i`'s actual `(destinationAddress, amount)`* — instead, both indices can report the outcome belonging to only one of them.

### Impact Explanation
An integrator building on `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` for a batch with two same-token withdrawals to different addresses/amounts could receive a "completed" status with the *same* `txHash` for both entries. This is a status misreport that could lead the integrator to credit/consider both withdrawals settled based on one actual on-chain transfer, i.e., a double-credit risk purely from the SDK's reporting layer, not from any privileged/malicious action — matching the "status or hash misreport making an integrator credit or refund twice" High-impact category.

### Likelihood Explanation
Requires a caller to construct a batch of `WithdrawalParams` containing two entries with the identical `assetId` routed through the POA Bridge (route `poa_bridge`). This is a normal application-level input (no privileged access needed) — e.g., a solver splitting a withdrawal of the same token into two different destination addresses in a single batch. The bug is unconditionally reachable whenever that shape of input occurs; it is explicitly acknowledged as unhandled in the code comment, indicating real likelihood.

### Recommendation
`findMatchingWithdrawal`/`describeWithdrawal` should either (a) reject/validate at `createWithdrawalIdentifiers` time when a batch contains duplicate `assetId` entries routed to POA Bridge, throwing a clear "unsupported" error, or (b) disambiguate matches using additional fields the POA API returns (e.g., destination address, amount, or a stable per-withdrawal correlation id) rather than relying solely on `assetId`, so that each `index` is deterministically bound to the withdrawal that produced it.

### Proof of Concept
1. Caller builds `withdrawalParams = [{assetId: "nep141:usdc.omft.near", destinationAddress: A, amount: 100}, {assetId: "nep141:usdc.omft.near", destinationAddress: B, amount: 200}]` and submits via `processWithdrawal`/`signAndSendWithdrawalIntent`.
2. NEAR intent settles, producing two POA withdrawal records with the same `near_token_id` but different destination/amount.
3. `sdk.createWithdrawalCompletionPromises` calls `PoaBridge.describeWithdrawal` once per index; both calls invoke `findMatchingWithdrawal(response.withdrawals, "nep141:usdc.omft.near")`, both returning `withdrawals[0]` (the first match) regardless of index — `promises[0]` and `promises[1]` resolve to the same `{status: "completed", txHash}` even though only one of the two on-chain withdrawals may actually be that hash [6](#0-5) .

Note: I could not fully verify how the POA Bridge API's withdrawal response distinguishes same-token entries within the scope provided (that API client lives outside the listed in-scope paths), so I cannot confirm whether additional distinguishing fields (e.g., amount) are present in `response.withdrawals` that a fix could leverage — this would need confirmation against `poaBridge.httpClient.getWithdrawalStatus`'s actual response shape.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
