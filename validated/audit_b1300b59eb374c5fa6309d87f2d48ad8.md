### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant/handler routing without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content solely from the raw HTTP body, while the `shop-domain`, `topic`, `api-version`, and `webhook-id` values are read directly from unauthenticated HTTP headers and are never included in the HMAC-covered material. `Registry.process` treats `Utils::HmacValidator.validate(request)` as proof that the whole request (including which shop and topic it belongs to) is authentic, then dispatches to handlers and constructs `WebhookMetadata` using those unverified header values.

### Finding Description
The gem documents `Registry.process` as verifying "the request did indeed come from Shopify" before invoking the handler (`docs/usage/webhooks.md`). In practice, only the raw body is authenticated: [1](#0-0) 

```
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers with no cryptographic binding to the body or to each other: [2](#0-1) .

`Registry.process` performs a single HMAC check against the body, and if it passes, unconditionally trusts `request.topic` to select the handler and `request.shop` to populate `WebhookMetadata.shop`, which apps use as the tenant key: [3](#0-2) .

The identity binding that should hold is:
`shop_that_produced_this_HMAC-verified_body == shop_the_handler_attributes_the_data_to`

Because the HMAC only covers `@raw_body`, this equality is not enforced. Any request whose body+HMAC pair was legitimately issued by Shopify for **some** shop can be replayed with the `shop-domain` (and/or `topic`) header rewritten to name a different shop/topic, and `Utils::HmacValidator.validate` will still return true, since it recomputes the signature only from `to_signable_string` (the body) and compares it against the supplied `hmac` field: [4](#0-3) .

An unprivileged attacker who controls any shop that has this app installed (a normal, low-privilege merchant/developer account, not requiring `api_secret_key` or a stolen token) receives genuine Shopify webhook deliveries for their own shop with valid bodies and HMACs. They can capture such a delivery and replay it directly to the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim shop's domain (and/or the `shopify-topic` header changed to a topic the attacker wants processed). The gem's own validation logic accepts this as authentic because it never binds the header-derived shop/topic to the HMAC-covered payload.

### Impact Explanation
This breaks the shop/tenant identity binding relied on by every consumer of `WebhookMetadata.shop` and by `Registry.process`'s topic-based handler dispatch. A host application that stores or acts on webhook data keyed by `data.shop` (the documented and recommended usage pattern shown in `docs/usage/webhooks.md`) will attribute attacker-supplied body content to an arbitrary victim shop chosen by the attacker — i.e., cross-tenant data injection/confusion, satisfying the "cross-tenant access" Critical-impact criterion. It can also be used to invoke a handler for a topic the attacker did not actually trigger, causing the app to perform tenant-scoped side effects (e.g., redact/data-request handlers, order-processing logic) against the wrong shop.

### Likelihood Explanation
The prerequisite (having any shop with the app installed) is achievable by any unprivileged internet user with a free/dev Shopify store, since Shopify allows anyone to install a public app on their own store and will deliver real webhooks with valid signatures for that store's own events. Capturing and replaying an HTTP request with modified headers requires no special access to the target application, no secrets, and no privileged account — only visibility into the webhook endpoint's public URL (which is inherently public, since it must receive Shopify's callbacks).

### Recommendation
Bind the routing/tenant-identifying headers into the HMAC-covered material, or independently verify `shop-domain` against the shop the app actually expects for a given delivery (e.g., cross-check against a known/registered shop record, and additionally validate that `topic` matches metadata already associated with the verified webhook, such as by cross-referencing `webhook_id` against Shopify's API). At minimum, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate the `shop-domain` and `topic` header values so that the HMAC comparison in `Utils::HmacValidator.validate` fails if those headers are altered relative to what Shopify actually signed for that delivery.

### Proof of Concept
1. Attacker installs the target app on their own Shopify dev store, `attacker.myshopify.com`.
2. Shopify delivers a legitimate webhook, e.g. `orders/create`, to the app's webhook URL with headers:
   - `x-shopify-topic: orders/create`
   - `x-shopify-hmac-sha256: <valid HMAC over raw body>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
3. Attacker replays the exact same raw body and `x-shopify-hmac-sha256` value to the same endpoint, but changes:
   - `x-shopify-shop-domain: victim.myshopify.com`
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present) and `Utils::HmacValidator.validate` succeeds because it only re-hashes `@raw_body`, which is unchanged: [5](#0-4) .
5. `Registry.process` invokes the registered `orders/create` handler with `WebhookMetadata.shop == "victim.myshopify.com"`, even though the payload actually originated from the attacker's own shop, and the host app (per the gem's documented usage pattern) stores/acts on this data under the victim's tenant.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
