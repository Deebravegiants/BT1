No duplicate-assetId validation exists in `sdk.ts` — a user can freely submit two withdrawal legs of the same NEP-141 assetId in one batch. This confirms the vulnerability is real and reachable.

### Title
Status/txHash misreport for concurrent same-asset withdrawal legs enables double-credit/missed-completion - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.findMatchingWithdrawal` matches a withdrawal status purely by `assetId`, ignoring `WithdrawalIdentifier.index`. When a single intent contains two POA-bridge withdrawal legs of the same NEP-141 asset (different amounts/destinations), `describeWithdrawal` returns the same (status, txHash) for both `index: 0` and `index: 1`, violating the STATUS_TRUTH invariant that the reported status for withdrawal `i` reflects the actual outcome of withdrawal `i`.

### Finding Description
The broken equality: `describeWithdrawal({index:0}).txHash` should equal the on-chain outcome of withdrawal leg 0, and `describeWithdrawal({index:1}).txHash` should equal the outcome of leg 1 — these must differ when the legs have different destinations. Instead both calls resolve to the identical array element.

Root cause is in `findMatchingWithdrawal` at [1](#0-0) , which does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` with no use of `index`. This function is called from `describeWithdrawal` at [2](#0-1) , which is invoked once per index by `watchWithdrawal` at [3](#0-2) .

Reachable attacker path: an unprivileged user calls `sdk.processWithdrawal` / `sdk.waitForWithdrawalCompletion` / `sdk.createWithdrawalCompletionPromises` with `withdrawalParams: [{assetId: "nep141:eth.omft.near", amount: A, destinationAddress: X}, {assetId: "nep141:eth.omft.near", amount: B, destinationAddress: Y}]`. No code in `sdk.ts` deduplicates or rejects repeated `assetId` values within a batch. `createWithdrawalIdentifiers` at [4](#0-3)  assigns per-route sequential indexes (0 and 1) to both legs since both route to `PoaBridge`. Both `watchWithdrawal` calls query the POA bridge indexer by the same `tx.hash` (`getWithdrawalStatus({ withdrawal_hash: args.tx.hash })`, [5](#0-4) ) which returns both withdrawals in an unsorted array; `findMatchingWithdrawal` then returns the first array element matching the shared `assetId` for **both** index-0 and index-1 lookups, regardless of which leg actually completed or its real `transfer_tx_hash`.

This is a known, explicitly documented limitation in the code comment ("Currently only matches by assetId... multiple withdrawals of the same token in a single transaction are not supported"), confirming the developers are aware the guarantee does not hold for this case, and there is no other guard (`supports()`, `validateWithdrawal`, `assert`) that rejects or serializes duplicate-assetId batches before this divergence can occur.

### Impact Explanation
An integrator that credits/refunds a user per `WithdrawalIdentifier.index` (a documented, expected pattern per the "Index correspondence: `promises[i]` corresponds to `withdrawalParams[i]`" note in the README) will: (a) credit both index 0 and index 1 with the same `txHash` even though only one leg actually completed, effectively crediting/confirming one leg twice, and (b) never learn the true status/hash of the other leg. This is a status/hash misreport causing double-credit, matching the High-severity category ("a status or hash misreport making an integrator credit or refund twice"). It's repeatable on every batch withdrawal containing ≥2 legs of the same POA-bridge asset.

### Likelihood Explanation
Preconditions: attacker only needs to submit an intent with two `ft_withdraw` legs for the same NEP-141 `assetId` routed through PoaBridge, using standard public SDK entry points (`processWithdrawal`, `waitForWithdrawalCompletion`, `createWithdrawalCompletionPromises`). No special privileges, relayer complicity, or unusual chain state are required — attacker cost is a single normal transaction. This is fully attacker-controlled and trivially repeatable.

### Recommendation
Match withdrawals to `WithdrawalIdentifier` by more than `assetId` — e.g., correlate by `destinationAddress`/`amount` in addition to `near_token_id`, sort both the API response and the local withdrawal params by amount before pairing (as the code comment itself suggests), or reject/serialize batches containing duplicate `assetId` values for the same route until the POA API supports disambiguation.

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
