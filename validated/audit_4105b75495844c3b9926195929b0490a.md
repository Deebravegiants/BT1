### Title
Webhook Shop Identity Spoofing via HMAC that Only Covers Request Body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively from the raw request body, while the `shop` (tenant) identifier is read from a separate, unauthenticated header. `ShopifyAPI::Webhooks::Registry.process` validates only the body HMAC and then unconditionally trusts the header-derived `shop` value when dispatching to the app's webhook handler, allowing a merchant who legitimately receives a valid webhook for their own store to replay it while claiming it originated from a different shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed payload at all: [2](#0-1) 

`Registry.process` validates the HMAC (which only proves the body was produced/known by an entity holding `api_secret_key`) and then forwards `request.shop` — an attacker-controllable header — straight to the app's handler as the trusted tenant identifier: [3](#0-2) 

The identity binding that should hold is: `hmac_signature == HMAC(secret, body_bound_to_shop)`. Instead the equality actually enforced is `hmac_signature == HMAC(secret, body)`, with `shop` entirely outside that binding. A merchant who has installed the app on their own store (a normal, unprivileged action requiring no secret material) legitimately receives real webhook deliveries with a valid `x-shopify-hmac-sha256` value computed over the body. Because the header carrying `shop` is never part of what's signed, that same `(body, hmac)` pair remains valid when replayed to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to any other shop. `Registry.process` will accept it and hand `WebhookMetadata` with the forged `shop` to the app's handler code.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: an attacker who is merely a legitimate merchant of one shop can make the app believe a webhook (with attacker-chosen JSON body content, since the attacker can request/trigger their own webhooks with content they influence, e.g., product or order fields) came from a shop they do not control. Depending on what the host application's handler does with `data.shop` (e.g., look up/update stored state keyed by shop, trigger uninstall/cleanup, write records attributed to that shop), this enables cross-tenant data corruption or state manipulation — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is significant: the only prerequisite is installing the app on any shop (a normal, unprivileged capability for any Shopify merchant/attacker) and capturing one delivered webhook, then replaying it against the app's public webhook endpoint with a rewritten shop header. No knowledge of `api_secret_key` or any other credential is required, since the HMAC never binds to the shop value in the first place.

### Recommendation
Bind the `shop` value into the signed material used for verification (or otherwise cryptographically tie the header-derived shop identity to the signed body/topic/webhook-id), and reject requests where the claimed shop cannot be tied to the same request that was HMAC-verified. At minimum, `Registry.process` should not treat `request.shop` as trustworthy for any authorization-sensitive decision without an additional binding check (e.g., verifying the delivering shop against a shop known to be associated with the current app installation before dispatching to handlers).

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to.
2. Capture the delivered request: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(secret, B)`).
3. Replay the same body `B` and same header `H` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`; `Registry.process` builds `WebhookMetadata` with `shop: "victim.myshopify.com"` and invokes the app's handler as if the webhook came from the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
