## Title
Emporium arbitrary-call output outside the declared `erc20TokenAddresses` set is silently unattributed and permanently stuck - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable::runAction()` only measures balance deltas for the token set that the prover chose to include in `circomData.erc20TokenAddresses`, and `handleOut()` only redistributes value for exactly those indices. Just like Cork's `VaultPoolLib::reserve()`, which tracked only the `Ra`-denominated leftover and left `Pa` "to sit there until rationed again" (never actually happening), any asset the arbitrary `EmporiumOperation` calls receive but which is not one of the declared, tracked tokens is never measured, never attributed to the user, and never returned - it simply accumulates on the `Emporium` contract with no code path to reclaim it.

### Finding Description
`runAction()` snapshots balances only for `circomData.erc20TokenAddresses`: [1](#0-0) 
then executes arbitrary, prover-supplied `EmporiumOperation`s against arbitrary `endpoint`s with arbitrary `callData`/`value`: [2](#0-1) 
Afterwards it iterates only over `circomData.erc20TokenAddresses` (again, a set chosen by the caller/prover) to compute `balanceChange` and calls `handleOut()`, which forwards any positive delta to `msg.sender` and produces a UTXO for it: [3](#0-2) 

There is no fallback loop or sweep step that reconciles balances for tokens outside this declared set. If any operation in `stack.ops` results in the `Emporium` contract receiving a token that is not included in `circomData.erc20TokenAddresses` (e.g., a reward token, airdrop, refund, or any secondary token returned by the called `endpoint`), that balance:
- is never measured (no before/after snapshot exists for it),
- is never attributed to any UTXO (`handleOut` only runs for indices in the declared array),
- and is never transferred out (no equivalent of Cork's `rationedToAmm` even attempts to deal with it).

This mirrors the Cork root cause exactly: the code comment in Cork acknowledged the leftover `Pa` would "sit there until rationed again," but no such mechanism existed - `rationedToAmm()` only used the `Ra` balance. Here, `Emporium`'s balance/UTXO reconciliation only operates on the caller-declared token array, and value received outside that array is permanently orphaned in the contract with no code path to ever move it back into the shielded balance equation enforced by `Hinkal.sol`'s outer balance-diff check: [4](#0-3) 

Because `Hinkal.sol` itself also only checks `balanceDif` for `circomData.erc20TokenAddresses`, the protocol-level invariant ("change in Hinkal balance == change in tracked UTXOs") never sees the untracked token either - it is entirely outside the equality the whole system is built to enforce.

### Impact Explanation
Any value that lands in the `Emporium` contract outside the declared token set is permanently frozen - no user, relayer, or admin function exists to retrieve it (no rescue/sweep function is present in `EmporiumUpgradeable.sol` or its base `ExternalActionBaseUpgradeable`). This is a permanent freezing of protocol/user funds, matching the "High - permanent freezing of protocol/relay fees" / "temporary or permanent freezing of user funds" impact bucket. Unlike Cork's version (an internal accounting artifact of an AMM), here it is directly reachable by any unprivileged EOA constructing an `EmporiumStack` whose operations interact with contracts that pay out secondary tokens (e.g., reward tokens, refunds, or dust from a called protocol) not listed in `erc20TokenAddresses`.

### Likelihood Explanation
Reasonably likely: the `EmporiumOperation.endpoint`/`callData` are fully attacker/prover chosen (bounded only by `onlyAllowedRecipient`/`allowedRecipients` at the `endpoint` level per `verifyWallet`/`ExternalActionBaseUpgradeable` allow-listing, not by which tokens flow back). Any interaction with a whitelisted DeFi protocol that can return more than one token (rewards, referral bonuses, LP incentive claims, etc.) - while the user only lists the "main" tokens they expect - will trigger this. A user (or a relayer building the calldata) simply forgetting to enumerate every token an operation could return is enough; no malicious intent is required to trigger the freeze, though a malicious actor can deliberately construct operations to strand relay/protocol fee tokens as well.

### Recommendation
Add a sweep/reconciliation step, or require operators to declare all tokens `endpoint` calls can plausibly return and revert if unexpected balances appear (fail-safe instead of silently swallowing value); alternatively, add an owner/relayer-gated rescue function scoped per Emporium message/signer so misrouted tokens can be recovered and returned to the rightful shielded owner, following the mitigation Cork itself proposed (redistribute/attribute leftover value rather than leaving it untracked).

### Proof of Concept
1. Prover submits `transact()` with `externalActionId` pointing at `Emporium`, and `circomData.erc20TokenAddresses = [USDC]`.
2. `EmporiumStack.ops` includes a stateless call to a whitelisted `endpoint` (e.g., a staking/farm contract) that, as a side effect of the call, also transfers a reward token `RWD` to `msg.sender` (the `Emporium` contract), in addition to returning `USDC`.
3. `runAction()` snapshots and later diffs balances only for `USDC` (lines 85-87, 122-151); `RWD`'s balance increase is never observed.
4. `handleOut()` never runs for `RWD`, so no UTXO is minted and no transfer occurs for the `Emporium` contract's `RWD` balance.
5. `RWD` remains in `Emporium` permanently; no function in `EmporiumUpgradeable.sol` can move it back to the user or the protocol - it is out of the tracked equality enforced by `Hinkal.sol`'s balance-diff/UTXO reconciliation loop entirely.
