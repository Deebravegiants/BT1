Webhook `shop-domain` header is trusted for tenant attribution but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop` is read directly from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` header. `Registry.process` validates the HMAC over the body only, then hands the unauthenticated `shop` value straight to the app's handler as trusted tenant identity, breaking the equality "shop authenticated == shop the data is attributed to."

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`hmac` is parsed from the `hmac-sha256` header and `to_signable_string` returns `@raw_body` — nothing else. `shop` is read straight from the `shop-domain` header with no cryptographic binding to the body or the HMAC.

`HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string`: [2](#0-1) 

`Registry.process` validates this HMAC (i.e., only proves the body's integrity/authenticity using the shared `client_secret`) and then immediately trusts `request.shop` to build `WebhookMetadata`, which is passed to the app-defined handler as the tenant identifier: [3](#0-2) 

The gem's own documentation instructs app authors to treat `data.shop` as the authoritative shop for the webhook and to key their processing/storage off it: [4](#0-3) 

Because `shop` is not part of `to_signable_string`, any raw body + HMAC pair that is valid for the shared `client_secret` for **any** shop remains valid regardless of which `shop-domain` header value is attached to it. A user who has installed the app on their own store (an ordinary, unprivileged action) can capture one of their own legitimately-signed webhook deliveries (body + `hmac-sha256` header), and replay it to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` value (e.g., a different, victim shop's domain). `HmacValidator.validate` still succeeds because it only checks the body against the secret; `Registry.process` then calls the handler with `WebhookMetadata.shop` set to the attacker-chosen value.

### Impact Explanation
This breaks the binding "the shop that authenticated the webhook == the shop the app attributes the webhook payload to." Any app built on this gem that uses `WebhookMetadata#shop` — as instructed by the library's own documentation and `Request` design — to key per-tenant storage/state updates can be made to write, or act on, data on behalf of a shop the attacker does not own, i.e., cross-tenant data injection/corruption. This matches the "cross-tenant access" Critical impact category, since the security boundary between merchants (tenant isolation) is enforced solely by this unauthenticated header.

### Likelihood Explanation
The attack requires only: (1) the attacker legitimately installs the app on any store they control (a normal unprivileged action many app install flows allow), (2) they capture one webhook delivery for a subscribed topic, and (3) they POST it to the app's public webhook endpoint with a forged `shop-domain` header. No access to `api_secret_key`, access tokens, or any privileged credential is required — the exploit works precisely because the header is unauthenticated. The only gating factor is that the app must expose its webhook endpoint publicly (a standard requirement for receiving Shopify webhooks) and must use `data.shop` for tenant attribution, which is exactly what the gem's documentation recommends.

### Recommendation
Bind `shop` (and ideally `topic`, `webhook_id`, `api_version`) into the value verified by the HMAC, or otherwise cryptographically tie the header-derived shop to the signed body (e.g., include the shop domain in `to_signable_string`, or independently verify the shop is one for which the app holds an active session/registration before trusting it). At minimum, document prominently that `data.shop` is not covered by the HMAC and must not be used as the sole tenant-isolation key without additional verification (e.g., cross-checking against a known/registered shop list).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real webhook, e.g. `orders/create`, and observes the raw body `B` and the valid `x-shopify-hmac-sha256` header `H` (computed by Shopify using the app's `client_secret` over `B`).
2. Attacker sends a forged HTTP request directly to the app's webhook endpoint:
   ```
   POST /callback/orders/create
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: H
   x-shopify-shop-domain: victim-shop.myshopify.com
   x-shopify-webhook-id: <any>
   x-shopify-api-version: 2024-01

   B
   ```
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is built; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string == B` and `H` is a valid HMAC of `B` under the shared secret [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed B, ...)` — the app now processes attacker-controlled data as belonging to a shop the attacker does not own [6](#0-5) .
