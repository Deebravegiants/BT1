Based on my investigation, I found a concrete off-by-one boundary-check analog in `Pair.sol`'s K-invariant enforcement.

### Title
K-invariant check in `Pair.swap` uses a `+1` slack on both reserves instead of an exact bound, permitting the curve to under-collateralize by up to the full reserve size per call - ([File: packages/contracts/src/Pair.sol])

### Summary
The external report describes an off-by-one bounds check (`>` instead of `>=`) in GLib's `gvs_tuple_is_normal` that weakens a safety check by exactly one unit, causing an out-of-bounds read. The alt.fun analog is `Pair.swap`'s K-invariant guard, which checks `(newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k` instead of the exact `newTokenReserve * newAssetReserve < _pool.k` [1](#0-0) . Both are boundary-check weakenings where a fixed additive slack (`+1`) is applied to a comparison that is supposed to be exact, changing "must be at least k" into "may be short of k by up to `newTokenReserve + newAssetReserve + 1`."

### Finding Description
`Pair.swap` is the sole invariant guard protecting the bonding-curve pool's reserves: `Router.buy`/`Router.sell` are the only callers (`onlyRouter`), and they compute `tokensOut`/`amountInUsed`/`assetOut` from `_computeBuy`/`_computeSell` in `Router.sol` before calling `pair.swap(...)` [2](#0-1) . The final on-chain check that the swap didn't violate the constant-product invariant is:

```solidity
uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();
``` [3](#0-2) 

Expanding the LHS: `newTokenReserve * newAssetReserve + newTokenReserve + newAssetReserve + 1 >= k` is what passes. That means the *actual* product `newTokenReserve * newAssetReserve` can be as much as `newTokenReserve + newAssetReserve + 1` **below** `k` and still pass — a slack proportional to the reserve size, not a fixed 1-wei rounding tolerance like Uniswap V2's `balance*1000 adjustments`. This is analogous in class to the GLib bug: a boundary comparison that should be tight (`>=` against the exact invariant) is loosened by an additive term, and the magnitude of the loosening (`+1` per side) is deceptively small-looking in the source but expands to a large absolute tolerance once the multiplication is distributed.

### Impact Explanation
If reachable with attacker-controlled `tokenIn`/`tokenOut`/`assetIn`/`assetOut` combinations that don't already satisfy the strict invariant (only `Router.BONDING_ROLE`-gated callers can invoke `swap`, and today the only caller is `Router` itself, which always derives amounts from `_computeBuy`/`_computeSell` that round in the curve's favor before calling `swap`), the loosened check would let a caller repeatedly extract value from the curve reserves — draining LT (the reserve asset) or tokens below the true backing implied by `k`, which is exactly the "unbacked token or LT payouts" / "concrete theft of trader funds" impact class called out in the validation rules. Because `k` also gates `virtualLtReserve` recovery (`Pair.k() / Token.TOTAL_SUPPLY()`) used by the graduation dual-trigger and `_prepareGraduationLiquidity`'s zero-gap LP seeding [4](#0-3) , any drift in the true reserve product relative to `k` would also corrupt the graduation math (`ltFromPair`, `tokensForLP`), producing an LP seeded away from the true curve close price.

### Likelihood Explanation
Low-to-uncertain today. `Router._computeBuy`/`_computeSell` always compute swap amounts that satisfy the *exact* invariant (rounding in the pool's favor), so the `+1` slack in `Pair.swap` is currently unreachable through the only production caller path (`Router.buy`/`Router.sell`). I was not able to find, in the time available, any other reachable call path that invokes `Pair.swap` with attacker-chosen `tokenIn/tokenOut/assetIn/assetOut` that would land outside the strict invariant but inside the loosened one — the check may currently be defense-in-depth rather than an exploitable gap. This is a real weakening of the invariant boundary (same bug *class* as the GLib off-by-one), but I could not prove a currently-reachable transaction sequence from an unprivileged address that exploits the slack to steal or freeze funds, given `Router` is the only `BONDING_ROLE` holder and its two entry points always pre-round correctly.

### Recommendation
Tighten `Pair.swap`'s invariant check to the exact `newTokenReserve * newAssetReserve < _pool.k` (or, if some rounding tolerance is intentional, bound it to a fixed 1-wei allowance rather than `+1` per reserve, which scales with reserve size) so that no future caller of `Router`/`Pair` with different rounding behavior can slip through a reserve-sized gap. Add a regression test that fuzzes `tokenIn/tokenOut/assetIn/assetOut` directly against `Pair.swap` (bypassing `Router`'s pre-rounding) to confirm the check rejects any product below the true `k`.

### Proof of Concept
Not constructible without a currently-reachable call path that invokes `Pair.swap` with amounts outside the strict invariant — the only caller (`Router.buy`/`sell`) always pre-computes amounts that already satisfy the strict bound, so I cannot demonstrate concrete fund loss with the access I have. This should be flagged for a background agent with terminal/test access to fuzz `Pair.swap` directly (as `Router` via `vm.prank`) with adversarial `tokenIn/tokenOut/assetIn/assetOut` combinations to check whether the `+1` slack is exploitable through any legitimate `BONDING_ROLE` grant path (e.g., `Bonding._pairRebalance`/`_seedRebalancing` internal helpers or any future Router logic change), which I could not fully trace within index limits.

    function swap(
        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }

    function buy(
        uint256 amountIn,
        address token,
        address to
    ) external onlyRole(BONDING_ROLE) returns (uint256 amountInUsed, uint256 tokensOut) {
        if (amountIn == 0) revert ZeroAmount();

        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);

        (amountInUsed, tokensOut) = _computeBuy(pairAddr, amountIn);

        IERC20(asset).safeTransferFrom(to, pairAddr, amountInUsed);

        IPair(pairAddr).transferToken(to, tokensOut);
        IPair(pairAddr).swap(0, tokensOut, amountInUsed, 0);
    }

    /// @notice External view of `_computeBuy`. Returns `(amountInUsed,
    ///         tokensOut)` for a hypothetical LT-in buy of `amountIn`,
    ///         honouring the same overflow cap as `buy()`. Used by `Zap` to
    ///         pre-size the LT mint and by the frontend for buy-quote previews.
    function previewBuy(
        address token,
        uint256 amountIn
    ) external view returns (uint256 amountInUsed, uint256 tokensOut) {
        if (amountIn == 0) revert ZeroAmount();
        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        return _computeBuy(pairAddr, amountIn);
    }

    /// @dev Capped: `amountInUsed` is back-calculated from the K invariant
    ///      (rounded up so the curve never under-charges).
    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

- **Dual trigger.** Phase 1 fires on whichever hits first: `(storedAssetReserve - virtualLtReserve) × exchangeRate ≥ $9K` (USD, for LT pumps) or `IPair.tokenBalance() == 0` (supply, for flat/bear markets). The USD trigger reads STORED reserves so direct LT donations to the pair don't count toward the threshold; the launch-time `virtualLtReserve` is recovered on-the-fly as `Pair.k() / Token.TOTAL_SUPPLY()` (K is set once at mint and never modified by `Pair.swap`). The supply trigger reads live `tokenBalance()`, which is donation-resistant in the opposite direction: token donations only INCREASE the balance and can never satisfy `== 0`, and any donated tokens are unconditionally burned by `_prepareGraduationLiquidity`.
- **Zero-gap LP seeding.** `_prepareGraduationLiquidity` computes `ltFromPair = storedAssetReserve - virtualLtReserve` (the real LT raised by the curve, donation-immune; `virtualLtReserve` is derived from `Pair.k() / Token.TOTAL_SUPPLY()`) and `tokensForLP = ltFromPair × storedTokenReserve / storedAssetReserve` at end-of-phase-1, caching the result. Phase 2 uses the cached value verbatim, so the curve→LP price match is invariant under the tx split. Donated LT stays in the curve pair under the trust assumption that `BONDING_ROLE` is only ever held by `Bonding` and `Bonding` won't call `Router.graduate` again post-graduation.
