### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The webhook `Request#to_signable_string` returns only `@raw_body`, so the HMAC signature validated by `HmacValidator.validate` covers the JSON body alone. The `shop-domain` header — the very field used to attribute the webhook to a tenant when it is handed to the app's handler — is never included in the signed bytes. An unprivileged holder of one authentic webhook (from their own store, since they are a legitimate merchant who installed the app) can replay that exact body/HMAC pair while substituting an arbitrary `shopify-shop-domain` (or `x-shopify-shop-domain`) header value, and `Registry.process` will accept it as coming from that other shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts `shop` from a header: [1](#0-0) 

But the HMAC is computed only over the raw body: [2](#0-1) 

`HmacValidator.validate` simply recomputes the HMAC over `verifiable_query.to_signable_string` (i.e., the body) and compares it to the received signature using `Context.api_secret_key`: [3](#0-2) 

`Registry.process` validates the HMAC, then immediately trusts `request.shop` (unauthenticated) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The broken identity binding is: `shop authenticated by HMAC` (∅ — the header is outside the signable string) ≠ `shop acted on by the handler` (`request.shop`, taken verbatim from a client-controlled header). Any bytes with a valid HMAC for *some* shop's body can be replayed with a different `shop-domain` header and will pass `Utils::HmacValidator.validate` unchanged, since the header never enters the signature computation.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce. A merchant who installs the app on their own store legitimately receives one correctly-signed webhook (e.g., `orders/create`). They can capture that raw body + HMAC and POST it to the app's public webhook endpoint again, substituting the victim shop's domain in the `shop-domain` header. `Registry.process` will still validate successfully (the HMAC only covers the body) and will invoke the host application's handler with `shop: <victim-domain>`, causing the fabricated/replayed data to be attributed to and processed under another tenant's identity — a cross-tenant access condition (Critical per the given impact taxonomy).

### Likelihood Explanation
Any user who can install the app on a store of their own (i.e., any unprivileged internet user who can create a Shopify dev/trial store) can obtain at least one legitimately-HMAC'd webhook body without needing `api_secret_key`, an access token, or any other privileged credential. Replaying it with a modified header requires only a normal HTTP client, making this straightforward to exploit for any app that keys tenant-specific behavior (data storage, session lookups, notifications) off `WebhookMetadata#shop`.

### Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically tie the `shop-domain` header to the HMAC-validated body — e.g., include the shop domain in the signable string, or independently verify that the shop belongs to a session/installation the gem already trusts before dispatching to handlers. At minimum, document that `request.shop` is unauthenticated and must not be trusted for tenant attribution without additional verification (such as confirming an existing offline session for that shop).

### Proof of Concept
```ruby
# Attacker legitimately installs the app on their own store "attacker.myshopify.com"
# and receives one authentic webhook call from Shopify with:
raw_body = '{"id":1,"note":"hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# The attacker now replays the exact same body+HMAC directly to the app's
# webhook endpoint, but swaps the shop header to a victim store:
headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => Base64.encode64(hmac),
  "shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) succeeds (only raw_body is checked),
#    and the handler is invoked with shop: "victim-shop.myshopify.com",
#    even though that shop never sent this webhook.
``` [4](#0-3) [5](#0-4)
