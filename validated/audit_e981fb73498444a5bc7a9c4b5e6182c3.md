Audit Report

## Title
Outbound HTTP response cache in the CRE Gateway omits `WorkflowID` from its cache key, breaking documented workflow isolation - (File: `core/services/gateway/handlers/capabilities/v2/response_cache.go`)

## Summary
The gateway's `responseCache` is documented to scope cached outbound HTTP responses by workflow ID, but the cache key used throughout `Fetch`, `Set`, and `isExpiredOrNotCached` is `gateway.OutboundHTTPRequest.Hash()`, which per the type's own doc comment and confirmed by unit tests only covers method, URL, headers, body, and `workflowOwner` — not `WorkflowID` or `CacheSettings` [1](#0-0) . As a result, two distinct workflows sharing the same owner, method, URL, headers, and body will collide on the same cache entry and receive each other's cached HTTP action responses.

## Finding Description
The README explicitly documents "Cache Key: Generated from workflow ID and request hash" and "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [2](#0-1) , but the actual implementation keys the cache map solely on `req.Hash()` in `Fetch`, `Set`, and `isExpiredOrNotCached` [3](#0-2) [4](#0-3) , with no separate workflow-ID-based namespacing anywhere in the type.

The in-repo test suite directly proves the gap: identical requests differing only in `WorkflowID` produce the same hash, and differing `CacheSettings` also produce the same hash, while differing `WorkflowOwner` correctly produces different hashes [5](#0-4) [6](#0-5) . This confirms the documented "workflow ID"-based isolation is not enforced by the code as written.

The cache is populated and consumed in `makeOutgoingRequest`, which is invoked from `HandleNodeMessage` when a DON node forwards an `OutboundHTTPRequest` derived from a workflow's HTTP Action execution [7](#0-6) . Any two workflow executions under the same owner that produce a matching method/URL/headers/body (e.g., pulling the same public reference-data endpoint) will read/write the same cache slot regardless of which workflow (`WorkflowID`) originated the request.

## Impact Explanation
This causes cross-workflow response confusion: a cached HTTP action response belonging to one workflow can be silently served to a different workflow under the same owner, contradicting the explicit "Workflow Isolation" guarantee in the module's own documentation. Because `CacheSettings` is also excluded from the hash, a request with `Store=false` can still receive (or contaminate) cache entries governed by a different request's `Store=true`/`MaxAgeMs` settings. This is a genuine logic bug and matches the "cross-user/cross-workflow response corruption" impact class, though the blast radius is bounded to workflows sharing the same `workflowOwner` (it is not a cross-tenant/cross-owner leak, since `WorkflowOwner` is correctly included in the hash).

## Likelihood Explanation
No special privilege beyond normal DON node message forwarding for a workflow's HTTP Action capability is needed to trigger a collision — it occurs automatically whenever an owner runs multiple workflows that happen to issue identical outbound requests (same method/URL/headers/body), which is a realistic and non-adversarial scenario (e.g., shared reference-data or price-feed pulls). This is directly demonstrated by existing unit tests in the repository, not merely theoretical.

## Recommendation
Include `WorkflowID` in `OutboundHTTPRequest.Hash()` (and consider incorporating relevant `CacheSettings` fields that affect cache eligibility), or otherwise namespace the `responseCache` map by workflow ID in addition to the request hash, so implementation matches the documented per-workflow isolation guarantee. Update the README/doc comment if owner-level (rather than workflow-level) sharing is instead the intended design.

## Proof of Concept
Existing tests already reproduce the flaw:
- `TestRequestHash/having different workflowID results in same Hash` in `core/services/gateway/handlers/capabilities/v2/response_cache_test.go` (lines 139-149) shows two requests differing only by `WorkflowID` produce an identical hash.
- `TestRequestHash/having different cacheSettings results in the same Hash` (lines 121-137) shows `CacheSettings` differences are likewise ignored.
- An integration-level PoC: submit two `OutboundHTTPRequest` node messages with the same `WorkflowOwner`/method/URL/headers/body but different `WorkflowID` and `CacheSettings.Store=true` on the first; the second request (different workflow) will receive the first workflow's cached response via `responseCache.Fetch`/`Set` in `makeOutgoingRequest` (`http_handler.go` lines 404-442), without any error or workflow-scoping check applied.

func (rc *responseCache) isExpiredOrNotCached(req gateway.OutboundHTTPRequest) bool {
	cachedResp, exists := rc.cache[req.Hash()]

	return false

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
