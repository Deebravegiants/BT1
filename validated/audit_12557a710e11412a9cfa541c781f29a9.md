### Title
`placeOrder()` escrows the pre-fee amount instead of the actual tokens received, breaking accounting for fee-on-transfer tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder()` credits escrow with the user-requested input amount (minus protocol fee) without verifying that the gateway actually received that amount of tokens. For a fee-on-transfer ERC20 input token, the escrow ledger `_orders[commitment][token]` will overstate the gateway's real token balance for that commitment.

### Finding Description
In the non-predispatch branch of `placeOrder`, the contract pulls tokens via `safeTransferFrom` and then unconditionally credits the pre-computed `reducedInputs[i].amount` (derived from the user-supplied `order.inputs[i].amount`, computed *before* any transfer) into escrow — with no balance-before/balance-after check: [1](#0-0) 

This mirrors the exact bug class from the external report (`BufferRouter.initiateTrade()`), where `transferFrom(msg.sender, address(this), totalFee)` is trusted at face value instead of measuring the actual received balance. The reduced amounts (and the `commitment` hash itself) are also computed purely from the requested `order.inputs[i].amount` before the transfer occurs: [2](#0-1) 

Notably, this exact vulnerability class was identified and fixed in the sibling EVM contract `evm/src/apps/IntentGatewayV2.sol`, which snapshots `balanceOf` before/after the transfer and mutates `order.inputs[i].amount` to the actual received amount before computing fees/commitment: [3](#0-2) 

The predispatch branch of the Tron contract is comparatively protected (it reverts via `InvalidInput`/`InsufficientNativeToken` if the swept balance is below `requiredAmount`), but the ordinary direct-transfer branch (lines 450-469) has no such guard and unconditionally trusts `order.inputs[i].amount`.

### Impact Explanation
For any fee-on-transfer (or otherwise lossy) ERC20 configured as an order input token, the gateway's actual token balance backing a given commitment will be less than what `_orders[commitment][token]` records. Since escrow release paths (fill/cancel/refund flows) pay out based on this recorded ledger value rather than actual balance, this creates a shortfall: the gateway becomes insolvent relative to its own accounting. Depending on downstream flow this manifests as reverting cancellations/refunds/fills (temporary freezing) or, when combined with multiple orders sharing the same token, a wider funds-freezing condition where correctly-collateralized orders can no longer be redeemed because the contract's real balance has been depleted by the shortfall from fee-on-transfer orders placed earlier. This is a Medium-severity accounting/fund-freezing bug reachable directly by any unprivileged user calling `placeOrder()`.

### Likelihood Explanation
Triggering this requires only that the deployment supports (or a user selects) a fee-on-transfer ERC20 as an order input token and calls the public, unprivileged `placeOrder()` function — no special permissions or race conditions needed. Likelihood depends on whether fee-on-transfer tokens are permitted as intent inputs on the Tron deployment; the codebase's own test suite (`IntentGatewayV2SameChainTest.sol`) explicitly exercises and fixes this exact scenario for the main EVM contract, confirming it's a recognized, in-scope threat model for this application family.

### Recommendation
Mirror the fix already applied in `evm/src/apps/IntentGatewayV2.sol`: snapshot the gateway's token balance immediately before `safeTransferFrom` and again immediately after, then use the delta (actual received amount) — not the caller-supplied `order.inputs[i].amount` — for computing `reducedInputs`, the `commitment` hash, and the value credited to `_orders[commitment][token]`.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a fee-on-transfer ERC20 (e.g., 1% fee) registered as a valid input token.
2. User calls `placeOrder()` with `order.inputs[0] = {token: FOT, amount: 1000e18}`, approving `1000e18`.
3. `safeTransferFrom(msg.sender, address(this), 1000e18)` executes, but due to the token's transfer fee the gateway only receives `990e18`.
4. `_orders[commitment][FOT]` is nonetheless credited with `reducedInputs[0].amount` computed from the full `1000e18` (minus only protocol fee, if any) — i.e., a value greater than the `990e18` actually held.
5. On cancellation/refund or solver-fill settlement that pays out based on `_orders[commitment][FOT]`, the contract attempts to transfer more `FOT` than its real balance for that commitment permits, reverting the recovery path or draining balance earmarked for other commitments — matching the report's core impact of "the order would not be able to be cancelled due to no enough balance."
