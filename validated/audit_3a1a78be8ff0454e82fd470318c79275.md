### Title
Escrow beneficiary/recipient address is never validated before token transfer in IntentGatewayV2/IntentsBase, permanently freezing escrowed funds - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The `Order.output.beneficiary` (destination fill target) and `order.user` (source-chain refund/settlement target) supplied by the order creator are never checked for `address(0)` or any other non-transferable/blacklisted address before the escrow-release code paths (`_withdraw`/`withdraw`, same-chain cancel, `fillOrder`) attempt to pay them out with `safeTransfer`/low-level `.call`. This is the same class of bug as the referenced report: an unvalidated recipient field that can make token transfers permanently revert, leaving escrowed funds stuck and orders un-fillable/un-cancelable.

### Finding Description
`placeOrder` copies the caller-supplied `order.output.beneficiary` and other order fields into the commitment without any zero-address or validity check: [1](#0-0) 

When the order is later settled — whether via a cross-chain `RedeemEscrow`/`RefundEscrow` message delivered through `onAccept`, or via a same-chain `cancelOrder`/`fillOrder` — the beneficiary bytes are decoded straight into an `address` and used as the transfer target with no validation: [2](#0-1) 

The Tron/EVM sibling implementation of the same flow has the identical pattern in its internal `withdraw()`: [3](#0-2) 

And on the destination-cancel and cross-chain-cancel paths, `order.user` (equally unvalidated at placement) is used directly as the beneficiary field of the `WithdrawalRequest` that eventually triggers the same unguarded transfer: [4](#0-3) [5](#0-4) 

Test fixtures throughout the suite escrow standard ERC20 tokens (e.g. USDC/DAI mocks) as order inputs/outputs, confirming the escrow model is meant to support stablecoin-class tokens whose real-world implementations (USDC/USDT) can revert transfers to blacklisted or frozen addresses: [6](#0-5) 

Because `order.user`/`beneficiary` is set once at `placeOrder` time and baked into the `commitment = keccak256(abi.encode(order))`, there is no way to alter the recipient after the fact — every future call path (fill, cancel-from-source, cancel-from-dest) that must eventually call `_withdraw`/`withdraw` targets the exact same broken address.

### Impact Explanation
If `order.user` (used as the refund/cancel beneficiary) or `order.output.beneficiary` (used as the fill beneficiary) is `address(0)` or a blacklisted address for the escrowed token (USDC/USDT-style transfer restrictions), then:
- `fillOrder`/`RedeemEscrow` handling will always revert on `safeTransfer(beneficiary, ...)`, so the order can never be filled and the solver can never claim payment on a successful cross-chain fill relay.
- `cancelOrder` (same-chain, source-chain, and destination-chain paths) will likewise always revert in `_withdraw`/`withdraw`, so the escrowed input tokens (and the user's fees) can never be recovered.
- Since escrow accounting (`_orders[commitment][token] -= amount`) happens together with the transfer inside the same reverting call, no partial state corruption occurs, but the funds remain permanently locked in the gateway contract with no recovery path — the order is uncancellable and unfillable forever, matching the reported "orders opened but never fully filled or closed, money stuck" impact.

This qualifies as permanent freezing of funds reachable from a single `placeOrder` transaction by any unprivileged user (self-inflicted or griefing another party's relay/fill attempt is not required — the order creator's own submitted transaction is sufficient to lock funds).

### Likelihood Explanation
Likelihood is user-error/edge-case driven rather than attacker-driven: a user or integrating dApp that mis-encodes the beneficiary/user bytes32 (e.g., truncation bug, wrong padding, or targeting a blacklisted/frozen stablecoin address) will trigger this permanently. Given `Order.user`/`beneficiary` are passed as raw `bytes32`→`address` casts sourced from user input (or client-side tooling) with zero on-chain sanity checks anywhere in `placeOrder`, `fillOrder`, or the cancel paths, this is readily triggerable, especially for integrators using automated address derivation across many chains where an off-by-one/encoding bug is plausible.

### Recommendation
Validate `order.output.beneficiary` and `order.user` (and any output/input recipient fields propagated into `WithdrawalRequest.beneficiary`) at `placeOrder` time, rejecting `address(0)` and reserved/sentinel addresses. Where possible, provide a governance/emergency-only recovery path (e.g., a delayed sweep to a fallback address) for orders whose payout target becomes non-transferable after placement (e.g., later blacklisted by a stablecoin issuer), since pre-placement validation cannot protect against retroactive blacklisting.

### Proof of Concept
1. Call `IntentGatewayV2.placeOrder` with `order.output.beneficiary = bytes32(0)` (or an address blacklisted by the output token, e.g. a sanctioned USDC address) and valid `inputs`— this succeeds because no beneficiary validation exists (`evm/src/apps/IntentGatewayV2.sol:194-226`).
2. A solver calls `fillOrder`; on the destination chain, `_withdraw`/`withdraw` attempts `IERC20(token).safeTransfer(beneficiary, amount)` to `address(0)` or the blacklisted address (`evm/src/apps/intentsv2/IntentsBase.sol:451-469`, `evm/tron/contracts/apps/IntentGatewayV2.sol:691-714`) — this reverts every time (ERC20 zero-address/blacklist transfer restrictions), so `fillOrder`/`onAccept` can never succeed.
3. Alternatively, the user calls `cancelOrder`; the same `_withdraw`/`withdraw` call, using `order.user` as beneficiary, reverts identically, so the escrowed input tokens can never be refunded — the funds are permanently stuck in the gateway contract.
