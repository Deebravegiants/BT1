Confirmed: `WebhookMetadata#shop` (used by the app's `WebhookHandler#handle`) is populated directly from `Request#shop`, which reads the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header — a value never included in the HMAC computation.

### Title
Webhook `shop` (tenant) identifier is not covered by the HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body (`to_signable_string` returns `@raw_body`). The `shop` value is never mixed into the signed material, so a request whose body-HMAC is valid can carry an arbitrary, attacker-chosen `shop` value.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by checking `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, request.to_signable_string)` and compares it to the `hmac` header: [1](#0-0) 

`to_signable_string` is defined as just the raw body: [2](#0-1) 

`shop` (and `topic`, `api_version`, `webhook_id`) are read independently from headers with no cryptographic binding to the signed payload: [3](#0-2) 

`Registry.process` then hands `request.shop` straight to the app's handler as the trusted tenant identifier: [4](#0-3) [5](#0-4) 

This breaks the intended identity binding: `HMAC(body)` verifies `body`, but the gem's API implicitly presents `WebhookMetadata#shop` as an authenticated attribute of the same signed request (`hmac_valid(body) == true` is treated as `shop_is_authentic == true`), when in fact `shop ⊄ signed_bytes`.

Since `api_secret_key` is a single, app-wide secret shared across every shop that installs the app (not per-tenant), any merchant who installs the app can capture a legitimately Shopify-signed webhook delivery for their own store (valid `hmac` over a given `raw_body`), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. `HmacValidator.validate` still succeeds because it never inspects `shop`, so the forged request is delivered to the handler as if it originated from the victim tenant.

### Impact Explanation
This is a cross-tenant identity confusion: an app relying on `WebhookMetadata#shop` to select which merchant's session/data/state to mutate (the gem's intended and documented usage pattern) can be tricked into acting on behalf of, or attributing data to, a different shop than the one that actually sent the payload. This matches the "Critical — cross-tenant access" impact bucket, since the boundary crossed is the per-shop authentication guarantee that the HMAC check is supposed to provide.

### Likelihood Explanation
Exploitation only requires the attacker to be a legitimate, unprivileged installer of the target app on their own store (no access token, no `client_secret`, no privileged account needed) — they trigger any webhook on their own shop, capture the resulting `(raw_body, hmac)` pair (which they receive directly, since it's delivered to their own configured endpoint or can be inspected via their own infrastructure), and replay it with a modified `shop` header at the app's public webhook endpoint.

### Recommendation
Bind the tenant identity to the signed material: include the `shop` domain (and ideally `topic`/`webhook_id`) inside the HMAC-signed payload, or independently verify `request.shop` against a shop that is already known to be installed for this specific webhook subscription/topic (e.g. compare against the shop stored for that `webhook_id`/subscription instead of trusting the header). At minimum, document that `Request#shop` is unauthenticated and must not be used as a tenant selector without an out-of-band binding.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook whose body content is generic/attacker-controllable enough to be reused (e.g. an event with an empty or attacker-supplied body), and captures the resulting `x-shopify-hmac-sha256` header and raw body from the delivered request.
3. Attacker POSTs the identical `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb` lines 12-22) recomputes the HMAC over `raw_body` only and it matches, so `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-199) proceeds and calls the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload never originated from that shop.
