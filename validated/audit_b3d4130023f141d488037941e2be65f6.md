### Title
Missing sender/source validation before processing `RequestState` retransmission requests bypasses the relay's src-check trust boundary - (File: orb-relay-client/src/client.rs)

### Summary
`PollerAgent::main_loop` in `orb-relay-client/src/client.rs` validates that an incoming relay message's `src.id` matches the expected `dst_id` before it is handed to `handle_message` (the untrusted-peer/trust-boundary check). However, one specific message type, `self_serve::app::v1::RequestState`, is matched and acted upon *before* that source check is performed, so the source validation is completely bypassed for this message type — directly analogous to the ENS `OffchainDNSResolver` bug where a nested/forwarded call's result is trusted without verifying the "sender" actually matches the expected caller.

### Finding Description
In the relay client's `main_loop`, incoming `RelayPayload` messages are supposed to be checked against the expected peer id before any action is taken: [1](#0-0) 

The code is:
```
if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: ...");
} else {
    self.handle_message(...).await?;
}
```
The `RequestState` branch is evaluated first, unconditionally on `src.id`. This means that any relay message decodable as `self_serve::app::v1::RequestState` will trigger a resend of `self.last_message` (the orb's last-sent state, which for an Orb client is signup/session-state data such as `AnnounceOrbId`, `CaptureStarted`, `SignupEnded`, etc.) regardless of whether it actually originated from the paired peer (`self.config.dst_id`). This is the same class of bug as the ENS finding: a nested/forwarded interaction (`self_serve::app::v1::RequestState::matches`) is trusted and acted upon without verifying the "sender" field against the expected callee/peer, which the specification (here, the relay's own subsequent `else if src.id != self.config.dst_id` check) clearly establishes as mandatory for every other message type.

The relay server multiplexes messages for a given client id and forwards `RelayPayload`s with `src` set to the actual originator; the client only enforces the peer-id check in the `else if` branch, not universally. Any entity able to make the relay deliver a `RequestState`-shaped payload to this client channel (e.g., a session, another connected peer scoped by the relay server, or a peer id mismatch/race during reconnect/session reuse) can force the orb (or app) to retransmit its last state message without being the legitimate paired party.

### Impact Explanation
This breaks the trust boundary the code itself establishes just one branch later (`src.id != self.config.dst_id`). Practically, it allows an unauthorized/unpaired relay peer to force retransmission of the orb's last outgoing state message (which can include ids/session data used to drive the self-serve signup flow, e.g. `SignupEnded`, `CaptureStarted`, `AnnounceOrbId`). Because the orb-relay channel underlies self-serve signup flows (`src/plans/mod.rs::orb_relay_announce_orb_id`, `do_signup`), an attacker who can trigger this unauthenticated resend could confuse app/orb session state association or trigger cross-session state bleed. This lines up with the "cross-signup state bleed" impact category since the retransmitted `last_message` is not scoped/re-verified against the actual requesting peer's identity.

### Likelihood Explanation
The `RequestState` message type exists specifically for a peer to ask the other side to resend its state; the relay server is the party that stamps `src`, but the client's code shows the developers considered `src.id` validation necessary for all other messages (evidenced by the explicit `else if` check) — the omission for `RequestState` is a straightforward, reachable branch-ordering bug, not a deep protocol flaw. Any party capable of causing the relay to deliver a `RequestState`-typed `RelayPayload` to the target queue (which is the express purpose of the message) triggers this without needing to pass the sender check that guards every other payload type.

### Recommendation
Move the `src.id != self.config.dst_id` check to occur before dispatching on the message type, so it applies uniformly (mirroring the EIP-3668-style recommendation of validating the sender before acting on any nested/derived response):
```rust
if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: {:?}: {payload:?}", src.id);
} else if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await.wrap_err(...)?;
} else {
    self.handle_message(...).await?;
}
```

### Proof of Concept
1. A relay peer (or any entity able to have the relay backend forward a `RelayPayload` into the target client's message queue) sends a payload matching `self_serve::app::v1::RequestState` with an arbitrary/mismatched `src.id`. [2](#0-1) 
2. In `main_loop`, the `RequestState::matches(&payload).is_some()` branch is taken immediately, bypassing the `src.id != self.config.dst_id` check that governs every other payload type. [3](#0-2) 
3. `self.last_message` (the previously sent state payload, e.g., `SignupEnded`/`CaptureStarted`/`AnnounceOrbId` used by the self-serve signup plan) is resent over `sender_tx` to the relay, without validating that the request truly came from the paired `dst_id`. [4](#0-3) 

Note: I could not fully trace how the relay backend server assigns/validates `src` on the wire (that server code is out of scope/not present in this repo), so the exact conditions under which an attacker-controlled `src.id` reaches this client for a `RequestState` payload are based on the client-side code alone; server-side authorization on the relay might partially mitigate this, but the client itself provides no defense-in-depth for this specific message type.
