**Analysis:**

The claim misunderstands how gas budgeting is enforced. `legacy_gas_used` in `SafeNativeContext` is a per-native-call staging value, but it is not the mechanism that enforces the transaction's overall gas budget. [1](#0-0)  After a native returns, the interpreter always forwards the reported cost to the persistent, transaction-scoped gas meter via `gas_meter.charge_native_function(cost, ...)`, for every `NativeResult` variant (`Success`, `Abort`, `OutOfGas`, `CallFunction`): [2](#0-1)  and again for `CallFunction` (the dispatch path used by dispatchable FA hooks): [3](#0-2) .

This `gas_meter` is the real `AptosGasMeter`, which persists for the whole transaction and tracks a single cumulative balance — it is not reset per native call or per `SafeNativeContext` instance. So no matter how an attacker fragments work across many small native invocations, every fragment's cost is summed against the same transaction-level budget the moment each native returns. Splitting one logical operation into more, smaller native calls does not let any cost escape accounting; it only changes how many times `charge_native_function` is invoked, not the total amount subtracted from the real balance.

The `legacy_gas_used`/`legacy_enable_incremental_gas_charging` path in `SafeNativeContext::charge` [4](#0-3)  only exists for gas-feature versions below `RELEASE_V1_32`, as a way to let a *single* native pre-emptively bail out mid-execution once it exceeds the transaction's remaining budget (queried via `legacy_gas_budget()`), before doing further unmetered work inside that one call. It is a local convenience for early-exit inside one native, not an independent budget — the real enforcement always happens afterward via `charge_native_function` against the persistent meter. For `gas_feature_version >= RELEASE_V1_32`, natives skip this legacy accumulator entirely and charge the live gas meter directly with `charge_native_execution`, so there's no accumulator to reset at all: [5](#0-4) .

Separately, the FA hook-registration path (`register_dispatch_functions`) itself does the signature-compatibility check and one-time `assert!(!exists<DispatchFunctionStore>...)` guard in Move code, and its only native call (`function_info::load_module_from_function` → `native_load_function_impl`) charges a flat base cost plus real dependency gas, again subject to the same persistent gas meter: [6](#0-5) , [7](#0-6) . There is no path by which fragmenting calls lets the total transaction gas cost of establishing a dispatch hook stay under the intended amount, nor does this affect any custody boundary (controller, holder, or authority state) — it is purely a gas-accounting question, and the accounting is correctly enforced at the persistent VM gas-meter level regardless of call fragmentation.

    pub fn charge(
        &mut self,
        abstract_amount: impl GasExpression<NativeGasParameters, Unit = InternalGasUnit>,
    ) -> SafeNativeResult<()> {
        let amount = abstract_amount.evaluate(self.gas_feature_version, self.native_gas_params);

        if let Some(hook) = self.gas_hook {
            let node = abstract_amount.to_dynamic();
            hook(node);
        }

        if self.has_direct_gas_meter_access_in_native_context() {
            self.gas_meter()
                .charge_native_execution(amount)
                .map_err(LimitExceededError::from_err)?;
            Ok(())
        } else {
            self.legacy_gas_used += amount;
            if self.legacy_gas_used > self.legacy_gas_budget()
                && self.legacy_enable_incremental_gas_charging
            {
                Err(SafeNativeError::LimitExceeded(
                    LimitExceededError::LegacyOutOfGas,
                ))
            } else {
                Ok(())
            }
        }
    }
