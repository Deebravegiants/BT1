### Title
Permanent freezing of pool funds via unrecoverable `CalcPnlError` in `calc_take_pnl` blocking Deposit/Withdraw/WithdrawPnl - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` enforces an invariant comparing current pool reserves against the previously-recorded `TargetOrders.calc_pnl_x`/`calc_pnl_y` values, and returns a hard `AmmError::CalcPnlError` if the check fails. This function is called unconditionally on the `Deposit`, `Withdraw` (unless status is `WithdrawOnly`), and `WithdrawPnl` code paths, so if the invariant is ever violated, all three of the pool's normal fund-movement instructions become permanently unusable for every LP, with no permissionless recovery path — structurally analogous to the Akutars incident where multiple accounting inconsistencies made the auction contract's withdrawal path permanently unusable and funds got locked.

### Finding Description
`calc_take_pnl` restores `target.calc_pnl_x`/`calc_pnl_y` (normalized "last-observed" reserve values) back to real token units and checks: [1](#0-0) 

If `pool_pc_amount * pool_coin_amount < calc_pc_amount * calc_coin_amount`, the function returns `Err(AmmError::CalcPnlError)` unconditionally: [2](#0-1) 

This function is invoked with `?` (i.e., any error aborts the whole instruction) from three separate entry points reachable by unprivileged actors:
- `process_deposit`, on every LP deposit: [3](#0-2) 
- `process_withdraw`, on every LP withdrawal, unless the pool's admin-controlled status is already `WithdrawOnly`: [4](#0-3) 
- `process_withdrawpnl`, the protocol PNL sweep: [5](#0-4) 

`target.calc_pnl_x`/`calc_pnl_y` are maintained across the lifetime of the pool by repeated `checked_sub`/`checked_mul`/`checked_div`/`integer_sqrt` arithmetic on `U128`/`U256` values derived from `Calculator::normalize_decimal_v2` and `restore_decimal` (decimal-normalization helpers), e.g. in `process_withdraw`: [6](#0-5) 

Because `x1`/`y1` (current normalized reserves) and `calc_pnl_x`/`calc_pnl_y` (last-observed baseline) are updated via independent rounding/truncating operations (`RoundDirection::Floor`/`Ceiling`, `integer_sqrt`, `restore_decimal`) on every deposit/withdraw/swap, the two quantities can drift apart over the life of a pool. Once `calc_pnl_x * calc_pnl_y` (the recorded baseline) exceeds the actual `pool_pc_amount * pool_coin_amount` (the real current reserves) by even a small margin, `calc_take_pnl` permanently returns `CalcPnlError` on every future call, since nothing in the instruction set decrements `calc_pnl_x`/`calc_pnl_y` independently of this same check.

The only bypass is for `process_withdraw` when `amm.status == AmmStatus::WithdrawOnly`, which is a status settable only via the admin-gated `SetParams` instruction — not reachable by an ordinary LP or swapper. `process_deposit` and `process_withdrawpnl` have no such bypass at all, so deposits (and pool "close-out" PNL withdrawal) can never recover once tripped, and withdrawals can only be recovered by trusting the pool admin to flip the status — an out-of-band, permissioned action outside of user control.

### Impact Explanation
If the invariant is violated (through accumulated rounding drift across many legitimate deposit/withdraw/swap operations — no admin or attacker action required to reach this state, only ordinary pool usage over time), every subsequent `Deposit` and `WithdrawPnl` transaction reverts, and `Withdraw` also reverts for as long as the pool remains in a normal trading status. All LP principal and any un-swept PNL held in the coin/pc vaults becomes locked in place: LPs cannot exit their position, and the protocol cannot sweep PNL, mirroring the Akutars scenario where a defect in the withdrawal accounting path permanently froze the auction's ETH. Recovery is not permissionless; it depends on the admin explicitly setting the pool to `WithdrawOnly` via `SetParams`, and even then only unblocks `Withdraw`, not `Deposit`/`WithdrawPnl`.

### Likelihood Explanation
Triggering requires numerical drift between `calc_pnl_x`/`calc_pnl_y` and the real vault balances to accumulate to the point the strict inequality flips — this is a function of many rounding-lossy operations (floor/ceiling divisions, integer square roots, decimal restoration) accumulating over the pool's operational lifetime rather than a single crafted transaction. I could not conclusively demonstrate, within the scope of this review, an attacker-controlled single-transaction sequence that flips the inequality deterministically; establishing that would require detailed numerical/differential analysis of `Calculator::normalize_decimal_v2`, `restore_decimal`, and `calc_x_power` under adversarial decimal/mint configurations (e.g., pools created with mismatched coin/pc decimals via `Initialize2`), which was not fully verified here. This should be treated as a plausible but not fully proven root cause; likelihood is assessed as low-to-medium absent a concrete numeric PoC.

### Recommendation
- Add a recovery/reconciliation path (permissionless or admin-gated) that resynchronizes `calc_pnl_x`/`calc_pnl_y` to the actual current vault reserves when `CalcPnlError` is hit, rather than permanently hard-failing every future call.
- Apply the same `WithdrawOnly`-style bypass (or an explicit "skip pnl" flag) uniformly across `process_deposit`, `process_withdraw`, and `process_withdrawpnl`, so a stuck PNL invariant cannot block deposits or the PNL sweep as well as withdrawals.
- Replace the strict inequality panic/hard-error with a saturating/clamping recomputation of `calc_pnl_x`/`calc_pnl_y` bounded by actual reserves, eliminating the possibility of an unrecoverable state purely from rounding drift.
- Add fuzz/property tests that repeatedly deposit/withdraw/swap at varying decimal configurations to confirm `calc_pnl_x * calc_pnl_y` never exceeds actual reserves over long operational sequences.

### Proof of Concept
A concrete deterministic single-transaction PoC was not established. The theoretical trigger path is:
1. Create a pool via `Initialize2` (attacker-chosen coin/pc mints with differing decimals is allowed): [7](#0-6) 
2. Repeatedly call `Deposit`/`Withdraw`/`SwapBaseIn`/`SwapBaseOut` with amounts chosen to maximize rounding loss in `Calculator::normalize_decimal_v2`/`restore_decimal` on each call, gradually increasing the gap between `target.calc_pnl_x * calc_pnl_y` and true reserves.
3. Once `pool_pc_amount * pool_coin_amount < calc_pc_amount * calc_coin_amount`, any subsequent `Deposit`, `WithdrawPnl`, or `Withdraw` (while not `WithdrawOnly`) reverts via `AmmError::CalcPnlError` at [2](#0-1) , freezing the pool's funds absent admin intervention.

Because step 2's exact numeric feasibility was not verified against `Calculator`'s decimal-normalization math (`program/src/math.rs`, not fully reviewed here), this finding is reported with the above caveat rather than a fully executable exploit script.
