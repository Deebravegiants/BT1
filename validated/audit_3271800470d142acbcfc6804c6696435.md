## Finding

### Title
Webhook HMAC only signs the raw body, not the `shop-domain` header, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers and are never included in the HMAC-signed material. `Registry.process` verifies the HMAC and then trusts `request.shop` as the tenant identity for the handler call, breaking the equality `shop covered by HMAC == shop the handler acts on`.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) [2](#0-1) [3](#0-2) 

`to_signable_string` returns `@raw_body` only, while `shop` and `topic` are parsed straight from the `shopify-shop-domain`/`shopify-topic` (or `x-shopify-*`) HTTP headers, with no cryptographic binding between those header values and the HMAC.

`Registry.process` validates the HMAC and then immediately forwards `request.shop` (and `request.topic`) to the handler as trusted tenant metadata: [4](#0-3) 

`Utils::HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string` and compares it with `OpenSSL.secure_compare`: [5](#0-4) 

Because the signed material is only the JSON body, an HMAC computed for a webhook delivered to shop A's raw body remains valid for the *exact same raw body* attached to a spoofed `x-shopify-shop-domain` (and/or `x-shopify-topic`) header identifying shop B. The identity binding broken is: **the `shop` field acted on by `Registry.process`/the handler is not covered by the HMAC that "authenticates" the webhook request.**

### Impact Explanation
An attacker who legitimately receives one valid webhook for their own store (e.g., by triggering `orders/create` in their own shop, which any merchant can do) obtains a raw body + valid HMAC pair. They can replay that same body to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` still passes because it only checks the body, and `Registry.process` calls the handler with `shop: request.shop` set to the attacker-chosen victim domain. Any downstream business logic keyed by `shop` (e.g. provisioning, order records, billing state, session lookups) is executed as if the data originated from the victim tenant — a cross-tenant data injection/spoofing condition.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to have a shop of their own (trivial to obtain) capable of generating at least one legitimately-signed webhook body of a topic that also makes sense for the victim tenant, plus generic HTTP access to the app's registered webhook endpoint. No secrets, tokens, or privileged access are required — only observation of one's own outbound webhook traffic.

### Recommendation
Include the shop domain (and preferably topic/webhook-id/api-version) headers in the signable string used for HMAC verification, or otherwise cryptographically bind them to the payload before trusting `request.shop` in `Registry.process`. At minimum, document that host applications must additionally validate that `request.shop` corresponds to a shop with an active, known installation/session before acting on webhook data, since the current HMAC scheme (matching Shopify's actual wire protocol) only proves body integrity, not header/tenant integrity.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) so the app's endpoint receives:
   - `raw_body = "{...attacker order json...}"`
   - `x-shopify-hmac-sha256 = HMAC(secret, raw_body)`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
2. Attacker replays the identical `raw_body` and `x-shopify-hmac-sha256` to the same endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` builds a request object where `hmac` and `to_signable_string` are unaffected by the header change (`to_signable_string` is only `@raw_body`).
4. `Utils::HmacValidator.validate` returns `true` because the body-only signature still matches.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker's JSON>, ...)`, i.e., attacker-controlled data is processed under the victim's tenant identity.
