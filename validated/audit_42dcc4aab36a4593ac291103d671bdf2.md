### Title
Governance update to `Precisions` mid-flight desynchronizes `send`/`on_accept` amount conversion in `pallet-hyper-fungible-token`, causing forged/incorrect mint amounts or permanent freezing of bridged funds - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`, `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token::send` converts the user's locally-denominated `amount` into the ERC20-denominated wire amount using the live value of `Precisions::<T>::get(asset_id, destination)` at dispatch time [1](#0-0) . The corresponding `on_accept` handler on the receiving side converts the wire amount back into local denomination using the live value of `Precisions::<T>::get(local_asset_id, source)` at delivery time [2](#0-1) . If governance calls `update_asset_precision` between the time a message is dispatched and the time it is delivered (or times out), the conversion rate used to encode the burn/lock amount no longer matches the rate used to decode the mint/unlock amount, exactly mirroring the `GOVERNANCE_TOKENS_PER_NFT` change window in the reference report.

### Finding Description
`send` computes `erc20_amount = convert_to_erc20(amount, erc_decimals, decimals)` where `erc_decimals` is read from `Precisions` for the *destination* chain at send time, and burns/locks `amount` in local denomination immediately [3](#0-2) . This value is baked into the outgoing `Message.amount` and dispatched as an ISMP POST request; there is no re-validation of the precision at delivery.

On the receiving chain, `on_accept` independently re-reads `Precisions` (this time keyed by `source`) at the moment the relayed message is executed, and uses whatever value is currently stored to convert the ERC20 amount back to local balance via `convert_to_balance` before minting/unlocking [4](#0-3) .

Because ISMP messages can be in flight for extended periods (finalization + relayer delay + timeout window), any governance-driven `update_asset_precision` call that lands between `send` and `on_accept`/timeout execution changes the decode-side conversion factor without touching the amount already locked/burned on the source side. This is structurally identical to `ApiologyDAOToken.changeGovTokensPerNFT` altering `GOVERNANCE_TOKENS_PER_NFT` after tokens were already minted under a different rate — a single governance-privileged parameter is read live on both sides of a two-phase, time-separated operation, with no snapshotting of the rate used for the in-flight amount.

### Impact Explanation
- If precision is decreased on the destination side after dispatch (fewer decimals expected), `convert_to_balance` will scale the amount up, minting/unlocking more local tokens than were actually locked/burned on the source — an unbacked mint / permanent value leak from the pallet's custody account.
- If precision is increased, the destination mints/unlocks less than the source actually escrowed, permanently freezing the difference in the pallet's custody account (unrecoverable, since the burn/lock already succeeded and cannot be "re-priced").
- Either direction breaks the 1:1 backing invariant documented for `native: true` assets, and for `native: false` assets it breaks the burn-then-mint supply parity across chains, both of which are direct, concrete impacts to funds.

### Likelihood Explanation
Governance-configurable precision changes are an explicit code path (`update_asset_precision`), and the documentation notes precision updates only guard against "failed transfers" — not against outstanding in-flight messages [5](#0-4) . Any window where a transfer is dispatched but not yet delivered (normal cross-chain finalization latency, or messages awaiting timeout) is exploitable by a governance-triggered precision change; this requires only routine ISMP message latency, not any additional adversarial timing beyond what is already achievable by an unprivileged user submitting `send` shortly before a scheduled precision update.

### Recommendation
Snapshot the resolved decimals/precision pair into the outgoing `Message` (or into per-commitment storage) at `send` time, and have `on_accept` use the snapshotted value rather than re-reading the live `Precisions` map. Alternatively, reject `update_asset_precision` while there are unsettled in-flight requests for the affected `(asset_id, chain)` pair, or require an explicit migration/reconciliation step so previously escrowed balances are settled under their original rate before the new rate takes effect.

### Proof of Concept
1. Governance registers asset `X` with `Precisions[X][DestChain] = 18` and `Precisions[X][SourceChain] = 18`.
2. User calls `send(asset_id=X, destination=DestChain, amount=1000)` on the source chain; the pallet burns/locks `1000` locally and dispatches `Message.amount = convert_to_erc20(1000, 18, decimals_src)` [6](#0-5) .
3. Before the ISMP message is relayed/finalized, governance calls `update_asset_precision` changing `Precisions[X][SourceChain]` (read by `on_accept` as `source`) from `18` to `6`.
4. The relayer delivers the message; `on_accept` computes `amount = convert_to_balance(message.amount, erc_decimals=6, decimals)`, which — due to the decimals mismatch versus what was actually encoded — mints/unlocks an amount inconsistent with the `1000` originally escrowed, either over-minting (unbacked funds) or under-minting (funds permanently stuck in the pallet's custody account) [7](#0-6) .

## Updating Asset Precision

Asset precision records the number of decimal places an asset uses on a remote chain. This allows the pallet to handle balance conversions correctly when transferring between chains with different decimal configurations (e.g. 10-decimal DOT on Polkadot vs 18-decimal DOT on Ethereum).
