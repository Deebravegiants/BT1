Based on my investigation, I found a genuine identity-binding gap in the webhook processing flow.

### Title
Webhook `shop` (and `topic`, `webhook-id`, `api-version`) header values are trusted without being covered by the HMAC signature, enabling cross-tenant data attribution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC only over the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and passed on to the app's webhook handler as trusted metadata.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and the HMAC digest is computed over that raw body alone: [1](#0-0) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` and, if valid, immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all sourced from headers — to build `WebhookMetadata` passed to the app's handler: [2](#0-1) 

The binding the library implicitly claims to enforce is:
`hmac_valid(raw_body) == true` implies `shop header == the shop that actually generated raw_body`

That equality does not hold, because `shop`, `topic`, `webhook_id`, and `api_version` are never included in `to_signable_string`. Any request whose body byte-for-byte matches a previously (or currently) validly-signed payload — trivially achievable since an attacker can register their own free Shopify development store, install the app, and trigger any webhook topic to obtain a body + valid `hmac` pair signed with the app's shared `client_secret` — can be replayed to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header. `Utils::HmacValidator.validate` will still pass because it only checks the raw body bytes: [3](#0-2) 

The host application's handler receives `WebhookMetadata` believing `shop` is authentic (it is the field host apps typically use to look up the correct merchant session/access token), but that field crossed the trust boundary unauthenticated.

### Impact Explanation
This breaks the identity binding between the HMAC-authenticated payload and the tenant (`shop`) it is attributed to. A host application that uses `WebhookMetadata#shop` to select which merchant's session/data to update (the intended and documented use per `docs/usage/webhooks.md`) can be made to apply attacker-supplied-topic data under a victim shop's identity — a cross-tenant integrity issue. Because `topic` is also unauthenticated, an attacker can additionally choose which registered handler processes the forged body, potentially triggering sensitive handlers (e.g., `customers/redact`, `shop/redact`) for a victim shop using attacker-controlled body content.

### Likelihood Explanation
Exploitation only requires the capability of any unprivileged internet user: creating a Shopify development/partner store and installing the target public app to legitimately trigger one webhook delivery, capturing the raw body and its valid `hmac-sha256` header, then re-sending that exact body/HMAC pair to the app's public webhook endpoint with modified `shop-domain`/`topic` headers. No access token, `client_secret`, or privileged account is required — the `client_secret` used to compute the HMAC is only ever presented as a hash the attacker can generate legitimately with their own store's traffic.

### Recommendation
Include the trust-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed payload used by `to_signable_string`, or otherwise cryptographically bind them to the body (e.g., verify shop domain matches an expected/registered value tied to the session used to fetch the webhook, and mix header values into the signable string) so that `Utils::HmacValidator.validate` cannot succeed unless the full metadata tuple — not just the body — matches what Shopify actually signed.

### Proof of Concept
1. Attacker creates a free Shopify partner/dev store `attacker.myshopify.com` and installs the target public app.
2. Attacker triggers webhook topic `orders/create` (or any registered topic) on their own store, causing Shopify to POST to the app's webhook endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(client_secret, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures `B` and `H` from their own delivery logs/inbound proxy.
4. Attacker resends the exact same `B` and `H` to the same public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request#hmac` decodes `H` and `Utils::HmacValidator.validate` succeeds because it only recomputes the HMAC over `B` [4](#0-3) , while `request.shop` now reports `victim.myshopify.com` [5](#0-4) , and `Registry.process` calls the registered handler for that topic with `WebhookMetadata` claiming the (forged) body belongs to `victim.myshopify.com` [6](#0-5) .

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
