### Title
Webhook tenant identity (`shop`, `topic`) is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, then hands the merchant-identifying `shop` and `topic` values — which are read from unauthenticated HTTP headers — to the app's handler. Because the shared app `client_secret` used to compute the HMAC is the same across every shop that installs the app, any unprivileged user who installs the app on their own store (a fully legitimate, unprivileged action) receives real, validly-signed webhook deliveries. They can then replay that exact body/HMAC pair to the app's public webhook endpoint while forging the `shop-domain` header to name a victim shop, and the signature will still validate, since the signature never covered the shop or topic in the first place.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` (the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as full authentication of the whole request, then forwards the unauthenticated `request.shop` (and `request.topic`) straight into `WebhookMetadata`, which is the value app code uses to determine which tenant/merchant record the payload belongs to: [4](#0-3) 

This is the exact bug class from the external report: a field that is *acted on* (here, the tenant-identifying `shop`) is not covered by the integrity check (`HMAC` over body only) that is used to authenticate the whole message, so the two can be desynchronized by an attacker. In the report, `balanceOf(to)` was read before the mutating effect of the same call, decoupling the check from the actual post-state. Here, `request.shop` is read from a channel (headers) entirely outside of what the HMAC binds, decoupling "whose secret signed this" from "which tenant this claims to be for."

The equality that should hold but doesn't: `shop_that_signed_the_hmac_relevant_bytes == shop_the_app_will_attribute_this_webhook_to`. Before the attack, both are the attacker's own shop. After forging the header, the left side is still (implicitly) the attacker's shop (since the client_secret is shared across all installs), but the right side (`request.shop`, i.e., `WebhookMetadata#shop`) is now the victim's shop domain.

### Impact Explanation
This crosses the tenant boundary this gem is responsible for enforcing on behalf of the host app: `ShopifyAPI::Webhooks::Registry.process` is the gem's public API for asserting "this payload was authentically delivered for shop X." Since `shop` isn't authenticated, an attacker who legitimately installs the app on their own store can make the app process attacker-controlled webhook bodies as if they belong to any other merchant, leading to cross-tenant data corruption/injection (e.g., poisoning another merchant's cached order/product/customer data, or triggering mandatory-compliance handlers like `customers/redact` against an arbitrary shop). This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that exposes its webhook endpoint publicly (as required by Shopify) and trusts `WebhookMetadata#shop`/`#topic` from `Registry.process` to select the tenant record to act on — this is the documented, intended usage of the API. The only prerequisite is installing the app once on an attacker-owned store, which is available to any unprivileged internet user, not a privileged account or leaked secret.

### Recommendation
Bind `shop` (and ideally `topic`, `api_version`, `webhook_id`) into the signed material, or otherwise cryptographically tie the header-derived identity to the payload before trusting it. Since Shopify's wire format doesn't naturally support this, the gem should not present `shop`/`topic` as a byproduct of a "validated" HMAC-checked request without cautioning callers, and/or should document/verify that the header-derived shop is independently confirmed against a stored session for the topic before use, rather than being handed to `WebhookMetadata` as a trusted value once `Utils::HmacValidator.validate(request)` returns `true`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a real webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker replays the exact same `B` and `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. In `ShopifyAPI::Webhooks::Registry.process`, `Utils::HmacValidator.validate(request)` succeeds because it only hashes `@raw_body` (`B`), which is unchanged: [5](#0-4) 
4. `WebhookMetadata` is built with `shop: request.shop` == `"victim.myshopify.com"`, even though the payload never originated from Shopify on behalf of that shop: [6](#0-5) 
5. The app's registered handler processes attacker-controlled data as belonging to `victim.myshopify.com`.
