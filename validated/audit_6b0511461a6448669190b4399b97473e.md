### Title
Batched same-asset withdrawals to different destinations are misattributed by `findMatchingWithdrawal` matching only on `assetId` - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` resolves each withdrawal's on-chain status via `findMatchingWithdrawal`, which selects a PoA API entry purely by `nep141:${w.data.near_token_id} === assetId`, with no disambiguation by destination address, amount, or index. When `signAndSendWithdrawalIntent`/`waitForWithdrawalCompletion` is used in batch mode (`WithdrawalParams[]`) with two withdrawals of the same `assetId` but different `destinationAddress`, both watcher calls converge on the same status entry and report an identical `txHash`/status for both indices even though they pay different recipients.

### Finding Description
The broken equality: `describeWithdrawal({index: 0, ...}).txHash` should equal the destination tx hash for withdrawal 0's specific payout to `destinationAddress_0`, and similarly for index 1 with `destinationAddress_1`. Because `findMatchingWithdrawal` only checks `w.data.near_token_id` against `assetId` [1](#0-0) , both indices resolve to the same first-matching withdrawal entry, so `describeWithdrawal` returns the same `{status, txHash}` for both, regardless of destination. The code comment explicitly acknowledges this: "multiple withdrawals of the same token in a single transaction are not supported" [2](#0-1) .

Nothing upstream prevents this input: `signAndSendWithdrawalIntent` in batch mode simply builds intents per `WithdrawalParams` entry with no duplicate-`assetId` check [3](#0-2) , and `createWithdrawalIdentifiers`/`findBridgeForWithdrawal` only assign a per-bridge-route sequential `index` used for `WithdrawalIdentifier.index`, which is never consulted by `findMatchingWithdrawal` [4](#0-3) . `watchWithdrawal` polls `describeWithdrawal` per `WithdrawalIdentifier` independently for each index [5](#0-4) , so both indices' polls hit the identical mismatch. The identical bug exists independently in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`'s own `findMatchingWithdrawal` [6](#0-5) .

### Impact Explanation
An integrator relying on `sdk.waitForWithdrawalCompletion`/`sdk.processWithdrawal` for a batch containing two same-`assetId` withdrawals to different addresses will receive the same `txHash` and completion status for both array indices. This can cause the integrator to mark/credit both recipients as paid using one recipient's actual destination tx hash, or refund/credit the wrong recipient based on a misattributed hash — matching the "status or hash misreport making an integrator credit or refund twice" High-severity category. This is repeatable on every such batch call as long as the PoA API returns entries for the shared token.

### Likelihood Explanation
Precondition: the caller (any integrator forwarding attacker-controlled `destinationAddress`, or an attacker directly using the SDK) must submit a batch of ≥2 `WithdrawalParams` sharing the same PoA-bridge `assetId` but different `destinationAddress`. This is a normal, unprivileged, publicly reachable SDK usage pattern (no documented restriction against it), costs nothing extra beyond the withdrawal itself, and is deterministically reproducible every time such a batch is submitted through PoA bridge assets.

### Recommendation
Extend `findMatchingWithdrawal` (in both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) to disambiguate among multiple same-asset withdrawals — e.g., match/consume entries by `(assetId, destinationAddress, amount)` combined, track already-consumed entries so repeated calls don't reuse the same entry across indices, or fail fast at `createWithdrawalIntents`/`signAndSendWithdrawalIntent` time by rejecting batches with duplicate `assetId` values that route to the PoA bridge until upstream API support for disambiguation exists.

### Proof of Concept
Vitest plan (mocks only `poaBridge.httpClient.getWithdrawalStatus`):
1. Construct `withdrawalParamsArray = [{assetId: "nep141:btc.omft.near", amount: 100000n, destinationAddress: "addrA", feeInclusive: false}, {assetId: "nep141:btc.omft.near", amount: 200000n, destinationAddress: "addrB", feeInclusive: false}]`.
2. Mock `poaBridge.httpClient.getWithdrawalStatus` to resolve `{ withdrawals: [{ status: "COMPLETED", data: { tx_hash: "near-tx", transfer_tx_hash: "dest-tx-for-addrA", near_token_id: "btc.omft.near", chain: "btc", address: "addrA", amount: 100000, ... } }] }` (only one entry present, corresponding to withdrawal for `addrA`).
3. Call `bridge.describeWithdrawal({ landingChain: Chains.Bitcoin, index: 0, withdrawalParams: withdrawalParamsArray[0], tx })` and `bridge.describeWithdrawal({ landingChain: Chains.Bitcoin, index: 1, withdrawalParams: withdrawalParamsArray[1], tx })`.
4. Assert both calls return `{ status: "completed", txHash: "dest-tx-for-addrA" }` — i.e., `result[1].txHash === result[0].txHash` even though `withdrawalParamsArray[1].destinationAddress !== withdrawalParamsArray[0].destinationAddress`, proving the equality "txHash reported for withdrawal i == outcome specific to withdrawal i" is broken.

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
