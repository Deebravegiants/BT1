Timing-unsafe comparison of OAuth `state` nonce enables session-fixation / forced OAuth completion - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` compares the anti-CSRF `state` nonce (stored server-side in the app's session cookie) against the `state` query parameter returned by Shopify using Ruby's built-in `==` operator, rather than a constant-time comparison. This is the same bug class as the reported JSON-RPC vulnerability: a security-critical secret is checked with a variable-time string comparison, allowing an attacker with the ability to time repeated requests to recover the nonce character-by-character and force/hijack the OAuth callback flow.

### Finding Description
`begin_auth` generates a random nonce and stores it both in a `SessionCookie` (sent to the browser) and in the `state` query parameter of the Shopify authorize URL: [1](#0-0) 

When the callback is processed, `validate_auth_callback` reads the cookie value back out and compares it to the `state` field of the (unauthenticated, attacker-suppliable) `AuthQuery` object using plain `==`: [2](#0-1) 

This is a binding check: `cookie.state == auth_query.state` is meant to prove that the party completing the callback is the same party that started the flow. Ruby's default `String#==` performs length and byte-wise short-circuiting comparison (analogous to V8's `String::SlowEquals` described in the reported vulnerability), so the number of correctly-guessed leading characters affects response time.

Critically, this codebase already demonstrates the correct fix pattern elsewhere: `Utils::HmacValidator` uses `OpenSSL.secure_compare` specifically to avoid this exact class of timing leak when checking the OAuth HMAC signature: [3](#0-2) 

The `state` check in `oauth.rb` was not given the same treatment, leaving an inconsistency: one secret-equality check in the OAuth flow is timing-safe, the other (immediately adjacent, in the same method) is not.

### Impact Explanation
The `state` nonce is the CSRF/session-fixation protection for the OAuth authorization-code flow. If an attacker can repeatedly invoke the callback endpoint against a target session (e.g., co-located/network-adjacent to the victim or app server, per the same threat model as the original report) while varying the `state` query parameter, they can use response-time differences to recover the correct nonce value one character at a time — without needing the `api_secret_key` or any credential. Recovering the nonce lets an attacker construct a forged callback request that passes the `state == auth_query.state` check, enabling forced OAuth completion / session fixation: the attacker can complete the OAuth exchange bound to a `code`/session of their choosing, which the app will then treat as validated. This falls under the High-impact category of "session fixation or forced OAuth completion."

### Likelihood Explanation
Exploitation requires precise, low-noise timing measurements against the callback endpoint (network co-location or similar, as in the original PoC) and the ability to trigger repeated comparisons against a fixed target `state` value — a non-trivial but demonstrated-practical attack model (per the external report's own PoC). Likelihood is lower than the original JSON-RPC report because the nonce is short-lived (cookie expires in 60 seconds, per `begin_auth`) and single-use, shrinking the exploitation window, but the code path is real and unauthenticated.

### Recommendation
Replace the plain `==` comparison of `state` in `lib/shopify_api/auth/oauth.rb` with a constant-time comparison, consistent with `Utils::HmacValidator`:
```ruby
raise Errors::InvalidOauthError, "Invalid state in OAuth callback." \
  unless OpenSSL.secure_compare(state, auth_query.state)
```

### Proof of Concept
1. Trigger `begin_auth`, capturing the `SessionCookie` value (`state`, a 15-char alphanumeric nonce) as it would appear in the victim's browser cookie jar (per `NONCE_LENGTH = 15` in `lib/shopify_api/auth/oauth.rb`).
2. From a network position able to obtain accurate timing (as in the original report's `attack.c`), repeatedly issue callback requests carrying the victim's session cookie and varying `state` query-parameter guesses.
3. Measure response latency of `validate_auth_callback`'s `state == auth_query.state` branch: increasing correctly-guessed prefix length increases the number of byte comparisons performed before divergence, producing a measurable timing "staircase," exactly as demonstrated against V8's `String::SlowEquals` in the source report.
4. Once the full nonce is recovered, submit a forged callback (with attacker-chosen `code`/HMAC computed appropriately, or racing the legitimate completion) to force session fixation on the OAuth exchange. [4](#0-3)

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
