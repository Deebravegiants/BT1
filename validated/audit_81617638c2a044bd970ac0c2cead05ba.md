### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) headers are not covered by the HMAC signature, allowing shop-domain spoofing on replayed webhooks - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from unauthenticated HTTP headers [2](#0-1) . `Utils::HmacValidator.validate` only checks the HMAC against `to_signable_string` (the body) [3](#0-2) , so none of these header-derived fields are cryptographically bound to the signature.

### Finding Description
`Registry.process` validates the webhook solely via `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the raw body only) and compares it to the `hmac-sha256`/`x-shopify-hmac-sha256` header [4](#0-3) . After this check passes, it builds `WebhookMetadata` using `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id`, all of which are pulled directly from headers with no relation to the signed content [2](#0-1) .

This breaks the intended identity binding: `HMAC-verified(body)` ≠ `shop attributed to that body`. An unprivileged internet user who owns any real Shopify store can trigger a legitimate webhook to capture a valid `(body, hmac)` pair signed with the app's `api_secret_key` (values Shopify itself computes and delivers to the app's endpoint on the attacker's own store events). The attacker can then POST that exact body/HMAC pair to the app's webhook endpoint again, but with the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header changed to a value naming a different, victim shop. `HmacValidator.validate` still succeeds because it never inspects those headers, and `Registry.process` dispatches the (attacker-chosen) `shop` value straight to the host application's handler.

### Impact Explanation
Host applications are documented to trust `data.shop` from `WebhookMetadata` to determine which merchant/tenant the webhook event belongs to (e.g., to look up that shop's session/access token or update that shop's stored data) [5](#0-4) . Since `shop` is not bound to the signed payload, an attacker with access to only their own store's genuine webhook traffic can cause the app to process/attribute webhook data under an arbitrary victim shop domain, corrupting per-tenant state or triggering shop-scoped side effects for a shop the attacker does not control — a cross-tenant identity-binding break.

### Likelihood Explanation
Any Shopify merchant (an unprivileged, unauthenticated party from this gem's perspective) can generate arbitrary numbers of validly-signed webhook bodies for their own store simply by performing normal store actions, then replay the captured body+HMAC with a substituted `shop-domain` header. No knowledge of `api_secret_key` or any credential belonging to the victim is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed material that `HmacValidator` verifies — e.g., have `Request#to_signable_string` incorporate the `shop`, `topic`, and `webhook_id` header values alongside the raw body — or otherwise cryptographically bind these attributes to the payload before trusting them in `Registry.process`/`WebhookMetadata`.

### Proof of Concept
1. Register a webhook handler in the host app that trusts `data.shop` for tenant lookup.
2. As the owner of `attacker-shop.myshopify.com`, trigger any subscribed event; capture the resulting POST body `B` and its `x-shopify-hmac-sha256` value `H` (a valid signature for `B` under the app's `api_secret_key`).
3. Send a new POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H`, but header `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `B`/`H` per `to_signable_string` [6](#0-5) ; `Registry.process` calls the handler with `data.shop == "victim-shop.myshopify.com"` [7](#0-6) , even though the payload actually originated from the attacker's own shop.
