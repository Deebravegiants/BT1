### Title
`SimplexPaymaster._executePermit` reverts unconditionally on permit failure, enabling front-running DOS of the EIP-2612 bootstrap path - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` supports a mode-0x00 "PERMIT" path where an EIP-2612 signature embedded in `paymasterData` is executed on-chain during `_validatePaymasterUserOp`. The permit call is wrapped in a bare `try/catch` that reverts the whole UserOperation validation if `permit()` fails, with no fallback check of the resulting allowance — the exact anti-pattern flagged in the referenced report for `TRANSFER_FROM_WITH_PERMIT`.

### Finding Description
`_executePermit` parses `owner`, `permitAmount`, `deadline`, `v`, `r`, `s` straight out of the calldata-visible `paymasterData` and calls the token's `permit()`: [1](#0-0) 

```solidity
function _executePermit(PackedUserOperation calldata userOp) internal {
    ...
    try IERC20Permit(tokenAddr).permit(owner, address(this), permitAmount, deadline, v, r, s) {
        emit PermitExecuted(tokenAddr, owner, permitAmount);
    } catch {
        revert PermitFailed(tokenAddr);
    }
}
```

This is invoked unconditionally for any mode-0x00 UserOperation from `_validatePaymasterUserOp` before the base `PaymasterERC20` prefund logic runs: [2](#0-1) 

Because `v, r, s, deadline, owner, permitAmount` are all visible in the pending UserOperation (mempool/alt-mempool), any unprivileged third party can extract them and call `IERC20Permit(token).permit(owner, address(paymaster), permitAmount, deadline, v, r, s)` directly, consuming the owner's sequential EIP-2612 nonce before the paymaster's own call executes. When the paymaster's `permit()` call is then attempted with the now-stale nonce, it reverts, and `_executePermit` converts that into an unconditional `revert PermitFailed(tokenAddr)` — there is no fallback check of `IERC20(token).allowance(owner, address(this))`, even though the front-run permit call granted the exact same allowance the paymaster needed.

The docs confirm this mode is reachable by any account performing a first-time delegation/bootstrap on a chain without a standing Permit2 allowance: [3](#0-2) 

### Impact Explanation
Because `permit()` execution happens in `_validatePaymasterUserOp` during ERC-4337 validation, a successful front-run makes the sponsored bootstrap UserOperation for a solver account unconditionally fail with `PermitFailed`, even though the intended allowance state (paymaster is approved for `permitAmount`) has already been achieved by the attacker's front-run call. Repeated front-running can indefinitely block a specific solver account from completing its one-time EIP-2612-funded delegation/bootstrap op, since a fresh signature (new nonce) is required for every retry and can itself be observed and front-run again. This denies that solver the ability to install its Permit2 allowance and participate in fills/bids/sweeps on that chain until it acquires native gas through another path, impacting availability of the intent-fulfilment/gas-sponsorship path documented as the sole no-native bootstrap mechanism: [4](#0-3) 

### Likelihood Explanation
Exploitation only requires observing a pending UserOperation using mode 0x00 (visible pre-inclusion) and issuing a plain `permit()` call with the extracted signature fields — no special privileges, capital, or race-condition sophistication beyond ordinary transaction ordering/front-running, which is the same low-cost vector the referenced report describes. The bootstrap path is explicitly the fallback used exactly when a solver has no native gas, making it a predictable target.

### Recommendation
In `_executePermit`, replace the unconditional `revert PermitFailed` in the `catch` block with a fallback check of the current allowance, mirroring the report's recommendation:

```solidity
try IERC20Permit(tokenAddr).permit(owner, address(this), permitAmount, deadline, v, r, s) {
    emit PermitExecuted(tokenAddr, owner, permitAmount);
} catch {
    if (IERC20(tokenAddr).allowance(owner, address(this)) < permitAmount) {
        revert PermitFailed(tokenAddr);
    }
}
```
This allows the UserOperation to proceed when a front-run (or otherwise redundant) permit call already produced the needed allowance, eliminating the front-running DOS vector while preserving the revert when the allowance genuinely is insufficient.

### Proof of Concept
1. Solver account signs an EIP-2612 permit naming `SimplexPaymaster` as spender for `permitAmount`, and submits a mode-0x00 UserOperation whose `paymasterData` carries `token, permitAmount, deadline, v, r, s` as built by `buildPermitMode`: [5](#0-4) 
2. Attacker observes the pending UserOperation, extracts `owner, token, permitAmount, deadline, v, r, s`, and calls `IERC20Permit(token).permit(owner, address(paymaster), permitAmount, deadline, v, r, s)` directly, consuming the owner's EIP-2612 nonce.
3. When the bundler's `handleOps` call reaches `_validatePaymasterUserOp` → `_executePermit` for the original UserOperation, `IERC20Permit(tokenAddr).permit(...)` reverts (stale nonce) and the `catch` branch unconditionally reverts with `PermitFailed`, per [6](#0-5) , even though `allowance(owner, paymaster) == permitAmount` already holds from the attacker's front-run call.
4. The solver's bootstrap UserOperation fails validation and must be resigned with a new nonce, which can again be front-run, repeatably denying the solver's only no-native bootstrap path on that chain.

	signer: Pick<Signer, "signTypedData">,
	solverAccount: HexString,
	paymasterAddress: HexString,
	tokenAddress: HexString,
	permitAmount: bigint,
	chainId: number,
): Promise<PaymasterResult> {
	const permitSignature = await signEip2612Permit(
		client,
		signer,
		solverAccount,
		paymasterAddress,
		tokenAddress,
		permitAmount,
		chainId,
	)

	const r = `0x${permitSignature.slice(2, 66)}` as HexString
	const s = `0x${permitSignature.slice(66, 130)}` as HexString
	const v = Number.parseInt(permitSignature.slice(130, 132), 16)

	const paymasterData = encodePacked(
		["uint8", "address", "uint256", "uint256", "uint8", "bytes32", "bytes32"],
		[0, tokenAddress, permitAmount, maxUint256, v, r, s],
	) as HexString

	return {
		paymaster: paymasterAddress,
		paymasterData,
		paymasterVerificationGasLimit: VERIFICATION_GAS_LIMIT_PERMIT,
		paymasterPostOpGasLimit: POST_OP_GAS_LIMIT_SIMPLEX,
	}
