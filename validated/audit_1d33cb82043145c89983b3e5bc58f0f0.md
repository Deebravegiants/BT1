### Title
`shop` used to route webhook handling is an unauthenticated header, not bound to the HMAC-signed body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Webhooks::Request#initialize` stores `@raw_body` and `@headers` as two independent values, and `HmacValidator.validate` only authenticates `@raw_body` (via `to_signable_string`) against the app's secret. `shop`, `topic`, `webhook_id`, and `api_version` are read straight from `@headers` with no cryptographic binding to the signed body, so an attacker who obtains one validly-signed body (e.g. from their own shop's genuine webhook delivery) can resubmit it to the same public endpoint with a different `shop-domain` header and have it pass `HmacValidator.validate`, causing `WebhookMetadata#shop` to carry an attacker-chosen value that the host app trusts for tenant routing.

### Finding Description
The claimed binding is:
`compute_signature(bytes_signed_by_Shopify) == compute_signature(request.to_signable_string)` **and** `request.shop == the shop that produced bytes_signed_by_Shopify`.

Tracing the code:
- `Request#initialize` (`lib/shopify_api/webhooks/request.rb:46-63`) only validates that the required header *names* are present; it never checks any relationship between header *values* and the body. [1](#0-0) 
- `Request#hmac` reads `shopify-hmac-sha256` from `@headers`, and `Request#shop` reads `shopify-shop-domain` from `@headers` — both independently, both attacker-suppliable in a raw HTTP request to the app's webhook endpoint. [2](#0-1) 
- `to_signable_string` returns only `@raw_body` — headers are never part of the signable material. [3](#0-2) 
- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against `verifiable_query.hmac`, i.e. it re-signs the raw body bytes and checks that the *received* HMAC header matches — this proves the body was signed by Shopify with the app's secret at some point, but proves nothing about which shop-domain header accompanies it now. [4](#0-3) 
- `Registry.process` calls `Utils::HmacValidator.validate(request)`, and on success builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` and dispatches it to the host app's `handler.handle(data:)` — the host app is expected to use `WebhookMetadata#shop` to decide which merchant's records to read or mutate. [5](#0-4) [6](#0-5) 

Root cause: the byte-identity invariant is violated. The bytes that produce a passing signature check (`@raw_body`) are decoupled from the bytes that decide tenant identity (`@headers["shopify-shop-domain"]`). Nothing in `Request`, `HmacValidator`, or `Registry.process` cross-checks that the shop asserted in the header actually corresponds to the shop that owns the signed body.

Attacker flow:
1. Attacker installs the target app on their own development/test shop (a legitimate, unprivileged action) and lets Shopify deliver a real webhook (e.g. `orders/create`) to the app's public endpoint. Attacker captures the exact raw request bytes and the `shopify-hmac-sha256` header Shopify computed for it.
2. Attacker resends that exact `raw_body` (byte-for-byte, so the HMAC still validates against `Context.api_secret_key`) to the same public webhook endpoint, but substitutes an arbitrary `shopify-shop-domain` header value (e.g. the victim merchant's domain) and/or a different `topic`/`webhook-id`.
3. `HmacValidator.validate` returns `true` because it only checks body/secret, not shop-header/body correspondence.
4. `Registry.process` builds `WebhookMetadata` with `shop: request.shop` set to the attacker-chosen victim domain, and invokes the host app's handler, which (per the gem's documented model) uses `data.shop` to select which merchant's database rows to touch.

Existing guards checked and found insufficient: `HmacValidator.validate` (body-only), `ShopValidator.sanitize!` (not invoked in this path at all — only format-validates a domain string, not present in `Request`/`Registry`), `Context.setup?`/`private?`/`embedded?` (irrelevant, no session/OAuth context here), Sorbet runtime typing (`T.cast` on `String` only enforces type, not provenance/authenticity).

### Impact Explanation
This is a cross-tenant confused-deputy: a value with no cryptographic authenticity (`shop-domain` header) is treated by the host application as the authenticated identity of the webhook sender, while the actual integrity guarantee (`HmacValidator.validate`) only covers the JSON body bytes. Any unprivileged attacker who can obtain one genuinely-signed webhook body — trivially achievable by installing the app on their own shop — can then impersonate an arbitrary victim shop for every subsequent replay of that same body to the app's shared webhook endpoint, repeatably and indefinitely (the same captured body/HMAC pair can be replayed against as many spoofed `shop-domain` values as desired, since neither the header nor body carry a nonce/timestamp check in this gem). Downstream, whatever the host handler does with `WebhookMetadata#shop` (look up merchant records, apply mutations, trigger fulfillment/redact logic, etc.) is now attacker-directed against a merchant the attacker never controls — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Preconditions are minimal and fully within reach of an unprivileged attacker: create a free/development shop, install the target app on it (standard, permitted per the gem's design), and receive one legitimate webhook delivery to capture a valid `(raw_body, hmac)` pair. No `api_secret_key`, access token, or any privileged credential is required — the attacker only needs to interact with the app's public webhook endpoint using their own legitimately-issued webhook payload data. The exploit is fully repeatable and requires no timing race or destructive side effects to set up.

### Recommendation
Do not trust `shopify-shop-domain` (or `topic`/`webhook-id`) as authenticated merely because `HmacValidator.validate` passed. Either (a) include the relevant headers (shop, topic, webhook id) in the signable string used for HMAC computation so they are cryptographically bound to the signature, or (b) independently verify `request.shop` against the shop that is expected to own the given `webhook_id`/topic combination (e.g. cross-check against the app's own webhook subscription registered per-shop via the Admin API) before dispatching to the handler, and reject mismatches.

### Proof of Concept
```ruby
# test/webhooks/request_shop_confusion_test.rb
require "test_helper"

class WebhookRequestShopConfusionTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(
      api_key: "key", api_secret_key: "secret", host_name: "app.example",
      scope: "read_products", is_embedded: false, is_private: false,
      api_version: ShopifyAPI::LATEST_API_VERSION,
    )
  end

  def test_same_body_two_shops_both_pass_hmac
    raw_body = '{"id":1}'
    hmac = OpenSSL::HMAC.base64digest(OpenSSL::Digest.new("sha256"), "secret", raw_body)

    headers_shop_a = {
      "shopify-topic" => "orders/create",
      "shopify-hmac-sha256" => hmac,
      "shopify-shop-domain" => "attacker-shop.myshopify.com",
      "shopify-api-version" => "2023-10",
      "shopify-webhook-id" => "1",
    }
    headers_shop_b = headers_shop_a.merge("shopify-shop-domain" => "victim-shop.myshopify.com")

    req_a = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers_shop_a)
    req_b = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers_shop_b)

    # BYTE IDENTITY invariant is violated: same signed bytes, different asserted shop
    assert_equal req_a.hmac, req_b.hmac
    refute_equal req_a.shop, req_b.shop

    assert ShopifyAPI::Utils::HmacValidator.validate(req_a)
    assert ShopifyAPI::Utils::HmacValidator.validate(req_b) # attacker-controlled shop also validates
  end
end
```
Both requests pass `HmacValidator.validate` despite asserting different shops for identical signed body bytes, demonstrating that `Registry.process` would dispatch attacker-controlled shop identity to the host app's handler.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
