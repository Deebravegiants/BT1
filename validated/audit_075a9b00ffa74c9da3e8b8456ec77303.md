### Title
Phantom-order price aggregation weights bids by live, unpinned `balanceOf` reads, letting a solver flash/borrow-inflate its balance to dictate the published pool rate used to price real intents - ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
`aggregatePhantomBids` prices each leg of a phantom order by taking the **liquidity-weighted median** of solver quotes, where a quote's weight is the solver's live `balanceOf` (plus vault/position balances) of the leg's output token on the destination chain, read via a synchronous `eth_call` at aggregation time. This mirrors the reported `AavePool` bug class: a balance read used directly as the weight/decider in a reward/price calculation, with no defense against a transiently inflated balance. Because `weightedMedian` is a *selection* (it returns one bidder's exact quoted price verbatim when that bidder holds the majority of the leg's weight), a solver that inflates its `balanceOf` above 50% of the leg's total weight at read time can force the published `medianPrice` to equal its own quote. That price is persisted into `PhantomOrderPriceSnapshotV2` and folded into `LiquidityPool.buyRate`/`sellRate`, which the SDK's `IntentGateway.quoteIntent` now uses **by default** (`indexed_rates` strategy) to price real cross-chain intents — i.e., real user funds are escrowed and paid out against this manipulated rate.

### Finding Description
In `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts`, `runAggregation` computes, per leg: [1](#0-0) 
a `weight` from `getBalance(destUrl, chain, outputToken, solver)` — a plain `balanceOf`-style RPC read of the solver's current wallet/vault balance for the leg's output token — and pushes `{price, weight}` into `quotesByLeg`.

The per-leg price is then chosen by: [2](#0-1) 
`weightedMedian(backedQuotes)`, documented explicitly as a **selection, not a blend** — "a solver holding over half the leg's weight sets the published price verbatim" (`docs/outbound-request-incentivization.md`-style comment in `docs/content/developers/...`/flow docs): [3](#0-2) 

This price is written into `PhantomOrderPriceSnapshotV2.medianPrice` and folded by `updateLiquidityPools` into the pool's `sellRate`/`buyRate`: [4](#0-3) 

Those aggregate rates are now the **default** pricing source for real orders placed through the SDK: [5](#0-4) 

The root cause is structurally identical to the reported `AavePool._userPendingstkAaveRewards` bug: an on-chain `balanceOf` snapshot is treated as ground truth for a value (there: reward share; here: price weight/selection) with no time-lock, checkpointing, or stake-based sizing to prevent a transiently or artificially inflated balance from dominating the calculation. Whoever controls the largest read-time balance of the output token unilaterally sets the "market" price other solvers' bids, and downstream real intents, are measured against.

### Impact Explanation
Because the resulting `medianPrice` becomes the pool's canonical `buyRate`/`sellRate` and is consumed by default (`quoteIntent`) to construct real order `inputs`/`output.assets` for the `IntentGateway`, an attacker able to inflate its output-token balance at the exact moment the aggregation's RPC read fires can:
- Force the published rate to its own arbitrarily-chosen quote (verbatim, per the median-selection design) whenever it holds >50% of the leg's readable weight.
- Cause real users' intents to be priced off this manipulated rate, moving real escrowed input tokens against a distorted output amount — a direct fund-impact vector (mispriced fills / value extraction from users who rely on `quoteIntent`'s default indexed rate).

This satisfies "Medium/High" impact under the rules (unsound/manipulable state used to size real fund movement), analogous to unbacked/incorrect payout in the original report.

### Likelihood Explanation
Likelihood is constrained by timing: the balance read is not necessarily pinned to the exact block of a flash loan, since aggregation runs asynchronously off-chain after the Hyperbridge `PhantomBidWindowExhausted` event, against the EVM chain's *current* head at call time (I could not fully confirm within the review whether any block-tag pinning mitigation - referenced in `sdk/packages/sdk/docs/ai/decisions/2026-09-01-blocktag-is-a-parameter-of-the-balance-read-and-a-per-chain-map.md`, which I was unable to open due to a tool error in the final iteration - already pins this specific read to a safe/adversary-resistant block). If the read is unpinned or pinned to a recent/attacker-influenceable block, a same-block flash loan is directly exploitable; if not, an attacker still only needs to hold (not necessarily flash-loan) enough of the output token for the short window between bid submission and aggregation, which is a materially lower bar than a full capital deployment, making this a realistic and repeatable attack for any actively-traded phantom-order pair with modest depth.

### Recommendation
- Do not let a single live balance read set the entire price via unweighted "winner-take-all" median selection. Cap any single bidder's influence (e.g., weight-cap per solver, or true weighted-average instead of exact selection).
- Pin the balance read to a block that predates the bid window's close by a safety margin (already appears to be a design goal per `2026-09-01-blocktag-is-a-parameter-of-the-balance-read` — verify this fix actually applies to the phantom-price weighting path, not only to the inventory-reading/refresh path documented in `pool-liquidity-refresh-orderfilled-partialfill-escrowreleased.md`).
- Require solvers to have held the balance for some minimum duration (checkpointed balance, not instantaneous), or require an on-chain stake/bond rather than a spot wallet balance, mirroring the standard fix for flash-loan governance/oracle attacks.

### Proof of Concept
1. Attacker (or colluding solver) submits a phantom bid quoting an arbitrary favorable `outputs[i].amount` for a leg, satisfying `isVerifiedSolverBid` with a valid EIP-7702-delegated `SolverAccount` signature.
2. Immediately before (or during) the window in which `handlePhantomOrderPrices` → `aggregatePhantomBids` performs its `getBalance` read for that solver/output-token pair, the attacker temporarily acquires (borrows/flash-loans) enough of the output token on the destination chain to exceed 50% of all bidders' combined weight for that leg.
3. `weightedMedian` selects the attacker's own quoted price verbatim as `medianPrice` for the leg (`sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts:1551`).
4. `updateLiquidityPools` writes this into `PoolChainLiquidity`/`LiquidityPool.sellRate`/`buyRate` (`sdk/packages/indexer/src/services/liquidityPool.service.ts:260-278`).
5. Any user calling `IntentGateway.quoteIntent` with the default `indexed_rates` strategy now receives amounts computed off the manipulated rate, and any order built from that quote moves real funds at the attacker-chosen price.
6. Attacker returns the borrowed tokens once the read has completed, retaining the balance-weight advantage only for the duration needed to win the median selection.

2. Per leg, a solver's quote is weighted by **its balance of that leg's OUTPUT token on the destination chain** — the inventory that actually backs the leg. Zero-weight quotes are dropped entirely, not down-weighted: they never reach the median, `bidCount`, or the bidder list. A leg where no bidder holds the output token is absent from the result, exactly as if nobody quoted it.

3. The leg's price is `weightedMedian` of the backed quotes — a **selection**, not a blend. It returns one bidder's exact integer, so a solver holding over half the leg's weight sets the published price verbatim, and the result can never be a value nobody quoted. `lowestPrice` and `highestPrice` are deliberately overwritten with the median so consumers cannot read an outlier bid as a tradeable bound.
