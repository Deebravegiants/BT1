### Title
Webhook Cross-Tenant Spoofing via HMAC Not Binding the `shop`/`topic` Headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` authenticates the *payload bytes* but never binds the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers to that signature. `Webhooks::Registry.process` then trusts `request.shop` and `request.topic` unconditionally once the body HMAC checks out, allowing a party that can obtain one valid (body, HMAC) pair to relabel it for an arbitrary target shop/topic.

### Finding Description
The HMAC is computed and verified purely over `@raw_body`: [1](#0-0) 

None of `topic`, `shop`, `api_version`, or `webhook_id` (all parsed straight from attacker-controllable HTTP headers) are part of the signed string: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` against the secret — it has no way to know that `shop`/`topic` were altered, since those fields never entered the signature computation: [3](#0-2) 

`Registry.process` then uses the now-"validated" request to dispatch the handler, passing the *unauthenticated* `request.shop` and `request.topic` straight into `WebhookMetadata`, which the host app uses as the tenant identifier for the webhook: [4](#0-3) 

The identity binding broken is: `shop header used by the handler for tenant scoping` ≠ `shop bytes actually covered by the HMAC (none)`. Any actor who can obtain one legitimately-signed `(body, hmac)` pair for the app — e.g., by installing the app on their own shop and receiving a real webhook, since all installs of the same app share the same `client_secret`/`api_secret_key` used to compute the HMAC — can replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for a different, victim shop. `HmacValidator.validate` will still return `true` because it never inspected those headers, and `Registry.process` will hand the attacker-chosen body to the handler labeled as having originated from the victim shop/topic.

### Impact Explanation
This breaks the tenant boundary the webhook mechanism is supposed to enforce: an attacker who is merely an installer of the app on their own store (no elevated credential, no access token, no `client_secret` needed) can inject data/events that a host application will process as belonging to a different merchant's shop. Depending on how the host app's `WebhookHandler` implementations use `shop` (e.g., to look up/update per-shop records), this enables cross-tenant data corruption/impersonation — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is realistic but requires a legitimate install of the target app on an attacker-owned shop to harvest a valid body+HMAC pair (any webhook topic can be used as the vector); no secret material, access token, or privileged account beyond the attacker's own store install is required. The header-swap-and-replay step is trivial once a valid pair is captured.

### Recommendation
Include the security-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed string, or otherwise bind them to the HMAC computation in `Webhooks::Request#to_signable_string`, so that altering any of these headers invalidates the signature. At minimum, document/enforce that `Registry.process` must not trust `request.shop`/`request.topic` as tenant identity unless they are cryptographically bound to the payload.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic (e.g. `orders/create`) to receive a legitimately Shopify-signed request: headers include `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, body `B`.
2. Replay the exact same body `B` and HMAC header `H` to the app's webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim.myshopify.com` (and/or spoof `X-Shopify-Topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) and matches `H` — validation succeeds.
4. The registered handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, processing attacker-supplied data as though it came from `victim.myshopify.com`.
