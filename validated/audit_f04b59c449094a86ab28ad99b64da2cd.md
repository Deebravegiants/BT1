### Title
Webhook shop-domain identity spoofing via HMAC signature that only covers the request body, not the shop header - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop` value that identifies which tenant the webhook belongs to is taken from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the signed payload. Consequently, the binding `hmac == HMAC(secret, body)` does not imply `shop == the shop that generated body`, so an attacker who can obtain any one valid `(body, hmac)` pair signed with the app's shared `api_secret_key` can freely relabel that payload as originating from any other shop.

### Finding Description
The HMAC verification for webhooks is implemented as:
- `Request#hmac` reads the signature from the `hmac-sha256` header.
- `Request#to_signable_string` returns `@raw_body` only [1](#0-0) .
- `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read directly from headers, none of which are part of `to_signable_string` [2](#0-1) .
- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC using `OpenSSL.secure_compare` — i.e., it only proves the body bytes were signed by the holder of `api_secret_key`, and says nothing about the shop header [5](#0-4) .
- `Registry.process` calls this validator, and on success immediately trusts `request.shop` to build the `WebhookMetadata` delivered to the host application's handler, with no secondary check that the header value matches whichever shop actually produced the signed body [3](#0-2) .

The identity binding that should hold is `shop (used by the handler) == shop (that legitimately produced the signed body)`. Because the HMAC only signs `@raw_body`, this binding is not enforced by the gem: `shop` is decoupled from the signature. Since a single app uses one shared `api_secret_key` across every installing merchant, any shop that has installed the app can receive an authentically-signed webhook from Shopify for its own store, then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with an arbitrary victim shop domain. The signature still validates because it never covered the header, so `Registry.process` will invoke the handler with attacker-chosen `shop` while the `body`/`topic` remain those of the attacker's own legitimate webhook. If the host application uses `WebhookMetadata#shop` to select which tenant's data to update (the documented purpose of this field), this results in cross-tenant data injection/corruption attributed to a shop the attacker does not own or control.

### Impact Explanation
This breaks the tenant isolation the webhook system is supposed to provide: the field host apps rely on to know "which merchant does this event belong to" is attacker-controlled and unauthenticated, even though the overall webhook is HMAC-"verified." This falls into the Critical bucket as cross-tenant access/data confusion, since a self-service app installer can inject events attributed to any other shop domain merely by knowing/guessing it (Shopify domains are public/predictable, `*.myshopify.com`).

### Likelihood Explanation
Likelihood is high for any app that trusts `WebhookMetadata#shop` for tenant selection (which is its stated purpose per `lib/shopify_api/webhooks/webhook_metadata.rb`/handler contract). The only requirement is installing the app once (a normal, unprivileged, free action for any Shopify Partner/dev store), capturing one legitimate webhook delivery, and replaying it with a modified header — no access to `api_secret_key`, tokens, or victim credentials is needed.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the signed material verified against the request, or otherwise cryptographically tie the header claims to the signed body before exposing them via `WebhookMetadata`. Since Shopify's own webhook HMAC scheme only signs the body by design, the practical mitigation is for `Registry.process`/`Request` to treat header-derived `shop` as untrusted unless independently corroborated (e.g., cross-check against a shop already known/registered for that specific webhook subscription, or validate the body's own tenant-identifying fields against the header) rather than passing the raw header value straight through to the handler as an implicitly-authenticated identity.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker-shop.myshopify.com` (free, self-service).
2. Trigger any webhook topic the app subscribes to (e.g., `orders/create`) and capture the raw HTTP request Shopify sends to the app's webhook endpoint, including the `X-Shopify-Hmac-Sha256` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` headers and the raw body.
3. Replay the exact same request to the app's webhook endpoint, keeping the body and `X-Shopify-Hmac-Sha256` header unchanged, but replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds because it only checks `@raw_body` against the unchanged HMAC [6](#0-5) ; `Registry.process` invokes the registered handler with `shop: "victim-shop.myshopify.com"` [7](#0-6) , causing the host application to act on `victim-shop.myshopify.com`'s behalf using attacker-supplied body content.
