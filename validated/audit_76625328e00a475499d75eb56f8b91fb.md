### Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `webhook_id`, and `api_version` from raw, unauthenticated HTTP headers, while `to_signable_string` (used by the HMAC check) only covers the raw request body. `Registry.process` validates the HMAC and then hands `request.shop` straight to the host application's handler as an authenticated tenant identifier, even though that field was never bound by the signature.

### Finding Description
`HmacValidator.validate` computes/verifies the HMAC exclusively over `verifiable_query.to_signable_string`, and for webhooks that string is just `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors instead read directly from HTTP headers (`shopify-*` / `x-shopify-*`), which are not part of the signed payload at all: [2](#0-1) 

`Registry.process` performs the HMAC check and then immediately trusts `request.shop` (and `request.topic`) as authoritative, passing them into the `WebhookMetadata` object delivered to the host application's registered handler: [3](#0-2) 

This breaks the intended identity binding: `shop_header == shop_bound_by_hmac` should hold, but the gem only enforces `hmac(raw_body) == received_hmac`; the `shop-domain` header is unauthenticated and attacker-controlled bytes as far as this gem's verification logic is concerned. An unprivileged internet user who can reach the app's webhook endpoint (or replay/craft a POST with an arbitrary `shop-domain`/`topic` header alongside *any* body, including a body they know the HMAC for from their own legitimately-owned test/dev shop) can cause the gem to report a different, victim shop domain to the host application's handler while the HMAC still validates correctly for the (attacker-controlled) body. Since many host applications use `WebhookMetadata#shop` to select which merchant record/session to act on (e.g., "which shop's data does this webhook belong to"), this allows cross-tenant confusion at the point where the gem hands off "verified" data to the app.

### Impact Explanation
This falls under cross-tenant access: the gem asserts a webhook is "valid" (HMAC verified) and simultaneously reports a `shop` value that was never cryptographically bound to that verification. Any application that keys behavior (e.g., data deletion, entitlement changes, order/customer processing) off `WebhookMetadata#shop` as returned by this gem is exposed to being told the wrong tenant for an otherwise-valid-looking signed payload, particularly in setups where the raw body can be shop-agnostic (e.g., identical/empty JSON bodies across shops, as seen in the test fixtures using `raw_body: "{}"`).

### Likelihood Explanation
Exploitability depends on the attacker being able to reach the app's public webhook endpoint and supply a body for which they can compute a valid HMAC with the real `api_secret_key` — which normally only Shopify can do for a genuine webhook. However, whenever the raw body is shop-independent (e.g. `{}` or any body reused across shops, which the test suite itself demonstrates is a valid signed payload), a webhook legitimately sent by Shopify for shop A can be replayed with the `shop-domain`/`topic`/`webhook-id` headers swapped to point at shop B while the HMAC over the (identical) body still validates. This does not require possession of `api_secret_key`.

### Recommendation
Bind the shop (and topic) into the HMAC-verified signable data, or otherwise cryptographically tie the header values to the request that Shopify actually signs (Shopify's own webhook signature currently only covers the body, so the header values should be treated by the gem as informational, not as verified tenant identity). At minimum, `Webhooks::Registry.process`/`WebhookMetadata` documentation should make explicit that `shop`, `topic`, and `webhook_id` are unauthenticated header values, and callers should cross-check them against server-side, already-authenticated session/shop state (e.g., an existing offline session already stored for that shop) before using them for tenant-scoped actions, rather than relying on this gem's HMAC check to vouch for them.

### Proof of Concept
1. Attacker obtains (or replays) a genuine Shopify webhook whose body is shop-independent, e.g. raw body `"{}"` with a valid `shopify-hmac-sha256` computed by Shopify for the app's `api_secret_key` (as shown to be a valid combination in the existing test suite): [4](#0-3) 
2. Attacker resends this exact `raw_body`/HMAC to the app's webhook endpoint but substitutes the `shopify-shop-domain` (and optionally `shopify-topic`) header with a different, victim shop's domain / a topic mapped to a sensitive handler.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC: [5](#0-4) 
4. The handler receives `WebhookMetadata` with the attacker-chosen `shop` value, believing it is authenticated because the HMAC check passed.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
