Found the analog: the `multisig_account` timelock feature lets a transaction's execution rule (immediate vs. timelocked, and its override threshold) be defined **not at approval time but at execution-check time**, and that rule can be changed by a separate `upsert_timelock`/`remove_timelock` transaction issued by the multisig itself in between approval and execution — exactly the "opcode changed after approval" pattern from the Llama report, mapped onto custody of a multisig-controlled account/APT.

### Title
Multisig timelock/override rules are re-evaluated at execution time, letting a subsequent `upsert_timelock`/`remove_timelock` transaction retroactively change the execution conditions of an already-approved pending transaction - (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

### Summary
`multisig_account` (an Aptos-native k-of-n custody primitive controlling a resource account, which may hold APT or other assets) determines whether a pending `MultisigTransaction` can execute via `can_execute_with_timelock`, which reads the *current* `MultisigAccountTimeLock` resource and the transaction's `creation_time_secs` at call time [1](#0-0) . The timelock configuration (period and override threshold) is not fixed when a transaction is created/approved — it can be freely mutated afterward via `upsert_timelock`/`remove_timelock`, which are themselves ordinary multisig-executed transactions [2](#0-1) .

### Finding Description
`can_execute` / `can_be_executed` gate execution on `num_approvals >= num_signatures_required(...) && can_execute_with_timelock(...)` [3](#0-2) . `can_execute_with_timelock` is `inline` and re-reads `MultisigAccountTimeLock` from global storage at the moment of the execution check, not at the moment the transaction was created or the moment owners cast their approvals [4](#0-3) .

Because Aptos multisig transactions execute strictly in sequence order (enforced by `sequence_number == last_resolved_sequence_number(multisig_account) + 1`), an owner can construct the following sequence, all self-authorized through the normal multisig quorum flow:

1. Owners approve transaction #1 (e.g., a large APT transfer out of the multisig-controlled resource account) under a strict policy — e.g., `override_threshold = 3` (of 3) with a long `timelock_period`. It has only 2 approvals and is not yet executable because `can_execute_with_timelock` returns false (2 < 3, timelock not elapsed).
2. The same 2 (or a different 2-of-3) owners create and immediately execute transaction #2, `upsert_timelock`/`remove_timelock`, lowering `timelock_period` to `MIN_TIMELOCK_PERIOD` or dropping the override threshold, or removing the timelock resource entirely (`remove_timelock` only requires the multisig's own quorum, not the original approvers' consent, and there is no rule preventing it from targeting the *next* pending sequence's execution semantics) [5](#0-4) .
3. Transaction #1, still holding only its original 2 approvals, now satisfies the *new* execution rule (timelock removed, or elapsed-time check trivially satisfied since `elapsed = now_seconds() - creation_time_secs` is computed against wall-clock time, not against "time since timelock was configured") and can be executed immediately [6](#0-5) .

The module's own doc comment on `upsert_timelock` acknowledges this exact mechanism as a known, "acceptable" residual risk for transactions queued between the timelock's activation and its next execution [7](#0-6) . This is precisely the LlamaCore-style bug: an action (the pending transfer) is approved under one set of execution semantics (strict timelock + override threshold, implicitly relied upon by owners who declined to grant an early override), but a second, differently-scoped action (`upsert_timelock`) mutates the global rule that governs whether the first action can now run — without directly amending the first action or requiring its original approvers' consent.

Unlike ownership removal (`remove_owners`), which the module explicitly re-validates against current owners at execution time via `num_approvals_and_rejections` (confirmed correct by `test_validate_transaction_should_not_consider_removed_owners`) [8](#0-7) , there is no analogous protection for the timelock/override-threshold execution rule — it is read fresh from mutable global state with no linkage back to what was in effect when the transaction accumulated its votes.

### Impact Explanation
This breaks the custody guarantee that a timelock+override-threshold policy protecting a multisig-held asset (APT or other value in the resource account) cannot be bypassed for a transaction that was approved under, and relies on, the original stricter rule. A minority-quorum (e.g., 2-of-3, below the configured 3-of-3 override) can weaponize the sequential single-threaded transaction queue to strip or weaken the timelock protecting a pending high-value transfer immediately before executing it, achieving early/unauthorized execution of a transfer that the full owner set intended to require additional time or additional signers to gate. This directly maps to "unauthorized takeover of ... freeze control ... tied to live assets" and "custody accounting corruption that moves value to the wrong holder," since the timelock/override threshold is itself a custody control gating asset movement out of a resource-account-backed multisig.

### Likelihood Explanation
Medium-High. It requires only the existing quorum threshold (`num_signatures_required`, e.g., 2-of-3) — not the elevated override threshold — and standard entry functions (`create_transaction`, `approve_transaction`, `upsert_timelock`/`remove_timelock`, `execute` via `MultisigTransaction`). No privileged role, governance, or external condition is needed; it is achievable entirely by the same set of owners who would otherwise be blocked by the timelock, making it a realistic insider/minority-collusion path rather than a purely theoretical one. It is gated behind the `multisig_timelock` feature flag (`features::is_multisig_timelock_enabled`), so impact is limited to multisig accounts that have adopted this newer, self-acknowledged feature.

### Recommendation
Snapshot the effective timelock policy (period and override threshold) onto the `MultisigTransaction` at creation time (or at first-approval time) rather than re-reading the live `MultisigAccountTimeLock` resource inside `can_execute_with_timelock`. Alternatively, require that any change to `MultisigAccountTimeLock` (via `upsert_timelock`/`remove_timelock`) only take effect for transactions created after the change, similar to how Llama's fix required the execution opcode to be fixed at approval time and not mutable by unrelated, differently-scoped actions.

### Proof of Concept
Given a 3-owner multisig with `num_signatures_required = 2` and a timelock configured with `override_threshold = 3`, `timelock_period = MAX_TIMELOCK_PERIOD`:
1. Owner A creates transaction #1 transferring APT out of the multisig; Owner B approves. 2 approvals total — below override (3), timelock not elapsed → `can_be_executed(#1) == false`.
2. Owners A and B (2-of-3, meeting `num_signatures_required`) create and execute transaction #2 calling `remove_timelock` (or `upsert_timelock` with `timelock_period = MIN_TIMELOCK_PERIOD`, `override_threshold = none`). This only needs the normal 2-of-3 quorum, per `remove_timelock`/`upsert_timelock_internal` [9](#0-8) .
3. Immediately after, `can_be_executed(#1)` is re-evaluated: `exists<MultisigAccountTimeLock>` is now false (or has a trivially low period), so `can_execute_with_timelock` returns `true` unconditionally [10](#0-9) .
4. Transaction #1 executes with only its original 2 approvals, despite the owner set having explicitly configured a 3-of-3 override requirement intended to prevent exactly this kind of minority-approved high-value transfer.

I was unable to execute this against a live Move test harness within this session, so the exact behavior should be confirmed by running/extending the existing test suite in `multisig_account.move` (e.g., adapting `test_timelock_with_override_at_boundary`) to interleave a `remove_timelock`/`upsert_timelock` transaction between approval and execution of a pending transaction, as the module's own tests do not currently cover this interleaving scenario.

    /// Return true if the transaction with given transaction id can be executed immediately, or it has to wait
    /// for the timelock to expire.
    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }

    /// Upsert the timelock configuration for the multisig account.
    /// timelock_period must be between MIN_TIMELOCK_PERIOD and MAX_TIMELOCK_PERIOD.
    /// override_threshold, if provided, must be > num_signatures_required and <= the number of owners.
    ///
    /// Note on pending transactions: the timelock check measures elapsed time from a transaction's
    /// `creation_time_secs`, not from when the timelock was activated. Because multisig transactions
    /// execute strictly in sequence order, this is only observable for transactions queued *after*
    /// this `upsert_timelock` call but *before* it executes — those transactions may become
    /// executable sooner than `timelock_period` seconds after this call takes effect, because part
    /// of their elapsed time is counted from before the new timelock was live. Transactions queued
    /// after this call has executed receive the full `timelock_period` protection. This residual
    /// window is bounded by the previous timelock period (or by approval time, if there was no
    /// prior timelock) and is considered an acceptable, operator-visible risk.
    entry fun upsert_timelock(multisig_account: &signer, timelock_period: u64, override_threshold: Option<u64>) {
        assert!(
            features::is_multisig_timelock_enabled(),
            error::unavailable(ETIMELOCK_NOT_ENABLED)
        );
        upsert_timelock_internal(multisig_account, timelock_period, override_threshold);
    }

    /// Shared validation + publish logic for timelock configuration. Used by `upsert_timelock` and
    /// by the creation-time variants (`create_with_owners_and_timelock`, ...) so the invariant that
    /// `MultisigAccountTimeLock` is only ever published through a single validated path is preserved.
    fun upsert_timelock_internal(
        multisig_account: &signer,
        timelock_period: u64,
        override_threshold: Option<u64>,
    ) {
        let multisig_address = address_of(multisig_account);
        assert_multisig_account_exists(multisig_address);

        assert!(
            timelock_period >= MIN_TIMELOCK_PERIOD && timelock_period <= MAX_TIMELOCK_PERIOD,
            error::invalid_argument(EINVALID_TIMELOCK_DURATION)
        );

        let multisig_account_resource = &MultisigAccount[multisig_address];
        assert!(
            override_threshold.is_none() || *override_threshold.borrow() > multisig_account_resource.num_signatures_required,
            error::invalid_argument(EINVALID_TIMELOCK_OVERRIDE_THRESHOLD)
        );
        assert!(
            override_threshold.is_none() || *override_threshold.borrow() <= multisig_account_resource.owners.length(),
            error::invalid_argument(EINVALID_TIMELOCK_OVERRIDE_THRESHOLD)
        );

        if (exists<MultisigAccountTimeLock>(multisig_address)) {
            let multisig_account_resource = &mut MultisigAccountTimeLock[multisig_address];
            multisig_account_resource.timelock_period = timelock_period;
            multisig_account_resource.override_threshold = override_threshold;
        } else {
            move_to(multisig_account, MultisigAccountTimeLock::V1 {
                timelock_period,
                override_threshold,
            });
        }

        emit(TimelockUpdated {
            multisig_account: multisig_address,
            timelock_period,
            override_threshold,
        });
    }

    /// Remove the timelock configuration for the multisig account.
    /// Aborts if no timelock is configured.
    entry fun remove_timelock(multisig_account: &signer) {
        let multisig_address = address_of(multisig_account);
        assert_multisig_account_exists(multisig_address);
        assert!(
            exists<MultisigAccountTimeLock>(multisig_address),
            error::not_found(ETIMELOCK_DOES_NOT_EXIST)
        );
        move_from<MultisigAccountTimeLock>(multisig_address);
        emit(TimelockRemoved {
            multisig_account: multisig_address,
        });
    }
