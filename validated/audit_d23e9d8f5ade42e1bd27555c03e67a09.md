## Title
Webhook shop-domain identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signable string from the raw body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values used to identify *which tenant* the webhook belongs to are taken from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` verifies only that the body's HMAC is valid for *some* shop, then blindly trusts the header-derived `shop` value when handing data to the app's webhook handler. Any party capable of obtaining one validly-signed webhook (e.g., by installing the app on a shop they control) can replay that same body/HMAC pair while substituting an arbitrary `shop-domain` header, causing the host application to process attacker-controlled content under a victim shop's identity.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are parsed straight from headers with no cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively from `to_signable_string`, i.e., only the body bytes: [3](#0-2) 

`Registry.process` only checks this body-only HMAC, then forwards the *unauthenticated* `request.shop` value directly to the app's handler as the tenant identity: [4](#0-3) 

The binding that should hold is:
`shop_that_HMAC_authenticates == shop_used_to_attribute_the_webhook_data`

In this gem, the left side is undefined (the HMAC secret is a single, shared app `client_secret`, and the signature covers zero identity fields), while the right side is an attacker-controlled header. Since the secret is shared across every shop that installs the app, a valid `(body, hmac)` pair generated for shop A remains valid verbatim when replayed with shop B's domain in the `x-shopify-shop-domain` header — the equality is never actually checked.

### Impact Explanation
This breaks tenant isolation for the webhook processing pipeline: an unprivileged user who can install the public/multi-tenant app on a shop they control obtains genuine, correctly-signed webhook deliveries (signed with the app's single shared `api_secret_key`). They can replay that exact body/HMAC pair to the app's webhook endpoint while swapping the `shop-domain` (and/or `topic`/`webhook-id`) header to any victim shop domain. `Registry.process` will pass this forged `WebhookMetadata` (with attacker-chosen body but victim's shop) straight to the host application's registered handler, since nothing about the body's HMAC constrains which shop it's allowed to be attributed to. This is a cross-tenant data-integrity/identity-spoofing issue at the SDK layer — the host application built on top of this gem has no way to detect the forgery because the gem itself asserts the data is authentic for `request.shop`.

### Likelihood Explanation
Requires only: (1) the ability to install/run the app for at least one shop (the normal, unprivileged onboarding flow for a public app), and (2) the ability to POST an HTTP request to the app's public webhook endpoint with custom headers — both trivially available to an ordinary internet user, no leaked secrets or privileged access needed.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the signable string used for HMAC computation, or otherwise cryptographically bind the shop identity to the signed payload (e.g., verify it against a value looked up server-side rather than trusting the header). At minimum, document that `request.shop`/`topic` are not authenticated by `HmacValidator.validate` and must not be used for tenant attribution without an independent check.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering Shopify to send a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures this request and resends it to the app's public webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and optionally the body content within what they control, e.g. a `customers/data_request` or `orders/create` style JSON payload with victim-relevant IDs), keeping the same `hmac-sha256` header if body is unchanged, or reusing an intercepted body.
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `Digest.hexencode(...)` against the raw body, which was never modified.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` to the app's handler, which now believes the (attacker-supplied) payload legitimately originates from `victim-shop.myshopify.com`.
