### Title
Unbounded k-invariant assertion in `calc_take_pnl` permanently disables Deposit/Withdraw/WithdrawPnl once precision drift trips it - (File: `program/src/processor.rs`)

### Summary
This is the closest reachable analog to the referenced "interest rate too high disables repay" bug class: a hard, unmitigated assertion inside a core accounting routine that, once tripped, causes every future call that depends on it to revert, permanently freezing user/LP funds. In `UToken`, the failure mode was an admin-settable rate exceeding a hardcoded ceiling in `borrowRatePerBlock()`. In this program, the analogous failure mode is the strict, non-tolerant invariant check in `Processor::calc_take_pnl`, which every unprivileged `Deposit`, `Withdraw`, and `WithdrawPnl` call depends on.

### Finding Description
`Processor::calc_take_pnl` is invoked by `process_deposit`, `process_withdraw`, and `process_withdrawpnl` — all reachable from a single transaction submitted by an unprivileged swapper/LP with attacker-influenced vault balances (via prior swaps) [1](#0-0) [2](#0-1) .

The function computes the current pool value product and compares it, with no tolerance/slack, against the stored `target.calc_pnl_x * target.calc_pnl_y` baseline: [3](#0-2) 

If the current product is even marginally below the stored baseline, the function returns `AmmError::CalcPnlError` instead of gracefully handling the discrepancy: [4](#0-3) 

The values being compared are derived through repeated fixed-point decimal conversions (`normalize_decimal_v2` / `restore_decimal`), which use integer (floor) division and therefore lose precision on every deposit/withdraw cycle: [5](#0-4) 

Because `target.calc_pnl_x`/`calc_pnl_y` (the baseline) are rewritten after every deposit/withdraw using truncated, restored values [6](#0-5) , repeated legitimate deposit/withdraw activity by ordinary, unprivileged accounts can accumulate rounding drift until the live pool value product falls (even by 1 unit) below the recorded baseline product. At that point `calc_take_pnl` unconditionally errors out.

### Impact Explanation
Since `calc_take_pnl` is called on the hot path of `Deposit`, `Withdraw`, and `WithdrawPnl` [7](#0-6) , once the assertion trips there is no way for any LP to withdraw liquidity or for the pool to settle pnl again — this is a **permanent freeze of all LP funds** in the affected pool, matching the "concrete permanent freezing of user or LP funds" bar. Swaps are unaffected (they don't call `calc_take_pnl`), so the pool would remain tradeable while liquidity providers are permanently locked out of withdrawing — a severe, fund-locking DoS reachable purely through normal deposit/withdraw usage, not through any privileged action.

### Likelihood Explanation
This does not require a malicious admin or privileged signer — it can be triggered purely by normal usage of `Deposit`/`Withdraw` by unprivileged LPs over time, because the check has zero tolerance for the inherent truncation in `normalize_decimal`/`restore_decimal`. The likelihood scales with pool activity (number of deposit/withdraw cycles) and with the difference between `native_decimal` and `sys_decimal_value` (larger decimal gaps amplify truncation), which are set at pool `Initialize2` time and not adjustable afterwards. This is a real, code-level design flaw analogous to the missing bound-check in `FixedInterestRateModel::setInterestRate()`, but here the trigger is protocol-native precision loss and repeated legitimate activity rather than an admin decision.

### Recommendation
Add a bounded tolerance (epsilon) to the `calc_take_pnl` invariant comparison instead of a strict `>=` check, so that small precision-induced discrepancies do not cause an unrecoverable protocol error. Alternatively, when the check would fail due to rounding, clamp/resync `target.calc_pnl_x`/`calc_pnl_y` to the current values rather than reverting, and add a recovery path (e.g., an admin/permissionless "resync" instruction) so a single stuck state cannot permanently block withdrawals.

### Proof of Concept
Exact numeric proof of drift crossing zero could not be fully derived within the available tooling/time (this would require simulating many deposit/withdraw cycles with specific decimal configurations to confirm the exact number of iterations needed to trip the assertion). The structural root cause, however, is directly verifiable in code:
1. `normalize_decimal`/`restore_decimal` use floored integer division, discarding remainders on every conversion [8](#0-7) .
2. `calc_take_pnl` performs a strict `>=` comparison with no tolerance and hard-errors otherwise [9](#0-8) [10](#0-9) .
3. This function is unconditionally called by `process_deposit` and `process_withdraw` [1](#0-0) , both instructions callable by any unprivileged account with LP tokens or deposit funds, meaning a persistent error here freezes ordinary user-facing functionality without any admin involvement.

I was unable to fully confirm the precise magnitude/frequency of drift needed to trigger the failure (would require running the on-chain math with concrete `pc_decimals`/`coin_decimals`/`sys_decimal_value` values across many cycles), so I present this as a structural/design-level analog rather than a confirmed exploit sequence.
