### Title
Webhook Shop Domain Not Covered by HMAC, Enabling Cross-Tenant Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body. The `shop` value, taken directly from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header, is never included in the signed content, yet it is handed to the app's webhook handler as the authoritative tenant identifier.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` covers exclusively the JSON payload: [1](#0-0) 

The `shop` accessor, however, reads straight from the request headers with no cryptographic binding to that signature: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app-supplied handler: [3](#0-2) 

Documentation instructs app authors to treat `data.shop` as the authenticated identity of the merchant that triggered the event, and to key business logic/job enqueueing off it directly: [4](#0-3) 

Because `shop` is excluded from `to_signable_string`, the equality the library implicitly guarantees — "HMAC valid" ⇒ "shop header is authentic" — does not hold. Any bytes verified by the HMAC (the body) are decoupled from the bytes the handler acts on for tenant attribution (the `shop` header).

### Impact Explanation
An attacker who can obtain any one validly-signed webhook delivery (e.g., by installing the target app on a shop they control, or by capturing a webhook in transit to an endpoint they can also reach) can replay that exact body with the `x-shopify-shop-domain` header swapped to a different, victim shop's domain. `Utils::HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` forwards the attacker-chosen `shop` to the handler as though Shopify had certified it. If the host application uses `data.shop` to scope database writes, credential lookups, or job dispatch (as the gem's own documentation recommends), this results in cross-tenant data injection/corruption — the handler applies attacker-supplied data under another merchant's identity, i.e. cross-tenant access.

### Likelihood Explanation
The gem's own documentation and `WebhookHandler` examples instruct developers to trust `data.shop` directly, so this pattern is expected to be widespread among consumers of this library, and the reused/rewritten request requires no possession of `api_secret_key`, access token, or any other privileged credential — only one legitimately-signed webhook body.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values in the HMAC-signed content, or otherwise cryptographically bind them to the body before `Registry.process` uses them, so that tampering with the `shop` header while replaying a valid body invalidates the signature.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook: body `{"id":1}`, headers include `x-shopify-hmac-sha256: <valid-for-body>` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only (`to_signable_string`) — it matches because the body is unchanged.
4. `Registry.process` builds `WebhookMetadata.new(shop: request.shop, ...)` with `shop == "victim.myshopify.com"` and invokes the app's handler, which processes/records data `{"id":1}` under the victim's tenant identity, despite it never having come from Shopify for that shop.

```ruby
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
```
