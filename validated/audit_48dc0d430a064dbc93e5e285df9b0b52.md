This confirms the vulnerability path. The `Registry.process` method verifies the HMAC over `raw_body` only [1](#0-0) , while `topic`, `shop`, `webhook_id`, and `api_version` are all read directly from HTTP headers that are never part of the signed data [2](#0-1) . `Registry.process` then trusts `request.shop` as the tenant identifier passed to the app's handler [3](#0-2) . This is a legitimate identity-binding break matching the report's bug class: "bytes verified versus bytes parsed" — the HMAC verifies `raw_body` bytes, but the `shop` byte range (an HTTP header) is parsed independently and never included in `to_signable_string`.

### Title
Webhook `shop` (and `topic`/`webhook_id`) header fields are not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , so `Utils::HmacValidator.validate` verifies only the body bytes against Shopify's `X-Shopify-Hmac-Sha256` signature [4](#0-3) . The `shop`, `topic`, and `webhook_id` values consumed by `Registry.process` come from separate HTTP headers (`shop-domain`, `topic`, `webhook-id`) that are not part of the signed payload [2](#0-1) .

### Finding Description
`Registry.process(request)` only checks `Utils::HmacValidator.validate(request)` before dispatching to the registered handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [3](#0-2) . Because `hmac` validation only covers `@raw_body`, the equality the gem implicitly assumes — "the shop attributed to this webhook == the shop whose secret produced this signature" — is never enforced for the `shop` header. An attacker who has captured or replayed one genuine `(raw_body, hmac)` pair signed by the app's own `client_secret` (e.g., from a webhook belonging to their own development/test store, or any store's webhook they can observe) can resend the exact same body and HMAC value while substituting an arbitrary `shopify-shop-domain` (and `shopify-topic`/`shopify-webhook-id`) header. `HmacValidator.validate` will pass because the body bytes and signature still match; `Registry.process` will then hand the handler a `WebhookMetadata` whose `shop` is fully attacker-controlled and unrelated to the actual signing key owner.

### Impact Explanation
Downstream host applications are documented to use `data.shop` directly as the tenant/session key to persist or act on webhook data (per the gem's own webhook handler example using `shop_domain: data.shop`) [5](#0-4) . Since the gem itself provides no binding between the verified bytes (body) and the trusted identity field (`shop`), any host app that follows the gem's documented contract inherits cross-tenant confusion: webhook data can be attributed to (and written under) a shop that never sent it, satisfying the "cross-tenant access" impact criterion.

### Likelihood Explanation
Exploitation requires possession of one valid `(raw_body, hmac)` pair for any shop signed with the app's own credentials (e.g. the attacker's own installed test shop sending itself a webhook, which is trivially available to any merchant who installs the app). No access to `api_secret_key` itself is needed — only a previously observed, legitimately-signed webhook request. The `shop`, `topic`, and `webhook_id` headers can then be freely rewritten by the attacker (as an "unprivileged internet user" sending a forged HTTP request to the app's public webhook endpoint) without invalidating the signature, since none of these fields are included in `to_signable_string`.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the HMAC-signed material (or independently verify them via a separate mechanism, e.g., an authenticated lookup instead of trusting the header directly), so that `to_signable_string` binds all fields the application acts upon, not just the raw body.

### Proof of Concept
1. Install the app on shop A (attacker-controlled) and capture a legitimate webhook request Shopify sends to the app for shop A: raw body `B`, header `shopify-hmac-sha256: H` (valid signature of `B` under the app's `client_secret`), `shopify-shop-domain: shop-a.myshopify.com`.
2. Replay this exact request to the app's webhook endpoint, but replace the `shopify-shop-domain` header with `shop-b.myshopify.com` (a victim shop that also has the app installed) — leaving `raw_body` and `shopify-hmac-sha256` unchanged.
3. `ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` are computed purely from the body [6](#0-5) ; `HmacValidator.validate` succeeds because `B` and `H` still match.
4. `Registry.process` dispatches to the app's handler with `WebhookMetadata(shop: "shop-b.myshopify.com", body: B, ...)` [7](#0-6) , causing the host application to process/store attacker-controlled data under shop B's tenant identity.
