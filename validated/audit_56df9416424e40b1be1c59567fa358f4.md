### Title
Unbounded UniswapV2 swap deadline (`block.timestamp`) in fee-payment swaps on `EvmHost.dispatch` and `IntentGatewayV2.placeOrder` — ([File: evm/src/core/EvmHost.sol], [File: evm/src/apps/IntentGatewayV2.sol])

### Summary
Both `EvmHost.dispatch(DispatchGet)` and `IntentGatewayV2.placeOrder` perform an on-the-fly UniswapV2 `swapETHForExactTokens` to convert user-supplied native token into the protocol fee token, passing `block.timestamp` as the swap's `deadline` argument.

### Finding Description
When a caller pays Hyperbridge dispatch fees (or IntentGateway order fees) with native ETH instead of the fee token directly, the contract swaps ETH for an exact amount of fee token via the local UniswapV2 router, using `block.timestamp` as the deadline: [1](#0-0) 

The same pattern recurs in the intent gateway's fee-escrow logic, reached from the unprivileged, user-facing `placeOrder` entrypoint: [2](#0-1) 

Because `block.timestamp` is evaluated at the moment the transaction is actually mined (not when it is signed/submitted), it can never be stale relative to execution — the deadline check is a no-op equivalent to passing `type(uint256).max`. A transaction can therefore sit in the public mempool (or be deliberately delayed/reordered by a builder/searcher) and still execute, at whatever price prevails at that later block, without reverting. This is the exact bug class flagged in the referenced Tokemak report for `BalancerV2Swap.sol`/`UniV3Swap.sol`.

### Impact Explanation
Both swaps are exact-output (`swapETHForExactTokens`): the output amount (`get.fee` / `order.fees`) is fixed, and the caller's `msg.value` acts as the maximum input. Because there is no real time bound on execution, the swap can be delayed and sandwiched/executed at an unfavourable price up to the full `msg.value` supplied, consuming more ETH than the price at submission time would have required. The excess is what gets refunded to the caller (`msgValue -= amounts[0]` in `IntentGatewayV2.sol`, similar logic in `EvmHost.sol`), so a worse execution price directly reduces the caller's refund — a quantifiable loss of user funds extracted via MEV, on every native-fee dispatch and every native-fee order placement, i.e. on a core, unprivileged, user-reachable dispatch/escrow path.

### Likelihood Explanation
Any unprivileged user can trigger this by calling `EvmHost.dispatch` (GET request) or `IntentGatewayV2.placeOrder` with `msg.value > 0` for fee payment — both are ordinary, permissionless entrypoints used on every dispatch/order that opts to pay fees in native token. Exploitation only requires an MEV searcher/builder observing the pending transaction and reordering/delaying it, which is standard, low-cost MEV tooling.

### Recommendation
Do not use `block.timestamp` as the swap deadline. Accept a caller-supplied `deadline` parameter (or a bounded relative offset) on `dispatch`/`placeOrder`, and pass that value to `swapETHForExactTokens`, so a transaction that sits too long in the mempool reverts instead of executing at a stale/manipulated price. Additionally consider allowing callers to specify a maximum acceptable input (slippage bound) rather than relying solely on `msg.value` as the implicit cap.

### Proof of Concept
1. Attacker/user calls `EvmHost.dispatch{value: X}(get)` (or `IntentGatewayV2.placeOrder{value: X}(order, graffiti)` with `order.fees > 0`), where the ETH→feeToken swap is exact-output for `get.fee`/`order.fees`.
2. A searcher observes the pending transaction and either delays its inclusion or sandwiches it, moving the ETH/feeToken pool price unfavourably.
3. Because `deadline = block.timestamp` is satisfied trivially at inclusion time, `swapETHForExactTokens` still executes rather than reverting, consuming more ETH from `msg.value` than it would have at submission time.
4. The caller receives a smaller refund of unspent ETH than expected, with the difference captured by the searcher — a direct, repeatable value extraction on every native-fee dispatch/order.
