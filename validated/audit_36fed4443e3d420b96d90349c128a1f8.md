### Title
Unprivileged intent order can drain a Simplex filler via unguarded Uniswap V4 pool-price manipulation - (File: sdk/packages/simplex/src/strategies/fx.ts)

### Summary
`FXFiller.resolveLegRates` prices any curveless, USD-stable-anchored intent leg directly from the live Uniswap V4 pool spot price (`getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd`, derived from `sqrtPriceX96`), the same "trust the pool's instantaneous reserves/price" pattern that let the RES attacker inflate a payout via flash-swap-manipulated AMM reserves. ### Finding Description
The mitigation, `checkPriceGuard`, is optional: a chain with no configured `referencePrice`/`maxDeviationBps` pair is left "unguarded" and every pool quote passes unconditionally. [3](#0-2) [4](#0-3)  Even with the guard set, it only bounds against a static reference deviation, not against execution/impact cost, and the code explicitly notes the pool's own fee tier is read but never applied — "there is no size or impact term" so `computeLegPolicyOutput` "extends the mid linearly across the whole priced quantity," meaning an attacker who moves the pool's tick within the same block (a flash-swap, exactly as in the RES exploit) can push the quoted rate to whatever value clears the static band. [5](#0-4)  A single intent order submitted by an unprivileged user is enough to trigger the fill/quote path against this manipulated price, since `FXFiller.evaluateOrder` pays out `targetOutput = policyMaxOutput` computed from this same rate and the "overfill clamp" that used to bound loss from "a manipulated venue price" is explicitly disabled ("NOTE: this removes the per-leg loss bound that previously protected against a bug / stale cache / manipulated venue price. Output is no longer capped; we only emit a warning."). [6](#0-5) 

### Impact Explanation
A pool manipulated via a flash loan (identical mechanics to the RES `pancakeCall` flash-swap sequence) immediately before an intent order is filled causes the Simplex solver to compute an inflated `policyMaxOutput` and pay it out via `IntentGateway.fillOrder`/escrow release, letting the attacker extract solver-owned funds (stablecoin/exotic-token inventory) for far less input than the true market rate. This is compounded by the removed overfill clamp, which the code's own comment identifies as the exact defense against "a manipulated venue price."

### Likelihood Explanation
Likelihood depends on operator configuration: the price guard is optional and, per the docs, only two fields need to be omitted together to leave a chain fully unguarded, and even when configured the guard does not account for pool-fee/impact cost, so a well-funded flash-loan attacker within the deviation band still profits. Given intents are open to any unprivileged submitter and pool state is externally observable/manipulable pre-fill, this is a realistically reachable path once a chain runs venue (pool) pricing without a guard, or with a loosely-set deviation band.

### Recommendation
Make the price guard mandatory whenever venue (pool) pricing is enabled rather than optional; incorporate the pool's fee tier and a size/impact term into `computeDirectPoolPriceUsd`/`computeLegPolicyOutput` rather than a linear mid-price extension; and reinstate an enforced (non-warn-only) overfill ceiling tied to the manipulated-price risk that the removed clamp used to cover.

### Proof of Concept
1. Operator runs Simplex with `[vault.uniswapV4]` positions configured for a pair, without `referencePrice`/`maxDeviationBps` (an explicitly supported, unguarded configuration). [7](#0-6) 
2. Attacker flash-loans the exotic token/stable pair on the same Uniswap V4 pool the filler reads, moving `sqrtPriceX96`/tick sharply in the attacker's favor within one block.
3. Attacker (or an accomplice) submits an `IntentGateway` order matching the manipulated pair; `FXFiller.evaluateOrder`/`resolveLegRates` reads the manipulated pool price with no guard rejecting it. [8](#0-7) 
4. `computeLegPolicyOutput` linearly extends the manipulated mid across the full order size (no impact term), producing an inflated `policyMaxOutput`; the disabled overfill clamp lets the solver pay it in full. [6](#0-5) 
5. Solver funds transfer out via `fillOrder`; attacker unwinds the flash loan, netting the difference between the manipulated and true price.

```typescript
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}
```

```typescript
		// would just be the asset's own USD price, not a spread).
		const curveless = !leg.pair.bidPricePolicy && !leg.pair.askPricePolicy

				// the venue-specific defense.
```

```markdown
# Venue pricing (Uniswap V4 funded pairs)

Verified 2026-08-19.

```
resolveLegRates(...)
  curveless pair && token0 is a USD stable
    -> venuePriceMemo() -> getVenueUsdPrice(chain, token1)
         -> UniswapV4FundingPlanner.getExoticTokenPrice
              picks the position with the largest pool liquidity
              -> computeDirectPoolPriceUsd -> sdkPool.token0Price / token1Price
    -> checkPriceGuard(...)   reject if outside maxDeviationBps of the static reference
    -> rate = 1 / venueUsd
  otherwise -> the pair's ask/bid curve at the leg's notional
```

`computeDirectPoolPriceUsd` returns the **raw pool mid** derived from `sqrtPriceX96`. The pool's
fee tier is read and stored on the hydrated position (`pos.fee`) but never applied to the price,
and there is no size or impact term — `computeLegPolicyOutput` extends the mid linearly across the
whole priced quantity. `checkPriceGuard` is the only defense on this path, and it checks deviation
from a static reference, not execution cost. A venue-priced pair that has to swap through its own
pool to source inventory pays a fee tier it never quoted against.
```

```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```
