## Title
Webhook `shop-domain` header is trusted for tenant routing but is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop` is read straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `Registry.process` validates only the body's HMAC via `Utils::HmacValidator.validate(request)` and then dispatches `WebhookMetadata.new(..., shop: request.shop, ...)` to the app's handler without ever binding `shop` to the signature [3](#0-2) .

### Finding Description
`HmacValidator.validate` computes `HMAC-SHA256(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` field via `OpenSSL.secure_compare` [4](#0-3) . For webhooks, `to_signable_string` is defined as `@raw_body` only [1](#0-0) . The `shop` accessor, however, is derived independently from the `shop-domain` header, which plays no role in the signed string [2](#0-1) .

Because a single app has one shared `api_secret_key` used to sign webhooks for *every* shop that installs it, any body+hmac pair that is valid for one shop is also a valid body+hmac pair for a request that merely swaps the `shop-domain` header to a different shop — the signature check in `Registry.process` cannot detect this, since it only verifies the body [5](#0-4) . The resulting `WebhookMetadata` passed to the app's `handler.handle` therefore carries an attacker-chosen `shop` value alongside a body that was legitimately produced (and HMAC-signed) for a different tenant [6](#0-5) .

This is exactly the "field acted on but not covered by the HMAC" identity-binding failure named in the bug-class rules: the equality that should hold is `hmac-covers(shop) == shop-used-for-tenant-routing`, but here `hmac-covers(shop) = false`.

### Impact Explanation
An unprivileged attacker who can install the app on their own store (a normal, non-privileged action available to any Shopify user) receives legitimately HMAC-signed webhooks for their own shop's events. By resending that exact `(raw_body, hmac)` pair to the app's webhook endpoint while overriding the `shopify-shop-domain` header to name a victim shop, the attacker gets the app to accept and process attacker-controlled webhook data *as if it originated from the victim's shop*. Any webhook handler that trusts `WebhookMetadata#shop` for tenant-scoped side effects (updating shop-keyed records, disabling/enabling features, writing to the victim's session/store row, etc.) is exposed to cross-tenant data confusion — the impact bucket "cross-tenant access" (Critical) as defined by the assessment rules.

### Likelihood Explanation
Likelihood is moderate-to-high for any integrator relying on the gem's default `Webhooks::Registry`/`Request` flow: the attacker needs no secret, no privileged account, and no TLS interception — only the ability to install the app on a shop they control (which is the app's normal, expected usage) and the ability to send an HTTP POST with a crafted header to the app's public webhook endpoint. The only unknowns are host-application specifics (whether the handler code actually keys sensitive actions by `data.shop` without additional server-side checks); this gem's contract, however, hands the unauthenticated `shop` value straight through as trusted metadata.

### Recommendation
Bind the `shop` identity into the HMAC-verified material for webhook requests — e.g., include the `shop-domain` header (and ideally `topic`/`webhook-id`) in `to_signable_string`, or independently verify that the header-derived shop matches a shop value embedded in the signed body/payload before it is exposed via `WebhookMetadata`. At minimum, document loudly that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant-scoping without an out-of-band check.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook-eligible event (e.g., `orders/create`), causing Shopify to send a webhook signed with the app's real `api_secret_key`:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body>`
   - Body: attacker-controlled JSON (attacker fully controls the order/content on their own store).
2. Attacker replays the identical `raw_body` and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only [5](#0-4)  — this still matches because the body was untouched.
4. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled body>, ...)` [7](#0-6) , causing the app to process attacker-supplied data under the victim's tenant identity.
