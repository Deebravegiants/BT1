### Title
Fee-on-transfer ERC20 as `WrappedHyperFungibleToken` underlying causes over-crediting on the destination chain, draining the wrapper's escrow - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken.send()` assumes that the amount pulled via `safeTransferFrom` equals the amount actually received by the contract, then dispatches a cross-chain message advertising the full requested `params.amount` as locked. If the underlying ERC20 is a fee-on-transfer token, the contract's balance increases by less than `params.amount`, but the destination-chain peer still unlocks/releases the full `params.amount` to the beneficiary, exactly matching the root cause of the referenced report (assuming transferred amount == received amount).

On the destination chain, `onAccept` unconditionally transfers out `message.amount` (the originally requested amount, not the actual amount locked): [4](#0-3)

### Impact Explanation
Each cross-chain send of a fee-on-transfer token locks `params.amount - fee` on the source chain but instructs the peer to release the full `params.amount` on the destination chain. Over repeated sends, the wrapper contract's actual token custody is systematically less than the sum of amounts it has promised to release across all chains. This is a real accounting shortfall (unbacked release of funds) that inevitably empties the escrow faster than deposits back it, ultimately causing legitimate later redemptions/unlocks to fail (funds get stuck) or, if the wrapper holds a shared pool for multiple underlying transfers, allows early actors effectively to redeem more value than they deposited at the expense of later users. This satisfies "concrete theft / permanent freezing of funds / unsound state commitment" since the commitment message asserts an amount that was never fully escrowed.

### Likelihood Explanation
Any owner/user can configure or use `WrappedHyperFungibleToken` with an arbitrary ERC20 as `_underlying` (set once via `configure()` by the owner, but the risk manifests for any unprivileged user calling `send()` afterward). No special privilege is needed to trigger the bug once a fee-on-transfer token is configured as the underlying — a single ordinary `send()` transaction reliably reproduces the shortfall. The codebase demonstrates it is aware of and actively mitigates this exact bug class elsewhere (`IntentGatewayV2`, with dedicated `FeeOnTransferToken` tests), showing the gap here is not a rejected design choice but a missed instance of the same class.

### Recommendation
Mirror the `IntentGatewayV2` pattern: measure `IERC20(_underlying).balanceOf(address(this))` before and after `safeTransferFrom`, use the actual received delta as the locked amount, and embed that delta (not `params.amount`) into `HyperFungibleToken.Message.amount` dispatched to the destination. Alternatively, explicitly document/enforce (e.g., via a whitelist or a transfer-amount assertion that reverts on any mismatch) that fee-on-transfer/rebasing tokens are unsupported as the underlying for `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken`, `configure()` it with `_underlying` set to a fee-on-transfer ERC20 (e.g. 1% fee), and register a peer contract on a destination chain via `addChain`.
2. User approves `1000e18` tokens and calls `send({ amount: 1000e18, dest: chainB, to: beneficiary, ... })`.
3. `safeTransferFrom(msg.sender, address(this), 1000e18)` actually credits the contract only `990e18` (1% fee burned/redirected) — confirmed by the `FeeOnTransferToken` test harness behavior already present in the repo test suite: [7](#0-6) 
4. `_buildDispatchPost` still encodes `amount: 1000e18` in the message body (line 241), and this message is dispatched and eventually delivered to the destination-chain `onAccept`.
5. On chain B, `onAccept` calls `IERC20(_underlying).safeTransfer(beneficiary, 1000e18)` — releasing `1000e18` even though only `990e18` was ever locked on chain A, leaving the wrapper permanently under-collateralized by `10e18` per such transfer.

    function _buildDispatchPost(HyperFungibleToken.SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(HyperFungibleToken.Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }
