### Title
`claim_swap` treats partial best-effort repatriation as full success, corrupting swap finality - (File: substrate/frame/atomic-swap/src/lib.rs)

### Summary
`claim_swap` determines success solely from `swap.action.claim(...)` returning `true`, and `BalanceSwapAction::claim` maps success to `C::repatriate_reserved(...).is_ok()`. Because `repatriate_reserved` is a `BestEffort`/`Polite` operation that can legitimately return `Ok(remaining_amount)` when only part of the reserved balance was actually moved (e.g. due to a freeze/lock on the source account), `claim_swap` unconditionally deletes the `PendingSwaps` entry and emits `SwapClaimed { success: true }` even when the target received less than the promised `value`.

### Finding Description
`claim_swap` reads the pending swap, then calls: [1](#0-0) 

The actual claim logic in `BalanceSwapAction::claim` is: [2](#0-1) 

`is_ok()` only checks that the call didn't error — it ignores the returned `Balance` remainder. `ReservableCurrency::repatriate_reserved` is explicitly documented as best-effort: "As much funds up to `value` will be deducted as possible... If this is less than `value`, then `Ok(non_zero)` will be returned", as seen in the trait doc: [3](#0-2) 

The pallet-balances implementation confirms `Ok(value.saturating_sub(actual))` is returned regardless of whether `actual == value`: [4](#0-3) 

`do_transfer_reserved` uses `Precision::BestEffort` and caps `actual` at `reducible_total_balance_on_hold(slashed, Polite)`, which is reduced by any freeze/lock that overlaps the held balance: [5](#0-4) [6](#0-5) 

This exact partial-transfer semantics is demonstrated in the existing test `frozen_hold_balance_best_effort_transfer_works`, where a source with a hold of 9 and a freeze of 5 only transfers 4 out of a requested 10, yet the call returns `Ok`: [7](#0-6) 

Exploit flow:
1. Source (attacker) calls `create_swap`, promising `target` a `value` reward, reserving `value` from their free balance via `action.reserve(&source)`.
2. Before the target claims, the source (fully unprivileged, using their own signed extrinsics) places a freeze/lock on their own account via any pallet that supports `fungible::MutateFreeze`/legacy locks (e.g. staking bond, vesting, or a custom pallet), sized so that `reducible_total_balance_on_hold(source, Polite)` is less than the swap's reserved `value`.
3. Target reveals the proof and calls `claim_swap`. `swap.action.claim` invokes `repatriate_reserved` which is capped by the frozen amount and only transfers part of `value` to the target, but returns `Ok(remaining)` (remaining > 0).
4. `succeeded = true` (`is_ok()`), so `claim_swap` unconditionally removes the `PendingSwaps` entry and emits `SwapClaimed { success: true }`.
5. The target — and any downstream/off-chain logic relying on the `success: true` event or absence of the swap entry — believes the swap fully settled, while in reality only a fraction of the promised funds moved. The rest remains reserved on the source's account.
6. Because the `PendingSwaps` entry is now gone, `cancel_swap` returns `Error::NotExist` for both source and target, so there is no on-chain path to reconcile or force the remaining reserved balance to be delivered or returned to free balance. The leftover reserved amount is stuck, un-spendable and undeliverable, permanently — it is neither returned to the source's free balance nor delivered to the target.

No check in `claim_swap` or `BalanceSwapAction::claim` verifies that the `Balance` remainder returned by `repatriate_reserved` is zero. This is the same bug class that was fixed in `pallet-assets::transfer_ownership` (see `prdoc/pr_12366.prdoc`), which now explicitly checks `remaining.is_zero()` and rejects the dispatch with `IncompleteDepositTransfer` otherwise: [8](#0-7) 
The atomic-swap pallet has no equivalent guard.

### Impact Explanation
An unprivileged source account can use a self-inflicted freeze/lock to short the counterparty in an atomic swap while the on-chain event and removed pending-swap state falsely signal full success. This is a concrete instance of "theft of user funds": the target (victim) receives less than the agreed `value`, believes the swap is finalized (`success: true`, entry removed), and has no recourse — `cancel_swap` is unreachable post-removal, and the shorted remainder stays reserved (locked) on the source's account indefinitely with no pallet-exposed path to release it.

### Likelihood Explanation
This is fully reachable by a normal signed user with no special privileges: `create_swap` and `claim_swap` are both plain signed extrinsics, and applying a freeze/lock to one's own account (e.g. via staking, vesting, or any `fungible::MutateFreeze` consumer) is a normal, unprivileged operation. The attack requires only that the source apply the freeze before the target claims, which the source fully controls the timing of. It is deterministically repeatable given any runtime that includes atomic-swap alongside a lock/freeze-capable pallet on the same `Currency`.

### Recommendation
In `BalanceSwapAction::claim`, capture the `Balance` remainder returned by `repatriate_reserved` and treat the claim as successful only if the remainder is zero (mirroring the `pallet-assets::transfer_ownership` fix). Alternatively, change `SwapAction::claim` to return a `Result` carrying the shortfall, and in `claim_swap`, if the shortfall is non-zero, either fail the whole dispatch (rolling back reservation state) or retain the `PendingSwaps` entry (reduced by the amount already delivered) so `cancel_swap`/a retried `claim_swap` can still resolve the remaining reserved balance instead of unconditionally deleting the entry.
