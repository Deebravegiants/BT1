Audit Report

## Title
Unbounded `web_api_trigger` registrations combined with unbounded caller-supplied `Topics` cause O(N×M) DoS in the WebAPI Trigger gateway handler - (File: core/capabilities/webapi/trigger/trigger.go)

## Summary
`triggerConnectorHandler.RegisterTrigger` places no cap on the number of entries added to `h.registeredWorkflows`, and `processTrigger` — invoked for every inbound `web_api_trigger` gateway message — performs a nested loop over all registered triggers and every caller-supplied `payload.Topics` entry, with no limit on `len(topics)` before the loop executes. This produces unbounded `O(len(registeredWorkflows) * len(Topics))` per-request cost that a normal (non-privileged) tenant can trigger by sending a message with a very large `Topics` array, potentially delaying gateway responsiveness for other tenants sharing the same handler.

## Finding Description
`RegisterTrigger` inserts into the shared map with no maximum-size check: [1](#0-0) 

`HandleGatewayMessage` decodes the untrusted payload and immediately dispatches to `processTrigger` for `MethodWebAPITrigger` messages, with no validation of `len(payload.Topics)`: [2](#0-1) 

`processTrigger` snapshots all registered triggers and iterates them against every topic in the caller-controlled `topics` slice, with no size guard analogous to `maxBatchedWorkflowIDs` used in `core/capabilities/remote/trigger_subscriber.go`: [3](#0-2) [4](#0-3) 

I confirmed by reading `core/services/gateway/handlers/capabilities/handler.go` that neither `HandleLegacyUserMessage` nor `HandleNodeMessage` impose any payload/body-size or topic-count limit before this path is reached; the only checks present are message staleness (`payload.Timestamp`) and method validation, not payload size.

## Impact Explanation
This is a resource-exhaustion / availability issue: a single caller able to reach the gateway's `web_api_trigger` endpoint can submit a message with an oversized `Topics` array, and because trigger count grows unboundedly with the number of deployed workflows, per-request CPU cost scales without bound. This can slow down or degrade gateway message processing for other tenants sharing the same DON/gateway handler instance. This is a legitimate Denial-of-Service class finding rather than an authentication/authorization bypass, fund-movement, or secret-exfiltration issue.

## Likelihood Explanation
No privileged role is required: registering a trigger only requires deploying a workflow using the `web_api_trigger` capability (an ordinary tenant action), and sending an oversized `Topics` payload only requires access to submit a `web_api_trigger` gateway message, which is the intended external-facing entry point. Both preconditions are realistically achievable by an unprivileged, single tenant, and the attack is trivially repeatable.

## Recommendation
- Cap the number of concurrently registered triggers in `RegisterTrigger`, returning an error once a configurable maximum is exceeded.
- Validate and cap `len(payload.Topics)` in `processTrigger` before the double loop, mirroring the `maxBatchedWorkflowIDs` truncation pattern in `core/capabilities/remote/trigger_subscriber.go`.
- Replace the O(N×M) linear scan with a topic-indexed lookup (e.g., `map[topic][]*webapiTrigger`) to avoid unbounded iteration cost entirely.

## Proof of Concept
1. Register a large number of `web_api_trigger` workflows via `RegisterTrigger` (no cap enforced), growing `h.registeredWorkflows` arbitrarily.
2. Send one JSON-RPC gateway message with `method: "web_api_trigger"` and a `TriggerRequestPayload.Topics` array containing tens of thousands of entries.
3. Observe that `processTrigger`'s nested loop (`core/capabilities/webapi/trigger/trigger.go` lines 106-156) consumes CPU/time proportional to `len(registeredWorkflows) * len(Topics)`, delaying processing of subsequent gateway messages for unrelated workflow owners routed through the same handler — verifiable via a Go benchmark/unit test that measures `processTrigger` latency as both `registeredWorkflows` size and `Topics` length scale up.
