### Title
Webhook `shop`, `topic`, `webhook_id` and `api_version` fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from raw HTTP headers, but `to_signable_string` — the data that `Utils::HmacValidator` actually authenticates — returns only the raw request body. `Registry.process` passes these unauthenticated header values straight to the app's webhook handler as the tenant-identifying `WebhookMetadata`, breaking the equality that should hold: `shop reported to the handler == shop that produced the signed payload`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers, independent of the signed body: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC exclusively over `to_signable_string`: [3](#0-2) 

`Webhooks::Registry.process` uses the *unauthenticated* header fields (`request.shop`, `request.topic`, `request.webhook_id`, `request.api_version`) to route the payload to a handler and to construct `WebhookMetadata`, which the app treats as the source-of-truth tenant identity for the event: [4](#0-3) 

The documentation confirms downstream apps rely on `data.shop` for tenant-scoped processing (e.g., enqueuing jobs keyed by `shop_domain`): [5](#0-4) 

Because the HMAC only binds the JSON body, the binding "`shop` header == shop that Shopify actually signed this payload for" does not hold. Any party that can obtain one legitimate `(raw_body, hmac)` pair signed by the app's secret — for example a merchant who has installed the app on their own store and can capture their own genuine webhook delivery — can replay that exact body/HMAC pair while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header, and any of `topic`/`webhook_id`/`api_version` headers, to a victim shop's domain. `HmacValidator.validate` still returns `true` because the signed body is unchanged, and `Registry.process` will then invoke the handler with `WebhookMetadata` claiming the event belongs to the victim shop.

### Impact Explanation
This breaks the tenant isolation the HMAC is supposed to guarantee: an app built on this gem cannot distinguish "genuine data for shop A" from "genuine payload replayed and falsely attributed to shop B." Depending on how the host app uses `data.shop` (e.g., writing customer/order data keyed by shop, redact/GDPR compliance topics such as `customers/redact` or `shop/redact`, billing-relevant topics), this enables cross-tenant data injection/corruption — one tenant's webhook can be forged to look like it originated from another tenant. This matches the Critical "cross-tenant access" category, since the shop-identity boundary that separates tenants is not authenticated.

### Likelihood Explanation
Exploitation requires the attacker to first obtain at least one legitimate `(body, hmac)` pair. The most realistic path is a party that already has an installed, low-privilege relationship with the app (e.g., a merchant who installs the app on their own store, an entirely unprivileged act from the app's perspective) capturing their own genuine webhook delivery and replaying it with a modified `shop-domain` header pointed at another tenant. No `api_secret_key`, access token, or `client_secret` is required — only observation of one's own legitimately-received webhook traffic, which is inherent to normal use of a multi-tenant app. This makes the attack realistically reachable by an unprivileged actor.

### Recommendation
Include the identity-relevant fields (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed material, or otherwise cryptographically bind the header values to the request (e.g., require the app to re-verify `shop` against a known/registered shop for that webhook subscription before trusting `WebhookMetadata`). At minimum, document prominently that `shop`, `topic`, `webhook_id`, and `api_version` are unauthenticated headers and must not be trusted for tenant-identification without additional verification (e.g., cross-checking against the shop associated with `webhook_id` via the Admin API, or maintaining a shop allowlist).

### Proof of Concept
1. Install the app on Shop A (fully legitimate, low-privilege merchant action).
2. Capture a genuine webhook delivery from Shopify to the app's HTTP endpoint for Shop A: raw body `B` and header `x-shopify-hmac-sha256: H` (valid over `B`), plus `x-shopify-shop-domain: shop-a.myshopify.com`.
3. Replay the exact same request to the app's webhook endpoint, keeping body `B` and `x-shopify-hmac-sha256: H` unchanged, but replacing `x-shopify-shop-domain` with `shop-b.myshopify.com` (a victim shop also using the app).
4. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/webhooks/registry.rb:190` returns `true` because it only checks `to_signable_string` (the unchanged body `B`).
5. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the forged `shop-b.myshopify.com` value and invokes the registered handler, which processes/stores the payload as belonging to Shop B — a cross-tenant data confusion the app cannot detect using this gem's verification alone.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
