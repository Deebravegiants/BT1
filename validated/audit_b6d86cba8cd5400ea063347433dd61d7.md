### Title
Weighted-median phantom price selection lets a solver holding majority output-token inventory set the on-chain-consumed quote verbatim - ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
`aggregatePhantomBids` weights each solver's quote for a phantom-order leg purely by that solver's balance of the leg's output token on the destination chain, then feeds the weighted set into `weightedMedian`, which is documented as a **selection, not a blend** — it returns one bidder's exact quoted integer. [1](#0-0) 
Any unprivileged EIP-7702-delegated solver — bidding is described as open to "anyone" who submits to the coprocessor, subject only to a signature/delegation check, not a permissioned allowlist — can acquire enough of a leg's output token to hold "over half the leg's weight," and the published price becomes exactly what that solver quoted. [2](#0-1) [3](#0-2) 

### Finding Description
This is the direct structural analog of the BonkDAO incident: instead of buying governance tokens to control a DAO vote, an attacker buys/acquires inventory of a specific ERC-20 (the leg's output token) on one destination chain to control a price-selection mechanism whose output is consumed by real, fund-moving transactions.

The published price is not merely informational — it is written to `PhantomOrderPriceSnapshotV2` and rolled up by `updateLiquidityPools` into a pool's `sellRate`/`buyRate`. [4](#0-3) 
That aggregate rate is the value `IndexedRateIntentQuoteStrategy`/`quoteIntent()` returns by default, and docs explicitly instruct integrators to use `quote.amountIn`/`quote.amountOut` **exactly as returned** when building a real `Order` for `placeOrder()`, which escrows real user funds on-chain. [5](#0-4) [6](#0-5) 

Because `weightedMedian` is a selection rather than an averaging/robust-statistic function, a single dominant-inventory solver does not need to merely influence the price — it sets it verbatim, and can do so with a temporary, purchasable, cheap inventory position in one output token on one chain (much cheaper than the $4M in the BonkDAO case, since inventory only needs to exceed 50% of the *other bidders'* weight for that specific leg, not the entire token supply).

### Impact Explanation
A manipulated median directly determines the `amountIn`/`amountOut` a user is told to use when escrowing tokens via `IntentGatewayV2.placeOrder`. An inflated or deflated published rate can induce users to escrow more input than the market rate justifies or accept less output than fair value, and could be paired with the attacker's own solver being positioned to fill the mispriced order — a concrete value-extraction/theft vector against real escrowed funds, reachable from a single submitted (fake, price-only) phantom bid rather than any privileged/governance action.

### Likelihood Explanation
Likelihood is moderate-to-high in principle: bidding is described as open to "anyone" (subject to a signature check and EIP-7702 delegation to `SolverAccount`), the manipulation cost scales only with the *other* bidders' weight on one leg/one chain (not global liquidity), and `weightedMedian`'s selection (not blending) behavior is explicitly acknowledged in the codebase's own documentation as a known, deliberate design property rather than a bug being tracked for a fix. However, exploitation still requires the attacker to (a) be able to delegate an EOA to `SolverAccount` and (b) accumulate dominant inventory of a specific output token on a specific chain at the moment of a phantom bid window, and to know that an integrator is currently defaulting to `indexed_rates`/`phantom_snapshot` for quoting rather than an independent price source — reducing but not eliminating practical likelihood.

### Recommendation
Do not let unbounded, unattested solver-declared inventory alone command majority weight on a price snapshot. Consider bounding any single solver's weight contribution per leg (a cap as a fraction of total leg weight), requiring a minimum number of independent solvers before a snapshot is published, or replacing pure `weightedMedian` selection with a method resistant to single-party domination (e.g., trimmed/quorum-weighted statistics), especially since this value feeds a default quote strategy used to size real on-chain escrow amounts.

### Proof of Concept
1. Attacker delegates an EOA to the chain's `SolverAccount` via EIP-7702 (a normal, permissionless onboarding step for any solver). [7](#0-6) 
2. Attacker acquires/holds a large balance of one leg's output token on the destination chain — enough to exceed the combined weight of all other bidders for that leg.
3. When a `PhantomOrderV2`'s bid window closes, the attacker submits a signed, verifiable phantom bid quoting an arbitrary (favorable-to-attacker) output amount for that leg.
4. `aggregatePhantomBids` verifies the bid (signature + delegation), computes the attacker's weight from its output-token balance, and because the attacker's weight exceeds 50% of the leg's total, `weightedMedian` selects the attacker's exact quoted price as `medianPrice`/`lowestPrice`/`highestPrice`. [8](#0-7) 
5. `updateLiquidityPools` rolls this into the pool's published `buyRate`/`sellRate`. [4](#0-3) 
6. Any user calling `quoteIntent()` (default `indexed_rates` strategy) receives the attacker-set rate and, per the SDK's own guidance, uses it verbatim to construct a real `Order` and calls `placeOrder()`, escrowing tokens at the manipulated rate. [9](#0-8)

### quoteIntent(params)

Quotes an intent from the latest aggregate pool buy or sell rate published by the indexer. The pool rate is depth-weighted from fresh chain samples. Pass token addresses directly—the SDK resolves their configured symbols and decimals. No `strategy` option is needed for indexed-rate quotes.

Indexed-rate quotes require an attached Hyperbridge indexer client. There is no automatic fallback to another price source.

Use `amountIn` and `amountOut` when constructing the `inputs` and `output.assets` for an IntentGateway V2 order.

```typescript lineNumbers
import { createQueryClient, IntentGateway } from "@hyperbridge/sdk";

const gateway = (await IntentGateway.create(source, dest)).withQueryClient(
  createQueryClient({ url: "https://nexus.indexer.polytope.technology" }),
);

const quote = await gateway.quoteIntent({
  tokenIn: "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
  tokenOut: "0x46C85152bFe9f96829aA94755D9f915F9B10EF5F",
  amountIn: 100_000_000n,
});

console.log(quote.amountIn, quote.amountOut);
if (quote.strategy === "indexed_rates") {
  console.log(quote.quoteMetadata.rateSide, quote.quoteMetadata.rate);
}
```

The order's source and destination chains select the configured token deployments. The SDK uses the pool's indexed buy rate when the order buys the quote token with the base token, and the indexed sell rate for the reverse direction. If that direction has no indexed rate, the quote fails clearly instead of using a different market.
