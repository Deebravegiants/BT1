### Title
Stale `TombStone.original_owner` in `object::burn`/`unburn` grants a prior owner a dormant reclaim right over an object after it has been legitimately transferred to a new owner - ([File: aptos-move/framework/aptos-framework/sources/object.move])

### Summary
Aptos's core `object` module implements a "soft burn" mechanic (`burn`/`unburn`) that tags an object with a `TombStone{original_owner}` resource without actually moving the object anywhere. Ordinary ownership transfers (`transfer`, `transfer_raw`, `transfer_call`) do not clear this tag - only privileged `TransferRef`-based transfers do. This lets a `TombStone` created by owner A survive an ordinary transfer of the object to a new legitimate owner B. If the object is later sent to the canonical `BURN_ADDRESS` (by B, or by any subsequent legitimate owner, which is the documented way to actually burn an object), the stale tag lets the *original* address A - not the actual last owner - reclaim the object via `unburn`.

### Finding Description
`object::burn` only asserts the caller is the *current* owner and installs a tombstone; it never transfers the object: [1](#0-0) 

`object::unburn` inspects the *current* owner of the object against two hard-coded cases: (1) current owner equals the caller (simple un-tag), or (2) current owner equals `BURN_ADDRESS`, in which case the *stored* `original_owner` inside the tombstone is checked against the caller and the object is transferred back to that stored address: [2](#0-1) 

Crucially, the only place a `TombStone` is ever cleared implicitly is inside `transfer_with_ref` (the `LinearTransferRef`-gated transfer path used for privileged, ref-based transfers): [3](#0-2) 

The ordinary, ungated transfer path - `transfer`, `transfer_to_object`, `transfer_call`, and the underlying `transfer_raw`/`transfer_raw_inner` used for everyday owner-signed transfers - never checks for or clears an existing `TombStone`: [4](#0-3) 

This produces a broken custody invariant: the `TombStone.original_owner` field is supposed to represent "the last legitimate owner who has the right to reclaim this specific burn," but it is never invalidated when ownership legitimately changes hands through the normal transfer path. The field becomes stale and grants unauthorized reclaim authority to a past holder.

### Impact Explanation
Concretely:
1. Owner A holds object O (could be an NFT/token object, an object wrapping a fungible store, or any object-held value).
2. A calls `object::burn(A, O)` - this only tags `TombStone{original_owner: A}` on O; A is still the owner.
3. A then legitimately sells/transfers O to B using an ordinary transfer (`object::transfer`, marketplace flow, etc.). The `TombStone{original_owner: A}` silently survives this transfer because `transfer_raw_inner` never inspects or clears it.
4. B, now the rightful owner, later performs an actual burn of O by sending it to `BURN_ADDRESS` (the documented mechanism for hard-burning objects, per the module doc referencing "burn_object_with_transfer").
5. At this point `unburn`'s second branch fires: current owner is `BURN_ADDRESS`, and the check is against the *stale* tombstone value A, not B. A (the previous, no-longer-legitimate owner) can call `unburn` and pass the `original_owner_addr == signer::address_of(original_owner)` check, causing `transfer_raw_inner(object_addr, A)` to send the object to A instead of it staying burned or belonging to whatever the true custody/recovery target should be.

This is a custody/ownership-control corruption: value (the object and everything it holds, e.g., a fungible store, NFT, or other object-held assets) is redirected to the wrong holder (a stale prior owner) instead of the true final owner or an intended recovery path, and it silently strips B's/the true owner's recovery rights over their own burned asset.

### Likelihood Explanation
The bug requires a specific but realistic sequence: an object must have been tagged by `burn()` by some owner and then transferred normally (rather than the tombstone being cleared, which only happens via `TransferRef`-based transfer) before a subsequent owner performs the "real" burn to `BURN_ADDRESS`. Any application or marketplace that (a) allows users to call `object::burn` freely (it's a public entry function requiring only current ownership) and (b) later moves objects to `BURN_ADDRESS` as part of a real burn/cleanup flow, without being aware that a leftover tombstone from a prior owner might still be attached, is exposed. Since `burn` is public and callable by any owner at any time with no requirement that the object subsequently be destroyed, and the object model widely supports composability (objects passed through marketplaces, NFT resale, generic transfer flows), this is a plausible, non-privileged attack path rather than a purely theoretical one.

### Recommendation
`transfer_raw_inner` (or `transfer_raw`) should clear any existing `TombStone` on the object whenever ownership legitimately changes via any transfer path, exactly as `transfer_with_ref` already does. Alternatively, `unburn`'s `BURN_ADDRESS` branch should track and validate against the *most recent* legitimate owner rather than a value that can become stale relative to intervening ordinary transfers, or `burn`/`unburn` should be redesigned so that a tombstone's reclaim right is invalidated as soon as the tagged object changes hands through any transfer mechanism.

### Proof of Concept
```move
// Pseudocode illustrating the exploit sequence using existing object.move APIs.

// 1. A owns object O.
object::burn(&A, O); // TombStone{original_owner: A} tagged; A still owns O.

// 2. A sells/transfers O to B via the ordinary transfer path (TombStone NOT cleared).
object::transfer(&A, O, address_of(&B));

// 3. B, the new legitimate owner, later performs a real burn by sending O to BURN_ADDRESS.
object::transfer_call(&B, object_address(O), BURN_ADDRESS);

// 4. A (a stranger with no current relationship to O) calls unburn and reclaims O,
//    because unburn's BURN_ADDRESS branch trusts the stale TombStone.original_owner = A.
object::unburn(&A, O); // succeeds: transfers O from BURN_ADDRESS back to A, not B.
```

    /// Transfer to the destination address using a LinearTransferRef.
    public fun transfer_with_ref(self: LinearTransferRef, to: address) {
        assert!(!exists<Untransferable>(self.self), error::permission_denied(EOBJECT_NOT_TRANSFERRABLE));

        // Undo soft burn if present as we don't want the original owner to be able to reclaim by calling unburn later.
        if (exists<TombStone>(self.self)) {
            let TombStone { original_owner: _ } = move_from<TombStone>(self.self);
        };

        let object = borrow_global_mut<ObjectCore>(self.self);
        assert!(
            object.owner == self.owner,
            error::permission_denied(ENOT_OBJECT_OWNER),
        );
        event::emit(
            Transfer {
                object: self.self,
                from: object.owner,
                to,
            },
        );
        object.owner = to;
    }

    /// Allow origin owners to reclaim any objects they previous burnt.
    public entry fun unburn<T: key>(
        original_owner: &signer,
        object: Object<T>,
    ) {
        let object_addr = object.inner;
        assert!(exists<TombStone>(object_addr), error::invalid_argument(EOBJECT_NOT_BURNT));

        // The new owner of the object can always unburn it, but if it's the burn address, we go to the old functionality
        let object_core = borrow_global<ObjectCore>(object_addr);
        if (object_core.owner == signer::address_of(original_owner)) {
            let TombStone { original_owner: _ } = move_from<TombStone>(object_addr);
        } else if (object_core.owner == BURN_ADDRESS) {
            // The old functionality
            let TombStone { original_owner: original_owner_addr } = move_from<TombStone>(object_addr);
            assert!(
                original_owner_addr == signer::address_of(original_owner),
                error::permission_denied(ENOT_OBJECT_OWNER)
            );
            transfer_raw_inner(object_addr, original_owner_addr);
        } else {
            abort error::permission_denied(ENOT_OBJECT_OWNER);
        };
    }
