### Title
Unfunded overpayment refunds in `recapitalize`/`repay` pay out of real pool custody beyond the measured inbound receipt, letting any caller drain supplier funds - ([File: contracts/pool/src/ops/recapitalize.rs])

### Summary

The reported bug class is an input that escapes an intended boundary: pymdown-snippets confined reads to `base_path`, but `os.path.join(base, "/etc/passwd")` let an absolute path override the base entirely. The XOXNO Lending analog is the pool's refund logic: the "base" that should bound any outbound transfer is the *measured* amount the payer actually transferred in, but `ops::recapitalize::apply` and `ops::repay::apply` compute the refund from the *declared* amount minus the applied shortfall/debt — and pay that refund out of live custody without debiting `cash` or passing `require_reserves`. The declared input escapes the measured-receipt bound exactly as `/etc/passwd` escapes `base_path`.

### Finding Description

Pool state keeps a `cash` book that is supposed to track real token custody per (hub, asset) market. Two ops refund an "excess" derived from the caller-declared amount rather than from what was actually received:

- `ops::recapitalize::apply` — the excess of the declared amount over the bad-debt shortfall is refunded to the payer.
- `ops::repay::apply` — the excess of the declared amount over `current_debt_ceil` is refunded.

Neither refund leg debits `cash` nor passes `require_reserves`; the refund is paid straight out of the pool's SAC balance. The test suite pins the consequence:

- `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` (`contracts/pool/tests/flows.rs:3408`): a payer calls `recapitalize` with no debt to cover, custody drops to 0, while the `cash` book still claims the full supplier deposit. A subsequent supplier `withdraw` clears the pool's own `InsufficientLiquidity`/`PoolInsolvent` guards (the book says funds exist) and then reverts inside the SAC transfer with `BalanceError = 10` — the market reports itself solvent and cannot pay.
- `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` (`contracts/pool/tests/flows.rs:3590`): a `repay` against a market with zero debt makes the whole declared amount "excess"; `resolve_repay` takes the full-close branch, `net_repay` is 0, the `RepayRoundsToZeroShares` assert passes on its `net_repay == 0` disjunct, and the full amount is refunded out of custody with the book untouched.
- `test_recapitalize_rejects_a_hub_asset_that_names_no_market` (`flows.rs:3525`) confirms the asset-substitution variant is *not* reachable (market key and `params.asset_id` are the same address), which isolates the bug to the unbounded refund amount itself — the traversal analog is in the amount dimension, not the asset dimension.

`recapitalize` is an unprivileged entrypoint (it exists precisely so anyone can cover bad debt), so no role or governance gate stands in front of this path.

### Impact Explanation

Any unprivileged address can declare a large `amount` on a market with no (or small) shortfall/debt and receive a refund paid out of suppliers' real custody. The `cash` book is not debited, so:

- Direct theft: the caller walks away with tokens that the books still attribute to suppliers (theft of user funds).
- Permanent freezing / insolvency: the book overstates custody, so honest supplier exits pass the pool's liquidity and solvency guards and then revert inside the SAC transfer. Withdrawals for the drained market are bricked until the shortfall is recapitalized, and because the book still shows the cash, the market does not even flag itself insolvent.

Because markets across hubs share one physical pool balance per token (`hub_asset` books are separate but custody is shared, per `docs/explanation/threat-model.md`), draining one market's custody can impair exits nominally booked to other hubs of the same asset.

### Likelihood Explanation

Reachable by a single unprivileged address via `recapitalize` (no auth beyond the payer's own signature on the inbound transfer, which can be zero measured receipt). Preconditions are minimal: a market whose bad-debt shortfall is smaller than the declared amount — trivially satisfied on a healthy market where the entire amount is excess. The `repay` leg requires the market have little outstanding debt. No oracle manipulation, no privileged state, no timing dependence. The only natural bound is live custody of that token, which is exactly what makes it a full-drain primitive.

### Recommendation

Bind every outbound refund to the measured inbound receipt, not the declared parameter:

1. In `ops::recapitalize::apply` and `ops::repay::apply`, compute the refund as `measured_inbound − applied` where `measured_inbound` is the balance delta the pool actually received for `hub_asset.asset` (the same `transfer_amount_measured` discipline used elsewhere), never `declared − applied`.
2. Debit `cash` (and run `require_reserves`, or treat the refund as a cash-neutral pass-through of the just-received funds) so the book can never overstate custody after the op.
3. Alternatively, cap the pull itself: pull only `min(declared, shortfall)`/`min(declared, debt)` so no excess ever exists to refund.

### Proof of Concept

Existing harness tests demonstrate both legs:

```rust
// contracts/pool/tests/flows.rs:3430 — recapitalize drains custody, book lies
let custody = token.balance(&t.pool);
t.client().recapitalize(&hub(&t.asset), &payer, &custody);
assert_eq!(token.balance(&t.pool), 0, "custody is gone");
assert!(t.state_snapshot().cash >= deposit, "book still claims the deposit");
// supplier withdraw then fails inside the SAC with BalanceError = 10
```

```rust
// contracts/pool/tests/flows.rs:3604 — repay with no debt refunds declared amount
let credited = t.client().repay(&payer, &t.ract(0, custody_before))
    .get_unchecked(0).actual_amount;
assert_eq!(credited, 0, "no debt retired");
// entire declared amount refunded out of real custody, book untouched
```

Attack path (single unprivileged address):

1. Pick a pool market `(hub_id, asset)` holding supplier custody with no pending bad-debt shortfall.
2. Call `recapitalize(hub_asset, attacker, X)` with `X` up to the pool's token balance.
3. The op applies zero (or dust) against the shortfall and refunds `X − applied` to `attacker` out of custody without debiting `cash`.
4. Suppliers' subsequent `withdraw` calls pass `require_reserves` and revert inside the token transfer — funds are stolen and remaining exits are frozen.

Note on uncertainty: the pinned tests exercise the pool entrypoints directly; whether the controller-facing `recapitalize` path adds a measured-inbound gate that bounds the refund was not fully verified in this pass. If the controller measures receipt and passes the *measured* value down, the residual exposure reduces to the pool entrypoint's own auth surface — that specific call chain should be confirmed before fix scoping.
