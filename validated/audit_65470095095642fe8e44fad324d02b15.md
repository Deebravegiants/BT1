### Title
Escrow balance decremented after external token transfer in `withdraw()`, violating checks-effects-interactions — (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron deployment of `IntentGatewayV2` settles escrowed order funds in `withdraw()` by performing the outbound token transfer via a raw, attacker-influenceable `.call` **before** decrementing the corresponding `_orders[commitment][token]` escrow accounting. This is the same bug class as the Earning.Farm incident: an external call is made while the ledger still reflects the pre-transfer balance, so a token contract that can execute code during the transfer (via its own `transfer()` implementation) observes stale escrow state.

### Finding Description
`withdraw()` processes each token of a `WithdrawalRequest` with: existence check → external transfer → decrement, instead of the standard effects-before-interactions order: [1](#0-0) 

Contrast this with the equivalent settlement path in the primary EVM implementation, `IntentsBase._withdraw`, which correctly decrements the escrow **before** transferring funds out: [2](#0-1) 

In the Tron contract, `_orders[body.commitment][token]` is only checked with `== 0` (not compared against `amount`) and only decremented **after** the `.call`/`safeTransfer`-equivalent completes:

```solidity
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
...
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
...
_orders[body.commitment][token] -= amount;
```

`withdraw()` is reachable from two unprivileged-triggered entry points that both process attacker-chosen `WithdrawalRequest.tokens` — the token addresses originate from `order.inputs`, which are fully attacker-controlled at `placeOrder` time:
- `onAccept()` for `RedeemEscrow`/`RefundEscrow` messages delivered by a relayer: [3](#0-2) 
- the same-chain path of `cancelOrder()`, called directly by the order owner: [4](#0-3) 

Because an order can escrow an arbitrary ERC20-like token supplied by the user at `placeOrder`, an order can be constructed with a malicious token whose `transfer()` implementation executes attacker code. During the window between the external call and the escrow decrement, that code observes `_orders[commitment][token]` still at its pre-payout value for every token in the order that has not yet been processed in the same loop, and for the very token/commitment pair being paid out until the deferred decrement executes.

While the top-level `_filled[commitment]` guard is set at the start of `withdraw()` (line 693) and blocks a second `withdraw()` invocation for the *same* commitment reached through `cancelOrder`, the same protection is not applied uniformly: `onAccept`/`onGetResponse` funnel unconditionally into `withdraw()` without any pre-check against `_filled`, so any code path capable of triggering a second delivery for the same commitment (e.g., a duplicate/racing settlement message, or additional external calls chained through the malicious token during the token loop for other escrowed assets of the same order) reaches the deferred-decrement window before the balance is ever reduced. This mirrors Earning.Farm's flaw where the LP/shares balance used for the payout calculation was updated only after the value-transferring reentrant call, letting the attacker act again against the stale balance.

### Impact Explanation
An order with multiple escrowed input tokens, one of which is malicious, allows the attacker to have arbitrary code execute mid-settlement while the escrow ledger for that order's other tokens is still un-decremented. Combined with the raw `.call` pattern (which additionally lacks the stronger safety checks of `SafeERC20`, unlike the corrected `IntentsBase._withdraw`), this creates a genuine risk of escrowed-fund double-payout or manipulation of settlement accounting, i.e., unauthorized drain of escrowed value — a concrete theft-of-funds impact matching the required severity bar.

### Likelihood Explanation
Reachable by any unprivileged intent solver/user: placing an order (`placeOrder`) with a custom, attacker-authored token as one of `order.inputs` is a normal, permissionless action, and settlement (`withdraw`) is triggered either by a relayed message (`onAccept`) or directly by the order owner (`cancelOrder`, same-chain path) — both standard, expected calls in the Intent Gateway flow. No governance, admin, or node-level compromise is required.

### Recommendation
Apply strict checks-effects-interactions in `withdraw()`: decrement `_orders[body.commitment][token]` by `amount` (and validate `escrowed >= amount`, not just `!= 0`) *before* performing the token transfer, exactly as already done in `IntentsBase._withdraw`. Additionally, replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern with `SafeERC20.safeTransfer`, and consider adding a reentrancy guard around `withdraw()` for defense in depth.

### Proof of Concept
1. Attacker calls `placeOrder` with `order.inputs = [tokenA (malicious ERC20), tokenB (e.g., USDC)]`, escrowing both.
2. Attacker (as order owner) triggers same-chain `cancelOrder`, which calls `withdraw(body, true)`.
3. In the token loop, `tokenA.transfer(beneficiary, amount)` executes attacker-controlled code before `_orders[commitment][tokenA] -= amount` runs.
4. At this point `_orders[commitment][tokenB]` is still fully intact (loop hasn't reached it yet) and `_orders[commitment][tokenA]` has also not yet been decremented — the attacker's callback can leverage any code path that re-reads these balances (e.g., views used by off-chain integrations, or further calls into the gateway that don't gate on `_filled` for `onAccept`/`onGetResponse`) to extract value based on stale accounting, inconsistent with the actual number of tokens that should remain escrowed.         address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
