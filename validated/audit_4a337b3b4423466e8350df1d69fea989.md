### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the `shop` (tenant identifier) is read from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` header. `Registry.process` validates the HMAC against the body alone and then trusts `request.shop` to build the `WebhookMetadata` that is handed to the app's webhook handler. This breaks the identity binding: `hmac == HMAC(body)` is verified, but `shop` (the value the handler will treat as the authenticated tenant) is never part of what the HMAC covers.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the supplied `hmac`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body, while `shop` is parsed from a separate, unauthenticated header: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then immediately trusts `request.shop` — a value that was never part of the signed bytes — to construct the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The binding the gem should enforce is: `authenticated(body) == tenant_context_used_by_handler`. Instead, what's actually enforced is `authenticated(body) == body`, and `tenant_context_used_by_handler = shop_header (unauthenticated)`. Any request whose `body` bytes and `hmac` are a valid pair (e.g., a webhook payload originally delivered for Shop A, which is not itself secret — bodies are sent over HTTPS to the app's own endpoint and are not encrypted end-to-end from Shopify's perspective once received) will pass `HmacValidator.validate` regardless of which `x-shopify-shop-domain` value is attached, because that header is not part of `to_signable_string`.

### Impact Explanation
This is a High-impact scope/identity-check bypass: the shop/tenant binding that downstream handlers rely on for per-shop dispatch (e.g., "look up local record for `data.shop`", "process order for `data.shop`") is not authenticated at all by the gem's HMAC check. An attacker who can capture or replay a valid `(body, hmac)` pair — for example one delivered by Shopify to the app's public endpoint, which is visible to anyone who can observe the HTTP request/response at the receiving endpoint (e.g., via logs, a misconfigured proxy, or simply because they operate their own shop and receive their own genuinely-signed webhooks) — can resubmit that exact body/hmac with a different `x-shopify-shop-domain` header. `Registry.process` will accept it as valid and dispatch it to the handler tagged with the attacker-chosen shop, producing cross-tenant confusion in any handler that keys off `WebhookMetadata#shop` without independently re-validating shop ownership.

### Likelihood Explanation
Likelihood is High: no secrets, tokens, or privileged access are required. Any actor who legitimately receives a single valid webhook for their own shop (trivial for any real or trial merchant) obtains a `(body, hmac)` pair valid for the app's single, shop-independent `api_secret_key`. They can then replay that pair with an arbitrary `shop-domain` header value against the app's registered webhook endpoint, and the gem's `Registry.process` provides no defense because the shop is never covered by the signature.

### Recommendation
Bind the shop identity into what is cryptographically verified before it is trusted:
- Include the `shop` (and ideally `topic`, `webhook_id`) in the signed material checked by `HmacValidator`, or
- After HMAC validation, independently confirm that `request.shop` corresponds to a shop that actually has this specific `webhook_id`/subscription registered (e.g., look it up against stored subscriptions) before constructing `WebhookMetadata`, rather than trusting the header value outright.

```diff
-      sig { override.returns(String) }
-      def to_signable_string
-        @raw_body
-      end
+      sig { override.returns(String) }
+      def to_signable_string
+        "#{shop}\n#{@raw_body}"
+      end
```
(and correspondingly document/require Shopify's webhook signing to include shop, or add a secondary server-side check binding `webhook_id` to the expected `shop`).

### Proof of Concept
1. Register a webhook handler that trusts `data.shop` (as the docs intend), e.g. `WebhookHandler#handle` looks up `Shop.find_by(domain: data.shop)` and updates that shop's local records with `data.body`.
2. As the operator of "attacker-shop.myshopify.com", trigger any subscribed event (e.g. `orders/create`) so Shopify sends a legitimately signed webhook to the app: `raw_body = B`, `hmac = HMAC(secret, B)`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Capture that `(B, hmac)` pair (attacker fully controls their own request/response cycle, so this requires no special access).
4. Resend the identical `raw_body` and `hmac` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `HMAC(secret, raw_body)`, which is unchanged.
6. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and invokes the handler, causing the app to act on victim-shop's tenant context using attacker-supplied body content — a cross-tenant integrity violation.
