### Title
Unauthenticated arbitrary `RuntimeCall` injection via cross-chain `calldata` in `pallet-hyper-fungible-token` - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
The Semaphore CVE (CVE-2023-39059) is a case where an "extra variables" field supplied by a caller is passed, unsanitized, into a privileged execution path (`exec.Command`) that ultimately runs attacker-controlled code. The Hyperbridge analog is `pallet_hyper_fungible_token`'s `on_accept` handler, which decodes an attacker-supplied `calldata` blob out of the cross-chain `Message` and, on a code path that requires **no cryptographic authentication**, dispatches it as a fully-privileged `RuntimeCall` under `RawOrigin::Signed`, gated only by the runtime's `BaseCallFilter`.

### Finding Description
`on_accept` decodes the incoming ABI `Message` and, if `message.data` is non-empty, decodes it into `SubstrateCalldata { signature: Option<Vec<u8>>, runtime_call: Vec<u8> }`: [1](#0-0) 

The `runtime_call` bytes are fully attacker-controlled — they come straight from the cross-chain message body, which any account holding the bridged token on the source chain can populate when calling `send()`. When `signature` is `None`, the dispatch `origin` is derived purely from the message's `from` bytes, with **no signature check at all**: [2](#0-1) 

That derived account is then used as the signer for an arbitrary, attacker-chosen `RuntimeCall`: [3](#0-2) 

The only safeguard against abuse is `BaseCallFilter::contains(&runtime_call)` — a chain-wide filter meant for maintenance/SafeMode gating, not for message-level authorization: [4](#0-3) 

This mirrors the Semaphore bug class exactly: a user-controlled payload (`extra vars` ↔ `runtime_call`) reaches a privileged execution primitive (`exec.Command` ↔ `Dispatchable::dispatch`) with the only "sanitization" being a generic allow/deny filter that was never designed to authenticate per-message intent. Unlike the signed branch — where a real Ed25519/Sr25519/ECDSA signature is verified against the beneficiary's own key before letting them dispatch a call as themselves — the unsigned branch trusts the bridged message's embedded `from` field as sufficient authorization to act as that account, without any proof of possession of the corresponding key.

### Impact Explanation
If the account derived from `message.from` does not strictly and verifiably correspond to the actual key-holder who authorized this specific `runtime_call` (any mismatch between the ISMP-level authenticated sender and the ABI-encoded `message.from` field the pallet trusts), an attacker can dispatch *any* dispatchable not excluded by `BaseCallFilter` under someone else's `AccountId` — e.g., `Balances::transfer_all`, asset transfers, governance votes, or other privileged pallet calls — directly on the destination chain. This is a concrete "unauthorized app action" / theft-of-funds primitive: arbitrary runtime code execution as an account the attacker doesn't control, reachable from a single token-bridging transaction dispatched through `EvmHost`/`HandlerV2` into `ProxyModule::on_accept` → `pallet_hyper_fungible_token::on_accept`.

### Likelihood Explanation
Reachable by any unprivileged user who can call the source-chain `HyperFungibleToken` contract's `send()` with a non-empty `data` field and omit the `signature` — no special privileges, governance, or relayer collusion required beyond normal message relaying. The severity is bounded only by whatever `BaseCallFilter` the destination runtime configures (default Substrate runtimes commonly use a permissive `Everything`/near-`Everything` filter for `BaseCallFilter`).

### Recommendation
Require a verified signature for *every* dispatched `runtime_call`, removing the unsigned/`message.from`-derived origin path entirely, or, at minimum, cryptographically bind `message.from` to the calldata (e.g., require it to equal the same authenticated identity that the ISMP layer already verified for the source contract call) rather than trusting an application-level field embedded in attacker-supplied ABI data. Additionally, do not rely on `BaseCallFilter` as the sole authorization boundary for cross-chain-triggered dispatch — it is a chain-wide policy knob, not a per-message ACL.

### Proof of Concept
1. Attacker acquires (or the token allows minimal-amount) `HyperFungibleToken` balance on a source EVM chain.
2. Attacker calls `send()` with `data` containing a `SubstrateCalldata { signature: None, runtime_call: <encoded privileged call, e.g. Balances::transfer_all(victim_derived_account -> attacker)> }`, and crafts the ABI `Message.from` bytes to correspond to a victim's EVM address (or otherwise an account the attacker does not control the key for).
3. On the destination chain, `pallet_hyper_fungible_token::on_accept` decodes the calldata, takes the unsigned branch, derives `origin` from the attacker-supplied `message.from`, and dispatches the victim-impersonating `runtime_call` — subject only to `BaseCallFilter` — with no signature check.

**Note:** I was not able to fully verify, within available context, whether the EVM-side `HyperFungibleToken.send()` function strictly forces `message.from == msg.sender` (the file was only partially indexed up to line 160). If `send()` does hard-code `from = msg.sender`, the practical exploitability narrows to cases where the source-chain caller and the destination-chain account derived via `EvmToSubstrate::convert` diverge from actual key ownership (still true for the default zero-padding conversion, since no proof-of-key is required for the *destination* AccountId, only that `msg.sender` on the *source* chain matches). This distinction affects exact exploitability and should be confirmed by reading the full `send()` implementation and its EVM/Substrate address-derivation guarantees before treating this as fully confirmed exploitable; the code as shown, however, unambiguously dispatches attacker-supplied `RuntimeCall` bytes under a `Signed` origin without cryptographic authentication whenever `signature` is omitted.
