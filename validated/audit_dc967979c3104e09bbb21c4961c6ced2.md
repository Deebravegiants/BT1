### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant routing without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content from the raw request body only, while the `shop` and `topic` values used to route and label the webhook are read directly from unauthenticated HTTP headers. `Utils::HmacValidator.validate` only proves that the *body* bytes match the signature — it proves nothing about which shop or topic the payload is claimed to belong to. Any caller who can reproduce a body/HMAC pair that was valid once (e.g. a merchant replaying their own previously-received, legitimately-signed webhook) can attach an arbitrary `shop-domain`/`topic` header pair, and `Registry.process` will pass that attacker-chosen `shop` straight to the app's handler as trusted tenant identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` and `Request#topic` are pulled straight from HTTP headers, entirely outside the signed content: [2](#0-1) 

`Utils::HmacValidator.validate_signature` recomputes the HMAC over `to_signable_string` (the body) and compares it to the `hmac-sha256` header — it never touches `shop` or `topic`: [3](#0-2) 

`Registry.process` validates the HMAC and then trusts `request.topic` and `request.shop` as authoritative for handler dispatch and for the metadata handed to the app: [4](#0-3) 

The implicit identity binding the gem is supposed to guarantee to the consuming app is:
`HmacValidator.validate(request) == true` ⇒ `request.shop == <the shop that actually generated this exact webhook body>` and `request.topic == <the topic Shopify actually tagged this payload with>`.

In reality the binding only holds for the body bytes:
`HmacValidator.validate(request) == true` ⇒ `HMAC(secret, raw_body) == received_hmac`

`shop` and `topic` are free variables that an unprivileged caller controls. A merchant who owns their own shop can capture a body/HMAC pair from a webhook Shopify legitimately sent them (the body is visible to them, e.g. via app logs, error responses, or a debug endpoint that echoes it), and resubmit that exact body to the app's public webhook endpoint with a forged `shopify-shop-domain` (and/or `shopify-topic`) header. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` then calls the registered handler with `WebhookMetadata.new(topic: <attacker-chosen>, shop: <attacker-chosen>, body: <replayed real data>, ...)`.

### Impact Explanation
This breaks the tenant boundary the app relies on: the app is told "this authentic Shopify data belongs to shop B / topic T" when it actually authenticated only that "this byte sequence was HMAC-signed with our secret at some point." Any app logic that uses `WebhookMetadata#shop` to select a per-tenant database record, session, or access token (a very common pattern, since `session: ...store_session_by_shop(shop)`-style lookups are exactly what `Utils::SessionUtils`/`Session` model expects) can be tricked into writing, overwriting, or acting on data under a shop identity the caller does not actually own — i.e. cross-tenant data injection/confusion, consistent with the report's bug class of "a value used for a security-relevant decision that is not actually covered by the signature that is supposed to authenticate it."

### Likelihood Explanation
Any unprivileged party who has legitimately received at least one real webhook for their own shop (trivial — installing any app that registers webhooks) can obtain a valid `(body, hmac)` pair and replay it with modified `shop`/`topic` headers against any app using this gem's default `Webhooks::Request`/`Registry` flow, with no access to `api_secret_key` or any merchant's access token required.

### Recommendation
Include `shop` and `topic` (and ideally a per-delivery identifier / timestamp) in the signed content that `to_signable_string` returns, or otherwise cryptographically bind them to the payload before trusting them in `Registry.process`/`WebhookMetadata`. At minimum, document that `shop`/`topic` are unauthenticated and instruct consuming apps to independently confirm the shop against a value that was authenticated as part of the OAuth-established session for that same webhook subscription (e.g. verify the destination path or a subscription-specific secret), rather than trusting the raw header value as tenant identity.

### Proof of Concept
1. App using this gem registers a webhook handler for topic `orders/create` and stores per-shop state keyed by `WebhookMetadata#shop`.
2. Attacker (a legitimate installer of the app on `attacker-shop.myshopify.com`) receives a real webhook from Shopify: body `B`, header `shopify-hmac-sha256: H`, `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-topic: orders/create`.
3. Attacker resends the exact same request to the app's webhook endpoint but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `Request.new` builds successfully (all three required headers present); `HmacValidator.validate(request)` recomputes `HMAC(secret, B)` — unchanged since `B` is unchanged — and it equals `H`, so validation passes: [5](#0-4) 
5. `Registry.process` dispatches to the handler with `shop: "victim-shop.myshopify.com"` and the attacker's real order body, even though `victim-shop` never sent this webhook: [6](#0-5)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
