## Title
Webhook `shop-domain` header is trusted for tenant attribution without being covered by the HMAC signature — cross-tenant webhook data confusion - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant identity) is read from the `X-Shopify-Shop-Domain` header, which is never included in the signed bytes. `Registry.process` validates the HMAC and then passes `request.shop` straight into `WebhookMetadata` for the host app's handler, meaning the "verified" bytes and the "acted-on" tenant identifier are disjoint.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only [1](#0-0) , and `Request#shop` reads the `shop-domain`/`x-shopify-shop-domain` header, which is not part of that signed string [2](#0-1) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., body integrity) before handing `request.shop` to the handler as the trusted tenant identifier [3](#0-2) . `Utils::HmacValidator.validate_signature` compares the HMAC only against `verifiable_query.to_signable_string` [4](#0-3) , so the header-derived `shop` value can be any string and still pass validation as long as the body bytes match a previously-seen valid (body, hmac) pair.

The equality that should hold — `shop_bound_by_hmac == shop_used_for_tenant_attribution` — is broken: the HMAC binds only the JSON body, not the shop header, so `Registry.process`'s tenant attribution (`WebhookMetadata#shop`) is unauthenticated relative to the cryptographic check that gates processing.

### Impact Explanation
This matches the "Critical - cross-tenant access" category: if an attacker can capture one legitimate (body, hmac) pair delivered to the app's webhook endpoint (e.g., from their own dev store, or via a compromised network path to the endpoint, or replay), they can resubmit the identical body/hmac with an arbitrary `shop-domain` header. The library's own validation (`HmacValidator.validate`) will accept it, and the host application — following the documented `ShopifyAPI::Webhooks::Registry.process` flow — will process the payload attributing it to a different (attacker-chosen) shop than the one it actually originated from. Any host app that uses `WebhookMetadata#shop` to scope data writes/lookups (the intended and documented usage) is exposed to cross-tenant data confusion sourced entirely from this gem's verification design.

### Likelihood Explanation
Requires the attacker to have network reachability to the app's public webhook endpoint (which is unauthenticated by design, gated only by HMAC) and to have observed at least one valid (body, hmac) pair for any shop — something reachable without any privileged credential, access token, or `client_secret`. This is squarely within the "unprivileged internet user" threat model and does not require intercepting TLS or obtaining Shopify's signing secret.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material, or independently require callers/`Registry.process` to cross-check `request.shop` against an expected/allow-listed shop domain before dispatching to handlers. At minimum, document and enforce that `WebhookMetadata#shop` must never be trusted without an out-of-band binding, and provide a helper that verifies header-derived identity fields are consistent with the values Shopify actually signs.

### Proof of Concept
1. Attacker registers/observes a legitimate webhook delivery to the target app for `shop-a.myshopify.com`, capturing the raw JSON body and its `X-Shopify-Hmac-Sha256` value (e.g., from their own store's webhook log, or a MITM-free network capture at the public endpoint).
2. Attacker replays an HTTP POST to the app's webhook endpoint with the identical raw body and HMAC header, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `to_signable_string` (the body) against the HMAC [5](#0-4) .
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(..., shop: request.shop, ...)`, attributing the payload to `shop-b` even though it was never signed for `shop-b` [6](#0-5) .
