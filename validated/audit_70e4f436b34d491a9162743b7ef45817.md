### Title
Session cookie value is a deterministic, guessable session identifier rather than a cryptographically random token, enabling session fixation - (File: `lib/shopify_api/auth/session.rb`, `lib/shopify_api/auth/oauth.rb`, `lib/shopify_api/utils/session_utils.rb`)

### Summary
For non-embedded (and cookie-fallback) OAuth flows, `ShopifyAPI::Auth::Session.from` sets the session `id` to a deterministic value computed only from public/guessable inputs — `"#{shop}_#{associated_user.id}"` for online sessions or `"offline_#{shop}"` for offline sessions — and this same value is used verbatim as the `SessionCookie` value that identifies the session going forward. Unlike the chainId/EIP712 issue, where the domain separator binds a signature to an immutable-but-wrong identity component, here the "identity token" (`session.id`) that binds a browser cookie to a specific merchant/user is not itself covered by any signature or MAC and is fully re-derivable by anyone who knows the shop domain and the target user's numeric id.

### Finding Description
`Session.from` computes the session id deterministically: [1](#0-0) 

For non-embedded apps, `Oauth.validate_auth_callback` sets this deterministic `session.id` directly as the value of the browser-facing `SessionCookie`: [2](#0-1) 

Later, `SessionUtils.current_session_id`/`cookie_session_id` reads this cookie value back out and treats it as the authoritative session identifier used by the host app to fetch the corresponding stored session (and its access token) with no additional verification of the value's provenance: [3](#0-2) [4](#0-3) 

The broken identity binding, expressed as an equality that should hold but does not:
`cookie_value == opaque_random_token_bound_to(shop, access_token)` is expected, but instead `cookie_value == f(shop, associated_user.id)` where `f` is a public, non-secret string concatenation. Only `shop` and online/offline status are attacker-observable already, and `associated_user.id` is Shopify's small sequential staff-account id, which is enumerable/guessable (e.g., via a malicious app installed in the same store, or brute force over a small integer range) — unlike a cryptographically random `SecureRandom.uuid` id that `Session.new` uses when no explicit `id:` is supplied (line `@id = T.let(id || SecureRandom.uuid, String)`), which the `from` factory deliberately overrides with the deterministic string.

### Impact Explanation
An attacker who can predict or learn a victim's `shop_userid` string can set their own browser's `shopify_app_session` cookie to that value. If the host application's session store keys sessions purely by this id (as the gem's documented API implies it should, since the gem hands the host app exactly this id/cookie pair to persist and later look up), the attacker's browser session becomes bound to the victim's stored `Session` object — including the victim's `access_token` — resulting in session fixation and cross-tenant/cross-user session hijacking without ever needing the victim's cookie or credentials.

### Likelihood Explanation
Exploitation requires only knowledge of the target shop's `myshopify.com` domain (public) and the target staff user's numeric id (small integer, often enumerable in a low-traffic app or guessable by iterating small ranges), both obtainable without any credential, access token, or privileged access — matching the "unprivileged internet user" threat model. The offline-session case (`"offline_#{shop}"`) requires no per-user secret at all — it depends solely on the public shop domain.

### Recommendation
Do not derive session/cookie identifiers deterministically from public or low-entropy data. Use a cryptographically random, high-entropy identifier (e.g., `SecureRandom.uuid`, which `Session.new` already supports as a fallback) for the cookie value, and store the mapping from that random id to `(shop, associated_user, access_token)` server-side. Alternatively, sign/HMAC the cookie value (similar to the `HmacValidator` already used for the OAuth callback) so that the host application can verify the cookie was issued by the gem/app and was not fabricated or guessed by a third party.

### Proof of Concept
1. App A (attacker-controlled, or attacker with app access) discovers `shop.myshopify.com` and enumerates small integer `associated_user.id` values (e.g., 1–1000) — Shopify staff ids are small sequential integers.
2. Attacker sets their own browser cookie `shopify_app_session` to `"shop.myshopify.com_<guessed_id>"` (or `"offline_shop.myshopify.com"` for the offline case) as produced by `Session.from` in `lib/shopify_api/auth/session.rb:114-116`.
3. The host app, following the documented flow, calls `SessionUtils.current_session_id`/`cookie_session_id` (`lib/shopify_api/utils/session_utils.rb:68-71`) which returns the attacker-supplied cookie value verbatim.
4. The host app looks up the stored `Session` (containing the victim's real `access_token`) by that id and authenticates the attacker's request as the victim — achieving cross-tenant/cross-user access without possessing any legitimate credential.
