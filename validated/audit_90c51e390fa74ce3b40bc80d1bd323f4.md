### Title
Webhook shop identity (`shop-domain` header) is not covered by the HMAC signature, allowing shop spoofing on otherwise-valid webhook requests - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` implements the `Utils::VerifiableQuery` contract but only signs the raw request body. The `shop`, `topic`, `api_version`, and `webhook_id` values — all read from unauthenticated HTTP headers — are used and forwarded to the app's handler without being part of the HMAC-signed content, breaking the binding between "HMAC verified" and "shop attributed to this event."

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from request headers with no cryptographic tie to the signature: [2](#0-1) 

`Registry.process` validates only this body-derived HMAC and then dispatches to the app's handler using the unauthenticated `request.shop`: [3](#0-2) 

`WebhookMetadata.shop` is a `const` field the gem hands the host app as trusted, verified data: [4](#0-3) 

Contrast this with the OAuth callback's `AuthQuery`, which correctly includes `shop` inside the HMAC-signed string, so the shop cannot be swapped without invalidating the signature: [5](#0-4) 

The identity binding the gem is supposed to guarantee is:
`HMAC valid ⇒ (shop, topic, body) are all authentic and bound together`

What is actually checked is only:
`HMAC valid ⇒ body is authentic`

Because `shop` (and `topic`/`webhook_id`/`api_version`) sit outside the signed bytes, any request whose body+signature pair was legitimately produced for shop A can be replayed with the `shop-domain` (or `x-shopify-shop-domain`) header rewritten to shop B, and `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` will still return `true` because it only recomputes the signature over `to_signable_string`, i.e. the body.

### Impact Explanation
An attacker who controls (or has installed) a shop of their own can trigger a legitimate webhook (including mandatory compliance topics like `shop/redact`, `customers/redact`, `customers/data_request`, which are enumerated in `Registry::MANDATORY_TOPICS`), capture the resulting `(raw_body, hmac)` pair signed by Shopify's shared secret, and then POST that same body/HMAC to the app's public webhook endpoint while substituting an arbitrary victim `shop-domain` header. `Registry.process` will accept it as HMAC-valid and hand the handler a `WebhookMetadata` claiming the event is for the victim shop. Any app logic that trusts `data.shop` for tenant-scoped actions (session/token lookup, data deletion, entitlement changes, audit logging) will act on the wrong tenant — a cross-tenant identity confusion driven entirely by this gem's failure to bind `shop` into its own HMAC check, not by host-app misuse of an undocumented contract.

### Likelihood Explanation
No privileged credentials, TLS interception, or social engineering are required. The attacker only needs a shop they legitimately control (any developer/merchant can create one) to obtain a valid `(body, hmac)` pair, plus knowledge of the target app's public webhook endpoint (which is, by design, an unauthenticated public URL). Crafting and sending the forged HTTP request with a different `shop-domain` header is trivial.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC-signable content for `Webhooks::Request`, or otherwise cryptographically bind them (e.g., derive them only from a signed body, or require Shopify's per-shop webhook secret verification of the header set) so that `Utils::HmacValidator.validate` can no longer succeed when any of these header-derived identity fields have been altered. At minimum, `to_signable_string` should not silently ignore fields (`shop`, `topic`, `webhook_id`, `api_version`) that are later exposed to and trusted by the host application via `WebhookMetadata`.

### Proof of Concept
1. Attacker registers/owns `attacker.myshopify.com` and subscribes the target app to a webhook topic (e.g. `customers/data_request`).
2. Shopify sends `POST /webhook` to the app with `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <hmac over raw_body>`, and some JSON `raw_body`.
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value.
4. Attacker (or a relay) sends a new request to the same endpoint with identical `raw_body` and `x-shopify-hmac-sha256`, but `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses headers; `Utils::HmacValidator.validate(request)` recomputes the HMAC over `to_signable_string` (`raw_body` only) — matches, returns `true`.
6. `Registry.process` proceeds and calls the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: ...)`, even though Shopify never issued this event for `victim.myshopify.com`.
