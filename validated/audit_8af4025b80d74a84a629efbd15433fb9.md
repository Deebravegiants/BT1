### Title
Webhook shop/topic identity spoofing via HMAC that binds only the raw body, not the routing headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` accepts the request purely on `Utils::HmacValidator.validate(request)` succeeding [3](#0-2) , then forwards `request.shop` and `request.topic` straight into `WebhookMetadata` for dispatch to the app's handler, without any check that the headers correspond to the shop that produced the signed body.

### Finding Description
The binding the gem is expected to enforce is: `hmac == HMAC(secret, body) AND shop_header identifies the same tenant that produced body`. In reality only the first half holds — the equality actually enforced is `hmac == HMAC(secret, body)`, with `shop`/`topic`/`webhook_id` entirely outside the signed material.

Concretely:
- `hmac` is computed from `shopify-hmac-sha256` header and compared against `HMAC(api_secret_key, @raw_body)` — the body is the only signed input [4](#0-3) [5](#0-4) .
- `shop`, `topic`, `webhook_id`, `api_version` are pulled from `shopify-*`/`x-shopify-*` headers with no cryptographic tie to the body or to each other [2](#0-1) [6](#0-5) .
- `Registry.process` validates only the HMAC and then uses `request.topic` to look up the handler and `request.shop` to build `WebhookMetadata`, trusting both fields as authenticated tenant/event identity [3](#0-2) .

Because the same `api_secret_key` is shared across all shops/installations of an app, any party who can obtain one genuine `(body, hmac)` pair for the app — e.g. by installing the app on their own store and capturing a real webhook delivery — possesses a signature that remains valid for that exact body regardless of which `shopify-shop-domain`/`shopify-topic`/`shopify-webhook-id` headers are attached to the replayed HTTP request. The gem's own verification step (`Utils::HmacValidator.validate`) will pass unchanged because it never inspects those headers, so the forged request is delivered to the host application's handler as if it originated from the victim shop and/or a different topic/webhook id.

### Impact Explanation
This breaks the tenant-identity binding between the signed payload and the shop/topic the app acts on behalf of. If the host application uses `WebhookMetadata#shop` (sourced from `request.shop`) to select which merchant's data/session to mutate, or uses `topic`/`webhook_id` to decide idempotent processing, an attacker can attribute a captured, still-validly-signed webhook body to an arbitrary victim shop or arbitrary topic, producing cross-tenant data corruption/action execution within the app — matching the "cross-tenant access" Critical-impact category the ruleset accepts.

### Likelihood Explanation
Medium-High. No credentials, tokens, or `api_secret_key` are required — obtaining one legitimate `(body, hmac)` pair only requires being any developer/merchant capable of installing the target app on a store they control (a normal, unprivileged action), then replaying that exact payload to the app's public webhook endpoint with attacker-chosen `shopify-shop-domain`/`shopify-topic` headers. The gem provides no defense against this because header/body binding was never part of its verification contract.

### Recommendation
Extend `Utils::VerifiableQuery`/`HmacValidator` usage for webhooks so that the signable string (or a secondary check performed by `Registry.process`) incorporates the routing headers (`shop`, `topic`, `webhook_id`) that the app relies on for tenant/event identity, or explicitly document that these headers are unauthenticated and must not be trusted for authorization decisions, and have `Registry.process` refuse to dispatch unless the caller separately confirms the `shop` against a known, previously-authenticated session/installation record.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own store "attacker.myshopify.com"
#    and receives a genuine webhook delivery for topic "orders/create":
raw_body = '{"id":123,"note":"hello"}'
real_hmac_b64 = <captured "shopify-hmac-sha256" header value from the genuine delivery>

# 2. The signature only ever covered raw_body:
#    HmacValidator.validate_signature computes:
#      OpenSSL::HMAC.hexdigest(sha256, api_secret_key, raw_body)
#    and compares it against Digest.hexencode(Base64.decode64(real_hmac_b64)).
#    It is identical no matter what headers accompany the request.

# 3. Attacker replays the exact same body/hmac but swaps the identity headers:
forged_headers = {
  "x-shopify-topic"       => "orders/create",         # or any registered topic
  "x-shopify-hmac-sha256" => real_hmac_b64,            # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-chosen target shop
  "x-shopify-webhook-id"  => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# 4. Registry.process only checks HMAC against the body -> passes -> dispatches
#    handler.handle(data: WebhookMetadata.new(topic: "orders/create",
#                                              shop: "victim-shop.myshopify.com", ...))
ShopifyAPI::Webhooks::Registry.process(request)
```
`Registry.process` [3](#0-2)  accepts this forged request because `HmacValidator.validate` only re-derives the HMAC from `raw_body` [7](#0-6) , never checking that `shop`/`topic` are the ones the body actually came from.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
