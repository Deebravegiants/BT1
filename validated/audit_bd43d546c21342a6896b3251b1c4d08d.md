### Title
Unsigned Emporium min-path allows unauthenticated arbitrary calls from Emporium's identity with zero fund accounting - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only constrains `message == Poseidon(messageSeed)`, `timeStamp`, and `calldataHash` — a proof any unprivileged attacker can trivially generate since `messageSeed` is self-chosen and no UTXO ownership, nullifier, or root membership is proven. Combined with `EmporiumStack.signerAddress == address(0)`, `verifyWallet` skips signature verification entirely, and the empty `erc20TokenAddresses` array makes the `balancesBefore`/`balancesAfter` accounting loop in `runAction` a no-op, letting the attacker force Emporium to execute arbitrary `op.endpoint.call{value: op.value}(op.callData)` as `msg.sender == Emporium` with no balance check whatsoever.

### Finding Description
The broken equality is: **assets Emporium can move in a tx == assets accounted in `balancesBefore`/`balancesAfter`**. When `circomData.erc20TokenAddresses.length == 0`:

- `formInputForCircom` selects `formInputEmporiumMin` [1](#0-0) , whose corresponding circuit `MainEVMCircuitMin` only proves `message <== Poseidon(1)([messageSeed])` [2](#0-1)  — no nullifier, root, or spending-key constraint at all. `dimensionsCheck` merely requires `dimensions.tokenNumber == erc20TokenAddresses.length == 0`, which is self-consistent and imposes no further restriction [3](#0-2) .
- In `EmporiumUpgradeable.runAction`, `getBalancesForArray(circomData.erc20TokenAddresses)` on an empty array returns an empty array, and `verifyWallet` returns immediately when `stack.signerAddress == address(0)` after only marking `usedMessages[emporiumMessage] = true` — no ECDSA check is performed [4](#0-3) .
- The ops loop then executes `op.endpoint.call{value: op.value}(op.callData)` directly with Emporium as `msg.sender` (CASE 2, since `stack.signerAddress == address(0)` disables the wallet-invocation branch) [5](#0-4) .
- Because `circomData.erc20TokenAddresses.length == 0`, the post-call balance-change/UTXO-output loop never executes [6](#0-5) , and the identical token loop in `Hinkal.transact` that enforces `balanceDif == amountChanges + utxoAmount` also never executes since it too iterates `circomData.erc20TokenAddresses` [7](#0-6) .

The attacker's call: `Hinkal.transact(a,b,c, dimensions{tokenNumber:0,...}, circomData{externalActionData:{externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalActionMetadata: abi.encode(EmporiumStack{signerAddress: address(0), ops: [{endpoint: <target>, invokeWallet:false, value:<attacker-chosen>, callData:<arbitrary>}], ...})}, erc20TokenAddresses: [], amountChanges: [], ...})`. Any valid `rootHashHinkal` from an existing, non-empty tree satisfies `rootHashExists` (unrelated to the min-circuit's public signals), so the "tree has exactly one leaf" precondition mentioned in the question is not actually a gating factor — any existing root works.

This lets an unprivileged attacker force Emporium to perform an arbitrary external call from its own address with **no signature requirement and no balance/UTXO accounting**, regardless of tree state.

### Impact Explanation
Any value that Emporium's contract already holds or controls (residual ERC20/ETH balance, e.g. unclaimed relay fees, dust from prior operations sent to the `receive()` fallback, or standing allowances granted to routers that trust Emporium as `msg.sender`) can be redirected to the attacker via a crafted `callData` (e.g., `token.transfer(attacker, amount)` or invoking a router that pulls funds Emporium was approved for). This is repeatable for every `emporiumMessage` value the attacker has not yet used (an unbounded, attacker-controlled nonce space), and requires no prior privilege, no UTXO ownership, and no valid Emporium-wallet signature. Depending on what Emporium is holding at attack time, this ranges from theft of protocol/relay fees (High) up to theft of funds actively resting in/routed through Emporium (Critical), since no accounting mechanism whatsoever exists to prevent it in this code path.

### Likelihood Explanation
Preconditions: (1) `HINKAL_EMPORIUM_ACTION_ID` registered as a valid external action (standard deployment state), (2) `erc20TokenAddresses.length == 0` chosen by the attacker, (3) `signerAddress == address(0)` chosen by the attacker, (4) Emporium holding or controlling some redirectable value (fees, dust, or router allowances) at attack time. Generating a satisfying proof is trivial (self-chosen `messageSeed`) and costs only normal transaction gas — no economic barrier, no privileged role, fully attacker-controlled and repeatable.

### Recommendation
Do not allow the "min" Emporium path to skip both signature verification and balance accounting simultaneously. Either: (a) require `stack.signerAddress != address(0)` (i.e., mandatory signed wallet interaction) whenever `erc20TokenAddresses.length == 0`, or (b) require `erc20TokenAddresses.length > 0` (forcing full balance accounting) whenever `stack.signerAddress == address(0)` and any `op` performs a stateless call, or (c) restrict CASE 2 stateless calls (Emporium acting as its own msg.sender) to a strict allowlist of endpoints/selectors that cannot move value, independent of the token-array length used for proof-size optimization.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (as an allowed recipient), and a mock ERC20/vulnerable router with balance/allowance held by `Emporium`.
2. Fund Emporium directly (simulate resident dust/fees): `token.transfer(address(emporium), 1000e18)`.
3. As an unprivileged attacker EOA, generate a Groth16 proof for `MainEVMCircuitMin` with a self-chosen `messageSeed`, computing `message = Poseidon(messageSeed)`.
4. Build `CircomData` with `erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionMetadata = abi.encode(EmporiumStack{signerAddress: address(0), ops: [{endpoint: address(token), invokeWallet: false, value: 0, callData: abi.encodeCall(token.transfer, (attacker, 1000e18))}]})`, valid `rootHashHinkal`/`rootHashHinkalIndex` from any existing tree state.
5. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from the attacker.
6. Assert: `token.balanceOf(attacker)` increases by `1000e18` and `token.balanceOf(address(emporium))` decreases by the same, with no nullifier consumed, no UTXO created, and none of `balancesBefore`/`balancesAfter` in `runAction` reflecting the transfer (both empty arrays) — proving the equality "assets moved == assets accounted" is violated.
