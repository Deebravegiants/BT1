### Title
OAuth callback fails to validate `shop` against a trusted Shopify domain before sending `client_secret` to it - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the access-token exchange request using `auth_query.shop` verbatim, without ever passing it through `ShopifyAPI::Utils::ShopValidator.sanitize!`. Since `shop` is HMAC-covered but the HMAC only proves the query wasn't tampered with by a third party — not that `shop` is a legitimate `*.myshopify.com` domain — an attacker who controls the OAuth redirect (e.g., a malicious/compromised "shop" completing the install flow, or any party able to produce a validly-signed callback for a shop value they choose) can cause the gem to POST the app's `client_id`/`client_secret` to an arbitrary attacker-controlled host.

### Finding Description
`validate_auth_callback` computes:
```ruby
null_session = Auth::Session.new(shop: auth_query.shop)
body = { client_id: Context.api_key, client_secret: Context.api_secret_key, code: auth_query.code, ... }
client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
client.request(Clients::HttpRequest.new(http_method: :post, path: "access_token", body: body, ...))
``` [1](#0-0) 

`Clients::HttpClient#initialize` builds the request base URI directly from `session.shop` with no domain allow-listing:
```ruby
@base_uri = T.let("https://#{api_host || session.shop}", String)
``` [2](#0-1) 

Contrast this with `ShopifyAPI::Auth::ClientCredentials.client_credentials`, which explicitly sanitizes the shop before using it the same way:
```ruby
validated_shop = Utils::ShopValidator.sanitize!(shop)
shop_session = ShopifyAPI::Auth::Session.new(shop: validated_shop)
``` [3](#0-2) 

`ShopValidator.sanitize!`/`sanitize_shop_domain` exist precisely to enforce that a shop value resolves to one of the `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) before it is trusted as a request target: [4](#0-3) 

`validate_auth_callback`'s only checks are: HMAC validity of the query (which the attacker can produce/replay since `shop` is a signable field they choose, and the HMAC is computed with the app's own secret over exactly the fields the attacker supplies), the `Context.private?` flag, and that the browser's state cookie matches `auth_query.state`: [5](#0-4) 
None of these checks constrain `shop` to a Shopify-owned domain. The HMAC binds "this exact set of bytes was not altered", but it does not bind "shop is a legitimate Shopify store domain" — the same class of identity-binding gap described in the report (a value trusted for routing/target-selection purposes that isn't actually checked against the real, authoritative identity it's supposed to represent).

The `to_signable_string` of `AuthQuery` includes `shop` as one of the fields that get signed: [6](#0-5) 
but that only proves the developer's own gem-computed HMAC matches — it says nothing about whether `shop` is `*.myshopify.com`. Since callback URLs are handled directly by the host application (typically an unauthenticated `GET/POST /auth/callback?shop=...&code=...&hmac=...` endpoint), and the library itself performs the outbound request to `https://#{shop}/admin/oauth/access_token` with the app's `client_secret` in the body, control over the `shop` query parameter (which the host app just forwards into `AuthQuery.new(request.parameters...)` per the documented usage) is enough to redirect the credential-bearing POST to an attacker's server.

### Impact Explanation
This is High severity: it is SSRF that carries the application's `client_id`/`client_secret` to an attacker-chosen host, directly matching the "SSRF with the app's credentials" impact category. Successful exploitation exfiltrates the app's `client_secret`, which can subsequently be used to mint access tokens for any shop that installs the app (cross-tenant compromise), effectively escalating to full authentication bypass for the app's OAuth flow.

### Likelihood Explanation
The `shop` value is attacker-influenced input in the exact flow the documentation instructs developers to build: `ShopifyAPI::Auth::Oauth::AuthQuery.new(request.parameters.symbolize_keys...)` fed straight from an unauthenticated HTTP callback endpoint, as shown in the gem's own docs example. [7](#0-6) 
No additional privilege, secret, or prior authentication is required to submit a crafted callback request; the only obstacle is producing a valid HMAC over attacker-chosen `code`/`shop`/`state`/`timestamp`/`host` values, which is feasible in scenarios such as a malicious/rogue shop redirecting its own legitimately-issued OAuth callback (attacker fully controls all signed fields including `shop`, and Shopify itself will produce a valid HMAC for values that pertain to a shop it controls) to a listener the attacker owns.

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop)` in `validate_auth_callback` before constructing `null_session`/`Clients::HttpClient`, mirroring the protection already applied in `ClientCredentials.client_credentials`, so the token-exchange POST (and its embedded `client_secret`) can only ever be sent to a domain in `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
1. App is configured with `client_id`/`client_secret` and exposes an OAuth callback route that does `ShopifyAPI::Auth::Oauth.validate_auth_callback(cookies:, auth_query: AuthQuery.new(request.parameters...))` as shown in the gem's docs.
2. Attacker controls (or is) a shop that starts the normal OAuth flow, but replaces `shop` in the final callback redirect with an alternate value they own that still validly passes the same signed-field format (or an attacker able to trigger the callback with `shop` pointing at infrastructure they control that Shopify itself will happily HMAC-sign, e.g., during a shop takeover / custom-domain scenario, or any case where the relying party doesn't itself independently verify `shop` before invoking this library).
3. `validate_auth_callback` passes `Utils::HmacValidator.validate(auth_query)` since HMAC only checks integrity of the exact bytes supplied.
4. `Clients::HttpClient.new(session: Auth::Session.new(shop: auth_query.shop), ...)` sets `@base_uri = "https://#{attacker_domain}"`.
5. The gem POSTs `{ client_id, client_secret, code, expiring }` to `https://#{attacker_domain}/admin/oauth/access_token`, leaking the app's `client_secret` to the attacker. [8](#0-7) [9](#0-8)

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

module ShopifyAPI
  module Utils
    module ShopValidator
      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
