### Title
Optional slippage protection in `Withdraw` instruction enables sandwich attacks on LP redemptions - (File: `program/src/processor.rs`, `program/src/instruction.rs`)

### Summary
The `Withdraw` instruction's slippage-protection parameters (`min_coin_amount`, `min_pc_amount`) are optional (`Option<u64>`), and the processor only enforces them when *both* are supplied. When a caller omits them (which the reference CLI/SDK does by default — see `slippage_limit: false` in the README example), the withdrawal executes with **no minimum-amount-out guarantee at all**, mirroring the hardcoded `minimum-amount-out = 0` root cause described in the ConvexStrategy report. Because the withdraw transaction is visible in the public mempool before confirmation, an attacker can sandwich it by manipulating pool reserves with swaps immediately before/after the withdrawal, extracting value from the withdrawing user's redemption.

### Finding Description
The `WithdrawInstruction` struct declares the minimum-amount fields as optional: [1](#0-0) 

During unpacking, if the instruction data does not include the extra 16 bytes, both fields default to `None`: [2](#0-1) 

In `Processor`'s withdraw handling, the coin/pc amounts returned to the user are computed purely from the current pool reserves (`total_coin_without_take_pnl`, `total_pc_without_take_pnl`) at the moment the instruction executes, proportional to the LP amount burned: [3](#0-2) 

The slippage check is only performed when **both** `min_coin_amount` and `min_pc_amount` are `Some`; if either is `None`, the withdrawal proceeds unconditionally and transfers whatever `coin_amount`/`pc_amount` the current (attacker-influenced) reserves dictate: [4](#0-3) 

This is functionally identical to the ConvexStrategy issue: a withdrawal path that computes output amounts from state that can be manipulated between mempool-visibility and execution, with no enforced minimum-received guarantee.

### Impact Explanation
An attacker (Eve) who observes Alice's `Withdraw` transaction in the mempool can:
1. Front-run with a `SwapBaseIn`/`SwapBaseOut` (both permissionless, callable by any signer with attacker-chosen accounts) to skew the pool's coin/pc ratio, e.g., dumping the coin token to inflate `total_pc_without_take_pnl` relative to `total_coin_without_take_pnl`.
2. Let Alice's `Withdraw` execute — since `coin_amount`/`pc_amount` are computed off the now-skewed reserves and no `min_coin_amount`/`min_pc_amount` protection was supplied, Alice receives a disadvantageous split of coin/pc tokens (or an output at a manipulated ratio) rather than her fair pro-rata share at the pre-attack price.
3. Back-run with an opposite swap to restore the pool ratio and capture the difference as profit, extracted directly from Alice's redemption.

This results in direct loss of user/LP funds through value extraction during a permissionless, single-transaction sandwich, matching the report's classified "High" difficulty / "Data Validation" impact category.

### Likelihood Explanation
The `Withdraw` instruction is reachable by any unprivileged holder of pool LP tokens. Both `SwapBaseIn`/`SwapBaseOut` used to sandwich it are equally unprivileged and reachable in the same slot/adjacent transactions. Because the vulnerable slippage check is bypassed simply by omitting two optional fields — which is the default behavior exposed by the CLI/SDK per the README (`slippage_limit: false`) — most real-world callers are exposed by default, making this a realistic and low-effort attack for any mempool observer.

### Recommendation
Make `min_coin_amount` and `min_pc_amount` mandatory (non-optional) in `WithdrawInstruction`, or enforce the check independently for each field (i.e., check `min_coin_amount` if `Some`, and separately check `min_pc_amount` if `Some`, rather than requiring both to be present before any check runs). Reject withdrawals with `AmmError::ExceededSlippage` whenever the actual `coin_amount`/`pc_amount` falls below a caller-specified floor, regardless of whether the other bound was supplied.

### Proof of Concept
1. Alice holds LP tokens and submits a `Withdraw` instruction via the CLI/SDK default path, which omits `min_coin_amount`/`min_pc_amount` (`other_amount_min`/`slippage_limit: false`), per [5](#0-4) .
2. Eve observes this in the mempool and submits a `SwapBaseIn` with a large `amount_in` and `minimum_amount_out = 0` (self-imposed, no protection needed since she controls both legs) to shift `amm_coin_vault`/`amm_pc_vault` balances before Alice's transaction lands, per the swap accounting in [6](#0-5) .
3. Alice's `Withdraw` executes; since `withdraw.min_coin_amount.is_some() && withdraw.min_pc_amount.is_some()` is false, the check at [7](#0-6)  is skipped, and Alice receives `coin_amount`/`pc_amount` computed from the manipulated reserves.
4. Eve back-runs with the reverse swap, restoring the pool and pocketing the value skimmed from Alice's withdrawal.
