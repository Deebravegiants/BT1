## Analysis

The strongest analog to the Godmode "stale rate applied over an un-flushed period" bug class is in `pallet-consensus-incentives`, which pays relayers a reward computed as `(latest_height - baseline) * cost_per_block`, where `baseline` is a persisted watermark (`LastRewardedHeight`) rather than the current block. This is structurally identical to Godmode's `last_claimed`/multiplier defect: a rate (`cost_per_block` ≈ multiplier) can be changed while a pending, un-flushed time/height span (the gap between `LastRewardedHeight` and the chain's current height ≈ un-flushed staking period) still exists, and the *new* rate is then applied retroactively across that entire pending span when the next (permissionless) consensus message is delivered.

### Title
Retroactive reward-rate application in pallet-consensus-incentives due to `update_cost_per_block`/`remove_incentives` not checkpointing `LastRewardedHeight` - (`modules/pallets/consensus-incentives/src/lib.rs`)

### Summary
`update_cost_per_block` mutates `StateMachinesCostPerBlock` for a `state_machine_id` in-place, and `remove_incentives` clears it, without ever flushing or resetting the `LastRewardedHeight` watermark for that state machine. [1](#0-0)  The reward calculation reads that stale watermark as the baseline for the *next* payout and multiplies the entire un-rewarded block span by whatever `cost_per_block` happens to be in effect at delivery time, not the rate(s) that were actually in effect while those blocks accrued. [2](#0-1) 

### Finding Description
The reward formula is:
```
reward = (latest_height - baseline) * cost_per_block   // baseline = LastRewardedHeight or previous_height fallback
``` [3](#0-2) 

`LastRewardedHeight` only advances inside `process_message`, which only runs as part of message execution (`on_executed`) — i.e., when a relayer actually delivers a `ConsensusMessage`. [4](#0-3)  Between deliveries, the state machine's underlying height can advance far ahead of `LastRewardedHeight` (e.g., a relayer delaying submission, or a chain that had no `cost_per_block` configured for a long period and is only later enabled). While that gap is open, governance can call `update_cost_per_block` to raise the price with no validation or side effect on the pending gap:
```rust
pub fn update_cost_per_block(...) -> DispatchResult {
    T::IncentivesOrigin::ensure_origin(origin)?;
    StateMachinesCostPerBlock::<T>::mutate(state_machine_id.clone(), |maybe_cost| {
        *maybe_cost = Some(cost_per_block);
    });
    ...
}
``` [5](#0-4) 

When any relayer next delivers a `ConsensusMessage` for that state machine — a fully permissionless action reachable by any unprivileged relayer via `pallet_ismp::handle_unsigned` — `calculate_reward` pays for the *entire* accumulated block span (which accrued under the old, lower rate) at the *new*, higher rate, directly from the treasury. [6](#0-5)  This is the same class of defect described in the Godmode report: a rate parameter (multiplier / `cost_per_block`) is changed without first checkpointing the accrual timer (`last_claimed` / `LastRewardedHeight`), so the new rate is silently and retroactively applied to time/height that already elapsed under the old rate.

### Impact Explanation
This causes an over-payment/drain of the `TreasuryAccount` funds to relayers (and mints matching `ReputationAsset` inflation) whenever the incentives price is raised while a state machine has a large un-rewarded height span outstanding — for example, right after `update_cost_per_block` is first used to enable incentives for a state machine that has been running for a long time, or after a price increase on a chain whose relayer has not submitted recently. The exploiting party (the relayer submitting the message) is an unprivileged, permissionless actor reachable via ordinary `pallet-ismp` message dispatch, and the payout is entirely automatic once the message is accepted — no separate authorization is needed to trigger the drain beyond delivering a normal consensus update.

### Likelihood Explanation
Likelihood is moderate: it requires a governance-driven `cost_per_block` change (a routine, expected operational action, not an attack) to occur while a state machine has an outstanding un-rewarded height gap, followed by any relayer delivering the next consensus message (which relayers do naturally and are economically incentivized to do promptly once a reward is enabled/raised). No malicious admin behavior is needed — a normal price update combined with normal relayer message delivery is sufficient to trigger the miscalculation.

### Recommendation
Before mutating `StateMachinesCostPerBlock` (in `update_cost_per_block`) or clearing it (in `remove_incentives`), settle/checkpoint any pending reward span at the *old* rate: pay out (or explicitly forfeit, with a fixed policy) the span between the current `LastRewardedHeight` and the state machine's latest known height at the old `cost_per_block`, then set `LastRewardedHeight` to the current height so the new rate only applies going forward — mirroring the fix that forces `update_points`-style checkpointing before `add_multiplier`/`remove_multiplier` in the referenced Godmode patch.

### Proof of Concept
1. State machine `SM` has been running and advancing height on Hyperbridge for a long period without `cost_per_block` configured (`StateMachinesCostPerBlock::get(SM) == None`), so no rewards accrue and `LastRewardedHeight::get(SM) == None`.
2. Governance calls `update_cost_per_block(SM, cost_per_block = X)` — a routine price-enablement action. [5](#0-4) 
3. A relayer (unprivileged) submits the next `ConsensusMessage` for `SM` via `pallet_ismp::handle_unsigned`. `calculate_reward` computes `baseline = previous_height` (the chain's previous commitment height, which reflects the full prior history) and pays `(latest_height - previous_height) * X` — potentially a very large span priced entirely at the newly-set rate `X`, even though the price was `None`/zero for essentially all of that historical span. [7](#0-6) 
4. Repeating with a subsequent price increase (rather than first enablement) has the identical effect: any span accrued while `cost_per_block` was `Y` gets paid at the newly-set `X > Y` once the relayer's next message lands, draining the treasury for the difference `(X - Y) * blocks`.

			Ok(())
		}

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

	/// Calculate the reward for a message based on the state machine id
	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}
