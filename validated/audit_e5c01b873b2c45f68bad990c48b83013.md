### Title
Webhook shop-domain (and topic/webhook-id) headers are not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the shop identity (`X-Shopify-Shop-Domain`) and other routing metadata (`X-Shopify-Topic`, `X-Shopify-Webhook-Id`) are read directly from unauthenticated HTTP headers. `Registry.process` verifies the HMAC over the body, then unconditionally trusts these headers to build the `WebhookMetadata` passed to the app's handler. This breaks the binding "the shop the HMAC was computed for" == "the shop the handler is told the webhook came from."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers with no cryptographic binding to the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC (over the body only) and then passes `request.shop`, `request.topic`, and `request.webhook_id` straight into the handler without any additional cross-check that the shop matches the tenant the body actually belongs to: [3](#0-2) 

Because `OpenSSL::HMAC` is computed only over `@raw_body`, the equality that should hold — `HMAC_secret(body) valid` implies `shop-domain header == originating shop of body` — does not hold. An attacker who controls any shop that has the app installed receives genuine webhook deliveries (valid body + valid HMAC, since Shopify signs with the app's own `client_secret`). The attacker can capture one such delivery and replay it to the app's public webhook endpoint after only changing the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to a victim shop's domain. `Utils::HmacValidator.validate` still succeeds because it only checks `to_signable_string` (`@raw_body`) against the received HMAC — the header modification is invisible to the signature check: [4](#0-3) 

The app's handler then receives `WebhookMetadata` claiming the data belongs to the victim shop, even though the payload actually originated from the attacker's own shop.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged merchant/app-installer (attacker on their own shop) can make the host application process attacker-supplied webhook data (and attacker-chosen topic, including mandatory GDPR topics like `shop/redact`, `customers/redact`, `customers/data_request`) under the identity of a completely different, victim shop. Any host application that keys persistence, deletion, or business logic off `WebhookMetadata#shop` (as the docs instruct apps to do) can have its per-tenant data corrupted or manipulated by an attacker with no privileged credentials, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
The attacker only needs: (1) their own working, unprivileged installation of the target app (any merchant can install a public app), and (2) the ability to send an HTTP POST to the app's known webhook endpoint with modified headers, which any internet client can do. No access token, `client_secret`, or session is required — only observation of one legitimate webhook body+HMAC pair from the attacker's own store.

### Recommendation
Include the shop domain (and ideally the topic/webhook id) inside the HMAC-verified signing material, or otherwise cryptographically bind the `X-Shopify-Shop-Domain` header to the payload before trusting it (e.g., cross-check it against a shop already known to be associated with a valid, stored session/access token before dispatching to handlers), rather than trusting the header verbatim after only validating the raw body's HMAC.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. for `orders/create`, with headers:
   - `X-Shopify-Hmac-Sha256: <valid HMAC of body>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Topic: orders/create`
2. Attacker resends the exact same body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but changes:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - (optionally) `X-Shopify-Topic: shop/redact`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `@raw_body` — validation succeeds because the body is unchanged.
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the host app to act on/store data as if it came from `victim-shop.myshopify.com`, despite the request never having been signed for that shop.
