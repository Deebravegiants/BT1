### Title
`StreamingYieldVault.totalAssets()` underflows and permanently bricks the vault when the underlying asset balance falls below the pending locked-yield tranche - ([File: sdk/packages/core/contracts/vaults/StreamingYieldVault.sol])

### Summary
`StreamingYieldVault.totalAssets()` computes `balanceOf(this) - _lockedYield()`, an unchecked Solidity 0.8 subtraction that reverts on underflow if the underlying token's real balance in the vault ever drops below the size of the currently-vesting tranche. Every ERC-4626 entrypoint (`deposit`, `mint`, `withdraw`, `redeem`, `maxWithdraw`, `convertToAssets/Shares`) routes through `totalAssets()`, so once this condition occurs the vault becomes permanently unusable for all depositors, including the intent solver treasury positions documented as sourcing live fills from these vaults.

### Finding Description

and `_lockedYield()` returns the not-yet-vested portion of the current tranche: [2](#0-1) 

The contract's own comments acknowledge this exact underflow risk and go out of their way to sequence `addYield`'s transfer before marking the tranche locked, specifically to avoid a *transient* underflow on the very first tranche: [3](#0-2) 

However, that guard only protects the `addYield` call path. It does nothing to protect against the underlying asset's balance decreasing through means outside the vault's own transfer logic while a tranche is vesting — e.g., a fee-on-transfer/rebasing/slashable underlying token, an external exploit or blacklist/clawback event on the asset contract, or any other mechanism (analogous to the Notional cToken/exchange-rate haircut scenario in the referenced report) that reduces `balanceOf(vault)` independent of vault-mediated transfers. If `balanceOf(this)` ever drops below `_lockedYield()`, `totalAssets()` reverts unconditionally with an arithmetic underflow, and there is no fallback path — `_lockedYield()` cannot itself be reduced or written off; it only decreases with elapsed time, not with the token's real backing.

This is a direct structural analog of the reported Notional bug class: an accounting function built as `currentValue - previousExpectedValue` reverts when the actual value falls below the expected value, and that revert propagates to block core financial operations that must remain available regardless of external losses.

### Impact Explanation
Because `totalAssets()` underlies every ERC-4626 view and mutating function in the OpenZeppelin base contract, once the underflow condition is reached:
- No depositor (including the solver operating this vault as treasury per `docs/content/developers/evm/simplex/treasury.mdx` and `VaultFundingPlanner`/`VaultLiquidityState`) can `deposit`, `withdraw`, or `redeem`.
- `maxWithdraw`/`maxDeposit` calls used by the intent-solver's funding planner will also revert or misbehave, since they depend on `convertToAssets`/`totalAssets`.
- All value already deposited into the vault (solver treasury funds sourcing live fills, and any LP's principal) becomes permanently frozen until/unless the underlying asset's balance recovers above the locked-yield threshold — which, for a genuine external loss, may never happen.

This satisfies the "permanent freezing of funds" impact bar: solver capital parked in the vault (used to fund intent fills per `docs/content/developers/evm/simplex/treasury.mdx`) is locked with no owner-level remediation path exposed in the contract (there is no function to write down `_vestingAmount`/`_vestingStart` or otherwise reconcile a shortfall).

### Likelihood Explanation
The vault is explicitly designed to hold arbitrary ERC-4626-eligible/ERC-1363 underlying tokens as configured by solver operators (the docs mention Aave `stataToken` as an example asset), so the operator, not the vault author, controls which token is used. Any underlying asset with fee-on-transfer semantics, negative rebasing, a blacklist/freeze/clawback function (e.g., regulated stablecoins), or exposure to an external protocol exploit can trigger the condition without any malicious action by the vault's owner or Hyperbridge governance — it is a property of the chosen underlying asset combined with the vesting mechanism's un-recoverable subtraction. Given multiple real-world token classes exhibit these properties and the vault is intended for general stablecoin treasuries, likelihood is realistic, not purely theoretical.

### Recommendation
Make `totalAssets()` loss-tolerant instead of reverting:
```solidity
function totalAssets() public view override returns (uint256) {
    uint256 bal = IERC20(asset()).balanceOf(address(this));
    uint256 locked = _lockedYield();
    return bal > locked ? bal - locked : 0;
}
```
Additionally consider capping `_lockedYield()` at the current balance, or adding an owner/governance-gated function to writhe down `_vestingAmount` when the underlying balance is proven to be permanently short, and add explicit tests exercising a `balanceOf(vault) < _lockedYield()` scenario alongside the existing "underflow safety" test suite in `StreamingYieldVault.t.sol`.

### Proof of Concept
1. Deploy `StreamingYieldVault` with an underlying token that can have its balance reduced by parties other than the vault (e.g., a mock token with an owner-controlled `burnFrom`, or any fee-on-transfer/rebasing/blacklistable stablecoin).
2. Seed the vault with a deposit, then call `addYield(amount)` to start a tranche (`_vestingAmount = amount`, `_vestingStart = now`).
3. While the tranche is vesting (`block.timestamp < _vestingStart + VEST`), trigger an external reduction of the vault's raw token balance (e.g., simulate the token issuer freezing/burning part of the vault's balance, or an underlying money-market exploit reducing the wrapped token's redeemable value) such that `balanceOf(vault) < _lockedYield()`.
4. Call `totalAssets()`, `deposit()`, `withdraw()`, or `redeem()` — all revert with an arithmetic underflow (`balanceOf(this) - _lockedYield()` underflows), and this condition persists as long as the shortfall exists, since nothing in the contract can reduce `_lockedYield()` other than the passage of time down to the (still-unrecoverable) full tranche amount.

```text
    /// @dev Linear unlock of the current tranche, keyed on `block.timestamp` so that a deposit
    ///      and withdrawal within the same block observe an identical, unchanged share price.
    function _lockedYield() internal view returns (uint256) {
        uint256 start = _vestingStart;
        uint256 elapsed = block.timestamp - start;
        if (elapsed >= VEST) return 0;
        return (_vestingAmount * (VEST - elapsed)) / VEST;
    }
```
