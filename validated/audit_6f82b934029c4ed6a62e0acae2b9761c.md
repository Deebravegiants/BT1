### Title
Webhook Shop/Topic Identity Spoofing via HMAC Signature Covering Only the Raw Body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC signature only to the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` — all derived from unauthenticated HTTP headers — are trusted downstream as verified tenant/identity claims by `Webhooks::Registry.process`. This breaks the identity binding `hmac ≟ (shop, topic, body)` down to just `hmac ≟ body`, letting a holder of one valid `(body, hmac)` pair replay it with a forged `shop-domain` header and have it accepted as coming from a different, arbitrary shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and the header-derived accessors `shop`, `topic`, `webhook_id`, `api_version` are pulled straight from attacker-controlled HTTP headers with no cryptographic binding to the payload or to each other: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC against this signable string only, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` as authenticated identity fields when dispatching to the merchant/app handler: [4](#0-3) 

The test fixtures confirm the HMAC is computed strictly over the body string (e.g. `"{}"`), never over headers such as `shop-domain`: [5](#0-4) 

The equality that should hold is:
`hmac == HMAC(secret, body || shop || topic)`
but the gem only enforces:
`hmac == HMAC(secret, body)`

Since a merchant/app can install the target app on their own store (an "unprivileged internet user" action), they legitimately receive real webhooks with valid `(raw_body, hmac)` pairs signed with the app's real secret. Because the webhook HTTP endpoint is a public, unauthenticated URL (that's the entire point of Shopify webhook delivery), the attacker can replay that exact `(raw_body, hmac)` pair to the app's endpoint while swapping the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to point at a victim shop. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` then calls the app's handler with `shop: <victim>` and attacker-controlled `body`.

### Impact Explanation
This crosses the tenant boundary this gem is supposed to enforce for webhook processing: an attacker can make the host application believe attacker-controlled webhook content originated from a shop they do not own or control. Any app logic keyed on `WebhookMetadata#shop` (e.g., updating that shop's local records, revoking access, syncing inventory, billing events) can be poisoned with attacker-chosen data under another tenant's identity — cross-tenant access/impersonation, rated Critical per the given impact classification.

### Likelihood Explanation
Moderately likely to be exploitable in practice: the attacker needs only (1) their own store with the target app installed to harvest a genuine `(body, hmac)` pair for a chosen topic, and (2) knowledge of the target webhook endpoint URL (which is public/unauthenticated by design) and the victim's shop domain (also public, e.g., `victimshop.myshopify.com`). No secrets, tokens, or privileged access are required — only interaction with the gem's own signature-verification and dispatch code path.

### Recommendation
Include the identity-critical header fields (`shop`, `topic`, and ideally `webhook_id`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the verified payload before they are propagated to `WebhookMetadata`. At minimum, `Registry.process` should not treat `request.shop`/`request.topic` as trusted/verified unless those values are covered by the signature check, and documentation/consumers should be warned that these header fields are unauthenticated.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST: headers (`X-Shopify-Topic`, `X-Shopify-Hmac-Sha256`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, ...) and `raw_body`.
2. Attacker resends this exact `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (== `raw_body` only) and matches the replayed signature — validation passes.
4. The app's registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: <attacker's own order payload>, ...)`, causing the host application to process attacker-controlled data under the victim shop's identity.
