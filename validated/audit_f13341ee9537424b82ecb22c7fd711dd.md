Confirmed: `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, and `webhook_id` are read directly from unauthenticated headers [2](#0-1) , and `Registry.process` uses `request.shop` for handler dispatch after validating only the body HMAC [3](#0-2) .

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body [4](#0-3) . The `shop`, `topic`, and `webhook_id` values used to route and act on the webhook come from HTTP headers that are never included in the signed payload [5](#0-4) . Because the app's `client_secret`/HMAC key is a single, app-wide secret shared across every merchant that has installed the app (not a per-shop secret), any unprivileged Shopify merchant who installs the app can capture a legitimately-signed `(body, hmac)` pair from their own store's webhooks, then replay that exact body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a victim shop's domain. `HmacValidator.validate` will still pass because it only recomputes the signature over `@raw_body` [6](#0-5) , and `Registry.process` will hand the spoofed shop to the registered handler as if it were an authentic event for that shop [3](#0-2) .

### Finding Description
The identity binding that should hold is: `shop value cryptographically bound in the HMAC == shop value the handler acts on`. In this gem, that equality does not hold — `to_signable_string` only returns `@raw_body` [1](#0-0) , so `shop`, `topic`, and `webhook_id`, all read straight from attacker-controllable HTTP headers via `shopify_header` [7](#0-6) , are never part of what `OpenSSL.secure_compare` verifies in `HmacValidator.validate_signature` [8](#0-7) .

`Registry.process` builds `WebhookMetadata` directly from `request.shop`, `request.topic`, and `request.webhook_id` after only confirming the body's HMAC, then dispatches it to the host app's handler [3](#0-2) . This means an app-level secret (identical for all shops using the app) combined with a body that any installer can legitimately obtain is sufficient to forge webhooks that are attributed to an arbitrary victim shop, as long as the JSON body content itself doesn't need to differ (e.g., topics like `app/uninstalled`, `shop/update`, or any topic whose body schema is shop-independent or guessable/constant).

### Impact Explanation
This is a Critical-severity cross-tenant issue: it lets an attacker who is merely an unprivileged installer of the vulnerable app impersonate webhook traffic from any other merchant shop that also uses the app, without ever needing that victim's or the app's `client_secret`. Depending on what the host application does inside its webhook handler (e.g., deactivating the shop's session on `app/uninstalled`, triggering data deletion on `shop/redact`, or updating billing/shop state), this can be leveraged to disrupt or manipulate another tenant's data purely by replaying an intercepted body+HMAC pair with a different `shop-domain` header.

### Likelihood Explanation
Exploitation only requires the attacker to be a legitimate installer of the target app on their own store (a standard, unprivileged action available to any Shopify merchant), and to control the raw HTTP headers of the request they send to the app's public webhook endpoint (any HTTP client can set arbitrary headers). No possession of the app's `client_secret`, no TLS interception, and no privileged account are required, only the ability to capture one legitimately-signed webhook body from their own installation and replay it with modified headers.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (in addition to the body) in the value that is HMAC-verified, or independently verify that the shop domain in the header matches a shop known to have a legitimate, currently-registered subscription for that topic before invoking the handler. At minimum, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate the shop-identifying headers so `HmacValidator.validate` binds them cryptographically, closing the gap between what is signed and what is trusted for dispatch.

### Proof of Concept
1. Install the vulnerable app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook (e.g. `app/uninstalled`) and capture the raw request: headers `X-Shopify-Hmac-Sha256: <hmac>`, `X-Shopify-Topic: app/uninstalled`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, and raw body `B`.
2. Replay a POST to the app's webhook endpoint with the identical body `B` and identical `X-Shopify-Hmac-Sha256` header, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` computes `hmac` from the header and `to_signable_string` from `B` only [9](#0-8) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` with the app's secret and matches the captured signature — validation passes [4](#0-3) .
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes it as if it were a genuine event from the victim shop [10](#0-9) .
