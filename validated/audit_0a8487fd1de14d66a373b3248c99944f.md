Audit Report

## Title
JWT replay guard in `WorkflowMetadataHandler.Authorize` is check-then-act, not atomic, allowing a single-use trigger token to authorize two concurrent workflow executions - (File: `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`)

## Summary
`Authorize` verifies an inbound HTTP-trigger request's JWT and is meant to enforce single-use ("replay protection") semantics via `jwtReplayCache`, but the "already used?" check (`isReplay`, under `RLock`) and the "mark as used" write (`recordUsage`, under a separate `Lock`) are two independent critical sections rather than one atomic check-and-set [2](#0-1) . Two concurrent requests carrying the identical `jti` can both pass `isReplay` before either calls `recordUsage`, letting a single signed JWT authorize two workflow executions.

## Finding Description
`Authorize` calls `h.jwtCache.isReplay(claims.ID)` early, and only calls `h.jwtCache.recordUsage(claims.ID)` at the very end, after the authorized-key lookups succeed [3](#0-2) . The two cache methods take separate locks on the same `sync.RWMutex`:

```go
func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()
	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()
	cache.cache[jti] = time.Now()
}
``` [4](#0-3) 

If two goroutines process requests with the same `jti` concurrently, both can observe `exists == false` in `isReplay` before either has executed `recordUsage`. Both then pass the replay check, both pass the authorized-signer lookup (which is a read against `h.authorizedKeys` and doesn't gate on the JWT cache at all), and both call `recordUsage` (a harmless idempotent overwrite), returning a valid `*gateway.AuthorizedKey` to each caller. `Authorize` is invoked from `httpTriggerHandler.authorizeRequest`, which is called by `HandleUserTriggerRequest` before dispatching the trigger to DON nodes [5](#0-4) , [6](#0-5) . There is no other atomic guard between the two authorization calls — the existing repository test only exercises the sequential (non-concurrent) case and asserts the second sequential call fails [7](#0-6) , which does not cover the concurrent race and does not demonstrate the guard is safe under concurrency. The comparable `vault.RequestReplayGuard.CheckAndRecord` correctly performs the check and the write under a single lock [1](#0-0) , confirming that the split-lock design in `jwtReplayCache` is an outlier and not an intentional architectural choice.

## Impact Explanation
A successful race lets one signed, single-use trigger JWT authorize more than one workflow execution/trigger dispatch to the DON, which is a duplicate/unauthorized job run stemming from a broken replay/authentication guard — an in-scope impact class (unauthorized job run from an authentication bypass). This requires no privileged role, no node compromise, and no cryptographic break — only concurrent submission of an otherwise-legitimate signed request that any unprivileged workflow caller already possesses.

## Likelihood Explanation
The race window between the `isReplay` read and the `recordUsage` write is narrow (only the authorized-key map lookups occur in between) but is real and independently reproducible by an attacker deliberately sending the same signed request twice over parallel connections; it does not depend on any external timing coincidence, host-level access, or privileged role — only ordinary internet-facing HTTP access to the gateway's trigger endpoint that an unprivileged caller already has by design.

## Recommendation
Merge `isReplay` and `recordUsage` into a single atomic check-and-set method under one lock, e.g.:
```go
func (cache *jwtReplayCache) checkAndRecord(jti string) bool {
	cache.mu.Lock()
	defer cache.mu.Unlock()
	if _, exists := cache.cache[jti]; exists {
		return false
	}
	cache.cache[jti] = time.Now()
	return true
}
```
and have `Authorize` reserve the `jti` via this single atomic call before any further authorization work proceeds, mirroring the already-correct pattern in `vault.RequestReplayGuard.CheckAndRecord`.

## Proof of Concept
1. Obtain one valid, signed HTTP-trigger JSON-RPC request with JWT claim `jti = X` for a registered workflow (as constructed by `createTestJWTToken` in the existing test suite).
2. Fire two goroutines that both call `handler.HandleUserTriggerRequest` (or directly `workflowMetadataHandler.Authorize`) concurrently with the identical request/token.
3. Because `isReplay`/`recordUsage` are separate lock sections, both goroutines can observe `isReplay(X) == false` before either records usage, so both return a non-nil `*gateway.AuthorizedKey` and no error.
4. Extend the existing `TestHttpTriggerHandler_HandleUserTriggerRequest` "duplicate JWT token and request ID" subtest [7](#0-6)  to invoke the two `HandleUserTriggerRequest` calls concurrently (e.g., via goroutines with a `sync.WaitGroup`/barrier synchronizing entry to `Authorize`) instead of sequentially, and assert that both succeed (or that `mockDon.SendToNode` is invoked for both callbacks), demonstrating the double-authorization.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
