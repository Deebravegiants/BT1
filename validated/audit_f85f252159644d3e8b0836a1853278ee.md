This confirms the core finding: the webhook HMAC in `lib/shopify_api/webhooks/request.rb` is computed only over `@raw_body` (`to_signable_string` returns `@raw_body`, line 36-38), while `shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers (lines 15-33) that are never included in the signed bytes. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) validates only this body-HMAC via `Utils::HmacValidator.validate(request)` and then forwards `request.shop` directly into `WebhookMetadata` used by the host app's handler, without any cross-check that the header-supplied shop actually corresponds to the body/HMAC that was validated.

### Title
Webhook shop/topic/webhook-id identity is not bound to the HMAC-verified bytes, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body, while `shop`, `topic`, `api_version`, and `webhook_id` are taken from unauthenticated HTTP headers.

### Finding Description
The identity binding that should hold is: `hmac_valid(raw_body) == true` implies `request.shop is the tenant that actually sent raw_body`. In this implementation, `hmac` is computed by `Digest.hexencode(Base64.decode64(shopify_header("hmac-sha256")))` [1](#0-0)  and verified via `HmacValidator.validate`, which only signs/verifies `to_signable_string`, i.e., `@raw_body` [2](#0-1) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors read directly from headers that are never part of the signed payload [3](#0-2) . `Registry.process` validates the HMAC and then trusts `request.shop`/`request.topic`/`request.webhook_id` as authenticated facts when constructing `WebhookMetadata` passed to the app's handler [4](#0-3) . Because these fields are never covered by the HMAC, they can be altered independently of the signed body while the signature check still passes, exactly the "field acted on but not covered by the HMAC" pattern highlighted in the analog bug class.

### Impact Explanation
A host application built on this gem is expected to trust `WebhookMetadata#shop` (and `topic`/`webhook_id`) as an authenticated tenant identifier once `Registry.process` succeeds, since that is the only verification step the gem performs. Because the header-derived shop is unauthenticated, this creates a possible cross-tenant data/action confusion in the consuming app: a webhook payload's signature only proves the body's authenticity for whatever shop actually holds the shared `client_secret`/webhook signing key, but the module lets the shop identity attached to that verified body be substituted at the HTTP layer. This matches the "cross-tenant access" impact class.

### Likelihood Explanation
Exploitation requires the ability to deliver an HTTP POST to the app's webhook endpoint with attacker-controlled headers alongside a body/HMAC pair that is valid for the shared secret (e.g., replaying or relaying a webhook the attacker's own shop legitimately receives, while swapping the `shop-domain`/`topic`/`webhook-id` headers before it reaches the app). No `api_secret_key`, access token, or privileged account is required beyond having any shop that can trigger a webhook delivery to a reachable endpoint, and no host-application misuse is needed — the gem itself treats the header value as trustworthy once body-HMAC validation passes.

### Recommendation
Bind the shop/topic/webhook-id to the verified payload instead of trusting bare headers: include these fields in the signable string used for the HMAC computation (mirroring how `Auth::Oauth::AuthQuery#to_signable_string` incorporates `shop` into the signed content [5](#0-4) ), or otherwise cryptographically bind the header-derived shop to the body before exposing it via `WebhookMetadata`.

### Proof of Concept
1. Attacker owns/controls a Shopify dev store and installs the target app, so Shopify legitimately delivers a webhook: `body = B`, headers include `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
2. Attacker intercepts/relays this HTTP request to the app's webhook endpoint but rewrites `x-shopify-shop-domain` to `victim.myshopify.com` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) while leaving `body` and `x-shopify-hmac-sha256` untouched.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: tampered_headers)` builds successfully since all required headers are present [6](#0-5) .
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares — it matches because `B` was untouched [7](#0-6) .
5. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", ...)` [8](#0-7)  — the app now processes attacker-supplied body content as though it belongs to `victim.myshopify.com`, despite the HMAC never having authenticated that shop/topic association.
