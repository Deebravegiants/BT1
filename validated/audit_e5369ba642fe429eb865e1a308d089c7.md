### Title
Unbounded scrypt cost parameters (n/r/p) from untrusted metadata enable CPU/memory DoS during unlock/import - (File: libraries/secure-container/src/crypto.js)

### Summary
`stretchPassphrase` passes `n`, `r`, `p` directly into `scrypt()` with no upper-bound validation, and these values originate from attacker-controlled, wire-decoded `metadata.scrypt` fields when importing/opening an untrusted `.seco` file. Because `boxDecrypt`/`decryptBlobKey` simply merge decoded metadata into scrypt params without sanitization, a crafted file can force the unlock pipeline to allocate excessive memory or burn excessive CPU inside `scrypt()`.

### Finding Description
The metadata format stores `n`, `r`, `p` as raw `UInt32BE` fields with no range constraints: [1](#0-0)  and `decode()` performs no validation beyond a size warning: [2](#0-1) .

`decryptBlobKey` forwards `metadata.scrypt` (fully attacker-controlled after decode) straight into `boxDecrypt`: [3](#0-2) .

`boxDecrypt` only fills in defaults for missing keys via object spread — it does not clamp or validate values that ARE present, then calls `stretchPassphrase`: [4](#0-3) .

`stretchPassphrase` itself performs no bound check on `n`/`r`/`p` (i.e., no cap on `n*r*p` memory/CPU cost) before invoking `scrypt()`: [5](#0-4) .

The reachable call chain from an untrusted imported file is: `metadata.decode(maliciousMetadata)` → `metadata.decryptBlobKey(metadata, passphrase)` → `boxDecrypt(passphrase, blob, {iv, authTag}, metadata.scrypt)` → `stretchPassphrase(passphrase, {n: huge, r: huge, p: huge})` → `scrypt(...)`. Nothing in `crypto.js` or `metadata.js` rejects excessive `n`/`r`/`p` combinations before this point.

Note: I could not locate the implementation of the underlying `@exodus/crypto/scrypt` dependency in this repo's index (it is an external package), so I cannot confirm whether that library independently enforces a hard memory/CPU ceiling (e.g., a `maxmem`-style guard). Regardless, the `secure-container` library itself — the code under audit — provides no application-level bound, so it relies entirely on an unverified downstream dependency to prevent this DoS.

### Impact Explanation
If the underlying scrypt implementation does not enforce a resource ceiling (or enforces one that still permits multi-second/multi-hundred-MB computations), an attacker-crafted `.seco` import file can cause excessive CPU/memory consumption when a user attempts to unlock/import it, degrading availability of the unlock flow (main-thread/worker stalls, OOM, app crash on constrained devices such as mobile/browser extension contexts). This matches an availability-degradation impact rather than key/secret disclosure or signing bypass; it does not by itself grant funds access or auth bypass, but could hinder lock-state checks or force restart/retry behavior in callers.

### Likelihood Explanation
Preconditions are met by the threat model: an unprivileged attacker can supply a crafted metadata blob (e.g., via a malicious file sent for import) prior to any decrypt call. The path is straightforward and requires no valid passphrase — `scrypt()` is invoked before password verification succeeds or fails, since `aesDecrypt`'s auth-tag check occurs only after the (potentially expensive) key stretching completes: [4](#0-3) . This makes the DoS trivially repeatable per malicious file with no rate-limit or pre-check in this library.

### Recommendation
Add explicit upper bounds on `n`, `r`, `p` (and on the derived cost `n*r*p`, and memory cost `128*n*r`) in `stretchPassphrase`/`boxDecrypt`/`metadata.decryptBlobKey` before calling `scrypt()`, rejecting metadata whose parameters exceed a sane maximum (e.g., matching `createScryptParams()` defaults or a documented ceiling), independent of whatever protection the underlying `@exodus/crypto/scrypt` package may or may not provide.

### Proof of Concept
Add a fuzz/unit test in `libraries/secure-container/src/__tests__/crypto.test.js`:
```js
test('stretchPassphrase should reject excessive scrypt cost params', async (t) => {
  t.plan(1)
  const passphrase = 'x'
  const salt = randomBytes(32)
  const maliciousParams = { salt, n: 2 ** 30, r: 2 ** 20, p: 2 ** 20 } // huge memory/CPU cost
  await t.rejects(
    () => scCrypto.stretchPassphrase(passphrase, maliciousParams),
    /parameter.*(exceed|too large|invalid)/i,
    'should reject unbounded scrypt params before calling scrypt()'
  )
})
```
Expected (pre-fix): either the test times out / consumes excessive memory, or passes through to `scrypt()` without an application-level guard rejecting the parameters. Expected (post-fix): `stretchPassphrase`/`boxDecrypt` throws a validation error before invoking `scrypt()`, with a documented hard upper bound on `n`, `r`, `p`.
