### Title
OAuth callback trusts unvalidated `shop` parameter to build the access-token exchange URI, leaking `client_secret` to an attacker-controlled host - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the URI used to exchange the OAuth `code` for an access token (a request that carries `client_id`, `client_secret`, and `code`) directly from `auth_query.shop`, without ever passing it through `Utils::ShopValidator.sanitize!`. Every other credential-bearing flow in this gem (`TokenExchange.migrate_to_expiring_token`, `ClientCredentials`, `RefreshToken`, the storefront GraphQL client) explicitly sanitizes the `shop` value against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before using it to build a request URL, but the classic authorization-code callback path does not.

### Finding Description
In `validate_auth_callback` [1](#0-0) , the only check performed on the query is the HMAC check via `Utils::HmacValidator.validate(auth_query)` [2](#0-1) , plus a nonce/state comparison against the cookie. The HMAC is computed over `code`, `host`, `shop`, `state`, `timestamp` [3](#0-2)  using the app's own `api_secret_key` [4](#0-3) . This HMAC is generated by Shopify itself when Shopify redirects the merchant's browser back to the app's callback URL — it does **not** prove that `shop` is a real, trusted `*.myshopify.com` domain, only that Shopify (not a third party) produced this particular query string for whatever `shop` value the OAuth authorization flow was started with.

`null_session = Auth::Session.new(shop: auth_query.shop)` is built directly from this unsanitized value [5](#0-4) , and it is used as the session for `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` [6](#0-5) , which is responsible for constructing the base host for the `access_token` POST request that includes `client_id`, `client_secret`, and `code` in its body [7](#0-6) . Because `Session`'s `shop` attribute drives the request host and there is no `ShopValidator.sanitize!` call anywhere on this path, whatever string reaches `shop` in `AuthQuery` is trusted implicitly to be a legitimate Shopify host.

Contrast this with `TokenExchange.migrate_to_expiring_token`, which explicitly calls `validated_shop = Utils::ShopValidator.sanitize!(shop)` before constructing the session used for the same kind of `client_secret`-carrying request [8](#0-7) . The identity binding that should hold is: *the host that receives the app's `client_secret` == a Shopify-trusted domain validated by `ShopValidator`*. In `validate_auth_callback`, that binding is broken — the host is taken from `auth_query.shop`/`Session#shop` with no `ShopValidator` check, so "verified by HMAC" is silently substituted for "verified to be a trusted Shopify domain."

### Impact Explanation
If a `shop` value that is not sanitized against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` can reach `AuthQuery#shop` and be signed by Shopify's own OAuth flow (e.g., via `begin_auth`, which also builds `auth_route` from an unsanitized `shop` and would forward it unchanged through Shopify's redirect), the resulting callback would cause the host application to POST the app's `client_id`, `client_secret`, and authorization `code` to a host derived from attacker-influenced data instead of a domain that `ShopValidator` would have accepted. This matches the High-impact class of "credential leakage" / SSRF carrying the app's credentials, since `client_secret` is transmitted based on an unchecked host.

### Likelihood Explanation
Likelihood is Low: exploitation requires the host application to accept an attacker-supplied `shop` value on the `begin_auth` entry point without first normalizing/validating it via `ShopValidator` itself (many integration guides sanitize `shop` before calling `begin_auth`), and the HMAC still ties the `shop` to a query Shopify actually signed for that same value. However, the gem provides no defense-in-depth here — unlike every sibling OAuth-adjacent flow in this codebase, `validate_auth_callback`/`begin_auth` never invoke `ShopValidator.sanitize!`, so the gem itself does not enforce the trusted-domain invariant that it enforces everywhere else.

### Recommendation
In `lib/shopify_api/auth/oauth.rb`, sanitize `shop` with `Utils::ShopValidator.sanitize!(shop)` (as already done in `token_exchange.rb`) at the start of both `begin_auth` and `validate_auth_callback`, before it is used to build `auth_base_uri`, `AuthQuery`, or `Auth::Session`. This ensures the host that ultimately receives `client_id`/`client_secret` during the `/admin/oauth/access_token` exchange is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`, matching the pattern already used in `TokenExchange`, `ClientCredentials`, and `RefreshToken`.

### Proof of Concept
1. A host application calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: attacker_supplied_shop, redirect_path: "/callback")` without first sanitizing `attacker_supplied_shop` via `ShopValidator` [9](#0-8) .
2. `auth_base_uri(shop)` builds `https://#{shop}/admin/oauth/authorize?...` directly from the unsanitized value [10](#0-9) .
3. Shopify's OAuth authorize endpoint (or the flow driving it) redirects back to the app's callback with a `shop` value and an HMAC computed over that same value.
4. `validate_auth_callback` verifies the HMAC succeeds (as it will, since it matches what was echoed back) and, without any `ShopValidator` check, uses `auth_query.shop` to build the `Session` passed into `Clients::HttpClient`, causing the POST containing `client_id`/`client_secret`/`code` to be sent to a host derived from that value [11](#0-10) .

Note: full exploitability depends on how the host application sources the initial `shop` value passed into `begin_auth`; this could not be independently confirmed beyond the library boundary, since the gem's own code path performs no `ShopValidator` check anywhere in `oauth.rb`, unlike its sibling flows.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))
