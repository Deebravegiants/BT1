### Title
Non-embedded session cookie value is an unsigned, guessable session identifier (`offline_{shop}`) - (File: lib/shopify_api/utils/session_utils.rb)

### Summary
For non-embedded (and cookie-fallback) apps, `ShopifyAPI::Auth::Oauth::SessionCookie#value` is set to the raw `Session#id`, and that same raw value is read back unauthenticated by `SessionUtils.cookie_session_id`/`current_session_id` and handed to the host app as "the session to load." Because offline session IDs are generated as the deterministic string `"offline_#{shop}"`, the identifier that binds a browser to a merchant's stored access token is not cryptographically bound to anything the gem verifies — it is just bytes an attacker can compute for any public shop domain.

### Finding Description
When OAuth completes for a non-embedded (or non-JWT/cookie fallback) app, `ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the session cookie directly from the session id: [1](#0-0) 

The session id for offline sessions is fully deterministic and derived only from the public shop domain: [2](#0-1) 

Later, when authenticating an incoming request, `SessionUtils.current_session_id` and `cookie_session_id` return this cookie's value **verbatim**, with no signature, HMAC, or other proof of provenance: [3](#0-2) [4](#0-3) 

The documented usage pattern instructs host apps to persist `session.id` and hand this exact cookie value back to `SessionRepository` for lookup, with no mention that the app must independently authenticate the cookie value beyond `secure`/`httpOnly` flags: [5](#0-4) 

The identity binding that is broken: **cookie value used as session lookup key == a value only obtainable by the legitimate session holder**. In fact: **cookie value == `"offline_" + shop`**, a string computable by anyone who knows the shop's domain (which is public — it's the store's own URL). The gem never re-derives or re-verifies this id against a signed artifact (unlike the JWT/token-exchange path, where `shop` comes out of an HS256-signed `dest` claim verified by `JwtPayload`). There is no HMAC, no signature, and no per-session secret componentized into this identifier.

This directly parallels the reported `swEXIT` bug class: a value that determines which tenant's funds/credentials are acted upon (`_processedRate` vs. `rateWhenCreated`) is accepted from an unauthenticated source rather than being derived from a verified source (`swETHToETHRate`). Here, the value that determines which merchant's access token is returned to the caller (`cookie_session_id`) is accepted verbatim from a client-controlled cookie rather than being derived from any signed source.

### Impact Explanation
If a host app follows this gem's own documented pattern verbatim (storing sessions keyed by `session.id` and retrieving them using `SessionUtils.current_session_id`'s cookie fallback, without adding its own independent session-cookie signing), an attacker who knows or guesses a target shop's `myshopify.com` domain can set their own browser's `shopify_app_session` cookie to `offline_{target-shop}.myshopify.com` and be treated by the host app as though they hold that shop's session — resulting in cross-tenant access to another merchant's stored offline access token and API scope. This matches the Critical category "cross-tenant access."

### Likelihood Explanation
Exploitability depends on the host app relying solely on the gem's documented, unsigned cookie value as an opaque bearer/session key (as the docs literally show), rather than adding independent CSRF/session-integrity protections. Because this is exactly what `docs/usage/oauth.md` demonstrates and what `SessionUtils.cookie_session_id` implements with zero verification, and because offline session ids are fully predictable from a public shop domain, this is a design-level weakness in the gem's own session-cookie contract, not merely a case of the host app ignoring documented guidance.

### Recommendation
Do not use the raw, predictable `session.id` as the cookie value. Instead, mint a random, unguessable session identifier for the cookie (or better, an HMAC/signed token binding the session id to a per-app secret) at cookie-creation time in `Oauth.validate_auth_callback`/`SessionCookie`, and verify that signature in `SessionUtils.cookie_session_id` before trusting the value to look up a stored session, mirroring the protection already used for the JWT/token-exchange path via `JwtPayload`.

### Proof of Concept
1. Configure a non-embedded app; a victim shop `victim-shop.myshopify.com` completes OAuth normally, and the host app stores an offline session keyed by `session.id == "offline_victim-shop.myshopify.com"` per the documented pattern in `docs/usage/oauth.md`.
2. Attacker, knowing the public shop domain `victim-shop.myshopify.com`, sets their own browser's cookie `shopify_app_session=offline_victim-shop.myshopify.com`.
3. Attacker requests any authenticated route in the host app.
4. `SessionUtils.current_session_id`/`cookie_session_id` in `lib/shopify_api/utils/session_utils.rb` returns the attacker-supplied value unmodified and unverified; the host app looks up and loads the victim's stored session/access token, granting the attacker access to the victim shop's data via the host app.
