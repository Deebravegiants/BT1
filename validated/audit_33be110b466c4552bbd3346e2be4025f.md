### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) header is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) and other metadata purely from HTTP headers, while `Utils::HmacValidator` only verifies the raw request body against the app's shared `client_secret`. The `shop-domain` header is never included in the signed payload, so the HMAC check cannot bind a given body to the shop it claims to originate from.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read straight from caller-supplied headers with no cryptographic tie to the signed content: [2](#0-1) 

`HmacValidator.validate` computes the signature only over `to_signable_string` (the body) using the app's `api_secret_key`, and compares it to the `hmac` header — it never checks that the `shop` header (or any other header) is consistent with the signed bytes: [3](#0-2) 

`Registry.process` uses this unauthenticated `request.shop` value directly as the tenant identity handed to the app's webhook handler: [4](#0-3) 

The identity binding that should hold is:
`shop_bound_by_HMAC == shop_used_as_tenant_identity`

Because the signed message is only the raw body, and the `client_secret` (and hence a valid HMAC) is the same for every shop that has installed the app, any raw body + HMAC pair that is valid for **one** tenant is also a valid HMAC for **any other** tenant claimed via the `shop-domain` header. The binding above is broken: the value verified by the HMAC (nothing about the shop) is disjoint from the value trusted as the shop (an arbitrary attacker-controlled header).

### Impact Explanation
This is a cross-tenant identity-binding bypass in a multi-tenant app: an attacker who is a legitimate merchant/tenant of the app can capture a genuine webhook body+HMAC pair generated by their own store's activity (which they fully control, e.g. by creating orders/products in their own store), then replay that exact body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` (and `shopify-topic`/`shopify-webhook-id`) header to name a victim shop. `Utils::HmacValidator.validate` will accept it because it only ever checks the body signature, and `Registry.process` will pass `WebhookMetadata` with the forged `shop` value to the handler, causing the host application to record/act on attacker-controlled data as if it originated from a different tenant. This matches the "cross-tenant access" class of impact.

### Likelihood Explanation
Exploitation requires the attacker to be a real (even free/trial) merchant of the app so they can generate at least one legitimate webhook delivery with body content they control, and requires the app's webhook endpoint to be reachable directly with attacker-forged headers (true for any HTTP endpoint that a host framework builds using `ShopifyAPI::Webhooks::Request`, since headers/body are supplied by the caller and this gem does no independent verification of header/body cohesion). No access to `api_secret_key` or another tenant's credentials is needed.

### Recommendation
Bind the tenant/topic/webhook identity into the signed material, or otherwise cryptographically tie the `shop-domain` header to the specific delivery: e.g. verify the header set against a per-webhook-id record fetched via the Admin API/GraphQL for that shop, or require the host application to independently authenticate that the `webhook_id` belongs to the claimed `shop` before trusting `WebhookMetadata#shop`. At minimum, document loudly that `request.shop` is unauthenticated and must not be used as the sole tenant key without further verification.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Attacker creates an order in their own shop, capturing the resulting webhook body `B` and the `shopify-hmac-sha256` header `H` that Shopify computed with the app's shared `client_secret`.
3. Attacker sends a POST directly to the app's webhook endpoint with body `B`, header `shopify-hmac-sha256: H` (unchanged, still valid because it only signs `B`), but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because `to_signable_string` (`request.rb:35-38`) only re-hashes `B`, unaffected by the forged shop header (`hmac_validator.rb:12-31`).
5. `ShopifyAPI::Webhooks::Registry.process` (`registry.rb:188-200`) invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)`, causing the host app to attribute attacker-controlled data to the victim tenant.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
