Based on my investigation, I found a concrete analog to the Longhorn CVE's "Missing Authentication for Critical Function" pattern in the `CallDispatcher` contract, which is the shared execution primitive used by `IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`, and the intents v2 apps.

### Title
Unauthenticated `CallDispatcher.dispatch()` allows any caller to drain stranded token/ETH balances via arbitrary external calls - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch(bytes memory encoded)` is `external` with no access control whatsoever — no `onlyHost`, no caller allowlist, no `msg.sender` check of any kind [1](#0-0) . It decodes an arbitrary `Call[]` and executes each entry with `to.call{value: call.value}(call.data)`, i.e. as a plain (non-delegate) call performed *from the dispatcher's own address* [1](#0-0) . Because the low-level call's `msg.sender` is `CallDispatcher` regardless of who invoked `dispatch()`, any address on any chain can force the dispatcher to spend whatever ERC20 balance/allowance or native ETH it is currently holding.

### Finding Description
`CallDispatcher` is a shared, stateless-by-design utility contract intended to be invoked only from trusted app contracts (`IntentGatewayV2`/`IntentsBase`, `HyperFungibleToken`, `WrappedHyperFungibleToken`) during a single atomic transaction: assets are transferred to it, `dispatch()` runs solver/user-supplied calls, then residual balances are swept back [2](#0-1) . The intended security boundary is "assets only sit in the dispatcher for the duration of one call," documented explicitly: "the dispatcher contract holds tokens temporarily during execution" [3](#0-2) .

However, `dispatch()` itself enforces none of this — it is a bare, permissionless function, not restricted to any specific caller (unlike every other privileged surface in the codebase, e.g. `EvmHost.dispatchIncoming` which uses `restrict(_hostParams.handler)` [4](#0-3) , or `HostManager.onAccept`'s relayer gate [5](#0-4) ). The sweep logic in the calling app is also scoped only to the *current order's* known output tokens: `IntentsBase._execute` sweeps balances only for `order.output.assets[i]` within `outputsLen`, not any arbitrary token the dispatcher might be holding [6](#0-5) . Any token or native balance that ends up in the dispatcher outside of that specific sweep set (leftover dust from partial fills across multiple calls, fee-on-transfer/rebasing token remainders, accidental direct transfers, or a failed sweep path) is *stranded* in a contract anyone can command to execute arbitrary calls. Since the dispatcher is a shared singleton across `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` deployments [7](#0-6) , and it has a `payable receive()` that accepts ETH from anyone [8](#0-7) , this significantly increases the surface for value to transiently or accidentally sit there.

### Impact Explanation
Any unprivileged address (a solver, relayer, or arbitrary third party) can call `CallDispatcher.dispatch()` directly, bypassing every app-level authorization (`onlyHost`, relayer gates, solver-selection checks in `IntentGatewayV2`) and steal any token/ETH balance or ERC20 allowance the dispatcher currently holds, by crafting a `Call` such as `{to: token, data: transfer(attacker, balance)}`. This is concrete theft of funds reachable from a single unauthenticated transaction, matching the CVE's "any workload... execute any binary... without authentication" pattern, translated to "any address execute any call as the shared CallDispatcher without authentication."

### Likelihood Explanation
Exploitation requires the dispatcher to hold a non-zero, unswept balance at the moment of the attack. Under the current happy-path flows (single-call approve+swap, single-token predispatch/postdispatch), sweeps are generally complete within the same transaction, making this a race/edge-case bug rather than trivially triggerable on every transaction. However, the surface is broad: multi-hop/multi-token calldata, non-standard tokens (fee-on-transfer, rebasing), partial/failed sweep paths, or a stray direct transfer to the dispatcher (its `receive()` accepts unconditional ETH) all create a window where funds are exposed to any third party watching the chain, and the dispatcher's total lack of caller restriction means the exploit itself is trivial and cheap.

### Recommendation
Add caller authentication to `CallDispatcher.dispatch()` — e.g., an allowlist of registered gateway/app addresses set at deployment or via governance, checked with a `require`/modifier before decoding and executing calls — so that only the trusted apps that are supposed to drive dispatcher execution (and which already enforce their own authorization) can invoke it. Alternatively, make the dispatcher per-app (non-shared) and add a reentrancy/single-use guard so any residual balance cannot be reached by a call outside the originating app's atomic transaction.

### Proof of Concept
1. Assume `CallDispatcher` at address `D` has a non-zero balance of token `T` (e.g., dust left over after `IntentsBase._execute`'s sweep for an order whose calldata caused `T` to be received but was not part of `order.output.assets`).
2. Attacker (any address, no relationship to any gateway) directly calls: `D.dispatch(abi.encode([Call({to: T, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, T.balanceOf(D))})]))`.
3. Inside `dispatch()`, `T.call(data)` executes with `msg.sender == D` (`extcodesize(T) > 0` so the `NotContract` check passes) and the transfer succeeds, since no restriction exists on who may call `dispatch()` [1](#0-0) .
4. Attacker now holds `T`'s full balance previously stranded in the shared dispatcher, with no gateway, host, or relayer authorization ever checked.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
