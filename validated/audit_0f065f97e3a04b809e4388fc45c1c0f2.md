### Title
HOT Bridge withdrawal completion status trusts unverified API hash - ([File: packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts])

### Summary
`HotBridge.describeWithdrawal()` reports a withdrawal as `"completed"` with a concrete `txHash` sourced from the HOT API fallback (`fetchWithdrawalHashFromApi`), but that function never checks the `verified_withdraw` or `chain_id` fields that the response schema itself defines and parses. This mirrors the OCSP analog class: a signed/attested field (`verified_withdraw`) that indicates whether the reported outcome is actually confirmed is fetched but never validated before the caller treats the record as authoritative.

### Finding Description
The schema for the HOT API withdrawal item explicitly models two integrity fields: [1](#0-0) 

However `fetchWithdrawalHashFromApi` only matches by `nonce` and returns the `hash` field, ignoring `verified_withdraw` and `chain_id` entirely: [2](#0-1) 

This result is then propagated directly into a `"completed"` status with the unverified hash, both in the EVM/Stellar/TON bridge-indexer-failure fallback path and in the generic non-EVM fallback path: [3](#0-2) [4](#0-3) 

The broken equality: "status reported == on-chain verified outcome for the requested `landingChain`." The code fetches a record keyed only by `nonce`, but never confirms (a) `verified_withdraw === true` (HOT's own attestation that the withdrawal was actually verified on the destination chain) or (b) `chain_id` corresponds to `args.landingChain`. As a result, an entry whose own API-reported `verified_withdraw` flag is `false`, or whose `chain_id` doesn't match the expected destination chain, is still accepted as `"completed"` with its `hash` surfaced to the caller as the authoritative destination transaction hash.

### Impact Explanation
`watchWithdrawal` (in `withdrawal-watcher.ts`) treats a `"completed"` status as terminal success and resolves the tx hash to the caller/integrator, who typically credits or closes out the withdrawal based on this hash. If the HOT API returns a matching nonce whose `verified_withdraw` is `false` (in-flight/unconfirmed) or whose `chain_id` belongs to a different chain than the one being polled, the SDK will still report `"completed"` with that hash — a status/hash misreport that can cause an integrator to mark a withdrawal settled/credit it prematurely or against the wrong destination chain, before the funds are actually confirmed delivered. This matches the "status or hash misreport making an integrator credit or refund twice" impact category.

### Likelihood Explanation
This path is reached automatically whenever the bridge indexer path is unavailable or fails and the SDK falls back to the HOT API (`fetchWithdrawalHashFromApi`), which is a normal, unprivileged, externally-triggerable degraded-service condition (no attacker privilege needed — it depends on the third-party HOT API returning an as-yet-unverified record for a matching nonce, which is plausible during withdrawal processing race windows). The schema explicitly carries `verified_withdraw`/`chain_id` fields, indicating the original API contract anticipates such disambiguation, but the SDK code path silently drops that check.

### Recommendation
In `fetchWithdrawalHashFromApi` (and equally in the EVM fallback call site), require `withdrawal.verified_withdraw === true` before treating the hash as authoritative, and confirm `withdrawal.chain_id` matches the expected destination chain for `args.landingChain` before returning `{ status: "completed", txHash }`. If either check fails, treat the withdrawal as still `"pending"` rather than `"completed"`.

### Proof of Concept
1. Call `describeWithdrawal` for a withdrawal whose bridge-indexer lookup fails or returns nothing (triggers the API fallback), or where the primary contract view returns `null`/pending (non-EVM path).
2. HOT API `/api/v1/evm/bridge_withdrawal_hash` returns a `withdrawals` entry with the matching `nonce`, a non-null `hash`, but `verified_withdraw: false` (or a `chain_id` for a different chain than `args.landingChain`).
3. `fetchWithdrawalHashFromApi` returns `hash` unconditionally since it only filters on `nonce`.
4. `describeWithdrawal` returns `{ status: "completed", txHash: formatTxHash(hash, args.landingChain) }`, and `watchWithdrawal` resolves as settled — even though HOT's own record marks the withdrawal unverified or belonging to a different chain.
