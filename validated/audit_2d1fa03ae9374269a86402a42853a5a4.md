### Title
Unchecked ERC20 `transfer` return value in `IntentGatewayV2.withdraw`/`SweepDust` permanently freezes escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.sol` (Tron variant of the IntentGateway app) escrows arbitrary user-supplied ERC20 tokens for cross-chain intents and later releases them via low-level `.call()` to the token's `transfer` function. The code only checks that the *external call itself* did not revert (`success`), but never decodes/validates the boolean return value that ERC20 `transfer` is supposed to return. This is the exact bug class described in the external report (ERC677/ERC20 return value unchecked): a token that returns `false` on failure instead of reverting will make the gateway believe the payout succeeded, permanently mark the order as filled/refunded, and decrement escrow accounting — while the beneficiary never actually receives the tokens.

### Finding Description
In `withdraw()`, escrowed tokens are released to the beneficiary using a raw low-level call: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

`success` only reflects whether the call reverted, not the boolean payload returned by `transfer`. Any ERC-20 implementation that returns `false` on failure (rather than reverting) — e.g. due to a paused state, a blacklist, insufficient allowance/balance edge cases, or a fee-on-transfer/deflationary token whose author chose to signal failure via return value — will pass the `success` check even though no tokens moved. Immediately after, the function decrements `_orders[...][token]` and (in the caller) sets `_filled[body.commitment] = beneficiary`, finalizing the order: [2](#0-1) 

The exact same unchecked pattern recurs in the fee payout at the end of `withdraw` and in the governance-driven `SweepDust` handler: [3](#0-2) [4](#0-3) 

Note that elsewhere in the same contract, inbound token pulls correctly use `SafeERC20.safeTransferFrom` (which reverts on a `false` return), showing the developers were aware of non-compliant tokens for the escrow path but omitted the equivalent guard for the payout path: [5](#0-4) 

The `withdraw()` function is reached from `onAccept` for `RequestKind.RedeemEscrow` / `RequestKind.RefundEscrow`, which is authenticated only against the registered peer gateway instance, not against any admin/governance role: [6](#0-5) 

Since the token address for an order's inputs is chosen freely by the order's creator (an ordinary user) at order-submission time, and delivery of the ISMP message is performed by any unprivileged relayer completing the intent lifecycle, this path is reachable end-to-end from a single unprivileged intent submission plus relay — no admin or governance action is required.

### Impact Explanation
If the escrowed input token silently returns `false` on `transfer` instead of reverting:
- The order is marked filled/refunded (`_filled` set) and its escrow ledger entry decremented as if payout succeeded, even though the beneficiary received nothing.
- Because `_filled` is now set, the order cannot be retried, redeemed, or refunded again — the tokens remain locked in the `IntentGatewayV2` contract with no code path to recover them for the rightful beneficiary.
- This constitutes a permanent freezing of user funds, and depending on subsequent contract logic/dust sweeping, could also enable funds to be misdirected/collected as "dust" by the protocol instead of the intended beneficiary.

### Likelihood Explanation
Reaching this bug does not require a compromised admin, governance, or relayer — only: (1) an order creator selecting/using a token that returns `false` on failed transfers (a known category of ERC-20 non-compliance, and trivially achievable by using a custom token as one of the order's input assets), and (2) a normal relayer delivering the resulting `RedeemEscrow`/`RefundEscrow` ISMP message, which is the standard intent-fulfillment flow. This makes the likelihood of triggering the bug for at least one input token realistic in an open, permissionless intents marketplace where arbitrary ERC-20s can be listed as order inputs.

### Recommendation
Replace the raw `.call()` + `success`-only checks in `withdraw()` (both the token loop and the transaction-fee payout) and in `SweepDust` with `SafeERC20.safeTransfer`, which is already imported and used elsewhere in the contract (`using SafeERC20 for IERC20;`). `safeTransfer` correctly reverts both on a failed call and on a `false` boolean return, ensuring the escrow state and `_filled` flag are never updated unless the token transfer genuinely succeeded.

### Proof of Concept
1. Order creator submits an intent whose `order.inputs` includes a custom ERC-20 token `T` that implements `transfer` to return `false` (instead of reverting) when, e.g., the caller is paused/blacklisted or a condition is not met — fully valid Solidity, no special privilege needed to deploy such a token.
2. A solver fills the order on the destination chain; the destination gateway dispatches a `RedeemEscrow` request back to the source chain gateway.
3. Any relayer delivers this message; `onAccept` → `authenticate` passes (message legitimately originates from the peer gateway) → `withdraw(body, false)` executes.
4. For token `T`, `token.call(...transfer...)` returns `(success=true, data=abi.encode(false))`; the contract only checks `success`, so it proceeds: `_orders[commitment][T] -= amount` and `_filled[commitment] = beneficiary` are set, `EscrowReleased` is emitted — but `beneficiary`'s balance of `T` never increased.
5. The beneficiary's tokens remain locked in `IntentGatewayV2` permanently, since the order is already recorded as filled and cannot be re-processed.
