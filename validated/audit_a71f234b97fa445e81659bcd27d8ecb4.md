### Title
Unvalidated route pool can execute arbitrary user-authorized token transfers - (File: contracts/swap-aggregator/src/execute/mod.rs)

### Summary
The swap router executes user-supplied pool addresses without checking that the invoked contract is a legitimate venue, so a malicious pool can perform unrelated token transfers while executing beneath the caller’s authorization tree. The controller only authorizes the exact routed input transfer, but this does not prevent route-selected pool code from adding another caller-authorized token transfer.

### Finding Description
`execute_strategy` requires `sender` authorization, decodes a caller-supplied `StrategyPayload`, and executes its packed instruction stream. [1](#0-0)  The address registry is caller-controlled and contains both token and pool addresses, while the program validator only range-checks registry indices and does not verify that a pool address belongs to an approved venue. [2](#0-1)  For a swap instruction, `execute_op` directly selects `pool`, `token_in`, and `token_out` from the caller’s registry and dispatches the selected venue adapter. [3](#0-2) 

For example, the Soroswap adapter invokes the pool’s `get_reserves`, transfers the routed input to that pool, and then invokes its `swap` entrypoint. [4](#0-3)  The dispatcher only measures the router’s input spend and output receipt around that call; it does not restrict unrelated calls made by the pool during `swap`. [5](#0-4) 

The same exposure exists through controller strategies: `swap_collateral` authenticates the account caller and passes the supplied swap bytes into the router path. [6](#0-5)  Before invoking the router, the controller authorizes one exact transfer of the routed input token, but the route itself still determines which pool contracts execute below the caller’s transaction authorization. [7](#0-6) 

A malicious pool can therefore call `wallet_token.transfer(victim, attacker, amount)` inside its venue entrypoint. Because that token call occurs beneath the victim’s signed route invocation, the host records it as a child authorization; if the victim signs the simulated authorization tree containing that child, the transfer succeeds alongside the measured swap.

### Impact Explanation
An attacker can steal an arbitrary amount of any token held by the victim, bounded by the amount encoded in the authorization tree the victim signs. The router’s minimum-output check and the controller’s measured-output and final-risk checks do not bound this unrelated wallet transfer because they only observe the routed tokens. [8](#0-7) 

The malicious route can still satisfy settlement by using attacker-funded output liquidity, so the swap can return a valid positive output while the separate theft succeeds. [9](#0-8) 

### Likelihood Explanation
No privileged role, oracle manipulation, leaked key, upgrade, or protocol admin action is required; the attacker only deploys a contract implementing the expected pool interface and supplies a route that names it. The practical prerequisite is convincing a victim or integrating client to sign the authorization tree produced for that route.

Simulation makes the malicious child transfer visible, so a correctly implemented client can detect and reject it. The contract nevertheless places the safety boundary on transaction inspection rather than enforcing that pool calls cannot create unrelated caller-authorized transfers.

### Recommendation
Constrain route pool addresses to a governance- or router-managed venue/pool allowlist rather than accepting arbitrary registry addresses. Independently, wallets and route builders should decode the signed authorization tree and reject any child invocation other than the expected input-token transfer.

### Proof of Concept
1. Deploy a malicious contract configured with the victim address, an unrelated wallet-token address, and the attacker address.
2. Implement the Soroswap-facing calls used by the adapter: return attacker-chosen reserves from `get_reserves`; in `swap`, call `wallet_token.transfer(victim, attacker, amount)` and then transfer a positive routed `token_out` amount to the router.
3. Construct a `StrategyPayload` whose `assets` registry contains the routed input token, routed output token, and malicious pool, and whose `ops` bytes encode one Soroswap swap naming that pool.
4. Have the victim invoke `Router::execute_strategy(sender=victim, total_in=X, swap_xdr=payload)` or a controller strategy such as `swap_collateral` that reaches the same router path.
5. Simulate the transaction and sign the resulting authorization tree containing `wallet_token.transfer(victim, attacker, amount)`.
6. Execution pulls the routed input from the victim, invokes the malicious pool, performs the unrelated wallet-token transfer, and returns enough routed output to satisfy the router’s positive-output and minimum-output checks.

pub(crate) fn swap(ctx: &HopContext<'_>) {
    let token_in_is_0 = ctx.hop.token_in < ctx.hop.token_out;

    let no_args: Vec<Val> = vec![ctx.env];
    let (reserve_0, reserve_1): (i128, i128) = ctx.env.invoke_contract(
        &ctx.hop.pool,
        &Symbol::new(ctx.env, "get_reserves"),
        no_args,
    );
    let (reserve_in, reserve_out) = if token_in_is_0 {
        (reserve_0, reserve_1)
    } else {
        (reserve_1, reserve_0)
    };

    let requested_out = soroswap_amount_out(ctx.env, ctx.amount_in, reserve_in, reserve_out);
    if requested_out <= 0 {
        panic_with_error!(ctx.env, Error::ZeroOutput);
    }

    let token_client = token::Client::new(ctx.env, &ctx.hop.token_in);
    token_client.transfer(ctx.router, &ctx.hop.pool, &ctx.amount_in);

    let (amount_0_out, amount_1_out) = if token_in_is_0 {
        (0_i128, requested_out)
    } else {
        (requested_out, 0_i128)
    };
    let args: Vec<Val> = vec![
        ctx.env,
        amount_0_out.into_val(ctx.env),
        amount_1_out.into_val(ctx.env),
        ctx.router.into_val(ctx.env),
    ];
    let _: () = ctx
        .env
        .invoke_contract(&ctx.hop.pool, &symbol_short!("swap"), args);
}
