### Title
Webhook `shop` (and other identity headers) are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body bytes, never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose body+HMAC matches the app's `api_secret_key`, then passes the unauthenticated `shop` header value straight into `WebhookMetadata` for the handler to act on as the tenant identity.

### Finding Description
The binding that should hold is: `shop header == shop that produced/authorized this signed body`. Because `to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) returns `@raw_body` alone, the HMAC in `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) only proves "this body was HMAC'd with the app's shared `api_secret_key`" — it proves nothing about which shop's domain header accompanies it. Since `api_secret_key` is one shared secret for *all* installations of the app across all merchants, any unprivileged internet user who can obtain one valid `(raw_body, hmac)` pair — e.g. by installing the app on their own free/dev store and capturing a webhook delivery, since delivery endpoints are typically public URLs — can replay that exact body+hmac to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header for a victim shop. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) validates the HMAC (passes, since it only checks body/secret) and then calls the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, so the handler executes attacker-supplied topic/body content under the identity of a shop the attacker doesn't control.

### Impact Explanation
This is a cross-tenant confusion: application logic that keys off `WebhookMetadata#shop` (e.g., to look up the merchant's session/access token, update per-shop records, or trigger shop-specific side effects) can be tricked into acting on forged data "from" an arbitrary victim shop, using only a body+HMAC pair the attacker legitimately obtained for their own shop. This crosses the tenant boundary the HMAC is meant to enforce.

### Likelihood Explanation
Requires only: (1) installing the app once on an attacker-controlled shop (any dev/trial store) to capture a legitimate webhook body+HMAC, and (2) POSTing that captured pair to the app's public webhook endpoint with a forged `shop-domain` header. No access token, `api_secret_key`, or privileged access is needed — this is reachable by any unprivileged internet user who knows the app's webhook URL.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`) header values in the HMAC-signed content, or otherwise cryptographically bind them to the body signature in `to_signable_string`, so the verified signature covers the full set of fields the handler treats as trusted (matching Shopify's documented webhook verification which signs body bytes with the app secret, but this gem should not let downstream code treat unsigned headers as verified).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggers any webhook topic, and captures the raw POST body `B` and `X-Shopify-Hmac-Sha256: H` header from the delivery to the app's registered endpoint.
2. Attacker sends a new POST to the same app endpoint with body `B` unchanged, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request object; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`= B`) with the app's `api_secret_key` and finds it matches `H` — validation succeeds.
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: request.topic, body: request.parsed_body, ...)`, causing the app to process attacker body content attributed to the victim shop.
