### Title
Webhook `shop-domain` header is trusted for tenant identity without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then unconditionally trusts the `shop-domain` HTTP header (unauthenticated, attacker-settable) as the tenant identity passed to the app's handler. This breaks the intended binding `hmac_signed_bytes == bytes_that_determine_tenant`, allowing an attacker who possesses any single valid `(raw_body, hmac)` pair (trivially obtainable by installing the app on their own store and receiving one legitimate webhook) to replay that exact body/HMAC to the app's public webhook endpoint while spoofing the `shop-domain` header to name a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers that are not part of the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC exclusively over `verifiable_query.to_signable_string`, i.e., only the body: [3](#0-2) 

`Registry.process` performs only this body-HMAC check, then immediately builds `WebhookMetadata` using the unauthenticated `request.shop` header and dispatches it to the app's handler: [4](#0-3) 

The identity binding that should hold is: `bytes verified by HMAC == bytes used to determine the shop/tenant that the event is attributed to`. Here, the shop identity is taken from a header entirely outside the HMAC's coverage, so the equality does not hold — the library computes `hmac(raw_body) == received_hmac` but then acts on `shop_header`, a value the signature says nothing about.

### Impact Explanation
Any actor who can get the app installed on a store they control (a free/dev store, no privileges beyond normal signup) will receive at least one legitimately Shopify-signed webhook for their own shop — a valid `(raw_body, hmac-sha256)` pair signed with the app's `client_secret`/`api_secret_key`. Because the signature covers only the body, the attacker can resend that identical body and HMAC directly to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` (or `x-shopify-shop-domain`) header naming a different, victim tenant. `Registry.process` will accept it (HMAC still matches, since body is unchanged) and hand the handler a `WebhookMetadata` whose `shop` field claims to be the victim shop. Any host application logic keyed off this `shop` value (e.g., updating billing/subscription state, triggering per-shop side effects, looking up/mutating the victim's stored session or app data) is executed under the wrong tenant identity — a cross-tenant confusion/access primitive attributable directly to this library's failure to bind the header to the signed payload.

### Likelihood Explanation
Exploitation requires no secret, no privileged account, and no leaked credential: any user can sign up for a Shopify development store, install the target app, and passively capture one legitimate webhook delivery to obtain a valid signed body/HMAC pair. Replaying an HTTP POST with modified headers to the app's own public webhook endpoint is trivial. The only constraint is that the resulting body content is fixed (it belongs to the attacker's own store's event), limiting the payload the attacker can inject, but the *shop attribution* of that payload is fully attacker-controlled.

### Recommendation
- Bind the shop (and topic/webhook-id) identity into the authenticated material: either include `shopify-shop-domain` in the HMAC-signed payload (not possible without a Shopify-side change) or, more practically, have `Registry.process`/host applications cross-check `request.shop` against the shop associated with the currently active/expected session or webhook subscription rather than trusting it unconditionally.
- Document and enforce that consumers of `WebhookMetadata.shop` must independently verify the shop is one they have an active install/session for before acting on the payload, and consider adding this check inside `Registry.process` itself (e.g., reject if `shop` is not a shop with an active session known to the host app, or expose an optional allowlist hook).
- Add defense-in-depth by validating `request.shop` through `Utils::ShopValidator.sanitize!` at minimum, and by rate/idempotency-limiting on `webhook_id` to reduce replay usefulness (note: this alone does not fix the identity-binding gap since a fresh legitimate webhook_id from the attacker's own shop is always available).

### Proof of Concept
1. Attacker signs up for a free Shopify development store `attacker-shop.myshopify.com` and installs the target app (any app using this gem's webhook processing).
2. Attacker triggers or waits for any webhook (e.g., `products/create`) to be delivered to the app; captures the raw request body `B` and the `shopify-hmac-sha256` header value `H` (both valid: `HMAC-SHA256(app_secret, B) == H`).
3. Attacker sends a new POST directly to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - Headers: `shopify-hmac-sha256: H` (unchanged), `shopify-topic: <same or original topic>`, `shopify-shop-domain: victim-shop.myshopify.com` (changed to a shop the attacker does not own).
4. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`, so validation succeeds.
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host application to process the event as if it originated from `victim-shop.myshopify.com`.
