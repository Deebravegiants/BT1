### Title
Unbounded growth of the mempool-watched intents `BidCache` allows remote memory-exhaustion DoS - (File: `modules/pallets/intents-coprocessor/rpc/src/lib.rs`)

### Summary
The intents-coprocessor RPC service maintains an in-memory `BidCache` that is populated directly from the transaction pool (mempool) by `run_bid_watcher`, before any bid extrinsic is even included in a block. The cache is a `HashMap<H256, OrderBids>` with no maximum size, and each `OrderBids` holds an unbounded `Vec<BidEntry>`. Eviction is purely time-based (`remove_expired`, driven by a periodic sweep), never size-based, so the cache's memory footprint is bounded only by how many distinct commitments/fillers an attacker can push into the pool within one TTL window — an analog of the Micronaut `DefaultHtmlErrorResponseBodyProvider` unbounded `ConcurrentHashMap` DoS (GHSA-2hcp-gjrf-7fhc, CWE-770).

### Finding Description
`BidCache` is defined and driven entirely by pool activity, not by finalized chain state: [1](#0-0) 

- `bids: RwLock<HashMap<H256, OrderBids>>` has no capacity limit and no per-key entry limit.
- `insert` unconditionally grows `order.entries` for any new `filler` value under a given `commitment`, and unconditionally creates a new `OrderBids` map entry for any new `commitment` key.

The cache is filled from `run_bid_watcher`, which subscribes to the pool's `import_notification_stream()` and reads *ready* (i.e., not-yet-included, mempool) transactions, extracting a bid tuple from any transaction recognized as a bid call and inserting it immediately: [2](#0-1) 

Eviction only happens on a fixed timer tick via `remove_expired`, which sweeps by TTL/`first_seen`, never by cache size: [3](#0-2) [4](#0-3) 

Because entries are added the moment a transaction becomes "ready" in the pool — prior to inclusion, finalization, or even necessarily paying full fees — an unprivileged party who can get transactions into the pool (any user broadcasting extrinsics to the node) controls both the number of distinct `commitment` keys and the number of distinct `filler` values per commitment, i.e., both axes of unbounded growth of this HashMap-of-Vecs.

### Impact Explanation
An attacker can flood the transaction pool of any node running this intents RPC service with cheap or ultimately-invalid "bid" extrinsics carrying many distinct `commitment` hashes and/or many distinct `filler`/`user_op` byte blobs per commitment. Since insertion happens on pool-readiness rather than on finalized inclusion, and eviction is strictly time-bound rather than size-bound, sustained submission faster than the TTL sweep interval causes the `HashMap<H256, OrderBids>` (and its `Vec<BidEntry>` fan-out per key) to grow without bound, exhausting node memory and causing an `OutOfMemoryError`/crash of the RPC node — a availability/DoS impact (CWE-770), directly analogous to the reported Micronaut vulnerability's unbounded `ConcurrentHashMap`.

### Likelihood Explanation
High. Reaching the vulnerable path requires no privileged access — any relayer, filler, or arbitrary network participant able to submit transactions to the node's transaction pool can trigger `run_bid_watcher`'s insertion path repeatedly with attacker-chosen `commitment`/`filler` values, and the cache has no bound to stop them.

### Recommendation
Bound `BidCache` by total size (e.g., cap total commitments and/or total entries with LRU/FIFO eviction similar to the fix applied upstream for the Micronaut advisory), and/or cap the number of `BidEntry` allowed per `commitment`, evicting oldest entries once a maximum is reached — in addition to, not instead of, the existing TTL-based sweep in `remove_expired`.

### Proof of Concept
1. Connect to a node exposing the `intents-coprocessor` RPC/bid-watcher service.
2. Repeatedly submit many transactions recognized by `extract_bid` as intents-coprocessor `bid` calls, each using a fresh random `commitment` (H256) and/or a fresh `filler` value under existing commitments, at a rate faster than the configured `cleanup_interval`/TTL.
3. Observe `BidCache.bids` (and the underlying process RSS) grow unbounded as `run_bid_watcher` inserts every ready transaction via `bid_cache.insert(...)` at `modules/pallets/intents-coprocessor/rpc/src/lib.rs:365`, with no size cap enforced by `insert` (`lib.rs:111-129`), eventually exhausting node memory.

/// In-memory bid cache.
pub struct BidCache {
	bids: RwLock<HashMap<H256, OrderBids>>,
	ttl: Duration,
}

impl BidCache {
	pub fn new(ttl: Duration) -> Self {
		Self { bids: RwLock::new(HashMap::new()), ttl }
	}

	pub fn insert(
		&self,
		commitment: H256,
		filler: Vec<u8>,
		user_op: Vec<u8>,
	) -> Result<(), String> {
		let entry = BidEntry { filler: filler.clone(), user_op };

		let mut bids = self.bids.write().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		let order = bids
			.entry(commitment)
			.or_insert_with(|| OrderBids { first_seen: Instant::now(), entries: Vec::new() });
		if let Some(existing) = order.entries.iter_mut().find(|e| e.filler == filler) {
			*existing = entry;
		} else {
			order.entries.push(entry);
		}
		Ok(())
	}

	pub fn remove_expired(&self) -> Result<(), String> {
		let now = Instant::now();
		let mut bids = self.bids.write().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		bids.retain(|_commitment, order| now.duration_since(order.first_seen) < self.ttl);
		Ok(())
	}
