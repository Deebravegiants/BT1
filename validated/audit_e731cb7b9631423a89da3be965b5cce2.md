### Title
Webhook shop-domain header is not covered by HMAC validation, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-verifying the raw request body, then trusts the `shop` value taken from the `x-shopify-shop-domain` (or `shopify-shop-domain`) header — a value that is never included in the signed content — when dispatching the webhook to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are read straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` verifies only what `to_signable_string` returns (the body), not the headers: [3](#0-2) 

`Registry.process` accepts the request once the body HMAC checks out, then forwards `request.shop` (the unauthenticated header) to the app's webhook handler as the identity of the shop the data belongs to: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop the handler acts on`. Because the header carrying `shop` is outside the signed bytes, these two values can diverge. Any internet user who can install the app on their own (attacker-controlled) shop can obtain a legitimately Shopify-signed `(raw_body, hmac)` pair for a real webhook delivered to their own endpoint. They can then replay that exact body/HMAC pair to the target app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` passes the forged victim shop identifier into `WebhookMetadata`, so the host application processes attacker-supplied data under the victim's tenant context — e.g., updating stored state, triggering uninstall/GDPR handling, or any other tenant-scoped logic keyed off `data.shop`.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to guarantee for webhook processing: an attacker who only needs a store of their own (no `api_secret_key`, access token, or privileged account) can make an application believe an event originated from a different, victim shop. This is cross-tenant data/identity confusion, matching the Critical "cross-tenant access" impact category since the "authenticated" shop and the shop the app relies on for tenant isolation are provably different values.

### Likelihood Explanation
The prerequisite (installing the app on an attacker's own shop to obtain one legitimately-signed webhook) is a routine, unprivileged action available to any internet user via Shopify's development/partner program, and replaying an HTTP request with a modified header is trivial. No secret material or elevated privileges are required to perform the spoof itself — only to construct the header replay, which any client can do.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the HMAC-signed content check, or otherwise cross-validate the header-provided shop against a shop the app already has an authenticated relationship with (e.g., only accept webhook shop values that correspond to a previously provisioned session), rejecting mismatches before invoking the handler.

### Proof of Concept
1. Install the vulnerable app on an attacker-owned dev shop `attacker.myshopify.com`; trigger any registered webhook topic so Shopify sends `POST /webhooks` with body `B` and header `x-shopify-hmac-sha256: HMAC(B, secret)`.
2. Capture `B` and the HMAC value.
3. Replay `POST /webhooks` to the same app endpoint with identical body `B` and HMAC header, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` (checking only `B`) passes; `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and invokes the app's handler as if the event came from `victim.myshopify.com`. [4](#0-3)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
