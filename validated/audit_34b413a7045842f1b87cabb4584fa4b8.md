### Title
Silent `uint128` truncation of swap amounts in `UniV4UniswapV2Wrapper` causes user funds to be lost or stuck - (File: `evm/src/utils/uniswapv2/UniV4UniswapV2Wrapper.sol`)

### Summary
`UniV4UniswapV2Wrapper`, used by `EvmHost` and `IntentGatewayV2` to swap native/fee tokens through Uniswap V4's Universal Router, narrows user-supplied `uint256` amounts to `uint128` with a plain Solidity cast (`uint128(amountIn)`, `uint128(amountOut)`, `uint128(amountOutMin)`, `uint128(msg.value)`) before building the swap calldata. Solidity narrowing casts truncate silently — any value above `type(uint128).max` (~3.4×10^38) loses its high-order bits, exactly the bug class described in the referenced Harpie `Vault.sol` report.

### Finding Description
In `swapExactTokensForETH` the full `amountIn` (a `uint256` controlled by the caller) is pulled from the caller and forwarded in full to the Universal Router via `safeTransferFrom`/`safeTransfer`: [1](#0-0) 

but the swap parameters that actually determine the trade executed by the pool use the truncated value: [2](#0-1) 

The same pattern appears for `amountOut`/`msg.value` in `swapETHForExactTokens`, and for the quoting helpers: [3](#0-2) [4](#0-3) [5](#0-4) 

None of these external functions have any bound check that `amountIn`, `amountOut`, `amountOutMin`, or `msg.value` stay below `type(uint128).max` before the cast.

### Impact Explanation
Because the token transfer into the router uses the full, untruncated `uint256` amount while the actual swap math (`SWAP_EXACT_IN_SINGLE`/`SWAP_EXACT_OUT_SINGLE`) is parameterized with the truncated `uint128` value, a caller whose amount exceeds `type(uint128).max` will have the majority of their transferred tokens either stranded in the Universal Router (unaccounted for by the smaller swap) or returned in far smaller output proceeds than expected, permanently losing the difference. This is a straightforward extension of the reported bug class (amounts above `uint128` max are silently truncated and lost) applied to a fund-moving path reachable by any unprivileged caller of the wrapper.

### Likelihood Explanation
This wrapper is wired into `EvmHost` (used for converting native currency to the protocol fee token, reachable whenever any user pays with native `msg.value` for message dispatch) and into `IntentGatewayV2` (referenced for intents' token conversion flow), both of which are dispatched by ordinary, unprivileged users: [6](#0-5) 

Triggering the overflow in practice requires an amount whose token-unit value (post-decimals) exceeds ~3.4×10^38, which is realistic only for extremely inflationary/high-decimal tokens, so the likelihood is low but the class matches the accepted "Medium" severity of the original report because impact (loss of the majority of the transferred amount) is severe when it happens.

### Recommendation
Replace the raw `uint128(...)` casts with `SafeCast.toUint128(...)` (OpenZeppelin) or an explicit `require(amount <= type(uint128).max, ...)` check in `swapETHForExactTokens`, `swapExactTokensForETH`, `getAmountsIn`, and `getAmountsOut` in `evm/src/utils/uniswapv2/UniV4UniswapV2Wrapper.sol`, so that oversized amounts revert instead of silently truncating and stranding user funds.

### Proof of Concept
1. Deploy `UniV4UniswapV2Wrapper` and initialize it (`init`) against a token pool.
2. Call `swapExactTokensForETH(amountIn, amountOutMin, path, to, deadline)` with `amountIn = type(uint128).max + 1` (achievable for a token whose smallest-unit balance can reach this magnitude, e.g. a high-decimal/inflationary token).
3. Observe: `IERC20(token).safeTransferFrom(msg.sender, address(this), amountIn)` at line 114 pulls the **full** `amountIn` from the caller.
4. The swap params at line 119 encode `uint128(amountIn)`, which wraps to `1` (or a small remainder), so the pool swap executes for a trivial amount.
5. The caller's `to.balance` increase (line 136) reflects only the output of the tiny truncated swap, while the bulk of the transferred tokens remain stuck in the Universal Router with no recovery path in the wrapper contract — a direct, permanent loss of funds.
