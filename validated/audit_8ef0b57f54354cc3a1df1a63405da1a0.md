### Title
Webhook shop attribution is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` binds a webhook's `shop` (tenant) identity to plain, unauthenticated HTTP headers, while the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` verifies covers only the raw body bytes. Any actor who can obtain one genuinely-signed webhook payload for a shop they control (e.g., by installing the target app on their own store) can replay the exact same body/HMAC pair while substituting the `X-Shopify-Shop-Domain` header, causing the host application's handler to process attacker-chosen data under a victim shop's identity.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop` is read straight from an attacker-controllable header with no cryptographic binding: [2](#0-1) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` — which hashes `to_signable_string` (the body alone) — and then immediately trusts `request.shop` to construct the metadata passed to the app's handler: [3](#0-2) 

`HmacValidator.validate_signature` compares `HMAC(secret, verifiable_query.to_signable_string)` to the `hmac` field, so for `Request` it only ever authenticates the body bytes, never the shop header: [4](#0-3) 

Broken identity binding, stated as an equality that should hold but does not:
`HMAC(client_secret, body) valid ⇒ shop == originating_shop` is **false** in this implementation, because `shop` is never part of the signed input. The `client_secret` used to sign webhooks is per-app, shared across every shop that installs the app — it is not per-tenant. Consequently, any principal capable of installing the target app on a store they control receives genuinely Shopify-signed `(body, hmac)` pairs. They can replay that exact pair to the app's webhook endpoint while altering only the `shopify-shop-domain` / `x-shopify-shop-domain` header to a victim shop's domain. `Utils::HmacValidator.validate(request)` still returns `true` (it only checked the body), and `Registry.process` forwards `request.shop` (now attacker-chosen) unauthenticated to the `WebhookHandler`, which per the library's own documented pattern is expected to use `shop` for tenant attribution (looking up/mutating the corresponding tenant record).

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged party (merely capable of installing the app on any store, including a free/dev store they control) can make the host application process spoofed webhook data under a different, victim tenant's identity. Depending on the webhook topic (e.g., `app/uninstalled`, `customers/redact`, `orders/create`, etc.) and how the host stores/keys data by `shop`, this can lead to state corruption, incorrect authorization decisions, or data leakage tied to the wrong tenant — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Reasonably likely for a motivated actor: it requires only the ability to install the target app on an attacker-controlled shop (typically low-friction, e.g. a free development store) to obtain a legitimately-signed body/HMAC pair, then a trivial HTTP replay changing one header. No possession of the app's `client_secret`, access tokens, or any privileged credential is required — only observation of one's own legitimately delivered webhook traffic.

### Recommendation
Include the shop-identifying data in the signed payload verification path, or otherwise cryptographically bind the `shop` value used for tenant attribution to the verified request. Concretely:
- Do not treat `request.shop` (from `Request#shop`) as trusted tenant identity for any authorization- or storage-key decision unless it is corroborated against a session/tenant record established via a separately authenticated channel (e.g., the offline access token already on file for that shop, verified independently of the webhook headers).
- Document explicitly in `lib/shopify_api/webhooks/request.rb` and `docs/usage/webhooks.md` that the `shop` header is not covered by the HMAC and must not be used as an unverified tenant key by host applications.
- Where feasible, extend `Registry.process` to cross-check `request.shop` against the shop associated with the stored session/access token which the app used to register that specific webhook subscription, rejecting mismatches.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a store they control), completing OAuth normally.
2. Shopify delivers a legitimate webhook (e.g., `orders/create`) to the app's endpoint with headers:
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Hmac-Sha256: <valid HMAC of raw body with app's client_secret>`
   - raw body: `{"id": 1, ...}`
3. Attacker captures this raw body and its valid HMAC value.
4. Attacker sends a new HTTP request to the same webhook endpoint with the *same* raw body and *same* HMAC header, but replaces the header:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, raw_body)` — unchanged — and passes validation:
```ruby
# lib/shopify_api/webhooks/registry.rb
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
```
6. `request.shop` now returns `"victim-shop.myshopify.com"`, so the host application's handler processes/attributes the forged order data to the victim shop, even though the payload never originated from Shopify on behalf of that shop.
