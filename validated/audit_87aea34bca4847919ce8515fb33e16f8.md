Audit Report

## Title
`pallet-asset-rewards::cleanup_pool` lacks an expiry check, allowing the pool admin to drain reward tokens (including third-party deposits made via `deposit_reward_tokens`) before any staker joins - ([File: substrate/frame/asset-rewards/src/lib.rs])

## Summary
`cleanup_pool` only verifies that the caller is the pool's `admin` and that `PoolStakers` is currently empty; it never checks `pool_info.expiry_block`, so it can be called immediately after pool creation, well before the reward program was meant to end. Since `deposit_reward_tokens` is a permissionless extrinsic that lets any signed account fund a pool's reward pot, an admin can create a pool, wait for third-party deposits, and sweep the entire reward balance to themselves before a single staker interacts with the pool.

## Finding Description
`cleanup_pool` performs exactly two checks before transferring the pool's entire reducible reward-asset balance to the admin and deleting the pool: caller equals `pool_info.admin`, and `PoolStakers::<T>::iter_key_prefix(pool_id).next()` is `None` [1](#0-0) . There is no check comparing `T::BlockNumberProvider::current_block_number()` against `pool_info.expiry_block`, unlike `unstake` and `harvest_rewards`, which explicitly gate non-staker-initiated calls on `now > pool_info.expiry_block` [2](#0-1) [3](#0-2) . This asymmetry confirms the expiry check was a deliberate design pattern elsewhere in the pallet but is missing from `cleanup_pool`.

Meanwhile, `deposit_reward_tokens` allows any signed account to transfer reward-asset tokens directly into the pool's pot account, with no restriction tying the depositor to the admin: [4](#0-3) . The doc comment on `cleanup_pool` itself states the admin should "receive the unutilized reward tokens back after the pool completion" [5](#0-4) , confirming the intended precondition of "pool completion" (i.e., expiry) that the code fails to enforce.

Exploit flow:
1. Pool created with `admin` and a future `expiry_block` via `create_pool` [6](#0-5) .
2. A third party calls `deposit_reward_tokens` to fund the reward pot, expecting rewards to accrue to future stakers.
3. Before any `stake` call is made, `admin` calls `cleanup_pool`. `PoolStakers` is empty (no staker has ever joined), so `stakers.is_none()` trivially passes; `expiry_block` is never checked; the entire pot balance, including the third party's deposit, is transferred to `admin`, and the pool is deleted.

## Impact Explanation
Funds deposited into the reward pot by a third party via the permissionless `deposit_reward_tokens` call can be unilaterally and immediately reclaimed by the pool admin, with no expiry or contribution-source check. This is a genuine loss of funds for the depositor and a broken accounting/security assumption for the reward-pool mechanism, matching the "rewards withdrawn before staking starts" failure mode described in the referenced report.

## Likelihood Explanation
Exploitability hinges on whether `T::CreatePoolOrigin` permits ordinary signed accounts to create pools. In the runtimes checked (`asset-hub-rococo`, `asset-hub-westend`, `substrate/bin/node/runtime`, `staking-async` parachain runtime), `CreatePoolOrigin` is configured per-runtime and was not fully verified as restricted or permissionless within this review; this is a residual unknown. However, independent of `CreatePoolOrigin`'s configuration, the core defect is real and repeatable in any configuration: even a legitimately-authorized admin can prematurely reclaim reward funds mid-program as soon as the staker set is transiently empty (e.g., after the last staker fully unstakes and before a new one joins) — this can occur without any malicious pool creation, purely due to the missing expiry check.

## Recommendation
Add an expiry check to `cleanup_pool`, e.g. `ensure!(now >= pool_info.expiry_block, Error::<T>::PoolNotExpired)`, mirroring the pattern already used in `unstake` and `harvest_rewards`. Consider also tracking admin-contributed vs. third-party-contributed reward balances separately, or documenting that `deposit_reward_tokens` deposits are made at the depositor's risk once the pool's admin-controlled lifecycle is understood.

## Proof of Concept
1. `create_pool(admin=Alice, expiry_block=1000, staked_asset=Y, reward_asset=X)` at block 0.
2. Bob calls `deposit_reward_tokens(pool_id, 10_000 X)` at block 1.
3. No account calls `stake`, so `PoolStakers::iter_key_prefix(pool_id)` is empty.
4. Alice calls `cleanup_pool(pool_id)` at block 2 (block 2 ≪ `expiry_block` 1000).
5. `stakers.is_none()` passes; `pool_balance` (10,000 X) is transferred entirely to Alice; the `Pools` entry is removed and `PoolCleanedUp` is emitted.
6. Verify via a unit test in `substrate/frame/asset-rewards` mock/test harness that `cleanup_pool` succeeds and drains Bob's deposited balance to Alice despite `current_block_number() < expiry_block`.

```rust
		pub fn cleanup_pool(origin: OriginFor<T>, pool_id: PoolId) -> DispatchResult {
			let who = ensure_signed(origin)?;

			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			ensure!(pool_info.admin == who, BadOrigin);

			let stakers = PoolStakers::<T>::iter_key_prefix(pool_id).next();
			ensure!(stakers.is_none(), Error::<T>::NonEmptyPool);

			let pool_balance = T::Assets::reducible_balance(
				pool_info.reward_asset_id.clone(),
				&pool_info.account,
				Preservation::Expendable,
				Fortitude::Polite,
			);
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&pool_info.admin,
				pool_balance,
				Preservation::Expendable,
			)?;
```
