### Title
Webhook shop/topic identity spoofing via HMAC that only signs the body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC only over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values are taken from unauthenticated HTTP headers. `Registry.process` uses the verified body's HMAC as proof of authenticity for the whole request, then dispatches to a handler using the topic and passes along the shop domain — none of which are bound by the signature.

### Finding Description
`Utils::HmacValidator.validate` verifies `verifiable_query.to_signable_string` against the HMAC: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body, while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers with no HMAC coverage: [2](#0-1) 

`Registry.process` treats a valid body HMAC as authorizing the whole request, then dispatches the handler keyed by the unauthenticated `topic` header and forwards the unauthenticated `shop` value into `WebhookMetadata`: [3](#0-2) 

The identity binding that should hold is: `hmac == HMAC(secret, body ‖ shop ‖ topic)`, but the actual check enforced is only `hmac == HMAC(secret, body)`. Since the app's `api_secret_key` is a single shared secret used for every shop that installs the app (confirmed by `HmacValidator.validate`/`validate_signature` using `Context.api_secret_key` unconditionally, with no per-shop key), any entity that can obtain one valid `(body, hmac)` pair for their own shop — trivial for an attacker who installs the app on their own store and receives its webhooks — can resend that identical body/HMAC pair while substituting a different `x-shopify-shop-domain` and/or `x-shopify-topic` header. `Registry.process` will accept it as authentic and hand `WebhookMetadata` with the attacker-chosen `shop`/`topic` to the registered handler.

### Impact Explanation
This breaks the tenant boundary the library's webhook processing is supposed to guarantee: `HMAC verifies (shop, topic, body) == what Shopify actually sent for that shop/topic`, but only `body` is actually protected. A host application that (reasonably) trusts `WebhookMetadata#shop` and `#topic` returned by this gem — e.g., to key per-tenant records, revoke tokens on `app/uninstalled`, or fulfill GDPR `customers/redact`/`shop/redact` mandatory webhooks — can be made to act on forged tenant identity, i.e., cross-tenant data operations using an unrelated, attacker-controlled shop domain. This falls under the Critical "cross-tenant access" bucket since the trust boundary crossed is between one merchant's data and another's, using only unprivileged means (installing the app once on the attacker's own store).

### Likelihood Explanation
Any developer or merchant who can install the app (an "unprivileged internet user" relative to other tenants) automatically receives legitimate `(body, hmac)` pairs for their own shop's real webhook events. Forging headers on an HTTP request is trivial; the only requirement is that the target host app's webhook endpoint is reachable (which it must be, since Shopify itself calls it). No access token, secret leakage, or privileged access is required — only participation as a normal, unprivileged merchant of the multi-tenant app.

### Recommendation
Bind `shop` and `topic` into the signed material verified by `HmacValidator`, or otherwise cryptographically tie the accepted shop/topic to the specific installation the secret was issued for (e.g., cross-check `request.shop` against a shop that is known to have a live session/webhook subscription for that HMAC, or include the header values in the signable string if Shopify's webhook signing scheme is extended to support this). At minimum, document and enforce that host applications must independently verify `WebhookMetadata#shop`/`#topic` against their own installed-shop registry before trusting them, and consider validating consistency between the topic requested at registration time and the topic delivered.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC_SHA256(api_secret_key, B)`.
2. Attacker replays the exact same `B`/`H` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: app/uninstalled`.
3. `Utils::HmacValidator.validate` recomputes `HMAC_SHA256(api_secret_key, B)` (the same secret is shared across all shops) and it matches `H`, so validation succeeds: [4](#0-3) 
4. `Registry.process` dispatches the `app/uninstalled` (or any registered topic) handler with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", body: parsed(B), ...)`: [5](#0-4) 
5. If the host app's handler trusts `data.shop`/`data.topic` (as the library's own docs/tests imply it should), it will perform tenant-scoped actions (e.g., wipe or mutate data) attributed to `victim-shop.myshopify.com` even though nothing from that shop was actually involved.
