## Finding

### Title
Non-standard ERC20 return values are silently ignored in `withdraw()`/`SweepDust` handling, causing escrow to be marked filled without tokens actually moving - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2` (Tron variant) imports and enables OpenZeppelin's `SafeERC20` [1](#0-0) , and correctly uses `safeTransferFrom` for deposits [2](#0-1) . However, the token payout paths in `withdraw()` and the `SweepDust` handler bypass this and instead perform a raw low-level `.call` with `IERC20.transfer.selector`, checking only that the call did not revert - never inspecting the returned boolean.

### Finding Description
In `withdraw()`, escrowed tokens are released using:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [3](#0-2) 

and identically for protocol fee payout: [4](#0-3) 

and in the `SweepDust` branch of `onAccept`: [5](#0-4) 

For any ERC20 token that follows the standard and returns `false` on a failed transfer instead of reverting (e.g. paused, blacklisted-recipient, or insufficient-balance-without-revert tokens), `token.call(...)` still returns `success = true` (the external call itself did not throw), because the low-level `call` never decodes/validates the returned `bool`. This is exactly the return-value-handling flaw described in the reference report (using raw `IERC20.transfer` without validating the boolean result), except here it's compounded: even the low-level-call pattern intended to tolerate no-return-data tokens fails to check the returned data when it *is* present and `false`.

Critically, in `withdraw()` the escrow accounting is updated (`_orders[body.commitment][token] -= amount;`, `_filled[body.commitment] = beneficiary;`) unconditionally alongside this unchecked call [6](#0-5) , so the order is marked filled/redeemed even though the beneficiary never received the tokens.

### Impact Explanation
`withdraw()` is reached via `onAccept` when handling `RedeemEscrow`/`RefundEscrow` requests delivered through the standard ISMP relay path (`authenticate(incoming.request)` then `withdraw(...)`) [7](#0-6) , and via `onGetResponse` for GET-based refund flows [8](#0-7) . These are triggered by relayers submitting valid cross-chain proofs as part of normal intent fill/cancel/refund flow - not privileged admin actions. If the escrowed token is one that returns `false` on failed transfer (a legitimate ERC20 behavior), the escrow bookkeeping permanently marks the order as filled/refunded and decrements the internal balance while the actual tokens remain stuck in the contract, permanently unreachable by the intended beneficiary (no other code path re-attempts payout for a "filled" commitment). This is a permanent freezing of user funds for otherwise standard-conforming tokens.

### Likelihood Explanation
Likelihood depends on whether a deployed input/output token for an order can return `false` instead of reverting on failure. Multiple ERC20 tokens (and TRC20 tokens on Tron, the target chain of this contract) implement this pattern, so it is a plausible scenario for a subset of listed tokens, especially any with pausability/blacklisting under conditions not tied to `msg.sender`'s explicit approval revert.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` (both token release and fee release) and in the `SweepDust` handler with `IERC20(token).safeTransfer(...)`, consistent with the `SafeERC20` usage already applied elsewhere in the same contract (e.g. in `safeTransferFrom` calls). This ensures both missing-return-data and explicit-`false`-return tokens revert the transaction instead of silently marking escrow as settled.

### Proof of Concept
1. Deploy an ERC20-like token whose `transfer()` returns `false` on failure without reverting (e.g. paused state prevents transfer, function returns `false`).
2. Create and fill an order using this token as an input asset in `IntentGatewayV2` (Tron).
3. Trigger `RedeemEscrow`/`RefundEscrow` via the ISMP relay path so `withdraw()` executes while the token is in a state that returns `false` (e.g. pause the token or configure a blacklist on the beneficiary).
4. Observe `withdraw()` proceeds: `success` is `true` from the low-level call (no revert occurred), so `TransferFailed` is never raised; `_orders[commitment][token]` is decremented and `_filled[commitment]` is set, while the beneficiary's on-chain balance is unchanged - the tokens are now permanently stuck in the gateway with no remaining code path to retrieve them.
