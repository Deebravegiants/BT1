### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read from unauthenticated HTTP headers. `Webhooks::Registry.process` validates the HMAC and then forwards the header-derived `shop` value to the app's handler as the tenant identifier for the webhook event. This mirrors the audited underflow bug's root cause: a value that drives tenant-critical logic (`userInfo[user].amount` in the audit; `shop` here) is acted upon without being bound to the cryptographic check that is supposed to guarantee its integrity (the subtraction validation in the audit; the HMAC signature here).

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are derived purely from HTTP headers, which are not part of the signed content: [2](#0-1) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (the raw body) and compares it with the `hmac` claim, but never touches the headers: [3](#0-2) 

`Registry.process` validates only this body-bound HMAC, then immediately uses the unauthenticated `request.shop` and `request.topic` header values to build the metadata delivered to the app's handler: [4](#0-3) 

Because the shop identity is never part of the signed payload, the binding "shop claimed in the webhook == shop the HMAC actually vouches for" does not hold. Any party that can obtain one validly-signed webhook body (e.g., because they run/administer a shop that has the app installed, or capture any real webhook delivery) can resend that exact body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for an arbitrary target shop. `HmacValidator.validate` will still pass because it only checks the body against the secret, and the handler will receive `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
This breaks the tenant isolation guarantee that `Webhooks::Registry.process` is supposed to provide to embedded apps: webhook handlers are documented to trust `WebhookMetadata#shop` as the authenticated source of the event. An attacker who controls one shop's outgoing webhook (or replays any leaked/captured payload) can inject webhook data attributed to a different merchant's `shop` domain, achieving cross-tenant data confusion/injection in any app that keys its per-shop state or authorization decisions off `WebhookMetadata#shop`, as the documented usage pattern instructs (see `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`). This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to possess at least one validly HMAC-signed webhook body (trivially available to anyone who installs/operates the app on their own shop, since GDPR/webhook events are regularly delivered to any installed shop) and the ability to POST to the app's public webhook callback endpoint with custom headers — both are unprivileged-internet-user capabilities requiring no `api_secret_key`, access token, or credential leakage.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable representation, or otherwise cryptographically bind them to the signed payload (e.g., by validating the `shop` against a canonical source recovered independently, such as an app-side webhook subscription/shop registry, rather than trusting the header verbatim). At minimum, document that `WebhookMetadata#shop` is unauthenticated and must be independently cross-checked by the host application before being used for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook event, capturing the raw POST body and its legitimate `x-shopify-hmac-sha256` value.
2. Attacker resends the identical body/HMAC to the app's webhook endpoint, replacing the `x-shopify-shop-domain` header with `victim-shop.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `@raw_body` against the secret: [4](#0-3) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, even though the payload never originated from Shopify for that shop.
