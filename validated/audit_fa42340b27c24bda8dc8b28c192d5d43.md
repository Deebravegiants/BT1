### Title
Webhook shop-domain is trusted for tenant identity but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signable string using only the raw request body, while the `shop` (tenant identifier) is read from an unsigned HTTP header and passed downstream to the app's webhook handler as the authenticated shop for that webhook payload.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` treats a request as authenticated once `Utils::HmacValidator.validate(request)` passes, then immediately builds `WebhookMetadata` using `request.shop`, handing it to the app-supplied handler as the trusted tenant identity: [1](#0-0) 

The HMAC validation, however, is only ever computed over the raw body: [2](#0-1) 

`shop` is derived purely from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is completely outside the signed content: [3](#0-2) 

The identity binding that should hold is:
`shop used to authorize/attribute the payload == shop covered by the HMAC signature`

but in this implementation:
`HMAC(secret, raw_body) is valid` ⇏ `shop header is authentic`

Because the header is never part of `to_signable_string`, any request whose body+HMAC pair is valid (e.g., a genuine webhook delivery for the attacker's own store, which the attacker fully controls and can replay) can have its `shop-domain` header rewritten to claim a different (victim) shop, and `HmacValidator.validate` will still return `true`, since it only recomputes the digest over `@raw_body`.

The gem's own documentation reinforces that `Registry.process` is expected to fully authenticate the source: "This will verify the request did indeed come from Shopify and then call the specified handler for that webhook" — but the `shop` field, which downstream apps are told to trust as `data.shop` (see `docs/usage/webhooks.md` lines 12-17, 125), is not actually verified as belonging to the signed payload.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` to key per-tenant business logic (multi-tenant lookups, per-shop state updates, access control decisions) can be made to process a request under an incorrect shop identity, despite `HmacValidator.validate` succeeding. Since HMAC validation is the gem's only authenticity check for webhook shop attribution, and no cross-check between the signed content and the header claiming a shop identity exists, this breaks the tenant isolation boundary that `Registry.process` implicitly promises ("verify the request did indeed come from Shopify" for that shop). This matches the High-impact "cross-tenant access" category, since a request nominally validated as authentic can be attributed to an arbitrary shop domain chosen by whoever crafts the header.

### Likelihood Explanation
Exploiting this requires the attacker to possess at least one valid `(raw_body, hmac)` pair — trivially obtainable by triggering any webhook to their own Shopify store — and the ability to control/replay the HTTP headers sent to the app's public webhook endpoint, which is realistic for any internet-reachable webhook receiver built directly on this gem's `Registry.process`/`Request` API without extra shop allow-listing.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the HMAC-signed content, or require the host application to independently verify `request.shop` against the shop associated with the corresponding webhook subscription/session, rather than trusting a header value that falls outside `to_signable_string`.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com` and has this app installed; they configure a webhook subscription and capture a legitimate delivery, giving them a valid `(raw_body="{}", x-shopify-hmac-sha256=H)` pair where `H = HMAC-SHA256(api_secret_key, "{}")`.
2. Attacker sends a forged POST to the app's webhook endpoint with:
   - `x-shopify-hmac-sha256: H` (unchanged, still valid for body `"{}"`)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (swapped from their own shop)
   - `x-shopify-topic`, `x-shopify-webhook-id` set to any registered topic/id.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — this passes because it only checks `HMAC(secret, "{}")` against `H`.
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to act on data attributed to the victim shop, as shown by how `shop` flows through `Registry.process`: [4](#0-3)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
