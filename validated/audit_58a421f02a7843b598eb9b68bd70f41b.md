## Analysis

Root cause pattern from the ENS report: a value is *validated* through one channel but *acted upon* using an unrelated, unauthenticated channel — breaking the equality `validated_value == acted_upon_value`. The ENS bug validated `registrar.ownerOf` but acted on trust derived from `ens.owner`. The analog here is Shopify's webhook processing.

### Where the binding breaks

`ShopifyAPI::Webhooks::Request` reads the tenant identity (`shop`) from an HTTP header, but the HMAC signature that authenticates the request only covers the raw body: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`, so `x-shopify-shop-domain` (and `x-shopify-topic`, `x-shopify-webhook-id`, `x-shopify-api-version`) are entirely outside the authenticated bytes: [3](#0-2) 

`Registry.process` validates only that HMAC: [4](#0-3) 

and then forwards `request.shop` (the unauthenticated header) straight into `WebhookMetadata`, which is the value the host application's handler uses to identify which tenant the webhook is for.

### Binding equality broken

`HMAC-verified(bytes) == raw_body` but `acted-on tenant identity (request.shop) != raw_body` — the shop claim is never bound into the signed bytes, so `verified_bytes ⊉ shop`.

### Exploit path

1. Attacker installs the app on their own shop (`attacker-shop.myshopify.com`) — an unprivileged action requiring no special credentials.
2. Shopify legitimately signs and delivers a webhook to the attacker's endpoint with a valid `x-shopify-hmac-sha256` computed over the body using the app's shared `api_secret_key`.
3. Attacker captures this `(raw_body, hmac)` pair — the HMAC only certifies the body content, never the shop.
4. Attacker replays the identical body/HMAC to the same app endpoint, substituting `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` still succeeds because it only checks the raw body/secret; `Registry.process` calls the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)`.
6. Any host application logic that trusts `data.shop` to select/update tenant-scoped records (the documented usage pattern) now writes attacker-controlled data under the victim's tenant — a cross-tenant data-injection primitive achieved without possessing the victim's access token or secret.

This matches Shopify's actual webhook spec (HMAC signs body only), so the "insidiousness" is identical to the ENS finding: the fix that validates the *primary* channel (body via HMAC) does not also bind the *secondary* channel (shop-domain header) that downstream code trusts as if it were authenticated.

### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing cross-tenant webhook forgery via header substitution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body; `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers and passed downstream as trusted tenant identity, even though `Registry.process` only verifies the HMAC over the body.

### Finding Description
`Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) validates `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) — returning only `@raw_body`. The `shop` accessor (`lib/shopify_api/webhooks/request.rb:20-23`) reads directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never included in the signed bytes. Because any shop that installs the app receives validly-signed webhooks for its own body content, and the HMAC secret (`api_secret_key`) is shared across all tenants of the app, an attacker who controls one tenant can capture a legitimately-signed `(body, hmac)` pair and resend it with a forged `shop-domain` header pointing at a victim tenant. The gem will report this as a validated request and hand the forged shop identity to the host application's webhook handler.

### Impact Explanation
This breaks the tenant/authentication boundary the HMAC is supposed to enforce: shop identity is unauthenticated data injected into a trusted API surface (`WebhookMetadata#shop`). Applications that key persistence, notifications, or business logic off `data.shop` (the documented and expected usage) can have their per-tenant data overwritten or forged by another tenant, i.e., cross-tenant access/data injection.

### Likelihood Explanation
Any user of the app (an unprivileged internet user relative to other merchants) can trivially become a legitimate webhook source for their own shop, then replay/reuse the body+HMAC while swapping the shop header — no access token, secret, or privileged access to the victim tenant is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id/api version) in the HMAC-signed material, or otherwise cryptographically bind the shop claim to the signature (e.g., derive/verify shop from a signed source, or require the caller to additionally confirm the shop against a known/active session before trusting `WebhookMetadata#shop`). At minimum, document prominently that `shop` is unauthenticated and must be independently verified by the host application before tenant-scoped actions are taken.

### Proof of Concept
```ruby
# 1. Attacker's own shop receives a legitimately signed webhook:
raw_body = '{"id":1,"note":"hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

legit_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
}

# 2. Attacker replays same body/hmac but forges the shop-domain header:
forged_headers = legit_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

req = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(req)
# => HMAC validation succeeds (it only checks raw_body); handler receives
#    WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker-controlled)
```

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
