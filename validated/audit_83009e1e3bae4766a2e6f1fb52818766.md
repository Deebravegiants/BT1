## Title
Unbounded, cost-free `ReputationAsset` minting via repeated self-relayed messages allows Sybil takeover of collator selection - (`modules/pallets/messaging-incentives/src/lib.rs`)

### Summary
`pallet-messaging-incentives` mints a soulbound `ReputationAsset` to whoever signs as the delivering relayer on every executed ISMP `Request`/`Response`, scaled by `max(body_len, 32) × MintPerByte`, with **no per-session cap, no rate limit, and no accounting of how much any single account has minted** [1](#0-0) . This reputation balance is the sole ranking signal `pallet-collator-manager` uses to select the next block-producing set [2](#0-1) . Because dispatch on `EvmHost` no longer charges any per-byte protocol fee — "on-chain dispatch now charges only the relayer fee carried in `DispatchPost.fee`", which the dispatcher fully controls and may set to `0` [3](#0-2)  — an attacker who is both the dispatching app and the self-signing relayer can mint an unbounded amount of `ReputationAsset` for negligible cost, exactly the "points minted without any cost" pattern described in the FlatMoney report, but here the minted asset directly controls consensus-participant (collator) selection rather than a rewards leaderboard.

### Finding Description
`on_executed` computes, per delivered `Request`/`Response` message, `bytes = max(body.len(), 32)` and mints `rate * bytes` of `ReputationAsset` to the sr25519 signer recovered from the message's `signer` field [4](#0-3) . The 32-byte floor is applied **per request**, explicitly to prevent gaming by splitting one payload into many — but this floor is exactly what an attacker exploits in the opposite direction: dispatching many trivially small (near size 0) requests, each independently floored to 32 bytes for reward purposes, multiplies the mint by the number of requests rather than by actual payload size [5](#0-4) .

The cost side of this loop is essentially zero: dispatching a POST request on the EVM host only requires the optional `DispatchPost.fee` (relayer fee), which the dispatcher sets and may set to `0` for self-relay — the per-byte protocol fee that used to exist on `EvmHost` has been removed entirely [3](#0-2) . An attacker controlling both the source-chain sender and the destination-chain relayer key can dispatch many tiny/no-fee messages between accounts they control, sign the delivery messages themselves, and repeatedly collect `32 × MintPerByte` reputation per message with no rate limit and "no per-session accounting" anywhere in the pallet [1](#0-0) .

`ReputationAsset` is not a cosmetic score: `pallet-collator-manager::new_session` ranks candidates purely by their controller's `ReputationAsset` balance and selects the top N as the next block-producing collator set, then burns their balance [6](#0-5) . This is the same "reputation-based collator selection" mechanism documented for validators/network security [7](#0-6) . Since minting is essentially free and unbounded, an attacker can out-rank every honest relayer/prover and force the selection of collators they control, or deny selection to legitimate high-throughput relayers by out-farming them at zero real cost — the same "mint large amounts cheaply, and use it to prevent others from earning/being selected" pattern flagged in the referenced FlatMoney report, except the impacted asset here gates block production rather than a points leaderboard.

### Impact Explanation
Because `ReputationAsset` balance directly determines the next session's collator set [8](#0-7) , unbounded cost-free minting is a path to unauthorized control of block production — an attacker can stack enough reputation to guarantee selection as a collator (or to starve legitimate operators out of slots), undermining the liveness/fraud-detection guarantees the collator set is relied on for (each collator also runs the in-node fisherman veto task) [9](#0-8) . This is a state-machine-level unauthorized action, not merely a rewards/points imbalance.

### Likelihood Explanation
The only real-world cost is gas for dispatch/delivery transactions plus (if `MintPerByte` is nonzero) the fixed 32-byte floor per message; there is no explicit rate limit, per-account cap, or per-session accounting to bound this, unlike the mitigation the FlatMoney report describes as only a partial fix. Any account able to dispatch ISMP messages and sign as a relayer — which is a normal, unprivileged capability — can run this loop.

### Recommendation
Introduce a per-account (or per-session) cap/rate-limit on `ReputationAsset` minted via `pallet-messaging-incentives` (and the analogous `pallet-consensus-incentives`), decouple the mint rate from a fixed per-request floor that rewards message count rather than genuine payload/bandwidth delivered, and/or require a minimum real dispatch cost proportional to the reward so that splitting into many tiny self-relayed messages is not profit-neutral.

### Proof of Concept
1. Attacker deploys/uses a contract on chain A and controls an sr25519 relayer key on Hyperbridge.
2. Attacker repeatedly calls `dispatch` with `DispatchPost{ body: <tiny/empty>, fee: 0, payer: attacker }` targeting a module the attacker also controls on the destination, paying no protocol per-byte fee (removed from `EvmHost`) [3](#0-2) .
3. Attacker (as relayer) delivers each message to Hyperbridge; `pallet_ismp`'s `FeeHandler::on_executed` invokes `pallet-messaging-incentives::on_executed`, which floors each request at 32 bytes and mints `32 * MintPerByte` `ReputationAsset` to the attacker's controller account [10](#0-9) .
4. Repeating this loop many times (bounded only by gas/time) accrues a `ReputationAsset` balance far above any honest operator's.
5. At the next session boundary, `CollatorManager::new_session` ranks candidates by `ReputationAsset` balance and selects the attacker's controller into the collator set ahead of legitimate operators [6](#0-5) .

impl<T: Config> Pallet<T>
where
	T::AccountId: From<[u8; 32]>,
{
	/// Same minimum-byte rule as the bandwidth gate (`max(body, 32)`),
	/// applied **per request** so packing requests into one envelope
	/// vs. splitting them across many produces identical mints.
	/// Applying the floor once per envelope would let a relayer inflate
	/// the mint by splitting (each split picks up its own 32-byte floor).
	fn message_bytes(message: &Message) -> u32 {
		match message {
			Message::Request(req) => req
				.requests
				.iter()
				.map(|p| core::cmp::max(p.body.len() as u32, 32))
				.sum::<u32>(),
			_ => 0,
		}
	}

impl<T: Config> FeeHandler for Pallet<T>
where
	T::AccountId: From<[u8; 32]>,
{
	fn on_executed(
		messages: Vec<MessageWithWeight>,
		_events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let rate = MintPerByte::<T>::get();
		if !rate.is_zero() {
			for mw in &messages {
				let bytes = Self::message_bytes(&mw.message);
				let bytes_balance: BalanceOf<T> = (bytes as u128).saturated_into();
				let amount = rate.saturating_mul(bytes_balance);
				if amount.is_zero() {
					continue;
				}
				if let Some(relayer) = Self::relayer_for(&mw.message) {
					match T::ReputationAsset::mint_into(&relayer, amount) {
						Ok(_) =>
							Self::deposit_event(Event::ReputationMinted { relayer, bytes, amount }),
						Err(err) => log::warn!(
							target: "messaging-incentives",
							"reputation mint failed for {bytes}b: {err:?}",
						),
					}
				}
			}
		}
		Ok(PostDispatchInfo { actual_weight: None, pays_fee: Pays::No })
	}

# Pallet Collator Manager

This pallet introduces a reputation-based collator selection mechanism. The primary goal is to select collators based on their accrued revenue, which is treated as a reputation score held in a `pallet-assets` token.
This system is designed to incentivize reliable and active relayer participation in the network.

This pallet provides:

* An implementation of the `SessionManager` trait.
* Core logic for selecting a new set of collators at the beginning of each session based on their reputation score.
* A mechanism for resetting the reputation scores of outgoing collators to ensure a fair and dynamic selection process.
