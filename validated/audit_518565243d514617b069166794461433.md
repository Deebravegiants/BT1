### Title
Webhook `shop` identity is not covered by the HMAC, allowing cross-tenant shop-domain spoofing on replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body [1](#0-0) . The `shop` field returned to the handler is read from the `shop-domain` header, which is never part of the HMAC-signed content [3](#0-2) . `Registry.process` validates only that the body's HMAC is correct, then trusts `request.shop` as the tenant identifier passed to the app's handler [2](#0-1) .

### Finding Description
This mirrors the "maxTranches" bug class: a check is performed (HMAC validity), but a field acted upon (`shop`) is not bound by that check. `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received `hmac` [6](#0-5) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, so the `shop-domain` header can be freely substituted without invalidating the HMAC, as long as the attacker possesses one valid `(raw_body, hmac)` pair signed by the app's `api_secret_key` for *any* shop.

Because `Registry` is a single global registry shared by all shops using the app (one `@registry` per topic, not one per shop) [7](#0-6) , and because the app's webhook endpoint is a plain public HTTP route (as shown in the documented Rails example, which does no additional shop-based authorization) [8](#0-7) , a merchant who has legitimately installed the app can capture a real, validly-signed webhook delivered to their own shop, then replay that exact `(raw_body, hmac)` pair directly to the app's public webhook endpoint while substituting the `shop-domain` (or `x-shopify-shop-domain`) header with a victim shop's domain. `Registry.process` will validate the HMAC successfully (it only checks the body) and will invoke the handler with `WebhookMetadata.new(shop: request.shop, ...)` where `shop` is now the attacker-chosen victim domain [9](#0-8) . Any app that uses `data.shop` to key writes, cache invalidation, job enqueueing, or session/token lookups (as the documented example does: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) will then process the attacker's data under the victim's tenant identity.

The binding that is broken, stated as an equality: the shop-domain claimed by `request.shop` (unsigned header) is trusted as if it equaled the shop-domain bound to the HMAC-covered payload — but `shop` is never part of `to_signable_string`, so this equality does not hold.

### Impact Explanation
This is a cross-tenant data confusion vector: an authenticated app-merchant (unprivileged relative to other merchants) can cause the app to attribute arbitrary attacker-controlled webhook payloads to a different, victim shop, since the shop identity is not cryptographically bound to the signed body. Downstream apps that trust `data.shop` for tenant-scoped persistence or authorization (as the gem's own documented handler pattern does) can have their per-tenant data integrity violated — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Requires only: (1) legitimate installation of the target app on an attacker-controlled shop to receive one genuine signed webhook, and (2) direct HTTP access to the app's public webhook endpoint with header control — both realistic for any external, unprivileged actor with a free/dev store, and no leaked secrets or privileged access are needed.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) in the HMAC-signed content, or otherwise cryptographically/contextually bind the declared shop to the signed payload (e.g., validate `shop` against the shop associated with the specific webhook subscription/session before invoking the handler) in `ShopifyAPI::Webhooks::Request#to_signable_string` and `ShopifyAPI::Webhooks::Registry.process`.

### Proof of Concept
1. Install the target app normally on Shop A (attacker-controlled); Shopify delivers a real webhook, e.g. `orders/create`, to the app's endpoint with a valid `x-shopify-hmac-sha256` for some `raw_body`.
2. Attacker captures this `(raw_body, hmac)` pair (it's delivered to a URL/route they control or can proxy).
3. Attacker POSTs directly to the app's public webhook route with the same `raw_body` and `hmac` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against `hmac` [10](#0-9) .
5. The handler is invoked with `data.shop == "victim-shop.myshopify.com"` even though the payload actually originated from Shop A, causing the app to process/attribute Shop A's data as Victim Shop's data.
