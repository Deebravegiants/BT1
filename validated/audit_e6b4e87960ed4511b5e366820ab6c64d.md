### Title
Webhook shop identity spoofable because `shop-domain` header is not covered by HMAC verification - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, then passes the unauthenticated `shop-domain` header straight through to the app's handler as the tenant identifier. Any party able to obtain one validly-signed webhook body (e.g., a merchant who has legitimately installed the app on their own store) can replay that exact body/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` header, causing the host application to process the payload as if it originated from a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC using only what `to_signable_string` returns, i.e. the body: [3](#0-2) 

`Registry.process` accepts the request purely on that body-only HMAC check, then forwards the unauthenticated `shop` value into `WebhookMetadata`, which the host app's handler is expected to trust as the tenant identity: [4](#0-3) [5](#0-4) 

This breaks the identity binding: `hmac(raw_body) == hmac(raw_body)` holds true regardless of which value is present in the `shop-domain` header, so the equality the gem should be enforcing — *the shop that the HMAC authenticates* == *the shop the handler is told the data belongs to* — does not hold. An attacker who can obtain any one genuinely-signed webhook (trivially achievable by installing the app on a shop they control and triggering a webhook, e.g. `app/uninstalled` or any subscribed topic) can retransmit that exact body/HMAC to the app's webhook endpoint while spoofing `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) to name a victim shop. `Registry.process` will treat this as fully valid and hand the host app a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This is a cross-tenant identity-confusion vector: a merchant/tenant that is unprivileged with respect to other tenants can cause the host application to attribute attacker-controlled event data to a different shop's tenant record. Depending on how the host app uses `data.shop` (e.g., to look up the tenant's session/access token and perform a write, to update billing/subscription state, or to trigger app-uninstall cleanup), this can result in cross-tenant data corruption or denial of a victim's app functionality — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Moderate-to-high. No credentials, `api_secret_key`, access tokens, or privileged accounts are required beyond installing the app on any shop (a normal, unprivileged action any merchant can take), obtaining one legitimately signed webhook for that shop, and replaying it with a forged shop header against the app's public webhook endpoint. The gem itself performs no binding between the authenticated body and the shop/topic/webhook-id headers it exposes to callers.

### Recommendation
Extend `Utils::VerifiableQuery#to_signable_string` for `Webhooks::Request` (or add a separate verification step in `Registry.process`) to bind the `shop-domain` (and ideally `topic`/`webhook-id`) header values into what is authenticated, or require host applications to independently verify that the reported shop has an active session/installation before trusting `WebhookMetadata#shop`. At minimum, document prominently that `data.shop` is not cryptographically authenticated by `HmacValidator` and must be cross-checked against a known, installed shop by the host application before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a subscribed webhook topic (e.g. `products/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent — this HMAC is valid because it was computed by Shopify using the app's real secret over that body.
2. Attacker resends the identical body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"` and invokes the host app's handler, which now processes attacker-supplied data believing it originated from the victim shop.
