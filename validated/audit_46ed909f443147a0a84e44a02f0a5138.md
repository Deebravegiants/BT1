### Title
Inconsistent length enforcement on user-identifier parsing allows legacy QR-code path to accept a truncated `user_id`, unlike the modern `decode_qr` path - ([File: src/plans/qr_scan/user.rs])

### Summary
`orb-core`'s user QR-code parser (`qr_scan::user::Data::try_parse`) supports two parsing paths for the identity token embedded in a QR code: the modern `orb_qr_link::decode_qr` path, which decodes a fixed-length, cryptographically well-formed UUID, and a legacy regex path (`QR_CODE_V2`) that accepts a `user_id` capture group whose length is **not fixed** — it can match either a full 128-bit UUID or a truncated fragment of one. This mirrors the reported bug class exactly: one code path enforces a strict length/format on an identity-bearing value while a parallel path used for the same purpose does not.

### Finding Description
`qr_scan::user::Data::try_parse` tries three parsing strategies in order, falling back progressively to laxer formats: [1](#0-0) 

The first strategy, `orb_qr_link::decode_qr`, is the strict, modern path and yields a fully-qualified UUID plus an optional hash of associated user data. The second strategy, matched against `QR_CODE_V2`, has a `user_id` capture group with a partially-optional structure: [2](#0-1) 

The last two hyphenated groups (`-[a-z0-9]{4}-[a-z0-9]{12}`) are wrapped in `(?:...)?`, making them optional. This means the regex accepts both a full 36-character UUID (`8-4-4-4-12`) and a truncated 18-character fragment (`8-4-4`) as a "valid" `user_id`. This is confirmed directly by the test suite: [3](#0-2) 

Unlike the reported Solidity issue — where `addValidators` enforces `_publicKeys.length % PUBLIC_KEY_LENGTH == 0` but `setWithdrawer`/`withdrawELFee` do not enforce any length on the same logical "public key" argument — here `decode_qr` implicitly enforces full UUID structure (128 bits) while `QR_CODE_V2` allows the same logical field (`user_id`, the signup identity) to be truncated to as little as the first three UUID groups, with no validation against a canonical length.

### Impact Explanation
The truncated `user_id` is subsequently treated as an opaque signup identity across the codebase: it is compared against the operator QR's `user_id` to filter duplicate scans, is hashed into the biometric-pipeline signature (`make_signature`), and is sent to the backend as `userId`/`distributorId` in the signup request: [4](#0-3) [5](#0-4) [6](#0-5) 

Because the regex silently accepts a shortened identifier without normalizing or rejecting it, a caller who supplies a valid-looking but truncated `userid:...` code changes what signature/identity material gets bound to a signup, versus what would be produced from the full-length identifier the backend expects elsewhere. This is a cross-signup identity-binding inconsistency: the same nominal field ("user_id") can be full-length in one code path and partial in another, with no orb-side length check to reconcile them before the value is baked into the signature and submitted to the backend for identity/authorization decisions.

### Likelihood Explanation
Reachability is straightforward: `QR_CODE_V2` is not test-only or feature-gated — it's compiled and evaluated unconditionally as the second fallback in `try_parse`, which runs on every normal QR scan (`qr_scan::Plan::<qr_scan::user::Data>::run`) as well as via CLI overrides (`user_qr_code` in `src/plans/mod.rs`). Any physically presentable QR code (or CLI-provided string in override mode) matching the shortened pattern would be accepted with no server round-trip needed to detect the truncation orb-side.

### Recommendation
Enforce a single canonical length for `user_id` across all QR parsing paths in `src/plans/qr_scan/user.rs`: either require the `QR_CODE_V2` regex's `user_id` group to always match the full `8-4-4-4-12` UUID shape (removing the optional group), or explicitly validate/parse the captured value as a `uuid::Uuid` (as the `decode_qr` path already effectively guarantees) before constructing `Data`. This mirrors the report's recommendation to unify all pubkey-accepting entry points on the same explicit length check rather than allowing format-dependent divergence.

### Proof of Concept
Using the existing test harness pattern in `src/plans/qr_scan/user.rs`:
```rust
let text = "userid:3bcf883d-ce22-4a03:1"; // 3 groups only, 18 chars vs. full 36-char UUID
let data = Data::from_v2(&QR_CODE_V2.captures(text).unwrap());
assert_eq!(data.user_id, "3bcf883d-ce22-4a03"); // accepted, non-canonical length
```
This is verified by the repository's own `test_v2_shortened` test [3](#0-2) , demonstrating that a QR-code payload with a truncated identity token is treated as valid `Data` by the same parser that, via its first branch (`decode_qr`), otherwise enforces full UUID structure.

    fn try_parse(code: &str) -> Option<Self> {
        if let Ok((user_id, user_data_hash)) = decode_qr(code) {
            return Some(Self {
                user_id: user_id.hyphenated().to_string(),
                signup_extension: false,
                signup_extension_config: None,
                user_data_hash: Some(user_data_hash),
            });
        }
        if let Some(captures) = QR_CODE_V2.captures(code) {
            return Some(Data::from_v2(&captures));
        }
        #[cfg(feature = "internal-data-acquisition")]
        if let Some(captures) = QR_CODE_SIGNUP_EXTENSION.captures(code) {
            return Some(Data::from_signup_extension(&captures));
        }
        None
    }
