### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw request body only, while the `shop` (tenant identity) is read from an unsigned header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then passes the header-derived `shop` straight to the registered handler, so a request whose body is legitimately signed for one shop can be replayed with an attacker-controlled `shop-domain` header to make the handler believe the event came from a different shop.

### Finding Description
The equality that should hold is: `shop bound by HMAC == shop acted upon by the handler`. In this codebase that equality is broken.

`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed material: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` (i.e., the body), never touching `shop`: [3](#0-2) 

`Registry.process` validates the HMAC and then forwards `request.shop` (the unsigned header value) directly into `WebhookMetadata`, which is handed to the app's business-logic handler as the tenant identifier for the event: [4](#0-3) 

This is structurally the same class of bug as the referenced report: a value that drives a sensitive decision (`shop`, the tenant binding) is not covered by the integrity check (HMAC) that is meant to authenticate the whole request, exactly as `fShare` was not updated by the mint/burn operation that the price formula depended on. Here the "price formula" is the webhook dispatch: it trusts an out-of-band, unauthenticated header for tenant attribution while only cryptographically authenticating the body.

Note by contrast that `Auth::Oauth::AuthQuery#to_signable_string` *does* include `shop` in the signed parameters, so the OAuth callback path correctly binds `shop` to the HMAC: [5](#0-4) 
This asymmetry confirms the webhook path is the outlier where the binding is missing.

### Impact Explanation
Any party capable of sending an HTTP request to the host application's webhook endpoint with a validly-signed body (for example, a merchant who owns their own shop and therefore legitimately receives HMAC-signed webhooks from Shopify for topics with predictable/empty bodies such as `{}`) can replay that signed body while substituting a different `shop-domain` header value. Because `Registry.process` only checks the HMAC of the body and then trusts the header for tenant attribution, the handler executes app logic (e.g., app-uninstalled cleanup, data deletion, subscription/billing state changes) attributing the event to a shop the attacker does not control. This is a cross-tenant integrity violation: the tenant boundary (`shop`) that the host application relies on this gem to authenticate is not actually authenticated.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that has at least one webhook topic with a fixed, predictable, or empty body (many `app/uninstalled`, `shop/redact`, or ping-style webhooks have such bodies). An attacker only needs their own working shop and secret-free capture/replay of a legitimately signed payload — no access to `api_secret_key`, access tokens, or TLS interception is required, satisfying the "unprivileged internet user" constraint.

### Recommendation
Bind `shop` into the signed material used for `to_signable_string`, or otherwise authenticate the `shop-domain` header out-of-band (e.g., cross-check it against a shop-specific secret/session rather than trusting the raw header), so the HMAC verification and the tenant used by `WebhookMetadata` refer to the same authenticated value.

### Proof of Concept
1. A malicious merchant installs the app on their own shop `attacker.myshopify.com` and receives a legitimately Shopify-signed webhook whose body is fixed/empty, e.g. `raw_body = "{}"` with header `x-shopify-hmac-sha256` computed by Shopify over `"{}"` using the app's `api_secret_key`.
2. The attacker resends this exact `raw_body` and `hmac` header to the app's webhook endpoint but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds the request object; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the HMAC only covers `raw_body` (`"{}"`), unaffected by the header change — see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:12-31`.
4. `Registry.process` then invokes the handler with `shop: request.shop` = `"victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host application to process the event as if it genuinely originated from the victim shop, even though nothing cryptographically ties that shop identity to the request.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
