### Title
Webhook `shop` (and `topic`/`webhook_id`) header fields are trusted for tenant routing without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then unconditionally forwards the `shop-domain` header value to the app's handler as the trusted tenant identifier. The HMAC never covers the `shop` (or `topic`/`webhook-id`) header, so the value the app uses to route/attribute the payload is not bound to the same bytes that were authenticated.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the HMAC exclusively against that signable string: [2](#0-1) 

`Registry.process` checks this HMAC, then builds `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id`, all of which are read straight from unauthenticated HTTP headers: [3](#0-2) [4](#0-3) 

The library's documented contract explicitly instructs the host app to use `data.shop` as the shop/tenant identifier for the received event: [5](#0-4) 

The broken equality is: `bytes verified by HMAC (raw_body)` != `bytes acted on as the tenant identifier (shop-domain header)`. Because the app's shared `client_secret` is identical for every shop that has installed the app, any shop that has installed the app can obtain a validly-signed webhook for its own store (a real HMAC over a real body Shopify sent them). Since the header carrying the shop domain is excluded from the signed payload, that same `(raw_body, hmac)` pair remains valid if replayed with an arbitrary `x-shopify-shop-domain` header value substituted for a different, victim shop. `Registry.process` will accept it as authentic and pass the victim's shop identifier along with the attacker-controlled body to the handler.

### Impact Explanation
This breaks the identity binding between the entity Shopify actually generated the event for and the entity the app attributes/stores the event data against, enabling cross-tenant data injection: an attacker who legitimately installs the target app on their own store (a normal unprivileged step, not requiring any secret or privileged access) can cause the app to process arbitrary attacker-controlled webhook bodies under a victim shop's identity. Depending on how the host app uses `data.shop` (e.g., looking up the corresponding merchant record, updating per-shop state, feeding into background jobs), this can inject false state into another tenant's data. This matches the Critical "cross-tenant access" impact category defined for this analysis.

### Likelihood Explanation
Likelihood is high for any consumer following the gem's documented usage: the docs instruct developers to trust `data.shop` directly, with no guidance to independently verify shop ownership or membership against a known, previously-authenticated session/shop list. No access token, `client_secret`, or privileged access is required — only that the attacker be able to install the app on a shop they control and can replay HTTP requests to the app's webhook endpoint.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`/`api-version`) header values in the HMAC-signed material, or otherwise cryptographically bind them to the payload, so that tampering with the header without knowledge of the secret is detected by `HmacValidator.validate`. At minimum, update `Registry.process`/`WebhookMetadata` documentation to explicitly warn that `shop` must be cross-checked against the app's own list of installed/authorized shops before being trusted, since it is not covered by the signature.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, triggering Shopify to send a real webhook: raw body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the exact same body `B` and HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B)` against the unmodified body — validation succeeds: [6](#0-5) 
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, and the host app processes/persists attacker-controlled data as if it originated from `victim.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
