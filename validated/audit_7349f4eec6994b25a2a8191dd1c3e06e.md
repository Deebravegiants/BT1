### Title
Permissionless `update_account_threshold` force-restamps a foreign account's cached LTV downward, freezing that account's borrows and withdrawals - (File: contracts/controller/src/risk/params.rs)

### Summary
The controller caches per-position risk parameters (`loan_to_value`, `liquidation_threshold`, `liquidation_bonus`, `liquidation_fees`) on each supply position rather than reading live spoke configuration. `update_account_threshold` is intentionally permissionless so keepers can refresh these snapshots, but its `LtvOnly` (`has_risks = false`) path performs no ownership check and, critically, no health-factor or solvency gate. Any authenticated address can therefore restamp any account's stored LTV to the current — possibly lower — spoke configuration, which can push the account's LTV-weighted collateral below its outstanding debt and block `withdraw` and `borrow` even though the account's health factor is unchanged and may be well above 1.0.

### Finding Description
`update_account_threshold` requires only `caller.require_auth()` via `require_authorized_caller` and then iterates arbitrary `account_ids` with no owner/delegate check (`contracts/controller/src/risk/params.rs:124-144`). For each target, `sync_account_thresholds` calls `refresh_supply_risk_params`, which unconditionally overwrites `position.loan_to_value` with `effective_config.loan_to_value` when scope is `LtvOnly` (`params.rs:34-39`). The HF ≥ 1.05 protection (`clears_min_hf`) only runs inside `apply_gated_liquidation_params`, i.e. only for `FullTuple` scope (`params.rs:36-38`, `params.rs:68-93`); the final `hf >= 1.05` assertion is also gated on `full_tuple` (`params.rs:221-234`). The declared invariant file justifies this path solely because "the health factor does not read" LTV — but the post-pool risk gates do: `require_post_pool_risk_gates` requires LTV-weighted collateral to cover debt (plus the `min_borrow_collateral_usd` floor) after `borrow`, `withdraw`, and all six account strategies (`contracts/controller/src/risk/validation.rs:27-30`, `docs/reference/endpoints.md:55`). So an account holding a grandfathered higher LTV snapshot — e.g. an asset whose LTV was reduced via `edit_asset_in_spoke` — keeps working until a stranger calls `update_account_threshold(false, [victim_id])` and permanently pins the lower value to the account.

### Impact Explanation
Temporary freezing of user funds. Once the victim's `loan_to_value` is restamped downward, every subsequent `withdraw`, `borrow`, `multiply`, `swap_collateral`, `repay_debt_with_collateral`, etc. must pass LTV coverage against the lower snapshot. A leveraged-but-healthy account can no longer withdraw any collateral (withdrawal re-checks the gate) or rebalance, until the debt is repaid — a state the victim could have avoided entirely had the snapshot not been forced. The attacker needs only a signed transaction; there is no way for the victim or anyone else to restore the old cached LTV since it always restamps to live config. This is the analog of the Redmine flaw class — an endpoint reachable by any registered user that mutates another user's resource-scoped state because the permission check stops at "is the caller authenticated" instead of "is the caller authorized for this account."

### Likelihood Explanation
Medium. Preconditions: governance lowers a spoke asset's LTV (a normal risk-management action), and at least one open account borrowed under the previous, higher LTV such that `Σ collateral·LTV_new < debt`. Calling `update_account_threshold(caller, false, [victim])` then succeeds unconditionally for any signed address, is not gated by pause, and incurs no cost to the attacker. The freeze persists until the victim repays or prices recover, so a single call can lock a borrower's collateral for an extended period. Rated Medium rather than High because exploitation depends on a governance parameter change creating a grandfathered set, and the frozen state is recoverable by repayment — no funds are directly stolen.

### Recommendation
Extend the existing gating logic to the LTV leg. In `refresh_supply_risk_params` / `sync_account_thresholds`, when `config.loan_to_value < position.loan_to_value` and the account has debt, either (a) skip the downgrade, or (b) apply it only if the post-change account still clears the same `THRESHOLD_UPDATE_MIN_HF_RAW`-style gate expressed on LTV-weighted coverage (i.e. `Σ collateral·LTV_new ≥ debt` and the min-borrow floor). Upgrades (new LTV ≥ stored) can remain permissionless since they only relax the owner's constraints. Alternatively, restrict `update_account_threshold` targets to accounts the caller owns or delegates, matching the authority model used by every other account-mutating entrypoint.

### Proof of Concept
1. Governance lists USDC in spoke 1 with `loan_to_value = 9000` BPS.
2. Alice calls `supply(alice, 0, 1, [(USDC, 100_000e6)])`, then `borrow(alice, alice_id, [(ETH, ...)])` so that `collateral·0.90 ≈ 1.02 × debt`. Position stores LTV 9000.
3. Owner calls `edit_asset_in_spoke` reducing USDC LTV to 8000. Alice's stored snapshot is still 9000, so she can still `withdraw` small amounts that keep `collateral·0.90 ≥ debt`.
4. Attacker Bob calls `update_account_threshold(bob, false, [alice_id])`. `sync_account_thresholds` restamps Alice's USDC position to LTV 8000 with no HF or coverage gate (`params.rs:182-205`, `params.rs:218`).
5. Now `collateral·0.80 < debt`, so every `withdraw`/`borrow` on Alice's account reverts in `require_post_pool_risk_gates`. Alice's collateral is frozen until she repays the full debt — a state change she never authorized, triggered by an unprivileged third party.

Supporting code: `contracts/controller/src/risk/params.rs:124-144` (permissionless entry, no owner check), `params.rs:34-39` (unconditional LTV overwrite), `params.rs:221-234` (HF gate only under `full_tuple`), `contracts/controller/src/risk/validation.rs:27-30` (LTV coverage gate applied post-pool on withdraw/borrow), `scripts/permissionless_entrypoints.txt:76` (declared justification covers only liquidation-HF safety, not LTV-coverage freezing).
