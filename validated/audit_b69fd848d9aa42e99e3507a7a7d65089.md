## Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body. This breaks the intended identity binding `shop_header == shop_authenticated_by_hmac`, letting anyone in possession of one legitimately-signed webhook payload replay it with an arbitrary `shop-domain` header value while the signature still validates.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `hmac` is computed/verified solely against that body: [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` checks only this body-derived HMAC, then hands `request.shop` straight to the app's webhook handler as the authoritative tenant identifier, with no separate binding between the header and the signed content: [4](#0-3) 

Because `shop` (and `topic`, `api_version`, `webhook_id`) come from headers that are entirely outside the HMAC's coverage, an unprivileged actor who has captured any one valid, HMAC-signed webhook body delivered to their own shop can resend that exact body/HMAC pair to the app's webhook endpoint while substituting a different value for the `shop-domain` header. The signature check in `HmacValidator.validate` still succeeds (it never looks at headers), and `Registry.process` will invoke the handler believing the event legitimately originated from the victim shop.

### Impact Explanation
Any app built with this gem that uses `WebhookMetadata#shop` (populated from `request.shop`) to select which merchant's records to create/update/delete is exposed to cross-tenant data corruption: an attacker-controlled `shop` value is trusted as if it were verified by the signature, even though it was never authenticated. This satisfies the "cross-tenant access" criterion (Critical), since the tenant boundary — enforced solely by `shop` — can be crossed by any party who has captured one valid signed webhook for their own store.

### Likelihood Explanation
Likelihood is Medium: the attacker must already have received at least one genuinely-signed webhook (trivial for anyone who installs the app on their own store, since apps deliver these to any registered endpoint they control), and the webhook endpoint must not be otherwise restricted (e.g., allowlisted to Shopify's IP ranges) — which matches this gem's documented design, since HMAC validation is presented as the sole verification mechanism (`docs`/webhook usage). No secrets, tokens, or elevated privileges are required.

### Recommendation
Bind the `shop` (and other identifying headers such as `topic`/`webhook_id`) into the HMAC-verifiable payload, or otherwise cryptographically tie the header values to the signed body (e.g., include them in `to_signable_string`), so that a mismatch between the signed body and the header claiming its origin causes `HmacValidator.validate` to fail. At minimum, document prominently that `request.shop`/`topic` are unauthenticated and must not be used as a sole tenant-selection key.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; capture a legitimate webhook POST (raw body `B`, headers including `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker.myshopify.com`), where `H` is a valid HMAC of `B` under the app's `api_secret_key`.
2. Replay the exact same body `B` and signature `H` to the app's webhook endpoint, but change the header to `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request whose `hmac` still equals `H` and whose `to_signable_string` is still `B`; `Utils::HmacValidator.validate` recomputes HMAC over `B` and it matches, so `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) proceeds and calls the handler with `shop: "victim.myshopify.com"` even though Shopify never sent this event for that shop.
