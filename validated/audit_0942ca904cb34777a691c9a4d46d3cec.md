The `_withdraw` function in `IntentsBase.sol` loops through all escrowed tokens for an order and transfers each atomically via `IERC20.safeTransfer`, called both from `onAccept` (cross-chain `RedeemEscrow`/`RefundEscrow` settlement, invoked once by the protocol via Hyperbridge) and `onGetResponse` (cancellation refund path). If any single token in the escrow's token list is a blacklist-capable token (e.g. USDT) and the beneficiary is blacklisted, the entire `safeTransfer` loop reverts, permanently freezing every other escrowed asset in that same order — including unrelated ERC20s that would otherwise be claimable — since this is the terminal, one-shot settlement message delivered via Hyperbridge with no retry/pull mechanism for partial asset recovery.

### Title
Blacklisted beneficiary token blocks release of all other escrowed assets in an order - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw()` iterates over all `body.tokens` in a `WithdrawalRequest` and transfers each with `IERC20.safeTransfer` inside a single atomic loop. This function is the sole settlement path for cross-chain `RedeemEscrow`/`RefundEscrow` messages (via `onAccept`) and for cancellation refunds (via `onGetResponse`). If any one of the multiple escrowed tokens in a multi-asset order is a blacklist-capable token (e.g. USDT/USDC-style tokens with an admin freeze list) and the beneficiary address is blacklisted for that token, the `safeTransfer` call reverts and the entire transaction — including the release of all other, unrelated escrowed tokens in the same order — reverts.

### Finding Description
`_withdraw` releases escrow for every token entry in `body.tokens` in one pass: [1](#0-0) 

This is invoked as the terminal step of cross-chain settlement in `onAccept`: [2](#0-1) 

and as the refund step after a validated cancellation GET response: [3](#0-2) 

Orders can escrow multiple distinct ERC20 tokens as inputs (`order.inputs`), and the same `WithdrawalRequest.tokens` array is used to release/refund all of them together in one call. Because `safeTransfer` reverts on failure and there is no per-token isolation (no try/catch, no partial release, no pull-based claim), a single blacklisted transfer poisons the entire batch. Both `onAccept` and `onGetResponse` are one-shot, protocol-driven message deliveries authenticated by Hyperbridge/relayer proofs — there is no retry path that omits the blacklisted token or delivers to an alternate address.

### Impact Explanation
For a cross-chain order with multiple input tokens, if the solver (redeem case) or user (refund case) is blacklisted on just one of the escrowed ERC20s, none of the escrowed tokens — including fully compliant ones — can ever be released through this path, permanently freezing the entire multi-asset escrow. This is a direct freezing-of-funds condition reachable by any user/solver combination that happens to include a blacklistable token among the order's inputs, without any malicious actor required.

### Likelihood Explanation
Likelihood is proportional to adoption of blacklist-capable stablecoins (USDT, and various centralized-issuer tokens) as intent-gateway input assets, and to beneficiaries being sanctioned/blacklisted addresses. Multi-token input orders are a supported, documented feature of the Intent Gateway (`order.inputs` accepts arbitrary `TokenInfo[]`), so this is a realistic configuration, not an edge case requiring an unusual setup.

### Recommendation
Change `_withdraw` to isolate per-token transfer failures, e.g. wrap each `safeTransfer` in a low-level call and catch failures, crediting failed amounts to a separate pull-based claim mapping keyed by `(beneficiary, token)` rather than reverting the whole batch. Alternatively, split settlement into a pull model where `onAccept`/`onGetResponse` only update escrow accounting and a separate `claim(token)` function lets the beneficiary withdraw each token independently.

### Proof of Concept
1. User places a cross-chain order with `order.inputs = [USDC: 1000, USDT: 1000]` on the source chain.
2. Solver fills the order on the destination chain; `_fillCrossChain` dispatches a `RedeemEscrow` message back to source.
3. Before the message is delivered, the solver's address becomes blacklisted on USDT (e.g., via Tether's centralized blacklist).
4. Relayer delivers the `RedeemEscrow` proof; `onAccept` calls `_withdraw(body, false, true)`.
5. The loop in `_withdraw` reaches the USDT transfer via `IERC20(token).safeTransfer(beneficiary, amount)` [4](#0-3) , which reverts because the solver is blacklisted.
6. The entire `onAccept` transaction reverts, so the solver also fails to receive the 1000 USDC that was otherwise fully claimable — the escrow for both tokens remains permanently locked in the gateway contract with no alternative retrieval path.
