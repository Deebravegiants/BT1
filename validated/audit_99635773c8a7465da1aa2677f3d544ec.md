### Title
Unvalidated empty `body` in `onAccept` causes out-of-bounds revert, permanently freezing undeliverable requests and griefing batched deliveries - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
Several EVM-side `IIsmpModule.onAccept` implementations decode a leading "request kind" discriminant byte from `incoming.request.body` via `uint8(incoming.request.body[0])` without first checking `body.length > 0`. Since `EvmHost.dispatch` permissionlessly accepts an empty `body` (confirmed by test fixtures dispatching `body: new bytes(0)`), and delivery calls `onAccept` directly with no `try/catch` isolation, a crafted zero-length-body POST request addressed to one of these modules causes a Solidity out-of-bounds panic that reverts the entire delivery transaction — analogous to vLLM's empty-prompt crash, but here manifesting as an un-relayable message / griefed batch rather than a full process crash.

### Finding Description
`IntentGatewayV2.onAccept` reads the request-kind discriminant unconditionally: [1](#0-0) 

The same unguarded pattern exists in the sibling intents module and in the paymaster governance handler: [2](#0-1) [3](#0-2) 

`EvmHost.dispatch` does not enforce a minimum body length — this is explicitly exercised in the test-suite with `body: new bytes(0)`: [4](#0-3) 

Delivery is performed by `HandlerV2.handlePostRequests`, which loops over the batch's leaves and calls `host.dispatchIncoming(leaf.request, _msgSender())` for each, with no isolation between individual requests: [5](#0-4) 

`dispatchIncoming` invokes the target module's `onAccept` directly (unlike, e.g., `HyperbridgeLzEndpoint`, which deliberately wraps its external delivery call in `try/catch` specifically to prevent one payload's revert from bricking the channel): [6](#0-5) 

Because dispatching a POST request is permissionless (any payer, any `to`, any `body`), an attacker can dispatch a request whose `dest` is a chain hosting `IntentGatewayV2`/`ExtrinsicIntents`/`SimplexPaymaster`, whose `to` is that contract's address, and whose `body` is empty (`bytes(0)`), with `timeout = 0` (never expires). When a relayer submits the corresponding `PostRequestMessage` for delivery, `body[0]` indexing on the empty `bytes` triggers a Solidity `Panic(0x32)` (array out-of-bounds), reverting the whole `handlePostRequests` call.

### Impact Explanation
- The malformed request can never be delivered — `onAccept` will revert on every delivery attempt for as long as the message exists.
- With `timeout = 0` the request never times out, so any fee attached to it (via `fee`/`fundRequest`) is permanently locked with no code path to reclaim it, and the request commitment is stuck forever un-fulfilled — a concrete freezing-of-funds / undeliverable-route condition per the finding criteria.
- Because `handlePostRequests` verifies a Merkle multiproof and processes all included leaves in a single transaction with no per-leaf isolation, a relayer that unknowingly batches the malicious leaf together with legitimate leaves will have the entire batch revert, denying delivery of the honest requests in that batch as well (griefing).

### Likelihood Explanation
High: dispatching an ISMP POST request with an empty body and arbitrary `to`/`dest` requires no special privilege — any account can call `EvmHost.dispatch` (paying only the standard relayer fee/gas, which can be zero for self-relay). The vulnerable `onAccept` code path is on the primary message-delivery route (`HandlerV2.handlePostRequests` → `EvmHost.dispatchIncoming` → module `onAccept`), which is exactly the reachable surface this scan targets.

### Recommendation
Add an explicit length guard at the top of each affected `onAccept` (and any other module decoding a discriminant byte from `request.body`), e.g. `if (incoming.request.body.length == 0) revert InvalidBody();`, returning a clean revert reason instead of an index-out-of-bounds panic. Additionally, consider isolating per-leaf delivery failures in `HandlerV2.handlePostRequests` (e.g., a `try/catch` around `host.dispatchIncoming`, mirroring the pattern already used in `HyperbridgeLzEndpoint.onAccept`) so that one malformed/malicious request cannot revert an entire batch of otherwise-valid deliveries.

### Proof of Concept
1. Attacker calls `EvmHost.dispatch(DispatchPost{ dest: <chain hosting IntentGatewayV2>, to: abi.encodePacked(intentGatewayV2Address), body: new bytes(0), timeout: 0, fee: 0, payer: attacker })` on the source chain — permitted, as shown by `evm/tests/foundry/EvmHostTest.sol` using `body: new bytes(0)` in the same dispatch call shape.
2. A relayer observes the commitment and, once finalized, submits `HandlerV2.handlePostRequests` with a `PostRequestMessage` whose `requests` array includes this leaf (possibly batched with other, unrelated legitimate leaves under one Merkle multiproof).
3. Inside the loop at `HandlerV2.sol:204-209`, `host.dispatchIncoming(leaf.request, _msgSender())` calls `IntentGatewayV2.onAccept`, which executes `uint8(incoming.request.body[0])` on a zero-length `bytes` — Solidity reverts with `Panic(0x32)`.
4. The revert propagates uncaught through `dispatchIncoming` and `handlePostRequests`, reverting the whole transaction; none of the batch's requests (including honest ones) get delivered, and the malicious request's commitment (with `timeout = 0`) remains permanently stuck, undeliverable and unrefundable.

Note: I was not able to independently verify from the index whether `EvmHost.dispatchIncoming`'s internal implementation wraps the module call in any additional safety mechanism beyond what's shown, since the full body of `dispatchIncoming` in `EvmHost.sol` was not fully retrieved in this session — a Devin session with full repository access should confirm the exact call-site behavior before treating this as fully conclusive.
