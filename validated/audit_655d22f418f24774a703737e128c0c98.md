### Title
Seller can frontrun a position-NFT purchase to strip collateral/debt before `transfer_from` executes - (File: contracts/position-nft/README.md)

### Summary
The class from the reference report — a counterparty settles against a parameter the target can still change ("owner allocates against a bid the bidder can raise") — maps directly onto XOXNO Lending's position NFT sale flow. A marketplace or escrow buys `token_id == account_id` via `approve`/`transfer_from`, pricing the position on its collateral and debt. The seller can frontrun the purchase transaction with `borrow` and `withdraw` (both owner-gated, fully unprivileged for the owner), extracting nearly all realizable value while leaving the NFT approval intact. The buyer receives an account at HF ≈ 1 with maximal debt — worth a fraction of what was paid.

### Finding Description
A lending position is a transferable NFT: `account_id == token_id`, "transferring the token transfers the whole position ... collateral and debt both move with the token" [1](#0-0) . `approve`/`approve_for_all`/`transfer_from` are the stock OpenZeppelin methods, and the docs explicitly note that approval "hands over the whole account" [2](#0-1) . The per-token approval is stored in `NFTStorageKey::Approval(token_id)` in the NFT contract and is keyed only to the token — nothing in a controller `borrow` or `withdraw` call reads or clears it [3](#0-2) .

The post-action risk gate on `borrow`/`withdraw` only requires LTV-weighted collateral to cover debt and `HF >= 1` [4](#0-3) . So a seller who has approved a marketplace retains full authority to call `borrow(caller=seller, account_id, borrows, to=seller)` up to the LTV limit — pulling debt-token cash out — right up until the buyer's transaction executes. This is structurally identical to the RFP bid: the buyer ("owner/allocator") has agreed a price for the position's state, but the seller ("recipient") can still modify that state until the settlement lands.

The in-scope whitelist includes `position-nft transfer/approve` and `borrow`/`withdraw`, and the attacker is the position owner — a single unprivileged address.

### Impact Explanation
Theft of user funds. The buyer pays the agreed price for a position whose economic value has been drained: collateral is converted into debt at the maximum LTV, and the seller keeps the borrowed tokens. The purchased NFT controls an account at HF ≈ 1 that will be liquidated for a further bonus loss. Analogous to "recipient receives a bigger payment than agreed": the seller receives a bigger payout (sale price + extracted borrow) than the position's state justified at agreement time.

### Likelihood Explanation
Requires only that position NFTs are sold OTC or on marketplaces — which the protocol explicitly anticipates ("wallets, indexers, and marketplaces can read and move it" [5](#0-4) ). A marketplace executing `transfer_from` inside a swap transaction creates a deterministic frontrunning window; Stellar transaction submission gives the seller the same ordering opportunity as in the RFP report. No privileged role, oracle manipulation, or leaked key is needed. Medium likelihood: it depends on secondary-market trading of positions, but the exploitation itself is trivial and cost-free to attempt.

### Recommendation
A buyer-side mitigation cannot be enforced inside `transfer`, but the protocol can shrink the window:
- Provide a controller-side "quiesce" flag the owner can set when listing (e.g., a storage flag that blocks `borrow`/`withdraw`/strategy calls while set and is cleared atomically on NFT transfer), so a seller can credibly commit that the account cannot change before settlement — the NFT contract can clear it inside `transfer`/`transfer_from`.
- Document for integrators that a purchase transaction must bundle a solvency/size check: read `get_health_factor`/`get_account_positions` and assert expected collateral and debt inside the same transaction as `transfer_from`, reverting if either changed — the transaction-layer equivalent of "pass the agreed payment as an argument".

### Proof of Concept
1. Alice owns `account_id = N` with $10,000 USDC collateral and no debt. She lists NFT `N` for $9,000 on a marketplace and calls `approve(seller=alice, marketplace, N, live_until_ledger)` [6](#0-5) .
2. Bob submits the purchase transaction: pays $9,000 to Alice via the marketplace, which calls `transfer_from(marketplace, alice, bob, N)`.
3. Alice sees Bob's transaction and submits `borrow(alice, N, [(USDC, max_ltv_amount)], to=alice)`. With e.g. 80% LTV she withdraws ~$8,000; the post-call gate passes because LTV-weighted collateral still covers debt with `HF >= 1` [7](#0-6) .
4. Bob's transaction executes (ordering him after Alice's borrow, or Alice self-sequences via a sandwich): the approval is unaffected by the borrow, so `transfer_from` succeeds. Bob now owns an account holding $10,000 collateral against ~$8,000 debt — net ~$2,000, not $10,000. Alice netted $9,000 + ~$8,000 for a position worth $10,000.
5. Optionally Alice's borrow pushes HF just above 1; a small price move or accrued interest makes the account liquidatable and Bob loses the residual equity to the liquidation bonus.
