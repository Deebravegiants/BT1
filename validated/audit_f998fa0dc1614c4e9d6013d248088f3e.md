### Title
Withdrawal status/tx-hash misattribution in batch withdrawals sharing the same `assetId` — ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal()` and the analogous `findMatchingWithdrawal()` helper in `internal-utils` resolve the on-chain outcome of a specific withdrawal leg by matching PoA-relay API results using **only the asset identifier** (`assetId` / `near_token_id`), ignoring `destinationAddress` and `amount`. When a batch withdrawal contains two or more legs of the same token (e.g., same asset sent to two different destination addresses, or two different amounts), the matcher returns the first API entry whose asset matches, which may belong to a *different* leg of the batch. The status and `txHash` reported to the caller can therefore describe the wrong withdrawal.

### Finding Description
`describeWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` (lines 313-344) does: [1](#0-0) 

```
const withdrawal = findMatchingWithdrawal(
  response.withdrawals,
  args.withdrawalParams.assetId,
);
...
if (withdrawal.status === "COMPLETED") {
  return { status: "completed", txHash: withdrawal.data.transfer_tx_hash };
}
```

The equivalent helper used by `waitForWithdrawalCompletion` in `internal-utils` is explicit about the limitation in its own comment: [2](#0-1) 

```
/**
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 */
function findMatchingWithdrawal(withdrawals, criteria) {
  return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === criteria.assetId);
}
```

The SDK explicitly supports batch withdrawals via `signAndSendWithdrawalIntent`/`processWithdrawal` with an array of `WithdrawalParams`, each carrying its own `destinationAddress` and `amount` [3](#0-2) . Nothing in the batch API prevents two entries with the identical `assetId` but different `destinationAddress`/`amount` (e.g., withdrawing the same USDC token to two different user addresses in one intent). Because the matcher keys only on `assetId`, `describeWithdrawal`/`waitForWithdrawalCompletion` cannot distinguish between the two legs and will attach the first matching relay entry's status/`txHash` to both `withdrawalParams[i]` promises.

The equality that should hold is: *the (status, txHash) reported for withdrawal i must correspond to the exact (assetId, amount, destinationAddress) tuple of withdrawal i's on-chain leg*. The current code only checks `assetId`, breaking this equality whenever `assetId` collides across legs of the same batch.

### Impact Explanation
If a caller/integrator processes a batch of two same-asset withdrawals to different addresses, the SDK can report withdrawal A as `"completed"` with the `txHash` that actually belongs to withdrawal B, while withdrawal B is reported `"pending"` (or vice versa). An integrator relying on `waitForWithdrawalCompletion`/`describeWithdrawal` to trigger downstream actions (e.g., marking a user's withdrawal as settled, releasing custody, crediting an off-chain ledger) could credit/mark-complete the wrong leg, or mark a still-pending withdrawal as done while the actually-completed leg is left unresolved. This matches the "status or hash misreport making an integrator credit or refund twice" High-impact category.

### Likelihood Explanation
Requires a batch of ≥2 withdrawals with an identical `assetId` (same token) but different `destinationAddress`/`amount` — a legitimate, unprivileged usage pattern already exposed and encouraged by the public SDK (`processWithdrawal`/`signAndSendWithdrawalIntent` batch mode). No malicious relayer/bridge behavior is required; it triggers purely from normal use whenever the PoA relay returns multiple entries for the same token before all legs are indexed.

### Recommendation
Extend `findMatchingWithdrawal` (in both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) to disambiguate using additional fields returned by the relay (e.g., `data.address`/`destinationAddress` and `data.amount`), not just the asset identifier. Where the relay response cannot be deterministically correlated to a specific batch index (e.g., truly identical amount+destination+asset), the SDK should either refuse silently-ambiguous matches or explicitly document/enforce that batches cannot contain indistinguishable legs.

### Proof of Concept
1. Call `sdk.processWithdrawal({ withdrawalParams: [ {assetId:"nep141:usdc.omft.near", amount:100n, destinationAddress:"0xAAA"}, {assetId:"nep141:usdc.omft.near", amount:200n, destinationAddress:"0xBBB"} ] })`.
2. Suppose only the `0xBBB` leg has settled on-chain (`COMPLETED` in the PoA relay), while `0xAAA` is still `PENDING`.
3. `PoaBridge.describeWithdrawal()`/`waitForWithdrawalCompletion` is called once per leg; because `findMatchingWithdrawal` matches solely on `nep141:usdc.omft.near`, both calls resolve to the same (first found) `COMPLETED` entry with `transfer_tx_hash` for the `0xBBB` transfer.
4. The caller's promise for the `0xAAA` withdrawal resolves as `"completed"` with the `0xBBB` transaction hash, even though `0xAAA` has not settled — demonstrated by the existing test `"matches withdrawal by criteria when multiple withdrawals exist"` in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.test.ts` (lines 141-175), which only verifies matching across *different* assets, not the same-asset multi-leg collision case described here.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
