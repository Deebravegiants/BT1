### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` validates the authenticity of an inbound webhook using an HMAC that is computed over the raw request body only, while the shop identity (`shop-domain` header) used to dispatch and process the webhook is never included in the signed material. Any party who can obtain one genuine, correctly-signed webhook body (e.g., by installing the app on their own store) can replay that exact body to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. The HMAC check passes because it never covers that header, so the handler processes the payload as if it came from the spoofed shop — an identity-binding break directly analogous to the referenced report's pattern of "a value that is acted upon but never covered by the integrity/consistency check."

### Finding Description
`Request#to_signable_string` — the only material fed into HMAC validation — returns solely the raw body: [1](#0-0) 

`Request#shop` is read from an unauthenticated, attacker-controlled HTTP header and is never mixed into the signable string: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e. only the body: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches the handler using `request.shop` taken straight from the header, with no cross-check that this shop matches anything tied to the signature: [4](#0-3) 

Because the app's `client_secret` (the HMAC key) is shared across every shop that installs the app, a genuine webhook obtained from *any* shop — including one the attacker fully controls (e.g., their own free/dev store) — produces a `(raw_body, hmac)` pair that remains valid HMAC-wise for that secret regardless of which shop domain is claimed in the header. The equality the code relies on is:
`hmac_valid(body) == true` implies `shop_header == originating_shop`
but the actual guarantee provided by the code is only:
`hmac_valid(body) == true` implies `body` was signed by *some* holder of `client_secret`, which for a multi-tenant app is any installed shop, not specifically `shop_header`.

### Impact Explanation
This allows a low-privilege attacker (any user who can install the app on a shop they control, or who otherwise obtains one valid webhook delivery) to make forged, attacker-chosen webhook payloads be processed by the app under the identity of any other tenant, since `request.shop` — the value handlers use to key off the affected tenant/session — is fully attacker-controlled and unauthenticated relative to the signature. This is a cross-tenant identity binding break (Critical: cross-tenant access) — the handler acts on data believed to originate from shop B while it was actually forged/replayed by an attacker associated with shop A.

### Likelihood Explanation
Exploitability requires: (1) an internet-reachable webhook endpoint (a standard, expected deployment for this gem), and (2) possession of one genuine `(body, hmac)` pair signed with the app's `client_secret`, which is trivially obtainable by any user by installing the app on any store (including their own) and capturing a real webhook delivery. No access token, leaked secret, or privileged account is required — only the shared, non-tenant-specific `client_secret` used identically for every shop's webhooks, which is precisely the condition under which the header-vs-signature binding fails.

### Recommendation
Bind the shop identity into what's verified before it is trusted for dispatch — e.g., verify that `request.shop` corresponds to a shop with an active, known session/registration in the consuming app before invoking handlers, or require host applications to cross-check `shop-domain` against their own installed-shop records (this can also be called out explicitly in `docs/usage/webhooks.md`). Note that Shopify's own webhook signing scheme does not include the shop header in the HMAC by design, so any fix must be enforced at the "isolate what identifies the tenant" layer (session/store lookup) rather than by modifying the signable string, since the gem cannot change Shopify's server-side signing behavior.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and lets it deliver a real webhook, e.g. `orders/create`, capturing the raw body `B` and the resulting `X-Shopify-Hmac-Sha256` header `H` (valid because `H = HMAC(client_secret, B)`).
2. Attacker POSTs to the app's public webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), `X-Shopify-Topic: orders/create` (unchanged), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers/body, `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` — see [5](#0-4) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the host application to process attacker-supplied data attributed to a shop the attacker does not control.
