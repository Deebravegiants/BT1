### Title
Webhook HMAC does not bind to the `shop-domain` header, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` (used by `Utils::HmacValidator.validate`) signs only the raw HTTP body of a webhook request. The `shop-domain` header — which the registry later treats as the authoritative tenant identifier for the event — is never included in the signed material, so it can be swapped without invalidating the HMAC.

### Finding Description
`Webhooks::Registry.process` validates a webhook purely by checking `Utils::HmacValidator.validate(request)` and, once that passes, trusts `request.shop` (sourced from the `shopify-shop-domain`/`x-shopify-shop-domain` header) as the tenant the event belongs to: [1](#0-0) 

The HMAC check, however, is computed only over the raw body: [2](#0-1) 

`hmac` and `shop` are both read from independent, unauthenticated headers (`shopify-hmac-sha256` and `shopify-shop-domain`), while `to_signable_string` returns only `@raw_body`: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `shop header used by the app == shop bound into the HMAC-verified payload`. Because the `shop` header is not part of `to_signable_string`, this equality is never enforced — a request with a valid `(body, hmac)` pair and an arbitrary `shop-domain` header will pass `HmacValidator.validate` and be dispatched to the app's handler as if it came from that arbitrary shop.

### Impact Explanation
Any user who can install the app on their own store (an unprivileged merchant with no access to the victim's data or the app's `client_secret`) legitimately receives real webhook deliveries with valid `(body, hmac)` pairs for their own shop. By replaying that exact body/HMAC pair to the app's public webhook endpoint while substituting the `shop-domain` header with a victim shop's domain, the attacker can make the app process/attribute the event as if it originated from the victim tenant. Since `WebhookMetadata.shop` is the only tenant signal handlers receive, downstream app logic keyed on `shop` (e.g., billing state changes, data synchronization, `customers/redact`/`shop/redact` compliance actions, order/product state updates) can be triggered for a shop the attacker does not control — a cross-tenant integrity/confusion issue.

### Likelihood Explanation
The webhook endpoint is a public, internet-reachable HTTP endpoint by design (it must be, so Shopify can deliver events to it). Obtaining a legitimate `(body, hmac)` pair only requires installing the app on any store — no privileged credentials, `api_secret_key`, or access tokens are needed. Replaying it with a modified header is trivial for anyone who can send raw HTTP requests.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the HMAC-verified signable string, or otherwise cryptographically bind the header values to the signed body (e.g., by validating that the shop domain associated with a stored session/registration matches the one presented, rather than trusting the header outright). At minimum, document that consumers must not rely on `WebhookMetadata#shop` for tenant identification without independent verification (e.g., cross-checking against the session/shop that the webhook subscription was registered for).

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker-shop.myshopify.com`; capture a genuine webhook delivery: raw body `B` and header `shopify-hmac-sha256: H` (valid for the app's `api_secret_key`).
2. Send a POST to the app's webhook endpoint with the same body `B` and the same `shopify-hmac-sha256: H`, but set `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request where `shop == "victim-shop.myshopify.com"`.
4. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `@raw_body` only (`to_signable_string` returns `@raw_body`), which still matches `H`, so validation succeeds.
5. `Registry.process` dispatches `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` to the registered handler, which now believes the event came from `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
