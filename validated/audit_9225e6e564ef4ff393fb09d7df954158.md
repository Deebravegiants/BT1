### Title
Overflow in accrued market-value calculation permanently freezes a saturated high-utilization market - (File: `common/src/rates/index.rs`)

### Summary
`update_supply_index` and supplier-reward calculation multiply stored scaled balances by the current index before applying the index ceiling. A sufficiently large market can therefore cross the `i128` value limit while the borrow index is still below `MAX_BORROW_INDEX_RAY`, causing every subsequent market operation to panic during mandatory accrual. [1](#0-0) [2](#0-1) 

### Finding Description
The pool stores `supplied` and `borrowed` as index-scaled `Ray` values, while accrual reconstructs their full RAY value with multiplication. `update_supply_index` computes `supplied.mul(old_index)` before clamping the resulting index, and `calculate_supplier_rewards` likewise computes both old and new total debt with `borrowed.mul(index)`. [1](#0-0) [2](#0-1) 

The resulting multiplication panics on `i128` overflow rather than saturating or rejecting only the operation that created the excess. The configured borrow-index cap does not prevent this condition because it is checked only after the multiplication and after total-value arithmetic has already overflowed. [3](#0-2) [4](#0-3) 

Every pool mutation loads the market through `synced_market`, which runs `global_sync` before performing the requested operation. Consequently, once the accrued state reaches the overflowing domain, `supply`, `borrow`, `withdraw`, `repay`, `flash_loan`, `seize_positions`, `net_settle`, `recapitalize`, and `claim_revenue` all revert before their own logic can reduce the scaled balance. [5](#0-4) [6](#0-5) 

The repository’s own long-horizon test demonstrates the exact failure: a one-billion-token, 18-decimal market at 98% utilization fails `update_indexes` with `MATH_OVERFLOW` while the borrow index remains below `MAX_BORROW_INDEX_RAY`, after which both withdrawal and repayment fail with the same overflow. [7](#0-6) 

### Impact Explanation
This is permanent freezing of all funds and debt operations in the affected market. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, and `recapitalize` cannot repair the market because each path performs the same failing accrual first. [5](#0-4) [8](#0-7) 

Unlike a temporary oracle or liquidity rejection, this panic arises from persisted `supplied`, `borrowed`, and index values. Because the panic occurs before any operation can write a lower scaled balance, the market cannot transition back below the overflowing domain through normal unprivileged or owner-mediated pool entrypoints. [9](#0-8) [5](#0-4) 

### Likelihood Explanation
The likelihood is limited by the required market scale: the demonstrated setup uses one billion whole 18-decimal tokens, 98% utilization, and multiple years of high-rate accrual. It does not depend on malformed calls or privileged mutation, but it does require market caps and token supply to permit that scale and sufficient attacker or market capital to establish the state. [10](#0-9) 

The spoke-cap check compares the next scaled balance against the configured cap, but it does not reserve headroom for future index multiplication. A cap admitted under the documented token/RAY domain can therefore remain individually valid while still permitting a later market-value overflow. [11](#0-10) [12](#0-11) 

### Recommendation
Bound every stored scaled market total to the maximum value that remains safe at `MAX_BORROW_INDEX_RAY` and `MAX_SUPPLY_INDEX_RAY`, and enforce that bound in `supply`, `borrow`, `create_strategy`, revenue accrual, and bad-debt paths before increasing `supplied` or `borrowed`. [1](#0-0) [11](#0-10) 

Accrual should also use checked total-value calculation that reports a recoverable cap-specific error or safely clamps the affected index before computing dependent totals. Do not solve this by silently saturating debt value alone, because understated liabilities would break backing and liquidation accounting; the safe fix is an explicit scaled-balance ceiling and tests proving that repayments, withdrawals, liquidations, and `update_indexes` remain executable at the ceiling. [2](#0-1) [4](#0-3) 

### Proof of Concept
An unprivileged user creates or uses a listed 18-decimal market with a steep borrow-rate curve and supplies `1_000_000_000 * 10^18` base units through `controller.supply(caller, 0, spoke_id, [(BIG18, amount)])`. A sufficiently collateralized unprivileged account then calls `controller.borrow(caller, account_id, [(BIG18, 980_000_000 * 10^18)], to)` to leave the market at 98% utilization. [13](#0-12) [10](#0-9) 

As ledger time advances, a call to the controller’s `update_indexes` path or any market operation runs `interest::global_sync`, which eventually multiplies the persisted scaled balance by an index large enough to overflow `i128`. [9](#0-8) [1](#0-0) 

The repository reproduces the result directly: `try_update_indexes_for(["BIG18"])` returns `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`, and subsequent `withdraw(BOB, BIG18, 1)` and `repay(ALICE, BIG18, 1.0)` attempts return the same overflow. [14](#0-13)

```rust
pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
```

```rust
/// Converts an asset-unit `cap` to a scaled `Ray` value, rounding down.
///
/// The division saturates at `i128::MAX` instead of panicking, so the cap check
/// fails open rather than trapping an entry path. The asset-to-RAY
/// rescale still panics on overflow; listings validate caps with
/// [`crate::validation::require_cap_within_asset_domain`]. Position accounting
/// uses [`calculate_scaled_supply`] and [`calculate_scaled_borrow`], which panic
/// on overflow.
pub fn calculate_scaled_cap(env: &Env, cap: i128, decimals: u32, index: Ray) -> Ray {
    Ray::from(fp_core::mul_div_floor_saturating(
        env,
        Ray::from_asset(env, cap, decimals).raw(),
        RAY,
        index.raw(),
    ))
}
```

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```
