Based on the exploration, I found a concrete equality-break in the Emporium relay-fee calculation, not an SSRF-style URL/data-validation issue (no off-chain URL fetching exists in this repo).

### Title
Emporium relay fee bypass via self-signed wallet path skips `variableRate` fee - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.payRelayFees` computes the relay/protocol fee differently depending on whether the caller routes the withdrawal through a signed `HinkalWallet` (`stack.signerAddress != address(0)`) or through the stateless Emporium balance path (`stack.signerAddress == address(0)`). Only the stateless path applies the `variableRate` component of `FeeStructure`; the signer/wallet path silently truncates the fee to `flatFee` only.

### Finding Description
`payRelayFees` branches on `signerAddress`: [1](#0-0) 

When `signerAddress == address(0)`, the fee is `calculateRelayFee(sumAbs, flatFee, variableRate)`, which combines both fee components. When `signerAddress != address(0)` (i.e., the caller supplies any valid `EmporiumStack` with a self-controlled `signerAddress`/wallet and a matching ECDSA signature they produced themselves, per `verifyWallet`), `relayFee` is simply set to `flatFee`, discarding `variableRate` entirely: [2](#0-1) 

`stack.signerAddress` and the entire `EmporiumStack` come from `circomData.externalActionData.externalActionMetadata`, which is user/prover-supplied and only bound by `calldataHash` — nothing in `verifyWallet` (`EmporiumUpgradeable.sol:302-349`) or `runAction` requires `signerAddress` to correspond to a wallet that already holds pre-existing balance or that the "stateful" op path (`invokeWallet`) is actually used. An unprivileged EOA can:
1. Deploy/own a `HinkalWallet` for itself (a normal, unprivileged action any user can take for their own funds).
2. Submit a `transact` call whose `CircomData.externalActionData.externalActionMetadata` encodes an `EmporiumStack` with `signerAddress = <their own wallet>`, a valid self-signature (since they hold the wallet's key), and `ops` that do nothing meaningful (e.g., an empty/no-op `invokeWallet` operation, or one that simply exercises `CASE 1` trivially).
3. Because `signerAddress != address(0)`, `payRelayFees` computes `relayFee = flatFee` only, skipping `variableRate` entirely — even though the withdrawal is functionally identical to the stateless path in terms of value moved out of the shielded pool.

This breaks the intended fee equality: the protocol's/relay's expected fee income for a withdrawal of amount `sumAbs` should be `flatFee + variableRate * (sumAbs - flatFee)` (as implemented in `calculateRelayFee`, mirrored in `_internalTransact`, `contracts/Hinkal.sol:189-224`), but the signer-path silently drops the variable-rate component.

### Impact Explanation
This is a **High** impact issue per the scan's own severity bands: "theft ... of protocol/relay fees." Any unprivileged user routing withdrawals through the Emporium's signed-wallet code path underpays the relay/protocol by the entire `variableRate` component on every such withdrawal, for arbitrarily large `sumAbs`. This is a systemic fee-avoidance vector reachable by any EOA with no special privileges — no admin, relay, or another user's key is required.

### Likelihood Explanation
High likelihood: any user who wants to reduce fees needs only to deploy their own `HinkalWallet` (unprivileged, one-time) and construct an `EmporiumStack` with `signerAddress` set and a self-signature. No race condition, no dependence on relayer or admin behavior, and repeatable on every transaction.

### Recommendation
Apply `variableRate` consistently regardless of the `signerAddress` branch — i.e., always call `_hinkalHelper.calculateRelayFee(sumAbs, flatFee, feeStructure.variableRate)` in `payRelayFees`, or otherwise ensure the fee formula does not depend on which internal execution path (`stateless` vs `signed wallet`) a user selects for an economically equivalent withdrawal.

### Proof of Concept
1. User has UTXOs proving ownership of `amount = 1_000_000` of token `T` inside the shielded pool, and calls `Hinkal.transact` with `externalActionData.externalActionId` pointing to `EmporiumUpgradeable`, with `amountChanges[T] = -1_000_000` (a withdrawal), `feeStructure = {feeToken: T, flatFee: 100, variableRate: 500 (5%)}`.
2. User deploys their own `HinkalWallet` (with `emporium` set to the `EmporiumUpgradeable` address) — fully unprivileged.
3. User crafts `externalActionMetadata = abi.encode(EmporiumStack({v,r,s: self-signed EIP-712 sig, signerAddress: <own wallet>, ops: [ ... a trivial or self no-op operation ... ], maxFee: <>=flatFee>, deadline: <future>}))`, matching `calldataHash`/`signedMessageHash` so the ZK proof remains valid.
4. `Hinkal.transact` → `_externalTransact` sends the withdrawn `1_000_000 - <fees>` tokens to `EmporiumUpgradeable`; `runAction` executes; because `stack.signerAddress != address(0)`, `payRelayFees` charges `relayFee = flatFee = 100` instead of `100 + 5%*(999,900) ≈ 50,095`.
5. Compare to the same withdrawal submitted with `signerAddress == address(0)` (stateless path): the relay/protocol receives the full `calculateRelayFee` amount. The discrepancy (~49,995 tokens in this example) is fee revenue the protocol/relay is entitled to but never receives, purely due to the caller's choice of code path — a concrete, repeatable theft of protocol/relay fees by an unprivileged user.
