### Title
Missing shop-domain sanitization in `TokenExchange.exchange_token` allows `client_secret` to be sent to an unvalidated host derived from the JWT `dest` claim - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` extracts the shop host directly from the session token's `dest` claim and uses it, unvalidated, to build the HTTP client that POSTs the app's `client_id`/`client_secret` to `https://{dest_shop}/admin/oauth/access_token`. Every sibling credential-exchange method in the same module/family sanitizes the shop host with `Utils::ShopValidator.sanitize!` before doing the same thing, but `exchange_token` does not.

### Finding Description
The binding that should hold is: `host_that_receives(client_id, client_secret) == validated_myshopify_host`.

In `exchange_token`:
```ruby
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = jwt_payload.shop          # lib/shopify_api/auth/token_exchange.rb:40-41
...
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)   # :51 -- no ShopValidator call
body = { client_id: ..., client_secret: Context.api_secret_key, ... }
client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")  # :65
```
`JwtPayload#shop` (`lib/shopify_api/auth/jwt_payload.rb:47-50`) is simply `@dest.gsub("https://", "")` with **no domain-format check** — `JwtPayload#initialize` only verifies the signature and that `aud == Context.api_key` (`lib/shopify_api/auth/jwt_payload.rb:43-44`); it never checks that `iss`/`dest` is a `*.myshopify.com` (or other trusted) domain. `HttpClient#initialize` then builds `@base_uri = "https://#{api_host || session.shop}"` (`lib/shopify_api/clients/http_client.rb:16-18`) and the `client_secret` is sent to that host as part of the POST body.

By contrast, every other method in the OAuth/token family — `TokenExchange.migrate_to_expiring_token` (`token_exchange.rb:103-104`), `RefreshToken.refresh_access_token` (`refresh_token.rb:24-25`), and `ClientCredentials.client_credentials` (`client_credentials.rb:25-26`) — explicitly calls `validated_shop = Utils::ShopValidator.sanitize!(shop)` before constructing the `Session`/`HttpClient` used to send the same `client_secret`-bearing request. `exchange_token` is the sole outlier that skips this validation, even though `docs/usage/oauth.md:70-77` documents it as the *recommended* flow ("Its `dest` claim determines which shop receives the token exchange request").

### Impact Explanation
If the value of the `dest` claim were ever not constrained to a genuine Shopify-controlled domain (the gem itself places no such constraint on it, unlike the sibling flows), the app's `client_id` and `client_secret` would be transmitted to that host. This matches the "SSRF with the app's credentials / credential leakage" impact category, since it is the request that carries the app's `client_secret` to a host chosen from unvalidated input, exactly analogous to the report's root cause: a critical downstream operation (mint/liquidity math there; credential POST here) proceeds on a value that was never validated for the invariant the rest of the codebase enforces elsewhere.

### Likelihood Explanation
Exploitability is dependent on whether an attacker can ever get a validly-HS256-signed session token (signed with the shared `api_secret_key`) whose `dest` claim is not restricted to a real Shopify domain — the gem does not enforce that restriction, and unlike the other three flows it deliberately omits the `ShopValidator.sanitize!` call that exists specifically to make this restriction hold. This is a genuine, provable code-level inconsistency (present in the file today) rather than a supposition, but full exploitability by an unauthenticated/unprivileged party additionally depends on how the host application obtains/passes `session_token`, which is outside this gem.

### Recommendation
In `lib/shopify_api/auth/token_exchange.rb#exchange_token`, sanitize `dest_shop` the same way the other credential-exchange flows do:
```ruby
dest_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)
```
so the host that receives `client_id`/`client_secret` is always constrained to `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`, matching `migrate_to_expiring_token`, `RefreshToken.refresh_access_token`, and `ClientCredentials.client_credentials`.
