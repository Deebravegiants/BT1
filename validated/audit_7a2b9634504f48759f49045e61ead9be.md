### Title
Webhook `shop-domain` header is trusted as tenant identity without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC only over the raw request body, while the `shop-domain` header — which is handed to host-app webhook handlers as the authoritative tenant identifier — is read directly from the (unauthenticated) HTTP header and never enters the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` simply reads the `shopify-shop-domain`/`x-shopify-shop-domain` header with no relation to the signed bytes [2](#0-1) . `Registry.process` verifies the HMAC via `Utils::HmacValidator.validate(request)`, which calls `validate_signature` comparing `compute_signature(verifiable_query.to_signable_string, secret)` against the received HMAC [3](#0-2)  — i.e., the equality check only binds `hmac == HMAC(body, secret)`, never `hmac == HMAC(body ∥ shop, secret)`. After that check passes, `Registry.process` forwards `request.shop` unauthenticated straight to the handler as `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [4](#0-3) . Because the app's `client_secret`/`api_secret_key` is a single shared value across every shop that installs the app, any body+HMAC pair that is valid for one shop's webhook delivery is equally valid HMAC-wise for a request claiming to be from any other shop — the signature carries no shop binding at all.

### Impact Explanation
Host applications built on this gem are documented to key their tenant records off `WebhookMetadata#shop` (the value returned by `Registry.process`). Since the HMAC never binds the request to a specific shop, a party that can obtain one legitimate (body, HMAC) pair — for example from their own shop's genuine webhook deliveries, or any publicly observable mandatory-compliance webhook — can resend the identical body/HMAC to the app's webhook endpoint with a different `shopify-shop-domain` header and have it accepted as authentic for a shop they do not control. This is a cross-tenant identity confusion at the boundary this gem is responsible for (it does the HMAC verification and hands the "authenticated" shop to the app), even though it stems from the app's use of the returned shop value.

### Likelihood Explanation
Exploitation requires only the ability to send arbitrary HTTP requests to the app's public webhook endpoint and knowledge of one valid signed body for any topic (trivially available to any merchant who installs the app and inspects their own webhook traffic, or via publicly known webhook payload formats since the shared secret is the only unknown but is not needed if a valid body/HMAC pair is reused verbatim). No access token, refresh token, or `api_secret_key` leakage is required to mount this replay-with-swapped-header attack.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`) values inside the signed/verifiable material, or otherwise cryptographically bind the asserted `shop-domain` header to the signature before exposing it via `WebhookMetadata`, so `HmacValidator.validate` enforces `hmac == HMAC(body ∥ shop, secret)` rather than `hmac == HMAC(body, secret)` alone.

### Proof of Concept
1. Attacker legitimately installs the app on `attacker-shop.myshopify.com` and receives (or triggers) a genuine webhook: body `B`, header `x-shopify-hmac-sha256: H = HMAC_SHA256(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same `B` and `H` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` recomputes `HMAC_SHA256(secret, B)`, which still equals `H` (body unchanged) [5](#0-4) , so verification passes.
4. `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` [6](#0-5)  and invokes the handler, which the host app treats as an authenticated event for the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
