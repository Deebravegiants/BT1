Based on extensive searching across the reachable attack surface — `EvmHost.dispatchIncoming`/`HandlerV2` message delivery, `pallet-ismp`'s `handle_unsigned`/`child_trie` commitments, the MMR accumulation pipeline (`modules/pallets/mmr/src/lib.rs`, `modules/pallets/mmr/src/mmr/storage.rs`), BEEFY/SP1 consensus verification, and the HyperFungibleToken/IntrinsicIntents mint-burn and escrow logic — I could not find a reachable analog to the Linux kernel bug class described.

The CVE's root cause is a driver leaving a stale/invalid buffer pointer in place after a failed allocation, which is later dereferenced and causes a kernel panic — a non-atomic, manually-managed memory buffer that can be left in an inconsistent state across two separate operations. This bug class does not map cleanly onto the Hyperbridge codebase because:

- EVM contract calls are atomic: any failed sub-operation reverts the entire transaction unless explicitly caught, and where explicit catching is used (e.g. `EvmHost.dispatchIncoming` deleting the receipt on failed `onAccept`), the code already restores state correctly on failure, mirroring the *fixed* version of the kernel bug rather than the vulnerable one. [1](#0-0) 
- `pallet-ismp`'s `handle_unsigned` is wrapped in `#[frame_support::transactional]`, so any error during message handling rolls back all storage writes made during that call, preventing partial/stale state from persisting. [2](#0-1) 
- The MMR pallet's `finalize()` explicitly comments that `mmr.push` "should never fail" and treats any failure defensively, but this path is only reachable through the block-finalization hook, not directly by an attacker-controlled single transaction, and no reachable exploitation path to fund loss or forged message delivery was found.
