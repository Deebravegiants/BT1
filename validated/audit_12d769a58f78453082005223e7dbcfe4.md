### Title
`RemoteConfig#update()` never resolves `#whenLoaded` on fetch/parse failure, causing `get()`/`getAll()` to hang forever - (File: features/remote-config/module/index.ts)

### Summary
`RemoteConfig#resolveLoaded()` is only invoked inside the success path of the `try` block in `update()`, and there is no corresponding call in the `catch` block. If the very first (and every subsequent) call to `#fetchConfig` fails — e.g. non-OK HTTP response, invalid JSON, or non-object payload — the `#whenLoaded` promise that gates `get()` and `getAll()` never resolves, causing those methods to hang indefinitely.

### Finding Description
`#whenLoaded` is a single instance-level promise created once in the class field initializer, with its `resolve` captured into `#resolveLoaded`: [1](#0-0) 

`get()` and `getAll()` both `await this.#whenLoaded` before returning any value: [2](#0-1) 

In `update()`, `this.#resolveLoaded!()` is called only on the success path just before `return { success: true }`. The `catch` block only tracks/logs the error and returns `{ error }` — it never resolves `#whenLoaded`: [3](#0-2) 

`#fetchConfig` throws in multiple realistic scenarios controlled by the remote-config server's response: non-OK HTTP status, JSON parse failure, or a payload where `data` is missing/non-object: [4](#0-3) 

`load()` retries `update()` in a loop with a backoff (`errorBackoffTime`, default 5s) as long as it keeps failing, but each retry still only calls `#resolveLoaded` on success, so `#whenLoaded` stays unresolved across arbitrarily many failed attempts: [5](#0-4) 

The existing test suite only asserts that errors get tracked in `errorsAtom`, but never asserts that `get()`/`getAll()` resolve after a failure — confirming this path is untested: [6](#0-5) 

This class is exposed directly to app code via `remoteConfigApi`, whose `get`/`getAll`/`update` methods forward straight to `RemoteConfig` instance methods: [7](#0-6) 

### Impact Explanation
Any caller of `exodus.remoteConfig.get(key)` or `.getAll()` will hang forever (unbounded await) if the remote-config endpoint is persistently unreachable or returns malformed/erroring responses from the very first fetch. This is a denial-of-service of the remote-config subsystem: any feature or UI flow that `await`s `remoteConfig.get(...)` before proceeding will freeze indefinitely rather than falling back to a safe default, undermining the fail-safe design intent of "always resolve, worst case with stale/default data." Note that the `feature-flags` module (`features/feature-flags/module/index.js`) does not itself call `remoteConfig.get`/`getAll` — it consumes separate `remoteConfigFeatureFlagAtoms` — so the impact is scoped to direct consumers of the `remoteConfig` module/API (e.g. `remoteConfigApi.get`/`getAll`) rather than the feature-flag pipeline specifically.

### Likelihood Explanation
Trivially reproducible: any server error (HTTP 5xx/4xx), transient network failure returning a non-OK response, or malformed JSON body on the first fetch is enough to trigger the hang — no special attacker privilege beyond controlling/disrupting the remote-config server or the network path (e.g. compromised CDN, misconfigured server, or MITM) is needed. Because `load()` retries indefinitely with backoff but never resolves `#whenLoaded` except on an eventual success, the hang persists for as long as the failures continue, which could be indefinite if failures are induced continuously.

### Recommendation
Ensure `#resolveLoaded()` is called regardless of success/failure of the first update, e.g. move the call to a `finally` block (or explicitly call it in the `catch` on first failure) so `#whenLoaded` always resolves after the first attempt, allowing `get()`/`getAll()` to return current/default (possibly empty) state instead of hanging. Alternatively, add a bounded timeout wrapping `#whenLoaded` in `get()`/`getAll()`.

### Proof of Concept
Unit test extending `features/remote-config/module/index.test.ts`:
1. Mock `fetch` to always resolve with `{ ok: false, status: 500, headers: { get: () => null }, json: async () => ({}) }` (always erroring, matching existing "should capture the error when response.ok is false" setup).
2. Create `remoteConfig` via `createRemoteConfig(...)` and call `void remoteConfig.load()`.
3. Call `const valuePromise = remoteConfig.get('some.key')` and race it against `delay(500)` using `Promise.race`.
4. Assert that the race resolves to the timeout sentinel, not to `valuePromise`, proving `get()` never resolves under sustained fetch failure — expected/desired behavior after fix: `get()` resolves (e.g., to `undefined`/default) within the timeout window instead of hanging.

      if (!this.#current && current) {

      }

      const { config, lastModified } = await this.#fetchConfig({ lastModified: _lastModified })

      const changes = config && (!this.#current || !isEqual(config, this.#current))

      if (changes) {
        this.#current = this.#freeze(config)
        this.#logger.debug('updated config with changes from remote')

          lastModified,

        namespace: safeString`remoteConfig`,
      })
