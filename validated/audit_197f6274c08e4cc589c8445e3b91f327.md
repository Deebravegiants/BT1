### Title
Webhook shop identity (and topic) not bound by HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the shop, topic, API-version, and webhook-id are all taken from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then blindly forwards `request.shop` (and `request.topic`) to the app's webhook handler as trusted tenant-identifying data, even though these values are never covered by the signature.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery`'s `hmac` attribute against `to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers (`shopify_header`), which are never part of the HMAC-signed bytes: [3](#0-2) 

`Registry.process` validates only the body's HMAC, then constructs `WebhookMetadata` using the unauthenticated `request.shop` and `request.topic` values and hands them directly to the app's registered handler: [4](#0-3) 

The broken identity binding is:
`hmac_covers(raw_body)` ⇏ `hmac_covers(shop)`

but the handler is invoked as if `shop` (and `topic`) were authenticated alongside the body: `handler.handle(shop: request.shop, body: verified_body, ...)`.

Because the app's global `api_secret_key` (not a per-shop secret) is used to sign every webhook for every shop that installs the app, any unprivileged user who legitimately installs the app on their own store receives real webhooks with valid `(body, hmac)` pairs for content they substantially control (e.g. by creating/editing their own orders, products, or customers, which are echoed back in the webhook body). That attacker can then replay the exact same `raw_body`/`hmac` pair to the same webhook endpoint while substituting the `shopify-shop-domain` header (and/or `shopify-topic`) to name a victim shop. `HmacValidator.validate` still succeeds because it only checks `raw_body` integrity, so `Registry.process` calls the handler believing the (attacker-controlled) payload originated from the victim shop.

### Impact Explanation
This breaks the tenant (shop) identity binding for webhook processing: an attacker who is merely a legitimate installer of a multi-tenant app on their own store can forge webhook deliveries that the host application will attribute to an arbitrary other shop. Any app logic that trusts `WebhookMetadata#shop` for tenant-scoped effects (writing to that shop's records, sending shop-scoped notifications, triggering per-shop side effects, updating shop state) can be manipulated cross-tenant with attacker-controlled body content, without ever needing the app's `client_secret`/`api_secret_key`, an access token, or a privileged account. This is a cross-tenant access vulnerability that satisfies the Critical impact bar.

### Likelihood Explanation
Any user capable of installing (or being a collaborator/staff on) an app on their own Shopify store can trigger this — the only prerequisite is that the app is a normal multi-tenant Shopify app relying on this gem's `Webhooks::Registry.process`/`Request` for webhook verification and dispatch, which is the intended and documented usage pattern of the gem.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signable string (or otherwise cryptographically bind them to the verified payload), so the HMAC verifies the full identity tuple, not just the raw body bytes. At minimum, the `shop` domain used to attribute a webhook to a tenant must be covered by the same signature that authenticates the payload.

### Proof of Concept
1. Attacker installs the target public/multi-tenant app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook topic they can influence (e.g. `products/update`) causing Shopify to POST a body `B` with header `shopify-shop-domain: attacker-shop.myshopify.com` and a valid `shopify-hmac-sha256` computed as `HMAC-SHA256(api_secret_key, B)` (per `Request#to_signable_string`, only `B` is signed — see `lib/shopify_api/webhooks/request.rb:35-38`).
3. Attacker resends the identical `B` and `hmac` to the app's webhook endpoint, but replaces the header with `shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) recomputes the HMAC over `B` only, which still matches.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body `B`, even though this data never actually originated from `victim-shop`.
