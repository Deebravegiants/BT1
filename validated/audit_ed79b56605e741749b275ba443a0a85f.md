### Title
`TokenExchange.exchange_token` sends the app's `client_secret` to a shop host derived from an unvalidated JWT `dest` claim, unlike its sibling method - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the host used for the `/admin/oauth/access_token` request (which carries `client_secret`) from `jwt_payload.shop` (the JWT `dest` claim) without ever passing it through `Utils::ShopValidator.sanitize!`, whereas the sibling method `migrate_to_expiring_token` explicitly validates the shop with `Utils::ShopValidator.sanitize!(shop)` before using it the same way.

### Finding Description
In `exchange_token`, the shop used to build the outgoing request session is taken directly from the decoded session token: [1](#0-0) 
This `dest_shop` is passed straight into `ShopifyAPI::Auth::Session.new(shop: dest_shop)` and then into `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")`, which posts `client_id`/`client_secret`/`subject_token` to that host: [2](#0-1) 

Compare this with `migrate_to_expiring_token` in the same file, which performs the exact same operation (build a session, send `client_secret` to `{shop}/admin/oauth/access_token`) but first calls `Utils::ShopValidator.sanitize!(shop)`: [3](#0-2) 

`ShopValidator.sanitize!`/`sanitize_shop_domain` is the gem's designated mechanism for binding a "shop" string to the trusted domain allow-list (`myshopify.com`, `shopify.com`, `spin.dev`, `shop.dev`, plus a caller-supplied `myshopify_domain`) before that string is used to target a request that discloses `client_secret`: [4](#0-3) [5](#0-4) 

`JwtPayload` decodes the token with signature verification and checks only that `aud == Context.api_key`; it performs no validation that `dest`/`iss` is a trusted Shopify domain, and simply strips `"https://"` off `dest` to produce `shop`: [6](#0-5) 

So the identity binding that should hold is: *shop host used to receive `client_secret` == a value that has passed `ShopValidator`'s trusted-domain check*. In `exchange_token` this binding is broken — the host is instead whatever raw string is embedded in the JWT's `dest` claim, unvalidated.

### Impact Explanation
If the `dest` claim can ever contain a value that is not a genuine `*.myshopify.com` (or otherwise trusted) domain — e.g. through JWT libraries/algorithm confusion, misconfigured verification, or any code path that constructs/re-signs a session token payload from less-trusted input — this method would cause the host application to POST its `client_id` + `client_secret` to an attacker-influenced host, i.e. SSRF with the app's OAuth credentials. This matches the "SSRF with the app's credentials" High-impact category. The inconsistency with `migrate_to_expiring_token` (which validates the exact same kind of value before the exact same kind of use) shows this is a missing check rather than an intentional design decision.

### Likelihood Explanation
Under normal operation, a session token's `dest` claim is set by Shopify and protected by the JWT HMAC signature verified against `Context.api_secret_key`/`old_api_secret_key`, so a value with a valid signature should originate from Shopify for a real shop. Exploitability therefore depends on some additional weakness (e.g., signature/algorithm handling in the `jwt` gem, or any caller path that feeds a token whose `dest` was not itself validated) to inject an attacker-controlled `dest`. I could not find such a bypass in the reachable code, and the JWT decode path is otherwise standard (`JWT.decode(token, secret, true, algorithm: "HS256")`). Given the rules restrict findings to concrete, provable exploit paths not requiring credential compromise, and I cannot demonstrate that `dest` is attacker-forgeable without the secret, this is a **defense-in-depth gap** (missing validation relative to the sibling method) rather than a demonstrated remotely exploitable bypass by an unprivileged, unauthenticated party.

### Recommendation
For consistency and defense-in-depth, `exchange_token` should validate `dest_shop` with `Utils::ShopValidator.sanitize!` (as `migrate_to_expiring_token` already does) before constructing the session/request that transmits `client_secret`, rejecting any `dest` value that does not resolve to a trusted Shopify domain.

### Proof of Concept
Not reproducible as a standalone, credential-free PoC: exploitation would require producing a session token whose `dest` claim contains a non-Shopify host while still passing `JwtPayload`'s signature/`aud` checks, which requires either the app's `api_secret_key` or an underlying JWT verification flaw neither of which was found in this codebase. This finding is reported as a code-level inconsistency/missing-validation gap rather than a proven exploit chain.
