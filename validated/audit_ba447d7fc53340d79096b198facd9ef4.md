Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant spoofing of the webhook's identity claim - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload solely from the raw HTTP body, while the shop identity used to route/attribute the webhook is read from a separate, unsigned HTTP header. This breaks the binding `bytes verified == bytes trusted for tenant identity`: the `shop-domain` header can be swapped without invalidating the HMAC, since it is never included in the signed content.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#hmac` decodes the `hmac-sha256`/`x-shopify-hmac-sha256` header for comparison: [2](#0-1) 

But `Request#shop` reads a completely different, unsigned header (`shop-domain`/`x-shopify-shop-domain`): [3](#0-2) 

`HmacValidator.validate` only checks the HMAC against `to_signable_string` (the body), never touching headers: [4](#0-3) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity, forwarding it to the app's webhook handler as an authenticated claim: [5](#0-4) 

Because the `client_secret` used to sign webhooks is a single per-app secret shared across every shop that has the app installed (there is no per-shop signing key), any body+HMAC pair that validates for shop A also validates unchanged for a request carrying a different `shop-domain` header. An attacker who can capture (or trigger, e.g. by installing/using the same app on their own store) one legitimate `body`/`hmac` pair can replay that exact body to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `Utils::HmacValidator.validate(request)` still returns `true` (it never inspects headers), and the forged `shop` value is handed to the handler as `WebhookMetadata#shop`, which apps use to select which tenant's records the payload applies to.

This is the direct analog of the reported issue: just as `processWithdrawal`/`cancelWithdrawal` trusted an unverified index to identify which record to act on, here the gem trusts an unverified header (`shop-domain`) to identify which tenant a signed body belongs to — the field acted upon (shop identity) is not the field actually covered by the integrity check (raw body only).

### Impact Explanation
This crosses a tenant boundary: a webhook payload cryptographically valid for shop A can be attributed to shop B purely by header substitution, with no knowledge of `api_secret_key` required beyond having legitimately received one webhook. Any app that uses `WebhookMetadata#shop` (as documented/intended, see `Registry.process`) to decide which merchant's data to create/update/delete based on the webhook body will act on attacker-chosen data under a victim shop's identity — a cross-tenant data-integrity/confidentiality issue. This qualifies as Critical: cross-tenant access enabled by the gem's own trust boundary between signed content and the identity field it hands to handlers.

### Likelihood Explanation
Exploitability requires only the ability to observe or generate one legitimate `(raw_body, hmac)` pair for the shared app secret (e.g., by installing the app to any test/free store, which is normal, unprivileged access) and then send a crafted HTTP request with the same body/HMAC but a different `shop-domain` header to the app's webhook endpoint. No `api_secret_key`, access token, or privileged account is needed — this is fully within "unprivileged internet user" capability, and the vulnerable code path (`Registry.process` → `HmacValidator.validate` → `request.shop`) is the gem's documented webhook processing flow.

### Recommendation
Include the shop identity (and other routing-critical headers such as `topic`, `webhook_id`, `api_version`) in the HMAC-signed content, or otherwise cryptographically bind the header values to the body before trusting them. At minimum, `Request#to_signable_string` should incorporate `shop-domain` (and any other header consumed by `WebhookMetadata`) so that tampering with those headers invalidates the signature, restoring the equality `bytes verified == bytes trusted as the tenant identity`.

### Proof of Concept
1. App has the same `client_secret` across all shops that install it (this is inherent to Shopify's webhook signing model).
2. Attacker installs/uses the app on their own store (`attacker.myshopify.com`) and triggers a webhook, capturing the raw body `B` and its valid `X-Shopify-Hmac-Sha256: H`.
3. Attacker sends a POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (valid), but `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates `H` against `B` — passes, since `shop-domain` is not part of the signed string: [6](#0-5) 
5. The handler receives `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker-controlled parsed body>, ...)` and acts on it as if it were a genuine webhook for `victim.myshopify.com`.
