Based on my investigation, the withdraw and deposit paths in this Raydium AMM implementation do have optional slippage protections, but they are **not enforced by default** since `min_coin_amount`/`min_pc_amount` (Withdraw) and `other_amount_min` (Deposit) are `Option<u64>` fields.

### Title
Optional (non-enforced) slippage checks on Withdraw allow sandwich attacks that drain value from LPs - (File: `program/src/processor.rs`)

### Summary
`process_withdraw` only validates `min_coin_amount`/`min_pc_amount` when **both** are supplied as `Some`; when a caller omits them (passes `None`), the withdrawal proceeds unconditionally at whatever `coin_amount`/`pc_amount` the pool state yields at execution time, with no protection against price manipulation between transaction submission and execution.

### Finding Description
In `Processor::process_withdraw`, the withdrawal amounts `coin_amount` and `pc_amount` are computed from the pool's current reserves (`total_coin_without_take_pnl`, `total_pc_without_take_pnl`) via `InvariantPool::exchange_pool_to_token` at the time the instruction executes [1](#0-0) . The slippage check is conditional on both `Option` fields being populated: [2](#0-1) 

The instruction schema defines these as optional (`Option<u64>`) for both `WithdrawInstruction` [3](#0-2)  and `DepositInstruction`'s `other_amount_min` [4](#0-3) . The unpack logic explicitly allows both to be omitted from the instruction data, defaulting to `None` and skipping the check entirely [5](#0-4) . The reference CLI/SDK also demonstrates building withdraw instructions with `slippage_limit: false` [6](#0-5) , indicating the unprotected path is a normal, expected usage mode, not just a theoretical edge case.

This mirrors the reported bug class: a liquidity-removal operation whose payout amounts are computed against live pool state with no mandatory minimum-output enforcement, permitting an attacker to manipulate the coin/pc ratio (via swaps) immediately before the withdraw executes and restore it immediately after (a sandwich), extracting value from the withdrawing LP just as in the Uniswap `decreaseLiquidity` case where `amount0Min`/`amount1Min` are hardcoded/left at 0.

### Impact Explanation
An attacker observing a pending `Withdraw` (or `Deposit`) transaction with no `min_coin_amount`/`min_pc_amount` set can front-run it with a swap that skews the pool's coin/pc ratio, causing `exchange_pool_to_token` to compute a less favorable split for the withdrawing LP, then back-run to restore the ratio and pocket the difference. This is a real value-extraction path against LP funds, matching the "concrete theft ... of user or LP funds" bar.

### Likelihood Explanation
Likelihood is moderate: it requires the withdrawing party to omit `min_coin_amount`/`min_pc_amount` (both must be `None` to skip the check — the code and default CLI example suggest this is common) and requires mempool visibility/atomicity to sandwich the transaction, which is readily achievable on Solana via bundling or fast-follow transactions.

### Recommendation
Make `min_coin_amount` and `min_pc_amount` (and `other_amount_min` for deposit) mandatory rather than `Option`, so slippage protection cannot be silently bypassed by a wallet/SDK default, and reject the instruction outright if these guards are absent instead of allowing an unconditional/unchecked path.

### Proof of Concept
Conceptual sequence (no code execution performed, derived from `process_withdraw` logic at [7](#0-6) ):
1. Victim submits `Withdraw` instruction with `amount = X`, `min_coin_amount = None`, `min_pc_amount = None`.
2. Attacker front-runs with a large `SwapBaseIn`/`SwapBaseOut` that skews `amm_coin_vault.amount`/`amm_pc_vault.amount` reserves.
3. Victim's `Withdraw` executes; since both mins are `None`, the slippage guard block is skipped entirely, and `coin_amount`/`pc_amount` are computed from the manipulated reserves, yielding a worse split than the victim expected.
4. Attacker back-runs, reversing the swap and capturing the value difference extracted from the victim's withdrawal.

**Caveat**: I could not fully verify the equivalent `process_deposit` code body within the tool budget (only confirmed the `other_amount_min` field is likewise `Option<u64>` and unpacked conditionally); if the deposit path applies the same conditional-check pattern, it would be an additional, symmetric instance of the same issue.
