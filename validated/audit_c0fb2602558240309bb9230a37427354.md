## Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header not covered by HMAC — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the webhook's trusted shop identity from the `X-Shopify-Shop-Domain` header, but the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates is computed only over the raw request body. The shop header is never bound to the signature, so a valid `(body, hmac)` pair captured from one tenant's legitimate webhook can be replayed with a different `shop-domain` header value and will still pass verification, letting the handler attribute attacker-controlled webhook data to an arbitrary other shop.

### Finding Description
`Registry.process` authenticates a webhook solely by checking `Utils::HmacValidator.validate(request)`: [1](#0-0) 

which delegates to `to_signable_string`. For webhooks that string is defined as only the raw HTTP body: [2](#0-1) 

Meanwhile the shop identity that is handed to the app's handler — and that `docs/usage/webhooks.md` explicitly documents as the trustworthy "shop domain of the webhook" — comes straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cross-check against anything covered by the HMAC: [3](#0-2) [1](#0-0) [4](#0-3) 

The HMAC secret (`api_secret_key`) is the app's single `client_secret`, shared across every shop that installs the app — it is not a per-shop credential. This means:
- Equality the boundary is supposed to enforce: `shop_attributed_to_handler == shop_that_actually_sent_the_request`.
- What is actually checked: `HMAC(body, shared_app_secret) == received_hmac`, which is entirely independent of the `shop-domain` header value.

Because the same shared secret signs webhooks for every shop of the app, any shop that has legitimately installed the app can capture one of its own valid `(body, X-Shopify-Hmac-Sha256)` pairs and resubmit it to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a different shop's domain (also an app installer). `HmacValidator.validate` will still succeed because it only re-hashes `@raw_body`, and `Registry.process` will construct `WebhookMetadata` with the attacker-chosen `shop` value and dispatch it to the handler as if it were legitimately from that shop: [5](#0-4) 

### Impact Explanation
This is a cross-tenant identity binding break: an unprivileged actor who is merely a legitimate installer of a multi-tenant app (not the victim tenant, and without needing the app's `client_secret`, an access token, or any privileged account) can cause the host application to process forged webhook payloads attributed to a different, arbitrary tenant of the same app. Depending on how the host app's handler uses `data.shop` (session lookup, order/inventory writes, GDPR/uninstall triggers, etc., as shown in the documented handler pattern), this enables cross-tenant data injection or corruption — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any merchant can install a public Shopify app for free to become a legitimate webhook recipient, then simply resend a captured request with one header changed; the attack requires no cryptographic secret, no other tenant's credentials, and only standard HTTP tooling. The main precondition is knowing/guessing another installed shop's domain, which is often discoverable or enumerable.

### Recommendation
Bind the shop identity into the authenticated material, e.g., include the `shop-domain` (and ideally `topic`, `webhook-id`) header values in `to_signable_string`, or require the host application to independently verify that `request.shop` corresponds to a shop with an active session/installation before trusting it — and document this requirement prominently. At minimum, `Registry.process` should not treat `request.shop` as authenticated data without such a cross-check.

### Proof of Concept
1. App `A` is installed by both `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, sharing one `api_secret_key`.
2. Attacker's shop receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H = HMAC-SHA256(secret, B)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker resends the identical `raw_body B` and `hmac H` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes `HMAC(secret, B)`, which still equals `H`, so validation passes (`lib/shopify_api/utils/hmac_validator.rb` + `lib/shopify_api/webhooks/request.rb#to_signable_string`).
5. `Registry.process` calls the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)`, causing the app to act on forged data attributed to the victim tenant.
