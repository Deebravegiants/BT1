### Title
Webhook `shop`, `topic`, and `webhook-id` identity fields are not bound by the HMAC, allowing cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` accepts a webhook as authentic solely by checking `Utils::HmacValidator.validate(request)`, which validates the HMAC over the raw body only. The `shop-domain`, `topic`, and `webhook-id` values used to route and identify the tenant for the webhook are taken from unauthenticated HTTP headers and are never included in the signed content, then handed directly to the app's handler as trusted identity data.

### Finding Description
This mirrors the H-8 bug class: an equality/authenticity check is performed on one representation of data (the raw body) while a separate, security-relevant field (the shop identity) is acted upon without being covered by that same check — breaking the intended binding `verified_bytes == acted_on_identity`.

- `Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

- `Webhooks::Request#shop`, `#topic`, and `#webhook_id` are read directly from HTTP headers, with no cryptographic link to the HMAC: [2](#0-1) 

- `HmacValidator.validate` computes and compares the HMAC only against `to_signable_string` (i.e., body bytes), never incorporating `shop`, `topic`, or `webhook_id`: [3](#0-2) 

- `Registry.process` validates the HMAC and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler, without any secondary binding check: [4](#0-3) 

By contrast, the OAuth callback path in this same gem does bind the `shop` field into the signed content (`AuthQuery#to_signable_string` includes `shop`), demonstrating that the library is capable of, and elsewhere does, bind identity fields into the HMAC: [5](#0-4) 

Because the webhook HMAC covers only the body, any two webhook deliveries (for different shops or different topics) that happen to carry an identical raw body produce an identical valid HMAC under the app's `api_secret_key`. Since `api_secret_key` is shared for all shops/tenants of the app (it's not per-shop), a party that legitimately receives one valid `(body, hmac)` pair for their own shop/topic can present that exact pair to the app's webhook endpoint with different `shop-domain`/`topic`/`webhook-id` headers, and `Registry.process` will accept it as authentic and route it as if it came from the spoofed shop/topic.

### Impact Explanation
This breaks tenant isolation for HTTP-delivered webhooks in a multi-tenant app: an actor who controls (or can trigger) a webhook delivery for shop A can cause an app to process it as an authentic webhook for shop B, since the identity fields used for routing/authorization (`shop`, `topic`, `webhook_id`) are outside the cryptographic proof. This is a cross-tenant confusion of authenticated data, matching the "cross-tenant access" impact category, and can lead to acting on/exposing another merchant's data or state within apps that key their business logic off `WebhookMetadata#shop`/`#topic` without additional verification.

### Likelihood Explanation
Exploitability requires the attacker to be able to trigger delivery of at least one genuine webhook with a body they can predict or that is content-invariant across shops/topics (e.g., empty-body or template-identical payloads for mandatory compliance topics such as `shop/redact` are plausible candidates, and many webhook topics contain limited or repeated boilerplate fields). This is a real, currently-reachable gap in the gem's own webhook signature verification logic (not a misuse of a documented API by the host app) — the gem itself defines `to_signable_string` to exclude the identity headers and defines `Registry.process` to trust those headers post-HMAC-check.

### Recommendation
Bind the identity-relevant headers into the value that is HMAC-verified, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the signed payload before trusting them in `Registry.process`. At minimum, applications should be warned (and the gem should enforce) that `shop`/`topic` from `Webhooks::Request` must be cross-checked against session/tenant records obtained through other authenticated channels before being used to key any tenant-specific action.

### Proof of Concept
1. App has `api_secret_key = S` shared across all installed shops.
2. Attacker's own shop (shop A) triggers a webhook with a body `B` that Shopify signs: `hmac = HMAC-SHA256(S, B)`. Attacker captures `(B, hmac)` (e.g., via their own logging or replaying their own webhook payload).
3. Attacker sends a forged request to the app's webhook endpoint with headers `x-shopify-shop-domain: shop-b.myshopify.com`, `x-shopify-topic: <same or different topic>`, and body `B` with `x-shopify-hmac-sha256: hmac`.
4. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(S, B)`, which matches, per [6](#0-5) .
5. `Registry.process` proceeds and invokes the handler with `WebhookMetadata` carrying `shop: "shop-b.myshopify.com"`, per [7](#0-6) , even though the underlying signed content was never associated with shop B by Shopify.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
