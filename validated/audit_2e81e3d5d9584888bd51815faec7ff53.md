### Title
Webhook shop-domain header spoofing bypasses HMAC verification, enabling cross-tenant webhook injection - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then trusts the `shop` value taken from an unsigned HTTP header and hands it directly to the app's `WebhookHandler` as the tenant identity for the event.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` as the HMAC-covered content [1](#0-0) , while `shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely outside the signed material [2](#0-1) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., the body/secret HMAC) before dispatching, and then constructs `WebhookMetadata` using `request.shop` verbatim as the tenant-binding field passed to the merchant's handler [3](#0-2) . `WebhookMetadata.shop` is a plain `String` field with no cryptographic linkage to the HMAC-verified body [4](#0-3) .

The broken identity binding is: `shop header value == shop value trusted by the app's tenant-scoped handler`, while the actual guarantee provided by `HmacValidator.validate` is only `HMAC(raw_body, secret) == received_hmac`, i.e. `shop ∉ signed_bytes`. Because the HMAC never covers the header, any party capable of producing a body/HMAC pair that matches a legitimate Shopify webhook delivery for one shop (e.g., replaying a captured request, or a proxy/CDN layer that forwards headers independently) can substitute an arbitrary `x-shopify-shop-domain` value while keeping the body and its HMAC untouched. `Registry.process` will accept the mutated request as valid and dispatch it to the merchant handler labeled with the attacker-chosen `shop`, since nothing in the verification path checks that the header shop matches any authenticated value derived from the signed payload.

This is an unprivileged-internet-user analog: an attacker who intercepts, replays, or otherwise causes delivery of an unmodified request body (network position, logging leak, open redirect via a shared proxy, etc.) does not need the app's `client_secret` to forge the HMAC — they reuse a real HMAC/body pair and only need to control the header that carries `shop`, which is not cryptographically bound to that HMAC at all.

### Impact Explanation
Apps that key tenant-scoped side effects (updating merchant records, marking orders paid, granting access, invalidating tokens, etc.) off `WebhookMetadata#shop` as returned by this gem can be tricked into attributing another shop's real webhook event to an attacker-chosen shop, or attributing a captured/replayed payload to a shop it never came from — a cross-tenant data/identity confusion inside the gem's own verified webhook boundary, since the gem itself asserts "HMAC validated" without asserting "shop is part of what was validated."

### Likelihood Explanation
Exploitation requires access to at least one legitimately-signed webhook body (its bytes and HMAC), which is realistic for any actor with network visibility into the delivery path (shared infrastructure, logging systems, request proxies) or via a shop the attacker legitimately owns issuing events under its own valid HMAC while relabeling the `shop` header before it reaches this gem's request parser. No possession of `api_secret_key` is needed to construct a mismatched header/body pair from a real prior delivery.

### Recommendation
Include the `shop` (and ideally `topic`, `api-version`) values in the HMAC-signable content, or independently cross-validate the header-derived `shop` against a value derivable from already-verified material (e.g., requiring the consuming app to look up and pin the expected shop for the delivery channel) before constructing `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a sole tenant-binding key.

### Proof of Concept
1. Capture a legitimate Shopify webhook delivery for `shop-a.myshopify.com` with topic `orders/create`: body `B`, and a valid `x-shopify-hmac-sha256` header computed as `HMAC-SHA256(secret, B)`.
2. Replay the identical body `B` and identical HMAC header, but modify `x-shopify-shop-domain` to `shop-b.myshopify.com`, at any point in transit that is not integrity-protected by TLS pinning end-to-end (e.g., a shared reverse proxy, load balancer log replay, or man-in-the-middle on an internal hop).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "shop-b.myshopify.com", hmac: "<original>"...})` is constructed; `to_signable_string` returns `B` unchanged.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(secret, B)` and matches the untouched header — validation succeeds [5](#0-4) .
5. `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: ..., ...)` is built and dispatched to the handler, which now believes this order-create event belongs to `shop-b` even though it was never generated for that shop [6](#0-5) .
