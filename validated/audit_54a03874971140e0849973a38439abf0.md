Audit Report

## Title
DMP messages enqueued to an on-demand para during its (unprivileged) offboarding grace window are silently destroyed by `clean_dmp_after_outgoing` with no refund or error - ([File: polkadot/runtime/parachains/src/dmp.rs])

## Summary
`can_queue_downward_message`/`queue_downward_message` in `polkadot/runtime/parachains/src/dmp.rs` only validate message size, queue capacity, and presence of a `paras::Heads` entry for the destination para; they never check whether the para has already been scheduled for offboarding. [1](#0-0)  Because `paras::Heads` remains populated until the session boundary where `clean_dmp_after_outgoing` unconditionally deletes `InboundDownwardQueue`/`DownwardMessageQueueHeads`, any message accepted into the DMP queue during the window between an unprivileged `deregister` call and the next session change is guaranteed to be wiped with no processing and no signal to the sender. [2](#0-1) 

## Finding Description
`Pallet::deregister` is reachable by a signed on-demand parachain owner through `ensure_root_para_or_owner`, requiring no privileged origin. [3](#0-2)  `do_deregister` only calls `schedule_para_cleanup`, which schedules removal for a future session boundary — it does not remove the `paras::Heads` entry immediately, and the deposit/`Paras` info is cleared but the head storage used by DMP gating is untouched. [4](#0-3) 

During the interval between the `deregister` extrinsic and the next session change, `paras::Heads::<T>::contains_key(para)` remains `true`, so `can_queue_downward_message` returns `Ok(())` and `queue_downward_message` accepts the message, appends it to `InboundDownwardQueue`, and updates the MQC head. [5](#0-4)  The gating check makes no reference to the para's scheduled lifecycle transition — the sole criterion is presence of a `Heads` entry. [6](#0-5) 

At the following session boundary, `initializer_on_new_session` invokes `perform_outgoing_para_cleanup`, which calls `clean_dmp_after_outgoing` for every para in the `outgoing_paras` list (which includes the deregistering para). This unconditionally deletes the entire `InboundDownwardQueue` and resets `DownwardMessageQueueHeads`, with no check for whether messages remain unprocessed and no notification or refund path. [7](#0-6)  This ordering (`initializer.rs` on_finalize wires `apply_new_session` → session change notifications → outgoing cleanup) confirms cleanup happens exactly at the session boundary, independent of whether the DMQ has been drained. [8](#0-7) 

Existing checks (`can_queue_downward_message`'s size/capacity/`Heads`-existence checks) are insufficient because none of them consult the para's offboarding schedule (e.g., an actions-queue-based "is being cleaned up" predicate), so a message can be legitimately queued into a channel that is guaranteed to be wiped without execution.

## Impact Explanation
Any DMP message sent to a para between its unprivileged `deregister` call and the next session boundary is deleted from storage rather than delivered — the sender receives `Ok(())` at send time with no later failure event, bounce, or refund. If the message payload encodes value logic (e.g., an XCM `Transact`/asset instruction whose value accounting was already finalized on the sending side), that value can be permanently lost from the sender's perspective, since the destination never executes it and no compensating mechanism exists in the DMP pallet. This is a genuine SDK-level gap in message-lifecycle handling rather than a privilege-escalation or fund-theft bug — the affected para itself is being decommissioned, so the "loss" is confined to messages sent into a known offboarding window rather than an attacker draining unrelated funds.

## Likelihood Explanation
The precondition (an on-demand para owner calling `deregister`) is normal, unprivileged, and expected. The window between `deregister` and the next session change is a fixed, non-zero interval during which `paras::Heads` remains populated, so `queue_downward_message` will accept messages exactly as the code shows. Any sender targeting that para id during this window is affected, and since the para is typically not scheduled for block production during this grace period, it has no reliable way to drain the queue itself. This is reproducible via a straightforward integration test combining `paras_registrar::deregister` and `dmp::queue_downward_message` followed by session advancement, as described in the report's PoC.

## Recommendation
Track offboarding-scheduled paras (e.g., check the paras action queue or an "is being offboarded" predicate) inside `can_queue_downward_message` and reject new downward messages with `QueueDownwardMessageError::Unroutable` once a para has been scheduled for cleanup. Alternatively, have `clean_dmp_after_outgoing` defer wiping non-empty queues, or emit an on-chain event/bounce mechanism so senders can detect and potentially recover from message loss.

## Proof of Concept
1. Register and onboard an on-demand para `P` so `paras::Heads::<Test>::contains_key(P)` is true.
2. As `P`'s owner (signed origin), call `Registrar::deregister(P)`; assert success with an unprivileged origin.
3. Before the next session, call `Dmp::queue_downward_message(&config, P, msg)`; assert `Ok(())`, and that the DMQ contents for `P` include `msg`.
4. Advance the chain to the session where `initializer_on_new_session` fires `perform_outgoing_para_cleanup` for `P`.
5. Assert the DMQ for `P` is empty and `DownwardMessageQueueHeads::<Test>::get(P) == Hash::default()`, confirming the message was deleted rather than delivered, refunded, or bounced.

	/// Deregister a Para Id, freeing all data returning any deposit.
	fn do_deregister(id: ParaId) -> DispatchResult {
		match paras::Pallet::<T>::lifecycle(id) {
			// Para must be a parathread (on-demand parachain), or not exist at all.
			Some(ParaLifecycle::Parathread) | None => {},
			_ => return Err(Error::<T>::NotParathread.into()),
		}
		polkadot_runtime_parachains::schedule_para_cleanup::<T>(id)
			.map_err(|_| Error::<T>::CannotDeregister)?;

		if let Some(info) = Paras::<T>::take(&id) {
			<T as Config>::Currency::unreserve(&info.manager, info.deposit);
		}

		PendingSwap::<T>::remove(id);
		Self::deposit_event(Event::<T>::Deregistered { para_id: id });
		Ok(())
	}
