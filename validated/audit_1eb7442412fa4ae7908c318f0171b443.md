This confirms the finding: the gem's own documentation states `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" (docs/usage/webhooks.md:125) and delivers `data.shop` to the handler as the trusted shop identity (docs/usage/webhooks.md:14, 25-26) — but the HMAC verification only covers the raw body, not the `shop` header.

### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0)  while `shop`, `topic`, `api_version`, and `webhook_id` are all read from unauthenticated headers [2](#0-1) . `Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` [3](#0-2) , so the `shop` value is never covered by the signature that "verifies the request did indeed come from Shopify," as the gem's own docs claim [4](#0-3) . `Registry.process` trusts this unauthenticated `shop` field and hands it directly to the app's handler as the tenant identity [5](#0-4) , and the docs instruct handlers to use `data.shop` to attribute/dispatch work (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [6](#0-5) .

### Finding Description
This is the same bug class as the report: an entity is authenticated (the HMAC proves the byte-for-byte body is genuine and came from a holder of `api_secret_key`), but a different, unauthenticated entity (the `shop` header) is the one actually acted upon/trusted downstream — analogous to burning tokens from the wrong account instead of the one that was actually verified/transferred. Here the equality that should hold is:

`shop attributed by Registry.process to the handler == shop that produced/owns the HMAC-authenticated body`

but nothing enforces this. `Request#shop` simply reads `shopify-shop-domain` (or `x-shopify-shop-domain`) directly from caller-supplied headers [7](#0-6) , and `HmacValidator.validate_signature` never includes this header in the signed material [3](#0-2) . By contrast, the OAuth callback's `AuthQuery#to_signable_string` explicitly includes `shop` in the signed parameters [8](#0-7) , showing the gem is capable of binding `shop` to the HMAC when it chooses to — but does not do so for webhooks.

Because `shop` is excluded from the signable string, a valid `(body, hmac)` pair generated for one shop's webhook remains cryptographically valid when replayed with a different `shopify-shop-domain` header value, since `OpenSSL.secure_compare(computed_signature, received_signature)` only checks the body's authenticity, not the header's [9](#0-8) .

### Impact Explanation
An attacker who legitimately installs the app on their own store (a real, unprivileged merchant account — no special credentials required) receives genuine webhook deliveries with valid `(raw_body, hmac)` pairs for their own shop. They can capture such a pair and replay it directly to the app's public webhook endpoint with a forged `shopify-shop-domain` header naming a victim shop. `Registry.process` will pass HMAC validation (since only the body is checked) [10](#0-9)  and dispatch the handler with `WebhookMetadata` claiming the event belongs to the victim's shop [11](#0-10) . Any app that uses `data.shop` to look up sessions, attribute writes, or drive per-tenant business logic (exactly as the gem's own example code does) will process attacker-controlled data under the wrong tenant, which is a cross-tenant identity/data-integrity violation.

### Likelihood Explanation
Likely and low-cost to exploit: it only requires installing the app as an ordinary merchant (which any of Shopify's app install flows readily permits), capturing one legitimate webhook body+HMAC pair, and POSTing it to the public webhook endpoint with a modified `shop-domain` header. No possession of `api_secret_key`, access tokens, or any privileged credential is needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the HMAC-verified material rather than trusting it purely from headers. Either include the relevant headers as part of the signable string (matching how Shopify's own webhook signing recommendations describe validating the header context), or require callers to cross-check `request.shop` against a known/expected session's shop before invoking the handler, and clearly document that `Registry.process`'s "verified the request came from Shopify" guarantee applies only to the body content and not to the `shop`/`topic`/`webhook_id` headers.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST: `raw_body` and the `shopify-hmac-sha256` header value.
2. Replay the exact same request to the app's public webhook endpoint, keeping `raw_body` and `shopify-hmac-sha256` unchanged, but set `shopify-shop-domain: victim-shop.myshopify.com` and `shopify-topic`/`shopify-webhook-id` as desired.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` [1](#0-0) .
4. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` [11](#0-10) , causing the app to process attacker-supplied content under the victim's tenant identity.
