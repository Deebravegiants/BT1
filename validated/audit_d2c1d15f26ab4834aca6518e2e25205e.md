### Title
Webhook shop attribution is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, then unconditionally trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers that are excluded from the signed content. Because the app's `client_secret` (used to compute the HMAC) is shared across every shop that has the app installed, any merchant who can trigger a webhook for their own store can capture the resulting valid `(body, hmac)` pair and replay it to the app's webhook endpoint with a forged `shop-domain` header, causing the handler to process attacker-supplied data under a victim shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read directly from request headers, which are not part of the signed string: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately forwards the unauthenticated `shop` header (along with topic/webhook_id/api_version) to the app's registered handler as trusted metadata: [3](#0-2) 

`HmacValidator.validate` only confirms that `verifiable_query.to_signable_string` (the raw body) was signed with `Context.api_secret_key`; it never checks that the signature is bound to the shop the request claims to be from: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by the HMAC == shop attributed to the webhook event`. Here, the HMAC authenticates only the body bytes; the "shop" side of the equality is populated from an arbitrary, unsigned header, so the equality can be broken by any party able to produce one valid `(body, hmac)` pair for the shared app secret.

Because `client_secret` is common to all shops that installed the given app (it's an app-level secret, not shop-specific), any merchant with the app installed can:
1. Trigger an event on their own shop (e.g., create/update a resource with attacker-chosen content) to receive a genuine webhook delivery with a valid `hmac-sha256` header over that body.
2. Replay that exact `raw_body` + `hmac-sha256` header to the app's webhook endpoint, substituting the `shop-domain` header with a victim shop's domain.
3. Since `to_signable_string` never includes the shop header, `Utils::HmacValidator.validate` still returns `true`, and `Registry.process` calls the handler with `WebhookMetadata.new(shop: request.shop, ...)` pointing to the victim shop.

### Impact Explanation
This breaks the tenant isolation the HMAC check is meant to guarantee: the gem's own webhook-processing API delivers attacker-controlled body content labeled as coming from an arbitrary shop of the attacker's choosing, to any app built on this library that trusts `WebhookMetadata#shop` (which is the documented and only way to determine the webhook's tenant). This is a cross-tenant access primitive — data intended to be scoped to one merchant's tenant can be forged to appear to originate from another merchant's tenant, purely through this gem's webhook verification logic.

### Likelihood Explanation
Any user who is a merchant with the vulnerable app installed on their own store can independently generate valid `(body, hmac)` pairs (no access to `client_secret` needed — Shopify signs the webhook on delivery), then simply replay the payload with a different `shop-domain` header value to the app's callback URL. No privileged credentials, TLS interception, or social engineering are required, only normal use of a shop that has the app installed and the ability to send an HTTP POST to the app's public webhook endpoint.

### Recommendation
Include the trust-critical headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the signable content used for HMAC verification, or otherwise cryptographically bind the shop identity to the signed payload before it is handed to `WebhookMetadata`. At minimum, `Registry.process` should cross-check `request.shop` against a value derived from data that is actually covered by the HMAC (or against the specific shop session used to register the webhook) before dispatching to the handler.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` and on `victim-shop.myshopify.com`, both using the same app `client_secret`.
2. Attacker triggers an event (e.g. `orders/create`) on `attacker-shop.myshopify.com` with attacker-chosen order data, receiving a webhook POST with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the shared app secret) plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the identical body `B` and header `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Utils::HmacValidator.validate` succeeds because `to_signable_string` only checks body `B` against `H`. [5](#0-4) 
5. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content, even though the actual event never occurred on that shop.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
