### Title
Unbounded, fee-less `handle_unsigned` batches let an unauthenticated submitter force full CPU-cost proof verification on every validating node before rejection - (File: modules/pallets/ismp/src/lib.rs)

### Summary
`pallet_ismp::Call::handle_unsigned` is a `TransactionSource::External`-reachable unsigned extrinsic that anyone can submit with no signature, no fee, and no bound on the size or content of the `messages: Vec<Message>` batch. `ValidateUnsigned::validate_unsigned` for this call fully executes the batch (`Self::execute(messages.clone())`) — running real cryptographic and Merkle/state-proof verification (consensus proofs, request/response/timeout batches) — before deciding whether the transaction is even valid to admit into the pool or propagate.

### Finding Description
`validate_unsigned` for `pallet_ismp` calls `Self::execute(messages.clone())` directly inside transaction-pool validation: [1](#0-0) 

This is the same code path invoked on dispatch: [2](#0-1) 

Because `handle_unsigned` accepts `origin: OriginFor<T>` filtered only by `ensure_none`, and there is no per-batch size/weight bound enforced on `messages` before `execute` runs, an attacker can submit an arbitrarily large batch of `Message::Request`/`Message::Response`/`Message::Timeout`/`Message::Consensus` entries, each of which triggers real proof verification (state/storage-trie membership/non-membership proofs, BEEFY/SP1/sync-committee/GRANDPA/BSC/Tendermint/Pharos consensus verification depending on the runtime) inside `execute`, *before* the pool can reject the transaction for an invalid proof. The declared extrinsic weight is a static constant unrelated to the batch content: [3](#0-2) 

so weight-based spam throttling in `frame_system`/transaction-pool priority does not reflect the real cost of validating the batch. Every node that receives this unsigned transaction over the network — not just the block author — must run `validate_unsigned` (and therefore `execute`, including all embedded proof verification) to decide whether to admit/propagate it, and this happens repeatedly across the transaction's `longevity: 25`-block lifetime as the pool revalidates on each new block, at zero cost to the submitter. This mirrors the Grafana CVE-2021-27358 pattern: an unauthenticated caller reaches a "commonly configured" code path (`handle_unsigned` is intentionally exposed so "anyone" can relay messages for free, per the pallet's own doc comment) that performs expensive server-side work disproportionate to any cost borne by the caller.

### Impact Explanation
A single unauthenticated, fee-less actor can repeatedly submit large/expensive `handle_unsigned` batches (e.g. many `Get`/`Post` requests each carrying storage proofs, or oversized consensus/fraud proofs) that every full node and collator on the network must cryptographically verify during mempool validation and gossip propagation, at no cost to the attacker. Because verification cost scales with attacker-supplied proof/batch content while runtime weight accounting for this call is static, this can degrade block production and node responsiveness network-wide — a Medium/High denial-of-service against the message-dispatch path that every relayer, token bridger, and application depends on for cross-chain delivery.

### Likelihood Explanation
Likelihood is high in principle: no signature, no fee, no admin permission is required to submit `handle_unsigned`, and the call is explicitly designed to be free ("This allows users execute ISMP datagrams for free. Use with caution."). The only friction is the cost of crafting proof-shaped payloads large/expensive enough to matter, and extrinsic/block size limits, but nothing in the reviewed code bounds batch size or ties declared weight to actual verification cost before the fee handler runs post-execution.

### Recommendation
- Enforce a hard cap on the number/size of messages accepted per `handle_unsigned` batch before any proof verification is attempted in `validate_unsigned`.
- Perform cheap, bounded pre-checks (e.g., proof size limits, message count limits, consensus-state existence) prior to invoking the expensive `execute`/proof-verification path, so `validate_unsigned` can reject malformed/oversized batches without paying the full verification cost.
- Make the declared `#[pallet::weight(...)]` for `handle_unsigned` scale with the actual batch size/content (or at least an upper bound derived from batch length) rather than a fixed constant, so pool priority/weight accounting reflects real cost.
- Consider rate-limiting or requiring a bond/stake for `handle_unsigned` submissions from unknown sources at the transaction-pool level.
