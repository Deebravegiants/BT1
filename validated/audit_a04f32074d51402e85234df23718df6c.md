### Title
Webhook shop identity not bound to HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` (and `topic`/`webhook_id`) values used to identify the tenant and dispatch the payload are read from HTTP headers that are never included in the signed content. An attacker who controls any shop with the target app installed can capture one legitimately-signed webhook (signed with the app's single, shop-independent `client_secret`) and resend it to the app's webhook endpoint with the `x-shopify-shop-domain` header swapped to a victim shop, and the library will accept it as a message about the victim's store.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`. For `Webhooks::Request`, that method returns only the raw body: [1](#0-0) 

but the `shop`, `topic`, and `webhook_id` accessors, which are the values actually used by the gem to identify the tenant and route the payload, are pulled straight from unauthenticated headers: [2](#0-1) 

`Registry.process` checks only the HMAC of the body, then hands the unauthenticated `shop` value straight to the caller's handler: [3](#0-2) 

The `client_secret` used to compute this HMAC is the app's single secret shared across every shop that has the app installed — it is not shop-specific. This is the same bug class as the report: a value that is *acted upon* (here, the tenant-identifying `shop` header, analogous to `agentBalance` being used instead of the bound value `record.shares`) is not the value that is *covered by the authenticator* (the HMAC only binds `raw_body`, not `shop-domain`). The identity binding that should hold is:

`shop_header_used_for_tenant_dispatch == shop_that_actually_produced_the_HMAC-verified_bytes`

but nothing enforces this equality.

### Impact Explanation
Because the app's `client_secret` is constant across all shops, any unprivileged user who installs the app on their own shop (a completely legitimate, low-privilege action) can trigger a real webhook event and capture a validly-signed `(raw_body, hmac)` pair. They can then replay that exact body/signature to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) header to claim it originated from a different, victim shop. `Registry.process` will validate the HMAC successfully (it only checks the body) and dispatch the payload to the handler tagged with the attacker-chosen `shop`, causing the host application to process/store data as if it came from the victim tenant. This is a cross-tenant identity-binding bypass reachable by any user of the multi-tenant app, without needing the victim's credentials.

### Likelihood Explanation
High: no special access is required beyond installing the target app on an attacker-controlled shop (a normal, unprivileged action for any Shopify merchant), and standard tools can capture and replay HTTP requests with modified headers.

### Recommendation
Bind the tenant-identifying fields into the signed content, or otherwise cryptographically tie `shop-domain` to the verified bytes, e.g. include `shop`, `topic`, and `webhook_id` in the HMAC computation (mirroring how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop` in its signable string), or require callers to cross-check `request.shop` against an already-established session/shop registered for that app before trusting it in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), receiving a POST with body `B` and header `x-shopify-hmac-sha256: H` where `H = HMAC(client_secret, B)`.
2. Attacker resends the identical `B`/`H` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` succeeds because it only checks `H` against `B` (`request.rb` line 36-38, `hmac_validator.rb` lines 26-31).
4. `Registry.process` dispatches `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` to the handler [4](#0-3) , causing the host application to act on behalf of the victim shop using attacker-supplied data.
