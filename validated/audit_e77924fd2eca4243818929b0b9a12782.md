## Title
Webhook shop-domain (and topic/webhook-id) header is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw request **body only**, while the `shop-domain`, `topic`, `api-version`, and `webhook-id` values are read from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then dispatches the handler using these header-derived, unsigned values as the tenant identity. This breaks the intended binding `shop_that_signed_body == shop_dispatched_to_handler`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from request headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the body) against the HMAC header, so it never inspects `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to build the dispatched metadata: [4](#0-3) 

Because the app's `api_secret_key` is shared across **all** shops that install the app, any shop with a legitimate install can trigger a real webhook (a valid `raw_body` + valid HMAC), capture it, and resend it to the app's webhook endpoint with an attacker-chosen `X-Shopify-Shop-Domain` (and/or topic/webhook-id) header. The HMAC still validates because it never covers those header fields, and the handler is invoked believing the event originated from an arbitrary victim shop.

This is exactly the bug class from the referenced report: a value that is *acted on* (here, the tenant identity used to route/process the webhook) is not covered by the authentication check (here, the HMAC), so the check answers permissively for a forged binding.

### Impact Explanation
This allows cross-tenant webhook spoofing: an unprivileged merchant/attacker who only has their own legitimate install of the app can make the app process fabricated events (e.g. `app/uninstalled`, `shop/update`, `orders/create`, GDPR `customers/data_request`) under a victim shop's identity, since `WebhookMetadata#shop` is taken verbatim from the unauthenticated header. Depending on how the consuming application's handler acts on `shop` (data writes, uninstall flows, entitlement changes), this can lead to cross-tenant data corruption or state changes — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any existing app install (a normal, unprivileged merchant) can generate a validly-HMAC-signed webhook body for themselves at will (by performing an action that triggers a subscribed webhook), then replay that raw body+HMAC to the app's public webhook endpoint with a forged shop header. No secret material beyond the ability to install the app (routine, low-privilege) is required, making this straightforward to reproduce.

### Recommendation
Include the tenant-identifying and routing fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable string, or otherwise cryptographically bind them to the body (e.g., by validating that they match a shop/session already known and expected by the consuming app, or by having `to_signable_string` concatenate the header values with the body before hashing, matching a documented, versioned wire format). At minimum, document clearly that consumers must independently corroborate `WebhookMetadata#shop` against a shop they already have a session for before trusting the payload.

### Proof of Concept
1. App merchant `shop-a.myshopify.com` performs an action that fires a subscribed webhook (e.g. `orders/create`) to the app's endpoint. The attacker (the merchant of shop-a, or anyone able to intercept their own outbound traffic) captures the raw POST body and the `X-Shopify-Hmac-Sha256` header — both valid, since Shopify itself computed them with the app's `api_secret_key`.
2. Attacker resends the exact same body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com` (the victim shop) instead of `shop-a.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Utils::HmacValidator.validate(request)` succeeds because it only checks the (unmodified) body against the HMAC:
`lib/shopify_api/webhooks/registry.rb:190`.
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, where `request.shop` now returns `"shop-b.myshopify.com"` even though shop-b never sent this webhook — successfully spoofing a webhook as belonging to a different tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac

        end
