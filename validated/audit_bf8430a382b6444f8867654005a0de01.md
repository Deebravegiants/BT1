### Title
Webhook `shop` domain is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` authenticates the *body bytes* but never binds the `shop` identity (the `x-shopify-shop-domain`/`shopify-shop-domain` header) to the signature. Any entity capable of installing the app on one shop (i.e., any Shopify merchant/unprivileged internet user) can capture a legitimately-signed webhook for their own store and replay it against the app's webhook endpoint with the shop-domain header rewritten to a victim shop. The signature still validates because it never covered that header, letting `ShopifyAPI::Webhooks::Registry.process` hand the attacker-chosen `shop` to the app's handler as if it were authenticated.

### Finding Description
`Registry.process` verifies authenticity purely via: [1](#0-0) 

The HMAC check delegates to `HmacValidator.validate`, which computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For webhook requests, `to_signable_string` is defined as just the raw body, while `shop` is read from an independent, unsigned header: [3](#0-2) 

Because `hmac` is computed only over `@raw_body` and `shop` is pulled from `shopify-shop-domain`/`x-shopify-shop-domain` with no cryptographic tie to that signature, the equality the app relies on — *"HMAC-authenticated request" == "request legitimately originating for this `shop`"* — does not actually hold. `Registry.process` then forwards the attacker-controlled `shop` straight to the handler: [1](#0-0) 

Since the app's `api_secret_key` is one shared secret for the whole app (not per-shop), any shop that has installed the app can produce a validly-signed body/HMAC pair for that body. Swapping only the `shop-domain` header before replaying the request to the app's public webhook endpoint preserves a valid signature while attributing the payload to an arbitrary victim shop.

### Impact Explanation
This breaks the tenant boundary the gem's webhook API is documented to provide: `WebhookMetadata.shop` is supposed to identify which merchant's data a webhook body pertains to. An attacker who installs the app on their own store can forge webhooks that are processed as if they came from any other installed shop, leading to cross-tenant data corruption/injection in any host application that keys its business logic (order/product updates, mandatory GDPR webhooks, uninstall handling, etc.) off `data.shop` — a Critical-severity cross-tenant access issue.

### Likelihood Explanation
Requires only: (1) installing the app for free on an attacker-controlled shop (trivial, unprivileged), (2) triggering one webhook to capture a valid `(body, hmac)` pair, (3) POSTing that same body/hmac to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header. No secrets, tokens, or privileged access are needed — high likelihood.

### Recommendation
Bind the shop identity into the signed payload verification, e.g. include the `shop` (and other identifying headers such as `topic`/`webhook-id`) in the value that is HMAC-verified, or otherwise cryptographically tie the header set to the body (such as verifying the shop against a per-shop stored session/secret rather than trusting the header verbatim). At minimum, document that `data.shop` from `Registry.process` is not covered by the HMAC and must not be trusted as an authenticated tenant identifier without an additional lookup (e.g., confirming the shop has a stored, previously-authorized session before acting on webhook content).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, a legitimate installation obtainable by anyone.
2. Attacker triggers any webhook subscription (e.g., `orders/create`) and captures the raw POST: body `B` and header `x-shopify-hmac-sha256: H`, where `H = Base64(HMAC-SHA256(api_secret_key, B))`.
3. Attacker resends the exact same body `B` and header `H` to the app's public webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)` — identical to `H` since `B` is unchanged — and returns `true`. [4](#0-3) 
5. `Registry.process` invokes the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker's parsed body>, ...)`, even though the payload never originated from that shop. [5](#0-4)

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
