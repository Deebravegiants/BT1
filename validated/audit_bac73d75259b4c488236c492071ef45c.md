Audit Report

## Title
Cheap, source-unbounded HRMP notification spam can fill a victim para's `InboundDownwardQueue` to the hard `dmq_max_length` cap, DoS-ing legitimate DMP delivery to that para - (File: polkadot/runtime/parachains/src/dmp.rs)

## Summary
`can_queue_downward_message` enforces a purely message-count-based hard cap (`dmq_max_length`, derived only from `MAX_POSSIBLE_ALLOCATION / max_downward_message_size`) on a para's downward message queue, with no accounting for actual bytes queued. [1](#0-0)  Because HRMP channel-management notifications (`HrmpNewChannelOpenRequest`, `HrmpChannelClosing`) are queued through the exact same `queue_downward_message` path as any other downward message, and `hrmp_init_open_channel`/`hrmp_cancel_open_request` allow an attacker-controlled para to cheaply and repeatedly generate such notifications toward an arbitrary victim para with a fully refundable deposit and no cooldown, an attacker can consume queue slots up to the hard cap and cause subsequent legitimate messages to that victim to be rejected with `ExceedsMaxQueueSize`.

## Finding Description
`Pallet::can_queue_downward_message` rejects a message only on size (`max_downward_message_size`) or on the hard count check `dmq_length(*para) > dmq_max_length(...)`, where `dmq_max_length` is a fixed constant unrelated to actual bytes queued. [1](#0-0) [2](#0-1)  Every enqueued message — a full-size XCM payload or a tiny HRMP notification — consumes the same "slot" toward this cap, and `queue_downward_message` only raises the `DeliveryFeeFactor` (a fee applied to *future* senders, not a rejection of the current message) once a threshold is crossed. [3](#0-2) 

`init_open_channel` sends `HrmpNewChannelOpenRequest` to the recipient via the notification path, gated only by the sender's own outbound-channel-count limits, not by anything protecting the recipient's queue. [4](#0-3)  `cancel_open_request` removes the pending request and fully unreserves the deposit with no notification cost or cooldown, allowing immediate re-triggering of the same `(origin, recipient)` open request. [5](#0-4)  `close_channel` similarly queues an `HrmpChannelClosing` notification once per channel closed. [6](#0-5) 

The described root cause — a count-based, size-agnostic hard cap with no per-sender/per-notification throttle — is accurately reflected in the code as written, and the module's own doc comment confirms the design intent is solely to prevent OOM via a message-count-based threshold/fee-factor mechanism, not to defend against a determined low-cost spammer. [7](#0-6) 

## Impact Explanation
If an attacker sustains enough queued notifications to push `dmq_length(victim)` above `dmq_max_length(max_downward_message_size)`, subsequent `queue_downward_message` calls targeting that para — including legitimate governance/XCM traffic — fail with `ExceedsMaxQueueSize`, denying downward delivery to that specific para until it drains its queue. [8](#0-7)  This is a real, in-scope, per-para denial-of-service vector reachable purely through HRMP pallet extrinsics without XCM sends or governance privileges.

## Likelihood Explanation
Practical feasibility is materially constrained by mechanics not fully addressed in the original claim: the victim's queue is continuously drained as its collators process downward messages each relay-parent (the "advancement rule" forces processing of at least one message per block when the queue is non-empty [9](#0-8) ), and generating each HRMP init/cancel cycle itself requires the attacker's own para to have its extrinsic included and its resulting UMP notification delivered through the relay chain, bounding the achievable spam rate per block. To actually overwhelm `dmq_max_length` (a potentially large constant derived from `MAX_POSSIBLE_ALLOCATION / max_downward_message_size`), the attacker must sustain a notification-generation rate that outpaces the victim's normal message-processing rate over many blocks — a materially harder bar than merely "looping calls," and one the claim does not quantify or demonstrate empirically. The underlying design characteristic (count-based cap independent of message size, no dedicated notification throttle) is real, but the claim overstates likelihood by treating the queue as static/unconsumed rather than continuously drained by an honest victim collator, which the protocol assumes and incentivizes.

## Recommendation
Track cumulative queued bytes per para (not just message count) so `dmq_max_length` reflects actual memory pressure, and/or add a per-sender or per-notification-type rate limit/cooldown on `hrmp_init_open_channel`/`hrmp_cancel_open_request`/`hrmp_close_channel` to prevent rapid open/cancel cycling from being used purely to grow another para's DMQ, and/or reserve a portion of the queue capacity for non-notification system messages.

## Proof of Concept
As described in the submission: in a mock runtime with a small `max_downward_message_size`/`MAX_POSSIBLE_ALLOCATION` ratio (small `dmq_max_length`), register victim para `V` and attacker para `A`; loop `hrmp_init_open_channel(A, V, ...)` followed by `hrmp_cancel_open_request(A, {sender: A, recipient: V})`, asserting `Dmp::dmq_length(V)` increases by 1 per cycle (without corresponding drain, i.e., without advancing blocks/processing messages between calls) until `dmq_length(V) == dmq_max_length(...)`; then assert a subsequent `Dmp::queue_downward_message(&config, V, msg)` returns `Err(QueueDownwardMessageError::ExceedsMaxQueueSize)`. Note this PoC as described operates within a single/few blocks without the victim draining its queue between cycles, which does not fully represent the multi-block, contested-throughput conditions a real attack would face against an honest, continuously-processing victim collator.

//! To prevent Out of Memory errors on the `DownwardMessageQueue`, an
//! exponential fee factor (`DeliveryFeeFactor`) is set. The fee factor
//! increments exponentially after the number of messages in the
//! `DownwardMessageQueue` passes a threshold. This threshold is set as:
//!
//! ```ignore
//! // Maximum max sized messages that can be send to
//! // the DownwardMessageQueue before it runs out of memory
//! max_messages = MAX_POSSIBLE_ALLOCATION / max_downward_message_size
//! threshold = max_messages / THRESHOLD_FACTOR
//! ```
//! Based on the THRESHOLD_FACTOR, the threshold is set as a fraction of the
//! total messages. The `DeliveryFeeFactor` increases for a message over the
//! threshold by:
//!
//! `DeliveryFeeFactor = DeliveryFeeFactor *
//! (EXPONENTIAL_FEE_BASE + MESSAGE_SIZE_FEE_BASE * encoded_message_size_in_KB)`
//!
//! And decreases when the number of messages in the `DownwardMessageQueue` fall
//! below the threshold by:
//!
//! `DeliveryFeeFactor = DeliveryFeeFactor / EXPONENTIAL_FEE_BASE`
//!
//! As an extra defensive measure, a `max_messages` hard
//! limit is set to the number of messages in the DownwardMessageQueue. Messages
//! that would increase the number of messages in the queue above this hard
//! limit are dropped.

		config: &HostConfiguration<BlockNumberFor<T>>,
		para: &ParaId,
		msg: &DownwardMessage,
	) -> Result<(), QueueDownwardMessageError> {
		let serialized_len = msg.len() as u32;
		if serialized_len > config.max_downward_message_size {
			return Err(QueueDownwardMessageError::ExceedsMaxMessageSize);
		}

		// Hard limit on Queue size

		if !paras::Heads::<T>::contains_key(para) {
			return Err(QueueDownwardMessageError::Unroutable);
		}

		Ok(())
	}

	pub fn queue_downward_message(
		config: &HostConfiguration<BlockNumberFor<T>>,
		para: ParaId,
		msg: DownwardMessage,
	) -> Result<(), QueueDownwardMessageError> {
		let serialized_len = msg.len();
		Self::can_queue_downward_message(config, &para, &msg)?;

		let inbound = InboundDownwardQueue::<T>::push_back(para, msg)
			.map_err(|_| QueueDownwardMessageError::ExceedsMaxQueueSize)?;
		let q_len = InboundDownwardQueue::<T>::len(para).unwrap_or(0);

		// obtain the new link in the MQC and update the head.
		DownwardMessageQueueHeads::<T>::mutate(para, |head| {
			let new_head =
				BlakeTwo256::hash_of(&(*head, inbound.sent_at, T::Hashing::hash_of(&inbound.msg)));
			*head = new_head;
		});

		let threshold =
			Self::dmq_max_length(config.max_downward_message_size).saturating_div(THRESHOLD_FACTOR);
		if q_len > threshold as u64 {
			Self::increase_fee_factor(para, serialized_len as u128);
		}

		Ok(())
	}
