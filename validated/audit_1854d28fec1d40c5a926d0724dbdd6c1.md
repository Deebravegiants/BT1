### Title
Webhook shop-tenant identity not bound by HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, then hands the caller-supplied `shop-domain` header straight to the app's handler as the tenant identifier. Because the HMAC signature never covers the `shop`, `topic`, or `webhook-id` headers, any request bearing a *valid* `(body, hmac)` pair can be replayed with an arbitrary `X-Shopify-Shop-Domain` header and will be processed by the app as if it originated from that (potentially victim) shop — a cross-tenant identity-binding failure analogous to the QUIC report's pattern of trusting unvalidated/unbound fields.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, and `webhook_id` are read verbatim from attacker-controllable HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (i.e., the body) against the secret-derived HMAC: [3](#0-2) 

`Registry.process` performs no additional binding check — once the HMAC over the body passes, it forwards `request.shop` directly into `WebhookMetadata` and invokes the app's handler: [4](#0-3) 

The equality that should hold but does not is:

`shop_used_by_handler == shop_covered_by_hmac`

Here, `shop_covered_by_hmac` is undefined (the signature only covers the body), so `request.shop` is trusted purely on the strength of the `X-Shopify-Shop-Domain` header, which is attacker-controlled input, not an authenticated claim.

### Impact Explanation
An attacker who legitimately installs the target app on their own store (an "unprivileged" tenant relative to other merchants) will receive real, correctly-HMAC-signed webhooks for events they trigger in their own shop (e.g., `orders/create` with attacker-chosen order content). Because the signature never binds `shop-domain`, the attacker can replay that same `(body, hmac)` pair to the app's webhook endpoint while substituting a victim shop's domain in the `X-Shopify-Shop-Domain` header. The gem will report the webhook as valid, and the app's `WebhookMetadata` will be constructed with `shop: <victim-shop>` and the attacker's body, causing the host application to process attacker-controlled data under another tenant's identity — cross-tenant data injection/confusion, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any app developer who installs the app on a shop they control can trivially obtain a valid signed webhook body/HMAC pair for arbitrary attacker-chosen body content (any webhook topic whose payload is influenced by data the attacker controls, e.g. order notes, product titles, customer fields), then replay it with a forged shop-domain header — no access to `client_secret` or privileged credentials is required, only normal use of the app as an installed merchant.

### Recommendation
Bind the tenant/topic identity into the authenticated material: either (a) include `shop-domain`, `topic`, and `webhook-id` in the HMAC-signed string alongside the body (matching what Shopify actually signs, if it differs), or (b) require callers to independently corroborate `request.shop` against a known/authorized session or shop record before trusting it in `WebhookMetadata`, rather than treating the header as authenticated once the body-only HMAC passes.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) with attacker-controlled JSON body `B`.
2. Capture the real request, including the valid `X-Shopify-Hmac-Sha256` header `H` computed over `B` with the app's real secret.
3. Replay the request to the app's webhook endpoint, keeping `body=B` and `X-Shopify-Hmac-Sha256=H` unchanged, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds because it only recomputes the HMAC over `B`; `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"` and the attacker's body `B`, demonstrating cross-tenant webhook spoofing.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
