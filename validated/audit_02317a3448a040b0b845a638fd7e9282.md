### Title
Webhook `shop-domain` header is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The webhook HMAC signature computed and verified by `ShopifyAPI::Utils::HmacValidator` binds only the raw request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are not part of the signed payload, so any request bearing a genuine `hmac-sha256`/body pair (obtainable from a legitimate webhook delivered to the attacker's own installed shop, since Shopify webhook HMACs are computed with the app's single shared `client_secret`, identical for every shop that installs the app) can have its `shop-domain` header rewritten to name a different, victim tenant, and `Registry.process` will still accept it and hand `WebhookMetadata` with the forged shop to the handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) and the shared `Context.api_secret_key`: [5](#0-4) 

`Registry.process` treats a passing HMAC check as sufficient to trust the whole `Request`, including `request.shop`, which is then forwarded verbatim into `WebhookMetadata` and passed to the app's handler as the tenant identifier: [4](#0-3) 

The equality that is broken: `shop_authenticated_by_hmac == shop_used_as_tenant_key` is assumed by `Registry.process`, but in reality `shop_authenticated_by_hmac == "any shop whose client_secret matches" (i.e. any shop of this app)` while `shop_used_as_tenant_key == unauthenticated_header_value`. Because Shopify signs webhooks with the app-wide `client_secret` (not a per-shop secret), any merchant who has installed the app can capture one of their own genuine webhook deliveries (valid body + valid `hmac-sha256`), then replay that same body/HMAC pair to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a different shop's domain. The HMAC still validates because it never covered the shop header, so `Registry.process` will call the handler with `WebhookMetadata#shop` set to the spoofed victim domain and the attacker-controlled body.

### Impact Explanation
If the host application relies on `WebhookMetadata#shop` to select the tenant/session/data-store to act on (a standard pattern for host apps built on this SDK, as recommended in `docs/usage/webhooks.md`), the attacker can inject arbitrary attacker-chosen payloads that the app processes as if they originated from a victim shop, corrupting or reading data cross-tenant. This is a cross-tenant access issue rated High/Critical depending on what the webhook handler does with `shop`, since it lets an unprivileged (but app-installed) user cause the app to attribute forged data to another merchant's tenant without ever needing that merchant's credentials.

### Likelihood Explanation
Likelihood is realistic but requires the attacker to have installed the app themselves (any public app is installable by anyone), then capture one legitimate webhook and replay it with a modified header — no secret material or victim credentials are needed, and no additional tenant-binding check exists anywhere in `Registry.process` or `Request` to catch the mismatch.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the signable string used for `to_signable_string`, or otherwise cryptographically bind them to the HMAC before trusting `request.shop` as a tenant key; alternatively, require the host app to independently verify that the header-derived shop is one that legitimately has this webhook subscribed (e.g., cross-check webhook id/shop pairing via the Admin API) before acting on `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and receives a genuine webhook delivery, e.g. body `{"id":1}"` with header `X-Shopify-Hmac-Sha256: <validHmacForBody>` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `@raw_body` [3](#0-2)  — validation passes.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: {"id"=>1}, ...)` [6](#0-5)  and, if the host app looks up the victim's session/store by this `shop` value, processes attacker-controlled data under the victim tenant's identity.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
