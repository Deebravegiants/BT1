Based on my investigation, here is the analog vulnerability I found — a cross-chain (Tron) intent-gateway variant that lacks the duplicate-input-token guard the main EVM contract has, causing escrow deposit/withdraw count mismanagement analogous to the Xen grant-table `GNTMAP_device_map`+`GNTMAP_host_map` merge followed by a single unmap.

### Title
Duplicate input tokens in `placeOrder` merge escrow into one accounting bucket while `withdraw`/cancel logic still assumes per-leg amounts, corrupting escrow accounting - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) escrows order inputs with `_orders[commitment][token] += reducedInputs[i].amount;` [1](#0-0)  and again on the native/ERC20 branch at [2](#0-1) , with no check rejecting duplicate token entries in `order.inputs`. This mirrors the Xen bug class: two independent "map" operations (two input legs for the same token) are merged into a single counter, while the "unmap" path in `withdraw()` iterates a token list and decrements `_orders[commitment][token] -= amount` per entry [3](#0-2) , without any cross-check that the sum of all decrements for a repeated token matches what was actually escrowed for that specific leg.

### Finding Description
The main branch of the contract (`evm/src/apps/IntentGatewayV2.sol`) already treats this class of bug as a security-relevant regression and explicitly guards against it:
```solidity
if (_orders[commitment][token] != 0) revert InvalidInput();
_orders[commitment][token] = reducedInputs[i].amount;
``` [4](#0-3) 

The accompanying Foundry tests explicitly document that duplicate input/output tokens previously caused **"same-chain partial fills over-release repeated input escrow"** and **"same-chain partial fills prematurely finalize repeated output legs"**: [5](#0-4) [6](#0-5) 

However, the Tron deployment target (`evm/tron/contracts/apps/IntentGatewayV2.sol`) still uses the vulnerable accumulate-in-place pattern with no duplicate-token rejection: [7](#0-6) 

Because escrow is keyed only by `(commitment, token)` and the commitment hash is derived from the full order struct (including duplicate legs), a duplicate-token order collapses into one summed bucket. Downstream consumers of `order.inputs[i]` — including `withdraw()`'s per-entry decrement and same-chain fill/cancel logic that computes proportional releases per input leg — operate on the assumption that each `order.inputs[i]` entry corresponds to an independent, non-overlapping escrow slice. When two legs reference the same token, this assumption is violated: a withdrawal/refund request can reference the same merged bucket multiple times (once per duplicate `WithdrawalRequest.tokens` entry derived from `order.inputs`), and `withdraw()`'s check `if (_orders[body.commitment][token] == 0) revert` only detects a fully-drained bucket — not a bucket that has already been reduced by a peer duplicate leg — permitting a second `_orders[...] -= amount` to underflow-revert *or*, more importantly, permitting proportional partial-release math (analogous to the same-chain `_fillSameChain` logic) to release more of the merged bucket than any single leg represents, exactly the "count mismanagement" pattern from the CVE (map merges two operations, unmap only accounts for one).

### Impact Explanation
An attacker (the order's own user, acting as an unprivileged caller of `placeOrder`) can construct an order with duplicate input token legs. Depending on how the resulting `WithdrawalRequest` is built from `order.inputs` on fill/cancel, this can cause: (1) a full withdrawal path to attempt to decrement the same merged escrow bucket twice, over-releasing tokens beyond what was actually deposited (theft of protocol/other-user funds/insolvency), or (2) legitimate withdrawal to revert unexpectedly (arithmetic underflow) once the bucket is drained by an earlier leg, permanently freezing the user's own escrowed funds since no other withdrawal path can be re-tried for that commitment (the commitment and `_filled` mapping are one-shot). Either outcome is a concrete fund-safety violation reachable from a single `placeOrder` transaction by any unprivileged user — no privileged actor is required.

### Likelihood Explanation
Likelihood is high for the "freeze funds" variant (any user can trivially construct a duplicate-input order and get their own escrow bricked) and moderate for the "over-release" variant, which depends on exactly how the Tron contract's fill/withdrawal path constructs `WithdrawalRequest.tokens` from `order.inputs` (same-chain fill logic mirroring `IntrinsicIntents._fillSameChain` was not confirmed to exist verbatim in the Tron file within the available index, so the precise over-release trigger path could not be fully confirmed from what I could read — this is a gap in my verification).

### Recommendation
Port the duplicate-input-token (and duplicate-output-token) rejection from the main `evm/src/apps/IntentGatewayV2.sol` (`if (_orders[commitment][token] != 0) revert InvalidInput();`) into `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder`, and audit/port the corresponding duplicate-output-token guard in `IntrinsicIntents`-equivalent same-chain fill logic if present in the Tron codebase, so escrow accounting per `(commitment, token)` is always 1:1 with a single input leg.

### Proof of Concept
1. User calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs = [ (USDC, 600), (USDC, 400) ]`.
2. Both legs accumulate into `_orders[commitment][USDC] = 1000` via the unguarded `+=` at [1](#0-0) .
3. On fill/cancel, a `WithdrawalRequest.tokens` array constructed per input leg (mirroring `order.inputs`) contains two `(USDC, ...)` entries.
4. `withdraw()` processes the first `(USDC, 600)` entry, decrementing `_orders[commitment][USDC]` from 1000 to 400, and transferring 600 USDC out [3](#0-2) .
5. Processing the second `(USDC, 400)` entry either succeeds (releasing an extra 400 that should already have been accounted for in the first leg's transfer, depending on how proportional/same-chain release amounts are computed from `order.inputs[i].amount`) or underflows and reverts, permanently bricking the withdrawal for that commitment.

**Note on completeness:** I was unable to locate a Tron-specific same-chain partial-fill implementation analogous to `IntrinsicIntents.sol` in the indexed portion of `evm/tron/contracts/apps/`, so I could not fully trace the exact call site that builds `WithdrawalRequest.tokens` from a duplicate-token `order.inputs` on that chain. If such a file exists but wasn't surfaced by the index, a full source review of `evm/tron/contracts/apps/` (potentially via a Devin session) is needed to confirm the exact exploitation path for the over-release variant versus the freeze-only variant.

        // Validate that order has inputs

        address hostAddr = host();
        // fill out the order preludes

        uint256 inputsLen = order.inputs.length;
        // Use destination-specific protocol fee, fallback to source chain fee if zero
        bytes32 destinationHash = keccak256(order.destination);
        uint256 protocolFeeBps = _destinationProtocolFees[destinationHash];
        if (protocolFeeBps == 0) {
            protocolFeeBps = _params.protocolFeeBps;
        }
        TokenInfo[] memory reducedInputs;
        bytes32 commitment;

        if (protocolFeeBps > 0) {
            reducedInputs = new TokenInfo[](inputsLen);

                    ++i;
                }
            }
