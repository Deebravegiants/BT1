This gem's webhook processing mirrors the report's root cause: a value that is *used* by the application to make authorization/tenant decisions is never covered by the cryptographic check that is supposed to bind it to a specific request.

### Title
Webhook `shop`, `topic`, and `webhook_id` are trusted but excluded from the HMAC binding, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so `Utils::HmacValidator.validate` authenticates the request payload bytes but never binds the `shop-domain`, `topic`, or `webhook-id` headers to that signature.

### Finding Description
`Request#to_signable_string` is defined as simply `@raw_body` [1](#0-0) , and `Registry.process` gates only on that value: `raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)` [2](#0-1) , then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the metadata dispatched to the app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))` [3](#0-2) . Those three values come straight from unauthenticated HTTP headers: `shopify_header("shop-domain")`, `shopify_header("topic")`, and `shopify_header("webhook-id")` [4](#0-3) .

This is the exact bug class described in the reference report: the code returns/acts on a value (`Coinbase` / here, `shop`) that a consumer relies on for identity, while the mechanism meant to guarantee its integrity (the block-context wiring / here, the HMAC) never actually covers it. The binding the library implicitly promises — `HMAC-verified bytes == the shop this webhook is attributed to` — does not hold. Concretely:
- Before: `hmac_valid(raw_body) == true` says nothing about `shop-domain`.
- After an attacker captures one legitimate `(raw_body, hmac)` pair for their own store (trivial — they are a genuine merchant subscribed to the app, so they legitimately receive real webhooks for their own shop) and replays that identical body+HMAC to the app's public webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop, `Utils::HmacValidator.validate` still returns `true` (it never examined the header), and `Registry.process` hands the app's handler a `WebhookMetadata` claiming `shop: <victim shop>` for content that was never actually generated for that shop.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` (the documented, library-provided tenant identifier) to select which merchant's data to update, without separately re-deriving the shop from the signed body content, can be made to attribute attacker-controlled webhook data to a different tenant — a cross-tenant data-integrity/confusion issue, matching the "cross-tenant access" impact bucket.

### Likelihood Explanation
The only requirement is that the attacker install/operate the app on any shop (even a normal merchant install) and receive one real webhook, which is guaranteed since `topic`, `shop-domain`, and `webhook-id` headers are always sent with every dispatched webhook and are never covered by the signature, so no privileged credential or secret leak is required — only a mundane app installation.

### Recommendation
Include `shop-domain`, `topic`, and `webhook-id` (or otherwise bind the shop identity used by `handler.handle`) into the signable string used by `Utils::HmacValidator`, or document/enforce that consuming apps must independently verify the shop against the payload body rather than the `shop` header exposed by `WebhookMetadata`.

### Proof of Concept
1. App installs, and the attacker's own shop `attacker.myshopify.com` receives a legitimate webhook: headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid hmac of body>`, body `{"id":123}`.
2. Attacker replays the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the headers [5](#0-4) ; `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC [6](#0-5) .
4. `Registry.process` invokes the app handler with `shop: "victim.myshopify.com"` even though the payload was never generated for that shop [7](#0-6) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
