### Title
Duplicate-token withdrawals in a single batch collapse to one status/txHash in `PoaBridge.describeWithdrawal`, causing false `completed` reports for unexecuted withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`findMatchingWithdrawal` matches a POA bridge withdrawal status entry solely by `nep141:<near_token_id>` and ignores both the withdrawal's `index` and its amount/destination. When a single NEAR intent transaction contains two or more POA withdrawals of the same token (fully attacker-controllable via the batch `withdrawalParams[]`), every per-index watcher resolves to the *same* array entry, so distinct withdrawals with different outcomes are reported identically.

### Finding Description
The broken equality is: *"the `(status, txHash)` returned for `WithdrawalIdentifier` at index i corresponds to the i-th withdrawal the user actually signed for that route."*

Trace:
- `IntentsSDK.processWithdrawal` / `signAndSendWithdrawalIntent` builds intents for an array of `withdrawalParams` and publishes them as a single NEAR transaction (`intentTx`), fully attacker/integrator-controlled at the API boundary. [1](#0-0) 
- `waitForWithdrawalCompletion` -> `createWithdrawalCompletionPromises` -> `createWithdrawalIdentifiers` assigns a per-bridge-route sequential `index` (0, 1, 2, …) to each `WithdrawalIdentifier`, all sharing the same `intentTx`. [2](#0-1) 
- `PoaBridge.createWithdrawalIdentifier` stores this `index` in the identifier but it is never used afterward for matching. [3](#0-2) 
- `PoaBridge.describeWithdrawal` queries the bridge status API by `tx.hash` (the shared NEAR tx hash) and then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` — matching purely by token, with no use of `index`, amount, or destination address. The code comment itself acknowledges: *"multiple withdrawals of the same token in a single transaction are not supported."* [4](#0-3) [5](#0-4) 

Exploit flow: an unprivileged user/integrator submits a batch containing two POA withdrawals of the same `assetId` (e.g., two withdrawals of `nep141:usdc.omft.near` to two different destination addresses) in one call to `processWithdrawal`/`waitForWithdrawalCompletion`. Both are settled in the same NEAR intent transaction. When watched, both index-0 and index-1 calls to `describeWithdrawal` query the API with the same `tx.hash` and same `assetId` predicate, so `.find()` returns the identical (documented as "unsorted") array entry for both calls. If the bridge has completed the first withdrawal but the second is still pending, refunded, or failed, the watcher for the second withdrawal will nonetheless report `status: "completed"` with the first withdrawal's `txHash`, because both branches read the same matched object.

Existing guards do not prevent this: `validateWithdrawal`/`supports()` validate destination address and token support per individual withdrawal but do not detect or reject duplicate-token withdrawals within a batch; there is no ordering or amount-based disambiguation implemented (the comment notes such an amount-sorting scheme is only a possible *future* improvement, not implemented).

### Impact Explanation
An integrator that credits a user's off-chain balance or releases a downstream payout upon seeing `status: "completed"` for a given withdrawal index will incorrectly credit for a withdrawal that never executed (or is still pending/failed), while the real completed withdrawal's txHash is reported redundantly for both indices. This directly matches the High severity category: "a status or hash misreport making an integrator credit or refund twice." It is repeatable for every batch containing duplicate-token POA withdrawals.

### Likelihood Explanation
Preconditions: a single call to `processWithdrawal`/`signAndSendWithdrawalIntent`/`waitForWithdrawalCompletion` with two or more `WithdrawalParams` sharing the same `assetId` routed through `PoaBridge`. This requires no privilege beyond being a normal SDK caller/integrator forwarding user-controlled withdrawal params — it is not a documented escape hatch, just ordinary batch usage of a publicly exposed feature. Cost to the attacker is a single normal withdrawal batch transaction; the divergence is deterministic whenever the underlying bridge processes the two same-token withdrawals with different outcomes/timing (a very common real-world timing scenario, e.g., one is processed before the other).

### Recommendation
Disambiguate `findMatchingWithdrawal` beyond `assetId`: use the withdrawal's `index` in combination with a stable, order-independent key (e.g., match by `near_token_id` + amount, or by a per-intent uniqueness token if the POA bridge API exposes one), or reject/guard batches containing duplicate-token withdrawals to the same bridge inside `createWithdrawalIdentifiers`/`supports()` until the POA bridge API supports disambiguation, per the code's own acknowledged limitation.

### Proof of Concept
Vitest plan (mock only the PoaBridge HTTP status endpoint):
1. Construct `withdrawalParams = [w0, w1]` both with `assetId = "nep141:usdc.omft.near"`, differing `destinationAddress`, same `intentTx.hash`.
2. Call `createWithdrawalIdentifiers` to get `wid0` (index 0) and `wid1` (index 1) — assert `wid0.index === 0` and `wid1.index === 1`.
3. Mock `poaBridge.httpClient.getWithdrawalStatus` to return `withdrawals: [ { data: { near_token_id: "usdc.omft.near", transfer_tx_hash: "0xAAA" }, status: "COMPLETED" }, { data: { near_token_id: "usdc.omft.near" }, status: "PENDING" } ]` (order representing withdrawal for `w1` still pending while `w0` completed).
4. Call `PoaBridge.describeWithdrawal(wid0)` and `PoaBridge.describeWithdrawal(wid1)`.
5. Assert the broken equality: expect `describeWithdrawal(wid1)` to equal `{ status: "pending" }` (correct expectation) but observe it instead returns `{ status: "completed", txHash: "0xAAA" }` — identical to `describeWithdrawal(wid0)` — demonstrating that index 1's reported status/txHash does not correspond to its actual (pending) underlying withdrawal.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

		args: WithdrawalIdentifier & { logger?: ILogger },

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
