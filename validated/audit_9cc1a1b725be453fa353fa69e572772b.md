### Title
BSC consensus verifier's supermajority check is vacuously satisfied when `current_validators` is empty, allowing forged state-commitment finality - (File: `modules/consensus/bsc/verifier/src/lib.rs`)

### Summary
This mirrors the GovHub `DEFEATED` bug class: a quorum/threshold comparison that is supposed to gate acceptance becomes trivially true once the underlying member/validator set is empty. In `verify_bsc_header`, the BSC supermajority check computes `participant_count < ((2 * current_validators.len()) / 3)`. When `current_validators.len() == 0`, this reduces to `0 < 0`, which is `false`, so the "not enough participants" branch is skipped even though zero validators signed anything.

### Finding Description
The BSC light-client verifier enforces the 2/3 BEP-126 supermajority purely via integer arithmetic on `current_validators.len()`: [1](#0-0) 

There is no explicit `NoParticipants`/`EmptyValidatorSet` guard before this arithmetic, unlike the Pharos verifier, which does check for empty participants before doing signature aggregation: [2](#0-1) 

`current_validators` is stored in `ConsensusState.current_validators: Vec<BlsPublicKey>`, and `ConsensusState` derives `Default`, meaning an empty vector is a syntactically valid, easily reachable state: [3](#0-2) 

`verify_bsc_header` is invoked directly from `BscClient::verify_consensus`, the `ConsensusClient` trait method that any relayer calls by submitting a consensus proof: [4](#0-3) 

If `current_validators` is empty (e.g., through a rotation that stages an empty/near-empty `next_validators.validators` list — note the epoch-header path only checks `!validators.is_empty()` at extraction time but nothing later re-validates size floor before promotion at `consensus_state.current_validators = next_validators.validators;`, or through any state where the client is left with a default/empty set), the supermajority check at line 88 is bypassed. Additionally, `aggregate_public_keys` over zero participants would produce the BLS identity element, and the pairing-based `bls::verify` check against an identity aggregate public key can be satisfied by a correspondingly trivial (identity/point-at-infinity) "signature," which an attacker fully controls since they need not know any real private key. This lets an attacker submit a completely forged `source_header`/`target_header` pair and have it accepted as finalized, injecting an arbitrary `state_root` as a trusted BSC state commitment.

### Impact Explanation
Acceptance of a forged state commitment on a supported EVM state machine is a critical unsound-state-commitment condition: any downstream request/response proof verified against that state root (via `pallet-ismp`/`HandlerV2` state membership proofs) would be forged, enabling unauthorized message delivery, unbacked mint-style actions in token bridges relying on BSC state proofs, or fund theft through fabricated cross-chain messages.

### Likelihood Explanation
Reaching this state requires `current_validators` to become empty or near-empty, which is not attacker-controlled in the ordinary case (validator promotion only occurs from a non-empty `next_validators.validators` extracted from real BSC epoch headers). However, the lack of an explicit floor/guard on `current_validators.len()` — unlike the `MissingValidatorSet`/`EmptyValidatorSet` checks present elsewhere in the codebase (Pharos, Tendermint) — means the threshold math is not robust against this edge case by construction, matching the audited GovHub bug class where the fix was to add an explicit minimum-threshold requirement rather than rely on the vote-ratio arithmetic alone.

### Recommendation
Add an explicit guard in `verify_bsc_header` (and anywhere `current_validators`/`next_validators` are set or promoted) rejecting an empty or below-minimum validator set before computing the supermajority threshold, e.g. `if current_validators.is_empty() { return Err(Error::EmptyValidatorSet) }`, mirroring the `NoParticipants` check already present in the Pharos verifier and the `validate()` checks in the Tendermint primitives (`validators.is_empty()` → error): [5](#0-4) 

### Proof of Concept
1. Reach a state where `ConsensusState.current_validators` is empty (e.g., default/uninitialized consensus state, or a validator-set promotion path that ends up with `Vec::new()`).
2. Craft a `BscClientUpdate` with a `source_header`/`target_header` of choice, matching `vote_data`, and an aggregate signature equal to the BLS identity/point-at-infinity encoding.
3. Call `BscClient::verify_consensus` with this update against the empty-validator-set `ConsensusState`.
4. `participant_count` (0) `< (2*0)/3` (0) evaluates to `false`, bypassing `Error::NotEnoughParticipants`; `aggregate_public_keys(&[])` yields the identity key, and `bls::verify` against the identity key and identity signature succeeds, so the forged `state_root` is committed as finalized BSC state.
