### Title
Webhook shop-domain identity is not bound to the HMAC signature, enabling cross-tenant impersonation - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC that `Registry.process` verifies covers *none* of the identity headers (`shop`, `topic`, `webhook_id`, `api_version`). `Registry.process` nonetheless treats `request.shop` as an authenticated tenant identifier and hands it straight to the app's handler.

### Finding Description
`Utils::HmacValidator.validate` computes and compares an HMAC over `verifiable_query.to_signable_string` only: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be just the raw JSON body — the `shop`, `topic`, `api-version`, and `webhook-id` values are read from separate, unsigned HTTP headers: [2](#0-1) 

`Registry.process` validates only that HMAC-over-body is correct, then unconditionally trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed to the app's handler — there is no cross-check that the shop belongs to the same tenant that produced the signed body: [3](#0-2) 

This is the same bug class as the reported analog: an identity-relevant field (`shop`) is *acted on* by the code but is not *covered by* the cryptographic check that is supposed to authenticate the request. The equality that should hold is:

`shop bound by HMAC == shop used by handler to select tenant/session`

but the actual relationship is:

`shop bound by HMAC == "no shop at all" (only raw body is signed) ≠ shop passed to handler.handle`

Because the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every merchant that installs the app, any merchant who legitimately installs the app receives real Shopify webhooks with a valid body+HMAC pair signed with that shared secret. Such a merchant can replay that exact body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` will invoke the handler with `WebhookMetadata.new(shop: request.shop, ...)` reporting the victim's domain as the source of the event.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as intended by this gem's own API) to look up the tenant/session and perform shop-scoped side effects (writing to a shop's data store, revoking access, processing GDPR redact/data-request payloads, updating billing, etc.), an attacker who is a legitimate installer of the app can forge webhook events attributed to any other shop that also uses the app, without needing that other shop's credentials. This crosses a tenant boundary using only a credential (the shared HMAC secret) that the attacker legitimately possesses through their own installation — matching the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Exploitation requires no privileged secrets beyond what a normal merchant installer already has (a captured webhook delivery to their own endpoint). Forging headers on an HTTP request to the app's own webhook endpoint is trivial. The only prerequisite is that the host application's webhook handler trusts `WebhookMetadata#shop`/`#topic` for tenant identification without independently re-verifying it against its own shop registry — which is exactly the intended, documented use of this field per `Registry.process`'s design (it is the library's job to hand back an authenticated shop).

### Recommendation
Since Shopify signs webhook payloads with an HMAC over the body only (matching the real platform's behavior), the gem cannot unilaterally "fix" the signature scope, but it can:
- Update documentation/comments in `lib/shopify_api/webhooks/request.rb` and `docs/usage/webhooks.md` to explicitly state that `shop`, `topic`, `webhook_id`, and `api_version` are **not** authenticated by the HMAC and must not be treated as a proven tenant identifier and to prompt this to the App developer.
- Consider providing a `WebhookMetadata` note/flag or validation helper that reflects this in the type system.

### Proof of Concept
1. Install the app as `attacker.myshopify.com`.
2. Capture a real webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared `client_secret`).
3. Replay the request to the app's webhook endpoint with the same body `B` and HMAC `H`, but with `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally; `Utils::HmacValidator.validate` returns `true` because it only checks `B` against `H` [4](#0-3) 
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop == "victim.myshopify.com"` [5](#0-4) 
even though the payload actually originated from, and was signed for, `attacker.myshopify.com`.
