Audit Report

## Title
Non-constant-time bearer token comparison on the internet-facing Prometheus metrics endpoint enables timing side-channel attacks - (File: core/web/router.go)

## Summary
The `/metrics` endpoint's bearer-token authentication in `prometheusHandler` compares the client-supplied token against the expected secret using Go's native `!=` string comparison, which short-circuits on the first mismatched byte. Every other secret comparison in the codebase uses `crypto/subtle.ConstantTimeCompare`, making this an inconsistent and vulnerable outlier.

## Finding Description
In `core/web/router.go`, `prometheusHandler` builds `bearer := "Bearer " + token` and checks `if header != bearer` [4](#0-3) . This is registered as the sole auth gate for the metrics route via `e.GET(p.MetricsPath, prometheusHandler(p.Token, h))` [5](#0-4) . Go's `!=` operator on strings performs byte-by-byte comparison that returns early on the first differing byte, creating a timing side channel proportional to the number of correctly-guessed leading bytes. By contrast, `AuthenticateUserByToken`, `AuthenticateExternalInitiator`, and `AuthenticateBridgeType` all correctly use `subtle.ConstantTimeCompare` [2](#0-1) [6](#0-5) [3](#0-2) , demonstrating this endpoint was overlooked when the constant-time pattern was applied elsewhere in the auth-sensitive code paths.

## Impact Explanation
This is an authentication weakness (CWE-697/CWE-208) on the `/metrics` endpoint specifically. Successful exploitation would allow an unauthenticated network attacker to recover the `Prometheus.AuthToken` and gain unauthorized read access to node metrics data. This is real but is a narrow-scope disclosure issue: it does not enable job execution, fund movement, key exfiltration, or node API authentication bypass for the broader web API — only the optional, operator-enabled metrics scraping endpoint is affected.

## Likelihood Explanation
Exploitation requires the operator to have configured `Prometheus.AuthToken` (this feature is opt-in; if unset, the handler bypasses auth entirely and is intentionally open) [7](#0-6) . Practical remote timing-attack extraction of a full token over a network is non-trivial and requires many samples and statistical averaging; feasibility is meaningfully higher on low-latency/local networks than over the public internet, as the report itself acknowledges.

## Recommendation
Replace the `!=` comparison with `subtle.ConstantTimeCompare`, padding for length equality first (mirroring the `constantTimeEmailCompare` pattern already used in `ldap.go`/`oidc.go`):
```go
if subtle.ConstantTimeCompare([]byte(header), []byte(bearer)) != 1 {
    c.String(http.StatusUnauthorized, ginprom.ErrInvalidToken.Error())
    return
}
```

## Proof of Concept
1. Start a node with `Prometheus.AuthToken` set to a known test value.
2. Issue repeated `GET /metrics` requests with `Authorization: Bearer <guess>` headers, incrementally extending a correctly-guessed prefix.
3. Measure response latency across many trials per guessed byte; correct-prefix guesses should show statistically higher average latency due to `!=` short-circuiting later in the comparison.
4. A Go benchmark/unit test directly measuring `prometheusHandler`'s response time for matching-prefix vs. non-matching-prefix tokens (holding total length constant) would demonstrate the timing differential without needing network-level attack infrastructure.
