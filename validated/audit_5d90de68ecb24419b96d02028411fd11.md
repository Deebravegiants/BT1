Audit Report

## Title
Malicious collator can permanently censor specific DMP messages by exploiting the weak `check_enough_messages_included_basic` advancement rule used for the DMQ path - ([File: cumulus/pallets/parachain-system/src/lib.rs] / [File: cumulus/pallets/parachain-system/src/parachain_inherent.rs])

## Summary
`enqueue_inbound_downward_messages` only applies `check_enough_messages_included_basic`, which merely requires one full message to exist whenever any message is hashed, whereas `enqueue_inbound_horizontal_messages` applies the stricter `check_enough_messages_included_advanced`, which requires that hashing only occur when a message truly didn't fit the size budget. This asymmetry lets a malicious collator submit a DMP message as "hashed" (with a correct hash matching the relay-chain MQC) even though it would have fit within the full-message size budget, causing that message's payload to never be dispatched while still being marked as permanently processed.

## Finding Description
`do_create_inherent` is only the honest default block-authoring algorithm calling `into_abridged`; a malicious collator is free to construct any `InboundMessagesData` and submit it via the unsigned (`ensure_none`) `set_validation_data` extrinsic, since it is produced exclusively by the block-authoring collator. The two guards on the submitted DMQ split are: (1) the DMQ MQC head-hash chain check at line 1362, which is agnostic to whether a message is represented as full or hashed since both `extend_downward` and `extend_with_hashed_msg` feed the same chain, and (2) `check_enough_messages_included_basic("DMQ")` at line 1323, which only asserts `full_messages.len() >= 1` and never checks whether hashing a specific message was actually necessary. This is in direct contrast to the `check_enough_messages_included_advanced` check applied to HRMP at lines 1444-1455, which enforces that the full-message byte total plus the max possible size of the first hashed message must exceed the size limit before hashing is legal — and per `prdoc/stable2603/pr_9086.prdoc`, this stricter rule was deliberately scoped only to HRMP ("Make HRMP advancement rule more restrictive"), leaving DMQ on the older, weaker rule.

Because only `full_messages` are dispatched to `T::DmpQueue::handle_messages` via `bounded_msgs_iter`, and hashed messages only advance `LastProcessedDownwardMessage`/the MQC head without executing their payload, a hashed-but-fitting DMP message is permanently treated as processed without ever being delivered, with no re-delivery mechanism.

## Impact Explanation
A malicious or colluding collator can selectively and permanently suppress the execution of arbitrary DMP messages (e.g., governance-originated calls, XCM `Transact`, or reserve-transfer completions) directed at the parachain, while producing an inherent that passes every on-chain check. This matches the censorship scenario explicitly called out in the code's own comment on `check_enough_messages_included_advanced`, but that mitigation was never extended to the DMQ path.

## Likelihood Explanation
The only requirement is control over block authoring for the parachain (i.e., being the collator producing the PoV for a given block) — a standard, expected adversarial capability in the Cumulus threat model, since `set_validation_data` is `ensure_none` and only ever submitted by the collator. No relay-chain collusion, privileged keys, or victim mistakes are required; DMP messages and their content are public on the relay chain, so the collator can always compute the correct hash for the message it wants to suppress. The attack is repeatable every block for any targeted DMP message.

## Recommendation
Apply the same strengthened advancement rule used for HRMP (`check_enough_messages_included_advanced`, or an equivalent size-based check using `messages_collection_size_limit()`) to the DMQ path, replacing the call to `check_enough_messages_included_basic("DMQ")` in `enqueue_inbound_downward_messages`.

## Proof of Concept
Unit test extending `parachain_inherent.rs`'s test module: construct an `AbridgedInboundDownwardMessages` with a 1-byte `full_messages` entry and a large (e.g., 900-byte) `hashed_messages` entry that would have fit under the size limit (e.g., 1000 bytes). Show that `check_enough_messages_included_basic("DMQ")` passes without panicking on this crafted collection, while `check_enough_messages_included_advanced("DMQ", AbridgedInboundMessagesSizeInfo { max_full_messages_size: 1000, first_hashed_msg_max_size: 900 })` panics on the identical data — demonstrating that the DMQ code path (which only invokes the basic check) accepts a split that the HRMP code path (which invokes the advanced check) would reject, confirming that a collator can hash a large, fitting DMP message and have it accepted on-chain, achieving permanent censorship of that message.

	pub fn check_enough_messages_included_advanced(
		&self,
		collection_name: &str,
		size_info: AbridgedInboundMessagesSizeInfo,
	) {
		// We should check that the collection contains as many full messages as possible
		// without exceeding the max expected size.
		let AbridgedInboundMessagesSizeInfo { max_full_messages_size, first_hashed_msg_max_size } =
			size_info;

		let mut full_messages_size = 0usize;
		for msg in &self.full_messages {
			full_messages_size = full_messages_size.saturating_add(msg.data().len());
		}

		// The worst case scenario is that were the first message that had to be hashed
		// is a max size message.
		assert!(
			full_messages_size.saturating_add(first_hashed_msg_max_size) > max_full_messages_size,
			"[{}] Advancement rule violation: full messages size smaller than expected. \
			full msgs size: {}, first hashed msg max size: {}, max full msgs size: {}",
			collection_name,
			full_messages_size,
			first_hashed_msg_max_size,
			max_full_messages_size
		);
	}

	fn enqueue_inbound_downward_messages(
		expected_dmq_mqc_head: relay_chain::Hash,
		downward_messages: AbridgedInboundDownwardMessages,
	) -> Weight {
		downward_messages.check_enough_messages_included_basic("DMQ");

		let mut dmq_head = <LastDmqMqcHead<T>>::get();

		let (messages, hashed_messages) = downward_messages.messages();
		let message_count = messages.len() as u32;
		let weight_used = T::WeightInfo::enqueue_inbound_downward_messages(message_count);
		if let Some(last_msg) = messages.last() {
			Self::deposit_event(Event::DownwardMessagesReceived { count: message_count });

			// Eagerly update the MQC head hash:
			for msg in messages {
				dmq_head.extend_downward(msg);
			}
			<LastDmqMqcHead<T>>::put(&dmq_head);
			Self::deposit_event(Event::DownwardMessagesProcessed {
				weight_used,
				dmq_head: dmq_head.head(),
			});

			let mut last_processed_msg =
				InboundMessageId { sent_at: last_msg.sent_at, reverse_idx: 0 };
			for msg in hashed_messages {
				dmq_head.extend_with_hashed_msg(msg);

				if msg.sent_at == last_processed_msg.sent_at {
					last_processed_msg.reverse_idx += 1;
				}
			}
			LastProcessedDownwardMessage::<T>::put(last_processed_msg);

			T::DmpQueue::handle_messages(downward_messages.bounded_msgs_iter());
		}

		// After hashing each message in the message queue chain submitted by the collator, we
		// should arrive to the MQC head provided by the relay chain.
		//
		// A mismatch means that at least some of the submitted messages were altered, omitted or
		// added improperly.
		assert_eq!(dmq_head.head(), expected_dmq_mqc_head, "DMQ head mismatch");
