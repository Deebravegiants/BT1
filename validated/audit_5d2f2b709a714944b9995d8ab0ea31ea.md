### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing shop-domain spoofing on webhook delivery - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , and `HmacValidator.validate` verifies the HMAC exclusively against that signable string [2](#0-1) . However, `Registry.process` reads `request.shop`, `request.topic`, and `request.webhook_id` — all pulled straight from unauthenticated HTTP headers — and hands them to the app's webhook handler as trusted identity fields [3](#0-2) [4](#0-3) . The `shop-domain` header value is a field acted upon by the handler but not covered by the HMAC that is supposed to authenticate the whole request.

### Finding Description
The identity binding that should hold is:

`shop covered by HMAC == shop delivered to WebhookMetadata.shop`

Before the request sequence: a legitimate webhook for shop A has `raw_body_A` and `hmac(raw_body_A, secret)`; a webhook for shop B has `raw_body_B` and `hmac(raw_body_B, secret)`. `raw_body` itself typically does not repeat the shop domain in a way the handler is guaranteed to cross-check, and the class explicitly excludes headers from the signed material — only `@raw_body` is signed [1](#0-0) .

Attack sequence: an attacker who can obtain any one valid `(raw_body, hmac)` pair (e.g., by installing the app on their own store and capturing a legitimate webhook delivery, since webhook secrets/HMACs are not scoped per-shop but derived from the app's single `api_secret_key`) can replay that exact body and HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` recomputes the HMAC over `@raw_body` only, so it still succeeds [5](#0-4) . `Registry.process` then invokes the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, attributing an attacker-controlled `shop` value to data that only the raw body's HMAC actually vouched for [6](#0-5) .

After the request: the app's webhook handler, which typically uses `shop` to key session lookup, tenant-scoped data updates, or state changes, now operates against the victim shop's tenant using data that was never actually authenticated for that shop.

Root cause is exactly analogous to the ECDSA report's bug class: a value used to make a security-relevant decision (`shop`) is not included in the bytes covered by the cryptographic check (`HmacValidator` only signs `@raw_body`), so the binding between "what was authenticated" and "what is acted upon" is broken.

### Impact Explanation
If a host application's webhook handler uses `data.shop` (from `WebhookMetadata`) to determine which tenant's records to read, write, or delete — a documented and expected usage pattern per this gem's webhook API — an attacker can forge the shop attribution of an HMAC-valid webhook payload and cause cross-tenant data operations. This matches the Critical impact category: cross-tenant access, since it lets one merchant's webhook traffic be misattributed to another merchant's tenant boundary purely by manipulating an unauthenticated header.

### Likelihood Explanation
Exploitability requires the attacker to obtain at least one valid `(raw_body, hmac)` pair, which is trivial for any developer/merchant who installs the target app on their own store (a normal, unprivileged action for public apps) and captures a webhook delivery. No `api_secret_key`, access token, or privileged account is needed — only the ability to receive one webhook from their own installation and then send a crafted HTTP POST to the app's public webhook endpoint with a different `shop-domain` header.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-covered signable string, or independently verify `request.shop` against a value that is cryptographically bound to the payload (e.g., validate that the shop header matches the shop encoded/expected for that specific webhook subscription) before passing it to the handler in `Registry.process`.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger any webhook event and capture the raw POST body and the `x-shopify-hmac-sha256` header Shopify sends.
2. Replay this exact body and HMAC header to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `HmacValidator.validate` succeeds because it checks only `@raw_body` against the HMAC [7](#0-6) [2](#0-1) .
4. `Registry.process` calls the registered handler with `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing any tenant-keyed logic in the handler to operate on the victim's tenant using attacker-supplied data.
