Audit Report

## Title
CORS wildcard origin allowlist bypass via unanchored suffix match - (File: core/services/gateway/network/httpserver.go)

## Summary
The Gateway HTTP server's `isAllowedOrigin` function checks a wildcard-configured origin allowlist entry (e.g. `*.ethereum.org`) by stripping the `*.` prefix and testing `strings.HasSuffix(originHost, allowedHost)`, with no requirement that the match be preceded by a `.` boundary. As a result, an attacker-registered domain like `evilethereum.org` satisfies the suffix check even though it is not a subdomain of `ethereum.org`, causing the attacker's origin to be reflected in `Access-Control-Allow-Origin`.

## Finding Description
In `isAllowedOrigin` [1](#0-0) , the wildcard branch strips `*.` from the configured allowed host and then performs a raw `strings.HasSuffix` comparison without checking for a preceding `.` or requiring the matched suffix to be a proper label boundary. `handleRequest` then reflects the raw `Origin` header value into the `Access-Control-Allow-Origin` response header whenever `isAllowedOrigin` returns true [2](#0-1) . There is no other validation, normalization, or boundary check applied between the suffix comparison and the CORS header being set, so this is the sole gate protecting the wildcard-configured domains. Exact-match entries (`originHost == allowedHost`) are unaffected, but wildcard entries are vulnerable exactly as described: `strings.HasSuffix("evilethereum.org", "ethereum.org")` evaluates to `true`.

## Impact Explanation
An operator configuring `CORSAllowedOrigins: ["*.ethereum.org"]` intends to permit only genuine subdomains of `ethereum.org`. Due to the missing `.` boundary check, any attacker who registers a domain ending in the same string (e.g., `evilethereum.org`, `notethereum.org`) can have their origin accepted and reflected back in `Access-Control-Allow-Origin`. This is a legitimate CORS allowlist bypass / origin impersonation bug — falling under the "gateway request impersonation / allowlist bypass" impact category — because it allows an attacker-controlled site to be treated as a trusted cross-origin caller of the Gateway's HTTP API, enabling credentialed cross-origin reads that the operator's allowlist was meant to prevent.

## Likelihood Explanation
Exploitation requires only that (1) the Gateway operator has enabled CORS with a wildcard entry — a documented, supported configuration exercised in the existing test suite (`TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards`, `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards`) — and (2) the attacker registers a domain string that happens to end with the allowed suffix without a dot separator. No authentication, credentials, or privileged access to the Gateway are needed by the attacker to trigger the flawed comparison itself; the request is a plain unauthenticated HTTP request with a crafted `Origin` header. The existing test `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` even demonstrates the intended behavior for a similar case (`https://ethereum.remix.org` correctly rejected because it doesn't end with `ethereum.org`), but does not cover the boundary-violating case (a domain that ends with `ethereum.org` but isn't a dot-separated subdomain, e.g. `evilethereum.org`), confirming the gap is untested and present in the shipped logic.

## Recommendation
Anchor the wildcard suffix comparison to a label boundary:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```
This ensures only exact matches or true dot-separated subdomains of the configured wildcard base are accepted.

## Proof of Concept
1. Start the Gateway HTTP server with `CORSEnabled: true` and `CORSAllowedOrigins: []string{"https://*.ethereum.org"}` (as in `startNewServer` helper in `core/services/gateway/network/httpserver_test.go`).
2. Send a POST request to the server with header `Origin: https://evilethereum.org`.
3. Observe that `isAllowedOrigin` returns `true` because `strings.HasSuffix("evilethereum.org", "ethereum.org")` is `true`, and the response contains `Access-Control-Allow-Origin: https://evilethereum.org`.
4. Add a Go unit test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` asserting that origin `https://evilethereum.org` (no dot before `ethereum.org`) is rejected — this test would fail against current code, confirming the vulnerability.
