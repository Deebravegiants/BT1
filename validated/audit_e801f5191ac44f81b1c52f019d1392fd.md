Confirmed: the panic path is explicit and intentional, not an unhandled crash bug — but it is a real chunk-apply panic if the overflow condition is ever reached.

### Title
`RuntimeError::UnexpectedIntegerOverflow` from congestion accounting deliberately panics chunk application instead of gracefully rejecting - (File: chain/chain/src/runtime/mod.rs)

### Summary
`CongestionInfo::add_receipt_bytes`/`add_delayed_receipt_gas` use `checked_add` and return `RuntimeError::UnexpectedIntegerOverflow` on failure, which is exactly the mechanism designed to prevent silent overflow. However, the call site that consumes `Runtime::apply`'s result explicitly converts this error into a `panic!`, with a `TODO(#2152): process gracefully` comment acknowledging this is not the desired long-term behavior. This is a known, marked limitation rather than an undiscovered bug, and reaching the overflow itself is not practically achievable by an unprivileged attacker within realistic gas/storage economics.

### Finding Description
`CongestionInfo::add_receipt_bytes` and `add_delayed_receipt_gas` guard against overflow with `checked_add`, returning `RuntimeError::UnexpectedIntegerOverflow` on failure [1](#0-0) [2](#0-1) . These are invoked from `DelayedReceiptQueueWrapper::push`/`pop` (which accumulate gas/bytes into local counters, themselves protected by `checked_add` returning `IntegerOverflowError`) and later applied via `apply_congestion_changes` [3](#0-2) [4](#0-3) [5](#0-4) .

At the top-level `Runtime::apply` call site in `chain/chain/src/runtime/mod.rs`, the `RuntimeError` returned is explicitly matched, and `UnexpectedIntegerOverflow` is turned into a `panic!`, annotated with `// TODO(#2152): process gracefully`: [6](#0-5) 

So yes — if the overflow were ever reached, chunk application panics rather than being handled gracefully. However:

1. `receipt_bytes` is `u64` and `delayed_receipts_gas`/`buffered_receipts_gas` are `u128` [7](#0-6) . Gas values are bounded per-chunk by the protocol gas limit (hundreds of Tgas ≈ 10^14), and even accumulating across a very large number of chunks, reaching `u128::MAX` (~3.4×10^38) via legitimate receipt gas accumulation is computationally infeasible — it would require far more chunks than the chain could ever produce.
2. `receipt_bytes` is `u64` (max ~1.8×10^19 bytes), and each receipt is bounded by `max_receipt_size` from bandwidth scheduler config, with buffered/delayed queues themselves bounded by congestion control's rejection thresholds (`reject_tx_congestion_threshold` in `shard_accepts_transactions`) which reject new transactions to a shard once congestion is high, preventing unbounded queue growth [8](#0-7) .
3. Congestion admission gates (`ClampOutgoingGasAdmission`, outgoing/incoming congestion fractions used to reject transactions) actively throttle new receipt admission long before gas/byte sums could approach integer limits, since congestion levels are computed as fractions of `max_congestion_incoming_gas`/`max_congestion_outgoing_gas`, which are themselves bounded, sane configuration constants far below `u128`/`u64` limits.

Thus, while the panic-on-overflow code path exists and is a real, currently-accepted trade-off (tracked by issue #2152), an unprivileged attacker submitting maximal-size transactions cannot practically drive `receipt_bytes`/`delayed_receipts_gas` to overflow within any realistic number of blocks/epochs — congestion control's own throttling and transaction rejection at `reject_tx_congestion_threshold` bound accumulation well before overflow becomes reachable.

### Impact Explanation
If the overflow condition were somehow reached, the impact would be a chunk-apply panic causing a node crash/stall on the affected shard (matching "node panic" bounty class). But this is a defense-in-depth panic on an already-effectively-unreachable condition given existing congestion admission control, not an exploitable path from ordinary transaction submission.

### Likelihood Explanation
Very low. Reaching `u64`/`u128` overflow of cumulative receipt bytes/gas would require sustained congestion far beyond what the protocol's own admission control (`shard_accepts_transactions`, congestion-based transaction rejection) permits; rejection kicks in long before values approach anywhere near integer limits. There is no known amplification vector (e.g., no missing bounds on receipt count/size) that lets a single unprivileged account bypass congestion admission checks to keep pushing after a shard is congested.

### Recommendation
No urgent fix required for exploitability, but as tracked by the existing `TODO(#2152)` comment, replacing the `panic!` on `RuntimeError::UnexpectedIntegerOverflow` with a graceful chunk-rejection/error-return path would improve defense-in-depth and align behavior with the `StorageError::FlatStorageBlockNotSupported`/`MissingTrieValue` handling pattern already used nearby [9](#0-8) .

### Proof of Concept
Not applicable as an exploitable finding — no PoC exists that drives congestion gas/bytes to `u64`/`u128` overflow via ordinary transaction submission, since existing congestion-based transaction rejection thresholds bound accumulation far below the overflow point. A defense-in-depth regression test could assert that `add_receipt_bytes`/`add_delayed_receipt_gas` never trigger under bounded, protocol-legal `CongestionControlConfig` values across an arbitrarily long simulated chunk-apply sequence, but this validates existing correct behavior rather than demonstrating a vulnerability.
