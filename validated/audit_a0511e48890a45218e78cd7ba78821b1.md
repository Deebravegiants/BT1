## Finding: Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook shop spoofing

### Title
Webhook shop identity is taken from an HMAC-unprotected header, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates its HMAC over the raw body only, while `Registry.process` trusts the `shop-domain` header — which is *not* part of the signed data — as the tenant identity passed to the app's webhook handler.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [1](#0-0) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the body) and compares it with the `hmac` from the `hmac-sha256`/`x-shopify-hmac-sha256` header: [2](#0-1) 

`Request#shop`, however, is read straight from the unauthenticated `shop-domain`/`x-shopify-shop-domain` header, which never enters `to_signable_string`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` — the unauthenticated header value — to the app's handler as the tenant identity, without ever re-deriving or cross-checking it against anything covered by the signature: [4](#0-3) 

This is exactly the reported bug class applied to this gem: a field (`shop`) that the code acts on as the authoritative tenant/session identity is not covered by the cryptographic binding (`hmac`) that is supposed to authenticate the whole request. The equality that should hold — `shop bound by HMAC == shop used to route/process the webhook` — is broken: only the body is bound by the HMAC, but `shop` comes from a header outside that binding.

### Impact Explanation
Because Shopify signs webhooks for *all* shops installed on an app using the same `client_secret`, an attacker who controls (or has installed the app on) shop A can capture a legitimately-signed webhook (valid `body` + valid `hmac`), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header with victim shop B's domain. `HmacValidator.validate` still passes (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to shop B when it actually originated from/was crafted by shop A. Any app that uses `WebhookMetadata#shop` to select tenant-scoped storage, trigger tenant-scoped side effects (e.g., data deletion/redaction, order/customer record creation, notifications) is exposed to cross-tenant data injection/corruption driven entirely by an unprivileged, unauthenticated attacker who is a legitimate (but unrelated) merchant/tenant of the same app. This matches the Critical "cross-tenant access" impact category since the tenant boundary is fully attacker-controlled despite the HMAC check passing.

### Likelihood Explanation
Any merchant who installs the app (a normal, unprivileged action requiring no special access) can obtain genuine `(body, hmac)` pairs from their own webhook deliveries and then send arbitrary HTTP requests with a forged `shop-domain`/`x-shopify-shop-domain` header directly to the app's webhook endpoint (the endpoint is a public HTTP route by design). No secrets, tokens, or elevated privileges are required beyond being any tenant of the app.

### Recommendation
Bind `shop` to the HMAC-covered payload rather than trusting the header alone. Options:
- Combine the `shop-domain` header value into `to_signable_string` (Shopify's actual webhook signature does not include headers, so a safer fix is to independently re-derive/verify the shop from a value inside the signed body when the topic payload contains identifying info) — or more robustly, cross-check the header-derived shop against a HMAC-covered identity claim.
- At minimum, document/require that host apps look up the shop by an app-issued, per-installation offline session rather than trusting `WebhookMetadata#shop` as the sole tenant key when acting on sensitive data, and update `Registry.process`/`Request` so `shop` cannot be spoofed independently of the signature.

### Proof of Concept
1. App has two merchants installed: Attacker-Shop (`attacker.myshopify.com`) and Victim-Shop (`victim.myshopify.com`), both sharing the app's single `client_secret`.
2. Attacker triggers any webhook event on their own shop (e.g., `orders/create`) and captures the raw POST: body `B` and header `x-shopify-hmac-sha256: H` — both valid, since `H = HMAC(client_secret, B)`.
3. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because it only checks `B` and `H`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb#188-200`) calls the handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...)`, even though the payload actually describes attacker-shop data — the app now believes/processes attacker-controlled data as belonging to the victim tenant.
