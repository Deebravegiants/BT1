### Title
Duplicate-assetId withdrawals in one MultiPayload cause `PoaBridge.describeWithdrawal` to misreport withdrawal 1's status/hash as withdrawal 0's - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.findMatchingWithdrawal` matches a POA withdrawal-status response entry by `assetId` alone, ignoring `WithdrawalIdentifier.index`. When a single signed intent contains two `ft_withdraw` intents for the same PoA token, both `watchWithdrawal` calls (index 0 and index 1) resolve to the same (first) matching entry, so an integrator watching index 1 can be told the tx hash/status that actually belongs to withdrawal 0.

### Finding Description
The broken equality: `describeWithdrawal({index:1, assetId:X}).txHash` should equal the outcome of the withdrawal at index 1, but it actually equals the outcome of whichever entry `Array.prototype.find` returns first for `assetId:X` — which for two withdrawals of the same asset is always the same entry (effectively withdrawal 0's data) regardless of which index is queried.

Code path: `createWithdrawalIdentifiers` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`) assigns per-route indexes 0 and 1 for two `ft_withdraw` intents of the same asset in one `intentTx`. `watchWithdrawal` then calls `bridge.describeWithdrawal({...wid})` for each identifier [1](#0-0) . `PoaBridge.describeWithdrawal` fetches all withdrawals for the tx hash and calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which only compares `nep141:${w.data.near_token_id} === assetId` and never consults `args.index` [2](#0-1) [3](#0-2) .

This is not a hidden oversight — it is explicitly acknowledged in the code's own comment: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported. POA API doesn't currently support this case either." [4](#0-3) 

No guard exists anywhere in `createWithdrawalIdentifiers`, `supports()`, or `validateWithdrawal` that rejects or deduplicates multiple withdrawals of the same `assetId` within one batch/tx — the index-assignment logic in `withdrawal-watcher.ts` happily assigns 0 and 1 for same-route withdrawals without checking for assetId collisions, and nothing downstream prevents the ambiguous match.

### Impact Explanation
Both index-0 and index-1 watchers converge on the same POA API entry, so the integrator ends up crediting the same on-chain transfer twice for two logically distinct withdrawal intents — a status/hash misreport that leads to double-crediting or refunding an already-completed withdrawal. This matches the "status or hash misreport making an integrator credit or refund twice" category (rated High in the rules' severity table, though the question frames it as Critical due to treasury double-crediting). The condition is deterministic and repeatable for every same-asset multi-withdrawal batch, not a one-off race.

### Likelihood Explanation
Preconditions are trivial and fully attacker/integrator-controllable: any unprivileged user (or a batch-withdrawal integrator flow) can construct a MultiPayload with two `ft_withdraw` intents for the same PoA `assetId` (e.g., `nep141:usdc.omft.near`) with different `destinationAddress`/`amount`, sign it, and submit it via the normal public SDK flow (`createWithdrawalIdentifiers` → `watchWithdrawal` for each). There is no special privilege needed, and the SDK itself does not reject or warn about this configuration before submission. Feasibility is high and cost is a single normal withdrawal transaction.

### Recommendation
Either (a) have `createWithdrawalIdentifiers`/`supports()` reject or explicitly disallow multiple withdrawals of the same `assetId` within a single POA-route batch until the POA bridge API supports disambiguation, or (b) implement the ordering-based matching the code comment proposes — sort both the API's returned withdrawals and the original `withdrawalParams` deterministically (e.g., by amount, since POA relayer fees are equal per token) and match by position/index instead of by `assetId` alone, consuming each matched entry so it cannot be returned again for a different index.

### Proof of Concept
Vitest plan (mock only `poaBridge.httpClient.getWithdrawalStatus`):
1. Mock `getWithdrawalStatus` to return `withdrawals: [{status:"COMPLETED", data:{near_token_id:"usdc.omft.near", transfer_tx_hash:"HASH_A"}}, {status:"COMPLETED", data:{near_token_id:"usdc.omft.near", transfer_tx_hash:"HASH_B"}}]`.
2. Call `poaBridge.describeWithdrawal({index:0, withdrawalParams:{assetId:"nep141:usdc.omft.near", ...}, tx})` and `poaBridge.describeWithdrawal({index:1, withdrawalParams:{assetId:"nep141:usdc.omft.near", ...}, tx})`.
3. Assert `result0.txHash === "HASH_A"` and `result1.txHash === "HASH_A"` (identical), demonstrating that index 1's reported hash equals index 0's outcome rather than `"HASH_B"`, i.e. `result1.txHash !== "HASH_B"` even though withdrawal 1 should map to `HASH_B`.

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
