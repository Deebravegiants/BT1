### Title
Cost-model's `allocated_accounts_data_size` estimate ignores CPI-invoked `system_program` allocations, allowing block-level accounts-data-size limits to be bypassed - ([File: cost-model/src/cost_model.rs])

### Summary
`CostModel::calculate_allocated_accounts_data_size` only inspects **top-level** compiled instructions returned by `transaction.program_instructions_iter()` and statically decodes only `system_program` `SystemInstruction` variants (`CreateAccount`, `Allocate`, `CreateAccountWithSeed`, etc.). Account-data growth performed by a custom BPF program that invokes `system_program::allocate`/`create_account` via CPI is invisible to this scan, both pre-execution and — critically — in the "actual" post-execution accounting path, since `calculate_cost_for_executed_transaction` still calls the same top-level-only `calculate_allocated_accounts_data_size` rather than using the real measured `accounts_resize_delta`.

### Finding Description
`calculate_allocated_accounts_data_size` (cost-model/src/cost_model.rs:265-301) sums `space` fields decoded only from top-level `SystemInstruction`s seen in `program_instructions_iter()`. Any allocation performed by a CPI from a custom program (invisible to this iterator, since it only sees top-level compiled instructions, not inner/CPI instructions) contributes `0` to the estimate via the `SystemProgramAccountAllocation::None` branch for non-`system_program` top-level program IDs (cost-model/src/cost_model.rs:242-261).

This static estimate is used in two places:
1. Pre-execution, via `calculate_cost` → `calculate_transaction_cost` (cost-model/src/cost_model.rs:103-127), used by banking stage to estimate cost before scheduling.
2. Post-execution "actual" cost, via `calculate_cost_for_executed_transaction` (cost-model/src/cost_model.rs:56-77), which is supposed to reflect real execution but **still calls `calculate_transaction_cost` with `transaction.program_instructions_iter()`**, i.e., still uses the same static, CPI-blind estimate for `allocated_accounts_data_size` rather than the real `accounts_deltas.accounts_resize_delta` that the runtime already tracks precisely per transaction (see `transaction_context/src/transaction_accounts.rs` `resize_delta`/`can_data_be_resized`, and `svm/src/transaction_processor.rs` `AccountsDeltas`).

`core/src/banking_stage/consumer.rs::calculate_processed_transaction_costs` (lines 490-520) calls `CostModel::calculate_cost_for_executed_transaction` with real `executed_units` and `loaded_accounts_data_size`, but the `allocated_accounts_data_size` field inside that returned `TransactionCost` is still derived from the static top-level scan. This value is what gets added to `CostTracker::allocated_accounts_data_size` via `try_add` (cost-model/src/cost_tracker.rs:172-239), which enforces the block-level `WouldExceedAccountDataBlockLimit` check against `CostTrackerLimits::allocated_data_size` (default `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`, cost-model/src/cost_tracker.rs:85-93).

The `apply_cost_tracker_during_replay` feature gate (feature-set/src/lib.rs) indicates this cost tracker (and hence this same flawed `allocated_accounts_data_size` accounting) is also applied during block replay/validation, not just leader-side scheduling.

Meanwhile, the actual per-transaction data-growth hard cap (`MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION`, transaction-context/src/lib.rs:23, enforced in `TransactionAccounts::can_data_be_resized`) is checked independently at the account-resize level regardless of call path (top-level or CPI), so per-transaction growth cannot exceed roughly ~20MB. But the **block-level accumulator** (`CostTracker::allocated_accounts_data_size`, intended to bound aggregate accounts-data growth per block via `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`) only accumulates the static, CPI-blind per-transaction estimate — not the real measured growth. A transaction that performs its allocation entirely via CPI (invisible to the static scan) contributes `0` to this block-level accumulator even though its real `accounts_resize_delta` can be large (up to the per-transaction cap).

### Impact Explanation
An attacker can craft transactions where large real account-data growth is achieved exclusively through a custom program's CPI into `system_program::allocate`/`create_account`/`create_account_with_seed`, none of which appear as top-level instructions. Because `calculate_cost_for_executed_transaction` never substitutes the real measured `accounts_resize_delta` for `allocated_accounts_data_size`, the `CostTracker`'s block-level `allocated_accounts_data_size` accumulator systematically undercounts real state growth for such transactions. This lets a block (whether produced by an honest leader packing many CPI-allocating transactions, or accepted during replay under `apply_cost_tracker_during_replay`) grow on-chain accounts data far beyond the intended `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` budget per block, defeating the resource-exhaustion protection that this budget is designed to enforce — a materially underpriced/underestimated accounts-data-size cost, matching the "resource exhaustion" bounty category for cost-model/fee-estimation flaws. Because both leader and replaying validators apply the identical (flawed) static estimate, this does not directly cause cross-node divergence, but it does allow attacker-controlled, unmetered accumulation of on-chain state growth beyond the designed per-block cap.

### Likelihood Explanation
Highly feasible and repeatable by any unprivileged user: deploy (or reuse an already-deployed) BPF program that CPIs into `system_program::allocate`/`create_account`, then submit ordinary transactions invoking that program as the sole top-level instruction. No special privileges, validator control, or non-standard RPC access is required — this is a single, ordinarily-formed transaction submitted via normal TPU/RPC paths, repeatable at will up to the account lock / per-tx growth cap each time.

### Recommendation
In `calculate_cost_for_executed_transaction` (cost-model/src/cost_model.rs), replace the static, top-level-only `calculate_allocated_accounts_data_size` result with the real measured account-data growth for executed transactions (e.g., the `accounts_resize_delta` already computed and tracked in `svm/src/transaction_processor.rs`'s `AccountsDeltas` / `TransactionAccounts::resize_delta()`), so that the cost added to `CostTracker::allocated_accounts_data_size` reflects true post-execution growth rather than an estimate blind to CPI-invoked allocations. The static instruction-scan estimate should remain only for the pre-execution/estimation path (`calculate_cost`/`estimate_cost`), where no execution result yet exists.

### Proof of Concept
Integration test plan (svm/tests or cost-model tests, extended with a mock BPF program):
1. Deploy a test BPF program `cpi_allocate` that, given a target account and a `space` argument in its instruction data, issues a CPI to `system_program::allocate(target, space)`.
2. Build a transaction whose only top-level instruction invokes `cpi_allocate` with `space = 100_000`.
3. Assert `CostModel::calculate_allocated_accounts_data_size(tx.program_instructions_iter(), ...)` (pre-execution) returns `0` (since the top-level program is not `system_program`).
4. Execute the transaction via the SVM (`svm/tests/integration_test.rs` harness) and read back the real `accounts_deltas.accounts_resize_delta` for the target account (via `TransactionExecutionDetails::accounts_deltas`).
5. Call `CostModel::calculate_cost_for_executed_transaction(&tx, executed_units, loaded_accounts_data_size, &feature_set)` and assert its `allocated_accounts_data_size()` is still `0`, while the real `accounts_resize_delta` is `100_000` — demonstrating the block-level cost-tracker input is undercounted by the full allocation size.
6. As a fuzz/invariant target: generate a corpus of CPI-heavy transactions with varying `space` arguments and assert the invariant `tx_cost.allocated_accounts_data_size() >= actual_accounts_resize_delta` fails for CPI-allocation transactions, confirming the estimate does not upper-bound real growth.
