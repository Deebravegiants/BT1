### Title
Cost model omits non-system-program account data growth (e.g. ExtendLookupTable), underpricing per-block account allocation budget - ([File: cost-model/src/cost_model.rs])

### Summary
`CostModel::calculate_allocated_accounts_data_size` only recognizes account-data growth caused by `SystemInstruction::{CreateAccount, CreateAccountWithSeed, Allocate, AllocateWithSeed, CreateAccountAllowPrefund}` issued by the System Program; any other program that resizes an account it owns (notably the Address Lookup Table program's `ExtendLookupTable`, parsed by `parse_address_lookup_table`) contributes `SystemProgramAccountAllocation::None`, i.e. zero, to the cost model's allocation accounting. This value is used both for the pre-execution `CostTracker` admission check and — because `calculate_cost_for_executed_transaction` recomputes `allocated_accounts_data_size` via the same static per-instruction function rather than from measured `accounts_resize_delta` — for the post-execution accounting as well, so the gap is never corrected.

### Finding Description
`CostModel::calculate_account_data_size_on_instruction` gates allocation accounting strictly on `program_id == &system_program::id()`: [1](#0-0) 
Any instruction issued to a different program — including the Address Lookup Table program, whose `ExtendLookupTable{new_addresses}` instruction (as decoded by `parse_address_lookup_table`) grows the lookup table account's data by `32 * new_addresses.len()` bytes — falls into the `else` branch and returns `SystemProgramAccountAllocation::None`: [2](#0-1) 

`calculate_allocated_accounts_data_size` sums these per-instruction allocation estimates and treats `None` as "no contribution": [3](#0-2) 

This value becomes `TransactionCost::allocated_accounts_data_size`, which `CostTracker::try_add` checks/accumulates against the block-wide `allocated_data_size` limit (`MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`), a budget meant to bound the *real* aggregate account-data growth committed to the block/AccountsDb per slot: [4](#0-3) 

Critically, this static, instruction-shape-based estimate is used both before execution (`calculate_cost`) and after execution (`calculate_cost_for_executed_transaction`) — the "actual" variant only refreshes CU execution cost and loaded-accounts-size cost, but recomputes `allocated_accounts_data_size` by calling the identical `calculate_transaction_cost`/`calculate_allocated_accounts_data_size` path over the same instructions, not from the transaction's real `AccountsDeltas::accounts_resize_delta` that is already computed and available post-execution: [5](#0-4) [6](#0-5) 

So an attacker who repeatedly submits `CreateLookupTable` + `ExtendLookupTable` transactions (each ExtendLookupTable growing the table by up to 32×20=640 bytes, well under any single-instruction limits) causes real byte growth in the lookup table account that is accounted as 0 bytes by both the admission-time and post-execution cost tracking, silently exhausting the intended per-block account-growth budget without ever being reflected in `CostTracker::allocated_accounts_data_size` telemetry or limit checks.

Note: this does **not** bypass the separate, independent per-transaction hard cap enforced directly in the transaction context (`TransactionAccounts::can_data_be_resized` / `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION`), which is a runtime invariant unrelated to the cost model: [7](#0-6) 
That guard limits growth *within a single transaction* to ~20MB but does nothing to limit or even measure the *aggregate* growth across many transactions in a block, which is exactly what the cost-model's `allocated_accounts_data_size` / `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` mechanism is supposed to police.

### Impact Explanation
This is a materially underpriced-execution / cost-model-underpricing bug (Agave bounty category: "cost model underprice — leader/validator resource exhaustion"). Because the block-level `allocated_accounts_data_size` counter never increases for ALT-owned account growth, an attacker's transactions are admitted into blocks as if they allocate zero account-data bytes even while genuinely growing AccountsDb usage. Repeated across many transactions/blocks this results in real per-block account-data growth exceeding the value the cost tracker believes it is enforcing, undermining the invariant that "declared compute-budget/cost-model estimates must upper-bound real work performed." The scoped impact is block-capacity/AccountsDb-growth-budget exhaustion, not a fund-loss or consensus-halt bug — the per-transaction hard cap (`MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION`) still bounds worst-case single-transaction damage.

### Likelihood Explanation
Highly feasible and fully within the unprivileged-attacker model: the attacker only needs to author their own lookup table (`CreateLookupTable`), sign it as authority, then submit successive `ExtendLookupTable` transactions (each cheap, low CU, and independently valid) — no special privileges, keys, or validator control required. This can be repeated indefinitely across blocks with ordinary RPC/TPU submission, and there is no rate-limiting from `allocated_data_size` since it never sees any growth from this program.

### Recommendation
Extend `CostModel::calculate_account_data_size_on_instruction` (or replace the static-instruction heuristic entirely) to also account for account growth performed by non-system-program instructions that resize accounts they own, in particular the Address Lookup Table program's `ExtendLookupTable` instruction (mirroring the size math already used by `transaction_address_lookup_table_scanner::scan_transaction`, which parses `ProgramInstruction::ExtendLookupTable{new_addresses}` and could be reused to compute `32 * new_addresses.len()`). More robustly, for `calculate_cost_for_executed_transaction`, use the already-computed real `AccountsDeltas::accounts_resize_delta` from `TransactionExecutionDetails` instead of recomputing the static per-instruction estimate, so post-execution cost/CostTracker accounting reflects actual account growth regardless of which program performed it.

fn test_calculate_allocated_accounts_data_size_ignores_alt_extend() {
    use solana_address_lookup_table_interface::instruction::extend_lookup_table;

    let authority = Keypair::new();
    let lookup_table_pubkey = Pubkey::new_unique();
    let new_addresses: Vec<Pubkey> = (0..20).map(|_| Pubkey::new_unique()).collect();
    // Real growth this instruction performs: 32 bytes * 20 addresses = 640 bytes.
    let expected_real_growth: u64 = 32 * new_addresses.len() as u64;

    let extend_ix = extend_lookup_table(
        lookup_table_pubkey,
        authority.pubkey(),
        Some(authority.pubkey()),
        new_addresses,
    );
    let transaction = Transaction::new_unsigned(Message::new(
        &[extend_ix],
        Some(&authority.pubkey()),
    ));
    let sanitized_tx = RuntimeTransaction::from_transaction_for_tests(transaction);

    let cost_model_allocation = CostModel::calculate_allocated_accounts_data_size(
        sanitized_tx.program_instructions_iter(),
        &FeatureSet::all_enabled(),
    );

    // Bug: cost model reports 0 bytes allocated even though ExtendLookupTable
    // will actually grow the lookup table account by `expected_real_growth` bytes.
    assert_eq!(cost_model_allocation, 0);
    assert!(expected_real_growth > 0);
    // A correct cost model should satisfy:
    // assert!(cost_model_allocation >= expected_real_growth);

    /// eventually, potentially determine account data size of all writable accounts
    /// at the moment, calculate account data size of account creation
    fn calculate_allocated_accounts_data_size<'a>(
        instructions: impl Iterator<Item = (&'a Pubkey, SVMInstruction<'a>)>,
        feature_set: &FeatureSet,
    ) -> u64 {
        let mut tx_attempted_allocation_size = Saturating(0u64);
        for (program_id, instruction) in instructions {
            match Self::calculate_account_data_size_on_instruction(
                program_id,
                instruction,
                feature_set,
            ) {
                SystemProgramAccountAllocation::Failed => {
                    // If any system program instructions can be statically
                    // determined to fail, no allocations will actually be
                    // persisted by the transaction. So return 0 here so that no
                    // account allocation budget is used for this failed
                    // transaction.
                    return 0;
                }
                SystemProgramAccountAllocation::None => continue,
                SystemProgramAccountAllocation::Some(ix_attempted_allocation_size) => {
                    tx_attempted_allocation_size += ix_attempted_allocation_size;
                }
            }
        }

        // The runtime prevents transactions from allocating too much account
        // data so clamp the attempted allocation size to the max amount.
        //
        // Note that if there are any custom bpf instructions in the transaction
        // it's tricky to know whether a newly allocated account will be freed
        // or not during an intermediate instruction in the transaction so we
        // shouldn't assume that a large sum of allocations will necessarily
        // lead to transaction failure.
        (MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION as u64)
            .min(tx_attempted_allocation_size.0)
    }

    pub(crate) fn can_data_be_resized(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        // The new length can not exceed the maximum permitted length
        if new_len > MAX_ACCOUNT_DATA_LEN as usize {
            return Err(InstructionError::InvalidRealloc);
        }
        // The resize can not exceed the per-transaction maximum
        let length_delta = (new_len as i64).saturating_sub(old_len as i64);
        if self.resize_delta.get().saturating_add(length_delta)
            > MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION
        {
            return Err(InstructionError::MaxAccountsDataAllocationsExceeded);
        }
        Ok(())
    }
