The documentation explicitly states `Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0)  — but the HMAC signature only covers the raw body, not the `shop-domain` or `topic` headers that the handler dispatches and trusts as the tenant identity.

### Title
Webhook `shop` and `topic` headers are not bound by HMAC, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [2](#0-1) , so `HmacValidator.validate` verifies the HMAC solely against the body bytes [3](#0-2) . Meanwhile `Registry.process` dispatches to the handler using `request.shop` and `request.topic`, both read directly from unauthenticated HTTP headers [4](#0-3) [5](#0-4) . The identity binding broken is: `hmac(raw_body) == hmac(raw_body)` (true) while `shop_header_used_by_handler != shop_that_actually_generated_the_signed_body` is never checked.

### Finding Description
Because the app's `client_secret` is shared across every shop that installs the app, any unprivileged user who installs the app on their own (e.g. free/dev) store legitimately receives real webhook deliveries with valid `(raw_body, hmac)` pairs signed by that same secret. Since `shop-domain` and `topic` headers are excluded from `to_signable_string`, that attacker can replay the exact same body+HMAC to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (impersonating a victim tenant) and/or an arbitrary `x-shopify-topic` header (redirecting the body to a different, potentially more sensitive, handler, including the mandatory `shop/redact` / `customers/redact` / `customers/data_request` handlers) [6](#0-5) . `Registry.process` will accept this request as authentic because `Utils::HmacValidator.validate` only checks the body against the signature [7](#0-6) , and will construct `WebhookMetadata` using the attacker-supplied `shop` and `topic` [8](#0-7) .

### Impact Explanation
This crosses the Critical "cross-tenant access" bar: a handler written per the documented contract (which explicitly trusts `data.shop` as "The shop domain of the webhook" [9](#0-8) ) can be tricked into executing actions attributed to a shop the attacker doesn't own — e.g. triggering `shop/redact`/`customers/redact` compliance deletion logic or `app/uninstalled` cleanup against a victim tenant's stored data, using only a signature the attacker legitimately obtained for their own tenant.

### Likelihood Explanation
Medium-to-High: it requires only (1) installing/using the target app on any shop the attacker controls (unprivileged, no special access needed) to capture one valid signed webhook body, and (2) sending a crafted HTTP request to the app's public webhook URL with swapped headers — no access to `api_secret_key`, tokens, or victim credentials is needed.

### Recommendation
Include the `shop-domain` and `topic` headers (and ideally `webhook-id`) in the signable string that the HMAC is computed over, or otherwise cryptographically bind them to the body signature, so that any header a handler relies on for tenant/topic identity is verified rather than merely parsed.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they control) and lets the app register for a webhook topic, e.g. `orders/create`.
2. Shopify sends a legitimately signed webhook to the app: body `B`, header `x-shopify-hmac-sha256: H` (valid because `H = HMAC-SHA256(client_secret, B)`), `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
3. Attacker resends the identical `B` and `H` to the app's webhook endpoint, but replaces headers with `x-shopify-shop-domain: victim-shop.myshopify.com` and `x-shopify-topic: shop/redact`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully [10](#0-9) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only re-derives `HMAC-SHA256(client_secret, B)` and compares to `H` [11](#0-10) .
5. `Registry.process` looks up the handler for `shop/redact` and invokes it with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "shop/redact", body: B, ...)` [4](#0-3) , causing the app to perform redaction/uninstall-style logic against a tenant the attacker never controlled.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
