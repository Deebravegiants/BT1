### Title
LP graduation seeding can permanently lock a mispriced LP when a large hostile pre-seed exceeds the rebalance swap budget - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.finalizeGraduation` → `_seedUniswapV2Direct` → `_seedRebalancing` tries to correct a hostile HyperSwap V2 pre-seed of the TOKEN/LT pair back to the curve-close ratio with a single direct `pair.swap`, but the swap input is hard-capped at 99% of Bonding's own graduation inventory (`_swapBudget`). When an attacker pre-seeds the pair with a ratio/size that requires a corrective swap larger than that budget, the swap is clamped, the pool is left off the curve-close ratio, and `_routerDepositAndDispose` still deposits the remaining inventory via `addLiquidity(..., 1, 1, ...)` at that skewed ratio. The resulting LP is minted to `LPLock.recordLock` — a one-shot, unfixable call — permanently locking a mispriced pool.

### Finding Description
`_prepareGraduationLiquidity` (`Bonding.sol:1073-1096`) pins `tokensForLP`/`ltFromPair` at the exact curve-close ratio. Phase 2 (`finalizeGraduation`, `Bonding.sol:1000-1034`) is supposed to seed the HyperSwap V2 pair at that identical ratio regardless of any pre-seed, per the "Regime 3" rebalance logic documented at `Bonding.sol:1132-1200`.

The rebalance leg (`_seedRebalancing`, `Bonding.sol:1279-1354`) computes the swap needed to bring the pool to the target ratio with `_noFeeSwapInput` (`Bonding.sol:1507-1522`), but clamps it: [1](#0-0) 

`maxSwap` is bounded by Bonding's own available inventory for that graduation — `_ltSwapInventory` (bounded near `ltFromPair`, itself capped by the ~$9K USD graduation threshold worth of LT) or `IERC20(tokenAddress).balanceOf(address(this))` (bounded by `tokensForLP ≤ LP_RESERVE`, 250M tokens). An attacker who buys tokens on the curve (`Zap.buy`) and later pre-creates/pre-seeds the HyperSwap V2 pair with a token:LT ratio far enough from the cached curve-close ratio can force the ideal corrective swap size (`s = sqrt(reserveIn·reserveOut·targetN/targetD) - reserveIn`) to exceed this fixed budget. When that happens, `_pairRebalance` still executes a swap, but only for the clamped amount — the pool does **not** reach the target ratio. [2](#0-1) 

`_routerDepositAndDispose` then deposits the remaining inventory into the still-off-target pool at `min0=1, min1=1` — by design there is no ratio tolerance check on this final deposit: [3](#0-2) 

The natspec on `_swapBudget` explicitly acknowledges this residual-drift scenario as an accepted tradeoff for "catastrophic pre-seeds," treating bricking as the only alternative: [4](#0-3) 

But the resulting LP is minted directly to `LPLock.recordLock`, which is a one-shot call `finalizeGraduation` cannot skip or retry once it fires: [5](#0-4) 

There is no post-hoc correction: the launched token's post-graduation trading price is permanently set by this mispriced, locked LP.

### Impact Explanation
The V2 pool that becomes the token's canonical post-graduation trading venue opens at a ratio the attacker chose, not at the curve-close price the entire two-phase graduation design (`Bonding.sol:26-45`, `_prepareGraduationLiquidity` natspec) is built to preserve. The attacker's own pre-existing (unlocked) LP position captures the mispricing: they can size the pre-seed so the pool opens overvaluing the token (letting them dump curve-bought tokens into the new pool at an inflated price) or undervaluing it (letting them buy back cheaply), while honest holders and the protocol-locked LP are stuck with a pool priced away from the value the curve actually established. This directly matches the accepted impact class "an LP seeded away from the curve close price."

### Likelihood Explanation
Every step is reachable by a single unprivileged address: `Zap.createToken`/`buy` are permissionless, creating/seeding the HyperSwap V2 pair via `IUniswapV2Factory.createPair` + direct `IUniswapV2Pair.mint` is explicitly an in-scope reachable action, and `finalizeGraduation` is permissionless. The only cost is acquiring enough token/LT to make the pre-seed's required corrective swap exceed Bonding's bounded per-graduation budget (a few thousand USD worth of LT or up to 250M tokens) — feasible for a moderately funded attacker and does not require any privileged role, upgrade, or off-chain component.

### Recommendation
Do not let `_routerDepositAndDispose` finalize a deposit when the corrective swap was budget-clamped and the pool remains materially off the cached curve-close ratio. Options: (a) after the (possibly clamped) rebalance swap, compare the pool's post-swap ratio to `(tokensForLP, ltFromPair)` within an explicit bps tolerance before calling `addLiquidity`, and if outside tolerance, hold the graduation open (or route the deposit to an owner-recoverable escrow) instead of minting into `LPLock`; (b) size `_swapBudget` off a bound tied to the pre-seed's reserves rather than a fixed fraction of Bonding's own inventory, so the corrective swap can always fully rebalance instead of silently truncating.

### Proof of Concept
1. Attacker acquires a large amount of the newly launched `Token` by buying on the curve via `Zap.buy` (unprivileged, allowed).
2. Before the token graduates, attacker calls `IUniswapV2Factory(uniswapV2Factory).createPair(token, lt)` to create the HyperSwap V2 pair, then transfers a large amount of `Token` and a minimal amount of `LT` into the pair and calls `pair.mint(attacker)` directly, minting themselves LP at an extreme, arbitrary TOKEN:LT ratio.
3. Trading continues/completes on the curve until `canGraduate` trips (or attacker/keeper calls `triggerGraduation`), moving the token to `Lifecycle.Graduating` and caching `(tokensForLP, ltFromPair)` at the true curve-close ratio (`_enterGraduating` → `_prepareGraduationLiquidity`, `Bonding.sol:938-953`, `1073-1096`).
4. Anyone calls `finalizeGraduation(token)`. `_seedRebalancing` computes the swap needed to correct the attacker's extreme ratio; because the required swap exceeds `_swapBudget(inventory)` (`Bonding.sol:1374-1378`), `_pairRebalance` executes only the clamped amount and the pool ends up still far from `(tokensForLP, ltFromPair)`'s ratio.
5. `_routerDepositAndDispose` deposits the remaining Bonding-held inventory via `addLiquidity(..., 1, 1, lpLock_, ...)` at this off-ratio pool state, and `LPLock.recordLock` finalizes it — the mispriced LP is now permanently locked and canonical for the token, while the attacker's original self-minted LP (never subject to `LPLock`) is free to withdraw at the manipulated price.

    function _pairRebalance(
        RebalanceParams memory p
    ) internal returns (bool) {
        uint256 s = _noFeeSwapInput(p.reserveIn, p.reserveOut, p.targetN, p.targetD, p.maxSwap);
        if (s == 0) return false;

        // Quote from the pair so the output tracks its live fee; a value
        // derived from a stale fee rate would trip the pair's K-check.
        uint256 expectedOut = IUniswapV2Pair(p.pair).getAmountOut(s, p.tokenIn);
        if (expectedOut == 0) return false;

        IERC20(p.tokenIn).safeTransfer(p.pair, s);
        (uint256 amount0Out, uint256 amount1Out) = p.tokenInIs0 ? (uint256(0), expectedOut) : (expectedOut, uint256(0));
        IUniswapV2Pair(p.pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
        return true;
    }
