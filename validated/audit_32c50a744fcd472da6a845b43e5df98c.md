### Title
Position NFT can be transferred to an unprepared contract address, permanently freezing the lending position and its collateral - (File: contracts/position-nft/src/contract.rs)

### Summary
The position NFT (`PositionNft`) exposes the stock OpenZeppelin `transfer`/`transfer_from` entrypoints with no recipient-side safeguard. On Soroban there is no ERC-721-style receiver hook, and a plain contract `Address` cannot satisfy `require_auth` (only custom account contracts implementing `__check_auth` can). Sending a position token to a contract address that cannot authenticate therefore bricks the account: the controller resolves ownership through `owner_of` and requires the owner's authorization for every owner-gated action, so the collateral and any recoverable value in the position are frozen forever.

### Finding Description
`transfer`/`transfer_from` are exported unchanged from the OZ `NonFungibleToken` trait (`contract.rs:131-133`). They move `Owner(token_id)` to `to` without checking that `to` can act. The protocol explicitly designs around this token being the sole authority record: "The controller stores no owner address for an account; it calls `owner_of(account_id)` on this contract every time it needs to know who may act on a position" (README, lines 3-9), and "Transferring the token transfers the whole position ... Collateral and debt both move with the token" (lines 39-41). Owner-gated controller calls (`withdraw`, `borrow`, `repay`, etc.) call `try_account_owner` → `owner_of` → `owner.require_auth()`. A recipient that is a non-account contract address can never produce that auth, so no one can ever move the token back or operate the position. Even liquidation becomes impossible in the owner-auth path (liquidator paths still work, but surplus collateral beyond debt is unrecoverable). This mirrors the reported bug class — NFT transferred to an unprepared contract ends up locked — with `transfer`/`transfer_from` playing the role of `transferFrom` and no safe-transfer alternative existing.

### Impact Explanation
Permanent freezing of funds: all collateral held by the transferred account becomes permanently inaccessible. Any address can reach this by calling `position_nft.transfer(from=self, to=<contract address>, token_id)`, or via `transfer_from` with a valid approval — both are unprivileged entrypoints listed in `docs/reference/endpoints.md:244-245`.

### Likelihood Explanation
Requires a user (or an approved operator) to send the token to a contract address — e.g., a marketplace, escrow, or multisig wrapper contract that integrates with the NFT without implementing account authentication. This is exactly the "unprepared contract recipient" scenario from the original report; on Soroban it is strictly worse than Ethereum `transferFrom` because the receiving contract is never invoked and has no opportunity to reject the token.

### Recommendation
Since Soroban lacks a receiver-hook standard, mitigate at the protocol level: either (a) add a guarded two-step position handover in the controller (propose recipient, recipient must explicitly accept by proving auth, only then is the NFT transferred), or (b) document and/or enforce that `to` is not a contract address by checking `to.require_auth()` inside a wrapped transfer entrypoint, ensuring the recipient can authenticate before receiving.

### Proof of Concept
1. Alice supplies collateral via `controller.supply`, minting position NFT `token_id = N` to Alice (`mint` → `Enumerable::sequential_mint`, `contract.rs:68-76`).
2. Alice calls `position_nft.transfer(alice, pool_or_any_contract_address, N)` — an unprivileged call; `from` auth succeeds and `Owner(N)` is set to the contract address (`contract.rs:131-133`, test `transfer_moves_ownership_and_enumeration` shows the mechanics, `test.rs:120-133`).
3. Any subsequent owner-gated controller call (`withdraw`, `borrow`, `transfer` of the NFT itself) resolves `owner_of(N)` to the contract and calls `require_auth` on it; a non-account contract cannot authorize, so every path fails permanently.
4. Collateral is locked in the pool's account `N` forever — same end state as an ERC-721 locked in a contract lacking `onERC721Received`. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
