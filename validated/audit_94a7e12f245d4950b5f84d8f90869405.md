### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant data misattribution via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` dispatches inbound webhooks to a merchant's handler using `WebhookMetadata#shop`, but that `shop` value is read from an unauthenticated HTTP header, not from the HMAC-signed payload. The library validates only that the request *body* was signed with the app's `api_secret_key`; it never binds the `shop-domain` header to that signature. Since the same `api_secret_key` is shared across every shop that installs the app, any request whose body matches a previously-observed (or predictable) signed body can be replayed with an arbitrary `shopify-shop-domain` header and will still pass `HmacValidator.validate`, causing the handler to process the payload as belonging to a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts `hmac`, `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers, but its `to_signable_string` — the value that is actually HMAC-verified — returns only the raw body: [1](#0-0) 

`HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, to_signable_string)` and compares it to the `hmac` header — it never incorporates `shop`, `topic`, or `webhook_id`: [2](#0-1) 

`Registry.process` then trusts the unauthenticated `request.shop` value and hands it directly to the app's handler as the tenant identifier for the payload: [3](#0-2) 

`WebhookMetadata#shop` is a plain `String` field with no independent verification: [4](#0-3) 

The equality this breaks is: `shop authenticated by the HMAC` == `shop used as the handler's tenant key`. In this codebase, the left side is always empty (the HMAC never covers `shop`), while the right side is the header value supplied by the caller. Because `api_secret_key` is a single app-wide secret shared by every installed shop (not per-shop), a valid `(body, hmac)` pair produced for shop A's webhook delivery remains valid when replayed with `shopify-shop-domain: shop-B.myshopify.com`. Any webhook body that is identical or predictable across tenants (e.g., mandatory topics like `shop/redact` with minimal/empty bodies, or any topic whose payload an attacker can otherwise capture) lets a caller who possesses one valid signed delivery re-post it while claiming a different shop, and `Registry.process` will pass that spoofed shop straight to the app's handler.

### Impact Explanation
This is a cross-tenant identity-binding failure: an app that uses the handler's `data.shop` to select which merchant's database record to create/update/delete (the documented and expected usage pattern for `WebhookHandler#handle`) can be made to attribute attacker-influenced webhook data to an arbitrary shop domain, because the gem provides no cryptographic assurance that the `shop` field is authentic. This matches the Critical "cross-tenant access" impact category, since it lets an unprivileged caller cause tenant-A data to be attributed/written under tenant-B's session/record.

### Likelihood Explanation
Exploitability depends on the attacker being able to obtain or predict a `(raw_body, hmac)` pair that is valid for the target app's shared `api_secret_key`. This is realistic for:
- Mandatory compliance topics with fixed/minimal bodies (`shop/redact`, `customers/redact`, `customers/data_request`), which are delivered to every installed shop with the app's `api_secret_key` and are the easiest to replay.
- Any merchant who is itself a legitimate app installer and can capture their own genuine webhook deliveries (headers + body + valid HMAC) and then resend them to the app's public webhook endpoint with a modified `shopify-shop-domain` header.

The library does nothing to prevent this replay across tenants because the shop identity is architecturally outside the signed content — this is a design gap in the library's verification surface, not solely a deployment mistake by the app author.

### Recommendation
Bind the tenant identity into the value that is actually verified, or require an out-of-band, per-shop check before trusting `WebhookMetadata#shop`:
- Extend `Webhooks::Request#to_signable_string` (or add a companion check in `Registry.process`) to also validate the `shop` (and ideally `topic`/`webhook_id`) against a known/allow-listed shop for the current app installation before invoking the handler.
- At minimum, document/enforce that `Registry.process` must cross-check `request.shop` against the caller's own persisted list of installed shops (session store) before treating the payload as authentic for that shop, since HMAC alone does not authenticate the shop field.
- Consider raising `Errors::InvalidWebhookError` in `Registry.process` when the `shop` header does not match a shop the app has an active session for.

### Proof of Concept
1. App installs on `shop-a.myshopify.com` and `shop-b.myshopify.com` using the same `api_secret_key` (standard multi-tenant Shopify app deployment).
2. Shopify (or the merchant on `shop-a`) triggers a webhook delivery with body `B` and headers including `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: H`, where `H = Base64(HMAC-SHA256(api_secret_key, B))`.
3. A user who can observe this delivery (e.g., the merchant on `shop-a`, who legitimately receives their own webhook via a configured relay, or by brute-forcing a mandatory-topic minimal body) resends the exact same body `B` and `H` to the app's webhook endpoint, but replaces the header with `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into `shop = "shop-b.myshopify.com"`, `hmac` unchanged.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` — identical to `H` — and returns `true`, since `shop` was never part of the signed content: [5](#0-4) 
6. The handler receives `WebhookMetadata(shop: "shop-b.myshopify.com", body: B, ...)` and performs whatever action it takes (e.g., data deletion/update) against tenant `shop-b`'s stored record, even though the payload actually originated from/for `shop-a`.
