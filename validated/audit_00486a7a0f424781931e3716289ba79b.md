## Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its verifiable signature over the raw request body only, while the shop domain used to identify the tenant is read from an unauthenticated HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates only that signature and then hands the header-derived `shop` value straight to the app's webhook handler as the tenant identifier. The `hmac` check therefore verifies *what bytes were sent*, but not *which shop they belong to* — the exact class of bug described in the report (a value that is acted upon differs from the value actually covered by the cryptographic check).

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is derived from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signed content at all: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (the body) and compares it with the `hmac` header using `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` only calls this HMAC check and then forwards `request.shop` — the unauthenticated header value — directly to the app's handler as the tenant identifier: [4](#0-3) 

Because the shop identity is never bound into the signed bytes, any entity that can obtain one genuine `(body, hmac)` pair signed with the app's shared secret (e.g., by installing the app on their own development/test store and receiving a real webhook for it) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. The signature still validates (it only checks the body), but the handler will process the payload as if it originated from the victim shop named in the forged header. This breaks the identity binding: `shop authenticated == shop used as tenant key` is required, but here `shop used as tenant key` comes from bytes that were never verified.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an unprivileged user who installs the app on their own store (or otherwise obtains one legitimately-signed webhook payload) can cause the receiving application to attribute that payload's data/events to a different, arbitrary shop of their choosing. Any host application that uses `WebhookMetadata#shop` to look up/update per-tenant state (the intended and only reasonable use of this field) will act on attacker-controlled data under another merchant's identity — a cross-tenant access impact.

### Likelihood Explanation
The only prerequisite is the ability to trigger one real webhook delivery for the app (installing the app on one's own store is sufficient, and does not require any elevated privilege, credentials, or the app's `client_secret`). Forging the shop header is trivial once a valid `(body, hmac)` pair is captured, since nothing in `HmacValidator` or `Registry.process` ties the header to the signed bytes.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the signed content that `to_signable_string` covers, or otherwise cryptographically bind the `shop` header to the HMAC before trusting it as a tenant identifier — analogous to fixing the USDT approval bug by ensuring the value actually acted upon is the same one that was verified.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any webhook (e.g., `orders/create`), capturing the genuine request: `raw_body`, and header `x-shopify-hmac-sha256` (valid for that `raw_body` under the app's `client_secret`).
2. Attacker resends this exact `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Request.new` accepts the forged headers (only presence, not authenticity, of `shop` is checked) — see `lib/shopify_api/webhooks/request.rb` lines 45-63.
4. `HmacValidator.validate(request)` succeeds because it only re-hashes `raw_body`, which is unmodified.
5. `Registry.process` invokes the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, causing the app to process the attacker's payload under the victim shop's identity.
