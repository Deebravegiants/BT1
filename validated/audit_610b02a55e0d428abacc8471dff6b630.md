### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then dispatches the handler using the `shop` value taken from the unauthenticated `x-shopify-shop-domain` header. Since the app's `client_secret` (used as the HMAC key) is shared across every shop that installs the app, any merchant who has installed the app can obtain genuine, validly-signed webhook bodies for their own store and replay them to the app's webhook endpoint with the `shop-domain` header rewritten to point at a different (victim) shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` / `validate_signature` compute and compare the HMAC strictly against that signable string (the body), never incorporating the `shop`, `topic`, or `webhook-id` headers: [2](#0-1) 

`Registry.process` uses this body-only HMAC check as its sole authentication step, and then trusts `request.shop` (read straight from the `x-shopify-shop-domain` header, with no cross-check against the HMAC or any known session/install record) to build the `WebhookMetadata` passed to the handler: [3](#0-2) [4](#0-3) 

The `client_secret` is the same shared HMAC key for every shop installation of a given app — it is not per-shop. Any shop that installs the app receives real webhook deliveries with valid `(body, hmac)` pairs signed with that shared secret. An attacker controlling such a shop can capture a legitimate `(body, hmac)` pair and resend it to the app's webhook endpoint after only changing the `x-shopify-shop-domain` header to name a victim shop. The HMAC check still passes because it never covered the shop header, yet `Registry.process` will invoke the handler with `WebhookMetadata#shop` equal to the victim's domain and attacker-chosen body content. This breaks the binding "shop that authenticated (signed) the request == shop attributed to the payload by the handler."

### Impact Explanation
This lets an unprivileged app-installing merchant forge webhook events that the host application attributes to a different tenant (shop) it does not control — a cross-tenant data-integrity/impersonation issue. Depending on how the host app's webhook handlers use `WebhookMetadata#shop` (e.g., to look up which shop's records to update, or to sync order/product/customer data), this can let an attacker inject or corrupt data belonging to another merchant's tenant, meeting the "cross-tenant access" Critical impact bar.

### Likelihood Explanation
Any entity able to install the target Shopify app on their own store (a normal, unprivileged action, not requiring `api_secret_key`, an access token, or credential theft) can trivially capture genuine `(body, hmac)` pairs from webhooks delivered to their own endpoint and replay them against the app's public webhook endpoint with a modified `shop-domain` header. No secret material needs to be extracted or brute-forced; the attacker already legitimately possesses valid signed payloads for arbitrary webhook topics/bodies triggered on their own store.

### Recommendation
Bind the shop identity into the value that is actually verified: either include the `shop-domain` (and ideally `topic`/`webhook-id`) header in `to_signable_string` before computing/verifying the HMAC, or independently verify that `request.shop` corresponds to a shop with a known, previously-established session/installation before dispatching to handlers, rather than trusting the header value directly for tenant attribution.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, a normal, unprivileged action.
2. Attacker triggers a webhook (e.g., `orders/create`) on their own store, capturing the raw body `B` and the resulting `x-shopify-hmac-sha256` header `H`, which was computed by Shopify using the app's shared `client_secret`.
3. Attacker sends a request directly to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (valid), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` passes because it only checks `B` against `H`.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` invokes the registered handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"` and body `B`, letting the attacker inject data attributed to a shop they do not control.
