### Title
Bad-debt write-down clamps the supply index to a non-zero floor, resurrecting wiped-out supply shares into an unbacked claim that drains later depositors - ([File: contracts/pool/src/interest.rs])

### Summary
The bug class hinted by CVE-2018-18337 is use-after-free: memory logically released is later read as if still valid. The analog in XOXNO Lending is `apply_bad_debt_to_supply_index` (`contracts/pool/src/interest.rs:73-89`). When bad debt is socialized, the supply index is reduced pro-rata — economically "freeing" supplier claims. But when the write-down exceeds (or nearly exhausts) total supplied value, the result is clamped *up* to `SUPPLY_INDEX_FLOOR_RAW` instead of zeroing the claim. Positions that should be worthless retain a positive claim (`scaled × RAY/1000`), which the withdraw path later pays out in real tokens. The pool's own test `test_raw_cache_floor_clamp_strands_claim_without_supply_guard` (`contracts/pool/tests/interest.rs:372-428`) demonstrates a wiped position withdrawing exactly a fresh supplier's deposit.

### Finding Description
`apply_bad_debt_to_supply_index` computes `remaining = total_supplied_value - min(bad_debt, total_supplied_value)` and sets `supply_index = supply_index * remaining / total_supplied_value`, then applies `.max(SUPPLY_INDEX_FLOOR_RAW)` (`interest.rs:80-88`). The clamp is intended to keep the divisor non-zero, but it fires precisely when `remaining` collapses toward zero — i.e., on a near-total wipeout. After the clamp, every scaled supply share still unscales to `scaled × RAY/1000` of claim value even though the backing was fully written off. This is the use-after-free: the share objects were never destroyed (positions keep `scaled_amount`), and the index that should have zeroed them is instead pinned to a floor, so a "dead" position is read again by `resolve_withdrawal` and paid.

Path: `seize::apply` (`contracts/pool/src/ops/seize.rs:24-27`) calls `apply_bad_debt_to_supply_index` on the `Borrow` side, reachable from the controller's permissionless `clean_bad_debt` / bad-debt socialization flow. Once the index is clamped, the wiped account can call `withdraw` (debt was burned, so INV-ACCT-09's no-debt-without-supply check does not block it), and `withdraw::accounting` (`contracts/pool/src/ops/withdraw.rs:65-79`) resolves the claim and debits cash, passing `require_reserves` whenever any fresh cash exists.

### Impact Explanation
After a bad-debt wipeout, the holder(s) of the wiped position retain a claim equal to `scaled × 10^-3` in RAY terms, backed by nothing. Any subsequent supplier's deposit becomes withdrawable by the wiped position up to that phantom amount, which the test shows drains the fresh deposit exactly (`gross == fresh_cash`, leaving `cash < fresh_claim`). This is theft of user funds / protocol insolvency: the pool pays out tokens it no longer has claim backing for, and the honest fresh supplier is left undercollateralized. The magnitude per victim is bounded by the residual claim (≈0.1% of the wiped supply value), but it is a direct, unprivileged transfer of later depositors' principal to the owner of a position that was economically zeroed.

### Likelihood Explanation
Requires a market wipeout severe enough that `bad_debt` drives the computed index below `RAY/1000` — i.e., bad debt exceeding ~99.9% of supplied value in that market. `clean_bad_debt` is permissionless (it is in the unprivileged entrypoint set and remains callable even under global pause), and bad debt arises whenever a position's collateral cannot cover its debt at seizure. An attacker can manufacture this with their own funds: supply collateral, borrow to the limit, let the collateral price fall (or push it on thin Aquarius/Soroswap markets they trade on themselves), allow liquidation to leave dust/excess bad debt, then trigger `clean_bad_debt`. The final drain requires only that someone supplies the market afterward — which the attacker can also do via a second account to confirm exploitability, though profit requires third-party deposits. The precondition (near-total wipeout) is severe but achievable, and the protocol's own invariant docs acknowledge the floor "can preserve an unbacked residual claim" (INV-IDX-02, `docs/reference/invariants.md:240-248`).

### Recommendation
When the write-down would push the supply index below `SUPPLY_INDEX_FLOOR_RAW`, do not clamp the index upward and leave shares live; instead either (a) burn the remaining supplied shares / zero the market so wiped positions unscale to zero, or (b) treat a floor-clamped index as a market-reset event and refuse withdrawals of pre-wipeout positions (e.g., store a wipeout generation counter and reject claims stamped before it). At minimum, gate `resolve_withdrawal` on a market that hit the floor so a position whose claim exists only because of the clamp cannot withdraw against unrelated cash.

### Proof of Concept
Provided by `contracts/pool/tests/interest.rs:372-428` (`test_raw_cache_floor_clamp_strands_claim_without_supply_guard`):

```rust
// market state: supplied = 1000*RAY shares, index = RAY, cash = 0
apply_bad_debt_to_supply_index(&mut cache, Ray::from(5_000 * RAY));
// supply_index clamps UP to SUPPLY_INDEX_FLOOR_RAW (RAY/1000), not to 0
let stranded = cache.unscale_supply_floor(old_scaled); // > 0: phantom claim

// fresh supplier deposits `stranded` tokens and mints shares
cache.mint_supply(fresh_scaled);
cache.credit_cash(fresh_cash);

// wiped account withdraws: resolve_withdrawal returns gross == fresh deposit
let (burn, gross) = cache.resolve_withdrawal(i128::MAX, old_scaled);
cache.burn_supply(burn);
cache.debit_cash(gross);
// cache.cash() < fresh supplier's claim -> depositor's funds are gone
```

On-chain reachability: attacker supplies collateral, borrows to the LTV limit, the position goes underwater, partial liquidations leave residual bad debt; anyone calls `clean_bad_debt(account_id)` which routes through `seize` → `apply_bad_debt_to_supply_index`, clamping the index. The wiped account owner then calls `withdraw` after a victim supplies the same market, extracting the victim's tokens via the phantom claim.

Note on uncertainty: the docs (`INV-IDX-02`) explicitly acknowledge the floor "can preserve an unbacked residual claim," so this may be argued a documented design trade-off; however, the documented bound describes claim *valuation*, while the demonstrated consequence — a wiped position withdrawing a later depositor's principal — is a concrete fund-loss path the pool's own audit test flags as unguarded.
