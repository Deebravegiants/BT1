This confirms a strong analog. The `qr-code` agent runs as an isolated process (`agentwire::agent::Process`) that decodes a QR code — attacker-controlled data scanned by an unprivileged user — into an `Output { payload: String, points: Points }` struct, which is serialized with `rkyv` and sent back to the trusted broker process over shared memory. The broker deserializes it via `deserialize_message` in `agentwire/src/port.rs`, which calls the inherently `unsafe` `rkyv::archived_root` without any `bytecheck`/`check_archived_root` validation, trusting the byte layout produced by the (potentially compromised) `qr-code` subprocess.

### Title
Unvalidated `rkyv::archived_root` deserialization of untrusted process-agent IPC output enables cross-process memory corruption - ([File: agentwire/src/port.rs])

### Summary
The `qr-code` agent is explicitly documented as a process-based agent used "to run untrusted or unreliable code" [1](#0-0) , since it directly parses attacker-controlled QR-code image data scanned by an unprivileged user via `rxing` in `decode_rxing` [2](#0-1) . The resulting `Output` is serialized into a fixed-size shared-memory buffer and read back by the trusted broker process using `deserialize_message`, which calls the unsafe, unchecked `rkyv::archived_root::<T>(bytes)` [3](#0-2) . This mirrors the Firedancer `fd_bank`/`fd_pack` bug class: data crossing a sandboxed-process IPC boundary is trusted and directly interpreted as a well-formed structured type without validating its internal layout/offsets, which can corrupt memory in the receiving (more privileged/trusted) process if the sending process is compromised.

### Finding Description
`agentwire`'s shared-memory IPC channel is the mechanism by which isolated process-agents (documented as sandboxes for "untrusted or unreliable code") communicate results back to the main `orb-core` broker process [4](#0-3) . The `qr-code` agent, which decodes fully attacker-controlled QR-code payloads from the camera in `decode_rxing`, sends its `Output` (containing a `String` payload and `Points` vector) through `port.try_send` [5](#0-4) .

On the write side, `serialize_message` writes a `usize` length prefix followed by the rkyv-serialized bytes into a fixed-size shared-memory slot [6](#0-5) . On the read side (executed in the trusted broker/parent process), `spawn_shared_tx_task` calls `deserialize_message::<T::Output>` on the raw shared-memory bytes [7](#0-6) :

```rust
let archived = deserialize_message::<T::Output>((*shared_memory).output());
let value = archived.deserialize(&mut SharedDeserializeMap::new()).unwrap();
```

`deserialize_message` reads a length header, carves out a byte slice, and calls `rkyv::archived_root::<T>(bytes)` [3](#0-2) :

```rust
unsafe fn deserialize_message<T>(buf: &[u8]) -> &T::Archived
where
    T: Archive + for<'a> Serialize<SharedSerializer<'a>>,
{
    let size = usize::from_ne_bytes(buf[..mem::size_of::<usize>()].try_into().unwrap());
    let bytes = &buf[mem::size_of::<usize>()..mem::size_of::<usize>() + size];
    unsafe { rkyv::archived_root::<T>(bytes) }
}
```

`rkyv::archived_root` performs no validation of the archive's internal relative pointers/offsets/lengths (that is what `check_archived_root`/`bytecheck` exists for, and it is not used anywhere in this crate — the only matches for `archived_root`/`bytecheck` in the codebase are this single call site and `Cargo.lock` entries). If the `qr-code` subprocess is compromised (e.g. through a vulnerability in the `rxing` QR decoding logic triggered by a crafted physical QR code, which is squarely an unprivileged-user-controlled input), it can write a byte sequence into the shared-memory `Output` slot whose internal offsets/lengths for the `String`/`Vec` fields point outside the buffer. When the broker's `.deserialize(...)` walks these archived fields, it can read out-of-bounds shared-memory or process memory, producing memory corruption in the trusted broker process — the same class of "cross sandboxed-process IPC boundary, unchecked structured data, memory corruption" bug reported for Firedancer's `fd_bank`/`fd_pack`.

This same unchecked `deserialize_message` path is shared by every process-based agent (`ir_net`, `iris`, `rgb_net`, `occlusion`, `face_identifier`, `mega_agent_one`/`two`), all of which use `SharedPort`/`RemoteInner` and inherit the identical trust assumption [8](#0-7) .

### Impact Explanation
A compromised process-agent (most plausibly the `qr-code` agent, whose entire purpose is to parse untrusted, physically-scanned QR-code data) can leverage this unchecked deserialization to corrupt memory in the trusted `orb-core` broker process. Because the broker process is responsible for orchestrating the signup/enrollment flow (QR-code parsing feeds into signup/session identity binding), a successful exploit here could lead to code execution or state corruption in the main process that drives signup authorization, i.e. cross-signup state bleed or misattributed signup, matching the accepted impact categories.

### Likelihood Explanation
Exploitation requires first compromising the `qr-code` (or another) process-agent, which is exactly the same precondition assumed in the original Firedancer report (attacker achieves code execution in `fd_pack` first). The likelihood of achieving that initial compromise depends on bugs in `rxing`'s QR decoding of attacker-supplied QR-code images — a purely unprivileged, external, attacker-controlled input vector — making this a realistic two-stage but non-hypothetical exploit chain rather than a requirement for a malicious operator/insider.

### Recommendation
- Replace the unchecked `rkyv::archived_root` call in `deserialize_message` (`agentwire/src/port.rs`) with `rkyv::validation::validators::check_archived_root` (or equivalent `bytecheck`-validated API) before dereferencing/deserializing the archive, for both the `T::Input` and `T::Output` paths.
- Bound-check the `size` value read from the shared-memory header against the buffer length before slicing (`buf[mem::size_of::<usize>()..mem::size_of::<usize>() + size]`) to avoid relying solely on Rust's panic-on-OOB behavior.
- Treat all process-agent output as untrusted input in the broker, consistent with the documented sandboxing intent in `agentwire/src/lib.rs`.

### Proof of Concept
1. Modify the `qr-code` agent process (analogous to modifying `fd_pack.c` in the original report) to, upon detecting a magic QR payload string, directly overwrite the shared-memory `Output` buffer's internal rkyv-relative offset/length fields for the `payload: String` field with out-of-bounds values before calling `port.try_send`.
2. Run `orb-core` with this modified `qr-code` binary and present the magic QR code to the camera.
3. Observe that the broker's `spawn_shared_tx_task` → `deserialize_message::<Output>` → `.deserialize(...)` call in `agentwire/src/port.rs` reads/writes outside the shared-memory buffer bounds, crashing or corrupting the broker process — mirroring the `blake3_hash_many_avx2` OOB crash triggered by the malicious `fd_txn_p_t.payload_sz` in the original report.
