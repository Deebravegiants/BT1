### Title
Cross-Tenant Webhook Confusion via Unbound `shop-domain` Header - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
The Zcash advisory's root cause is a binding break: the block *header* commitment (`hashBlockCommitments`) is not checked before the body is accepted and cached, so the body's authorizing data is trusted for an identity (the block hash) it doesn't cryptographically match. The analogous binding in this gem's webhook path is: `shop == HMAC(shop, body, secret)`. In `ShopifyAPI::Webhooks::Registry.process`, only the raw body bytes are HMAC-verified; the `shop` (and `topic`/`webhook_id`) values are read from unauthenticated HTTP headers and handed to the app's handler as trusted tenant identity, breaking the equality `verified_bytes == identity_used`.

### Finding Description
`Registry.process` validates only:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
``` [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature only over `request.to_signable_string`, which is the raw request body: [2](#0-1) [3](#0-2) 

The `shop`, `topic`, and `webhook_id` are read straight from headers with no cryptographic binding to the HMAC: [4](#0-3) 

`process` then forwards this unauthenticated `request.shop` value directly into `WebhookMetadata`, which is the value the host app's handler receives and is expected to use as the tenant identifier: [5](#0-4) 

Because the HMAC secret (`api_secret_key`) is the app's single client secret, shared across *every* installed shop for that app — not a per-shop secret — a valid `hmac-sha256` signature over a body only proves "this body was produced/known by someone with the app's secret" (e.g., a legitimately installed low-privilege shop that receives real webhooks), not "this body/shop pairing is authentic." An unprivileged actor who controls one shop where the app is installed receives real webhooks with valid HMACs computed with the shared secret, and can then replay that exact raw body with the `x-shopify-shop-domain` header changed to a different (victim) shop's domain. `HmacValidator.validate` still passes because it only checks the body bytes, so `Registry.process` will invoke the handler with `shop: "victim-shop.myshopify.com"` even though the body's real origin is the attacker's own shop.

### Impact Explanation
This breaks the identity binding a webhook consumer relies on: `shop` is meant to scope data writes/reads to the correct tenant. If the host application (per this gem's documented `WebhookMetadata#shop` contract) uses that value to select the tenant's session/store record for processing the webhook payload (e.g., `orders/create`, `app/uninstalled`, GDPR topics), an attacker with any shop where the app is installed can inject attacker-controlled but "HMAC-valid" data attributed to a victim shop — a cross-tenant data-poisoning/confusion primitive, matching the report's "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Requires only that the attacker control (or be) one shop where the app is installed (an "unprivileged internet user" in the sense that no elevated app credentials, access tokens, or the app's `client_secret` are needed — just observation of one legitimate webhook body+HMAC pair they legitimately received) and the ability to POST to the app's public webhook endpoint with modified headers. No TLS interception, social engineering, or leaked credentials required.

### Recommendation
`Registry.process` (or `Request`) should bind the authenticated `shop` to the request by validating it against the shop known to be associated with the webhook subscription (e.g., via `webhook_id` looked up server-side, or by having the host app pass the expected shop and asserting equality) before dispatching to the handler, rather than trusting the unauthenticated header value as tenant identity.

### Proof of Concept
1. App is installed on attacker's own shop `attacker.myshopify.com`; attacker receives a real webhook POST with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared `api_secret_key`).
2. Attacker resends the identical body `B` and HMAC `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `B` [2](#0-1) .
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)` [5](#0-4) , causing the host app to process attacker-controlled data under the victim shop's identity.
