### Title
Webhook `shop` identity field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` (and `topic`, `webhook_id`) values come from separate, unauthenticated HTTP headers. `Registry.process` validates the HMAC and then forwards the header-derived `shop` value to the app's handler as if it were an authenticated field, breaking the binding `hmac-authenticated bytes == identity fields acted upon`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `shop` is read from a separate header that is never mixed into the signed bytes: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the body) against the HMAC secret shared by the whole app (`Context.api_secret_key`), not per shop: [3](#0-2) 

`Registry.process` treats a successful HMAC check as authorizing use of `request.shop` and forwards it, unauthenticated, to the app's webhook handler: [4](#0-3) 

Because `Context.api_secret_key` is a single value shared across every shop that has installed the app (it is the app's client secret, not a per-shop secret), an entity that controls one legitimate installation of the app can obtain a genuinely-signed `(raw_body, hmac)` pair from Shopify (e.g. by triggering an `orders/create` webhook on their own store), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header for a different, victim shop. `HmacValidator.validate` still succeeds because it never inspects the shop header, so `Registry.process` calls the handler with `WebhookMetadata` claiming the payload originated from the victim shop, even though the body/content belongs to the attacker's own store.

### Impact Explanation
This breaks the identity binding `shop-claimed-in-request == shop-actually-authenticated-by-HMAC`. Any host application that uses `WebhookMetadata#shop` for tenant-scoped operations (associating orders/products/customers with a specific merchant's records, looking up that shop's session, updating per-shop data) can be made to process attacker-supplied payload content under another tenant's identity — a cross-tenant data-integrity/access issue satisfying the Critical "cross-tenant access" impact category, since the library itself provides and validates this field as if it were authenticated.

### Likelihood Explanation
Requires the attacker to have (or create) at least one legitimate installation of the target app (a normal, unprivileged capability for any Shopify merchant, since app installation itself needs no special privilege), plus the ability to POST arbitrary headers to the app's public webhook endpoint (trivial, it's just an HTTP callback URL). No secrets, tokens, or elevated access are required beyond what any merchant already has via a self-service install. Exploitability is otherwise deterministic since the same `api_secret_key` is used for HMAC validation across all shops of the app.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the HMAC-verified data, or otherwise independently verify that the `X-Shopify-Shop-Domain` header corresponds to a shop with an active session/installation known to the host app before trusting it, rather than passing it through unauthenticated in `WebhookMetadata` once only the body HMAC has been checked.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger a real event (e.g., create an order) so Shopify sends a webhook with a valid `hmac-sha256` computed over the JSON body using the app's `api_secret_key`.
2. Capture the raw body and the `X-Shopify-Hmac-Sha256` header from that legitimate request.
3. Replay a POST to the app's webhook endpoint with the same raw body and HMAC header, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` (via `lib/shopify_api/utils/hmac_validator.rb`) passes because it only checks the body bytes against the shared secret.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the handler with `shop: "victim.myshopify.com"` even though the payload content is the attacker's own order data, demonstrating the unauthenticated shop-identity confusion.
