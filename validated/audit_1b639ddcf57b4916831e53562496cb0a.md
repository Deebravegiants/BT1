### Title
Webhook shop-domain identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic if `Utils::HmacValidator.validate(request)` succeeds, and then forwards `request.shop` (an unauthenticated header value) to the app's handler as the tenant identifier. Because the HMAC only signs the raw body — never the `shop-domain` header — a shop that legitimately installs the app can capture one of its own genuine webhook deliveries (valid body + HMAC, since Shopify signs it with the app's secret) and replay that exact body/signature pair against the app's webhook endpoint while substituting a victim shop's domain in the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header. The signature still validates, so the host application's handler is invoked believing the data belongs to the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `#shop` is read straight from an attacker-controlled HTTP header with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates the HMAC purely against that signable string (the body) and, on success, passes `request.shop` straight into the metadata handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (the body) against the secret — it never incorporates `shop`: [4](#0-3) 

The identity binding that should hold is: `hmac_verified(body) == true` should imply `shop_header == shop_that_body_actually_belongs_to`. In this gem that equality does not hold, because `shop` is entirely outside the signed byte range. The library's own documentation reinforces the false assumption, stating that `Registry.process` "will verify the request did indeed come from Shopify," and recommends host apps dispatch background jobs keyed on `data.shop`: [5](#0-4) [6](#0-5) 

### Impact Explanation
Any unprivileged internet user who can install the app on their own (attacker-controlled) shop can obtain a genuine, validly-HMAC-signed webhook body/signature pair (e.g., by triggering an `orders/create` webhook on their own store). They can then replay that exact body and HMAC to the app's webhook endpoint with the `shop-domain` header set to a victim merchant's domain. The signature check passes, and the app's handler executes with `data.shop` equal to the victim's domain while `data.body` is attacker-controlled content from the attacker's own store. Any host application that follows this gem's documented pattern of keying persistence/business logic off `data.shop` (as the docs literally recommend) will attribute attacker-supplied data to the victim tenant — a cross-tenant data-integrity/confusion attack reachable without any credentials, satisfying the Critical "cross-tenant access" impact bar.

### Likelihood Explanation
Likelihood is Medium-to-High: exploitation requires only that the attacker be a legitimate, unprivileged merchant of the same app (a normal, unprivileged install — no special access, no leaked secrets, no social engineering), and standard HTTP tooling to replay the captured request with one header changed. No knowledge of `api_secret_key` is needed since the attacker reuses a signature Shopify already computed for them.

### Recommendation
Bind the tenant identity into the verified material before it is trusted. Concretely: include `shop-domain` (and ideally `topic`/`webhook-id`) with the raw body in `to_signable_string`, or — since header inclusion is dictated by Shopify's own signing scheme and can't unilaterally be changed — have `Registry.process` cross-check `request.shop` against an expected/known shop that the caller supplies out-of-band (e.g., require the host app to pass the shop it expected for that route/session and reject mismatches), rather than trusting the header as an implicit, HMAC-covered value. At minimum, update the documentation to make clear that `data.shop`/`data.topic` are **not** covered by the HMAC and must be independently validated (e.g., against a known list of installed shops) before being used as a tenant key.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and registers for `orders/create`.
2. Attacker creates an order, triggering Shopify to POST a real webhook to the app's endpoint with headers `shopify-shop-domain: attacker.myshopify.com`, `shopify-topic: orders/create`, `shopify-hmac-sha256: <valid HMAC of raw_body>`.
3. Attacker intercepts/replays this exact request to the same endpoint but rewrites the header to `shopify-shop-domain: victim.myshopify.com` (body and HMAC unchanged).
4. `ShopifyAPI::Webhooks::Registry.process` runs:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
# validation succeeds because HmacValidator only checks the body
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
# request.shop == "victim.myshopify.com" even though the body came from attacker's own shop
``` [3](#0-2) 
5. The host app's handler (per the gem's own documented pattern) processes/persists attacker-controlled data under the victim's tenant identifier.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
