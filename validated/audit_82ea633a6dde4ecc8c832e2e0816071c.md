## Title
Webhook signature covers only the raw body, not `shop-domain`/`topic`/`webhook-id` headers, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `api_version`, and `webhook_id` are all read from unauthenticated headers and handed to the app's webhook handler untouched. `Utils::HmacValidator.validate` verifies the HMAC exclusively against this body-only signable string. Consequently, any request carrying a body+HMAC pair that was legitimately produced for *one* shop/topic can be replayed with a different `x-shopify-shop-domain` or `x-shopify-topic` header and will still pass HMAC validation, because those identity-bearing fields are never part of the signed material.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `shop`, `topic`, `api_version`, `webhook_id` are all pulled straight from headers with no cryptographic tie to the body or to each other: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which only calls `verifiable_query.to_signable_string` (i.e., the raw body) through `compute_signature`, and then immediately dispatches to the handler using the unauthenticated `request.shop` / `request.topic`: [3](#0-2) [4](#0-3) 

The identity binding that should hold is:
`hmac_signed_bytes == bytes_that_determine(shop, topic, webhook_id)`

but in this implementation:
`hmac_signed_bytes == raw_body` only, while `shop`/`topic`/`webhook_id` are attacker-controlled headers that are trusted downstream (`WebhookMetadata.new(topic:, shop:, ...)`), breaking the equality the app relies on to attribute a webhook event to the correct tenant.

Since the app's `client_secret` (used to compute the HMAC) is shared across every shop that has the app installed, any merchant who has the app installed can obtain a validly-signed `(body, hmac)` pair simply by triggering a real webhook event on their own store (e.g. via the Shopify Admin actions that fire webhooks) — no secret leakage or privileged access is required. That merchant can then replay the exact same body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) for a different shop/topic. `HmacValidator.validate` still returns `true` because it never inspects those headers, and `Registry.process` passes the attacker-chosen `shop`/`topic` straight to the registered handler.

### Impact Explanation
This crosses a tenant boundary without any additional secret: an unprivileged app user (any merchant who has installed the app) can cause the app to process webhook data under the identity of an arbitrary other shop. Depending on what the host app's webhook handler does with `WebhookMetadata#shop` (e.g. updating that shop's stored settings/state, crediting an action, invalidating a cache entry, or triggering a shop-scoped side effect), this results in cross-tenant data manipulation — satisfying the "Critical: cross-tenant access" bar in the rubric, since the shop identifier that gates per-tenant behavior is not bound to the signature that is supposed to authenticate the request.

### Likelihood Explanation
Likelihood is high for any app that has more than one shop able to trigger the same webhook topic/handler: the attacker needs only (a) the app installed on their own shop so they can generate one legitimately signed webhook body, and (b) the ability to POST to the app's public webhook endpoint with custom headers, which is inherent to how webhook delivery is received (no mTLS or IP allow-listing is enforced by this gem). No access token, `api_secret_key`, or privileged role is required — only being an ordinary app user.

### Recommendation
Bind the identity fields into the signed material, or independently verify them:
- Prefer verifying `shop` against a known/installed-shop list (session store) before trusting `request.shop`, rather than relying on the header alone.
- Alternatively (matching the analog's stated mitigation of adding the missing field to the hash), include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified — e.g. compute the signature over a canonical string of `raw_body + shop-domain + topic + webhook-id` instead of `raw_body` alone — so a signature computed for one shop/topic cannot be replayed for another.
- At minimum, document/enforce that consuming applications must cross-check `request.shop` against their own session/shop registry before acting on the payload, since this gem does not do so.

### Proof of Concept
1. App merchant A has the app installed; a genuine webhook fires for shop A, producing body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(client_secret, B)`.
2. Attacker (merchant A) captures `(B, H)` from their own store's webhook delivery (trivially available to any app user via their own webhook logs/proxy).
3. Attacker POSTs to the app's webhook endpoint with the same body `B` and header `H`, but sets:
   - `x-shopify-shop-domain: shop-b.myshopify.com` (a victim shop that also has the app installed)
   - `x-shopify-topic:` any topic registered by the app
4. `HmacValidator.validate` recomputes `HMAC(client_secret, B)` — using only the raw body per `Request#to_signable_string` — and it matches `H`, so validation succeeds.
5. `Registry.process` looks up the handler by the attacker-supplied topic and invokes it with `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)`, causing the app to execute shop-B-scoped logic using attacker-supplied data, even though shop B never sent this webhook.
