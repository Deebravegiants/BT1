## Analysis Result

### Title
Reentrancy via low-level call before storage decrement in `withdraw()` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.withdraw()`, invoked from `onAccept()` for `RedeemEscrow`/`RefundEscrow` requests, performs a low-level ETH/ERC-20 transfer to the beneficiary **before** decrementing the corresponding `_orders[commitment][token]` escrow accounting, and again transfers the accumulated transaction fee before clearing `_orders[commitment][TRANSACTION_FEES]`. This mirrors the report's root cause exactly: a low-level call executed prior to completing storage updates, violating Checks-Effects-Interactions.

### Finding Description
In `withdraw()`, for each token in the withdrawal body, the ETH/ERC-20 transfer is dispatched via `beneficiary.call{value: amount}("")` or `token.call(...)` and only afterward is `_orders[body.commitment][token] -= amount` applied: [1](#0-0) 

The same pattern repeats for the transaction-fee payout, where `feeToken.call(...)` is issued and only afterward is `_orders[commitment][TRANSACTION_FEES]` deleted: [2](#0-1) 

While `_filled[body.commitment] = beneficiary` is set at the top of `withdraw()` — protecting `fillOrder()` reentry, as validated by `IntrinsicIntentsReentrancyTest.sol` — nothing in `withdraw()` itself guards against the escrow-accounting mapping (`_orders`) being read/used again for the same commitment/token before it is decremented. Any recipient controlled by the caller (a malicious beneficiary contract for the native-ETH branch, or a token with transfer-hook/callback semantics for the ERC-20 branch) executes arbitrary code mid-transfer, before `_orders[...]` reflects the paid-out amount. `withdraw()` is only reachable through `onAccept()`'s `RedeemEscrow`/`RefundEscrow` branches: [3](#0-2) 

### Impact Explanation
If the escrow-accounting state (`_orders[commitment][token]`) can be observed/relied upon again by the recipient's reentrant call before it is decremented — e.g., through a duplicate delivery of the same or a related ISMP request touching the same commitment while the first `withdraw()` invocation is still on the call stack — the same escrowed balance could be paid out more than once, resulting in direct loss of user/protocol escrowed funds (unbacked withdrawal analogous to unbacked mint/theft of funds).

### Likelihood Explanation
This requires the withdrawal beneficiary (or fee token) to be attacker-controlled and capable of re-entering the contract during the native-ETH/`call`-based transfer, and for the escrow bookkeeping to still reflect a non-zero balance during that reentrant window. The report's original bug class (low-level-call before storage finalize) is directly present here at the source-code level; whether it can be chained into a full duplicate-payout requires that a second `onAccept` call for the same commitment/token can reach `withdraw()` before the first call's `_orders[...] -= amount` executes — a scenario gated by the ISMP relayer/duplicate-message protections in `HandlerV2`/`EvmHost`, which I was not able to fully trace within the available index in this session.

### Recommendation
Apply Checks-Effects-Interactions: decrement `_orders[body.commitment][token]` (and delete/zero the fee entry) **before** performing the native/ERC-20 transfer in `withdraw()`, for both the per-token loop and the transaction-fee payout.

### Proof of Concept
Not independently verified with a working exploit in this session; the CEI violation is confirmed by direct code inspection at [4](#0-3) , matching the report's bug class (low-level call before storage update completes). Full exploitability depends on the duplicate-message/receipt-ordering guarantees of `EvmHost.dispatchIncoming`, which could not be confirmed with the tools available in this session — a Devin session with full repository access would be needed to trace `EvmHost.sol`'s exact `requestReceipts` write-ordering relative to the `onAccept` callback to confirm end-to-end reentrant double-payout.
