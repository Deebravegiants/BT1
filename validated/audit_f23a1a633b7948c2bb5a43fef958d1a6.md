### Title
Webhook `shop` domain is trusted without being covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, while the `shop` (tenant identity) used by the handler is read from an unauthenticated header that is never part of the signed bytes. Because the app's `client_secret` (`api_secret_key`) is shared across every shop that installs the app, any merchant who installs the app can capture a legitimately-signed webhook from their own store and replay it against the app's webhook endpoint with the `shop-domain` header swapped to a victim shop, producing a webhook the app will accept and attribute to the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is pulled straight from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header, which is never included in the signable string: [2](#0-1) 

`Registry.process` validates only the body's HMAC via `Utils::HmacValidator.validate(request)`, then hands `request.shop` straight to the handler as the tenant identity, with no independent check that this shop matches anything cryptographically bound to the signed payload: [3](#0-2) 

`Utils::HmacValidator.validate_signature` confirms only that the body bytes were signed with `Context.api_secret_key` — it says nothing about which shop the signature was issued for: [4](#0-3) 

The broken identity binding, stated as an equality that should hold but doesn't:
`shop_bound_by_signature == shop_used_by_handler`
In fact `shop_bound_by_signature` doesn't exist at all — the signature only binds `raw_body`, so `shop_used_by_handler` (`request.shop`) can be any value the requester sets in the header, independent of what was actually signed by Shopify for that body.

Because `client_secret` is a single shared secret per **app** (not per **shop**), an unprivileged party — a merchant who simply installs the app on their own store, the least privileged interaction possible with a Shopify app — receives real webhooks from Shopify signed with that same shared secret. They can:
1. Capture one legitimately-signed webhook delivered to their own store (valid `body` + valid `hmac`, both attributable to secret `S`).
2. Replay that exact `body`/`hmac` pair to the app's webhook endpoint, but change only the `X-Shopify-Shop-Domain` header value to a victim shop's domain.
3. `HmacValidator.validate` still passes (it never looked at the shop header), so `Registry.process` calls the handler with `WebhookMetadata.new(shop: <victim-domain>, ...)` and the attacker's own body content, causing the app to process attacker-controlled data as though it originated from the victim tenant.

### Impact Explanation
This crosses the tenant boundary that the webhook signature is supposed to enforce: it lets an unprivileged app installer forge webhook events (e.g. spoofing `app/uninstalled`, `shop/redact`, `customers/data_request`, or order/product update topics) attributed to any other shop domain, without ever needing that victim's credentials. This satisfies the "cross-tenant access" Critical-impact category, since app logic keyed off `WebhookMetadata#shop` (e.g., per-shop data stores, uninstall/redaction/session-clearing flows) can be triggered or poisoned for a shop the attacker does not control.

### Likelihood Explanation
Likelihood is high for any app that installs on more than one merchant and relies on this gem's `Webhooks::Registry`/`Request` for handling: the attacker needs no special privilege beyond installing the app on their own shop (a completely ordinary, unprivileged action), and capturing/replaying an HTTP request with a modified header is trivial. No knowledge of `api_secret_key` or any victim credential is required.

### Recommendation
Bind the `shop` header into the HMAC-signed material (as Shopify's own signing already covers headers is not the case here, so the gem should include the shop domain, together with the raw body, in `to_signable_string`), or otherwise require callers to pass the expected shop and assert it matches `request.shop` before invoking the handler. At minimum, document/enforce that host apps must independently correlate `request.shop` against a shop known to be associated with the specific webhook subscription (e.g., via webhook ID lookup) rather than trusting the header value as authenticated.

### Proof of Concept
1. App is installed on attacker's own shop `attacker.myshopify.com` and on victim's shop `victim.myshopify.com` (multi-tenant same app, shared `client_secret`).
2. Shopify delivers a legitimate webhook to the app for `attacker.myshopify.com`:
   - Headers: `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - Body: attacker-controlled JSON (e.g. crafted order payload), since it's the attacker's own store, they fully control the body content and this is delivered with a genuinely valid HMAC.
3. Attacker replays this exact HTTP request to the app's public webhook endpoint, changing only the header value:
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
4. The endpoint constructs `ShopifyAPI::Webhooks::Request.new(raw_body: <same body>, headers: <modified headers>)` and calls `ShopifyAPI::Webhooks::Registry.process(request)`.
5. `Utils::HmacValidator.validate(request)` returns `true` because it only rehashes `@raw_body`, which is unchanged.
6. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: <attacker's data>, ...)`, causing the app to act on attacker-controlled data under the victim shop's identity — e.g. corrupting victim per-shop state, or triggering shop-scoped side effects (uninstall/redact handling, order sync, etc.) for a tenant the attacker does not control.
