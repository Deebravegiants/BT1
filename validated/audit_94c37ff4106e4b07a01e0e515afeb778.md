### Title
FIFO subscription eviction in `pallet-bandwidth` lets any payer permanently destroy another app's prepaid bandwidth via 1024 cheap dust purchases - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth`'s `Allowance` storage is a per-`(app_chain, app)` FIFO list of `Subscription`s capped at `MAX_SUBSCRIPTIONS = 1024` [1](#0-0) . Any chain can dispatch a purchase message that credits bandwidth to *any* `(app_chain, app)` pair — the pallet explicitly documents that "any deployment can sponsor any app on any chain" [2](#0-1) . When the list is full, `push_subscription` unconditionally evicts index `0` (the oldest, which may still hold substantial unused prepaid bytes) to make room for the new entry, with no check on the *value* or ownership of what is being evicted [3](#0-2) .

This is the same bug class as the Velodrome `_burn()` finding: a bounded, per-victim structure (`dstRep` there, `Allowance[app_chain][app]` here) can be filled by an attacker with worthless/dust entries until it hits its cap, and the structure has no way to protect entries that legitimately belong to the honest party — the cheapest, newest attacker entries simply displace the victim's real, valuable ones.

### Finding Description
`push_subscription` is the single insertion path used both by real purchases (`on_accept`, triggered by any relayed `PurchaseMessage` from a registered `BandwidthManager` contract) and by admin `force_credit` [4](#0-3) . The `Allowance` map is keyed by `(app_chain, app)`, not by the *payer* — the payer (`request.source`) is only recorded for the event, and is deliberately decoupled from the app being credited so "sponsorship" works [5](#0-4) .

Because:
1. Any account able to trigger a purchase message (via `BandwidthManager.sol`'s purchase flow) can target an arbitrary `(app_chain, app)` pair, not just their own app.
2. Each purchase — even the cheapest tier at the shortest duration — appends one more `Subscription` entry to that pair's bounded list.
3. Once the list reaches `MAX_SUBSCRIPTIONS` (1024), each further insertion evicts `list.remove(0)` — the oldest entry — regardless of how many bytes remain unconsumed on it, and emits `SubscriptionEvicted` with the lost bytes, but performs no restitution [6](#0-5) .

an attacker can repeatedly purchase the cheapest configured tier (`TierIndex::TierOne`) against a victim app's `(app_chain, app)` key. Once the list saturates at 1024 entries, every additional dust purchase evicts one victim subscription — including ones that still carry large unused `remaining_bytes` from an expensive, long-duration tier the victim legitimately paid for. Repeating this 1024+ times (or however many entries the victim currently holds) permanently destroys the victim's prepaid, unconsumed bandwidth allowance with no possibility of recovery — the bytes are gone and the event only logs the loss after the fact.

This mirrors the report's root cause precisely: a bounded per-target list that grows on an action any third party can trigger, with no decrement/preservation logic tied to entry value or ownership, letting an attacker force out the victim's legitimate state purely by volume of cheap transactions.

### Impact Explanation
This is a concrete, permanent loss-of-funds vector: an app that has paid real value (e.g., `TierFour`, many months, deep prepaid byte balance) for cross-chain messaging bandwidth can have that balance evicted and destroyed by an attacker spending only the cost of 1024 minimum-tier, minimum-duration purchases. Once evicted, the `BandwidthGate::try_consume` check in the ISMP router will reject the victim's genuine ISMP dispatches for insufficient/absent allowance, effectively denying the app the ability to send messages through Hyperbridge until it repurchases — a direct financial loss plus an availability/DoS impact on message dispatch, which the scope explicitly recognizes as a valid impact (route/app unable to operate due to a forged/attacker-controlled state transition).

### Likelihood Explanation
The purchase path is permissionless by design (the pallet's own module docs state "any deployment can sponsor any app on any chain"), and the cost to the attacker is bounded by 1024 × (price of the cheapest configured tier at 1 month) — a cost the pallet's own admin/tier configuration does not defend against, since `set_tier` only enforces `bytes > 0 && duration_secs > 0`, not any minimum price relative to the cap-filling cost [7](#0-6) . Any competitor of an app, or any actor wishing to grief a specific `(app_chain, app)` pair, can execute this without special privileges, matching the "always griefable by a rolled address" reasoning the original judge used to justify Medium severity.

### Recommendation
- Scope `Allowance` eviction so it cannot destroy another payer's unused entries: e.g., track subscriptions per `(app_chain, app, payer)` rather than merging all payers into one FIFO list, or
- Reject/queue new purchases once the list is full instead of silently evicting the oldest live (non-expired, non-zero remaining_bytes) entry, or
- Only allow eviction of *expired* or *zero-remaining* entries, refusing the purchase (or requiring an explicit swap) if no evictable slot exists, so attacker purchases cannot destroy value a victim has already paid for.

### Proof of Concept
1. Victim's app on `(app_chain, app)` legitimately purchases `TierFour` for many months, crediting a `Subscription` with large `remaining_bytes` and long `expires_at`, appended to `Allowance[app_chain][app]`.
2. Attacker (any account, from any registered source chain's `BandwidthManager`) repeatedly triggers `on_accept` purchase messages of `TierOne` (cheapest, 1 month) targeting the same `(app_chain, app)` key, via `push_subscription` [8](#0-7) .
3. After enough dust purchases fill the list to `MAX_SUBSCRIPTIONS = 1024`, each subsequent attacker purchase evicts `list.remove(0)` [9](#0-8) ; once the eviction pointer reaches the victim's `TierFour` entry, it is destroyed and `SubscriptionEvicted{ lost_bytes }` is emitted for the victim's still-unused bytes.
4. Victim's subsequent ISMP dispatches on `(app_chain, app)` are throttled/rejected by `BandwidthGate::try_consume` for insufficient allowance, even though the victim paid for and never consumed those bytes.

Note: I was unable to fully inspect `evm/src/apps/BandwidthManager.sol`'s exact pricing/access-control logic (e.g., whether `purchase()` enforces a minimum price floor or restricts callers) within the available index; a Devin session with full repo access should confirm the exact per-purchase cost floor to precisely quantify attacker cost before remediation.

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

	impl<T: Config> IsmpModule for Pallet<T> {
		fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
			let manager = BandwidthManager::<T>::get(&request.source).ok_or_else(|| {
				anyhow::anyhow!(format!("no bandwidth manager registered for {:?}", request.source))
			})?;

			if request.from != manager.0.to_vec() {
				return Err(anyhow::anyhow!(format!(
					"purchase from unauthorised sender on {:?}: expected {:x?}, got {:x?}",
					request.source, manager.0, request.from
				)));
			}

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

			let bytes = cfg.bytes.saturating_mul(msg.months as u128);
			let duration = cfg.duration_secs.saturating_mul(msg.months as u64);

			let key = AppKey::truncate_from(msg.app);
			let expires_at = Self::push_subscription(&msg.chain, &key, tier, bytes, duration);

			Self::deposit_event(Event::BandwidthCredited {
				app_chain: msg.chain,
				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

			Ok(Weight::zero())
		}
