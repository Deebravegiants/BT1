## Title
Webhook shop-tenant identity spoofing due to `X-Shopify-Shop-Domain` header not covered by HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an incoming webhook exclusively from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, while the HMAC signature that `Utils::HmacValidator` verifies only covers the raw request body. This breaks the identity binding: `verified_bytes (raw_body) != bytes_used_for_tenant_identity (shop header)`. An attacker who controls one legitimate shop that has the app installed can obtain validly-signed webhook payloads (body + HMAC, both signed with the app's single shared `client_secret`) and relabel them with a different shop's domain, causing the app to process attacker-controlled data as belonging to another tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from an HTTP header that is not part of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` only checks that the received `hmac` matches `HMAC(secret, to_signable_string)`, i.e. `HMAC(secret, raw_body)`; the `shop` header is never included in the signable material: [3](#0-2) 

`Registry.process` trusts this unauthenticated `shop` value and forwards it directly to the app's webhook handler as the tenant identifier: [4](#0-3) 

Because a single app uses one `client_secret` shared across every merchant that installs it, any shop owner that has installed the app can generate a legitimately-signed webhook (e.g. by editing a product in their own store to control the body content and topic), capture the `raw_body` + valid `hmac-sha256` header pair Shopify sent them, then replay the identical body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (body and signature match), but `WebhookMetadata.shop` is now the victim's domain — a cross-tenant identity confusion introduced entirely inside the gem's webhook-verification code path.

### Impact Explanation
This breaks the binding `hmac_verified(shop) == shop_used_for_tenant_routing`, letting an unprivileged app-installing merchant impersonate another tenant to the app's webhook handling logic. Depending on what the host app's registered `WebhookHandler` does with `WebhookMetadata#shop` (e.g., updating per-shop records, triggering per-shop side effects, or writing data keyed by shop domain), this results in cross-tenant access/contamination — data or actions intended for one merchant get attributed to a different merchant, satisfying the "cross-tenant access" Critical impact category, entirely through a flaw in this gem's HMAC verification scope rather than any host misuse.

### Likelihood Explanation
The prerequisite is only that the attacker is a legitimate but unprivileged installer of the target app (any merchant can install most public apps), which lets them obtain real signed webhook traffic for their own store and control its topic/body content. No access to `api_secret_key`, access tokens, or the victim's credentials is required — only the ability to relay an HTTP request with a modified header, which is squarely within an "unprivileged internet user" threat model for a multi-tenant app.

### Recommendation
Bind the `shop` (and ideally `topic`, `api-version`) values into the HMAC-signed material, or at minimum require the app to independently confirm that the `shop` header corresponds to a shop that legitimately owns the webhook subscription (e.g., cross-check against the `webhook_id`/subscription registered for that specific shop) before trusting `WebhookMetadata#shop`. At the library level, `Request#to_signable_string` should not silently exclude header-derived identity fields from what callers are told was "verified."

### Proof of Concept
1. App `A` is installed by two shops: `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, sharing the same `client_secret`.
2. Attacker triggers a webhook (e.g., `products/update`) on their own store, causing Shopify to POST to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC(secret, B)`, and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same `body=B` and `hmac=H`, but changes the header to `X-Shopify-Shop-Domain: victim-shop.myshopify.com`, and sends it to the app's webhook endpoint.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which computes `HMAC(secret, B)` and finds it equals `H` — validation passes: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body: B`, even though the request was never signed for, or sent by, the victim shop.
