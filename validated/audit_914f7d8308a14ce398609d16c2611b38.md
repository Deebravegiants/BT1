### Title
Attacker-controlled swap routes can execute unauthorized token transfers from the caller - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` accept caller-supplied opaque `swap` bytes and pass them to the configured router. The controller protects only its own input transfer, while route-selected third-party pool code can add a token `transfer` from the caller beneath the caller's signed authorization tree and steal unrelated wallet assets. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral` authorizes the account owner or delegate and forwards its caller-controlled `swap` argument into `withdraw_and_swap_from_supply` without constraining which route venues or pool contracts the payload names. [3](#0-2) 

The shared swap helper grants the router exactly one controller-token transfer for `amount_in`, but it then invokes `router.execute_strategy` with the attacker-controlled route blob. [2](#0-1) 

The router's strategy payload contains an arbitrary `assets` address registry used for pools and tokens, while packed opcodes select the venue adapter. [4](#0-3) 

For a Soroswap hop, the pool address comes from that registry and the adapter invokes attacker-selected code through `get_reserves` and `swap`; there is no pool allowlist. [5](#0-4) [6](#0-5) 

Soroban records a nested `from.require_auth()` token transfer made by that route-selected contract as a child of the caller's controller authorization, so signing the simulated tree authorizes the extra transfer. [7](#0-6) [8](#0-7) 

### Impact Explanation
An attacker can provide a route whose malicious pool transfers an unrelated wallet token from the victim to the attacker while still paying a fair swap output, so the controller's positive-output and solvency checks do not bound the wallet theft. [9](#0-8) [10](#0-9) 

This is theft of user funds rather than bad route pricing: the stolen token need not be listed by the protocol, deposited as collateral, or otherwise exposed to the swap amount. [11](#0-10) [12](#0-11) 

### Likelihood Explanation
The attack requires the victim to submit a strategy entrypoint with a malicious route and sign the authorization tree containing the rogue child transfer. [13](#0-12) 

That prerequisite is realistic when routes are supplied by a frontend, solver, or quoted-route service: simulation can display the child invocation, but the protocol itself imposes no venue allowlist or authorization-tree bound. [14](#0-13) 

The same pattern applies to every strategy that accepts route bytes, including `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply`. [15](#0-14) [1](#0-0) [16](#0-15) 

### Recommendation
Do not allow strategy payloads to name arbitrary pool contracts. Maintain a governance-approved venue/pool registry, validate every hop against it, and reject routes containing unlisted addresses. [4](#0-3) 

Until route destinations are constrained, wallets and integrations should refuse any simulated controller authorization containing children beyond the expected token transfer, but this client-side check is not a substitute for protocol-level route validation. [14](#0-13) 

### Proof of Concept
1. Alice owns a funded lending account and an unrelated wallet token; the attacker deploys a malicious contract with a `swap` method that calls `token::transfer(alice, attacker, amount)`. [17](#0-16) 
2. The attacker encodes a route naming that contract as the hop pool while returning a fair output amount. [9](#0-8) 
3. Alice calls `swap_collateral(caller=alice, account_id, current=USDC, amount=50_000_000_000, new=ETH, swap=route)`. [18](#0-17) 
4. The malicious hop invokes `wallet_token.transfer(alice, attacker, WALLET_BALANCE)`, which simulation records as a child of Alice's `swap_collateral` authorization. [19](#0-18) 
5. Signing the recorded tree makes the swap succeed, transfers the entire unrelated wallet-token balance to the attacker, and still deposits the fair ETH output for Alice. [13](#0-12)

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
