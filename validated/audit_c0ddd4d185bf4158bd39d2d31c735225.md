### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) are read from unsigned headers while the HMAC only covers the raw body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `webhook_id`, and `api_version` fields entirely from HTTP headers (`shopify_header("shop-domain")`, etc.), but its HMAC-signable representation (`to_signable_string`) is only the raw request body. `Registry.process` validates the HMAC and then passes the unvalidated header-derived `shop` straight to the app's webhook handler as the authoritative tenant identifier. Because none of these header values are covered by the signature, an attacker who can obtain one valid `(raw_body, hmac)` pair for the app's client secret domain (e.g. by triggering/observing a genuine webhook to their own installed shop) can replay that exact body/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, or `X-Shopify-Api-Version` header. The HMAC still validates because it only checks the body bytes, letting the attacker impersonate a different shop or a different topic/webhook event to the app's webhook handler.

### Finding Description
`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` and compares it to the `hmac` value [1](#0-0) . For webhooks, `to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers via `shopify_header`, which is never part of the signed string [3](#0-2) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body-only integrity) before dispatching to the handler with `shop: request.shop`, `topic: request.topic`, `webhook_id: request.webhook_id`, and `api_version: request.api_version` taken straight from the request object [4](#0-3) . The identity binding the gem is supposed to enforce is "the shop that the HMAC-signed bytes came from" == "the shop the handler is told the webhook belongs to." Since headers carrying `shop`, `topic`, and `webhook_id` are outside the HMAC, that equality is not actually checked - only body-bytes authenticity is checked, not header authenticity.

The gem's own documentation instructs host apps to trust this value directly for tenant-scoped work, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [5](#0-4) , meaning apps following the documented API contract have no independent way, within the gem, to detect that `shop`/`topic`/`webhook_id` are unauthenticated.

### Impact Explanation
This breaks a tenant/authentication boundary the merchant relies on: a merchant/attacker who has their own shop with the app installed can receive a legitimate signed webhook for their own shop/topic (with a valid HMAC over that body) and resend the exact same body+HMAC to the app's webhook endpoint while swapping in a different `shop-domain`, `topic`, or `webhook-id` header. The `Registry.process` call will still validate (`HmacValidator.validate` only checks the body), and the handler will process the payload under the attacker-chosen shop/topic label — for example causing the app to process an "app/uninstalled" or "shop/redact" event, or attribute order/customer data, for a shop the attacker does not own. This is a cross-tenant impersonation vector reachable by any unprivileged internet user who has (or can create) a shop where the app is installed, requiring no access token, `client_secret`, or privileged account.

### Likelihood Explanation
Likelihood is realistic: any merchant with the app installed on their own shop can trigger events on that shop (e.g., updating a product, or uninstalling the app) to capture a genuine `(raw_body, hmac)` pair, then simply replay that HTTP request to the shared webhook endpoint with different headers. No cryptographic secret needs to be recovered — the header fields are simply outside what is authenticated at all.

### Recommendation
Include the header-derived identity fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed representation, or otherwise cryptographically bind them to the body (Shopify's actual webhook signature scheme signs the raw body only by design, so the gem should independently verify the `shop-domain` header against a shop the app expects, e.g. by cross-referencing an existing session/shop record) before handing `WebhookMetadata` to the handler. At minimum, document prominently that `shop`, `topic`, and `webhook_id` are unauthenticated header values and must be independently verified by the host app before being trusted for tenant-scoped actions.

### Proof of Concept
1. App has `WebhookHandler` registered for topic `orders/create` and trusts `data.shop` as documented in `docs/usage/webhooks.md`.
2. Attacker installs the app on `attacker-shop.myshopify.com` and triggers an `orders/create` event, capturing the genuine POST request Shopify sends, including its `X-Shopify-Hmac-Sha256` header and raw body.
3. Attacker replays the identical raw body and HMAC header to the app's shared webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and/or changes `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Registry.process` calls `Utils::HmacValidator.validate(request)` which recomputes the HMAC only over `@raw_body` — unchanged — so validation succeeds [6](#0-5) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes the attacker's order data as if it belonged to the victim shop [7](#0-6) .
