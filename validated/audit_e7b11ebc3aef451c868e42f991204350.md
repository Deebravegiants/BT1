### Title
Unauthenticated arbitrary external call via Emporium's `signerAddress == address(0)` + zero-token `MainEVMCircuitMin` path bypasses both signature and ZK-proof checks - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When a transaction targets the Hinkal Emporium action with `circomData.erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes the proof to the minimal `formInputEmporiumMin` public-input set [1](#0-0) , which is verified against `MainEVMCircuitMin.circom` — a circuit that only proves knowledge of a `messageSeed` whose Poseidon hash equals `message`, with **no EdDSA signature check, no nullifier check, and no Merkle-root check at all** [2](#0-1) . Separately, `EmporiumUpgradeable.verifyWallet` skips all EIP-712 signature verification whenever `stack.signerAddress == address(0)`, only marking the `emporiumMessage` nonce as used [3](#0-2) . Combining these two facts, an unprivileged EOA can submit a `transact()` call with an empty token list and an `EmporiumStack{signerAddress: address(0), ops: [...]}` where `ops` execute arbitrary `endpoint.call{value}(callData)` from the Emporium contract's own context (CASE 2, "stateless interaction") [4](#0-3) , with **zero cryptographic authorization** of any kind — no valid EdDSA signature over a spend, no valid EIP-712 wallet signature, and no nullifier/root check tying the call to any shielded balance.

### Finding Description
`runAction` only performs its balance-equation safety check (`balancesBefore`/`balancesAfter` comparison, `BalanceChangeShouldBePositive`) over the range `0..circomData.erc20TokenAddresses.length` [5](#0-4) . If `erc20TokenAddresses.length == 0` (which is exactly the condition that routes to the trivial `MainEVMCircuitMin`, per `formInputForCircom`), that loop is empty, so **no balance movement is checked whatsoever** while the arbitrary `ops` calls are still executed:
- `_externalTransact` skips any pre-funding transfer since there are no tokens to iterate over [6](#0-5) .
- `verifyWallet` returns immediately for `signerAddress == address(0)`, without checking any ECDSA/EIP-712 signature over `stack.ops` [3](#0-2) .
- The Groth16 proof itself, for this dimension configuration, only needs to satisfy `MainEVMCircuitMin` — proving `Poseidon(messageSeed) == message`, with `calldataHash` and `outTimeStamp` as the only meaningful public signals [2](#0-1) . `messageSeed` is fully attacker-chosen private input, so any caller can trivially produce a valid proof for any `calldataHash`/`timeStamp` pair — the circuit provides **no binding to a spendingPublicKey, EdDSA signature, or Merkle root**, unlike the full `MainEVMCircuit` [7](#0-6) .
- `performHinkalChecks` only verifies `calldataHash` integrity and sender/relay consistency, not signature-of-spend [8](#0-7)  — it does not compensate for the missing signature check in this branch.

As a result, in CASE 2 the Emporium contract executes `op.endpoint.call{value: op.value}(op.callData)` directly from its own address/balance [9](#0-8) , using whatever ETH/ERC20 balance or approvals the Emporium contract happens to hold (e.g., transiently-held relay fees, dust left from prior/failed operations, or approvals granted to routers), with the caller supplying completely unauthenticated `endpoint`/`callData`/`value`. This breaks the equality that the balance-equation and signature checks are meant to enforce: value moved by an external action is not counted/authorized anywhere in the proof or balance equation.

### Impact Explanation
This is direct theft of protocol/Emporium-held funds and, depending on what token approvals/balances the Emporium contract holds at call time, of in-flight user funds that are momentarily routed through the Emporium contract during other users' legitimate operations. The attacker fully controls `endpoint` and `callData`, allowing e.g. `transferFrom`/`transfer` calls on any ERC20 the contract has balance of, or draining ETH held in the contract. This matches "Critical – direct theft of shielded or in-flight user funds ... executing calls or moving assets a wallet owner or prover never authorised."

### Likelihood Explanation
Requires no privileges — a plain EOA can call `Hinkal.transact()` directly (`relay == address(0)`, `originalSender == msg.sender`, satisfying `performHinkalChecks`'s "invalid value for originalSender" check [10](#0-9) ), needs no wallet, no relay, no shielded balance, and needs only to generate a trivial Groth16 proof for `MainEVMCircuitMin` and craft an `EmporiumStack` with `signerAddress = address(0)`. The only constraint is that the Emporium contract must be holding some balance/approval reachable via `endpoint.call`, which is a normal operating condition for a relayer/fee-routing contract.

### Recommendation
- Do not allow `signerAddress == address(0)` to bypass authorization when `erc20TokenAddresses.length == 0`; require the balance-equation check (or an equivalent zero-value invariant) to run even when the token array is empty, or reject Emporium actions with empty `erc20TokenAddresses` combined with `signerAddress == address(0)`.
- Tie `MainEVMCircuitMin`'s validity to some authenticated actor (e.g., include a real signature check, or restrict its use strictly to flows that carry no `ops`/external call capability).
- Ensure `runAction`'s post-call balance verification is enforced for the Emporium contract's own address/asset exposure independent of `circomData.erc20TokenAddresses`, i.e., assert the Emporium contract's balance for any token/ETH actually touched by `ops` is not net-negative.

### Proof of Concept
1. Attacker (plain EOA, no shielded deposit, no relay) prepares `circomData` with `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `amountChanges = []`, `originalSender = attacker`, `relay = address(0)`.
2. `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({v:0, r:0, s:0, signerAddress: address(0), ops: [EmporiumOperation({endpoint: TARGET_ERC20, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, EMPORIUM_BALANCE))})], maxFee: 0, deadline: type(uint256).max}))`.
3. Attacker computes `calldataHash` per `CircomDataBuilder.getHashedCalldata` and generates a Groth16 proof for `MainEVMCircuitMin` using any `messageSeed` (fully attacker-controlled, no signature needed) that matches the public `calldataHash`/`outTimeStamp`.
4. Attacker calls `Hinkal.transact(a, b, c, dimensions, circomData)`.
5. `performHinkalChecks` passes (calldata hash matches, sender==originalSender, relay==0); `verifyProof` succeeds trivially against the minimal circuit; `_externalTransact` invokes `EmporiumUpgradeable.runAction`; `verifyWallet` returns immediately since `signerAddress == address(0)` — no signature check; the op executes `TARGET_ERC20.transfer(attacker, EMPORIUM_BALANCE)` directly from the Emporium contract, draining its ERC20 balance with no balance-equation check (loop bound is 0) and no proof of ownership of any spent value.

    function performHinkalChecks(
        CircomData calldata circomData,
        Dimensions calldata dimensions,
        address sender
    ) external view returns (uint256[] memory) {
        require(
            (circomData.originalSender == address(0) &&
                circomData.relay != address(0)) ||
                (circomData.originalSender == sender &&
                    circomData.relay == address(0)),
            "invalid value for originalSender"
        );

        require(
            CircomDataBuilder.getHashedCalldata(circomData) ==
                circomData.calldataHash,
            "Calldata Hash Integrity Check Failed"
        );
        relayerIsValid(circomData.relay);
        dimensionsCheck(circomData, dimensions);
        checkOnchainCreation(circomData);

        return
            CircomDataBuilder.formInputForCircom(
                block.chainid,
                hinkalAddress,
                circomData
            );
    }
