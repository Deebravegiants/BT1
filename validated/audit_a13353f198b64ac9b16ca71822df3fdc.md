Based on my investigation, I found a strong analog to the ClamAV OLE2 out-of-bounds write DoS pattern: unchecked slice arithmetic on attacker-influenced byte lengths that can panic the node.

### Title
Unchecked slice-length arithmetic on relayed token-transfer message can panic the runtime - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
The `hyper-fungible-token` pallet's message execution path decodes an ISMP `PostRequest`'s `from` field and, when no signature is present, derives the acting account by slicing that field based on its length without first validating the length matches what the slicing arithmetic assumes.

### Finding Description
In the calldata-execution branch of the incoming message handler, when `substrate_data.signature` is `None`, the code falls back to deriving the origin account directly from `message.from`: [1](#0-0) 

For an EVM source, it computes `&from_bytes[from_bytes.len() - 20..]` — if `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows (in `usize` arithmetic), producing either a panic (debug/checked builds) or a huge out-of-range index that panics on slice indexing (release builds), either way resulting in an out-of-bounds index panic during message execution. For the non-EVM branch, `account.copy_from_slice(from_bytes)` panics whenever `from_bytes.len() != 32`, since `copy_from_slice` requires equal-length slices.

This mirrors the ClamAV OLE2 bug class: a malformed/adversarial input field (the `from` address bytes embedded in a cross-chain message body) is consumed by low-level byte-slicing logic that assumes a fixed length without validating it first, leading to an out-of-bounds panic instead of a graceful `Result::Err`.

### Impact Explanation
`message.from` originates from the ISMP `PostRequest.from` field of a cross-chain message that is dispatched through the standard ISMP delivery path (`handle_unsigned`/`pallet-ismp` message execution) and ultimately routed to this module's `on_accept` callback. Because ISMP request bodies are attacker/relayer-influenced payloads relayed from a source chain, a malicious or buggy source-chain contract (or a relayer replaying/crafting requests) could produce a `from` field whose length is not exactly 20 (EVM) or 32 (Substrate) bytes. Once such a request is delivered and executed on the destination chain, this code panics, halting execution of that transaction/block context — a denial-of-service on the token-bridge message-processing path, directly analogous to the ClamAV crash-via-malformed-input primitive.

### Likelihood Explanation
The `from` field length is determined by the source-chain application dispatching the cross-chain message; nothing in the shown code path enforces that it is exactly 20 or 32 bytes before this slicing occurs, so any adversarial or malformed cross-chain dispatch (which is normally permitted from an arbitrary/foreign application when the calldata path is used) can trigger the panic. This makes it reachable by a single relayed cross-chain message without special privileges.

### Recommendation
Validate `from_bytes.len()` against the expected length for each `source` branch before slicing/copying, returning a proper `HftError` (e.g., a new `InvalidFromAddressLength` variant) instead of allowing the runtime to panic; use `checked_sub`/`try_into` conversions rather than raw arithmetic and `copy_from_slice`.

### Proof of Concept
1. A relayer delivers an ISMP `PostRequest` to the `hyper-fungible-token` pallet where `source.is_evm()` is true, `message.data` is non-empty with `substrate_data.signature = None`, and `message.from` is fewer than 20 bytes (e.g., 5 bytes).
2. The pallet executes `from_bytes.len() - 20` as part of `T::EvmToSubstrate::convert(H160::from_slice(&from_bytes[from_bytes.len() - 20..]))`. [2](#0-1) 
3. The subtraction underflows / the subsequent slice index is out of range, causing a panic during message execution instead of returning a decode/validation error.

Note: I was unable to fully trace the exact construction path of `message.from` (i.e., whether an earlier ISMP validation layer already enforces a fixed length before reaching this pallet) due to tool/file-read errors in the final iteration. I recommend a Devin session with full repo access to confirm whether any upstream check already constrains `PostRequest.from` length before this pallet processes it, which would determine whether this is fully reachable or mitigated upstream.
