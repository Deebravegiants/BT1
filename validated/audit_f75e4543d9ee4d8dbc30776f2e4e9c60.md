This is a **critical finding**: `TokenExchange.exchange_token` in `lib/shopify_api/auth/token_exchange.rb` derives `dest_shop` directly from `jwt_payload.shop` and uses it, unvalidated, as the shop for both the HTTP request session (which controls the Shopify host the app's `client_id`/`client_secret` are sent to) and the returned `Session` object, **without ever passing it through `Utils::ShopValidator.sanitize!`**, unlike every other OAuth entry point in this gem.

### Title
SSRF / Client-Secret Exfiltration via Unvalidated `dest` Claim in Token Exchange - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` trusts the `dest` claim of the caller-supplied session token as the destination host for the token-exchange HTTP request, sending the app's `client_id` and `client_secret` to that host, with no allow-list check.

### Finding Description
`JwtPayload#shop` returns `@dest.gsub("https://", "")` [1](#0-0)  without any validation that `dest` is a Shopify-owned domain (`myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`, `shopify.com`). The only checks performed during decoding are signature validity, `exp`/`nbf` leeway, and `aud == Context.api_key` [2](#0-1) .

`TokenExchange.exchange_token` takes this unvalidated `dest_shop` value and constructs `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)`, which is then used to build the `HttpClient` base host, and includes `client_id` and `client_secret` in the POST body sent to `#{shop}/admin/oauth/access_token`: [3](#0-2) 

Every sibling OAuth-token method in the same file/module calls `Utils::ShopValidator.sanitize!(shop)` before constructing the session used to build the request host: `migrate_to_expiring_token` [4](#0-3) , `ClientCredentials.client_credentials` [5](#0-4) , and `RefreshToken.refresh_access_token` [6](#0-5) . `exchange_token` is the sole exception — it deliberately bypasses `ShopValidator` and uses the JWT's `dest` claim directly, per the code comment "the shop always comes from the session token `dest` claim" (also documented in `docs/usage/oauth.md`).

The identity binding broken: **host that receives the `client_secret`** should equal **a Shopify-trusted domain** (as enforced by `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` for every other credential-bearing call), but for `exchange_token` it instead equals **whatever `dest` string is embedded in the caller-supplied session token**, since `dest` is never checked against the trusted-domain allow-list before being turned into a request host.

Note: because the JWT itself must be signed with the app's `api_secret_key` (or `old_api_secret_key`) to pass `JwtPayload`'s HMAC verification, an attacker without knowledge of that secret cannot forge an arbitrary `dest` value on their own. This significantly limits exploitability compared to a pure unauthenticated bypass — the practical path requires a legitimately-issued session token whose `dest` was manipulated or a host application that fails to further validate/scope the caller-facing session-token exchange endpoint before forwarding an arbitrary token to `exchange_token`.

### Impact Explanation
If exploitable (e.g., a host app blindly relays an externally-influenced session token, or a future signing/validation regression), this allows sending the app's `client_id` and `client_secret` to an attacker-controlled host (SSRF with credential exfiltration), qualifying as High severity per the report's own criteria ("SSRF with the app's credentials"). It also breaks the shop/session identity binding that the rest of the module enforces uniformly via `ShopValidator`.

### Likelihood Explanation
Low-to-Medium. The `dest` claim is inside a token that must carry a valid HMAC signature checked against `Context.api_secret_key`/`old_api_secret_key`, so an anonymous internet attacker cannot forge it outright. Likelihood rises only if the calling application does not itself constrain which tokens are exchanged, or if a legitimate token can be replayed/relayed with attacker influence over the shop context, which is outside strict "in-gem" control but is a real gap relative to the gem's own established pattern of always sanitizing shop hosts before using them for credentialed requests.

### Recommendation
Apply `Utils::ShopValidator.sanitize!(dest_shop)` (or equivalent) to the `dest` claim inside `JwtPayload#shop`/`shopify_domain`, or explicitly in `TokenExchange.exchange_token` before constructing `shop_session`, mirroring the validation already performed in `migrate_to_expiring_token`, `ClientCredentials.client_credentials`, and `RefreshToken.refresh_access_token`.

### Proof of Concept
1. Obtain (or otherwise supply) a session token whose `dest` claim is set to an attacker-controlled or otherwise untrusted host, but signed correctly (e.g., in a scenario where the signing key is known/reused, or the host app forwards a token without further origin checks).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")` is built against `dest_shop` unchecked [7](#0-6) , causing the POST containing `client_id`/`client_secret` to be sent to that host instead of a verified `myshopify.com`-family domain.
