### Title
`connectedOrigins` trust and auto-approve permissions are keyed only by `origin`, not by wallet account, causing cross-account privilege bleed - ([File: features/connected-origins/module/connections.js])

### Summary
The `ConnectedOrigins` module tracks whether a dApp origin is `trusted` and whether it has `autoApprove` enabled, but these flags are stored and checked purely by `origin` string, ignoring which `walletAccount` originally granted that trust. This mirrors the reported bug class in the external report: a permission/state map that should be scoped by two dimensions (there: user × reward-token; here: origin × walletAccount) is only keyed by one dimension, so state legitimately granted in one context (one token / one wallet account) silently applies to — or blocks/bleeds into — another context (another token / another wallet account) that never independently earned it.

### Finding Description
`ConnectedOrigins#add` stores a `walletAccount` field on the connection record [1](#0-0) , but the authorization checks `isTrusted` and `isAutoApprove` only look up the record by `origin` and never validate that the currently active wallet account matches the `walletAccount` that was present when trust/auto-approve was granted: [2](#0-1) 

Likewise `#getOrigin` resolves purely by `origin`: [3](#0-2) 

The `connectedOriginsApi` exposes `isTrusted` and `isAutoApprove` directly to callers (e.g. the background/RPC layer that decides whether to prompt the user before signing) without any wallet-account parameter or check: [4](#0-3) 

Because the wallet supports multiple `WalletAccount`s under the IoC/Argo architecture (with an `activeWalletAccountAtom` the module already depends on for `getConnectedAccounts`) [5](#0-4) , switching the active wallet account does not reset or re-scope `trusted`/`autoApprove` state for an origin. A dApp origin approved (and possibly set to `autoApprove`) while account A is active remains "trusted"/"auto-approved" once the user switches to account B, even though the user never authorized that origin in the context of account B.

### Impact Explanation
If `autoApprove` is set for an origin (e.g., after repeated manual approvals under wallet account A), the background/API layer can skip user confirmation for signing requests originating from that origin. Since the check `isAutoApprove({ origin })` is account-agnostic, once the active wallet account is switched to B, a malicious or compromised dApp at the same origin can obtain silent (auto-approved) transaction/message signing against account B's keys — an account the user never explicitly trusted from that origin. This is a direct unauthorized-signing / auth-bypass impact: the origin gains signing privileges over an account for which it was never independently vetted, purely because the permission map is missing the wallet-account dimension.

### Likelihood Explanation
This requires: (1) a user connecting/trusting (and optionally enabling auto-approve for) a dApp origin while one wallet account is active, and (2) later switching the active wallet account while keeping the browser/session (and thus the connectedOrigins state) intact — a common and expected user flow in a multi-account wallet, not requiring any attacker-controlled infrastructure beyond a normal dApp origin. No special privileges or malicious peer/operator behavior are needed, so likelihood is moderate-to-high for any user who uses multiple wallet accounts with the same connected dApp.

### Recommendation
Scope trust and auto-approve state by both `origin` and `walletAccount` (analogous to the suggested fix of nesting the reward-claim mapping by token): e.g., change `isTrusted`/`isAutoApprove`/`setAutoApprove`/`untrust` to accept and check `walletAccount` alongside `origin`, and store `trusted`/`autoApprove` as sub-maps keyed by wallet account (or store separate connection records per `origin`+`walletAccount` pair) rather than a single flat record per origin. Ensure the background/API consumers pass the currently active wallet account into these checks so that a permission granted for one account can never be silently applied to another.

### Proof of Concept
1. As wallet account A (active), connect to a dApp at `origin: "example.com"` via `connectedOrigins.add({ origin: "example.com", walletAccount: "exodus_0", trusted: true, ... })`.
2. Enable `connectedOrigins.setAutoApprove({ origin: "example.com", value: true })` (e.g., after several approved requests).
3. Switch the active wallet account to B via `activeWalletAccountAtom.set('exodus_1')`.
4. Call `connectedOrigins.isTrusted({ origin: "example.com" })` and `connectedOrigins.isAutoApprove({ origin: "example.com" })` — both still return `true`, even though account B never independently granted trust or auto-approve, allowing the dApp to obtain auto-approved signing against account B.

*(Note: I could not fully trace, within the available index, the exact background/RPC call site(s) that gate the actual signing confirmation dialog with `isAutoApprove`/`isTrusted` — the index only surfaces the module/API definitions and tests shown above. If a background/session layer already re-validates the active wallet account elsewhere before invoking these checks, the practical exploitability could be narrower than described; verifying that call site would require a full repository checkout via a Devin session.)*

  add = async ({
    connectedAssetName,
    origin,
    name,
    icon,
    assetNames = [],
    trusted,
    favorite,
    walletAccount,
  }) => {
    const value = await this.#getOrigin({ origin })

    const allConnectedAssetNames = new Set([
      connectedAssetName,
      ...assetNames,
      ...(value?.assetNames ?? []),
    ])

    if (value) {
      await this.#setAttributes({
        origin,
        attributes: {
          icon: icon ?? value.icon,
          name: name ?? value.name,
          connectedAssetName: connectedAssetName ?? value.connectedAssetName,
          trusted: trusted ?? value.trusted,
          favorite: favorite ?? value.favorite,
          assetNames: [...allConnectedAssetNames],
          walletAccount: walletAccount ?? value.walletAccount,
        },
      })

    }

      origin,
      icon,
      name,
      connectedAssetName,
      trusted,
      favorite,
      assetNames: [...allConnectedAssetNames],

  isTrusted = async ({ origin }) => {
    const value = await this.#getOrigin({ origin })

    if (!value) {
      return false
    }

    // backward compatibility
    return value.trusted === undefined || value.trusted
  }

  isAutoApprove = async ({ origin }) => {
    const value = await this.#getOrigin({ origin })
    return value?.autoApprove || false
  }

  setAutoApprove = async ({ origin, value }) => {
    return this.#setAttributes({ origin, attributes: { autoApprove: value } })
  }

  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
