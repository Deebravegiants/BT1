## Finding

The strongest reachable analog to the `office-converter` RCE ("insufficient input validation → arbitrary execution with attacker-controlled parameters") is in `pallet-hyper-fungible-token`'s ISMP handler, where an unsigned, attacker-controlled field is used as the dispatch origin for an arbitrary `RuntimeCall`.

### Title
Unauthenticated Origin Spoofing Enables Arbitrary Runtime Call Dispatch in `hyper-fungible-token::on_accept` - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`Pallet::<T>::on_accept` decodes an ISMP `PostRequest.body` into an application-level `Message` (containing `to`, `amount`, `data`), then optionally executes a `SubstrateCalldata { signature, runtime_call }` blob taken from `message.data`. When `signature` is `None`, the dispatch origin is derived directly from `message.from` — a field inside the attacker/relay-controlled ABI-encoded body — with no cryptographic binding proving that whoever controls that address actually authorized the call. [1](#0-0) 

### Finding Description
`on_accept` authenticates only the *source contract* via `ContractToAsset::<T>::get(source, &from)` (the ISMP-level `PostRequest.from`), which establishes that the request came from a registered bridge contract for a given asset — not that the `Message` payload's internal fields (`to`, `data.from`, `data.signature`) are trustworthy. [2](#0-1) 

The optional-calldata path then decodes `SubstrateCalldata` from `message.data` (fully attacker-controlled, part of the ABI-encoded body) and branches on whether a signature is present:

- If a `MultiSignature` is present, it is verified against `beneficiary_bytes` (the actual token recipient) — a real cryptographic check. [3](#0-2) 

- If **no signature is present**, the origin used to dispatch `runtime_call` is instead derived straight from `message.from`, with zero verification that this address corresponds to the actual off-chain caller: [4](#0-3) 

The decoded `runtime_call` is only checked against `BaseCallFilter` (a global filter for disabled calls, not a per-account authorization check), then dispatched as `RawOrigin::Signed(origin)`: [5](#0-4) 

Because `message.data` (including the `SubstrateCalldata.signature` and `.runtime_call` fields) is decoded from the ABI-encoded `body`, and `message.from` is a separate field inside that same attacker-controlled body (not the same as the ISMP `PostRequest.from` used for `ContractToAsset` lookup), a caller of the registered source-chain bridge contract can freely set `data.from` to any 20/32-byte account identifier and omit `data.signature`. The pallet will then dispatch an arbitrary `T::RuntimeCall` under `RawOrigin::Signed(<victim account>)`, i.e., unauthorized app action / identity spoofing — the Substrate analogue of unvalidated input driving arbitrary command execution.

### Impact Explanation
This allows an unprivileged relayer/message submitter (anyone able to trigger the registered source contract's outbound message with arbitrary calldata) to impersonate any Substrate account and dispatch arbitrary runtime calls as that account — e.g., transferring assets, or any other privileged action expressible as a `RuntimeCall` and not excluded by `BaseCallFilter`. This is a full authorization bypass / unauthorized app action, satisfying the "unauthorized app action" acceptance criterion, and is reachable purely by control over an ISMP-dispatched message body.

### Likelihood Explanation
The path is reached automatically on every incoming `on_accept` call with non-empty `data` and no supplied signature — no special privilege beyond the ability to have the source-side registered contract emit a cross-chain `PostRequest` with an arbitrary `body` (the token-bridge dispatch entrypoint on the EVM side is normally callable by any user for a bridge transfer, since it just needs `to`, `amount`, `data`). No proof-forgery, consensus break, or governance/admin action is required — this is squarely in the message-dispatch/relayer-reachable class.

### Recommendation
Never derive a dispatch origin from an unauthenticated field. Require `SubstrateCalldata.signature` to be mandatory whenever `data` requests call execution (reject `None` outright, or bind the "unsigned" case to the actual verified token beneficiary derived from `PostRequest`-level authenticated fields, never to `message.from`). If a signature-less path must be kept for parity with the EVM sender, tie the origin strictly to the already-authenticated `beneficiary` computed from `message.to` (bounded to what the transfer step already verified) rather than to an independent attacker-chosen `message.from` value.

### Proof of Concept
1. Register a legitimate source contract/asset pair in `ContractToAsset` (as required for any valid bridge use).
2. From that source contract, submit (or have a relayer submit) a `PostRequest` whose ABI-encoded `body` contains a `Message` with:
   - `to` = attacker-controlled or irrelevant recipient (for the token mint/transfer leg),
   - `data` = SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <arbitrary call, e.g., Balances::transfer from victim to attacker> }`,
   - `from` = victim's 32-byte (or 20-byte EVM) account identifier.
3. When `pallet-ismp` delivers this request, `on_accept` reaches the `else` branch at [4](#0-3)  and sets `origin = victim`, then dispatches the attacker-chosen `runtime_call` as `RawOrigin::Signed(victim)` at [6](#0-5) , with no proof the victim authorized it.

**Note on verification limits:** I was not able to inspect the EVM-side contract that emits these `PostRequest`s (to fully confirm that an unprivileged caller can freely set the `data`/`from` sub-fields of the ABI-encoded body) within the available tool budget, nor the exact `Message`/`SubstrateCalldata` field layout in `modules/pallets/hyper-fungible-token/src/types.rs`. The Substrate-side logic shown above is unambiguous, but confirming full end-to-end unprivileged reachability from the EVM sender contract would require reading `types.rs` and the paired EVM contract source, which a full Devin session with unrestricted file access could verify.
