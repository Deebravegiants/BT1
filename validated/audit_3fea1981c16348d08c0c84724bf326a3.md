## Finding: Missing length validation on `message.from` causes a panic (DoS) in HyperFungibleToken's calldata-execution path [1](#0-0) 

### Title
Unbounded-length `message.from` causes slice-index/`copy_from_slice` panic in `on_accept` calldata execution - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
In `Pallet::on_accept` (the `IsmpModule` handler invoked when a relayer delivers a `PostRequest` to the `hyper-fungible-token` pallet), the code that derives the calldata-execution `origin` from `message.from` performs a raw `copy_from_slice`/slice-index operation without first validating the byte length of `message.from`, unlike the sibling handling of `message.to` a few lines above in the same function.

### Finding Description
`message` is decoded from attacker/relayer-relayed ABI-encoded request body via `Message::abi_decode(&body)` [2](#0-1) . For the `to` field, the pallet explicitly validates the length is exactly 32 or 20 bytes and returns `HftError::InvalidRecipientLength` otherwise: [3](#0-2) 

However, when optional calldata is present and no `substrate_data.signature` is supplied, the sender/`origin` is derived from `message.from` with no equivalent length check: [4](#0-3) 

- For an EVM source: `&from_bytes[from_bytes.len() - 20..]` — if `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows a `usize`, and slicing with that value panics with "index out of bounds" (Rust `usize` subtraction overflow panics in debug builds; in release it wraps to a huge index and still panics on the out-of-range slice).
- For a non-EVM source: `account.copy_from_slice(from_bytes)` into a fixed `[0u8; 32]` — `copy_from_slice` panics immediately if `from_bytes.len() != 32`.

By contrast, the analogous refund path in `on_timeout` for the very same `message.from` field correctly validates the length before copying: [5](#0-4) 

This confirms `message.from` is a variable-length `bytes` field from the wire-format `Message` (ABI-decoded, not a fixed-size Solidity `address`), and that length validation is the established pattern elsewhere in this same module — it is simply missing on this one code path.

### Impact Explanation
`on_accept` is reached by any relayer submitting a valid ISMP `PostRequest` from a source contract registered in `ContractToAsset` (this only requires that the *token contract address* be a legitimate, pre-registered bridge contract — it does not constrain the arbitrary `from`/`data` fields encoded inside the message body that the registered contract itself may pass through user calldata). Any message reaching this branch with calldata present, no signature, and a `from` byte length other than 20 (EVM) or 32 (substrate) triggers an unhandled Rust panic instead of a graceful `Err`. A panic inside pallet dispatch inside `#[frame_support::transactional]` `handle_unsigned` aborts execution non-gracefully rather than cleanly reverting via `DispatchResult`, and — depending on how the runtime handles panics in unsigned-extrinsic execution — can disrupt block execution/validation for this class of unsigned message, effectively a routed-message-denial-of-service on the token-bridge delivery path. This matches the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
Reachable from a single relayed message once a source contract is registered (a normal, expected bridge configuration state) and calldata is used — a feature the pallet explicitly supports (`SubstrateCalldata`/`runtime_call`). No privileged/admin action is needed; a relayer or attacker who can influence the ABI-encoded `from` field-length inside the deposited message body (via the source-chain HyperFungibleToken contract's user-facing deposit call) can trigger the panic deterministically.

### Recommendation
Add the same explicit length check used for `message.to` (and used in `on_timeout` for `message.from`) before deriving the calldata-execution origin in `on_accept`:
```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    if from_bytes.len() != 20 {
        Err(HftError::InvalidSenderLength(from_bytes.len()))?
    }
    T::EvmToSubstrate::convert(H160::from_slice(from_bytes))
} else {
    if from_bytes.len() != 32 {
        Err(HftError::InvalidSenderLength(from_bytes.len()))?
    }
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
```

### Proof of Concept
1. Register a valid `ContractToAsset` mapping for `(source, from_contract)`.
2. Craft a `PostRequest` body that ABI-decodes to a `Message` with `data` non-empty, `substrate_data.signature = None`, and `message.from` set to a byte string of length e.g. 5 (neither 20 nor 32).
3. Relay this as part of an unsigned `handle_unsigned` extrinsic (or equivalent EVM `handlePostRequests` delivery leading to the pallet's `on_accept`).
4. Execution reaches `&from_bytes[from_bytes.len() - 20..]` (EVM source) or `account.copy_from_slice(from_bytes)` (substrate source) and panics instead of returning `HftError`.

Note: I was unable to fully verify, within the available search budget, the exact Solidity-side encoding constraints on the `from` field emitted by `HyperFungibleToken.sol`/`WrappedHyperFungibleToken.sol` (i.e., whether the source contract always encodes exactly 20 bytes for EVM `msg.sender`, or whether a caller-supplied path can produce an arbitrary-length `from`). This should be verified against `sdk/packages/core/contracts/apps/HyperFungibleToken.sol` before treating likelihood as confirmed at the "single unprivileged transaction" level; regardless, the missing bounds check itself is a clear code-level defect matching the CVE's "unchecked fixed-size buffer copy from untrusted-length input" bug class.
