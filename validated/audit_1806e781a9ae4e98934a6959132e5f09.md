## Finding

### Title
Webhook `shop` (and other identity headers) are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the `shop`, `topic`, `api-version` and `webhook_id` values taken directly from HTTP headers — none of which are covered by that signature. Since the app's HMAC secret (`Context.api_secret_key`) is shared across every shop that has the app installed, any merchant with the app installed can generate a validly-signed webhook body for their own shop and replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a victim shop, causing the handler to process attacker-controlled data as if it originated from the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are read straight from client-supplied headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body, then immediately hands the unauthenticated `shop` value (along with topic/version/id) to the app's registered handler as trusted metadata identifying the tenant: [3](#0-2) 

`HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to the supplied `hmac` header, i.e. it authenticates *only the body bytes*, never the shop-domain header: [4](#0-3) 

The identity binding that should hold is: `shop` used for authorization/tenant-scoping decisions == `shop` covered by the verified signature. In this implementation that equality does not hold — `to_signable_string` == `raw_body` only, while `request.shop` is parsed from an out-of-band header. Because `api_secret_key` is a single per-app secret shared by all shop installations (not a per-shop signing key), any tenant that has installed the app can produce a validly-signed `(body, hmac)` pair for their own account (e.g., by triggering a real webhook event in their own store) and then replay that exact body/hmac pair to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header rewritten to point at a different, victim shop. `Utils::HmacValidator.validate` will still return `true` because it never inspects the header, and `Registry.process` will pass the forged `shop` through to the host application's handler as the webhook's origin.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: it allows one merchant/tenant of a multi-tenant Shopify app to inject events that the host application will process as belonging to a different, victim tenant (cross-tenant data injection/impersonation), matching the "cross-tenant access" Critical impact category. Downstream effects depend on how the host app's webhook handler uses `shop`, but since this is the only identity field the gem exposes for webhooks and the host app is expected to trust it per the gem's documented API, forging it directly undermines correct tenant attribution.

### Likelihood Explanation
Likelihood is high for any developer who has installed the target app on their own store: they can generate a legitimate webhook (e.g. update a product), capture the valid `(raw_body, hmac)` from their own delivery, and resend it to the app's public webhook endpoint with a rewritten `shop-domain` header — no access to the app's `client_secret` or any victim credentials is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed material used for webhook verification, or otherwise cryptographically bind the header-derived `shop` to the verified payload before trusting it (e.g., require the gem's `HmacValidator`/`Request` to incorporate these headers into `to_signable_string`, or cross-check the header shop against an independently-known/expected shop for the destination endpoint before dispatching to handlers).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers any subscribed webhook topic (e.g., `products/update`) in their own store, capturing the exact `raw_body` and the `X-Shopify-Hmac-Sha256` header Shopify sends — this HMAC is valid because it's computed with the app-wide `api_secret_key`, not a shop-specific secret.
3. Attacker POSTs the identical `raw_body` and `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC.
5. `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` is invoked with `shop == "victim.myshopify.com"`, even though the payload actually originated from the attacker's shop — demonstrated by: [5](#0-4)
