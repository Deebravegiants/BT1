### Title
Duplicate-`assetId` withdrawals in the same transaction cause `describeWithdrawal` to report the same status/txHash for both indices - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which matches solely on `assetId` and ignores `index`, amount, and destination. When a caller submits two POA withdrawals of the same `assetId` in one transaction, both calls to `describeWithdrawal` (for `index:0` and `index:1`) can return the identical matched record, misreporting the status/txHash of the second withdrawal.

### Finding Description
The broken equality: STATUS_TRUTH requires that `describeWithdrawal({index: i, ...})` reports the `(status, txHash)` of withdrawal `i` specifically. `findMatchingWithdrawal` at [1](#0-0)  returns `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)`, i.e., the first array entry whose token matches — with no use of `args.index`, amount, or destination address to disambiguate. `describeWithdrawal` at [2](#0-1)  passes only `args.withdrawalParams.assetId` into this lookup, explicitly noting "Response list is unsorted, so we match by assetId instead of index" (line 318).

The code's own comment at [3](#0-2)  acknowledges: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported. POA API doesn't currently support this case either."

Exploit flow: an unprivileged user submits a batch with two `ft_withdraw` intents for the same `assetId` (e.g., to two different `destinationAddress`es), producing two `WithdrawalIdentifier`s with `index:0` and `index:1` but the same `assetId`. The POA bridge's HTTP API returns an unsorted list of withdrawal records for the transaction hash. When `describeWithdrawal` is called for `index:0`, `findMatchingWithdrawal` returns the first matching record (say the one for withdrawal 1, already `COMPLETED` with `transfer_tx_hash: X`). When called for `index:1`, the same lookup (matching only by `assetId`) can return that same first record again, since there is no disambiguation by index/amount/destination. Both calls report `{status: "completed", txHash: X}`, even though the second withdrawal may still be `PENDING` or have `FAILED`.

No existing guard prevents this: `supports()`, `validateWithdrawal`, `compareAddresses`, and the intents-contract's own nonce/signature checks operate on withdrawal creation, not on the after-the-fact status matching logic, and none of them enforce assetId uniqueness across withdrawals in a batch.

### Impact Explanation
An integrator polling per-index withdrawal status via `describeWithdrawal`/`getWithdrawalStatus` (or higher-level `waitForWithdrawalCompletion`) can be told withdrawal index 1 is `completed` with a specific `txHash` that actually belongs to withdrawal index 0. This is a status/hash misreport that can cause the integrator to credit or reconcile the second withdrawal as done when it is not (or vice versa if the first is still pending while the second one actually completed), matching the "High" impact category of "a status or hash misreport making an integrator credit or refund twice." This is repeatable on every batch with duplicate `assetId` withdrawals, at zero attacker cost beyond constructing such a batch.

### Likelihood Explanation
Preconditions: the caller must submit a batch containing two (or more) POA-bridge withdrawals of the identical `assetId` in one `signAndSendIntent` transaction — an ordinary, unprivileged operation requiring no special access. This is entirely under the caller's/integrator's control and needs no cooperation from a malicious relayer or bridge admin. The bug is deterministic whenever the POA API returns the records in an order where the first match doesn't correspond to the queried index, which is exactly the scenario the code's own comment says is unhandled.

### Recommendation
Disambiguate matches within `findMatchingWithdrawal` by tracking which array entries have already been consumed per `describeWithdrawal` call sequence (e.g., pass already-claimed record identifiers, or sort both the API's withdrawal list and the batch's withdrawal params deterministically by amount/order and match by relative position, as suggested in the existing code comment), or reject/warn when `supports()`/`createWithdrawalIntents` detects duplicate `assetId` values within a single batch so integrators are not silently exposed to this ambiguity.

it("misreports withdrawal status when two withdrawals share the same assetId", async () => {

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
