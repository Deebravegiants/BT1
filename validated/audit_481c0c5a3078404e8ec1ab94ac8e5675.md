### Title
Missing Native-ETH Refund in `IntentGatewayV2.placeOrder()` Permanently Locks User Funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder()` performs a `swapETHForExactTokens` fee swap using the tracked `msgValue` but never decrements `msgValue` by the amount actually spent, and — unlike the canonical EVM implementation — never refunds any leftover `msgValue` to the caller at the end of the function. Any native ETH sent in excess of what the order inputs and the exact-output fee swap require is silently stranded in the contract with no accounting entry and no withdrawal path, permanently freezing user funds. This is the same bug class as the reported `ReachAffiliateDistribution.swapEth()` issue: a variable meant to track "funds not yet spent" is used to authorize a swap but is not correctly reconciled afterward, breaking the contract's internal accounting of native-token balances.

### Finding Description
In `placeOrder()`, `msgValue` is initialized to `msg.value` and decremented as native-token order inputs are escrowed: [1](#0-0) 

When `order.fees > 0` and the user pays the fee in native ETH (`msgValue > 0`), the contract swaps ETH for the exact fee-token amount required via Uniswap V2: [2](#0-1) 

`swapETHForExactTokens{value: msgValue}` only consumes as much ETH as needed to obtain `order.fees` output tokens and refunds any unused ETH to the caller of the router — which is `address(this)` (the `IntentGatewayV2` contract), not the end user. The Tron contract never captures this refund: it does not decrement `msgValue` by the amount actually spent (`amounts[0]`, as the canonical EVM contract does), and it has no post-fee "refund unspent native tokens" step at all.

Compare with the canonical (fixed) EVM implementation, which both tracks the spent amount and refunds the remainder to `msg.sender`: [3](#0-2) 

The Tron contract has neither `msgValue -= amounts[0];` nor the trailing `if (msgValue > 0) { _sendValue(msg.sender, msgValue); }` block found in the EVM version, so:
1. Router-refunded ETH lands on the gateway contract's balance without being recorded anywhere.
2. The user who overpaid `msg.value` (e.g., sent extra ETH as slippage buffer for the fee swap, which is standard/expected client behavior, as documented for the EVM path) has no way to reclaim the difference — there is no `sweep`/`withdraw` function for arbitrary stray native balance tied to this flow.

### Impact Explanation
Any ETH sent by a user beyond what is strictly required for order inputs plus the exact fee-token swap output is permanently locked in the `IntentGatewayV2` contract. Because users are expected (per the SDK/docs "quote and send with buffer" pattern used across the EVM version) to send more ETH than the exact requirement to guard against price movement in the exact-output swap, this loss is not just a theoretical edge case — it will occur routinely on every `placeOrder()` call that pays fees in native ETH with any margin above the exact quoted swap cost. This constitutes a permanent freezing/loss of user funds, reachable by any unprivileged user placing an order — squarely in scope as an intents-escrow fund-accounting defect.

### Likelihood Explanation
High likelihood: this triggers on the ordinary/expected call pattern (`placeOrder{value: ...}` paying `order.fees` in native ETH) without requiring any adversarial conditions, malicious actors, or governance/admin involvement. It reproduces deterministically whenever `msg.value` supplied for the fee swap exceeds the exact ETH `amounts[0]` consumed by `swapETHForExactTokens`.

### Recommendation
Mirror the canonical EVM `IntentGatewayV2.sol` fix in the Tron contract:
1. Capture the return value of `swapETHForExactTokens` and subtract the actually-spent ETH from `msgValue`:
```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
    order.fees, path, address(this), block.timestamp
);
msgValue -= amounts[0];
```
2. After the fee-handling block, refund any remaining unspent native tokens to `msg.sender`:
```solidity
if (msgValue > 0) {
    (bool sent,) = msg.sender.call{value: msgValue}("");
    if (!sent) revert InsufficientNativeToken();
}
```

### Proof of Concept
1. User calls `placeOrder{value: X}(order, graffiti)` on the Tron `IntentGatewayV2`, where `order.inputs` are ERC-20 tokens (no native input) and `order.fees > 0` is to be paid via native-ETH swap.
2. `msgValue` starts at `X` and remains `X` through the ERC-20 escrow loop (no native inputs consumed).
3. The fee-swap branch executes `swapETHForExactTokens{value: X}(order.fees, ...)`; suppose only `Y < X` ETH is actually needed — the router refunds `X - Y` ETH to `address(this)` (the gateway).
4. The function completes without decrementing `msgValue` or refunding `X - Y` to the user; `X - Y` ETH remains on the gateway's balance, unaccounted for in any storage mapping and with no user-facing withdrawal mechanism for it.
5. Repeating this for every `placeOrder` call with native-fee payment accumulates permanently stuck ETH in the contract, unrecoverable by affected users.
