### Title
`fund_message` mutates request/response fee metadata without emitting an audit event and without checking delivery completion, enabling silent accounting drift and permanent fund freezing - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`pallet_ismp::Pallet::fund_message` lets any signed account top up the relayer fee on an existing request or response commitment. It mutates the `RequestCommitments`/`ResponseCommitments` child-trie metadata (the same commitment records that are the canonical, on-chain audit trail for message fees/state) but never deposits any pallet event, and it never checks whether the message has already been delivered.

### Finding Description
`fund_message` looks up the commitment metadata, transfers the caller's tokens to `RELAYER_FEE_ACCOUNT`, and then directly re-inserts the updated `RequestMetadata`/`FeeMetadata` into the child trie: [1](#0-0) 

Two properties make this analogous to CVE-2020-29160 (a call that changes underlying data "in a way that defeats auditing"):

1. **No auditable event is emitted.** Every other state-affecting call in this pallet (`handle_unsigned`, `create_consensus_client`, fee withdrawal, etc.) deposits a corresponding `Event`, which is how off-chain indexers/relayer-fee accounting reconstruct the true fee state, e.g. the indexer explicitly reads request/response commitment metadata via `childstate_getStorage`/events to track fees: [2](#0-1) 
`fund_message` bypasses this pattern entirely — the fee top-up changes the committed `RequestMetadata`/`FeeMetadata` that downstream relayer-fee accounting and auditing logic depend on, but leaves no `Event` trail, so any off-chain reconciliation of "fees paid" vs "fees recorded on-chain via events" silently diverges.

2. **No completion check.** The pallet doc comment itself acknowledges the commitment is not guaranteed to represent a message still awaiting delivery: [3](#0-2) 
The only way a request/response commitment is removed from the child trie is via the timeout path (`delete_request_commitment`/`delete_request_receipt`), documented as being invoked when a request is timed out: [4](#0-3) 
There is no corresponding deletion path shown for the *successful delivery* case in the reviewed code, meaning a commitment can remain queryable/fundable in the child trie after a message has already been delivered and its receipt recorded. Because `fund_message` only checks `RequestCommitments::<T>::get(commitment).is_some()` and not any delivery/"claimed" flag, a caller (or anyone racing a relayer) can add funds to a commitment that is already delivered, with those transferred tokens going to `RELAYER_FEE_ACCOUNT` for a relayer action that will never occur.

### Impact Explanation
Funds sent via `fund_message` after a message is already delivered are permanently locked/lost — they sit in `RELAYER_FEE_ACCOUNT` with no relayer action left to trigger their payout, and no code path shown reclaims them. This is a concrete, unprivileged, single-extrinsic path to permanent freezing of user funds. Separately, the missing event breaks the integrity of the on-chain audit trail relied on by the relayer-fee/reward accounting system (an explicitly in-scope surface per the reachable-path criteria), since fee changes to commitment metadata are invisible to anything that reconstructs state from `Event`s rather than raw storage reads.

### Likelihood Explanation
`fund_message` is a public, unsigned-origin-free extrinsic (`ensure_signed` only) reachable by any account with a small balance and knowledge of a commitment hash (which is public via `Request`/`Response` events). No special timing beyond "call after the target message has already been delivered" is required, and delivery timing is publicly observable on-chain.

### Recommendation
- Emit an `Event` (e.g. `MessageFunded { commitment, amount, account }`) on every successful `fund_message` call so fee changes are auditable via the same event-based trail used elsewhere in the pallet.
- Track and check message completion state (not just commitment existence) before accepting additional funding — reject `fund_message` calls against commitments whose corresponding request/response has already been delivered (e.g. via `RequestReceipts`/`ResponseReceipts`/`Responded` lookups), returning funds or erroring instead of silently accepting them.

### Proof of Concept
1. Party A dispatches a `PostRequest`/`GetResponse` with fee metadata created via `store_request_commitment`.
2. A relayer submits a valid proof through `handle_unsigned`, delivering the message and (per documented behavior) only removing the commitment on timeout — not on success — leaving `RequestCommitments`/`ResponseCommitments` metadata intact. [5](#0-4) 
3. Any account calls `fund_message` with that commitment and a nonzero `amount`. [6](#0-5) 
4. Tokens transfer to `RELAYER_FEE_ACCOUNT`, `metadata.fee.fee` increases in storage, but no event fires and no relayer action remains to consume this fee — the funds are permanently unrecoverable, and the change is invisible to any off-chain component watching only pallet events for fee/audit reconciliation.

		pub fn fund_message(
			origin: OriginFor<T>,
			message: FundMessageParams<T::Balance>,
		) -> DispatchResult {
			let account = ensure_signed(origin)?;

			let metadata = match message.commitment {
				MessageCommitment::Request(commitment) => RequestCommitments::<T>::get(commitment),
				MessageCommitment::Response(commitment) =>
					ResponseCommitments::<T>::get(commitment),
			};

			let Some(mut metadata) = metadata else {
				return Err(Error::<T>::MessageNotFound.into());
			};

			T::Currency::transfer(
				&account,
				&RELAYER_FEE_ACCOUNT.into_account_truncating(),
				message.amount,
				Preservation::Expendable,
			)?;

			match message.commitment {
				MessageCommitment::Request(commiment) => {
					metadata.fee.fee += message.amount;
					RequestCommitments::<T>::insert(commiment, metadata);
				},
				MessageCommitment::Response(commiment) => {
					metadata.fee.fee += message.amount;
					ResponseCommitments::<T>::insert(commiment, metadata);
				},
			};

			Ok(())
		}
