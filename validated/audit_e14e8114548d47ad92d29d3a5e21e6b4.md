### Title
Webhook `shop` field is passed to the handler unauthenticated by the HMAC signature, allowing cross-tenant impersonation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator.validate` only covers the raw request body, not this header. `Registry.process` validates the HMAC and then forwards `request.shop` to the app's `WebhookHandler#handle` as trusted tenant identity inside `WebhookMetadata`, even though that value was never bound to the signature.

### Finding Description
The intended trust invariant for a Shopify webhook is: *the shop identity delivered to the handler must be the shop that Shopify's HMAC actually vouches for*. This gem breaks that binding.

`Utils::HmacValidator.validate_signature` computes the signature over `verifiable_query.to_signable_string` only: [1](#0-0) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop` is read straight from an HTTP header that is not part of the signed material: [3](#0-2) 

`Registry.process` validates the HMAC (which only proves the body's integrity) and then constructs `WebhookMetadata` using this unauthenticated `request.shop`, handing it to the app-supplied handler as if it were verified tenant identity: [4](#0-3) [5](#0-4) 

Contrast this with `Auth::Oauth::AuthQuery`, used in the OAuth callback path, where the equivalent identity field `shop` **is** included in the signed string, i.e. the shop is cryptographically bound to the HMAC there: [6](#0-5) 

So the equality the library should guarantee — `hmac_verified(shop) == shop_delivered_to_handler` — holds for OAuth but does not hold for webhooks. For webhooks, `Request#shop` is attacker-controllable header data with no cryptographic tie to the HMAC that was checked; only the byte-identity of the JSON body is verified, not the header set that carries the tenant identifier.

### Impact Explanation
Any actor able to influence the headers of an otherwise-valid, Shopify-signed webhook delivery to the app's endpoint (e.g., a misconfigured shared reverse proxy/load balancer terminating and re-emitting webhook headers, a webhook relay/queue that fans out deliveries for multiple shops through a shared HMAC secret without preserving header integrity, or any component sitting between Shopify and the app that can rewrite headers while the body+HMAC pair remains untouched) can cause the library to report a different shop than the one that produced the signed body. Because `WebhookHandler#handle` implementations commonly use `data.shop` to select the tenant's data/config/access token to act on, this can result in the app performing actions or exposing data under the wrong shop's identity — a cross-tenant confusion caused entirely by this gem's failure to bind `shop` into the HMAC-checked value, even though the HMAC check nominally "passed."

### Likelihood Explanation
Exploitability depends on the deployment having some component between Shopify and the Rails/Rack app that can decouple headers from body+HMAC while a valid Shopify signature is reused (e.g., webhook aggregators, custom proxies, or bugs in header-forwarding infrastructure) — this is a real deployment pattern for high-volume Shopify apps that queue/relay webhooks. The root cause is squarely inside the gem: `to_signable_string` for `Request` was designed to cover only the body, unlike `AuthQuery`, which deliberately includes `shop` in its signed string. This asymmetry is a design defect, not merely host-application misuse.

### Recommendation
Extend the webhook signature verification to include shop-identifying headers, or explicitly document/enforce that `Request#shop` is untrusted metadata and must never be used for authorization decisions without an independent binding (e.g., cross-checking `shop` against an established, previously-authenticated session/shop record before invoking the handler). At minimum, `Registry.process` should not let `WebhookMetadata#shop` be treated as validated identity when only the body HMAC has been checked; if Shopify's protocol doesn't sign the header, the gem should surface this loudly to consumers rather than delivering it inside a struct that looks like the rest of the verified metadata.

### Proof of Concept
1. Attacker/relay receives a legitimate Shopify webhook delivery: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, header `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker/relay forwards the exact same body `B` and HMAC header unchanged to the app's webhook endpoint, but rewrites `x-shopify-shop-domain` to `shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (== `B`) and succeeds, since the body was untouched.
4. `request.shop` returns `shop-b.myshopify.com` (spoofed), and this value is placed into `WebhookMetadata#shop` passed to the app's handler as verified data — despite the signature having said nothing about which shop this payload belongs to.
