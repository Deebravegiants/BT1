Based on the code I reviewed, this claim describes a real and confirmed double-application hazard in the storage deposit metering logic.

The mechanism is exactly as described: `RawMeter::apply_pending_changes_to_contract` takes `&self` and explicitly documents that it "does not consume the pending diff" [1](#0-0) , leaving `own_contribution` as `Contribution::Alive(diff)` after mutating `info`. Later, `finalize_own_contributions` applies the *same* `own_contribution` to `info` a second time via `self.own_contribution.update_contract(info)` [2](#0-1) . The refund computation in `Diff::update_contract` is explicitly ratio-based against `info.storage_bytes`/`info.storage_items`, which are themselves mutated as a side effect of each application [3](#0-2) . This ratio calculation is only self-cancelling if `info` is untouched between the preview and final application — but the entire purpose of calling `apply_pending_storage_changes` before spawning a nested frame is to let that nested frame further mutate the same `info` [4](#0-3) .

The existence of the "safe" counterpart `bank_pending_changes`, which explicitly resets `own_contribution` "so finalize does not apply it a second time" [5](#0-4) , is strong corroborating evidence that the codebase authors are aware of exactly this double-application hazard and chose to guard against it in one call path but not in `apply_pending_storage_changes`/`apply_pending_changes_to_contract`, which is `&self` and cannot reset frame state.

I was not able to fully trace the call sites in `substrate/frame/revive/src/exec.rs` to confirm the precise sequencing (i.e., whether `apply_pending_storage_changes` is always followed by a nested frame that mutates the same `ContractInfo`, and whether `finalize_own_contributions`/`absorb` is subsequently called on the same frame's `own_contribution` without any intervening reset) — my last tool call for that file's surrounding context did not return content in time. This is the crux of confirming actual reachability and exploitability versus a purely theoretical construct with no live double-invocation path. Given this residual uncertainty about the exact call ordering in `exec.rs`, and because the report itself acknowledges the PoC would need to be written as a targeted unit test to demonstrate the failure (rather than pointing to an existing test that already fails), I cannot fully confirm the end-to-end exploit path from an unprivileged contract call through to actual over-refund via `execute_postponed_deposits`.

Given the strong internal evidence (the doc comments explicitly describing the non-consuming behavior, the existence of a "safe" counterpart that was clearly added to address this exact class of issue, and the mathematically demonstrable ratio-based refund logic that breaks under intervening mutation), the core technical claim about the mechanism is well-supported by the code. However, without being able to trace the exact `exec.rs` call sequence to confirm that `finalize_own_contributions`/`absorb` is actually invoked on the same frame after `apply_pending_storage_changes` without an intervening `bank_pending_storage_changes` reset call in the reentrant path described, I cannot fully certify this as an exploitable, unprivileged-triggerable vulnerability versus a theoretical one where the calling code may already correctly bank/reset before any double-application could occur. Audit Report

## Title
Double-application of a frame's pending storage diff to `ContractInfo` via `apply_pending_storage_changes` enables storage-deposit refund/charge miscalculation in reentrant nested calls - (File: substrate/frame/revive/src/metering/storage.rs)

## Summary
`RawMeter::apply_pending_changes_to_contract` mutates `ContractInfo` from a frame's pending `own_contribution` diff without consuming it, and `finalize_own_contributions`/`absorb` later apply the same diff again; because the refund side of `Diff::update_contract` is ratio-based against `info.storage_bytes`/`storage_items`, any mutation of `info` by a nested/reentrant call between the two applications corrupts the refund calculation.

## Finding Description
`apply_pending_changes_to_contract` explicitly documents it "does not consume the pending diff" and leaves `own_contribution` as `Contribution::Alive(diff)` [1](#0-0) . `finalize_own_contributions` subsequently applies `own_contribution` to `info` again [2](#0-1) . `Diff::update_contract`'s refund computation is a ratio against the contract's current `storage_bytes`/`storage_items`, which is mutated in place by each call [3](#0-2) , so the two applications are only benign if nothing else touches `info` in between — which contradicts the documented purpose of `apply_pending_storage_changes`, i.e., letting a nested frame observe and further mutate the same `info` before the parent's diff is finalized [4](#0-3) . The existence of `bank_pending_changes`, which resets `own_contribution` specifically "so finalize does not apply it a second time" [5](#0-4) , confirms this double-application hazard is a known concern in this module that is not addressed in the `apply_pending_storage_changes` path itself.

## Impact Explanation
If reachable end-to-end, this could allow a contract to cause the deposit meter to compute a refund/charge inconsistent with real net storage change, ultimately paid out via `execute_postponed_deposits` [7](#0-6) , potentially extracting more balance than deposited.

## Likelihood Explanation
I was unable to confirm from the available code whether `substrate/frame/revive/src/exec.rs` actually sequences `apply_pending_storage_changes` followed by a nested-call mutation of the same `ContractInfo` and then `finalize_own_contributions`/`absorb` on the same frame without an intervening `bank_pending_storage_changes` reset. This ordering is essential to prove actual reachability from an unprivileged contract call, and this could not be verified within the available tool budget.

## Recommendation
Ensure the pending diff previewed via `apply_pending_storage_changes` is applied to `info` exactly once for real accounting — either reset `own_contribution` after preview (mirroring `bank_pending_changes`) or snapshot/reconcile the diff explicitly before final application.

## Proof of Concept
A unit test extending `substrate/frame/revive/src/metering/storage/tests.rs` that creates nested frames sharing one `ContractInfo`, calls `apply_pending_changes_to_contract`, has an inner nested frame further mutate the same `info`, then finalizes the outer frame and asserts the total refund via `execute_postponed_deposits` does not exceed what a single non-reentrant application of the same diffs would produce — this test needs to be written since no existing regression test covers this reentrant path.

	pub fn execute_postponed_deposits(
		&mut self,
		origin: &Origin<T>,
		exec_config: &ExecConfig<T>,
	) -> Result<DepositOf<T>, DispatchError> {
		// Only refund or charge deposit if the origin is not root.
		let origin = match origin {
			Origin::Root => return Ok(Deposit::Charge(Zero::zero())),
			Origin::Signed(o) => o,
		};

		// Coalesce charges of the same contract
		self.charges.sort_by(|a, b| a.contract.cmp(&b.contract));
		self.charges = {
			let mut coalesced: Vec<Charge<T>> = Vec::with_capacity(self.charges.len());
			for mut ch in mem::take(&mut self.charges) {
				if let Some(last) = coalesced.last_mut() {
					if last.contract == ch.contract {
						match (&mut last.state, &mut ch.state) {
							(
								ContractState::Alive { amount: last_amount },
								ContractState::Alive { amount: ch_amount },
							) => {
								*last_amount = last_amount.saturating_add(&ch_amount);
							},
							(ContractState::Alive { amount }, ContractState::Terminated) |
							(ContractState::Terminated, ContractState::Alive { amount }) => {
								// undo all deposits made by a terminated contract
								self.total_deposit = self.total_deposit.saturating_sub(&amount);
								last.state = ContractState::Terminated;
							},
							(ContractState::Terminated, ContractState::Terminated) => {
								debug_assert!(
									false,
									"We never emit two terminates for the same contract."
								)
							},
						}
						continue;
					}
				}
				coalesced.push(ch);
			}
			coalesced
		};

		// refunds first so origin is able to pay for the charges using the refunds
		for charge in self.charges.iter() {
			if let ContractState::Alive { amount: amount @ Deposit::Refund(_) } = &charge.state {
				E::charge(origin, &charge.contract, amount, exec_config)?;
			}
		}
		for charge in self.charges.iter() {
			if let ContractState::Alive { amount: amount @ Deposit::Charge(_) } = &charge.state {
				E::charge(origin, &charge.contract, amount, exec_config)?;
			}
		}

	/// Apply pending storage changes to a ContractInfo without finalizing the meter.
	///
	/// This is used before creating a nested frame to ensure the child frame can see
	/// the parent's pending storage changes when calculating refunds.
	///
	/// Unlike [`Self::finalize_own_contributions`], this does not consume the pending diff,
	/// allowing the meter to continue tracking changes after the nested call returns.
	pub fn apply_pending_changes_to_contract(&self, info: &mut ContractInfo<T>) {
		if let Contribution::Alive(diff) = &self.own_contribution {
			// Apply the diff to update the ContractInfo's storage deposit fields.
			// We don't care about the return value (the deposit amount) here,
			// we just want to update the ContractInfo so child frames can see it.
			let _ = diff.update_contract::<T>(Some(info));
		}
	}
