### Title
Webhook `shop` (and topic/api-version/webhook-id) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value purely from an HTTP header, while the HMAC signature that `Utils::HmacValidator` verifies only covers the raw request body. Because the header is never bound into the signed content, any party who can legitimately obtain one valid `(body, hmac)` pair from Shopify can replay it to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header, and the signature check will still pass — causing the webhook handler to process attacker-chosen data as if it originated from a different, victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read directly from HTTP headers that are never part of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature only from `to_signable_string` (i.e., the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` trusts `request.shop` (an unauthenticated header) as the tenant identity handed to the app's handler once the (body-only) HMAC check passes: [4](#0-3) 

This breaks the intended identity binding: `shop verified by HMAC` should equal `shop delivered to handler`, but in reality `shop delivered to handler = shop header value`, which is completely independent of the HMAC-covered bytes (the body). A single `api_secret_key` is shared across every shop that has installed the app (Shopify webhooks are authenticated per-app, not per-shop), so a valid `(body, hmac)` pair generated for one tenant's webhook remains valid for any `shop` header value. Any merchant who has installed the app can capture a legitimate webhook Shopify sent to their own endpoint (body + `X-Shopify-Hmac-Sha256`) and POST that same body/hmac pair directly to the app's webhook endpoint (bypassing Shopify) while substituting the `X-Shopify-Shop-Domain`/`X-Shopify-Topic`/`X-Shopify-Webhook-Id` headers with a victim shop's domain or a different topic/id. `HmacValidator.validate` will still return `true` because it only re-derives the signature from the body, and `Registry.process` will invoke the handler with `WebhookMetadata` claiming the forged `shop`, `topic`, and `webhook_id`.

### Impact Explanation
This is a cross-tenant identity confusion: data or side effects that a host application scopes to `request.shop` (e.g., updating records, deleting/redacting shop-specific data for mandatory GDPR topics, or triggering business logic keyed by shop) can be triggered under an attacker-chosen shop identity by any other installed tenant, without needing the app's `client_secret`. This matches the "Critical - cross-tenant access" impact class, since the fundamental boundary (which tenant a webhook belongs to) is not cryptographically bound.

### Likelihood Explanation
Any merchant/developer who has installed the app is, from the app's perspective, an unprivileged actor relative to other tenants, and legitimately receives real webhooks with valid bodies and HMACs for their own shop. Replaying that pair to the public webhook endpoint with a modified `shop`/`topic`/`webhook-id` header requires only basic HTTP tooling — no secrets, no privileged access, and no interception of Shopify's traffic is needed.

### Recommendation
Bind the tenant/topic identity into the verified signature space rather than trusting headers unconditionally:
- Where the webhook payload includes shop identification, cross-check `request.shop` against the shop embedded in `parsed_body` before dispatching to handlers.
- Alternatively/additionally, include the relevant headers (`shop`, `topic`, `webhook-id`, `api-version`) in the signable string used by `HmacValidator`, or require the host application to independently confirm `request.shop` corresponds to a session/shop it already trusts before acting on the payload.
- Document clearly (and enforce in code) that `Request#shop`/`#topic`/`#webhook_id` are unauthenticated and must not be used as the sole tenant key.

### Proof of Concept
1. App has two installed shops: `victim.myshopify.com` and `attacker.myshopify.com`, sharing one `Context.api_secret_key`.
2. Shopify sends a legitimate webhook to the app for `attacker.myshopify.com`:
   - Headers: `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - Body: `{"id": 1, ...}`
3. Attacker captures this `(body, hmac)` pair (it was delivered to their own server).
4. Attacker POSTs directly to the app's public webhook endpoint with the same body and `hmac`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` (only body is checked): [5](#0-4) 
6. `Registry.process` dispatches to the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "orders/create", ...)`, causing the app to act on attacker-supplied data under the victim's tenant identity. [6](#0-5)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
