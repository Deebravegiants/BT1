### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw body via HMAC, while the `shop` domain that identifies which tenant the webhook belongs to is read from an unauthenticated header and passed straight through to the handler as the trusted tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `#shop` (as well as `#topic`, `#api_version`, `#webhook_id`) are read directly from HTTP headers that are never part of the signed content: [2](#0-1) 

`Registry.process` verifies the HMAC over the request and, if valid, dispatches the handler using the unauthenticated `request.shop` value as the tenant identity for the event: [3](#0-2) 

`HmacValidator.validate` computes/verifies the HMAC exclusively against `to_signable_string` (the raw body), never mixing in the `shop`, `topic`, or `webhook_id` headers: [4](#0-3) 

This breaks the intended identity binding: **`shop` claimed in the header == `shop` the HMAC actually authenticates**. In reality, the HMAC authenticates only the byte content of `raw_body`; it says nothing about which shop, topic, or webhook_id the byte content is attributed to. Any legitimately-signed `(raw_body, hmac)` pair — which an attacker can obtain simply by being a merchant who installs the app on their own store and receives their own genuine webhook deliveries from Shopify — can be replayed to the app's webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) header swapped to an arbitrary victim shop. `HmacValidator.validate` will still report success (it only checks the body bytes), and `Registry.process` will invoke the app's handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop domain.

### Impact Explanation
Any app built on this gem that uses `data.shop` from the webhook handler (as the documented usage guides consumers to do, e.g. `docs/usage/webhooks.md`) to select the tenant/session context for its own writes (e.g. updating per-shop billing state, marking a shop as installed/uninstalled, syncing per-shop resources, revoking or granting access) can be made to perform that tenant-scoped action against a shop the attacker does not control, using only content the attacker legitimately received from Shopify for their own shop. This is a cross-tenant identity confusion enabled directly by this gem's `Request`/`Registry`/`HmacValidator` trio, not by host-application misuse of an undocumented API — the gem's own webhook headers ("shop domain") are documented and handed to handlers as trusted, yet are outside the cryptographic binding it provides.

### Likelihood Explanation
Requires only that the attacker be a merchant who installs the target app (an unprivileged, ordinary path) and can trigger at least one webhook delivery for their own shop (trivial, e.g. any topic subscribed by the app), then replay the captured `(raw_body, hmac)` to the app's public webhook endpoint with a forged `shop`/`topic` header. No access token, `client_secret`, or privileged credential of the gem is required — only observation of the attacker's own legitimately delivered webhook.

### Recommendation
Bind the tenant/topic identity into the HMAC-verified surface: include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or otherwise cryptographically bind them, e.g. by having `HmacValidator` verify a canonicalized string of headers + body rather than body alone), or, at minimum, document loudly that `shop`/`topic`/`webhook_id` headers are unauthenticated metadata and must never be used by consuming apps to select tenant-scoped write operations without an independent verification step (e.g. cross-checking against the shop embedded in the parsed body, when present, or against a known/registered shop list).

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com` and subscribe to any topic the app has registered (e.g. `orders/create`).
2. Trigger a real event on `attacker.myshopify.com` so Shopify sends a legitimate webhook: capture the raw POST body `B` and the genuine `x-shopify-hmac-sha256` header `H` (valid because `H = HMAC_SHA256(api_secret_key, B)`, which only depends on `B`).
3. Replay the exact same `B` and `H` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com` (and, if desired, a different `x-shopify-topic`/`x-shopify-webhook-id` matching a topic the app also handles).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(B) == H`, per `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb#to_signable_string`.
5. The app's handler is invoked with `WebhookMetadata.shop == "victim.myshopify.com"`, causing any tenant-scoped logic in the handler to act on the victim shop's context using attacker-supplied body content.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
