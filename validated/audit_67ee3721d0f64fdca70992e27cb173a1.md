### Title
Unbounded memory allocation in Pharos validator-set proof decoding before proof verification - ([File: modules/consensus/pharos/verifier/src/state_proof.rs])

### Summary
`compute_all_storage_keys` derives the number of BLS-key storage slots to expect for each validator directly from an attacker-controlled, **unverified** raw storage value, and immediately builds a `Vec<H256>` sized by that number — before the storage proof for that value is ever checked against the state root. A relayer submitting a crafted `ValidatorSetProof` can set this length field to a huge value, causing the verifier to attempt an enormous heap allocation, analogous to CVE-2019-6975's uncontrolled memory consumption from an attacker-supplied numeric value flowing unchecked into a size-driven operation.

### Finding Description
`compute_all_storage_keys` walks `storage_values` to recompute the expected storage keys for each validator's BLS public key [1](#0-0) . For each validator it calls `bls_data_slots_from_header(&storage_values[idx])`, where `storage_values[idx]` is a raw byte blob supplied by whoever submits the proof — this happens **before** `verify_all_storage_proofs` runs, so the value has not yet been checked against `state_root` [2](#0-1) .

`bls_data_slots_from_header` decodes this unverified value as a Solidity long-string header and computes a slot count from it with no upper bound:
```
let length = (header_val - 1) / 2;
let str_len = length.low_u64() as usize;
Ok((str_len + 31) / 32)
``` [3](#0-2) 

`header_val` is a full `U256` decoded from the attacker-supplied bytes [4](#0-3) , so `str_len` can be forced up to `u64::MAX`, giving `slots_needed` on the order of `2^64/32 ≈ 5.76×10^17`.

This unbounded count is then passed straight into `get_validator_keys`, which allocates a `Vec<H256>` and pushes one 32-byte element per slot in a loop with no cap:
```
for i in 0..bls_data_slot_count {
    let slot_pos = bls_data_base_pos + U256::from(i);
    keys.push(H256(slot_pos.to_big_endian()));
}
``` [5](#0-4) 

While the outer validator `count` is capped at `MAX_VALIDATORS = 4096` [6](#0-5) [7](#0-6) , there is **no bound on the per-validator BLS data slot count** derived from `bls_data_slots_from_header`. A single crafted header value is enough to trigger a request for an allocation of hundreds of petabytes to exabytes, which aborts the process (Rust's default allocation-failure handler calls `abort`) rather than returning a gracefully handled error.

Critically, this computation runs on **raw, not-yet-proven** storage values — the very first pass over attacker-supplied proof data, prior to any cryptographic check. This mirrors the CVE-2019-6975 bug class: an externally supplied numeric value is fed, unchecked, into logic whose cost/memory scales with that value, with no upper bound enforced before the expensive operation runs.

### Impact Explanation
Any relayer that can submit a Pharos consensus/validator-set proof to the light client can crash the node processing it (uncontrolled/aborting memory allocation) with a single malformed proof, requiring no valid signatures or state-root match. This halts consensus verification for the Pharos route, preventing further state updates and message delivery through that light client — a denial of service against the route rather than a targeted resource cost, satisfying the "route unable to deliver messages" impact criterion. Because the crash occurs before proof verification, the cost of the attack to the submitter is negligible while the cost to the victim node is a hard crash.

### Likelihood Explanation
High. The vulnerable code path is reached on the normal proof-decoding flow (`verify_validator_set_proof` → `compute_all_storage_keys` → `bls_data_slots_from_header` → `get_validator_keys`), requires only a single controlled 32-byte "header" value in the submitted `storage_values` list, and no cryptographic proof of that value is needed to trigger the allocation attempt.

### Recommendation
Bound `str_len`/`slots_needed` in `bls_data_slots_from_header` (and the equivalent check in `decode_bls_key_from_string_slot`) to a small sane maximum (e.g., the expected ~4 slots for a 96/98-character BLS key string) and reject the proof early if it exceeds that bound, before any allocation proportional to the value is performed. Apply the same defensive check inside `get_validator_keys`/`compute_all_storage_keys` so the key-recomputation step itself never allocates based on an unverified value.

### Proof of Concept
1. Construct a `ValidatorSetProof` with `storage_values[1]` (the `activePoolSets` length) set to `1`, so the count check passes trivially.
2. Set the corresponding pool-id entry to any 32 bytes.
3. Set the "BLS header" storage value (`storage_values[idx]` at the validator's header slot) to a `U256` value with the low bit set (marking it as a Solidity "long string") and the upper bits maximized, e.g. `U256::MAX`.
4. Submit this proof to `verify_validator_set_proof`.
5. Execution reaches `compute_all_storage_keys` → `bls_data_slots_from_header`, computing `str_len ≈ u64::MAX/2`, then `slots_needed ≈ 5.76×10^17`.
6. `layout.get_validator_keys` attempts to build a `Vec<H256>` of that length, triggering an allocation failure and process abort — before `verify_all_storage_proofs` ever runs, i.e., without any valid Merkle/state proof.

	storage_values: &[Vec<u8>],
	layout: &StakingContractLayout,

	if storage_values.len() < 2 {
		return Err(Error::InsufficientStorageValues { expected: 2, got: storage_values.len() });
	}

	let mut keys = Vec::new();

	// Index 0: totalStake
	keys.push(layout.raw_slot_key(layout.total_stake_slot));

	// Index 1: activePoolSets length
	keys.push(layout.raw_slot_key(layout.active_pool_set_slot));

	let count = decode_u256_from_storage(&storage_values[1])?.low_u64() as usize;

	if count > MAX_VALIDATORS {
		return Err(Error::TooManyValidators { count, max: MAX_VALIDATORS });
	}

	let pool_ids_end = pool_set_start + count;

	if storage_values.len() < pool_ids_end {
		return Err(Error::InsufficientPoolIds {
			expected: pool_ids_end,
			validators: count,
			got: storage_values.len(),
		});
	}

	// Pool ID array element keys
	for i in 0..count {
		keys.push(layout.array_element_key::<H>(layout.active_pool_set_slot, i as u64));
	}

	pub fn get_validator_keys<H: Keccak256>(
		&self,
		pool_id: &H256,
		bls_data_slot_count: usize,
	) -> Vec<H256> {
		let offsets = ValidatorStructOffsets::default();
		let mut keys = Vec::new();

		// BLS public key string slot (stores length for long strings)
		let bls_string_slot = self.validator_field_slot::<H>(pool_id, offsets.bls_public_key);
		keys.push(bls_string_slot);

		// BLS public key data slots (for long strings)
		// Data is stored at keccak256(string_slot) for `bls_data_slot_count` slots
		let bls_data_base = self.string_data_slot::<H>(&bls_string_slot);
		let bls_data_base_pos = U256::from_big_endian(bls_data_base.as_bytes());
		for i in 0..bls_data_slot_count {
			let slot_pos = bls_data_base_pos + U256::from(i);
			keys.push(H256(slot_pos.to_big_endian()));
		}

		// totalStake field
		keys.push(self.validator_field_slot::<H>(pool_id, offsets.total_stake));

		keys
	}

pub fn bls_data_slots_from_header(header_value: &[u8]) -> Result<usize, Error> {
	let header_val = decode_u256_from_storage(header_value)?;
	let header_bytes = header_val.to_big_endian();
	let lowest_byte = header_bytes[31];

	if lowest_byte & 1 == 0 {
		// Short string - data is in the header itself
		Ok(0)
	} else {
		// Long string - header = length * 2 + 1
		let length = (header_val - 1) / 2;
		let str_len = length.low_u64() as usize;
		Ok((str_len + 31) / 32)
	}

/// Decode a U256 value from raw big-endian storage bytes.
pub fn decode_u256_from_storage(value: &[u8]) -> Result<U256, Error> {
	if value.is_empty() {
		return Ok(U256::zero());
	}

	if value.len() <= 32 {
		let mut padded = [0u8; 32];
		padded[32 - value.len()..].copy_from_slice(value);
		Ok(U256::from_big_endian(&padded))
	} else {
		Err(Error::StorageValueTooLarge)
	}
