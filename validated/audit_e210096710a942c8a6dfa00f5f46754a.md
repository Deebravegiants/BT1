### Title
Unchecked ERC20 return value in `IntentGatewayV2.withdraw()` finalizes escrow release even when the token transfer silently fails - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.withdraw()` on Tron moves escrowed tokens out with a raw low-level `.call` and only checks that the call did not revert (`success`), never decoding/validating the ERC20 `transfer` return value. It then unconditionally decrements the internal escrow accounting and marks the order filled/refunded, exactly mirroring the reported class of bug: an accounting layer that assumes a withdrawal delivered the full accounted amount without verifying the actual result of the underlying asset movement.

### Finding Description
`withdraw()` is the internal settlement routine invoked from `onAccept()` (for `RedeemEscrow`/`RefundEscrow` messages relayed from the source/destination chain) and from `onGetResponse()` (cancellation path). It iterates the escrowed tokens and releases them: [1](#0-0) 

For every ERC20 token it does:
```
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
...
_orders[body.commitment][token] -= amount;
```
This checks only that the low-level call did not revert. Per the ERC20 standard, `transfer` is permitted to return `false` on failure instead of reverting (many legacy/non-standard TRC20/ERC20 tokens on Tron behave this way). In that case `success` is still `true` (the call executed without reverting), the `if (!success)` guard never fires, yet no tokens were actually delivered to `beneficiary`. Despite that, the function proceeds to:
- mark the order `_filled[body.commitment] = beneficiary` (finalizing/closing the order),
- decrement `_orders[body.commitment][token] -= amount` (destroying the escrow accounting for the full `amount`),
- emit `EscrowReleased`/`EscrowRefunded` as if settlement succeeded.

The same unchecked-call pattern is used for the transaction-fee payout in the same function and for `SweepDust`: [2](#0-1) 

This is the direct analog of the reported issue: `AssetManager.withdraw()` returns success (`true`) without guaranteeing the requested amount was actually moved, and the caller (`redeem()`) burns/reduces its accounting by the full nominal amount regardless. Here, `withdraw()`'s "success" signal (a call that didn't revert) is likewise decoupled from whether the beneficiary actually received `amount`, and the escrow bookkeeping (`_orders[...][token] -= amount`, `_filled[...] = beneficiary`) is updated as though it did.

Note: the equivalent EVM contract, `IntentsBase._withdraw`, uses OpenZeppelin's `SafeERC20.safeTransfer`, which does validate the return data and reverts on a `false` return — so this specific weakness is confined to the Tron variant, which deliberately bypasses `SafeERC20` for its token transfers in `withdraw()`/`SweepDust`.

### Impact Explanation
For any TRC20/ERC20 token integrated with the Tron `IntentGatewayV2` that returns `false` on transfer failure rather than reverting (common among older/non-standard tokens, which are prevalent on Tron), a `RedeemEscrow`/`RefundEscrow` settlement or a cancellation refund can be processed and permanently finalized (`_filled` set, escrow slot zeroed/decremented, event emitted) while the beneficiary receives nothing. The escrowed user or solver funds are then unrecoverable through the protocol's normal flows — the order is already marked filled/refunded and the escrow balance is already gone, so no legitimate retry path exists. This is a permanent freezing/loss-of-funds condition triggered purely by a relayed message delivery (an unprivileged, expected code path), not by any privileged actor.

### Likelihood Explanation
Reachability requires only: (1) a token configured for the Intent Gateway that follows the non-reverting "return false on failure" ERC20 variant (or a token that can be made to return `false` transiently, e.g. via a paused/blacklist state at settlement time), and (2) the ordinary relayer-driven delivery of a `RedeemEscrow`/`RefundEscrow` post request or a `GET` cancellation response — both are core, expected parts of the intents settlement flow and require no special privilege. No malicious insider or governance compromise is needed; a single relayed message against an order paying out in such a token is sufficient to trigger the loss.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` (and in the `SweepDust` handling and fee payout) with OpenZeppelin's `SafeERC20.safeTransfer`, matching the EVM implementation in `IntentsBase._withdraw`. `SafeERC20` decodes the return value when present and reverts on `false`, ensuring escrow accounting is only mutated and the order only finalized when the transfer is verified to have succeeded.

### Proof of Concept
1. Deploy/configure `IntentGatewayV2` (Tron) with an ERC20-like token whose `transfer()` returns `false` on failure instead of reverting (e.g., paused, blacklisted recipient, or insufficient contract-side balance handled via a `bool` return rather than a revert).
2. A user places an order escrowing this token via `placeOrder`.
3. A solver fills the order on the destination chain; a `RedeemEscrow` post request is relayed back and delivered through `onAccept()` → `withdraw()`.
4. Arrange for the token's `transfer(beneficiary, amount)` call to return `false` (e.g., the beneficiary is blacklisted at settlement time) while not reverting.
5. `withdraw()` observes `success == true` (the call itself didn't revert), skips the `TransferFailed()` revert, decrements `_orders[commitment][token] -= amount`, sets `_filled[commitment] = beneficiary`, and emits `EscrowReleased`.
6. The beneficiary's token balance is unchanged (transfer silently failed), yet the escrow record shows the order settled and the underlying tokens are unrecoverable — funds are permanently frozen/lost from the protocol's perspective.
