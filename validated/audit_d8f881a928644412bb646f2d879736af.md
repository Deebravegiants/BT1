### Title
Auto-lock passphrase cache validity window can be silently extended after inactivity, allowing stale cached passphrase to bypass re-authentication - (File: features/application/src/modules/passphrase-cache.ts)

### Summary
`PassphraseCache` decides whether a cached (plaintext) wallet passphrase may be replayed to auto-unlock the wallet by comparing `inactiveAt + ttl` (or `addedAt + maxTtl`) against `Date.now()`. `changeTtl()` — reachable through `Application.changeLockTimer()` — mutates the stored `ttl` used in that comparison without resetting `inactiveAt`, which was set at the moment the session actually went inactive. This mirrors the Cap `slashTimestamp()` bug class: a timestamp-derived security boundary can be pushed later by an action unrelated to the event the boundary is supposed to measure, always biasing the outcome toward "still valid" rather than reflecting the true elapsed inactivity.

### Finding Description
`PassphraseCache.get()` computes validity purely from stored timestamps: [1](#0-0) 

`scheduleClear()` stamps `INACTIVE_AT_KEY` with `Date.now()` the moment the session is considered inactive (e.g. on `Application.unload()` / `restartAutoLockTimer()`): [2](#0-1) [3](#0-2) 

`changeTtl()` — invoked via the public `Application.changeLockTimer()` API — is allowed to raise the `TTL_KEY` used in the `get()` check up to `maxTtl`, but it does not touch `INACTIVE_AT_KEY`: [4](#0-3) [5](#0-4) 

Because `get()`'s validity test is `inactiveAt + ttl > Date.now()`, increasing `ttl` after `inactiveAt` was already recorded retroactively extends the window during which the cached passphrase is treated as fresh — exactly the same root cause pattern as Cap's `slashTimestamp()`: the boundary timestamp is not re-derived from the actual triggering event (last borrow / last inactivity), so a later, unrelated call (borrow / `changeLockTimer`) can always push the check in the caller's favor.

`#autoUnlock()` then trusts `passphraseCache.get()` unconditionally to decrypt and unlock the wallet without any user-entered passphrase: [6](#0-5) 

### Impact Explanation
If `changeLockTimer` is reachable in a context where a stale, otherwise-expired cached passphrase still exists in storage (e.g. extension restarted, or the call is triggered right at/after the intended expiry), an attacker (or malicious script with access to the exposed application API surface) can extend the auto-unlock validity window after the fact and cause the wallet to auto-unlock using the previously cached decrypted passphrase — bypassing the auto-lock re-authentication control that is supposed to require re-entry of the passphrase once the TTL elapses. This is a direct auth-bypass / wallet-compromise-adjacent impact, since it defeats the "wallet re-locks and requires passphrase re-entry after inactivity" security guarantee.

### Likelihood Explanation
Exploitability depends on whether `Application.changeLockTimer` / `PassphraseCache.changeTtl` can be invoked by an untrusted caller (e.g., through the RPC bridge exposed to dApp/content-script contexts) independent of whether the wallet is currently unlocked, and on timing (the call must land before the scheduled `clear-passphrase` alarm actually clears storage). I could not fully confirm the authorization boundary of the `changeLockTimer` API entry point from the indexed files alone (i.e., whether it is gated to only be callable while already unlocked, or exposed to untrusted RPC callers) — this would need to be confirmed in a full checkout.

### Recommendation
Reset `INACTIVE_AT_KEY` to `Date.now()` (or clear it) whenever `changeTtl` is called, and/or derive the validity comparison strictly from the last real inactivity/authentication event rather than allowing a subsequent, unrelated write to widen an already-open window. Additionally, verify that `changeLockTimer` cannot be invoked from untrusted/unauthenticated call sites.

### Proof of Concept
Conceptual sequence (based on code above, not executed):
1. User authenticates; `passphraseCache.set(passphrase)` stores `addedAt`, `ttl`.
2. App goes inactive; `Application.unload()` → `passphraseCache.scheduleClear()` stores `inactiveAt = t0` and schedules clearing after `ttl`.
3. Just before/after `t0 + ttl` (the intended expiry), a caller invokes `Application.changeLockTimer({ ttl: maxTtl })` → `passphraseCache.changeTtl(maxTtl)`, which raises `TTL_KEY` to `maxTtl` without updating `inactiveAt`.
4. On next `Application.start()`, `#autoUnlock()` calls `passphraseCache.get()`, which now evaluates `inactiveAt + maxTtl > Date.now()` as true, and the wallet is auto-unlocked with the stale cached passphrase well past the originally configured inactivity limit. [4](#0-3) [7](#0-6)

  async changeTtl(ttl: number) {
    const newTtl = Math.min(this.#maxTtl, ttl)

    await this.#autoLockTimerAtom.set(newTtl)

    const passphrase = await this.#storage.get(PASSPHRASE_KEY)

    if (passphrase) {
      await this.#storage.set(TTL_KEY, newTtl)

      void this.#scheduleClear()
    }
  }
