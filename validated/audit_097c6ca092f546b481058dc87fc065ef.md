### Title
Backend-supplied `user_centric_signup` flag lets orb-core skip server-side enrollment/dedup/fraud verification without any cooldown - (File: src/plans/mod.rs)

### Summary
The external report describes an attack where a compromised, externally-controlled trust source (an LST) can instantly grant an attacker elevated protocol privileges because the consuming system (EigenDA/AVS) performs no additional delay or independent verification before honoring the externally-supplied value. The same root-cause pattern — trusting an externally-supplied "shortcut" flag to skip the authoritative verification step, with no cooldown/second check — exists in orb-core's signup flow via the `user_centric_signup` boolean.

### Finding Description
`user_centric_signup` is a boolean received from the backend/app as part of `authenticated_app_data` in the `/status` response, deserialized into `orb_qr_link::UserData` and only checked with a hash comparison (`user_data.verify(user_data_hash)`), not cryptographically bound to enrollment outcome: [1](#0-0) [2](#0-1) 

This flag is carried through the signup pipeline as `qr_codes.user_data.user_centric_signup` and, when `true` and the local `ignore_user_centric_signups` config is `false` (which is the default: `ignore_user_centric_signups: false`), causes the orb to **bypass the authoritative backend enrollment call entirely** (`enroll_user::Plan.run()`), and instead locally decide "success" purely from the local biometric-pipeline result: [3](#0-2) [4](#0-3) 

The backend enrollment call (`enroll_user::Plan`) that gets skipped is exactly the step that performs backend-side duplicate detection, in-flight match detection, and backend fraud detection, as documented directly in the code comments: [5](#0-4) 

In other words, a single boolean sourced from an external, less-trusted channel (app/backend `authenticated_app_data`, validated only by a hash check that must match `user_data_hash` embedded in the scanned QR code) is enough to instantly and irrevocably steer the orb into treating the signup as complete/authorized without contacting the canonical enrollment/fraud/duplicate-check endpoint — analogous to how a compromised LST value is enough to instantly and irrevocably increase an attacker's stake/power without any independent, delayed verification step by the consuming AVS.

### Impact Explanation
If the `user_centric_signup`/`user_data_hash` trust boundary is compromised (e.g., a forged or replayed QR-linked payload, or a compromise of whatever key/mechanism produces `authenticated_app_data`), the orb will locally mark the signup as `Success` (`SignupReason::Normal`) and proceed to build and upload the Personal Custody Package (identity credentials) for that user without ever invoking the backend's real enrollment/dedup/fraud pipeline. This maps to the accepted impact categories of unauthorized/misattributed signup and fraud-enforcement bypass: an identity/credential could be issued or bound while completely skipping the backend’s duplicate-detection and fraud-detection safeguards, and there is no cooldown or secondary confirmation step giving the backend a chance to intervene, mirroring the "two-block window" problem in the original report but at the orb signup-authorization layer.

### Likelihood Explanation
Likelihood is **low-to-medium** and inherits from the same class as the original finding: it does *not* require any weakness in the orb itself, only compromise of an external/less-trusted upstream signal (here, the value or verification key backing `authenticated_app_data`/`user_data_hash`), exactly as the original report requires compromise of an external LST. Given orb-core's local index does not expose the implementation of `orb_qr_link::UserData::verify()` (it lives in an external crate not indexed here), the strength of the hash/signature binding could not be independently verified — this is a genuine gap in this analysis, not a confirmed weakness.

### Recommendation
- Do not allow a single externally-supplied boolean to fully bypass the backend's authoritative enrollment call. At minimum, retain a lightweight backend confirmation/duplicate check even in the `user_centric_signup` path, or require a signed, time-bound confirmation independent of the QR-derived hash.
- Add a rate limit / cooldown on the number of `user_centric_signup=true` signups accepted from a given orb before requiring a full backend enrollment round trip, so that if the upstream signing/verification mechanism is ever compromised, the blast radius per unit time is bounded (directly analogous to the `rateLimitAmountPerBlock` mitigation proposed in the original report).
- Audit and, if possible, obtain the source of `orb_qr_link::UserData::verify()` to confirm the hash/signature binding cannot be forged or replayed for an attacker-chosen `user_centric_signup=true`.

### Proof of Concept
1. Attacker (or compromised upstream component) that can produce a validly-hashed `authenticated_app_data` payload for a given QR (i.e., pass `user_data.verify(user_data_hash)`) sets `user_centric_signup: true`. [1](#0-0) 
2. Orb runs the biometric pipeline; assuming it returns any non-fraud pipeline result (`SignupReason::Normal`), the orb reaches the branch at: [6](#0-5) 
3. Because `user_centric_signup && !ignore_user_centric_signups` is true (default config leaves `ignore_user_centric_signups = false`), the orb sets `enrollment_status` to `Success` and marks the signup successful **without ever calling** `enroll_user::Plan.run()` — the code path that performs backend duplicate/in-flight/fraud detection: [5](#0-4) 
4. The Personal Custody Package (identity credentials) is built and uploaded (`build_pcp`/`upload_pcp_tier_0`, lines 580-636 of `src/plans/mod.rs`) even though the backend's canonical enrollment/fraud/duplicate check was never invoked for this signup — no cooldown or secondary verification exists to catch this in the same way the LST report’s two-block window offered no time for defensive action.
