Webhook `shop-domain` header is trusted for tenant identity but is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value used by the app's webhook handler purely from the `X-Shopify-Shop-Domain` HTTP header, while `ShopifyAPI::Utils::HmacValidator` only validates the HMAC over the raw request body. This breaks the identity binding: `shop header verified == shop header used for tenant identification`. Because the HMAC secret (the app's `client_secret`) is shared across every shop that installs the app, any unprivileged attacker who installs the app on their own shop can capture a genuinely-signed webhook (valid body + valid HMAC), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Registry.process` will accept it as valid and hand the handler a `WebhookMetadata` claiming the victim shop, even though nothing cryptographically bound the shop identity to that signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is a separate accessor read directly from the (unsigned) header: [2](#0-1) 

`Utils::HmacValidator.validate` computes/verifies the HMAC solely against `to_signable_string` (i.e., the body), never incorporating `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` validates the HMAC and then trusts `request.shop` (and `request.topic`/`request.webhook_id`) to build the metadata passed to the app's handler, with no secondary verification that the shop is the one that actually owns/subscribed to that webhook body: [4](#0-3) 

The equality that should hold but does not:
`shop bound by HMAC signature == shop used to attribute/act on the webhook payload`

In reality: `shop covered by HMAC == {}` (nothing) while `shop used for tenant attribution == X-Shopify-Shop-Domain header` (fully attacker-controllable, since Shopify's webhook `client_secret` for a given app is identical across all shops that install it — this is standard Shopify webhook behavior, not specific to this gem, but the gem is the layer responsible for verifying which fields are authenticated).

Because the HMAC key (app `client_secret`) is shared across tenants and the signature covers only the body, an attacker who is a legitimate, unprivileged installer of the app on their own store can:
1. Register a webhook topic and receive a real, correctly-signed Shopify webhook for their own shop (attacker owns the raw body and the valid `X-Shopify-Hmac-Sha256` value for that body).
2. Replay the identical raw body + HMAC header to the app's public webhook endpoint, but swap `X-Shopify-Shop-Domain` (and, since it's also unsigned, `X-Shopify-Webhook-Id`/`X-Shopify-Api-Version` if desired) to name a victim shop.
3. `HmacValidator.validate` succeeds because the signature check never referenced the shop header — only the (attacker-supplied, self-consistent) body.
4. The app's own webhook handler receives `WebhookMetadata` claiming the event is `shop: <victim>.myshopify.com`, and typically uses that `shop` value to look up the victim's stored session/access token and act on the victim's data (e.g., re-triggering fulfillment logic, marking uninstall, updating locally cached order/customer data, or any app-specific action keyed by `data.shop`).

This is the exact class of bug the rules flag: "a field acted on but not covered by the HMAC."

### Impact Explanation
This crosses a tenant boundary: an attacker with no privileges beyond installing the app on their own shop can make the app process a fabricated event as though it originated from a different (victim) merchant's shop, since the shop identity attribute is unauthenticated. Depending on how the host app consumes `WebhookMetadata#shop` (which the gem's own documentation instructs apps to trust directly, e.g. `data.shop`), this can drive actions using the victim's real stored access token/session (looked up by `shop`), corrupt the victim's locally cached state, or falsely trigger app/uninstalled-style logic for the victim tenant — i.e., cross-tenant access/manipulation, matching the "Manipulation of governance voting result... resulting in a direct change from intended effect" analog class and the "Cross-tenant access" impact bucket.

### Likelihood Explanation
High likelihood of exploitability for any app built on this gem's documented webhook pattern: the attacker only needs to install the target app on a shop they control (a normal, unprivileged action any internet user can take for any public Shopify app) and capture one legitimate webhook. No access token, leaked secret, or privileged account is required — the `client_secret`/HMAC key is common to all installs of the app, which is intrinsic to Shopify's webhook design, and this gem does nothing to bind the shop claim to the signature to compensate.

### Recommendation
Bind the shop (and ideally topic/webhook id) to the authenticated data before it is trusted:
- Do not treat `request.shop` (or `topic`, `webhook_id`) as authenticated identity data derived solely from HTTP headers.
- After HMAC validation, cross-check `request.shop` against the set of shops for which the app actually has an active session/registration for that specific webhook subscription (e.g., verify the webhook id belongs to a subscription registered for that shop via the Admin API), or require the host application to independently verify tenant ownership before acting on `data.shop`.
- At minimum, document loudly (and ideally enforce in `Registry.process`) that `shop` in `WebhookMetadata` must not be used as an authorization key without additional verification, since it is not part of the signed payload.

### Proof of Concept
```ruby
# Attacker legitimately installs the app on their own shop and receives one real webhook.
# raw_body and its valid hmac header are captured from that real request, e.g.:
raw_body = '{"id":123,"note":"hello"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_CLIENT_SECRET, raw_body)
)
# (APP_CLIENT_SECRET is the SAME secret used for every shop that installs this app —
#  attacker never needs to know it, they just captured a real Shopify-signed request.)

# Attacker now replays the SAME body+hmac to the app's public webhook endpoint,
# but claims the victim's shop domain instead of their own:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # <-- unsigned, attacker-controlled
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# This passes HMAC validation because the signature only covers raw_body:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "orders/create", body: {...}))
```
`Utils::HmacValidator.validate` returns `true` for this request because it only checks `OpenSSL.secure_compare(computed_signature, hmac)` against `raw_body`, never the `shop` header: [5](#0-4) 

The handler then receives `data.shop == "victim-shop.myshopify.com"`, an identity the attacker fabricated with a signature that was never bound to that value.
