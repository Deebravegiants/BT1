Audit Report

## Title
Legacy gateway trigger messages bypass allowlist and rate-limiting checks - ([File: core/services/gateway/handlers/capabilities/handler.go])

## Summary
`HandleLegacyUserMessage` in the `capabilities` gateway handler forwards `web_api_trigger` requests to every DON member without applying any caller allowlist or rate-limit check, as confirmed by the explicit `// TODO: apply allowlist and rate-limiting here` comment. However, this handler's own `HandleJSONRPCUserMessage` counterpart is completely unimplemented (returns `"capabilities handler does not support JSON-RPC user messages"`), so the legacy path is not bypassing a parallel authorization check within this same handler — it is the *only* supported entry point for this capability's trigger flow.

## Finding Description
`gateway.ProcessRequest` routes requests with a `DonID` set to the legacy path, calling `h.HandleLegacyUserMessage` [1](#0-0) . Inside `HandleLegacyUserMessage`, after basic payload/timestamp/staleness checks, the code reaches `// TODO: apply allowlist and rate-limiting here` and then only checks the method name and structural validity before unconditionally forwarding the request to every DON member via `don.SendToNode` [2](#0-1) .

Critically, the same `handler` struct's `HandleJSONRPCUserMessage` — the method the report claims is the "modern" parallel path that does perform allowlist checks — is a stub that unconditionally rejects all JSON-RPC requests: `return errors.New("capabilities handler does not support JSON-RPC user messages")` [3](#0-2) . The actual final authorization for delegating trigger events to registered workflows happens downstream, inside `triggerConnectorHandler.processTrigger` in the node-side capability (`core/capabilities/webapi/trigger/trigger.go`), which checks `trigger.allowedSenders[sender.String()]` and `trigger.rateLimiter.Allow(...)` per-topic before dispatching to any registered workflow [4](#0-3) . This means the gateway forwards the raw request to all DON nodes (which is by design — the gateway does not know which workflows/senders are permitted, only the DON node capability does), and each node's own trigger capability enforces the allowlist/rate-limit before actually triggering any workflow execution.

The `httpTriggerHandler.validatedTriggerRequest`/`authorizeRequest` code cited in the report belongs to an entirely different handler package (`core/services/gateway/handlers/capabilities/v2`), used for a different capability (`web_api_action`/HTTP trigger via `MethodWorkflowExecute`), not to the same `handler` struct that implements `HandleLegacyUserMessage`. Comparing these two as "the same gateway handler's" dual entry points is inaccurate — they are separate handler implementations serving separate capability types, each registered independently in the gateway's routing table.

The TODO comment is real and does indicate a known gap (the gateway itself performs no caller-level allowlisting before fan-out to DON nodes), but the actual sender/topic-based authorization gate for this particular trigger capability lives at the DON node, not at the gateway, and that gate is applied identically regardless of how the message reaches the node.

## Impact Explanation
There is a real, unaddressed TODO indicating the gateway lacks caller-level allowlisting/rate-limiting before forwarding legacy trigger messages to DON nodes. However, this does not by itself allow an unauthenticated actor to trigger unauthorized workflow execution: the final trigger authorization (`allowedSenders`, `allowedTopics`, per-sender rate limiting) is enforced in `triggerConnectorHandler.processTrigger` on each DON node before any workflow's channel is written to. The claim that this is a "bypass" of a check performed by "the modern JSON-RPC trigger path used by the same gateway" is not supported — the cited v2 HTTP trigger handler is a different capability/handler with a different auth model entirely, not a parallel code path for the same `MethodWebAPITrigger` flow. The gateway lacking a pre-DON allowlist check causes unnecessary network fan-out/potential DoS load on DON nodes, but each node itself still gates actual trigger execution.

## Likelihood Explanation
An unprivileged client can indeed reach `HandleLegacyUserMessage` by sending a legacy DonID-formatted request, as claimed. That part of the reachability analysis is correct. But the consequence claimed — unauthorized workflow triggering — is not proven, since the downstream node-side allowlist (`allowedSenders`) still blocks any sender not explicitly allowed for a given workflow's topics.

## Recommendation
Not applicable as a confirmed vulnerability at the claimed severity; if pursued, the TODO could still be addressed to reduce unnecessary DON-wide fan-out of unauthenticated requests (a resource-exhaustion/DoS hardening improvement), but this is materially different from the claimed "allowlist bypass leading to unauthorized workflow execution."

## Proof of Concept
Not applicable — the claim's core impact (bypassing authorization to trigger unauthorized workflow execution) is not reproducible because the described "modern JSON-RPC trigger path" comparison is between two different, unrelated handler implementations, and the actual sender allowlist for `MethodWebAPITrigger` triggers is enforced at the DON node level (`processTrigger`) regardless of which gateway code path delivered the message.
