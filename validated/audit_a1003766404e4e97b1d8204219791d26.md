## Analog Found

### Title
Unbounded, fee-free `handle_unsigned` message batches trigger unmetered synchronous proof verification during transaction-pool validation, enabling a network-wide DoS - ([File: modules/pallets/ismp/src/lib.rs])

### Summary
The vLLM advisory's root cause is that an unvalidated, attacker-controlled request parameter (`chat_template_kwargs`) is passed unfiltered into a lower-level function, silently flipping a default from cheap to a synchronous, blocking, and unbounded-cost operation (`tokenize=True`) that starves the event loop for all other requests. The structural analog in Hyperbridge is `pallet_ismp::Pallet::handle_unsigned`, whose `ValidateUnsigned::validate_unsigned` implementation calls `Self::execute(messages.clone())` — fully running consensus/state-proof verification, trie lookups, and signature checks — synchronously on every node that receives the gossiped unsigned extrinsic, before it is ever included in a block and before any real fee or weight constraint is applied.

### Finding Description
`handle_unsigned` is dispatched as `ensure_none(origin)` (fully permissionless, no signer, no fee) and simply calls `Self::execute(messages.clone())`: [1](#0-0) 

Its `validate_unsigned` hook — which every full node runs merely to admit the extrinsic into its transaction pool during gossip, i.e. *before block inclusion and before any weight accounting is enforced* — performs the *entire* message execution eagerly to compute validity: [2](#0-1) 

That execution path (`Pallet::execute` → `handlers::response::handle` / `handlers::request::handle`) walks every `Request`/`Response` in the batch and, for `Get` responses, calls `verify_state_proof` once per request with the caller-supplied `keys: Vec<Vec<u8>>`, each key driving its own trie lookup / hashing operation with no upper bound enforced before the walk begins: [3](#0-2) [4](#0-3) 

Crucially, the declared weight for `handle_unsigned` is a hard-coded constant, disconnected from the actual number of messages, requests, or keys in the batch: [5](#0-4) 

So the only "protection" the docs describe — "the transaction pool will check if the submitted extrinsics are valid before they are included in the pool... preventing unnecessary processing and potential network congestion" — is precisely the mechanism that forces every full node in the network to eagerly perform the full, unbounded verification cost as a side effect of gossip admission, exactly analogous to vLLM's `apply_hf_chat_template(tokenize=True)` being invoked unconditionally as a side effect of an otherwise cheap-looking request path: [6](#0-5) 

### Impact Explanation
Because `handle_unsigned` costs nothing to submit (no signer, no fee, `Pays::No` on the "free" path) and its `validate_unsigned` re-executes the *entire* batch's cryptographic and trie work on every node that receives it via gossip — independent of whether it's ever included in a block — an attacker can craft large batches (many `GetRequest`/`GetResponse` entries, each with many `keys`, plus large state/membership proofs) that are cheap to construct but expensive to verify. Submitting a stream of such extrinsics forces every collator/full node's transaction-pool validation logic to burn CPU synchronously, degrading block production and network responsiveness — a resource-exhaustion DoS reachable by any unprivileged relayer/dispatcher, matching CWE-770 in the reference advisory.

### Likelihood Explanation
`handle_unsigned` is explicitly designed to be permissionless and free ("This allows users execute ISMP datagrams for free. Use with caution.") and is the intended ingress point for relayers delivering cross-chain messages, so the attack surface is directly reachable with a single unsigned transaction — no privileged role, governance action, or chain compromise is required.

### Recommendation
Bound the cost of `validate_unsigned` before performing full execution: cap the number of messages per batch, the number of `keys` per `GetRequest`/`GetResponse`, and proof sizes with hard limits enforced up front (mirroring the existing `MAX_PROOF_DEPTH` guard pattern used in `modules/consensus/pharos/primitives/src/spv.rs`), and/or make the declared weight for `handle_unsigned` scale with the actual batch/key/proof size rather than being a fixed constant, so that oversized batches are rejected cheaply (by size/shape) prior to any expensive cryptographic verification during pool admission.

### Proof of Concept
1. Construct a `Message::Response` containing a `ResponseMessage` whose `requests: Vec<GetRequest>` includes many `GetRequest`s, each with a large `keys: Vec<Vec<u8>>` (bounded only by extrinsic size limits, which are megabytes), together with a corresponding proof.
2. Submit this as an unsigned `handle_unsigned` extrinsic via RPC/gossip.
3. Every node that receives the gossiped transaction invokes `ValidateUnsigned::validate_unsigned`, which calls `Self::execute(messages.clone())` and therefore `verify_state_proof` once per key across the whole batch — performing full trie verification for every key before the transaction is even known to be includable in a block, at zero cost to the sender.
4. Repeating this submission (varying content to bypass the `provides` dedupe tag) allows sustained CPU consumption on every full node in the network, decoupled from the fixed, non-scaling `weight()` used for fee/weight accounting.

```text
## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
```
