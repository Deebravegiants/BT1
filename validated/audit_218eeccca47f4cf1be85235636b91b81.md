## Title
Duplicate-signature counting in BEEFY supermajority check allows forged consensus updates with fewer than 2/3+1 distinct signers - (File: modules/consensus/beefy/verifier/src/lib.rs)

### Summary
The CVE analog is a "check ≠ what is actually verified" bypass: goxmldsig counted/validated something different from what was cryptographically bound, letting an attacker satisfy a validity check without genuine authorization. The BEEFY consensus verifiers (both the Substrate `verify_mmr_update_proof` and the EVM `EcdsaBeefy.verifyMmrUpdateProof`) compute the supermajority participation count from the raw length of the submitted signature/vote array, not from the number of distinct authority indices actually proven to be members of the trusted authority set.

### Finding Description
In `modules/consensus/beefy/verifier/src/lib.rs`, `verify_mmr_update_proof` derives `signatures_length` directly from `mmr.signed_commitment.signatures.len()` and gates admission with `check_participation_threshold(signatures_length as u32, authority_set.len)` [1](#0-0) . Only afterward does the function recover per-signature authority addresses and check inclusion in the authority-set Merkle root via `merkle_proof.verify(..., &authority_indices, &authority_leaves, authority_set.len as usize)` [2](#0-1) . Nowhere in this path is there a de-duplication check on `authority_indices` (or on the underlying signer addresses) before the count is used to satisfy the threshold.

The identical pattern exists in the EVM ECDSA-BEEFY verifier: `sigLen = relayProof.signedCommitment.votes.length` is checked against the threshold before any authority-address recovery or Merkle-multi-proof verification [3](#0-2) .

If a relayer can submit multiple vote entries that all resolve (via `ECDSA.recover` / `secp256k1_recover`) to the same authority address/index — e.g., by attaching the same valid signature multiple times, or multiple distinct valid signatures produced by one signer over the same `commitmentHash` — the raw count `sigLen`/`signatures_length` is inflated without a corresponding increase in the number of genuinely participating (distinct) authorities. The `MerkleMultiProof`/`rs_merkle` inclusion check that follows verifies that each submitted `(index, hash)` pair is consistent with the authority-set root, but it does not by itself guarantee the *set* of indices is unique — a Merkle multi-proof over an intentionally repeated index/leaf pair can still validate correctly against the root because the index/leaf pair is genuinely a member of the tree; the proof-of-membership check does not encode "each authority may only be counted once."

This mirrors CVE-2020-15216's core defect: the code validates a claim ("N signatures are present," "these bytes are covered by a valid signature") but the quantity actually gated on (participation count) is decoupled from the identity uniqueness that the security property (2/3+1 *distinct* authorities) requires — exactly the class of "verified ≠ what is trusted" bypass in the report.

### Impact Explanation
BEEFY consensus updates gate the acceptance of new relay-chain/parachain state commitments that Hyperbridge then treats as source-of-truth for cross-chain message delivery (`EvmHost`/`HandlerV2` membership proofs, ISMP request/response handling). If the supermajority check can be satisfied by fewer than 2/3+1 distinct authorities — via signature/index replay inflating the raw count — an adversary controlling even a minority of BEEFY authority keys (or replaying leaked/observed signatures from a legitimate commitment) could push a forged MMR root and finalized parachain state into the light client. This is a state-commitment/consensus-forgery vector that would let an attacker forge message delivery or authorize unbacked state transitions across the bridge — a concrete, protocol-critical impact matching "unsound state commitment / forged message delivery."

### Likelihood Explanation
This requires the relayer submitting the consensus proof to control (or replay) signatures such that duplicate authority indices/addresses appear in the vote list while `sigLen`/`signatures_length` is only checked as a raw count. This is reachable from a single relayed proof — no privileged access needed, matching the "route reachable by relayer" requirement in the rules. Exploitability further depends on the exact behavior of the downstream `MerkleMultiProof.VerifyProof` (Solidity) / `rs_merkle::MerkleProof::verify` (Rust) implementations when given duplicate `(index, leaf)` entries in the same call — if either implementation tolerates or does not reject repeated indices (which is plausible since these libraries are designed to prove membership of a set of leaves, not enforce set uniqueness), the bypass is directly exploitable without any additional primitive.

### Recommendation
Before computing/checking the supermajority threshold, de-duplicate on authority index (and preferably on recovered signer address) in both `modules/consensus/beefy/verifier/src/lib.rs::verify_mmr_update_proof` and `evm/src/consensus/EcdsaBeefy.sol::verifyMmrUpdateProof`. Reject the proof if `authority_indices` (respectively the `vote.authorityIndex` set) contains duplicates, and only then count the deduplicated length against `check_participation_threshold` / `checkParticipationThreshold`. This mirrors the fix pattern already applied elsewhere in the codebase, e.g. the Pharos verifier's explicit `verify_validator_membership` which checks `deduped.len() != participants.len()` and returns `Error::DuplicateParticipant` [4](#0-3) .

### Proof of Concept
1. Obtain (or wait for) one legitimate BEEFY commitment signature from authority `A` at authority index `i` over `commitment_hash`.
2. Construct a `signed_commitment.signatures` (or Solidity `votes`) array of length `≥ (2/3)*N + 1` where the majority of entries are copies of the single valid `(i, signature_A)` pair (or several distinct valid signatures all recoverable to authority `i`/`A`, if reusable).
3. Submit this as the BEEFY consensus proof via `verify_consensus` / `EcdsaBeefy.verify`.
4. `check_participation_threshold(signatures_length, authority_set.len)` / `checkParticipationThreshold(sigLen, authoritySet.len)` passes because the raw array length meets the threshold, even though only one distinct authority actually signed.
5. If the subsequent `merkle_proof.verify` / `MerkleMultiProof.VerifyProof` call does not reject the duplicated `(index, leaf)` entries, the forged commitment (with attacker-chosen MMR root / parachain state) is accepted as finalized consensus state.

Note: Full confirmation that `rs_merkle::MerkleProof::verify` and `MerkleMultiProof.VerifyProof` (external `solidity-merkle-trees` and `rs_merkle` dependencies) actually accept duplicate `(index, leaf)` inputs without rejecting could not be completed within the scope of this index-based search — this is the load-bearing assumption of the finding and should be verified against those library implementations (outside this repository) before treating this as a confirmed, exploitable bug rather than a design-level gap.

/// Verify that all participating validators are members of the trusted validator set.
fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}
