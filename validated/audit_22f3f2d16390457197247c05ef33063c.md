### Title
RAY-scaled aggregate debt overflows before the index cap, permanently freezing the market - (File: common/src/rates/simulate.rs)

### Summary
`accrue_step` converts total scaled debt and supply into RAY-denominated values before applying the configured borrow-index ceiling. [1](#0-0) [2](#0-1)  When `borrowed * borrow_index / RAY` exceeds `i128::MAX`, the fixed-point multiplication panics before accrual can commit, leaving all later operations that touch the market to hit the same panic. [3](#0-2) [4](#0-3) 

### Finding Description
`scaled_to_original` delegates directly to `Ray::mul` and provides no saturation or debt-specific ceiling. [3](#0-2)  The underlying half-up multiplication returns `MathOverflow` whenever the widened quotient cannot fit back into `i128`. [5](#0-4) [6](#0-5) 

`update_borrow_index` caps only the next index after multiplying by the interest factor; it does not bound the already-existing aggregate debt value read at the start of the step. [2](#0-1)  Consequently, the absolute `MAX_BORROW_INDEX_RAY` ceiling cannot prevent overflow once `borrowed` is large enough that a much smaller live index still produces an unrepresentable debt value. [7](#0-6) 

The permissionless controller maintenance path authenticates the caller and forwards the selected markets to the pool. [8](#0-7) [9](#0-8)  The pool’s `update_indexes` owner entrypoint calls `ops::market::accrue`, which loads each market and runs `global_sync` before committing state. [10](#0-9) [11](#0-10) 

`global_sync` invokes `accrue_chunk` for every elapsed chunk, and `accrue_chunk` unconditionally executes the vulnerable `accrue_step`. [12](#0-11) [13](#0-12) 

### Impact Explanation
Once the aggregate debt valuation exceeds the `i128` domain, `update_indexes` reverts before `cache.commit()`, so `last_timestamp` remains behind the ledger timestamp and every later accrual retries the same overflowing multiplication. [11](#0-10)  Pool operations are built around a cache that is synchronized through `global_sync` before mutation. [14](#0-13)  Batched operations execute their legs through this operation framework, so withdrawals, repayments, borrows, liquidation payment/seizure legs, and other market mutations cannot bypass the failed accrual. [15](#0-14)  The result is permanent freezing of supplier funds, borrower repayment paths, liquidation, and revenue handling for that market absent a code upgrade or migration. [16](#0-15) 

### Likelihood Explanation
The trigger condition is `borrowed.raw() * borrow_index.raw() / RAY > i128::MAX`; with the configured index ceiling equal to `10^9 * RAY`, the ceiling alone does not guarantee that large books remain representable. [7](#0-6)  Reaching the condition requires an exceptionally large scaled debt book and sustained interest accrual, so this is not triggerable on a small market merely by submitting one transaction. [17](#0-16)  Nevertheless, an unprivileged caller can create the state through ordinary `supply` and `borrow` activity where caps and liquidity permit, wait for accrual, and then submit `update_indexes`; no privileged parameter change, oracle manipulation, leaked key, or external service is required at the triggering step. [18](#0-17) [19](#0-18) 

### Recommendation
Add a debt-value-aware bound before unscaling aggregate balances: for each market, cap the borrow index at `min(MAX_BORROW_INDEX_RAY, i128::MAX * RAY / borrowed)` using checked or widened arithmetic, and apply the analogous bound to aggregate supply and revenue accounting. [20](#0-19)  Alternatively, keep aggregate valuations in `I256` through accrual and define an explicit saturation policy at the `i128` token boundary, but do not use the global index ceiling as a substitute for a book-size-aware bound. [6](#0-5)  Add a regression test that grows a high-decimal, high-utilization book until the RAY debt value reaches the `i128` boundary and proves that `update_indexes`, `repay`, `withdraw`, and liquidation remain executable. [14](#0-13) 

### Proof of Concept
Assume a listed debt market `D`, a collateral market `C`, and parameters whose caps permit the position below.

```text
attacker = one unprivileged address

liquidity_account = controller.supply(
    caller = attacker,
    account_id = 0,
    spoke_id = S,
    assets = [(D, enough_liquidity)]
)

borrower_account = controller.supply(
    caller = attacker,
    account_id = 0,
    spoke_id = S,
    assets = [(C, enough_collateral)]
)

controller.borrow(
    caller = attacker,
    account_id = borrower_account,
    borrows = [(D, large_debt)],
    to = None
)

// Allow ledger time to advance until:
// borrowed_scaled(D) * borrow_index(D) / RAY > i128::MAX.

controller.update_indexes(
    caller = attacker,
    assets = [HubAssetKey { hub_id: H, asset: D }]
)
// Reverts with MathOverflow before committing accrual.
```

The triggering call reaches the public controller maintenance function, forwards to pool `update_indexes`, and panics in the first `scaled_to_original` aggregate-debt conversion. [19](#0-18) [11](#0-10) [21](#0-20) 

Subsequent calls such as `withdraw` on the liquidity account, `repay` on the borrower account, or `liquidate` enter pool operation paths that first synchronize the market and therefore revert on the same multiplication. [14](#0-13) [22](#0-21)  Because the failed accrual never advances `last_timestamp`, the condition is persistent rather than a one-transaction failure. [23](#0-22)
