### Title
Emporium's `signerAddress == address(0)` stateless-op path lets any unprivileged attacker force `EmporiumUpgradeable` to execute arbitrary calls (e.g. drain any ERC20 allowance granted to the Emporium contract) - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.verifyWallet` skips all signature/authorization checks whenever `stack.signerAddress == address(0)`, and `runAction`'s "Case 2: Stateless Interaction" branch then executes `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract's own context with fully attacker-controlled `endpoint`/`callData`. Because the `MainEVMCircuitMin` circuit used for this path requires no real UTXOs, nullifiers, or ownership proof (it only checks `message == Poseidon(messageSeed)` for an attacker-chosen `messageSeed`/`emporiumMessage`), any unprivileged EOA can drive `msg.sender == address(Emporium)` to call any contract, including calling `transferFrom` on any ERC20 for which some third party has ever approved the Emporium contract address.

### Finding Description
The intended invariant is: *the party whose assets are moved or whose allowance is spent by an Emporium op must be the party who cryptographically authorized that specific op* (AUTHORITY). This is broken.

Trace:
- `EmporiumUpgradeable.runAction` decodes an attacker-supplied `EmporiumStack` from `circomData.externalActionData.externalActionMetadata` and calls `verifyWallet(stack, circomData)`: [1](#0-0) 
- `verifyWallet` only records `usedMessages[circomData.emporiumMessage] = true` and returns immediately with no signature check at all when `stack.signerAddress == address(0)`: [2](#0-1) 
- For each op, since `stack.signerAddress == address(0)`, CASE 2 executes `op.endpoint.call{value: op.value}(op.callData)` directly in Emporium's own context (only `callHinkalWallet`/`doSendToRelay` selectors are blocked): [3](#0-2)  This means `msg.sender` seen by `op.endpoint` is `address(Emporium)`, and both `endpoint` and `callData` are 100% attacker-chosen.
- `Hinkal._externalTransact` invokes `runAction` as a plain external call (not delegatecall), preserving this context: [4](#0-3) 
- Critically, when `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputEmporiumMin` reduces the circuit's public input to just `[emporiumMessage, timeStamp, calldataHash]`: [5](#0-4)  and `MainEVMCircuitMin` only constrains `message <== Poseidon(1)([messageSeed])`: [6](#0-5) . This means the attacker can pick an arbitrary `messageSeed`, compute the corresponding `emporiumMessage = Poseidon(messageSeed)` off-chain, and trivially produce a valid Groth16 proof, with zero UTXOs, nullifiers, or real balance required (`dimensionsCheck` is satisfied with all-empty arrays: `tokenNumber=0`, `nullifierAmount=0`, `outputAmount=0`): [7](#0-6) .
- Because `circomData.erc20TokenAddresses.length == 0`, the balance-based checks in both `runAction` and `Hinkal.transact` never execute (their loops iterate zero times), so a `transferFrom` that moves tokens directly from an arbitrary victim to the attacker (bypassing Emporium's own balance entirely) triggers none of the guard checks (`BalanceChangeShouldBePositive`, slippage checks).

Root cause: the "stateless" branch conflates "no wallet needed" with "no authorization needed." There is no binding between `circomData.originalSender`/the attacker's own identity and the specific `endpoint`/`callData` being executed; any address that has ever approved the Emporium contract (for any legitimate reason, complete or partial use) can have that allowance drained by an unrelated party.

### Impact Explanation
Direct theft of third-party ERC20 tokens via any stale/leftover `allowance(victim, Emporium)`, executed with zero cost beyond gas and a trivially-generated proof (no real UTXOs needed). This is repeatable against every address/token pair with a nonzero allowance to the Emporium contract, and more broadly the Emporium contract can be forced to make arbitrary external calls as `msg.sender == Emporium`, which is a critical break of the AUTHORITY invariant — matching "Critical – direct theft of shielded or in-flight user funds" / execution of calls a wallet owner never authorized.

### Likelihood Explanation
Preconditions: some address must have granted `allowance(victim, address(Emporium))` greater than what was consumed (a common pattern for the intended legitimate flow of depositing ERC20 into Emporium via the stateless path). Attacker cost is minimal: crafting `CircomData`/`EmporiumStack` fields and generating one Groth16 proof for the trivial `MainEVMCircuitMin` circuit — both explicitly within the modeled attacker's capabilities (deposit their own funds is not even required here). This is fully repeatable for every outstanding allowance to the Emporium address.

### Recommendation
Do not allow arbitrary, unauthenticated external calls in the `signerAddress == address(0)` branch. Either: (1) require `verifyWallet` to bind `circomData.originalSender == msg.sender-equivalent authorizer` for stateless ops and restrict `op.endpoint`/`op.callData` to a strictly allow-listed set of safe operations (e.g., only pulling exactly the funds the same transaction is depositing, matching `deltaAmountChanges`), or (2) require a valid EIP-712 signature from `circomData.originalSender` covering the exact `ops` even when no `IHinkalWallet` is used, so no third party's pre-existing allowance can ever be spent by an unrelated caller's crafted calldata.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (registered as external action `HINKAL_EMPORIUM_ACTION_ID`), and a mock ERC20.
2. Simulate the "legitimate" prior flow: a `victim` address calls `token.approve(address(emporium), 1000e18)` directly (representing leftover/partial-use approval).
3. As an unrelated `attacker` EOA, build `CircomData` with `erc20TokenAddresses = []`, `dimensions.tokenNumber = 0`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: address(token), invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transferFrom.selector, victim, attacker, 1000e18)})], ...}))`.
4. Compute `emporiumMessage = Poseidon(messageSeed)` for an attacker-chosen `messageSeed`, generate a valid Groth16 proof for `MainEVMCircuitMin` locally (snarkjs), set `calldataHash` accordingly.
5. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from `attacker`.
6. Assert equality violated: before, `token.allowance(victim, address(emporium)) == 1000e18` and `token.balanceOf(attacker) == 0`; after the call, `token.balanceOf(attacker) == 1000e18` and `token.allowance(victim, address(emporium)) == 0`, with no signature from `victim` and no proof of `victim`'s UTXOs ever supplied — i.e., AUTHORITY(`from == victim`, authorized-by == victim) is false while the transfer still executed.
