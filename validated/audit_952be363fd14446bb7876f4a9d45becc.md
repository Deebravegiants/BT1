Audit Report

## Title
Incomplete origin/hostname validation in Gateway `isAllowedOrigin` wildcard matching allows CORS bypass via unanchored suffix comparison - (File: core/services/gateway/network/httpserver.go)

## Summary
The Chainlink Gateway's `httpServer.isAllowedOrigin` validates the `Origin` header against `CORSAllowedOrigins` before reflecting it into `Access-Control-Allow-Origin`. Its wildcard branch strips the `*.` prefix from a configured pattern (e.g. `*.mycompany.com` → `mycompany.com`) and then performs `strings.HasSuffix(originHost, allowedHost)` with no domain-label boundary check, so a hostname like `evilmycompany.com` incorrectly satisfies the "subdomain of mycompany.com" check.

## Finding Description
`isAllowedOrigin` splits both the request `Origin` and each configured allowed origin into scheme/host/port via `splitURL`, then for wildcard entries (`strings.HasPrefix(allowedHost, "*.")`) strips the `*.` and checks `strings.HasSuffix(originHost, allowedHost)` [1](#0-0) . Because `HasSuffix` is a raw character-tail comparison, it does not require a `.` immediately before the matched suffix, so `originHost = "evilmycompany.com"` passes against `allowedHost = "mycompany.com"` exactly like the intended `foo.mycompany.com` would. `handleRequest` calls this function on every request when `CORSEnabled` is set and, if it returns true, sets `Access-Control-Allow-Origin` to the raw, attacker-controlled `Origin` header value [2](#0-1) . There is no other origin/domain-boundary validation elsewhere in the file; the only checks performed are scheme match, port match, exact host match, and this flawed wildcard suffix match [4](#0-3) .

## Impact Explanation
When exploited, the Gateway grants CORS access to an attacker-controlled origin that was never intended to be allowlisted, letting attacker JavaScript running in a victim's browser read cross-origin JSON-RPC responses from Gateway handlers (WebAPI/Capabilities-v2, Vault, Confidential Relay) that the browser would otherwise block. This maps to the in-scope "cross-user response corruption / unauthorized cross-origin data disclosure" impact class via a CORS/allowlist-boundary bypass (CWE-1385 style), analogous in root cause to the cited Bokeh `match_host` CVE.

## Likelihood Explanation
Exploitability requires an operator to configure a wildcard entry in `CORSAllowedOrigins`, which is a supported and documented usage pattern for the Gateway (as evidenced by the corresponding test in `httpserver_test.go`). Given such a configuration, any unprivileged external attacker can register a domain string that merely ends with the allowed suffix (e.g., `evilmycompany.com` for `*.mycompany.com`) with no elevated privileges, network position, or credentials — only requiring a victim (a legitimate user of the Gateway-fronted service) to visit the attacker's page, consistent with the standard CORS/CSWSH exploitation model.

## Recommendation
Anchor the wildcard match to a domain-label boundary instead of a raw suffix, e.g., compare against the suffix including the leading dot (`".mycompany.com"`) and require `strings.HasSuffix(originHost, suffix)` while also allowing exact equality only via the already-present exact-match branch — ensuring `evilmycompany.com` no longer satisfies `*.mycompany.com`.

## Proof of Concept
1. Configure `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.mycompany.com"]`.
2. Send `OPTIONS`/`POST` to the Gateway HTTP endpoint with header `Origin: https://evilmycompany.com`.
3. Observe the response includes `Access-Control-Allow-Origin: https://evilmycompany.com`, proving `isAllowedOrigin` incorrectly returned `true`.
4. Add a Go unit test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go`, but asserting that origin `https://evilmycompany.com` against allowlist `https://*.mycompany.com` is rejected (currently it is accepted) — this test would fail against current code, confirming the bug.

func (s *httpServer) isAllowedOrigin(origin string) bool {
	originScheme, originHost, originPort, err := s.splitURL(origin)
	if err != nil {
		s.lggr.Debug("error parsing origin URL", err)
		return false
	}
	for _, allowed := range s.config.CORSAllowedOrigins {
		// probably better to do this once when server starts and store it in a map
		// this is an easier solution so we don't have to apply more changes to the code
		// just need to be careful when specifying allowed origins in the config file
		allowedScheme, allowedHost, allowedPort, err := s.splitURL(allowed)
		if err != nil {
			s.lggr.Debug("error parsing allowed origin URL", err)
			continue
		}
		// skip if the scheme doesn't match at all
		if originScheme != allowedScheme {
			continue
		}
		// skip if the port doesn't match at all
		if originPort != allowedPort {
			continue
		}
		// check for exact host match (e.g., remix.com)
		if originHost == allowedHost {
			return true
		}
		// check for wildcard host match (e.g., *.remix.com)
		if strings.HasPrefix(allowedHost, "*.") {
			allowedHost = allowedHost[2:]
			if strings.HasSuffix(originHost, allowedHost) {
				return true
			}
		}
	}
	return false
}
