### Title
Unescaped health-check output/name injected into HTML response - (File: core/web/health_controller.go)

### Summary
The `/health` endpoint's HTML renderer builds its output by directly interpolating check `Name`, `Status`, and `Output` fields into raw HTML via `fmt.Fprintf`, with no HTML-escaping. This mirrors the CVE-2021-35502 root cause: an index/detail view template that concatenates backend field values into HTML without sanitization, enabling injected markup/script to execute in the viewer's browser.

### Finding Description
`checkTree.writeHTMLTo` in `core/web/health_controller.go` writes each check's `Name` and `Output` straight into an HTML `<summary title="%s">`/`<pre>%s</pre>` fragment: [1](#0-0) 

These values originate from `HealthReport()` implementations across the codebase (job/service names, and `err.Error()` strings), which are then wrapped into `presenters.Check{Name: name, Output: output}` and passed unmodified into the HTML writer when the client requests `Accept: text/html`: [2](#0-1) 

Because `err.Error()` values can be built from data such as job names, bridge names, external initiator URLs, or other operator-configured/dynamic identifiers (e.g., `js.lggr.Errorw("Couldn't start job", "jobID", jb.ID, "jobName", jb.Name.ValueOrZero(), "err", err)` shows job names propagating into health/error state [3](#0-2) ), any HTML metacharacters in these strings are rendered verbatim in the resulting HTML document — a classic unsanitized-output pattern.

### Impact Explanation
If an attacker (an authenticated low-privileged API user, or any actor able to influence a job name, bridge name, or other identifier that gets embedded into a `HealthReport()` error string) can supply `<script>`/`<img onerror=...>` payloads into such identifiers, and an operator subsequently views `/health` in a browser with `Accept: text/html`, the injected markup executes in the context of the Operator UI session — enabling session/cookie theft, CSRF-token exfiltration, or UI-redressing against the node administrator. This is a stored/reflected XSS in an internet/operator-facing surface, directly analogous to the MISP `generic_field.ctp` finding.

### Likelihood Explanation
Exploitability depends on whether any user-influenceable string (job name, bridge name, chain/relayer identifier, etc.) can end up unsanitized inside a `HealthReport()` map value and whether the operator ever requests the HTML variant of `/health` (this requires setting an `Accept: text/html` header — browsers don't do this by default for JSON APInormally, but a crafted link or the endpoint being directly browsed to would trigger it). The `/health` route's exact auth requirements were not confirmed within the available index (whether it sits behind `requiresAuth` middleware in `router.go`), so likelihood cannot be pinned down with certainty from what was retrieved — this should be verified in the actual router configuration.

### Recommendation
HTML-escape all dynamic values (`Name`, `Status`, `Output`) before interpolating them into `checkTree.writeHTMLTo`, e.g., using `html.EscapeString` or `template/html` auto-escaping (`html/template` instead of raw `fmt.Fprintf` + `io.WriteString`) for the `<summary title="...">` and `<pre>...</pre>` fragments.

### Proof of Concept
1. Cause a health check to fail with an error message containing HTML, e.g. via a job/service name containing `"><script>alert(document.cookie)</script>` (if job name or other value propagates unescaped into a `HealthReport()` error, per `core/services/job/spawner.go:159-163`).
2. Request `GET /health` with `Accept: text/html`.
3. Observe the injected `<script>` tag rendered verbatim inside `<pre>` in the returned HTML (per `core/web/health_controller.go:254-261`), executing in the viewing browser's context.

*Note: full confirmation that a specific user-controlled field flows unescaped into a `HealthReport()` error string, and confirmation of `/health`'s authentication requirement in `core/web/router.go`, could not be completed within the available search results — a Devin session with full repo access would be needed to trace every `HealthReport()` implementation and the router's auth middleware chain to fully validate exploitability.*
