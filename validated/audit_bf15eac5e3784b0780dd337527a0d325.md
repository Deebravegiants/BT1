This confirms the root cause: `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) validates the HMAC via `Utils::HmacValidator.validate(request)`, but the HMAC signable string (`Request#to_signable_string`, `lib/shopify_api/webhooks/request.rb:36-38`) is `@raw_body` only — it never includes the `shop` value. Yet `Registry.process` trusts `request.shop` (parsed from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header, `lib/shopify_api/webhooks/request.rb:20-23`) and forwards it straight into `WebhookMetadata` for the app's handler to act on.

### Title
Webhook `shop` identity is not bound by the HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic once `Utils::HmacValidator.validate(request)` passes, but that HMAC only covers the raw request body — not the `shop` (tenant) identifier. Because the `shop` field is read straight from an unauthenticated header and passed unchanged into `WebhookMetadata`, an attacker who can obtain any one valid `(body, hmac)` pair signed with the app's `api_secret_key` can replay it with a different `shop-domain` header and have the app process it as if it came from an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . `Utils::HmacValidator.validate_signature` computes/compares the HMAC exclusively against that signable string: [2](#0-1) . Meanwhile `Request#shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the HMAC: [3](#0-2) .

`Registry.process` performs exactly one check — HMAC validity of the body — and then unconditionally forwards `request.shop` into the `WebhookMetadata` object handed to the app's registered handler: [4](#0-3) . The handler (per the documented contract) is expected to act on `data.shop` as the authoritative tenant identifier, e.g. loading a stored session/access token for that shop and performing merchant-side actions: [5](#0-4)  and as illustrated in the docs (`docs/usage/webhooks.md:24-26`, `BREAKING_CHANGES_FOR_V15.md:118-121`).

This breaks the intended identity binding:
`shop the app authenticates the webhook for` ≠ `shop the HMAC actually authenticates`.

Concretely, the HMAC proves "this body was signed by someone holding `api_secret_key`" — it says nothing about which shop the body belongs to. Any legitimately obtained webhook (e.g., one delivered to the attacker's own installed/trial shop, which is a normal unprivileged action) yields a `(raw_body, hmac)` pair that remains valid under `HmacValidator.validate` no matter what `shop-domain` header value is substituted, because that header is outside the signed content.

### Impact Explanation
This is a cross-tenant boundary crossing: an attacker who controls only their own (unprivileged) shop installation of the app can forge webhook deliveries that the app's `Registry.process` accepts as authentic for a different, victim shop. Any app whose handler logic keys off `data.shop` to fetch the victim's session/access token or to mutate victim-shop state (the pattern the gem's own documentation recommends) can be tricked into performing actions attributed to, or affecting, a shop the attacker does not control — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is Low-to-Medium: the attacker needs at least one legitimately-signed `(body, hmac)` pair for the target app (trivially obtainable by installing the same app on their own store and capturing a real webhook), plus the ability to POST to the app's known webhook endpoint with a modified `shop-domain` header. No secret material or privileged access is required — only knowledge of the app's public webhook URL and one observed webhook delivery.

### Recommendation
Bind the tenant identity into the authenticated signal. Options: fold the `shop` header (and other trust-sensitive headers like `topic`/`webhook-id`) into the HMAC signable string when verifying (mirroring Shopify's actual header set if supported), or, at minimum, have the app's integration cross-check `request.shop` against an existing, previously-verified session/installation record before invoking the handler, rather than trusting the header value on its own. Document clearly in `docs/usage/webhooks.md` that `data.shop` is not itself cryptographically authenticated and must be cross-validated against known installed shops.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` (a normal, unprivileged action) and triggers a webhook (e.g. `orders/create`), capturing the raw POST: body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC over `B` with the app's `api_secret_key`, per `lib/shopify_api/utils/hmac_validator.rb`).
2. Attacker resends this exact POST to the same app endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but replacing `x-shopify-shop-domain: attacker.myshopify.com` with `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, including the forged `shop` (`lib/shopify_api/webhooks/request.rb:20-23`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because the HMAC only covers `B` (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/webhooks/request.rb:36-38`).
5. `Registry.process` builds `WebhookMetadata.new(..., shop: "victim.myshopify.com", ...)` and invokes the app's handler, which now processes attacker-controlled data believing it originates from `victim.myshopify.com` (`lib/shopify_api/webhooks/registry.rb:198-199`).
