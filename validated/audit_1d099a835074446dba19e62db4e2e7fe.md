### Title
Bad-debt supply-index write-down clamps to `SUPPLY_INDEX_FLOOR_RAW` instead of zeroing shares, leaving wiped-out suppliers a phantom claim that drains fresh deposits - (File: contracts/pool/src/interest.rs)

### Summary
The bug-class analog of CVE-2024-41311 (insufficient bounds checking on attacker-influenced values producing out-of-bounds state) maps onto the pool's bad-debt write-down path: when a bad-debt write-down exceeds what the supply side can absorb, `apply_bad_debt_to_supply_index` does not zero the supply index and the share count together — it clamps `supply_index` up to `SUPPLY_INDEX_FLOOR_RAW` (`RAY / 1000`) while leaving `supplied` shares intact. The clamped index is still positive, so every pre-wipeout share retains a phantom redeemable claim with no backing cash. The next deposit into the market mints correctly-priced shares, but the stranded wiped-out holder can withdraw real tokens against the clamped index, directly stealing the fresh deposit and leaving the pool insolvent.

### Finding Description
`apply_bad_debt_to_supply_index` in `contracts/pool/src/interest.rs` computes the supply-index haircut for `clean_bad_debt`/post-liquidation bad-debt cleanup. Instead of treating an over-100% write-down as a total wipeout (index → 0 or shares → 0), it saturates the index at `SUPPLY_INDEX_FLOOR_RAW`. The pool's own test demonstrates the consequence (`contracts/pool/tests/interest.rs:372-427`): [1](#0-0) 

- After `apply_bad_debt_to_supply_index(&mut cache, 5_000 * RAY)` against `1_000 * RAY` of scaled supply, `supply_index` is clamped UP to `SUPPLY_INDEX_FLOOR_RAW` rather than zeroing the position set (`contracts/pool/tests/interest.rs:389-394`).
- `cache.unscale_supply_floor(old_scaled)` still returns a positive claim (`stranded > 0`) while `cache.cash() == 0` — the invariant violation is only masked by `require_reserves` at withdraw time, not prevented (`contracts/pool/tests/interest.rs:395-401`).
- A fresh deposit of `stranded` tokens mints `fresh_scaled` shares at the clamped index; the wiped-out holder then resolves `WITHDRAW_ALL` to `gross == fresh_cash`, and `require_reserves` passes because the cash exists — the withdrawal pays out exactly the fresh deposit, after which `cache.cash() < fresh_claim` and the new supplier's claim is unbacked (`contracts/pool/tests/interest.rs:414-426`).

The insufficient-checks analog is exact: the write-down path fails to bound the haircut against the position set it applies to, and the floor clamp manufactures a claim (the "out-of-bounds write" analog) on state that should have been zeroed. Index validation constants `SUPPLY_INDEX_FLOOR_RAW`, `MIN/MAX_ASSET_DECIMALS`, and index bounds live in `common/src/constants` and are exercised by the pool cache in `contracts/pool/src/cache/scale.rs` (`unscale_supply_floor`, `resolve_withdrawal`), which happily converts the phantom shares back into asset units.

### Impact Explanation
Theft of user funds and protocol insolvency. Any holder of supply shares stranded by a clamped wipeout can submit a normal `withdraw` (or the liquidation/`CloseWd` path) and receive real tokens until pool cash is exhausted. Since the phantom claim equals the wiped position's remaining value at `RAY/1000`, a large wiped position converts into a large claim that drains whatever fresh liquidity arrives. This is a direct transfer of new suppliers' principal to accounts whose collateral was already written off — the pool cannot honor the fresh supplier, i.e., market-level insolvency in that (hub, token) book.

### Likelihood Explanation
Triggering requires a bad-debt cleanup where the write-down exceeds the supply-side absorption capacity — i.e., insolvency large enough to push the index below the floor. `clean_bad_debt` and post-liquidation `execute_bad_debt_cleanup` are reachable by an unprivileged address once an account is deeply insolvent (dust-threshold/socializable bad debt per `is_socializable_bad_debt` in `contracts/controller/src/positions/liquidation/curve.rs` and `check_bad_debt_after_liquidation` in `contracts/controller/src/positions/liquidation/apply.rs:301-316`). An attacker can manufacture the condition by holding a supply position and engineering maximal bad debt (e.g., borrow, let price move past bands, or use `update_account_threshold` restamping), then calling the cleanup so the clamp fires — no privileged role is needed for either step. Caveat: the demonstration in the repo drives the cache directly rather than through the public entrypoint, so the precise market state needed to push `supply_index` to the floor via the controller path should be confirmed, but the cleanup path is documented as unprivileged and the pool-side defect is unconditional once reached.

### Recommendation
Treat a write-down that would push `supply_index` to/below `SUPPLY_INDEX_FLOOR_RAW` as a full wipeout: explicitly zero the index (or burn/zero `supplied` shares) and emit the wiped position state instead of clamping the index upward. At minimum, bound the haircut by the actual claim set — `new_index = max(computed_index, floor)` is only sound if shares are simultaneously rescaled so `supplied * new_index` never exceeds post-write-down backing. Alternatively, route full-wipeout cases through `recapitalize`-style settlement that reconstructs the market without preserving stale claims, and add an invariant assertion that `unscale_supply_floor(supplied) <= cash + debt` after every bad-debt application.

### Proof of Concept
The repository already contains the executable proof. In `contracts/pool/tests/interest.rs`, `test_raw_cache_floor_clamp_strands_claim_without_supply_guard`:

1. Seed a market with `supplied = 1_000 * RAY` scaled shares, `supply_index = RAY`, `cash = 0` (post-wipeout state reachable via the bad-debt cleanup path).
2. Call `apply_bad_debt_to_supply_index(&mut cache, Ray::from(5_000 * RAY))` — a write-down five times the supply side.
3. Observe `cache.supply_index() == SUPPLY_INDEX_FLOOR_RAW` while `cache.unscale_supply_floor(old_scaled) > 0` — the stranded phantom claim.
4. A fresh supplier deposits `stranded` tokens; `mint_supply` + `credit_cash` give them a correct claim.
5. The wiped-out holder calls `resolve_withdrawal(i128::MAX, old_scaled)`; `require_reserves(gross)` passes because the fresh cash is present; `debit_cash(gross)` pays the full fresh deposit to the wiped holder.
6. Result: `cache.cash() < fresh_claim` — the fresh supplier's claim is unbacked; funds are stolen.

This mirrors CVE-2024-41311's shape: a missing bound check on a derived offset/index lets a forged (here, clamped) state claim memory/value outside the legitimate region — here, claims against cash belonging to a different depositor.
