### Title
Webhook HMAC only covers the raw body, not the `shop-domain` header used for tenant identification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC verified by `Registry.process` proves nothing about the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id` headers. `Registry.process` passes `request.shop` (read straight from the unauthenticated header) into `WebhookMetadata`, which host apps use as the tenant key for the event. This breaks the identity binding "shop authenticated == shop the event is attributed to."

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
only the body bytes are signed. `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled from HTTP headers that are not part of that signable string: [2](#0-1) 
`Registry.process` verifies the HMAC and, once it passes, unconditionally trusts `request.shop`/`request.topic` to build the metadata object handed to the app's handler: [3](#0-2) 
`HmacValidator.validate` only recomputes the signature over `to_signable_string` (i.e. the raw body) and compares it to the `hmac` accessor, again never touching the headers: [4](#0-3) 

Because the signature never covers `shop-domain`/`topic`/`webhook-id`, a party that has received one legitimate webhook (with a valid body+HMAC pair, e.g. for their own store) can replay the exact same body and HMAC to the app's webhook endpoint while substituting a different `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen shop domain. The documented usage pattern in `docs/usage/webhooks.md` explicitly instructs apps to trust `data.shop` from the processed request, with no guidance to independently verify it: [5](#0-4) 

This is the same class of bug as the audit finding: a check (HMAC validity) is treated as if it establishes a stronger guarantee (correct tenant attribution) than it actually does, because a field that is acted upon (`shop`) is not covered by the verification (HMAC over body only).

### Impact Explanation
This allows cross-tenant confusion/spoofing: a request with a genuinely valid HMAC (obtained from a legitimate webhook delivery for shop A) can be replayed with the shop-domain header changed to shop B. If the host application uses `data.shop` from `WebhookMetadata` as the tenant key to look up sessions, apply mutations, or attribute mandatory GDPR events (`shop/redact`, `customers/redact`, `customers/data_request`) without an independent check that the domain actually installed the app or matches an expected allowlist, an attacker can cause the app to process another shop's data/actions or misattribute events across tenants — a cross-tenant access/integrity issue.

### Likelihood Explanation
Exploitation requires the attacker to already possess at least one valid (body, HMAC) pair, which in practice they can obtain by installing the app on their own store and receiving any real webhook. No `api_secret_key`, access token, or privileged credential is needed beyond that — replaying the header change is a simple unauthenticated HTTP POST. However, exploitation impact depends on how the host app trusts `data.shop`; apps that additionally verify the shop against a known/installed-shop list before acting are unaffected. This is a design gap in the gem's verification surface, not solely a host-app misuse, since the gem provides no header-binding and its own docs guide developers to trust `data.shop` directly.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) in the signable string used for HMAC verification, or otherwise cryptographically bind these header values to the request before they are handed to `WebhookMetadata`. At minimum, document prominently that `data.shop`, `data.topic`, and `data.webhook_id` are unauthenticated and must be independently validated by the host app (e.g., checked against a shop that is known to have the app installed) before being used for any tenant-scoped action.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`. Shopify delivers a legitimate webhook:
   - Body: `{"id":1,...}`
   - Headers: `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`
2. Attacker captures this exact `(raw_body, hmac)` pair.
3. Attacker POSTs the same `raw_body` and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds `shop == "victim-shop.myshopify.com"`.
5. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (the unchanged raw body) and succeeds, since the signature was never a function of the shop header.
6. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...))` is invoked; the host app processes the event as if it originated from `victim-shop.myshopify.com`, despite the payload actually belonging to the attacker's own shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
