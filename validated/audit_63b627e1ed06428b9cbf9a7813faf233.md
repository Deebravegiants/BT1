## Title
Webhook `shop` identity not covered by HMAC allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`, `topic`, `webhook_id`, `api_version`) from unauthenticated HTTP headers, while its HMAC signature (`to_signable_string`) covers only the raw request body. `Webhooks::Registry.process` validates the HMAC and then trusts `request.shop` as the tenant identity handed to the app's handler, without that value ever being part of the signed data.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from attacker-controllable headers: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` (the body only) and `request.hmac` — never `request.shop`. After that check passes, it forwards the unauthenticated `request.shop` value straight into the handler as the tenant identity: [3](#0-2) 

`HmacValidator.validate` and `compute_signature` only ever hash `verifiable_query.to_signable_string`, confirming the shop header plays no role in the signature: [4](#0-3) 

**Broken identity binding (equality that should hold but doesn't):**
`shop_that_produced_the_valid_HMAC(raw_body)` == `shop_header_value_trusted_by_handler(request.shop)`

Because the HMAC is computed over `raw_body` alone, an unprivileged user who legitimately operates their own Shopify store (or otherwise obtains one genuine `(raw_body, hmac)` pair signed with the app's real `api_secret_key` — e.g. by installing the app on a dev store they control) can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds (body/HMAC unchanged), and `Registry.process` calls the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` attributing the (attacker-controlled) body content to the victim shop.

### Impact Explanation
This breaks the tenant/shop identity boundary that host applications rely on `ShopifyAPI::Webhooks` to enforce — the whole reason apps consult `data.shop` is to know which merchant's data/session the payload belongs to. Depending on how the host app uses `data.shop` (e.g., looking up/updating that shop's stored session, processing `app/uninstalled`, `shop/redact`, `customers/data_request`, or order/product state keyed by shop), an attacker can inject data or trigger actions attributed to a shop they do not own — a cross-tenant access vector, which maps to the "Critical: cross-tenant access" impact bucket defined in scope.

### Likelihood Explanation
The attack is straightforward for anyone who can obtain one legitimately-signed webhook payload from the app (installing the target app on a shop they control, or capturing one), since headers other than the body are not authenticated at all. No access to `api_secret_key`, access tokens, or privileged accounts is required — only observation/capture of one genuine webhook delivery and the ability to POST to the app's public webhook endpoint with a modified `shop-domain` header.

### Recommendation
Bind the shop/topic identity into the signed material, or otherwise cryptographically bind the header values to the payload before trusting `request.shop`. At minimum, `Webhooks::Registry.process` (or `Request`) should verify that the shop domain claimed in the header matches an expectation the host app can validate (e.g., cross-check against a previously known/authorized shop for this webhook subscription), rather than passing the raw header value straight through as trusted identity after only a body-only HMAC check.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they control) and triggers a webhook topic the app subscribes to (e.g., `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header — both computed by Shopify using the app's real `api_secret_key`.
2. Attacker resends that exact `(raw_body, hmac)` pair to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which hashes `request.to_signable_string` (== `raw_body`, unchanged) — validation succeeds.
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled parsed body>, ...)`, and the host app processes attacker-supplied data as though it came from `victim-shop.myshopify.com`.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(signable_string: String, secret: String).returns(String) }
        def compute_signature(signable_string, secret)
          OpenSSL::HMAC.hexdigest(
            OpenSSL::Digest.new("sha256"),
            secret,
            signable_string,
          )
        end
