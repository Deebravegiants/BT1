## Analog Found

### Title
Zap trusts BounceTech LT's unverified `mint()`/`redeem()` return values for downstream accounting instead of measuring real balance deltas - ([File: packages/contracts/src/Zap.sol])

### Summary
`Zap._executeBuy` and `Zap._sellInternal` trust the raw return value of the external `IBounceLeveragedToken.mint()` / `.redeem()` calls (`ltMinted`, `grossUsdc`) as ground truth for how many LT/USDC units were actually produced, and propagate those numbers directly into curve trade sizing, fee computation, refunds, and the amount transferred to the user — without ever cross-checking against the actual token balance change on `Zap`. This is the same bug class as the reported ERC4626 issue: trusting a vault-like external contract's function return value instead of verifying the real output via `balanceOf`.

### Finding Description
In `_executeBuy` [1](#0-0) , `ltMinted` comes straight from `IBounceLeveragedToken(lt).mint(address(this), baseToConvert, 0)`'s return value and is used as-is to size the subsequent curve buy (`_buyOnCurve(tokenAddress, lt, ltMinted)`) or the post-graduation HyperSwap swap (`_buyOnUniswapV2(tokenAddress, lt, ltMinted)`), and later to compute `ltExcess = ltMinted - amountInUsed` which is transferred back to the caller [2](#0-1) , and to compute the pro-rated fee via `effectiveBaseSpent = (amountInUsed * baseToConvert) / ltMinted` [3](#0-2) .

Symmetrically, in `_sellInternal`, `grossUsdc = IBounceLeveragedToken(lt).redeem(address(this), ltReceived, 0)` is trusted directly to compute the fee and the `usdcOut` transferred to the seller [4](#0-3) .

The `IBounceLeveragedToken` interface itself documents `mint`/`redeem` as returning `ltAmount` / `baseAmount` respectively [5](#0-4) , but nothing in `Zap` verifies that `IERC20(lt).balanceOf(address(this))` or `IERC20(usdc).balanceOf(address(this))` actually increased by the reported amount. If BounceTech's LT ever behaves like the vaults described in the external report — returning a value that doesn't match the real balance change (e.g. due to a rounding discrepancy, a fee-on-transfer quirk, a streaming-fee checkpoint interacting with mint/redeem, or any future LT upgrade that changes accounting) — Zap will use the wrong figure for: how much LT to route into the curve/AMM, how much fee to charge, how much LT/USDC excess to refund, and how much USDC to pay out to the seller.

This mirrors the report's exact recommendation gap: "fetch the real output directly from the ... balance ... for extra security," which is not done anywhere in `_executeBuy` / `_sellInternal`.

### Impact Explanation
If `mint()`'s reported `ltAmount` exceeds the real LT balance increase, `Zap` will attempt to forward more LT into the curve/AMM or refund more LT to the buyer than it actually holds, reverting on the terminal transfer/approve step (denial of service on buys) or, if the shortfall is absorbed elsewhere, silently under/over-crediting the fee split feeding `FeeVault`. If `redeem()`'s reported `baseAmount` exceeds the real USDC received, `Zap.usdc.safeTransfer(msg.sender, usdcOut)` in `_sellInternal` [6](#0-5)  pays the seller out of USDC that was deposited by other buyers/sellers, draining the shared `Zap` USDC float and ultimately causing insolvency for later sellers — direct fund loss for other unrelated users of the protocol, satisfying the "theft or permanent freezing of trader funds" bar.

### Likelihood Explanation
Likelihood depends entirely on whether BounceTech's live LT ever violates the assumed invariant that its `mint`/`redeem` return values equal the real balance delta. The protocol's own comments show it already treats the LT as an external, only-partially-trusted dependency (mint-pausable, rate view can be stale, LT can be "retired") [7](#0-6) , showing the authors are aware BounceTech's behavior can deviate from naive expectations, but there is no defensive check anywhere against a return-value/balance mismatch specifically. This is a lower-likelihood, dependency-triggered class (medium) rather than one an unprivileged trader can directly force today, since BounceTech's LT is assumed honest; but it is a real gap that a misbehaving or upgraded LT (or a subtle existing accounting edge case, e.g. streaming-fee interaction with mint/redeem) could trigger without any protocol-side mitigation.

### Recommendation
In `_executeBuy`, snapshot `IERC20(lt).balanceOf(address(this))` before and after `mint()` and use the actual delta as `ltMinted` rather than the raw return value; likewise in `_sellInternal`, snapshot `$.usdc.balanceOf(address(this))` before and after `redeem()` and use the delta as `grossUsdc`. Optionally add a sanity `require` that the reported return value matches the measured delta, reverting otherwise, consistent with the external report's recommendation.

### Proof of Concept
A fully worked PoC requires a BounceTech LT deployment (or malicious/buggy mock) whose `mint`/`redeem` return value diverges from its actual `transfer`/`_mint` balance effect — e.g. a mock that returns `ltAmount * 2` from `mint()` while only minting `ltAmount` real LT tokens to `Zap`. With such a mock:
1. Call `Zap.buy` with any valid USDC amount.
2. `_executeBuy` calls `mint()`, receives the inflated `ltMinted` return value.
3. `_buyOnCurve`/`_buyOnUniswapV2` is sized using the inflated `ltMinted`, and the "excess" refund logic (`ltExcess = ltMinted - amountInUsed`) attempts to transfer more LT than `Zap` actually holds, reverting the transaction (DoS) — or, in a redeem-side variant, `_sellInternal`'s `usdcOut = grossUsdc - fee` pays the seller more USDC than was actually redeemed from the LT, draining `Zap`'s shared USDC balance held for other users.

This PoC's exact numerical divergence depends on the specific LT implementation's misbehavior, which is outside the scope of alt.fun's own contracts (per the exclusion of BounceTech LT internals) — the root cause proven here is Zap's failure to independently verify the balance delta, the same missing safeguard the external report flags for ERC4626 vaults.
