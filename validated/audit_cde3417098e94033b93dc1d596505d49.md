## Analog Found: Escrow Over-Crediting for Fee-on-Transfer Tokens in Tron `IntentGatewayV2.placeOrder`

The reported `DSTContract.sol` bug is a class of vulnerability where an accounting variable (`collectedEther`) is incremented by the *nominal* value sent (`msg.value`) rather than the *actual* value retained by the contract after a refund/short-transfer, letting an attacker inflate internal accounting beyond the contract's real balance. The Tron variant of `IntentGatewayV2` has the same bug class for ERC20 escrow accounting.

### Title
Escrow accounting credited by nominal input amount instead of actual tokens received, allowing escrow liabilities to exceed contract balance - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In the Tron deployment of `IntentGatewayV2.placeOrder`, the ERC20 escrow path calls `safeTransferFrom` for the stated `order.inputs[i].amount` but never measures the actual tokens received before crediting `_orders[commitment][token]`. For any ERC20 with a transfer fee (fee-on-transfer / deflationary token), the contract receives less than `order.inputs[i].amount`, yet the full (fee-adjusted) `reducedInputs[i].amount` is still credited to escrow — exactly mirroring the `collectedEther += msg.value` bug where the accounting increment ignores the value actually retained.

### Finding Description
In the non-predispatch branch of `placeOrder`: [1](#0-0) 


`reducedInputs[i].amount` is derived purely from the user-supplied `order.inputs[i].amount` (minus the protocol fee bps), not from any post-transfer balance check. If `token` charges a transfer fee, the actual tokens received by the contract are `order.inputs[i].amount - transferFee`, but the escrow ledger (`_orders[commitment][token]`) is still credited as if the full nominal amount arrived.

This is precisely the class of bug the external report describes: an accounting variable is incremented by a value larger than what the contract actually retained, because a “fee/refund” mechanism (here, the token's own transfer fee) silently reduces the true balance.

Contrast this with the canonical (non-Tron) `IntentGatewayV2.sol`, which was hardened specifically against this issue by measuring the balance delta and overwriting `order.inputs[i].amount` with the actual received amount before computing the escrow/fee split: [2](#0-1) 

The Tron contract lacks this `balBefore`/`balanceOf` delta check entirely, indicating the fix present on the canonical EVM contract was never ported to the Tron variant.

The escrow is later paid out via `withdraw()`, which transfers `body.tokens[i].amount` (equal to the over-credited `reducedInputs[i].amount`) directly against a simple non-zero check, with no verification against the contract's actual token balance for that specific order: [3](#0-2) 

### Impact Explanation
Because escrow credit exceeds the tokens actually deposited, the sum of all `_orders[...][token]` entries for a fee-on-transfer token can exceed the gateway's real token balance. When withdrawals occur (via `RedeemEscrow`/`RefundEscrow` `onAccept` calls or `cancelOrder`), the shortfall is paid out of the pooled balance funded by *other users'* orders in the same token — i.e., later legitimate depositors/solvers cannot fully withdraw their entitled escrow (funds freezing), or an attacker can repeatedly place orders with a fee-on-transfer token and immediately cancel them to siphon more tokens out than they put in, effectively stealing from the shared token pool (theft of funds). This satisfies the "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
`placeOrder` is a fully unprivileged, directly reachable entry point for any user/token bridger on the Tron `IntentGatewayV2` deployment. The trigger requires nothing more than specifying a fee-on-transfer/deflationary ERC20 as an input token — a common token category on-chain (fee-on-transfer test coverage already exists for the *canonical* EVM contract, confirming this is a recognized, realistic threat model that was simply not carried over to Tron): [4](#0-3) 

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure `IERC20(token).balanceOf(address(this))` before and after `safeTransferFrom`, set `order.inputs[i].amount` (and consequently `reducedInputs[i].amount`) to the actual delta received, and only then compute protocol fees and credit `_orders[commitment][token]`.

### Proof of Concept
1. Deploy/identify a fee-on-transfer ERC20 (e.g., 1% fee) as `token` and use it as `order.inputs[0].token` with `amount = 1000e18` in Tron `IntentGatewayV2.placeOrder`.
2. User approves and calls `placeOrder`; the contract's actual `token` balance increases by only `990e18` (fee deducted), but `_orders[commitment][token]` is credited `reducedInputs[0].amount` computed from the full `1000e18` (minus protocol fee), overstating the escrow by ~1%.
3. Repeat with multiple orders/users using the same fee-on-transfer token; the aggregate `_orders[...][token]` values across commitments now exceed `IERC20(token).balanceOf(gateway)`.
4. When orders are later settled/cancelled (`withdraw`), the transfers drawn against the shared pool exhaust it before all legitimate claims can be honored — the last claimant(s) get a reverted/failed withdrawal (funds frozen), while earlier claimants effectively extracted more value than they deposited (funds stolen from later depositors).
