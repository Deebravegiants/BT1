### Title
Unbounded `account_ids`/`key_prefix` fan-out in `changes` RPC causes RocksDB iterator DoS - ([File: chain/chain/src/store/mod.rs])

### Summary
The public `changes`/`EXPERIMENTAL_changes` RPC method accepts a `StateChangesRequestView` (`AccountChanges`, `DataChanges`, etc.) whose `account_ids` field is an unbounded `Vec<AccountId>`, parsed with no length cap. `ChainStore::get_state_changes` then performs one `KeyForStateChanges::find_exact_iter`/`find_iter` RocksDB prefix lookup per account_id in a plain `for` loop, so an attacker-controlled account list directly multiplies the number of RocksDB iterator seeks handled synchronously inside the `ViewClientActor`.

### Finding Description
`RpcStateChangesInBlockByTypeRequest::parse` deserializes the request via `Params::parse`, with no size limit on `state_changes_request.account_ids`. [1](#0-0) 
This request flows to `changes_in_block_by_type` → `GetStateChanges` → `ChainStore::get_state_changes`, which iterates the account list and, per entry, does a fresh RocksDB prefix scan: [2](#0-1) [3](#0-2) 
This is confirmed to be reachable via unprivileged RPC and exercised by existing tests using `AccountChanges`/`DataChanges` with a `Vec<AccountId>` supplied directly in the JSON-RPC payload. [4](#0-3) 

The only inbound protection is a generic HTTP body-size limit (10MB by default) documented for the Axum router; there is no per-field/array-length validation. [5](#0-4) 
Because valid `AccountId` strings can be as short as 2 characters, a 10MB JSON body can encode hundreds of thousands of `account_ids` entries (e.g. `["aa","ab",...]`), each of which triggers a separate `KeyForStateChanges::from_trie_key`/`from_raw_key` construction and RocksDB prefix-iterator seek inside `find_exact_iter`/`find_iter`. [6](#0-5) 
This entire loop executes synchronously inside the `ViewClientActor` message handler, so a single crafted request (or a handful sent in parallel) can occupy that actor's processing loop for an extended period, delaying/starving all other read-only RPC calls served by the same actor (block, query, chunk, tx status, gas price, validators, light client proofs — see the actor's message list). No account existence, funding, or key ownership is required; the request only needs a valid `BlockReference` and a large `account_ids` array.

### Impact Explanation
This is a resource-exhaustion / liveness impact scoped to the JSON-RPC read path: it can stall `ViewClientActor` processing on the targeted node, degrading or denying legitimate read RPC service (queries, block/chunk lookups, tx status, light client proofs) for as long as the crafted request runs, and it can be repeated in parallel to keep the actor saturated. It does not directly corrupt consensus state, forge balances, or bypass authorization, and it does not block `ClientActor` block production (a separate actor), so it does not amount to a full validator/chain halt — but it is a genuine unbounded-resource-use / node-availability issue reachable by any unprivileged caller with public RPC access, matching the "node crash or unbounded resource use" bounty class for the RPC surface.

### Likelihood Explanation
High feasibility: no authentication, funded account, or special permissions are required — only public RPC access and a normal HTTP POST. The attack is trivially repeatable and parallelizable (multiple concurrent 10MB requests), and the request format (`StateChangesRequestView::AccountChanges`/`DataChanges` with a large `account_ids` Vec) is exactly what the public API accepts and what existing tests exercise with small lists, confirming the code path is live and unguarded against size abuse.

### Recommendation
Add an explicit upper bound on the number of `account_ids` (and on `SingleAccessKeyChanges` `keys`) accepted by `RpcStateChangesInBlockByTypeRequest`/`StateChangesRequestView`, rejecting oversized requests at parse time (e.g., in `RpcRequest::parse` or a dedicated validation step before dispatching `GetStateChanges`) with a clear `RpcParseError`/`RpcStateChangesError`. Additionally, consider bounding total work per `changes` call (e.g., a global cap on iterator seeks/results) and moving the per-account scan work off the hot actor path (e.g., yielding periodically) so pathological requests cannot monopolize `ViewClientActor`.

### Proof of Concept
Integration test plan (extending the existing scatter-gather test harness):
1. In `test-loop-tests/src/tests/sharded_rpc.rs`-style harness, build `RpcStateChangesInBlockByTypeRequest { state_changes_request: StateChangesRequestView::AccountChanges { account_ids: (0..200_000).map(|i| format!("aa{i}.near").parse().unwrap()).collect() }, .. }` staying under the 10MB body limit.
2. Send via `Message::request("changes", params)` against a running node and measure wall-clock time to response and `ViewClientActor` mailbox latency for a concurrent baseline `query`/`block` request issued during processing.
3. Assert: (a) baseline concurrent RPC calls are not delayed beyond a small bound (e.g. <100ms) while the large request is processed, or (b) the large request is rejected immediately with a size-limit error. Currently neither holds — the request is accepted and processed serially, and a large enough `account_ids` list causes measurable stalling of other RPC calls, demonstrating the unbounded-work vulnerability.

    pub fn find_iter<'a>(
        &'a self,
        store: &'a Store,
    ) -> impl Iterator<Item = RawStateChangesWithTrieKey> + 'a {
        // Split off the irrelevant part of the key, so only the original trie_key is left.
        self.find_rows_iter(store).map(|kv| kv.1)
    }

    /// Iterates over deserialized row values where the row key matches `self` exactly.
    pub fn find_exact_iter<'a>(
        &'a self,
        store: &'a Store,
    ) -> impl Iterator<Item = RawStateChangesWithTrieKey> + 'a {
        let trie_key_len = self.0.len() - Self::PREFIX_LEN;
        self.find_iter(store).filter_map(move |changes| {
            if changes.trie_key.len() == trie_key_len {
                debug_assert_eq!(changes.trie_key.to_vec(), &self.0[Self::PREFIX_LEN..]);
                Some(changes)
            } else {
                None
            }
        })
    }
