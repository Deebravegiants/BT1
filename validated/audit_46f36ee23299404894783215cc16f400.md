Audit Report

## Title
CORS Origin Allowlist Bypass via Unanchored Suffix Match on Wildcard Domains - (File: core/services/gateway/network/httpserver.go)

## Summary
The Gateway HTTP server's `isAllowedOrigin` function uses `strings.HasSuffix(originHost, allowedHost)` to validate wildcard CORS allowlist entries (e.g., `*.example.com`), but performs no check that the match is preceded by a domain-label boundary (`.`). This allows an attacker-registered domain like `evilexample.com` to be treated as a trusted subdomain of `example.com`, when it is in fact a completely independent, attacker-controlled domain.

## Finding Description
In `isAllowedOrigin`, once the `*.` prefix is stripped from a configured wildcard entry, the remaining check is a bare substring suffix comparison with no boundary anchoring: [1](#0-0)  This conflates "originHost textually ends with allowedHost" with "originHost is a genuine subdomain of allowedHost." For an allowlist entry `https://*.example.com`, `allowedHost` becomes `example.com`, and `strings.HasSuffix("evilexample.com", "example.com")` evaluates to `true`, even though `evilexample.com` is a distinct, independently-registrable domain with no relation to `example.com`. No other check in the function (scheme/port equality checks at [2](#0-1) ) mitigates this, since those only constrain scheme and port, not the host boundary.

## Impact Explanation
If a Gateway operator configures a wildcard CORS entry such as `CORSAllowedOrigins = ["https://*.example.com"]`, an attacker who registers/controls a domain like `evilexample.com` can serve a malicious web page from that origin. When a victim browser (holding valid session/credentials for the Gateway) visits the attacker's page, cross-origin requests from that page will receive `Access-Control-Allow-Origin: https://evilexample.com` from `handleRequest`, [3](#0-2)  allowing the attacker's JavaScript to read cross-origin credentialed responses from Gateway endpoints (e.g., `ProcessRequest`), which may include job run data or other sensitive DON-routed responses. This maps to an in-scope "allowlist bypass" / "cross-user response corruption/exfiltration" impact class.

## Likelihood Explanation
Exploitation requires no privileged access to the Gateway or node — the attacker only needs to register any domain name that textually ends in the allowed suffix (a normal, unauthenticated DNS registration action) and lure/induce a victim with an active session into visiting a page on that domain. This is fully attacker-controlled and repeatable, though it depends on the operator configuring a wildcard CORS entry rather than exact-origin allowlisting.

## Recommendation
Anchor the wildcard suffix match to a domain-label boundary, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```
This ensures the origin is either exactly the allowed domain or a true subdomain of it, rather than any domain that happens to end with the same character sequence.

## Proof of Concept
1. Configure Gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.example.com"]`.
2. Send an HTTP request to the Gateway (e.g., a preflight `OPTIONS` or a `GET`) with header `Origin: https://evilexample.com`.
3. Observe that `isAllowedOrigin` returns `true` (via the `strings.HasSuffix` branch) and the response includes `Access-Control-Allow-Origin: https://evilexample.com`.
4. This can be verified with a Go unit test calling `isAllowedOrigin("https://evilexample.com")` on a server configured with `CORSAllowedOrigins: []string{"https://*.example.com"}` and asserting it returns `true`, demonstrating the allowlist bypass.
