### Title
Tokens sent directly to the pool or controller are permanently locked — no sweep or claim path exists - (File: contracts/pool/src/cache/cash.rs)

### Summary
XOXNO Lending's pool books `cash` only through measured receipt inside controller-driven flows (`supply`, `repay`, `recapitalize`). A direct `token::transfer` to the pool or controller raises the real SAC balance but is never credited to any market's book and can never be claimed or swept, so the tokens are frozen forever — the Soroban analog of "ETH sent to SwapRouter will be lost."

### Finding Description
The pool treats `cash` as a pure bookkeeping number credited only on the controller's word (`contracts/pool/README.md:54-63`: "`cash` is a bookkeeping number... `supply`, `repay` and `recapitalize` all credit `cash` on the controller's word"). `INV-ACCT-02` states "token donations alone do not increase it" (`docs/reference/invariants.md:104-109`), and `docs/reference/architecture.md:57-65` confirms "direct donations do not automatically increase booked cash" even though sibling markets share one physical pool balance.

No recovery path exists:

- `claim_revenue` is capped by booked cash (`contracts/pool/README.md:337-339`: `min(cash, floor(revenue_value))`), so donations cannot be claimed as revenue.
- `recapitalize` credits cash only up to `backing_shortfall` and refunds the rest — a healthy market applies 0 and refunds everything (`contracts/pool/tests/flows.rs:3330-3344`).
- `flash_loan` only measures a balance transition around the callback; it does not absorb pre-existing surplus.
- Neither the pool nor the controller ABI exposes any `sweep`/`rescue`/`skim` entrypoint; the only sweeps in the repo live in the out-of-scope `swap-aggregator`. On the controller side, "undeclared controller balances are not credited" and "Neither category sweeps prior balances" (`docs/explanation/threat-model.md:172-173`).

The codebase itself treats this as a live hazard: `borrow`/`withdraw` reject `to = pool` or `to = controller` with `InvalidFlashloanReceiver` (#412) precisely because "the controller holds funds no balance-delta measurement can ever claim" (`tests/test-harness/tests/controller/recipient_is_protocol_contract.rs:1-5`). That guard protects protocol payouts, but nothing stops a user from transferring tokens directly to either address.

### Impact Explanation
Any token (including native XLM) transferred directly to the pool or controller is permanently frozen: it inflates `token.balance(pool)` above `sum(cash)` but belongs to no market, no revenue share, and no refund path. There is no admin or governance operation that can extract it — even `claim_revenue` is bounded by the `cash` book, and `upgrade` is governance-controlled (privileged, excluded). This is permanent freezing of user funds.

### Likelihood Explanation
Reachable by a single unprivileged address: `token::Client::transfer(user, pool, amount)` or `transfer(user, controller, amount)`. This is user-error driven (like the original SwapRouter report), so likelihood is moderate — misrouted repayments, mistaken "donations," or integrators paying the pool directly instead of going through `controller.repay` are realistic, and the liquidations skill already warns that "transferring repayment directly to the pool is a donation" (`skills/xoxno-lending-liquidations/SKILL.md:77-79`). Medium severity, matching the source report.

### Recommendation
Add a governance-gated `sweep(hub_asset)`/`rescue` entrypoint to the pool (and controller) that pays out `token.balance(pool) - sum(cash across all markets sharing that asset)`, or document the trap prominently and have clients/SDK block transfers whose `to` is a protocol address. At minimum, extend the existing `InvalidFlashloanReceiver` philosophy to a view that integrators can check before paying.

### Proof of Concept
1. Setup: market for XLM exists on `(hub_id=1)`; pool holds `cash = B` matching `token.balance(pool)`.
2. Unprivileged `alice` calls `token::Client::new(&env, &xlm_sac).transfer(&alice, &pool, &1_000_000_000)`.
3. `token.balance(pool) == B + 1_000_000_000`, but `get_reserves` still returns `cash = B`; the donation belongs to no `(hub, token)` book (`tests/test-harness/tests/pool_money_flow_audit.rs:86-103` asserts exactly this shape).
4. Try every recovery route:
   - `claim_revenue` → capped at `min(cash, revenue)`; donated amount unreachable.
   - `recapitalize` → `backing_shortfall == 0`, full refund to payer, donation untouched.
   - `update_indexes`, `seize_positions`, `net_settle` → no token movement.
   - Controller has no sweep; stranded controller balances are never credited or refunded.
5. Result: `1_000_000_000` stroops remain in the pool SAC balance forever with no code path that can move them.
