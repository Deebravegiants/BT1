### Title
Attacker-controlled route bytes let arbitrary on-chain code run under the caller's signed authorization tree in controller swap strategies - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The Vim bug class — attacker-controlled data reaching a command-execution context without sanitization — maps directly onto the controller's strategy swaps. `swap_tokens` forwards the caller-supplied `swap: StrategySwap` bytes verbatim to `router.execute_strategy`, and the router invokes whatever pool/token addresses the payload names. The router keeps no venue allowlist, so a crafted `routeXdr` can place an attacker-deployed contract on the call stack, and any `token.transfer(victim, attacker, X)` it makes is recorded as a child of the victim's `require_auth` entry on the controller call. A victim who signs the simulated auth tree (as wallets do after `simulateTransaction`) authorizes draining any token in their wallet — far beyond the routed amount.

### Finding Description
The controller exposes several unprivileged entrypoints that take opaque route bytes: `swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`, and `flash_position`. Each funnels into `swap_tokens`, which performs only two checks on the swap: it is non-empty, and measured balances behave (`RouterOverspend`, `NoSwapOutput`). Neither check inspects *what* the route calls [1](#0-0) .

The router resolves venues purely from payload registries (`assets` addresses, instruction opcodes) and dispatches to them; the payload docs confirm "The router calls the pool and token addresses its payload names and keeps no allowlist of them" [2](#0-1) . Because `execute_strategy(sender = controller)` runs beneath the account owner's `require_auth` on the controller entrypoint, any nested `transfer` from the victim recorded during simulation becomes part of the auth tree the victim signs. The harness test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates exactly this: a `RoutedSwap` naming an attacker `RogueHopPool` causes `token.transfer(alice, attacker, WALLET_BALANCE)` to be recorded under Alice's `swap_collateral` auth entry and to execute, emptying an unrelated token the protocol never listed [3](#0-2) [4](#0-3) .

This is the same shape as the Vim flaw: untrusted input (Visual selection / route bytes) is passed to an executor (shell / Soroban host invocation) without a boundary that separates data from code, and the ambient authority of the invoking context (user's shell / user's signed auth tree) is abused.

### Impact Explanation
Theft of user funds. The malicious child transfer is not bounded by the routed amount, the payload `min_out`, or the controller's post-swap risk gates — it moves any token the victim holds, in full. The delivered swap output still satisfies `NoSwapOutput` and the account's final HF check, so the transaction succeeds and looks like a normal swap [5](#0-4) .

### Likelihood Explanation
Routes are built off-chain and supplied as opaque XDR bytes; the controller never decodes them (`swap_xdr` is forwarded untouched) [6](#0-5) . An attacker who can influence the bytes a victim signs — a malicious or compromised quote source, phishing frontend, or a crafted payload handed to the victim — reaches this path with no privileges. Exploitation requires the victim to sign the poisoned auth tree; wallets surface child invocations poorly, and the simulation itself "succeeds" in recording mode, so there is no on-chain tripwire. The mitigation is delegated entirely to clients decoding routes before signing, which the contracts cannot enforce [7](#0-6) . Rated Medium–High likelihood-weighted severity given the user-interaction requirement against Critical impact.

### Recommendation
Constrain execution at the trust boundary rather than trusting payload bytes:
- Maintain an on-chain venue allowlist in the router (or controller) and reject instructions whose pool/token addresses are not registered venues — matching how whitelist infrastructure already exists for fee tokens.
- Alternatively, have the controller validate that the route's declared `token_in`/`token_out` and venue set match the caller-requested pair before authorizing the input transfer.
- At minimum, document and enforce in the SDK/wallet layer that any auth tree for a strategy call containing children other than the single input `transfer` must be refused (the threat model already prescribes this; making it contractual is safer).

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` is a working PoC:

1. Alice supplies 10 000 USDC and holds `WALLET_BALANCE` of an unlisted token.
2. Attacker deploys `RogueHopPool` whose `swap()` calls `token.transfer(alice, attacker, WALLET_BALANCE)` [8](#0-7) .
3. Attacker builds `routeXdr` naming that pool as the hop venue; Alice calls `controller.swap_collateral(alice, account_id, USDC, 5_000e7, ETH, route)` and signs the simulated tree.
4. Result: `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, and Alice still receives fair ETH output — the swap "succeeds" [9](#0-8) .

    pub fn execute_strategy(env: Env, sender: Address, total_in: i128, swap_xdr: Bytes) -> i128 {
        sender.require_auth();
        let route = RoutedSwap::from_xdr(&env, &swap_xdr).expect("route must decode");
        let router = env.current_contract_address();
        token::Client::new(&env, &route.token_in).transfer(&sender, &router, &total_in);
        let _: Val = env.invoke_contract(&route.hop_pool, &symbol_short!("swap"), vec![&env]);
        token::Client::new(&env, &route.token_out).transfer(&router, &sender, &route.min_out);
        route.min_out
    }
}

pub struct RogueHopPool;

#[contractimpl]
impl RogueHopPool {
    pub fn __constructor(env: Env, victim: Address, token: Address, to: Address, amount: i128) {
        env.storage()
            .instance()
            .set(&symbol_short!("PLAN"), &(victim, token, to, amount));
    }

    pub fn swap(env: Env) {
        let (victim, wallet_token, to, amount): (Address, Address, Address, i128) = env
            .storage()
            .instance()
            .get(&symbol_short!("PLAN"))
            .expect("plan is set by the constructor");
        if amount > 0 {
            token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount);
        }
    }
