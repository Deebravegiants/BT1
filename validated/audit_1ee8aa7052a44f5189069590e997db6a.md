### Title
Passphrase-validity oracle via `getMnemonic()` distinct error messages for wrong-password vs. bad-seedId - ([File: features/wallet/module/wallet.js])

### Summary
`Wallet.getMnemonic({ passphrase, seedId })`, directly exposed on the public RPC surface via `wallet.getMnemonic` in the wallet API, decrypts the primary seed with the supplied `passphrase` before ever checking whether `seedId` exists. Because decryption failure and "seedId not found" are surfaced as two distinguishable error messages, an attacker can supply an arbitrary/non-existent `seedId` and use the returned error text as an oracle to test passphrase correctness without ever needing a valid seedId or retrieving the mnemonic.

### Finding Description
In `getMnemonic` [1](#0-0) , the flow is:

1. `const { mnemonic } = await this.#getSeed({ passphrase })` — this calls `this.walletStorage.get(SEED_KEY, { passphrase })`, which decrypts the stored encrypted seed using the supplied `passphrase`. If the passphrase is wrong, this call throws (decryption failure).
2. Only after successful decryption does the code check `seedId` against the primary seed id or the list from `#getExtraSeeds()`, throwing `'No seed matches seedId.'` if no match is found.
3. The outer `catch` block special-cases exactly one message: if `err.message === 'No seed matches seedId.'` it re-throws that specific error; for *every other* error (including decryption failure due to wrong passphrase) it normalizes to `'Wrong password. Try again.'`.

This means the message returned to the RPC caller is a direct function of whether the passphrase decrypted the seed successfully, independent of whether `seedId` was ever valid:
- Wrong `passphrase` + any `seedId` (valid or garbage) → decryption throws → caught → `'Wrong password. Try again.'`
- Correct `passphrase` + non-existent `seedId` → decryption succeeds, loop finds no match → `'No seed matches seedId.'` is thrown and preserved as-is.

Since `getMnemonic` is exposed directly and unmodified by the wallet API layer (`features/wallet/api/index.js`, `getMnemonic: wallet.getMnemonic`), there is no additional gating (e.g., rate limiting, origin/consent approval) visible in the searched code between the RPC entry point and this logic. An attacker who can invoke this RPC method (e.g., a compromised/malicious dapp connection, or any caller with RPC access) can therefore probe arbitrary passphrase guesses using a `seedId` that is guaranteed not to exist, and learn from the distinct error string whether the guess was correct — all without needing to know any real `seedId`, and without ever receiving the mnemonic itself. This constitutes a password-validity oracle that is separate from (and does not require) a successful `unlock()`, accelerating offline/online brute-force attacks against the wallet passphrase.

### Impact Explanation
This is a passphrase-verification oracle that leaks whether an attacker's passphrase guess is correct, using an unauthenticated/unlocked-independent path (`getMnemonic`) rather than the dedicated `unlock()` flow. It doesn't by itself return the mnemonic, but it lets an attacker binary-search/brute-force the true passphrase far more cheaply and stealthily than through `unlock()` (whose sole purpose is presumably rate-limited/monitored), because `getMnemonic` reveals correctness via error message text with a trivially reachable, cheap request (bogus `seedId`) that never triggers full unlock semantics or associated protections such as lockouts tied to `unlock()`. Once the passphrase is recovered via this oracle, the attacker can call `getMnemonic` (or `unlock`) with the correct passphrase to fully decrypt and exfiltrate the seed/mnemonic — a complete wallet-secrets compromise.

### Likelihood Explanation
- Preconditions: the RPC surface must expose `wallet.getMnemonic` to the attacker's context (this is the case per `features/wallet/api/index.js`, where it is listed unmodified among public methods) [2](#0-1) .
- The call requires no privileged access — it's a normal RPC/API call with a guessed passphrase and a fabricated `seedId` string.
- It is fully repeatable: each call is independent and yields a deterministic error type based purely on passphrase correctness, enabling automated brute-force scripting.
- No visible rate limiting, throttling, or lockout mechanism was found in the wallet module gating repeated `getMnemonic` calls, distinguishing it from typical `unlock()` protections (if any exist elsewhere, they are not applied here).

### Recommendation
Ensure `getMnemonic` returns a uniform, generic error for *all* failure modes—whether due to wrong passphrase or non-existent `seedId`—so no information about passphrase correctness leaks independent of a full successful decryption+match. Specifically:
- Validate `seedId` membership using data that does not require decrypting with the caller-supplied passphrase (e.g., derive/compare seed ids using a separately keyed lookup, or defer the seedId-existence check until after establishing the passphrase is confirmed via an already-rate-limited/audited path).
- Alternatively, restructure so that "no seed matches seedId" is only distinguishable if it can be proven independently of the guessed passphrase (e.g., check `seedId` shape/existence against a passphrase-independent seed-id list before attempting decryption, and if it doesn't exist there, throw a normalized "Wrong password" style response, or just always return the same generic message for both failure cases as `unlock()` does).
- Apply the same lock/rate-limiting protections to `getMnemonic` passphrase attempts as exist (or should exist) for `unlock()`.

### Proof of Concept
Unit test plan (extending `features/wallet/module/__tests__/index.test.js` patterns):
```js
test('getMnemonic error type leaks passphrase correctness via seedId oracle', async () => {
  // setup wallet with usePassword: true, a known passphrase, and maxExtraSeeds > 0
  await wallet.create({ passphrase: 'correct-horse' })

  // Case 1: wrong passphrase + non-existent seedId -> generic "Wrong password"
  await expect(
    wallet.getMnemonic({ passphrase: 'wrong-guess', seedId: 'does-not-exist' })
  ).rejects.toThrow('Wrong password. Try again.')

  // Case 2: correct passphrase + non-existent seedId -> distinguishable "No seed matches seedId."
  await expect(
    wallet.getMnemonic({ passphrase: 'correct-horse', seedId: 'does-not-exist' })
  ).rejects.toThrow('No seed matches seedId.')

  // Assertion: error message/type differs between Case 1 and Case 2 purely based on
  // passphrase correctness, despite seedId being invalid in both cases -- this is the oracle.
  // A fix should make both cases indistinguishable (e.g., both throw 'Wrong password. Try again.'
  // or both throw a uniform generic error), and the PoC should assert that after the fix,
  // getMnemonic with a non-existent seedId always yields the same error regardless of
  // passphrase correctness.
})
```

```javascript
  getMnemonic = async ({ passphrase, seedId } = {}) => {
    try {
      // always need to get primary seed first to make sure the user entered the right passphrase
      // even if passed seedId is not primary
      const { mnemonic } = await this.#getSeed({ passphrase })
      if (!mnemonic) throw new Error('Wrong password. Try again.')

      if (!seedId || (await this.getPrimarySeedId()) === seedId) return mnemonic

      // Sequential, as sync fallback is slower
      for (const seed of await this.#getExtraSeeds()) {
        if (seedId !== (await getSeedId(seed.seed))) continue
        if (!seed.mnemonic) throw new Error('No mnemonic found for seedId.')
        return seed.mnemonic
      }

      throw new Error('No seed matches seedId.')
    } catch (err) {
      if (err.message === 'No seed matches seedId.') {
        this.#logger.debug('getMnemonic() failed: no seed matches seedId.')
        throw err
      }

      this.#logger.debug('getMnemonic() failed: wrong password')
      throw new Error('Wrong password. Try again.')
    }
  }
```
