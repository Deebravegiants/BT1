### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then dispatches the webhook to handlers using the `shop`, `topic`, and `webhook_id` values taken from HTTP headers that are never included in the signed material. This breaks the intended binding "the shop this data is attributed to == the shop Shopify actually sent it for."

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it with the `hmac` value on the query object [1](#0-0) .

For webhooks, `Request#to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cryptographic binding to the body or to the HMAC value [3](#0-2) .

`Registry.process` then validates only the HMAC (i.e., only the body) before dispatching to the handler using the unauthenticated `shop` header value: [4](#0-3) . `WebhookMetadata` receives `shop: request.shop` straight from the header, so the app's handler code processes/attributes the payload to whatever shop domain is present in the header, regardless of which shop's secret produced the payload.

Because the app's `api_secret_key` (used to compute/verify the HMAC) is shared across all shops that install the app, not shop-specific, the HMAC only proves "this body was produced by someone holding the app's secret" — it does not prove "this body was sent for shop X." An attacker who has installed the app on their own store (an unprivileged, non-victim tenant) receives legitimate webhooks with valid `body` + `hmac` pairs. They can replay that exact `body`/`hmac` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` (and optionally `shopify-topic`/`shopify-webhook-id`) header to name a victim shop. `HmacValidator.validate` still succeeds because it only checks the body's HMAC, and `Registry.process` will hand the payload to the handler tagged with the victim's shop domain.

This exactly matches the requested analog class: "a field acted on but not covered by the HMAC" — here, `shop` (and `topic`/`webhook_id`) are trusted/acted-upon identity fields excluded from the signed payload.

### Impact Explanation
This is a cross-tenant identity-confusion vulnerability: a low-privilege attacker (any merchant who installs the public app) can make the host application process/store webhook data under a different, victim shop's identity, since the application logic keys off `request.shop`/`WebhookMetadata#shop` believing it is authenticated. Depending on how the host app's handler uses `shop` (e.g., writing data associated with that store, triggering side effects like disabling/enabling features, updating billing/inventory records, or deleting the victim shop's data), this can lead to cross-tenant data corruption or unauthorized actions attributed to another merchant, satisfying the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Requires only that the attacker be a legitimate (if unprivileged) install of the app on their own shop, capture one legitimate webhook body+HMAC (trivial, as webhook payloads are delivered over plain HTTP callback endpoints that the attacker's own server can log), and replay it with a modified `shopify-shop-domain` header to the same public webhook endpoint. No access to the `api_secret_key`, access tokens, or any credentials belonging to the victim is needed.

### Recommendation
Include the shop domain (and topic/webhook id, if they drive dispatch logic) in the signed material, or otherwise cryptographically bind them to the verified body (e.g., verify that the `shop` claimed in the header matches a shop-specific secret/session, not just the shared app secret). At minimum, document that `request.shop`/`topic` are unauthenticated and must be independently validated by the host application (e.g., cross-checked against an installed/offline session for that shop) before being trusted.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and stands up a server to receive webhooks, capturing a legitimate `(raw_body, shopify-hmac-sha256)` pair from Shopify for topic `orders/create`.
2. Attacker sends a POST to the victim app's webhook endpoint with the same `raw_body` and `shopify-hmac-sha256`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the shared `api_secret_key` HMAC [5](#0-4) .
4. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from and was signed for the attacker's own shop, demonstrating the cross-tenant identity break.
