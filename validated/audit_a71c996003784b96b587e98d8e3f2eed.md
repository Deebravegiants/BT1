### Title
Webhook `shop` (and `topic`) identity is taken from headers not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , so `Utils::HmacValidator.validate` only proves that the *body bytes* were signed by Shopify with the app's secret [2](#0-1) . However, `Registry.process` uses `request.shop` and `request.topic` - both read straight from HTTP headers with no cryptographic binding to the signed body - to route the webhook and to populate `WebhookMetadata` handed to the app's business logic [3](#0-2) , and those header values are extracted unauthenticated in `Request#shop`/`Request#topic` [4](#0-3) .

### Finding Description
The identity binding that should hold is:
`shop asserted to the handler == shop that Shopify actually generated the HMAC for`

In reality the code only proves:
`HMAC(body, api_secret_key) == received hmac`

The `shop-domain` and `topic` headers are never included in `to_signable_string`, so they are not part of what the signature covers [1](#0-0) . Any unprivileged internet user who operates their own Shopify store can install the target app and receive genuine, validly-signed webhooks for their own shop. Because the HMAC is computed only over the body, that attacker can replay the exact same signed body while altering the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to any value before it reaches the app's webhook endpoint. `Registry.process` will accept the HMAC as valid (it never re-derives `shop`/`topic` from anything the signature covers) [5](#0-4)  and will hand the attacker-chosen `shop` value to the app's `WebhookHandler#handle` as if it were authenticated, cross-tenant, Shopify-verified data.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: an app relying on `WebhookMetadata#shop` (the value this library asserts is the authenticated source shop) to decide which merchant's data/session to act on can be tricked into attributing attacker-supplied webhook payloads to an arbitrary victim shop - a cross-tenant access primitive, without needing the app's `client_secret`, an access token, or any privileged account.

### Likelihood Explanation
Any internet user can freely create a Shopify development/trial store, install the target app, and receive a genuinely-signed webhook. Modifying an HTTP header before it reaches the app's webhook endpoint (e.g. via a simple proxy) requires no special access. The only barrier is that the app must expose an endpoint that forwards raw headers/body to this gem's `Request`/`Registry.process` largely unchanged, which is exactly the documented usage pattern in this repo's tests and docs.

### Recommendation
Bind the trusted identity fields into the signed material, or independently verify them: e.g., have the library refuse to trust `shop`/`topic` header values unless they are cross-checked against out-of-band knowledge (such as a previously stored, verified shop for that HMAC/webhook subscription), or advocate/require apps register per-shop signing verification instead of relying on unauthenticated headers for routing.

### Proof of Concept
1. Attacker registers `attacker-shop.myshopify.com`, installs the target app, and triggers a real event (e.g., `orders/create`) so Shopify sends a genuinely HMAC-signed webhook to the app's endpoint.
2. Attacker intercepts/replays this exact HTTP request through a proxy, keeping the raw body and `X-Shopify-Hmac-Sha256` header untouched, but rewrites `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and optionally `X-Shopify-Topic`).
3. The app passes this to `ShopifyAPI::Webhooks::Registry.process(request)`. `Utils::HmacValidator.validate` succeeds because it only checks the (unmodified) raw body [6](#0-5) .
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ...)` [7](#0-6) , causing the app to act on attacker-controlled data as if it legitimately originated from the victim shop.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
