### Title
Webhook HMAC does not bind the `shop` identity field, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then trusts the `shop` value taken from the unauthenticated `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header when constructing the `WebhookMetadata` passed to the host app's handler. Because the HMAC does not cover the shop-domain header, the identity binding `HMAC-authenticated-body == shop-claimed-in-header` does not hold, letting a party who already receives valid webhooks for their own shop relabel them as belonging to a different merchant.

### Finding Description
`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler: [1](#0-0) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw body (`@raw_body`), never the headers: [3](#0-2) 

Yet `shop` — read from the `shopify-shop-domain`/`x-shopify-shop-domain` header — is treated as trusted tenant identity and forwarded unchanged into `WebhookMetadata`, which host apps use to resolve which merchant/session the event belongs to: [4](#0-3) [5](#0-4) [6](#0-5) 

The webhook HMAC secret is the app-level `api_secret_key` (the app's `client_secret`), shared across every shop that has installed the app — it is not shop-specific: [7](#0-6) 

Since the signature only binds `raw_body`, and any shop that installs the app can trigger arbitrarily-crafted body content and receive a validly-signed webhook for their own tenant, that party can take the valid `(raw_body, hmac)` pair they received and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to any other victim shop's domain. `HmacValidator.validate` still passes (it never inspected the header), and `Registry.process` hands the handler a `WebhookMetadata` claiming the forged victim `shop`, with attacker-chosen `body` content.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook authenticity: `shop`-authenticated (should equal) `shop`-covered-by-HMAC. Any app that uses `WebhookMetadata#shop` to select which merchant's session/data to update (the documented and expected usage pattern) can be made to apply attacker-controlled webhook payloads under another shop's identity — a cross-tenant access primitive, matching the report's Critical impact bar.

### Likelihood Explanation
Exploitation only requires being (or controlling) any shop that has legitimately installed the app — no leaked secret, no privileged account, and no TLS interception is needed. That shop naturally receives real webhooks with valid `(body, hmac)` pairs; the attacker only needs to swap one unauthenticated header before replaying the request to the app's public webhook endpoint.

### Recommendation
Include the shop-domain (and other trust-relevant headers such as `topic`, `webhook-id`, `api-version`) in the signable payload used for HMAC computation, or independently verify that the `shop` header value corresponds to a shop legitimately associated with this specific webhook delivery (e.g. cross-check against the webhook subscription/shop registered for that `webhook_id`) before trusting it in `WebhookMetadata`.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook with body `B`, `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker captures this request and resends it to the app's webhook endpoint, only replacing the `X-Shopify-Shop-Domain` header value with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only — validation succeeds because the header change is invisible to the signature check. [8](#0-7) 
4. The handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)` and processes attacker-controlled data as if it originated from the victim shop.
