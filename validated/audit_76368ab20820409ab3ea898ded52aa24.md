### Title
Webhook `shop` tenant identifier is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an incoming webhook from an HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body. Because the `shop` value is never part of the signed material, any party who can reach the app's webhook endpoint with a *validly signed body* can attach an arbitrary `shop-domain`/`x-shopify-shop-domain` header and have the app process the payload as belonging to a different merchant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an unauthenticated header, independent of the signed body: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e. the raw body — it never touches headers: [4](#0-3) 

`Registry.process` accepts the request once the body-only HMAC passes, and then forwards the *unauthenticated* `request.shop` straight into `WebhookMetadata`, which host applications use to key sessions/data per merchant: [5](#0-4) 

The identity binding that should hold is:
`hmac == HMAC(secret, raw_body)` should imply `shop` is authentic, i.e. `signed_bytes == (raw_body, shop)`.
In reality the code enforces only `signed_bytes == raw_body`, while `shop` is taken from a header that is fully attacker-controlled and never included in the signable string. This is exactly the "field acted on but not covered by the HMAC" bug class: the byte range that is cryptographically verified (`raw_body`) is smaller than the byte range that is trusted and acted upon (`raw_body` + `shop-domain` header).

### Impact Explanation
Any attacker who can obtain one validly-signed webhook body for *any* shop (e.g. by installing the app on their own store and receiving a real webhook, or via any other channel that yields a signed body) can replay that exact body to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `Utils::HmacValidator.validate` will still return `true` because the signature only covers the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload came from the victim shop. If the host application uses `WebhookMetadata#shop` to select the tenant's session, database record, or access token (the documented and expected use of this field), this results in cross-tenant data confusion/access — the app performs work or applies mutations under the identity of a shop the attacker does not control.

### Likelihood Explanation
Webhook endpoints are public HTTP(S) endpoints exposed by the host application; headers on any HTTP request reaching that endpoint are fully attacker-controlled. Obtaining a validly-signed body is trivial for an attacker who owns any shop where the app is installed (they simply capture their own legitimate webhook traffic, since the `client_secret` is shared across all shops for a given app and the HMAC key does not vary per-tenant). No privileged credentials, `api_secret_key` disclosure, or social engineering are required — only network reachability to the app's endpoint, which is inherent to the webhook delivery model. This is a straightforward, reliably reproducible bypass of the tenant binding within the gem's own verification logic.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material that `to_signable_string` returns, or otherwise cryptographically bind `shop` to the HMAC (e.g., compute the signature over a canonical string containing both the raw body and the shop domain), and document that consumers of `Utils::HmacValidator`/`Registry.process` must not trust any field outside `to_signable_string`. At minimum, `Registry.process`/`WebhookMetadata` should not expose header-derived `shop` as a value implicitly guaranteed to be authentic by a passing `HmacValidator.validate` check.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; capture a legitimate webhook delivery (raw body `B`, valid `hmac-sha256` header `H`, `shop-domain: attacker.myshopify.com`).
2. Replay the exact same request to the app's webhook endpoint, but change the `shop-domain` (or `x-shopify-shop-domain`) header to `victim.myshopify.com`, keeping body `B` and HMAC header `H` unchanged.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) and successfully matches `H` — see `lib/shopify_api/webhooks/request.rb` (`to_signable_string`, lines 35-38) and `lib/shopify_api/utils/hmac_validator.rb` (lines 12-31).
4. The handler is invoked with `WebhookMetadata.new(..., shop: request.shop, ...)` where `request.shop` now reads `"victim.myshopify.com"` from the attacker-modified header — `lib/shopify_api/webhooks/registry.rb` lines 198-199 — despite the payload never having been authorized for or originating from that shop.
