### Title
Webhook shop-domain header is trusted as tenant identity without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic once `Utils::HmacValidator.validate` succeeds, but the HMAC signature only covers the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values, which are read straight from HTTP headers, are never part of the signed content, so they are unauthenticated relative to the cryptographic check that the gem performs.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: ` [1](#0-0) `. `Utils::HmacValidator.validate` computes and compares the HMAC exclusively over that signable string: ` [2](#0-1) `. Meanwhile, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read directly from attacker-controllable HTTP headers with no cryptographic binding to the signed body: ` [3](#0-2) `.

`Registry.process` performs exactly one check — the body HMAC — and then unconditionally forwards `request.shop` into `WebhookMetadata`, which the host app's handler uses as the tenant identifier: ` [4](#0-3) `. The `WebhookMetadata` struct and the gem's own documentation instruct integrators to trust `data.shop` as "the shop domain of the webhook" and use it directly to route/attribute data per tenant: ` [5](#0-4) ` and ` [6](#0-5) `.

This breaks the intended identity binding: `hmac(raw_body) == valid` should imply `shop header == shop that produced raw_body`, but the equality actually verified is only `hmac(raw_body) == valid`; `shop` is disjoint from what's signed. Any user who can obtain one legitimately-signed `(raw_body, hmac)` pair for a topic — trivially true for the operator of their own shop who registers a webhook to their own endpoint and inspects the traffic — can replay that exact body/HMAC pair to a shared multi-tenant app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `Registry.process` will accept it as valid (since the body HMAC still matches) and hand the attacker-chosen `shop` value straight to the app's handler.

### Impact Explanation
This is a cross-tenant identity-binding break: the value the app uses to select which merchant's data/session to operate on (`data.shop`) is not covered by the same authentication check that vouches for the payload's authenticity. Any multi-tenant app built per the gem's documented pattern will attribute attacker-supplied webhook content to an arbitrary victim shop of the attacker's choosing (e.g., corrupting per-tenant order/customer records, triggering tenant-scoped side effects, or polluting another merchant's data pipeline), which meets the Critical bar of cross-tenant access.

### Likelihood Explanation
Exploitation requires no privileged credentials beyond controlling a shop the attacker can register a webhook against (any developer/merchant can create a free/dev shop) to harvest one valid `(body, hmac)` pair, then a single unauthenticated HTTP POST to the target app's public webhook endpoint with a forged `x-shopify-shop-domain` header — the exact header name is documented and predictable. This is a straightforward, repeatable action available to any unprivileged internet user who can reach the app's webhook route.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value verified by `HmacValidator`, or have `Registry.process` independently assert that the authenticated body actually pertains to the shop asserted in the header (e.g., by requiring the host app to look up a session/secret keyed off the verified body content, not the raw header) before constructing `WebhookMetadata`. At minimum, document prominently that `data.shop` is unauthenticated and must not be trusted for tenant selection without an independent verification step.

### Proof of Concept
1. Attacker registers a webhook (e.g., `orders/create`) to an endpoint they control, using their own shop `attacker-shop.myshopify.com`.
2. Shopify delivers a webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's shared `client_secret`), and header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, H)` and POSTs them to the target multi-tenant app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(B, client_secret) == H`.
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled content as if it originated from `victim-shop.myshopify.com`.
