### Title
Webhook Shop/Topic Headers Not Covered by HMAC Allows Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC of the raw JSON body, then unconditionally trusts the `shop-domain` and `topic` HTTP headers — which are not part of the signed payload — to attribute the event to a tenant and dispatch a handler. An app user (any merchant who installs the app) can capture a genuine, validly-signed webhook delivered for their own shop and replay it against the app's webhook endpoint with the `shop-domain` (and/or `topic`) header rewritten to a different shop, and the gem will still report the HMAC as valid.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read directly from headers, none of which feed into the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the body) and compares it to the received `hmac`: [3](#0-2) 

`Registry.process` uses this same HMAC check to authenticate the whole request, then builds `WebhookMetadata` from the **unauthenticated** `request.topic` and `request.shop` headers and hands it to the registered handler: [4](#0-3) 

The binding the gem is supposed to enforce is: `{shop, topic, body}` signed-and-verified == `{shop, topic, body}` acted upon. In reality it verifies only `body` (`HMAC(body) == received_hmac`) but then acts on `shop` and `topic` taken from headers that carry no cryptographic binding to that HMAC. Because the shared `api_secret_key` is the same for every shop that installs the app, any shop's legitimately-signed webhook body/HMAC pair remains valid when replayed with a different `shop-domain` header — the verification step cannot distinguish "this body was signed for shop A" from "this body+hmac is being presented for shop B."

### Impact Explanation
This breaks the tenant isolation the webhook subsystem is expected to provide: a malicious merchant (an ordinary, unprivileged installer of the app — no special credentials, tokens, or `api_secret_key` needed) can capture a webhook Shopify sends for their own store and resend it to the same public endpoint with `x-shopify-shop-domain` set to an arbitrary victim shop and/or `x-shopify-topic` changed. Because the HMAC still validates (it only ever covered the body), `Registry.process` will accept it and invoke the topic's handler with attacker-chosen `WebhookMetadata#shop`/`#body`, causing the host application to process fabricated or misattributed data under another tenant's identity — e.g., triggering `app/uninstalled`, `shop/redact`, or order/customer data handlers as if they originated from the victim shop. This is a cross-tenant integrity violation stemming directly from this gem's `Registry`/`Request`/`HmacValidator` design.

### Likelihood Explanation
Any merchant capable of installing the app on their own store can generate an arbitrary number of validly-signed webhook bodies for themselves at will (by performing actions like creating orders/customers, or triggering `app/uninstalled` by reinstalling), intercept the delivery, and replay it with rewritten headers using nothing more than a basic HTTP client. No secrets, tokens, or race conditions are required — only header manipulation on a replay, which is straightforward and repeatable.

### Recommendation
Bind the shop (and topic) identity into the value that's actually verified. Either:
- Include the `shop-domain` (and `topic`) header values in `to_signable_string` before computing/comparing the HMAC, or
- After HMAC validation, independently verify that `request.shop` corresponds to a shop that is actually installed/known to the app (e.g., cross-check against a stored session for that shop) before dispatching the handler, rather than trusting the header value implicitly.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers an event (e.g., updates an order) causing Shopify to POST a webhook to the app's public webhook endpoint with headers:
   - `x-shopify-topic: orders/updated`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC over body, using app secret>`
   - body: `{...attacker-controlled order JSON...}`
3. Attacker intercepts this exact request (their own inbox/proxy) and re-sends it to the same endpoint, unmodified except:
   - `x-shopify-shop-domain: victim.myshopify.com`
4. `Utils::HmacValidator.validate` recomputes HMAC over the identical body and it still matches — validation passes.
5. `Registry.process` builds `WebhookMetadata.new(topic: "orders/updated", shop: "victim.myshopify.com", body: <attacker JSON>, ...)` and invokes the app's `orders/updated` handler as if `victim.myshopify.com` sent it, letting the attacker inject/spoof data attributed to a shop they do not control.
