### Title
Webhook `shop`, `topic`, and `webhook_id` Identifiers Are Not Covered by HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while the `shop`, `topic`, and `webhook_id` values that `Registry.process` uses to dispatch and act on the webhook are read from unauthenticated HTTP headers that are never included in the signed data. An attacker who obtains one valid `(raw_body, hmac)` pair for the app's shared `client_secret` can replay it while forging the `shop-domain`, `topic`, and `webhook-id` headers, and the gem's own HMAC check will still pass.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (i.e., the raw body) against the `hmac` header: [3](#0-2) 

`Registry.process` trusts the HMAC check and then dispatches/acts using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [4](#0-3) 

The broken identity binding is: `hmac == HMAC(raw_body, client_secret)` is verified, but the equality that the application logic actually depends on — `(shop, topic, webhook_id)` used by the handler == the `(shop, topic, webhook_id)` that Shopify actually sent for that body — is never checked. Any unprivileged internet user who can obtain (or brute-force via a shared body format, e.g. an empty `{}` payload as used in this repo's own tests) a valid `(body, hmac)` pair can freely substitute the `shop-domain`, `topic`, and `webhook-id` headers on a replayed POST to the app's public webhook endpoint, and `HmacValidator.validate` will still return `true`.

### Impact Explanation
This breaks the tenant/topic binding that host applications rely on when processing webhooks: a handler registered for `topic` "customers/redact" (say) can be invoked with attacker-chosen `shop` while the signature only proves the body's authenticity for *some* shop/topic, not this one. Because the app's `client_secret` is shared across all shop installations, a body that legitimately validates for one shop (e.g. a trivial/predictable payload such as `{}`) can be replayed with a forged `shop-domain` header claiming to be a different, victim shop — resulting in cross-tenant webhook processing (e.g. spoofed mandatory GDPR webhooks, spoofed `app/uninstalled` events, or handler logic keyed on `data.shop` operating on the wrong tenant's data/session).

### Likelihood Explanation
Exploitability requires the attacker to possess at least one valid `(raw_body, hmac)` pair signed with the app's `client_secret` for some topic/shop — which is realistic because webhook bodies are often deterministic/predictable (empty bodies, fixed-schema JSON such as `shop/redact`), and the signature never varies with `shop`/`topic`/`webhook_id`. Once obtained, replay with modified headers against the app's public, internet-facing webhook endpoint is trivial and requires no secrets.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the HMAC-verified data, or otherwise cryptographically tie them to the body before use — e.g., include these header values in `to_signable_string`, or independently validate that the `shop` domain matches an active, previously-established session/registration for that specific webhook subscription before invoking the handler. At minimum, `Registry.process` should not treat header-derived `shop`/`topic`/`webhook_id` as trusted context passed to handlers without this binding.

### Proof of Concept
1. Register a handler for topic `customers/redact` with `ShopifyAPI::Webhooks::Registry.add_registration`.
2. Compute `hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, "{}")` — reproducible by anyone who has previously observed one legitimate `{}` -body webhook (or any deterministic payload) for the app.
3. POST to the app's webhook endpoint with headers:
   - `shopify-topic: customers/redact`
   - `shopify-hmac-sha256: Base64.encode64(hmac)`
   - `shopify-shop-domain: victim-shop.myshopify.com` (attacker-chosen, not the shop that ever sent this body)
   - `shopify-webhook-id: forged-id`
   - body `{}`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the secret, then invokes the handler with `shop: "victim-shop.myshopify.com"` even though that shop never sent this request.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
