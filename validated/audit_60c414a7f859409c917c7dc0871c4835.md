### Title
Initialize2 accepts freezable coin/pc mints, letting the pool creator permanently freeze all LP funds - (File: program/src/processor.rs)

### Summary
`Processor::process_initialize2` never validates that the `coin_mint`/`pc_mint` supplied for a new pool are non-freezable SPL mints. Any unprivileged user can create a permissionless pool (`Initialize2`) using a token mint whose `freeze_authority` they control, then later freeze the pool's `coin_vault`/`pc_vault` token account, permanently locking all liquidity providers' deposited funds.

### Finding Description
This is the same "critical argument not validated when whitelisting/creating a config" class described in the external report for `VaultConfig.setVaultConfig`, where currency/vault parameters supplied by the caller are trusted without checking they are safe to use. In Raydium, the analogous unprivileged entry point is `Initialize2`, which lets any caller create a brand-new AMM pool by supplying `amm_coin_mint_info`/`amm_pc_mint_info` and vault accounts.

`process_initialize2` unpacks the mints and vault token accounts and performs several sanity checks — e.g. it verifies the vaults have no delegate/close authority, and that the LP mint has no freeze authority: [1](#0-0) 

However, it never checks the freeze authority of the pool's actual `coin_mint`/`pc_mint` (only the freshly-created `lp_mint` is checked). The vault token accounts are also only checked for `delegate`/`close_authority`, not for whether their underlying mint is freezable: [2](#0-1) 

Because `Initialize2` is permissionless and attacker-chosen mints are accepted as-is, an attacker can create their own SPL mint, set the `freeze_authority` to themselves (or a controlled account), and use it as `coin_mint` or `pc_mint` when calling `Initialize2` to whitelist the pool. Other unrelated users can then deposit into this pool as normal LPs via `Deposit`. At any later point the attacker can invoke the SPL Token program's `FreezeAccount` instruction (using their retained freeze authority) directly on the AMM's `coin_vault`/`pc_vault` token account. Once frozen, all instructions that perform SPL token transfers out of that vault (`Withdraw`, `SwapBaseIn/Out`, `SwapBaseInV2/OutV2`, `WithdrawPnl`) will fail, because the CPI `Invokers::token_transfer` calls into `spl_token::transfer` on a frozen account, which the SPL Token Program rejects.

### Impact Explanation
This results in permanent freezing of LP and swapper funds: once the vault token account is frozen, no depositor can withdraw their proportional coin/pc holdings and no swap can execute against that pool. Since the vaults are owned by the pool's PDA authority (not the attacker), there is no privileged path in the AMM program to unfreeze or migrate out of a frozen vault, making the loss permanent for all liquidity already deposited.

### Likelihood Explanation
`Initialize2` is fully permissionless — any account can call it with attacker-controlled mint/vault arguments in a single transaction. Creating a mint with a freeze authority is trivial and standard SPL Token functionality (no non-default validator/build or off-chain component required). The only extra step is that at least one other user must deposit before the attacker exercises the freeze, but pool-creation-then-luring is a common pattern for scam pools, and the program provides no signal to LPs that the mint is freezable.

### Recommendation
In `process_initialize2`, reject mints where `coin_mint.freeze_authority` or `pc_mint.freeze_authority` is `Some(_)`, mirroring the existing check already applied to `lp_mint.freeze_authority`: [3](#0-2) 

### Proof of Concept
1. Attacker creates SPL mint `M` with `freeze_authority = attacker`.
2. Attacker calls `initialize2` (program/src/instruction.rs `initialize2`) using `M` as `amm_coin_mint`/`amm_pc_mint`, funding the pool with a small initial deposit; `process_initialize2` accepts it because no freeze-authority check exists on `coin_mint`/`pc_mint`. [4](#0-3) 
3. Victim LPs call `Deposit`, transferring real tokens into `amm_coin_vault`/`amm_pc_vault` owned by the pool's PDA authority.
4. Attacker invokes SPL Token `FreezeAccount` on `amm_coin_vault` (or `amm_pc_vault`) using their retained freeze authority over mint `M`.
5. All subsequent `Withdraw`/`SwapBaseIn`/`SwapBaseOut` calls fail at the `Invokers::token_transfer` CPI because the frozen token account rejects transfers, permanently locking victim funds in the vault.
