### Title
Webhook `shop` identity not covered by HMAC signature enables cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body. The `shop-domain` header, which is exposed to app handlers as the authoritative tenant identifier (`WebhookMetadata#shop`), is never included in the HMAC-signed content. This breaks the intended binding `hmac == HMAC(secret, body || shop)` down to `hmac == HMAC(secret, body)`, allowing a genuine, validly-signed webhook payload (obtainable by any merchant/tenant that has installed the app) to be replayed with an attacker-chosen `shop-domain` header and be accepted by the app as if it came from a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) 
`hmac` is read from the `hmac-sha256` header, and `shop` is read independently from the `shop-domain` header. Critically, `to_signable_string` only returns the raw body: [2](#0-1) 

`HmacValidator.validate` computes the signature purely over `to_signable_string` (the body) and compares it to the received `hmac`: [3](#0-2) 

`Registry.process` uses this HMAC check as the sole authentication gate before handing `request.shop` to the app's handler as the trusted tenant identity: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: **the shop attributed to a webhook event == the shop the HMAC-authenticated bytes were generated for**. Here, the equality actually enforced is only **HMAC(body) is valid for *some* shop that installed the app**, while **shop == whatever value the `shop-domain` header claims**, with no cryptographic link between the two. Because `shop` is a plain header value never mixed into `to_signable_string`, any bytes (body + valid HMAC) legitimately produced for shop A can be replayed to the app's webhook endpoint with the `shop-domain` header rewritten to shop B, and `HmacValidator.validate` will still return `true`.

This exactly matches the report's flagged bug class: "a field acted on but not covered by the HMAC" — here the field is the tenant (`shop`) identity used by the host application's handler logic (session lookup, per-shop data operations, GDPR redact/uninstall handling, etc.), while only the body is authenticated.

### Impact Explanation
An attacker who is a legitimate merchant on the platform (i.e., installs the app on their own store, which is a low, unprivileged bar — no special access, no leaked secrets required) can capture genuine webhook deliveries (body + HMAC) that Shopify sends to the app for their own shop, then replay that exact body+HMAC pair to the app's public webhook endpoint with the `shop-domain` header swapped to any other shop's domain that also uses the app. `HmacValidator.validate` still passes because the header isn't part of the signed content, so `Registry.process` dispatches to the app's handler with `WebhookMetadata#shop` set to the victim's domain. Depending on which topics the app subscribes to, this enables cross-tenant impact such as:
- Forcing `app/uninstalled` semantics for a victim shop the attacker doesn't own (denial of service / bogus session teardown).
- Triggering compliance webhooks like `shop/redact` or `customers/redact` against a victim shop, causing the app to delete or alter data belonging to a tenant the attacker does not control.
- Injecting attacker-influenced webhook body content (order/product/customer data) that the app's handler attributes to and processes under the victim shop's identity, corrupting that tenant's data or state.

This is a cross-tenant access/integrity violation stemming purely from this gem's own webhook verification code, satisfying the "cross-tenant access" Critical-impact category defined in scope.

### Likelihood Explanation
Likelihood is meaningful: exploitation requires only that the attacker be able to install the target app on any shop they control (the normal, unprivileged path any merchant can take) and be able to send an HTTP POST to the app's public webhook callback endpoint with custom headers — both trivially available to any internet user without needing `api_secret_key`, tokens, or social engineering. The only constraint is producing/possessing a genuinely Shopify-signed body for *some* shop, which the attacker can always obtain by triggering a topic-appropriate event on their own installed store and capturing Shopify's own webhook delivery.

### Recommendation
Bind the tenant identity into the authenticated bytes so it cannot be swapped independently of the signed payload:
- Include the `shop-domain` (and ideally `webhook-id`/`topic`) header value as part of `to_signable_string`, and have the host app's webhook secret verification recompute HMAC over `shop + topic + body` (this requires a corresponding change in how Shopify signs/or an app-side secondary check).
- At minimum, since this gem cannot change what Shopify signs, the gem should require and document that host applications MUST independently verify that `request.shop` corresponds to a shop that has an active, registered webhook subscription/session for the app (i.e., cross-check the claimed shop against the app's own webhook registration/session store) before trusting `WebhookMetadata#shop`, and this requirement should be enforced or at least surfaced prominently in `Registry.process`/`webhooks.md`, since currently nothing in the gem or its documented usage flags that `shop` is unauthenticated.
- Consider raising `InvalidWebhookError` in `Registry.process` if the topic is a compliance/uninstall topic and the shop cannot be corroborated against a known registration.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and subscribes it (as the app already does) to a webhook topic, e.g. `app/uninstalled` or `shop/redact`.
2. Shopify delivers a legitimate webhook to the app's endpoint with headers including `x-shopify-shop-domain: attacker-shop.myshopify.com` and a valid `x-shopify-hmac-sha256` computed over the raw body using the app's real `client_secret`. The attacker captures this raw body and HMAC value (e.g., via a proxy they control, since it's their own shop's data).
3. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac` reads the (unchanged, still valid) HMAC header, and `to_signable_string` returns only `raw_body`, matching what was signed — so `Utils::HmacValidator.validate(request)` returns `true`: [6](#0-5) 
5. `ShopifyAPI::Webhooks::Registry.process` proceeds and invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: ...)`: [4](#0-3) 
6. The app's handler (following the gem's own documented pattern of trusting `data.shop`) performs shop-scoped actions (e.g., session teardown, data redaction) against `victim-shop.myshopify.com`, even though that shop never sent this webhook.
