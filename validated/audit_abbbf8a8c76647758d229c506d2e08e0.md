### Title
Webhook shop-domain identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, while the `shop` (tenant identifier) used to dispatch and label the event is read from an unauthenticated HTTP header that plays no part in the HMAC computation.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC signature exclusively over `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only `@raw_body`: [1](#0-0) [2](#0-1) 

Meanwhile, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are parsed straight from HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` checks only `Utils::HmacValidator.validate(request)` (i.e., body integrity) before trusting `request.shop` as the tenant identity and forwarding it, unmodified, into `WebhookMetadata`, which is what host applications use to key their per-tenant data/session lookups: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `shop authenticated by HMAC == shop used to route/attribute the event`. Because `to_signable_string` only covers the body, this equality is not enforced — the `shop-domain` header value is a field that is *acted on* (used to select the tenant) but *not covered by the HMAC*, matching the analog pattern of a binding-breaking identity substitution.

### Impact Explanation
An unprivileged actor who legitimately receives a genuine webhook for their own shop (e.g., a merchant installing the app, who is a valid recipient of Shopify webhooks for their own store) can capture a valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a different shop's domain. `HmacValidator.validate` will still pass because it never inspects the header, and `Registry.process` will hand the forged shop identity to the handler. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to select a session/access token or to write into that tenant's data store), this can result in cross-tenant data corruption/misattribution — one tenant's event content being processed and stored under another tenant's identity. This matches the Critical-tier "cross-tenant access" category since the tenant/session boundary that this gem is responsible for establishing (`shop`) is not actually authenticated.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker needs one valid `(body, hmac)` pair, which they can obtain without any secret key simply by being a legitimate recipient of their own shop's webhooks (no `api_secret_key`, TLS interception, or privileged access is required — only normal use of the app as an installed merchant). This is squarely within the "unprivileged internet user" threat model: it does not require guessing the HMAC secret, only reusing a signature that was validly produced for a different, attacker-controlled context (their own shop) but presented with a different claimed shop identity.

### Recommendation
Bind the tenant identity to the signed payload rather than trusting an unauthenticated header:
- Include the `shop` (and ideally `topic`/`webhook_id`) in the HMAC-signed material, or
- Cross-check the `shop-domain` header against a shop identifier embedded in the JSON body (Shopify webhook payloads generally include shop-scoped resource data) before trusting it for routing/tenant attribution, or
- At minimum, document/enforce that host applications must independently verify `WebhookMetadata#shop` against a known/expected value (e.g., the session under which the webhook was registered) before using it to key any data access.

### Proof of Concept
1. Merchant "A" installs the app and receives a legitimate webhook delivery for shop `a.myshopify.com`:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC over BODY>
   x-shopify-shop-domain: a.myshopify.com
   BODY: {"id": 123, ...}
   ```
2. Merchant "A" resends the exact same request to the app's webhook endpoint, only changing the shop header:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same valid HMAC over BODY>
   x-shopify-shop-domain: victim-shop.myshopify.com
   BODY: {"id": 123, ...}
   ```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only validates `BODY` against the HMAC — the `shop-domain` header is never part of the check (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {...}, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) and the host application processes shop A's order data as if it belonged to `victim-shop.myshopify.com`.
