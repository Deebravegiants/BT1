### Title
Unchecked ERC20 `transfer` return value in `IntentGatewayV2.withdraw()` (Tron) can falsely emit `EscrowReleased`/`EscrowRefunded` and desync escrow accounting - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` performs raw low-level `.call` invocations of the ERC20 `transfer` selector and only checks that the call itself did not revert (`success`), never decoding/validating the boolean return value the ERC20 standard requires. This is the same bug class as the referenced report: an unchecked `transferFrom`/`transfer` return value lets the code proceed and emit success events/mutate state even when the underlying token transfer silently failed.

### Finding Description
In `withdraw()`, escrowed order tokens, transaction fees, and dust are all paid out via:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) 
and in the `SweepDust` handling branch of the incoming request processor:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
``` [2](#0-1) 

`success` here only reflects whether the external call reverted at the EVM/TVM level — it does not inspect the ABI-encoded boolean returned by non-reverting-but-failing ERC20 implementations (a widely-deployed pattern, e.g. tokens that return `false` on insufficient balance/allowance instead of reverting). Because the return data is discarded, a token that returns `false` will still report `success == true`, so the code proceeds to:
- decrement `_orders[body.commitment][token] -= amount` as if the transfer succeeded,
- emit `EscrowReleased`/`EscrowRefunded` (fill/refund success events), and
- emit `DustSwept` for the dust-sweep path,

even though the beneficiary never received the tokens.

This directly mirrors the referenced Joyn finding: the return value of `transfer`/`transferFrom` is unchecked, so downstream consumers (indexers, relayers, solvers reading `EscrowReleased`/`EscrowRefunded`/`DustSwept` events, or the on-chain `_orders` mapping) capture an inconsistent state relative to actual token balances.

### Impact Explanation
This function is reached from `IApp` callbacks (`onPostRequest`/`onPostRequestTimeout`/`onGetResponse` paths that call `withdraw(body, ...)`) triggered by any relayed Hyperbridge message with a valid proof — i.e., by any unprivileged relayer delivering a fill, cancellation, or timeout message for an intent order. If the underlying escrowed token is one of the non-reverting-on-failure ERC20s, a filler/solver or the escrow contract itself can end up in a state where:
- The `_orders` accounting is decremented (order marked settled/withdrawn) while the beneficiary received nothing, permanently freezing/losing the escrowed funds for the legitimate recipient, and
- `EscrowReleased`/`EscrowRefunded`/`DustSwept` events falsely signal successful settlement, corrupting off-chain relayer/indexer state and enabling downstream double-accounting or improper release of dependent funds (e.g., relayer fee payout in the same function, which uses the identical unchecked pattern for the fee token transfer).

This constitutes a concrete permanent freezing/loss-of-funds and forged-state-commitment scenario reachable via a single relayed message, meeting High severity.

### Likelihood Explanation
Likelihood is High for tokens with non-reverting failure semantics (returns `false` instead of reverting), which are common among older or non-standard ERC20 tokens likely to be whitelisted for intent-based bridging. Any relayer delivering a `withdraw`-triggering message (fill completion, cancellation, or timeout) with such a token configured as an order asset can trigger the inconsistency without needing special privileges — the call is reachable by the normal, permissionless relaying flow of Hyperbridge intents.

### Recommendation
Decode and require the boolean return value (or use OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the mainline `evm/src/apps/IntentGatewayV2.sol`, which already uses `safeTransferFrom`) for every `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` site in `evm/tron/contracts/apps/IntentGatewayV2.sol`, e.g.:
```solidity
(bool success, bytes memory data) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success || (data.length != 0 && !abi.decode(data, (bool)))) revert TransferFailed();
```
Apply the same fix to the fee-token transfer and the `SweepDust` transfer paths.

### Proof of Concept
1. Configure an intent order whose escrowed input/output token is an ERC20 that returns `false` on transfer failure instead of reverting (common in several legacy/non-standard tokens).
2. Drain the `IntentGatewayV2` contract's balance of that token below the amount recorded in `_orders[commitment][token]` (e.g. via a prior partial sweep, protocol-fee skim, or a race with another withdrawal), OR use a token that returns `false` due to some other condition (e.g. blacklist/pause) while balance still nominally appears sufficient in the mapping.
3. Relay a valid fill/cancel/timeout message causing `withdraw()` to execute for that commitment.
4. `token.call(...)` succeeds (`success == true`) because the token returns `false` rather than reverting; `withdraw()` decrements `_orders[commitment][token]` and emits `EscrowReleased`/`EscrowRefunded` despite the beneficiary receiving zero tokens. [3](#0-2)

                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

        // redeem tx fees
