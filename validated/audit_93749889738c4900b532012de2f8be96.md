### Title
Cross-tenant webhook confusion via unauthenticated `shop`/`topic`/`webhook-id` headers not covered by HMAC - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain`, `topic`, `webhook-id`, and `api-version` values taken directly from unauthenticated HTTP headers and hands them to the app's handler as if they were verified.

### Finding Description
`Registry.process` does: [1](#0-0) 

The only integrity check performed is `Utils::HmacValidator.validate(request)`. That validator computes the signature over `request.to_signable_string`, which is defined as just the raw body: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, none of which are included in `to_signable_string`: [3](#0-2) 

The equality that the code implicitly assumes is:

`bytes verified by HMAC == bytes acted upon for tenant identification (shop)`

but in reality the HMAC only binds the **body**; the `shop`, `topic`, and `webhook_id` headers are free-form and can be set to anything by whoever sends the POST request, as long as they can produce *any* valid `(body, hmac)` pair signed with the app's shared secret.

Any unprivileged user can obtain a legitimate `(body, hmac)` pair for a given app without ever seeing the app's `client_secret`: they simply install the target public app on their own store, and Shopify will deliver a real, correctly-signed webhook to the app's webhook endpoint. Because the header values are not part of the signed content, that same intercepted-or-observed `(body, hmac)` pair can be resent to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic` / `X-Shopify-Webhook-Id`) header rewritten to name a different, victim shop. `HmacValidator.validate` will still pass (the body and hmac still match), and `Registry.process` will hand the handler a `WebhookMetadata` object whose `shop` field falsely claims to be the victim's shop: [4](#0-3) 

Any host application that uses `data.shop` from the handler callback to key its per-tenant logic (look up settings, sync data, trigger tenant-scoped side effects, etc.) will act on the wrong tenant, because the library presents `shop` as if it came from a verified channel, when only the body bytes were actually verified.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce: the `shop` value returned to the host app's webhook handler is not bound to the HMAC that supposedly authenticates the request. An attacker who can install the target app on any store (a normal, unprivileged action available to anyone) can generate an arbitrary number of valid `(body, hmac)` pairs and replay them against a victim shop's identity, producing cross-tenant webhook confusion — the impact category matches "cross-tenant access" for host applications that rely on `WebhookMetadata#shop` as an authenticated tenant identifier.

### Likelihood Explanation
Likelihood is moderate to high: obtaining a signed `(body, hmac)` pair requires no privileged credentials — installing a public app on one's own store is available to any internet user, and webhook delivery is automatic. Replaying the POST with a modified `shop-domain` header requires only basic HTTP tooling, no access token, `client_secret`, or TLS interception. The main constraint is that this depends on host applications trusting `data.shop` without independent cross-checking (e.g. against a known session/shop registry), which is a common pattern the gem's documentation and `WebhookMetadata` API implicitly encourage by exposing `shop` as a first-class, post-"validation" attribute.

### Recommendation
Include the `shop`/`topic`/`webhook_id` (and ideally `api_version`) header values in the HMAC-signed content check, or otherwise cryptographically bind them to the verified body before exposing them via `WebhookMetadata`. At minimum, document prominently that `shop`, `topic`, and `webhook_id` are *not* covered by the HMAC and must be independently cross-validated by the host application against its own known-shop list before being trusted for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`. Shopify delivers a legitimately signed webhook to the app's endpoint:
   - Headers: `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - Body: `{"id": 1, ...}`
2. Attacker captures this `(body, hmac)` pair (e.g., via their own logging/proxy of traffic to their own endpoint — no secret needed).
3. Attacker resends the exact same body and HMAC header to the app's webhook endpoint, but replaces the header:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Request.new` parses this into a request object; `Utils::HmacValidator.validate` succeeds because it only checks the body against the HMAC ( [2](#0-1) , [5](#0-4) ).
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ...)` ( [4](#0-3) ), causing the host app to act as though the (attacker-controlled) payload originated from `victim-shop.myshopify.com`.

        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
