I have enough to finalize the analysis.### Title
Webhook `shop` identity is not covered by the HMAC, allowing cross-tenant attribution of webhook payloads - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook only by validating the HMAC over the raw request body, then forwards the `shop` value taken from an unsigned request header to the app's handler as the tenant identity for that event. The `shop` field is "acted on" (used by every consuming app as the tenant key to look up sessions/records) but it is not part of the HMAC-covered bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` are defined as: [1](#0-0) 

The HMAC (`hmac-sha256` header) is verified only against `@raw_body`. The `shop` attribute, however, is read straight from the `shop-domain` header, which is not included in the signable string at all: [2](#0-1) 

`Registry.process` calls `Utils::HmacValidator.validate(request)` (which only checks the body-derived HMAC) and, if it passes, immediately builds a `WebhookMetadata` using `request.shop` and hands it to the app's `handler.handle`: [3](#0-2) [4](#0-3) 

The documented usage pattern explicitly tells integrators to trust `data.shop` as the tenant identifier to route/attribute the webhook's side effects: [5](#0-4) [6](#0-5) 

The identity binding that should hold is:
`bytes verified by HMAC (raw_body) == bytes used to attribute the event to a tenant (shop-domain header)`

That equality does not hold in this library: the HMAC only binds the body, while `shop` is parsed from a separate, unsigned header and passed on as if it were authenticated. Because every shop that uses the app shares the same `api_secret_key`, a webhook subscriber for shop A can capture one of their own legitimately-signed webhook deliveries (valid body + valid HMAC, both real values sent by Shopify) and resend that exact same body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary value in the `X-Shopify-Shop-Domain` header (e.g., a victim shop's domain). `Utils::HmacValidator.validate` still succeeds, because it never inspects the header, and `Registry.process` forwards the attacker-chosen `shop` value to the handler unmodified.

### Impact Explanation
This breaks tenant isolation ("cross-tenant access") for any app built on the documented pattern: the webhook consumer, following the gem's own documentation, uses `data.shop` to select which merchant's session/record the event applies to (e.g., "sync this order for shop X"). An attacker who is a normal (unprivileged) installer of the app on their own shop can cause the app to apply another merchant's webhook payload attribution to their own or a third shop, or vice versa — without needing the app's `api_secret_key`, an access token, or any privileged access. This matches the Critical category "cross-tenant access" since a boundary between merchants is crossed using only a legitimately-received, replayable webhook.

### Likelihood Explanation
Any app integrator that installs webhook handlers exactly as documented is affected, and the attacker only needs to be a normal merchant who has installed the app (i.e., capable of receiving at least one real webhook for their own shop from Shopify) and can send arbitrary HTTP requests to the app's public webhook endpoint. No secret material, TLS interception, or social engineering is required — only a replay with a modified, unsigned header.

### Recommendation
Do not trust the `shop-domain` header (or any header) as tenant identity unless it is cryptographically bound to the verified bytes. Options:
- Extend `VerifiableQuery`/`Request#to_signable_string` used for webhooks to include the `shop`, `topic`, and `webhook-id` values (canonicalized) in the HMAC-covered payload, or
- Document/emit the raw body's own `shop_domain`/`id` field embedded by Shopify inside the JSON body (which is part of the HMAC-signed bytes) instead of the header value, and have `WebhookMetadata#shop` be derived from body content rather than headers, or
- At minimum, add a documented warning that `data.shop` is not authenticated and must not be used as a tenant key without additional verification (e.g., cross-checking against the webhook subscription owner via a separate authenticated lookup).

### Proof of Concept
1. Attacker installs the target app on their own shop (`attacker.myshopify.com`) and triggers any webhook subscribed by the app (e.g. `orders/create`), receiving a genuine POST from Shopify:
   - Headers: `X-Shopify-Hmac-Sha256: <valid HMAC of body>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`
   - Body: `{"id": 123, ...}`
2. Attacker replays the exact same body and the same `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint, but changes the header to `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged header into `request.shop`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `@raw_body` — unchanged from step 1 — so validation succeeds: [7](#0-6) 
5. The handler is invoked with `WebhookMetadata(shop: "victim.myshopify.com", ...)`, and the app (following the documented pattern) applies the order data to the victim shop's records/session.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
