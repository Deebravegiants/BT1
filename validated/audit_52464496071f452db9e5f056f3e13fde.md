### Title
Webhook `shop-domain` header is trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` only authenticates the raw body bytes against the app's `client_secret` [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers via `shopify_header` [3](#0-2) [4](#0-3) .

`Registry.process` validates the HMAC and then immediately forwards `request.shop` — an unverified header — into `WebhookMetadata`, which is handed to the host application's handler as the tenant identifier for the delivered payload [5](#0-4) . The identity binding broken is: `shop header used to route/attribute webhook data` ≠ `shop bound inside the HMAC-covered bytes`. Unlike the OAuth `AuthQuery`, where `shop` is explicitly included in `to_signable_string` and thus covered by the HMAC [6](#0-5) , the webhook `Request` has no equivalent binding for `shop`.

Because all shops installing the same app share a single `client_secret`, any store owner who has the app installed receives real, validly-HMAC'd webhook deliveries for their own store. An attacker (an unprivileged internet user who merely installed the app on their own shop) can capture one such legitimate `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Utils::HmacValidator.validate` re-derives the signature purely from `raw_body` and the secret, so it still passes [7](#0-6) , and the host app's handler then processes the attacker-controlled payload/body under the victim's shop identity.

### Impact Explanation
This lets an unprivileged attacker who has only installed the app on their own store make the host application believe attacker-controlled webhook data (order data, customer data, `shop/redact` payloads, etc.) belongs to a different, victim tenant, since `data.shop` in `WebhookMetadata` is what apps typically key their per-shop state/session lookups on. This is a cross-tenant data-integrity breach reachable without any credentials beyond installing the app once on a shop the attacker controls.

### Likelihood Explanation
Exploitation only requires the attacker to install the app on any shop they control (or otherwise obtain one valid `(body, hmac)` pair), and to resend the request with a forged `shop-domain` header — no secret material, session, or token is needed, and the gem provides no defense since `to_signable_string` never binds `shop`.

### Recommendation
Extend the webhook signable payload (or a secondary check) to bind the `shop-domain` header value into the HMAC-covered material, or otherwise verify the claimed shop against server-side state (e.g., that an active session/installation exists for that shop) before dispatching to the handler, mirroring how `AuthQuery#to_signable_string` binds `shop` for OAuth in `lib/shopify_api/auth/oauth/auth_query.rb`.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; trigger any webhook (e.g. `orders/create`) and capture the raw body and the `X-Shopify-Hmac-Sha256` header Shopify sends — this HMAC is valid because `HmacValidator` only signs `raw_body` [1](#0-0) .
2. Replay the exact same body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` [8](#0-7) .
4. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` using the forged header and dispatches it to the handler as if it originated from `victim-shop.myshopify.com` [9](#0-8) .
