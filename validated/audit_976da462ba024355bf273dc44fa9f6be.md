Confirmed: `Webhooks::Request#hmac` is computed over the raw body only, via `to_signable_string` returning `@raw_body` [1](#0-0) , while `shop` is read directly and unauthenticated from the `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `Registry.process` validates only this body-based HMAC and then forwards `request.shop` straight into the handler's `WebhookMetadata` [3](#0-2) .

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant shop-attribution spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC computed over the raw request body [4](#0-3) . The `shop` value passed to the app's handler is taken from an HTTP header that is never included in that HMAC computation [2](#0-1) [1](#0-0) . This breaks the identity binding `shop authenticated == shop acted upon`.

### Finding Description
`Webhooks::Request` includes `Utils::VerifiableQuery` and defines `to_signable_string` to return only `@raw_body` [1](#0-0) . `HmacValidator.validate_signature` computes the expected HMAC exclusively over that signable string and secure-compares it against the `hmac` header value [5](#0-4) . Meanwhile, `shop` is read verbatim, unauthenticated, from the `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) .

`Registry.process` uses this unauthenticated `shop` value directly to build `WebhookMetadata` passed to the app-supplied handler, which typically uses `data.shop` to look up per-tenant session/state and process the payload for that shop [6](#0-5) ; this matches the documented handler contract (`data.shop`) [7](#0-6) .

Because the same `api_secret_key` is shared by the app across every merchant/tenant that installed it, and only the raw body is HMAC'd, any tenant who has installed the app can capture one of their own genuine, validly-signed webhook deliveries (body + HMAC) and replay it to the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim tenant's shop domain. `HmacValidator.validate` still returns `true` because the signature check never touched the header, so `Registry.process` proceeds and calls the handler with `shop` set to the victim's domain while `body` is fully attacker-controlled.

### Impact Explanation
This is a cross-tenant identity-binding break: the shop that was cryptographically authenticated (i.e., "some shop belonging to this app installation, whichever one produced this HMAC") is not the shop attributed to and acted upon by the handler. Depending on how the host application's webhook handler uses `data.shop` (e.g., updating per-shop database records, cache invalidation, triggering per-shop business logic), an attacker-controlled shop tenant can inject attacker-controlled webhook bodies attributed to a victim shop, corrupting or manipulating that victim's data/state — a cross-tenant access/integrity impact.

### Likelihood Explanation
Exploitability requires only that the attacker be a legitimate (even trial) installer of the app — no privileged credentials, no access to `api_secret_key`, and no other credential are needed. They only need to capture one webhook delivery Shopify sends to their own endpoint (trivial, since they control that endpoint) and replay it with a modified header, which is entirely within reach of an "unprivileged internet user" who is simply an app tenant.

### Recommendation
Bind the shop domain (and other identity fields like topic/webhook-id) into the signed material, or otherwise authenticate the `shop` header against the actual signing tenant. Since Shopify signs only the body by design, the gem should additionally verify that the shop domain in the header corresponds to a shop for which this app instance is registered/expected (e.g., cross-check against a known, previously-established session for that shop) before trusting `request.shop`, rather than passing it through unauthenticated into `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and lets it register the `orders/create` webhook.
2. Shopify sends a webhook to the app: body `B`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, header `x-shopify-hmac-sha256: HMAC(secret, B)`.
3. Attacker captures this request (they control the receiving endpoint/logs).
4. Attacker crafts body `B'` — actually attacker can't forge `HMAC(secret, B')`, so they must replay the same `B` (fully attacker-controlled since `orders/create` payload is generated from an order attacker created), but resend it with header `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` (over raw body only, per `to_signable_string`) and it matches the original signature, so validation passes [8](#0-7) .
6. `Registry.process` calls the app's handler with `data.shop == "victim-shop.myshopify.com"` and `data.body == B` (attacker-controlled), even though the request never actually originated from Shopify for `victim-shop` [9](#0-8) .
