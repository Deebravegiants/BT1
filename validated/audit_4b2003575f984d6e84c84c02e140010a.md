## Finding

### Title
Webhook shop identity spoofing via HMAC that only covers the request body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC signature validated by `HmacValidator` never covers the `shop-domain`, `topic`, `api-version`, or `webhook-id` headers. [1](#0-0)  `Registry.process` still trusts `request.shop` as the authoritative merchant identity when dispatching to the handler, after only checking that the HMAC (body-only) is valid. [2](#0-1) 

### Finding Description
The binding that should hold is: `shop authenticated by HMAC == shop delivered to the handler`. In reality, `HmacValidator.validate` only checks the HMAC against `verifiable_query.to_signable_string`, which for a webhook `Request` is just `@raw_body`. [3](#0-2) [1](#0-0)  The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers with no cryptographic binding to the signature. [4](#0-3) 

Because the signature is only a function of the body, any request that has an unchanged body and a valid signature will pass `Utils::HmacValidator.validate(request)` in `Registry.process` regardless of what the `shop-domain` (or other) headers say. [2](#0-1)  The handler is then invoked with `shop: request.shop` taken directly from the attacker-controlled header, with no re-validation that this shop matches the tenant the signature was actually produced for. [5](#0-4) 

An attacker who legitimately installs the app on their own shop (Shop A) receives real, validly-signed webhook deliveries. They can capture one such delivery (valid signature + body) and resend the exact same raw body/signature to the app's webhook endpoint while changing only the `X-Shopify-Shop-Domain` header to Shop B (a victim tenant). The signature check still passes because the body is untouched, and the host application's webhook handler (built per this gem's documented `WebhookMetadata#shop`) will process the event as if it originated from Shop B.

### Impact Explanation
This breaks the tenant-identity binding between "the merchant whose secret validated this delivery" and "the merchant the app acts on behalf of," enabling cross-tenant data confusion/injection: a host app that uses `WebhookMetadata#shop` to look up a shop's session/data (e.g., to update or delete resources, or to treat the event as originating from the victim shop) can be manipulated into acting on data associated with the wrong tenant using a payload the attacker fully controls (their own webhook body) but with the target's identity. This matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
No access to `api_secret_key`, access tokens, or privileged credentials is required. An attacker only needs to install the app on any shop (a normal, low-privilege merchant action) to receive their own signed webhook, then replay the same body with a rewritten `shop-domain` header at the app's public webhook endpoint. This is a straightforward request-replay from an otherwise-unprivileged internet-facing actor.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the signable string that `HmacValidator` verifies, so the signature cryptographically binds the identity fields the handler consumes — not just the body. Alternatively, require host applications to independently verify that `request.shop` corresponds to a shop with an active, known installation before trusting it, and document that `shop-domain` is currently unauthenticated by the HMAC check.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; capture a legitimate webhook POST, e.g. `orders/create`, with headers `X-Shopify-Hmac-Sha256: <valid>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, and raw body `B`.
2. Resend the identical body `B` and identical `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) only — validation succeeds. [6](#0-5) 
4. The handler is invoked with `shop: request.shop` = `"victim-shop.myshopify.com"`, even though the signature was never produced for that shop. [5](#0-4)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
