### Title
Escrow withdrawal reverts on subtraction underflow when the requested amount exceeds the recorded escrow, permanently freezing funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The reported bug class is an unchecked subtraction (`spentAmount -= amount`) that underflows and reverts whenever `amount` exceeds the tracked value, permanently blocking the function that performs it. The same pattern exists in the Tron `IntentGatewayV2.sol` escrow-release path: `withdraw()` only checks that the per-token escrow balance is non-zero, not that it is greater than or equal to the amount being released, before doing `_orders[body.commitment][token] -= amount`.

### Finding Description
`withdraw()` iterates over `body.tokens` from a `WithdrawalRequest` (delivered either locally via `onGetResponse`/cross-chain cancellation or remotely via `onAccept` on a `RedeemEscrow`/`RefundEscrow` message) and does: [1](#0-0) 

```solidity
for (uint256 i; i < len;) {
    address token = address(uint160(uint256(body.tokens[i].token)));
    uint256 amount = body.tokens[i].amount;
    if (_orders[body.commitment][token] == 0) revert UnknownOrder();
    ...
    _orders[body.commitment][token] -= amount;
    ...
}
```

The guard only rejects the case where escrow is exactly `0`; it never checks `_orders[body.commitment][token] >= amount`. If, for any reason, the amount encoded in the `WithdrawalRequest` (constructed on the *other* chain, from `order.inputs`, and delivered across Hyperbridge as an ISMP message) is larger than what is actually escrowed on this chain for that commitment/token — e.g. due to a mismatch between the escrowed (fee-reduced) amount recorded at `placeOrder` and the raw `order.inputs` amount echoed back in the cross-chain `RedeemEscrow`/`RefundEscrow` body, or any other accounting drift between the two legs of a cross-chain order — the subtraction underflows in Solidity 0.8's checked-arithmetic mode and reverts the entire transaction. This mirrors exactly the `GenericRouter.sol` root cause: a subtraction of an externally-influenced "amount" from an internally-tracked balance, with only a non-zero check instead of a sufficiency check.

For comparison, the newer `IntentsBase.sol` used by the main EVM `IntentGatewayV2` implementation has the identical pattern (`escrowed - amount` with only `escrowed == 0` checked): [2](#0-1) 

### Impact Explanation
Because `_filled[body.commitment]` is set to the beneficiary *before* the loop that can revert, and the whole `onAccept`/`onGetResponse` call reverts atomically if the subtraction underflows, a relayer cannot successfully deliver the settlement message. The escrowed input tokens for that order become permanently unretrievable: they cannot be redeemed by the solver (RedeemEscrow) nor refunded to the user (RefundEscrow), and there is no other function that can force-write `_orders[...]` down. This is a permanent freezing of user/solver funds in the escrow — a High-severity impact matching the "reachable path unable to deliver messages / permanent freezing of funds" criteria.

### Likelihood Explanation
Triggering requires only that the amount encoded by the counterpart chain's `WithdrawalRequest` construction disagree with what was actually escrowed for the commitment/token pair on this chain — a bookkeeping/rounding mismatch condition rather than a privileged action, and reachable through the normal cross-chain fill/cancel flow that any solver or user (an unprivileged actor) exercises by placing/filling/cancelling an order and having the relayer deliver the resulting ISMP message. No admin or governance action is required; the only guard in the code is `escrowed == 0`, so any positive discrepancy trips the underflow. Likelihood is Medium: it depends on the two legs of a cross-chain order momentarily diverging in tracked-vs-declared amount (e.g., fee-on-transfer tokens, protocol-fee-reduction bookkeeping asymmetries, or partial-fill accounting edge cases), which the codebase elsewhere explicitly acknowledges as a risk class (see the fee-on-transfer handling added in `IntentGatewayV2.sol`/`IntentGatewayV2SameChainTest.sol` for the main EVM implementation) but which the Tron contract's `withdraw()` does not defend against with a sufficiency check.

### Recommendation
Replace the `== 0` check with a full sufficiency check before subtracting, e.g.:
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed < amount) revert UnknownOrder(); // or a dedicated InsufficientEscrow error
_orders[body.commitment][token] = escrowed - amount;
```
Apply the same fix to the analogous `_withdraw` function in `IntentsBase.sol` (`escrowed == 0` check at line 462) so both are hardened symmetrically. Additionally, audit all call sites that build a `WithdrawalRequest.tokens[].amount` to guarantee it can never exceed the escrow amount actually recorded on the settling chain (i.e., cross-chain messages should carry the fee-reduced/escrowed amount, not the raw declared `order.inputs` amount, if those can differ).

### Proof of Concept
Conceptual PoC (cannot be executed without local tooling access, but the code path is deterministic):
1. Place a cross-chain order on the Tron-deployed `IntentGatewayV2` where the escrowed amount recorded for a token (`_orders[commitment][token]`) is reduced relative to the raw `order.inputs[i].amount` used to build the `WithdrawalRequest` (e.g., via a protocol-fee deduction or fee-on-transfer token whose actual received/escrowed amount is less than the nominal order amount — a scenario the codebase's own tests demonstrate exists on the main EVM implementation, see `IntentGatewayV2SameChainTest.sol` FeeOnTransferToken tests).
2. Fill the order cross-chain; the destination gateway dispatches a `RedeemEscrow` `WithdrawalRequest` carrying the raw (larger) amount.
3. The relayer delivers the message to the source-chain `IntentGatewayV2.onAccept`, which calls `withdraw()`.
4. `_orders[body.commitment][token]` (the smaller, escrowed value) is non-zero, so the `== 0` guard passes, but `_orders[body.commitment][token] -= amount` underflows because `amount` (the larger, declared value) exceeds it, reverting the transaction.
5. The relayer cannot re-deliver a different amount (the message content is fixed by the source dispatch), so the order permanently cannot settle, and the escrowed tokens are stuck. [3](#0-2)

```text
    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
```
