### Title
Username Enumeration via Inconsistent Authentication Failure Delay in `/sessions` Login Endpoint - (File: `core/sessions/localauth/orm.go`)

### Summary
The `CreateSession` login flow used by the unauthenticated `/sessions` HTTP endpoint performs a fast-failing database lookup for the supplied email before ever running the (deliberately slow) bcrypt password comparison. An attacker probing arbitrary emails against this endpoint can distinguish "no such user" (fast SQL-only failure) from "user exists, wrong password" (slow failure, because bcrypt hashing/comparison is invoked) purely by response timing — the same bug class as CVE-2019-12953 (Dropbear's inconsistent failure delay revealing valid usernames).

### Finding Description
`orm.CreateSession` first calls `o.FindUser(ctx, sr.Email)`, which is a single indexed SQL `SELECT` (`core/sessions/localauth/orm.go:145-148`, `core/sessions/localauth/orm.go:55-59`). If no row matches, the function returns immediately with an error — this path only costs a database round trip. [1](#0-0) [2](#0-1) 

If the email does exist, execution continues to `utils.CheckPasswordHash(sr.Password, string(user.HashedPassword))`, which is backed by `golang.org/x/crypto/bcrypt` (imported in `core/utils/utils.go`). Bcrypt is intentionally computationally expensive (adaptive cost factor), so this comparison takes orders of magnitude longer than the initial SQL lookup. [3](#0-2) [4](#0-3) 

The same pattern is duplicated in the other pluggable authentication providers' local-admin fallback paths — `ldapAuthenticator.localLoginFallback` and `oidcAuthenticator.localLoginFallback` — both of which do a cheap DB lookup first and only invoke `utils.CheckPasswordHash` (bcrypt) if a row is found. [5](#0-4) [6](#0-5) 

The `/sessions` route is reachable by any unauthenticated client sending `{"email":..., "password":...}` (as exercised in `TestSessionsController_Create`), making this attacker-observable without any credentials. [7](#0-6) 

### Impact Explanation
An unauthenticated network attacker can enumerate valid node-operator/admin email addresses by measuring response latency on repeated login attempts. Confirmed valid usernames materially narrow the attack surface for subsequent credential-stuffing, phishing, or brute-force attacks against the Chainlink node's admin/API-user accounts (which control job configuration and, transitively, funds/keys). This matches CVSS 3.1 vector `AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N` (low confidentiality impact, no integrity/availability impact) — consistent with the referenced CVE's medium severity.

### Likelihood Explanation
The `/sessions` endpoint is a standard, always-present, unauthenticated HTTP endpoint on the node's operator API; no special network position or privileges are required. Timing side channels of this magnitude (bcrypt hash computation vs. a single indexed SQL lookup) are typically on the order of tens to hundreds of milliseconds and are reliably distinguishable with a modest number of samples over a network, even accounting for jitter.

### Recommendation
Ensure the failure-path timing is independent of whether the email exists:
- Always perform a bcrypt-equivalent comparison (e.g., against a fixed dummy hash) when the user lookup fails, so the "user not found" and "wrong password" code paths take comparable time.
- Alternatively, unify both checks behind a single constant-time-equivalent function that always executes the expensive hash comparison step regardless of lookup outcome.
- Apply the same fix consistently to `orm.CreateSession` (`core/sessions/localauth/orm.go`), `ldapAuthenticator.localLoginFallback` (`core/sessions/ldapauth/ldap.go`), and `oidcAuthenticator.localLoginFallback` (`core/sessions/oidcauth/oidc.go`).

### Proof of Concept
1. Send `POST /sessions` with `{"email":"definitely-not-a-real-user@test.net","password":"x"}` and measure response time — this returns fast because `FindUser`/`localLoginFallback` fails on the SQL lookup before any bcrypt call.
2. Send `POST /sessions` with `{"email":"<valid-admin-email>","password":"wrong-password"}` and measure response time — this is measurably slower because `utils.CheckPasswordHash` performs a bcrypt comparison.
3. Repeating this against a list of candidate emails allows an attacker to statistically distinguish existing accounts from non-existing ones based on the timing delta, as illustrated by the test cases in `TestSessionsController_Create` (`{"incorrect pwd", user.Email, "incorrect", false}` vs `{"incorrect email", "incorrect@test.net", cltest.Password, false}`), both of which currently return generic errors but with different underlying computation cost.
