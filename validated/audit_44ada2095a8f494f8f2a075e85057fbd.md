### Title
Webhook `shop-domain`, `topic`, `webhook-id` and `api-version` are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC signature computed and checked by `Utils::HmacValidator` covers the payload bytes but not the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, or `shopify-api-version` headers. `Registry.process` trusts these unauthenticated header values verbatim when dispatching to the host application's handler.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via: [1](#0-0) 

The HMAC check calls `Utils::HmacValidator.validate(request)`, which in turn calls `request.to_signable_string` to build the string that is HMAC-signed with the app's shared `api_secret_key`: [2](#0-1) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` is defined as just the raw body — it does not include `shop`, `topic`, `webhook_id`, or `api_version`, all of which are pulled straight from client-supplied HTTP headers instead: [3](#0-2) 

Consequently the identity binding the library implicitly claims — "the HMAC-authenticated request equals the shop/topic/webhook it is dispatched for" — does not hold: `HMAC(body) == HMAC(body)` is verified, but `shop_header == actual_originating_shop` is never checked. Because the shared app secret (`api_secret_key`) is the same for every shop/merchant that installs the app, any merchant who has legitimately received one authentic webhook delivery (a valid `(raw_body, hmac)` pair for their own shop and one topic) can resubmit that exact body and HMAC to the app's webhook endpoint while substituting arbitrary values for the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, and `shopify-api-version` headers. `Utils::HmacValidator.validate` still returns `true` because it only re-derives the HMAC over `@raw_body`, and `Registry.process` then hands the forged `shop`, unmodified `parsed_body`, and forged `topic`/`webhook_id`/`api_version` straight to the host application's handler as authoritative metadata: [1](#0-0) 

This lets an unprivileged merchant of shop A impersonate shop B (or any other topic) to the app's own webhook-handling logic, which typically uses `shop` to select the tenant record/session to mutate (e.g. uninstall processing, GDPR data-erasure webhooks, order/customer data webhooks) — a cross-tenant confused-deputy condition entirely inside this gem's `Utils::HmacValidator` / `Webhooks::Request` design.

### Impact Explanation
This is a cross-tenant identity-binding break: the app trusts `shop`/`topic` values that were never covered by the cryptographic authenticity check. Depending on how the host app's webhook handlers key off `shop`/`topic` (uninstall cleanup, GDPR redact/erase, order cancellation, etc.), a malicious merchant can trigger tenant-B-scoped side effects using only a webhook payload legitimately delivered to their own tenant A — satisfying the "Critical: cross-tenant access" bar defined in scope.

### Likelihood Explanation
Exploitation requires only: (1) being a legitimate, unprivileged merchant who has installed the app (so they naturally receive at least one authentic webhook `(body, hmac)` pair for their own shop), and (2) the ability to POST an HTTP request with attacker-chosen headers to the app's public webhook endpoint. No access to `api_secret_key`, access tokens, or any privileged account is required — this fits squarely in the analog rules (no secret/credential needed, only the shared HMAC key which is never disclosed to the attacker).

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` (i.e., all attacker/host-supplied identity fields the handler will act upon) in the HMAC-signed material, or otherwise cryptographically bind them (e.g., HMAC over `headers + body` rather than body alone), so that tampering with any of these fields invalidates the signature.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com`; capture one legitimate webhook delivery, e.g. `orders/create`, yielding `raw_body = B` and header `shopify-hmac-sha256 = H` (valid because `H = HMAC(api_secret_key, B)`).
2. Replay to the same endpoint with the same body `B` and same header `shopify-hmac-sha256: H`, but set:
   - `shopify-shop-domain: victim-shop.myshopify.com`
   - `shopify-topic: customers/redact` (or any other registered topic for which `B`'s JSON shape happens to satisfy the handler, or simply target a topic whose handler only inspects `shop`)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and matches `H` — validation succeeds despite the forged `shop`/`topic` headers.
4. The registered handler is invoked with `WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the host app to perform victim-shop-scoped actions triggered by the attacker.
