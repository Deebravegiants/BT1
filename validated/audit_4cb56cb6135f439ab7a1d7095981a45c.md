### Title
Checks-Effects-Interactions violation in `withdraw()` allows double-payout of escrowed order funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The reported `releaseTokens` bug class is fundamentally about a token-distribution function that moves value out to a beneficiary without first durably updating the accounting state that prevents a repeat payout (no `withdrawnTokens` increment before transfer). The same anti-pattern exists in `IntentGatewayV2.withdraw()` on the Tron contracts: escrowed tokens are transferred to the beneficiary via a raw external call *before* the internal `_orders` escrow-accounting mapping is decremented, reachable from a relayed cross-chain proof (`onAccept`/`onGetResponse`).

### Finding Description
`withdraw()` is the internal function that redeems escrowed order funds for either a fill (`RedeemEscrow`) or a cancellation/timeout (`RefundEscrow`). For every token in the withdrawal body it:

1. Checks `_orders[body.commitment][token] == 0` (guard against unknown order),
2. Performs the external transfer (native `.call{value}` or ERC20 `token.call(transfer(...))`),
3. **Only afterwards** decrements `_orders[body.commitment][token] -= amount`. [1](#0-0) 

This is invoked by `onAccept` for `RedeemEscrow`/`RefundEscrow` kinds and by `onGetResponse` on a verified GET response, both gated only by `onlyHost`, i.e., triggered purely by relayed/verified cross-chain messages — exactly the kind of "relayed proof" entrypoint in scope: [2](#0-1) [3](#0-2) 

Because `order.inputs` (the escrowed token list) is fully attacker-controlled at `placeOrder` time, a user can escrow a malicious/callback-bearing ERC20 as the input token. When that token's `transfer()` hook executes during step 2 above, `_orders[body.commitment][token]` still holds its pre-decrement (non-zero) value. If a second independently-valid delivery for the same order commitment can be triggered in that reentrant window — e.g. a solver's `RedeemEscrow` fill and the user's own `RefundEscrow` cancellation, both of which can be legitimately dispatched and proven against the same `commitment` under real-world races between fill and cancel — the second delivery's `_orders[commitment][token] == 0` check still passes and the same escrowed balance is paid out a second time, before the first call's decrement lands.

This mirrors the report's core defect class 1:1: value is released to a party while the ledger entry that should prevent a repeat/duplicate release has not yet been committed.

### Impact Explanation
A successful double-delivery drains escrowed order funds beyond what was ever deposited for that commitment — i.e., concrete theft/loss of funds from the `IntentGatewayV2` escrow, paid to whichever party can arrange the race (solver vs. canceller), at the expense of the protocol's solvency for other, unrelated escrowed orders sharing the same token balance.

### Likelihood Explanation
Reachability only requires: (1) placing an order with an attacker-controlled/malicious ERC20 input token (fully permissionless via `placeOrder`), and (2) getting two independently-provable messages referencing the same order commitment delivered in close succession (fill vs. cancel race, or a relayer submitting both proofs back-to-back via `batchCall`). No admin, governance, or node compromise is required — this is exploitable by a normal user/solver interacting with the public contract functions and standard ISMP proof delivery flow, consistent with the "unprivileged... relayer/token bridger/intent solver" reachability requirement.

### Recommendation
Apply checks-effects-interactions: decrement `_orders[body.commitment][token]` (and delete/zero the transaction-fee entry) *before* performing the external token/native transfer, mirroring the pattern already used correctly in the newer `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` (state is updated prior to `_sendValue`/`safeTransfer`): [4](#0-3) 

Additionally, replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern with OpenZeppelin's `SafeERC20.safeTransfer`, which both reduces reentrancy surface (standard, audited call) and correctly reverts on non-compliant tokens that return `false` instead of reverting.

### Proof of Concept
1. Attacker deploys a malicious ERC20 `M` whose `transfer()` implementation, when called with a specific counterparty, re-enters the host's handler to deliver a second already-verified message referencing the same order `commitment`.
2. Attacker calls `placeOrder` on the source chain escrowing `M` as `order.inputs[0]`.
3. A solver fills the order; the fill flow ultimately produces a valid `RedeemEscrow` (or `GET` response) message provable against `IntentGatewayV2` on the source chain, and — in a race — the attacker also obtains a valid `RefundEscrow` proof for the same commitment (e.g., by cancelling right at expiry, or via any two independently provable requests touching the same commitment).
4. Relayer delivers the first message; `withdraw()` reaches the `M.transfer(beneficiary, amount)` call before decrementing `_orders[commitment][M]`.
5. `M.transfer()`'s hook calls back into `HandlerV2`/host to deliver the second, distinct, already-proven message for the same commitment; because `_orders[commitment][M]` has not yet been decremented, the check `_orders[body.commitment][token] == 0` passes again and a second transfer of `amount` is issued.
6. Net effect: `2 * amount` of token `M`'s escrow accounting is paid out for a single `amount` actually deposited, at the expense of the shared token pool backing other orders.

Note: full confirmation of the reentrant "second distinct message" precondition (i.e., that `EvmHost`/`dispatchIncoming` do not pre-mark receipts before invoking `onAccept` for *every* leaf in a manner that would block this) could not be independently verified within the scope of the available context; the checks-effects-interactions violation itself, however, is definitively present in the code as cited.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

                ++i;
            }
        }
