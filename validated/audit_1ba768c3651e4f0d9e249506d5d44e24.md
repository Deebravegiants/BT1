### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` fields are trusted for tenant identification but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` field, along with `topic`, `webhook_id`, and `api_version`, directly from unauthenticated HTTP headers, while the HMAC signature verified by `Registry.process` only covers the raw request body. This breaks the intended binding `verified_bytes == acted_on_bytes`: the bytes cryptographically verified (body only) are not the bytes the host application relies on to attribute the webhook to a shop (the `shopify-shop-domain` header).

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers, none of which participate in the HMAC computation: [2](#0-1) 

`Registry.process` validates the HMAC over the request (i.e., over `raw_body` only via `HmacValidator.validate`) and then unconditionally forwards `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` to the app's handler as trusted metadata: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` compute and compare the HMAC solely against `verifiable_query.to_signable_string`, i.e. the body: [4](#0-3) 

The resulting `WebhookMetadata` struct — which the host application uses to route data to the correct tenant — carries `shop` as a plain, unverified `String`: [5](#0-4) 

This is the same bug class as the referenced report: a value that is *acted on* (here, `shop`, used to attribute the payload to a merchant/tenant) is not part of the data set that is *cryptographically verified* (here, only the raw body bytes). The equality that should hold is:

`hmac_verified_bytes == identity_binding_bytes (shop, topic, webhook_id)`

but in this gem it reduces to:

`hmac_verified_bytes == raw_body` while `identity_binding_bytes` (headers) are attacker-controlled and never checked.

### Impact Explanation
An attacker who can install the app on a shop they control (any unprivileged internet user can create a Shopify development/trial store and install a public app) legitimately receives genuine, correctly HMAC-signed webhook deliveries for events they trigger on their own store. Because the signature covers only the body, the attacker can replay that body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`, `x-shopify-api-version`) headers with values referencing a different shop. `HmacValidator.validate` still succeeds (the body and the secret are both correct), so `Registry.process` calls the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain and `parsed_body` derived from the attacker's own controlled event data. Any host application that uses `data.shop` from this gem to key per-tenant storage, invalidate caches, trigger tenant-scoped side effects, or attribute customer PII/redaction requests (e.g. `customers/redact`, `customers/data_request`, `shop/redact`) will process attacker-supplied data under a victim's tenant identity — a cross-tenant identity confusion enabled entirely within this gem's webhook-processing surface.

### Likelihood Explanation
Likelihood is moderate to high: the required capability is only an unprivileged Shopify Partner/developer account able to install the target public app on a self-owned store and capture one legitimately delivered webhook, then replay it with modified headers to the app's public webhook callback URL. No access to `client_secret`, tokens, or the target shop is required. The only mitigating factor is that this class of attack is only exploitable through the host application's own use of `data.shop`; still, the gem's `Registry`/`Request`/`HmacValidator` are the component that should have bound the identity fields to the signature and does not.

### Recommendation
- Include the `shop`, `topic`, and `webhook_id` header values in the signable content that `HmacValidator` verifies (or otherwise cryptographically bind them to the signed payload), not just the raw body.
- Alternatively, have `Registry.process` independently authenticate `request.shop` (e.g., cross-checking it against a value embedded in and covered by the signed body, or against session/installation records) before constructing `WebhookMetadata`, rather than trusting the raw header.
- Document clearly for consumers of `WebhookMetadata#shop` that, as currently implemented, this value is unauthenticated header data and must not be used as the sole tenant key without additional verification.

### Proof of Concept
1. Attacker creates their own Shopify development store `attacker-shop.myshopify.com` and installs the target public app (any unprivileged Shopify user can do this).
2. Attacker triggers an event on their own store (e.g., updates a product) so Shopify sends a legitimately HMAC-signed `products/update` webhook to the app's registered callback URL, with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
3. Attacker intercepts/replays this same request to the app's webhook endpoint but changes the header `x-shopify-shop-domain` from `attacker-shop.myshopify.com` to `victim-shop.myshopify.com` (and optionally other headers), leaving the body `B` and the HMAC header untouched.
4. `HmacValidator.validate` recomputes `HMAC(secret, B)` — which still matches, because verification never depends on the `shop` header: [6](#0-5) 
5. `Registry.process` passes validation and invokes the host handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)`: [7](#0-6) 
6. The host application processes attacker-controlled data `B` as if it originated from `victim-shop.myshopify.com`, corrupting tenant-scoped state or triggering tenant-scoped side effects for a shop the attacker does not control.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
