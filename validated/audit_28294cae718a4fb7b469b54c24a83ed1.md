### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, allowing cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content from the raw request body only, while the `shop` (tenant identifier), `topic`, `api-version`, and `webhook-id` are all read from unauthenticated HTTP headers. `Registry.process` trusts these header-derived values to build the `WebhookMetadata` handed to the app's handler, even though only the body is bound to the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight from HTTP headers with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (the body) and compares it against `verifiable_query.hmac` — it never folds `shop` into the signed material: [3](#0-2) [4](#0-3) 

The equality the code implicitly assumes is: `shop_header == shop_that_produced(hmac_over_body)`. In reality the HMAC only proves `hmac == HMAC(secret, raw_body)`; it says nothing about which shop the body belongs to. Since a single app uses one `client_secret` (and thus one HMAC key) across every installed shop, any tenant of the app can capture one of their own legitimately-delivered webhooks (valid `body` + valid `hmac`, both readable from their own inbound traffic) and replay that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a different, victim shop. `HmacValidator.validate` will still succeed because it only checks the body against the hmac, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop: [5](#0-4) 

This is the same bug class as the reported vesting issue: a downstream consumer (webhook handler / vesting listing) trusts a value (`shop` / `stepsClaimed`) that "rides along" with data whose integrity was verified for a different, unbound field (`raw_body` / `totalAmount`), letting an attacker who controls one instance of that value contaminate another tenant's processing.

### Impact Explanation
If an app's webhook handler uses `WebhookMetadata#shop` to select which merchant/tenant record to update (a very common pattern), an attacker with their own legitimate shop installation can trigger the handler with a forged `shop` value pointing at any other shop using the same app, causing cross-tenant data corruption or state changes attributed to a shop the attacker doesn't control. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
The attacker only needs to be a normal, unprivileged installer of the app on their own shop (no access token, no `client_secret`, no TLS interception of anyone else's traffic — only their own legitimately received webhook). The endpoint is public by design (Shopify must be able to reach it over the internet), so replaying a captured request with a modified header is straightforward.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-signed material, or otherwise cryptographically bind the header-derived tenant identity to the verified body (e.g., require the handler to cross-check `shop` against a separately-verified value, or document/enforce that `shop` must never be trusted for authorization decisions without additional verification such as IP allow-listing).

### Proof of Concept
1. Install the app on shop A (attacker-controlled) and capture a legitimate webhook POST it receives at its callback endpoint, noting the raw body and the `X-Shopify-Hmac-Sha256` header value.
2. Re-send an HTTP POST to the same webhook endpoint with the identical raw body and `X-Shopify-Hmac-Sha256` header, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over the (unchanged) body and matches the (unchanged) header — validation passes.
4. The handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)`, believing the (attacker-supplied) payload belongs to the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
