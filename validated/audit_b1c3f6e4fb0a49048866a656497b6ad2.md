### Title
Webhook `shop` field is trusted tenant identity that is not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw body only, while the `shop` value that the gem hands to app handlers as the authoritative tenant identifier is read from an unauthenticated HTTP header. This mirrors the reported bug class: the value that is cryptographically verified (the body) is not the same value that is trusted for identity/tenant binding (the `shop` header), analogous to a mapping keyed on the wrong field.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic tie to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC of the body via `Utils::HmacValidator.validate(request)`, then immediately constructs `WebhookMetadata` using the unauthenticated `request.shop` value and hands it to the app's handler as trusted tenant context: [3](#0-2) 

The `HmacValidator` itself only compares `verifiable_query.to_signable_string` (the body) against the HMAC, never binding the `shop` field into that comparison: [4](#0-3) 

The gem's own documentation instructs developers to treat `data.shop` as the trusted shop identity coming out of a "validated" webhook, with no caveat that it is unsigned: [5](#0-4) [6](#0-5) 

Because Shopify apps share a single `client_secret` (`Context.api_secret_key`) across every shop that installs the app, any shop that installs the app receives genuinely signed webhooks for its own events using that same shared secret. An attacker who installs the app on their own (freely creatable) development/test shop can capture a legitimate `(raw_body, hmac)` pair for their own shop, then POST that exact `raw_body` and `hmac-sha256` header to the app's webhook endpoint again while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the shop header), so `Registry.process` calls the handler with `shop` set to the attacker-chosen victim domain and a signature-valid body/topic combination the attacker controls (from their own shop).

This breaks the identity equality that the gem implicitly promises to callers: `authenticated(bytes) == trusted(shop)`. In reality `authenticated(bytes)` only proves "some real Shopify webhook for the app's client_secret," while `trusted(shop)` is an arbitrary, attacker-supplied header.

### Impact Explanation
If a host application uses `data.shop` returned by this gem to select which tenant's records to update (a documented, encouraged pattern — see the `docs/usage/webhooks.md` example `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), an attacker who can install the app on any shop (a normal, unprivileged onboarding action, not a privileged credential) can inject webhook events that the app will process as belonging to a different, victim tenant. This is a cross-tenant data-integrity/isolation violation stemming directly from the gem trusting an unauthenticated field as if it were authenticated — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target app on an attacker-controlled shop (freely available to any internet user via Shopify's development store program), (2) capturing one legitimate webhook body+HMAC pair delivered to the attacker's own endpoint for their own shop, and (3) replaying it toward the app's public webhook endpoint with a forged shop header. No leaked secrets, TLS interception, or privileged account access is needed — only normal app installation, which any unprivileged user can do. Likelihood is moderate-to-high for any app that keys tenant data off the `shop` field the gem provides without independent verification.

### Recommendation
Bind the `shop` value into the HMAC-verified material, or otherwise cryptographically/architecturally tie the trusted tenant identity to the signed payload:
- Include the `shop`/`webhook_id`/`topic` headers in the signable string used by `HmacValidator`, or
- Cross-check `request.shop` against the shop associated with the specific `webhook_id` (looked up independently, e.g., via a stored subscription-to-shop mapping) before trusting it, and
- Update `docs/usage/webhooks.md` to explicitly warn that `data.shop` is not covered by the webhook signature and must not be used as the sole tenant-selection key without additional verification.

### Proof of Concept
1. Attacker signs up for a free Shopify development store and installs the target app (using the app's single, shared `client_secret`).
2. Shopify delivers a legitimate webhook to the attacker's app endpoint, e.g.:
   - body: `{"id":123,...}` for `orders/create`
   - headers: `x-shopify-hmac-sha256: <valid HMAC of body with client_secret>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`
3. Attacker captures this exact `(raw_body, hmac)` pair (they own this shop, so no MITM is needed).
4. Attacker sends a new POST to the same app webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Registry.process` → `Utils::HmacValidator.validate(request)` succeeds (only body is checked) at [7](#0-6) 
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, and if the host app uses `data.shop` to route/update tenant data, victim-shop's records are affected by attacker-supplied content.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
