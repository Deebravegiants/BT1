### Title
Webhook shop identity not covered by HMAC signature enables cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — all read directly from unauthenticated HTTP headers — are excluded from the HMAC-signed content. `HmacValidator.validate` only proves that the raw body bytes were signed with the app's `api_secret_key`; it says nothing about which shop the webhook is "from." The `Registry.process` method trusts `request.shop` (an unauthenticated header) to build the `WebhookMetadata` passed to the app's handler, breaking the binding: `HMAC-verified bytes == raw_body` but `identity used by handler == shop header (never verified)`.

### Finding Description
`Webhooks::Request` exposes `shop`, `topic`, `webhook_id`, and `api_version` purely from HTTP headers: [1](#0-0) 

Crucially, `to_signable_string` — the value actually fed into the HMAC computation — returns only `@raw_body`, omitting every header including `shop`: [2](#0-1) 

`HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` header — again, this only authenticates the body bytes, not the `shop` header: [3](#0-2) 

`Registry.process` calls this validator, and on success immediately forwards the *unverified* `request.shop` into `WebhookMetadata`, which is handed to the app's webhook handler as the trusted tenant identity: [4](#0-3) [5](#0-4) 

Because the `api_secret_key` used to validate webhooks is a single, app-wide secret (not shop-specific — see the same key used across all shops in `Oauth.validate_auth_callback` and `HmacValidator.validate`), any party who can obtain one valid `(raw_body, hmac)` pair — e.g., a merchant who installed the app on their own store and received a legitimate webhook — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. Since `shop` is never part of the signed content, the signature check still passes, and the app's handler will process/act on data believing it originated from the victim shop.

**Identity binding broken (as equality):**
`shop authenticated by HMAC` (∅ — not included in `to_signable_string`) **≠** `shop trusted by handler` (`request.shop`, read from an arbitrary header).

### Impact Explanation
This is a cross-tenant identity confusion vulnerability: an attacker with a legitimate app installation on one shop can forge webhook deliveries that the receiving application will attribute to any other shop, without possessing that victim shop's session, access token, or any credential beyond a validly-signed body they already control. Depending on how the host app's `WebhookHandler#handle` uses `data.shop` (e.g., looking up/mutating shop-scoped records, or acting on mandatory compliance topics like `shop/redact` / `customers/redact` / `customers/data_request`), this can lead to unauthorized cross-tenant data access or mutation — a Critical-class cross-tenant access issue per the scoring rubric.

### Likelihood Explanation
Exploitability requires the attacker to possess at least one legitimately-signed `(body, hmac)` pair, which is trivial for any user who can install the app on their own store and observe outgoing webhook traffic (or trigger a webhook with attacker-controlled body content, e.g. product/order webhooks containing attacker-supplied text fields). No knowledge of `api_secret_key` or any other tenant's credentials is required — only a header rewrite (`X-Shopify-Shop-Domain`) on replay. This makes the likelihood moderate-to-high wherever a webhook endpoint is exposed to replay (i.e., not behind additional Shopify-only network controls).

### Recommendation
Include the shop domain (and ideally `topic`/`webhook_id`) in the signed payload, or otherwise cryptographically bind the shop identity to the signature — e.g., verify against a shop-specific secret/session rather than a single app-wide `api_secret_key`, or require that `request.shop` matches a value independently confirmed via a trusted lookup (registered/authorized shop with an active offline session) before dispatching to the handler. At minimum, document that `WebhookHandler` implementers must not trust `data.shop` from an HMAC-valid request without independently verifying that shop has an active app installation/session.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., updates a product) so Shopify sends a webhook with body `B` and header `X-Shopify-Hmac-Sha256: H` (a valid HMAC of `B` under the app's `api_secret_key`), plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same HTTP request to the app's webhook endpoint, but changes only the header:
   `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
3. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`, which calls `Utils::HmacValidator.validate(request)`: [6](#0-5) 
   Since `to_signable_string` only returns `@raw_body` (`B`), the recomputed HMAC over `B` still equals `H`, so validation succeeds.
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"` and passed to the handler, which now processes attacker-controlled data as if it came from the victim shop.
