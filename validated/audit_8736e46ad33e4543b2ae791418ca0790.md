Confirmed root cause: `Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC computed by `HmacValidator.validate` in `Registry.process` verifies only the request body bytes. The `shop` (and `topic`, `webhook_id`, `api_version`) values are read straight from HTTP headers via `shopify_header` and are never included in the signed data, yet `Registry.process` immediately forwards `request.shop` (the unauthenticated header) into `WebhookMetadata` as the tenant identifier the app's handler acts on.### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop` (and `topic`/`webhook_id`/`api_version`) used to route and attribute the webhook to a tenant come from unauthenticated HTTP headers. `Registry.process` validates the HMAC over the body and then trusts the header-derived `shop` as the tenant identity handed to the app's handler, breaking the binding `authenticated(body) == identity(shop)`.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the signed payload: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which only re-computes the signature over `to_signable_string` (the body) and compares it to the received `hmac`: [4](#0-3) 

Immediately after that check passes, `process` forwards the unauthenticated `request.shop` header value into `WebhookMetadata`, which is the tenant identity the app's `handler.handle` acts on: [5](#0-4) 

The binding that should hold is: `shop bound in HMAC == shop used by the handler`. Here, the HMAC binds only the body bytes; `shop` is parsed from headers that are never part of the signed material, so the equality is never enforced by this gem.

### Impact Explanation
Because the signature only covers the JSON body, any request with a body/HMAC pair that once validated for shop A can be replayed with the `shopify-shop-domain` header rewritten to shop B (or to the attacker's own shop), and `Utils::HmacValidator.validate` will still return `true` since the raw body bytes are unchanged. The `Registry.process` handler then executes app business logic (`WebhookMetadata#shop`) attributing shop A's data to shop B — a cross-tenant data/identity confusion. If bodies for different topics can carry attacker-influenced content (e.g., mandatory GDPR webhooks such as `customers/data_request`, `customers/redact`, `shop/redact`, or any webhook whose body an attacker can otherwise obtain, e.g. because they run their own shop and receive it legitimately) an attacker-controlled shop can spoof the `shop` field on a replayed/forged HTTP call to the app's public webhook endpoint and get the app to process it as if it originated from a different shop, since only the body — not the header set — is authenticated. This is a genuine cross-tenant identity-binding gap in this gem's own webhook verification code, distinct from documented best-practices notes; it is the gem's `HmacValidator`/`Request` design, not something the host app can fix by following documented API usage, since the gem doesn't expose signed headers to the app at all.

### Likelihood Explanation
Exploitation requires an attacker to obtain at least one legitimate `(raw_body, hmac)` pair — for example, by owning their own shop that is a legitimate app install and receiving the webhook they control the content of, or observing publicly-repeating bodies (e.g., empty-body test webhooks) — then POST that pair to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header. No knowledge of `api_secret_key` is required to perform the header substitution because the header is outside the signed scope. This is a realistic, unprivileged-internet-user-executable action against any app built on this gem's `Webhooks::Registry`/`Webhooks::Request`.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used by `Webhooks::Request#to_signable_string`, or otherwise cryptographically bind them (e.g., derive `shop` only after independently verifying it against a known/allow-listed shop list, or require the HMAC to cover a canonical string incorporating these headers) so that `HmacValidator.validate` cannot succeed unless the `shop` value used downstream matches the one Shopify actually signed for.

### Proof of Concept
1. An attacker installs the app on their own shop `attacker.myshopify.com` and lets it receive a legitimate webhook (e.g., empty-body topic) so they capture a valid `(raw_body="{}", x-shopify-hmac-sha256=<valid HMAC over "{}">)` pair — this is trivially computable/observable since HMAC is only over the body: [1](#0-0) 
2. Attacker POSTs to the app's webhook endpoint with the same body/HMAC but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `"{}"` only and matches: [4](#0-3) 
4. `process` builds `WebhookMetadata` with `shop: request.shop` = `"victim-shop.myshopify.com"` and invokes the app's handler, which now performs tenant-scoped actions (e.g., data deletion for GDPR topics, cache invalidation, notification dispatch) attributing it to the victim shop even though the payload never originated from Shopify for that shop: [6](#0-5)
