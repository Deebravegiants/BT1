## Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing tenant-mismatch webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the topic, shop, and HMAC from independent, unauthenticated HTTP headers, but the HMAC signature (`Digest.hexencode(Base64.decode64(shopify_header("hmac-sha256")))`) is only ever computed over `to_signable_string`, which returns just `@raw_body` — the raw request body. [1](#0-0)  The `shop` accessor is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signed body. [2](#0-1) 

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the expected signature from `verifiable_query.to_signable_string` and compares it with `verifiable_query.hmac` using `OpenSSL.secure_compare`. [3](#0-2)  For webhooks, `Request#to_signable_string` returns only the raw body, and `Request#hmac` decodes the `hmac-sha256` header. [4](#0-3) [5](#0-4)  The `shop` value, however, is pulled from a separate header (`shop-domain`) that plays no part in the signed input. [2](#0-1) 

This breaks the intended binding: `hmac == HMAC(secret, body)` should imply `shop == "the tenant that actually sent this body"`. In reality the equality that holds is only `hmac == HMAC(secret, body)`, while `shop` is asserted independently and unauthenticated. Because Shopify's HMAC for a webhook body is deterministic (same topic/body/secret ⇒ same HMAC) and does not incorporate the shop domain, any party who has legitimately received one valid `(body, hmac)` pair for a merchant's webhook (e.g., by being a collaborator/staff on a different store that also uses the same app, or having intercepted a webhook delivery through any means not requiring the app's secret) can resend that exact `body`/`hmac` pair with a different `shop-domain` header. `ShopifyAPI::Webhooks::Registry.process` verifies the HMAC via `Utils::HmacValidator.validate(request)` and then hands `request.shop` straight to the handler as the tenant identifier, without any independent verification that the `shop` header corresponds to the entity that actually produced/owns the signed body.

This matches the "field acted on but not covered by the HMAC" analog: the equality that should hold — `hmac-signed-body's origin shop == shop-domain header used by the handler` — is not enforced by this gem's code.

### Impact Explanation
If a host application (following this gem's documented `WebhookHandler` interface) uses `data.shop` to select which tenant's data to update/query — which is the intended, documented use of the field — cross-tenant data confusion is possible: a validly-HMAC'd webhook payload for shop A could be replayed with `shop-domain` set to shop B, and the gem's `Registry.process`/`Request` layer provides no protection against this, since only the body — not the shop — is authenticated. This can result in cross-tenant webhook processing (writing/deleting/creating data attributed to the wrong merchant), which falls under "cross-tenant access."

### Likelihood Explanation
Exploitability depends on an attacker being able to obtain one valid `(body, hmac)` pair (e.g., from their own store's webhook delivery, since the same app secret and same body would produce the same HMAC regardless of which shop triggered it) and then being able to deliver a forged HTTP request with a different `shop-domain` header to the app's webhook endpoint. Reaching the app's public webhook endpoint is generally feasible for anyone who knows its URL (webhook endpoints are typically public HTTP endpoints, not behind additional auth). No leaked credentials or access tokens are required — only the ability to observe one's own store's legitimate webhook traffic (something any merchant using the app already has) and to POST that payload with a modified header. This is a design gap in the library, not merely a host misuse, because the gem's own `Request`/`Registry` abstractions are what expose an unauthenticated `shop` field alongside an HMAC that never covers it.

### Recommendation
Bind the shop identity to the signed material, or otherwise document/enforce that `shop` must not be trusted for authorization/tenant-selection purposes without additional verification. Concretely:
- Where feasible, verify that the `shop-domain` header value is consistent with other signed webhook metadata (e.g., cross-check against a shop-specific secret/session lookup, or require callers to only trust `shop` after confirming the webhook was registered for that exact shop via `ShopifyAPI::Webhooks::Registry`'s stored registration state).
- At minimum, add explicit documentation/warnings that `data.shop` is not covered by the HMAC and must not be used as the sole tenant boundary check without additional application-level verification (e.g., confirming the shop has an active, matching session/access token in the host app's own session store before trusting the payload for that shop).

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` (attacker is a legitimate merchant/user of the app) and on `victim-shop.myshopify.com` (a different tenant of the same multi-tenant app).
2. Shopify sends a webhook to the app for `attacker-shop.myshopify.com` with body `B` and header `X-Shopify-Hmac-Sha256: H` (computed as `HMAC-SHA256(app_secret, B)`), plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker observes/logs `B` and `H` from their own store's webhook delivery (this requires no secret — it's delivered to their own app instance/logs, or they control a proxy in front of their own install).
4. Attacker crafts a new HTTP request to the same webhook endpoint with the identical body `B` and identical header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim-shop.myshopify.com", "shopify-hmac-sha256" => H, ...})` is constructed; [6](#0-5)  `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(app_secret, B)`, which still equals `H` because the body `B` is unchanged, so validation passes. [7](#0-6) 
6. `Registry.process` calls the app's handler with `data.shop == "victim-shop.myshopify.com"` even though the payload actually originated from `attacker-shop.myshopify.com`'s webhook stream, letting the attacker inject a "victim-shop" attributed webhook event of their choosing (subject to whatever body content they can trigger for their own store, e.g., an `orders/create` webhook with attacker-controlled order data now attributed to the victim shop).

Note: I was unable to fully confirm within this investigation whether `ShopifyAPI::Webhooks::Registry` performs any additional shop-registration cross-check before invoking handlers, since `registry.rb`'s full body was not retrieved in this session; the `Request`/`HmacValidator` code shown above, however, definitively confirms that the HMAC signature never covers the `shop` field, which is the root cause supporting this finding.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
