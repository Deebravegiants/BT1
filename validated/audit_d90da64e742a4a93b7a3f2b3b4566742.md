### Title
Enrollment success is locally asserted before backend confirms uniqueness/verification in the `user_centric_signup` path - ([File: src/plans/mod.rs])

### Summary
The reported C4 finding describes `PrivatePool.buy()` granting the buyer's asset (NFT transfer) before the payment/verification step is actually confirmed, letting a malicious callback exploit the gap. The closest reachable analog in `orb-core` is in `MasterPlan::do_signup`, where for `user_centric_signup` flows the Orb marks the signup's `enrollment_status` as `Success` purely from the *locally computed* `signup_reason`, without going through the backend round-trip (`signup_post::request` + `signup_poll::request`) that normally confirms uniqueness/fraud checks before a signup is accepted.

### Finding Description
In the normal enrollment path, `MasterPlan` calls `self.enroll_user(...)`, which POSTs the signup to the backend and then polls `signup_poll::request` in a loop until the backend explicitly returns `Completed`/`success: true` [1](#0-0) . This backend round-trip is what turns local "the pipeline ran and matched no fraud" into an authoritative signup acceptance (it is the equivalent of "funds actually received" in the reported analog).

However, in `do_signup`, when `user_centric_signup && !orb.config.lock().await.ignore_user_centric_signups` is true, `enroll_user` (and hence the backend confirmation round-trip) is skipped entirely, and success is derived directly from the locally computed `signup_reason`: [2](#0-1) 

```
let success = if user_centric_signup && !orb.config.lock().await.ignore_user_centric_signups
{
    debug_report.enrollment_status(match signup_reason {
        SignupReason::Normal => enroll_user::Status::Success,
        _ => enroll_user::Status::Error,
    });
    signup_reason == SignupReason::Normal
} else {
    Box::pin(self.enroll_user(...)).await.is_success()
};
```

`signup_reason` itself is computed purely from local, Orb-side signals (pipeline output presence and local fraud-detection result), not from any backend confirmation: [3](#0-2) 

The `user_centric_signup` flag is attacker-influenceable in the sense that it originates from the backend `UserData` returned for the *user's* QR code (`backend::user_status::UserData::user_centric_signup`) [4](#0-3) , meaning the code path taken (with or without backend confirmation) is determined by data tied to the user QR code being scanned, i.e., by the unprivileged end user's registration state.

### Impact Explanation
This is a genuine structural analog to the reported bug class (result/asset granted before the authoritative check completes): in `user_centric_signup` mode, the Orb declares the signup a `Success` (and proceeds to build/upload the Personal Custody Package) based solely on the local pipeline's "no fraud detected" signal, without waiting for/relying on the backend's authoritative accept/duplicate/fraud decision that the standard `enroll_user` flow enforces via `signup_poll`. Because the local fraud/pipeline check and the backend's server-side uniqueness/duplicate check are different trust boundaries, a Personal Custody Package can be built and uploaded, and `signup_finished(success=true)` announced over DBus and self-serve relay, before the backend has verified the signup is not a duplicate/fraudulent enrollment — a cross-signup state bleed / misattributed-signup risk class matching the reported analog's "grant before verification" pattern.

### Likelihood Explanation
Reaching this path requires only an unprivileged user's QR-code-driven session where the backend flags the user as `user_centric_signup` and the Orb config has `ignore_user_centric_signups` unset — both realistic, no-privilege-required, standard runtime conditions given the way `user_centric_signup` is threaded through `qr_codes.user_data`.

### Recommendation
Do not assert `enrollment_status::Success` from the local `signup_reason` alone in the `user_centric_signup` branch. Ensure that, similar to the standard `enroll_user` path, PCP construction/upload and the `Success` determination only proceed after an explicit backend confirmation (or an equivalent authoritative uniqueness/fraud check) rather than a purely local `signup_reason` flag.

### Proof of Concept
Not independently executable from static analysis alone (would require driving `do_signup` with `user_centric_signup = true` and controlling `signup_reason` via the local pipeline/fraud-detection output) — this is inferred directly from the code paths cited above: the `user_centric_signup` branch at [5](#0-4)  bypasses the backend round-trip performed by `enroll_user::Plan::run` at [6](#0-5) .
