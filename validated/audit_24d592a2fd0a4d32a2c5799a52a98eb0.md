### Title
`Bonding#initializeBounceGlobalStorage` lacks access control, allowing anyone to front-run the owner and permanently poison the `bounceGlobalStorage` reference - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.initializeBounceGlobalStorage` is an externally callable, unprotected function gated only by `reinitializer(2)`, with no `onlyOwner` (or equivalent) check. Any unprivileged address can call it directly on the proxy before the legitimate deployer/owner does, exactly the same access-control gap described in the external report for `CollateralManager#setCollateralEscrowBeacon`, which is also gated only by `reinitializer` with no owner check.

### Finding Description
`initializeBounceGlobalStorage` is defined as: [1](#0-0) 

```solidity
/// @notice Backfill `bounceGlobalStorage` on a proxy deployed before this
///         slot existed. Invoked atomically via `upgradeToAndCall`. The
///         `address(0)` guard closes the reinitializer-front-run window on
///         fresh proxies that haven't been initialised yet.
function initializeBounceGlobalStorage(
    address bounceGlobalStorage_
) external reinitializer(2) {
    if (bounceGlobalStorage_ == address(0)) revert ZeroAddress();
    BondingStorage storage $ = _s();
    if (address($.bounceGlobalStorage) != address(0)) revert InvalidInput();
    $.bounceGlobalStorage = IBounceGlobalStorage(bounceGlobalStorage_);
    emit BounceGlobalStorageUpdated(address(0), bounceGlobalStorage_);
}
```

There is no `onlyOwner` modifier, unlike essentially every other privileged setter in the codebase (`FeeVault`, `Zap`, `LPLock` setters all gate with `onlyOwner`). The only protections are:
1. `reinitializer(2)` — prevents replay, but does **not** restrict the caller, only that it can be called once.
2. The `address($.bounceGlobalStorage) != address(0)` guard — prevents *overwriting* an already-set value, but does nothing to prevent the *first* call being made by an attacker instead of the owner.

The developer comment itself acknowledges "the reinitializer-front-run window on fresh proxies that haven't been initialised yet," meaning the team was aware this function is racing against the legitimate initialization transaction, but the fix applied (the zero-address/already-set guard) only prevents double-setting — it does not stop an attacker from winning that race and setting `bounceGlobalStorage_` to an attacker-controlled contract first. This is structurally identical to the CollateralManager bug class: a state-critical setter is reachable via `reinitializer` with zero caller restriction.

### Impact Explanation
`bounceGlobalStorage` (`IBounceGlobalStorage`) is a permanent proxy-storage reference used pervasively throughout `Bonding.sol` (13 references), and cannot be changed once set (enforced by the same guard that is meant to protect it). If an unprivileged attacker front-runs the intended initialization call — e.g., by monitoring the mempool for the `upgradeToAndCall` transaction that is supposed to atomically call this function, or simply calling it directly against a freshly-deployed/upgraded proxy before the owner's transaction lands — the attacker permanently wires an attacker-controlled contract into `Bonding` as its `bounceGlobalStorage`. Because the value can never be reset (the guard reverts on any subsequent call once non-zero), this is a permanent, irreversible corruption of a core dependency of the bonding-curve/graduation logic, with no owner recovery path other than a full contract upgrade. Depending on what `IBounceGlobalStorage` is read for elsewhere in `Bonding`, this can be leveraged to corrupt graduation logic, curve parameters, or global storage reads relied on by trading/graduation, causing freezing or manipulation of trader/creator funds routed through `Bonding`.

### Likelihood Explanation
This requires only a plain call from any address — no privilege, no signature, no special role — with the sole constraint being winning the race against the owner's intended call. Since the deploy/upgrade script's `upgradeToAndCall` calldata revealing the exact call is visible on-chain/in the mempool before inclusion, an attacker can trivially front-run it with a higher gas bid. This is a realistic MEV/front-running scenario on any public chain, matching the class of "anyone can call the unprotected re-initializer" bugs.

### Recommendation
Add an owner/deployer-restricted check to `initializeBounceGlobalStorage`, e.g. gate it with `onlyOwner` (consistent with other privileged setters in the codebase), or better, pass `bounceGlobalStorage_` as part of the atomic `initialize`/`upgradeToAndCall` payload so there is no separate externally-callable window at all. If `onlyOwner` cannot be used because `Ownable` state may not yet be set at this reinitialization step, restrict the caller to a hardcoded deployer address or use a commit-reveal / two-step confirmation pattern that only the owner can complete.

### Proof of Concept
1. `Bonding` proxy is deployed/upgraded to a version containing `initializeBounceGlobalStorage`, intended to be invoked atomically via `upgradeToAndCall(newImpl, abi.encodeCall(Bonding.initializeBounceGlobalStorage, (legitimateStorageAddr)))`.
2. Attacker observes the pending transaction in the mempool (or simply monitors for the upgrade transaction landing without an atomic call).
3. Attacker submits their own transaction calling `bonding.initializeBounceGlobalStorage(attackerControlledContract)` with higher gas, landing before the legitimate call.
4. `$.bounceGlobalStorage` is now permanently set to `attackerControlledContract`; any subsequent legitimate call reverts with `InvalidInput()` since `address($.bounceGlobalStorage) != address(0)`.
5. All logic in `Bonding.sol` that reads `bounceGlobalStorage` now operates against attacker-supplied data/logic indefinitely, with no recovery short of a full contract upgrade.
