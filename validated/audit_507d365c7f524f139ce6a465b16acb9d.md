### Title
Webhook shop/topic identity spoofing via unauthenticated headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` only binds the HMAC signature to the raw request body, while the shop domain, topic, and webhook id are read directly from unauthenticated HTTP headers. `Registry.process` validates the body's HMAC and then blindly trusts these header-derived values to route and tag the webhook payload delivered to the host application's handler, breaking the equality between "the tenant whose secret signed this data" and "the tenant the handler is told owns this data."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (the body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` uses this validator as the sole authentication check, then constructs `WebhookMetadata` using `request.shop` and `request.topic` taken from the same unauthenticated headers, handing them to the host application's handler as if they were verified: [4](#0-3) 

Because the shop domain and topic are never part of the signed payload, any party who obtains one valid `(raw_body, hmac-sha256)` pair — e.g. from a webhook legitimately delivered to their own installed shop, since apps share one `api_secret_key` across all installations — can replay that same body/signature to the app's webhook endpoint while substituting the `x-shopify-shop-domain` and `x-shopify-topic` headers for a different shop and/or topic. `HmacValidator.validate` will still return `true` because it never inspects those headers, and `Registry.process` will invoke the topic handler with a forged `shop` value.

### Impact Explanation
This breaks the identity binding `shop authenticated by HMAC == shop delivered to the handler`. A host application that relies on `WebhookMetadata#shop` (as documented) to select which tenant's data to write/read will act on behalf of an attacker-chosen shop using a signature that was never generated for that shop or that topic — a cross-tenant data integrity/access issue driven entirely by this gem's own webhook verification contract, not by host misuse.

### Likelihood Explanation
Any developer/merchant who can install the app on a shop they control receives legitimately signed webhooks for that shop (all shops share the same `api_secret_key`, since it's per-app not per-shop). Capturing and replaying one such webhook with edited headers requires only network access to the app's public webhook endpoint — no leaked secrets, tokens, or privileged access needed.

### Recommendation
Include the authenticated identity fields (at minimum `shop` and `topic`) in the HMAC-signed material, or otherwise cryptographically bind the headers to the signed body before trusting them in `Registry.process`/`WebhookMetadata`. Barring a protocol change from Shopify's side, the library should treat header-derived `shop`/`topic` as unauthenticated and document this prominently, or reject requests where header values can't be corroborated.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. body `{"id":1}` with header `x-shopify-hmac-sha256: <valid signature over the body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical raw body and `hmac-sha256` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because it only checks the (unmodified) body against the (unmodified) signature.
4. `Registry.process` looks up the handler for the requested topic and calls it with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to process attacker-controlled data as though Shopify had authenticated it for `victim-shop.myshopify.com`.
