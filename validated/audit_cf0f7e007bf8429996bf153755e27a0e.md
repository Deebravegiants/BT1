Based on my investigation, I found a close analog to the reported bug class in `IntentGatewayV2.placeOrder()`, where `protocolFeeBps` is read live at order-placement time and can be raced against a governance fee-increase update.

### Title
Governance fee increase in `IntentGatewayV2` can be frontrun via `placeOrder()` to pay a stale, lower protocol fee - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2` charges a `protocolFeeBps` (or a per-destination override) on every order's input amount, computed live at `placeOrder()` call time from mutable storage (`_params.protocolFeeBps` / `_destinationProtocolFees`). Governance updates these values via an ISMP `onAccept` cross-chain message that is delivered by a public relayer transaction. Because both the fee-increasing `onAccept` delivery and a user's `placeOrder()` call are ordinary, publicly-visible mempool transactions on the same chain, a user can observe the pending fee-increase delivery and submit `placeOrder()` with higher gas to land first, locking in the old, lower fee.

### Finding Description
The protocol fee is computed inline inside `placeOrder()`: [1](#0-0) 

`protocolFeeBps` (and the per-destination override in `_destinationProtocolFees`) is only mutable through `_updateParams`, invoked from `onAccept` when Hyperbridge governance dispatches a `ParamsUpdate` cross-chain message: [2](#0-1) 

That `onAccept` delivery is itself a normal, unprivileged-relayer-submitted transaction that becomes visible in the mempool before inclusion (any relayer can carry and submit the proof for the governance-originated request). There is no timelock, effective-block delay, or grace-period mechanism between the governance decision and the on-chain fee change taking effect — the new `protocolFeeBps` is applied atomically to `_params` the instant the `onAccept` transaction is mined, with no protection against transactions ordered ahead of it in the same block or a preceding block.

### Impact Explanation
This is directly analogous to the referenced Footium `setDivisionFees()` finding: whenever governance raises `protocolFeeBps` (or sets a higher per-destination fee), any user watching the mempool for the pending delivery transaction can front-run it with `placeOrder()` calls, permanently locking in the stale/lower fee for that order. Because there is no per-account rate limiting or cap on order size/count, this can be repeated across many orders in the block(s) preceding the fee-increase, resulting in a systematic, engineered shortfall of protocol fee revenue relative to what governance intended to charge from the moment of decision. This constitutes a route by which the protocol's dust/fee-collection stream is reduced below the intended amount for an unbounded number of orders placed in the frontrunning window.

### Likelihood Explanation
Fee changes are rare but observable in advance (the source PostRequest and proof are public before being relayed/included), and exploitation requires only a standard frontrunning bot watching the mempool for the specific `onAccept` calldata pattern (`RequestKind.UpdateParams`) targeting the gateway contract — no privileged access or governance compromise is needed on the attacker's side; the attacker is an ordinary, unprivileged order-placer.

### Recommendation
Introduce an effective-time delay for `protocolFeeBps` / `_destinationProtocolFees` changes (e.g., store `(newValue, effectiveBlock)` and apply only once `block.number >= effectiveBlock`), or batch/commit-reveal the update so it cannot be observed and raced against before finalization. Alternatively, snapshot the fee at commitment time using a value that cannot be manipulated by transaction ordering (e.g., apply fee changes only at epoch boundaries known in advance).

### Proof of Concept
1. Governance decides to raise `protocolFeeBps` from 5 bps to 50 bps and dispatches the cross-chain `ParamsUpdate` request from Hyperbridge.
2. A relayer submits the proof to `IntentGatewayV2.onAccept` on the destination chain; this transaction sits in the public mempool before inclusion.
3. An attacker (or any user) observes this pending transaction, and submits `placeOrder()` with a higher gas price/priority fee so it mines before the `onAccept` transaction, per the fee computation at [3](#0-2) .
4. The order's protocol fee is computed and locked in using the old 5 bps rate instead of the intended 50 bps, as shown by the existing test suite's direct read of `_params.protocolFeeBps` at placement time: [4](#0-3) .
5. This can be repeated by the same or colluding accounts across every block until the `onAccept` transaction confirms, cumulatively reducing collected protocol fees below what governance intended.

    /**
     * @dev Updates the gateway's configuration parameters and per-destination protocol fees.
     * Called by Hyperbridge governance to modify fee settings, host address, dispatcher,
     * price oracle, and other operational parameters.
     *
     * Validates all params before applying. Emits ParamsUpdated with the old and new params,
     * then iterates over any destination-specific fee overrides and applies them to
     * `_destinationProtocolFees`.
     *
     * @param update The parameter update containing new params and destination fee overrides.
     */
    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }
