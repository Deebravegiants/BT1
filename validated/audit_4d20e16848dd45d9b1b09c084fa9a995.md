The Tron variant of the intent gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) departs from the EVM version's `SafeERC20`-only pattern and instead uses raw low-level `.call()` checks that only validate call-success, not the ERC20 boolean return value — this is the exact bug class from the report.

### Title
Unchecked ERC20 boolean return value in Tron IntentGateway's escrow withdraw/sweep lets a false-returning token silently "release" escrow while leaving tokens locked, permanently freezing user/solver funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron `IntentGatewayV2` contract re-implements escrow settlement with raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks that the low-level call did not revert (`success`), never decoding/validating the ABI-encoded boolean return value. Unlike the canonical EVM `IntentsBase._withdraw`/`_sweepDust`, which correctly use OpenZeppelin's `SafeERC20.safeTransfer` (`evm/src/apps/intentsv2/IntentsBase.sol:468`, `evm/src/apps/intentsv2/IntentsBase.sol:649`), the Tron contract's `withdraw()` and `onAccept` dust-sweep path do not.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the `withdraw()` function (reachable from `onAccept` for `RequestKind.RedeemEscrow`/`RequestKind.RefundEscrow`, i.e. after any relayer delivers a valid Hyperbridge POST) does: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
_orders[body.commitment][token] -= amount;
```

For ERC20 tokens that return `false` on failure instead of reverting (the same class of non-standard token flagged in the referenced Tracer report), `success` is `true` (the external call itself does not revert), so `TransferFailed` never fires, yet no tokens actually move to `beneficiary`. The function nonetheless decrements `_orders[body.commitment][token]` and, on `finalize`, sets `_filled[body.commitment] = beneficiary` and emits `EscrowReleased`/`EscrowRefunded`. The same unchecked pattern is used in the `SweepDust` branch of `onAccept`: [2](#0-1) 

and in the fee-forwarding path at the end of `withdraw()`: [3](#0-2) 

Because the order is marked `_filled` and its escrow accounting zeroed out on this silent failure, there is no retry path — the escrowed tokens remain stuck in the contract with no accounting entry pointing to them, and the intended beneficiary/solver/user never receives their funds.

### Impact Explanation
This causes permanent loss/freezing of escrowed input tokens and fees for solvers (on `RedeemEscrow`) or users (on `RefundEscrow`): the contract's internal state says the order is finalized and paid out, but the actual token balance never reached the beneficiary. There is no compensating mechanism to re-trigger the transfer once `_orders[...]` has been decremented and `_filled` set, so the funds are unrecoverable — meeting the "permanent freezing of funds" bar.

### Likelihood Explanation
Exploitability depends on the escrowed/output token itself returning `false` instead of reverting (e.g., legacy or non-standard ERC20 implementations), which is a known real-world class of tokens (this is the identical precondition the original Tracer report relies on). Any intents user/solver who selects such a token as an input/output asset — or any deployment that later allowlists such a token — triggers the bug purely through the normal, permissionless `placeOrder`/`fillOrder`/relayer-delivered `onAccept` flow, with no attacker privilege required.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()`, the `SweepDust` handling in `onAccept`, and the fee-forwarding call) with OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, mirroring the already-correct implementation in `evm/src/apps/intentsv2/IntentsBase.sol`. This decodes and enforces the ERC20 return value (or handles the no-return-value USDT-style case), preventing silent transfer failures from being treated as successful settlement.

### Proof of Concept
1. A destination-chain (Tron) deployment escrows an ERC20 whose `transfer()` returns `false` on failure (e.g., insufficient allowance/blacklist) instead of reverting.
2. A relayer delivers a valid Hyperbridge `RedeemEscrow`/`RefundEscrow` POST to `onAccept`, invoking `withdraw()`.
3. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` with encoded `false` payload, so no tokens are transferred.
4. `withdraw()` proceeds to decrement `_orders[body.commitment][token]`, set `_filled[body.commitment]`, and emit `EscrowReleased`/`EscrowRefunded` as if the transfer succeeded.
5. The escrowed tokens remain in the contract with no order entry referencing them and `_filled` already set, permanently unreachable by the intended beneficiary.
