### Title
Webhook `shop` identity not covered by HMAC signature allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` computes the HMAC-verified content from the raw request body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read straight from HTTP headers and passed to the handler unauthenticated. Because Shopify webhook HMACs are computed with the app-wide `client_secret`/`api_secret_key` (shared across every merchant that has installed the app), any merchant that receives a legitimately signed webhook for their own store can replay it against the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to point at a different, victim shop. The signature still validates because it never covered the shop header, but `ShopifyAPI::Webhooks::Registry.process` hands the attacker-controlled `shop` straight to the app's handler as trusted `WebhookMetadata#shop`.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the supplied HMAC: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated headers and exposed as separate attributes: [3](#0-2) 

`Registry.process` validates the HMAC against the body, then immediately forwards the header-derived `shop` value (never covered by the signature) to the app's handler as trusted metadata: [4](#0-3) [5](#0-4) 

The equality that should hold is: `shop == shop-domain-bound-by-signature`. In reality the gem enforces only `hmac == HMAC(body, secret)`, independent of `shop`. Because `secret` is the app's single `api_secret_key`/`client_secret`, it is identical for every merchant that installs the app — it is not a per-tenant value. Any merchant (an "unprivileged internet user" relative to other tenants of the same app) can:
1. Install the app and receive a real webhook for their own shop, obtaining `(body, valid_hmac)`.
2. Send `(body, valid_hmac)` to the app's webhook endpoint again, but with the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header changed to a victim shop's domain.
3. `HmacValidator.validate` still passes (it only checks the body), and `Registry.process` calls the handler with `WebhookMetadata.new(shop: <victim-shop>, ...)`.

The gem's own documentation instructs apps to key business logic off `data.shop` directly (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), so this metadata is expected to be trusted as the tenant identifier: [6](#0-5) 

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: a value (`shop`) that host applications are told to trust as the authenticated tenant identifier is not bound by the cryptographic check that is supposed to authenticate the request. An attacker with access to only their own (possibly free/trial) shop installation of the app can inject data attributed to another merchant's shop into the host app's webhook processing pipeline (e.g. causing order/customer/product data to be written to, or actions taken against, another tenant's stored session/state). This is a cross-tenant access vulnerability that maps to the "Critical" impact bucket in the rules.

### Likelihood Explanation
Exploitation requires only: (a) the attacker's own account be a merchant who has installed the target app (a normal, unprivileged step available to any internet user), and (b) the ability to send an HTTP POST to the app's public webhook endpoint with a modified header — both trivial. No access to `api_secret_key`, access tokens, or any victim credentials is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed payload verification, or otherwise validate that the `X-Shopify-Shop-Domain` header corresponds to a shop that is known/registered for the receiving app installation before trusting it. At minimum, `docs/usage/webhooks.md` should explicitly warn implementers that `data.shop` is not authenticated by the HMAC and must be cross-checked against the app's own session/shop store before being used for any tenant-scoped action.

### Proof of Concept
1. Install the target Shopify app on `attacker-shop.myshopify.com`.
2. Trigger any subscribed webhook topic (e.g. `orders/create`) and capture the raw POST body and the `X-Shopify-Hmac-Sha256` header sent by Shopify — this HMAC is valid because it's computed with the app-wide `api_secret_key`.
3. Replay the exact same body/HMAC to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. Observe that `ShopifyAPI::Webhooks::Registry.process` still succeeds:
```ruby
request = ShopifyAPI::Webhooks::Request.new(
  raw_body: captured_body,
  headers: {
    "x-shopify-topic" => "orders/create",
    "x-shopify-hmac-sha256" => captured_valid_hmac,
    "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled
  },
)
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
```
5. The app's registered handler receives `data.shop == "victim-shop.myshopify.com"` and `HmacValidator.validate` reported success — the attacker's own body/HMAC pair is now attributed to a different tenant.
