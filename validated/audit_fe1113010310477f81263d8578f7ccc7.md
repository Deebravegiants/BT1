### Title
Webhook `shop` (tenant) identifier is not covered by the HMAC signature, allowing shop-domain spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, but exposes a separate `shop` accessor that is read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header. `Registry.process` validates the HMAC and then hands `request.shop` straight to the host app's webhook handler as the tenant identifier, without that value ever being part of the signed bytes.

### Finding Description
`Registry.process` is the sole entry point for verifying and dispatching inbound Shopify webhooks: [1](#0-0) 

It calls `Utils::HmacValidator.validate(request)`, which recomputes an HMAC over `request.to_signable_string` and compares it to `request.hmac`: [2](#0-1) 

But `Request#to_signable_string` returns only `@raw_body` — nothing derived from headers is included in the signed material: [3](#0-2) 

Meanwhile `Request#shop` (the tenant identity used downstream) is read straight from the `shopify-shop-domain` header, which is never mixed into `to_signable_string`: [4](#0-3) 

After the HMAC check passes, `Registry.process` builds `WebhookMetadata` using this unauthenticated `request.shop` value and passes it to the app's registered handler: [1](#0-0) 

The identity binding this breaks, stated as an equality that should hold but doesn't:
`shop_bound_by_hmac(raw_body, api_secret_key)` (the tenant Shopify actually signed for) `== request.shop` (the tenant the handler is told the payload belongs to).

Because `shop` is entirely outside the HMAC-covered bytes, whoever can produce *any* validly-HMAC'd `(raw_body, hmac)` pair for the shared `api_secret_key` — e.g. a merchant who has the app installed on their own store and thus receives real webhooks with a valid signature for their own shop — can replay that exact `raw_body`/`hmac` pair while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` will still return `true` (it never inspects the header), and `Registry.process` will forward the attacker-chosen `shop` to the handler as if it were authenticated.

### Impact Explanation
Any host application that uses the `shop` field from `WebhookMetadata` to select which merchant's data/session/tenant record to mutate (a normal and expected usage pattern, since that is the only "authenticated" tenant identifier `shopify_api` gives handlers) can be tricked into applying a legitimately-signed payload under a different, attacker-chosen shop. This is a cross-tenant data-confusion vector: an attacker with app access on their own store can forge webhook deliveries that appear to originate from a different, arbitrary shop, since the gem provides no cryptographic binding between the verified bytes and the shop identity attached to them. This matches the "Critical – cross-tenant access" impact bucket in scope, because the gem's own API (`WebhookMetadata#shop`) is the thing that lies about which tenant a signed payload belongs to.

### Likelihood Explanation
Exploitation requires only the ability to send arbitrary HTTP requests to the app's registered webhook endpoint plus one genuine `(raw_body, hmac)` pair signed under the app's shared `api_secret_key` — trivially obtainable by any merchant with the app installed on their own development/trial store, who can then capture a real webhook delivery and replay it with a modified `shopify-shop-domain` header. No access token, `client_secret`, or privileged account is required, satisfying the "unprivileged internet user" analog requirement.

### Recommendation
Include the shop-domain (and topic/webhook-id, if they are relied upon by handlers) in the HMAC-covered material, or otherwise cryptographically bind them to the verified body — e.g., derive `to_signable_string` from a canonical concatenation of `shop-domain + raw_body`, and have `HmacValidator` verify against that combined string rather than the body alone. At minimum, document prominently that `Request#shop`/`WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant routing, and provide a verified alternative.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook delivery, capturing the raw body `B` and the corresponding valid header `shopify-hmac-sha256: H` (computed by Shopify using the app's shared `api_secret_key`), together with header `shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the exact same HTTP request to the app's webhook endpoint, keeping `raw_body = B` and `shopify-hmac-sha256 = H` unchanged, but rewrites `shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`== B`) and compares to `H` — validation succeeds because the header was never part of the signed bytes: [5](#0-4) 
4. `Registry.process` builds `WebhookMetadata.new(topic:, shop: request.shop, ...)` using `request.shop == "victim-shop.myshopify.com"` (from the tampered header) and invokes the app's handler with this spoofed tenant identity: [6](#0-5) 
5. The host application processes the (attacker-controlled-provenance) payload as though it belongs to `victim-shop.myshopify.com`, achieving cross-tenant data confusion despite HMAC "validation" having succeeded.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
