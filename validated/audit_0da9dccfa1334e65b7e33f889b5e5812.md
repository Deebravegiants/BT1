### Title
Stale Cached Operator Authorization Enables Unauthorized Signups After Revocation - (File: `src/plans/mod.rs`)

### Summary
The Orb caches the result of a one-time backend validation of an operator's QR code (`OperatorData`) and reuses that cached "valid" snapshot to authorize an unbounded number of subsequent, unrelated signups for up to `operator_qr_expiration_time` (23 hours by default), without ever re-querying the backend to confirm the operator is still authorized during that window. This mirrors the H-1 bug class: a security-relevant value (operator authorization) is fetched once, cached, and then used repeatedly for decisions that should require a fresh check, so a change in the authoritative state (operator revoked/banned/relocated on the backend) is not reflected until the local expiry timer — not the actual backend state — elapses.

### Finding Description
`verify_operator_qr_code` performs the authoritative check against the backend (`backend::operator_status::request`), which returns `valid: true/false` and can be revoked/changed server-side at any time. [1](#0-0) 

The validated result is wrapped into an `OperatorData` struct carrying just an `Instant` timestamp, with no re-validation hook: [2](#0-1) 

This cached `OperatorData` is then reused across the idle loop (`scan_initial_qr_codes`) and across `do_signup`'s QR resolution (`scan_remaining_qr_codes`) purely based on a local elapsed-time check against `operator_qr_expiration_time`, never re-confirming operator status with the backend as long as the cache is "not yet expired": [3](#0-2) [4](#0-3) 

The expiration window defaults to 23 hours, meaning the Orb can run many independent signups relying on an operator-authorization decision that is up to 23 hours stale: [5](#0-4) 

This is structurally identical to the H-1 root cause: a boolean/derived value ("operator valid") is snapshotted at time T1 and used for many downstream security decisions at T2..Tn without confirming it is still true, because the update path (backend revoking/deactivating the operator) and the consumption path (signup authorization) are decoupled and not synchronized.

### Impact Explanation
If a distributor/operator's authorization is revoked, geofenced out, or otherwise invalidated on the backend (e.g., due to fraud, policy violation, or de-provisioning) after the Orb has cached a valid `OperatorData`, the Orb will continue accepting and completing signups under that operator's credentials for up to the full `operator_qr_expiration_time` window (23 hours by default) instead of rejecting them immediately. This allows unauthorized signups to be completed and enrolled/paid out under a distributor code that should have been blocked, directly enabling misattributed/unauthorized signup activity — the same class of "act on stale authorization state for improper benefit" as the original finding, just mapped onto the Orb's signup-authorization boundary rather than a token-conversion boundary.

### Likelihood Explanation
Likelihood is moderate-to-high in self-serve or long-running orb deployments: `scan_initial_qr_codes` and `idle_wait_for_signup_request` are explicitly designed to keep reusing the operator scan across many signups without operator interaction until the timer lapses, which is the intended UX but also the exact mechanism that makes any backend-side revocation ineffective until the cache naturally expires. No attacker action beyond normal signup flow is required to trigger the stale-authorization window; an operator being revoked mid-window is a normal administrative/business event, not a hypothetical.

### Recommendation
Do not rely solely on the local timestamp/expiration window to decide whether cached operator authorization is still valid for a fresh signup. Re-validate operator status against the backend (`backend::operator_status::request`) at the start of every `do_signup`/`scan_remaining_qr_codes` invocation — or at minimum on a much shorter, security-appropriate interval — rather than only when `operator_data.timestamp.elapsed() >= operator_qr_expiration_time`. This mirrors the accepted fix pattern in the original report: replace the stale cached authorization value with a call to the authoritative/live source before using it to gate a security-sensitive action.

### Proof of Concept
1. Operator scans QR code; Orb calls `verify_operator_qr_code`, backend returns `valid: true`; Orb caches `OperatorData { timestamp: Instant::now(), .. }`. [6](#0-5) 
2. Backend administrator revokes/deactivates this operator/distributor code minutes later (e.g., fraud detected).
3. Because `operator_data.timestamp.elapsed() < operator_qr_expiration_time` still holds, subsequent calls to `scan_remaining_qr_codes` skip re-verification and go straight to scanning/validating the user QR code, reusing the now-invalid `operator_data`: [7](#0-6) 
4. Multiple additional signups complete successfully under the revoked operator's identity for up to `operator_qr_expiration_time` (23h default) after revocation, with no backend re-check ever occurring in between.

    async fn scan_initial_qr_codes(
        &mut self,
        orb: &mut Orb,
        qr_codes: &mut QrCodes,
        self_serve: bool,
        operator_qr_expiration_time: Duration,
    ) -> Result<()> {
        if self_serve
            && qr_codes
                .operator_timestamp()
                .map_or(true, |ts| ts.elapsed() > operator_qr_expiration_time)
        {
            loop {
                let qr_capture_start = Instant::now();
                let operator_qr_code =
                    self.scan_operator_qr_code(orb, None).await?.expect("to never timeout");
                let Some(operator_qr_code) =
                    self.handle_magic_operator_qr_code(orb, operator_qr_code).await?
                else {
                    continue;
                };
                let Some((_, operator_location_data)) =
                    self.verify_operator_qr_code(orb, &operator_qr_code, qr_capture_start).await?
                else {
                    continue;
                };
                *qr_codes = QrCodes::Operator {
                    operator_data: OperatorData {
                        qr_code: operator_qr_code,
                        location_data: operator_location_data,
                        timestamp: Instant::now(),
                    },
                };
                break;
            }
        }
        Ok(())
    }
