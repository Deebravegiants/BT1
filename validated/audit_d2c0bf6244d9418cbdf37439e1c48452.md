### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing shop-domain spoofing on otherwise validly-signed webhook payloads - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an inbound webhook from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but the HMAC signature computed by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body, not this header. `Registry.process` validates the HMAC and then blindly trusts `request.shop` when building the `WebhookMetadata` passed to the host app's handler, binding attacker-controlled tenant identity to a validly-signed payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` header with no relation to the signed bytes: [2](#0-1) 

`HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` checks only that the HMAC is valid, then forwards `request.shop` (the header value) — never re-derived from or cross-checked against the signed body — to the handler: [4](#0-3) 

This is the same identity-binding gap described in the report: a field that downstream logic acts on (`l1QueueOrigin` there, `shop`/tenant here) is not included in the value that is cryptographically verified (the transaction/HMAC). The equality that should hold is:

`shop used by handler.handle(WebhookMetadata#shop)` == `shop that produced the HMAC-covered body`

but the gem only enforces:

`HMAC(secret, raw_body)` == `received hmac`

with `shop` completely outside that equation. Anyone able to produce one validly-HMAC'd body/HMAC pair for the app's `client_secret` (which happens legitimately whenever Shopify sends a real webhook to the app for *any* shop that has the app installed, including a shop controlled by the attacker) can then replay that exact `raw_body` + `hmac` header pair while substituting an arbitrary `shopify-shop-domain` header value. The signature still validates because the header is not part of the signed content, so `Registry.process` accepts it and dispatches to the handler with a forged `shop`.

### Impact Explanation
This breaks the tenant/shop authentication boundary that host applications rely on `ShopifyAPI::Webhooks::Registry`/`WebhookMetadata#shop` to provide. A host application built on this gem's documented API reasonably treats a webhook that passes `HmacValidator.validate` as authentically originating from the `shop` reported by the request, since the gem's own `Request`/`Registry` abstraction is the only place where HMAC verification occurs and `shop` is surfaced. An attacker who has the app installed on their own shop (an unprivileged, ordinary merchant — no special privileges, no access token or client_secret needed) can capture a real, validly-signed webhook and resend it to the app's public webhook endpoint with a spoofed `shop` header, causing the app to process attacker-controlled payload data as if it belongs to a different, victim tenant. Depending on how the host app persists/keys data by `WebhookMetadata#shop` (as documented/intended usage of this exact API), this can produce cross-tenant data corruption or injection under another merchant's identity.

### Likelihood Explanation
The attacker does not need the app's `client_secret`, an access token, or any credential beyond installing the app on a shop they control (a routine, unprivileged action) and the ability to send arbitrary HTTP requests to the app's public webhook callback URL. Capturing a legitimate HMAC + body pair from their own shop's webhook deliveries is straightforward (webhook deliveries are visible via the Partner Dashboard or a controlled receiving endpoint). Replaying with a different `shop` header is a trivial HTTP request modification.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value verified by the HMAC, or otherwise cross-check the header-derived `shop` against a value embedded in the signed payload before constructing `WebhookMetadata`. At minimum, document/enforce that `Registry.process` must not trust `request.shop` for authorization decisions unless it is corroborated by an out-of-band verified session/shop record, and consider including these headers in `to_signable_string` if compatible with Shopify's signing scheme, or require callers to validate `shop` against their own registered shop list post-HMAC-check.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) with attacker-controlled body content.
2. Attacker captures the resulting POST request, including `x-shopify-hmac-sha256: <valid_hmac>` and raw body `B`.
3. Attacker resends the identical request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, B)` against the unchanged `hmac` header: [5](#0-4) 
5. The handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)`, believing the attacker-crafted body legitimately originated from the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
