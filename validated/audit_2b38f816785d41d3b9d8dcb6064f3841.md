Based on my investigation, `jsonAPIError` at `core/web/helpers.go:21-29` writes `err.Error()` directly into the HTTP JSON response body via `models.NewJSONAPIErrorsWith(err.Error())`. The `SessionsController.Create` handler at `core/web/sessions_controller.go:56-60` calls `AuthenticationProvider().CreateSession(ctx, sr)` and, on any error, forwards that error string straight to the unauthenticated caller with `jsonAPIError(c, http.StatusUnauthorized, err)`.

However, when I traced the actual error strings produced by each `CreateSession` implementation, they are **already normalized to be indistinguishable regardless of account existence**:

- `core/sessions/localauth/orm.go:144-162` — `CreateSession` calls `FindUser`, and on a `sql.ErrNoRows` (nonexistent email) the raw db error is returned. But then, for existing users with bad password, it returns `pkgerrors.New("Invalid password")` and for bad email match `pkgerrors.New("Invalid email")` — these **are different strings for "user doesn't exist" vs "wrong password"**. [1](#0-0) 

- Similarly in `core/sessions/ldapauth/ldap.go:622-642` and `core/sessions/oidcauth/oidc.go:580-597`, `localLoginFallback` returns `errors.New("invalid email")` vs `errors.New("invalid password")` as distinguishable branches. [2](#0-1) [3](#0-2) 

Since `jsonAPIError` echoes `err.Error()` verbatim in the JSON response to an unauthenticated `/sessions` POST caller, an attacker submitting a login attempt can distinguish "no such user" (raw DB not-found error, or `"invalid email"`) from "wrong password" (`"invalid password"`/`"Invalid password"`), directly enabling **username/account enumeration** — the same bug class as the ZITADEL advisory (CWE-203, observable-response account-existence disclosure), reachable unauthenticated through the exposed `/sessions` endpoint at `core/web/router.go:215`.

This is a genuine analog: it's an unprivileged, internet-facing session/login endpoint, uses no mocked-only path, and directly maps to the bug class (distinguishable error responses revealing account existence to an unauthenticated actor).

### Title
Username/Account Enumeration via Distinguishable Login Error Messages - (File: core/web/sessions_controller.go)

### Summary
The unauthenticated `POST /sessions` login endpoint returns different, attacker-observable error messages depending on whether the submitted email corresponds to an existing account, allowing account/username enumeration analogous to CVE-2024-41952 (ZITADEL "ignoring unknown usernames").

### Finding Description
`SessionsController.Create` forwards any error returned by `AuthenticationProvider().CreateSession` directly to the HTTP client via `jsonAPIError(c, http.StatusUnauthorized, err)` [4](#0-3) , and `jsonAPIError` serializes `err.Error()` verbatim into the JSON response body [5](#0-4) .

The underlying authentication providers produce different error strings for "email doesn't match / user not found" versus "password mismatch":
- Local auth: `pkgerrors.New("Invalid email")` vs `pkgerrors.New("Invalid password")` [6](#0-5) 
- LDAP local fallback: `errors.New("invalid email")` vs `errors.New("invalid password")` [2](#0-1) 
- OIDC local fallback: `errors.New("invalid email")` vs `errors.New("invalid password")` [3](#0-2) 

The endpoint is registered unauthenticated, only rate-limited: `unauth.POST("/sessions", sc.Create)` [7](#0-6) .

### Impact Explanation
An unauthenticated network attacker can enumerate valid node-operator email/usernames by observing whether the login response says "invalid email" (account doesn't exist) versus "invalid password" (account exists, wrong password). This is low direct impact (CWE-203, information disclosure only — matches the referenced CVSS: C:L/I:N/A:N) but materially aids credential-stuffing/brute-force targeting of the Chainlink node's admin API, which controls job runs and funds movement.

### Likelihood Explanation
High likelihood of exploitability: the endpoint is unauthenticated and internet-facing by design, and the error text is deterministic and directly reflects the internal branch taken (email-not-found vs email-found-password-wrong). It is mitigated somewhat by the existing rate limiter (`rl.UnauthenticatedPeriod()`/`rl.Unauthenticated()`), which throttles but does not eliminate enumeration.

### Recommendation
Return a single generic error message (e.g., `"invalid email or password"`) for both the account-not-found and wrong-password cases across `localauth`, `ldapauth`, and `oidcauth` `CreateSession`/`localLoginFallback` implementations, and ensure `SessionsController.Create` does not leak provider-internal error text distinguishing these cases to the client.

### Proof of Concept
1. `POST /sessions` with `{"email":"nonexistent@test.com","password":"anything"}` → response body contains `"Invalid email"` (or DB not-found derived text).
2. `POST /sessions` with `{"email":"<known-existing-admin-email>","password":"wrongpassword"}` → response body contains `"Invalid password"`.
3. The differing message content between (1) and (2) lets the attacker confirm which emails are registered node-operator accounts.

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
