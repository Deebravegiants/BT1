### Title
Unchecked scaled-balance multiplication overflows and permanently freezes a market - (File: `common/src/rates/scaling.rs`)

### Summary
The fixed-point balance accounting can overflow `i128` when a sufficiently large scaled supply or debt balance is multiplied by a sufficiently high index. Interest accrual performs this conversion before mutating the market, so once the product exceeds the `i128` ceiling, `update_indexes`, `withdraw`, `repay`, liquidation, and even rate-model replacement revert repeatedly. [1](#0-0) [2](#0-1) 

### Finding Description
`Controller::supply` and `Controller::borrow` are public entrypoints that allow an unprivileged caller to create a large supplied market and high utilization. [3](#0-2)  Any caller can subsequently trigger `Controller::update_indexes`, which routes to pool accrual. [4](#0-3) 

Pool accrual loops over each requested market and calls `interest::global_sync`. [5](#0-4)  Each accrual chunk calls `accrue_step` with the stored scaled borrowed balance, scaled supplied balance, and indexes. [6](#0-5)  The utilization calculation converts scaled balances back to underlying RAY values through `scaled_to_original`, effectively multiplying scaled shares by their index. [7](#0-6) 

Because the exact value is constrained to `i128`, a market with approximately `1e9` units of an 18-decimal asset can exceed the representable range once its index rises above roughly `170×`. The panic occurs before the configured borrow-index cap can protect the market. [8](#0-7) 

### Impact Explanation
This permanently freezes all funds in the affected market. Interest accrual is attempted before normal market mutations, so suppliers cannot withdraw and borrowers cannot repay once the multiplication overflows. [9](#0-8) [10](#0-9)  Liquidation and bad-debt processing also depend on the same synchronized market state, preventing the protocol from resolving insolvency. `update_params` cannot safely rescue the market because it accrues interest under the old model before installing new parameters. [11](#0-10) 

The repository's long-horizon test demonstrates this exact terminal state: `update_indexes`, `withdraw`, and `repay` all fail with `MathOverflow`. [12](#0-11) 

### Likelihood Explanation
Likelihood is constrained by the required market size and index growth. The demonstrated setup uses a one-billion-whole-token market at 18 decimals and approximately 98% utilization, then lets the XLM rate curve compound until the aggregate value exceeds `i128::MAX`. [13](#0-12)  This is not a casual zero-cost attack, but it does not require privileged access once market configuration permits the size; any caller can supply, borrow, and invoke `update_indexes`. The resulting denial affects every user of that market, making this a Medium-severity permanent-freeze condition.

### Recommendation
Represent intermediate aggregate values in `I256`, or check `scaled_balance * index` before converting back to `i128`. If the result exceeds the representable range, cap the index or value before committing accrual rather than panicking. The index ceiling should be enforced before utilization recalculation so that `update_indexes`, repayment, withdrawal, liquidation, and governance rate-model replacement remain executable at the boundary.

### Proof of Concept
The repository already contains an executable scenario in `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`. [14](#0-13) 

Conceptually, an unprivileged caller can reproduce it as follows:

1. Supply `1_000_000_000 * 10^18` units of an 18-decimal borrow asset through:
   `supply(caller, 0, spoke_id, [(BIG18, 1_000_000_000 * 10^18)])`.
2. Supply sufficient collateral to the same account through another `supply` call.
3. Borrow 98% of the pool through:
   `borrow(caller, account_id, [(BIG18, 980_000_000 * 10^18)], Some(caller))`.
4. Advance ledger time while utilization remains high and repeatedly call:
   `update_indexes(caller, [BIG18])`.
5. Once `scaled_supply * supply_index` or `scaled_borrow * borrow_index` exceeds `i128::MAX`, `update_indexes` panics with `MathOverflow`.
6. Subsequent `withdraw`, `repay`, `liquidate`, or `clean_bad_debt` calls attempt accrual first and panic on the same overflow, leaving all market balances frozen.

fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
