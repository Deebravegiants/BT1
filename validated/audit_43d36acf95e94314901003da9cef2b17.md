## Analog Found

### Title
Shared `CallDispatcher` permits unrestricted arbitrary calls, enabling persistent ERC20 approval theft of tokens routed to it by other users - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch()` executes any `Call{to, value, data}` supplied by whoever invokes it, with zero restriction on the target contract or function selector [1](#0-0) . This is the exact bug class from the report: a single shared "executor" contract that anyone can drive to call arbitrary functions on arbitrary targets. Unlike the report's isolated `executorAddress`, this `CallDispatcher` is a **single shared, stateful (via ERC20 allowances) singleton** reused across every `IntentGatewayV2` order (`predispatch`/`output.call`) and every `HyperFungibleToken`/`WrappedHyperFungibleToken` cross-chain calldata execution, configured once as `_params.dispatcher` / `_dispatcher` [2](#0-1) .

### Finding Description
Any user can place an `IntentGatewayV2` order whose `predispatch.call` or `output.call` is an ABI-encoded `Call[]` containing `IERC20(token).approve(attacker, type(uint256).max)` targeted at an arbitrary ERC20 token, with `to = token` and no restriction preventing this [1](#0-0) . Because `CallDispatcher` is the caller (`msg.sender`) of that `approve`, the allowance `allowance[CallDispatcher][attacker]` is written into the token's persistent storage and **survives indefinitely across transactions** — it is not reset by any sweep logic in the gateway, since the sweep logic only moves balances (`transfer`), never touches allowances [3](#0-2) .

For `IntentGatewayV2`, the balance-sweeping in `placeOrder`/`_execute` is scoped only to that specific order's own `inputs`/`output.assets` token list, using `balanceOf(dispatcher)` at that moment [4](#0-3) . Any token balance left on the dispatcher that isn't part of the current order's own token list is never accounted for or swept.

More directly exploitable: `HyperFungibleTokenUpgradeable.onAccept` mints tokens to `beneficiary` (which the sender can set to the `CallDispatcher` address per the documented "swap-then-forward" pattern) and then executes the attached calldata via `ICallDispatcher(_dispatcher).dispatch(message.data)` — with **no subsequent sweep or dust-collection step** [5](#0-4) . If the attached calls don't fully spend the minted balance (e.g., a partial swap, a call that reverts on the full amount, or calldata that simply doesn't move 100% of the tokens), the leftover balance remains parked in the shared `CallDispatcher` indefinitely.

Combining these: an attacker (1) plants a persistent `approve(attacker, MAX)` on token `T` via one cheap `IntentGatewayV2.placeOrder` (or an HFT `send` with calldata) routed through the shared dispatcher, then (2) waits for any other unrelated user's HFT cross-chain transfer (or any flow that leaves residual `T` balance on the dispatcher) to leave tokens behind, and (3) calls `T.transferFrom(dispatcher, attacker, leftoverAmount)` directly — an ordinary, permissionless call requiring no interaction with the gateway at all.

### Impact Explanation
This is a concrete theft-of-funds vector: any tokens of a type the attacker has pre-approved that end up resting on the shared `CallDispatcher` — even momentarily uncollected dust from a legitimate user's cross-chain calldata execution — can be drained by the attacker via a plain `transferFrom`. Because the dispatcher is shared across all `IntentGatewayV2` orders and all `HyperFungibleToken`/`WrappedHyperFungibleToken` deployments pointing at it, the blast radius is every user who ever routes that token type through calldata execution on that chain, not just the attacker's own order.

### Likelihood Explanation
Likelihood is high for the "plant the approval" step: it costs only a normal `placeOrder`/`send` call with attacker-chosen calldata, no privileged access needed, matching exactly the "user can call any function of executorAddress" pattern in the reference report. The "collect leftover balance" step depends on some other flow leaving tokens on the dispatcher, which is most reliably achievable via the unswept `HyperFungibleTokenUpgradeable.onAccept` path where a beneficiary sets `to = CallDispatcher` and the developer-supplied calldata doesn't move 100% of the minted amount.

### Recommendation
- Restrict `CallDispatcher.dispatch` calls from ever invoking privileged/stateful functions like `approve`/`increaseAllowance` on arbitrary tokens on behalf of the dispatcher, or disallow persistent state changes entirely (e.g., only allow `transfer`/`call` patterns that move funds out atomically, never leave allowances).
- Alternatively, deploy an ephemeral (e.g., `CREATE2`-then-`SELFDESTRUCT`, or per-order minimal-proxy) dispatcher instance per order/message instead of one long-lived shared contract, so no approval or balance can persist across unrelated flows.
- Add an explicit "revoke all approvals granted during this call batch" step, or sweep/verify zero balance for every token the calldata touched (not just the order's declared input/output list) before returning control.
- For `HyperFungibleToken`/`WrappedHyperFungibleToken`, add a mandatory dust-sweep of the minted token back from the dispatcher to the beneficiary after calldata execution, mirroring `IntentsBase._execute`'s sweep pattern.

### Proof of Concept
1. Attacker calls `IntentGatewayV2.placeOrder` with a trivial/self-funded order whose `predispatch.call` (or `output.call`) is `abi.encode([Call({to: TOKEN, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)})])`. `CallDispatcher.dispatch` executes it unconditionally [1](#0-0) ; `allowance[CallDispatcher][attacker] = type(uint256).max` for `TOKEN` is now permanently set.
2. Separately, a victim uses `HyperFungibleTokenUpgradeable.send` with `to = CallDispatcher` and `data` encoding a `Call[]` meant to only partially route `TOKEN` (e.g., a swap for less than the full minted amount, or a call that no-ops on the remainder). On delivery, `onAccept` mints `TOKEN` to the `CallDispatcher` and executes the calldata with no post-sweep [5](#0-4) , leaving residual `TOKEN` balance on the dispatcher.
3. Attacker calls `TOKEN.transferFrom(CallDispatcher, attacker, residualAmount)` directly, using the allowance planted in step 1, draining funds that belonged to the victim's cross-chain transfer.

**Note:** I was not able to fully trace every possible code path that could leave a non-zero token balance on `CallDispatcher` beyond the `HyperFungibleTokenUpgradeable.onAccept` case identified above (e.g., whether `WrappedHyperFungibleTokenUpgradeable` or the tron variant of `IntentGatewayV2` have equivalent gaps) due to iteration limits — a full audit of every dispatcher-touching flow across `evm/src/apps`, `sdk/packages/core/contracts/apps`, and `evm/tron/contracts/apps` would be needed to enumerate all exploitable residual-balance windows.
