### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature only over the raw request body, while the `shop` (and `topic`, `api_version`, `webhook_id`) values are taken from unauthenticated HTTP headers and passed straight through to the app's webhook handler as trusted identity. Because the app's `api_secret_key` is shared across every shop that installs the app, any merchant who receives a legitimately-signed webhook for their own shop can replay that same body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop, and the signature will still validate.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor simply reads the `shop-domain` header without any cryptographic binding to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` only ever verifies `verifiable_query.to_signable_string` (i.e., the body) against `verifiable_query.hmac`: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed to the app's handler, with no cross-check that the shop is the one the body was actually generated for: [4](#0-3) 

`WebhookMetadata.shop` is a plain `T::Struct` field with no additional verification, and this is the value host applications are expected to use as the tenant identifier when processing the webhook payload: [5](#0-4) 

The identity binding that should hold is: `shop the HMAC was computed for == shop attributed to the webhook payload`. Because `to_signable_string` excludes the `shop-domain` header, this equality is never enforced by the gem — the HMAC only proves "signed with this app's secret," not "signed for this specific shop." Since `api_secret_key` is one value shared by the app across all its installed shops (not shop-specific), a legitimate merchant who installed the app can:
1. Trigger a real webhook delivery to their own endpoint for shop A, capturing the genuine `raw_body` and `x-shopify-hmac-sha256` value.
2. Replay that exact body and HMAC to the app's webhook endpoint, but with `x-shopify-shop-domain` set to shop B (or any other installed shop).
3. `Utils::HmacValidator.validate` succeeds (the body/secret pair is valid), and `Registry.process` hands the handler a `WebhookMetadata` claiming `shop: "shop-B.myshopify.com"` even though the payload actually originated from shop A.

This is a cross-tenant identity break directly caused by the gem's design of exposing an unauthenticated `shop` field as if it were verified alongside the HMAC.

### Impact Explanation
This enables cross-tenant data injection/confusion: a webhook handler that uses `data.shop` to select which merchant's database records to create/update/delete (a standard and expected pattern per the library's own documentation and `WebhookMetadata` struct) can be tricked into writing or deleting data belonging to shop A under shop B's tenant context, or vice versa — without ever having shop B's credentials. This matches the "Critical — cross-tenant access" impact category, since the boundary crossed is between two independently authenticated merchant tenants of the same app.

### Likelihood Explanation
Likelihood is significant for any app that supports more than one merchant installation (the normal case for public/multi-tenant apps) and follows the documented webhook processing flow via `ShopifyAPI::Webhooks::Registry.process`. Any user with access to their own shop's admin (an "unprivileged internet user" relative to other tenants) can trigger arbitrary webhook topics for their own shop (e.g. by performing actions like updating a product) and capture the resulting signed payload/HMAC pair, then replay it with a forged shop header — no access to the app's `api_secret_key` or any other tenant's credentials is required.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook_id`, `api_version`) header values in the signable string used for HMAC verification, or otherwise cryptographically bind the shop claim to the signature (e.g., verify the shop against a per-shop secret/session record established at install time, or require the app to independently confirm the delivered shop is one that legitimately installed the app before trusting `data.shop`). At minimum, document this gap prominently so host apps cannot assume `WebhookMetadata.shop` is verified data.

### Proof of Concept
```ruby
require "shopify_api"

ShopifyAPI::Context.setup(
  api_key: "key",
  api_secret_key: "shared_app_secret", # same secret for shop A and shop B installs
  api_version: "2024-01",
  is_embedded: true,
  is_private: false,
)

# Step 1: Attacker (owner of shop A) triggers a real webhook and captures
# the genuine raw_body + hmac Shopify computed using the shared api_secret_key.
raw_body = '{"id":123,"note":"legit data from shop A"}'
hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "shared_app_secret", raw_body)
)

# Step 2: Attacker replays the same body+hmac, but swaps the shop-domain header
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac,          # still valid! body/secret unchanged
  "x-shopify-shop-domain" => "shop-b.myshopify.com", # victim tenant, forged
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HmacValidator.validate(request) => true, because only raw_body is checked.
# Registry.process(request) will invoke the app's handler with
# WebhookMetadata(shop: "shop-b.myshopify.com", body: {...from shop A...}),
# i.e. shop A's data attributed to shop B.
ShopifyAPI::Webhooks::Registry.process(request)
```
