### Title
Anyone can permanently cancel any other user's pending `EmporiumStack` by front-running `emporiumMessage` - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`cancelEmporiumMessage` only verifies that the caller (`msg.sender`) produced *some* valid EIP-712 signature over `EmporiumCancel(message)`, but `message` is a bare `uint256` with no cryptographic binding to the actual owner of that message (`stack.signerAddress`) that would eventually consume it in `verifyWallet`. Any unprivileged attacker can therefore self-sign `EmporiumCancel(M)` for an arbitrary `M` value belonging to another user's not-yet-relayed `EmporiumStack`, permanently marking `usedMessages[M] = true` and freezing the victim's pending action.

### Finding Description
The broken equality is:

`AUTHORITY(message M)` (the party who legitimately owns/created the `EmporiumSignature` for `M`, i.e. `stack.signerAddress`) `!= ACCOUNT THAT CANCELLED M` (whoever's key produced a valid signature over `EmporiumCancel(M)`).

`cancelEmporiumMessage` performs: [1](#0-0) 

The recovered signer is only checked against `msg.sender` — never against the `signerAddress` that is bound to `M` inside the original `EmporiumSignature`. Since `EMPORIUM_CANCEL_TYPEHASH` is `keccak256("EmporiumCancel(uint256 message)")`, it carries no reference to any particular signer/owner: [2](#0-1) 

Any attacker, knowing (or observing) the public `message` value `M` for a victim's queued, not-yet-relayed `EmporiumStack`, can trivially self-sign `EmporiumCancel(M)` with their own private key (the typed-data hash depends only on `M`, and `msg.sender` in the check is the attacker's own address). This passes `ECDSA.tryRecover`/`recoveredAddress == msg.sender` and sets: [3](#0-2) 

When the victim's legitimate flow later reaches `verifyWallet` during `runAction`, it reverts because the message is already used: [4](#0-3) 

None of the existing guards (`performHinkalChecks`, `verifyProof`, `rootHashExists`, nullifier insertion, etc.) protect against this because the cancellation path is completely independent of proof verification — it is a standalone, unauthenticated-with-respect-to-`M` state mutation on shared storage (`EmporiumStorageVars.usedMessages`), reachable by any external account with zero cost beyond gas and one signature.

### Impact Explanation
The victim's queued `EmporiumStack`/message becomes permanently unusable: any subsequent legitimate `transact`/`runAction` call using proof data referencing `emporiumMessage = M` reverts with `UsedMessage()` forever, since the nonce space (`usedMessages` mapping) cannot be reset or reused. This permanently freezes the victim's queued shielded operation (and any funds/UTXOs whose spend was structured around that specific message/nullifier set), matching the "permanent freezing of user funds" Critical category. The attack is repeatable against any victim message and costs the attacker only gas and a self-generated signature.

### Likelihood Explanation
- Precondition: the attacker must learn `M` before it's relayed/executed — the message is a plain public `uint256` field of `CircomData`/`EmporiumStack` that is visible once broadcast to relayers, in a public mempool, or otherwise disclosed off-chain prior to on-chain execution, which is a normal part of the relay flow.
- No special role is required: `cancelEmporiumMessage` is `external` with no access control beyond a self-produced valid signature over an attacker-controlled `EmporiumCancel(message)`.
- Cost is a single signature and one transaction; fully repeatable across arbitrary victim messages.

### Recommendation
Bind the `EmporiumCancel` typed-data or the on-chain check to the actual `signerAddress` of the corresponding `EmporiumStack`/`EmporiumSignature`, not merely to `msg.sender`. Concretely, require that `recoveredAddress` matches the same `signerAddress` that was (or will be) used to authorize operations under `message` — e.g., have callers submit the associated `signerAddress` (and validate it's the legitimate owner via the original stack/commitment), or restrict cancellation such that only the account that could have produced a valid `EmporiumSignature(message, ...)` (i.e., verified against `stack.signerAddress`) can burn that `message`.

### Proof of Concept
Foundry test outline:
1. Deploy `EmporiumUpgradeable`, initialize with a Hinkal helper and owner.
2. Victim (`signerV`) constructs an `EmporiumStack` with `signerAddress = signerV` and some `message = M` (arbitrary victim-chosen uint256, simulating a Poseidon-derived public output).
3. Do NOT call `runAction`/`verifyWallet` yet (simulate "not-yet-relayed").
4. Attacker (`attackerA`, unrelated EOA) computes `hashedMessage = _hashTypedDataV4(keccak256(abi.encode(EMPORIUM_CANCEL_TYPEHASH, M)))` and signs it with `attackerA`'s own private key.
5. Attacker calls `cancelEmporiumMessage(M, v, r, s)` from `attackerA` — assert it succeeds (no revert) and `usedMessages[M] == true` (assert via a subsequent call reverting, since mapping is private — can instead directly assert via a follow-up `runAction` attempt).
6. Victim then attempts the legitimate flow (`runAction`/`verifyWallet` path with `circomData.emporiumMessage = M`) — assert it reverts with `UsedMessage()`.
7. Assert the equality broken: `attackerA != signerV` yet `usedMessages[M]` was set by `attackerA`'s call, permanently blocking `signerV`'s legitimate operation.

```text
    function cancelEmporiumMessage(uint256 emporiumMessage, uint8 v, bytes32 r, bytes32 s) external {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(abi.encode(EMPORIUM_CANCEL_TYPEHASH, emporiumMessage))
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(hashedMessage, v, r, s);
        bool verified = err == ECDSA.RecoverError.NoError && recoveredAddress == msg.sender;
        if (!verified) {
            revert InvalidSignature();
        }

        $.usedMessages[emporiumMessage] = true;
    }
```
