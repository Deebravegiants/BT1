### Title
`Webhooks::Request#initialize` accepts unsigned `shop`/`topic` headers while `HmacValidator` only signs the raw body, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC verified by `Utils::HmacValidator.validate` covers none of the `x-shopify-shop-domain` or `x-shopify-topic` headers. Because the `api_secret_key` used to sign webhooks is per-app (shared across every shop that installs the app), an attacker who installs the target app on their own shop can capture one genuinely-signed webhook body and replay it to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header naming a victim merchant; the signature still validates and the handler receives `WebhookMetadata#shop` set to the forged victim shop.

### Finding Description
The intended binding is: `bytes signed by compute_signature(request.to_signable_string, secret)` == `bytes the host app trusts to select which merchant's records to touch`. In `Webhooks::Request`: [1](#0-0) 

`to_signable_string` returns `@raw_body` exclusively — it never includes `@headers`. Yet `shop` and `topic` are read straight from attacker/Shopify-supplied headers with no cryptographic tie to the body: [2](#0-1) 

`Registry.process` verifies only the body-derived HMAC, then trusts `request.shop` and `request.topic` to build `WebhookMetadata`, which the host app uses to route work to a specific merchant's job queue/records: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` only ever hash `verifiable_query.to_signable_string` (the raw body) with `Context.api_secret_key`: [4](#0-3) 

`Context.api_secret_key` is a single, app-wide (client) secret, not scoped per shop — every shop that installs the app shares the same signing key. Consequently the invariant "bytes passed to `compute_signature`" == "bytes later parsed and acted on for tenant selection" is false: the signature covers only the JSON body, while the tenant-selection value (`shop`) and handler-selection value (`topic`) travel unsigned in headers.

**Attacker's exact request:** The attacker (unprivileged, per the rules) creates their own development shop, installs the target app, and lets it deliver a genuine webhook (e.g. `orders/create`) to their own controlled endpoint — capturing the raw body and its valid `x-shopify-hmac-sha256` value. They then POST that identical body + HMAC header to the app's real public webhook route, but replace `x-shopify-shop-domain` with the victim's shop domain (and optionally alter `x-shopify-topic` to select a different handler than the one that actually produced the body). Because `to_signable_string` is body-only, `HmacValidator.validate` still returns `true`. `Registry.process` then invokes the handler with `WebhookMetadata#shop == victim-shop` and `WebhookMetadata#topic` as forged, causing the host app (per its documented usage, e.g. `docs/usage/webhooks.md`'s example `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) to enqueue/act on data attributed to the victim shop using attacker-supplied body content.

**Why existing guards fail:** `HmacValidator.validate` (checked in `Registry.process`) only guarantees the body bytes were signed by someone holding `api_secret_key` — it says nothing about which shop or topic the signer intended, since those are carried in unsigned headers. There is no `ShopValidator.sanitize!` or shop-membership check anywhere in `Registry.process`; nothing cross-checks `request.shop` against the session/shop that legitimately owns the signed body.

### Impact Explanation
Any shop that has ever installed the app (including an attacker's own trial/dev shop) can produce arbitrarily many "validly signed" webhook deliveries whose `shop`/`topic` metadata is fully attacker-controlled, because the shared app secret signs only the body. This lets one merchant's request cause the host app to read or mutate a different merchant's data (cross-tenant access), and is repeatable against arbitrary victim shop domains for any topic the attacker's own shop can generate a payload for. This matches the "Critical – cross-tenant access" impact category.

### Likelihood Explanation
Preconditions are low-cost and fully within the stated attacker capability: create a free development shop, install the target app (a normal, unprivileged action), receive one genuine webhook, and replay it with a modified header to the app's already-public webhook endpoint. No secrets, tokens, or privileged access are required. It requires the host app to key its business logic off `WebhookMetadata#shop` without independently verifying the shop against its own session/install records — this is the pattern shown in the gem's own documentation example, so it is a realistic real-world configuration.

### Recommendation
Bind the shop/topic identity cryptographically to the verified request instead of trusting unsigned headers: either (a) include the normalized `shop`, `topic`, and `webhook_id` headers in the signable string used by `to_signable_string`/`compute_signature` (this would be a breaking change vs. Shopify's documented HMAC scheme, so coordinate with Shopify's webhook spec), or (b) require host apps to cross-validate `WebhookMetadata#shop` against a known, previously-established session/installation record before trusting it, and document this requirement prominently, and/or (c) additionally validate that `shop` is a syntactically valid `*.myshopify.com` domain and matches an existing OAuth session for that exact shop before dispatching to the handler.

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (new test)
require "test_helper"

class RegistryCrossTenantTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    @handler = mock
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/create", delivery_method: :http, handler: @handler, path: "cb"
    )
  end

  def test_forged_shop_header_still_passes_hmac_and_is_handed_to_handler
    raw_body = '{"id":1,"note":"attacker-controlled"}'
    secret = ShopifyAPI::Context.api_secret_key
    valid_hmac = Base64.strict_encode64(
      OpenSSL::HMAC.digest("sha256", secret, raw_body)
    )

    headers_attacker_shop = {
      "x-shopify-hmac-sha256" => valid_hmac,
      "x-shopify-topic" => "orders/create",
      "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
      "x-shopify-webhook-id" => "1", "x-shopify-api-version" => "2023-10",
    }
    headers_victim_shop = headers_attacker_shop.merge(
      "x-shopify-shop-domain" => "victim-shop.myshopify.com"
    )

    req_attacker = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers_attacker_shop)
    req_victim   = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers_victim_shop)

    # Same bytes, same HMAC, different (unsigned) shop claim:
    assert_equal req_attacker.hmac, req_victim.hmac
    assert ShopifyAPI::Utils::HmacValidator.validate(req_attacker)
    assert ShopifyAPI::Utils::HmacValidator.validate(req_victim) # <-- passes despite forged shop

    @handler.expects(:handle).with(
      data: ShopifyAPI::Webhooks::WebhookMetadata.new(
        topic: "orders/create", shop: "victim-shop.myshopify.com",
        body: JSON.parse(raw_body), api_version: "2023-10", webhook_id: "1"
      )
    )
    ShopifyAPI::Webhooks::Registry.process(req_victim)
  end
end
```
This demonstrates: identical signed bytes (`raw_body`), identical valid HMAC, yet divergent trusted `shop` identity accepted by `Registry.process`, satisfying the required byte-identity violation and cross-tenant impact with no live shop or secret access needed beyond the gem's own configured test secret.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(signable_string: String, secret: String).returns(String) }
        def compute_signature(signable_string, secret)
          OpenSSL::HMAC.hexdigest(
            OpenSSL::Digest.new("sha256"),
            secret,
            signable_string,
          )
        end
