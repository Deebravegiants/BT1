### Title
`token_exchange` sends the app's `client_secret` to an attacker-chosen host because the shop is taken from an unvalidated JWT `dest` claim - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ClientCredentials.client_credentials` and `RefreshToken`/`Storefront` all pass the caller-supplied `shop` through `Utils::ShopValidator.sanitize!` before it is used to build the request host, as seen in `lib/shopify_api/auth/client_credentials.rb:25`. `TokenExchange.exchange_token`, however, derives the shop directly from the JWT `dest` claim without ever calling `ShopValidator`, and then uses that raw value to build the HTTP host that receives the app's `client_secret`.

### Finding Description
`ShopifyAPI::Auth::TokenExchange.exchange_token` does: [1](#0-0) 

`dest_shop` comes straight from `jwt_payload.shop`, which is simply `@dest.gsub("https://", "")` from the JWT payload: [2](#0-1) 

`JwtPayload#initialize` only verifies the token's signature and that `aud == Context.api_key`; it performs no check that `iss`/`dest` is a `*.myshopify.com` (or other trusted Shopify) domain: [3](#0-2) 

That unsanitized `dest_shop` is then used to build `shop_session`, whose `shop` attribute later becomes the request host in `Clients::HttpClient`: [4](#0-3) [5](#0-4) 

Compare this to the sibling flow `ClientCredentials.client_credentials`, which explicitly calls `Utils::ShopValidator.sanitize!(shop)` before constructing the session used for the very same `HttpClient` request path that carries `client_id`/`client_secret`: [6](#0-5) 

The identity binding that should hold is: **`shop` used to select the HTTP destination for the client-secret-bearing token request == a value drawn from `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`** (`lib/shopify_api/utils/shop_validator.rb:9-18`). In `token_exchange.rb` this binding is broken: the value used for the destination host is only checked to be *inside a JWT whose signature validates against the app secret*, not to be a legitimate Shopify-owned domain. Since the JWT's `aud` must equal the app's `api_key` but nothing constrains `dest`/`iss` to a Shopify domain, and `JwtPayload#==` / equality checks never involve domain allow-listing either.

### Impact Explanation
If an app ever passes attacker-influenced input into `exchange_token` as a session token that was minted for a `dest` value outside `*.myshopify.com` (e.g., a spoofed/relayed App Bridge session token, or a token obtained via an app-embedding trick where the host page controls what `dest` looks like before the token is even generated upstream), the resulting `TokenExchange` request will place the real `client_id` and `client_secret` in a POST body sent to `https://#{dest_shop}/admin/oauth`. This is SSRF-with-credentials: the app's `client_secret` is transmitted to a host the gem itself never validates as a genuine Shopify tenant, unlike the parallel `client_credentials` and `refresh_token` flows which enforce `ShopValidator.sanitize!` on exactly this same class of request.

### Likelihood Explanation
This requires a session token whose `dest` claim is attacker-influenced but still signed by a party the app trusts to have `aud == api_key` (or with the JWT decode/verify boundary otherwise satisfied). The gem cannot control what upstream signs this token, so exploitability depends on how the host embeds/receives session tokens; nonetheless, within this gem's own code, `token_exchange.rb` is the *only* client-secret-carrying flow that skips the `ShopValidator` check that its sibling flows apply, which is itself a code-level defect regardless of upstream token provenance.

### Recommendation
In `lib/shopify_api/auth/token_exchange.rb`, sanitize `dest_shop` the same way `client_credentials.rb` and `refresh_token.rb` do, e.g. `dest_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)`, and raise `Errors::InvalidShopError` if it doesn't resolve to a trusted Shopify domain before constructing `shop_session`/issuing the HTTP request.

### Proof of Concept
Not independently exploitable purely from this gem's code without a way to mint a signed session token with a non-Shopify `dest`; the finding is the missing invariant (comparable to `client_credentials.rb`'s explicit `ShopValidator.sanitize!` call) rather than a demonstrated end-to-end exploit chain, since token minting occurs outside this repository's scope.
