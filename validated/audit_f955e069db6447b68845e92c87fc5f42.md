Audit Report

## Title
`ERC20Transactor` assumes exact requested amount is transferred by arbitrary ERC20 contracts, enabling shared-checking-account balance-shortfall DoS - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` call the target contract's `IERC20::transfer` and, upon a boolean `true` return, unconditionally trust that the *requested nominal* `amount` (not an observed balance delta) was moved, crediting/debiting that exact amount into XCM holding and a single pooled `TransfersCheckingAccount`. Because the matcher (`ERC20Matcher`) accepts any `AccountKey20` location as a valid ERC20 asset with no allow-list, an unprivileged user can permissionlessly deploy a non-conforming/rebasing-style ERC20 contract and route it through this exact path, creating a real risk of the shared checking account's on-chain balance drifting below what XCM holdings assume it holds.

## Finding Description
In `withdraw_asset_with_surplus`, after `bare_call` to the ERC20 contract's `transfer(checking_address, amount)` succeeds and decodes to `true`, the code does `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` using the caller-supplied `amount`, not any post-call balance check. [1](#0-0)  Symmetrically, `deposit_asset_with_surplus` transfers the same nominal `amount` out of `TransfersCheckingAccount` to the beneficiary, trusting only the boolean success return. [2](#0-1)  The `Erc20Credit` type's own doc comment confirms this design assumption — "the actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime." [3](#0-2) 

Critically, the `ERC20Matcher` used in the asset-hub-westend runtime configuration matches *any* location with an `AccountKey20` junction — there is no curated allow-list of "safe"/standards-conforming ERC20 contracts: `pub type ERC20Matcher = MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;` [4](#0-3)  and `IsLocalAccountKey20` simply checks the junction shape. [5](#0-4)  This is corroborated by the repo's own tests, which deploy arbitrary contracts via `bare_instantiate` and immediately use their address in `AccountKey20` locations inside XCM `withdraw_asset`/`deposit_asset` instructions with no prior registration step. [6](#0-5)  The `TransfersCheckingAccount` (`ERC20TransfersCheckingAccount`) is a single pooled account for all ERC20 assets/users in the runtime config. [7](#0-6) 

The existing test suite (`smart_contract_does_not_return_bool_fails`, `expensive_erc20_runs_out_of_gas`, etc.) only covers revert/decode-failure/gas-exhaustion cases — none test or guard against a contract that returns `true` while transferring less than `amount` (the stETH-style rounding scenario). No balance-before/after check exists anywhere in the transactor to catch this.

## Impact Explanation
If a routed ERC20 contract ever transfers less than the nominal `amount` while returning `true` (rebasing/share-accounting/fee-on-transfer semantics), the shared checking account's real token balance can fall behind what XCM holdings assumed was credited. Since deposits pull the nominal (not verified) amount back out of the same shared account, this can cause `IERC20::transfer` from the checking account to revert/return `false` due to insufficient real balance, surfacing as `XcmError::FailedToTransactAsset` and trapping assets/failing the XCM message — for the triggering message and potentially for other users' subsequent transfers of the same asset if the deficit persists in the pooled account. No direct fund theft occurs since the ERC20 contract's own accounting stays authoritative, but the DoS/asset-trapping impact is concrete and matches an in-scope class (broken accounting assumption leading to message/asset failures).

## Likelihood Explanation
This is triggerable by a fully unprivileged user: `pallet-revive` contract deployment is permissionless, and `ERC20Matcher`/`IsLocalAccountKey20` impose no allow-list — any `AccountKey20` address can be used as an XCM asset routed through `ERC20Transactor`, as directly demonstrated by the repo's existing tests using freshly deployed, non-standard contracts. The likelihood of actual exploitation still depends on whether a production runtime deployment restricts which ERC20 contracts are practically discoverable/tradeable via other layers (e.g., front-ends, indexers) — an XCM-level restriction is not present in this code path itself.

## Recommendation
Do not trust the requested `amount` or the boolean return value as proof of exact transfer. Query the ERC20 balance of the checking account/beneficiary before and after the `transfer` call and use the observed delta to construct `Erc20Credit`/drive the deposit amount. Consider replacing the single shared `TransfersCheckingAccount` with a per-asset or per-transaction isolated escrow so that a shortfall on one asset cannot cascade into failures for unrelated transfers of the same asset.

## Proof of Concept
1. Deploy (as any unprivileged user) an ERC20-like contract via `pallet-revive` whose `transfer(to, value)` moves `value - 1` wei internally but returns `true` (legal per ERC20 spec; mirrors stETH's documented rounding behavior) — analogous to the existing `MyTokenFake`/`MyTokenExpensive` test fixtures used in `asset-hub-westend/tests/tests.rs`.
2. Reference this contract's address directly as an `AccountKey20` location in an XCM `WithdrawAsset`/`DepositAsset` program, exactly as done in `withdraw_and_deposit_erc20s` and `smart_contract_does_not_return_bool_fails`.
3. Observe that `withdraw_asset_with_surplus` credits the full nominal `amount` into holding while the checking account's real balance increases by less.
4. Repeat across multiple messages/users of the same contract until the checking account's real balance for that asset is insufficient to satisfy a subsequent `deposit_asset_with_surplus` call, producing `XcmError::FailedToTransactAsset` and asset trapping for an unrelated user's message using the same ERC20 asset.
