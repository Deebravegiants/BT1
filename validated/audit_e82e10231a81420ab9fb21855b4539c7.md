Based on the codebase, the strongest analog to the oracle-confidence-check bug class is a quorum/threshold verification gap in the BSC consensus light client, which is reachable by any relayer submitting a BSC consensus update to Hyperbridge.

### Title
Insufficient BSC validator supermajority threshold allows forged consensus finalization - ([File: modules/consensus/bsc/verifier/src/lib.rs])

### Summary
The `verify_bsc_header` function in the ismp-bsc consensus client checks that the number of participating validators meets a "supermajority" threshold before accepting a BSC (Parlia/BEP-126) finalization vote and mining an intermediate state commitment. Unlike every other consensus verifier in this codebase (BEEFY, sync-committee, Pharos), which enforce a strict `> 2n/3` (i.e. `>= floor(2n/3)+1`) bar, the BSC verifier accepts participation as low as `>= floor(2n/3)` — one signer short of the majority the BSC Parlia protocol itself requires for safety.

### Finding Description
`verify_bsc_header` computes the threshold check as: [1](#0-0) 

```rust
// We have to use the same threshold specified in the bsc parlia consensus which is 2/3
// https://github.com/bnb-chain/bsc/blob/.../parlia.go#L557
let participant_count = validators_bit_set
    .iter()
    .take(current_validators.len())
    .filter(|bit| **bit)
    .count();
if participant_count < ((2 * current_validators.len()) / 3) {
    Err(Error::NotEnoughParticipants)?
}
```

This rejects only when `participant_count < floor(2n/3)`, i.e. it *accepts* any `participant_count >= floor(2n/3)`. The actual upstream BSC/Parlia rule cited in the comment is `cnt*3 > len*2` (strictly greater than two-thirds). For `n=21` that requires `cnt > 14`, i.e. `cnt >= 15`; but the Rust implementation here accepts `cnt == 14` (exactly `floor(2*21/3)`), one signer below the real BSC finality bar. This is confirmed by the module's own test comments describing "threshold is 14" for `n=21`.

Contrast this with the sibling verifiers in the same codebase, which all use the correct `(2n/3)+1` strict-majority form: [2](#0-1) [3](#0-2) [4](#0-3) 

Each of those explicitly adds `+ 1` to `(2*total)/3` to guarantee a true supermajority (tolerating up to `floor((n-1)/3)` Byzantine validators). The BSC verifier's off-by-one under-counts the required quorum by exactly the margin that separates "supermajority" from "exactly 2/3," which is precisely the boundary where a Byzantine-fault-tolerant assumption (`f < n/3`) can be violated: with `n=3f+1` (`f` malicious), a valid BSC finalization always needs `2f+1` honest signers, but this check can be satisfied with only `2f` signers, some or all of which could be colluding malicious validators sitting exactly at the fault-tolerance boundary.

### Impact Explanation
The BSC verifier's output directly produces a `VerificationResult` with a finalized header and state root that is committed to `EvmHost`/`IsmpHost` state as a trusted, verified BSC state commitment (`modules/ismp/clients/bsc`). Any relayer/prover can submit a `BscClientUpdate`. If an attacker controls (or colludes to reach) a coalition of validators at the fault-tolerance boundary, they can produce a valid BLS aggregate signature over a finalization vote that would be rejected by genuine BSC nodes but is accepted here, forging a state commitment. This is a consensus-unsoundness bug that can lead to forged message delivery / unbacked mint on chains that trust BSC state proofs relayed through Hyperbridge (e.g., token bridge mint against a bogus BSC state root).

### Likelihood Explanation
The path is reachable from a single relayed consensus proof (`verify_bsc_header`), with no privileged role required beyond being a permissionless consensus relayer/prover, matching the reachable-surface constraints (consensus verification for BSC). Exploitation additionally requires colluding validator signatures right at the `f < n/3` boundary, which is a real but non-trivial precondition (same class of assumption BEEFY/sync-committee/Pharos correctly harden against with their `+1`).

### Recommendation
Change the BSC participation check to match the strict supermajority form used elsewhere in the codebase and match the actual Parlia rule `cnt*3 > len*2`:
```rust
if participant_count * 3 <= current_validators.len() * 2 {
    Err(Error::NotEnoughParticipants)?
}
```
or equivalently `if participant_count < ((2 * current_validators.len()) / 3) + 1`, mirroring `check_participation_threshold` in the BEEFY verifier.

### Proof of Concept
1. Configure a BSC validator set of `n=21` (as in the module's own tests).
2. Construct a `BscClientUpdate` whose `vote_address_set` bitset has exactly 14 in-range bits set (below the true BSC `cnt > 14` requirement, but at/above the Rust check's `>= 14` bar).
3. Produce a valid BLS aggregate signature from those 14 validators over the vote data (achievable if an attacker controls a fault-boundary coalition).
4. Call `verify_bsc_header` — the participation check at [5](#0-4)  passes, allowing the header to finalize despite not meeting BSC's real consensus finality bar, and the resulting state commitment is submitted to Hyperbridge as canonical BSC state.

/// Verify that participating validators have more than 2/3 of total stake.
fn verify_stake_threshold(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let participating_stake = validator_set.participating_stake(participants);
	let total_stake = validator_set.total_stake;
	let required = (total_stake * 2 / 3) + 1;

	if participating_stake >= required {
		Ok(())
	} else {
		Err(Error::InsufficientStake {
			participating: participating_stake,
			required,
			total: total_stake,
		})
	}
}
