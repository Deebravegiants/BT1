### Title
Escrow and fee balances are decremented after external transfer in `IntentGatewayV2.withdraw()`, enabling reentrant multi-drain of order funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` in the Tron `IntentGatewayV2` contract pays out each escrowed token and the accumulated transaction fee via an external `.call` **before** it updates the corresponding `_orders[commitment][token]` accounting, mirroring the C4 finding's root cause where `self.adminFees[i]` is read and paid out without being zeroed first, letting the same balance be drained again through a nested call.

### Finding Description
In `withdraw()`, for each token in the withdrawal request the contract does the external transfer and only afterwards decrements the escrow entry: [1](#0-0) 

The same ordering is repeated for the accumulated relayer/transaction fee — the fee is read and transferred to the beneficiary, and only deleted from storage afterward: [2](#0-1) 

Both the native-asset branch (`beneficiary.call{value: amount}("")`) and the ERC20/TRC20 branch (`token.call(...transfer...)`) execute an external call while the corresponding storage entry (`_orders[commitment][token]` or `_orders[commitment][TRANSACTION_FEES]`) is still non-zero. If `beneficiary` is a contract (attacker-controlled, since the beneficiary is set by the order/withdrawal request and can be any address the solver/user designates), the native-token `.call` hands control to attacker code mid-loop, before the state update for that token — and before the fee entry is cleared at all if the fee redemption happens later in the same call. A reentrant call into any externally reachable path that reads/consumes `_orders[commitment][...]` (e.g. a repeated `onAccept`/`withdraw` invocation for the same commitment triggered through the host, or another token's payout path within the same multi-token order) can observe stale, not-yet-decremented balances and cause the same escrowed amount or fee to be paid out more than once.

This is the same class of bug as the reported `withdrawAdminFees()` issue: a balance that should be zeroed at the moment of payout is instead zeroed (or decremented) only after the external transfer, so a re-entrant/second call sees the pre-payout balance and withdraws it again. The upstream, non-Tron `IntentsBase.sol._withdraw()` has already been hardened against exactly this pattern — it decrements `_orders[body.commitment][token]` immediately before the transfer and `delete`s `TRANSACTION_FEES` before transferring the fee — as documented by the CEI-fix comments and reentrancy regression tests: [3](#0-2) [4](#0-3) 

The Tron contract at `evm/tron/contracts/apps/IntentGatewayV2.sol` was not updated to match, and still performs the transfer-then-update ordering that the fix in the main EVM contract was specifically designed to eliminate.

### Impact Explanation
A successful reentrant drain lets an attacker (acting as the withdrawal beneficiary of a settled order) redeem escrowed input tokens and/or the accumulated relayer fee more than once from the same commitment, directly stealing funds that belong to other users/solvers held in the gateway's escrow — a concrete theft-of-funds impact reachable from a single relayed cross-chain settlement message (`RedeemEscrow`/`RefundEscrow` delivered via `onAccept`), which is within the reachable "message dispatcher/handler delivery" surface named in scope.

### Likelihood Explanation
Reaching `withdraw()` only requires a relayer to deliver a legitimately-authenticated `RedeemEscrow`/`RefundEscrow` message (the normal, permissionless settlement flow already exercised by any solver filling an order), and the beneficiary address is attacker-controllable (it is taken directly from the order/solver-selected beneficiary field). No admin or governance privilege is needed to trigger the vulnerable code path — only a beneficiary contract designed to re-enter during the native-asset `.call`.

### Recommendation
Apply the same checks-effects-interactions ordering already used in `evm/src/apps/intentsv2/IntentsBase.sol`: decrement `_orders[body.commitment][token]` (or `delete` it for `TRANSACTION_FEES`) immediately before performing the corresponding external transfer/call in `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `withdraw()`, for both the per-token loop and the fee payout.

### Proof of Concept
1. Place and fill a multi-input cross-chain order whose `beneficiary` on settlement is a malicious contract `Attacker`.
2. When the settlement `RedeemEscrow` message is delivered, `onAccept` → `withdraw()` iterates `body.tokens`. For a native-asset (TRX) entry, the contract calls `beneficiary.call{value: amount}("")` — handing control to `Attacker.fallback()` — while `_orders[commitment][address(0)]` is still unchanged.
3. `Attacker.fallback()` re-enters a path that reads `_orders[commitment][someOtherToken]` (still non-zero) or, if the fee entry is processed after the loop, the not-yet-decremented `_orders[commitment][TRANSACTION_FEES]`, and triggers a second payout for the same commitment before the original call finishes decrementing those entries.
4. `Attacker` receives the escrowed token/fee twice for a single settled order. [5](#0-4)

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
