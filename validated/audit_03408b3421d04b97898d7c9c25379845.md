## Analog Analysis

The M-16 report's core bug class is "a field the code trusts/acts on that isn't actually covered/bound by the cryptographic check." Mapping this onto `shopify_api`'s webhook processing pipeline reveals exactly that pattern.

`Registry.process` treats a webhook request as authenticated the moment `Utils::HmacValidator.validate(request)` returns true, then immediately hands the handler `request.shop` (and `topic`/`webhook_id`/`api_version`) as trusted tenant-identifying data: [1](#0-0) 

But `Webhooks::Request#to_signable_string` — the value that actually gets HMAC-verified — is only the raw body, never the headers: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers, with zero cryptographic binding: [3](#0-2) 

And `HmacValidator.validate_signature` computes/compares the HMAC solely over `to_signable_string` (the body), never touching the headers: [4](#0-3) 

The identity binding that should hold is: **`shop` (used by the app to route/attribute webhook data) == `shop` that was cryptographically authenticated by the HMAC**. It does not hold — the HMAC only authenticates *that the body came from an app installed with this `client_secret`*, not *which shop the body belongs to*.

### Title
Webhook `shop`, `topic`, and `webhook_id` headers are unauthenticated (not covered by HMAC), enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#hmac` is verified against `to_signable_string`, which returns only the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values — all read from HTTP headers — are never included in the signed payload, yet `Registry.process` passes them straight through to the app's `WebhookHandler` as authenticated (`WebhookMetadata#shop` etc.), after only checking `Utils::HmacValidator.validate(request)` succeeded.

### Finding Description
`Registry.process` performs exactly one check before dispatching to the handler:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
```
`Utils::HmacValidator.validate` only proves that the *body* bytes were HMAC'd with the app's `client_secret` — i.e., that the request came from some install of this specific app (any shop that has installed the app, including one an attacker fully controls). It proves nothing about which `shop-domain`, `topic`, or `webhook-id` header value is attached to that body, because those headers are excluded from `to_signable_string`.

An app owner/user who installs the app on their own store legitimately receives real webhooks with valid HMACs for bodies they fully control (they can trigger arbitrary orders/products/customers events in their own store). Because the signature never binds the `shop-domain` header, that attacker can replay the same `(body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (e.g., a victim shop that also uses the app). The library will report `HmacValidator.validate` as `true` and hand the handler `shop: "victim.myshopify.com"` with attacker-chosen body content.

This exactly matches the requested analog pattern: *a field acted on (the `shop` used for tenant attribution) but not covered by the HMAC*.

### Impact Explanation
Downstream apps (per this gem's own documentation example) key off `data.shop` to decide which merchant's records to update, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`. Because `shop` is unauthenticated, this allows a low-privilege attacker (any user who can install the app on a store they control) to inject arbitrary, attacker-chosen webhook payloads that are attributed to a different tenant (shop) of the same app. Depending on how the host app processes webhooks, this is a cross-tenant data-integrity/confusion vector — satisfying the "cross-tenant access" impact bar, since the gem provides no mechanism, nor any documented warning, that the `shop` field is unauthenticated and must be independently verified (e.g. against a list of shops with an active, valid access token/session) before being trusted.

### Likelihood Explanation
Likelihood is realistic but bounded: the attacker must (a) be able to install the target app on a shop they control (self-service for most public Shopify apps) to obtain valid `(body, hmac)` pairs, and (b) know/guess a target shop domain that also has the app installed (shop domains are often discoverable/guessable, e.g. `<name>.myshopify.com`). No TLS interception, leaked credentials, or `client_secret` access is required — only ordinary use of the app as an unprivileged merchant plus direct HTTP requests to the app's public webhook endpoint.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed payload (`to_signable_string`) rather than trusting them as unauthenticated header values. If that's infeasible without a server-side spec change, at minimum document that `WebhookMetadata#shop`/`topic`/`webhook_id` are unauthenticated header echoes and callers **must** independently confirm the shop is one for which they hold an active, valid session/access token before acting on the payload's contents.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (self-service, no privileged access needed).
2. Attacker triggers a real event (e.g. creates an order) in their own store, causing Shopify to POST a legitimately-HMAC'd webhook body `B` with `hmac = HMAC(client_secret, B)` to the app's webhook endpoint, with header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures/replays this request directly to the app's public webhook URL, changing only the header to `x-shopify-shop-domain: victim-shop.myshopify.com` (or `x-shopify-topic`, etc.), keeping body `B` and `hmac` unchanged.
4. `Webhooks::Request.new` parses the forged header; `Utils::HmacValidator.validate` recomputes HMAC over `B` only, which still matches, so `Registry.process` calls `handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...))`, attributing attacker-controlled data to the victim shop.
