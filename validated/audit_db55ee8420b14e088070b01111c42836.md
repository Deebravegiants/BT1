### Title
Webhook shop-domain identity spoofing — HMAC signs only the body, not the shop header (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by verifying only the raw request body against the HMAC signature. The `shop` (and `topic`, `webhook_id`, `api_version`) values are read from unauthenticated HTTP headers and handed to the app's webhook handler as trusted tenant identity, even though those header values are never covered by the HMAC computation.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from the `shopify-*`/`x-shopify-*` headers, with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC solely via `HmacValidator.validate(request)` (i.e., only `to_signable_string`/body bytes), then immediately trusts `request.shop` as the tenant identity passed into the handler: [3](#0-2) 

`HmacValidator.validate_signature` confirms only that `to_signable_string` (the body) matches the signature — it says nothing about which shop or topic produced it: [4](#0-3) 

The identity binding the gem should be enforcing is: `shop asserted to handler == shop the HMAC authenticates`. In reality the equality only holds for `body authenticated == body bytes hashed`; `shop` is asserted independently and unauthenticated. Because the `client_secret`/`api_secret_key` used to compute this HMAC is the same across every shop that installs the app (it's the app's own secret, not a per-shop secret), an attacker who installs the app on their own (attacker-controlled) shop can legitimately receive a webhook with a valid HMAC for a body of their choosing (they control their own store's data, e.g. by creating an order with attacker-chosen content). They can then replay that exact `raw_body` + `hmac-sha256` header combination to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and optionally `topic`/`webhook-id`) to name a victim shop. `HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` forwards `shop: request.shop` (now the victim's domain) to the handler, which per the documented API is expected to trust this value as the originating tenant: [5](#0-4) 

This crosses the "shop authenticated versus the shop stored/acted-upon" boundary called out in the rules: the gem authenticates the payload bytes but asserts an unauthenticated shop identity to the caller as if it had been verified as part of the same signed message.

### Impact Explanation
Any handler that keys tenant-scoped actions off `WebhookMetadata#shop` (session lookup, per-shop data writes, billing/usage decisions, audit logs) can be made to attribute attacker-controlled webhook content to an arbitrary other merchant using this app. This is a cross-tenant data/identity confusion vulnerability: the attacker doesn't need the app's `client_secret` (they only need to be one of the app's legitimate installers), yet they can forge events "from" any other shop domain string, since the shop domain is never range-checked against any registered/valid installation either. This matches the Critical "cross-tenant access" impact category, mediated entirely through this gem's own webhook verification API contract (not a host-app misuse of an undocumented feature) — the gem's documented `Registry.process`/`WebhookMetadata` contract is exactly what's exploited.

### Likelihood Explanation
Likelihood is Medium: the attacker must be capable of installing the target app on a shop they control (a normal, permitted action for any Shopify merchant/dev on many public apps) and must know/guess the target victim's `.myshopify.com` domain (often public/discoverable). No leaked secrets, TLS interception, or privileged access are required — only the ability to install the app and to send a crafted HTTP POST to the app's public webhook endpoint with a swapped header.

### Recommendation
- Bind `shop` (and ideally `topic`/`webhook_id`) into the signed payload verification, or otherwise validate the header-derived `shop` against an authoritative record (e.g., only accept webhooks for shops with an active, previously-established session/installation in the app), rather than trusting a header value never covered by HMAC.
- Alternatively/additionally, document (and, where feasible, enforce) that the gem's webhook signature validation does not authenticate the shop-domain header, and that consuming apps must independently verify `request.shop` is one of their installed shops before trusting it.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`, so shared `api_secret_key` (`client_secret`) applies to attacker's traffic too.
2. Trigger a webhook delivery to the app for a topic the app has registered (e.g., `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify computed for it — this HMAC is valid for that exact body under the shared secret.
3. Replay that captured `raw_body` and `hmac-sha256` header to the app's webhook endpoint unchanged, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because only `raw_body` is checked; `Registry.process` invokes the handler with `shop: "victim.myshopify.com"` and the attacker-chosen `body`, causing the app to process/attribute forged data as originating from the victim's store.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
