### Title
Cross-chain amount truncates to zero on decimal down-conversion, permanently burning small transfers - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`pallet-hyper-fungible-token`'s `on_accept` converts an incoming ERC20-denominated amount (e.g. 18 decimals) into the local asset's balance (e.g. 6 decimals) via integer division in `convert_to_balance`. For amounts smaller than `10^(erc_decimals - local_decimals)`, the division floors to zero, and the pallet proceeds to mint/transfer `0` to the beneficiary with no revert — while the corresponding tokens were already burned/escrowed on the source chain. This mirrors the reported bug class: a low-decimal/high-decimal precision mismatch causes a value used downstream (here, actual fund transfer) to silently round to zero.

### Finding Description
`convert_to_balance` divides the raw ERC20 `U256` value by `10^(erc_decimals - local_decimals)` and parses the resulting decimal string into the target balance type: [1](#0-0) 

This is invoked unconditionally in `on_accept` (message delivery from a remote chain) to compute the amount to mint or release to the beneficiary: [2](#0-1) 

and again in `on_timeout` for refunds: [3](#0-2) 

If a token is registered with `erc_decimals` (destination chain precision) greater than `decimals` (local asset precision) — e.g., an EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract at 18 decimals bridging into a 6-decimal Substrate asset — then any incoming `message.amount` smaller than `10^(erc_decimals - decimals)` (e.g., less than `1e12` wei, i.e. less than `0.000001` whole tokens) truncates to `0` in `convert_to_balance`. The function only errors if the parsed string fails `FromStr`; `"0"` parses successfully, so no error is raised. The pallet then calls `mint_into`/`transfer` with `amount = 0` and emits `TokenReceived`/`TokenRefunded` with a zero amount, completing "successfully."

The tokens that funded this transfer were already irreversibly burned or debited on the source chain before the corresponding `send` extrinsic or the EVM contract's dispatch — going the other direction, `convert_to_erc20` only multiplies (source: local → destination), so no truncation happens there, meaning the source-side debit for a small amount is real and non-zero, but the destination-side credit can legitimately compute to zero.

### Impact Explanation
Any account can trigger this by calling the permissionless `send` extrinsic (or the mirrored EVM-side send) with a sufficiently small amount, or simply as an ordinary user unaware of the decimals asymmetry between the two chains' token representations. The result is a message that Hyperbridge faithfully delivers and the pallet faithfully processes, but the beneficiary receives zero tokens while the source-side balance was already consumed — a permanent, unrecoverable loss of the transferred value. This is a direct violation of the bridging invariant (value preserved across chains, modulo intended precision) and fits the "permanent freezing/loss of funds" impact category, reachable from a single unprivileged extrinsic without needing malicious governance, admin, or relayer collusion.

### Likelihood Explanation
Likelihood is proportional to how the pallet is configured: whenever a non-native asset with low local decimals (e.g. 6, like USDC-style assets) is registered against a chain whose HyperFungibleToken/WrappedHyperFungibleToken contract uses 18 decimals — a very plausible and even typical deployment — the truncation threshold (`10^12` wei ≈ `1e-6` whole token) is well within the range of amounts users (or dust/rounding leftovers from partial fills, refunds, fee remainders, etc.) could plausibly send. No attacker privilege is required; the bug triggers on ordinary usage.

### Recommendation
In `convert_to_balance` (or immediately after calling it in `on_accept`/`on_timeout`/`send`), reject a zero result derived from a non-zero input instead of silently proceeding:
```rust
if !value.is_zero() && amount == B::default() {
    return Err(...); // or a dedicated HftError::AmountRoundsToZero
}
```
This should cause `on_accept` to fail (leaving state unaffected, and the ISMP layer to treat it as a rejected/failed message so the source-chain timeout/refund path is triggered) rather than silently minting zero while the source-side funds are already gone. Equivalently, enforce a minimum transferable amount at `send`-time on both the pallet and EVM contract sides, computed from the registered decimals difference, so a transfer that would truncate to zero is rejected before source funds are ever debited.

### Proof of Concept
1. Register a non-native asset `X` with local `decimals = 6` on the Substrate chain, and configure `Precisions::<T>::insert(X, evm_chain, 18)` (the EVM contract for `X` uses 18 decimals) — see `register_token`/`Precisions` storage: [4](#0-3) .
2. On the EVM chain, a user (or the paired `HyperFungibleToken` contract logic) dispatches a `send` with `amount = 500_000_000_000` wei (0.0000005 of a token in 18-decimal terms, i.e., less than `10^12`), burning/escrowing that amount on the EVM side and posting the cross-chain message.
3. Hyperbridge relays and delivers the request; `on_accept` runs `convert_to_balance(500_000_000_000, 18, 6)` → division by `10^12` → `0`, parsed successfully as `B::default()`.
4. `<T::Assets>::mint_into(X, &beneficiary, 0)` (or `transfer(..., 0, ...)`) succeeds, `TokenReceived { beneficiary, amount: 0, source }` is emitted, and the extrinsic/message processing completes without error.
5. The beneficiary's balance of `X` is unchanged (0 credited) while the sender's EVM-side tokens were already burned/escrowed — the value is permanently lost, with no revert or refund path taken since `on_accept` did not fail.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
