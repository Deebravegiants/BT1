### Title
Webhook Shop Identity Not Bound by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, then dispatches the event using the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers that are never covered by that HMAC. The binding "shop the HMAC was computed for" == "shop the app treats the payload as belonging to" does not hold, because only the body bytes are signed.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from request headers, with no cryptographic binding to the signed body: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (i.e., the raw body only, see `lib/shopify_api/utils/hmac_validator.rb:26-31`), and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to route and construct the metadata handed to the app's handler: [3](#0-2) 

Because the HMAC signature never covers the `shop-domain`, `topic`, or `webhook-id` headers, any request carrying a *valid* `(raw_body, hmac)` pair for the app's shared secret will pass verification regardless of what `shop-domain` header is attached to it. The equality the app implicitly relies on — "the shop identified in the (HMAC-verified) request equals the shop the payload actually originated from" — is broken, since the shop identity is asserted purely through an unauthenticated header.

### Impact Explanation
An attacker who is able to obtain (or resend) one legitimately HMAC-signed `(raw_body, hmac)` pair for the app (for example, from a webhook fired for their own installed/dev shop, where the raw body and its HMAC are visible to them through normal request logging/tooling on infrastructure they control) can replay that exact body/HMAC to the app's public webhook endpoint while substituting the `shopify-shop-domain` header for a different, victim shop. Because `Registry.process` passes `request.shop` straight into `WebhookMetadata` without any second check tying the header to the signed content, the app's webhook handler will process the payload as if it came from the victim shop — a cross-tenant data/identity confusion inside the app's own webhook handling logic.

### Likelihood Explanation
The webhook endpoint is a public, unauthenticated HTTP endpoint by design (`docs/usage/webhooks.md`), and this bug class — shop identity carried in an unsigned header alongside an HMAC that only covers the body — mirrors the exact pattern flagged in the reference report (a field acted upon that is not covered by the authentication mechanism). Any party capable of producing or replaying one valid signed webhook body for the target app (e.g., a merchant with their own store install, replaying their own captured deliveries with a modified shop header) can trigger this.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the HMAC-signable content (or independently verify the `shop-domain` header against a shop known to have a valid, active session/installation) before trusting it in `ShopifyAPI::Webhooks::Registry.process`. At minimum, document and enforce that consumers must cross-check `WebhookMetadata#shop` against their own installed-shop records rather than trusting it as authenticated by the HMAC check alone.

### Proof of Concept
1. Obtain one legitimate webhook delivery `(raw_body, x-shopify-hmac-sha256)` for the target app (e.g., from a shop the attacker controls/installed the app on).
2. Send a POST request to the app's public webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but set `x-shopify-shop-domain` to a victim shop's domain.
3. `Utils::HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb:12-22) succeeds because it only checks the raw body against the HMAC.
4. `Registry.process` (lib/shopify_api/webhooks/registry.rb:188-200) dispatches the handler with `WebhookMetadata` carrying the attacker-supplied `shop` header value, causing the app to process/act on the payload as belonging to the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
