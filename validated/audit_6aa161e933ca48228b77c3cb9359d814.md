### Title
Webhook shop/topic identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` binds `shop`, `topic`, `webhook_id`, and `api_version` to unauthenticated HTTP headers, while the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. Because the `api_secret_key` used to compute the HMAC is shared across every shop that installs the app, any merchant who has genuinely installed the app (an unprivileged, low-trust actor from the app's perspective) can obtain a validly-signed webhook body from their own store and replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header. The signature check passes because only the bytes it protects (the body) are unchanged, but the value the application actually trusts and acts on (the shop identity) is never included in what was signed.

### Finding Description
`Request#hmac` and `Request#to_signable_string` show the actual verified content is exactly the raw body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from headers with no cryptographic linkage to the body or the HMAC: [2](#0-1) 

`HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string`, i.e. just the raw body for webhooks: [3](#0-2) 

`Registry.process` trusts the header-derived `request.topic` to select a handler and forwards the header-derived `request.shop` directly into the data given to the app's business logic, with the only gate being the body-only HMAC check: [4](#0-3) 

Equality that should hold but doesn't: `shop authenticated by HmacValidator == shop acted upon by Registry.process/WebhookMetadata`. In reality, `HmacValidator` authenticates only `raw_body`, while `Registry.process` acts on `request.shop`/`request.topic`, which are attacker-controlled headers outside the signed scope.

Exploit path: an attacker installs the target app on a store they control (a normal, unprivileged merchant action, not requiring `api_secret_key`, an access token, or any privileged account). They trigger a legitimate webhook delivery to their own endpoint/proxy (e.g., `orders/create`) with attacker-chosen body content from their own shop. Shopify computes and sends a genuine `X-Shopify-Hmac-Sha256` value using the app's real `api_secret_key` — the same secret shared by all installations of that app. The attacker then re-POSTs this exact body and HMAC header to the app's real webhook endpoint, but substitutes `X-Shopify-Shop-Domain` with the victim shop's domain (and optionally a different `X-Shopify-Topic`). `HmacValidator.validate` still succeeds because the body bytes and HMAC are unchanged, and `Registry.process` dispatches the (attacker-crafted) body to the handler tagged with the victim's shop.

### Impact Explanation
This crosses a tenant boundary: data nominally scoped to one shop's session/account is delivered and processed as if it originated from a different, victim shop, without needing the victim's credentials, access token, or `client_secret`. Depending on the app's webhook handler logic (e.g., writing order/customer data keyed by `shop`, updating billing state, or triggering shop-scoped side effects), this enables cross-tenant data injection/corruption — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is realistic in any multi-tenant app using this gem's webhook stack: it requires only that the attacker be a legitimate (even free/dev) installer of the target app — no special access, no leaked secrets, and no interaction with the victim. The only prerequisite is that the attacker's own store can trigger a webhook event with body content they influence, which is standard merchant capability (creating orders, customers, etc., in their own store).

### Recommendation
Bind the identity fields into the verified material instead of trusting bare headers: include `shop`, `topic`, and `webhook_id` in the HMAC-covered signable string (or independently verify `shop` against the session/shop the webhook subscription was registered for), so that spoofing any of these headers invalidates the signature. At minimum, `Registry` should cross-check `request.shop` against a known/registered shop for the topic before invoking handlers.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; register/receive a webhook for topic `orders/create`.
2. Capture the genuine POST Shopify sends, including body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Replay the request to the app's webhook endpoint, keeping body `B` and header `H` identical, but replacing `X-Shopify-Shop-Domain: attacker.myshopify.com` with `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers (only checks presence, not the shop value) and `HmacValidator.validate` passes because it only rehashes `B`, per [5](#0-4)  and [6](#0-5) .
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, per [7](#0-6) , causing the app to act on attacker-controlled data under the victim's shop identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
