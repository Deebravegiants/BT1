### Title
Missing sender authentication in `RequestState` fast-path bypasses source verification in orb-relay client - ([File: orb-relay-client/src/client.rs])

### Summary
The `PollerAgent::main_loop` message-handling logic in `orb-relay-client/src/client.rs` normally enforces that incoming `RelayPayload` messages are only accepted from the expected paired peer, checked via `src.id != self.config.dst_id`. However, a special-cased branch for `self_serve::app::v1::RequestState` messages is evaluated *before* this source check and unconditionally causes the client (running on the Orb) to resend `self.last_message` to whoever sent the `RequestState` message, without ever validating that `src.id` matches the configured `dst_id`. This mirrors the reported `burn()` access-control flaw: a state-affecting/sensitive action (replaying the last signup-relevant message) is exposed without checking that the caller is the legitimate, authorized counterparty.

### Finding Description
In `orb-relay-client/src/client.rs`, `PollerAgent::main_loop` processes incoming `RelayConnectResponse` payloads: [1](#0-0) 

The relevant branch structure is:
```
if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source...");
} else {
    self.handle_message(...).await?;
}
```

For every other message type, the code explicitly checks `src.id != self.config.dst_id` and drops/logs unexpected-source messages — this is the intended access-control boundary between the Orb and its paired self-serve App session. The `RequestState` branch, however, is checked first and short-circuits this authorization gate entirely: any payload matching `RequestState`, regardless of its `src` entity, causes the Orb-side client to resend `self.last_message` (the last outbound protocol message, which can include self-serve signup-flow state such as `AnnounceOrbId`/session state) back over the relay connection.

This is structurally analogous to the `TokenStableV6.burn()` bug: an operation (`burn`, in the analog "replay last outbound state message") is dispatched without validating that the caller/source is the authorized party. Just as `burn()` could be invoked on an arbitrary target address because it lacked an owner/msg.sender check, the `RequestState` handler resends session-scoped state to an arbitrary `src`, because the same-file source-identity check that governs the rest of the message-handling logic is skipped for this message type.

### Impact Explanation
Because the relay session is identified by `session_id`/entity IDs rather than by this per-message source check being applied uniformly, bypassing the `src.id == dst_id` verification for `RequestState` means the Orb will re-emit its last relay message (potentially containing signup/session state, such as `AnnounceOrbId` data used to bind an Orb to a specific self-serve app session) to any entity capable of sending a `RequestState` payload into that channel, not only the legitimately paired app. This can lead to cross-session/cross-signup state disclosure or misattribution within the self-serve relay flow — an unprivileged participant able to inject a `RequestState` message can obtain state intended only for the authenticated peer, undermining the identity binding between Orb and App for a signup session.

### Likelihood Explanation
The bypass is unconditional and requires no privileged access — it only requires being able to deliver a message that matches the `RequestState` schema into the relay stream the client is processing, which is a reachable attacker action for any party able to interact with the relay session (e.g., an app-side or peer able to influence the relay stream). No credentials beyond reaching the message stream are needed to trigger the resend, since the check is skipped entirely for this message type. Note: full exploitability depends on relay/session-scoping guarantees enforced by the backend `RelayService` that are outside this file and were not available for direct inspection here — this should be verified against the relay server's own session isolation before treating this as fully conclusively remotely exploitable.

### Recommendation
Move the `RequestState` handling below (or make it subject to) the same `src.id != self.config.dst_id` check applied to all other messages, so that only the authenticated/paired peer can trigger a resend of `self.last_message`. I.e., restructure the `if/else if/else` so the source-authorization check is the first gate for every payload type, including `RequestState`, consistent with how `burn()` should have required an owner/authorization check before proceeding.

### Proof of Concept
Conceptual flow (exact reachability depends on relay-server session scoping, which was not directly inspectable):
1. An Orb-side client is connected with `Mode::Orb` and has previously sent a message (populating `self.last_message`).
2. An entity other than the configured paired peer (`dst_id`) sends a payload that matches `self_serve::app::v1::RequestState` into the same processed response stream.
3. Per [2](#0-1) , the `RequestState::matches(&payload).is_some()` branch is taken first, and `sender_tx.send(self.last_message.clone())` executes — bypassing the `src.id != self.config.dst_id` check that would otherwise reject this unauthorized source, as demonstrated by the fact that this check is only applied in the subsequent `else if` branch for all non-`RequestState` messages.
