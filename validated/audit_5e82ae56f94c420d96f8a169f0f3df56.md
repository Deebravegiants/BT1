### Title
Webhook `shop-domain` (and `topic`) header is not covered by the HMAC signature, allowing cross-tenant shop-identity spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then trusts the unauthenticated `shop-domain` HTTP header as the tenant identity passed to the app's handler. Because the signature never binds the shop (or topic) header to the signed bytes, any party who can obtain one valid `(body, hmac)` pair for their own shop can replay it to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header, and the gem will accept it as an authentic webhook for that spoofed shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers without any cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate`, which internally calls `to_signable_string` (body only) via `validate_signature`: [3](#0-2) 

After the body-only HMAC check succeeds, `Registry.process` dispatches to the topic handler and constructs `WebhookMetadata` directly from the unauthenticated `request.shop` header: [4](#0-3) 

The equality the gem should enforce is:
`hmac_valid(body) == true` **implies** `shop_header == shop_that_Shopify_actually_signed_for`.

In reality the gem only proves `hmac_valid(body) == true`; it never proves that the `shop` (or `topic`) header is the one Shopify associated with that body when it computed the HMAC. Since `OpenSSL::HMAC.hexdigest` is computed only over `@raw_body`, the `shop-domain` header can be freely substituted post-hoc without invalidating the signature, because the header was never part of the signed input in the first place.

### Impact Explanation
This breaks the binding between "the webhook body Shopify sent for Shop A" and "the shop the handler attributes the payload to." An attacker who operates (or has previously installed the app on) their own shop can capture one valid `(raw_body, hmac)` webhook pair delivered to them, then re-send it to the merchant app's webhook endpoint with the `shop-domain` header swapped for a victim shop. `Registry.process` will pass HMAC validation (body unchanged) and hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop. Any app logic that uses `data.shop` to select which tenant's session/database record to update (a standard pattern for multi-tenant Shopify apps) will act on the wrong tenant, i.e., cross-tenant data confusion/access driven entirely by attacker-controlled headers.

### Likelihood Explanation
Exploitation requires no privileged credentials or `api_secret_key` knowledge — only a body+HMAC pair the attacker can legitimately obtain for their own shop (e.g., from a webhook delivered to their own app installation, which they fully control and can replay at will) and the ability to send an HTTP request with custom headers to the app's public webhook endpoint. This is trivially reachable by any unprivileged internet user/merchant who has installed the app once.

### Recommendation
Include the shop domain (and ideally topic) in the signed material that `Utils::HmacValidator` verifies, or independently verify `request.shop` against a value cryptographically derived from the payload/Shopify infrastructure (e.g., cross-check against the shop associated with the webhook subscription via a separately authenticated channel) before it is passed to `WebhookMetadata`/handler dispatch. At minimum, document clearly that `request.shop` is unauthenticated and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker resends an HTTP POST to the app's webhook endpoint with the same body `B` and same header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (i.e., `B`) and finds it matches `H` — validation passes: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the app to process/act on the payload as though it originated from `victim-shop.myshopify.com`.
