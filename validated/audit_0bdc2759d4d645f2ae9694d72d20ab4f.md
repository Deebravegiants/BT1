### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/utils/hmac_validator.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then trusts the `shop-domain` header — a value entirely outside the HMAC's coverage — to attribute the webhook payload to a tenant. This breaks the intended binding `hmac == HMAC(secret, raw_body + shop)`, since in reality `hmac == HMAC(secret, raw_body)` only. Any user who can obtain one genuine, validly-signed webhook body/HMAC pair (e.g. by installing the public app on their own store) can replay that same body+HMAC pair while substituting an arbitrary victim `shop-domain` header, and the gem will accept it as authentic and hand it to the app's handler labeled as coming from the victim shop.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the signable string exclusively from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`, while `Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never mixed into the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler, with no check that this shop is the one the payload actually originated from: [3](#0-2) 

The identity binding the gem is supposed to enforce is: *the shop this webhook data is attributed to* == *the shop that Shopify cryptographically vouches for*. Because the HMAC only covers `raw_body`, that equality never actually holds — `shop` is a free-form, attacker-controlled header value. A user who legitimately installs the app on their own store (an ordinary, unprivileged action requiring no special credential) will receive genuine webhooks: real `raw_body` + real `hmac` computed with the app's `client_secret`, addressed to their own shop domain. That same user can then replay this exact `raw_body`/`hmac` pair to the app's webhook endpoint while swapping the `shop-domain` header to any victim `myshopify.com` domain. `HmacValidator.validate` will still pass, since it never inspects `shop`, and the handler will process the (attacker's own) payload as if it belongs to the victim tenant.

### Impact Explanation
This crosses a tenant boundary using only a signature that was never meant to authorize a shop identity claim: it is a form of cross-tenant data injection. A host application that uses `data.shop` from `WebhookMetadata` to look up sessions, update per-tenant records, or make authorization decisions (the exact intended and documented usage per `docs/usage/webhooks.md`) can be made to apply attacker-supplied webhook content to a victim shop's data/session context, corrupting or leaking cross-tenant state without ever needing the victim's credentials.

### Likelihood Explanation
Any user can trivially become a "legitimate" source of a signed `raw_body`/`hmac` pair simply by installing the public app on a store they control (no privileged access, no leaked secrets, no social engineering) — this satisfies the "unprivileged internet user" constraint. Replaying an HTTP POST with a different header value is trivial. The only friction is that the attacker's own webhook body content is fixed (they can't forge arbitrary content without knowing `client_secret`), but they fully control *which* topic/shop pairing they subscribe their own store to and can pick a topic/body they want reflected onto the victim shop.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) inside the value that is HMAC-verified, or otherwise bind the verified `raw_body` to the specific shop it was issued for (e.g., by requiring the caller to supply the expected shop and comparing it against a shop resolved through an independently-trusted channel, not a client-suppliable header). At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted for tenant-sensitive decisions without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, subscribing to a webhook topic (e.g. `customers/create`).
2. Shopify sends a legitimate webhook to the app: body `B`, header `x-shopify-shop-domain: attacker.myshopify.com`, header `x-shopify-hmac-sha256: H` where `H = HMAC_SHA256(client_secret, B)`.
3. Attacker captures `B` and `H`, then POSTs to the same webhook endpoint with the same `B` and `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(client_secret, B)` and finds it equals `H` — validation passes because `shop` is never part of `to_signable_string`, per `lib/shopify_api/webhooks/request.rb` lines 21-38 and `lib/shopify_api/utils/hmac_validator.rb` lines 26-31.
5. The handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)` and processes it as authentic data for the victim shop.
