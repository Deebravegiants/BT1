### Title
Webhook `shop`/`topic` attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then trusts the unauthenticated `shop-domain` (and `topic`) headers to decide which merchant/tenant the payload belongs to. Because the signed bytes and the identity-bearing bytes are different, an attacker who can obtain one validly-signed webhook body/HMAC pair for their own shop can replay it to the app's webhook endpoint with a forged `shop-domain` header, making the app process attacker-controlled data as if it belonged to a victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body, not the shop or topic headers: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the HMAC purely against `to_signable_string`, i.e. purely against the body: [2](#0-1) 

`Registry.process` accepts the request once that body-only HMAC checks out, and then hands the *unauthenticated* `request.shop` and `request.topic` (both read straight from HTTP headers) to the registered handler as the tenant/topic identity for the event: [3](#0-2) [4](#0-3) 

The binding that should hold is:
`shop that produced the HMAC-valid bytes == shop attributed to the event that the handler acts on`

This equality is broken because the HMAC only certifies the body; it says nothing about which shop the request headers claim to be from. A merchant using the app can register their own webhook subscription pointing at an interception endpoint (a capability normal Shopify merchants have via the Admin API `webhookSubscriptions` mutation with their own access token — no elevated privilege needed), capture a Shopify-issued, validly-signed `(raw_body, hmac)` pair for their own shop, then send an HTTP request directly to the app's public webhook receiver with that same body/HMAC but with the `x-shopify-shop-domain`/`shopify-shop-domain` header replaced with a victim shop's domain. `HmacValidator.validate` still passes because it never looks at that header, and `Registry.process` will invoke the handler with `data.shop` equal to the victim's domain while `data.body` is fully attacker-chosen content.

### Impact Explanation
This is a cross-tenant identity-binding break reachable by any merchant/app-user without needing the app's `client_secret` or an access token belonging to another tenant — only their own legitimate access to their own shop's webhook data. Depending on how the host application's webhook handler uses `WebhookMetadata#shop` (e.g., looking up the shop's record, writing data keyed by shop, triggering per-shop side effects, or deciding trust based on shop identity), this allows an attacker to inject attacker-controlled webhook payloads that the app will process as belonging to another merchant — a cross-tenant data/action integrity violation.

### Likelihood Explanation
Medium-to-High: any merchant installing the target app can, with only their own permissions, register a custom webhook subscription and observe a real signed payload for their own shop, then replay it against the app's public webhook URL with a forged shop header. No secret material or victim credentials are required — only the ability to author one’s own subscription and send an HTTP POST to the app's known webhook endpoint.

### Recommendation
Bind the shop (and topic, api-version) into the signed material, or otherwise authenticate the header values against the source that produced the payload — e.g. verify that the `shop-domain` header matches a shop value embedded and covered inside the HMAC-signed body (Shopify includes shop identifying fields inside most webhook JSON payloads), or require the application layer to independently confirm `WebhookMetadata#shop` against a known/installed-shop list before trusting it for tenant-scoped operations, rather than trusting the unauthenticated header alone.

### Proof of Concept
1. As a normal merchant with the target app installed on `attacker-shop.myshopify.com`, use the Admin API (with the merchant's own access token) to create a webhook subscription for topic `orders/create` pointing at an interception endpoint the attacker controls.
2. Trigger an order create event on `attacker-shop.myshopify.com`; Shopify sends the app's normal webhook endpoint a POST — but because the attacker owns the subscription callback in step 1 pointed to their interceptor first (or, alternatively, they capture the outgoing raw body + `x-shopify-hmac-sha256` value some other legitimate way for their own shop, e.g. by logging their own server before forwarding), the attacker records `(raw_body, hmac)`.
3. The attacker sends a POST directly to the real target app's webhook receiver URL with:
   - Body = the captured `raw_body`
   - Header `x-shopify-hmac-sha256` = the captured, validly-signed HMAC value
   - Header `x-shopify-shop-domain` = `victim-shop.myshopify.com` (any shop, spoofed)
   - Header `x-shopify-topic` = `orders/create`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the body against the HMAC. The handler is then invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"` and `body` fully controlled by the attacker, even though the victim shop never sent this event.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
