### Title
Unauthenticated stateless Emporium ops via `signerAddress == 0` reachable through the unaccounted `formInputEmporiumMin` proof path let an attacker force Emporium to `approve()` an arbitrary allowance over its held tokens - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`, `contracts/CircomDataBuilder.sol`)

### Summary
`CircomDataBuilder.formInputForCircom` routes any `transact` call with `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0` to `formInputEmporiumMin`, which only proves `message == Poseidon(messageSeed)` and leaves every other field of `CircomData` unconstrained. Because `erc20TokenAddresses` is empty, none of `Hinkal.transact`'s balance/slippage-accounting loop nor `EmporiumUpgradeable.runAction`'s own before/after balance loop ever execute, while `verifyWallet` fully skips signature verification when `EmporiumStack.signerAddress == address(0)`, letting an attacker execute an arbitrary stateless op (e.g. `token.approve(attacker, type(uint256).max)`) from Emporium's own address with zero accounting.

### Finding Description
The claimed invariant is: *assets Emporium can move/authorize in a transaction == assets accounted for in `balancesBefore`/`balancesAfter` (and in `Hinkal.transact`'s `oldBalances`/`newBalances` loop)*. This equality is broken.

Path:
1. `Hinkal.transact` (`contracts/Hinkal.sol:30-168`) calls `hinkalHelper.performHinkalChecks`, which calls `CircomDataBuilder.formInputForCircom` (`contracts/CircomDataBuilder.sol:134-148`). When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, it dispatches to `formInputEmporiumMin` [1](#0-0) , which only feeds `emporiumMessage`, `timeStamp`, and `calldataHash` into the proof — matching the circuit `MainEVMCircuitMin`, whose only real constraint is `message <== Poseidon(1)([messageSeed])` [2](#0-1) . The attacker trivially picks any `messageSeed` and computes `emporiumMessage` themselves — no shielded funds, nullifiers, or amounts are proven.
2. Because `erc20TokenAddresses.length == 0`, the entire balance/slippage accounting loop in `Hinkal.transact` (lines 97-147) never executes [3](#0-2) , and `rootHashExists` only requires any historical valid root (trivial, public data, no nullifiers consumed).
3. `_externalTransact` builds an **empty** `deltaAmountChanges` array and calls `EmporiumUpgradeable.runAction` [4](#0-3) .
4. In `runAction`, `balancesBefore`/`balancesAfter` are computed over the empty `erc20TokenAddresses` array, so they account for nothing [5](#0-4) .
5. `verifyWallet` is called with the attacker-supplied `EmporiumStack`. If `stack.signerAddress == address(0)`, the function returns immediately after marking the message used — **no ECDSA signature check, no `deadline`/`maxFee` check at all** [6](#0-5) .
6. The op loop then executes each `EmporiumOperation` in stateless "CASE 2" mode (since `stack.signerAddress == address(0)` forces `op.invokeWallet && stack.signerAddress != address(0)` to be false): `op.endpoint.call{value: op.value}(op.callData)` is only blocked from targeting `callHinkalWallet`/`doSendToRelay` selectors — any other endpoint and calldata is permitted [7](#0-6) . This call executes with `msg.sender == Emporium`, so an attacker can set `op.endpoint = <ERC20 token held by Emporium>` and `op.callData = approve(attacker, type(uint256).max)`, making Emporium grant the attacker an unlimited allowance over any of its token balances.
7. Because `circomData.erc20TokenAddresses` is empty, the after-call accounting loop in `runAction` (which would normally detect unexpected balance changes and revert via `BalanceChangeShouldBePositive`) never runs, and `Hinkal.transact`'s own balance-diff/slippage check is likewise skipped. No code path anywhere in this transaction constrains or reports the `approve()` side effect.
8. In a later, ordinary (non-Hinkal) transaction the attacker calls `token.transferFrom(Emporium, attacker, amount)` using the granted allowance to actually move out any balance the Emporium contract holds of that token (e.g. residual/in-flight balances from other users' multi-step operations, dust, or fees) — realizing the theft.

Existing guards fail because: `performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation` do not require `erc20TokenAddresses.length > 0` for the Emporium action id, `verifyProof` only checks the trivial Poseidon commitment (no nullifier/amount constraints exist in `MainEVMCircuitMin`), and `verifyWallet`'s `signerAddress == 0` branch is an explicit, unconditional bypass of signature verification rather than a constrained "stateless direct-balance-only" mode.

### Impact Explanation
An unprivileged attacker can force the Emporium contract to `approve()` unlimited spending rights over any ERC20 token it holds, to any address, with no signature, no proof of ownership, and no on-chain accounting recording the action. Combined with a subsequent public `transferFrom`, this is direct theft of any token balance sitting in Emporium (residual balances from other users' in-flight multi-step Emporium operations, un-swept dust, or fee tokens). This matches Critical severity ("direct theft of shielded or in-flight user funds"). The attack is repeatable for every ERC20 token Emporium ever holds and for every fresh `emporiumMessage` the attacker chooses (bounded only by `usedMessages` tracking, which the attacker trivially avoids by picking new seeds each time).

### Likelihood Explanation
Preconditions: (1) a valid, verifiable Groth16 proof for `MainEVMCircuitMin` — trivial to generate off-chain since the attacker fully controls `messageSeed`; (2) a `Verifier`/`buildVerifierId` entry registered for the Emporium-action + all-zero-dimensions combination, which is exactly the intended "min" path the protocol ships; (3) Emporium holding a nonzero balance of the targeted token at call time (from any prior legitimate flow, dust, or fee accrual). No privileged role, no relay, and no victim cooperation is required — the attacker only needs to call `Hinkal.transact` directly. Cost is a single transaction plus gas; feasibility is high given the code as written.

### Recommendation
- Remove the unconditional bypass in `verifyWallet` for `stack.signerAddress == address(0)`; stateless (no-wallet) Emporium calls must still be constrained to only pull/act on funds the *current* transaction accounted for (i.e., forbid arbitrary `op.endpoint`/`op.callData` combinations, or require the balance-accounting loop to run even when `erc20TokenAddresses.length == 0`).
- Do not allow `formInputEmporiumMin`/the "min" proof path to be paired with externally executable `EmporiumStack` ops that can call arbitrary endpoints; either require `erc20TokenAddresses` to enumerate every token any op could touch so the existing before/after balance checks in `runAction` catch unauthorized transfers/approvals, or restrict the min path to a non-value-moving, whitelisted set of calls.
- Consider tracking and reverting on any allowance/state change that isn't reflected by the declared token list, or disallow `approve`-style selectors entirely in the stateless branch.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (as an allowed recipient/external action registered under `HINKAL_EMPORIUM_ACTION_ID`), and a mock ERC20 token.
2. Fund the Emporium contract directly with `mockToken.mint(address(emporium), 1000e18)` to simulate residual/in-flight balance.
3. Off-chain, generate a valid Groth16 proof for `MainEVMCircuitMin` with attacker-chosen `messageSeed`, computing `emporiumMessage = Poseidon(messageSeed)`.
4. Build `CircomData` with `erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalAddress = address(emporium)`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: address(mockToken), invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.approve, (attacker, type(uint256).max))})], maxFee: 0, deadline: 0, v:0, r:0, s:0}))`, valid `rootHashHinkal`/index, correctly computed `calldataHash`.
5. Call `hinkal.transact(a, b, c, dimensions, circomData)` from `attacker` — assert it succeeds without reverting.
6. Assert `mockToken.allowance(address(emporium), attacker) == type(uint256).max`.
7. From `attacker`, call `mockToken.transferFrom(address(emporium), attacker, 1000e18)` and assert `mockToken.balanceOf(attacker) == 1000e18` and `mockToken.balanceOf(address(emporium)) == 0`, proving the equality "assets moved by Emporium == assets accounted in balancesBefore/balancesAfter" (both sides were `0` in `runAction`'s and `Hinkal.transact`'s accounting despite `1000e18` in real, ultimately-extractable value being authorized) is broken.
