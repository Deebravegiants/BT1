### Title
Webhook HMAC does not bind the `shop` field, allowing cross-tenant shop-identity spoofing in `ShopifyAPI::Webhooks::Registry.process` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so the HMAC computed by `Utils::HmacValidator.validate` authenticates the JSON body only, never the `shop-domain` header [2](#0-1) . `Registry.process` nonetheless forwards `request.shop` straight into `WebhookMetadata` as the trusted tenant identifier passed to the app's handler, with no additional check that the HMAC was ever computed for that shop [3](#0-2) .

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac-sha256` header value [4](#0-3) . For webhooks, `to_signable_string` is defined as just the raw body [1](#0-0) . The `shop` accessor reads the `shop-domain` header independently, entirely outside the signed material [2](#0-1) .

`Registry.process` checks `Utils::HmacValidator.validate(request)` and, if it passes, dispatches to the handler using `request.shop` as the shop identity, with no cross-check that this shop is the one the HMAC was actually generated for [5](#0-4) .

Because `api_secret_key` is a single, app-wide secret (the same key is used to sign webhooks for *every* shop that has installed the app, not a per-shop key) [6](#0-5) , any webhook body legitimately delivered by Shopify to the app (e.g. one triggered from an attacker's own installed/dev shop) carries an HMAC that is valid for that exact body under the app's shared secret — independent of which shop header accompanies it. An attacker who controls a shop that has the app installed can capture one of their own legitimate webhook deliveries (valid body + valid HMAC), then replay the identical body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still passes because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: <victim-shop>` together with the attacker-supplied body.

This breaks the binding the gem's own documentation promises: "verify the request did indeed come from Shopify" for **that shop** [7](#0-6) , and it directly violates the pattern the app is told to rely on: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [8](#0-7) .

### Impact Explanation
Any host application that uses `data.shop` from `WebhookMetadata` to scope side effects to a specific merchant tenant (look up that shop's session/store record, write data attributed to that shop, trigger per-shop business logic) can be made to process attacker-controlled body content under a victim shop's identity. This is a cross-tenant boundary violation: an unprivileged attacker who merely installs the app on their own store (a normal, unprivileged action available to any developer) can inject falsified webhook events attributed to a shop they do not control, without ever obtaining that shop's access token or the app's `client_secret`.

### Likelihood Explanation
Requires only: (1) the ability to install the target app on an attacker-controlled shop (trivial/unprivileged for public or install-by-URL apps), (2) capturing one legitimate webhook delivery via a network proxy or logging inside the attacker's own server, and (3) replaying that request with a modified shop header to the public webhook endpoint. No secret material or privileged access is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed material verified by `HmacValidator`, or otherwise cryptographically/structurally bind the verified body to the specific shop header before trusting `request.shop` — e.g., pass a `shop` claim through the same MAC computation instead of separately parsing it from the header, or require host applications to independently corroborate `data.shop` against a pre-registered webhook subscription record before use.

### Proof of Concept
1. App has `api_secret_key = S`. Shops A (attacker-owned) and B (victim) both have the app installed.
2. Shopify delivers a legitimate webhook to the attacker for shop A: body `{"id":123}` with header `X-Shopify-Shop-Domain: shop-a.myshopify.com` and `X-Shopify-Hmac-Sha256: HMAC(S, "{\"id\":123}")`.
3. Attacker captures this exact request (e.g. via a proxy on their own server).
4. Attacker sends a new POST to the app's registered webhook path with the identical body and identical `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses headers/body as usual; `Utils::HmacValidator.validate` recomputes `HMAC(S, "{\"id\":123}")`, which still matches, so validation passes [4](#0-3) .
6. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: {"id"=>123}, ...)` [9](#0-8) , causing the host app to process attacker-chosen data as if it originated from shop B.
