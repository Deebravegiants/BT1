Audit Report

## Title
Unverified/unauthenticated ERC20 accounting in `ERC20Transactor` allows non-standard tokens to desynchronize XCM holding bookkeeping - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` credit/debit the XCM holding register with the *requested* transfer `amount` immediately upon receiving a `true` boolean return from the ERC20 contract's `transfer()` call, without ever checking the actual balance delta at the `TransfersCheckingAccount` or beneficiary. [1](#0-0) [2](#0-1)  Combined with `ERC20Matcher`/`IsLocalAccountKey20`, which treats *any* local `AccountKey20` location as a valid asset with no allow-list or curation, this lets an unprivileged user deploy an arbitrary non-standard ERC20 contract via `pallet-revive` and reference it in XCM, causing the accounting to diverge from the token's real balances. [3](#0-2) 

## Finding Description
`ERC20Matcher` is defined as `MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>`, and `IsLocalAccountKey20::contains` matches any `Location` of the form `(0, [AccountKey20 { .. }])` — there is no registry check, allow-list, or governance gate restricting which contract addresses are treated as valid fungible assets. [4](#0-3) 

In `withdraw_asset_with_surplus`, the transactor calls `IERC20::transferCall` toward the `TransfersCheckingAccount`, and on a decoded `true` return value it unconditionally constructs `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` using the requested `amount`, not an observed balance change. [5](#0-4) [6](#0-5)  `deposit_asset_with_surplus` mirrors this: it transfers `amount` from the checking account to the beneficiary and simply returns `Ok(surplus)` on a `true` decode, again without confirming the beneficiary's balance actually increased. [7](#0-6) 

This design is explicitly acknowledged in the code comment on `Erc20Credit`: "the actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime." [8](#0-7)  That assumption only holds if the contract is a standards-compliant ERC20 that moves exactly `amount` whenever it returns `true` — an assumption the matcher does nothing to enforce, since it accepts any `AccountKey20` address, including one the caller controls and can deploy fresh via `pallet-revive`.

I confirmed `ERC20Transactor` is actually wired into `asset-hub-westend`'s `xcm_config.rs` (referenced there), so this is not dead/test-only code in that runtime's configuration.

## Impact Explanation
The verified, code-level impact is a bookkeeping desynchronization between an ERC20 contract's real balances and the `AssetsInHolding`/`Erc20Credit` amount recorded by the XCM executor for a given operation — the holding register can be inflated relative to what was actually moved in the checking account, purely by controlling the semantics of a freely-deployable contract's `transfer()` function. Whether this escalates beyond an accounting inconsistency confined to the attacker's own token depends on whether some other component (e.g., `pallet-asset-conversion` pools, reserve-backed cross-chain transfers) treats this ERC20-backed holding credit as real, transferable collateral outside of operations solely involving the attacker's own contract — this downstream sink was not verified in the available context.

## Likelihood Explanation
The reachability preconditions (permissionless contract deployment via `pallet-revive`, and submission of an XCM program via `pallet_xcm::execute` from a signed origin) are consistent with the codebase's general design and are exercised by the existing test suite for erroring cases (`smart_contract_does_not_return_bool_fails`, `non_existent_erc20_will_error` in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs`), supporting that this contract-address-as-asset-id pattern is a live, reachable path rather than purely theoretical.

## Recommendation
- Verify the actual balance delta (via `balanceOf` before/after `transfer()`) at the checking account/beneficiary and use the observed delta, not the requested `amount`, when constructing/consuming `AssetsInHolding` credit.
- Restrict which `AccountKey20` locations can be treated as valid XCM assets via an explicit, curated allow-list rather than matching any syntactically valid local `AccountKey20` location.
- Audit any consumer (asset-conversion pools, reserve/bridging logic) that could treat this holding credit as fungible, transferable collateral, and ensure the same balance-delta verification applies there.

## Proof of Concept
1. Deploy a contract via `pallet-revive` implementing `IERC20::transfer()` that always returns `true` without moving the claimed amount (or applies a fee/rebase).
2. Submit `pallet_xcm::execute` with a `WithdrawAsset` instruction referencing `AccountKey20 { key: <malicious_contract> }` and an inflated `amount`.
3. Observe that `ERC20Transactor::withdraw_asset_with_surplus` credits `AssetsInHolding` with `Erc20Credit(amount)` based solely on the `true` return value, per `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs:191-203`, with no verification against the `TransfersCheckingAccount`'s real balance change.
4. Chain a follow-on instruction consuming that holding credit and confirm it is honored as if fully backed.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
