### Title
Webhook `shop` (and `topic`/`webhook-id`) headers are trusted by `ShopifyAPI::Webhooks::Registry.process` without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then passes the unauthenticated `shop-domain`, `topic`, and `webhook-id` headers straight through to the app's handler as trusted tenant-identifying data. Because the HMAC signable string is the raw body only, none of these headers are cryptographically bound to the signature, so an attacker who possesses one valid `(body, hmac)` pair can freely swap the `shop-domain` header to make the app process the payload as if it came from a different merchant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over that signable string and compares it with the `hmac-sha256` header: [2](#0-1) 

`Registry.process` uses this HMAC check as its only authentication gate, then immediately builds `WebhookMetadata` from the raw, unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` headers and forwards it to the app-supplied handler: [3](#0-2) 

The `shop`, `topic`, and `webhook_id` accessors on `Request` simply read the corresponding HTTP headers with no cross-check against the HMAC-covered body: [4](#0-3) 

The identity binding that should hold is: `shop` used to key/act on tenant data == `shop` authenticated by the HMAC. In this gem the binding is broken: `shop` acted upon by `WebhookMetadata` != anything covered by the HMAC (which binds only the body bytes). Consequently, `Registry.process` cannot distinguish "this body was really sent for shop X" from "this body was sent for shop X, but the shop-domain header now says Y" — both produce a passing HMAC check.

### Impact Explanation
Any internet user who can obtain one legitimate `(raw_body, x-shopify-hmac-sha256)` pair for the app (e.g. by installing the app on their own store, an unprivileged tenant relationship) can replay that exact body to the app's webhook endpoint with the `shop-domain` header (and `topic`/`webhook-id`) rewritten to name a different, victim shop. `Registry.process` will validate the HMAC successfully (it only checks the body) and will invoke the app's registered handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain. Any host application that uses `data.shop` to look up/act on tenant records (the pattern this gem's own documentation instructs developers to use, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will process attacker-supplied data under a foreign tenant's identity — a cross-tenant confusion/injection primitive rooted entirely in this gem's webhook verification logic.

### Likelihood Explanation
Exploitation requires only: (1) a single previously-observed valid webhook body+HMAC pair from the app (trivially available to any merchant who installs the app, satisfying the "unprivileged internet user" bar), and (2) the ability to POST to the app's public webhook endpoint with custom headers, which is inherent to how webhook endpoints work. No access token, `client_secret`, or privileged credential is required. The only constraint is that the replayed body must be one the attacker has already seen (their own webhook traffic), which still yields concrete impact for topics whose body content the app trusts independent of specific values (e.g., `customers/data_request`, `shop/redact`, or any handler that primarily keys off `data.shop`/`data.topic` rather than deeply validating body contents against the claimed shop).

### Recommendation
Bind the tenant-identifying headers into the HMAC-verified surface, or otherwise validate them against a source of truth after HMAC verification:
- Extend `VerifiableQuery`/`Request#to_signable_string` (or add a secondary check in `Registry.process`) so that `shop`, `topic`, and `webhook_id` are verified as belonging together with the body — e.g., look up the shop's installation/session before trusting `request.shop`, and reject processing if the shop is not a known/installed shop for this app.
- At minimum, document and enforce that host applications must independently authorize `data.shop` against their own installed-shop records before using it, and add a guard in the gem itself so `Registry.process` cannot be tricked by header manipulation alone.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook, capturing the raw body `B` and its valid header `x-shopify-hmac-sha256: H` (computed by Shopify over `B` with the app's real secret).
2. Attacker POSTs to the app's webhook endpoint with the same body `B` and same header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`/`x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers and body:
`ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which only hashes `request.to_signable_string` (== `B`) and compares to `H` — this succeeds because `B` and `H` are unchanged from the legitimate capture.
4. `Registry.process` then invokes the app's handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)`, causing the host application to act on `B`'s content attributed to `victim-shop.myshopify.com` instead of `attacker-shop.myshopify.com`.           received_signature = verifiable_query.hmac
