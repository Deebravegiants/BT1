Audit Report

## Title
Unbounded Growth of Gateway HTTP-Action Response Cache Enables Memory-Exhaustion DoS - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

## Summary
The CRE gateway's `responseCache`, which backs outbound HTTP Action caching for `http_handler.go`, stores every cacheable response in a plain Go map keyed by `req.Hash()` with no maximum entry count or aggregate byte-size bound, relying solely on a periodic TTL-based sweep (`DeleteExpired`) for reclamation. This is inconsistent with the sibling `common.RequestCache` abstraction in the same codebase, which explicitly enforces a `maxCacheSize` and rejects new entries once the limit is reached.

## Finding Description
`gatewayHandler.makeOutgoingRequest` stores every outbound HTTP response into `h.responseCache` whenever `req.CacheSettings.Store` is true, or via `Fetch` when `MaxAgeMs > 0`: [1](#0-0) 

The `responseCache` type stores entries in an unbounded map with no size limit, only a TTL field, and the only path that removes entries is the timer-driven `DeleteExpired`: [2](#0-1) [3](#0-2) 

Both `Set` and `Fetch` insert into `rc.cache` unconditionally (subject only to being a cacheable 2xx/4xx status) with no check against map size or memory footprint: [4](#0-3) 

By contrast, `common.RequestCache` — used elsewhere in the same gateway package for pending-request tracking — explicitly bounds itself with `maxCacheSize` and returns an error once the limit is exceeded, confirming that the codebase is aware of and applies this pattern elsewhere but omitted it from `responseCache`: [5](#0-4) [6](#0-5) 

Cache keys are derived from `req.Hash()`, which reflects method, URL, headers, body, and workflow owner — all of which are effectively controlled by whatever request parameters a workflow author configures for its HTTP Action calls. Rate limiting in `http_handler.go` (`globalNodeRateLimiter`, `perNodeRateLimiters`) throttles the *rate* of requests processed from DON nodes, but this is orthogonal to and does not bound *aggregate cache memory*; a sustained stream of uniquely-keyed, `Store: true` requests within normal rate limits will still accumulate indefinitely until the next `CleanUpPeriodMs` tick (default 10 minutes).

## Impact Explanation
This allows an unprivileged workflow author — someone with only the ability to author/execute a workflow whose nodes issue HTTP Action capability calls — to cause the gateway process to accumulate cache entries proportional to `unique_requests_in_ttl_window × response_size`, with no per-entry-count or per-byte ceiling other than the TTL cleanup interval and per-request `MaxResponseBytes`. This is a genuine, code-confirmed resource-exhaustion / DoS risk affecting the shared gateway process (impacting all DONs/workflows served by that instance), distinct from an ordinary rate-limit-bounded load scenario, since the existing rate limiters bound throughput/sec, not the size of retained state.

## Likelihood Explanation
The attack requires no privilege beyond normal workflow authoring: vary URL query strings/headers/body per invocation while setting `CacheSettings.Store = true`, and trigger the workflow repeatedly within the existing per-sender/global rate limits (default `globalRPS = 500`). This is a low-effort, repeatable, sustainable attack from a legitimate workflow author's vantage point, and does not require any operator, admin, host, or database access, nor a malicious node/peer.

## Recommendation
Add a maximum entry count and/or maximum aggregate byte-size bound to `responseCache` (mirroring `common.RequestCache`'s `maxCacheSize` pattern), evicting oldest/LRU entries once exceeded, in addition to the existing TTL-based `DeleteExpired` cleanup.

## Proof of Concept
1. Author a workflow whose HTTP Action requests set `CacheSettings.Store = true` and vary URL query parameters or headers on each invocation, targeting an endpoint returning 2xx/4xx.
2. Trigger the workflow repeatedly within normal per-node/global rate limits, so many distinct requests flow through `gatewayHandler.makeOutgoingRequest` → `responseCache.Set`/`Fetch`.
3. Observe (e.g., via the `RecordCacheSize` metric emitted in `DeleteExpired`) that `len(rc.cache)` grows unboundedly between cleanup cycles, with no rejection or eviction occurring regardless of map size, unlike `common.RequestCache.NewRequest`, which would reject new entries once `maxCacheSize` is reached (see `TestRequestCache_MaxSize`).

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}

func (rc *responseCache) DeleteExpired(ctx context.Context) int {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	now := time.Now()
	var expiredCount int
	for key, cachedResp := range rc.cache {
		if now.After(cachedResp.storedAt.Add(rc.ttl)) {
			delete(rc.cache, key)
			expiredCount++
		}
	}
	rc.lggr.Debugw("Removed expired cached HTTP responses", "count", expiredCount, "remaining", len(rc.cache))
	rc.metrics.IncrementCacheCleanUpCount(ctx, int64(expiredCount), rc.lggr)
	rc.metrics.RecordCacheSize(ctx, int64(len(rc.cache)), rc.lggr)
	return expiredCount
}
