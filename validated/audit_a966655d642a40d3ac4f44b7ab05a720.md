Audit Report

## Title
Ethereum claim signatures are replayable across independent `mint_claim` cycles, allowing redirection of a newly re-minted claim to a stale `dest` - (File: polkadot/runtime/common/src/claims/mod.rs)

## Summary
`Pallet::claim`/`claim_attest` recover an Ethereum signer from a signature over only `prefix || dest` (plus optional statement), with no nonce, amount, or mint-cycle identifier bound into the signed payload. `validate_unsigned` only checks `Claims::<T>::contains_key(&signer)`, and since `mint_claim` can re-populate `Claims` for an address whose prior claim was already paid and removed, a previously broadcast `claim` extrinsic becomes valid again and will redirect the newly minted balance to the stale `dest` from the original claim.

## Finding Description
`claim` recovers `signer` via `Self::eth_recover(&ethereum_signature, &dest.using_encoded(to_ascii_hex), &[][..])` [1](#0-0) , and the signed message construction in `ethereum_signable_message`/`eth_recover` includes only the prefix and `dest` bytes (plus statement for `claim_attest`), with no nonce or claim-instance data [2](#0-1) . `validate_unsigned` re-derives the same signer for both `claim` and `claim_attest` and only checks `Claims::<T>::contains_key(&signer)` [3](#0-2) . `Claims` is a flat `StorageMap<EthereumAddress, BalanceOf<T>>` with no versioning/nonce field [4](#0-3) . `mint_claim` (root-only) simply re-inserts a value into `Claims` for the given address regardless of prior history [5](#0-4) . `process_claim` pays the stored balance to whatever `dest` is supplied in the call and then clears `Claims`/`Vesting`/`Signing` for that signer [6](#0-5) .

This confirms the mechanics: nothing in the signed payload or in `validate_unsigned` distinguishes a fresh `mint_claim` cycle from a stale, already-executed one for the same Ethereum address. If root calls `mint_claim` again for an address that previously had its claim fully paid and removed, any historical `claim(dest_A, sig)` extrinsic for that address becomes valid again and will redirect the new balance to `dest_A`.

## Impact Explanation
This is a real logic flaw in the claims pallet: the signature scheme provides no binding to a specific mint instance, so re-minting for an already-claimed address silently revives old signatures. The impact is redirection of newly minted claim funds to a destination address chosen in a prior, unrelated claim cycle, without requiring any new signature from the Ethereum key holder — a legitimate accounting/security defect in the pallet as claimed.

## Likelihood Explanation
Exploitation is trivial (resubmitting old, publicly visible extrinsic bytes) but strictly conditional on root/governance choosing to call `mint_claim` a second time for an Ethereum address that has already been fully claimed and had its `Claims` entry removed. This is an unusual but plausible administrative action (e.g., re-crediting or correcting a claim). The report itself acknowledges this precondition, and the "attacker action" (replay) requires no privilege once the precondition is met — this matches a normal user-triggerable exploit path once governance re-mints.

## Recommendation
Bind the signed message to a claim-instance identifier, such as a per-address nonce/epoch incremented by `mint_claim`, or include the value/mint block number in `ethereum_signable_message`, and validate that identifier in both `validate_unsigned` and `process_claim`. Alternatively, prevent `mint_claim` from creating a new claim for an address whose previous claim was already fully paid unless the stored state also resets a nonce that invalidates prior signatures.

## Proof of Concept
As described in the report: (1) `mint_claim(root, eth_addr, 100)`; (2) submit `claim(dest=42, sig_over_42)` — succeeds, pays 100 to account 42, removes `Claims[eth_addr]`; (3) `mint_claim(root, eth_addr, 200)` again for the same address; (4) resubmit the original `claim(dest=42, sig_over_42)` extrinsic — `validate_unsigned` succeeds because `Claims::contains_key(eth_addr)` is true again, and `process_claim` pays the new 200 to the stale `dest=42` instead of any newly intended destination, with no new signature produced. This can be implemented as a Rust unit test in `polkadot/runtime/common/src/claims/tests.rs` following the exact steps in the report.

	// Constructs the message that Ethereum RPC's `personal_sign` and `eth_sign` would sign.
	fn ethereum_signable_message(what: &[u8], extra: &[u8]) -> Vec<u8> {
		let prefix = T::Prefix::get();
		let mut l = prefix.len() + what.len() + extra.len();
		let mut rev = Vec::new();
		while l > 0 {
			rev.push(b'0' + (l % 10) as u8);
			l /= 10;
		}
		let mut v = b"\x19Ethereum Signed Message:\n".to_vec();
		v.extend(rev.into_iter().rev());
		v.extend_from_slice(prefix);
		v.extend_from_slice(what);
		v.extend_from_slice(extra);
		v
	}

	// Attempts to recover the Ethereum address from a message signature signed by using
	// the Ethereum RPC's `personal_sign` and `eth_sign`.
	fn eth_recover(s: &EcdsaSignature, what: &[u8], extra: &[u8]) -> Option<EthereumAddress> {
		let msg = keccak_256(&Self::ethereum_signable_message(what, extra));
		let mut res = EthereumAddress::default();
		res.0
			.copy_from_slice(&keccak_256(&secp256k1_ecdsa_recover(&s.0, &msg).ok()?[..])[12..]);
		Some(res)
	}

	fn process_claim(signer: EthereumAddress, dest: T::AccountId) -> sp_runtime::DispatchResult {
		let balance_due = Claims::<T>::get(&signer).ok_or(Error::<T>::SignerHasNoClaim)?;

		let new_total =
			Total::<T>::get().checked_sub(&balance_due).ok_or(Error::<T>::PotUnderflow)?;

		let vesting = Vesting::<T>::get(&signer);
		if let Some(_) = vesting {
			if T::VestingSchedule::vesting_balance(&dest).is_some() {
				return Err(Error::<T>::VestedBalanceExists.into());
			}

			// A vesting schedule installs a balance lock, which requires the account to stay alive,
			// otherwise it is dusted and the lock placed on a non-existent account. The `dest` may
			// already hold funds, so a small claim that tops an existing account over the ED is
			// valid.
			let free_after = CurrencyOf::<T>::free_balance(&dest).saturating_add(balance_due);
			ensure!(
				free_after >= CurrencyOf::<T>::minimum_balance(),
				Error::<T>::ClaimBelowExistentialDeposit,
			);
		}

		// We first need to deposit the balance to ensure that the account exists.
		let _ = CurrencyOf::<T>::deposit_creating(&dest, balance_due);

		// Check if this claim should have a vesting schedule.
		if let Some(vs) = vesting {
			// This can only fail if the account already has a vesting schedule or its balance is
			// below the existential deposit, both of which are checked above.
			T::VestingSchedule::add_vesting_schedule(&dest, vs.0, vs.1, vs.2)
				.map_err(|_| Error::<T>::VestedBalanceExists)?;
		}

		Total::<T>::put(new_total);
		Claims::<T>::remove(&signer);
		Vesting::<T>::remove(&signer);
		Signing::<T>::remove(&signer);

		// Let's deposit an event to let the outside world know this happened.
		Self::deposit_event(Event::<T>::Claimed {
			who: dest,
			ethereum_address: signer,
			amount: balance_due,
		});

		Ok(())
	}
