### Title
`findMatchingWithdrawal` matches by `assetId` only, misattributing a completed withdrawal's `txHash` across multiple same-asset withdrawal indices in one batch - ([File: packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts])

### Summary
`findMatchingWithdrawal` (used both by `PoaBridge.describeWithdrawal` in `poa-bridge.ts:313-343` and by `waitForWithdrawalCompletion.ts:144-153`) selects the first withdrawal entry from the POA API response whose `nep141:${w.data.near_token_id}` equals `criteria.assetId`, without disambiguating by `index`, amount, or destination address. If an unprivileged caller submits a batch withdrawal with two entries sharing the same `assetId` but different `destinationAddress`, both indices resolve to the same underlying API record, so a single completed transfer's `txHash` gets reported for both destinations.

### Finding Description
The broken equality: `describeWithdrawal(index=1).txHash` should equal "the txHash of the on-chain transfer sent to `withdrawalParams[1].destinationAddress`", but the code guarantees only `describeWithdrawal(index=0).txHash === describeWithdrawal(index=1).txHash === firstMatch.data.transfer_tx_hash` whenever `withdrawalParams[0].assetId === withdrawalParams[1].assetId`.

Code path: `describeWithdrawal` (`poa-bridge.ts:313-343`) calls `getWithdrawalStatusWithRetry` then `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` (`poa-bridge.ts:319-322`). `findMatchingWithdrawal` (`waitForWithdrawalCompletion.ts:144-153`) does `withdrawals.find((w) => \`nep141:${w.data.near_token_id}\` === criteria.assetId)` — an `Array.prototype.find` that returns the *first* match regardless of amount, destination, or the caller-supplied `index`. The code's own comment (`waitForWithdrawalCompletion.ts:135-143`) explicitly acknowledges: "This means multiple withdrawals of the same token in a single transaction are not supported. POA API doesn't currently support this case either."

This is a genuinely reachable path: an unprivileged NEAR Intents user constructs their own batch withdrawal intent (e.g., two BTC withdrawals to two different destination addresses within a single `ft_withdraw`/multi-payload intent), which the SDK does not reject — `createWithdrawalIdentifier` (`poa-bridge.ts:295-311`) builds one `WithdrawalIdentifier` per array element with no assetId-uniqueness check, and no `validateWithdrawal`/`supports()`/`assert` guard in `poa-bridge.ts` rejects duplicate `assetId` entries in a batch. When the integrator later calls `describeWithdrawal` (directly, or via `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion`) for index 0 and index 1, both calls query the same `tx.hash` and get the same `response.withdrawals` list; `findMatchingWithdrawal` returns the identical first-matching record for both, so both indices report the identical `status`/`txHash` even though the POA API might have (or eventually will have) two distinct withdrawal records for the two different destinations.

No existing guard prevents this: `validateAddress`, `compareAddresses`, and `FeeExceedsAmountError` operate on per-request validation, not on cross-index disambiguation within a batch's status polling; the intents contract's own signature/nonce checks are irrelevant to this off-chain status-reporting logic.

### Impact Explanation
This is a status/hash misreport, not a fund-movement bug — no additional funds are moved, and no signature is replayed. The integrator, trusting the SDK's per-index `describeWithdrawal`/`waitForWithdrawalCompletion` results, would attribute one destination's `txHash` (and its "completed" status) to the *other* destination as well. If the integrator's off-chain bookkeeping credits/refunds users based on this per-index status (as the RFC in `docs/design/rfc-batch-withdrawal-granular-control.md` explicitly describes as the intended usage pattern — e.g. `if (index === 0) quoteEntity.destinationTx = tx.hash; if (index === 1) quoteEntity.refundTx = tx.hash;`), it may mark both destinations "completed" using the same `txHash`, potentially causing a double-credit/wrong-payout report for a transfer that only actually happened once. This matches the "status or hash misreport making an integrator credit or refund twice" category — **High** severity (misreport), not Critical, since no on-chain fund misrouting or signature abuse occurs; the actual on-chain destination is still whatever address was validated and submitted in the withdrawal intent itself.

### Likelihood Explanation
Preconditions: the caller must construct a batch withdrawal with ≥2 entries sharing the same `assetId` (same token, same chain) but different destinations — a normal, permissionless action requiring no privilege beyond authoring one's own intent. Attacker cost is minimal (one intent, standard fees). The bug is deterministic and repeatable for every batch with duplicate `assetId`s, as long as the integrator relies on per-index `describeWithdrawal` results for financial bookkeeping. However, it self-reports as a known, documented limitation in the code (`waitForWithdrawalCompletion.ts:138-142`) rather than a silent unknown flaw, and its ultimate harm requires the integrator to use this per-index API in the described batch-credit pattern.

### Recommendation
Disambiguate matching in `findMatchingWithdrawal` by more than `assetId` — e.g., match by `destinationAddress`/amount in addition to token, or require the POA API to return withdrawals tagged with an index/nonce so each `WithdrawalIdentifier.index` can be mapped to the correct API record; alternatively, when duplicate `assetId`s are detected within a single batch's `withdrawalParams`, reject the batch at construction with an explicit "duplicate asset withdrawals unsupported" error rather than silently returning ambiguous status data at query time.

### Proof of Concept
```ts
// mock poaBridge.httpClient.getWithdrawalStatus to return a single withdrawals[]
// entry: { status: "COMPLETED", data: { near_token_id: "btc.omft.near", transfer_tx_hash: "0xABC", chain: "bitcoin" } }
// for assetId "nep141:btc.omft.near"

const withdrawalParams = [
  { assetId: "nep141:btc.omft.near", destinationAddress: "bc1_addr_A", amount: 1000n },
  { assetId: "nep141:btc.omft.near", destinationAddress: "bc1_addr_B", amount: 2000n },
];

const status0 = await poaBridge.describeWithdrawal({ index: 0, withdrawalParams: withdrawalParams[0], tx, landingChain });
const status1 = await poaBridge.describeWithdrawal({ index: 1, withdrawalParams: withdrawalParams[1], tx, landingChain });

expect(status0.status).toBe("completed");
expect(status1.status).toBe("completed");
expect(status0.txHash).toBe("0xABC");
expect(status1.txHash).toBe("0xABC"); // BUG: same txHash reported for destination B though only one transfer completed (to A)
```
