Found a valid analog: `handle_unsigned` in `pallet-ismp` uses a **fixed static weight** regardless of the number of messages/requests in the batch, while `Self::execute(messages.clone())` (via `handlers::request::handle`, `response::handle`, `timeout::handle`) contains unbounded loops over `msg.requests` — an attacker-controlled `Vec` with no length cap.

### Title
Unsigned `handle_unsigned` extrinsic charges a fixed weight for an unbounded message batch, enabling a block-execution DoS - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`pallet_ismp::Pallet::handle_unsigned` is declared `#[pallet::weight(weight())]` where `weight()` returns a constant `Weight::from_parts(300_000_000, 0)` [1](#0-0)  irrespective of `messages: Vec<Message>` size. This extrinsic is permissionless (`ensure_none(origin)`) [2](#0-1)  and reachable by any relayer submitting an unsigned transaction.

### Finding Description
Each `Message` variant dispatched by `handle_unsigned` fans out into per-request loops with no cap on `requests.len()`: `handlers::request::handle` iterates `msg.requests` twice (dedup + membership-proof build) and again for dispatch [3](#0-2) , `response::handle` similarly iterates `msg.requests` for state-proof verification and dispatch [4](#0-3) , and `timeout::handle` loops over `requests`/timeouts for both `Post` and `Get` variants [5](#0-4) . `validate_unsigned` itself calls `Self::execute(messages.clone())` before the extrinsic is even included in a block, to compute the priority tag [6](#0-5) , meaning the unbounded work runs at least twice per submission — once during pool validation, once during actual dispatch — for a declared weight that never scales with `messages.len()` or the size of the nested request vectors.

This mirrors the reported `massUpdatePools()` gas-overflow class: an unbounded, size-dependent loop reachable without special privilege, with no offset/limit and no explicit "small array" invariant, but here the consequence is worse than simple exhaustion because the extrinsic's *declared* weight is fixed and does not reflect the *actual* computational cost, which is the mechanism Substrate uses to bound block-authoring time.

### Impact Explanation
A relayer can submit `handle_unsigned` with a very large `Vec<Message>` (or a small number of `Message::Request`/`Message::Response`/`Message::Timeout` each carrying a huge inner `requests`/`timeouts` vector). Because the pallet's weight annotation is a constant unrelated to the payload size, the runtime's weight-based block-fullness accounting will under-charge this extrinsic, letting the block builder include it while the actual execution time (proof verification, hashing, signature checks per request, router dispatch per request) vastly exceeds the block's real time budget. This can stall or delay block production/finality for the chain, which blocks *all* pending ISMP message delivery routes (a "route unable to deliver messages" condition) until the offending block is produced or the node recovers — a network-wide liveness/DoS impact rather than a self-inflicted revert, because Substrate's weight system (unlike EVM per-tx gas) is meant to bound collator-side execution across the whole block, and a mis-costed extrinsic breaks that invariant for every transaction sharing the block.

### Likelihood Explanation
Medium-High: no privileged role or state is required — only an unsigned extrinsic with an oversized `messages` vector or oversized nested `requests`/`timeouts` arrays. `validate_unsigned` runs `Self::execute` unconditionally on every submission (mempool + block execution), so the cost is paid even to reject a batch, and the only guard is transaction-pool rate limiting, not a protocol-level bound on batch size.

### Recommendation
Bound `messages.len()` and the per-message `requests`/`timeouts` vector lengths at the transaction-validity layer (reject oversized `Vec`s in `validate_unsigned`/`pre_dispatch` before calling `execute`), and make `#[pallet::weight(...)]` for `handle_unsigned` a function of the actual batch size (e.g., benchmarked per-request weight × `messages.iter().map(|m| m.len()).sum()`) rather than a flat constant, so the runtime's weight accounting reflects real execution cost and can reject over-large batches before they are included in a block.

### Proof of Concept
1. Craft a single `Message::Request(RequestMessage { requests: <N very large>, proof, signer })` with `N` large enough that the state-proof verification, dedup and per-request dispatch loops in `handlers::request::handle` (`modules/ismp/core/src/handlers/request.rs`) take substantially longer than the time budget implied by the fixed 300,000,000-weight annotation on `handle_unsigned`.
2. Submit it as an unsigned extrinsic; `validate_unsigned` calls `Self::execute(messages.clone())` once to build the pool tag [7](#0-6) , and if it validates, the same unbounded work runs again in `handle_unsigned`'s dispatch [8](#0-7) , all charged at the fixed weight.
3. Repeat/batch such extrinsics to make collator block-building time diverge from the weight-derived block budget, delaying block production and therefore all ISMP message delivery routes on the chain.
