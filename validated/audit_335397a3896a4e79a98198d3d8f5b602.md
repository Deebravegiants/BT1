### Title
Webhook Shop-Tenant Spoofing via Unsigned HTTP Headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates an incoming webhook solely by validating the `X-Shopify-Hmac-Sha256` signature against the **raw request body**. The tenant-identifying fields the gem hands to application handlers — `shop`, `topic`, `api-version`, and `webhook-id` — are all read from HTTP headers that are **not included in the signed payload**. The identity binding the app relies on (`shop == HMAC-authenticated shop`) is broken: the HMAC only proves "signed with this app's `client_secret`", not "this event is about shop X".

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from headers with no cryptographic binding to the signature: [2](#0-1) 

`Webhooks::Registry.process` validates the HMAC and then constructs `WebhookMetadata` using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`, and forwards them to the app's handler as trusted identifiers: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and `Context.api_secret_key`: [4](#0-3) 

Because `Context.api_secret_key` is a single value shared by the app across **every** installed shop (all merchants share the same `client_id`/`client_secret` pair for a given app), any tenant that has installed the app can obtain a validly-signed webhook body for their own store's events. An attacker can then replay that request to the app's webhook endpoint while altering the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header to name a victim shop. The HMAC check still passes because it never covers those headers — `request.shop` is a field "acted on but not covered by the HMAC," exactly the identity-binding gap called out in scope.

### Impact Explanation
Apps built on this gem are expected to trust `WebhookMetadata#shop` to look up the correct merchant's session/access token and perform tenant-scoped actions (e.g., data deletion, order sync, entitlement changes). Since that value is unauthenticated, an attacker who controls one legitimately-installed shop can force the app to execute webhook-triggered logic under a different, victim shop's identity — a cross-tenant access impact, which is explicitly in the Critical impact category defined by the rules.

### Likelihood Explanation
Exploitation requires only that the attacker (1) install the target app on any shop they control (a normal, unprivileged action for any merchant) and (2) POST a captured/replayed webhook body to the app's public webhook endpoint with a forged `shop-domain` header. No access token, `client_secret`, or privileged account is required — only ordinary merchant-level access to a shop that has the app installed, which is available to any unprivileged internet user who installs the app for free.

### Recommendation
Bind the tenant-identifying headers into the HMAC-verified payload instead of trusting them unauthenticated. For example, include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or independently re-derive/verify `shop` against a value obtained through an authenticated channel, such as looking up the session by a value covered by the signature) before constructing `WebhookMetadata` and dispatching to handlers in `Webhooks::Registry#process`.

### Proof of Concept
1. Install the target Shopify app on `attacker-shop.myshopify.com` (any unprivileged Shopify Partner/merchant account can do this).
2. Trigger any webhook event (e.g. `orders/create`) on `attacker-shop`; capture the resulting POST — raw body `B`, header `X-Shopify-Hmac-Sha256: H` (valid because it's computed over `B` with the app's real `client_secret`), and header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Replay the exact same request to the app's webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and optionally the topic/webhook-id headers).
4. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `B` against `H`; `Webhooks::Registry#process` (`lib/shopify_api/webhooks/registry.rb:188-199`) proceeds and calls the app's handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, causing the app to perform the webhook's action against the victim tenant's stored session/access token.

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(signable_string: String, secret: String).returns(String) }
        def compute_signature(signable_string, secret)
          OpenSSL::HMAC.hexdigest(

            secret,
