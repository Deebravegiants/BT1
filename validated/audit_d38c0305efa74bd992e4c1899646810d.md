## Analog Found

### Title
Withdrawal status matched only by `assetId` causes status/hash misattribution across same-asset batch withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` identifies which on-chain withdrawal record corresponds to a given `WithdrawalIdentifier` by matching solely on `assetId`, via `findMatchingWithdrawal` [1](#0-0) . When a single NEAR transaction contains two or more withdrawals of the same token (a supported "batch withdrawal" pattern per the SDK's `WithdrawalParams[]` / `createWithdrawalCompletionPromises` API [2](#0-1) ), `Array.prototype.find` always returns the *first* withdrawal record whose `near_token_id` matches, regardless of which index/withdrawal is actually being queried. This is analogous to the Knox bug class: multiple distinct records (orders / withdrawals) that share a lookup key collapse into a single tracked identity, so one withdrawal's completion status/tx-hash is (mis)reported for another.

### Finding Description
`describeWithdrawal` is called once per withdrawal index in a batch, with `args.withdrawalParams.assetId` as the only correlation key: [3](#0-2) . The identifier itself, built by `createWithdrawalIdentifier`, carries an `index` field [4](#0-3) , but this `index` is never used in `findMatchingWithdrawal` to disambiguate between multiple same-asset withdrawals in the response array — it is matched purely by `nep141:{near_token_id} === assetId` [5](#0-4) . The equivalent standalone helper in `internal-utils` carries the same limitation and even documents it explicitly: "multiple withdrawals of the same token in a single transaction are not supported" [6](#0-5) .

Consequently, for a batch like `withdrawalParams = [ {assetId: USDC, dest: A}, {assetId: USDC, dest: B} ]`, both `describeWithdrawal` calls (index 0 and index 1) query the same bridge response and both resolve to the *same* array element (whichever `.find()` returns first). If that element is `COMPLETED`, `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` resolve **both** promises as completed with the **same `transfer_tx_hash`**, even though the withdrawal to `B` may still be pending or may have failed on-chain.

### Impact Explanation
This breaks the equality "status/hash reported for withdrawal i == the actual on-chain outcome of withdrawal i." Per the SDK's documented per-index correspondence contract ("Index correspondence: `promises[i]` corresponds to `withdrawalParams[i]`" [7](#0-6) ), a consuming integrator that persists/credits per-withdrawal completion (as illustrated in the project's own RFC recovery flow, e.g. `saveSuccess(index, tx)` [8](#0-7) ) would incorrectly mark the second (still-pending/different) withdrawal as completed and record the wrong destination tx hash for it. This matches the High-severity class "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
Requires only that a caller submit a batch withdrawal (a supported, documented feature) with two or more entries sharing the same `assetId`/token, which is an entirely legitimate, unprivileged use case (e.g., splitting one token to two destination addresses) — no malicious relayer/bridge/admin behavior needed. The code comments confirm the authors are aware same-asset batches are unhandled but the guard is only documentation, not an actual runtime rejection or disambiguation.

### Recommendation
Disambiguate matching using more than `assetId` — e.g., correlate by `destinationAddress`/`amount` in addition to token, or (as the existing code comments suggest) sort both the API response and the local `withdrawalParams` array by amount for withdrawals of the same asset, and match by relative order. Until the POA API can return a stable per-withdrawal identifier, `describeWithdrawal`/`waitForWithdrawalCompletion` should refuse (throw) rather than silently return an ambiguous match when multiple same-asset withdrawals exist in the same batch, to avoid a false "completed" status/hash being propagated to callers.

### Proof of Concept
1. Submit `signAndSendWithdrawalIntent` with `withdrawalParams = [{assetId: "nep141:usdc.near", amount: 100, destinationAddress: A}, {assetId: "nep141:usdc.near", amount: 200, destinationAddress: B}]` in one NEAR intent transaction.
2. Call `sdk.createWithdrawalCompletionPromises({ withdrawalParams, intentTx })`, producing `promises[0]` and `promises[1]`, each internally calling `PoaBridge.describeWithdrawal` with `index: 0` and `index: 1` respectively but identical `assetId`.
3. Suppose the POA bridge processes withdrawal to `A` first and it reaches `COMPLETED` while the withdrawal to `B` is still `PENDING`. The bridge status API returns an array containing (at least) the `A` record as `COMPLETED`.
4. `findMatchingWithdrawal` for index 1's query (`args.withdrawalParams.assetId` = USDC) also matches the `A` record via `.find()` since it only filters by `near_token_id`, and returns `{status: "completed", txHash: A's tx}` for `promises[1]` too.
5. Both `promises[0]` and `promises[1]` resolve with `{status:"completed"}` using `A`'s transfer tx hash, even though `B`'s withdrawal is not actually complete — an integrator following the SDK's documented per-index recovery pattern would incorrectly credit/finalize withdrawal `B` using the wrong (or duplicate) transaction hash.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**

	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,

	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {

		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
