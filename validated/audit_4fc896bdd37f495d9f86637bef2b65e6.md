### Title
Interest-accrual `i128` overflow in `scaled_to_original` permanently freezes a market — every entrypoint panics before reaching the borrow-index cap - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
Analogous to CVE-2024-47213 (a single malformed input crashes the validation path and halts all event processing), XOXNO Lending's pool has a state-dependent hard crash in the accrual path that, once reached, panics *every* subsequent operation on that market forever. The accrual step unscales total debt via `scaled_to_original(env, borrowed, borrow_index)` — a plain `i128` multiply — before any index-cap clamp can engage. When `borrowed_shares × borrow_index / RAY` exceeds `i128::MAX`, the call panics with `MathOverflow` (33). Because `interest::global_sync` runs first in every market mutation (`Cache::load → accrue → mutate → guards`), no `update_indexes`, `repay`, `withdraw`, `liquidate`, `clean_bad_debt`, `claim_revenue`, `recapitalize`, `supply`, or `borrow` can ever execute for that market again. The protocol's own regression test demonstrates the freeze end-to-end.

### Finding Description
- `common/src/rates/simulate.rs:60` — `accrue_step` computes `borrowed_original = scaled_to_original(env, borrowed, borrow_index)` unconditionally on every accrual chunk.
- `common/src/rates/scaling.rs:14-16` — `scaled_to_original` is `scaled.mul(env, index)`, a checked `i128` mul that panics on overflow; there is no saturation or debt-value cap.
- `common/src/rates/index.rs:13-19` — `update_borrow_index` clamps the *index* at `MAX_BORROW_INDEX_RAY`, but that clamp runs *after* the debt-value multiply at simulate.rs:60 already panicked, and only bounds index growth, not the `borrowed × index` product.
- `contracts/pool/src/interest.rs:20-33` — `global_sync` runs this step on every market mutation before any state change, in chunks of `MAX_COMPOUND_DELTA_MS`; the overflow occurs inside the chunk loop, so `last_timestamp` never advances and there is no partial-progress escape.
- `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361` — `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` proves the cliff: an 18-decimal market at 98% utilization on a steep rate curve grows `borrowed × index` past `i128::MAX` *before* `borrow_index` reaches `MAX_BORROW_INDEX_RAY` (the test asserts `last.borrow_index < MAX_BORROW_INDEX_RAY`), and then `try_update_indexes_for`, `try_withdraw_raw`, and `try_repay` all fail with `MATH_OVERFLOW`.
- `docs/reference/invariants.md` (INV-IDX-01) acknowledges the residual: "Debt-value overflow can still revert accrual before that ceiling is reached. Bounded indexes do not guarantee representable position or market values" — i.e., the cap does not prevent the freeze.

Reachable path for a single unprivileged address: `supply` a very large amount of a high-decimals asset into a spoke whose cap permits it, `borrow` near-maximum utilization, then simply wait (or repeatedly call the permissionless `update_indexes`) until sustained interest pushes `borrowed × borrow_index` over `i128::MAX`. No privileged call is needed at trigger time; the panic is reached by ordinary market usage plus elapsed time.

### Impact Explanation
Permanent freezing of funds (accepted impact). Once the product crosses the cliff, the market's debt can never be repaid or liquidated, suppliers can never withdraw, protocol revenue can never be claimed, and `recapitalize` cannot unstick it because it too accrues first. Borrowers keep debt they cannot repay and suppliers' claims are permanently locked. The bad-debt socialization escape (`clean_bad_debt`) also hits `global_sync` and panics, so there is no recovery path short of a contract upgrade — i.e., the funds are frozen permanently from the perspective of unprivileged actors.

### Likelihood Explanation
Medium-Low. The trigger requires an extreme `borrowed × index` product: the repo test uses a 1-billion-whole-token-scale 18-decimal asset at 98% sustained utilization on the XLM-style curve, taking multiple years of elapsed time. A realistic trigger needs (a) a listed asset with very large token supply/decimals such that RAY-scaled `borrowed` is near `i128::MAX / MAX_BORROW_INDEX_RAY`, (b) a borrow cap set high enough to permit that debt (cap domain is bounded by `require_cap_within_asset_domain`, but for high-decimal assets the representable cap is still astronomically large), and (c) sustained high utilization. An attacker cannot shortcut the time component, but the condition is irreversible once approached — there is no mechanism to reduce `borrowed` shares without accrual succeeding first. Protocols listing high-decimal, high-total-supply assets with generous caps are exposed.

### Recommendation
- Make `accrue_step` saturate rather than panic: clamp `borrowed_original` (and `supplied_original`) at a protocol constant (e.g., `MAX_RAY_VALUE`) the same way `update_borrow_index` clamps the index, so accrual degrades gracefully instead of bricking the market.
- Alternatively, pre-check `borrowed` against `i128::MAX / borrow_index` in `global_sync` and short-circuit accrual (booking no further interest) once debt value is unrepresentable — interest loss is preferable to a permanent freeze.
- Add a hard utilization or debt-ceiling guard independent of token caps so `borrowed` shares can never approach the overflow domain for listed assets.
- Extend `clean_bad_debt`/`seize_positions` with an accrual-bypass escape hatch so bad debt can be written down even when accrual itself is uncomputable.

### Proof of Concept
Existing in-repo reproduction: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`, `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`:

1. Create an 18-decimal market with the XLM rate curve; lift caps; BOB supplies `1e9 × 10^18` units.
2. ALICE borrows 98% of it (`borrow_raw`), driving utilization into the steep curve segment.
3. Loop: `advance_time(YEAR_SECS)` then `try_update_indexes_for(["BIG18"])`. Within the tested bound, the call returns `Error(Contract, #33)` (`MATH_OVERFLOW`) while `borrow_index < MAX_BORROW_INDEX_RAY` — the index cap never engages.
4. Assert the freeze: `try_withdraw_raw(BOB, "BIG18", 1)` → `MATH_OVERFLOW`; `try_repay(ALICE, "BIG18", 1.0)` → `MATH_OVERFLOW`. The same panic hits `liquidate`, `clean_bad_debt`, `claim_revenue`, `recapitalize`, and `supply`/`borrow`, since all run `Cache::load` → `global_sync` → `accrue_step` → `scaled_to_original` first.

Uncertainty note: whether a *realistically capped* mainnet market can reach the cliff depends on the governed borrow cap and the asset's decimals/total supply; with conservative caps the product may stay representable. The vulnerability is a missing saturation bound in a universally executed path, not dependent on a privileged misconfiguration of the arithmetic itself.
