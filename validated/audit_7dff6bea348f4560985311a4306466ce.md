### Title
Skipped authority-set epochs during consensus catch-up leave `EvmHost._epochs[set_id]` unset, permanently forfeiting the associated relayer reward - (File: evm/src/core/HandlerV2.sol)

### Summary
`HandlerV2.handleConsensus` attributes a consensus-proof delivery to a relayer by recording only a single epoch — `nextAuthoritySetId - 1` — exactly mirroring the Perennial vault's assumption that only the "current + 1" version needs to be checked. If a delivered consensus proof advances the destination's authority set by more than one increment in a single call, every epoch strictly between the previously recorded `currentEpoch` and `nextAuthoritySetId - 1` is silently skipped and can never be attributed to any relayer.

### Finding Description
`handleConsensus` computes and records the epoch as follows: [1](#0-0) 

This only compares the new epoch against `host.currentEpoch()` and unconditionally advances it — it never checks or iterates any epochs that may lie strictly between the old `currentEpoch` and the new one, just as Perennial's `BalancedVault` only checked `currentVersion`/`currentVersion+1` and silently mis-happened when the product actually skipped a version.

Downstream, `OutboundConsensusDeliveryReward` claims are validated purely by proving that the destination's `EvmHost._epochs[set_id]` storage slot equals the claimant's signing address for the exact `set_id` being claimed: [2](#0-1) 

`_epochs[set_id]` is populated only via `HandlerV2.handleConsensus` → `EvmHost.recordEpoch`, and the recording logic (above) has no backfill path for skipped intermediate epochs. If a set_id is skipped, its `_epochs[set_id]` slot stays at `address(0)` forever, and no relayer signature can ever recover that address in the claim's ECDSA-recovery check, so the claim can never be satisfied for that `set_id`.

The protocol itself acknowledges destinations can fall multiple epochs behind and require multi-rotation catch-up: [3](#0-2) 

and that this catch-up is explicitly "best-effort," with partial failures logged and surfaced rather than guaranteed to submit every intervening rotation: [4](#0-3) 

If the catch-up loop fails partway (or a relayer submits only the final/most-recent rotation proof instead of every intermediate one — nothing in `HandlerV2.handleConsensus` prevents a valid `verify()` result whose `nextAuthoritySetId` jumps by more than 1 from being accepted), the epochs in between are permanently orphaned in exactly the same way Perennial's vault treated a skipped oracle version as a phantom loss.

### Impact Explanation
Each orphaned epoch's `OutboundConsensusDeliveryReward` becomes a permanently unclaimable line item: the treasury-funded reward earmarked for delivering that authority-set rotation can never be paid to any relayer because the on-chain attribution slot required by the claim's proof-of-slot-ownership check (`_epochs[set_id] == recovered_address`) can never be made non-zero after the fact. This is a permanent, protocol-level loss of reward accounting for the affected epochs — the same "medium" class of unintended-settlement/miscalculation impact for which the Perennial report was ultimately scored, translated here to the relayer/reward-accounting domain explicitly in scope.

### Likelihood Explanation
This requires a destination `EvmHost` to fall behind by more than one authority-set rotation and then be updated via a single `handleConsensus` call (or a catch-up sequence that does not submit every intermediate rotation proof individually) whose returned `nextAuthoritySetId` is more than 1 greater than `host.currentEpoch()`. The system's own catch-up code explicitly anticipates and handles multi-epoch backlogs, and treats partial catch-up failures as recoverable/best-effort rather than fatal, which is precisely the condition that produces the skip. I was not able to fully confirm from the indexed code whether every concrete `IConsensusV2` implementation (BEEFY, SP1-based) is structurally prevented from returning a `nextAuthoritySetId` more than one epoch ahead of the previously recorded epoch in a single `verify()` call; this should be verified directly against the consensus-client implementations before treating likelihood as certain.

### Recommendation
Do not assume only one epoch boundary (`nextAuthoritySetId - 1`) was crossed. When `nextAuthoritySetId - 1 > host.currentEpoch() + 1`, either (a) record/credit the delivering relayer for the entire span of epochs from `host.currentEpoch()+1` through `nextAuthoritySetId - 1` (analogous to `pallet_consensus_incentives::calculate_reward`'s span-based `latest - baseline` model rather than an exact match), or (b) explicitly disallow/require sequential epoch delivery so gaps cannot occur, forcing every intermediate rotation to be proven and recorded individually before it becomes unrecoverable.

### Proof of Concept
1. Destination `EvmHost` is at `currentEpoch = 5` (last rotation recorded via `recordEpoch(5, relayerA)`).
2. The BEEFY/SP1 authority set on Hyperbridge subsequently rotates through epochs 6, 7, and 8 without any relayer submitting an intermediate consensus proof to this destination (e.g., low traffic to this chain, or a partial catch-up failure as anticipated in `tesseract/messaging/messaging/src/outbound.rs`).
3. A relayer eventually submits a single consensus proof whose `verify()` result reports `nextAuthoritySetId = 9` (i.e., the destination is caught straight up to the latest set).
4. `HandlerV2.handleConsensus` computes `epoch = 9 - 1 = 8`; since `8 > currentEpoch (5)`, it calls `host.recordEpoch(8, relayer)`, setting `_epochs[8] = relayer` and `currentEpoch = 8`.
5. `_epochs[6]` and `_epochs[7]` remain `address(0)` permanently — `handleConsensus` never revisits them because `currentEpoch` has already advanced past them.
6. Any later attempt to `claim_outbound_consensus_delivery_reward` for `set_id = 6` or `7` via `modules/pallets/relayer/src/outbound_consensus.rs` will prove `_epochs[6]/[7] == address(0)` against Hyperbridge's state commitment, which no valid relayer signature can satisfy — the rewards for epochs 6 and 7 are permanently forfeited.
