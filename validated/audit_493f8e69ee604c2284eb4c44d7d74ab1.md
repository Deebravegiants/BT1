### Title
Webhook `shop-domain` Header Is Not Covered By The HMAC Signature, Enabling Cross-Tenant Webhook Forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)` [1](#0-0) . The `Request#to_signable_string` method used for that HMAC computation returns only `@raw_body`, never the `shop-domain` header [2](#0-1) . Yet the `shop` attribute, parsed straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header, is trusted and forwarded unchanged to the webhook handler as the tenant identity [3](#0-2) [4](#0-3) .

### Finding Description
The binding that should hold is: `shop-domain header == shop bound by HMAC`. In reality, the code only proves `raw_body == raw_body signed by api_secret_key`; the `shop` field is never part of the signed material.

Because the webhook HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that installs the app, any merchant who installs the app on their own store is a valid "oracle" for HMAC-valid `(raw_body, hmac)` pairs. An attacker who installs the app on their own tenant can capture a legitimately signed webhook delivery (raw body + `x-shopify-hmac-sha256` header) and replay the exact same bytes to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain`/`shopify-shop-domain` header value (e.g., a victim shop's domain). `HmacValidator.validate` re-computes the HMAC only from `to_signable_string` (the raw body) [5](#0-4) , so the forged request passes validation unchanged, and `Registry.process` dispatches the handler with `shop: request.shop` set to the attacker-chosen victim domain [6](#0-5) .

### Impact Explanation
This breaks the tenant/shop identity binding that host applications rely on when processing `WebhookMetadata#shop` to key data changes, cache invalidation, billing events, or account state per merchant. An attacker with no privileges beyond installing the app on any store (or capturing one delivered webhook) can forge webhook events that appear to originate from an arbitrary victim shop, resulting in cross-tenant data/state corruption in the host application — a Critical, cross-tenant impact per the gem's own trust boundary (the HMAC is meant to authenticate both origin and content of a webhook, but only authenticates content).

### Likelihood Explanation
Likelihood is high for any actor able to install the app at least once (a standard, unprivileged action for public/embedded Shopify apps) and directly POST to the app's public webhook endpoint (which must be internet-reachable by design). No access token, `client_secret`, or privileged credential is required — only a captured, legitimately-signed body/HMAC pair from the attacker's own installation.

### Recommendation
Include the shop domain (and ideally topic) in the signable payload used for webhook HMAC validation, or independently verify that `request.shop` corresponds to a known/installed shop associated with the specific webhook subscription (e.g., cross-check against the webhook subscription owner returned by Shopify, not merely trust the header). At minimum, document that `WebhookMetadata#shop` is unauthenticated header data and must not be trusted for tenant-scoping decisions without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers any webhook (e.g., `orders/create`), capturing the exact `raw_body` and the `x-shopify-hmac-sha256`/`shopify-hmac-sha256` header value delivered to the app's webhook endpoint.
2. Attacker sends a new HTTP POST directly to the same app webhook endpoint with:
   - Body: identical to the captured `raw_body`
   - Header `x-shopify-hmac-sha256`: identical to the captured value
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (attacker-chosen)
   - Header `x-shopify-topic`: unchanged
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the forged header [3](#0-2) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only from `raw_body` and matches the (unmodified) signature, returning `true` [7](#0-6) .
5. The registered handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own store, achieving cross-tenant webhook impersonation [4](#0-3) .
