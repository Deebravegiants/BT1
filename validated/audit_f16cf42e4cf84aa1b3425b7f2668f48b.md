Based on my investigation, I found a valid analog in the `IntentGatewayV2` intents contracts.

### Title
Same-chain partial fill escrow release miscalculates proportional share against the pre-fee input amount, allowing solvers to drain more escrow than remains available - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_fillSameChain` computes the escrow amount to release to a solver on a partial fill using `order.inputs[i].amount`, the value baked into the order's commitment hash. As documented in `IntentsBase.sol`, `OrderPlaced.inputs` is described as "the escrowed input tokens (after protocol fee deduction)" [1](#0-0) , and `IntentGatewayV2Test.sol` confirms the commitment is hashed with the reduced (post-protocol-fee / post-fee-on-transfer) amount, matching what's actually stored in `_orders[commitment][token]` [2](#0-1) . This mirrors the reported bug class: a proportional/ratio-based payout calculation (`growth.accPerShare` style) that assumes the tracked "total" amount equals the actual custodied balance, without accounting for losses/deductions taken before or during custody.

### Finding Description
In `_fillSameChain`, the per-leg escrow release for a partial fill is:

```solidity
escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
``` [3](#0-2) 

This is a pro-rata calculation that trusts `order.inputs[i].amount` (a value supplied by the caller as part of the `order` struct, and which must equal whatever was hashed into the commitment for `fillOrder` to pass its authentication) as the true escrowed balance for that leg. If the token is a fee-on-transfer token, or if a caller can construct/replay an order whose declared `inputs[i].amount` diverges even slightly from the actual amount held in `_orders[commitment][token]` (e.g., due to rounding, prior partial releases, or an implementation change in how the pre-fee vs post-fee amount is committed), every subsequent proportional release computed from this formula is wrong relative to what is really escrowed. `_withdraw`, which performs `escrowed - amount` in `IntentsBase.sol`, will `revert UnknownOrder` once amount checks fail, but not until real value has already leaked, or a legitimate solver is undercompensated. [4](#0-3) 

Contrast this with the full-fill path just above it, which correctly reads the live storage value instead of recomputing from the order struct:
```solidity
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
}
``` [5](#0-4) 

Only the *partial*-fill branch trusts the caller-supplied `order.inputs[i].amount` rather than the ground-truth escrow balance, so any discrepancy between the two is exploitable specifically through repeated partial fills.

### Impact Explanation
An attacker (as either the order placer or a colluding solver) who can cause `order.inputs[i].amount` to diverge from the true `_orders[commitment][token]` balance can drain more input tokens than were actually escrowed for that order across a sequence of partial fills, at the expense of the protocol/other users' escrowed funds, or conversely cause legitimate solvers to receive less than they are entitled to. This is a direct funds-theft/fund-freezing vector reachable by any address that can call `fillOrder` with attacker-chosen `FillOptions`, matching the "Users can claim more fees than the pool actually holds" bug class from the report (proportional payout not reconciled against actual custodied balance).

### Likelihood Explanation
Likelihood depends on whether a real-world path exists to desynchronize `order.inputs[i].amount` from `_orders[commitment][token]` for a token used in partial (same-chain) fills — e.g., fee-on-transfer tokens, upgrade edge cases, or rounding across repeated partial fills of the same leg. Given that the code base already special-cases fee-on-transfer tokens at `placeOrder` time and there is explicit test coverage for rounding dust in `IntentGatewayV2SameChainTest.sol`, this is a plausible and previously-recognized risk area, though I could not fully verify in the given time whether the current `placeOrder` path fully closes every divergence scenario for all token types combined with multiple partial fills.

### Recommendation
In the partial-fill branch of `_fillSameChain`, replace the pro-rata calculation based on `order.inputs[i].amount` with a calculation derived from the live `_orders[commitment][token]` storage balance (e.g., `escrowedAmount = (_orders[commitment][token] * fillAmount) / remaining`, where `remaining` reflects the currently outstanding output requirement), so that every release — partial or full — is bounded by and computed against the actual custodied balance rather than a caller-influenced/commitment-encoded amount.

### Proof of Concept
1. Place a same-chain order with an input token whose escrowed amount ends up smaller than the raw `order.inputs[i].amount` a caller can still supply when calling `fillOrder` (e.g., via a fee-on-transfer input token combined with rounding across multiple partial fills, or a future/alternate encoding path where the "post-fee" invariant does not hold for every leg).
2. Solver calls `fillOrder` multiple times with `outputs[i].amount` sized to trigger the partial-fill branch each time.
3. Each partial fill computes `escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired` using the caller-supplied, pre-desync amount rather than reading `_orders[commitment][token]`.
4. Summed across fills, total input tokens released can exceed the token amount actually held in escrow for that commitment, until `_withdraw`'s `escrowed - amount` underflow-guard (`if (escrowed == 0) revert UnknownOrder()`) triggers only after excess value has already been transferred out on an earlier fill.
