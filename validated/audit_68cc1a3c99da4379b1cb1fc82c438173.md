### Title
Multi-token withdrawal reverts entirely on a single failing transfer, permanently freezing all other escrowed tokens and protocol fees in the order - (File: evm/src/apps/intentsv2/IntentsBase.sol / evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentsBase._withdraw` (and its Tron analog `IntentGatewayV2.withdraw`) settles an order by looping over the order's escrowed `tokens[]` array and transferring each one to the beneficiary, then, if `finalize` is true, also sweeping the accumulated transaction fees to the beneficiary in the same call. Because all of these transfers happen inside one atomic function with no per-token failure isolation, a single reverting/blacklisting token anywhere in the array (or a `TransferFailed`/`InsufficientNativeToken` check on any leg) reverts the whole withdrawal, permanently blocking release of every other (otherwise fine) escrowed token and the protocol fee for that order — the same "one bad reward token blocks all reward token claims" bug class as the original Olympus finding.

### Finding Description
`_withdraw` iterates `body.tokens` and unconditionally uses `safeTransfer`/native `call` for each entry, decrementing `_orders[commitment][token]` before/around the transfer: [1](#0-0) 

If `finalize` is true, it then also sweeps the accumulated `TRANSACTION_FEES` entry to the same beneficiary in the same transaction: [2](#0-1) 

The Tron sibling contract implements the identical pattern, using low-level `.call` with an explicit `TransferFailed()` revert per token, and unconditionally reverting the whole function if any single leg fails: [3](#0-2) 

None of these code paths isolate failures per token: `SafeERC20.safeTransfer` reverts on failure (e.g. a blacklist-capable token like USDC/USDT refusing a sanctioned beneficiary, a paused token, or a fee-on-transfer/hook token that reverts under certain conditions), and the explicit `if (!success) revert TransferFailed();` checks do the same. A single problematic token entry in `body.tokens` therefore aborts the settlement of *all* tokens in the order plus the transaction fees, exactly mirroring the Olympus `claimRewards()` bug where a revert in one reward-token payout blocks the unrelated, otherwise-claimable payout.

This is reachable without any privileged role: `withdraw`/`_withdraw` is invoked from the `onGetResponse`/`onAccept` message-handling path when a relayer delivers the `RedeemEscrow`/`RefundEscrow`/GET-response message for an order (see `IntentGatewayV2.onGetResponse` calling `withdraw(body, true)`): [4](#0-3) 

Any user who creates an order can pick which tokens are escrowed/output for it (multi-token orders), and any solver/relayer that submits the corresponding proof triggers this settlement path.

### Impact Explanation
If any one token in a multi-token order becomes non-transferable to the resolved beneficiary (blacklist, pause, revert-on-condition, or even just running out of gas/edge-case revert in an ERC777-style hook), the entire order's escrow — including all other, perfectly healthy tokens and the accumulated transaction fee — becomes permanently stuck: `withdraw`/`_withdraw` can never complete for that commitment, since `_filled[commitment]` is only set once `withdraw` succeeds. This is a permanent freezing-of-funds condition affecting the intent depositor/solver/beneficiary for that order, satisfying the "concrete... permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment that supports orders with multiple output tokens and where at least one supported token has admin-controlled transfer restrictions (USDC/USDT-style blacklisting is common on EVM chains Hyperbridge targets). No attacker privilege is required beyond normal order creation and the standard relayer flow; an adversarial or unlucky beneficiary/token combination is sufficient to trigger the freeze, and there is no permissioned recovery path shown in this code to redeem the non-blocked tokens separately.

### Recommendation
Isolate token payouts so a failure in one does not block the others:
- Use low-level calls wrapped in try/catch (or a `call`-then-check pattern without `revert`) per token, and on failure credit the beneficiary's amount to a per-user/per-token "owed" mapping that can be claimed later instead of aborting the whole settlement.
- Decouple the transaction-fee sweep from the escrowed-token transfer loop so a failing escrow-token transfer does not also block fee release, and vice versa.
- Still mark the order `_filled`/finalized based on escrow debits succeeding logically, independent of whether every transfer physically completed, so retried/queued withdrawal of the stuck token doesn't re-open the order.

### Proof of Concept
1. A user creates an order whose output/escrow token list includes token `A` (a normal ERC20) and token `B` (a USDC-like token with blacklist capability).
2. The beneficiary address gets blacklisted on token `B` after order creation but before settlement (or is blacklisted from the start due to sanction lists).
3. A relayer submits the fill/redeem proof, triggering `onGetResponse` → `withdraw(body, true)` (or `onAccept` → `_withdraw`).
4. The loop reaches token `B`; `IERC20(B).transfer(beneficiary, amount)` reverts (blacklisted) or `call` returns `success=false`, causing `revert TransferFailed()` / bubbling the `SafeERC20` revert.
5. The entire `withdraw`/`_withdraw` call reverts: token `A`'s legitimate, unblocked transfer never happens, `_orders[commitment][A]` is never decremented, `_filled[commitment]` is never set, and the accumulated transaction fee is never paid — all funds for the order are permanently stuck since every future retry hits the same revert on token `B`.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
