### Title
Predictable, unauthenticated `SessionCookie` value used as the session-store lookup key enables session fixation for non-embedded apps - (File: `lib/shopify_api/auth/oauth.rb`, `lib/shopify_api/utils/session_utils.rb`)

### Summary
For non-embedded apps, `ShopifyAPI::Auth::Oauth.validate_auth_callback` issues a browser cookie whose value is the raw, predictable `Session#id` (`"offline_#{shop}"` or `"#{shop}_#{associated_user.id}"`), and `ShopifyAPI::Utils::SessionUtils.cookie_session_id` later trusts that exact cookie value as the primary key to look up the merchant's stored (access-token-bearing) session, with no cryptographic binding between the cookie and the browser/session it was issued to.

### Finding Description
The invariant the library should guarantee is: *the session id used to fetch a merchant's access-token session must be bound to a value only the authenticated party could present* (an equality like `cookie_value == HMAC_or_secret_derived_binding(session)`). Instead:

- `Session#id` for offline sessions is `"offline_#{shop}"` [1](#0-0) , and for online sessions is `"#{shop}_#{associated_user.id}"` [2](#0-1)  — both fully derivable from public information (the shop's `myshopify.com` domain, and for online sessions the numeric user id which is often enumerable/observable).
- `validate_auth_callback` sets this exact predictable value as the plaintext cookie for non-embedded apps: `SessionCookie.new(value: session.id, expires: ...)` [3](#0-2) .
- Later, on every subsequent request, `SessionUtils.current_session_id` for non-embedded apps reads that cookie value directly with zero verification and returns it as the session id to fetch from storage: `cookie_session_id(cookies)` just returns `cookies[SESSION_COOKIE_NAME]` [4](#0-3) [5](#0-4) .

Unlike the OAuth callback (`AuthQuery`), the JWT session token (`JwtPayload`), and webhook requests, which all carry an HMAC/JWT signature computed with `Context.api_secret_key` that binds the payload to Shopify [6](#0-5) [7](#0-6) , the non-embedded session cookie value carries **no such binding at all**. It is a bare, guessable string acting as the authoritative identity key for a stored, access-token-bearing session. This is the exact "session id derived from unauthenticated bytes" pattern: the equality the gem implicitly assumes — `cookie.value == the id that only the legitimately-authenticated browser could hold` — is false, because `cookie.value` is fully reconstructable by anyone who knows the target shop's domain.

### Impact Explanation
Any unprivileged party who knows (or guesses) a target merchant's `myshopify.com` domain — public information, often equal to the shop's own storefront hostname — can construct the exact session id `"offline_#{shop}"` and set it as their own session cookie against a host application built with this gem. If the host app's storage backend uses `Session#id` as the storage key (which is the documented and intended usage pattern of this gem, since `SessionUtils` derives and returns exactly that key from the cookie for lookup), the attacker's request will resolve to the victim shop's real session object, including its `access_token`. This is a session fixation / cross-tenant session hijack that requires no access token, no `api_secret_key`, and no privileged access — only knowledge of a shop's domain name, satisfying the "session fixation" High-impact category.

### Likelihood Explanation
Likelihood is high for the offline-session case: the predictable id format `"offline_#{shop}"` is fixed and documented behavior of `Session.from` / `SessionUtils.offline_session_id`, requiring no guesswork beyond the public shop domain. It is somewhat lower for online sessions since it also requires the numeric `associated_user.id`, which is not always public but is frequently enumerable (sequential Shopify staff account ids, or observable in other contexts). This applies specifically to non-embedded apps using cookie-based sessions per the library's own flow (`Context.embedded?` false branch) [8](#0-7) .

### Recommendation
Do not use a value derivable purely from public shop/user identifiers as the session cookie value or storage key for non-embedded apps. Instead, generate an unguessable, high-entropy session cookie value (e.g., `SecureRandom.uuid`, which the library already generates for `Session#id` when no `id:` is passed in the generic constructor path [9](#0-8) ) and map that opaque value to the real `Session#id` server-side, or HMAC-sign the cookie value with `Context.api_secret_key` and verify the signature in `cookie_session_id` before trusting it.

### Proof of Concept
1. Attacker learns/guesses the victim merchant's shop domain, e.g., `victim-shop.myshopify.com` (public — appears in the shop's own storefront URL).
2. Attacker computes the predictable offline session id: `"offline_victim-shop.myshopify.com"` per `SessionUtils.offline_session_id` / `Session.from` [10](#0-9) .
3. Attacker sends a request to the host application (built on this gem, non-embedded mode) with a cookie `shopify_session_id=offline_victim-shop.myshopify.com`.
4. `SessionUtils.current_session_id` returns this raw, unverified value [11](#0-10) , the host app looks up the corresponding stored session (containing the victim's real access token), and the attacker's request is now serviced using the victim shop's credentials — a full cross-tenant session takeover with no secret, token, or privileged access required.
