### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop` (tenant) value the gem hands to the application's webhook handler is read from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the signed material. This breaks the identity binding `HMAC-authenticated-bytes == bytes-the-shop-is-derived-from`, allowing the shop attribution of an otherwise validly-signed webhook payload to be forged.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

`#shop`, however, is pulled from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely outside the signed payload: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` (body only) and `hmac` (also derived from a header, but at least matched against the body-derived signature). Once validation "succeeds," the gem constructs `WebhookMetadata` using the *unauthenticated* `request.shop` value and hands it straight to the application handler as the trusted tenant identifier: [3](#0-2) 

Because `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) only ever checks `verifiable_query.to_signable_string` against `verifiable_query.hmac`, and `to_signable_string` for webhooks is `@raw_body` alone, the `shop-domain` header can be swapped for any value without invalidating the signature. The equality that should hold — `shop-domain header == shop bound inside the HMAC-covered bytes` — does not hold; the header is fully attacker-controllable independent of the signature check.

Since all shops installed on a given app share the same signing secret (`Context.api_secret_key`), any body+HMAC pair that was legitimately produced by Shopify for one tenant (e.g. for an attacker's own shop, or one captured via a webhook delivery the attacker controls) remains "valid" when replayed with the `shop-domain` header rewritten to name a different, victim shop.

### Impact Explanation
This is a cross-tenant identity-binding failure: the gem's own authentication primitive (`HmacValidator.validate`) reports success for a request whose declared tenant (`shop`) was never actually authenticated. Any application that trusts `WebhookMetadata#shop` returned by `Registry.process` (which is the documented/intended way to consume webhook data from this gem) can be made to process attacker-supplied data under another merchant's identity — i.e., cross-tenant access/data injection, one of the explicitly listed critical impacts.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one validly-signed (body, HMAC) pair — trivially obtainable by any merchant who has the app installed on their own store (Shopify will legitimately sign and deliver webhooks for their own shop's events, and the callback URL for HTTP-delivery webhooks can, in Shopify's model, be redirected to an attacker-observable endpoint). The attacker then only needs to replay that same body/HMAC to the app's real webhook endpoint while altering the `shop-domain` header. No knowledge of `api_secret_key` is required, only the ability to make an HTTP request with attacker-chosen headers — squarely within the "unprivileged internet user" analog class.

### Recommendation
Bind the shop identity into the authenticated material, or otherwise cryptographically verify that the `shop-domain` header matches a shop the gem/application independently trusts (e.g., only accept `request.shop` values for shops that have a valid, existing session/installation, and prefer deriving tenant identity from data that is itself covered by the signature, such as embedding the shop in the signable string, or requiring the caller to separately confirm the shop is a known, previously-installed shop before trusting `WebhookMetadata#shop`). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as the sole tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and captures a legitimately Shopify-signed webhook delivery, e.g.:
   - Headers: `X-Shopify-Hmac-Sha256: <valid-hmac>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`
   - Body: `{"id": 1, ...attacker-crafted order fields...}`
2. Attacker resends the exact same body and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only (`lib/shopify_api/webhooks/request.rb:35-38`) — validation succeeds because the body is unchanged.
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), and the application's handler processes attacker-controlled data as if it originated from the victim's shop.
