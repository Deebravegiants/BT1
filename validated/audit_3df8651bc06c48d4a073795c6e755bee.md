### Title
Borrow-index accrual overflows before its cap and permanently freezes a large high-utilization market - (File: contracts/pool/src/interest.rs)

### Summary
A market whose scaled debt multiplied by the borrow index exceeds `i128::MAX` panics during `scaled_to_original` while accrual is running, before the configured `MAX_BORROW_INDEX_RAY` cap can stop index growth. Because every controller market operation calls the pool’s accrual path first, the same panic then blocks withdrawals, repayments, liquidations, bad-debt cleanup, parameter updates, and further index updates for that market. The result is permanent freezing of supplier funds and protocol operations absent a contract upgrade.

### Finding Description
`LiquidityPool::update_indexes` calls `ops::market::accrue`, which loads each requested market and invokes `interest::global_sync`. [1](#0-0) [2](#0-1)  `global_sync` splits elapsed time into bounded chunks and calls `accrue_chunk` for each interval. [3](#0-2)  Each chunk computes the next indexes and revenue through `accrue_step`, then writes them into the cache. [4](#0-3) 

The accrual path evaluates the current scaled balances against their indexes using `scaled_to_original`; the same helper is used for utilization through both borrowed and supplied values. [5](#0-4)  For an 18-decimal market holding a one-billion-token principal at 98% utilization, the repository’s own harness demonstrates that the RAY value reaches the `i128` ceiling before `borrow_index` reaches `MAX_BORROW_INDEX_RAY`. [6](#0-5)  The resulting checked-arithmetic panic is reachable through the permissionless `Controller::update_indexes(caller, assets)` path after ordinary `supply` and `borrow` calls create the required market state. [7](#0-6) 

### Impact Explanation
Once the value ceiling is crossed, the panic occurs inside the mandatory pre-operation accrual, so the market cannot transition to a lower-debt state. The harness explicitly verifies that subsequent `update_indexes`, `withdraw`, and `repay` all fail with `MathOverflow`. [8](#0-7)  Liquidation, bad-debt cleanup, revenue claims, recapitalization, and rate-model replacement also load or renew the market through the same accrual-first flow, so they cannot recover the market after the overflow. [9](#0-8) [10](#0-9) 

This permanently freezes supplier balances, outstanding borrower positions, and market operations because the state cannot advance and no allowed unprivileged action can bypass accrual. The index ceiling intended to bound growth never engages because the absolute RAY value overflows first. [11](#0-10) 

### Likelihood Explanation
The trigger does not require privileged access, malformed parameters, leaked keys, or control of an external service. An unprivileged user can invoke `supply`, `borrow`, and later `update_indexes`; `update_indexes` only requires caller authorization before forwarding the requested `HubAssetKey` list to the pool. [12](#0-11) [7](#0-6) 

The practical barrier is capital and market duration: the demonstrated configuration uses a billion 18-decimal-token supply with 98% borrowed and sustained high-utilization rate parameters. [13](#0-12)  Those requirements reduce likelihood for low-value markets, but they are reachable with a sufficiently valuable listed asset or a whale attacker, and the failure only requires the market to remain at the steep part of its configured curve long enough for the RAY value—not the index itself—to exceed `i128::MAX`. [14](#0-13) 

### Recommendation
Bound the absolute RAY value and enforce the borrow-index cap before evaluating `scaled_to_original` during accrual. In `common::rates::accrue_step` and its callers, compare intermediate products using widened `I256` arithmetic or precompute a safe per-market bound such as `floor(i128::MAX / borrow_index)` for scaled debt and `floor(i128::MAX / supply_index)` for scaled supply.

Once either bound is reached, clamp the index or reject further debt growth with a recoverable error while still allowing repayments, liquidations, withdrawals, parameter updates, and bad-debt cleanup to bypass or safely continue accrual. The `MAX_BORROW_INDEX_RAY` check should execute before any operation that can overflow on `scaled * index`, rather than after interest has been simulated. Add a regression test matching the existing whale-market scenario and assert that repayments and withdrawals remain executable after the cap engages. [4](#0-3) [15](#0-14) 

### Proof of Concept
1. Configure an 18-decimal market with the harness’s steep XLM rate curve, disabled utilization limit, and caps raised enough to admit a one-billion-token market. [16](#0-15) 
2. Call `Controller::supply(caller, account_id, spoke_id, [(BIG18_key, 1_000_000_000 * 10^18)])` from an account holding that balance. [17](#0-16) 
3. Supply sufficient collateral and call `Controller::borrow(caller, account_id, [(BIG18_key, 980_000_000 * 10^18)], to)` to establish approximately 98% utilization. [18](#0-17) [19](#0-18) 
4. Advance ledger time and repeatedly call `Controller::update_indexes(caller, vec![BIG18_key])`; the controller forwards the market to `pool_update_indexes_call`, which invokes the pool’s `update_indexes`. [7](#0-6) [20](#0-19) 
5. `update_indexes` calls `interest::global_sync`, which runs `accrue_step` in bounded chunks. [1](#0-0) [3](#0-2) 
6. When `borrowed_scaled_ray * borrow_index` exceeds `i128::MAX`, accrual panics with `MathOverflow` even though `borrow_index < MAX_BORROW_INDEX_RAY`. [14](#0-13) 
7. Subsequent `withdraw` and `repay` calls revert with the same `MathOverflow` because they accrue the market before mutating positions, leaving supplier funds and debt positions frozen. [21](#0-20)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```

fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
