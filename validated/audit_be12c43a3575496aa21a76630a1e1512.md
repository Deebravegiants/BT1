### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so `Utils::HmacValidator.validate` only proves that the *body bytes* were signed with the app's `client_secret`; it never binds the `X-Shopify-Shop-Domain` header to that signature. `Webhooks::Registry.process` uses this HMAC check as the sole authenticity gate, then passes the unauthenticated `request.shop` value straight into `WebhookMetadata` for the handler to trust as the tenant identifier.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are computed purely from the raw body [3](#0-2) . `Request#shop` simply reads the `shopify-shop-domain` / `x-shopify-shop-domain` header verbatim, with no cryptographic relationship to the HMAC at all [4](#0-3) .

`Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., body vs. HMAC) and then immediately builds `WebhookMetadata` using `request.shop` as the shop identity handed to the app's handler: [5](#0-4) .

This breaks the intended identity binding: `hmac_verified_shop == header_shop` is assumed but never enforced — the equality that should hold is `shop bound to signed bytes == shop delivered to handler`, but the gem only checks `signed(body) == hmac`, not `signed(body, shop) == hmac`. Because the same app `client_secret` is shared across all shops that install the app, any attacker who can obtain one valid `(body, hmac)` pair for their own tenant (e.g., by installing the app on their own development/trial store, which is unprivileged and requires no special access) can replay that exact body and HMAC to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value naming a different, victim merchant. `HmacValidator.validate` will report success (the body/HMAC pair is genuinely valid for the app's secret), and `Registry.process` will dispatch to the handler with `data.shop` set to the attacker-chosen victim shop domain.

### Impact Explanation
Per the gem's own documentation, `data.shop` is the field host applications are told to trust as "The shop domain of the webhook" [2](#0-1) , and `Registry.process` is documented as verifying "the request did indeed come from Shopify" [1](#0-0) . Because the shop identity is not bound to the HMAC, any host application that uses `data.shop` to select which merchant's session/access token/records to act on (the documented and expected usage pattern) can be induced to attribute one shop's webhook payload to a different shop, resulting in cross-tenant data confusion/access — writing, invalidating, or acting on another merchant's data using an attacker-controlled payload.

### Likelihood Explanation
The only prerequisite is the ability to install the target app on any shop (including a free/trial development store) to obtain one legitimately-signed `(body, hmac)` pair, and the ability to POST directly to the app's public webhook endpoint with a forged shop-domain header — both are actions available to an unprivileged internet user with no access to the victim's credentials, `api_secret_key`, or access tokens.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed payload verification, or otherwise cryptographically bind `request.shop` to the validated body before it is trusted, e.g. by making `to_signable_string` incorporate the shop header, or by requiring the handler layer to independently verify that `request.shop` corresponds to a shop with an active, previously-established session/registration before acting on the payload.

### Proof of Concept
1. Attacker installs the target Shopify app onto their own store `attacker.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Shopify delivers a webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)` — valid per `HmacValidator.validate_signature` [6](#0-5) .
3. Attacker captures `(B, H)` and replays it directly to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed; `request.hmac` and `request.to_signable_string` are unaffected by the forged shop header.
5. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H` [5](#0-4) .
6. The registered handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host application to process attacker-controlled data under the victim's tenant identity.
