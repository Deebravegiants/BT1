This confirms the vulnerability: the webhook `shop` field is read from an unauthenticated header and is never included in the HMAC-signed bytes, yet the documented flow (`docs/usage/webhooks.md`) directs host apps to trust `data.shop` for per-tenant routing/attribution.

### Title
Webhook `shop` identity is not bound by the HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the HMAC-signed bytes exclusively from the raw request body via `to_signable_string`, while `shop` (and `topic`, `webhook_id`, `api_version`) are read directly from HTTP headers that are never part of the signed payload. `ShopifyAPI::Webhooks::Registry.process` only validates the HMAC of the body and then forwards `request.shop` — an unauthenticated header value — straight into `WebhookMetadata` handed to the host application's handler. [1](#0-0) [2](#0-1) 

### Finding Description
This mirrors the M-3 bug class exactly: a field that is *acted upon* (here, the `shop` used to attribute/route the webhook to a merchant tenant) is not covered by the cryptographic check that is supposed to bind the whole message together. `HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`, and for `Request` that string is just `@raw_body`: [3](#0-2) [4](#0-3) 

The equality that should hold is: `shop bound in HMAC == shop used to attribute the webhook`. Instead the code enforces only `HMAC(secret, body) == received_hmac`, and separately trusts `shop = header["x-shopify-shop-domain"]` with no cryptographic tie between the two. Since every installation of a given app shares the same `api_secret_key` (`Context.api_secret_key` is a single app-level secret, not a per-shop secret), any merchant that has legitimately installed the app can capture a valid `(raw_body, hmac)` pair from their own real webhook deliveries, then replay that exact body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` will still return `true` because it never looks at the shop header, and `Registry.process` will call the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain: [5](#0-4) 

The documented handler contract explicitly tells host apps to key their per-tenant logic off `data.shop`: [6](#0-5) 

so this is not "the host app ignoring documented behavior" — it is the gem's documented API steering integrators into trusting an unauthenticated value as the tenant identity.

### Impact Explanation
This breaks the tenant-isolation guarantee that webhook processing is supposed to provide: an app cannot distinguish "this body was really pushed by Shopify for shop A" from "this body was replayed by shop A's own operator while claiming to be shop B." Any host application that uses `data.shop` to look up per-merchant records, apply per-shop business logic, or write into a per-tenant data store (exactly as the docs instruct) can have data attributed to, or state mutated for, a shop the attacker does not control — a cross-tenant access primitive achievable by any unprivileged merchant who has installed the app once.

### Likelihood Explanation
Any developer/merchant who has installed the app can capture one legitimate webhook delivery (body + `x-shopify-hmac-sha256`) from their own store — no special privilege or secret access is required — and then POST that exact body/HMAC pair to the victim app's public webhook endpoint with a forged `x-shopify-shop-domain` header. No `api_secret_key`, access token, or Shopify-side compromise is needed; this only requires standard HTTP access to the app's public webhook route.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values in the bytes that are HMAC-verified, or otherwise cryptographically bind the shop domain to the payload before trusting it (e.g., compute the signature over `shop-domain header + raw_body`, or independently verify the shop's known secret/session before acting on `request.shop`). At minimum, update `Request#to_signable_string` so `HmacValidator.validate` fails whenever the shop-domain header has been altered relative to what was actually signed by Shopify.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify deliver a real webhook (e.g. `orders/create`) to the app's registered callback URL. Attacker captures the raw request: `raw_body` and header `x-shopify-hmac-sha256`.
2. Attacker sends a new HTTP request to the same app endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. Server calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body:, headers:))`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, raw_body)` — identical to step 1 — and returns `true`, since `shop` is never part of `to_signable_string`.
5. The handler receives `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker's own order data>, ...)` and, following the documented pattern, processes/stores it as data belonging to `victim.myshopify.com`.
