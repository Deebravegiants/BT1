### Title
Block-level accounts-data-size throttle (`MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`) is bypassable via CPI-driven `SystemInstruction::CreateAccount`/`Allocate` because `CostModel::calculate_allocated_accounts_data_size` only scans top-level instructions - (`cost-model/src/cost_model.rs`)

### Summary
`CostModel::calculate_allocated_accounts_data_size` is fed only `transaction.program_instructions_iter()`, i.e. the transaction's top-level compiled instructions, and only recognizes allocations when the top-level `program_id` equals `system_program::id()`. A transaction whose sole top-level instruction invokes an attacker-controlled BPF program that internally CPIs into the System Program to `CreateAccount`/`Allocate` is scored with `allocated_accounts_data_size == 0`, both at admission time (`calculate_cost`) and after execution (`calculate_cost_for_executed_transaction`), while the real accounts-data growth is correctly tracked by the bank via `accounts_resize_delta`/`accounts_data_size_delta_on_chain`.

### Finding Description
`CostModel::calculate_allocated_accounts_data_size` iterates `instructions: impl Iterator<Item = (&Pubkey, SVMInstruction)>` and for each instruction calls `calculate_account_data_size_on_instruction`, which only recognizes an allocation if `program_id == &system_program::id()` for that *top-level* instruction: [1](#0-0) 

Both the pre-execution estimate (`calculate_cost`) and the post-execution "actual" cost recomputation (`calculate_cost_for_executed_transaction`) call `calculate_transaction_cost` with `transaction.program_instructions_iter()` — i.e. still only the top-level instructions, never the CPI instruction trace: [2](#0-1) [3](#0-2) 

So if the top-level instruction's `program_id` is an attacker-deployed BPF program (not `system_program::id()`), `calculate_account_data_size_on_instruction` returns `SystemProgramAccountAllocation::None` regardless of what that program does internally via CPI: [4](#0-3) 

This `allocated_accounts_data_size` value is exactly what `CostTracker::would_fit`/`add_transaction_cost` use to enforce the block-wide `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` (100 MB) budget via `CostTrackerLimits::allocated_data_size`: [5](#0-4) [6](#0-5) [7](#0-6) 

Meanwhile, the *actual* accounts-data growth from CPI'd allocations is correctly measured by the runtime and folded into the bank's accounts data size accounting (`accounts_resize_delta` → `accounts_data_size_delta_on_chain`), completely independent of the cost tracker's `allocated_accounts_data_size`: [8](#0-7) 

The only per-transaction guard against unbounded CPI allocation growth is `TransactionAccounts::can_data_be_resized`, which caps growth per transaction against `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` regardless of call depth (top-level or CPI): [9](#0-8) 

That per-transaction cap prevents a *single* transaction from allocating unboundedly, but it does **not** feed back into `CostTracker::allocated_accounts_data_size`, which is the mechanism that is supposed to cap the *aggregate* per-block accounts-data growth at `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`. Because the cost model records `0` for any CPI-driven allocation, an attacker can submit many transactions, each invoking a program that CPIs `CreateAccount`/`Allocate` up to the per-transaction cap, and the `CostTracker` will admit far more of them into a single block than the `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` (100 MB) limit is intended to allow, since each transaction is scored with `allocated_accounts_data_size = 0`.

The unit tests in `cost_model.rs` only cover top-level `SystemInstruction` cases (`test_calculate_allocated_accounts_data_size_*`), confirming the scanner was never designed to look through CPI: [10](#0-9) 

### Impact Explanation
This is a materially underpriced-execution / cost-model-bypass bug (Agave bounty category: "Underpriced compute-budget/cost-model/fee accounting" / DoS via resource exhaustion). The scoped invariant — "declared/estimated compute and account-load costs must upper-bound real work" — is violated specifically for accounts-data allocation cost: `CostTracker`'s `allocated_accounts_data_size` bookkeeping can be driven arbitrarily far below the real, bank-tracked accounts-data growth for a block. This allows a leader (or an attacker flooding a leader's mempool) to pack a block with far more real account-data growth than `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` (100 MB) was designed to permit, undermining the resource-exhaustion protection that limit exists for (excess account-data growth increases replay/snapshot/validator memory & I/O load cluster-wide). It does not cause double-settlement or fund loss, but it is a genuine underpriced-cost/DoS-adjacent accounting bug reachable by an unprivileged transaction submitter with no special privileges — only the ability to deploy and invoke an ordinary BPF program.

### Likelihood Explanation
- Fully reachable by an unprivileged user: deploy any BPF program that CPIs into the System Program's `CreateAccount`/`Allocate`, then submit transactions invoking it as the sole top-level instruction.
- No special validator/leader/staked privileges are needed.
- Repeatable per transaction, bounded only by `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` per transaction, but unbounded in aggregate across the many transactions in a block since the block-wide cost-tracker check always sees `allocated_accounts_data_size = 0` for these transactions.
- This is a purely code-path/logic issue, not requiring races, timing, or exotic preconditions — it is deterministic.

### Recommendation
`calculate_allocated_accounts_data_size` (or its callers) should not rely solely on statically scanning top-level instructions when computing the *actual* cost after execution. For `calculate_cost_for_executed_transaction`, the real `accounts_resize_delta` (already computed by the runtime and available in `TransactionExecutionDetails`/`LoadedTransaction`) should be threaded through and used to populate `TransactionCost::allocated_accounts_data_size` for actual-cost accounting, instead of re-invoking the static top-level-only estimator. For pre-execution estimation (before CPI depth is known), the current static heuristic is inherently conservative-only for top-level System Program calls; consider either (a) tracking real CPI-derived allocation growth in `CostTracker::add_transaction_cost` using post-execution data (fixing the "actual" path is the priority, since the estimate is inherently approximate pre-execution), or (b) enforcing `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` directly against the bank's `accounts_data_size_delta_on_chain` counter as an additional/authoritative gate at block-commit time, independent of the cost-tracker's static estimate.

    fn calculate_allocated_accounts_data_size<'a>(
        instructions: impl Iterator<Item = (&'a Pubkey, SVMInstruction<'a>)>,
        feature_set: &FeatureSet,
    ) -> u64 {
        let mut tx_attempted_allocation_size = Saturating(0u64);
        for (program_id, instruction) in instructions {
            match Self::calculate_account_data_size_on_instruction(
                program_id,
                instruction,
                feature_set,
            ) {
                SystemProgramAccountAllocation::Failed => {
                    // If any system program instructions can be statically
                    // determined to fail, no allocations will actually be
                    // persisted by the transaction. So return 0 here so that no
                    // account allocation budget is used for this failed
                    // transaction.
                    return 0;
                }
                SystemProgramAccountAllocation::None => continue,
                SystemProgramAccountAllocation::Some(ix_attempted_allocation_size) => {
                    tx_attempted_allocation_size += ix_attempted_allocation_size;
                }
            }
        }

        // The runtime prevents transactions from allocating too much account
        // data so clamp the attempted allocation size to the max amount.
        //
        // Note that if there are any custom bpf instructions in the transaction
        // it's tricky to know whether a newly allocated account will be freed
        // or not during an intermediate instruction in the transaction so we
        // shouldn't assume that a large sum of allocations will necessarily
        // lead to transaction failure.
        (MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION as u64)
            .min(tx_attempted_allocation_size.0)
    }

    fn would_fit(
        &self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
    ) -> Result<(), CostTrackerError> {
        let cost: u64 = tx_cost.sum();

        if self.block_cost().saturating_add(cost) > self.limits.block_cost {
            // check against the total package cost
            return Err(CostTrackerError::WouldExceedBlockMaxLimit);
        }

        // check if the transaction itself is more costly than the account_cost_limit
        if cost > self.limits.account_cost {
            return Err(CostTrackerError::WouldExceedAccountMaxLimit);
        }

        let allocated_accounts_data_size =
            self.allocated_accounts_data_size + Saturating(tx_cost.allocated_accounts_data_size());

        if allocated_accounts_data_size.0 > self.limits.allocated_data_size {
            return Err(CostTrackerError::WouldExceedAccountDataBlockLimit);

    pub(crate) fn update_accounts_resize_delta(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        let accounts_resize_delta = self.resize_delta.get();
        self.resize_delta.set(
            accounts_resize_delta.saturating_add((new_len as i64).saturating_sub(old_len as i64)),
        );
        Ok(())
    }

    pub(crate) fn can_data_be_resized(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        // The new length can not exceed the maximum permitted length
        if new_len > MAX_ACCOUNT_DATA_LEN as usize {
            return Err(InstructionError::InvalidRealloc);
        }
        // The resize can not exceed the per-transaction maximum
        let length_delta = (new_len as i64).saturating_sub(old_len as i64);
        if self.resize_delta.get().saturating_add(length_delta)
            > MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION
        {
            return Err(InstructionError::MaxAccountsDataAllocationsExceeded);
        }
        Ok(())
    }
