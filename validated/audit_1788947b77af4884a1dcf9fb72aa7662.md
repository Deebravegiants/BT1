### Title
Silent asset-scope widening via `add()` merge lets a previously-trusted origin gain addresses for assets never explicitly approved - (File: features/connected-origins/module/connections.js)

### Summary
`ConnectedOrigins#add` merges new call parameters into an existing trusted connection via `#setAttributes`, using `trusted ?? value.trusted` and unconditionally unioning `assetNames` (`allConnectedAssetNames`) with the previously stored ones. A second `add()` call that omits `trusted` (preserving `trusted:true`) but supplies new `assetNames` therefore expands the address-exposure scope of `getConnectedAccounts` without any new explicit consent for those assets.

### Finding Description
`add()` computes `allConnectedAssetNames` as the union of the incoming `assetNames`/`connectedAssetName` and the origin's previously stored `value.assetNames` [1](#0-0) , then calls `#setAttributes` with `trusted: trusted ?? value.trusted` and `assetNames: [...allConnectedAssetNames]` [2](#0-1) . Because `trusted` defaults to the prior value when omitted, and `assetNames` is always widened (never intersected or gated on a fresh trust confirmation), a follow-up `add({origin, assetNames:[...]})` call silently grows the asset scope of an already-trusted origin. `getConnectedAccounts` then uses exactly this `value.assetNames` (plus `connectedAssetName`) to `pick` which addresses to return for every enabled wallet account [3](#0-2) , so the newly-added assets' addresses are returned even though no new explicit trust grant occurred for them. This is directly demonstrated by the existing test `updates accounts when new assets added`, where a second, trust-omitted `add()` call adds `ethereum` to a connection originally trusted only for `solana` [4](#0-3) .

Note: the `walletAccount` field described in the question is not actually consulted by `getConnectedAccounts` at all — the function iterates over every entry in `#connectedAccountsAtom` (i.e., all enabled wallet accounts) regardless of the connection's `walletAccount` value [5](#0-4) . This is pre-existing behavior present from the very first `add()` call (test `trust new origin` already returns both `exodus_0` and `exodus_1` after a single trusted add) [6](#0-5) , so the "wallet account" widening scenario in the question is not caused by the merge bug — `walletAccount` is effectively unused for scoping purposes in `getConnectedAccounts`. The real, code-supported issue is the **asset-scope** widening via merge, not a wallet-account scope escape.

I was unable to locate, within the indexed portion of this repo, the caller/RPC boundary that invokes `connectedOrigins.add` on behalf of an actual dapp request (only test callers were found), so I cannot confirm from this codebase alone whether a per-call user-facing confirmation gate exists upstream before `add()` is invoked with attacker/dapp-supplied `assetNames`. `connectedOriginsDefinition` is marked `public: true` [7](#0-6) , consistent with being exposed as a callable API, but the exact gating layer is outside what I could verify here.

### Impact Explanation
If `add()` can be invoked again for an already-trusted origin with an expanded `assetNames` set (e.g., a dapp requesting access to more assets after initial connection) without a fresh explicit trust confirmation for those new assets, `getConnectedAccounts` will return addresses for assets the user never explicitly approved for that origin. This breaks the "consent is explicit and scoped" invariant and is a real address-provider isolation violation for asset scope, though not for wallet-account scope (which was already always fully exposed by design).

### Likelihood Explanation
Preconditions: an origin must already be trusted via one prior `add({trusted:true, ...})` call. The subsequent `add()` call only needs to omit `trusted` (or pass nothing) while supplying additional `assetNames`; this is fully reachable purely through repeated calls to the public `add` API and is deterministically reproducible per the existing unit test `updates accounts when new assets added` [4](#0-3) .

### Recommendation
Require an explicit, freshly-confirmed `assetNames`/asset-scope parameter (not silently unioned with prior state) whenever `add()` is called for an already-trusted origin, or require re-confirmation (e.g., a UI approval step) any time the effective asset scope for a trusted origin grows. Do not default-merge `assetNames` growth under an implicit `trusted ?? value.trusted` carry-over; instead, gate scope expansion behind the same trust-granting confirmation path used for the initial `add()` call.

### Proof of Concept
Unit test (extends existing `features/connected-origins/module/__tests__/connections.test.js`):
1. `connectedOrigins.add({origin:'exodus.com', connectedAssetName:'solana', assetNames:['solana'], trusted:true})`.
2. `connectedOrigins.add({origin:'exodus.com', assetNames:['solana','ethereum']})` (no `trusted` field).
3. `const accounts = await connectedOrigins.getConnectedAccounts({origin:'exodus.com'})`.
4. Assert: `accounts` addresses must NOT include an `ethereum` address, since `ethereum` was never part of an explicit trust-granting call — expected behavior is that step 3 returns only `{solana: ...}` per account, but current code returns both `solana` and `ethereum`, demonstrating the silent scope widening.

  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
