## Finding

### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw body only, while the `shop` (and `topic`/`webhook-id`) values used by the registry and forwarded to the app's handler are taken directly from unauthenticated HTTP headers. Because the HMAC secret (`Context.api_secret_key`) is shared across every shop that has installed the app, any tenant that receives a legitimately signed webhook can replay that exact `(body, hmac)` pair against the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to impersonate a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic binding to the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` verifies only `request.to_signable_string` (the raw body) against `request.hmac`, using the single, app-wide `Context.api_secret_key`: [3](#0-2) 

`Webhooks::Registry.process` accepts the request once that body-only HMAC check passes, and then hands the handler a `WebhookMetadata` built directly from the unauthenticated `request.shop` header, with no cross-check against the signed body: [4](#0-3) 

The broken identity binding is: `hmac_valid(body, secret) == true` should imply `shop == the tenant that body actually belongs to`, but the library only proves `hmac_valid(body, secret) == true`; it never proves `shop` is bound to that body. Since `secret` (`Context.api_secret_key`) is the same value for every shop using the app (not per-shop), any tenant who is a legitimate app installer receives real, validly-signed webhooks for their own shop and can capture a `(body, hmac)` pair from one of them. They can then send that identical body/HMAC pair to the app's webhook endpoint again, but with the `shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` will still return `true` (it never looks at the shop header), so `Registry.process` will dispatch the handler with `WebhookMetadata#shop` set to the victim's domain while the body content actually belongs to the attacker's own shop.

### Impact Explanation
Any application built on this gem that uses the `shop` field of `WebhookMetadata` to select which tenant's record to read/write (the standard and documented pattern, e.g. "look up the order/customer belonging to `data.shop`") can be tricked into associating attacker-supplied webhook content with an arbitrary victim shop. This is a cross-tenant integrity/confidentiality violation reachable by any unprivileged party who can install the app on their own store (the normal, unprivileged entry point for a public app) — no access token, `client_secret`, or leaked credential is required, only observation of one's own legitimately delivered webhook.

### Likelihood Explanation
High. Any merchant who installs a public app automatically receives real webhook deliveries with valid HMACs signed with the app's single shared secret. Capturing and replaying an HTTP POST with a modified `shop-domain` header is trivial and requires no special access.

### Recommendation
Bind the shop identity to the signed payload, e.g. by including `shop`/`topic`/`webhook-id` in `to_signable_string` (matching what Shopify itself signs), or by cross-validating the shop header against a shop-specific expectation (e.g., comparing to the session/shop the webhook subscription was registered for) before dispatching to the handler. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (a normal, unprivileged installation).
2. Attacker triggers/receives any real webhook, e.g. `orders/create`, capturing the raw request body `B` and the `X-Shopify-Hmac-Sha256` header `H` (valid because it's signed with the app's single, shared `api_secret_key`).
3. Attacker POSTs to the app's webhook endpoint again with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` in [3](#0-2)  returns `true` because it only checks the body against the shared secret.
5. `Webhooks::Registry.process` in [4](#0-3)  dispatches the handler with `shop: "victim.myshopify.com"` and the attacker's own order body, causing the app to process attacker-controlled data as if it belonged to the victim tenant.
