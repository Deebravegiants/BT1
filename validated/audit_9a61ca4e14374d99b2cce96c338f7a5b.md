### Title
Unbounded `DispatchGet.keys` lets any user force an O(n) per-key proof-verification loop with no cap, freezing that GET request's fee and blocking its resolution - ([File: modules/ismp/core/src/dispatcher.rs])

### Summary
`DispatchGet::keys` is an attacker-controlled `Vec<Vec<u8>>` with no length bound anywhere in the dispatch path. Any unprivileged caller (any EVM contract via `IDispatcher.dispatch`, or any parachain pallet such as the demo pallet's `get_request` extrinsic) can submit a GET request carrying an arbitrarily large `keys` array. Every downstream consumer of that request — `pallet_state_coprocessor::handle_get_requests`, `ismp::handlers::response::handle`, and every `verify_state_proof`/`verify_non_membership` implementation (EVM, substrate-EVM, Tendermint, Pharos, Substrate) — iterates once per key with no cap check, doing trie lookups/hash derivation/proof verification for each. This mirrors the reported "Loop gas limit" bug class: an unbounded, permissionlessly-grown array that a later, unprivileged-but-required processing step must fully iterate over in a single call/extrinsic.

### Finding Description
`DispatchGet` is defined with an unbounded key vector: [1](#0-0) 

It is dispatched with no length validation in `pallet_ismp::dispatcher::dispatch_request` (Substrate) — `dispatch_get.keys` is copied verbatim into the on-chain `GetRequest`: [2](#0-1) 

and the same is true on the EVM side (`DispatchGet.keys` is a raw `bytes[]` with no size check), as shown in the docs mirroring the Solidity struct: [3](#0-2) 

Any signed account can trigger this today via the demo pallet, which forwards `params.keys` unmodified: [4](#0-3) 

When the request is eventually processed, every keys-consuming code path loops once per key with no cap:
- `pallet_state_coprocessor::handle_get_requests` verifies the response for each `GetRequest` by handing `req.keys.clone()` straight to `verify_state_proof`: [5](#0-4) 
- The core response handler does the same per-request: [6](#0-5) 
- Every state-machine's `verify_state_proof` (EVM, substrate-EVM, Tendermint, Pharos, plain Substrate) loops over the full `keys` vector doing hashing/grouping/trie verification per entry, with no cap: [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9) 

The equivalent EVM `IHandler` batch loops (`handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts`) show the same pattern of per-element, uncapped iteration used throughout the protocol's message-handling surface: [11](#0-10) 

No length check on `keys` was found anywhere in the dispatch or handling path (`grep` for `MAX_KEYS`, `keys.len() >`, `MaxKeys`, etc. across the repo returned no matches for a `keys`-length guard).

### Impact Explanation
A single unprivileged dispatch (`DispatchGet` from any EVM contract or `get_request`/pallet call from any signed Substrate account) with a very large `keys` array creates a `GetRequest` commitment that:
1. Escrows a relayer fee (if non-zero) that can only be released on successful response delivery or timeout callback (`on_request_timeout`).
2. Cannot be answered: `pallet_state_coprocessor::handle_get_requests` and `handlers/response.rs::handle` must loop over every key to build/verify the response's state proof, and the resulting extrinsic (weight-metered on Hyperbridge) or transaction (gas-metered on EVM destinations) grows unbounded with `keys.len()`, exceeding the block weight/gas limit and becoming permanently un-includable.
3. Because it never gets a successful response nor callback, if `timeout == 0` (a documented, explicitly supported "never expires" option) the request is unresolvable forever, permanently freezing the escrowed relayer fee and leaving `RequestCommitments` bloated indefinitely. Even with a non-zero timeout, this is a griefing vector that reliably prevents legitimate responses/timeouts within the challenge window, since no relayer can economically or feasibly submit an oversized proof.

This satisfies "permanent freezing of funds" (escrowed relayer fee) and "route unable to deliver messages" for that specific request.

### Likelihood Explanation
High reachability: the entry point is a single permissionless `dispatch`/extrinsic call available to any user with no special role, no state precondition, and no cost scaling that prevents an attacker from choosing an oversized `keys` array (cost is proportional to calldata/extrinsic size only, which is far cheaper than the downstream verification work required to resolve it). This is directly analogous to the reported class: an actor-controlled, unbounded collection that a subsequent unprivileged-but-mandatory step must fully iterate, with no bound enforced anywhere in the pipeline.

### Recommendation
Introduce and enforce a `MAX_GET_KEYS` (or per-chain configurable) bound on `DispatchGet.keys.len()` at dispatch time, in both `pallet_ismp::dispatcher::dispatch_request` (Substrate) and the EVM `Dispatcher`/`EvmHost.dispatch` implementation for `DispatchGet`, rejecting requests that exceed the cap before a commitment/fee escrow is created. Additionally, consider metering `handle_get_requests`/`response::handle` weight proportionally to `keys.len()` so oversized batches fail fast rather than relying solely on a static weight annotation.

### Proof of Concept
1. Call the EVM `IDispatcher.dispatch(DispatchGet)` (or the Substrate demo pallet's `get_request` extrinsic) with `keys` containing e.g. 50,000 arbitrary 32-byte entries and a non-zero relayer `fee` and `timeout = 0`.
2. The request is accepted and committed (`RequestCommitments`/on-chain host state), escrowing the fee (Substrate) or requiring later gas-metered handling (EVM), because no length check exists in `dispatch_request` / `DispatchGet` handling.
3. Any relayer or the `pallet_state_coprocessor::handle_get_requests` / `response::handle` path attempting to resolve the request must build and verify a state proof over all 50,000 keys; the resulting extrinsic/transaction exceeds the destination's block weight/gas limit and can never be included.
4. Because `timeout = 0`, the request never times out and the escrowed fee remains locked forever, and the bloated `keys` payload remains unprocessable, illustrating the freeze/DoS.

	fn verify_state_proof(
		&self,
		_host: &dyn IsmpHost,
		keys: Vec<Vec<u8>>,
		root: H256,
		proof: &Proof,
	) -> Result<BTreeMap<Vec<u8>, Option<Vec<u8>>>, Error> {
		// The trie root is supplied by the caller, bound to the calling context, so a relayer
		// cannot steer verification at the wrong trie.
		let StateMachineProof { hasher, storage_proof } =
			codec::Decode::decode(&mut &*proof.proof)
				.map_err(SubstrateStateMachineError::ProofDecodeError)?;
		let data = match hasher {
			HashAlgorithm::Keccak => {
				let db = StorageProof::new(storage_proof).into_memory_db::<Keccak256>();
				let trie = TrieDBBuilder::<LayoutV0<Keccak256>>::new(&db, &root).build();
				keys.into_iter()
					.map(|key| {
						let value = trie
							.get(&key)
							.map_err(|e| SubstrateStateMachineError::TrieError(format!("{e:?}")))?;
						Ok::<_, SubstrateStateMachineError>((key, value))
					})
					.collect::<Result<BTreeMap<_, _>, _>>()?
			},
			HashAlgorithm::Blake2 => {
				let db = StorageProof::new(storage_proof).into_memory_db::<BlakeTwo256>();
				let trie = TrieDBBuilder::<LayoutV0<BlakeTwo256>>::new(&db, &root).build();
				keys.into_iter()
					.map(|key| {
						let value = trie
							.get(&key)
							.map_err(|e| SubstrateStateMachineError::TrieError(format!("{e:?}")))?;
						Ok::<_, SubstrateStateMachineError>((key, value))
					})
					.collect::<Result<BTreeMap<_, _>, _>>()?

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }
