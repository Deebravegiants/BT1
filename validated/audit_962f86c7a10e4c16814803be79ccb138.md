## Title
Unbounded token arrays in `IntentGatewayV2`/`IntentsBase` orders permanently freeze escrowed funds — analog of the Moloch `_ragequit` whitelisted-tokens DoS ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`placeOrder()` in `IntentGatewayV2` (and the Tron variant) does not bound the number of distinct tokens a user may put into `order.inputs` or `order.output.assets`. Every escrowed token must later be walked, one `SLOAD`/`SSTORE`/external-call per token, in `_withdraw()` to release, refund, or cancel an order. This mirrors the reported Moloch bug class: an attacker (or even an ordinary user, since this path is self-inflicted but permissionless) can construct a data structure whose settlement loop scales linearly with an attacker-controlled array length, exceeding the block gas limit and permanently freezing the escrowed value.

### Finding Description
`placeOrder()` only checks that `order.inputs.length != 0` [1](#0-0) , and the duplicate-output-token check merely dedupes, it does not cap the length of `order.output.assets` [2](#0-1) . Both `inputs` and `output.assets` are attacker/caller-controlled `TokenInfo[]` arrays with no `MAX_INPUTS`/`MAX_OUTPUTS` style guard anywhere in the codebase (confirmed absent via grep for `MAX_INPUTS`, `MAX_OUTPUTS`, `TooManyInputs`, `TooManyOutputs`).

Each input token is escrowed individually via a loop over `inputsLen` doing a `safeTransferFrom` and an `_orders[commitment][token] +=` write per entry [3](#0-2) . Settlement later reverses this per-token: `_withdraw()` iterates over `body.tokens.length`, decrementing escrow and performing a native/`ERC20` transfer for every single token in the withdrawal request:

```solidity
uint256 len = body.tokens.length;
for (uint256 i; i < len; i++) {
    address token = address(uint160(uint256(body.tokens[i].token)));
    uint256 amount = body.tokens[i].amount;
    if (amount == 0) continue;
    uint256 escrowed = _orders[body.commitment][token];
    if (escrowed == 0) revert UnknownOrder();
    _orders[body.commitment][token] = escrowed - amount;
    if (token == address(0)) { _sendValue(beneficiary, amount); }
    else { IERC20(token).safeTransfer(beneficiary, amount); }
}
``` [4](#0-3) 

This is the direct analog of the Moloch `_ragequit` loop: the number of iterations is not bounded by protocol configuration but by the size of an array the depositor themself chose when creating the order (each `TokenInfo` entry can point at a distinct arbitrary ERC-20 address; there is no whitelist or cap, and even fee-on-transfer/no-op tokens are accepted, since `placeOrder` calls `safeTransferFrom` for every listed token regardless of validity beyond a non-zero-amount check). A single order with hundreds of distinct token legs makes the escrow release path (`_withdraw`, invoked from `RedeemEscrow`/`RefundEscrow` handling in `onAccept`, and from `cancel`) exceed the block gas limit.

The `_execute()` path used for order fulfillment output calldata has the same shape — it loops over `outputsLen` sweeping token balances back with one `IERC20(token).balanceOf` check per asset [5](#0-4) , and `placeOrder`'s asset-transfer phases loop identically over `inputsLen`/`assetsLen` [6](#0-5) .

### Impact Explanation
If a user (attacker or unwittingly) places an order whose `inputs` (or `output.assets`) array is large enough that the corresponding `_withdraw` (or `_execute`) call cannot fit in a block's gas limit, the escrowed tokens for that order become permanently unrecoverable: neither a normal fill (`RedeemEscrow`), a refund (`RefundEscrow`), nor cancellation can complete, because the entire settlement transaction must process the full token list atomically inside `_withdraw`. This is a **permanent freezing of funds** for that specific order — matching the report's "all funds will be blocked forever" impact class, though scoped to the order's own escrow rather than the whole pool. Because `IntentGatewayV2`/`ExtrinsicIntents`/`IntrinsicIntents` are permissionless dispatch surfaces reachable from a single `placeOrder` transaction, this satisfies the "route unable to deliver messages / permanent freezing of funds" acceptance bar.

### Likelihood Explanation
Likelihood is Medium-High: any user can trigger it unintentionally by batching many small-value legs into one order (e.g., dust-sweeping or airdrop-style intents with dozens/hundreds of token addresses), and a griefer could deliberately craft an order with hundreds of distinct token addresses at minimal cost (fees are only charged in basis points on real value, and dust amounts still count as valid legs since only `amount == 0` is rejected). No admin/whitelist governs the length, so the attack requires only gas to submit one `placeOrder` call.

### Recommendation
- Enforce a hard cap (`MAX_ORDER_TOKENS`, comparable to the ~300-token estimate in the referenced report but tuned to the gas cost of `_withdraw`'s external-call-per-token loop, including SafeERC20 overhead) on `order.inputs.length` and `order.output.assets.length` in `placeOrder()`, reverting with a dedicated error if exceeded.
- Alternatively/additionally, allow partial, incremental withdrawal of an order's escrowed tokens (e.g., `withdrawToken(commitment, token)` callable per-token) so a stuck order is not required to process its whole token list atomically, decoupling "finalize" bookkeeping from the token transfer loop.
- Add fuzz/gas-benchmark tests exercising `_withdraw`/`_execute` with the maximum allowed token count to confirm the loop stays well under the destination chain's block gas limit.

### Proof of Concept
1. Attacker (or careless integrator) crafts an `Order` with `inputs` containing N (e.g., 400) distinct dummy ERC-20 tokens each with `amount = 1` (any nonzero amount is accepted, only duplicate detection applies to `output.assets`, not `inputs`).
2. Calls `placeOrder(order, graffiti)`, approving each of the N tokens for transfer; the call succeeds because there is no cap on `inputs.length`, escrowing all N tokens under one `commitment` in `_orders[commitment][token]`.
3. Order is later filled (or times out and needs refunding). Delivery of `RedeemEscrow`/`RefundEscrow` via `onAccept` invokes `_withdraw(body, ...)` with `body.tokens` mirroring all N escrowed tokens.
4. `_withdraw`'s `for` loop must perform N `SLOAD`s, N `SSTORE`s, and N external token-transfer calls in one transaction; for sufficiently large N this transaction cannot fit under the destination chain's block gas limit and always reverts.
5. Because `_withdraw` is the only code path that releases escrow for a commitment (used by both fill and refund/cancel), the escrowed assets for that order are now permanently unrecoverable.

Note: full verification of exactly how `WithdrawalRequest.tokens` is populated on the fill/refund dispatch side (`ExtrinsicIntents.sol` / `IntrinsicIntents.sol`) was not completed before the tool budget was exhausted — I was unable to read the full `fillOrder`/`cancel` implementations to confirm whether `body.tokens` is always set to the complete `order.inputs` set or can be chunked by the caller. If chunking is already possible off-chain, the practical severity could be lower than described; this should be confirmed directly against `evm/src/apps/intentsv2/ExtrinsicIntents.sol` and `IntrinsicIntents.sol` before finalizing severity.

        if (order.inputs.length == 0) revert InvalidInput();
