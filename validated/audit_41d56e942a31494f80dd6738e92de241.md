## Analog Found: Shop identity in webhook processing is not bound to the HMAC signature

The reported Solidity issue is a generic "you verified fewer bytes/fields than you acted on" bug class — the balance check protects some values but not others that are used downstream. The equivalent identity-binding break in this gem is in the webhook verification path: the `shop` value that `ShopifyAPI::Webhooks::Registry.process` hands to app handlers as the trusted tenant identifier is never included in the bytes that the HMAC actually authenticates.

### Title
Webhook shop-domain header is not covered by HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `#shop` is read straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header. `Registry.process` validates the HMAC over the body only, then forwards `request.shop` unchecked into `WebhookMetadata` passed to the app's `WebhookHandler#handle`. Because the signing secret (`Context.api_secret_key`) is the single app-wide `client_secret` shared by every shop that installs the app, any attacker who controls one legitimately-installed shop can capture a real, validly-signed webhook body for their own shop and replay it with the `shop-domain` header swapped to a victim shop. The HMAC check still passes because it never inspects the header, so the handler processes attacker-supplied data as if it authentically came from the victim tenant.

### Finding Description
- `Request#hmac`/`#to_signable_string` bind the signature check exclusively to `@raw_body`: [1](#0-0) [2](#0-1) 
- `HmacValidator` computes/compares the HMAC purely against `verifiable_query.to_signable_string` (the body), with no shop binding: [3](#0-2) 
- `Registry.process` validates that HMAC, then trusts `request.shop` (the unauthenticated header) to construct the `WebhookMetadata` delivered to the app's handler: [4](#0-3) 
- `WebhookMetadata.shop` is the field apps are documented/expected to use as the tenant identity for the event: [5](#0-4) 

The identity binding broken is: `shop authenticated by the signature` ≠ `shop delivered to the handler`. The HMAC only proves "this body byte-string was produced with knowledge of the app's `client_secret`" — it says nothing about which shop that secret-holder claims to be. Since the `client_secret` is shared across every shop that installs the app, *any* installed shop can produce a validly-signed body/HMAC pair for arbitrary content (e.g., its own genuine webhook traffic), and then relabel it as belonging to any other shop simply by changing an HTTP header the signature never covers.

### Impact Explanation
This crosses a tenant boundary using only a capability every installer of a public/multi-tenant app already has (the ability to trigger webhooks for their own store, i.e., valid `(body, hmac)` pairs signed with the shared `client_secret`). By relabeling the `shop-domain` header, the attacker can make the host application believe an event (order created, app uninstalled, GDPR redact request, etc.) came from a different merchant. Depending on how the host app keys its per-shop state off `WebhookMetadata#shop` (common pattern: look up/update records by shop domain), this enables cross-tenant data corruption or state confusion — e.g., forging an `app/uninstalled` or `shop/redact` event for a victim shop, or injecting fabricated order/customer data attributed to a shop the attacker does not control.

### Likelihood Explanation
Any actor able to install the app on a store (trivial for public apps, or any dev/test store for the same client_secret) can capture a legitimately signed webhook and replay it with a modified header field to the app's webhook endpoint — no access to `api_secret_key`, tokens, or TLS interception is required, since the header is not authenticated at all.

### Recommendation
Bind the tenant identity to the signed payload rather than to an out-of-band header:
- Where the webhook topic's JSON body contains shop-identifying data, prefer/validate against that instead of (or in addition to) the header.
- Require host applications to cross-check `request.shop` against a shop that is already known/installed (e.g., present in session storage) before trusting it, and document this requirement clearly if the library cannot include the shop in the signed bytes itself.
- Consider exposing a stricter API where callers pass the expected shop domain into `Registry.process`, so the library can assert `request.shop == expected_shop` before invoking the handler.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real event (e.g., updates an order), receiving a legitimately signed webhook POST with headers `x-shopify-hmac-sha256: <valid HMAC over raw body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same raw body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `request.to_signable_string` (the untouched raw body) — validation succeeds because the body and secret are unchanged.
4. `request.shop` now returns `"victim-shop.myshopify.com"`, and this value is placed into `WebhookMetadata#shop`, which is delivered to the app's `WebhookHandler#handle` as the trusted tenant identity, even though the victim shop never sent this webhook.
