Confirmed: `WebhookMetadata.shop` is passed directly to the app-supplied `WebhookHandler#handle` callback, sourced from `request.shop` which reads only the `shopify-shop-domain`/`x-shopify-shop-domain` header — a value never included in `to_signable_string`.

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC signature, allowing tenant-spoofed webhook delivery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)`. However, `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while the `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from unauthenticated HTTP headers [2](#0-1) . These header-derived fields are never part of the HMAC-signed material, yet `Registry.process` forwards `request.shop` (and the other header fields) directly into `WebhookMetadata`, which is handed to the app's own `WebhookHandler#handle` as the trusted tenant identity [3](#0-2) .

### Finding Description
The binding that should hold is: `shop used by the handler == shop authenticated by the HMAC`. In this gem it does not — the HMAC only binds `secret + raw_body == hmac`; it says nothing about which shop, topic, or webhook id the request claims to be for [4](#0-3) .

Because the signature is computed purely from `secret` and `raw_body`, any request that reuses a previously captured, genuinely-Shopify-signed `(raw_body, hmac)` pair (e.g., a webhook delivery observed on the wire, retried by Shopify with visible headers, or logged/exposed by any intermediary) will pass `HmacValidator.validate` regardless of what `shop-domain`, `topic`, `webhook-id`, or `api-version` headers accompany it. An unprivileged attacker with network reachability to the app's webhook endpoint can replay that exact body+HMAC while substituting an arbitrary `shopify-shop-domain` header value (a different real or attacker-controlled shop domain string) and the check still succeeds, because the header was never part of `to_signable_string`. `Registry.process` then instantiates `WebhookMetadata` with the attacker-chosen `shop`, `topic`, and `webhook_id`, and dispatches it to the host app's handler as if it were an authenticated fact [3](#0-2) .

This is the direct structural analog of the reported bug class: a field that the recipient acts on (`shop`, used for tenant attribution) is not covered by the cryptographic check (`hmac` over `raw_body` only) that is supposed to authenticate the request, exactly as the auction's `startAuctionTimestamp` was mutated by a call whose authorization check didn't cover that state.

### Impact Explanation
Host applications built on this gem rely on `WebhookMetadata#shop` to route webhook data to the correct tenant record (store credit, order sync, inventory, GDPR redaction handlers, etc.) without independently re-verifying which shop actually generated the payload — the gem's own documentation and struct design present `shop` as the trusted, HMAC-validated field. An attacker who can present a replayed body+HMAC pair with a forged `shop-domain` header can cause the host app to attribute (or misattribute) webhook content to a different tenant, producing cross-tenant data confusion in the app's persisted state. This matches the "cross-tenant access" criterion in scope.

### Likelihood Explanation
Exploitation requires no `api_secret_key`, no access token, and no privileged account — only a single captured legitimate `(raw_body, hmac)` pair (obtainable via network observation, logs, or any legitimate webhook delivery the attacker can trigger against their own installed instance of the app) and the ability to POST to the app's public webhook endpoint with a modified header. This is a realistic, low-effort replay, not a theoretical concern, since header values are explicitly excluded from the signed payload by design in `to_signable_string`.

### Recommendation
Bind the identity headers into the signed material, or otherwise independently verify `shop`/`topic`/`webhook_id` against server-side state before trusting them: extend `Webhooks::Request#to_signable_string` to canonically include `shop`, `topic`, and `webhook_id` (mirroring how `Oauth::AuthQuery#to_signable_string` binds `code`, `host`, `shop`, `state`, and `timestamp` together) [5](#0-4) , or document loudly that host apps must never trust `WebhookMetadata#shop` without cross-checking it against a known-installed shop list obtained from an already-authenticated session store.

### Proof of Concept
```ruby
# Attacker captures ANY legitimate webhook delivery for shop-a.myshopify.com:
raw_body = '{"id":123,"note":"legit payload"}'
real_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)
)

# Attacker replays same body+hmac but swaps the shop-domain header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => real_hmac,     # unchanged - still valid, since hmac covers body only
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # attacker-chosen
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes validation because HMAC only covers raw_body:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process dispatches to the app's handler with the forged shop attribution:
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", ...))
```
