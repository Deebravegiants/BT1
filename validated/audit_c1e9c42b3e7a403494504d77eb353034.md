### Title
Hardcoded `VALIDATOR_BIT_SET_SIZE = 64` in BSC consensus verifier can silently desynchronize from BNB Smart Chain's actual validator-set size, corrupting quorum verification - ([File: modules/consensus/bsc/verifier/src/primitives.rs])

### Summary
The BSC consensus client hardcodes the width of the validator vote bitvector to 64 bits (`VALIDATOR_BIT_SET_SIZE`), used to decode the `vote_address_set` bitmap that records which validators signed a given attestation. This constant mirrors the BSC Parlia/BEP implementation detail rather than a protocol invariant, and is not configurable per network like `BOHR_FORK_TIMESTAMP` is via the `Config` trait. If BNB Smart Chain's validator set ever grows to more than 64 active validators (which is an explicit, governance-adopted decentralization direction for BSC), or if the wire encoding of the vote bitmap otherwise changes, the on-chain and relayer code parses/validates against a fixed-width bitvector that is out of sync with the real chain.

### Finding Description
`VALIDATOR_BIT_SET_SIZE: usize = 64` is defined once in `modules/consensus/bsc/verifier/src/primitives.rs` and is consumed directly by the security-critical quorum check in `verify_bsc_header`: [1](#0-0) 

```
pub const VALIDATOR_BIT_SET_SIZE: usize = 64;
```

This is deserialized as a fixed-size SSZ `Bitvector` and then used both to reject "out of range" bits and to compute the 2/3 supermajority participant count that gates acceptance of a finalized BSC header as a trusted state commitment: [2](#0-1) 

Unlike `BOHR_FORK_TIMESTAMP`, which is deliberately made per-network configurable through the `Config` trait (`Mainnet`/`Testnet`) precisely because BSC protocol parameters change over time, [3](#0-2)  `VALIDATOR_BIT_SET_SIZE` is a bare, non-configurable constant baked into the verifier and prover regardless of which BSC network/fork the client tracks. If the real BNB Smart Chain validator set count ever exceeds 64 (or its consensus encoding widens the vote-address bitmap accordingly), all of the following invariants break simultaneously for every relayed BSC consensus update, both on-chain (`ismp_bsc::verify_consensus` at `modules/ismp/clients/bsc/src/lib.rs`) and in the relayer:
- Bits for validators at indices ≥ 64 are silently unrepresentable, meaning the participant/quorum count computed from `validators_bit_set.iter().take(current_validators.len())` at [4](#0-3)  no longer reflects the real vote, either permanently failing quorum (bricking the light client — a state machine unable to deliver messages) or, depending on how deserialization truncates/wraps the oversized bitmap, admitting a signature set that does not correspond to the intended supermajority.
- `get_rotation_block`/epoch-rotation math in `modules/consensus/bsc/prover/src/lib.rs` derives the validator rotation delay from `validator_size / 2`, which is unaffected by the bitset constant directly, but any related off-by-width deserialization failure in `parse_extra`/`verify_bsc_header` would make legitimate epoch-rotation updates unverifiable, permanently stalling the BSC client the same way `ensure_finalized_epoch_consistent` warns against being "permanently stuck." [5](#0-4) 

This is a direct structural analog to the report's core complaint: a numeric constant that mirrors an external chain's current implementation detail (BSC's active validator-set width) is hardcoded into the consensus-verification path rather than tracked/validated against the live chain's actual parameters, so if the counterparty implementation and Hyperbridge's assumption drift apart, the ISMP BSC light client either forges/mis-validates a consensus update or is permanently unable to deliver any further state commitments/messages from that route.

### Impact Explanation
High: `verify_bsc_header` is the sole gate that decides whether a BSC block's `state_root` is committed as a trusted `StateCommitment` for the `StateMachine::Evm` BSC chain, which downstream `HandlerV2`/proof verification relies on to validate cross-chain state membership proofs. A desynchronized bit-width either (a) permanently halts consensus updates for the BSC route (denial of message delivery for the entire BSC-connected route), or (b) in the worst case, causes the quorum/participant computation over a truncated/misaligned bitmap to no longer faithfully represent real validator votes, undermining the soundness of the finalized state commitment used for state proof verification.

### Likelihood Explanation
Low-to-Medium: BSC does not currently have more than 64 active consensus validators, so the condition is not exploitable today, but BNB Smart Chain has an explicit governance-driven roadmap toward more validators (mirroring the report's underlying concern about "implementation and specification... in flux"), and there is no on-chain guard, network `Config` field, or governance path to update `VALIDATOR_BIT_SET_SIZE` when that happens — unlike `BOHR_FORK_TIMESTAMP` which is already made configurable for exactly this reason.

### Recommendation
- Make `VALIDATOR_BIT_SET_SIZE` a per-network `Config` constant (like `BOHR_FORK_TIMESTAMP`) rather than a fixed literal, so mainnet/testnet validator-set width can be updated independently as BSC's validator count grows.
- Add an explicit bounds check when parsing `extra.validators`/`vote_address_set` that fails loudly (rather than silently truncating) if `validator_size` exceeds the configured bitset width, and track BSC's validator-count roadmap so the constant is proactively updated well ahead of any mainnet increase past 64.
- Add integration tests parameterized on validator counts approaching and exceeding 64 to catch this drift before it reaches production.

### Proof of Concept
Not directly exploitable today since live BSC has fewer than 64 validators; the vulnerability is latent and becomes live the moment BSC's active validator set exceeds 64:
1. BSC governance activates a hard fork raising the active validator count above 64 (an already-signaled direction for BSC decentralization).
2. A relayer submits a `BscClientUpdate` whose `attested_header.extra_data` encodes a `vote_address_set` reflecting >64 validators/votes.
3. `verify_bsc_header` (`modules/consensus/bsc/verifier/src/lib.rs:63-90`) deserializes this into a fixed `Bitvector::<64>`, silently losing/misaligning bits for validator indices ≥ 64.
4. Depending on SSZ deserialization behavior on oversized input, either every subsequent update fails supermajority/`InvalidSignature` checks (client permanently stuck, no further BSC state commitments deliverable), or the truncated bit-count still happens to clear the `2 * n / 3` threshold against the wrong validator subset, committing a `state_root` that was not actually attested by the reported supermajority.

/// Enforce that `finalized_height` never runs ahead of the validator set the client holds.
///
/// A BSC epoch-N validator set signs for `current_epoch` and remains valid into the first half of
/// `current_epoch + 1` (until the mid-epoch rotation block), so an update finalizing a header early
/// in the next epoch verifies fine against it. But the client may only *rely* on that overlap once
/// the next set has been staged (`next_validators_staged`) so the rotation can subsequently be
/// enacted. An update that finalizes a header in a new epoch without staging that rotation leaves
/// `current_epoch`/`current_validators` a full epoch behind `finalized_height`; the relayer derives
/// its sync target from `max(epoch(finalized_height), current_epoch)`, so it would skip the
/// un-staged epoch forever and the client would be permanently stuck (also a griefing vector).
///
/// The finalized height may therefore cross an epoch boundary only via a validator-set-staging
/// (sync) update, and by at most one epoch: `epoch(finalized_height) <= current_epoch +
/// next_validators_staged`.
pub fn ensure_finalized_epoch_consistent(
	finalized_height: u64,
	current_epoch: u64,
	next_validators_staged: bool,
	epoch_length: u64,
) -> Result<(), Error> {
	let finalized_epoch = compute_epoch(finalized_height, epoch_length);
	let max_finalized_epoch = current_epoch + next_validators_staged as u64;
	if finalized_epoch > max_finalized_epoch {
		return Err(Error::StaleValidatorSet {
			finalized_epoch,
			current_epoch,
			next_validators_staged,
		});
	}
	Ok(())
}
