### Title
Duplicate `address(0)` entries in `erc20TokenAddresses` let a single `msg.value` back multiple independent balance-equation checks, minting unbacked shielded ETH - (File: `contracts/Hinkal.sol`)

### Summary
`Hinkal.transact` validates the balance equation independently for every index of `circomData.erc20TokenAddresses`, and for `address(0)` it always adds the *same* `msg.value` into `balanceDif` regardless of how many times ETH appears in the array. Because the check `balanceDif == amountChanges[i] + utxoAmount` is evaluated per index rather than per unique token, an attacker can list `address(0)` twice with `amountChanges[i] = amountChanges[i'] = msg.value`, satisfying both checks off a single ETH transfer.

### Finding Description
The equality that should hold is: **total real ETH received (`msg.value`, credited once) == total ETH value committed across all output channels (`Σ amountChanges[i]` for ETH slots + `Σ utxoAmount` for ETH slots)**.

In `transact`, `oldBalances`/`newBalances` are captured once for the whole `erc20TokenAddresses` array via `getBalancesForArray` [1](#0-0) , and then the per-index loop computes, for every occurrence of `address(0)`:

```
balanceDif = newBalances[i] + msg.value - oldBalances[i]
``` [2](#0-1) 

Because `msg.value` is credited to `address(this).balance` by the EVM *before* the function body runs, `oldBalances[i]` already includes it once; the extra `+ msg.value` term is meant to represent the single deposit being distributed to exactly one accounting term. If `address(0)` appears at two indices `i` and `i'`, `oldBalances[i] == oldBalances[i']` and `newBalances[i] == newBalances[i']` (same address, same point in time), so `balanceDif` is identical (`V`) at both indices.

The equation is then checked independently per index:
```
require(balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount);
``` [3](#0-2) 

Nothing deduplicates `erc20TokenAddresses` or tracks how much of `V` has already been "claimed" by a prior index — each duplicate slot can independently declare `amountChanges[i] = V` and pass.

In `_internalTransact` (reached when `externalActionId == 0`), the same per-index loop performs the deposit-side transfer check:
```
transferERC20TokenFromOrCheckETH(address(0), externalAddress, address(this), amountChanges[i])
```
which for ETH only does `require(msg.value == _value)` [4](#0-3)  — a stateless comparison against the *whole* `msg.value`, not a running total. It can therefore pass at every duplicated index, since `msg.value` never changes and nothing is decremented.

Since `utxoSet` is always empty for the internal-transact path (`UTXO[] memory utxoSet;` is never assigned when `externalActionId == 0`) [5](#0-4) , there is no out-of-bounds `onChainCommitments` write to catch the duplication (that only happens on the external-action path when real on-chain UTXOs are matched). Each `erc20TokenAddresses` slot maps to its own `amountChanges[i]`/`onChainCreation[i]`/output-commitment channel that is fed into the circuit's public inputs (each slot independently constrained by `inTotal + amountChanges === outTotal` per the circuit design). With two ETH slots both declaring `amountChanges = V`, the attacker can generate a valid proof producing two independent sets of shielded output commitments each worth `V`, while only ever transferring `V` of real ETH into the contract once.

None of the existing guards prevent this: `performHinkalChecks`/`dimensionsCheck` validate array *lengths* match `dimensions`, not uniqueness of token addresses; `rootHashExists` and `verifyProof` only validate that the supplied proof is internally consistent with the public inputs the attacker themselves constructs; the balance/slippage `require`s are evaluated per index and are satisfiable independently as shown above; `insertNullifiers`/`insertCommitments` simply insert whatever commitments were computed, with no cross-check against actual received value.

### Impact Explanation
The attacker can mint shielded ETH value without backing: for `N` duplicate `address(0)` entries in `erc20TokenAddresses`, they can produce up to `N` independent shielded output channels each worth the single deposited `msg.value`, while only ever paying that `msg.value` once into the contract. This is direct protocol insolvency — shielded balances become unbacked by real contract ETH — matching the "Critical: minting shielded value without backing" impact category. The attack is repeatable per transaction/block and scales with the number of duplicate entries (bounded only by `dimensions`/array-length limits).

### Likelihood Explanation
The attacker is fully unprivileged: they only need to be able to call `transact` with `externalActionId == 0`, craft `CircomData` with a duplicated `address(0)` entry in `erc20TokenAddresses`, matching `amountChanges` entries equal to `msg.value`, and generate a valid proof for their own chosen public inputs/UTXOs (which they are explicitly permitted to construct under the stated attacker model). No relay, admin, or victim interaction is required. The only nontrivial cost is generating a valid Groth16 proof for the crafted circuit inputs, which is standard prover work available to any user of the protocol.

### Recommendation
Aggregate `erc20TokenAddresses` by unique token before computing `balanceDif`/performing the equation check (e.g., require the array contains no duplicate addresses, or sum `amountChanges`/`utxoAmount` per unique token and compare against a single balance delta per token computed once). Additionally, the `+ msg.value` term for `address(0)` should be applied exactly once globally, not once per array index, and `transferERC20TokenFromOrCheckETH`'s `msg.value` check should be tied to a single running total consumed across the whole call rather than compared statelessly per index.

### Proof of Concept
Foundry test outline:
1. Deploy `Hinkal` with a mock verifier that accepts attacker-controlled proofs (or use the real prover to generate a valid proof for the crafted `CircomData`), a test `HinkalHelper`, and record `address(this).balance` (Hinkal contract) before the call.
2. Craft `circomData` with `externalActionData.externalActionId = 0`, `erc20TokenAddresses = [address(0), address(0)]`, `amountChanges = [V, V]`, `onChainCreation = [false, false]`, `slippageValues = [V, V]`, `externalActionData.externalAddress = attacker`.
3. Call `hinkal.transact{value: V}(a, b, c, dimensions, circomData)`.
4. Assert: contract ETH balance increased by exactly `V` (`address(this).balance` delta == `V`), but the sum of newly inserted shielded commitments' declared ETH value (via `amountChanges` accepted by both loop iterations) == `2V`.
5. Assert the broken equality directly: `V (msg.value, contract balance delta) != amountChanges[0] + amountChanges[1] (2V, minted shielded value)` — confirming unbacked minting.
