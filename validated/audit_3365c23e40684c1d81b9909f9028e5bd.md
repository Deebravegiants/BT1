## Title
Webhook shop/topic/webhook-id identity spoofing — HMAC only covers the body, not the `Shopify-Shop-Domain` header — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read from unauthenticated HTTP headers. `Webhooks::Registry.process` trusts these header-derived values and forwards them unchanged to the app's `WebhookHandler`, breaking the intended binding: `hmac_verifies(body) == identity_of(shop, topic, webhook_id)`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers, with no cryptographic linkage to the signed body: [2](#0-1) 

`Webhooks::Registry.process` validates only the body HMAC via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app-supplied handler: [3](#0-2) 

`HmacValidator.validate` confirms this — it only ever calls `verifiable_query.to_signable_string`, which for `Request` is the raw body: [4](#0-3) 

Because a single app-level `client_secret` is shared across every shop that installs the app, the HMAC over a given body is identical no matter which shop it "belongs" to. This means the `shop` field — the identity binding the whole webhook-processing model depends on — is acted upon by the handler without being part of what the HMAC verifies. The equality the code assumes but does not enforce is: `hmac_valid(body) == authentic(shop_header)`. In reality, `hmac_valid(body)` only proves the body was signed with the app secret by *some* shop, not that the accompanying `shop` header is genuine for that body.

### Impact Explanation
An attacker who controls any shop that has installed the target app can capture a legitimate webhook delivery to their own shop (a valid `raw_body` + `hmac-sha256` pair signed with the app's shared `client_secret`), then replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and `topic`/`webhook-id`) header naming a different, victim shop. `Utils::HmacValidator.validate` still returns `true` because it only checks the (unmodified) body, so `Registry.process` builds a `WebhookMetadata` claiming the event originated from the victim shop and hands it to the app's handler. This is a cross-tenant identity-confusion vector: the app's business logic (data sync, redaction, billing triggers, etc.) is invoked believing it is acting on behalf of a shop the attacker does not control. The mandatory compliance topics (`shop/redact`, `customers/redact`, `customers/data_request`) are especially concerning, since a forged `shop/redact` event impersonating a victim's domain could cause the app to redact/destroy data belonging to a shop the attacker never installed on.

### Likelihood Explanation
Exploitation requires the attacker to install the target app on their own (or a trial) shop — a routine, unprivileged action for any Shopify merchant/developer — then capture one legitimate webhook and resend it with a modified `shop` header. No access to another shop's access token, session, or the app's `client_secret` is needed, and the HTTP layer/headers used by `Webhooks::Request` are populated from whatever the caller (any HTTP client hitting the app's public webhook endpoint) supplies.

### Recommendation
Bind the shop identity to the signed content: include the shop domain (and ideally topic/webhook id) in the HMAC-covered signable string, or otherwise cross-check the header-derived `shop` against a value tied to the current registration/session before trusting it in `WebhookMetadata`. At minimum, document that host applications must independently authenticate `shop` (e.g., by verifying it against known installed shops) since the HMAC in this gem does not cover it.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com"
# and receives a legitimate webhook:
raw_body = '{"id":1}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_CLIENT_SECRET, raw_body)

# Attacker replays the same body+hmac but swaps the shop-domain header:
headers = {
  "x-shopify-topic" => "shop/redact",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (only checks raw_body),
#    handler.handle receives WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "shop/redact", ...)
```

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
