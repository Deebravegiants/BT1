### Title
Interest accrual overflows the RAY value domain and permanently freezes an oversized market - (File: common/src/rates/simulate.rs)

### Summary
A market whose scaled supply or debt value grows beyond `i128::MAX` can no longer accrue interest because `accrue_step` first converts scaled shares back into RAY-denominated value using panicking fixed-point multiplication. [1](#0-0) [2](#0-1)  Once this boundary is crossed, `update_indexes`, repayments, withdrawals, liquidations, bad-debt cleanup, recapitalization and other market mutations all execute the same accrual path and revert with `MathOverflow`. [3](#0-2) [4](#0-3) 

### Finding Description
The pool stores `supplied` and `borrowed` as index-scaled RAY shares rather than native balances. [5](#0-4)  Every accrual computes `borrowed * borrow_index / RAY` and `supplied * supply_index / RAY` through `scaled_to_original`, which delegates to `Ray::mul`. [1](#0-0) [6](#0-5)  `Ray::mul` returns an `i128` result and panics with `GenericError::MathOverflow` when the exact result exceeds the representable range. [7](#0-6) [8](#0-7) 

The protocol’s index ceiling is `10^36`, which is only `10^9` times the initial index, but the admitted asset domain can still produce a scaled position whose future indexed value exceeds `i128::MAX` before that ceiling is reached. [9](#0-8)  This is not protected by `update_borrow_index`, because the vulnerable total-value multiplication occurs before the new borrow index is calculated and capped. [10](#0-9) [11](#0-10) 

An unprivileged caller can invoke `Controller::update_indexes(caller, assets)` directly after creating the oversized market position. [12](#0-11)  The controller forwards the supplied `Vec<HubAssetKey>` to the pool, whose `accrue` implementation loads each market and calls `interest::global_sync`. [13](#0-12) [4](#0-3) 

### Impact Explanation
Once `scaled_to_original` overflows, `global_sync` cannot stamp `last_timestamp`, so every later transaction retries accrual from the same stale state and hits the same overflow. [14](#0-13)  Because all ordinary pool legs use `synced_market`, suppliers cannot withdraw and borrowers or third parties cannot repay after the cliff. [15](#0-14) [16](#0-15)  Liquidation and bad-debt cleanup also depend on the same pool market accrual, leaving collateral and pool cash inaccessible. [17](#0-16) 

The included integration test reaches this state with a one-billion-whole-token, 18-decimal market at 98% utilization and demonstrates that `update_indexes`, `withdraw`, and `repay` all return `MATH_OVERFLOW` while the borrow index remains below `MAX_BORROW_INDEX_RAY`. [18](#0-17)  The result is permanent freezing of supplied collateral and borrowed-account settlement functionality unless a privileged contract upgrade replaces the accounting arithmetic. [14](#0-13) 

### Likelihood Explanation
The attack requires a very large position and sustained debt accrual rather than a single instantly malicious numeric argument. [19](#0-18)  It is nevertheless reachable by an unprivileged account through ordinary `supply`, collateral `supply`, `borrow`, and later `update_indexes`; a single caller can control both the funded supply account and the collateralized borrowing account. [20](#0-19) [12](#0-11)  The probability depends on asset supply, market caps, price risk requirements and realized utilization, but the protocol’s own arithmetic bounds show that valid admitted inputs can reach the cliff before the configured index cap. [21](#0-20) 

### Recommendation
Prevent any market from reaching an unrepresentable indexed total, rather than relying only on the index ceiling. Enforce a checked invariant such as `scaled_shares * index / RAY <= i128::MAX` before minting supply or debt and before committing an index update, using `try_mul_div_half_up` or an `I256` comparison so the guard itself cannot overflow. [22](#0-21)  Alternatively, refactor accrual and utilization calculations to carry widened totals through `accrue_step`, calculate rewards from the widened delta, and allow share-denominated repayment or withdrawal paths without first materializing the total value as `i128`. [23](#0-22)  The admission cap should account for future index growth or be paired with a fail-safe accrual mode that remains executable near the domain boundary. [24](#0-23) 

### Proof of Concept
1. As one unprivileged caller, create supply account A and call `Controller::supply(caller, 0, spoke_id, [(BIG18, 1_000_000_000 * 10^18)])`. [25](#0-24) 
2. Create collateral account B for the same caller, supply enough collateral, and call `Controller::borrow(caller, B, [(BIG18, 980_000_000 * 10^18)], Some(caller))`. [26](#0-25) 
3. Keep utilization high while ledger time advances until `borrowed * borrow_index / RAY > i128::MAX`. [10](#0-9) 
4. Call `Controller::update_indexes(caller, [HubAssetKey { hub_id, asset: BIG18 }])`; `global_sync` reaches `scaled_to_original` and panics with `MathOverflow`. [12](#0-11) [4](#0-3) [7](#0-6) 
5. Subsequent `repay` and `withdraw` calls fail at the same stale accrual step because both pool legs call `interest::global_sync` before performing their state mutation. [15](#0-14) [27](#0-26)

```rust
/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}
```

```rust
/// Computes `x * y / d` rounded half up. Returns `None` if `x < 0`, `y < 0`, `d <= 0`, or the
/// result does not fit in `i128`.
pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```
