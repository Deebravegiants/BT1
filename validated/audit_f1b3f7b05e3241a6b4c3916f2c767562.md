## Finding

Confirmed: `ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` are the values used to validate the webhook, but they only cover the raw request body — never the `shop` field that the host application receives and treats as the tenant identifier. [1](#0-0) 

`Registry.process` validates only that HMAC (i.e., only the body) and then hands `request.shop`, taken verbatim from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header, straight to the app's handler as the authoritative tenant: [2](#0-1) 

The header is read with no cross-check against the signed bytes: [3](#0-2) 

The HMAC validator itself is generic and only compares `to_signable_string` against `Context.api_secret_key` (a single secret shared by the app across every installed shop, not a per-shop secret): [4](#0-3) 

### Title
Webhook `shop` field is trusted without being covered by the HMAC, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`. The HMAC that `Registry.process` verifies via `HmacValidator.validate` therefore authenticates the request body only, never the `shop-domain` header. Because `api_secret_key` is a single value shared across every shop that has installed the app, any tenant who can trigger a legitimate webhook to their own shop obtains a `(body, hmac)` pair that is valid under the app's secret regardless of which shop it is attributed to. That pair can be replayed with the `X-Shopify-Shop-Domain` header changed to a victim shop, and `HmacValidator.validate` will still accept it because it only checks the body against the secret.

### Finding Description
The identity binding that should hold is: `shop header used by the handler == shop that the signed bytes originated from`. In this gem that binding is broken — the equality actually enforced is only `HMAC(body, secret) == received_hmac`, with no linkage from `shop` into the signable string. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) passes `request.shop` — parsed straight from an attacker-influenced header — into `WebhookMetadata`, which host apps typically use to look up/write tenant-scoped records (shop settings, install state, order data, etc.). Since `api_secret_key` is per-app, not per-shop, a merchant who installs the app on `attacker.myshopify.com` can capture a validly-HMAC'd webhook body from Shopify and resend it (directly to the app's webhook endpoint) with the `shop-domain` header set to `victim.myshopify.com`. The gem's `HmacValidator` reports the request as authentic because it never checked the shop field.

### Impact Explanation
This crosses the tenant boundary the gem is responsible for enforcing on behalf of the host application: an app trusting `WebhookMetadata#shop` (which is the documented, intended way to consume webhook data from this SDK) can be made to apply another merchant's webhook data/actions to the wrong shop record, i.e. cross-tenant access/write using only a validly-signed body the attacker legitimately obtained for their own shop. This matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Any developer/attacker can install the target app on their own store, causing Shopify to send at least one real webhook (or use a mandatory GDPR webhook) whose body+HMAC they capture. No credentials beyond having an install of the app are required, and the replay is a simple direct HTTP POST to the app's public webhook endpoint with a modified header — the header is attacker-controlled input to `Request.new(raw_body:, headers:)`.

### Recommendation
Bind the shop identity into the verified bytes: include the shop domain header in `to_signable_string`, or otherwise validate that the resolved `shop` corresponds to a session/shop that this app secret is actually authorized for before invoking the handler, rather than trusting an unauthenticated header.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com`.
2. Shopify sends a webhook (e.g. `orders/create`) to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(B, api_secret_key)`, `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures `B` and the HMAC value.
4. Attacker POSTs the same body `B` and HMAC to the app's webhook endpoint again, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(B, api_secret_key)` — it succeeds because `B` and the HMAC are unchanged.
6. The handler receives `WebhookMetadata.new(... shop: "victim.myshopify.com", body: parsed(B) ...)`, i.e., attacker-controlled data attributed to the victim shop. [5](#0-4) [6](#0-5)
