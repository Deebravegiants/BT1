### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing in `ShopifyAPI::Webhooks::Registry.process` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0)  , while the `shop` attribute used downstream to attribute a webhook to a tenant is pulled directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header [2](#0-1) . `Registry.process` validates only the HMAC over the signable string (the body) via `Utils::HmacValidator.validate(request)`, and then forwards `request.shop` unauthenticated into the handler as the tenant identifier [3](#0-2) .

### Finding Description
The identity binding that should hold is: `shop-domain header == shop bound by HMAC`. In this gem that equality does not hold — the HMAC is computed with `OpenSSL::HMAC.hexdigest(sha256, client_secret, raw_body)` [4](#0-3) , and `raw_body` is the only signed input (per `to_signable_string`). The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are entirely outside the signed payload.

`Utils::HmacValidator.validate` checks the HMAC computed over `verifiable_query.to_signable_string` (i.e. just the body) against the received `hmac` header [5](#0-4) . `Registry.process` calls this validator and then passes `request.shop` (from the unsigned header) straight into `WebhookMetadata`, which the host application's handler treats as the authenticated tenant for the event [3](#0-2) [6](#0-5) .

Because `hmac-sha256` only proves that *the body bytes* were signed by Shopify with the app's `client_secret` — it says nothing about which shop's header set accompanies that body — any body/HMAC pair remains valid for a request that carries a different `shop-domain` header. A given webhook body ("{}", or any JSON payload) combined with its valid HMAC can be resent with an arbitrary `shop-domain` header pointing at a victim tenant, and `Utils::HmacValidator.validate` will still return `true` because it re-derives the HMAC solely from the (unchanged) body.

### Impact Explanation
This breaks the tenant boundary that `Registry.process`/`WebhookHandler` implementations rely on: the app is designed so that only Shopify (holder of `client_secret`) can produce a valid HMAC for a webhook, and the accompanying `shop` field is implicitly trusted to identify which merchant the event belongs to. Because `shop` is not bound into the signature, an attacker who has observed (or can produce, e.g. by installing the app on their own store and receiving a real webhook delivery for a body they can predict/control, such as an empty-body `app/uninstalled` event) any valid `(body, hmac)` pair can replay it to the app's webhook endpoint with a forged `shop-domain` header naming a different, victim shop. The host application will process this as a legitimate event for the victim shop — cross-tenant event injection/spoofing (e.g. triggering uninstall/data-deletion handling, order/webhook-driven business logic, or state changes) attributed to a shop the attacker does not control.

### Likelihood Explanation
Exploitability only requires network access to the app's public webhook endpoint plus one legitimately signed `(body, hmac)` pair, which is trivial to obtain since HMAC coverage is body-only and constant/predictable bodies exist for several webhook topics (e.g., empty `{}` payloads). No access token, `client_secret`, or privileged account is needed — this fits the "unprivileged internet user" threat model.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the signed material verified against the HMAC, or otherwise cryptographically bind the shop identity to the signature (e.g., verify shop against a separately authenticated channel such as a stored webhook-id-to-shop mapping) before trusting `request.shop` in `WebhookMetadata`. At minimum, document that consuming applications must independently re-validate `shop` against their own tenant records before acting on webhook data, since this gem's HMAC check does not cover it.

### Proof of Concept
1. App receives (or attacker independently obtains, e.g. via their own installed instance) a legitimate webhook delivery: `raw_body = "{}"`, headers include `x-shopify-hmac-sha256: <valid HMAC of "{}">`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: app/uninstalled`.
2. Attacker resends the exact same body and HMAC to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds the request object; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `"{}"` only and matches the (unchanged) `hmac` header — validation succeeds [7](#0-6) .
4. The registered handler is invoked with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...)` [8](#0-7) , causing the host app to process an uninstall/other event as if it originated from `victim-shop.myshopify.com`, despite the request never actually being signed for that shop.
