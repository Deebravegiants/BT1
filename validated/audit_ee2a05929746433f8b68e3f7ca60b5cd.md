## Title
Early-stage pools can be trapped in an extreme skew (via a large self-swap or a direct vault donation) that DoSes honest depositors from adding liquidity - (File: `program/src/processor.rs`)

### Summary
The external report describes a lending-market LEX where an attacker who is the first liquidity provider can push the market to an extreme debt/collateral ratio while liquidity is still tiny, so that any small price move later makes the market "undercollateralized" and blocks all further `mint` calls, freezing honest LPs out. The Raydium constant-product AMM has a structurally analogous weakness: the pool's exchange ratio used for `Deposit` is derived directly from the *live* SPL token balances of the coin/pc vaults, not from an amount tracked purely through AMM instructions. When the pool is newly created with very small reserves, the same attacker who created it (or any other user) can skew that ratio to an extreme value — either by executing a single large self-swap or by directly transferring ("donating") tokens into the vault accounts — and this extreme ratio then causes legitimate `Deposit` calls with normal-sized amounts to revert (`ExceededSlippage` or `InvalidInput`), DoS-ing bootstrapping of the pool.

### Finding Description
`process_deposit` computes the exchange rate purely from the vaults' current SPL balances: [1](#0-0) 

These `total_pc_without_take_pnl` / `total_coin_without_take_pnl` values feed the `InvariantToken`/`InvariantPool` conversions that compute how much of the "other" token a depositor must provide and how many LP tokens they receive: [2](#0-1) 

If the ratio between `total_coin_without_take_pnl` and `total_pc_without_take_pnl` is pushed to an extreme (e.g. coin reserve near-zero relative to pc reserve, or vice versa), then for a depositor specifying reasonable `max_coin_amount`/`max_pc_amount`:
- `exchange_coin_to_pc` / `exchange_pc_to_coin` can compute a required "other side" amount that is either far larger than the caller's specified max (triggering `ExceededSlippage`) or rounds down to `0` (triggering `InvalidInput`), and
- the corresponding `mint_lp_amount` computed via `InvariantPool::exchange_token_to_pool` with `RoundDirection::Floor` can also round to `0`, which is explicitly rejected: [3](#0-2) 

Because the swap math (`Calculator::swap_token_amount_base_in` / `swap_token_amount_base_out` in `math.rs`) uses the same live vault-balance based `total_pc_without_take_pnl`/`total_coin_without_take_pnl` inputs, a single attacker who is the sole (or dominant) LP right after `Initialize2` can execute one large `SwapBaseIn`/`SwapBaseOut` — the same tactic as the external report's PoC (swap "a huge portion" while the pool is small) — and push the ratio to a state where honest, "normal size" `Deposit` transactions systematically fail. This mirrors the report's root cause: an attacker exploits the fact that early-stage, thin-liquidity state is disproportionately sensitive to a single large action taken by whoever provides the first liquidity, permanently degrading usability for subsequent legitimate participants until reserves happen to normalize.

Additionally, because `amm_coin_vault.amount`/`amm_pc_vault.amount` are read straight from the token accounts (see also the same pattern in `process_initialize2`'s liquidity computation, `program/src/processor.rs:908-917`), any party who knows the vault addresses can also directly SPL-transfer tokens into the vault (a "donation") to distort this ratio without ever calling into the AMM program, compounding the same effect.

### Impact Explanation
This is not a direct fund-theft path, but it can freeze legitimate liquidity provisioning for a newly created pool: depositors submitting economically reasonable amounts get reverted (`ExceededSlippage`/`InvalidInput`), which prevents the pool from ever reaching healthy, balanced liquidity depth — analogous to the "Medium" impact rated in the source report ("honest users are unable to add liquidity and the market becomes unstable").

### Likelihood Explanation
Reachable by any unprivileged actor who creates the pool via `Initialize2` (a single default instruction with attacker-chosen `init_coin_amount`/`init_pc_amount`) and then issues one `SwapBaseIn`/`SwapBaseOut` swap while they are the dominant/only LP — exactly the two-step pattern (mint then swap large amount) used in the report's PoC — or, more simply, a raw SPL token transfer to the vault account. No privileged signer or special conditions are required, and the attack is most effective (and most likely to be attempted) while the pool is new and thin, which is the normal state of any freshly-created Raydium pool before it accumulates deep liquidity.

### Recommendation
Do not derive the deposit/swap invariant purely from raw vault balances that can be inflated by an out-of-band SPL transfer, and consider bounding how far a single swap can move the pool's price/ratio while total liquidity is below some threshold (or require a minimum liquidity depth before allowing large swaps), similar to the source report's suggestion of restricting the specific action that "worsens" the extreme state while still allowing normal operations (here, deposits) to proceed.

### Proof of Concept
1. Attacker calls `Initialize2` with small `init_coin_amount`/`init_pc_amount` (e.g., 1000/1000), becoming the pool's only LP (`program/src/processor.rs:897-985`).
2. Attacker calls `SwapBaseIn`/`SwapBaseOut` with a large `amount_in` on one side (e.g., swapping in a large multiple of the pc reserve for coin, or vice versa), which is computed via `Calculator::swap_token_amount_base_in` using the live vault balances (`math.rs:289-325`) and moves the coin/pc ratio to an extreme value bounded only by the constant-product invariant (never fully draining one side, but making it disproportionately small).
3. A separate honest user calls `Deposit` with `max_coin_amount`/`max_pc_amount` and `base_side` sized for a "normal", pre-skew ratio. `process_deposit` recomputes the current (post-skew) ratio from vault balances (`processor.rs:1138-1250`) and either: (a) computes a required "other-side" amount exceeding the honest user's specified max, reverting with `AmmError::ExceededSlippage` (`processor.rs:1206-1222` / `1257-1273`), or (b) computes `mint_lp_amount`/`deduct_coin_amount`/`deduct_pc_amount` that rounds to `0`, reverting with `AmmError::InvalidInput` (`processor.rs:1323-1325`).
4. Honest liquidity providers are effectively blocked from adding liquidity to the pool until they discover and match the attacker-skewed ratio, mirroring the DoS-on-honest-liquidity outcome in the source report.
