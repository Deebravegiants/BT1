### Title
Webhook `shop`, `topic`, and `webhook_id` values are not covered by the HMAC signature, allowing shop/topic spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC over the raw request body, then dispatches to a handler using the `topic` and attributes the event to a `shop` — both of which are taken from HTTP headers that are never included in the signed material. This breaks the identity binding `signed(shop, topic) == acted-upon(shop, topic)`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `hmac` is parsed from the `hmac-sha256` header [2](#0-1) . `Registry.process` verifies only that this body/HMAC pair is valid, then uses the `topic` and `shop` header values (also unauthenticated) to select a handler and to populate `WebhookMetadata`: [3](#0-2) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read directly from headers with no cryptographic binding to the signed body [4](#0-3) . `HmacValidator.validate`/`validate_signature` only checks `verifiable_query.to_signable_string` (the raw body) against the shared `api_secret_key` — it never touches `shop` or `topic` [5](#0-4) .

Because the app's `api_secret_key` is shared across every shop that installs the app, any unprivileged merchant who installs the app on their own store legitimately receives valid `(raw_body, hmac)` pairs signed with that same secret. Since `shop`, `topic`, and `webhook_id` sit outside the signed content, that merchant can replay the identical body+signature to the app's webhook endpoint while substituting a different `shopify-shop-domain` header (a victim shop) and/or a different `shopify-topic` header, and the signature will still validate — `Registry.process` will hand the payload to the handler for the victim shop/topic combination.

### Impact Explanation
Host applications rely on `WebhookMetadata#shop` to identify which tenant a webhook pertains to (e.g., to look up/act on that shop's stored session or delete shop-scoped data for mandatory `shop/redact`, `customers/redact`, `customers/data_request` topics). Because `shop` is not bound to the HMAC, an attacker can misattribute a signed payload to an arbitrary victim shop, and can also redirect a payload to a different topic handler than the one Shopify actually signed it for. This is a cross-tenant integrity/authentication issue: the app processes data "as if" it came from shop X's `topic` Y, when the cryptographic proof only covers the byte content, not who it's about or what event it is.

### Likelihood Explanation
No privileged access, leaked secrets, or credentials are required — merely the ability to install the target app on any shop (an action any merchant can perform) to obtain one legitimately signed webhook, then replay it with modified headers to the app's public webhook endpoint.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed/verifiable material (or otherwise cryptographically bind them, e.g. by having the host application independently verify that the `shop` header corresponds to a known/expected tenant before trusting it), rather than relying on the HMAC covering only the raw body while headers dictate identity and dispatch.

### Proof of Concept
1. Attacker registers/installs the target Shopify app on their own shop `attacker.myshopify.com`, triggering a legitimate webhook (e.g. `app/uninstalled`) delivered with a valid `x-shopify-hmac-sha256` computed over some raw body `B`.
2. Attacker captures `(B, hmac(B))`.
3. Attacker POSTs to the app's webhook endpoint with the same raw body `B` and the same `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`).
4. `Utils::HmacValidator.validate` succeeds because it only checks `B` against the shared secret [6](#0-5) .
5. `Registry.process` invokes the handler with `shop: "victim.myshopify.com"` [7](#0-6) , causing the host application to perform shop-scoped actions attributed to a shop the attacker does not own.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
