### Title
Escrow release performs external token/native transfers before decrementing escrow accounting, enabling reentrant double-withdrawal of the same escrow — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.withdraw()` on the Tron deployment transfers escrowed native ETH or ERC20 tokens to the beneficiary via a raw `.call` *before* decrementing the corresponding `_orders[commitment][token]` accounting, violating checks-effects-interactions. This is the code-pattern analog of the Africrypt-class incident hinted at in the report ("funds transferred out and made untraceable") — here the mechanism is a state-update-after-external-call bug that can drain escrowed user/protocol funds if the transfer callback can re-enter before the escrow ledger is updated.

### Finding Description
`withdraw()` is the function that finalizes both cross-chain fills (`RedeemEscrow`) and cross-chain cancellations (`RefundEscrow`/`onGetResponse`) by releasing escrowed input tokens to a beneficiary: [1](#0-0) 

For every token in the withdrawal request, the function only guards against a fully-zeroed escrow slot (`if (_orders[body.commitment][token] == 0) revert UnknownOrder();`), then performs the external transfer (`beneficiary.call{value: amount}("")` for native, or `token.call(...IERC20.transfer...)` for ERC20), and only afterwards executes `_orders[body.commitment][token] -= amount;`. The equivalent same-chain logic in `IntentsBase._withdraw` (used by the non-Tron EVM deployments) does the opposite — it decrements escrow before making the transfer: [2](#0-1) 

The Tron `withdraw()` reverses this order, so the accounting write that should prevent re-entrant re-withdrawal happens only after control has already been handed to the beneficiary (a native-ETH receiver or a token contract executing a `transfer` hook). Because `_filled[body.commitment]` is set at the very top of the function, a second re-entrant call into `withdraw` for the *same* commitment before it returns is only reachable if the same `WithdrawalRequest` can be dispatched again before the outer receipt/duplicate-message guard in the message pipeline records the delivery. `HandlerV2.handlePostRequests` checks `host.requestReceipts(...)` for duplicates and then calls `host.dispatchIncoming(...)` per request, one at a time: [3](#0-2) 

Whether the receipt is written before or after the module callback inside `EvmHost.dispatchIncoming` could not be confirmed from the code excerpts retrieved — I was not able to load the body of `dispatchIncoming` in `evm/src/core/EvmHost.sol` before running out of tool calls, so I cannot conclusively prove a full end-to-end reentrant double-spend through the ISMP delivery path with certainty.

### Impact Explanation
If the receipt is recorded only after the module callback completes (unverified), a malicious beneficiary/token contract could re-enter the message-handling pipeline during the native/ERC20 transfer inside `withdraw()` and cause the same escrow slot to be paid out twice before `_orders[...] -= amount` ever executes, directly draining escrowed user/solver funds — a concrete theft-of-funds bug matching the report's bug class (funds transferred out of custody). Even absent a provably reachable double-call through the ISMP receipt guard, the pattern itself (external call before effects) is a latent reentrancy hazard in a fund-custody function and is inconsistent with the safer ordering used elsewhere in the codebase (`IntentsBase._withdraw`), which is the audited/expected pattern.

### Likelihood Explanation
Medium — exploitation depends on whether `EvmHost.dispatchIncoming` records the request receipt before or after invoking the destination module's `onAccept`/`onGetResponse`. If the receipt write happens first, the outer duplicate-message check blocks a second delivery of the same request and this ordering bug in `withdraw()` is unreachable for a double-spend (though still a code-quality/defense-in-depth issue). I could not confirm this ordering with the tools available before this session ended.

### Recommendation
In `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`, decrement `_orders[body.commitment][token]` (and the transaction-fee entry) *before* making the external native/ERC20 transfer, mirroring the checks-effects-interactions ordering already used in `IntentsBase._withdraw`. Add a `nonReentrant` guard as defense-in-depth, and confirm/verify the exact ordering of receipt recording vs. module callback in `EvmHost.dispatchIncoming` to close out whether this is independently reachable via the ISMP delivery path.

### Proof of Concept
Not fully constructible without confirming `EvmHost.dispatchIncoming`'s receipt-write ordering; the reentrant double-withdrawal would require: (1) a `WithdrawalRequest` with `beneficiary` set to an attacker-controlled contract, (2) that contract's `receive()`/token-transfer hook re-entering the ISMP handler/host to redeliver the same request commitment before its receipt is persisted, (3) causing `withdraw()` to run a second time and transfer the same escrowed amount again prior to either invocation's `_orders[...] -= amount` decrement taking effect.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();

                if (!success) revert TransferFailed();

                ++i;
            }
        }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
