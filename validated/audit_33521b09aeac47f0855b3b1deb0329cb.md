### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC verification to the raw request body only, while the `shop` (tenant identifier), `topic`, and `webhook_id` are read directly from unauthenticated HTTP headers and passed straight through to the app's handler by `ShopifyAPI::Webhooks::Registry.process`. Any unprivileged user who installs the app on their own store can capture a legitimate `(body, hmac)` pair Shopify sends them, then replay that exact body/hmac to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. The signature check still passes because it never covers the header, so the app processes attacker-supplied data under the victim's tenant identity.

### Finding Description
`VerifiableQuery#to_signable_string` is the value that `Utils::HmacValidator.validate` HMACs and compares against the received signature: [1](#0-0) 

For webhooks, this signable string is only `@raw_body` — it does not include the shop domain, topic, or webhook id: [2](#0-1) 

Meanwhile, `shop` is read straight from the (attacker-reachable) HTTP header with no cross-check against anything the HMAC covers: [3](#0-2) 

`Registry.process` validates only the body's HMAC, then forwards the header-derived `shop` (and `topic`) to the app's handler as the authoritative tenant identity for the event, with no additional binding check: [4](#0-3) 

This is the same bug class as the reference report: two values that should advance/verify together (`index` vs `lastBalance` in the original; here, the *authenticated body* vs the *tenant-identifying header*) are allowed to diverge. The equality that should hold is:

`shop_bound_by_hmac == shop_used_for_tenant_dispatch`

but in this code:

`shop_used_for_tenant_dispatch (header, attacker-controlled)` is never checked against anything covered by `shop_bound_by_hmac (nothing — HMAC covers only body)`.

### Impact Explanation
An unprivileged user only needs to be able to install the app on a store they control (a completely normal, unprivileged action) to receive one legitimate `(raw_body, hmac)` pair from Shopify. They can then replay that exact HTTP request to the app's public webhook endpoint, changing only the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to point at any other installed shop. `HmacValidator.validate` still succeeds since it only hashes `raw_body`, and `Registry.process` hands the handler `shop: <attacker-chosen value>` together with the (now cross-tenant) body. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up which merchant's records to update, or to authorize/attribute the update), this enables cross-tenant data corruption/leakage — satisfying the "Critical: cross-tenant access" bar.

### Likelihood Explanation
High. Any user can become an "installer" of the target app on their own store without any special privilege, giving them a validly-signed body for a topic/shape of their choosing (webhook topics/bodies are often predictable, e.g. `app/uninstalled`, `customers/data_request`, or content the attacker themselves triggers on their own store, such as updating their own order/customer data to shape the body). Replaying the request with a different shop header requires no secret material — just a normal HTTP request to the app's already-public webhook receiver URL.

### Recommendation
Bind the shop identity into the value that is HMAC-verified, or otherwise cross-check the header-derived shop against server-side state that isn't attacker-controlled:
- Include `shop-domain` (and ideally `topic`/`webhook_id`) in `to_signable_string`, matching against the same fields the HMAC was computed over on Shopify's side (Shopify's real webhook signature does only cover the body, so this specific field can't be added to the signable string unilaterally) — instead, require host apps to cross-verify the header-derived shop against a known set of currently-installed shop domains before trusting it as a tenant key, and document this requirement prominently in `ShopifyAPI::Webhooks::WebhookMetadata`/`Registry.process`.
- At minimum, add validation in `Registry.process` (or `Request`) rejecting shop domains that aren't in the app's registered/installed-shops list, so a replayed cross-shop body cannot be attributed to a shop the app didn't expect to receive this webhook from.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, which is a normal unprivileged action.
2. Attacker triggers a webhook they control (e.g. updates their own customer record), causing Shopify to POST `body`, `x-shopify-hmac-sha256: HMAC(body)`, `x-shopify-shop-domain: attacker.myshopify.com` to the app's webhook endpoint.
3. Attacker intercepts/records this exact request.
4. Attacker replays the identical `body` and `hmac` header to the same endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `Utils::HmacValidator.validate` in `Registry.process` recomputes `HMAC(body)` using the app's secret and it still matches (body unchanged), so the check passes.
6. `Registry.process` dispatches `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: <attacker's data>, ...)` to the app's handler, which processes attacker-controlled data under the victim tenant's identity.
