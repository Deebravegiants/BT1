### Title
Webhook Shop-Domain Spoofing via HMAC That Only Covers the Body, Not the Shop Header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates its HMAC only over the raw request body, while the `shop` identifier that the application uses to attribute the webhook to a tenant is taken from an unsigned HTTP header. Because the same `api_secret_key` is shared across every shop that has installed the app, an attacker who legitimately installs the app on their own shop can capture a genuinely-signed webhook and replay it against the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop, producing a request that passes HMAC validation but is attributed to the wrong tenant.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is read from a header that is never included in that signable string: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` only checks the HMAC over `to_signable_string` (i.e., the body): [3](#0-2) 

`Registry.process` validates only this body HMAC, then hands the unauthenticated `request.shop` value straight to the app's handler as the tenant identifier: [4](#0-3) 

The equality this design implicitly (and incorrectly) assumes is:

`shop_used_by_handler (request.shop, from unsigned header)` == `shop_the_body_HMAC_actually_authenticates (implicit shop that generated this payload)`

But because `api_secret_key` (the app's `client_secret`) is identical for every shop that has the app installed, any merchant who installs the app can generate an arbitrarily-bodied, validly-HMAC'd webhook of any topic/body they choose (by triggering the corresponding event on their own store), then replay that exact `raw_body` + `hmac` pair to the app's webhook endpoint while substituting `x-shopify-shop-domain` for any other shop name. The library performs no binding between the signed bytes and the header used for tenant attribution, so `HmacValidator.validate` returns `true` for a cross-tenant forged request.

### Impact Explanation
This breaks the tenant isolation boundary: the app will process webhook data (order creation, GDPR/compliance events, app-uninstalled, shop update, etc.) as if it originated from a shop it did not come from. Depending on how the host app uses `WebhookMetadata#shop`, this enables cross-tenant data injection, cross-tenant record corruption, spoofed `app/uninstalled` or `shop/redact` events against a victim shop, or misuse of the victim's stored access token/session when the handler looks up per-shop credentials keyed by `shop`. This satisfies the "cross-tenant access" Critical impact category, since the identity binding between the authenticated payload and the tenant used for authorization/storage lookups is broken.

### Likelihood Explanation
Exploitation requires only unprivileged capability: the attacker installs the app on a shop they control (a normal, allowed action for any Shopify merchant/developer), triggers a webhook event to receive one legitimately signed `raw_body`/`hmac` pair, then sends a normal HTTP POST replay to the app's public webhook endpoint with a different `x-shopify-shop-domain` header value. No `api_secret_key`, access token, or privileged account is needed beyond what any app-installer already has. This is directly reachable through the library's documented `Registry.process` / `Request.new` API as used by host apps.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value verified by the HMAC, or otherwise cryptographically tie the webhook's declared shop to the signing key/context (e.g., look up the expected shop's own per-shop secret if using multiple secrets, or additionally validate that `request.shop` corresponds to a shop actually known/installed for this app before invoking handlers). At minimum, document that `request.shop` is not part of the authenticated payload and must not be trusted for tenant attribution without additional verification (e.g. cross-checking against a known/installed shop list) before use in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (normal merchant action).
2. Attacker triggers a webhook event (e.g., `orders/create`) and captures the raw POST: `raw_body` and header `x-shopify-hmac-sha256` — both are validly generated by Shopify using the app's shared `api_secret_key`.
3. Attacker replays this exact POST to the app's webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` unchanged but setting `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because it only checks the body bytes.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` invokes the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, causing the app to process attacker-controlled webhook content under the victim's tenant identity.
