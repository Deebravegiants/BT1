### Title
Sensitive-tier timelock operations enforce a 12-ledger (~1 minute) delay floor instead of the documented 7-day minimum - (File: contracts/governance/src/constants.rs)

### Summary
The governance timelock classifies admin operations into delay tiers, where `Sensitive` operations are supposed to wait a documented minimum of ~7 days (120,960 ledgers) before they become executable. The on-chain floor constant `TIMELOCK_SENSITIVE_MIN_DELAY_LEDGERS` is set to `12` ledgers, so any scheduled sensitive operation is executable by anyone roughly one minute after it is scheduled — during the audit period this is effectively no delay at all.

### Finding Description
`operation_delay` in `contracts/governance/src/timelock/mod.rs` computes the required delay per tier as `min.max(tier_floor)`:

```rust
DelayTier::Sensitive => min.max(constants::TIMELOCK_SENSITIVE_MIN_DELAY_LEDGERS),
```

The floor constant is defined in `contracts/governance/src/constants.rs:17`:

```rust
// Audit-period value. The target value is 120_960 (about 7 days), set through
// a governance-executed `UpgradeGov`.
pub const TIMELOCK_SENSITIVE_MIN_DELAY_LEDGERS: u32 = 12;
```

The documented target is 120,960 ledgers (~7 days), but the deployed value is 12 ledgers (~1 minute at ~5s ledger close). Worse, `operation_delay` uses `min.max(floor)`, so the *configured* `min_delay` — which `validate_delay_update` (`mod.rs:59-67`) constrains only to `>= current` and `<= TIMELOCK_MAX_DELAY_LEDGERS` — dominates the floor. If `min_delay` is ever set above the floor, sensitive ops wait `min_delay`; but during the audit period the sensitive floor itself is only 12 ledgers, so a sensitive operation scheduled while `min_delay <= 12` becomes ready almost immediately.

Execution is permissionless: `authorize_executor` (`mod.rs:77-82`) performs no auth check when `executor` is `None`, explicitly documenting "anyone may drive execution of a ready op." This mirrors the Bond finding exactly: a documented safety minimum (3-day vesting there, 7-day sensitive delay here) that exists to give participants time to react is under-enforced in code (1 day there, ~1 minute here).

### Impact Explanation
The sensitive delay exists so users can observe a pending high-impact admin operation (parameter changes, oracle reconfiguration, upgrades, collateral factor changes routed through the sensitive tier) and exit the protocol before it executes. With a 12-ledger floor, a sensitive operation scheduled during the audit period can be executed by any unprivileged address within about a minute of being proposed. Users have no practical window to withdraw collateral or repay debt before adverse risk parameter changes take effect, exposing them to liquidation or loss of funds they would have avoided with the documented 7-day notice.

### Likelihood Explanation
The vulnerable state is the default deployment state: the constant is compiled in and the comment confirms the real 7-day floor is only applied later via a separate `UpgradeGov` operation. Any sensitive-tier operation scheduled while `min_delay` is small (e.g., a mis-set or default `min_delay`, since `TIMELOCK_MIN_DELAY_LEDGERS` is only "suggested" and "the contract does not enforce it" per `constants.rs:4-6`) is executable almost immediately by anyone calling execute with `executor: None`.

### Recommendation
Set the audit-period floor to the intended target now rather than deferring it:

```rust
pub const TIMELOCK_SENSITIVE_MIN_DELAY_LEDGERS: u32 = 120_960;
```

Additionally, consider enforcing `TIMELOCK_MIN_DELAY_LEDGERS` as a constructor floor instead of documenting it as merely suggested, since `operation_delay` only ever raises the configured minimum, never lowers a too-small one for the `Standard` tier.

### Proof of Concept
1. Deploy governance with `min_delay = 12` (or any value `<= 12`; the constructor does not enforce `TIMELOCK_MIN_DELAY_LEDGERS`).
2. A proposer schedules any `Sensitive`-tier `AdminOperation`. `operation_delay` returns `12.max(12) = 12` ledgers.
3. After ~12 ledgers (~1 minute), any unprivileged address calls the execute entrypoint with `executor: None`; `authorize_executor` performs no auth check, `require_operation_not_expired` passes, and the operation executes — despite the documented intent that sensitive operations wait ~7 days so users can react.
