### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook by validating only the HMAC of the raw request body, then hands the handler a `shop` value read straight from an unauthenticated header. Because the shop identity is never bound to the HMAC, anyone who can obtain one validly-signed webhook (e.g. from their own store, which is trivial to trigger) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, causing the handler to process the payload as if it belonged to a different merchant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is parsed from the `shopify-shop-domain` / `x-shopify-shop-domain` header independently, with no cryptographic tie to the signature: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which computes the signature only over `to_signable_string` (i.e., the body) and compares it to the `hmac` header: [3](#0-2) [4](#0-3) 

After this check passes, `process` immediately constructs `WebhookMetadata` using `request.shop` — the unauthenticated header value — and forwards it to the app's handler as the shop the event is "for": [5](#0-4) 

The identity binding broken is: `hmac_valid(raw_body, api_secret_key) == true` should imply `shop_header == shop_that_actually_sent(raw_body)`, but the gem only proves `hmac_valid(raw_body, api_secret_key) == true`; it never proves anything about the `shop` field that accompanies that body. Since the app's `api_secret_key` is shared across every shop that installs the app (it's not shop-specific), any attacker who operates (or has previously operated) their own install of the target app can capture a legitimately-signed webhook delivery for their own shop and resend it to the app's webhook endpoint with the `shop-domain` header changed to a victim merchant's domain. The HMAC check still passes because it only covers the body, and the app's handler will act on the payload believing it originates from the victim shop.

### Impact Explanation
This crosses a tenant boundary: an unprivileged party who controls any single installation of the app can inject webhook events that are attributed to a different (victim) merchant. Depending on how the host app's webhook handler uses `data.shop` (e.g., to look up which merchant's session/store to update, to key a webhook-driven cache, or to trigger merchant-specific side effects), this enables cross-tenant data corruption or information disclosure without ever needing the victim's access token or `client_secret`. This matches the "cross-tenant access" criteria for a Critical-impact finding, since the identity binding between HMAC-authenticated bytes and the shop that the payload is attributed to is missing.

### Likelihood Explanation
Exploitation only requires the attacker to have (or briefly install) their own store with the target app, capture one legitimate webhook delivery (trivial — apps typically log or can trigger their own webhook events, e.g., by placing a test order), and replay it with a modified `shop-domain` header to the app's public webhook endpoint. No access token, `client_secret`, or privileged credential is required, and the HMAC check as implemented in this gem provides no defense against it.

### Recommendation
Bind the shop identity to the verified bytes: include the `shop` (and ideally `topic`, `webhook-id`) header values in `to_signable_string`'s signing input alongside the raw body, or have `HmacValidator`/`Registry.process` independently verify that the shop domain in the payload matches a shop the app expects/has an active session for, rather than trusting the raw header as-is. At minimum, document clearly that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant-scoping decisions without additional verification (e.g., cross-checking against a known/expected shop for that endpoint).

### Proof of Concept
1. App developer installs the target Shopify app on their own test shop `attacker.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Attacker triggers that webhook, capturing the full legitimate HTTP request Shopify sends, including a valid `x-shopify-hmac-sha256` header computed over the raw JSON body using the app's real `api_secret_key`.
3. Attacker resends the exact same raw body and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the unchanged raw body) — validation succeeds: [4](#0-3) 
5. `process` builds `WebhookMetadata.new(... shop: request.shop ...)` using the forged `shop-domain` header and invokes the app's handler, which processes the payload as belonging to `victim-shop.myshopify.com`: [3](#0-2)
