### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the `HMAC-SHA256` header against the **raw request body**, using the app's single, shared `Context.api_secret_key`. The `shop` (tenant) identifier that the SDK then hands to the application's webhook handler is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is never included in the signed data. This breaks the intended identity binding: `hmac_valid(raw_body) == true` is treated as proof that `shop_header` is authentic for that body, when in fact `shop_header` can be swapped freely without invalidating the signature.

### Finding Description
`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and compares it to the `hmac` value: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw HTTP body (`@raw_body`), and `hmac` is decoded from the `hmac-sha256` header — nothing about the `shop-domain`, `topic`, or `webhook-id` headers is included in the signed material: [2](#0-1) [3](#0-2) 

`Registry.process` performs the HMAC check and then immediately trusts `request.shop` (parsed straight from the unauthenticated header) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because the app's `client_secret` (`Context.api_secret_key`) is the **same secret for every shop that has the app installed**, any merchant who has installed the app can legitimately receive a real webhook delivery for their own shop — i.e., a genuine `(raw_body, hmac)` pair that passes `HmacValidator.validate`. That merchant can then replay the identical body/HMAC pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (the body and secret are unchanged), so `Registry.process` will dispatch the forged event to the handler with `shop: <victim's domain>`.

The equality that should hold but doesn't:
`shop_used_by_handler == shop_that_the_signature_actually_authenticates`
In reality: `shop_used_by_handler = header_value` (attacker-controlled), while `signature_authenticates = raw_body_only` (shop-independent).

### Impact Explanation
This is a cross-tenant identity-binding break: an attacker who is a legitimate, low-privilege tenant of the app (any merchant who installs it) can forge webhook events that the SDK will accept and label as belonging to an arbitrary other shop, without ever holding that victim's credentials. Depending on how the host application's handlers act on `WebhookMetadata#shop` (e.g. `app/uninstalled`, `shop/redact`, `customers/redact`, `orders/create` used to sync/update per-shop state), this can be used to corrupt or exfiltrate another tenant's data path, trigger uninstall/redaction logic for a shop that never uninstalled, or inject fabricated records attributed to a victim shop — a cross-tenant access impact.

### Likelihood Explanation
High: no secrets need to be recovered or leaked. Any actor who can install the app on their own store (a normal, unprivileged action) automatically obtains valid `(raw_body, hmac)` pairs from real webhook deliveries, since all merchants share the same app `client_secret`. Replaying that pair to the app's public webhook URL with a modified shop header is trivial and requires no interaction with Shopify's authentication systems.

### Recommendation
Do not rely on the `shop` value parsed from the unauthenticated header as the source of truth for which tenant a webhook belongs to. Options:
- Include the shop domain (and topic) as part of the signed payload check, or independently verify that the shop in the header is one for which the host application has an active session/installation before trusting it.
- At minimum, document/require host applications to cross-check `request.shop` against their own list of installed shops before acting on the payload, and consider exposing this check inside `Registry.process` itself rather than leaving the header fully trusted post-HMAC-validation.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (normal, unprivileged onboarding).
2. Shopify sends a real webhook, e.g. `orders/create`, to the app's registered callback URL with headers:
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC over raw_body using app's client_secret>`
   - body: `{...attacker's own order data...}`
3. Attacker captures this exact `(raw_body, hmac)` pair.
4. Attacker sends a new HTTP request to the same webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the (forged) header; `Utils::HmacValidator.validate` still succeeds because only `raw_body` is checked against the shared secret.
6. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker_controlled_body, ...)`, causing the host application to act on forged data as if it originated from `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
