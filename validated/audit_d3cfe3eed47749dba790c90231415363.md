### Title
Backend-controlled signup/validation flags are applied without integrity checks, letting a malicious/compromised management backend bypass user-QR/identity validation and age-gating - ([File: src/config.rs])

### Summary
The reported issue is a class of bug where a privileged party (an "admin") can remotely set configuration values that are trusted unconditionally by client logic, degrading or bypassing security controls. In `orb-core`, the analogous trust boundary is the Orb `Config` object downloaded from the management backend (`src/backend/config.rs`, `src/config.rs`). Several security-relevant boolean/threshold fields — `user_qr_validation_use_full_operator_qr`, `user_qr_validation_use_only_operator_location`, `ignore_user_centric_signups`, `self_serve_ask_op_qr_for_possibly_underaged`, and `child_threshold` — are taken from this backend response and applied directly to the identity-binding and age-verification flow with no bounds or consistency validation.

### Finding Description
`Config::validate()` only checks that `sound_volume <= MAX_SOUND_VOLUME`; no other security-relevant field is validated: [1](#0-0) 

Yet these unvalidated fields directly gate identity-binding logic. `verify_user_qr_code` pulls `user_qr_validation_use_full_operator_qr` and `user_qr_validation_use_only_operator_location` straight from the shared config and forwards them to the backend request that decides whether a scanned user QR-code is valid for this orb/operator session: [2](#0-1) 

The actual query selected is controlled entirely by these two admin-settable booleans — switching between a location-based check, an operator-QR-based check, or a weaker per-user-id-only check with no cross-checking of the operator context: [3](#0-2) 

Similarly, `self_serve_ask_op_qr_for_possibly_underaged` (which controls whether an operator must confirm/scan for a possibly-underaged individual) and `child_threshold` (the underage classification threshold) are both plain backend-supplied values merged into defaults with `unwrap_or`, without any sanity bound (e.g. threshold range) or backend-authenticity binding beyond basic auth of the orb itself: [4](#0-3) [5](#0-4) [6](#0-5) 

This mirrors the reported bug class precisely: config values equivalent to `updateOracle`/`updateRouter`/`withdrawable` are admin-controllable, callable/updatable at any time (`config_update` polls every `CONFIG_UPDATE_INTERVAL`), and consumed without independent validation: [7](#0-6) 

### Impact Explanation
If the management backend is compromised or a malicious insider with backend access pushes a manipulated config, they can:
- Force `user_qr_validation_use_only_operator_location: true` (already the default) or toggle to the weaker `api/v1/user/{id}/status` path (both flags false), reducing the identity-binding check to a bare user-ID lookup with no cross-verification against the actual operator/location context, enabling misattributed or unauthorized signup sessions to be validated as belonging to the wrong operator/session.
- Set `self_serve_ask_op_qr_for_possibly_underaged: false` and/or manipulate `child_threshold` to disable the safeguard that requires operator confirmation for possibly-underaged individuals in self-serve mode, allowing unauthorized/underage signups to proceed without the intended human-in-the-loop check.

This is a concrete unauthorized/misattributed-signup and fraud/age-enforcement-bypass impact, matching the validation criteria.

### Likelihood Explanation
Low, consistent with the original report: it requires a malicious or compromised management-backend operator, since the orb itself has no way to independently validate these specific flags' authenticity or bounds beyond the orb's own auth token used to fetch them.

### Recommendation
- Add explicit validation/clamping in `Config::validate()` (or a per-field validator) for all security-relevant booleans and thresholds (`user_qr_validation_use_full_operator_qr`, `user_qr_validation_use_only_operator_location`, `self_serve_ask_op_qr_for_possibly_underaged`, `child_threshold`), rejecting configs that weaken identity binding/age-gating below a defined minimum-security baseline.
- Avoid letting a single config toggle silently downgrade to the weakest user-validation query path (`api/v1/user/{id}/status`); require an explicit, signed, or multi-party-reviewed change for such downgrades, and log/alert when the validation mode changes.
- Apply defense-in-depth: keep the underage/age-verification decision from being fully determined by a single remotely-mutable boolean and threshold with no local floor/ceiling enforcement.

### Proof of Concept
1. Compromise or gain write-access to the management backend `/api/v1/orbs/{ORB_ID}` config endpoint response.
2. Set `UserQrValidationUseFullOperatorQr: false` and `UserQrValidationUseOnlyOperatorLocation: false` in the response body consumed by `backend::config::request` (`src/backend/config.rs:26-76`).
3. On the next `CONFIG_UPDATE_INTERVAL` poll (`src/brokers/observer.rs:187-205`), the orb adopts this config via `Config::from_backend`, which performs no additional validation of these fields (`src/config.rs:267-271`, `src/config.rs:322-326`).
4. Subsequent signups call `backend::user_status::request` with both flags false, causing validation to fall back to the weakest `api/v1/user/{id}/status` check (`src/backend/user_status.rs:130-133`), independent of the actual operator/session context — enabling misattributed signup validation.
5. Separately, set `SelfServeAskOpQrForPossiblyUnderaged: false` to remove the operator-confirmation safeguard for possibly-underaged individuals in self-serve mode, bypassing that enforcement path entirely.

async fn do_request(
    qr_code: &qr_scan::user::Data,
    operator_data: &OperatorData,
    use_full_operator_qr: bool,
    use_only_operator_location: bool,
) -> Result<Response> {
    let request = if use_only_operator_location {
        super::client()?
            .get(format!("{}/api/v2/session/{}/status", *SIGNUP_BACKEND_URL, qr_code.user_id,))
            .query(&[
                ("lat", operator_data.location_data.session_coordinates.latitude),
                ("lon", operator_data.location_data.session_coordinates.longitude),
            ])
    } else if use_full_operator_qr {
        super::client()?
            .get(format!("{}/api/v2/session/{}/status", *SIGNUP_BACKEND_URL, qr_code.user_id))
            .query(&[("operator_id", &operator_data.qr_code.user_id)])
    } else {
        super::client()?
            .get(format!("{}/api/v1/user/{}/status", *SIGNUP_BACKEND_URL, qr_code.user_id))
    }
    .basic_auth(&*ORB_ID, Some(get_orb_token()?));

    fn config_update(&mut self, observer: &mut Observer) -> Result<()> {
        if self.before_config_update()? {
            match observer.config_update.as_mut().map(future::FutureExt::now_or_never) {
                Some(None) => return Ok(()),
                Some(Some(result)) => result??,
                None => {}
            }
            let config = Arc::clone(&observer.config);
            let ui = observer.ui.clone();
            observer.config_update = Some(tokio::spawn(async move {
                if let Ok(new_config) = Config::download().await {
                    *config.lock().await = new_config;
                    config.lock().await.propagate_to_ui(ui.as_ref());
                }
                Ok(())
            }));
        }
        Ok(())
    }
