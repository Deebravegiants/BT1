### Title
Deposit/Withdraw instructions accept user-specified slippage-protection minimums (`other_amount_min`, `min_coin_amount`, `min_pc_amount`) that are parsed but never enforced on-chain - (File: `program/src/instruction.rs`, `program/src/processor.rs`)

### Summary
The `Deposit` and `Withdraw` instructions expose optional slippage-protection fields that mirror the `minimum_amount_out` / `max_amount_in` protections present in the swap instructions. These fields are unpacked from instruction data but the processor functions (`process_deposit`, `process_withdraw`) never read or check them, so a caller who supplies a non-zero minimum receives no actual protection — mirroring the Keras report's pattern where a security-relevant parameter (`safe_mode`) is accepted by the API but silently has no effect for a given code path, creating a false sense of security.

### Finding Description
`AmmInstruction::unpack` parses an optional `other_amount_min` for `Deposit` and optional `min_coin_amount`/`min_pc_amount` for `Withdraw` when extra bytes are present in the instruction data: [1](#0-0) 

These fields are stored in `DepositInstruction` and `WithdrawInstruction` and are clearly intended as user-supplied minimum-output guarantees, analogous to `minimum_amount_out` in `SwapInstructionBaseIn`, which the swap processors do check: [2](#0-1) 

However, a search of `program/src/processor.rs` for the field names `min_coin_amount`, `min_pc_amount`, and `other_amount_min` returns **zero matches** — `process_deposit` and `process_withdraw` never reference `deposit.other_amount_min`, `withdraw.min_coin_amount`, or `withdraw.min_pc_amount` anywhere in their bodies. The withdraw/deposit flows compute output amounts purely from the current pool ratio via `Calculator::calc_total_without_take_pnl_no_orderbook` and mint/burn LP or transfer vault tokens based on that ratio, with no comparison against any user-supplied minimum: [3](#0-2) [4](#0-3) 

By contrast, the swap processors do enforce the equivalent protections (`minimum_amount_out`, `max_amount_in`) before performing the CPI transfers — showing the codebase is capable of, and normally does, enforce these guarantees, but the guarantee is silently dropped specifically for `Deposit`/`Withdraw`. This is architecturally identical to the Keras bug class: a safety parameter that works for one code path (swap) but is silently ignored for another (deposit/withdraw), with no warning, error, or documentation indicating the discrepancy.

### Impact Explanation
Because Deposit/Withdraw compute amounts strictly from the live pool ratio with no minimum-output enforcement, a user submitting a `Deposit` or `Withdraw` transaction with a non-zero `other_amount_min`/`min_coin_amount`/`min_pc_amount` (reasonably believing this protects them, exactly as `minimum_amount_out` does for swaps) receives no actual on-chain protection. This is exploitable via sandwich attacks: an attacker observes the pending Deposit/Withdraw transaction, front-runs it with a `SwapBaseIn`/`SwapBaseOut` to shift the coin/pc ratio unfavorably, lets the victim's deposit/withdraw execute at the manipulated ratio (silently accepted despite the user's specified minimum), then back-runs with a reverse swap to capture the extracted value. This directly enables theft of user/LP funds through price manipulation that the user believed was prevented by the minimum-amount parameters they supplied.

### Likelihood Explanation
High. Any unprivileged actor can submit ordinary `SwapBaseIn`/`SwapBaseOut` transactions immediately before and after a victim's `Deposit`/`Withdraw` in the same block (classic sandwich pattern), and no special privileges, malicious validator behavior, or off-chain component is required — the sandwiching transactions and the victim's transaction are all standard instructions reachable by any submitter with attacker-chosen accounts and data.

### Recommendation
In `process_deposit` and `process_withdraw`, after computing the actual coin/pc amounts to be deposited/withdrawn (and LP amount minted/burned), explicitly compare against `deposit.other_amount_min` / `withdraw.min_coin_amount` / `withdraw.min_pc_amount` when `Some`, and return an `AmmError` (e.g., a new `ExceededSlippage`/`InvalidInput` variant) if the computed amount is worse than the caller's specified minimum — mirroring the enforcement already present in `process_swap_base_in`/`process_swap_base_out`.

### Proof of Concept
1. Victim submits `Withdraw` with `amount = X` LP tokens and `min_coin_amount = Y`, `min_pc_amount = Z` (nonzero), expecting the transaction to fail if the received amounts fall below `Y`/`Z`.
2. Attacker front-runs with `SwapBaseIn`/`SwapBaseOut` that heavily skews the coin/pc vault ratio in the same slot/transaction bundle.
3. Victim's `Withdraw` executes: `process_withdraw` computes `total_pc_without_take_pnl`/`total_coin_without_take_pnl` from the now-skewed vault balances and transfers proportional amounts to the user — with no code path ever reading `withdraw.min_coin_amount`/`withdraw.min_pc_amount` to reject the transaction, even though the actual amounts fall below `Y`/`Z`.
4. Attacker back-runs with a reverse swap to restore the ratio, pocketing the value extracted from the victim's withdrawal.
5. This is confirmed by the absence of any `min_coin_amount`/`min_pc_amount`/`other_amount_min` reference in `program/src/processor.rs`, despite these fields being explicitly parsed in `program/src/instruction.rs`.
