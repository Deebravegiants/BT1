### Title
Webhook Shop-Domain Header Spoofing via HMAC That Only Covers the Raw Body - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` from an unauthenticated header while the HMAC signature only ever covers the raw request body, so `Registry.process` accepts and dispatches webhook events whose declared tenant (`shop`) is never bound to the cryptographic proof of authenticity.

### Finding Description
The bug class in the referenced report is fees being *acted upon* (recorded) using data that is not properly bound to the state used for the actual health/availability check — an identity/binding mismatch between what is verified and what is used. The structural analog here is the webhook `shop` field: it is used by the handler to make tenant-specific decisions, but it is never part of the signed payload.

`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header, completely outside of the HMAC-covered content: [2](#0-1) 

`Registry.process` validates the HMAC (which only proves the raw body was signed by holder of the app secret) and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler, without any check that `shop` corresponds to the body/topic that was actually signed: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` confirm this: the comparison is strictly `computed_signature` (over `to_signable_string`, i.e. body only) vs. the received `hmac`; `shop` never enters the equality: [4](#0-3) 

Binding that should hold but does not:
`shop` used to authorize/attribute the event == `shop` implicitly certified by the HMAC-signed bytes.
In reality: `shop` used to authorize/attribute the event ⊆ arbitrary attacker-supplied header, while HMAC-signed bytes ⊆ `raw_body` only.

### Impact Explanation
An unprivileged holder of one valid `(raw_body, hmac)` pair for their own shop — which they legitimately receive as an app-installing merchant, without needing the app's `client_secret`/`api_secret_key` — can resend that exact `raw_body` and `hmac` to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a different, victim shop's domain. Because `Utils::HmacValidator.validate` never incorporates `shop` into the signable string, the signature still validates, and `Registry.process` dispatches the handler with `WebhookMetadata.shop` set to the victim's domain. Any host application that uses `data.shop` (a documented, expected field of `WebhookMetadata`) to select which tenant's data to mutate, delete, or read is now acting on attacker-controlled tenant attribution under a check that reported success — a cross-tenant access outcome consistent with the "Critical" bucket in this program.

### Likelihood Explanation
The attacker only needs to be a legitimate (even trial) merchant who installs the app once to receive at least one real webhook delivery, which is an ordinary unprivileged interaction — no `api_secret_key`, access token, or social engineering is required. Replaying an HTTP POST with a modified header is trivial. The only limiting factor is that the replayed `raw_body` content must not itself internally reference/require validation of the shop (topic-dependent), but the vulnerable code path — `Request#shop`, `HmacValidator.validate`, `Registry.process` — imposes no such check itself, so the binding gap exists unconditionally in the gem regardless of topic.

### Recommendation
Include `shop` (and ideally `topic`) inside the HMAC-signable content, or otherwise cryptographically/contextually bind the `shop` header value to the verified body before it is handed to the handler — mirroring the report's mitigation of never trusting an unverified field for a security-relevant decision. Concretely, `Request#to_signable_string` should incorporate the shop-domain header, and/or `Registry.process` should cross-check `request.shop` against an independently trusted value before constructing `WebhookMetadata`.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid_hmac_for_body>`, and some `raw_body`.
2. Attacker captures `raw_body` and `x-shopify-hmac-sha256`.
3. Attacker POSTs to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` ( [5](#0-4) ) succeeds because it only checks the body against the secret.
5. `Registry.process` ( [3](#0-2) ) calls the app's handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the host app to act as if the event pertains to `victim-shop.myshopify.com`.
