### Title
Arbitrary swap-route contracts can inject unauthorized token transfers into the caller's signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral`, `swap_debt`, `multiply`, and related strategy entrypoints accept opaque route bytes and delegate execution to the configured router. Because route-selected venue code can execute beneath the caller's authorization context, a malicious venue can invoke an unrelated `token.transfer(caller, attacker, amount)` that transaction simulation records as a child authorization. If the signed transaction includes that generated tree, the transfer succeeds and steals wallet assets unrelated to the lending operation. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The controller authenticates only the top-level `caller` before executing a strategy. [4](#0-3) 

For a routed swap, the controller grants the router authority for one exact input-token transfer and then invokes `execute_strategy` with caller-supplied route bytes. [5](#0-4) 

That exact controller grant is narrow, but it does not constrain other contract calls made by route-selected code under the caller's top-level authorization. [6](#0-5) 

The router permits payload-selected pool and token addresses rather than enforcing a venue allowlist. [7](#0-6) 

Consequently, an attacker can deploy a route hop that calls `transfer` on any token held by the caller. Simulation records that transfer beneath the caller's `swap_collateral` authorization entry, and enforced authorization accepts it when the signed tree includes the injected child invocation. [8](#0-7) [9](#0-8) 

This is analogous to the Gogs issue's unsafe incorporation of attacker-controlled content into a privileged operation: here, attacker-selected route code injects an additional state-changing invocation into a transaction that appears to be an ordinary collateral swap.

### Impact Explanation
A victim can lose arbitrary wallet balances in tokens that are unrelated to the lending markets and were never supplied to the protocol. [10](#0-9) 

The protocol's measured output, overspend, residual, and final health checks do not bound the unrelated wallet transfer, because that transfer is outside the routed input amount and controller balance accounting. [11](#0-10) [12](#0-11) 

The regression test demonstrates a complete theft of `WALLET_BALANCE` from Alice to an attacker while the malicious swap still returns fair ETH output to Alice's lending account. [10](#0-9) 

### Likelihood Explanation
An unprivileged attacker can deploy the malicious venue contract and construct route bytes naming that contract as a hop. [13](#0-12) [14](#0-13) 

The victim must submit or sign the poisoned authorization tree produced by simulation, which lowers exploitability relative to a fully unauthenticated vulnerability. [15](#0-14) [9](#0-8) 

Nevertheless, ordinary route-generation and simulation workflows can present the extra transfer as implementation detail unless the client explicitly decodes and compares the complete authorization tree. [16](#0-15) 

### Recommendation
Restrict routed execution to governance-approved venue contracts, or encode and validate an allowlisted venue identity for every hop before dispatch.

At a minimum, the controller and router should prevent route-selected code from performing caller-authorized sub-invocations unrelated to the declared route. Clients must continue rejecting any signed authorization tree containing children beyond the single expected input transfer, but relying exclusively on client-side inspection leaves the protocol exposed. [17](#0-16) 

The route decoder should additionally bind token addresses, venue addresses, and expected nested authorization effects before execution, and transactions should revert if execution produces an unexpected authorization child.

### Proof of Concept
1. Alice owns a debt-free lending account with USDC collateral and also holds `77_770_000_000` units of an unrelated wallet token. [18](#0-17) 
2. The attacker deploys `RogueHopPool`, whose `swap` function calls `wallet_token.transfer(alice, attacker, WALLET_BALANCE)`. [19](#0-18) 
3. The attacker supplies route bytes naming that pool while the router otherwise pays fair ETH output for Alice's USDC input. [14](#0-13) 
4. Alice invokes `Controller::swap_collateral(alice, account_id, usdc, SWAP_IN_USDC, eth, route)`. [20](#0-19) 
5. Simulation records the unrelated wallet-token transfer as a child of Alice's `swap_collateral` authorization. [21](#0-20) 
6. If Alice signs the returned tree, the malicious venue transfers her entire unrelated wallet balance to the attacker while the lending swap succeeds and deposits fair ETH collateral. [10](#0-9) [9](#0-8)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),

        sub_invocations: std::vec![stolen_transfer],

    assert_eq!(s.wallet(&s.alice), 0);

pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
