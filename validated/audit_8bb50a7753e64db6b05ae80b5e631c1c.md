## Analysis

The gem's webhook `HmacValidator` verifies the HMAC signature over only the **raw request body**, never the HTTP headers that carry the identity fields (`shop`, `topic`, `webhook_id`, `api_version`). Those header-derived fields are what the `Webhooks::Registry` uses to route and label the payload it hands to the host app's webhook handler.

### Title
Webhook Shop/Topic Identity Spoofing via HMAC Not Covering Headers - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs/verifies only the raw JSON body via HMAC, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers. Because the app's `client_secret` used for HMAC is static per-app (not per-shop, per-topic, or per-delivery), any raw body the attacker can obtain a valid signature for (e.g., from a webhook delivered to their own store) remains validly signed no matter which `shop-domain`/`topic` headers are attached to the replayed request. This breaks the binding: `shop` (and `topic`) dispatched to the handler == `shop` (and `topic`) covered by HMAC bytes — the equality does not hold, since HMAC coverage is `raw_body` only.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

The header accessors for `shop`, `topic`, `webhook_id`, and `api_version` are read straight from attacker-controlled HTTP headers with no cryptographic tie to the signed payload: [2](#0-1) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (i.e., the raw body only) and secure-compares it to the received signature: [3](#0-2) 

`Registry.process` trusts this validation, then dispatches by header-derived `request.topic` and forwards header-derived `request.shop` straight into the `WebhookMetadata` given to the host app's handler: [4](#0-3) 

Because the HMAC secret (`Context.api_secret_key`) is the same for every shop and every webhook topic of a given app, any body+HMAC pair that an attacker can legitimately obtain (e.g., by triggering an event in their own store which installed the target app, or intercepting a webhook they are entitled to receive) remains cryptographically valid when replayed with a *different* `x-shopify-shop-domain` header value and/or `x-shopify-topic` header value pointing at another merchant/shop or another topic. `HmacValidator.validate` never inspects headers, so it passes.

### Impact Explanation
This is a cross-tenant identity-binding break: the shop and topic delivered to the host app's business logic are not the shop/topic actually covered by the cryptographic signature. An attacker with a working installation of the target app (any legitimate merchant/dev account) can:
- Capture one legitimate webhook body+HMAC pair from their own store.
- Replay it to the app's public webhook endpoint with the `shop-domain` header set to an arbitrary victim shop's domain, and/or the `topic` header changed to a different registered topic.
- `Registry.process` will accept it as authentic (HMAC passes) and hand the attacker's body to the host app's handler tagged as belonging to the victim shop (or under a different topic than the body was ever meant for, e.g. relabeling arbitrary JSON as `app/uninstalled` or `shop/redact`).

Depending on how the host app's webhook handlers use `WebhookMetadata#shop`/`#topic` (most do — to look up the tenant record and route business logic), this enables cross-tenant data injection/corruption, forged lifecycle events (uninstall, GDPR redact/request) against a shop the attacker doesn't control, or state confusion between topics — satisfying the "cross-tenant access" Critical bar.

### Likelihood Explanation
Exploitability requires only:
1. The attacker to be any user capable of installing the target app on a store (self-serve, unprivileged relative to the victim tenant) so as to receive one legitimate webhook, and
2. Network access to POST to the app's public webhook endpoint (which is internet-facing by design).

No access token, `client_secret`, or privileged account for the *victim* shop is needed — only knowledge of the victim's `myshopify.com` domain, which is generally guessable/public. This fits the "unprivileged internet user" analog class exactly.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the signed/verified material — i.e., compute/verify the HMAC over a canonical string that binds the header claims to the body (this generally has to be a documented API contract change with Shopify's side, or minimally: cross-check webhook delivery IDs / topics against server-tracked expected values before trusting `request.shop`). At minimum, update `lib/shopify_api/webhooks/registry.rb`/`request.rb` documentation to make explicit that `shop`, `topic`, `webhook_id`, `api_version` are **not** authenticated by `HmacValidator.validate`, and host apps must not treat them as trusted tenant identifiers without additional verification (e.g., correlating `webhook_id` against a store of previously seen IDs per expected shop/topic).

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker-shop.myshopify.com`; trigger any webhook event (e.g., `orders/create`) to capture a legitimate `(raw_body, x-shopify-hmac-sha256)` pair.
2. Replay the exact same HTTP POST to the app's webhook endpoint, but replace:
   - `x-shopify-shop-domain: attacker-shop.myshopify.com` → `x-shopify-shop-domain: victim-shop.myshopify.com`
   - optionally `x-shopify-topic` to a different registered topic.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which validates successfully because it only hashes `@raw_body`, unaffected by the header changes.
4. The host app's handler receives `WebhookMetadata.new(topic: <forged>, shop: "victim-shop.myshopify.com", body: <attacker body>, ...)` and processes it as an authentic event from the victim shop.
