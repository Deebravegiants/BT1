### Title
Webhook shop/topic headers are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs (and `HmacValidator` verifies) only the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and attribute the webhook are read directly from unauthenticated HTTP headers. This breaks the intended binding `hmac_signed_bytes == bytes_the_handler_trusts_as_tenant_identity`, allowing a party who can obtain any one valid `(body, hmac)` pair for the shared app secret to replay it with an arbitrary `shop-domain` header and have the handler process it as if it came from a different (victim) shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors read straight from HTTP headers, which are never part of the signed payload: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. against the raw body — never against the headers: [3](#0-2) 

`Registry.process` trusts `request.topic` for handler dispatch and forwards `request.shop` (an unsigned header) straight into `WebhookMetadata`, which the app's handler treats as the authoritative tenant identity: [4](#0-3) 

Because every shop that installs the same app shares the same `api_secret_key`, an attacker can install the app on their own store (a normal, unprivileged action), capture a genuinely-signed `(raw_body, x-shopify-hmac-sha256)` pair delivered to their own webhook endpoint, and replay that exact body/HMAC to the app's public webhook endpoint while substituting `x-shopify-shop-domain` (and optionally `x-shopify-topic`) with a victim shop's domain. `HmacValidator.validate` still returns `true` because the signature only ever covered the body, so `Registry.process` dispatches the payload to the handler labeled with the attacker-chosen `shop`/`topic`.

This is the exact analog called out in scope: "a shop authenticated versus the shop stored as a session key" / "a field acted on but not covered by the HMAC" — the equality that should hold is `hmac_verifies(body) == body_and_shop_are_bound`, but in this code `hmac_verifies(body)` is independent of `shop`.

### Impact Explanation
If the host application's webhook handler uses `WebhookMetadata#shop` to select the tenant record to update (a very common pattern — e.g., updating orders/customers/inventory keyed by `shop`), an attacker can inject attacker-controlled webhook data attributed to an arbitrary victim shop domain, causing cross-tenant data confusion/corruption without ever possessing that victim's credentials. This matches the Critical impact category "cross-tenant access."

### Likelihood Explanation
Exploitation requires only:
1. The ability to install the target app on any Shopify store (including a free/dev store the attacker controls) to receive a legitimately HMAC-signed webhook.
2. The ability to send an arbitrary HTTP POST with custom headers to the app's public webhook endpoint (a capability every unprivileged internet user has, since that endpoint must be internet-reachable to receive Shopify's webhooks).

No access token, `api_secret_key`, or privileged account is required — the attacker never needs to know the secret, only to replay a validly-signed body under different headers.

### Recommendation
Include the tenant-identifying and routing fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed/verified material, or otherwise independently verify that the `shop-domain` header matches an expected/allow-listed value tied to the session that registered the webhook, before trusting it for dispatch or data attribution. At minimum, document prominently that `request.shop`/`request.topic` are unauthenticated and must not be used as the sole tenant key without additional verification (e.g., cross-checking against the app's own webhook registration records for that specific topic id).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a real webhook, e.g. for `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (a valid HMAC of `B` under the shared `api_secret_key`).
2. Attacker sends a POST to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - `x-shopify-hmac-sha256: H` (unchanged, still validates because `to_signable_string` only covers the body)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (changed)
   - `x-shopify-topic: orders/create` (unchanged or changed to any registered topic)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — this returns `true` since it only checks `B` against `H`.
4. The registered handler for `orders/create` is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the host application to process attacker-supplied data under the victim shop's identity. [5](#0-4) [6](#0-5)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
