Confirmed: `Webhooks::Request` (path: `lib/shopify_api/webhooks/request.rb`) implements `VerifiableQuery` with `to_signable_string` returning only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only the HMAC-over-body via `Utils::HmacValidator.validate(request)` and then forwards `request.shop` (header value) into the handler as the tenant identity, with no cross-check against anything inside the signed body [3](#0-2) .

### Title
Webhook tenant identity (`shop` header) is not covered by HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body [1](#0-0) . The `shop` value that identifies which merchant/tenant the event belongs to is read from the `x-shopify-shop-domain` HTTP header, which is never included in the HMAC-signed material [4](#0-3) .

### Finding Description
`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares it against the `hmac` header using `OpenSSL.secure_compare` [5](#0-4) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop` accessor used downstream for tenant attribution is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely outside the signed bytes [4](#0-3) .

`Registry.process` raises only if the HMAC over the body fails; once that check passes, it hands `request.shop` directly to the application's webhook handler as the authenticated tenant identifier, with no binding between the verified body and the claimed shop: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [6](#0-5) .

This breaks the intended identity binding: `hmac_verified(body) == true` is treated as equivalent to `shop_header == true_origin_shop`, but the equality that is actually proven is only `hmac_verified(body)`, independent of `shop_header`. Any actor who can obtain one genuine, validly-signed webhook body (e.g., by installing the app on their own shop and receiving a real webhook for it) can replay that exact body to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` header value. The HMAC still validates (it only covers the body), but the application will process the event as if it originated from the victim shop named in the header.

### Impact Explanation
This crosses a tenant boundary: an unprivileged actor who legitimately controls one shop can cause the receiving application to attribute webhook data (order/customer/app-uninstall/etc. events) to an arbitrary other shop domain of their choosing, since the gem does not bind the `shop` field to the HMAC-verified content. Depending on how the host application uses `WebhookMetadata#shop` (e.g., as a lookup key to load/mutate that tenant's session or data), this can lead to cross-tenant data corruption or unauthorized actions performed against another merchant's account — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitability requires only the ability to send arbitrary HTTP requests to the app's public webhook endpoint with attacker-chosen headers plus a body/HMAC pair the attacker can legitimately obtain (e.g., from their own shop installation, or any topic whose body content is attacker-influenceable). No access token, `api_secret_key`, or privileged account is required — the attacker only needs to be an ordinary merchant/user of the app on any shop.

### Recommendation
Bind the `shop` (and ideally `topic`) claim to the HMAC computation, or otherwise cryptographically tie the header-derived tenant identity to the signed payload before trusting it (e.g., verifying the target shop against records already associated with the specific triggering resource/topic in the raw body, or including the header values in the signable string if Shopify's signing scheme is extended to support this). At minimum, document that `Webhooks::Request#shop` is unauthenticated and instruct consuming applications to independently corroborate it against body contents where topic semantics allow.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) to capture a genuine `raw_body` and its valid `x-shopify-hmac-sha256` header.
2. Replay the exact same HTTP request to the app's webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` unchanged, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks the body [7](#0-6) .
4. `Registry.process` proceeds and calls the handler with `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing the host application to process attacker-supplied data under the victim's tenant identity.
