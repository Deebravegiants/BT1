This confirms the root cause. `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `HmacValidator.validate` only authenticates the JSON body bytes against the app's shared `api_secret_key` [2](#0-1) . The `shop`, `topic`, and `webhook_id` values that `Registry.process` hands to the handler as the tenant identity come straight from unauthenticated HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`) [3](#0-2)  and are never included in the signed string, then passed on unchanged: [4](#0-3) .

### Title
Webhook tenant identity (`shop`/`topic`/`webhook_id`) is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-ing only the raw request body, while the `shop-domain`, `topic`, and `webhook-id` values used by application code to route/act on the webhook are taken from plain HTTP headers that are excluded from the signature. Since Shopify apps use one shared `client_secret`/`api_secret_key` across every merchant that installs the app, any merchant who installs the app can capture a genuinely-signed webhook delivered for their own shop and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header swapped to a victim shop, while the HMAC still validates successfully.

### Finding Description
`Request#to_signable_string` is defined as simply `@raw_body` [1](#0-0) . `HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over exactly that signable string and compares it to the `hmac` header value [2](#0-1) . Nothing in the signed material binds the `shop`, `topic`, or `webhook_id` accessors — all three are parsed straight from attacker-controllable headers [3](#0-2) .

`Registry.process` trusts these unauthenticated fields directly: after the HMAC check passes, it dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` to the registered handler [4](#0-3) . The equality the library should be enforcing is: *shop that produced the signed bytes == shop the handler is told the data belongs to*. That equality is broken because only the body contributes to the signed bytes, and `api_secret_key` is the single, non-shop-specific secret configured for the whole app (`Context.api_secret_key`), so it cannot itself distinguish which shop generated a given signature.

Concretely, a malicious merchant who has installed the target app:
1. Triggers an event in their own store, causing Shopify to deliver a legitimately HMAC-signed webhook (body `B`, valid `hmac` for `B`, `x-shopify-shop-domain: attacker-shop.myshopify.com`).
2. Captures that request and replays it to the app's public webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`), leaving body `B` and its `hmac` untouched.
3. `HmacValidator.validate` still succeeds because it only re-hashes `B` [5](#0-4) .
4. `Registry.process` looks up the handler by `request.topic` and invokes it with `shop: request.shop` set to the victim's domain [4](#0-3) .

Any host application logic that uses the `shop` field from `WebhookMetadata` to select which tenant's data to read/write (a common, expected usage pattern for multi-tenant Shopify apps) will act on the victim tenant using attacker-supplied body content.

### Impact Explanation
This breaks the shop-authentication boundary that HMAC validation is meant to guarantee, letting one merchant forge apparently-legitimate webhook events for a different, unrelated merchant (cross-tenant). Depending on how the host app consumes `WebhookMetadata#shop`/`#body`, this can corrupt or fabricate a victim shop's data (e.g. order/fulfillment/inventory state), or trigger privileged side effects (e.g. app data resets, redaction flows) attributed to the wrong tenant — a cross-tenant access impact.

### Likelihood Explanation
Exploitability requires only that the attacker be able to install the app on their own shop (an unprivileged, self-service action for any Shopify merchant) and be able to send arbitrary HTTP requests to the app's public webhook endpoint — no access token, `client_secret`, or privileged account is needed. The only "special" knowledge required is the target's shop domain, which is typically public.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) in the signed material used for `to_signable_string`, or otherwise cross-check `request.shop` against a value that is itself authenticated (e.g. bind the webhook registration/callback URL per shop, or require the caller to additionally supply the shop as part of a signed, per-shop secret/lookup) before trusting it in `WebhookMetadata`. At minimum, document clearly that `request.shop` is unauthenticated and must not be used as a sole tenant-selection key without additional verification.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the target app,
# so Shopify legitimately signs webhooks with the app's shared api_secret_key.
raw_body = '{"id": 1, "note": "forged"}'
hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# Attacker replays the captured request, only changing the shop-domain header:
forged_headers = {
  "x-shopify-topic" => "orders/updated",
  "x-shopify-hmac-sha256" => hmac,          # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # swapped
  "x-shopify-webhook-id" => "attacker-supplied-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC check passes (only raw_body is verified), handler receives
#    WebhookMetadata(shop: "victim-shop.myshopify.com", body: {"id"=>1,"note"=>"forged"}, ...)
```
