### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop` (and `topic`/`webhook-id`) values consumed by `Registry.process` are taken from unauthenticated HTTP headers. This breaks the identity binding `HMAC-verified-bytes == shop-attributed-to-request`, letting an attacker who can obtain any one legitimately-signed webhook body (e.g. from their own shop's install of the app) replay it with a forged `shop-domain` header pointing at a victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature purely from `verifiable_query.to_signable_string`. For webhooks this is defined as: [1](#0-0) 

which returns only `@raw_body`. None of the Shopify headers, including `shop`, are part of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC over the request and, once it passes, unconditionally trusts `request.shop` (derived from the header) to attribute the event to a tenant and dispatch it to the handler: [3](#0-2) 

Because the api_secret_key is shared across every shop that has the app installed, any merchant who installs the public app on their own store will legitimately receive webhook deliveries signed with that same shared secret. Since the header block (topic/shop-domain/webhook-id) is outside the signed bytes, that merchant can resend the exact same raw body to the app's webhook endpoint while substituting the `shop-domain` header (and optionally `topic`/`webhook-id`) for a victim shop. The signature check still succeeds because it only re-hashes the untouched raw body, so `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true`, and the handler is invoked believing the event originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: an event that is only proven to have originated from *a* shop known to Shopify's servers (the attacker's own shop) is delivered to the host application's handler tagged as belonging to *any shop the attacker chooses*. If the host application (following this library's documented `WebhookMetadata.shop` contract) uses that shop value to select the tenant's stored session/access token or otherwise perform tenant-scoped effects, the attacker can trigger cross-tenant processing/actions using a victim shop's identity without ever needing that shop's credentials.

### Likelihood Explanation
Any unprivileged internet user can install a public embedded app on a free/dev store, thereby legitimately receiving HMAC-signed webhook deliveries for arbitrary payload content they can influence indirectly (e.g. by taking actions in their own store), then replay the raw body against the shared endpoint with a rewritten `shop-domain` header. No access token, `client_secret`, or privileged account for the victim shop is required.

### Recommendation
Bind the tenant-identifying header(s) into the material that is HMAC-verified (e.g. include `shop`, `topic`, and `webhook-id` in `to_signable_string`, or separately require that `request.shop` matches a shop already known/authorized for the currently active session before dispatching to a handler), so the shop attribution cannot be forged independently of the signed body.

### Proof of Concept
1. Install the target public app on an attacker-controlled shop `attacker.myshopify.com`; wait for/trigger a webhook delivery, capturing the raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B`, computed with the app's shared secret).
2. Replay a request to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only re-hashes `B` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) and processes the attacker-supplied body as if it came from the victim's shop.
