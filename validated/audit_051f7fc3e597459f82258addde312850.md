### Title
`PoaBridge.describeWithdrawal` misreports withdrawal status/txHash for batched same-token withdrawals - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
When a single NEAR intents transaction contains two or more POA-bridge withdrawals of the same token (`nep141:<same>`) to different destination addresses, `findMatchingWithdrawal` matches API results only by `nep141:<near_token_id>`, ignoring `WithdrawalIdentifier.index`/destination/amount. Both per-index watchers therefore receive the same (first-matching) withdrawal record, so the SDK can report `completed` with another withdrawal's `txHash` for an index whose actual destination transfer has not finalized.

### Finding Description
The broken equality: for `watchWithdrawal({ wid })` with `wid.index = i`, the returned `(status, txHash)` should correspond to the `i`-th withdrawal the user signed for that route (i.e., the withdrawal to `withdrawalParams[i].destinationAddress`/amount). Instead, both sides only agree on `assetId`.

Code path:
- `createWithdrawalIdentifiers` in [1](#0-0)  assigns a per-route `index` to each withdrawal in the batch but keeps them all pointed at the same `intentTx` (same NEAR tx hash).
- `PoaBridge.describeWithdrawal` in [2](#0-1)  queries `getWithdrawalStatus({ withdrawal_hash: args.tx.hash })` - the same tx hash for every index in the batch - and then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`.
- `findMatchingWithdrawal` in [3](#0-2)  matches purely by `nep141:<near_token_id> === assetId` and returns the first array match, with an explicit code comment admitting: "multiple withdrawals of the same token in a single transaction are not supported."

Exploit flow: an integrator/user submits `withdrawalParams: [{assetId: "nep141:X", destinationAddress: A}, {assetId: "nep141:X", destinationAddress: B}]` in one call. `watchWithdrawal` is invoked twice (index 0 for A, index 1 for B), both polling the same `tx.hash`. Once the POA API reports the withdrawal to `A` as `COMPLETED`, `findMatchingWithdrawal` returns that same record for *both* index-0 and index-1 queries (since the search does not use `index`, amount, or destination address to disambiguate), so index 1 (destined for `B`) is also reported `completed` with `A`'s `transfer_tx_hash`, even though `B`'s transfer may still be pending or fail.

Existing guards (`validateAddress`, `compareAddresses`, `validateWithdrawal`, `supports()`, `assert` checks) operate on withdrawal creation/validation, not on the post-submission status-matching logic, so none of them detect or prevent this mismatch.

### Impact Explanation
An integrator that keys off `watchWithdrawal`'s resolved `(status, txHash)` per index to release funds, mark an off-chain ledger entry as settled, or refund a customer, can be told that withdrawal `B` completed using withdrawal `A`'s transaction hash before `B`'s destination transfer is final. This is a status/hash misreport that can cause an integrator to credit or refund twice, or to under-detect a failed/pending withdrawal - matching the "High" impact category. This is repeatable on every batch containing ≥2 withdrawals of the same token in one call.

### Likelihood Explanation
Preconditions are trivial and fully attacker/user-controlled: submit a batch (`withdrawalParams[]`) with two entries sharing the same `nep141:<token>` `assetId` but different destination addresses/amounts - a legitimate, expected use case (batching withdrawals of the same token to multiple recipients), not a crafted edge case. No privileged access, malicious relayer, or RPC compromise is required; the SDK's own documented code comment acknowledges the limitation, confirming it is a known, reachable gap rather than a theoretical one.

### Recommendation
Disambiguate matches beyond `assetId`: match POA withdrawal records to `WithdrawalIdentifier`s using additional discriminating fields (e.g., destination address/amount, or the order of appearance when combined with amount-based sorting as the code comment suggests), and until POA API surfaces a per-withdrawal identifier, reject or serialize (force sequential submission/wait) same-token batched withdrawals in `createWithdrawalIdentifiers`/`createWithdrawalCompletionPromises` rather than allowing concurrent ambiguous status polling.

### Proof of Concept
Vitest plan (mock only the POA HTTP client):
1. Mock `poaBridge.httpClient.getWithdrawalStatus` to return `{ withdrawals: [ { status: "COMPLETED", data: { near_token_id: "X", transfer_tx_hash: "hashA" } } ] }` (only withdrawal A has landed; B has not yet been indexed/returned).
2. Call `describeWithdrawal` twice: once with `wid.index = 0` (params for destination A) and once with `wid.index = 1` (params for destination B), both sharing `assetId: "nep141:X"` and the same `tx.hash`.
3. Assert the broken equality: both calls return `{ status: "completed", txHash: "hashA" }`, i.e., index 1 (destination B) incorrectly reports `hashA` (belonging to destination A) as its completion hash, violating the invariant that index `i`'s result must correspond to the `i`-th signed withdrawal's own destination transfer.
4. Extend with `sdk.createWithdrawalCompletionPromises` end-to-end, asserting `promises[1]` resolves to `{ hash: "hashA" }` even though the underlying transfer to `B` never appeared as completed in the mocked API response.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

		args: WithdrawalIdentifier & { logger?: ILogger },

		// Response list is unsorted, so we match by assetId instead of index

			args.withdrawalParams.assetId,

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",

		};

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
