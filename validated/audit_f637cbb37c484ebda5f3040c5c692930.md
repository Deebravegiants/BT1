## Analog Vulnerability Found

### Title
`pallet-hyper-fungible-token::on_accept` can convert a valid incoming transfer to zero local balance and mint/transfer nothing, permanently destroying the sender's bridged funds - (File: `modules/pallets/hyper-fungible-token/src/module.rs`, `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` converts an ERC20-denominated incoming amount to the local asset's balance denomination via `convert_to_balance`, which performs a plain integer division with no minimum-output check. [1](#0-0)  When the local asset's decimals are smaller than the EVM token's decimals (a very common configuration, e.g. local=6, EVM=18), any incoming amount smaller than the truncation threshold silently converts to `0` and is minted/transferred as `0` — while the tokens were already burned/escrowed on the source EVM chain and the message is recorded as successfully delivered (not eligible for timeout refund).

### Finding Description
`convert_to_balance` divides the incoming `U256` value by `10^(erc_decimals.saturating_sub(local_decimals))` and parses the string result with no check that the result is non-zero: [2](#0-1) 

`on_accept` calls this helper to compute `amount`, then unconditionally mints (non-native asset) or transfers from escrow (native asset) to the beneficiary using that possibly-zero `amount`, with no floor/zero guard before proceeding: [3](#0-2)  

This is reachable by any unprivileged user: a `HyperFungibleToken`/`WrappedHyperFungibleToken` EVM contract on the source chain burns/escrows the sender's tokens and dispatches a POST request with `message.amount` denominated in the source chain's ERC20 decimals: [4](#0-3) . Any relayer can then deliver the proof, triggering `on_accept` on the pallet. If `message.amount` is smaller than `10^(erc_decimals - local_decimals)`, the destination mint/transfer is for `0`, but the request is treated as successfully delivered — `Ok(...)` is returned and `TokenReceived` is emitted with `amount: 0`: [5](#0-4) . Because the request was accepted (not timed out), `on_timeout`'s refund path is never triggered, so the sender's original burned/escrowed tokens on the EVM side are never recovered.

This exactly matches the reported bug class: MainVault.deposit converts a deposit to shares via an exchange-rate division with no check that the resulting shares are non-zero, silently burning the depositor's funds. Here, the same pattern of "divide-then-use-with-no-zero-check" appears in `convert_to_balance`/`on_accept`, and the effect is identical: the user's real value is destroyed with no minted/transferred equivalent and no path to recovery.

### Impact Explanation
Any user who bridges a token amount below the decimals-truncation threshold from an EVM chain to this pallet's chain has their tokens burned/locked on the source chain but receives nothing on the destination — a silent, permanent loss of funds. Because `on_accept` succeeds (rather than reverting or timing out), the standard timeout-refund mechanism never engages, so there is no recovery path. This is a concrete permanent loss of user funds satisfying the Medium-severity bar of the analog report.

### Likelihood Explanation
Decimal mismatches between EVM tokens (commonly 18 decimals) and substrate assets (commonly 6, 10, or 12 decimals) are the normal configuration for this pallet, per the `Precisions` storage design intended specifically to handle this scaling. [6](#0-5)  Any user sending a small/dust amount, or making an off-by-decimals unit mistake in the frontend/SDK, will trigger this truncation. No privileged role, race condition, or malicious actor is required — a normal single-transaction transfer suffices.

### Recommendation
In `convert_to_balance` (or immediately after calling it in `on_accept`/`on_timeout`), reject (return an error / cause the request to fail so it can time out and refund the sender) whenever the input `value` is non-zero but the converted local `amount` is zero. This mirrors the standard ERC-4626 zero-shares guard and ensures dust-sized transfers either round up to a minimum unit or fail cleanly, preserving the sender's ability to recover funds via the existing timeout/refund mechanism.

### Proof of Concept
1. Register a token where `local_decimals = 6` and `erc_decimals = 18` in `Precisions`.
2. On the source EVM chain, call `HyperFungibleToken.send` with `amount = 1` (1 wei of an 18-decimal token) targeting this pallet — the EVM contract burns the sender's 1 wei and dispatches the POST request.
3. A relayer delivers the request; `on_accept` runs `convert_to_balance(1, 18, 6)` → `1 / 10^12 = 0` → `"0"` → `amount = 0`.
4. The pallet mints/transfers `0` to the beneficiary and emits `TokenReceived { amount: 0, .. }`, returning `Ok(...)` — the request is marked delivered.
5. `on_timeout` is never invoked (the request succeeded), so the sender's 1 wei burned on the EVM side is never refunded and no equivalent value is ever created on the destination chain.

	value: U256,
