### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are not covered by the HMAC signature, allowing cross-tenant identity spoofing of processed webhooks - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying field `shop` exclusively from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, while `Utils::HmacValidator.validate` only verifies the raw request body against the `hmac-sha256` header. The `shop` value that the host application receives via `WebhookMetadata` is therefore not bound by the same HMAC that authenticates the payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate`/`validate_signature` compute and compare the HMAC solely over that signable string [2](#0-1) . Meanwhile `Request#shop` (and `topic`, `webhook_id`, `api_version`) are read directly from request headers with no cryptographic binding to the signed body [3](#0-2) .

`Registry.process` validates only `Utils::HmacValidator.validate(request)` and then immediately trusts `request.shop` as the tenant identity, passing it straight into `WebhookMetadata` for the handler to act on: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) . Because the header is outside the signed material, the equality the system implicitly relies on — "the `shop` value verified by the HMAC" equals "the `shop` value the handler uses to determine which tenant's data to act on" — does not actually hold. The HMAC only proves "this body was signed by the secret", not "this body came for shop X".

This is the same identity-binding class as the reported bug: an operative field (there, `decimals`; here, `shop`) is trusted/acted upon without being covered by the authoritative check (there, the token's own `decimals()`; here, the HMAC signature).

### Impact Explanation
An attacker who legitimately controls one shop/app-installation can capture a real webhook delivery for their own store (valid body + valid HMAC, since the secret is shared per app not per shop) and replay it against the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. `HmacValidator.validate` will still pass, because it never inspects the header. If the host application uses `WebhookMetadata#shop` (as documented/intended by this gem) to look up the shop's session, store record, or tenant-scoped data, the attacker can inject events that get attributed to — and processed against — a different tenant's data. This crosses a tenant boundary using only a spoofed header, matching the "cross-tenant access" High/Critical impact class in scope.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one legitimately-signed webhook body/HMAC pair, which any merchant who installs the app (an unprivileged, self-service action) can obtain by triggering a webhook-eligible event on their own store. No access token, `client_secret`, or privileged account is required — only normal use of the app as an installing merchant, plus the ability to POST an HTTP request with modified headers to the app's public webhook endpoint.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` values inside the signed material used by `to_signable_string`, or otherwise cryptographically bind them to the body before trusting them (e.g., canonicalize header + body into the HMAC input, consistent with how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` together with `code`/`state`/`timestamp`) [5](#0-4) . At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must be cross-checked against an independently-verified tenant record before being used for data access.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g., `orders/create`) to receive a legitimately signed delivery: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for secret), header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Replay the exact same body `B` and `Hmac-Sha256: H` to the app's public webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` in `Registry.process` recomputes the HMAC over `B` only [6](#0-5) , which still matches `H`, so validation passes.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` and processes attacker-controlled data as if it originated from the victim's shop.
