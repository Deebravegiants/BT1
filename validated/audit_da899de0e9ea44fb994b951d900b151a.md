### Title
Raw private key material exposed to pluggable asset-library adapters instead of a restricted signer interface - (File: features/tx-signer/src/module/interfaces.ts)

### Summary
The `@exodus/keychain` module is explicitly documented as a "walled garden" that should prevent private key material from escaping its boundary, exposing only `KeyIdentifier`-scoped signing operations. However, the transaction/message signing interfaces still support an escape hatch where raw `privateKey` bytes are optionally handed to pluggable per-asset "adapters" (`asset.api.signTx` / `asset.api.signMessage`), which are third-party asset-library code selected dynamically via the `assetPlugins` adapter map.

### Finding Description
`@exodus/keychain`'s own README states the exact architectural risk analogous to the MetaSwap report: "Private key material is passed directly to asset libraries which can contain code by third party developers" [1](#0-0) . This is not purely historical — the current `AssetSignTx` type signature still carries an optional raw `privateKey: Buffer` field alongside the safer `signer` object: [2](#0-1) . Similarly, `asset.api.signMessage` accepts an optional raw `privateKey: Bytes` in addition to a `signer` [3](#0-2) .

Asset implementations ("adapters" in the MetaSwap-analog sense) are registered dynamically through the `assetPlugins` map, e.g. `bitcoin`, `ethereum`, `solana` from `@exodus/bitcoin-plugin`, `@exodus/ethereum-plugin`, `@exodus/solana-plugin` [4](#0-3) . Just as MetaSwap's adapters could intercept fund approvals because the interface let them access balances directly, a newly added/buggy/malicious asset plugin that opts to consume the `privateKey` parameter (instead of exclusively using `signer.sign`) gains direct access to raw key material for the wallet account being used, rather than being constrained to opaque sign/getPublicKey operations mediated by the keychain.

The preferred, safer pattern (analogous to the MetaSwap `Spender` delegatecall fix) is `SeedBasedTransactionSigner#createSigner`, which only ever passes a `signer` object exposing `sign`/`getPublicKey` methods backed by `keychain.signBuffer`/`keychain.getPublicKey`, never the raw key [5](#0-4) . But the type contract (`AssetSignTxParams.privateKey`) still permits the unmediated path, and the keychain README confirms this gap is a known, unresolved limitation on the roadmap, not yet eliminated.

### Impact Explanation
If any registered asset plugin (including third-party or newly-added ones, mirroring "a new malicious adapter" in the MetaSwap report) uses the `privateKey` parameter path instead of the `signer` abstraction, it obtains direct access to a user's raw private key for that asset/account. This is a direct wallet-compromise vector: a compromised or malicious asset-plugin dependency could exfiltrate raw private keys instead of only being able to request signatures.

### Likelihood Explanation
Likelihood is moderate: the `privateKey` field is declared optional in the type interfaces and is not the primary path used by `SeedBasedTransactionSigner`/`SeedBasedMessageSigner` today (both construct a `signer` object) [6](#0-5) , so the escape hatch requires either a legacy caller or an asset plugin/adapter that decides to consume `privateKey` directly. The keychain package README itself flags this as an acknowledged, unresolved architectural limitation, indicating the surface still exists in production code paths that supply this parameter.

### Recommendation
Follow the same mitigation pattern used in the MetaSwap fix: eliminate any code path that hands raw `privateKey` bytes to asset-plugin code, and require all signing to flow exclusively through the `signer.sign`/`signer.getPublicKey` mediated interface. Remove `privateKey` from `AssetSignTxParams` and `signMessage` options, refactor any remaining asset plugins that consume it, and enforce (e.g., via lint rule or runtime assertion) that plugins cannot receive raw key material — consistent with the keychain README's stated roadmap goal.

### Proof of Concept
Not applicable in the traditional sense (no test harness in scope demonstrates exploitation), but the codebase evidence supporting the vulnerable code path is:
1. `AssetSignTxParams` type declares `privateKey?: Buffer` as a legitimate parameter alongside `signer` [7](#0-6) .
2. `signMessage` asset API type declares `privateKey?: Bytes` as a legitimate parameter alongside `signer` [8](#0-7) .
3. Asset plugins are pluggable/dynamically registered adapters [4](#0-3) .
4. The keychain module's own documentation acknowledges this exact risk as unresolved [9](#0-8) .

# `@exodus/keychain`

The keychain is a module designed to work more securely with private key material. It can be compared with a walled garden from which private keys should not escape. All operations using private keys, such as signing and encryption data should be executed within the module, with `KeyIdentifier`s used to specify which key to use for which operation. Notice the "should," as we're not quite there yet.

In its current state, this library aims to provide a good interface for working with cryptographic material. However, it has some security limitations, which are on our roadmap to address:

- Private key material is passed directly to asset libraries which can contain code by third party developers. This is on our roadmap to eliminate by refactoring asset libraries to accept signing functions instead of keys.
- Private keys _can_ be exported, via `keychain.exportKey`
- `keychain.removeAllSeeds()` does not guarantee that private keys get completely cleared from memory

  #createSigner({
    seedId,
    getDefaultKeyIdentifier,
  }: {
    seedId?: string
    getDefaultKeyIdentifier: () => KeyIdentifier
  }) {
    const getPublicKey = async ({
      keyId = getDefaultKeyIdentifier(),
    }: GetPublicKeyParams = {}): Promise<Buffer> => {
      return this.#keychain.getPublicKey({ seedId, keyId })
    }

    const sign = ({
      data,
      keyId = getDefaultKeyIdentifier(),
      signatureType,
      enc,
      tweak,
      extraEntropy,
    }: KeychainSignerParams): Promise<any> => {
      assert(KeyIdentifier.validate(keyId), 'signBuffer: invalid `keyId`')

      if (!signatureType) {
        // temporary because some assets (algorand) do not pass signatureType
        signatureType = keyId.keyType === 'secp256k1' ? 'ecdsa' : 'ed25519'
      }

      return this.#keychain.signBuffer({
        seedId,
        keyId,
        data,
        signatureType,
        enc,
        tweak,
        extraEntropy,
      })
    }

    return { sign, getPublicKey }
  }
