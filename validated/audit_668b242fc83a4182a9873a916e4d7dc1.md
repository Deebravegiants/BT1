### Title
Webhook `shop` (and `topic`) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, but then trusts the `shop` (and `topic`) identity from unauthenticated HTTP headers when dispatching the payload to the app's handler. Because Shopify signs webhooks with the app's single, shop-independent `api_secret_key`, any legitimate webhook a merchant receives for their own shop can be replayed with a forged `x-shopify-shop-domain` header pointing at a different tenant, and the HMAC check will still pass.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` and `topic`, however, are read straight from request headers and are never included in the signed bytes: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the received HMAC against `verifiable_query.to_signable_string` (the body only), using the app's `Context.api_secret_key`: [3](#0-2) 

`Webhooks::Registry.process` only checks this HMAC, then immediately builds `WebhookMetadata` from the unauthenticated `request.shop` and `request.topic` and hands it to the app's registered handler: [4](#0-3) 

The identity binding that should hold is: `shop asserted to the handler == shop that Shopify actually cryptographically vouched for`. Because the signature only covers the body, and the app's `api_secret_key` is identical for every shop installing the app, an attacker who is a legitimate (unprivileged) merchant on Shop A can:
1. Install the app on Shop A and receive a genuine webhook (valid raw body + valid `x-shopify-hmac-sha256`, signed with the app's shared secret).
2. Replay that exact body/HMAC pair to the app's webhook endpoint, substituting `x-shopify-shop-domain` (and optionally `x-shopify-topic`) with Shop B's domain.
3. `HmacValidator.validate` recomputes the HMAC over the unchanged body and succeeds, since the signature never covered `shop`/`topic`.
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: <Shop A's data>, ...)`, so the host application processes attacker-controlled data as authenticated events belonging to a different tenant.

### Impact Explanation
This breaks the cross-tenant isolation the gem is supposed to guarantee via `Utils::HmacValidator.validate`: an "authenticated" webhook can be attributed to any arbitrary shop the attacker chooses, letting them inject spoofed events (and body content) into another tenant's webhook processing pipeline purely through calls this gem exposes (`HmacValidator.validate`, `Registry.process`). This is a cross-tenant access vulnerability.

### Likelihood Explanation
The attacker only needs to be a normal merchant who can install any public app that uses this gem (no privileged credentials, no access token, no leaked secrets required) and can capture one legitimate webhook delivery to their own endpoint before replaying it with a modified header.

### Recommendation
Bind the header-derived `shop` (and `topic`) into the HMAC-signed material, or otherwise cryptographically tie them to the verified body (e.g., require the handler/registry to cross-check `shop` against a value independently known to be associated with the signing secret, or reject processing unless `shop` matches an expected/registered shop for that webhook subscription) before invoking the handler in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on `shop-a.myshopify.com` and triggers any subscribed webhook topic, capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header sent by Shopify.
2. Attacker sends a new HTTP request to the app's webhook endpoint with the identical raw body and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com` (a different, victim shop that also installed the app).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the secret [5](#0-4) .
4. The registered handler is invoked with `WebhookMetadata` whose `shop` is `"shop-b.myshopify.com"` even though the payload and event actually originated from Shop A, demonstrating cross-tenant event spoofing [6](#0-5) .

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
