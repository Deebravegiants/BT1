## Custody Analog Found: Stale `TombStone.original_owner` Allows Theft of Objects Sent to `BURN_ADDRESS` After a Legitimate Ownership Transfer

### Title
Unauthorized object ownership reassignment via stale `TombStone` reclaim in `object::unburn` - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
`object::burn` marks an object as tombstoned by recording the *caller* as `TombStone.original_owner`, but does not disable transfers or clear the tombstone. Because the standard transfer path (`transfer_raw_inner`, used by `object::transfer`/`transfer_call`/`transfer_to_object`) never removes a `TombStone`, a stale tombstone from a previous owner can survive one or more legitimate ownership transfers. If any later legitimate owner subsequently sends the object to the well-known `BURN_ADDRESS`, the *original, now-unrelated* burner can call `object::unburn` and reclaim the object for themselves — stealing custody from the actual current/former owner who performed the burn-to-address action.

### Finding Description
`object::burn` only requires the caller to be the *current* owner and stamps the tombstone with that owner's address, without disabling further transfers: [1](#0-0) 

The generic transfer path used by `object::transfer`, `object::transfer_call`, and `object::transfer_to_object` goes through `transfer_raw` → `transfer_raw_inner`, which updates `owner` but never inspects or clears `TombStone`: [2](#0-1) 

By contrast, the `TransferRef`-based path explicitly purges the tombstone before transferring, with a comment acknowledging exactly this risk ("we don't want the original owner to be able to reclaim by calling unburn later"): [3](#0-2) 

This inconsistency means only `TransferRef`-mediated transfers are protected; the far more common raw/entry-function transfer (`object::transfer`) is not.

`unburn`'s reclaim check for the "sent-to-burn-address" branch only compares the caller against the tombstone's stored `original_owner`, with no check that this caller was the most recent owner prior to the `BURN_ADDRESS` transfer: [4](#0-3) 

**Exploit path (custody invariant broken: "owner reassignment must reflect the true, current controller"):**
1. Attacker A owns an object with default `allow_ungated_transfer = true` (true for freshly created objects unless explicitly disabled — the common case for NFTs / token objects created via `object::create_object`/`create_named_object`).
2. A calls `object::burn(A, object)` → `TombStone { original_owner: A }` is attached; A still owns the object.
3. A legitimately sells/transfers the object to victim B via the standard `object::transfer` entry function. Ownership moves to B; the stale `TombStone { original_owner: A }` is **not** cleared (per the `transfer_raw_inner` gap above).
4. B later sends the object to the well-known `BURN_ADDRESS` (`0xff...ff`) — a common user action for permanently discarding an asset (e.g., NFT "burn by sending to dead address" pattern), using the normal `object::transfer`/`transfer_call` function since ungated transfer is still enabled.
5. Attacker A calls `object::unburn(A, object)`. Since `object_core.owner == BURN_ADDRESS` and `original_owner_addr == A == caller`, the check passes and `transfer_raw_inner(object_addr, A)` is executed, restoring ownership to A — even though A had no rights to the object since step 3 and never sent it to `BURN_ADDRESS`.

The root cause is entirely local: a single-owner-check omission in `transfer_raw_inner` combined with `unburn`'s trust in a `TombStone` field that is not guaranteed to reflect the most recent legitimate owner.

### Impact Explanation
This is a direct owner-reassignment/custody-theft primitive: an unprivileged former owner can reclaim exclusive control of any object-held asset (NFTs, other Object<T>-based value) that a later, legitimate owner intentionally sent to `BURN_ADDRESS`, without any authorization from that legitimate owner. Any object minted through the framework's default object-creation path (ungated transfer enabled by default) and later resold/transferred is susceptible if the chain of custody ever included a self-burn-then-transfer step by a prior holder — including malicious sellers who could deliberately pre-plant a tombstone before selling an NFT, then reclaim it once the buyer (unaware of the tombstone, since burnt objects are hidden from indexers) sends it to the burn address. This satisfies "Unauthorized takeover... owner reassignment of... token objects or other object-held value" under the custody impact gate.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: burning-by-transferring-to-a-known-dead-address is a widely used pattern in token/NFT ecosystems, and Aptos's `BURN_ADDRESS` constant is a natural target for such deliberate transfers. A malicious seller can proactively set up the tombstone before selling, making exploitation fully attacker-controlled and requiring no cooperation or error from the victim beyond the routine act of "burning" the NFT normally.

### Recommendation
Clear any existing `TombStone` whenever ownership changes via `transfer_raw_inner` (mirroring the fix already present in `transfer_with_ref`), or alternatively, disallow `object::burn`/`unburn` semantics from surviving any subsequent non-`TransferRef` ownership change by re-validating that the `TombStone.original_owner` was the immediately preceding owner (not merely some address at any point in history) before permitting reclaim in `unburn`.

### Proof of Concept
```move
// Step 1: Attacker A creates/owns an object (allow_ungated_transfer = true by default)
let ctor = object::create_object(signer::address_of(&a));
let obj: Object<SomeType> = object::object_from_constructor_ref(&ctor);

// Step 2: A burns it (tombstones), still owns it
object::burn(&a, obj);

// Step 3: A sells/transfers to B via standard raw transfer path (TombStone NOT cleared)
object::transfer(&a, obj, signer::address_of(&b));

// Step 4: B, believing the object is now clean, later "burns" it the common way
// by sending to the well-known BURN_ADDRESS
object::transfer_call(&b, object::object_address(&obj), BURN_ADDRESS);

// Step 5: A reclaims the object that rightfully passed through B's custody
object::unburn(&a, obj);
// object_core.owner is now `a` again -- B's asset has been stolen back by A.
```

Note: I was unable to execute this PoC in a live Move test harness within this session; the logical trace above is fully supported by the cited source lines showing (a) `transfer_raw_inner`'s lack of `TombStone` cleanup and (b) `unburn`'s caller-vs-stored-`original_owner` check that does not verify recency of ownership.

    /// Allow origin owners to reclaim any objects they previous burnt.
    public entry fun unburn<T: key>(
        original_owner: &signer,
        object: Object<T>,
    ) {
        let object_addr = object.inner;
        assert!(exists<TombStone>(object_addr), error::invalid_argument(EOBJECT_NOT_BURNT));

        // The new owner of the object can always unburn it, but if it's the burn address, we go to the old functionality
        let object_core = borrow_global<ObjectCore>(object_addr);
        if (object_core.owner == signer::address_of(original_owner)) {
            let TombStone { original_owner: _ } = move_from<TombStone>(object_addr);
        } else if (object_core.owner == BURN_ADDRESS) {
            // The old functionality
            let TombStone { original_owner: original_owner_addr } = move_from<TombStone>(object_addr);
            assert!(
                original_owner_addr == signer::address_of(original_owner),
                error::permission_denied(ENOT_OBJECT_OWNER)
            );
            transfer_raw_inner(object_addr, original_owner_addr);
        } else {
            abort error::permission_denied(ENOT_OBJECT_OWNER);
        };
    }
