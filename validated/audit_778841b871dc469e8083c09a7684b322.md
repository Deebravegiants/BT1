### Title
`DeliveryFeeFactor` for a DMP destination can grow unbounded and has no unprivileged decay path if the destination para never processes its queue - (File: `polkadot/runtime/parachains/src/dmp.rs`)

### Summary
`Pallet::queue_downward_message` calls `increase_fee_factor` whenever the destination para's DMQ length exceeds `threshold`, but the only decrease path, `decrease_fee_factor`, is invoked exclusively from `prune_dmq`, which only runs when the destination para actually gets an included candidate that reports `processed_downward_messages > 0`. A destination para that never produces/includes blocks (protocol-valid, since queue draining is not mandatory) can accumulate an ever-increasing `DeliveryFeeFactor` with no way for any unprivileged actor to reset or decay it.

### Finding Description
`queue_downward_message` unconditionally raises the fee factor once the queue length passes `threshold = dmq_max_length / THRESHOLD_FACTOR`: [1](#0-0) 

The corresponding decrease only happens in `prune_dmq`, called when the para's block inclusion reports processed messages and the queue subsequently falls at/below threshold: [2](#0-1) 

`check_processed_downward_messages` explicitly documents that a parachain is *not* forced to process any particular pace of messages beyond the minimal advancement rule, and that this leniency is intentional ("only 'stupid' parachains would do it and we don't (and can't) force anyone to act on messages"): [3](#0-2) 

Crucially, if the destination para simply never gets a candidate included at all (stalls entirely, which is permitted protocol behavior for an offline/misbehaving/deliberately-idle collator set), `prune_dmq` is never invoked, so `decrease_fee_factor` is never reachable for that para. `increase_fee_factor`/`decrease_fee_factor` are generic `FeeTracker` trait methods with no reset entrypoint exposed to unprivileged callers: [4](#0-3) 

`can_queue_downward_message` only enforces a hard cap on total queue length (`dmq_max_length`), not a per-block/per-sender rate limit, so repeated sends past the threshold (but under the hard cap) keep multiplying the fee factor by `EXPONENTIAL_FEE_BASE * (1 + size_factor)` each time: [5](#0-4) 

The exploit does not require privileged relay-chain calls: any mechanism that causes `queue_downward_message` to be invoked against a chosen destination — e.g., HRMP channel management notifications triggered by `hrmp_init_open_channel`/`hrmp_accept_open_channel`, which are ordinary para-signed/XCM-`Transact`-reachable extrinsics — can push messages into the target's DMQ. As long as the target para is controlled by (or colludes with) the attacker and never includes blocks that drain/report processed messages, the factor keeps climbing and never decreases.

### Impact Explanation
Once `DeliveryFeeFactor::<T>::get(para)` grows large, every subsequent legitimate DMP send to that para (via `xcm_sender.rs`'s `FeeTracker`-based pricing) becomes proportionally more expensive, since the fee factor multiplies the base delivery fee. This can price out or economically deny delivery of governance/system-relevant DMP traffic (e.g., HRMP notifications, XCM messages) directed at that para, with no unprivileged remedy — only a chain restart of message processing by the destination (which the destination itself controls and can refuse) drains the queue and triggers `decrease_fee_factor`. This is a scoped denial-of-service on DMP delivery economics, not a fund-loss issue, matching the described impact.

### Likelihood Explanation
Feasibility depends on how repeatably an attacker can drive `queue_downward_message` calls to a chosen para without an unprivileged reset. The mechanism is real and unconditionally reachable via any code path that calls `queue_downward_message` (HRMP channel management, XCM `Transact`-triggered pallet calls, UMP-triggered DMP messages, etc.), and requires no relay-chain governance. The main constraint is repeatability of the specific triggering call (e.g., `hrmp_init_open_channel` is keyed per sender/recipient pair, so sustained spam may require multiple distinct sending paras or repeated open/cancel cycles) — this repeatability was not fully verified against `hrmp.rs`'s request-lifecycle rules within available context, so the exact throughput of the attack (how fast/cheaply the threshold and beyond can be crossed) is not fully confirmed. However, the underlying architectural gap — no unprivileged decay/reset path independent of the destination para's own willingness to process its queue — is confirmed in code and is a genuine self-inflicted-but-externally-consequential DoS vector.

### Recommendation
Decouple `decrease_fee_factor` from requiring the destination para to itself process messages. Options: (1) add a time-based/block-based decay of `DeliveryFeeFactor` in `on_initialize`/`on_idle` independent of `prune_dmq`, so fee factors trend back toward `MIN_FEE_FACTOR` over time regardless of whether the destination drains its queue; (2) cap the maximum multiplier reachable purely from queue backlog growth, separate from a floor that only relay-chain-forced pruning (e.g., via `lazy_delete_some` hard queue eviction) can raise; (3) rate-limit `increase_fee_factor` increments per relay-chain block per destination para so backlog-driven growth cannot exceed a bounded multiplier within a fixed number of blocks even if the destination never processes anything.

### Proof of Concept
Rust unit test in `polkadot/runtime/parachains/src/dmp/tests.rs`:
1. Register a para (`make_parachain_reachable`) and set config so `threshold` is small.
2. Repeatedly call `Pallet::queue_downward_message` for that para without ever calling `prune_dmq` (simulating the para never including a block), driving `q_len` above `threshold` many times.
3. Assert `DeliveryFeeFactor::<T>::get(para)` strictly increases each iteration and never decreases, even after many blocks pass with no `prune_dmq` call.
4. Assert that calling `decrease_fee_factor(para)` is only reachable through `prune_dmq`, and that no unprivileged extrinsic/dispatchable in the pallet exposes a reset/decay of `DeliveryFeeFactor` independent of destination-side processing.
5. Optionally simulate the HRMP path: call `Hrmp::init_open_channel` from several distinct sender paras targeting the same victim para and confirm each triggers a `queue_downward_message` to the victim, contributing to the same unbounded growth.

	pub fn can_queue_downward_message(
		config: &HostConfiguration<BlockNumberFor<T>>,
		para: &ParaId,
		msg: &DownwardMessage,
	) -> Result<(), QueueDownwardMessageError> {
		let serialized_len = msg.len() as u32;
		if serialized_len > config.max_downward_message_size {
			return Err(QueueDownwardMessageError::ExceedsMaxMessageSize);
		}

		// Hard limit on Queue size
		if Self::dmq_length(*para) > Self::dmq_max_length(config.max_downward_message_size) {
			return Err(QueueDownwardMessageError::ExceedsMaxMessageSize);
		}

		// If the head exists, we assume the parachain is legit and exists.
		if !paras::Heads::<T>::contains_key(para) {
			return Err(QueueDownwardMessageError::Unroutable);
		}

		Ok(())
	}

	/// Checks if the number of processed downward messages is valid.
	pub(crate) fn check_processed_downward_messages(
		para: ParaId,
		relay_parent_number: BlockNumberFor<T>,
		processed_downward_messages: u32,
	) -> Result<(), ProcessedDownwardMessagesAcceptanceErr> {
		let dmq_length = Self::dmq_length(para);

		if dmq_length > 0 && processed_downward_messages == 0 {
			// The advancement rule is for at least one downwards message to be processed
			// if the queue is non-empty at the relay-parent. Downwards messages are annotated
			// with the block number, so we compare the earliest (first) against the relay parent.
			let first = InboundDownwardQueue::<T>::peek_front(para);

			// sanity: if dmq_length is >0 this should always be 'Some'.
			if first.map_or(false, |msg| msg.sent_at <= relay_parent_number) {
				return Err(ProcessedDownwardMessagesAcceptanceErr::AdvancementRule);
			}
		}

		// Note that we might be allowing a parachain to signal that it's processed
		// messages that hadn't been placed in the queue at the relay_parent.
		// only 'stupid' parachains would do it and we don't (and can't) force anyone
		// to act on messages, so the lenient approach is fine here.
		if dmq_length < processed_downward_messages {
			return Err(ProcessedDownwardMessagesAcceptanceErr::Underflow {
				processed_downward_messages,
				dmq_length,
			});
		}

		Ok(())
	}

	/// Prunes the specified number of messages from the downward message queue of the given para.
	pub(crate) fn prune_dmq(para: ParaId, processed_downward_messages: u32) {
		InboundDownwardQueue::<T>::drop_front_n(para, processed_downward_messages as u64);
		let q_len = InboundDownwardQueue::<T>::len(para).unwrap_or(0);

		let config = configuration::ActiveConfig::<T>::get();
		let threshold =
			Self::dmq_max_length(config.max_downward_message_size).saturating_div(THRESHOLD_FACTOR);
		if q_len <= threshold as u64 {
			Self::decrease_fee_factor(para);
		}
	}

	fn do_increase_fee_factor(fee_factor: &mut FixedU128, message_size: u128) {
		let message_size_factor = FixedU128::from(message_size.saturating_div(1024))
			.saturating_mul(Self::MESSAGE_SIZE_FEE_BASE);
		*fee_factor = fee_factor
			.saturating_mul(Self::EXPONENTIAL_FEE_BASE.saturating_add(message_size_factor));
	}

	/// Increases the delivery fee factor by a factor based on message size and records the result.
	fn increase_fee_factor(id: Self::Id, message_size: u128) {
		let mut fee_factor = Self::get_fee_factor(id);
		Self::do_increase_fee_factor(&mut fee_factor, message_size);
		Self::set_fee_factor(id, fee_factor);
	}

	fn do_decrease_fee_factor(fee_factor: &mut FixedU128) -> bool {
		const { assert!(Self::EXPONENTIAL_FEE_BASE.into_inner() >= FixedU128::from_u32(1).into_inner()) }

		if *fee_factor == Self::MIN_FEE_FACTOR {
			return false;
		}

		// This should never lead to a panic because of the static assert above.
		*fee_factor = Self::MIN_FEE_FACTOR.max(*fee_factor / Self::EXPONENTIAL_FEE_BASE);
		true
	}

	/// Decreases the delivery fee factor by a constant factor and records the result.
	///
	/// Does not reduce the fee factor below the initial value, which is currently set as 1.
	///
	/// Returns `true` if the fee factor was actually decreased, `false` otherwise.
	fn decrease_fee_factor(id: Self::Id) -> bool {
		let mut fee_factor = Self::get_fee_factor(id);
		let res = Self::do_decrease_fee_factor(&mut fee_factor);
		Self::set_fee_factor(id, fee_factor);
		res
	}
