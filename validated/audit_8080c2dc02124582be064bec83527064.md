### Title
Webhook shop/topic identity headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authorizes an incoming webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain` (and `topic`) HTTP headers to decide which shop the webhook belongs to. The signature never covers those headers, so an attacker who possesses one genuine, HMAC-valid webhook body/signature pair for their own shop can resubmit it with a different `x-shopify-shop-domain` header and have it processed as if it originated from another shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` derive the signature check purely from `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated HTTP headers, with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC of the request, then immediately trusts `request.shop`/`request.topic` (taken from headers) to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

Because `Context.api_secret_key` (the HMAC key) is a single, app-wide secret shared across every shop that installs the app (not a per-shop key), any bytes+signature pair that is valid for one installed shop is also a valid signature for a request claiming to be from any other shop — the signature says nothing about which shop the bytes belong to. This breaks the intended binding: **HMAC-verified bytes == the shop identity acted on**. In practice, verified bytes (the raw body) and the shop identity consumed by the handler come from two different, independently-controlled channels: the signed body versus the unsigned header.

This is the direct analog to the reported bug class: a check exists ("is the HMAC valid?") but a related, security-relevant field it should also cover (`shop`) is left unchecked/unbound, so the wrong actor can be substituted without failing verification — same pattern as `leverage()` skipping the borrow-duration check that `borrow()` enforces.

### Impact Explanation
This meets the High-severity bar for scope/expiry-check bypass style issues: an app instance normally processes webhooks under the assumption that a passing HMAC check implies "this event truly happened for this specific shop." Since the shop identifier isn't covered, an attacker (a merchant who has installed the app, i.e., an ordinary tenant of the app — not requiring `api_secret_key` or another shop's credentials) can cause the app to process events attributed to a shop they don't control, corrupting per-tenant state, potentially triggering privileged actions (e.g. re-triggering `shop/redact`, `customers/data_request`, order/customer webhooks) against another merchant's stored session/data — i.e., cross-tenant confusion.

### Likelihood Explanation
Likely and cheaply reachable: the attacker only needs to be a legitimate, unprivileged installer of the target app in order to receive at least one genuine webhook (any topic) with a valid HMAC for their own shop. They then replay that exact body+signature to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header. No `api_secret_key`, access token, or other privileged credential is required — only the app's public webhook URL and one captured legitimate webhook.

### Recommendation
Bind the header-derived identity fields (`shop`, `topic`, `api_version`, `webhook_id`) into the signed payload used for HMAC verification (e.g., verify a canonical string that includes these headers plus body, matching how Shopify signs the values it intends to guarantee), or otherwise cryptographically tie the shop claim to the signature before it is trusted by `Registry.process`/`WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and captures a real webhook delivery: raw JSON body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, B)`).
2. Attacker sends a forged HTTP POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes `HMAC(api_secret_key, B)` and compares to `H` — this passes because `B`/`H` are unchanged.
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes the (attacker-controlled) body as if it were a legitimate event for the victim shop. [3](#0-2) [4](#0-3)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
