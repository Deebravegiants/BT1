### Title
`describeWithdrawal` reports `status: "completed"` for any destination `ChainKind` not explicitly handled, without checking finalization — ([File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts])

### Summary
`OmniBridge.describeWithdrawal` derives `destinationChain` from the real transfer record returned by `omniBridgeAPI.getTransfer` and only checks for finalization data (`transfer.finalised` / `utxo_meta`) on chains it explicitly recognizes (EVM, Sol, Fogo, Strk, Aptos, UTXO). Any other `ChainKind` value falls through to the final `else` branch, which returns `{status: "completed", txHash: null}` purely because `transfer.recipient` is non-null, with no verification that the bridge actually finalized/paid out the transfer.

### Finding Description
The broken equality is: **`status: "completed"`** must mean *the bridge has finalized and paid out the transfer on the destination chain*, but the code instead sets `completed` whenever `destinationChain` doesn't match one of the five hardcoded branches, based solely on `transfer.recipient != null`: [1](#0-0) 

The `destinationChain` is computed from `getChain(transfer.recipient as OmniAddress)`, i.e., from the actual recipient address recorded by the bridge for this transfer — not directly from an arbitrary user string, but ultimately reflecting whatever chain the withdrawal's `routeConfig.chain` caused the on-chain Omni Bridge transfer to target. The exhaustive `if/else if` ladder (`isEvmChain`, `Sol`, `Fogo`, `Strk`, `Aptos`, `isUtxoChain`) is a hardcoded, manually maintained list in this SDK. If the underlying Omni Bridge protocol supports (or later adds) a destination `ChainKind` not present in this list — which has clearly grown over time (Fogo/Strk/Aptos were added incrementally) — any transfer routed to that chain permanently short-circuits into the `else` branch and is reported `completed` the instant the transfer record exists with a recipient, regardless of whether `transfer.finalised` is set.

Existing guards do not prevent this: there is no `assert` that `destinationChain` is one of the known kinds before falling into the `else`, and no code path revalidates completion by checking `transfer.finalised` in the `else` branch.

### Impact Explanation
An integrator using `describeWithdrawal` to gate downstream settlement (releasing funds, marking an off-chain ledger entry as done, unlocking a wrapped-asset mint, etc.) would treat the withdrawal as fully executed and irreversible the moment a transfer record with a recipient appears — even if the destination-chain leg of the bridge has not finalized. This matches the "status misreport causing integrator to credit twice / prematurely" High/Critical category: funds could be considered delivered when they are not, with no automatic re-check once `completed` is reported, and no recovery path if the bridge later fails or delays finalization on that chain kind.

### Likelihood Explanation
Exploitability strictly depends on whether the deployed Omni Bridge protocol currently defines a `ChainKind` value that is not one of `isEvmChain`, `Sol`, `Fogo`, `Strk`, `Aptos`, or `isUtxoChain` in this repository's snapshot. I was unable to locate and fully enumerate the `ChainKind` type/enum definition within the indexed codebase (grep for `ChainKind` definitions and `getChain` implementation did not resolve in this session), so I cannot confirm with certainty whether such an unmapped, protocol-supported chain currently exists. Given the pattern of incremental additions (Fogo, Strk, Aptos were clearly added after EVM/Sol/UTXO support), this is a real structural risk of enum drift between the shared Omni Bridge chain list and this SDK's hardcoded branches, but confirming a *currently* exploitable unmapped chain requires inspecting the full `ChainKind` enum from `@near-one/omni-bridge` (or wherever it's defined), which the index did not surface.

### Recommendation
Replace the `else` fallback with an explicit failure/pending state rather than `completed`: e.g., throw/log an "unsupported destination chain" error, or return `{status: "pending"}` unless `transfer.finalised` (or the chain-appropriate finalization signal) is present. Do not infer `completed` from `transfer.recipient != null` alone for any chain kind; require finalization evidence uniformly across all branches, and add an exhaustive-check (e.g., a `never` assertion) on `ChainKind` so new chain kinds fail loudly instead of silently defaulting to `completed`.
