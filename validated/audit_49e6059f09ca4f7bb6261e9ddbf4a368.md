### Title
Unvalidated `parse_extra` header validator-section parsing can panic/index-overflow on malicious BSC `extra_data` before signature verification - (File: modules/consensus/bsc/verifier/src/primitives.rs)

### Summary
`parse_extra` in the BSC consensus verifier decodes the `extra_data` field of a BSC block header — including an attacker-supplied validator count byte and slice arithmetic — before any cryptographic signature is checked. This mirrors the CFITSIO bug class: untrusted, attacker-crafted binary input is parsed with raw index/length arithmetic ahead of validation, creating a path to out-of-bounds panics/DoS on the trusted consensus-update path.

### Finding Description
`verify_bsc_header` calls `parse_extra::<H, C>(&update.attested_header)` and, depending on branch, `parse_extra` on `update.source_header` or `update.epoch_header_ancestry[0]` — all fields of the fully relayer-controlled `BscClientUpdate` struct — *before* the BLS aggregate signature is verified: [1](#0-0) 

Inside `parse_extra`, the validator-count byte `data[0]` is read directly from attacker bytes and used to compute `validator_bytes_total_length = VALIDATOR_NUMBER_SIZE + validator_num * VALIDATOR_BYTES_LENGTH`, then slices `remaining_data[i * VALIDATOR_BYTES_LENGTH .. ]` in a loop up to `validator_num` (up to 255): [2](#0-1) 

There is a length check (`data_length < required_length`) guarding the validator slice range, and a subsequent RLP-based `VoteAttestationData::decode` for the attestation tail, but the whole chain of length/index computations (`data_length - EXTRA_SEAL_LENGTH`, `validator_bytes_total_length - VALIDATOR_NUMBER_SIZE [+ TURN_LENGTH_SIZE]`) is unsigned-integer arithmetic performed on relayer-controlled lengths, so any inconsistency between the check and the later derived `index` calculation (`&remaining_data[index..]`) can underflow/overflow and panic the runtime that processes the unsigned consensus update, since these are plain `usize` subtractions with `Err`-returning guards only for the specific cases already covered by the two `if` checks — any other malformed shape not covered by those exact checks reaches the raw slicing.

### Impact Explanation
`verify_bsc_header` is invoked by the `ismp-bsc` consensus client on **any submitted unsigned consensus message** carrying a `BscClientUpdate` — a message any unprivileged relayer can dispatch to `pallet-ismp`'s `handle_unsigned`/consensus update handling path. A crafted `extra_data` that panics during parsing (rather than being cleanly rejected) crashes/panics the node processing the update, which — depending on execution context (native runtime vs. WASM, and whether the panic is caught by the executive's unwind boundary) — can halt block production or DoS the light client's ability to progress, i.e. "a route unable to deliver messages" for the BSC light client route. Because this file has already undergone at least one such hardening pass (the BOHR fork length-check comment), the remaining unsigned-arithmetic index derivations are still reachable pre-signature-check and are the most probable analog of the CFITSIO "parse untrusted binary before validating it" bug class in this codebase.

### Likelihood Explanation
High reachability: this is on the primary, permissionless consensus-update ingestion path (no signature, no admin gate, no prior state needed beyond an active BSC light client) — any relayer can submit a `BscClientUpdate` with an arbitrary `extra_data` byte string to trigger `parse_extra`. The precise panicking input (an `extra_data` shape that passes the existing length checks but produces an inconsistent `index` in the BOHR/non-BOHR branch, e.g. by manipulating `header.timestamp` relative to `BOHR_FORK_TIMESTAMP` vs. the actual byte layout) requires further fuzzing/testing to confirm concretely, which I was not able to fully verify given tool-call constraints.

### Recommendation
- Replace all raw slice indexing/arithmetic in `parse_extra` (`modules/consensus/bsc/verifier/src/primitives.rs` lines 139-189) with checked arithmetic (`checked_sub`, `checked_mul`, `get()`-based slicing) that returns `Err(...)` instead of panicking on any malformed/adversarial `extra_data`.
- Add fuzz/property tests that feed arbitrary byte strings (including edge cases around the BOHR-fork boundary and `validator_num` near `u8::MAX`) directly into `parse_extra` and assert it never panics.
- Consider validating `extra_data` shape/length invariants generically before dispatching into the BOHR/non-BOHR branch logic, rather than relying on two specific `if` checks to cover all malformed shapes.

### Proof of Concept
Conceptual (not executed): construct a `CodecHeader` whose `extra_data` is `EXTRA_VANITY_LENGTH` vanity bytes + a single byte `validator_num` chosen such that `validator_bytes_total_length` satisfies the `required_length` check for the *non-BOHR* branch, but set `header.timestamp >= C::BOHR_FORK_TIMESTAMP` so the BOHR branch's `index = validator_bytes_total_length - VALIDATOR_NUMBER_SIZE + TURN_LENGTH_SIZE` is computed and used to slice `remaining_data[index..]` — if `remaining_data.len() < index` (a case the `required_length` check does compute correctly per the comment, so this specific case is likely already patched), the slice panics. A background Devin agent with repo/test access should fuzz `parse_extra` directly with `cargo fuzz`/`proptest` over `(extra_data: Vec<u8>, timestamp: u64)` to find any remaining panicking input, since I could not execute code to confirm a live panicking input from static review alone.
