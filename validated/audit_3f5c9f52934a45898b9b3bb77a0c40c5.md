### Title
Shared `onChainEncryptedOutput` field allows one ciphertext to be bound to multiple distinct on-chain UTXO leaves - ([File: contracts/HinkalBase.sol])

### Summary
`CircomData.onChainEncryptedOutput` is declared as a single `bytes` value, not an array indexed per UTXO. In `Hinkal.transact`, every element of `utxoSet` returned by an external action is paired with this same shared value via `createOnchainCommitment(utxoSet[j], circomData.onChainEncryptedOutput)`, so if an external action returns 2+ on-chain UTXOs with different `amount`/`erc20Address`/`stealthAddressStructure`, all resulting leaves are emitted with byte-identical `onChainEncryptedOutput`.

### Finding Description
The broken equality: for each `NewCommitment` leaf `i`, `onChainEncryptedOutput_i` must decrypt to exactly `(utxo_i.amount, utxo_i.erc20Address, utxo_i.stealthAddressStructure, utxo_i.timeStamp)`. Instead, `onChainEncryptedOutput_i == circomData.onChainEncryptedOutput` for all `i`, a single constant supplied once per transaction.

Code path:
- `contracts/types/CircomData.sol` line 31: `bytes onChainEncryptedOutput;` — a single field, not `bytes[]`.
- `contracts/Hinkal.sol` lines 116-132: for each `erc20TokenAddresses[i]`, the code loops `utxoSet` and for every matching UTXO calls `createOnchainCommitment(utxoSet[j], circomData.onChainEncryptedOutput)` — the same `circomData.onChainEncryptedOutput` is reused across all `j` matches and across all `i` token iterations. [1](#0-0) 
- `contracts/HinkalBase.sol` lines 53-70: `createOnchainCommitment` computes a leaf-specific `commitment = hash4(amount, erc20Address, stealthAddress, timeStamp)` but stores the passed-in, shared `onChainEncryptedOutput` verbatim into `OnChainCommitment.onChainEncryptedOutput`. [2](#0-1) 
- `insertCommitments` (lines 122-131) then emits one `NewCommitment` event per on-chain commitment, each carrying `abi.encode(onChainCommitments[i].utxo, onChainCommitments[i].onChainEncryptedOutput)` — distinct `utxo` payloads but identical `onChainEncryptedOutput` bytes when the source `utxoSet` had more than one entry. [3](#0-2) 

Attacker's call: an unprivileged EOA deploys a custom `IExternalActionV2`-compliant contract, registers/uses it as `circomData.externalActionData.externalAddress` (assuming it is a whitelisted/registered external action — see caveat below), and has `runAction` return a `UTXO[]` with two or more entries differing in `amount` and/or `erc20Address`. Because `onChainEncryptedOutput` is a single top-level field in `CircomData` supplied directly by the caller and not an array keyed to each UTXO, the same ciphertext is bound to every resulting leaf regardless of how many distinct on-chain UTXOs are created.

Existing guards do not catch this: `performHinkalChecks`/`dimensionsCheck` constrain array lengths and general proof-input shape but there is no field or circuit constraint tying `onChainEncryptedOutput` per-leaf, since the type only carries one value for the whole transaction; `verifyProof` validates the ZK proof's public inputs (commitments, nullifiers, roots, amounts) but the encrypted-output ciphertext is off-circuit auxiliary calldata not constrained by the proof at all (it is only ever consumed off-chain by a would-be recipient to decrypt UTXO details) — the ZK circuit does not, and structurally cannot, constrain the semantic correctness of a ciphertext string. The balance/slippage checks (`balanceDif`, `utxoAmount`) verify aggregate token amounts move correctly, but say nothing about which ciphertext is attached to which leaf.

Note: I was not able to load `contracts/types/IExternalActionV2.sol`, `DepositOnChainUtxosExternalAction.sol`, or `contracts/HinkalHelper.sol` fully in this pass to confirm whether external actions returning multiple heterogeneous on-chain UTXOs is a normal, permissionless flow, or whether external action registration (`registerExternalAction`, `onlyRole(DEFAULT_ADMIN_ROLE)`) restricts which actions can produce multi-UTXO output. If external actions are admin-registered/vetted contracts only, an attacker cannot arbitrarily inject their own `runAction` logic returning colliding UTXOs, which would materially reduce (or eliminate) attacker control over `utxoSet` contents, since they could not deploy new registered external actions themselves.

### Impact Explanation
If exploitable, the second and subsequent on-chain UTXO leaves in the same transaction get a ciphertext that does not correspond to their own `(amount, erc20Address, stealthAddressStructure, timeStamp)`. The intended recipient of that leaf (whoever the `stealthAddress` belongs to) would be unable to decrypt/discover their own UTXO details from `onChainEncryptedOutput`, since it actually encodes a different leaf's data. This could permanently strand funds encoded in those additional on-chain UTXOs for their rightful owner — matching the "permanent freezing of user funds" Critical category, provided the attacker (or a benign multi-UTXO external action integrator) can trigger multiple heterogeneous on-chain UTXOs in one call.

### Likelihood Explanation
Preconditions: an external action registered in `externalActionMap` (via `registerExternalAction`, admin-only) must return (via `runAction`) two or more `UTXO` entries with differing `erc20Address`/`amount`/`stealthAddressStructure` in a single `transact` call. Whether an unprivileged attacker can cause this depends on whether any already-registered external action (e.g., swap or emporium action) can be driven to output multiple distinct on-chain UTXOs, or whether the attacker needs the admin to register a malicious external action (which would violate the "unprivileged attacker" threat model). I could not fully verify this in the available context (`ExternalActionSwap.sol`, `EmporiumUpgradeable.sol`, `DepositOnChainUtxosExternalAction.sol` were listed but not read in depth). If a legitimate registered action can naturally produce multi-token/multi-UTXO output (plausible for a swap splitting proceeds, or a multi-hop deposit action), the bug is real and triggerable by any user simply by using that feature normally — not even requiring malicious intent, only that the current `CircomData` schema physically cannot carry more than one on-chain ciphertext per transaction.

### Recommendation
Change `CircomData.onChainEncryptedOutput` from a single `bytes` to `bytes[]`, indexed identically to how on-chain UTXOs are enumerated in `utxoSet`/`onChainCommitments`, and update `createOnchainCommitment` / the loop in `Hinkal.transact` (lines 116-132) to pass `circomData.onChainEncryptedOutput[onChainCommitmentCounter]` (or an equivalent per-UTXO index) instead of the single shared field. Update `performHinkalChecks`/`dimensionsCheck` to validate that the length of `onChainEncryptedOutput` matches the number of on-chain UTXOs actually produced.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, and a mock `IExternalActionV2` contract whose `runAction` returns a `UTXO[]` of length 2 with different `erc20Address` (e.g., `tokenA`, `tokenB`) and different `amount`.
2. Register the mock as an external action via `registerExternalAction` (test setup, not attacker-privileged in the PoC harness).
3. Build a valid `CircomData` with `erc20TokenAddresses = [tokenA, tokenB]`, matching `amountChanges`/`slippageValues`, a single `circomData.onChainEncryptedOutput = X`, and generate a valid proof for these public inputs (or use a mocked verifier per repo test conventions).
4. Call `transact(...)`.
5. Capture both emitted `NewCommitment` events; decode the `bytes data` field for the two on-chain leaves as `(UTXO memory utxo, bytes memory onChainEncryptedOutput)`.
6. Assert: `utxo` fields differ (`amount`/`erc20Address` differ) between the two events, AND `keccak256(onChainEncryptedOutput_1) == keccak256(onChainEncryptedOutput_2) == keccak256(X)` — proving the same ciphertext `X` is bound to two leaves whose underlying UTXO data differs, violating the required per-leaf ciphertext-to-UTXO equality.

    function createOnchainCommitment(
        UTXO memory utxo,
        bytes calldata onChainEncryptedOutput
    ) internal view returns (OnChainCommitment memory) {
        uint256 commitment = hash4(
            utxo.amount,
            uint256(uint160(utxo.erc20Address)),
            utxo.stealthAddressStructure.stealthAddress,
            utxo.timeStamp
        );

        OnChainCommitment memory onChainCommitment = OnChainCommitment({
            utxo: utxo,
            commitment: commitment,
            onChainEncryptedOutput: onChainEncryptedOutput
        });
        return onChainCommitment;
    }
