### Title
Attacker-inflated HyperSwap pre-seed reserves can force `router.addLiquidity` to mint zero LP, causing `finalizeGraduation` to revert forever and permanently freeze the token's curve-raised LT and 250M reserved tokens - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.finalizeGraduation` is a permissionless, non-reentrant, two-phase graduation step that seeds a HyperSwap V2 pair via `_seedUniswapV2Direct` → `_seedRebalancing` → `_routerDepositAndDispose`, then calls the one-shot `LPLock.recordLock`. The protocol's own natspec documents that if the deposit leg mints zero LP, `finalizeGraduation` cannot complete and the token is stuck in `Lifecycle.Graduating` forever — with all curve-raised LT and the 250M `LP_RESERVE` tokens parked in `Bonding` and unrecoverable, because there is no admin override and `finalizeGraduation` is deterministic on the cached `PendingGraduation` state, so every retry hits the identical revert.

### Finding Description
`_seedRebalancing` caps the rebalance swap at 99% of Bonding's own inventory of the swapped-in asset via `_swapBudget` [1](#0-0) , guaranteeing the *residual* `remToken`/`remLT` balances that feed `_routerDepositAndDispose`'s `router.addLiquidity(..., 1, 1, ...)` call are non-zero [2](#0-1) .

The cap, however, only bounds the deposit amount relative to *Bonding's own held balance* of that asset — it does nothing to bound the deposit relative to the *pool's existing reserves/totalSupply*. Uniswap V2's `mint()` computes `liquidity = min(amount0 * totalSupply / reserve0, amount1 * totalSupply / reserve1)` and reverts with `INSUFFICIENT_LIQUIDITY_MINTED` if that rounds to zero. An attacker who has pre-seeded the pair (permitted by the in-scope "pre-creating or pre-seeding the HyperSwap V2 TOKEN/LT pair before graduation" surface) with sufficiently large reserves relative to the tiny residual `remToken`/`remLT` that reach the deposit leg (bounded to ≤1% of Bonding's rebalance-side inventory, per the developers' own accounting in the `_swapBudget` natspec) can make `remToken * totalSupply < reserve0` (or the LT-side analog), forcing `router.addLiquidity`'s underlying `pair.mint()` to revert.

This revert propagates out of `_routerDepositAndDispose` → `_seedRebalancing` → `_seedUniswapV2Direct` → `finalizeGraduation`, so the entire `finalizeGraduation` transaction reverts [3](#0-2) . Because `PendingGraduation` (`tokensForLP`, `ltFromPair`) is cached and immutable once `Lifecycle.Graduating` is set [4](#0-3) , and the pool reserves the attacker set up don't shrink on their own, every future call to `finalizeGraduation` recomputes the identical rebalance/deposit math and reverts identically. The token is permanently stuck in `Lifecycle.Graduating`: trading stays frozen (buy/sell revert with `TokenIsGraduating`), and the curve-raised LT plus the 250M `LP_RESERVE` tokens sit in `Bonding` with no rescue path, exactly the class of "brick" the protocol's own `_swapBudget` comment acknowledges as the failure mode this defense is supposed to close [1](#0-0) , and the same class the `LPLock.recordLock` one-shot design cannot recover from [5](#0-4) .

This mirrors the CVE-2026-53244 bug class: a code path assumes an error/degenerate outcome is always caught and neutralized by an earlier guard (here, the 99%-of-own-inventory swap budget), but that guard doesn't actually cover the real failure surface (the *pool's* reserve/totalSupply ratio, not Bonding's own balance), so the "unlock" step (`finalizeGraduation` completing and calling `LPLock.recordLock`/flipping `Lifecycle` to `Graduated`) can permanently fail to run, leaving state locked forever.

### Impact Explanation
Permanent freezing of funds: all LT raised by the bonding curve for the affected token (moved into `Bonding` via `Router.graduate` at phase 1) plus the 250M `LP_RESERVE` tokens become permanently unreachable — the token can never reach `Lifecycle.Graduated`, trading never reopens, and there is no admin/owner recovery function for a token stuck in `Graduating`. This satisfies the "permanent freezing of trader, creator or LP funds" acceptance criterion.

### Likelihood Explanation
Reachable entirely from unprivileged transactions: pre-seeding/pre-minting into the HyperSwap V2 pair before graduation is explicitly a permitted attack surface, and `finalizeGraduation` is permissionless so the attacker (or anyone) triggering it is not a barrier. The only cost to the attacker is the capital needed to inflate the pool's `reserve`/`totalSupply` enough that the post-rebalance residual deposit (capped at ~1% of Bonding's own swap-side inventory) rounds to zero LP under V2's `mint()` formula — a cost that scales with the size of the graduating curve but does not require any privileged role.

### Recommendation
Bound the deposit leg's minimum acceptable LP mint (or the ratio between the residual deposit and the pool's live reserves/totalSupply) rather than only Bonding's own inventory, and add an explicit fallback (mirroring `_pairRebalance`'s `false`-return/`_seedDirectMint` fallback) for the case where `router.addLiquidity`'s implied LP-mint would round to zero, so `finalizeGraduation` can still complete (e.g., via a larger direct mint that overpowers the inflated reserve) instead of reverting deterministically forever.

### Proof of Concept
1. Creator launches a token via `Bonding.launch`; curve trading proceeds normally.
2. Before the threshold-crossing buy fires (or between phase 1 and phase 2), attacker pre-creates the HyperSwap pair and mints an extremely large, self-funded LP position (`pair.mint(attacker)`), inflating `reserve0/reserve1` and `totalSupply` far beyond the graduation's expected `tokensForLP`/`ltFromPair`.
3. Curve crosses the graduation threshold; phase 1 (`_enterGraduating`) caches `tokensForLP`/`ltFromPair` at the curve-close price and freezes trading.
4. Anyone calls `finalizeGraduation`. `_seedRebalancing` computes the rebalance swap (capped at 99% of Bonding's own inventory of the swapped-in asset) and calls `_routerDepositAndDispose`, whose residual deposit amounts, relative to the attacker's massively inflated pool reserves/`totalSupply`, cause `router.addLiquidity`'s underlying `pair.mint()` to compute `liquidity == 0` and revert with `INSUFFICIENT_LIQUIDITY_MINTED`.
5. `finalizeGraduation` reverts. Because `PendingGraduation` state and the pool's inflated reserves are both static, every subsequent call to `finalizeGraduation` (by anyone) reverts identically — the token is permanently stuck in `Lifecycle.Graduating`, with its curve-raised LT and 250M reserved tokens locked in `Bonding` forever.

    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }

    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }

    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
