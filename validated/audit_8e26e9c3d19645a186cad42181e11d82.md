## Title
Webhook `shop`, `topic`, and `webhook_id` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the shop domain, topic, and webhook id used for dispatching and business logic come from unauthenticated HTTP headers. Any party who can obtain one valid `(body, hmac)` pair for the app's shared secret (e.g., a legitimate merchant using the app, who receives real Shopify webhooks) can replay that exact body/HMAC combination to the app's webhook endpoint while substituting a different `shop-domain` header. `HmacValidator` will still validate successfully because it never checks the header values, and `Registry.process` will hand the handler a `WebhookMetadata` object stamped with the attacker-chosen shop.

### Finding Description
The equality the code should enforce is:

`shop identity authenticated by HMAC == shop identity acted on by the webhook handler`

Instead the code implements:

`shop identity authenticated by HMAC (over body only) != shop identity read from an unauthenticated header, but the header value is trusted anyway`

`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate` only ever compares the computed signature against `verifiable_query.to_signable_string`, i.e. the body — it has no visibility into any header: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards the unauthenticated `request.shop` (along with `topic`/`webhook_id`/`api_version`) to the registered handler as trusted metadata: [4](#0-3) 

Because the HMAC secret (`Context.api_secret_key`) is shared across every shop that installs the app (it is not per-shop), any shop that legitimately receives a real webhook from Shopify obtains a `(raw_body, hmac)` pair that is valid for that same secret regardless of which shop it is replayed against. An attacker who controls their own installed instance of the app (an "unprivileged" actor with no special access to Shopify or to other merchants) can:
1. Capture a legitimate webhook delivered to their own shop (valid body + `x-shopify-hmac-sha256`).
2. Replay the identical body and HMAC header to the app's webhook endpoint, but with `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) changed to a victim shop's domain.
3. `HmacValidator.validate` succeeds because it only checks the body against the shared secret.
4. `Registry.process` looks up the handler by the (attacker-controlled) topic and invokes it with `WebhookMetadata#shop` set to the victim's domain, `body` set to the attacker's captured payload.

This breaks the identity binding between the cryptographically-verified sender and the shop identity the handler is told to act on.

### Impact Explanation
This is a cross-tenant identity confusion: the gem authenticates *that a request came from someone holding the app secret*, but the handler is told to act *as a different, attacker-chosen shop*. If a host application uses `WebhookMetadata#shop` (as documented/intended by this gem) to select which merchant's session/data to update, an attacker-controlled shop can inject events, spoofed body content, or attacker-chosen `webhook_id`/`topic` combinations attributed to a victim shop it does not own — i.e., cross-tenant access, satisfying the Critical impact bar.

### Likelihood Explanation
Any merchant that installs the app receives legitimate webhooks and thus has natural access to a valid `(body, hmac)` pair signed with the app's single shared `api_secret_key`. No credential theft, TLS interception, or privileged access is required — replaying the header-modified request only requires basic HTTP tooling. This is reachable purely through the gem's own webhook verification logic (`Request`/`HmacValidator`/`Registry`), not through misuse of the host application.

### Recommendation
Bind the header-derived identity fields into the signed material, or otherwise independently verify them:
- Include `shop-domain` (and ideally `topic`/`webhook_id`) in the signable string used by `HmacValidator`, so a mismatch invalidates the signature, or
- Have `Registry.process`/`WebhookMetadata` cross-check the header-derived shop against a shop identifier embedded in the verified body payload (most Shopify webhook payloads include shop-scoped identifiers) before dispatching to handlers, or
- Document loudly and enforce in-code that host applications must never trust `WebhookMetadata#shop` without an additional check that the shop is one the app actually expects/knows about for that specific webhook delivery.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and legitimately receives this webhook:
raw_body = '{"id":123,"note":"hello"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# Attacker replays the same body+hmac but claims to be the victim shop:
spoofed_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,          # unchanged, still valid because body unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, NOT covered by HMAC
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

req = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: spoofed_headers)
ShopifyAPI::Webhooks::Registry.process(req)
# => HmacValidator.validate(req) returns true (only checks raw_body)
# => handler receives WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)
#    even though "victim-shop" never sent this webhook.
```
