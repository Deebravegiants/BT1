### Title
Webhook `shop` (and `topic`/`webhook-id`) headers are trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking `Utils::HmacValidator.validate(request)`, but the HMAC signable string is defined as only the raw request body. The `shop`, `topic`, `webhook-id`, and `api-version` values are read from unauthenticated HTTP headers and passed straight into the handler as trusted tenant-identifying metadata.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, by contrast, is read directly from the `shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed material: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` — i.e., it validates that the body matches the HMAC computed with `Context.api_secret_key` — and then immediately forwards `request.shop` (along with `request.topic` and `request.webhook_id`, also header-derived) to the app's handler as trusted data: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` field; it has no knowledge of, and does not bind, the `shop` header: [4](#0-3) 

The gem's own documentation instructs integrators to treat `data.shop` as the authoritative tenant identifier for routing/processing the webhook payload (e.g., `shop_domain: data.shop`): [5](#0-4) 

**The broken equality**: the gem implicitly asserts `shop header value == shop that produced/authorized this body`, but the HMAC only proves `body == HMAC(body, secret)`. There is no cryptographic binding between the `shop-domain` header and the signed body. Any request whose body+HMAC pair is valid (for any topic/shop that ever sent that exact body) will pass validation regardless of what `shop-domain` header accompanies it.

This mirrors the report's bug class precisely: a value acted upon by the receiving logic (`shop`, used for tenant attribution/dispatch) is not covered by the same authentication check (HMAC) that is otherwise required and enforced for the request.

### Impact Explanation
Because a webhook consumer (the host application, following this gem's documented contract) treats `data.shop` as the merchant identifier for storing/dispatching data, an attacker who is a legitimate merchant on the app (thus can trigger real webhooks for their own shop and legitimately observe `body`+`hmac` pairs for generic/templated topics) can replay that same body+hmac pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header for a different, victim shop. `HmacValidator.validate` will still pass (it never inspects the header), and `WebhookMetadata#shop` will report the attacker-chosen shop. If the host app uses this value to select which tenant's data store to write into (the exact pattern the gem's docs recommend), this results in cross-tenant data corruption/injection — writing attacker-controlled webhook payloads into another merchant's records.

This satisfies the Critical impact bar of "cross-tenant access" via the gem's own trust boundary, without requiring the app's `client_secret`, an access token, or any privileged credential — only the ability to receive webhooks for one's own (attacker-controlled) shop and knowledge of the target's app webhook endpoint URL (typically public/known).

### Likelihood Explanation
Likelihood is meaningful but not maximal: it requires the attacker to have at least one legitimate installation of the vulnerable app (to obtain a valid body+HMAC pair from a genuine webhook delivered to their own shop) and for a topic/body to be shop-agnostic or predictable enough to be replayed for another target (e.g., a fixed-schema/test payload, or a topic whose body doesn't itself encode the shop). It also requires the host application to trust `data.shop` for tenant dispatch without independent verification (e.g., without re-deriving shop from a stored webhook-id/shop registration) — which is exactly what this gem's own documentation directs developers to do.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the HMAC signable string, or otherwise cryptographically bind them to the verified body (e.g., validate that the `shop-domain` header corresponds to a shop with an active webhook registration/session before dispatch). At minimum, update `to_signable_string` in `lib/shopify_api/webhooks/request.rb` to include the shop header, and update `HmacValidator`/documentation to make clear that only the body is authenticated so integrators do not rely on unauthenticated headers for tenant identification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers/receives a webhook for a topic with a body that does not itself encode the shop (or is otherwise reusable), e.g. `{}` or a generic payload.
2. Attacker captures the genuine `x-shopify-hmac-sha256` value Shopify sent for that body (computed by Shopify using the real `api_secret_key`, valid for that exact body regardless of shop).
3. Attacker POSTs the same raw body and HMAC to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and any desired `x-shopify-topic`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` — see `lib/shopify_api/webhooks/registry.rb:190` — which only re-computes HMAC over `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`) and succeeds, since the body is unchanged.
5. The handler receives `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"` even though the body was never issued for that shop, and the host app processes/stores it under the victim's tenant per the documented handler contract in `docs/usage/webhooks.md:12-29`.

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
