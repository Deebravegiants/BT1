## Title
Webhook Shop/Topic Spoofing via HMAC Scope Gap — Cross-Tenant Webhook Confusion - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the tenant-identifying fields `shop` and `topic` are read from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only the body-derived HMAC and then dispatches the handler using these unsigned header values, so a caller who possesses one valid `(body, hmac)` pair can attach that untouched signature to a request with an attacker-chosen `X-Shopify-Shop-Domain` and `X-Shopify-Topic`, causing the app to process the payload under a different tenant's identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` and `topic` accessors instead read directly from HTTP headers, which are not part of the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the signature from `verifiable_query.to_signable_string` (i.e., the body) and compares it to the received `hmac`: [3](#0-2) 

`Registry.process` performs this HMAC check and then immediately trusts `request.topic` and `request.shop` (both unauthenticated headers) to select the handler and to build the `WebhookMetadata` passed to application code: [4](#0-3) 

The binding that is broken is: **the shop/topic that is validated (none) ≠ the shop/topic that is acted upon (headers)**. Since the HMAC only binds the *body*, any request with a previously-observed valid `(body, hmac)` pair remains valid regardless of what `shop-domain`/`topic` headers are attached to it. An unprivileged actor who has installed the target app on their own store will receive genuine webhook deliveries (valid body + valid HMAC) for their own shop. Nothing in this gem prevents them from re-submitting that exact body/HMAC pair to the app's public webhook endpoint while swapping in a different `shop-domain` (and/or `topic`) header — the signature check in `HmacValidator.validate` still passes because it never inspects those headers.

### Impact Explanation
This crosses the tenant boundary the gem is supposed to enforce for webhook processing: the app will invoke the registered handler believing the event originated from an arbitrary target shop, with `WebhookMetadata#shop` set to that attacker-chosen value. Any host application logic that keys off `data.shop` (e.g., looking up/updating that shop's stored session or triggering shop-scoped side effects) will act on attacker-controlled data as if it came from the target shop — a cross-tenant confusion/injection primitive at the credential/tenant-boundary level this gem is meant to guarantee.

### Likelihood Explanation
Any user who can install the app on a shop they control (a normal, unprivileged app installation, not requiring `api_secret_key` or any leaked credential) obtains real webhook deliveries with valid `(body, hmac)` pairs. Replaying such a request to the app's webhook endpoint with modified `shop-domain`/`topic` headers requires no cryptographic material beyond what Shopify already handed them for their own shop, and the gem's own `HmacValidator`/`Registry.process` code path offers no defense since it never binds those headers to the signature.

### Recommendation
Include `shop` and `topic` (and any other header fields the handler relies on for identity/routing) in the signed material used for HMAC verification, or otherwise cryptographically bind them to the verified body (e.g., require the app layer to cross-check `shop` against the session/shop the webhook is expected for). At minimum, document that `shop-domain`/`topic` headers are unauthenticated and must not be trusted for tenant identification without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook to the app's public endpoint:
   - Headers: `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid signature of body B>`
   - Body: `B`
3. Attacker resends the identical body `B` and `X-Shopify-Hmac-Sha256` value to the same endpoint, but changes the header to `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) only — validation succeeds because the body/signature pair is untouched: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(topic: <attacker-chosen>, shop: "victim-shop.myshopify.com", body: <attacker body>, ...)`, and any host logic keyed on `shop`/`topic` now operates against the victim tenant using attacker-supplied data.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
