### Title
Unsafe `IERC20.transfer` low-level call ignores boolean return value in `IntentGatewayV2::withdraw` and `SweepDust` handling, permanently freezing solver/user funds on non-standard ERC20 tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` releases escrowed order funds to solvers/users via a raw low-level `.call()` to `IERC20.transfer`, checking only that the external call itself did not revert (`success`), and never inspecting or decoding the returned boolean. Tokens that signal failure by returning `false` instead of reverting (the classic non-compliant ERC20 case, e.g. ZRX-style tokens) will cause the contract to treat a failed transfer as successful, permanently freezing the escrowed funds while marking the order as settled.

### Finding Description
In `withdraw()`, escrowed token amounts are released to the beneficiary using: [1](#0-0) 
```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```
`success` here only reflects whether the low-level call reverted, not whether the ERC20 `transfer` returned `true`. For tokens that return `false` on failure instead of reverting, `success` is `true`, the accounting in `_orders` is decremented, and `_filled[body.commitment]` is set — permanently finalizing the order — even though no tokens were actually transferred to the beneficiary.

The same unsafe pattern is repeated for transaction fee redemption in the same function: [2](#0-1) 

And again in the `SweepDust` request handler within `onAccept`: [3](#0-2) 

This is notable because the rest of the same contract (and the non-Tron `evm/src/apps/IntentGatewayV2.sol`) consistently uses OpenZeppelin's `SafeERC20.safeTransferFrom`/`safeTransfer` for escrow intake and other transfers — e.g. `IERC20(token).safeTransferFrom(msg.sender, dispatcher, amount)` — and the contract even imports and declares `using SafeERC20 for IERC20;`. The `withdraw()` and `SweepDust` paths, however, deliberately bypass `safeTransfer` in favor of a raw `.call` that never checks the returned boolean, breaking that safety guarantee specifically at the fund-release step.

### Impact Explanation
`withdraw()` is the function that finally pays out escrowed order inputs to the winning solver (on `RedeemEscrow`) or refunds the original user (on `RefundEscrow`), and it is directly reachable via a single relayed cross-chain message (`onAccept` → `authenticate` → `withdraw`) or via a GET response callback (`onGetResponse` → `withdraw`) after a user cancels an unfilled order. Once the escrow is decremented and the order marked filled/refunded without an actual successful token transfer occurring, the underlying tokens remain stuck in the `IntentGatewayV2` contract balance with no accounting entry left to claim them — the escrow slot is now zero and the order is finalized, so the funds become permanently unrecoverable through the normal protocol flow. This is a concrete permanent freezing-of-funds scenario for any ERC20 asset in this class that is added to the intents system's supported token set on the Tron deployment.

### Likelihood Explanation
This triggers deterministically whenever the input/output/fee token used in an order is a non-reverting-on-failure ERC20 (a known, documented class of tokens), combined with any transient condition that would cause `transfer` to return `false` (e.g., blacklist status, paused state, or other implementation-specific gating some tokens use instead of reverting). No malicious actor is required — a normal relayed settlement message for a legitimate order is sufficient to trigger the freeze, as long as the escrowed token belongs to this token class. Likelihood is Medium since it depends on which ERC20s the protocol operators choose to support with the Tron IntentGateway deployment, but the code path itself is always reachable by ordinary users, solvers and relayers.

### Recommendation
Use `SafeERC20.safeTransfer` (already imported and used elsewhere in this same contract via `using SafeERC20 for IERC20;`) instead of the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` (both the input-token loop and the fee redemption) and in the `SweepDust` branch of `onAccept()`. This ensures both call-reversion and boolean return-value failures are treated uniformly as reverts, preventing the escrow accounting from being finalized ahead of the actual, successful token transfer.

### Proof of Concept
1. Governance/owner registers a non-standard ERC20 token (one that returns `false` on failed `transfer` rather than reverting, e.g. legacy ZRX-style tokens) as a valid input/output asset for `IntentGatewayV2` on the Tron deployment.
2. A user calls `placeOrder`, escrowing that token; a solver fills the order on the destination chain and the resulting `RedeemEscrow` message is relayed back.
3. `onAccept` → `authenticate` → `withdraw(body, false)` is executed. If the token contract internally rejects the transfer to the beneficiary (e.g., beneficiary blacklisted, contract paused, or any condition the token handles by returning `false`) at line 706, `token.call(...)` still returns `success = true` because the call did not revert.
4. `_orders[body.commitment][token] -= amount` executes, zeroing the escrow record, and `_filled[body.commitment] = beneficiary` marks the order permanently settled — despite the beneficiary never receiving the tokens.
5. The tokens remain stranded in the `IntentGatewayV2` contract's balance with no remaining escrow entry or code path to reclaim them, resulting in a permanent loss of funds for the intended beneficiary.
