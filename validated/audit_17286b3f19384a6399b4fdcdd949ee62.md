### Title
Webhook shop identity spoofing via replay — HMAC signs only the request body, not the `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body. The `shop` identity that the handler subsequently trusts is read from an unsigned header and is never bound to that HMAC, so a legitimate (but malicious) merchant can replay one of their own valid webhook deliveries against the app's webhook endpoint while swapping the shop-domain header to a victim tenant, and the signature check will still pass.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e. the body) and compares it to the received `hmac` header: [2](#0-1) 

`Registry.process` uses this body-only HMAC check as its sole authentication step, then immediately trusts `request.shop` — read from the unsigned `shopify-shop-domain`/`x-shopify-shop-domain` header — as the tenant identity forwarded to the app's handler: [3](#0-2) [4](#0-3) 

Because the app's webhook secret (`api_secret_key`) is shared across every shop that installs the app, an unprivileged internet user who is simply a merchant on the app (i.e., has their own shop with the app installed, no special privilege) can legitimately trigger a webhook on their own store, capture the resulting `(raw_body, hmac)` pair, and replay that exact HTTP request to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to any other shop's domain (a target tenant of the same app). `HmacValidator.validate` will still return `true` because it never inspects the shop header — only the body bytes are covered by the signature. `Registry.process` then dispatches to the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain, even though the body actually originated from the attacker's own shop.

This is the exact bug class flagged in the analog report: a field (`shop`) is acted upon by the identity-sensitive code path but is not covered by the authenticating HMAC. The broken equality is:
`shop authenticated by HMAC` (∅, since HMAC only covers body) ≠ `shop trusted as the tenant key` (`request.shop`, taken from an unauthenticated header).

### Impact Explanation
This breaks tenant isolation: an app built on this gem, relying on `WebhookMetadata#shop` from `Registry.process` to select which merchant's data/config to update, can be made to apply another shop's data-driven action under a spoofed shop identity — a cross-tenant access/write vector, since the attacker fully controls both body content (via their own legitimate webhook triggers) and the claimed shop identity.

### Likelihood Explanation
Exploitation requires no possession of `api_secret_key`, no TLS interception, and no privileged account — only that the attacker be an ordinary merchant with the app installed (an "unprivileged internet user" in the sense of not being a target-tenant admin or holding the app's secret). They can trivially capture a legitimate webhook delivery from their own store (e.g., via a proxy or logging on their own server) and resend it to the public webhook endpoint with a modified shop header.

### Recommendation
Bind the shop identity into the authenticated signable content, or otherwise cryptographically tie the claimed shop-domain header to the HMAC (e.g., include the shop-domain header in the HMAC-signed string, or require per-shop webhook secrets/validation against a known, previously-registered shop for that webhook subscription) before trusting `request.shop` in `Registry.process`.

### Proof of Concept
1. App merchant M installs the app on `m-shop.myshopify.com` and triggers an order webhook, capturing the raw body `B` and the resulting `X-Shopify-Hmac-Sha256: H` header from the delivery to the app's public webhook endpoint.
2. M resends the exact same HTTP request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but replacing `X-Shopify-Shop-Domain: m-shop.myshopify.com` with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the app to process attacker-supplied data as if it came from `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
