### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC signature computed over the raw request body, but the `shop-domain` (as well as `topic`, `webhook-id`, and `api-version`) header used to attribute the event to a tenant is never included in the signed payload. Anyone who can obtain one genuine, validly-signed webhook body/HMAC pair (trivially available to any merchant who installs the app on their own shop) can replay that body to the shared webhook endpoint while swapping the `x-shopify-shop-domain` header to a victim shop, and the gem will accept it as an authentic event for the victim.

### Finding Description
The identity binding that should hold is:
`HMAC-covered bytes == bytes the handler treats as attacker-controlled input for shop attribution`

In `Utils::HmacValidator.validate`, the signature is computed over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw HTTP body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated HTTP headers, independent of the signed body: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then dispatches the handler using `request.shop`, which was never part of the signed material: [4](#0-3) 

Because the same `api_secret_key` is shared across every shop that installs the app, a genuine webhook delivery to *any* shop (including one the attacker legitimately controls, e.g. a free/dev store running the app) produces a `(body, hmac)` pair that is valid for the whole app — not scoped to that shop. The attacker can then POST that same body/hmac to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` will pass (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the victim shop.

### Impact Explanation
This breaks tenant isolation (cross-tenant access): a merchant/attacker with their own legitimate install of the app can inject fabricated webhook events (e.g. `orders/create`, `app/uninstalled`, `customers/redact`, GDPR mandatory webhooks, etc.) that the host application will process as if they originated from a different, victim shop. Depending on how the host app's handler uses `WebhookMetadata#shop` (e.g., to look up/mutate per-tenant records, trigger data deletion, or update billing/subscription state), this can lead to data corruption, spoofed compliance actions, or state confusion across tenants — matching the "cross-tenant access" impact category.

### Likelihood Explanation
The prerequisite is only that the attacker be an unprivileged merchant able to install the app on any shop (including a free development store) and observe one webhook delivery — no access to the app's `client_secret`, TLS interception, or privileged account is required. This is a realistic and cheap-to-execute scenario for any publicly-installable app.

### Recommendation
Do not rely solely on the body HMAC for identity attribution. Either:
- Bind the `shop-domain` (and other identity-relevant headers such as `topic`/`webhook-id`) into the signed material verified against the shop's own webhook secret (Shopify supports per-topic/per-shop verification patterns), or
- Cross-check `request.shop` against the shop associated with the session/subscription the webhook claims to belong to (e.g., verify the shop is a known, currently-installed shop and that the specific `webhook_id` was registered for that shop) before invoking the handler, rather than trusting the header value implicitly.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify sent to the app's shared webhook endpoint.
2. Attacker (or any actor who can reach the app's public webhook endpoint) re-sends an HTTP POST to that same endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (changed)
   - Header `X-Shopify-Topic`/`X-Shopify-Webhook-Id` optionally changed as desired
3. `Utils::HmacValidator.validate` recomputes the HMAC over `B` only and it matches `H`, so validation passes: [1](#0-0) 
4. `Registry.process` invokes the registered handler with `shop: "victim-shop.myshopify.com"` and the attacker-supplied body `B`, even though this event never originated from `victim-shop`: [5](#0-4)
