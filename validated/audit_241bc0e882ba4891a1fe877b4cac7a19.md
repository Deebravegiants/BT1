Confirmed: `WrappedHyperFungibleToken` is deployed by the owner around a fixed `underlying` ERC20 chosen at configuration time (`WrappedConfigOptions.underlying`), and `send()` never verifies the actual amount received before crediting the cross-chain message.

### Title
Fee-on-transfer underlying tokens cause unbacked cross-chain mint/unlock in WrappedHyperFungibleToken - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken.send()` pulls the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` and then dispatches a cross-chain `Message` that always encodes the full `params.amount` requested by the caller, without checking how much the contract actually received.

### Finding Description
In `send()`:
```solidity
function send(HyperFungibleToken.SendParams calldata params) external payable whenNotPaused {
    uint256 msgValue = msg.value;
    if (_isWeth && msgValue >= params.amount) {
        msgValue = msgValue - params.amount;
        IWETH(_underlying).deposit{value: params.amount}();
    } else {
        IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
    }

    DispatchPost memory request = _buildDispatchPost(params);
    ...
``` [1](#0-0) 

`_buildDispatchPost` encodes `params.amount` verbatim into the `Message` body that is delivered to the peer contract on the destination chain, which will mint/unlock that exact amount:
```solidity
bytes memory body = abi.encode(HyperFungibleToken.Message({
    from: abi.encodePacked(msg.sender),
    to: params.to,
    amount: params.amount,
    data: params.data
}));
``` [2](#0-1) 

If `_underlying` is (or later becomes, e.g. via a governance/fee-switch upgrade on the token itself) a fee-on-transfer or rebasing-down token, `safeTransferFrom` delivers `params.amount - fee` to the contract, but the dispatched message still instructs the destination chain to credit the caller-specified `params.amount` in full — an amount the source-chain contract never actually custodied. The identical unguarded pattern also exists in `WrappedHyperFungibleTokenUpgradeable.send()`.

This is the exact bug class from the referenced report: the deposit/lock logic assumes `transferFrom` delivers the exact requested amount and has no way to react when the collateral/underlying token's transfer behavior changes, silently crediting more than was received. Hyperbridge's own `IntentGatewayV2` explicitly guards against this by measuring `balanceOf` before/after `safeTransferFrom` and mutating the escrowed amount to the actual received value:
```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
``` [3](#0-2) 

`WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` lack this safeguard entirely.

### Impact Explanation
Each `send()` call that under-delivers due to transfer fees creates a permanent deficit between the underlying tokens actually locked on the source chain and the wrapped-token liabilities credited on peer chains. Over repeated calls the deficit compounds: the pool of locked underlying tokens becomes insufficient to honor all destination-side redemptions (`onAccept`/timeout refunds transfer the full `message.amount` via `safeTransfer`), eventually causing later redeemers to be unable to withdraw — a permanent freezing/loss of funds for some users, and effectively an unbacked mint/unlock of value on the destination chain relative to what is escrowed on the source. There is no mechanism to detect, halt, or remediate this once the underlying token's transfer behavior changes.

### Likelihood Explanation
`_underlying` is set once by the deploying owner and is expected to remain a normal ERC20; however many real-world tokens (USDT-style tokens, tokens with governance-controlled fee switches, rebasing tokens) can introduce or change transfer fees after initial integration, exactly mirroring the report's scenario ("protocol was supporting collateral X … after some time collateral introduces fee on transfer"). Any single unprivileged `send()` call triggers the mismatch — no special privileges are required, only that the configured underlying token exhibits fee-on-transfer/deflationary behavior.

### Recommendation
Mirror the pattern already used in `IntentGatewayV2`: measure the contract's `balanceOf(_underlying)` before and after `safeTransferFrom` in `send()` (and the WETH deposit path, where applicable) and use the actual received/wrapped amount when building the dispatched `Message`, rather than trusting the caller-supplied `params.amount`. Apply the same fix to `WrappedHyperFungibleTokenUpgradeable.send()`.

### Proof of Concept
1. Owner deploys `WrappedHyperFungibleToken` with `_underlying = TokenX`, currently a standard ERC20 with 0% transfer fee.
2. `TokenX` governance later enables a 1% transfer fee (a supported, unprivileged real-world token behavior; the wrapper contract has no way to remove/replace `_underlying`).
3. Alice calls `send({amount: 1000, dest: ChainB, to: Bob, ...})`. `safeTransferFrom` moves 1000 tokens from Alice, but the wrapper only receives 990 due to the fee.
4. `_buildDispatchPost` still encodes `amount: 1000` in the `Message` sent via ISMP.
5. On `ChainB`, the peer `onAccept` unlocks/transfers 1000 units of the underlying to Bob, even though only 990 were ever locked on `ChainA`.
6. Repeating this drains the `ChainA` custody balance faster than it is topped up; eventually a legitimate redemption on `ChainA` (`onAccept` unlocking back to a user) reverts due to insufficient balance, permanently freezing those users' funds. [4](#0-3)
