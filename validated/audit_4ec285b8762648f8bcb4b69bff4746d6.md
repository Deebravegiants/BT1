Wrong-direction decimal scaling via `saturating_sub` in `convert_to_erc20`/`convert_to_balance` causes unbacked mint or fund loss on cross-chain HFT transfers - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s decimal-scaling helpers, `convert_to_erc20` and `convert_to_balance`, only handle the case where the ERC20-side decimals are *greater than or equal to* the local asset's decimals. When the local asset actually has *more* decimals than the configured remote ERC20 decimals, `u8::saturating_sub` clamps the exponent to `0`, so no scaling is applied at all in the direction that is actually required (division on send, multiplication on receive). The raw balance is forwarded unscaled across the ISMP message, and the destination contract mints/releases exactly `message.amount` with no independent decimals check, trusting the source chain's arithmetic completely.

### Finding Description
`convert_to_erc20` (used in `send()`) and `convert_to_balance` (used in `on_accept`/`on_timeout`) are defined as: [1](#0-0) 

Both use `erc_decimals.saturating_sub(local_decimals)` (or the reverse) as the scaling exponent. `saturating_sub` on unsigned integers clamps negative differences to `0` instead of signaling that the scaling direction must flip. This is correct only when `erc_decimals >= local_decimals` for `convert_to_erc20`, and when `erc_decimals >= local_decimals` for `convert_to_balance` — i.e., only in the single case the comments describe. When a token's local (Substrate) decimals are configured to be *greater* than the registered EVM decimals for a destination chain (a perfectly ordinary configuration — assets frequently have different native decimal precision across chains, e.g., 18 on the parachain vs 6 on the EVM side), the exponent silently clamps to `0` and **no scaling is performed in either direction**:

- `send()` (`modules/pallets/hyper-fungible-token/src/lib.rs`, lines 237-325) burns/locks `params.amount` in local (high-decimal) units, then calls `convert_to_erc20(amount, erc_decimals, decimals)` with `erc_decimals < decimals`. The exponent clamps to 0, so `erc20_amount == amount` — the raw, unshrunk local-decimal value is sent as the ERC20 message amount, i.e. inflated by `10^(local_decimals - erc_decimals)` relative to what should have been sent. [2](#0-1) 

- On the destination EVM contract, `onAccept` decodes `message.amount` and calls `_mint(beneficiary, message.amount)` directly, with zero decimals validation or cross-check against what was actually escrowed on the source chain: [3](#0-2) 

  This mints an amount inflated by `10^(local_decimals - erc_decimals)` relative to the tokens actually escrowed/burned on the source chain — an unbacked mint.

- The reverse direction is also broken: `convert_to_balance`, called in `on_accept` and `on_timeout` on the Substrate side, has the identical clamp bug for the case `erc_decimals < local_decimals` (`modules/pallets/hyper-fungible-token/src/impls.rs` lines 43-52; used at `modules/pallets/hyper-fungible-token/src/module.rs` lines 82-91 and 246-255). In this direction the raw ERC20 amount is credited to the local balance unscaled, which under-credits users if the local asset actually has fewer decimals than assumed, or fails to scale up in the mismatched-decimals configuration, causing permanent fund loss for legitimate cross-chain refunds/receives.

This is structurally the same bug class as the Surge Protocol M-1 finding: an arithmetic helper meant to scale a value between two different decimal precisions uses a subtraction that can go the "wrong way," collapsing to a no-op (equivalent to the interest-calculation division truncating to zero) instead of applying the correct scaling factor, and the result is trusted downstream without any sanity check.

### Impact Explanation
This directly matches "unbacked mint" / "concrete theft or permanent freezing of funds" from the validation criteria:
- If a token is registered with `local decimals > configured erc_decimals` for some destination chain, every `send()` call by any ordinary signed user mints an inflated (by a power-of-ten factor) amount of the wrapped/native ERC20 on the destination chain relative to what was actually locked/burned on the source — draining the token's backing/solvency on that chain, or minting far more supply than was ever escrowed for non-native (mint/burn) tokens.
- The reverse case (receiving inbound messages, or `on_timeout` refunds) can permanently freeze/lose user funds by crediting far less than the amount actually sent, with no way to recover the difference.

Both are triggered by an ordinary user's own extrinsic (`send()`), not by a privileged party — this is reachable from a single submitted extrinsic once the decimal configuration exists, which is a normal (not malicious) registration scenario for assets with heterogeneous decimal precision across chains.

### Likelihood Explanation
Likelihood depends on `register_token`/`update_token` (privileged, `CreateOrigin`) configuring a token whose local decimals exceed the destination chain's registered ERC20 decimals — a config that is entirely legitimate and plausible (e.g., a parachain asset with 18 decimals bridged to a chain whose paired ERC20 was deployed with 6 decimals, or any asymmetric decimals setup). Given that decimals asymmetry across chains is common in production token deployments (as acknowledged by the `Precisions` storage item existing specifically to handle asymmetric decimals), this is a realistic configuration, not a contrived edge case, and once configured, every subsequent `send()`/receive by any unprivileged user triggers the bug automatically and silently (no revert, no bounds check).

### Recommendation
Replace the unsigned `saturating_sub` scaling logic in `convert_to_erc20` and `convert_to_balance` with signed direction-aware scaling: compute `if erc_decimals >= local_decimals { value * 10^(erc_decimals - local_decimals) } else { value / 10^(local_decimals - erc_decimals) }` for `convert_to_erc20`, and the mirrored logic for `convert_to_balance`. Additionally, consider having the destination EVM contract independently validate/cross-check the received `message.amount` against the source's escrowed/burned amount (e.g., by exchanging decimals metadata during registration and re-deriving the expected amount) rather than trusting the raw cross-chain value unconditionally.

### Proof of Concept
1. Governance registers asset `X` via `register_token`/`update_token` with `native = false` (mint/burn model), local `decimals = 18` (the runtime's fungible-asset metadata), and `Precisions::<T>::insert(X, StateMachine::Evm(dest), 6)` (destination ERC20 configured with 6 decimals) — a legitimate config for e.g. a USDC-style asset bridged from an 18-decimal Substrate representation.
2. Any user calls `send(SendParams { asset_id: X, destination: Evm(dest), amount: 1_000 * 10^18, ... })` — burning `1000 * 10^18` raw units of `X` locally.
3. In `send()`, `erc_decimals = 6`, `decimals = 18`. `convert_to_erc20(1000e18, 6, 18)` computes `erc_decimals.saturating_sub(local_decimals) = 6u8.saturating_sub(18u8) = 0`, so `erc20_amount = 1000e18 * 10^0 = 1000e18` unchanged (see `modules/pallets/hyper-fungible-token/src/impls.rs` lines 57-58).
4. The message with `amount = 1000e18` is dispatched to the destination `HyperFungibleTokenUpgradeable` contract, whose `onAccept` calls `_mint(beneficiary, 1000e18)` unconditionally (`sdk/packages/core/contracts/apps/HyperFungibleTokenUpgradeable.sol` line 329).
5. The user burned `1000` tokens' worth (`1000e18` at 18 decimals) on the source chain but receives `1000e18` raw units at 6-decimal precision on the destination — i.e., `10^12` times the intended amount (`1,000,000,000,000,000` tokens instead of `1,000`), an unbacked mint of enormous magnitude, confirmable by unit-testing `convert_to_erc20(1000e18, 6, 18)` and observing it returns `1000e18` instead of the correct `1000e18 / 10^12 = 1000e6`.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({from: message.from, to: beneficiary, source: string(request.source), amount: message.amount});
    }
