## Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` fields are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook only by HMAC-validating the raw request body, but the `shop`, `topic`, `webhook_id`, and `api_version` values used to identify the tenant and route the payload come from unauthenticated HTTP headers that are never included in the signed data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`HmacValidator.validate` HMACs exactly that signable string against `Context.api_secret_key`: [2](#0-1) 

But `Registry.process` then trusts the `shop` (and `topic`, `webhook_id`, `api_version`) fields — which are read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header, entirely outside the HMAC computation — and forwards them to the app's handler as the tenant identity: [3](#0-2) [4](#0-3) 

The gem's own documentation instructs host apps to use `data.shop` to route/attribute the webhook to a specific merchant (e.g., enqueue a background job keyed by `shop_domain`), and explicitly claims processing "will verify the request did indeed come from Shopify": [5](#0-4) [6](#0-5) 

The broken identity binding, stated as an equality that fails to hold:
`shop authenticated by HMAC (covers only raw_body)` ≠ `shop used to attribute/process the webhook (read from unauthenticated shop-domain header)`.

Because a given Shopify app uses a single `api_secret_key` shared across every installed shop, an attacker who controls one legitimately-installed shop can capture a validly HMAC-signed webhook body that Shopify sent for their own shop, then replay that body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) to name a *different* victim shop. The HMAC check in `HmacValidator.validate_signature` (`OpenSSL.secure_compare` over `to_signable_string`, i.e. the body only) still passes because the body itself is untouched, yet `WebhookMetadata.shop` reported to the handler is now the attacker-chosen victim shop.

### Impact Explanation
This is a cross-tenant integrity issue: the app-side webhook handler will process attacker-supplied data believing it originates from an arbitrary victim shop (any shop the attacker chooses to name, not just their own), since the tenant identity (`shop`) carried through `WebhookMetadata` is never bound to the HMAC signature. Any host application that uses `data.shop`/`data.topic` to key data storage, trigger per-tenant side effects, or authorize downstream actions (exactly the pattern shown in the gem's own docs and in `shopify_app`) can be tricked into associating attacker-controlled body content with another merchant's shop, i.e., cross-tenant access/confusion.

### Likelihood Explanation
Requires only that the attacker control (or previously receive webhooks for) one shop using the same app — a realistic "unprivileged internet user" position for any developer/merchant who installs the target app. No access to `api_secret_key`, access tokens, or Shopify infrastructure is needed; only the ability to replay an HTTP POST with modified headers to the app's public webhook endpoint.

### Recommendation
Include the identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed string, or otherwise cryptographically bind them to the verified payload before they are used to attribute the webhook to a tenant, and document that host apps must not trust unauthenticated request headers for tenant routing. At minimum, cross-check the header-derived `shop` against the shop domain embedded in the (currently unsigned) JSON body where such a field exists, or fetch/verify shop identity independently rather than relying solely on `x-shopify-shop-domain`.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST: body `B`, and header `x-shopify-hmac-sha256: H` (valid, computed by Shopify using the app's `api_secret_key` over `B`).
2. Replay to the app's webhook endpoint:
   - `raw_body`: unchanged `B`
   - `x-shopify-hmac-sha256`: unchanged `H`
   - `x-shopify-shop-domain`: rewritten to `victim.myshopify.com`
   - `x-shopify-topic`: unchanged or attacker-chosen registered topic
3. `HmacValidator.validate` succeeds because it only checks `B` against `H`; `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled body content attributed to the victim shop.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
