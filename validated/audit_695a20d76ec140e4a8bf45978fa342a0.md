### Title
Webhook `shop` (and `topic`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing/replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies the webhook HMAC over the raw request body only, but the `shop` (and `topic`) values that the application actually uses to identify the tenant are read from HTTP headers that are completely excluded from the signed content. This breaks the identity binding "shop the webhook claims to be from == shop the HMAC actually authenticates," letting an attacker who can obtain a single valid `(raw_body, hmac)` pair from the shared app-level HMAC secret replay it while forging the `shop-domain` header to impersonate any other merchant/shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers, none of which participate in the HMAC computation: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` (i.e., the body) and compares it against the `hmac` header value: [3](#0-2) 

`Registry.process` treats a passing HMAC check as sufficient to trust the request, then forwards the *header-derived, unauthenticated* `request.shop` and `request.topic` straight to the application's webhook handler as the tenant identity for that webhook: [4](#0-3) 

Because the app's HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is the same for every shop the app serves, any `(raw_body, hmac)` pair that was ever validly generated for the app — for example a genuine webhook delivered to the attacker's own development/test store — remains cryptographically valid forever and is not bound to a particular shop. An attacker who has legitimate access to one shop connected to the app can capture such a pair and replay it to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will report success because it never looks at that header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop while the body content is actually the attacker's own (replayed) payload.

This is the same class of bug flagged in the report: the code authenticates one set of bytes (`raw_body`) but acts on a different, unauthenticated field (`shop`) as if it were verified — an identity binding of `verified_shop == acted_upon_shop` that does not actually hold.

### Impact Explanation
This allows cross-tenant confusion in webhook processing: an app that keys any behavior off `WebhookMetadata#shop` (e.g., looking up/loading the shop's session or record, applying data to "this shop") can be made to associate attacker-controlled, replayed webhook content with an arbitrary victim shop's identity, despite a "successful" HMAC check. This matches the Critical/High bucket of cross-tenant access enabled by a signature check that authenticates the wrong scope of data.

### Likelihood Explanation
The attacker needs at least one legitimately obtained `(raw_body, hmac)` pair for the app (e.g., from their own connected store, or from any leaked/logged webhook delivery), which is a low bar for anyone with access to an installed instance of the app. No access to `api_secret_key`, access tokens, or the victim's credentials is required — only the ability to replay an HTTP POST with a modified header.

### Recommendation
Include `shop`, `topic`, and `webhook_id`/`api_version` in the signed payload used for HMAC validation (or otherwise cryptographically bind them to the raw body), and/or require the consuming application to cross-check `request.shop` against a shop it has an active, previously-established session/install for before trusting the payload, rather than relying on the header value alone once the HMAC over the body passes.

### Proof of Concept
1. Attacker installs/uses the target app on their own shop `attacker.myshopify.com` and receives a genuine webhook: raw body `B`, `X-Shopify-Hmac-Sha256: H` (valid for the app's shared secret), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends the exact same `B`/`H` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `HmacValidator.validate` recomputes the HMAC over `B` only and it matches `H`, so it passes: [5](#0-4) 
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop == "victim.myshopify.com"`, even though the payload `B` never originated from or was authenticated for that shop.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
