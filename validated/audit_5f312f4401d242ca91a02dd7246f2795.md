### Title
Zero-length `erc20TokenAddresses` bypasses all Emporium/Hinkal balance accounting while `EmporiumStack.ops` can still move real ETH - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `dimensions.tokenNumber == 0`, `HinkalHelper.dimensionsCheck` forces `circomData.erc20TokenAddresses` to be an empty array, which makes both the accounting loop in `EmporiumUpgradeable.runAction` and the accounting loop in `Hinkal.transact` execute zero iterations. The `stack.ops` execution loop in `runAction`, however, is bounded by `stack.ops.length`, not by `circomData.erc20TokenAddresses.length`, so it still runs and can call `op.endpoint.call{value: op.value}(...)`, moving ETH out of Emporium's balance with no `balancesBefore`/`balancesAfter` check anywhere in the call stack.

### Finding Description
The claimed equality: `{ETH moved by the tx} == {assets accounted for in balancesBefore/balancesAfter}`.

- `HinkalHelper.dimensionsCheck` (`contracts/HinkalHelper.sol:68-71`) requires `circomData.erc20TokenAddresses.length == dimensions.tokenNumber`, so an attacker choosing `dimensions.tokenNumber = 0` forces `erc20TokenAddresses = []`. [1](#0-0) 
- `EmporiumUpgradeable.runAction` computes `balancesBefore`/`balancesAfter` from `circomData.erc20TokenAddresses` (empty), then unconditionally executes `stack.ops` for `i < stack.ops.length` (independent of the token array), where the stateless branch does `op.endpoint.call{value: op.value}(op.callData)`. [2](#0-1) 
- The final accounting loop `for (i < circomData.erc20TokenAddresses.length)` that computes `balanceChange` and reverts on `BalanceChangeShouldBePositive` never runs (0 iterations) because the array is empty. [3](#0-2) 
- The outer caller, `Hinkal.transact`, has an identical loop over `circomData.erc20TokenAddresses` for `balanceDif`/slippage checks, which is likewise skipped entirely for a zero-length array. [4](#0-3) 
- The code even documents that Emporium can legitimately carry a resting balance across transactions ("the only case when balanceChange can be < 0, when there were some funds on emporium before the call"), i.e., Emporium's ETH/token balance is not guaranteed to be zero between transactions (e.g., dust left from swaps/partial fills), so real funds can sit there. [5](#0-4) 
- `verifyWallet` requires no signature at all when `stack.signerAddress == address(0)` (only marks `usedMessages`), so an attacker fully controls an unsigned `EmporiumStack` with an arbitrary `ops` array of their choice. [6](#0-5) 

**Why this is gated, and the residual uncertainty:** to reach `runAction` at all, the attacker's transaction must pass `Hinkal.transact`'s `verifyProof(... buildVerifierId(dimensions, externalActionId) ...)` check, which requires a **registered verifier for the exact `(tokenNumber=0, nullifierAmount=0, outputAmount=0, externalActionId=Emporium)` combination**. Verifier registration is `onlyOwner` (`VerifierFacade.registerVerifiers`), so the attacker cannot register this verifier themselves; whether the deployed protocol ever compiles/registers a degenerate zero-dimension circuit could not be confirmed from this repo (circuit-generation/deployment scripts enumerating supported dimensions were not found in the indexed portion of the codebase). If no such verifier exists on-chain, `verifyProof` reverts with "Cannot find appropriate verifier" and the entire path is blocked. This is a genuine unknown that could not be resolved with the available tools, and per the indexing-coverage note, a Devin session with full repo/script access would be needed to confirm whether a zero-token verifier is ever deployed.

### Impact Explanation
If a verifier for the degenerate `(0,0,0,EmporiumId)` dimensions is registered, an attacker can drain any ETH resting in the Emporium contract (dust/leftover balances from prior legitimate swaps or actions) to an address they control, with zero on-chain accounting anywhere in `Hinkal.transact` or `EmporiumUpgradeable.runAction`. This is repeatable every time Emporium accumulates a nonzero ETH balance. This matches the Critical category ("direct theft of shielded or in-flight user funds") only insofar as the drained ETH belongs to other users/protocol flows rather than the attacker's own self-deposited funds; the question's own proposed PoC (attacker funds Emporium via `receive()` with their own ETH) does not establish theft of a third party's assets by itself.

### Likelihood Explanation
- Requires the attacker to construct an unsigned `EmporiumStack` (`signerAddress = address(0)`) with an `ops` entry whose `op.value` targets Emporium's resting balance — fully within attacker control.
- Requires `dimensions = {0,0,0}` and correspondingly empty `CircomData` arrays — passes `dimensionsCheck` trivially.
- **Hard precondition outside attacker control**: a verifier must be registered on-chain for that exact zero-dimension `verifierId`. This is an owner/deployment decision that could not be confirmed to exist in this codebase.
- Requires Emporium to actually be holding ETH at attack time (either attacker's own deposit, which is not theft, or residual dust from other flows, which would be theft but its magnitude/frequency is unconfirmed).

### Recommendation
- In `EmporiumUpgradeable.runAction`, do not allow the `stack.ops` execution loop to run when `circomData.erc20TokenAddresses.length == 0` unless `stack.ops` is also empty, or otherwise require that any ETH/token moved by `op.value`/`op.callData` be tied to a declared token in `circomData.erc20TokenAddresses` (i.e., forbid `tokenNumber == 0` combined with non-empty `stack.ops` that carry `value > 0` or touch balances).
- Track Emporium's ETH/ERC20 balance independent of `circomData.erc20TokenAddresses` (e.g., snapshot `address(this).balance` and all touched token balances regardless of the declared array length) so `BalanceChangeShouldBePositive` cannot be structurally bypassed by an attacker-chosen empty array.
- As defense in depth, never register a verifier for `tokenNumber == 0` for external-action-bearing `verifierId`s, and add an explicit `require(dimensions.tokenNumber > 0)` for any transaction with `externalActionId != 0`.

### Proof of Concept
Foundry test plan (blocked on confirming a `(0,0,0,EmporiumId)` verifier is registered in the target deployment; if none exists, this path is unreachable and the finding is theoretical only for this repo's default configuration):
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, and a mock verifier registered for `dimensions = {0,0,0}` with `externalActionId = EmporiumId` that always returns `true` (simulating an attacker who can produce a valid proof for the degenerate circuit, or noting this requires the real circuit/verifier to exist).
2. Send ETH directly to Emporium via a third-party legitimate transaction that intentionally leaves dust (or, to isolate the code-level bug only, via `receive()`); record `address(emporium).balance` as `B0`.
3. Craft `circomData` with `erc20TokenAddresses = []`, `dimensions = {0,0,0}`, `externalActionData.externalActionMetadata` encoding an `EmporiumStack{signerAddress: 0, ops: [{endpoint: attacker, invokeWallet: false, value: B0, callData: ""}]}`.
4. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from the attacker EOA.
5. Assert: `address(emporium).balance == 0` after the call, `attacker.balance` increased by `B0`, and the returned `utxoSet` is length 0 (empty), i.e., no accounting entry exists for the moved ETH — proving `{ETH moved} = {B0} != {} = {accounted}`.
