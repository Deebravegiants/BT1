### Title
Webhook HMAC Does Not Cover Shop Domain, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from only the raw request body, while the shop identity used by the handler (`request.shop`) is taken from an unauthenticated HTTP header. This breaks the intended binding `HMAC(secret, signed_bytes) == HMAC(secret, signed_bytes)` from also covering *which shop* the payload is attributed to, letting an attacker who controls one installed shop replay a legitimately-signed webhook body under a different, victim shop's identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then unconditionally trusts `request.shop` (and other headers) to construct the `WebhookMetadata` handed to the app's registered handler: [3](#0-2) 

`HmacValidator.validate` confirms only that the body bytes are authentic for the app's shared `api_secret_key`; it says nothing about which shop the body came from: [4](#0-3) 

Because `Context.api_secret_key` is a single static secret configured once for the whole app (not derived per-shop/session), the same secret is used to validate webhook deliveries for every shop that installs the app: [5](#0-4) 

Equality that should hold but doesn't: `shop-that-produced-and-signed-this-body == shop-claimed-in-header`. Since the header is outside the HMAC, the two can diverge without invalidating the signature.

### Impact Explanation
This is a cross-tenant identity-binding break. Consider a multi-tenant app installed on many shops with one global `api_secret_key`. An attacker who owns/controls Shop A (an unprivileged internet user relative to other tenants) can:
1. Trigger a legitimate Shopify event on their own Shop A, causing Shopify to deliver a webhook to the app with a valid `X-Shopify-Hmac-Sha256` computed over the body using the shared `api_secret_key`.
2. Capture that `(raw_body, hmac)` pair.
3. Replay the identical body/HMAC to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header with a victim shop B's domain.

`Registry.process` will call `HmacValidator.validate`, which passes because the body is unchanged and the secret is shared, and will then invoke the app's handler with `WebhookMetadata#shop == "shop-b.myshopify.com"`. If the host application's handler trusts `data.shop` to select which tenant's records to update, sync, or delete (a documented, expected usage per this gem's webhook contract), the attacker achieves cross-tenant data injection/manipulation — satisfying the "cross-tenant access" Critical impact bar.

### Likelihood Explanation
Likelihood is elevated because: no credentials beyond installing the app on one's own shop (a normal unprivileged onboarding action) are required; capturing a genuine webhook delivery for one's own shop is trivial (the attacker is the recipient's shop owner); and forging the `X-Shopify-Shop-Domain` header requires no cryptographic material since it sits entirely outside the signed bytes.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed payload verification, or independently bind `request.shop` to a value verified through a channel that is itself authenticated (e.g., cross-check against the shop associated with the specific webhook subscription/session, not a raw incoming header). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted by handlers without additional verification.

### Proof of Concept
1. Register an app-level webhook handler that trusts `data.shop` to select a tenant record, per the documented pattern: [6](#0-5) 
2. As the owner of Shop A (attacker-controlled, legitimately installed the app), trigger any subscribed event so Shopify delivers a real webhook: raw body `B`, header `X-Shopify-Hmac-Sha256: H = HMAC_SHA256(api_secret_key, B)`, and `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
3. Resend an HTTP request to the app's webhook endpoint with the same body `B` and same `H`, but header `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Utils::HmacValidator.validate(request)` returns `true` because it only checks `B` against `H` using the shared secret (`lib/shopify_api/utils/hmac_validator.rb:12-31`).
5. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to act on victim-shop's tenant using attacker-supplied body content.
