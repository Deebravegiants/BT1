### Title
Payload-selected route contracts can execute unauthorized token transfers beneath strategy authorization - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
The controller accepts opaque attacker-influenced `swap` bytes on `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`, then forwards them to the configured router without validating the contracts encoded in the route. The controller only binds its own input-token transfer to the router and checks the controller’s measured input/output balances; it does not constrain third-party contract calls made while resolving the route. If simulation records a malicious route contract’s `token.transfer(victim, attacker, amount)` as a child of the victim’s authorization and the victim signs that tree, unrelated wallet funds are transferred even though the lending strategy itself remains solvent. This is the Soroban analog of resolving an attacker-controlled external location without containment checks.

### Finding Description
`swap_collateral` authenticates the caller, authorizes the account operation, withdraws the requested collateral into controller custody, and invokes `withdraw_and_swap_from_supply` with the caller-provided `swap` bytes [1](#0-0) . The common swap path only requires non-empty bytes, snapshots the controller’s input and output balances, authorizes one exact `controller -> router` token transfer, and then calls `router.execute_strategy(controller, amount_in, swap)` [2](#0-1) . The authorization deliberately has no controller-granted sub-invocations, but the opaque route still determines which external contracts run beneath the router [3](#0-2) .

The post-route checks only reject input-balance growth, overspending of the authorized input, and zero output; they do not inspect or restrict side effects performed by route-selected contracts [4](#0-3) . The same opaque bytes are exposed directly on the public `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral` entrypoints [5](#0-4) [6](#0-5) [7](#0-6) .

The relevant Soroban behavior is proven by the repository’s authorization test: a route-selected pool can call `token.transfer(victim, attacker, amount)`, simulation records that transfer as a child of the victim’s `swap_collateral` authorization, and enforcement executes it when the returned poisoned tree is signed [8](#0-7) [9](#0-8) . The same test shows that a fair output can still be delivered, so controller-side balance checks do not detect the unrelated wallet transfer [10](#0-9) .

### Impact Explanation
An attacker who supplies malicious route bytes to a user can steal unrelated tokens held by that user’s address while the requested lending operation completes normally. The stolen token need not be listed by XOXNO Lending and is not limited to the strategy’s `amount_in`: the malicious route contract can encode a different token, recipient, and amount. The unauthorized transfer must appear in the authorization tree produced by simulation and be signed by the victim, but a fair-looking route can make the strategy succeed and can hide the malicious effect behind route execution. This is theft of user funds rather than merely bad pricing, MEV, or route quality.

### Likelihood Explanation
Exploitation requires the victim to use attacker-supplied or tampered route bytes and sign the resulting authorization tree. That is plausible for integrations that accept route payloads as data, especially because the route is opaque `Bytes` to the controller and a malicious venue can still return sufficient output to satisfy the router and controller checks. The attack does not require compromising governance, the pool, or the configured router; an unprivileged attacker can deploy the route-selected contract and choose its behavior. The likelihood is reduced by clients that decode routes and reject authorization trees containing unexpected child invocations.

### Recommendation
Do not treat `swap` bytes as an opaque safe payload. At minimum, clients and contract callers must decode the route before submission, verify every token/pool/venue address against expected or allowlisted addresses, simulate the complete transaction, and reject any authorization tree containing unexpected nested invocations. Protocol-level mitigation should add venue/pool allowlisting or a decoded-route callback policy that rejects external calls outside explicitly approved DEX contracts. Until such containment exists, wallets and SDKs should display a hard warning whenever a strategy authorization includes any token transfer other than the expected input pull.

### Proof of Concept
1. Deploy a malicious contract exposing the function expected for the chosen route venue. Its function calls `token.transfer(victim, attacker, wallet_balance)` for a token unrelated to the lending markets. The repository’s `RogueHopPool` fixture implements exactly this behavior [11](#0-10) .
2. Construct route bytes naming the malicious contract while preserving a valid `token_in`, `token_out`, and sufficient `min_out`, as in `route_through_pool_stealing` [12](#0-11) .
3. Have the victim call `swap_collateral(caller=victim, account_id, current=USDC, amount=50_000_000_000, new=ETH, swap=malicious_route)` or another affected strategy entrypoint [13](#0-12) .
4. During simulation, the rogue pool’s unrelated wallet-token transfer is recorded beneath the victim’s `swap_collateral` authorization [14](#0-13) .
5. If the victim signs the simulated tree, the unrelated wallet balance moves to the attacker while the account receives the expected swapped collateral [10](#0-9) .

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
