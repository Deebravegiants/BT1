### Title
`validateDogeAddress` accepts base58 strings with corrupted checksums, letting unpayable addresses reach the POA withdrawal memo - (File: packages/intents-sdk/src/lib/validateAddress.ts)

### Summary
`validateDogeAddress` matches only the shape `/^[DA][1-9A-HJ-NP-Za-km-z]{25,33}$/` and never verifies the base58Check `sha256(sha256(payload))` checksum, unlike `validateBtcBase58Address`, `validateTronBase58Address`, `validateLitecoinBase58Address`, and `validateDashAddress` in the same file which all decode and compare the 4-byte checksum. Because `PoaBridge.validateWithdrawal` relies solely on `validateAddress` to gate `destinationAddress` before calling `createWithdrawIntentPrimitive`/`createWithdrawMemo` (which embeds the address verbatim as `WITHDRAW_TO:<address>`), a Dogecoin address with one flipped base58 character but the right shape/length passes validation and gets signed into the withdrawal intent.

### Finding Description
The claimed broken equality is: "address accepted by `validateAddress(address, Chains.Dogecoin)` == a real, checksum-valid, payable Dogecoin address." Tracing the code:

- `validateAddress` dispatches Dogecoin to `validateDogeAddress` at packages/intents-sdk/src/lib/validateAddress.ts:41-42, 329-331.
- `validateDogeAddress` is purely a regex test with no `base58.decode` call and no checksum comparison, in contrast to `validateBtcBase58Address` (lines 140-158), `validateTronBase58Address` (lines 384-403), `validateLitecoinBase58Address` (lines 537-567), and `validateDashAddress` (lines 801-831), all of which decode the base58 payload and verify `sha256(sha256(payload))` against the trailing 4 checksum bytes.
- `PoaBridge.validateWithdrawal` (packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:170-188) is the only gate on `destinationAddress` for the POA Dogecoin route; it throws `InvalidDestinationAddressForWithdrawalError` only if `validateAddress` returns `false`. `compareAddresses` (lines 207-219) only checks the address doesn't equal the token's own origin-chain address — it does not re-validate payability.
- `createWithdrawIntentPrimitive` → `createWithdrawMemo` (packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.ts:6-49) embeds `receiverAddress` verbatim into `WITHDRAW_TO:<address>` with no additional checksum check.

An attacker (an ordinary user calling `sdk.createWithdrawalIntents`/`processWithdrawal` with their own `destinationAddress`) can supply a base58 string of the correct length and alphabet, starting with `D` or `A`, whose last character has been altered from a valid captured address, so the checksum bytes no longer match `sha256(sha256(payload))`. The regex still matches (base58 alphabet membership and length are unaffected by single-character substitution within the same alphabet), so `validateAddress` returns `true`, `validateWithdrawal` does not throw, and the corrupted address is signed into the on-chain withdrawal intent's memo.

### Impact Explanation
The user's own intents-balance funds are debited via a signed `ft_withdraw` intent whose `memo` field contains an address that will not resolve to a spendable UTXO on the Dogecoin network (real DOGE wallets/nodes reject invalid checksums). Once the relayer bridge executes the withdrawal against this memo, the funds leave the intents balance with no way to recover them — this matches the "Critical: funds delivered to a wrong address ... with no recovery" category. This is repeatable per withdrawal call and requires no privileged access; only the caller's own signature over their own withdrawal request.

### Likelihood Explanation
Preconditions: attacker only needs to be a normal user withdrawing DOGE (`nep141:doge.omft.near`) with a `destinationAddress` they construct (or mistype) themselves; no dependency on relayer/RPC/bridge trust. Cost is trivial — flipping one base58 character in an otherwise well-formed 26–34 char string starting with `D`/`A` still satisfies the regex with high probability (base58 alphabet is 58 characters, so most single-character substitutions keep it within charset). This is deterministic and fully client-side reproducible without any external component.

### Recommendation
Implement full base58Check verification for `validateDogeAddress`, mirroring `validateBtcBase58Address`/`validateDashAddress`: decode with `base58.decode`, require exactly 25 bytes, validate the version byte(s) for Dogecoin mainnet (`0x1e` for P2PKH "D...", `0x16` for P2SH "A..."), and verify the trailing 4-byte checksum equals `sha256(sha256(payload)).subarray(0,4)`.

function validateBtcBase58Address(address: string): boolean {
	const decoded: Uint8Array = base58.decode(address);

	// version (1) + hash160 (20) + checksum (4) = 25 bytes
	if (decoded.length !== 25) return false;

	const version = decoded[0];
	// 0x00 = P2PKH mainnet, 0x05 = P2SH mainnet
	if (version !== 0x00 && version !== 0x05) return false;

	const payload = decoded.subarray(0, 21);
	const checksum = decoded.subarray(21, 25);
	const expectedChecksum = sha256(sha256(payload)).subarray(0, 4);

	for (let i = 0; i < 4; i++) {
		if (checksum[i] !== expectedChecksum[i]) return false;
	}
	return true;
}

export function createWithdrawIntentPrimitive(params: {
	assetId: string;
	destinationAddress: string;
	destinationMemo: string | undefined;
	amount: bigint;
}): Extract<IntentPrimitive, { intent: "ft_withdraw" }> {

		params.assetId,

	return {

		token: tokenAccountId,
		receiver_id: tokenAccountId,
		amount: params.amount.toString(),
		memo: createWithdrawMemo({

		}),
		min_gas: MIN_GAS_AMOUNT,
	};
}

function createWithdrawMemo({
	receiverAddress,
	xrpMemo,
}: {
	receiverAddress: string;
	xrpMemo: string | undefined;
}) {
	// Strip "bitcoincash:" prefix from BCH CashAddr addresses
	const normalizedAddress = receiverAddress
		.toLowerCase()
		.startsWith("bitcoincash:")
		? receiverAddress.slice("bitcoincash:".length)
		: receiverAddress;

	const memo = ["WITHDRAW_TO", normalizedAddress];

	if (xrpMemo != null && xrpMemo !== "") {
		memo.push(xrpMemo);
	}

	return memo.join(":");
}
