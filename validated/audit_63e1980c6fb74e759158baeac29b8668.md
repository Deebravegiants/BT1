## Finding

Confirmed: the fix applied to `IntentGatewayV2.placeOrder` (balance-delta measurement for fee-on-transfer/rebase tokens, see `evm/src/apps/IntentGatewayV2.sol:320-322` and `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` FoT tests) was **not** applied to `WrappedHyperFungibleToken.send()`, which is the exact analog of the reported `BlueBerryBank.lend` bug.

### Title
Rebase/FoT underlying tokens cause reserve insolvency in `WrappedHyperFungibleToken` cross-chain bridging - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` locks the `_underlying` ERC-20 via `safeTransferFrom(msg.sender, address(this), params.amount)` and then dispatches a cross-chain message asserting that `params.amount` was locked, without ever checking the actual balance delta received by the contract.

### Finding Description
In `send()`: [1](#0-0) 

the contract calls `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` and immediately builds and dispatches a `Message{ amount: params.amount, ... }` via `_buildDispatchPost`, using the nominal `params.amount` rather than the actually-received balance delta. If `_underlying` is a fee-on-transfer or negative-rebase token, the contract receives strictly less than `params.amount`, yet the cross-chain message still claims the full nominal amount was locked.

On the destination chain, the peer `WrappedHyperFungibleToken` deployment's `onAccept` unconditionally releases the full claimed amount from its own local reserve pool: [2](#0-1) 

Since this is a lock-and-release (not mint/burn) bridge model — each chain's `WrappedHyperFungibleToken` deployment holds its own segregated `_underlying` reserve — every FoT/rebase transfer permanently drains more from the destination reserve than was actually escrowed on the source chain. This is architecturally identical to the reported `BlueBerryBank.lend` issue: the contract trusts the nominal transfer amount instead of computing `balanceAfter - balanceBefore`. The exact fix pattern already exists elsewhere in the same codebase in `IntentGatewayV2.placeOrder`, confirming the vulnerable pattern here was simply not remediated: [3](#0-2) 

The identical unguarded pattern also exists in `WrappedHyperFungibleTokenUpgradeable.send()`: [4](#0-3) 

### Impact Explanation
Each cross-chain transfer of a FoT/rebase underlying token causes the destination-chain reserve to pay out more than was actually locked on the source chain, progressively insolvent-izing the destination `WrappedHyperFungibleToken` reserve pool. This is a real fund-freezing/loss condition: legitimate later users attempting to bridge back or redeem will find the reserve pool short, effectively freezing/losing a portion of aggregate user funds. This is reachable by any unprivileged user calling `send()` with a whitelisted-but-FoT/rebase underlying, requiring no privileged role.

### Likelihood Explanation
Likelihood depends on the owner configuring `_underlying` to a fee-on-transfer or rebasing ERC-20 via `configure()`. Given the sibling `IntentGatewayV2` module explicitly added handling and dedicated tests for FoT tokens, it is evident that the protocol intends to support such tokens as bridged assets, making this a realistic misconfiguration/oversight rather than a purely theoretical scenario.

### Recommendation
In `WrappedHyperFungibleToken.send()` (and the upgradeable variant), measure `balanceBefore`/`balanceAfter` of `_underlying` around the `safeTransferFrom` call, and use the actual delta as the `amount` encoded into the dispatched `Message`, mirroring the fix already present in `IntentGatewayV2.placeOrder` (`evm/src/apps/IntentGatewayV2.sol:319-323`).

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` = a 1% fee-on-transfer token, deployed identically on chain A and chain B, each holding independent reserves.
2. User on chain A calls `send({ amount: 1000, to: recipient, dest: chainB, ... })`. `safeTransferFrom` moves 1000 tokens from user, but the contract only receives 990 (1% fee burned/redirected). `send()` still dispatches `Message{ amount: 1000 }`.
3. On chain B, `onAccept` executes `IERC20(_underlying).safeTransfer(beneficiary, 1000)` — releasing 1000 from chain B's reserve even though chain A's reserve only grew by 990.
4. Repeating this drains chain B's reserve pool by the cumulative FoT/rebase deficit, eventually preventing other users from redeeming/bridging back their own legitimately-escrowed balances.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }
