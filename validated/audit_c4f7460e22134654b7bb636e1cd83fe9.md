### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body, but the `shop` value that the gem hands to the application's webhook handler is read from an HTTP header that is not part of the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read from HTTP headers, none of which feed into `to_signable_string`: [2](#0-1) 

`Registry.process` validates only that HMAC: [3](#0-2) 
then immediately builds `WebhookMetadata` using the unauthenticated `request.shop` header value and passes it to the app's handler.

The documented contract explicitly states that `process` "will verify the request did indeed come from Shopify": [4](#0-3) 
and instructs app authors to trust `data.shop` as "The shop domain of the webhook": [5](#0-4) 

The identity binding that should hold is:

`shop value cryptographically bound by HMAC == shop value delivered to the application handler`

In reality, the HMAC (computed with the app's single, shop-independent `client_secret`) only binds the raw body bytes; the `shop` header is never part of the signed material, so:

`HMAC-authenticated bytes (raw_body only) ≠ shop attribute trusted by the handler (x-shopify-shop-domain header)`

Because a single app secret signs webhooks for *every* installed shop, any shop that has legitimately installed the app (an ordinary, unprivileged action available to any merchant/attacker) will receive genuine webhook deliveries with a valid `hmac` over a body the attacker fully controls (their own shop's data). The attacker can then replay that exact `raw_body` + `hmac` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with a victim shop's domain. `HmacValidator.validate` still passes (it never looks at the header), and `Registry.process` calls the handler with `shop: <victim-shop>` while `body` is fully attacker-controlled content originally signed for the attacker's own shop.

### Impact Explanation
This breaks the tenant isolation the gem is documented to provide: an app relying on `data.shop` from `WebhookMetadata` (as instructed by the gem's own docs) to select which merchant's data/session to update will attribute attacker-controlled webhook content to an arbitrary victim shop, since the signature check gives false assurance that the whole request (including the shop identity) originated from Shopify for that shop. This is a cross-tenant data/identity confusion reachable by any unprivileged internet user who can install the app on their own store (or otherwise obtain one valid signed webhook), without needing the app's `client_secret`, an access token, or any privileged access.

### Likelihood Explanation
Requires only: (1) a genuine webhook delivery to an attacker-owned shop that has installed the app (a normal unprivileged app-installation flow), and (2) sending a forged HTTP request with the captured `raw_body`/`hmac` and a modified shop-domain header to the app's public webhook endpoint. No secrets, TLS interception, or elevated privileges are needed, so likelihood is high for any multi-tenant app author who follows the gem's documented `data.shop` usage.

### Recommendation
Bind the shop (and ideally topic/api_version/webhook_id) into the value verified by `HmacValidator`, e.g. by including the shop-domain header in `to_signable_string`, or by having `Registry.process` cross-check that `request.shop` matches a shop bound into the signed payload/registered session before constructing `WebhookMetadata`. At minimum, the documentation should stop stating that headers such as `shop` are verified by `process`, since only the raw body currently is.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`; app subscribes to a webhook topic.
2. Shopify delivers a genuine webhook to the app for `attacker.myshopify.com`:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw_body computed with app's client_secret>`
   - Body: attacker-controlled payload (e.g. crafted `orders/create` JSON referencing arbitrary data).
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value.
4. Attacker sends a new POST to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but replaces the header with `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate(request)` at [6](#0-5)  succeeds because only `raw_body` is checked.
6. The app's handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled `body`, and — following the documented pattern of trusting `data.shop` — processes/attributes the forged data to the victim tenant.
