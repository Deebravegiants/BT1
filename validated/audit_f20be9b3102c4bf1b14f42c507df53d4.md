### Title
`Rectangle::is_correct()` fails to enforce well-formed box geometry, allowing degenerate/inverted bounding boxes to pass qualification - ([File: src/agents/python/rgb_net.rs])

### Summary
`Rectangle::is_correct()` only validates that each coordinate individually falls in `[0.0, 1.0]`, but never checks that `start_x <= end_x` and `start_y <= end_y`. A degenerate or inverted bounding box (e.g. `start_x=0.9, end_x=0.1`) satisfies all four per-coordinate checks and is accepted as "correct," letting `handle_rgb_net` populate `FrameInfoRgb` from a geometrically invalid detection.

### Finding Description
`RgbNet::estimate` output is parsed by `extract`/`extract_rectangle` in `src/agents/python/rgb_net.rs` (lines 296-331), which places four raw floats straight into a `Rectangle { start_x, start_y, end_x, end_y }` with no ordering constraint [1](#0-0) .

The only geometric qualification gate on this value is `Rectangle::is_correct()`:
```rust
pub fn is_correct(&self) -> bool {
    self.start_x >= 0.0 && self.end_x <= 1.0 && self.start_y >= 0.0 && self.end_y <= 1.0
}
``` [2](#0-1) 

This check verifies range membership per-axis but never verifies `start_x <= end_x` or `start_y <= end_y`. Consequently a box such as `start_x=0.9, start_y=0.9, end_x=0.1, end_y=0.1` (inverted, negative width/height) passes `is_correct()` because every individual bound is within `[0.0,1.0]`.

`handle_rgb_net` in `src/plans/biometric_capture/mod.rs` relies solely on this check as the qualification gate before storing the frame:
```rust
if let Some(prediction) = estimate.primary() {
    if prediction.bbox.coordinates.is_correct() {
        ...
        *slot = Some(FrameInfoRgb::new(estimate, frame));
    }
}
``` [3](#0-2) 

Once accepted, this bbox flows into `Capture` and is later reused as `face_bbox_left`/`face_bbox_right` in `biometric_pipeline::Plan::new` [4](#0-3) , and separately as the crop box fed to the occlusion-detection agent, which is one of the fraud checks in the pipeline [5](#0-4) . Because `NaN` comparisons in Rust are always `false`, `is_correct()` does correctly reject `NaN` coordinates (any comparison against `NaN` evaluates to `false`), so the "NaN" branch of the question is not exploitable. The real gap is the missing `start <= end` invariant, which permits degenerate/inverted, effectively-zero or negative-area boxes to be treated as valid geometry and propagate downstream unchanged.

### Impact Explanation
Accepting a geometrically invalid (inverted/degenerate) face bounding box breaks the fail-closed qualification invariant for RGB frame capture. It lets a bbox that does not correspond to a sane face region populate `FrameInfoRgb` and continue through `into_capture`, and it is later reused unchecked to crop the frame for the occlusion/fraud-check model. A degenerate crop region can produce meaningless or empty input to the occlusion model, undermining the fraud-check signal it is meant to provide, and generally allows a degraded/occluded capture to be treated as qualifying data at the RGB-Net gate — matching the "degraded-signal path accepted as qualifying capture" impact class.

### Likelihood Explanation
Exploitability depends entirely on the RGB-Net model producing an inverted/degenerate box for some physical presentation (extreme lighting, occlusion, odd angle, adversarial input) — the attacker has no direct control over model internals, only the presented scene, so triggering this specific output is not guaranteed and is likely rare/model-dependent. However, the validation code itself has no defense against this class of output regardless of how often the model produces it, so the check is unconditionally unsound for this input class.

### Recommendation
Strengthen `Rectangle::is_correct()` to also require `self.start_x < self.end_x && self.start_y < self.end_y` (or `<=` with a minimum-area threshold), rejecting inverted or zero/negative-area boxes in addition to the existing per-axis range checks.

### Proof of Concept
Add a unit test in `src/agents/python/rgb_net.rs`:
```rust
#[test]
fn rectangle_is_correct_rejects_degenerate_geometry() {
    // Inverted box: passes current per-axis bounds but is degenerate.
    let inverted = Rectangle { start_x: 0.9, start_y: 0.9, end_x: 0.1, end_y: 0.1 };
    assert!(!inverted.is_correct(), "inverted rectangle must be rejected");

    // Zero-area box.
    let zero_area = Rectangle { start_x: 0.5, start_y: 0.5, end_x: 0.5, end_y: 0.5 };
    assert!(!zero_area.is_correct(), "zero-area rectangle must be rejected");

    // Well-formed box still accepted.
    let valid = Rectangle { start_x: 0.1, start_y: 0.1, end_x: 0.9, end_y: 0.9 };
    assert!(valid.is_correct());
}
```
With the current implementation, the first two assertions fail (both `inverted` and `zero_area` are incorrectly accepted), demonstrating that `is_correct()` is not fail-closed against degenerate geometry.
