### Title
`calc-treasury-lp-preview` can underflow and permanently revert `accrue`, blocking all vault operations - (File: `mainnet/contracts/vault/v0-vault-sbtc.clar` and analogous `v0-vault-*.clar` files)

### Summary
The reported Zest Squeeth-style bug ("normalization factor computation can fail" due to an unguarded subtraction in a divisor) has a structural analog in Zest's vault accrual math. In `mainnet/contracts/vault/v0-vault-sbtc.clar` (and the identical pattern repeated in `v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`), the treasury-LP mint preview subtracts `reserve-inc` from `ta-preview` without a floor/clamp check, unlike every other subtraction in the same file which is defensively guarded with `(if (> a b) (- a b) u0)`. [1](#0-0) 

### Finding Description
`calc-treasury-lp-preview` computes:
```
reserve-inc = mul-div-down debt-delta fee-reserve BPS
ta-preview  = total-assets-preview()
result      = mul-div-down reserve-inc (total-supply) (- ta-preview reserve-inc)   ;; unguarded subtraction
``` [2](#0-1) 

`total-assets-preview` derives its "interest" component from `debt-preview - total-borrowed`, clamped at zero when `total-borrowed >= debt-preview`:
```
interest = if (> debt borrowed) (- debt borrowed) u0
``` [3](#0-2) 

The identity the code relies on (analogous to `(1+rFunding)*mark > index*rFunding` in the original report) is:
```
reserve-inc <= total-assets-preview()
```
This holds only as long as `total-borrowed <= total-debt` (i.e., `debt-preview >= total-borrowed`), because `reserve-inc` is bounded by the period's debt delta, which is itself bounded by cumulative accrued interest when that invariant holds. However, `total-borrowed` and the debt ledger (`principal-scaled` × `index`) are updated through two different, independently-rounded formulas in `system-repay` and `socialize-debt`:
- `system-repay` computes `principal-repaid = mul-div-down capped-amount total-borrowed-amount debt` (line 912) while reducing `principal-scaled` via a separately rounded `calc-principal-ratio-reduction` (line 909) — two different round-down ratios applied to the same repayment.
- `socialize-debt` computes `principal-reduction = mul-div-down scaled-amount borrowed scaled-principal` (line 951) while reducing `principal-scaled` by the raw `scaled-amount` directly, using yet another ratio than `debt-reduction = mul-div-down scaled-amount idx INDEX-PRECISION` (line 949). [4](#0-3) [5](#0-4) 

Because `total-borrowed` and `principal-scaled`/`index` are decremented by different formulas across repeated `borrow`/`repay`/`socialize-debt` cycles, rounding drift can accumulate such that `total-borrowed` ends up strictly greater than `debt-preview` (i.e., the "interest" clamp in `total-assets-preview` hits `u0` while `total-assets` no longer reflects any of the outstanding debt-delta). In that state, if a subsequent accrual period still produces a positive `debt-delta` (and hence `reserve-inc > 0`) while `current-assets` (the actual on-hand `assets` var) is low relative to `reserve-inc`, the unguarded `(- ta-preview reserve-inc)` underflows a `uint` in Clarity, which aborts the transaction with a runtime error rather than returning a `response` error.

### Impact Explanation
`calc-treasury-lp-preview` is invoked from `total-supply-preview`, which feeds `convert-to-shares-preview`/`convert-to-assets-preview`, and its non-preview twin is invoked directly inside `accrue` on every state-changing entry point (`system-borrow`, `system-repay`, deposits, withdrawals, liquidations) via the pattern seen at lines 841-865. If the underflow condition is reached, `accrue` (and therefore every public function that calls it) reverts unconditionally and permanently for that vault, since the vault's own reducer state (`total-borrowed`, `principal-scaled`, `index`) cannot be corrected by any available public entry point once drift has occurred — this is a temporary/permanent freezing-of-funds condition (deposits, withdrawals, borrows, and repayments in the affected vault all become unusable), matching the "blocking interactions with the Controller contract" impact in the original report.

### Likelihood Explanation
This requires accumulated rounding drift from repeated `mul-div-down` operations across `system-repay` and `socialize-debt`, which use inconsistent ratios to shrink `total-borrowed` versus `principal-scaled`/`index`. I was not able to fully trace every caller of `system-repay`/`socialize-debt` (e.g., the market/liquidation contracts that authorize calls into these vault functions) within the available index to construct a concrete numeric trace proving the drift crosses the exact threshold needed to flip `total-borrowed > debt-preview` while `reserve-inc` also exceeds `current-assets` in the same block. This makes the likelihood assessment uncertain — the missing defensive clamp is real and inconsistent with the rest of the file's style, but I could not confirm a concrete, minimal transaction sequence that triggers it without deeper access to `socialize-debt`'s caller (governance/liquidation-only?) and full repay-cycle bookkeeping across all vault files.

### Recommendation
Guard the subtraction the same way every other subtraction in this file is guarded:
```
(if (> ta-preview reserve-inc) (mul-div-down reserve-inc (total-supply) (- ta-preview reserve-inc)) u0)
```
Additionally, reconcile the rounding ratios used in `system-repay` and `socialize-debt` so `total-borrowed` and the `principal-scaled`/`index` debt ledger are always reduced proportionally and cannot drift such that `total-borrowed > debt-preview`.

This would need direct file access (or a Devin session with full repo/test access) to trace all authorized callers of `system-repay`/`socialize-debt` and simulate the rounding drift numerically before this can be confirmed as concretely exploitable rather than theoretical.

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
