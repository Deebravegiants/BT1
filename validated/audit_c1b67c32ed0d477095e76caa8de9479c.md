### Title
No check for the returned boolean of ERC20 `transfer()` in `IntentGatewayV2.withdraw()` and `SweepDust` handling on Tron - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` escrows input tokens on `placeOrder` using `SafeERC20.safeTransferFrom` [1](#0-0) , but when releasing escrowed funds back out (on `withdraw()`, called from `onAccept` for `RedeemEscrow`/`RefundEscrow`, and in the `SweepDust` admin path) it uses a raw low-level `.call` with `abi.encodeWithSelector(IERC20.transfer.selector, ...)` and only checks that the call did not revert — it never decodes/validates the returned boolean.

### Finding Description
In `withdraw()`:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [2](#0-1) 
and for fee redemption:
```solidity
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
``` [3](#0-2) 
and the same pattern in `SweepDust`:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
``` [4](#0-3) 

This only verifies that the external call did not revert (i.e., the callee is a contract and execution succeeded); it never inspects the return data to confirm the token actually returned `true`. Many TRC20/ERC20 tokens (particularly common on Tron, e.g. non-standard tokens returning `false` instead of reverting on failure, or tokens with no return value that get silently treated as success by the empty-`returndata` decode) can return `false` while the low-level call itself "succeeds." Because `success` is `true`, the code proceeds to decrement `_orders[commitment][token] -= amount` (escrow accounting) and mark the order filled/refunded, even though no tokens were actually moved out of the contract.

This is functionally identical in root cause to the reported Cooler `Cooler.sol` issue: return values from `transfer()`/`transferFrom()` are not checked, so a token that reports failure via `false` instead of reverting is treated as a successful transfer.

Note that the same underlying `IntentsBase`/EVM-mainline `IntentGatewayV2.sol` uses `SafeERC20.safeTransfer` for the analogous outbound path [5](#0-4) , so only the Tron variant regressed to the unchecked raw-call pattern.

### Impact Explanation
This is reachable by any relayer delivering a `RedeemEscrow`/`RefundEscrow` cross-chain message (an unprivileged/permissionless action — anyone can relay a valid proof once the counterpart chain dispatched it) or by the admin `SweepDust` path. If the escrowed token silently returns `false` on transfer failure (e.g. insufficient balance edge case, blacklist, paused state, or any TRC20 with non-reverting failure semantics), the contract will:
- Mark the order as filled/refunded (`_filled[commitment] = beneficiary`) and decrement escrow accounting, permanently losing the ability to retry or refund the user/solver.
- Leave the token balance stuck inside the `IntentGatewayV2` contract while the beneficiary receives nothing — a permanent freezing/loss of user or solver funds with no recovery path, since the accounting state has already been finalized.

This matches the required bar of "concrete theft or permanent freezing of funds."

### Likelihood Explanation
Likelihood depends on encountering a non-standard ERC20/TRC20 token that returns `false` (rather than reverting) on failed transfer — a known real-world token behavior class, especially prevalent among Tron-native TRC20 tokens. Since `IntentGatewayV2` is a generic intents gateway accepting arbitrary `TokenInfo.token` addresses supplied by users/solvers in orders, an attacker or unlucky configuration could deliberately or accidentally use such a token to trigger fund loss. This is a realistic, not purely theoretical, condition given the explicit fee-on-transfer/non-standard token handling already present elsewhere in the same codebase (e.g., the fee-on-transfer test suite for the mainline gateway).

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check in `withdraw()`, the transaction-fee redemption, and `SweepDust` in `evm/tron/contracts/apps/IntentGatewayV2.sol` with `SafeERC20.safeTransfer`, consistent with how `safeTransferFrom` is already used for inbound transfers in the same file, and consistent with `IntentsBase._withdraw` in the mainline EVM contract.

### Proof of Concept
1. A user places an order with `order.inputs[0].token` set to a non-standard ERC20/TRC20 token `T` that returns `false` (does not revert) when a `transfer` fails (e.g., simulate by making `T.transfer` return `false` unconditionally for a targeted address, or by having the beneficiary become blacklisted after escrow but before redemption).
2. The order is filled cross-chain; the destination gateway dispatches `RedeemEscrow` to the source chain.
3. A relayer delivers the message; `onAccept` → `withdraw()` executes:
   `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));`
   Since the call to `T.transfer` doesn't revert but returns `false`, `success == true`.
4. `_orders[commitment][token] -= amount;` executes, and if this is the last token, `_filled[commitment] = beneficiary;` finalizes the order — but `beneficiary` received zero tokens, while `T`'s balance remains locked in the `IntentGatewayV2` contract with no state left to trigger a retry or refund.     function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
