This confirms a real finding. `BandwidthManager.purchase()` dispatches with `timeout: 0` (non-expiring) as documented in `evm/src/apps/BandwidthManager.sol:179-188`, and the pallet-side `on_accept` in `modules/pallets/bandwidth/src/lib.rs:454-489` rejects the credit (returning an `Err`) whenever the tier isn't configured, the app-key is malformed, or the manager mismatch occurs — with `on_timeout` explicitly unreachable and stated as an invariant violation since these messages are "non-timeouting" (`modules/pallets/bandwidth/src/lib.rs:495-499`). Since the fee token was already pulled via `safeTransferFrom` before dispatch (`BandwidthManager.sol:170`), a rejected/failed credit leaves the buyer's funds permanently stuck in the `BandwidthManager` contract with no user-facing recovery path — only governance's `dispatch_withdraw` (admin-only) can move funds out, and that's not a refund mechanism tied to the failed purchase.

### Title
Permanent Loss of Buyer Funds on Rejected/Failed BandwidthManager Purchases with No User-Facing Recovery - (File: evm/src/apps/BandwidthManager.sol)

### Summary
`BandwidthManager.purchase()` pulls the full fee-token payment from the buyer up front and dispatches a zero-timeout POST request to `pallet-bandwidth`. If `on_accept` on the pallet side rejects the message (unknown tier, malformed app key, oversized/mismatched data not caught by the manager's client-side checks, or any other decode/config failure), the ISMP request is dropped without crediting any subscription. Because `timeout: 0` was used, `on_timeout` can never fire to trigger any refund path, and the pallet's `on_timeout` implementation explicitly treats being invoked as an invariant violation. The buyer's tokens sit in the `BandwidthManager` contract balance indefinitely, recoverable only via the admin-gated `dispatch_withdraw` governance call — which is not a per-buyer refund mechanism and requires off-chain trust that governance will restitute the exact buyer.

### Finding Description
In `purchase()` (`evm/src/apps/BandwidthManager.sol:153-200`), the manager performs only shallow validation (`app.length`, `chain.length`, `months`, known local `tierPrice`) before calling `IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount)` and then `IDispatcher(_host).dispatch(...)` with `timeout: 0`. The pallet's own tier configuration (`Tiers::<T>::get(tier)` in `modules/pallets/bandwidth/src/lib.rs:470`) is independent state from the manager's `tierPrice` mapping — the two are only kept in sync manually via `dispatch_set_tiers` governance calls. A desync (a tier priced on the manager but not yet configured/already revoked on the pallet, or vice versa), a malformed `app` that fails `AppKey::truncate_from` semantics, or a manager registration mismatch (`request.from != manager.0.to_vec()`) causes `on_accept` to return `Err(...)` (`lib.rs:456-471`), which drops the credit with no on-chain state change and no refund event.

Because the dispatch always uses `timeout: 0` (`BandwidthManager.sol:184`, confirmed in the docs at `docs/content/developers/evm/bandwidth/purchasing.mdx:220-226`), there is no timeout window during which the payer could reclaim funds via ISMP's standard timeout-refund mechanism (as used elsewhere in the protocol, e.g. `EvmHost.sol:901-905`). The pallet's `on_timeout` for this module unconditionally errors out (`modules/pallets/bandwidth/src/lib.rs:495-499`), confirming timeouts are architecturally excluded from this flow.

### Impact Explanation
A single unprivileged transaction (`purchase()`) by any buyer can result in permanent loss of the paid fee-token amount whenever the cross-chain credit fails to land — a state fully reachable by ordinary user error (wrong tier ID, stale tier price scraped from an outdated frontend, chain/app parameter mismatch) or by benign protocol operational drift (governance revokes/updates a tier on one side before the other, per the documented "a tier is unconfigured until both sides have set it" caveat). There is no `rescueFunds`-style function, no per-buyer refund path, and no view function to determine whether a specific purchase's fee was actually credited versus silently dropped. This is a concrete, permanent freezing-of-funds condition satisfying the "Validate" criteria.

### Likelihood Explanation
High likelihood: the documentation itself calls out routine desync failure modes ("Until every step lands, purchases fail — usually UnknownManager (pallet) or UnknownTier() (manager)" and "Credit message dispatched but no BandwidthCredited event ... Check pallet logs" in `docs/content/developers/evm/bandwidth/purchasing.mdx:227-234`), meaning the protocol's own operators acknowledge this failure mode occurs in normal operation, not merely as an edge case requiring an adversarial setup.

### Recommendation
Adopt the same rescue-style remediation the external report recommends for Pip.sol: either (1) set a non-zero `timeout` on the bandwidth purchase dispatch so the standard ISMP timeout-refund path (`payer` refund on `on_timeout`) applies, or (2) implement an explicit buyer-initiated `reclaimFailedPurchase(commitment)` function on `BandwidthManager` that verifies (via an on-chain/Hyperbridge-provided proof or a corresponding failure acknowledgment) that a given purchase commitment was never credited, and refunds the original payer. Additionally, expose a view function correlating a purchase `commitment` to its credited/uncredited status so buyers/tooling can detect failures deterministically rather than relying on off-chain log inspection.

### Proof of Concept
1. Governance configures tier `2` price on `BandwidthManager` (`tierPrice[2] = X`) but has not yet (or no longer) configured the matching `TierConfig` for `TierIndex::Two` on `pallet-bandwidth` (a state explicitly possible per the two-sided tier setup described in the docs).
2. A buyer calls `manager.purchase(app, 2, months, chain)`. The manager's checks pass (`tierPrice[2] != 0`), `safeTransferFrom` pulls the fee token, and a `DispatchPost` with `timeout: 0` is sent to `"BWMARKET"`.
3. A relayer delivers the message; `pallet-bandwidth::on_accept` executes `Tiers::<T>::get(tier)`, finds `None`, and returns `Err("tier ... is not configured")` (`modules/pallets/bandwidth/src/lib.rs:470-471`).
4. No `BandwidthCredited` event fires, and because `timeout == 0`, no `on_timeout` refund is ever possible (`lib.rs:495-499`).
5. The buyer's fee-token payment (`amount`, computed at `BandwidthManager.sol:168`) remains permanently held in the `BandwidthManager` contract balance, recoverable only through an admin-initiated `dispatch_withdraw` — not a buyer-facing remedy. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

    function purchase(bytes calldata app, uint256 tier, uint256 months, bytes calldata chain)
        external
        returns (bytes32 commitment)
    {
        if (app.length == 0 || app.length > MAX_APP_LENGTH || chain.length == 0 || months == 0) {
            revert InvalidPurchase();
        }
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);

        BandwidthPurchaseMsg memory body = BandwidthPurchaseMsg({
            app: app,
            tier: tier,
            months: months,
            chain: chain
        });

        commitment = IDispatcher(_host).dispatch(
            DispatchPost({
                dest: IDispatcher(_host).hyperbridge(),
                to: PALLET_BANDWIDTH_MODULE_ID,
                body: abi.encode(body),
                timeout: 0,
                fee: 0,
                payer: address(this)
            })
        );

        emit BandwidthPurchased({
            payer: msg.sender,
            feeToken: feeToken,
            tier: tier,
            months: months,
            amountPaid: amount,
            app: app,
            chain: chain,
            commitment: commitment
        });
    }

		fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
			let manager = BandwidthManager::<T>::get(&request.source).ok_or_else(|| {
				anyhow::anyhow!(format!("no bandwidth manager registered for {:?}", request.source))
			})?;

			if request.from != manager.0.to_vec() {
				return Err(anyhow::anyhow!(format!(
					"purchase from unauthorised sender on {:?}: expected {:x?}, got {:x?}",
					request.source, manager.0, request.from
				)));
			}

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

			let bytes = cfg.bytes.saturating_mul(msg.months as u128);
			let duration = cfg.duration_secs.saturating_mul(msg.months as u64);

			let key = AppKey::truncate_from(msg.app);
			let expires_at = Self::push_subscription(&msg.chain, &key, tier, bytes, duration);

			Self::deposit_event(Event::BandwidthCredited {
				app_chain: msg.chain,
				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

			Ok(Weight::zero())
		}

		fn on_response(&self, _response: GetResponse) -> Result<Weight, anyhow::Error> {
			Err(ismp::Error::CannotHandleMessage.into())
		}

## Cost of a Purchase

A purchase is an ordinary ISMP dispatch under the hood. The pallet-side credit pays no relayer fee (`fee: 0` in the dispatch) because the pallet itself is the recipient — there's no relayer network involvement in landing the credit. The only on-chain cost on the source side is:

- The scaled tier price, in the fee token (paid to the manager and held until governance withdraws it).
- Gas for `purchase()` — one ERC-20 transfer plus one `IDispatcher.dispatch()` call.

## Failure Modes

| Symptom | Likely cause |
|---------|--------------|
| `purchase()` reverts with `UnknownTier()` | Governance hasn't called `SetTiers` for that tier yet on this manager, or the tier was revoked (price reset to 0). |
| `purchase()` reverts with `PriceNotRepresentable()` | Tier price isn't a multiple of `10**(18 - feeTokenDecimals)`. Coordinate with governance to round the price. |
| `purchase()` reverts with `ERC20InsufficientAllowance` | Caller didn't approve the manager for the scaled amount, or approved for the 18-decimal value instead of the scaled value. |
| Credit message dispatched but no `BandwidthCredited` event on Hyperbridge | The pallet rejected the message. Most common causes: source chain has no registered `BandwidthManager`, `request.from` doesn't match the registered manager address, or `tier` isn't configured on the pallet side. Check pallet logs / `on_accept` errors. |
| `BandwidthCredited` fired but the `(chain, app)` bucket is empty next block | A `SubscriptionEvicted` event fired in the same block — the FIFO list was already at 1024 entries. |
