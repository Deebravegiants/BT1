### Title
Webhook `shop` (and `topic`/`webhook-id`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, and `webhook_id` fields are read straight from HTTP headers that are never part of that signed content. `Registry.process` trusts the header-derived `shop` for tenant identification after validating only the body's HMAC. Any merchant who has installed the app (an "unprivileged" action, requiring no stolen credentials) receives Shopify-signed webhooks whose HMAC is computed with the app's single shared secret — the same secret used for every tenant. That merchant can capture one of their own legitimate `(body, hmac)` pairs and replay it to the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim shop, and the request will still pass HMAC validation.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are parsed straight from headers that are not part of that signable string: [2](#0-1) 

`HmacValidator.validate` verifies the signature only over `to_signable_string` (i.e., the body): [3](#0-2) 

`Registry.process` accepts the request once the body HMAC checks out, then dispatches the handler using the header-derived, unauthenticated `shop`, `topic`, and `webhook_id`: [4](#0-3) 

The identity binding that should hold is:
`authenticated_principal (HMAC-verified sender) == shop asserted to the handler (request.shop)`

What is actually enforced is only:
`HMAC(raw_body, api_secret_key) == received_hmac`

Because the webhook HMAC secret (`Context.api_secret_key`) is the app's single shared secret, identical for every shop that installs the app, any shop tenant can generate a validly-signed `(body, hmac)` pair for its own webhooks. Since `shop` (and `topic`/`webhook_id`) are excluded from the signed content, that same valid `(body, hmac)` pair can be resent with an arbitrary `shopify-shop-domain` header value — the signature still validates, but `WebhookMetadata.shop` (passed to the app's handler) now falsely identifies a different, victim shop.

### Impact Explanation
This breaks the tenant isolation the gem's HMAC check is meant to provide. A malicious but otherwise unprivileged merchant (any user who installs the app on a store they control, and thus receives legitimate app webhooks) can forge webhook events attributed to any other shop domain, without needing the app's `client_secret`, an access token, or any credential belonging to the victim. Downstream host applications almost always key tenant-scoped side effects (order sync, billing, data writes) off `WebhookMetadata#shop`, so this is a cross-tenant access primitive — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-controlled shop to receive one legitimate webhook (freely available to anyone, including via Shopify's free developer/partner accounts), and (2) resending that captured request to the app's public webhook endpoint with a modified `shopify-shop-domain` header. No secrets, tokens, or privileged access are needed, making this readily reachable by any internet user willing to install the app once.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signable content (or otherwise cryptographically bind them to the verified body/signature), so that `HmacValidator.validate` fails if any of these header-derived identity fields are altered relative to what Shopify actually signed for that specific delivery.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; capture a legitimate webhook POST, e.g. body `{"id":1}` with header `x-shopify-hmac-sha256: <valid HMAC of body with the app's shared secret>` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Resend the identical body and HMAC header to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks the body's HMAC.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` invokes the handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, causing the host application to act on data attributed to `victim.myshopify.com` that was never sent by Shopify for that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
