## Title
JWT Replay Guard Uses Non-Atomic Check-Then-Record, Allowing Concurrent Replay of a Single JWT in HTTP Trigger Workflow Authorization - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` checks `h.jwtCache.isReplay(claims.ID)` and later calls `h.jwtCache.recordUsage(claims.ID)` as two separately-locked operations rather than one atomic check-and-set, confirmed at [1](#0-0) . The `jwtReplayCache` implements `isReplay` with an `RLock`/`RUnlock` and `recordUsage` with a separate `Lock`/`Unlock`, confirmed at [2](#0-1) , creating a genuine TOCTOU race window where two concurrent `Authorize` calls with the identical JWT can both observe "not yet seen" and both pass the replay check.

## Finding Description
The root-cause claim is accurate: `isReplay` and `recordUsage` are independent critical sections rather than a single atomic `CheckAndRecord`-style operation, unlike the pattern used in `RequestReplayGuard.CheckAndRecord` in `core/capabilities/vault/request_replay_guard.go`, which performs lookup and insertion under one lock. This is a real code defect.

However, tracing the actual exploitation path through `httpTriggerHandler.HandleUserTriggerRequest` shows the downstream impact is substantially mitigated. `VerifyRequestJWT` binds the JWT's `Digest` claim to `req.Digest()` — i.e., the JWT is cryptographically tied to the exact JSON-RPC request digest, confirmed at [3](#0-2) . To replay the "same JWT," an attacker must resend the identical `req` (including the same `req.ID`, since the digest binds to request content). After `authorizeRequest` succeeds (even twice, due to the race), `HandleUserTriggerRequest` calls `h.setupCallback`, which atomically checks-and-inserts on `req.ID` under a single `callbacksMu` lock, confirmed at [4](#0-3) . Since the replayed request necessarily carries the same `req.ID` (the digest ties JWT to the full request content, and `req.ID` is part of that request), the second concurrent call would be rejected here with "requestID has already been used," even if it slipped past the racy JWT check. This means the described race, while real at the `jwtReplayCache` level, does not concretely translate into duplicate dispatch to the DON or duplicate workflow execution in the code path examined — the `req.ID` uniqueness guard in `setupCallback` is atomic and independently prevents the claimed "unauthorized job run" / duplicate-trigger impact for the identical-request replay scenario described in the PoC.

## Impact Explanation
The claim's stated impact — "duplicate/unauthorized triggering of workflow executions from a single captured token" — is not fully substantiated. While the JWT replay-cache race is a genuine, reproducible concurrency bug, the concrete exploit path requires the exact same `req` (same `req.ID`) to be resent, and that scenario is independently blocked by the atomic `req.ID` uniqueness check in `setupCallback` before any dispatch to the DON occurs. The report does not address or rule out this downstream mitigation, so the proof of a concrete in-scope impact (duplicate job execution) is incomplete.

## Likelihood Explanation
Even granting the race exists in `jwtReplayCache`, achieving the claimed end-to-end impact (bypassing the "single-use JWT" guarantee to actually re-trigger a workflow) requires defeating both the JWT check and the separate atomic `req.ID` check in `setupCallback`, which the report does not demonstrate or acknowledge. The scenario as described (identical JWT+identical request sent twice) is caught by the request-ID de-duplication, reducing realistic likelihood of the claimed impact to effectively none for the described PoC.

## Recommendation
N/A — while the underlying `isReplay`/`recordUsage` non-atomicity in `workflow_metadata_handler.go` is a legitimate code smell and could be hardened (e.g., via a `CheckAndRecord` method mirroring `RequestReplayGuard`), the report as submitted does not establish that this race produces the claimed unauthorized-job-run impact, since the `req.ID` uniqueness check in `setupCallback` independently prevents duplicate dispatch for the exact PoC scenario described.

## Proof of Concept
Not reproducible as concrete impact: the report's PoC (send the identical JWT+request pair twice concurrently) is blocked downstream by `setupCallback`'s atomic `req.ID` uniqueness check before any request reaches the DON, so no duplicate execution would occur even though the JWT cache's `isReplay`/`recordUsage` pair is technically non-atomic.

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
