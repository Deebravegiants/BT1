### Title
Passphrase cache TTL extension does not verify the cached secret has already expired - (File: features/application/src/modules/passphrase-cache.ts)

### Summary
The external report describes `increaseQuestDuration()` in `QuestBoard.sol` extending a quest's duration without checking whether the quest was already over, requiring the Paladin team to add a check that the quest's current period must still be at or before its last period, otherwise revert. The analogous pattern in hydra is `PassphraseCache.changeTtl()`, which extends the TTL (and reschedules the auto-clear alarm) of a cached wallet passphrase without checking whether that cached passphrase has *already* logically expired according to the same expiry rules enforced in `PassphraseCache.get()`.

### Finding Description
`PassphraseCache.get()` treats a cached passphrase as expired (and clears it) under two conditions: [1](#0-0) 
- if `inactiveAt` is set and `inactiveAt + ttl <= Date.now()`, or
- if no `inactiveAt` and `addedAt + maxTtl <= Date.now()`.

However, `changeTtl()` — invoked via `Application.changeLockTimer()` and exposed publicly as `exodus.application.changeLockTimer` — never runs this same expiry check. It only verifies that a passphrase key exists in storage, then unconditionally updates the TTL and reschedules the clear alarm from `Date.now()`: [2](#0-1) [3](#0-2) [4](#0-3) 

Because the storage-level clearing of an expired passphrase is lazy (it only happens when `get()` is explicitly called and detects expiry, or when the extension-alarm `clear-passphrase` fires) [5](#0-4) , there is a window where a passphrase has already passed its intended `inactiveAt + ttl` (or `addedAt + maxTtl`) boundary but has not yet been physically removed from storage, and the pending `clear-passphrase` alarm has not yet fired. If `changeLockTimer` (i.e. `changeTtl`) is called during that window, it does not consult the same expiry predicate used by `get()`; it simply sees a non-empty `passphrase` entry, computes `newTtl`, resets `TTL_KEY`, and reschedules the clear alarm relative to "now." This effectively resurrects/extends the life of an already-expired cached secret rather than rejecting the extension — the same root cause described in the QuestBoard report where `increaseQuestDuration()` extended an already-past quest instead of validating the current period against the quest's last period and reverting.

### Impact Explanation
The passphrase cache stores the actual decryption passphrase in plaintext-adjacent storage, gated only by the TTL-driven auto-clear mechanism, which is a core secret-lifetime security control (`security-auto-lock-time-set` analytics event and the `autoLockTimer` atom exist specifically to bound how long this secret persists) [6](#0-5) [7](#0-6) . Extending the TTL of an entry that should already be considered expired defeats the intended secret-lifetime guarantee, keeping a decryption passphrase available in storage/memory for longer than the security model intends — a direct secret-disclosure risk if the timing race is hit (e.g. a delayed alarm callback combined with a lock-timer change request racing against the natural expiry boundary).

### Likelihood Explanation
This requires a specific timing window: the `inactiveAt + ttl` (or `addedAt + maxTtl`) boundary must have passed but the scheduled `clear-passphrase` alarm has not yet fired (alarms have coarse, minute-level granularity via `delayInMinutes`), and `changeLockTimer` must be invoked in that window. This is plausible in normal operation (e.g., a settings screen calling `changeLockTimer` shortly after the device becomes active again, or programmatic calls right around the TTL boundary), making it a real but timing-dependent issue rather than a directly attacker-triggerable one from an untrusted origin.

### Recommendation
In `changeTtl()`, before extending the TTL, re-validate the cached passphrase's expiry using the same predicate as `get()` (i.e., check `inactiveAt + ttl` / `addedAt + maxTtl` against `Date.now()`). If the entry is already past its expiry boundary, clear it instead of extending it, mirroring the Paladin fix pattern of checking that the current period is still at/before the last valid period before allowing the extension.

### Proof of Concept
1. Cache a passphrase with a short `ttl` (e.g. 1 minute) via `PassphraseCache.set()`. [8](#0-7) 
2. Call `scheduleClear()` to set `inactiveAt = Date.now()` and schedule the `clear-passphrase` alarm. [9](#0-8) 
3. Advance time past `inactiveAt + ttl` but before the alarm callback executes (simulate alarm latency).
4. Call `exodus.application.changeLockTimer({ ttl: newTtl })` → `changeTtl()` runs, sees `passphrase` still present in storage, and reschedules `TTL_KEY`/alarm from "now" without ever checking that `inactiveAt + ttl <= Date.now()` was already true. [2](#0-1) 
5. Call `get()` — it will now report the passphrase as valid based on the newly extended TTL, even though it should have been cleared at step 3.
