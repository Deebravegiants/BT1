### Title
Webhook `shop`/`topic`/`webhook_id` headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `HmacValidator.validate` only proves the body's integrity/authenticity. The `shop`, `topic`, `webhook_id`, and `api_version` values — which the registry hands to the app's handler as the authoritative tenant identity for the event — come straight from HTTP headers that are never covered by the HMAC.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as:
```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`HmacValidator.validate_signature` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` value: [3](#0-2) 

Since `to_signable_string` is only `@raw_body`, the signature never binds `shop`, `topic`, `webhook_id`, or `api_version` — all read from headers in `Request#shop`, `#topic`, `#webhook_id`, `#api_version` [4](#0-3) .

`Registry.process` validates only the HMAC and then dispatches the handler using the unauthenticated header-derived `shop`/`topic`/`webhook_id`/`api_version` as if they were verified:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [2](#0-1) 

The library's own documentation tells integrators that `Registry.process` "will verify the request did indeed come from Shopify" [5](#0-4) , and lists `shop` as trusted data ("`shop`, `String` - The shop domain of the webhook") [6](#0-5) , and the documented handler example uses `data.shop` directly as a tenant identifier to key jobs/storage [7](#0-6) . This is exactly the binding gap called out in the rules: a field (`shop`) is acted on by the app but not covered by the HMAC.

Because Shopify signs webhooks with the app's single `client_secret` shared across every installing shop (not a per-shop secret), any unprivileged party who can install the app on their own store (or who otherwise obtains one valid `(raw_body, hmac)` pair for a topic they control) possesses a signature that is valid for that exact body regardless of which shop header accompanies it. That party can then send a raw HTTP POST to the app's public webhook endpoint with the captured `(raw_body, hmac)` pair unchanged, but with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still passes (it never looked at the header), and `Registry.process` calls the handler believing the attacker-controlled body belongs to the victim shop.

### Impact Explanation
This breaks the identity binding `shop authenticated == shop the app acts on`. An attacker-controlled body (e.g., order/customer/product payload content they fully control in their own store) gets attributed to an arbitrary victim `shop` domain that the attacker does not own. Any app logic that uses `data.shop` to select the tenant record/session to update (exactly as shown in the gem's own documented handler example) will write or act on attacker-supplied content under the wrong tenant — a cross-tenant data-integrity/confidentiality violation, matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires no credentials belonging to the victim and no access to the app's `client_secret`: the attacker only needs to (a) install the app on their own store (or otherwise trigger one webhook delivery for a topic they control) to obtain a valid `(body, hmac)` pair, and (b) send an ordinary unauthenticated HTTP POST to the app's public webhook URL with a forged `shop-domain` header. The webhook endpoint is by design internet-reachable and unauthenticated apart from the HMAC check, so this is directly reachable by any unprivileged internet user who can install/use the app once.

### Recommendation
Bind the header-derived identity fields into the HMAC-protected signable string (or otherwise cryptographically verify them), for example by requiring the application to cross-check `request.shop` against the shop associated with the specific webhook subscription/session that was registered, rather than trusting the header alone. At minimum, document prominently that `shop`, `topic`, `webhook_id`, and `api_version` are NOT covered by the HMAC and must be independently corroborated (e.g., against the app's own webhook registration/session store) before being used as a tenant key.

### Proof of Concept
1. Attacker installs the target app on their own development store `attacker.myshopify.com` and registers a webhook topic they control (e.g. `products/update`).
2. Shopify delivers a legitimate webhook to the app: `POST /webhook` with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(client_secret, B)`, `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures this exact `(B, hmac)` pair (they own the request, so they can read it directly, e.g. via a proxy).
4. Attacker crafts body `B` beforehand to contain content they want to inject (e.g. a manipulated product/customer field) — since it's their own store's webhook, they control what triggers it.
5. Attacker sends `POST /webhook` to the same app endpoint with the identical body `B` and `hmac` header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
6. `HmacValidator.validate` succeeds because it only checks `HMAC(secret, B) == hmac` — reading `lib/shopify_api/webhooks/request.rb` lines 10-38 and `lib/shopify_api/utils/hmac_validator.rb` lines 26-31 confirms headers are excluded from the signed string.
7. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-200) invokes the registered handler with `shop: "victim.myshopify.com"` and the attacker's body, causing the app to process attacker-controlled data as if it originated from the victim's store.
