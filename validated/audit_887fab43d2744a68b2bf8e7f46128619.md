## Title
Webhook shop-tenant identity not covered by HMAC signature enables cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only. The `shop` (tenant identifier), `topic`, `webhook_id`, and `api_version` values — all taken from unauthenticated HTTP headers — are never included in the signed payload. `Webhooks::Registry.process` treats `Utils::HmacValidator.validate(request)` succeeding as proof that the *entire request*, including `request.shop`, is authentic and hands `request.shop` straight to the handler as the tenant identity.

### Finding Description
`to_signable_string` for a webhook request returns only the raw body: [1](#0-0) 

The `shop` accessor reads directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to the HMAC: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (the raw body) against the HMAC header: [3](#0-2) 

`Webhooks::Registry.process` uses this single check as the sole authenticity gate, then dispatches to the handler using `request.shop` — the unverified header value — as the merchant/tenant identity: [4](#0-3) 

Because `shop` is not part of the signed content, the equality the system implicitly relies on — `shop_used_for_tenant_routing == shop_that_was_actually_signed_by_Shopify` — does not hold. Any `(raw_body, hmac)` pair that is valid for *some* shop remains HMAC-valid no matter what `X-Shopify-Shop-Domain` value accompanies it, because the header is not part of the signed material.

### Impact Explanation
An attacker who can produce (or capture) one legitimately-signed `(body, hmac)` pair — trivially available to any merchant who installs the app on their own store and lets Shopify deliver a real webhook to the app's public callback URL — can resend that exact body/HMAC pair directly to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `Registry.process` validates successfully (HMAC covers only the body) and passes the attacker-chosen shop value through to `WebhookMetadata#shop`, which host applications use to route/attribute the webhook payload to a tenant record, session, or store. This enables cross-tenant data injection/misattribution — a merchant-controlled webhook body being processed under a victim shop's identity — meeting the Critical "cross-tenant access" bar.

### Likelihood Explanation
Webhook endpoints are public HTTP endpoints with no additional authentication layer beyond this HMAC check; forging the header requires no secret, no access token, and no privileged account — only a normal app installation (to obtain one valid signed body) and the ability to send an arbitrary POST request, which is squarely "unprivileged internet user" capability.

### Recommendation
Bind the tenant/shop identity into the signed material that `HmacValidator` verifies, or otherwise cryptographically tie the `shop`, `topic`, and `webhook_id` header values to the same trust boundary as the body (e.g., include them in `to_signable_string`, or independently corroborate `request.shop` against a value obtained through a channel that is covered by the signature) before it is passed downstream as the tenant identity in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the app on their own store `attacker-shop.myshopify.com` and triggers any webhook-eligible event (e.g., updates a product), capturing the resulting POST request (raw body + `x-shopify-hmac-sha256` header) sent by Shopify to the app's public webhook endpoint.
2. Attacker resends that exact captured body and HMAC header to the same webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the (unchanged) body against the (unchanged) HMAC — validation succeeds.
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's own webhook body>, ...)`, causing the host application to process attacker-controlled data under the victim shop's tenant context.
