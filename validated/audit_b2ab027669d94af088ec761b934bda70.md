### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing tenant (shop) spoofing on a validly-signed webhook body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, but the `shop` value used downstream to identify the tenant is read from the unauthenticated `X-Shopify-Shop-Domain` header. `Webhooks::Registry.process` validates the HMAC and then trusts `request.shop` for tenant attribution without that field ever being covered by the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC using `verifiable_query.to_signable_string` (body only) and `verifiable_query.hmac` (also body-derived): [3](#0-2) 

`Registry.process` validates the HMAC and, immediately after, forwards `request.shop` (the unauthenticated header) to the handler as the tenant identifier, with no re-check that the header matches anything cryptographically bound to the payload: [4](#0-3) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop used by the handler to attribute the webhook data`

Because `to_signable_string` only covers the body, this binding is broken: an attacker who possesses one validly-signed `(raw_body, hmac)` pair for shop A (e.g. because they operate a store that has this app installed and can capture their own legitimate webhook deliveries) can replay that same body+HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header for shop B. `HmacValidator.validate` will still return `true` because it only checks the body-derived signature, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to shop B, even though it was signed for shop A.

### Impact Explanation
This crosses a tenant boundary: it lets a possessor of a validly-signed webhook body relabel that data as belonging to a different, victim shop, causing the host application's webhook handlers to associate arbitrary attacker-controlled body content with any shop domain of the attacker's choosing. Any app logic that trusts `WebhookMetadata#shop` (e.g., mandatory-compliance webhooks like `shop/redact`, `customers/redact`, `customers/data_request`, or app-specific per-shop side effects) can be tricked into acting on behalf of, or attributing sensitive data to, a shop the attacker does not control. This matches the "cross-tenant access" class of impact.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one legitimately-signed `(raw_body, hmac)` pair, which is realistic for any merchant/developer that has the app installed on their own store and can observe their own webhook deliveries (this does not require the app's `client_secret`). Likelihood is Low-to-Medium since it depends on the specific handler logic trusting `shop` for security-relevant decisions, but the header-vs-signature mismatch itself is unconditionally present in the gem.

### Recommendation
Include the `shop` domain (and ideally `topic`, `api_version`, `webhook_id`) in the signable string used for HMAC verification, or independently and cryptographically bind the shop header to the payload before it is trusted by `Registry.process`/handlers. At minimum, document that `request.shop` is unauthenticated and must not be used for tenant-security decisions without additional verification (e.g., cross-checking against the session/shop that installed the app).

### Proof of Concept
1. Attacker's own shop `attacker.myshopify.com` has the app installed; Shopify sends a webhook with body `B` and header `X-Shopify-Shop-Domain: attacker.myshopify.com`, signed as `HMAC(client_secret, B)`.
2. Attacker captures `(B, hmac)`.
3. Attacker sends a forged HTTP request to the app's webhook endpoint with the same raw body `B` and the same `hmac` header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(client_secret, B)` against `to_signable_string` (`B`) — the shop header is never included. [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)`, misattributing attacker-supplied body content to `victim.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
