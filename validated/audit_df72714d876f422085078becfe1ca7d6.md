## Title
Webhook `shop` domain identity is trusted from an unauthenticated header while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor sourced from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body [1](#0-0) . `Registry.process` validates the HMAC and then hands `request.shop` straight to the app's handler as the tenant identifier, without any cryptographic binding between that value and the verified body [2](#0-1) .

### Finding Description
The binding that should hold is: `hmac == HMAC(secret, shop || body)`, i.e. the shop identity acted upon should be covered by the same signature that authenticates the payload. Instead the code implements `hmac == HMAC(secret, body)` and `shop == header["shopify-shop-domain"]` — two independent, unbound values.

- `Request#hmac`/`to_signable_string` derive the signature check exclusively from `@raw_body` [3](#0-2) .
- `Request#shop` is read straight out of attacker-controllable HTTP headers with no cross-check against the signed body [4](#0-3) .
- `Registry.process` only asserts `Utils::HmacValidator.validate(request)` (body-only) before dispatching `request.shop` into `WebhookMetadata` for the handler to act on [2](#0-1) .

Because the app's shared `client_secret` signs webhook bodies identically for every shop that has the app installed, any unprivileged internet user can legitimately install the target app on their own (e.g. free/dev) store and receive a real webhook with a **valid** HMAC over a body they control the content of (their own customer/order/app data). They can then replay that exact `raw_body` + `hmac` to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` forwards `shop: <victim-shop>` together with the attacker-authored body to the handler — a direct violation of the equality `verified-shop == acted-on-shop`.

### Impact Explanation
This breaks the tenant boundary the library is expected to provide: the only integrity guarantee (`HmacValidator`) does not protect the field (`shop`) that host applications use to route/attribute the webhook to a merchant. Depending on how the host app keys off `WebhookMetadata#shop` (session/token lookup, GDPR `customers/redact`, `app/uninstalled` handling, inventory/order mutations, etc.), this enables cross-tenant data confusion or spoofed mandatory-compliance actions attributed to a shop the attacker does not control — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any user can install the target app for free on a store they control and immediately obtain a validly-signed webhook body/HMAC pair, since the same `api_secret_key` signs webhooks for all installs of the app. Replaying it with a forged shop header requires only the ability to send an arbitrary HTTP POST to the app's public webhook endpoint — no access token, secret, or privileged account is needed.

### Recommendation
Bind the shop identity to the signed payload before trusting it: either (a) require host apps to cross-check `request.shop` against a shop already known/authorized for the specific resource referenced in `parsed_body` before acting, or (b) have `Registry.process` reject/flag webhooks whose header-derived `shop` cannot be corroborated against session/installation state maintained by the host app, and clearly document in `WebhookMetadata` that `shop` is unauthenticated header data, not part of the HMAC-verified integrity boundary.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `customers/create`) containing attacker-chosen data.
2. Shopify sends the webhook to the app's endpoint with a body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` — both `B` and the HMAC are legitimate.
3. Attacker replays `POST <same body B, same HMAC header>` to the same endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B)` — this still passes [5](#0-4) .
5. `request.shop` returns `"victim-shop.myshopify.com"` from the spoofed header [4](#0-3) , and this is passed to the handler as if it were an authentic webhook from the victim shop [6](#0-5) .

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
