### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while the shop identity used to route and label the webhook comes from an HTTP header (`shopify-shop-domain`) that is never included in the HMAC-signed data [2](#0-1) . `Registry.process` validates only that the body's HMAC matches, then unconditionally trusts `request.shop` (along with `topic`, `api_version`, `webhook_id`) to build `WebhookMetadata` passed to the app's handler [3](#0-2) .

### Finding Description
The identity binding that should hold is: `HMAC-verified bytes == bytes the handler trusts for tenant identification`. Here that equality is broken — the HMAC only binds the JSON body, not the `shopify-shop-domain` header. `HmacValidator.validate` computes the signature purely from `to_signable_string`, i.e. the raw body [4](#0-3) , and `Registry.process` raises only if that body-HMAC check fails [5](#0-4) ; it never re-derives or checks `request.shop` against anything cryptographically bound to the signature.

Since `api_secret_key` is the app's single client secret shared across every merchant who installs the app (not a per-shop credential), any merchant who installs the app can legitimately receive a webhook whose body-HMAC is valid (signed by Shopify using that shared secret). Because the `shop-domain` header sits outside the signed payload, that attacker-controlled merchant can replay the same validly-signed body while substituting the `shopify-shop-domain` header for a victim shop's domain. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` claiming to be from the victim shop [6](#0-5) , even though the payload never actually originated from, nor was authorized by, that shop.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` (or `request.shop`) as the tenant key for data updates, cache invalidation, GDPR/mandatory topics (`shop/redact`, `customers/redact`, `customers/data_request`), or uninstall handling will act on/for the wrong tenant. This is a cross-tenant boundary violation: an attacker-controlled shop can inject a webhook payload that the app processes as if it belonged to a victim shop, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate but unprivileged installer of the target app on their own store (no leaked secrets, no privileged access, no host-app misconfiguration needed) — they can capture a real, validly-HMAC-signed webhook body sent to their own endpoint and resend it with a forged `shopify-shop-domain` header to the app's webhook endpoint. This is directly reachable through the gem's own `Registry.process`/`Request` API as documented.

### Recommendation
Include the header-derived identity fields (`shop`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable string, or otherwise cryptographically bind them (e.g., have `Registry.process`/`Request` require the shop domain to be validated against session/installation records before invoking the handler) rather than trusting header values solely gated by a body-only HMAC.

### Proof of Concept
1. App installs on attacker's shop `attacker.myshopify.com`; Shopify sends a legitimate webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-for-body>`, and some JSON body.
2. Attacker captures this request and resends it to the same endpoint, only changing the header to `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts it (all required headers present) [7](#0-6) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the signature only from `@raw_body` and matches the unchanged body — validation passes [5](#0-4) .
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes the attacker's body as though it came from the victim shop [6](#0-5) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
