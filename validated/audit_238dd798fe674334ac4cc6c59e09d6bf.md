### Title
Incorrect decimal-scaling direction in `pallet-hyper-fungible-token`'s ERC20↔local amount conversion causes unbacked cross-chain mint - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
The reported ULTI bug is a wrong, hardcoded assumption about token decimals (assuming WETH/18-decimals) that breaks amount math when the real input token differs. The same class of bug exists in `pallet-hyper-fungible-token`'s `convert_to_balance` / `convert_to_erc20` helpers: they assume the EVM-side (`erc_decimals`) precision is always ≥ the local asset's (`local_decimals`) precision and hardcode `saturating_sub` on that difference. When a registered asset has *more* decimals locally than on the destination chain, the subtraction underflows, `saturating_sub` clamps to 0, and the "scale factor" silently becomes `10^0 = 1` instead of correctly dividing (or multiplying) in the opposite direction.

### Finding Description
`convert_to_balance` and `convert_to_erc20` in [1](#0-0)  compute the scale exponent as `erc_decimals.saturating_sub(local_decimals)`:

```rust
pub fn convert_to_balance<B: core::str::FromStr>(value, erc_decimals, local_decimals) -> Result<B, B::Err> {
    let dec_str = (value / U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))).to_string();
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value, erc_decimals, local_decimals) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

This is only correct when `erc_decimals >= local_decimals`. Whenever a registered token is configured with `local_decimals > erc_decimals` (a perfectly legitimate, non-malicious registration — e.g. a Substrate asset created with 18 decimals bridged to an EVM chain whose token contract uses 6 decimals), `saturating_sub` returns `0`, so the scale factor collapses to `1` instead of the mathematically required division/multiplication by `10^(local_decimals - erc_decimals)`.

This function is used on both directions of the bridge:
- Outbound `send()` in [2](#0-1)  locks/burns `params.amount` at full local precision, then calls `convert_to_erc20(amount, erc_decimals, decimals)` to build the ISMP `Message.amount` that is dispatched to the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract, which mints/releases that raw ERC20 value 1:1 with no further scaling on the EVM side.
- Inbound `on_accept` / `on_timeout` in [3](#0-2)  and [4](#0-3)  use `convert_to_balance` to translate an incoming ERC20 amount back into local balance units before minting/releasing.

When `local_decimals > erc_decimals`, outbound `convert_to_erc20` fails to divide the amount down by `10^(local_decimals - erc_decimals)`, so the `Message.amount` encoded to the destination chain is inflated by that same factor relative to what was actually escrowed/burned locally. Since the EVM contract mints/unlocks the raw `amount` field verbatim (per the architecture docs: scaling only happens on the pallet side, not the Solidity side), the destination chain will mint or release far more tokens than were locked on the source — draining the destination-side escrow/liquidity or unbacked-minting tokens beyond what backs them.

### Impact Explanation
Any single signed user can call the public `send` extrinsic of `pallet-hyper-fungible-token` for a token registered with `local_decimals > erc_decimals` for the chosen destination, and have the destination chain mint/release an amount inflated by `10^(local_decimals - erc_decimals)` relative to what was actually locked/burned. This directly produces unbacked minting / drains destination-side custody (`WrappedHyperFungibleToken` escrow or minted supply), a High-impact loss of funds for the protocol/liquidity providers on the counterpart chain.

### Likelihood Explanation
Reaching the bug requires only a normal token registration (via `register_token`/`update_token`, a routine governance action, not malicious governance) where the local chain's asset decimals exceed the configured remote `erc_decimals` — a realistic, common configuration (e.g., bridging an 18-decimal Substrate asset to an EVM contract deployed with 6 decimals). No privileged or malicious actor is needed to trigger the exploit itself; any user calling `send()` triggers the miscalculation. Likelihood is Medium-to-High given plausible, non-adversarial registration scenarios.

### Recommendation
Fix the scaling helpers to handle both directions explicitly rather than relying on `saturating_sub`:
```rust
pub fn convert_to_balance<B>(value: U256, erc_decimals: u8, local_decimals: u8) -> Result<B, B::Err> {
    let scaled = if erc_decimals >= local_decimals {
        value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    };
    scaled.to_string().parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
Add regression tests covering `local_decimals > erc_decimals` for both `send`/`on_accept`/`on_timeout` paths.

### Proof of Concept
1. Register a non-native asset (`register_token`) whose local `Assets` pallet decimals = 18, and configure `Precisions` for destination chain `D` with `decimals = 6` (a normal, legitimate registration).
2. User calls `send(params)` with `amount = 1_000_000_000_000_000_000` (1 token at 18 decimals). This burns/locks 1 full token locally.
3. `convert_to_erc20(amount=1e18, erc_decimals=6, local_decimals=18)` computes `10u128.pow(6u8.saturating_sub(18u8) as u32) = 10u128.pow(0) = 1`, so `erc20_amount = 1e18` is dispatched in the `Message.amount` field — instead of the correct `1e18 / 10^12 = 1e6` (1 token at 6 decimals).
4. The destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract mints/releases `1e18` raw units (i.e., `1e12` tokens at 6-decimal precision) against only 1 token locked on the source chain — a `10^12`x unbacked mint.
