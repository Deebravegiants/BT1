## Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing in `ShopifyAPI::Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the webhook HMAC over the raw request body only, yet exposes `shop`, `topic`, `api_version`, and `webhook_id` straight from unauthenticated HTTP headers. `Webhooks::Registry.process` trusts `request.shop` and forwards it, unchecked, to the host application's webhook handler as the tenant identifier.

### Finding Description
`HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string`. For webhook requests, `to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is pulled directly from the `shop-domain` header without any cryptographic binding to the signed payload: [2](#0-1) 

`Registry.process` validates only the body's HMAC and then trusts `request.shop`/`request.topic` to build the metadata handed to the app's handler: [3](#0-2) 

Because the same `api_secret_key` is used to sign every webhook body sent by Shopify to a given app (across all installed shops of that app), an unprivileged party who can obtain any one legitimate `(body, hmac)` pair for the app — e.g. from their own store's webhook delivery, which they fully control as the merchant of that store — can replay that exact body/HMAC to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header. `HmacValidator.validate` will still return `true` because it only checks the body bytes against the HMAC; the `shop` field is never part of the signed material. This breaks the identity binding: **shop value authenticated by the HMAC (none — body only) vs. shop value consumed as the tenant identity** (`request.shop`, taken from an unauthenticated header) fail to be equal.

### Impact Explanation
This lets an attacker who controls one shop that has the app installed forge webhook deliveries that the host application will attribute to a different, victim shop — a cross-tenant data-integrity/confusion issue. Any host application logic keyed off `WebhookMetadata#shop` (e.g., writing incoming order/customer data to the "shop" database record, triggering per-shop side effects, or updating billing state) can be tricked into acting on behalf of a shop the attacker does not control.

### Likelihood Explanation
Moderate: exploitation requires the attacker to already be a legitimate (even low-trust) merchant that has installed the app, so they can generate at least one valid `(body, hmac)` pair from their own shop's webhook traffic, then replay it to the shared, internet-reachable webhook endpoint with a forged `shop-domain` header. No access to `api_secret_key` or any other privileged credential is required.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the HMAC-signed material, or otherwise cryptographically bind the shop claim to the payload, so `Request#shop` cannot be forged independently of the verified body. At minimum, document that host applications must independently verify `request.shop` corresponds to a shop with an active, matching session before trusting webhook payload attribution.

### Proof of Concept
1. Attacker installs the target app on their own `attacker-shop.myshopify.com`.
2. Shopify delivers a legitimate webhook to the app: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same `B` and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` computes `HMAC(secret, B)` (per [4](#0-3)  and [5](#0-4) ) and it matches, since the body `B` is unchanged.
5. `Registry.process` invokes the host handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)`, causing the application to process attacker-supplied data under the victim shop's identity.
