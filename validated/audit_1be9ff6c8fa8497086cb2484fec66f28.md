### Title
Stale/inconsistent `self_serve` config re-reads during a single signup allow cross-phase trust-boundary mismatch - (File: `src/plans/mod.rs`, `src/brokers/observer.rs`)

### Summary
The SecondSwap bug is a classic "read config once for a decision, read it again (possibly changed) for the actual enforcement" flaw within a single logical transaction. `orb-core` has a structurally identical pattern: the shared, mutable `Config` (`Arc<Mutex<Config>>`) can be overwritten by a background task at any point during an in-progress signup, while different phases of that same signup independently re-lock and re-read the config instead of using a single value cached for the whole signup.

### Finding Description
`do_signup` takes an initial snapshot of `self_serve` (and other fields) from the shared config at the very start of the signup: [1](#0-0) 

That snapshot is used to decide things like whether `orb_relay_app_id` is required and to drive `orb_relay_announce_orb_id`, and it is passed down into `after_biometric_capture`: [2](#0-1) 

However, deeper in the same signup, other phases independently re-lock the config and re-read `self_serve` fresh instead of reusing the value snapshotted at the top of `do_signup`:
- `proceed_with_biometric_capture` re-reads `self_serve`, `self_serve_app_skip_capture_trigger`, `self_serve_app_capture_trigger_timeout`: [3](#0-2) 
- `detect_face` re-reads `self_serve` to pick a timeout: [4](#0-3) 
- `biometric_capture` re-reads `self_serve` and `self_serve_biometric_capture_timeout` again: [5](#0-4) 

Meanwhile, a background task in the `Observer` broker downloads a new config from the backend and atomically replaces the entire shared `Config` object on a timer (`CONFIG_UPDATE_INTERVAL`), with no coordination with an in-progress signup (`signup_flag` is not checked before triggering `config_update`): [6](#0-5) [7](#0-6) 

Because signups can span a long wall-clock duration (QR scanning, a 3-second sound-wait, face detection, biometric capture), and the config-refresh task runs concurrently and unconditionally, the value of `self_serve` (and its associated timeouts) observed at the start of `do_signup` can legitimately differ from the value observed later in `detect_face`/`biometric_capture`/`proceed_with_biometric_capture` within that same signup — exactly mirroring the SecondSwap pattern where the penalty fee read at "decision time" (early in the flow) differs from the fee applied at "enforcement time" (later in the same flow) because no per-transaction cache was used.

### Impact Explanation
`self_serve` is a trust-boundary flag: it determines whether biometric capture proceeds autonomously (self-serve, unsupervised) or is gated by operator-driven flow/timeouts. If the flag flips mid-signup due to a concurrent backend config refresh, different stages of the very same signup can act under inconsistent trust assumptions — e.g., the signup is initiated under one trust mode (self-serve app-triggered flow, requiring `orb_relay_app_id`) but the capture-trigger/timeout logic and face-detection timeouts are later evaluated under the opposite mode, or vice versa. This can produce inconsistent gating of the capture-start trigger (`proceed_with_biometric_capture`) and mismatched timeout enforcement across phases of one signup, undermining the intended consistency of a single authorization/session decision — the same root cause class judged Medium in the source report (user/operator should be protected from a value silently changing mid-operation).

### Likelihood Explanation
The backend config poll runs on a fixed interval independent of signup state and is not synchronized with signup progress in any way found in the reachable code (`network_unblocked` gates it, `signup_flag` does not). Any operator/backend-initiated config change that lands inside the window of an in-progress signup will trigger this inconsistency; no attacker action is required, only a config update that happens to race with a signup, making it a real, actor-independent race window rather than a purely theoretical one — but I could not confirm from the indexed code exactly how frequently `CONFIG_UPDATE_INTERVAL` fires (defined in `src/consts.rs`, contents of which I did not get to inspect), so I cannot state a concrete probability of the race window overlapping a given signup.

### Recommendation
Snapshot the entire relevant `Config` subset exactly once per signup (as already partially done at the top of `do_signup`) and thread that single, immutable snapshot through all sub-phases (`detect_face`, `biometric_capture`, `proceed_with_biometric_capture`, `after_biometric_capture`) instead of letting each phase independently re-lock and re-read the live, mutable `orb.config`. This guarantees a signup observes one consistent configuration state for its full duration, eliminating the possibility of a background config refresh silently changing enforcement behavior mid-transaction.

### Proof of Concept
Not directly executable without live backend/config-server access; the race requires:
1. Start a signup; `do_signup` snapshots `self_serve = true` at line 497-506.
2. While the signup is still in progress (during QR scan / 3s wait / face-detection), the background `Observer::config_update` task (`src/brokers/observer.rs:187-205`) completes a backend poll that flips `self_serve` to `false` in the shared `Arc<Mutex<Config>>`.
3. `detect_face` (line 1097) and `biometric_capture` (line 1167) subsequently re-read the now-changed `self_serve = false`, causing the remainder of the signup to run under different timeout/trigger semantics than the ones used to make the initial self-serve/orb-relay decisions earlier in the same `do_signup` call — a cross-phase inconsistency within one logical signup transaction, structurally identical to the outdated-fee bug in the source report.

    fn config_update(&mut self, observer: &mut Observer) -> Result<()> {
        if self.before_config_update()? {
            match observer.config_update.as_mut().map(future::FutureExt::now_or_never) {
                Some(None) => return Ok(()),
                Some(Some(result)) => result??,
                None => {}
            }
            let config = Arc::clone(&observer.config);
            let ui = observer.ui.clone();
            observer.config_update = Some(tokio::spawn(async move {
                if let Ok(new_config) = Config::download().await {
                    *config.lock().await = new_config;
                    config.lock().await.propagate_to_ui(ui.as_ref());
                }
                Ok(())
            }));
        }
        Ok(())
    }
