### Title
Missing caller-authorization check in `ConnectedOrigins.add()` allows unvalidated self-trust escalation - (File: `features/connected-origins/module/connections.js`)

### Summary
The Solidity report centers on `GatewayManagerFacet::register()` accepting attacker-supplied parameters (`collateral`, `genesisCircSupply`) and creating privileged state (a registered subnet with stake) without validating that `msg.sender` is authorized to do so. The structural analog in this repo is `ConnectedOrigins.add()` in `features/connected-origins/module/connections.js`, which creates/updates a "trusted" origin record — the gate that controls whether a website can silently obtain wallet addresses via `getConnectedAccounts()` — using only caller-supplied parameters, with no verification of who/what is invoking it.

### Finding Description
`add()` [1](#0-0)  accepts `origin`, `trusted`, `walletAccount`, `assetNames`, etc. directly from its caller and, if no record exists, calls `#addNewItem` [2](#0-1)  to persist a new origin entry with whatever `trusted` value was passed — there is no check that the request actually came from the extension's own approval-popup flow versus any other caller of this module's public API. Likewise, `isTrusted()` [3](#0-2)  and `getConnectedAccounts()` [4](#0-3)  gate exposure of wallet addresses purely on the `trusted` flag stored by `add()`, with no cross-check against an actual user-approval event.

This module is wired into the SDK surface as a `public: true` API module — `connectedOrigins.add`, `connectedOrigins.connect`, `setAutoApprove`, etc. are all exported verbatim as callable methods in `features/connected-origins/api/index.js` [5](#0-4) . This mirrors the Solidity bug's root cause precisely: a state-mutating, privilege-granting entry point (`register()` / `add()`) is exposed with the intended trust boundary ("gateway restricts subnet creation" / "the popup UI is the only thing allowed to mark an origin as trusted") enforced only by *documentation/convention* (`docs/web3-providers/solana-provider-api.md`: "This will open a pop-up asking the user to approve") rather than by a check inside the function itself.

### Impact Explanation
If any caller other than the legitimate user-approval popup flow can reach `connectedOrigins.add({ origin, trusted: true, walletAccount, assetNames })` (e.g., via a compromised or malicious RPC channel, a bug in message-origin validation elsewhere in the extension messaging pipeline, or a future refactor that exposes this API module directly to content-script-facing RPC without an intermediary approval gate), an attacker-controlled origin could self-grant `trusted: true` status. That directly yields `getConnectedAccounts()` returning the user's wallet addresses across all wallet accounts to that origin without any user consent — a cross-origin/account privilege bleed analogous to the fund-draining privilege bleed in the Solidity finding (unauthorized entity performing a privileged registration/trust action that the system's design says should be gated).

### Likelihood Explanation
I was not able to confirm, within this investigation, that the `connectedOriginsApi` module is reachable directly by an untrusted content script/webpage bypassing the popup-approval UI — the actual wiring between `window.exodus.solana.connect()` and the internal call to `connectedOrigins.add()` (likely implemented in a web3-provider/background handler package not indexed/found in this search) could not be located to conclusively trace the caller-side gate. The vulnerability described here is therefore a **defense-in-depth / root-cause architecture gap** (the privileged mutation function itself trusts all callers), not a proven end-to-end exploit chain confirmed against the actual RPC boundary in this codebase. This should be treated as moderate-confidence pending verification of the concrete message-routing code that invokes `connectedOrigins.add`.

### Recommendation
Add an explicit authorization check inside `ConnectedOrigins.add()` (or at the API layer in `features/connected-origins/api/index.js`) that verifies the call originates from the trusted internal approval flow (e.g., a signed/internal-only invocation marker, or restrict `trusted: true` to be settable only by a separate, non-origin-callable internal method), rather than relying solely on other layers of the system to gate the call before it reaches this module — mirroring the recommended fix of adding a sender check inside `GatewayManagerFacet::register()` itself rather than relying on external convention.

### Proof of Concept
Not established end-to-end in this session — the concrete external entry point that lets an arbitrary web page or content script invoke `connectedOrigins.add` without going through the user-approval popup could not be located via available search. Locating the background/provider handler that binds `window.exodus.solana.connect()` to `connectedOrigins.add`/`connectedOrigins.connect` (likely in a `solana-plugin`/`web3-provider` package not surfaced by the index) is required to confirm or refute reachability from an unprivileged origin.

  add = async ({
    connectedAssetName,
    origin,
    name,
    icon,
    assetNames = [],
    trusted,
    favorite,
    walletAccount,
  }) => {
    const value = await this.#getOrigin({ origin })

    const allConnectedAssetNames = new Set([
      connectedAssetName,
      ...assetNames,
      ...(value?.assetNames ?? []),
    ])

    if (value) {
      await this.#setAttributes({
        origin,
        attributes: {
          icon: icon ?? value.icon,
          name: name ?? value.name,
          connectedAssetName: connectedAssetName ?? value.connectedAssetName,
          trusted: trusted ?? value.trusted,
          favorite: favorite ?? value.favorite,
          assetNames: [...allConnectedAssetNames],
          walletAccount: walletAccount ?? value.walletAccount,
        },
      })

      return
    }

    await this.#addNewItem({
      origin,
      icon,
      name,
      connectedAssetName,
      trusted,
      favorite,
      assetNames: [...allConnectedAssetNames],
      walletAccount,
    })
  }

  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
