This confirms the vulnerability. `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `topic`, `shop`, `api_version`, and `webhook_id` are all read directly from HTTP headers without being part of the signed payload [2](#0-1) . `Utils::HmacValidator.validate_signature` only checks `verifiable_query.to_signable_string` against the HMAC [3](#0-2) , and `Registry.process` passes the unverified `request.shop`/`request.topic` straight into the handler's `WebhookMetadata` after only checking the HMAC [4](#0-3) .

### Title
Webhook `shop`/`topic` identity headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw JSON body via `Utils::HmacValidator.validate(request)` [5](#0-4) . However, `Webhooks::Request#to_signable_string` — the value that is actually HMAC-verified — returns only `@raw_body`, and never includes the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers [6](#0-5) . Those header-derived fields are nonetheless trusted as the tenant/topic identity and forwarded unchanged to the app's webhook handler [7](#0-6) .

### Finding Description
The binding that should hold is: `shop header verified by HMAC == shop attributed to the processed webhook`. In this gem that equality does not hold — the HMAC only binds the request body, not the `shop` field consumed downstream.

Because Shopify apps that serve multiple shops all share a single `client_secret` (`Context.api_secret_key`) for HMAC signing across every installed shop, any unprivileged user who installs the app on their own shop can trigger a legitimate webhook and obtain a body + HMAC pair that is valid under the shared secret. `Utils::HmacValidator.validate` (via `validate_signature`/`compute_signature`) only re-derives the HMAC from `verifiable_query.to_signable_string`, i.e. the raw body, using `Context.api_secret_key` [8](#0-7) . It has no dependency whatsoever on the `x-shopify-shop-domain`, `x-shopify-topic`, or `x-shopify-webhook-id` headers, all of which are read straight out of attacker-controllable request headers by `Request#shop`, `Request#topic`, and `Request#webhook_id` [2](#0-1) .

An attacker can therefore:
1. Capture a genuine `(raw_body, hmac)` pair from a webhook fired by their own (attacker-controlled) shop installation.
2. Replay that exact body and HMAC to the app's webhook endpoint, but substitute the `x-shopify-shop-domain` header with a victim shop's domain (and optionally change `x-shopify-topic` to route to a different handler).
3. `Registry.process` finds `Utils::HmacValidator.validate(request)` still returns `true` (body/HMAC pair is legitimately signed by the shared secret) and dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` to the registered handler with the spoofed `shop` [7](#0-6) .

Any app logic that uses `WebhookMetadata#shop` to look up or mutate per-tenant records (e.g., "delete data for this shop", "update subscription status for this shop") will act on the attacker-chosen victim shop identifier while using attacker-controlled body content, since the gem gives the host application no way to detect that `shop` was never actually covered by the signature.

### Impact Explanation
This breaks the tenant isolation the HMAC check is meant to provide — a shop-authenticated boundary is defeated by an unprivileged multi-tenant user, satisfying the Critical "cross-tenant access" category: an attacker can forge webhook events that appear to originate from any other shop, without needing any of the victim's credentials.

### Likelihood Explanation
The attacker needs no privileged access — merely being able to install the app on their own (attacker-controlled) shop, which is the normal, unprivileged onboarding flow for any public multi-tenant Shopify app. Capturing their own legitimate webhook and replaying it with a modified `shop-domain` header is a simple HTTP-level manipulation requiring no cryptographic secret knowledge, since the shared `client_secret` is never exposed to the attacker but its output for attacker-triggered events is.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-covered signable string, or otherwise cryptographically bind the tenant identity used by `Registry.process`/`WebhookMetadata` to the verified request context rather than to independently-parsed, unauthenticated headers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any registered webhook topic (e.g., `orders/create`), receiving a POST with a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's shared `client_secret`.
2. Attacker resends the identical raw body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, replacing only `x-shopify-shop-domain: attacker-shop.myshopify.com` with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` computes `Utils::HmacValidator.validate(request)` → `true` (body unchanged, secret unchanged), then calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...))`, causing the app to act as if the (attacker-supplied) event happened for `victim-shop.myshopify.com` [4](#0-3) .
