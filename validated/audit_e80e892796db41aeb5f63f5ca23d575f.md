### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so `Utils::HmacValidator.validate` verifies nothing but body integrity. The `shop` (and `topic`/`webhook_id`/`api_version`) values consumed by `Registry.process` come from `x-shopify-shop-domain` and related headers, which are never part of the HMAC computation.

### Finding Description
`Utils::HmacValidator.validate_signature` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the received signature. For webhooks, `to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) is defined as `@raw_body` only — none of `shop`, `topic`, `webhook_id`, `api_version` participate in the signed bytes; they are pulled straight from HTTP headers via `shopify_header` (`lib/shopify_api/webhooks/request.rb:67-70`).

`Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) validates only `Utils::HmacValidator.validate(request)` and then builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` from the header-derived, unauthenticated values, passing this directly to the app's registered handler as the tenant/shop identity for the delivered payload.

The binding this breaks, stated as an equality that should hold but doesn't:
`shop_bound_by_HMAC(raw_body) == shop_attributed_to_handler(request.shop_header)`

Before the fix such an equality is never enforced — the HMAC only proves "the app secret produced this body," it proves nothing about which shop the body/headers describe. Any body+HMAC pair generated by Shopify for *any* shop that has installed the app (all shops share the same app `client_secret`, hence the same HMAC key) can be replayed directly to the app's public webhook endpoint with an attacker-chosen `x-shopify-shop-domain` header, and it will still pass `HmacValidator.validate`.

### Impact Explanation
An unprivileged internet user who has installed the target app on their own (attacker-controlled) shop — a normal, self-serve action requiring no special privilege, credential, or leaked secret — can capture one legitimate `(raw_body, hmac)` pair delivered to the app's webhook endpoint (e.g., from `orders/create` or any topic the app subscribes to). They can then POST that exact body and HMAC directly to the app's public webhook endpoint while substituting a victim shop's domain in `x-shopify-shop-domain`. Since the shop header isn't covered by the signature, `Registry.process` will accept the request and dispatch it to the app's handler with `WebhookMetadata#shop` set to the victim shop. Any handler logic that uses `shop` to route data or actions to per-tenant storage (the intended and documented use of this field) is confused into applying the attacker's payload to the victim's tenant record — a cross-tenant data/action injection, matching the Critical "cross-tenant access" bucket.

### Likelihood Explanation
High likelihood: the only prerequisite is a self-serve app install on an attacker-owned shop (no credentials, no `api_secret_key`, no leaked tokens, no privileged account), after which the attacker directly crafts an HTTP POST to the app's webhook endpoint with fully attacker-controlled headers. No timing or race condition is required, and the replayed HMAC is always valid because it was legitimately produced by Shopify for that body.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed content used by `to_signable_string` for webhook requests, or otherwise cryptographically bind the shop-domain header to the verified payload before it is handed to `Registry.process`/the app handler, so that `HmacValidator.validate` can no longer be satisfied by mixing a valid body/HMAC pair from one shop with an attacker-chosen shop header.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` (self-serve, no special privilege).
2. Attacker triggers a webhook event (e.g., creates an order) and captures the legitimately delivered request to the app's public webhook endpoint: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker sends a new HTTP POST directly to the same public webhook endpoint with:
   - Body: the exact captured `B`
   - Header `x-shopify-hmac-sha256: H` (unchanged, still valid since it only signs `B`)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (spoofed)
   - Header `x-shopify-topic`: same topic as before
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(secret, B) == H`.
5. `Registry.process` dispatches to the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), topic: ...)`, so the app processes attacker-supplied data as though it originated from the victim's shop. [1](#0-0) [2](#0-1) [3](#0-2)
