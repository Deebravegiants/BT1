### Title
Unprivileged Value Sent Directly to a User's `HinkalWallet` Bypasses Emporium's Balance Equation and Is Stuck Until a Manual Sweep - (File: `contracts/external-actions/emporium/HinkalWallet.sol`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`HinkalWallet` is the per-user contract that Emporium ops operate on behalf of (analogous to Dolomite's per-user `InfraredBGTMetaVault`). Its `receive()` function accepts ETH from anyone with no access control [1](#0-0) , and as an ordinary contract it can also receive ERC20 tokens pushed by any third party (e.g. via a permissionless "claim/distribute-for-X" function on whatever external protocol an Emporium op previously interacted with on the wallet's behalf), with no hook back to Hinkal. However, `EmporiumUpgradeable.runAction` measures the balance-in/balance-out equation only on the Emporium contract's own address (`address(this)`), not on the wallet's address [2](#0-1) [3](#0-2) . Value that lands directly on the wallet is therefore never reflected in any UTXO and is not automatically retrievable — the wallet exposes no owner-callable withdrawal function, only `onlyEmporium`-gated `callHinkalWallet`/`doSendToRelay` [4](#0-3) .

### Finding Description
`HinkalWallet.receive()` is unguarded, so any unprivileged EOA can send ETH straight to a known wallet address [1](#0-0) . The same applies to ERC20 tokens: nothing in `HinkalWallet` restricts who can transfer tokens to it, and if the wallet has ever interacted with an external protocol through an Emporium op (staking, lending, LP positions, etc.), that protocol may expose a permissionless "claim for user" style function — exactly the `getRewardForUser`-style pattern from the reference report — that a third party can trigger to push reward tokens onto the wallet's balance without the wallet or Emporium ever being called.

The only path that reconciles balances into Hinkal's private UTXO ledger is `EmporiumUpgradeable.runAction`, and it snapshots balances of the **Emporium contract**, not the wallet:
```solidity
uint256[] memory balancesBefore = getBalancesForArray(circomData.erc20TokenAddresses); // measures address(this) == Emporium
...
uint256[] memory balancesAfter = getBalancesForArray(circomData.erc20TokenAddresses);
``` [5](#0-4) 

Value that arrives on the wallet outside of an explicit, signed Emporium operation moving it from the wallet into Emporium is invisible to this equation: `balancesBefore == balancesAfter` for the Emporium contract regardless of what happened on the wallet, so no UTXO is minted for it and it is not swept automatically.

Recovering such stray value requires the wallet owner to notice it and manually construct a new signed Emporium operation with `invokeWallet = true` whose `endpoint`/`callData` explicitly transfers the stray tokens/ETH from `HinkalWallet` into the Emporium contract, at which point the balance delta finally gets counted and a UTXO is created for it [6](#0-5) . There is no first-class flow for this; it is not part of the normal deposit/transact UX and depends on the owner discovering the stray balance out-of-band. Until that happens, the funds are unusable within Hinkal's private balance system — mirroring the Dolomite report's observation that rewards forced onto the vault "stay in the MetaVault contract, never being staked... distributed."

### Impact Explanation
This breaks the equality that the Emporium/Hinkal system relies on: change in the wallet's real token/ETH balance is supposed to always be reflected as a UTXO change, but out-of-band inbound transfers (triggerable by any unprivileged EOA sending ETH, or by anyone invoking a permissionless claim function on any external protocol the wallet has previously interacted with) create a balance the accounting never sees. This is a temporary freezing of user funds (High severity per the rubric): the value is not lost forever (the owner can eventually sign a sweep operation), but it is unusable within Hinkal's private ledger and cannot be spent, withdrawn privately, or accounted for until the owner manually crafts a non-standard remediation transaction.

### Likelihood Explanation
Triggering the ETH case requires nothing more than sending ETH to a known wallet address — trivial and always possible for any unprivileged EOA once a wallet's address is known (it must be known publicly since Emporium ops reference `stack.signerAddress` and the wallet interacts with external protocols on-chain). The ERC20/reward-claim case requires the wallet to have interacted with an external protocol exposing a permissionless claim-for-user function (the exact bug class from the reference report), which is plausible for any DeFi integration routed through Emporium's arbitrary `op.endpoint.call` mechanism.

### Recommendation
Have `EmporiumUpgradeable.runAction` account for the wallet's balance (not just Emporium's) when `stack.signerAddress != address(0)`, e.g. by snapshotting `getBalancesForArray` against the wallet address as well as Emporium's, or by forcing every op sequence to end with an explicit sweep of the wallet's full balance into Emporium before computing `balanceChange`. Alternatively, add an owner/signature-gated `sweep` function on `HinkalWallet` that unconditionally forwards any stray balance to Emporium as part of normal operation, and treat any balance the wallet holds at the start of `runAction` as part of the trackable delta (i.e. include stray pre-existing wallet balances in `balancesBefore`/`balancesAfter` bookkeeping) so it cannot silently sit outside the UTXO ledger.

### Proof of Concept
1. User's `HinkalWallet` (deployed for them at address `W`) previously used an Emporium op to open a position in an external staking protocol `P`.
2. Attacker (any unprivileged EOA) calls `P`'s permissionless claim function specifying `W` as the reward recipient (or simply sends ETH directly to `W` via `W.call{value: X}("")`, which succeeds unconditionally due to `HinkalWallet.receive()` [1](#0-0) ).
3. `W`'s ERC20/ETH balance increases, but no Emporium `runAction` call ever happened, so `EmporiumUpgradeable`'s balance snapshots (taken on the Emporium contract, not `W`) never observe this change [5](#0-4) .
4. No UTXO is created for these funds and the user cannot spend them privately through Hinkal until they notice the stray balance and manually sign a bespoke Emporium operation (`invokeWallet = true`, `endpoint` = token/ETH transfer to Emporium) to sweep it in — a step outside the normal transact flow.
