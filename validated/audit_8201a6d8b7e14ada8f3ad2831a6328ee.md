## Analysis Result

### Title
DeleteAccount `beneficiary_id` is only syntactically validated, not checked for existence — refund to a dead/nonexistent beneficiary is silently burnt - (File: `runtime/runtime/src/actions.rs`, `runtime/runtime/src/action_validation.rs`)

### Summary
The C4 finding is a Solidity "missing zero-address check" pattern: functions that send value to a caller-supplied address (`claimYield`, `_withdraw`, `_unsponsor`) never check `_to != address(0)`, so a mistaken/empty destination silently burns the transferred value instead of reverting. The nearcore analog is `DeleteAccountAction.beneficiary_id`: the field is validated only for *account-id syntax*, never for *existence*, and the balance sent there is a "refund" receipt whose failure semantics are "burn the amount" — the same accidental-burn behavior class.

### Finding Description
`validate_delete_action` only checks that `beneficiary_id` is a syntactically well-formed `AccountId`, via `validate_action_account_id`, with no existence check: [1](#0-0) [2](#0-1) 

When `action_delete_account` executes, the account's remaining balance is unconditionally pushed as a `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)`, with no check that the beneficiary account exists: [3](#0-2) 

That refund receipt is then routed through `apply_action` with `is_refund = receipt.predecessor_id().is_system()`. Critically, `implicit_account_creation_eligible = is_the_only_action && !is_refund`, so for refund receipts this is always `false`: [4](#0-3) 

`check_account_existence` for a `Transfer` action to a non-existent account calls `check_transfer_to_nonexisting_account`, which — because `implicit_account_creation_eligible` is `false` for refunds — returns `AccountDoesNotExist` even if the beneficiary id happens to look like a valid implicit-account hex string: [5](#0-4) 

Per the protocol's documented refund semantics: refund receipts are free (predecessor `"system"`), and if execution of a refund fails, the deposit amount is burnt rather than retried or returned: [6](#0-5) 

This is corroborated by the runtime code path for system-predecessor receipts, which explicitly adds the failed deposit to `other_burnt_amount`: [7](#0-6) 

So an ordinary unprivileged account owner who submits a `DeleteAccount` action naming a `beneficiary_id` that does not exist on-chain (e.g. a typo, an account that was itself deleted between signing and inclusion, or a valid-looking but never-created named/implicit id) will have their entire remaining account balance permanently burnt instead of returned to them or the transaction failing outright.

### Impact Explanation
This is a genuine, unprivileged, reachable value-destruction bug: any account owner deleting their own account can lose their full balance to an unrecoverable burn purely because of a destination-validation gap, exactly mirroring the reported Solidity "accidental burn via missing zero-address check" bug class. Funds are not stolen by an attacker, but they are irrecoverably destroyed by a preventable check — the same "assets are at risk due to external factors" reasoning the original judge used to confirm severity.

### Likelihood Explanation
High likelihood of accidental triggering: `beneficiary_id` is fully attacker/user controlled with only string-format validation (`validate_action_account_id`), no requirement that the account exist at signing or execution time. Common real-world causes: typos, referencing an already-deleted account, or a race where the beneficiary account is deleted between constructing and executing the `DeleteAccount` receipt. No special privileges are needed — any signer deleting their own account can hit this path.

### Recommendation
Before executing `action_delete_account`, verify that `beneficiary_id` refers to an existing account (or is eligible for implicit-account creation via a real transfer path rather than a refund), and reject the action (return an `ActionError`, e.g. a new `BeneficiaryAccountDoesNotExist` kind) if it does not, instead of silently generating a refund receipt destined to fail and burn.

### Proof of Concept
1. Account `alice.near` holds `N` NEAR and 0 locked stake.
2. `alice.near` signs a `DeleteAccount { beneficiary_id: "nonexistent123.near" }` action where `nonexistent123.near` has never been created (or was deleted in a preceding block).
3. `action_delete_account` runs: passes storage-usage and gas-key checks, computes `account_balance = N`, and unconditionally emits `Receipt::new_balance_refund("nonexistent123.near", N)`, then deletes `alice.near`'s account: [3](#0-2) 
4. The refund receipt is processed with `predecessor_id = "system"` (`is_refund = true`), so `implicit_account_creation_eligible = false`: [4](#0-3) 
5. `check_account_existence` fails with `AccountDoesNotExist` (`check_transfer_to_nonexisting_account`, `implicit_account_creation_eligible = false`): [8](#0-7) 
6. Because the receipt is a refund and failed, the runtime adds the full `N` deposit to `other_burnt_amount`, permanently destroying it: [7](#0-6) 

**Note on confidence**: I traced the full code path (`validate_delete_action` → `action_delete_account` → refund receipt → `check_account_existence`/`check_transfer_to_nonexisting_account` → burn-on-refund-failure) and it consistently supports this conclusion, corroborated by the `docs/RuntimeSpec/Refunds.md` documentation of burn-on-refund-failure semantics. I was not able to run the actual test suite to observe this behavior at runtime (index/tool access is read-only), so this is based on static code-path analysis rather than an executed reproduction — a Devin session with full repo/test access could confirm this with an integration test (e.g. in `runtime/runtime/src/tests/apply.rs`).

**File:** docs/RuntimeSpec/Refunds.md (L10-13)
```markdown
Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.

If the execution of a refund fails, the refund amount is burnt.
The refund receipt is an `ActionReceipt` that consists of a single action `Transfer` with the `deposit` amount of the refund.
```
