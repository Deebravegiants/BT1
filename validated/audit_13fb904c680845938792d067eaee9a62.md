### Title
`superApprove()` Grants Unlimited ERC20 Allowance To Any Caller Without Authorization - (File: `evm/src/utils/HyperFungibleTokenImpl.sol`)

### Summary
`HyperFungibleTokenImpl.sol`, the role-gated fungible token used as the fee token in non-mainnet Hyperbridge deployments (via `DeployIsmp.s.sol`) and extended by `FeeToken.sol` in the test/deploy tooling, exposes a `public` function `superApprove(address owner, address spender)` with **no access control whatsoever**. Any address can call it to set an unlimited (`type(uint256).max`) ERC20 allowance from *any* token holder to *any* spender, then drain that holder's balance with `transferFrom`. This mirrors the `[H-02]` report's bug class exactly: a function intended to be restricted (here, clearly a "test helper," analogous to a "whitelisted-only" function) is fully reachable by an unprivileged caller because the required check is missing.

### Finding Description
`superApprove` is declared `public` with no modifier and directly manipulates ERC20 internal state: [1](#0-0) 

Unlike `mint`/`burn`, which are correctly gated behind `onlyRole(MINTER_ROLE)` / `onlyRole(BURNER_ROLE)`: [2](#0-1) 

`superApprove` has no such gate, despite performing an equally privileged, state-mutating action — granting spending rights over an arbitrary owner's balance. Since `_approve(owner, spender, type(uint256).max)` is called with attacker-controlled `owner` and `spender` parameters, any unprivileged caller can invoke:
```
superApprove(victim, attacker)
```
and subsequently call `transferFrom(victim, attacker, victim.balance)` on the standard ERC20 interface to steal the victim's entire balance of this token.

This contract is not confined to test scaffolding: it is deployed as the live fee token in every non-mainnet Hyperbridge deployment via `DeployIsmp.s.sol`: [3](#0-2) 

The fee token is the asset every `IApp` (message dispatchers, relayers, token bridgers, intent participants) approves to the `IDispatcher`/`IHost` in order to pay for dispatching cross-chain messages (see `HyperApp.dispatchWithFeeToken`, which relies on `IERC20(feeToken).safeTransferFrom`). Any balance held in this fee token by a user, relayer, or app contract is directly exposed to theft through `superApprove`.

### Impact Explanation
This is a direct path to concrete theft of funds: an unprivileged attacker can drain the entire balance of any holder of the deployed `HyperFungibleTokenImpl`-based fee token (or any other token built on this base, e.g. `FeeToken`), including relayer fee balances and any user funds held in the token pending fee payment for dispatched ISMP messages. This satisfies the "concrete theft ... of funds" criterion via an unauthorized app action (arbitrary approval bypassing the owner's consent) — the same class of flaw as the reference `FCFSMint()` finding, where a function meant to be gated to specific principals was callable by anyone.

### Likelihood Explanation
High. The vulnerable function is `public`, requires no proof, signature, or special state, and is trivially reachable in a single transaction by anyone holding gas money. It is live in the fee token deployed by the standard non-mainnet deployment script, meaning any holder of that fee token (users funding message dispatch, relayers, bridging contracts) is at risk the moment the token is deployed.

### Recommendation
Remove `superApprove` from the production contract entirely, or restrict it to `onlyRole(DEFAULT_ADMIN_ROLE)` and confine its use strictly to test contexts (e.g., move it into a test-only mock contract rather than the shared `HyperFungibleTokenImpl` base that is deployed as the live fee token). At minimum, gate it so that `msg.sender == owner` (self-approval) or require the caller to hold a dedicated role, preventing arbitrary third parties from approving allowances on behalf of other accounts.

### Proof of Concept
1. Attacker observes `feeTokenInstance` (a `HyperFungibleTokenImpl`/`FeeToken`) deployed by `DeployIsmp.s.sol` on a non-mainnet Hyperbridge chain, holding balances for users/relayers who fund cross-chain dispatch fees.
2. Attacker calls `feeTokenInstance.superApprove(victim, attacker)` — no permission check blocks this call.
3. Attacker calls `feeTokenInstance.transferFrom(victim, attacker, feeTokenInstance.balanceOf(victim))`, using the newly granted `type(uint256).max` allowance to drain the victim's entire balance.
4. Repeat for every holder of the token, including relayers' escrowed fee balances and app contracts (e.g., `BridgeToken`, `IntentGatewayV2`) that hold fee-token balances pending dispatch.
