### Title
`authHandleToIntentsUserId` maps distinct Solana and WebAuthn Ed25519 credentials to identical `IntentsUserId` - (File: `packages/internal-utils/src/utils/authIdentity.ts`)

### Summary
`authHandleToIntentsUserId` derives the `solana` branch's user id as `hex.encode(base58.decode(identifier))` and the `webauthn`/`ed25519` branch's user id (via `webAuthnIdentifierToIntentsUserId`) as `hex.encode(publicKey)`, with no method-specific prefix or domain separation in either case. For any raw 32-byte Ed25519/Curve25519 key, both code paths produce the exact same hex string, so a Solana wallet key and an unrelated WebAuthn passkey sharing the same raw bytes collapse into one `IntentsUserId`.

### Finding Description
The broken equality:
`authHandleToIntentsUserId({identifier: base58.encode(rawPubKey), method:"solana"})` === `authHandleToIntentsUserId({identifier: "ed25519:" + base58.encode(rawPubKey), method:"webauthn"})`

Code path:
- `solana` case: `return hex.encode(base58.decode(authHandle.identifier))` [1](#0-0) 
- `webauthn` case delegates to `webAuthnIdentifierToIntentsUserId`, which for `ed25519` curve returns `hex.encode(publicKey)` with no prefix distinguishing it from other methods [2](#0-1) 
- `parsePublicKey` strips the `"ed25519:"` prefix and base58-decodes the remaining 32 bytes into `publicKey`, which is exactly the raw Ed25519 public key bytes [3](#0-2) 

Both branches ultimately hex-encode the identical raw 32-byte public key with no method tag, curve tag, or salt mixed in. The existing test suite even documents this shape without noticing the collision risk: the Solana test and the Ed25519 WebAuthn test both return bare 64-character hex strings with no distinguishing prefix [4](#0-3) .

Root cause: unlike the `p256` WebAuthn branch, which mixes a `"p256"` domain-separation tag into a `keccak_256` hash before truncating [5](#0-4) , the `ed25519` WebAuthn branch and the `solana` branch both skip any hashing or tagging step and directly hex-encode the raw public key. There is no cross-check between `AuthMethod` values anywhere in this function or its callers before returning the `IntentsUserId`.

Exploit flow: an attacker generates one raw Ed25519 key pair, registers it as a Solana wallet (`base58.encode(rawPubKey)`) and separately registers/attests the same raw bytes as an `ed25519:`-prefixed WebAuthn credential. Both calls to `authHandleToIntentsUserId` return the identical string, so any integrator logic that uses this id as a account/signer identity key (e.g., balance ledger, allow-list, session binding) treats the two distinct credentials as the same account.

Existing guards do not catch this: there is no `validateAddress`, `compareAddresses`, or cross-method `assert` check inside `authIdentity.ts` that rejects raw-byte overlap between the `solana` and `webauthn`/`ed25519` cases.

### Impact Explanation
The `IntentsUserId` returned by this function is the SDK's canonical representation of "who owns this intents account." If an integrator uses it to route balances, credit deposits, or gate signing authority per user, an attacker who controls both a Solana keypair and a WebAuthn Ed25519 passkey sharing the same raw bytes can make the system treat two independently-controlled credentials as one identity. This matches the Critical category: intent manipulation via signer-id conflation allowing one keyholder to act on funds/positions the other party's credential is presumed to exclusively control.

### Likelihood Explanation
Preconditions are trivial and fully attacker-controlled: generate one Ed25519 key pair, base58-encode it as a Solana identifier, and separately format it with an `ed25519:` prefix as a WebAuthn credential identifier — both are valid inputs an unprivileged user can register through any SDK-integrating application. No relayer, RPC, or contract-side collusion is required; the collision exists purely in this client-side derivation function and is deterministic and repeatable for every key of this kind.

### Recommendation
Add method/curve-specific domain separation before hex-encoding, e.g., hash `(method_tag || curveType_tag || rawPublicKey)` (as already done for the `p256` case) rather than returning the bare `hex.encode(publicKey)` for the `ed25519` WebAuthn branch, and consider prefixing the `solana` branch's output similarly so that raw-byte collisions across unrelated auth methods cannot occur.

### Proof of Concept
```ts
import { describe, expect, it } from "vitest";
import { base58 } from "@scure/base";
import { authHandleToIntentsUserId } from "./authIdentity";

describe("authHandleToIntentsUserId collision", () => {
  it("solana and webauthn ed25519 identifiers collide for same raw pubkey", () => {
    // 32 raw bytes shared by both credentials
    const rawPubKey = new Uint8Array(32).fill(7);

    const solanaId = authHandleToIntentsUserId(
      base58.encode(rawPubKey),
      "solana",
    );

    const webauthnId = authHandleToIntentsUserId(
      `ed25519:${base58.encode(rawPubKey)}`,
      "webauthn",
    );

    // SIGNED == BUILT identity check fails: two distinct credential types
    // resolve to the same IntentsUserId.
    expect(solanaId).toBe(webauthnId);
  });
});
```
