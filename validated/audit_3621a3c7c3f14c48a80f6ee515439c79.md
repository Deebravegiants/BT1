### Title
Webhook HMAC only signs the request body, not the `shop-domain`/`topic`/`webhook-id` headers, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The identity binding that should hold is: `hmac_signed_bytes == (shop, topic, webhook_id, body)` that the handler acts on. In this gem, `hmac_signed_bytes == body_only`, while `shop`, `topic`, and `webhook_id` are taken from unauthenticated HTTP headers and handed to the webhook handler unchanged. An attacker who owns any shop that has the app installed can capture one legitimately-signed webhook (valid body + HMAC) and replay it with a different `shop-domain`, `topic`, or `webhook-id` header, since none of those fields are covered by the signature check.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers with no cryptographic tie to the body or to each other: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header — it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts the header-derived `request.shop`, `request.topic`, and `request.webhook_id` when dispatching to the registered handler: [4](#0-3) 

Because the same `api_secret_key` is shared across every shop that installs the app, any shop owner can legitimately trigger a webhook for their own store, capture the raw body + valid HMAC, and then resend it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop (or the `topic`/`webhook-id` header changed to a different event type). `HmacValidator.validate` will still return `true`, because the signature only ever proved "this body was produced under our shared secret," not "this body belongs to this shop/topic/webhook-id." This is exactly analogous to the report's root cause pattern: a value that downstream logic acts on (the exchange rate / here, the tenant and event identity) is not bound by the check that is supposed to make it trustworthy (the curve pool price oracle / here, the HMAC).

### Impact Explanation
Any app handler that uses `WebhookMetadata#shop` to select which merchant's data to update, or `WebhookMetadata#topic` to decide what action to take, can be made to process a forged (shop, topic) combination while still passing HMAC validation. Since installing a public/free app on a self-owned development store requires no special privilege, this lets an unprivileged internet user forge webhook events attributed to a shop domain they don't own, i.e., cross-tenant data manipulation in the host application through a security guarantee this gem explicitly documents itself as providing (`Utils::HmacValidator`/`Errors::InvalidWebhookError`).

### Likelihood Explanation
Requires only: (1) attacker installs the app on any shop they control (no privileged Shopify credentials needed — installation is a normal merchant action), (2) attacker triggers any webhook event and captures the raw body + `X-Shopify-Hmac-Sha256` value, (3) attacker replays the POST to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header swapped. No secrets, TLS interception, or victim interaction are required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (and `api_version`) in the signable content used for HMAC verification, or otherwise cryptographically bind them to the body before dispatching to handlers, so that `HmacValidator.validate` fails if any of these header values are altered independently of the signed payload.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com`; trigger any webhook (e.g., `orders/create`) and capture the request: raw body `B`, header `X-Shopify-Hmac-Sha256: H`.
2. Compute/keep `H` — it is `HMAC-SHA256(api_secret_key, B)`, independent of shop/topic.
3. Send a new POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H`: [4](#0-3) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes `B` as if it legitimately originated from the victim's store.
