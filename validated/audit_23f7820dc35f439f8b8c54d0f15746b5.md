### Title
Webhook `shop`/`topic`/`webhook-id` headers are trusted for tenant routing without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw body, then dispatches the handler using the `shop`, `topic`, and `webhook_id` values taken from unauthenticated HTTP headers. None of those header values are included in the signed payload, so the "authenticated" HMAC does not actually bind the request to the shop it is attributed to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors read straight from HTTP headers, which are not part of the signed string: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC only against `verifiable_query.to_signable_string` (i.e., the body): [3](#0-2) 

`Registry.process` accepts the request once that body-only HMAC check passes, and then routes/attributes the event using the unauthenticated `shop` header: [4](#0-3) 

This is exactly the reported bug class: a value (`shop`/`topic`/`webhook_id`) is *acted on* by the trust boundary (`Registry.process` → `WebhookMetadata` → handler business logic keyed by shop) but is never covered by the integrity check (`Utils::HmacValidator.validate`) that gates acceptance. The check answers "is this body authentic" while the code treats the answer as "is this (shop, topic, body) tuple authentic."

### Impact Explanation
Any party that can obtain one genuinely-signed webhook for a given body (e.g., a merchant who installs the app on their own shop and receives real webhooks from Shopify for that shop) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for a different, victim shop. The HMAC check still passes because it only ever validated the body. The handler then executes tenant-specific business logic (e.g., updating stored data, triggering redaction, invalidating sessions) believing the event legitimately originated from the victim shop — a cross-tenant identity-binding break using data the attacker never needed the victim's or Shopify's credentials to produce.

### Likelihood Explanation
Exploitation requires only a normal, unprivileged Shopify merchant account: install the target app on an attacker-controlled shop, capture one legitimate webhook (any topic/body combination the app subscribes to), and replay it against the app's public webhook endpoint with a forged `shop-domain` (and optionally `topic`/`webhook-id`) header. No access to `client_secret`, access tokens, or Shopify infrastructure is needed, making this reachable by any developer who can install the app.

### Recommendation
Bind the identity fields into the authenticated payload before trusting them: either include `shop`, `topic`, and `webhook_id` in the string that is HMAC-verified, or independently re-validate that the shop asserted by the header actually owns/matches an active, previously-established session/webhook registration before invoking the handler with that shop context. At minimum, `Registry.process` should not use unauthenticated header values to select tenant-scoped behavior when the only integrity guarantee (`HmacValidator.validate`) covers the body alone.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and lets it register for a webhook topic (e.g. `app/uninstalled` or any subscribed topic).
2. Shopify sends a legitimately signed webhook: body `B`, header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same body `B` and HMAC header to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and optionally the topic header, if the handler for that topic exists).
4. `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only — identical to step 2 — so validation passes. [4](#0-3) 
5. `Registry.process` invokes the registered handler with `shop: "victim-shop.myshopify.com"`, so the app performs the webhook's business logic against the victim shop's tenant data despite the request never being authenticated for that shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
