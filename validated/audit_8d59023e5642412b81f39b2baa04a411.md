### Title
Unauthenticated NULL Pointer Dereference in Vault `MethodPublicKeyGet` Handling via Missing Params Nil-Check - (File: core/capabilities/vault/gw_handler.go)

### Summary
The gateway-side vault handler skips authorization and nil-params validation for the `MethodPublicKeyGet` method (treating it as a public, unauthenticated request), and the node-side `GatewayHandler.handlePublicKeyGet` unconditionally dereferences `req.Params` without a nil guard, unlike every other vault RPC method in the same file.

### Finding Description
`HandleJSONRPCUserMessage` special-cases `vaulttypes.MethodPublicKeyGet` at the top of the function: "Public key requests don't require authorization, Let's process this request right away." [1](#0-0)  Unlike the `SecretsCreate`/`Update`/`Delete`/`List` methods, which are routed through `h.requestProcessor.ProcessRequest`, which unmarshals params only after checking `req.Params == nil` (`core/capabilities/vault/gateway_vault_request_processor.go:115,157,198,230`), the `MethodPublicKeyGet` path performs no such check — it goes straight from `newActiveRequest` to `h.handlePublicKeyGet(ctx, ar)`.

That active request (carrying the raw, attacker-controlled `req`, including a `nil` `Params` if the client omitted the field) is forwarded to DON nodes over the gateway connector. On the node side, `GatewayHandler.HandleGatewayMessage` dispatches `MethodPublicKeyGet` directly to `handlePublicKeyGet`: [3](#0-2)  which immediately dereferences the pointer: `json.Unmarshal(*req.Params, r)` with no nil check at all, unlike `handleSecretsGet`/`handleCapabilityExecute` in the analogous `confidentialrelay` handler which explicitly guard `if req.Params == nil` before dereferencing. [2](#0-1) 

This is structurally the same bug class as CVE-2025-55639: a missing null check before dereferencing a pointer derived directly from unvalidated, attacker-supplied input, causing a crash.

### Impact Explanation
A `nil` pointer dereference in Go causes an unrecoverable panic in the goroutine unless explicitly recovered. `HandleGatewayMessage` on the node runs the vault gateway connector handler synchronously per incoming gateway message; a panic here can crash the node process or, at minimum, take down the vault capability processing goroutine for that DON node, denying vault/public-key service to that node without requiring any authentication, since `MethodPublicKeyGet` is explicitly exempted from authorization.

### Likelihood Explanation
High. Any unprivileged external client that can reach the Gateway's public HTTP endpoint can send a JSON-RPC request with `method: "vault_publicKeyGet"` and `params` omitted or `null`. Because this method bypasses the authorizer and the shared params-nil validation used by all other vault methods, no authentication, allowlisting, or crafted secret payload is required — just an empty/omitted `params` field.

### Recommendation
Add an explicit `if req.Params == nil` check in `handlePublicKeyGet` (`core/capabilities/vault/gw_handler.go`) before dereferencing, mirroring the guard pattern already used in `core/capabilities/confidentialrelay/handler.go`'s `handleSecretsGet`/`handleCapabilityExecute`. Additionally, consider validating `req.Params` for `MethodPublicKeyGet` in the gateway-side `HandleJSONRPCUserMessage` before forwarding to nodes, consistent with the validation applied to all other vault methods.

### Proof of Concept
1. Send a JSON-RPC request to the Gateway's public HTTP endpoint targeting the vault DON, with:
```json
{"jsonrpc":"2.0","id":"1","method":"vault_publicKeyGet"}
```
(no `params` field, or `"params": null`).
2. The gateway-side `HandleJSONRPCUserMessage` skips authorization/nil-check for `MethodPublicKeyGet` and forwards the request as-is to the DON node(s) (assuming no cached public key is present, e.g., shortly after node startup, forcing the "fetch from nodes" branch).
3. The node's `GatewayHandler.handlePublicKeyGet` executes `json.Unmarshal(*req.Params, r)` with `req.Params == nil`, dereferencing a nil pointer and panicking.
