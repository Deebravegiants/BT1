## Analysis

The reported JUSD bug is a "balance-of-the-shared-resource used as proof of value received" flaw: a `balanceOf` check on a location that can be topped up by activity unrelated to the current caller lets an attacker take credit for value they didn't actually contribute. Hyperbridge has a structurally identical pattern in `IntentGatewayV2.placeOrder`'s predispatch flow, using the protocol-wide, publicly documented, shared `CallDispatcher` singleton as the "balance oracle." ### Title
Order escrow can be funded with stranded funds sitting on the shared `CallDispatcher`, letting a user obtain solver output for zero contributed capital - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder`'s predispatch path measures how much of an input token was "received" by reading the *entire* current `balanceOf(dispatcher)` rather than the delta actually produced by the caller's own predispatch assets/call. Because `_params.dispatcher` is a single `CallDispatcher` contract shared across every order and every Hyperbridge app on the chain (`IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`), any token balance that is sitting on that address for any reason — misrouted swap output, dust left by a prior partial operation, or a user simply sending tokens to the well-known, documented `CallDispatcher` address — is indistinguishable from funds the current caller actually contributed.

### Finding Description
In `placeOrder`, when `order.predispatch.call` is set, predispatch assets are pushed to `dispatcher`, the attacker-supplied `predispatch.call` is executed via `ICallDispatcher(dispatcher).dispatch(...)`, and then for each `order.inputs[i]` the code does: [4](#0-3) 

```
uint256 balance = IERC20(token).balanceOf(dispatcher);
if (balance < requiredAmount) revert InvalidInput();
transferCalls[i] = Call({to: token, value: 0, data: transfer(address(this), balance)});
```

This sweeps `dispatcher`'s *total* current balance of `token`, not the amount actually produced by this specific predispatch call. The subsequent measurement on the gateway itself: [5](#0-4) 

only computes the delta relative to the gateway's own pre-sweep balance, which correctly excludes third-party interference at the *gateway*, but does nothing to validate that the amount swept *from the dispatcher* originated from the caller. `CallDispatcher` itself is a completely stateless, permissionless pass-through with a `receive()` function and no access control on who can send it tokens/ETH: [6](#0-5) 

The dispatcher's address is publicly documented and intentionally used as a landing pad by multiple independent flows — e.g. cross-chain `HyperFungibleToken`/`WrappedHyperFungibleToken` messages instruct relayers to mint/unlock tokens directly `to: CALL_DISPATCHER` so that attached calldata can spend them: [7](#0-6) 

If any token ends up resting at that address (e.g., an HFT calldata swap that leaves change, an integrator mis-targeting a swap's recipient to the dispatcher, or simply a user directly transferring tokens to the documented dispatcher address), that balance is not owned by, or reserved for, any specific order — it is captured wholesale by whichever `placeOrder` predispatch call next touches that same token.

### Impact Explanation
An attacker can place an order whose `order.inputs[i].token` matches a token they know (or can cause) to be resting on `CallDispatcher`, with `order.inputs[i].amount` set up to that resting balance, and a trivial/no-op `predispatch.call` and near-zero `predispatch.assets`. The `balanceOf(dispatcher) >= requiredAmount` check passes using someone else's stranded funds, and the entire amount is swept into the attacker's escrow as if the attacker had contributed it, backing `order.inputs[i].amount` with contributed capital of effectively zero. The attacker can then have a solver fill the order and receive real `order.output` tokens in exchange for escrow they never actually funded — a direct theft of value from whoever's funds were resting on the dispatcher, mediated through an unrelated solver's payment. This satisfies "concrete theft ... unauthorized app action" from a single `placeOrder` transaction.

### Likelihood Explanation
Likelihood is moderate-to-high: the `CallDispatcher` address is intentionally shared and publicly documented across several Hyperbridge apps as a landing pad for token routing, so residual balances are foreseeable (integrator swap misconfiguration, dust from calldata execution, or accidental direct transfers by end users who see the address in documentation/explorers). No privileged access or complex setup is needed by the attacker beyond monitoring `CallDispatcher`'s token balances and submitting one `placeOrder` transaction.

### Recommendation
Do not use the dispatcher's absolute `balanceOf` as the measure of value received. Track only the delta the current predispatch operation itself produced — e.g., snapshot `balanceOf(dispatcher)` for each relevant token immediately *before* transferring `predispatch.assets` to it (before the untrusted call), and only sweep/credit `balanceOf(dispatcher) - preTransferSnapshot`, reverting or routing any additional resting balance to a separate, explicitly-permissioned sweep function rather than crediting it to the current caller's escrow.

### Proof of Concept
1. Some token `T` ends up resting on the shared `CallDispatcher` (e.g., leftover from an `HyperFungibleToken` calldata swap that sent output back to `CallDispatcher` instead of the intended recipient, or a direct transfer by a confused user), balance `X`.
2. Attacker calls `IntentGatewayV2.placeOrder` with:
   - `order.inputs[0] = {token: T, amount: X}`
   - `order.predispatch.assets = [{token: address(0), amount: 1}]` (1 wei ETH)
   - `order.predispatch.call` = an ABI-encoded `Call[]` that trivially succeeds (e.g., calling `WETH.deposit{value:1}()`), never touching `T`.
3. In `placeOrder`, the predispatch loop finds `balanceOf(dispatcher, T) == X >= requiredAmount (X)` and sweeps the full `X` back to the gateway, crediting `order.inputs[0].amount = X` to the attacker's escrow, despite the attacker never having deposited any `T`.
4. Attacker's order is now fully collateralized with someone else's stranded `T`. A solver fills it and pays real `order.output` tokens to the attacker in exchange for the (not-really-owned) escrow. [8](#0-7)

```text
contract CallDispatcher is ICallDispatcher {
    /**
     * @dev error thrown when the target is not a contract.
     */
    error NotContract(address target);

    /**
     * @dev error thrown when a call fails.
     */
    error CallFailed(address target, bytes result);

    /**
     * @dev Receive function to accept ETH transfers
     */
    receive() external payable {}

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```
