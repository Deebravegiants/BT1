Audit Report

## Title
CORS wildcard-origin allowlist bypass via missing subdomain boundary check - (File: core/services/gateway/network/httpserver.go)

## Summary
The Gateway's public HTTP server validates cross-origin requests against an operator-configured allowlist (`CORSAllowedOrigins`). For wildcard entries (`*.example.com`), `isAllowedOrigin` strips the `*.` prefix and performs a raw `strings.HasSuffix(originHost, allowedHost)` comparison without verifying a `.` label boundary, so any hostname that merely ends with the configured suffix string (not just a true subdomain) is treated as an allowed origin.

## Finding Description
`isAllowedOrigin` handles wildcard entries with the following logic: [1](#0-0) 

Because this is a plain suffix check rather than a label-boundary-aware comparison, a host like `evilethereum.org` or `evil-remix.ethereum.org` will incorrectly satisfy `strings.HasSuffix(originHost, "ethereum.org")` for an operator-configured wildcard `*.ethereum.org`, and be treated as a legitimate subdomain even though it is an unrelated, attacker-registrable domain.

This result feeds directly into the CORS response header in `handleRequest`: [2](#0-1) 

A matching origin causes the server to echo the attacker-controlled `Origin` header value back in `Access-Control-Allow-Origin`, which instructs the victim's browser to allow the attacker's page to read the cross-origin JSON-RPC response. The existing test suite covers negative cases where the origin does not end with the allowed suffix at all (e.g., `https://ethereum.remix.org`), and scheme/port mismatches, but does not cover the boundary-bypass case where an attacker's hostname literally ends with the configured suffix without a preceding dot: [3](#0-2)  This confirms no existing check catches the reported bypass class.

## Impact Explanation
When an operator uses a wildcard `CORSAllowedOrigins` entry — a supported and documented configuration pattern demonstrated in the test suite itself (`https://*.ethereum.org`) — an attacker who registers a lookalike domain ending in the same suffix string (e.g. `evilethereum.org`) can have their web page bypass the intended origin restriction and read cross-origin responses from the Gateway's HTTP endpoint, undermining the allowlist boundary the feature is meant to enforce. This maps to the in-scope "allowlist bypass" impact category for the Gateway's browser-facing surface. [4](#0-3) 

## Likelihood Explanation
Exploitation requires: (1) the operator configuring at least one wildcard entry in `CORSAllowedOrigins`, and (2) an attacker registering or controlling a hostname whose string ends with the configured suffix (e.g. `evilethereum.org` for `*.ethereum.org`). No operator/admin credentials or victim social engineering beyond a normal page visit/CORS request are needed by the exploiting party — only crafting the `Origin` header, which any unprivileged web client fully controls. This is a well-known CORS suffix-matching bug class and is straightforward and repeatable to trigger with any domain-suffix collision.

## Recommendation
Replace the raw suffix check with a proper subdomain-boundary comparison, requiring an exact match or a `.`-preceded suffix match:
```go
if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
    return true
}
```

## Proof of Concept
1. Operator configures `CORSAllowedOrigins = ["https://*.ethereum.org"]` for the Gateway (as shown supported in `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards`).
2. Attacker registers `evilethereum.org` and serves a page from `https://evilethereum.org`.
3. Attacker's page issues a `fetch()` to the Gateway's HTTP endpoint with `Origin: https://evilethereum.org`.
4. `isAllowedOrigin` returns `true` because `strings.HasSuffix("evilethereum.org", "ethereum.org")` is true; the server responds with `Access-Control-Allow-Origin: https://evilethereum.org`.
5. Add a Go unit test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go`, asserting that origin `https://evilethereum.org` against allowed `https://*.ethereum.org` should NOT receive `Access-Control-Allow-Origin` — this test currently fails against the existing implementation, proving the bypass.

	for _, allowed := range s.config.CORSAllowedOrigins {
		// probably better to do this once when server starts and store it in a map
		// this is an easier solution so we don't have to apply more changes to the code
		// just need to be careful when specifying allowed origins in the config file
		allowedScheme, allowedHost, allowedPort, err := s.splitURL(allowed)
		if err != nil {
			s.lggr.Debug("error parsing allowed origin URL", err)
			continue
		}
		// skip if the scheme doesn't match at all
		if originScheme != allowedScheme {
			continue
		}
		// skip if the port doesn't match at all
		if originPort != allowedPort {
			continue
		}
		// check for exact host match (e.g., remix.com)
		if originHost == allowedHost {
			return true
		}
		// check for wildcard host match (e.g., *.remix.com)
		if strings.HasPrefix(allowedHost, "*.") {
			allowedHost = allowedHost[2:]
			if strings.HasSuffix(originHost, allowedHost) {
				return true
			}
		}
	}
	return false
}
