### Title
Webhook shop-domain identity spoofing due to HMAC not covering the shop header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` (tenant identity) is read from a separate, unsigned header. `Registry.process` verifies only that body-only HMAC and then dispatches the request to the topic handler, passing the unverified `shop` value straight through. This breaks the identity binding `hmac_signed_bytes == bytes_that_determine_tenant`, letting anyone who can produce one valid `(raw_body, hmac)` pair (e.g., from a legitimately delivered webhook to their own installed shop) replay it to the app's public webhook endpoint with an arbitrary forged `shop-domain`/`shop-domain` header, causing the app to process attacker-chosen webhook content under a victim shop's identity.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

- `hmac` is read from the `hmac-sha256` header.
- `shop` is read from the `shop-domain` header.
- `to_signable_string` returns only `@raw_body`.

`Utils::HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (i.e., the raw body only) and compares it to the `hmac` header value: [2](#0-1) 

`Webhooks::Registry.process` then verifies only this body-only HMAC before dispatching, and forwards the unverified `request.shop` (and `request.topic`, `request.webhook_id`) directly to the registered handler: [3](#0-2) 

There is no code path anywhere in this flow that binds the `shop-domain` (or `topic`/`webhook-id`) header to the HMAC. The equality the system implicitly relies on — `hmac == HMAC(secret, body)` implies `shop == the shop that produced that body` — does not hold, because `shop` is never part of the signed material. Any HTTP client (not just Shopify's delivery infrastructure) can `POST` to the app's public webhook route; the gem cannot distinguish the caller by network origin, only by this HMAC check, and that check ignores the `shop` header entirely.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who obtains one authentic `(raw_body, hmac)` pair — trivially available to them for any shop where they run/install the app, or for any webhook payload whose body content they can otherwise reproduce and get signed — can replay that pair to the same app endpoint while substituting the `shop-domain` header for a victim shop. `Registry.process` will accept it (HMAC over body still validates) and hand the handler a `WebhookMetadata` claiming to be from the victim shop with attacker-chosen body content. Any app logic that trusts `data.shop` from a webhook handler (e.g., to look up/mutate that shop's stored session, or to attribute orders/customers/inventory changes) is now driven by attacker-controlled tenant identity, which is a cross-tenant access primitive per the Critical impact bar in scope.

### Likelihood Explanation
Requires only network access to the app's public webhook endpoint (no `api_secret_key`, no access token, no privileged account) plus one prior legitimate webhook body+hmac pair, which is easy for an unprivileged user who can install the target app on their own store and observe a delivered webhook. This is a realistic, low-effort exploit path.

### Recommendation
Bind the identity fields used downstream to the HMAC-verified material: include `shop`, `topic`, and `webhook_id` in the signable string (or otherwise cryptographically bind them, e.g. by signing a canonicalized concatenation of headers + body), and reject the webhook if that combined signature fails, rather than validating only the raw body.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`. Shopify delivers a real webhook to the app's shared webhook endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B`), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker captures `(B, H)`.
3. Attacker sends their own `POST` to the same webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid because HMAC only covers `B`), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which passes because it only checks `HMAC(secret, B) == H`.
5. The handler is invoked with `WebhookMetadata` whose `shop` is `"victim-shop.myshopify.com"`, even though this request never originated from Shopify on behalf of that shop. [3](#0-2)
