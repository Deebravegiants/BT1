### Title
User-centric signup path bypasses backend enrollment verification, allowing local success attribution without server-side duplicate/fraud confirmation - ([File: src/plans/mod.rs])

### Summary
`MasterPlan::do_signup` has two divergent code paths to reach a "signup succeeded" terminal state. The normal path calls `enroll_user()`, which performs the authoritative round-trip to the backend (`signup_post`/`signup_poll`) that confirms uniqueness, records the enrollment, and can reject the signup as a duplicate or fraud. The `user_centric_signup` path skips this backend call entirely and derives `success` purely from the orb's own local `signup_reason`, mirroring the reported bug class where an alternate path (`depositAndBridge`) skips the finalization hook (`_afterPublicDeposit`) that the primary path performs.

### Finding Description
In `do_signup` [1](#0-0) , the code branches on `user_centric_signup && !ignore_user_centric_signups`:

- If true, it never invokes `enroll_user()` (the function that performs `signup_post::request` and polls `signup_poll::request` against the backend, see [2](#0-1) ). Instead it sets `debug_report.enrollment_status` directly from the locally computed `signup_reason` and treats `SignupReason::Normal` as success.
- If false, it calls `Box::pin(self.enroll_user(...)).await.is_success()`, which is the authoritative path that talks to the backend and can return `SignupVerificationNotSuccessful` for "Backend duplicates... Backend detected fraud... Orb detected fraud" (comment at [3](#0-2) ).

The `signup_reason` used to decide the user-centric branch is derived from `detect_fraud()`, which in this build is a stub: `// FOSS: WE HAVE DELETED ALL FRAUD CHECKS` and unconditionally returns `Ok(false)` [4](#0-3) . This means for `user_centric_signup` sessions, the orb's own fraud engine performs no real check, and the code entirely bypasses the backend's independent verification (duplicate detection, backend fraud detection) that the "normal" path relies on.

This is structurally the same class of bug as the report: a secondary/alternate flow (`user_centric_signup`) reaches the same terminal effect (marking the signup a "Success", triggering `report_signup_reason` / `debug_report.signup_successful()` / UI success state) as the primary flow, but omits the step that performs authoritative, security-relevant finalization (the equivalent of `_afterPublicDeposit` — here, backend `signup_post`/`signup_poll` verification).

### Impact Explanation
If `user_centric_signup` is set to true for a session, the orb will mark the signup process as successful and proceed to generate/upload the Personal Custody Package for the resulting identity commitment without ever confirming with the backend that this person hasn't already enrolled, and without the backend-side fraud detection that the "normal" enrollment path enforces. This maps to the External Report's accepted impact categories of "unauthorized or misattributed signup" and "cross-signup state bleed" (a person could be locally marked "enrolled" repeatedly, or fraud/duplicate detection could be bypassed for this class of signups), because the state-changing "enrollment success" determination is made unilaterally by the orb's local pipeline result rather than the backend authority.

### Likelihood Explanation
The determining flag `user_centric_signup` is sourced from `orb_qr_link::UserData` embedded in `authenticated_app_data`, which flows through the backend's `/status` response tied to the user QR code [5](#0-4) . I could not confirm from the available index whether the backend cryptographically attests/validates the `user_centric_signup` value itself, or whether it is data supplied by the companion mobile app and merely relayed by the backend to the orb (the surrounding `verify(user_data_hash)` check appears to bind the response to the QR code but its exact scope over `user_centric_signup` is not clear from the code retrieved). This uncertainty affects whether an unprivileged user/app can set this flag to trigger the bypass, or whether it's a trusted backend-controlled configuration value — this should be verified with a full read of `orb_qr_link` crate and the backend's response construction before treating this as high-likelihood.

### Recommendation
Regardless of who sets `user_centric_signup`, the local-only success determination should not be treated as equivalent to backend-confirmed enrollment: consider always requiring a backend round trip (or at minimum an authoritative uniqueness/fraud confirmation) before setting `debug_report.enrollment_status` to `Success`/marking `signup_successful()`, similar to how the report recommends calling `_afterPublicDeposit` for deposits routed through the alternate path. If `user_centric_signup` is intended to change *who* performs the enrollment call (e.g., the app calls the backend instead of the orb), the orb should still receive and honor a backend-confirmed status before it locally reports success, rather than deriving it solely from local pipeline fraud results (which are currently stubbed out).

### Proof of Concept
Not directly reproducible from the indexed code alone; the observable code path is:
1. Orb resolves `qr_codes.user_data.user_centric_signup == true` and `ignore_user_centric_signups == false` (backend config) [6](#0-5) .
2. `signup_reason` is computed only from local pipeline + stubbed `detect_fraud()` (always `false`) [7](#0-6) [4](#0-3) .
3. `debug_report.enrollment_status` is set to `Success` and `success = true` without any call to `enroll_user()`/`signup_post`/`signup_poll` [8](#0-7) .
4. `report_signup_reason` marks `debug_report.signup_successful()` and the UI reports `signup_success()` [9](#0-8) , all without backend confirmation of uniqueness/fraud.
