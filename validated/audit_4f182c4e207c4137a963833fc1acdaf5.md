### Title
Reachable liquidity-starvation path in `Bonding._routerDepositAndDispose` can drive `LPLock.recordLock` into a permanent `ZeroAmount` revert, freezing a graduating token forever - ([File: packages/contracts/src/Bonding.sol])

### Summary
The CVE describes an InnoDB bug that lets a reachable, low-privilege operation (crafted SQL over a network protocol) permanently hang/crash the server — an availability (DoS) bug triggered by an adversarial but permitted input shape. The closest analog in alt.fun's own code is the hostile-pre-seed defense inside `finalizeGraduation` → `_seedUniswapV2Direct` → `_seedRebalancing` → `_pairRebalance` → `_routerDepositAndDispose`. This is the exact "permissionless two-phase graduation" surface named in scope, and its own code comments acknowledge that under certain reserve shapes the deposit leg can be skipped, leaving `liquidity == 0`, which is then passed into `LPLock.recordLock`, a function that explicitly reverts on `amount == 0`.

### Finding Description
`finalizeGraduation` is permissionless and can be called by any unprivileged address once a token is in `Lifecycle.Graduating` [1](#0-0) . It computes `liquidity` via `_seedUniswapV2Direct` and then unconditionally calls `LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity)` [2](#0-1) .

`LPLock.recordLock` reverts with `ZeroAmount` whenever `amount == 0` [3](#0-2) , and there is no owner override, no removal path, and — per the code's own natspec — "no on-chain recovery" if the locker mapping or this call path ever gets stuck [4](#0-3) .

`liquidity` is produced by `_routerDepositAndDispose`, which only calls `addLiquidity` (and thus only sets a non-zero `liquidity`) when `remToken > 0 && remLT > 0` [5](#0-4) . If either side rounds to zero after the rebalance swap consumes it, `liquidity` stays at its default `0` and is passed straight into `recordLock`, guaranteeing revert.

The code's own comment on `_swapBudget` explicitly documents the underlying failure mode this was meant to prevent: an extreme hostile pre-seed can drive the unconstrained `_noFeeSwapInput` swap size past the per-side budget, `_pairRebalance` clamps to the full budget, and the swap "consumes 100% of one side" so that `_routerDepositAndDispose` then "skips `addLiquidity`" — the comment states this results in "`finalizeGraduation` returns `liquidity = 0`" and "`LPLock.recordLock(...)` records a zero-sized lock" [6](#0-5) . But this description is inconsistent with `LPLock.recordLock`'s actual behavior: it does not "record a zero-sized lock" — it reverts on `amount == 0` [7](#0-6) . The 99%-budget mitigation is intended to keep `remToken`/`remLT` both non-zero, but the authors' own comment shows the team is aware the zero-liquidity boundary condition exists and is only defended by the 1% margin, not by an explicit floor/guard in `_routerDepositAndDispose` or a graceful zero-liquidity path in `LPLock`.

Because `_enterGraduating` already froze trading (`lifecycle: Curve → Graduating`) and drained the curve's real LT (`ltFromPair`) plus reserved 250M tokens onto `Bonding` before `finalizeGraduation` runs [8](#0-7) , any reserve shape that deterministically drives `remToken` or `remLT` to zero on every retry (the shape is a pure function of on-chain reserves, not of tx ordering, so it is reproducible on every subsequent call) permanently bricks that token: it can never leave `Lifecycle.Graduating`, and the curve-raised LT plus the 250M reserved tokens sitting in `Bonding` become unreachable — no path back to `Curve`, no sell, no redemption, no admin override.

### Impact Explanation
If reachable, this is a permanent freeze of funds: the LT raised by the curve (`ltFromPair`) and the 250M token LP reserve are parked in `Bonding` with no unlock path once a token is wedged in `Lifecycle.Graduating` with a perpetually-zero-liquidity retry outcome. This matches the "permanent freezing of trader, creator, or LP funds" impact bar in scope, and is the analog of the InnoDB CVE's "hang or frequently repeatable crash" — here, a repeatable revert that can never succeed for the affected token.

### Likelihood Explanation
Reaching `Lifecycle.Graduating` with a hostile pre-seed is fully permissionless: any address can front-run `finalizeGraduation` by calling `factory.createPair`, `transfer`-ing tokens/LT into the pair, and calling `pair.mint(attacker)` at an arbitrary ratio, exactly as described in the protocol's own threat model for Regime 3 [9](#0-8) . Whether the specific zero-remainder boundary is actually reachable in production depends on precise numeric conditions (uint112 reserve caps, the 99%/1% split, and the router's `quote()` rounding) that I could not fully verify from the available context — the `_noFeeSwapInput` implementation and its exact interaction with `_swapBudget`'s 1% floor were only partially inspected. This is a plausible-but-unconfirmed boundary condition rather than a proven, concretely-exploitable input; the team's own commentary suggests they believe the 1% reservation closes it, but the comment's mismatched description of `LPLock.recordLock`'s actual revert behavior (claiming it "records a zero-sized lock" when the code reverts) indicates the safety argument was not fully reasoned through against the real `LPLock` semantics.

### Recommendation
- Add an explicit, tested floor in `_routerDepositAndDispose` / `_seedRebalancing` guaranteeing `remToken > 0 && remLT > 0` before returning, or fall back to `_seedDirectMint` (as done elsewhere) whenever the post-rebalance remainder would deposit as zero on either side, rather than relying solely on the 99%/1% budget split.
- Change `LPLock.recordLock` to accept `amount == 0` as a documented no-op (skip storing a lock / emit a distinct event) rather than reverting, OR make `finalizeGraduation` detect a would-be-zero `liquidity` before calling `recordLock` and take an explicit, tested recovery branch instead of reverting unconditionally.
- Re-derive and add a fuzz/regression test (the removed `HostilePreSeed.t.sol` coverage) that specifically drives the rebalance swap to consume ~100% of one side's budget and asserts `finalizeGraduation` still succeeds with non-zero `liquidity`, closing the gap between the `_swapBudget` comment's stated intent and `LPLock.recordLock`'s actual revert-on-zero behavior.

### Proof of Concept
Not independently reproduced against a running deployment/test harness within the scope of this analysis. The trace of the failure mode is derived directly from the codebase's own documentation of the boundary condition:
1. Launch a token, buy enough LT to cross a graduation trigger and land in `Lifecycle.Graduating` via `_enterGraduating` (either inline in `Bonding.buy` or via `Bonding.triggerGraduation`) [10](#0-9) .
2. Before `finalizeGraduation` is called, front-run with `factory.createPair(token, lt)` + `transfer` + `pair.mint(attacker)` to seed an extreme, maximally-imbalanced hostile ratio, per the documented Regime-3 exploit shape [9](#0-8) .
3. Call `finalizeGraduation(tokenAddress)`. If the resulting rebalance swap consumes the full per-side budget such that `remToken == 0 || remLT == 0` in `_routerDepositAndDispose`, `liquidity` stays `0` and the call reverts inside `LPLock.recordLock` with `ZeroAmount`.
4. Any subsequent call to `finalizeGraduation` against the same pre-seeded reserves reproduces the identical revert, since the reserve shape is deterministic and `lifecycle` never advances past `Graduating`.

I was unable to construct and run the exact numeric inputs (uint112 reserve values, `tokensForLP`/`ltFromPair` ratios) that would concretely force this boundary within the given tool access; this should be validated with a Foundry fuzz/PoC test targeting `_pairRebalance`/`_routerDepositAndDispose` before treating it as fully confirmed.

        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }

    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }

### The exploit

A vanilla UniswapV2 pair is deployable by anyone: `factory.createPair(token, lt)` is permissionless, and after creation anyone can call `pair.mint(to)` against pre-transferred tokens. So between phase 1 (`_enterGraduating` flips lifecycle to `Graduating` and caches `tokensForLP / ltFromPair`) and phase 2 (`finalizeGraduation` mints LP via `pair.mint(lpLock)`), an attacker can:

1. Front-run by calling `factory.createPair(token, lt)` themselves
2. `transfer(pair, smallToken)` and `transfer(pair, smallLT)` at any ratio they choose
3. Call `pair.mint(attacker)` — they now own LP at a hostile reserve ratio

When our `pair.mint(lpLock)` runs in phase 2 against this non-empty pair, V2's mint formula picks up the existing reserves:

```
liquidity = min(amount0 · totalSupply / reserve0, amount1 · totalSupply / reserve1)
```

The `min(...)` arm whose denominator is bigger relative to its numerator wins, and the OTHER arm's "excess" deposit is donated pro-rata to existing LP holders — i.e. to the attacker. Two harms:

- **Wrong opening price.** Post-mint reserves are `(R_attacker + T_a, R_attacker + T_b)`, so the LP opens at `(R_a + T_a) / (R_b + T_b)`, NOT at the curve close `T_a / T_b`. A `$15` LT pre-seed at 50% off curve close opens the pool ~454 bps off.
- **LP capture.** The wasted-side excess goes to the attacker's LP claim. A `1 wei + 1 LT` pre-seed (~`$1` attack budget) captures ~34 bps of LP.

A cheaper variant skips step 3 entirely: `transfer(pair, dust) + pair.sync()` forces the stored reserves to the dust ratio without minting any LP, leaving the pair at `reserves > 0 && totalSupply == 0`. Regime 1 below covers both shapes by keying on supply rather than reserves.
