### Title
Anyone can dust-donate collateral into an insolvent account via third-party `supply` to permanently block permissionless `clean_bad_debt` and delay bad-debt socialization - (File: contracts/controller/src/positions/supply.rs)

### Summary
XOXNO Lending has no auctions, but the same bug class — "a favorable-state/terminal condition gated on a raw balance/dust threshold that an outsider can defeat with a dust donation" — maps onto the bad-debt cleanup gate. `clean_bad_debt` is permissionless only while the insolvent account's remaining collateral is at or below the fixed `BAD_DEBT_USD_THRESHOLD` ($5 WAD) [1](#0-0) . Third-party `supply` explicitly allows any caller to top up a hub asset the account already supplies [2](#0-1) , and `supply` deliberately skips the post-action solvency gates [3](#0-2) . An attacker can therefore push an insolvent account's collateral above the dust cap, causing every subsequent `clean_bad_debt` call to revert with `CannotCleanBadDebt`.

### Finding Description
`socialize_bad_debt` admits permissionless cleanup only under `BadDebtGate::DustCapped`, i.e. `is_socializable_bad_debt(total_debt, total_collateral)` — debt exceeds collateral **and** collateral ≤ $5 [1](#0-0) . The `supply` path is reachable by any unprivileged address against an existing supply position of a foreign account (`require_third_party_existing_supply` only checks `account.supply_positions.contains_key`) [4](#0-3) . No health or solvency check runs on `supply` — confirmed by the endpoint table and by the harness test topping up an underwater account [5](#0-4) [6](#0-5) .

Attack path for a single unprivileged address:
1. Wait for (or create via price movement) an insolvent account `A` with `0 < total_collateral ≤ $5` and any live supply position in market `M`.
2. Call `supply(caller=attacker, account_id=A, spoke_id=A.spoke, assets=[(M, dust)])` where `dust` is just enough of `M` to push `total_collateral` above $5 — cost is bounded by ~$5 worth of tokens.
3. `clean_bad_debt` now reverts for all callers (`CannotCleanBadDebt`), and `check_bad_debt_after_liquidation` silently skips cleanup inside `liquidate` as well [7](#0-6) . The attacker can re-top-up after each liquidation, keeping the account just above the cap.

Like the original report's donated-wei auction extension, a dust-sized donation flips a terminal-condition gate that was designed around a threshold, not around "exactly zero".

### Impact Explanation
Insolvent debt that should be written off stays live indefinitely on the permissionless path: it keeps accruing interest against the market, keeps the account's positions consuming spoke usage, and prevents the NFT/account removal. Actual socialization then depends entirely on the owner-only `force_socialize_bad_debt`, which goes through a governance `Sensitive`-tier timelock [8](#0-7) . The donated dust is itself seized as revenue when cleanup eventually runs, so the attacker's cost is capped near the threshold; meanwhile suppliers carry an accruing shortfall. This is temporary freezing/persistent deferral of bad-debt resolution with a griefing cost of a few dollars — a Medium-severity DoS of the cleanup path, not a silent theft.

### Likelihood Explanation
Fully permissionless: `supply` and `clean_bad_debt` are both open during global pause [9](#0-8) , the top-up requires only caller auth and an existing supply slot, and it is repeatable after every liquidation that drags collateral back under the cap. The only prerequisite is an insolvent account retaining a nonzero supply position, which is exactly the population `clean_bad_debt` exists for. No profit motive is required; griefing (or a debtor delaying their own write-off for strategic reasons) suffices.

### Recommendation
Make the dust gate robust to inbound donations, mirroring the fix recommendation in the source report:
- Reject `supply` into accounts that currently satisfy `is_socializable_bad_debt` (or any account with HF < 1 and collateral within a margin of the cap), so a stranger cannot push a dying account back over the threshold; and/or
- Have `check_bad_debt_after_liquidation` and `clean_bad_debt` treat near-threshold collateral as socializable unconditionally regardless of how the balance arrived — e.g. evaluate the gate on collateral at the moment insolvency was first observable, or auto-seize residual collateral as part of cleanup so donations only enlarge protocol revenue rather than block it.
- Alternatively, allow `clean_bad_debt` to succeed when the caller is willing to absorb the residual collateral (credit it to a caller-owned account), turning the donation into a bounty instead of a blocker.

// Seed: victim is insolvent with collateral <= $5 (dust-gate admissible).
// e.g. USDC collateral crashed; clean_bad_debt currently succeeds.
assert!(t.try_clean_bad_debt_by_id(victim_id).is_ok()); // hypothetical pre-check

// Attacker (unprivileged) tops up the victim's *existing* USDC supply slot.
let usdc = t.resolve_asset("USDC");
t.try_supply_to_account(ATTACKER, VICTIM, "USDC", 6.0) // pushes collateral to ~$5..$11
    .expect("third-party top-up of an existing slot is allowed");

// Permissionless cleanup is now permanently refused...
assert_contract_error(
    t.try_clean_bad_debt_by_id(victim_id),
    errors::CANNOT_CLEAN_BAD_DEBT,
);

// ...and liquidation's in-call cleanup silently skips it too
// (apply.rs: check_bad_debt_after_liquidation -> is_socializable_bad_debt fails),
// leaving the insolvent account, its accruing debt and its spoke usage alive
// until governance executes the timelocked force_socialize_bad_debt.

### Risk checks and pause flags

After pool accounting, `borrow`, `withdraw` and the six account strategies require LTV-weighted collateral to cover debt and health factor (HF) to be at least 1. If debt remains, LTV-weighted collateral must also meet the minimum-borrow floor. Ordinary `supply` and `repay` skip these checks; repayment loads debt positions only. Liquidation uses separate admission and sizing rules. See [formulas](formulas.md) for the calculations.

pub(crate) fn check_bad_debt_after_liquidation(

    account_id: u64,
    account: &Account,
    totals: &AccountRiskTotals,

        account::cleanup_account_if_empty(env, account, account_id);
