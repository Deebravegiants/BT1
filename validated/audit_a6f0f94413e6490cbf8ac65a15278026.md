## Title
Cross-function signature/nonce collision between `withdraw_fees` and `accumulate_fees`'s beneficiary redirect allows front-running that grieves relayer reward accounting - (File: `modules/pallets/relayer/src/withdrawal.rs`, `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`pallet-ismp-relayer` exposes two unsigned, publicly-visible extrinsics that both authorize actions on behalf of a relayer using a signature over `(nonce, state_machine, beneficiary)` and the **same** `Nonce` storage map: `withdraw_fees` and the beneficiary-redirect branch of `accumulate_fees`. Because the two signed messages hash byte-identically for the same inputs, and share the same nonce counter, a signature a relayer broadcasts to authorize one operation is simultaneously valid for the other. Anyone watching the public mempool can front-run a pending `accumulate_fees` (with beneficiary redirect) call by replaying its exact signature into `withdraw_fees`, consuming the shared nonce and causing the original call to revert — the exact bug class described in the referenced report (same signature usable for two different privileged operations, enabling front-running/DoS).

### Finding Description
`withdraw_fees` signs over:
```rust
// modules/pallets/relayer/src/withdrawal.rs
pub fn message(nonce: u64, dest_chain: StateMachine, beneficiary: Option<Vec<u8>>) -> [u8; 32] {
	if let Some(beneficiary) = beneficiary {
		return sp_io::hashing::keccak_256(&(nonce, dest_chain, beneficiary).encode());
	}
	sp_io::hashing::keccak_256(&(nonce, dest_chain).encode())
}
``` [1](#0-0) 

The beneficiary-redirect branch of `accumulate_fees` signs over:
```rust
// modules/pallets/relayer/src/accumulate.rs
pub fn beneficiary_message(nonce: u64, state_machine: StateMachine, beneficiary: &[u8]) -> [u8; 32] {
	sp_io::hashing::keccak_256(&(nonce, state_machine, beneficiary).encode())
}
``` [2](#0-1) 

`Vec<u8>` and `&[u8]` SCALE-encode identically, so for the same `(nonce, chain, beneficiary_bytes)` triple, `message(nonce, chain, Some(beneficiary))` and `beneficiary_message(nonce, chain, &beneficiary)` produce the **identical 32-byte digest**. There is no domain separator distinguishing "this signature authorizes a fee redirect inside `accumulate_fees`" from "this signature authorizes an immediate `withdraw_fees` payout."

Both functions also read and increment the exact same `Nonce::<T>` double-map entry keyed by `(address, state_machine)`:
- `accumulate_fees`: `Nonce::<T>::get(&delivery_address, state_machine)` then `Nonce::<T>::try_mutate(&delivery_address, state_machine, ...)`. [3](#0-2) 
- `withdraw_fees`: `Nonce::<T>::get(address.clone(), withdrawal_data.dest_chain)` then `Nonce::<T>::try_mutate(address.clone(), withdrawal_data.dest_chain, ...)`. [4](#0-3) 

Both calls are dispatched as unsigned extrinsics (`origin: OriginFor<T>` validated via `ValidateUnsigned::validate_unsigned`, `ensure_none`), meaning both the `WithdrawalProof` (with its `beneficiary_details`) and `WithdrawalInputData` travel through the public transaction pool before inclusion: [5](#0-4) 

An observer who sees a relayer's `accumulate_fees` call (carrying `beneficiary_details = (beneficiary_address, signature)` for nonce `N` on `state_machine`) in the mempool can extract that signature and immediately submit a `withdraw_fees` extrinsic with `WithdrawalInputData { signature, dest_chain: state_machine, beneficiary: Some(beneficiary_address) }`. Because the digest matches and the recovered signer matches the address that `accumulate_fees` expects, the front-run `withdraw_fees` succeeds: it consumes nonce `N`, zeroes the relayer's currently accrued `Fees` balance, and dispatches an actual cross-chain withdrawal early. When the original `accumulate_fees` call is then processed, `Nonce::<T>::get` returns `N+1`, the recomputed `beneficiary_message` no longer matches the signature, and `signature.verify` fails with `InvalidSignature`, aborting the whole extrinsic.

### Impact Explanation
This is a griefing/DoS on relayer fee accounting, analogous to the referenced report's paymaster front-running: an unprivileged party monitoring the public mempool can repeatedly invalidate a relayer's pending `accumulate_fees` (beneficiary-redirect) submissions by replaying the same signed payload into `withdraw_fees`. Because the failed `accumulate_fees` call reverts entirely before marking the underlying request commitments as `claimed`, the fee credit is not lost permanently, but the relayer's ability to redirect/accumulate fees to a chosen beneficiary can be persistently blocked, and it forces an unplanned, early cross-chain withdrawal dispatch of the relayer's already-accrued balance. This falls under "relayer fee and reward accounting" and constitutes a Medium-severity griefing/DoS vector, matching the judged severity of the referenced analog.

### Likelihood Explanation
Both `accumulate_fees` and `withdraw_fees` are unsigned extrinsics submitted to the public transaction pool, so any relayer's beneficiary-redirect signature is visible before inclusion. No special privilege is needed to front-run — only observing the mempool and submitting a `withdraw_fees` call with better priority/fee, exactly as described in the original report's race-condition scenario. The precondition (a relayer choosing to use the beneficiary-redirect feature) is a normal, supported usage path.

### Recommendation
Add a distinct domain separator/tag to each signed message so that `message()` (used by `withdraw_fees`) and `beneficiary_message()` (used by `accumulate_fees`) can never collide, e.g. prefix each hash input with a unique constant such as `b"RELAYER_WITHDRAW"` vs `b"RELAYER_BENEFICIARY_REDIRECT"`. Additionally, consider using independent nonce namespaces (or an explicit purpose/call-index field folded into the hash) for `withdraw_fees` versus `accumulate_fees`'s beneficiary redirect, so that consuming one nonce cannot invalidate a signature intended for the other operation.

### Proof of Concept
1. Relayer `R` with delivery address `A` has accrued fees on `state_machine=S`, and constructs a `WithdrawalProof` with `beneficiary_details = (beneficiary_bytes, sig)` where `sig` is `R`'s signature over `beneficiary_message(nonce=N, S, beneficiary_bytes)`, and submits `accumulate_fees(withdrawal_proof)` as an unsigned extrinsic.
2. Attacker `M` observes this extrinsic in the mempool and extracts `(sig, beneficiary_bytes)`.
3. `M` submits `withdraw_fees(WithdrawalInputData { signature: sig, dest_chain: S, beneficiary: Some(beneficiary_bytes) })` with higher priority so it lands first.
4. In `Pallet::withdraw` (`modules/pallets/relayer/src/withdrawal.rs`), `message(N, S, Some(beneficiary_bytes))` equals `beneficiary_message(N, S, beneficiary_bytes)` bit-for-bit, so signature verification succeeds; `Nonce::<T>[A][S]` is incremented to `N+1`, `Fees::<T>[S][A]` is zeroed, and a withdrawal is dispatched.
5. `R`'s original `accumulate_fees` call is then processed: `Nonce::<T>::get(A, S)` now returns `N+1`, `beneficiary_message(N+1, S, beneficiary_bytes)` no longer matches `sig`, `signature.verify` returns an error, and the whole `accumulate` call returns `Err(Error::InvalidSignature)`, causing the unsigned extrinsic to be rejected — griefing the relayer's fee accumulation/redirect attempt.
