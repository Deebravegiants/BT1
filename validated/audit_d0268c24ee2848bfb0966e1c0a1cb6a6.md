## Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, while the shop identity attached to the resulting event (`request.shop`, taken from the `x-shopify-shop-domain` header) is never part of the signed material. Because a single app-level `api_secret_key` is shared across every shop that installed the app, a valid HMAC computed for a webhook sent to one shop remains valid for that same body no matter which shop the header claims it came from. An attacker who controls (or has legitimately installed the app on) shop A can capture one of their own real webhooks and resubmit it to the app's public webhook endpoint with the `shop-domain` header rewritten to victim shop B; the signature still validates and the gem hands the handler a `WebhookMetadata` claiming the event is from shop B.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, and `webhook_id` are all read straight from attacker-controllable HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` performs exactly one authenticity check — the HMAC over that signable string — and then trusts `request.shop` (and `request.topic`, `request.webhook_id`) as the authenticated identity for the event: [3](#0-2) 

`HmacValidator.validate` confirms this: it only ever signs/compares `verifiable_query.to_signable_string`, i.e. the body, never the shop or topic headers: [4](#0-3) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop the gem attaches to the processed event`

Because the HMAC secret (`api_secret_key`) is a single per-app secret shared by all shops that install the app, and the signed content is only the JSON body, this equality does not hold: the `shop` field can be swapped by an unprivileged caller (anyone able to POST to the app's public webhook URL, including a legitimate installer of the app on their own store) without invalidating the signature, as long as the body bytes are unchanged.

### Impact Explanation
This is a cross-tenant identity-confusion vulnerability: a party with a legitimate installation on shop A can produce a *validly-signed* webhook payload and cross-tenant redirect it as if it originated from arbitrary shop B by only editing the `x-shopify-shop-domain` header. Any app built on this gem that keys its webhook side effects off `WebhookMetadata#shop` (e.g. mandatory `shop/redact`, `customers/redact`, `customers/data_request`, `app/uninstalled`, order/customer sync, etc.) will act on shop B's tenant using attacker-controlled webhook content, without any authentication that ties the claimed shop to the actual signer. This falls under cross-tenant access.

### Likelihood Explanation
Any internet-reachable app that registers a webhook endpoint using `ShopifyAPI::Webhooks::Registry.process`/`Request` is affected by construction of the gem's own verification logic — no misuse of undocumented behavior is required, and the only prerequisite is a single genuine webhook delivery (obtainable simply by installing the target app on any shop, including the attacker's own).

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook_id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the raw body before trusting `request.shop`/`request.topic` in `Registry.process`. At minimum, document and encourage host apps to independently confirm that `data.shop` corresponds to a shop that is actually known/installed and matches an active session before acting on webhook content, since the gem itself provides no such binding.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, obtaining a real webhook delivery, e.g. `orders/create` with body `B` and header `x-shopify-hmac-sha256` = `HMAC(api_secret_key, B)`.
2. Attacker replays a POST to the app's public webhook endpoint using the same body `B` and same HMAC header, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Webhooks::Request.new` parses headers/body; `Registry.process` calls `HmacValidator.validate(request)`, which only checks `HMAC(api_secret_key, B)` — this still passes because `B` and the secret are unchanged.
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), topic: "orders/create", ...)`, i.e. the app processes attacker-controlled webhook content attributed to a shop the attacker does not control.
