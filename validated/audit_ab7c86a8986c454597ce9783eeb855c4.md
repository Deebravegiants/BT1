### Title
Configuration flag allows operator identity validation to be replaced by unauthenticated GPS coordinates, causing misattributed signup validation - (File: `src/backend/user_status.rs`, `src/plans/mod.rs`, `src/config.rs`)

### Summary
The `Strategy`/`ERC20Rewards` bug in the external report stems from a configuration path that lets two conceptually distinct values (the reward-token balance and the base-token balance) collapse into a single balance used for a security-relevant calculation, because nothing in the code enforces that they stay distinct. `orb-core` has a structurally analogous configuration path in the user-QR validation flow: the `user_qr_validation_use_only_operator_location` flag (which defaults to `true`) causes the backend request that is supposed to authenticate/authorize a signup against a specific, vetted operator to instead be reduced to a bare GPS coordinate pair, with no cryptographic or identity binding to the operator that produced it.

### Finding Description
`verify_user_qr_code` in `src/plans/mod.rs` reads the `Config` fields `user_qr_validation_use_full_operator_qr` and `user_qr_validation_use_only_operator_location` and forwards them unchanged into `backend::user_status::request`: [1](#0-0) 

`do_request` in `src/backend/user_status.rs` then branches on these flags to build the validation request. When `use_only_operator_location` is set, the request that is supposed to validate the *user* QR code against the *operator* who scanned it is built using only `operator_data.location_data.session_coordinates` (raw latitude/longitude) — it drops the operator's QR/identity (`operator_data.qr_code.user_id`) entirely from the request: [2](#0-1) 

This is precisely the same class of configuration flaw as the external report: a value that is supposed to represent one concept (a verified, distinct operator identity) is, through a configuration toggle, silently conflated with a weaker/different concept (an unauthenticated location signal) that the validation logic was never designed to rely on exclusively. Just as `Strategy.burnForBase()` assumes the base-token balance reflects only base-token deposits (an assumption broken when the reward token is configured to equal the base token), `user_status::request`'s "operator validation" step assumes it authenticates the operator, an assumption broken when `use_only_operator_location` reduces the "operator" input to spoofable GPS floats.

Crucially, this reduced validation is the **default** in the codebase: [3](#0-2) 

### Impact Explanation
Because `OperatorData.location_data.session_coordinates` come from the operator-status backend response (itself just a numeric field, `Coordinates { latitude, longitude }` as seen in `src/backend/operator_status.rs`), and because the flag causes the operator's actual QR/identity (`operator_data.qr_code.user_id`) to be dropped from the request, a user-QR validation performed under this default configuration is not actually tied to which operator scanned it — only to a GPS coordinate. This enables a misattributed-signup scenario: a signup can be validated/attributed as if performed under one operator's session while the operator identity used for authorization purposes is never actually checked, undermining the operator-accountability guarantee the validation step is meant to provide. This maps to the "misattributed signup" impact class.

### Likelihood Explanation
This is the shipped default (`user_qr_validation_use_only_operator_location: true`), so it applies to production signups by default rather than requiring an unusual admin misconfiguration, making it more likely to be hit in practice than a one-off configuration mistake. No privileged/hardware access is required to trigger it — it is exercised on every normal signup flow through `scan_remaining_qr_codes` → `handle_user_qr_code` → `verify_user_qr_code`.

### Recommendation
Short term: ensure the "operator validation" path always includes a value that is cryptographically or otherwise strongly bound to a specific, vetted operator (not just coordinates), and avoid a configuration mode where operator identity is entirely absent from the validation request. Add explicit checks/tests asserting that `use_only_operator_location` cannot be the sole authorization signal for user-QR validation.

Long term: audit all `Config`/`BackendConfig` flags that alter what identity/authorization data is sent to the backend (e.g. `user_qr_validation_use_full_operator_qr`, `user_qr_validation_use_only_operator_location`) to ensure no combination of flags removes the operator-identity binding from a security-relevant validation call.

### Proof of Concept
1. Deploy/operate with default config (`user_qr_validation_use_only_operator_location: true`, as set in `src/config.rs`'s `Default for Config`).
2. During a normal signup, `scan_remaining_qr_codes` obtains `OperatorData` (operator QR + `LocationData`) and later calls `verify_user_qr_code` → `backend::user_status::request` with `use_only_operator_location = true`.
3. `do_request` builds the request using only `operator_data.location_data.session_coordinates` — `operator_data.qr_code.user_id` is never transmitted: [4](#0-3) 
4. The backend authorizes/attributes the signup based solely on the coordinate pair, which is not bound to the scanning operator's identity, allowing the signup to be validated/attributed without the operator's actual identity ever being checked by this call path.

#[cfg(not(feature = "skip-user-qr-validation"))]
async fn do_request(
    qr_code: &qr_scan::user::Data,
    operator_data: &OperatorData,
    use_full_operator_qr: bool,
    use_only_operator_location: bool,
) -> Result<Response> {
    let request = if use_only_operator_location {
        super::client()?
            .get(format!("{}/api/v2/session/{}/status", *SIGNUP_BACKEND_URL, qr_code.user_id,))
            .query(&[
                ("lat", operator_data.location_data.session_coordinates.latitude),
                ("lon", operator_data.location_data.session_coordinates.longitude),
            ])
    } else if use_full_operator_qr {
        super::client()?
            .get(format!("{}/api/v2/session/{}/status", *SIGNUP_BACKEND_URL, qr_code.user_id))
            .query(&[("operator_id", &operator_data.qr_code.user_id)])
    } else {
        super::client()?
            .get(format!("{}/api/v1/user/{}/status", *SIGNUP_BACKEND_URL, qr_code.user_id))
    }
    .basic_auth(&*ORB_ID, Some(get_orb_token()?));
