## Finding

### Title
Webhook signature does not cover the `shop`, `topic`, `webhook-id`, or `api-version` headers, allowing cross-tenant webhook forgery - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw request body only, while the `shop`, `topic`, `api_version` and `webhook_id` values are read from unauthenticated HTTP headers that are never included in the signature. `ShopifyAPI::Webhooks::Registry.process` validates only that the body's HMAC is correct, then blindly trusts the `shop` header to route/attribute the event to a tenant. An attacker in possession of any one genuinely-signed `(body, hmac)` pair issued by Shopify for the shared app secret (e.g., from webhooks Shopify sends to the attacker's own installed shop) can replay that exact body/hmac pair while substituting an arbitrary `shop-domain` header, and the signature will still validate.

### Finding Description
`to_signable_string` in `ShopifyAPI::Webhooks::Request` only returns the raw body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are derived independently from HTTP headers that are not part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e., the body) and compares it to the `hmac` header: [3](#0-2) 

`ShopifyAPI::Webhooks::Registry.process` only checks this body HMAC, then constructs `WebhookMetadata` directly from the unauthenticated `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` values, and dispatches it to the app's handler as trusted, verified data: [4](#0-3) 

Because the app-wide `client_secret` (`Context.api_secret_key`) is shared across all shops that install the app, any tenant that legitimately receives one authentic webhook (any topic, any body) obtains a valid `(body, hmac)` pair signed with that shared secret. That tenant can then submit the identical body/hmac to the app's webhook endpoint while forging the `shop-domain` header (and, independently, `topic`/`webhook-id`/`api-version` headers) to any other merchant's shop domain. The gem has no mechanism to reject this because the identity binding `hmac == HMAC(secret, body)` never constrains `shop`, so `shop` claimed by the header is not equal to `shop` actually authenticated by the signature.

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is meant to enforce: any app that keys per-shop side effects (e.g., "shop XYZ's subscription was cancelled", "shop XYZ's order was fulfilled", data sync, billing state, deauthorization handling) off `WebhookMetadata#shop` can be made to apply another merchant's genuine, secret-signed webhook body under an attacker-chosen shop identity. This is a cross-tenant access/data-integrity issue reachable by any unprivileged merchant who has installed the app (no access token, `client_secret`, or other credential theft required beyond being a normal installed tenant), matching the Critical "cross-tenant access" impact class in scope.

### Likelihood Explanation
Likelihood is moderate-to-high in any host app that installs on multiple shops: the attacker only needs to be a legitimate installed merchant (which is the normal, unprivileged position of any app user) to capture one authentic `(body, hmac)` pair from their own store's webhook traffic, then replay it against the app's public webhook endpoint with a forged `shop-domain` header. No secret material, TLS interception, or social engineering is required — only observation of traffic the attacker's own account legitimately receives.

### Recommendation
Include the `shop`, `topic`, and other headers relied upon by `Registry.process`/`WebhookMetadata` inside the signed payload used for HMAC verification (or otherwise cryptographically bind them to the body), so that `hmac` verifies the full set of fields the handler trusts, not just the body. At minimum, `to_signable_string` should incorporate `shop-domain` so that forged/replayed shop attribution fails verification.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both configured with the same app `client_secret`.
2. Shopify sends a legitimate webhook to the attacker's endpoint for `attacker-shop.myshopify.com`:
   - Headers: `x-shopify-topic: app/uninstalled`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`
   - Body: `{"id":123}`
3. Attacker captures this `(body, hmac)` pair (they own this shop and can freely observe traffic sent to their own server).
4. Attacker replays the identical body and hmac to the app's webhook endpoint, but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks the body against the HMAC — it never inspects the `shop` header.
6. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` (lines 188-200) calls the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", body: {"id":123}, ...)`, causing the app to treat this as an authentic `app/uninstalled` (or any other captured topic) event for the victim shop, e.g., deprovisioning or resetting victim-shop's app state.
