Webhook shop-tenant identity spoofing via HMAC that only covers the raw body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, but the `shop` value that identifies *which tenant* the webhook belongs to is read from an HTTP header that is never included in the signed material. Any unprivileged party who can trigger a webhook for their own (attacker-controlled) shop installation can capture a valid `(body, hmac)` pair and replay it with a different `X-Shopify-Shop-Domain` header, causing the app's webhook handler to process attacker-supplied data under another merchant's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines the signable string as only the raw body: [1](#0-0) 

Meanwhile, the tenant-identifying field `shop` is parsed straight from a header that is not part of that signable string: [2](#0-1) 

`Registry.process` verifies only the HMAC-over-body via `Utils::HmacValidator.validate(request)`, then immediately hands `request.shop` (and the rest of the unauthenticated header fields) to the registered handler as trusted identity data: [3](#0-2) 

`Utils::HmacValidator.validate` and `validate_signature` confirm the HMAC is computed only from `verifiable_query.to_signable_string` (the body) against the app's single, app-wide `client_secret` — a secret shared across *every* shop that has installed the app, not scoped per shop: [4](#0-3) 

**The broken equality:** the identity binding the app relies on is `shop (used by handler) == shop (that produced/authorized this HMAC)`. Because the HMAC only covers the body and the `client_secret` is identical for every shop under the same app installation, this equality does not hold — `hmac(body)` is valid for **any** shop domain the attacker chooses to put in the header, as long as the body bytes match one that was legitimately signed for the attacker's own store.

### Impact Explanation
An unprivileged internet user who installs the target app on their own (attacker-controlled) test store — a normal, permission-less action for any public/custom Shopify app — can:
1. Trigger a webhook topic on their own store to receive a legitimately-signed `(raw_body, X-Shopify-Hmac-Sha256)` pair.
2. Replay that exact body and HMAC to the app's webhook endpoint, but with `X-Shopify-Shop-Domain` (or `X-Shopify-Shop-Domain`/`shopify-shop-domain`) rewritten to a victim shop's domain.
3. `Registry.process` accepts the signature (it only checks the body) and calls the app's handler with `WebhookMetadata.new(... shop: request.shop ...)` populated with the victim's shop domain.

Any app logic that uses this `shop` value to select which tenant's data store/record to write to, delete, or reset (order sync, GDPR redact handlers, inventory updates, etc.) will act on the wrong tenant using attacker-controlled data — a cross-tenant data integrity/confidentiality breach that fits the Critical "cross-tenant access" impact category, structurally identical to the reported `LineOfCredit._close()` pattern where a value used to determine effect (`debt.lender`/here: target shop) was not the value actually verified by the binding check (repayment amount/here: HMAC-over-body).

### Likelihood Explanation
High. No credentials, access tokens, or `api_secret_key` knowledge are required beyond what any developer/merchant already has by legitimately installing the target app on their own store (a normal unprivileged action). Constructing the replay only requires copying an already-valid, previously-observed HMAC/body pair and modifying one HTTP header, which any client controlling the raw request can do.

### Recommendation
Include the shop identity (and ideally topic/webhook-id) in the signed material verified by `HmacValidator`, or independently verify that `request.shop` corresponds to a shop with a currently valid, previously-established session/installation before invoking the handler — do not trust `shop-domain` as authenticated purely because the body's HMAC validated. At minimum, document and enforce that consuming applications must cross-check `request.shop` against their own installed-shops table before processing, since the gem currently provides no such binding.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and configures webhook delivery to the app's endpoint.
2. Attacker triggers (or waits for) any registered webhook topic (e.g. `orders/create`) for `attacker.myshopify.com`, capturing the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` sent by Shopify — `H` is valid because `H = HMAC-SHA256(client_secret, B)`, and `client_secret` is the same for every shop using this app installation.
3. Attacker crafts a new HTTP POST to the same app endpoint with:
   - Body: `B` (unchanged, or edited to contain attacker-chosen order/customer data as long as JSON matches expected topic shape)
   - Headers: `X-Shopify-Hmac-Sha256: H` (unchanged), `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` and matches `H` — validation succeeds because the shop header was never part of the signed input.
5. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to act as if this data came from `victim-shop.myshopify.com`. [5](#0-4) [6](#0-5)

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
