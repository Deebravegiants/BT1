## Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats the `X-Shopify-Shop-Domain` header as the authoritative tenant identity for an incoming webhook, but the HMAC signature that "proves" the webhook is authentic only covers the raw request body. Any attacker who can obtain one legitimately-signed webhook body (e.g. by installing the app on their own store) can replay that exact body with a forged `shop-domain` header pointing at a different, victim shop, and the gem will report the request as verified and hand the attacker-chosen shop identity to the app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the HMAC purely over that signable string: [2](#0-1) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated headers with no cryptographic binding to the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` — the unauthenticated header value — to the app's handler as the trusted tenant identity: [4](#0-3) 

The documented usage pattern explicitly instructs apps to key their downstream logic off `data.shop`: [5](#0-4) 

The equality that should hold is: `hmac_signed_shop == shop_the_handler_acts_on`. Instead, the code only verifies `hmac(body) == received_hmac`; the shop field is completely outside that binding. An attacker who legitimately receives a webhook for their own store (a valid `body` + `hmac`, since Shopify signs it with the app's real `client_secret`) can resend that identical body/HMAC pair to the app's webhook endpoint while swapping only the `X-Shopify-Shop-Domain` header to a victim shop domain. `HmacValidator.validate` still passes (body unchanged), and `Registry.process` calls the handler with `shop: "<victim-shop>"` alongside the attacker's own webhook body.

### Impact Explanation
Because the gem's own documented pattern is to use `data.shop` as the tenant key when persisting/enqueuing webhook data, a successful forgery lets an unprivileged attacker (who only needs to be a merchant/installer of the target app on their own shop) inject data that the host application attributes to an arbitrary victim shop. This is a cross-tenant data-confusion/injection primitive entirely mediated by this gem's webhook verification logic returning "valid" for a request whose tenant-identifying header was never authenticated.

### Likelihood Explanation
Exploitation requires no secrets beyond installing the target app on an attacker-controlled shop (a normal, unprivileged action) and the ability to send an arbitrary HTTP request with modified headers to the app's public webhook endpoint — both trivial for an internet-based attacker. The gem's own API surface (`Registry.process`, `Request#shop`) offers no way for an app to detect the mismatch, since the mismatch is by design invisible to `HmacValidator.validate`.

### Recommendation
Do not treat `request.shop` as verified merely because `HmacValidator.validate` passed. Either:
- Include the shop domain (and ideally topic/webhook_id) in the signable string used for HMAC computation, matching it to a per-shop secret or verifying it out-of-band, or
- Document/require that consuming apps cross-check `data.shop` against a known/registered installed shop (e.g., existing session storage) before trusting the payload, and consider exposing a helper in the gem to do so, since currently the "verified" webhook API returns an unauthenticated shop value alongside the authenticated body.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook event (e.g. `orders/create`). Shopify sends:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid hmac over raw body>
   X-Shopify-Shop-Domain: attacker.myshopify.com
   Body: {"id":123,...}
   ```
2. Attacker captures this exact `raw_body` and `X-Shopify-Hmac-Sha256` value.
3. Attacker POSTs to the app's public webhook endpoint with the same body/HMAC but:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `hmac(raw_body)` — this still matches, so verification succeeds: [6](#0-5) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's own order body, and — following the gem's documented pattern — the host app enqueues/stores this data under the victim shop's tenant record.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
