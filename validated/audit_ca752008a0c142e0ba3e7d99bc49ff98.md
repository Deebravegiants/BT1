Confirmed the design: `Context.api_secret_key` is a single, app-wide secret configured once via `ShopifyAPI::Context.setup` [1](#0-0) , and it is the same secret used to HMAC-validate webhooks for every shop that installs the app [2](#0-1) .

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `HmacValidator.validate` computes/verifies the HMAC solely over that body using the app-wide `Context.api_secret_key` [3](#0-2) [4](#0-3) . The `shop-domain` header, however, is read directly and unauthenticated, then handed to the app's webhook handler as the trusted tenant identifier via `WebhookMetadata` [5](#0-4) [6](#0-5) . Since the same `api_secret_key` is shared across every shop that installs the app, any legitimate webhook payload signed for one tenant remains validly signed when replayed with a different `shop-domain` header value, breaking the binding between "shop the HMAC actually authenticates" (none — the secret is app-global, not shop-specific) and "shop the application attributes the event to."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` (used as the HMAC-signed content) is exactly `@raw_body` — it never mixes in `topic`, `shop-domain`, `webhook-id`, or `api_version` [3](#0-2) . `Utils::HmacValidator.validate_signature` computes `OpenSSL::HMAC.hexdigest` over that same signable string and compares against the `hmac-sha256` header using the single, app-wide `Context.api_secret_key` (or `old_api_secret_key`) [2](#0-1) . Because this secret is identical for every merchant/shop that has installed the app (it is configured once in `ShopifyAPI::Context.setup`, not per-tenant), a valid `(body, hmac)` pair captured from one tenant's webhook delivery remains cryptographically valid for *any* `shop-domain` value.

`Webhooks::Registry.process` trusts `request.shop` (the raw header) as the tenant identity passed to the handler once the (body-only) HMAC check passes [6](#0-5) . The gem's own documentation instructs integrators to use `data.shop` as the authoritative shop identifier for routing/persisting the webhook payload (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [7](#0-6) , so an app following the documented API is directly exposed.

The identity binding that should hold is:
`shop authenticated by the HMAC == shop the payload is attributed to`

In reality the HMAC authenticates only "signed with this app's secret" (true for all tenants), while `shop` comes from an attacker-controllable, unsigned header. An attacker who is a legitimate user of the app (installs it on their own store, an unprivileged action) can capture one of their own valid webhook deliveries (body + `hmac-sha256`) and replay it to the app's shared webhook endpoint with the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header rewritten to a victim shop's domain. `HmacValidator.validate` will still return `true` because the signature check never inspects the header, and the handler will process the attacker's payload as though it originated from the victim shop.

### Impact Explanation
This breaks the tenant/shop boundary that the whole HMAC scheme exists to protect: an unprivileged app user can inject events, order data, or lifecycle notifications (e.g. `app/uninstalled`, `orders/create`, `customers/data_request`) attributed to a shop they do not own, into any app built with this gem that trusts `WebhookMetadata#shop` as documented. Depending on how the host app uses `data.shop` (e.g., to look up which shop's session/data to mutate), this is a cross-tenant data-integrity/confidentiality issue — a forged webhook can cause the app to act on or corrupt another merchant's records.

### Likelihood Explanation
Any user can install a Shopify app on their own store for free/dev purposes, giving them a stream of validly-signed webhook bodies for "their" shop. Replaying that exact body with a modified shop header against the app's single public webhook endpoint requires no secret material beyond what a legitimate installer already receives. This is straightforward to exploit against any app that follows the documented pattern of trusting `data.shop`.

### Recommendation
Bind the shop identity into the material that is actually HMAC-verified, or otherwise cross-check it: e.g., require host apps to verify `request.shop` against the shop associated with the session/webhook registration that was expected to receive that specific `webhook_id`/topic, or have `Request#to_signable_string` incorporate the shop header (and other webhook metadata) into the signed content rather than only the body, so a captured body+HMAC pair cannot be replayed under a different shop identity.

### Proof of Concept
1. App merchant M installs the target Shopify app on shop `m.myshopify.com` and registers a webhook handler for `orders/create`.
2. Shopify delivers a legitimate webhook to the app's endpoint: body `B`, header `X-Shopify-Hmac-Sha256: H` (computed over `B` with the app's single `api_secret_key`), and `X-Shopify-Shop-Domain: m.myshopify.com`.
3. Attacker M captures this request (it was delivered to infrastructure they control, since it's their own shop's webhook).
4. Attacker replays the identical `(B, H)` pair to the same app endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim.myshopify.com"...})` is constructed; `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`, so validation succeeds [4](#0-3) .
6. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim.myshopify.com", body: B, ...)` [8](#0-7) , causing the host app to process attacker-controlled data as if it belonged to `victim.myshopify.com`.
