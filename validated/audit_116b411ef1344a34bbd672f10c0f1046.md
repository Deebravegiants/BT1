### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) used to route a webhook to the host application's handler from the `X-Shopify-Shop-Domain` HTTP header, but that header is never included in the bytes that are HMAC-verified. Only the raw request body is signed. As a result, an attacker who can obtain any single validly-HMAC-signed webhook payload (e.g. from a shop they themselves control, since the HMAC secret is the app's single, shared `client_secret` across all installs) can replay that payload while substituting an arbitrary victim `shop-domain` header, and `ShopifyAPI::Webhooks::Registry.process` will still accept it as authentic and hand it to the host app's handler tagged with the victim's shop identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated headers: [2](#0-1) 

`Utils::HmacValidator.validate` only compares the HMAC over `to_signable_string` (i.e., the body) against the `hmac-sha256` header value: [3](#0-2) 

`Webhooks::Registry.process` performs this HMAC check and then immediately trusts `request.shop` (an unauthenticated header) to build the tenant-identifying `WebhookMetadata` object that is dispatched to the host application's `handle` implementation: [4](#0-3) 

`WebhookMetadata#shop` is a plain `String` const with no additional binding to the HMAC-verified content: [5](#0-4) 

This is precisely the identity-binding break the report's bug class describes: a field (`shop`) is acted on by the handler dispatch logic but is not covered by the HMAC that is supposed to authenticate the request. The equality that should hold — `shop value cryptographically bound in the verified signature == shop value used to attribute the webhook to a tenant` — does not hold in this gem's implementation.

Notably, this gem does apply the correct pattern elsewhere: for OAuth callback verification, `Auth::Oauth::AuthQuery#to_signable_string` explicitly includes `shop` in the signed parameter set: [6](#0-5) 

This confirms the omission in the webhook path is an inconsistency in this gem's own code, not an inherent limitation of Shopify's webhook protocol design.

### Impact Explanation
Because the HMAC secret (`api_secret_key`/`client_secret`) is shared by the app across every merchant install, any unprivileged party who installs the app on their own (attacker-controlled) shop can trigger events and capture legitimately-signed webhook deliveries (valid `hmac-sha256` over a body they fully control). By replaying that body/HMAC pair with the `X-Shopify-Shop-Domain` header rewritten to a victim shop, they produce a request that `Registry.process` accepts as fully authenticated and forwards to the host application's webhook handler labeled as belonging to the victim tenant. Any host application that (as documented for this gem) uses `WebhookMetadata#shop` to select the victim's session/access token or otherwise act on the victim's tenant data will process attacker-controlled content under the victim's identity — a cross-tenant access/data-integrity breach attributable to this gem's verification gap.

### Likelihood Explanation
The prerequisite (installing the target app on an attacker-owned shop, or otherwise obtaining one signed webhook body for that app) is trivial for many public apps, since app installation itself typically requires no special privilege. No secrets, tokens, or MITM capability are required — only a single captured signed webhook and the ability to send an HTTP POST with modified headers to the app's webhook endpoint.

### Recommendation
Bind the tenant/topic identity into the HMAC-verified content instead of trusting unauthenticated headers. At minimum, include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in `Request#to_signable_string`, mirroring the approach already used in `Auth::Oauth::AuthQuery#to_signable_string`, so that `HmacValidator.validate` fails if any of these attacker-controllable header values are altered.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com` (or otherwise obtain any legitimately delivered webhook for the app).
2. Capture a real webhook delivery: raw body `B`, and `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(client_secret, B)`.
3. Re-send the request to the app's webhook endpoint unchanged except for `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `to_signable_string` (`B` only) and accepts it, since `B` and `H` are unchanged.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) builds `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and forwards it to the app's handler, which now processes attacker-chosen body content attributed to `victim-shop.myshopify.com`.
