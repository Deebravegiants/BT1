### Title
No enforced origin/account binding at the `getFees` module boundary; unauthorized cross-account fee computation possible if any RPC surface exposes it directly - ([File: features/fees/module/index.js])

### Summary
`feesModule.getFees` accepts a raw `walletAccount` string and uses it directly to read `walletAccountsAtom`, `txLogsAtom`, and `accountStatesAtom` with no check that the caller/origin is authorized for that account. This module contains zero origin-awareness — enforcement, if any, must happen entirely outside this file, and the generic RPC transport layer in this repo (`@exodus/json-rpc`, `@exodus/sdk-rpc`) provides no such enforcement.

### Finding Description
`createFees` destructures `walletAccount` from the caller-supplied params and uses it as a raw lookup key into `walletAccountsData[walletAccount]`, `txLogs[walletAccount]`, and `accountStates[walletAccount]` [1](#0-0) , with no `origin`, `id`, or caller-identity parameter anywhere in the function signature or body [2](#0-1) . The module is registered with `public: true` [3](#0-2) , and the thin `fees` API layer just forwards the module's `getFees` verbatim with no additional guard [4](#0-3) .

The generic RPC plumbing in this repo (`@exodus/json-rpc` and `@exodus/sdk-rpc`) is origin-agnostic: `RPC.exposeMethods` just flattens an object of functions into a method-name map and dispatches requests to them by name, with no concept of caller identity, origin, or per-account authorization anywhere in `libraries/json-rpc/index.js` or `libraries/sdk-rpc/src/rpc.ts` [5](#0-4) [6](#0-5) . Similarly, `browser-extension-rpc`'s `createBackgroundRpc`/`createUiRpc` just wire up a port transport and call `rpc.exposeMethods(methods)` — again no origin binding [7](#0-6) .

Separately, the repo does have an explicit origin-authorization primitive: `features/connected-origins`, whose `ConnectedOrigins.isTrusted`/`getConnectedAccounts` gate access to accounts based on a stored per-origin trust/connection record [8](#0-7) [9](#0-8) . However, I could not find any code path that wires `connectedOrigins.isTrusted`/`getConnectedAccounts` into the fees module or into a request-dispatch layer that intercepts calls like `fees.getFees` and rejects/rewrites `walletAccount` based on the requester's origin. No dapp-facing "provider" (e.g., an injected `window.exodus`-style bridge with a method allowlist per origin) was found in the indexed portions of this repo; the only concrete RPC exposure points found (`sdk-minimal-demo`, `browser-extension-rpc`) forward the whole SDK/API surface generically.

This is architecturally consistent with the described threat: if any RPC/dapp-facing surface exposes `fees.getFees` (which is `public: true` and part of the exported `feesApi`) without an intermediate origin-scoping wrapper, then any caller on that RPC channel can pass an arbitrary `walletAccount` value and have it processed end-to-end, since neither the module, the API layer, nor the generic RPC library performs any origin/account binding.

### Impact Explanation
If reachable via an untrusted-origin channel, this allows unauthorized cross-account computation: reading another wallet account's cached tx logs/account state (`txLogsAtom`, `accountStatesAtom`) and deriving that account's receive address via `addressProvider.getReceiveAddress`, disclosing account linkage/address information for an account the origin was never authorized to access. This is an origin-isolation/authorization-boundary violation, not itself a key-compromise or signing bug, since `getFees` never signs, exposes secrets, or moves funds.

### Likelihood Explanation
Exploitability is entirely conditional on whether an actual product surface (browser extension content script → background RPC, or mobile webview RPC) exposes the full SDK/`public: true` module set to untrusted dapp origins without an intervening origin-scoping/allowlist layer. Within the code actually indexed in this repo, no such unscoped, dapp-reachable exposure of `fees.getFees` was found — the concrete RPC wiring examples found (`sdk-minimal-demo`, generic `browser-extension-rpc`) are either demo/internal-thread code or generic libraries without origin concepts baked in, and the dapp-provider/content-script code that would perform origin scoping for real dapp traffic was not located in the index. This makes the finding a design-level absence-of-defense-in-depth at the module/API layer rather than a demonstrated exploitable path in this codebase as indexed.

### Recommendation
Do not rely on outer layers alone to enforce origin/account scoping. Have the `fees` module (or the `feesApi` wrapper) require an authorized-account-list/`origin` parameter and validate `walletAccount` against `connectedOrigins.getConnectedAccounts({ origin })`/`isTrusted({ origin })` before touching `walletAccountsAtom`, `txLogsAtom`, or `accountStatesAtom`, rejecting the call if `walletAccount` is not in the origin's authorized set. Additionally, whatever RPC bridge is actually used to expose the SDK to untrusted dapp content should implement a per-origin method/account allowlist rather than relying on generic `exposeMethods` flattening.

### Proof of Concept
Because no dapp-facing RPC/provider wiring that binds origin to `fees.getFees` was found in this repo's index, a conclusive integration PoC through "the RPC bridge layer" cannot be constructed from available code. A representative unit-level PoC demonstrating the module's lack of internal scoping:

export const flattenObject = <T>(obj: T, path: string[] = []): { [name: string]: Fn } => {
  if (typeof obj === 'function') {
    return { [serializePath(path)]: obj as Fn }
  }

  if (typeof obj !== 'object' || !obj) return {}

  return Object.keys(obj).reduce((acc, key) => {
    return { ...acc, ...flattenObject(obj[key as keyof T], [...path, key]) }
  }, {})
}

  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
