### Title
Escrowed funds become permanently unrecoverable when an order's fixed `beneficiary` address is blacklisted by the escrowed ERC20 token - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2`'s cross-chain escrow settlement (`RedeemEscrow`/`RefundEscrow`) always pays out to an immutable `beneficiary` address baked into the order at creation/fill time. If that token enforces a blacklist (e.g., USDC's `isBlacklisted`), and the beneficiary address is or becomes blacklisted, the `safeTransfer` inside `_withdraw` reverts every single time the message is (re)delivered, and there is no mechanism to change the beneficiary or otherwise recover the escrowed tokens.

### Finding Description
`IntentsBase._withdraw` unconditionally sends escrowed tokens to a `beneficiary` decoded from the cross-chain `WithdrawalRequest` via `safeTransfer`: [1](#0-0) 

This beneficiary is fixed at order-creation/fill time and cannot be altered later:
- For `RefundEscrow`, the beneficiary is `order.user`, embedded in the message dispatched from `_cancelFromSource`/`_cancelFromDest`: [2](#0-1) 
- For `RedeemEscrow`, the beneficiary is `msg.sender` (the filling solver), embedded in `_fillCrossChain`: [3](#0-2) 

`onAccept` decodes and dispatches to `_withdraw` with `finalize=true`, marking `_filled[commitment]` and releasing escrow in the same call: [4](#0-3) 

When the ERC20 `safeTransfer` reverts (e.g., recipient blacklisted by USDC), the entire `onAccept` external call fails. `EvmHost.dispatchIncoming` catches this failure via a low-level `.call` and only deletes the request receipt "so it can be retried" - it does not otherwise handle or discard the message: [5](#0-4) 

Because the beneficiary encoded in the request is immutable and there is no admin/governance function in `IntentsBase`/`ExtrinsicIntents`/`IntrinsicIntents` to update it or force-release funds to an alternate address, every retry of the same commitment will deterministically hit the same `safeTransfer` revert. The escrow entry in `_orders[commitment][token]` is never decremented (the revert occurs before/atomically with that state change), so the tokens remain locked in the `IntentGatewayV2` contract indefinitely.

This mirrors the Predy `vault.recipient` bug class: a token-transfer to an attacker/user-controlled address that a token issuer can blacklist, embedded in a payout path with no fallback, causing the payout operation to permanently fail. In the Predy case the impact was temporary (liquidation could still occur at reduced margin); here, since `_withdraw`/`onAccept` is the *only* code path that releases escrow for a given commitment and there is no zero/negative-margin equivalent fallback, the impact is a full and permanent freeze of the escrowed principal.

### Impact Explanation
Any order whose input token enforces a blacklist (USDC on most EVM chains explicitly supports this and is a standard settlement asset for intents/bridging) can have its escrowed principal permanently frozen if the `order.user` (refund path) or filling solver (redeem path) address is blacklisted at the time of message delivery. Because Hyperbridge relayers will keep re-delivering/retrying a request whose receipt was deleted, the transaction will keep failing identically, and the funds sit unclaimable in the `IntentGatewayV2` contract forever - a concrete, permanent freezing of user/solver funds with no on-chain recovery path.

### Likelihood Explanation
This does not require any protocol/governance error — it only requires:
1. An order denominated in a blacklist-capable token (USDC), and
2. The `order.user` or filling solver's address becoming blacklisted between order placement/fill and settlement (e.g., an address sanctioned, or a griefing user deliberately using/associating a blacklistable address), or a malicious solver deliberately filling with a soon-to-be-blacklisted address to lock a competitor's/protocol's escrow accounting flow.

The likelihood is realistic for the `RefundEscrow` path in particular, since order cancellation after deadline can be triggered by "anyone" per the code's own documentation, meaning the transfer target cannot be re-verified or substituted by the triggering party. Given USDC's real-world blacklist usage, this is a plausible, externally-triggerable Medium-severity condition, matching the judged severity of the original Predy finding.

### Recommendation
- Add a pull-based/escrow-claim pattern as a fallback: if `safeTransfer` to `beneficiary` fails, credit the amount to an internal claimable balance for that beneficiary (or an admin-designated alternate address) instead of reverting the whole `onAccept`/`_withdraw` call.
- Alternatively, wrap the transfer in a try/catch and, on failure, hold funds in a per-commitment "stuck funds" mapping withdrawable by the beneficiary from a different, unblacklisted address (e.g., via signature-based redirection), analogous to Predy's recommendation to require health/validity checks or blacklist checks before finalizing a payout.
- Ensure that `_orders[commitment][token]` bookkeeping is not left in a permanently unresolvable state when the payout target cannot receive tokens.

### Proof of Concept
1. User places a cross-chain order with `inputs = [USDC, amount]` on the source chain via `IntentGatewayV2`, escrowing USDC and setting `order.user` to their own address.
2. A solver fills the order on the destination chain (`_fillCrossChain`), which dispatches a `RedeemEscrow` `WithdrawalRequest` with `beneficiary = solver`.
3. Before the message is relayed and delivered, the solver's or (in the refund path) `order.user`'s address is added to USDC's blacklist (simulating a real-world compliance blacklisting event, as also used in the original PoC's `MockERC20` with a `notBlacklisted` modifier).
4. The relayer delivers the `PostRequest` to `EvmHost.dispatchIncoming`, which calls `IntentGatewayV2.onAccept` → `_withdraw` → `IERC20(token).safeTransfer(beneficiary, amount)`, which reverts due to the blacklist.
5. `dispatchIncoming` catches the revert, deletes `_requestReceipts[commitment]`, and returns — allowing (but not guaranteeing success of) a retry. Every subsequent retry with the same request body fails identically since `beneficiary` is immutable.
6. `_orders[commitment][token]` retains the escrowed balance forever; the tokens are permanently frozen in the `IntentGatewayV2` contract with no recovery function available to reclaim them.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
