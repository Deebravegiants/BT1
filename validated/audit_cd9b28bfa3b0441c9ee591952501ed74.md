### Title
Wallet-account index reuse causes connected dApp origins to silently inherit access to a different account's addresses - (File: `features/wallet-accounts/src/module/utils.ts`, `features/connected-origins/module/connections.js`)

### Summary
`getNextIndex` reuses a previously-freed wallet-account `index` (and therefore the same wallet-account name, e.g. `exodus_1`) for a brand-new, unrelated wallet account when `fillIndexGapsOnCreation` is enabled, while `connected-origins` persists dApp trust/connection state keyed only by that wallet-account **name** string, never re-validating that the underlying account identity (`seedId`/`id`) still matches what was originally approved.

### Finding Description
`getNextIndex` (`features/wallet-accounts/src/module/utils.ts:47-75`) computes the index for a newly created wallet account by scanning for a gap in the *currently enabled* accounts: [1](#0-0) 
When `fillIndexGapsOnCreation` is true, a disabled/removed account's index (and thus its canonical name, e.g. `exodus_1`) becomes eligible for reuse by a subsequently-created account, confirmed by the `removeMany` test suite: [2](#0-1) 

`WalletAccounts.#replaceAll` writes the new account under that same name key without any binding to the previous account's identity beyond the name string: [3](#0-2) 

Meanwhile, `ConnectedOrigins` (`features/connected-origins/module/connections.js`) stores per-origin trust, `walletAccount`, and cached `connectedAccountsAtom` addresses **keyed purely by wallet-account name**: [4](#0-3) 
`getConnectedAccounts` resolves addresses for a trusted origin straight from `connectedAccountsAtom` using the current name-to-address mapping, with no check that the account occupying that name is the same entity that was originally connected/trusted: [5](#0-4) 
`updateConnectedAccounts` recomputes `connectedAccountsAtom` from `enabledWalletAccountsAtom` whenever the account set changes (verified in tests), again purely by name: [6](#0-5) 

This mirrors the `AvalancheL1Middleware` `nodeId` reuse bug precisely: an identifier that is durable/permanently recorded against Party A (`operatorNodes[A]` / a trusted origin's `walletAccount` name) is later re-bound on the "current" side (`registeredValidators(P_X)` / `walletAccountsInternalAtom[name]`) to a completely different entity (Operator B / a newly created, unrelated wallet account), and the consuming code (`getActiveNodesForEpoch` / `getConnectedAccounts`) resolves state through the *current* binding of the reused identifier rather than the *original* entity that was actually authorized.

### Impact Explanation
If a wallet account is removed and, due to `fillIndexGapsOnCreation`, a new and entirely different account (different seed, different keys) is created and lands on the same name slot (e.g. `exodus_1`), any dApp origin that was previously trusted/connected against that name transparently gains visibility into (and, depending on downstream signing flows keyed by the same name, potential access to sign for) the new account's addresses — without the user re-approving the connection for the new account. This is a cross-account privilege bleed: trust granted to one account identity leaks to a different, unrelated account identity solely because they share a recycled name/index.

### Likelihood Explanation
Requires: (1) `fillIndexGapsOnCreation` enabled for the platform, (2) the user removing a wallet account that had an active dApp connection, and (3) creating a new account that happens to fill the freed index/name. This is a normal user-driven sequence (not attacker-controlled without user action), which lowers likelihood relative to the original externally-triggerable Avalanche exploit, but the resulting privilege bleed is unintentional and silent from the user's perspective — the user does not expect a previously-granted dApp permission to transfer to a new, unrelated account.

### Recommendation
Bind `connected-origins` trust/connection records to a durable account identity (e.g. `seedId` + `id`, not just the mutable/reusable name), or invalidate/require re-approval of a connection whenever the wallet account occupying a given name changes identity (e.g., `seedId` differs from what was recorded at connect-time). `getConnectedAccounts`/`updateConnectedAccounts` should verify the recorded identity still matches the current occupant of the name before returning addresses.

### Proof of Concept
1. Enable `fillIndexGapsOnCreation`. Create wallet account `exodus_1` (Seed A).
2. Connect a dApp origin to `exodus_1`, granting it trust and caching its addresses in `connectedAccountsAtom.exodus_1`.
3. Remove `exodus_1` (`removeMany(['exodus_1'])`), confirmed possible per [2](#0-1) .
4. Create a new wallet account under an unrelated seed/source; `getNextIndex` assigns it index `1`/name `exodus_1` again, per [7](#0-6) .
5. `updateConnectedAccounts` recomputes `connectedAccountsAtom.exodus_1` with the new account's addresses.
6. The still-trusted origin calls `getConnectedAccounts`, and per [8](#0-7)  receives the *new* account's addresses under the old trust grant — without any fresh user approval.

Note: full confirmation that this reuse path is reachable in a shipped platform (vs. test-only `fillIndexGapsOnCreation` usage) and whether UI-layer reconnect prompts mitigate this in practice was not fully verifiable within available tooling; a Devin session with full repo/runtime access would be needed to confirm end-to-end exploitability across the extension/mobile UI layers.

export const getNextIndex = ({
  walletAccounts,
  seedId,
  source,
  compatibilityMode,
  fillIndexGapsOnCreation,
}: GetNextIndexParams) => {
  const existing = Object.values(walletAccounts)
    .filter(
      (w) =>
        w.source === source &&
        w.compatibilityMode === compatibilityMode &&
        w.seedId === seedId &&
        !w.id &&
        (!fillIndexGapsOnCreation || w.enabled)
    )
    .sort((a, b) => (a.index ?? 0) - (b.index ?? 0))

  if (fillIndexGapsOnCreation) {
    return (
      [...existing.keys()].find((i) => existing[Number(i)]?.index !== Number(i)) ?? existing.length
    )
  }

  const indexes = existing
    .map(({ index }) => index)
    .filter((i): i is number => typeof i === 'number')
  return Math.max(-1, ...indexes) + 1
}

  /**
   * Returns the connected accounts for a given origin with the active wallet account sorted first. Can be used while
   * the wallet is locked
   */
  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
