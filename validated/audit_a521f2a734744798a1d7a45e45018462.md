Audit Report

## Title
LDAP DN injection via `ldap.EscapeFilter` misuse when constructing bind DN and search-base DN strings - (File: core/sessions/ldapauth/ldap.go)

## Summary
The LDAP authentication path in `core/sessions/ldapauth/ldap.go` escapes user-supplied email input with `ldap.EscapeFilter` (RFC 4515 filter-value escaping) and then concatenates the result directly into RFC 4514 Distinguished Name (DN) strings that are used as the bind DN passed to `conn.Bind`. Since `EscapeFilter` does not escape DN-structural metacharacters (`,`, `+`, `"`, `<`, `>`, `;`), an attacker-controlled `email` value can inject additional RDN components into the DN that the LDAP server parses for `Bind`, which is the wrong escaping primitive for this context.

## Finding Description
In `CreateSession` [1](#0-0) , and identically in `TestPassword` [2](#0-1) , the code builds `searchBaseDN` by string-formatting `l.config.BaseUserAttr()=%s` with an `EscapeFilter`-escaped but not DN-escaped email, then passes this directly as the bind DN to `conn.Bind`. `EscapeFilter` only escapes `(`, `)`, `\`, `*`, and NUL per RFC 4515 — it leaves `,`/`+`/`"`/`<`/`>`/`;` untouched, which are exactly the characters that delimit RDN components in a DN string (RFC 4514). This confirms the root cause described in the claim: the wrong escaping function is applied for the context in which the value is used. In `FindUser`, a similarly-escaped value is embedded inside a filter expression `(&(uniquemember=%s=%s,%s,%s))` [3](#0-2) ; here the value sits as a comparison value inside filter parentheses, so `EscapeFilter` is the appropriate/sufficient primitive against filter-syntax breakout for that call site, but the DN-shaped bind-DN construction in `CreateSession`/`TestPassword` is not similarly protected. No DN-escaping helper exists anywhere in the codebase (`grep` for `EscapeDN` returns nothing), confirming the described gap.

## Impact Explanation
This is a genuine coding defect in a security-sensitive path: DN metacharacters from attacker-controlled email input flow unescaped into the DN string passed to `conn.Bind`, which is a broken security assumption (that filter-escaping is sufficient sanitization for DN construction) that maps to CWE-90 LDAP injection. However, note that exploiting this into an actual authentication bypass or impersonation requires that the resulting malformed/injected DN happens to resolve to an existing directory entry, and that `conn.Bind` still enforces the LDAP server's own password check against whatever DN results — an attacker cannot simply authenticate as another identity without also supplying valid credentials for the resulting DN, unless a misconfigured directory permits unauthenticated/anonymous bind for empty passwords. This tempers the "auth bypass" severity of the finding to primarily a DN-structure-corruption / injection defect with directory- and configuration-dependent downstream effects, as acknowledged even in the report's own hedged impact language ("depending on the directory layout").

## Likelihood Explanation
The vulnerable code is reachable directly from the unauthenticated login endpoint (`CreateSession`) with fully attacker-controlled `sr.Email`, requiring only that LDAP authentication is configured (`NewLDAPAuthenticator`) — a standard, supported deployment mode, not a misconfiguration. No prior session or elevated privilege is needed to submit the crafted email, satisfying the "unprivileged actor" requirement.

## Recommendation
Implement and use a proper RFC 4514 DN-escaping routine (escaping `,`, `+`, `"`, `\`, `<`, `>`, `;`, leading/trailing spaces, and a leading `#`) for any user-supplied value interpolated into `searchBaseDN` construction in `CreateSession` (ldap.go:405-411) and `TestPassword` (ldap.go:511-514). Reserve `ldap.EscapeFilter` strictly for values placed inside filter expressions (as in `FindUser`'s `uniquemember=...` filter value), and never rely on it to sanitize DN components used directly as a bind DN.

## Proof of Concept
1. Configure chainlink with LDAP auth enabled, `BaseUserAttr=uid`, `UsersDN=ou=users`, `BaseDN=dc=example,dc=com`, against a test LDAP directory containing an entry with a DN that could be reached via comma-injection (e.g., `uid=victim,ou=admins,dc=example,dc=com`).
2. Send a request to the session-creation endpoint with `email = "victim,ou=admins,dc=example,dc=com"` and any password.
3. Observe the resulting `searchBaseDN` in `CreateSession` becomes `uid=victim,ou=admins,dc=example,dc=com,ou=users,dc=example,dc=com` instead of a single-RDN value under `ou=users`, demonstrating that unescaped input controls DN structure.
4. To fully demonstrate impact beyond structural corruption, show a directory configuration/entry where this injected DN resolves and `conn.Bind` succeeds or otherwise misbehaves (e.g., anonymous/unauthenticated bind edge case), which is directory-configuration dependent.
