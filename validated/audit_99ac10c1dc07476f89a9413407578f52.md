### Title
Webhook shop-tenant confusion: `x-shopify-shop-domain` header is not covered by HMAC verification - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated for a given shop based on `Utils::HmacValidator.validate(request)` returning true, then immediately trusts `request.shop` (read from the `X-Shopify-Shop-Domain` header) as the tenant identity passed to the app's handler [2](#0-1) . However, the HMAC that is actually verified only covers the raw request body — `to_signable_string` returns `@raw_body` and nothing else [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values are all pulled straight from unauthenticated HTTP headers [3](#0-2) . `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it only against `verifiable_query.hmac`, never touching `shop` [4](#0-3) .

### Finding Description
The equality the code implicitly asserts is:
`HMAC-verified(raw_body) == HMAC-verified(shop-that-owns-this-webhook)`

This equality is false. Because the same app-level `api_secret_key` is shared across every shop that installs the app, and the HMAC signature is computed purely from the body bytes, any body that produces a given valid signature under that shared secret is validly signed *regardless of which shop header accompanies it*. A user who has (or creates) their own legitimate, low-privilege Shopify store on the same app can:
1. Register/trigger a webhook for their own shop and capture a real HTTP request from Shopify, including a validly computed `X-Shopify-Hmac-Sha256` for some raw body.
2. Replay that exact `raw_body` (and therefore the exact same valid signature) to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. `HmacValidator.validate` still returns `true`, because it only checks `raw_body` against the signature — it never binds `shop` to the signature. `Registry.process` then calls the handler with `WebhookMetadata.new(..., shop: request.shop, ...)` where `shop` is now the attacker-supplied victim domain [5](#0-4) .

Any host application logic that uses this trusted-looking `shop` field to look up per-tenant sessions/tokens, write to per-tenant data stores, or make follow-up authenticated Admin API calls on behalf of "the shop that sent this webhook" will act cross-tenant, using an attacker-chosen shop identity for a payload the attacker fully controls (since it's their own webhook body).

### Impact Explanation
This breaks the tenant boundary the library is expected to enforce for webhook authenticity: `Registry.process`'s job is specifically to "verify the request did indeed come from Shopify" (per the gem's own documentation) before handing off `shop`-scoped data to the app, but the shop identity itself is never included in what's verified. This is a cross-tenant confusion vulnerability — an unprivileged holder of any single Shopify store on the app can cause the app to process a fully attacker-controlled webhook body under a victim shop's identity.

### Likelihood Explanation
Likelihood is moderate-to-high: it requires no special access beyond installing the app on any store (the normal, unprivileged path any merchant/developer can take), capturing one legitimate webhook delivery for their own store, and replaying it with a modified header — a trivial HTTP-level operation once the flaw is known. No access token, `client_secret`, or leaked credential is required.

### Recommendation
`Utils::HmacValidator`/`Webhooks::Request` should bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is authenticated, not leave them as bare, unauthenticated headers trusted by `Registry.process`. Concretely, the app should be required/encouraged to cross-check `request.shop` against the shop associated with the actual webhook subscription (e.g., correlate `webhook_id`/`topic` with a value stored at registration time), or the gem should document/enforce that `shop` must not be relied upon as an authenticated value from `Webhooks::Request` alone.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` (any developer can do this).
2. Register a webhook subscription; trigger it (e.g., via `orders/create`) and capture the raw POST Shopify sends, including headers `X-Shopify-Hmac-Sha256: <sig>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`.
3. Resend the identical raw body and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request whose `shop` returns `"victim-shop.myshopify.com"` [6](#0-5) .
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the raw body signature [7](#0-6) .
6. The handler receives `WebhookMetadata` claiming this attacker-controlled body originated from `victim-shop.myshopify.com` [5](#0-4) , and any tenant-scoped action the host app takes based on that field is now cross-tenant.
