### Title
Webhook `shop` field trusted by `Registry.process` is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity using `Utils::HmacValidator.validate`, which computes the HMAC over `Webhooks::Request#to_signable_string`. For webhooks, that signable string is only the raw request body [1](#0-0) . The `shop` value that is subsequently handed to the app's webhook handler as an authenticated identifier is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never included in the signed bytes [2](#0-1) . This breaks the binding: `hmac-verified bytes == body only`, while `shop identity used by the handler == unauthenticated header`.

### Finding Description
`Registry.process` performs exactly one authenticity check before dispatching to the app-provided handler: [3](#0-2) 

`Utils::HmacValidator.validate` in turn calls `validate_signature`, which computes the HMAC solely over `verifiable_query.to_signable_string` and compares it to the `hmac` header value with `OpenSSL.secure_compare`: [4](#0-3) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, and `webhook_id` are all pulled from unauthenticated headers [5](#0-4) .

Once validated, `Registry.process` passes `request.shop` straight into `WebhookMetadata`, which the gem's own documentation describes as an authenticated attribute of "a webhook request from Shopify" that has been verified: *"This will verify the request did indeed come from Shopify and then call the specified handler for that webhook."*

Because a single app has one `Context.api_secret_key` shared across every shop that installs it, an unprivileged merchant who has installed the app (an "unprivileged internet user" with respect to any other tenant) legitimately receives real, validly-signed webhooks at their own callback URL for their own store. Nothing in this gem prevents that same person from replaying the exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain: the HMAC still validates (it only checks body bytes against the shared secret), yet `WebhookMetadata#shop` — the value the handler uses to decide "which tenant does this event belong to" — now falsely claims to be the victim.

### Impact Explanation
This is a cross-tenant identity-binding break: the HMAC authenticates "these bytes were produced with our api_secret_key" but the gem (and the documented contract of `Registry.process`) implicitly extends that trust to "this event happened for shop X," which is never actually bound to the signature. An attacker-controlled shop can trigger webhook handling logic (e.g., `app/uninstalled`, `shop/redact`, `customers/redact`, or any topic with an attacker-predictable/constant body) attributed to an arbitrary victim shop domain of the attacker's choosing, causing the host application to take shop-scoped actions (revoking sessions, deleting data, marking a tenant as uninstalled, etc.) against a tenant the attacker does not control. This falls squarely under cross-tenant access.

### Likelihood Explanation
Any merchant who installs the app can capture a legitimately-signed webhook sent to their own endpoint (trivial, no special access needed) and replay it against the app's public webhook URL with a modified `shop-domain` header. No access token, `client_secret`, or privileged access is required — only a normal, valid installation of the target app.

### Recommendation
Bind the identity fields to the signature rather than trusting unauthenticated headers. Options:
- Have `Webhooks::Request#to_signable_string` include `shop`, `topic`, and `webhook_id` in the signed material (this requires a corresponding change server-side/Shopify support, so more practically:)
- Document and/or enforce that host applications must cross-check `request.shop` against their own store of shops that have actually installed the app (a known, previously-onboarded tenant) before trusting `WebhookMetadata#shop`, rather than presenting `shop` as an already-authenticated value once `HmacValidator.validate` succeeds.
- At minimum, update `Registry.process`/documentation so it's explicit that only the request body is authenticated by the HMAC, not the shop/topic/webhook-id headers, so host apps do not conflate "HMAC valid" with "shop identity trustworthy."

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and receives a real webhook (e.g. `app/uninstalled` with body `{}`), signed by Shopify using the app's shared `api_secret_key`:
```
POST /callback/webhooks
x-shopify-topic: app/uninstalled
x-shopify-hmac-sha256: <valid-signature-of-{}>
x-shopify-shop-domain: attacker-shop.myshopify.com
Body: {}
```
2. Attacker replays the identical body and HMAC header to the app's public webhook endpoint, only changing the shop header:
```
POST /callback/webhooks
x-shopify-topic: app/uninstalled
x-shopify-hmac-sha256: <same valid-signature-of-{}>
x-shopify-shop-domain: victim-shop.myshopify.com
Body: {}
```
3. `HmacValidator.validate` recomputes the HMAC over `{}` and it matches, so `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [6](#0-5) , causing the app to process an uninstall (or other topic) event for a shop that never sent it.
