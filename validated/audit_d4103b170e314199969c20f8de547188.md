### Title
User-Centric Signup Bypasses Backend Verification of Enrollment Completion, Analogous to Unverified Debt-Clearance Trust - (File: `src/plans/mod.rs`)

### Summary
The reported bug describes `StabilityPool.liquidateBorrower()` trusting `LendingPool.finalizeLiquidation()` to have fully cleared a borrower's debt, without verifying `getUserDebt(borrower) == 0` afterward — creating a state mismatch ("zombie debt") between the collateral transfer and the debt bookkeeping. The analogous pattern in `orb-core` exists in the signup finalization flow: when a signup is marked `user_centric_signup`, the orb skips the backend-verified enrollment step (`enroll_user::Plan::run`) entirely and instead locally asserts success based solely on its own `signup_reason`, without ever confirming with the backend that the identity/uniqueness enrollment actually completed.

### Finding Description
In `MasterPlan::do_signup`, the orb branches based on `user_centric_signup` (a flag that originates from backend/app-provided `UserData`, see `src/backend/user_status.rs`): [1](#0-0) 

When `user_centric_signup` is true, the code sets `success` purely from the locally computed `signup_reason` (`SignupReason::Normal` vs others), and skips calling `self.enroll_user(...)` altogether — the branch that would call `enroll_user::Plan::run`.

In contrast, the standard (non-user-centric) path calls `enroll_user::Plan::run`, which posts the signup to the backend via `signup_post::request` and then polls `signup_poll::request` in a loop, only returning `Status::Success` when the backend explicitly reports `signup_poll::Status::Completed` with `success: true`. This poll loop's comments show it is specifically responsible for catching backend duplicate detection and fraud, i.e., the real, authoritative verification of enrollment completion: [2](#0-1) 

For the `user_centric_signup` branch, none of this backend confirmation is performed — the local `enrollment_status` is set to `Success` merely because the orb's own `signup_reason` was `Normal`, and `signup_reason` itself depends on `detect_fraud`, which in this build has all fraud checks removed and unconditionally returns `false`: [3](#0-2) 

This mirrors the reported bug class precisely: one component (`do_signup`) trusts that another component/process (a backend/app-side uniqueness or fraud check implied by `user_centric_signup`) has already completed the critical verification step, but never checks or waits for confirmation before marking the operation ("signup") as finalized. The PCP (biometric credential package) is still built and uploaded to the backend in this branch (independent of `user_centric_signup`), but the orb's local record of "signup successful" is asserted without any confirmation that the backend actually validated/bound that credential.

### Impact Explanation
Because `result.success` and `debug_report.signup_successful()` are set without backend confirmation, the orb's local record of the signup outcome can diverge from the backend's actual processing outcome — an accounting/state mismatch analogous to "zombie debt": the device believes and reports the signup is fully verified and complete, potentially triggering downstream UX/telemetry (`Self::ui_complete_signup`, `dd_incr!("main.count.signup.result.success.successful_signup")`) and relay notifications (`SignupEnded { success: true, .. }`) for a signup whose uniqueness/fraud verification was never actually confirmed by the orb.

### Likelihood Explanation
This code path is reachable whenever the backend-provided `user_status::UserData.user_centric_signup` flag is `true` and `orb.config.ignore_user_centric_signups` is not set, which is a standard, backend-controlled configuration path rather than a privileged/operator-only condition — it does not require any hardware tampering or node/operator compromise.

### Recommendation
For the `user_centric_signup` branch, do not assert local success solely from `signup_reason`. Instead, require an explicit backend confirmation (equivalent to the `signup_poll` success/duplicate check performed in the standard path) before setting `enrollment_status` to `Success`, ensuring the orb's reported signup outcome always reflects a backend-verified completion rather than a locally-assumed one.

### Proof of Concept
1. Backend/app returns `UserData { user_centric_signup: true, .. }` for a QR-scanned user (`src/backend/user_status.rs`).
2. Orb completes biometric capture/pipeline; since `detect_fraud` always returns `false` in this build, `signup_reason == SignupReason::Normal`.
3. In `do_signup` (`src/plans/mod.rs:639-656`), the `user_centric_signup` branch executes: `enrollment_status` is set to `Success` and `success = true` without ever calling `enroll_user` (i.e., without `signup_post`/`signup_poll` backend confirmation).
4. The orb marks the signup as finalized/successful (`debug_report.signup_successful()`, UI success animation, relay `SignupEnded{success:true}`), even though the backend never confirmed enrollment completion or performed the duplicate/uniqueness check that `signup_poll` normally guards.
