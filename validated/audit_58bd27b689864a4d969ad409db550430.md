### Title
Cross-tenant webhook shop-domain spoofing via unauthenticated header not covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop` value used by `Registry.process` to dispatch business logic is read from an HTTP header that is never included in that signature. This breaks the identity binding `shop_verified_by_hmac == shop_used_for_dispatch`, mirroring the report's bug class of "a field acted on but not covered by the HMAC."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` and `#topic` are pulled straight from the `x-shopify-shop-domain` / `x-shopify-topic` headers, with no cryptographic binding to the signed body: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `hmac` against `to_signable_string` (the body): [3](#0-2) 

`Registry.process` verifies the HMAC and then immediately trusts `request.shop` (the header) to build `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because the app's `client_secret`-derived HMAC key is shared across every shop that installs the app, an attacker who controls (or installs the app on) their own shop will legitimately receive real, correctly-signed webhook deliveries `(raw_body, hmac)` from Shopify. Since the signature covers only `raw_body` and never `shop-domain`, that same valid `(raw_body, hmac)` pair remains valid when replayed to the app's single webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. `Utils::HmacValidator.validate` will still return `true` (the body/HMAC pair is unmodified and genuinely signed), and `Registry.process` will hand the handler a `WebhookMetadata` object claiming the event belongs to the victim shop, even though it never actually occurred on that shop and the body content may be attacker-controlled (from the attacker's own store).

### Impact Explanation
This allows cross-tenant confusion: a merchant who has installed the app on their own store (a normal, unprivileged capability) can forge webhook events attributed to another merchant's shop domain. Any host application logic that uses `WebhookMetadata.shop` as the tenant key (e.g., to look up an access token, write records, or trigger `shop/redact`-style compliance actions) can be tricked into acting on/for the wrong tenant. This satisfies the "Critical - cross-tenant access" impact bucket.

### Likelihood Explanation
The attack requires only that the attacker operate their own app installation (something any merchant/developer can trivially obtain) and be able to POST arbitrary headers/body to the app's public webhook endpoint — no privileged credentials, TLS interception, or leaked secrets are needed. The library's own documented usage pattern (`docs/usage/webhooks.md`) instructs developers to trust `data.shop` from `WebhookMetadata` directly, so this is not a case of the host ignoring documented API — it is the documented API surface itself that exposes the unauthenticated `shop` field as trustworthy.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the signable string used for HMAC verification, or otherwise cryptographically bind them to the signed payload, so that `Utils::HmacValidator.validate` fails if any of these values are altered independently of the signed body. At minimum, document prominently that `WebhookMetadata.shop` is not covered by the HMAC and must be cross-checked against a shop the app has an active session/install for before being trusted as a tenant identifier.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers for topic `orders/create`.
2. Shopify sends a legitimately signed webhook: `raw_body = B`, header `X-Shopify-Hmac-Sha256 = H` (computed with the app's `client_secret`), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker replays the exact same `raw_body = B` and `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` → validation passes. [5](#0-4) 
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, causing the app to process attacker-controlled data as if it originated from the victim's store.
