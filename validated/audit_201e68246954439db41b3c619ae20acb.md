### Title
Unauthenticated, Caller-Supplied `user_id` in Legacy QR-Code Flow Allows Misattributed Signup - (File: `src/backend/user_status.rs`, `src/plans/qr_scan/user.rs`)

### Summary
Analogous to the `getPrivyUserId()` IDOR, orb-core's user QR-code handling trusts a caller-supplied identifier (`user_id`) as the binding target for a signup/enrollment without requiring any cryptographic proof of possession, whenever the backend responds in the "old QR-code format" branch (no `backend_keys`/`authenticated_app_data`). In that branch the returned `UserData` is built purely from the QR-code-provided `user_id`/session response with no `user_data_hash` verification step at all.

### Finding Description
The v2 QR-code format is parsed as plain text and produces a `Data` struct with `user_data_hash: None`: [1](#0-0) 

This `user_id` (attacker/operator supplied, simply typed or copied as `userid:<uuid>:1`) is sent directly to the backend endpoint keyed only by that string, authenticated with the Orb's own device credentials (not any per-user secret): [2](#0-1) 

Crucially, when the backend does **not** return `backend_keys`/`authenticated_app_data` (the "old QR-code format" path), the code accepts the response and constructs a `UserData` using nothing but the caller-supplied `user_id`/session validity — there is no `user_data.verify(user_data_hash)` check at all in this branch: [3](#0-2) 

By contrast, the "new" branch does enforce a hash-based binding, but only when `qr_code.user_data_hash` is present: [4](#0-3) 

The resulting `user_id` is then used, unverified, as the identity under which the entire signup proceeds: it's embedded in the personal-custody package info JSON, used as the S3/data-uploader `user_id` for biometric package uploads, and sent to the enrollment backend as the signature/session context: [5](#0-4) [6](#0-5) 

This mirrors the reported bug class exactly: a caller-controlled identifier is used to bind a privileged operation (here, biometric enrollment/signup) to an identity, without that identifier being proven to belong to the actor performing the operation (there is no possession/secret check — just a plaintext, guessable/typeable UUID string) for accounts routed through the legacy/no-hash branch.

### Impact Explanation
If an attacker obtains or guesses a victim's `user_id` (a UUID transmitted in plaintext QR form and not treated as a secret in this code path), they can present it (e.g., handwritten/typed QR, or a copied QR that reached this legacy branch) at any Orb. The device will treat the attacker's own biometrics as belonging to the victim's `user_id`, since the only server-side control that binds `user_id` to a session (the `user_data_hash` cryptographic check) is skipped entirely in the "old QR-code format" branch. The practical outcome is a misattributed/cross-user signup: the attacker's iris code and identity_commitment (none in this path, but the enrollment/session is still tied to victim's `user_id`) are recorded and enrolled server-side under someone else's account/session — a direct identity-binding bypass with the same root cause pattern as the reported vulnerability (trusting a caller-supplied identity value instead of enforcing it at a verified session/possession layer).

### Likelihood Explanation
This requires the specific server-side condition where the backend does not populate `backend_keys`/`authenticated_app_data` for a given `user_id`/session (the legacy path), and it also requires physical presence of the attacker at an Orb device (in-person biometric capture), which reduces remote scalability but does not eliminate the identity-binding flaw itself — the code-level root cause (accepting an unverified, caller-typed `user_id` as binding identity) is unconditional in that branch.

### Recommendation
Remove or gate the "old QR-code format" fallback so that `user_id` is never trusted as a signup/session-binding identity without an accompanying `user_data_hash` (or equivalent server-issued, unguessable, possession-bound token) verified via `UserData::verify`. If the legacy branch must remain for compatibility, add a session-nonce or short-lived signed token issued by the backend specifically for that scan event, and validate it in `src/backend/user_status.rs::request` before returning `Some(UserData { .. })`.

### Proof of Concept
1. Obtain or construct a QR code string in the format `userid:<victim-uuid>:1` (parsed by `Data::from_v2`, no hash attached). [1](#0-0) 
2. Present this QR to an Orb as the "user QR-code" during a signup flow whose backend account is provisioned without `backend_keys`/`authenticated_app_data` (legacy path).
3. `backend::user_status::request` returns `Some(UserData)` built solely from the caller-provided `user_id`, with no `user_data_hash` verification performed: [3](#0-2) 
4. The Orb proceeds with `do_signup`, capturing the attacker's biometrics and uploading/enrolling them tagged with the victim's `user_id`: [5](#0-4)

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
