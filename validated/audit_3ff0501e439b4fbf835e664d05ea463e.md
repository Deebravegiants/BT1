### Title
Webhook Shop-Domain Spoofing via HMAC Not Binding `shop` Header — Cross-Tenant Webhook Forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates incoming webhooks solely via an HMAC computed over the raw request body, while the `shop` (and `topic`/`webhook_id`) values that drive tenant-specific handler logic are taken from unauthenticated HTTP headers. Because the app's `client_secret`/`api_secret_key` is shared across *all* shops that install the app, any merchant who has legitimately installed the app can capture a validly-signed webhook delivered to their own store and replay it with a forged `X-Shopify-Shop-Domain` header pointing at a victim shop, causing the handler to execute as if the event originated from that other tenant.

### Finding Description
`Webhooks::Registry.process` validates a webhook using: [1](#0-0) 

The HMAC check delegates to `Utils::HmacValidator.validate`, which computes the signature purely from `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw HTTP body — it does **not** include `shop`, `topic`, or `webhook_id`: [3](#0-2) 

Yet `shop` (parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header) is passed directly into the dispatched `WebhookMetadata` used by the app's business logic: [4](#0-3) 

The binding that should hold is: `HMAC-verified content == content acted upon (including shop)`. Here that equality is broken — the HMAC only proves "this body/`client_secret` combination is authentic for *some* shop of this app," but the `shop` field trusted for tenant routing is never part of that proof, breaking `hmac_verified_shop == request.shop`.

Because the `api_secret_key` is shared by every store that installs the app (it's not per-shop), any attacker who is themselves a legitimate merchant installing the app can obtain valid `(raw_body, hmac)` pairs for webhooks Shopify sends to their own store, then POST that exact body/HMAC pair directly to the app's public webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `Registry.process` will accept it as authentic and invoke the handler believing the event is for the victim tenant.

### Impact Explanation
This is a cross-tenant confusion vulnerability reachable by any unprivileged internet user who can install the target app on a shop they control (a normal, low-barrier action for any Shopify app). Depending on what the host application's webhook handler does with `data.shop` (e.g., GDPR compliance actions like `customers/redact`/`shop/redact`, inventory/order mutations, cache invalidation, billing state changes keyed by shop), the attacker can trigger tenant-scoped side effects attributed to a shop they do not control, i.e., cross-tenant access/action — a Critical-severity impact per the stated criteria.

### Likelihood Explanation
Moderate-to-high: the attacker only needs (1) their own instance of the app installed (self-service, no special privilege) to capture one legitimately-signed webhook of the desired topic, and (2) knowledge of the victim's `myshopify.com` domain (public information). No secrets, tokens, or privileged access are required — this is purely an unprivileged internet actor exploiting the identity-binding gap.

### Recommendation
Bind the trusted `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-supplied shop to the signed payload before it is handed to handlers — for example, verify the shop against a store-specific secret/session record rather than trusting the unauthenticated header, or reject processing unless the shop domain is independently corroborated against the app's known/installed-shop list before dispatch. At minimum, document prominently that `WebhookMetadata#shop` is NOT cryptographically authenticated and must not be used as a sole tenant-authorization signal by consuming applications.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and subscribes it to a webhook topic (e.g., `customers/redact`).
2. Shopify delivers a webhook to the app's endpoint with a valid `X-Shopify-Hmac-Sha256` computed over the raw body using the app's shared `client_secret`. Attacker captures `raw_body` and the `hmac` header.
3. Attacker sends a new HTTP POST to the same webhook endpoint with the identical `raw_body` and `hmac` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `hmac(raw_body)`. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) then calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to act as though the event pertains to the victim's tenant.
