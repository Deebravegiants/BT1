This confirms the finding. The docs explicitly document `data.shop` as "The shop domain of the webhook" — a trusted identity field the host app is meant to use for tenant routing (e.g., `perform_later(shop_domain: data.shop, ...)` in the doc's own example), yet this value comes straight from an HTTP header that the HMAC never covers.

### Title
Webhook `shop`/`topic`/`webhook_id` metadata is trusted but not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while `shop`, `topic`, and `webhook_id` are read directly from attacker-controllable HTTP headers and are never included in the HMAC-verified data. `ShopifyAPI::Webhooks::Registry.process` trusts these header-derived values to route to a handler and to populate `WebhookMetadata`, which the gem's own documentation tells developers to use as the tenant identifier for downstream processing.

### Finding Description
`HmacValidator.validate` calls `verifiable_query.to_signable_string` and compares its HMAC against the `hmac` header [1](#0-0) . For webhooks, `to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, and `webhook_id` are read from headers that are excluded from the signed content [3](#0-2) .

`Registry.process` validates only the HMAC and then uses these unsigned header values both to select the handler (`@registry[request.topic]`) and to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) .

Because the same `api_secret_key` is used to sign webhooks for every shop that installs the app, an attacker who legitimately installs the app on their own shop can trigger a webhook, capture the genuinely-signed `(body, hmac)` pair, and replay it to the app's public webhook endpoint with the `shop-domain` (and optionally `topic`/`webhook-id`) header rewritten to name a victim shop. The HMAC still validates (it only checks `body` against the secret), but `request.shop` now returns the attacker-chosen victim domain. The docs instruct apps to key downstream work off exactly that value: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [5](#0-4) .

This breaks the identity binding: `shop` acted upon by the host application ≠ `shop` actually covered/authenticated by the HMAC.

### Impact Explanation
If the host application uses `data.shop` to look up the shop's stored session/access token, associate the webhook payload with the tenant's data, or otherwise gate processing per-tenant (exactly as the gem's documentation recommends), an attacker can make the application process attacker-controlled webhook content under an arbitrary victim shop's identity. Depending on the handler, this can lead to cross-tenant data corruption/injection (writing attacker data into a victim's records) — a cross-tenant access impact.

### Likelihood Explanation
Exploitation only requires the attacker to be able to install the app on a shop they control (e.g., a free development store) to obtain one genuinely-signed `(body, hmac)` pair for a topic of their choosing, and to send an HTTP POST with a forged `shop-domain` header to the app's public webhook endpoint. No knowledge of `api_secret_key` or any victim credential is required.

### Recommendation
Bind the shop identity to the signed content: verify `shop` against the shop stored when the webhook was registered/installed (not merely the header), or include `shop`, `topic`, and `webhook_id` in the HMAC-signed payload/signable string so header tampering invalidates the signature. At minimum, document that `data.shop`/`data.topic` must not be trusted for tenant identification without independent verification against the app's own installation records.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and registers for topic `orders/create`.
2. Attacker triggers an order creation, causing Shopify to POST a genuinely HMAC-signed webhook to the app: body `B`, header `x-shopify-hmac-sha256: H` (valid for `B` under the app's real `api_secret_key`), `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the exact same `B` and `H` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` succeeds because it only checks `B` against `H` [2](#0-1) ; `Registry.process` invokes the handler with `shop: "victim.myshopify.com"` [6](#0-5) , and the app processes attacker-controlled body `B` as if it originated from the victim shop.
