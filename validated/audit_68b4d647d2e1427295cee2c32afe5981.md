Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the raw request body against the HMAC signature, then trusts the unsigned `shop-domain` header to determine which tenant the webhook belongs to. Because the shop identity is never bound to the HMAC, an attacker who possesses one genuine (body, HMAC) pair signed with the app's shared `client_secret` can replay it with an arbitrary `shop-domain` header value and have the app process the webhook as if it originated from a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor reads the `shopify-shop-domain`/`x-shopify-shop-domain` header directly, completely independent from the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (the body) and compares it to the `hmac` header value: [3](#0-2) 

`Registry.process` calls this validator, then immediately uses the unverified `request.shop` value to build the `WebhookMetadata` passed to the app's handler, which is what host applications use to scope database writes/updates to a tenant: [4](#0-3) 

The identity binding broken is: `HMAC(client_secret, body) == received_hmac` proves only that `body` was signed by the holder of `client_secret`; it does **not** prove `shop-domain header == shop that generated body`. Since a single app's `client_secret` is shared across every shop that installs the app, any attacker who installs the app on their own store legitimately receives a genuinely-signed `(body, hmac)` pair for a chosen topic (e.g. `customers/data_request`, `app/uninstalled`, `orders/create`). The HMAC does not bind that pair to the attacker's own shop domain, so the attacker can resend the identical body/HMAC to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (it never inspects the header), and the handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker_controlled_body, ...)`.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an unprivileged attacker (any user able to install the app on their own store, which requires no special privilege) can inject/forge webhook events that the host application attributes to any other merchant using the app. Depending on the handler logic built on top of this gem (order processing, GDPR data-request/redact handlers, uninstall cleanup, subscription/billing state changes, etc.), this can result in data corruption, state changes, or privileged actions being executed against a tenant the attacker does not control — satisfying the "cross-tenant access" criterion for a Critical-impact finding.

### Likelihood Explanation
Likelihood is high for any app built with this gem's webhook module, because:
- No credentials beyond the ability to install the app on any store (a normal, unprivileged action) are required.
- The attacker fully controls the reused body content (by choosing which webhook their own store generates before capturing it), and only needs to swap one HTTP header on replay.
- `Registry.process` is the sole authentication gate and it never checks that the header-derived shop matches anything in the signed payload.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values into the signable string / HMAC computation before validating, or otherwise cryptographically bind the shop identity to the webhook payload (e.g., re-derive/verify shop identity independently, such as looking up the shop's per-tenant secret if using per-shop secrets, or including the header values in the canonical string that is HMAC'd). At minimum, document to consuming apps that `request.shop` is unauthenticated and must not be trusted for tenant scoping without additional verification (e.g., cross-checking against a known/installed shop list before persisting webhook data).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a legitimate, unprivileged action).
2. Shopify delivers a genuine webhook to the attacker's registered endpoint (attacker controls the endpoint, e.g. `app/uninstalled` or `orders/create`) with headers `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, body `B`. Because `HmacValidator` and `Request#to_signable_string` only sign `B`, `H = HMAC_SHA256(client_secret, B)` is independent of the shop domain.
3. Attacker resends an HTTP POST to the app's real webhook endpoint with the identical body `B` and HMAC header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(client_secret, B)` and finds it equal to `H` — validation passes. [5](#0-4) 
5. `request.shop` returns `"victim-shop.myshopify.com"` from the forged header, and the handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to act on victim-shop data/state using attacker-controlled content. [6](#0-5)
