### Title
Swap fees (`hinkalFee`/`relayFee`) permanently stranded in `ExternalActionSwap`/`LifiExternalAction` when `circomData.relay == address(0)` - (`contracts/external-actions/swaps/ExternalActionSwap.sol`)

### Summary
`ExternalActionSwap.swap()` unconditionally computes `hinkalFee` and `relayFee` and subtracts their sum (`totalFee`) from `swappedAmount` before crediting the caller's UTXO, but the transfer of that fee via `sendToRelay` is a silent no-op whenever `circomData.relay == address(0)`. Since `relay == address(0)` is an explicitly valid, unprivileged self-relay path (enforced/allowed by `performHinkalChecks`), any user can trigger this and cause `totalFee` worth of `outputToken` to be permanently stuck inside the external-action contract's balance, credited to nobody.

### Finding Description
Equality that should hold: value leaving `ExternalActionSwap`/`LifiExternalAction` for a given `transact()` call == the sum of (fees actually paid out + UTXO amount credited to the caller). This breaks when `circomData.relay == address(0)`.

Code path:
- `performHinkalChecks` in `contracts/HinkalHelper.sol` explicitly permits `circomData.relay == address(0)` for an unprivileged, self-relaying `originalSender == sender` transaction — this is not a privileged or malformed state.
- `Hinkal._externalTransact` forwards to `IExternalActionV2.runAction` → `ExternalActionSwap.swap` (`contracts/external-actions/swaps/ExternalActionSwap.sol:40-102`).
- In `swap()`, `relayFee = circomData.feeStructure.flatFee` and `hinkalFee = hinkalHelper.calculateRelayFee(...)` are computed unconditionally (lines 70-76), independent of `circomData.relay`. [1](#0-0) 
- Fee payout is attempted via `sendToRelay(circomData.relay, ..., ...)` (lines 78-87), but `Transferer.sendToRelay` only performs the transfer `if (relay != address(0) && actualAmount > 0)`. [2](#0-1) 
- Regardless of whether the transfer happened, `totalFee` is subtracted from `swappedAmount` to compute `amountToSendToHinkal`, which is the only amount actually transferred to `msg.sender` (Hinkal.sol) and the only amount minted as the resulting UTXO.
- Result: when `relay == address(0)`, `totalFee` worth of `outputToken` remains in the external-action contract's own balance — it is neither paid to a relay, nor to any protocol treasury, nor credited to the user's UTXO.
- `Hinkal.transact`'s balance-diff invariant (`contracts/Hinkal.sol:134-146`) only checks Hinkal.sol's own balance against `amountChanges + utxoAmount`; since `amountToSendToHinkal` (post-fee-deduction) is exactly what reaches Hinkal.sol and becomes the UTXO amount, this invariant is satisfied and does not detect the stranding inside the action contract.
- No rescue/sweep function exists in `ExternalActionSwap`, `LifiExternalAction`, or elsewhere in the codebase to recover this stuck balance.

I could not substantiate the question's secondary claim that a later, unrelated caller can "harvest" this stranded balance through `callRouter`'s balance measurement: `LifiExternalAction.callRouter` computes `swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore` — a pure delta over the router call — so pre-existing stranded balance sitting in the contract before/after that delta window is not captured by a later user's `swappedAmount`, unless the router itself sweeps the contract's full balance, which is LI.FI-router-internal behavior explicitly out of scope for this audit ("LI.FI router defects with no exploit path through this repo's code"). I reject that specific "theft by third party" mechanism as unverified from repo code alone.

### Impact Explanation
Every self-relayed swap (`circomData.relay == address(0)`) permanently strands `hinkalFee` (+ `relayFee` if `outputToken == feeToken`) worth of `outputToken` inside the `ExternalActionSwap`/`LifiExternalAction` contract balance. This is unrecoverable by anyone — not the user (whose UTXO already excludes it), not a relay (never paid), not the protocol (no sweep mechanism found). This matches the "High - theft or permanent freezing of protocol/relay fees" category. It is repeatable by any unprivileged user on every self-relayed swap they perform, growing the stranded balance over time.

### Likelihood Explanation
No special privileges are required: `relay == address(0)` combined with `originalSender == sender` is an explicitly supported, checked-valid code path in `performHinkalChecks`, meaning any ordinary self-relaying user (or an attacker deliberately choosing to self-relay) triggers this every time they use the swap external action without a relay. The `feeStructure.flatFee`/`variableRate` are also attacker-supplied fields of `CircomData`, constrained only by `variableRate <= 10000`, so `hinkalFee` can be made non-trivial. This requires no contract deployment tricks, only calling `Hinkal.transact()` with a valid self-generated proof for the swap external action.

### Recommendation
In `ExternalActionSwap.swap()`, gate fee computation/deduction on whether a relay/fee recipient actually exists: if `circomData.relay == address(0)`, either (a) do not deduct `totalFee` from `amountToSendToHinkal` (credit the full `swappedAmount` to the user's UTXO), or (b) route the un-relayed portion of the fee to a fixed protocol treasury address instead of `circomData.relay`, ensuring `sendToRelay`'s no-op case can never silently consume value that is deducted elsewhere. Add an invariant test/assert that `totalFee` transferred out + `amountToSendToHinkal` == `swappedAmount` for every code path.

### Proof of Concept
Hardhat fork test plan:
1. Deploy `LifiExternalAction` (or a mock `ExternalActionSwap` subclass) wired to a mock router that performs a fixed-rate swap.
2. Craft `CircomData` for a `transact()` call with `originalSender == msg.sender`, `circomData.relay == address(0)`, `feeStructure.variableRate` and/or `flatFee` set to a non-zero value, `erc20TokenAddresses = [inputToken, outputToken]`.
3. Generate a valid proof locally for this data (using the existing snark artifacts / circuit test harness in the repo).
4. Call `Hinkal.transact(...)`.
5. Assert:
   - `outputToken.balanceOf(externalActionContract)` increases by exactly `totalFee` (hinkalFee + relayFee if same token) after the transaction (funds stuck, not zero).
   - The UTXO amount encoded/emitted (`amountToSendToHinkal`) equals `swappedAmount - totalFee`, i.e., strictly less than `swappedAmount`, with no corresponding transfer of the difference to any address.
   - No relay balance change occurred (`circomData.relay == address(0)` so no external recipient received `totalFee`).
6. Repeat the self-relayed swap multiple times and show the stranded balance in the external-action contract accumulates monotonically with no way to recover it (no owner-only sweep function exists to test against).
