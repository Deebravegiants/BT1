### Title
Webhook `shop` domain is trusted for tenant routing but not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed payload [2](#0-1) . `Registry.process` accepts any request whose HMAC matches the body under the app's shared `api_secret_key`, then forwards the (unverified) header-derived shop straight into `WebhookMetadata` passed to the app's handler [3](#0-2) .

### Finding Description
The identity binding that should hold is: `shop used by the app handler == shop cryptographically bound to the signed bytes`. In this implementation that equality does not hold — `HmacValidator.validate` only proves "the body bytes were signed by someone possessing `api_secret_key`" [4](#0-3) ; it says nothing about which shop the header claims to be from. `WebhookMetadata` is built from `request.shop` (header-derived) after only the body-HMAC check passes [5](#0-4) .

Because `api_secret_key` is a single shared app-level secret used for every installed shop, any merchant who has legitimately installed the app receives genuine webhook deliveries with a valid HMAC for their own store's payload. That merchant can capture one such `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value (e.g., a victim shop's domain). `Utils::HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"` with attacker-controlled `body` [3](#0-2) . Any app that uses `data.shop` to select which tenant's data/record to update — as the documented usage pattern explicitly encourages (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [6](#0-5)  — will process attacker-supplied data under the victim's tenant identity.

### Impact Explanation
This breaks the shop/tenant boundary that webhook processing is supposed to preserve: an unprivileged app installer (no access to `api_secret_key`, no privileged account, no token) can inject arbitrary attacker-chosen webhook body content attributed to any other shop using the same app, because the shop-domain header used for tenant attribution is outside the cryptographically verified data. This is a cross-tenant access primitive as defined by the rubric's Critical severity bucket.

### Likelihood Explanation
Likelihood is high for any app that follows the gem's own documented handler pattern (using `data.shop` for tenant routing/storage, as shown in `docs/usage/webhooks.md`). The only prerequisite is that the attacker be a legitimate installer of the target app on some shop (unprivileged, self-service) — no leaked secrets, no social engineering, and no interaction with the victim required.

### Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically tie the header-derived `shop` to the verified body. Concretely, `Utils::HmacValidator` (or `Webhooks::Request#to_signable_string`) should incorporate `shop`, `topic`, and `webhook_id` into the value being HMAC-verified (mirroring how `Auth::Oauth::AuthQuery#to_signable_string` includes all trust-relevant fields, not just a subset) [7](#0-6) , or document/require a per-shop shared secret so a replayed payload cannot be revalidated with a different shop header. At minimum, the gem should not present `WebhookMetadata.shop` as a value the handler can trust for tenant identification unless it is bound to the signature.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` (self-service, no special privilege).
2. Shopify delivers a genuine webhook to the app: raw body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, HMAC(secret, B))` from their own delivered webhook (no secret extraction needed).
4. Attacker POSTs the same body `B` and same HMAC header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is built; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` via `to_signable_string` (body-only) and it matches, so validation passes [8](#0-7) .
6. The handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's own webhook body>, ...)` and processes/stores it as if it originated from the victim's store.
