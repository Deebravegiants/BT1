### Title
`ExternalInitiatorsEnabled=false` is not enforced for existing initiators' authenticated job-run triggering - ([File: core/web/router.go])

### Summary
The `JobPipeline.ExternalInitiatorsEnabled` config flag is intended to disable the External Initiator feature. It is only checked in `ExternalInitiatorsController.Create`, but `AuthenticateExternalInitiator` (used to authenticate requests to `POST /v2/jobs/:ID/runs`) never checks this flag, so previously-created external initiators can still authenticate and trigger job runs after the operator disables the feature.

### Finding Description
`ExternalInitiatorsController.Create` explicitly blocks creating new external initiators when the feature is disabled: [1](#0-0) 

However, the authentication path that lets an external initiator act as a `run`-role user and trigger job runs — `AuthenticateExternalInitiator` — has no such check: [2](#0-1) 

This middleware is wired into the route group for `POST /v2/jobs/:ID/runs` in `router.go`, alongside `AuthenticateByToken`/`AuthenticateBySession`, with no gating on `ExternalInitiatorsEnabled`: [3](#0-2) 

Because `ExternalInitiator` records persist in the `external_initiators` table (created before the flag was disabled), `FindExternalInitiator` will still find them and `bridges.AuthenticateExternalInitiator` will still validate their access-key/secret pair regardless of the current config value: [4](#0-3) [5](#0-4) 

This is the same bug class as the `ResolvStaking.withdraw()` issue: a feature-disable flag (`claimEnabled` / `ExternalInitiatorsEnabled`) is enforced on one code path (`claim()` / `Create`) but bypassed via a second reachable path (`withdraw()` / authenticated run-triggering) that achieves the equivalent privileged action.

### Impact Explanation
An operator disabling `ExternalInitiatorsEnabled` expects the External Initiator feature to be fully turned off (e.g., for security/compliance reasons, or to revoke this class of remote-run-triggering credentials). Instead, any external initiator credential created before the flag flip remains fully functional to authenticate as `UserRoleRun` and trigger arbitrary job runs via `POST /v2/jobs/:ID/runs`. This undermines the operator's intended access control and could allow continued unauthorized job execution after the feature was believed disabled.

### Likelihood Explanation
Medium: it requires the possession of a previously-issued (or still-listable, since `GET /v2/external_initiators` has no disabled check either) external initiator access key/secret, and requires the operator to have disabled the feature expecting it to take effect immediately. In deployments where operators use `ExternalInitiatorsEnabled=false` as a runtime kill switch for a compromised or deprecated integration, this bypass directly defeats that mitigation.

### Recommendation
Add an explicit check of `app.GetConfig().JobPipeline().ExternalInitiatorsEnabled()` inside `AuthenticateExternalInitiator` in `core/web/auth/auth.go` (or in the `userOrEI` route group setup in `core/web/router.go`), returning `auth.ErrorAuthFailed`/401 when the feature is disabled, so that disabling the flag revokes all external-initiator-based authentication, not just creation of new ones.

### Proof of Concept
1. Create an external initiator while `JobPipeline.ExternalInitiatorsEnabled = true` (via `POST /v2/external_initiators`), obtaining `AccessKey`/`Secret`.
2. Operator disables the feature by setting `JobPipeline.ExternalInitiatorsEnabled = false` and restarts/reconfigures the node.
3. Using the previously obtained `AccessKey`/`Secret` in the `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers, call `POST /v2/jobs/:ID/runs`.
4. Request succeeds and triggers a job run — as demonstrated by the existing test pattern in `core/web/router_test.go` (`TestTokenAuthRequired_TokenCredentials`), which shows the same header-based flow succeeding with no dependency on `ExternalInitiatorsEnabled`: [6](#0-5)

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

func AuthenticateExternalInitiator(eia *auth.Token, ea *ExternalInitiator) (bool, error) {
	hashedSecret, err := auth.HashedSecret(eia, ea.Salt)
	if err != nil {
		return false, err
	}
	return subtle.ConstantTimeCompare([]byte(hashedSecret), []byte(ea.HashedSecret)) == 1, nil
}
