This confirms the finding. The gem's own documentation (`docs/usage/webhooks.md` lines 123-125) states that `Registry.process` "will verify the request did indeed come from Shopify" — implying full authentication of the webhook including its `shop` identity — but the actual verification only covers the raw body bytes, not the `shop-domain` header.

### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop-domain` (and `topic`/`webhook-id`) headers, which are handed to the app's handler as the trusted tenant identifier, are never included in the signed material. Any party capable of producing one valid signed webhook body for a given app (e.g., an attacker who installs the app on their own shop and receives a legitimate webhook) can replay that exact body with a forged `x-shopify-shop-domain` header naming a different, victim shop, and the signature will still validate.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the HMAC exclusively over `to_signable_string`: [2](#0-1) 

`Registry.process` uses this single check as the sole gate before dispatching to the app-provided handler, and forwards `request.shop` (an unauthenticated header) as the trusted tenant identity in `WebhookMetadata`: [3](#0-2) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers without any cryptographic binding to the body they accompany: [4](#0-3) 

The intended equality this mechanism should enforce is: `shop that produced/authorized the signed payload == shop attributed to that payload by the handler`. Because `shop-domain` is outside the signed bytes, this equality is never actually checked — only `raw_body == raw_body` is checked. This is the same class of bug as the reference report: a guard/verification is scoped to a subset of the data (raw body) while a security-relevant field acted upon downstream (`shop`) sits outside that scope, exactly like `registerProposal`'s zero-address check omitting the value that later drives contract state.

The gem's own documentation asserts the opposite guarantee — that `process` "will verify the request did indeed come from Shopify" for that webhook as a whole: [5](#0-4)  and that `data.shop` is "The shop domain of the webhook" to be trusted by handlers [6](#0-5) , so apps built per this gem's documented contract will treat `data.shop` as authenticated.

### Impact Explanation
Since the HMAC secret (`api_secret_key`) is the same for every shop that has installed a given app, a body payload legitimately signed for one merchant is a valid signature for that same body under any `shop-domain` value. An attacker who controls or has installed the app on Shop A can capture a genuine webhook (or trigger one, e.g. by editing a product to fire `products/update`), then replay the identical body to the app's webhook endpoint with the `shop-domain` header rewritten to Shop B. `Utils::HmacValidator.validate` passes because it only checks the body bytes, and `WebhookMetadata.shop` is populated with the attacker-controlled value. If the handler uses `data.shop` to select a tenant's database record, credentials, or shop-scoped session (as recommended in the docs), this results in cross-tenant data injection/confusion — data belonging to shop A being processed/attributed under shop B's identity.

### Likelihood Explanation
The attacker only needs to be a legitimate, currently-authorized installer of the target app on any one shop (a normal unprivileged merchant, not requiring `api_secret_key`, an access token, or any credential leak) to obtain one validly-signed webhook body, then replay it with a modified header value — no cryptographic secret is required to exploit the header/body mismatch itself.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-verified material, or otherwise cryptographically bind the `shop-domain` header to the signed body before trusting it in `WebhookMetadata`, mirroring the fix pattern in the reference report of requiring the acted-upon value to be covered by the same guard that authorizes the action.

### Proof of Concept
1. App installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, sharing the same app `api_secret_key`.
2. Attacker triggers a `products/update` webhook on their own shop and captures the raw POST body and its valid `x-shopify-hmac-sha256` header.
3. Attacker replays the exact same body/HMAC to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` returns `true` because it only checks `raw_body` against the HMAC [7](#0-6) .
5. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [8](#0-7) , and the host app processes attacker-supplied data under the victim shop's identity.
