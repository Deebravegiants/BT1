### Title
Cross-Tenant Session Hijack via Unauthenticated, Predictable Session-ID Cookie - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` returns the raw, unverified value of the `shopify_app_session` cookie as the session identifier for non-embedded (and cookie-fallback embedded) flows. Because offline session IDs are a fully deterministic, public function of the shop domain (`"offline_#{shop}"`, produced by `ShopifyAPI::Auth::Session.from` and mirrored by `SessionUtils.offline_session_id`), and the cookie itself carries no signature or binding to the OAuth exchange that created it, any client can set this cookie to an arbitrary value and have the gem hand that value straight back to the host application as an authenticated session key.

### Finding Description
The intended identity binding is: *session id returned to the host app* == *session id that this gem itself generated and bound to a specific shop during a completed OAuth handshake*. Instead the code implements: *session id returned* == *bytes present in an unauthenticated client cookie*.

- `SessionUtils.current_session_id` falls back to `cookie_session_id(cookies)` whenever no `shopify_id_token` is supplied, for both embedded and non-embedded flows: [1](#0-0) 
- `cookie_session_id` performs zero verification — it just indexes into the cookie hash and returns the value verbatim: [2](#0-1) 
- The `SessionCookie` object that legitimately carries this value after OAuth is a plain `T::Struct` with no HMAC, signature, or encryption of any kind — `name`, `value`, `expires` are just plaintext fields: [3](#0-2) 
- The offline session id format the gem itself produces after a real OAuth exchange is deterministic and derivable from public information (the shop's `myshopify.com` domain), with no random/secret component: [4](#0-3) 
- `Oauth.validate_auth_callback` sets this exact deterministic id as the cookie value at the end of a legitimate OAuth flow, reinforcing that this is the value host applications key their session storage by: [5](#0-4) 

Because the returned session id is used by host applications (per this gem's documented usage) to look up a previously persisted `Session` object — containing the shop's real access token — in their session store, an attacker who knows or guesses a victim shop's domain (public information; every Shopify store has a discoverable `*.myshopify.com` domain) can set `shopify_app_session=offline_victim-shop.myshopify.com` in their own browser and have `current_session_id` hand back that exact string, unmodified and unverified. If the host app's storage contains a session under that key (created by the victim's genuine OAuth completion), the attacker's request is now treated as authenticated for the victim's shop.

### Impact Explanation
This breaks the tenant-isolation boundary entirely without requiring any credential, `api_secret_key`, or access token from the attacker — only knowledge of the target's shop domain, which is public. The consequence is cross-tenant access to a shop's persisted `Session`, including its Admin API access token, satisfying the "Critical – cross-tenant access, theft of a merchant access token" bar. No HMAC, JWT, or secret-key knowledge is needed to construct the malicious identifier — it is purely a naming-scheme collision exploited via an unauthenticated cookie value.

### Likelihood Explanation
High for any deployment that follows the documented, non-embedded (or cookie-fallback) usage pattern described in the gem's own guidance — passing raw `cookies` straight into `current_session_id` and trusting the returned string as a session-store key. The only prerequisite is that the host app's session storage is keyed exactly by the string this gem returns, which is the intended and documented contract of `SessionUtils`. The predictable `"offline_#{shop}"` / `"#{shop}_#{user_id}"` formats make guessing/targeting trivial once a shop domain is known.

### Recommendation
Never trust `cookies[SESSION_COOKIE_NAME]` as an authenticated identity by itself. Either:
1. Bind the session cookie to a value that is cryptographically signed/HMAC'd by the app (e.g., sign the session id with `Context.api_secret_key` and verify the signature in `cookie_session_id` before returning it), so the id cannot be forged without the secret, or
2. Require that the returned session id always be cross-checked against a server-side, cookie-independent proof of shop identity (e.g., always require and validate the JWT/id_token path rather than falling back to a bare cookie value) before it is used to key into session storage.

### Proof of Concept
1. Attacker identifies the victim's Shopify store domain, e.g. `victim-shop.myshopify.com` (publicly visible on the storefront).
2. Attacker sends a request to the host application (which uses this gem per its documented pattern) with the cookie:
   `shopify_app_session=offline_victim-shop.myshopify.com`
3. The host app calls:
   `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`
   which, per [1](#0-0)  and [2](#0-1) , returns `"offline_victim-shop.myshopify.com"` verbatim — with no verification that this browser ever completed OAuth for that shop.
4. The host application looks up its session store using this id, retrieves the `Session` object previously created for the victim shop by a real OAuth completion (id format matches [4](#0-3) ), and serves the attacker's request as if it were the victim shop, exposing the victim's Admin API access token/data.

      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
      end
