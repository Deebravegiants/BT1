### Title
Webhook `shop` (and topic/webhook_id) identity is not bound by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` (and `topic`/`webhook_id`) values that the handler subsequently trusts are read from unauthenticated HTTP headers that are never included in the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are parsed straight out of headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which — per `HmacValidator#validate_signature` — computes the HMAC over `verifiable_query.to_signable_string` (i.e. the body only) and compares it against the `hmac` header: [3](#0-2) 

Once that body-only signature check passes, `Registry.process` immediately builds `WebhookMetadata` from the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` and forwards it to the app's handler as trusted tenant/event identity: [4](#0-3) 

The webhook HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that has installed the app — it is not shop-specific. Consequently, any merchant who installs the app on their own store legitimately receives webhook deliveries with a valid `(body, hmac)` pair signed with that same shared secret. Because the `shop-domain`, `topic`, and `webhook-id` headers are never part of the signed material, an attacker (an installed/unprivileged merchant) can replay their own genuinely-signed webhook body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` (the body's signature is untouched), and `Registry.process` will dispatch the handler with `WebhookMetadata.shop` claiming to be the victim shop, while the body content is fully attacker-controlled.

This breaks the identity binding: `shop authenticated == shop the app acts upon`. The HMAC only proves "this body byte-string was produced with the app's secret"; it does not prove "this body belongs to this shop."

### Impact Explanation
This is a cross-tenant confusion: an attacker who is merely an installed (unprivileged) user of the app on their own shop can forge webhook events that the app processes as if they originated from a different (victim) shop, feeding attacker-controlled body content into the victim shop's webhook handling logic (e.g., triggering data writes, cache invalidation, order/customer processing, or mandatory-compliance webhook handlers keyed by `shop`). This matches the Critical category "cross-tenant access."

### Likelihood Explanation
Likelihood is high for any app that (a) allows self-installation or trial installation by an attacker-controlled shop, and (b) uses the `shop` value from `WebhookMetadata` to key data or trigger tenant-specific side effects — which is the documented, expected usage pattern of `ShopifyAPI::Webhooks::Registry`/`WebhookHandler`. No secret material needs to be obtained; only a legitimately delivered webhook from the attacker's own installation is required as the source of a valid `(body, hmac)` pair.

### Recommendation
Bind the identity fields into the signed material, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the verified body before trusting them — e.g., include the shop domain and topic in `to_signable_string`, or require the app layer to cross-check `request.shop` against a known/authenticated shop before invoking handlers. At minimum, document prominently that `request.shop`/`topic`/`webhook_id` are NOT covered by HMAC verification and must not be trusted as tenant identifiers without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, granting the app access under the shared `client_secret`.
2. Shopify delivers a genuine webhook to the app with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body B>`, body `B` (attacker can also just directly craft `B` and self-compute the HMAC if their shop ever received one for the same body, or use a shop where they have a legitimate valid signature for a controlled body).
3. Attacker replays the same body `B` and `hmac` header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)` — which passes because it only checks the body against the secret — and then calls `handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...))`, causing the app to act on attacker-controlled data as if it belonged to `victim-shop.myshopify.com`.
