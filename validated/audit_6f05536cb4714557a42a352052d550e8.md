## Finding

### Title
`Processor::calc_take_pnl` invariant check can permanently freeze Deposit/Withdraw/WithdrawPnl for a pool - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` enforces a hard invariant — the pool's current reserve product must be `>=` the last recorded PnL-tracking product (`calc_pnl_x * calc_pnl_y`) — before it will proceed. If this comparison ever fails, the function unconditionally returns `AmmError::CalcPnlError`, and every unprivileged instruction that calls it (`Deposit`, `Withdraw`, `WithdrawPnl`) reverts, with no on-chain recovery path other than an admin manually switching the pool to `AmmStatus::WithdrawOnly`.

### Finding Description
`calc_take_pnl` computes the PnL to skim by comparing the current invariant (`pool_pc_amount * pool_coin_amount`) against the previously stored invariant (`calc_pc_amount * calc_coin_amount`, derived from `target.calc_pnl_x`/`calc_pnl_y`): [1](#0-0) 

If the current product is smaller than the stored one, the function does not attempt any graceful degradation — it logs and returns `AmmError::CalcPnlError`: [2](#0-1) 

This function is called unconditionally (no fallback) from the reachable, unprivileged instruction handlers:

- `process_deposit` (Deposit): [3](#0-2) 
- `process_withdraw` (Withdraw, whenever status != `WithdrawOnly`): [4](#0-3) 
- `process_withdrawpnl` (WithdrawPnl, admin-only but still blocks reward/pnl accounting for the whole pool): [5](#0-4) 

`target_orders.calc_pnl_x`/`calc_pnl_y` are re-derived after every Deposit/Withdraw/WithdrawPnl call via integer division and `integer_sqrt()` truncation: [6](#0-5) 

Because these updates rely on truncating integer square roots and integer division/multiplication chains (`restore_decimal`, `normalize_decimal_v2`, `calc_x_power`), rounding error accumulates across many Deposit/Withdraw cycles. There is no tolerance or self-correcting mechanism in the `>=` check — any accumulated rounding drift that makes the tracked "last k" transiently exceed the freshly computed current reserve product causes `calc_take_pnl` to hard-fail.

This exactly matches the reported bug class: an ad-hoc invariant/threshold check meant to catch an "unexpected" situation, but which can be tripped by ordinary, legitimate usage and has no recovery path other than a privileged, manual intervention.

### Impact Explanation
Once the invariant is tripped for a given pool:
- `Deposit` reverts unconditionally for that pool (no LP can add liquidity).
- `Withdraw` reverts for every LP unless the pool status equals `AmmStatus::WithdrawOnly` — a state that only an admin (via `SetParams`) can set. Ordinary LPs have no way to withdraw their funds themselves.
- `WithdrawPnl` (protocol PnL sweep) also reverts, freezing the accrued `need_take_pnl_pc`/`need_take_pnl_coin` balances.

This is a freezing-of-funds condition: LP liquidity becomes inaccessible to its owners through the normal, unprivileged instruction set until an out-of-band, privileged admin action changes the AMM status — the same class of impact described in the external report ("blocked until manual intervention").

### Likelihood Explanation
The condition depends on accumulated rounding error across `restore_decimal`/`normalize_decimal_v2`/`integer_sqrt` computations performed on every Deposit/Withdraw. Any sufficiently active pool (many small deposits/withdraws, or pools with disparate coin/pc decimals causing more truncation) can reach the edge condition without any attacker-controlled malicious input — it is a byproduct of normal usage, matching the report's framing that "something unexpected... should be resolved manually," i.e., a systemic, likelihood-increasing-over-time issue rather than a single-shot exploit.

### Recommendation
Replace the hard revert in `calc_take_pnl` with a tolerant/self-healing path: when the current invariant is marginally below the tracked one due to rounding, clamp/reset `target.calc_pnl_x`/`calc_pnl_y` to the current reserves (skipping PnL skim for that call) instead of returning `AmmError::CalcPnlError`. This avoids freezing `Deposit`/`Withdraw`/`WithdrawPnl` while still preserving PnL accounting for legitimate divergences, removing the dependency on a privileged admin to unblock user funds.

### Proof of Concept
Not applicable as a single-transaction PoC — this is a state-drift condition. Conceptually: repeatedly perform Deposit followed by Withdraw of varying amounts (including values chosen to maximize truncation in `Calculator::restore_decimal`/`normalize_decimal_v2`/`integer_sqrt`) on a pool with coin/pc decimal mismatch. Over many cycles, `target_orders.calc_pnl_x * calc_pnl_y` can end up marginally larger than the freshly computed `total_pc_without_take_pnl * total_coin_without_take_pnl`, causing the next `Deposit`/`Withdraw` call to hit the `else` branch in [2](#0-1)  and revert with `AmmError::CalcPnlError`, blocking further deposits/withdrawals for the pool.
