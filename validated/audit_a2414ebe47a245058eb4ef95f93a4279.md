### Title
Webhook shop/topic attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string from the raw request body only, while the `shop`, `topic`, and `webhook_id` fields — which are passed straight into the business-logic handler — come from unsigned HTTP headers. `Registry.process` verifies the HMAC and then hands the handler a `WebhookMetadata` built from these unauthenticated header fields, so the tenant/topic attribution of a verified webhook can be forged independently of the signed payload.

### Finding Description
`Utils::HmacValidator.validate` recomputes the signature over `verifiable_query.to_signable_string` and compares it to the request's `hmac` value using `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body — it does not include `shop`, `topic`, or `webhook_id`: [2](#0-1) 

`Registry.process` validates that HMAC and then immediately trusts `request.shop` / `request.topic` / `request.webhook_id`, none of which are covered by the signature, to construct the metadata passed to the app's handler: [3](#0-2) 

The identity binding that should hold is:
`shop authenticated (used for tenant attribution in the handler) == shop covered by the HMAC signature`

This equality does not hold. Before the attacker's request: a legitimate webhook for shop `A` has a valid `hmac` computed over `raw_body` and headers `shop-domain: A`, `topic: T`. After the attacker's request: the same `raw_body` and `hmac` are replayed to the app's public webhook endpoint with headers changed to `shop-domain: B`, `topic: T'`. `Utils::HmacValidator.validate` still returns `true` because it only checks `raw_body`/`hmac`, and `Registry.process` dispatches the handler with `shop: "B"` — a shop that never actually produced this event — bypassing the intended per-tenant binding.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: an unprivileged internet user who can obtain any one valid `(raw_body, hmac)` pair (e.g., from a webhook payload sent to their own trial/dev shop, or one they can otherwise observe) can replay it to the app's public webhook receiver endpoint while freely rewriting the `shop-domain` and `topic` headers, since those are never part of the signed material. Any app that trusts `WebhookMetadata#shop`/`#topic` for per-tenant processing (data storage keyed by shop, side effects scoped by shop, topic-specific business logic) can be made to process or store data under an arbitrary victim shop, i.e. cross-tenant confusion/access through the app that relies on this gem's webhook verification.

### Likelihood Explanation
The webhook receiver route is necessarily public (Shopify must be able to POST to it from the internet), and no code path in this gem binds `shop`/`topic`/`webhook_id` to the HMAC — the check is structural, not a data/timing issue, so it is reliably reproducible by anyone who can capture one legitimate `(body, hmac)` pair for any topic.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable material used for webhook HMAC verification (or otherwise cryptographically bind these header fields to the verified body), so `Registry.process` cannot be made to attribute a validly-signed body to an arbitrary shop or topic.

### Proof of Concept
1. Register a handler for topic `orders/create` in the target app.
2. Obtain any one legitimate webhook delivery `(raw_body, x-shopify-hmac-sha256)` — e.g., from a shop the attacker controls, or by observing a delivery.
3. POST that same `raw_body` and `hmac` header to the target app's public webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (a shop the attacker does not own) and/or a different `x-shopify-topic`.
4. `Utils::HmacValidator.validate` returns `true` because it only checks the body against the secret: [4](#0-3) 
5. `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"`, even though that shop never sent this event: [5](#0-4)

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
