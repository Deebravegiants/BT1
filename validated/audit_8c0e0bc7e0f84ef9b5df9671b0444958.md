Based on my review of `polkadot/runtime/parachains/src/on_demand/migration.rs`, the claim's technical description of the code is accurate: `pre_upgrade`'s overflow check is only compiled under `#[cfg(any(feature = "try-runtime", test))]` (the `pre_upgrade`/`post_upgrade` associated functions live in that gated `impl` block, and the trait-level `pre_upgrade`/`post_upgrade` hooks are further gated by `#[cfg(feature = "try-runtime")]`), while `on_runtime_upgrade` itself performs no equivalent bound check and instead silently `break`s with only a `log::warn!` when `order_status.queue.try_push` fails due to capacity.

Audit Report

## Title
Silent loss of paid on-demand orders during V1→V2 migration when legacy queue size exceeds `ON_DEMAND_MAX_QUEUE_MAX_SIZE` - (File: `polkadot/runtime/parachains/src/on_demand/migration.rs`)

## Summary
`UncheckedMigrateToV2::on_runtime_upgrade` drains all V1 `FreeEntries` and `AffinityEntries` orders and pushes them into the bounded V2 `OrderStatus::queue` via `try_push`, silently stopping and only logging a warning if the queue fills up before all orders are migrated [1](#0-0) . The capacity check that could catch this (`total_orders > polkadot_primitives::ON_DEMAND_MAX_QUEUE_MAX_SIZE`) exists only in `pre_upgrade`, which is gated behind `try-runtime`/`test` features and is not invoked during a genuine runtime upgrade [2](#0-1) [3](#0-2) .

## Finding Description
`v1::ON_DEMAND_MAX_QUEUE_MAX_SIZE` used for legacy queue-index wraparound arithmetic is a very large constant (`1_000_000_000`) [4](#0-3) , while the current, much smaller `polkadot_primitives::ON_DEMAND_MAX_QUEUE_MAX_SIZE` bounds the size of the new single V2 queue and is checked only inside the `try-runtime`-gated `pre_upgrade` [5](#0-4) . During a real (non-`try-runtime`) `on_runtime_upgrade` execution, `v1::FreeEntries::take()` and `v1::AffinityEntries::drain()` unconditionally consume the old storage, sort the combined orders, and push them into `order_status.queue` one at a time; once `try_push` returns `Err`, the loop `break`s and the remaining orders — whose backing storage has already been taken/drained — are permanently lost, with no on-chain error, event, or recovery mechanism, only a `log::warn!` [6](#0-5) . The trait-level `UncheckedOnRuntimeUpgrade::pre_upgrade`/`post_upgrade` hooks that would normally run these checks as part of the migration framework are compiled out entirely unless the `try-runtime` feature is enabled [3](#0-2) , confirming that in production builds no capacity check runs before the drain-and-merge occurs.

## Impact Explanation
Any on-demand orders queued via ordinary, unprivileged `place_order_*` extrinsics before the migration executes can be silently and permanently dropped if the combined V1 queue population exceeds the new, smaller V2 capacity at upgrade time — resulting in loss of already-paid-for service with no refund, no error signaled to affected paras, and no on-chain trace beyond a log line. This is a genuine, concrete loss-of-funds/service class impact scoped to the excess portion of the queue, matching an in-scope runtime storage-migration correctness bug.

## Likelihood Explanation
The precondition (V1 queue size exceeding the new V2 cap) is reachable purely through normal, unprivileged use of `place_order_*` extrinsics and requires no special privilege to create; the only externally-controlled trigger is the timing of a governance-initiated runtime upgrade that this migration executes, which is a normal, expected occurrence for any pallet migration in the SDK. The existing `pre_upgrade` check, which is the only in-repo defense, is demonstrably inert on production chains because it is compiled only under `try-runtime`/`test`.

## Recommendation
Move the `total_orders > ON_DEMAND_MAX_QUEUE_MAX_SIZE` validation (or an equivalent overflow-safe check) into `on_runtime_upgrade` itself, unconditionally, before draining `FreeEntries`/`AffinityEntries`. If the precondition would cause overflow, either preserve the excess orders (e.g., retain them in a spillover storage item pending manual handling) instead of discarding already-taken data, or design the migration so it does not take/drain storage until it can guarantee lossless placement into the new bounded queue.

## Proof of Concept
The existing test `queue_full_handling` in the file already demonstrates the underlying mechanics: it inserts 1000 orders into `v1::FreeEntries`, runs `on_runtime_upgrade`, and only asserts `new_status.queue.len() > 0`, explicitly acknowledging in a comment that "some orders may be dropped if queue is full" without asserting an error or recovery path [7](#0-6) . To conclusively prove the claim: populate `v1::FreeEntries`/`v1::AffinityEntries` with a combined count exceeding the current `polkadot_primitives::ON_DEMAND_MAX_QUEUE_MAX_SIZE` (valid under the old `1_000_000_000` bound), call `UncheckedMigrateToV2::<Test>::pre_upgrade()` and confirm it returns `Err(...)`, then separately call `UncheckedMigrateToV2::<Test>::on_runtime_upgrade()` directly (bypassing `pre_upgrade`, as happens on a real chain upgrade) and assert `OrderStatus::<Test>::get().queue.len() < total_orders_inserted` with no compensating event or storage record of the dropped orders.

#[cfg(any(feature = "try-runtime", test))]
impl<T: Config> UncheckedMigrateToV2<T> {
	pub fn pre_upgrade() -> Result<alloc::vec::Vec<u8>, sp_runtime::TryRuntimeError> {
		let old_queue_status = v1::QueueStatus::<T>::get();
		let free_entries = v1::FreeEntries::<T>::get().unwrap_or_default();
		let affinity_keys: alloc::vec::Vec<_> = v1::AffinityEntries::<T>::iter_keys().collect();

		let mut total_orders = free_entries.len();
		for core_idx in affinity_keys.iter() {
			total_orders += v1::AffinityEntries::<T>::get(core_idx).unwrap_or_default().len();
		}

		let affinity_count = v1::ParaIdAffinity::<T>::iter().count();

		log::info!(
			target: LOG_TARGET,
			"Before migration: {} total orders ({} free, {} in affinity queues), {} affinity mappings, traffic: {:?}",
			total_orders,
			free_entries.len(),
			total_orders - free_entries.len(),
			affinity_count,
			old_queue_status.as_ref().map(|s| s.traffic)
		);

		// Check that queue won't overflow during migration
		if total_orders > polkadot_primitives::ON_DEMAND_MAX_QUEUE_MAX_SIZE as usize {
			log::error!(
				target: LOG_TARGET,
				"Migration would lose orders: {} total orders exceeds V2 capacity of {}",
				total_orders,
				polkadot_primitives::ON_DEMAND_MAX_QUEUE_MAX_SIZE
			);
			return Err("Too many orders to migrate - queue capacity exceeded".into());
		}

		Ok((total_orders as u32, affinity_count as u32, old_queue_status.map(|s| s.traffic))
			.encode())
	}
