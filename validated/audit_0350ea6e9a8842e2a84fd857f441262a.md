### Title
Cross-workflow denial-of-service via globally-scoped `requestID` collision in HTTP trigger gateway handler - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
The internet-facing HTTP Trigger gateway handler tracks in-flight workflow-trigger requests in a single map keyed only by the client-supplied `requestID` (the JSON-RPC `req.ID`), with no binding to the workflow or the authorized owner that submitted it. Any party that can get a request authorized for *any* workflow (a normal, permissionless action — registering/owning a workflow and signing with its own key) can pick an arbitrary `requestID` and occupy that slot in the global map, causing a completely unrelated request from a different workflow/owner that happens to use the same `requestID` to be rejected outright. This mirrors the reported bug class: a security-relevant piece of shared state (here, an "in-flight" guard analogous to the `lastInteractedTimestamp` cooldown) can be mutated by a cheap, unprivileged/unrelated interaction and used to block a legitimate, unrelated party's operation.

### Finding Description
`httpTriggerHandler.HandleUserTriggerRequest` processes an inbound trigger request in this order: validate → resolve `workflowID` → `authorizeRequest` (JWT signature check scoped to that specific `workflowID`) → `checkRateLimit` → `setupCallback`. [1](#0-0) 

Critically, `setupCallback` guards concurrency solely by `requestID`, using a map that is **not** scoped by `workflowID` or by the authorized owner/key resolved just one step earlier: [2](#0-1) 

The backing struct confirms the map's key space is deliberately global — a single `requestID -> savedCallback` table shared across every workflow the gateway serves: [3](#0-2) 

Because authorization (`authorizeRequest`) only checks that the caller's signature is valid for *the workflowID present in that particular request* — not that the `requestID` itself is scoped to that workflow — any actor who legitimately owns/operates their own workflow (a normal, unprivileged, permissionless action any workflow developer can perform) can submit their own authorized trigger request using a `requestID` value equal to one they expect (or manage to race) a victim's unrelated workflow to use. The first request to reach `setupCallback` claims the slot; the second (the legitimate one, for a completely different workflow/owner) is rejected with a conflict error and never dispatched to the DON: [2](#0-1) 

This is the same root-cause pattern as the external report: a check meant to protect one actor's operation ("has this requestID/asset/timestamp already been consumed?") is keyed by attacker-influenceable, unscoped shared state instead of being bound to the actor's own identity, so a cheap, unrelated interaction from any other actor can consume/poison that shared state and block the legitimate actor's subsequent, otherwise-valid operation.

### Impact Explanation
A successful collision causes the legitimate workflow trigger to be dropped with `jsonrpc.ErrConflict` ("requestID: %s has already been used") instead of being dispatched to the DON, so the victim's workflow execution never starts. Because job/workflow triggers on the gateway are what ultimately cause on-chain fund movement or off-chain automation actions for CRE workflows, blocking them can prevent time-sensitive executions (e.g., missed automation windows), i.e., a denial-of-service on a specific, targeted workflow execution triggered by an unrelated, unprivileged party — analogous to the "freezing of funds"/DoS impact rated Medium in the source report.

### Likelihood Explanation
Exploitation requires the attacker to control (or race) the exact `requestID` string the victim will use. This is not attacker-arbitrary in the fully unauthenticated sense (the attacker still needs *some* authorized workflow to get past `authorizeRequest`), but:
- Getting an authorized workflow is a normal, permissionless, low-cost action (any developer can register a workflow and sign requests for it).
- The `requestID` collision is entirely feasible whenever request IDs are not high-entropy/attacker-unpredictable (e.g., deterministic/sequential IDs generated by client SDKs, retried requests reusing IDs, or an attacker simply flooding the map with many guesses/races during a narrow window) — since nothing on the server enforces a workflow-scoped namespace, the effective "keyspace" collision probability is far higher than intended.
- The check occurs *after* authorization/rate-limiting, so it is reachable by any authorized-but-unrelated caller with no dependency on the victim's credentials.

This is assessed as Medium likelihood: practical under realistic ID-generation practices, but bounded by needing a valid credential for *some* workflow and by needing to predict/race the target `requestID`.

### Recommendation
Scope the in-flight request guard to the tuple of `(workflowID, requestID)` or `(authorizedOwner, requestID)` rather than `requestID` alone, so that no external, unrelated workflow can occupy or collide with another workflow's request-tracking slot:
```go
key := workflowID + ":" + requestID
if _, found := h.callbacks[key]; found { ... }
```
Alternatively, derive the callback key after authorization succeeds, binding it to the resolved `AuthorizedKey`/owner, so cross-workflow collisions are structurally impossible.

### Proof of Concept
1. Attacker registers their own workflow `W_attacker` on-chain and obtains a valid signing key for it (permissionless, ordinary developer action) — this passes `authorizeRequest` for `W_attacker`.
2. Attacker sends `HandleUserTriggerRequest` with `req.ID = "shared-id-123"` and `Workflow.WorkflowID = W_attacker`. This call reaches `setupCallback`, which inserts `h.callbacks["shared-id-123"]`. [2](#0-1) 
3. Concurrently (or immediately after), the victim's client sends a legitimate, correctly authorized trigger for an entirely different workflow `W_victim`, also using `req.ID = "shared-id-123"` (e.g., due to deterministic ID generation in their SDK, or because the attacker predicted/raced this value).
4. Because `h.callbacks` is keyed only by `req.ID` (not by workflow), the victim's `setupCallback` call finds the slot already `found`, and the handler responds with `jsonrpc.ErrConflict`, and the victim's workflow execution is never dispatched to the DON: [4](#0-3) 
5. Result: the attacker, without any relationship to `W_victim` or its owner, has caused a denial of service on the victim's legitimate, authorized workflow trigger.

Note: I could not fully verify how `requestID` values are generated by production client SDKs (whether they are sufficiently high-entropy/random to make collision infeasible in practice); this affects the practical likelihood rating and could not be resolved from the indexed code alone.

func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	key, err := h.authorizeRequest(ctx, workflowID, req, callback)
	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
