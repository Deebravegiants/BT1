### Title
Orb OS version block is not enforced on "stage" builds, allowing signups on blocked software versions - (File: src/plans/mod.rs)

### Summary
In `VaultFactory`, the blacklist check that guards contract creation is missing from the migration path, letting a vault reach a blacklisted (vulnerable) implementation. The structurally analogous defect in `orb-core` is in the pre-signup gate `is_orb_os_version_allowed`: the check that is supposed to stop signups from Orbs running a `Blocked` software version is only enforced on non-"stage" builds. On "stage" builds, the failing check is swallowed (just a UI notification) and execution falls through to continue the signup instead of aborting.

### Finding Description
`is_orb_os_version_allowed` queries the backend and returns `true` only when `OrbOsVersionStatus::Allowed` is returned [1](#0-0) . The intended enforcement point is in `do_signup`:

```rust
if !self.is_orb_os_version_allowed(debug_report).await {
    #[cfg(feature = "stage")]
    notify_failed_signup(orb, Some(SignupFailReason::SoftwareVersionBlocked));
    #[cfg(not(feature = "stage"))]
    return Ok(result);
}
``` [2](#0-1) 

When the `stage` feature is compiled in, a failed/blocked version check only triggers a UI notification and does **not** return — execution proceeds to `scan_remaining_qr_codes`, `biometric_capture`, `biometric_pipeline`, `build_pcp`, and PCP upload as if the version check had passed [3](#0-2) . Only when the `stage` feature is absent does the function correctly `return Ok(result)` and stop the flow. This mirrors the reported bug class exactly: one code path (`create`-equivalent / default/production build) enforces the version/blacklist gate, while a second reachable path (`migrate`-equivalent / `stage` build) omits the enforcement and allows the same privileged action (full biometric capture + backend signup) to proceed despite the negative status.

There is a second, independent version-status enforcement in `enroll_user::Plan::run`, which inspects `signup_post::Response.software_version_status` after the enrollment POST and returns `Status::SoftwareVersionOutdated` on `Blocked` [4](#0-3) , but that check runs on the *backend's* independently-computed status for the same request and does not restore the guarantee removed from `do_signup`'s pre-capture gate: it fires only after biometric capture, pipeline processing, and (depending on flow) PCP upload/other side effects that the early gate was meant to prevent in the first place.

### Impact Explanation
An Orb built with the `stage` feature that has a version explicitly reported as `Blocked` by the management backend (e.g., due to a known security flaw in fraud detection, iris/face pipeline, or signature calculation) will still proceed through biometric capture, the fraud/liveness pipeline, and personal-custody-package construction/upload before any later-stage check might catch it. Since the early gate is the intended defense-in-depth barrier for exactly this scenario, its silent bypass on `stage` builds allows signups (and the associated biometric data disclosure/processing) to occur using software know to be vulnerable or deprecated below the acceptable threshold — the same class of impact as the original report (exposure to consequences the blocking mechanism was designed to prevent).

### Likelihood Explanation
This does not require an attacker to do anything unusual — it triggers automatically whenever a `stage`-featured build runs against a version the backend marks `Blocked`, which is the normal maintained purpose of the blocklist. The bypass is unconditional given that build configuration, so likelihood is high whenever `stage` builds are used with a version the backend intends to block.

### Recommendation
Make the pre-signup gate unconditionally abort when the version check fails, regardless of the `stage` feature flag:

```diff
 if !self.is_orb_os_version_allowed(debug_report).await {
-    #[cfg(feature = "stage")]
     notify_failed_signup(orb, Some(SignupFailReason::SoftwareVersionBlocked));
-    #[cfg(not(feature = "stage"))]
     return Ok(result);
 }
```
If `stage` builds intentionally need to continue for testing purposes with non-`Blocked` statuses (e.g. `Deprecated`/`Unknown`), that distinction should be made explicit in `is_orb_os_version_allowed`'s return type rather than collapsing "check failed" into a no-op fallthrough for an entire build configuration.

### Proof of Concept
1. Build `orb-core` with `--features stage`.
2. Configure/mock the backend `orb_os_status` endpoint (`src/backend/orb_os_status.rs`, `POST /api/v1/orbs/check/orbos/version`) to respond with `status: "BLOCKED"`.
3. Initiate a signup flow (`MasterPlan::do_signup`). Observe that `is_orb_os_version_allowed` returns `false`, but because `stage` is enabled, the code takes the `notify_failed_signup(...)` branch and does not `return` — execution continues into `scan_remaining_qr_codes`/`biometric_capture`/`biometric_pipeline`/`build_pcp`, i.e., the signup proceeds despite the Orb software version being explicitly blocked [5](#0-4) .

    /// Checks if Orb OS is in an allowed version range.
    async fn is_orb_os_version_allowed(&self, debug_report: &mut debug_report::Builder) -> bool {
        match backend::orb_os_status::request().await {
            Ok(orb_os_status::OrbOsVersionCheckResponse {
                status: OrbOsVersionStatus::Allowed,
                ..
            }) => return true,
            Ok(orb_os_status::OrbOsVersionCheckResponse { status, error }) => {
                dd_incr!("main.count.signup.result.failure.orb_os_version");
                tracing::error!("Orb OS version check failed. Status: {status:?} Error: {error:?}");
                debug_report.signup_server_failure();
                debug_report.enrollment_status(enroll_user::Status::SoftwareVersionOutdated);
            }
            Err(e) => tracing::error!("Orb OS version check request failed: {e:?}"),
        }
        false
    }
