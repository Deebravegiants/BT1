### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant identity) used downstream to attribute the webhook is read from an unauthenticated HTTP header. The two are never bound together, so a webhook payload that is validly signed for one shop can be replayed with a different `shop-domain` header and still pass HMAC validation.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` is derived purely from the `hmac-sha256`/`x-shopify-hmac-sha256` header: [1](#0-0) [2](#0-1) 

The `shop` value is read independently from the `shop-domain`/`x-shopify-shop-domain` header, which is not part of the signable string at all: [3](#0-2) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` (which in turn calls `to_signable_string`, i.e. only the body) and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because a single app has one `client_secret`/`api_secret_key` shared across every merchant that installs it, an HMAC computed by Shopify for a webhook delivered to shop A is a valid HMAC for that exact body regardless of which shop header accompanies it. The binding that should hold is:

`shop authenticated by the HMAC == shop attributed to the processed webhook data (request.shop)`

This binding does not exist: the HMAC only proves "this body was signed by Shopify with the app's secret," not "this body belongs to shop X."

### Impact Explanation
An unprivileged actor who operates their own shop with the app installed can capture a legitimately-signed webhook body (e.g., by installing the app on their own store and triggering an event such as `orders/create`), then replay the exact same body + HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a different (victim) shop's domain. `HmacValidator.validate` still succeeds because the header is not part of the signed content, and `Registry.process` hands the handler a `WebhookMetadata` claiming the victim shop, causing the host application to process/store attacker-controlled data under another tenant's identity — a cross-tenant data injection/corruption vector reachable without any credentials belonging to the target shop.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-owned shop (any unprivileged internet user can do this for a public app), (2) capturing one legitimately delivered webhook, and (3) resending the same body with a swapped shop header to the app's public endpoint. No possession of `api_secret_key`, access tokens, or the victim's credentials is required.

### Recommendation
Bind the shop identity into the authenticated content, e.g. include the `shop-domain` header value in the HMAC-signed material (or otherwise cryptographically bind headers to the payload), and/or have `Registry.process` cross-check `request.shop` against the shop the webhook was actually registered for before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers an event (e.g. creates an order) so Shopify sends a webhook with a valid `x-shopify-hmac-sha256` for the resulting JSON body.
2. Attacker captures the raw body and HMAC header from that delivery.
3. Attacker POSTs the same raw body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` (it only checks the body against the shared secret) and `ShopifyAPI::Webhooks::Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)`, causing the app to process attacker-controlled data as if it belonged to the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
