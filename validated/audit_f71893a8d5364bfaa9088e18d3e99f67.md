### Title
ERC1155 batches accepted via unconditional `onERC1155BatchReceived` are untracked by `erc20TokenAddresses` balance accounting and can be drained by any attacker's own CASE2 op - (File: contracts/Transferer.sol, contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`Transferer.onERC1155BatchReceived` (contracts/Transferer.sol:38-46) accepts any ERC1155 batch unconditionally with no bookkeeping, while `EmporiumUpgradeable.runAction`'s balance-diff/UTXO-creation loop (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:132-151) only iterates `circomData.erc20TokenAddresses`, a fungible-token address list that cannot represent an ERC1155 `(address, tokenId)` pair. Any ERC1155 tokens that land on Emporium through a legitimate CASE2 call (e.g. a vault that mints/returns NFT shares to `msg.sender == Emporium`) are therefore never converted into a UTXO, never nullifier-protected, and never balance/slippage-checked - leaving them as bare, unattributed tokens sitting on Emporium that any unrelated attacker can pull out with their own unrelated CASE2 op.

### Finding Description
The equality that must hold is: *value entering Emporium during a user's `runAction` call == value represented by the `UTXO[]` returned from that call (and thus protected by the corresponding output commitment)*. This equality is enforced only for tokens explicitly listed in `circomData.erc20TokenAddresses` via the `balancesBefore`/`balancesAfter` diff at contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:85-151: [1](#0-0) 

`circomData.erc20TokenAddresses` is an `address[]` with no accompanying token-id dimension (see `formBasicInput` encoding it as `uint160(erc20TokenAddresses[i])`): [2](#0-1) 
so it structurally cannot enumerate ERC1155 `(contract, id)` balances. Any ERC1155 batch received during `runAction`'s CASE2 stateless call is accepted unconditionally by: [3](#0-2) 
and simply never appears in `balancesBefore`/`balancesAfter`, so no `UTXO` is minted for it and it is not gated by `balanceDif >= circomData.slippageValues[i]` in `Hinkal.sol` (contracts/Hinkal.sol:110-114) either, since that loop is also keyed off `erc20TokenAddresses`.

Root cause: the CASE2 stateless branch of `runAction` executes attacker(or victim)-supplied `op.endpoint.call{value: op.value}(op.callData)` with `msg.sender == address(Emporium)` at the target contract: [4](#0-3) 
The only restriction is that the selector is not `callHinkalWallet`/`doSendToRelay`; `op.endpoint` and the rest of `op.callData` are fully attacker-controlled fields of `circomData.externalActionData.externalActionMetadata` in the attacker's own proof, and `onlyAllowedRecipient` only checks that the caller of `runAction` is the Hinkal contract, not the contents of the ops: [5](#0-4) 

Exploit flow:
1. A victim runs a legitimate CASE2 op (e.g. depositing into an external vault/minting protocol) whose result is an ERC1155 batch minted/transferred back to `msg.sender`, which at that call point is Emporium. Emporium accepts it via `onERC1155BatchReceived` with no further processing. Because `circomData.erc20TokenAddresses` for that transaction lists only fungible tokens, the ERC1155 batch is never turned into a `UTXO` and is not covered by any nullifier or commitment - it is simply idle balance on Emporium.
2. An unrelated attacker, using their own valid proof over their own unrelated UTXOs, submits `transact()` with a CASE2 op: `endpoint = ERC1155 token address`, `callData = abi.encodeWithSelector(IERC1155.safeBatchTransferFrom.selector, address(emporium), attacker, ids, amounts, "")`.
3. Inside `runAction`, this executes as `token.call(callData)` with `msg.sender == Emporium`. Standard ERC1155 `_safeBatchTransferFrom` authorization is `_msgSender() == from || isApprovedForAll(from, _msgSender())`; here `_msgSender() == from == Emporium`, so the transfer succeeds with zero prior approval.
4. The attacker's own `erc20TokenAddresses`/`balancesBefore`/`balancesAfter` arrays never reference the ERC1155 token or its ids, so this transfer produces no `balanceChange` violation and no revert; `deltaAmountChanges` for the attacker's declared (unrelated) tokens is unaffected, so `payRelayFees`/`handleOut` proceed normally and the attacker's own real UTXO output is created as usual.

No existing guard - `performHinkalChecks`, `verifyProof`, `rootHashExists`, `insertNullifiers`, `onlyAllowedRecipient`, or the circuit's `inTotal + amountChanges === outTotal` constraint - references ERC1155 balances at all, because ERC1155 assets are entirely outside the `erc20TokenAddresses`/`amountChanges` accounting model that those constraints protect.

### Impact Explanation
Any unprivileged attacker can permanently steal ERC1155 assets that are custodied by Emporium as a side effect of another user's legitimate CASE2 interaction, since those assets are never represented by any UTXO, nullifier, or balance/slippage check. This is direct theft of in-flight user funds by a third party who never had any claim on them, satisfying the Critical severity bar. The attack is fully repeatable against any ERC1155 balance that accumulates on Emporium and costs the attacker only their own transaction/proof-generation cost.

### Likelihood Explanation
Preconditions: some victim (or the attacker themselves acting as "depositor," e.g. to bait future victims) must cause an ERC1155 batch to be transferred to Emporium as a side effect of a CASE2 `op.endpoint.call`, which is entirely plausible for NFT-vault/tranche-style DeFi protocols that mint or return ERC1155 shares/receipts to the caller. Once that happens, exploitation requires nothing beyond an attacker's own ordinary, unprivileged `transact()` call with a self-crafted `CircomData`/`externalActionMetadata` - no signature, no role, no interaction with the victim is needed. This is a low-cost, deterministic, and repeatable drain of any ERC1155 balance left on Emporium.

### Recommendation
Either (a) make Emporium reject ERC1155 transfers entirely (revert in `onERC1155Received`/`onERC1155BatchReceived` rather than returning the selector unconditionally, since the protocol's accounting model has no representation for non-fungible/semi-fungible balances), or (b) extend `CircomData`/`runAction` to explicitly enumerate ERC1155 `(address, tokenId)` pairs analogous to `erc20TokenAddresses`, include their before/after balance diffs in the `balanceChange`/slippage checks, and mint corresponding UTXOs/commitments for them before any value is considered "settled" on Emporium. Until such accounting exists, CASE2 stateless calls should also be restricted (allow-list of `op.endpoint` targets, or disallow arbitrary `safeTransferFrom`/`safeBatchTransferFrom` selectors targeting `address(this)` as `from`) to prevent draining any assets not covered by the `erc20TokenAddresses` model.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable` (allowed recipient), a mock ERC1155 contract, and a mock "vault" external contract whose `deposit()` mints an ERC1155 batch to `msg.sender`.
2. Victim calls `transact()` with a CASE2 op: `endpoint = vault`, `callData = deposit(...)`, `erc20TokenAddresses = [someERC20]` (no ERC1155 entry). Assert: `mockERC1155.balanceOf(emporium, id) == amount` after the call, and assert the returned `UTXO[]` from `runAction` contains no entry accounting for `amount`/`id` (equality broken: assets on Emporium != UTXO-represented value).
3. Attacker (different EOA, unrelated deposit/UTXO/proof) calls `transact()` with a CASE2 op: `endpoint = mockERC1155`, `callData = safeBatchTransferFrom(emporium, attacker, [id], [amount], "")`, `erc20TokenAddresses` unrelated to the ERC1155 token.
4. Assert after step 3: `mockERC1155.balanceOf(emporium, id) == 0` and `mockERC1155.balanceOf(attacker, id) == amount`, with the attacker's transaction succeeding and no revert from `BalanceChangeShouldBePositive`, slippage checks, or nullifier/root verification - proving the ERC1155 batch was extracted without ever being represented in `nullifiers`, `roots`, or any `amountChanges`/`balanceDif` field.
