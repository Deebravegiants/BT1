### Title
Webhook `shop` and `topic` headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers, which are used to route and tag the webhook to a tenant, are read straight from the request headers and are never included in the HMAC-signed material. Because the app's webhook secret is shared across every shop that installs the app, an attacker who controls one shop can capture a validly-signed webhook delivery from their own store and replay it against the app's webhook endpoint while substituting the `shop-domain` header for a victim shop, producing a request the app will process as if it originated from the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all parsed directly from HTTP headers and are not part of the signed data: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC solely against `verifiable_query.to_signable_string`, i.e. the raw body: [3](#0-2) 

`Registry.process` raises only if the HMAC (over the body) fails, then immediately uses the unauthenticated `request.shop` and `request.topic` to dispatch to the tenant-specific handler: [4](#0-3) 

The identity binding that should hold is: `shop header == shop that generated this HMAC`. Because the HMAC secret (`Context.api_secret_key`) is the same for all shops on a given app installation, and the `shop-domain` header is excluded from the signed bytes, this equality is never enforced — any request whose body+secret produce a valid HMAC will be accepted regardless of which shop's domain is declared in the header. An attacker who owns/controls a shop with the app installed can trigger a webhook for their own store, capture the `raw_body` and `x-shopify-hmac-sha256` value from that legitimate delivery, and replay it to the app's public webhook endpoint with `x-shopify-shop-domain` rewritten to a victim shop. `HmacValidator.validate` still passes (body and secret are unchanged), and `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with the attacker-chosen shop value, causing the registered handler to act on data intended for the attacker's own shop under the victim's tenant identity.

### Impact Explanation
This breaks the tenant boundary the app relies on webhook `shop` to establish. Depending on how the host application's handler uses `WebhookMetadata#shop` (e.g., looking up/loading the victim's session, updating victim-scoped records, or acting on `app/uninstalled` for the wrong shop), this can result in cross-tenant data corruption or unauthorized actions being taken against a victim merchant's account, which matches the "cross-tenant access" High/Critical impact category.

### Likelihood Explanation
Any developer/attacker who can install the app on a shop they control (a normal, unprivileged action for public apps) can obtain a validly HMAC-signed webhook body and hmac value for arbitrary topics simply by triggering real store events. Replaying it with a forged `shop-domain` header requires no secret material beyond what Shopify itself sends the attacker for their own shop.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the signed payload before trusting it: either verify the `shop` header against a shop-specific secret/session already known to the app (not the shared `api_secret_key`), or require handlers to independently confirm the deduced shop corresponds to a shop that actually has this webhook/topic registered/expected, rather than trusting the header value once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers a real webhook (e.g., `orders/create`); Shopify delivers a request with a valid `x-shopify-hmac-sha256` over the JSON body, signed with the app's single `api_secret_key`.
2. Attacker captures `raw_body` and the `x-shopify-hmac-sha256` value.
3. Attacker POSTs to the app's webhook endpoint with the same `raw_body`/HMAC but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:27-31`) passes because it only checks the body bytes against the secret.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the handler with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"`, even though the payload actually belongs to the attacker's own shop.
