### Title
Webhook shop-tenant identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
Shopify webhooks are authenticated with a single HMAC-SHA256 signature computed over the request body only, using the app's shared `client_secret` (the same secret is valid for every shop installed on the app). The `shop`, `topic`, `api_version`, and `webhook-id` values are taken straight from HTTP headers and are never part of the signed payload. Any party who has ever received one legitimately-signed webhook body (e.g., from their own shop's install) can replay that exact body+HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` header, and the gem's `Registry.process` will accept it as coming from that arbitrary shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are derived purely from headers supplied with the HTTP request, with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (i.e., the body) against `verifiable_query.hmac`: [4](#0-3) 

`Registry.process` uses this single check as the sole authentication gate, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The equality the code implicitly relies on is:
`shop authenticated (bytes covered by HMAC) == shop acted upon (header value passed to the handler)`

This equality is false. The HMAC secret (`client_secret`) is identical for all shops that install the same app, and Shopify computes the signature only over the raw body. Consequently, any attacker who has captured one valid `(raw_body, hmac)` pair from a webhook delivered to Shop A (e.g., by installing/uninstalling their own test store using the same app, or via a leaked webhook log) can send that exact body and HMAC to the app's webhook endpoint again but with the `X-Shopify-Shop-Domain` header changed to Shop B. `Utils::HmacValidator.validate` still returns `true` because it never inspects the `shop` header, and `Registry.process` will invoke the registered handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)`, causing the host application to process Shop A's webhook payload as if it belonged to Shop B.

### Impact Explanation
This breaks the tenant-isolation boundary the HMAC is meant to enforce: an unprivileged actor with no access token, no `client_secret`, and no relationship to the victim shop can cause a webhook payload to be misattributed to an arbitrary shop domain that also uses the same app. Depending on how the host app's webhook handler uses `shop` (most apps key their data updates, uninstall/GDPR redaction actions, or billing state entirely off this field, per this gem's own `WebhookMetadata` design), this results in cross-tenant data corruption or a redaction/uninstall action being triggered against a shop that never sent that event. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
The prerequisite is only a single legitimately-signed webhook body/HMAC pair, which is trivial to obtain (install the app once on any store, or via webhook logs/backups) — no access token, `client_secret`, or privileged account is needed. The replay is a simple unauthenticated HTTP POST with a modified header. Because the body's content also stays attacker-controlled from that captured sample (only the `shop` header changes), the practical severity depends on payload content, but the authentication bypass itself is fully exploitable with no special access.

### Recommendation
Bind the tenant identity into the signed material, or otherwise cryptographically verify the `shop` header against a value derived from data that is actually covered by the HMAC (Shopify's actual webhook contract does not sign `shop` either, so the safer fix is at the consumption layer): `Webhooks::Request#to_signable_string` should not be treated as sufficient to authorize `shop`. At minimum, document/guard that `request.shop` must be cross-checked by the caller against a known/expected shop domain (e.g., one already associated with a stored session/access token) before it is trusted, and `Registry.process` should require callers to supply the expected shop rather than accept whatever value arrives in the header as-is.

### Proof of Concept
1. App "MyApp" is installed by both `shop-a.myshopify.com` and `shop-b.myshopify.com`; both installs share the same `client_secret`.
2. Attacker controls `shop-a.myshopify.com` (installs the app themselves) and captures a legitimate webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC-SHA256(client_secret, B)`), together with `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
3. Attacker replays the exact same request to the app's webhook endpoint, changing only the header to `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "shop-b.myshopify.com", hmac-sha256: H...})` is constructed.
5. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` and compares it to `H` — it matches, since `shop` is not part of `to_signable_string`.
6. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: parsed(B), ...)`, causing shop-a's webhook data/action to be processed under shop-b's tenant identity.
