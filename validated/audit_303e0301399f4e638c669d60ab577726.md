### Title
Webhook tenant identity (`shop`, `topic`, `webhook_id`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers that are never included in the HMAC computation. `Webhooks::Registry.process` trusts these header-derived fields to route the payload to a tenant-specific handler, breaking the equality `bytes verified == bytes acted on`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements the `VerifiableQuery` interface used by `Utils::HmacValidator`. Its `hmac` and `to_signable_string` methods are: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`. Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers: [3](#0-2) 

`HmacValidator.validate` only checks that `HMAC-SHA256(secret, raw_body)` matches the `hmac-sha256`/`x-shopify-hmac-sha256` header: [4](#0-3) 

`Registry.process` calls `Utils::HmacValidator.validate(request)` — which only proves the body bytes are authentic — and then unconditionally trusts `request.shop`, `request.topic`, and `request.webhook_id` (all header-derived, unsigned) to dispatch to the tenant-specific `WebhookHandler`: [5](#0-4) 

This is the exact bug class described in the external report generalized to this gem: the cryptographic check ("approve amount signed") covers less than what is subsequently acted upon ("transfer of `amount+1`"). Here, the HMAC "covers" only the body bytes, but the code acts on `shop`/`topic`/`webhook_id` header values that are outside that covered set — i.e., `bytes verified != bytes acted on`.

### Impact Explanation
Because the tenant identity (`shop`) is not bound to the signed payload, an attacker who possesses one validly-signed webhook body/HMAC pair (e.g., from their own store's app installation, which they are entitled to receive) can replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. The signature still validates (it only checks the body), and `Registry.process` will hand the attacker-controlled body to the handler tagged with the victim's `shop` in `WebhookMetadata`: [6](#0-5) 

Depending on how the host application's `WebhookHandler` implementation persists data keyed by `shop`, this enables cross-tenant data injection/corruption — writing or triggering actions against a merchant record the attacker does not control, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The webhook HTTP endpoint is by design internet-reachable and unauthenticated aside from the HMAC check, so no credentials, tokens, or `client_secret` are required, only a validly-signed body (which any app-installing merchant can legitimately obtain from their own store's webhook traffic) and a header value they control. This is a fully unprivileged-internet-user-reachable path through the gem's own header-parsing and dispatch code.

### Recommendation
Bind the tenant/topic identity into the verified material: either require the host application to independently confirm that `shop`/`topic` headers match the session or subscription that requested the webhook before invoking `handler.handle`, or extend `to_signable_string` (or a dedicated check in `Registry.process`) to cross-validate the header-derived `shop` against a value embedded in (or separately authenticated against) the signed body, rather than trusting the raw header value unconditionally.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook delivery: `raw_body = B`, header `X-Shopify-Hmac-Sha256 = H`, header `X-Shopify-Shop-Domain = attacker.myshopify.com`.
2. `H` is a valid HMAC over `B` under the app's shared secret (this is how Shopify signs webhooks; the gem's own `HmacValidator` computes exactly this).
3. Attacker replays `POST` to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but header `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac` reads `H` from the header, `to_signable_string` returns `B`; `HmacValidator.validate` succeeds since only `B` and `H` are checked ( [1](#0-0) , [7](#0-6) ).
5. `Registry.process` passes `request.shop == "victim.myshopify.com"` to the handler along with attacker-controlled body content ( [8](#0-7) ), causing the host app to process attacker data under the victim tenant's identity.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
