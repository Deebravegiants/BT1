### Title
`exchange_token` sends the app's `client_secret` to a shop host taken from an unvalidated JWT `dest` claim - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the destination host for the OAuth token-exchange request directly from the `dest` claim of the caller-supplied session token, without passing it through `Utils::ShopValidator`, unlike the sibling method `migrate_to_expiring_token` in the same file which explicitly sanitizes its `shop` argument before use.

### Finding Description
`exchange_token` decodes the session token and takes `dest_shop = jwt_payload.shop` (i.e., the `dest` claim with the scheme stripped) with no domain validation: [1](#0-0) 

That `dest_shop` value is used verbatim to build the `Session` object whose `shop` field becomes the request host inside `Clients::HttpClient`: [2](#0-1) 

The client then POSTs a body containing `client_id` and `client_secret` (the app's confidential Shopify API secret) to `https://#{session.shop}/admin/oauth/access_token`: [3](#0-2) 

By contrast, the neighboring `migrate_to_expiring_token` method — which performs the same kind of request carrying `client_secret` — explicitly calls `Utils::ShopValidator.sanitize!(shop)` before constructing the session/host used for the request: [4](#0-3) 

`ShopValidator` exists specifically to constrain a shop string to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`), rejecting anything else: [5](#0-4) 

`JwtPayload` itself performs no such domain restriction on `dest`; it only checks the JWT signature, `aud == Context.api_key`, and expiry — the `dest` string is otherwise passed through unmodified: [6](#0-5) 

This breaks the identity binding: "the host validated" (none, for `exchange_token`) versus "the host that receives the `client_secret`" (whatever `dest` says). The `dest` claim is documented as directly controlling which host receives the token-exchange request: [7](#0-6) 

### Impact Explanation
If an attacker can influence the `dest` value in the session token passed into `exchange_token` (e.g., a session token is expected to be validated only via HMAC signature and `aud`, but nothing in this gem constrains `dest` to a `*.myshopify.com`/trusted domain before it is used as an outbound request host), the app's `client_secret` and `client_id` are sent to an attacker-controlled host over HTTPS. This is exactly the SSRF-with-credentials pattern called out in scope: leaking the app's `client_secret` to an arbitrary host is a Critical-severity credential exfiltration, and the asymmetry with `migrate_to_expiring_token` (which does sanitize) shows this is not an intentional design choice but a missing check in this one code path.

### Likelihood Explanation
Exploitability depends entirely on how trustworthy the `dest` claim is. Session tokens are normally minted and signed by Shopify itself using the app's shared secret, so an external, unprivileged attacker cannot forge an arbitrary `dest` without already possessing the `client_secret` — which is out of scope per the rules ("anything requiring `api_secret_key` ... or leaked credentials"). I could not verify from this gem's code alone whether there is any legitimate flow in which a caller-supplied session token with an attacker-chosen `dest` reaches `exchange_token` without secret compromise (e.g., a token minted for a different, attacker-owned app that shares no verification of shop ownership) — that would depend on integration details outside this library. Given the rules require the vulnerability to be reachable by an unprivileged internet user without a leaked secret, and I cannot conclusively demonstrate that path within this gem's own code, this finding should be treated as a hardening gap (missing defense-in-depth `ShopValidator.sanitize!` call, matching the pattern already applied one method away) rather than a fully proven exploit chain.

### Recommendation
Apply `Utils::ShopValidator.sanitize!(dest_shop)` (or equivalent) to the `dest` claim in `exchange_token` before constructing `shop_session`, mirroring the validation already performed in `migrate_to_expiring_token`, so the host that receives `client_id`/`client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` regardless of the JWT's `dest` value.

### Proof of Concept
Not fully constructible with the code available in this gem alone, because triggering it requires supplying a session token whose `dest` claim is attacker-controlled while still passing signature/`aud` checks in `JwtPayload.initialize` — a precondition that (per this gem's code) normally requires the app's `api_secret_key`, which is out of scope. The concrete, verifiable defect is the code-level asymmetry shown above: `exchange_token` omits the `ShopValidator.sanitize!` call that `migrate_to_expiring_token` performs on the same class of untrusted "host" input before it is used to route a request carrying `client_secret`.

        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
