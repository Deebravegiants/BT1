### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an incoming webhook from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but the HMAC signature that `ShopifyAPI::Utils::HmacValidator` verifies is computed only over the raw request body. The shop-domain header is never part of the signed material, so an attacker who possesses one valid `(body, hmac)` pair for their own shop can replay it against the app's webhook endpoint with an arbitrary `shop-domain` header, and the request will still pass HMAC validation while being attributed to a different (victim) shop.

### Finding Description
`Request#to_signable_string` returns only the raw body:

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`shop` is read straight from an unauthenticated header, with no cryptographic binding to the HMAC:

```ruby
sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [2](#0-1) 

`Registry.process` validates the HMAC over `to_signable_string` (i.e., the body only) via `Utils::HmacValidator.validate(request)`, and if that passes, it trusts `request.shop` (from the header) when building `WebhookMetadata` that is handed to the app's handler:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

`HmacValidator.validate` computes the expected signature purely from `verifiable_query.to_signable_string` (the body) and the app's `api_secret_key`, independent of any shop/tenant field:

```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [4](#0-3) 

**Identity binding broken:** the equality that should hold is `shop_used_for_authorization == shop_covered_by_hmac`. In this gem it is instead `shop_used_for_authorization (header, unauthenticated) != anything_covered_by_hmac (body only)`. Any two shops running the same app share the same `api_secret_key`, and Shopify's webhook bodies for many topics are shop-agnostic or predictable (e.g., `app/uninstalled` bodies contain no shop-specific data, or an attacker's own shop can generate a body with attacker-chosen content that happens to match a state transition meaningful for another shop, e.g. `shop/update`, `customers/data_request`, or a topic whose body the attacker fully controls via their own shop's settings). Because the header is never part of the signed payload, the same valid `(body, hmac)` pair generated for the attacker's own shop can be replayed with the `shop-domain` header rewritten to any victim shop's domain, and it will pass verification, causing the app to process the payload as if it originated from the victim shop.

### Impact Explanation
This crosses a tenant boundary: an unprivileged user who has their own shop (and thus can legitimately receive real, correctly-signed webhooks from Shopify for their own shop) can forge the shop attribution of that same signed payload to any other shop known to be using the app, since the shop identity is not part of the HMAC-signed content. Depending on the handler logic built by the app on top of `WebhookMetadata#shop` (e.g., uninstalling/deauthorizing a shop, updating shop-scoped records, honoring `customers/redact` or `shop/update` semantics), this enables cross-tenant data manipulation using only the attacker's own legitimately-signed webhook traffic — no `api_secret_key`, access token, or other credential theft is required, since the attacker already legitimately receives HMAC'd webhooks for their own shop.

### Likelihood Explanation
Any developer using an app registered with Shopify and installed on more than one shop is affected, since all shops of a single app share the same `client_secret`/`api_secret_key` used to compute webhook HMACs. The attacker only needs to be an app user for one shop (fully unprivileged relative to any other tenant) and control of the standard webhook delivery endpoint the app already exposes and documented for use, as shown in `docs/usage/webhooks.md`.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signable string used for webhook HMAC verification, or independently verify that the shop-domain header corresponds to a shop actually authorized/known to have this webhook subscription (e.g., cross-check against the shop that registered the specific `webhook_id`) before trusting `WebhookMetadata#shop`. At minimum, document prominently that `WebhookMetadata#shop` is not cryptographically bound to the HMAC and must not be trusted as the sole tenant identifier by downstream handlers.

### Proof of Concept
1. App is installed on Attacker's shop `attacker.myshopify.com` and Victim's shop `victim.myshopify.com`, both under the same Shopify app (`api_secret_key` shared).
2. Attacker's shop receives (or attacker triggers, e.g. via changing their own shop settings) a legitimate Shopify webhook for some topic with body `B`, correctly signed as `HMAC(api_secret_key, B) = H`.
3. Attacker sends a request to the app's webhook endpoint with:
   - `shopify-hmac-sha256: Base64(H)`
   - `shopify-shop-domain: victim.myshopify.com`
   - `shopify-topic: <same topic>`
   - body: `B`
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(api_secret_key, B) == H`, matching `Request#to_signable_string` at `lib/shopify_api/webhooks/request.rb:35-38`.
5. `Registry.process` calls the app handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...)`, per `lib/shopify_api/webhooks/registry.rb:198-199`, even though the payload was never signed for `victim.myshopify.com`.
