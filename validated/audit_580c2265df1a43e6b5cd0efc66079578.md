### Title
Webhook `shop` (tenant identifier) is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic for a given shop as long as the HMAC over the raw body validates, but the `shop` (and `topic`/`webhook-id`) fields used to attribute the webhook to a tenant are taken from HTTP headers that are never included in the signed bytes.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` only [1](#0-0) . `HmacValidator.validate` computes `HMAC-SHA256(client_secret, to_signable_string)` and constant-time-compares it against the `X-Shopify-Hmac-Sha256` header [4](#0-3) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from separate, unsigned headers (`x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, `x-shopify-api-version`) [2](#0-1) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` and then forwards `request.shop` (and `request.topic`, `request.webhook_id`) unchecked into the handler as the tenant identity for the event [3](#0-2) .

The identity binding that should hold is: `shop header value == shop bound inside the HMAC-signed bytes`. Because the signature only covers the body, this equality is never enforced — any request with a valid `(body, hmac)` pair can carry an arbitrary `shop-domain` header and will still pass `Registry.process`'s check.

The critical detail that makes this exploitable rather than purely theoretical: the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is **shared across every shop that installs the app** — it is not a per-shop secret. So a merchant who legitimately installs the app on their own store (Shop A) will receive genuine webhook deliveries with a valid `(body, hmac)` pair signed with that same shared secret. That merchant can then replay the exact `body` + `hmac` to the app's public webhook endpoint while substituting `x-shopify-shop-domain: shop-b.myshopify.com` (a different, victim tenant). `HmacValidator.validate` still passes because it never inspects the header, and `Registry.process` hands `shop: "shop-b.myshopify.com"` straight to the handler.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to guarantee to host applications: a request that Registry.process accepts as "verified" for shop B was never actually authenticated as originating from Shopify for shop B — only the body bytes were verified, and those bytes came from a different, attacker-controlled shop's webhook stream. Any host application that trusts `WebhookMetadata#shop` (as documented) to determine which tenant's data to write, delete, or expose (e.g., GDPR redaction handlers, order/customer sync) can be tricked into cross-tenant data corruption or disclosure. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires only that the attacker (a) has installed the same app on a shop they control (a normal unprivileged user action, no special access needed) and (b) can send an arbitrary HTTP request with custom headers to the app's public webhook endpoint (also normal unprivileged internet access, no credentials, TLS interception, or leaked secrets required). No access to the target's or the app's `client_secret` is needed — only a normal, legitimate webhook delivery to the attacker's own store is used as the raw material.

### Recommendation
Bind the tenant identity into the signed material, e.g., include `shop`, `topic`, and `webhook_id` in the value passed to `to_signable_string` (or otherwise validate a signed value against these header fields), or require callers to independently corroborate `request.shop` against an out-of-band trusted mapping (e.g., session store keyed by `webhook_id`/topic combination confirmed via a fresh Admin API call) before trusting `WebhookMetadata#shop` for tenant-sensitive actions.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a real Shopify webhook delivery for topic `orders/create` with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker captures `(B, H)` from the legitimate request their own store receives.
3. Attacker sends a new HTTP request to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and `X-Shopify-Topic: orders/create`.
4. `Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)` which recomputes HMAC over `B` and matches `H` — validation succeeds [5](#0-4) .
5. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed_body, ...))`, causing the host application to process attacker-controlled order data as if it belonged to `victim-shop.myshopify.com` [6](#0-5) .
