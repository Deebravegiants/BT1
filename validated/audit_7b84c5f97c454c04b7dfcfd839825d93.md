### Title
`pallet-state-coprocessor::handle_unsigned` charges a flat 2-DB-op weight regardless of batch size, letting an unbounded, fee-free `GetRequestsWithProof` overrun a block's real execution budget - (File: `modules/pallets/state-coprocessor/src/lib.rs`)

### Summary
`pallet_state_coprocessor::Pallet::handle_unsigned` is declared with a constant weight of `<T as frame_system::Config>::DbWeight::get().reads_writes(1, 2)` [1](#0-0) , no matter how many `GetRequest`s or how large the state proof inside the submitted `GetRequestsWithProof` message is. The actual work done by `handle_get_requests` — SCALE-decoding the state proof, rebuilding a trie/proof-db per contract, verifying membership/state proofs for every key, and ABI-encoding every resulting `GetResponse` for bandwidth metering — scales with `requests.len()` and the number of keys per request, which is entirely attacker-controlled and unbounded (`Vec<GetRequest>`, `Vec<Vec<u8>>` keys, `Proof.proof: Vec<u8>`) [2](#0-1) . This is the same bug class as the ConcreteCMS report: the code path that performs bulk work per user-supplied batch element has no accounting/limit tied to the batch size, so declared cost (here, weight) is decoupled from real cost (here, CPU/memory), letting a single request balloon resource consumption far past what the runtime scheduler assumes.

### Finding Description
`handle_unsigned` is an unsigned, fee-free extrinsic (`ensure_none(origin)`) reachable by anyone who can construct a valid `GetRequestsWithProof` [3](#0-2) . Its `#[pallet::weight]` is a fixed `reads_writes(1, 2)` — i.e. treated as if it always does 1 storage read and 2 writes, independent of `message.requests.len()` [1](#0-0) .

`handle_get_requests`, however, iterates the full `requests` vector multiple times and per request:
- dedups and validates timeouts/source/dest metadata (cheap, linear) [4](#0-3) 
- runs `verify_state_proof` per `GetRequest`, which for EVM/Substrate/Pharos/Tendermint state machines decodes the whole proof, rebuilds a `TrieDB`/`MemoryDB`, and for every requested key resolves a value (each EVM account query clones the full contract proof and rebuilds a trie) [5](#0-4) 
- ABI-encodes every `GetResponse` for bandwidth metering [6](#0-5) 

None of this cost is reflected in the declared `Weight`, so the runtime's weight-based block-fullness accounting under-counts the real CPU/memory this call consumes. Because the call is unsigned, `validate_unsigned` also fully executes `handle_get_requests` on every full node that receives the extrinsic over the network before it is even included in a block [7](#0-6) , so the same unbounded-cost work runs unmetered on every peer's mempool validation path, not just the block author's.

This is the direct analog of the ConcreteCMS `download` handler: an authenticated/permissionless bulk operation (`ZipArchive::addFromString` + `file_get_contents` for every selected file / here, per-`GetRequest` trie rebuild + proof verification + ABI encoding) is not bounded or priced by its input size, so an attacker can submit a single "batch" whose real cost is orders of magnitude larger than what the system's cost model (declared extrinsic weight in Hyperbridge; expected file count in ConcreteCMS) accounts for.

### Impact Explanation
Because `handle_unsigned`'s declared weight never grows with the batch, the block-authoring/weight-limiting logic that Substrate uses to decide how many extrinsics fit in a block will admit far more real computational work than the block's weight budget assumes. Repeatedly submitting `GetRequestsWithProof` messages with very large `requests` vectors (backed by a correspondingly large but otherwise valid state proof) lets an unprivileged actor push actual per-block execution time well beyond the chain's intended per-block budget, and forces every full node's mempool (`validate_unsigned`) to re-do the same unbounded verification/encoding work for free before inclusion. This can degrade block production and message-processing throughput chain-wide, i.e. "a route unable to deliver messages" for legitimate GetResponse/POST traffic while the network is starved by oversized, underpriced batches — the accepted impact class for this analog per the validation rules.

### Likelihood Explanation
The call is unsigned and fee-free by design ("This allows users execute ISMP datagrams for free" applies to the sibling `pallet-ismp::handle_unsigned`, and `pallet-state-coprocessor::handle_unsigned` follows the identical unsigned/no-fee pattern) [8](#0-7) . Any relayer or third party that can produce a valid state proof covering many keys (which honest relayers already do for legitimate GET batches, per `tesseract/messaging/messaging/src/get_requests.rs`) can trivially inflate `requests.len()` and `keys.len()` up to the runtime's extrinsic/block-length limit. No signature, stake, or economic cost gates the size of the batch relative to its declared weight, so exploitation only requires normal relayer tooling plus a willingness to submit oversized batches.

### Recommendation
Make the declared `#[pallet::weight]` for `pallet_state_coprocessor::handle_unsigned` a function of the message's size — e.g. proportional to `message.requests.len()`, the total `keys.len()` across all requests, and the proof byte length (mirroring how `pallet_ismp`'s `handle_unsigned` already uses a computed `weight()` rather than a flat constant) — and/or enforce an explicit maximum on `requests.len()` / total keys per `GetRequestsWithProof`, rejecting oversized batches in `validate_unsigned` before any proof verification work is performed.

### Proof of Concept
1. As an unprivileged relayer, construct a legitimate `GetRequestsWithProof` whose `requests: Vec<GetRequest>` contains a very large number of valid `GetRequest`s (each with real, timed-in-future timeouts and correct source/dest metadata) together with a `source`/`response` `Proof` that legitimately covers all of their storage keys — sized up to the runtime's max extrinsic/block length.
2. Submit it via `StateCoprocessor::handle_unsigned` as an unsigned extrinsic. `validate_unsigned` runs `handle_get_requests` in full on every peer receiving the extrinsic over gossip [7](#0-6) , at a declared cost of only `reads_writes(1,2)` [1](#0-0) .
3. Repeat/parallelize submissions from multiple accounts; because the extrinsic is free and its declared weight is flat, the weight-based scheduler will happily admit many such extrinsics per block while the actual CPU cost (trie rebuilds, per-key verification, ABI encoding across all requests) scales linearly with the attacker-chosen batch size, exceeding the block's intended execution budget and degrading throughput/liveness for legitimate message delivery.

(Note: I could not execute this against a live node within this session; the finding is based on static analysis of the weight declaration versus the unbounded per-request work in `handle_get_requests`. A Devin session with access to a running test network would be needed to empirically measure block execution time/overweight-block behavior under this batch shape.)
