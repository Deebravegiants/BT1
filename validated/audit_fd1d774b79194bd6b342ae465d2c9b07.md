### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` by exposing `hmac` (from the `x-shopify-hmac-sha256` header) and `to_signable_string`, which returns **only the raw body**: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from unauthenticated HTTP headers via `shopify_header`, completely outside the byte range that is HMAC-verified: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` verifies only the body HMAC and then forwards the unverified `request.shop` (and `request.topic`) directly into `WebhookMetadata` handed to the app's handler as the tenant identity for the event: [3](#0-2) 

This is the exact "field acted on but not covered by the HMAC" analog: the equality that should hold is `shop_bound_by_signature == shop_acted_on`, but the gem instead checks `hmac(raw_body) == valid` and then trusts `header["shop-domain"]` unconditionally as the tenant identity.

### Impact Explanation
Because the header `shop-domain` (and `topic`) is never part of `to_signable_string`, any request bearing a **previously valid `(raw_body, hmac)` pair** will pass `Utils::HmacValidator.validate` regardless of which `shop-domain` header is attached to it. An unprivileged user who can install the app on their own store legitimately receives real webhook deliveries containing a valid `hmac` for a given body. That exact `(body, hmac)` pair can be replayed to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop, and the library will report the request as authentic and attribute the event to the victim tenant. Any app logic that uses `WebhookMetadata#shop` to select which tenant's data to mutate (e.g., `app/uninstalled`, GDPR `shop/redact`, `customers/data_request`, or business logic keyed by shop) can be tricked into acting against the wrong tenant — a cross-tenant integrity/confidentiality violation attributable to this gem's `Registry.process`/`Request` implementation, not to host-application misuse.

### Likelihood Explanation
Requires no secrets: only a normal, unprivileged interaction with the app (installing it or observing a webhook delivery it will legitimately receive for the attacker's own shop) followed by a replayed HTTP POST with a modified header, both trivially available to any internet user testing against a public webhook endpoint.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC-covered signable material (e.g., by concatenating the relevant headers with the body before computing/comparing the signature, mirroring how Shopify signs the full payload) so the verified bytes and the bytes the registry acts on are the same. At minimum, `Registry.process` should independently validate that `request.shop`/`request.topic` are consistent with data derived from a verified source (e.g., cross-check against an authenticated session/registration record) rather than trusting raw headers outright.

### Proof of Concept
1. App installs the webhook handler; attacker legitimately installs the same app on `attacker-shop.myshopify.com` and receives a webhook delivery:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid-for-body>`
   - Body: `{"id":123, ...}`
2. Attacker resends the identical HTTP POST to the app's public webhook endpoint but replaces only the header: `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` computes `Utils::HmacValidator.validate(request)`, which HMACs only `request.to_signable_string` (`@raw_body`) — unchanged from step 1 — so validation succeeds: [4](#0-3) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the event data actually belongs to `attacker-shop.myshopify.com`, letting the attacker inject spoofed events attributed to a shop they do not control.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
