### Title
Permanent market freeze from unchecked RAY value overflow during accrual - (File: common/src/rates/scaling.rs)

### Summary
A sufficiently large high-utilization market can grow its index until converting scaled debt back into RAY-denominated value exceeds `i128::MAX`. Because every pool mutation performs interest accrual before applying the requested action, the resulting `MathOverflow` permanently blocks withdrawals, repayments, liquidations, recapitalization, and index updates for that market.

### Finding Description
`Controller::update_indexes` is permissionlessly callable and forwards the selected `HubAssetKey` list to the pool. [1](#0-0)  The pool then loads each market and invokes `interest::global_sync`. [2](#0-1) 

Accrual calculates market utilization by multiplying the stored scaled debt and supply by their respective indexes through `scaled_to_original`. [3](#0-2)  That helper performs a checked `Ray::mul`, which panics on overflow. [4](#0-3) [5](#0-4) 

The in-repository regression test demonstrates the complete path: an unprivileged supplier deposits a billion whole 18-decimal tokens, another account borrows 98% against separate collateral, and a later `update_indexes` returns `MathOverflow` while the borrow index remains below `MAX_BORROW_INDEX_RAY`. [6](#0-5)  The same test then proves both `withdraw` and `repay` fail with `MathOverflow`. [7](#0-6) 

The freeze is structural rather than a one-off failed call: every operation leg calls `load_leg`, which calls `synced_market`, which unconditionally calls `global_sync` before the mutation. [8](#0-7)  Both withdrawal and repayment use `load_leg`, so they cannot bypass the overflowing accrual. [9](#0-8) [10](#0-9) 

### Impact Explanation
All user funds represented by the affected market become inaccessible: suppliers cannot withdraw, borrowers cannot repay or improve positions, and liquidators cannot execute debt reductions touching that market. Protocol revenue claims, recapitalization, and ordinary parameter updates that accrue first are also blocked. Since the stored scaled balances remain too large for every subsequent accrual, the freeze persists unless the deployed code is replaced with an arithmetic fix.

### Likelihood Explanation
Severity is Medium because exploitation requires extreme market size, sustained high utilization, and sufficient collateral to establish the borrow. However, no privileged action, oracle manipulation, leaked key, or external service failure is required: an unprivileged actor can create the state through ordinary `supply` and `borrow` calls, then trigger the overflow through `update_indexes`.

### Recommendation
Ensure every RAY-denominated intermediate used by accrual remains representable before the index-cap calculation. Concretely:

- Enforce market caps and scaled-total limits such that `scaled * MAX_BORROW_INDEX_RAY` and `scaled * MAX_SUPPLY_INDEX_RAY` cannot exceed `i128::MAX`.
- Use widened arithmetic for index/value calculations, or saturate intermediate debt value before calculating rewards and utilization.
- Apply the borrow-index ceiling before any multiplication that can overflow, while preserving conservative accounting for accrued interest.
- Add a deployment-level regression test proving repayment and withdrawal still succeed at the maximum admitted scaled balances and index boundary.

### Proof of Concept
The existing test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` provides a complete reproduction. [11](#0-10) 

Equivalent user-facing sequence:

1. Attacker calls `Controller::supply` with a billion-unit 18-decimal asset position.
2. A collateralized account controlled by the attacker calls `Controller::borrow` for 98% of that market.
3. The market remains at high utilization while interest compounds.
4. Any caller invokes `Controller::update_indexes(caller, vec![hub_asset])`.
5. `global_sync` attempts to calculate `borrowed * borrow_index`; the product exceeds `i128::MAX` and panics with `GenericError::MathOverflow`.
6. Subsequent `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `recapitalize`, and later `update_indexes` calls touching the same market repeat the same accrual and revert.

fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);

/// Loads a market cache and accrues interest through the current ledger time.
pub(crate) fn synced_market(env: &Env, hub_asset: &HubAssetKey) -> Cache {
    let mut cache = Cache::load(env, hub_asset);
    interest::global_sync(env, &mut cache);
    cache
}

/// Renews instance TTL, then loads and accrues the market.
pub(crate) fn renewed_market(env: &Env, hub_asset: &HubAssetKey) -> Cache {
    renew_instance(env);
    synced_market(env, hub_asset)
}

/// Validates `action.amount ≥ 0`, syncs the market, and returns (cache, scaled position).
pub(crate) fn load_leg(env: &Env, action: &PoolAction) -> (Cache, Ray) {
    require_nonneg_amount(env, action.amount);
    let cache = synced_market(env, &action.hub_asset);
    (cache, Ray::from(action.position.scaled_amount))
}
