### Title
Hostile HyperSwap pre-seed can force graduation LP to be deposited at an off-curve-close ratio - ([File: packages/contracts/src/Bonding.sol])

### Summary
The CVE describes a validation gap where a minimum-size check is enforced for one code path but silently skipped for a structurally similar path, letting malformed input reach logic that assumes it has already been validated. `Bonding`'s hostile-pre-seed defense (`_seedRebalancing` / `_pairRebalance` / `_routerDepositAndDispose`) has the analogous gap: the rebalance swap that is supposed to correct a pre-seeded HyperSwap V2 pair's ratio back to curve-close price is capped only by *this graduation's own inventory budget*, with no check that the swap actually achieved convergence before the code unconditionally proceeds to deposit liquidity.

### Finding Description
`finalizeGraduation` → `_seedUniswapV2Direct` routes a pre-seeded (mint-based) pair to `_seedRebalancing` [1](#0-0) . When the pool is judged "LT-rich" or "TOKEN-rich," it calls `_pairRebalance` with `maxSwap` capped by `_swapBudget`, which is 99% of *this graduation's own* remaining inventory (`tokensForLP` balance or `_ltSwapInventory`) — not derived from how large the attacker's hostile reserve actually is [2](#0-1) .

`_noFeeSwapInput` computes the theoretically required swap `s` to reach the target ratio and then clamps it to `maxSwap` with no re-check of whether the clamped swap actually gets the pool close to the curve-close ratio [3](#0-2) . `_pairRebalance` only bails out (`return false`) when the *no-fee input rounds to zero* or the *pair's quoted output rounds to zero* — i.e. only the "too small to matter" case is guarded, mirroring the CVE's pattern of validating one branch (undersized) while leaving the other (oversized/mismatched) branch unvalidated [4](#0-3) . When the swap executes but the budget cap prevented it from correcting a massively skewed pre-seed, execution falls through unconditionally to `_routerDepositAndDispose`, which deposits the remaining TOKEN/LT balances at whatever ratio the (still-skewed) pair now has, via `router.addLiquidity(..., 1, 1, lpLock_, ...)` [5](#0-4) . There is no check that the post-swap ratio is actually within a tolerance of `tokensForLP / ltFromPair` (the true curve-close price) before this deposit is finalized and permanently locked via `LPLock.recordLock` [6](#0-5) .

Because the reserve asset is an externally-tradable Leveraged Token (LT) that anyone can acquire in unbounded quantity, an attacker can pre-create the HyperSwap V2 TOKEN/LT pair and `pair.mint()` with a comparatively small amount of the launched Token (bounded by what they can buy pre-graduation off the curve) against an arbitrarily large amount of LT, producing a reserve ratio that overwhelms the graduation's own rebalance budget. The budget cap (`_swapBudget`) is sized purely against `Bonding`'s own graduation inventory, with no dependency on, or validation against, the magnitude of the attacker's pre-seeded reserves.

### Impact Explanation
This permanently locks the graduation's curve-raised LT and 250M-scale token allocation into a HyperSwap LP priced far from the true curve-close price, functionally donating value to the attacker's pre-existing LP position — a concrete instance of "an LP seeded away from the curve close price," one of the explicitly recognized impact classes for this contest. Because `LPLock.recordLock` is one-shot and `finalizeGraduation` cannot be re-run once `Lifecycle.Graduated` is set, the mispriced seeding is irreversible.

### Likelihood Explanation
The attacker's needed actions — buying Token off the bonding curve pre-graduation (a normal unprivileged `Zap.buy` action, bounded but nonzero) and creating/pre-seeding the HyperSwap V2 pair with an unbounded quantity of freely-tradable LT — are both explicitly listed as reachable, in-scope actions for an unprivileged/unrelated wallet in the contest rules. The natspec on `_seedUniswapV2Direct`/`_swapBudget` shows the team already reasoned carefully about DoS-resistance for hostile pre-seeds but frames the mitigation goal as "a hostile pre-seed of any shape cannot DoS `finalizeGraduation`" — i.e., liveness, not price-accuracy — so a scenario where the swap successfully executes but is too small to correct an extreme ratio is not explicitly excluded by the code's guards.

### Recommendation
After the rebalance swap in `_pairRebalance`, re-derive the post-swap reserve ratio and compare it against `targetN/targetD` within an explicit tolerance before allowing `_routerDepositAndDispose` to proceed; if the deviation exceeds tolerance (i.e., the swap budget was insufficient to correct a large hostile pre-seed), fall back to the safe `_seedDirectMint` path (as already done for the "too-small-to-swap" case) rather than depositing at a still-skewed ratio.

### Proof of Concept
1. Attacker buys a bounded amount of `Token` pre-graduation via `Zap.buy`, staying just under the graduation threshold so `canGraduate` remains false.
2. Attacker (or anyone) calls HyperSwap V2 Factory to create the `TOKEN/LT` pair for this not-yet-graduated token, then transfers a large amount of LT (freely acquirable/mintable via BounceTech) plus their bounded Token balance into the pair and calls `pair.mint(attacker)`, establishing an extremely LT-skewed reserve ratio.
3. Attacker (or any other trader) pushes the curve to the graduation threshold via `Zap.buy`/`Bonding.triggerGraduation`, entering `Lifecycle.Graduating`.
4. Anyone calls `Bonding.finalizeGraduation(tokenAddress)`. `_seedUniswapV2Direct` detects `totalSupply != 0` and routes to `_seedRebalancing`; because `reserveLT` is enormous relative to `ltFromPair`/`tokensForLP`, the pool is judged "LT-rich," and `_pairRebalance`'s swap is capped by `_swapBudget(tokensForLP balance)`, insufficient to correct the ratio.
5. `_routerDepositAndDispose` deposits the graduation's remaining Token/LT at the still-skewed post-swap ratio into the attacker's pre-existing LP, permanently locking the mispriced position via `LPLock.recordLock`.

    function _pairRebalance(
        RebalanceParams memory p
    ) internal returns (bool) {
        uint256 s = _noFeeSwapInput(p.reserveIn, p.reserveOut, p.targetN, p.targetD, p.maxSwap);
        if (s == 0) return false;

        // Quote from the pair so the output tracks its live fee; a value
        // derived from a stale fee rate would trip the pair's K-check.
        uint256 expectedOut = IUniswapV2Pair(p.pair).getAmountOut(s, p.tokenIn);
        if (expectedOut == 0) return false;

        IERC20(p.tokenIn).safeTransfer(p.pair, s);
        (uint256 amount0Out, uint256 amount1Out) = p.tokenInIs0 ? (uint256(0), expectedOut) : (expectedOut, uint256(0));
        IUniswapV2Pair(p.pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
        return true;
    }

    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
