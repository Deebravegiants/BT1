## Title
Tokens Received via Arbitrary Emporium Calls Outside the Declared `erc20TokenAddresses` Set Are Permanently Locked - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction()` executes a caller-supplied list of arbitrary external calls (`op.endpoint.call{value: op.value}(op.callData)`) and afterward only measures balance deltas for the token set declared in `circomData.erc20TokenAddresses`. This mirrors exactly the reported `SellerFinancing.sol` class of bug: when the invoked contract (e.g. a marketplace/exchange call analogous to fulfilling a Seaport order) returns any asset that is not one of the pre-declared tracked tokens, that asset is received by the Emporium contract but never accounted for, never converted into a UTXO, and never becomes withdrawable — it is permanently locked.

### Finding Description
In `runAction()`: [1](#0-0) 
balances are snapshotted only for `circomData.erc20TokenAddresses` before the loop of arbitrary `op.endpoint.call` invocations, and the post-call reconciliation loop again only iterates over that same fixed array: [2](#0-1) 

`handleOut()` is the only mechanism that turns a balance increase into a spendable UTXO returned to the user/relay, and it is keyed strictly by index `i` into `circomData.erc20TokenAddresses`: [3](#0-2) 

`circomData.erc20TokenAddresses` is a prover/signer-chosen, fixed-length array whose length is fixed by `dimensions.tokenNumber` and checked only for internal consistency, not against what the invoked external call might actually return: [4](#0-3) 

Because the Emporium's stateless-interaction path allows calling *any* `op.endpoint` with *any* `op.callData` (subject only to blocking `callHinkalWallet`/`doSendToRelay` selectors): [5](#0-4) 
a user (or relay acting on the user's signed op set) can construct an operation that fulfills an order/swap on an arbitrary external protocol that pays out in a token not listed in `circomData.erc20TokenAddresses`. That payout lands on the Emporium contract's balance, is invisible to the `balancesBefore`/`balancesAfter` diff (which only enumerates the declared tokens), is never wrapped into a UTXO via `handleOut`, and there is no owner/rescue/sweep function anywhere in `ExternalActionBaseUpgradeable.sol` or `EmporiumUpgradeable.sol` to recover it — it sits in the contract forever.

This breaks the balance equality the protocol relies on: total value entering/leaving Hinkal-tracked balances for a `transact()` call must equal the sum of UTXOs created/consumed. Any asset received outside the declared token vector is silently excluded from that equation and permanently stranded, exactly as described in the external report for `SellerFinancing.sol`'s missing `order.parameters.offer.length == 1` check.

### Impact Explanation
This is a Critical/High-severity permanent freezing of user funds: assets paid out by any external protocol the Emporium interacts with, if not enumerated in advance in `circomData.erc20TokenAddresses`, cannot ever be withdrawn by the depositor, the relay, or anyone else, since no rescue mechanism exists in the contract. The loss is not confined to the attacker's own shielded balance — any user relying on the Emporium's generic call-execution feature to interact with an external marketplace/exchange risks having a portion of the proceeds (e.g., an unexpected reward token, a fee rebate, dust, or a token swap that pays in a different token than expected) become permanently locked.

### Likelihood Explanation
Likelihood is moderate to high: the Emporium is explicitly designed as a generic call-execution primitive to interact with arbitrary external contracts (marketplaces, DEXs, aggregators), and users/relays construct the `erc20TokenAddresses` list themselves off-chain before generating the proof. Any mismatch between what the external call actually returns and what was declared up front — whether due to protocol behavior the integrator didn't anticipate, a multi-asset settlement, or a bug in the calling logic — results in stuck funds with no code path to recover them.

### Recommendation
Add a strict post-call validation that no unaccounted asset balance changes occurred on the Emporium contract outside of `circomData.erc20TokenAddresses`, or alternatively require that any token/ETH received by an operation be explicitly declared and slotted for UTXO creation. As a defense-in-depth measure (consistent with the client's fix in the referenced report — restricting Seaport `offer` length to 1), consider adding an owner-controlled sweep function scoped to non-tracked tokens as a fallback recovery mechanism, and require external calls used in `runAction` to only interact with pre-vetted endpoints/selectors whose settlement tokens are known and match the declared `erc20TokenAddresses`.

### Proof of Concept
1. A signer builds an `EmporiumStack` with a single stateless operation targeting an external marketplace contract `M` and constructs `circomData.erc20TokenAddresses = [tokenA]` (the token they expect to spend/receive).
2. `M`'s fulfillment logic, however, settles the order by paying out `tokenB` (not `tokenA`) to `msg.sender` (the Emporium contract) — analogous to a Seaport order whose `offer` array is not limited to WETH.
3. `EmporiumUpgradeable.runAction()` executes the call successfully via `op.endpoint.call{value: op.value}(op.callData)`.
4. The post-call reconciliation loop only checks `balancesBefore`/`balancesAfter` for `tokenA`; the received `tokenB` balance increase is never observed.
5. `handleOut()` is never invoked for `tokenB`, so no UTXO is minted for it, and `tokenB` remains in the Emporium contract.
6. No function in `EmporiumUpgradeable.sol` or its base contracts allows withdrawing `tokenB` — it is permanently locked.

    function handleOut(
        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
    ) internal returns (UTXO memory outUtxo) {
        // total change can be less than zero if there was some balance before the call -> that's why we have <=
        if (balanceChange <= 0) {
            return outUtxo;
        }

        transferERC20TokenOrETH(
            circomData.erc20TokenAddresses[i],
            msg.sender,
            uint256(balanceChange)
        );

        outUtxo = UTXO(
            uint256(balanceChange),
            circomData.erc20TokenAddresses[i],
            circomData.stealthAddressStructure,
            circomData.timeStamp
        );
    }
