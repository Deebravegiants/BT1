### Title
`IntentGatewayV2.placeOrder()` on the Tron deployment does not refund excess native-token (TRX) overpayment - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder()` accepts `msg.value` to fund native-token order inputs and the native-to-fee-token swap for `order.fees`, but unlike the canonical EVM implementation, it never returns any leftover `msgValue` to the caller. Any TRX sent in excess of what is strictly consumed by native inputs and the Uniswap fee swap is silently retained by the contract with no user-facing recovery path — the same overpayment-not-refunded bug class described in the external report for `mintWithEth`/`mintUsername`.

### Finding Description
In the reference/canonical implementation, `IntentGatewayV2.placeOrder()` tracks the running `msgValue` as it consumes native input legs and the fee-token swap, and explicitly refunds any leftover amount at the end: [1](#0-0) 

The Tron deployment (`evm/tron/contracts/apps/IntentGatewayV2.sol`) implements the identical `placeOrder()` flow — decrementing `msgValue` for native predispatch assets, native inputs, and the `swapETHForExactTokens` fee swap — but the function ends immediately after emitting `OrderPlaced` with no equivalent refund step: [2](#0-1) 

Specifically:
- Native inputs are debited from `msgValue` via `msgValue -= order.inputs[i].amount` [3](#0-2) 
- The fee swap consumes `msgValue` via `swapETHForExactTokens{value: msgValue}` (note: it passes the *entire remaining* `msgValue`, not a bounded amount, and the returned `amounts[0]` actually spent is never captured/subtracted from `msgValue`, unlike the canonical version which does `msgValue -= amounts[0]`) [4](#0-3) 
- No `_sendValue(msg.sender, msgValue)` or equivalent refund call exists anywhere in `placeOrder()`.

Because `receive() external payable {}` accepts arbitrary TRX [5](#0-4) , and the contract's only outbound-fund mechanisms are `withdraw()` (bound to specific escrowed order amounts recorded in `_orders[commitment][token]`) and the governance-only `SweepDust` action reachable solely through `onAccept` from Hyperbridge/admin [6](#0-5) , any TRX sent beyond what is metered into `_orders[...]` is untracked and permanently stuck — it is neither escrowed against the commitment nor refundable by the depositing user.

This is directly analogous to the reported bug class: a permissionless, single-transaction call (`placeOrder`) that accepts `msg.value >=`-style overpayment for a real charge, with no excess-refund logic, resulting in unintentional and unrecoverable loss of user funds.

### Impact Explanation
Any user who overestimates the native-token amount required for `order.fees`'s Uniswap swap (a common defensive practice, since the exact swap cost is not knowable in advance without simulating the AMM state at execution time) or otherwise sends surplus TRX with `placeOrder` permanently loses that surplus to the contract. Funds are not stolen by an attacker but are irrecoverably locked/frozen from the user's perspective — meeting the "permanent freezing of funds" bar for this scan's validation criteria. This affects the Tron deployment of the Intent Gateway, a production token-bridging/intents contract reachable by any unprivileged order placer.

### Likelihood Explanation
Likelihood is Medium-to-High: the documented SDK/UI flow explicitly instructs callers to pad the native-token value sent for solver-fee swaps beyond the exact quote to tolerate slippage ("Send 5 ETH for a fee swap that should cost much less" pattern is tested and expected in the canonical contract's test suite), so overpayment during `placeOrder` is a normal, expected user behavior — not an edge case. Every such overpayment on the Tron deployment is lost by default, with no special conditions required to trigger the bug.

### Recommendation
Mirror the canonical EVM contract's refund logic in the Tron `IntentGatewayV2.placeOrder()`:
1. Capture the actual amount spent by `swapETHForExactTokens` (its return value) and subtract it from `msgValue`, instead of assuming the entire `msgValue` was consumed.
2. After all native consumption (predispatch, inputs, fee swap) is accounted for, add a refund step at the end of `placeOrder()`:
```solidity
if (msgValue > 0) {
    (bool sent,) = msg.sender.call{value: msgValue}("");
    if (!sent) revert InsufficientNativeToken();
}
```
3. Apply the same audit to any other native-token-accepting entry points in the Tron contract (e.g., `cancelOrder`'s dispatch-fee payment paths) to ensure no leftover `msg.value` is stranded.

### Proof of Concept
1. User calls `placeOrder(order, graffiti)` on the Tron `IntentGatewayV2` with `order.fees = X` (paid via native-token swap) and sends `msg.value = X_estimate` where `X_estimate` comfortably exceeds the actual TRX needed to swap for `X` fee-tokens (a normal slippage-buffer practice, as documented and tested for the canonical EVM contract).
2. Inside `placeOrder`, `swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), block.timestamp)` executes the swap, consuming only the TRX actually required by the AMM, but the function neither reads `amounts[0]` nor recalculates the true leftover.
3. `placeOrder()` returns without any transfer back to `msg.sender`; the difference between `msg.value` and the TRX actually spent remains in the contract's balance.
4. There is no user-callable function to reclaim this residual TRX: `withdraw()` only releases amounts explicitly recorded in `_orders[commitment][token]` (which reflects only `order.inputs`/`order.fees`, not swap change), and `SweepDust` is only triggered by a Hyperbridge/governance-originated `onAccept` message, not by the depositor.
5. The overpaid TRX is permanently unrecoverable by the user who sent it.
