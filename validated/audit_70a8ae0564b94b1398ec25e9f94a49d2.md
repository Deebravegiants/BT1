### Title
Zone-B vault-read restriction can be bypassed via stale DON-membership cache during a capabilities-registry lookup failure - ([File: core/capabilities/vault/zone_b_restriction.go])

### Summary
`zoneBRestrictor.isZoneBWorkflowDON` caches the last successfully-resolved "is this WorkflowDonID in the zone-b family" result and falls back to that cached value whenever a live capabilities-registry lookup fails. If a DON's family membership changes (e.g. a workflow DON is moved into the `zone-b` family, which is defined specifically to further-restrict which workflow owners may read vault secrets) at the same time the capabilities-registry view is transiently unavailable, the enforcement point re-uses the stale, pre-reclassification membership instead of re-validating the DON's current scope, exactly mirroring the Mattermost bug class of failing to re-check a resource's current scope before allowing/denying an action on it.

### Finding Description
`enforce()` in `core/capabilities/vault/zone_b_restriction.go` gates `vault.GetSecrets` reads: if the calling `WorkflowDonID` is currently in the `zone-b` family, the requesting workflow owner must be present in a per-owner allowlist (`ownerAllowed`), otherwise the read is denied. [1](#0-0) 

Membership is meant to be resolved "authoritatively from the node's own capabilities registry view, never from caller-supplied metadata" [2](#0-1) 

but `isZoneBWorkflowDON` falls back to a `zoneCache[workflowDonID]` value—the last successfully resolved membership—whenever the live `DONByID` lookup errors: [3](#0-2) 

This cache is never invalidated when a DON's `Families` change on-chain/in-registry; it is only ever overwritten by the *next successful* lookup. Consequently, if:
1. A `WorkflowDonID` is first resolved while it is **not** in `zone-b` (e.g. `zone-a`), caching `isZoneB=false`, and
2. That DON is later moved into the `zone-b` family (analogous to a Mattermost channel being moved into a different team), and
3. A `DONByID` lookup fails during that window (the code explicitly documents this as an expected, non-rare occurrence: "not yet synced after startup, or nil mid-update")

then `enforce()` uses the stale `isZoneB=false` cached value and skips the `ownerAllowed` allowlist check entirely, allowing a non-allowlisted workflow owner to read vault secrets that the zone-b restriction was specifically designed to block for them.

The unit tests in `zone_b_restriction_test.go` explicitly validate only the "safe" direction of this fallback (a DON that stays zone-a or stays zone-b keeps the same decision across an outage) but do not cover — and the implementation does not defend against — a re-classification occurring concurrently with an outage, which is the precise TOCTOU gap. [4](#0-3) 

### Impact Explanation
A successful exploitation lets a workflow owner who is not on the `VaultZoneBGetSecretsAllowed` allowlist read vault secrets they should be barred from reading once their DON is reclassified into the restricted `zone-b` family, i.e. an allowlist/authorization bypass leading to secret disclosure. This matches the "allowlist bypass" / secret-disclosure impact category called out for this analog class.

### Likelihood Explanation
Exploitation requires two conditions to coincide: (1) a DON transitioning into the `zone-b` family, and (2) a capabilities-registry lookup failure for that DON occurring after the transition but before a fresh successful resolution repopulates the cache. The code's own comments acknowledge such registry unavailability windows are expected in practice (startup sync, mid-update `nil` registry), so this is a plausible, naturally-occurring race rather than a purely theoretical one, though it is not trivially triggerable on demand by an attacker and requires the DON reclassification timing to line up with an outage.

### Recommendation
- Invalidate or bound the trust of `zoneCache` entries with a TTL, and/or fail closed (treat as zone-b, the more restrictive outcome) rather than fail-open when serving a cached value during a registry outage, so uncertainty always resolves toward the safer (restricted) decision.
- Proactively invalidate/refresh cache entries when the capabilities registry pushes a family-membership change for a DON, instead of only updating on the next successful lookup triggered by traffic from that DON.
- Add a regression test that resolves a DON as zone-a, changes its registry family to zone-b, then forces a `DONByID` failure, asserting the read is denied (not silently allowed via the stale zone-a cache entry).

### Proof of Concept
1. Configure `VaultZoneBWorkflowGetSecretsRestrictEnabled=true` and leave workflow owner `O` off the `VaultZoneBGetSecretsAllowed` list.
2. Have workflow DON `D` initially registered in family `zone-a`; issue a `vault.GetSecrets` request from owner `O` via `D` — `isZoneBWorkflowDON` resolves `false` and caches `zoneCache[D]=false`.
3. Update the capabilities registry so `D`'s `Families` now includes `zone-b`.
4. Trigger (or wait for) a transient `DONByID` failure for `D` (e.g. "metadataRegistry information not available" during a registry sync window).
5. Issue another `vault.GetSecrets` request from owner `O` via `D` during that failure window: `isZoneBWorkflowDON` returns the cached stale value `false`, `enforce()` skips the `ownerAllowed` check, and owner `O`'s read succeeds despite `D` now being a restricted zone-b DON and `O` not being allowlisted.

func (z *zoneBRestrictor) enforce(ctx context.Context, workflowDonID uint32) error {
	enabled, err := z.restrictEnabled.Limit(ctx)
	if err != nil {
		return fmt.Errorf("could not evaluate zone-b vault read restriction gate: %w", err)
	}
	if !enabled {
		return nil
	}

	isZoneB, err := z.isZoneBWorkflowDON(ctx, workflowDonID)
	if err != nil {
		// Fail closed: if we cannot authoritatively resolve the caller's zone, do
		// not proceed. The registry is in-process, so this only fires for an
		// unknown/unregistered WorkflowDonID.
		return err
	}
	if !isZoneB {
		return nil
	}

	if err := z.ownerAllowed.AllowErr(ctx); err != nil {
		return fmt.Errorf("zone-b workflow DON may only read vault secrets for allowlisted workflow owners: %w", err)
	}
	return nil
}

func (z *zoneBRestrictor) isZoneBWorkflowDON(ctx context.Context, workflowDonID uint32) (bool, error) {
	don, err := z.capabilitiesRegistry.DONByID(ctx, workflowDonID)
	if err != nil {
		// The registry view can be transiently unavailable (e.g. not yet synced
		// after startup, or nil mid-update: DONByID returns "metadataRegistry
		// information not available"). That error is not specific to zone-b
		// callers, so failing closed here would block every vault GetSecrets read
		// DON-wide. Fall back to the last successfully-resolved membership for this
		// DON; only a never-before-resolved DON fails closed.
		if cached, ok := z.cachedZoneMembership(workflowDonID); ok {
			z.lggr.Warnw("capabilities registry lookup failed; using cached zone-b membership",
				"workflowDonID", workflowDonID, "isZoneB", cached, "err", err)
			return cached, nil
		}
		return false, fmt.Errorf("could not resolve caller workflow DON %d for zone-b vault read restriction: %w", workflowDonID, err)
	}
	// Case-insensitive match: family casing may vary across registry sources.
	isZoneB := slices.ContainsFunc(don.Families, func(family string) bool {
		return strings.EqualFold(family, zoneBFamily)
	})
	z.storeZoneMembership(workflowDonID, isZoneB)
	return isZoneB, nil
}

// MUST-2: a transient capabilities registry outage must not fail every vault
// read DON-wide. Once a DON's zone membership has been resolved, a subsequent
// registry lookup failure falls back to the cached value instead of erroring;
// a DON never resolved before still fails closed. Crucially, the cached value
// preserves the security decision in both directions: a cached zone-b DON stays
// denied during the outage rather than slipping through.
func TestZoneBRestrictor_RegistryOutageUsesCachedMembership(t *testing.T) {
	t.Parallel()
	const restrictEnabled = `{"global":{"VaultZoneBWorkflowGetSecretsRestrictEnabled":"true"}}`

	t.Run("cached zone-a membership survives outage (still allowed)", func(t *testing.T) {
		t.Parallel()
		z, fake := newOutageTestRestrictor(t, restrictEnabled)
		md := capabilities.RequestMetadata{WorkflowOwner: "0xdeadbeef", WorkflowDonID: zoneADonID}
		ctx := md.ContextWithCRE(t.Context())

		// Warm the cache while healthy: zone-a caller is allowed.
		require.NoError(t, z.enforce(ctx, zoneADonID))
		// Outage: cached (non-zone-b) membership keeps the read allowed.
		fake.fail.Store(true)
		require.NoError(t, z.enforce(ctx, zoneADonID))
	})

	t.Run("cached zone-b membership survives outage (still denied)", func(t *testing.T) {
		t.Parallel()
		z, fake := newOutageTestRestrictor(t, restrictEnabled)
		md := capabilities.RequestMetadata{WorkflowOwner: "0x" + allowlistedOwner, WorkflowDonID: zoneBDonID}
		ctx := md.ContextWithCRE(t.Context())

		// Warm the cache while healthy: zone-b + non-allowlisted owner is denied,
		// and the zone-b membership is cached.
		require.ErrorContains(t, z.enforce(ctx, zoneBDonID), "allowlisted workflow owners")

		// Outage: the cached zone-b membership must still be enforced. The caller
		// is denied via the allowlist, not allowed through by a resolve failure.
		fake.fail.Store(true)
		err := z.enforce(ctx, zoneBDonID)
		require.ErrorContains(t, err, "allowlisted workflow owners")
		require.NotContains(t, err.Error(), "could not resolve caller workflow DON")
	})
