### Title
Live re-read of `challengePeriod` in `HandlerV2` lets a routine `updateHostParams` retroactively shrink the dispute window for already-pending state commitments - (File: evm/src/core/HandlerV2.sol)

### Summary
`HandlerV2.handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts` all gate message processing on `host.challengePeriod()` compared against `block.timestamp - host.stateMachineCommitmentUpdateTime(height)`. `challengePeriod` is a single global value stored in `EvmHost`'s `_hostParams` and can be changed at any time via `updateHostParams`/`updateHostParamsInternal`, which applies immediately to every state commitment already stored (including ones stored before the update). No commitment stores its own snapshot of the challenge period that was in effect when it was created. This is the same bug class as the Lido `updateBondCurve` finding: a global parameter update is applied "live" to already-existing per-item state whose safety invariant depended on the parameter value at creation time, instead of being applied only prospectively or forcing a synchronized recompute.

### Finding Description
`EvmHost.updateHostParams` (restricted to `_hostParams.hostManager`, i.e. cross-chain governance) calls `updateHostParamsInternal`, which unconditionally overwrites `_hostParams.challengePeriod = params.challengePeriod;` with no interaction with, or awareness of, currently pending (not-yet-finalized) state machine heights: [1](#0-0) [2](#0-1) 

Every message-processing entrypoint in `HandlerV2` reads this same mutable, global `challengePeriod` at call time and compares it against the *stored* `stateMachineCommitmentUpdateTime` for the specific height being proven: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

The `stateMachineCommitmentUpdateTime` is fixed at the moment the intermediate state was stored by `handleV2Consensus` (in `HandlerV2.sol`) via `host.storeStateMachineCommitment`, and never changes afterward: [7](#0-6) 

Because `challengePeriod` is read live rather than being snapshotted per-commitment (analogous to the bond curve being applied without forcing a synchronized recompute of the "depositable" state derived from it), a change to `challengePeriod` retroactively changes the security guarantee that relayers, fishermen, and downstream apps were relying on for commitments that already exist:

- If governance reduces `challengePeriod` (e.g., from 6 hours to 1 hour, or to `0`), every state commitment stored under the old, longer window instantly becomes eligible for message processing — even though fishermen only budgeted for the shorter elapsed time and had not yet had the full window they were promised to submit a fraud/veto proof. Setting it to `0` fully disables the delay check (`challengePeriod != 0 && challengePeriod > delay`), immediately unlocking every currently pending commitment for processing.
- Conversely, increasing `challengePeriod` retroactively extends the required wait for commitments already past their originally-expected window, freezing legitimate in-flight messages/requests beyond their intended timeline (a liveness/freezing issue for pending cross-chain messages).

This directly parallels the report's root cause: a governance-controlled parameter update ("bond curve" there, "challengePeriod" here) is not decoupled from already-existing per-item state ("NO's unbonded/depositable amounts" there, "pending state commitment's dispute window" here), so the same governance action inconsistently changes the effective security posture of already-created items without any two-step/snapshot mechanism to keep them in sync.

### Impact Explanation
If `challengePeriod` is lowered as part of a routine or well-intentioned governance parameter tuning (not necessarily a malicious admin action — e.g., adjusting for improved sync-committee/BEEFY finality assumptions), any state commitments already stored but not yet past the *old* challenge window become immediately processable. This means requests/responses proven against those commitments can be delivered through `HandlerV2.handlePostRequests` / `handleGetResponses` before fishermen had their originally-promised opportunity to veto a fraudulent or byzantine commitment, i.e. before the security assumption underlying `stateMachineCommitmentUpdateTime`-based finality is actually satisfied. This is a "premature finality" / unsound state-commitment-timing bug that can allow message delivery based on a state commitment that has not been given its intended dispute window — matching the "unsound state commitment" / "forged message delivery" acceptance criteria, since messages can be finalized and dispatched to destination `IApp` modules (including token bridges/intents gateways reachable from `onAccept`) sooner than the protocol's documented security model guarantees.

### Likelihood Explanation
Medium likelihood: this requires a legitimate `updateHostParams` governance call that changes `challengePeriod` while state commitments are in-flight (a normal, expected operational event — parameter tuning is documented as routine, e.g. in the `EvmHostParamUpdate` struct and `host-executive` pallet's `update_host_params` extrinsic), not an attacker-controlled or malicious governance path. Any coordinated reduction of `challengePeriod` without pausing new-message processing during the transition window will affect all currently pending commitments simultaneously, matching the "medium severity, systemic inconsistency" classification of the original report.

### Recommendation
Snapshot `challengePeriod` per state-machine commitment at the time it is stored (e.g., store it alongside `stateMachineCommitmentUpdateTime`/`StateCommitment`), and have `HandlerV2` compare `delay` against the snapshotted value instead of the live `_hostParams.challengePeriod`. Alternatively, apply `challengePeriod` changes only to commitments stored after the update (a "2-step" activation: queue the new value, and only use it for `intermediate.height` values whose consensus update happens after the change is applied), so that already-pending commitments are always evaluated against the challenge period that was in effect when they were created.

### Proof of Concept
1. Governance calls `EvmHost.updateHostParams` with `challengePeriod = 6 hours` (baseline). A relayer submits a consensus update via `HandlerV2.handleV2Consensus`, which calls `host.storeStateMachineCommitment` for height `H`, setting `stateMachineCommitmentUpdateTime[H] = T0`.
2. At `T0 + 1 hour`, governance (through `hostManager`, a routine parameter update, not a compromised key) calls `updateHostParams` again, this time with `challengePeriod = 0` (or any value ≤ 1 hour) for legitimate operational reasons.
3. Immediately after, anyone calls `HandlerV2.handlePostRequests` with a valid MMR proof anchored at height `H`. The check `challengePeriod != 0 && challengePeriod > delay` at `evm/src/core/HandlerV2.sol:184-185` now passes (or is bypassed entirely when `challengePeriod == 0`), even though fishermen only had 1 of the originally-promised 6 hours to veto commitment `H`.
4. The request is dispatched to the destination `IApp` (e.g., a token bridge or `IntentGatewayV2`) via `host.dispatchIncoming`, finalizing effects (mints, escrow releases) based on a state commitment that never received its originally-guaranteed challenge window.
