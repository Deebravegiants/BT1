## Analog Found: Front-runnable public order-matching in `IntentGatewayV2.fillOrder`

### Title
Public, unauthenticated `fillOrder` permits front-running of solver fills when `solverSelection` is disabled - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.fillOrder` is a `public payable` function that anyone can call to fulfill a placed intent order and claim the escrowed input tokens, mirroring the reported `executeMatchedOrders` pattern: order-matching logic is exposed on a public function with no caller-identity binding by default. Front-running protection (`solverSelection`) exists but is opt-in per-gateway-deployment, so on any deployment where it is disabled (the default `Params.solverSelection = false`), a solver's pending fill transaction is visible in the mempool and can be copied and outbid.

### Finding Description
`fillOrder(Order calldata order, FillOptions calldata options)` only checks the order hasn't expired, isn't already filled, and — conditionally — that the caller matches a solver staged via `select()` when `_params.solverSelection` is true: [1](#0-0) 

When `solverSelection` is false (the flag governance/deployer must explicitly opt into), the block at lines 464-472 that enforces `msg.sender == authorizedSolver` is skipped entirely — `fillOrder` becomes fully permissionless order matching, exactly the class described in the reported issue. A legitimate solver who has identified a profitable spread (their output tokens are worth less than the escrowed input they'll receive) submits `fillOrder` to the network; any observer of the pending transaction can resubmit byte-identical `order`/`options` calldata from their own address with a higher gas price/fee, land first, and become `_filled[commitment]`, thereby capturing the escrowed input tokens (and, per docs, a share of `surplusShareBps`) that the original solver had priced in.

The project's own documentation acknowledges this exact bug class exists and needs an explicit toggle to close: "When `solverSelection` is enabled ... orders are protected from unauthorized fills" and the `SolverAccount` fast-path comment explicitly reasons about bid front-running/griefing risk (a related but narrower case, guarded only inside `SolverAccount`, not inside the gateway itself): [2](#0-1) [3](#0-2) 

### Impact Explanation
On any `IntentGatewayV2` deployment with `solverSelection` disabled, a front-runner can systematically snipe every profitable fill visible in the public mempool, taking the escrowed input tokens and surplus share while forcing the original, capital-committed solver to lose gas and the arbitrage opportunity. Because solvers must pre-fund their fill transactions with real output tokens, this is not a costless griefing vector for the attacker, but it is a real, repeatable value-extraction path against solvers who do the price-discovery work, which can suppress solver participation and liquidity/fill quality for users across the whole Intent Gateway market — a medium-severity, protocol-level MEV/front-running exposure of exactly the shape described in the source report.

### Likelihood Explanation
High for any gateway configured with `solverSelection = false`: `fillOrder` calldata is fully public once broadcast, requires no solver-specific secret, and a copy-and-outbid strategy is a standard, low-cost MEV pattern. The protocol already had to build the `select()`/`SolverAccount`/session-key machinery specifically to close this gap, confirming the underlying exposure is real whenever that opt-in mitigation is not enabled.

### Recommendation
Require `solverSelection` (or an equivalent binding of the filler identity, e.g., a commit-reveal or session-key authorization) to be mandatory rather than optional, or otherwise ensure `fillOrder` cannot be executed by an arbitrary address that did not originate the fill intent — e.g., by defaulting `solverSelection` to `true` for all new deployments and treating disabling it as an explicit, documented risk acceptance.

### Proof of Concept
1. Deploy `IntentGatewayV2` with `Params.solverSelection = false` (as in `testFillOrderExpired`/base test setup which use `session: address(0)`), per `evm/tests/foundry/IntentGatewayV2Test.sol`.
2. A user places an `Order` escrowing input tokens (`placeOrder`), per lines 391-415 of `IntentGatewayV2.sol`.
3. Solver A builds and broadcasts a `fillOrder(order, options)` transaction supplying the required output tokens.
4. Attacker observes Solver A's pending transaction in the mempool, copies `order` and `options` verbatim, funds their own account with the same output tokens, and submits an identical `fillOrder` call with a higher gas price.
5. Attacker's transaction is mined first; `_filled[commitment]` is set to the attacker, and Solver A's later transaction reverts with `Filled()` — the attacker has captured the escrow (and surplus share) that Solver A intended to receive.

    function fillOrder(Order calldata order, FillOptions calldata options) public payable nonReentrant {
        uint256 blockNumber = _blockNumber();
        if (order.deadline < blockNumber) revert Expired();
        // The solver's own bound on how long its quoted price stands. Zero means unbounded,
        // which is the right default for a solver filling directly — it is only at risk from
        // its own staleness. It matters for a bid signed through the coprocessor, where the
        // order placer chooses the moment of execution and nothing else caps the wait.
        if (options.validUntil != 0 && blockNumber > options.validUntil) revert FillExpired();
        bytes32 commitment = keccak256(abi.encode(order));

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain && orderSource != currentChain) revert WrongChain();
        if (!isSameChain && orderDest != currentChain) revert WrongChain();

        if (_filled[commitment] != address(0)) revert Filled();

        if (_params.solverSelection) {
            bytes32 storedSelectionHash;
            assembly {
                storedSelectionHash := tload(commitment)
            }

            bytes32 expectedSelectionHash = keccak256(abi.encode(msg.sender, order.session));
            if (storedSelectionHash != expectedSelectionHash) revert Unauthorized();
        }
