### Title
Webhook `shop` identity not covered by HMAC, allowing cross-tenant shop-domain spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking the HMAC of the raw request body only, then passes the caller-supplied `shop-domain` header value — which is never covered by that HMAC — into the handler as the trusted tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC solely against `to_signable_string` using `Context.api_secret_key` [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` values are all read directly from HTTP headers and are not part of the signed payload [3](#0-2) .

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity, forwarding it unchanged into `WebhookMetadata`, which the host application's `WebhookHandler#handle` uses to key data/session lookups for the store: [4](#0-3) . `WebhookMetadata` declares `shop` as a plain `String` field with no cryptographic binding to the signed body: [5](#0-4) .

Because the app's `client_secret` (`api_secret_key`) is the same across every shop that installs the app, a legitimate webhook payload/HMAC pair delivered to shop A remains a *valid* signature for that same body when replayed with the `shop-domain` header rewritten to shop B — the HMAC check in `Utils::HmacValidator.validate` passes identically. This breaks the identity binding `shop authenticated == shop trusted by the handler`: the gem authenticates only the body bytes, not the header that callers use as the tenant key.

### Impact Explanation
This lets an unprivileged party who can capture/replay their own genuinely-signed webhook (e.g., a merchant who installed the app, or anyone who can observe a webhook delivery to any tenant of a multi-tenant app) forge a webhook that the gem reports as originating from an arbitrary other shop domain, since `request.shop`/`WebhookMetadata#shop` is not bound to the HMAC. Any host application that follows this gem's documented pattern of using `data.shop` to select the tenant/session (a normal, expected usage of this API) can be tricked into writing attacker-controlled body content under another merchant's identity — cross-tenant data injection/impersonation.

### Likelihood Explanation
Likelihood is bounded by the need for the attacker to possess at least one validly-signed webhook body from Shopify (i.e., be an installer of the target app, or intercept an unencrypted delivery), then modify only the `shop-domain` header and resubmit to the app's webhook endpoint — no access token, `client_secret`, or privileged account is required, satisfying the "unprivileged internet user" bar.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed material, or otherwise cryptographically bind `request.shop` to the verified payload before constructing `WebhookMetadata`, so that a valid HMAC for one shop cannot be replayed under a different shop's identity.

### Proof of Concept
1. App is installed on `victim-shop.myshopify.com` and `attacker-shop.myshopify.com` (same `client_secret`).
2. Shopify delivers a legitimate webhook to the attacker's endpoint for `attacker-shop.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC_SHA256(client_secret, B)`.
3. Attacker resends the exact same body `B` and HMAC header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H` — validation succeeds [6](#0-5) .
5. `WebhookMetadata.new(... shop: request.shop ...)` is built with `shop = "victim-shop.myshopify.com"` and passed to the handler [7](#0-6) , causing the application to process attacker-supplied body content as if it came from the victim shop.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
