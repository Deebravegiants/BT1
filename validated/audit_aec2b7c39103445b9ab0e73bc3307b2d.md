### Title
Webhook `shop`/`topic` identity spoofing due to HMAC covering only the raw body, not the identifying headers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` only proves that the *body* was produced with the app's secret. The `shop`, `topic`, `api_version`, and `webhook_id` values that `Webhooks::Registry.process` uses to route and label the webhook are taken from unauthenticated HTTP headers and are never included in, or checked against, the HMAC. This breaks the identity binding: `hmac-signed bytes == raw body` while `bytes acted on == raw body + headers`.

### Finding Description
`Webhooks::Registry.process` validates a webhook purely by checking the body's HMAC signature and then trusts the header-derived `shop`, `topic`, and `webhook_id` to build `WebhookMetadata` that is handed to the app's handler: [1](#0-0) 

The HMAC is validated with `Utils::HmacValidator.validate`, which calls `verifiable_query.to_signable_string`: [2](#0-1) 

For webhook requests, `to_signable_string` is defined to return only the raw JSON body, while `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from HTTP headers with no cryptographic tie to that signature: [3](#0-2) 

Because none of `shop-domain`, `topic`, `webhook-id`, or `api-version` are part of the signed material, any party who can produce (or has legitimately received, e.g. for their own shop's install) a single valid `(raw_body, hmac)` pair can resend that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and `x-shopify-topic`) header. `HmacValidator.validate` will still return `true` (the body/HMAC pair is unchanged and valid), and `Registry.process` will invoke the registered handler with `WebhookMetadata.new(shop: request.shop, ...)` where `shop` is the attacker-chosen value, not the shop the HMAC was actually generated for.

This is directly analogous to the royalty bug: the check (`existingRoyalty + share < FEE_DENOMINATOR` / HMAC over raw body) does not account for the full state being mutated/acted upon (all royalty holders' shares / the `shop`+`topic` identity used by the handler), so a value the application relies on (`share` size / `shop` identity) can diverge from what was actually validated.

### Impact Explanation
Any handler that uses `WebhookMetadata#shop` to identify which tenant/session to act on (the standard integration pattern documented in this gem, e.g. looking up a session/access token by `shop` and processing the payload against that tenant's data) can be made to attribute attacker-controlled webhook content to a victim shop of the attacker's choosing. Depending on the handler, this enables cross-tenant data injection/corruption (e.g., spoofing `app/uninstalled` for a victim shop to trigger session/token deletion, or spoofing `orders/*`/`customers/*` payloads to be processed under a different shop's session). This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one valid `(raw_body, hmac)` pair for the app — trivially available to any merchant who installs the app themselves and receives webhooks for their own store (or subscribes to a webhook whose body they can predict/observe) — and to be able to send an arbitrary HTTP request directly to the app's public webhook endpoint with modified headers (endpoints are public URLs, no additional per-request secret is required). No possession of `api_secret_key` is needed, since only the (unaltered) body needs to match a previously-obtained legitimate HMAC.

### Recommendation
Bind the identifying headers to the verified signature, or otherwise re-derive/validate `shop` and `topic` independently of client-supplied headers before dispatching to handlers, e.g. by including `shop`, `topic`, and `webhook_id` in the signable string used for the HMAC comparison, or by validating the `shop` against a separately-authenticated source (e.g. requiring the resolved session for that shop to exist and match other trusted webhook metadata) before invoking the handler.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and captures one legitimate webhook delivery, e.g. for topic `orders/create`, noting the raw body `B` and the valid `x-shopify-hmac-sha256` header `H` (valid because Shopify computed it over `B` using the app's secret).
2. Attacker sends a new POST request directly to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: `H` (unchanged, still valid since only body is signed)
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (spoofed)
   - Header `x-shopify-topic`: `orders/create` (or any registered topic)
3. `Utils::HmacValidator.validate` recomputes the HMAC over `B` and it matches `H`, so `Registry.process` proceeds and calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: parsed(B), ...)`.
4. The handler processes attacker-supplied `orders/create` data as if it originated from `victim-shop.myshopify.com`, even though the HMAC was never generated for that shop. [1](#0-0) [4](#0-3)
