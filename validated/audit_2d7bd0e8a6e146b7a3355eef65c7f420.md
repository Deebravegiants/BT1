### Title
Webhook shop/topic identity spoofing via headers not covered by HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-verifiable content as only the raw request body [1](#0-0) , while `topic`, `shop`, `webhook_id`, and `api_version` — the very fields the registry acts on to route and attribute the webhook — are read straight from HTTP headers that are completely excluded from the signed content [2](#0-1) . Since the app's `api_secret_key` used for HMAC is a single shared secret across every merchant installation of the app (not per-shop) [3](#0-2) , an attacker who legitimately installs the app on their own (attacker-controlled) shop can obtain a genuinely-signed `(raw_body, hmac)` pair from a real webhook delivery, then replay that exact body/HMAC to the app's webhook endpoint while forging the `shop-domain` and/or `topic` headers to any other tenant/topic. `Utils::HmacValidator.validate` only checks the body signature [4](#0-3)  and then blindly trusts the forged headers to build the `WebhookMetadata` passed to the app's handler [5](#0-4) .

### Finding Description
This is the same identity-binding bug class as the reported `DebtorNFT._validateLoan` issue: a value that is acted upon (there, vault balance driving loan acceptance; here, the `shop`/`topic` used to attribute and route webhook data) is not actually covered by the check meant to authenticate it (there, `balanceOf()` equality; here, the HMAC signature, which covers only `@raw_body`).

Concretely:
- `Request#shop`, `Request#topic`, `Request#webhook_id`, and `Request#api_version` are all pulled from headers [2](#0-1) .
- `Request#to_signable_string` — the string the HMAC is verified against — returns only `@raw_body` [1](#0-0) .
- `Registry.process` validates the HMAC over that body-only string, and if valid, unconditionally trusts `request.shop`/`request.topic`/`request.webhook_id`/`request.api_version` for dispatch [6](#0-5) .
- The signing secret (`Context.api_secret_key`) is a single app-level credential shared by all shops that install the app [3](#0-2) , so a signature that is valid for shop A's webhook body is equally valid for the identical body claimed to be from shop B — the HMAC carries no shop-binding information at all.

Equality that should hold but doesn't: `shop_authenticated_by_hmac == shop_acted_on_by_handler`. Before the attack, both are the header value from a legitimate Shopify-originated request. After the attack, the HMAC still validates (it only ever checked the body) while `shop`/`topic` are attacker-controlled headers — breaking the binding.

### Impact Explanation
An attacker with any account capable of installing the app on a shop they control (i.e., any merchant/developer) can generate valid signed webhook bodies, then replay them against the app's public webhook endpoint with forged `shop-domain`/`topic` headers, causing the app to process attacker-supplied data as belonging to an arbitrary victim shop and/or as an arbitrary registered topic. This is cross-tenant data injection: the app's webhook handler will act on data (e.g. update local records, dispatch background jobs, sync inventory/customer data) under a false tenant identity, potentially corrupting a victim shop's data or triggering incorrect side effects attributed to that victim. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The prerequisite (installing the app on an attacker-owned shop to obtain one valid signed body) is available to any unprivileged internet user who can install the target app — no leaked credentials, TLS interception, or privileged access are required. Forging HTTP headers on a replayed request to a public webhook endpoint is trivial. The webhook endpoint is by design internet-reachable and unauthenticated apart from this HMAC check.

### Recommendation
Bind the HMAC signature to the header-derived fields it is used to authorize, not just the raw body. At minimum, include `shop-domain` and `topic` in the signed material verified for each request (or require the app to independently confirm, via a stored/authenticated mapping, that the `webhook_id`/`shop` pair corresponds to a subscription actually created for that shop) before dispatching to a handler. Do not treat any header as trusted input unless it is part of the byte range the HMAC actually covers.

### Proof of Concept
1. Attacker registers/installs the target app on their own shop `attacker.myshopify.com`, subscribing to a topic (e.g. `orders/create`) handled by the app.
2. Attacker triggers a real event, causing Shopify to send a legitimately-signed webhook: raw body `B`, header `x-shopify-hmac-sha256: H` (valid because `H = HMAC-SHA256(api_secret_key, B)`), `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the exact same body `B` and `hmac-sha256: H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally alters `x-shopify-topic` to any topic the app has registered a handler for).
4. `Utils::HmacValidator.validate(request)` succeeds because it only re-derives the HMAC over `@raw_body`, which is unchanged [1](#0-0) .
5. `Registry.process` dispatches `WebhookMetadata.new(topic: "victim-attacker-forged-topic", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` to the app's handler [7](#0-6) , which acts on attacker-controlled data under the victim shop's identity.
