### Title
Webhook `shop-domain` Header Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs and validates only the raw request body via HMAC, while the `shop` field (read from the `shopify-shop-domain`/`x-shopify-shop-domain` header) is never included in the signed payload. `Registry.process` trusts this unauthenticated header to attribute the webhook to a specific merchant, breaking the binding: `shop identity used by handler == shop bytes actually covered by HMAC`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop` accessor instead reads directly from the (attacker-controllable, since it originates from HTTP headers relayed by the host app) `shopify-shop-domain` header: [2](#0-1) .

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the body only) and compares it against the `hmac` field: [3](#0-2) . Since `shop` is not part of `to_signable_string`, its value is never authenticated by the signature check.

`Registry.process` calls `Utils::HmacValidator.validate(request)` to authorize the request, and if it passes, immediately builds `WebhookMetadata` using `request.shop` as the tenant identity handed to the app's handler: [4](#0-3) .

Because the api_secret_key (client_secret) used to sign webhooks is shared across all shops that installed the app, an attacker who controls a shop that has the app installed (e.g., their own development/trial store) can:
1. Trigger a legitimate webhook delivery to their own endpoint for a chosen topic/body (e.g., `orders/create`), obtaining a body + a Shopify-computed valid `hmac` for that body.
2. Replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint, but substitute the `shopify-shop-domain` header with a victim shop's domain.
3. `HmacValidator.validate` still succeeds, because it only checks the body signature — the substituted `shop` header is never covered by the HMAC.
4. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: request.shop ...)` set to the victim's shop, so the host application processes attacker-supplied data as if it came from the victim tenant.

### Impact Explanation
This breaks a core identity binding relied upon by every app built on this gem: the shop attribution of an inbound webhook is not authenticated even though the endpoint appears HMAC-verified. Any host application that uses `WebhookMetadata#shop` to look up sessions, write shop-scoped data, or trigger shop-specific side effects will attribute attacker-controlled webhook data to an arbitrary target shop, resulting in cross-tenant data injection/corruption — satisfying the High-risk "cross-tenant access" criterion, since it requires no privileged credential from the attacker, only that they control any shop where the app is installed (or otherwise obtain one valid `(body, hmac)` pair) and knowledge of the target shop's domain (public/discoverable).

### Likelihood Explanation
Likelihood is significant: obtaining a valid `(raw_body, hmac)` pair only requires triggering an ordinary event (e.g., placing a test order) on any shop that installed the vulnerable app — no secret is needed by the attacker. The victim shop domain (`*.myshopify.com`) is not a secret. The only barrier is that the replayed body content is fixed by whatever legitimate event the attacker triggered, limiting the payload to bodies the attacker can naturally generate on their own store, but topic/body pairs like `orders/create`, `customers/create`, etc. are fully attacker-controlled through normal shop actions.

### Recommendation
Include the `shop` (and other trust-relevant identity fields, such as `topic`) in the signed/verified payload, or validate the `shopify-shop-domain` header against an out-of-band trusted source (e.g., cross-check it against the shop associated with the session/access token used to register that specific webhook subscription) before trusting it in `WebhookMetadata`. At minimum, document that host applications must independently verify `WebhookMetadata#shop` against an installed-shop record rather than trusting it implicitly once HMAC validation succeeds.

### Proof of Concept
1. Install the vulnerable app on attacker-controlled shop `attacker.myshopify.com`; trigger an `orders/create` event to receive a legitimate webhook delivery with body `B` and header `shopify-hmac-sha256: H` (a valid HMAC of `B` using the app's shared `api_secret_key`).
2. POST to the app's webhook endpoint with the same raw body `B`, the same `shopify-hmac-sha256: H` header, `shopify-topic: orders/create`, but `shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` in [5](#0-4)  returns `true` because it only checks `B` against `H`.
4. `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and invokes the app's handler as if `victim-shop` sent this order data: [6](#0-5) .
