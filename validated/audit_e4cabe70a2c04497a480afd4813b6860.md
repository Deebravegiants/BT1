### Title
Webhook shop-domain attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the shop identity that gets handed to the application's webhook handler is read from the unsigned `X-Shopify-Shop-Domain` header. `Registry.process` validates the HMAC but then passes the header-derived `shop` straight to the handler, so the value an app trusts for tenant attribution is not the value the signature actually protects.

### Finding Description
`to_signable_string` for a webhook request returns only `@raw_body`: [1](#0-0) 

The shop domain, however, is read separately from the (unsigned) header: [2](#0-1) 

`Registry.process` validates the HMAC over the request (i.e., over the body only) and then constructs `WebhookMetadata` using `request.shop`, the header value that was never part of the signed material: [3](#0-2) 

`HmacValidator.validate` simply calls `verifiable_query.to_signable_string` and compares against `verifiable_query.hmac`; it has no notion of which fields are “covered”: [4](#0-3) 

The identity binding that should hold is:
`HMAC-verified(raw_body)` == `shop attributed to that body by the handler`

But because the HMAC signs only `raw_body` and `shop` comes from a separate, unauthenticated header, this equality does not hold. Anyone in possession of one legitimate `(body, hmac)` pair — which every merchant naturally receives for their own shop's webhook events — can replay the identical body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a different (victim) shop. The signature check still passes (it only re-verifies the body), and the handler receives `WebhookMetadata` claiming the victim shop for data that was never actually generated for, or signed on behalf of, that shop.

### Impact Explanation
This breaks the tenant-identity binding at the gem level: a signature that authenticates "this payload came from Shopify for *some* shop" is treated by downstream application code as authenticating "this payload came from Shopify for *this specific* `shop`" header value. If a host application uses `WebhookMetadata#shop` to route/store data (e.g., "update this shop's inventory record" or "look up the session for `shop`"), an attacker can cause it to apply another merchant's webhook body (or a replay of their own body) under an arbitrary victim shop identity — a cross-tenant data-integrity/attribution issue.

### Likelihood Explanation
Exploitability only requires access to any one legitimate `(raw_body, hmac)` pair for the app (e.g., a merchant's own webhook traffic, which is not secret to that merchant) and the ability to POST directly to the app's public webhook endpoint with a modified header — no access to `api_secret_key`, tokens, or the target shop's credentials is needed. The gem provides no protection against this because it does not bind the shop domain into the signed material.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the value that is HMAC-verified, or otherwise cryptographically bind the header-derived `shop` to the signed body before it is handed to application handlers, so that `to_signable_string` covers every field the application is expected to trust.

### Proof of Concept
1. Merchant A's app receives a legitimate webhook: body `{"id":1}}`, headers include `x-shopify-hmac-sha256: <valid hmac of body>` and `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker (merchant A, or anyone who intercepted/received this payload) resends the exact same body and HMAC to the app's webhook endpoint but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `Registry.process` at [5](#0-4)  validates the HMAC successfully (it only checks the body) and invokes the handler with `shop: "shop-b.myshopify.com"`, even though this payload was never generated or signed for shop B.

```ruby
      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```
