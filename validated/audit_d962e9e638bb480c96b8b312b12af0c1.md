### Title
Webhook shop identity spoofing via HMAC that only covers the request body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw body, while the `shop` value that is handed to the application's webhook handler comes from an HTTP header that is never included in that signature. Any user who can obtain one genuinely-signed webhook (e.g. by installing the app on their own store) can replay the identical body/HMAC pair with a forged `shop-domain` header, causing the host application to process attacker-supplied data under a victim shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes/verifies the HMAC exclusively against `verifiable_query.to_signable_string`: [2](#0-1) 

Meanwhile `Request#shop` is read straight from the `x-shopify-shop-domain` (or `shopify-shop-domain`) header, which is not part of the signed material: [3](#0-2) 

`Registry.process` validates the HMAC and then forwards `request.shop` straight to the application's handler as the tenant identifier, without any additional binding check: [4](#0-3) 

This breaks the intended identity binding: `HMAC-valid(body) == authenticated(shop)`. In reality the HMAC only proves `HMAC-valid(body) == sent-by-Shopify(body)`; it says nothing about which shop the body belongs to. An attacker who legitimately installs the app on their own store (an unprivileged, self-service action requiring no special credential) will receive real webhooks with valid `hmac-sha256` values for their own shop's body content. Because the header carrying the shop identity is excluded from the signature, the attacker can resend that exact body+HMAC pair while substituting `x-shopify-shop-domain`/`shopify-shop-domain` with a victim shop's domain. `HmacValidator.validate` will still return `true`, and `Registry.process` will dispatch the payload to the handler tagged as belonging to the victim shop.

### Impact Explanation
Any application built on this gem that keys per-tenant logic off `WebhookMetadata#shop` (the normal, documented pattern demonstrated in `docs/usage/webhooks.md`, and required because that's the only shop identifier the gem gives handlers) can be fed attacker-controlled data — order/customer/app-uninstall events, etc. — while believing it originates from a different merchant. This is a cross-tenant data-integrity/confidentiality break: an attacker can inject spoofed events into a completely unrelated merchant's data pipeline (e.g. trigger `app/uninstalled` or `customers/data_request` processing, or falsify order data) without ever compromising that merchant's credentials. This satisfies the "cross-tenant access" Critical-impact bar.

### Likelihood Explanation
Exploitation requires only: (1) install the target app on any Shopify store (self-service, no special privilege), (2) capture one webhook body and its HMAC from that store, (3) POST it to the app's webhook endpoint with a forged shop-domain header. No secrets, tokens, or social engineering are required — only interaction the gem itself exposes (`Registry.process`), making this readily reachable by any unprivileged internet user who can register as an app installer.

### Recommendation
Bind the `shop` identity into the authenticated material, e.g. include the `shop-domain` header (and ideally `topic`/`webhook-id`) in `to_signable_string`, or independently verify that the shop in the payload/header matches a shop that is expected to be sending this specific body (for topics whose body contains a `myshopify_domain`/`shop_id`, cross-check it against the header before trusting `request.shop`). At minimum, document prominently that `request.shop` is unauthenticated header data and must not be trusted as a tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and configures a webhook, e.g. `customers/data_request`.
2. Shopify sends a real webhook to the app: body `B`, header `x-shopify-hmac-sha256: H` (valid for secret key + `B`), `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the exact same body `B` and header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `B` — the shop header was never part of the digest: [5](#0-4) 
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)` and the host application processes attacker-controlled content as if it came from `victim.myshopify.com`.
