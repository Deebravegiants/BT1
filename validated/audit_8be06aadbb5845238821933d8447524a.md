### Title
Webhook `shop` (and `topic`) header is trusted for tenant routing but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw HTTP body, while `shop`, `topic`, and `webhook_id` are read from unauthenticated HTTP headers and passed straight through to the app's handler via `WebhookMetadata`. This breaks the intended binding `hmac-verified bytes == data acted on`: the identity of the tenant (`shop`) that the handler trusts is never covered by the signature that `Registry.process` checks.

### Finding Description
`Utils::HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns `@raw_body` alone: [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are pulled from headers that are entirely outside the signed material: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`/`request.topic` to build `WebhookMetadata`, which is handed to the app's handler as the tenant/topic identity for the payload: [3](#0-2) [4](#0-3) 

Because the `api_secret_key` used to sign webhooks is a single, app-wide secret shared across *every* shop that installs the app (the same secret validated in `HmacValidator.validate_signature`), any shop that has installed the app can legitimately receive a real webhook (valid `body` + valid `hmac`) from Shopify for its own store, then replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting the `shop-domain` (and/or `topic`) header for a different, victim tenant. `HmacValidator.validate` still returns `true` because it only checks the body bytes; `Registry.process` then dispatches the handler with `shop: <victim-shop>`, causing the app to attribute attacker-controlled data to a tenant the attacker does not control.

This matches the report's bug class directly: a field that is acted on (`shop`, used as the tenant identity for the handler) is not covered by the integrity check (HMAC is computed over body only), letting an attacker force a mismatch between "verified bytes" and "bytes acted on," exactly as the ZRX exploit forced a mismatch between the observed and actual swap type to evade the fee check.

### Impact Explanation
This is a cross-tenant integrity/authentication issue: an unprivileged user who has installed the app on their own (attacker-owned) shop can forge webhook deliveries that the app will process as though they originated from a different, arbitrary shop. Any app logic that trusts `WebhookMetadata#shop` to scope writes, cache invalidation, order/customer sync, or authorization decisions can be corrupted by an attacker-chosen tenant identifier, despite `Registry.process` reporting a "verified" HMAC. This satisfies the Critical "cross-tenant access" impact bucket, since the confused tenant boundary is enforced entirely by this gem's `Registry.process`/`HmacValidator` combination.

### Likelihood Explanation
Likelihood is moderate-to-high for any real multi-tenant app: the only prerequisite is that the attacker install the target app on their own (or any) shop — which is the normal, unprivileged flow for any Shopify merchant — and be able to POST to the app's public webhook endpoint with custom headers, which is standard HTTP capability. No access token, `client_secret`, or privileged account is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the signed material verified by `HmacValidator`, or otherwise cross-check the header-derived `shop` against a shop known to be associated with the specific HMAC/webhook subscription (e.g., look up webhook subscriptions by `webhook_id` scoped per shop) before constructing `WebhookMetadata`. At minimum, document that `Webhooks::Request#shop`/`#topic` are unauthenticated fields and must not be trusted as tenant identifiers without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Shopify sends the attacker a legitimate webhook for that install: `raw_body = '{"id":1}'`, `X-Shopify-Hmac-Sha256 = HMAC(app_secret, raw_body)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays the identical `raw_body` and `X-Shopify-Hmac-Sha256` to the same app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only [1](#0-0)  and it matches, since `raw_body` is unchanged.
5. `Registry.process` proceeds and calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {"id"=>1}, ...)` [5](#0-4) , causing the app to process attacker-controlled data as if it came from `victim-shop.myshopify.com`.
