### Title
`begin_auth` builds the OAuth redirect from an unsanitized `shop` param, leaking `client_id`/`redirect_uri` to attacker-controlled hosts - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` constructs the OAuth authorize URL via `auth_base_uri(shop) + "/oauth/authorize?..."` without ever calling `Utils::ShopValidator.sanitize!` on `shop`, unlike every sibling OAuth flow (`TokenExchange`, `ClientCredentials`, `RefreshToken`). An attacker who controls the `shop` value the host app forwards can force the app to issue a 307 redirect to an arbitrary domain, carrying the app's `client_id` and `redirect_uri` in the query string.

### Finding Description
The binding that should hold is `ShopifyAPI::Utils::ShopValidator.sanitize!(shop) == shop` before `shop` is used to build a URL that will receive the app's OAuth credentials in the query string. This binding never holds because `begin_auth` never invokes `sanitize!` at all:

```ruby
def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
  ...
  auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"
  { auth_route: auth_route, cookie: cookie }
end

def auth_base_uri(shop)
  return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")
  ...
end
``` [3](#0-2) [2](#0-1) 

By contrast, `TokenExchange`, `ClientCredentials`, and `RefreshToken` all call `ShopValidator.sanitize!` on `shop` before using it, confirming this is an oversight specific to `Oauth.begin_auth`. The documentation instructs host apps to pass a raw, attacker-influenceable value straight into `begin_auth` (e.g., `shop = request.headers["Shop"]`) [4](#0-3) , so there is no expectation the host app is required to sanitize it first.

Exploit flow: attacker's browser hits the app's login route with `shop=evil.attacker.com`. The host app calls `begin_auth(shop: "evil.attacker.com", redirect_path: "/auth/callback")`. `auth_base_uri` returns `"https://evil.attacker.com/admin"` (the `.my.shop.dev` DevServer branch is irrelevant here), producing `auth_route = "https://evil.attacker.com/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=<app-host>/auth/callback&state=...&grant_options%5B%5D=..."`. The app returns a 307 redirect to that URL. No guard in the codebase (`Context.setup?`, `Context.private?`, `HmacValidator`, `state` comparison, JWT checks) applies here since this is the *outbound* redirect construction, not the inbound callback validation — those guards only run in `validate_auth_callback`, which is never reached in this path.

### Impact Explanation
The attacker's own browser receives a redirect to `https://evil.attacker.com/admin/oauth/authorize` containing the app's real `client_id` and the exact `redirect_uri` the app expects for its callback. This discloses the app's OAuth client configuration to an untrusted party and can be leveraged to set up phishing/redirect races against real merchants using the same `redirect_uri`. This matches the High-severity category: SSRF-adjacent misdirection of an authenticated-looking flow to an unintended, attacker-controlled host. It does not directly hand over a merchant's live access token in this call alone, but it is a real, repeatable configuration leak driven purely by client-supplied input, reachable by any unprivileged attacker against any app instance using this gem's documented pattern.

### Likelihood Explanation
Preconditions are minimal: the host app must call `begin_auth` with attacker-influenced `shop` (explicitly the documented pattern), the app must be non-private (`Context.private?` false, the normal case), and `Context.setup?` must be true (standard). No credentials, secrets, or special access are needed — the attacker only needs to hit their own app's public login route with a crafted `shop` value. This is trivially repeatable per request.

### Recommendation
Call `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` inside `begin_auth` (mirroring `TokenExchange`, `ClientCredentials`, and `RefreshToken`) before constructing `auth_base_uri`, raising `Errors::InvalidShopError` for any `shop` that is not a trusted Shopify domain.
