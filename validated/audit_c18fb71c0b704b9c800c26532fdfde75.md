### Title
Missing length cap on `image` tag's base64 data-URI `href` in svg-safe validator allows oversized icon payloads through remote-config token flow - (File: libraries/svg-safe/src/validate.mjs)

### Finding Description
In `validateOption`, the `path`'s `d` attribute has an explicit length cap enforced before pattern matching: `assert(value.length <= 50_000, ...)` [1](#0-0) . The `image` tag's `href`/`xlink:href` data URI, by contrast, is validated only against `/^(data:image\/(png|jpeg);base64,[\d+/A-Za-z=]+={0,2})$/u` with no length bound whatsoever [2](#0-1) . Any base64 string of arbitrary size will pass this regex.

This is reachable from remote-config-fed token data: `assets-module.js`'s `#fetchTokens`/`fetchToken`/`addRemoteTokens` fetch custom token definitions from a remote CTR endpoint and call `#storeIcons` on them [3](#0-2) . The icon adapters (`icons-storage.js` in both browser and mobile) call `unzipIcon`, which gunzip-decompresses the attacker-supplied base64 blob and passes the resulting SVG string through `cleanup()`, which calls `validate()` [4](#0-3) [5](#0-4) . `getIcon` also re-validates on read [6](#0-5) .

However, the token schema is passed through `validateCustomToken`/`isValidCustomToken` from `@exodus/asset-schema-validation` before being stored [7](#0-6) . Project changelog history explicitly documents a feature "increase maxLength validation for CT icons" (`storage-icons-mobile` CHANGELOG, PR #15748), indicating that an icon length/maxLength constraint already exists somewhere in the custom-token schema validation pipeline upstream of `svg-safe`. I was not able to load the actual `asset-schema-validation` schema source (glob/grep for it in the index returned no file contents), so I cannot confirm the exact cap value or whether it fully bounds the base64 payload size that eventually reaches `validate.mjs`'s `image` href check.

### Impact Explanation
If no upstream length cap on the token's `icon`/base64 payload exists (or if it is large enough to still allow a multi-megabyte decoded SVG with a large embedded `data:image/*;base64` blob), an attacker who controls a remote/custom-token registry entry could cause a large synchronous base64 payload to be stored and repeatedly re-validated/rendered whenever the asset list or icon is displayed, including in flows that show pending signing/approval requests. This is a potential memory/CPU DoS but does not itself lead to key disclosure, unauthorized signing, or auth bypass — the scoped impact would be denial-of-service/degraded UI, not direct wallet compromise.

### Likelihood Explanation
Uncertain. The `image` href regex in `validate.mjs` is definitively missing a length bound compared to the `path` `d` attribute. However, exploitability depends entirely on whether `@exodus/asset-schema-validation`'s custom-token schema (used by `validateCustomToken`/`isValidCustomToken`, called in `#fetchTokens`/`fetchToken`/`addRemoteTokens` before `#storeIcons`) already caps the icon field's size — and the changelog entry ("increase maxLength validation for CT icons") strongly suggests such a cap already exists at the schema layer. I could not retrieve the schema-validation source to confirm the actual bound or whether it is generous enough to still enable a meaningful memory-exhaustion primitive through the `image` tag path specifically (as opposed to raw SVG size). Without that confirmation, I cannot assert this is a currently-exploitable, unmitigated vulnerability with confidence.

### Recommendation
Regardless of any upstream schema cap, add a defense-in-depth length assertion in `validateOption` for the `image` tag's `href`/`xlink:href` value, mirroring the `path` `d` attribute check, e.g. `assert(value.length <= <some bound>, 'image href too long')` before or as part of the regex test at libraries/svg-safe/src/validate.mjs lines 165-169. This ensures `svg-safe` is self-sufficiently robust and does not depend solely on upstream schema validation for this invariant.

### Proof of Concept
Test plan (to be run to confirm exploitability, since I could not verify upstream bounds):
1. Unit test `validate()`/`validateOption()` directly with an SVG containing `<image href="data:image/png;base64,<N MB of valid base64 chars>=" />` for increasing `N` (e.g. 1MB, 10MB, 100MB) and assert it throws — currently it will not, confirming the missing cap in `svg-safe` itself.
2. Separately, fuzz-test the full pipeline via `assets-module.js#fetchToken`/`addRemoteTokens` with a mocked CTR response containing an oversized `icon` (gzip+base64 of a large SVG with an embedded oversized `image` href) to determine whether `validateCustomToken`/`isValidCustomToken` (in `@exodus/asset-schema-validation`) rejects it before it reaches `#storeIcons`/`unzipIcon`/`cleanup`/`validate`. If the schema-level cap allows payloads large enough to be problematic, the finding is confirmed end-to-end; if the schema cap is strict enough (e.g., a few KB), the `svg-safe`-level gap is only a defense-in-depth issue, not an exploitable DoS on its own.

```javascript
import { gunzip } from 'zlib'
import { cleanup } from '@exodus/svg-safe'

export const unzipIcon = async (base64) => {
  const buff = Buffer.from(base64, 'base64')
  const unzip = await new Promise((resolve, reject) => {
    gunzip(buff, (err, res) => {
      if (err) {
        reject(err)
        return
      }

      resolve(res)
    })
  })
  return cleanup(unzip.toString('utf8'))
}
```
