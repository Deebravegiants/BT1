This confirms the analysis: `DurableNonce::from_blockhash` is derived purely from the per-slot `environment_config.blockhash` and does not incorporate the nonce account's pubkey [1](#0-0) , so *all* nonce accounts advanced within the same slot deterministically share the identical `DurableNonce` value by design — this is not an attacker-induced "collision," it is the normal, expected behavior of every block.

### Title
No vulnerability: status-cache dedup is keyed on message_hash, not blockhash, so shared/colliding nonce hashes cannot cause double-settlement - (File: runtime/src/bank/check_transactions.rs)

### Summary
The premise that "colliding DurableNonce values across two nonce accounts" could break the status-cache's one-signed-message-settles-once guarantee is invalid. `get_processed_slot`/`check_status_cache` dedupe on the transaction's `message_hash` (a hash of the full signed message, including all account keys and instructions), using `transaction_blockhash` only as a bucketing key for lookup performance, not as the identity key.

### Finding Description
`get_processed_slot` calls `status_cache.get_status(key, transaction_blockhash, &self.ancestors)` where `key = sanitized_tx.message_hash()` [2](#0-1) . Internally, `StatusCache::get_status` first looks up the `cache` map by `transaction_blockhash`, then within that bucket looks up the `message_hash` as the key in a `keymap` [3](#0-2) . Two distinct transactions signing different messages (e.g., referencing different nonce accounts, different instructions, or different account lists) necessarily produce different `message_hash` values, regardless of whether their `recent_blockhash` happens to be the same durable-nonce hash. Since `DurableNonce::from_blockhash` is keyed only by the slot's `environment_config.blockhash` and not by the nonce account's pubkey [4](#0-3) , it is in fact *normal* (not an exploit) for many distinct nonce accounts advanced in the same slot to end up with the same `DurableNonce` hash value simultaneously — yet this causes no confusion because the message content (and thus `message_hash`) still differs between transactions using different nonce accounts.

The `strict_nonce_size_check` parameter only gates whether `load_message_nonce_data`/`validate_transaction_nonce` require `nonce_account.data().len() == NonceState::size()` before calling `verify_nonce_account` [5](#0-4) [6](#0-5) . This has no connection to `message_hash` computation or the status-cache key at all; it only affects whether an oversized nonce account (e.g. `NonceState::size() + 1` as tested) can still be parsed for nonce validity, and a genuinely undersized account simply fails to deserialize inside `verify_nonce_account`/`state_from_account`, returning `None` rather than "ambiguous state" (confirmed by `test_state_from_account`'s `wrong_data_size_account` case returning `Err(InvalidAccountData)` and `test_check_nonce_transaction_validity_strict_nonce_size_check_fail`) [7](#0-6) [8](#0-7) .

Additionally, `advance_nonce_account` explicitly forbids re-advancing a nonce to the same value twice in one slot ("nonce can only advance once per slot") [9](#0-8) , and `check_nonce_transaction_validity`/`validate_transaction_nonce` require `nonce_data.durable_nonce != next_durable_nonce` before permitting consumption [10](#0-9) [11](#0-10) , further preventing any same-slot ambiguity for a single nonce account.

### Impact Explanation
No impact: no reachable path allows a distinct signed message to be treated as `AlreadyProcessed` for a different message, nor allows double-commit of a single signed message, because the status-cache dedup identity is `message_hash`, which is cryptographically bound to the full transaction content and is unaffected by shared/colliding durable-nonce blockhash values.

### Likelihood Explanation
Not applicable — the attack requires either a SHA-256 preimage/collision (acknowledged infeasible in the prompt) or a mechanism by which `message_hash` collides across distinct messages, and no such mechanism exists in the reviewed code; the `strict_nonce_size_check` flag does not influence `message_hash` or status-cache keying.

### Recommendation
No fix needed. If desired for clarity, documentation could be added near `DurableNonce::from_blockhash` usage in `advance_nonce_account` noting explicitly that the per-slot shared durable-nonce value is intentional and safe because status-cache/transaction identity is keyed on `message_hash`, not on the nonce blockhash value.

### Proof of Concept
Not applicable — no valid exploit path exists to construct a PoC for.
