### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC against that body alone. `Registry.process`, however, trusts `request.shop` (parsed from the unauthenticated `X-Shopify-Shop-Domain` header) to attribute the webhook to a tenant when invoking the handler, even though that field was never part of the signed material.

### Finding Description
The equality that should hold is: *the tenant identity acted upon == the tenant identity cryptographically bound by the HMAC*. Here that equality is broken.

- `Request#to_signable_string` only returns `@raw_body`, excluding every header: [1](#0-0) 
- `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of `to_signable_string`: [2](#0-1) 
- `HmacValidator.validate`/`validate_signature` compute and compare the HMAC only over `verifiable_query.to_signable_string` (i.e., only the body), so the `shop` header can be freely changed without invalidating the HMAC: [3](#0-2) 
- `Registry.process` validates the HMAC, then immediately trusts `request.shop` to construct the `WebhookMetadata` passed to the host application's handler, treating it as an authenticated tenant identifier: [4](#0-3) 

Because the `api_secret_key` is a single per-app secret shared across every shop that installs the app, HMAC validity says only "this body was signed by our app's secret" — it says nothing about *which* shop the body belongs to. An attacker who legitimately installs the app on their own shop receives genuine, validly-HMAC-signed webhook deliveries for that shop. They can then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (the body/HMAC pair is untouched), and `Registry.process` will hand the host application a `WebhookMetadata` claiming the (attacker-controlled) body originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem's own webhook-processing primitive (`Registry.process` + `HmacValidator`) lets an unprivileged attacker (who only needs a legitimate install of the multi-tenant app on their own store — no special credentials, no leaked secrets, no access to `api_secret_key`) inject arbitrary attacker-chosen webhook payloads that are misattributed to a shop they do not control. Any host application that relies on `WebhookMetadata#shop` (the value the gem itself parses and injects, per `Registry.process`) to select a tenant record for side effects (e.g., "app uninstalled" cleanup, order/product sync, GDPR data-request handling) is fed spoofed data under a false tenant identity. This satisfies the "cross-tenant access" impact category.

### Likelihood Explanation
High. No secret material, TLS interception, or privileged account is required — only an ordinary install of the app on an attacker-owned store (a normal, permitted action for any Shopify merchant/developer testing an app), then replaying an intercepted or self-observed webhook body/HMAC pair with a modified `shop-domain` header. The vulnerable code path (`HmacValidator.validate`, `Request#to_signable_string`, `Registry.process`) is exercised by every consumer of `ShopifyAPI::Webhooks::Registry.process`, which is the gem's documented entry point for webhook handling.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed/verified material, or otherwise cryptographically/contextually bind the `X-Shopify-Shop-Domain` header to the request before trusting it — e.g., compare it against the shop associated with the session/install that the request claims to originate from, rather than trusting the header verbatim once the body-only HMAC passes. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must be cross-checked by the host application against a known/installed shop list before being used for tenant-sensitive operations.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, triggering a real webhook delivery, e.g. `orders/create`, with body `B` and header `X-Shopify-Shop-Domain: attacker.myshopify.com`, correctly signed as `HMAC = HMAC-SHA256(api_secret_key, B)`.
2. Attacker captures `(B, HMAC)` (they own this shop and can trivially observe the delivery, or run their own webhook receiver to log it).
3. Attacker crafts a new HTTP POST to the app's webhook endpoint with the *same* body `B` and the *same* `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` and, if desired, `X-Shopify-Topic`/`X-Shopify-Webhook-Id` to a topic of choice.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed by the host app and passed to `ShopifyAPI::Webhooks::Registry.process`.
5. `HmacValidator.validate` passes because it only checks `B` against the HMAC (`to_signable_string` returns only `@raw_body`).
6. `Registry.process` calls the host's handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)`, letting the attacker's payload `B` masquerade as data originating from `victim.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
