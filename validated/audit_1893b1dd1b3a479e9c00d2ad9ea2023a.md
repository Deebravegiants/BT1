## Title
Unbounded-input `swapETHForExactTokens` fee-payment swaps in `EvmHost`/`IntentGatewayV2` let MEV sandwich bots extract value from any user paying dispatch/order fees in native token - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, `EvmHost.fundRequest`, and `IntentGatewayV2.placeOrder` all convert user-supplied native token into the protocol fee token via Uniswap V2's `swapETHForExactTokens`, using `block.timestamp` as the deadline and no explicit slippage/maximum-input bound beyond whatever `msg.value` happens to be. This repeats the exact implicit Uniswap-V2 assumption ("the exact-output swap will execute near the quoted price") that caused the Alpha Homora V2 incident: a public, unprivileged transaction performs an on-chain, exact-output swap with no price-impact guard, so it can be sandwiched to extract value from the caller.

In every one of these call sites, `swapETHForExactTokens` is invoked with:
- `amountOut` fixed (the fee/`post.fee`/`order.fees` needed),
- `path = [WETH, feeToken]`,
- `to = address(this)`,
- `deadline = block.timestamp` (a no-op deadline — it can never be stale within the same block),
- and the *implicit* maximum input capped only by whatever native value the caller happened to attach (`msg.value`).

There is no on-chain reference price, no `amountInMax` derived from an oracle, and no minimum-received check independent of the live AMM state at execution time. This mirrors the exact class of bug described in the Alpha Finance report: code trusts Uniswap V2's spot price at execution time as if it were tamper-proof, when in fact it is the most manipulable value on-chain within a single block.

Any unprivileged caller — an app or user dispatching a `PostRequest`/`GetRequest` through `EvmHost`, or a user placing an `IntentGatewayV2` order and choosing to pay `order.fees` in native token — triggers this code path directly from a public, mempool-visible transaction. That makes it a canonical MEV sandwich target:
1. Attacker observes the pending `dispatch()`/`placeOrder()` transaction carrying `msg.value` ETH for the fee swap.
2. Attacker front-runs with a large buy of `feeToken` against the same Uniswap V2 pool, pushing the effective price of `feeToken` in ETH up.
3. The victim's `swapETHForExactTokens` still succeeds (Uniswap V2 exact-output swaps only fail if `msg.value` is insufficient), but consumes materially more ETH than a fair, unmanipulated price would require to obtain the same fixed `amountOut` of `feeToken`. The overpaid ETH is not refunded (the refund is `msg.value - amounts[0]`, and `amounts[0]` itself is inflated by the manipulation) — this is the value extracted.
4. Attacker back-runs by selling the `feeToken` back, capturing the price impact as profit, funded by the extra ETH the victim was forced to pay.

This is the direct EVM analog of the Alpha Homora V2 incident: a protocol-initiated Uniswap V2 exact-output swap, run inline in a public transaction, with no protection against the pool being moved against the caller in the same block.

### Impact Explanation
Every dispatcher of a Hyperbridge message or intent-gateway order that opts to pay in native token is exposed to value extraction proportional to the fee-swap size and the pool's manipulability (thinner `WETH/feeToken` pools are worse). Because these are core, frequently-used entry points (`EvmHost.dispatch`, `fundRequest`, `IntentGatewayV2.placeOrder`), this is a systemic, repeatable MEV-extractable leak of user funds rather than an isolated edge case, matching the "Medium" severity of the referenced incident (loss distributed across many callers rather than a single catastrophic drain).

### Likelihood Explanation
High likelihood of opportunistic exploitation: any public mempool transaction that calls these functions with `msg.value > 0` is trivially detectable by MEV searchers/sandwich bots monitoring pending transactions, and the attack requires no privileged access — only capital and speed, which is the same MEV-bot capability set that caused the referenced Alpha Finance loss.

### Recommendation
Do not rely on the router's live spot price as the caller's implicit maximum. Either:
- require callers to pass an explicit `amountInMax` (or a `minAmountOut` fee-token slippage bound) that is checked against a governance/oracle-bounded reference price before calling `swapETHForExactTokens`, or
- replace `block.timestamp` deadlines with a real time bound and add an explicit maximum acceptable ETH cost check (revert if `amounts[0]` exceeds a bound derived from a TWAP or Chainlink-style reference price, similar to the pattern already used in `SimplexPaymaster.swapAndDeposit`'s `_getOraclePrice`-derived `amountOutMin`), so the swap reverts rather than silently overcharging the caller when the pool is being manipulated.

### Proof of Concept
1. Attacker monitors the mempool for a `dispatch(DispatchPost)` / `placeOrder()` call carrying `msg.value` for a native-token fee payment.
2. Attacker front-runs with a large `WETH -> feeToken` buy on the same Uniswap V2 pool used by `_hostParams.uniswapV2`, moving the pool price against the victim.
3. Victim's transaction executes `swapETHForExactTokens(post.fee, [WETH, feeToken], address(this), block.timestamp)` — succeeds but consumes disproportionately more ETH than the pre-manipulation price implied, because there is no `amountInMax`/reference-price check anywhere in `EvmHost.dispatch`/`fundRequest`/`IntentGatewayV2.placeOrder`.
4. Attacker back-runs by selling `feeToken` back into the pool, realizing the price-impact profit funded by the victim's excess ETH spend. [1](#0-0) [4](#0-3)
