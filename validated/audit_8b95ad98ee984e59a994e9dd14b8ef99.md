### Title
Webhook shop-domain header is trusted for tenant identification but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `Utils::HmacValidator` verifies the HMAC solely over that body. The `shop`, `topic`, `webhook_id`, and `api_version` values, however, are read directly and unauthenticated from HTTP headers and are handed to the application's webhook handler as trusted tenant identity. This breaks the intended binding: `hmac_verified_bytes == raw_body` but `raw_body != shop_identity_used_by_handler`.

### Finding Description
`Request#hmac` and `#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

`to_signable_string` returns `@raw_body` only — none of `shop`, `topic`, `webhook_id`, or `api_version` (all read from unauthenticated headers via `shopify_header`) are folded into the signed payload: [3](#0-2) [4](#0-3) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it against the `hmac` header: [5](#0-4) 

`Registry.process` gates only on this body-only HMAC check, then immediately forwards the unauthenticated `request.shop` header value to the handler as the tenant identity in `WebhookMetadata`: [6](#0-5) 

The equality that should hold is: `shop_bound_by_signature == shop_used_for_tenant_dispatch`. In this implementation, the signature only binds the raw body bytes; the shop identity dispatched to the handler is taken from a header that carries no cryptographic binding to that signature at all.

### Impact Explanation
Because the HMAC is computed only from the body and the same app `client_secret`/`api_secret_key` is used for every shop that installs the app, any two webhook deliveries with identical body content and the same secret produce identical valid HMACs regardless of which shop they were destined for. An attacker who controls one shop (their own, unprivileged, self-installed instance of the target app) receives genuine, validly-signed webhook deliveries for that shop. They can replay the exact same raw body + valid HMAC to the victim app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks body integrity against the app secret), and `Registry.process` dispatches the event to the handler tagged with the victim's `shop`. Any host application that trusts `WebhookMetadata#shop` as an authenticated tenant identifier (a documented, expected use of this field) will process/attribute the forged event under the wrong tenant — a cross-tenant data-integrity/dispatch confusion rooted entirely in this gem's verification logic, not in host misuse.

### Likelihood Explanation
Exploitation requires only an unprivileged actor able to install/operate any instance of the target app (e.g., a public/dev app on the Shopify App Store) to harvest one legitimately signed webhook body+HMAC pair, then send a forged HTTP request with a substituted shop-domain header to the app's public webhook endpoint — no access token, `client_secret`, or privileged account is needed. Likelihood is elevated by the fact that webhook endpoints are, by design, publicly reachable.

### Recommendation
Bind the tenant identity to the HMAC verification: either include the `shop` (and ideally `topic`/`webhook_id`) header values in `to_signable_string`, or independently cross-check `request.shop` against a shop already known/registered for the given `api_secret_key`/session before dispatch, so that `Registry.process` cannot attribute a validly-signed body to an attacker-chosen shop.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and receives a legitimate webhook delivery: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` and the app's shared secret), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the same `B` and `H` to the app's webhook endpoint, replacing the shop header: `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally: [7](#0-6) 
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` only, matches `H`, returns `true`: [8](#0-7) 
5. `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"` despite the event content actually originating from the attacker's own shop, since `request.shop` is read straight from the unauthenticated header: [9](#0-8)

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
