## Title
Front-running a single message in a relayer's batch reverts/rolls-back the entire `handle_unsigned` batch (and `HandlerV2` batch calls), enabling griefing that can stall message delivery to the point of timeout - (File: `modules/pallets/ismp/src/impls.rs`, `modules/pallets/ismp/src/lib.rs`, `evm/src/core/HandlerV2.sol`)

### Summary
`pallet-ismp`'s permissionless `handle_unsigned` extrinsic (and the EVM `HandlerV2` equivalents `handlePostRequests`/`handleGetResponses`/`batchCall`) process an entire batch of messages atomically. If any single message in the batch has already been delivered by someone else, the batch handler returns an error for that message which short-circuits/atomically reverts the whole batch, discarding all the other valid, not-yet-delivered messages along with it. Because delivery of ISMP messages is permissionless and unsigned (free to submit on the Substrate side, and cheap on EVM), an attacker can watch the mempool/tx-pool for a relayer's large batch and front-run it by submitting just one of its constituent messages, causing the relayer's entire batch to fail and delaying delivery of every other message in it. Repeated griefing can push messages past their timeout, resulting in a route that is unable to deliver messages and forces timeout/refund handling instead of successful delivery.

### Finding Description
On the Substrate side, `handle_unsigned` is an unsigned, permissionless extrinsic wrapped in `#[frame_support::transactional]`: [1](#0-0) 

It calls `Pallet::<T>::execute(messages)`, which maps `handle_incoming_message` over **every** message in the batch and `.collect()`s the results into a single `Result`, short-circuiting on the first error: [2](#0-1) 

Because the whole call is `#[frame_support::transactional]`, a single failing message anywhere in the batch causes `Error::<T>::InvalidMessage` and rolls back state changes for *all* messages in that extrinsic, not just the offending one.

The per-message request handler checks for an existing receipt (i.e., a message that was already delivered) up front, before any dispatch happens, and errors out if found: [3](#0-2) 

So if even one message out of N in a relayer's batch was already delivered by a third party, `handle_incoming_message` for that message returns `Err(DuplicateRequest)`, which propagates up through `execute()`'s `.collect::<Result<Vec<_>, _>>()` and aborts the entire batch — the other N-1 legitimate, not-yet-delivered messages are discarded along with it.

The equivalent EVM-side handler `HandlerV2.handlePostRequests` performs the same "verify proof for whole batch, then duplicate-check every leaf, revert on first duplicate" pattern: [4](#0-3) 

and `batchCall`, used by the relayer to bundle a consensus update with application messages into one tx, is explicitly documented as atomic — "any failure reverts the entire batch": [5](#0-4) 

Relayer tooling itself relies on this batching (`submit_batch_messages` groups many ISMP messages into a single `batchCall` transaction, describing it as "Atomic: if any inner call reverts, the whole transaction reverts"): [6](#0-5) 

An attacker who observes a large pending relayer batch (mempool on EVM, or the transaction pool for the unsigned extrinsic on Substrate) can extract just one of the leaves/requests from the visible calldata/proof and submit it alone (a much cheaper, smaller message) ahead of the relayer's transaction. If the attacker's transaction lands first, the targeted message now has a receipt, and the relayer's larger batch fails as described above — wasting the relayer's gas/weight and, more importantly, delaying delivery of every other request bundled in that batch.

### Impact Explanation
- Relayers lose gas/weight for the entire batch even though only one message in it was actually a duplicate.
- All other legitimate, undelivered messages bundled with the front-run message are also delayed, since they must be resubmitted in a fresh transaction.
- If an attacker repeats this griefing across a relayer's retries (which is cheap, since delivery is permissionless and unsigned extrinsics carry no direct fee on Substrate, and only requires knowledge of a single leaf/proof on EVM), the delayed messages can exceed their configured timeout window. Once timed out, they can no longer be delivered and must instead be processed via the timeout path, meaning the intended cross-chain action (e.g., a token mint, intent fulfillment, or state update) never completes — this is a functional denial of message delivery for that route, matching the "route unable to deliver messages" impact class.
- This is systemic griefing risk against the permissionless relayer set that keeps Hyperbridge's message-passing live, degrading delivery throughput and reliability of the bridge under adversarial mempool conditions.

### Likelihood Explanation
Likelihood is moderate-to-high: message delivery is explicitly permissionless (`ensure_none(origin)` for `handle_unsigned`; `handlePostRequests`/`handleGetResponses`/`batchCall` have no access control on the EVM side), all proof/message data needed to extract and resubmit a single leaf is publicly visible in the pending transaction, and the cost to the attacker of submitting a single-message duplicate is far lower than the cost the relayer incurs processing/losing the full batch. Any actor motivated to disrupt delivery of a specific message (e.g., to force a timeout/refund instead of a delivery, or simply to grief competing relayers) can execute this repeatedly and cheaply.

### Recommendation
Avoid all-or-nothing batch semantics for message delivery:
- In `Pallet::<T>::execute` (`modules/pallets/ismp/src/impls.rs`), do not short-circuit the whole batch on a single message's error. Process each message independently, collect per-message successes/failures, deposit an `Errors` event for the failed ones, and continue processing/charging fees for the messages that succeeded, rather than aborting the entire transactional block.
- Similarly, in `HandlerV2.handlePostRequests`/`handleGetResponses` (`evm/src/core/HandlerV2.sol`), skip (rather than revert on) leaves that are already duplicates/delivered, continuing to dispatch the remaining valid leaves in the same call.
- For `batchCall`, consider offering an optional "best-effort" mode that tolerates individual inner-call failures (e.g., duplicate-message errors) without reverting calls that would otherwise succeed, while keeping the current atomic mode as an opt-in for callers that require it.

### Proof of Concept
1. Relayer R builds a Substrate `handle_unsigned` extrinsic (or EVM `batchCall`/`handlePostRequests` tx) bundling N valid, undelivered ISMP requests `[req_1 ... req_N]` with their combined membership proof.
2. R broadcasts this transaction; it sits in the mempool/transaction queue, with request contents visible.
3. Attacker A extracts `req_k` (any single request/leaf) from R's pending transaction along with a valid sub-proof, and submits their own transaction containing only `req_k`, with higher priority/gas so it lands first.
4. A's transaction succeeds, storing a receipt for `req_k` (`store_request_receipt` on Substrate / `host.dispatchIncoming` + receipt write on EVM).
5. R's original transaction executes: `handle_incoming_message`/`handlePostRequests` for `req_k` now hits `Error::DuplicateRequest` / `DuplicateMessage`; `execute()`'s `.collect::<Result<Vec<_>, _>>()` (Substrate) or the `revert DuplicateMessage` in the duplicate-check loop (EVM) causes the whole call to fail.
6. Because the extrinsic/tx is transactional/atomic, `req_1...req_{k-1}, req_{k+1}...req_N` are also rolled back despite being perfectly valid and undelivered — R must resubmit them, and A can repeat the attack on the resubmitted batch, indefinitely delaying delivery until the remaining requests time out.

    /**
     * @dev Process a batch of encoded handler calls in a single transaction.
     * Uses delegatecall to self so msg.sender is preserved and storage writes
     * happen in this contract's context. Atomic, any failure reverts the entire batch.
     * @param calls - array of ABI-encoded handler function calls
     */
    function batchCall(bytes[] memory calls) external {
        uint256 len = calls.length;
        for (uint256 i = 0; i < len; ++i) {
            (bool success, bytes memory returnData) = address(this).delegatecall(calls[i]);
            if (!success) revert BatchCallFailed(i, returnData);
        }
    }

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }
