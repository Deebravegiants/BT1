### Title
Oscillating grow/shrink of account data bypasses `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` net-delta cap, allowing unmetered repeated full-size `Vec::resize` work - ([File: transaction-context/src/instruction_accounts.rs] / [File: transaction-context/src/transaction_accounts.rs])

### Summary
`TransactionAccounts::can_data_be_resized` and `update_accounts_resize_delta` only track a running **net** sum of `(new_len - old_len)` across the whole transaction, not the sum of actual bytes touched by each resize. An attacker packing multiple instructions in one transaction that alternately grow an owned account to a large size and shrink it back to zero keeps `resize_delta` near zero, so the transaction-wide cap never trips, while each `set_data_length` call still triggers a real `TransactionAccountViewMut::resize` (`Vec::resize` + zero-fill, `transaction_accounts.rs:105-108`) proportional to the size involved.

### Finding Description
`BorrowedInstructionAccount::set_data_length` (`transaction-context/src/instruction_accounts.rs:197-207`) calls `can_data_be_resized`, which delegates to `TransactionAccounts::can_data_be_resized` (`transaction_accounts.rs:309-326`). That function enforces exactly two checks:
1. `new_len <= MAX_ACCOUNT_DATA_LEN`
2. `resize_delta.get() + (new_len - old_len) <= MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION`

`resize_delta` is updated via `update_accounts_resize_delta` (`transaction_accounts.rs:297-307`) as `resize_delta += (new_len - old_len)` — a signed, saturating running total. When an account is shrunk, this subtracts from `resize_delta`, effectively "refunding" prior growth budget. There is no accounting of *gross* bytes moved (sum of `|new_len - old_len|` or sum of `resize()` calls), and no per-call compute-unit charge tied to the size of the underlying `Vec::resize` inside `TransactionAccountViewMut::resize` (`transaction_accounts.rs:105-108`), which performs the actual zero-fill/reallocation work each time it is invoked, independent of net delta.

Consequently, a sequence of instructions that alternately call `set_data_length(LARGE)` then `set_data_length(0)` on the same account keeps `resize_delta` oscillating near zero (bounded only by `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` at any single point in the sequence), while each call still performs a full-size real resize/zero-fill in native code. The number of such instructions is bounded only by how many can be packed into a transaction (subject to the 1232-byte packet limit and per-transaction compute budget), not by the resize-delta accounting, so the real memory-touching work can scale with the number of instructions rather than with the net data growth the accounting model was designed to bound.

### Impact Explanation
This allows a normal unprivileged user to construct a single transaction that forces the validator to perform a multiple of `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` worth of real memory allocation/zero-fill work (once per oscillating instruction) while only "spending" a bounded, near-zero net resize-delta budget. This is a CPU/memory amplification issue: cost accounting (resize-delta) does not upper-bound real resize work, matching the Agave bounty category of underpriced execution / compute-DoS via amplification, scoped to `transaction-context::TransactionAccounts`/`instruction_accounts` resize accounting.

### Likelihood Explanation
Preconditions are minimal and available to any unprivileged transaction sender: an attacker only needs to own (be the program/owner of) a writable, resizable account and issue a sequence of instructions in one transaction that call `set_data_length` with alternating large/zero lengths (e.g., via a program that exposes a resize instruction, or via existing native processors such as `system_processor.rs`/`bpf_loader`/`vote_state/handler.rs`, all of which call into this same `set_data_length` path). This is repeatable on every transaction and requires no special timing, staking, or leader control — it is directly reachable from an ordinary RPC-submitted transaction.

### Recommendation
Change the per-transaction accounting to bound gross resize work rather than (or in addition to) net delta — e.g., track `sum(|new_len - old_len|)` (or `sum(max(new_len, old_len))`) against a cap, and/or explicitly charge compute units proportional to the bytes touched by each `set_data_length`/`resize` call in `update_accounts_resize_delta` / `can_data_be_resized`, so that oscillating grow/shrink cannot be used to perform unbounded real work for a bounded net-delta budget.

### Proof of Concept
```rust
// transaction-context/src/transaction_accounts.rs (test module)
#[test]
fn test_oscillating_resize_bypasses_net_delta_cap() {
    use crate::{MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION, MAX_ACCOUNT_DATA_LEN};

    let accounts = vec![(
        Pubkey::new_unique(),
        AccountSharedData::new(1_000_000_000, 0, &Pubkey::new_unique()),
    )];
    let tx_accounts = TransactionAccounts::new(accounts);

    let large_len = (MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION as usize)
        .min(MAX_ACCOUNT_DATA_LEN as usize);

    let mut total_bytes_touched: u128 = 0;
    for _ in 0..100 {
        // Grow
        tx_accounts.can_data_be_resized(0, large_len).unwrap();
        tx_accounts.update_accounts_resize_delta(0, large_len).unwrap();
        total_bytes_touched += large_len as u128; // real Vec::resize work

        // Shrink back to 0
        tx_accounts.can_data_be_resized(large_len, 0).unwrap();
        tx_accounts.update_accounts_resize_delta(large_len, 0).unwrap();
        total_bytes_touched += large_len as u128; // real Vec::resize work

        // resize_delta always returns to ~0, so the cap never trips
        assert!(tx_accounts.resize_delta().abs() <= MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION);
    }

    // Assert: 100 * 2 * large_len bytes of real resize work were permitted
    // despite the transaction-wide net-growth cap being MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION.
    assert!(total_bytes_touched > 100 * MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION as u128);
}
```
Expected result: the test passes today (no error is returned across the 100 grow/shrink cycles), demonstrating that `total_bytes_touched` (real work) vastly exceeds `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` (the intended cap), confirming the accounting bounds net delta, not gross resize work.     pub(crate) fn update_accounts_resize_delta(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        let accounts_resize_delta = self.resize_delta.get();
        self.resize_delta.set(
            accounts_resize_delta.saturating_add((new_len as i64).saturating_sub(old_len as i64)),
        );
        Ok(())
    }

    pub(crate) fn can_data_be_resized(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        // The new length can not exceed the maximum permitted length
        if new_len > MAX_ACCOUNT_DATA_LEN as usize {
            return Err(InstructionError::InvalidRealloc);
        }
        // The resize can not exceed the per-transaction maximum
        let length_delta = (new_len as i64).saturating_sub(old_len as i64);
        if self.resize_delta.get().saturating_add(length_delta)
            > MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION
        {
            return Err(InstructionError::MaxAccountsDataAllocationsExceeded);
        }
        Ok(())
    }

    /// Resizes the account data (transaction wide)
    ///
    /// Fills it with zeros at the end if is extended or truncates at the end otherwise.
    pub fn set_data_length(&mut self, new_length: usize) -> Result<(), InstructionError> {
        self.can_data_be_resized(new_length)?;
        // don't touch the account if the length does not change
        if self.get_data().len() == new_length {
            return Ok(());
        }
        self.touch()?;
        self.update_accounts_resize_delta(new_length)?;
        self.account.resize(new_length, 0);
        Ok(())
    }
