The gem's `WebhookMetadata.shop` field is documented as the trustworthy shop domain (`docs/usage/webhooks.md:14`), and the library's own `Registry.process` uses `request.shop` for tenant identification while validating only via `Utils::HmacValidator.validate(request)`, whose signable string is body-only.

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body alone, excluding the `shop-domain` header that `ShopifyAPI::Webhooks::Registry.process` later trusts and forwards to the app's webhook handler as the authoritative tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `#shop` is read directly and unauthenticated from the `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `Registry.process` verifies the request solely with `Utils::HmacValidator.validate(request)` [3](#0-2) , and `HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (body only) using the app's shared `Context.api_secret_key` [4](#0-3) . After a successful HMAC check, `Registry.process` builds `WebhookMetadata` directly from `request.shop` (the unauthenticated header) and hands it to the app's handler [5](#0-4) . The documented contract explicitly tells integrators that `data.shop` is "The shop domain of the webhook" [6](#0-5) , i.e. this is the gem's own trusted output, not something the host app is expected to independently re-verify.

Because the API secret (`client_secret`) used for the HMAC is shared across every shop that installs the same app (it is not per-shop), any real merchant who installs the target app on their own store legitimately receives genuine Shopify webhook deliveries with a valid HMAC computed over the body using that shared secret. That attacker-controlled merchant can capture one such genuine `(raw_body, hmac)` pair from their own store and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. Since the header is not part of the signed content, `HmacValidator.validate` still returns `true`, and `Registry.process` will invoke the app's handler with `shop` set to the victim's domain and `body` set to the attacker's chosen payload.

Equality broken: `shop_authenticated_by_hmac == shop_the_app_acts_on` is assumed by the documented `data.shop` contract, but in the code `shop_authenticated_by_hmac` (nothing — the shop is never part of the HMAC input) `!= request.shop` (attacker-controlled header value forwarded as the acted-upon tenant).

### Impact Explanation
This breaks the tenant boundary the gem is responsible for establishing before invoking the handler: an unprivileged attacker who merely installs the app on their own store (no special privilege, no access token theft) can forge webhook events that the host app will process as belonging to an arbitrary victim `myshopify.com` domain, with attacker-controlled body content. Depending on how the host app uses `data.shop` (e.g. looking up the victim's stored session/access token and using `data.body` to drive it), this can lead to cross-tenant data corruption or actions being taken against a merchant who never sent that event — matching the "cross-tenant access" High/Critical impact class, rooted entirely in this gem's own HMAC-verification/shop-extraction design rather than host-app misuse.

### Likelihood Explanation
Requires only an ordinary Shopify Partner/merchant account to install the target app once and capture a single valid webhook delivery (trivial, unprivileged, no secrets needed) — then any tool capable of sending arbitrary HTTP requests with custom headers to the app's public webhook endpoint completes the attack. No access token, `client_secret`, or elevated privilege is needed.

### Recommendation
Bind the shop identity into the signed payload verification path, e.g. include `shop-domain` (and ideally `webhook_id`/`topic`) as part of `to_signable_string`, or independently verify that the `shop-domain` header matches a shop the app knows is installed and to which a webhook was actually registered (e.g. cross-check against stored registration/session state) before trusting `request.shop` in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggers any subscribed webhook topic (e.g. `orders/create`), and captures the raw POST body plus the `X-Shopify-Hmac-Sha256` header Shopify sent — this HMAC is valid because it's computed with the app's single shared `client_secret`.
2. Attacker resends the exact same raw body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into `shop = "victim-shop.myshopify.com"`, `hmac` unchanged.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (raw body only, per `lib/shopify_api/webhooks/request.rb:35-38`) and matches — validation passes despite the domain having been swapped.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's payload>, ...)`, and the host app processes the forged event as if it originated from the victim's store.
