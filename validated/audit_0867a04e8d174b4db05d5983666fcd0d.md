### Title
Fee-on-transfer underlying tokens drain WrappedHyperFungibleToken custody pools due to unchecked transfer amount - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken.send()` and `WrappedHyperFungibleTokenUpgradeable.send()` lock the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` but never verify the amount actually received by the contract. The dispatched cross-chain message always encodes the nominal `params.amount`, not the real balance delta. If the underlying token deducts a transfer fee (fee-on-transfer / deflationary token), the destination-chain peer will release the full nominal `message.amount` from its own custody pool even though the source-chain peer only locked a smaller, fee-reduced amount.

### Finding Description
In `send()`: [1](#0-0) 

the token transfer is performed without a before/after balance check, and `params.amount` (the caller-supplied nominal amount) is embedded directly in the dispatched `Message`: [2](#0-1) 

On the destination chain, `onAccept` unconditionally transfers out `message.amount` of its own underlying token from its custody balance to the beneficiary: [3](#0-2) 

This is the same root-cause bug class as the referenced Basin Well finding: the contract accounts for a nominal/requested transfer amount instead of the actual amount received, and for tokens that charge fees on transfer, that discrepancy is never reconciled. Notably, the sibling contract `IntentGatewayV2.placeOrder()` in this same codebase already defends against exactly this class of bug by snapshotting balances before/after and mutating the order to the actually-received amount: [4](#0-3) 
`WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` lack this defense entirely.

The identical unchecked pattern also exists in the timeout/refund path and the WETH branch, and is duplicated verbatim in `WrappedHyperFungibleTokenUpgradeable.sol`: [5](#0-4) 

### Impact Explanation
If a fee-on-transfer/deflationary ERC20 is configured as the `_underlying` for a `WrappedHyperFungibleToken` deployment on any chain, every `send()` call locks strictly less than `params.amount` on the source side, while the destination peer always releases the full `params.amount` from its own custody balance. Repeated sends progressively drain the destination custody pool beyond what was ever actually locked/backed, allowing an attacker (or even honest users, cumulatively) to withdraw more of the underlying token than was ever deposited system-wide. This is a permanent, unbacked loss of funds from the bridge's custody reserves — a direct token-bridge mint/burn (lock/unlock) accounting break reachable from a single unprivileged `send()` transaction.

### Likelihood Explanation
Likelihood depends on whether a fee-on-transfer token is ever configured as the `_underlying` for this wrapper. The contract places no restriction against such tokens (no `require` on balance delta, no rejection of exotic ERC20 behavior), and the `configure()` function is a normal owner-set parameter with no built-in validation of token semantics. Given that Hyperbridge is designed to support arbitrary "existing ERC20 tokens" (per the contract's own docstring), and fee-on-transfer tokens are common in the wild, an operator wrapping such a token — deliberately or by oversight — immediately exposes the custody pool to continuous drain with each cross-chain transfer, with no privileged action required by the attacker.

### Recommendation
Mirror the pattern already used in `IntentGatewayV2.placeOrder()`: measure the contract's underlying-token balance before and after `safeTransferFrom` in `send()`, and use the actual received delta (not `params.amount`) when building the dispatched `Message.amount`. Symmetrically, ensure `onAccept`/`onPostRequestTimeout` transfer-outs cannot exceed the contract's own custody balance, and consider explicitly rejecting configuration of tokens whose `balanceOf` delta does not match transfer amount, or documenting this as an unsupported token class.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` A on chain X and B on chain Y, both configured with the same fee-on-transfer token (1% fee) as `_underlying`, and register each other via `addChain`.
2. Attacker calls `A.send({amount: 1000, to: attacker, dest: Y, ...})`. Due to the 1% fee, A actually receives only 990 tokens, but the dispatched message still encodes `amount: 1000`.
3. Once the ISMP request is delivered to B, `B.onAccept` executes `IERC20(_underlying).safeTransfer(beneficiary, 1000)`, releasing 1000 tokens from B's custody pool even though only 990 were ever locked on A's side.
4. Repeating this cycle continuously drains 1% extra tokens from the aggregate custody reserves per cycle, eventually leaving one side's pool unable to honor legitimate unlocks/refunds (analogous to the referenced Basin Well "running out of well").

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
