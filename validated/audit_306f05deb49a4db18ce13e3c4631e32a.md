### Title
Webhook `shop`/`topic`/`webhook_id` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read directly from unauthenticated HTTP headers and are never part of what `HmacValidator` verifies. `Registry.process` then forwards this unverified `shop` value straight to the app's handler as the tenant identifier, breaking the binding between "shop authenticated by HMAC" and "shop the app acts on."

### Finding Description
`Request#to_signable_string` returns only the raw request body: [1](#0-0) 

All the other identifying fields are pulled straight from headers with no cryptographic binding to that signature: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` only checks the HMAC over `to_signable_string`, i.e. the body — it never touches `shop`, `topic`, or `webhook_id`: [4](#0-3) 

`Registry.process` treats a passing HMAC check as full authentication of the request, then forwards the header-derived, unverified `shop` value directly to the app's handler as the tenant identity: [5](#0-4) 

`WebhookMetadata.shop` is a plain struct field with no further validation, and is the value host applications use to key tenant state: [6](#0-5) 

This is structurally the same class of bug as the reported issue: a value that is *acted on* (here, the `shop` field used to key tenant-specific webhook processing) is not covered by the security check (the HMAC) that is supposed to authenticate the request as legitimately belonging to that shop. The equality that should hold is:

`shop verified by HMAC == shop the handler acts on`

but the code actually enforces only:

`body verified by HMAC` (unrelated to the `shop` header used downstream)

### Impact Explanation
Any unprivileged internet user who can obtain one valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` — trivially available to any merchant/attacker who installs the public app on their own store and receives one legitimate webhook — can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or topic/webhook-id) header with an arbitrary victim shop domain. `HmacValidator.validate` still passes because it only checks the body. `Registry.process` will then invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen domain, causing the host application to process (and potentially persist or act on) attacker-supplied data under a victim tenant's identity — a cross-tenant identity confusion originating purely from this gem's webhook verification logic.

### Likelihood Explanation
The webhook endpoint is by design a public, unauthenticated HTTP endpoint (any internet host can POST to it), and obtaining one valid signed body is straightforward for anyone who can install the app on any store (public apps allow free installation). No access token, `client_secret`, or privileged access is required — only a single legitimately-delivered webhook capture, satisfying the "unprivileged internet user" and "no privileged credentials" scoping constraints.

### Recommendation
Include the identity-critical headers (`shop`, `topic`, `webhook_id`) in the signable content verified by the HMAC, or otherwise cryptographically bind them (e.g., derive the shop from a signed value rather than a raw header) before passing them to `WebhookMetadata`/the handler. At minimum, `Utils::HmacValidator` should validate a canonical representation that includes these headers, not just the raw body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and legitimately receives one webhook, capturing the raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (both are signed correctly against `api_secret_key`).
2. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and same header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Request.new` accepts the headers as-is; `HmacValidator.validate` computes the HMAC over `B` only and it matches `H`, so `Registry.process` proceeds:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request) # passes
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)) # shop == "victim-shop.myshopify.com"
```
4. The app's handler executes tenant-scoped logic believing the webhook genuinely originated from `victim-shop.myshopify.com`, even though only `attacker-shop.myshopify.com`'s webhook data was ever HMAC-verified.

          received_signature = verifiable_query.hmac
