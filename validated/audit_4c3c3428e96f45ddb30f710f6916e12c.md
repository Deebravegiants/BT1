### Title
Webhook shop/topic/id headers are not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signable string from the raw body only, but `Registry.process` trusts the unsigned `shop`, `topic`, and `webhook_id` header values to route and label the webhook payload to a tenant.

### Finding Description
The binding that should hold is: `hmac_verified_bytes == bytes_the_handler_acts_on`. In practice this breaks down to: `to_signable_string == raw_body` (only the JSON body) [3](#0-2) , while `shop`, `topic`, and `webhook_id`, the fields the handler uses to attribute the payload to a merchant/topic, come from `shopify_header("shop-domain")`, `shopify_header("topic")`, and `shopify_header("webhook-id")` [4](#0-3) , which are plain HTTP headers with no cryptographic binding to the HMAC.

`Registry.process` calls `Utils::HmacValidator.validate(request)` which only recomputes the HMAC against `to_signable_string` (the body) and compares it to the `hmac-sha256` header value [5](#0-4) . If that check passes, `process` proceeds to dispatch `WebhookMetadata.new(topic: request.topic, shop: request.shop, ..., webhook_id: request.webhook_id)` to the registered handler [2](#0-1) .

Because an attacker without the app's `client_secret`/`api_secret_key` cannot forge a valid HMAC for an arbitrary body, this is not directly exploitable by a fully unprivileged internet user in isolation. However, this design still breaks the intended identity binding "bytes verified vs bytes parsed": any party who can obtain one valid `(body, hmac)` pair for a legitimate webhook — e.g., by owning a test/development shop that installs the same app, or by observing a webhook delivery to a public endpoint — can replay that exact `(body, hmac)` pair while substituting `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) headers naming a different, victim shop. The HMAC check still passes because it never covers those headers, so `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from the victim shop, even though it did not.

### Impact Explanation
This crosses a tenant boundary: an app's webhook handler may perform shop-scoped side effects (e.g., updating local records keyed by `shop`, or GDPR/redact processing for `shop/redact` and `customers/redact`) based on a `shop` value that is not authenticated by the HMAC. An attacker with access to any one valid webhook delivery (e.g., their own store) can inject fabricated events attributed to a different merchant's shop domain into the host app, corrupting that merchant's data without ever compromising Shopify or the app's secret. This matches the report's underlying theme of an identity/security check ("hmac validated") being interpreted as covering data ("shop", "topic") it doesn't actually bind.

### Likelihood Explanation
Exploitation requires the attacker to first obtain one genuine, HMAC-valid webhook body — feasible for anyone who can install the app on a shop they control (a very low bar, since Shopify app installation for a dev/test store is unprivileged) — and then replay it with a modified `shop-domain` header to the app's public webhook endpoint. No possession of `api_secret_key`, access tokens, or the target merchant's credentials is required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string covered by the HMAC verification, or otherwise cryptographically bind them to the body (e.g., verify `shop` against a value looked up server-side using `webhook_id`, or require it to match the session/shop the app expects for this endpoint), so header values cannot be swapped independently of the signed payload.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw body `B` and the resulting `X-Shopify-Hmac-Sha256` header `H` computed by Shopify over `B` using the app's shared secret.
2. Attacker sends `POST <victim-app>/webhooks` with body `B` unchanged, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds [6](#0-5) .
4. The registered handler is invoked with `WebhookMetadata` reporting `shop: "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own shop, letting the attacker inject cross-tenant webhook data into the host application's shop-scoped processing.
