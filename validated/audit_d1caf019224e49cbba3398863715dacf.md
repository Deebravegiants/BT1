### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) header is trusted for tenant identity while excluded from the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but defines `to_signable_string` to return only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop` as the tenant identity handed to app-defined webhook handlers, without that value ever being bound by the signature.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and comparing to `verifiable_query.hmac`: [1](#0-0) 

For `Webhooks::Request`, `to_signable_string` returns solely `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all parsed directly from HTTP headers that are never part of the signed material: [3](#0-2) 

`Registry.process` validates the HMAC (over body only) and then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` as authenticated tenant/event metadata, forwarding them to the app's registered handler: [4](#0-3) 

This breaks the identity binding: `HMAC-verified(body) == HMAC-verified(shop)` is assumed true by `Registry.process`, but the equality the code actually enforces is only `HMAC-verified(body)`. `request.shop` (and `topic`/`webhook_id`) can be swapped to any value without invalidating the signature, since the signature never covered them in the first place. This is exactly the analog class called out in the rules: "a field acted on but not covered by the HMAC."

Concretely, any actor who can obtain one valid `(body, hmac)` pair signed with the app's `client_secret` — e.g., an attacker who installs/operates their own shop with this app and triggers a webhook event carrying attacker-chosen body content — can replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to name a different, victim shop. `HmacValidator.validate` will still return `true` because it only checks the body, and `Registry.process` will invoke the app's handler with `WebhookMetadata` claiming the victim shop as the source of that (attacker-controlled) payload.

### Impact Explanation
This crosses a tenant boundary purely through this gem's own verification logic: the `shop` value handed to the app's webhook handler is not actually bound to the cryptographic proof of authenticity, so an app that keys its per-tenant behavior (session lookup, data writes/deletes, GDPR redaction routines for `shop/redact`, `customers/redact`, uninstall handling, etc.) off `WebhookMetadata#shop` can be made to act on a shop it did not receive a genuine webhook from. This matches the "cross-tenant access" Critical impact category defined in scope.

### Likelihood Explanation
The attacker only needs their own (or any) shop's genuine app installation to legitimately trigger one webhook delivery and capture its raw body + `X-Shopify-Hmac-Sha256` value — no access to the app's `client_secret`, access tokens, or any other shop's credentials is required. The replay itself is a trivial HTTP request with one header changed, so likelihood is high once an attacker controls or monitors any shop that has the target app installed.

### Recommendation
Include the tenant/event-identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) inside `to_signable_string` so they are covered by the HMAC, or otherwise bind them cryptographically before they are trusted by `Registry.process`. At minimum, document that consumers of `ShopifyAPI::Webhooks::Request` must not rely on `shop`/`topic`/`webhook_id` for authorization decisions without independent verification (e.g., cross-checking against a shop that is known to have a live, previously-registered session), and consider adding delivery de-duplication/replay protection keyed on `webhook_id` plus a freshness check.

### Proof of Concept
```ruby
# Attacker owns/operates "attacker-shop.myshopify.com" with the target app installed.
# They trigger any webhook (e.g. orders/create) and capture the raw POST body + the
# X-Shopify-Hmac-Sha256 header Shopify sent, both signed correctly with the app's client_secret.

captured_body = '{"id":1,"malicious":"payload"}'
captured_hmac_b64 = "‹captured valid Base64 HMAC for captured_body›"

# Replay to the same webhook endpoint, but swap the shop-domain header to the victim shop.
headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => captured_hmac_b64,
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged, not covered by HMAC
  "x-shopify-webhook-id"   => "attacker-chosen-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: headers)

# Passes validation because HmacValidator only checks captured_body, never the shop header:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process now dispatches to the handler believing this came from victim-shop:
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", ...))
