### Title
Webhook `shop` and `topic` identity fields are unauthenticated (not covered by HMAC) while the raw body is verified - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `webhook_id`, and `api_version` purely by reading HTTP headers, while `to_signable_string` (used by `Utils::HmacValidator.validate`) only returns `@raw_body`. The HMAC therefore proves the JSON body was signed by Shopify with the app's secret, but it proves nothing about which shop or topic the request headers claim to be for.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` and `Request#topic` are derived exclusively from headers, which are attacker-controlled data on the wire and are never mixed into the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string`, which for a webhook request is only the body: [3](#0-2) 

The identity binding that should hold is: `shop-domain header == shop the HMAC-signed body was generated for`. Because the header is outside the HMAC, an attacker who can reach the app's public webhook endpoint (no secret required) can replay/craft a request with a *valid* `X-Shopify-Hmac-Sha256` for some body (e.g., by replaying a legitimately-received webhook payload for shop A) but substitute the `X-Shopify-Shop-Domain` and `X-Shopify-Topic` headers for shop B or a different topic. `HmacValidator.validate` will still return `true` because it only checks the body bytes, not the headers the host application will use to route/act on the event as belonging to a specific tenant.

### Impact Explanation
This breaks the tenant-authentication boundary: any code that trusts `Webhooks::Request#shop`/`#topic` after `HmacValidator.validate` returns true (as documented/intended usage of this gem) can be tricked into processing a cross-tenant event under the wrong shop identity, since the HMAC provides no binding between body and headers. This matches "Cross-tenant access" under the Critical impact bucket, since the gem's own verification primitive returns "valid" while the identity fields the host app is expected to rely on are forged.

### Likelihood Explanation
Requires only network access to the app's public webhook endpoint and a previously-observed (or intercepted, non-TLS-required) legitimately signed payload/HMAC pair for any topic/shop — no `api_secret_key`, access token, or privileged account needed, matching the unprivileged-internet-user threat model. Likelihood is moderate: the attacker needs one valid `(body, hmac)` pair to replay with forged headers, which is plausible since webhook bodies/HMACs are not bound to a nonce or timestamp field checked by this library either.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed input (or otherwise incorporate them into `to_signable_string`), so that any tampering with the headers invalidates the signature, restoring the `header == verified data` binding.

### Proof of Concept
1. Attacker captures/observes a legitimately signed webhook body+HMAC pair for `topic=orders/create`, `shop-domain=shop-a.myshopify.com` (this is possible without secrets since bodies/HMACs traverse the network and are not confidentiality-protected by this gem).
2. Attacker (or a compromised intermediary/malicious webhook relay) POSTs the same `raw_body` and same `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com` and/or a different `X-Shopify-Topic`.
3. App code calls `ShopifyAPI::Utils::HmacValidator.validate(request)` → returns `true`, because validation only hashes `@raw_body`. [1](#0-0) 
4. App proceeds to call `request.shop` / `request.topic` to route the (now-verified-looking) event to shop B's tenant data, using attacker-controlled header values that were never authenticated. [2](#0-1)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
