### Title
Unbounded state-proof verification cost during unsigned-extrinsic mempool validation causes CPU-exhaustion DoS - ([File: modules/pallets/state-coprocessor/src/lib.rs])

### Summary
CVE-2016-1499 is an ownCloud bug where an unprivileged authenticated user could pass a `force` parameter to `ajax/scan.php` and trigger an unbounded, expensive recursive directory scan on the server, causing CPU exhaustion. The Hyperbridge analog is `pallet_state_coprocessor::Pallet::validate_unsigned`, which runs the *entire* expensive state-proof verification pipeline (`handle_get_requests`) synchronously during transaction-pool validation of an unsigned, permissionless extrinsic, with no bound on the number of `GetRequest`s or keys in the batch.

### Finding Description
`pallet_state_coprocessor::Call::handle_unsigned` takes an unsigned origin (`ensure_none`) and is intended to be gossiped and validated by every node's mempool before block inclusion: [1](#0-0) 

Critically, `validate_unsigned` does not perform a cheap, structural check before accepting the transaction into the pool — it directly calls `Self::handle_get_requests(message.clone())`, the *same* full-cost function used at actual dispatch time: [2](#0-1) 

`handle_get_requests` performs, per request in the batch: membership-proof verification against the source chain state root, and destination state-proof verification (trie construction and lookups) for every key in every `GetRequest`: [3](#0-2) 

For EVM destinations, `verify_state_proof` groups keys by contract and, for each distinct contract referenced, clones the *entire* contract proof and rebuilds a trie to resolve the account/storage root before verifying any key against it — the code's own comments note this cost: [4](#0-3) [5](#0-4) 

Because this whole pipeline runs inside `validate_unsigned`, which every full node executes on every unsigned transaction it receives over the network (before any economic cost or inclusion has occurred), an attacker who crafts a `GetRequestsWithProof` batch with a large number of `GetRequest`s (each carrying many distinct-contract keys, up to the node's extrinsic-size limit) forces every peer's mempool to perform full state/trie verification work repeatedly:
- Once when the transaction is first gossiped/validated by each peer node (`validate_unsigned`).
- Again on every block for the transaction's `longevity` window (25 blocks) as the pool re-validates queued transactions.
- Optionally, once more at actual dispatch if it ever gets included.

There is no bound (`MaxKeys`, `MaxRequests`, or similar) on the number of `GetRequest`s per batch or the number of `keys` per `GetRequest` enforced before this expensive verification runs; the only implicit ceiling is the block/extrinsic size limit, but proof-verification cost (trie walks, RLP decode, cloning of "unrequested"/entire contract proofs) scales with the number of distinct contracts and keys, not merely the raw byte size, making the CPU cost disproportionate to the bytes gossiped. This is the direct structural analog of the ownCloud bug: an unauthenticated/unprivileged (here, permissionless unsigned) request parameter triggers a full, un-throttled recursive scan/verification operation before any authorization or economic gate is applied.

### Impact Explanation
This is a network-wide CPU-consumption denial-of-service vector reachable by any actor able to gossip a transaction (no signature, no fee, no prior state required — `ensure_none` origin). Because `validate_unsigned` is executed by every node in the network's mempool (and re-validated across the `longevity` window and on propagation to peers), an attacker can multiply a modest amount of submitted data into disproportionate CPU cost across the entire relayer/validator set, degrading block production and honest relayer/message-delivery throughput — impairing the "route unable to deliver messages" criterion in scope.

### Likelihood Explanation
High likelihood: the call is explicitly `ensure_none` / permissionless and designed to be free (per pallet-ismp docs, "Execute the provided batch of ISMP messages for free"), so no stake, fee, or authorization gates the attempt. An attacker needs only to construct a syntactically valid (or partially valid) `GetRequestsWithProof` with many distinct-contract keys or many GetRequests to make each validation pass costly, and can resubmit continuously.

### Recommendation
- Add cheap, size-based bounds (e.g., `MaxRequestsPerBatch`, `MaxKeysPerRequest`) enforced in `validate_unsigned` *before* calling `handle_get_requests`, rejecting oversized batches immediately.
- Consider a lightweight pre-check (e.g., cap on total distinct contract addresses / proof node count) prior to running full trie verification during mempool validation.
- Rate-limit or require minimal economic cost (e.g., a bond or weight-fee even for unsigned extrinsics) to prevent free resubmission at scale.
- Apply the same bound checks to `pallet_ismp::handle_unsigned`'s message batch, which likewise executes `Self::execute(messages.clone())` unbounded (this repo's `handle_unsigned` doc explicitly says it filters malformed/invalid-proof messages via the same validity check performed at pool level, meaning the full processing cost is already paid at validation time for every message in the batch).

### Proof of Concept
Conceptual (not executed): craft a `GetRequestsWithProof` with N `GetRequest`s, each referencing M distinct EVM contract addresses (52-byte keys with distinct 20-byte contract prefixes) within the size budget of a normal extrinsic, and an accompanying `response.proof` blob containing plausible-looking but ultimately invalid contract/storage proofs. Submit as an unsigned extrinsic to `StateCoprocessor::handle_unsigned`. Every receiving node's `validate_unsigned` will execute `handle_get_requests`, which will iterate N×M keys, clone/reconstruct a trie per distinct contract, and only fail late in verification — the CPU cost is paid by every node in the gossip path regardless of the transaction's ultimate validity, and can be repeated by resubmitting variants (to bypass the `provides` tag dedup) indefinitely at negligible attacker cost.

				propagate: true,
			})
