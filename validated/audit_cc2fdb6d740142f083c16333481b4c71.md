### Title
Infinite-retry PCP upload loop can permanently starve upload slots and DoS the signup/enrollment pipeline for all subsequent users - (File: `src/agents/data_uploader.rs`)

### Summary
This is an analog of the reported "queued item never cleared" DoS class: in the referenced report, a single blacklisted withdrawal recipient permanently jams a sequential processing loop because the failing item is never removed. In `orb-core`, the Data Uploader agent's `upload_pcp` retry loop has the same structural flaw: a single Personal Custody Package (PCP) upload that the backend persistently fails to accept (with any error that isn't classified as an HTTP 4xx client error) is retried forever with no backoff, no retry cap, and no path to abandon/clear the item. Because only a small, fixed number of upload slots exist, a handful of such stuck uploads can permanently consume all available capacity, after which the queue never drains and every subsequent legitimate signup blocks indefinitely waiting on the queue.

### Finding Description
`Agent::upload_pcp` retries the upload request in an unconditional `loop`, breaking out only on success or when the error is a `reqwest::Error` carrying an explicit HTTP client-error (4xx) status code: [1](#0-0) 

Any other failure mode — a persistent 5xx from the backend, a connection reset, a TLS/DNS failure, or a timeout that doesn't surface as a `reqwest::Error` with a `.status()` — causes the loop to retry forever without ever completing. Since the future returned by `upload_pcp` is what the main agent loop awaits via `uploaders.next()`, a never-completing upload permanently occupies one of the limited `PARALLEL_UPLOAD_STREAMS` (4) concurrent slots: [2](#0-1) [3](#0-2) 

The agent only refills an upload slot when an existing upload in `uploaders` resolves (`Some((tier, id)) = uploaders.next()`), so a stuck upload is never replaced. As more signups occur and their tier-1/tier-2 PCPs get pushed, per-tier queues grow. Once a queue reaches `pcp_tier{1,2}_blocking_threshold`, `check_blocking` reports `true` and any caller of `WaitQueues` is queued in `waiters`, which are only ever notified from the `uploaders.next()` branch — the same branch that a stuck upload prevents from firing for that slot: [4](#0-3) [5](#0-4) 

Critically, `wait_queues()` is called synchronously in the main signup flow before every subsequent user's tier-0 custody package is uploaded, i.e. before enrollment can proceed: [6](#0-5) 

If enough stuck uploads accumulate to hit the blocking threshold, this call never resolves, since `do_signup` propagates the error/hang via `?` and blocks the whole plan. Because `wait_queues` is `await`ed with no timeout, this hangs the signup pipeline for every future user on the orb.

Beyond blocking, once a queue also reaches `pcp_tier{1,2}_dropping_threshold`, the oldest queued PCP (belonging to some other, unrelated legitimate signup) is silently dropped via `drop_oldest()`, permanently losing that user's personal-custody biometric package before it is ever uploaded: [7](#0-6) [8](#0-7) 

### Impact Explanation
A small number of signups whose PCP uploads trigger a persistent non-4xx failure (e.g., a transient-looking but effectively permanent backend error, or any error path not classified as `reqwest` 4xx) can occupy all `PARALLEL_UPLOAD_STREAMS` slots forever. This:
1. Blocks `data_uploader::wait_queues` indefinitely for every subsequent signup attempt on the orb, effectively bricking the orb's ability to complete any further enrollments (denial of service against the signup/enrollment pipeline).
2. Once the dropping threshold is reached, causes silent loss of other users' tier-1/tier-2 personal custody packages (biometric data never gets uploaded/retained), which is a data-loss/integrity impact analogous to state bleed between unrelated signups.

This matches the reported bug class: a single unprocessable, never-cleared queue item permanently disables processing for all future, unrelated legitimate participants.

### Likelihood Explanation
No malicious or privileged actor is required — the trigger is simply a PCP upload that the backend fails to accept for reasons other than a clean 4xx (e.g., backend-side validation quirks, oversized/malformed payload triggering repeated 5xx, network instability classified as a non-HTTP error). Given `PARALLEL_UPLOAD_STREAMS` is only 4, it takes very few "poisoned" uploads to exhaust all slots. Since orb-core already handles adversarial/edge-case biometric and QR inputs from unprivileged users during normal operation, hitting a backend condition that isn't cleanly classified as a 4xx is plausible over the lifetime of an orb's operation, especially given the retry loop has no delay/backoff and will hammer the backend endpoint continuously while stuck.

### Recommendation
- Bound `upload_pcp`'s retry loop with a maximum retry count / total elapsed time (similar to the `RETRIES_COUNT` pattern already used in `upload_pcp_tier_0` in `src/plans/mod.rs`), and treat exhaustion as a terminal failure that always returns `(tier, id)` so the slot is freed and the item is discarded or moved to a dead-letter path.
- Add exponential backoff between retries to avoid hammering the backend.
- Ensure `wait_queues` callers use a timeout so a stuck upload cannot indefinitely block the signup pipeline; consider failing open (proceeding without waiting) rather than hanging forever.
- Avoid silently dropping unrelated in-flight PCPs (`drop_oldest`) as the sole overflow strategy without alerting/telemetry that biometric data is being permanently lost.

### Proof of Concept
1. Configure/observe a backend condition where uploads for a given PCP consistently fail with a non-4xx error (e.g., a 500, or a network-layer error not exposed as `reqwest::Error::status()`).
2. Trigger `PARALLEL_UPLOAD_STREAMS` (4) signups whose tier-1/tier-2 PCP uploads hit this condition; each spawns an `upload_pcp` future stuck in its infinite retry `loop` (`src/agents/data_uploader.rs:176-215`), permanently occupying a slot in `uploaders`.
3. Perform additional signups; their PCPs queue up in `Queue::Memory`/`Persistent` until `pcp_tier{1,2}_blocking_threshold` is reached.
4. Any subsequent signup calls `data_uploader::wait_queues(...).await?` at `src/plans/mod.rs:599`, which never resolves because `check_blocking` remains `true` and the notifying branch (`uploaders.next()`) never fires for the stuck slots — the signup pipeline hangs indefinitely, and once the dropping threshold is reached, other users' queued custody packages are silently discarded.

    async fn upload_pcp(&self, pcp: Pcp, id: u64) -> (u8, u64) {
        let Pcp { signup_id, user_id, data, checksum, tier } = pcp;
        tracing::info!(
            "Start uploading a personal custody package tier {tier} for signup_id={signup_id}"
        );
        let t = Instant::now();
        loop {
            let response = backend::upload_personal_custody_package::request(
                &signup_id,
                &user_id,
                checksum.as_ref(),
                &data,
                Some(tier),
                &self.config,
            )
            .await;
            match response {
                Ok(()) => {
                    dd_timing!("main.time.signup.upload_custody_images" + format!("t{}", tier), t);
                    tracing::info!(
                        "Personal custody package tier {tier} uploading completed in: {}ms",
                        t.elapsed().as_millis()
                    );
                    break;
                }
                Err(err) => {
                    tracing::error!("UPLOAD PERSONAL CUSTODY PACKAGE TIER {tier} ERROR: {err:?}");
                    dd_incr!(
                        "main.count.http.upload_custody_images.error.network_error",
                        "error_type:normal"
                    );
                    if let Some(reqwest_err) = err.downcast_ref::<reqwest::Error>() {
                        if let Some(status) = reqwest_err.status() {
                            if status.is_client_error() {
                                dd_incr!(
                                    "main.count.signup.result.failure.upload_custody_images",
                                    "type:network_error",
                                    "subtype:signup_request"
                                );
                                break;
                            }
                        }
                    }
                }
            }
        }
        (tier, id)
    }

    async fn drop_oldest(&mut self) {
        match self {
            Self::Memory { queue } => {
                queue.pop_back();
            }
            Self::Persistent { path, queue, .. } => {
                let Some(id) = queue.pop_back() else { return };
                match ssd::perform_async(fs::remove_dir_all(path.join(id.to_string()))).await {
                    None => {
                        tracing::error!(
                            "Persistent queue is failed during drop_oldest, switching to memory"
                        );
                        *self = Self::new_memory();
                    }
                    Some(()) => {}
                }
            }
        }
    }
