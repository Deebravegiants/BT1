### Title
Webhook shop domain is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the shop-identifying field (`shop-domain`) is read from an unauthenticated header and passed straight through to the webhook handler. This breaks the identity binding `shop verified-by-HMAC == shop dispatched-to-handler`, allowing an attacker who possesses one validly-signed webhook body/HMAC pair (e.g. from their own shop's webhook delivery) to relabel it as belonging to a different merchant.

### Finding Description
`Registry.process` verifies the request purely via `Utils::HmacValidator.validate(request)`, which in turn calls `request.to_signable_string`: [1](#0-0) 

`to_signable_string` returns only `@raw_body`: [2](#0-1) 

Meanwhile `shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of the signed payload at all: [3](#0-2) [4](#0-3) 

After `HmacValidator.validate` succeeds (proving only that `raw_body` was signed by the app's secret at some point), `Registry.process` forwards `request.shop` — the unverified header value — straight into `WebhookMetadata`, which is delivered to the app's handler as the tenant identifier: [5](#0-4) [6](#0-5) 

The identity binding that should hold is:
`shop_bound_by_HMAC == shop_delivered_to_handler`

Instead, the actual binding is:
`shop_delivered_to_handler == shop_header (arbitrary, attacker-controlled, unauthenticated)`
while
`HMAC covers == raw_body only`

Since a single `api_secret_key` is shared by the app across all installed shops, any body+HMAC pair that is valid for one shop's webhook delivery is also a valid HMAC for that same body regardless of which shop-domain header accompanies it. An attacker who can obtain one legitimately-signed `(raw_body, hmac)` pair (for example from their own store's webhook deliveries to the same app, or from a captured/replayed delivery) can resubmit that exact body/HMAC to the app's webhook endpoint with a different `X-Shopify-Shop-Domain` header. `Registry.process` will accept it as valid (the HMAC check only validates the body) and dispatch it to the handler labeled as belonging to the spoofed shop.

### Impact Explanation
This allows cross-tenant webhook injection: data intended to be scoped to the attacker's own shop can be delivered to the handler attributed to a victim shop chosen by the attacker (or vice versa — an attacker's own webhook data can be injected disguised as another merchant's). Depending on how the host app trusts `WebhookMetadata#shop` to look up sessions/access tokens or update per-shop state, this can lead to cross-tenant data corruption or unauthorized actions performed under another merchant's identity — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Medium: the attacker needs at least one genuinely-signed webhook body/HMAC pair, which any developer/attacker who installs the app on their own store (a normal, unprivileged action) can obtain, since the app's webhook secret is shared across all shops. No access to `api_secret_key`, access tokens, or privileged accounts is required — only a normal app installation plus the ability to POST to the app's public webhook endpoint with custom headers.

### Recommendation
Bind the shop domain (and other routing metadata such as topic/webhook-id) into the HMAC-signed payload, or independently verify that the `shop-domain` header corresponds to a shop known to have generated the exact `raw_body`/`hmac` pair (e.g., by tracking per-shop webhook secrets, or validating shop against the session store before trusting `WebhookMetadata#shop`) before dispatching to `WebhookHandler#handle`.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) so Shopify sends a legitimately HMAC-signed request: raw body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for secret `S`), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Capture `(B, H)`.
3. POST to the same app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H`, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged shop header (only checks header presence, not correlation to body) and `Registry.process` computes HMAC over `B` only — validation succeeds — and the handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: JSON.parse(B), ...)`, i.e., attacker-controlled data attributed to the victim shop.           raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
