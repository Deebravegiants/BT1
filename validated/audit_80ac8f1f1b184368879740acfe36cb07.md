### Title
SSRF with app credentials via unvalidated `shop` in `Oauth.validate_auth_callback` / `Oauth.begin_auth` — (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the access-token request host directly from `auth_query.shop` and POSTs the app's `client_secret` to `https://#{shop}/admin/oauth/access_token` without ever running the value through `Utils::ShopValidator.sanitize!`, unlike the parallel `ClientCredentials`, `RefreshToken`, and `TokenExchange.migrate_to_expiring_token` flows, which all call `Utils::ShopValidator.sanitize!(shop)` before constructing a `Session`/`HttpClient`.

### Finding Description
The binding that should hold is: `destination host that receives client_secret == a verified *.myshopify.com (or other Shopify-trusted) domain`. In `lib/shopify_api/auth/oauth.rb`:

- `begin_auth` builds `auth_route = auth_base_uri(shop) + "/oauth/authorize?..."` [1](#0-0)  where `auth_base_uri` simply interpolates the caller-supplied `shop` into `"https://#{shop}/admin"` with no domain validation [2](#0-1) .
- `validate_auth_callback` takes `auth_query.shop` and immediately constructs `null_session = Auth::Session.new(shop: auth_query.shop)`, then issues an HTTP POST containing `client_id` and `client_secret` to that `shop`'s `/admin/oauth/access_token` via `HttpClient.new(session: null_session, ...)` [3](#0-2) . `HttpClient` derives the request host straight from `session.shop` with no format check [4](#0-3) .

By contrast, the newer flows explicitly sanitize the shop before using it as a network destination:
- `ClientCredentials.client_credentials` calls `Utils::ShopValidator.sanitize!(shop)` before sending `client_secret` [5](#0-4) .
- `RefreshToken.refresh_access_token` does the same [6](#0-5) .
- `TokenExchange.migrate_to_expiring_token` does the same [7](#0-6) .

`Utils::ShopValidator` exists specifically to restrict outbound hosts to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) [8](#0-7) , but `oauth.rb` never invokes it, so `shop` flows unchecked from `begin_auth`'s caller-supplied argument through to the credential-bearing POST in `validate_auth_callback`.

The `hmac` on the callback only binds `code, host, shop, state, timestamp` together as a self-consistent set signed by the app's own secret [9](#0-8) ; it does not assert that `shop` is a genuine `*.myshopify.com` host — it only proves the tuple wasn't tampered with in transit relative to whatever `shop` value the OAuth initiation step (`begin_auth`) used. Since `begin_auth`'s `shop` argument is taken as-is from the calling application (the documented integration pattern even pulls it from a request header, e.g. `shop = request.headers["Shop"]`), an application that does not itself pre-validate the shop domain will pass an attacker-influenced `shop` straight through `begin_auth` → Shopify redirect → `validate_auth_callback`, and the gem will happily construct the token-exchange request against that host, sending `client_id` and `client_secret` to it.

### Impact Explanation
If the host application does not independently validate `shop` against Shopify's domain format before calling `begin_auth`, an attacker who controls the `shop` value can cause the OAuth flow to redirect to an attacker-controlled host and, more critically, cause `validate_auth_callback` to POST the app's `client_secret` and `client_id` to that attacker-controlled host during the token exchange step — this is SSRF with credential exfiltration of the app's `client_secret`, matching the Critical impact category (credential leakage/theft of the app's client secret). This directly parallels the report's core theme: a value that is trusted for building the network destination is not actually bound to the intended (Shopify) domain, letting an unprivileged party redirect a credentialed request.

### Likelihood Explanation
Likelihood depends on the host application's own input handling of the `shop` parameter passed into `begin_auth`/used to build the `AuthQuery`. The gem's own shipped documentation example demonstrates taking `shop` directly from an HTTP header without sanitization, and the gem provides no built-in guard here (unlike the sibling `ClientCredentials`/`RefreshToken`/`TokenExchange.migrate_to_expiring_token` code paths, which do call `Utils::ShopValidator.sanitize!`). This is a real gap in the gem's own defense-in-depth for the credential-bearing request in `validate_auth_callback`, even though a defensively-coded host app could avoid triggering it.

### Recommendation
In `lib/shopify_api/auth/oauth.rb`, call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the top of `begin_auth` before computing `auth_base_uri(shop)`, and again on `auth_query.shop` inside `validate_auth_callback` before constructing `null_session`/`Session.from`, mirroring the pattern already used in `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb`'s `migrate_to_expiring_token`. This ensures the token-exchange request (which carries `client_secret`) can only ever be sent to a trusted Shopify domain regardless of what `shop` value the caller passes in.

### Proof of Concept
1. A host application built with this gem implements the documented pattern: `shop = request.headers["Shop"]; ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")` without its own shop-format validation.
2. An attacker sends a request with `Shop: attacker-controlled-host.example` (a host the attacker controls, which mimics the Shopify admin OAuth endpoints, e.g. serving `/admin/oauth/authorize` and later `/admin/oauth/access_token`).
3. `begin_auth` builds `auth_route = "https://attacker-controlled-host.example/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=...&state=..."` via `auth_base_uri` [1](#0-0)  and the browser is redirected there.
4. The attacker's server can complete a self-signed "OAuth" round trip: it needs the callback to carry a valid HMAC. Because `AuthQuery`'s HMAC only proves consistency of `code/host/shop/state/timestamp`, and because the host application is the one invoking `validate_auth_callback` with the (still attacker-influenced) `shop` from the callback params, if the host app's callback route reconstructs `AuthQuery` straight from request parameters (as shown in `docs/usage/oauth.md`'s example) and the attacker can get their chosen `shop` echoed with a matching, gem-validated HMAC via any weakness in the host app’s parameter handling, `validate_auth_callback` will send `client_id`/`client_secret` to `https://attacker-controlled-host.example/admin/oauth/access_token` [10](#0-9) , exfiltrating the app's `client_secret`.

Note: full end-to-end exploitation ultimately still requires a valid HMAC over the chosen `shop`, which the gem itself cannot forge without `api_secret_key`; the concrete exploitability therefore hinges on how the host application wires `shop` through its own routes (outside this gem). This PoC should be treated as demonstrating the gem's missing defense-in-depth (absence of `ShopValidator` sanitization in `oauth.rb`) rather than a fully self-contained, gem-only exploit chain — flag this uncertainty when triaging.
