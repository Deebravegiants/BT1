## Finding

### Title
Missing Chainlink round-completeness check in `SimplexPaymaster` oracle pricing - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster._getOraclePrice` consumes Chainlink's `latestRoundData()` but discards `roundId` and `answeredInRound`, checking only that the answer is positive and that `updatedAt` is within `maxOracleAge`. This is the same missing-completeness pattern flagged in the external report against `ChainLinkOracle.sol`.

### Finding Description
`_getOraclePrice` destructures `latestRoundData()` and drops the first (`roundId`) and last (`answeredInRound`) return values entirely: [1](#0-0) 

```solidity
function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
    (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();
    if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
    if (block.timestamp - updatedAt > maxOracleAge) {
        revert StaleOraclePrice(address(oracle), updatedAt);
    }
    ...
}
```

There is no `answeredInRound >= roundId` check anywhere in the contract, matching the exact recommendation gap identified in the external report for `ChainLinkOracle.sol`. The `AggregatorV3Interface` used here does expose both fields, so the values are simply never validated: [2](#0-1) 

This function is the sole entry point for reading both `nativeOracle` and any registered `tokenOracle`, and it is exercised on two unprivileged/near-unprivileged paths:

1. **`_tokenPrice` → `getTokenPrice`/`estimateTokenCost`**, and the paymaster's `validatePaymasterUserOp` flow (via `PaymasterERC20`), which any account can trigger simply by submitting an ERC-4337 `UserOperation` that uses this paymaster to pay gas in a registered token: [3](#0-2) 

2. **`swapAndDeposit`**, which uses the same unchecked price to compute `amountOutMin` for a Uniswap V2 swap of accrued token fees into native currency: [4](#0-3) 

The test suite confirms staleness and non-positive answers are covered, but there is no test or check for round completeness/carry-over answers: [5](#0-4) 

### Impact Explanation
If the underlying Chainlink aggregator answer is carried over from an incomplete/stuck round (`answeredInRound < roundId`) while `updatedAt` still falls inside `maxOracleAge` (feeds with long heartbeats, e.g. the documented "Base/Ethereum stablecoins up to 24h" window noted in the code's own comments), `_getOraclePrice` will accept it as fresh: [6](#0-5) 

Consequences:
- **Mispriced gas payments**: every UserOp sender paying gas in a registered ERC-20 is charged based on a potentially stale/incorrect `tokenUsd`/`nativeUsd` ratio, causing over- or under-charging relative to the true market rate.
- **Weakened slippage protection in `swapAndDeposit`**: `amountOutMin` is derived from the same unchecked price, so a stuck round can shift the computed minimum output away from the true price, letting a sandwich/MEV actor extract value from the treasury-triggered swap that the slippage guard is meant to prevent.

Given the 24h heartbeat windows explicitly acknowledged in this codebase, the gap between "stale by round-completeness" and "stale by timestamp" is materially wide, unlike feeds with sub-minute heartbeats where the timestamp check alone is a strong mitigant.

### Likelihood Explanation
Likelihood is moderate: it requires a genuine Chainlink aggregator malfunction or a round grinding to a halt (has occurred historically, e.g. bridge/aggregator incidents), and it is bounded by `maxOracleAge` — the primary mitigant already in place reduces exploitability. It is a supplementary defense-in-depth gap rather than a trivially triggerable exploit, which is consistent with the Medium severity of the original report.

### Recommendation
Capture `roundId` and `answeredInRound` from `latestRoundData()` and require `answeredInRound >= roundId`, reverting with a new error (e.g. `IncompleteRound`) otherwise, mirroring the fix recommended in the external report:

```solidity
(uint80 roundId, int256 answer, , uint256 updatedAt, uint80 answeredInRound) = oracle.latestRoundData();
if (answeredInRound < roundId) revert IncompleteRound(address(oracle), roundId, answeredInRound);
```

### Proof of Concept
1. Deploy `SimplexPaymaster` with a token registered against a mock/real Chainlink feed.
2. Simulate the feed returning `latestRoundData()` with `answeredInRound < roundId` (a round still in progress, carrying forward the previous answer) but `updatedAt` within `maxOracleAge`.
3. Call `getTokenPrice`/submit a sponsored UserOp, or call `swapAndDeposit` — observe that `_getOraclePrice` accepts the value without reverting, since only `answer <= 0` and the timestamp-staleness checks are enforced (see `evm/src/utils/SimplexPaymaster.sol:662-668`).

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
