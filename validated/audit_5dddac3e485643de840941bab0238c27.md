Based on this analysis, I've confirmed the vulnerability. The docs explicitly promise: "This will verify the request did indeed come from Shopify" — but the verification only binds the raw body, not the `shop` or `topic` fields that are trusted and passed downstream to the app's handler.

### Title
Webhook `shop` and `topic` fields are trusted without HMAC binding, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body [1](#0-0) , so `Utils::HmacValidator.validate` only proves that the *body* bytes are authentic [2](#0-1) . The `shop` and `topic` accessors are read straight from HTTP headers and are never included in the signed material [3](#0-2) . `Registry.process` validates the HMAC and then forwards `request.shop` and `request.topic` unchecked into `WebhookMetadata`, which the host app's handler treats as trustworthy tenant/topic identifiers [4](#0-3) .

### Finding Description
This is the same bug class as the report's "verified bytes vs. acted-on bytes" mismatch (there, `transfer` sent value without accounting for gas semantics; here, the code verifies one set of bytes — the raw body — but *acts on* a different, unverified set of bytes — the `shop-domain` and `topic` headers).

Concretely:
- `hmac` is computed over `@raw_body` only: `Digest.hexencode(Base64.decode64(shopify_header("hmac-sha256")))` is compared against `HMAC-SHA256(secret, raw_body)` [5](#0-4) [6](#0-5) .
- `shop` and `topic` come from `shopify_header("shop-domain")` / `shopify_header("topic")`, i.e., directly from attacker-controllable HTTP headers, with no cryptographic tie to the signature [3](#0-2) .
- The documentation explicitly tells app developers that `Registry.process` "will verify the request did indeed come from Shopify" [7](#0-6) , and instructs handlers to use `data.shop` as the shop identity for downstream actions (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [8](#0-7) .
- All shops installed on a given app share the **same** `api_secret_key` — the HMAC secret is not shop-specific [9](#0-8) .

The identity binding that should hold is: `shop header used by the handler == shop that the HMAC-signed payload was actually generated for`. Because `shop` is outside the signed string, this equality is never checked. A merchant who has installed the app on their own store (an "unprivileged" actor relative to other tenants) legitimately receives real, correctly-HMAC-signed webhook deliveries from Shopify for their own shop. Since the signing secret is shared across all installs of the app, that same merchant can replay the identical `raw_body` + `hmac-sha256` header to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `HmacValidator.validate` still passes (it only checks the body/secret pair), and `Registry.process` dispatches to the handler with `shop` set to the victim's domain [4](#0-3) . Any app logic keyed on `data.shop` (job dispatch, per-tenant data writes, session/record lookups) is confused into acting as if the event belongs to a different tenant.

### Impact Explanation
This matches the "Cross-tenant access" criterion: an attacker with only their own legitimate app installation can inject events that impersonate another merchant's tenant identity into the app's webhook processing pipeline, without ever needing the `api_secret_key`, an access token, or any other privileged credential — they only need a webhook naturally delivered to them by Shopify for their own shop.

### Likelihood Explanation
Moderate-to-high: it requires only that (1) the attacker's own shop has the app installed and receives at least one webhook of the topic they want to forge, and (2) the app's webhook endpoint is reachable and uses this gem's documented `Registry.process`/`Request` flow as instructed in `docs/usage/webhooks.md`. No secrets or elevated access are needed — capturing one's own legitimate webhook delivery (e.g., via browser devtools proxy, or any HTTP logging) is trivial for any merchant who installs the app.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed material, or independently verify that the `shop-domain` header matches an expected/allow-listed value tied to the specific webhook subscription (e.g., cross-check against the webhook registration's expected shop before dispatch), instead of trusting the header value directly in `WebhookMetadata`.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; attacker triggers an event (e.g. `orders/create`) and captures the real webhook POST Shopify sends to the app, including body and `x-shopify-hmac-sha256` header.
2. Attacker resends the identical body and HMAC header to the same webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, raw_body)` and it matches (body/secret are unchanged) [9](#0-8) .
4. `Registry.process` dispatches `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))` [4](#0-3) , and the app processes/stores the event as if it originated from `victim-shop.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
