## Title
Excess native-token payment in `EvmHost.dispatch()`/`fundRequest()` is stranded in the host and never refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` forward the caller's entire `msg.value` to the Uniswap V2 router's `swapETHForExactTokens`, but never verify that the amount sent equals the amount actually required, nor do they refund any leftover ETH back to the original depositor. This is the exact bug class in the reference report — an app accepts more native token than needed and the surplus is left unaccounted for in the contract instead of returning to the payer.

### Finding Description
In `EvmHost.dispatch(DispatchPost)`: [1](#0-0) 

and identically in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest()`: [3](#0-2) 

In each case, `msg.value` is passed in full to `swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. The standard Uniswap V2 Router `swapETHForExactTokens` implementation only spends `amounts[0]` (the ETH actually required for the exact-output swap) and refunds `msg.value - amounts[0]` via `TransferHelper.safeTransferETH(msg.sender, ...)`. Since `EvmHost` itself is the direct caller of the router (not the original transaction sender), that refund lands back on `EvmHost`'s own balance rather than being returned to `_msgSender()`. `EvmHost` accepts native ETH via its `receive()` function, confirmed in the ABI/ typescript bindings, so this refund silently increases the host's own balance.

Unlike this code path, the same repository's `IntentGatewayV2` and `intentsv2` contracts explicitly track any unspent `msgValue` after a swap/dispatch and refund it to the caller in the same transaction, e.g.: [4](#0-3) 
and [5](#0-4) 

This shows the correct pattern is well understood elsewhere in the codebase, but `EvmHost.dispatch`/`fundRequest` — the primary entry points used by every application dispatching a cross-chain message with native-token fee payment — omit it entirely.

Once stranded in `EvmHost`, this ETH is indistinguishable from legitimate protocol fee revenue and can only be recovered through the privileged, cross-chain-governed `withdraw()` function: [6](#0-5) 

There is no user-facing mechanism to reclaim the specific overpaid amount — it is permanently commingled with real bridge revenue and swept to whatever beneficiary the `hostManager` designates.

### Impact Explanation
Any unprivileged user or application calling `IDispatcher(host).dispatch{value: ...}(...)` or `fundRequest{value: ...}(...)` with more native token than is actually consumed by the Uniswap swap (e.g. due to price movement between quote and execution, front-end estimation slack, or accidental overpayment as in the original report) permanently loses the difference. The funds are not stolen by a front-runner in the same block as in the referenced report, but they are permanently and irrecoverably absorbed into the host contract's balance and only extractable by governance's `withdraw()`, not by the original payer — this is a permanent loss of user funds, matching the accepted "permanent freezing/loss of funds" impact category. Given `dispatch()`/`fundRequest()` are the core, most-used entry points of the entire messaging protocol (every `HyperApp` cross-chain call that pays with native token routes through these), the surface area is broad.

### Likelihood Explanation
The documentation itself warns that `quote()` (used off-chain to estimate the exact fee to send) is vulnerable to sandwich attacks and price movement, explicitly telling integrators to expect their `msg.value` to differ from the exact amount needed: [7](#0-6) 
This means overpayment via `dispatch{value: msg.value}` is a normal, expected occurrence in production usage (any slippage between off-chain quote and on-chain execution), not an edge case — making the likelihood high.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, after calling `swapETHForExactTokens`, compute the unspent portion of `msg.value` (e.g. from the returned `amounts[0]`) and refund it to `_msgSender()` in the same transaction, mirroring the pattern already used in `IntentGatewayV2._createOrder`/`fillOrder` (`_sendValue(msg.sender, msgValue)`).

### Proof of Concept
1. Caller estimates `post.fee` in fee-token terms and calls `IDispatcher(host).dispatch{value: X}(post)`, where `X` is slightly more than the amount actually required to acquire `post.fee` of fee-token via Uniswap (common due to price movement between off-chain quoting and on-chain execution, as the docs themselves warn against on-chain `quote()` use due to sandwich risk).
2. `EvmHost.dispatch` calls `swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)` [8](#0-7) .
3. The router spends only `amounts[0] < X` and refunds `X - amounts[0]` to `msg.sender` of the swap call, which is `EvmHost`, not the original caller.
4. `EvmHost`'s native balance increases by `X - amounts[0]`; the original caller receives no refund and has no function to reclaim it.
5. The surplus is now indistinguishable from legitimate fee revenue and can only leave the contract via the governance-restricted `withdraw()` [9](#0-8) , permanently out of reach of the original payer.

     * @dev withdraws host revenue to the given address, can only be called by cross-chain governance
     * @param params, the parameters for withdrawal

    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }
