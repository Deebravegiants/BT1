### Title
Relayer fee accounting on `pallet-ismp-relayer::Fees` is corrupted when an `EvmHost`'s `feeToken` is changed to a token with different decimals - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
`pallet-ismp-relayer` accumulates relayer rewards as raw, decimal-agnostic `U256` amounts in the `Fees` storage map, keyed by the destination chain and relayer address. When a relayer later calls `withdraw`, the pallet reads the **current** `feeToken` configured on that chain's `EvmHost` and instructs it to pay out the raw accumulated amount in that token, with no rescaling. If governance changes `EvmHost.feeToken` to a token with a different decimal count in between the time fees were accumulated and the time they are withdrawn, the payout amount is wrong by orders of magnitude — the exact bug class described in the external report for `PaymentSettler`, reproduced here in `pallet-ismp-relayer`.

### Finding Description
`Fees::<T>` is credited in raw units taken directly from proven `RequestCommitments[...].fee` values on the source chain, with no decimals metadata stored alongside the balance: [1](#0-0) 

`withdraw` later reads `available_amount = Fees::<T>::get(dest_chain, address)` — the raw accumulated units — and dispatches a `WithdrawalParams` request whose `token` field is populated from the **live** `HostParams::<T>::get(dest_chain)` lookup, not from whatever `feeToken` was active when each `Fees` increment happened: [2](#0-1) 

On the EVM side, `EvmHost.updateHostParamsInternal` allows the `feeToken` to be swapped to any new address, and its only safety check is that the **host contract's own current ERC20 balance** of the *old* token is zero — it has no visibility into, and does not consider, relayer fee balances accrued on Hyperbridge's `pallet-ismp-relayer`: [3](#0-2) [4](#0-3) 

Because `Fees` and the `EvmHost`'s ERC20 balance are two independently-updated ledgers, it is entirely possible for the host's own balance to be zero (e.g. after governance sweeps revenue via `withdraw`/`WithdrawParams`) while relayers still hold nonzero, unclaimed `Fees` credit that was denominated in the *old* token's decimals. Once `feeToken` is swapped to a token with different decimals (e.g. 6-decimal USDC → 18-decimal DAI, or vice versa), any subsequent `withdraw()` call pays out the stale raw amount as if it were still denominated in the old decimals, off by a factor of `10^Δdecimals`.

This mirrors exactly the reported `PaymentSettler` bug class: accounting state is captured/accumulated based on one token's decimals and later consumed against a different token's decimals without conversion, after a governance-controlled token swap.

### Impact Explanation
- If decimals decrease (e.g. 18 → 6), relayers are paid `10^12`-times less than owed — permanent, unrecoverable loss of relayer fee income (the `Fees` entry is zeroed on withdrawal regardless of amount actually paid, per `Fees::<T>::insert(dest_chain, address, U256::zero())`).
- If decimals increase (e.g. 6 → 18), relayers are paid `10^12`-times more than owed, draining the new fee token from the `EvmHost`/host manager far beyond what governance intended — a direct theft-of-funds vector against the protocol's treasury/host balance.
- The trigger requires only a normal governance `feeToken` update (a supported, expected operational action per the code comments — "It's important that before changing this parameter, that all funds have been drained from the previous feeToken") followed by an ordinary, permissionless relayer `withdraw` extrinsic. No malicious admin/governance behavior is needed; the bug fires under entirely honest operation whenever a feeToken swap occurs while relayer credit is outstanding.

### Likelihood Explanation
`feeToken` changes are a documented, supported governance operation (`EvmHostParamUpdate.fee_token`), and relayers routinely accrue `Fees` balances continuously as part of normal protocol operation. The existing guard (`CannotChangeFeeToken`) only checks the host contract's own balance of the *old* token, giving operators false confidence that a swap is "safe" while leaving Hyperbridge-side relayer accounting completely unprotected. Any relayer with an outstanding balance who withdraws after such a swap triggers the miscalculation — a Medium-to-High likelihood scenario in a protocol whose docs explicitly instruct fee-token rotation.

### Recommendation
Track the decimals (or the specific feeToken address) associated with each `Fees` credit at accumulation time, and either: (1) settle/flush all pending relayer `Fees` for a chain before permitting a `feeToken` update on that chain (extending the existing `CannotChangeFeeToken` invariant to also check `pallet-ismp-relayer::Fees` totals for that state machine), or (2) store fee credits with an explicit decimals tag and rescale at withdrawal time to the currently configured `feeToken`'s decimals.

### Proof of Concept
1. Relayer delivers several messages destined for `EVM-X`, whose `EvmHost.feeToken` is a 6-decimal stablecoin (e.g. USDC). Source-chain `RequestCommitments[...].fee` values are proven and accumulated via `accumulate()`, crediting `Fees::<EVM-X>(relayer) = 1_000_000` (i.e. $1.00 in 6-decimal units).
2. Governance/host-executive sweeps the host's USDC balance to zero via `IHostManager.withdraw` (an unrelated, routine treasury withdrawal), then calls `updateHostParams` to swap `feeToken` to an 18-decimal token (e.g. DAI). `updateHostParamsInternal`'s check at `evm/src/core/EvmHost.sol:617-621` passes because the *host's* USDC balance is 0 — it has no knowledge of the relayer's pending `1_000_000`-unit claim.
3. The relayer calls `pallet-ismp-relayer::withdraw` for `dest_chain = EVM-X`. `withdrawal.rs` reads the current `HostParams` (now DAI, 18 decimals) and dispatches `WithdrawalParams{ amount: 1_000_000, token: <DAI address> }`.
4. `EvmHost.withdraw` (restricted to `hostManager`) executes `IERC20(DAI).safeTransfer(relayer, 1_000_000)` — the relayer receives `0.000000000001` DAI instead of the `$1.00` they were owed, an under-payment of 12 orders of magnitude (or, in the reverse decimals direction, a corresponding over-payment/drain).     /**
     * @dev Updates the HostParams. Will reset all fishermen accounts and initialize any new state machines.
     * @param params, the new host params.
     */
    function updateHostParamsInternal(HostParams memory params) internal {
        // check the params to prevent the host from getting bricked.
        if (
            params.hostManager == address(0) || address(params.hostManager).code.length == 0
                || !IERC165(params.hostManager).supportsInterface(type(IApp).interfaceId)
        ) {
            // otherwise cannot process new cross-chain governance requests
            revert InvalidHostManager();
        }

        if (
            params.handler == address(0) || address(params.handler).code.length == 0
                || !IERC165(params.handler).supportsInterface(type(IHandlerV2).interfaceId)
        ) {
            // otherwise cannot process new datagrams
            revert InvalidHandler();
        }

        if (
            params.consensusClient == address(0) || address(params.consensusClient).code.length == 0
                || !IERC165(params.consensusClient).supportsInterface(type(IConsensusV2).interfaceId)
        ) {
            // otherwise cannot process new consensus datagrams
            revert InvalidConsensusClient();
        }

        // otherwise cannot process new cross-chain governance requests
        if (keccak256(params.hyperbridge) == keccak256(bytes(""))) revert InvalidHyperbridgeId();

        // otherwise cannot process new datagrams
        uint256 stateMachinesLen = params.stateMachines.length;
        if (stateMachinesLen == 0) revert InvalidStateMachinesLength();

        // otherwise cannot process new datagrams
        if (1 days > params.unStakingPeriod) revert InvalidUnstakingPeriod();

        address oldFeeToken = feeToken();
        if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
            uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
            if (balance != 0) revert CannotChangeFeeToken();
        }

        // safe to emit here because invariants have already been checked
        // and don't want to store a temp variable for the old params
        emit HostParamsUpdated({oldParams: _hostParams, newParams: params});

        _hostParams.feeToken = params.feeToken;
        _hostParams.admin = params.admin;
        _hostParams.handler = params.handler;
        _hostParams.hostManager = params.hostManager;
        _hostParams.uniswapV2 = params.uniswapV2;
        _hostParams.unStakingPeriod = params.unStakingPeriod;
        _hostParams.challengePeriod = params.challengePeriod;
        _hostParams.consensusClient = params.consensusClient;
        _hostParams.stateMachines = params.stateMachines;
        _hostParams.hyperbridge = params.hyperbridge;

        // add whitelisted state machines
        for (uint256 i = 0; i < stateMachinesLen; ++i) {
            // create if it doesn't already exist
            if (_latestStateMachineHeight[params.stateMachines[i]] == 0) {
                _latestStateMachineHeight[params.stateMachines[i]] = 1;
            }
        }
    }
