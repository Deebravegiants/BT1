### Title
Webhook Shop Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated once the HMAC check passes, then hands the caller-supplied `shop-domain` header to the app's handler as trusted tenant identity. The HMAC signature, however, only ever covers the raw request body — it never covers the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. Any party capable of obtaining one validly-signed webhook (e.g., any merchant who installs the app) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, and the gem will report it as verified.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field with a constant-time comparison: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from attacker-controllable HTTP headers, with no cryptographic tie to the signature: [3](#0-2) 

`Registry.process` performs exactly one check — HMAC over the body — and then immediately forwards the unauthenticated `request.shop` value into `WebhookMetadata` as the tenant identity for the handler: [4](#0-3) 

The documented contract for this API tells integrators that `process` "will verify the request did indeed come from Shopify" and that `data.shop` is simply "The shop domain of the webhook," encouraging host apps to key persistence/dispatch (e.g., `perform_later(shop_domain: data.shop, ...)`) directly off this field: [5](#0-4) [6](#0-5) 

The broken identity binding, stated as an equality that should hold but doesn't:
`shop_identity_trusted_by_handler (header "shop-domain")` == `shop_identity_covered_by_HMAC (∅, since to_signable_string == raw_body only)`

Because the app's `client_secret` (`api_secret_key`) is shared across every shop that installs the app, any merchant who installs the app receives their own validly-HMAC'd webhook deliveries. That merchant can capture one such delivery (same body + same valid `hmac-sha256` header) and re-POST it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. `Registry.process` recomputes the HMAC over the identical raw body, finds it valid, and dispatches the handler with `data.shop` set to the victim's domain — even though the victim's shop had nothing to do with this request.

### Impact Explanation
This breaks the tenant boundary the gem is documented to enforce: a request is described as "verified" to come from Shopify for a given shop, but the shop attribution is unauthenticated. A host application that (as documented) uses `data.shop` to route the webhook body to a shop-scoped job queue, database record, or feature-gate can be made to associate attacker-supplied webhook payloads (order data, product data, GDPR/customer data payloads, etc.) with an arbitrary victim shop, i.e., cross-tenant data injection/confusion using only the attacker's own legitimate app installation — no access to the victim's credentials, session, or the app's `client_secret` required.

### Likelihood Explanation
Any user able to install the app on their own store (an ordinary, unprivileged action for any Shopify merchant) automatically receives genuine signed webhooks and can immediately mount this attack by editing one HTTP header before replaying the request. No secret material, brute forcing, or advanced capability is needed, and the flaw is inherent to how `Webhooks::Request`/`Registry.process` are implemented and documented, not a misuse of an undocumented API.

### Recommendation
Do not treat `shop`, `topic`, `webhook_id`, or `api_version` as trusted solely because the body HMAC validated. At minimum, document prominently that these header-derived fields are unauthenticated and must not be used as a tenant/authorization key without independently cross-checking them (e.g., against the shop recorded for the `webhook_id`, or against an active session for that shop). Where feasible, extend the verification to bind the `shop-domain` header (and ideally `topic`/`webhook_id`) into the value that is HMAC-validated, or require callers to separately confirm `request.shop` against known/installed shop records before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Install the target app on `attacker.myshopify.com`; register a webhook (e.g., `orders/create`).
2. Capture a legitimate webhook delivery: raw body `B` and header `shopify-hmac-sha256: H` (valid for `B` under the app's shared `client_secret`).
3. Resend the same request to the app's webhook endpoint, keeping body `B` and header `shopify-hmac-sha256: H` unchanged, but replacing `shopify-shop-domain: attacker.myshopify.com` with `shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` (`B`) only — matches `H` — validation succeeds.
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, so the host application processes/persists attacker-controlled webhook data under the victim shop's identity.

```ruby
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
```

```markdown
- `topic`, `String` - The topic of the webhook

- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
```

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
