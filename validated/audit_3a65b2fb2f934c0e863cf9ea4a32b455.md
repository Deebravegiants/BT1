Based on the evidence gathered, I found a real asymmetry in the length validation of user-controlled fields in the Hyper Fungible Token (HFT) ISMP module callback, which is the closest and only concrete, scope-matching analog to the "crafted length causing an out-of-bounds/overflow crash" bug class in CVE-2020-19187.

### Title
Missing length validation on `message.from` causes a panic/DoS on token-bridge message delivery - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`HyperFungibleToken::on_accept` ABI-decodes an attacker/source-app-influenced `Message` from the cross-chain request body and, when optional calldata is present without a signature, derives the dispatch `origin` from `message.from` without validating its length, unlike the parallel `to` field which is explicitly length-checked.

### Finding Description
In `on_accept`, the recipient (`to`) bytes are defensively validated before use: [1](#0-0) 

But the sender (`from`) bytes, used later to resolve the dispatch origin for optional calldata execution, are used directly with no length check: [2](#0-1) 

Specifically:
- `&from_bytes[from_bytes.len() - 20..]` underflows/panics if `from_bytes.len() < 20`.
- `H160::from_slice(..)` panics if the resulting slice isn't exactly 20 bytes.
- `account.copy_from_slice(from_bytes)` panics if `from_bytes.len() != 32` for the non-EVM branch.

`message` is decoded generically via `Message::abi_decode(&body)` where `from` is an ABI `bytes` field of arbitrary length [3](#0-2) , so nothing in this pallet enforces that the length matches 20 or 32 bytes before the slicing/copy operations above execute.

### Impact Explanation
A malformed or malicious `from` length in the relayed cross-chain message triggers a Rust panic (integer underflow or length-mismatch panic) inside the ISMP module callback that is invoked when a relayer delivers a proven cross-chain HFT message. This aborts execution of that specific message and, depending on how `pallet-ismp` invokes module callbacks, can halt processing of the request, leaving the corresponding cross-chain transfer/message permanently undelivered — matching the "route unable to deliver messages" impact bucket. This is reachable by any relayer delivering a message whose body was produced by (or on behalf of) the counterpart on the source chain, without requiring privileged access.

### Likelihood Explanation
Reaching this code path requires: (1) the calldata field (`message.data`) to be non-empty, and (2) the optional signature (`substrate_data.signature`) to be `None`, both of which are attacker/app-controllable per-message flags in the ABI-encoded body. Whether the `from` field's length is itself fully attacker-controlled (versus fixed to `msg.sender`, always 20 bytes, by the source-chain `HyperFungibleToken.sol` contract) could not be confirmed — I was unable to inspect the send-side Solidity contract logic in the remaining time. This uncertainty affects likelihood: if the source contract always hard-codes a well-formed 20-byte `from`, this path is not exploitable by an ordinary user; if the encoding contract or any custom app registered via `ContractToAsset` can emit `from` of arbitrary length, it is trivially triggerable.

### Recommendation
Add the same defensive length checks used for `to_bytes` to `from_bytes` before slicing/copying, returning a typed error (e.g., `HftError::InvalidSenderLength`) on mismatch instead of allowing the runtime to panic.

### Proof of Concept
Not fully verifiable without confirming that the source-chain contract can emit a `from` field with length other than 20/32 bytes; the vulnerable code path itself is demonstrated at [2](#0-1) , which will panic for any `from_bytes` whose length is not exactly 20 (EVM source) or exactly 32 (non-EVM source).

**Note on confidence**: Because I ran out of tool-call budget, I could not read `sdk/packages/core/contracts/apps/HyperFungibleToken.sol` to confirm whether `from` is attacker-influenced or always fixed at 20 bytes by the sending contract, nor could I confirm whether `pallet-ismp`'s dispatcher catches panics from module callbacks (which affects whether the blast radius is a single failed message or broader block-execution disruption). If you need those specifics confirmed with certainty, a follow-up session reading `HyperFungibleToken.sol`'s send/dispatch function and `pallet-ismp`'s `handle`/dispatch pipeline would be required.
