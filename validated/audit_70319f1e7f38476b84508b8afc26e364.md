### Title
Webhook `shop`, `topic`, and `webhook_id` identity fields are trusted from unauthenticated headers while the HMAC only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers, but `Utils::HmacValidator` only validates the raw request body against the HMAC. These header-derived identity fields are handed to the app's `WebhookHandler#handle` as trusted `WebhookMetadata` without ever being covered by the signature check.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the body) and the app's `api_secret_key`: [2](#0-1) 

`Registry.process` gates only on this body-HMAC check, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` — all sourced from headers, none of which participate in the signature — and passes them straight into the handler as `WebhookMetadata`: [3](#0-2) [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `shop header == shop covered by HMAC`. In this implementation that equality never holds — the `shop`, `topic`, and `webhook_id` headers are entirely outside the HMAC's scope. Any request whose body+HMAC pair is valid for the app's secret (obtainable by an attacker who installs the same app on their own store and receives a real webhook) can be replayed with the `shop-domain`, `topic`, and `webhook-id` headers rearranged to name a different, unrelated shop. `Registry.process` will pass validation (body HMAC still matches) and hand the handler a `WebhookMetadata` claiming the victim shop's identity while carrying the attacker's body content. This is the same bug class as CL-2021-40 (signature not bound to the value it's meant to authenticate) applied to a shop/tenant identity field instead of a peer challenge.

### Impact Explanation
Multi-tenant apps commonly key persistence, cache invalidation, or authorization decisions off `WebhookMetadata#shop` because it comes from a "verified" webhook request. An attacker holding a legitimately signed webhook from their own store install can forge the `shop-domain` header to point at any victim shop, causing the app to process attacker-controlled body data under another tenant's identity — a cross-tenant data/action injection.

### Likelihood Explanation
Requires only that the attacker install the target app on a shop they control (an ordinary, unprivileged action for any public app) and capture one legitimately delivered webhook. No `api_secret_key`, access token, or privileged access is needed to mount the header-swap replay against a victim app instance.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material, or validate that the header-derived `shop` matches an id embedded/verifiable within the signed body, before constructing `WebhookMetadata`. At minimum, document loudly that `request.shop`/`topic`/`webhook_id` are unauthenticated and must not be trusted as tenant identity without independent verification (e.g., cross-checking against the session/shop already on file for the given webhook subscription).

### Proof of Concept
1. Install the app on attacker-controlled shop `evil.myshopify.com`; Shopify delivers a real webhook with a valid `x-shopify-hmac-sha256` for body `B`.
2. Attacker resends the identical body `B` and HMAC to the app's webhook endpoint, replacing `x-shopify-shop-domain: evil.myshopify.com` with `x-shopify-shop-domain: victim.myshopify.com`.
3. `HmacValidator.validate` recomputes HMAC over `B` only and it matches, per [6](#0-5) .
4. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, per [7](#0-6) , letting attacker-controlled content be processed under the victim shop's identity.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
