### Title
TOCTOU race in External Initiator name uniqueness check allows unprivileged front-running/hijack of initiator names - ([File: core/web/external_initiators_controller.go])

### Summary
`ExternalInitiatorsController.Create` performs a check-then-act sequence identical in shape to the reported `initializeDistributor` bug: it reads external state (`FindExternalInitiatorByName`) to assert an invariant ("name not already taken"), then later performs a separate write (`CreateExternalInitiator`) that assumes the invariant still holds. There is no transactional/locking guarantee between the two calls, so a concurrent unprivileged actor can insert a row with the same name in between, defeating the uniqueness check the same way a malicious front-run defeated the balance-equality check in the report.

### Finding Description
`ValidateExternalInitiator` calls `orm.FindExternalInitiatorByName(ctx, exi.Name)` and only proceeds if it returns `sql.ErrNoRows` [1](#0-0) . `ExternalInitiatorsController.Create` then separately calls `eic.App.BridgeORM().CreateExternalInitiator(ctx, ei)` [2](#0-1) . These are two independent, non-atomic operations (read-check, then write), exactly analogous to the reported pattern where a precondition is checked externally and then relied upon during a later action, allowing a race/front-run window for an unprivileged party to alter the state in between.

The External Initiator creation endpoint is reachable by any authenticated API-token/session user permitted to call `/v2/external_initiators` (an unprivileged, non-owner-only actor in the node's HTTP API surface), matching the "unprivileged-actor" and "session/token/external-initiator handling" scope explicitly called out in the rules.

### Impact Explanation
If two callers race to create an external initiator with the same `Name`, the uniqueness check can pass for both, and whichever `CreateExternalInitiator` insert wins (or, depending on DB constraints, one fails with a raw DB error rather than the intended validation error) can result in inconsistent behavior: unexpected 500s instead of clean validation errors, or — if the underlying table lacks a unique constraint — duplicate initiators under the same name, breaking `FindExternalInitiatorByName`/`Destroy` lookups (which key by name) for the legitimate owner. This does not directly move funds or bypass authentication of the resulting initiators (each still gets its own `AccessKey`/`HashedSecret`), but it degrades availability/correctness of the external-initiator management API in a manner functionally analogous to the reported "DoS on initialization" — a race window in a check-then-act invariant that an unprivileged party can exploit to disrupt a legitimate actor's operation.

### Likelihood Explanation
Low-to-medium. It requires the attacker to know or guess the target initiator name and race a request to `/v2/external_initiators` at the same time as the legitimate creation call — similar low-likelihood, no-direct-benefit-to-attacker profile as the original report ("front-running attack with no benefit for the attacker" but capable of blocking/disrupting the legitimate operation). Whether it's actually exploitable in practice further depends on whether the `external_initiators` table enforces a DB-level unique constraint on `name` (not visible in the reviewed code/index), which would determine if this manifests as a hard failure (DoS-like) or silent duplicate-row corruption.

### Recommendation
Rely on a database-level unique constraint on `external_initiators.name` and perform the uniqueness enforcement atomically as part of the `INSERT` (e.g., `INSERT ... ON CONFLICT DO NOTHING`/unique constraint violation handling) rather than via a separate prior `SELECT` check, mirroring the report's core recommendation of removing the disjoint check-then-act sequence in favor of a single atomic operation.

### Proof of Concept
Two concurrent requests to `POST /v2/external_initiators` with the same `Name` value: both invoke `ValidateExternalInitiator`, and since `FindExternalInitiatorByName` for both can return `sql.ErrNoRows` before either `CreateExternalInitiator` insert commits, both validations pass; the two `CreateExternalInitiator` calls then race, depending on schema constraints, either failing unexpectedly for one client or creating two rows sharing the same name.

Note: I could not verify the exact schema/migration for `external_initiators.name` (whether a DB unique constraint exists) — the index did not surface the migration file, so the concrete DoS-vs-silent-duplication outcome is uncertain and would need confirmation in the full repo (e.g., via a Devin session) before treating this as a hard finding rather than a design smell.

func ValidateExternalInitiator(
	ctx context.Context,
	exi *bridges.ExternalInitiatorRequest,
	orm bridges.ORM,
) error {
	fe := models.NewJSONAPIErrors()
	if len([]rune(exi.Name)) == 0 {
		fe.Add("No name specified")
	} else if !externalInitiatorNameRegexp.MatchString(exi.Name) {
		fe.Add("Name must be alphanumeric and may contain '_' or '-'")
	} else if _, err := orm.FindExternalInitiatorByName(ctx, exi.Name); err == nil {
		fe.Add(fmt.Sprintf("Name %v already exists", exi.Name))
	} else if !errors.Is(err, sql.ErrNoRows) {
		return errors.Wrap(err, "validating external initiator")
	}
	return fe.CoerceEmptyToNil()
}
