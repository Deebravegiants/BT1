### Title
Webhook shop identity spoofing: `shop-domain` header is not covered by the HMAC signature, breaking the binding between the verified body and the acted-upon tenant - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `#shop` (and `#topic`, `#api_version`, `#webhook_id`) are read from unauthenticated headers. `Registry.process` validates the HMAC over the body only, then passes the header-derived `shop` straight into `WebhookMetadata` for the host app's handler, so the tenant identity acted upon is not the tenant whose bytes were actually verified.

### Finding Description
`Utils::HmacValidator.validate` computes/compares the signature against `verifiable_query.to_signable_string`, and for webhooks that method is defined as: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are derived purely from HTTP headers, which are never part of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC against the body, then immediately forwards the unauthenticated `request.shop` (and `request.topic`, `request.webhook_id`) to the app's `WebhookHandler`: [3](#0-2) 

`WebhookMetadata` carries `shop` as a plain field with no independent verification: [4](#0-3) 

The binding that should hold is: `shop-that-produced-the-HMAC-verified-bytes == shop-passed-to-the-handler`. Because the header is outside the signed string, this equality is not enforced. Any body+HMAC pair that is valid for the app's secret (e.g., a genuine webhook delivery received by any shop that has installed the app, or Shopify's webhook test-delivery feature which any merchant can trigger for their own store) remains valid when replayed with an arbitrary `X-Shopify-Shop-Domain` header, because the app's `api_secret_key` is shared across all shops/tenants that installed the app — it is not shop-specific. This is the same root-cause class as the referenced report: a check (HMAC validation) is performed on a representation (raw body) that does not include a field (`shop`) that is subsequently trusted and acted on (tenant selection in `WebhookMetadata.shop`).

### Impact Explanation
This breaks tenant isolation (cross-tenant access), which is explicitly a Critical-severity category. For mandatory/GDPR topics such as `shop/redact` and `customers/redact` (defined in `MANDATORY_TOPICS`), or any handler that uses `data.shop` to select which merchant's records to update/delete/query, an attacker who legitimately controls one shop that installed the app can capture a validly-HMAC'd webhook body (their own real delivery, or a Shopify test webhook they trigger themselves) and replay it to the app's webhook endpoint with a forged `shop-domain` header naming a victim shop. The HMAC check passes (it never inspected the header), and the handler executes tenant-scoped logic (e.g., data deletion, cache invalidation, state update) against the victim shop identified only by the forged header. [5](#0-4) 

### Likelihood Explanation
Any user who can install the app on a shop (a free/dev store is sufficient — no `api_secret_key`, access token, or privileged account is needed) can obtain at least one legitimately signed webhook body/HMAC pair for that app, either from real event delivery or Shopify's "send test notification" feature. Replaying it against the endpoint with a different `shop-domain` header is a simple unauthenticated HTTP request; no credential leakage or interception is required. Likelihood is high wherever a host app derives tenant identity from `WebhookMetadata#shop` (a common pattern, since this is the field the gem explicitly exposes for that purpose).

### Recommendation
Include the shop domain (and ideally topic/webhook-id/api-version) inside the HMAC-signed material, or otherwise cryptographically bind the header-derived shop to the request before trusting it — e.g., verify `to_signable_string` incorporates the `shop-domain`, `topic`, and `webhook-id` headers concatenated with the body, not just the raw body alone. At minimum, document/require that host applications cross-check `WebhookMetadata#shop` against a known, previously stored session/shop record before performing any tenant-scoped mutation.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` and configures a webhook handler for `customers/redact` (or any handler keyed on `WebhookMetadata#shop`).
2. Shopify sends (or the attacker triggers via "send test notification") a legitimate webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same `B` and `X-Shopify-Hmac-Sha256` value to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` recomputes HMAC over `request.to_signable_string` (= `B` only) and it matches, so `Registry.process` proceeds.
5. `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))` is invoked — the app's handler now executes tenant-scoped logic against `victim-shop.myshopify.com` despite the HMAC never having covered that value, demonstrating cross-tenant identity confusion. [6](#0-5)
