Based on the codebase investigation, I found a valid analog matching the "field acted on but not covered by the HMAC" bug class described in the rules.I have sufficient evidence to complete the analysis.

### Title
Webhook `shop` identity is unauthenticated by HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
The gem's webhook HMAC verification only covers the raw request body, while the `shop` (tenant) identity is read from an unsigned HTTP header and passed straight to the host application's handler as trusted data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#hmac` reads the `hmac-sha256` header value [1](#0-0) [2](#0-1) . `Request#shop` independently reads the `shop-domain` header, which is never included in the signable string [3](#0-2) . `HmacValidator.validate`/`validate_signature` compute the HMAC only over `verifiable_query.to_signable_string` (i.e., the body) using `OpenSSL.secure_compare` [4](#0-3) . `Registry.process` checks `Utils::HmacValidator.validate(request)` and then, on success, immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` and hands it to the app's handler [5](#0-4) .

The identity binding broken is: `HMAC-verified bytes == body only`, whereas the app's tenant-routing logic implicitly assumes `HMAC-verified bytes == (body, shop)`. Because Shopify webhook HMACs are computed with the app's single shared `client_secret`/`api_secret_key` (not a per-shop secret) — see `Context.api_secret_key` usage in `HmacValidator.validate` — any valid `(body, hmac)` pair captured from one installed shop remains a *valid* signature no matter what `shop-domain` header value accompanies it. `Registry.process` never cross-checks that the `shop` header is consistent with anything cryptographically bound to the payload.

### Impact Explanation
An attacker who controls one shop that has the target app installed can capture a legitimate webhook delivery (body + `x-shopify-hmac-sha256`), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header for a *different* merchant. `HmacValidator.validate` still returns `true` because it never inspects the shop header, and `Registry.process` passes the attacker-chosen `shop` value straight into `WebhookMetadata` for the host app's handler to act on. If the host application (as documented/intended by this gem's API) uses `WebhookMetadata#shop` to select the tenant/session/database row to update (a normal and expected usage pattern for this gem), the attacker can inject their own payload data under another merchant's identity — a cross-tenant data-integrity/confusion issue.

### Likelihood Explanation
Exploitation requires the attacker to be a legitimate, unprivileged customer of the multi-tenant app (i.e., install the app on their own low-privilege shop) — no access to `api_secret_key`, access tokens, or the target app's infrastructure is needed. Capturing their own valid webhook and replaying it with a modified header is trivial (any HTTP client). The likelihood is moderate: it depends on the host application trusting `WebhookMetadata#shop` for tenant routing without any secondary cross-check, which is the pattern this gem's own documentation instructs apps to follow [6](#0-5) .

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) header values into the HMAC-signed material that `HmacValidator` verifies, or otherwise cryptographically tie the asserted shop domain to the payload before constructing `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and must not be used alone to resolve tenant identity without additional verification (e.g., confirming the shop is registered/expected for that webhook topic via a separate store lookup).

### Proof of Concept
1. Install the target app on attacker-controlled Shop A; capture a real webhook delivery: body `B`, headers including `x-shopify-hmac-sha256: H` (valid for `B` under the app's shared `api_secret_key`) and `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Replay to the same endpoint with identical body `B` and `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which returns `true` (HMAC over `B` still matches) [7](#0-6) .
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [6](#0-5) , causing attacker-controlled data to be processed under the victim shop's identity if the host app trusts this field for tenant selection.
