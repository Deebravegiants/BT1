### Title
Phantom-order price snapshot uses a live, unlocked `balanceOf()` as bid weight, letting a solver flash-borrow inventory to set the published `LiquidityPool` rate that real orders are priced against - ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
The Phantom-order price-discovery pipeline weights each solver's quote by a live ERC‑20 `balanceOf()`/vault-`maxWithdraw()` read taken at the block the bid window closes, and then selects the exact price of whichever bidder holds the largest share of that live weight (`weightedMedian` is a *selection*, not a blend). This mirrors the ITO bug's root cause — a proportional-share calculation driven by a spot, manipulable on-chain balance rather than a stake that is actually locked or verified against real exposure — and the resulting `medianPrice` is persisted into `LiquidityPool.sellRate`/`buyRate`, which the SDK's `quoteIntent()`/`IndexedRateIntentQuoteStrategy` uses to size real users' `IntentGatewayV2` orders (`inputs`/`output.assets`).

### Finding Description
`aggregatePhantomBids` in `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts` weights each leg's quote by `getBalance(destUrl, chain, outputToken, solver)`, which resolves to `getTotalSolverBalance` — a plain `balanceOf(address)` (plus ERC‑4626 `maxWithdraw`) eth_call at the bid-window-closing block: [1](#0-0) [2](#0-1) 

These weights feed `weightedMedian`, which is documented and implemented to *select* one bidder's exact price rather than average across bidders — "a solver holding over half the leg's weight sets the published price verbatim": [3](#0-2) 

Nothing requires the weighting balance to be committed capital, locked for any duration, or backed by an actual fill obligation — it is a single `balanceOf` snapshot at one block, exactly as the ITO bug's `totalSupply()` was a single, freely-manipulable snapshot. The indexer's own documentation confirms the mechanism and its exploitability characteristic ("a solver with no capital [could] set the published rate by quoting an extreme" is explicitly called out as the reason zero-weight quotes are dropped — but a *large transient* balance is not defended against at all): [4](#0-3) [5](#0-4) 

The published median flows through `updateLiquidityPools`/`mergeChainRowsIntoPool` into the pool's persistent `sellRate`/`buyRate`: [6](#0-5) 

Those rates are exactly what `IntentGateway.quoteIntent()` uses by default (`indexed_rates` strategy) to size a user's real order inputs/outputs: [7](#0-6) [8](#0-7) 

An unprivileged intent solver (any EIP‑7702-delegated `SolverAccount`, which is a permissionless role any address can adopt) can therefore:
1. Move a large amount of the leg's output token into its solver wallet on the destination chain (via flash loan, temporary partner transfer, or moving inventory it briefly custodies) just before `PhantomBidWindowExhausted` fires.
2. Submit a single signed phantom bid quoting an extreme price on that leg.
3. Because its `balanceOf` weight dominates, `weightedMedian` returns that bidder's price verbatim as `medianPrice`, which becomes the pool's `sellRate`/`buyRate`.
4. Move the borrowed/transient tokens back out immediately after the snapshot block.
5. Any user whose SDK client subsequently calls `quoteIntent()` gets a mispriced order sized off the manipulated rate, and places a real `IntentGatewayV2` order with unfavorable `inputs`/`output.assets` amounts — a genuine loss of user funds when a solver fills that order at the skewed rate (or the skew otherwise misprices the user's expected output).

### Impact Explanation
This is a price-oracle-manipulation-style bug feeding directly into fund-moving decisions of the `IntentGatewayV2` order flow: a manipulated `LiquidityPool.sellRate`/`buyRate` causes real users to construct and place under- or over-priced orders, resulting in concrete loss of user funds when solvers fill at the corrupted rate advantage. Because `weightedMedian` is a selection (not an average), a single well-weighted malicious bid can set the entire published price for a leg, with no dampening. This satisfies "concrete theft ... of funds" via a manipulated price used by an unprivileged intent-solver-reachable path, analogous to the ITO's governance-power/fund-misallocation impact caused by a manipulable proportional-share input.

### Likelihood Explanation
Likelihood is meaningful but not trivial: it requires (a) being (or acquiring) an EIP‑7702-delegated `SolverAccount`, (b) obtaining a large transient balance of the specific leg's output token on the destination chain (feasible via flash loans for common tokens like stablecoins), and (c) timing the bid to land before `PhantomBidWindowExhausted`. All three are achievable by a permissionless actor with capital and do not require any privileged role, governance, or node compromise — matching the "unprivileged intent solver" reachability required.

### Recommendation
- Do not weight phantom-bid quotes by a single spot `balanceOf` read. Require the weighting balance to be time-averaged (e.g., minimum balance held over a window spanning several blocks before the snapshot) or backed by a bond/stake that cannot be withdrawn within the same block as bidding.
- Cap the influence any single solver's weight can have on `weightedMedian` (e.g., clamp weight share below some percentile) so no single bidder can set the price verbatim.
- Cross-check the phantom price against an independent reference (e.g., a real-fill-derived price, a TWAP, or a Uniswap V4 quote) before persisting it to `LiquidityPool.sellRate`/`buyRate`, and reject/flag snapshots that diverge sharply from the reference (similar to the existing `warnOnDivergentSample` cross-chain divergence check, but applied against ground truth, not just other chains' equally-manipulable samples).
- Consider requiring the weighting inventory to be inventory the solver has provably held for prior blocks (e.g., balance-at-block minus N, not balance-at-block).

### Proof of Concept
1. Deploy/adopt a `SolverAccount` delegated address `S` with no prior inventory of output token `T` on destination chain `D`.
2. Just before a `PhantomOrderV2`'s bid window closes, flash-loan (or otherwise transiently acquire) a large amount of `T` into `S` on chain `D`.
3. Submit a single signed UserOperation bid quoting an extreme `solverAmount` for the leg priced in `T` (e.g., far above or below the fair market rate), satisfying `isVerifiedSolverBid`.
4. Repay/move out the borrowed `T` in the same or next block.
5. Observe `handlePhantomOrderPrices` → `aggregatePhantomBids` → `weightedMedian` select `S`'s extreme price as `medianPrice` because `getTotalSolverBalance(S, T)` dominates total weight (`sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts:1022-1037,1479-1497,709-724`).
6. Observe `updateLiquidityPools`/`mergeChainRowsIntoPool` persist the corrupted rate into `LiquidityPool.sellRate`/`buyRate` (`sdk/packages/indexer/src/services/liquidityPool.service.ts:461-496`).
7. Call `IntentGateway.quoteIntent()` (default `indexed_rates` strategy) and observe it returns a mispriced `amountIn`/`amountOut` derived from the manipulated rate (`sdk/packages/sdk/src/protocols/intents/quote/indexedRates.ts:37-77`, `LiquidityEngine.ts:120-175`), which a user would then use to construct a real, underpriced/overpriced `IntentGatewayV2` order.

// Liquidity-weighted median of solver quotes. Each quote's influence is proportional to `weight` —
// the solver's total balance for the output token across native + vault venues — so a solver that
// can actually deliver size moves the price more than one quoting on thin liquidity. Returns the
// lower weighted median: the smallest price whose cumulative weight reaches half of the total.
// Zero-weight quotes contribute nothing.
//
// Callers must not hand this an entry set whose weights are all zero: with nothing to weight by it
// can only pick a quote by position, and for an even-sized set that position is the upper of the
// two middles — so "the median" becomes "whoever quoted higher", settable by a solver holding no
// inventory at all. aggregatePhantomBids drops such legs instead of pricing them. The fallback
// below stays only so an unguarded caller gets a number rather than a crash; treat reaching it as
// a caller bug.
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}

2. Per leg, a solver's quote is weighted by **its balance of that leg's OUTPUT token on the destination chain** — the inventory that actually backs the leg. Zero-weight quotes are dropped entirely, not down-weighted: they never reach the median, `bidCount`, or the bidder list. A leg where no bidder holds the output token is absent from the result, exactly as if nobody quoted it.

It returns one bidder's exact integer, so a solver holding over half the leg's weight sets the published price verbatim, and the result can never be a value nobody quoted. `lowestPrice` and `highestPrice` are deliberately overwritten with the median so consumers cannot read an outlier bid as a tradeable bound.

/**
 * Collapses a pool's per-(chain, direction) rows into its single buy/sell rate, depth and bid
 * count, in place. `referenceBlock` is the Hyperbridge block the sample ages are measured
 * against — the block being processed when a snapshot writes, the freshest row when a fill
 * refresh does, which is the same reading either way.
 *
 * Does not touch the pool's own `lastUpdatedBlock`/`lastUpdatedAt` or save it: those record which
 * snapshot last priced the pool, and a caller that is not a snapshot must leave them alone.
 */
function mergeChainRowsIntoPool(pool: LiquidityPool, rows: PoolChainLiquidity[], referenceBlock: bigint): void {
	for (const direction of [SELL, BUY]) {
		const directionRows = rows.filter((row) => row.direction === direction)
		if (directionRows.length === 0) continue

		// Blocks are processed in order, so the difference is non-negative in practice; a row
		// from a "future" block would simply count as fresh, which is the right reading anyway.
		const fresh = directionRows.filter((row) => referenceBlock - row.lastUpdatedBlock <= MAX_SAMPLE_AGE_BLOCKS)
		const merged = fresh.length > 0 ? fresh : directionRows

		warnOnDivergentSample(pool.id, direction, merged)

		const depth = merged.reduce((acc, row) => acc + row.depth, 0n)
		const rate = weightedRate(merged)
		const bidCount = merged.reduce((acc, row) => acc + row.bidCount, 0)

		if (direction === SELL) {
			pool.sellRate = rate
			pool.sellDepth = depth
			pool.sellBidCount = bidCount
		} else {
			pool.buyRate = rate
			pool.buyDepth = depth
			pool.buyBidCount = bidCount
		}
	}
}

export class IndexedRateIntentQuoteStrategy implements IntentQuoteStrategyHandler {
	constructor(
		private readonly chainConfigService: ChainConfigService,

		destination: IntentQuoteChainContext,

		const destinationConfig = getConfigByStateMachineId(destination.stateMachineId)

				destination: destinationConfig.stateMachineId,

				tokenOut: tokenOut.symbol,
			})
		}

		const selectedRate = selectIndexedRate(rates, tokenIn.symbol, tokenOut.symbol)
		return quoteWithIndexedRate(params, tokenIn, tokenOut, selectedRate, rates, protocolFeeBps)
	}

	/**
	 * Returns the indexed pool's aggregate buy and sell rates in less-valued
	 * quote-token units per one base token.
	 *
	 * The indexer depth-weights fresh per-chain samples into the pool rates. The
	 * source and destination chains remain part of the result because they define
	 * the cross-chain route whose configured token symbols were resolved.
	 */
	async getBuyAndSellRates(params: {
		sourceChain: Chains
		destinationChain: Chains
		tokenInSymbol: ConfiguredAssetSymbol
		tokenOutSymbol: ConfiguredAssetSymbol
	}): Promise<BuyAndSellRates | undefined> {
		const pool = resolveLiquidityPool(params.tokenInSymbol, params.tokenOutSymbol)
		const response = await this.queryClient.request<BuyAndSellRatesResponse>(BUY_AND_SELL_RATES, {
			poolId: pool.poolId,
		})
		if (!response?.liquidityPools?.nodes) {
			throw new InvalidLiquidityIndexerResponseError("liquidity pool connection is missing")
		}
		const indexedPool = response.liquidityPools.nodes[0]
		if (!indexedPool) return undefined
		validateIndexedPool(indexedPool, pool)

		const sell = readIndexedRate(indexedPool.sellRate, indexedPool.lastUpdatedAt, "pool sell rate")
		const buy = readIndexedRate(indexedPool.buyRate, indexedPool.lastUpdatedAt, "pool buy rate")
		const inputIsToken0 = params.tokenInSymbol.toLowerCase() === pool.token0Symbol.toLowerCase()
		const direct = inputIsToken0 ? sell : buy
		const reverse = inputIsToken0 ? buy : sell
		if (!direct && !reverse) return undefined

		const quoteTokenSymbol = resolveQuoteTokenSymbol(
			params.tokenInSymbol,
			params.tokenOutSymbol,
			direct?.scaledRate,
			reverse?.scaledRate,
		)
		const quoteIsTokenOut = quoteTokenSymbol === params.tokenOutSymbol
		const orientedBuy = quoteIsTokenOut ? direct : reverse
		const orientedSell = quoteIsTokenOut ? reverse : direct

		return {
			baseTokenSymbol: quoteIsTokenOut ? params.tokenInSymbol : params.tokenOutSymbol,
			quoteTokenSymbol,
			sourceChain: params.sourceChain,
			destinationChain: params.destinationChain,
			buyRate: orientedBuy ? formatUnits(orientedBuy.scaledRate, INDEXER_FIXED_POINT_DECIMALS) : null,
			sellRate: orientedSell
				? formatUnits(reciprocalRate(orientedSell.scaledRate, "sell rate"), INDEXER_FIXED_POINT_DECIMALS)
				: null,
			buyRateUpdatedAt: orientedBuy?.updatedAt ?? null,
			sellRateUpdatedAt: orientedSell?.updatedAt ?? null,
		}
	}
}
