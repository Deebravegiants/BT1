### Title
Webhook `shop`/`topic` identity is not covered by the HMAC, allowing cross-tenant/topic replay of a legitimately-signed webhook body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)`, where `Webhooks::Request#to_signable_string` returns only `@raw_body`. However, `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` are read straight from HTTP headers and are never included in the signed bytes. These header-derived fields are then trusted for handler dispatch and passed into `WebhookMetadata` as the tenant/topic identity the host application acts on.

### Finding Description
The binding that should hold is:
`HMAC-verified bytes == bytes the application treats as authoritative for shop/topic identity`

In this gem, that equality fails:
- `Webhooks::Request#to_signable_string` returns `@raw_body` only [1](#0-0) .
- `Webhooks::Request#shop` and `#topic` are pulled from the `x-shopify-shop-domain` / `x-shopify-topic` (or `shopify-*`) headers, which are not part of the signed string [2](#0-1) .
- `Registry.process` verifies only the HMAC of the request, then dispatches using `request.topic` for handler lookup and constructs `WebhookMetadata` using `request.shop` for tenant identity, without any additional binding check [3](#0-2) .

Because `HmacValidator.validate` computes `HMAC(secret, raw_body)` and compares it against the `hmac-sha256` header [4](#0-3) , two requests with identical body content but different `shop-domain`/`topic` headers produce the *same valid signature*. The signature proves only "this body was produced with knowledge of the secret" (i.e., it once came from Shopify for *some* delivery) — it proves nothing about which shop or which topic it was for.

### Impact Explanation
An app installer for Shop A legitimately receives real webhook deliveries for their own store, each with a valid `(body, hmac)` pair signed by the app's shared `api_secret_key`. Because that same `api_secret_key` is used to sign webhooks for every shop that has installed the app, and the signature never binds to the `shop-domain` or `topic` headers, that installer (an unprivileged actor with respect to any other tenant) can resend the exact same body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for Shop B and/or the `x-shopify-topic` header for any topic registered in the app. `Registry.process` will accept the HMAC as valid and hand the attacker-chosen `shop` and `topic` to the registered handler via `WebhookMetadata`, which is exactly the tenant-identifying data host applications use to decide which shop's records to modify (e.g., data deletion via `MANDATORY_TOPICS` such as `customers/redact`, `shop/redact`, or any custom handler keyed on `data.shop`). This is a cross-tenant identity/authorization break rooted in this gem's own webhook verification logic (`Registry`, `Request`, `HmacValidator`), not merely "host app ignores documented behavior" — the gem provides no mechanism at all to bind shop/topic to the signature, and `WebhookMetadata.shop`/`.topic` are the values the gem itself hands to handlers as trusted identity.

### Likelihood Explanation
Requires only that the attacker (1) be a normal, legitimately-installed user of the target app on their own shop (no special privilege, no leaked secret, no access to another tenant), and (2) be able to send arbitrary HTTP requests with custom headers to the app's public webhook endpoint — both are within "unprivileged internet user" capability. No cryptographic secret needs to be known or brute-forced since the attacker reuses a genuine signature they already legitimately received.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the signable material used for HMAC verification, or otherwise cryptographically bind them (e.g., verify `shop` against a value embedded/expected in the parsed body, or require the caller to additionally check that `request.shop` matches an expected shop before trusting `WebhookMetadata`). At minimum, document loudly that `WebhookMetadata#shop`/`#topic` are unauthenticated header values and must not be treated as verified tenant identity by consuming applications, and provide an API to enforce shop allow-listing before dispatch inside `Registry.process`.

### Proof of Concept
1. App has two shops installed: `victim-shop.myshopify.com` and `attacker-shop.myshopify.com`, both sharing the same `api_secret_key`.
2. Attacker's own store triggers a real webhook delivery, e.g. `orders/create` with body `B`; Shopify computes `hmac = HMAC-SHA256(api_secret_key, B)` and sends headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: hmac`.
3. Attacker captures `B` and `hmac` (they own this delivery — no interception of others' data needed).
4. Attacker POSTs the identical body `B` and `hmac` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and (if a different handler is desired) `x-shopify-topic: customers/redact`.
5. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: attacker_headers)` accepts the headers, and `Utils::HmacValidator.validate(request)` returns `true` because it only checks `HMAC(secret, B)` [5](#0-4) .
6. `Registry.process` dispatches to the handler registered for `customers/redact` with `WebhookMetadata.shop == "victim-shop.myshopify.com"` [3](#0-2) , causing the host application's handler to act against `victim-shop`'s tenant data using attacker-supplied content, despite the webhook never actually having been sent by Shopify for that shop or topic.
