## Title
Shared Emporium identity + signature-skippable stateless ops let an attacker drain any standing token/Permit2 allowance left on `EmporiumUpgradeable`, stealing another user's escrowed balance - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable` is a single, shared contract registered once in `Hinkal.externalActionMap` and used by every Hinkal user as their on-chain execution identity for CASE-2 "stateless" ops [1](#0-0) . Any allowance a user's op leaves standing on Emporium's own address (e.g. a Permit2 `approve` to a router) is a shared, spender-controlled resource that a completely unrelated, unprivileged attacker can drain in a later transaction, because `runAction`'s only safety check is a balance diff scoped to the attacker's own self-chosen `circomData.erc20TokenAddresses` list.

### Finding Description
The broken equality is:

`tokens_leaving_emporium_via_allowance[victim_token] == -deltaAmountChanges[i for victim_token]` (as enforced by the post-loop balance-diff check).

In `runAction`, CASE 2 ("Stateless Interaction") executes `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract, so `msg.sender` as seen by any external contract is always the Emporium address, identical for every Hinkal user [2](#0-1) . When `stack.signerAddress == address(0)`, `verifyWallet` returns immediately without any signature check at all [3](#0-2) , so an attacker can freely craft any sequence of arbitrary `endpoint`/`callData` ops as part of their own proof's `externalActionMetadata` — nothing in the ZK circuit can constrain the semantics of an arbitrary external call.

The only guard against balance loss is the before/after diff loop, but it only iterates over `circomData.erc20TokenAddresses`, a list the calling transaction itself supplies [4](#0-3) . If a victim's earlier transaction executed a CASE-2 op such as `permit2.approve(token, router, amount)` (owner recorded as Emporium, since `msg.sender==Emporium`) and did not consume it atomically in the same call, that allowance persists in Permit2's storage. An attacker can then submit their own valid proof/transaction whose `EmporiumStack.ops` contains a CASE-2 call to `router.swapExactTokensForTokens(..., to: attacker)`; the router pulls `token` from Emporium via the standing Permit2 allowance and forwards output to the attacker. Because the attacker's own `circomData.erc20TokenAddresses` never lists `token`, there is no loop index for it — the real decrease in Emporium's balance is never compared against any `deltaAmountChanges` entry, so `balanceChange < 0` is never evaluated for that token and the theft is never reverted.

### Impact Explanation
This is direct theft of a victim's escrowed/shielded balance (the funds backing their UTXO sit in Emporium's real token balance, protected only by the per-transaction diff check) with no privileged role required — Critical severity per the theft-of-shielded-funds category. It is repeatable against every standing allowance any user leaves on Emporium (a natural pattern for Permit2's `AllowanceTransfer`, which is explicitly designed for persistent, reusable allowances), and each drainable allowance can be exploited exactly once (until amount is exhausted) but the pattern (dangling approval + `signerAddress=0` unsigned CASE-2 op) recurs for every user who uses this flow.

### Likelihood Explanation
Preconditions: (1) some user's Emporium-routed op grants an allowance from Emporium's address to a router/spender via CASE 2 and does not fully consume it in the same atomic call (a plausible, even encouraged, Permit2 usage pattern for gas savings); (2) attacker can freely generate their own valid proof for their own UTXOs and craft `EmporiumStack.ops` with `signerAddress=0` (no signature needed) and an `erc20TokenAddresses` list that omits the target token. Both preconditions require no special privilege — only ordinary Hinkal usage by the victim and self-service proof generation by the attacker, which is exactly the tool-set the unprivileged attacker is granted. The attacker's cost is one on-chain transaction with a self-generated proof.

### Recommendation
Do not let Emporium (or any shared/singleton external-action contract) hold or grant allowances that outlive a single atomic `runAction` call: require `approve`+`consume` operations to be paired and fully spent (e.g. reset allowance to 0, or use exact, single-use Permit2 signatures) within the same ops array, or refuse to route open-ended `approve`/Permit2 `approve` calls through the shared Emporium address entirely. Additionally, require `stack.signerAddress != address(0)` (mandatory per-op signature) for any op whose `endpoint` is not on an explicit allow-list, closing the unsigned/unauthenticated call-crafting path.

### Proof of Concept
Foundry fork test:
1. Deploy `Hinkal`, `EmporiumUpgradeable` (registered as external action), a mock ERC20/Permit2, and a mock router with `swapExactTokensForTokens(tokenIn, amountIn, tokenOut, to)` that calls `permit2.transferFrom(msg.sender, address(this), amountIn, tokenIn)` then sends `tokenOut`/equivalent to `to`.
2. "Victim" transaction: call `Hinkal.transact` with a valid proof depositing `token` into Emporium and an `EmporiumStack` whose single CASE-2 op (`invokeWallet=false`, `signerAddress=0`) calls `permit2.approve(token, router, amount, expiration)`. Assert Permit2 allowance `allowance[emporium][token][router] == amount` and Emporium's `token` balance == `amount`.
3. "Attacker" transaction: with attacker's own unrelated UTXOs/proof, craft `EmporiumStack` with a CASE-2 op calling `router.swapExactTokensForTokens(token, amount, token, attacker)`, and set `circomData.erc20TokenAddresses` to exclude `token` (or include an unrelated token only). Call `Hinkal.transact`.
4. Assert: transaction succeeds (no revert), attacker's `token` balance increased by `amount`, Emporium's `token` balance decreased by `amount`, and no `deltaAmountChanges` entry / balance-diff check ever fired for `token` — i.e. `0 == amount_moved` was never checked and does not hold.
