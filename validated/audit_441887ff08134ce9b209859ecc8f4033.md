Confirmed: `Codec.DecodeHeader` is reached from `EcdsaBeefy.verifyParachainHeaderProof`, which any unprivileged relayer can trigger by calling `verify(previousState, proof)` with an attacker-supplied `para.header` byte string. ### Title
Unbounded digest-count field in BEEFY header decoding allows attacker-forced excessive memory allocation / DoS - (File: evm/src/consensus/Codec.sol)

### Summary
`Codec.DecodeHeader` reads a SCALE compact-encoded digest count directly from attacker-supplied header bytes and immediately allocates a `Digest[]` array of that size, with no upper bound check and no validation that the remaining input actually contains that many digest entries.

### Finding Description
`DecodeHeader` decodes the digest-item count with `ScaleCodec.decodeUintCompact(slice)` and uses it unchecked to allocate memory: [1](#0-0) 

`decodeUintCompact`'s "mode 2" branch alone permits values up to 1,073,741,823, and "mode 3" permits values up to 4,503,599,627,370,496 by reading a caller-controlled byte length (up to 8 bytes): [2](#0-1) 

This length is never compared against the remaining bytes in `encoded` before `new Digest[](length)` is executed, unlike other length-bearing fields in the codebase (e.g. Pharos and EVM state-machine proof paths, which enforce `MAX_VALIDATORS`/`InsufficientStorageValues` checks before array sizing, as seen in `modules/consensus/pharos/verifier/src/state_proof.rs`). The same unsafe pattern is exercised in the BEEFY parachain-header verification path, which is directly reachable by any relayer submitting a consensus proof: [3](#0-2) 

`EcdsaBeefy.verify` is an external, unauthenticated entry point (`IConsensusV2.verify`), and `para.header` is fully attacker-controlled calldata, so nothing prevents a relayer from crafting a tiny proof whose embedded header claims a digest-item count far larger than the actual header bytes.

### Impact Explanation
This is the same bug class as GHSA-g9hh-vvx3-v37v (HtmlUnit-Neko): a length/count field taken from untrusted input drives a resource allocation before the input is validated as internally consistent, which lets a small malicious input force disproportionately large memory/gas consumption. In the EVM context, `new Digest[](length)` for a very large `length` triggers Solidity/EVM memory-expansion gas costs that grow quadratically with size; an attacker can choose `length` such that the single call reverts with out-of-gas, consuming the caller's full gas allowance and, more importantly, wasting the gas of the on-chain execution attempting the allocation before any real validation happens (the loop reading digest kinds hasn't even started). Because `verifyParachainHeaderProof` is invoked as part of consensus-proof verification that updates trusted state and delivers cross-chain messages, a relayer can repeatedly submit such malformed proofs to grief consensus-client operation, forcing wasted gas on every submission attempt and denying timely, cheap verification of legitimate headers (a route-availability / message-delivery degradation), even though it does not directly corrupt state (the transaction ultimately reverts rather than persisting bad state).

### Likelihood Explanation
High: no privileges are required, the header bytes are fully attacker-controlled calldata reachable through the public `verify` entry point, and constructing a compact-encoded digest count that is arbitrarily large relative to the actual header payload requires only a handful of crafted bytes.

### Recommendation
Bound the decoded digest length against the remaining bytes in `slice` (e.g. require `length <= (encoded.length - slice.offset)` or enforce a hard maximum digest count, mirroring the `MAX_VALIDATORS`/`InsufficientStorageValues`-style guards already used in the Pharos and EVM state-machine proof-decoding paths) before calling `new Digest[](length)`, so an oversized claimed count is rejected cheaply instead of driving array allocation.

### Proof of Concept
1. Construct a parachain header byte string with a valid 32-byte parent hash, valid block-number compact encoding, valid state/extrinsics roots, then a SCALE compact-encoded digest count using mode 2 or mode 3 encoding for a very large value (e.g. `0xFE FF FF FF` decodes near `0x3FFFFFFF` under mode 2), followed by no actual digest bytes.
2. Submit this header inside a `ParachainProof.parachains[i].header` as part of a call to `EcdsaBeefy.verify(previousState, proof)` with an otherwise-valid MMR/authority-set proof envelope so execution reaches `verifyParachainHeaderProof`.
3. Observe `Codec.DecodeHeader` attempting `new Digest[](length)` for the inflated `length`, causing the transaction to run out of gas / revert on memory expansion cost before any digest content is validated, at minimal calldata cost to the attacker relative to the gas forced onto the call.
