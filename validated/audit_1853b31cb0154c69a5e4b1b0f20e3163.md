### Title
Oversized legitimate DMP messages are silently and permanently dropped during `dmp-queue` migration - ([File: cumulus/pallets/dmp-queue/src/migration.rs])

### Summary
`migrate_page` and `migrate_overweight` drop any stored message that fails `BoundedVec::<u8, MaxDmpMessageLenOf<T>>::try_from`, logging only via `log::error!` and, in `migrate_page`'s inner loop, without emitting any pallet event at all. Because the relay chain's `max_downward_message_size` (host-configurable up to `1024*1024` bytes, see `polkadot/runtime/westend/src/genesis_config_presets.rs`) can legitimately exceed the parachain-side `MaxDmpMessageLenOf<T>` (`<T::DmpSink as HandleMessage>::MaxMessageLen`), a message that was validly enqueued into the old `Pages`/`Overweight` storage before migration can be dropped irrecoverably when the migration runs.

### Finding Description
`migrate_page` at [1](#0-0)  iterates messages in a page and does `continue` on a `try_from` failure, logging an error but never emitting a per-message event; the enclosing page-level result is still `Ok(())`, so `on_idle` fires `Event::Exported` as if nothing were lost. `migrate_overweight` at [2](#0-1)  returns `Err(())` after already calling `Overweight::<T>::take(i)`, so the message is removed from storage and permanently lost even though the caller fires `Event::ExportOverweightFailed` at [3](#0-2)  — that event carries no message content, so recovery is impossible either way.

The size mismatch is real: DMP messages are size-checked only against `config.max_downward_message_size` at enqueue time on the relay chain ( [4](#0-3) ), which is a runtime-configurable, potentially large value (`1024*1024` in Westend's default preset, see `polkadot/runtime/westend/src/genesis_config_presets.rs` lines 116). `MaxDmpMessageLenOf<T>` on the parachain side ( [5](#0-4) ) is a separate, independently configured bound tied to the new `message-queue` pallet's heap/page size, and can be smaller. Old messages sitting in `Pages`/`Overweight` were valid under the old (larger) relay-chain bound, and there is no re-validation or resizing step — only a drop. This is confirmed by the pallet's own regression test `migration_too_long_ignored` at [6](#0-5) , which explicitly constructs a "long" message and asserts it disappears from storage without appearing in `RecordedMessages`.

### Impact Explanation
A previously valid, unprocessed DMP message (which may carry an XCM instruction transferring assets, e.g., `ReserveAssetDeposited`/`ReceiveTeleportedAsset` plus a `Transact`/deposit) sitting in `Pages` or `Overweight` at the time of migration can be permanently destroyed with no recoverable trace of its payload, only a debug-level log line and, for `Overweight`, a generic failure event with no content. This is a real, non-reversible loss of the underlying XCM message and any assets/logic it represented, matching the scoped impact of "silent permanent loss."

### Likelihood Explanation
This requires: (1) the parachain's `MaxDmpMessageLenOf<T>` to be smaller than the relay's configured `max_downward_message_size` at the time the message was originally enqueued, and (2) an unprocessed page/overweight message near that size boundary to exist when the one-time migration runs. This is a one-time, historical migration performed by each parachain team, not a perpetually-exploitable extrinsic path; the attacker does not control the migration timing and cannot force it, only opportunistically send oversized messages before migration completes. The condition and its consequence are already known and explicitly tested by the pallet authors (`migration_too_long_ignored`), indicating this is accepted/expected behavior for a one-off, admin-scheduled legacy migration rather than an unrecognized vulnerability of ongoing user-triggered risk.

### Recommendation
Not applicable as a new fix — behavior is already covered by an explicit test acknowledging the trade-off. If stronger guarantees are desired, the migration could be enhanced to (a) emit an event carrying the dropped message hash/length for off-chain recovery/refund tooling, or (b) split oversized messages across `DmpSink` calls if the sink route supports chunking, but this is a design decision for the one-time legacy migration, not a security defect in ongoing user-facing logic.

### Proof of Concept
The existing test `migration_too_long_ignored` ( [6](#0-5) ) already reproduces this: it inserts a "long" message exceeding the mock's `MaxMessageLen` into both `Pages` and `Overweight`, runs the migration, and asserts the message is gone from storage and absent from `RecordedMessages`, confirming the drop is real and already characterized behavior rather than an unknown bug.

/// Too long messages are dropped by the migration.
#[test]
fn migration_too_long_ignored() {
	new_test_ext().execute_with(|| {
		// Setup the storage:
		PageIndex::<Runtime>::set(PageIndexData {
			begin_used: 10,
			end_used: 11,
			overweight_count: 2,
		});

		let short = vec![1; 16];
		let long = vec![0; 17];
		Pages::<Runtime>::insert(10, vec![(10, short.clone()), (10, long.clone())]);
		// Insert one good and one bad overweight msg:
		Overweight::<Runtime>::insert(0, (0, short.clone()));
		Overweight::<Runtime>::insert(1, (0, long.clone()));

		// Run the migration:
		pre_upgrade_checks::<Runtime>();
		run_to_block(100);
		post_upgrade_checks::<Runtime>();

		assert_eq!(RecordedMessages::take(), vec![short.clone(), short]);

		// Test the storage removal:
		assert!(!PageIndex::<Runtime>::exists());
		assert_eq!(Pages::<Runtime>::iter_keys().count(), 0);
		assert_eq!(Overweight::<Runtime>::iter_keys().count(), 0);
	});
}
