### Title
Webhook shop identity not covered by HMAC signature allows cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The gem's webhook verification (`ShopifyAPI::Utils::HmacValidator.validate`) authenticates only the raw request body of an incoming webhook. The `shop` identity that the host application actually acts on (`WebhookMetadata#shop`, passed to every webhook handler) is read from the `X-Shopify-Shop-Domain` header, which is never included in the HMAC-signed material. Any tenant that legitimately receives one authentic webhook can replay it with a different `shop` header value and it will still pass verification, letting that tenant's payload be attributed to another merchant's shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, however, is pulled straight from a header that is not part of the signed content: [2](#0-1) 

`HmacValidator.validate` computes/compares the HMAC only against `verifiable_query.to_signable_string`, i.e. the body — it never incorporates `shop`: [3](#0-2) 

`Registry.process` verifies the HMAC and then immediately trusts `request.shop` to construct the `WebhookMetadata` object dispatched to the app's handler: [4](#0-3) 

The identity binding the system implicitly relies on is:
`HMAC-verified bytes (body) == tenant identity acted upon (shop header)`

In reality the equality does not hold — the HMAC only covers the body, while `shop` (the tenant-scoping value every downstream handler keys off) travels unauthenticated in a header. Any actor who is a legitimate installed merchant of the app (an "unprivileged" tenant relative to other merchants, requiring no `api_secret_key`, access token, or privileged access) receives real, correctly-HMAC-signed webhook deliveries from Shopify for their own store. Because the signature is body-only, that same body+HMAC pair remains valid if replayed to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header rewritten to name a different, victim shop. `HmacValidator.validate` still returns `true`, and the handler is invoked with `WebhookMetadata.shop` set to the victim's domain instead of the attacker's own.

### Impact Explanation
This breaks the tenant boundary that host applications rely on this gem to enforce: `WebhookMetadata#shop` is the only tenant-scoping signal `Registry.process` hands to application code, and it is exactly the value that is not authenticated. A host application that looks up/updates per-shop records keyed by `data.shop` (the intended and documented usage) can be made to apply an attacker-controlled body under another merchant's identity — a cross-tenant data confusion/write primitive achievable purely by replaying one's own legitimately received webhook with a modified header, at Critical severity (cross-tenant access).

### Likelihood Explanation
Any merchant who has installed the app receives real webhooks with valid signatures for their own shop by design — no secret needs to be recovered, no token needs to be stolen. Modifying an HTTP header on a replayed request is trivial. The only constraint is that the app must actually consume `WebhookMetadata#shop` to make tenant-scoped decisions, which is the intended/documented use of this field, making exploitation straightforward wherever that pattern is used.

### Recommendation
Bind the shop identity to the verified signature. Options:
- Include the shop domain (and topic) inside the signable string used for HMAC verification when possible, or
- Require the host application to cross-check `WebhookMetadata#shop` against an out-of-band trusted value (e.g., session/shop record looked up by `webhook_id` or a registered callback), and document this requirement prominently, or
- At minimum, have `Registry.process` treat `shop` as untrusted and require callers to pass the expected shop for comparison before dispatching to handlers.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers an event (e.g., `orders/create`) that causes Shopify to send a legitimately signed webhook:
   - Headers: `x-shopify-hmac-sha256: <valid HMAC of body>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`
   - Body: attacker-controlled order JSON (attacker fully controls their own store's order content, e.g. custom fields/notes).
2. Attacker resends the exact same body and HMAC header to the app's webhook endpoint, but changes only:
   - `x-shopify-shop-domain: victim.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body as usual; `HmacValidator.validate` recomputes HMAC over `@raw_body` only — unchanged — and returns `true`. [5](#0-4) 
4. The registered handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled>, ...)` and, if the host app uses `data.shop` to select which merchant's records to update (the documented pattern), performs that update against the victim's tenant using attacker-supplied data.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
