## Finding

A GIF-buffer-overflow class bug (fixed-size buffer write sized from an untrusted length field with no bounds check) has a direct analog in the HyperFungibleToken pallet's inbound message handler.

### Title
Unchecked `copy_from_slice` into fixed 32-byte array panics on non-EVM `PostRequest.from` of wrong length - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
When `HandlerV2`/pallet-ismp delivers an inbound ISMP `PostRequest` to the HFT module's `on_accept` path and the request carries embedded `SubstrateCalldata` with no signature, the module derives the dispatch origin from `message.from`. For EVM sources it correctly truncates to the last 20 bytes, but for non-EVM sources it copies the raw bytes directly into a fixed `[u8; 32]` buffer with no length check.

### Finding Description [1](#0-0) 

```rust
} else {
    let from_bytes = message.from.as_ref();
    if source.is_evm() {
        T::EvmToSubstrate::convert(H160::from_slice(
            &from_bytes[from_bytes.len() - 20..],
        ))
    } else {
        let mut account = [0u8; 32];
        account.copy_from_slice(from_bytes);
        account.into()
    }
};
```

`message.from` originates from the cross-chain `PostRequest.from` field, which is attacker/relayer-controlled data (any non-EVM state machine's "from" identity is essentially free-form bytes chosen by whoever originates or forges the request on the source chain, or by a malicious/compromised relayer's message construction). `Vec<u8>::copy_from_slice` into a `[0u8; 32]` **panics** if the source slice length is not exactly 32 — unlike the EVM branch immediately above, which defensively slices only the trailing 20 bytes, this branch performs no length validation before the fixed-size write.

This is analogous to the reported CVE's root cause: a length taken from untrusted/parsed input is used to fill a fixed-size buffer without verifying the length matches the buffer size first.

### Impact Explanation
A panic inside pallet logic executed during extrinsic/message dispatch (`decode_and_execute` → `handle_unsigned`/`on_accept`) is not merely an application-level revert; depending on how the runtime is compiled and how panics are handled in the WASM executor, an unhandled panic during block execution can abort transaction/block processing, effectively giving any relayer routing an ISMP message from a non-EVM chain the ability to break message delivery for the HFT pallet — a "route unable to deliver messages" condition, and in the worst case a node/panic-induced liveness fault for the block that includes the message.

### Likelihood Explanation
High: this path is reachable by any unprivileged party that can get a `PostRequest` delivered to the HFT module from a non-EVM source state machine with a `from` value not exactly 32 bytes (e.g. crafting the message via a malicious/permissionless counterparty chain or a compromised/malicious relayer submission), and with calldata that omits the `signature` field (`substrate_data.signature == None`) so this else-branch executes.

### Recommendation
Validate `from_bytes.len() == 32` before `copy_from_slice`, returning an `HftError` (mirroring the pattern already used for the EVM branch and elsewhere in the codebase, e.g. `to_bytes_32` in `modules/ismp/state-machines/evm/src/utils.rs:118-128`) instead of panicking.

### Proof of Concept
1. Construct/relay an ISMP `PostRequest` targeting the HFT pallet with `source` set to a non-EVM `StateMachine` and `from` set to a byte vector of length ≠ 32 (e.g. 4 or 33 bytes).
2. Embed `SubstrateCalldata` in `message.data` with `signature: None`.
3. Deliver via `pallet_ismp::Call::handle_unsigned` (reachable through `modules/pallets/call-decompressor/src/lib.rs:277-279` or the normal ISMP dispatch path).
4. Execution reaches `modules/pallets/hyper-fungible-token/src/module.rs:183-184`, where `account.copy_from_slice(from_bytes)` panics because `from_bytes.len() != 32`. [1](#0-0)
