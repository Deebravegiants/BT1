### Title

Route-controlled contract execution can smuggle caller-authorized token transfers - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary

The controller accepts an opaque route in its strategy entrypoints and invokes the configured router under the caller’s authorization tree. A malicious route can place attacker-deployed pool code on the call stack; that code can request a token transfer from the caller to an attacker-controlled address. The transfer executes when the caller signs the authorization tree returned by simulation, bypassing the controller’s routed-input and measured-output checks.

### Finding Description

`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` all expose a caller-supplied `swap: Bytes` argument and require only owner or delegate authorization before executing the strategy. [1](#0-0) 

Each path eventually reaches `swap_tokens`, which loads the configured router, authorizes only the exact controller-to-router input transfer, and forwards the opaque `swap` payload to `execute_strategy`. [2](#0-1) 

The controller validates only the router’s token balance effects: input cannot overspend, unused input is refunded, and output must increase. These checks do not inspect or restrict additional contract invocations made below the caller’s authorization. [3](#0-2) 

The router decodes route-selected asset and pool addresses from the payload and dispatches each hop to the selected pool. [4](#0-3) [5](#0-4) 

The pool address is not allowlisted; it is an arbitrary `Address` registry entry selected by the submitted strategy. [6](#0-5) 

Consequently, a malicious pool invoked as a route hop can call `token.transfer(victim, attacker, amount)`. Soroban records that transfer as a child of the caller’s strategy authorization, and it succeeds if the caller signs the simulated tree containing it. [7](#0-6) [8](#0-7) 

### Impact Explanation

A malicious route can steal tokens held directly in the caller’s wallet, including tokens unrelated to the lending position. The protocol’s positive-output and solvency checks can still pass because the rogue transfer is independent of the routed input amount and measured router output. [9](#0-8) 

The repository’s regression test demonstrates loss of an entire unrelated wallet balance while the requested collateral swap still deposits the expected output. [8](#0-7) 

### Likelihood Explanation

Exploitation requires the victim to submit a maliciously constructed route and sign the authorization tree containing the extra token transfer. A caller that signs only a root authorization without the poisoned child causes the transfer and enclosing transaction to fail. [10](#0-9) 

The attack is nevertheless reachable by an unprivileged attacker through ordinary route construction for `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply`; no protocol privilege or leaked key is required. Its likelihood depends on a wallet, SDK, or aggregator client failing to reject unexpected authorization children before signing. [9](#0-8) 

### Recommendation

Treat router payloads and simulated authorization trees as untrusted executable input. Before signing, clients must decode the route and require the exact expected authorization tree: no children for a normal composed strategy, and only the expected input transfer for a direct router swap. Reject any additional `token.transfer`, approval, or other invocation involving the caller. [9](#0-8) 

Where feasible, constrain routes to authenticated venue adapters and previously admitted pool deployments, or provide a signed-route mechanism that commits the user to a reviewed pool set rather than arbitrary route-selected contract addresses. [5](#0-4) 

### Proof of Concept

The repository contains a complete harness in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`. `UnlistedPoolRouter` decodes a route and invokes the route-selected pool, while `RogueHopPool::swap` transfers the victim’s unrelated wallet token to the attacker. [11](#0-10) 

The test constructs a `swap_collateral` call for Alice, records the rogue transfer beneath Alice’s controller authorization, and asserts that Alice’s wallet balance becomes zero while the attacker receives the full amount and the strategy still supplies the expected output. [8](#0-7)

pub struct UnlistedPoolRouter;

#[contractimpl]
impl UnlistedPoolRouter {
    pub fn execute_strategy(env: Env, sender: Address, total_in: i128, swap_xdr: Bytes) -> i128 {
        sender.require_auth();
        let route = RoutedSwap::from_xdr(&env, &swap_xdr).expect("route must decode");
        let router = env.current_contract_address();
        token::Client::new(&env, &route.token_in).transfer(&sender, &router, &total_in);
        let _: Val = env.invoke_contract(&route.hop_pool, &symbol_short!("swap"), vec![&env]);
        token::Client::new(&env, &route.token_out).transfer(&router, &sender, &route.min_out);
        route.min_out
    }
}

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
