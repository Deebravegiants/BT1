### Title
Single-solver control of the median phantom-bid price lets one bidder set the published pool rate that real intents are priced from - (File: `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts`)

### Summary
`weightedMedian` in `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts` (lines 709-724) is a *selection* median: it walks bids sorted by price and returns the exact price of whichever entry's cumulative weight first reaches half the total weight. The weight is the bidding solver's on-chain balance of that leg's output token [1](#0-0) . As the code's own documentation states, "a solver holding over half the leg's weight sets the published price verbatim" [2](#0-1) . This is structurally the same weakness as the Trail of Bits `DapiServer` finding: a single participant among many "oracles" (here, phantom-order bidders) can dictate the aggregated value, and — unlike a true median over honest participants — the result is not bounded to lie between other honest submissions once the attacker holds majority weight for that leg; it is simply the attacker's own submitted number, in either direction.

### Finding Description
1. `aggregatePhantomBids` collects bids for a phantom order, verifies each solver's signature/delegation, and computes each leg's weight as the bidding solver's live balance (ERC-20 + vault + declared Uniswap V4 position) of that leg's output token on the destination chain [3](#0-2) .
2. `weightedMedian` then picks the price of the first sorted entry whose cumulative weight crosses half the total weight [4](#0-3) . If one solver's weight for a leg exceeds 50% of the total, the entry selected is guaranteed to be that solver's own quoted price — it is not clamped to the range of the other bidders' prices, because the majority bidder's price is itself part of the sorted set and the cumulative-weight threshold is reached at (or before) its own entry regardless of where in the sorted order that price falls.
3. `lowestPrice`/`highestPrice` are deliberately overwritten with this same median value [5](#0-4) , removing the only field that would otherwise expose the manipulation as an outlier.
4. `updateLiquidityPools` (`sdk/packages/indexer/src/services/liquidityPool.service.ts`) folds this per-leg `medianPrice` into `PoolChainLiquidity.rate` [6](#0-5) , and then depth-weight-averages chain rows into the pool's single `sellRate`/`buyRate` [7](#0-6) . Because depth itself is measured by the same solver's balance, an attacker who dominates weight on a leg also dominates the depth-weighted merge across chains and across time (subject to `MAX_SAMPLE_AGE_BLOCKS` staleness filtering).
5. `IndexedRateIntentQuoteStrategy.quote` (`sdk/packages/sdk/src/protocols/intents/quote/indexedRates.ts`), which `IntentGateway.quoteIntent` uses **by default** for real, capital-moving intents, reads this `buyRate`/`sellRate` directly and computes `amountIn`/`amountOut` from it with no sanity check against any independent price source [8](#0-7) .

The only mitigation present, `warnOnDivergentSample`, is a >5x-divergence log warning between chains' samples — it never rejects or clamps a value, and does not apply to a single-chain leg with only one quoted direction [9](#0-8) .

### Impact Explanation
A solver that funds a large enough balance of a leg's output token on one chain (this requires capital, not necessarily "compromise" of a private key, but the DapiServer report's threat model — one dishonest participant among many — maps directly onto "one dishonest/well-capitalized solver among many bidders") can:
- Publish an arbitrarily bad `sellRate`/`buyRate` for a token pair (e.g., quote itself an extreme lowball or highball price and win the weighted-median selection).
- Cause `quoteIntent`'s default `indexed_rates` strategy to construct real orders at that manipulated rate, so a user who accepts the quote and submits the intent overpays or under-receives, and/or the manipulating solver (or a colluding solver) fills that mispriced order for guaranteed profit — a direct value-extraction vector via the intents/escrow settlement path.
- Because `lowestPrice`/`highestPrice` are overwritten with the same median, downstream consumers have no visibility that the "market price" is a single participant's number rather than a consensus of quotes.

This satisfies the "concrete theft ... via a route unable to deliver messages" / unauthorized value-extraction bar: real user funds move through `IntentGateway`/escrow at an attacker-controlled rate.

### Likelihood Explanation
Requires the attacker to hold, at settlement/snapshot time, more than half of the total *weight* (destination-chain balance of the output token) among bidders on a given leg. This is more of a capital/liquidity-concentration condition than a cryptographic compromise, so likelihood depends on how thin liquidity is for a given pair/chain — plausible for newly listed or low-liquidity pairs, or if a single large market maker also runs a bidding solver. The `>5x divergence` warning only fires when multiple chains quote the same pool and diverge; a pool with liquidity concentrated on one chain, or where the attacker controls the rate on every chain consistently, produces no warning at all.

### Recommendation
- Do not let a single bidder's weight alone satisfy the majority threshold in `weightedMedian`; require either a minimum number of independent, verified bidders per leg, or cap any single solver's effective weight contribution (e.g., at some fraction of total weight) before it can move the price.
- Bound the published `medianPrice` (and hence `sellRate`/`buyRate`) to the range spanned by the *other* bidders' quotes rather than allowing the majority-weight quote to be selected verbatim and unclamped.
- Feed `IndexedRateIntentQuoteStrategy.quote` a secondary reference price (e.g., a CEX/DEX oracle or a minimum bidder-count/quorum requirement) and reject or flag quotes that deviate materially, rather than trusting `LiquidityPool.buyRate`/`sellRate` unconditionally.
- Turn `warnOnDivergentSample`'s divergence check into an enforced guard (reject/quarantine the pool rate) rather than a log-only warning, and extend divergence detection to single-chain/single-bidder-dominated pools.

### Proof of Concept
1. Register a phantom order for pair `(tokenA, tokenB)` on chain `C` with a `standardAmount` probe.
2. Have two honest solvers bid a fair price (~100 units) for the leg, each backed by modest balances of `tokenB` on `C`.
3. Have the attacker's solver (which is delegated and passes signature/nonce verification, e.g. via `isVerifiedSolverBid`) acquire and hold more than the combined balance of `tokenB` that the honest solvers hold on `C`, and submit a bid at an extreme price (e.g., 1 unit, or 10,000 units).
4. `aggregatePhantomBids` → `weightedMedian` selects the attacker's price verbatim because its weight alone exceeds half the total weight [4](#0-3) .
5. `updateLiquidityPools` writes this into `PoolChainLiquidity.rate` and then `LiquidityPool.sellRate`/`buyRate` [10](#0-9) .
6. A user calling `IntentGateway.quoteIntent` for the same pair receives an `IndexedRateIntentQuoteStrategy` quote computed from the manipulated rate [8](#0-7) , and if the user submits the resulting intent, real funds move at the attacker-controlled rate.

export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}

/**
 * Collapses a pool's per-(chain, direction) rows into its single buy/sell rate, depth and bid
 * count, in place. `referenceBlock` is the Hyperbridge block the sample ages are measured
 * against — the block being processed when a snapshot writes, the freshest row when a fill
 * refresh does, which is the same reading either way.
 *
 * Does not touch the pool's own `lastUpdatedBlock`/`lastUpdatedAt` or save it: those record which
 * snapshot last priced the pool, and a caller that is not a snapshot must leave them alone.
 */
function mergeChainRowsIntoPool(pool: LiquidityPool, rows: PoolChainLiquidity[], referenceBlock: bigint): void {
	for (const direction of [SELL, BUY]) {
		const directionRows = rows.filter((row) => row.direction === direction)
		if (directionRows.length === 0) continue

		// Blocks are processed in order, so the difference is non-negative in practice; a row
		// from a "future" block would simply count as fresh, which is the right reading anyway.
		const fresh = directionRows.filter((row) => referenceBlock - row.lastUpdatedBlock <= MAX_SAMPLE_AGE_BLOCKS)
		const merged = fresh.length > 0 ? fresh : directionRows

		warnOnDivergentSample(pool.id, direction, merged)

		const depth = merged.reduce((acc, row) => acc + row.depth, 0n)
		const rate = weightedRate(merged)
		const bidCount = merged.reduce((acc, row) => acc + row.bidCount, 0)

		if (direction === SELL) {
			pool.sellRate = rate
			pool.sellDepth = depth
			pool.sellBidCount = bidCount
		} else {
			pool.buyRate = rate
			pool.buyDepth = depth
			pool.buyBidCount = bidCount
		}
	}
}

// A pair prices identically across chains, so one sample far off the others' consensus almost
// certainly means a wrong registry decimals entry poisoning that chain's normalization — worth an
// alarm, but the sample still merges: this cannot tell a bad entry from a genuinely dislocated
// market, and silently dropping data would hide the bug the alarm exists to surface.
function warnOnDivergentSample(
	poolId: string,
	direction: string,
	rows: { chain: string; rate: bigint; depth: bigint }[],
): void {
	if (rows.length < 2) return
	for (const row of rows) {
		const consensus = weightedRate(rows.filter((other) => other !== row))
		if (consensus === 0n) continue
		if (row.rate > consensus * 5n || row.rate * 5n < consensus) {
			logger.warn(
				{ poolId, direction, chain: row.chain, rate: row.rate.toString(), consensus: consensus.toString() },
				"Pool chain sample diverges >5x from the other chains — check the token registry decimals",
			)
		}
	}
}

function quoteWithIndexedRate(
	params: QuoteIntentParams,
	tokenIn: ResolvedQuoteAsset,
	tokenOut: ResolvedQuoteAsset,
	selectedRate: SelectedIndexedRate,
	rates: BuyAndSellRates,
	protocolFeeBps: bigint,
): IndexedRateQuoteIntentResult {
	const inputUnit = 10n ** BigInt(tokenIn.decimals)
	const outputUnit = 10n ** BigInt(tokenOut.decimals)
	if (params.amountIn !== undefined) {
		const netAmountIn = deductProtocolFee(params.amountIn, protocolFeeBps)
		const amountOut =
			selectedRate.side === "buy"
				? (netAmountIn * selectedRate.scaledRate * outputUnit) / (inputUnit * INDEXED_RATE_SCALE)
				: (netAmountIn * outputUnit * INDEXED_RATE_SCALE) / (inputUnit * selectedRate.scaledRate)
		if (amountOut <= 0n) throw new InvalidIndexedRateError("quote rounds down to zero output")
		return buildResult("EXACT_INPUT", params.amountIn, amountOut, selectedRate, rates, protocolFeeBps)
	}

	if (params.amountOut === undefined) throw new Error("Quote amount is missing after validation")
	const netAmountIn =
		selectedRate.side === "buy"
			? divCeil(params.amountOut * inputUnit * INDEXED_RATE_SCALE, selectedRate.scaledRate * outputUnit)
			: divCeil(params.amountOut * inputUnit * selectedRate.scaledRate, outputUnit * INDEXED_RATE_SCALE)
	const amountIn = grossUpForProtocolFee(netAmountIn, protocolFeeBps)
	return buildResult("EXACT_OUTPUT", amountIn, params.amountOut, selectedRate, rates, protocolFeeBps)
}
