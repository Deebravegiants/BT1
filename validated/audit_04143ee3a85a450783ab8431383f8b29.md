### Title
`DepositOnChainUtxosExternalAction.runAction` trusts an unauthenticated `circomData.originalSender` field, letting Emporium relay a forged deposit that pulls a victim's approved tokens into a shielded UTXO minted for the attacker - (contracts/external-actions/DepositOnChainUtxosExternalAction.sol)

### Summary
`DepositOnChainUtxosExternalAction.runAction` only checks `onlyAllowedRecipient` (i.e. that the immediate caller is a registered relay such as `EmporiumUpgradeable`) and never verifies that `circomData.originalSender` corresponds to the actual, ZK-proof-bound transaction sender. Because `EmporiumUpgradeable.runAction` forwards attacker-supplied, un-checked `op.callData` (including a nested, forged `CircomData` struct) to any allowed endpoint, an attacker can make Emporium call the deposit action with `originalSender = V` and pull V's standing ERC20 approval into Emporium's balance, which `EmporiumUpgradeable.handleOut` then re-mints as a shielded UTXO under the attacker's own `stealthAddressStructure`.

### Finding Description
The broken equality: the top-level `balanceDif == amountChanges + utxoAmount` check in `Hinkal.sol` (lines 137-146) is supposed to guarantee that any UTXO amount created for the caller is backed by value the caller's own proof committed to move (`amountChanges`). Instead, `utxoAmount` here is populated with tokens whose provenance is V's wallet, not the attacker's proof: [1](#0-0) 

`performHinkalChecks` binds **only the outer, ZK-proven** `circomData.originalSender` to the real caller: [2](#0-1) 

But the `externalActionMetadata` bytes (decoded into an `EmporiumStack` inside `EmporiumUpgradeable.runAction`) are only checked for calldata-hash integrity - the circuit/hash never semantically constrains their *decoded content*, so the attacker freely crafts a second, nested `CircomData` (`circomData2`) embedded in `op.callData`, with `circomData2.originalSender = V`: [3](#0-2) 

`DepositOnChainUtxosExternalAction.runAction` blindly trusts this nested `circomData2.originalSender` as the token owner to pull from, and only guards entry with `onlyAllowedRecipient` (checking `msg.sender`, i.e. Emporium, is allowlisted - not that `originalSender` matches anyone authenticated): [4](#0-3) 

The only real guard left is ERC20 `allowance(V, DepositOnChainUtxosExternalAction)`, which is exactly the standing approval V would have granted to use Hinkal's normal on-chain deposit flow - it is not scoped to be spent only when V personally initiates the top-level transaction. Contrast this with `Hinkal._internalTransact`, which does enforce `circomData.externalActionData.externalAddress == msg.sender` to tie a deposit's source to the actual caller - no equivalent binding exists for `DepositOnChainUtxosExternalAction` reached through Emporium: [5](#0-4) 

Exploit flow: attacker calls `Hinkal.transact()` with their own valid proof, `externalActionData.externalAddress = Emporium`, `amountChanges[token] = 0` for the target token, and `externalActionMetadata` encoding an `EmporiumStack` whose op targets `DepositOnChainUtxosExternalAction` with a forged `circomData2.originalSender = V`. Emporium's stateless branch does a raw `.call` to the deposit action, which executes `transferERC20TokenFrom(token, V, msg.sender=Emporium, amount)`, pulling V's approved tokens into Emporium. Back in `EmporiumUpgradeable.runAction`, `balancesAfter - balancesBefore` reflects V's tokens; `handleOut` transfers them onward and returns a UTXO keyed to the attacker's own `circomData.stealthAddressStructure` (from the outer, legitimately-proven CircomData). This UTXO is inserted into Hinkal's shielded pool as if backed by the attacker's own funds.

### Impact Explanation
This is direct theft of a third party's approved on-chain tokens and minting of shielded value without legitimate backing (attacker's proof declared zero movement for that token), which maps to the Critical category: "direct theft of shielded or in-flight user funds, minting shielded value without backing." Any victim who has ever approved `DepositOnChainUtxosExternalAction` (a normal, expected step for using Hinkal's deposit UTXO feature) is at risk for the full remaining allowance, and the attack is repeatable per victim/approval up to the allowance amount.

### Likelihood Explanation
Requires (a) `EmporiumUpgradeable` to be registered as an allowed recipient on `DepositOnChainUtxosExternalAction` (a plausible, likely-necessary deployment configuration since Emporium exists to compose calls into other registered external actions), and (b) a victim with a live, non-zero ERC20 approval to `DepositOnChainUtxosExternalAction`. Both conditions are ordinary consequences of normal protocol usage/configuration, not privileged states. The attacker needs no special role - only the ability to submit their own valid proof/transact call and craft arbitrary `op.callData`, both explicitly within the stated attacker capabilities.

### Recommendation
`DepositOnChainUtxosExternalAction.runAction` (and any external action reachable indirectly through a relay like Emporium) must not trust an unauthenticated `circomData.originalSender` for authorizing `transferFrom`. Either (1) require the immediate `msg.sender` in `transferERC20TokenFrom` calls to equal the value being credited only when the call originates from the trusted top-level Hinkal contract with a proof-bound `originalSender`, disallowing relaying through Emporium for this action, or (2) have `EmporiumUpgradeable` explicitly validate/pass-through and bind any nested `CircomData.originalSender` used by ops to the outer, ZK-checked `circomData.originalSender`/`msg.sender`, so a nested deposit can never specify a third-party address as the fund source.

### Proof of Concept
Hardhat fork test:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, `DepositOnChainUtxosExternalAction`; register Emporium as allowed recipient on the deposit action; register the deposit action + Emporium in Hinkal's `externalActionMap`.
2. Victim `V` approves `DepositOnChainUtxosExternalAction` for `amount` of an ERC20 token (simulating normal prior usage).
3. Attacker generates a valid proof for `circomData` with `externalActionData.externalAddress = Emporium`, `amountChanges[token] = 0`, `originalSender = attacker`, and `externalActionMetadata` encoding an `EmporiumStack` whose single op calls `DepositOnChainUtxosExternalAction.runAction` with a forged `circomData2.originalSender = V` and `utxoAmounts = [[amount]]`.
4. Call `Hinkal.transact(...)` as attacker.
5. Assert: V's token balance decreased by `amount`; a shielded on-chain UTXO commitment is inserted with `stealthAddressStructure == attacker's` and `amount == amount`; assert this violates `balanceDif == amountChanges[token] (0) + utxoAmount` being satisfied only because `utxoAmount` was funded by V, not by the attacker's declared `amountChanges`.

        int256[] calldata deltaAmounts

        uint256 tokenCount = circomData.erc20TokenAddresses.length;
        require(
            tokenCount > 0 && deltaAmounts.length == tokenCount,
            "DepositOnChainUtxosExternalAction: token count mismatch"
        );

        address userAddress = circomData.originalSender;
        require(
            userAddress != address(0),
            "DepositOnChainUtxosExternalAction: Invalid originalSender"
        );

        uint256[][] memory utxoAmounts = abi.decode(
            circomData.externalActionData.externalActionMetadata,
            (uint256[][])
        );
        require(
            utxoAmounts.length == tokenCount,
            "DepositOnChainUtxosExternalAction: metadata length mismatch"
        );

        utxoSet = new UTXO[](countUtxos(utxoAmounts));

        uint256 utxoIndex = 0;
        for (uint256 i = 0; i < tokenCount; i++) {
            require(
                deltaAmounts[i] == 0,
                "DepositOnChainUtxosExternalAction: Delta amount must be zero"
            );

            address tokenAddress = circomData.erc20TokenAddresses[i];
            uint256 tokenTotal = 0;

            for (uint256 j = 0; j < utxoAmounts[i].length; j++) {
                uint256 amount = utxoAmounts[i][j];
                require(
                    amount > 0,
                    "DepositOnChainUtxosExternalAction: UTXO amount must be positive"
                );
                tokenTotal += amount;

                utxoSet[utxoIndex] = UTXO({
                    amount: amount,
                    erc20Address: tokenAddress,
                    stealthAddressStructure: circomData.stealthAddressStructure,
                    timeStamp: circomData.timeStamp + utxoIndex
                });
                utxoIndex++;
            }

            if (tokenAddress != address(0) && tokenTotal > 0) {
                transferERC20TokenFrom(
                    tokenAddress,
                    userAddress,
                    msg.sender,
                    tokenTotal
                );
