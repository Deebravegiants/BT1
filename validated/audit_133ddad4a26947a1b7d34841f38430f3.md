### Title
Malformed/corrupted extra seed can permanently block wallet unlock — ([File: features/wallet/module/wallet.js])

### Summary
The external report describes a class of bug where an operation that depends on multiple sub-items succeeding atomically (reward-token transfers in a withdraw loop) is blocked entirely if a single malicious/misbehaving item fails, locking legitimate users out of their funds. `Wallet.unlock()` in `features/wallet/module/wallet.js` exhibits the same structural pattern: it must add the primary seed *and every extra seed* to the in-memory keychain before it will mark the wallet as unlocked, and any single failing extra seed aborts the whole operation.

### Finding Description
`unlock()` first decrypts and adds the primary seed, then loads and adds every extra (multi-seed) entry in one `Promise.all`, only setting `this.#isLocked = false` after all of them resolve: [1](#0-0) 

```js
unlock = async ({ passphrase } = {}) => {
  try {
    const { seed } = await this.#getSeed({ passphrase })
    const primarySeedId = await this.#keychain.addSeed(seed)
    this.#primarySeedIdAtom.set(primarySeedId)

    const extraSeeds = await this.#getExtraSeeds()
    await Promise.all(extraSeeds.map(({ seed }) => this.#keychain.addSeed(seed)))

    this.#isLocked = false

    return { primarySeedId }
  } catch (err) {
    this.#logger.debug('unlock() failed: wrong password', err)
    throw new Error('Wrong password. Try again.')
  }
}
```

`Promise.all` rejects as soon as any single `addSeed` call rejects. `Keychain.addSeed` enforces a strict invariant on its input (`seed instanceof Uint8Array && seed.length === 64`) and throws otherwise: [2](#0-1) 

If any one of the stored extra seeds is corrupted (e.g., wrong length, non-buffer, or fails master-key derivation validated by `throwIfInvalidMasters`), the whole `unlock()` call throws — even though the primary seed and passphrase were completely correct — and is reported to the user as `"Wrong password. Try again."`, which is misleading and unrecoverable via correct-password retry. Because `this.#isLocked` is only ever set to `false` at the very end of the successful path, the wallet is left in the locked state, with no way for the user to reach `application.unlock()` success, `Hook.Unlock`, transaction signing, or fund access — even though they know the correct passphrase.

This mirrors the report's root cause exactly: an operation over N independently-supplied sub-items (extra seeds here; reward tokens there) is only considered successful if every sub-item’s side effect succeeds, so one bad/corrupted/malicious item denies service to a legitimate operation the user is entitled to perform.

The only path to add an "extra seed" is through `addSeed`, which is reachable while unlocked and only validates the mnemonic length/format, not that the derived seed will remain valid indefinitely against `keychain.addSeed`'s invariants: [3](#0-2) 

Storage/serialization corruption of the persisted `extraSeeds` blob (`EXTRA_SEEDS_KEY`, encrypted with a per-primary-seed derived key via `#getExtraSeedsPassphrase`) is enough to trigger this: any bit flip, truncation, or migration bug that alters a stored extra seed's buffer length breaks unlock for all future sessions, not just for the one extra seed.

Contrast this with `Balances` module, which explicitly isolates per-item failures with `Promise.allSettled` and `swallowErrors` so that one broken asset's balance calculation cannot block computing balances for the rest: [4](#0-3) [5](#0-4) 

`Wallet.unlock()` has no equivalent isolation for the extra-seeds loop.

### Impact Explanation
A user with a multi-seed wallet (`maxExtraSeeds > 0`) can be permanently locked out of their entire wallet — including the primary seed, which was successfully validated and would otherwise unlock fine — if exactly one extra seed entry becomes corrupted or otherwise fails `keychain.addSeed`'s strict validation. Since the error is swallowed into a generic "Wrong password" message, the user has no actionable path to recovery (re-entering the correct password will always fail the same way), and there is no `emergencyWithdraw`-equivalent/"unlock ignoring broken extra seed" fallback. This is a direct denial of legitimate wallet access, matching the "user funds get stuck" impact class from the report, scoped to the unprivileged wallet owner and to the auth/encrypted-storage trust boundary (wallet unlock gates all signing and fund access).

### Likelihood Explanation
Triggering requires an extra seed entry to become invalid relative to `keychain.addSeed`'s assertions. This is plausible through: storage corruption/migration bugs affecting the encrypted `extraSeeds` blob, a future regression in `addSeed`/`mnemonicToSeed` that stores a malformed seed, or platform storage bugs truncating data. It is not an attacker-controlled remote exploit in the same sense as a malicious ERC-20 in the original report, but it is a realistic reachable failure mode for any legitimate multi-seed user, and I could not find any test or code path that exercises "extra seed corrupted" recovery — the existing tests only cover the happy path and seed removal, not partial/corrupted extra-seed unlock failures.

### Recommendation
Make `unlock()` resilient to individual extra-seed failures instead of failing atomically:
- Use `Promise.allSettled` (or a per-seed try/catch) for the extra-seeds loop, log/telemetry-report failures per seed, and still set `this.#isLocked = false` once the primary seed is loaded successfully.
- Surface a distinguishable error/warning (not "Wrong password") when the primary seed succeeds but one or more extra seeds fail to load, and expose a way to remove/repair the broken extra seed metadata after unlock.
- Add a regression test asserting that `unlock()` succeeds with the correct passphrase even if one stored extra seed is corrupted, mirroring the pattern already used in `features/balances/module/__tests__/index.test.js:1345` ("survives failure of individual asset balance calculations").

### Proof of Concept
1. Create a wallet and add an extra seed via `wallet.addSeed({ mnemonic: otherMnemonic })` (multi-seed config, `maxExtraSeeds > 0`).
2. `wallet.lock()`.
3. Corrupt the persisted `extraSeeds` entry so its `seed` buffer no longer satisfies `seed instanceof Uint8Array && seed.length === 64` (e.g., simulate by monkey-patching `#getExtraSeeds`/`walletStorage` in a test to return a malformed seed, or by directly tampering with the underlying storage record used by `walletStorage.set(EXTRA_SEEDS_KEY, seeds, { passphrase })`).
4. Call `wallet.unlock({ passphrase })` with the correct passphrase.
5. Observe: `keychain.addSeed(seed)` throws for the corrupted extra seed inside `Promise.all`, `unlock()` catches it and throws `"Wrong password. Try again."`, and `this.#isLocked` remains `true` — the wallet cannot be unlocked at all, despite the correct passphrase and a valid primary seed, matching the report's "funds get stuck" outcome pattern in an auth/encrypted-storage context.
