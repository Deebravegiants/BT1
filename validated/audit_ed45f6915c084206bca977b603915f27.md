### Title
Missing zero-address check on `order.output.beneficiary` permanently burns solver funds in `fillOrder` - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`IntentGatewayV2.placeOrder` accepts an arbitrary `bytes32 output.beneficiary` from any unprivileged caller and never validates that it decodes to a non-zero address. That same unchecked value is later used in `fillOrder` (both the same-chain path `_fillSameChain` and the cross-chain path `_fillCrossChain`) as the recipient of the solver's output tokens/ETH. If `beneficiary` is `address(0)` — e.g. due to a front-end bug, a malformed SDK order, or an uninitialized struct field — the solver's tokens are sent to `address(0)` and are permanently lost.

### Finding Description
`placeOrder` in `evm/src/apps/IntentGatewayV2.sol` (lines 194-415) stamps `order.user`, `order.source`, `order.nonce`, but performs no validation on `order.output.beneficiary` before escrowing the user's inputs and emitting `OrderPlaced`.

Later, when a solver calls `fillOrder`, the order routes to:
- `IntrinsicIntents._fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:53-143`), where line 59 does:
```solidity
address beneficiary = address(uint160(uint256(order.output.beneficiary)));
```
and then, per output asset, either sends native ETH via `beneficiary.call{value: beneficiaryTotal}("")` (line 99) or `IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal)` (line 102) — with no check that `beneficiary != address(0)`.
- `ExtrinsicIntents._fillCrossChain` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:164-220`), where line 170 does the identical unchecked cast, then sends value/tokens to `beneficiary` at lines 189 and 192.

Neither `_authenticate`, `onAccept`, nor any other guard in the intent-fill path rejects a zero `beneficiary`. Since `Order` is entirely attacker/user-supplied data hashed into the `commitment` at `placeOrder` time, and the fill logic trusts that commitment verbatim, a zero beneficiary silently propagates from order creation straight through to the token transfer.

This mirrors the reported bug class exactly: an unchecked, user-supplied address parameter (`destination_`/`beneficiary`-style field) that, if zero, causes funds to be irrecoverably locked/burned — except here the unprivileged, single-transaction path is `IntentGatewayV2.placeOrder` → `fillOrder`, which is explicitly in the reachable intents-escrow surface for this scan. ### Impact Explanation
A zero-address beneficiary causes the solver's output tokens (which can be substantial — the full requested output amount plus any surplus share) to be sent to `address(0)`, permanently destroying them with no recovery path. This is a direct, unbacked loss of solver funds triggered by a single `placeOrder`/`fillOrder` transaction pair — no privileged role, governance, or malicious admin is required. Because the escrowed input side proceeds normally (the user's input tokens are released to the solver as usual), the solver is the party that suffers the loss while the order still "completes" from the protocol's perspective, satisfying the "permanent freezing/loss of funds" bar for Medium/High severity.

### Likelihood Explanation
The order struct is entirely user/front-end supplied; `beneficiary` is a raw `bytes32` field with no contract-side default or non-zero enforcement, and it is directly exposed in the SDK order-building flow (`docs/content/developers/evm/intent-gateway/placing-orders.mdx`) where a coding error, an uninitialized variable, or a bug in third-party SDK/tooling integration could easily leave it as `bytes32(0)`. This exactly matches the report's cited exploit scenario ("a bug in the front end... uninitialized variable is used to construct the transaction"). Any solver filling such an order without independently validating the beneficiary would trigger the loss.

### Recommendation
- **Short term**: In `placeOrder` (or as a shared validation step reachable by both fill paths), revert if `address(uint160(uint256(order.output.beneficiary))) == address(0)`. Alternatively/additionally, validate in `_fillSameChain` and `_fillCrossChain` before any transfer is attempted, so that solvers filling a maliciously/accidentally crafted order also revert safely instead of losing funds.
- **Long term**: Comprehensively validate all externally supplied addresses embedded in structs (`Order.output.beneficiary`, `Order.session`, token addresses, etc.) at the earliest point they enter contract state, and add Slither/static-analysis CI checks for functions performing token transfers to unchecked address parameters.

### Proof of Concept
1. User (or a buggy front end) calls `IntentGatewayV2.placeOrder(order, graffiti)` with `order.output.beneficiary = bytes32(0)` and valid `order.inputs` (e.g., 1000 USDC). The call succeeds; USDC is escrowed and `OrderPlaced` is emitted with `beneficiary = bytes32(0)`.
2. A solver observes the order and calls `fillOrder(order, options)` with `options.outputs` matching the requested output (e.g., 900 DAI), same-chain case.
3. Inside `_fillSameChain`, `beneficiary` resolves to `address(0)`. The solver's DAI is transferred via `IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal)` — i.e., `safeTransferFrom(solver, address(0), 900e18)`. Because `IERC20.transferFrom` to the zero address is not blocked by all ERC20 implementations (and is not blocked here), the 900 DAI is burned; the solver simultaneously receives the escrowed 1000 USDC.
4. Net effect: the solver has irrevocably lost 900 DAI with no way to recover it, and the order is marked filled (`OrderFilled` emitted), closing off any retry/cancel path.

        if (order.inputs.length == 0) revert InvalidInput();

        // Reject duplicate output tokens
        uint256 outputsLen_ = order.output.assets.length;
        for (uint256 i; i < outputsLen_;) {
            bytes32 token = order.output.assets[i].token;
            assembly ("memory-safe") {
                if tload(token) {
                    mstore(0, 0xb4fa3fb3) // InvalidInput.selector
                    revert(0x1c, 0x04)
                }
                tstore(token, 1)
            }
            unchecked {
                ++i;
            }
        }
        // Clean up transient storage so repeated placeOrder calls in the same tx don't false-positive.
