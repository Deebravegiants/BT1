### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by verifying the HMAC over the raw request body, but the `shop` (and `topic`/`api-version`/`webhook-id`) values that are handed to the application's handler are read from unauthenticated HTTP headers that are never included in the signed payload. Because the same `api_secret_key` is shared by every shop that has the app installed, any shop that has installed the app can generate a validly-signed webhook body and then relabel it as coming from a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header and is not part of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, and then forwards `request.shop` (the unauthenticated header) into `WebhookMetadata` that is passed to the app's handler: [3](#0-2) 

`WebhookMetadata#shop` is a plain struct field with no additional binding to the HMAC-verified body: [4](#0-3) 

The identity binding the gem is supposed to enforce is: `shop delivered to the handler == shop that produced the HMAC-valid request`. Because the HMAC secret (`api_secret_key`, i.e. the app's `client_secret`) is identical for every merchant that has the app installed (it is not a per-shop secret), any shop with the app installed can:
1. Trigger a legitimate webhook for its own store (producing a validly HMAC-signed body under the shared `api_secret_key`).
2. Capture that `raw_body` + `x-shopify-hmac-sha256` pair.
3. Replay the same body/HMAC to the app's webhook endpoint, but with `x-shopify-shop-domain` (and `x-shopify-topic`) rewritten to a victim shop's domain.

`Utils::HmacValidator.validate` only checks that the HMAC matches the body: [5](#0-4) 

The check has no knowledge of, and does not bind, the `shop` header, so the forged request passes validation and the handler is invoked believing the (attacker-controlled) payload originated from the victim shop.

This directly parallels the reported bug class ("field acted on but not covered by the HMAC"): the `shop` field is acted upon by the application (attribution, storage key, per-tenant business logic) but is excluded from the cryptographic binding, unlike the OAuth `AuthQuery`, where `shop` is explicitly part of `to_signable_string` and thus IS bound to the HMAC: [6](#0-5) 

### Impact Explanation
An attacker who merely installs the (public) app on any shop they control gains the ability to submit forged, validly-authenticated webhook events under the identity of any other shop that has the same app installed, without needing that victim's credentials, `api_secret_key`, or access token. Depending on how the host application uses `WebhookMetadata#shop` (e.g., as a tenant/session lookup key, to route data writes, or to trigger per-shop side effects), this enables cross-tenant data confusion/injection — writing or triggering attacker-controlled content against another merchant's tenant record. This matches the "Critical – cross-tenant access" impact category defined in scope.

### Likelihood Explanation
Likelihood is high for any multi-tenant app that relies on the gem's documented webhook verification (`Registry.process` / `HmacValidator.validate`) as the sole authentication mechanism and trusts `WebhookMetadata#shop` for tenant attribution — which is the intended, documented usage of this API, not a misuse of it. Any user who can install the app on a shop (a normal, unprivileged action for public apps) can trigger genuinely signed webhooks and replay them with a modified shop header; no secrets or privileged access beyond "having the app installed on one's own store" are required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the value that is bound to the HMAC, or otherwise cryptographically bind the header-sourced `shop` to the verified body — e.g., compute/verify the HMAC over a canonical string incorporating the shop domain, or have `Registry.process` independently confirm that `request.shop` corresponds to a session/shop record that was granted access to trigger this specific webhook subscription (e.g., matching the shop-specific webhook subscription that this endpoint/topic pair was registered for) before invoking the handler.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (both `attacker-shop` and `victim-shop` share the same `api_secret_key` since it's the same app).
2. Attacker performs an action on their own store that triggers a webhook (e.g., `orders/create`), causing Shopify to POST:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC over body B, using shared api_secret_key>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   body: B  (attacker-controlled order content)
   ```
3. Attacker captures body `B` and the HMAC.
4. Attacker replays the same request to the app's webhook endpoint, replacing only:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
   keeping body `B` and the same HMAC unchanged.
5. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, B) == received_hmac` — it never inspects `shop`.
6. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...))`, and the host app processes attacker-controlled data `B` under `victim-shop`'s identity.
