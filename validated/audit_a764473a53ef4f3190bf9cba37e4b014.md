### Title
IntentGatewayV2 (Tron) credits full requested escrow for fee-on-transfer input tokens without measuring actual received balance, causing an accounting overstatement that leads to insolvency - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder()`'s non-predispatch branch escrows ERC20 inputs by calling `safeTransferFrom` for the exact `order.inputs[i].amount` and then unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount` — the nominal (fee-adjusted-for-protocol-fee only) amount — without ever checking the gateway's actual token balance delta. This mirrors the root cause in the M-15 report (`expectedUnderlying`/`withdrawAmount` not accounting for transfer fees), except here the mismatch is baked directly into the escrow ledger rather than a revert-only guard.

For a fee-on-transfer ERC20 input, `safeTransferFrom` moves `order.inputs[i].amount` from the user, but the gateway actually receives `order.inputs[i].amount - transferFee`. The code never measures `IERC20(token).balanceOf(address(this))` before/after the transfer — it simply credits `reducedInputs[i].amount` (derived from the gross, pre-fee `order.inputs[i].amount`) into the `_orders` escrow mapping. The escrow ledger therefore overstates the gateway's true token holdings by exactly the transfer-fee amount.

This is the same root-cause pattern as the M-15 finding: an on-chain accounting value (`expectedUnderlying`/here, `reducedInputs[i].amount`) is derived from the pre-transfer-fee amount and used as if it represented actual tokens held, with no balance-based reconciliation.

Notably, the sibling contract `evm/src/apps/IntentGatewayV2.sol` (main EVM version) *does* correctly guard against this by snapshotting `balanceOf` before/after the transfer and mutating `order.inputs[i].amount` to the actual received delta: [2](#0-1) 
This confirms the Tron variant is missing the fix that exists elsewhere in the codebase, and is the more privileged/exploitable analog.

### Impact Explanation
Because `_orders[commitment][token]` records more than the tokens the gateway actually holds, subsequent `withdraw()` calls (triggered by `RedeemEscrow`, `RefundEscrow` via `onAccept`, or same-chain `cancelOrder`) will attempt to pay out the inflated escrow amount from the gateway's real token balance. Any single unprivileged user placing an order with a fee-on-transfer ERC20 as input creates a shortfall between the ledger and reality. When that order is settled/cancelled, the payout either reverts (freezing funds/breaking that order's flow) or, if the gateway holds surplus tokens (e.g., dust from other orders' protocol fees or other escrows), the shortfall is silently paid out of funds belonging to other orders/depositors — a cross-order fund-draining/insolvency condition. This satisfies "concrete theft or permanent freezing of funds" via unsound state commitment/accounting in the token-bridge/intents escrow path reachable by an unprivileged order placer.

### Likelihood Explanation
Any unprivileged user can trigger this by calling `placeOrder()` with a fee-on-transfer token as an input asset — no special privileges, governance, or admin actions required. The bug is deterministic (triggers on every fee-on-transfer token input in the non-predispatch path), and while it depends on the protocol supporting/allowing fee-on-transfer tokens as intent inputs, the contract places no restriction preventing such tokens from being used, unlike the main EVM variant which explicitly handles this case.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: snapshot `IERC20(token).balanceOf(address(this))` before `safeTransferFrom`, compute the actual received delta afterward, and base both the commitment computation and the `_orders[commitment][token]` credit on the measured received amount rather than the nominal `order.inputs[i].amount`/`reducedInputs[i].amount`.

### Proof of Concept
1. Deploy/select a fee-on-transfer ERC20 token (e.g., 1% fee) as an intent input on the Tron `IntentGatewayV2`.
2. User calls `placeOrder()` with `order.inputs[0] = {token: FOT, amount: 1000e18}`, taking the non-predispatch (`else`) branch.
3. `safeTransferFrom(msg.sender, address(this), 1000e18)` executes; due to the 1% fee, the gateway's actual balance increases by only 990e18.
4. The contract nonetheless sets `_orders[commitment][FOT] += reducedInputs[0].amount` (990e18 if no protocol fee is deducted from the *actual* received but instead computed from the gross 1000e18 minus protocol fee — i.e., still overstated relative to the true 990e18 balance whenever a further transfer-fee reduction is missing from the calculation).
5. When `cancelOrder`/`onAccept` (`RedeemEscrow`/`RefundEscrow`) is later invoked, `withdraw()` attempts to transfer out the recorded escrow amount, which exceeds the token balance actually attributable to this order, causing either a revert (frozen order) or, when other tokens are commingled in the same contract balance, a payout drawn from funds belonging to other users' escrowed orders.
