### Title
Unbounded, unpriced `handle_unsigned` message batches allow free, unconstrained resource consumption on every Hyperbridge node - ([File: modules/pallets/ismp/src/lib.rs])

### Summary
`pallet_ismp::Pallet::handle_unsigned` and its `ValidateUnsigned::validate_unsigned` implementation accept an arbitrary `Vec<Message>` (each `Message::Request`/`Message::Response`/`Message::Timeout` itself wraps an unbounded `Vec` of requests/responses) with no enforced cap on the number of entries, yet the extrinsic is charged a single **static** weight (`weight()` → `Weight::from_parts(300_000_000, 0)`) that does not scale with the size of the batch. Because this is an unsigned, free-of-charge call, `validate_unsigned` fully executes `Self::execute(messages.clone())` — including dedup checks, MMR/state membership-proof verification, and module callback dispatch for every request in the batch — on **every node that receives the gossiped transaction**, before it is even included in a block.

### Finding Description
`handle_unsigned` is dispatched with `ensure_none(origin)` and simply calls `Self::execute(messages.clone())`: [1](#0-0) 

The weight annotation for this call is a fixed constant, independent of `messages.len()` or the size of any nested `requests`/`responses` vectors: [2](#0-1) 

`ValidateUnsigned::validate_unsigned` for this pallet unconditionally re-executes the entire batch (`Self::execute(messages.clone())`) purely to compute the `provides`/`priority` tags for the transaction pool — this runs on **every full node** that receives the gossiped unsigned extrinsic, before any block-weight accounting or fee-based throttling applies: [3](#0-2) 

Inside `execute`, each nested message (e.g. `Message::Request`) is processed by `ismp::handlers::request::handle`, which iterates the full `msg.requests` vector multiple times — deduplication, receipt lookups, timeout checks, proxy checks — then verifies a single membership proof against the whole batch and finally dispatches every request to router module callbacks (`on_accept`): [4](#0-3) 

None of these code paths, nor `handle_unsigned` itself, nor the runtime call filter (`IsmpCallFilter`, which only special-cases BEEFY consensus messages and `fund_message`) enforce any maximum on `messages.len()` or on the length of the `requests`/`responses` vectors nested inside each `Message` variant: [5](#0-4) 

Because the extrinsic is unsigned, it carries no `SignedExtra`/`CheckWeight` extension, so the only practical ceiling on batch size is the node's raw transaction-pool byte-size limit — not any protocol-level count limit. An attacker can therefore craft a single unsigned extrinsic containing as many `PostRequest`/`GetRequest`/`Response` entries as fit in that byte budget (thousands, given individually small request bodies), each of which triggers proof verification and router dispatch work when every peer's `validate_unsigned` runs it — all for free, with the weight system believing the call costs a fixed ~300M weight units regardless of actual size.

### Impact Explanation
This is unconstrained resource consumption (CWE-770) analogous to the Keycloak advisory: an unprivileged party (anyone who can submit/gossip an unsigned extrinsic — no signature, no fee, no prior relationship with the chain) can force **every node in the network** to perform O(n) (or worse, given dedup/sort operations) proof-verification and callback-dispatch work per submitted batch, with the cost hidden from the weight/fee accounting system. Because weight is fixed rather than scaled with `messages.len()`, a maliciously large but still fee-free batch can consume disproportionate CPU/memory relative to what the runtime's weight limits assume, risking degraded block production, mempool congestion, or resource exhaustion across relayers and validators/collators that must validate the same transaction repeatedly as it propagates. This does not directly steal funds, but it threatens availability of the message-delivery path itself — a route that becomes unable to reliably deliver messages under load, which is one of the explicitly in-scope impact categories.

### Likelihood Explanation
Likelihood is high: submitting an unsigned extrinsic requires no stake, fee, or privileged role — only network access to a node's RPC/P2P layer — and the vulnerable code path (`validate_unsigned` → `execute`) runs unconditionally for every unsigned transaction observed by a node, by protocol design ("this allows users to execute ISMP datagrams for free, use with caution", per the code comment). The batch size is bounded only by generic transaction-pool/extrinsic byte-size defaults, not by any ISMP-specific cap, so building a maximal-size batch is straightforward for any relayer-capable actor.

### Recommendation
- Enforce an explicit, protocol-level cap on `messages.len()` and on the length of nested `requests`/`responses` vectors within each `Message` variant, rejecting oversized batches in both `handle_unsigned` and `validate_unsigned` before any expensive proof verification/dispatch work is performed.
- Make the declared `#[pallet::weight(...)]` for `handle_unsigned` a function of the actual batch size (number of messages/requests/responses), rather than a fixed constant, so weight/fee accounting reflects real execution cost and the runtime's block-weight limit correctly throttles large batches.
- Consider charging or rate-limiting unsigned batches (e.g., via priority/longevity tuning already present, plus a hard per-batch size ceiling) so that `validate_unsigned` cannot be used as a free amplification vector across the network.

### Proof of Concept
1. Construct a `pallet_ismp::Call::handle_unsigned` extrinsic with `messages: Vec<Message>` containing a single `Message::Request(RequestMessage { requests, proof, signer })` where `requests` contains the maximum number of minimal `PostRequest` entries that fit within the node's transaction-pool byte-size limit (thousands of entries with minimal `body`/`from`/`to` fields), paired with a proof structured to pass the up-front `dedup_requests` and format checks (it can still fail final membership verification — the expensive dedup/iteration/lookup work in `ismp::handlers::request::handle` happens before the proof is checked).
2. Submit this unsigned extrinsic to a node's RPC endpoint or gossip it over the P2P network.
3. Observe that `ValidateUnsigned::validate_unsigned` (modules/pallets/ismp/src/lib.rs:614) invokes `Self::execute(messages.clone())` on every node receiving the transaction, iterating and hashing every entry in the batch — while the call's declared weight (`weight()`, a constant `300_000_000`) remains unchanged regardless of batch size, showing the accounting/cost mismatch that enables disproportionate resource consumption relative to what the fee-free unsigned path is priced for.

pub fn handle<H>(host: &H, msg: RequestMessage) -> Result<MessageResult, anyhow::Error>
where
	H: IsmpHost,
{
	if msg.requests.is_empty() {
		Err(Error::EmptyBatch)?
	}

	let state_machine = validate_state_machine(host, msg.proof.height)?;
	let consensus_clients = host.consensus_clients();
	let check_state_machine_client = |state_machine: StateMachine| {
		consensus_clients
			.iter()
			.find_map(|client| client.state_machine(state_machine).ok())
			.is_none()
	};

	let router = host.ismp_router();

	// Reject duplicate requests within the batch. Wire format is `Vec`,
	// so this is the line of defence against an attacker padding a
	// batch with identical requests.
	let wrapped: Vec<Request> = msg.requests.iter().cloned().map(Request::Post).collect();
	dedup_requests::<H>(&wrapped)?;

	for req in msg.requests.iter() {
		let req = Request::Post(req.clone());
		// If a receipt exists for any request then it's a duplicate and it is not dispatched
		if host.request_receipt(&req).is_some() {
			Err(Error::DuplicateRequest { meta: req.clone().into() })?
		}

		// can't dispatch timed out requests
		if req.timed_out(host.timestamp()) {
			Err(Error::RequestTimeout { meta: req.clone().into() })?
		}

		// either the host is a router and can accept requests on behalf of any chain
		// or the request must be intended for this chain
		if req.dest_chain() != host.host_state_machine() && !host.is_router() {
			Err(Error::InvalidRequestDestination { meta: req.clone().into() })?
		}

		let source_chain = req.source_chain();

		// in order to allow proxies, the host must configure the given state machine
		// as it's proxy and must not have a state machine client for the source chain
		let allow_proxy = host.is_allowed_proxy(&msg.proof.height.id.state_id) &&
			check_state_machine_client(source_chain);

		// check if the request is allowed to be proxied
		if source_chain != msg.proof.height.id.state_id && !allow_proxy {
			Err(Error::RequestProxyProhibited { meta: req.clone().into() })?
		}
	}

	// Verify membership proof
	let state = host.state_machine_commitment(msg.proof.height)?;
	let commitments = msg
		.requests
		.iter()
		.map(|post| hash_request::<H>(&Request::Post(post.clone())))
		.collect();
	state_machine.verify_membership(host, commitments, state, &msg.proof)?;

	let mut total_weights = Weight::zero();
	let result = msg
		.requests
