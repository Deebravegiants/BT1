## Analog Found

Based on my investigation of the `CallDispatcher` contract and its usage in `IntentGatewayV2`, I found a valid analog of CVE-2024-21574's "unvalidated attacker-controlled parameter reaching a dangerous sink" pattern.

### Title
Unauthenticated `CallDispatcher.dispatch()` allows theft of pooled funds left in the shared dispatcher singleton - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` is a fully public, unauthenticated function that executes an arbitrary caller-supplied array of `Call{to, value, data}` against any contract, exactly analogous to ComfyUI-Manager's unvalidated `pip` field being passed straight into `pip install`. Just as the CVE let an unauthenticated request trigger an attacker-chosen package install, this function lets *any* address trigger an attacker-chosen external call with whatever ETH/ERC20 balance is currently held by the dispatcher.

### Finding Description
`CallDispatcher.dispatch(bytes memory encoded)` decodes an arbitrary `Call[]` and executes `to.call{value: call.value}(call.data)` for each entry, with the only check being that `to` has code (`extcodesize > 0`). There is no `onlyOwner`, `onlyGateway`, or any caller restriction: [1](#0-0) 

`IntentGatewayV2` uses a single shared `_params.dispatcher` address (one global `CallDispatcher` instance) for *all* orders. In `placeOrder`, tokens/ETH are pushed to this shared dispatcher, an order-supplied `order.predispatch.call` is executed against it, and only the tokens/amounts explicitly listed in `order.inputs` are swept back out — the sweep pulls the dispatcher's *entire* balance of each listed token, not just what this order deposited: [2](#0-1) 

Because (1) the dispatcher is a shared singleton across all orders/users, (2) predispatch calldata can leave residual balances of intermediate tokens that are never listed in `order.inputs` (e.g. an LP token being unwrapped into a different output token), and (3) `dispatch()` has no access control at all, any third party can directly call the `CallDispatcher` contract with their own `Call[]` to sweep out ETH/ERC20 balances left behind by other users' orders — funds that were never theirs.

### Impact Explanation
Any unprivileged actor can call `CallDispatcher.dispatch()` to drain any token/ETH balance sitting in the shared dispatcher at the time of the call — including dust, unswept intermediate tokens from other users' predispatch unwrap/swap operations, or ETH sent via `_sendValue(dispatcher, amount)` for native-token orders. This is a direct theft-of-funds vector on a component that legitimate order flows rely on to temporarily hold user assets.

### Likelihood Explanation
High. `dispatch()` requires no privilege and no proof — a plain, unauthenticated transaction. Any user who constructs a `placeOrder` with a `predispatch.call` that intentionally leaves residual balances (e.g., unwraps to a token not listed in `order.inputs`, or under-consumes forwarded ETH) creates directly-stealable value in the shared dispatcher that anyone (including the attacker themself, or a front-runner) can then claim by calling `dispatch()` independently.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the authorized `IntentGatewayV2` (or a fixed allow-listed caller), and/or make the dispatcher accept a scoped session/order id so calls only ever act on that order's already-escrowed funds. Alternatively, sweep the *entire* dispatcher balance of every touched token back to the gateway (not just amounts matching `order.inputs`) so no residual balance can accumulate in the shared singleton between transactions.

### Proof of Concept
1. Attacker (or any user) calls `IntentGatewayV2.placeOrder` with `predispatch.assets` = some LP token, and `predispatch.call` that unwraps the LP token into token A and token B, but `order.inputs` only lists token A.
2. `placeOrder` sweeps only token A back to the gateway (`transferCalls` built from `order.inputs`); token B balance remains inside the shared `CallDispatcher` contract, per [3](#0-2) .
3. Any third party then calls `CallDispatcher.dispatch(abi.encode([Call({to: tokenB, value: 0, data: transfer(attacker, balance)})]))` directly — this succeeds because `dispatch()` has no caller restriction, per [1](#0-0) .
4. The attacker walks away with token B that belonged to the original order's flow.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
