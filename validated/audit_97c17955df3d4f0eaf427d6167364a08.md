### Title
Webhook shop-domain spoofing via header field excluded from HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating an HMAC that covers only the raw request body, then trusts the `shop` value taken from an HTTP header that is never included in that signature. An attacker who controls one shop installed on the app can capture a legitimate, correctly-signed webhook delivered to their own shop and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header rewritten to a victim shop's domain. The HMAC check still passes because it only verifies the body bytes, not the shop identity, letting the attacker's data be processed as if it belonged to the victim tenant.

### Finding Description
The webhook HMAC is computed and verified over `to_signable_string`, which for webhooks is simply the raw HTTP body: [1](#0-0) [2](#0-1) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are all read from HTTP headers and are only checked for *presence*, never included in the signed payload: [3](#0-2) 

`HmacValidator.validate` only calls `validate_signature`, which compares `compute_signature(verifiable_query.to_signable_string, secret)` against the received HMAC — again, purely a function of the body and the shared `api_secret_key`, with no binding to `shop`: [4](#0-3) 

Despite this, `Registry.process` uses the header-derived, unauthenticated `request.shop` as the tenant identity handed to the app's webhook handler immediately after the HMAC check passes: [5](#0-4) 

The broken identity binding is:
`shop_bound_by_HMAC (∅, since to_signable_string == @raw_body only)` ≠ `shop_used_as_tenant_key (request.shop, from an unsigned header)`

Because the `api_secret_key` is shared across every shop that has the app installed, any merchant/attacker with the app installed on their own store legitimately receives real, validly-signed webhook deliveries. They can capture such a delivery (valid body + valid HMAC) and resend it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop that also has the app installed. The gem's `Registry.process` will accept it as authentic and dispatch it to the handler tagged with the victim's shop, since nothing ties the signed body to the shop header.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: an attacker can inject attacker-controlled webhook payloads (and hence attacker-controlled data content in `data.body`) tagged as originating from a different, victim shop. Any app logic that keys per-shop side effects (e.g., updating shop records, writing to shop-scoped storage, triggering shop-scoped business logic) off `WebhookMetadata#shop` can be manipulated cross-tenant, which matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The prerequisite is only having the app installed as a normal (even free/trial) merchant — no access to `api_secret_key`, tokens, or privileged accounts is required, and the request is a straightforward HTTP call with a modified header. This is realistically reachable by any unprivileged user of a multi-tenant app built on this gem.

### Recommendation
Bind the shop identity into the authenticated material: either include the `shop-domain` (and ideally `topic`/`webhook_id`) header values in the HMAC-signable string alongside the raw body, or independently verify that `request.shop` corresponds to a shop session/installation the app already trusts before dispatching to the handler, rather than trusting the header value implicitly once the body-only HMAC succeeds.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged install).
2. Shopify sends a legitimate webhook to the app's endpoint: body `B`, headers including `x-shopify-hmac-sha256: H` (valid over `B`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same body `B` and HMAC `H` to the same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` — see [6](#0-5) .
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-supplied data under the victim's tenant identity — see [7](#0-6) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
