### Title
Duplicate `address(0)` entries in `erc20TokenAddresses` let `msg.value` double-count in `transact()`'s balance equation, minting unbacked shielded ETH - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact` recomputes `balanceDif` independently for every index of `circomData.erc20TokenAddresses`, and for any index equal to `address(0)` it unconditionally adds `msg.value` back into that index's balance delta. Because `msg.value` is a single transaction-wide value, listing `address(0)` at two indices causes the *same* ETH to be credited twice, letting the attacker satisfy two independent `balanceDif == amountChanges[i] + utxoAmount[i]` equations with only one real ETH deposit.

### Finding Description
The invariant that should hold is:

`msg.value` (real ETH received once by the contract) `==` exactly one term in the balance equation across the whole `erc20TokenAddresses` array for the ETH slot.

In `transact()`: [1](#0-0) 

```solidity
for (uint64 i; i < circomData.erc20TokenAddresses.length; i++) {
    int256 balanceDif;
    if (circomData.erc20TokenAddresses[i] == address(0)) {
        balanceDif = int256(newBalances[i]) + int256(msg.value) - int256(oldBalances[i]);
    } else { ... }
    ...
    require(balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + int256(utxoAmount), ...);
}
```

`oldBalances`/`newBalances` are snapshots of `address(this).balance` taken via `getBalancesForArray`, which are queried once for the whole array before and after `_internalTransact`/`_externalTransact` run. Since `msg.value` is already credited to `address(this).balance` before the function body executes, if no further ETH moves during the action, `newBalances[i] - oldBalances[i] == 0` for every ETH index, and the loop's `+ msg.value` term is what "reconstructs" the real deposit for the balance check.

Because this addition happens **per loop index**, not once for the whole transaction, an attacker can place `address(0)` at two indices `i1` and `i2` in `erc20TokenAddresses`. Both indices see identical `oldBalances`/`newBalances` (same address, same snapshot), so:
- `balanceDif[i1] = ΔB + msg.value`
- `balanceDif[i2] = ΔB + msg.value`

Both are independently checked against `amountChanges[i]/onChainCreation[i] + utxoAmount[i]` (line 137-146), and `utxoAmount[i]` sums the amounts of any UTXOs in `utxoSet` whose `erc20Address` matches `circomData.erc20TokenAddresses[i]` (line 116-132), including on-chain UTXOs produced by an external action (e.g. `IExternalActionV2(...).runAction`, `contracts/Hinkal.sol:258-260`, reached for a non-zero `externalActionId` such as Emporium).

Exploit flow with Emporium (`externalActionId != 0`, `signerAddress == 0` unsigned/stateless path):
1. Attacker sends a single `transact()` call with `msg.value = X` and `erc20TokenAddresses = [address(0), address(0)]` (two entries for ETH).
2. Index `i1`: sets `amountChanges[i1] = X`, `onChainCreation[i1] = false`, no on-chain UTXO for this index — satisfies `balanceDif[i1] (=X) == amountChanges[i1] (X) + 0`. This is consumed as the "deposit" leg, matched by a normal off-chain output UTXO created via the proof for value `X` (standard, backed).
3. Index `i2`: sets `amountChanges[i2] = 0`, and crafts the Emporium `runAction` call (unsigned/stateless op, `signerAddress == 0`) to return an on-chain UTXO of value `X` for `erc20Address == address(0)` without moving any real ETH out of/into the contract during the action. This satisfies `balanceDif[i2] (=X) == 0 + utxoAmount[i2] (X)`.
4. Both checks pass using the *same* physical `X` ETH, but the total newly created shielded value is `2X` (one off-chain UTXO of `X` plus one on-chain UTXO of `X`), for a single real deposit of `X`.

None of the existing guards catch this: `performHinkalChecks`/`dimensionsCheck` validate array-length consistency between `circomData` fields but the code inspected does not perform de-duplication of `erc20TokenAddresses` entries; the circuit's `inTotal + amountChanges === outTotal` constraint is enforced per index/token slot as provided by the public inputs and does not know that two slots physically alias the same ETH balance; `rootHashExists`, `insertNullifiers`, and `onlyAllowedRecipient` are unrelated to this specific balance-accounting step.

### Impact Explanation
The attacker mints shielded ETH value greater than what was actually deposited into the contract, directly causing protocol insolvency (unbacked shielded balance) — matching the Critical category "minting shielded value without backing." The attack is repeatable every time `transact()` is called with a duplicated `address(0)` entry and a cooperating external action (or any external action whose `runAction` can be made to produce an extra UTXO for the duplicated index without moving real funds).

### Likelihood Explanation
Preconditions: attacker needs (a) an external action registered via `registerExternalAction` that can be driven to create an on-chain UTXO for an arbitrary token/amount without a corresponding real transfer (the question specifies Emporium's unsigned/stateless op path with `signerAddress == 0`), and (b) the ability to craft `CircomData`/`Dimensions`/proof inputs with a duplicated `address(0)` entry. All of this is within the stated attacker capabilities (deploy/craft own proofs, choose ordering, use any registered external action). The attacker only pays gas plus the single real deposit `X`, and gains `X` of extra unbacked shielded balance per call — fully repeatable. I was not able to fully re-verify `HinkalHelper.performHinkalChecks`/`dimensionsCheck` or the exact Emporium `signerAddress == 0` code path in this session (files not fully read before reaching the tool-call limit), so full confirmation that no duplicate-address check exists elsewhere in `HinkalHelper.sol` or that Emporium's unsigned path can actually fabricate an on-chain UTXO without real value transfer should be re-validated by reading `contracts/HinkalHelper.sol` and `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol` in full.

### Recommendation
Track `msg.value` consumption once per transaction rather than per array index: accumulate a single `ethCredited` flag/variable, add `msg.value` to the balance-equation accounting exactly once (e.g., only for the first occurrence of `address(0)`, or by reducing `msg.value` from a running total as it is consumed), and/or explicitly reject `erc20TokenAddresses` arrays containing duplicate addresses in `performHinkalChecks`/`dimensionsCheck`.

### Proof of Concept
Foundry fork test plan:
1. Deploy `Hinkal`, register a mock external action (`MockEmporiumLike`) whose `runAction` returns a `UTXO[]` containing one entry `{erc20Address: address(0), amount: X}` without transferring any ETH.
2. Build `CircomData` with `erc20TokenAddresses = [address(0), address(0)]`, `amountChanges = [X, 0]`, `onChainCreation = [false, true]`, `slippageValues = [0,0]`, a locally generated valid proof/circuit inputs matching one off-chain output UTXO of value `X` at index 0.
3. Call `hinkal.transact{value: X}(...)`.
4. Assert: `address(hinkal).balance` increased by exactly `X` (real backing), but the sum of newly inserted commitments' shielded value (`off-chain UTXO X` + `on-chain UTXO X`) equals `2X`.
5. Equality to check before/after: `address(hinkal).balance_after - address(hinkal).balance_before == X` while `Σ(amountChanges[i] + utxoAmount[i]) == 2X` — demonstrating the broken invariant `msg.value backing == exactly one accounting term`.
