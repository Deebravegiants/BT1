## Title
Webhook `shop` (and `topic`/`webhook-id`) header values are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `Utils::HmacValidator.validate` verifies the HMAC exclusively against that body [1](#0-0) . The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are read directly from unauthenticated HTTP headers and are never included in the signed material [2](#0-1) . `Registry.process` accepts the request once the body HMAC checks out, then hands the *unverified* `request.shop` straight to the handler as the tenant identifier [3](#0-2) .

### Finding Description
The identity binding that should hold is:

`shop authenticated by HMAC == shop the host application uses as the tenant/session key`

Here it does not: the HMAC (computed with the app's single, shared `api_secret_key`) only binds the *body bytes*, not the `shop-domain` header [4](#0-3) . Because a single app-level secret signs webhooks for *every* shop that installs the app, any merchant who has the app installed can:

1. Receive a legitimate webhook for their own shop (valid body + valid HMAC over that body, signed with the shared app secret).
2. Replay that exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint, but substitute the `x-shopify-shop-domain` header with a victim shop's domain (and/or change `topic`/`webhook-id`).
3. `HmacValidator.validate` still succeeds because it only checks the body bytes against the HMAC [5](#0-4) .
4. `Registry.process` looks up the handler by `request.topic` and calls it with `shop: request.shop` taken straight from the forged header, with no cross-check against the body or against any known session for that shop [3](#0-2) .

The result is that "bytes verified" (the body) and "shop acted on" (the header) are decoupled — exactly the class of binding failure described in the prompt ("a shop authenticated versus the shop stored as a session key" / "bytes verified versus bytes parsed").

### Impact Explanation
This crosses a tenant boundary: an attacker who is a legitimate but malicious merchant of the app can make the host application process webhook events under the identity of an arbitrary other shop. Depending on how the host app's `WebhookMetadata` handler uses `shop` (e.g., to select which stored session/access token to act on, to write to per-shop records, or to trigger data deletion/mandatory-compliance workflows), this enables cross-tenant data injection or corruption without ever needing another merchant's credentials — a Critical-class cross-tenant access issue per the impact taxonomy.

### Likelihood Explanation
Requires only that the attacker be an installed (even free/trial) merchant of the target app — no privileged account, leaked secret, or TLS interception is needed. They only need one genuine webhook delivery to their own shop, plus the ability to POST arbitrary headers to the app's public webhook endpoint, both of which are trivially available to any app installer.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) values into the signed material that `HmacValidator` checks — e.g. include them in `to_signable_string`, or have the host app cross-verify `request.shop` against an independently known list of shops that installed the app before trusting it, rather than trusting the raw header once the body-only HMAC passes.

### Proof of Concept
```ruby
# Attacker is an installed merchant of the app; app_secret is shared across all installs.
legit_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(
    OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_secret, raw_body)
  ),
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
}

# Attacker captured `raw_body` + valid hmac for their own webhook, then replays with a spoofed shop header:
forged_headers = legit_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate succeeds (body unchanged), handler is invoked with
#    WebhookMetadata.shop == "victim-shop.myshopify.com", even though that shop
#    never sent this webhook.
```

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
