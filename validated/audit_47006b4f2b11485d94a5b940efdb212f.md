### Title
Webhook `shop`/`topic`/`webhook_id` metadata is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then dispatches to the app's handler using `shop`, `topic`, `webhook_id`, and `api_version` values that are read from HTTP headers never covered by that HMAC. This breaks the equality that should hold between "the tenant/topic whose bytes were HMAC-authenticated" and "the tenant/topic the handler is told the data belongs to," letting anyone who can obtain one valid `(body, hmac)` pair for the app's shared `api_secret_key` (e.g. by installing the app on their own store) replay it while claiming an arbitrary victim shop domain or topic.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `topic`, `shop`, `api_version`, and `webhook_id` are pulled straight from attacker-controllable HTTP headers with no cryptographic binding to the signed bytes: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e. only the raw body: [3](#0-2) 

`Webhooks::Registry.process` treats this body-only HMAC check as sufficient proof of authenticity for the whole request, then immediately uses the unauthenticated header-derived `request.topic` and `request.shop` to select the handler and to construct the `WebhookMetadata` handed to the app: [4](#0-3) 

The identity binding that should hold is:
`shop/topic/webhook_id bound in the HMAC == shop/topic/webhook_id delivered to the handler`

but in this code the left side doesn't exist at all — only `raw_body` is bound. Since `api_secret_key` is shared across all shops installed on a given app (it is the app's secret, not a per-shop secret), any unprivileged user who installs the app on their own Shopify store legitimately receives real `(raw_body, x-shopify-hmac-sha256)` pairs signed with that same shared secret. That attacker can then POST the identical `raw_body` and `hmac` value to the app's public webhook endpoint while substituting `x-shopify-shop-domain` (any victim shop) and/or `x-shopify-topic` (any topic) headers. `HmacValidator.validate` still returns `true` because it never inspects those headers, and `Registry.process` calls the handler with `WebhookMetadata.new(topic: <attacker-chosen>, shop: <victim-chosen>, body: <attacker's own real payload>, ...)`.

### Impact Explanation
This is a cross-tenant confusion vector at the gem level: the library hands the host application data it asserts came from shop X/topic Y, when in fact only the byte content was authenticated and the shop/topic were never bound to that content. Any application logic that trusts `WebhookMetadata#shop` or `#topic` (e.g. to update the correct tenant's record, to route to a topic-specific handler that makes trust assumptions about payload shape) can be tricked into attributing attacker-supplied data to a different, victim tenant — a cross-tenant access class impact directly caused by the gem's verification routine.

### Likelihood Explanation
Exploitation requires no privileged credentials and no possession of `api_secret_key`: an attacker only needs to be able to install the app on any store they control (a normal, unprivileged action available to the public for public apps) to obtain a valid `(raw_body, hmac)` pair, and then send an ordinary unauthenticated HTTP POST to the app's public webhook endpoint with forged headers. This is fully within the "unprivileged internet user" threat model and requires no host-application misuse — `Registry.process`/`HmacValidator.validate` are the library's own documented verification path.

### Recommendation
Bind the routing/metadata fields into the signed content, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the verified payload before trusting them:
- Extend `VerifiableQuery`/`Webhooks::Request#to_signable_string` so that `shop-domain`, `topic`, and `webhook-id` headers are canonicalized and included in the string that gets HMAC-verified, or
- Have `Registry.process` independently confirm that `request.shop` matches an expected/installed shop (e.g. against session storage) before dispatching, rather than trusting it purely because the body's HMAC validated.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, triggering a legitimate webhook delivery. They capture the raw body `B` and header `x-shopify-hmac-sha256: H` — a valid pair under the app's shared `api_secret_key` per `lib/shopify_api/utils/hmac_validator.rb`.
2. Attacker POSTs to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `x-shopify-hmac-sha256: H` (unchanged)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - `x-shopify-topic: orders/create` (forged, potentially different from the original topic)
3. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B`/`H` (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's parsed body>, ...)`, i.e., data the attacker fully controls is delivered to the app labeled as belonging to `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
