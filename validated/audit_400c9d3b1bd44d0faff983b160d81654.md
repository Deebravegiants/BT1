### Title
Attacker-controlled router calldata lets swap output bypass fee accounting, stealing relay/protocol fees - (File: `contracts/external-actions/swaps/ExternalActionSwap.sol`, `contracts/external-actions/swaps/LifiExternalAction.sol`)

### Summary
`ExternalActionSwap.swap()` computes the relay/protocol fee as a percentage of `swappedAmount`, which is measured purely as a token-balance delta on the swap-executor contract after calling an arbitrary, attacker-supplied router payload. Because that payload (`externalActionMetadata`) is fully controlled by the transacting user (it is only integrity-checked via `calldataHash`, never validated against a required recipient), the user can instruct the router to send the bulk of the swap output directly to their own address instead of back to the `ExternalActionSwap`/`LifiExternalAction` contract, leaving only a negligible residual for fee calculation. This is a direct analog of Method 1 in the referenced report ("leave 2 wei on the contract to avoid paying fees").

### Finding Description
`ExternalActionSwap.swap()` derives fees from the router's measured output: [1](#0-0) 

`callRouter` (LI.FI implementation) computes `swappedAmount` as a plain balance diff on `address(this)` around an arbitrary low-level call to the router using attacker-supplied calldata: [2](#0-1) 

`externalActionMetadata` is part of `ExternalActionData`, which is only bound via `calldataHash`/`signedMessageHash` for internal consistency with the rest of the signed transaction — it is never checked to require the router call to send output back to the swap contract: [3](#0-2) [4](#0-3) 

The only slippage guard inside the swap is a non-zero check, not a check tied to the actual expected output: [5](#0-4) 

Finally, `Hinkal.transact()`'s balance-equation check is tautological with respect to this diversion: it only verifies that Hinkal's own balance change equals the UTXO amount that `ExternalActionSwap` chose to report/forward, not that the full swap proceeds were captured: [6](#0-5) 

Because the LI.FI/router calldata format generally allows specifying an arbitrary output receiver, the attacker can set that receiver to their own EOA, causing `swappedAmount` (and thus both `hinkalFee` and the fee-token `relayFee`) to be computed on a near-zero residual balance, while the actual swap proceeds land directly in the attacker's wallet, completely outside of Hinkal's/the relay's fee accounting.

### Impact Explanation
This breaks the balance equality that is supposed to guarantee the relay/protocol receives its `flatFee`/`variableRate` cut of every swap executed through a whitelisted relay. When a legitimate third-party relay (`circomData.relay != address(0)`, whitelisted, `tx.origin == relay`) submits the transaction on the attacker's behalf, the attacker fully controls the signed `externalActionMetadata` and can divert essentially the entire swap output away from fee calculation, stealing the relay's/protocol's expected fee. This matches the "High - theft of protocol/relay fees" impact category.

### Likelihood Explanation
The attacker only needs the ability to construct their own `circomData`/EdDSA-signed transaction (any regular user can do this) and craft router calldata that specifies an alternate output recipient — a capability inherent to how LI.FI/DEX-aggregator calldata is typically structured. No privileged role, oracle assumption, or admin access is required; the only external dependency is a whitelisted relay agreeing to relay the transaction without deeply validating the embedded router calldata, which is the normal trust model for this component.

### Recommendation
Do not compute fees from a self-measured balance delta on a contract whose call target and calldata are attacker-controlled. Either:
- Enforce that the router call's output recipient parameter is decoded/verified to equal `address(this)` before trusting `swappedAmount`, or
- Require the router call to be constructed by the relay/protocol (not signed arbitrarily by the user) so that the receiver field can be trusted, or
- As the original report recommends, collect a fixed fee in a fixed token (e.g., ETH) independent of the swap's realized output, so diverting swap proceeds cannot reduce the fee owed.

### Proof of Concept
1. Attacker prepares a shielded swap transaction through `ExternalActionSwap`/`LifiExternalAction`, choosing `circomData.relay` = a real whitelisted relay address (so the relay agrees to submit it) and `circomData.slippageValues[1] = 1` (satisfies the non-zero check).
2. Attacker encodes `externalActionMetadata` as a LI.FI/router call whose embedded receiver/destination parameter is the attacker's own EOA rather than `address(this)` (the `LifiExternalAction` contract), while the router still pulls `inputToken` from the contract via the pre-approved allowance.
3. Attacker signs this `circomData` (EdDSA signature covers `calldataHash`/`signedMessageHash`, which include `externalActionData` verbatim — nothing enforces the receiver field's value) and generates a valid proof.
4. Relay submits `Hinkal.transact()`. `callRouter` executes the router call: the bulk of `outputToken` is sent straight to the attacker's EOA by the router; only a negligible residual (or zero) balance change occurs on `LifiExternalAction`.
5. `swappedAmount` ≈ 0 ⇒ `hinkalFee` ≈ 0 and `relayFee` (if `outputToken != feeStructure.feeToken`) is only charged against the negligible residual sent through the fee-token path (or 0 if the flat fee also nets against near-zero funds, causing revert avoidance by setting `flatFee = 0`).
6. Attacker has received the swap output directly, the relay processed the transaction, and the relay/protocol received effectively no fee — while the accounting checks in `Hinkal.transact()` pass because they only compare against the (attacker-manipulated) `utxoAmount` reported by `ExternalActionSwap`.     function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
