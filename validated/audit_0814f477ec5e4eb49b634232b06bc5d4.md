### Title
Emporium Min-path (`erc20TokenAddresses = []`) skips all balance accounting, enabling unauthenticated theft/freeze of Emporium's balance - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `CircomData.erc20TokenAddresses` is empty (the "Min" Emporium path), both `Hinkal.transact`'s value-conservation loop and `EmporiumUpgradeable.runAction`'s `handleOut`/UTXO-minting loop are entirely skipped because they iterate over `circomData.erc20TokenAddresses.length == 0`. Combined with `MainEVMCircuitMin` proving essentially nothing and `verifyWallet` skipping signature checks when `signerAddress == address(0)`, any unprivileged EOA can force Emporium to execute arbitrary stateless calls (including direct ERC20 transfers out of Emporium) with no accounting, no UTXO backing, and no authentication.

### Finding Description
The broken equality is: **value gained/held by Emporium during a call must equal `utxoAmount` minted for a real shielded owner** (`Hinkal.sol:137-146`: `balanceDif == amountChanges[i] + utxoAmount`). Under the Min path this equality is never even evaluated because the loop bound is `circomData.erc20TokenAddresses.length`, which is `0` by definition of the Min path (`contracts/CircomDataBuilder.sol:139-148`).

Path: attacker calls `Hinkal.transact` with a trivially-generated `MainEVMCircuitMin` proof (only constraint: `message = Poseidon(messageSeed)`, `contracts/circuits/MainEVMCircuitMin.circom:1-18`), `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, and `externalActionMetadata` encoding an `EmporiumStack{ signerAddress: address(0), ops: [...] }`. `Hinkal.sol` calls `_externalTransact` → `EmporiumUpgradeable.runAction`. `verifyWallet` sees `stack.signerAddress == address(0)` and returns immediately after marking `emporiumMessage` used, performing no signature check (`EmporiumUpgradeable.sol:302-317`). The stateless branch (`invokeWallet == false` or `signerAddress == 0`) then executes `op.endpoint.call{value: op.value}(op.callData)` for attacker-chosen `endpoint`/`callData`/`value` (`EmporiumUpgradeable.sol:103-113`), e.g. `ERC20(token).transfer(attacker, Emporium.balanceOf(token))`. Because `erc20TokenAddresses` is empty, the subsequent `balanceChange`/`handleOut` loop (`EmporiumUpgradeable.sol:132-151`) never runs, so this transfer is completely unaccounted for — no revert on negative balance, no UTXO minted, nothing returned to `Hinkal.sol`. Back in `Hinkal.transact`, the balance-check loop (`Hinkal.sol:97-146`) also iterates 0 times, so nothing catches the missing accounting either.

Existing guards fail because: `onlyAllowedRecipient` only checks that the call arrives via `Hinkal.sol`'s `_externalTransact` (i.e., any depositor can trigger it with their own valid-but-vacuous Min proof) — it does not check ownership of the funds being moved; `verifyWallet` explicitly no-ops for `signerAddress == address(0)`; and the circuit itself constrains nothing about `ops`, `endpoint`, `callData`, or any UTXO amount.

### Impact Explanation
Two related but distinct outcomes, both Critical:
1. **Freezing**: any legitimate balance gain credited to Emporium during a Min-path call (e.g., a claimed airdrop landing on Emporium's address) is never turned into a UTXO and is invisible to future accounted calls (which only measure balance *deltas* within a call, not absolute residual balance), so it is permanently stuck.
2. **Theft**: any attacker can, independently and repeatedly, submit their own Min-path `transact` with `ops` that directly call `token.transfer(attacker, amount)` against whatever ERC20/ETH balance currently sits in Emporium (whether from the above freeze scenario or any other source, e.g. fees/dust), draining it with zero authentication and zero on-chain accounting.

This breaks the core value-conservation invariant that the protocol relies on and results in direct theft of/unauthorized access to funds routed through Emporium, and permanent freezing of any Emporium-side gains under Min. Repeatable by any EOA at will (cost = one Min-path transact, which requires only a valid Hinkal Merkle root and a self-generated trivial proof — no real UTXO ownership is needed for pure Min-with-empty-token-array calls).

### Likelihood Explanation
- Precondition: attacker must be able to submit a valid `Hinkal.transact` call, requiring `rootHashExists` to pass (any valid root works, no specific UTXO needed since `erc20TokenAddresses` is empty and Min circuit doesn't reference nullifiers/UTXO amounts) and `externalActionMap[HINKAL_EMPORIUM_ACTION_ID]` to be registered (already the case for a deployed Emporium).
- Attacker cost is negligible: generate a Min proof for an arbitrary `messageSeed`, craft `EmporiumStack` with `signerAddress = address(0)` and one `op` calling `token.transfer`.
- Fully repeatable, limited only by whatever balance happens to sit on the Emporium contract at call time.

### Recommendation
Do not allow the Min path to skip accounting when Emporium's balance can change. Either (a) always require `erc20TokenAddresses` to include every token touched by `ops` (verified on-chain, not just trusted from `externalActionMetadata`), forcing the standard `handleOut`/balance-check loop to run, or (b) restrict the stateless "Case 2" branch so it can only be reached with `stack.signerAddress != address(0)` and a valid EIP-712 signature (i.e., remove the `signerAddress == address(0)` bypass in `verifyWallet`, or reject `signerAddress == address(0)` combined with non-empty/attacker-controlled `ops` in the Min path). Additionally, disallow direct external `call` targets and values chosen freely by an unauthenticated `circomData.originalSender` when there is no accompanying token array to reconcile balance changes.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, a mock ERC20, and register Emporium under `HINKAL_EMPORIUM_ACTION_ID`.
2. Seed Emporium with a nonzero mock-token balance (simulate an "airdrop"/stray transfer directly to Emporium's address).
3. As an unprivileged attacker EOA with a valid Hinkal Merkle root (from depositing their own funds), generate a Min proof for `MainEVMCircuitMin` with an arbitrary `messageSeed`.
4. Call `Hinkal.transact` with `circomData.erc20TokenAddresses = []`, `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionMetadata` = ABI-encoded `EmporiumStack{signerAddress: address(0), ops: [{endpoint: mockToken, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, emporiumBalance))}]}`.
5. Assert: (a) the call succeeds without any `require` in `Hinkal.transact`'s balance-check loop firing (loop body never executes since array length 0); (b) no UTXO is minted (`utxoSet` empty / no `insertCommitments` for this token); (c) `mockToken.balanceOf(attacker)` increased by `emporiumBalance` and `mockToken.balanceOf(Emporium)` is now 0 — demonstrating theft with zero accounting.
6. Separately, demonstrate the freeze case: have a Min-path `op` call a mock "claim" contract that mints/transfers tokens to Emporium during the same `transact`; assert `utxoSet.length == 0` after that call (no UTXO minted for the gain), showing the funds are stranded until step 4-5's theft path retrieves them.
