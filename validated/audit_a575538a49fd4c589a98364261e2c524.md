## Analog Found: Missing Chainlink `minAnswer`/`maxAnswer` Bounds Check in `SimplexPaymaster::_getOraclePrice`

### Title
`SimplexPaymaster::_getOraclePrice` accepts Chainlink answers clamped at `minAnswer`/`maxAnswer` without reverting, causing mispriced gas payments during a depeg or oracle-tracked asset crash - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` prices ERC-20 gas payments (USDC, USDT, or any Chainlink-quoted token) against a native-asset/USD feed and a token/USD feed. The price-fetch routine only checks that the Chainlink answer is positive and not stale; it never checks the answer against the underlying aggregator's configured `minAnswer`/`maxAnswer` bounds, which is exactly the bug class described in the external report for `ChainlinkUtil::getPrice`.

### Finding Description
`_getOraclePrice` reads `latestRoundData()` and only validates positivity and staleness: [1](#0-0) 

There is no check that `answer` lies strictly between the aggregator's `minAnswer` and `maxAnswer`. Chainlink aggregators clamp reported answers to a configured range; if the real market price of the underlying asset moves outside that range (e.g., a stablecoin depeg below `minAnswer`, or a violent native-asset crash), `latestRoundData()` continues to return the clamped boundary value as if it were current, valid data. `_getOraclePrice` treats that clamped value as ground truth.

This price feeds directly into `_tokenPrice`, which is used both to size the prefund pulled from the fee-payer during `_validatePaymasterUserOp`/`_prefund` and to compute `estimateTokenCost`/`getTokenPrice` used by off-chain sizing: [2](#0-1) 

### Impact Explanation
This code path is reachable by an unprivileged actor without any governance interaction: any ERC-4337 sender paying gas through the paymaster (including intent solvers bidding on orders, per the `ContractInteractionService.prepareBidUserOp` flow that selects the Simplex paymaster as its `paymasterAndData` provider) triggers `_tokenPrice`/`_getOraclePrice` on every UserOp validation: [3](#0-2) 

If the token/USD feed clamps at `minAnswer` during a depeg (token actually worth less than the floor), the computed `tokenPrice = nativeUsd * 10^decimals * markup / tokenUsd` is understated, so senders are systematically undercharged relative to the true value of gas consumed — a direct, ongoing drain against the paymaster's treasury/surplus for every UserOp processed while the depeg persists. Conversely, if the native-asset feed clamps at `minAnswer` during a native-asset crash, `tokenPrice` is overstated, causing sender overcharges. Both are concrete fund-loss/mispricing outcomes stemming from trusting a clamped Chainlink answer, matching the report's "loss of funds for users" impact class.

### Likelihood Explanation
Chainlink aggregators for volatile or peg-tracking assets (stablecoins particularly) have historically hit `minAnswer` during real depeg events (e.g., USDC/USDT depeg incidents). Given `SimplexPaymaster` explicitly documents support for "USDC, USDT, or any token with a Chainlink feed," and BSC/L2 stablecoin feeds are named directly in the contract's own comments, this is a realistic trigger condition rather than a purely theoretical one, and requires no attacker action — normal market events suffice, and any sender/solver interacting with the paymaster during that window is exposed.

### Recommendation
In `_getOraclePrice`, fetch each aggregator's `minAnswer`/`maxAnswer` (via `AggregatorV3Interface(oracle).aggregator()` → `minAnswer()`/`maxAnswer()`, or by exposing that data as governance-configured immutable bounds per feed) and revert if `answer <= minAnswer || answer >= maxAnswer`, in addition to the existing positivity and staleness checks.

### Proof of Concept
1. Token/USD Chainlink aggregator for a paymaster-registered stablecoin has `minAnswer = 0.90e8`.
2. The stablecoin depegs to $0.50 in the real market; the aggregator, per Chainlink's clamping behavior, continues reporting `answer = 0.90e8` (its floor) via `latestRoundData()`.
3. `_getOraclePrice` at `evm/src/utils/SimplexPaymaster.sol:662-676` accepts this answer unchanged since it is positive and fresh.
4. `_tokenPrice` computes gas cost using the inflated $0.90 valuation instead of the real $0.50, so every UserOp paying gas in that token is charged ~44% less token value than the gas actually costs, draining paymaster surplus/treasury funds relative to true cost on every subsequent UserOp until governance detects and deactivates the token via `DeactivateToken`.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
