### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose body matches the HMAC and then dispatches the handler using the header-derived `shop` value, without any binding between the verified bytes and the claimed tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which plays no role in signature verification: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` (the raw body for webhooks) — it never touches the shop header: [3](#0-2) 

`Registry.process` validates only the HMAC, then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The binding that should hold is:
`hmac == HMAC(secret, raw_body)` AND `shop-domain header == tenant that produced raw_body`

But the gem only proves the first equality. The `shop-domain` header (and `topic`/`webhook-id`) are bytes that are *acted on* (used to attribute the payload to a tenant and dispatch business logic) but *not covered* by the cryptographic check — exactly the class of binding break called out for this scan (“a field acted on but not covered by the HMAC”).

Because Shopify apps share a single `client_secret`/webhook endpoint across all installed shops, any unprivileged user who installs the app on their own shop receives fully valid `(raw_body, hmac)` pairs signed with the app's real secret for their own store's events. Since the header is not part of the signed material, that same valid `(raw_body, hmac)` pair remains valid if replayed with the `shop-domain` header changed to point at a different (victim) shop. The receiving app, using only this gem's `Registry.process` / `Request`, cannot detect the substitution: the HMAC check still passes, and the handler is invoked with `shop: <victim-shop>`.

### Impact Explanation
An attacker with only their own (unprivileged, self-installed) copy of the app can generate legitimate webhook signatures and then replay them against the app's public webhook endpoint with an arbitrary `shop-domain` header value. Any app logic that trusts `WebhookMetadata#shop` to select per-tenant records, tokens, or state (a very common pattern, since the shop is the natural tenant key) can be tricked into applying attacker-supplied webhook data to another tenant's records — a cross-tenant data integrity/confusion issue. This satisfies the "cross-tenant access" impact category.

### Likelihood Explanation
Requires no privileged credentials beyond a normal, self-service app installation (something any internet user can do for a public/embedded app), plus the ability to POST directly to the app's public webhook callback URL with custom headers — both trivially available to an external attacker. The only reason this is not immediately "Critical/trivial" is that it depends on the host application's use of `WebhookMetadata#shop` for tenant-sensitive decisions, but the gem itself provides no protection or documentation warning that the shop header is unauthenticated.

### Recommendation
Bind the tenant/topic identifiers into the HMAC-verified material (or otherwise cryptographically or contextually validate them) before dispatch, e.g.:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string` if Shopify's webhook signing scheme supports it, or
- At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated header values and require host applications to cross-check them against an independently known set of installed shops/subscriptions before trusting them, and consider adding a built-in cross-check against a registered-shop allowlist provided by the host app.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, becoming a legitimate merchant of the app.
2. Shopify sends a real webhook to the app's shared callback endpoint:
   `headers: {x-shopify-shop-domain: attacker-shop.myshopify.com, x-shopify-hmac-sha256: <valid HMAC over raw_body>}`, `body: raw_body`.
3. Attacker captures this exact `(raw_body, hmac)` pair (it's delivered to their own inbox/endpoint if they control the delivery URL, or they can observe it via a proxy on their own infra).
4. Attacker resends the identical `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls `Utils::HmacValidator.validate`, which succeeds because it only checks `raw_body` against the HMAC (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
6. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` even though the payload actually originated from the attacker's own shop, allowing the attacker to inject data attributed to the victim tenant.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
