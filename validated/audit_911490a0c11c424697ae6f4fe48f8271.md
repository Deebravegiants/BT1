The strongest reachable analog to the Teleportation daily-limit DOS is `pallet-bandwidth`'s FIFO subscription eviction: any unprivileged caller can `purchase()` on a `BandwidthManager` for an *arbitrary target app* (via the sponsorship `chain`/`app` fields, which are not validated against the caller), cheaply queuing the minimum tier repeatedly until the victim's 1024-slot FIFO fills and its paid, unexpired allowance gets evicted — denying the victim's dispatches ("route unable to deliver messages") until it repurchases, exactly mirroring the reported Teleportation daily-limit exhaustion.

### Title
Unprivileged Bandwidth-Subscription Eviction DoS via Sponsored `purchase()` Flooding - ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
`pallet-bandwidth`'s `Allowance` ledger is a per-`(app_chain, app)` FIFO list capped at `MAX_SUBSCRIPTIONS` (1024). `BandwidthManager.sol::purchase()` lets *any* caller credit *any* `(app, chain)` pair by simply naming them in the purchase payload — the `chain` argument is explicitly "not validated against the source chain," and the `app` field is attacker-controlled bytes, not `msg.sender`. An attacker can therefore cheaply flood a victim app's subscription list with minimum-tier purchases until it hits the 1024 cap, at which point each further purchase evicts the victim's real, unexpired, paid-for subscription from the head of the FIFO — exactly analogous to the reported Teleportation attack where a bad actor exhausts a shared, unprotected resource (the daily limit) to deny service to legitimate users, here denying the victim's cross-chain message dispatches until it notices and re-purchases bandwidth.

### Finding Description
`BandwidthManager.sol::purchase()` takes `app`, `tier`, `months`, and `chain` as plain calldata with no ownership check tying `app`/`chain` to `msg.sender`: [1](#0-0) 

The docs confirm this is by design for "sponsorship," but the same mechanism means the identity of `app`/`chain` is entirely attacker-controlled and unauthenticated relative to the payer: [2](#0-1) 

On the Hyperbridge side, `on_accept` credits the subscription by appending to the `(app_chain, app)` FIFO with no rate limiting or per-payer isolation, and `push_subscription` evicts the oldest entry once the list is full: [3](#0-2) [4](#0-3) 

The docs explicitly acknowledge the eviction mechanic and its cost profile: [5](#0-4) 

The pallet's own test suite (`subscription_cap_evicts_oldest`) proves the eviction happens once the cap of 1024 is reached, always removing the oldest (front) entry, which is whatever the victim currently has queued: [6](#0-5) 

Because a victim app typically holds only 1–2 live subscriptions ("at the default of one purchase per cycle, 1024 buys is years of headroom" — an assumption the attack directly violates), an attacker only needs to push the list from its current (near-empty) length up to 1024, then continue purchasing to evict each subsequent entry as it's pushed in, including the victim's real allowance once it's shifted to the front.

### Impact Explanation
Once the victim's subscription is evicted, `BandwidthGate::try_consume` finds no live subscriptions for `(source, app)` and returns `GateError::NoAllowance`, rejecting every subsequent ISMP dispatch from that app until it re-purchases bandwidth — a denial-of-service against a specific application's ability to relay messages through Hyperbridge, i.e., "a route unable to deliver messages." This is functionally identical to the reported bug class: an economically cheap, unprivileged action exhausts a shared capacity limit and locks out legitimate users for a period of time (here, until the app notices and repurchases, rather than a fixed 24 hours).

### Likelihood Explanation
Likelihood is High for any specific, known target app: the attack requires only calling `purchase()` on the public `BandwidthManager` contract with the victim's `app` bytes and a supported `chain` string, repeated a bounded number of times (up to 1024 minimum-tier purchases minus the victim's current queue depth). This is fully unprivileged, requires no special permissions, and is explicitly the class of behavior the docs label as "pathological repeat-buy behavior" without any on-chain mitigation (e.g., no per-payer or per-source purchase rate limit, no minimum reserved slots per legitimate subscriber).

### Recommendation
- Isolate or reserve FIFO capacity per payer (or require a minimum floor of un-evictable slots for organically-purchased subscriptions) rather than a single shared 1024-slot list per `(app_chain, app)`.
- Consider requiring the purchasing manager's registered source chain to match the credited `chain`, or otherwise authenticate/limit sponsorship so an unrelated third party cannot cheaply flood an arbitrary victim's queue.
- Alternatively, charge a much higher marginal cost for purchases that would trigger an eviction (i.e., detect `list.len() == MAX_SUBSCRIPTIONS` and require an explicit, higher-priced "eviction fee" or reject silently), so exhausting the cap is not economically trivial for an attacker.

### Proof of Concept
1. Victim app `V` on chain `C` legitimately purchases Tier 1 bandwidth via `BandwidthManager.purchase(V, 1, 1, C)`, landing one `Subscription` in `Allowance[C][V]`.
2. Attacker, from any source chain with a registered `BandwidthManager`, repeatedly calls `purchase(V, 1, 1, C)` (cheapest tier, `months=1`), each time paying only the Tier-1 price, until `Allowance[C][V].len() == MAX_SUBSCRIPTIONS (1024)` — confirmed reachable via `push_subscription`'s `list.try_push` path: [7](#0-6) 
3. Attacker issues one more `purchase(V, 1, 1, C)`; `push_subscription` evicts index 0 — the victim's original subscription — emitting `SubscriptionEvicted`, exactly as demonstrated by the pallet's own `subscription_cap_evicts_oldest` test: [8](#0-7) 
4. `V`'s next ISMP dispatch is now checked by `BandwidthGate::try_consume` against a list whose only live entries are the attacker's junk subscriptions (or none, if those also expire/drain); if insufficient or absent, `V`'s message is rejected with `GateError::NoAllowance`/`Insufficient`, denying `V` service until it manually repurchases and out-competes the attacker's queue depth.

```rust
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}
```

```text
## Subscription Lifecycle

Each `(chain, app)` row holds a FIFO list of subscriptions, capped at **1024** entries. Every purchase appends a new subscription — same-tier repurchases don't stack, they queue.

A subscription is immutable across its lifetime:

| Field             | Behavior                                                                       |
| ----------------- | ------------------------------------------------------------------------------ |
| `tier`            | Recorded at purchase time. Used for events and analytics, not for gating.      |
| `remaining_bytes` | Drains as the gate consumes messages. Pops once it hits zero.                  |
| `expires_at`      | Fixed at purchase. Never extends — a repurchase is a _new_ row, not a renewal. |
| `purchased_at`    | Insertion timestamp. Fixes FIFO order under same-block buys.                   |

### Drain order

The gate drains from the **head** of the list. Once the head is fully consumed it pops and continues into the next. If the next entry is expired it's swept silently — what you paid for is yours only until it expires.

This matters when you queue multiple tiers: the cheapest/oldest entry is consumed first regardless of which tier it came from. Plan top-ups so a higher tier doesn't sit behind a soon-to-expire lower tier you'd rather burn last.

### Eviction

Pushing onto a full list (1024 entries) evicts the **oldest** entry and emits `SubscriptionEvicted` with the lost bytes so the loss is auditable on-chain. In practice this only happens under pathological repeat-buy behavior — at the default of one purchase per cycle, 1024 buys is years of headroom.
```

```rust
/// The 1024-sub cap evicts the oldest entry. force_credit reuses the
/// same push path as purchase, so this also covers the purchase cap.
#[test]
fn subscription_cap_evicts_oldest() {
	new_test_ext().execute_with(|| {
		jump_to(T0);
		let cap = MAX_SUBSCRIPTIONS as u128;

		// Fill the list to exactly the cap. `bytes` encodes the index
		// so we can prove which one got evicted.
		for i in 0..cap {
			Bandwidth::force_credit(
				RuntimeOrigin::root(),
				ForceCreditParams {
					app_chain: APP_CHAIN,
					app: app_key(),
					tier: TIER1,
					bytes: i + 1,
					duration_secs: MONTH_SECS,
				},
			)
			.unwrap();
		}
		assert_eq!(sub_count(APP_CHAIN), cap as usize);
		assert_eq!(sub_at(APP_CHAIN, 0).unwrap().remaining_bytes, 1, "oldest is index 1");

		// One more push: evicts the oldest, appends the new one.
		Bandwidth::force_credit(
			RuntimeOrigin::root(),
			ForceCreditParams {
				app_chain: APP_CHAIN,
				app: app_key(),
				tier: TIER1,
				bytes: cap + 1,
				duration_secs: MONTH_SECS,
			},
		)
		.unwrap();

		assert_eq!(sub_count(APP_CHAIN), cap as usize, "still capped");
		assert_eq!(
			sub_at(APP_CHAIN, 0).unwrap().remaining_bytes,
			2,
			"former second-oldest is now front",
		);
		assert_eq!(
			sub_at(APP_CHAIN, (cap - 1) as usize).unwrap().remaining_bytes,
			cap + 1,
			"new sub is at the back",
		);
	});
}
```
