### Title
Unauthenticated `RequestState` replay bypasses the relay source-identity check, allowing any party to obtain the Orb's/App's last signup-relay message before source validation - ([File: orb-relay-client/src/client.rs])

### Summary
The bug-class in the external report is: a check meant to gate an action to a specific, expected precondition (only-before/only-after a completion state) is implemented via a special-cased branch that runs *before* the state/authorization check, letting an attacker take the branch that skips the intended gate. In `orb-relay-client`, the connection loop that processes incoming `RelayPayload`s for the Orb⇄App signup channel exhibits the same pattern: it special-cases `RequestState` messages and replies with the last cached message *before* verifying that the message's `src.id` matches the expected communicating peer (`self.config.dst_id`).

### Finding Description
In the message-processing loop of the relay client (`orb-relay-client/src/client.rs`), each incoming `RelayConnectResponse::Payload` is matched as follows:

```rust
if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx
        .send(self.last_message.clone())
        .await
        .wrap_err("Failed to send outgoing message")?;
} else if src.id != self.config.dst_id {
    tracing::error!(
        "Skipping received message from unexpected source: {:?}: {payload:?}",
        src.id
    );
} else {
    self.handle_message(
        RelayPayload { src: Some(src), dst, seq, payload: Some(payload) },
        message_buffer,
    )
    .await?;
}
``` [1](#0-0) 

The `src.id != self.config.dst_id` validation — the mechanism intended to enforce that only the expected paired peer (the Orb for a given signup session, or the App for that same session) can influence this client's state — is only evaluated in the `else if` branch. The `RequestState` branch is checked first and is taken unconditionally, regardless of who sent the message. This mirrors the reported flaw: a completion/goal-state gate (`liquidityGoalReached()` in the report; the source-identity gate here) is bypassed by taking an alternate code path that executes before the gate is consulted.

Any relay peer that can reach the same relay channel (identified only by `orb_id`/`session_id`, which are transmitted over the wire and visible to both `Client::new_as_app` and `Client::new_as_orb` per `orb-relay-client/src/lib.rs` and `orb-relay-client/src/bin/manual-test.rs`) can send a `RequestState` payload and receive `self.last_message` echoed back — without needing to be the legitimate counter-party.

### Impact Explanation
`last_message` holds the most recent message sent over the relay channel for that signup session, e.g. `AnnounceOrbId` or `SignupEnded` payloads used to coordinate the App-Orb self-serve signup flow. Because the identity check is bypassed for this control message, an unauthorized party on the relay channel can:
- Retrieve state intended only for the legitimate paired peer (information disclosure across a supposed trust boundary), and
- Repeatedly trigger replay/re-delivery of the last relayed message, which can be used to desynchronize or confuse the signup state machine on either the Orb or App side (a state-bleed/DoS-adjacent condition analogous to the reported transfer DoS, where a completion/goal check is defeated by an alternate branch).

This does not by itself allow biometric data exfiltration or forged attestations, but it does violate the intended cross-signup isolation of relay state and can cause misattributed or confused signup coordination between an Orb and an App that are not the legitimate pair.

### Likelihood Explanation
Reaching this code requires only the ability to send a message on the relay channel that decodes as `self_serve::app::v1::RequestState` — no cryptographic proof of being the paired peer is required for this specific message type, and the check that would normally filter by `src.id` is structurally skipped for it. Likelihood is Medium: it depends on whether the relay backend itself restricts message routing/session membership at a layer above this client code (which this repository does not implement) — the client-side code alone does not enforce the boundary here.

### Recommendation
Move the `src.id != self.config.dst_id` check ahead of the `RequestState` special case so all inbound payloads are subject to the same source-identity validation before any reply/state-disclosure logic executes:

```diff
- if self_serve::app::v1::RequestState::matches(&payload).is_some() {
-     sender_tx.send(self.last_message.clone()).await...
- } else if src.id != self.config.dst_id {
-     tracing::error!(...);
- } else {
-     self.handle_message(...).await?;
- }
+ if src.id != self.config.dst_id {
+     tracing::error!(...);
+ } else if self_serve::app::v1::RequestState::matches(&payload).is_some() {
+     sender_tx.send(self.last_message.clone()).await...
+ } else {
+     self.handle_message(...).await?;
+ }
```

### Proof of Concept
1. A relay peer connects using the same `orb_id`/`session_id` pair as an in-progress legitimate Orb↔App signup session (these identifiers are transmitted in plaintext relay messages, e.g. observable via `orb-relay-client/src/bin/manual-test.rs` usage patterns). [2](#0-1) 
2. The rogue peer sends a `self_serve::app::v1::RequestState {}` payload. [3](#0-2) 
3. Because the match on `RequestState` in the receive loop executes before the `src.id != self.config.dst_id` check, the legitimate client immediately replies with `self.last_message.clone()` to the rogue peer, regardless of the rogue peer's identity. [1](#0-0) 

**Note on limitations:** I was not able to view the full surrounding context of `orb-relay-client/src/client.rs` (lines 1-120, 380-460) in this final iteration due to a tool-call error, so I could not fully confirm how/where `self.config.dst_id` is established relative to session/channel membership on the relay backend side, nor whether any server-side authorization independently restricts which peers can attach to a given `orb_id`/`session_id` channel before reaching this client code. If the relay backend strictly binds one Orb and one App per session at the transport layer, the practical exploitability of this client-side ordering bug would be reduced; this could not be verified from the indexed contents available.
