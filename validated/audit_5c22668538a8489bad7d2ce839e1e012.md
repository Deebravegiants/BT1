### Title
`MasterPlan::detect_fraud` unconditionally returns `Ok(false)` and `fraud_check::Report` has zero checks, causing all signups to be tagged `SignupReason::Normal` regardless of scene manipulation - ([File: src/plans/mod.rs, src/plans/fraud_check.rs])

### Summary
`MasterPlan::detect_fraud` in `src/plans/mod.rs` is hardcoded to return `Ok(false)` for any completed biometric pipeline, and the backing `fraud_check::Report` struct in `src/plans/fraud_check.rs` is defined with `N_FRAUD_CHECKS = 0` (empty check list), so `fraud_detected()` can never evaluate to `true`. This means any signup — including one driven by a presented photo/printed-iris scene that completes the biometric pipeline — is always classified `SignupReason::Normal` and forwarded as such to `signup_post::request`'s `reason` form field and into `personal_custody_package` enrollment.

### Finding Description
`detect_fraud` is called from the signup flow at [1](#0-0)  as `!self.skip_fraud_checks() && self.detect_fraud(orb, debug_report, pipeline.as_ref()).await?`. Its implementation is: [2](#0-1) 
When a biometric pipeline exists (`Some(_pipeline)`), the function still returns `Ok(false)` unconditionally — the comment `// FOSS: WE HAVE DELETED ALL FRAUD CHECKS` documents that no actual analysis of the pipeline output occurs.

The underlying `fraud_check::Report` type is likewise gutted: `N_FRAUD_CHECKS` is set to `0`, `Report {}` has no fields, and `fraud_checks()`/`fraud_checks_strict()` return empty arrays, so `fraud_detected()` (`self.fraud_checks_strict().iter().any(|&v| v)`) always evaluates over an empty iterator and returns `false`, per [3](#0-2)  and [4](#0-3) . `FraudChecks::run` similarly just returns `Report {}` without evaluating anything: [5](#0-4) .

Because `fraud_detected` is always `false`, the branch at [6](#0-5)  always selects `SignupReason::Normal` (unless the pipeline itself failed, giving `SignupReason::Failure`). This `signup_reason` is passed into `build_pcp` (feeding `personal_custody_package::Plan.signup_reason`) and into `enroll_user::Plan.signup_reason`, and ultimately reaches `signup_post::request`'s `reason` parameter, which is serialized into the outgoing form as `"reason": "NORMAL"` at [7](#0-6) .

Note, however, that `signup_post.rs` itself documents that this locally-computed reason is distinct from server-side fraud analysis: [8](#0-7)  — "Signup was detected as a fraud attempt at the orb (not to be confused with the backend fraud checks)". The raw iris codes/images are also uploaded (`codes` field, `format_pipeline`), so backend-side duplicate/fraud detection using the biometric payload itself is a separate, out-of-repo control not affected by this bug. This finding is specifically about the orb-local fraud signal being permanently disabled/fail-open.

### Impact Explanation
Any signup that reaches a completed biometric pipeline (e.g., one performed by presenting a spoofed/printed iris or photo that nonetheless satisfies capture quality gates) is unconditionally reported to the backend as `SignupReason::Normal` rather than `SignupReason::Fraud`, because the on-device fraud detection layer is a permanent no-op (`Ok(false)` / empty `Report`). This corresponds to a liveness/fraud-bypass class impact: any backend-side handling, quarantine, or reduced-trust workflow that keys off the orb-reported `reason=FRAUD` tag is defeated, since the orb never emits that tag under any circumstance. This is scoped to the local reporting signal; it does not itself forge cryptographic signatures or bypass server-side iris-uniqueness checks that operate on the uploaded biometric codes.

### Likelihood Explanation
This is deterministic and always occurs — the code path unconditionally returns `Ok(false)` whenever a pipeline exists, so it requires no special attacker skill beyond completing a normal signup flow (e.g., successfully forcing biometric_pipeline to produce output via a presented photo/printed iris that passes upstream capture-quality checks, which is a separate concern from this specific check). Every signup on this build is affected identically, with 100% repeatability.

### Recommendation
Restore or re-implement the fraud detection checks referenced by `fraud_check::Report`/`FraudChecks::run` and `MasterPlan::detect_fraud`, so that `N_FRAUD_CHECKS` reflects actual evaluated rules and `detect_fraud` returns the true result of pipeline analysis (e.g., liveness, occlusion, previously-flagged face-identifier results) instead of a hardcoded `Ok(false)`. At minimum, if this "FOSS" build intentionally strips proprietary checks, `SignupReason` reporting and any downstream trust decisions should not silently default to `Normal`; the removal should be made explicit to operators/backend rather than an implicit fail-open path.
