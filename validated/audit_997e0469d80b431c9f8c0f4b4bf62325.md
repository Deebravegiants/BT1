### Title
Unbacked shielded-ETH minting via duplicate `address(0)` slots in `erc20TokenAddresses` - (File: `contracts/Hinkal.sol`)

### Summary
In `Hinkal.transact`, the balance-equality check that is supposed to enforce "ETH actually received == shielded value created" is computed **independently per token-array index**, and for every index whose token is `address(0)` the code unconditionally re-adds the *entire* `msg.value` to that index's `balanceDif`. Because `circomData.erc20TokenAddresses` has no uniqueness constraint (neither in Solidity nor in `MainEVMCircuit.circom`), an attacker can list `address(0)` more than once and get `msg.value` credited once *per occurrence*, letting a single ETH payment back multiple shielded UTXOs.

### Finding Description
The per-token balance check is: [1](#0-0) 

For every index `i` where `erc20TokenAddresses[i] == address(0)`, `balanceDif` adds `msg.value` on top of `newBalances[i] - oldBalances[i]`. Since ETH for a deposit is already sitting in the contract before `oldBalances`/`newBalances` are captured (no actual internal ETH transfer happens for deposits — see `transferERC20TokenFromOrCheckETH` only validating `msg.value`), `newBalances[i] - oldBalances[i]` is `0` for ETH, and the entire credited amount for that index comes from the unconditional `+ msg.value` term.

This value is then checked per-index against the claimed created value: [2](#0-1) 

Because this equality (`balanceDif == amountChanges[i] + utxoAmount`) is evaluated **per index**, and `msg.value` is re-added at *every* matching index, listing `address(0)` twice (or N times) lets the contract "see" `msg.value` credited N times, once for each slot, even though only one ETH payment was made.

Nothing prevents duplicate `address(0)` entries:
- `dimensionsCheck` only validates array *lengths* match `dimensions.tokenNumber`, not uniqueness: [3](#0-2) 
- `getHashedCalldata`/`getSignedMessageHash` bind `erc20TokenAddresses` into the signed message (so the array itself can't be tampered with post-signing), but they never enforce distinctness of its elements: [4](#0-3) 
- `MainEVMCircuit.circom` computes commitments/nullifiers per token slot `i` independently — nothing ties slot `i`'s address to be different from slot `j`'s address, so two slots can both legitimately be constrained to token `address(0)`: [5](#0-4) 

Because each slot's UTXO commitment independently encodes `erc20TokenAddress = address(0)` via `OriginalCommitmentCalculator`, both resulting UTXOs are valid, spendable ETH UTXOs once inserted into the tree via `insertCommitments`: [6](#0-5) 

### Impact Explanation
This breaks the core balance-conservation invariant of the protocol: shielded ETH value is minted without backing. An attacker sends `X` wei once but ends up with `N*X` wei worth of valid, later-spendable ETH UTXOs in the shielded pool, which can subsequently be withdrawn draining the contract's real ETH reserves collected from other users. This is a direct "minting shielded value without backing" — Critical impact per the defined severity categories.

### Likelihood Explanation
The attacker only needs to be an unprivileged EOA capable of constructing a valid proof for `MainEVMCircuit` with `tokenCount >= 2`, listing `address(0)` in two (or more) slots of `erc20TokenAddresses`, and generating the corresponding EdDSA signature/nullifiers/commitments — all of which are within a normal user's control (their own spending key), and require no privileged role, relay collusion, or price-oracle assumption. No component of the check-suite (dimensions, calldata hash, signed message hash, circuit) rejects the duplicate-address configuration, so likelihood is high once tokenCount ≥ 2 circuits/verifiers are deployed.

### Recommendation
Aggregate ETH-specific balance accounting once (not per index), or explicitly disallow duplicate `erc20TokenAddresses` entries (e.g., require strictly-increasing/unique addresses) both in `dimensionsCheck`/`performHinkalChecks` and as a circuit constraint, so `msg.value` cannot be attributed to more than one token slot.

### Proof of Concept
1. Deploy/use a `MainEVMCircuit` variant with `tokenCount = 2` (or any `>=2`).
2. Craft `circomData.erc20TokenAddresses = [address(0), address(0)]`.
3. Set `amountChanges = [X, X]`, `onChainCreation = [false, false]` (or true, depending on desired commit path), with valid empty `inputNullifiers` for each slot (since this is a deposit) and two `outCommitments`, one per slot, each committing a UTXO of amount `X` and `erc20TokenAddress = address(0)`, tagged with the attacker's own stealth key.
4. Generate a matching EdDSA signature over `signedMessageHash` (built from `getSignedMessageHash`, which includes `erc20TokenAddresses`, `amountChanges`, etc., all consistent with the above) and produce the zk-proof for `MainEVMCircuit` satisfying all constraints (each slot's Merkle/overflow/commitment constraints are independent per-slot, no cross-slot uniqueness constraint exists).
5. Call `Hinkal.transact(a, b, c, dimensions, circomData)` with `msg.value = X`.
6. In `_internalTransact`, `deltaAmountChange` for slot 0 and slot 1 are both `X > 0`; `transferERC20TokenFromOrCheckETH` is invoked twice for `address(0)` but since ETH transfer for `address(0)` is a no-op check against already-received `msg.value`, no additional ETH is required.
7. Back in `transact`, for slot 0: `balanceDif = 0 + X - 0 = X`, matches `amountChanges[0] (X) + utxoAmount(0)`. For slot 1: identical result `X`, matches `amountChanges[1] (X) + utxoAmount(0)`. Both `require` checks pass.
8. `insertCommitments` inserts both UTXO commitments (each worth `X` ETH) into the Merkle tree — the attacker now holds `2X` in spendable shielded ETH backed by only `X` wei actually deposited.

    function insertCommitments(
        uint256[][] memory offChainCommitments,
        bytes[][] memory offChainEncryptedOutputs,
        OnChainCommitment[] memory onChainCommitments,
        bool[] memory onChainCreation
    ) internal {
        // 1) Total Length of Commitments
        uint256 length = 0;
        for (uint256 i = 0; i < offChainCommitments.length; i++) {
            for (uint256 j = 0; j < offChainCommitments[i].length; j++) {
                if (onChainCreation[i]) break;
                length += offChainCommitments[i][j] != 0 ? 1 : 0;
            }
        }
        length += onChainCommitments.length;

        if (length > 0) {
            // 2) Flattening leaves array
            uint256[] memory leaves = new uint256[](length);
            uint256 index = 0;
            for (uint256 i = 0; i < offChainCommitments.length; i++) {
                for (uint256 j = 0; j < offChainCommitments[i].length; j++) {
                    if (onChainCreation[i] == true) break;
                    if (offChainCommitments[i][j] != 0) {
                        leaves[index++] = offChainCommitments[i][j];
                    }
                }
            }
            for (uint256 i = 0; i < onChainCommitments.length; i++) {
                leaves[index++] = onChainCommitments[i].commitment;
            }

            // 3) Inserting Leaves
            uint256[] memory insertedIndexes = insertMany(leaves);

            // 4) Emitting Commitments/EncryptedOutputs
            index = 0;
            for (uint256 i = 0; i < offChainEncryptedOutputs.length; i++) {
                for (uint256 j = 0; j < offChainEncryptedOutputs[i].length; j++) {
                    if (onChainCreation[i] == true) break;
                    if (offChainCommitments[i][j] != 0) {
                        emit NewCommitment(
                            leaves[index],
                            int256(insertedIndexes[index]),
                            offChainEncryptedOutputs[i][j]
                        );
                        index++;
                    }
                }
            }
            for (uint256 i = 0; i < onChainCommitments.length; i++) {
                emit NewCommitment(
                    leaves[index],
                    -1 * int256(insertedIndexes[index++]),
                    abi.encode(
                        onChainCommitments[i].utxo,
                        onChainCommitments[i].onChainEncryptedOutput
                    )
                );
            }
        }
    }
