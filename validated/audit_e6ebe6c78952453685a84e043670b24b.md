### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing tenant spoofing on replayed webhook bodies - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature check over the raw request body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and forwarded to the app's webhook handler as trusted tenant-identifying metadata.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` decodes the `hmac-sha256` header for comparison: [1](#0-0) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which calls `validate_signature`, computing `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` (i.e., the raw body) and comparing it to the received signature: [2](#0-1) 

After this check passes, `Registry.process` builds `WebhookMetadata` directly from `request.shop`, `request.topic`, and `request.webhook_id` — all values sourced from headers that were never part of the signed payload: [3](#0-2) 

The identity binding that should hold is: `shop header == shop cryptographically bound to the HMAC-signed payload`. In this implementation, the equality that actually holds is only `hmac(raw_body) == received_hmac`; `shop` (and `topic`/`webhook_id`/`api_version`) are parsed from headers with no cryptographic tie to that signature at all. Any attacker who can obtain one valid `(body, hmac)` pair — trivially available by installing the app on their own store and receiving a legitimate webhook for any topic that produces an empty or attacker-known body (e.g. `{}` as used in the test fixtures, or any webhook whose payload the attacker fully controls/knows) — can replay that exact body and HMAC while substituting an arbitrary `x-shopify-shop-domain` header value. `Utils::HmacValidator.validate` will still return `true` because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the forged `shop`.

### Impact Explanation
This breaks the shop/tenant binding that host applications rely on to route webhook data and access-token lookups per shop. Since `WebhookMetadata#shop` is the value app developers are documented to use to load per-shop credentials/session data, an attacker can cause the app to process attacker-supplied (or replayed) webhook content under an arbitrary victim shop's identity, enabling cross-tenant data confusion in the app.

### Likelihood Explanation
Exploitation requires no privileged credentials: any user can install the app on a store they control (or otherwise obtain one legitimate `(body, hmac)` pair for a predictable/empty payload, e.g. mandatory `shop/redact` or `customers/redact` topics which can have small/predictable bodies) and then send that body+hmac to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header. This is a pure unprivileged internet-facing HTTP request against the gem's documented `Registry.process` entry point.

### Recommendation
Include the tenant-identifying fields (`shop`, `topic`, and ideally `webhook_id`/`api_version`) in the signed material, or otherwise cryptographically bind them to the payload before trusting them in `WebhookMetadata`. At minimum, document/enforce that consumers must independently verify `shop` against a known-installed-shop list rather than trusting `WebhookMetadata#shop` as authenticated, and consider having `Request#to_signable_string` incorporate the header values that downstream code treats as authenticated.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook delivery with headers `x-shopify-hmac-sha256: <H>` and body `{}` (as shown by the test fixture computing `hmac = OpenSSL::HMAC.digest(sha256, api_secret_key, "{}")`): [4](#0-3) 
2. Attacker replays this exact `(raw_body="{}", hmac=<H>)` to the victim app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and any `x-shopify-topic` the app has a handler for.
3. `Utils::HmacValidator.validate` returns `true` because it only checks `raw_body` against `<H>`, which is unchanged.
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: {}, ...)`, causing the app to act as if it received a genuine webhook from `victim-shop.myshopify.com`.
