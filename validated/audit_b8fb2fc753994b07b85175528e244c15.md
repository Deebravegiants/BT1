### Title
Webhook `shop` domain is trusted from an unauthenticated header while the HMAC only covers the raw body, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the `hmac-sha256` header against the raw request body, then hands the caller-supplied `shop-domain` header straight to the app's handler as the tenant identifier. The `shop` field is never included in the signed material, so the binding "`shop` the app acts on" == "`shop` verified by the HMAC" does not hold.

### Finding Description
`Registry.process` gates webhook handling on `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator` computes the expected signature purely from `verifiable_query.to_signable_string` and the app's `api_secret_key`: [2](#0-1) 

For webhooks, `to_signable_string` returns only `@raw_body`: [3](#0-2) 

Meanwhile `shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is not part of the signed string at all: [4](#0-3) 

After HMAC validation succeeds, `request.shop` is passed unchanged into `WebhookMetadata`, which the host application's handler is documented to trust as "The shop domain of the webhook": [1](#0-0) [5](#0-4) 

The `api_secret_key` used to compute the HMAC is the app's single client secret, shared across every shop that installs the app — it is not shop-specific. Consequently any two webhook deliveries with the same body (e.g. an empty-body test event, or any event whose payload an attacker can control/predict for their own store) will carry HMACs that verify successfully regardless of which shop they were originally sent for.

### Impact Explanation
An unprivileged attacker who installs the app on their own (attacker-controlled) shop can trigger any registered webhook topic and capture a `(raw_body, hmac)` pair that is valid under the app's shared secret. Because the shop identity is carried in an unauthenticated header, the attacker can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` value (e.g. a victim shop). `Registry.process` will accept it as authentic and invoke the handler with `WebhookMetadata#shop` set to the victim's domain, since HMAC validation never inspects the shop field. Any host application that uses `data.shop` (as the documentation instructs) to key data lookups, cache invalidation, uninstall/reinstall handling, or other tenant-scoped side effects can be made to act on the wrong tenant — a cross-tenant data-integrity/confidentiality issue driven entirely through this gem's own webhook verification API.

### Likelihood Explanation
Moderate-to-high for topics with static, predictable, or attacker-influenced bodies (e.g. `app/uninstalled`, `shop/redact`, or any topic where the attacker's own shop can produce a body identical or similar to what a victim's shop would produce, or where the attacker doesn't need to match a real victim payload at all because the handler primarily keys off `data.shop`). No credentials, tokens, or elevated access are required — only the ability to install the target app on one's own store (a normal, unprivileged action) and to send an HTTP POST to the app's public webhook endpoint.

### Recommendation
Bind the shop domain into the signed material verified for webhooks, or otherwise authenticate it independently before trusting it as the tenant key. For example, include the shop-domain header value in `to_signable_string` (requiring per-request re-derivation using a value Shopify itself signs) or cross-check `request.shop` against a shop already known/authorized for the specific `webhook_id`/subscription before handing it to the handler. At minimum, document prominently that `data.shop` is unauthenticated and must be independently verified against records the app owns (e.g. only accept it if a corresponding registration/session already exists for that shop and that shop is expected to send this `webhook_id`).

### Proof of Concept
```ruby
# Attacker installs the app on their own store "attacker.myshopify.com"
# and triggers a webhook (e.g. app/uninstalled), capturing what Shopify sends:
raw_body = '{}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker now replays the same body+hmac to the victim's webhook endpoint,
# forging the shop-domain header:
forged_headers = {
  "x-shopify-topic" => "app/uninstalled",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-chosen, unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HMAC validation passes (it only checks raw_body against the shared secret);
# the registered handler is invoked with data.shop == "victim-shop.myshopify.com"
```

Note: I was not able to fully trace how downstream consumers (e.g. `shopify_app`) use `data.shop` in every deployment, so real-world severity depends on how host applications key data off this field; this is inherent to the gem's own webhook-processing API and documented contract, not a misuse of an undocumented feature.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))

          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
