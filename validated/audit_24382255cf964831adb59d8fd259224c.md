### Title
Webhook `shop`/`topic` headers are not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating `Utils::HmacValidator.validate(request)` against the raw request body [4](#0-3) . The HMAC is computed only over `to_signable_string`, which returns `@raw_body` and nothing else [1](#0-0) . The `shop`, `topic`, and `webhook_id` values consumed by `process` and forwarded to the app's `WebhookHandler` come from HTTP headers that are never included in the signed payload [2](#0-1) .

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, raw_body + shop + topic)` (or at minimum the tenant identity should be cryptographically bound to the signature). In this codebase the actual equality enforced is only `hmac == HMAC(secret, raw_body)` [5](#0-4) . The `client_secret` used to sign webhooks is shared by the app across every shop that installs it — it is not per-tenant. Consequently, any party who can obtain one valid `(raw_body, hmac)` pair signed with that shared secret (e.g., by installing the public app on a shop they control and capturing a legitimately delivered webhook) can replay that exact body/hmac pair to the app's public webhook endpoint while substituting arbitrary `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` header values. `Registry.process` will still consider it "Invalid webhook HMAC."-free because the signature check never touches those headers, and it will dispatch to the handler with `shop: request.shop` and `topic: request.topic` taken straight from the attacker-controlled headers [6](#0-5) .

### Impact Explanation
This breaks the tenant binding an app relies on to route webhook side effects (e.g. uninstall cleanup, GDPR redaction, order/customer processing) to the correct shop. An attacker can make the app believe a forged event (with attacker-chosen topic and shop) occurred for a victim shop, using only a body/signature pair harvested from their own, unprivileged install of the same public app — no access token, `client_secret`, or privileged account required. Depending on the handler logic this enables cross-tenant data confusion or corruption (e.g., triggering `shop/redact` or `app/uninstalled` handling for a shop that never requested it).

### Likelihood Explanation
Any internet user can install a publicly listed app on a shop under their control at no privilege cost, causing Shopify to deliver at least one legitimately-signed webhook to the app's public endpoint. Because the signing secret is shared across all tenants of the app and the signature covers only the body, capturing and replaying that single body/hmac pair with forged `shop`/`topic` headers is a direct, low-effort attack requiring no interception of TLS or victim credentials.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that's verified, e.g. include the relevant headers in `to_signable_string`, or have `Registry.process` cross-check `request.shop` against an app-maintained list of shops it actually installed/registered webhooks for before invoking the handler.

### Proof of Concept
1. Install the target public app on `attacker-shop.myshopify.com` (no special privilege needed).
2. Trigger any subscribed webhook topic and capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends to the app's webhook endpoint.
3. Re-issue the exact same POST body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [4](#0-3) ; since the hmac was computed over the same raw body, validation succeeds and the handler executes with `shop: "victim-shop.myshopify.com"` even though that shop never sent this event.
