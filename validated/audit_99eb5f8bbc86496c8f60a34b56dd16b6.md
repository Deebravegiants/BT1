## Title
Webhook shop/topic/version/id headers are trusted for tenant routing despite not being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` (and `topic`, `api_version`, `webhook_id`) values from unauthenticated HTTP headers, while the HMAC signature that `Utils::HmacValidator.validate` checks only covers the raw request body. `ShopifyAPI::Webhooks::Registry.process` accepts the request as valid based solely on that body-only signature and then forwards the header-derived `shop` value to the app's handler as the authoritative tenant identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes and compares the HMAC exclusively over that signable string: [2](#0-1) 

Meanwhile, `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read straight from HTTP headers, none of which are part of the signed payload: [3](#0-2) 

`Registry.process` validates only the HMAC and then dispatches to the handler using the unauthenticated `request.shop` and `request.topic` as the tenant/topic identity: [4](#0-3) 

This mirrors the report's bug class exactly: a field that is *acted on* (the `shop` value used for tenant routing/authorization inside the handler) is not *covered by the HMAC* that supposedly authenticates the message. The equality that should hold — `hmac_signed_bytes == bytes_the_handler_trusts_for_tenant_identity` — is broken: the signature only binds the body; it says nothing about which shop, topic, or webhook the body belongs to.

Because `Context.api_secret_key` is a single app-level secret shared across every shop that installs the app (not a per-shop secret), any merchant who has installed the app can obtain genuinely-signed webhook deliveries for their own shop (e.g., by editing their own store data to trigger a webhook with attacker-chosen body content) and then replay that HTTP request to the app's webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header changed to point at a different shop. `HmacValidator.validate` still succeeds because the signature only ever checked `@raw_body`, and `Registry.process` will hand the attacker-controlled body to the handler tagged with the victim shop's domain.

### Impact Explanation
This is a cross-tenant identity-binding break: the app's webhook handlers (which typically use `WebhookMetadata#shop` to look up the corresponding merchant session/access token and act on that merchant's data) can be made to process attacker-supplied body content under a different shop's identity. Depending on what the host app's handler does with `shop` (e.g., `customers/redact`, `shop/redact`, order/product sync), this can lead to cross-tenant data corruption or actions taken against a shop that never sent the corresponding data — meeting the High-severity "cross-tenant access" bar via a broken identity binding, achieved without any credential, token, or privileged access.

### Likelihood Explanation
Exploitation requires only: (1) being a legitimate but unprivileged merchant who has installed the target app (a normal, low-privilege state, not requiring `api_secret_key` or any stolen token), and (2) the ability to replay/modify an HTTP header on a request the attacker's own store legitimately triggered. No secret material needs to be recovered — the attacker simply reuses a validly-signed body/signature pair obtained through their own tenant and relabels it. This is a realistic, low-effort attack path within the gem's own webhook processing code.

### Recommendation
Bind the trusted identity fields into the signed payload verification, e.g., include `shop`, `topic`, and `webhook_id`/`api_version` in the value that `to_signable_string` returns (or otherwise cryptographically bind them to the body before computing/verifying the HMAC), so that `HmacValidator.validate` fails if any of those header values are altered relative to what Shopify actually signed for that specific shop and topic.

### Proof of Concept
1. App merchant A installs the app and triggers a webhook (e.g., updates a product) causing Shopify to POST a legitimately HMAC-signed webhook to the app's endpoint with body `B` and headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: H(secret, B)`.
2. Attacker (merchant A) intercepts/replays this exact request to the app endpoint but rewrites `x-shopify-shop-domain` to `shop-victim.myshopify.com` (and/or a different `x-shopify-topic`), keeping body `B` and the original `x-shopify-hmac-sha256` unchanged.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares against the header value — it matches because the signature never covered the shop/topic headers: `lib/shopify_api/webhooks/request.rb` lines 35-38, `lib/shopify_api/utils/hmac_validator.rb` lines 12-22.
4. The handler in the host app receives `WebhookMetadata` with `shop: "shop-victim.myshopify.com"` and body `B` (`lib/shopify_api/webhooks/registry.rb` lines 198-199), processing attacker-controlled data as if it originated from `shop-victim`.
