## Analysis

The relevant equality this question challenges is: **tokens leaving `ExternalActionSwap`/`LifiExternalAction` in a transaction == `-deltaAmountChanges` that Hinkal sent to it that same transaction.** Tracing the code shows this equality is *not* enforced for the ERC-20 leg of a LiFi swap.

### Root cause

In `LifiExternalAction.callRouter` [1](#0-0) , the `inputAmount` parameter (equal to `-deltaAmounts[0]`, i.e. exactly what Hinkal transferred to the action this transaction) is **only used for the native-ETH branch** as `msg.value`. For the ERC-20 branch, the function calls `approveUnlimited(inputToken, router)` and then blindly executes `router.call(externalActionMetadata)` — a fully attacker-supplied calldata blob. `swappedAmount` is computed purely as the *output*-token balance delta (`getERC20OrETHBalance(outputToken) - balanceBefore`); nothing checks that the router actually consumed only `inputAmount` of `inputToken`.

`approveUnlimited` in `TransfererBase.sol` [2](#0-1)  leaves a standing max allowance from the action contract to the router once granted, persisting across transactions.

`ExternalActionSwap.swap` then unconditionally forwards the *entire* `swappedAmount` (minus fees) to `msg.sender` (Hinkal) as the caller's new UTXO output: [3](#0-2) .

### Why nothing catches this

- `Hinkal.transact`'s balance-diff check only verifies **Hinkal's own** balances against `amountChanges`/`utxoAmount`; it is self-consistent with whatever the external action reports and does not look at the action contract's internal token accounting [4](#0-3) .
- `_externalTransact` only transfers `-deltaAmountChanges[i]` (the caller's own declared input) to the action *before* calling `runAction`; it never checks what balance existed in/leaves the action afterward [5](#0-4) .
- `calldataHash`/`getHashedCalldata` only bind the raw bytes of `externalActionMetadata` to the signed proof so it can't be swapped after signing; they do not constrain the *semantic* amount encoded inside that calldata to equal `inputAmount` [6](#0-5) [7](#0-6) .
- `dimensionsCheck`/`checkOnchainCreation` validate array shapes and onchain-creation flags only, not router calldata semantics [8](#0-7) .

So an attacker who observes/creates any residual `inputToken` balance sitting in `LifiExternalAction` (e.g. dust left by a prior swap whose router calldata under-consumed the transferred amount, since nothing forces the router calldata to consume the full `inputAmount` either) can submit their own tiny genuine swap whose `externalActionMetadata` instructs the router to pull the full current balance (their own `inputAmount` plus the stranded residual) via the pre-existing unlimited allowance, and collect the resulting larger `swappedAmount` entirely as their own output UTXO.

### #### Title
Unbounded router calldata combined with `approveUnlimited` lets an attacker sweep stranded token balance in `ExternalActionSwap`/`LifiExternalAction` into their own swap output - (File: contracts/external-actions/swaps/LifiExternalAction.sol)

### Summary
`LifiExternalAction.callRouter` never ties the amount of `inputToken` actually consumed by the router to the `inputAmount` (`-deltaAmounts[0]`) that Hinkal transferred in for this transaction; it only measures the resulting `outputToken` delta. Combined with the standing unlimited router allowance from `approveUnlimited`, any residual `inputToken` balance parked in the action contract (from a prior under-consuming swap or otherwise) can be pulled by an attacker's own crafted router calldata and folded into the attacker's `amountToSendToHinkal`, which is minted entirely as the attacker's UTXO.

### Finding Description
The invariant "value leaving the action this tx == `-deltaAmountChanges` sent to it this tx" is broken because `swap()`/`callRouter()` in `ExternalActionSwap.sol`/`LifiExternalAction.sol` derive the claimed output solely from the output-token balance delta, with the router calldata (`externalActionMetadata`) being entirely attacker-controlled and unconstrained as to how much `inputToken` it pulls via the pre-approved unlimited allowance [1](#0-0) . An attacker deposits a minimal amount of `inputToken`, generates a valid proof/UTXO for that small amount, and supplies `externalActionMetadata` whose router call actually consumes `inputAmount + residualBalance` of `inputToken` already sitting in the contract (from `approveUnlimited`'s standing approval to the router). The resulting `swappedAmount` includes value attributable to the stranded residual, and `ExternalActionSwap.swap` sends the whole `amountToSendToHinkal` to `msg.sender` (Hinkal), which mints it as the attacker's new UTXO [9](#0-8) . Hinkal's top-level balance-diff check only verifies Hinkal's own ledger self-consistently against whatever the action reports and cannot detect that the action's *internal* input/output balances no longer match `-deltaAmountChanges` [10](#0-9) .

### Impact Explanation
Any stranded/parked token value sitting in `LifiExternalAction` — belonging to the protocol or to a prior user whose swap calldata under-consumed the input amount — can be directly stolen by any subsequent unprivileged caller of the swap action, minted as their own shielded UTXO. This matches "Critical: direct theft of shielded or in-flight user funds," and is repeatable each time residual balance accumulates in the action contract.

### Likelihood Explanation
Preconditions: some non-zero `inputToken` balance already sitting in the action contract (achievable either by a prior swap whose router calldata consumed less than the full approved/transferred `inputAmount`, since nothing enforces full consumption either, or simply by anyone transferring tokens directly to the contract). The attacker needs only their own valid deposit/UTXO and full control over `externalActionMetadata` (a normal capability of any Hinkal user performing a swap). No privileged role is required, and the attack is directly reachable through `Hinkal.transact` → `_externalTransact` → `LifiExternalAction.runAction`/`swap`.

### Recommendation
Enforce that the router consumes exactly `inputAmount` of `inputToken`: measure `inputToken` balance before/after the router call and require the decrease equals `inputAmount` (mirroring the `balanceChange` accounting pattern already used in `EmporiumUpgradeable.handleOut`), or use `safeApprove`/`forceApprove` scoped exactly to `inputAmount` per call instead of `approveUnlimited`, revoking/resetting after use so no standing allowance beyond the current transaction's input persists.

### Proof of Concept
Foundry test plan:
1. Deploy `LifiExternalAction` with a mock router that, given arbitrary calldata, transfers a caller-specified `amountIn` of `inputToken` from itself (via `transferFrom`) and pays out a proportional `outputToken` amount.
2. Simulate a first, legitimate transaction that leaves a residual `inputToken` balance in `LifiExternalAction` (e.g., router calldata that intentionally consumes less than the transferred `inputAmount`), confirming `approveUnlimited` has granted the router max allowance.
3. As the attacker, call `Hinkal.transact` with a minimal genuine deposit/UTXO (`inputAmount` small) but with `externalActionMetadata` instructing the mock router to pull `inputAmount + residualBalance`.
4. Assert: attacker's resulting UTXO (`amountToSendToHinkal`) is strictly greater than what corresponds to their own `-deltaAmountChanges[0]` times the expected exchange rate — i.e., assert `swappedAmount > f(inputAmount)` and that `residualBalance` after the tx is zero, proving the stranded value left the action attributed entirely to the attacker's output.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
