### Title
Signup `distributorId` (and `reason`) fields are excluded from the cryptographic signature, allowing misattributed signup credit - ([File: src/plans/enroll_user.rs])

### Summary
The orb-core signup flow computes a cryptographic signature over only a subset of the fields sent to the backend in the `/api/v2/signups/{signup_id}` request. The `distributorId` (`operator_qr_code.user_id`) and `reason` fields are transmitted in the same multipart form but are never included in the signed digest, so the backend has no cryptographic guarantee that these values match what was actually captured/authorized during the signup session, mirroring the reported "parameter not covered by signature" bug class.

### Finding Description
`make_signature` builds the SHA-256 digest that is signed by the secure element and sent as the `signature` form field. It only hashes `ORB_ID`, `user_qr_code.user_id`, and the iris code/mask/version data from the pipeline: [1](#0-0) 

However, `signup_post::request` builds the actual HTTP form sent to the backend, and it includes `distributorId` (from `operator_qr_code.user_id`) and `reason` (the `SignupReason`) as separate, unsigned form fields alongside the signature: [2](#0-1) 

Because `distributorId` and `reason` never enter the signed digest, the signature validates identically regardless of what value is placed in those two fields. This is the direct structural analog of the reported issue: a parameter that is transmitted alongside a signed payload but not covered by that signature, so it can be altered independently without invalidating the accompanying cryptographic proof.

### Impact Explanation
`distributorId` is used by the backend to attribute a completed signup to a specific operator/distributor (visible in the debug report as well, via `operator_qr_code.user_id`): [3](#0-2) 

If this field can be changed between signing and transmission (e.g., a compromised in-process component, a modified/rooted orb build, or any actor positioned to modify the outgoing multipart request before it leaves the device) without breaking the biometric signature, a signup that was legitimately captured under one operator/distributor could be credited or reported to a different one. This is a cross-signup misattribution: the biometric proof stays valid, but the business-record attribution ("who ran this signup") is forgeable, matching the accepted "misattributed signup" impact category.

### Likelihood Explanation
Exploitation requires the ability to modify the outgoing HTTP form on the orb device after signing but before/at network transmission — this is a lower-likelihood, higher-trust-boundary scenario than a fully remote attacker, since it depends on tampering within the orb's own request pipeline rather than a public entry point. Nonetheless, the root cause (a value sent unsigned alongside a signature meant to attest integrity of the signup) is a genuine design gap, consistent with the reported bug class of "signature doesn't cover a parameter that materially changes accounting/attribution."

### Recommendation
Include `distributorId` (`operator_qr_code.user_id`) and `reason` in the signed digest computed by `make_signature`, so that any request whose form fields don't match what was actually authorized/captured fails signature verification on the backend. This closes the gap where a value can be substituted without invalidating the accompanying cryptographic signature.

### Proof of Concept
1. Orb completes a signup under operator A, computing `signature` via `make_signature` (which never references `operator_qr_code.user_id`).
2. Before the multipart form is sent (or if the form is reconstructed/replayed with the same `signature` value), `distributorId` is swapped to operator B's `user_id`.
3. The backend validates `signature`, which is still valid because it was never computed over `distributorId`, and records the signup as attributed to operator B instead of A. [1](#0-0) [2](#0-1)

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
