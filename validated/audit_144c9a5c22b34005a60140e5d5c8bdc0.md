### Title
`transferCreator` is a single-step ownership change with no two-step confirmation, risking permanent freezing of creator fee attribution - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.transferCreator()` reassigns the `creator` role for a launched token in a single transaction, with no acceptance step from the new address. A mistaken address (typo, wrong checksum, or an address whose private key isn't controlled by the intended party) permanently and irrecoverably redirects all future creator fee attribution, exactly the bug class described in the `changeDAO` finding.

### Finding Description
`transferCreator` sets `info.creator = newCreator` immediately, gated only by `msg.sender != info.creator`: [1](#0-0) 

Once this call executes, only the address in `info.creator` can call `transferCreator` again (`if (msg.sender != info.creator) revert NotCreator();`). If `newCreator` is an incorrect or inaccessible address, the original creator has no way to reverse the change, and no third party (not even the protocol) has a path to correct it — `Bonding` has no admin override for `tokenInfo.creator`.

This is the same root cause as the external `changeDAO` report: a privileged role transfer performed as a single atomic write, requiring the *new* address to be the one that signs any future correction, with no proposal/accept flow and no timelock. Notably, the codebase's own `FeeVault` deliberately avoids this exact pattern for its `owner` role by using `Ownable2StepUpgradeable`, with an explicit comment acknowledging the risk: [2](#0-1) 

`transferCreator` was not given the same two-step protection.

### Impact Explanation
`info.creator` is the sole attribution key used by `FeeVault.accrue()` to credit ongoing trading-fee revenue: [3](#0-2) 

and by `FeeVault.claim()` to pay out that balance to `msg.sender`: [4](#0-3) 

If `transferCreator` is called with a mistaken address, every subsequent 0.25% creator-side fee from every future buy/sell on that token (pre- and post-graduation) accrues to `creatorBalance[wrongAddress]` in `FeeVault` and becomes permanently unclaimable by the rightful creator — a permanent freeze of creator funds with no recovery path on-chain.

### Likelihood Explanation
Low-to-moderate: this requires a creator (or whoever operates `transferCreator`) to mis-enter an address, the same "extremely low probability" scenario the original judges accepted as the residual risk for `changeDAO`. It is not attacker-triggerable against a victim's will (creator must self-inflict), which mirrors the original finding's accepted severity discussion.

### Recommendation
Convert `transferCreator` into a two-step propose/accept flow analogous to `Ownable2StepUpgradeable` already used in `FeeVault`: the current creator calls a `proposeCreator(token, newCreator)` that stores a pending address, and the new address must call `acceptCreator(token)` (from `newCreator`) to finalize the role change. This allows the original creator to correct a mistaken proposal before it takes effect, and guarantees the new address controls its own private key.

### Proof of Concept
1. Creator `C` launches a token via `Bonding` and accrues creator fees through normal `Zap.buy`/`sell` activity, crediting `FeeVault.creatorBalance[C]`.
2. `C` calls `bonding.transferCreator(tokenAddr, wrongAddress)` where `wrongAddress` is a typo'd or otherwise inaccessible address. [1](#0-0) 
3. All subsequent `FeeVault.accrue()` calls for `tokenAddr` now credit `creatorBalance[wrongAddress]` instead of `C`.
4. `C` attempts to call `transferCreator` again to fix the mistake but reverts with `NotCreator` since `msg.sender` (`C`) no longer equals `info.creator` (`wrongAddress`).
5. All future and already-accrued creator fees for `tokenAddr` are permanently stranded in `FeeVault`, unclaimable by anyone with real control, matching the `changeDAO` bug class exactly.

```text
    function transferCreator(
        address tokenAddress,
        address newCreator
    ) external {
        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
    }
```

```text
    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }
```

```text
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
```
