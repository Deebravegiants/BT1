## Analysis

The report's bug class ("bytes verified versus bytes parsed" / missing length or scope validation before trusting external data) maps to a concrete identity-binding gap in this gem's webhook processing path. [1](#0-0) 

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#hmac` returns the decoded `hmac-sha256` header. The `shop` accessor, however, simply returns the raw `shopify-shop-domain` header value, completely independent of the signed payload:

```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end

def shop
  T.cast(shopify_header("shop-domain"), String)
end

def to_signable_string
  @raw_body
end
``` [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the raw body only) and compares it against the `hmac` header — it never incorporates `shop`, `topic`, `webhook_id`, or `api_version`: [3](#0-2) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts `request.shop` (along with `request.topic`, `request.webhook_id`, etc., none of which are HMAC-covered) to build the `WebhookMetadata` handed to the host app's handler:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the HMAC signature exclusively over the raw request body (`to_signable_string` returns `@raw_body` only). The `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers and are never included in the signed content, yet `Registry.process` passes `request.shop` straight through to the host application's webhook handler as the tenant identifier after HMAC validation succeeds.

### Finding Description
The binding the gem is supposed to guarantee is: *"the shop whose HMAC-covered payload was verified" == "the shop attributed to the webhook event handed to the app."* Because `to_signable_string` only returns `@raw_body`, and `HmacValidator.validate_signature` computes/compares the HMAC solely against that string, the `shop-domain` header is entirely outside the cryptographic guarantee. An attacker who possesses one valid, previously-delivered `(raw_body, hmac)` pair — trivial to obtain since anyone can install an app on their own development/test store and receive genuinely signed webhooks for it — can replay that exact body and HMAC while substituting an arbitrary `x-shopify-shop-domain` / `shopify-shop-domain` header value. `Utils::HmacValidator.validate` will still return `true` because the signature check never touches the shop header, and `Registry.process` will forward the attacker-chosen `shop` value to the app's handler via `WebhookMetadata`.

### Impact Explanation
Any host application built on this gem that uses `WebhookMetadata#shop` to select which merchant's session/access-token/data the webhook payload applies to (the intended and documented use of this field) can be tricked into associating one tenant's webhook body with another tenant's shop identity. This is a cross-tenant identity-binding break: verified bytes (the body) are trusted, but the tenant label attached to those bytes is not verified at all.

### Likelihood Explanation
Exploitation requires only a single legitimately-signed webhook (obtainable from any shop the attacker controls, including a free development store) and the ability to send an arbitrary HTTP request with forged headers to the app's public webhook endpoint — both trivially available to an unprivileged internet user with no access token, secret, or privileged account needed.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signed/verified material (e.g., bind them into `to_signable_string`, or independently verify `shop` against session state established via OAuth for that specific webhook subscription) so that HMAC validation authenticates the full identity tuple, not just the JSON body bytes.

### Proof of Concept
1. Install the target app on an attacker-controlled development store; capture a genuine webhook delivery — raw body `B` and header `shopify-hmac-sha256: H` (valid because `H = HMAC(secret, B)`).
2. Replay a request to the app's webhook endpoint with the same body `B` and header `H`, but set `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac` still decodes to `H`; `HmacValidator.validate` still succeeds because it only hashes `B`.
4. `Registry.process` invokes the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-supplied data under the victim shop's identity.
