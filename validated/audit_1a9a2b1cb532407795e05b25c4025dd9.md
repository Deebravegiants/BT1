### Title
Webhook `shop` (and `topic`/`webhook-id`) identity is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` (tenant identity) delivered to the handler is read from an unauthenticated HTTP header. This breaks the equality "shop authenticated == shop used as the tenant/session key", allowing a merchant who has installed the app to replay a legitimately-signed webhook body under a different shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [5](#0-4) , and `HmacValidator.validate` computes/compares the HMAC exclusively over this signable string [6](#0-5) . The `shop`, `topic`, and `webhook_id` values, however, are all read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) that are never included in the signed content [7](#0-6) .

`Registry.process` trusts these header-derived values once the body HMAC passes, and forwards `request.shop` directly into `WebhookMetadata` given to the app's handler as the authoritative tenant identity [2](#0-1) . The documented handler contract explicitly instructs apps to key their business logic (job enqueueing, per-shop data updates, etc.) off `data.shop`, treating it as trusted [8](#0-7) .

Because Shopify webhook HMACs are computed with the app's single shared `client_secret` (not per-shop), any shop that has installed the app receives legitimately-signed webhook deliveries. An attacker who controls one such shop can capture a raw webhook body plus its valid `X-Shopify-Hmac-Sha256` header for their own shop, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to name a different, victim shop that also uses the app. `HmacValidator.validate` still succeeds (the body is unmodified and correctly signed), so `Registry.process` invokes the registered handler with `WebhookMetadata(shop: <victim-shop>, body: <attacker-controlled-but-signed body>, ...)`, impersonating a webhook event for the victim tenant.

### Impact Explanation
This crosses the tenant boundary this gem is meant to enforce: the value host applications use to select per-shop data/session context (`data.shop`) is attacker-controllable even though the request passes signature verification. Depending on how the host app uses `data.shop` (e.g., to fetch a stored session/access token for that shop, update per-shop records, or trigger downstream authenticated API calls), this can lead to cross-tenant data corruption or actions being performed against a shop the attacker does not control, satisfying the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires only that the attacker control (install the app on) one shop that is a legitimate tenant of the app — no access to `api_secret_key`, tokens, or any privileged account is needed. Capturing your own shop's webhook payload/HMAC and replaying it with a modified header is straightforward for any app that exposes webhook endpoints per the documented pattern in `docs/usage/webhooks.md`.

### Recommendation
Do not trust header-derived `shop`/`topic`/`webhook_id` as authenticated identity. At minimum, bind the shop to the signature by including it (and topic/webhook_id) in the signed payload verified by `HmacValidator`, or have `Registry.process` cross-check `request.shop` against an independently retrieved/authenticated per-shop record (e.g., verifying the shop is one that legitimately owns the specific `webhook_id`) before dispatching to the handler.

### Proof of Concept
1. Install the vulnerable app on attacker-controlled shop `evil.myshopify.com`; trigger a webhook (e.g. `orders/create`) so Shopify sends:
   - Headers: `X-Shopify-Shop-Domain: evil.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - Body: `{"id": 123, ...}` (attacker can also shape order/product content on their own shop to control this body)
2. Capture the raw body and the `X-Shopify-Hmac-Sha256` value exactly as sent.
3. Replay a POST to the same app webhook endpoint with the identical raw body and `X-Shopify-Hmac-Sha256` header, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (a real installed victim shop).
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only checks the (unmodified) body against the shared secret [9](#0-8) .
5. `Registry.process` dispatches to the handler with `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker's data>, ...)` [10](#0-9) , causing the host app to act on the victim tenant using attacker-supplied webhook content.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
