### Title
Cross-tenant webhook spoofing via `shop-domain` header not covered by HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, using the app's single, shop-independent `api_secret_key`. The `shop-domain` header — which the library exposes as `request.shop` and forwards to the host application's handler as the authoritative tenant identifier — is never included in the signed payload. This breaks the identity binding: `shop authenticated by HMAC != shop attributed to the event`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`request.shop` is read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header, independent of the body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (i.e. the body only) using the single app-wide `Context.api_secret_key` (falling back to `Context.old_api_secret_key`), and does not incorporate the shop header at all: [3](#0-2) 

`Registry.process` uses only this body-only HMAC check as the sole authentication gate, then immediately trusts `request.shop` (the unauthenticated header) and hands it to the app's handler as the tenant identity for the event: [4](#0-3) 

Because `api_secret_key` is the app's single client secret shared across every merchant that has installed the app (not a per-shop secret), any merchant who has installed the app receives real webhook deliveries from Shopify with a valid `body + hmac` pair for events on their own store. That merchant can replay the exact same `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still succeed (it never looks at the header), and `Registry.process` will invoke the registered handler with `WebhookMetadata` whose `shop` field is the attacker-chosen victim domain, e.g.: [5](#0-4) 

If the host application uses `data.shop` (as documented/expected — see tests asserting `data.shop == @shop`) as a lookup/session key to load per-tenant records, credentials, or perform side effects, this allows a malicious/low-privileged tenant to inject events attributed to a different tenant, i.e. cross-tenant confusion driven purely by an unauthenticated header value.

### Impact Explanation
This crosses the tenant boundary defined by the Rules ("a shop authenticated versus the shop stored as a session key" / "a field acted on but not covered by the HMAC"). Depending on how the consuming application keys its per-shop data/state off `WebhookMetadata#shop`, this enables cross-tenant data corruption, spoofed lifecycle events (e.g. fake `app/uninstalled`, `shop/redact`, order/customer events) attributed to a victim shop, or triggering of privileged per-shop side effects for a shop the attacker does not control. This qualifies as "Critical – cross-tenant access" per the Rules' impact bar, since the identity binding the app relies on (webhook shop = authenticated shop) is broken entirely within the gem's own webhook-processing code path.

### Likelihood Explanation
Any actor who can install the target app on their own store (a normal, unprivileged onboarding flow, no special access needed) can capture a legitimate webhook delivery (body + HMAC) for their own shop, then replay it with a forged `shop-domain` header at the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only the ability to receive one real webhook for their own store, which is inherent to installing any Shopify app. Likelihood is high for any multi-tenant app relying on `WebhookMetadata#shop` from this gem.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook-id`) header into the signed data used for HMAC verification, or independently verify that `request.shop` corresponds to a shop with an active, known installation/session before dispatching the event to handlers. At minimum, `Registry.process` should not treat `request.shop` as trusted tenant identity without cross-checking it against the shop implied by an installed/offline session, since the HMAC in `HmacValidator` only proves knowledge of the app-wide secret, not the origin shop.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged installation).
2. Shopify sends a legitimate webhook to the app, e.g. body `{"id":1}}`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body under the app's api_secret_key>`.
3. Attacker replays the identical body and HMAC to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(raw_body, api_secret_key)`, unaffected by the header change: [6](#0-5) 
5. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop == "victim-shop.myshopify.com"`: [5](#0-4) 
6. The host application's handler processes the event as if it originated from `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
