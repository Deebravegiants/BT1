### Title
Opaque swap routes can smuggle an attacker-chosen token transfer into the caller’s signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`StrategySwap` is an opaque `Bytes` payload supplied through `multiply`, `swap_debt`, `swap_collateral`, or `repay_debt_with_collateral`. [1](#0-0) [2](#0-1)  The controller passes this payload to the configured router while the caller’s authorization covers the invocation, then validates only controller input/output balance deltas rather than constraining contracts invoked by the route. [3](#0-2)  Consequently, code reached through a malicious route can add an unrelated token transfer to the victim’s authorization tree and execute it if the victim signs that poisoned tree. [4](#0-3) 

### Finding Description
The affected entrypoints authenticate `caller`, bind the operation to an owned or delegated account, and forward the caller-supplied route bytes into the swap flow. [5](#0-4) [6](#0-5)  `swap_tokens` authorizes only the controller’s exact input-token transfer to the configured router, but the opaque `swap` payload is then executed inside the caller-authorized transaction. [7](#0-6)  Its post-execution checks measure only the controller’s `token_in` decrease and `token_out` increase, so they do not detect additional calls that spend unrelated assets belonging to the caller. [8](#0-7) 

This is analogous to the smuggled proxy header: an externally supplied opaque control payload selects code that can alter the security context of the enclosing operation. A route-reached contract can request `token.transfer(victim, attacker, amount)`; Soroban records that request beneath the victim’s controller authorization, and a signature over the returned tree authorizes it. [9](#0-8) 

### Impact Explanation
A malicious frontend or quote can cause theft of unrelated wallet assets while still delivering a valid-looking swap result and leaving the lending account solvent. [8](#0-7) [10](#0-9)  The exploit is not limited to the collateral amount routed through the lending operation because the injected authorization request can target a different token and a different recipient. [11](#0-10) 

### Likelihood Explanation
An unprivileged attacker can deploy the malicious route component and distribute the encoded route, while the victim must sign an authorization tree containing the unexpected child invocation. [12](#0-11) [13](#0-12)  Wallets or clients that fully decode and prominently display every authorization child can prevent the theft, but the route itself remains opaque to users and the transaction can otherwise appear economically normal. [1](#0-0) [10](#0-9) 

### Recommendation
Do not execute attacker-controlled opaque routes beneath an account owner’s authorization without constraining the contracts they can invoke. [7](#0-6)  Replace or wrap the opaque route with a structured representation whose venues and pool addresses are validated against an allowlist before invocation, and reject any route capable of introducing calls outside the expected swap path. Clients should also simulate every strategy transaction, display the complete authorization tree, and reject unexpected child invocations rather than relying on final swap output or account solvency checks. [8](#0-7) [14](#0-13) 

### Proof of Concept
1. The victim holds collateral in a lending account and also holds an unrelated wallet token. [15](#0-14) 
2. The attacker deploys route-reachable code that calls `token.transfer(victim, attacker, wallet_balance)` during the swap. [16](#0-15) 
3. The attacker supplies a route naming that code through the `swap` argument to `swap_collateral`. [17](#0-16) [18](#0-17) 
4. Simulation records the unrelated transfer as a child of the victim’s `swap_collateral` authorization, and signing that tree drains the wallet token while crediting the expected swap collateral. [19](#0-18) 
5. If the victim signs only the honest tree, the unauthorized transfer is rejected and the operation rolls back, confirming that exploitation requires the poisoned signed tree. [14](#0-13)
