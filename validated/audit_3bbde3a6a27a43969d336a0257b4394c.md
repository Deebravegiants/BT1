### Title
Blacklisted creator's accrued USDC fees are permanently frozen in `FeeVault` with no recovery path - ([File: packages/contracts/src/FeeVault.sol])

### Summary
`FeeVault.claim()` pays out a creator's pooled USDC balance exclusively to `msg.sender`, and `Bonding.transferCreator` only redirects *future* fee attribution, not the already-accrued `creatorBalance`. If USDC blocklists the creator's address (e.g. an OFAC/compliance action, which is explicitly the blacklist scenario the external report is about), that creator's outstanding `creatorBalance[creator]` becomes permanently unclaimable — there is no alternate recipient, admin sweep, or reassignment path for it.

### Finding Description
`FeeVault.accrue` credits `creatorBalance[creator]` in USDC on every buy/sell routed through `Zap`, per `packages/contracts/src/FeeVault.sol:101-123`. The only way to withdraw this balance is:

```solidity
function claim() external nonReentrant returns (uint256 amount) {
    FeeVaultStorage storage $ = _s();
    amount = $.creatorBalance[msg.sender];
    if (amount == 0) revert NothingToClaim();
    $.creatorBalance[msg.sender] = 0;
    $.totalAccruedCreator -= amount;
    $.usdc.safeTransfer(msg.sender, amount);
    emit CreatorFeesClaimed(msg.sender, amount);
}
``` [1](#0-0) 

`claim()` always transfers to `msg.sender` — it has no `to` parameter and no owner-assisted redirect. `IERC20.safeTransfer(msg.sender, amount)` reverts unconditionally if USDC's issuer has blocklisted that specific address, per the same blacklisting mechanism the external report analyzes (a transfer to/from a blocklisted address always reverts).

The mitigation that exists — `Bonding.transferCreator` — only rewires *future* attribution, not the funds already sitting in `creatorBalance`:
```solidity
function transferCreator(address tokenAddress, address newCreator) external {
    if (newCreator == address(0)) revert ZeroAddress();
    TokenInfo storage info = _s().tokenInfo[tokenAddress];
    if (msg.sender != info.creator) revert NotCreator();
    if (newCreator == info.creator) revert InvalidInput();
    info.creator = newCreator;
    emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
}
``` [2](#0-1) 

Because `transferCreator` lives on `Bonding` (which has no knowledge of `FeeVault.creatorBalance`) and `FeeVault.accrue` keys strictly off the `creator` argument passed in at call time [3](#0-2) , calling `transferCreator` after being blocklisted only redirects fees accrued *after* the switch. Anything already pooled under the old (now-blocklisted) creator address stays permanently stuck: `claim()` will always attempt `safeTransfer(msg.sender, amount)` to the blocklisted address and revert, and there is no owner function, sweep, or alternate-recipient path in `FeeVault` to move a specific creator's `creatorBalance` elsewhere. `claimProtocol()` and `sweepDonations()` only touch `protocolBalance` / unbacked surplus, never a creator's own balance [4](#0-3) .

### Impact Explanation
This is a permanent freeze of creator funds: the accrued creator-fee share of every buy/sell on the affected token(s) up to the moment of blocklisting becomes permanently unrecoverable. Since the fee flow runs on every trade (0.25% creator cut, per `docs/contracts-scope.md:112-121`), this can represent a nontrivial, ever-growing balance for popular tokens before the creator notices the block and switches attribution — and the balance accrued *before* the switch can never be retrieved by anyone. Unlike the C4 report's auction/liquidation case, this does not brick a shared process for other users, but it satisfies the accepted impact criterion of "permanent freezing of ... creator ... funds."

### Likelihood Explanation
Requires the specific precondition that a creator's address gets added to USDC's blocklist while they have an unclaimed balance — an out-of-protocol event (compliance/sanctions action), but one the underlying asset (real USDC) explicitly supports and that this same contest's own README/AGENTS docs treat blocklisting as in-scope. Given `FeeVault` is a core, permissionless, unprivileged-reachable contract (`claim()` is called directly by any creator) and the freeze is unconditional and irreversible once triggered, likelihood is that of any USDC-blocklist-class issue: low-frequency but concrete and unmitigated when it occurs.

### Recommendation
Add either:
1. A `claimTo(address to)` variant (self-authorized only) so a creator anticipating/discovering a block can redirect payout before/at claim time, or
2. An owner-gated `rescueCreatorBalance(address creator, address to)` that can only move a specific creator's stuck balance to an address of that creator's choosing (e.g. authenticated off-chain via signature) after a timelock, keeping `totalAccruedCreator` accounting consistent, or
3. At minimum, wrap `claim()`'s transfer in a try/catch that, on failure, leaves the balance flagged as "claim failed" and emits an event, and expose a `claimFor(address creator, address to)` signed-message path so the creator can nominate an alternate receiving address without needing the blocklisted address to be capable of receiving.

### Proof of Concept
1. `Zap.buy`/`Zap.sell` on a token accrues creator fees via `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)` — `creatorBalance[creator]` grows over many trades [3](#0-2) .
2. Real-world USDC blocklists `creator`'s address (out-of-protocol compliance action).
3. `creator` calls `Bonding.transferCreator(token, newCreator)` to redirect *future* fees — this succeeds but does not touch the already-accrued `creatorBalance[creator]` in `FeeVault` [2](#0-1) .
4. `creator` (or anyone acting for them) calls `FeeVault.claim()`. `$.usdc.safeTransfer(msg.sender, amount)` reverts because USDC's own `_beforeTokenTransfer`/blocklist check rejects transfers to a blocklisted `to` address [1](#0-0) .
5. There is no other function in `FeeVault` capable of moving `creatorBalance[creator]` to any other address — the balance is permanently stuck.

    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }

    function claimProtocol() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.protocolBalance;
        if (amount == 0) revert NothingToClaim();
        $.protocolBalance = 0;
        address feeTo_ = $.feeTo;
        $.usdc.safeTransfer(feeTo_, amount);
        emit ProtocolFeesClaimed(feeTo_, amount);
    }

    /// @notice Sweep unbacked USDC (donations) to `feeTo`. Required because
    ///         direct USDC transfers would otherwise inflate `balanceOf` above
    ///         the accrual tally and silently mask the `accrue` underfund
    ///         check. Permissionless — funds always go to the admin-set `feeTo`.
    function sweepDonations() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        uint256 backed = $.totalAccruedCreator + $.protocolBalance;
        uint256 balance = $.usdc.balanceOf(address(this));
        if (balance <= backed) revert NothingToClaim();
        amount = balance - backed;
        address feeTo_ = $.feeTo;
        $.usdc.safeTransfer(feeTo_, amount);
        emit DonationsSwept(feeTo_, amount);
    }
