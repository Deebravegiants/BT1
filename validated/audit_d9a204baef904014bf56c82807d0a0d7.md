Audit Report

## Title
Pipeline run resumption does not verify the target task run is still pending, allowing an already-finished task result to be overwritten and the run to be re-processed - (File: core/services/pipeline/orm.go)

## Summary
`UpdateTaskRunResult` in `core/services/pipeline/orm.go` gates its `UPDATE pipeline_task_runs` statement only on the parent `pipeline_runs.state` being `running` or `suspended`, without checking whether the specific `pipeline_task_runs` row (`finished_at IS NULL`) is still pending. This lets a replayed or duplicate call to the Resume endpoint overwrite an already-completed task's `output`/`error` and, if the run had transitioned to `suspended`, force the pipeline back into `RunStatusRunning` and re-execute downstream tasks with attacker/replay-controlled data.

## Finding Description
`PipelineRunsController.Resume` accepts a caller-supplied JSON body keyed only by the `taskID` UUID parsed from the URL and forwards it unmodified to `App.ResumeJobV2` → `runner.ResumeRun`: [1](#0-0) 

`ResumeRun` calls the ORM to persist the result and conditionally restarts the pipeline: [2](#0-1) 

The ORM update verified in the current codebase confirms the claim exactly: the `SELECT ... FOR UPDATE` only filters on `pipeline_runs.state in ('running', 'suspended')`, and the subsequent `UPDATE pipeline_task_runs SET output = $2, error = $3, finished_at = $4 WHERE id = $1` has no `finished_at IS NULL` guard: [3](#0-2) 

By contrast, `StoreRun`'s restart-detection loop explicitly checks `tr.IsPending()` before treating a task as eligible for state transition, showing the codebase elsewhere applies the narrower per-task check that is missing here: [4](#0-3) 

The handler logs this action under `audit.UnauthedRunResumed`, confirming this is intentionally reachable without full session/user authentication and is secured solely by possession of the `taskID`: [5](#0-4) 

This matches the described bug class: the coarse-grained parent state (`pipeline_runs.state`) is validated, but the fine-grained sub-item state (whether this specific task row already finished) is never checked before the mutating UPDATE is applied.

## Impact Explanation
A second/replayed resume request for a `taskID` whose task has already completed (but whose parent run has since become `suspended` again due to a later task) can overwrite the finished task's `output`/`error` and re-trigger `RunStatusRunning`, causing the runner to re-execute downstream DAG nodes — including side-effecting tasks such as ETH transactions or external bridge calls — with different, attacker/replay-supplied input. This falls under the "unauthorized job run" impact category, since it allows re-processing of a pipeline run outside its intended single-completion semantics.

## Likelihood Explanation
The Resume endpoint is explicitly designed for asynchronous external adapters to post back results using only the `taskID` as a capability token (per the `UnauthedRunResumed` audit event), so no user session or API key is required to reach it. Exploitability requires knowledge of a `taskID` for a task whose result has already been recorded but whose parent run is still `suspended` (e.g. due to a later async task in the same run) — a plausible race in multi-async-task pipelines or via bridge retry/duplicate delivery, which is a common at-least-once delivery pattern for external adapters. The precise DB gating conditions were confirmed by direct inspection of `core/services/pipeline/orm.go`.

## Recommendation
Add `AND pipeline_task_runs.finished_at IS NULL` to the task-row lookup/update condition in `UpdateTaskRunResult` (or perform a `SELECT ... FOR UPDATE` on the specific task row and check `finished_at` before overwriting), returning a distinct "task already resolved" error instead of silently applying the update.

## Proof of Concept
1. Create a job pipeline containing two or more `Async: true` bridge tasks so the run transitions through multiple `suspended` states.
2. Let the first async task's adapter legitimately POST to `/v2/resume/:taskID1`, completing that task; the run remains `suspended` awaiting the second async task.
3. Replay a second POST to the same `/v2/resume/:taskID1` with a different `data`/`error` payload while the run is still `suspended`.
4. Observe that `UpdateTaskRunResult` (core/services/pipeline/orm.go:271-308) accepts the replay because it only checks `pipeline_runs.state in ('running','suspended')`, overwriting `taskID1`'s already-set `output`/`error`/`finished_at`, and (since `run.State == RunStatusSuspended`) transitions the run back to `RunStatusRunning`, causing `ResumeRun` to re-invoke `r.Run` and re-process the pipeline.

func (o *orm) UpdateTaskRunResult(ctx context.Context, taskID uuid.UUID, result Result) (run Run, start bool, err error) {
	if result.OutputDB().Valid && result.ErrorDB().Valid {
		panic("run result must specify either output or error, not both")
	}
	err = o.transact(ctx, func(tx *orm) error {
		sql := `
		SELECT pipeline_runs.*, pipeline_specs.dot_dag_source "pipeline_spec.dot_dag_source", job_pipeline_specs.job_id "job_id"
		FROM pipeline_runs
		JOIN pipeline_task_runs ON (pipeline_task_runs.pipeline_run_id = pipeline_runs.id)
		JOIN pipeline_specs ON (pipeline_specs.id = pipeline_runs.pipeline_spec_id)
		JOIN job_pipeline_specs ON (job_pipeline_specs.pipeline_spec_id = pipeline_specs.id)
		WHERE pipeline_task_runs.id = $1 AND pipeline_runs.state in ('running', 'suspended')
		FOR UPDATE`
		if err = tx.ds.GetContext(ctx, &run, sql, taskID); err != nil {
			return fmt.Errorf("failed to find pipeline run for task ID %s: %w", taskID.String(), err)
		}

		// Update the task with result
		sql = `UPDATE pipeline_task_runs SET output = $2, error = $3, finished_at = $4 WHERE id = $1`
		if _, err = tx.ds.ExecContext(ctx, sql, taskID, result.OutputDB(), result.ErrorDB(), time.Now()); err != nil {
			return fmt.Errorf("failed to update pipeline task run: %w", err)
		}

		if run.State == RunStatusSuspended {
			start = true
			run.State = RunStatusRunning

			sql = `UPDATE pipeline_runs SET state = $2 WHERE id = $1`
			if _, err = tx.ds.ExecContext(ctx, sql, run.ID, run.State); err != nil {
				return fmt.Errorf("failed to update pipeline run state: %w", err)
			}
		}

		return loadAssociations(ctx, tx.ds, []*Run{&run})
	})

	return run, start, err
}
