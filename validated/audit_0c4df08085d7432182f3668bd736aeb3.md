### Title
Webhook `shop` domain identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking that `X-Shopify-Hmac-SHA256` matches an HMAC computed over the raw request body. The `shop` domain (and `topic`/`webhook_id`) come from separate, unsigned headers that are never included in the signable string, then that unauthenticated `shop` value is handed directly to the app's handler as the tenant identity. This is the exact bug class described in the report: a field ("shop") is acted upon by downstream logic but is not covered by the HMAC that is meant to authenticate the request.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from an independent header and is never mixed into the signed material: [2](#0-1) 

`HmacValidator.validate` computes the signature exclusively from `verifiable_query.to_signable_string` (i.e. the body) and compares it with the received HMAC: [3](#0-2) 

`Registry.process` treats a passing HMAC check as sufficient authentication for the whole request, then forwards the unauthenticated `request.shop` straight into `WebhookMetadata`, which the app's handler uses as the tenant/shop identifier for all subsequent business logic: [4](#0-3) 

The identity binding that should hold is: `shop-domain header == shop authenticated by HMAC`. In reality: `shop-domain header != any value covered by HMAC` — the HMAC only proves "this body was signed with the client secret," not "this body belongs to this shop." Because a single `client_secret` is shared across every shop/tenant installing the app, anyone who can obtain one genuine `(body, hmac)` pair for their own shop — e.g., an ordinary developer/merchant who installs the app on a free/trial store and captures the request their own app-server implementation receives — can replay that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting the `shopify-shop-domain` header (and/or `shopify-topic`) with a victim shop's domain. `Registry.process` will accept it as valid (the HMAC still matches the untouched body) and dispatch it to the handler labeled as coming from the victim shop.

### Impact Explanation
This crosses a tenant boundary in a multi-tenant SaaS app built on this gem: an unprivileged party (any user who can install the app, even on a disposable dev store) can forge webhook events attributed to any other merchant using the app, because the library exposes an unauthenticated `shop` field as if it were verified. Depending on what the handler does with `data.shop` (e.g., writing to that shop's DB records, triggering per-shop side effects, updating that shop's state, resolving to that shop's stored access token for follow-up API calls), this enables cross-tenant data corruption or unauthorized actions performed under another merchant's identity — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires the attacker to be able to install the target app on at least one shop they control (commonly trivial - free trial/dev stores) in order to observe one legitimate `(body, hmac)` pair, and knowledge of the app's public webhook endpoint URL (which is unauthenticated by design and often discoverable/guessable, e.g. `/webhooks/<topic>`). No access to `client_secret`, tokens, or privileged accounts is required. This is a realistic scenario for any commercial multi-tenant Shopify app.

### Recommendation
Bind the shop identity to the authenticated payload rather than trusting the separate header:
- Where the webhook body itself contains a shop-identifying value (many Shopify webhook payloads include `myshopify_domain` or `id`/`domain` fields, and mandatory `shop/redact`, `customers/redact` payloads always do), cross-check the header-provided `shop` against a shop identifier embedded in the signed body before dispatching to the handler, and reject on mismatch.
- At minimum, document prominently in `docs/usage/webhooks.md` that `data.shop` is **not** cryptographically authenticated and that handlers must independently verify the shop is a known/installed tenant (e.g., look up a stored session/access token for that shop) before trusting the payload, since the HMAC check performed by `Registry.process` only proves body integrity, not sender/tenant identity.
- Consider exposing a stricter validation mode where `Request` requires the caller to supply the list of currently installed shops (or a session lookup callback) and refuses to build/process a request for an unrecognized shop.

### Proof of Concept
```ruby
# Attacker installs the multi-tenant app on their own (attacker-controlled) shop
# "attacker.myshopify.com" and captures one legitimate webhook their own
# app-server implementation receives, e.g. for topic "customers/create":

raw_body = '{"id":1,"email":"me@attacker.example"}'
hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_CLIENT_SECRET, raw_body)
)
# (the attacker doesn't know APP_CLIENT_SECRET, but Shopify sends this pair
#  to the attacker's own registered callback URL, so the attacker legitimately
#  observes a valid (raw_body, hmac) pair for their own tenant)

# Attacker now replays the exact same body+hmac to the app's public webhook
# endpoint, but swaps the shop-domain header to a victim shop:
forged_headers = {
  "x-shopify-topic"        => "customers/create",
  "x-shopify-hmac-sha256"  => hmac,               # unchanged, still valid for raw_body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com",  # forged
  "x-shopify-webhook-id"   => "forged-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds (only checks raw_body),
# handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# is invoked as if this event genuinely originated from victim-shop.
```
This demonstrates that `Registry.process`/`HmacValidator.validate` provide no binding between the HMAC and `shop`, allowing forged tenant attribution as long as the raw body itself was legitimately signed once by Shopify for any installation of the app.
