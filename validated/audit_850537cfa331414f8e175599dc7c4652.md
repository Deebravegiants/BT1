### Title
Webhook `shop` (and `topic`/`webhook_id`) attribution is not covered by the HMAC signature, allowing cross-tenant webhook forgery via header substitution - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` HTTP header to attribute the event to a tenant. Because the header is never part of the signed material, any party that possesses one valid `(raw_body, hmac)` pair signed with the app's shared secret can replay it with an arbitrary `shop-domain` header and have the library accept and dispatch it as if it originated from a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read directly from HTTP headers that are outside the HMAC's coverage: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` (and the other unauthenticated header values) to the application's webhook handler without any cross-check that the shop is the one the body/signature was actually generated for: [3](#0-2) 

The identity binding that should hold is: `shop attributed to the event == shop the HMAC was computed for`. Since the HMAC only signs `@raw_body` and the `shop-domain` header is attacker-controlled transport metadata, this equality is not enforced. A holder of any single legitimately-signed webhook body (e.g., from their own shop where they installed the app) can resend that exact body with a different `shopify-shop-domain` / `x-shopify-shop-domain` header value pointing at a victim shop. The HMAC check in `HmacValidator.validate` still passes because it only recomputes the signature over the body bytes: [4](#0-3) 

The handler then receives `WebhookMetadata` with the forged `shop`, `topic`, and `webhook_id`, and any host application that keys off `data.shop` to look up tenant records, apply data, or perform per-tenant side effects would apply the (attacker's) payload under the wrong tenant's identity.

### Impact Explanation
This breaks the tenant-attribution guarantee that consumers of this gem reasonably rely on: "if `Registry.process` didn't raise `InvalidWebhookError`, then `data.shop` is the shop that produced this payload." Any application that persists or acts on webhook data keyed by `data.shop` (nearly all multi-tenant Shopify apps do this, e.g., updating shop-scoped records, triggering shop-scoped billing/inventory actions, or invalidating/creating sessions for that shop) can be made to process one tenant's data under another tenant's identity — a cross-tenant access primitive achievable by any user who can install the app on at least one shop (including a free/dev store) and capture one webhook delivery.

### Likelihood Explanation
Any unprivileged actor able to install the app on a shop they control (a normal, unprivileged path — free developer stores are trivially obtainable) can capture a real webhook and its valid HMAC, since delivery bodies and signatures are visible to the receiving endpoint/app. Replaying that exact body with a substituted `shop-domain` header requires no secret material and no special privilege — only the ability to send an HTTP POST to the app's public webhook endpoint, which is unauthenticated by design (HMAC is the only defense). No `client_secret` or access token disclosure is needed.

### Recommendation
Bind the attributed shop cryptographically to the signed payload rather than trusting the header verbatim:
- Include the `shop-domain` (and ideally `topic`/`webhook_id`) header values in the string that is HMAC-verified, or
- Cross-verify `request.shop` against an independent trusted source (e.g., the shop associated with the session/access token used to register that specific webhook subscription) before dispatching to the handler, and
- Document/require host applications to treat the webhook `shop` value as authenticated only after such a bound check, or perform the check inside `Registry.process` itself so all consumers of the gem get the guarantee by default.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; attacker triggers any webhook event (e.g., `orders/create`) and captures the raw POST body `B` and the legitimate `X-Shopify-Hmac-Sha256` header `H` that Shopify sent (HMAC over `B` using the app's real secret).
2. Attacker resends the same request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body successfully; `Utils::HmacValidator.validate` recomputes the HMAC over `B` only and it matches `H`, so validation passes: [5](#0-4) 
4. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` and invokes the registered handler, which will act as though `victim-shop.myshopify.com` produced this payload — even though it never did.
