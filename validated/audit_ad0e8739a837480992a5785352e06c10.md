### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook is authentic by checking the HMAC over the raw request body only. The `shop` value that the verified webhook is attributed to (`request.shop`, exposed to app handlers as `WebhookMetadata#shop`) comes straight from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is never part of the signed content. This breaks the identity binding `hmac_signed_bytes == (shop, body)` down to `hmac_signed_bytes == body`, letting an attacker splice a valid `(body, hmac)` pair from one shop's webhook onto an arbitrary spoofed `shop` header.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read independently from a header, with no cryptographic tie to the body or the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string` (i.e., the body) and compares it to the `hmac` header — it never incorporates `shop`: [3](#0-2) 

`Registry.process` accepts the request purely on this body-only HMAC check, then immediately hands the unauthenticated `shop` header value to the app's handler as the tenant identity: [4](#0-3) 

Since a given app's `api_secret_key` (the HMAC key) is shared across **every shop** that has the app installed (it is per-app, not per-shop — see `Utils::HmacValidator.validate` using `Context.api_secret_key`), any shop that has legitimately installed the app can receive one authentic `(raw_body, hmac)` pair from Shopify for its own webhook, then replay that exact body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a different, victim shop domain (and optionally a different topic header, which is also unsigned). The signature still validates, because `hmac` only ever attests to the body bytes, not to which shop or topic they belong to.

This is the "field acted on but not covered by the HMAC" bug class described in the report: the gem validates the bytes it received are authentic (`body` + `hmac`), but the field the application actually uses to select and act on tenant data (`shop`) is disjoint from what was verified.

### Impact Explanation
The library documents (`docs/usage/webhooks.md`) that `Registry.process` "will verify the request did indeed come from Shopify" and that host applications should key their processing on `data.shop` (`WebhookMetadata#shop`). Because `shop` is unauthenticated, any of the app's own installed-shop tenants can forge webhook events "from" any other tenant shop while still passing the gem's authenticity check — this is a cross-tenant identity binding break entirely within the gem's own verification logic, directly matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires nothing more than access to one legitimate, unprivileged webhook delivery for a shop that has installed the app (any merchant who installs a public app can trivially capture a real webhook body + HMAC via a proxy/logging), then replaying it with a different `shop` header value to the app's public webhook endpoint. No access token, secret, or privileged account is needed.

### Recommendation
Bind `shop` (and `topic`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived `shop`/`topic` to the signed body — e.g. include them in `to_signable_string`, or require the caller to independently confirm that the delivered `shop` corresponds to a shop for which this exact `webhook_id`/subscription was registered before invoking the handler.

### Proof of Concept
1. Shop A (attacker, has legitimately installed the victim app) triggers an event that causes Shopify to send it a genuine webhook, e.g. `orders/create`, with body `B` and headers including `x-shopify-hmac-sha256: H` (computed over `B` with the app's shared `api_secret_key`) and `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker intercepts this legitimate delivery (e.g., via their own reverse proxy/logging in front of their installed app instance, or replays it directly since they control where their shop's webhooks are delivered).
3. Attacker sends a new HTTP request to the app's public webhook endpoint with the identical raw body `B` and identical `x-shopify-hmac-sha256: H`, but with `x-shopify-shop-domain: shop-b.myshopify.com` (a victim shop also using the app).
4. `ShopifyAPI::Webhooks::Request.new` parses these headers; `HmacValidator.validate` recomputes the HMAC over `B` only, matches `H`, and returns `true`.
5. `Registry.process` invokes the app handler with `WebhookMetadata(shop: "shop-b.myshopify.com", body: B, ...)`, causing the app to act on/mutate victim shop B's data using attacker-controlled body content, despite the request never having been authenticated as pertaining to shop B.
