### Title
Webhook shop attribution is not covered by the HMAC signature, enabling cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body. The `shop` value that is handed to the app's webhook handler for tenant attribution is read from the `x-shopify-shop-domain` HTTP header, which is never included in the signed material. Any caller that can produce one validly-signed webhook body (e.g., a merchant who installs the app on their own store and thus legitimately receives real, correctly-signed webhooks) can resend that same body/HMAC pair to the app's webhook endpoint with an arbitrary `shop-domain` header, and the gem will report it as a valid, authenticated webhook for a shop of the attacker's choosing.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Webhooks::Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all derived purely from HTTP headers, outside of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC exclusively against `verifiable_query.to_signable_string` (the raw body): [3](#0-2) 

`Webhooks::Registry.process` checks only this body-derived HMAC, then immediately trusts `request.shop` (a header value with no cryptographic binding to the signature) to construct the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The equality that should hold but doesn't:
`HMAC_valid(raw_body) == true` should imply `shop_header == shop_that_produced(raw_body)`. In this implementation, `HMAC_valid(raw_body)` only proves the body was signed by Shopify for *some* webhook; it says nothing about which shop's `x-shopify-shop-domain` header was sent alongside it, because that header is never part of `to_signable_string`. An attacker who can capture (or self-generate, by installing the app on a store they control) one genuinely-signed `(raw_body, hmac)` pair can replay it against the app's public webhook endpoint with a different `x-shopify-shop-domain` header. `Registry.process` will pass HMAC validation and hand the host application a `WebhookMetadata` claiming the payload belongs to a different, victim shop.

If the host application (as the gem's own docs instruct) uses `data.shop` from `WebhookMetadata` to look up which tenant's session/record to act on, this breaks the shop-authenticated-versus-shop-used-as-key binding and allows cross-tenant data injection/impersonation — an attacker-controlled shop's payload gets attributed to an arbitrary other shop.

### Impact Explanation
This is a cross-tenant identity-binding failure: verified bytes (the HMAC-signed raw body) are decoupled from the identity field (`shop`) that host applications use to select the tenant context. Depending on how the application's webhook handler uses `data.shop` (e.g., writing order/inventory/customer data keyed by shop, or triggering shop-scoped side effects), this can lead to cross-tenant data corruption or disclosure attributed to a victim merchant, meeting the Critical "cross-tenant access" impact bar.

### Likelihood Explanation
Exploitation requires only the ability to send an HTTP request to the app's public webhook endpoint with attacker-chosen headers and a `raw_body`/`hmac` pair that the attacker can obtain simply by installing the app on their own store (an ordinary, unprivileged action) and capturing one of their own legitimately-delivered webhooks. No access to `api_secret_key`, access tokens, or any Shopify-side credential is required.

### Recommendation
Bind the shop identity to the verified payload before trusting it:
- Where the webhook topic's JSON body contains a shop-identifying field (e.g., `myshopify_domain`), validate that it matches the `x-shopify-shop-domain` header before dispatching to the handler.
- Alternatively, extend `VerifiableQuery`/`to_signable_string` (or perform a secondary check) so the `shop-domain`, `topic`, and other headers relied upon for authorization decisions are cryptographically bound to the signature, not merely carried alongside it.
- Document explicitly in `docs/usage/webhooks.md` that `WebhookMetadata#shop` is unauthenticated header data and must not be used as the sole tenant key without additional verification against session/subscription state (e.g., confirming a webhook was actually registered for that shop/topic combination via `Registry` bookkeeping).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets it register webhooks normally.
2. Shopify sends a legitimately signed webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`
   - Body: `raw_body`
3. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` value to the same endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `raw_body` only — this still matches, since the body is unchanged.
5. `Webhooks::Registry.process` in `lib/shopify_api/webhooks/registry.rb` calls the app's handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, even though the payload actually originated from `attacker.myshopify.com`.
6. If the host app trusts `data.shop` to select which tenant's session/records to update, victim's data is now cross-contaminated with attacker-controlled content.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
