## Analog Found

### Title
Reentrancy in `IntentGatewayV2.withdraw` due to external token/native transfers preceding escrow-state updates — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) implements escrow release with the exact "external call before state update" anti-pattern described in the Market.sol report. Its internal `withdraw()` function performs a raw native-token `.call` or an ERC-20 `token.call(transfer(...))` to the beneficiary/token contract, and only decrements the `_orders[commitment][token]` escrow accounting *after* that external call returns [1](#0-0) . This is the same class of bug the sibling EVM contracts (`IntentsBase.sol`) already fixed by moving the state decrement before the transfer [2](#0-1) , and it is the exact class of bug the project's own regression suite documents as previously exploitable and patched [3](#0-2) .

### Finding Description
`withdraw()` is reachable from three places:
- `cancelOrder()` (same-chain path), directly callable by the order's own user [4](#0-3) 
- `onAccept()` for `RedeemEscrow`/`RefundEscrow` cross-chain messages [5](#0-4) 
- `onGetResponse()` for the cancel-from-source GET response [6](#0-5) 

Inside `withdraw()`, for every escrowed token, the sequence is: check `_orders[commitment][token] == 0`, then **transfer** (`beneficiary.call{value: amount}("")` for native, or `token.call(transfer(beneficiary, amount))` for ERC-20), and only afterward `_orders[body.commitment][token] -= amount;` [7](#0-6) . The same ordering repeats for transaction fees [8](#0-7) .

Unlike the primary EVM `IntentGatewayV2.sol`, which guards every state-mutating entry point (`placeOrder`, `cancelOrder`, `fillOrder`) with `nonReentrant` (6 occurrences project-wide, all in that one file), the Tron contract has **zero** `nonReentrant` modifiers anywhere. The order creator fully controls which ERC-20 contracts are used as escrow inputs at `placeOrder` time — including deploying their own token/beneficiary contract with a `transfer` hook — so the external call in `withdraw()` hands control flow to attacker-controlled code while the escrow ledger (`_orders[commitment][token]`) for tokens not yet processed in the same loop is still un-decremented, and while other commitments' `_orders`/`_filled` entries remain fully mutable. This is the precise bug class from the report: "state update is done after making the external call," opening a reentrancy window during fund disbursement.

        bytes32 commitment = keccak256(abi.encode(order));

        // order has already been filled

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");

                if (!success) revert TransferFailed();
            }

                ++i;
            }
