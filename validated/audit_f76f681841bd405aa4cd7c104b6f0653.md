## Analysis

The binding the question claims is broken: `WebhookMetadata#shop` (and `#topic`, `#webhook_id`, `#api_version`) should equal a value that was authenticated by the HMAC signature check, i.e. `request.shop == <value protected by to_signable_string>`. Tracing `Utils::HmacValidator.validate` shows the signable string is defined in `Webhooks::Request#to_signable_string`, which returns only `@raw_body` [1](#0-0) . The `hmac`, `topic`, `shop`, `api_version`, and `webhook_id` accessors all read from unsigned HTTP headers (`shopify-*`/`x-shopify-*`) rather than from the signed body [2](#0-1) .

`Registry.process` validates only that *some* body produces the received HMAC, then unconditionally trusts `request.topic` for handler dispatch and `request.shop` for `WebhookMetadata#shop` [3](#0-2) . `HmacValidator.validate_signature` computes the signature strictly from `to_signable_string` (the raw body) and compares it to the `hmac` header via `OpenSSL.secure_compare` [4](#0-3) . Nothing binds `shop-domain`, `topic`, or `webhook-id` headers into that computation.

Consequence: an attacker who operates their own development shop with the app installed will legitimately receive HMAC-valid webhook deliveries (signed with the app's real `client_secret`, since Shopify signs deliveries for any shop that installed the app). Because the signature covers only the raw JSON body, the attacker can take one such genuinely-signed delivery and resubmit it to the app's webhook endpoint with the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers rewritten to arbitrary values (e.g., a victim merchant's `myshop.myshopify.com`, or `shop/redact`/`customers/redact` for a shop they don't control). `HmacValidator.validate` still returns `true` because the body/HMAC pair is unchanged, and `Registry.process` dispatches the handler for the attacker-chosen `topic` and hands the attacker-chosen `shop` to the app via `WebhookMetadata#shop` [5](#0-4) . There is no delivery-id or timestamp state kept anywhere in `Registry` or `HmacValidator` to detect this reuse/mutation, and no mechanism binds header values into `to_signable_string`.

This matches the stated invariant failure exactly: "every value acted on downstream" (topic, shop, webhook_id, api_version) is **not** inside the string handed to `HmacValidator` via `to_signable_string` — only the raw body is. `ShopValidator`, `JwtPayload`, `Context.setup?`, and the OAuth `state` comparison are unrelated to this webhook code path and provide no mitigation here; none of them are invoked in `Registry.process`.

### Title
Webhook headers (`shop`, `topic`, `webhook_id`, `api_version`) are excluded from the HMAC signable string, allowing cross-tenant shop/topic spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only the raw request body, so `HmacValidator.validate` never authenticates the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Registry.process` still uses these unauthenticated headers to select the handler and populate `WebhookMetadata#shop`, letting anyone who has ever received one genuinely-signed webhook (e.g., an attacker's own installed dev shop) resubmit it with rewritten headers to impersonate an arbitrary shop and/or topic.

### Finding Description
The broken binding: `request.shop` (and `request.topic`, `request.webhook_id`) should be constrained by `HmacValidator.validate(request) == true` such that they equal values the app secret actually vouched for. In reality `to_signable_string` returns `@raw_body` only [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are parsed from unsigned headers [2](#0-1) . `HmacValidator.validate_signature` recomputes HMAC over `to_signable_string` and compares to the `hmac` header [4](#0-3) , so the check is satisfied by body+hmac alone, independent of every other header. `Registry.process` then uses `request.topic` to pick `@registry[request.topic]&.handler` and passes `request.shop` straight into `WebhookMetadata#shop` for the handler to act on [6](#0-5) .

Attack: attacker installs the app on their own development shop (unprivileged, self-service) and captures a legitimately signed webhook delivery (body + `hmac-sha256` header valid under the app's real secret). They POST that identical body/HMAC pair to the app's public webhook endpoint again, but with `X-Shopify-Shop-Domain` set to a victim merchant's domain and/or `X-Shopify-Topic` set to `shop/redact` or `customers/redact` or any other registered topic. `HmacValidator.validate` still passes (body unchanged), `Registry.process` dispatches the handler for the attacker-chosen topic, and the handler receives `WebhookMetadata#shop` equal to the victim's domain — a value the signature never covered. No delivery-id/timestamp store exists to catch the replay with mutated headers, and no other guard in this gem (`ShopValidator`, `JwtPayload`, `Context.setup?`) runs in this path.

### Impact Explanation
An app whose webhook handlers key off `WebhookMetadata#shop` (e.g., to select which merchant's local record to delete/update, common for mandatory `shop/redact`/`customers/redact`/`customers/data_request` handlers) will act on the attacker-supplied shop value while believing it is authenticated by Shopify's HMAC. This is a cross-tenant trust failure: one tenant's (the attacker's own) signed delivery can be relabeled to trigger actions attributed to a different, arbitrary victim shop, and is repeatable for any topic the app has registered, against any shop domain string the attacker supplies. This matches "Critical - authentication bypass" / cross-tenant access: a forged combination of (topic, shop) is accepted as authentic because signature coverage does not extend to it.

### Likelihood Explanation
Preconditions are minimal and attacker-controlled: create a free development shop, install the target app (standard, unprivileged), passively capture one legitimately signed webhook delivery sent by Shopify to the app (attacker controls their own server as the webhook endpoint target during development/testing, or can otherwise obtain one signed body+hmac pair), then replay it to the app's production webhook route with rewritten headers. No secrets, tokens, or victim cooperation are required. Feasibility is high and the attack is trivially repeatable for each topic/shop combination the attacker wants to spoof.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the canonical string that is HMAC-verified — either by having Shopify's signature scheme cover them (not possible to change without break with Shopify's actual signing, since Shopify only signs the body) or, more practically, treat `shop`/`topic` from headers as advisory only and re-derive/re-validate them against server-side state (e.g., look up the shop's own webhook secret/session and confirm the topic was registered for that shop) before dispatch, and add delivery-id tracking/persistence to reject replays regardless of header mutation.

### Proof of Concept
minitest + WebMock plan under `test/webhooks/registry_test.rb`:
1. `Registry.clear`; register two handlers for topics `"orders/create"` and `"shop/redact"` via `Registry.add_registration`.
2. Build one raw JSON body and compute its HMAC with the test `Context.api_secret_key` (mirroring `test/utils/hmac_validator_test.rb` setup).
3. Construct a `Webhooks::Request` with headers `{"x-shopify-topic" => "orders/create", "x-shopify-hmac-sha256" => valid_hmac, "x-shopify-shop-domain" => "attacker-shop.myshopify.com", ...}` and call `Registry.process(request)`; assert the `orders/create` handler's mock is invoked.
4. Re-issue the identical body/hmac but with headers mutated to `"x-shopify-topic" => "shop/redact"` and `"x-shopify-shop-domain" => "victim-shop.myshopify.com"`; assert `Registry.process(request)` still returns true from `HmacValidator.validate` and now dispatches the `shop/redact` handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, proving dispatch and shop attribution follow unsigned headers rather than the signature, i.e. `to_signable_string` (asserted via `request.to_signable_string == raw_body` with no header content present) does not bound the observed `topic`/`shop` values.
