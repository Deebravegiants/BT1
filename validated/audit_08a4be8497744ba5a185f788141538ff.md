Based on the documentation, `Registry.process` is explicitly described as verifying "the request did indeed come from Shopify" as a whole, and `data.shop` is presented to handler authors as a trustworthy field alongside `data.body`, `data.topic`, etc., with no caveat that `shop` is unauthenticated. This confirms the analog is a genuine, in-scope gem defect rather than something dependent on the host app ignoring documented behavior.

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before invoking the app's webhook handler with a `WebhookMetadata` struct that includes `shop`. In reality, the HMAC signature only covers the raw request body; the `shop` (and `topic`, `webhook_id`, `api_version`) header values are never included in the signed payload, so any attacker able to reach the app's public webhook endpoint can supply a forged `shop` value alongside a validly-signed body, causing the handler to process the payload under an arbitrary victim shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read directly from the `x-shopify-shop-domain` / `shopify-shop-domain` header without any cryptographic binding to the HMAC: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string`, i.e. only the body, and does not touch `shop`/`topic`/`webhook_id`: [3](#0-2) 

`Registry.process` verifies only that HMAC, then constructs `WebhookMetadata` directly from the unauthenticated `request.shop` and hands it to the app's handler as if it were verified: [4](#0-3) 

This breaks the intended identity binding: `hmac_signed_bytes == request.raw_body` while the field actually acted upon by the handler is `request.shop`, which is never part of `hmac_signed_bytes`. The equality the code implicitly assumes — "if HMAC(secret, raw_body) is valid then shop is the shop that sent this webhook" — does not hold, because `shop` is attacker-controlled header data that rides along outside the signature.

Since the secret used for the HMAC (`Context.api_secret_key`) is the app's single shared secret across all shops using the app (not shop-specific), any genuine webhook payload the attacker can obtain a valid signature for (e.g., a webhook legitimately delivered to their own shop/test store, or any other body whose HMAC they can obtain) remains validly signed no matter what `shop` header value accompanies it. An attacker who controls a shop that has the app installed can trigger a real webhook delivery (valid body + valid HMAC using the app's shared secret) to the app's public webhook endpoint, then replay that exact body/HMAC pair while substituting the `x-shopify-shop-domain` header for a victim shop's domain.

### Impact Explanation
The documented usage pattern (`docs/usage/webhooks.md`) explicitly tells developers that `data.shop` is a trustworthy field to key off of ("the shop domain of the webhook"), and shows it being used directly, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`. Because `Registry.process` presents this field as verified alongside the HMAC check, applications built on this gem's documented contract are led to trust `data.shop` for tenant-scoping decisions (e.g., looking up the victim shop's stored access token/session by this shop domain and performing shop-scoped writes or side effects). This enables cross-tenant confusion: a webhook body genuinely signed under the app's own secret can be attributed to any other merchant shop using the app, without possessing that shop's credentials.

### Likelihood Explanation
Any unprivileged party who can install the app on any shop (or otherwise trigger a legitimately signed webhook delivery to the app, e.g. via a store they control) and can reach the app's public webhook endpoint can perform this attack; no access token, `client_secret`, or privileged account is required — only a request to the webhook callback URL with a forged `shop` header alongside a body/HMAC pair that is validly signed under the app's shared `api_secret_key`.

### Recommendation
Include the `shop` domain (and ideally `topic`/`webhook_id`) in the HMAC-signed payload used for verification, or otherwise cryptographically bind the shop identity to the signed body (e.g., validate that the reported `shop` is a shop your app has completed OAuth/token-exchange installation for, and treat the header as untrusted metadata rather than an authenticated identity). At minimum, document clearly that `shop` in `WebhookMetadata` is unauthenticated header data and must be cross-checked against known installed shops before being used for tenant-scoping decisions.

### Proof of Concept
```ruby
# Attacker controls "attacker-shop.myshopify.com" which has the app installed.
# Shopify delivers a legitimately-signed webhook for this shop's own order:
raw_body = '{"id":1,"note":"hello"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_secret, raw_body)

# Attacker replays the exact body + hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to the victim shop:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds because it only checks raw_body's HMAC.
# The app's handler receives data.shop == "victim-shop.myshopify.com" as if verified.
```
