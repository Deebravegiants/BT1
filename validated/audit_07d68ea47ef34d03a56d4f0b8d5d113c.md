### Title
`AdminOperation::UpdateGovDelay` is resolved with the `Standard` delay tier despite modifying the timelock's own security parameter - (File: contracts/governance/src/op.rs)

### Summary
The governance contract classifies every admin operation into a `DelayTier` (`Standard`, `Sensitive`, `Recovery`) that determines the minimum timelock delay before execution (`operation_delay` in `contracts/governance/src/timelock/mod.rs:42-49`). Sensitive actions — role grants/revocations, ownership transfers, contract upgrades, `set_position_manager`, `force_socialize_bad_debt` — are all placed in the `Sensitive` tier, which enforces a floor of `TIMELOCK_SENSITIVE_MIN_DELAY_LEDGERS`. However, `AdminOperation::UpdateGovDelay`, which rewrites the timelock's own `min_delay` via `apply_update_delay`/`set_min_delay`, is resolved with `DelayTier::Standard` (`op.rs:135-143`). This is the direct analog of Olympus's `Timelock::setDelay` being excluded from the high-risk quorum: the function that changes the delay security parameter itself is not treated as sensitive.

### Finding Description
In `resolve_op` (`contracts/governance/src/op.rs:124-432`):

```rust
AdminOperation::UpdateGovDelay(new_delay) => {
    validate_delay_update(env, *new_delay);
    self_operation(env, "update_delay", ..., DelayTier::Standard)  // line ~141
}
```

Compare with `GrantGovRole`, `RevokeGovRole`, `TransferGovOwnership`, `UpgradeGov`, `SetPriceAggregator`, `SetSwapAggregator`, upgrades, and `ForceSocializeBadDebt`, all of which resolve to `DelayTier::Sensitive`.

`validate_delay_update` (`timelock/mod.rs:59-67`) only enforces `new_delay >= current` and `new_delay <= TIMELOCK_MAX_DELAY_LEDGERS` (241,920 ledgers), so a queued `UpdateGovDelay` op can ratchet the minimum delay to the ~14-day ceiling. Because it sits in `Standard`, it becomes executable after the shortest delay — faster than any `Sensitive`-tier defensive operation that could be queued in response.

### Impact Explanation
Any unprivileged address may call the timelock `execute` entrypoint for a ready operation (`authorize_executor` performs no check when `executor` is `None`, `timelock/mod.rs:77-82`). A `UpdateGovDelay` op raising `min_delay` to `TIMELOCK_MAX_DELAY_LEDGERS` therefore takes effect after only the standard delay. Every subsequently *scheduled* operation — including `AdminOperation::Unpause` (Standard) and all `Sensitive` ops — must then wait up to ~14 days, extending any pause or delaying emergency response. This produces temporary freezing of user funds/contract functionality via delayed unpause or delayed corrective admin actions, matching the report's concern that security-parameter changes should require the strongest scrutiny window.

### Likelihood Explanation
Requires a `UpdateGovDelay` operation to be scheduled (proposer-gated), after which execution is permissionless. The misclassification is deterministic in `resolve_op`; no economic or oracle conditions are needed. Impact is bounded since the delay can only increase and is capped, which keeps severity at Medium rather than High.

### Recommendation
Resolve `AdminOperation::UpdateGovDelay` with `DelayTier::Sensitive` in `resolve_op` (`contracts/governance/src/op.rs:135-143`), consistent with the other governance self-operations (`GrantGovRole`, `TransferGovOwnership`, `UpgradeGov`), so changes to the timelock's own delay receive the elevated minimum delay floor.

### Proof of Concept
1. A `UpdateGovDelay(TIMELOCK_MAX_DELAY_LEDGERS)` operation is scheduled; `resolve_op` assigns it `DelayTier::Standard`, so `operation_delay` returns only `get_min_delay` (no sensitive floor).
2. Once ready, any unprivileged caller executes it (no `executor` auth required); `apply_self_op` → `apply_update_delay` sets `min_delay = 241_920` (`op.rs:442`, `timelock/mod.rs:70-73`).
3. A subsequently scheduled `Unpause` or any defensive `Sensitive` op must now wait ~14 days instead of the prior minimum, prolonging a pause or delaying mitigation — an outcome the `Sensitive` tier exists to prevent for equally sensitive self-governance changes.
