### Title
Session Fixation via Unauthenticated, Predictable Session Cookie Value in `ShopifyAPI::Utils::SessionUtils.cookie_session_id` - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` (used by host apps to resolve which stored `Auth::Session` to load for a request) trusts the raw, unsigned value of the `shopify_app_session` cookie as the session storage key, with no cryptographic binding to the requesting browser. Because the cookie's value is set in `ShopifyAPI::Auth::Oauth.validate_auth_callback` to the deterministic, guessable `Session#id` (`"offline_#{shop}"` or `"#{shop}_#{associated_user_id}"`), an attacker can set this cookie in their own browser to a victim shop's session id and cause the host application to retrieve and act with the victim shop's stored access token.

### Finding Description
`ShopifyAPI::Auth::Oauth.validate_auth_callback` sets the non-embedded session cookie to the plain session id: [1](#0-0) 

`Session.from` derives this id deterministically from the shop domain (and user id for online sessions), with no random/secret component: [2](#0-1) 

At request time, `SessionUtils.current_session_id` retrieves the session id used to look up the stored session either from a validated JWT (`session_id_from_shopify_id_token`) or — as a fallback, or always for non-embedded apps — directly from the unauthenticated cookie value via `cookie_session_id`, with no HMAC, signature, or ownership check on the cookie: [3](#0-2) [4](#0-3) 

Contrast this with the `HmacValidator`, which binds `shop`/`state` to a server-known secret in the OAuth flow: [5](#0-4) 

The binding that should hold is: `cookie_value == session_id_bound_to_this_browser`. Instead the code accepts `cookie_value == any_valid_session_id_string`, i.e., "bytes verified" (none) versus "bytes trusted" (the raw cookie) is broken — the gem never verifies that the party presenting the cookie is the one that completed OAuth for that shop.

### Impact Explanation
Because `Session#id` is fully predictable from public information (the shop's `myshopify.com` domain, and for online sessions the associated user id, which is often guessable/enumerable), an attacker who signs up their own trial/dev shop and installs the app can:
1. Observe the deterministic id format returned by their own install (e.g., `offline_attacker-shop.myshopify.com`).
2. Set their browser's `shopify_app_session` cookie to `offline_victim-shop.myshopify.com` (or `victim-shop.myshopify.com_<user_id>` for online sessions).
3. Cause the host app (following this gem's documented `current_session_id`/`cookie_session_id` API) to fetch the victim shop's stored `Session`, including its `access_token`, and use it to serve the attacker's request.

This results in cross-tenant access and access-token misuse/exfiltration through the app's own session-resolution primitive — a Critical-class impact (cross-tenant access, theft of merchant access token) achievable by an unprivileged internet user with no access to `api_secret_key`, tokens, or TLS interception.

### Likelihood Explanation
Likelihood is high for non-embedded apps (which rely solely on the cookie per `current_session_id`) and for embedded apps that fall back to cookie-based session lookup when no `shopify_id_token` is presented. The attacker needs only: (a) their own legitimate install of the target app to learn the session-id format, and (b) the ability to set an arbitrary cookie value in their own browser — both trivial. The only obstacle is guessing/knowing the exact victim shop domain (and user id for online sessions), which is typically public (`*.myshopify.com` shop names are often disclosed in storefronts, emails, or app listings) or enumerable.

### Recommendation
Do not use the raw, attacker-controllable cookie value as a trusted session-storage key. Instead:
- Sign/HMAC the cookie value (or store an opaque, high-entropy, unguessable token in the cookie that maps server-side to the session id), and verify that signature/token before using it to key session lookup.
- Alternatively, bind the cookie to session state established during the OAuth `state` nonce flow so it cannot be replayed/fixated across shops or users.
- Document explicitly in `docs/usage/oauth.md` that `SessionUtils.cookie_session_id` returns an untrusted value and that host apps must not use it directly to authorize privileged operations without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` via normal OAuth (`Oauth.begin_auth` / `Oauth.validate_auth_callback`), and observes their `shopify_app_session` cookie is set to `offline_attacker-shop.myshopify.com` per [6](#0-5) , confirming the deterministic id format from `Session.from` (`"offline_#{shop}"`) shown at [7](#0-6) .
2. Attacker manually rewrites their browser cookie `shopify_app_session` to `offline_victim-shop.myshopify.com`.
3. Attacker makes any request to the host application; the host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which (per [3](#0-2)  and [4](#0-3) ) returns the attacker-supplied string `offline_victim-shop.myshopify.com` with no verification.
4. Host app loads the stored `Session` for that id from its session repository and uses its `access_token` to serve the attacker's request against the victim shop's data — a cross-tenant compromise.

          end
        end
