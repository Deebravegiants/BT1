### Title
Strategy authorization checks the stale `Account.owner` snapshot instead of the current NFT owner, letting a former owner keep acting on a transferred account - (File: contracts/controller/src/account.rs)

### Summary
The FUXA bug class is a security-critical check run against the wrong, attacker-influenced representation of identity: the middleware matched a substring of the raw URL (which includes query parameters) instead of the canonical path, so `?x=/socket.io` "looked like" a public path. The same class exists here: `load_or_create_account` authorizes account-mutating strategies by comparing the caller against `Account.owner`, a value written once at account creation (`create_account_with`, account.rs:64-66), instead of the canonical ownership record `storage::account_owner` / the position NFT. After a `position-nft` transfer changes the real owner, the stored snapshot is never refreshed, so the previous owner (and any manager they delegated before selling) still passes the guard and can execute `multiply`, `migrate_from_blend`, and `flash_position` against an account they no longer own — including paths that mint debt into it and refund leftovers to the caller.

### Finding Description
`Account.owner` is populated once in `create_account_with` from the creator's address and stored with the account (contracts/controller/src/account.rs:64-71). The position NFT is the transferable source of truth for ownership — `require_account_owner` (account.rs:143-148) correctly reads `storage::account_owner` for `renew_account` and delegate management — but `load_or_create_account` uses `require_owner_or_delegate` (account.rs:101-108), which calls `is_owner_or_delegate` and returns true when `caller == account.owner` (account.rs:121-122). `account.owner` is a stale snapshot: nothing updates it on NFT transfer, since transfers happen entirely inside the position-nft contract without notifying the controller. `AccountGuard::Migrate` and `AccountGuard::Multiply` (used by `migrate_from_blend`, `multiply`, and `flash_position` per the call sites in `strategies/flash_position.rs` and `strategies/migrate_blend.rs`) therefore accept any caller who was the owner at creation time, plus delegates recorded under that stale owner (`storage::get_delegates(env, account_id, owner)` at account.rs:126 is keyed to the stored owner). The previous owner only needs to authenticate as themselves — which they legitimately can — so the check is bypassed not by forged auth but by evaluating authorization against the wrong field, exactly like the FUXA middleware evaluating `req.originalUrl` instead of `req.path`.

### Impact Explanation
A seller who transfers their account NFT retains full strategy authority over the buyer's account. Through `multiply`/`flash_position`, the attacker can mint debt against the victim's collateral and arrange routes so that unspent inputs and refund-listed callback receipts return to `refund_to = caller` (the strategies' refund path in `strategies/swap.rs` sends leftover input to the caller-supplied refund address), extracting value while leaving the debt and impaired health factor on the victim's account — direct theft of user funds. Through `migrate_from_blend`, the attacker can force a migration of the victim's approved Blend position under conditions they choose. Even absent direct extraction, minted debt accrues interest and can push the victim to liquidation or leave protocol bad debt.

### Likelihood Explanation
Reachability is high: `position-nft` `transfer`/`approve` is an in-scope unprivileged entrypoint, accounts are explicitly designed to be transferable NFTs, and no re-auth or cooldown gates strategy calls on ownership change. The only cost is having once created the account and retaining delegate grants — `set_account_delegate` requires an active manager at grant time, but the grant persists under the stale owner key after transfer. One uncertainty I could not fully verify within scope: whether any of the affected strategy entrypoints re-check `require_account_owner` deeper in the call chain before settlement; the guards in `load_or_create_account` clearly do not, and none of the strategy files' auth reads surfaced an NFT-owner recheck.

### Recommendation
Replace the snapshot comparison in `require_owner_or_delegate`/`is_owner_or_delegate` with the canonical owner read: resolve `current_owner = storage::account_owner(env, account_id)` (NFT owner) and evaluate `caller == current_owner` plus delegates keyed under `current_owner`, mirroring `require_account_owner`. Alternatively, derive the delegate list from the live NFT owner so stale grants keyed to a previous holder cannot authorize.

### Proof of Concept
1. Alice calls `supply` (or any account-creating entrypoint) with `account_id = 0`; `create_account_with` stores `Account{ owner: alice, ... }` and mints account NFT #1 to Alice.
2. Alice optionally calls `add_delegate(account 1, mallory_manager)` where `mallory_manager` is an active manager.
3. Alice transfers NFT #1 to Bob via the position-nft `transfer` entrypoint. `storage::account_owner(1)` now returns Bob; `Account.owner` still returns Alice.
4. Alice (or the delegated manager) calls `multiply`/`flash_position` with `account_id = 1` and `caller = alice`. `load_or_create_account` → `require_owner_or_delegate` sees `caller == account.owner` (Alice) and passes — Bob's auth is never required.
5. The strategy mints debt on Bob's account; leftover inputs and refund-listed callback receipts are sent to the attacker-controlled `refund_to` address. Bob's account is left leveraged/impaired while he never signed anything.
