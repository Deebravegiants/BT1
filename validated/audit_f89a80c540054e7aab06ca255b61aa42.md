### Title
Deposit LP-share pricing uses raw SPL vault balances with no minimum-LP-out check, enabling donation-based inflation theft on a newly created pool - ([File: program/src/processor.rs])

### Summary
`process_deposit` prices new LP shares against the *actual token balances* of `amm_coin_vault`/`amm_pc_vault` rather than an internally accumulated deposit ledger, and `DepositInstruction` has no `min_lp_amount` parameter. Because pool creation via `Initialize2` is permissionless and only requires liquidity above a small floor, an attacker can create a pool they dominate, then directly donate SPL tokens to one of the vaults right before a victim's `Deposit` lands, skewing the exchange-rate denominator and reducing the LP tokens minted to the victim relative to the real value they contribute — mirroring the Napier "vault inflation via `balanceOf` + rounding" bug class.

### Finding Description
`process_deposit` computes the LP-mint ratio from real, unrestricted SPL token balances: [1](#0-0) 
This uses `unpack_token_account` on the vaults, i.e. their live SPL balance — equivalent to the `balanceOf`-style read flagged as the root cause in the reference report.

The mint amount is derived by a floor-division `InvariantPool::exchange_token_to_pool`: [2](#0-1) 
against `amm.lp_amount`, the program's own supply counter (not the LP mint's real supply): [3](#0-2) 

The `DepositInstruction` payload only allows bounding the coin/pc amounts exchanged (`max_coin_amount`, `max_pc_amount`, `other_amount_min`) — there is no field to require a minimum number of LP tokens minted: [4](#0-3) 
So a victim cannot protect against a reduced LP-token outcome caused by vault-balance manipulation, exactly the gap called out in the reference report's recommendation section (mint dead shares / avoid `balanceOf`).

`Initialize2` is permissionless — any user can spin up a brand-new pool, subject only to a minimum-liquidity floor (`InitLpAmountTooLess`), after which nearly the entire LP supply belongs to the creator: [5](#0-4) 
Note only `liquidity - 10^lp_decimals` LP is actually minted to the creator, while `amm.lp_amount = liquidity` — this deliberately locks a *dead* share amount analogous to Uniswap V2 `MINIMUM_LIQUIDITY`, but does not prevent an attacker who owns the pool from manipulating vault balances afterward via a raw SPL transfer.

### Impact Explanation
An attacker who creates a low-liquidity pool (which they fully control) can, immediately before a legitimate user's `Deposit` transaction executes, send a plain SPL token transfer directly into `amm_coin_vault` or `amm_pc_vault`. This inflates the balance used as the ratio denominator in the victim's deposit, causing the victim to receive fewer LP tokens (rounded down) than the value they contributed. The attacker, holding essentially all existing LP supply, then withdraws and captures both their donated tokens and a disproportionate share of the victim's deposited value — a direct theft of user funds, matching the "Loss of assets for the victim" impact in the reference report.

### Likelihood Explanation
This requires the attacker to control the target pool (trivial, since pool creation is permissionless) and to time a donation transaction ahead of a victim's `Deposit` into that same low-liquidity pool — a realistic scenario for any freshly created pool before deep liquidity accumulates, since no `min_lp_amount` guard exists to protect depositors. It does not require any privileged signer, leaked key, or malicious validator — a single unprivileged SPL transfer plus normal deposit account references suffice.

### Recommendation
- Add a `min_lp_amount` (or equivalent) parameter to `DepositInstruction` and enforce it in `process_deposit`, letting depositors bound the minimum LP tokens they will accept.
- Consider tracking pool token totals via an internally maintained accounting value (updated only through program-processed transfers) rather than trusting the raw SPL vault balance for LP-mint pricing, or reconcile any "excess" balance (donations) into the fee/pnl accounting rather than silently affecting the deposit ratio.

### Proof of Concept
1. Attacker calls `Initialize2` to create a new pool with the minimum `init_coin_amount`/`init_pc_amount` that satisfies `InitLpAmountTooLess`, becoming owner of nearly all `amm.lp_amount`.
2. Attacker waits for a victim's `Deposit` transaction targeting this pool to be observed/queued.
3. Attacker submits an SPL `Transfer` instruction sending a large amount of the coin (or pc) token directly into `amm_coin_vault`, landing before the victim's `Deposit`.
4. Victim's `Deposit` executes: `calc_total_without_take_pnl_no_orderbook` reads the now-inflated `amm_coin_vault.amount`, so `mint_lp_amount = deduct_coin_amount * amm.lp_amount / total_coin_without_take_pnl` rounds down to a value disproportionately smaller than the victim's real contribution; no `min_lp_amount` check exists to abort the transaction.
5. Attacker withdraws their dominant LP position via `Withdraw`, redeeming a share of the pool that now includes both their donation and a disproportionate cut of the victim's deposited assets.
