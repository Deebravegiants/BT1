### Title
Attacker/replayed `Request` headers can override account-binding headers (`x-exodus-app-id`, `x-exodus-version`, `x-api-key`) in `FetchFactory#create` - ([File: adapters/fetch-factory/src/fetch-factory.js])

### Finding Description
`FetchFactory#create()` handles two input shapes differently. For a plain URL/string it calls `this.#buildHeaders(url, opts.headers)`, where `opts.headers` is merged in via `new Headers(existingHeaders).forEach(...)` *inside* `#buildHeaders`, after the global and domain-scoped header configs are applied [1](#0-0) . But for a `Request` instance, the method builds domain headers with `this.#buildHeaders(urlOrRequest.url)` (no `existingHeaders` argument), and then separately iterates `urlOrRequest.headers.forEach(...)` and `opts.headers` to overwrite entries on the already-built `Headers` object via `headers.set(key, value)` [2](#0-1) .

Because `Headers.set` replaces any existing value for a given key, any header name present on the incoming `Request` object — including `x-exodus-app-id`, `x-exodus-version`, `x-requested-with` (set via `setDefaultExodusIdentifierHeaders`) or any domain-scoped header configured via `setHeaders(..., [hostname])` such as `x-api-key` — will be silently overwritten by whatever value the `Request` object already carries. This is confirmed by the existing test `options headers take precedence over Request headers` [3](#0-2) , which demonstrates the intended override semantics for `opts.headers`, and by `adds domain-specific headers to Request objects` [4](#0-3) , which only tests the case where the `Request` does *not* already define the domain-scoped key — it never asserts that a `Request` carrying its own `x-api-key`/`x-exodus-app-id` is blocked from overriding the domain-bound value. There is no denylist/whitelist enforcement at header-application time in `create()` (unlike `setHeaders`, which does enforce `WHITELISTED_HEADERS`/`WHITELISTED_X_AUTH_HEADERS` for what can be *configured* globally, but that check does not apply to headers arriving via an in-flight `Request` object).

### Impact Explanation
If any calling code constructs or forwards a `Request` object to a `fetchFactory.create()`-produced fetch wrapper where the `Request`'s headers are influenced by non-trusted or stale/cross-context sources (e.g., a cached `Request`, an RPC/message-passing bridge that reconstructs a `Request` from serialized/attacker-supplied data), the resulting outbound HTTP call to `exodus.io` (or any configured domain) can carry a spoofed `x-exodus-app-id`/`x-api-key`/`x-exodus-version` instead of the value the application intended to bind. Depending on how the backend interprets these headers for account/app attribution, this could result in requests being misattributed to the wrong app/account context.

### Likelihood Explanation
Exploitability depends entirely on whether any production call site actually passes a `Request` object whose headers are attacker/stale-influenced into a `fetchFactory.create()` wrapper. My search located usages of `setDefaultExodusIdentifierHeaders`/`x-exodus-app-id` in `apps/sdk-minimal-demo/src/background/adapters/fetch.ts` and `apps/sdk-playground/src/background/shims.js`, but I could not confirm within the available index whether these call sites ever pass a `Request` object (as opposed to a plain URL string) with externally-influenced headers into the factory's fetch wrapper — the index did not return the full contents of those files for me to verify the exact call pattern. This uncertainty needs to be resolved (e.g., via a Devin session with full repo access) before treating this as a confirmed exploitable path; what is confirmed is the underlying code defect in `fetch-factory.js` itself.

### Recommendation
In the `Request` branch of `create()`, apply the incoming `Request`'s headers and `opts.headers` the same way as the URL branch: merge them into `#buildHeaders` as `existingHeaders` *before* domain-scoped/account-binding headers are applied, or explicitly re-apply the account-binding headers (`x-exodus-app-id`, `x-exodus-version`, `x-requested-with`, and any domain-scoped auth headers such as `x-api-key`) after merging in caller-supplied headers, so server-authoritative values always win regardless of input order.

### Proof of Concept
```js
// adapters/fetch-factory/__tests__/request-object.test.js (extension)
test('Request-supplied headers should NOT override account-binding headers', async () => {
  const fetchFactory = new FetchFactory(mockFetch)
  fetchFactory.setDefaultExodusIdentifierHeaders({
    appId: 'legit-app-id',
    appVersion: '1.0.0',
    appBuild: 'build',
  })
  fetchFactory.setHeaders({ 'x-api-key': 'legit-key' }, ['exodus.io'])

  const fetch = fetchFactory.create()
  const spoofedRequest = new Request('https://exodus.io/api', {
    headers: {
      'x-exodus-app-id': 'attacker-app-id',
      'x-api-key': 'attacker-key',
    },
  })

  await fetch(spoofedRequest)

  const [passedRequest] = mockFetch.mock.calls[0]
  // EXPECTED (fixed behavior): server-authoritative values win
  expect(passedRequest.headers.get('x-exodus-app-id')).toBe('legit-app-id')
  expect(passedRequest.headers.get('x-api-key')).toBe('legit-key')
  // CURRENT (vulnerable) behavior: attacker values win
})
```
