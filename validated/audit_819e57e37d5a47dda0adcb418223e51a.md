## Analysis

The claim concerns `TwoKeyRegistry` in `types/src/state_store/state_key/registry.rs`, an internal interning/caching layer that deduplicates `Arc<Entry>` objects representing `StateKeyInner` values (for `AccessPath`, `TableItem`, `Raw`, etc.), not an accounting or custody data structure itself. [1](#0-0) 

**Race handling is actually sound.** Both `write_lock_get_or_add` and `maybe_remove` operate exclusively under the same shard's `RwLock::write()` lock: [2](#0-1) [3](#0-2) 

Because these two operations are mutually exclusive on the same `RwLock`, they cannot interleave. The purported race — `insert_key2` overwriting a slot mid-drop while a concurrent `maybe_remove` "belonging to the prior Entry" is in flight — cannot occur simultaneously; whichever thread acquires the write lock first fully completes before the other proceeds.

More importantly, `maybe_remove` does **not** target "the exact Entry it was invoked for" by identity — it re-reads whatever `Weak<Entry>` currently sits in the map at call time and only removes it if that live weak's `strong_count() == 0`:

    fn maybe_remove(&self, key1: &Key1, key2: &Key2) {
        let mut locked = self.inner.write();
        if let Some(map2) = locked.get_mut(key1) {
            if let Some(entry) = map2.get(key2) {
                if entry.strong_count() == 0 {
                    map2.remove(key2);
                    if map2.is_empty() {
                        locked.remove(key1);
                    }
                }
            }
        }
    }
