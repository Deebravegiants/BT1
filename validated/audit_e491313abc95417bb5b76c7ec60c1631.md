### Title
`EvmHost.dispatch()` native-fee swap has no slippage protection and a meaningless deadline, exposing callers to sandwich attacks - (File: `evm/src/core/EvmHost.sol`)

### Summary
When any Hyperbridge app or user pays for a dispatch (POST/GET) with native ETH, `EvmHost.dispatch()` swaps ETH for the exact fee-token amount via UniswapV2 with no independent minimum/maximum bound beyond `msg.value` and a `deadline` parameter that is always trivially satisfied. This mirrors the report's bug class (a permissionless swap performed with no slippage protection, enabling a sandwich attack against the caller), reachable by any unprivileged dispatcher of a message.

### Finding Description
`dispatch()` performs the native-fee path unconditionally whenever `msg.value > 0`: [1](#0-0) 

```solidity
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        address[] memory path = new address[](2);
        address uniswapV2 = _hostParams.uniswapV2;
        path[0] = IUniswapV2Router02(uniswapV2).WETH();
        path[1] = feeToken();
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } ...
```

Two problems combine here:

1. **`deadline = block.timestamp`** is a no-op — it is always satisfied at the instant of execution regardless of how long the transaction sat in the mempool, so it provides none of the front-running/staleness protection a real deadline is meant to give (the same anti-pattern the reported `AuraSpell.closePositionFarm` used `type(uint256).max`, effectively disabling deadline protection entirely).
2. **No caller-supplied minimum/maximum bound distinct from `msg.value`.** `swapETHForExactTokens` is an exact-output swap, so the only implicit bound on the ETH spent is the full `msg.value` the caller sent. Any excess ETH the router does not need is refunded by the router to `msg.sender` of the swap call, which is `EvmHost` itself (`address(this)` is used only as the *token* recipient in the router call, but the router's ETH refund target for `swapETHForExactTokens` is always `msg.sender`, i.e. `EvmHost`) — not the original transaction sender (`_msgSender()`). A caller who intends to send more ETH than strictly required (a common, reasonable pattern to tolerate normal price movement) has no path to recover any unspent portion; it is not attributed back to them anywhere in `dispatch()`.

An attacker who observes a pending `dispatch()` call with `msg.value` set generously above the current fair-market input requirement can sandwich it: front-run to move the WETH→feeToken price against the victim so the router consumes close to the entire `msg.value` to produce `post.fee` tokens, then back-run to restore the price and capture the difference. Because there is no independent slippage bound the caller can set (only the size of `msg.value` itself, which by design is meant to include headroom), the victim's headroom is fully extractable by the attacker, and — because refunds route to the host contract rather than the caller — that value is not even returned to the original sender to detect and reclaim.

This path is reachable by any unprivileged party: any app or contract that calls `IDispatcher(host).dispatch{value: ...}(...)` (e.g., a `HyperFungibleToken.send()` paying in native token, `BandwidthManager` purchase flows that could be adapted to pay in native, or any third-party HyperApp), and equally applies to the sibling `dispatch(DispatchGet)` and `fundRequest` functions that follow the identical `swapETHForExactTokens{value: msg.value}(..., block.timestamp)` pattern in the same file.

### Impact Explanation
Concrete loss of user funds: any unspent ETH margin a caller includes to tolerate normal price movement can be captured by a sandwiching attacker instead of being refunded to the caller, and the documented SDK/docs guidance itself acknowledges the underlying `quote()`/Uniswap-based fee pricing is "vulnerable to sandwich attacks" for on-chain use [2](#0-1) , but that warning only covers the read-only `quote()` helper — it does not extend to (nor does the code implement) any mitigation in the actual `dispatch()` swap execution path itself.

### Likelihood Explanation
High. `dispatch()` is a core, frequently-invoked, fully permissionless entry point (used by every HyperApp paying fees in native token), and sandwiching a pending mempool transaction with visible `msg.value` and a known feeToken pair is a standard, low-cost MEV technique requiring no special access or timing beyond normal block-builder/searcher capability.

### Recommendation
- Replace `deadline: block.timestamp` with a caller-supplied, meaningful deadline parameter.
- Give the caller a way to bound the ETH actually spent (e.g., accept an explicit `amountInMax` distinct from `msg.value`), and explicitly refund any leftover ETH from the swap back to `_msgSender()` rather than leaving it attributed to `EvmHost`.
- Apply the same fix to the analogous swap in `fundRequest` and any other `EvmHost` function performing `swapETHForExactTokens`.

### Proof of Concept
Conceptual (mempool-based, not a unit test since it requires an AMM pool and searcher infrastructure):
1. Victim calls `dispatch{value: V}(post)` where `V` is comfortably above the fair-market ETH cost of `post.fee` feeTokens, intending any surplus to be refunded.
2. Attacker observes the pending transaction, front-runs with a large WETH→feeToken swap on the same pool to spike the feeToken price.
3. Victim's transaction executes: `swapETHForExactTokens(post.fee, ...)` now requires close to the full `V` in ETH to obtain `post.fee` tokens; any refund goes to `EvmHost`, not the victim.
4. Attacker back-runs to restore the pool price, pocketing the price impact created in step 2, while the victim's expected refund is never returned to them. [1](#0-0)
