### Title
Fee Evasion via Direct Call to `Hinkal.prooflessDeposit()` Bypassing `HinkalWrapper` Fee Collection - (File: `contracts/Hinkal.sol`, `contracts/HinkalWrapper.sol`)

### Summary
`HinkalWrapper.prooflessDeposit()` is meant to be the entrypoint for depositors: it collects a protocol fee (`ProoflessFeeStructure`) via `_settleFee`, pulls/approves the deposit tokens, and only then forwards the call to `Hinkal.prooflessDeposit()`. However, `Hinkal.prooflessDeposit()` is `public payable` with no restriction requiring the caller to be `HinkalWrapper`, so any user can call it directly and obtain the identical on-chain deposit commitment while paying zero protocol fee, exactly mirroring the reported `BatcherPaymentService`/`AlignedLayerServiceManager` "core-bypass" fee-evasion pattern.

### Finding Description
`HinkalWrapper.prooflessDeposit()` is documented as "Settles the protocol fee for a proofless deposit, then forwards the deposit itself to Hinkal (which has no fee-taking logic of its own)" [1](#0-0) . It calls `_settleFee(feeStructure)` to transfer `feeStructure.feeAmount` (ETH or ERC20) to `feeStructure.feeRecipient` before forwarding to `IHinkal(hinkal).prooflessDeposit(...)` [2](#0-1) .

However, `Hinkal.prooflessDeposit()` itself has no `msg.sender == hinkalWrapper` (or any equivalent) restriction — it is declared `public payable` and only calls `hinkalHelper.performProoflessDepositChecks(...)` before pulling tokens and creating commitments [3](#0-2) . The delegated check function only validates array-length consistency and non-zero amounts/encrypted outputs — it performs no fee or caller-origin validation whatsoever [4](#0-3) .

Because `Hinkal.prooflessDeposit()` is directly callable by any EOA, a user can bypass `HinkalWrapper` entirely, calling `Hinkal.prooflessDeposit()` with the same `erc20Addresses`, `amounts`, `stealthAddressStructures`, and `onChainEncryptedOutputs` arguments, producing the exact same valid on-chain UTXO commitments [5](#0-4)  without ever paying the `feeStructure.feeAmount` that would otherwise go to `feeStructure.feeRecipient`.

This is the direct analog of the external report's finding: `BatcherPaymentService.createNewTask()` collects `feePerProof` before forwarding to the unauthenticated `AlignedLayerServiceManager.createNewTask()`, allowing fee evasion by calling the core function directly. Here, `HinkalWrapper.prooflessDeposit()` plays the role of the fee-collecting wrapper, and `Hinkal.prooflessDeposit()` plays the role of the unguarded core function.

### Impact Explanation
This breaks the intended fee equality: the protocol/fee recipient is guaranteed `feeStructure.feeAmount` per deposit only if users go through `HinkalWrapper`, but nothing enforces that path. Any user can permanently deny the protocol/fee recipient its due fee for every proofless deposit by calling `Hinkal.prooflessDeposit()` directly, resulting in **permanent loss of protocol fee revenue** — matching the "High: theft or permanent freezing of protocol/relay fees" impact category. The deposit itself remains internally consistent (token pulled == commitment created), so no shielded-pool insolvency results; the loss is isolated to the fee income stream.

### Likelihood Explanation
Likelihood is high: `Hinkal.prooflessDeposit()` is a `public` function on the main contract, requires no special permissions, proof, or signature, and any rational user wanting to avoid the fee would simply call it directly instead of going through `HinkalWrapper`. No privileged role or race condition is needed.

### Recommendation
Restrict `Hinkal.prooflessDeposit()` (or the underlying `performProoflessDepositChecks`) so that it can only be invoked via `HinkalWrapper`, e.g., add a caller check (`require(msg.sender == prooflessWrapper)`) similar to the existing `onlyHinkal` pattern used elsewhere in `HinkalHelper.sol`, or move the fee-settlement logic into `Hinkal.sol` itself so it cannot be bypassed by calling the core function directly.

### Proof of Concept
1. Attacker observes the `ProoflessFeeStructure` normally required by `HinkalWrapper.prooflessDeposit()` (fee token, amount, recipient).
2. Instead of calling `HinkalWrapper.prooflessDeposit(...)`, the attacker calls `Hinkal.prooflessDeposit(erc20Addresses, amounts, stealthAddressStructures, onChainEncryptedOutputs, createBlockedUtxos, orderId)` directly on the `Hinkal` contract, supplying the same deposit parameters they would have used with the wrapper.
3. `Hinkal.prooflessDeposit()` executes `performProoflessDepositChecks`, pulls the deposit tokens from the attacker, and creates the identical on-chain commitments [6](#0-5)  — with zero fee paid to `feeStructure.feeRecipient`, since `_settleFee` in `HinkalWrapper.sol` was never invoked.
4. The attacker obtains a valid shielded deposit UTXO indistinguishable from one made through the wrapper, having evaded the protocol fee entirely.

    function _settleFee(
        ProoflessFeeStructure calldata feeStructure
    ) internal returns (uint256 ethForHinkal) {
        ethForHinkal = msg.value;
        if (feeStructure.feeToken == address(0)) {
            require(
                msg.value >= feeStructure.feeAmount,
                "insufficient ETH for fee"
            );
            ethForHinkal = msg.value - feeStructure.feeAmount;
            if (feeStructure.feeAmount > 0) {
                transferETH(feeStructure.feeRecipient, feeStructure.feeAmount);
            }
        } else if (feeStructure.feeAmount > 0) {
            transferERC20TokenFrom(
                feeStructure.feeToken,
                msg.sender,
                feeStructure.feeRecipient,
                feeStructure.feeAmount
            );
        }
    }

    function _createProoflessDepositCommitments(
        address[] calldata erc20Addresses,
        uint256[] calldata amounts,
        StealthAddressStructure[] calldata stealthAddressStructures,
        bytes[] calldata onChainEncryptedOutputs
    ) private {
        uint256 length = erc20Addresses.length;
        OnChainCommitment[]
            memory onChainCommitmentsArray = new OnChainCommitment[](length);

        for (uint256 i = 0; i < length; i++) {
            onChainCommitmentsArray[i] = createOnchainCommitment(
                UTXO({
                    amount: amounts[i],
                    erc20Address: erc20Addresses[i],
                    stealthAddressStructure: stealthAddressStructures[i],
                    timeStamp: block.timestamp
                }),
                onChainEncryptedOutputs[i]
            );
        }

        insertCommitments(
            new uint256[][](0), // off-chain commitments are empty
            new bytes[][](0), // off-chain encrypted outputs are empty
            onChainCommitmentsArray,
            new bool[](0) // on-chain creation is empty
        );
    }

        address[] calldata erc20Addresses,
        uint256[] calldata amounts,
        StealthAddressStructure[] calldata stealthAddressStructures,
        bytes[] calldata onChainEncryptedOutputs
    ) external view onlyHinkal {

            amounts.length == erc20Addresses.length &&
                amounts.length == stealthAddressStructures.length &&
                amounts.length == onChainEncryptedOutputs.length,
            "amounts length must match erc20Addresses, stealthAddressStructures, onChainEncryptedOutputs length"
        );

        require(
            erc20Addresses.length <= MAX_LEAVES_PD,
            "no more than MAX_LEAVES_PD entries allowed"

            require(
                onChainEncryptedOutputs[i].length > 0,
                "Missing encrypted output for on-chain commitment"
            );
            require(amounts[i] > 0, "Amount must be greater than zero");
        }
    }
