### Title
Webhook `shop` identity field is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content from the raw body only, but exposes a separate `shop` accessor sourced from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never included in the signed payload. `Registry.process` trusts this unauthenticated `shop` value and forwards it to the app's webhook handler as if it were verified, breaking the binding `shop authenticated == shop delivered to handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` verifies the HMAC solely over `to_signable_string`, i.e., the raw body: [2](#0-1) 

The `shop` value, however, comes straight from an HTTP header that is not part of the signed content: [3](#0-2) [4](#0-3) 

`Registry.process` checks the HMAC once (over the body), then unconditionally forwards `request.shop` into `WebhookMetadata`, which the host app's `WebhookHandler#handle` consumes as the trusted tenant identifier: [5](#0-4) [6](#0-5) 

Because Shopify signs webhooks with the app's single `client_secret` (the same secret is used for every shop that installs the app, not a per-shop secret) and `to_signable_string` only covers the JSON body, any body+HMAC pair that is valid for one shop's webhook delivery is also a mathematically valid HMAC for that same body regardless of which `shop-domain` header accompanies it. This is the exact bug class described in the report: a field acted upon by the application (`shop`) is not bound by the field the HMAC actually authenticates (`raw_body`), i.e. the check `hmac_valid(raw_body) == shop_is_authentic` does not hold.

### Impact Explanation
An unprivileged attacker who has installed the target app on their own Shopify shop can legitimately receive a genuine, correctly-HMAC-signed webhook from Shopify for their own shop's events. Because the HMAC check performed by this gem is oblivious to the `shop-domain` header, the attacker can replay that valid `(raw_body, hmac)` pair directly against the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with an arbitrary victim shop's domain. `HmacValidator.validate` will still pass (it never looks at `shop`), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-controlled) body originated from the victim tenant. Any host application that uses `WebhookMetadata#shop` to resolve tenant context, look up a session, or write/redact tenant data (e.g., `customers/redact`, `shop/redact`, `orders/create`) will process attacker-supplied data under the wrong tenant's identity — a cross-tenant data-injection/confusion primitive rooted entirely in this gem's webhook verification logic.

### Likelihood Explanation
Any Shopify Partner/developer can freely create a development store and install an app that supports webhooks, obtaining as many genuine signed webhook bodies for arbitrary self-controlled topics as they like, at no cost and with no privileged credentials. Forging the `shop-domain` header on a direct HTTP POST to the app's own public webhook route requires no secret at all. The only variable outside the attacker's control is the exact JSON body content Shopify chooses to send for a given topic, but several mandatory/simple topics (e.g., `customers/data_request`, `shop/redact`) have small, attacker-influenceable payloads.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values into the signable content used for HMAC verification, or independently verify that the `shop-domain` header matches a shop value embedded in and covered by the signed body/metadata Shopify provides. At minimum, `Utils::HmacValidator`/`Webhooks::Request` should not allow header-only fields that identify the tenant to bypass the cryptographic check, and `Registry.process` should not pass an unauthenticated `shop` field to handlers as though it were verified.

### Proof of Concept
1. Attacker creates Shop A, installs the target app, and configures a webhook subscription for a topic they control the payload of (or observes an existing one).
2. Shopify delivers a real webhook POST to the app: `raw_body = B`, header `x-shopify-hmac-sha256 = HMAC(app_secret, B)`, header `x-shopify-shop-domain = shop-a.myshopify.com`.
3. Attacker captures this exact request, then re-sends it directly to the app's public webhook route, changing only `x-shopify-shop-domain` to `shop-victim.myshopify.com`.
4. `Utils::HmacValidator.validate` ( [7](#0-6) ) recomputes `HMAC(app_secret, B)` and it matches — validation succeeds.
5. `Registry.process` ( [5](#0-4) ) invokes the handler with `WebhookMetadata(shop: "shop-victim.myshopify.com", body: B, ...)`, even though body `B` actually originated from Shop A, not Shop-victim.

          received_signature = verifiable_query.hmac
