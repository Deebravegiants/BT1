### Title
Truncated ERC20→local decimal conversion in `pallet-hyper-fungible-token` silently burns bridged funds with no matching credit - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`convert_to_balance` in `pallet-hyper-fungible-token` performs an integer division to rescale an arbitrary, user-controlled EVM (ERC20) amount down to the pallet's local balance precision. Any remainder from that division is dropped with no accounting for it, no revert, and no dust-tracking mechanism — mirroring the exact root cause of the reported "Precision Truncation on Stake" bug (a value crossing a decimal-precision boundary is floor-divided and the truncated remainder is unrecoverable, causing a permanent mismatch between what was locked/burned on one side and what is credited on the other).

### Finding Description
`convert_to_balance` divides the incoming ERC20 `U256` amount by `10^(erc_decimals - local_decimals)` with no check that the amount is evenly divisible: [1](#0-0) 

This function is invoked directly in `on_accept` (crediting a beneficiary from an incoming cross-chain post) and in `on_timeout` (refunding a sender), using the `Precisions` map value configured per-asset/per-chain and an arbitrary `message.amount` decoded straight out of the untrusted request body: [2](#0-1) 

The `message.amount` value originates from an unprivileged EVM caller of `HyperFungibleToken`/`BridgeToken.send()` — an ordinary user picks any `uint256 amount`, which is burned/escrowed exactly on the EVM side, then relayed as an ISMP `PostRequest` and delivered by any relayer to `pallet-hyper-fungible-token::on_accept`. If that amount is not a clean multiple of `10^(erc_decimals - local_decimals)` (registration only enforces `erc_decimals >= local_decimals`, never that decimals differences yield "safe" amounts, and `register_token`/`update_token` allow arbitrarily large decimal gaps), the fractional remainder is silently discarded by `convert_to_balance`'s floor-division. In the degenerate case where the local asset has fewer decimals than the ERC20 side by enough orders of magnitude (e.g. local `decimals = 0`, ERC decimals `= 18`), any amount under `10^18` is burned on the EVM side yet mints/credits `0` on the substrate side — a full, permanent loss of the bridged funds, not just "dust." The reverse direction (`convert_to_erc20`, used in `send()`) multiplies rather than divides, so it never loses precision — the vulnerability is one-directional, exactly analogous to the reported `_distributeStake`/`truncatedAmount` issue where only one leg of the accounting (the deposit direction) suffered non-reversible truncation.

### Impact Explanation
Any unprivileged EVM sender who dispatches a `HyperFungibleToken`/`BridgeToken` cross-chain send with an amount not aligned to the configured decimal-scaling factor causes an unrecoverable loss: tokens are burned/escrowed on the source chain, but the destination pallet mints/credits strictly less (potentially zero) with no compensating mechanism, no dust ledger, and no way to redeem the difference. This is a permanent freezing/loss of user funds triggered from a fully unprivileged path (message dispatch + relay + delivery), matching the "concrete... permanent freezing of funds" bar. Severity scales with the configured decimal gap between the local asset and the EVM asset — for large gaps (as intentionally allowed by `register_token`'s `erc_decimals >= local_decimals` check with no upper bound), entire transfers below the scaling factor can be lost outright, which is a High-severity systemic accounting break rather than negligible dust.

### Likelihood Explanation
High: no privilege is required. Any user can call `send()` on the EVM-side `HyperFungibleToken`/`BridgeToken` contract with an amount they choose freely; nothing on the EVM side or in `pallet-hyper-fungible-token::on_accept`/`on_timeout` validates or enforces amount alignment to `10^(erc_decimals-local_decimals)` before or after the divide. It happens on every misaligned transfer, not just an edge case triggered by prior buffer-state drift, so it is arguably easier to trigger than the original HYPE-staking bug.

### Recommendation
- In `convert_to_balance`, reject (revert the ISMP call / return an error) any amount whose remainder modulo `10^(erc_decimals-local_decimals)` is non-zero, rather than silently truncating.
- Alternatively, track the truncated remainder explicitly (e.g., a per-asset "dust" storage item) and expose an governance/permissionless mechanism to reconcile or refund it, instead of dropping it.
- Enforce at `register_token`/`update_token` time that `erc_decimals - local_decimals` stays within a bound that keeps rounding losses negligible relative to typical transfer sizes, and document/require senders to align amounts client-side.
- Add symmetry checks/tests (as already exist for the EVM `IntentGatewayV2`'s explicit `DustCollected` dust-accounting pattern) so any inevitable rounding is tracked rather than silently discarded, consistent with how `IntentGatewayV2.sol` already handles dust explicitly elsewhere in this codebase.

### Proof of Concept
Given a registered asset with `local_decimals = 0` and `erc_decimals = 18` (a valid configuration under the existing `ensure!(config.decimals >= local_decimals, ...)` check in `register_token`):
1. Attacker calls `HyperFungibleToken.send()` on the EVM chain with `amount = 999_999_999_999_999_999` (18-decimal wei, i.e., just under 1 whole unit). This is burned exactly on the EVM side. [3](#0-2) 
2. The ISMP request is relayed and delivered to `pallet-hyper-fungible-token::on_accept`, which calls `convert_to_balance(U256::from(999_999_999_999_999_999), 18, 0)`. [4](#0-3) 
3. `convert_to_balance` computes `value / 10^18 = 0`, so `amount = 0` local units are minted/transferred to the beneficiary — the entire burned value is permanently lost with no error, no revert, and no recorded dust.

Note: I could not locate an explicit runtime configuration file specifying concrete `local_decimals`/`erc_decimals` values used in production registrations (this would confirm how large the real-world decimal gap is for currently deployed assets); the index may not include that runtime config, and a Devin session with full repository access would be needed to confirm exact production parameters.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
