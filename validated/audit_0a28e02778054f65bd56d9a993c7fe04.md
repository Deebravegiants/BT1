### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values used by the registry to route and dispatch webhook data are read from unauthenticated headers. Because Shopify apps share a single `api_secret_key` across every installed shop, any tenant that legitimately receives a webhook (with a valid HMAC over the body) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header of a different shop. `Utils::HmacValidator.validate` will still report success, and `Registry.process` will hand the attacker-chosen `shop` value to the app's webhook handler as if it came from Shopify for that shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read straight from request headers, entirely outside the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the received HMAC only against `to_signable_string` (the body): [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`) to build the data passed to the app's handler, with no additional binding check between the verified bytes and the parsed shop identity: [4](#0-3) 

The identity binding that should hold is:

`shop_verified_by_hmac == shop_used_by_handler`

But in reality:

`shop_verified_by_hmac = ∅ (HMAC only covers @raw_body)`
`shop_used_by_handler = request.shop (unauthenticated header)`

Since `api_secret_key` is the same secret for every shop that installs a given app (it is the app's client secret, not a per-shop secret), a low-privileged attacker who simply installs the app on their own store receives genuine webhooks with a valid `X-Shopify-Hmac-Sha256` computed with that shared secret. The attacker can then replay the identical `raw_body` + `hmac` header pair to the app's public webhook endpoint, but with the `X-Shopify-Shop-Domain` (and, if desired, `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header rewritten to name a victim shop. `HmacValidator.validate` still succeeds because it never inspects the shop header, and `Registry.process` dispatches the forged event to the handler tagged with the victim's shop domain.

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is supposed to enforce: any shop able to install the app (an "unprivileged" tenant relative to other merchants) can inject fabricated webhook events that the host application will process as authentic events originating from an arbitrary other shop. Depending on how the host application's webhook handler uses `WebhookMetadata#shop` (e.g., to look up that shop's stored access token/session, update per-shop records, or trigger per-shop side effects), this enables cross-tenant data injection/corruption — a Critical-impact cross-tenant access issue per the assessment criteria.

### Likelihood Explanation
Likelihood is high for any app that: (1) is installable by arbitrary merchants (i.e., not a single-tenant custom app), and (2) has at least one other shop's webhook topic/body content that is guessable, replayable, or previously observed by the attacker (e.g., a topic with static or predictable payloads such as `app/uninstalled`, `shop/update`, or any webhook where the attacker can trigger the same body content in their own store and then relabel it). No access token, `api_secret_key`, or privileged account is required — only the ability to install the app on one's own shop and send raw HTTP requests to the app's public webhook endpoint.

### Recommendation
Bind the shop (and topic) identity into the value that is HMAC-verified, or otherwise cryptographically tie the verified body to the specific tenant before dispatch:
- Include the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`) header value as part of the signable string used by `HmacValidator`, matching how Shopify's own delivery is scoped per shop, or
- Require the host application to independently confirm that the `shop` in `WebhookMetadata` corresponds to a shop it expects for this specific `webhook_id`/subscription (e.g., cross-check against a per-shop webhook registration record) rather than trusting the header value implicitly once `HmacValidator.validate` passes.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`, receiving normal webhook traffic signed with the app's single, shared `api_secret_key`.
2. Attacker triggers (or waits for) a webhook, e.g. `orders/create`, and captures the raw POST body and its `X-Shopify-Hmac-Sha256` header — both valid and verifiable via `HmacValidator.validate`.
3. Attacker resends the exact same body and HMAC header to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` at [5](#0-4) 
 which succeeds because only the body bytes are checked.
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)`, causing the app to process attacker-supplied data as though it came from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
