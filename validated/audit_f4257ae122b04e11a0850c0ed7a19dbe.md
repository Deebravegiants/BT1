Audit Report

## Title
JWT replay-protection race condition allows a single-use gateway token to authorize multiple concurrent requests - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

## Summary
`WorkflowMetadataHandler.Authorize` checks whether a JWT `jti` has been used via `isReplay()` under an `RLock`, then performs additional workflow/key-authorization work, and only afterward calls `recordUsage()` under a separate `Lock` to mark the `jti` as spent. Because the check and the record are two independent, non-atomic critical sections, two concurrent `Authorize` calls carrying the same JWT can both pass the `isReplay` check before either calls `recordUsage`, allowing a token intended to authorize exactly one request to authorize two (or more) concurrent requests.

## Finding Description
`Authorize` verifies the JWT signature, then calls `h.jwtCache.isReplay(claims.ID)`, which takes `cache.mu.RLock()`, checks map membership, and returns: [1](#0-0) 

Only after further workflow-ID lookup and signer-authorization checks does it call `h.jwtCache.recordUsage(claims.ID)`, which separately acquires `cache.mu.Lock()` and writes the entry: [2](#0-1) [3](#0-2) 

No lock or synchronization is held across the entire "check → authorize → record" sequence, so this is a textbook check-then-act race. The separate JSON-RPC-level dedup in `httpTriggerHandler.HandleUserTriggerRequest`/`setupCallback` keys on the outer JSON-RPC request ID, not the JWT `jti`, and thus provides no protection against replaying the same token with two different request IDs concurrently. `HandleUserTriggerRequest` calls `authorizeRequest` (which invokes `Authorize`) before rate-limiting and callback setup, confirming the call ordering: validate → resolve workflow ID → authorize → rate limit → callback: [4](#0-3) 

The exploit path is reachable by any unprivileged external client capable of sending two HTTP trigger requests to the gateway with the same JWT and different JSON-RPC request IDs; no privileged access is required.

## Impact Explanation
This breaks the intended "one JWT authorizes exactly one workflow trigger" guarantee, enabling an unprivileged attacker holding a single, previously issued token to trigger duplicate concurrent workflow executions instead of being rejected with "JWT token has already been used." This maps to an in-scope impact — unauthorized/duplicate job run via gateway request path — since replay protection meant to gate execution can be bypassed by winning a race, with no operator or admin access needed.

## Likelihood Explanation
The race window spans the time between `isReplay()` and `recordUsage()` calls in `Authorize`, which includes JWT-signature verification and map lookups for workflow/key authorization — a real, non-trivial window. Firing two requests with the same JWT (differing only in the outer JSON-RPC request ID, which the JSON-RPC-level `setupCallback` dedup does not protect against since it keys on request ID, not `jti`) is straightforward for any client with one valid token, making the race practically achievable and repeatable.

## Recommendation
Make the "check jti unused" and "mark jti used" operations atomic under a single critical section, e.g., introduce a `jwtReplayCache.CheckAndRecord(jti)` method that acquires `mu.Lock()` once, checks for existence, and inserts the entry in the same critical section (mirroring the pattern already used correctly in `vault.RequestReplayGuard.CheckAndRecord`). Call this atomic check-and-set at the very start of `Authorize`, before any further authorization-dependent work, so only the first of two concurrent callers for a given `jti` can proceed.

## Proof of Concept
1. Register a workflow and obtain one valid JWT for it (mirroring the setup in `TestHttpTriggerHandler_HandleUserTriggerRequest`'s "duplicate JWT token and request ID" subtest).
2. Construct two `jsonrpc.Request[json.RawMessage]` HTTP-trigger messages with different `req.ID` values but the identical JWT `Auth` token (same `jti`).
3. Dispatch both concurrently — e.g., from two goroutines calling `httpTriggerHandler.HandleUserTriggerRequest` (or directly `WorkflowMetadataHandler.Authorize`) at the same time.
4. Observe (e.g., with `go test -race` and a small artificial delay injected between `isReplay` and `recordUsage`, or via repeated runs) that both calls can pass `isReplay` before either calls `recordUsage`, resulting in both being authorized and both triggering workflow execution — instead of the second being rejected with "JWT token has already been used."

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
