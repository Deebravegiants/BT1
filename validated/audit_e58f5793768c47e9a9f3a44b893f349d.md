## Title
Webhook Shop Attribution Not Covered by HMAC Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The webhook HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body, not the `shop-domain` header. Since a single app-wide `client_secret` (`Context.api_secret_key`) is used to sign webhooks for *every* merchant that installs the app, an attacker who legitimately installs the app on their own store can capture one of their own genuinely-signed webhook deliveries (valid body + HMAC) and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to point at a victim shop. The signature check still passes because it never binds the signature to the shop identity, so the host application's webhook handler processes the payload as if it came from the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is read from a separate, unsigned header: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC strictly against `to_signable_string`, i.e., the body alone, using the app's `api_secret_key`: [3](#0-2) 

`Registry.process` accepts the request once this body-only HMAC passes, and then dispatches to the handler using `request.shop` — the unauthenticated header value — as the tenant identity: [4](#0-3) 

Because `Context.api_secret_key` is the app's single `client_secret`, shared across every shop that installs the app (it is not a per-shop key), any merchant who installs the app can trigger benign webhooks to themselves (Shopify signs these with the same shared secret), capture the resulting `(raw_body, x-shopify-hmac-sha256)` pair, and resend that exact pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header value. `HmacValidator.validate` will accept it because the header is not part of the signed content — the equality `signature-covered bytes == shop attributed to the event` is broken: the HMAC verifies the body was signed by the app's secret, but does not bind that body to the specific shop the request now claims to be from.

### Impact Explanation
This breaks the tenant-identity binding for inbound webhooks. The application's webhook handler will process the attacker's captured payload/topic as if it originated from a different (victim) shop, per `WebhookMetadata.new(... shop: request.shop ...)`. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up/update the victim's session-scoped state, orders, inventory, or app-installation records), this results in cross-tenant data injection/corruption without ever presenting a valid access token for the victim shop — a cross-tenant access issue.

### Likelihood Explanation
An attacker only needs to be an ordinary, unprivileged merchant who installs the app once (no special credentials, no access token or `client_secret` theft required) to obtain a valid `(body, hmac)` pair from their own store's webhook traffic, then replay it against the shared webhook endpoint with a forged `shop-domain` header. This is fully reachable using only this gem's own `Webhooks::Request` / `Webhooks::Registry` code path.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-covered content, or otherwise cryptographically bind the verified header value to the signed body before trusting `request.shop`, e.g. by validating that the shop matches a shop associated with the topic/webhook subscription recorded at registration time, or by incorporating `shopify-shop-domain` into `to_signable_string`.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com`; Shopify sends a genuine webhook (e.g., `orders/create`) signed with the app's shared `client_secret`, producing `raw_body` and `x-shopify-hmac-sha256`.
2. Attacker captures this `(raw_body, hmac)` pair.
3. Attacker POSTs this exact `raw_body` and `hmac` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates only against `raw_body` [5](#0-4)  — validation succeeds.
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload/HMAC never originated from or was bound to that shop.
