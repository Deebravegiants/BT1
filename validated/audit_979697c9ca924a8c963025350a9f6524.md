### Title
Missing account-length validation before unchecked `Loadable::load_mut` transmute in `process_initialize2` - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` deserializes `AmmInfo` and `TargetOrders` using the unchecked `Loadable::load_mut` helper instead of the `load_mut_checked` variant used everywhere else in the program (Deposit, Withdraw, Swap, WithdrawPnl). `Loadable::load_mut` transmutes the raw account byte buffer directly into the fixed-size `Pod` struct with `from_bytes_mut` and never validates that `account.data_len()` equals `size_of::<Self>()` before doing so [1](#0-0) . This mirrors the root cause of CVE-2017-6387: a parser that transmutes/reads a fixed-size structure out of attacker-influenced data without first checking that the buffer is large enough, leading to an out-of-bounds condition and a crash.

### Finding Description
Every other privileged-account loader in the program enforces a strict size check before casting the account bytes, e.g. `AmmInfo::load_mut_checked` and `TargetOrders::load_mut_checked` both explicitly compare `account.data_len()` against `size_of::<Self>()` and return `AmmError::ExpectedAccount` on mismatch [2](#0-1) [3](#0-2) .

`process_initialize2`, however, calls the bare `load_mut` for both `AmmInfo` and `TargetOrders`, skipping that size check entirely: [4](#0-3) [5](#0-4) 

The only checks performed before `TargetOrders::load_mut` are an owner check (`amm_target_orders_info.owner == program_id`) — there is no check that the account's data length matches `size_of::<TargetOrders>()` [6](#0-5) . `load_mut` itself just does `RefMut::map(account.try_borrow_mut_data()?, |data| from_bytes_mut(data))`, which is a `bytemuck` cast that panics/aborts if the byte slice length does not exactly match `size_of::<TargetOrders>()` (or `size_of::<AmmInfo>()`) [7](#0-6) .

Since `amm_target_orders_info` and `amm_info` are both accounts supplied in the transaction's account list by the caller (the pool creator initiating `Initialize2`), the caller controls which account is passed at these positions. If, prior to (or in place of) the associated-account creation step, an account owned by the program but with a mismatched data length reaches this deserialization path, the unchecked transmute will panic, aborting the transaction — the same denial-of-service class as CVE-2017-6387's unchecked `dex_loadcode` parsing that crashes on malformed length data.

### Impact Explanation
A panic during `Initialize2` aborts the whole instruction. Because this codepath already performed real token transfers into the coin/pc vaults and can be reached with attacker-influenced account state before the fatal transmute, a wrong-sized owned account reaching `load_mut` turns a pool-creation attempt into a guaranteed-crash instruction, which is a reachable denial-of-service via account-length mismatch. This is a weaker but structurally identical instance of the reported bug class (unchecked length before struct-casting untrusted data), and stands in contrast to the size-validated `load_mut_checked` path used by every fund-moving instruction (Deposit/Withdraw/Swap/WithdrawPnl).

### Likelihood Explanation
Medium-to-low. I could not fully confirm within available tool calls whether `generate_amm_associated_account` (the CPI helper that creates the `TargetOrders`/`AmmInfo` accounts before these unchecked loads) rejects an already-existing, wrong-sized, program-owned account or forces a fresh allocation of the exact size every time; the file read for that function's body was truncated before I could inspect it. If it does not strictly re-validate size/ownership pre-conditions on an already-existing account (e.g., a griefer could pre-create/rent a PDA at that seed with a different owner/size in the same slot before the legitimate `Initialize2` lands, or reuse of a stale, differently-sized account from an incompatible earlier program version), the unchecked `load_mut` becomes directly reachable by a single attacker-controlled transaction.

### Recommendation
Replace both `AmmInfo::load_mut(&amm_info)` and `TargetOrders::load_mut(amm_target_orders_info)` in `process_initialize2` with their `_checked` counterparts (`load_mut_checked`), which already exist in `state.rs` and enforce `account.data_len() == size_of::<Self>()` plus ownership, consistent with every other instruction handler in `processor.rs`.

### Proof of Concept
1. Craft an `Initialize2` transaction where the account passed as `amm_target_orders_info` (or `amm_info`) is owned by the Raydium AMM `program_id` but was allocated with a data length different from `size_of::<TargetOrders>()` (or `size_of::<AmmInfo>()`) — e.g., due to a race with `generate_amm_associated_account`'s creation step or reuse of a stale/incompatible account at the derived PDA.
2. Submit the transaction; execution reaches line 844 / line 964 in `program/src/processor.rs`.
3. `Loadable::load_mut` (`program/src/state.rs:40-45`) calls `from_bytes_mut` on a buffer whose length does not match the target struct size, causing a `bytemuck` panic and aborting the instruction after prior side effects (fee charge, token transfers) were already invoked, without the graceful `AmmError::ExpectedAccount` returned by `load_mut_checked` elsewhere in the program.

        account: &'a AccountInfo,
        program_id: &Pubkey,
        owner: &Pubkey,
    ) -> Result<RefMut<'a, Self>, ProgramError> {
        if account.owner != program_id {
            return Err(AmmError::InvalidTargetAccountOwner.into());
        }
        if account.data_len() != size_of::<Self>() {
            return Err(AmmError::ExpectedAccount.into());
        }
        let data = Self::load_mut(account)?;
        if data.owner != *owner {
            return Err(AmmError::InvalidTargetOwner.into());
        }
        Ok(data)
    }
