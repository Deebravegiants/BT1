Based on my research, the closest analog to the PoolTogether access-control flaw exists in the Orb Relay client's message-handling loop, where one message type bypasses the sender-identity check that every other message must pass.

### Title
Unauthenticated `RequestState` request bypasses sender-identity check and triggers state replay - (File: `orb-relay-client/src/client.rs`)

### Summary
The relay client's `main_loop` enforces that any received `RelayPayload` must originate from the expected session counterpart (`src.id == self.config.dst_id`) before it is buffered and processed. However, one message type — `self_serve::app::v1::RequestState` — is handled in a special branch that runs *before* this identity check, meaning it is honored regardless of who sent it.

### Finding Description
In `orb-relay-client/src/client.rs`, the `PollerAgent::main_loop` function processes incoming `RelayPayload` messages from the backend relay stream: [1](#0-0) 

The logic is:
```
if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...   // no src check
} else if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source...");
} else {
    self.handle_message(...).await?;                     // src already validated
}
```

Every other payload type is gated by `src.id != self.config.dst_id`, which is the mechanism that binds a session's Orb and App together (analogous to the `rngAuctionRelayer` check that should gate `rngComplete`). The `RequestState` arm is evaluated first and skips that identity comparison entirely, so it will echo back `self.last_message` — the last outbound protocol message for that session (e.g., `AnnounceOrbId`, `CaptureStarted`, `SignupEnded`, or other self-serve session-state messages) — to *any* sender on the stream, not just the legitimate paired counterpart identified by `dst_id`.

This mirrors the root cause of the reference finding: a privileged/side-effecting handler omits the authorization check that parallel code paths in the same function correctly apply, letting an unauthorized party trigger behavior meant only for a specific, verified counterpart.

### Impact Explanation
An entity able to reach the relay stream for a session but not equal to the expected `dst_id` can force replay of the session's last message. Because `self_serve` self-serve signup flow uses this channel to coordinate biometric-capture start/end and QR-derived session identifiers between the physical Orb and the user's app (see `orb_relay_announce_orb_id` and `SignupEnded`/`CaptureStarted` usage in `src/plans/mod.rs`), an unauthorized party could obtain a copy of the latest session-state message intended for the legitimate paired participant, producing a cross-signup state disclosure/bleed within the self-serve signup protocol. This is a narrower blast radius than the PoolTogether fund-theft case (no direct biometric payload leaks, since actual capture data flows through the separate PCP/upload pipeline), but it is a genuine omission of the same authorization check pattern within the same function.

### Likelihood Explanation
Exploitation requires the attacker to already be able to open a relay stream connection tied to the session (i.e., pass the relay server's `ConnectRequest`/auth-token or ZKP verification) but present a mismatched `src.id`/`dst_id` pairing when sending `RequestState`. Whether that is achievable depends on server-side enforcement not visible in this repository (the relay server, not `orb-core`), so likelihood is moderate/uncertain from the client code alone, but the client-side logic itself provides no defense-in-depth for this specific message type where every other message type is protected.

### Recommendation
Move the `src.id != self.config.dst_id` check before the `RequestState` branch (or fold `RequestState` handling into the same `else` branch after the identity check), so that state-replay requests are only honored from the verified session counterpart, consistent with how all other payload types are already handled:

```rust
if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: {:?}", src.id);
} else if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else {
    self.handle_message(...).await?;
}
```

### Proof of Concept
1. A third party obtains (or is issued) valid relay credentials/token for the backend relay endpoint but is not the legitimate `dst_id` for a given `orb_id`/`session_id` pair.
2. The third party sends a `self_serve::app::v1::RequestState` payload on the stream, with any `src`/`dst` values.
3. In `main_loop` ( [2](#0-1) ), the `RequestState::matches` branch fires immediately and `self.last_message.clone()` (the session's last outgoing message, e.g. containing session/state info) is sent back to the requester — without ever reaching the `src.id != self.config.dst_id` check that guards every other message type.
