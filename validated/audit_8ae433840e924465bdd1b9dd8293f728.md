### Title
Webhook shop-domain attribution is not covered by the HMAC, allowing tenant-spoofing of otherwise-genuine webhook payloads - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` only verifies the HMAC over the raw request body before dispatching a webhook to the registered handler, but the `shop` value it hands to that handler is taken from an unsigned HTTP header, so the "authenticated bytes" and the "tenant identity" are two different, independently-controlled pieces of data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, completely independent of the signed string: [2](#0-1) 

`Registry.process` validates the HMAC of the request and then immediately builds `WebhookMetadata` using `request.shop`, handing it to the application's handler as the trusted tenant identifier: [3](#0-2) 

`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it against the `hmac` field — for webhooks this is `HMAC(secret, raw_body)` only: [4](#0-3) 

The equality the gem is implicitly asserting to the host application is:
`shop_the_handler_trusts == shop_that_produced_the_signed_bytes`

but what is actually proven is only:
`HMAC(secret, raw_body) == received_hmac`

Since `shop-domain` is not part of `raw_body` nor part of `to_signable_string`, the two sides are not bound together. Anyone who possesses one genuine, validly-signed webhook delivery (body + HMAC) for their own shop — obtainable by any merchant who installs the app on their own store and inspects/replays their own webhook deliveries — can resend that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `Registry.process` will still accept it as HMAC-valid (the body is untouched) and will dispatch it to the handler tagged with the attacker-chosen shop, in `WebhookMetadata#shop`.

### Impact Explanation
If the host application's webhook handler uses `data.shop` (or the equivalent value from `Registry.process`) as the tenant key to route to which merchant's data a webhook update is applied — the common pattern for multi-tenant Shopify apps — an attacker who legitimately controls one installed shop can forge webhook events that are recorded against a different, unrelated shop. This is a cross-tenant integrity/confidentiality violation: an unprivileged user of one tenant can inject or corrupt state attributed to another tenant purely by capturing their own genuine webhook and replaying it with a modified shop header, without needing the app's `client_secret` or any credential belonging to the victim shop.

### Likelihood Explanation
Any merchant installing the app can trigger and observe genuine webhook deliveries and their signature for their own store (e.g., via order/product mutation events, or by inspecting their own webhook endpoint traffic). Modifying an HTTP header on a replayed request requires no cryptographic material and no access to `api_secret_key`. The only precondition is that the host application's handler trusts the `shop` value supplied via `WebhookMetadata` to select the tenant context — a reasonable and common usage pattern given the gem exposes `shop` specifically for that purpose.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) inside the HMAC-signed material, or otherwise cryptographically bind the shop attribute to the payload before it is trusted. At minimum, document prominently that `shop` in `WebhookMetadata` is unauthenticated and must be cross-checked against a shop known to have valid session data / an active app installation before being used as a tenant key, and consider validating it against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` combined with a lookup against known installed/authenticated shops rather than trusting the header value outright.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and observes (or triggers) a genuine webhook delivery: body `B`, header `x-shopify-hmac-sha256: H` (valid for `HMAC(secret, B)`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same request to the app's webhook endpoint, keeping body `B` and hmac header `H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body successfully [5](#0-4) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(secret, B) == H` [6](#0-5) .
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, i.e., the app processes attacker-supplied data as if it came from `victim-shop`, despite the payload having actually been generated for `attacker-shop`.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
