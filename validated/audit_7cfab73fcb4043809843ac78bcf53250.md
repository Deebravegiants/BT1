### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Webhooks::Registry.process` verify the HMAC over the raw request body only. The `shop-domain` header (as well as `topic`, `webhook_id`, `api_version`) that is handed to the app's handler as the identity of the originating shop is never included in the signed material, so anyone who can produce (or capture) a validly-signed body can attach an arbitrary `shop-domain` header and have the app process it as if it belonged to a different tenant.

### Finding Description
`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from unauthenticated HTTP headers with no cryptographic binding to the body or the HMAC: [3](#0-2) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., body-only) before dispatching `request.shop` straight to the app's handler as trusted identity: [4](#0-3) 

The binding that should hold is: `shop_header == shop_that_the_signed_bytes_actually_originated_from`. Because the HMAC only covers `@raw_body`, this equality is never checked — the gem verifies "bytes are validly signed by our secret" but not "these bytes, from this shop, arrived together." Any actor capable of obtaining one validly-signed `(body, hmac)` pair (e.g., a merchant who has legitimately installed the app on their own shop and thus receives real Shopify-signed webhooks for events they can trigger themselves, such as creating a product with attacker-chosen content) can replay that exact `(body, hmac)` pair directly to the app's public webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop. Because `Registry.process` never checks the header against anything derived from the signed bytes, the forged request passes HMAC validation and the handler receives `WebhookMetadata` claiming the victim shop as the source.

### Impact Explanation
This is a cross-tenant identity confusion: an app built on this gem cannot distinguish "signed data for shop A" from "signed data for shop A, replayed under shop B's name." Any downstream logic that trusts `data.shop` (as the documented usage pattern does — see `docs/usage/webhooks.md`, which shows `data.shop` being used directly to key jobs/storage) can be tricked into writing, updating, or acting on data under the wrong shop's account, i.e., cross-tenant access/data corruption without any credential beyond having (or capturing) one legitimately-signed body from any shop, including the attacker's own.

### Likelihood Explanation
Reasonably likely for a low-skill unprivileged attacker: standing up their own free/dev Shopify store and installing the target app gives them a stream of validly HMAC-signed webhook bodies under their own name. They only need to POST that unmodified body with a swapped `shop-domain` header to the app's public webhook route — no secret key, session, or elevated privilege required, since the header is not covered by the signature check.

### Recommendation
Bind the shop (and ideally the topic/webhook id) into the material that is verified, e.g., by including the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` header values in `to_signable_string` (or otherwise cryptographically tying them to the signed payload) so `HmacValidator.validate` fails if any of these values are altered independently of the signed body.

### Proof of Concept
1. Attacker installs the target app on their own dev shop `attacker.myshopify.com` and triggers a webhook event (e.g., `products/create`) with attacker-controlled body content.
2. Shopify sends the legitimate webhook with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and the raw JSON body.
3. Attacker captures this exact `(raw_body, hmac)` pair.
4. Attacker crafts a new HTTP POST to the app's public webhook route, using the same `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against `hmac` — this succeeds because the body was not modified.
6. `Registry.process` dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with `shop == "victim.myshopify.com"` to the app's handler, which processes attacker-controlled data as if it originated from the victim shop: [5](#0-4)
