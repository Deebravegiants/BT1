Confirmed: the webhook HMAC in this gem only signs the raw request body, while the `shop` (and `topic`) values used downstream come from HTTP headers that are entirely outside the signed content.

### Title
Webhook `shop` identity is trusted from an unsigned header while the HMAC only covers the raw body, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `ShopifyAPI::Utils::HmacValidator.validate` computes/verifies the HMAC exclusively against that string. The `shop` (and `topic`) values consumed by `ShopifyAPI::Webhooks::Registry.process` and handed to handlers via `WebhookMetadata` are read from HTTP headers (`shopify-shop-domain`/`x-shopify-shop-domain`) that are never included in the signed payload. This breaks the identity binding `hmac(signed_bytes) == authenticated_shop`: the bytes that are cryptographically verified (the body) are not the bytes that determine which tenant/shop the webhook is attributed to.

### Finding Description
`Registry.process` only checks the body's HMAC before dispatching to the handler with the shop taken from an unsigned header: [1](#0-0) 

The `Request` class exposes `shop` from a raw header, while `to_signable_string`/`hmac` are computed strictly from the body: [2](#0-1) 

`HmacValidator.validate` only ever hashes `verifiable_query.to_signable_string` (the body), never the shop header: [3](#0-2) 

Because the `shop-domain` header is not part of the signed content, any request that carries a **previously-valid `(raw_body, hmac)` pair** — trivially obtainable by an unprivileged user who registers their own free Shopify development store and captures a webhook Shopify sends them — will pass HMAC validation for the app's webhook endpoint **regardless of which `shop-domain` header is attached**. An attacker can therefore replay that valid body/hmac pair while substituting the victim shop's domain in the header, and the gem will report the webhook as authentic for the victim shop.

### Impact Explanation
This is a Critical-class cross-tenant access issue: an app that uses `WebhookMetadata#shop` (as returned by `Registry.process`) to select which merchant's data/session to update will process attacker-supplied data under the wrong tenant's identity, since the gem's own verification does not bind the shop identity to the cryptographic proof. The app is left with no way, using this gem alone, to distinguish "this shop really sent this webhook" from "someone captured any valid webhook and changed the shop header."

### Likelihood Explanation
Obtaining one legitimate `(raw_body, hmac)` pair requires no special privilege — merely creating an unpaid Shopify partner/dev store and receiving any webhook is sufficient, since `api_secret_key` is never needed by the attacker. Sending a crafted HTTP request with attacker-chosen headers directly to a public webhook endpoint is standard unauthenticated internet access. The main constraint is that the replayed body's content must still make sense to the target handler, but for topics such as `app/uninstalled`, `shop/update`, or similar shop-level events with generic bodies, this is easily satisfiable.

### Recommendation
Bind the header-derived identity fields (`shop`, `topic`, `webhook_id`) into the value that is HMAC-verified, or otherwise explicitly document/require host apps to independently re-verify that the `shop` header corresponds to a shop that is expected to be delivering that specific `webhook_id`/topic. At minimum, `Registry.process` should not treat `Utils::HmacValidator.validate(request)` as proof of the `shop` header's authenticity, and downstream consumers should be warned in the docs that only the body — not the shop header — is cryptographically verified.

### Proof of Concept
1. As an unprivileged attacker, register your own Shopify store/app and capture one legitimate webhook delivery, e.g. a `shop/update` POST with body `{"id":123, ...}` and header `x-shopify-hmac-sha256: <valid-hmac-for-body>`.
2. Send a POST request directly to the victim app's webhook endpoint with the exact same raw body and `x-shopify-hmac-sha256` header, but set `x-shopify-shop-domain: victim-shop.myshopify.com` and `x-shopify-topic` to the desired topic.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` [4](#0-3) .
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is `"victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own store [5](#0-4) .
