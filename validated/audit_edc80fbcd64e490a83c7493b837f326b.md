### Title
Webhook `shop` (tenant) identifier is not covered by the HMAC signature, allowing cross-tenant webhook data injection - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the HMAC over the raw request body only, while the `shop` field used to identify which tenant a webhook belongs to is read from an unauthenticated HTTP header. Any actor who can produce one valid `(body, hmac)` pair (e.g., from a webhook fired for their own shop/app installation, since the HMAC secret — `client_secret` — is shared by the app across all its installed shops, not per-shop) can replay that same body+hmac to the app's webhook endpoint with a different `x-shopify-shop-domain`/`shopify-shop-domain` header and have it accepted as valid for an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor, by contrast, is pulled straight from the header without any cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate` only checks the signable string (the body) against the HMAC, never incorporating `shop`, `topic`, `webhook_id`, or `api_version`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build `WebhookMetadata`, which is handed to the host app's `WebhookHandler#handle`: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:
`shop-domain header used for tenant attribution == shop bound inside the HMAC-covered bytes`

But the code only proves:
`HMAC(secret, raw_body) == received_hmac`

with no assertion that `shop-domain header` is cryptographically tied to that body. Because Shopify's `client_secret` (and therefore the webhook signing key) is per-app, not per-shop, a single secret signs webhooks for every shop that has installed the app. Consequently, an attacker who controls one shop where the app is installed can capture a legitimately-signed `(body, hmac)` pair from their own webhook deliveries and replay it to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` calls the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker's body, ...)`.

### Impact Explanation
This breaks the tenant/shop identity boundary the gem is expected to enforce for webhook authenticity: the "verified" bytes (the body) are decoupled from the "trusted" identity (the shop), allowing cross-tenant data injection into a victim shop's account inside the host application (e.g., forged `orders/create`, `app/uninstalled`, or `customers/data_request` payloads being processed as if they came from the victim shop). Depending on what the host app's webhook handlers do with the data (e.g., updating stored order/customer records, revoking access on `app/uninstalled`, or triggering GDPR data workflows), this can lead to cross-tenant state corruption or privilege/state changes on a shop the attacker does not control, matching the "cross-tenant access" impact class.

### Likelihood Explanation
Requires the attacker to (a) have the app installed on a shop they control (a standard, unprivileged installation available to any Shopify merchant/developer), and (b) capture one valid signed webhook payload from their own shop (trivial — they can trigger any subscribed webhook topic themselves, e.g. by placing an order or updating a product). No access to `api_secret_key`, tokens, or the victim's credentials is needed. The only additional requirement is that the app's webhook endpoint is reachable and forwards raw body/headers into `ShopifyAPI::Webhooks::Request` without an out-of-band shop/header binding — which is exactly the documented integration pattern shown in this gem's webhook usage.

### Recommendation
Bind the shop identity to the verified bytes before trusting it:
- Include `shop-domain`, `topic`, and `webhook-id` in the signed/verified material (or require the host app to independently confirm that `shop` corresponds to a shop with an active, stored session/installation before processing), or
- At minimum, document/enforce that `Registry.process` must cross-check `request.shop` against an already-authenticated session store keyed by shop before invoking handlers, rather than trusting the header value implicitly once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (a normal, unprivileged shop signup).
2. Attacker triggers a webhook topic the app subscribes to (e.g. creates an order), receiving from Shopify a request with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker replays the exact same `B` and `H` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb:13-22) succeeds because it only recomputes HMAC over `B`.
5. `Registry.process` (lib/shopify_api/webhooks/registry.rb:188-200) builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body_from_B, ...)` and invokes the host app's handler as if the data legitimately originated from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
