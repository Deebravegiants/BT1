### Title
OAuth callback trusts unsanitized `shop` to build the access-token exchange host, leaking `client_secret` to an attacker-controlled server - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the session used to request the access token directly from `auth_query.shop`, with no call to `Utils::ShopValidator.sanitize!`, unlike the analogous `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb` flows which all sanitize `shop` before using it as a request host.

### Finding Description
`validate_auth_callback` validates the HMAC over the query parameters (`code`, `host`, `shop`, `state`, `timestamp`) via `Utils::HmacValidator.validate(auth_query)` [1](#0-0) , and the signable string is built directly from `auth_query.shop` [2](#0-1) . HMAC validity here only proves that `shop` matches what was signed with `Context.api_secret_key`/`old_api_secret_key` — it says nothing about whether `shop` is a genuine `*.myshopify.com` host.

That unsanitized value is used to build the `Session` and `HttpClient` that then POSTs the app's `client_id`/`client_secret`/authorization `code` to `/admin/oauth/access_token`: [3](#0-2) 

The HTTP client resolves the request host from `session.shop` via `auth_base_uri`, which simply does `"https://#{shop}/admin"` with no domain allowlist check [4](#0-3) .

Compare this to the three other flows that construct a request host from a caller/attacker-influenced `shop` string — they all call `Utils::ShopValidator.sanitize!`, which restricts the host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) before use [5](#0-4) : [6](#0-5) 

The identity binding that is broken: `shop` field verified by HMAC == `shop` host that the access-token request (containing `client_secret`) is sent to. HMAC only proves byte-for-byte integrity of whatever value the OAuth initiator (i.e., the host app calling `begin_auth`) chose to send through the flow; it does not prove that value is a legitimate Shopify shop domain. Since `begin_auth` itself also takes `shop` with no sanitization [7](#0-6)  and uses it to build `auth_base_uri(shop)` for the authorize redirect, an attacker who can influence the initial `shop` value (e.g., via a `login` route that reads `shop` from a request header/param, as shown in the gem's own docs example) can drive the entire flow, including the final token exchange, to a host they control.

### Impact Explanation
If an attacker can supply the `shop` value used to start OAuth (a pattern the docs literally demonstrate: `shop = request.headers["Shop"]` feeding `begin_auth`) [8](#0-7) , the resulting authorize URL and the callback's `shop` param can point to an attacker-controlled host. Because `validate_auth_callback` never restricts `auth_query.shop` to `TRUSTED_SHOPIFY_DOMAINS`, the code+state HMAC-consistency check passes for any host the initiator chose, and the subsequent `client.request(...)` POST — carrying `client_secret` in the body — is sent to `https://#{attacker-controlled-shop}/admin/oauth/access_token`. This is SSRF carrying the app's `client_secret`, matching the "High" impact criterion (SSRF with the app's credentials / credential leakage).

### Likelihood Explanation
Exploitability depends entirely on whether the host application passes an untrusted `shop` value into `begin_auth`/`validate_auth_callback` without its own validation. The gem's documentation itself shows exactly this pattern (`shop = request.headers["Shop"]`), so a host app following the documented example verbatim is exposed. This is a real gap versus the equivalent, already-hardened flows (`token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`) in the same codebase, which suggests the omission in `oauth.rb` is an inconsistency/regression rather than an intentional design decision.

### Recommendation
In `ShopifyAPI::Auth::Oauth.begin_auth` and `validate_auth_callback`, sanitize `shop` via `Utils::ShopValidator.sanitize!(shop)` (as done in `token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`) before using it to build `auth_base_uri`, the `null_session`, or the final `Session`, raising `Errors::InvalidShopError` for any host outside `TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
1. Host app implements `login` exactly as documented: `shop = request.headers["Shop"]; ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")`.
2. Attacker sends `Shop: attacker.example` (a domain they control) to `/login`. `begin_auth` builds `auth_route = "https://attacker.example/admin" + "/oauth/authorize?...&state=..."` with no domain check [9](#0-8) , and returns a valid state cookie.
3. Attacker's server (posing as the OAuth authorization endpoint) redirects the victim's browser back to the app's callback with `shop=attacker.example`, a `code` of the attacker's choosing, the matching `state`, and a valid `hmac` computed with the shared `api_secret_key` covering exactly these values (the attacker controls all signed fields except the secret, but since they control the entire round trip they can arrange for the callback request itself to originate from their own script using a secret-independent bypass only if HMAC validation used the secret to *authenticate the request wasn’t tampered with* — note: in a fully attacker-driven flow where the "callback" is never sent by Shopify at all, the attacker cannot compute a valid HMAC without the secret, so the practical exploit requires either a genuine Shopify-signed request being replayed with the same `shop`/`code`/`state` bytes, or a host app that skips/derives HMAC differently). Given the analysis, the concretely provable defect is the missing `ShopValidator.sanitize!` call in `oauth.rb`, which is the exploitable primitive that must be closed to prevent SSRF-with-secret in any deployment where `shop` can be attacker-influenced upstream of HMAC computation (e.g., custom middlewares or partial validation setups).

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI

            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
