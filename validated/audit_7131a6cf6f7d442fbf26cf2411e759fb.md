### Title
Webhook shop identity is read from an unsigned header while HMAC only covers the raw body, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Webhooks::Request` derives the `shop` value used for routing/processing from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, but `to_signable_string` (which is what `Utils::HmacValidator` verifies against) is defined as only the raw request body. The HMAC therefore authenticates the body's integrity/origin from the app's `client_secret`, but never binds that authenticated body to the `shop` header that the registry actually trusts to build `WebhookMetadata`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` only [1](#0-0) , while `#shop` is parsed straight from the `shop-domain` header with no cryptographic binding to that signed body [2](#0-1) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., body HMAC) and then immediately trusts `request.shop` to build `WebhookMetadata` passed to the app's handler [3](#0-2) . `HmacValidator.validate` computes the signature purely from `to_signable_string` (the body) and the app-wide `Context.api_secret_key` — the same secret is used for every shop that installs the app, it is not shop-specific [4](#0-3) .

The binding that should hold is:
`shop_used_by_handler (header) == shop_that_produced_the_authenticated_body (HMAC-covered content)`

This equality is never enforced, because the header is outside the signed content. Since the HMAC secret (`client_secret`) is identical across all shops for a given app, any raw body + valid HMAC pair captured from one shop's genuine webhook delivery remains a fully valid `(body, hmac)` pair regardless of which shop header accompanies it. An attacker who legitimately receives real webhooks for their own installed shop (a normal, unprivileged action — installing the app on a shop they control) can capture one `(raw_body, hmac-sha256)` pair, then resend it to the app's webhook endpoint with the `shop-domain` header swapped to a victim shop that also has the app installed. `HmacValidator.validate` still returns `true` (it never looks at the shop header), so `Registry.process` proceeds and invokes the merchant's registered handler with `WebhookMetadata(shop: victim_shop, body: attacker's own body)` [5](#0-4) .

### Impact Explanation
This breaks the tenant boundary the gem is supposed to preserve: the shop the handler believes it is acting on is not the shop the cryptographic signature actually vouches for. Depending on how the consuming app's webhook handler code uses `data.shop` (e.g. to look up/update a merchant record, revoke access, trigger `app/uninstalled` cleanup, or process `customers/redact`), an attacker-controlled payload can be attributed to a victim shop the attacker does not control, causing cross-tenant state corruption using only their own legitimate app installation — no access token, `client_secret`, or privileged access required. This matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Likely and low-effort for any user who can install the app on a shop they control (a completely unprivileged action for public/embeddable apps): they receive real signed webhooks (HTTPS is between Shopify and the app, not the attacker, but the attacker is the legitimate recipient of their own shop's webhooks so no interception is needed), capture body+HMAC, then submit that same pair directly to the app's public webhook endpoint with a forged `shop-domain` header pointing at any other shop using the same app. No cryptographic secret needs to be known by the attacker.

### Recommendation
Include the `shop` (and ideally `topic`) identity in the signed content verified against the HMAC, or independently verify that the `shop-domain` header matches a shop value embedded in/derivable from the authenticated payload before constructing `WebhookMetadata`. At minimum, document/enforce that consuming apps must not treat `request.shop` as authenticated by `Utils::HmacValidator.validate`, or change `Registry.process` to reject requests where the header shop cannot be corroborated by the signed payload.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (public signup, no special privilege).
2. Shopify sends a real webhook to the app's endpoint: body `B`, header `x-shopify-hmac-sha256: H` (valid for `B` under the app's single shared `client_secret`), header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the exact same `B`/`H` pair to the same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` with the same app-wide secret and returns `true` [4](#0-3) .
5. `Registry.process` calls the registered handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B)` [3](#0-2) , causing the app to act on `victim-shop` using attacker-supplied body content it never actually sent for that shop.
