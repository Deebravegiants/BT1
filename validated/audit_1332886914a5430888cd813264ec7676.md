## Title
Attacker-controlled fee `payer` address can permanently block POST/GET request timeout processing via reverting fee-token transfer - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch()`/`dispatchGet()` let the caller pick an arbitrary `post.payer` address that is stored as the `FeeMetadata.sender` for the request. [1](#0-0)  When that request times out, `dispatchTimeOut()` first invokes the destination app's timeout callback and, only if it succeeds, unconditionally pushes the escrowed fee to `meta.sender` via `safeTransfer`, with no try/catch around the transfer. [2](#0-1)  If `meta.sender` is a contract/token pairing that reverts on receipt (e.g. a hostile contract, or a blacklisted address on a compliance-gated fee token), the whole external call reverts.

### Finding Description
This mirrors the SEDA `postBatch`/`postResult` pattern: an unprivileged party plants an address in persistent state during one transaction (`dispatch`, analogous to `postBatch` recording `msg.sender` as batch sender) that a later, unrelated transaction is forced to pay out to (`dispatchTimeOut`, analogous to `postResult`'s `_transferFee(batchSender, ...)`). Both `dispatchTimeOut` overloads (`PostRequestTimeout` and `GetRequestTimeout`) have identical unguarded refund logic. [3](#0-2) 

Critically, `HandlerV2.handlePostRequestTimeouts` and `handleGetRequestTimeouts` iterate over an array of timeouts proven against a single state root and call `host.dispatchTimeOut(...)` for each entry inside a plain loop — there is no per-item try/catch, unlike `dispatchIncoming`'s pattern of deleting the receipt on callback failure so the item can be retried in isolation. [4](#0-3)  A single poisoned entry (attacker-chosen reverting `payer`) therefore reverts the entire batched transaction, blocking delivery of every other, unrelated timeout bundled in that same message.

### Impact Explanation
- The poisoned request's escrowed fee becomes permanently unrecoverable: `dispatchTimeOut` can never complete for that commitment because the refund step always reverts, so `_requestCommitments[commitment]` is never cleared and the fee token sits stuck in `EvmHost` forever — a permanent freezing of funds.
- Because `handlePostRequestTimeouts`/`handleGetRequestTimeouts` process multiple timeouts per call without isolating failures, an attacker can grief relayers into batching a malicious request alongside legitimate ones (or simply force relayers to always process timeouts one-by-one, degrading throughput and increasing gas costs, since any co-batched malicious entry deterministically reverts the whole submission).
- This satisfies "permanent freezing of funds" / "route unable to deliver messages" criteria: legitimate timeout refunds for unrelated requests can be blocked as long as they end up batched with the malicious entry.

### Likelihood Explanation
Any address can call `dispatch()`/the GET equivalent and set an arbitrary `payer`; no privilege is required. Deploying a reverting receiver contract or using a token/address pair guaranteed to revert (e.g. self-blacklisting on a compliance-gated fee token) is trivial and cheap. The only mitigating factor is that relayers choose batching granularity off-chain, so they can work around it by isolating the poisoned request once identified — but the affected request's own fee remains permanently stuck either way.

### Recommendation
- Wrap the `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` calls in `dispatchTimeOut` (both overloads) in a low-level `call`/try-catch so a reverting recipient cannot block completion of the timeout (mark it delivered/cleared regardless, and let the recipient claim later via a pull-based withdrawal, similar to how `pallet-relayer`'s `Fees` bookkeeping decouples accrual from payout). [5](#0-4) 
- Alternatively, isolate each timeout dispatch in `HandlerV2`'s batch loops behind its own try/catch (mirroring `dispatchIncoming`'s failure isolation) so one bad entry cannot revert the whole batch. [6](#0-5) 

### Proof of Concept
1. Attacker deploys `MaliciousPayer`, a contract with no fallback/receive-compatible ERC20 hook that reverts on token pull or simply implements a token-side blacklist trick (or just relies on the fact `safeTransfer` reverts if the recipient is blacklisted on the fee token, e.g. USDC).
2. Attacker (or any app) calls `EvmHost.dispatch(DispatchPost{..., payer: address(MaliciousPayer), fee: X})`, storing `FeeMetadata{sender: MaliciousPayer, fee: X}` for the resulting commitment. [7](#0-6) 
3. Request times out; a relayer (possibly batching it together with other unrelated timed-out requests for gas efficiency) calls `HandlerV2.handlePostRequestTimeouts` with this and other commitments in one `PostRequestTimeoutMessage`.
4. Inside the loop, `host.dispatchTimeOut(...)` is invoked for the poisoned commitment; the app callback succeeds but `safeTransfer(MaliciousPayer, X)` reverts, reverting the entire `handlePostRequestTimeouts` call and every other timeout bundled in it. [8](#0-7) 
5. The poisoned request's fee stays escrowed forever since no future call to `dispatchTimeOut` for that commitment can ever succeed.

    function handlePostRequestTimeouts(IHost host, PostRequestTimeoutMessage calldata message)
        external
        notFrozen(host)
    {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            PostRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            // known request? also serves as source check
            bytes32 requestCommitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(requestCommitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(REQUEST_RECEIPTS_STORAGE_PREFIX, requestCommitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(PostRequestTimeout(request, _msgSender()), meta, requestCommitment);
        }
    }
