### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking `Utils::HmacValidator.validate(request)`, which computes the signature over `request.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only the raw HTTP body — it never includes the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. Those header values are nevertheless trusted downstream and handed to the app's webhook handler as the record's identity.

### Finding Description
`Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 
only the `@raw_body` is signed. The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read directly from unauthenticated headers: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity for the handler: [3](#0-2) 

The `HmacValidator.validate` implementation confirms only `verifiable_query.hmac` vs. `to_signable_string` (the body) is checked — no header is part of the signable string: [4](#0-3) 

This breaks the intended identity binding:
`hmac_valid(body, secret) == true` should imply `shop-domain header == the shop that Shopify actually generated this body for`. In reality the check only proves `hmac_valid(body, secret) == true`; the `shop-domain` (and `topic`/`webhook_id`) headers are unauthenticated and can be swapped for any value independent of the signed body.

Any party who has legitimate access to their own shop's webhooks (an ordinary, unprivileged app merchant — no special privilege needed) receives genuinely HMAC-signed bodies for their own shop. Because the header carrying the tenant identity (`shop-domain`) is not part of the signed material, that same merchant can replay their own valid `(body, hmac)` pair against the app's public webhook endpoint while substituting an arbitrary victim shop's domain in the `shop-domain` header. `HmacValidator.validate` still passes (it only checks the body), and `Registry.process` calls the handler with `shop: request.shop` set to the attacker-chosen victim domain, causing the app to process/attribute the payload as belonging to a different tenant.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged actor (any merchant/user able to trigger any real webhook to themselves) can make the gem consumer's webhook handler believe attacker-controlled data belongs to a different shop, since the shop identity is not part of the authenticated payload. Any app that keys per-tenant data or authorization decisions off `WebhookMetadata#shop` is exposed to cross-tenant data corruption/access, which matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires only network access to the app's public webhook endpoint plus possession of one genuinely signed `(body, hmac)` pair for any topic/shape the attacker wants to use (trivially available to anyone with a store on which the app is installed, or by triggering any of their own store's real webhook events). No credentials, TLS interception, or privileged access is required — only the ability to POST HTTP requests with custom headers, satisfying the "unprivileged internet user" threat model.

### Recommendation
Bind the trusted identity fields to the verified payload rather than relying on unauthenticated headers alone:
- Include `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) in the HMAC-covered signable string, or
- Cross-validate the `shop-domain` header against an independently trusted source (e.g., the session/shop the webhook subscription was registered for) before invoking the handler, rejecting the request if they don't match.

### Proof of Concept
1. App merchant A installs the app; Shopify sends a legitimate webhook: body `B`, headers `shopify-hmac-sha256: HMAC(B)`, `shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker (merchant A) captures `B` and `HMAC(B)`.
3. Attacker POSTs to the app's public webhook endpoint with the same body `B` and same `hmac`, but sets `shopify-shop-domain: shop-victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(B)` against `B` — passes.
5. `handler.handle(data: WebhookMetadata.new(shop: "shop-victim.myshopify.com", body: parsed(B), ...))` runs, and the app processes attacker-controlled data as if it originated from `shop-victim`.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
