### Title
Webhook `shop` (and other metadata) is trusted but not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, and `ShopifyAPI::Webhooks::Registry.process` uses `Utils::HmacValidator.validate(request)` to authenticate that body against Shopify's HMAC. However, the `shop` (and `topic`, `webhook_id`, `api_version`) values used downstream by webhook handlers come from HTTP headers (`x-shopify-shop-domain` / `shopify-shop-domain`) that are never included in the signed bytes.

### Finding Description
The HMAC binding this gem enforces is: `HMAC_valid == secure_compare(HMAC(secret, raw_body), received_hmac)` [1](#0-0)  where `to_signable_string` for a webhook request is defined as just the raw body: [2](#0-1) .

Meanwhile, the tenant-identifying field `shop` is read straight from an HTTP header with no cryptographic tie to the signed payload: [3](#0-2) .

`Registry.process` validates the HMAC and then immediately hands `request.shop` (the unauthenticated header value) to the application's webhook handler as the tenant identity for the event: [4](#0-3) .

This breaks the intended equality `authenticated_bytes == bytes_the_handler_trusts_as_tenant_identity`. The gem authenticates the body only; the shop/topic/webhook-id metadata that the handler actually keys tenant-specific logic on is parsed from headers outside the signature. This is directly analogous to the reported Solidity bug class: a value ("provider"/"shop") is *acted upon* by privileged logic (`coverDefault`/`handler.handle`) without being *covered* by the authorization mechanism (token approval/HMAC) that is supposed to bind it.

### Impact Explanation
Any actor capable of producing one valid `(raw_body, hmac)` pair signed with the app's secret — e.g., a merchant on their own legitimately-installed shop capturing their own genuine webhook delivery — can replay that exact body+HMAC while substituting an arbitrary `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header value. `HmacValidator.validate` will still return `true` because it never inspects headers, and `Registry.process` will dispatch the payload to the handler tagged with the attacker-chosen shop domain. If the host application uses `WebhookMetadata#shop` to select which tenant's records to create/update/delete (a common and expected pattern for this gem's documented webhook API), this results in cross-tenant data injection — one merchant's webhook events being attributed to and processed against a different merchant's data. This satisfies the "High - scope/expiry check bypass" / cross-tenant impact bar since it crosses a tenant boundary using only a legitimately-obtained webhook, no privileged Shopify credentials required for the *victim* shop.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment that installs the app on multiple shops and dispatches to shared handler logic keyed by `WebhookMetadata#shop`, since a malicious merchant only needs to capture one webhook delivery to their own store (trivial — install the app, trigger an event) and can then freely re-send it to the app's public webhook endpoint with a rewritten shop header, entirely within this gem's documented API contract (`Registry.process(request)`).

### Recommendation
Include the identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed/verified representation, or otherwise cryptographically bind them to the request before trusting them — e.g., require the application to cross-check `request.shop` against the shop associated with the currently active/authenticated session rather than trusting the header value on its own. At minimum, document prominently that `WebhookMetadata#shop` (and other headers) are *not* covered by the HMAC and must not be used as the sole tenant-identity source for privileged actions.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw body `B` and the valid header `x-shopify-hmac-sha256: H` computed by Shopify over `B` with the app's real secret.
2. Attacker replays the exact same `B`/`H` pair to the app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` parses successfully; `shop` returns `"victim.myshopify.com"` [3](#0-2) .
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H` — validation succeeds [5](#0-4) .
5. `handler.handle` receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` and the application processes attacker-controlled data as if it originated from `victim.myshopify.com` [6](#0-5) .
