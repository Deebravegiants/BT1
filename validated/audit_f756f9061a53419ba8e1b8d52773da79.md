### Title
Webhook shop-domain tenant identity spoofing via header not covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating its HMAC signature, then hands the request's `shop` value—read from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header—to the host application's webhook handler as the trusted tenant identifier. The HMAC signature only covers the raw request body, not any header, so the `shop` value used for tenant attribution is never bound to the value that was actually authenticated.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `#shop` is derived purely from the `shop-domain` header: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC over exactly that `to_signable_string` value: [3](#0-2) 

`Registry.process` performs the authentication check and then immediately trusts `request.shop`, passing it into `WebhookMetadata` for the handler to act on: [4](#0-3) 

This is exactly the report's bug class applied to a different binding: the identity equality that should hold is `shop_bound_by_hmac == shop_used_by_handler`, but the gem instead enforces `body_bytes_verified_by_hmac == body_bytes_parsed` while `shop` is taken from an unauthenticated header. An attacker who has ever observed one valid `(raw_body, hmac)` pair from Shopify for any topic/shop (e.g., from browser dev tools, logs, a proxy, or a webhook relay they control) can replay that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary value in the `x-shopify-shop-domain` header. `HmacValidator.validate` still returns `true` because it never looks at headers, and `Registry.process` will invoke the handler with the attacker-chosen `shop`, causing the host application to process/act on data (e.g., writing "shop X's" webhook payload into shop Y's tenant data) under the wrong tenant.

### Impact Explanation
This breaks the shop/tenant identity binding that host applications rely on to route webhook data to the correct merchant record — a cross-tenant data integrity issue. Because the `shop` field feeding tenant-scoped business logic is not part of the authenticated payload, an attacker with access to any single legitimately-signed webhook body can cause the library to attribute it to a different, arbitrary shop domain, despite HMAC validation reporting success.

### Likelihood Explanation
Exploitation requires the attacker to have captured at least one valid `(raw_body, hmac)` pair, which is a realistic bar since webhook payloads and their HMAC headers are frequently visible in browser network logs, third-party webhook relay/proxy tools, non-TLS internal hops, or logging systems — no possession of `api_secret_key` is required. Once obtained, replaying with a modified `shop-domain` header is trivial and deterministic.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed payload, or otherwise cryptographically bind the `shop` value to the verified body — for example by having `HmacValidator`/`VerifiableQuery` sign over a canonical string that incorporates the header-derived `shop`, `topic`, and `webhook_id` fields rather than the raw body alone, so `process` cannot be fed a `shop` value that wasn't part of what was verified.

### Proof of Concept
1. Attacker captures a legitimately-signed webhook request sent by Shopify to the app, e.g. `raw_body = B`, headers include `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: legit-shop.myshopify.com`.
2. Attacker replays the exact same `raw_body = B` and `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` in the new request to the app's webhook endpoint.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: replayed_headers)` builds a request object; `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` only and it matches `H`, so validation passes.
4. `Registry.process(request)` calls the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process shop A's payload attributed to shop B.
