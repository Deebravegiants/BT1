### Title
Webhook shop-domain identity used for tenant routing is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body, but it then forwards the tenant identifier (`shop`) taken from an unauthenticated HTTP header to the app's handler. The equality the app relies on — "the shop that produced a valid signature" == "the shop the handler attributes the data to" — does not hold, because the signature never covers the header.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` define the signed content as only the raw JSON body: [1](#0-0) 

The `shop` accessor, however, is read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is not part of the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC over the body via `HmacValidator.validate(request)` and, once that succeeds, immediately builds `WebhookMetadata` using `request.shop` — the unauthenticated header — as the tenant key handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the digest purely from `verifiable_query.to_signable_string` (the body) and the app's secret, and never touches `shop`: [4](#0-3) 

Because the HMAC only binds to the *body bytes*, any two webhook deliveries carrying byte-identical bodies (e.g. a webhook payload for the same topic, or a payload whose JSON fields are attacker-influenced but happen to collide/be replayable) will produce byte-identical valid signatures regardless of which shop header accompanies them. A holder of one authentic `(body, hmac)` pair for shop A — obtainable by any merchant who installs the same app (an "unprivileged" party relative to other tenants of the app) — can resend that exact body/hmac pair to the app's webhook endpoint while substituting `x-shopify-shop-domain` with victim shop B's domain. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` passes the attacker-chosen `shop` value straight into `WebhookMetadata`, so the host application processes/attributes the (originally-shop-A) payload as if it belongs to shop B.

The documented API for webhook handlers explicitly instructs developers to trust `data.shop` as *the* shop identity for the event (`docs/usage/webhooks.md` — "`shop`, `String` - The shop domain of the webhook"), with no caveat that the gem leaves this field unauthenticated. There is no code path in the gem, at any layer (`Request`, `HmacValidator`, `Registry`), that cross-checks the `shop` header against anything derived from the signed payload or against a known/installed-shop set.

### Impact Explanation
This breaks the tenant/identity binding: `shop_that_signed_the_bytes == shop_attributed_to_the_data` does not hold. An attacker controlling one tenant's webhook traffic can cause the host application to process, store, or act on webhook data under a different (victim) shop's identity, i.e. cross-tenant data confusion. Depending on how the host app uses `data.shop` (e.g., to select a tenant DB record, override tenant metadata, trigger tenant-scoped side effects), this can result in cross-tenant data corruption/exfiltration triggered by an unprivileged app-installing user, which maps to the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation only requires: (1) being a legitimate but unprivileged merchant with the target app installed (to receive one authentic HMAC'd webhook body), and (2) the ability to POST an arbitrary HTTP request with attacker-chosen headers to the app's public webhook endpoint (webhook endpoints are typically public, unauthenticated HTTP routes by design). No access to `api_secret_key`, access tokens, or the victim's credentials is required. The main constraint is finding webhook topics/bodies whose content the attacker fully controls or can predict byte-for-byte (many webhook bodies, e.g. `app/uninstalled`, or bodies with attacker-supplied product/order data on the attacker's own store, are fully attacker-influenced), making this practically reachable for at least some topics.

### Recommendation
Bind the shop identity into the authenticated material before it is trusted for routing/attribution:
- Include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in the HMAC-signed content (`to_signable_string`), or
- Independently verify `request.shop` against the set of shops/sessions the app has legitimately installed/authorized before invoking the handler, or
- Document prominently (and enforce in `Registry.process`) that `data.shop` must never be trusted for tenant routing unless cross-validated against stored session data, and provide a built-in check for this in the gem rather than leaving it entirely to host applications.

### Proof of Concept
1. App has two merchants installed: Shop A (attacker-controlled) and Shop B (victim).
2. Attacker triggers/receives one legitimate webhook from Shopify for Shop A whose JSON body is fully attacker-influenced (e.g., editing a product/customer field they control), capturing the exact `raw_body` and the corresponding `x-shopify-hmac-sha256` header Shopify computed with the app's secret.
3. Attacker sends a forged HTTP request to the app's public webhook endpoint:
   - Body: the captured `raw_body` (unchanged, so the HMAC stays valid).
   - Headers: `x-shopify-hmac-sha256` = the captured (valid) value, `x-shopify-topic` = same or compatible topic, `x-shopify-shop-domain` = `shop-b.myshopify.com` (victim), `x-shopify-webhook-id` = arbitrary.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and succeeds.
5. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` with `request.shop == "shop-b.myshopify.com"`, and invokes the app's handler, which now processes attacker-supplied data as if it originated from Shop B. [3](#0-2) [5](#0-4)

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end

          received_signature = verifiable_query.hmac
