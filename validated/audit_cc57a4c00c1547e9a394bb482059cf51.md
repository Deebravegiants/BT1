### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are not covered by HMAC verification, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the handler a `WebhookMetadata` object whose `shop`, `topic`, and `webhook_id` fields are taken verbatim from unauthenticated HTTP headers. Because the HMAC never binds these header values to the signed payload, any holder of one valid `(raw_body, hmac)` pair for the shared app secret can relabel that payload as originating from a different shop by changing the `X-Shopify-Shop-Domain` header, while `Utils::HmacValidator.validate` still reports success.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors read directly from HTTP headers that are not part of the signed data at all: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the metadata that is dispatched to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate_signature` recomputes the signature purely from `verifiable_query.to_signable_string` (i.e., only the body) and compares it against the `hmac` header: [4](#0-3) 

The identity binding that should hold is:
`HMAC-verified data == data acted upon by the handler`

But in this gem the equality actually is:
`HMAC-verified data (raw_body only) ⊂ data acted upon by the handler (raw_body + shop + topic + webhook_id)`

The `shop`, `topic`, and `webhook_id` fields are "acted on but not covered by the HMAC," exactly matching the class of bug in the report (identity/binding fields excluded from the cryptographic check). Since the app's `api_secret_key` is shared across all shops that install the app (it is not per-shop), any shop that has legitimately installed the app can capture a real `(raw_body, hmac)` pair generated for its own webhook deliveries (these arrive at endpoints the shop owner controls, or can be triggered by the shop owner performing an action that fires a webhook), and then resend that exact `raw_body`/`hmac` pair to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (and optionally forged `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header claiming to be a different, victim shop. `Utils::HmacValidator.validate` will still return `true` because it only checks the body against the shared secret, and `Registry.process` will dispatch the (attacker-supplied) body to the handler tagged as if it came from the victim shop.

### Impact Explanation
This breaks the tenant boundary the webhook mechanism is meant to enforce: the host application's handler is designed to trust `WebhookMetadata#shop` to determine which merchant's records to create/update/delete. An attacker who has installed the app on their own shop can inject arbitrary (self-controlled) payloads that are processed and attributed to a shop they do not own, resulting in cross-tenant data corruption/injection — e.g., forging `orders/create`, `app/uninstalled`, `customers/data_request`, or other lifecycle webhooks against a victim shop's tenant record. This matches the Critical "cross-tenant access" impact category, since a single unprivileged app installer can cause the application to process attacker-chosen data under another merchant's identity.

### Likelihood Explanation
Likelihood is moderate-to-high in typical deployments: the attacker only needs to be a legitimate (unprivileged) installer of the target app on their own store — no leaked credentials, no access token, and no privileged account are required. They can capture their own genuine webhook deliveries (bodies and matching HMACs) simply by observing traffic to their own webhook endpoint, then replay the same body/HMAC pair with a spoofed shop header directly to the app's public webhook URL. The only constraint is that the forged webhook's body must be one the attacker can legitimately obtain (from their own shop's real webhook traffic), which is trivially satisfied for many common webhook topics.

### Recommendation
Bind the identity fields into the verified signature space, or otherwise re-authenticate them independently of headers:
- Track/validate that `request.shop` corresponds to a shop with an active session/installation known to the app, and reject webhooks for shops that are not currently installed/recognized in that HMAC-verified body when relevant (e.g., verify the shop domain embedded in the JSON body, if present, matches the header).
- Where possible, incorporate the `topic`, `shop-domain`, and `webhook-id` headers into the value passed to `Utils::HmacValidator.validate` (e.g., include them in `to_signable_string`) so header tampering invalidates the signature, rather than validating raw body bytes alone.
- Document clearly (and enforce where feasible) that consumers of `Registry.process` must additionally correlate `WebhookMetadata#shop` against their own installed-shop registry before trusting it, since the HMAC does not attest to shop identity.

### Proof of Concept
1. App `MyApp` has `api_secret_key = S` shared by all installed shops.
2. Attacker installs `MyApp` on `attacker-shop.myshopify.com` and, through normal app usage, triggers/receives a legitimate webhook delivery at their own configured endpoint with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(S, B)`.
3. Attacker sends a new HTTP request directly to the target app's webhook endpoint (the one built with `ShopifyAPI::Webhooks::Registry.process`) using the same raw body `B` and the same `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(S, B)` (using only `@raw_body`, per `Request#to_signable_string`) and it matches, so validation passes: [5](#0-4) 
5. `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` (from the forged header) and `body: parsed_body` (attacker-controlled content from their own shop's webhook), and invokes the app's handler as though this data legitimately belongs to `victim-shop.myshopify.com`: [6](#0-5)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
