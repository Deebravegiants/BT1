## Analog Confirmed

### Title
Overpaid native token for POST/GET dispatch fee swap is permanently stuck in EvmHost instead of being refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` swap any `msg.value` sent by the caller into `feeToken` via `IUniswapV2Router02.swapETHForExactTokens`, but never refund the leftover native token that the router sends back after the swap. This mirrors the Predy `M-07` bug: excess value generated by an operation is sent to the intermediary contract that performed the call (`EvmHost`) instead of the entity that supplied the funds (the original transaction sender), and there is no recovery path for the depositor.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 

and in `dispatch(DispatchGet)`: [2](#0-1) 

Both functions call `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`. `swapETHForExactTokens` is an *exact-out* swap: it only spends as much ETH as needed to buy `post.fee`/`get.fee` worth of `feeToken`, and refunds any unspent ETH — but that refund is sent to `msg.sender` **of the router call**, which is `EvmHost` itself, not `_msgSender()` (the actual caller of `dispatch`). Just like in the Predy report, where `exceedsQuote` was sent to `msg.sender` of the reallocation call (the Market contract) instead of the reallocator who actually supplied the swap capital, here the leftover ETH is sent to `EvmHost` instead of the application/user who sent the overpaid `msg.value`.

Neither `dispatch(DispatchPost)` nor `dispatch(DispatchGet)` contains any subsequent logic to forward this refunded ETH back to `_msgSender()`. The only path that can move native tokens out of `EvmHost` is the governance-restricted `IHostManager.withdraw()`: [3](#0-2) 
which is callable only by the `hostManager` module, not by the depositor.

Contrast this with the correct pattern used elsewhere in the codebase — e.g., `IntentGatewayV2` and `IntentsBase` explicitly track `msgValue` and refund any residual native token to `msg.sender`: [4](#0-3) [5](#0-4) 
`EvmHost.dispatch` lacks this equivalent refund step.

### Impact Explanation
Any unprivileged application or user dispatching a POST or GET request with more native token than strictly required to cover the fee-token swap permanently loses the excess — it becomes locked in `EvmHost` with no caller-accessible retrieval mechanism, matching a "permanent freezing of funds" outcome for that value. Because `dispatch()` is the primary entry point used by every IApp/router (including `HyperApp`-based integrations documented for POST request dispatch), this is broadly reachable from any single dispatched request, and estimating the exact required `msg.value` precisely (accounting for slippage/price movement between quote and execution) is impractical for callers, making overpayment routine rather than an edge case.

### Likelihood Explanation
High likelihood: any caller relying on the documented "send native token, we'll swap for you" flow (as advertised in `docs/content/developers/evm/messaging/post-requests.mdx`) must estimate `msg.value` in advance of an on-chain swap whose price can move, so slight overestimation (a common and recommended safety margin) triggers the loss on every such call.

### Recommendation
After the `swapETHForExactTokens` call, measure the actual native balance spent (or capture `amounts[0]` returned by the router) and refund any leftover native token to `_msgSender()`, mirroring the refund pattern already implemented in `IntentGatewayV2`/`IntentsBase` (`_sendValue(msg.sender, msgValue)`).

### Proof of Concept
1. Caller invokes `EvmHost.dispatch(DispatchPost)` (or `DispatchGet`) with `msg.value` intentionally or naturally exceeding the ETH needed to purchase `post.fee` worth of `feeToken` (e.g., due to price movement between fee quoting and transaction execution).
2. `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` executes; Uniswap V2 Router spends only the ETH needed and refunds the remainder to `msg.sender`, i.e., `EvmHost`.
3. `dispatch()` completes without forwarding the refunded ETH anywhere; it remains in `EvmHost`'s balance.
4. The original caller has no function to reclaim this value — only `hostManager.withdraw()` can move native ETH out of `EvmHost`, and that is a governance-only path unrelated to the specific depositor.

        if (msg.value > 0) {
