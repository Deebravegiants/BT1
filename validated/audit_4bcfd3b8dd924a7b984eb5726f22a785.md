This confirms the pattern: `client_credentials.rb` and `refresh_token.rb` both call `Utils::ShopValidator.sanitize!(shop)` before building a session and sending the request (which includes `client_secret` in the body) to `https://#{shop}/admin/oauth/access_token`. `oauth.rb`'s `begin_auth` and `validate_auth_callback`, however, never call `ShopValidator.sanitize!` on `shop` — they pass it directly into `auth_base_uri(shop)`.

### Title
Missing shop-domain validation in `ShopifyAPI::Auth::Oauth.begin_auth`/`validate_auth_callback` allows attacker-controlled OAuth host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
Unlike `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, which both sanitize the caller-supplied `shop` through `Utils::ShopValidator.sanitize!` before using it to build the request host, `Oauth.begin_auth` and `Oauth.validate_auth_callback` use the raw `shop` value directly in `auth_base_uri(shop)` with no domain allow-listing.

### Finding Description
`Utils::ShopValidator` exists specifically to bind a `shop` string to Shopify's trusted domain list (`myshopify.com`, `myshopify.io`, `shopify.com`, `spin.dev`, `shop.dev`) before it is used to construct a URL that will receive the app's confidential `client_secret` [1](#0-0) . Both other OAuth-token-acquisition flows call this validator prior to using `shop` as the request host: `client_credentials.rb` calls `Utils::ShopValidator.sanitize!(shop)` and only then builds the session/host that receives `client_secret` in the body [2](#0-1) , and `refresh_token.rb` follows the identical pattern [3](#0-2) .

`Oauth.begin_auth`, by contrast, takes the `shop:` parameter directly from the caller (which in a real app is typically taken straight from the unauthenticated install-request query string) and passes it unsanitized into `auth_base_uri(shop)` to build the authorization redirect URL containing `client_id` and `redirect_uri` [4](#0-3) . `Oauth.validate_auth_callback` similarly uses `auth_query.shop` — bound only by the HMAC computed over `code/host/shop/state/timestamp` — to build the host that then receives the app's `client_secret` in the POST body to `#{auth_base_uri(shop)}/oauth/access_token` [5](#0-4) . `auth_base_uri` performs no domain allow-listing at all, simply interpolating the value into `https://#{shop}/admin` [6](#0-5) .

The equality that should hold — "the host that is authorized to receive `client_id`/`client_secret` == a Shopify-trusted domain" — is not enforced in this code path, breaking the same identity binding that `ShopValidator` was introduced to protect in the sibling flows.

### Impact Explanation
For `begin_auth`, an unsanitized `shop` lets an attacker who controls the initial "install" request (e.g., a merchant clicking a crafted install link with `shop=attacker.example`) cause the app to redirect the browser to `https://attacker.example/admin/oauth/authorize?client_id=...&redirect_uri=...`, disclosing the app's `client_id` and callback URL to an arbitrary host and enabling forced/confused OAuth flows.

For `validate_auth_callback`, reaching the code with a `shop` value pointing away from a genuine Shopify domain and a corresponding valid HMAC requires knowledge of `api_secret_key`, which is out of scope per the rules governing this analysis. Consequently, only the `begin_auth` path is reachable by an unprivileged party without already holding the app's secret, limiting the practically exploitable impact to host/parameter disclosure and forced-flow initiation rather than direct `client_secret` exfiltration.

### Likelihood Explanation
`begin_auth` is designed to be called with a `shop` value taken from an inbound, unauthenticated HTTP request (this is the very first step of the authorization-code OAuth flow, before any Shopify-issued signature exists), so the unsanitized value is directly attacker-reachable in typical integrations that follow the library's documented usage pattern [7](#0-6) .

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the start of `Oauth.begin_auth`, and validate/normalize `auth_query.shop` in `Oauth.validate_auth_callback` before it is used to construct `auth_base_uri`, consistent with `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`.

### Proof of Concept
1. Host app exposes `GET /login?shop=<value>` and calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/callback")` directly, per the documented pattern [8](#0-7) .
2. Attacker sends the merchant a link to `/login?shop=attacker.example`.
3. `auth_base_uri("attacker.example")` returns `https://attacker.example/admin` since no domain check is performed [9](#0-8) .
4. The app redirects the merchant's browser to `https://attacker.example/admin/oauth/authorize?client_id=<APP_CLIENT_ID>&redirect_uri=<APP_CALLBACK>&state=<nonce>`, leaking the app's `client_id`/`redirect_uri` to the attacker's server and enabling a forced/confused OAuth initiation, whereas the equivalent `client_credentials`/`refresh_token` flows would have rejected `attacker.example` via `ShopValidator.sanitize!` [10](#0-9) .
