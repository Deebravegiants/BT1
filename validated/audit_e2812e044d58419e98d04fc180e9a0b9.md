Based on my research, the closest legitimate analog in `agave--002` is in the SIMD-0123 "delegator rewards" / block-revenue-sharing reward distribution path, which mirrors the reported bug class: a lamport-tracking field is credited on deposit but is not correspondingly consumed/decremented at the point where it is used to compute and mint new value, so the same balance keeps being treated as available to distribute.

### Title
Delegator `pending_delegator_rewards` balance is never decremented when consumed for block-reward minting - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
`VoteStateV4::pending_delegator_rewards` is a lamport-denominated accounting field that is incremented whenever a delegator/authority deposits lamports into a vote account via the `DepositDelegatorRewards` instruction. `calculate_block_reward` reads this same field every epoch as the "pool" size to proportionally distribute to all currently active stake delegations of that vote account, and the resulting `block_reward` amounts are minted as brand-new lamports into stake accounts, increasing total capitalization. No code path was found that decrements `pending_delegator_rewards` after it has been used as the basis for a block-reward distribution.

### Finding Description
`deposit_delegator_rewards` transfers lamports into the vote account and then calls `vote_state.add_pending_delegator_rewards(deposit)`, which only ever adds to the field: [1](#0-0) [2](#0-1) 

Each epoch, `calculate_block_reward` reads `pending_delegator_rewards` from the (possibly stale, cached) vote-state view and computes a per-delegation share of it, capped at the full pending amount: [3](#0-2) 

This is invoked from `calculate_stake_rewards_and_commissions` for every stake delegation of the vote account, every epoch that `block_revenue_sharing` is active: [4](#0-3) 

The resulting `block_reward` is then *minted* as new lamports directly into stake accounts (not moved out of the vote account's own balance) during distribution: [5](#0-4) 

and the bank's `capitalization` is increased by exactly this newly-created amount: [6](#0-5) 

I searched the codebase for any assignment that subtracts from or resets `pending_delegator_rewards` after it is consumed as a block-reward basis (`pending_delegator_rewards -=`, `checked_sub`, `set_pending_delegator_rewards`, etc.) and found none outside of the additive `add_pending_delegator_rewards` path and the read-only accessor in `handler.rs`/`vote_state_view`. The only other mutation site is the initial deposit path itself.

This is the direct structural analog to the reported bug: in the Popcorn report, `underlyingBalance` is incremented on withdraw/deposit accounting but never updated when the strategy re-deposits harvested funds, so a share-conversion function keeps returning a stale ratio. Here, `pending_delegator_rewards` is incremented on deposit but never decremented when it is consumed as the sizing basis for a real lamport-minting distribution, so the same nominal "pool" is available to be redistributed again in the next epoch unless deliberately reset elsewhere.

### Impact Explanation
If confirmed that no reset/decrement exists in the full distribution pipeline, this would mean a single `DepositDelegatorRewards` deposit produces unbounded lamport creation: every subsequent epoch that the vote account continues to have active stake delegations and `block_revenue_sharing` enabled, `calculate_block_reward` would again treat the full (undiminished) `pending_delegator_rewards` value as an available reward pool, minting the same (or a similarly-sized) amount of new lamports into stakers' accounts each epoch and inflating `capitalization` indefinitely. This is a direct, concrete creation of value beyond what was legitimately deposited, and would cause cross-validator state divergence if any implementation-specific interpretation differs, or bank-hash mismatches versus intended protocol design (SIMD-0123 clearly intends the deposit to fund a one-time or bounded block-reward payout).

### Likelihood Explanation
This is reachable through a normal, unprivileged, permissionless path: any signer can call `DepositDelegatorRewards` against any V4 vote account they have signing authority over as the source account, and does not require validator/operator privilege. Whether it manifests depends entirely on whether some other, not-yet-located code path resets or debits `pending_delegator_rewards` after distribution (e.g., inside `redeem_rewards`, the vote-account update logic during distribution, or a follow-up sysvar/state update not surfaced by my searches). I was unable to find such a reset within the reward-calculation/distribution modules, the vote program, or the vote-state handler despite targeted greps across the whole repository for decrement/reset patterns on this field. Given the index-size limits on Ask, I cannot be fully certain no such code exists elsewhere (e.g., a companion PR/commit not indexed, or logic buried deeper in `redeem_rewards`/`DelegatedVoteState` update paths that I did not fully trace). I recommend a Devin session with full repository access specifically trace: (1) every writer of `VoteStateV4::pending_delegator_rewards`, (2) whether `redeem_rewards`/`store_stake_accounts_in_partition` or any vote-account update during `distribute_partitioned_epoch_rewards` mutates the vote account's `pending_delegator_rewards`, and (3) whether the field is intentionally meant to be a decaying pool vs. a permanent multiplier base per SIMD-0123.

### Recommendation
If no decrement exists: after `calculate_block_reward` computes and finalizes the distributed `block_reward` total for a vote account's epoch, subtract that total from `pending_delegator_rewards` in the vote account state as part of distribution (mirroring how stake `credits_observed` is advanced only once rewards are redeemed), and persist the updated vote account. This ensures a delegator deposit funds a bounded amount of future rewards rather than being reusable indefinitely as an unlimited minting basis.

### Proof of Concept
Conceptual sequence (pending full-codebase confirmation of absence of a reset path):
1. Attacker deposits `X` lamports via `DepositDelegatorRewards` into vote account `V` that has active stake delegations, setting `pending_delegator_rewards = X`. [7](#0-6) 
2. At epoch boundary, `calculate_block_reward` computes proportional shares of `X` for each of `V`'s delegations and mints them as new stake-account lamports, increasing `capitalization` by up to `X`. [8](#0-7) [9](#0-8) 
3. `pending_delegator_rewards` in `V`'s state remains `X` (no observed decrement), so the next epoch's `calculate_block_reward` call again treats the full `X` as distributable, repeating the mint.
4. Repeat indefinitely across epochs for unbounded lamport creation from a single deposit.

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

    pub(crate) fn add_pending_delegator_rewards(
        &mut self,
        amount: u64,
    ) -> Result<(), InstructionError> {

            TargetVoteState::V4(v4) => {
                v4.pending_delegator_rewards = v4
                    .pending_delegator_rewards
                    .checked_add(amount)
                    .ok_or(InstructionError::ArithmeticOverflow)?;
