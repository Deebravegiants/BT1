### Title
Webhook `shop` (and `topic`) identity fields are not covered by the HMAC, enabling cross-tenant webhook replay/attribution spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives its HMAC-signable material solely from the raw request body [1](#0-0) , while the `shop` and `topic` fields used to route and attribute the webhook are read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only the HMAC of the body and then forwards the header-derived `shop`/`topic` to the app's handler as if they were verified [3](#0-2) . This breaks the intended binding `hmac == HMAC(secret, body ∥ shop ∥ topic)`; in reality the equality enforced is only `hmac == HMAC(secret, body)`, so `shop` is a free variable an attacker can set to any value while keeping a valid signature.

### Finding Description
`VerifiableQuery#to_signable_string` for webhook requests returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC over exactly that signable string [4](#0-3) . The `shop`, `topic`, `api_version`, and `webhook_id` values are all pulled straight from HTTP headers with no cryptographic binding to the body or to each other [5](#0-4) .

`Registry.process` raises only if the HMAC over the body fails; it then builds `WebhookMetadata` directly from `request.shop` and passes it to the registered handler [3](#0-2) . The handler interface (`WebhookHandler#handle`) receives this `WebhookMetadata.shop` as trusted tenant identity [6](#0-5) .

Any unprivileged internet user who can install the app on a shop they control (or otherwise legitimately receive one signed webhook, e.g. for a public/free listing) obtains a genuinely valid `(body, hmac)` pair signed with the real `api_secret_key`. Because the signature never covers the `shop-domain` header, that same `(body, hmac)` pair remains valid if replayed to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to a victim shop's domain — and likewise the `topic` header can be altered to relabel the payload as a different event type. `Registry.process` will accept it, because `Utils::HmacValidator.validate` only checks the body signature [7](#0-6) , and will hand the handler a `WebhookMetadata` claiming the victim shop as the source of the (attacker-controlled) body content.

This is exactly the class of bug the rules call out: "a field acted on but not covered by the HMAC." The equality that should hold — `authenticated(shop) == shop_the_handler_acts_on` — is broken: the shop the handler acts on is taken from an unauthenticated header, while the only authenticated data is the body bytes.

### Impact Explanation
Any downstream logic that uses `WebhookMetadata#shop` to select which tenant's session/access token to operate with, or to attribute/store the payload under a specific shop's records, can be tricked into applying attacker-supplied body content to a victim shop's identity. This is a cross-tenant data-attribution/injection primitive reachable by an unprivileged internet user who merely needs one legitimately signed webhook of their own (e.g., from installing the app on their own store) to replay against arbitrary victim shop identifiers. Depending on how the host application's handler consumes `data.shop` (e.g., to look up a session and act with that shop's access token, or to write records keyed by shop), this can escalate to cross-tenant access using another merchant's credentials/context, matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is moderate-to-high: obtaining one valid `(body, hmac)` pair requires no privileged access — it only requires the attacker to install the app on a shop they control (or otherwise be a legitimate recipient of one webhook), which is the normal path for any unprivileged merchant/developer. Replaying the request with a modified `shop-domain` header is a trivial HTTP manipulation, since the header is not part of the signed material. The gem provides no additional binding or shop-header signing, so any host application that trusts `WebhookMetadata.shop` as authenticated is exposed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) identity to the HMAC verification step rather than trusting it purely from headers: e.g., verify that the resolved `shop` corresponds to a shop with an active session/installation known to the app before acting on the payload, or extend the signable string / add an independent verification step that ties header-derived routing fields to the authenticated payload. At minimum, document prominently that `WebhookMetadata.shop` and `.topic` are NOT covered by the HMAC and must be independently validated by host applications (e.g., cross-checked against the app's known-installed-shops list) before being used for any privileged action or tenant attribution.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (or otherwise legitimately triggers a webhook for a topic the app subscribes to) and captures a real webhook POST, including a valid `x-shopify-hmac-sha256` header computed over the raw body with the app's real `api_secret_key` [1](#0-0) .
2. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally [8](#0-7) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the body against the secret [9](#0-8) .
4. The registered handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)` [10](#0-9)  and, if it uses `data.shop` to select the tenant session/token to act with or to attribute stored data, performs the action/storage against the victim shop's identity even though the payload originated from the attacker's own shop event.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
