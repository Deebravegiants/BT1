### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant event spoofing - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the raw request body via HMAC, but hands the caller's `shop` value — taken from an unauthenticated HTTP header — as if it were verified tenant identity. This breaks the binding `shop authenticated == shop used for tenant identification`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC computed by `Utils::HmacValidator` covers just the JSON body bytes, using the app's single, shop-independent `api_secret_key`: [1](#0-0) [2](#0-1) 

`Registry.process` validates that HMAC and, if it passes, immediately trusts `request.shop` (read from the `X-Shopify-Shop-Domain` header, never included in the signed bytes) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` confirms only that *some* valid body was signed with the app secret — it says nothing about which shop the payload belongs to: [4](#0-3) 

Because the `api_secret_key` is shared across every shop that has installed the app (it is not per-shop), any shop that has legitimately installed the app can receive a validly-signed webhook body+HMAC pair from Shopify for its own events, then replay that exact body (with its still-valid HMAC) to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the header), and `Registry.process` calls the handler with `shop: "<victim-shop>.myshopify.com"` and body data that actually belongs to the attacker's own shop.

The gem's own documentation instructs consumers to key persisted webhook data directly off this `shop` field, confirming this is the gem's intended trust boundary, not a host-app misuse: [5](#0-4) 

### Impact Explanation
This allows a single confirmed shop identity to inject or overwrite webhook-driven data (e.g., simulate `orders/create`, `app/uninstalled`, `customers/redact`, etc.) into another tenant's records inside the host application, without ever possessing the app's `client_secret` or any victim-shop credential. This is a cross-tenant data-integrity breach reachable purely by an internet-facing, "unprivileged" party who has installed the app at least once.

### Likelihood Explanation
Requires the attacker to have installed the target app on any shop they control (a normal, unprivileged action any Shopify merchant can perform), capture one legitimate webhook delivery for their own shop, and replay it with a spoofed `Shop-Domain` header to the app's public callback URL. No secret material or victim access is required, so likelihood is moderate-to-high for any app that keys tenant data solely off `WebhookMetadata#shop`, exactly as this gem's docs recommend.

### Recommendation
Do not treat `request.shop` as verified. Either bind the shop domain into the signed content (not possible since Shopify controls the wire format), or require `Registry.process`/`HmacValidator` to cross-check `request.shop` against the shop of a webhook subscription that this app actually registered (e.g., match against known installed/session shops) before invoking the handler, and document clearly that `data.shop` is unauthenticated and must be revalidated by the host app against its own shop registry.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; Shopify sends a legitimately HMAC-signed `orders/create` webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` + app secret), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same `B`/`H` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...spoofed shop...})` builds successfully (headers only checked for presence, not value binding) — see `initialize` in `lib/shopify_api/webhooks/request.rb` lines 45-63.
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H` since `to_signable_string` never includes the shop header.
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...))`, and the host app persists/acts on data `B` under the victim shop's tenant record, per the gem's documented pattern in `docs/usage/webhooks.md`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
