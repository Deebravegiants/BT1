### Title
Operator QR-code authorization bypass via unvalidated `signup_extension` flag - ([File: src/plans/mod.rs])

### Summary
The external report concerns `Staking.sol` administration functions that fail to validate that critical parameters are non-zero/non-default before granting a trusted state (e.g., `setOwner` accepting `0x0`). The analogous root cause exists in orb-core's operator QR-code authorization path: `verify_operator_qr_code` grants an operator "valid" status and default/placeholder location data without ever validating the operator's identity with the backend, whenever the scanned code merely sets the `signup_extension` flag — a flag that is fully attacker-controlled via QR-code content, with no accompanying check that the value/context is legitimate.

### Finding Description
`verify_operator_qr_code` is the function that is supposed to authenticate an operator QR-code against the backend before an orb enters signup flow: [1](#0-0) 

```
async fn verify_operator_qr_code(...) -> Result<Option<(u64, backend::operator_status::LocationData)>> {
    if qr_code.signup_extension() || self.operator_qr_code_override.is_some() {
        return Ok(Some((0, backend::operator_status::LocationData {
            team_operating_country: "DEV".to_string(),
            session_coordinates: Coordinates { latitude: 0.0f64, longitude: 0.0f64 },
            stationary_location_coordinates: None,
        })));
    }
    ...
```

The condition `qr_code.signup_extension()` is not restricted to any privileged/authorized context — it is simply a boolean set by parsing the scanned QR-code text via the `QR_CODE_SIGNUP_EXTENSION` regex: [2](#0-1) [3](#0-2) 

Any string matching `userid:<id>:<digits>(::<mode>(:<params>)?)?::` sets `signup_extension = true`. There is no server-side (backend) verification, no check that the "mode" is a legitimate/authorized value, and no check that the operator ID is registered — the function short-circuits with a hard-coded, always-valid response (`"DEV"` country, `0.0/0.0` coordinates) instead of calling `backend::operator_status::request`, which is the actual authorization/validation call used for every other operator code: [4](#0-3) 

This mirrors the Staking.sol bug class precisely: a security-critical field (`newOwnerAddress`, `root`, delay) is accepted without validating that it represents a legitimate/expected value, silently placing the system into a privileged/trusted state (here: "authorized operator," analogous to "owner") using default/placeholder data instead of a validated one.

### Impact Explanation
This bypass means the "operator authorization" check — the administrative gate that is supposed to confirm the person scanning is a registered/authorized operator before biometric capture proceeds — can be trivially satisfied by anyone able to present a crafted QR code, with zero backend validation. Downstream, `handle_user_qr_code` further short-circuits full user verification and hands back `backend::user_status::UserData::default()` when both operator and user codes carry the extension flag: [5](#0-4) 

The result is that an unauthenticated, unregistered "operator" can initiate signup/biometric-capture sessions under a fabricated identity and location (`"DEV"`, `0.0/0.0`), which the debug report and personal custody package will subsequently persist as if they were legitimate session metadata: [6](#0-5) 

This constitutes an unauthorized/misattributed signup and biometric capture initiated through a spoofed operator identity, since the system never validated that the "operator" credential was real before trusting it — the same class of impact as losing/misattributing privileged access in the Staking.sol report.

### Likelihood Explanation
Likelihood is high for any orb build compiled with the `internal-data-acquisition` feature (which enables the `QR_CODE_SIGNUP_EXTENSION` regex and the `signup_extension` code paths in `qr_scan::user::Data`). No secret, credential, or network privilege is required — only the ability to present a QR-code with a specific text pattern to the orb's camera, which is exactly the "unprivileged user" action modeled by the analog rules (QR parsing / signup authorization). The bypass condition (`qr_code.signup_extension()`) has no additional gating (e.g., feature check, allow-list, or backend confirmation) in `verify_operator_qr_code` itself.

### Recommendation
Short term: Remove or gate the `qr_code.signup_extension()` short-circuit in `verify_operator_qr_code` so that operator identity/location is never accepted without a genuine backend `operator_status::request` call; require the same for `operator_qr_code_override`, restricting it strictly to non-production test/CI builds. Explicitly validate that `signup_extension`-flagged QR-codes cannot themselves imply operator authorization.

Long term: Add negative tests asserting that a `signup_extension`-formatted operator code without a corresponding backend validation is rejected, and audit all other locations where QR-derived flags directly short-circuit backend authorization/validation calls (mirroring the "expand testing to include zero/default-value tests" recommendation from the source report).

### Proof of Concept
1. Enable a build with the `internal-data-acquisition` feature (or use a target that ships with it enabled).
2. Present a QR code as the "operator" code with text matching, e.g.: `userid:12345678-1234-1234-1234-123456789012:1::0::` (matches `QR_CODE_SIGNUP_EXTENSION`, setting `signup_extension = true`).
3. `try_parse` in `src/plans/qr_scan/operator.rs` accepts it as `Data::Normal(user::Data{ signup_extension: true, .. })` because `signup_extension_config.is_some()` [7](#0-6) .
4. `verify_operator_qr_code` sees `qr_code.signup_extension() == true` and immediately returns `Ok(Some((0, LocationData{country:"DEV", coords:(0.0,0.0), ..})))` — no backend call is made [8](#0-7) .
5. The orb proceeds as if a fully validated, registered operator had presented their code, entering signup/biometric-capture flow under fabricated operator identity/location.

/// Makes a validation request.
pub async fn request(qr_code: &qr_scan::user::Data) -> Result<Status> {
    let request = super::client()?
        .get(format!(
            "{}/api/v1/distributor/{}/orb/{}/status",
            *SIGNUP_BACKEND_URL, qr_code.user_id, *ORB_ID
        ))
        .basic_auth(&*ORB_ID, Some(get_orb_token()?));
    let status: Status = match request.send().await?.error_for_status() {
        Ok(response) => response.json().await?,
        Err(err) => {
            tracing::error!("Received error response {err:?}");
            return Err(err.into());
        }
    };
    if !status.valid {
        tracing::info!(
            "Operator QR-code invalid: {qr_code:?}, reason: {:?}",
            status.reason.as_deref().unwrap_or("<empty>")
        );
        return Ok(status);
    }
