### Title
Inflated escrow accounting for non-standard-transfer tokens permanently freezes user funds and breaks settlement in Tron `IntentGatewayV2.placeOrder` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder` credits escrow using the order's *declared* input amount (`reducedInputs[i].amount`) rather than the amount actually received via `safeTransferFrom`, unlike the hardened mainline EVM implementation which measures balance deltas.

### Finding Description
In the non-predispatch branch of `placeOrder`:
```solidity
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
...
_orders[commitment][token] += reducedInputs[i].amount;
``` [1](#0-0) 

the code trusts `order.inputs[i].amount` as the amount received, and stores that declared amount into escrow. For tokens with non-standard transfer semantics — e.g. tokens like `cUSDCv3` that special-case `amount == type(uint256).max` to transfer only the caller's balance, or any fee-on-transfer/rebasing token — the actual balance received by the gateway can be strictly less than the amount recorded in `_orders[commitment][token]`.

This is precisely the bug class from the external report: trusting the requested transfer amount instead of measuring the actual balance delta corrupts internal accounting for tokens with special-case transfer behavior.

Notably, the sibling production contract `evm/src/apps/IntentGatewayV2.sol` already defends against this exact issue by measuring `balanceOf` before and after the transfer and mutating `order.inputs[i].amount` to the actual received value before it is used for escrow/commitment:
```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
``` [2](#0-1) 

and there are dedicated fee-on-transfer regression tests validating this behavior for the mainline contract. [3](#0-2) 

The Tron variant, `evm/tron/contracts/apps/IntentGatewayV2.sol`, lacks this balance-delta measurement entirely in both the predispatch escrow-crediting path (`_orders[commitment][token] += reducedInputs[i].amount` at line 441, using the fixed declared amount rather than actual dust-adjusted balance) and the direct-transfer path (line 463), even though the predispatch path does correctly measure a `dust` value for excess but never reduces the escrow for a *shortfall*. [4](#0-3) 

### Impact Explanation
Once `_orders[commitment][token]` records an amount larger than what the gateway actually holds for that token, settlement of that specific order becomes unrecoverable:
- On the destination chain, `withdraw()` (invoked via `onAccept` for `RedeemEscrow`) or via `cancelOrder`'s same-chain refund path will attempt to transfer the recorded (inflated) escrow amount to the solver/user. [5](#0-4) [6](#0-5) 
- Since the gateway's actual token balance is short of that recorded amount, the ERC20 transfer inside `withdraw` will revert, permanently freezing both the user's escrowed principal (real balance, unable to be withdrawn because the accounting demands more than exists) and blocking the solver from ever being paid for that order. This satisfies "permanent freezing of funds" from a single user-initiated `placeOrder` transaction using an in-scope, reachable token behavior (no privileged actor required — any unprivileged order placer using a special-case-transfer token triggers this).

### Likelihood Explanation
Likelihood is Medium-High: it requires no privileged access and is triggered by ordinary usage of a `placeOrder` call with a token that has non-standard transfer semantics (fee-on-transfer tokens, or `cUSDCv3`-style contracts special-casing `type(uint256).max`), both of which are common in the wild and not filtered/blocklisted by the contract. The mainline `evm/src/apps/IntentGatewayV2.sol` already anticipates and defends against exactly this token category, confirming it's a realistic and expected token class for this protocol, while the Tron deployment omits the fix.

### Recommendation
Apply the same balance-delta pattern used in `evm/src/apps/IntentGatewayV2.sol` to the Tron contract: measure `IERC20(token).balanceOf(address(this))` before and after each `safeTransferFrom` (and after predispatch sweep transfers), and use the *actual received* amount — not the caller-declared `order.inputs[i].amount` — when computing `reducedInputs`, the commitment hash, and the `_orders[commitment][token]` escrow credit. This should mirror both the direct-transfer branch and the predispatch/dust-accounting branch already fixed in the mainline EVM contract.

### Proof of Concept
1. User calls `placeOrder` on the Tron `IntentGatewayV2` with an input token that is a `cUSDCv3`-style contract, setting `order.inputs[i].amount = type(uint256).max` (or any amount exceeding the user's actual approved/held balance under such a token's special-case semantics).
2. `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` succeeds but transfers only the caller's actual balance (less than `type(uint256).max`), per the token's special-case logic.
3. `_orders[commitment][token] += reducedInputs[i].amount` records the full declared (fee-reduced) `type(uint256).max`-derived amount, vastly exceeding the gateway's actual token holdings for this order.
4. When the order is later filled and `withdraw()` is invoked (same-chain cancel, or cross-chain `RedeemEscrow`/`RefundEscrow`), the contract attempts to transfer the inflated escrow amount to the beneficiary/solver, which reverts because the gateway does not hold that many tokens — permanently freezing the escrowed funds and preventing settlement of that order.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
