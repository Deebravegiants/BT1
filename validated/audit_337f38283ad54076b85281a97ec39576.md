### Title
Withdrawal status misreported for duplicate-asset batch withdrawals due to non-unique matching by `assetId` only - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain status of a specific withdrawal (identified by `index` in a batch) by calling `findMatchingWithdrawal`, which matches purely on `assetId`, ignoring `index`, amount, or destination. When a single intent transaction contains two or more withdrawals of the same token (a supported use case in this SDK, e.g. multi-leg withdrawals), every one of those withdrawals resolves to the *same* API entry, so distinct withdrawals in the batch report an identical status/`txHash`.

### Finding Description
`createWithdrawalIdentifiers` (in `withdrawal-watcher.ts`) builds one `WithdrawalIdentifier` per entry of `WithdrawalParams[]`, each carrying its own `index` for a given `bridge.route`: [1](#0-0) 

For each identifier, `watchWithdrawal` polls `bridge.describeWithdrawal(...)` until completion: [2](#0-1) 

For the POA route, `describeWithdrawal` fetches the full list of withdrawals for the NEAR transaction hash and then calls `findMatchingWithdrawal`, which selects the first item whose `near_token_id` matches the given `assetId` — the `index` field on `WithdrawalIdentifier` is never consulted: [3](#0-2) [4](#0-3) 

The comment at the matching function even documents this limitation explicitly, acknowledging that "multiple withdrawals of the same token in a single transaction are not supported" by this matching logic: [5](#0-4) 

The equality that should hold is: *`describeWithdrawal({index: i, assetId: A})` reports the on-chain outcome of exactly the i‑th withdrawal of asset A in this transaction*. Instead, because `Array.find` returns only the first array element matching `assetId` (with the underlying API response explicitly documented as "unsorted"), every identifier sharing the same `assetId` in the batch collapses onto the same status/`txHash`, regardless of `index`.

No SDK-level guard prevents a caller (e.g., a user or an integrator building `WithdrawalParams[]`) from constructing a batch with two withdrawals of the same `assetId` to two different `destinationAddress` values — `createWithdrawalIntents` in `sdk.ts` iterates and resolves a bridge per param with no uniqueness check across the batch: [6](#0-5) 

The identical structural flaw exists in the generic `waitForWithdrawalCompletion` helper in `internal-utils`, which likewise matches only on `assetId` and documents the exact same limitation: [7](#0-6) 

### Impact Explanation
If an integrator relies on the SDK's per-index/per-withdrawal status (or `txHash`) to decide when to credit or reconcile a destination, a batch containing two same-asset withdrawals will cause both indices to report the same `txHash`/`completed` status once *any one* of them lands on-chain. This can make an integrator believe two separate legs of a withdrawal have both completed (crediting or reconciling twice) while only one has actually settled on-chain — matching the "status or hash misreport making an integrator credit or refund twice" High-impact category. This is directly analogous to the referenced report's root cause: a check ("at least one"/"first match") that is supposed to apply per-item is instead applied uniformly across an entire batch, breaking the per-item correctness guarantee.

### Likelihood Explanation
This requires only that a caller construct a `WithdrawalParams[]` batch with two entries sharing the same `assetId` (different destinations/amounts) — no bridge operator, relayer, or admin misbehavior is needed, and this is a normal, unprivileged SDK usage pattern (the RFC in this repo explicitly discusses "batch withdrawals" such as "USDC to Solana + BTC refund to Bitcoin" as a supported feature, and nothing prevents two same-asset legs). The likelihood of accidental triggering is non-trivial for any integrator building multi-destination withdrawal batches of the same token, and it is trivially reproducible by a user/integrator who wants to force the misreport.

### Recommendation
Match withdrawals deterministically per `index` rather than by `assetId` alone: sort both the local `withdrawalParams` (by amount, since fees are equal for same token per the existing code comment) and the API's returned `withdrawals` array by amount, then pair them positionally; or fail closed (throw/treat as unsupported) when a batch contains more than one withdrawal of the same `assetId`, until the POA bridge API provides a stable per-withdrawal identifier.

### Proof of Concept
1. Build a NEAR intents transaction containing two POA-bridge withdrawals of the same `assetId` (e.g., `nep141:usdc.omft.near`) to two different `destinationAddress` values (`indexes 0` and `1`).
2. Call `sdk.waitForWithdrawalCompletion({ withdrawalParams: [w0, w1], intentTx })`.
3. Internally, `createWithdrawalIdentifiers` assigns `index: 0` and `index: 1` to the two `WithdrawalIdentifier`s [1](#0-0) .
4. Both calls to `PoaBridge.describeWithdrawal` query the same `tx.hash` and call `findMatchingWithdrawal(response.withdrawals, assetId)`, which returns the same (first-matching) `withdrawal` object for both `index=0` and `index=1` queries [3](#0-2) .
5. As soon as the first of the two legs settles, both promises returned by `waitForWithdrawalCompletion` resolve as `completed` with the identical `txHash`, even though the second leg has not yet (or may never) settle on-chain — an integrator crediting per index would incorrectly treat both destinations as paid.

	withdrawalParams: WithdrawalParams[];

}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
