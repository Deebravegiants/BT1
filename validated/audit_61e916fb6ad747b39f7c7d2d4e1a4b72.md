### Title
Webhook shop-domain header is trusted for tenant attribution without HMAC coverage, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body [1](#0-0) , yet `Registry.process` uses the unauthenticated `shop-domain` header value from the same request as the trusted tenant identifier passed to the app's webhook handler [2](#0-1) . Because the header is not part of the signed payload, an attacker who legitimately owns a shop (and therefore can generate a validly-HMAC'd webhook body for their own store) can replay that exact `raw_body`/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` header value. `Registry.process` will still accept the request as authentic (since `Utils::HmacValidator.validate` only checks the body signature) and will invoke the app's handler with the attacker-chosen `shop`, breaking the equality that `verified_bytes(hmac) == shop_used_for_tenant_routing`.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` [3](#0-2)  and defines `to_signable_string` to return only `@raw_body` [1](#0-0) . The `shop` accessor instead reads directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never mixed into the signable string [4](#0-3) .

`HmacValidator.validate` verifies only `verifiable_query.to_signable_string` against `verifiable_query.hmac` [5](#0-4) , so it never authenticates the `shop` header at all.

`Registry.process` performs the HMAC check and then, having validated only the body, immediately forwards the unauthenticated `request.shop` value into `WebhookMetadata` which is passed to the app's registered handler: [2](#0-1) . `WebhookMetadata.shop` is a plain `String` field with no further validation [6](#0-5) .

The gem's own documentation instructs host apps to treat `data.shop` as the trusted tenant/shop identifier of the webhook (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [7](#0-6) , i.e., this is the gem's documented, intended usage pattern rather than the host app misusing an internal API.

Attack sequence:
1. Attacker operates their own Shopify store, shop `attacker.myshopify.com`, with the target app installed (satisfies "no privileged access needed" — any unprivileged merchant account can trigger webhooks like `orders/create` on their own store).
2. Shopify sends the app a legitimately signed webhook: `raw_body` + valid `X-Shopify-Hmac-Sha256` (computed with the app's real `client_secret`) + `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker intercepts/replays this exact `raw_body` and HMAC value to the app's public webhook endpoint, but rewrites the `X-Shopify-Shop-Domain` header to `victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the (unchanged) body against the (unchanged) HMAC — the header is irrelevant to the check [8](#0-7) .
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker-controlled body content, and processes/persists it as if it originated from the victim tenant.

### Impact Explanation
This breaks the tenant/shop identity binding the report's bug class targets: a value (`shop`) that downstream code uses to attribute and route sensitive state, but which is not covered by the cryptographic signature relied upon for authenticity. Any app that uses `data.shop` (as the gem's own docs recommend) to write/update per-tenant data, dedupe, or trigger tenant-scoped side effects (e.g., updating order/customer records, redaction flows, inventory sync) can have attacker-controlled content injected under a victim shop's identity — a cross-tenant data injection.

### Likelihood Explanation
High for any app following the gem's documented pattern of trusting `data.shop`. The attacker needs no credentials beyond operating any (even free/trial) Shopify store that has the target app installed — an unprivileged internet user in the target app's ecosystem. No access token, `client_secret`, or victim credentials are required; only a legitimately-issued webhook payload from the attacker's own shop and the ability to send an HTTP POST with modified headers.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed payload used for HMAC verification, or independently verify that the `shop-domain` header corresponds to a shop actually registered/authorized for this app before trusting it (e.g., cross-check against the app's own session/shop store). At minimum, the gem should document/enforce that `data.shop` must not be trusted as an authenticated value on its own, or extend `to_signable_string` to include the shop header so `HmacValidator` covers it.

### Proof of Concept
```ruby
# Attacker's own shop generates a legitimately signed webhook (captured by attacker):
raw_body = '{"id":1,"note":"malicious payload"}'
hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# Attacker replays the SAME body+hmac but swaps the shop-domain header to the victim's shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac,          # still valid, body unchanged
  "x-shopify-shop-domain" => "victim.myshopify.com", # attacker-controlled, unauthenticated
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Passes HMAC validation (lib/shopify_api/webhooks/registry.rb:190) and invokes the
#    app's handler with WebhookMetadata(shop: "victim.myshopify.com", body: attacker's body)
```

        def validate(verifiable_query)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
