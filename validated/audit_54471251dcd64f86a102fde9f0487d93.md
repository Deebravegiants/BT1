### Title
Permanently unrecoverable LT donated to a curve Pair leaks value with no sweep path, unlike FeeVault's `sweepDonations` - (File: packages/contracts/src/Pair.sol / Router.sol / Bonding.sol)

### Summary
CVE-2017-11534 is a class of bug where a resource is allocated (a font map entry) and never released, causing an ever-growing, unrecoverable memory leak. The alt.fun analog is a value-leak: any LT sent directly to a bonding-curve `Pair` via a plain ERC20 `transfer` (a reachable, unprivileged action explicitly named in scope) is permanently unrecoverable capital once the token leaves `Lifecycle.Curve` — there is no sweep function analogous to `FeeVault.sweepDonations()` for the `Pair`/`Bonding` side of the protocol.

### Finding Description
`Pair.transferAsset` is the only function capable of moving LT out of a `Pair`, and it is gated `onlyRouter` [3](#0-2) . `Router` exposes it in exactly two places: `sell` (which pays out only the AMM-computed `assetOut`, not arbitrary donated balance) and `graduate`, which transfers an *explicit* `amount = ltFromPair` computed as `storedAssetReserve - virtualLtReserve`, deliberately excluding anything donated directly to the pair via `IERC20.transfer` [1](#0-0) .

`Router.graduate` can only be called by `Bonding`, and `Bonding` only calls it once, from `_prepareGraduationLiquidity`, which runs during `_enterGraduating` (phase 1) while the token is still `Lifecycle.Curve` [4](#0-3) . After that single call, the token's lifecycle flips to `Graduating`/`Graduated` and `Bonding` never calls `Router.graduate` for that token again, by design (`AGENTS.md` explicitly states "Bonding won't call Router.graduate again post-graduation") [5](#0-4) . `_prepareGraduationLiquidity`/`_enterGraduating` are the only Bonding paths through which `Router.BONDING_ROLE` privileges are exercised against that specific pair for this purpose. The code's own comment even acknowledges the "leftover is unreachable" and calls the invariant a "trust-assumption claim, not an on-chain guarantee" [2](#0-1) .

Any unprivileged address can trigger the leak by sending LT (or an already-launched Token) directly to a `Pair` address via a plain ERC20 transfer at any time before graduation — this is explicitly listed as an in-scope reachable action. Once that pair graduates (either via the USD trigger or the supply trigger, both permissionlessly reachable via `Bonding.triggerGraduation` / a threshold-crossing `Zap.buy`), the donated LT is stranded forever inside the now-dead `Pair` contract, which has no owner, no upgradeability, and no other extraction path [6](#0-5) .

This differs materially from the symmetric situation in `FeeVault`, where donated/unbacked USDC is explicitly recoverable via the permissionless `sweepDonations()` function that computes `balance - backed` and forwards the surplus to `feeTo` [7](#0-6) . The `Pair`/`Bonding` graduation path has no equivalent recovery mechanism — the analogous "sweep" was designed only for the `_prepareGraduationLiquidity` LT drain and only fires once, before lifecycle transition, and the surplus is designed to be *left behind*, not later reclaimed.

### Impact Explanation
Value permanently locked in a dead contract is economically equivalent to a burn, but unlike an intentional burn it is neither expected by the donor nor recoverable by any party — not the protocol owner, not the token creator, not the original sender. Any unprivileged party (a griefer, a confused user, or an attacker trying to camouflage a larger attack) can strand real LT value with a single ERC20 transfer to a Pair address before graduation completes, and that value is unrecoverable in perpetuity. Over the lifetime of the protocol across many launched tokens, this represents a growing, unbounded loss of value with no mitigation — directly analogous to a memory leak's unbounded resource growth with no free.

### Likelihood Explanation
High. The precondition is a single unprivileged ERC20 `transfer` call to a publicly known `Pair` address, requiring no special timing, no race condition, and no cooperation from any other actor. It is even acknowledged as an accepted design tradeoff in the existing documentation and comments, meaning it is a known, reachable, and unaddressed gap rather than a hypothetical edge case.

### Recommendation
Add a permissionless sweep function analogous to `FeeVault.sweepDonations()`, callable by `Bonding` (or exposed via `Router` under `BONDING_ROLE`) once a token has reached `Lifecycle.Graduated`, that computes the `Pair`'s live LT balance in excess of any protected/expected amount (which is `0` post-finalize) and forwards it to a configured recipient (e.g., protocol `feeTo` or back to depositors via a claims registry), mirroring the existing sweep pattern already proven safe in `FeeVault`.

### Proof of Concept
1. Launch a token via `Zap.createToken`, creating `Bonding`/`Pair` state in `Lifecycle.Curve`.
2. As any unprivileged wallet, call `IERC20(lt).transfer(pairAddress, 1000e18)` directly, donating LT straight into the `Pair` contract. `Pair.assetBalance()` now exceeds the stored `assetReserve` by `1000e18`.
3. Trigger graduation normally (buy past threshold, or call `Bonding.triggerGraduation` once `canGraduate` is true), then call `Bonding.finalizeGraduation`. `_prepareGraduationLiquidity` computes `ltFromPair = storedAssetReserve - virtualLtReserve`, which excludes the donated `1000e18`; `Router.graduate` transfers only `ltFromPair` out.
4. Post-graduation, `IERC20(lt).balanceOf(pairAddress)` still shows the donated `1000e18`. `info.lifecycle == Lifecycle.Graduated`; `Bonding` never calls `Router.graduate` for this token again, and no other function can reach `Pair.transferAsset`. The `1000e18` LT is now permanently stranded — verifiable by attempting any call path in `Bonding`, `Router`, or `Zap` and confirming none targets this pair's residual asset balance.

- **Dual trigger.** Phase 1 fires on whichever hits first: `(storedAssetReserve - virtualLtReserve) × exchangeRate ≥ $9K` (USD, for LT pumps) or `IPair.tokenBalance() == 0` (supply, for flat/bear markets). The USD trigger reads STORED reserves so direct LT donations to the pair don't count toward the threshold; the launch-time `virtualLtReserve` is recovered on-the-fly as `Pair.k() / Token.TOTAL_SUPPLY()` (K is set once at mint and never modified by `Pair.swap`). The supply trigger reads live `tokenBalance()`, which is donation-resistant in the opposite direction: token donations only INCREASE the balance and can never satisfy `== 0`, and any donated tokens are unconditionally burned by `_prepareGraduationLiquidity`.
- **Zero-gap LP seeding.** `_prepareGraduationLiquidity` computes `ltFromPair = storedAssetReserve - virtualLtReserve` (the real LT raised by the curve, donation-immune; `virtualLtReserve` is derived from `Pair.k() / Token.TOTAL_SUPPLY()`) and `tokensForLP = ltFromPair × storedTokenReserve / storedAssetReserve` at end-of-phase-1, caching the result. Phase 2 uses the cached value verbatim, so the curve→LP price match is invariant under the tx split.
