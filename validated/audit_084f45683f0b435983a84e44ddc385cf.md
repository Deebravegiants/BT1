### Title
Unauthenticated livestream TCP upstream allows any network client to hijack the live biometric video downstream mid-signup - ([File: src/agents/livestream/mod.rs])

### Finding Description
The livestream agent's `run()` loop accepts any TCP connection on the `Upstream` listener (port 9201) with no authentication or authorization check. When `Event::Connected(addr)` is received, the code unconditionally executes `downstream = Some(Arc::new(Downstream::new(addr.ip())?))` [1](#0-0) , replacing any prior downstream target with the new connecting client's IP, and begins streaming to it via `Downstream::push`, which sends raw BGRx video frames over UDP to `addr.ip():9200` with no encryption or credential exchange [2](#0-1) .

`Upstream::new()` simply binds `TcpListener::bind("0.0.0.0:9201")` with no TLS, token, or peer allow-list check, and `poll_accept` immediately yields `Event::Connected` for any incoming connection [3](#0-2) .

The GPU texture state (`camera_ir_eye_texture`, `camera_rgb_texture`, etc.) is updated continuously from `Input::IrEyeFrame`, `Input::RgbFrame`, etc. as camera frames arrive during signup, and is only reset on an explicit `Input::Clear` message [4](#0-3) . Because texture state is not tied to any per-connection/session identity, and `gpu.render(events, downstream.push)` is called on every loop iteration once `downstream` is set regardless of who or what triggered the state [5](#0-4) , an attacker's freshly-opened TCP connection to port 9201 gets whatever texture state currently exists in the GPU buffers — including frames captured under a victim's in-progress, different signup session — with no session/identity binding check anywhere in this path.

### Impact Explanation
This results in disclosure of raw IR-eye/IR-face/RGB biometric camera frames belonging to a different, unauthenticated signup session to any unprivileged network client capable of reaching TCP port 9201 on the Orb's network interface. This matches the "biometric data disclosure" impact category, since iris/face imagery is exposed outside authorized backend channels to an arbitrary network viewer.

### Likelihood Explanation
Requires the livestream feature to be compiled in and enabled at runtime (`orb.livestream.enabled()`), and requires network-level reachability to port 9201/9200 (e.g., same LAN/interface as the Orb). No authentication, token, or handshake is required beyond opening the TCP socket, so exploitation is straightforward and fully repeatable once network access exists — every new connection immediately hijacks the downstream target with whatever GPU state currently exists.

### Recommendation
Add authentication/authorization to `Upstream`'s TCP accept path (e.g., mutual TLS, pre-shared token exchanged over an authenticated channel, or restricting `Downstream` bind to a backend-controlled/allow-listed address) before allowing a new connection to receive rendered frames. Additionally, clear GPU textures (`gpu.clear_textures()`) or gate rendering whenever a new `Downstream` is established mid-signup, and bind rendered output to the signup/session identity so a newly connected viewer cannot receive frames captured under a different, unrelated session.

### Proof of Concept
Integration test plan:
1. Start the livestream agent with `livestream.enabled()` true and the port 9201 `Upstream` bound.
2. Simulate a victim signup: feed a sequence of `Input::IrEyeFrame`/`Input::RgbFrame` messages into the port to populate `gpu`'s textures, without ever sending `Input::Clear`.
3. From a separate unprivileged process, open a raw TCP connection to `127.0.0.1:9201` (simulating the attacker), without sending any credentials.
4. Assert that `Event::Connected` fires and `downstream` becomes `Some`, and that the subsequent `gpu.render` call invokes `Downstream::push` with buffer data derived from the frames fed in step 2 (i.e., non-empty/non-cleared texture data), before any `Clear` input is processed.
5. Expected (secure) behavior: connection should be rejected or `push` should only occur after a validated/authenticated handshake tied to the current signup/session id, and stale texture data should be cleared/blocked from being sent to a newly connected, unauthenticated client.

impl Upstream {
    pub async fn new() -> Result<Self> {
        let listener = TcpListener::bind(format!("0.0.0.0:{PORT}")).await?;
        Ok(Self { listener, stream: None })
    }
}

impl Stream for Upstream {
    type Item = Result<Event>;

    fn poll_next(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Option<Self::Item>> {
        if let Some((stream, event_reader)) = &mut self.stream {
            match event_reader.poll_stream(cx, Pin::new(stream)) {
                Poll::Ready(events) => {
                    *event_reader = EventReader::default();
                    match events {
                        Ok(Some(events)) => {
                            return Poll::Ready(Some(Ok(Event::UiEvents(events))));
                        }
                        Ok(None) => {
                            self.stream = None;
                            return Poll::Ready(Some(Ok(Event::Closed)));
                        }
                        Err(err) => return Poll::Ready(Some(Err(err))),
                    }
                }
                Poll::Pending => {}
            }
        }
        match self.listener.poll_accept(cx) {
            Poll::Ready(Ok((stream, addr))) => {
                self.stream = Some((stream, EventReader::default()));
                Poll::Ready(Some(Ok(Event::Connected(addr))))
            }
            Poll::Ready(Err(err)) => {
                Poll::Ready(Some(Err(eyre!("Error accepting connection: {err}"))))
            }
            Poll::Pending => Poll::Pending,
        }
    }
