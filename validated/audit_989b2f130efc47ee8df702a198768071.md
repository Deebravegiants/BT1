Webhook shop identity spoofing via unsigned `X-Shopify-Shop-Domain` header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (and `topic`/`webhook_id`/`api_version`) values consumed by `Registry.process` are read from HTTP headers that are never included in the signed payload. This breaks the equality that should hold between "the tenant whose secret produced a valid HMAC" and "the tenant the app processes the webhook for," letting an unprivileged party who possesses any one genuine (body, HMAC) pair for the app relabel it as belonging to a different, victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers, none of which are part of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC against the app's `api_secret_key` via `HmacValidator.validate(request)`, and — once that check passes — trusts `request.shop`, `request.topic`, and `request.webhook_id` to construct the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` compute `HMAC(secret, verifiable_query.to_signable_string)` and compare it to the `hmac` header — again, only the body enters the signature: [4](#0-3) 

`WebhookMetadata.shop` is a plain, unauthenticated string that the host application's `WebhookHandler#handle` implementation is expected to trust as the identity of the shop the event is about: [5](#0-4) 

The identity binding that should hold is: `shop verified by HMAC == shop the handler acts on`. Because `shop-domain` is excluded from the signable string, this equality never actually holds — the gem only proves "this body was HMAC'd with our secret at some point," not "for this shop." Any entity that legitimately receives one authentic webhook from Shopify for the app (e.g., a merchant who installs the app on their own store, an unprivileged, unauthenticated-relative-to-other-tenants actor) can capture that body+HMAC pair and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header swapped to point at a victim shop domain. `HmacValidator.validate` still succeeds (it never looked at the header), and the app's handler executes with `WebhookMetadata.shop` set to the attacker-chosen victim shop, causing the app to act as if the event/data belongs to that other tenant. This is the direct analog of the "no deposit token validation" pattern in the report: a field that is acted upon (`shop`) is not covered by the integrity check (`HMAC`) that is supposed to authorize the operation.

### Impact Explanation
This is a cross-tenant identity confusion: a party with access to any one legitimate webhook delivery for the app (their own store's webhook) can forge deliveries that the host application will process as belonging to a different merchant's shop. Depending on how the host app's `WebhookHandler` implementations use `data.shop` (e.g., to look up/void records, deauthorize a shop, process `app/uninstalled`, `shop/redact`, GDPR data requests, or update per-shop state), this can lead to cross-tenant data corruption, spoofed uninstall/redact events against a victim shop, or other tenant-boundary violations — matching the "cross-tenant access" criterion.

### Likelihood Explanation
Moderate-to-high: the attacker needs a genuine (body, hmac) pair, which any developer/merchant using the app (or an actor able to trigger a webhook to themselves, e.g. by installing the app on a test store or triggering a topic like `app/uninstalled` on their own shop) can obtain trivially, since HMAC validity is independent of the shop header. No secrets, tokens, or privileged access are required — only receipt of one legitimate webhook body, which is not treated as confidential by Shopify.

### Recommendation
Include the shop-identifying header (and ideally `topic`) in the HMAC-signed content, or independently bind `request.shop` to an out-of-band-verified value (e.g., require the caller to supply an expected shop and compare it, or verify the shop domain via a separate trusted channel such as a per-shop webhook secret/HMAC scheme) before constructing `WebhookMetadata`. At minimum, document/enforce that `WebhookHandler` implementations must not treat `data.shop` as authenticated by the HMAC check alone, or update `Webhooks::Request#to_signable_string`/`HmacValidator` so the signature covers the full identity tuple used downstream.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers any webhook subscription (e.g., `products/update`), receiving a genuine POST with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC(api_secret_key, B)`.
2. Attacker replays this exact request to the app's webhook endpoint, but rewrites the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`, leaving body `B` and `H` unchanged.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and matches `H` — validation succeeds because the shop header was never part of the signed content (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), so the app processes attacker-controlled data as an authentic event for the victim's shop.
