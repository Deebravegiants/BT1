### Title
Webhook shop identity spoofing via unauthenticated header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body, not this header. This breaks the intended binding: `shop_header == shop_that_signed_the_body`. Any caller able to reach the app's public webhook endpoint can keep a validly-signed body/HMAC pair and change only the shop header to attribute the payload to an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from a header that is not part of that signable string: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC (which only proves the body was signed by someone holding `api_secret_key`) and then unconditionally trusts `request.shop` as the tenant identity handed to the application's handler: [4](#0-3) 

`HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string`, i.e. the body, with no knowledge of or dependence on the shop header: [5](#0-4) 

The intended identity binding is: `shop delivered to handler == shop whose secret produced the HMAC`. Because the header is outside the signed material, this equality does not hold — the HMAC only proves *some* valid body/secret pairing exists, not which shop it came from.

**Attack path (unprivileged internet user):** An attacker who owns any Shopify store can install the target app on their own store and receive a legitimately signed webhook (body `B`, valid HMAC `H` for `B`, computed with the app's real `api_secret_key`, but that is Shopify's job — the attacker never needs to know `api_secret_key`, they simply capture a webhook Shopify already sent them). The attacker then replays the exact same POST (`raw_body = B`, `x-shopify-hmac-sha256 = H`) directly to the app's public webhook endpoint, but substitutes `x-shopify-shop-domain` with an arbitrary victim shop domain (e.g. `victim-store.myshopify.com`). `HmacValidator.validate` still succeeds because it only checks `B` against `H`; `Registry.process` then invokes the handler with `shop: "victim-store.myshopify.com"` even though the payload content originated from the attacker's own store.

### Impact Explanation
This is a cross-tenant identity confusion: the app is made to process/attribute webhook data to a shop the request never actually came from, without needing that shop's credentials, session, or the app's `client_secret`. Depending on how the host app keys its data/session lookups by webhook `shop` (the standard documented pattern — `WebhookMetadata` exposes `shop` for exactly this purpose), this allows injecting attacker-controlled data (e.g. fake `orders/create`, `app/uninstalled`, GDPR topics, etc.) into another tenant's data path, or triggering unintended actions keyed to the victim's shop/session. This matches the "Critical - cross-tenant access" impact category, since it breaks the tenant isolation the HMAC check is supposed to guarantee.

### Likelihood Explanation
High. No secret material is required — only a normal, ordinary Shopify store owned by the attacker (installing any app that exposes this library's webhook processing is sufficient to obtain one valid signed body/HMAC pair). The webhook endpoint is public-facing by design (Shopify must be able to reach it over the internet), and replaying a POST with a modified header is trivial.

### Recommendation
Include the shop domain (and ideally topic/webhook-id/api-version) inside the HMAC-signed material, or independently verify that the `shop` header corresponds to a shop actually known/installed by the app (cross-check against stored session data) before trusting it, rather than trusting the header purely because the body-only HMAC passed. At minimum, document and enforce that `request.shop` must be validated against the app's own list of installed/authorized shops before being used as a lookup key.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`. Shopify sends a real webhook, e.g.:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC of body B>
x-shopify-shop-domain: attacker.myshopify.com
x-shopify-webhook-id: ...

B = {"id": 1, "note": "malicious payload"}
```
2. Attacker records `B` and the valid `x-shopify-hmac-sha256` value `H`.
3. Attacker sends a forged request directly to the app's public webhook endpoint:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: H          # unchanged, still valid for B
x-shopify-shop-domain: victim.myshopify.com   # changed
x-shopify-webhook-id: ...

B  # unchanged body
```
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only checks `B` against `H`. [6](#0-5) 
5. `Registry.process` calls the app's handler with `shop: "victim.myshopify.com"`, and the handler processes attacker-controlled body `B` as if it legitimately originated from `victim.myshopify.com`.
