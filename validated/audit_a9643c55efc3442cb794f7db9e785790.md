### Title
Unchecked ERC20 return value in escrow withdrawal allows permanent freezing of funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.sol` (Tron variant) imports and uses `SafeERC20` for inbound token transfers (`safeTransferFrom`), but its escrow-release paths — `withdraw()` and the `SweepDust` handler in `onAccept()` — bypass `SafeERC20` and instead perform raw low-level `.call` invocations of `IERC20.transfer`, checking only that the call did not revert (`success`) and ignoring the ABI-decoded boolean return value. This is the exact bug class described in the analog report: a token that returns `false` on failed transfer instead of reverting will cause `success` to be `true`, so the failure is silently accepted while internal escrow accounting is still decremented as if the transfer succeeded.

### Finding Description
In `withdraw()`, escrowed tokens are released to a beneficiary via: [1](#0-0) 

and transaction fees are redeemed the same way: [2](#0-1) 

The identical pattern is used in the governance-triggered dust-sweep handler: [3](#0-2) 

In all three spots, only the low-level call's `success` boolean (whether the call reverted) is checked; the actual `bytes` return data — which per ERC20 should encode a `bool` indicating transfer success — is discarded (`(bool success,) = token.call(...)`). Contrast this with the deposit path in the same contract and the sibling `evm/src/apps/IntentGatewayV2.sol` / `intentsv2` modules, which consistently use `IERC20(token).safeTransferFrom(...)` / `safeTransfer(...)` from OpenZeppelin's `SafeERC20`, e.g.: [4](#0-3) 

`SafeERC20.safeTransfer` correctly reverts both when the low-level call reverts and when it returns `false` or non-boolean garbage; the manual `.call` pattern in `withdraw()` and `SweepDust` does neither.

`withdraw()` is reached from `onAccept()` for `RequestKind.RedeemEscrow` / `RequestKind.RefundEscrow` after `authenticate(incoming.request)` verifies the ISMP proof: [5](#0-4) 

The tokens used for an order's escrow (`order.inputs[i].token`) are chosen by the order-creating user, not validated as compliant ERC20s, so an order can be created with a non-standard/malicious token whose `transfer` returns `false` on failure without reverting (a well-known real-world ERC20 behavior class). When a relayer (an unprivileged, permissionless actor per the in-scope reachability list) delivers the corresponding cross-chain `RedeemEscrow`/`RefundEscrow` message with a valid proof, `withdraw()` executes: the failing `transfer` call returns `(true, abi.encode(false))`, `success` is `true`, so `TransferFailed()` is never triggered, yet `_orders[body.commitment][token] -= amount` still fires, permanently marking the escrow as redeemed.

### Impact Explanation
Because the internal `_orders` accounting is decremented regardless of whether the token actually moved, the escrowed balance for that token becomes irrecoverable: it is not delivered to the beneficiary (transfer silently failed) and it can never be withdrawn again (the accounting believes it was already paid out). This is a permanent freezing/loss of escrowed user funds within the `IntentGatewayV2` contract, triggered without any privileged action — a normal solver/user/relayer flow suffices once a non-standard token is involved in an order.

### Likelihood Explanation
Reachability requires only: (1) a user creates an order using a token whose `transfer` returns `false` on failure instead of reverting (a documented, common ERC20 non-compliance pattern the same report explicitly calls out), and (2) a relayer submits the standard, otherwise-valid `RedeemEscrow`/`RefundEscrow` proof to complete the intent lifecycle — both are ordinary, permissionless actions in the intent-fulfillment flow, not privileged operations. No malicious admin/governance/collator is needed.

### Recommendation
Replace the manual `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` (both the token loop and the fee-redemption block) and in the `SweepDust` handler with `SafeERC20.safeTransfer`, consistent with the rest of the contract's inbound-transfer handling, so that both reverting and boolean-`false`-returning tokens cause the release to fail atomically instead of silently marking escrow as redeemed.

### Proof of Concept
1. User places an order via `placeOrder` using a custom ERC20 `MaliciousToken` as an input asset; `MaliciousToken.transfer` returns `false` (does not revert) whenever an internal flag is set (e.g., simulate insufficient allowance/blacklist without reverting).
2. Order is filled on the destination chain and a `RedeemEscrow` message with valid ISMP proof is relayed back to the source `IntentGatewayV2` (Tron variant).
3. `onAccept` → `withdraw(body, false)` executes; `MaliciousToken.transfer(beneficiary, amount)` returns `false`, but `token.call(...)` reports `success = true` since no revert occurred.
4. `if (!success) revert TransferFailed();` does not trigger; execution continues to `_orders[body.commitment][token] -= amount;`, permanently zeroing out the escrow record while the beneficiary received nothing — the tokens remain stuck in the contract with no accounting path to reclaim them.
