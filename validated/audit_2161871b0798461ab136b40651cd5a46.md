### Title
Emporium-mediated call to `DepositOnChainUtxosExternalAction.runAction` lets an attacker forge `circomData.originalSender` and drain any victim's standing ERC20 approval - (File: `contracts/external-actions/DepositOnChainUtxosExternalAction.sol`)

### Summary
`HinkalHelper.performHinkalChecks` only enforces `circomData.originalSender == sender` on the **outer** `CircomData` struct submitted to `Hinkal.transact`. When `DepositOnChainUtxosExternalAction` is invoked indirectly through `EmporiumUpgradeable.runAction`'s generic `op.endpoint.call(op.callData)`, the `CircomData` decoded inside `runAction` is an entirely separate, attacker-fabricated ABI blob embedded in `externalActionMetadata`, whose `originalSender` field was never checked against any real sender. An attacker can set that field to a victim's address and drain the victim's outstanding ERC20 approval to `DepositOnChainUtxosExternalAction`.

### Finding Description
The equality claimed to hold everywhere is: `circomData.originalSender == sender` where `sender` is the address that produced the proof, enforced in `performHinkalChecks`: [1](#0-0) 

This check is applied exactly once, to the **top-level** `circomData` passed into `Hinkal.transact`: [2](#0-1) 

When `externalActionData.externalActionId` routes to `EmporiumUpgradeable`, `Hinkal._externalTransact` calls `EmporiumUpgradeable.runAction(circomData, deltaAmountChanges)` with that same top-level struct: [3](#0-2) 

Inside `EmporiumUpgradeable.runAction`, an `EmporiumStack` (containing arbitrary `EmporiumOperation[]`, i.e. arbitrary `endpoint`/`callData` pairs) is decoded from `circomData.externalActionData.externalActionMetadata` and each op is executed via a raw low-level call, with only a check against reusing the wallet-only selectors: [4](#0-3) 

If one op targets `DepositOnChainUtxosExternalAction` with `callData = abi.encodeWithSelector(runAction.selector, forgedCircomData, deltaAmounts)`, `msg.sender` seen by `DepositOnChainUtxosExternalAction` is the Emporium contract (satisfying `onlyAllowedRecipient` per the stated precondition that Emporium is an allowed recipient), and `forgedCircomData` is a completely independent struct decoded from attacker-controlled bytes - never validated by `performHinkalChecks`: [5](#0-4) [6](#0-5) 

The attacker sets `forgedCircomData.originalSender = victim`, so `transferERC20TokenFrom(tokenAddress, victim, msg.sender=Emporium, tokenTotal)` pulls from the victim's `allowance[victim][DepositOnChainUtxosExternalAction]` established by a prior, legitimate deposit.

The `calldataHash` mechanism does not prevent this: `getHashedCalldata`/`formInputForCircom` only guarantee that the `externalActionMetadata` bytes the attacker submits on-chain match the bytes they used to generate their own proof - since the attacker generates the entire proof themselves for their own top-level transaction, they can freely choose the embedded `EmporiumOperation.callData` (and thus the forged inner `CircomData.originalSender`) with no semantic constraint tying it to their own identity: [7](#0-6) 

Stolen tokens land in the Emporium contract's balance (since `_to = msg.sender` inside `DepositOnChainUtxosExternalAction.runAction` resolves to Emporium). Back in `EmporiumUpgradeable.runAction`, the pre/post balance diff on the attacker's own declared `erc20TokenAddresses` list picks up this stolen balance and mints the attacker a legitimate-looking outgoing UTXO for it via `handleOut`: [8](#0-7) [9](#0-8) 

Finally, Hinkal's own balance-diff invariant is satisfied because the stolen funds flow victim → Emporium → Hinkal and are counted as the attacker's created UTXO amount, so the check `balanceDif == amountChanges[i] + utxoAmount` in `Hinkal.transact` passes with `amountChanges[i] = 0` and `utxoAmount = tokenTotal`: [10](#0-9) 

None of `performHinkalChecks`, `verifyProof`, the calldata-hash integrity check, or the balance-diff invariant constrain the *content* of the inner forged `CircomData.originalSender` - they only bind the attacker's own outer submission to itself.

### Impact Explanation
Direct theft of a victim's ERC20 allowance previously granted to `DepositOnChainUtxosExternalAction` (e.g. from a normal prior deposit flow), converted into shielded value credited to the attacker's own stealth address with no backing funds from the attacker. This is Critical: theft of shielded/in-flight user funds and effectively minting shielded UTXO value unbacked by the attacker's own deposit. The attack is repeatable against any victim with an outstanding approval, up to the size of that approval, each time the attacker submits a new self-generated proof.

### Likelihood Explanation
Preconditions: (1) `DepositOnChainUtxosExternalAction.isAllowedRecipient[EmporiumUpgradeable] == true`, (2) `EmporiumUpgradeable.isAllowedRecipient[Hinkal] == true` (needed for the normal Emporium flow), (3) a victim has an outstanding `approve(DepositOnChainUtxosExternalAction, X)`. Attacker cost is only generating one valid proof for their own (possibly zero-value) transaction; no special privileges, relayer, or victim cooperation required. If the described allowed-recipient configuration exists in deployment, exploitation is straightforward and fully attacker-controlled.

### Recommendation
`DepositOnChainUtxosExternalAction.runAction` (and any other `ExternalActionBaseV2`/`ExternalActionBaseUpgradeable` action reachable through Emporium's generic `op.endpoint.call`) must not trust a self-contained `CircomData.originalSender` field decoded from attacker-supplied `callData`. Either (a) remove `DepositOnChainUtxosExternalAction` (and any action performing `transferFrom` against a user-held allowance) from Emporium's set of allowed recipients, since Emporium ops are not proof-bound to a specific user's identity, or (b) require Emporium to pass through and cryptographically bind the *outer*, proof-verified `originalSender`/`msg.sender` context to any nested action call instead of allowing arbitrary ABI-encoded `CircomData` to be forged inside `callData`, and require actions that move funds via `transferFrom` to check `originalSender == outer verified sender` rather than trusting a field from an unverified nested struct.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (proxy), and `DepositOnChainUtxosExternalAction`; register both as external actions; set `DepositOnChainUtxosExternalAction.isAllowedRecipient[Emporium] = true` and `Emporium.isAllowedRecipient[Hinkal] = true`.
2. Victim calls `erc20.approve(DepositOnChainUtxosExternalAction, 1000e18)` (simulating a stale legitimate deposit approval).
3. Attacker (as `sender`) builds outer `CircomData` with `originalSender = attacker`, `externalActionData.externalActionId` = Emporium's id, and `externalActionMetadata` = ABI-encoded `EmporiumStack` whose single op has `endpoint = DepositOnChainUtxosExternalAction`, `callData = abi.encodeWithSelector(runAction.selector, forgedCircomData, [0])` where `forgedCircomData.originalSender = victim` and metadata specifying `utxoAmounts = [[1000e18]]` for the victim's token.
4. Attacker generates a locally valid proof/`calldataHash` for their own outer `CircomData` (all fields self-consistent), and calls `Hinkal.transact`.
5. Assert on both sides of the equality: `performHinkalChecks` passes because outer `circomData.originalSender == attacker == sender`; but `transferERC20TokenFrom` inside `DepositOnChainUtxosExternalAction.runAction` executes with `userAddress = victim` (from the forged inner struct), pulling `1000e18` from `victim`'s allowance.
6. Assert `erc20.balanceOf(victim)` decreased by `1000e18` and attacker's resulting UTXO/shielded balance increased by the same amount with zero attacker-side deposit - confirming the invariant "`forged originalSender` inside nested `runAction` == verified `sender`" is broken.
