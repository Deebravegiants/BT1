### Title
Duplicate `address(0)` entries in `erc20TokenAddresses` let a single `msg.value` ETH deposit back two independent shielded UTXOs - ([File: contracts/Hinkal.sol])

### Summary
`Hinkal.transact`'s balance-verification loop computes `oldBalances`/`newBalances` once via `getBalancesForArray`, but for `address(0)` (native ETH) this returns the contract's total ETH balance, which is identical no matter which array index references it. Because `dimensionsCheck` never enforces uniqueness of `erc20TokenAddresses`, an attacker can list `address(0)` twice with equal positive `amountChanges[i]==amountChanges[k]==msg.value`, causing the `balanceDif` check to pass independently at both indices and mint two shielded UTXOs of value `msg.value` each from a single real ETH transfer.

### Finding Description
The broken equality is: **real ETH received (`msg.value`, sent once) must equal total shielded value minted across all ETH-denominated indices in `circomData`**. The code instead lets `msg.value` satisfy that equality at every duplicate index independently.

Path: `Hinkal.transact` captures `oldBalances = getBalancesForArray(circomData.erc20TokenAddresses)` before `_internalTransact`, and `newBalances` after [4](#0-3) . For each `i` where `erc20TokenAddresses[i]==address(0)`, `balanceDif = newBalances[i] + msg.value - oldBalances[i]` [5](#0-4) , and this must equal `amountChanges[i] + utxoAmount[i]` [6](#0-5) .

In `_internalTransact`, for a positive `deltaAmountChange` (deposit) at each index, `transferERC20TokenFromOrCheckETH(address(0), sender, address(this), uint256(amountChanges[i]))` is invoked [7](#0-6) . For `address(0)` with `_to==address(this)`, this function only asserts `msg.value == _value` and performs no actual transfer [8](#0-7) . If the attacker sets `amountChanges[i] == amountChanges[k] == msg.value == X` at two duplicate `address(0)` indices `i` and `k`, both `require(msg.value == X)` checks trivially pass using the *same* single ETH transfer.

After `_internalTransact`, `newBalances[i]` and `newBalances[k]` both equal `address(this).balance` (post-call), which is `oldETH + X` (ETH is credited atomically with the call, before any deposit logic runs) — identical at both indices since `getERC20OrETHBalance` for `address(0)` ignores the index entirely [1](#0-0) . Thus at each index: `balanceDif = (oldETH+X) + X - oldETH = 2X`. The check `balanceDif == amountChanges[idx] + utxoAmount[idx]` becomes `2X == X + utxoAmount[idx]`, satisfied by `utxoAmount[idx] == X` — independently, at **both** duplicate indices. This lets the attacker create two off-chain UTXOs of value `X` each (backed only by one real `X` ETH deposit), i.e. mint `2X` of shielded value for `X` of real backing.

None of the existing guards prevent this: `dimensionsCheck` checks array-length equality across `Dimensions`-declared fields but never checks for duplicate `erc20TokenAddresses` entries [3](#0-2) ; `checkOnchainCreation` only restricts `onChainCreation`/nullifier fields, not duplicate tokens [9](#0-8) ; the circuit-side `inTotal + amountChanges === outTotal` constraint operates per-index on the attacker-supplied `amountChanges`/UTXO amounts and has no on-chain-anchored knowledge that two indices reference the same physical ETH balance — it only enforces internal consistency of the proof's own declared values, which the attacker fully controls since they are generating their own proof for their own UTXOs.

### Impact Explanation
This is direct minting of shielded value without backing (protocol insolvency): a single real ETH transfer of `X` is used to back two independent shielded outputs of `X` each, doubling the attacker's shielded balance relative to actual assets held by `Hinkal`. This can be repeated (with more duplicate `address(0)` entries, potentially scaling to N duplicates crediting `N*X` shielded value for one `X` deposit) and drains the contract's real ETH reserves once other users try to withdraw, since the ledger of shielded value would exceed on-chain assets. This matches **Critical** severity: minting shielded value without backing / protocol insolvency.

### Likelihood Explanation
The attacker is a fully unprivileged EOA: they only need to craft `circomData` with a duplicated `address(0)` entry in `erc20TokenAddresses`, matching `amountChanges` at both indices equal to `msg.value`, and generate a valid proof for their own UTXOs declaring these values (fully within their control, no relay/owner privilege needed). No special preconditions on tree state are required beyond a normal deposit transaction. This is straightforward and repeatable at low cost (gas plus one legitimate-looking ETH deposit).

### Recommendation
Enforce uniqueness of `erc20TokenAddresses` entries in `dimensionsCheck` (or in `transact` before the balance loop), rejecting any `CircomData` where the same token address (including `address(0)`) appears more than once. Alternatively, restructure the balance-diff loop to aggregate `amountChanges`/`utxoAmount` per unique token address before comparing against a single `balanceDif` per token, rather than iterating per raw array index.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal` with a permissive verifier mock (or use a real proof generation pipeline) so `verifyProof` passes for attacker-controlled `inputForCircom`.
2. Build `circomData` with `erc20TokenAddresses = [address(0), address(0)]`, `amountChanges = [X, X]`, `onChainCreation = [false, false]`, `slippageValues` set to `X` (or lower), `dimensions.tokenNumber = 2`, `externalActionData.externalActionId = 0`, `externalActionData.externalAddress = attacker`.
3. Call `hinkal.transact{value: X}(a, b, c, dimensions, circomData)`.
4. Assert the transaction succeeds (both `balanceDif` checks pass with `utxoAmount == X` at each index).
5. Assert `address(hinkal).balance` increased by only `X`, while `insertCommitments` recorded two separate UTXO outputs (or off-chain-decodable commitments) each representing `X` in ETH — i.e., total newly minted shielded ETH value (`2X`) exceeds the real ETH deposited (`X`), proving the double-credit.
