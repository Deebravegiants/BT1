### Title
Protocol treasury reward silently overwritten when the treasury account is also a validator - ([File: chain/epoch-manager/src/reward_calculator.rs])

### Summary
`RewardCalculator::calculate_reward` builds a `HashMap<AccountId, Balance>` of per-account rewards by first inserting the protocol treasury's share and then inserting each validator's share in a loop, using the account id as the map key. If the protocol treasury account also happens to be a validator that epoch (i.e., it also appears in `validator_block_chunk_stats`), the validator-reward insertion for that same account id overwrites the treasury reward instead of accumulating with it, silently discarding the treasury's portion of the reward pool.

### Finding Description
In `calculate_reward`, the treasury reward is inserted first: [1](#0-0) 

Then, for every account present in `validator_block_chunk_stats`, the loop computes a per-validator `reward` and writes it into the same map with a plain `HashMap::insert`, which replaces any prior value for that key rather than adding to it: [2](#0-1) 

This mirrors the GNTDeposit `batchTransfer` bug class: a data structure tracking "who gets how much" is populated once for a special participant (there: `balances[msg.sender]`, here: the protocol treasury account) and later a per-iteration write for the same key clobbers it instead of merging, because the code assumes the two code paths never target the same identity. If the protocol treasury account id is ever also a staking validator that produces blocks/chunks in that epoch, `res.insert(account_id, reward)` for that validator will overwrite the earlier `res.insert(protocol_treasury_account, epoch_protocol_treasury)`, so the final `res` map used as `validator_reward` no longer contains the treasury's `epoch_protocol_treasury` amount at all — it is replaced by the (typically much smaller) block/chunk-production reward.

Meanwhile `epoch_actual_reward`, which tracks total newly-minted balance and seeds from `epoch_protocol_treasury`, still accumulates correctly: [3](#0-2) [4](#0-3) 

This produces a divergence: the protocol accounts for having minted `epoch_protocol_treasury + Σreward` (used for total-supply/inflation bookkeeping), but the `validator_reward` map that is later used by `Runtime::update_validator_accounts` to actually credit balances only contains the validator's own reward for that account id, because the treasury entry was overwritten: [5](#0-4) 

### Impact Explanation
If the treasury reward is overwritten, the treasury-designated tokens are minted into the protocol's accounting (inflation/total supply increases as if the treasury were paid) but are never actually credited to any account's balance — the value is effectively burned/lost, and the network's `total_supply` bookkeeping diverges from the sum of account balances. This matches the "concrete token inflation… or state divergence" impact bar.

### Likelihood Explanation
Likelihood is low-to-uncertain: it requires the network's `protocol_treasury_account` to also be actively staking and appear as a produced/expected validator in `validator_block_chunk_stats` for the same epoch — an operational choice, not something an unprivileged attacker can force directly, though nothing in the code prevents the treasury account from staking. I was not able to fully trace, within the available tool budget, whether `validator_block_chunk_stats`/epoch validator-selection logic explicitly excludes the treasury account id from being a validator; this exclusion, if present elsewhere, would make the bug unreachable. This uncertainty should be resolved by a deeper trace of `EpochManager::finalize_epoch` / `proposals_to_epoch_info` to confirm whether the treasury account can co-occur as a validator.

### Recommendation
In `calculate_reward`, use `res.entry(account_id).and_modify(|r| *r = r.checked_add(reward).unwrap()).or_insert(reward)` (or an equivalent additive merge) instead of a blind `res.insert(...)`, so that a treasury account which is simultaneously a validator accumulates both reward components rather than one overwriting the other.

### Proof of Concept
Not independently executed; based on static code review of `chain/epoch-manager/src/reward_calculator.rs` lines 84 and 140-144. A concrete PoC would configure a test genesis where `protocol_treasury_account` equals a staking validator account id, run `RewardCalculator::calculate_reward` with that account present in both the treasury slot and `validator_block_chunk_stats`, and assert that the returned map's value for that account equals only the validator's production reward, not `epoch_protocol_treasury + reward`, while `epoch_actual_reward` still includes the full treasury amount.
