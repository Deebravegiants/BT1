### Title
Webhook `shop` identity is trusted from an HTTP header that is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) exclusively from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, while the HMAC signature computed by `ShopifyAPI::Utils::HmacValidator` only ever covers the raw request body (`to_signable_string` returns `@raw_body`). The `shop` value is never included in the signed material, so it can be modified in transit or replayed with a different value without invalidating the HMAC check that gates `Registry.process`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from headers and exposed as a plain accessor, independent of the signed content: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates the webhook solely via `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (the body) and compares it to the `hmac` header — never touching `shop`: [3](#0-2) [4](#0-3) 

Once the body+HMAC pair validate, `request.shop` (an unauthenticated header value) is passed straight into the handler dispatch as the tenant identifier: [5](#0-4) 

Because the HMAC secret (`api_secret_key`) is shared across all shops installed on the app (it is not per-shop), any actor who can install the app on their own store can legitimately obtain a valid `(body, hmac)` pair from a real Shopify-delivered webhook. Since `shop` is excluded from the signed string, that same valid `(body, hmac)` pair remains valid if replayed to the app's webhook endpoint with the `shopify-shop-domain` header changed to an arbitrary victim shop domain. The identity binding that should hold — "the shop whose data the HMAC authorizes" == "the shop the handler believes it is processing for" — is broken.

### Impact Explanation
This falls under cross-tenant confusion: an app that uses `WebhookMetadata#shop` (built from `request.shop`) to decide which tenant's database row/record to update, notify, or credit will process attacker-supplied body content under an arbitrary victim shop's identity, since the library's HMAC validation gives no assurance that `shop` matches the entity that produced the signed body. This can lead to cross-tenant data corruption or unauthorized actions attributed to a shop that never sent the request.

### Likelihood Explanation
Requires only: (1) the app to be installed on any shop the attacker controls (a routine app-install, not a privileged action), (2) capture of one legitimate outbound webhook (topic/body/hmac) sent by Shopify to the attacker's own endpoint, and (3) replaying it with a modified `shop` header to the app's public webhook endpoint. No access to `api_secret_key`, access tokens, or TLS interception is required, since the attacker is a legitimate (if low-trust) merchant of the app.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the material Shopify signs, or — since Shopify's HMAC scheme only covers the raw body by protocol design — do not treat the `shop` header as an authenticated tenant identifier. At minimum, the gem's documentation/`Utils::VerifiableQuery` contract should make explicit that `Webhooks::Request#shop` is unauthenticated, and `Registry.process`/`WebhookMetadata` should cross-check `shop` against a value that is independently verified (e.g., the webhook subscription previously registered per-shop, or an out-of-band shop lookup) before dispatching to handlers, rather than passing the raw header value through as trusted tenant context.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST: body `B`, header `shopify-hmac-sha256: H`, and `shopify-shop-domain: attacker.myshopify.com`.
2. Confirm `H` validates: `OpenSSL::HMAC.hexdigest("sha256", api_secret_key, B) == Base64.decode64(H)` — this is exactly what `HmacValidator.validate` checks per `hmac_validator.rb:26-31`, independent of `shop`.
3. Replay the same `B` and `H` to the app's webhook endpoint, but set `shopify-shop-domain: victim.myshopify.com`.
4. `Registry.process` (`registry.rb:190`) calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B`/`H`. The handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` (`registry.rb:198-199`), even though the body content actually originated from the attacker's own shop.
