Audit Report

## Title
`AllowNext` reentrancy heuristic never triggers for real value-transferring calls, leaving classic reentrancy protection disabled - ([File: substrate/frame/revive/src/vm/evm/instructions/contract.rs])

## Summary
In `run_call`, the reentrancy-protection selection is a `match (value.is_zero(), gas_limit == CALL_STIPEND)` whose first arm `(false, _) => (true, ReentrancyProtection::AllowReentry)` matches unconditionally whenever `value` is nonzero, regardless of the gas limit passed. This means the gas-stipend check is never evaluated for value-transferring calls, and per the project's own `pr_11227.prdoc` documentation of solc's calling convention, real `.transfer(amount)`/`.send(amount)` calls with `amount > 0` are compiled to pass `value > 0` — exactly the case that always resolves to `AllowReentry`.

## Finding Description
The `ReentrancyProtection::AllowNext` variant is explicitly documented as being needed "for calls that transfer value but restrict gas so that the callee only has a stipend gas amount," specifically because "due to gas scale differences that guarantee does not automatically hold in revive and we enforce it explicitly here." [1](#0-0) 

The `run_call` implementation is:
```rust
let (add_stipend, reentracy) =
    match (value.is_zero(), gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND))
    {
        (false, _) => (true, ReentrancyProtection::AllowReentry),
        (_, true) => (true, ReentrancyProtection::AllowNext),
        (_, _) => (false, ReentrancyProtection::AllowReentry),
    };
``` [2](#0-1) 

Both the `(false, _)` and `(_, true)` arms set `add_stipend = true` — meaning the actual gas granted to the callee is computed identically (stipend added) in both cases via `CallResources::from_ethereum_gas(gas_limit, add_stipend)`. [3](#0-2)  The only difference between the two arms is the `ReentrancyProtection` variant selected: `AllowReentry` (no protection) vs `AllowNext` (protects the immediate next reentrant call). Because Rust `match` evaluates arms top-to-bottom and the first arm's pattern `(false, _)` uses a wildcard for the second tuple element, any nonzero-value call takes that arm before the gas-stipend condition is even inspected. This makes the `gas_limit == CALL_STIPEND` check unreachable whenever `value != 0`.

Downstream, `Ext::call` only clears `allows_reentry` for `Strict` and `AllowNext`; `AllowReentry` performs no reentrancy restriction at all, so `allows_reentry(&dest)` never blocks a reentrant callback for calls that land in the `AllowReentry` branch. [4](#0-3) [5](#0-4) 

The claim's own evidence — `pr_11227.prdoc`'s table of solc 0.8.30 calling conventions — confirms that for `target.transfer(amount)`/`target.send(amount)` with `amount > 0`, the compiler passes `value > 0`, which by itself is sufficient to route into the `(false, _)` arm and get `AllowReentry`, independent of whatever raw gas value is on the stack. Only the zero-value edge case (`transfer(0)`/`send(0)`, where `value.is_zero()==true` and the compiler explicitly pushes `gas_limit=2300`) reaches the `AllowNext` arm — and this is exactly the scenario the referenced PR's tests (`evmCallStipendsWorkForTransferZero`, `evmCallStipendsWorkForSendZero`) cover, as stated directly in the prdoc. [6](#0-5) 

I was not able to fully trace `CallResources::from_ethereum_gas`'s exact gas-scaling arithmetic or the `interpreter.ext.call` implementation for `AllowReentry` within the available context, but the reentrancy-protection dispatch logic itself, the doc comment describing its intended purpose, and the prdoc's calling-convention table are all directly confirmed in the repository and are consistent with the claim: the match ordering makes the gas-stipend check dead code whenever `value != 0`, which is precisely the case the mechanism is meant to protect.

## Impact Explanation
Any PVM/EVM contract on `pallet_revive` using the classic `.transfer(amount)`/`.send(amount)` withdrawal pattern (transfer funds, then update accounting state) relies on the stipend-gas restriction plus `AllowNext` to prevent the callee from re-entering the caller during the transfer callback. Because value-transferring calls always resolve to `AllowReentry`, this protection is never actually applied for the real-world case, allowing an attacker contract's `receive()`/fallback to re-enter the victim's withdrawal logic before state is updated — a classic reentrancy drain of contract funds. This is an in-scope, concrete impact (fund theft in a widely-relied-upon protection mechanism) affecting any unprivileged user's deployed contract.

## Likelihood Explanation
The path is reachable by any unprivileged account through the standard EVM `call` instruction path (`eth_call`/contract-to-contract calls) with no special privileges required. The behavior is deterministic — every nonzero-value call always takes the `(false, _)` arm — so the bug triggers on every value-transfer call, not just under specific race conditions, making it fully repeatable given a victim contract that follows the vulnerable transfer-then-update pattern.

## Recommendation
Reorder the match so the gas-stipend condition is checked independently of the zero-value branch, e.g.:
```rust
let is_stipend = gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND);
let (add_stipend, reentracy) = match (value.is_zero(), is_stipend) {
    (_, true) => (true, ReentrancyProtection::AllowNext),
    (false, false) => (true, ReentrancyProtection::AllowReentry),
    (true, false) => (false, ReentrancyProtection::AllowReentry),
};
```
Add integration tests that exercise nonzero-value `.transfer()`/`.send()` reentrancy attempts (not only the zero-value edge case already covered by `pr_11227`), asserting the reentrant callback is rejected with `Error::ReentranceDenied`.

## Proof of Concept
1. Deploy a `Victim` fixture contract with `withdraw()`: reads the caller's recorded balance, calls `msg.sender.transfer(balance)` (nonzero value), then zeroes the balance record.
2. Deploy an `Attacker` fixture contract whose `receive()`/fallback re-enters `Victim.withdraw()`.
3. Fund `Victim` with `N` tokens credited to `Attacker`; call `Victim.withdraw()` from `Attacker`.
4. Without the fix: the reentrant `withdraw()` call inside `receive()` succeeds (no `ReentranceDenied`), and `Victim`'s balance decreases by more than `N` (double withdrawal).
5. With the fix applied: the reentrant call fails with `Error::<T>::ReentranceDenied`, and `Victim`'s balance decreases by exactly `N`.
