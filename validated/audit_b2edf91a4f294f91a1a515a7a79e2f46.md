## Title
Webhook Shop-Domain Header Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The `ShopifyAPI::Webhooks::Request` class computes its HMAC signature over the raw request body only, while the `shop` value used to attribute the webhook to a tenant is read from an unauthenticated HTTP header. This breaks the binding: `HMAC-verified-bytes == raw_body` but `tenant-identifying-field (shop) ∉ HMAC-verified-bytes`. Any request bearer that can produce (or replay) a valid `(raw_body, hmac)` pair can attach an arbitrary `shop-domain` header, and `Registry.process` will accept it and hand the payload to the handler tagged with the attacker-chosen shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor pulls straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic linkage to the signed body: [2](#0-1) 

`HmacValidator.validate` verifies `verifiable_query.to_signable_string` (i.e., only the body) against the HMAC, never incorporating the shop header: [3](#0-2) 

`Registry.process` performs exactly this HMAC check and then forwards `request.shop` — the unauthenticated header value — directly into `WebhookMetadata`, which is the tenant-identifying field the handler acts on: [4](#0-3) 

The equality that should hold but does not: `shop_bound_by_hmac == shop_used_for_tenant_attribution`. In fact `shop_bound_by_hmac` doesn't exist at all — the HMAC only proves the body bytes are unmodified from *some* signed payload, not which shop the body belongs to, or that the accompanying `shop-domain` header is the one originally paired with it at signing time.

### Impact Explanation
This is a cross-tenant confusion primitive (Critical, per the "cross-tenant access" category): a party in possession of any single valid `(raw_body, hmac)` pair — e.g., a merchant who legitimately receives their own real webhook deliveries from Shopify (webhooks are delivered over plain HTTP POST to the app's public callback URL, not secret to the recipient's process) — can resend that same body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a different, victim shop. Since the gem's own validation logic never checks the header against the signed content, `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop, letting attacker-controlled body content be processed/stored/acted upon under another tenant's identity within the host app.

### Likelihood Explanation
Exploitation requires only network access to the app's webhook endpoint plus one legitimately obtained `(body, hmac)` pair (trivial for any merchant with the app installed, since they receive real webhooks routinely) — no `api_secret_key`, access token, or privileged account is needed. The gem itself performs no additional binding, so any host app relying solely on the documented `Registry.process`/`HmacValidator.validate` flow is affected without any misuse of the API.

### Recommendation
Include the shop domain (and ideally topic/api-version) inside the value that is HMAC-verified, or independently verify that `request.shop` corresponds to a shop with an active, previously-established session/installation before dispatching to the handler, rather than trusting the header value on its own.

### Proof of Concept
1. As a merchant with the app installed, capture one legitimate webhook delivery: raw body `B` and its `X-Shopify-Hmac-Sha256` header value `H` (valid because it was signed by Shopify with the app's `api_secret_key` for body `B`).
2. Replay a POST to the app's webhook endpoint with the same body `B` and header `H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(B) == H` — this still passes. [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the body content actually originated from the attacker's own shop, demonstrating the tenant-binding break.

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
