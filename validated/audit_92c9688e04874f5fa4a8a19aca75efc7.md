Confirmed: `readLoop` at [1](#0-0)  runs the per-gateway read loop in its own goroutine (`go c.readLoop(gatewayState)`) and calls `handler.HandleGatewayMessage` synchronously with no `recover()` wrapper. Audit Report

## Title
NULL Pointer Dereference (Crash/DoS) in Vault Gateway `handlePublicKeyGet` via Missing `params` Field - (File: core/capabilities/vault/gw_handler.go)

## Summary
`GatewayHandler.HandleGatewayMessage` routes `vaulttypes.MethodPublicKeyGet` requests directly to `handlePublicKeyGet` without going through `requestProcessor.ProcessRequest`, and `handlePublicKeyGet` unconditionally dereferences `*req.Params` before any nil-check, unlike sibling handlers reached via the request processor pipeline and unlike other codebase call sites (`ValidatedMessageFromReq`, `httpTriggerHandler.validatedTriggerRequest`) that explicitly guard `req.Params == nil`. A crafted JSON-RPC request omitting `params` (or `"params": null"`) causes a Go nil-pointer panic in this code path.

## Finding Description
`HandleGatewayMessage` dispatches on `req.Method` [2](#0-1) , and for `vaulttypes.MethodPublicKeyGet` calls `h.handlePublicKeyGet(ctx, gatewayID, req)` with no prior validation or authorization step. `handlePublicKeyGet` then does `json.Unmarshal(*req.Params, r)` without checking `req.Params` for nil [3](#0-2) . Since `req` is a `*jsonrpc.Request[json.RawMessage]` and `Params` is `*json.RawMessage`, a JSON-RPC request with a missing or `null` `params` field decodes `req.Params` to `nil`, and `*req.Params` panics with a nil pointer dereference.

This is confirmed as a recognized hazard elsewhere in the same codebase: `common.ValidatedMessageFromReq` explicitly checks `if req.Params == nil` before use, and `httpTriggerHandler.validatedTriggerRequest` does the same. No such guard exists in `handlePublicKeyGet`, nor is this method routed through `requestProcessor.ProcessRequest` (which is used by the other Vault Secrets methods and might otherwise perform validation).

Critically, requests are received and dispatched in `gatewayConnector.readLoop`, which runs in its own goroutine (`go c.readLoop(gatewayState)`) and calls `handler.HandleGatewayMessage(ctx, gatewayState.config.ID, &req)` synchronously with no `recover()` anywhere in the call chain [4](#0-3) . An unrecovered panic in any goroutine terminates the entire Go process, so this is not merely a per-request failure — it crashes the whole node.

## Impact Explanation
This is a genuine Denial-of-Service: any Gateway-connected node running the Vault capability can be crashed by a single crafted JSON-RPC message with method `vault.publicKeyGet` and no (or null) `params`. Because the panic occurs before `requestProcessor.ProcessRequest`/`Authorizer` runs, no allowlist/JWT authorization gate protects this path for this specific method, and the panic propagates unrecovered through `readLoop`, crashing the node process. This maps to CWE-476 Crash/DoS impact.

## Likelihood Explanation
High. Constructing a JSON-RPC request without `params` (or with `"params": null`) is trivial for any client able to reach the gateway endpoint that relays messages to this node's Vault handler. No credentials, special role, or complex setup is required beyond being able to send a message to the relevant Gateway that gets routed to this handler.

## Recommendation
Add an explicit `req.Params == nil` check at the top of `handlePublicKeyGet` (mirroring `common.ValidatedMessageFromReq` / `httpTriggerHandler.validatedTriggerRequest`) and return a `UserMessageParseError`/`ErrInvalidRequest` response instead of dereferencing a possibly-nil pointer. Additionally, consider adding a top-level `recover()` in `gatewayConnector.readLoop` (or in `HandleGatewayMessage`) so that a panic in any single handler cannot crash the whole node process, and evaluate whether `MethodPublicKeyGet` should also flow through `requestProcessor.ProcessRequest` for consistency with the other Vault methods.

## Proof of Concept
Send a Gateway JSON-RPC message such as:
```json
{
  "jsonrpc": "2.0",
  "id": "poc-1",
  "method": "vault.publicKeyGet"
}
```
(omitting `params`, or `"params": null`). This is delivered via `gatewayConnector.readLoop` to `GatewayHandler.HandleGatewayMessage` → `handlePublicKeyGet`, where `req.Params` is `nil` and `json.Unmarshal(*req.Params, r)` panics. A Go unit test can directly call `GatewayHandler.HandleGatewayMessage(ctx, gatewayID, &jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, Params: nil})` and observe the panic, or an integration test can send the equivalent raw JSON message over the WebSocket connection from a Gateway to a node and observe the node process crash.

func (c *gatewayConnector) readLoop(gatewayState *gatewayState) {
	defer c.closeWait.Done()
	ctx, cancel := c.shutdownCh.NewCtx()
	defer cancel()

	for {
		select {
		case <-c.shutdownCh:
			return
		case item := <-gatewayState.conn.ReadChannel():
			var req jsonrpc.Request[json.RawMessage]
			err := json.Unmarshal(item.Data, &req)
			if err != nil {
				c.lggr.Errorw("parse error when reading from Gateway", "id", gatewayState.config.ID, "err", err)
				break
			}
			c.handlersMu.RLock()
			handler, exists := c.handlers[req.Method]
			c.handlersMu.RUnlock()
			if !exists {
				c.lggr.Errorw("no handler for method", "id", gatewayState.config.ID, "method", req.Method)
				break
			}
			// do not break on error. HandleGatewayMessage handles errors
			// by sending a response back to the Gateway.
			err = handler.HandleGatewayMessage(ctx, gatewayState.config.ID, &req)
			if err != nil {
				c.lggr.Warnw("failed to handle message from Gateway", "id", gatewayState.config.ID, "method", req.Method, "err", err)
			}
		}
	}
}
