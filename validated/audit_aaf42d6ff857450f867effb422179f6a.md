### Title
PoaBridge.findMatchingWithdrawal matches only by assetId, causing status/txHash misattribution between two same-asset withdrawals in one intent - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` delegates to `findMatchingWithdrawal`, which selects a withdrawal record from the PoA bridge API purely by matching `nep141:${near_token_id}` to `assetId`, with no use of `destinationAddress`, `amount`, or `index`. When a user constructs a single intent containing two POA withdrawals of the same `assetId` to different `destinationAddress`es, both `describeWithdrawal({index:0})` and `describeWithdrawal({index:1})` calls resolve against the same (typically first-found) API record, so an integrator can attribute one recipient's `transfer_tx_hash` to the other's withdrawal.

### Finding Description
Broken equality: `(status, txHash)` returned for `WithdrawalIdentifier{index: i}` must equal the actual outcome of withdrawal `i`. Instead, `findMatchingWithdrawal` (packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:418-427) does:
```
return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
```
This ignores `index` entirely and returns `Array.prototype.find`'s first match. `createWithdrawalIdentifiers` (packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107) assigns `index: 0, 1, 2...` per bridge route as it iterates the caller-supplied `withdrawalParams` array, but nothing rejects or reorders when two entries share the same `assetId` under the same bridge route.

An unprivileged user (or the counterparty whose withdrawal params an integrator forwards) can submit `withdrawalParams = [{assetId: "nep141:btc.omft.near", destinationAddress: A, amount: X}, {assetId: "nep141:btc.omft.near", destinationAddress: B, amount: Y}]` in one call. Both entries pass `PoaBridge.supports()` (same route), so `createWithdrawalIdentifiers` produces `wid0 = {index:0,...}` and `wid1 = {index:1,...}` for the same bridge instance. When the PoA API later reports two COMPLETED withdrawal records with the same `near_token_id` but different `transfer_tx_hash`/`address`, `describeWithdrawal` for both `wid0` and `wid1` calls `findMatchingWithdrawal` with the same `assetId` and receives the identical first array element — same `transfer_tx_hash` — because there is no disambiguation by `index`, `destinationAddress`, or `amount`.

The code comment above `findMatchingWithdrawal` (lines 409-416) explicitly documents this as a known, unresolved limitation ("multiple withdrawals of the same token in a single transaction are not supported"), confirming this is not a hypothetical edge case but an acknowledged gap with no compensating guard anywhere in `supports()`, `validateWithdrawal()`, or the `withdrawal-watcher` index-assignment logic.

### Impact Explanation
An integrator relying on `sdk.watchWithdrawal`/`createWithdrawalCompletionPromises` (built on `describeWithdrawal`) to determine when/how to credit off-chain balances or mark a withdrawal fulfilled will receive the wrong `txHash` for one of the two withdrawals. This is a status/hash misreport that can cause the integrator to credit or refund incorrectly — e.g., treat withdrawal for recipient B as completed using recipient A's `transfer_tx_hash`, or vice versa — matching the "High" impact category ("a status or hash misreport making an integrator credit or refund twice"). It occurs for any pair (or more) of same-asset POA withdrawals batched in a single intent, and is fully repeatable by any user who batches such withdrawals.

### Likelihood Explanation
Precondition: the user (or a counterparty whose params an integrator forwards unmodified) must include ≥2 withdrawal params with the same POA-bridge `assetId` in a single call that gets translated into one intent/transaction, and the PoA bridge indexer must return ≥2 matching records for that `withdrawal_hash`. Nothing in `supports()`, `validateWithdrawal()`, or `createWithdrawalIdentifiers` blocks or reorders duplicate-asset withdrawals, so the attacker cost is zero — it only requires normal SDK usage with a crafted `withdrawalParams` array. This is deterministic and repeatable every time duplicate-asset POA withdrawals are batched together.

### Recommendation
Disambiguate `findMatchingWithdrawal` beyond `assetId` — e.g., additionally match by `destinationAddress`/`amount`, or (per the existing code comment's suggestion) sort both the API's returned withdrawals and the local per-bridge withdrawal params by `amount` (since relayer fees are identical for same-token withdrawals, relative ordering is preserved) and match by position/`index`. Alternatively, reject/flag batches containing duplicate `assetId` for the POA bridge route in `createWithdrawalIdentifiers` or `PoaBridge.supports()` until the API/indexer can disambiguate withdrawals unambiguously.

```typescript
/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```

```typescript
export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
```
