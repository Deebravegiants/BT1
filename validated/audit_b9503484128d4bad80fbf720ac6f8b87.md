### Title
Hostile mint pre-seed of the HyperSwap V2 TOKEN/LT pair can force the locked graduation LP to open materially off the curve-close price when the corrective rebalance swap exceeds its per-side budget cap - (File: packages/contracts/src/Bonding.sol)

### Summary
The external report's bug class is "administrators can change system parameters/state at any time with no advance notice, letting them front-run users." alt.fun has no admin-timelock surface reachable by unprivileged users, but it has a structurally analogous *timing/front-running* window: graduation is split into two permissionless transactions (`_enterGraduating` then `finalizeGraduation`), and any address can act on the intervening `Graduating` state before the protocol's own liquidity-seeding transaction lands. The protocol's own documentation and tests (`test/TwoPhaseGraduation.t.sol`) acknowledge an accepted residual ("M-02 regime") where an extreme hostile pre-seed of the HyperSwap pair pushes the rebalance swap past its per-side budget, so the final LP is seeded at a price materially different from the curve-close price — one of the explicitly in-scope impact categories ("an LP seeded away from the curve close price").

### Finding Description
`Bonding._enterGraduating` fires inline at the end of the threshold-crossing buy, caches `tokensForLP`/`ltFromPair` at the curve-close ratio, and flips lifecycle to `Graduating`, freezing curve trading [1](#0-0) . `finalizeGraduation` is a separate, permissionless transaction that seeds the HyperSwap V2 pair using the cached values [2](#0-1) . Between these two transactions, any unprivileged address can pre-create the pair and mint a hostile-ratio LP position (`pair.mint(attacker)`), as demonstrated by the project's own `_grieferMintPreSeed` helper [3](#0-2) .

`_seedUniswapV2Direct` defends against this by rebalancing the pool toward the curve-close ratio via a direct `pair.swap`, computing the swap input with `_noFeeSwapInput`, "capped at our per-side budget" [4](#0-3) . The project's own regression test proves that when the pre-seed ratio is extreme enough (e.g. LT reserve at 200× the curve-close ratio relative to a tiny token reserve), the optimal rebalancing swap exceeds this budget cap, and the resulting pool "opens materially off curve-close" — explicitly asserted to be more than 20% away from the true curve-close price: [5](#0-4) 

This is a direct, code-confirmed instance of the report's underlying "unpredictable behavior from bad timing" class: because `finalizeGraduation` is permissionless and separated in time from `_enterGraduating`, and the corrective mechanism is capped, an attacker can act in the timing gap to force the *protocol's own locked LP* (held in `LPLock`, which "has no withdraw / rescue path in v1" [6](#0-5) ) to be seeded at a materially wrong price.

### Impact Explanation
The test's own assertions show the *pre-seeder* cannot personally profit (`claimValue <= depositValue`) [7](#0-6) . However, the underlying economic fact remains: the LP that opens materially off curve-close (>20% price deviation in the test) is *the protocol's own permanently-locked LP* backing every post-graduation trader. Any third party (not necessarily the original pre-seeder) can immediately arbitrage the mispriced pool against the true curve-close price / external LT exchange rate, extracting value from `LPLock`'s frozen position — this is unrecoverable because `LPLock` cannot withdraw. This directly matches the in-scope impact bar: "an LP seeded away from the curve close price" causing permanent freezing/loss of LP funds, at the expense of the protocol and, transitively, every trader who trades the graduated pool at a materially wrong opening price.

### Likelihood Explanation
Requires only unprivileged actions: minting/holding some LT and the launched token (obtainable via a normal curve buy, as the test's `_grieferAccumulate` shows [8](#0-7) ), creating the HyperSwap pair, and calling `pair.mint` with an extreme reserve ratio before `finalizeGraduation` executes. This is achievable by watching for the `TokenGraduating` event and racing the keeper (a Cloudflare Worker keeper handles the happy path, but "anyone can call to rescue a stuck token" [2](#0-1) , meaning `finalizeGraduation` timing is not guaranteed). The exact budget threshold and magnitude needed (per the test, a 200× LT-rich pre-seed with reserves scaled at ~1/100 of `tokensForLP`) is fully computable on-chain from `pendingGraduation` state, which is publicly readable, making the attack deterministic rather than probabilistic.

### Recommendation
- Increase or make dynamic the per-side rebalance budget so that realistic hostile-pre-seed magnitudes are always fully correctable, rather than accepting an off-price residual once the swap is capped.
- Alternatively, when the budget cap binds (i.e., the optimal swap exceeds it), don't deposit the remaining off-ratio inventory into the LP at all — hold it in `Bonding` (or route it through an iterative/multi-step rebalance across the swap cap) until the ratio can be safely corrected, rather than locking a mispriced LP permanently in `LPLock`.
- Consider giving `LPLock` (or a dedicated permissioned/timelocked path) an emergency rebalancing/withdrawal capability precisely for this documented M-02 residual, since "no withdraw path in v1" turns a temporary mispricing into a permanent loss.
- Re-evaluate whether `finalizeGraduation`'s permissionless, un-timed execution window should be bounded (e.g., a maximum delay after `_enterGraduating` before which no external pre-seed can be canonicalized, or requiring the pair to be created atomically inside `_enterGraduating` even though pre-creation alone doesn't fully close the gap per the team's own analysis [9](#0-8) ).

### Proof of Concept
This is exercised end-to-end by the project's own test, confirming the vulnerable state is reachable and produces an off-curve-close LP price: [10](#0-9) 

1. Launch a token and buy enough on the curve to accumulate the launched token (`_grieferAccumulate`).
2. Drive the curve into `Graduating` via a threshold-crossing buy (`_enterGraduating` fires inline).
3. Before `finalizeGraduation` is called, create the HyperSwap V2 pair for TOKEN/LT and call `pair.mint(attacker)` with an extreme LT-rich ratio (e.g. `reserveToken = tokensForLP/100`, `reserveLt = ltFromPair*200`), which the test shows exceeds the `_noFeeSwapInput` per-side budget (`> 99% of tokensForLP`).
4. Call `finalizeGraduation(tokenAddress)` (permissionless, callable by anyone).
5. Observe the resulting pool price is >20% off the curve-close price (`_poolPriceLtPerToken` assertion), and that the LP is permanently locked in `LPLock` with no rescue path — the mispricing persists and is extractable by arbitrage against the true price, at the expense of the protocol's frozen LP.

```markdown
#### Regime 3 — mint pre-seed (the actual exploit)

Attacker called `pair.mint(attacker)` against a self-funded dust seed. Reserves are non-zero at a hostile ratio. We:

1. **Compute the swap input** that would drive the pool ratio back to the curve-close ratio under the no-fee constant-product model: `s = sqrt(reserveIn · reserveOut · targetN / targetD) − reserveIn`, capped at our per-side budget. Implementation in `_noFeeSwapInput`. Closed-form via OZ `Math.sqrt + Math.mulDiv`; no binary search, no convergence loop.
2. **Execute the swap directly on the pair** via `pair.swap(amount0Out, amount1Out, address(this), "")`. We read the output from the pair's own fee-aware `getAmountOut` quote and pass it as the output. **Bypasses the router** — HyperSwap's V2 router has no canonical `swapExactTokensForTokens` (see "HyperSwap Router non-standard ABI" above). Same direct-to-pair pattern Zap uses for post-grad user swaps. Implementation in `_pairRebalance`.
3. **Deposit the remaining inventory** via `router.addLiquidity(rest, 1, 1, lpLock, ...)`. The router's `quote()`-based optimal split deposits only the matched-ratio subset; neither side becomes a `min()` donation. Off-ratio remainder stays in `Bonding`. The router's `addLiquidity` IS canonical V2 on HyperSwap (verified selector `0xe8e33700`), so this leg is safe to keep on the router and gets the `quote()` math for free.
```

```text
    function _grieferMintPreSeed(
        address tokenAddr,
        uint256 reserveTokenAmt,
        uint256 reserveLtAmt
    ) internal returns (address hyperPair) {
```

```text
    ///         deposits materially off curve-close. Finalize must still succeed
    ///         (no brick), the over-funded LT side must be confiscated to the
    ///         owner, and the pre-seeder must end net-negative.
    function test_hostilePreSeed_budgetCappedSwap_isNotProfitable() public {
        (address tokenAddr,) = _launchToken();
        _enterGraduating(tokenAddr);

        (uint256 tokensForLP, uint256 ltFromPair,,) = bonding.pendingGraduation(tokenAddr);

        // Extreme LT-rich shape: TOKEN side at 1% of target, LT side at 200x.
        // The optimal TOKEN-in swap to reach the cached ratio is ~1.4x
        // `tokensForLP`, so the 99%-of-`tokensForLP` budget cap binds and the
        // pool stays ~2x off curve-close after the swap.
        uint256 reserveToken = tokensForLP / 100;
        uint256 reserveLt = ltFromPair * 200;

        // M-02 precondition: the optimal swap exceeds the budget (this is the
        // budget-capped regime, distinct from the swap-rounds-to-zero fallback
        // covered by the dust tests above).
        assertGt(
            _noFeeSwapInputUncapped(reserveToken, reserveLt, tokensForLP, ltFromPair),
            (tokensForLP * 99) / 100,
            "setup: optimal rebalance swap must exceed the per-side budget (M-02 regime)"
        );

        deal(tokenAddr, griefer, reserveToken);
        address hyperPair = _grieferMintPreSeed(tokenAddr, reserveToken, reserveLt);
        uint256 grieferLp = MockHyperswapPair(hyperPair).balanceOf(griefer);
        uint256 ownerLtBefore = lt.balanceOf(bonding.owner());

        bonding.finalizeGraduation(tokenAddr);
        assertTrue(bonding.isGraduated(tokenAddr), "finalize must succeed despite an unrecoverable pre-seed");

        // The accepted residual: no bounded swap can correct a 200x LT-rich
        // pre-seed, so the pool opens materially off curve-close.
        assertGt(
            _poolPriceLtPerToken(hyperPair, tokenAddr),
            (((ltFromPair * 1e18) / tokensForLP) * 12) / 10,
            "M-02 regime: pool opens materially off curve-close"
        );

        // The over-funded LT side is arbed out by the rebalance swap and swept
        // to the owner — the pre-seeder cannot recover it.
        assertGt(
            lt.balanceOf(bonding.owner()) - ownerLtBefore,
            reserveLt / 2,
            "the over-funded LT side must be confiscated to the owner"
        );

        // P&L: the pre-seeder's residual LP, valued at the fair (curve-close)
        // price, is worth a fraction of what they deposited — the attack is
        // cost-negative.
        uint256 claimValue = _lpValueAtCurveClose(hyperPair, tokenAddr, grieferLp, tokensForLP, ltFromPair);
        uint256 depositValue = _depositValueAtCurveClose(reserveToken, reserveLt, tokensForLP, ltFromPair);
        assertLe(claimValue, depositValue, "pre-seeder must not profit (P&L <= 0)");
        assertLt(claimValue * 2, depositValue, "pre-seeder must lose materially, not merely break even");
    }
```
