### Title
Relayer fee withdrawals and governance host-revenue withdrawals both drain the same unreserved `EvmHost` balance, so the relayer's on-chain "amount owed" cache can outlive the actual funds backing it - ([File: evm/src/core/EvmHost.sol])

### Summary
`pallet-ismp-relayer` tracks how much fee-token each relayer is owed on a given destination chain in a `Fees` storage map, and zeroes that entry the moment a withdrawal is dispatched — before the payout is actually confirmed on the destination chain. The payout itself is executed by `EvmHost.withdraw()`, an unconditional `transfer`/`safeTransfer` of `params.amount` out of the host's total fee-token balance, gated only by `restrict(_hostParams.hostManager)`. The exact same function and the exact same balance are also used to pay out unrelated governance "host revenue" withdrawals dispatched from `pallet-ismp-host-executive`. Neither side's cached "amount owed" accounts for what the other side has already claimed or intends to claim from the shared pool, so a relayer's withdrawal — even though `Fees` has already been optimistically zeroed on Hyperbridge — can permanently fail on-chain once governance (or another relayer) has drained the shared balance below what is actually still owed.

### Finding Description
`pallet-ismp-relayer::withdrawal::Pallet::withdraw` reads `available_amount = Fees::<T>::get(dest_chain, address)`, dispatches a POST to the destination chain's `HostManager`, and immediately zeroes the entry: [1](#0-0) 

The destination `HostManager.onAccept` unconditionally forwards the amount to `IHostManager(host).withdraw(...)`: [2](#0-1) 

`EvmHost.withdraw()` performs a raw, unconditional transfer out of the host's total fee-token/native balance with no reservation accounting tying the amount to what is actually earmarked for that specific relayer: [3](#0-2) 

The same `withdraw()` entry point (and the same underlying balance) is also used for governance-initiated "host revenue" withdrawals dispatched independently from `pallet-ismp-host-executive::withdraw`, which has its own unrelated accounting and knows nothing about relayers' outstanding `Fees` balances: [4](#0-3) 

This is structurally identical to the referenced M-25 bug: a single shared pool of funds is drawn down by more than one code path/actor, while a cached "amount available/owed" value (here, `pallet-ismp-relayer::Fees[dest_chain][relayer]`, there, `treasury.liquidatedCollateralAmountInWei`) is not reconciled against the other path's consumption. In the CDS case the treasury balance dropped after `updateDepositedCollateralAmountInWei` moved collateral to "liquidated" without ever being decremented on withdrawal; here, the EVM host's actual fee-token balance can be depleted by governance's protocol-revenue withdrawal (or by other relayers whose accumulation/withdraw races complete first) without any decrement to the relayer's already-zeroed `Fees` claim, and `EvmHost.withdraw()` has no per-claimant reservation to prevent overspending the shared balance.

Because `Fees` is zeroed optimistically at dispatch time (see the doc comment "The `Fees` entry is zeroed so the same balance cannot be withdrawn twice"), a relayer whose payout request reverts on the destination host (insufficient balance) loses its accounted claim outright — there is no on-chain record left to retry against, unlike a simple insufficient-balance revert that could be resubmitted with knowledge of the owed amount. [5](#0-4) 

### Impact Explanation
A relayer's withdrawal transaction to the destination `HostManager`/`EvmHost` can revert (`WithdrawalFailed()` on native transfers, or the `SafeERC20` revert on ERC20 transfers) once the shared fee-token balance held by `EvmHost` has been drawn down below the aggregate amount actually owed to all relayers plus any governance revenue withdrawal. Because Hyperbridge's `Fees` entry for that relayer is already zeroed at dispatch time, the relayer's accounted claim is permanently lost with no path to re-claim the same amount — this is a permanent freezing/loss of relayer-earned funds, reachable by any permissionless relayer simply calling the unsigned `withdraw` extrinsic (a normal part of protocol operation, not requiring any privileged role).

### Likelihood Explanation
Likelihood depends on whether relayer fee accumulation and governance host-revenue withdrawal genuinely compete for the same underlying `EvmHost` fee-token balance without any headroom/reservation being enforced elsewhere (e.g., a governance-side check that only withdraws "excess" balance above all currently-owed relayer fees). I was unable to fully trace the fee-collection code in `EvmHost.dispatch`/`IsmpDispatcher` before running out of investigation budget, so I cannot confirm with certainty that governance's protocol-fee revenue is not segregated from relayer-fee revenue at the point of collection. What is confirmed is that both withdrawal paths ultimately funnel through the identical `EvmHost.withdraw()` primitive against the identical balance, with zero on-chain reservation logic — the same structural gap that produced M-25 in the audited project.

### Recommendation
- Add an on-chain reservation/accounting invariant in `EvmHost` (or the `HostManager`) that tracks how much of the fee-token balance is earmarked for accumulated-but-unwithdrawn relayer fees, and refuse governance/host-revenue withdrawals that would dip into that earmarked amount.
- Alternatively, segregate relayer-fee revenue and protocol/governance revenue into separate balances/tokens (or separate escrow accounts) at collection time so the two withdrawal paths never compete for the same pool.
- On the relayer side, avoid zeroing `Fees` before the destination-chain payout is confirmed successful; keep the claim recorded (or refundable) until delivery succeeds so a transient insufficient-balance failure does not translate into a permanently lost claim.

### Proof of Concept
Conceptual sequence (not a instrumented PoC due to tool limits):
1. Relayer A accumulates fees on Hyperbridge for delivering messages from `StateMachine::Evm(X)`, increasing `Fees[Evm(X)][A]` to `N` fee-tokens — backed by fee-token previously escrowed into `EvmHost` on chain X.
2. Governance separately dispatches a `pallet-ismp-host-executive::withdraw` for chain X requesting the entire (or a large fraction of the) current `feeToken.balanceOf(EvmHost)`, believing it is "host revenue," and this executes successfully before relayer A's withdrawal is delivered.
3. Relayer A calls `pallet-ismp-relayer::withdraw`, which zeroes `Fees[Evm(X)][A]` and dispatches a POST instructing `HostManager`/`EvmHost.withdraw()` to pay `N` fee-tokens to A.
4. `EvmHost.withdraw()` attempts `IERC20(feeToken).safeTransfer(A, N)`, which reverts because the balance was already drained in step 2.
5. Relayer A's `Fees` entry is already zero on Hyperbridge — the claim is unrecoverable through the normal flow.

    function onAccept(IncomingPostRequest calldata incoming)
        external
        override
        restrict(msg.sender, _params.host)
        restrict(incoming.relayer, _params.admin)
    {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        } else if (action == OnAcceptActions.SetAdmin) {
            // Rotates the governance relayer.
            address newAdmin = abi.decode(request.body[1:], (address));
            if (newAdmin == address(0)) revert InvalidAdmin();
            emit AdminUpdated({previous: _params.admin, current: newAdmin});
            _params.admin = newAdmin;
        }
    }

    /**
     * @dev withdraws host revenue to the given address, can only be called by cross-chain governance
     * @param params, the parameters for withdrawal
     */
    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }

		/// Issues a call to withdraw the protocol fees from an evm chain
		#[pallet::weight(T::DbWeight::get().writes(1))]
		#[pallet::call_index(4)]
		pub fn withdraw(
			origin: OriginFor<T>,
			state_machine: StateMachine,
			withdrawal_params: WithdrawalParams,
		) -> DispatchResult {
			T::HostExecutiveOrigin::ensure_origin(origin)?;

			ensure!(state_machine.is_evm(), Error::<T>::UnsupportedStateMachine);

			let HostParam::EvmHostParam(params) = HostParams::<T>::get(state_machine)
				.ok_or_else(|| Error::<T>::UnknownStateMachine)?;

			let data = withdrawal_params
				.abi_encode()
				.map_err(|_| Error::<T>::InvalidBeneficiaryAddress)?;

			let post = DispatchPost {
				dest: state_machine,
				from: PALLET_ID.to_bytes(),
				to: params.host_manager.0.to_vec(),
				timeout: 0,
				body: data,
			};

			let dispatcher = <T as Config>::IsmpHost::default();

			// Account is not useful in this case
			dispatcher
				.dispatch_request(
					DispatchRequest::Post(post),
					FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() },
				)
				.map_err(|_| Error::<T>::DispatchFailed)?;

			Self::deposit_event(Event::<T>::Withdraw {
				address: sp_runtime::BoundedVec::truncate_from(
					withdrawal_params.beneficiary_address,
				),
				state_machine,
				amount: withdrawal_params.amount,
			});

			Ok(())
		}
