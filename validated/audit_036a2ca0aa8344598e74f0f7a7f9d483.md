### Title
Deposit-free HRMP channel-open/cancel loop against system parachains enables cost-free DMP queue/fee-factor griefing - (File: `polkadot/runtime/parachains/src/hrmp.rs`)

### Summary
`Pallet::init_open_channel` waives the sender deposit whenever either endpoint `is_system()`, and `Pallet::cancel_open_request` allows immediate, uncooled cancellation of a pending (unconfirmed) request. Any parachain sovereign origin reachable through `ensure_parachain` can therefore loop `hrmp_init_open_channel` → `hrmp_cancel_open_request` against a system parachain indefinitely at zero HRMP-specific cost, each iteration pushing an `HrmpNewChannelOpenRequest` downward message into the victim's DMQ.

### Finding Description
`Pallet::init_open_channel` computes the deposit as: [1](#0-0) 
Because `is_system = origin.is_system() || recipient.is_system()`, any request targeting a system chain sets `deposit = 0`, skipping `T::Currency::reserve` entirely. The only bound on concurrent outstanding requests is the outbound-channel-limit check: [2](#0-1) 
but this check only limits *simultaneous* open requests, not the rate of open/cancel cycles over time. After each `init_open_channel`, a downward `HrmpNewChannelOpenRequest` message is unconditionally queued to the recipient via `Self::send_to_para`: [3](#0-2) 
`Pallet::cancel_open_request` then immediately removes the request (no cooldown, no minimum request lifetime) and unreserves whatever deposit was taken (zero, in the system-chain case): [4](#0-3) 
The dispatchables `hrmp_init_open_channel` and `hrmp_cancel_open_request` only require `ensure_parachain` origin, i.e., any registered parachain's sovereign/UMP-origin can call them: [5](#0-4) [6](#0-5) 
Because the sender deposit is the only economic disincentive in this flow, and it is explicitly waived for any request touching a system chain, an attacking para can repeat init→cancel every block (subject only to its own UMP message quota), continuously injecting protocol notification messages into the target's downward message queue without ever paying `hrmp_sender_deposit`/`hrmp_recipient_deposit` and without ever completing a channel.

### Impact Explanation
Each loop iteration adds one message to the victim system parachain's `DownwardMessageQueue`, forcing the victim to spend block weight dequeuing/decoding `HrmpNewChannelOpenRequest` XCMs it never asked for, and contributes to congestion-based `DeliveryFeeFactor` escalation on the relay→para queue, which raises delivery fees for all legitimate senders to that system chain. Because the deposit that normally scales the cost of this spam with volume is waived for system-chain targets, the attacker's cost is effectively just relay-chain UMP bandwidth from its own parachain, not a per-request bond — breaking the intended "queue/fee logic must not be bypassable at no cost" invariant for this specific system-chain code path.

### Likelihood Explanation
The precondition (control of a registered parachain sovereign account able to dispatch through `ensure_parachain`) is non-trivial but realistic — it covers any malicious, compromised, or economically motivated para team, which is the standard threat actor model for HRMP-level griefing analyses. The attack is fully repeatable every block the attacker can include a UMP dispatch, with no cooldown, minimum request age, or per-target rate limiter preventing the open/cancel cycle.

### Recommendation
- Do not fully waive the sender/recipient deposit for `is_system` channels; instead require a minimal, non-refundable-on-cancel fee (or a short-lived bond) that scales with request frequency, or
- Add a cooldown / minimum request lifetime before `cancel_open_request` can be invoked for the same `(sender, recipient)` pair, and/or a per-origin rate limiter (e.g., max open+cancel cycles per session) independent of the concurrent-channel-count check, especially for system-chain destinations.

### Proof of Concept
Integration test in `polkadot/runtime/parachains/src/hrmp/tests.rs` style:
1. Register attacker para `para_a` (non-system) and configure a system para id `sys` (e.g. inside the reserved system range) with zero free balance for `para_a` beyond ED (no funds reserved for deposit since `is_system` waives it).
2. Loop N times per block: call `Hrmp::init_open_channel(para_a, sys, cap, size)` then `Hrmp::cancel_open_request(para_a, HrmpChannelId{sender: para_a, recipient: sys})`.
3. Assert after N iterations: `Dmp::dmq_length(sys)` == N (or grows linearly with iterations before `sys` processes them), `Balances::reserved_balance(para_a)` stays `0` throughout (no deposit ever taken), and `Dmp::DeliveryFeeFactor::<T>::get(sys)` increases as the queue backlog grows — demonstrating unbounded, cost-free queue/fee-factor churn against the victim system para.

			origin: OriginFor<T>,
			channel_id: HrmpChannelId,
			open_requests: u32,
		) -> DispatchResult {
			let origin = ensure_parachain(<T as Config>::RuntimeOrigin::from(origin))?;
			ensure!(
				HrmpOpenChannelRequestsList::<T>::decode_len().unwrap_or_default() as u32 <=
					open_requests,
				Error::<T>::WrongWitness
			);
			Self::cancel_open_request(origin, channel_id.clone())?;
			Self::deposit_event(Event::OpenChannelCanceled { by_parachain: origin, channel_id });
			Ok(())
		}

	fn cancel_open_request(origin: ParaId, channel_id: HrmpChannelId) -> DispatchResult {
		// check if the origin is allowed to close the channel.
		ensure!(channel_id.is_participant(origin), Error::<T>::CancelHrmpOpenChannelUnauthorized);

		let open_channel_req = HrmpOpenChannelRequests::<T>::get(&channel_id)
			.ok_or(Error::<T>::OpenHrmpChannelDoesntExist)?;
		ensure!(!open_channel_req.confirmed, Error::<T>::OpenHrmpChannelAlreadyConfirmed);

		// Remove the request by the channel id and sync the accompanying list with the set.
		HrmpOpenChannelRequests::<T>::remove(&channel_id);
		HrmpOpenChannelRequestsList::<T>::mutate(|open_req_channels| {
			if let Some(pos) = open_req_channels.iter().position(|x| x == &channel_id) {
				open_req_channels.swap_remove(pos);
			}
		});

		Self::decrease_open_channel_request_count(channel_id.sender);
		// Don't decrease `HrmpAcceptedChannelRequestCount` because we don't consider confirmed
		// requests here.

		// Unreserve the sender's deposit. The recipient could not have left their deposit because
		// we ensured that the request is not confirmed.
		T::Currency::unreserve(
			&channel_id.sender.into_account_truncating(),
			open_channel_req.sender_deposit.unique_saturated_into(),
		);

		Ok(())
	}
