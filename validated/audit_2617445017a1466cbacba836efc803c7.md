### Title
Owner-removal quorum can silently downgrade the multisig timelock override threshold, letting a minority coalition bypass the safety delay - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`multisig_account.move` adds a `MultisigAccountTimeLock` resource with a `num_signatures_required` (base quorum) and a stricter `override_threshold` that is documented to require more approvals than the base quorum in order to bypass the timelock delay (`EINVALID_TIMELOCK_OVERRIDE_THRESHOLD: "Timelock override threshold must be greater than num_signatures_required and at most the number of owners"`) [2](#0-1) . However, the shared `update_owner_schema` function — invoked by `remove_owners`/`remove_owner`/`swap_owners*`, all of which only need the *base* `num_signatures_required` approvals to execute — automatically clamps `override_threshold` down whenever it exceeds the (now-shrunk) owner count, and does so without re-validating that the override threshold still exceeds `num_signatures_required` by any meaningful safety margin: [3](#0-2) .

### Finding Description
The intended custody invariant is: `override_threshold > num_signatures_required`, so that bypassing the timelock delay for a pending transaction always requires strictly more owner approvals than are needed for ordinary governance actions like adding/removing owners. This is meant to prevent exactly the coalition size that can pass normal multisig proposals (the base quorum) from also being able to instantly execute a transaction that is supposed to be delayed.

The `remove_owners`/`remove_owner`/`swap_owners`/`swap_owners_and_update_signatures_required` entry functions only require the base `num_signatures_required` approvals (standard multisig quorum) [4](#0-3) . All of these route through `update_owner_schema`, which — after mutating the owner list — clamps `override_threshold` to `num_owners` if it now exceeds the owner count, and re-asserts only that `override_threshold > num_signatures_required` using the value it just clamped: [3](#0-2) .

Because owner removal itself only needs base quorum, a coalition of exactly `num_signatures_required` owners can:
1. Use their base quorum to remove enough non-colluding owners so that `num_owners` shrinks to a value they fully control (e.g., equal to their own coalition size).
2. This triggers the auto-clamp, setting `override_threshold = num_owners` (attacker-controlled value), which the assertion then accepts as long as it is still `> num_signatures_required` — a condition the coalition can arrange to just barely satisfy, or which may pass trivially depending on owner-count math.
3. With `override_threshold` now reduced to a value the same coalition can single-handedly reach, they can use it on a separately queued high-value transaction (e.g., a fund transfer) to bypass the timelock delay entirely, defeating the entire purpose of the safety period meant to give other owners/monitors time to react to a malicious pending transaction.

This is the direct analog of the reported bug class: a parameter that gates custody-relevant safety behavior (`bonus_rate`/`max_ltv` in the Mars example; `override_threshold` here) can be changed via a lower-privilege pathway (governance in the original; base-quorum owner-management in this one) than the value's security purpose demands, without an explicit unrestricted-value check tying the update back to the intended stronger invariant.

### Impact Explanation
If confirmed against the actual timelock-bypass execution logic, this allows a coalition meeting only the base multisig quorum (which could be a small subset of total owners, e.g. 2-of-5) to strip the extra-approval protection meant to prevent that exact-sized coalition from instantly moving custody-held assets (APT, coins, or any assets held by the multisig account) once a malicious transaction is queued, defeating the timelock's entire threat model (protection against a subset of compromised/colluding keys). This is custody-grade because it affects control over assets held by the multisig account itself.

### Likelihood Explanation
Requires an active colluding coalition of exactly the base-quorum size (not a single compromised key, and not full unanimous owner set) that is willing to also remove other owners — a reasonably deliberate but plausible insider/compromise scenario for any multisig protecting valuable custody. It also depends on whether the multisig's owners actually configured a `MultisigAccountTimeLock` with a meaningfully higher `override_threshold` in the first place; if timelock is unused, this path is irrelevant. Likelihood is low-to-moderate.

### Recommendation
Do not allow the standard `update_owner_schema` (reachable via base-quorum owner-removal/swap operations) to silently lower `override_threshold`. Instead, either (a) require the removal/swap operation itself to meet `override_threshold` approvals whenever an existing timelock config would need to be down-clamped, or (b) reject the owner-removal operation outright if it would force-clamp `override_threshold` below its originally configured value, requiring a separate, explicitly authorized (e.g., override-threshold-gated) transaction to intentionally lower the timelock protection.

### Proof of Concept
Conceptual sequence (exact function for override-threshold-based timelock bypass not directly located in this pass, so this should be validated against it):
1. Create a multisig account with 5 owners, `num_signatures_required = 2`, and a `MultisigAccountTimeLock` with `override_threshold = 5` (near-unanimous bypass).
2. Owners A and B (meeting the 2-of-5 base quorum) propose and execute `remove_owners` removing the other 3 owners C, D, E via `update_owner_schema` [5](#0-4) .
3. `num_owners` becomes 2; since `override_threshold (5) > num_owners (2)`, the code auto-clamps `override_threshold` to 2 [6](#0-5) .
4. A and B now fully control both the base quorum and the (clamped) override threshold, allowing them to bypass the timelock on any subsequently queued fund-transfer transaction that would otherwise require the delay for other owners to react.
