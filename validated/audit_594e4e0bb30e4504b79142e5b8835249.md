### Title
Venue-priced fills read Uniswap V4 pool mid with no size/impact term, letting a manipulated pool price drain solver liquidity - (File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts)

### Summary
The external report flags `mintSynth()`/`burnSynth()` in VaderPoolV2 for pricing large mint/redeem operations directly off pool reserves with no slippage/`minAmountOut` control, making them exploitable via front-running. The closest reachable analog in this repo is Hyperbridge's Simplex intent filler: when a trading pair has no static bid/ask curve, its price is derived directly from a Uniswap V4 pool's live tick (`sqrtPriceX96`), with no price-impact term and no execution-cost-based slippage bound, and this price is used to size real fills that pay out solver funds.

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` / `computeDirectPoolPriceUsd` compute a token's USD price directly from `sdkPool.token0Price`/`token1Price` (i.e., the pool's current mid, derived from `sqrtPriceX96`) at the moment of pricing: [1](#0-0) [2](#0-1) 

This price feeds `resolveLegRates` in `FXFiller` (the venue-pricing path for curve-less pairs), which uses it to compute how much output token the solver must pay for an order leg. The developer's own flow documentation confirms there is no defense against price manipulation beyond a static reference-price band: [3](#0-2) 

> "`computeDirectPoolPriceUsd` returns the **raw pool mid**... there is no size or impact term — `computeLegPolicyOutput` extends the mid linearly across the whole priced quantity. `checkPriceGuard` is the only defense on this path, and it checks deviation from a static reference, not execution cost."

The only mitigation is an optional `referencePrice`/`maxDeviationBps` guard, which is off by default and only bounds *drift from a hand-configured reference*, not manipulation within a single block/transaction: [4](#0-3) 

Because Uniswap V4 pool ticks can be moved atomically by a swap immediately preceding the order fill (classic sandwich/flash manipulation), an attacker can:
1. Swap in the exotic-token pool used for pricing to push the tick to a favorable mid price.
2. Place (or already have queued) an intent order whose output amount is sized by the filler off that manipulated mid, within the (optional, often unconfigured or wide) reference-price band.
3. Let the solver's `FXFiller`/`UniswapV4FundingPlanner` fill the order at the manipulated rate, paying out more of the exotic token (or stablecoin) than the true market price justifies.
4. Reverse the initial swap, netting the price-impact cost against the profit extracted from the over-priced fill.

This is structurally identical to the reported bug class: assets are minted/paid out based on a pool's spot price without any slippage/`minAmountOut`-style bound tied to execution cost, only an optional static-reference sanity check.

### Impact Explanation
A successful attack causes the solver to pay out tokens (stablecoin or exotic token) at a manipulated rate, directly transferring value from the solver's escrowed inventory to the attacker for a single filled intent order — a concrete loss of funds for whoever configures a `[vault.uniswapV4]` pool-priced pair without (or with a wide) `referencePrice`/`maxDeviationBps` guard. Given the design explicitly notes "no size or impact term," larger orders are priced identically to small ones at the manipulated mid, amplifying the extractable value with order size (bounded only by `maxOrderSize`).

### Likelihood Explanation
The `referencePrice`/`maxDeviationBps` guard is optional ("The two fields must be set together; omit both to leave the chain unguarded") and defaults to unguarded, so any deployer using pool-based pricing without configuring it is immediately exposed. Even with the guard configured, the guard only checks static deviation, not manipulation cost/depth, so a sufficiently liquid attacker (or thin pool) can still move the price within the allowed band while still extracting profit, since the guard is not an execution-cost-aware slippage check. Front-running/sandwiching a pool tick within a single block is a well-understood, cheap technique (flash loans, MEV), so likelihood is Medium-to-High for deployments using the venue-pricing feature.

### Recommendation
- Do not price fills purely from the instantaneous `sqrtPriceX96` mid; incorporate a TWAP/observation-based price or require multi-block confirmation before using pool state to size a fill.
- Apply an execution-cost-aware price-impact/slippage bound tied to the actual order size (analogous to `minAmountOut`), not only a static `referencePrice` deviation check.
- Make the `referencePrice`/`maxDeviationBps` guard mandatory (fail closed) for any pool-priced pair, rather than optional/unguarded by default.
- Consider bounding the swap/withdrawal `sqrtPriceLimitX96` and re-validating the post-fill pool state against the pre-fill quote to detect and revert on manipulation between quoting and execution.

### Proof of Concept
1. Configure a `[vault.uniswapV4]` pair without `referencePrice`/`maxDeviationBps` (an allowed, documented configuration) so pricing is purely pool-mid based: [5](#0-4) 
2. Attacker swaps a large amount in the exotic/stable Uniswap V4 pool used by `computeDirectPoolPriceUsd`, moving `sqrtPriceX96`/tick to a favorable direction.
3. Attacker submits (or has already submitted, timed to land after the manipulation) an intent order sized so `FXFiller.resolveLegRates` → `getExoticTokenPrice` reads the manipulated mid and computes an inflated `policyMaxOutput` for the leg, as shown in the linear-extension pricing path: [6](#0-5) 
4. The solver's fill logic (`UniswapV4FundingPlanner.planWithdrawalForToken`) withdraws liquidity/pays out based on that inflated price with only a fixed `spreadBps` (default 50 bps) LP-redemption slippage tolerance — not a price-manipulation guard: [7](#0-6) 
5. Attacker reverses the initial pool swap, realizing profit equal to the mispriced fill minus manipulation cost.

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

## Pool-Based Pricing

When **`[vault.uniswapV4]`** lists at least one position, cross-asset pairs without curves derive bid/ask prices from **Uniswap V4 pool state** (current tick). The pool acts as the price oracle instead of a static curve. Note this yields a **single** price used in both directions — a venue-priced pair has no bid/ask spread of its own, so its margin comes from `order.fees` alone.

With Uniswap V4 positions configured, you can **omit** `bidPriceCurve` and `askPriceCurve` on the pair. Pool pricing requires the pair's `token0` to be a USD stablecoin, and same-token pairs always need their curve. The optional **`spreadBps`** field (basis points) sets the slippage tolerance for on-chain LP redemptions; defaults to `50` (0.50%).

Uniswap V4 venue pricing uses pools that pair the exotic token with **USDC or USDT** (addresses from your chain config). When multiple positions exist for the same exotic token on a chain, the most-liquid qualifying pool's price is used.

```toml lineNumbers
[assets.CNGN]
"EVM-8453" = "0x46C85152bFe9f96829aA94755D9f915F9B10EF5F"

[[pairs]]
token0 = "USDC"
token1 = "CNGN"
maxOrderSize = "5000"       # no curves — priced from the pool

[vault.uniswapV4]
spreadBps = 50  # 0.5% slippage tolerance on LP redemptions
positions = [
    { chain = "EVM-8453", tokenId = "2087350" },
]
```

<Callout type="info">
Startup validation requires a pricing source per pair: **either** bid/ask price curves, **or** at least one `[vault.uniswapV4]` position. A pair with neither fails validation.
</Callout>

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```
