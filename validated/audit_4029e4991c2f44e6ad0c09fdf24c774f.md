This confirms the vulnerability. `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read from unauthenticated headers [2](#0-1) . `HmacValidator.validate` only verifies `to_signable_string` against `hmac` [3](#0-2) , so the `shop` field used for tenant identification is never covered by the signature. `Registry.process` still trusts `request.shop` to build `WebhookMetadata` passed to the handler [4](#0-3) .

### Title
Webhook `shop` header not covered by HMAC allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop` (and `topic`/`webhook_id`) values used to identify the tenant are taken from HTTP headers that are never part of the signed bytes. This breaks the identity binding `hmac == HMAC(bytes actually verified)` vs `bytes acted upon (shop header)`, mirroring the reported bug class where a field acted on (destination/tenant identity) is not covered by the integrity check that is supposed to authenticate it.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively:
```ruby
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers with no integrity protection:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [5](#0-4) 

`Utils::HmacValidator.validate` only checks `verifiable_query.to_signable_string` against the received HMAC — it never validates the headers:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [6](#0-5) 

`Registry.process` gates handling only on this body-only HMAC check, then forwards the unauthenticated `request.shop` straight into the handler's metadata, which host applications use to scope data to a tenant:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

Because the header `shop-domain` is excluded from the signed content, any request whose body produces a valid HMAC for the merchant's `api_secret_key` will be accepted with **whatever `shop` value the attacker places in the header**, regardless of which shop actually generated that HMAC-signed body. Concretely: an attacker who operates their own shop (Shop A) installed on the app receives real, validly-signed webhooks from Shopify for Shop A. They can then replay the exact same body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with Shop B's domain. `HmacValidator.validate` will still pass because it only checks the body bytes, and `Registry.process` will dispatch the payload to the handler labeled as belonging to Shop B.

### Impact Explanation
This breaks the binding `shop attributed to webhook == shop that actually produced the signed bytes`, letting an unprivileged attacker (any merchant who installs the app to obtain one legitimately signed webhook) forge webhook events attributed to an arbitrary other tenant/shop domain. Host applications built on this gem commonly use `WebhookMetadata#shop` to look up the tenant's session/access token and to write/update tenant-scoped data (e.g., processing `orders/create` payloads keyed by `shop`), so this is a cross-tenant data confusion vector reachable purely through the gem's documented webhook-processing API, with only replay of a self-obtained legitimate webhook required — no leaked secret, TLS interception, or privileged access needed.

### Likelihood Explanation
Any developer/merchant with an app installation can trigger genuine webhooks for their own shop (e.g., by updating an order), capture the raw body + valid HMAC, and replay it to the app's public webhook endpoint with a forged `shop-domain` header. This requires no special access beyond installing the app as an ordinary merchant, which the threat model treats as an unprivileged internet-adjacent actor.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed content that `to_signable_string` returns (or otherwise cryptographically bind them, e.g., signing the header block along with the body, as Shopify's own delivery does not sign headers so binding must occur in the app's session/token lookup instead of trusting the header). At minimum, document/require that host applications must not use `WebhookMetadata#shop` as an authoritative tenant identifier without cross-checking it against a shop known independently (e.g., derived from a persisted session tied to the specific delivery), and consider deriving shop identity from the payload body itself when available rather than from headers excluded from the HMAC.

### Proof of Concept
1. Install the target app on attacker-controlled Shop A; trigger a real event (e.g., create an order) so Shopify sends a legitimately HMAC-signed webhook: body `B`, header `x-shopify-hmac-sha256: H = HMAC(secret, B)`, `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Capture `B` and `H` from the delivery (attacker's own shop, no special privilege required).
3. Replay a POST to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: shop-b.myshopify.com` (any other merchant's shop domain known to the attacker, e.g., discoverable via the app's public storefront or other means).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `H` against `HMAC(secret, B)` — this passes since `B` and `H` are unchanged. [7](#0-6) 
5. The handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` and the attacker-controlled body `B`, causing the host app to process/store the forged event as if it came from Shop B. [8](#0-7)
