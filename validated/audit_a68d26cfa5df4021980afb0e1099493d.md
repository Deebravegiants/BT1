### Title
Webhook `shop` (and `topic`/`webhook-id`) identity is taken from unauthenticated HTTP headers never covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, then unconditionally trusts the `shop`, `topic`, and `webhook_id` values that were parsed from unsigned HTTP headers to dispatch the handler and populate `WebhookMetadata`. This breaks the intended identity binding `HMAC-verified bytes == bytes used to derive tenant identity`, because the header-derived shop domain is never part of the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`. Its `to_signable_string` returns only `@raw_body`: [1](#0-0) 

Its `hmac` is decoded from the `X-Shopify-Hmac-Sha256` header: [2](#0-1) 

But `shop`, `topic`, and `webhook_id` are read from separate, independent headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) that are **not** included in `to_signable_string` and therefore are not covered by the HMAC at all: [3](#0-2) [4](#0-3) 

`Registry.process` validates only the HMAC (i.e., only the body integrity), and then trusts `request.topic`, `request.shop`, and `request.webhook_id` directly to select the handler and build the metadata passed to the app's handler code: [5](#0-4) 

`HmacValidator.validate` / `validate_signature` only compare the computed HMAC of `to_signable_string` (the raw body) against the received HMAC header — nothing ties the `shop-domain` header value to that signature: [6](#0-5) 

**Binding broken (equality that should hold but doesn't):**
`shop_used_for_dispatch (from unsigned "shopify-shop-domain" header)` should equal `shop_bound_by_the_HMAC_signature`, but the signature only binds the raw body — it says nothing about which shop sent it. Any party who can produce a request with a valid HMAC over some body (which, notably, is computable if the body content itself is not secret/tied to the shop — e.g., for topics whose exact body an attacker can predict or replay from a legitimately-owned shop) can freely substitute the `shopify-shop-domain` header for any target shop, and the gem will accept the HMAC as valid and hand the attacker-chosen `shop` value straight to the host application's webhook handler via `WebhookMetadata`.

### Impact Explanation
This matches the reported bug class: an identity/tenant field (`shop`) that is acted upon (used to build `WebhookMetadata.shop`, and dispatched into the app's business logic keyed by that shop) is not part of the cryptographically verified data. A host application that trusts `WebhookMetadata#shop` (a very natural and expected assumption, since the gem's own `HmacValidator.validate(request)` call implies "this webhook request has been authenticated") to look up/act on a specific merchant's records can be tricked into acting on data attributed to the wrong tenant — a cross-tenant data confusion. This aligns with the "Critical - cross-tenant access" impact category, since the shop identity used to key merchant-specific processing is not authenticated even though the gem's API implies it is validated.

### Likelihood Explanation
Exploitability requires the attacker to have a valid HMAC for *some* body under the app's `client_secret` — which they can generate legitimately for their own shop (an unprivileged, attacker-owned Shopify store can create the exact same event, e.g. `orders/create`, and capture the resulting webhook request), then replay/re-issue the outer HTTP request with the `shopify-shop-domain` (and/or `shopify-webhook-id`) header value swapped to a victim shop's domain, while keeping the same (HMAC-covered) body bytes. Because `to_signable_string` never mixes in the shop header, the HMAC still validates. This is realistic for any host application that owns/operates an endpoint receiving webhooks from many shops (the standard multi-tenant SaaS pattern that this gem is built for).

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`) header values into the signed payload verification, e.g., by having `Webhooks::Request#to_signable_string` incorporate the shop/topic/webhook-id headers into the signable string (mirroring how Shopify's own webhook verification only guarantees body integrity per-request, so the gem must independently re-derive/pin the shop from a trusted channel), or by requiring hosts to cross-check the `shop` header against out-of-band knowledge (e.g., session/registration state) before trusting it. At minimum, document explicitly that `WebhookMetadata#shop` is unauthenticated header data and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Attacker registers/owns `attacker-shop.myshopify.com` and subscribes it to the same app/webhook topic (e.g., `orders/create`).
2. Attacker triggers an event on their own shop, capturing the legitimate webhook POST: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's secret), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker re-sends the request to the app's webhook endpoint, keeping body `B` and HMAC `H` unchanged, but replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the new shop header; `Utils::HmacValidator.validate(request)` still succeeds because `to_signable_string` only returns `B`.
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...))`, causing the host app to process/store attacker-controlled data under the victim shop's identity — a cross-tenant integrity/confusion issue, despite the request having "passed" the gem's HMAC check.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
