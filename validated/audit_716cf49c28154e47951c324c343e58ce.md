## Analysis Result [1](#0-0) 

Found a valid analog: a status-misreport bug in the PoA Bridge withdrawal-status matcher that breaks the equality "status reported == on-chain outcome" when a batch contains multiple withdrawals of the same asset.

### Title
Withdrawal status/hash misreported for batched same-asset withdrawals due to assetId-only matching - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal()` resolves the on-chain outcome of a specific withdrawal by asking `findMatchingWithdrawal()` to find the record in the PoA bridge indexer response that matches by `assetId` alone, ignoring the destination address and per-withdrawal index. When a single intent transaction contains two or more withdrawals of the same token (e.g. splitting one asset to two different destination addresses), `Array.prototype.find` returns the first record whose `near_token_id` matches — which may belong to a different withdrawal than the one being queried.

### Finding Description
`describeWithdrawal` is called per `WithdrawalIdentifier` (one per withdrawal in a batch) and delegates matching to: [2](#0-1) 

The comment explicitly acknowledges: "multiple withdrawals of the same token in a single transaction are not supported" — but this constraint is not enforced anywhere (no assertion/throw when duplicate assetIds are detected in a batch). The consuming code (`watchWithdrawal` / `sdk.waitForWithdrawalCompletion` / `createWithdrawalCompletionPromises`) treats the returned `WithdrawalStatus` as authoritative truth for that specific withdrawal index/destination: [3](#0-2) 

If withdrawal #0 (asset X → address A) completes with `transfer_tx_hash` H1, and withdrawal #1 in the same intent (asset X → address B) is still pending, `findMatchingWithdrawal` for withdrawal #1 will also match the same completed record (asset X, hash H1) because matching is only on `assetId`, not on destination address or index. The equality that breaks is: "status/hash reported for withdrawal #1" should equal "the on-chain outcome for the transfer to address B", but instead it reports the outcome for the transfer to address A.

### Impact Explanation
This is a status/hash misreport: an integrator awaiting `waitForWithdrawalCompletion` for withdrawal #1 will be told it "completed" with hash H1 (which actually corresponds to a transfer paid to a different destination address). An integrator that credits/marks-as-settled based on this response could incorrectly consider the second withdrawal fulfilled and release funds, credit a user, or reconcile against the wrong transaction hash — a "status or hash misreport making an integrator credit or refund twice" scenario, matching the High-impact category in scope.

### Likelihood Explanation
This triggers under normal (non-malicious) usage whenever a caller batches ≥2 withdrawals of the same NEP-141 asset to different destinations in one intent — a legitimate use case the SDK's batch APIs (`WithdrawalParams[]`, `createWithdrawalCompletionPromises`) otherwise support and document. No malicious relayer, bridge operator, or admin action is required; it is purely a consequence of the SDK's own matching logic combined with the PoA indexer returning an unsorted list keyed only by token.

### Recommendation
Enforce the documented invariant (reject/throw if a batch contains duplicate assetIds routed through PoA bridge) or fix the matcher to disambiguate by destination address and/or amount ordering as suggested in the existing code comment, so a status object is never returned for a withdrawal it does not correspond to.

### Proof of Concept
1. Construct one intent with `withdrawalParams = [{assetId: "nep141:btc.omft.near", destinationAddress: A, amount: 100}, {assetId: "nep141:btc.omft.near", destinationAddress: B, amount: 200}]`.
2. Submit via `sdk.signAndSendWithdrawalIntent`; PoA bridge processes withdrawal to A first and it completes (`status: "COMPLETED", data.transfer_tx_hash: H1`), while withdrawal to B is still `"PENDING"` in the indexer response.
3. Call `sdk.waitForWithdrawalCompletion` (or `createWithdrawalCompletionPromises`) for index 1 (destination B). Internally `describeWithdrawal` calls `findMatchingWithdrawal(response.withdrawals, "nep141:btc.omft.near")`, which returns the first entry (A's completed record) since matching only checks `near_token_id`.
4. The caller receives `{status: "completed", txHash: H1}` for the withdrawal to B, even though B's transfer never happened — a wrong-outcome status/hash report.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
