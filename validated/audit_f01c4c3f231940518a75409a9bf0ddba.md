Audit Report

## Title
CORS wildcard origin allowlist bypass via unanchored suffix match - (File: core/services/gateway/network/httpserver.go)

## Summary
The gateway HTTP server's `isAllowedOrigin` function implements wildcard CORS allowlist matching using an unanchored `strings.HasSuffix` check that does not enforce a dot-separated subdomain boundary. As a result, a wildcard entry like `*.remix.com` also matches attacker-controlled hosts such as `evilremix.com`, which merely share the trailing string but are not actual subdomains.

## Finding Description
The vulnerable logic is: [1](#0-0) 

`allowedHost` is derived by stripping the `*.` prefix, leaving `remix.com`, and the check `strings.HasSuffix(originHost, allowedHost)` only verifies that `originHost` ends in that literal string — it does not require a `.` character immediately preceding the suffix. This means `evilremix.com`, `notremix.com`, or any domain ending in `remix.com` without a dot separator passes the check even though it is not a subdomain.

This function is invoked directly against the unauthenticated `Origin` request header on every incoming request: [2](#0-1) 

When the check succeeds, the attacker-supplied `Origin` is reflected back in `Access-Control-Allow-Origin`, granting the attacker's page CORS read access to the gateway's HTTP responses. There is no additional boundary check, normalization, or validation elsewhere in the code path that would prevent this — the existing tests only cover cases where the suffix literally doesn't match (e.g., `ethereum.remix.org` vs `*.ethereum.org`), not the dot-boundary bypass case (e.g., a domain like `otherethereum.org` against `*.ethereum.org`), confirming this specific gap is untested and unmitigated: [3](#0-2) 

## Impact Explanation
This is a genuine allowlist-bypass logic bug matching the "allowlist bypass" impact class. An operator who configures a wildcard CORS entry (a legitimate, intended configuration feature, not a misuse) is exposed to any attacker who registers a domain sharing the same suffix without a subdomain relationship (e.g., `evilremix.com` for `*.remix.com`). A victim browsing to the attacker's site while their browser also talks to the gateway would allow the attacker's origin to read gateway HTTP responses that should only be visible to the legitimately configured origins — an unauthorized cross-origin response disclosure.

## Likelihood Explanation
Exploitation requires: (1) an operator to configure a wildcard entry in `CORSAllowedOrigins` (an intended, documented usage pattern, not negligence), and (2) an attacker to register any domain that happens to share the suffix string (cheap and trivial), and (3) a victim's browser to interact with both the attacker page and the gateway. No node/API authentication, admin role, or elevated network position is needed to trigger the code path itself — `isAllowedOrigin` is reached purely from the client-controlled `Origin` header.

## Recommendation
Anchor the wildcard suffix match on a dot boundary, e.g., compare against `"."+allowedHost` (the full `.remix.com` suffix) instead of the bare `remix.com`, so that `foo.remix.com` still matches while `evilremix.com` does not:
```go
if strings.HasPrefix(allowedHost, "*.") {
    suffix := allowedHost[1:] // ".remix.com"
    if strings.HasSuffix(originHost, suffix) {
        return true
    }
}
```

## Proof of Concept
1. Configure the gateway with `CORSEnabled: true` and `CORSAllowedOrigins: ["https://*.remix.com"]`.
2. Send a request to the gateway's configured path with header `Origin: https://evilremix.com`.
3. Observe `isAllowedOrigin` returns `true` (since `"evilremix.com"` has suffix `"remix.com"`), and the response includes `Access-Control-Allow-Origin: https://evilremix.com`, confirmed by the code at [1](#0-0)  and the request-handling flow at [2](#0-1) . A Go unit test mirroring the existing `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` structure but using an origin such as `https://evilethereum.org` against `CORSAllowedOrigins: ["https://*.ethereum.org"]` would demonstrate `Access-Control-Allow-Origin` is incorrectly set, proving the bypass.

		if s.isAllowedOrigin(origin) {
			w.Header().Set("Access-Control-Allow-Origin", origin)
