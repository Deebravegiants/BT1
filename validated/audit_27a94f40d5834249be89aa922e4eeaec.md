### Title
Missing shop-domain validation in `ShopifyAPI::Auth::Oauth.begin_auth`/`validate_auth_callback` allows OAuth redirect and `client_secret` delivery to an attacker-controlled host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` both use a caller/attacker-influenced `shop` string to build the host that (a) receives the OAuth authorization redirect and (b) later receives the app's `client_secret` in the access-token exchange, without ever calling the library's own `ShopifyAPI::Utils::ShopValidator.sanitize!`/`sanitize_shop_domain`. Every other OAuth-adjacent flow in this same gem (`TokenExchange`, `ClientCredentials`, `RefreshToken`, `Clients::Graphql::Storefront`) does call `ShopValidator` on the shop value before using it as a host, making the Authorization Code Grant path an inconsistent, unvalidated outlier within the library itself.

### Finding Description
`begin_auth` builds the authorization redirect URL directly from the caller-supplied `shop` parameter: [1](#0-0) 

The host portion of that URL is produced by `auth_base_uri`, which simply interpolates the raw `shop` string into `https://#{shop}/admin` with no membership check against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`: [2](#0-1) 

Symmetrically, `validate_auth_callback` builds a "null" session whose `shop` is taken straight from the callback's `auth_query.shop` and uses it as the host for the token-exchange POST that carries the app's `client_id`/`client_secret`: [3](#0-2) 

Note that the HMAC over the callback query does cover `shop` (see `AuthQuery#to_signable_string`), so a callback query cannot be *tampered with* without the app secret. But that guarantee never validated the *initial* `shop` value used to kick off `begin_auth` — the redirect host used to start the flow is fully attacker-controllable by whoever can reach the app's "login"/"start OAuth" route with a `shop` query/header value, exactly as illustrated in this gem's own documentation, where the value is taken straight from a request header with no sanitization step shown: [4](#0-3) 

The library ships a dedicated `ShopValidator` module precisely for this class of check (rejecting any domain outside `shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`): [5](#0-4) 

and other OAuth grant implementations in the same codebase apply it before using the shop as a request host, e.g. `TokenExchange`/`ClientCredentials`/`RefreshToken`: [6](#0-5) 

But `Oauth.begin_auth`/`Oauth.validate_auth_callback` — the module implementing the standard Authorization Code Grant flow — never invokes `ShopValidator` at all, so the equality that should hold, "host redirected/host that receives client_secret == a domain in `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`", is never checked in this code path.

### Impact Explanation
An unprivileged internet user who can influence the `shop` value passed into `begin_auth` (a normal, expected input to the "start OAuth" route per this gem's documented usage) can cause the app to redirect a merchant's browser to an attacker-controlled host instead of Shopify's real authorization page. This is a forced/spoofed OAuth completion: the victim is shown a phishing page mimicking Shopify's install/authorize screen, hosted by the attacker, while the app has already disclosed its `client_id` and the OAuth `state` value to that attacker-controlled host via the redirect. This matches the High-severity category "SSRF ... or session fixation or forced OAuth completion, scope or expiry check bypass" from the impact list, since the redirect target is never verified against Shopify's trusted domain set the way the library's own `ShopValidator` requires elsewhere.

### Likelihood Explanation
The entry point (a shop identifier used to start OAuth) is by definition attacker-reachable — it's the value an unauthenticated visitor supplies to begin installing/logging into the app, and this gem's own documentation shows it being taken directly from a request header. No access token, `client_secret`, or privileged account is required to trigger `begin_auth` with an arbitrary `shop` string.

### Recommendation
Call `ShopifyAPI::Utils::ShopValidator.sanitize!` (or `sanitize_shop_domain`) on the `shop` parameter inside `Oauth.begin_auth` before constructing `auth_base_uri`, and likewise validate `auth_query.shop` inside `Oauth.validate_auth_callback` before it is used to build the host that receives `client_id`/`client_secret`, mirroring what `TokenExchange`, `ClientCredentials`, and `RefreshToken` already do.

### Proof of Concept
1. Deploy an app using this gem's documented Authorization Code Grant pattern, i.e. its `login` route calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: <value from request>, redirect_path: "/auth/callback")` as shown in `docs/usage/oauth.md`.
2. As an unauthenticated user, request the login route with `shop` set to an attacker-controlled string, e.g. `evil.example.com`.
3. `auth_base_uri("evil.example.com")` returns `https://evil.example.com/admin`, so `begin_auth` returns `auth_route: "https://evil.example.com/admin/oauth/authorize?client_id=...&redirect_uri=https://legit-app.com/auth/callback&state=..."`.
4. The victim's browser is redirected to the attacker's server, which can present a fake "Install app" page and harvest the leaked `state`/`client_id`, or otherwise manipulate the flow — none of this requires the app's `client_secret` or any privileged access, only the ability to reach the app's login endpoint.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end

class ShopifyAuthController < ApplicationController
  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission
    # This will lead the user to the Shopify Authorization page
    head 307
    response.set_header("Location", auth_response[:auth_route])
  end
