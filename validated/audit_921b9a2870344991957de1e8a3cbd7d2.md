### Title
Stale/unbound face-IR and thermal frames attached to winning self-custody RGB candidate without temporal correlation - ([File: src/plans/biometric_capture/mod.rs])

### Summary
`handle_ir_face_camera` and `handle_thermal_camera` unconditionally overwrite `self.last_face_ir`/`self.last_thermal` on every raw sensor broadcast frame, regardless of face validity, distance, or occlusion gating. `handle_face_identifier` then blindly takes whatever is currently buffered (`self.last_face_ir.take()`/`self.last_thermal.take()`) and binds it to the newly-winning `self_custody_candidate_rgb` frame the moment a higher-scoring `FaceIdentifier::IsValidImage` result arrives, with no timestamp/adjacency check against the RGB frame it is being paired with.

### Finding Description
The `Plan` struct maintains `last_face_ir`/`last_thermal` as raw, continuously-updated frame buffers: [1](#0-0) 

These handlers run for the full duration of the biometric-capture session (which can span multiple objectives/wavelengths and up to the configured timeout) and are fed by the IR-face and thermal camera broadcast streams independent of whether a face is currently detected, well-positioned, or unoccluded.

In `handle_face_identifier`, whenever a new best-scoring valid face frame arrives, the plan immediately snapshots whatever is sitting in `last_face_ir`/`last_thermal` at that instant and binds it to the winning candidate: [2](#0-1) 

There is no check that the `last_face_ir`/`last_thermal` frame's timestamp is close to (or the same capture instant as) the RGB frame's timestamp — unlike `FrameInfo`, which does record a `timestamp` field for other slots (`left_ir`, `left_rgb`, `right_ir`, `right_rgb`, `self_custody_candidate_rgb`), no equivalent temporal comparison exists between `face_ir`/`thermal` and the RGB candidate they get attached to in `into_capture`: [3](#0-2) 

Because the IR-face/thermal camera streams keep running and overwriting `last_face_ir`/`last_thermal` throughout the whole capture session (multiple seconds, bounded only by the session timeout), any subject appearing in front of the sensor between two `handle_face_identifier` invocations — e.g., a bystander leaning toward the Orb, or the enrolling subject briefly turning away and someone else's face/heat signature appearing in frame — can have their IR/thermal frame captured into `last_face_ir`/`last_thermal` and subsequently bound to the attacker's own winning RGB self-custody frame the next time `handle_face_identifier` fires with a higher score. This capture then flows unmodified into `Capture.face_ir`/`Capture.thermal` via `into_capture`, and ultimately into `personal_custody_package::make_tier2`'s packaged `face_ir.png`/`thermal.png` output.

### Impact Explanation
This is a wrong-identity/biometric-data-mixing bug: a tier-2 personal custody package for one enrolled identity (bound by iris + winning RGB face) can end up containing another person's face-IR/thermal biometric image data. This is a real disclosure/binding-integrity issue — the packaged artifact no longer faithfully represents a single subject's full biometric set, undermining the guarantee that tier-2 packages are self-consistent per-identity, and can leak a bystander's IR/thermal facial signature under an unrelated identity's custody package.

### Likelihood Explanation
Exploitability depends on getting a different subject's face into the IR-face/thermal camera's field of view at some point during the multi-second capture window, then having a higher-scoring RGB self-custody frame arrive afterward for the true attacker. Because the capture session runs continuously across multiple objectives (both eyes, potentially multiple wavelengths) without gating `last_face_ir`/`last_thermal` on validity, distance, or occlusion, this is plausible without any special privilege — it only requires physical presence near the Orb during someone's (including the attacker's own) signup, which is consistent with "the scene shown to the cameras" as an attacker-controlled input. However, it does require timing (getting the substitute face/heat signature captured before the final winning RGB frame is confirmed), so it is not trivially guaranteed on every attempt but is realistically achievable and repeatable via camera-facing manipulation.

### Recommendation
Record a timestamp when `last_face_ir`/`last_thermal` are updated in `handle_ir_face_camera`/`handle_thermal_camera`, and in `handle_face_identifier` only accept `self.last_face_ir`/`self.last_thermal` if their timestamp is within a small tolerance window of the winning RGB frame's capture time (and ideally re-validate that the IR/thermal frame is not occluded / matches expected face bounding box position). Otherwise, discard and leave `face_ir`/`thermal` unset for that update.

### Proof of Concept
Integration test in `src/plans/biometric_capture/mod.rs` test module:
1. Construct a `Plan` and drive `handle_ir_face_camera`/`handle_thermal_camera` with a first "subject A" IR/thermal frame.
2. Call `handle_face_identifier` with a low-score valid output for subject-A's RGB frame; assert `self.face_ir`/`self.thermal` are now bound to subject A's frames.
3. Advance time, then deliver a "subject B" IR/thermal frame via `handle_ir_face_camera`/`handle_thermal_camera` (simulating a bystander/out-of-band subject), without any corresponding higher-score RGB frame from subject B.
4. Call `handle_face_identifier` again with a higher-score valid output using subject A's RGB frame (the winning self-custody candidate).
5. Assert (expected to fail with current code): `Capture.face_ir`/`Capture.thermal` from `into_capture()` should equal subject A's IR/thermal frame, not subject B's — demonstrating that the current implementation incorrectly binds subject B's stale frame to subject A's winning RGB candidate due to the missing temporal/identity correlation check.
