## Analysis Result

Based on investigation of the gateway's HTTP Action response cache, I found a genuine analog to the CVE-2024-32663 bug class (unbounded server-side memory growth from attacker-influenced cache/table entries with no capacity bound, only time-based cleanup).

### Title
Unbounded HTTP Action response cache growth in Gateway allows workflow-triggered memory exhaustion - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

### Summary
The Gateway's `responseCache` used by the HTTP Capability handler (v2) caches outbound HTTP responses keyed by a hash of the request, with **no maximum entry count and no total memory/size bound**. Eviction only happens lazily via a periodic TTL sweep (`DeleteExpired`), similar in structure to Suricata's HTTP/2 dynamic header table, which also lacked a hard cap and relied only on later cleanup, enabling memory exhaustion (CVE-2024-32663).

### Finding Description
`responseCache` is a plain map with no size limit: [1](#0-0) 

`Set` and `Fetch` unconditionally insert new entries into the map whenever a request is cacheable and not already cached/expired — there is no check on the number of entries or aggregate size before insertion: [2](#0-1) 

The only cleanup mechanism is a periodic, time-based sweep that removes entries older than the TTL: [3](#0-2) 

This cache is populated whenever a workflow (via its capability node) issues an outbound HTTP action with `CacheSettings.Store == true`, driven entirely by workflow-controlled request parameters (URL, headers, body) which determine the cache key via `req.Hash()`: [4](#0-3) 

Default TTL and cleanup period are both 10 minutes: [5](#0-4) 

The design intent (per the module's own documentation) confirms cache entries are scoped only by workflow ID + request hash and rely purely on "time-based expiration with periodic cleanup" for invalidation — no cap on entries is documented or implemented: [6](#0-5) 

Because a workflow author (an unprivileged customer who can only deploy workflow code, not a node operator) fully controls the HTTP action's URL/headers/body and `CacheSettings.Store`, a workflow can generate an unbounded number of distinct cache keys (e.g., by varying query strings or headers per request) and mark them all cacheable, each producing a new map entry retained for up to the entire TTL window (default 10 minutes) regardless of how much aggregate memory is consumed.

### Impact Explanation
An untrusted or malicious workflow can force the Gateway process to buffer an unbounded number of full HTTP response bodies in memory (bounded per-request only by `MaxResponseBytes`, which can be tens of megabytes per the deployment config), for up to the full cache TTL, with no global memory ceiling. Sustained abuse — especially from multiple workflows/nodes — can exhaust Gateway memory, causing degraded service or crash (availability impact), matching the "Impact: Availability: High" profile of the CVE-2024-32663 analog.

### Likelihood Explanation
Reaching this path only requires deploying a workflow capable of issuing HTTP actions with `CacheSettings.Store=true` and varying request parameters — no special privilege beyond normal workflow authoring/deployment is needed. The only mitigating factor is per-node/global rate limiting on inbound node messages (`globalNodeRateLimiter`, `perNodeRateLimiters`), which throttles request *rate* but does not bound the total number of *distinct cached entries* that can accumulate over the multi-minute TTL window, nor total cache memory.

### Recommendation
Add a maximum entry count (or aggregate byte-size budget) to `responseCache`, evicting the oldest/least-recently-used entries (or rejecting new `Set` calls) once the limit is reached, in addition to the existing TTL-based cleanup — analogous to how `RequestCache` already enforces `maxCacheSize`: [7](#0-6) 

### Proof of Concept
1. Deploy a workflow that, on each trigger/execution, issues an `OutboundHTTPRequest` HTTP action with a unique query parameter or header value (ensuring a unique `req.Hash()`) and `CacheSettings.Store = true`.
2. Repeatedly execute/trigger the workflow at the maximum allowed rate under `perNodeRateLimiters`/`globalNodeRateLimiter`.
3. Each unique request produces a new entry in `responseCache.cache` (line 111-120 of `response_cache.go`), which is retained until the next `DeleteExpired` TTL sweep (default every 10 minutes, `defaultCleanUpPeriodMs`), accumulating full response bodies (up to `MaxResponseBytes` each) in Gateway memory with no cap on total entries or size.

```go
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
```

```go
func (rc *responseCache) DeleteExpired(ctx context.Context) int {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	now := time.Now()
	var expiredCount int
	for key, cachedResp := range rc.cache {
		if now.After(cachedResp.storedAt.Add(rc.ttl)) {
			delete(rc.cache, key)
			expiredCount++
		}
	}
	rc.lggr.Debugw("Removed expired cached HTTP responses", "count", expiredCount, "remaining", len(rc.cache))
	rc.metrics.IncrementCacheCleanUpCount(ctx, int64(expiredCount), rc.lggr)
	rc.metrics.RecordCacheSize(ctx, int64(len(rc.cache)), rc.lggr)
	return expiredCount
```

```markdown
### 3.2 Caching Behavior

- **Cacheable Responses**: 2xx (success) and 4xx (client error) status codes.
- **Cache TTL**: Configurable, default 10 minutes
- **Cache Key**: Generated from workflow ID and request hash
- **Cache Invalidation**: Time-based expiration with periodic cleanup
- **Cache Strategy**: All cacheable responses are cached; Non-zero `CacheSettings.MaxAgeMs` determines whether to return a cached value or make a fresh request
- **Workflow Isolation**: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage
```

```go
func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
```
