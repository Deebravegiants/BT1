### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-signing only the raw request body, while the `shop` (and `topic`/`webhook_id`) that the handler acts on are taken from unauthenticated HTTP headers. This breaks the identity binding `shop authenticated == shop trusted`, allowing any attacker who can obtain one genuine `(body, hmac)` pair (e.g., from their own shop's installation of the app) to replay that exact body+HMAC to the app's public webhook endpoint while spoofing the `X-Shopify-Shop-Domain` header to point at a victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC over `verifiable_query.to_signable_string` only: [1](#0-0) 

For webhooks, `to_signable_string` returns just the raw body — it does not incorporate the shop domain, topic, or webhook id: [2](#0-1) 

Yet `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from attacker-reachable HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` validates only the body HMAC and then dispatches the handler using the unauthenticated `request.shop`: [4](#0-3) 

Since `Context.api_secret_key` (the HMAC secret) is the same for every shop that installs the app, `HMAC(secret, body)` is identical regardless of which shop the body actually came from. An unprivileged attacker who installs the app on their own shop can trigger a webhook with attacker-controlled body content (e.g., by setting a product title, order note, or customer field to a chosen JSON-adjacent string), capture the genuine `(raw_body, hmac)` pair Shopify sends them, and then POST that identical body+HMAC to the app's webhook endpoint with `X-Shopify-Shop-Domain` rewritten to the victim's shop. `HmacValidator.validate` will accept it because the signature only ever covered the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: <victim>`.

This is exactly the class of bug described in the report: a signed payload (`RestoreData` / here, the webhook body) is not rooted to the specific identity (`RestorationTX` account / here, the shop) it is meant to apply to, so it can be replayed/relabeled against a different identity.

### Impact Explanation
If the app's webhook handler uses `data.shop` to identify the tenant for state changes (e.g., updating billing status, provisioning resources, revoking access, looking up and using that shop's stored access token to perform admin API actions), an attacker can trigger those actions against an arbitrary victim shop without ever having credentials for that shop — a cross-tenant access/action vulnerability, which is Critical per the given impact categories.

### Likelihood Explanation
Exploitation only requires: (1) attacker can install the app on their own store (typical, unprivileged, self-service for any Shopify app), (2) attacker can cause a webhook body with content of their choosing (many webhook topics reflect user-supplied fields), and (3) attacker can send an arbitrary HTTP POST with a forged `X-Shopify-Shop-Domain` header to the app's public webhook receiving endpoint (which by design is internet-reachable). No secrets or victim credentials are needed.

### Recommendation
Bind the shop identity into the signed payload validation, or otherwise cryptographically root the webhook to the shop it claims to be for. Options:
- Cross-check `request.shop` against a shop known to be registered/authorized for this app (e.g., verify a stored offline session/access token exists for that shop) before trusting the event, rather than trusting the header value outright.
- Include `shop`/`topic`/`webhook_id` in the HMAC-signed material if Shopify's webhook contract is changed to support it, or otherwise require the app layer to independently verify shop membership.
- At minimum, document/enforce that `WebhookMetadata#shop` must not be treated as authenticated proof of tenant origin unless additionally verified against known installed shops.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (self-service, unprivileged).
2. Attacker triggers a webhook (e.g., `products/update`) with body content of their choosing, and captures the genuine `raw_body` and `X-Shopify-Hmac-Sha256` value Shopify sends for it.
3. Attacker sends a forged HTTP POST directly to the app's webhook endpoint:
   ```
   POST /webhooks HTTP/1.1
   X-Shopify-Topic: products/update
   X-Shopify-Hmac-Sha256: <captured-hmac>
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   X-Shopify-Webhook-Id: <any>

   <captured-raw-body>
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(api_secret_key, raw_body)`, per [2](#0-1) .
5. The handler executes with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)`, causing the app to act as though the event genuinely originated from the victim shop.
