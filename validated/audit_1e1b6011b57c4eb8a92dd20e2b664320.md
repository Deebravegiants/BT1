### Title
Webhook HMAC signs only the request body and never binds the `X-Shopify-Shop-Domain` header, allowing cross-tenant webhook data injection - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw HTTP body. The `shop` value that is subsequently trusted and handed to the app's handler as the tenant identifier comes from the `X-Shopify-Shop-Domain` header, which is **not** part of the signed payload. This breaks the identity binding `hmac_signed_bytes == shop_domain_attributed_to_request`, letting an unprivileged actor who can obtain one valid `(body, hmac)` pair (e.g. from their own shop's webhook deliveries) replay it while swapping the shop-domain header to any other shop, causing the app to process attacker-controlled data as if it originated from a victim tenant.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from a header that is completely independent of the signed bytes: [2](#0-1) 

`HmacValidator.validate` (and `validate_signature`) only ever hashes `verifiable_query.to_signable_string`, i.e. the raw body, against the app's `api_secret_key`: [3](#0-2) 

`Registry.process` checks this body-only HMAC and then immediately trusts `request.shop` as the tenant identity forwarded to the handler, with no cross-check that the shop header is consistent with anything cryptographically bound to the signature: [4](#0-3) 

Because a single Shopify app has one `client_secret`/`api_secret_key` shared across *every* merchant installation, the HMAC computed for a webhook delivered to Shop A's install of the app is mathematically identical to what would be computed for the exact same body delivered "from" Shop B. The gem's own `to_signable_string` implementation confirms the shop identity is deliberately excluded from what gets signed — contrast this with `Auth::Oauth::AuthQuery#to_signable_string`, which *does* fold `shop` into the signed string: [5](#0-4) 

So the OAuth callback path binds `shop` into the HMAC, but the webhook path does not — an inconsistent and unsafe design that leaves the shop attribution unauthenticated for every webhook handler built on this gem.

### Impact Explanation
An unprivileged party who owns/controls any shop with the target app installed (trivial to obtain — anyone can install a public app or, for many apps, simply have an account) can capture one legitimate webhook body + HMAC pair sent to their own shop (e.g. via `orders/create`), then POST that identical `(body, hmac-sha256)` pair to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to an arbitrary victim shop domain. `HmacValidator.validate` will report the signature as valid (it never looked at the shop header), and `Registry.process` will invoke the registered handler with `WebhookMetadata#shop` set to the victim's domain and attacker-chosen `body` content. Any app logic that uses the webhook `shop` value to write/update per-tenant state (e.g., updating a customer record, order, inventory count, or triggering a side effect keyed by shop) can be poisoned with forged data attributed to a tenant the attacker does not own — a cross-tenant data-integrity/write vulnerability inherent to how this gem authenticates webhooks.

### Likelihood Explanation
High. Any actor able to install the target app on a store they control (or one that already receives one webhook, which is common) can extract a valid `(body, hmac)` pair from network capture or their own webhook receiver, then trivially forge the `X-Shopify-Shop-Domain` header on a replay — no secret material, privileged account, or race condition is required, and the gem performs no additional binding check.

### Recommendation
Bind the shop identity into the value that is HMAC-verified, or otherwise cryptographically tie the `shop` header to the signed body — e.g., include the `X-Shopify-Shop-Domain` (and ideally `X-Shopify-Webhook-Id`) value in `Webhooks::Request#to_signable_string`, mirroring what `Auth::Oauth::AuthQuery` already does for `shop`. At minimum, document and enforce that host applications must independently verify the `shop` domain belongs to their tenant list *before* trusting it, but the safer fix is to make the gem itself refuse to authenticate a webhook whose declared shop is not covered by the signature.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (or otherwise has a shop where the app is installed and can trigger a webhook, e.g. `orders/create`).
2. Attacker captures the webhook POST sent to the app's endpoint: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` — verifiable via `HmacValidator.validate_signature`, which only hashes `to_signable_string` (`B`) — [1](#0-0) .
3. Attacker replays the identical request to the same endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` while keeping body `B` and header `H` unchanged.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and compares it to `H` — [6](#0-5)  — validation succeeds because `B` and `H` are untouched.
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` — [7](#0-6)  — causing the app to process attacker-supplied webhook data under the victim shop's identity.
