### Title
Balance-based sweep of the shared `dispatcher` in `IntentGatewayV2.placeOrder` lets stray/leftover token balances from other orders be misattributed and escrowed to an attacker's order - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder`'s predispatch branch determines how many "input" tokens to escrow for an order by reading `IERC20(token).balanceOf(dispatcher)` — the *entire* balance the shared `CallDispatcher` instance currently holds for that token — rather than the amount that this specific order's predispatch call actually produced. Because `dispatcher` (`_params.dispatcher`) is one shared, persistent contract address used by every `placeOrder` call that carries predispatch calldata, any token left behind in the dispatcher by a previous, unrelated order (e.g. a token that was produced by that order's predispatch call but is not one of that order's declared `inputs`, and therefore never gets swept out) remains there until some *later* order that happens to list the same token as an input sweeps it — in full — into its own escrow accounting.

### Finding Description
In `placeOrder`, when `order.predispatch.call.length > 0`, the contract: [1](#0-0) 

1. Executes the caller-supplied predispatch call through `ICallDispatcher(dispatcher).dispatch(...)`.
2. For each declared input token, reads `uint256 balance = IERC20(token).balanceOf(dispatcher)` (the dispatcher's *total* balance of that token, not the amount produced by this call), and requires only `balance >= requiredAmount`.
3. Builds a transfer call that sweeps the dispatcher's **entire** balance of the token back into the gateway, then snapshots the gateway's balance as `balancesBefore[i]` right before executing that sweep.
4. After the sweep, computes `received = IERC20(token).balanceOf(address(this)) - balancesBefore[i]` and credits `order.inputs[i].amount = received` (or records the excess as "dust" if it's larger than requested): [2](#0-1) 

This logic never verifies that the swept balance in `dispatcher` actually originates from the current caller's predispatch execution. If a prior, unrelated `placeOrder` call's predispatch calldata produces a token that is *not* part of that order's own `inputs` array (so it is never swept out for that order), the resulting balance is stranded in the shared `dispatcher` contract indefinitely. Any subsequent order — from any user, including an attacker — that declares that same token as one of its `inputs` will sweep the dispatcher's full balance (stranded funds + whatever its own predispatch call produced) and have up to `requiredAmount` of it credited to its own escrow via `_orders[commitment][token] = reducedInputs[i].amount`, at line: [3](#0-2) 

The attacker's order can then be cancelled (refunding the escrowed amount to the attacker) or otherwise redeemed, effectively letting the attacker claim tokens that another user's transaction inadvertently left in the shared dispatcher — the same "balance-conflation across unrelated actions" root cause as the referenced Blueberry finding (`balance = IERC20(token).balanceOf(address(this))` picking up unrelated funds and crediting them to the wrong operation).

The same balance-based, non-delta-scoped sweep pattern exists in the Tron port of this contract: [4](#0-3) 

### Impact Explanation
This is a fund-misattribution / theft vulnerability reachable by any unprivileged user placing intent orders with predispatch calldata — exactly the class of actor this scan is scoped to (intent solver / order placer via `IntentGatewayV2`). An attacker can engineer or simply wait for another order's predispatch execution to leave a token balance stranded in the shared `dispatcher`, then place their own low-cost order listing that token as an input to sweep and escrow it under their own commitment, later reclaiming it via cancellation. This constitutes theft of funds that rightfully belong to the escrow of a different user's order (or to the protocol as unswept dust), satisfying the "concrete theft of funds via unsound accounting" bar.

### Likelihood Explanation
Likelihood depends on predispatch calldata (arbitrary, user-supplied `Call[]` executed via `CallDispatcher`) leaving a residual balance of some token in the shared dispatcher that is not part of the originating order's declared `inputs`. Because `predispatch.call` is attacker-controlled and can be an arbitrary interaction (e.g., unwrapping LP tokens, claiming rewards, swaps) it is plausible — and an attacker could even seed their own leftover deliberately in one transaction and reap it in a second, self-inflicted transaction, making this attacker-triggerable without needing another victim at all: place order A with predispatch producing token X not listed in A's inputs (stranding X in dispatcher), then place order B listing X as an input to sweep and escrow it, then cancel B. This requires no victim and no special timing, only two ordinary `placeOrder` calls.

### Recommendation
Do not use the dispatcher's raw `balanceOf` as the sweep amount. Instead:
- Track dispatcher balances immediately before executing the predispatch call (`balanceOf(dispatcher)` pre-call) and only sweep/credit the delta produced by *this* call (`postCallBalance - preCallBalance`), mirroring the "record actual received" pattern already used elsewhere in the same function for the non-predispatch path.
- Alternatively, require the dispatcher to be a fresh, single-use, per-order contract (e.g. deployed via `CREATE2` per order and self-destructed / drained fully at the end of `placeOrder`) so no state can persist across orders.
- Sweep *all* tokens the predispatch call could plausibly have produced (not just `order.inputs`), or explicitly disallow predispatch calls from producing tokens outside the declared `inputs` set, to eliminate stranded balances.

### Proof of Concept
1. Attacker calls `placeOrder` (order A) with `predispatch.call` that performs an action producing `tokenX` (e.g., unwrap/claim) but declares `order.inputs` containing only `tokenY` (not `tokenX`). The predispatch dispatch call runs; `tokenX` ends up sitting in `dispatcher` and is never swept because it isn't part of A's `inputs` loop.
2. Attacker calls `placeOrder` (order B) with a `predispatch.call` that is a harmless no-op, but declares `order.inputs` containing `tokenX` with `requiredAmount` set to (or below) the amount stranded from order A.
3. Inside B's execution, `balance = IERC20(tokenX).balanceOf(dispatcher)` reads the full stranded balance (from A), passes the `balance >= requiredAmount` check, and the entire balance is swept into the gateway and credited to B's escrow (`_orders[commitmentB][tokenX] = requiredAmount`, excess emitted as dust).
4. Attacker cancels order B (`cancelOrder`), receiving `requiredAmount` of `tokenX` back — tokens that were never actually contributed by the attacker for order B, but rather orphaned from order A's predispatch execution. [5](#0-4)
