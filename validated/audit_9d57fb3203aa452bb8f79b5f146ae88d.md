Confirmed: the docs say `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`), but the actual verification (`ShopifyAPI::Utils::HmacValidator.validate` over `Request#to_signable_string`, which is only `@raw_body`) never covers the `shop-domain`, `topic`, `api-version`, or `webhook-id` headers, which are exactly the fields handed unchecked to the handler as tenant identity in `WebhookMetadata`.

### Title
Webhook tenant identity (`shop`, `topic`, `webhook_id`) is not bound to the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Utils::HmacValidator.validate` computes/verifies the HMAC over that body alone. The `shop`, `topic`, `webhook_id`, and `api_version` values are all read directly from unauthenticated HTTP headers and are never included in the signed payload, yet `ShopifyAPI::Webhooks::Registry.process` treats `Utils::HmacValidator.validate(request)` as proof the whole request "did indeed come from Shopify" (per `docs/usage/webhooks.md`) before dispatching `request.shop` straight into `WebhookMetadata` for the handler to act on.

### Finding Description
The binding that should hold is: `hmac_valid(body, secret) ⇒ shop_header == originating_shop`. In reality the code only proves `hmac_valid(body, secret)`; the `shop-domain` header is disjoint from the signed bytes: [1](#0-0) [2](#0-1) [3](#0-2) 

`Utils::HmacValidator` only ever signs/verifies `to_signable_string`, i.e. the raw body: [4](#0-3) 

`Registry.process` gates everything on that body-only HMAC check, then forwards the unverified `request.shop`, `request.topic`, and `request.webhook_id` headers to the handler as the trusted tenant/event identity: [5](#0-4) 

Because every shop that installs a multi-tenant app shares the same app `client_secret` (`Context.api_secret_key`), any merchant who has legitimately installed the app receives real webhook deliveries with a valid `X-Shopify-Hmac-SHA256` value computed over a body they fully control the shape of (e.g. an empty-object body `{}` for topics like `app/uninstalled`, or any topic/body combination that recurs across shops). That merchant can replay the exact same `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) with a victim shop's values. The HMAC check still passes because it never inspected those headers, and the handler executes business logic attributing the event to the victim shop.

### Impact Explanation
This breaks the tenant isolation the HMAC check is documented to provide ("verify the request did indeed come from Shopify" for *this* shop). A malicious but otherwise unprivileged app-installing merchant can forge webhook events that the app's `WebhookHandler` implementations will process as belonging to another, victim tenant — e.g. triggering `orders/create`/`app/uninstalled`/`customers/redact` style side effects, cache/state updates, or data writes keyed by `data.shop` for a shop they do not control. This is a cross-tenant access primitive built directly on this gem's own webhook verification API.

### Likelihood Explanation
Requires only: (1) the attacker's own legitimate install of the app (any shop can install most public apps), (2) a publicly reachable webhook endpoint (mandatory, since Shopify itself must POST to it), and (3) a topic/body combination that is static or attacker-influenced (many webhook topics have small/predictable bodies). No access to `api_secret_key`, tokens, or the victim's environment is needed.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the signed/verified payload — e.g. verify HMAC over `header_string + raw_body` or otherwise cryptographically bind `request.shop` to the signature — instead of validating the body alone, so that `Registry.process`'s HMAC check actually authenticates the tenant and topic it hands to the handler, not just that *some* valid webhook body was ever produced for the shared app secret.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`. Shopify delivers a real webhook, e.g. `app/uninstalled` with body `{}`, headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-"{}">`.
2. Attacker captures `raw_body = "{}"` and the valid `X-Shopify-Hmac-Sha256` value (both are theirs to read/observe — no secret required).
3. Attacker POSTs to the app's public webhook endpoint with the same body/HMAC but `X-Shopify-Shop-Domain: victim.myshopify.com` (and/or an attacker-chosen topic that shares body `{}`).
4. `ShopifyAPI::Utils::HmacValidator.validate` computes `HMAC("{}", api_secret_key)` and it matches the replayed header, so validation succeeds (`lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(shop: "victim.myshopify.com", ...))` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to execute victim-attributed logic on the attacker's forged event.
