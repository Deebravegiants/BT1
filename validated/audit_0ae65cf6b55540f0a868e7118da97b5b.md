### Title
Missing/optional shop-domain validation lets host app forward the `client_secret` to an attacker-controlled host in OAuth Token Exchange - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::ClientCredentials.client_credentials`, `ShopifyAPI::Auth::RefreshToken.refresh_access_token`, and `ShopifyAPI::Auth::TokenExchange.migrate_to_expiring_token` all validate the caller-supplied `shop` string with `Utils::ShopValidator.sanitize!` before using it to build the HTTP client that sends the app's `client_secret` to `https://#{shop}/admin/oauth/access_token`. `ShopifyAPI::Auth::TokenExchange.exchange_token` accepts the same kind of `shop:` keyword argument, but that argument is now only used to emit a deprecation warning — the shop actually used to build the request host is taken from the JWT `dest` claim, *except* the `shop:` parameter is still part of the public signature and documented for backward compatibility, and there is no `ShopValidator` call binding it to the request destination.

### Finding Description
Every other credential-exchange entry point in this gem treats the caller-supplied `shop` string as untrusted input and funnels it through `Utils::ShopValidator.sanitize!`, which restricts the resulting host to Shopify-owned domains (`TRUSTED_SHOPIFY_DOMAINS`) before it is used to build `Clients::HttpClient` and issue a POST containing `client_secret`: [1](#0-0) [2](#0-1) [3](#0-2) 

`exchange_token` is structurally the same "singular vs. batch" sibling: it exposes the identical `shop:` keyword parameter, but the implementation silently ignores it for host construction and instead derives `dest_shop` from the JWT, with only a deprecation log tying the two together: [4](#0-3) 

The equality that should hold across all four sibling functions is:
`host_used_to_send(client_secret) == ShopValidator.sanitize!(caller_supplied_shop)`

For `exchange_token`, this equality is not guaranteed by a `ShopValidator` check inside the function itself; it is guaranteed only because `dest_shop` happens to come from a JWT signed with `Context.api_secret_key` via `JwtPayload`, which is validated only for `aud` matching `Context.api_key` and expiry, with no verification that `dest` is a myshopify-style trusted domain the way `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` enforces elsewhere: [5](#0-4) 

Because Shopify itself controls what `dest` value it puts in a session token it issues, this specific path is not currently exploitable by an unprivileged attacker without already controlling a valid signed session token. However, it represents a real inconsistency in the codebase's defense-in-depth: three of four sibling OAuth/token functions enforce `ShopValidator.sanitize!` on the host before sending `client_secret`, and `exchange_token` is the one outlier that does not perform this check on the value used to build the destination host, relying entirely on an implicit, undocumented trust assumption about `dest` always being a legitimate Shopify domain.

### Impact Explanation
If this trust assumption about JWT `dest` is ever violated — e.g., a future change accepts an id_token from a source other than the strict JWT-signature-and-domain-bound Shopify session token flow, or a host application passes through a token from an untrusted source into `exchange_token` — `client_secret` would be sent to a host determined by an unvalidated `dest` value, unlike every other credential-exchange function in the gem which enforces `ShopValidator.sanitize!` before doing so. This would be a High-severity SSRF-with-credentials / client_secret leak, matching the impact categories in scope.

### Likelihood Explanation
Low under the current, intended usage, because `dest` is bound inside a JWT that must be signed by `Context.api_secret_key` (or `old_api_secret_key`), which only Shopify and the app know. There is no direct exploitation path from an unprivileged internet user today; the concern is the missing defense-in-depth check (the same code smell flagged in the original report: a check present on parallel functions but omitted on one), not a proven live bypass.

### Recommendation
Add an explicit `Utils::ShopValidator.sanitize!` (or equivalent domain allow-list check) on the value derived from `jwt_payload.shop` inside `exchange_token`, consistent with `client_credentials`, `refresh_access_token`, and `migrate_to_expiring_token`, so that host construction for any credential-bearing request is uniformly validated regardless of where the `shop` value originates, rather than relying implicitly on JWT signature validity alone.

### Proof of Concept
Not exploitable with the current, intended call path since `dest` is bound by a signature only Shopify can produce; this is reported as a missing-defense-in-depth analog to the report's "check present in one function, absent in its sibling" pattern rather than a demonstrated live bypass. No standalone unprivileged-attacker PoC exists against `exchange_token` today.
