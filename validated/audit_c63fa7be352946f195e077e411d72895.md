## Title
`findMatchingWithdrawal` matches by `assetId` only, causing cross-withdrawal status/txHash misreport for same-token batches - (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the status of a specific withdrawal purely by looking up the POA bridge's status list for an entry whose `near_token_id` matches the withdrawal's `assetId`, without ever comparing the reported recipient address or amount against the signed intent's `destinationAddress`/`amount`. When a batch contains two withdrawals of the same token to two different addresses, both indices resolve to the same (first-matching) API entry, so the wrong `txHash`/completion status can be reported for a withdrawal that never actually happened for that destination.

### Finding Description
The equality that should hold is: for withdrawal `i` in the batch, `reported.recipient == signed[i].destinationAddress` and `reported.amount == signed[i].amount` (the API entry attributed to index `i` must be the one that actually paid out `withdrawalParams[i]`).

The code path:
1. `IntentsSDK.createWithdrawalIntents` lets an unprivileged integrator/attacker pick `assetId`, `destinationAddress`, `amount`, `routeConfig` for each withdrawal in a batch [1](#0-0) .
2. `PoaBridge.createWithdrawalIdentifier` derives a `WithdrawalIdentifier` purely from `landingChain` (blockchain) and a per-bridge counter `index`, not the actual destination or amount [2](#0-1) ; `createWithdrawalIdentifiers` in the watcher increments `index` per bridge route only [3](#0-2) .
3. `describeWithdrawal` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which is explicitly documented as matching by `assetId` only and explicitly states multiple withdrawals of the same token in one tx are "not supported" [4](#0-3) .
4. `watchWithdrawal` polls `bridge.describeWithdrawal` per index independently and returns whatever `txHash`/status is reported, with no cross-check against the destination address or amount that was actually signed [5](#0-4) .

Exploit flow: an unprivileged caller of `createWithdrawalIntents`/`processWithdrawal` submits a batch of two `ft_withdraw` intents for the same `assetId` (e.g. `nep141:usdc.omft.near`) but two different `destinationAddress` values (address X, amount 100; address Y, amount 200). Both intents are validly signed and settle. On the POA bridge side, both withdrawals appear in `getWithdrawalStatus` response keyed by the same `near_token_id`. `Array.prototype.find` returns the *first* entry matching `nep141:<near_token_id>` regardless of which entry actually corresponds to address X vs Y. If withdrawal to X completes first, `describeWithdrawal` for index 1 (destined for Y) will return X's `COMPLETED` status/`txHash`, while Y's own withdrawal might still be pending or has a different hash. `waitForWithdrawalCompletion`/`processWithdrawal` surfaces this misreported `txHash` to the integrator for index 1 as if it were Y's transfer, with no later validation reconciling `txHash` back to `destinationAddress`/`amount`.

No later step (`validateAddress`, `compareAddresses`, `validateWithdrawal`, `assert` sanity checks, or the intents contract's own signature/nonce verification) detects this, because these all execute *before* signing/settlement and check the request being sent, not the reported completion status coming back from the bridge API.

### Impact Explanation
This is a status/txHash misreport: an integrator relying on `processWithdrawal`/`waitForWithdrawalCompletion` to decide when to credit a user or mark a withdrawal complete can be told the wrong `txHash` for a given `destinationAddress`, potentially causing double-crediting (crediting user Y based on a transaction that actually paid X) or premature release of downstream funds. This matches the "High: a status or hash misreport making an integrator credit or refund twice" category. It is repeatable any time an integrator batches ≥2 withdrawals of the identical token to different destinations via PoaBridge, which is an ordinary, permitted usage pattern of the public API, not a misuse of a documented escape hatch.

### Likelihood Explanation
Preconditions: a batch withdrawal (`processWithdrawal` with `WithdrawalParams[]`, or independent `createWithdrawalCompletionPromises` calls) containing ≥2 entries with the same POA-bridge `assetId` but different `destinationAddress`/`amount`. This is explicitly acknowledged as an unhandled case in the code's own comment, indicating the maintainers know matching is assetId-only and multi-withdrawal-same-token batches are not correctly supported. Attacker cost is low (a normal integrator flow, no privileged access needed); the divergence is a byproduct of ordinary batching, not adversarial input crafting beyond choosing two same-token destinations, and is repeatable per batch.

### Recommendation
`findMatchingWithdrawal` (and the POA status API contract) should disambiguate withdrawals within the same transaction hash by more than token id — e.g., match by `(near_token_id, recipient_address, amount)` tuple, or the POA API should return the amount/recipient per entry so the SDK can validate `reported.recipient === signed.destinationAddress && reported.amount === signed.amount` before treating a status/txHash as authoritative for a given index. Until upstream API support exists, `describeWithdrawal` should refuse to report "completed" for ambiguous matches (multiple withdrawals to the same asset in one tx) rather than silently returning a possibly-wrong entry.

### Proof of Concept
Vitest plan (mock only HTTP for `poaBridge.httpClient.getWithdrawalStatus`):
1. Build two `WithdrawalParams` for the same `assetId` (`nep141:usdc.omft.near`), destination X (amount 100) and destination Y (amount 200), both routed via `PoaBridge`.
2. Call `createWithdrawalIdentifiers` to get `wid` for index 0 (X) and index 1 (Y), using the same `intentTx`.
3. Mock `getWithdrawalStatus` to return a `withdrawals` array containing a single entry with `near_token_id: "usdc.omft.near"`, `status: "COMPLETED"`, `transfer_tx_hash: "0xXXXX"` (which corresponds to X's actual on-chain transfer).
4. Call `bridge.describeWithdrawal` for both `wid[0]` and `wid[1]`.
5. Assert the broken equality: both calls return `{status:"completed", txHash:"0xXXXX"}`, i.e. `describeWithdrawal(wid[1]).txHash === describeWithdrawal(wid[0]).txHash` even though `wid[1].withdrawalParams.destinationAddress !== wid[0].withdrawalParams.destinationAddress` — demonstrating `reported != signed` for index 1 with no detection anywhere in `watchWithdrawal` or `processWithdrawal`.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
