### Title
XRPL destination-address self-transfer block bypassed via X-address encoding - (File: packages/intents-sdk/src/lib/compareAddresses.ts)

### Summary
`compareAddresses` compares XRPL addresses with plain string equality (`a === b`), while `validateAddress`/`validateXrpAddress` accepts both classic (`r...`) addresses and X-addresses (`isValidXAddress`) as valid XRPL destination formats. An X-address encodes the same underlying classic account (plus an optional destination tag) in a different string, so a token's classic-address `origin_chain_address` and an X-address encoding of that same account will never be string-equal, letting `compareAddresses` return `false` even though both refer to the same account.

### Finding Description
The invariant that should hold is: for any destination `d` accepted by `validateAddress(d, Chains.XRPL)` and token address `t`, if `d` and `t` denote the same XRPL account, then `compareAddresses(t, d, Chains.XRPL)` must be `true`.

In `packages/intents-sdk/src/lib/compareAddresses.ts`, the `Chains.XRPL` case falls into the generic raw-string branch: [1](#0-0) 
No XRPL-specific canonicalisation (e.g., decoding X-address to classic address + tag) is performed, unlike TON/Tron which have dedicated normalisers.

Meanwhile `packages/intents-sdk/src/lib/validateAddress.ts` explicitly accepts either encoding as valid for XRPL: [2](#0-1) 

In `PoaBridge.validateWithdrawal` (packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts), the flow is: validate address format, then block self-transfer via `compareAddresses(tokenInfo.origin_chain_address, args.destinationAddress, assetInfo.blockchain)`: [3](#0-2) 

If `tokenInfo.origin_chain_address` for an XRPL-bridged token is a classic address (`r...`), an attacker supplying the X-address encoding of that exact same classic account as `destinationAddress` would: (1) pass `validateAddress` (since `isValidXAddress` accepts it), and (2) fail the `compareAddresses` raw string-equality check (since the X-address string differs from the classic address string), so `DestinationAddressMatchesTokenAddressError` is never thrown. The withdrawal would then proceed to the XRPL account existence/deposit-auth checks (which only validate the destination account's flags, not whether it equals the token address) and could successfully submit a withdrawal transaction sending tokens to the token's own account.

I was not able to fully confirm from the available index whether `tokenInfo.origin_chain_address` values returned by the POA bridge API for XRPL tokens are always in classic-address format (vs. potentially already X-address), which is a precondition for this bypass to be exploitable in practice. This should be verified with a live/staging POA bridge token list, since the vulnerability requires the *token's own* origin address to be encodable as a valid X-address distinct in string form from the value returned by the API.

### Impact Explanation
If exploitable, an unprivileged user calling `IntentsSDK.processWithdrawal` for an XRPL asset bridged via PoaBridge could construct a `destinationAddress` that is a valid X-address encoding of the token's own origin chain address. This defeats the self-transfer guard and can send bridged tokens irrecoverably to the token's issuing/holding account, matching the "funds delivered to a wrong address/chain/contract with no recovery" Critical impact category. This is repeatable for any withdrawal request on the affected route as long as the token's origin address permits X-address encoding.

### Likelihood Explanation
Preconditions: the target must be an XRPL-route PoA-bridged token whose `origin_chain_address` is a classical XRPL account address; the attacker needs no privileges beyond normal SDK usage (choosing their own `destinationAddress` string). Constructing a valid X-address from a known classic address is straightforward using standard XRPL address libraries (`ripple-address-codec`), so attacker cost is negligible if the precondition holds. I could not verify from indexed code/tests whether any indexed test covers X-address self-transfer detection, so likelihood is uncertain pending confirmation of the origin_chain_address format for XRPL tokens.

### Recommendation
Add XRPL-specific canonicalisation to `compareAddresses` (and ideally to `validateAddress`'s consumers) that decodes both classic and X-address forms to a canonical `(classicAddress, tag)` pair (using `ripple-address-codec`'s `xAddressToClassicAddress`/`classicAddressToXAddress`) before comparing, analogous to the TON/Tron normalisers already present, so that `compareAddresses(t, d, Chains.XRPL)` returns `true` whenever `t` and `d` decode to the same classic account.

### Proof of Concept
```ts
// packages/intents-sdk/src/lib/compareAddresses.spec.ts (proposed addition)
import { classicAddressToXAddress } from "ripple-address-codec";
import { compareAddresses } from "./compareAddresses";
import { Chains } from "./caip2";

it("BUG: XRPL classic and X-address forms of the same account are not recognised as equal", () => {
  const classic = "rEXAMPLEclassicXRPLAddress0000000000"; // token's origin_chain_address
  const xAddress = classicAddressToXAddress(classic, false, false); // no tag, mainnet

  // both are accepted as valid destinations
  expect(validateAddress(xAddress, Chains.XRPL)).toBe(true);
  expect(validateAddress(classic, Chains.XRPL)).toBe(true);

  // but compareAddresses fails to recognise they denote the same account
  expect(compareAddresses(classic, xAddress, Chains.XRPL)).toBe(true); // currently false -> bug
});
```
