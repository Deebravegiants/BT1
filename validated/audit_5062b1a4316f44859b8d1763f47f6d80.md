### Title
Supplier can dodge a bad-debt write-down by frontrunning `clean_bad_debt` with `withdraw`, concentrating the loss on remaining suppliers - (File: contracts/pool/src/ops/withdraw.rs)

### Summary
A liquidation that leaves residual unpaid debt does not write down the supply index at seizure time for the surviving market — the write-down happens only when someone later calls the permissionless `clean_bad_debt` (or owner-only `force_socialize_bad_debt`). During that window the market's books still count the unpayable debt at face value as backing (`backing = cash + outstanding_debt`), and `withdraw` enforces only `require_reserves`, `require_utilization_below_max` (skippable when `max_utilization >= RAY`), and `require_supply_for_debt`. An unprivileged supplier who watches for the liquidation or the pending `clean_bad_debt` call can withdraw at the pre-write-down supply index, exiting at full claim value while the cash lasts. Whoever is left when `clean_bad_debt` executes absorbs more than their pro-rata share of the loss via `apply_bad_debt_to_supply_index`.

### Finding Description
`apply` in `contracts/pool/src/ops/withdraw.rs` burns supply shares and pays `gross = shares * supply_index` with no awareness that part of `borrowed` is already uncollectible. The guards in `gate_and_debit` are:

- `cache.require_reserves(net_transfer)` — only checks `cash >= draw` (`contracts/pool/src/guards.rs:36-47` context, cash book).
- `require_utilization_below_max` — a post-state utilization check that early-returns when `max_utilization >= RAY` and otherwise compares `borrowed / supplied`, both still at pre-write-down values (guards.rs:19-34).
- `require_supply_for_debt` — only fires when `supplied == 0` (guards.rs:69-73).

Critically, `require_backed_market`/`backing_shortfall` — the guard that would detect `supplied_claim > cash + debt` — is applied to `supply` only, not `withdraw` (pool README guard table; guards.rs:52-66). And even that check counts the doomed debt as backing until `seize_positions` burns it.

Socialization is a separate, later, permissionless step: `clean_bad_debt_standalone` → `socialize_bad_debt` (`contracts/controller/src/positions/liquidation/mod.rs:241-249`), which calls `seize_positions` → `ops/seize.rs::apply` → `interest::apply_bad_debt_to_supply_index`, lowering the market's `supply_index` pro-rata (`contracts/pool/src/interest.rs:73-89`, `contracts/pool/src/ops/seize.rs:23-34`). INV-LIQ-04 confirms cleanup is "explicit" and separate from liquidation, and the bad-debt eligibility (`debt > collateral`, collateral ≤ $5) is publicly computable, so the timing of the index cut is fully predictable.

### Impact Explanation
The pool loss from bad debt is fixed; the only question is which suppliers bear it. A supplier who withdraws between the insolvency-creating event and `clean_bad_debt` redeems shares at the unwritten-down index and takes real cash out, so the same loss is divided over a smaller remaining `supplied` base — remaining suppliers lose strictly more than their pro-rata share, up to total loss while the frontrunner loses nothing. This is theft of user funds via a first-come-first-served exit, identical in shape to the source report's "wait, monitor, frontrun the last transaction to get the best price": the supplier waits risk-free and exits at the best (pre-write-down) exchange rate the instant cleanup is imminent.

### Likelihood Explanation
The trigger conditions are common and public: any liquidation that fails to fully cover debt (insolvent branch, under-delivery, or dust-capped collateral) creates the window, and `clean_bad_debt` is permissionless so its timing is driven by any observer. The attacker needs only a supply position in the affected `(hub, asset)` market and calls the ordinary `controller::withdraw`. The escape is bounded by (a) available `cash` and (b) the `max_utilization` cap when configured below `RAY` — on uncapped or under-utilized markets nothing blocks it. Soroban transaction ordering makes frontrunning a pending cleanup straightforward for a watcher submitting in the same or earlier ledger.

### Recommendation
Make the write-down atomic with the event that creates the bad debt, or make exits pay for it:

- Run bad-debt socialization inside `liquidate` itself when the post-liquidation state already satisfies the insolvency gate (the code already re-checks socializability after `liquidate`; extend it to always attempt cleanup rather than leaving a separate callable window), or
- Have `withdraw`/`net_settle`/`claim_revenue` evaluate `backing_shortfall` (or a "pending bad debt" flag set at liquidation time) and revert with `PoolInsolvent` until `clean_bad_debt` or `recapitalize` runs, mirroring how `supply` is already gated by `require_backed_market`, or
- Record a per-market `pending_bad_debt` at seizure time and charge withdrawing suppliers their pro-rata share of it before paying out.

### Proof of Concept
1. Market `(hub, USDC)`: `max_utilization = RAY` (cap disabled), suppliers S1 (attacker) and S2 each supply 500 USDC; cash = 1_000.
2. Borrower B posts ETH collateral, borrows 600 USDC; cash = 400.
3. ETH price crashes; `liquidate` seizes all collateral but repays only 550 of the 600 debt. Residual 50 USDC debt remains on B's account; `borrowed` still counts it, `cash` = 400 + repayments.
4. Before anyone calls `clean_bad_debt` (eligibility: `debt 50 > collateral ~0 ≤ $5`, publicly checkable via `is_socializable_bad_debt`), S1 calls `withdraw(account_id, [(USDC, 0 /* all */)])`. `supply_index` is still ~1.0; S1 receives the full 500 (bounded by cash), leaving cash for S2 short by exactly the 50 bad debt.
5. Keeper calls `clean_bad_debt(B)`; `apply_bad_debt_to_supply_index` writes the 50 loss down on the remaining `supplied` — now only S2's shares — so S2's claim drops by ~50 USDC plus, instead of 25 each. S1 escaped the write-down entirely; absent the race, each supplier would have borne 25.
