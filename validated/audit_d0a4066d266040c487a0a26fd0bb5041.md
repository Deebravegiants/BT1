## Title
`EvmHost.dispatch()` swaps native ETH for fee tokens at the live, un-guarded Uniswap V2 spot price, letting a front-runner sandwich any dispatcher and strand refunded ETH in the Host - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` accept `msg.value` and, when native token is supplied, immediately swap it for the exact `post.fee`/`get.fee` amount of fee token via `IUniswapV2Router02.swapETHForExactTokens` inside the same transaction, using the pool's current spot price with no TWAP, no slippage bound configurable by the caller, and no minimum/maximum price check [1](#0-0) . This is functionally the same primitive flagged in the BondVault report: a protocol contract commits value against a manipulable, single-block AMM spot price with no TWAP guard.

### Finding Description
Both dispatch entry points execute the swap unconditionally against the live pool state: [1](#0-0) [2](#0-1) 

`swapETHForExactTokens` is called with `path`, output amount fixed at `post.fee`/`get.fee`, and `msg.value` as the input cap; any unused ETH from the swap is refunded by the router to its caller — which is `address(this)` (the `EvmHost` contract), not the end user who supplied `msg.value` — because `to` is set to `address(this)` and the router's ETH-refund logic returns unspent ETH to `msg.sender` of the router call. The docs themselves acknowledge this exact pricing model is sandwich-exploitable when read off-chain: `HyperApp.quote()` explicitly warns "Do not call `quote()` in smart contract transactions. It uses Uniswap's `getAmountsIn`, making it vulnerable to sandwich attacks" [3](#0-2) , yet `dispatch()` itself performs the analogous state-writing swap on-chain, in the same transaction as the user's call, with the identical AMM as its sole price source.

A user (or their wallet/dApp) computes an ETH amount to send with `dispatch()` off-chain via `quote()`/`getAmountsIn` against the pool's current price, then submits the transaction. An attacker can:
1. Front-run the dispatch transaction, moving the WETH↔feeToken pool price in the direction that makes the fee-token leg of `swapETHForExactTokens` cost *more* WETH than the victim provided.
2. The victim's `dispatch()` call then either reverts (denial of dispatch / wasted gas, `Uniswap: INSUFFICIENT_INPUT_AMOUNT`-style revert) or, if the victim over-provisioned `msg.value` as a buffer, the swap silently consumes more of that buffer than expected while refunding whatever ETH remains — into `EvmHost`, not the caller — since `EvmHost` has no path to return leftover native ETH to the payer.
3. Back-run to restore the pool, pocketing the AMM sandwich profit; the ETH stranded inside `EvmHost` from the refund has no user-facing withdrawal path in the dispatch flow, unlike the `feeToken` refund path used elsewhere in the contract (`onGetTimeout`/`dispatchTimeOut` explicitly refund `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` on failure, but the native-ETH `dispatch` swap has no equivalent per-user refund) [4](#0-3) .

This mirrors the BondVault root cause precisely: a protocol-owned contract commits value (here, native ETH pulled from the caller and swapped) against a spot price with no TWAP/price-band protection, executed atomically inside the victim's own transaction so it can be sandwiched by anyone watching the mempool — exactly the "no TWAP guard, single-block spot price" pattern the report calls out, adapted from an LP-matching mechanism to a fee-payment swap mechanism.

### Impact Explanation
An attacker with no privileged role can sandwich any `dispatch()` call paid in native token, causing:
- Griefing/DoS of the dispatch (revert due to insufficient input, wasting the user's gas and delaying the cross-chain message), and/or
- Native ETH sent by the user beyond what the manipulated swap consumes becomes stranded inside `EvmHost` with no visible per-dispatch refund mechanism to the payer, which is a permanent, if partial, freezing of user funds.
- The attacker profits from the classic AMM sandwich margin extracted from the WETH/feeToken pool, funded by the excess ETH the victim supplied.

This affects the primary way third parties reach `EvmHost` — dispatching POST/GET requests, the base primitive underlying the intents, token-gateway, and general messaging apps — so the exposure is broad, but the loss is bounded by pool depth and `msg.value` sizing per call, not an unbounded systemic drain. This lands at Medium, consistent with the judge's rating of the original report.

### Likelihood Explanation
Likelihood is moderate-to-high: any application or user paying dispatch fees in native token computes `msg.value` off-chain from the current spot price (the docs explicitly steer integrators to do this), giving an attacker a predictable, mempool-visible target to sandwich with ordinary flash/atomic trades on the configured Uniswap V2 pool. No special permissions or governance are required — only capital to move the pool within one block, the same cost structure as the original BondVault exploit.

### Recommendation
- Require callers to pass an explicit maximum-input (slippage) bound and use `swapETHForExactTokens` behavior consistent with that bound, or switch to `swapExactETHForTokens` with a caller-specified `amountOutMin` and refund any resulting fee-token/ETH surplus directly to `_msgSender()`/`post.payer` rather than retaining it in `EvmHost`.
- Guard the swap against a TWAP or bounded deviation from a recent price, similar to the `checkPriceGuard`/`maxDeviationBps` pattern already used elsewhere in this codebase for Uniswap V4 venue pricing.
- Add an explicit refund path so any native ETH left over after the swap returns to the original payer instead of being implicitly retained by the Host contract.

### Proof of Concept
1. Attacker observes a pending `dispatch(DispatchPost)` / `dispatch(DispatchGet)` transaction with `msg.value` sized to the current WETH→feeToken spot price for `post.fee`/`get.fee` tokens.
2. Attacker front-runs with a trade on the configured `uniswapV2` pool that raises the WETH cost of the fee token.
3. Victim's `dispatch()` executes `swapETHForExactTokens{value: msg.value}(post.fee, [WETH, feeToken], address(this), block.timestamp)` [5](#0-4)  at the now-worse price; it either reverts (DoS) or, if `msg.value` had headroom, consumes more ETH than intended, with the router-refunded remainder landing in `EvmHost` rather than back to the payer.
4. Attacker back-runs to restore the pool and realizes the AMM sandwich profit.

Note: I was not able to inspect the router wrapper contracts (`UniV3UniswapV2Wrapper`, `UniV4UniswapV2Wrapper`, `GnosisUniswapV2Wrapper`) in full detail to confirm whether any of them add slippage protection on top of this call path for specific deployments; a background agent should verify whether any configured `uniswapV2` router in production wraps additional protection before finalizing severity.

        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();

            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }
