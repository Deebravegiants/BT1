### Title
Webhook `shop`/`topic`/`webhook_id` Identity Fields Not Covered by HMAC, Allowing Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the `hmac-sha256` header exclusively against that body. The `shop-domain`, `topic`, and `webhook-id` headers — which are read from the unauthenticated HTTP request and then trusted to build `WebhookMetadata` for the host app's handler — are never included in the signed material.

### Finding Description
`Registry.process` performs the only authenticity check on an incoming webhook: [1](#0-0) 
It calls `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string`: [2](#0-1) 
`to_signable_string` for a webhook `Request` is defined as just `@raw_body`, while `shop`, `topic`, and `webhook_id` are parsed straight from HTTP headers with no cryptographic binding to that signature: [3](#0-2) 
The binding the gem needs to hold is: `shop header == shop bound by HMAC`. Instead, the HMAC binds only `body == HMAC(body, secret)`, and `shop`/`topic`/`webhook_id` are accepted from the request headers unauthenticated, then handed to the app's handler as trusted identity fields: [4](#0-3) 
This is the same bug class as the reported `onlyInitOr` issue: a check (the HMAC/role check) is performed, but the value that downstream logic actually relies on for its identity/authorization decision (`shop`/`_role`) is not the value that was actually verified.

### Impact Explanation
Because the signature only ever depends on the byte content of the body, any request whose body byte-for-byte matches a body an attacker has previously obtained a valid signature for (e.g., by installing the app on their own store and capturing a `webhook-id`/`shop-domain`-agnostic webhook such as an empty-body or fixed-content topic) will pass `HmacValidator.validate` even if the `shop-domain`, `topic`, or `webhook-id` headers are swapped to point at a different shop, topic, or webhook. Host applications built on this gem are documented to use `WebhookMetadata#shop`/`#topic` as the trusted tenant/action identifiers for their handler dispatch and data writes, so this allows cross-tenant confusion: a request "verified" as authentic for the attacker's own body can be relabeled to be processed as belonging to a victim shop or to a different, more sensitive topic than the one actually signed.

### Likelihood Explanation
This does not require the app's `client_secret`, an access token, or any other privileged credential. An attacker only needs one unprivileged capability: to trigger a real webhook to their own low-privilege/self-owned install (installing an unprivileged free/dev store is a normal, non-privileged action) so they can observe a valid `(body, hmac)` pair for a body they can also produce elsewhere or that is content-independent of shop identity, and then re-send it to the app's public webhook endpoint with altered `shop-domain`/`topic`/`webhook-id` headers.

### Recommendation
Bind the identity headers into the signed material verified by `HmacValidator`, or otherwise independently verify that `shop-domain` (and `topic`/`webhook-id`) correspond to the tenant the caller is authorized to act as before dispatching to `WebhookHandler#handle`. At minimum, document that host applications must independently re-validate `shop` against a known/installed-shop list before trusting webhook payload attribution, since the gem's own HMAC check does not cover those headers.

### Proof of Concept
1. App developer installs their own app on a self-controlled/free shop `attacker-shop.myshopify.com` and captures a legitimate webhook delivery with an empty or fixed JSON body, e.g. raw body `"{}"`, headers `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-topic: app/uninstalled`, `shopify-hmac-sha256: <valid signature of "{}">`.
2. Attacker resends the exact same raw body `"{}"` and `hmac-sha256` value to the app's public webhook endpoint, but changes `shopify-shop-domain` to `victim-shop.myshopify.com` and/or `shopify-topic` to a different registered topic.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `OpenSSL.secure_compare(computed_signature, hmac)` over `@raw_body`, which is unchanged.
4. `Registry.process` dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-controlled `victim-shop.myshopify.com`/spoofed topic values as if they were verified, per `lib/shopify_api/webhooks/registry.rb:198-199`.
