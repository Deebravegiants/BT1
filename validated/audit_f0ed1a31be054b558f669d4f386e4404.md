### Title
Orb-Relay client resends last outbound state message to any sender presenting a `RequestState` payload, bypassing source-identity verification - (File: `orb-relay-client/src/client.rs`)

### Summary
The Convex `getReward` bug lets any unauthorized caller invoke a "for-anyone" function on behalf of a Vault, corrupting the Vault's own accounting logic that assumes only its own `claimRewards` call would trigger the reward transfer. The structural analog in orb-core is in `PollerAgent::main_loop`, where an incoming `self_serve::app::v1::RequestState` payload causes the client to immediately resend its cached `last_message` **before** the code validates that the message actually originated from the expected peer (`src.id == self.config.dst_id`).

### Finding Description
`PollerAgent::main_loop` processes each `RelayConnectResponse` payload received over the multiplexed orb-relay stream: [1](#0-0) 

The `RequestState` branch is checked and acted on *unconditionally*, without any check on `src.id`:
```
if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: ...");
} else {
    self.handle_message(...).await?;
}
```
Every other payload type is validated against `self.config.dst_id` (the specific `session_id`/`orb_id` this client believes it is paired with) before being accepted — and the developers' own `TODO` on `main_loop` acknowledges the stream can receive messages "from different sources" that need to be filtered: [2](#0-1) 

`last_message` is the most recent state-carrying message the orb sent to its paired app/session — for a signup flow this includes `AnnounceOrbId`, `CaptureStarted`, `CaptureEnded`, `SignupEnded`, etc., which encode live signup-session state: [3](#0-2) [4](#0-3) 

Because the `RequestState` branch never checks `src.id`, any entity able to place a `RequestState`-typed message onto this client's incoming stream — including, per the code's own acknowledged multiplexing risk, an entity other than the intended session/app peer — will get the client's last signup-state message replayed back to it, regardless of whether that entity is the legitimately bound counterpart for that signup session.

### Impact Explanation
This is a direct analog of the report's root cause: a function/handler intended to be invoked only by the legitimate counterpart of a session is instead reachable by anyone who can reach the same channel, and the reachable side effect (replaying `last_message`) leaks live signup-session state (e.g. capture/signup progress and orb identity) to an unauthenticated-relative-to-that-session party. This constitutes cross-signup state bleed / disclosure of in-progress signup session data to a party not bound to that identity/session, which the `SECURITY.md`/rules class as an acceptable analog impact category (misattributed signup / cross-signup state bleed) rather than a pure availability nuisance.

### Likelihood Explanation
The likelihood depends on whether the relay backend enforces strict 1:1 stream binding between a connected client and its declared `dst_id`, or whether — as the code's own `TODO` comment states — the stream can carry messages from multiple sources to the same connected client. Given the code was explicitly written to defensively filter unexpected sources for every other message type, and the `RequestState` branch was carved out as an exception, this strongly suggests the multiplexing scenario is a real, anticipated condition in production rather than a theoretical one. I could not verify the relay server-side implementation (not present in this repo) to confirm definitively whether unrelated sessions' messages can reach this stream; this is a genuine gap in what I could confirm from the orb-core client code alone.

### Recommendation
Move the `src.id != self.config.dst_id` check ahead of the `RequestState` handling so that `RequestState` requests are honored only when they originate from the expected paired peer, consistent with every other message type handled in this loop.

### Proof of Concept
1. An orb connects to the relay as `Mode::Orb` with `dst_id` set to the specific session/app id from the current signup (`self.config.dst_id`), and sends state messages such as `CaptureStarted`/`SignupEnded`, each cached into `self.last_message`.
2. A different, non-paired entity (per the acknowledged multiplexing condition in the `TODO`) manages to have a payload matching `self_serve::app::v1::RequestState` delivered on the same response stream to this orb client.
3. `main_loop` matches the `RequestState` branch unconditionally and sends `self.last_message` back out over `sender_tx`, without ever checking that the requester's `src.id` equals `self.config.dst_id` — leaking the orb's most recent signup-session state message to the unrelated requester.
