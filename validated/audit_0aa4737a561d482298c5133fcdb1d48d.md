### Title
Operator QR-code verification bypassed for QR codes flagged as `signup_extension`, skipping backend authorization - ([File: src/plans/mod.rs])

### Summary
`verify_operator_qr_code` in `src/plans/mod.rs` is the function responsible for verifying an operator's QR code against the backend before a signup session is allowed to proceed. It contains a shortcut that skips backend verification entirely and unconditionally treats the QR code as valid whenever the QR code's `signup_extension` flag is set, mirroring the reported bug class where a privileged state transition (marking a QR/session as a special "extension" mode) is not gated by any authorization check.

### Finding Description
`verify_operator_qr_code` short-circuits the backend call: [1](#0-0) 

```rust
if qr_code.signup_extension() || self.operator_qr_code_override.is_some() {
    return Ok(Some((0, backend::operator_status::LocationData {
        team_operating_country: "DEV".to_string(),
        session_coordinates: Coordinates { latitude: 0.0f64, longitude: 0.0f64 },
        stationary_location_coordinates: None,
    })));
}
```

`signup_extension` is a boolean parsed straight out of the scanned QR-code string itself [2](#0-1) , via a regex the code itself decodes when the `internal-data-acquisition` feature is compiled in [3](#0-2) [4](#0-3) . Unlike the normal operator-QR path, no backend round-trip (`backend::operator_status::request`) is performed and no server-side "valid" check occurs; a dummy "DEV" location and zero-latency `duration_since_shot_ms` are fabricated in its place.

This is directly analogous to the reported Algebra bug: a privileged/authorization-relevant code path ("deactivated pool" / here "operator/session validated") can be forced into an accepted state by an unprivileged actor supplying a specific value (rate / QR content) without the code re-checking that the actor/state is actually allowed to take that shortcut. Here, whether the QR bypasses backend verification is controlled entirely by data embedded in the (attacker-influenced) QR-code content, not by any server-side or orb-side authorization check tying "signup_extension" mode to a verified operator/internal role.

### Impact Explanation
If an entity can present a QR code that parses into `Data { signup_extension: true, .. }` (i.e. matches the `QR_CODE_SIGNUP_EXTENSION` regex format), the orb will accept it as an "operator" QR code without ever validating it against the backend `operator_status` service. This effectively grants operator-level authorization to start and drive a signup session (including its `signup_extension` special capture modes — pupil contraction, focus sweep, overcapture, multi-wavelength, etc.) purely from local QR content, bypassing the backend's ability to reject unknown/unauthorized operators, enforce team/location constraints, or revoke operator status. Downstream, this operator identity is embedded in signup records and enrollment (`operator_qr_code` is forwarded through `debug_report`, `enroll_user::Plan`, and PCP credential packaging), which can lead to misattributed/unauthorized signup sessions being run under a spoofed "operator."

### Likelihood Explanation
Reaching this code requires the `internal-data-acquisition` feature to be compiled into the running orb-core build (the regex/parsing that sets `signup_extension` is gated by `#[cfg(any(feature = "internal-data-acquisition", test))]`); this is a real (non-test-only) feature used for the orb's internal data-acquisition capability, not a dev-only toggle. Any party able to present a physically or optically scannable QR code to the orb's camera during operator-QR scanning can attempt this bypass — no special hardware access or backend credentials are needed, only knowledge of the accepted QR text format.

### Recommendation
Do not allow `signup_extension`-flagged QR codes to unconditionally skip backend operator verification. At minimum:
- Still perform the backend `operator_status::request` call for `signup_extension` QR codes, and only use the shortcut location/duration values after the backend confirms the operator/session is valid.
- If the intent is to allow "data acquisition" QR codes to skip location-based checks specifically, decouple that from skipping identity/authorization validation entirely — validate the operator identity encoded in the QR against the backend regardless of `signup_extension`.
- Ensure `operator_qr_code_override` (CLI/test override) remains restricted to non-production builds only, and is not reachable when `internal-data-acquisition` is enabled in production.

### Proof of Concept
1. Build/deploy orb-core with the `internal-data-acquisition` feature enabled.
2. Craft a QR-code string matching `QR_CODE_SIGNUP_EXTENSION`, e.g. `userid:<any-uuid-like-string>:0::0::` (per the test fixtures in `qr_scan/user.rs`), which parses to `Data { signup_extension: true, .. }` [5](#0-4) .
3. Present this QR code to the orb during the operator QR-code scan step (`scan_operator_qr_code` → `verify_operator_qr_code`).
4. Observe that `verify_operator_qr_code` returns `Ok(Some(...))` immediately with dummy "DEV" location data, without ever calling `backend::operator_status::request`, thereby accepting an operator that the backend never authorized.
