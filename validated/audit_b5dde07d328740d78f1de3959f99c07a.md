### Title
User QR-code signup extension path bypasses backend user-ID validation, returning default `UserData` for an unverified/non-existent user - (File: `src/plans/mod.rs`)

### Summary
In `handle_user_qr_code`, when both the operator and user QR codes indicate a "signup extension" mode, the code short-circuits and returns `backend::user_status::UserData::default()` for the scanned `user_qr_code` without ever calling `verify_user_qr_code`/`backend::user_status::request`, which is the function that actually confirms the `user_id` exists and is valid on the backend. This is the same bug class as the reported `DropBox::tokenURI` issue: data (here, a "verified" `UserData`/signup outcome) is returned for an identifier (`user_id`) whose existence was never checked.

### Finding Description
`handle_user_qr_code` in [1](#0-0)  parses the user QR code and, before reaching the normal validation path, checks whether either QR code sets the `signup_extension` flag: [2](#0-1) 

If this branch is taken, it returns `Ok(Some(Some((user_qr_code, backend::user_status::UserData::default(), user_qr_code_string))))` directly — it never calls `self.verify_user_qr_code(...)`, which is the only code path that queries the backend (`backend::user_status::request`, `/api/v1/user/{id}/status` or `/api/v2/session/{id}/status`) to confirm the `user_id` is `valid` for signup [3](#0-2) . Contrast this with the normal flow at the bottom of the same function, which only proceeds after `verify_user_qr_code` succeeds: [4](#0-3) 

The `signup_extension()` accessor merely reflects a boolean set locally while parsing the QR-code string [5](#0-4) , and is populated only via `Data::from_signup_extension`, itself only reachable when the QR-code text matches `QR_CODE_SIGNUP_EXTENSION` — a regex that accepts an essentially free-form `user_id` (`[a-z0-9_-]+`, not required to be a UUID) [6](#0-5) . There is no server round-trip confirming that this `user_id` actually corresponds to an existing/authorized signup session.

This mirrors the `DropBox::tokenURI` root cause exactly: an accessor/returner of "existing entity data" (`UserData`) skips the existence/ownership check (`_requireOwned` analog would be `verify_user_qr_code`/backend `valid` check) and instead unconditionally returns a default/placeholder record for an ID that was never confirmed to exist.

### Impact Explanation
If reachable, this allows a signup to proceed for a `user_id` that was never validated against the backend as an existing, authorized session — i.e., the orb treats an arbitrary/self-asserted `user_id` from a QR code as legitimate. Because `UserData::default()` zeroes out `backend_iris_public_key`, `backend_face_public_key`, `id_commitment`, etc. [7](#0-6) , downstream biometric encryption/identity-binding logic would operate with placeholder keys tied to an unverified identifier, creating a signup/identity-binding integrity gap (misattributed or unauthorized signup) rather than a simple data-display bug.

### Likelihood Explanation
This path is gated by `signup_extension`/`signup_extension_config`, which is only set via the `internal-data-acquisition` Cargo feature at QR-parse time [8](#0-7) . Whether `internal-data-acquisition` is compiled into the production Orb binary could not be confirmed within the available context/index (the search for it in `Cargo.toml` returned matches but the surrounding feature-flag definitions/defaults were not retrieved before the tool budget ran out). If this feature is enabled in production builds, likelihood is high given the operator can simply present matching operator/user QR codes with the extension marker; if it is a build-only/internal-testing feature disabled in production, this would fall under the "test-only path" exclusion in the rules, and the finding would not qualify.

### Recommendation
Require that the `signup_extension` branch still calls `verify_user_qr_code` (or an equivalent backend existence/authorization check) before returning `UserData`, instead of substituting `UserData::default()`. At minimum, gate this bypass so it can never be reachable in production builds (confirm `internal-data-acquisition` is excluded from release feature flags), and add an explicit backend round-trip validating `user_qr_code.user_id` exists/is authorized prior to returning any `UserData`.

### Proof of Concept
1. Build/run the orb with the `internal-data-acquisition` feature enabled.
2. Present an operator QR code encoding a `signup_extension` marker (`userid:<id>:<policy>::<mode>::`) matching `QR_CODE_SIGNUP_EXTENSION`.
3. Present a user QR code with an arbitrary/never-issued `user_id` also encoding the `signup_extension` marker with a valid `mode` (e.g., `0` for `Basic`).
4. Observe `handle_user_qr_code` takes the branch at [2](#0-1)  and returns `Ok(Some(Some((user_qr_code, UserData::default(), ...))))` without any call to `backend::user_status::request`, i.e., without the backend ever confirming the `user_id` is `valid`.

**Uncertainty note:** I could not verify within the available tool budget whether `internal-data-acquisition` is enabled in production Orb builds (default features in `Cargo.toml`) or is strictly a dev/test-only feature; this materially affects whether the finding is in-scope per the "reject test-only paths" rule. A background session with full repo/file access would be needed to check `Cargo.toml`'s `[features]` defaults and any build/release configuration that selects feature flags.
