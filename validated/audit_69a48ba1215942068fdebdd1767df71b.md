### Title
Missing chain/network binding in `DelegateAction` (NEP-366) signatures enables cross-network meta-transaction replay - (File: core/primitives/src/action/delegate.rs)

### Summary
The NEAR meta-transaction (`DelegateAction`, NEP-366) signing scheme hashes only `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key`, tagged with a NEP-number discriminant. Unlike ordinary `SignedTransaction`s, which embed a recent `block_hash` that is chain-specific (a hash from chain A will not exist as a recent block in chain B), a `DelegateAction` embeds no chain-identifying data at all — `max_block_height` is a bare integer, not a hash. Any two NEAR-protocol networks that share account state (same `sender_id`, same registered `public_key`, and access-key nonce in the valid range) will accept the exact same signed `DelegateAction` bytes and signature.

### Finding Description
`SignedDelegateAction::sign`/`verify` and `VersionedSignedDelegateAction::sign`/`verify` compute the signed hash purely from the `DelegateAction`/`DelegateActionV2` payload via `get_nep461_hash`, which wraps the action in a `SignableMessage` carrying only a NEP-number discriminant (366 or 611) [3](#0-2) [4](#0-3) . The discriminant mechanism itself is explicitly scoped to disambiguate *message types* (NEP-366 vs NEP-611 vs ordinary transactions), not networks or chains [5](#0-4) .

On execution, `apply_delegate_action` only validates the signature, `max_block_height` against the *local* block height, that `sender_id` matches the tx receiver, and the access key's nonce/permissions — none of which is chain-specific data supplied by the signer [6](#0-5) [7](#0-6) . `max_block_height` is just a height threshold (`current height must be <= max_block_height`), and it is trivially satisfiable on any chain that has produced at least that many blocks — it provides no chain-identity guarantee. In contrast, ordinary `SignedTransaction`s bind to a specific chain via their embedded recent `block_hash`, checked against `InvalidChain`/`Expired` in the verifier [8](#0-7)  — a protection `DelegateAction` never had, because it doesn't carry a block hash at all.

Consequently, if an account holder (or a relayer acting for them) uses the same account id and the same key pair across two NEAR-protocol networks — a very common real-world pattern for testnet/mainnet parity, disaster-recovery forks, "forknet"-style mainnet-state clones used for shadow testing, or any network split/rollback that preserves account and key state — a `DelegateAction` signed and intended for use on one network can be captured and replayed verbatim (wrapped in a new outer transaction by any relayer/attacker) on the other network, as long as the nonce/`max_block_height` constraints happen to still be satisfiable there. This is the direct analog of the Harpie `changeRecipientAddress()` issue: the signed payload lacks any chain-binding value (there, `chain.id`; here, a chain/genesis identifier), so an action intended for chain A executes with full effect on chain B.

### Impact Explanation
A relayer or attacker who observes a `DelegateAction` signed by a user on one network can resubmit it on a different network sharing that user's account/key state, causing the delegated actions (e.g., transfers, adding attacker-controlled full-access keys, function calls moving funds) to execute there without the user's consent for that specific network. This is an unauthorized state/balance change executed via a normal, unprivileged transaction-submission path (`apply_delegate_action`, reached from any submitted transaction containing `Action::Delegate`/`Action::DelegateV2`), matching the "unauthorized state or balance change" / "theft" impact category.

### Likelihood Explanation
Exploitability depends on an attacker being able to observe a signed `DelegateAction` (they are transmitted off-chain to a relayer per the NEP-366 design, so relayers or anyone the relayer discloses to routinely see them [9](#0-8) ) and on the same account/key pair being valid with a satisfiable nonce/height on a second NEAR-protocol network. This is realistic in NEAR's ecosystem given shared genesis/testnet tooling and common key reuse, but requires this specific dual-network condition, so likelihood is moderate rather than universal.

### Recommendation
Include a chain/network-identifying value (e.g., genesis hash or a protocol-configured chain ID) as part of the `SignableMessage`/`DelegateAction` payload that is hashed and signed, analogous to including `chain.id` in the Harpie fix, so that a `DelegateAction` signed for one network cannot be verified successfully on another.

### Proof of Concept
1. On Network A (e.g., testnet), account `alice.near` with access key `K` signs a `DelegateAction{ sender_id: alice.near, receiver_id: bob.near, actions: [AddFullAccessKey(attacker_key)], nonce: N, max_block_height: H, public_key: K }` via `SignedDelegateAction::sign` [10](#0-9) , intending it for a relayer on Network A only.
2. An attacker (the relayer, or anyone who intercepts the off-chain payload) instead submits this same `SignedDelegateAction` bytes wrapped in an outer `SignedTransaction` on Network B, where `alice.near` also exists with the same public key `K` and access-key nonce `< N < H * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`.
3. `apply_delegate_action` on Network B verifies the signature successfully (no chain-binding data to reject it) [11](#0-10) , passes nonce/height checks [7](#0-6) , and executes `AddFullAccessKey(attacker_key)` on `alice.near`'s account on Network B, giving the attacker control of Alice's funds there — despite Alice never intending this action on Network B.

    /// Delegate action hash used for NEP-461 signature scheme which tags
    /// different messages before hashing
    ///
    /// For more details, see: [NEP-461](https://github.com/near/NEPs/pull/461)
    pub fn get_nep461_hash(&self) -> CryptoHash {
        let signable = SignableMessage::new(&self, SignableMessageType::DelegateActionV2);
        let bytes = borsh::to_vec(&signable).expect("failed to serialize");
        hash(&bytes)
    }

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
