### Title
Webhook `shop-domain` header is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity used by webhook handlers purely from the unauthenticated `X-Shopify-Shop-Domain` header, while the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body. This breaks the identity binding `hmac(body) == hmac(body, shop)` that the handler dispatch logic implicitly assumes, allowing a previously-observed, validly-signed webhook body to be replayed with an attacker-chosen `shop` header and still pass HMAC verification.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is read directly from a request header with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature exclusively from `verifiable_query.to_signable_string` (the body), and never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Webhooks::Registry.process` accepts any request whose body HMAC validates, then forwards `request.shop` (the unauthenticated header) straight into the handler as the tenant identifier: [4](#0-3) 

Because a single app (and single `api_secret_key`) serves many merchant shops, and the HMAC is app-scoped rather than shop-scoped, **any** validly-signed webhook body legitimately delivered to the app for **any** shop remains validly signed for **every** shop. An attacker who can obtain one authentic `(body, hmac)` pair (e.g., by installing the app on their own shop and receiving a real webhook, or intercepting/logging one) can resubmit the exact same body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` will still return `true` because it never looks at the header, and `Registry.process` will hand the forged `shop` value to the handler as if Shopify itself delivered it for that shop.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce: the handler receives `WebhookMetadata` claiming to be for shop B while the cryptographic proof only established "some data the app itself generated/received for shop A." Applications that key persistence, cache invalidation, GDPR/data-erasure, order/inventory sync, or entitlement changes off `WebhookMetadata#shop` can be tricked into applying attacker-supplied (but validly-signed-for-a-different-shop) payloads to another merchant's tenant, i.e. cross-tenant data corruption/access — a Critical-class impact per the scan's rules.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the app on any shop (trivial for a public/embedded app) or otherwise obtain a single legitimate `(body, hmac)` webhook pair, and (2) the ability to POST to the app's own publicly-reachable webhook endpoint with a modified `shop-domain` header — no possession of `api_secret_key` or any credential belonging to the victim shop is needed. This is reachable purely through this gem's documented `Webhooks::Request`/`Registry.process` API, with no reliance on host-application misuse.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to the specific delivery, e.g.:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string` (this deviates from Shopify's wire format, so instead:
- After body HMAC validation succeeds, additionally verify that the request's `shop` corresponds to a session/shop for which this specific delivery was actually expected (e.g., cross-check against Shopify's per-shop webhook subscription record or require TLS-terminated, IP-restricted delivery from Shopify), and document to consumers that `WebhookMetadata#shop` is unauthenticated and must not be trusted as sole tenant identifier without additional verification.
- At minimum, update documentation/API to make clear the header-derived `shop` is not covered by the signature so host applications don't rely on it alone to select tenant context, and consider rejecting requests where `shop` does not match an app-known, currently-installed shop.

### Proof of Concept
```ruby
require "openssl"
require "base64"

secret = ShopifyAPI::Context.api_secret_key
body = '{"id":1,"note":"hello"}'

hmac_digest = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body)
hmac_b64 = Base64.encode64(hmac_digest)

# Step 1: Attacker legitimately receives this exact (body, hmac) pair for THEIR OWN shop
# e.g. from a real Shopify webhook delivery to "attacker-shop.myshopify.com"

# Step 2: Attacker replays identical body/hmac but swaps the shop header to a victim shop
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac_b64,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, not signed
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

ShopifyAPI::Utils::HmacValidator.validate(request) # => true, even though shop was forged
ShopifyAPI::Webhooks::Registry.process(request)
# Handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", body: {...})
# even though Shopify never sent anything for victim-shop with this body.
```

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
