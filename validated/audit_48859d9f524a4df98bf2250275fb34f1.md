### Title
Fraud detection is a hardcoded no-op that always reports "no fraud," discarding real biometric fraud signals - (File: src/plans/mod.rs)

### Summary
The Sherlock bug is a case where a value that is supposed to be dynamically computed from real state (Aave/Beta protocol exchange rate) is instead hardcoded to a fixed value (1 or 0), which causes a downstream decision (gamer reward calculation) to always resolve to the same wrong outcome regardless of actual protocol activity. The same structural pattern — a security-relevant decision function that ignores the real computed signals and unconditionally returns a fixed result — exists in `detect_fraud` in `src/plans/mod.rs`.

### Finding Description
`detect_fraud` is called after the biometric pipeline completes, and its boolean result determines whether a signup is flagged as fraudulent: [1](#0-0) 

However, the function body ignores the actual pipeline output and unconditionally returns `false`: [2](#0-1) 

This mirrors `fraud_check.rs`, where the number of fraud checks is hardcoded to zero: [3](#0-2) 

Just as `AaveProvider.exchangeRate()` always returning `1` makes the "yield" calculation numerator always `0` regardless of real protocol yield, `detect_fraud` always returning `Ok(false)` makes the "fraud" signal always negative regardless of the real biometric pipeline results (`pipeline.face_identifier_fraud_checks`, occlusion detection, iris agent errors, etc., which are computed and attached to the debug report but never fed into the fraud decision). The computed signals exist in the pipeline (e.g. `pipeline.face_identifier_fraud_checks` at line 1355 is stored into `debug_report` for audit purposes) but are structurally disconnected from the actual `fraud_detected` boolean that drives `SignupReason`.

### Impact Explanation
`fraud_detected` feeds `signup_reason`, which is propagated into `enroll_user::Plan` and `personal_custody_package::Plan`, and ultimately into the backend `signup_post` request as `SignupReason`. Because the value is structurally pinned to `false`, no signup can ever be routed down the `SignupReason::Fraud` path from local computation, meaning any fraud enforcement that depends on the local pipeline result is fully bypassed for every user, unconditionally, regardless of what the underlying biometric checks actually computed. This is analogous to the vault case where the entire yield calculation is skewed to a fixed, wrong outcome for every rebalancing cycle, benefiting one class of participant (depositors) at the expense of another (gamers) — here, every signup benefits from "not fraud" classification regardless of true state.

### Likelihood Explanation
This is not a probabilistic or edge-case bug — the return value is unconditional (`Ok(false)` is the only path out of the function once `_pipeline` is `Some`), so the bypass occurs on 100% of signups where a pipeline is present, exactly as the referenced exchange-rate bug applies to every rebalancing.

### Recommendation
Wire the actual computed pipeline signals (`face_identifier_fraud_checks`, occlusion results, iris agent errors, etc.) into `detect_fraud`'s return value instead of hardcoding `Ok(false)`, so that `SignupReason::Fraud` can be genuinely derived from biometric pipeline output.

### Proof of Concept
1. Complete a signup so that `biometric_pipeline` returns `Some(pipeline)` with fraud-indicating internals (e.g., populated `face_identifier_fraud_checks` or occlusion errors), as stored via `debug_report.face_identifier_results(...)` / `debug_report.occlusion_error(...)` at lines 1355–1359 in `src/plans/mod.rs`.
2. Observe that `detect_fraud` at lines 1392–1406 in `src/plans/mod.rs` still returns `Ok(false)` unconditionally.
3. Observe `signup_reason` at lines 565–571 is therefore always `SignupReason::Normal` (never `SignupReason::Fraud`) whenever a pipeline exists, regardless of the fraud signals captured in step 1. [2](#0-1) [3](#0-2)
