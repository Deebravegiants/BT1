### Title
Unbounded backend-controlled retry loop in `orb_relay_announce_orb_id` can wedge self-serve signup sessions - ([File: src/plans/mod.rs])

### Summary
`Config::from_backend` copies `orb_relay_announce_orb_id_retries` (a `u32`) straight from the backend response with no upper bound, and `Config::validate` only checks `sound_volume`, so a malicious/compromised backend can set retries to `u32::MAX`. `orb_relay_announce_orb_id`, called from `do_signup` for every self-serve session with a `orb_relay_app_id`, loops `for _ in 0..reties` calling `send_blocking(..., timeout)` with no overall deadline, so a backend that also controls (or fails at) the relay ack can force this loop to run effectively forever, wedging `do_signup` after QR validation and before biometric capture.

### Finding Description
`orb_relay_announce_orb_id_retries` and `orb_relay_announce_orb_id_timeout` are deserialized from the backend config response without range limits: [1](#0-0) , and passed through unchanged in `Config::from_backend` [2](#0-1) . `Config::validate` performs no bound check on these fields, only on `sound_volume` [3](#0-2) .

In `do_signup`, once the QR codes are validated and the user is a self-serve user with an `orb_relay_app_id`, the plan calls `orb_relay_announce_orb_id` with the backend-supplied `retries`/`timeout` before biometric capture starts [4](#0-3) . The function itself loops `for _ in 0..reties`, calling `send_blocking` per iteration and only sleeping 1s if there are pending messages, with no cumulative/overall deadline bounding the loop: [5](#0-4) . Each iteration's worst case is bounded by `timeout` (from `send_blocking`'s `tokio::time::timeout`, see `orb-relay-client/src/client.rs:282-290`), but the total loop time is `retries * (timeout + reconnect time)`, unbounded by `reties = u32::MAX`.

There is no outer cancellation, deadline, or watchdog wrapping this call in `do_signup` — it is a plain `.await` on the future, so if the relay backend always fails the ack (or the loop otherwise makes slow progress), the signup task will not return control to the state machine for a very long time (practically unbounded for `u32::MAX` retries even at sub-second per-iteration cost).

### Impact Explanation
This causes a session-level denial of service on the self-serve signup flow: the state machine is stuck in `do_signup` after identity has been validated (QR scanned) and before biometric capture, holding session resources (agents, debug report, allocated capture buffers) without progressing or timing out. This matches an availability/DoS-style impact bounty category (state-machine wedge / resource exhaustion in the signup flow) rather than a data-disclosure or identity-binding bypass.

### Likelihood Explanation
Requires an attacker-controlled or compromised backend config response and a relay endpoint that fails/never acks — both are within the stated "attacker-controlled backend config" precondition for this question, and self-serve mode (`self_serve: true` with `orb_relay_app_id` present) is a normal, reachable configuration. The bug is deterministic and repeatable: any self-serve signup session under such a config will hang on `orb_relay_announce_orb_id_retries`/`timeout` combination.

### Recommendation
Enforce sane upper bounds on `orb_relay_announce_orb_id_retries` (and ideally an overall wall-clock deadline for the whole announce loop, not just per-attempt) in `Config::validate`, and wrap the call in `do_signup` with a bounded `tokio::time::timeout` so a misconfigured or malicious backend cannot make the loop run beyond a fixed ceiling (e.g., a few tens of seconds total), returning a signup failure instead.

### Proof of Concept
Integration test: construct `Config` with `orb_relay_announce_orb_id_retries = u32::MAX` and `orb_relay_announce_orb_id_timeout` at its small default; point the relay client at a test server that always drops/never acks `AnnounceOrbId`. Call `orb_relay_announce_orb_id` (or run `do_signup` through the self-serve path) and assert that the call returns an `Err` within a bounded overall deadline (e.g., wrap the call in `tokio::time::timeout(Duration::from_secs(30), ...)` and assert `Ok(Err(_))` rather than the outer timeout firing), proving that the current implementation has no such bound and the outer timeout will fire instead.
