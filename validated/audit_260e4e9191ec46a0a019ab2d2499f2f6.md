## Analysis

The report describes a class of bug where a value that's *acted upon* isn't the value that was actually *authenticated*. The strongest analog in this gem is in the webhook processing pipeline: the HMAC signature only covers the raw request body, while the `shop` (and `topic`/`webhook-id`) values used to identify the tenant are taken straight from unauthenticated HTTP headers.

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

but `shop` (and `topic`, `webhook_id`, `api_version`) are read directly from headers, entirely outside the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies the signature over `to_signable_string` (i.e. the body): [3](#0-2) 

And `Registry.process` uses that unauthenticated `shop` header directly to build the data passed to the app's handler, with no cross-check against the signed content: [4](#0-3) 

### Title
Webhook tenant identity (`shop`) is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies only that the raw HTTP body was signed with the app's shared `api_secret_key`; it never binds that signature to the `x-shopify-shop-domain` (or `topic`/`webhook-id`) header. Since the signing key is shared across every shop that installs the app, any shop that legitimately receives a webhook (a valid `(body, hmac)` pair) can replay that body against the app's webhook endpoint while substituting a different shop's domain in the header, and the signature check will still pass. The handler then processes the payload as if it genuinely originated from the victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the signature only against `verifiable_query.to_signable_string`, and for webhook requests that string is defined as `@raw_body` alone [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` values are parsed straight from HTTP headers with no cryptographic linkage to the signature [5](#0-4) [6](#0-5) .

`Registry.process` raises only if the HMAC check on the body fails, then immediately forwards the caller-controlled `request.shop` into `WebhookMetadata` for the app's handler to consume as the tenant identity [4](#0-3) .

The equality that should hold — `shop bound in HMAC == shop acted on by the handler` — does not hold: the HMAC only proves "this body was produced with the app's secret," not "this body pertains to shop X." Because Shopify uses one shared `api_secret_key` per app across all installing shops, any shop's genuinely-delivered webhook gives an attacker a valid `(body, hmac)` pair they can freely relabel with a different `x-shopify-shop-domain` header and POST to the shared, public webhook endpoint.

### Impact Explanation
This breaks the tenant boundary the report's bug class targets: the field acted on (`shop`, used by host apps to select which merchant's records to update per the documented pattern in `docs/usage/webhooks.md`) is not the field the cryptographic proof actually covers. An attacker who is a legitimate (if low-privilege) merchant on the same multi-tenant app can forge webhook deliveries "from" any other merchant, leading to cross-tenant data confusion/corruption (e.g., causing the app to create/update/delete data attributed to a victim shop, or trigger app-side side effects scoped to that shop) — this is a cross-tenant access issue, one of the Critical impact categories in scope.

### Likelihood Explanation
Likelihood is realistic: any entity can install the target app on their own shop (a normal, unprivileged action), thereby legitimately receiving webhooks with valid `(body, hmac)` pairs signed with the app's single shared secret. No possession of `api_secret_key`, access tokens, or privileged access is required — only a body/signature pair obtainable through ordinary use of the app, which is then replayed with a forged shop header to the same publicly reachable webhook endpoint used by every installed shop.

### Recommendation
Bind the tenant identity into the verified material rather than trusting unauthenticated headers:
- Include `shop`, `topic`, and `webhook_id` in the signable string used by `HmacValidator`, or
- Require host applications to independently correlate the header-derived `shop` against per-shop verification (e.g., per-shop secrets, or verifying that the shop belongs to an existing, expected session before acting on the webhook), and document this gap clearly in `Registry.process`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop (`attacker.myshopify.com`), a normal unprivileged action.
2. Shopify delivers a legitimate webhook to the app's public webhook endpoint, signed with the app's shared `api_secret_key`:
   ```
   POST /webhook
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid signature over the body>
   X-Shopify-Shop-Domain: attacker.myshopify.com
   Body: {"id": 1, ...}
   ```
3. Attacker captures this `(body, hmac)` pair (they control the endpoint that received it, or otherwise obtain it from their own installation).
4. Attacker replays the exact same body/hmac to the app's webhook endpoint, but swaps the shop header:
   ```
   POST /webhook
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <same valid signature — body unchanged>
   X-Shopify-Shop-Domain: victim.myshopify.com
   Body: {"id": 1, ...}
   ```
5. `Utils::HmacValidator.validate` passes because it only checks the (unchanged) body signature [7](#0-6) ; `Registry.process` dispatches the handler with `shop: "victim.myshopify.com"` [4](#0-3) , causing the app to act on `victim`'s tenant data using attacker-supplied content.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
