## Finding: `CallDispatcher.dispatch()` is a permissionless function that lets anyone drain any ETH/token balance left on the shared dispatcher contract

### Title
Anyone can call `CallDispatcher.dispatch()` to steal residual ETH/token balances held by the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a single, shared, unowned utility contract used by multiple Hyperbridge apps (`HyperFungibleTokenUpgradeable`, `WrappedHyperFungibleTokenUpgradeable`, `IntentsBase`) to execute arbitrary calldata attached to cross-chain messages/orders. Its `dispatch()` entrypoint has no access control whatsoever, exactly analogous to D3Proxy's unrestricted `refundETH()` — it operates on the contract's *own* balance/allowances and can be invoked by anyone, at any time, to redirect any funds currently sitting on the dispatcher.

### Finding Description
`CallDispatcher.dispatch()` is `external` with no caller restriction: [1](#0-0) 

It accepts an arbitrary `Call[]` and executes `to.call{value: call.value}(call.data)` for each entry, in the dispatcher's own context (not `delegatecall`), gated only by an `extcodesize(to) != 0` check — trivially satisfiable by deploying any throwaway contract.

The contract is designed to *temporarily hold* funds: it has `receive() external payable {}` and is documented as the destination for unlocked tokens/native ETH before executing composable calls: [2](#0-1) [3](#0-2) 

For `HyperFungibleTokenUpgradeable.onAccept`, when the message carries calldata, tokens are minted directly to the `beneficiary` (which is set to the `CallDispatcher` address by design so the dispatcher can spend them), and `dispatch()` is invoked with **no residual-balance sweep afterward**: [4](#0-3) 

The same pattern (unwrap-to-dispatcher, dispatch, no sweep) exists in `WrappedHyperFungibleTokenUpgradeable.onAccept`: [5](#0-4) 

Because `message.data` is attacker/sender-controlled (it originates from the source-chain caller of `send()`), any leftover ETH/tokens that the encoded `Call[]` doesn't fully spend (e.g. slippage, over-approval, partial consumption, or a benign/no-op call array) remains permanently parked on the shared `CallDispatcher` contract. Since `dispatch()` has zero access control and no notion of "whose funds these are," **any third party** can subsequently call `CallDispatcher.dispatch()` directly with a `Call` that sweeps `address(this).balance` (native ETH) or calls `IERC20.transfer` for any token balance to an address they control.

Unlike `IntentsBase._execute`, which explicitly sweeps dust back to itself after dispatching output calls in the same atomic flow, the token apps' `onAccept` paths leave the dispatcher's balance unprotected between transactions: [6](#0-5) 

### Impact Explanation
This is a direct theft-of-funds vector: any residual native ETH or ERC20 tokens left on the shared `CallDispatcher` — a contract that is deliberately funded via cross-chain unlock/mint flows and payable receive — is claimable by any unprivileged caller. Because `CallDispatcher` is shared across all `HyperFungibleToken`/`WrappedHyperFungibleToken` deployments and `IntentsBase`-derived apps referencing the same deployed instance, this can affect multiple apps' users simultaneously, and any dust or under-spent calldata execution result becomes permanently stealable rather than recoverable by the intended beneficiary or governance.

### Likelihood Explanation
Likelihood is high in practice: calldata-execution flows (swaps, multi-step DeFi calls) routinely leave small residual balances due to slippage/rounding, and nothing in `HyperFungibleTokenUpgradeable`/`WrappedHyperFungibleTokenUpgradeable` sweeps this back. An attacker only needs to monitor the `CallDispatcher`'s ETH/token balance and front-run/opportunistically call `dispatch()` — a single, cheap, always-available transaction with no preconditions or privileges required.

### Recommendation
Restrict `CallDispatcher.dispatch()` so it cannot be invoked by arbitrary EOAs to sweep unrelated balances — e.g., require the caller to be an authorized app (allowlist of `HyperFungibleToken`/`WrappedHyperFungibleToken`/`IntentsBase` instances), or redesign so calldata execution happens via `delegatecall`/ephemeral per-call escrow instead of a shared, standing balance. At minimum, add a mandatory sweep-back step (like `IntentsBase._execute` already does) in every `onAccept` path that funds the dispatcher, and consider forbidding `dispatch()` from targeting/transferring more than what was explicitly earmarked in the same transaction.

### Proof of Concept
1. Sender on source chain calls `HyperFungibleTokenUpgradeable.send()` with `to = <CallDispatcher address>` and `data` encoding a `Call[]` that performs a token swap intentionally leaving 1% slippage dust on the dispatcher (or simply a no-op `Call` array with `data.length > 0` but calls that don't spend the full minted amount).
2. Relayer submits the proof; `onAccept` mints `message.amount` tokens to the `CallDispatcher` and calls `ICallDispatcher(_dispatcher).dispatch(message.data)` — legitimate calls execute but leave residual token balance on `CallDispatcher`.
3. Attacker deploys a trivial contract `Sink` with a `receive()`/`fallback` to satisfy `extcodesize(to) != 0`.
4. Attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: address(Sink), value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, IERC20(token).balanceOf(address(dispatcher)))})]))` — wait, correct pattern: attacker calls `dispatch` with `Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, residualBalance)})` directly (token itself has code, satisfying the check), transferring the entire residual ERC20 balance held by `CallDispatcher` to themselves. For native ETH dust, attacker uses `Call({to: attackerContract, value: address(dispatcher).balance, data: ""})`.
5. Funds are irrecoverably stolen from the shared dispatcher; no relationship between attacker and the original cross-chain transfer is required.

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({from: message.from, to: beneficiary, source: string(request.source), amount: message.amount});
    }
