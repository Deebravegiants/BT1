## Analog Found: Mutable global-contract code breaks the "fixed code and fixed initial state" guarantee of NEAR deterministic accounts

### Title
Deterministic accounts referencing a mutable `GlobalContractIdentifier::AccountId` contract can have their code silently changed post-creation, breaking the deterministic-account trust/ownership guarantee - (File: `runtime/runtime/src/global_contracts.rs`, `runtime/runtime/src/deterministic_account_id.rs`)

### Summary
NEAR's NEP-616 "deterministic accounts" (`DeterministicStateInitAction`) are documented as accounts with "fixed code and fixed initial state," and the account id is cryptographically derived from a `DeterministicAccountStateInit` so that "only an identical deployment with identical properties" maps to that id — exactly the property the external report says is missing from `SuperchainTokenBridge`. However, when the `code` field of that state-init is a `GlobalContractIdentifier::AccountId` (as opposed to `CodeHash`), the "fixed code" guarantee is not actually anchored to bytecode content — it's anchored to a mutable reference. The account that originally deployed the referenced global contract can redeploy new code under that same `AccountId` identifier at any later time, and every deterministic (and non-deterministic) account that "uses" that identifier will silently start executing the new code, without its address/account-id ever changing and without any action from the deterministic account's actual data-owner.

### Finding Description
`GlobalContractDeployMode::AccountId` is explicitly documented as mutable: "Contract is deployed under the owner account id... This allows the owner to update the contract for all its users." [1](#0-0) 

When a global contract is (re)deployed in `AccountId` mode, `initiate_distribution` always computes the identifier as `GlobalContractIdentifier::AccountId(account_id)` — i.e., the same identifier is reused/overwritten regardless of how many times the code is redeployed: [2](#0-1) 

`use_global_contract` — invoked both by the plain `UseGlobalContractAction` and internally by deterministic-account creation — stores only a reference (`AccountContract::GlobalByAccount(id)`) on the account, not a hash of the actual bytecode: [3](#0-2) 

`deploy_deterministic_account` (the code path executed by `DeterministicStateInitAction`) calls this same `use_global_contract` with `state_init.code()`: [4](#0-3) 

Crucially, the deterministic account id is derived by borsh-encoding the entire `DeterministicAccountStateInit` (which embeds the `GlobalContractIdentifier::AccountId(account_id)` value, not a hash of the code bytes) and hashing it: [5](#0-4) 

So the deterministic account id only commits to *which account id to defer to for code*, not to the code itself. Once the referenced global-contract owner redeploys different code (a normal, permitted action — `action_deploy_global_contract` with `AccountId` mode), every account that already executed `UseGlobalContractAction`/`DeterministicStateInitAction` against that identifier begins running the new code. This is confirmed by the test suite itself, which demonstrates exactly this behavior change without any new deployment/creation at the consuming accounts: [6](#0-5) 

This directly parallels the external report's root cause: a system component (`sendERC20`/`relayERC20` there, `DeterministicStateInitAction`/`UseGlobalContractAction` here) treats an address/identifier as if it commits to fixed, verifiable behavior, when in fact the identifier only commits to a mutable pointer. In the SuperchainERC20 case, two different depoyers can get the same address with different constructor outcomes; in NEAR's case, one nominally-fixed "deterministic" address's *behavior* can change after the fact because the `code` field is a mutable account reference rather than a content hash.

The blast radius is amplified by NEP-616's own intended usage pattern: the reference "sharded contract" implementation uses deterministic-account-id equality to establish a **trust relationship between peer accounts** (`peer_check`), assuming that matching account ids implies matching code and owner semantics: [7](#0-6) 

If the code was deployed via `GlobalContractDeployMode::AccountId`, the global-contract deployer can change what "peer" code actually does for every already-onboarded sharded-contract instance (e.g. `spread`-onboarded users), invalidating the `root_check`/`peer_check` trust assumptions and any funds/permissions gated behind them, without those instances’ account ids ever changing.

### Impact Explanation
Any deterministic account (or any account using `UseGlobalContractAction`) whose code is referenced via `GlobalContractIdentifier::AccountId` does not actually have immutable/fixed logic despite NEP-616 documenting deterministic accounts as having "fixed code and fixed initial state." A malicious or compromised global-contract owner can push new logic (e.g., functions that drain balances, bypass `root_check`/`peer_check`, or redefine storage semantics) into every account referencing that identifier, at any time, with no new transaction required from the affected accounts. Where such accounts hold balances or gate authorization on "same code" trust (as the reference sharded-contract pattern does), this enables unauthorized state/balance manipulation reachable purely through ordinary transactions (`DeployGlobalContractAction`, `DeterministicStateInitAction`, `UseGlobalContractAction`) — no validator or P2P privilege required.

### Likelihood Explanation
This requires an attacker to control (or later compromise) the account that deployed the global contract in `AccountId` mode, or to convince a user/dApp to reference an `AccountId`-mode contract that they do not fully trust for its entire future lifetime — a realistic scenario for any "shared library" style global contract used across many onboarded deterministic accounts, since `AccountId` mode is explicitly provided as a normal, documented deployment option (not a misuse). The mechanism is directly demonstrated to work as described by existing tests (`test_global_contract_update`), so no exotic conditions are needed — it is a designed capability whose interaction with deterministic-account "fixed code" guarantees and NEP-616's peer-trust pattern is the actual risk.

### Recommendation
- Clearly document, at the `DeterministicAccountStateInit`/deterministic-account level, that using `GlobalContractIdentifier::AccountId` for `code` does **not** provide the "fixed code" guarantee otherwise implied for deterministic accounts, since the referenced code is mutable by its deployer.
- Recommend (or enforce via tooling/lint) that deterministic accounts and any code implementing peer/ownership trust checks (like the sharded-contract `root_check`/`peer_check` pattern) only reference code via the immutable `GlobalContractIdentifier::CodeHash` variant, mirroring the OP Labs recommendation to bind identity to immutable, content-addressed values rather than mutable references.
- Consider surfacing a protocol-level warning/error when `DeterministicStateInitAction` is used with a `code: GlobalContractIdentifier::AccountId` value, so integrators are forced to make an explicit, informed choice.

### Proof of Concept
1. Account `owner` deploys global contract `V1` via `DeployGlobalContractAction { deploy_mode: AccountId }` (as in `test_deploy_global_contract`/`test_global_contract_update`). [8](#0-7) 
2. User `alice` creates a deterministic account via `DeterministicStateInitAction` with `state_init.code = GlobalContractIdentifier::AccountId(owner)` and `data = {"root": alice}` — establishing "alice owns this instance" per the sharded-contract pattern.
3. Later, `owner` redeploys new code `V2` (still `AccountId` mode) containing a backdoor (e.g., a function bypassing `root_check`/draining balance) via another `DeployGlobalContractAction`.
4. Without any new action targeting alice's deterministic account, it now executes `V2`'s logic (per `test_global_contract_update`'s demonstrated behavior), including the backdoor, while its account id and stored `root` data remain unchanged — undermining the "fixed code and fixed initial state" property NEP-616 relies on for the deterministic account id to convey any security guarantee.

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())
}

fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple

    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.

        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
