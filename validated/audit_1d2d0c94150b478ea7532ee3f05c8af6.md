### Title
Webhook HMAC only signs the request body, not the `shop-domain`/`topic` headers, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` binds its `hmac` value to `@raw_body` alone, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers and never included in the signable string. `Utils::HmacValidator.validate` only proves that the raw body was signed with the app's secret — it says nothing about which shop or topic that body belongs to. Any bearer of one genuine webhook (e.g. an attacker who installs the app on their own store) can replay the same body+HMAC pair while swapping the `shop-domain`/`topic` headers, and the validator still returns `true`.

This is the exact class of bug in the analog rule: a field that is *acted on* (the `shop` used to identify the tenant, and `topic` used to route to a handler) is not *covered by the HMAC*. The binding that should hold is:
`HMAC_valid(body, secret) ⇒ (shop, topic, body)` all genuinely originated together from Shopify for that shop.
In this implementation the actual guarantee is only `HMAC_valid(body, secret)`, decoupled from `shop`/`topic`. Because `shop` and `topic` are headers under the sender's control on the wire, and Shopify signs `raw_body` deterministically for identical payloads, a valid `(body, hmac)` pair captured from one tenant/topic remains valid when replayed with a different `shop-domain`/`topic` header.

### Impact Explanation
An unprivileged internet user who can obtain any single genuine webhook delivery (trivially achievable by installing the app — even for free/public apps — on their own test store, since Shopify will deliver real webhooks with a valid HMAC to that install) can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a victim shop or a different registered topic. `HmacValidator.validate` will accept it, and `Registry.process` will invoke the app's handler with `WebhookMetadata` claiming the forged shop/topic. Any app logic that uses `data.shop` to look up a merchant session, write to per-tenant storage, or make authenticated Admin API calls "on behalf of" that shop will act on forged data attributed to another tenant — i.e. cross-tenant access/data corruption using only a header swap, no access token or `client_secret` needed.

### Likelihood Explanation
Requires no privileged credentials — only the ability to receive one legitimate webhook (trivial for any developer/attacker who installs the target app on their own store) and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with attacker-chosen headers, both of which are within reach of an unprivileged internet user.

### Recommendation
Include `shop`, `topic`, (and ideally `webhook_id`/`api_version`) in the HMAC-covered signable string, or otherwise cryptographically bind the header-derived identity fields to the signed payload, so that `HmacValidator.validate` cannot succeed for a body replayed under a different shop or topic.

### Proof of Concept
1. Install the target embedded app on attacker-owned store `attacker.myshopify.com`, triggering Shopify to deliver a genuine webhook (e.g. `orders/create`) with body `B` and header `x-shopify-hmac-sha256: H` where `H = Base64(HMAC-SHA256(client_secret, B))`.
2. Capture `B` and `H` from this legitimate delivery.
3. POST to the app's webhook endpoint with the same raw body `B` and the same `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim.myshopify.com` (and/or a different `x-shopify-topic`).
4. `ShopifyAPI::Webhooks::Request#hmac` still decodes to the same bytes as `H`; `to_signable_string` still returns `B`; `HmacValidator.validate` computes the same HMAC over `B` and returns `true`.
5. `Registry.process` dispatches to the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: JSON.parse(B), ...)` — the app now processes forged data as if it originated from `victim.myshopify.com`. [5](#0-4) [4](#0-3)
