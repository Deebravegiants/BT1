**Analysis:**

The premise misdescribes what `StateApi::resource` in `api/src/state.rs` actually does. This function is a thin, generic read-only accessor: it takes an `address` and an already-validated `resource_type` (`MoveStructTag`), looks up the exact BCS-encoded resource bytes for that struct tag at that address via `find_resource`, and deserializes them with `try_into_resource` into an `AnnotatedMoveStruct`/`MoveResource`. [1](#0-0) 

Critically, `try_into_resource` (in `MoveConverter`) performs a pure BCS-to-JSON annotation of the struct fields as declared in the module's type layout — it does **not** perform any cross-reference resolution of `Object<T>` handles to look up "the pointed-to metadata's actual issuing module" or compute an "owner" of that metadata. An `Object<Metadata>` field is stored and rendered simply as its `inner: AccountAddress` value, exactly as it was written on-chain. [2](#0-1) [3](#0-2) 

So there is no "metadata owner field" in the API response that could be "corrupted" — `FungibleStore.metadata` is just the raw address the store's creator set at `create_store` time, and `resource()` reports that address verbatim. [4](#0-3) [5](#0-4) 

The scenario describes two independent, legitimate on-chain facts: (1) anyone can permissionlessly create a `Metadata` object with an arbitrary `name`/`symbol` that collides with an existing asset's display strings (this is a known, accepted design property of `fungible_asset.move`, not an API defect), and (2) each `FungibleStore` correctly points to whichever `Metadata` object its owner chose to associate with it when the store was created. `StateApi::resource` does not conflate these — it never looks past the raw address stored in the `metadata` field, so there's no code path where an attacker-controlled `resource_type` string could cause the API to misattribute one store's metadata pointer to a different, unrelated metadata object's owner. There is no "custody boundary" crossed here: no balance, ownership, freeze, mint/burn, or upgrade authority changes hands based on this API call; it is a read-only reflection of already-committed state.

This is a display/UX phishing concern (users/wallets must verify object addresses rather than trusting display names for asset identity) rather than a custody-control vulnerability in `api/src/state.rs` or the underlying `try_into_resource` conversion path.
