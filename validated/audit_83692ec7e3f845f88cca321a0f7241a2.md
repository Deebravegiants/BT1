### Title
Attacker-supplied route payload executes arbitrary pool code under the caller's authorization tree, enabling wallet-token theft - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
The swap router executes a caller-provided `StrategyPayload` whose `assets` registry can name any contract as a hop pool. The router keeps no allowlist of pools or tokens: `dispatch_hop` invokes whatever `pool` address the payload names (`venues/mod.rs`, `aquarius/pool.rs::invoke_pool_swap`). Because the venue call runs inside the sender's `require_auth` invocation tree (`execute/mod.rs::run`), code in an attacker-deployed "pool" can call `token.transfer(sender, attacker, x)` on any token the sender holds, and the host records that transfer as a child of the sender's signed auth entry. A victim who signs the simulated transaction therefore authorizes theft of wallet funds far beyond the routed amount — the direct analog of uploading an attacker-crafted archive that then executes code.

### Finding Description
- `execute_strategy(sender, total_in, swap_xdr)` decodes the payload, resolves `token_in`, `token_out`, and hop pools purely from `payload.assets` indices, and calls `sender.require_auth()` before the instruction loop ( [1](#0-0) ).
- `dispatch_hop` calls the venue adapter with `hop.pool` taken verbatim from the registry; the Aquarius adapter then does `env.invoke_contract(pool, "swap", ...)` on that arbitrary address ( [2](#0-1) , [3](#0-2) ).
- There is no pool/token allowlist; the only venue restriction is the opcode → adapter mapping. The router's own safety checks (measured `spent == amount_in`, `received > 0`, `total_out >= min_out`) bound the *routed* funds only, not what the invoked contract does inside the caller's auth frame.
- The same exposure reaches lending users: controller strategies (`swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`) forward the caller-supplied `swap` bytes to `router.execute_strategy` while the caller's `require_auth` on the controller entrypoint is the root of the auth tree ( [4](#0-3) ). A rogue pool invoked below that frame can attach a child `transfer` stealing any token in the caller's wallet, exactly as `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates (`RogueHopPool::swap` transfers `WALLET_BALANCE` of an unrelated token from Alice to the attacker, and recording mode shows the theft nested under Alice's `swap_collateral` entry).

### Impact Explanation
Theft of user funds. The stolen amount is the victim's balance of any token the attacker names, unrelated to the swap's `total_in`, `min_out`, or the account's post-swap health checks. Neither the router's measured-delta accounting nor the controller's risk gates bound it; `docs/explanation/threat-model.md` explicitly states the loss "is then the caller's wallet, not the routed amount." A single signed transaction containing a poisoned route drains arbitrary wallet tokens to the attacker.

### Likelihood Explanation
Execution requires the victim to sign a transaction whose simulated auth tree contains the rogue child transfer. Simulation surfaces the malicious subtree rather than hiding it, so an inspecting client can detect it — but the protocol ships no such check, the payload is opaque XDR, and standard wallet signing UX does not decode nested auth children. An attacker controls route construction wherever routes are sourced (compromised/malicious quote path, phishing frontend, or a crafted `swap_xdr` handed to a user), and can offer an honest-looking fair swap so the transaction succeeds and the theft is silent. The repo's own harness PoC confirms both recording-mode attachment and enforcing-mode success once the tree is signed.

### Recommendation
- Maintain a governance-curated allowlist of pool (and token) contracts the router will invoke, rejecting payload-named addresses not on it; or pin pool addresses to a registry keyed by (venue, token pair) rather than free `assets` indices.
- Short of an allowlist, structurally isolate venue calls so third-party code cannot attach children to the sender's auth entry — e.g., require pools to be pulled via the router's invoker-contract auth only, and document/enforce that no user-token `transfer` may appear below the sender's root.
- Client-side mitigation (decode the route and reject any auth tree with children beyond the single input `transfer`) should be enforced in the SDK/quote server, not left as user guidance.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` is a working PoC: a `RogueHopPool` contract whose `swap()` calls `token::Client::transfer(alice, attacker, WALLET_BALANCE)` on an unrelated wallet token is registered and named as the hop pool in a `swap_collateral` route. Under `mock_all_auths` (simulation/recording mode) the call succeeds, the recorded auth tree shows the stolen `transfer` as a child of Alice's `swap_collateral` invocation, and the assertions confirm `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, while the swap itself still delivered a fair `FAIR_OUT_ETH` output — so every router and controller post-check passes while the wallet is drained. The same construction applies to a direct `execute_strategy` call and to any strategy verb that forwards `swap` bytes (`multiply`, `swap_debt`, `repay_debt_with_collateral`).

```rust
pub(crate) fn run(env: Env, sender: Address, total_in: i128, payload: StrategyPayload) -> i128 {
    sender.require_auth();

    if total_in <= 0 {
        panic_with_error!(&env, Error::InvalidAmount);
    }

    let StrategyPayload {
        amounts,
        assets,
        ops,
    } = payload;
    let program = Program::decode(&env, &ops, assets.len(), amounts.len());

    let input_token = assets.get_unchecked(program.token_in);
    let output_token = assets.get_unchecked(program.token_out);
```
