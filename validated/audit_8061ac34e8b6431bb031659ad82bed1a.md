### Title
Fee-on-transfer / deflationary token support absent, causing pool accounting desync — (File: `program/src/processor.rs`)

### Summary
Raydium's `Deposit`, `Withdraw`, and swap instructions compute vault-balance deltas, LP mint amounts, and swap outputs using the *nominal* transfer amount supplied in instruction data (or derived arithmetically from it), and never re-read the destination vault's post-CPI token balance to confirm the actual amount received. If either the coin or pc mint is a fee-on-transfer/deflationary SPL token, the vault will receive less than the nominal amount used in the AMM's internal accounting, permanently desynchronizing the on-chain pool state from the true vault balances.

### Finding Description
In `process_deposit`, the deducted amounts (`deduct_coin_amount`, `deduct_pc_amount`) are computed from the invariant math and then transferred via `Invokers::token_transfer` [1](#0-0) . Immediately after, `mint_lp_amount` (already computed before the transfer, from `total_coin_without_take_pnl`/`total_pc_without_take_pnl` snapshots) is minted to the depositor, and `amm.lp_amount` plus `target_orders.calc_pnl_x/y` are updated using the nominal `deduct_coin_amount`/`deduct_pc_amount`, not the vault's actual post-transfer balance [2](#0-1) .

`Invokers::token_transfer` and `token_transfer_with_authority` in `program/src/invokers.rs` simply issue the SPL `Transfer` instruction with the caller-specified amount and return `Ok(())` on success; they do not inspect or return the actual balance change of the destination account [3](#0-2) .

The same pattern repeats in every swap path (`process_swap_base_in`, `process_swap_base_out`, and their v2 variants): `swap_amount_out`/`swap.amount_out` is computed from the constant-product invariant using the *vaults' pre-swap balances* and the *nominal* `amount_in`, then the input transfer and output transfer are both issued for the nominal, pre-computed amounts, with no verification that the coin/pc vault actually received the full `amount_in` [4](#0-3) [5](#0-4) .

If the coin or pc mint charges a transfer fee/burn (a "deflationary" token), the vault ends up holding strictly less than the amount the program's accounting believes it holds. On deposit, this causes LP tokens to be minted against liquidity that was never actually deposited, i.e., unbacked LP minting and insolvent pool accounting. On swap, since the output amount is computed from `swap.amount_in` rather than the vault's actual balance increase, every swap against a deflationary coin/pc mint pays out more than the true constant-product invariant allows, gradually draining the counter-asset vault below what LP holders are owed.

### Impact Explanation
This directly causes insolvent pool accounting and enables theft of pooled liquidity: repeated deposits with a deflationary token mint unbacked LP against phantom liquidity, and repeated swaps against a deflationary input mint extract more of the counter-asset than the invariant permits, draining value from existing LPs. This satisfies the "unbacked LP minting / insolvent pool accounting" impact bar.

### Likelihood Explanation
Any AMM pool created with a fee-on-transfer/rebasing/deflationary SPL mint as `coin_mint` or `pc_mint` (via `Initialize2`) is affected. Since pool creation and vault mint selection are open/permissionless in this class of AMM, an attacker (or an unaware pool creator) can trivially create or use such a pool, then reach `Deposit`/`Withdraw`/`SwapBaseIn`/`SwapBaseOut` with attacker-chosen token accounts in a single transaction to realize the drain, with no privileged signer required.

### Recommendation
After each SPL token transfer into a vault, read back the destination token account's actual balance (or its delta) and use that value — not the nominal instruction amount — for all downstream accounting: `mint_lp_amount` calculation, `target_orders.calc_pnl_x/y` updates, and swap-output computation. Alternatively, explicitly reject mints with a non-zero `TransferFeeConfig` extension (or any transfer-fee/deflationary behavior) at `Initialize2` / deposit time, and document unambiguously that fee-on-transfer tokens are unsupported.

### Proof of Concept
1. Create a pool via `Initialize2` where the `pc_mint` is an SPL token with a transfer fee (e.g., 5% burned on every transfer).
2. Call `Deposit` with `max_pc_amount = 1000`. The program computes `deduct_pc_amount = 1000` and transfers it via `Invokers::token_transfer` (`program/src/processor.rs:1334-1340`); only 950 actually lands in `amm_pc_vault` due to the fee.
3. `mint_lp_amount` was computed from the invariant assuming a full 1000 pc was deposited, so LP tokens are minted representing 1000 pc-worth of value while the vault only holds 950 — unbacked LP.
4. Repeating deposits/withdrawals amplifies the gap between `amm.lp_amount`'s implied backing and the vaults' real balances, and any subsequent swap computed off the (inflated) tracked totals pays out more of the coin side than the real pc reserve justifies, draining the pool.

    pub fn token_transfer<'a>(

        source: AccountInfo<'a>,
        destination: AccountInfo<'a>,
        owner: AccountInfo<'a>,
        deposit_amount: u64,
