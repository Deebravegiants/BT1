### Title
Donated LT permanently stranded in a graduated curve `Pair` with no recovery path - ([File: packages/contracts/src/Pair.sol], [File: packages/contracts/src/Bonding.sol])

### Summary
Any address can send the reserve LT directly to a token's curve `Pair` via a plain ERC20 `transfer`. Because `Pair` has no `sync`/`skim` mechanism, this donation never updates the pair's *stored* `assetReserve`, so it is excluded from `ltFromPair` at graduation and is left behind when the curve drains. Once the token graduates, `Pair.transferAsset` — the only function that can move the reserve asset out of the pair — is gated `onlyRouter`, and `Bonding` never calls `Router.graduate` (or any other `transferAsset` path) again for that pair after `Lifecycle.Graduated`. The donated LT is therefore permanently locked in the `Pair` contract, forfeited/unattributed value with no sweep, exactly the same class of bug as the referenced report where reward-period value that fell outside the tracked accounting window was never rolled over and remained stuck with "no usage."

### Finding Description
`Pair` tracks reserves only in an internal `Pool` struct (`_pool.tokenReserve`, `_pool.assetReserve`), updated exclusively by `mint` and `swap`: [1](#0-0) 

There is no `sync()`/`skim()` equivalent, so a raw ERC20 `transfer` of the LT (`assetToken`) straight to the `Pair` address increases `IERC20(assetToken).balanceOf(pair)` (readable via `assetBalance()`) without ever touching `_pool.assetReserve`.

At graduation, `_prepareGraduationLiquidity` computes the amount to drain using the *stored* reserve, not the live balance: [2](#0-1) 

This is a deliberate design choice — documented directly in the codebase — specifically to make the graduation math donation-resistant on the USD-threshold side. But the same design leaves the donated LT physically sitting in the `Pair` after the drain, and the docs explicitly acknowledge it is retrievable *only* via `Pair.transferAsset`, which is `onlyRouter`: [3](#0-2) [4](#0-3) 

`Router.graduate` — the only caller that ever triggers `Pair.transferAsset` for the reserve asset — is invoked exactly once per token, during `_prepareGraduationLiquidity`/`_graduate`, and only for the computed `ltFromPair` amount. Once `info.lifecycle` flips to `Graduating`→`Graduated` in `finalizeGraduation`, nothing in `Bonding` ever calls back into that `Pair` again: [5](#0-4) 

The project's own `AGENTS.md` states the trust assumption plainly — the donated LT "stays in the curve pair under the trust assumption that BONDING_ROLE is only ever held by Bonding and Bonding won't call Router.graduate again post-graduation": [6](#0-5) 

Since `Pair` exposes no other privileged or public withdrawal function, and `Router` is immutable/non-upgradeable per `Pair.router` and `Factory.setRouter`'s one-shot lock, there is no code path — owner, keeper, or otherwise — that can move this stranded LT out of the `Pair` once the token has graduated. This mirrors the referenced report's root cause: value that arrives during a window the accounting model doesn't track (there, a "no-deposit" interval before staking began; here, a donation the stored-reserve model deliberately ignores) is silently excluded from the live accounting and never swept back into circulation, so it sits permanently unused.

### Impact Explanation
Any LT donated to a `Pair` before graduation is permanently frozen once that token graduates — it is neither returned to the donor, credited to `FeeVault`, added to the LP, nor recoverable by the protocol owner. This is a permanent freezing of funds within the definition of accepted impacts (permanent freezing of funds, here LT value that could otherwise be pooled/creator-attributed). It also represents forfeited value never attributable to any party, the same characterization the original judge applied to the analogous staking-rewards report ("protocol leaked value ... isn't attributed to anyone").

### Likelihood Explanation
Reachable by any unrelated wallet with a single unprivileged ERC20 `transfer` of the paired LT to a known `Pair` address — no permissions, no special timing beyond "before that token's `finalizeGraduation` runs," and no revert or defensive check blocks it. Given `Bonding`/`Zap`'s documented tolerance for direct-transfer donations to the pair (explicitly called out as an in-scope interaction), this can happen accidentally (mis-sent transfer) or deliberately (a griefer permanently burying reserve LT that the pair, and by extension the protocol/creator/LPs, can never use), across every graduated token.

### Recommendation
Add a permissioned, one-time-per-pair sweep (e.g. `Router`/`Bonding`-gated `Pair.skimAsset(recipient)` callable only after `Lifecycle.Graduated`, or fold any residual `assetBalance() - assetReserve` into `finalizeGraduation`'s LP-seeding/fee-forwarding step) so that donated LT sitting in a graduated pair is either burned, forwarded to `FeeVault`, or returned to the LP instead of being permanently stranded.

### Proof of Concept
1. `Zap.createToken` launches `tokenAddress` with pair `pairAddr` paired to LT `lt`.
2. Any wallet (not the creator, not a router) calls `lt.transfer(pairAddr, X)` directly — a plain ERC20 transfer that `Pair` never rejects, since `Pair` has no `sync`/`skim` guard.
3. The token curve trades normally and eventually graduates: `Bonding._enterGraduating` → `_prepareGraduationLiquidity` computes `ltFromPair = storedAssetReserve - virtualLtReserve`, which does **not** include `X` (stored reserve was never updated by the raw transfer). `Router.graduate` drains only `ltFromPair`.
4. `finalizeGraduation` runs, `info.lifecycle` becomes `Graduated`, `pendingGraduation[tokenAddress]` is deleted.
5. `lt.balanceOf(pairAddr)` still holds `X`. No function in `Bonding`, `Router`, `Zap`, `FeeVault`, or `Pair` itself can ever move it out — `Pair.transferAsset` is `onlyRouter`, and `Router.graduate`/any other `transferAsset` call site is never invoked again for this pair — so `X` is permanently frozen.

    function mint(
        uint256 tokenReserve,
        uint256 assetReserve
    ) external onlyRouter returns (bool) {
        if (_pool.k != 0) revert AlreadyMinted();
        _pool = Pool({tokenReserve: tokenReserve, assetReserve: assetReserve, k: tokenReserve * assetReserve});
        emit Mint(tokenReserve, assetReserve);
        return true;
    }

    function swap(
        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }

        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }
