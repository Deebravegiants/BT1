### Title
Webhook Shop/Topic/ID Identity Fields Not Covered by HMAC Signature Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts `shop`, `topic`, and `webhook_id` values that are read from unauthenticated HTTP headers and are never included in the signed material. An attacker who obtains a single genuine `(body, hmac)` pair can replay it with arbitrary `shopify-shop-domain`/`shopify-topic`/`shopify-webhook-id` header values and the signature check will still pass, producing a `WebhookMetadata` object whose identity fields are fully attacker-controlled.

### Finding Description
`Webhooks::Request#to_signable_string` (the method used by `Utils::HmacValidator`) returns only the raw body: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read directly from headers that are not part of the signed payload at all: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC of the body only, then immediately builds the tenant identity metadata from these unauthenticated header values and dispatches it to the app's handler: [4](#0-3) 

The identity binding that should hold is:
`bytes authenticated by HMAC == bytes used to determine "shop"/"topic"/"webhook_id"`

but the code actually implements:
`bytes authenticated by HMAC (body only) ⊊ bytes used to determine shop identity (body ∪ headers)`

Because `shop`, `topic`, and `webhook_id` sit outside the HMAC-covered region, they can be freely modified on a replayed/relayed request without invalidating `Utils::HmacValidator.validate`, which only recomputes and compares the HMAC of `raw_body`: [5](#0-4) 

### Impact Explanation
An attacker who has observed one legitimate webhook delivery (for any shop/topic) can craft a forged request with the same body and HMAC but a different `shopify-shop-domain` header, causing `Registry.process` to accept it as valid and hand the handler a `WebhookMetadata` claiming a different shop than the one that actually produced the body/signature. Depending on how the host application keys data off `WebhookMetadata#shop` (e.g., to select which merchant's session/record to update), this results in cross-tenant data corruption/confusion — data intended for shop A being processed and stored under shop B's identity, or vice versa. This maps to the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to have captured one valid `(raw_body, hmac)` pair delivered by Shopify (e.g., via a network position between Shopify and the app's endpoint, application logs, or a previously-processed webhook they can resend). No knowledge of `api_secret_key` or any access token is required — the attacker reuses a signature they already possess rather than forging one. This is a plausible, low-complexity replay once a single sample has been captured, since the gem places no additional binding (nonce, timestamp freshness, or header coverage) between the signed bytes and the trust decision made from headers.

### Recommendation
Include the shop domain, topic, and webhook ID in the HMAC-verified material (or independently verify `shop`/`topic` against the shop registered for that webhook subscription, and enforce delivery timestamp/idempotency checks using `webhook_id` to reject replays). At minimum, `Utils::HmacValidator` should bind the `shop-domain` header into `to_signable_string` so that changing it invalidates the signature.

### Proof of Concept
1. Attacker captures a legitimate webhook request sent by Shopify to the app for `shop-a.myshopify.com`: raw body `B` and header `shopify-hmac-sha256: H` (valid HMAC of `B`).
2. Attacker replays the same body `B` and signature `H` to the app's webhook endpoint, but sets `shopify-shop-domain: shop-b.myshopify.com` (and optionally a different `shopify-webhook-id`).
3. `Utils::HmacValidator.validate` recomputes HMAC over `raw_body` (`B`) only — unaffected by the header change — and returns `true`: [6](#0-5) 
4. `Registry.process` proceeds and invokes the handler with `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: parsed_body_of_B, ...)`, even though the body/signature actually originated from `shop-a`: [7](#0-6)
