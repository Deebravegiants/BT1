### Title
Unsynchronized concurrent `addSeed()`/`removeSeed()` calls cause lost-update race on `extraSeeds` storage and `seedMetadataAtom`, resurrecting removed seeds - ([File: features/wallet/module/wallet.js])

### Summary
`Wallet.addSeed()` and `Wallet.removeManySeeds()` (aliased by `removeSeed()`) each perform an unguarded read-modify-write on the `extraSeeds` array in `walletStorage` and on `seedMetadataAtom`, with no mutual-exclusion lock between the two operations (unlike `create`/`import`, which are wrapped with `makeConcurrent({ concurrency: 1 })`). When `removeSeed(oldId)` and `addSeed(newMnemonic)` are invoked concurrently, their get→modify→set sequences interleave, and whichever write lands last overwrites the other's result — allowing a just-removed seed's data to be silently rewritten back into `extraSeeds` storage after `removeSeed()` has already resolved, while `seedMetadataAtom` no longer has a corresponding entry for it.

### Finding Description
`addSeed` reads the current extra seeds, appends the new one, and writes the whole array back: [1](#0-0) 

`removeManySeeds` (used by `removeSeed`) independently reads the current extra seeds, filters out the removed one(s), and writes the filtered array back, plus asynchronously deletes matching metadata **without awaiting it**: [2](#0-1) 

Both `#getExtraSeeds`/`#setExtraSeeds` sequences span multiple `await` points (including an async `keychain.exportKey` call inside `#getExtraSeedsPassphrase`), and neither `addSeed` nor `removeManySeeds`/`removeSeed` is wrapped in `makeConcurrent`, unlike `create`/`import`: [3](#0-2) 

Race sequence for `Promise.all([wallet.removeSeed(oldId), wallet.addSeed(newMnemonic)])`:
1. `addSeed` reads `extraSeeds = [seedA, seedB(oldId)]` (snapshot S1).
2. `removeSeed`→`removeManySeeds` reads the same snapshot S1 before `addSeed` writes.
3. `removeManySeeds` computes `remainingSeeds = [seedA]` and writes it via `#setExtraSeeds`, then fires (without `await`, line 191) `#removeManySeedsMetadata([oldId])`, which itself does a separate `get()`→`delete`→`set()` on `seedMetadataAtom`.
4. `addSeed` pushes the new seed onto its stale snapshot S1 (`[seedA, seedB(oldId), newSeed]`) and calls `#setExtraSeeds`, **overwriting** step 3's write — `seedB` (the just-"removed" seed) is restored into the `extraSeeds` storage array even though `removeSeed(oldId)` already resolved to the caller.
5. Depending on ordering of the unawaited metadata deletion vs. `addSeed`'s functional `#seedMetadataAtom.set((previous) => ...)`, `seedMetadataAtom` can end up with no entry for `oldId` while the raw seed data for `oldId` still lives in `extraSeeds` storage.

On the next `unlock()`, the wallet unconditionally re-adds every seed found in `extraSeeds` storage to the keychain: [4](#0-3) 

so the seed the user explicitly removed is silently reinstated into the active keychain, without any corresponding `seedMetadataAtom` entry — breaking the 1:1 invariant between `extraSeeds` and `seedMetadataAtom` and resurrecting private key material the user intended to delete.

No lock/auth guard exists at the `Wallet` module level to prevent this: `#assertWalletIsUnlocked` only checks lock state, not concurrency, and the underlying storage's `concurrencyLock` (in `libraries/browser-extension-adapters/unsafe-storage/storage.js` and similar adapters) only serializes individual `get`/`set` calls, not the whole read-modify-write sequence spanning two separate wallet-level calls. [5](#0-4) 

### Impact Explanation
This is a data-integrity/secret-persistence bug in core seed management: a seed the user explicitly removed via `removeSeed()` can be silently resurrected into the extra-seeds storage and reloaded into the keychain on the next `unlock()`, with no metadata trace tying it to a label/date, and no way for the UI (which relies on `seedMetadataAtom`) to reflect its existence. This is a privilege-persistence issue — a "deleted" secret continues to be usable for signing/derivation after the user believed it was purged — and corrupts the invariant that `extraSeeds` entries and `seedMetadataAtom` keys are 1:1.

### Likelihood Explanation
Requires two `Wallet` mutating calls (`addSeed` and `removeSeed`/`removeManySeeds`) to be in flight concurrently against the same wallet instance/storage — e.g., triggered by rapid/duplicate UI actions, automated seed-management flows, or any code path that calls these without external serialization. Since neither method is protected by `makeConcurrent` (unlike `create`/`import`), any concurrent invocation of these two methods is sufficient; no special privilege or malicious input is needed, only ordinary application-level concurrency.

### Recommendation
Wrap `addSeed`, `removeManySeeds` (and any other extra-seed/metadata mutators) in a single `makeConcurrent({ concurrency: 1 })` gate (or a shared mutex) exactly as already done for `create`/`import`, so that the extra-seeds get-modify-set cycle and the corresponding `seedMetadataAtom` updates are executed atomically with respect to each other. Additionally, add the missing `await` on `this.#removeManySeedsMetadata(seedIds)` in `removeManySeeds` (line 191) so metadata deletion is guaranteed to complete before the method resolves.

### Proof of Concept
Integration test in `features/wallet/module/__tests__/index.test.js` style:
1. `await wallet.create(); await wallet.unlock()`.
2. `const oldId = await wallet.addSeed({ mnemonic: otherMnemonic })`.
3. Run `await Promise.all([wallet.removeSeed(oldId), wallet.addSeed({ mnemonic: thirdMnemonic })])`.
4. Read `extraSeeds = await seedStorage.namespace('wallet').get('extraSeeds')` and `metadata = await wallet.getSeedMetadata()`.
5. Assert invariant: every seed in `extraSeeds` (by `getSeedId(seed.seed)`) has a corresponding key in `metadata`, and `oldId` is absent from both `extraSeeds` and `metadata`.
6. Expected (buggy) result under race: `extraSeeds` still contains the seed for `oldId` (or `metadata` is missing an entry for the newly added seed), demonstrating the 1:1 invariant violation; repeat the interleaving across many iterations/orderings (e.g., using a deferred-promise harness to force specific await orderings) to make the race deterministic for the PoC.

    const metadata = await this.#seedMetadataAtom.get()
    seedIds.forEach((seedId) => delete metadata[seedId])
    await this.#seedMetadataAtom.set(metadata)
  }

  removeManySeeds = async (seedIds) => {
    this.#assertMultiSeedSupport()
    await this.#assertWalletIsUnlocked()

    const primarySeedId = await this.#primarySeedIdAtom.get()
    if (seedIds.includes(primarySeedId)) {
      throw new Error('Cannot remove primary seed')
    }

    const extraSeeds = await this.#getExtraSeeds()
    const extraSeedsIds = new Map(
      await Promise.all(extraSeeds.map(async (seed) => [seed, await getSeedId(seed.seed)]))
    )

    const remainingSeeds = extraSeeds.filter((seed) => !seedIds.includes(extraSeedsIds.get(seed)))
    const seedsToRemove = extraSeeds.filter((seed) => seedIds.includes(extraSeedsIds.get(seed)))

    await this.#setExtraSeeds(remainingSeeds)
    this.#removeManySeedsMetadata(seedIds)
    await this.#keychain.removeSeeds(seedsToRemove.map((seed) => seed.seed))
  }

  removeSeed = (seedId) => {

      this.#primarySeedIdAtom.set(primarySeedId)

      return { primarySeedId }

  }
