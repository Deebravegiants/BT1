### Title
Reentrancy in Tron `IntentGatewayV2.withdraw()` allows draining escrowed funds via external call before state update - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed tokens to a beneficiary via an external call (`.call{value: amount}` for native tokens or a raw low-level `token.call(...IERC20.transfer...)` for ERC-20s) *before* decrementing the internal escrow accounting (`_orders[body.commitment][token] -= amount`), and the contract has no reentrancy guard anywhere in the file. This violates checks-effects-interactions and allows a malicious beneficiary/token to re-enter `withdraw()` (or the entry points that call it: `onGetResponse`, and `RedeemEscrow`/`RefundEscrow` handling on `onAccept`) while the escrow balance still reflects its pre-transfer value, and drain more than what was actually escrowed.

### Finding Description
`withdraw()` in the Tron contract performs, per token in the withdrawal: [1](#0-0) 
```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;
        ...
```
The state mutation `_orders[body.commitment][token] -= amount` happens **after** the external `.call`. The guard `if (_orders[body.commitment][token] == 0) revert UnknownOrder()` only checks that the balance is non-zero, not that it covers `amount`, and it is stale by the time of re-entry because it isn't decremented until after the transfer completes. This is exactly the "use of state that should already be invalidated before it is actually invalidated" bug class the CVE-2024-4948 UAF hint maps to at the logic level: the escrow balance is read/used to authorize a payout while it is still in its pre-transfer ("not yet freed/updated") form, letting a reentrant call reuse it.

This is reachable from two unprivileged/permissionless entry points that ultimately call `withdraw`:
- `onGetResponse` (called by the host after a Hyperbridge GET response, `onlyHost`, but the value transferred to `beneficiary` is attacker-controlled and can be a malicious contract/receiver): [2](#0-1) 
- `onAccept` (handles `RedeemEscrow`/`RefundEscrow` cross-chain messages) similarly ends in `withdraw`.

Critically, none of the public/external functions in this file (`placeOrder`, `cancelOrder`, `withdraw`-reaching handlers) carry a `nonReentrant` modifier — confirmed by an empty search for `nonReentrant|ReentrancyGuard` across `evm/tron/**`. This contrasts with the fixed, non-Tron `IntentGatewayV2`/`IntentsBase.sol` withdrawal path, which already applies checks-effects-interactions correctly (decrements escrow *before* transferring) and is guarded by `nonReentrant` on `cancelOrder`, per the reentrancy regression tests in `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`: [3](#0-2) 
```solidity
function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    if (finalize) _filled[body.commitment] = beneficiary;
    ...
    _orders[body.commitment][token] = escrowed - amount;
    if (token == address(0)) {
        _sendValue(beneficiary, amount);
    } else {
        IERC20(token).safeTransfer(beneficiary, amount);
    }
```
The main EVM contract updates `_orders` before the external transfer — the Tron contract does the opposite, reintroducing exactly the class of bug the main contract's tests (`IntrinsicIntentsReentrancyTest.sol`) were written to prevent.

### Impact Explanation
A malicious beneficiary contract (e.g., set as `order.user`/beneficiary on a same-chain order, or the destination-chain filler triggering a cross-chain refund/redeem) can re-enter `withdraw` from the native-token `.call{value: amount}("")` fallback (or via a malicious/hooked ERC-20 token if one is ever used as an input) before `_orders[body.commitment][token]` is decremented. Each reentrant call re-passes the `_orders[...][token] == 0` check (it is still non-zero) and triggers another payout of `amount`, permanently draining escrowed funds beyond what was legitimately owed — a concrete theft of user/solver escrow funds, i.e. "concrete theft ... of funds" as required by the validation rubric.

### Likelihood Explanation
Likelihood is High for native-token orders: any user or attacker can place/fill/cancel an order (all permissionless), designate a malicious contract as beneficiary, and trigger `withdraw` through the ordinary `onGetResponse`/`onAccept` message-delivery paths that any relayer will eventually submit. No special privileges, governance, or malicious admin/node assumptions are required — a single relayed message (a "relayed proof"/"relayer fee and reward accounting" path explicitly in scope) is sufficient to trigger the vulnerable code path.

### Recommendation
Apply checks-effects-interactions in `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`: decrement `_orders[body.commitment][token]` (and the `TRANSACTION_FEES` slot) **before** performing the external `.call`/token transfer, mirroring the fixed pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`. Additionally, add a `nonReentrant` guard (OpenZeppelin `ReentrancyGuard`) to `withdraw`, `onGetResponse`, `onAccept`, `cancelOrder`, and `fillOrder` in the Tron contract, consistent with the non-Tron `IntentGatewayV2` which already uses `nonReentrant` on `cancelOrder`/`fillOrder`.

### Proof of Concept
1. Attacker calls `placeOrder` with a same-chain order where `order.output.assets` includes a native-token output and `order.output.beneficiary` is a malicious contract `Attacker`.
2. `Attacker` fills/cancels the order such that `withdraw(body, ...)` is eventually invoked with `body.tokens[0].token == address(0)` and `amount` equal to the full escrowed balance.
3. Inside `withdraw`, `beneficiary.call{value: amount}("")` invokes `Attacker`'s `receive()`/`fallback()`, which re-enters the same withdrawal path (e.g., by re-triggering `onGetResponse`/`onAccept` if the message can be replayed before `_filled`/order state fully blocks it, or via a nested call into `withdraw` if additional tokens are present in `body.tokens` so the loop hasn't yet decremented all balances).
4. Because `_orders[body.commitment][token] -= amount` has not yet executed for this token, the check `_orders[...][token] == 0` still passes on reentry, and a second `amount` payout is issued from the same escrow, cumulatively transferring more value than was ever deposited.
