### Title
Permanent DoS of vested claims via griefing pre-seeded `VestedBalanceExists` on `dest` account - (File: polkadot/runtime/common/src/claims/mod.rs)

### Summary
For claims minted with an attached vesting schedule, `process_claim` refuses to complete if the destination account already has *any* active vesting schedule, returning `Error::VestedBalanceExists`. Because `Claims`/`Vesting`/`Signing` storage for that claim is never mutated on this failure path, an unprivileged attacker who knows the target `dest` `AccountId` can pre-seed it with an unrelated vesting schedule via `pallet_vesting::vested_transfer`, permanently blocking the legitimate claimant from ever completing that vested claim.

### Finding Description
In `process_claim`, the vesting-conflict guard is checked before any state mutation:

```rust
let vesting = Vesting::<T>::get(&who);
if vesting.is_some() && T::VestingSchedule::vesting_balance(&dest).is_some() {
    return Err(Error::<T>::VestedBalanceExists.into());
}
``` [1](#0-0) 

This check exists because later the code calls `T::VestingSchedule::add_vesting_schedule(&dest, ...)` and expects it to succeed (it is guarded with an `.expect(...)`, since `pallet-vesting` limits the number of concurrent schedules per account and refuses to add another if the destination is already vesting). To avoid that panic, `process_claim` bails out early with `VestedBalanceExists` whenever the claim carries a vesting component and `dest` is already vesting for any unrelated reason.

Crucially:
- The trigger condition only depends on `T::VestingSchedule::vesting_balance(&dest).is_some()`, which is `true` for *any* active vesting schedule on `dest`, regardless of its origin or amount.
- `dest` is a plain, freely-choosable `AccountId` supplied by the caller of `claim`/`claim_attest`, and is known ahead of time to anyone who can observe/predict the claimant's intended destination (e.g. leaked/predictable front-end address, or simply the claimant announcing their intended DOT destination).
- `Vesting::<T>::get(&who)` (the claim's own vesting component) is set at `mint_claim` time and is out of scope, but represents a legitimate, common real-world case (SAFT-holder claims minted with vesting).
- Because `Claims`, `Vesting`, and `Signing` storage entries for `who` are removed only on the success path at the end of `process_claim`, a failed claim due to `VestedBalanceExists` leaves the claim state completely intact and re-triggerable — but every future `claim` attempt with the same `dest` will hit the identical guard as long as `dest` keeps an active vesting schedule.
- There is no user-facing mechanism to clear or bypass another account's vesting schedule, nor to change the claim's target `dest`; the only path to unblock the claim is the privileged, governance-only `move_claim` extrinsic (root/`MoveClaimOrigin`), which is not user-triggered and thus out of scope for a griefing-DoS fix from the victim's perspective.

An attacker (any unprivileged signed account with sufficient balance to satisfy `pallet_vesting`'s `MinVestedTransfer`/existential-deposit constraints) simply calls `Vesting::vested_transfer(dest, small_but_valid_schedule)` targeting the claimant's known `dest` before the claimant submits `claims::claim(dest, sig)`. As long as the attacker chooses a vesting schedule whose locked balance stays non-zero for a long duration (e.g. far-future `starting_block`/long `per_block`), `vesting_balance(&dest)` continues to return `Some(_)` indefinitely, keeping the claim permanently blocked.

### Impact Explanation
Concrete scoped impact: permanent freeze of the claimable DOT amount recorded in `Claims`/`Vesting`/`Total` for the affected Ethereum-address claim. The legitimate claimant can never successfully call `claim`/`claim_attest` for that `dest` while the attacker-seeded vesting schedule remains active (which the attacker fully controls the duration of), and the funds sit unclaimable in the claims pallet's pot indefinitely, with no self-service recovery available to the victim.

### Likelihood Explanation
- Requires the target claim to have been minted with a vesting component (a real, expected configuration for SAFT/vested claims, not attacker-controlled but a legitimate precondition already present in the system design).
- Requires the attacker to know or predict the claimant's `dest` `AccountId` before the claimant submits their claim — plausible when claim destination addresses are announced/shared in advance (e.g. through claim front-ends, exchanges, or public claim requests), matching the stated precondition.
- The attacker's cost is only the `pallet_vesting` `MinVestedTransfer` amount (recoverable/lockable to self indirectly, e.g. transferring to their own alt account is not applicable here since it must go to the victim's `dest`, so the funds are genuinely spent/locked into `dest`, but the attacker can choose a minimal qualifying amount).
- Fully repeatable and requires no race condition beyond simple front-running (mempool ordering), which is realistic on a public network.

### Recommendation
Do not permanently deny the claim when `dest` already has an unrelated vesting schedule. Instead, either: (1) allow `process_claim` to top up/merge into the destination's existing vesting schedules if `pallet-vesting`'s schedule capacity allows, falling back to a hard error only when the schedule limit is truly exhausted, or (2) expose a user-triggered (non-privileged) way for the *claimant* to specify or migrate their own vesting destination/claim independent of pre-existing third-party vesting state, so that an attacker cannot unilaterally lock out a specific `dest` by seeding a long-lived low-value vesting schedule.

### Proof of Concept
Rust integration test outline (using `pallet_vesting` + `pallet_claims` test runtimes wired together, mirroring `polkadot/runtime/common/src/claims/tests.rs`):
1. `mint_claim(root, eth_address, amount, Some((total_vesting, per_block, starting_block)))` — creates a vested claim for `eth_address` intended for `dest = victim_account`.
2. Before the victim claims, from an unrelated `attacker_account` call `pallet_vesting::Pallet::<Test>::vested_transfer(RuntimeOrigin::signed(attacker_account), victim_account, VestingInfo::new(min_vested_amount, per_block_long_duration, far_future_or_current_start))`.
3. Assert `pallet_vesting::Pallet::<Test>::vesting_balance(&victim_account).is_some()`.
4. Victim calls `Claims::claim(RuntimeOrigin::none(), victim_account, sig_for(eth_address))`.
5. Assert the call returns `Err(Error::<Test>::VestedBalanceExists)`.
6. Assert `Claims::<Test>::get(eth_address)`, `Vesting::<Test>::get(eth_address)` are still `Some(_)` (state not cleared).
7. Repeat step 4 in a later block (still within the attacker's vesting duration) and assert it fails identically, demonstrating the freeze persists indefinitely under attacker control with no self-service recovery for `victim_account`.
