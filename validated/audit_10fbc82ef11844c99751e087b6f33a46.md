### Title
Webhook `shop` field is not covered by the HMAC signature, enabling cross-tenant webhook forgery/replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which HMACs only the raw request body [1](#0-0) . The `shop` value read from the `shopify-shop-domain`/`x-shopify-shop-domain` header is never included in the signed content [2](#0-1) , yet it is passed straight into `WebhookMetadata.shop` and handed to the app's handler as the authoritative tenant identifier [3](#0-2) .

### Finding Description
`HmacValidator.validate` computes `HMAC(api_secret_key, to_signable_string)` and compares it to the `hmac` header [4](#0-3) . For webhook requests, `to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop` accessor is derived purely from an HTTP header that is not part of that signable string [2](#0-1) .

Because the app's `api_secret_key` is shared across every shop that installs the app, `HmacValidator.validate` only proves "this body+hmac pair was produced by someone holding this app's secret" — it does not prove "this body came from shop X." An attacker who is an unprivileged user of the app on their own store (e.g., shop A) can capture a legitimately-signed webhook body+HMAC from Shopify, then replay that exact `raw_body`/`hmac` pair to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with an arbitrary victim shop domain (shop B). `Registry.process` will validate successfully (the body/HMAC pair is genuinely valid), and the handler will receive `WebhookMetadata.new(shop: "shop-B...")` [3](#0-2) , i.e. `shop` equality is broken: `authenticated_hmac_owner != claimed_shop_used_by_handler`.

The gem's own documentation instructs developers to treat `data.shop` as the trusted tenant identifier for routing/persisting webhook data (`shop_domain: data.shop`) [5](#0-4) , so this is not merely a host-application misuse — it is the gem's documented, intended usage pattern that this unbound field directly enables to be abused for cross-tenant data injection/impersonation.

### Impact Explanation
This meets the Critical bar of cross-tenant access: an attacker who has one legitimate installation of the app can forge webhook events (with attacker-fully-controlled `body`/`topic`/`webhook_id`, replayed with a valid HMAC) that are attributed to any other merchant shop of the attacker's choosing, since `shop` is never cryptographically bound to the payload. Depending on the handler's logic (documented pattern shows shop-keyed job enqueueing), this can lead to writing/mutating data under another tenant's identity, cross-tenant confusion, or triggering shop-scoped side effects (e.g., mandatory `shop/redact`, `customers/redact` handling) for a shop the attacker doesn't control.

### Likelihood Explanation
Webhook endpoints are public HTTP endpoints reachable by any internet user; the only gate is `HmacValidator.validate`, which this analog does not need to break — it only requires a validly-signed body from the attacker's own (legitimately installed) shop, which the attacker can trivially obtain by installing the app itself and observing its own webhook traffic. No access token, `client_secret`, or privileged account is required, and the header (`shop-domain`) is entirely attacker-controlled per HTTP request.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value verified by the HMAC, or otherwise never trust the `shopify-shop-domain` header as a tenant key unless it is independently corroborated (e.g., against a shop known to have an active, registered subscription for that specific `webhook_id`/topic combination). At minimum, update `Request#to_signable_string` or `Registry.process` to cross-check the header-derived `shop` against server-side state (e.g., confirm the `webhook_id` was actually registered/expected for that shop) before handing it to the handler, and update documentation to warn that `data.shop` is not itself HMAC-verified.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook (e.g. `orders/create`) and capture the raw POST: `raw_body` and header `shopify-hmac-sha256`.
2. Replay the exact same HTTP request to the app's webhook endpoint, but change the `shopify-shop-domain` (or `x-shopify-shop-domain`) header value to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `raw_body` [1](#0-0)  — validation succeeds unchanged.
4. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [6](#0-5) , causing the app to process attacker-controlled webhook content as if it originated from the victim shop.
