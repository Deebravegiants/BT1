### Title
Unguarded `refund_assets` transfers in `flash_position` allow same-account reentry that resurrects withdrawn supply shares — ([File: contracts/controller/src/strategies/flash_position.rs])

### Summary
The kernel bug is a data race on a shared accounting counter: two threads interleave charge/uncharge/reclaim, each computing `reclaimable` from a stale snapshot, so the final reclaim drives `sk->sk_forward_alloc` negative. The structural analog in XOXNO Lending is `process_flash_position`: the flash guard is lifted before `refund_listed_assets` runs (line 148, deliberately — see the comment at line 240), while the mutated `account` (new minted debt + deposited collateral) is still only in memory and is persisted later by `strategy_finalize` (line 153). A token with a transfer hook listed as a `refund_asset` can therefore reenter the controller during the refund transfer and run a full monetary operation (e.g. `withdraw`) against the stale on-ledger account — the same "interleaved mutation of a counter from a stale snapshot" shape.

### Finding Description
`with_flash_guard` wraps only `mint_and_forward` + `invoke_receiver` (lines 121–143). After it closes, the code:

1. `process_deposit` merges callback collateral into the in-memory `account` (line 146)
2. `refund_listed_assets` transfers positive deltas of caller-listed refund tokens back to `caller` (line 148)
3. `strategy_finalize` persists the in-memory account (line 153)

`validate_refund_assets` only requires the asset to be a listed asset in the debt hub and the account's spoke, disjoint from collateral declarations (lines 232–255). The test at `tests/test-harness/tests/strategy/flash_position_adversarial.rs:170-188` confirms refund `balance`/`transfer` calls run *after* the guard closes. The pool README states the trust assumption explicitly: flash-guard coverage is enforced by `with_flash_guard`, and `supply`/`withdraw`/`repay`/`recapitalize` trust that "tokens arrived before any cash-crediting call" plus the guard — none of them recheck that an outer flow is mid-flight once the flag is cleared.

During step 2, a hook-capable listed token (the codebase itself models these: `with_transfer_hook_market`, and `test_flash_position_transfer_hook_cannot_reenter` proves hook reentry is a designed-for threat — it is only blocked because the *debt* transfer is inside the guard) fires a callback to `caller` (a contract the attacker controls — `require_authorized_caller` accepts contract callers via invoker auth). From that hook the attacker calls `withdraw(caller, account_id, …)`:

- `withdraw` loads `account` **from storage** — the pre-flash version, still containing the attacker's previously supplied collateral shares, because `strategy_finalize` has not run yet.
- It burns those shares at the pool (`burn_supply` decrements `supplied` and pays out cash), then persists the reduced account.
- The hook returns; the outer call continues and `strategy_finalize` persists *its* in-memory account — which still holds the full collateral plus the freshly minted debt — overwriting the inner withdraw's write.

This is exactly the `sk_forward_alloc` trace: pool `supplied` (the shared counter) was decremented by the inner op, while the account's share position (the per-socket `reclaimable` snapshot) is restored by the outer write — the two views of one accounting fact diverge, breaking `INV-ACCT-10` (sum of account supply shares = `supplied − revenue`).

### Impact Explanation
The attacker receives real collateral tokens from the inner `withdraw` while their persisted account still owns the same supply shares. The shares can be withdrawn again (subject to the new flash debt's risk gate — the attacker can size it so HF stays ≥ 1 by only double-spending surplus collateral), paid to `Credit` receivers via self-liquidation, or simply left as claims that exceed pool `supplied`. Either way the pool pays out value no shares back — theft of other suppliers' funds / protocol insolvency. The same primitive works on `borrow` (mint debt from a stale snapshot that is then overwritten while pool `borrowed` keeps the minted total) and `repay`/`supply` for mirror-image corruption.

### Likelihood Explanation
Requires: (a) `flash_position` reachable by any unprivileged address on a market with `is_flashloanable` — it is; (b) a listed token in the same hub+spoke that executes a callback to the recipient on `transfer` — the protocol's own test suite treats transfer-hook tokens as listable and already relies on the guard as the sole mitigation (`test_flash_position_transfer_hook_cannot_reenter`); (c) the attacker pre-seeds the account with collateral so the stale stored account has shares worth stealing. All steps are within a single transaction submitted by one unprivileged contract caller; no governance action, oracle manipulation, or leaked keys needed once such a token is listed. Medium-High likelihood, High impact.

### Recommendation
Move `refund_listed_assets` (and ideally `collect_collateral_deposits`/`process_deposit`) inside the `with_flash_guard` window, or persist/finalize the account *before* any unguarded token transfer so reentrant calls see committed state. At minimum, keep the guard set until `strategy_finalize` completes — refund measurement uses pre-callback baselines already captured inside the guard, so extending the window does not change refund semantics.

### Proof of Concept
1. Governance has listed `HOOK` token (transfers invoke `to.__transfer_hook(...)`) in `(hub_id, spoke)`. Attacker contract `A` calls `supply` → creates `account_id` with 10,000 USDC collateral (persisted).
2. `A` calls `flash_position(caller=A, account_id, spoke_id, Multiply, debt=ETH, amount=1.0, receiver=R, data=…, collaterals=[(USDC, min)], refund_assets=[HOOK])`.
3. Guard opens; ETH debt minted into the in-memory account and forwarded; `R` pushes USDC collateral to the controller; guard closes.
4. `refund_listed_assets` sends the callback-delivered HOOK delta to `A`. The HOOK token invokes `A`'s hook.
5. Inside the hook, `A` calls `withdraw(caller=A, account_id, [(USDC, 0 /*full*/)])`. No flash flag → passes `require_not_flash_loaning`. It loads the stored account (still showing all 10,000 USDC, no new debt), burns shares at the pool, pays `A` ~10,000 USDC, persists the emptied account.
6. Hook returns; `strategy_finalize` persists the outer account (10,000 USDC supply + 1.0 ETH debt), overwriting step 5. `HF ≥ 1` gates pass because the supply position is intact in that copy.
7. Result: `A` holds ~10,000 USDC tokens *and* an account claiming 10,000 USDC supply; pool `supplied` was decremented once but the claim exists twice — `supplied − revenue < Σ account shares`, and the excess is paid out of other suppliers' cash on the next withdraw or liquidation credit.

Caveat: reachability hinges on a listed token executing recipient hooks; if every listed asset is a plain SAC/SEP-41 token with no callback surface, the refund window is unreachable and this collapses to a defense-in-depth gap rather than an exploitable bug. The harness's `with_transfer_hook_market` fixture indicates hook-capable tokens are within the intended threat model, which is why the guarded window exists for the debt leg in the first place — the same protection was simply not extended to the refund leg.
