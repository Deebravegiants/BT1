### Title
Emporium "min-circuit" path lets an unprivileged attacker drain all funds held by the Emporium contract via unaccounted arbitrary calls - (File: contracts/CircomDataBuilder.sol, contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol, contracts/Hinkal.sol)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, whose underlying circuit (`MainEVMCircuitMin`) only proves `message == Poseidon(messageSeed)` — a fact any attacker can compute themselves with no knowledge of protocol secrets, UTXOs, or signatures. Because the token array is empty, every balance-accounting loop in `Hinkal.transact` and `EmporiumUpgradeable.runAction` is skipped, while the `EmporiumStack.ops` loop still executes arbitrary low-level calls from Emporium's own address (with `signerAddress == 0` bypassing signature verification), allowing theft of any ERC20/ETH balance held by the Emporium contract.

### Finding Description
The broken equality is: **assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter`**.

Path:
1. `Hinkal.transact` calls `hinkalHelper.performHinkalChecks` → `CircomDataBuilder.formInputForCircom` [1](#0-0) . With `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, it calls `formInputEmporiumMin`, whose public input vector is only `[emporiumMessage, timeStamp, calldataHash]` [2](#0-1) .
2. The corresponding circuit `MainEVMCircuitMin` only constrains `message <== Poseidon(1)([messageSeed])` and does not constrain `outTimeStamp`, `calldataHash`, `rootHashHinkal`, nullifiers, or any ownership of shielded funds [3](#0-2) . Any attacker can generate a valid proof trivially by picking their own `messageSeed`.
3. `dimensionsCheck` in `HinkalHelper` is satisfiable with `dimensions.tokenNumber == 0`, so all per-token arrays (`erc20TokenAddresses`, `amountChanges`, `onChainCreation`, `slippageValues`, `inputNullifiers`, `outCommitments`, `encryptedOutputs`) can legitimately be empty [4](#0-3) .
4. `rootHashExists` only requires *some* historically valid root (trivially satisfiable, e.g. genesis root), and since `checkOnchainCreation`/nullifier logic loops over an empty array, no real shielded funds need to be spent [5](#0-4) .
5. `Hinkal.transact` proceeds to `_externalTransact`, which requires only that `externalActionMap[HINKAL_EMPORIUM_ACTION_ID] == externalAddress` (the genuine, already-registered Emporium address) [6](#0-5) . `deltaAmountChanges` is built from the empty `erc20TokenAddresses` array, so it is empty too.
6. `EmporiumUpgradeable.runAction` decodes `circomData.externalActionData.externalActionMetadata` into an attacker-controlled `EmporiumStack` [7](#0-6) . `balancesBefore`/`balancesAfter` and the reconciliation loop are computed over `circomData.erc20TokenAddresses`, which is empty, so **no accounting or revert check runs at all** [8](#0-7) .
7. `verifyWallet` is called; with `stack.signerAddress == address(0)`, it only marks `emporiumMessage` used and returns immediately — no ECDSA signature is required for the ops [9](#0-8) .
8. The `ops` loop then executes each attacker-supplied `EmporiumOperation` via `op.endpoint.call{value: op.value}(op.callData)`, with `msg.sender == Emporium contract` [10](#0-9) . An attacker sets `op.endpoint` to any ERC20 token held by Emporium and `op.callData = transfer(attacker, balance)` (selector is not `callHinkalWallet`/`doSendToRelay`, so it is not blocked), draining Emporium's token balance directly.
9. Back in `Hinkal.transact`, `oldBalances`/`newBalances` are also computed over the empty `erc20TokenAddresses` array, so the outer balance-diff/slippage checks never fire for the stolen token [11](#0-10) .

Root cause: the "min" proof path was designed to skip per-token accounting when there are no tokens declared, but `EmporiumStack.ops` execution is not gated on `erc20TokenAddresses.length > 0`, letting an attacker use the accounting-free path to run arbitrary calls from Emporium's own identity with zero balance reconciliation.

### Impact Explanation
Any ERC20 or ETH balance custodied by the Emporium contract (funds in-flight for shielded operations, fees, or any token Emporium holds at call time) can be stolen outright by an unprivileged attacker with a single transaction, using only a self-generated trivial proof. This is direct theft of protocol/user funds held by Emporium — Critical severity, matching "direct theft of shielded or in-flight user funds." The attack is fully repeatable for every token Emporium holds, limited only by Emporium's balance at the time of attack.

### Likelihood Explanation
Preconditions: the attacker needs no privileged role, no ownership of shielded UTXOs, and no relay whitelisting when `circomData.relay == address(0)` and `originalSender == msg.sender`. They need only: a registered Emporium contract address (public/known), a trivially self-generated ZK proof for `MainEVMCircuitMin`, and Emporium holding a nonzero token/ETH balance at attack time (which happens whenever users route funds through Emporium, e.g. between deposit and Emporium-mediated operations). Cost is a single transaction's gas. This is highly feasible and repeatable.

### Recommendation
Do not allow `EmporiumStack.ops` (arbitrary external calls from Emporium's identity) to execute when `circomData.erc20TokenAddresses.length == 0`/the min-proof path is used, or otherwise decouple the "min circuit" fast-path from the ability to run `ops`. At minimum, require `stack.signerAddress != address(0)` (a valid signed message) whenever ops perform external calls, and ensure Emporium's own token/ETH custody is reconciled against a balance check that is not conditioned on `circomData.erc20TokenAddresses` being non-empty (e.g., track and verify Emporium's total balances independent of attacker-supplied array length).

### Proof of Concept
Foundry test plan:
1. Deploy Hinkal, HinkalHelper, VerifierFacade with the real `MainEVMCircuitMin` verifier registered for `buildVerifierId(dimensions{tokenNumber:0,...}, HINKAL_EMPORIUM_ACTION_ID)`.
2. Deploy `EmporiumUpgradeable`, register it in `Hinkal.externalActionMap[HINKAL_EMPORIUM_ACTION_ID]`, add Hinkal as allowed recipient.
3. Fund Emporium with `TOKEN.transfer(emporium, 1000e18)` to simulate in-flight/escrowed balance.
4. Generate a real snarkjs proof for `MainEVMCircuitMin` with a self-chosen `messageSeed`, computing `message = Poseidon(messageSeed)`, setting `emporiumMessage = message`.
5. Build `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, `onChainCreation = []`, `slippageValues = []`, `encryptedOutputs = []`, `externalActionData = {externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalAddress: address(emporium), externalActionMetadata: abi.encode(EmporiumStack{v:0,r:0,s:0, signerAddress:address(0), ops:[EmporiumOperation{endpoint:address(TOKEN), invokeWallet:false, value:0, callData: abi.encodeCall(IERC20.transfer,(attacker,1000e18))}], maxFee:0, deadline: block.timestamp+1000})}`.
6. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from attacker EOA.
7. Assert: `TOKEN.balanceOf(attacker)` increases by `1000e18` and `TOKEN.balanceOf(emporium)` goes to `0`, while `oldBalances == newBalances` (both empty arrays, no revert), proving the equality "assets moved == assets accounted" is violated.
