## Analog Found

### Title
Uniswap V4 venue pricing in the Simplex intent filler uses the manipulable instantaneous pool spot price (no TWAP), risking solver fund loss on curveless pairs - (File: `sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts`)

### Summary
For "venue-priced" (curveless) trading pairs, Simplex's `FXFiller` prices and funds order legs directly from a Uniswap V4 pool's instantaneous state (`sqrtPriceX96` -> `token0Price`/`token1Price`) rather than from a manipulation-resistant TWAP. This is the exact bug class in the referenced Sherlock report: `getBunniTokenPrice` derived value from a single-block AMM state that flash-loan-style liquidity moves can distort within one transaction window. The only mitigation is an optional, static `referencePrice`/`maxDeviationBps` band, which the filler's own docs acknowledge leaves the pool "exposed to a manipulated, stale, or thin pool returning a bad quote."

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` iterates the solver's hydrated V4 positions and calls `computeDirectPoolPriceUsd`, which reads the pool's current mid price straight off the SDK `Pool` object (`sdkPool.token0Price` / `sdkPool.token1Price`, derived from live `sqrtPriceX96`): [1](#0-0) 

This price is fetched fresh via `state.refresh()` immediately before use, i.e., it is the current instantaneous pool state, not a time-weighted average: [2](#0-1) 

`FXFiller.resolveLegRates` uses this venue price to set the actual fill rate for curveless pairs, and `referenceRate` uses it to size confirmation depth — both gated only by `checkPriceGuard`, which compares the live quote against a *static* reference price within a configurable bps band: [3](#0-2) [4](#0-3) 

Critically, the guard is explicitly optional and per-chain — "The two [`referencePrice`, `maxDeviationBps`] fields must be set together; omit both to leave the chain unguarded" — and even when configured, it is a static band with no execution-cost or pool-depth awareness: [5](#0-4) 

The project's own internal flow documentation confirms this design gap: `computeDirectPoolPriceUsd` "returns the raw pool mid derived from sqrtPriceX96... there is no size or impact term... `checkPriceGuard` is the only defense on this path, and it checks deviation from a static reference, not execution cost": [6](#0-5) 

Once a venue price passes the (optional) guard, the solver commits to filling the order at that rate and physically withdraws the exotic token via `planWithdrawalForToken`, which decreases liquidity on the same manipulated pool and hands out real tokens: [7](#0-6) 

### Impact Explanation
An attacker who can move the referenced Uniswap V4 pool's spot price within the guard's tolerance (or on an unguarded chain, arbitrarily) can induce the solver to price and settle real cross-chain intent legs at a manipulated exchange rate, extracting value from the solver's LP-backed inventory. Because `computeDirectPoolPriceUsd` derives price purely from `sqrtPriceX96` with no depth/impact term, and because it is trusted immediately after `refresh()`, a pool with modest depth relative to the order size (and any unconfigured/loosely configured chain) allows theft of solver capital — a real, on-chain economic loss, consistent with the "concrete theft ... of funds" bar.

### Likelihood Explanation
The guard is optional per chain ("omit both to leave the chain unguarded") and, even when present, is a static ±bps band around an operator-set reference that does not account for pool depth or trade size, so a sufficiently large/well-timed swap against a thinner pool still clears the band while moving the mid price materially. The filler's own documentation flags this as an acknowledged, un-remediated gap on the pool-pricing path, and pricing runs on every quote for curveless pairs, making the path reachable by any external actor able to trade on the referenced pool and have (or induce) an order the filler prices with `getExoticTokenPrice`/`referenceRate`.

### Recommendation
Replace or supplement the instantaneous `sqrtPriceX96`-derived mid with a manipulation-resistant reference (e.g., a Uniswap V4 TWAP oracle observation over a sufficient window, or a depth/impact-aware quote), and make the `referencePrice`/`maxDeviationBps` guard mandatory (not optional) for any chain enabling venue pricing, scaling the allowed deviation with the pool's available liquidity relative to the order size rather than a fixed static band.

### Proof of Concept
1. Configure a Simplex filler with a curveless `[[pairs]]` entry priced via `[vault.uniswapV4]`, either with no `referencePrice`/`maxDeviationBps` guard, or with a wide-enough band, per `docs/content/developers/evm/simplex/pricing.mdx` lines 68-84.
2. Attacker swaps a sizeable amount through the referenced Uniswap V4 pool to shift `sqrtPriceX96` toward a rate favorable to the attacker, within (or absent) the guard's tolerance.
3. Attacker immediately submits/triggers an intent order on the affected pair; `FXFiller.resolveLegRates` → `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` reads the now-manipulated pool mid (`sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts` lines 206-240), and `checkPriceGuard` passes it.
4. The solver fills the order at the manipulated rate and withdraws exotic-token liquidity via `planWithdrawalForToken` (lines 293-330), transferring more value to the attacker than the pool's true (unmanipulated) price would justify.
5. Attacker reverses/unwinds the pool position, realizing the arbitrage profit extracted from the solver's inventory.

```typescript
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}
```

```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```
