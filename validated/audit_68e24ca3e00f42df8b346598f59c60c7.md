Based on my investigation, I found a valid analog. The core bug pattern is: **removing a registered route/peer permanently orphans funds already committed to that route, with no recovery path**, mirroring the `StakingModule` plugin-removal issue where a user's already-earned entitlement becomes permanently unclaimable once the referencing key is deleted.

### Title
Removing a chain from `HyperFungibleToken`/`WrappedHyperFungibleToken` while an in-flight (non-expiring) transfer targets it permanently strands the sender's burned tokens - (File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol)

### Summary
`HyperFungibleToken.send()` burns the caller's tokens immediately and dispatches a POST request whose recovery (refund) is entirely dependent on either (a) successful delivery via `onAccept` on the destination, or (b) a timeout callback `onPostRequestTimeout` firing after `timeoutTimestamp` elapses. If a user (or an integrator building `data`/calldata flows) sets `params.timeout == 0` ("no timeout" - a value explicitly supported by the protocol, see `Message.timeout()` returning `type(uint64).max` and `get_timeout` in `modules/ismp/core/src/router.rs`), and the destination owner subsequently calls `removeChain()` for the source chain's entry (or the entry was never/no-longer configured on the destination), the request can never be delivered (`onAccept` reverts with `UnsupportedChain`) and can never time out. The burned tokens are permanently unrecoverable — there is no other refund mechanism in the contract.

### Finding Description
`send()` at [1](#0-0)  burns tokens up-front and dispatches the request with the caller-chosen `params.timeout`. The dispatch layer treats `timeout == 0` as "never expires": [2](#0-1)  and the ISMP core confirms this semantic: [3](#0-2) .

Recovery of burned funds relies solely on two paths:
1. Successful delivery: `onAccept` checks `_supportedChains[request.source]` and reverts with `UnsupportedChain` if the source entry has been removed via `removeChain()`, per [4](#0-3) .
2. Timeout refund: `onPostRequestTimeout` re-mints the burned amount back to the sender, per [5](#0-4) . This can only ever fire if `timeoutTimestamp != 0`.

`removeChain()` unconditionally deletes the routing entry with no check for requests currently in flight to/from that chain: [6](#0-5) . The same pattern is repeated identically in `HyperFungibleTokenUpgradeable.sol` and `WrappedHyperFungibleToken(Upgradeable).sol`.

This is structurally identical to the referenced Telcoin `StakingModule` bug: a mapping-gated resource (`pluginsMapping` there, `_supportedChains` here) is deleted by an ordinary administrative action, and the only code path that could make the user whole (claim / timeout-refund) is gated by that exact same mapping check, so once the entry is gone, the user's already-committed value (accrued rewards there, burned tokens here) becomes permanently unrecoverable.

### Impact Explanation
Permanent freezing of user funds: tokens burned by `send()` cannot be minted on the destination (blocked by `UnsupportedChain`) and cannot be refunded on the source (no timeout ever fires since `timeoutTimestamp == 0`). This is a direct, unbacked loss of user funds with no admin/governance override capable of restoring the burned balance (there is no "re-mint" or manual recovery function in the contract). This qualifies as concrete permanent freezing of funds.

### Likelihood Explanation
Zero-timeout transfers are an explicitly supported, documented configuration ("0 for no timeout... Messages will never expire" — `docs/content/developers/evm/messaging/post-requests.mdx`), not a misuse. Any legitimate deprecation/rotation of a peer deployment via `removeChain()` (e.g., migrating to a new contract address, responding to a compromise, or decommissioning a chain) performed while such zero-timeout transfers are still in flight triggers the freeze. Since `removeChain` is a normal maintenance operation (not attacker-controlled malicious governance) and zero-timeout sends are a standard, encouraged feature for gas-fee-sensitive integrators, this is reasonably likely to occur in production operation.

### Recommendation
- Disallow `timeout == 0` in `send()`/`_buildDispatchPost()`, enforcing a mandatory minimum timeout so every dispatched transfer has a guaranteed refund path.
- Alternatively/additionally, have `removeChain()` check for or migrate in-flight commitments, or provide an owner-gated emergency refund/re-mint function for `UnsupportedChain`-orphaned deliveries, guarded by proof of the original burn.
- Document and enforce that `_supportedChains` changes must never occur while sends with `timeout == 0` targeting that chain are outstanding, or block `removeChain` unless the chain has no unresolved outbound requests.

### Proof of Concept
1. Chain A's `HyperFungibleToken` and Chain B's `HyperFungibleToken` are mutually configured via `addChain`.
2. User calls `send({dest: B, to: recipient, amount: 100, timeout: 0, ...})` on Chain A: `_burn(user, 100)` executes, POST request dispatched with `timeoutTimestamp = 0` (per `EvmHost.dispatch`, [2](#0-1) ).
3. Before the message is relayed/delivered, Chain B's owner calls `removeChain(A)` (e.g., migrating to a new deployment address for chain A).
4. Relayer submits the POST request to Chain B: `onAccept` reads `_supportedChains[A]` as empty and reverts with `UnsupportedChain` ( [7](#0-6) ) — message delivery fails permanently.
5. Because `timeoutTimestamp == 0`, `PostRequest.timeout()` returns `type(uint64).max` ( [3](#0-2) ), so the request can never be reported as timed out and `onPostRequestTimeout` (the only refund path) is never invocable.
6. The user's 100 tokens, burned in step 2, are permanently lost with no code path to recover them.

/// Get the timeout in seconds
fn get_timeout(timeout_timestamp: u64) -> Duration {
	// zero timeout means no timeout.
	if timeout_timestamp == 0 {
		Duration::from_secs(u64::MAX)
	} else {
		Duration::from_secs(timeout_timestamp)
	}
}
