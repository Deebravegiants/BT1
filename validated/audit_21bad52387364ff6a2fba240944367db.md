Based on my investigation, I found a genuine identity-binding gap in the webhook verification path of this gem.

### Title
Webhook HMAC signs only the raw body, not the `shop-domain`/`topic`/`webhook-id` headers, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` by exposing `hmac` from the `hmac-sha256` header and `to_signable_string` from the raw request body only. [1](#0-0)  `Utils::HmacValidator.validate` recomputes the HMAC solely over `to_signable_string` and compares it to the supplied signature. [2](#0-1)  `Webhooks::Registry.process` accepts the request once that check passes and then forwards `request.shop` (a header value never covered by the signature) to the merchant-facing handler as the trusted tenant identifier. [3](#0-2)  The equality the library implicitly claims — "HMAC valid ⇒ `shop` header is authentic for this body" — does not hold, because `shop` (and `topic`, `webhook-id`) are outside the signed bytes.

### Finding Description
The webhook signature scheme signs `@raw_body` exclusively:
```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end

def to_signable_string
  @raw_body
end
``` [1](#0-0) 

Because the same app `client_secret` is used to sign webhooks for every shop that installs the app, a request with a valid body+HMAC pair captured from one tenant (e.g., the attacker's own store, which they can freely install the app on) remains "valid" under `HmacValidator.validate` even after the `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers are swapped for arbitrary values, since none of those bytes participate in `to_signable_string`. [4](#0-3)  `Registry.process` trusts this and passes the (forged) `shop` straight through to the handler as `WebhookMetadata#shop`:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))
end
``` [3](#0-2) 

This breaks the binding `verified(hmac) == authentic(shop, topic, webhook_id)`: the gem verifies bytes of the body, but the identity fields the host application relies on for tenant scoping are unverified.

### Impact Explanation
An unprivileged internet user who can install the target app on any shop (a normal, permission-less action for public/OAuth-installable apps) can legitimately trigger a webhook, capture the raw body and its valid HMAC, and replay it against the same public webhook endpoint with a forged `x-shopify-shop-domain` header pointing at a victim tenant. Because `HmacValidator.validate` only checks body bytes, this request passes verification, and the host application receives `WebhookMetadata` claiming the payload originated from the victim shop. Any host logic that scopes database writes, cache invalidation, order/customer processing, or de-duplication by `WebhookMetadata#shop` can be tricked into attributing attacker-controlled body content to another tenant — a cross-tenant data integrity/confidentiality issue.

### Likelihood Explanation
Exploitation requires only (1) the ability to install the app on an attacker-controlled shop — trivial for any public app — and (2) the ability to send an HTTP POST to the app's public webhook endpoint with modified headers, which is inherent to how webhook endpoints are exposed. No access token, `client_secret`, or privileged credential is required beyond what a normal, unprivileged install already grants.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material used for verification, or independently confirm in `Webhooks::Request`/`Registry.process` that the `shop` header matches an expected/allow-listed value bound to the specific installation before handing it to the handler. At minimum, document clearly that `Registry.process` does not authenticate the `shop` header and that host apps must independently verify shop identity before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers any webhook (e.g., `orders/create`), capturing the raw POST body `B` and header `x-shopify-hmac-sha256: H` (valid since signed with the shared app `client_secret`).
2. Attacker sends a new POST to the app's public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate(request)` recomputes the HMAC over `B` only and matches `H`, returning `true`. [2](#0-1) 
4. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled data under the victim tenant's identity. [5](#0-4)
