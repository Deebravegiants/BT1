Confirmed: `WebhookMetadata` carries `topic`, `shop`, `body`, `api_version`, `webhook_id` — all populated straight from unauthenticated HTTP headers — and passed to the host app's `handle` callback as trusted identity fields, while `Utils::HmacValidator.validate` only ever authenticates the raw JSON body.

### Title
Webhook `shop`/`topic`/`webhook_id` identity fields are trusted while excluded from the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` authenticates nothing but the JSON payload bytes. The `shop`, `topic`, `webhook_id`, and `api_version` values — read straight from HTTP headers — are never part of the signed material, yet `Registry.process` forwards them unchecked into `WebhookMetadata`, which the host app's `WebhookHandler#handle` treats as authenticated tenant identity.

### Finding Description
`Webhooks::Request#hmac` and `#to_signable_string` are defined as: [1](#0-0) 

Only `@raw_body` is signed. The `shop`, `topic`, `webhook_id`, and `api_version` accessors are pulled from headers that are completely outside the HMAC's coverage: [2](#0-1) 

`Registry.process` validates only this body-scoped HMAC, then builds `WebhookMetadata` directly from the unauthenticated header fields and passes it to the handler as if it were trustworthy: [3](#0-2) 

`WebhookMetadata` is the struct the host app relies on to know *which shop* a webhook belongs to: [4](#0-3) 

This is the same class of bug as the referenced report: a value that is acted upon (`shop`) is not covered by the cryptographic check (`hmac`) that is supposed to bind the message to its sender. The equality that should hold — `hmac_signed_bytes == bytes_that_determine_shop_identity` — is broken because `hmac_signed_bytes = raw_body` while `shop_identity = header("shop-domain")`.

### Impact Explanation
Any internet user who has legitimate access to a store where the target app is installed (e.g., their own free/dev shop) can trigger a real webhook, capturing a `(raw_body, hmac)` pair that Shopify legitimately signed with the app's secret. They can then replay that exact `raw_body`/`hmac` pair directly to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) header. `HmacValidator.validate` still succeeds because it only checks the untouched body bytes against the untouched signature. The handler then executes business logic (order/customer/data processing, cache/DB writes keyed by `data.shop`) believing the payload originated from the spoofed shop — a cross-tenant identity-binding bypass using only the attacker's own legitimately-obtained webhook, no access token or `client_secret` required.

### Likelihood Explanation
Webhook endpoints are public HTTP routes reachable by anyone; Shopify's webhook authentication model relies entirely on this gem's HMAC check (there is no IP allowlisting requirement). Obtaining a signed `(body, hmac)` pair only requires installing the app on any shop the attacker controls, which is trivial for an unprivileged internet user. The header substitution requires no cryptographic material.

### Recommendation
Bind the identity headers into the signed material, or otherwise authenticate them: e.g., include `shop-domain`, `topic`, and `webhook-id` in `to_signable_string` (mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop`/`host` into its signature), or cross-check `request.shop` against the shop associated with the session/store the app expects for that webhook subscription before trusting it in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any subscribed webhook (e.g. `orders/create`), capturing the raw POST body `B` and the `x-shopify-hmac-sha256` value `H` that Shopify computed with the app's real secret.
2. Attacker sends a POST directly to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim-shop.myshopify.com` and `x-shopify-topic`/`x-shopify-webhook-id` of their choosing.
3. `ShopifyAPI::Webhooks::Request.new` parses these headers into `shop`/`topic`/`webhook_id`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` only checked `B` against `H`.
5. `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...))` executes with attacker-controlled body under the victim shop's identity — a cross-tenant spoof.
