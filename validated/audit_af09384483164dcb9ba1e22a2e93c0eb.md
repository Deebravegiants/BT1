### Title
HOT API fallback reports a withdrawal as "completed" without checking the `verified_withdraw` flag - (File: `packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts`)

### Summary
`HotBridge.describeWithdrawal()` falls back to the HOT off-chain API (`fetchWithdrawalHashFromApi`) to determine whether a withdrawal has completed. The API response is validated against `HotApiWithdrawalResponseSchema`, which explicitly parses a `verified_withdraw: boolean` field per withdrawal entry, but this field is never consulted before the SDK reports the withdrawal as `"completed"` and returns a destination `txHash`.

### Finding Description
The schema for the HOT API withdrawal object includes `verified_withdraw`: [1](#0-0) 

But `fetchWithdrawalHashFromApi`, which is used as the fallback source of truth when the bridge indexer fails or doesn't have the hash yet, only checks that `withdrawal.hash` exists and is a valid hex string — it ignores `verified_withdraw` entirely: [2](#0-1) 

This hash is then propagated straight up as a `"completed"` status: [3](#0-2) 

and also in the non-EVM/non-Stellar/non-TON branch: [4](#0-3) 

This breaks the equality "status reported == on-chain outcome": the SDK signals `status: "completed"` with a concrete destination `txHash` purely on the basis of a hash string being present and hex-formatted, without checking the API's own `verified_withdraw` indicator of whether that withdrawal hash has actually been confirmed/verified. `watchWithdrawal()` in `withdrawal-watcher.ts` immediately resolves to `{ hash: status.txHash }` on receiving `"completed"`, with no further verification: [5](#0-4) 

### Impact Explanation
If an integrator uses `watchWithdrawal`/`createWithdrawalCompletionPromises` to decide when to credit a user or release downstream funds, it will treat the withdrawal as final and settled as soon as an unverified hash is returned by the HOT API fallback. Since `verified_withdraw` is parsed but discarded, a hash that HOT itself has not verified can trigger premature "completed" reporting, potentially followed by a different/legitimate completion event later — a status misreport that can make an integrator credit or refund based on an incorrect on-chain outcome, matching the High-severity category "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This path is reached automatically whenever the primary bridge indexer errors out or is skipped (e.g., non-EVM/non-Stellar/non-TON chains going straight to the API fallback), which is a normal, non-privileged, no-attacker-action-required code path — it doesn't require any malicious actor, just the routine occurrence of the bridge indexer being unavailable or slow, which the code already anticipates via its fallback design.

### Recommendation
Check `withdrawal.verified_withdraw === true` before accepting `withdrawal.hash` as evidence of completion in `fetchWithdrawalHashFromApi`; if `verified_withdraw` is `false`, treat the result as `null` (i.e., keep withdrawal `"pending"`) rather than returning a hash that gets reported as `"completed"`.

### Proof of Concept
1. A withdrawal is submitted on a HOT-bridge-supported chain that relies on the API fallback path (`fetchWithdrawalHashFromApi`), e.g. because `fetchWithdrawalHashBridgeIndexer` throws.
2. The HOT API returns a withdrawal entry with `hash: "0xabc..."` and `verified_withdraw: false` (i.e., HOT has not verified this transfer yet, perhaps a stale/incorrect candidate hash).
3. `fetchWithdrawalHashFromApi` only checks `isHex(hash)`, ignoring `verified_withdraw`, and returns the hash.
4. `describeWithdrawal` returns `{ status: "completed", txHash: formatTxHash(apiHash, ...) }`.
5. `watchWithdrawal` resolves immediately with `{ hash: status.txHash }`, and any integrator logic gating fund release/credit on this promise proceeds — despite HOT not having verified the withdrawal.
