## Title
Unsigned, fee-free `handle_unsigned` message batches allow relayer-triggered memory-consumption DoS during transaction-pool validation - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
Substrate parachains normally bound block/extrinsic byte length via `frame_system::BlockLength`, which limits how large a single unsigned extrinsic's *class-normal* payload can be. However, `pallet_ismp::Call::handle_unsigned` takes an unbounded `messages: Vec<Message>` and its `ValidateUnsigned::validate_unsigned` implementation fully decodes, clones, and *executes* (`Self::execute(messages.clone())`) the entire batch — including proof deserialization and full membership/consensus verification work — for every single unsigned extrinsic that reaches a node's mempool, before any fee is charged and before the extrinsic is included in a block.

### Finding Description
`handle_unsigned` is explicitly documented as free-to-call by any unauthenticated party: "This is an unsigned extrinsic that permits anyone execute ISMP messages for free" [1](#0-0) . Its `ValidateUnsigned::validate_unsigned` handler calls `Self::execute(messages.clone())` directly on submission to the pool — this is a *cloning* and full-processing step performed for every unsigned tx a peer gossips, run by every full node validating the transaction pool [2](#0-1) . `execute` itself clones the message vector again and maps `handle_incoming_message` over every message in the batch [3](#0-2) .

The sibling `pallet-call-decompressor` had this exact bug class fixed explicitly for its own unsigned `decompress_call`/`decompress` path — the code comment documents that the "fee-less attacker could claim `encoded_call_size = u32::MAX`... and have a tiny zstd bomb expanded to gigabytes during transaction-pool validation" and was patched by moving the size-bound check into the shared `decompress` function used by both the dispatch and `validate_unsigned` paths [4](#0-3) . That fix, however, only protects the compressed-call path. The direct, uncompressed `pallet_ismp::Call::handle_unsigned { messages: Vec<Message> }` path has no equivalent cap on the number of messages in the batch, the number of `PostRequest`s per `RequestMessage`, the size of each `PostRequest.body`, or the number of `keys` in a `GetRequest`/`DispatchGet` (`keys: Vec<Vec<u8>>`) [5](#0-4) . This mirrors the request/response structures shown in the docs and test fixtures, e.g. tests constructing batches of 1,000 `PostRequest`s each carrying arbitrary bodies, or `GetRequest`s with 256 keys per request [6](#0-5) [7](#0-6) .

Because the extrinsic is unsigned and free (no `pre_dispatch` deducts a fee, and `pre_dispatch` is a no-op — see `fn pre_dispatch(_call: &Self::Call) -> Result<(), TransactionValidityError> { Ok(()) }` [8](#0-7) ), an attacker who submits many large-but-structurally-valid `handle_unsigned` extrinsics (large request bodies/keys, wrapped in invalid or bogus proofs so they don't need to be accepted onchain) forces every peer that receives and gossips the transaction to fully decode and process the payload in `validate_unsigned` before rejecting it — this is analogous to CVE-2019-20888's memory-consumption DoS via unauthenticated webhook/slash-command payload processing.

### Impact Explanation
This is a network/memory-consumption denial-of-service vector reachable by an unprivileged party (no signature, no fee, no prior state) simply by submitting `Ismp::handle_unsigned` extrinsics with maximally-sized message batches to the p2p network. Each node that receives and re-validates the gossiped extrinsic performs full clone + decode + proof-verification work in `validate_unsigned`, which can be repeated cheaply and continuously since it costs nothing to submit. This can degrade node performance/availability network-wide (a route unable to deliver messages / DoS on message dispatch infrastructure), which falls within the in-scope categories (EvmHost/HandlerV2 dispatch and delivery infrastructure equivalent on the Substrate side, i.e., pallet-ismp `handle_unsigned`).

### Likelihood Explanation
Likelihood is constrained by whatever `frame_system::BlockLength`/max-extrinsic-size configuration each runtime (Gargantua/Nexus) applies to normal-class unsigned extrinsics — I was not able to fully confirm the exact configured limits within this investigation's time budget (grep found relevant config references in `parachain/runtimes/gargantua/src/lib.rs` and `parachain/runtimes/nexus/src/lib.rs` but the exact byte cap and whether it materially bounds the number/size of `Message`s that can be packed was not verified). If the configured max extrinsic/block length is generous (common for parachains supporting large batched proofs), the number of PostRequests/keys/body bytes that fit in one call is still large enough to make `validate_unsigned`'s cloning and processing cost meaningfully higher per-tx than a minimal message, and this can be repeated indefinitely for free.

### Recommendation
Apply the same "single choke point" size/count bounding pattern already used for `pallet-call-decompressor`'s `decompress`, to `pallet_ismp::Call::handle_unsigned`:
- Bound the number of `Message`s per batch, the number of requests/responses per message, and per-item body/key sizes with a configurable `Config::MaxMessages`/`MaxBatchBytes`-style constant, enforced identically in both `validate_unsigned` and the dispatchable body before any cloning/processing occurs.
- Ensure `pre_dispatch`/`validate_unsigned` reject oversized batches cheaply (based on cheap length checks) before calling `execute`, mirroring the `ensure!(encoded_call_size < T::MaxCallSize::get() * ONE_MB, ...)` early-exit pattern used in `pallet-call-decompressor::decompress`.

### Proof of Concept
Conceptual PoC (not executed): submit repeated unsigned extrinsics `Ismp::handle_unsigned { messages: vec![Message::Request(RequestMessage { requests: vec![PostRequest { body: vec![0u8; MAX_ALLOWED_SIZE], .. }; N], proof: <garbage or expensive-to-verify but structurally valid Proof>, signer: vec![] })] }` from many peer connections without holding any funds. Each node's `validate_unsigned` clones and processes the full `messages` payload via `Self::execute(messages.clone())` [2](#0-1)  before ultimately rejecting on invalid proof — repeated submission drives up memory/CPU consumption network-wide at zero cost to the attacker.

	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;
