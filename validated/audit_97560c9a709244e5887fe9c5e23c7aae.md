### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted from unauthenticated headers while the HMAC only binds the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` by defining `to_signable_string` as `@raw_body` only [1](#0-0) . Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers, which are never included in the HMAC computation [2](#0-1) . `ShopifyAPI::Webhooks::Registry.process` validates only the HMAC of the body and then dispatches to the handler using the unauthenticated `request.shop`/`request.topic`/`request.webhook_id` values [3](#0-2) . This is directly analogous to the reported bug class: a field that is acted upon (`shop`, used as the tenant identity for the webhook) is not covered by the integrity check (the HMAC), so the two can be desynchronized by an attacker who controls the request that reaches the app's public webhook endpoint.

### Finding Description
The webhook processing endpoint described in the gem's own docs is a plain public HTTP endpoint on the app's server: `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h))` [4](#0-3) . Anyone who can reach this endpoint — not just Shopify — can send arbitrary headers together with any raw body.

`Utils::HmacValidator.validate` computes and compares an HMAC over `verifiable_query.to_signable_string` [5](#0-4) . For `Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) . The equality that must hold for tenant-safety is:
`shop_used_by_handler == shop_that_the_HMAC-signer_intended_for_this_body`

Because `shop` (and `topic`, `webhook_id`) come from the `shopify-shop-domain`/`shopify-topic`/`shopify-webhook-id` headers, which are outside the signed bytes, this equality is not enforced by the gem at all — the HMAC only proves the body bytes were signed by the holder of the API secret; it says nothing about which shop or topic they were signed for.

Concretely: if an attacker (e.g., an app installer/merchant who legitimately triggers a real webhook for **their own** shop and can observe/capture that exact `(raw_body, HMAC header)` pair, since it is delivered to their own callback URL/log) replays that captured raw body and HMAC header unchanged, but substitutes the `shopify-shop-domain` header (and optionally `shopify-topic`/`shopify-webhook-id`) to point at a different tenant, `HmacValidator.validate` still succeeds (only the body bytes are checked), and `Registry.process` will call the registered handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [6](#0-5)  — attributing the (attacker-supplied/legitimately-signed-for-a-different-shop) payload to an arbitrary victim shop.

### Impact Explanation
This breaks the tenant/identity boundary that the webhook mechanism is supposed to establish: the app-level handler trusts `data.shop` (and `data.topic`) as authenticated facts derived from a verified Shopify webhook, per the gem's own documentation ("This will verify the request did indeed come from Shopify") [7](#0-6) , but the gem never actually binds `shop`/`topic`/`webhook_id` to the HMAC. Any app that keys per-tenant business logic (uninstall, GDPR redact, order/customer state changes, billing state, etc.) off `data.shop` can have that logic invoked for a shop that never actually sent the webhook, using a body payload the attacker fully controls the pairing of. This is a cross-tenant identity-binding break rooted in the gem's own `Request`/`Registry` implementation, not merely host-application misuse of a documented contract — the gem promises "verify the request did indeed come from Shopify" but does not verify the header-derived shop/topic at all.

### Likelihood Explanation
Exploitability requires the attacker to be able to reach the app's public webhook endpoint (true for any internet-facing webhook route, by design) and to possess at least one valid `(raw_body, hmac)` pair — trivially obtainable by any merchant who has legitimately installed the app and can trigger a subscribed webhook topic for their own store (e.g., updating a product to fire `products/update`), since Shopify will deliver a genuinely HMAC-signed payload to the app's endpoint, and the attacker (as the shop owner) can capture that exact body/HMAC pair via their own network tooling before/while it's delivered, or via any logging/proxy they control in front of their own installation. No access to the app's `client_secret` or another shop's credentials is needed. This satisfies the "unprivileged internet user" bar.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the HMAC verification, or otherwise cryptographically tie header-derived identity fields to the signed payload:
- Include the relevant headers (at minimum `shopify-shop-domain` and `shopify-topic`) in the signable string used for HMAC verification, or
- Require that the `shop` in the webhook body/headers matches an expected/known shop for the receiving path/session that registered that webhook, and reject on mismatch.

### Proof of Concept
1. App registers `orders/create` handler; attacker installs the app for `attacker-shop.myshopify.com` and triggers an order creation, causing Shopify to POST to the app's webhook route with headers `shopify-topic: orders/create`, `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: <valid HMAC of raw body>`.
2. Attacker captures the exact `raw_body` and `shopify-hmac-sha256` value (e.g., via a proxy in front of their own listener, or by using a webhook-forwarding tool they control).
3. Attacker crafts a new POST to the same webhook endpoint with the identical `raw_body` and `shopify-hmac-sha256` header, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `@raw_body` against the HMAC and passes [8](#0-7) [1](#0-0) .
5. The handler executes with `data.shop == "victim-shop.myshopify.com"` and the attacker's chosen body content, despite the payload never having been generated for or signed in relation to the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
