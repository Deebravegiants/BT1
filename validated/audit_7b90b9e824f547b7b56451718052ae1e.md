### Title
Webhook `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` field (and `topic`, `api_version`, `webhook_id`) from unauthenticated HTTP headers, while the HMAC signature that `ShopifyAPI::Utils::HmacValidator` verifies only covers the raw request body. This breaks the intended binding: `hmac == HMAC(secret, body + shop + topic)`, when in fact only `hmac == HMAC(secret, body)`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers, entirely outside the signed material: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` to build `WebhookMetadata`, which is passed to the app's registered handler as the tenant/topic identity for the webhook: [3](#0-2) 

`WebhookMetadata.shop` is a plain, unsigned string field consumed by host-application handler code as the authoritative shop for the event: [4](#0-3) 

Because `OpenSSL.secure_compare(computed_signature, received_signature)` in `HmacValidator.validate_signature` is computed solely from `to_signable_string` (the body), any request with a body/HMAC pair that Shopify issued for one shop remains valid if the `x-shopify-shop-domain` (or `shopify-shop-domain`) header is swapped to a different shop domain — the signature check still passes because it never covered that header: [5](#0-4) 

An unprivileged internet user who operates their own Shopify development/trial store (installing the app themselves) legitimately receives real, validly-signed webhook deliveries containing this body/HMAC pair from Shopify for their own shop. That user can replay the exact same body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header (and/or `topic`/`webhook-id`) with an arbitrary victim shop's domain. `Registry.process` will accept the HMAC (it only checks the body) and dispatch a `WebhookMetadata` whose `shop` is attacker-controlled to the handler, which will treat the event as authoritative for that victim shop.

### Impact Explanation
This breaks the identity binding "shop authenticated == shop the event is attributed to," letting an attacker inject events attributed to a shop they do not own into the app's webhook processing pipeline. Depending on what the host application's webhook handler does with `data.shop` (e.g., look up/mutate that shop's session, trigger shop-scoped side effects, or update per-shop state), this is a cross-tenant confusion vector purely from the gem's own unsigned-field design, satisfying the cross-tenant access impact bar.

### Likelihood Explanation
Requires only an attacker-controlled shop capable of installing the app and receiving at least one legitimate webhook (a normal, unprivileged action any merchant/developer can do), plus the ability to send an arbitrary HTTP POST with modified headers to the app's public webhook endpoint — no `api_secret_key`, access token, or privileged access needed.

### Recommendation
Include `shop-domain`, `topic`, `webhook-id`, and `api-version` in the signed/verifiable material (e.g., by having `to_signable_string` incorporate these header values, or by independently verifying `shop` against a value embedded in the signed body) so the HMAC binds the full identity tuple, not just the body bytes.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com` and receive any real webhook, e.g. `orders/create`, capturing `raw_body` and the valid `x-shopify-hmac-sha256` value Shopify computed for it.
2. Replay a POST to the app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-computes the HMAC over `raw_body` [1](#0-0)  — validation succeeds despite the shop header being forged.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` [6](#0-5)  and processes it as if it were a genuine event for `victim.myshopify.com`.
