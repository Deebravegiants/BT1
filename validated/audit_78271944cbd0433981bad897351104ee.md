### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its verifiable signature over the raw request **body only**, while the `shop` identity that downstream handlers rely on is read from an unsigned HTTP header. This breaks the intended binding: *bytes verified by HMAC* ≠ *bytes the handler trusts for tenant identity*.

### Finding Description
`Utils::HmacValidator.validate` computes an HMAC over `verifiable_query.to_signable_string` and compares it against the `hmac` value supplied by the caller: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only the raw HTTP body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers, none of which are included in the signed content: [3](#0-2) 

`Registry.process` validates only the HMAC and then trusts `request.shop` verbatim to build the tenant context that is handed to the app's webhook handler: [4](#0-3) 

The equality the code implicitly assumes is:
`hmac_sha256(api_secret_key, raw_body) == received_hmac` ⇒ `shop-domain header == the shop that actually generated raw_body`

That equality does not hold, because `shop-domain` is never part of the signed material. Any party that can obtain one legitimately-signed webhook body/HMAC pair for *some* shop (e.g., an attacker who installs the app on their own store, which is a normal unprivileged action any merchant can take) can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary value in the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header. `HmacValidator.validate` will still return `true`, since it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
This is a **cross-tenant identity-binding break**: the field the app's business logic trusts to select the tenant (`shop`) is disjoint from the field that is cryptographically authenticated (the raw body). A host application built on this gem's documented API (using `Registry.process` and reading `data.shop` from `WebhookMetadata`) has no gem-level guarantee that the `shop` it receives is the shop that produced the signed payload. Depending on how the host app persists/acts on webhook data keyed by `data.shop` (e.g., looking up the victim's stored session/access token, writing attacker-supplied data into the victim's tenant records, or triggering actions using the victim's credentials), this enables cross-tenant data injection/corruption — satisfying the Critical "cross-tenant access" impact class.

### Likelihood Explanation
Any user who can install the app on a shop they control (a normal unprivileged action, not requiring `api_secret_key` or any privileged credential) can capture a valid `(body, hmac)` pair from a real webhook delivery to their own shop and replay it directly to the app's public webhook endpoint with a forged `shop-domain` header. No secret material, TLS interception, or social engineering is needed — only the ability to POST an HTTP request with attacker-chosen headers, which is standard for any internet client hitting a public webhook URL.

### Recommendation
Bind the shop identity into the value that is actually verified. Concretely:
- Include the `shop-domain` (and ideally `topic`/`webhook_id`) header value in the signable content used by `Webhooks::Request#to_signable_string`, matching what Shopify actually signs, if Shopify includes shop in its HMAC computation for webhooks; or
- If Shopify's HMAC is body-only by design, `Registry.process` (or the gem's documentation) must require/perform an independent authoritative check that the `shop-domain` header corresponds to a shop with an active, verified installation before handing it to the handler, rather than passing the raw unauthenticated header straight into `WebhookMetadata`.
- At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted as a tenant key without additional verification (e.g., cross-checking against the app's own list of installed shops) — because the current API surface (`Registry.process` → `WebhookMetadata`) makes it easy for host apps to conflate the signed body with the unsigned shop header.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (no privileged credentials required).
2. Shopify delivers a real webhook to the app, e.g. `POST /webhooks` with body `{"id":1,"note":"hi"}`, headers:
   - `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Topic: orders/create`
3. Attacker captures this raw request, then replays it to the same endpoint, keeping the body and `X-Shopify-Hmac-Sha256` identical, but changing the header to:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
4. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/utils/hmac_validator.rb:13-22` computes the HMAC over `to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`), which is unchanged (`raw_body` untouched) — validation succeeds.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the handler with `WebhookMetadata.new(... shop: request.shop ...)`, where `request.shop` now returns `"victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/request.rb:20-23`).
6. The handler acts on attacker-controlled body content believing it originated from `victim-shop.myshopify.com`.
