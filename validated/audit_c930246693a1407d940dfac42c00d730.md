### Title
Webhook HMAC only signs the request body, allowing shop/topic/metadata header spoofing across tenants - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content solely from the raw body (`to_signable_string` returns `@raw_body`), while the `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers and never included in the signed payload. `Registry.process` validates only that HMAC before handing these header-derived, unauthenticated values to the app's webhook handler as `WebhookMetadata`, which apps rely on to identify the tenant (shop) that the event belongs to.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` calls `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` value [1](#0-0) . For webhooks, `Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` decodes the `X-Shopify-Hmac-Sha256`/`shopify-hmac-sha256` header [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from other headers (`shopify-shop-domain`, `shopify-topic`, etc.) and are never part of the signed bytes [3](#0-2) .

`Registry.process` verifies only `Utils::HmacValidator.validate(request)` (i.e., the body signature) and then constructs `WebhookMetadata` directly from `request.topic`, `request.shop`, `request.webhook_id`, and `request.api_version` — all unauthenticated header values — before invoking the app's handler [4](#0-3) .

This breaks the intended equality: `shop asserted by the HMAC-signed request == shop delivered to the app's webhook handler`. In reality only the body is authenticated; the shop (tenant) claim is parsed but never verified.

The documentation explicitly tells app developers to trust `data.shop` as "The shop domain of the webhook" and use it to dispatch/store per-tenant work (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [5](#0-4) . Every app built on this gem's documented pattern inherits the same cross-tenant confusion.

### Impact Explanation
Because every shop running the same app shares the same `api_secret_key`, an attacker who controls their own shop (a legitimate, unprivileged installer of the app) can capture a validly-signed `(raw_body, hmac)` pair for content they fully control (for instance, by registering their own HTTP webhook endpoint and receiving Shopify's real delivery, or by using `ShopifyAPI::Webhooks::Registry` themselves to trigger topics with attacker-influenced body content on their own store). They can then replay that exact `raw_body` + `hmac` header pair directly against the target app's public webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) header with a victim shop's domain. Since none of those fields are covered by the signature, `Utils::HmacValidator.validate` still passes, and the app's handler receives `WebhookMetadata` claiming to be from the victim shop. Any app that uses `data.shop` to look up the shop's session/access token, store data keyed by shop, or make authenticated calls on the victim's behalf (the pattern the docs recommend) processes attacker-controlled data under the victim's tenant identity — a cross-tenant data-integrity/confusion issue reachable by any unprivileged app-installer, with no need for TLS interception, credential theft, or the app's `api_secret_key`.

### Likelihood Explanation
Moderate-to-high: exploitation requires only that the attacker install the same public app on their own shop (a normal, unprivileged action) and understand the documented webhook processing flow. No secrets need to be extracted; the attacker legitimately possesses one valid `(body, hmac)` pair for content they control, and header spoofing to a plain HTTP POST endpoint requires no special privilege.

### Recommendation
Include the security-relevant metadata (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed payload, or otherwise cryptographically bind them to the raw body before trusting them (e.g., have `to_signable_string` incorporate the shop/topic/webhook_id alongside the body, matching how `AuthQuery#to_signable_string` binds `shop`, `state`, etc. into its signature [6](#0-5) ). At minimum, document prominently that `WebhookMetadata#shop`/`topic`/`webhook_id`/`api_version` are NOT authenticated by the HMAC check and must not be trusted for tenant-identification without additional verification (e.g., cross-checking against the shop stored for the currently active session/subscription).

### Proof of Concept
1. App installs the same public app on attacker's own shop `attacker.myshopify.com` and on the victim's shop `victim.myshopify.com` (same `api_secret_key` shared by the app across all installs).
2. Attacker registers/receives (or otherwise obtains) a legitimate webhook delivery to their own endpoint for a topic/body they can influence, capturing the raw `body` bytes and the corresponding `X-Shopify-Hmac-Sha256` header — this is a validly signed `(body, hmac)` pair.
3. Attacker sends a request to the target app's public webhook route with the same `body` and same `hmac` header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and adjusts `X-Shopify-Topic`/`X-Shopify-Webhook-Id` as desired).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the hmac and passes [7](#0-6) .
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: attacker_controlled_body, ...)` [8](#0-7) , and any app logic keyed on `data.shop` (as the docs recommend) now operates on attacker-controlled data under the victim's tenant identity.
