### Title
Escrow credited with nominal order amount instead of actual balance increase for fee-on-transfer/non-standard tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits escrow using the requested/nominal input amount (minus protocol fee) rather than the amount actually received by the contract, unlike the mainline EVM implementation which was patched to measure the real balance delta.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the non-predispatch branch of `placeOrder` performs: [1](#0-0) 
```solidity
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {
            ...
        } else {
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
        }
        // Store reduced amount (after protocol fees) in escrow
        _orders[commitment][token] += reducedInputs[i].amount;
        ...
    }
}
```
`reducedInputs[i].amount` is derived purely from `order.inputs[i].amount` (the amount the user *claims* to transfer) reduced only by the protocol fee basis points — it is never checked against the actual contract balance delta caused by `safeTransferFrom`. For a fee-on-transfer ERC20 (or any token whose `transferFrom` delivers less than the requested amount, e.g. via internal fees, rebasing, or blacklists), the gateway will hold strictly less than `_orders[commitment][token]` records as escrowed for that order.

This is precisely the bug class described in the referenced report (C4 M-13, FactoryDAO `fundPool`): the contract must remember the balance before the transfer and use the balance delta, not the nominal `amount`, when crediting internal accounting. The mainline EVM contract in this repo was already fixed for exactly this issue: [2](#0-1) 
```solidity
} else {
    ...
    uint256 balBefore = IERC20(token).balanceOf(address(this));
    IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
    order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
}
```
This fix (measuring `balanceOf` before/after and using the delta to compute `order.inputs[i].amount`, which subsequently drives `reducedInputs` and the escrow credit) is entirely absent from the Tron contract's non-predispatch path — the divergent fork regressed the fix that exists in `evm/src/apps/IntentGatewayV2.sol`.

### Impact Explanation
`_orders[commitment][token]` is the shared per-order escrow ledger that backs solver payouts on `RedeemEscrow` and refunds on `RefundEscrow`/cancellation. If the recorded escrow balance for a token systematically exceeds the contract's real token balance (because fee-on-transfer/non-standard tokens deliver less than the nominal amount), the sum of all outstanding order escrow claims can exceed the actual token balance held by `IntentGatewayV2`. Any solver or user who redeems/cancels an order whose escrow ledger is over-credited will be paid out of the pooled balance, effectively draining funds that back *other* unrelated legitimate orders — a direct theft/insolvency vector against other users' escrowed funds, not merely the depositor's own loss. This satisfies "concrete theft ... of funds" via unauthorized draining of shared escrow.

### Likelihood Explanation
Reachable by a single unprivileged `placeOrder` transaction using any ERC20 token that is fee-on-transfer, deflationary/rebasing, or otherwise delivers less than the requested `amount` on `transferFrom` — no privileged role, governance, or malicious admin is required. The gateway does not restrict `order.inputs[i].token` to a token allow-list in this code path, so any user can select an arbitrary ERC20 as input. Given many chains (and Tron/TRC20 ecosystems especially) host fee-on-transfer and non-standard tokens, likelihood is realistic and directly exploitable by an ordinary depositor.

### Recommendation
Apply the same balance-snapshot pattern already used in `evm/src/apps/IntentGatewayV2.sol` to the Tron variant: capture `IERC20(token).balanceOf(address(this))` before `safeTransferFrom`, compute the actual received amount as the post-transfer balance delta, and use that measured amount — not the nominal `order.inputs[i].amount` — as the basis for `reducedInputs` and the `_orders[commitment][token]` escrow credit, for both the predispatch and non-predispatch code paths.

### Proof of Concept
1. Attacker deploys/uses a fee-on-transfer ERC20 `FOT` (e.g., 50% transfer fee) as `order.inputs[0].token` with `amount = 1000e18`.
2. Attacker calls `placeOrder` on the Tron `IntentGatewayV2`. `safeTransferFrom(msg.sender, address(this), 1000e18)` executes, but the contract only actually receives `500e18` of `FOT` due to the transfer fee.
3. `reducedInputs[0].amount` is computed from the nominal `1000e18` (minus protocol fee, if any), and `_orders[commitment][FOT] += reducedInputs[0].amount` credits roughly `1000e18` (or `1000e18` minus protocol fee) to escrow — double what the contract actually holds.
4. When a solver fills the order and redeems escrow (`RedeemEscrow`), or the order is cancelled/refunded, the contract attempts to pay out the recorded escrow amount, which exceeds the actual `FOT` balance contributed by this order, drawing on `FOT` balance escrowed for other legitimate orders and depleting the shared pool — a theft of funds from other users' orders.
