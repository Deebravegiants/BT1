### Title
Unsigned-origin arbitrary runtime call dispatch via attacker-controlled `message.from` in hyper-fungible-token cross-chain calldata - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`Pallet::on_accept` in the `hyper-fungible-token` ISMP module decodes an ABI-encoded `Message` (with fully attacker-controlled `from`, `to`, `amount`, `data` fields) from an incoming `PostRequest` body, and if `data` carries a SCALE-encoded `SubstrateCalldata`, it dispatches the embedded `RuntimeCall`. When `SubstrateCalldata.signature` is `None`, the dispatch origin is derived directly from the attacker-controlled `message.from` bytes with no cryptographic proof that the caller controls that account, allowing arbitrary-origin, arbitrary-call dispatch. [1](#0-0) 

### Finding Description
`on_accept` authenticates only that the *source contract address* (`source`, `from` at the ISMP transport layer) maps to a registered asset via `ContractToAsset`: [2](#0-1) 

It then ABI-decodes the request `body` into an application-level `Message` struct whose `from` field is an arbitrary `bytes` value chosen by whoever calls the source-chain gateway contract — it is not the msg.sender captured by consensus/state proofs, just a payload field: [3](#0-2) 

If `message.data` is non-empty, the pallet SCALE-decodes it as `SubstrateCalldata { signature: Option<Vec<u8>>, runtime_call: Vec<u8> }`: [4](#0-3) [5](#0-4) 

When `signature` is `Some(..)`, the code verifies it against `(nonce, runtime_call)` for the `beneficiary` account (derived from `message.to`), correctly binding the call to a specific signer: [6](#0-5) 

But when `signature` is `None`, the code falls back to deriving the dispatch origin from `message.from` with **no signature check at all**: [7](#0-6) 

It then decodes the raw `runtime_call` bytes into `T::RuntimeCall`, checks only the runtime's generic `BaseCallFilter`, and dispatches it as `RawOrigin::Signed(origin)`: [8](#0-7) 

Because `message.from` is an unauthenticated, attacker-chosen payload field (unlike `PostRequest.from`, which is authenticated by the ISMP consensus/state proof), any account holding a small amount of the bridged token on the source chain (or even zero, if `amount = 0` is accepted) can craft a cross-chain transfer whose `data` field encodes an arbitrary `RuntimeCall` and sets `from` to any victim's 20/32-byte account identifier. On delivery, `pallet-ismp`'s trustless `handle_unsigned` extrinsic (reachable by any relayer with a valid state/consensus proof of the source-chain event — the routing, message decoding and delivery framework this analog targets) invokes this module's `on_accept`, which dispatches the attacker's call as if the victim account had signed it. This is effectively unvalidated deserialization of untrusted, attacker-controlled application data (`Message`, `SubstrateCalldata`, and finally `T::RuntimeCall`) driving privileged execution — the same bug class as the ureport2 CVE, where untrusted external data feeding a deserialization path led to arbitrary code execution, except here it manifests as arbitrary *dispatchable* execution under a forged, unauthenticated signer.

### Impact Explanation
An attacker can dispatch any runtime call filtered only by `BaseCallFilter` (transfers, staking operations, asset burns/mints, governance-adjacent calls not blocked by the filter, etc.) as `RawOrigin::Signed(<any account>)`. This permits theft of funds from arbitrary accounts (e.g., dispatching `Balances::transfer_all` or asset transfers out of a victim's account) and unauthorized app actions network-wide, since the origin is fully forgeable. This satisfies the "unauthorized app action" / "concrete theft of funds" acceptance criteria.

### Likelihood Explanation
Reachable from a single, permissionless cross-chain post: any address able to call the source-chain HyperFungibleToken/WrappedHyperFungibleToken gateway contract (typically unpermissioned, requiring only token approval) can set `data` to a crafted `SubstrateCalldata` with `signature = None` and `from` = victim bytes, then have any relayer deliver it via `pallet-ismp`'s standard, fee-free `handle_unsigned` path. No special privileges, validator collusion, or malicious-admin assumptions are required — this is directly reachable by an ordinary bridge user/relayer.

### Recommendation
Require a valid signature (bound to the target account and its `data`) for every dispatched `runtime_call`, removing the unsigned fallback branch entirely, or if an unsigned convenience path is intentionally desired, restrict its origin strictly to the ISMP-authenticated `PostRequest.from`/`source` identity (never to the attacker-supplied `message.from` field) so a caller cannot impersonate arbitrary accounts.

### Proof of Concept
1. Attacker holds/acquires the bridged token on the EVM source chain and calls the `HyperFungibleToken` gateway with `Message{ from: <victim_account_bytes>, to: <attacker_or_any>, amount: <any>, data: SubstrateCalldata{ signature: None, runtime_call: SCALE-encode(Balances::transfer_all(dest: attacker)) }.encode() }`.
2. Any relayer submits the resulting ISMP `PostRequest` with a valid state/consensus proof to the destination chain via `pallet_ismp::Call::handle_unsigned` (an unsigned, fee-free extrinsic reachable by anyone) — see `handle_unsigned` at [9](#0-8) 
3. `Pallet::on_accept` decodes the message, sees no signature, sets `origin = EvmToSubstrate::convert(H160::from(victim_bytes))`, decodes `runtime_call`, and dispatches it as `RawOrigin::Signed(victim)`. [10](#0-9) 
4. The victim's assets are moved/transferred without their consent or any cryptographic proof of authorization.
