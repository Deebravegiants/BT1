### Title
Permanent market freeze from RAY-value overflow before the borrow-index cap - (File: common/src/rates/simulate.rs)

### Summary

A sufficiently large borrowed position can make `borrowed * borrow_index` exceed `i128::MAX` before `borrow_index` reaches its configured `1e36` ceiling. Once that happens, every market operation that accrues interest reverts, permanently preventing repayment, withdrawal, liquidation, index updates, and recapitalization for that market. This is a Medium-severity permanent-freezing-of-funds analogue to the reported memory-safety/unchecked-arithmetic class.

### Finding Description

Interest accrual begins each chunk by unscaling both market totals. `accrue_step` calls `scaled_to_original` on `borrowed` and `supplied` before calculating utilization or updating the indexes. [1](#0-0) 

`scaled_to_original` performs a checked fixed-point multiplication and panics on overflow. [2](#0-1) 

The later call to `update_borrow_index` clamps the index only after multiplying it by the interest factor, so the index ceiling does not protect the earlier `borrowed * borrow_index` multiplication. [3](#0-2) 

`MAX_BORROW_INDEX_RAY` is `1e36`, but `i128::MAX` is only about `1.70e38`. Therefore a market with roughly `1e36` RAY of scaled debt overflows once the borrow index exceeds approximately `170`, far below the `1e36` index cap. [4](#0-3) 

`global_sync` runs this accrual loop before the mutating operation can proceed and does not catch or recover from the panic. [5](#0-4) 

### Impact Explanation

Once `scaled_to_original(borrowed, borrow_index)` overflows, `repay`, `withdraw`, `liquidate`, `update_indexes`, `flash_loan`, and `recapitalize` cannot touch the affected market because their pool paths load and accrue market state first. [6](#0-5) 

The pool retains the underlying token balance, but suppliers cannot withdraw it, borrowers cannot repay it, and liquidators cannot liquidate the debt. Other users cannot bypass the failure by direct token transfers to the pool because accounting state remains stale and every subsequent accrual repeats the same multiplication.

Because the stored state does not advance past the failing multiplication, there is no in-protocol recovery path shown for an unprivileged user. This qualifies as permanent freezing of user funds and a market unable to operate despite holding token funds.

### Likelihood Explanation

The trigger requires a very large market: enough scaled debt that ordinary index growth makes its RAY value exceed `i128::MAX`. A single unprivileged address can create the necessary state through `supply` and `borrow` if the deployed spoke caps, collateralization, token supply, and available liquidity permit it. [7](#0-6) 

After the position exists, any caller can advance the market into the failing state through the normal `update_indexes` path once sufficient time has elapsed. No malicious token, oracle manipulation, privileged action, leaked key, reentrancy, or invalid parameter is required at the trigger point; the overflow is produced by ordinary bounded index growth over a previously admitted book.

The capital requirement and elapsed-time requirement reduce practical likelihood, but the impact applies to all suppliers in the market rather than only the attacker.

### Recommendation

Bound the unscaled values before multiplying, rather than letting `scaled_to_original` panic.

In `accrue_step`, compare `borrowed` and `supplied` against `i128::MAX / index` or use a saturating/widened market-total calculation before utilization is calculated. If the intended terminal behavior is the index cap, detect that `borrow_index` has reached `MAX_BORROW_INDEX_RAY` and short-circuit accrual before unscaling market totals.

The entry-side caps should also account for future index growth. A safe bound needs `scaled_amount * maximum_reachable_index <= i128::MAX`, not merely `scaled_amount <= i128::MAX`; otherwise an initially valid position can become permanently unprocessable through time-based index growth.

### Proof of Concept

Conceptual transaction sequence:

1. User calls controller `supply` with `account_id = 0`, the target `spoke_id`, and `assets = [(hub_asset, very_large_amount)]`. At `18` decimals, `1_000_000_000` whole tokens produce approximately `1e36` scaled RAY at index `RAY`. [8](#0-7) 
2. The same or another unprivileged account supplies enough collateral and calls `borrow` for `borrows = [(hub_asset, debt_amount)]`, keeping utilization high but within the configured maximum. [9](#0-8) 
3. Time elapses while the debt accrues. Once `borrow_index` exceeds approximately `i128::MAX / borrowed_scaled`, utilization calculation overflows before `update_borrow_index` can clamp the next index. [10](#0-9) 
4. Anyone calls `update_indexes` for the market. `global_sync` invokes `accrue_chunk`, which invokes `accrue_step` and panics inside `scaled_to_original`. [11](#0-10) 
5. Subsequent `repay`, `withdraw`, or `liquidate` calls fail for the same reason because they must accrue the market before applying their respective mutation.

```rust
pub fn accrue_step(
    env: &Env,
    params: &MarketParams,
    borrowed: Ray,
    supplied: Ray,
    borrow_index: Ray,
    supply_index: Ray,
    delta_ms: u64,
) -> AccrualStep {
    let borrowed_original = scaled_to_original(env, borrowed, borrow_index);
    let supplied_original = scaled_to_original(env, supplied, supply_index);
    let util = utilization(env, borrowed_original, supplied_original);
    let borrow_rate = calculate_borrow_rate(env, util, params);
    let interest_factor = compound_interest(env, borrow_rate, delta_ms);

    let new_borrow_index = update_borrow_index(env, borrow_index, interest_factor);

    let (supplier_rewards, protocol_fee) =
        calculate_supplier_rewards(env, params, borrowed, new_borrow_index, borrow_index);
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);
```
