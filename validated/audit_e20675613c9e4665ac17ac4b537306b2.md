### Title
HTTP action response cache key omits mTLS client-certificate identity, allowing an mTLS-authenticated response to be served to a different, unauthenticated/differently-identified request - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The gateway's HTTP action response cache stores responses keyed by `req.Hash()`, which is documented and tested to be derived from method, URL, headers, body, and `WorkflowOwner` only. `WorkflowID` is explicitly excluded from the hash (confirmed by test), and the `Mtls` credential field used to authenticate the outbound request to the external endpoint is not part of the identity used for cache storage/lookup either. This mirrors the reported bug class ("funds/response sent to the wrong recipient because the code uses the wrong identity for routing") applied here to a cached HTTP response being handed back to a request context whose identity differs from the one that originally produced it.

### Finding Description
`sendResponseToNode`/`makeOutgoingRequest`/`Fetch` treats a cache hit as safe to return to *any* subsequent request that hashes to the same key [1](#0-0) . The cache key is computed purely from `req.Hash()` [2](#0-1) , and the handler's `send` function branches on `req.Mtls` to decide whether the outbound call is made with a client certificate (an authenticated, per-workflow-owner identity to the external endpoint) or via the shared, unauthenticated default client [3](#0-2) . Because the hash does not include the mTLS certificate/key material, two `OutboundHTTPRequest`s with identical method/URL/headers/body but different (or absent) `Mtls` credentials collapse to the same cache key. A response fetched using one workflow's mTLS identity can be cached and then transparently replayed to a request from a different requester/workflow that does not present that certificate (or presents a different one), since `Set`/`Fetch` never validate that the credential used to populate the cache matches the credential of the request reading it [4](#0-3) .

The project's own documentation and code comments show the team is aware that authenticated (mTLS) responses must not leak across requesters — e.g. "we don't accidentally leak auth'd connections to other users" and the dedicated test asserting the default client is never used for mTLS flows [5](#0-4) [6](#0-5) . However, that protection only covers the live HTTP connection layer; it does not extend to the response cache, which sits above `send()` and is unaware of `Mtls`.

Additionally, the README explicitly claims "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [7](#0-6) , but the actual `Hash()` behavior is tested to be workflow-ID-independent (only `WorkflowOwner` matters) [8](#0-7) , confirming the code diverges from its documented isolation guarantee and that the actual isolation boundary (owner, not workflow, and not credential) is weaker than intended.

### Impact Explanation
If an external endpoint returns different, sensitive content depending on the client TLS certificate presented (a common mTLS use-case — endpoint identifies caller by cert and returns caller-specific data), a workflow lacking the correct certificate could receive a cached response that was originally fetched using another workflow's/owner's mTLS-authenticated identity, and vice versa. This is a cross-user/cross-workflow response confusion analogous to the JOJO bug where excess funds went to the wrong recipient because the routing key (`to`) didn't match the actual party that should receive them — here the routing key (`req.Hash()`) doesn't reflect the actual authentication identity (`Mtls`) under which the response was obtained.

### Likelihood Explanation
Exploitability requires: (1) two `OutboundHTTPRequest`s with identical method/URL/headers/body but differing `Mtls` credentials or workflow identity beyond `WorkflowOwner`, and (2) `CacheSettings.Store`/`MaxAgeMs` set so the cache is used, and (3) the target endpoint actually varying its response by client certificate. Requests are constructed by workflow (capability) nodes already inside the DON, not directly by end users, which somewhat narrows the practical attack surface to workflow-level actors sharing the gateway's cache rather than a fully external unauthenticated caller. This makes the issue more of a workflow-isolation defect than a straightforward external-attacker takeover, and I could not confirm from the available index whether `Mtls` is populated from end-user-controlled workflow configuration reachable without operator involvement, or whether such certificate-dependent endpoints are used in practice.

### Recommendation
Include a representation of the `Mtls` credential (e.g., a hash of the certificate, or nothing/deny-caching when `Mtls` is set) and align the cache key with the documented isolation unit (`WorkflowID`, not just `WorkflowOwner`) in `req.Hash()`/`responseCache`. At minimum, bypass the cache entirely whenever `req.Mtls != nil`, and update the README claim to match actual behavior, or fix `Hash()` to incorporate `WorkflowID` as documented.

### Proof of Concept
Not independently reproducible from the indexed code alone — the `Hash()` implementation lives in `chainlink-common`'s `gateway.OutboundHTTPRequest` type, which is outside this repo's index, so I could not directly inspect its exact field list to confirm `Mtls` is excluded; this is inferred from the test suite (`response_cache_test.go`) which only asserts hash stability against `CacheSettings`/`WorkflowID` and hash difference for `WorkflowOwner`, with no test covering `Mtls` at all. A Devin session with access to the `chainlink-common` module and the ability to run `go test ./core/services/gateway/handlers/capabilities/v2/...` could confirm this by writing a table test with two requests identical except for `Mtls`, asserting whether `Hash()` differs.

func (h *gatewayHandler) send(ctx context.Context, httpReq network.HTTPRequest, req gateway_common.OutboundHTTPRequest) (*network.HTTPResponse, error) {
	if req.Mtls == nil {
		return h.httpClient.Send(ctx, httpReq)
	}

	if h.httpClientFactory == nil {
		return nil, errors.New("nil http client factory, cannot make mtls request")
	}

	// Instantiate a throwaway HTTP client with the provided Mtls client certificate provided.
	// We do this to ensure that we don't accidentally leak auth'd connections to other users.
	// Note: this isn't a DOS vector because
	// a) we have a global rate limit above which limits abuse
	// b) we apply rate limits limiting the ability of sending nodes to spam requests
	// c) we apply per-owner rate limits in the action capability in the
	// workflow node limiting the ability of users to abuse this flow by spamming Mtls requests.
	// The client enforces the mtls concurrency limit internally (on the request's
	// capped-timeout context) before delegating to the underlying transport.
	client, err := h.httpClientFactory(network.HTTPClientConfig{
		Mtls: &gateway_common.MtlsAuth{
			PrivateKey:  req.Mtls.PrivateKey,
			Certificate: req.Mtls.Certificate,
		},
		ConcurrencyLimiter: h.mtlsConcurrencyLimiter,
	})
	if err != nil {
		return nil, fmt.Errorf("failed to instantiate http client for mtls request: %w", err)
	}

	// We don't have access to the org here, so this will fall back to the environment default (=false).
	// That's appropriate because all fields set on the request come from untrusted nodes.
	// The capability separately applies an org-specific check.

	// Note: we intentionally consume the rate-limit after instantiating the client so that a malicious user
	// can't send requests with invalid mtls credentials and thus cheaply consume global tokens.
	if !h.mtlsRequestRateLimiter.Allow(ctx) {
		return nil, fmt.Errorf("global mtls request rate limit exceeded: %w", network.ErrBlockedRequest)
	}

	return client.Send(ctx, httpReq)
}

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}

// TestGatewayHandler_Send_MtlsRoutesThroughCallbackOnly_DefaultClientUntouched
// verifies that an mTLS request flowing through the full callback path does not
// touch the default (shared) http client even when the factory returns a working
// client. This is the core property that prevents auth'd connections from
// leaking between users.
func TestGatewayHandler_Send_MtlsRoutesThroughCallbackOnly_DefaultClientUntouched(t *testing.T) {
	handler := createTestHandler(t)
	handler.mtlsRequestRateLimiter = limits.GlobalRateLimiter(100, 100)

	httpReq := network.HTTPRequest{Method: "GET", URL: "https://example.com/api", Timeout: 5 * time.Second}
	outboundReq := gateway_common.OutboundHTTPRequest{
		Method: "GET",
		URL:    "https://example.com/api",
		Mtls:   &gateway_common.MtlsAuth{PrivateKey: []byte("k"), Certificate: []byte("c")},
	}

	mtlsClient := httpmocks.NewHTTPClient(t)
	mtlsClient.EXPECT().Send(mock.Anything, mock.Anything).
		Return(&network.HTTPResponse{StatusCode: 200, Body: []byte("body")}, nil).Once()
	handler.httpClientFactory = func(config network.HTTPClientConfig) (network.HTTPClient, error) {
		return mtlsClient, nil
	}

	callback := handler.createHTTPRequestCallback(t.Context(), "req-id", httpReq, outboundReq)
	resp := callback()
	require.Empty(t, resp.ErrorMessage)
	require.Equal(t, 200, resp.StatusCode)
	require.Equal(t, []byte("body"), resp.Body)

	mockDefault := handler.httpClient.(*httpmocks.HTTPClient)
	mockDefault.AssertNotCalled(t, "Send", mock.Anything, mock.Anything)
}

### 3.2 Caching Behavior

- **Cacheable Responses**: 2xx (success) and 4xx (client error) status codes.
