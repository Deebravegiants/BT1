## Title
Unguarded `send()` in `WrappedHyperFungibleToken` allows re-entrant/fee-on-transfer token abuse leading to unbacked cross-chain dispatch - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

## Summary
`WrappedHyperFungibleToken.send()` pulls the configured `_underlying` ERC-20 via `safeTransferFrom` and then unconditionally dispatches a cross-chain message carrying `params.amount` as the locked/backing amount, without a reentrancy guard and without verifying how many tokens were actually received. This is the same root-cause class as the referenced SizeSealed report: a token whose transfer path can invoke a callback on the sender *before* balances are finalized (ERC777 `tokensToSend`, or any fee-on-transfer/deflationary token) lets an attacker escrow/claim more value in cross-chain messages than what the contract actually holds.

## Finding Description
`send()` does the following, with no `nonReentrant` guard: [1](#0-0) 

It calls `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` and then builds the `DispatchPost` body using the caller-supplied `params.amount` directly, never re-checking the contract's actual token balance delta. Compare this to `IntentGatewayV2.placeOrder`, which explicitly measures `balBefore`/`balAfter` around `safeTransferFrom` precisely to defend against fee-on-transfer tokens: [2](#0-1) 

That defensive pattern is absent in `WrappedHyperFungibleToken.send()`. If `_underlying` is configured (via `configure()`) as an ERC777-style token or any token with pre-transfer hooks/deflationary transfer semantics, two problems compound:

1. **No balance verification**: for a token that burns/deducts a fee during transfer (as in the SizeSealed PoC's `TaxERC777`), `send()` will still dispatch a message claiming the full `params.amount` was locked, even though the contract received less. Any peer/destination logic (or this same contract's `onAccept` on other deployments) that unlocks/mints based on `message.amount` will over-issue relative to actual collateral.
2. **No reentrancy guard**: ERC777's `_send` internally invokes `_callTokensToSend` on the `from` address *before* moving the balance. Since `send()` has no lock (unlike `IntentGatewayV2.placeOrder`, which is `nonReentrant`), a malicious `msg.sender` contract registered as its own `ERC777TokensSender` can re-enter `send()` from within that hook — before the first transfer's balance effects are settled — and dispatch a second `Sent` message. Both messages assert collateral against a shared/overlapping balance the contract has not yet fully received, exactly mirroring how the SizeSealed PoC created two auctions whose combined `totalBaseAmount` exceeded the actual `SizeSealed` token balance.

`onAccept` on the receiving side blindly trusts `message.amount` from the decoded body and transfers/unlocks that exact value: [3](#0-2) 

There is no reconciliation anywhere in this contract between what was actually locked in `send()` and what gets unlocked in `onAccept`/`onPostRequestTimeout`.

## Impact Explanation
This breaks the fundamental lock/mint (or lock/unlock) invariant of the token bridge: the sum of cross-chain messages' claimed amounts can exceed the collateral actually escrowed in `WrappedHyperFungibleToken`. This is an unbacked-mint / permanent-freezing-of-funds condition — later legitimate `onAccept` calls for other users will attempt to pay out from an underlying balance that has already been drained relative to what was promised, causing either direct fund theft by the attacker (double-claimed value) or permanent freezing of other users' funds when the pool is insufficient.

## Likelihood Explanation
The owner-controlled `configure()` function allows setting `_underlying` to any ERC20-compatible token, including ones with non-standard transfer semantics (fee-on-transfer, rebasing, ERC777-with-hooks). The codebase itself acknowledges this token category is expected/supported, since `IntentGatewayV2.placeOrder` already implements the balance-delta defense for exactly this reason. `WrappedHyperFungibleToken.send()` lacking the equivalent guard and lacking any `nonReentrant` modifier makes this a straightforward, single-transaction exploit for any unprivileged user who bridges such a token (whether the token was already non-standard, or the attacker registers an ERC1820 hook on an ERC777-based underlying).

## Recommendation
1. Add a reentrancy guard (`nonReentrant`, already used in `IntentGatewayV2.sol`) to `send()`.
2. Mirror `IntentGatewayV2.placeOrder`'s pattern: measure `balanceOf(address(this))` before and after `safeTransferFrom`, and dispatch the message using the actual received delta rather than the caller-supplied `params.amount`.

## Proof of Concept
Following the structure of the referenced SizeSealed PoC:
1. Deploy an ERC777-compatible token (e.g., `TaxERC777` from the report) as `_underlying` via `configure()`.
2. Deploy an attacker contract, register it via `ERC1820Registry.setInterfaceImplementer(attacker, keccak256("ERC777TokensSender"), attacker)`.
3. Attacker approves `WrappedHyperFungibleToken` for a large allowance and calls `send()`.
4. Inside the token's `_send` → `_callTokensToSend` hook (fired on the attacker as `from`, before balance is debited), the attacker re-enters `send()` with a second `SendParams`, causing a second `safeTransferFrom` and a second `DispatchPost`/`Sent` event before the first transfer's balance effects have settled.
5. Assert: `sum(message.amount across both Sent events) > IERC20(_underlying).balanceOf(address(wrappedToken))`, demonstrating that cross-chain claimed value exceeds actual locked collateral — analogous to `auction1_amount + auction2_amount > auction_balance` in the original report.

        uint256 msgValue = msg.value;

            msgValue = msgValue - params.amount;

        } else {
            commitment = dispatchWithFeeToken(request);
        }

        emit Sent({
            from: msg.sender,
            to: params.to,
            dest: string(params.dest),
            amount: params.amount,

        });

            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of

                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
