### Title
Cross-user response hijacking via attacker-controlled `MessageID` collision in `WebAPIHandler.HandleLegacyUserMessage` - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The gateway's legacy WebAPI trigger handler stores the caller's response callback in a shared map keyed solely by the client-supplied `MessageID`, with no uniqueness check and no binding to the requesting session/sender. An unprivileged client can submit a request using the same `MessageID` as another user's in-flight request, silently overwriting that user's callback entry. When the DON later responds for that `MessageID`, the response is delivered to the attacker's callback instead of the original requester's, resulting in cross-user response confusion (leakage of another user's job/capability result).

### Finding Description
`gateway.ProcessRequest` (`core/services/gateway/gateway.go`) is the internet-facing entry point; for legacy DON-ID requests it calls `h.HandleLegacyUserMessage(ctx, msg, callback)` where `msg` is decoded directly from the untrusted client payload [1](#0-0) . The message's `MessageID` comes straight from the client-controlled JSON-RPC request ID / message body (`m.Body.MessageID = req.ID` in `ValidatedMessageFromReq`) [2](#0-1) .

Inside `handler.HandleLegacyUserMessage`, the callback is registered unconditionally, overwriting any existing entry with the same key:

```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageID] = &savedCallback{id: msg.Body.MessageID, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [3](#0-2) 

There is no check for an existing in-flight entry for that `MessageID` (unlike the newer `httpTriggerHandler.setupCallback`, which explicitly rejects duplicate request IDs with `jsonrpc.ErrConflict`) [4](#0-3) .

When a node's response later arrives, it is routed purely by `MessageID`:

```go
h.mu.Lock()
savedCb, found := h.savedCallbacks[msg.Body.MessageID]
delete(h.savedCallbacks, msg.Body.MessageID)
h.mu.Unlock()

if found {
    // Send first response from a node back to the user, ignore any other ones.
    codec := api.JSONRPCCodec{}
    return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
}
``` [5](#0-4) 

Because the map key is entirely attacker-chosen and unauthenticated, and no ownership/session check ties a `MessageID` to the caller who created it, a second unprivileged caller who reuses the same `MessageID` (guessed, observed, or brute-forced) hijacks the callback slot. The first legitimate caller's callback reference is dropped/overwritten; the eventual DON response for that `MessageID` is delivered to whichever caller's callback is currently registered — i.e., the attacker.

This is structurally the same bug class as the PancakeBunny exploit: the system trusts an externally supplied identifier/value (the flash-loaned deposit amount there; the `MessageID` here) as ground truth for accounting/dispatch without validating it belongs to the entity presenting it, letting an unprivileged actor corrupt shared state to redirect value (funds there, a privileged response payload here) to themselves.

### Impact Explanation
An unprivileged HTTP client of the gateway can:
- Cause denial of service for another user's in-flight `web_api_trigger` request (their callback is evicted and never resolves other than by timeout).
- Receive the DON's response payload intended for another user's request, causing cross-user response confusion and potential disclosure of another workflow's trigger/execution result data through the gateway.

This satisfies the "cross-user response confusion" acceptance criterion. Because the callback map is also unbounded in the sense that any string is accepted as a key (up to the `len > 200` cutoff enforced earlier in `gateway.ProcessRequest`), the attack surface is any external client able to reach the gateway's legacy JSON-RPC/DON-ID endpoint.

### Likelihood Explanation
Likelihood is limited by requiring the attacker to know or predict a `MessageID` in use by a victim within the callback's TTL (`CallbackMaxAgeSec`, default 120s) [6](#0-5) . If client applications generate `MessageID`s predictably (sequential, timestamp-based, or derived from public workflow/execution identifiers as seen in `getMessageID` for the target capability, which joins `WorkflowExecutionID` and method name) [7](#0-6) , collision is straightforward rather than requiring brute force. Even without prediction, this is exploitable in a race/DoS sense whenever two arbitrary callers happen to choose (or intentionally collide on) the same ID, which the legacy handler does nothing to prevent.

### Recommendation
- Reject `HandleLegacyUserMessage` requests whose `MessageID` already has an active entry in `savedCallbacks`, mirroring the duplicate-ID conflict check already implemented in `httpTriggerHandler.setupCallback`.
- Bind saved callbacks to the authenticated caller/session (or at minimum to a per-connection identifier) rather than trusting the raw client-supplied `MessageID` as the sole lookup key.
- Consider migrating the legacy WebAPI trigger path fully onto the newer `httpTriggerHandler` request/response model, which already implements this protection.

### Proof of Concept
1. Attacker A sends a legacy JSON-RPC request to the gateway's DON-ID endpoint with `MessageID = "X"`, method `web_api_trigger`, targeting some DON; `HandleLegacyUserMessage` stores `savedCallbacks["X"] = callbackA` and fans the request out to DON nodes.
2. Before the DON responds, victim B (independently, or with an ID guessed/observed by the attacker) sends another request also using `MessageID = "X"`; `HandleLegacyUserMessage` overwrites `savedCallbacks["X"] = callbackB` with no conflict check.
3. When the DON node responds for `MessageID = "X"` (satisfying whichever request the nodes actually processed), `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds `callbackB`, and delivers the response payload to B — even if the response actually corresponds to A's original request/payload, or vice versa depending on timing — demonstrating cross-user response confusion caused entirely by trusting an unauthenticated, attacker-controlled `MessageID` as an exclusive routing key.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}

func getMessageID(req capabilities.CapabilityRequest) (string, error) {
	if err := validation.ValidateWorkflowOrExecutionID(req.Metadata.WorkflowID); err != nil {
		return "", fmt.Errorf("workflow ID is invalid: %w", err)
	}
	if err := validation.ValidateWorkflowOrExecutionID(req.Metadata.WorkflowExecutionID); err != nil {
		return "", fmt.Errorf("workflow execution ID is invalid: %w", err)
	}
	messageID := []string{
		req.Metadata.WorkflowExecutionID,
		ghcapabilities.MethodWebAPITarget,
	}
	return strings.Join(messageID, "/"), nil
}
