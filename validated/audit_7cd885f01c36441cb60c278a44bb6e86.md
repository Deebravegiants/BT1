### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, while the shop identity used to route/process the webhook (`x-shopify-shop-domain` header) is taken directly from unauthenticated headers and is never included in the signed content. This breaks the equality "the shop that is HMAC-authenticated" ≠ "the shop the app acts on," letting any user in possession of one validly-signed webhook payload (e.g., a merchant who installed the app on their own store) replay it with a forged `shop-domain` header attributing the event to a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is parsed independently from the `x-shopify-shop-domain`/`shopify-shop-domain` header and is never mixed into the signable string: [2](#0-1) 

`Registry.process` validates only the HMAC of the body via `Utils::HmacValidator.validate(request)`, and then immediately trusts `request.shop` (the unauthenticated header) to build `WebhookMetadata`, which is handed to the app's handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute the signature purely from `verifiable_query.to_signable_string` (the raw body) against the app's single shared `api_secret_key`: [4](#0-3) 

Because a single app (and therefore a single `api_secret_key`) serves many installed shops, and the HMAC only binds the body — not the shop — any party who can obtain one legitimately-signed webhook body/HMAC pair (trivially available to any merchant that installs the app on their own store, since Shopify sends them real webhooks with a valid signature) can resend that exact `raw_body` + `hmac` to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header naming a different tenant. `Registry.process` will accept it (the body-only HMAC still validates) and dispatch it to the handler as if it came from the victim shop. This is exactly the "field acted on but not covered by the HMAC" pattern: the `shop` binding that downstream handlers rely on for tenant isolation is not part of the cryptographic proof.

### Impact Explanation
This breaks the authentication boundary between tenants in a multi-shop app: an unprivileged installer of the app (attacker's own shop) can forge webhook events that the app processes as belonging to a different, victim shop. Depending on the handler's use of `WebhookMetadata#shop` (e.g., creating/updating orders, fulfillments, or triggering side effects keyed by shop), this enables cross-tenant data corruption or unauthorized actions attributed to another merchant's shop — a Critical-class cross-tenant access issue.

### Likelihood Explanation
Likelihood is realistic: the attacker only needs to be a legitimate (even free-tier) installer of the target app to receive at least one authentic webhook with a valid HMAC over some body, then can replay that same body with a modified shop header at will (webhook endpoints are typically public HTTP endpoints with no additional per-request authentication beyond this HMAC check).

### Recommendation
Bind the shop identity into the authenticated material, or verify it independently and consistently:
- Include the shop domain (and any other routing header) in `to_signable_string`, so a change in `shop` invalidates the HMAC, or
- Require callers to independently confirm the `shop` header corresponds to a shop with a valid installation/session before trusting it for any state-changing action, and reject webhooks whose shop cannot be corroborated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a real webhook, e.g. `orders/create`, with body `B` and Shopify-computed `X-Shopify-Hmac-Sha256: H = HMAC(secret, B)`.
2. Attacker resends to the app's webhook endpoint:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: H
   x-shopify-shop-domain: victim-shop.myshopify.com
   <raw body B>
   ```
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches `H` — validation succeeds because `shop` is not part of the signed payload: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)` and performs whatever tenant-scoped action it implements against `victim-shop`, even though the event never originated from that shop.
