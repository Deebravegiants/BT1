### Title
Permanent freeze of curve-raised funds via an unbounded-low `virtualLtReserve` causing `finalizeGraduation` to permanently revert - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._deployAndSeed` only bounds `virtualLtReserve` from **above** (`ExchangeRateTooLow`), never from below [1](#0-0) . Any permissionless creator can launch against a legitimate, already-registered BounceTech LT (`ltExists` gate only checks registration, not price) whose `exchangeRate()` is very large, which drives `virtualLtReserve = VIRTUAL_LIQUIDITY_USD*1e18/exchangeRate` down to a tiny value. Because `Pair.k = TOTAL_SUPPLY * virtualLtReserve` is fixed forever at mint [2](#0-1) , the whole curve — and therefore the real LT amount needed to reach either graduation trigger — becomes vanishingly small. When graduation fires (either the `tokenBalance()==0` sellout trigger or the USD trigger, both computed off this tiny reserve [3](#0-2) ), `_prepareGraduationLiquidity` derives `tokensForLP`/`ltFromPair` as pure ratio arithmetic off the same tiny reserves [4](#0-3) . These cached amounts are then fed unconditionally to the first HyperSwap V2 `pair.mint()` in `_seedDirectMint`/`finalizeGraduation` [5](#0-4) [6](#0-5) . Standard UniswapV2 `mint()` reverts when `sqrt(amount0*amount1) <= MINIMUM_LIQUIDITY (1000)` on the first mint, and `LPLock.recordLock` independently reverts on `amount == 0` [7](#0-6) . Either revert unwinds the *entire* `finalizeGraduation` transaction, including `info.lifecycle = Lifecycle.Graduated` and `delete $.pendingGraduation[tokenAddress]` [8](#0-7) , because Solidity fully reverts state on any downstream revert in the same call.

This is the direct analog of CVE-2024-26845: an item (`LUN_RESET`) is added to a completion-wait list expecting a companion event (the abort's completion) that will never arrive, hanging forever. Here, the token is moved into `Lifecycle.Graduating` — a state that "parks all curve-raised LT and 250M tokens on Bonding" and is only exitable via `finalizeGraduation` — but the deterministic inputs cached at phase 1 guarantee `finalizeGraduation` will *always* hit the same revert on every retry, so the token can never reach `Lifecycle.Graduated`. There is no on-chain recovery path; only a UUPS upgrade by the owner (a privileged, off-protocol action) can rescue it, which for practical purposes on the live proxy means the funds are permanently frozen.

### Finding Description
1. `launch()` accepts any LT registered in BounceTech's `Factory.ltExists` map with no floor on `exchangeRate()` [9](#0-8) .
2. `_deployAndSeed` computes `virtualLtReserve = (VIRTUAL_LIQUIDITY_USD * 1e18) / exchangeRate` and only reverts if it is too **large** (`> type(uint112).max/4`), never if it is too small [10](#0-9) .
3. `Pair.mint` bakes `k = TOTAL_SUPPLY * virtualLtReserve` in permanently (natspec explicitly states this is immutable and never recomputed) [11](#0-10) [12](#0-11) . A tiny `virtualLtReserve` makes `k` tiny, so the real LT needed to move the curve to either graduation trigger (`tokenBalance()==0` or the USD leg, both read off `assetReserve - virtualLtReserve` [3](#0-2) ) is correspondingly tiny.
4. `_prepareGraduationLiquidity` computes `ltFromPair = assetReserve - virtualLtReserve` and `tokensForLP = ltFromPair * tokenReserve / assetReserve`, purely from these tiny stored reserves, with no floor [13](#0-12) .
5. `finalizeGraduation` → `_seedUniswapV2Direct` → `_seedDirectMint` (the ~99% empty-pair happy path) unconditionally calls `IUniswapV2Pair(pair).mint(lpLock)` with these cached, possibly sub-`MINIMUM_LIQUIDITY` amounts [5](#0-4) . Standard UniswapV2 reverts on the first mint whenever `sqrt(amount0*amount1) <= 1000`.
6. Even if `mint()` somehow returns a nonzero-but-degenerate `liquidity`, `LPLock.recordLock` independently reverts with `ZeroAmount` if `amount == 0` [14](#0-13) .
7. Because `finalizeGraduation` is a single atomic call, any revert inside it (the `pair.mint` underflow or `LPLock.recordLock`'s `ZeroAmount`) unwinds `info.lifecycle = Lifecycle.Graduated`, `$.graduatedPair[...]` and `delete $.pendingGraduation[...]` as well [6](#0-5) . The token is left exactly as it was after phase 1: `Lifecycle.Graduating`, with `pendingGraduation` still cached and all the curve-raised LT plus the 250M-token LP reserve already parked inside `Bonding` (moved there by `_prepareGraduationLiquidity`/`Router.graduate` in phase 1). No function exists to re-derive smaller amounts, retry with different inputs, or exit `Lifecycle.Graduating` back to `Curve`/`Graduated` — the lifecycle enum is explicitly "strictly-forward" [15](#0-14) , so every subsequent call to `finalizeGraduation(tokenAddress)` (by anyone, since it's permissionless) recomputes byte-identical inputs from the same frozen `pendingGraduation` and reverts identically, forever.
8. `LPLock.isLocker` is add-only with the natspec explicitly acknowledging that a locker revocation would "brick every in-flight `finalizeGraduation`… no on-chain recovery" [16](#0-15)  — confirming the authors already recognize `recordLock` as a one-shot dependency `finalizeGraduation` cannot skip, but the low-`virtualLtReserve` root cause that can drive `recordLock`'s inputs to zero was not closed.

### Impact Explanation
Once a token enters this state:
- All real LT raised by curve buyers (`ltFromPair`, drained into `Bonding` by `Router.graduate` during phase 1) is permanently stranded inside `Bonding` with no withdrawal function.
- The 250M-token LP reserve (`LP_RESERVE`) is likewise stranded/unusable inside `Bonding`.
- The token can never graduate to a tradable HyperSwap V2 pool; all curve traders' capital and the creator's raised value is permanently frozen (no theft vector needed — it is a permanent freeze of funds, one of the explicitly accepted impact classes).
- Recovery requires a privileged UUPS upgrade by the protocol owner, which is out of scope for an unprivileged actor and does not exist as an on-chain self-service path today.

This satisfies "High" severity: total, permanent, protocol-wide freezing of both trader and creator funds triggered by a fully permissionless launch parameter (choice of LT).

### Likelihood Explanation
Reaching this state requires only:
1. Launching a token (`Zap.createToken`/`Bonding.launch`) against any BounceTech LT that is already registered (`ltExists`) but happens to have a high `exchangeRate()` (e.g., an LT that has been running/accruing for a long time, or one deliberately deployed by the same or a colluding creator with a high initial rate — LT deployment is BounceTech's own permissionless process and outside `Bonding`'s control, so `Bonding` cannot assume a "reasonable" rate range).
2. Trading normally (or the creator's own seed buy) until either the USD threshold or the sellout trigger fires — both thresholds are reached with correspondingly minuscule real LT amounts because the entire curve depth (`k`) scales with the tiny `virtualLtReserve`.
3. Calling the fully permissionless `finalizeGraduation(tokenAddress)`.

No adversarial pre-seeding of the V2 pair or any other complex setup is strictly required — an unusually high-rate (but entirely valid) LT is sufficient by itself, making this reachable by an ordinary creator/trader interaction, not just a sophisticated attacker. Given `exchangeRate()` for leveraged tokens is expected to grow over the life of the LT, this failure mode becomes more likely to be hit accidentally as BounceTech LTs mature, in addition to being trivially triggerable by an attacker who launches against a known high-rate LT.

### Recommendation
Add a **lower** bound on `virtualLtReserve` in `_deployAndSeed` (mirroring the existing upper-bound check) sized so that `tokensForLP`/`ltFromPair` at every possible graduation point are guaranteed to exceed UniswapV2's `MINIMUM_LIQUIDITY` floor and `LPLock.recordLock`'s nonzero-amount requirement. Additionally, harden `finalizeGraduation`/`_seedDirectMint` to not let a `pair.mint` or `recordLock` revert silently unwind the lifecycle transition — e.g., pre-validate `tokensForLP`/`ltFromPair` against the minimum-liquidity floor before entering `Lifecycle.Graduating`, or provide an owner-gated (or time-delayed permissionless) escape hatch that can re-price/retry a stuck graduation rather than relying purely on a UUPS upgrade.

### Proof of Concept
1. Creator calls `Zap.createToken` / `Bonding.launch` with `ltAddress` pointing to a legitimate, `ltExists`-registered BounceTech LT whose `exchangeRate()` is very high (e.g., such that `virtualLtReserve = VIRTUAL_LIQUIDITY_USD*1e18/exchangeRate` computes to a very small integer, well below `type(uint112).max/4` so it passes `ExchangeRateTooLow`, but small enough that `TOTAL_SUPPLY * virtualLtReserve` yields a curve whose full depth in real LT terms is only on the order of a few thousand wei).
2. Curve trades (or the creator's own seed buy) push the pair to either `tokenBalance()==0` or the USD threshold — both reachable with a correspondingly tiny amount of real LT because `assetReserve - virtualLtReserve` (the "real raised" figure `canGraduate` and `_prepareGraduationLiquidity` use) is scaled to the same tiny curve depth [3](#0-2) .
3. `_enterGraduating` fires (either inline in `_executeBuy` or via permissionless `triggerGraduation`), caching `tokensForLP`/`ltFromPair` as sub-`MINIMUM_LIQUIDITY` values in `pendingGraduation` [17](#0-16) .
4. Any address calls `finalizeGraduation(tokenAddress)`. `_seedDirectMint`'s call to `IUniswapV2Pair(pair).mint(lpLock)` reverts inside standard UniswapV2 `mint()` because `sqrt(amount0*amount1) <= MINIMUM_LIQUIDITY`, or — if it somehow returns 0 — `LPLock.recordLock` reverts with `ZeroAmount` [14](#0-13) .
5. The whole `finalizeGraduation` transaction reverts, leaving `Lifecycle.Graduating` and `pendingGraduation` unchanged. Every subsequent call by any address reproduces the identical revert, permanently freezing the curve-raised LT and the 250M LP-reserve tokens inside `Bonding` with no on-chain recovery path.

    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }

    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }

    /// @dev Recovers the launch-time virtual LT reserve from immutable
    ///      identities: `Pair._pool.k = tokenReserve_init * assetReserve_init
    ///      = TOTAL_SUPPLY * virtualLtReserve_init` is set ONCE in
    ///      `Pair.mint` and never modified by `Pair.swap` (swap only
    ///      mutates `tokenReserve` / `assetReserve` and asserts K-floor).
    ///      So `Pair.k() / Token.TOTAL_SUPPLY()` returns the exact
    ///      `virtualLtReserve` that was passed to `addInitialLiquidity` at
    ///      launch — for any pair, in any phase, with no storage of our own.
    ///
    ///      Going through this derivation rather than a stored mirror
    ///      eliminates an admin-writable economic-state slot and makes the
    ///      donation-immunity property a pure consequence of the pair's
    ///      already-immutable accounting. The `TOTAL_SUPPLY`-equality check
    ///      in `setTokenImplementation` keeps the divisor consistent across
    ///      impl rotations, so tokens launched under different
    ///      `tokenImplementation` versions still derive the same way.
    function _launchTimeVirtualLtReserve(
        address token_,
        address pair_
    ) internal view returns (uint256) {
        return IPair(pair_).k() / Token(token_).TOTAL_SUPPLY();
    }

    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
