### Title
Webhook `topic` and `shop-domain` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC verification performed by `ShopifyAPI::Utils::HmacValidator.validate` only proves that the *body bytes* were signed by Shopify — it proves nothing about the `x-shopify-topic` or `x-shopify-shop-domain` headers that `Registry.process` subsequently trusts to route the payload and to populate `WebhookMetadata#shop`/`#topic` for the host application's handler.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

only `@raw_body` is signed. `topic` and `shop` are read straight from unauthenticated headers: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts these unauthenticated fields to select the handler and build the metadata delivered to the app: [3](#0-2) 

The identity binding that should hold is: `shop authenticated-by-HMAC == shop delivered-to-handler`. Because `shop` (and `topic`) are outside the signed byte range, that equality is never enforced — only `raw_body == raw_body` is checked via `OpenSSL.secure_compare`: [4](#0-3) 

This is a real divergence from `ShopifyAPI::Auth::Oauth::AuthQuery`, where `shop` *is* part of the signed string: [5](#0-4) 

so the same library applies inconsistent binding rules for the two "verifiable query" implementations.

### Impact Explanation
An unprivileged attacker who can install the target app on their own (attacker-controlled) shop can legitimately trigger a webhook delivery with a body of their choosing (or a fixed, predictable body such as `"{}"` for topics with empty payload) and capture the resulting `(raw_body, hmac)` pair — this pair is valid proof of `HMAC(app_secret, raw_body)` but says nothing about which shop or topic it belongs to. The attacker can then replay that exact body+HMAC to the victim app's webhook endpoint while freely substituting `x-shopify-shop-domain` (to any other shop, including shops the attacker does not control) and `x-shopify-topic` headers. `HmacValidator.validate` still returns `true` because it only re-hashes the body, and `Registry.process` will dispatch the forged event to the app's real handler tagged with an arbitrary victim shop/topic. If the host application uses `WebhookMetadata#shop` to select the tenant's stored session/access token or to write/update tenant data (the documented and expected usage pattern), this is a cross-tenant data-integrity/confusion vector: attacker-controlled webhook content gets attributed to and processed against a victim shop's tenant context.

### Likelihood Explanation
Requires only: (1) the ability to install the app for a free/trial shop to obtain one legitimate signed body (something any internet user can do for a public Shopify app), and (2) direct HTTP access to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — this matches the "unprivileged internet user" threat model. The main constraint is that the attacker needs a payload whose body content is acceptable/parseable for the topic they want to spoof, which is achievable for topics with minimal or predictable bodies.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the signed material that `Request#to_signable_string` returns, or otherwise cryptographically bind them (e.g., concatenate them with the body before hashing, matching how `AuthQuery` binds `shop` into its signable string). At minimum, document that `WebhookMetadata#shop`/`#topic` are unauthenticated and must not be used as a tenant-selection key without an independent verification step (e.g., looking up the resource via the API using the shop's already-verified stored token).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook whose body content they control/predict (e.g. an empty-body-eligible topic).
2. Attacker records the raw body `B` and the `X-Shopify-Hmac-Sha256` value `H` from that real delivery — `H = HMAC-SHA256(app_secret, B)`.
3. Attacker sends `POST /webhooks` to the victim app with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and `X-Shopify-Topic: <topic-of-choice>`.
4. `ShopifyAPI::Webhooks::Request.new` parses these forged headers; `HmacValidator.validate` recomputes HMAC over `B` only, matches `H`, returns `true`.
5. `Registry.process` dispatches to the handler with `WebhookMetadata.new(topic: "<topic-of-choice>", shop: "victim-shop.myshopify.com", body: parsed(B), ...)` — the app processes attacker data as if it originated from `victim-shop.myshopify.com`.
