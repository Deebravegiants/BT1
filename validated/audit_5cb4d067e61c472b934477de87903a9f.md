Audit Report

## Title
Unauthenticated-role disclosure of External Initiator credentials via `GET /v2/external_initiators` (missing role gate) - (File: core/web/router.go)

## Summary
The `GET /v2/external_initiators` route is registered without any role-based access wrapper, unlike `POST`/`DELETE` on the same resource which require `auth.RequiresEditRole`. Any authenticated user — including one provisioned with the lowest-privileged `UserRoleView` — can call this endpoint and receive every External Initiator's `AccessKey` and `OutgoingToken` in the system, not just their own.

## Finding Description
In `core/web/router.go`, the External Initiator routes are:
```go
authv2.GET("/external_initiators", paginatedRequest(eia.Index))
authv2.POST("/external_initiators", auth.RequiresEditRole(eia.Create))
authv2.DELETE("/external_initiators/:Name", auth.RequiresEditRole(eia.Destroy))
```
`GET` only passes through the generic session/token authentication middleware applied to the `authv2` group (`auth.Authenticate(..., AuthenticateByToken, AuthenticateBySession)`), with no `RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` wrapper. This is confirmed by the RBAC test table in `core/web/auth/auth_test.go` at line 224, which explicitly marks `GET /v2/external_initiators` as accessible to view-only, edit-minimal, and edit roles alike (`true, true, true`), in contrast to the `POST`/`DELETE` rows on lines 225–226 which require edit role.

The handler `ExternalInitiatorsController.Index` (`core/web/external_initiators_controller.go`) fetches all initiators via `BridgeORM().ExternalInitiators` (paginated, but unfiltered by requester/owner) and maps them through `presenters.NewExternalInitiatorResource`, which serializes `AccessKey` and `OutgoingToken` into the JSON response for every initiator returned. The integration test `TestExternalInitiatorsController_Index` (`core/web/external_initiators_controller_test.go`) confirms both fields are present in list responses for initiators the requesting client did not create.

`AccessKey`/`OutgoingToken` are genuine credential material: `AccessKey` pairs with a secret (`HashedSecret`) used in `AuthenticateExternalInitiator` to authenticate inbound External-Initiator-triggered job run requests, and `OutgoingToken` is used by the node when calling out to the initiator's URL. Compared to every other credential-bearing resource in the router (CSA/ETH/OCR/OCR2/P2P/VRF keys), the pattern is consistently: index/list may be view-accessible, but sensitive secret material (private keys, seeds) is not embedded in those list responses, and mutating/exporting always requires elevated roles. Here, however, sensitive credential fields are embedded directly in the unguarded list response.

## Impact Explanation
This is a genuine role-based access control gap: a `UserRoleView` account (intended for read-only/dashboard access) can retrieve `AccessKey` and `OutgoingToken` values belonging to External Initiators it did not create and has no operational entitlement over. This maps to the in-scope "key/secret exfiltration" and "node API authentication or role bypass" impact categories — it is a concrete, code-verified vertical privilege violation, not speculative. The severity is bounded by the fact that the paired secrets (`Secret`/`OutgoingSecret`, shown only once at creation) are not exposed by `Index`, limiting the practical exploitability of the `AccessKey` alone; `OutgoingToken` disclosure has a more direct impact since it could potentially be replayed against the third-party endpoint the node calls out to, if that endpoint treats the token as sufficient authentication.

## Likelihood Explanation
High likelihood in any deployment where `ExternalInitiatorsEnabled` is on and `UserRoleView` accounts exist alongside higher-privileged operators (a common configuration for granting read-only dashboard access to auditors/less-trusted users). Exploitation requires only a single authenticated `GET` request with any valid session/API token — no elevated role, no additional steps.

## Recommendation
Wrap `GET /v2/external_initiators` in `auth.RequiresEditRole` (or at minimum `auth.RequiresRunRole`), matching the access level already enforced for `POST`/`DELETE` on the same resource. Additionally, consider removing `AccessKey`/`OutgoingToken` from the list/index presenter (`ExternalInitiatorResource`), surfacing them only in the one-time `Create` response (`ExternalInitiatorAuthentication`), consistent with how other credential resources avoid re-exposing secret material on subsequent reads.

## Proof of Concept
1. Enable `JobPipeline.ExternalInitiatorsEnabled = true`.
2. As an Edit/Admin-role user, `POST /v2/external_initiators {"name":"foo"}` — the server records `AccessKey`/`OutgoingToken`/secrets.
3. Provision a session/API token for a `UserRoleView` user.
4. As that `UserRoleView` user, call `GET /v2/external_initiators?size=50`.
5. Observe the JSON response includes `accessKey` and `outgoingToken` for the initiator created in step 2 — reproduced by the assertions in `TestExternalInitiatorsController_Index` (`core/web/external_initiators_controller_test.go` lines 104–126), and by the RBAC route table entry `{"GET", "/v2/external_initiators", true, true, true}` in `core/web/auth/auth_test.go` line 224, which is a unit test directly verifying view-role access to this route. func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}
