### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but `Utils::HmacValidator` only authenticates the raw request body, not this header. This breaks the intended binding: `authenticated(HMAC) == shop attributed to the webhook`.

### Finding Description
`Webhooks::Registry.process` validates a webhook by calling `Utils::HmacValidator.validate(request)` and, if it passes, immediately trusts `request.shop` to build `WebhookMetadata` that is handed to the app's handler: [1](#0-0) 

The HMAC validator computes/verifies the signature over `verifiable_query.to_signable_string` only: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — the shop-domain header is excluded from the signed material, while `shop` is read straight from an unauthenticated header: [3](#0-2) 

By contrast, the OAuth callback flow deliberately includes `shop` inside the HMAC-signed payload (`AuthQuery#to_signable_string`), proving that binding `shop` into the signature is the library's own established pattern for this class of check: [4](#0-3) 

This is exactly the reported bug class translated to this gem: "a field acted on but not covered by the HMAC" — here, `shop`, which is the tenant key used by `WebhookMetadata` and ultimately by the host application to decide *which merchant's* data/session the webhook body applies to: [5](#0-4) 

### Impact Explanation
Since the app-level `client_secret` used to compute the webhook HMAC is the same across every shop that installs the app, an actor who legitimately controls one tenant (e.g., their own development/test store with the app installed) can obtain a genuinely Shopify-signed webhook (valid body + valid HMAC) for their own shop, and then replay/relay that exact body+HMAC to the target app's webhook endpoint while substituting the `shop-domain` header for an arbitrary victim shop. `HmacValidator.validate` will still pass because it never inspected the header, and `Registry.process` will dispatch to the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain. Any host application that uses this `shop` field as a tenant/session lookup key (the documented and intended usage pattern) will process attacker-controlled webhook `body` content under a victim shop's identity — a cross-tenant data confusion inside the webhook pipeline that this gem hands to the app as "verified."

### Likelihood Explanation
The webhook endpoint is a public HTTP endpoint by design (that's the entire point of webhooks), and forming the modified request requires no secret — only a legitimate, unprivileged install of the app on any shop the attacker controls, plus the ability to craft raw HTTP requests (trivial). No TLS interception, credential theft, or privileged account is required, satisfying the scope constraints.

### Recommendation
Bind the shop domain (and ideally topic/webhook id) into the HMAC-verified material for webhooks, e.g., include the `shop-domain`, `topic`, and `webhook-id` headers in `Request#to_signable_string` (matching Shopify's own webhook verification guidance of authenticating exactly the delivered payload/headers pair), or otherwise cryptographically bind the header-derived `shop` to the signed body before it is exposed via `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they legitimately control) and lets Shopify deliver a real webhook, e.g., `orders/create`, to their configured callback URL. They capture the raw body and the `x-shopify-hmac-sha256` header — both genuinely produced by Shopify using the app's `client_secret`.
2. Attacker sends a POST directly to the app's webhook endpoint with:
   - the exact same `raw_body` and `x-shopify-hmac-sha256` value captured above,
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (any shop, not one they control),
   - `x-shopify-topic: orders/create`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and matches, so validation passes: [1](#0-0) 
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`, i.e., attacker-controlled content is processed under the identity of a shop the attacker never installed the app on or otherwise proved control over.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
