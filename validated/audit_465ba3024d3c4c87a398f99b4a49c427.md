This confirms a clear asymmetry: in the OAuth flow, `AuthQuery#to_signable_string` binds `shop` into the signed payload alongside `code`, `host`, `state`, and `timestamp` [1](#0-0) , so the HMAC in `HmacValidator.validate` cryptographically ties the `shop` claim to the request [2](#0-1) . In the webhook flow, however, `Webhooks::Request#to_signable_string` returns only `@raw_body` [3](#0-2) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers [4](#0-3) . `Registry.process` validates only the HMAC of the body and then trusts `request.shop` to build `WebhookMetadata` passed to the app's handler [5](#0-4) . The documentation explicitly states this call "will verify the request did indeed come from Shopify," implying the whole webhook (including shop identity) is authenticated [6](#0-5) , which is not actually true for the `shop` header.

Given this, however, I need to be careful about likelihood/impact: exploiting this requires the attacker to already possess a validly-HMAC-signed webhook body (i.e., a real webhook Shopify sent to the app for the attacker's own shop, since the HMAC secret, `Context.api_secret_key`, is shared across all shops using the app and not attacker-controlled) and then replay that same body with a forged `shop`-domain header to make the app's handler believe the data belongs to a different (victim) merchant. This is a real cross-tenant identity-binding gap in this gem's webhook verification, matching the bug-class hint (a field acted on but not covered by the HMAC).

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only (`to_signable_string` returns `@raw_body`), while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `Registry.process` to route and attribute the webhook to a tenant are taken directly from HTTP headers that are never included in the signed content.

### Finding Description
`HmacValidator.validate` verifies `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, verifiable_query.to_signable_string)` against the received HMAC [7](#0-6) . For `Webhooks::Request`, `to_signable_string` is simply the raw body [3](#0-2) . The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to that header's value [8](#0-7) . `Registry.process` calls `Utils::HmacValidator.validate(request)` and, if it passes, builds `WebhookMetadata` using `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to hand off to the app-registered handler [5](#0-4) . Thus the equality the app relies on — "the shop attributed to this webhook equals the shop Shopify actually sent it for" — is never actually checked; only "the body bytes are unmodified" is checked. This differs from the OAuth callback flow, where `AuthQuery#to_signable_string` explicitly folds `shop` into the signed string, so `HmacValidator.validate` there does bind shop identity to the signature [9](#0-8) .

### Impact Explanation
An attacker who controls a shop that has installed the app receives their own legitimately HMAC-signed webhooks from Shopify (same shared `api_secret_key` HMAC key used for every shop on the app). By resending that same raw body and valid HMAC to the app's webhook endpoint while substituting a victim shop's domain in the `shopify-shop-domain` header, the attacker can make the app process attacker-supplied webhook data as if it originated from a different, victim tenant. Because the library's own webhook validation is documented as verifying "the request did indeed come from Shopify" [6](#0-5) , apps built on this gem's documented API can reasonably (but incorrectly) treat `data.shop` as authenticated, enabling cross-tenant data confusion/injection in downstream processing (e.g., queued jobs keyed by `shop_domain`, as shown in the gem's own webhook handler example) [10](#0-9) .

### Likelihood Explanation
Moderate. It requires the attacker to have (or obtain) a valid webhook delivery for a shop they control on the same app installation (a normal, unprivileged interaction — installing the app on a test/dev shop and triggering a real event), then replay it against the app's public webhook endpoint with a forged shop header. No access to `api_secret_key` or any privileged credential is needed.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-signed content, or require the receiving app to cross-check `request.shop` against the shop-to-session/install mapping obtained during OAuth before trusting it. At minimum, update `Webhooks::Request#to_signable_string` and the underlying validation contract so that headers used for tenant identification are cryptographically bound to the signature rather than trusted implicitly once body-only HMAC validation succeeds.

### Proof of Concept
1. App is installed by an attacker on `attacker-shop.myshopify.com`; the attacker registers a webhook and receives a genuine event from Shopify: raw body `B`, header `shopify-shop-domain: attacker-shop.myshopify.com`, valid `shopify-hmac-sha256` computed over `B` with the app's shared secret.
2. Attacker sends a POST to the app's webhook endpoint with the same body `B` and same `shopify-hmac-sha256`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses the forged headers; `HmacValidator.validate` recomputes HMAC over `B` only and it matches, so validation succeeds [11](#0-10) .
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the app to process/attribute attacker-controlled data under the victim's tenant identity [12](#0-11) .
