### Title
Unaccounted arbitrary calls from Emporium's identity via the Min-circuit Emporium path allow theft of any tokens/ETH held by Emporium - (File: contracts/CircomDataBuilder.sol, contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol, contracts/Hinkal.sol)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, whose circuit (`MainEVMCircuitMin.circom`) only proves `message == Poseidon(messageSeed)` for a **self-chosen** `messageSeed`. This "proof" carries no authorization over the `EmporiumStack` content, yet `EmporiumUpgradeable.runAction` executes `stack.ops` (arbitrary `endpoint.call{value}(callData)`) unconditionally when `stack.signerAddress == address(0)`, and the balance-accounting loop in `Hinkal.sol` (lines 97-147) is skipped entirely because it iterates over the empty `erc20TokenAddresses` array.

### Finding Description
The claimed invariant — *assets Emporium can move in a tx == assets accounted in balancesBefore/balancesAfter (and in Hinkal's `balanceDif`/`slippageValues` checks)* — is broken.

Path:
1. `Hinkal.transact` → `hinkalHelper.performHinkalChecks` → `CircomDataBuilder.formInputForCircom` (contracts/CircomDataBuilder.sol:134-148) selects `formInputEmporiumMin` (contracts/CircomDataBuilder.sol:150-161) whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`. The resulting public input only contains `emporiumMessage, timeStamp, calldataHash`.
2. The matching circuit `MainEVMCircuitMin.circom` (lines 6-17) proves nothing but `message <== Poseidon(1)([messageSeed])`. Since `messageSeed` is chosen entirely by the caller, any unprivileged attacker can trivially generate a valid proof for a fresh, never-used `emporiumMessage` of their own choosing — this is not an authorization mechanism over any specific `EmporiumStack`/ops.
3. `Hinkal.transact` then calls `_externalTransact` → `EmporiumUpgradeable.runAction` (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-160). It `abi.decode`s the attacker-controlled `circomData.externalActionData.externalActionMetadata` into an `EmporiumStack` with `signerAddress == address(0)`.
4. `verifyWallet` (lines 302-349) checks only that `emporiumMessage` hasn't been used, marks it used, and **returns immediately** when `stack.signerAddress == address(0)` — no EIP-712 signature or other authorization is required.
5. The op loop (lines 91-118) then executes CASE 2 "Stateless Interaction": `op.endpoint.call{value: op.value}(op.callData)` — executed with `msg.sender == EmporiumUpgradeable` itself. If `endpoint` is any ERC20 token Emporium holds a balance of, `callData = transfer(attacker, amount)` succeeds because Emporium is the caller.
6. Because `circomData.erc20TokenAddresses.length == 0`, `getBalancesForArray` returns empty arrays both before and after (lines 85-87, 122-124); the `balanceChange`/`handleOut`/`BalanceChangeShouldBePositive` checks (lines 132-157) never execute for the stolen token. In `Hinkal.sol`, the outer loop at lines 97-147 that enforces `balanceDif >= slippageValues[i]` and the on/off-chain UTXO balance equation also iterates 0 times, so nothing is checked or reverted there either.
7. Any value moved out of Emporium by the injected op is completely unaccounted for — no UTXO is minted for it, no slippage check applies, and the transaction succeeds.

The specific "slippage negative" framing in the question is a red herring for this Min path: the slippage/balance checks in `Hinkal.sol` never execute at all for zero-length token arrays, so the vulnerability doesn't even need slippage to be set — it's an unconditional accounting bypass. This matches the pattern already visible in `payRelayFees`/`runAction`, which likewise only loops over `circomData.erc20TokenAddresses`.

Existing guards do not prevent this: `performHinkalChecks`'s `getHashedCalldata`/`calldataHash` check only verifies internal consistency of attacker-supplied fields against each other, not against any prior legitimate deposit; `dimensionsCheck` only enforces array-length agreement (which is trivially satisfiable with all-empty arrays); `rootHashExists` is irrelevant since no nullifiers are spent; `onlyAllowedRecipient` only checks that the caller of `runAction` is the registered `Hinkal` contract, not that the op content is authorized.

### Impact Explanation
Any ERC20/ETH balance sitting in the `EmporiumUpgradeable` contract (e.g., prior deposits mid-flow, ops leftovers, protocol/relay fees, or funds inadvertently or transiently held there) can be moved to an attacker-controlled address with zero accounting, by anyone who can call `Hinkal.transact` with a self-crafted Min-path proof. This is direct theft of shielded/in-flight user funds and/or protocol funds held by Emporium, repeatable per available balance and per unused `emporiumMessage` (attacker can generate an unlimited number of fresh valid `messageSeed`s).

### Likelihood Explanation
Preconditions: Emporium contract must hold some token/ETH balance (a very ordinary state for a multi-step "deposit then later execute" pattern) and there must exist a registered verifier for the Min-circuit dimensions (`tokenNumber=0`) + `HINKAL_EMPORIUM_ACTION_ID`. Attacker cost is minimal (gas + generating a trivial self-referential proof); no privileged role, victim's private key, or victim cooperation is required. Fully repeatable.

### Recommendation
- Require `EmporiumStack.signerAddress != address(0)` (i.e., mandatory EIP-712 authorization) whenever the transaction uses the Min-circuit / zero-token-array path, or disallow the Min path from invoking arbitrary `ops` entirely — restrict it to a narrow, pre-committed action (e.g., only allow it to *cancel* or *finalize* a specific previously-signed stack hash, not decode a fresh `EmporiumStack`).
- Bind `emporiumMessage` (and thus the Min proof) cryptographically to the specific `EmporiumStack`/ops content (e.g., include `keccak256(abi.encode(stack))` in the signed/hashed message or in the circuit's public input) rather than allowing an attacker to mint an arbitrary fresh message unrelated to any prior deposit.
- Do not skip the balance/slippage accounting in `Hinkal.sol` and `EmporiumUpgradeable.runAction` when `erc20TokenAddresses.length == 0`; if any op moves ERC20/ETH value, that value must be captured in `circomData.erc20TokenAddresses`/`amountChanges` and validated identically to the normal path.

    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }

        if (block.timestamp > stack.deadline) {
            revert SignatureExpired();
        }

        if (circomData.feeStructure.flatFee > stack.maxFee) {
            revert FeeExceedsSignedMax();
        }
    }
