## Analysis

The report's bug class — a shared pool of externally-accrued value (Compound's COMP rewards) that gets swept as if it were ordinary reserve/protocol funds, with no attribution to the party that actually earned it — has a direct analog in Hinkal's `EmporiumUpgradeable` external action.

### Root cause

`EmporiumUpgradeable.runAction()` lets a user submit an arbitrary sequence of calls (`EmporiumStack.ops`) that are executed with `msg.sender == Emporium` in the "Stateless Interaction" branch (`stack.signerAddress == address(0)`): [1](#0-0) 

Any endpoint/calldata is allowed except the two `HinkalWallet` selectors, so a user can direct the Emporium's shared address to deposit into a lending/staking protocol, or to call a permissionless reward-claim function on behalf of the Emporium address: [2](#0-1) 

The output UTXO given to the caller is computed purely from the *contract-wide* token-balance delta of the shared Emporium address, not from any per-depositor ledger: [3](#0-2) 

Because `signerAddress == address(0)` means the position/funds live on the Emporium contract's own address (as opposed to a per-user `HinkalWallet` instance used in the stateful branch, see `contracts/external-actions/emporium/HinkalWallet.sol`), any yield/reward paid out later to that shared address (e.g., a lending-market reward token like COMP, claimable by anyone on behalf of any address) is indistinguishable from principal. Whoever next calls `runAction()` with that reward token listed in `circomData.erc20TokenAddresses` will have `balancesAfter[i] - balancesBefore[i]` include the reward and receive it as their own private output UTXO via `handleOut`: [4](#0-3) 

This is the same equality break as the original report: value that accrued because of User A's position (their deposit/stake routed through the shared Emporium address) is not tied to User A's shielded balance anywhere in the circuit's public inputs (`erc20TokenAddresses`/`amountChanges`/`calldataHash` only commit to *that caller's own* op sequence and declared deltas). The reward is only ever accounted for as "whatever raw balance diff the current caller's transaction produces," so an attacker with no stake in the underlying position can insert an op that triggers/claims the reward for the shared address and walk away with it.

I confirmed `externalActionData` (containing the `EmporiumStack`/ops) is committed inside `calldataHash`, which is itself bound into the circuit's public inputs, so a relayer/prover cannot swap ops after proof generation — the attack vector is not proof malleability, but simply that any user is free to *choose* an op sequence that harvests whatever balance is sitting on the shared Emporium address, regardless of who caused it to be there. [5](#0-4) 

### Title
Shared Emporium balance-diff accounting lets any user sweep reward/yield tokens accrued by other users' pooled positions - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction()` executes user-chosen arbitrary calls from the Emporium contract's own address (when `signerAddress == address(0)`) and mints an output UTXO to the caller equal to the raw balance delta of the contract for the tokens listed. Because the Emporium address is shared across all "stateless" users, any external yield/reward (e.g., a lending-protocol reward token that is claimable on behalf of any address, or a delayed payout on a position opened by another user's prior transaction) that lands on the Emporium contract is not attributed to whoever generated it. Any user can submit an op that claims/triggers that payout and receive it as their own shielded output.

### Finding Description
The stateless branch of the op loop performs `op.endpoint.call{value: op.value}(op.callData)` with `msg.sender == Emporium`, so it can call any external protocol, including a lending/staking market where the Emporium address itself accumulates a position (e.g., depositing collateral to earn a reward token). The reward-out calculation is a pure balance snapshot diff (`balancesAfter[i] - balancesBefore[i]`, adjusted for the caller's own declared inflow via `deltaAmountChanges`), with no ledger tracking which prior transaction/position caused funds to accrue to the shared address. Consequently, once a position held by the Emporium address accrues a claimable reward (via an external protocol's permissionless claim function, exactly analogous to `Comptroller.claimComp(address,address[])` in the original report), whoever next calls `runAction()` and lists that reward token in `circomData.erc20TokenAddresses` receives it as their own private balance, even though they contributed no principal to the position that generated it.

### Impact Explanation
This is theft of shielded value belonging to another user: yield/rewards generated by User A's position (routed through the shared, address(0)-signer Emporium instance) can be diverted into Attacker's own shielded UTXO by simply including the reward-claim call in their own op sequence. This falls under "Critical - direct theft of shielded ... user funds" since real value that should have gone into User A's shielded balance is redirected to an unrelated party.

### Likelihood Explanation
Requires: (1) the deployed external-action stack to expose lending/staking-style ops through Emporium (permitted by the fully generic `op.endpoint.call`), and (2) the target protocol to allow reward claims on behalf of an arbitrary address (a common pattern, as noted in the original Morpho/Compound report). Exploitation needs no special privilege — any unprivileged EOA can craft the winning op sequence and race to call `runAction()` after a reward becomes claimable.

### Recommendation
Track ownership/attribution of any position opened through the stateless Emporium branch (e.g., require lending/staking-style, multi-block-accruing interactions to go through the per-user `HinkalWallet` stateful path instead of the shared address(0) signer), or maintain an explicit ledger of principal vs. externally-accrued rewards per opener so that `runAction`'s balance-diff payout cannot include value the current caller did not contribute.

### Proof of Concept
1. User A calls `Hinkal.transact` with an Emporium `externalActionData`, `signerAddress == address(0)`, whose op deposits token X into an external lending market, crediting the position to the Emporium contract's own address; User A receives their principal-equivalent UTXO back per the balance diff at that time.
2. Time passes; the lending market accrues a reward token R to the Emporium's position, claimable via a permissionless `claim(address account)`-style call.
3. Attacker (no prior deposit) calls `Hinkal.transact` with an Emporium action whose op list is just `[claim(EmporiumAddress)]`, and lists reward token R in `circomData.erc20TokenAddresses`.
4. `runAction()` computes `balancesAfter[R] - balancesBefore[R]` = the claimed reward, and `handleOut` sends it to Attacker and mints it as Attacker's private UTXO — funds generated by User A's position are stolen by Attacker.

    function handleOut(
        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
    ) internal returns (UTXO memory outUtxo) {
        // total change can be less than zero if there was some balance before the call -> that's why we have <=
        if (balanceChange <= 0) {
            return outUtxo;
        }

        transferERC20TokenOrETH(
            circomData.erc20TokenAddresses[i],
            msg.sender,
            uint256(balanceChange)
        );

        outUtxo = UTXO(
            uint256(balanceChange),
            circomData.erc20TokenAddresses[i],
            circomData.stealthAddressStructure,
            circomData.timeStamp
        );
    }
