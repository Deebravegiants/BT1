### Title
Webhook shop-domain and topic identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The gem's webhook processing pipeline validates an inbound webhook's HMAC against the raw request body only. The `shop`, `topic`, `webhook_id`, and `api_version` values that `ShopifyAPI::Webhooks::Registry.process` hands to the host application's handler are parsed from unauthenticated HTTP headers that are never part of the HMAC-signed byte range. Any party that possesses one validly-signed webhook payload (e.g., any merchant who has installed the app, since HMAC uses the single shared `client_secret` for the whole app) can replay that payload while altering the `shop-domain` header, and the gem will report it to the handler as originating from an arbitrary other shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts the `hmac`, `topic`, `shop`, `api_version`, and `webhook_id` from HTTP headers: [1](#0-0) 

Its `to_signable_string`, which is what actually gets HMAC-verified, returns only the raw request body: [2](#0-1) 

`Registry.process` validates the HMAC using this signable string, but then constructs the `WebhookMetadata` object passed to the app's handler using `request.shop`, `request.topic`, and `request.webhook_id` — none of which were part of the verified bytes: [3](#0-2) 

`HmacValidator.validate` confirms the check is scoped strictly to `verifiable_query.to_signable_string` (the body) against the shared `Context.api_secret_key`: [4](#0-3) 

The identity binding that should hold is:
`shop_that_signed(payload) == shop_reported_to_handler(request.shop)`

Because `request.shop` is taken from an unauthenticated header while the HMAC only proves "this body byte-for-byte came from an app installation using this `client_secret`" (not "this body belongs to shop X"), the equality is never enforced. Since a single `client_secret` is shared across every shop that installs the app, any shop that has legitimately received one authentic webhook can capture its body+HMAC and resend it to the app's webhook endpoint with the `x-shopify-shop-domain` header swapped to a different, victim shop's domain. The gem will accept the HMAC (it only checks the body) and hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This breaks a cross-tenant boundary: an attacker who is a legitimate (even trial/free) installer of the app can inject arbitrary webhook body content that the host application will process and persist under a different, victim shop's identity (since `WebhookMetadata#shop` is the identifier host apps use to determine which merchant record to update). Depending on the webhook topic used by the app (e.g., `app/uninstalled`, `customers/redact`, `shop/update`), this can cause cross-tenant state corruption, unauthorized data association, or trigger the app to treat the victim's tenant as if it sent attacker-controlled data — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires the attacker to have captured one authentic webhook (achievable by installing the app themselves, which the app's flow already allows to any merchant), and requires the target app's webhook handler to key off `WebhookMetadata#shop`/`topic` for tenant-sensitive logic (a very common usage pattern that the docs and this gem's API encourage, since `shop` is exposed as first-class metadata on every webhook). No possession of `client_secret`, access tokens, or other privileged credentials is needed beyond what any regular merchant installation grants.

### Recommendation
Bind the identity fields into the HMAC-verified byte range, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the signed payload before exposing them via `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are not covered by the HMAC and must not be trusted for tenant routing without corroborating the shop identity against data embedded in the verified JSON body (or against a known/stored shop session), and consider making `Registry.process` reject requests where the header-derived `shop` cannot be independently corroborated.

### Proof of Concept
1. Install the target app as Shop A; capture one legitimate webhook POST (e.g. `orders/create`) including its `X-Shopify-Hmac-Sha256` header and raw body.
2. Replay the exact same raw body and HMAC header to the app's webhook endpoint, but change `X-Shopify-Shop-Domain` to `shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`) calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the raw body against the shared `client_secret`.
4. The handler receives `WebhookMetadata.new(shop: "shop-b.myshopify.com", topic: ..., body: <Shop A's body>, ...)`, causing the host app to process Shop A's data as if it belonged to Shop B.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
