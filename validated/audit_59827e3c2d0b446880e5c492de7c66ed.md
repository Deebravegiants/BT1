Confirmed: `HyperFungibleToken.onAccept` at [1](#0-0)  mints tokens to `beneficiary` then unconditionally forwards `message.data` to the shared `CallDispatcher` with no post-execution sweep back to the HFT contract, and `CallDispatcher.dispatch` at [2](#0-1)  is a completely unrestricted `external` function — anyone, not just HFT or IntentGatewayV2, can call it directly with an arbitrary `Call[]` to make the dispatcher execute any call as itself.

### Title
Unauthenticated `CallDispatcher.dispatch()` lets anyone drain any token/ETH balance left in the shared dispatcher - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher` is a single, chain-wide, unowned contract shared by every `HyperFungibleToken`/`WrappedHyperFungibleToken` deployment and by `IntentGatewayV2`, used to execute attacker/user-supplied `Call[]` payloads carried in cross-chain messages and orders. Its `dispatch(bytes)` function has no access control (no `onlyCaller`, no allow-list, no reentrancy/ownership check) and simply loops over the decoded `Call[]`, low-level-calling each `to` with `value`/`data` as the dispatcher itself. Because the dispatcher is a long-lived, address-stable, multi-tenant contract that regularly holds tokens/ETH mid-flight (minted HFT tokens routed to it for compose-on-receive swaps, native value forwarded for predispatch swaps in `IntentGatewayV2`), any balance that is not atomically and completely swept back out in the same transaction is permanently exposed: anyone can call `CallDispatcher.dispatch()` directly, at any later time, with a `Call[]` that transfers that balance to themselves.

### Finding Description
`HyperFungibleToken.onAccept` mints bridged tokens straight to `message.to` (which per the documented pattern is frequently set to the `CallDispatcher` address itself so the attached calldata can spend them) and then calls `ICallDispatcher(_dispatcher).dispatch(message.data)` [3](#0-2) . Unlike `IntentGatewayV2`, which explicitly snapshots and sweeps 100% of the dispatcher's balances back to itself after every `ICallDispatcher(dispatcher).dispatch(...)` call (`evm/src/apps/IntentGatewayV2.sol:258-300`), HFT's `onAccept` performs no such sweep: whatever the attached `Call[]` does not fully consume (rounding remainders, a swap that doesn't spend the full input, a call that reverts on a later leg but not the whole batch structure, or a user simply forgetting to route dust back out) stays in the `CallDispatcher`'s own token/ETH balance indefinitely.

`ICallDispatcher.dispatch` is documented as "dispatch untrusted call(s)" [4](#0-3) , and the concrete implementation enforces only that each `to` has code — it performs zero access control on the caller: `function dispatch(bytes memory encoded) external { ... (bool success, bytes memory result) = to.call{value: call.value}(call.data); ... }` [2](#0-1) . Because this function is `external` with no modifier restricting the caller to `HyperFungibleToken` or `IntentGatewayV2`, any unprivileged address can call the deployed `CallDispatcher` directly and instruct it to `transfer`/`safeTransfer` out any ERC-20 balance, or send any ETH balance, that currently sits at the dispatcher's address — regardless of which protocol flow (or user error, e.g. an accidental direct token send to the dispatcher) put it there.

This is the structural analog of the MCMS "Template Management" RCE: a general-purpose, protocol-wide "execute arbitrary payload" primitive is exposed without verifying the caller is an authorized orchestrator, so a crafted payload from an unprivileged party can act on state (fund balances) it was never meant to reach.

### Impact Explanation
Any token or native-currency balance temporarily or accidentally resident in the shared `CallDispatcher` — e.g., leftover amounts from an HFT `onAccept` composed-swap that doesn't fully spend the minted tokens, or tokens mistakenly sent to the well-known, address-stable `CallDispatcher` (published on the "contract addresses" page for every chain) — can be permanently and unilaterally stolen by any third party simply by calling `dispatch()` themselves. This is concrete theft of funds reachable from a single, unprivileged transaction with no relayer, proof, or governance step required, and it affects every integrator relying on the documented HFT "transfer-and-swap" calldata-execution pattern.

### Likelihood Explanation
Likelihood is high for any HFT deployment or integrator that follows the documented composability pattern of routing minted tokens through the `CallDispatcher` for a destination-chain swap/stake/deposit, since partial fills, slippage, fee-on-transfer tokens, or any calldata that doesn't 100%-drain its own output leaves exploitable dust at a public, well-known address with an unrestricted arbitrary-call function. No special privileges, timing races, or governance compromise are needed — an attacker only needs to observe (via public token `Transfer` events or block explorer scans) that the `CallDispatcher` currently holds a nonzero balance and front-run/immediately call `dispatch()`.

### Recommendation
Restrict `CallDispatcher.dispatch` to a caller allow-list (the specific `HyperFungibleToken`/`WrappedHyperFungibleToken`/`IntentGatewayV2` instances configured to use it), or make each integrator deploy/own a dedicated dispatcher instance with an `onlyOwner`/`onlyCaller` guard. Independently, `HyperFungibleToken.onAccept` (and any other integration that mints/unlocks to the dispatcher before executing calldata) should sweep 100% of the dispatcher's resulting balances for the tokens involved back to a safe recipient in the same transaction, mirroring the sweep-back pattern already implemented in `IntentGatewayV2`.

### Proof of Concept
1. A user calls `HyperFungibleToken.send` on chain A with `to = CALL_DISPATCHER` and `data` encoding a swap `Call[]` that, due to slippage/rounding, leaves `100` units of `DEST_TOKEN` unswapped in the dispatcher after `onAccept` executes on chain B (`sdk/packages/core/contracts/apps/HyperFungibleToken.sol:292-313`).
2. Because `onAccept` never sweeps the dispatcher's residual `DEST_TOKEN` balance back anywhere, those `100` units remain at the `CallDispatcher` address.
3. An unrelated attacker calls `CallDispatcher.dispatch(abi.encode(Call[]))` directly (no restriction on `msg.sender`, per `evm/src/utils/CallDispatcher.sol:44-62`) with a single `Call{ to: DEST_TOKEN, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, 100) }`.
4. The call succeeds because `dispatch` only checks `extcodesize(DEST_TOKEN) != 0`; the attacker receives the `100` units that belonged to the original bridging user/integrator.

```text
    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
```

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```
