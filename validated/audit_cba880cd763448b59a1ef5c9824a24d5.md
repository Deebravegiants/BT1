### Title
Webhook HMAC only binds the request body, not the shop-domain header used for tenant dispatch - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then dispatches the handler using the `shop` value taken from the unsigned `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header. Because Shopify's `client_secret` (the HMAC signing key) is scoped to the *app*, not to an individual *shop*, any merchant who has legitimately installed the app can generate a validly-signed webhook body from their own store and then replay it to the app's public webhook endpoint with the shop-domain header changed to point at a different, victim shop. The signature check still passes because the header is not part of the signed material, so the handler processes attacker-supplied body data under the identity of an arbitrary target shop.

### Finding Description
`Utils::VerifiableQuery`/`HmacValidator.validate` computes and compares the signature only over `to_signable_string`. For webhooks, `Request#to_signable_string` returns `@raw_body` exclusively: [2](#0-1) 

The `shop` (and `topic`, `webhook_id`, `api_version`) accessors are read straight from HTTP headers with no cryptographic binding to the signed body: [4](#0-3) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` (and `request.topic`) to build `WebhookMetadata` and invoke the registered handler: [3](#0-2) 

The intended equality is: `shop_that_produced_the_valid_signature == shop_used_to_dispatch_and_process_the_payload`. Since the app's `client_secret` (the HMAC key) is identical for every shop that installs the app, "a valid signature" only proves "signed by someone who owns a real installation of this app" — it does not prove which shop. An attacker who installs the app on their own store (a completely unprivileged, self-service action) can:
1. Trigger any webhook topic they control (e.g. `orders/create`, `app/uninstalled`) on their own shop, capturing the genuine raw body and its genuine `X-Shopify-Hmac-Sha256` value.
2. Replay that exact `(body, hmac)` pair to the app's public webhook endpoint, substituting `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` still succeeds (it only checks the body bytes and the app secret), and `Registry.process` calls the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)`.

This breaks the binding "bytes verified == identity acted upon:" the header field that determines *which tenant's* data store/handler logic runs is not covered by the HMAC that is supposed to authenticate the request.

### Impact Explanation
This allows an unprivileged Shopify merchant (i.e., anyone who can install the target app on their own free/dev store) to inject attacker-chosen webhook payloads that the host application will process as belonging to a different, arbitrary shop. Depending on how the host app's webhook handlers use `shop`/`body` (e.g., updating per-shop records, provisioning, billing state, uninstall cleanup), this enables cross-tenant data corruption or cross-tenant state changes — matching the "Critical: cross-tenant access" impact category, since the tenant boundary (`shop`) is not authenticated even though the request as a whole is treated as verified.

### Likelihood Explanation
Likelihood is significant: any user can self-install the target app to obtain a genuinely signed webhook body, and the shop-domain header is a plain HTTP header with no additional verification performed anywhere in `lib/shopify_api/webhooks/**`. No access token, `client_secret`, or privileged account is required — only the ability to install the app on a store the attacker controls, which is a standard, unprivileged Shopify capability.

### Recommendation
Bind the tenant identity into the authenticated material, or otherwise independently verify it before dispatch:
- Verify that the `shop` header value corresponds to a shop for which the recipient app actually has an active session/installation record before invoking handlers, rather than trusting the header at face value.
- Where possible, include the shop domain (and topic) as part of the data that is cryptographically checked (e.g., cross-checking against a known-installed-shop list keyed independently of the header), so that a validly-signed payload from shop A cannot be attributed to shop B by simply changing a header.
- Document this limitation prominently for consumers of `ShopifyAPI::Webhooks::Registry.process` / `WebhookMetadata`, since today the library implicitly signals "verified" via `HmacValidator.validate` while the shop attribute used downstream is unauthenticated.

### Proof of Concept
1. As an attacker, install the target Shopify app on `attacker-shop.myshopify.com`.
2. Trigger a webhook topic the app subscribes to (e.g. `orders/create`) on `attacker-shop`, capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header `H` that Shopify sends to the app's webhook endpoint.
3. Send a new POST request to the same webhook endpoint with body `B` (unchanged), header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds successfully; `HmacValidator.validate(request)` returns `true` because it only checks `Digest.hexencode(...)` against `to_signable_string` (`B`), not the shop header.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` — the host application now processes attacker-controlled data under the victim shop's identity, despite a "successful" HMAC validation.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
