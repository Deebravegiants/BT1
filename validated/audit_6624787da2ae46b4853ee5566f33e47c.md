### Title
Webhook HMAC only signs the request body, so the shop/topic/webhook-id headers used for tenant routing are forgeable, enabling cross-tenant webhook injection - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC that covers only the raw request body, then trusts the `shop`, `topic`, `webhook_id`, and `api_version` fields — all taken from unauthenticated HTTP headers — to decide which tenant/handler the payload belongs to. This breaks the binding `HMAC-authenticated bytes == fields used to identify the tenant`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `shop`, `topic`, `webhook_id`, `api_version` are read straight from HTTP headers with no cryptographic coverage: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the signature against `verifiable_query.to_signable_string` (the raw body only) using the app's `api_secret_key`: [3](#0-2) 

`Registry.process` then raises only if the HMAC over the body is invalid, and otherwise dispatches the handler with the tenant identity taken from the unauthenticated headers: [4](#0-3) 

Because the same `api_secret_key` signs webhooks for every shop that has installed the app, any shop owner (an unprivileged actor with respect to other tenants of the same app) can trigger a legitimate webhook for their own shop, capture the resulting `(raw_body, hmac)` pair, and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header rewritten to name a different, victim shop. The HMAC check still passes because it only verifies the body bytes, not the header that the code treats as the authenticated tenant identity. `WebhookMetadata.shop` is then handed to the app's handler as if it were verified, exactly mirroring the report's bug class of "bytes verified versus bytes/fields acted on."

### Impact Explanation
This allows cross-tenant webhook injection: an attacker who is a legitimate (but unprivileged relative to other merchants) user of the app can make the app process attacker-controlled webhook data under a victim shop's identity, since `request.shop` is not covered by the signature. Depending on the app's webhook handlers, this can lead to cross-tenant state corruption, fake order/customer events being attributed to another merchant, or triggering mandatory-compliance handlers (e.g. `customers/redact`) for a shop that never requested them.

### Likelihood Explanation
Exploitation requires only: (1) installing the app on one's own shop (attacker's own tenant, no special privilege), (2) triggering any webhook topic to capture a valid `(body, hmac)` pair, and (3) replaying it with a modified `shop-domain`/`topic` header, since none of these header values are part of the signed payload. No access token, secret, or elevated privilege is required beyond normal use of the app as a merchant.

### Recommendation
Include the identity-binding fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed body (e.g., verify the shop domain against the session/shop that installed the webhook subscription, not solely against the header value) before trusting them in `Registry.process`.

### Proof of Concept
1. App has multiple installs: shop `attacker.myshopify.com` and shop `victim.myshopify.com`.
2. Attacker triggers a real webhook (e.g. `orders/create`) on their own shop, capturing the raw POST body and the valid `X-Shopify-Hmac-Sha256` header sent by Shopify (signed with the app's shared `api_secret_key`).
3. Attacker replays this exact body/HMAC to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (body unchanged), and `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the app to act as though the event originated from the victim's shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
