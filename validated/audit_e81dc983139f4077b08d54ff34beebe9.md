### Title
Webhook tenant identity (`shop`, `topic`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop` and `topic` by reading them directly from HTTP headers, but `to_signable_string` (the value that `HmacValidator` actually verifies) is just the raw request body. The HMAC therefore authenticates *that the body came from Shopify*, but not *which shop or topic it belongs to*.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook with: [1](#0-0) [1](#0-0) 

which calls `Utils::HmacValidator.validate(request)`: [2](#0-1) 

This validator computes and compares a signature over `verifiable_query.to_signable_string`. For webhook requests, that method returns only the raw body: [3](#0-2) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from unauthenticated headers with no cryptographic binding to the HMAC: [4](#0-3) 

The broken identity binding, stated as an equality: `hmac_verified(body) == true` should imply `shop_used_for_tenant_routing == hmac_signer's shop`, but in fact `shop` is never part of the signed content, so the equality does not hold. Any request whose *body* carries a valid signature is accepted, regardless of which `shop-domain`/`topic` header accompanies it.

`Registry.process` then forwards `request.shop` and `request.topic` straight to the host application's handler as trusted tenant context: [5](#0-4) 

This matches the gem's own documented contract, which explicitly tells integrators that `data.shop` is a trustworthy "shop domain of the webhook" to key their multi-tenant processing on: [6](#0-5) [7](#0-6) 

### Impact Explanation
An app's webhook client secret (`api_secret_key`) is a single shared secret across every merchant that installs the app — it is not per-shop. Any merchant that legitimately installs the app can trigger real webhook deliveries for their own store (e.g. by placing an order), thereby obtaining a request whose body carries a **validly-signed HMAC** computed with the app's shared secret. Because the signature never covers the `x-shopify-shop-domain` (or `x-shopify-topic`) header, that same merchant can replay the identical body/HMAC pair while substituting an arbitrary victim `shop-domain` header. `HmacValidator.validate` still passes (body/signature match), and `Registry.process` will route the (attacker-crafted) payload into the handler under a spoofed `shop` identity. In a host application that uses `data.shop` to select which tenant's records to create/update (the exact pattern the gem's own docs recommend), this breaks the shop-to-payload identity binding and enables cross-tenant data corruption/injection using another merchant's identity — a cross-tenant impact.

### Likelihood Explanation
Likelihood is high for any app built per the gem's documented pattern: it requires no privileged credentials, no leaked secrets, and no TLS interception — only that the attacker already be a legitimate (unprivileged) installer of the target app on their own store, which is the normal, expected way anyone interacts with a public Shopify app.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`) inside the signed payload used for HMAC verification, or otherwise cryptographically bind them (e.g., derive `shop` only from a value that is itself covered by the signature, similar to how `AuthQuery#to_signable_string` includes `shop` for OAuth callbacks: [8](#0-7) ). At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated header values and must not be trusted for tenant routing without additional verification.

### Proof of Concept
1. App `MyApp` is installed by attacker's own store `attacker.myshopify.com` and by victim store `victim.myshopify.com`.
2. Attacker triggers a real webhook on their own store (e.g., `orders/create`), capturing the raw POST body `B` and the valid `x-shopify-hmac-sha256` header `H` that Shopify computed using the app's single shared `client_secret`.
3. Attacker resends the same request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but replacing `x-shopify-shop-domain: attacker.myshopify.com` with `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(body, secret) == H` — this still passes because `body` and `H` are unmodified.
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, processing attacker-controlled data under the victim shop's identity.
