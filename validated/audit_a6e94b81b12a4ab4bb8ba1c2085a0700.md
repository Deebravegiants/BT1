### Title
Webhook Shop-Domain Header Spoofing via HMAC Scope Mismatch - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, and `webhook_id` fields are read directly from unauthenticated HTTP headers and are never included in the signed data. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then passes the header-derived, unauthenticated `shop` value straight to the merchant-supplied handler as the tenant identity for the event.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, and `webhook_id` are pulled unauthenticated from headers: [2](#0-1) 

`Registry.process` validates only the HMAC over that body and then forwards the *header* value of `shop` (not anything cryptographically bound to it) to the application's webhook handler as the authoritative tenant identifier: [3](#0-2) 

The identity binding that should hold is:
`shop value covered by HMAC == shop value used by the handler for tenant-scoped actions`

Here that equality does not hold: the HMAC only authenticates the raw JSON body bytes; it says nothing about which shop the request claims to be from. Any party in possession of one validly-signed webhook body/HMAC pair for tenant A (trivially available to any merchant who installs the app on their own shop and captures their own webhook deliveries) can resend that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header for tenant B. `Utils::HmacValidator.validate` will still succeed because it only checks the unchanged raw body against the HMAC, and `Registry.process` will invoke the handler with `shop: "tenant-B"` even though the body content originated from and was signed for tenant A's shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: a value that host applications treat as an authenticated tenant identifier (`WebhookMetadata#shop`, consumed directly by application handlers to scope database writes, notifications, etc.) is in fact attacker-controlled and decoupled from the HMAC-verified payload. This is a cross-tenant confusion vulnerability — data cryptographically bound to shop A can be attributed to shop B purely by changing an unauthenticated header, satisfying the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Low difficulty / low privilege required: any user who can install the app on a shop they control can legitimately receive one authentic webhook (valid body + HMAC), then replay it against the app's public webhook endpoint with only the `shop-domain` header changed. No secrets, tokens, or elevated access are needed — only a single previously-seen valid webhook and the ability to send an HTTP POST to the app's public webhook receiver.

### Recommendation
- Short term: Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the HMAC-signable content, or otherwise cryptographically bind the claimed shop to the verified payload before it is exposed via `WebhookMetadata`.
- Long term: Adopt one consistent verification approach across the library so that every field consumed downstream as an identity/tenant indicator is provably covered by the same signature that gates request acceptance.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and captures one legitimate webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `HMAC(secret, B) == H`), along with `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker sends a new POST to the app's public webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers/body [4](#0-3) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`= B`) only, and it matches `H`, so validation passes [5](#0-4) .
5. The handler is invoked with `shop: "victim-shop.myshopify.com"` even though body `B` was never signed for, nor originated from, that shop [6](#0-5) .

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
