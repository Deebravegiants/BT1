### Title
Unconditional relayer fee `safeTransfer` in `EvmHost.dispatchIncoming`/`dispatchTimeOut` can be blocked by a paused fee token, DoS'ing GET-response and timeout delivery - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost` pays out or refunds the relayer fee in the configured `feeToken()` via `IERC20(feeToken()).safeTransfer(...)` immediately after successfully invoking the destination module's callback (`onGetResponse`, `onGetTimeout`, `onPostRequestTimeout`). These transfers are not wrapped in any try/catch, unlike the module callback itself, which is invoked via a low-level `.call` whose failure is tolerated and simply un-does the receipt so it can be retried.

The same unconditional pattern appears for GET request timeouts and POST request timeouts: [2](#0-1) [3](#0-2) 

Contrast this with the module-callback invocation, which is deliberately allowed to fail without reverting the whole transaction so it can be retried later: [4](#0-3) 

If `feeToken()` is a pausable ERC20 (or otherwise reverts on transfer, e.g. during a pause window) and it is paused at the time a relayer submits a proof for delivery, the `safeTransfer` call reverts. Because this transfer is not guarded, the entire `dispatchIncoming`/`dispatchTimeOut` call reverts — even though the module callback (`onGetResponse`/`onGetTimeout`/`onPostRequestTimeout`) already executed successfully. These entry points are called by `HandlerV2` (`evm/src/core/HandlerV2.sol`) when a relayer submits proofs to deliver GET responses or timeouts; `HandlerV2` batches multiple message deliveries per call, so a revert here reverts the *entire batch transaction*, not just the affected message.

### Impact Explanation
This blocks delivery of GET responses and timeouts (and their associated protocol logic in downstream apps such as the Intent Gateway's cancellation/settlement flow, which relies on GET responses to release escrow — see `IntrinsicIntents.sol`/`ExtrinsicIntents.sol` `onGetResponse`/`withdraw`) for as long as the fee token remains paused. Any relayer batch containing an affected commitment cannot complete, and since the module-side effects (`onGetResponse` etc.) already ran but the receipt commitment write happens before the callback, retried submissions would re-invoke the same callback path. Depending on downstream module idempotency, this can either stall settlement (temporary freeze of escrowed funds pending cancellation, DoS of the relayer's fee collection) or force relayers to stop servicing that state machine, since they cannot get paid. This aligns with the reported bug class: pausable-token reverts breaking payout/settlement flows in a way not anticipated by the code's error-tolerant design for the callback itself.

### Likelihood Explanation
Low likelihood of the token actually pausing (it requires the external fee-token operator to trigger a pause, not an attacker action), but when it happens the blast radius is broad: it affects the shared `feeToken()` used network-wide by all `EvmHost` message deliveries with a non-zero fee, and batches other unrelated commitments in the same relayer transaction. This matches the external report's classification as Medium severity — rare precondition, high-impact effect.

### Recommendation
Wrap the fee transfer/refund in a try/catch (or use a low-level `call` with a success check similar to the module callback pattern) so that a failing fee-token transfer does not revert the whole delivery. On failure, either retain the fee liability in storage for later retrieval, or emit an event and let a separate withdrawal path collect it, mirroring the "so that it can be retried" pattern already used for the module callback.

### Proof of Concept
1. Configure `EvmHost.feeToken()` to point to a pausable ERC20 (e.g., an OZ `ERC20Pausable`/BNB-like token).
2. A user dispatches a GET request with `fee != 0`, recorded in `_requestCommitments[commitment].fee`.
3. Before the relayer submits the response proof, the fee-token owner calls `pause()`.
4. The relayer submits the GET-response proof through `HandlerV2`, which calls `EvmHost.dispatchIncoming(GetResponse, relayer)`.
5. The module callback `onGetResponse` executes successfully (`success == true`), but the subsequent `IERC20(feeToken()).safeTransfer(relayer, fee)` call at `evm/src/core/EvmHost.sol:844` reverts because the token is paused.
6. The entire `dispatchIncoming` transaction reverts, including any other unrelated message deliveries batched in the same `HandlerV2` call, blocking delivery until the token is unpaused.

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
