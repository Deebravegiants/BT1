### Title
Unprotected `CallDispatcher.dispatch()` allows anyone to drain tokens/ETH transiently held by the shared dispatcher during order/message execution - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch()` is `external` with **no caller restriction, no reentrancy guard, and no check that the invocation originates from a legitimate `IApp.onAccept`/`_execute` flow**. It is the exact same bug class as the Starstream `DistributorTreasury.execute` incident: an unprotected external function that can be used to trigger arbitrary external calls from a contract that is expected to only ever be invoked by a trusted caller. [1](#0-0) 

### Finding Description
`CallDispatcher` is a single shared utility contract deployed once per chain and wired into multiple independent apps: `IntentGatewayV2`/`IntentsBase` (`_execute`), `HyperFungibleToken.onAccept`, `WrappedHyperFungibleToken.onAccept`, and `BridgeToken`. [2](#0-1) [3](#0-2) 

Its `dispatch(bytes)` function decodes a `Call[]` and blindly forwards `to.call{value}(data)` for every element — it never checks `msg.sender`: [1](#0-0) 

The documentation itself acknowledges the dispatcher "holds tokens temporarily during execution," which is the exact precondition an attacker needs: [4](#0-3) 

Two reachable attack surfaces stem from this:
1. **Direct external call**: because `dispatch()` has no access control, *anyone* can call it directly (not just the app that is supposed to own the flow). If any ERC20 balance or ETH is ever left sitting on the CallDispatcher address — e.g., a swap-router that sends output tokens to the dispatcher before the sweep step runs in `IntentsBase._execute`, or a token mint/unlock in `HyperFungibleToken.onAccept`/`WrappedHyperFungibleToken.onAccept` that lands on the dispatcher before its optional calldata executes — an attacker's own crafted `Call[]` can sweep that balance to themselves before the legitimate sweep/forward step executes.
2. **Reentrancy through the call target**: `IntentsBase._execute` first calls `ICallDispatcher(dispatcher).dispatch(order.output.call)` (the solver-supplied composable call, which can target an attacker-controlled contract), and only afterwards sweeps residual balances back with a second `dispatch` call: [5](#0-4) 

Since `dispatch()` has no reentrancy guard, an attacker-controlled `to` invoked from within `order.output.call` can re-enter `CallDispatcher.dispatch()` and redirect any token/ETH balance that has already landed on the dispatcher (e.g., from an earlier leg of a multi-hop composable call, or DEX swap proceeds) before the legitimate `_execute` sweep runs — permanently diverting funds that were meant to flow back to `IntentsBase`/the beneficiary.

This mirrors the Starstream root cause precisely: the `DistributorTreasury.execute`-style function was `external`, unguarded, and could be used to trigger arbitrary calls out of a contract that legitimate flows expected to be the only caller of it.

### Impact Explanation
Any token or native-asset balance transiently resident on the shared `CallDispatcher` — across any of the apps that use it (IntentGatewayV2 solver fills, HyperFungibleToken/WrappedHyperFungibleToken cross-chain receives, BridgeToken) — can be redirected to an attacker instead of the intended recipient. This is a direct theft-of-funds vector reachable by any unprivileged relayer/solver/attacker who can either (a) call `dispatch()` directly, or (b) supply a malicious contract as a call target inside legitimate order/message calldata to reenter `dispatch()`.

### Likelihood Explanation
The precondition (funds transiently on the `CallDispatcher`) is explicitly acknowledged as an expected, documented state of the system ("the dispatcher contract holds tokens temporarily during execution"), and `order.output.call` / `message.data` are attacker/solver-supplied fields that can name arbitrary contracts as call targets. No privileged role is required — a single submitted order (IntentGatewayV2) or a single cross-chain message with calldata (HyperFungibleToken family) is sufficient to set up the reentrant call.

### Recommendation
- Restrict `CallDispatcher.dispatch()` to a caller allowlist (e.g., `onlyAuthorizedCaller` set at construction/config, similar to `onlyHost` patterns used elsewhere) so arbitrary EOAs/contracts cannot invoke it directly.
- Add a reentrancy guard to `dispatch()` so a call executed mid-dispatch cannot recursively invoke `dispatch()` again.
- In `IntentsBase._execute`, perform the sweep atomically with the execute call (or verify no attacker-reachable balance window exists) rather than relying on a second, separate `dispatch()` invocation after the first one returns.

### Proof of Concept
Note: I was not able to fully trace whether `IntrinsicIntents`/`ExtrinsicIntents` transfer output-asset tokens to the `dispatcher` address *before* calling `_execute` (which would create a directly drainable balance) due to running out of investigation budget — this should be verified against `evm/src/apps/intentsv2/IntrinsicIntents.sol` and `ExtrinsicIntents.sol`'s `_fillSameChain`/`_fillCrossChain` implementations. Conceptual PoC:
1. Solver submits an order via `IntentGatewayV2` with `order.output.call` pointing to an attacker-controlled contract `Evil`.
2. During `_execute`, `CallDispatcher.dispatch(order.output.call)` calls `Evil`.
3. `Evil` reenters `CallDispatcher.dispatch()` directly (no access control blocks it) with a `Call[]` that sweeps any token/ETH balance currently on the `CallDispatcher` to `Evil`'s own address.
4. The legitimate sweep-back call in `_execute` (lines 501-545) subsequently finds zero balance, and the funds intended for the protocol/beneficiary are lost to the attacker. [6](#0-5)

                revert NotContract(to);
            }

            if (!success) revert CallFailed(to, result);
        }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

    function _execute(Order calldata order, uint256 outputsLen) internal {
        if (order.output.call.length == 0) return;

        address dispatcher = _params.dispatcher;
        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            } else {
                uint256 balance = IERC20(token).balanceOf(dispatcher);
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({
                        to: token,
                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
                    });
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            }

            unchecked {
                ++i;
            }
        }

        if (sweepCount > 0) {
            Call[] memory finalCalls = new Call[](sweepCount);
            for (uint256 i; i < sweepCount;) {
                finalCalls[i] = sweepCalls[i];
                unchecked {
                    ++i;
                }
            }
            ICallDispatcher(dispatcher).dispatch(abi.encode(finalCalls));
        }
    }
