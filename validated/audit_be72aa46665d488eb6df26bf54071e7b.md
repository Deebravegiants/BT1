### Title
Poa Bridge withdrawal status resolution matches only by `assetId`, allowing wrong destination’s completion/hash to be reported for a different batched withdrawal - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain completion status of a withdrawal by looking up the PoA relayer’s withdrawal list and selecting the entry whose `defuse_asset_identifier` equals the withdrawal’s `assetId`. It does not disambiguate by `index`, `destinationAddress`, or `amount`. When a caller batches multiple withdrawals of the **same** `assetId` (e.g. splitting one token to two different destination addresses in a single intent, which the SDK explicitly supports via `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` with index-correspondence guarantees), the lookup can bind the wrong on-chain transaction hash/status to the wrong index.

### Finding Description
`describeWithdrawal` in `PoaBridge` is implemented as: [1](#0-0) 

The comment at the call site states explicitly: *“Response list is unsorted, so we match by assetId instead of index”*. The matching helper `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` is only given the asset identifier — it is never given `args.index`, `args.withdrawalParams.destinationAddress`, or `args.withdrawalParams.amount` to disambiguate between multiple withdrawals of the same asset within the same NEAR transaction.

The SDK’s own batch-withdrawal contract (`sdk.createWithdrawalCompletionPromises`, `sdk.waitForWithdrawalCompletion`) guarantees strict index correspondence between `withdrawalParams[i]` and the returned `promises[i]` / result `[i]`: [2](#0-1) 

Each per-withdrawal promise is driven by `watchWithdrawal`, which polls `bridge.describeWithdrawal` using the `WithdrawalIdentifier` created for that specific index: [3](#0-2) 

Because `PoaBridge.describeWithdrawal` only filters by `assetId`, if two (or more) withdrawals within the same batch/intent share the same `assetId` but different `destinationAddress`/`amount` (a supported and documented use case — batching multiple withdrawals in one intent), the relayer’s response for that asset can be non-deterministically bound to whichever index queries it first. This breaks the equality that the reported completion status/txHash for withdrawal `i` must correspond to the actual on-chain outcome of withdrawal `i`, not of a different withdrawal `j` of the same asset in the same batch.

The existing test explicitly documents that matching happens by `assetId`, not index, but only exercises the case where the two batched withdrawals have **different** asset ids (so it incidentally still resolves correctly): [4](#0-3) 

No test covers same-`assetId` multi-destination batching, and the implementation provides no mechanism to disambiguate that case.

### Impact Explanation
If a caller batches two withdrawals of the same PoA-bridged asset to two different destination addresses, `describeWithdrawal` can report the completed transaction hash / status of destination B against index A (and vice-versa). An integrator relying on the documented index correspondence (`promises[i]` ↔ `withdrawalParams[i]`) to reconcile withdrawals (e.g., mark a user’s withdrawal as settled and release funds/credits) would attribute a transaction hash to the wrong end-user. This can cause:
- A user’s withdrawal being marked “completed” with a transaction that actually paid a different address (misreport of the on-chain outcome).
- Double crediting: integrator sees withdrawal[0] “completed” using the same tx hash that actually belongs to withdrawal[1], and later also resolves withdrawal[1] with the same or another matching entry, potentially crediting both users based on a single actual transfer.

This matches the High-impact class: “a status or hash misreport making an integrator credit or refund twice.”

### Likelihood Explanation
Likelihood requires: (1) a batch of withdrawals containing two or more entries with the same `assetId` but different destination/amount routed through the PoA bridge, and (2) the relayer’s withdrawal list containing multiple entries for that asset (which happens naturally once both withdrawals are submitted in the same underlying NEAR transaction, since `getWithdrawalStatus` is queried by NEAR tx hash and returns all entries for that tx). Since batching is a first-class, documented SDK feature (`processWithdrawal`, `createWithdrawalCompletionPromises`) and nothing prevents two same-asset withdrawals in one call, this is straightforward to trigger without any privileged or malicious actor — it can occur in normal integrator usage.

### Recommendation
Update `findMatchingWithdrawal` (and its call in `PoaBridge.describeWithdrawal`) to disambiguate using additional fields already available on both the `WithdrawalIdentifier` and the relayer response — e.g., `destinationAddress`/`address`, `amount`, and ideally a stable per-withdrawal correlation id — rather than `assetId` alone. If the relayer response provides no way to disambiguate multiple same-asset withdrawals from a single NEAR transaction, the SDK should either: reject/serialize batched same-asset withdrawals to separate NEAR transactions, or explicitly document and guard against batching multiple same-`assetId` withdrawals through the PoA route until the relayer API exposes a disambiguating field.

### Proof of Concept
1. Call `sdk.processWithdrawal` (or `createWithdrawalCompletionPromises`) with `withdrawalParams = [{assetId: "nep141:eth.omft.near", amount: A, destinationAddress: addrA, ...}, {assetId: "nep141:eth.omft.near", amount: B, destinationAddress: addrB, ...}]` routed via PoA bridge, in the same intent/NEAR transaction.
2. The relayer’s `getWithdrawalStatus(nearTxHash)` returns two `withdrawals` entries with `defuse_asset_identifier: "nep141:eth.omft.near"`, one for `addrA`, one for `addrB`, with distinct `transfer_tx_hash`.
3. `describeWithdrawal` is invoked once per index (`index: 0`, `index: 1`) each with the same `withdrawalParams.assetId`, per [5](#0-4) .
4. `findMatchingWithdrawal` selects a withdrawal by `assetId` only, so both calls can resolve to the same (e.g., the first-found) entry, causing `promises[0]` and/or `promises[1]` to report a `txHash`/status that does not correspond to the actual withdrawal made to that index’s destination address.

Note: I was unable to retrieve the exact body of `findMatchingWithdrawal` in this session (tool access ended before that read completed), so the precise selection logic (e.g., whether it takes the first match, last match, or something else) is unconfirmed. This does not change the core finding — the call site’s own comment confirms matching is done by `assetId` and explicitly not by index — but the exact tie-breaking behavior when multiple entries share the same `assetId` should be verified directly in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.ts` (or wherever `findMatchingWithdrawal` is defined) before implementing the fix.
