### Title
User-centric signup enrollment status is finalized locally from the app-supplied flag, bypassing the authoritative backend duplicate/fraud verification round-trip - (File: `src/plans/mod.rs`)

### Summary
In the Fractional buyout report, the vault's `SUCCESS` state (`totalSupply`) was allowed to become authoritative before the external verification/side-effects that were supposed to gate it had actually completed, because the code took a shortcut that skipped the canonical check-then-update ordering. The same class of bug exists in `MasterPlan::do_signup`: when a signup is flagged `user_centric_signup` (a boolean carried in `backend::user_status::UserData`, ultimately sourced from the user's app via the QR-link payload), the orb sets `enrollment_status` to `Success`/`Error` purely from the *locally computed* `signup_reason`, entirely skipping the `enroll_user::Plan::run` call that normally performs the backend `signup_post`/`signup_poll` round-trip.

### Finding Description
`MasterPlan::do_signup` computes `signup_reason` locally (based on whether the biometric pipeline succeeded and local fraud detection) and then branches: [1](#0-0) 

```rust
let success = if user_centric_signup && !orb.config.lock().await.ignore_user_centric_signups
{
    debug_report.enrollment_status(match signup_reason {
        SignupReason::Normal => enroll_user::Status::Success,
        _ => enroll_user::Status::Error,
    });
    signup_reason == SignupReason::Normal
} else {
    Box::pin(self.enroll_user(orb, debug_report, &capture, pipeline.as_ref(), signup_reason))
        .await
        .is_success()
};
```

In the `else` branch, `enroll_user::Plan::run` performs the real state-finalizing sequence: it POSTs the signup to the backend (`signup_post::request`) and then polls (`signup_poll::request`) until the backend reports `Completed`/`success: true`. That poll loop is explicitly documented to catch "Backend duplicates … Backend legacy signup requests … Backend inflight matches … Backend detected fraud" before the enrollment status is allowed to become `Success`: [2](#0-1) 

When `user_centric_signup` is `true`, none of that backend confirmation ever happens — `debug_report.enrollment_status` (and consequently `SignupResult.success`, used to drive `dbus::Signup::signup_finished`, `self_serve::orb::v1::SignupEnded`, and the success telemetry counters) is committed as `Success` based solely on the local pipeline result: [3](#0-2) 

`user_centric_signup` itself originates from `orb_qr_link::UserData` returned in the backend's `user_status` response, but that response is driven by data supplied by the user's app during the signup and is only verified against a HMAC of the QR payload — it is not an out-of-band, orb-independent confirmation that the backend has actually finished/deduplicated the signup: [4](#0-3) 

This mirrors the `redeem`-before-`totalSupply`-update pattern: a state that is supposed to only become "success"/final after an authoritative external confirmation step is instead finalized based on locally available data, with the confirmation step (here, the `signup_post`/`signup_poll` backend round trip that detects duplicates/fraud/in-flight matches) skipped entirely for a code path that is reachable using app-controlled input (`user_centric_signup`).

### Impact Explanation
If the user-centric-signup path is taken, a signup can be marked `Success` on the Orb side without the backend ever confirming that the signup was uniquely accepted, was not a duplicate, was not an in-flight match, or was not flagged for fraud by the backend. This can lead to misattributed or duplicated signup outcomes being reported as successful (UI, dbus `signup_finished`, self-serve relay `SignupEnded`, and success metrics), i.e. a signup state bleed analogous to the buyout module reaching `SUCCESS` without the totalSupply/verification step it was supposed to depend on.

### Likelihood Explanation
The vulnerable branch is gated by `user_centric_signup && !ignore_user_centric_signups`. `user_centric_signup` is a boolean field surfaced through the app-provided QR-link payload and is exercised whenever the operator/backend enables app-centric signup mode for a user, so the code path is reachable under normal, expected app-driven signup flows rather than requiring privileged access — it does not require compromising the Orb, only controlling/observing the app-side signup configuration that sets this flag. I could not verify from the available index what specific conditions the backend uses to set `user_centric_signup` to `true`, so the exact operational likelihood (how often/under what real-world conditions this branch executes) is uncertain and would need confirmation against backend/app configuration outside `orb-core`.

### Recommendation
Do not allow `enrollment_status`/`SignupResult.success` to be finalized as `Success` purely from the locally computed `signup_reason` when `user_centric_signup` is set. Route user-centric signups through the same backend confirmation (`signup_post` + `signup_poll`) used in `enroll_user::Plan::run`, or otherwise require an explicit backend acknowledgment that duplicate/fraud/in-flight checks passed before marking `enrollment_status` as `Success`.

### Proof of Concept
Not directly executable from the indexed files: reproducing this requires driving `MasterPlan::do_signup` with a `qr_codes.user_data.user_centric_signup == true` (obtainable by controlling the app-supplied QR-link `UserData.user_centric_signup` field verified in `src/backend/user_status.rs:203-244`) and `ignore_user_centric_signups == false` in config, then completing a biometric capture/pipeline locally. Because the code path shown at `src/plans/mod.rs:639-656` never calls `enroll_user::Plan::run`, the resulting `enrollment_status`/`SignupResult.success` is set to `Success` without any `signup_post`/`signup_poll` backend confirmation ever occurring, unlike the `else` branch. Full exploit confirmation (e.g., proving what value the backend actually assigns to `user_centric_signup` and under what conditions) would require code/config outside this repository's index; a Devin session with full repo/backend access could validate this further.
