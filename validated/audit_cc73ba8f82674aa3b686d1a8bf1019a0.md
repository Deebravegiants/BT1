### Title
Permanent freeze of Deposit/Withdraw/WithdrawPnl via unconditional `CalcPnlError` revert in `calc_take_pnl` after invariant drifts below the last recorded PnL checkpoint - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` is invoked by `process_deposit`, `process_withdraw`, and `process_withdraw_pnl`, and it unconditionally reverts with `AmmError::CalcPnlError` whenever the current pool invariant (`pool_pc_amount * pool_coin_amount`) is smaller than the invariant recorded at the last PnL checkpoint (`target.calc_pnl_x * target.calc_pnl_y`). Critically, `process_swap_base_in`/`process_swap_base_out` and their `_v2` variants **never update** `target_orders.calc_pnl_x`/`calc_pnl_y` nor call `calc_take_pnl` at all — only Deposit/Withdraw/WithdrawPnl do. This mirrors the Cega bug class: a state field is updated unconditionally/naively by one code path (here: swaps changing vault balances without updating the checkpoint) while a *different, unconditional* check in another code path (`calc_take_pnl`) later reverts hard based on stale/mismatched values, with no recovery path — freezing the vault (here: freezing deposits/withdrawals). [1](#0-0) 

### Finding Description
`calc_take_pnl` gates all of its PnL-taking and invariant-updating logic behind:
```rust
if pool_pc_amount.checked_mul(pool_coin_amount).unwrap()
    >= (calc_pc_amount).checked_mul(calc_coin_amount).unwrap()
{ ... } else {
    return Err(AmmError::CalcPnlError.into());
}
``` [2](#0-1) 

`pool_pc_amount`/`pool_coin_amount` are derived from live vault balances via `Calculator::calc_total_without_take_pnl_no_orderbook`, which simply subtracts the already-accrued `need_take_pnl_pc`/`need_take_pnl_coin` from current vault balances: [3](#0-2) 

`calc_pc_amount`/`calc_coin_amount` are restored from `target.calc_pnl_x`/`calc_pnl_y`, the last-updated invariant checkpoint, which is only mutated inside `process_deposit`/`process_withdraw`: [4](#0-3) [5](#0-4) 

Meanwhile, `process_swap_base_in`/`process_swap_base_out` (and `_v2` variants) mutate the vault balances via SPL token transfers but never touch `target_orders.calc_pnl_x`/`calc_pnl_y`: [6](#0-5) 

Because `restore_decimal`/`normalize_decimal_v2` perform integer (truncating) division when normalizing between `sys_decimal_value` and native token decimals, and because `calc_take_pnl`'s comparison is done in normalized-decimal space while a large sequence of small swaps (each individually respecting the constant-product with fees) is executed in raw-decimal space, an attacker fully controlling the `amount_in`/`amount_out` on each of many chained swap transactions can drive the *normalized* comparison `pool_pc*pool_coin < calc_pc*calc_coin` to become true through accumulated truncation loss, even though the underlying raw-token invariant technically never decreases. Because the comparison and revert are unconditional and there is no code path that ever resets or re-synchronizes `target.calc_pnl_x`/`calc_pnl_y` except successful Deposit/Withdraw/WithdrawPnl (all of which themselves call `calc_take_pnl` first and will hit the same revert), once the condition is violated the vault permanently cannot process Deposit, Withdraw, or WithdrawPnl — this is a hard `.unwrap()`-free but still unconditional `Err(...)` with no admin recovery instruction that clears/reinitializes `target.calc_pnl_x`/`calc_pnl_y` independent of this same check.

### Impact Explanation
If triggered, `process_deposit`, `process_withdraw`, and `process_withdraw_pnl` will permanently revert for the affected pool. This freezes LP funds (no depositor can add liquidity, no LP holder can redeem their LP tokens for underlying tokens, and PnL cannot be withdrawn by the pool owner), a permanent freezing-of-funds impact. Swaps remain callable since they don't touch `calc_take_pnl`, but the pool's liquidity becomes irrecoverable by depositors — consistent with the "Medium/High/Critical, permanent freezing of user or LP funds" criteria.

### Likelihood Explanation
This requires an attacker to precisely engineer a sequence of swap instructions (attacker-chosen `amount_in`/`amount_out`, alternating directions/extreme ratios) to accumulate enough decimal-normalization truncation drift to flip the invariant comparison in `calc_take_pnl`. This is a multi-transaction, precision-dependent attack whose exact feasibility depends on the magnitude of `sys_decimal_value` vs. native decimals and the size of trades relative to pool depth — I was not able to fully verify with a concrete numeric trace within the available tool budget whether realistic pool parameters (e.g., 6-9 decimal SPL tokens) allow accumulating sufficient truncation loss within an economically feasible number of transactions to flip the comparison. This uncertainty affects the likelihood rating; it is plausible but unconfirmed by a full worked numeric proof-of-concept.

### Recommendation
- Update `target_orders.calc_pnl_x`/`calc_pnl_y` (or otherwise track the invariant baseline) on every swap, not just Deposit/Withdraw/WithdrawPnl, so the checkpoint used in `calc_take_pnl` never falls stale relative to swap-driven balance changes.
- Replace the hard revert in `calc_take_pnl`'s `else` branch with a no-op/skip-PnL-taking path when `pool_pc*pool_coin < calc_pc*calc_coin` (treat the deviation as zero deliverable PnL) rather than aborting the entire deposit/withdraw transaction, so Deposit/Withdraw always remain callable regardless of small invariant fluctuations from rounding.
- Perform the invariant comparison using consistent precision (e.g., compare in raw/native decimal space or use higher-precision fixed point) to eliminate normalization-induced truncation drift as a trigger.

### Proof of Concept
1. Attacker (or anyone) repeatedly calls `swap_base_in`/`swap_base_out` with amounts chosen to maximize decimal-normalization truncation loss (e.g., alternating tiny swaps at the boundary of `normalize_decimal_v2`'s integer division), across coin/pc mints with differing decimals so `sys_decimal_value` truncation is asymmetric between the two legs. [7](#0-6) 
2. These swaps never update `target_orders.calc_pnl_x`/`calc_pnl_y` (only Deposit/Withdraw do), so the checkpoint becomes stale relative to the live vault ratio. [6](#0-5) 
3. Once accumulated truncation drift causes `pool_pc_amount.checked_mul(pool_coin_amount) < calc_pc_amount.checked_mul(calc_coin_amount)` in normalized space, any subsequent call to `process_deposit`, `process_withdraw`, or `process_withdraw_pnl` reaches `calc_take_pnl` and unconditionally returns `Err(AmmError::CalcPnlError)`. [8](#0-7) 
4. Because there is no unprivileged or privileged instruction that resets `target.calc_pnl_x`/`calc_pnl_y` independently of this same failing check, the vault is permanently unable to process Deposit/Withdraw/WithdrawPnl, freezing LP funds.

        pc_amount: u64,

    }
