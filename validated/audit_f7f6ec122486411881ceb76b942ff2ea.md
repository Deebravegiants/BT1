### Title
Accrual-time scaled-value overflow can permanently freeze a market before the borrow-index cap - (File: common/src/rates/simulate.rs)

### Summary
A market whose scaled debt or supply value overflows `i128` during interest accrual makes every state-changing path that synchronizes that market panic with `MathOverflow`. Because `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `recapitalize`, `claim_revenue`, and `update_indexes` all accrue first, once the market crosses this boundary there is no in-contract recovery path and the market's cash, debt, supply claims, and unclaimed revenue remain frozen.

### Finding Description
`common/src/rates/simulate.rs:60-61` computes `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)` at the start of `accrue_step`, before `update_borrow_index` can clamp the index. `scaled_to_original` is a half-up `Ray::mul` (`common/src/rates/scaling.rs:14-16`, `common/src/math/fp.rs:50-52`) backed by `mul_div_half_up`, which panics with `GenericError::MathOverflow` when the resulting RAY value does not fit `i128` (`common/src/math/fp_core.rs:108-118`).

The mutating accrual loop in `contracts/pool/src/interest.rs:20-33` runs this step before marking the market accrued, and callers reach it through `Cache` market synchronization. The pool README states every market mutation accrues first (`contracts/pool/README.md:71-80`). The overflow can therefore be triggered by permissionless `controller::update_indexes(caller, vec![hub_asset])`, after which `withdraw`, `repay`, and `liquidate` on the same market keep panicking because each retries the same accrual.

This is not the index-ceiling path: `update_borrow_index` clamps only after multiplying (`common/src/rates/index.rs:13-18`), and `scaled_to_original` overflows while computing the current value needed for utilization and rewards. The dedicated regression test reaches exactly this state and asserts that `update_indexes`, `withdraw`, and `repay` all revert with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:315-356`).

### Impact Explanation
Permanent freezing of funds. Once `borrowed * borrow_index` or `supplied * supply_index` exceeds the `i128` RAY domain, no user can repay, withdraw, liquidate, clean bad debt, claim revenue, or recapitalize that market through the controller, because the shared accrual precondition panics before any repayment or write-down logic runs. Pool cash backing the frozen supply cannot be recovered by an in-protocol path, and accrued revenue is unclaimable.

### Likelihood Explanation
Reachable only by unprivileged protocol use but at extreme scale: an account can `supply` large collateral, `borrow` a market to sustained high utilization, and later anyone can call `update_indexes`; repeated accrual can push the scaled value across the ceiling before the borrow index reaches `10^36`. The harness reproduces the cliff with an 18-decimal billion-unit market at 98% utilization over multi-year accrual, so the trigger is real but requires very large listed markets, caps that admit the exposure, and elapsed time.

### Recommendation
Make accrual value computation overflow-tolerant before it is used as a gate. Options: compute utilization and reward inputs with saturating/widened arithmetic and clamp them to a protocol-defined maximum instead of panicking; detect representability before `scaled_to_original` and degrade to the index cap or a safe bounded rate; or add governance/market admission limits that bound `scaled_amount * max_index` for every admitted market so the state cannot be reached. At minimum, add an explicit pre-accrual check with a recoverable error path that still permits repayment/withdrawal-sized operations that reduce the overflowing position.

### Proof of Concept
1. Create an 18-decimal market and collateral market with caps/utilization high enough to admit a roughly billion-unit debt book, matching the fixture in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-333`.
2. `supply` the large asset as liquidity and `borrow` about 98% of it from an overcollateralized account.
3. Advance ledger time in yearly chunks while calling permissionless `controller::update_indexes(caller, vec![BIG18])`.
4. After enough accrual, `update_indexes` panics with `MATH_OVERFLOW` inside `scaled_to_original` while `borrow_index` remains below `MAX_BORROW_INDEX_RAY`.
5. Subsequent `withdraw`, `repay`, and liquidation attempts on `BIG18` hit the same accrual panic, leaving suppliers and the protocol unable to operate that market.
