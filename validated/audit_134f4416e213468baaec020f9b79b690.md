### Title
Webhook `shop-domain` header is not covered by HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain` (and `topic`/`api-version`/`webhook-id`) HTTP header as the tenant identity passed to the app's handler. Because the header is never included in the signed payload, the cryptographic binding between "the request that was HMAC-verified" and "the shop the handler believes it came from" is broken.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is read directly and unauthenticatedly from the `shop-domain` header: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers the body) and then forwards `request.shop` straight into the handler's `WebhookMetadata` as the trusted tenant identifier, with no additional check that the header value is bound to the signed content: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) against the shared `api_secret_key`: [4](#0-3) 

The identity binding that should hold is:
`shop-domain header used by handler == shop that the HMAC-verified bytes originated from`

In this gem, the HMAC only authenticates `raw_body`; it says nothing about which shop sent it. The `api_secret_key` is a single value shared across *all* shops that have the app installed — it is not shop-specific. Consequently, any party who can obtain one legitimate `(raw_body, hmac)` pair signed with the app's secret (e.g., an unprivileged user who installs the app on their own store and receives real webhooks for it) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` (and `webhook-id`/`topic`) header. `Utils::HmacValidator.validate` will still pass, since it only checks the body, and the handler will process the payload attributing it to the attacker-chosen victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker-controlled webhook body is accepted as if it originated from an arbitrary victim shop, because the shop identity used to key any downstream session/data association is asserted by an unauthenticated header rather than being bound to the HMAC-verified bytes. Depending on how the host application uses `WebhookMetadata#shop` (commonly to look up/update the shop's session, sync local state keyed by shop, or trigger data changes scoped to that shop), this enables cross-tenant data corruption/access using only knowledge of the shared app secret's effect on one legitimate webhook, not the secret itself. This maps to the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation only requires the attacker to be a legitimate but unprivileged installer of the app on their own shop (or otherwise obtain one legitimate raw_body+hmac pair for the app) and the ability to send an arbitrary HTTP request to the app's webhook receiving endpoint with attacker-controlled headers — both of which are realistic for any developer/merchant able to install a public or custom app. No access token, `client_secret`, or privileged account is needed.

### Recommendation
Bind the shop identity cryptographically to the verified request instead of trusting an unauthenticated header: include `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) in the HMAC-signed payload used by `Request#to_signable_string`, or otherwise cross-check the header value against Shopify-provided, tamper-proof data before passing it to `WebhookMetadata`.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; capture a legitimate webhook delivery, e.g. `raw_body = "{}"` with its valid `x-shopify-hmac-sha256` value computed by Shopify using the app's shared `api_secret_key` (as shown in the test fixture pattern): [5](#0-4) 
2. Replay the exact same `raw_body` and `hmac` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against the secret; `Registry.process` then invokes the handler with `shop: "victim-shop.myshopify.com"`, causing the app to process attacker-supplied data under the victim shop's identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
