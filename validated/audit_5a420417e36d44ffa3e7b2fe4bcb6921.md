Based on my research, this codebase's OP-Stack fault-dispute-game consensus client (`modules/ismp/clients/optimism/src/lib.rs`) contains the analog of the reported bug class: the on-chain check that decides whether an output root is "safe to accept" does not match the real Optimism fault-proof finality rule.

### Title
On-chain "not challenged" check for FaultDisputeGame accepts unresolved/mid-window games as finalized, diverging from OP Stack's actual dispute-game finality rule - ([File: modules/ismp/clients/optimism/src/lib.rs])

### Summary
`verify_optimism_dispute_game_proof` / `verify_not_challenged` decide whether an Optimism L2 output root can be trusted purely from `claimData.length == 1` (for `FaultDisputeGame`) or `counteredByIntermediateRootIndexPlusOne == 0` (for `AggregateVerifier`). Neither check reflects the actual Optimism protocol rule for output finality, which requires the dispute game's `status` to have resolved to `DEFENDER_WINS` (or, for unchallenged games, that the `MAX_CLOCK_DURATION` / air-gap resolution window has fully elapsed) before the claim is considered final and non-reorgable, per the [Fault Dispute Games spec](docs/content/protocol/state-machine/fault-dispute-games.mdx). ### Finding Description
On real OP Stack, a dispute game's root claim is only *safe to trust as finalized* once the game's `resolve()`/`status` mechanics have run to completion — i.e., either the challenge clock for both sides has fully elapsed with no successful counter (`status == DEFENDER_WINS`) or an explicit resolution occurred. The Hyperbridge OP consensus client instead approximates "unchallenged" by reading `claimData.length` (or the AggregateVerifier's counter slot) at the *current* L1 block, and treats `claimData.length == 1` (i.e., no `move()` has been made yet) as proof the state root is trustworthy: [3](#0-2) 

This is structurally the same defect pattern as the Goldfinch analog in the report: the codebase substitutes a *local proxy heuristic* ("no counter-move has been submitted yet") for the *actual protocol-defined finality condition* ("the dispute game has fully resolved / the clock has run out"). A freshly created game has `claimData.length == 1` immediately upon creation and remains so until someone bothers to challenge it — this is true for the entire duration of the challenge window, not just after it has safely elapsed. Nothing in `verify_optimism_dispute_game_proof` checks `createdAt`, `resolvedAt`, `status`, or that `MAX_CLOCK_DURATION` has passed.

The comments in the code openly acknowledge this is only a "not yet challenged" check, not a "finality achieved" check: [4](#0-3) 

Because this consensus client feeds directly into `host.state_machine_commitment`, which HandlerV2/pallet-ismp use (after only the generic, operator-configured `challenge_period`) to admit POST/GET requests and responses from the L2, an attacker (a proposer or any actor who can create a dispute game with a forged root claim and simply not challenge it during the observation window used by the relayer) can get a malicious/incorrect L2 state root accepted as a trusted `StateCommitment` well before the real OP Stack protocol would consider that output final.

### Impact Explanation
If the operator's configured ISMP `challenge_period` for the OP-derived state machine is shorter than (or not aligned with) OP's actual dispute-game resolution window, a forged or premature output root can be accepted as a valid state commitment. Any request/response/message proven against that state root (storage proofs for `IntentGatewayV2`, request receipts, etc.) would then be accepted by `HandlerV2`/pallet-ismp as authentic, enabling forged message delivery, unauthorized app actions (e.g., fabricated `RedeemEscrow`/withdrawal proofs in the Intent Gateway), or unsound state commitments — a Critical/High-severity class of bug matching "forged message delivery" / "unsound state commitment" in the validation criteria.

### Likelihood Explanation
Likelihood depends on operator configuration of the per-state-machine `challenge_period` and the timing at which the relayer submits/accepts the dispute-game proof, both of which are external, adjustable, and not enforced to match OP's `MAX_CLOCK_DURATION`/resolution semantics anywhere in this code path. Because the check is a storage-layout heuristic rather than a protocol-state check, this is a latent design gap in the verifier itself, independent of any specific misconfiguration — making it reachable by any relayer/prover submitting a `ConsensusMessage` with an `OpFaultProofGames` proof for a claim that has not yet been resolved.

### Recommendation
Extend `verify_optimism_dispute_game_proof`/`verify_not_challenged` to additionally prove and check the game's resolution status (`status == DEFENDER_WINS`) or, at minimum, prove `createdAt + MAX_CLOCK_DURATION` (and any air-gap) has elapsed relative to the referenced L1 header before accepting the claim as final, rather than relying solely on `claimData.length == 1`/`counteredBy == 0`. Align this with the documented OP Stack dispute-game finality rule referenced in `docs/content/protocol/state-machine/fault-dispute-games.mdx`.

### Proof of Concept
Not independently exploitable in a sandbox from this analysis alone — I could not verify at what stage (relayer selection logic in `tesseract/consensus/op-host`, or the operator's configured ISMP `challenge_period`) an additional real-world timing safeguard might already compensate for this gap. I was unable to find any explicit `resolvedAt`/`status`/`MAX_CLOCK_DURATION` check anywhere in `modules/ismp/clients/optimism` or `tesseract/consensus/op-host` (confirmed via repo-wide grep for those terms, which only matched ABI JSON and unrelated files), which supports the conclusion that this check is genuinely missing, but a live/full-repo review (e.g., via a Devin session with complete file access) would be needed to confirm no compensating control exists elsewhere in the relayer or governance-configured challenge period defaults.

fn verify_not_challenged<H: Keccak256 + Send + Sync>(
	kind: &DisputeGameImpl,
	root: H256,
	proxy_address: H160,
	proxy_account_proof: Vec<Vec<u8>>,
	challenge_proof: Vec<Vec<u8>>,
) -> Result<(), Error> {
	if matches!(kind, DisputeGameImpl::OPSuccinct) {
		// OPSuccinctDisputeGame has no challenge mechanism by construction, so any game we
		// accepted as registered in the factory is unchallenged.
		return Ok(());
	}

	let proxy_storage_root =
		get_contract_account::<H>(proxy_account_proof, &proxy_address.0, root)?
			.storage_root
			.0
			.into();

	match kind {
		DisputeGameImpl::FaultDisputeGame => {
			// `claimData` is a dynamic `ClaimData[]` at `FAULT_DISPUTE_CLAIM_DATA_SLOT`. Solidity
			// stores a dynamic array's element count in the slot itself (the elements live at
			// `keccak256(slot)`). A freshly created, unchallenged game holds exactly one entry —
			// the root claim appended in `initialize()` — and every `move()` (attack or defense)
			// appends another. So `claimData.length == 1` iff the game has not been challenged.
			// Any other length (including absence, i.e. length 0 for a game that never registered
			// its root claim) is rejected.
			//
			// The MPT trie path for a direct storage slot is `keccak256(slot)`.
			let storage_key = U256::from(FAULT_DISPUTE_CLAIM_DATA_SLOT).to_big_endian();
			let trie_path = H::keccak256(&storage_key);
			let value = get_value_from_proof::<H>(
				trie_path.0.to_vec(),
				proxy_storage_root,
				challenge_proof,
			)?
			.ok_or(Error::ClaimDataSlotMissing)?;
			let raw = <alloy_primitives::Bytes as Decodable>::decode(&mut &*value)
				.map_err(|_| Error::DecodeClaimData(format!("{:?}", value)))?
				.0
				.to_vec();
			if raw.len() > 32 {
				Err(Error::ClaimDataTooLong)?
			}
			// RLP strips leading zeros from the stored length; reconstruct the uint256 and require
			// it to be exactly one.
			if U256::from_big_endian(&raw) != U256::one() {
				Err(Error::FaultDisputeGameChallenged)?
			}
			Ok(())
		},
