### Title
SimplexPaymaster trusts Chainlink `latestRoundData()` without validating against feed's min/max circuit-breaker bounds - ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster._getOraclePrice` only rejects a Chainlink answer that is `<= 0` or stale; it never compares the returned `answer` against the feed's `minAnswer`/`maxAnswer` circuit-breaker bounds. Any unprivileged user submitting a `UserOperation` chooses which registered token to pay gas with in `paymasterData`, and the resulting price feeds directly into how much of that token the paymaster charges for gas.

### Finding Description
`_getOraclePrice` is the sole validation applied to both the native-asset oracle and every registered token oracle: [1](#0-0) 

It checks only `answer <= 0` and staleness via `updatedAt`. Chainlink aggregators internally clamp `answer` to a hard-coded `minAnswer`/`maxAnswer` range; when the real market price of an underlying asset moves outside that range, the aggregator keeps reporting the boundary value rather than reverting or flagging the deviation — exactly the class of bug described in the referenced report. `_getOraclePrice` has no way to detect this condition, so a token or native asset in freefall (or a runaway spike) will continue to be priced at the stale floor/ceiling value indefinitely.

That mis-priced value feeds `_tokenPrice`, which determines the exact `tokenPrice` used to size prefunds and the eventual gas charge: [2](#0-1) 

`_tokenPrice` is invoked from `_fetchDetails` (called during normal UserOp validation for every gas payment) and from `_prefund`/`swapAndDeposit`: [3](#0-2) 

The token used is fully attacker-chosen: any address can submit a `UserOperation` naming any registered, active token in `paymasterData[1:21]`, with no allowlist restricting which unprivileged sender may trigger a price read.

### Impact Explanation
If a registered token's price collapses below its Chainlink feed's `minAnswer` (e.g. during a de-peg or flash crash of a non-major asset the paymaster comment explicitly allows — "any token with a Chainlink feed"), the aggregator continues returning the artificially high floor price. `_tokenPrice` then computes a `tokenPrice` (token units per wei) that is systematically too low, because the token appears more valuable in USD than it actually is. Every UserOp paid with that token undercharges relative to the true USD cost of gas, letting an attacker drain the paymaster's EntryPoint-deposited native balance by repeatedly paying gas with a near-worthless token that the oracle still prices at its frozen floor. Symmetrically, if `nativeOracle` (BNB/USD, ETH/USD, etc.) spikes past its `maxAnswer` ceiling and freezes there, every subsequent charge overcharges all paymaster users. Both directions are a direct, unbacked economic loss enforced purely by an on-chain price the paymaster cannot distinguish from a genuine, un-clamped reading — a concrete theft/drain of protocol funds, not merely a griefing vector.

### Likelihood Explanation
Likelihood is tied to real-world volatility of the weakest supported token/oracle pair, but requires no privileged access or governance compromise: any address that can submit a UserOperation through the standard ERC-4337 flow can pick the token and trigger the mispriced charge the moment a feed pins to its bound. Governance can mitigate exposure by choosing conservative tokens, but the contract itself provides no on-chain defense, so the vulnerability is live for the lifetime of every registered feed.

### Recommendation
In `_getOraclePrice`, fetch the aggregator's `minAnswer`/`maxAnswer` (via `AggregatorV3Interface(oracle).aggregator()` or a governance-configured bound per feed) and revert (e.g. a new `OraclePriceOutOfBounds` error) when `answer` is within a small tolerance of either extreme, mirroring the existing `StaleOraclePrice`/`InvalidOraclePrice` pattern already used for zero/negative answers and staleness. Alternatively, fall back to a secondary oracle or halt token acceptance for that asset until a human-reviewed price is restored.

### Proof of Concept
1. Governance registers a volatile token via `RegisterToken` with a Chainlink feed whose `minAnswer` is, say, `$0.10`.
2. The token's real market price crashes to `$0.001` during a de-peg/exploit event; the Chainlink aggregator's circuit breaker keeps `latestRoundData().answer` pinned at `$0.10`.
3. `_getOraclePrice` at `evm/src/utils/SimplexPaymaster.sol:662-676` accepts this value unconditionally (it is positive and fresh).
4. An attacker submits UserOperations with `paymasterData` selecting this token; `_tokenPrice` (`evm/src/utils/SimplexPaymaster.sol:653-658`) computes a gas price based on the false `$0.10` valuation instead of the true `$0.001`, so the attacker pays ~100x less real value than the gas actually costs.
5. Repeating this drains the paymaster's EntryPoint deposit funded by the treasury, at the expense of the protocol.

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
