## Answer

The ClamAV CVE's bug class — an out-of-bounds condition from unguarded arithmetic while "indexing remaining data" against attacker-influenced input — has a direct analog in `Router._computeBuy`'s overflow-cap branch.

### Title
Unguarded underflow in `Router._computeBuy`'s overflow-cap branch when a TOKEN donation inflates `tokenBalance()` above the stored virtual reserve, permanently freezing the tail of the bonding curve - (File: `packages/contracts/src/Router.sol`)

### Summary
`Router._computeBuy` caps `tokensOut` at the pair's live `tokenBalance()` and then computes `cappedReserveToken = reserveToken - tokensOut`. `reserveToken` is the *stored* virtual reserve, while `tokensOut` is set to the *live* `realBalance` when the cap binds. If an attacker inflates `realBalance` above `reserveToken` via a plain ERC20 donation of the launched `Token` to the pair, this subtraction underflows and every buy that would hit the overflow-cap path reverts with a Solidity Panic, permanently bricking the tail of the curve. [1](#0-0) 

### Finding Description
In `_computeBuy`:
```
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;   // underflows if realBalance > reserveToken
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    ...
}
``` [2](#0-1) 

`reserveToken` is the pair's *stored* virtual reserve (only mutated by `Pair.swap`), while `realBalance = pair.tokenBalance()` is a live `IERC20.balanceOf` read that includes any tokens directly donated to the pair via a plain `Token.transfer`. The codebase's own test suite proves the precondition `realBalance > reserveToken` is reachable: the "Donation attack regression" section in `test/Zap.t.sol` stages exactly this by draining the curve and then having an attacker `transfer` the bought tokens back to the pair directly (bypassing `sell`), which "drives `realBalance > reserveToken`." [3](#0-2) 

The project already recognized and patched this exact underflow shape in `Bonding.previewLtUntilGraduation`'s supply leg (`if (realBalance >= reserveToken) return ltUntilThreshold;`), with an explicit comment: "A TOKEN donation that drives `realBalance > reserveToken` previously underflowed `Bonding.previewLtUntilGraduation`'s supply leg, cascading into a `Zap.buy` DoS. Guard added." [4](#0-3) 

However, the identical subtraction in `Router._computeBuy`'s cap branch — the function actually invoked from every `Router.buy` call, reachable from `Bonding.buy` → `Zap.buy`/`Zap.buyWithPermit` for any unprivileged trader — has **no equivalent guard**. It only checks `cappedReserveToken == 0` *after* the subtraction, which in Solidity 0.8.x already reverts with a Panic before that check is ever reached if `tokensOut > reserveToken`. [5](#0-4) 

### Impact Explanation
Once `realBalance > reserveToken` is engineered (a trivial, permissionless ERC20 transfer of the launched `Token` into its own `Pair`), any buy that would need to fill the remainder of the curve (i.e., where uncapped `tokensOut` would exceed `realBalance`) reverts on arithmetic underflow instead of gracefully capping. This:
- Permanently freezes the remaining real token balance sitting in the `Pair` — no buyer can ever purchase past that point while the condition holds, since the cap branch (the only path that lets a buy consume the final chunk of `tokenBalance()`) always panics.
- Blocks the supply-side graduation trigger (`IPair.tokenBalance() == 0`), since the last buy that would drain the balance to zero can never complete; for tokens whose LT/USD value never crosses the USD trigger (documented flat/bear-market case), the token is permanently stuck in `Lifecycle.Curve`, with the curve-held tokens and any trader funds destined for that final purchase permanently unreachable.
This satisfies the "permanent freezing of trader ... funds" criterion, since real value (the unsold token allocation plus any trader's LT that would have completed that buy) becomes permanently unreachable through normal protocol operation.

### Likelihood Explanation
High. The precondition requires only a standard ERC20 `transfer` of the launched `Token` to its own `Pair` address — no privileged role, no special contract call, and the project's own regression tests demonstrate the exact `realBalance > reserveToken` state is reachable with an ordinary drain-then-donate sequence available to any wallet. No `BONDING_ROLE` or admin access is needed anywhere in the attack path.

### Recommendation
Add the same defensive guard used in `Bonding.previewLtUntilGraduation` to `Router._computeBuy`'s cap branch: check `realBalance >= reserveToken` (or equivalently guard the subtraction) before computing `cappedReserveToken`, and define a safe fallback behavior (e.g., treat it as already at the terminal state, matching how the analogous supply-leg preview degrades to the USD-leg-only path) rather than letting the subtraction underflow.

### Proof of Concept
1. Launch a token via `Zap.createToken` and buy through the curve enough that a large chunk of `curveSupply` (750M) is sold to a wallet — see `_stageDonationAttack` helper pattern already in the test suite. [6](#0-5) 
2. That wallet calls `Token(tokenAddr).transfer(pairAddr, donatedTokens)` directly (a plain, permissionless ERC20 transfer) to push `IPair(pairAddr).tokenBalance()` above the pair's stored `reserveToken`. [7](#0-6) 
3. Any subsequent trader calls `Zap.buy`/`Bonding.buy` with an amount large enough that uncapped `tokensOut` from `_computeBuy` would exceed the (now donation-inflated) `realBalance`. `Router._computeBuy` sets `tokensOut = realBalance`, then computes `cappedReserveToken = reserveToken - tokensOut`, which underflows and reverts (Panic 0x11), bricking that buy and every subsequent buy attempting to consume the remaining curve. [1](#0-0) 

Note: I was unable to fully trace whether any later code path (e.g., during `_prepareGraduationLiquidity`'s unconditional burn of `tokenBalance()` at graduation) can restore the invariant before this cap branch is hit in practice, since that only runs after graduation triggers — and the whole point of this bug is that the supply-trigger graduation path itself can be blocked by the same underflow. A background engineer should add a unit test mirroring `test_donation_realBalanceExceedsReserveToken` but driving an actual `Router.buy`/`Bonding.buy` call through the cap branch to confirm the revert empirically before landing the fix.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
```

    function _stageDonationAttack(
        address tokenAddr
    ) internal returns (uint256 drainLtSpent, uint256 donatedTokens) {
        address pairAddr = bonding.getTokenInfo(tokenAddr).pair;
        address drainer = makeAddr("donationDrainer");
        // Size the drain so `tokensOut > 250M` (the LP-reserve floor) under
        // any `VIRTUAL_LIQUIDITY_USD`. Constant-product math gives
        // `tokensOut = TOTAL_SUPPLY × ltIn / (virtual + ltIn)`, which crosses
        // 250M (= ¼ of TOTAL_SUPPLY) when `ltIn = virtual / 3`. Spending the
        // full opening virtual reserve lands `tokensOut = 500M` — plenty of
        // headroom to push `realBalance > reserveToken` after the donation.
        drainLtSpent = _initialVirtualLt();
        lt.mintDirect(drainer, drainLtSpent);
        if (!bonding.isRouter(drainer)) bonding.addRouter(drainer);
        vm.startPrank(drainer);
        lt.approve(address(curveRouter), drainLtSpent);
        bonding.buy(drainLtSpent, tokenAddr, 0, drainer);
        vm.stopPrank();
        donatedTokens = Token(tokenAddr).balanceOf(drainer);
        vm.prank(drainer);
        Token(tokenAddr).transfer(pairAddr, donatedTokens);
    }

    function test_donation_realBalanceExceedsReserveToken() public {
        address tokenAddr = _createToken(0);

        (, uint256 donated) = _stageDonationAttack(tokenAddr);
        assertGt(donated, 250_000_000 ether, "Drain must yield > 250M tokens to break the gap");

        uint256 realBalance = IPair(pairAddr).tokenBalance();
