Verifying the exact branch structure in the two preview helper functions and their guard checks in `deposit`/`redeem` confirms the claimed asymmetry is real and provable directly from the code.### Title
`deposit()` silently mints zero shares for a non-zero underlying deposit when `total-assets-preview()==0` and `total-supply-preview()>0`, while `redeem()` correctly reverts in the mirrored state - ([File: mainnet/contracts/vault/v0-vault-ststx.clar])

### Summary
`convert-to-assets-preview` (used by `redeem`) checks `ta==0` before `ts==0`, and `redeem` has an explicit `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` guard, so `redeem` safely reverts when `ta=0`. `convert-to-shares-preview` (used by `deposit`) checks `ts==0` *before* `ta==0`, and `deposit` has no equivalent zero-output guard, so when `ta=0` and `ts>0`, `deposit` accepts the depositor's underlying tokens and mints `(ok u0)` shares. This is a genuine, provable asymmetry between the two mirrored functions.

### Finding Description
Broken identity: `redeem_reverts_at_ta0 == deposit_reverts_at_ta0` should both be `true`; measured `redeem_reverts=true`, `deposit_reverts=false`.

- `convert-to-assets-preview` (lines 317-324): outer branch is `(if (is-eq ta u0) u0 ...)` — for `ta=0` it always returns `u0` regardless of `ts`.
- `redeem` (lines 797-831): computes `inkind (convert-to-assets-preview amount)` then `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` at line 811. When `ta=0`, `inkind=0`, and this assertion reverts the call with `ERR-OUTPUT-ZERO` (`u802012`). Redeem is safe in this state — the `ts==0` inner branch of `convert-to-assets-preview` is indeed dead code for any caller that already passed the `ta==0` check, but that doesn't matter because the outer branch already catches `ta==0` correctly.
- `convert-to-shares-preview` (lines 308-315): outer branch is `(if (is-eq ts u0) amount ...)`. When `ts>0` but `ta==0`, execution falls to the inner branch `(if (is-eq ta u0) u0 ...)`, returning `u0`.
- `deposit` (lines 763-795): computes `inkind (convert-to-shares-preview amount)` and only asserts `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` (line 776) and `(asserts! (> amount u0) ERR-AMOUNT-ZERO)` (line 775). There is **no** assertion that `inkind > 0`. With default `min-out=0`, `inkind=0` passes the slippage check trivially. The function proceeds to `(try! (receive-underlying amount account))` (line 779) — pulling the depositor's real tokens into the vault — then `(try! (ft-mint? zft inkind recipient))` mints `0` shares, and `(var-set assets (+ current-assets amount))` (line 781) increases `assets` (raising `ta` for everyone else), and returns `(ok u0)`.

Root cause: the two preview helpers check the zero-conditions in opposite order (`ta` first in one, `ts` first in the other), and only `redeem` has the corresponding zero-output guard; `deposit` is missing its mirrored guard.

Reachability: `ta==0` while `ts>0` cannot be produced by an ordinary unprivileged caller directly (it requires `assets` to be driven to `0` via `socialize-debt`, which is gated by `check-caller-auth`/`is-authorized-contract`, i.e., only callable by an authorized market/lending contract as part of normal bad-debt write-off). However, once that state legitimately arises through normal protocol operation (a bad-debt event socializing losses, leaving only the unredeemable `NULL-ADDRESS` minimum-liquidity shares, or other real shares, outstanding with `assets=0`), **any ordinary unprivileged user who then calls `deposit`** loses their entire deposited amount for zero shares — no privileged access is required for the depositor to trigger the loss, only for the state to be prior-established via the protocol's own normal debt-socialization flow.

### Impact Explanation
Per call in the vulnerable state (`ta=0`, `ts>0`), a depositor transfers `amount` of underlying `ststx-token` into the vault and receives `0` `zft` shares back — a full, non-slippage-bounded loss of principal (min-out=0 default does not protect against zero-output on deposit, since inkind itself is checked against min-out and 0>=0 passes). The lost value is not burned; it silently increases `assets`/`total-assets-preview` for the benefit of whoever holds the outstanding shares at that time (which continue to exist and can later be redeemed for a share of the now-larger asset pool). This is repeatable for every deposit made while the state persists, and the loss is borne entirely by depositors unaware of the zero-value state; value is transferred to existing shareholders — matching Critical impact ("direct theft of user funds at rest or in motion", closely bordering "permanent freezing of funds" for the depositor's principal).

### Likelihood Explanation
The triggering precondition (`ta=0`, `ts>0`) requires a prior bad-debt socialization event executed by an authorized lending-market contract, which is normal (non-privileged-attacker) protocol behavior in a severe-loss scenario, not a DAO compromise. Once that state exists, any unprivileged user calling `deposit` with default parameters (`min-out=0`) — the common case for most integrators/front-ends — triggers the loss with no special capital requirement beyond the deposit amount itself. It is fully repeatable for every subsequent depositor until the state changes.

### Recommendation
Add a zero-output guard in `deposit` mirroring `redeem`'s `ERR-OUTPUT-ZERO` check, e.g. `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` right after computing `inkind` in `deposit` (mainnet/contracts/vault/v0-vault-ststx.clar, near line 776), and/or align `convert-to-shares-preview`'s branch ordering with `convert-to-assets-preview` (check `ta==0` before `ts==0`) so that a `ta==0` state with outstanding shares cannot silently mint zero shares for a real deposit.

### Proof of Concept

2. As an authorized contract (test harness impersonating the authorized caller solely to *establish* the precondition state, not as part of the exploit itself), call `socialize-debt` with a scaled amount sized so `assets` becomes `u0` while `ts` remains `u1000`.
3. As the unprivileged attacker principal, call `(contract-call? .v0-vault-ststx deposit u1000000 u0 attacker)` and assert the result is `(ok u0)` and that the attacker's `ststx` balance decreased by `u1000000` while `zft` balance stays `u0`.
4. Separately, grant attacker `u1` `zft` share balance before step 2 sets `ta=0` (or use `NULL-ADDRESS`-equivalent held shares), then call `(contract-call? .v0-vault-ststx redeem u1 u0 attacker)` and assert it returns `(err u802012)`.
5. Assert the boolean identity: `redeem_reverts == true` and `deposit_reverts == false`, proving the asymmetry numerically (`amount-in=1000000`, `shares-minted=0` vs `redeem` reverting for `shares-burned=1`).
