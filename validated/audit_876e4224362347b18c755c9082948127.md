### Title
Webhook shop identity not bound to HMAC signature enables cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw webhook body, while the `shop` value used to route webhook processing to a specific tenant is taken from an HTTP header that is completely outside the HMAC's coverage. Because the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across every merchant that has the app installed, any merchant who legitimately receives webhooks for their own shop can replay a valid `(body, hmac)` pair while substituting an arbitrary `shop` header, and `ShopifyAPI::Webhooks::Registry.process` will accept it as authentic for the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop` from the `shopify-shop-domain` / `x-shopify-shop-domain` header: [1](#0-0) 

but `to_signable_string`, which is what actually gets HMAC-verified, only returns the raw request body: [2](#0-1) 

`Registry.process` verifies the request using this signable string and, if valid, dispatches the handler using `request.shop` taken straight from the (unverified) header: [3](#0-2) 

`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the supplied `hmac`: [4](#0-3) 

Since `to_signable_string` for webhooks is just the raw body, the `shop` header is never part of the signed material. The identity binding that should hold is:

`shop authenticated by the HMAC == shop used to attribute/process the webhook data`

but here the gem lets:

`shop covered by HMAC (none) != shop consumed by handler.handle (header value)`

The secret used to compute this HMAC is the single, app-wide `client_secret`, not a per-shop secret — every shop that installs the app receives webhooks signed with the exact same key. This means a merchant who is a legitimate, unprivileged user of the app (i.e., has it installed on their own store, so they can capture real webhook deliveries containing valid `(body, hmac)` pairs) can take a captured body+hmac from their own shop and re-POST it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a different tenant's domain. `Registry.process` will validate the HMAC successfully (it never looked at the shop header) and will invoke the app's webhook handler with `WebhookMetadata` claiming the body belongs to the victim shop: [5](#0-4) 

### Impact Explanation
This breaks tenant isolation: an unprivileged merchant of a multi-tenant app can inject forged/replayed webhook events that the host application will process as if they originated from another shop, using only information gained through their own, unprivileged use of the app (no `api_secret_key`, no stolen tokens, and no access to the victim's data required). Depending on what the app does in its webhook handlers (e.g., updating shop-scoped records, triggering shop-scoped side effects, billing, or provisioning based on the declared shop), this results in cross-tenant data corruption or cross-tenant action — matching the Critical "cross-tenant access" impact bucket.

### Likelihood Explanation
Any app built with this gem that has more than one shop installed is exposed. The attacker needs only to be a legitimate merchant of the app (an "unprivileged internet user" with respect to any other tenant) and the ability to send an HTTP POST to the app's public webhook endpoint with a chosen `shop` header — both are trivially available to any app user. No secrets, tokens, or elevated access are required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is actually HMAC-verified, or otherwise cryptographically tie the declared shop to the signed payload before it is trusted for dispatch — e.g., include the shop domain in `to_signable_string`, or independently verify that the declared shop matches a shop known to have a currently valid, stored session/webhook registration for this specific webhook, rather than trusting the header value at face value in `Registry.process`.

### Proof of Concept
1. App has been installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`.
2. Attacker's shop receives a legitimate webhook delivery: body `B`, header `shopify-hmac-sha256: H` (computed by Shopify using the app's single `client_secret`), header `shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays this exact `(B, H)` pair directly to the app's public webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim-shop.myshopify.com", "shopify-hmac-sha256" => H})` is constructed.
5. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches `H` — validation succeeds because `to_signable_string` never included the shop domain.
6. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled webhook content as if it belonged to `victim-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
