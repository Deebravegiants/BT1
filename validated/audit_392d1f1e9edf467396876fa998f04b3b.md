### Title
Webhook shop identity spoofing via unauthenticated `shop` header — cross-tenant webhook processing (`File: lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` value that is handed to application webhook handlers comes from an HTTP header that is never included in the signed bytes. This breaks the identity binding `hmac-authenticated-bytes == (shop, body)` down to `hmac-authenticated-bytes == body`, letting any shop that has legitimately installed the app relabel a genuinely-signed webhook payload as belonging to a different (victim) shop.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by comparing the received HMAC against a signature computed over `to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw HTTP body, and `hmac` is derived from the `x-shopify-hmac-sha256`/`shopify-hmac-sha256` header: [2](#0-1) [3](#0-2) 

The `shop` accessor, however, is read straight from an unauthenticated header, with no cryptographic binding to the body or the HMAC at all: [4](#0-3) [5](#0-4) 

`Registry.process` validates the HMAC and then constructs the metadata passed to the app's handler using this unauthenticated `request.shop` value: [6](#0-5) 

Because the app's `api_secret_key` is shared across every shop that installs the app, any tenant that has legitimately installed the app can obtain a validly-signed webhook body/HMAC pair for their own shop (e.g., by pointing their own delivery endpoint at infrastructure they control, or simply reading the raw request their own server received). They can then resend that exact `raw_body` + `hmac-sha256` header to the app's shared webhook endpoint while swapping only the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the shop header), and `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the victim's domain, even though the signed body content and the HMAC were generated for the attacker's own shop.

### Impact Explanation
This is a cross-tenant identity confusion: the equality the code should enforce is `hmac_verified_bytes == (shop, topic, body)`, but it actually enforces only `hmac_verified_bytes == body`. Any webhook handler that uses `data.shop` (from `WebhookMetadata`) to look up or mutate per-tenant state — e.g. updating a victim shop's stored product/order/subscription record, billing state, or settings based on attacker-supplied body content — can be made to act on the wrong tenant's data using a request that passes signature verification. This satisfies the Critical "cross-tenant access" impact category, since an attacker with only their own (legitimately installed) shop can inject data attributed to another merchant's tenant record without ever possessing the app's `client_secret` directly — they only reuse a signature that Shopify itself already computed and delivered to them.

### Likelihood Explanation
Likelihood is high for any app relying on this gem's `Webhooks::Registry.process`/`Webhooks::Request` for shop attribution: the exploit requires no secrets, only that the attacker (1) install the target app on a shop they control, which is available to any internet user, and (2) capture one legitimately delivered webhook for that shop and replay it with a modified `shop` header at the shared webhook endpoint.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the signed material, or otherwise cryptographically bind `shop` to the verified body — e.g., validate `request.shop` against an out-of-band trusted mapping (session store) keyed by a value that is itself covered by the HMAC, rather than trusting the `x-shopify-shop-domain` header directly. At minimum, document and enforce that consuming applications must not trust `WebhookMetadata#shop` for authorization/tenant-selection decisions without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a store they control) and registers a webhook, e.g., `orders/create`.
2. Shopify delivers a legitimately HMAC-signed webhook to the app's endpoint:
   - Body: `{"id":1,...}`
   - Header: `x-shopify-hmac-sha256: <valid HMAC over the body, using the app's api_secret_key>`
   - Header: `x-shopify-shop-domain: attacker-shop.myshopify.com`
3. Attacker captures this exact raw body and HMAC header (they own the shop and can log or proxy their own webhook traffic).
4. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but sets:
   - Header: `x-shopify-shop-domain: victim-shop.myshopify.com`
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body against the HMAC: [6](#0-5) 
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content, causing the application to process/store data as if it originated from the victim shop.
