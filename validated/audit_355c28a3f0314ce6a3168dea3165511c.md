### Title
Rounding-driven underflow in `Bonding.canGraduate` permanently bricks buy/sell on a curve - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.canGraduate` computes the curve's real (non-virtual) LT raised as a bare subtraction, `assetReserve - _launchTimeVirtualLtReserve(...)`, with no floor/clamp [1](#0-0) . This function is invoked unconditionally on *every* `Bonding.buy` and `Bonding.sell` call [2](#0-1) [3](#0-2) , as well as by the permissionless `triggerGraduation` [4](#0-3) . If the stored `assetReserve` (the pair's LT reserve1) is ever driven at or below the launch-time virtual LT reserve, the subtraction underflows and reverts with an unhandled `Panic(0x11)` — the same bug class as the Handlebars report: an un-guarded computation whose failure mode is an unhandled runtime exception rather than a clean revert, reachable from ordinary, unprivileged calls, and hitting a code path that every subsequent transaction must also execute.

### Finding Description
`_computeSell` in `Router.sol` derives the new stored asset reserve via floor division: `newReserveAsset = k / newReserveToken`, then `assetOut = reserveAsset - newReserveAsset` [5](#0-4) . Because `k / newReserveToken` always rounds down, each sell removes a hair more real LT from the pool than the exact continuous-math constant-product formula would dictate, and the stored `reserveAsset` after every sell is pushed slightly below its "true" value. This asymmetric-rounding erosion is exactly what the `Pair.swap` K-invariant "+1 slack" is designed to tolerate per-trade (per the protocol's own AGENTS.md design notes on the AMM's rounding tolerance), but nothing in `canGraduate` accounts for the cumulative effect of that tolerated per-trade slack across many trades.

An unprivileged trader can repeatedly round-trip a small amount of tokens through `Zap.buy` → `Zap.sell` on the same curve. Each cycle:
1. Buys a small amount of tokens (adds LT to the real reserve, no rounding loss on the buy side since `amountInUsed` is added directly rather than derived from division).
2. Immediately sells the tokens back — the floor-rounded `newReserveAsset` computation extracts marginally more LT than was added, and the stored `reserveAsset` in the `Pair` drifts down by the rounding remainder.

Repeating this is cost-bounded only by gas and the LT's tiny per-trade dust/fees, and over enough iterations drives `assetReserve` down toward — and eventually to or below — `virtualLtReserve = Pair.k() / Token.TOTAL_SUPPLY()` [6](#0-5) . The next call to `canGraduate` (i.e., the very next buy or sell) then executes `assetReserve - _launchTimeVirtualLtReserve(...)` with `assetReserve <= virtualLtReserve`, underflows, and reverts with an unrecoverable `Panic(0x11)`.

Because `canGraduate` is called unconditionally at the tail of every `Bonding.buy` and at the top of every `Bonding.sell`, this one bad state permanently bricks **all** further trading on the curve — no user can buy, sell, or (since `triggerGraduation` also calls `canGraduate`) manually push the token to graduation. The curve-raised LT and the 250M reserved LP tokens remain permanently parked inside `Bonding`, unreachable by any code path, since `finalizeGraduation` can only run once `Lifecycle.Graduating` has been entered via `_enterGraduating`, which in turn is only reachable through `canGraduate` returning `true` — but the function now reverts instead of returning `false`, so the lifecycle can never transition.

### Impact Explanation
This is a permanent freezing of trader/creator funds: every holder's tokens are stuck on a curve that can never trade, sell, or graduate; the LT raised by the curve and the LP reserve are permanently locked inside `Bonding` with no rescue path (mirroring the "one-shot, cannot-be-skipped" LPLock/graduation flow the scope calls out). This meets the High-severity bar for concrete, permanent freezing of funds via a fully unprivileged, transaction-reachable path.

### Likelihood Explanation
The attack requires no special privilege — any address can call `Zap.buy`/`Zap.sell` repeatedly. The magnitude of rounding drift per cycle is small (sub-wei to low-wei per trade depending on reserve sizes), so the number of round-trips needed scales with how far `assetReserve` starts above `virtualLtReserve`, but it is bounded and mechanical, not probabilistic — an attacker with modest capital and patience (or a bot performing many cheap round-trips) can reliably force the underflow. Likelihood is Medium-to-High depending on gas costs and LT transaction-size floors, which may in practice bound how small each round-trip can be, but the primitive itself is real and deterministic.

### Recommendation
Clamp the subtraction in `canGraduate` (and the identical pattern in `previewLtUntilGraduation`) so that `realLtRaised` floors at zero instead of underflowing, e.g. `assetReserve > virtualReserve ? assetReserve - virtualReserve : 0`. Additionally, consider whether `Router._computeSell`'s floor-rounding should be biased to protect the stored reserve invariant (round in the pool's favor rather than the seller's) to stop the cumulative drift at its source rather than only patching the downstream read.

### Proof of Concept
1. Launch a token normally via `Bonding.launch`/`Zap.createToken`, establishing `virtualLtReserve = Pair.k() / Token.TOTAL_SUPPLY()` and initial `assetReserve == virtualLtReserve` (since `realLtRaised == 0` at launch).
2. Have an unprivileged trader repeatedly call `Zap.buy(token, smallUsdc, 0, referrer)` immediately followed by `Zap.sell(token, tokensJustBought, 0)` on the same token, many times.
3. Each buy adds LT to the pair's asset reserve; each sell removes it via `Router._computeSell`'s floor-rounded `newReserveAsset = k / newReserveToken`, which extracts marginally more LT than was added back, causing `reserveAsset` to drift downward by the rounding remainder every cycle.
4. After enough cycles, `reserveAsset` reaches `virtualLtReserve` (or drops below it due to rounding overshoot in a single cycle).
5. The next `Zap.buy` or `Zap.sell` call triggers `Bonding.canGraduate`, which executes `assetReserve - _launchTimeVirtualLtReserve(...)` and underflows, reverting with `Panic(0x11)`.
6. From this point on, every `Bonding.buy`, `Bonding.sell`, and `triggerGraduation` call on this token reverts unconditionally — the curve, its raised LT, and its 250M LP reserve are permanently stuck.

Note: exact iteration counts and dust-fee interactions (e.g., BounceTech's `minTransactionSize` floor on LT mint/redeem) were not verified end-to-end in a live fuzz/PoC run within this investigation — this should be confirmed with a Foundry fuzz/invariant test (e.g., extending `test/GraduationInvariants.t.sol` or `test/Router.t.sol`) that repeatedly round-trips buy/sell and asserts `IPair(pair).getReserves()`'s asset leg never falls to or below `Pair.k() / Token.TOTAL_SUPPLY()`.

    function _computeSell(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 assetOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        uint256 newReserveToken = reserveToken + amountIn;
        assetOut = reserveAsset - (k / newReserveToken);
