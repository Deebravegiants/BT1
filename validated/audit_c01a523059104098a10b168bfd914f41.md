### Title
Tokens sent directly to a liquidity pool are permanently locked — the pool has no way to release funds above its `cash` book - (File: contracts/pool/src/lib.rs)

### Summary
The BathBuddy report describes a contract that can receive value (ETH) but exposes no path to release it. XOXNO Lending's pool contract has the same shape: it is a plain address that can receive direct SAC token transfers, yet every outbound path (`withdraw`, `borrow`, `repay` refund, `recapitalize` refund, `claim_revenue`, `flash_loan`, `create_strategy`) is bounded by the tracked `cash` bookkeeping number, which unsolicited transfers never increase. There is no `sweep`/`rescue` entrypoint in the pool surface at all, so any token donated directly to the pool address is locked forever.

### Finding Description
The pool's reserve model is a bookkeeping number, not a balance. `get_reserves` returns tracked `cash`, and `INV-ACCT-02` states "token donations alone do not increase it" [1](#0-0) . The threat model confirms "Direct donations do not rewrite those books" [2](#0-1) , and a dedicated test pins that minting to the pool leaves `reserves` unchanged [3](#0-2) .

The complete entrypoint list (`supply`, `borrow`, `withdraw`, `repay`, `net_settle`, `seize_positions`, `claim_revenue`, `recapitalize`, `flash_loan`, `create_strategy`, `update_indexes`, `update_params`, `create_market`, `upgrade`) contains no function that transfers out balance in excess of the `cash` book [4](#0-3) . The pool's owner is the controller, fixed at deploy with no transfer or renounce [5](#0-4) , and the controller likewise has no path to withdraw a pool surplus — `repay` and `recapitalize` refunds are bounded by declared/measured amounts, and `withdraw`/`claim_revenue` draw against `cash`. The same gap exists for tokens stranded on the controller: the flash-position docs note "An undeclared token left on the controller is neither deposited nor refunded" [6](#0-5) , and balance-delta measurement means pre-existing controller balances are never credited to anyone.

### Impact Explanation
Permanent freezing of funds. Any unprivileged address that transfers a supported (or any) token directly to a pool or the controller address loses it irrevocably — no entrypoint, including owner-only ones, can ever route those tokens back out, because all outbound legs are capped by the `cash` book and refund paths only pay out measured inbound deltas. Unlike the swap-aggregator, which deliberately exports `sweep_balance` for exactly this scenario [7](#0-6) , the pool has no equivalent.

### Likelihood Explanation
Reachable by any unprivileged address via a plain token `transfer` to the pool/controller address — explicitly within the allowed attack surface ("direct token transfers to the pool or controller"). The pool is a shared physical custody for one token across multiple hubs [8](#0-7) , so its address is well known, and accidental or third-party (e.g., venue reward) transfers are realistic: the docs themselves describe callers pushing "accrued rewards into the pool address as an unbooked donation" [9](#0-8) . Rated Medium: requires a user mistake or third-party push rather than a deliberate exploit, but the loss is permanent once it happens. Caveat: the protocol documents donations as a known design property (INV-ACCT-02), which may be argued a documented ADR choice.

### Recommendation
Add an owner/governance-reachable recovery entrypoint on the pool (e.g., `sweep(token, recipient)` transferring `token.balance(pool) - total_cash_across_all_markets`) and an equivalent rescue on the controller, mirroring the swap-aggregator's `sweep_balance` pattern. Alternatively, if donations are intended to accrue to the protocol, credit the surplus as revenue shares so the value is recoverable through `claim_revenue` rather than locked.

### Proof of Concept
1. Deploy pool and list a market; a supplier deposits so `cash = balance = B`.
2. Anyone calls `token.transfer(user, pool, X)` directly on the SAC.
3. `pool.get_reserves(hub_asset)` still returns `B` (pinned by `test_reserves_returns_accounted_cash_not_token_balance`, `contracts/pool/tests/views.rs:210`).
4. Enumerate every pool entrypoint: the maximum any of them transfers out is bounded by `cash` (withdraw/claim_revenue/borrow) or by a measured inbound delta (repay/recapitalize refunds). `X` is never transferable — it is locked for the lifetime of the contract.

```rust
    /// Transfers each token's balance above its reserved fee total to `recipient`. Owner only.
    #[only_owner]
    fn sweep_balance(env: Env, recipient: Address, tokens: Vec<Address>) {
        renew_instance(&env);
        let router = env.current_contract_address();
        let n = tokens.len();
        for i in 0..n {
            // `i < n == tokens.len()`, so the index is in range by construction.
            let token = tokens.get_unchecked(i);
            let client = token::Client::new(&env, &token);
            let balance = client.balance(&router);
            let reserved = storage::reserved_fee_balance(&env, &token);
            if balance > reserved {
                client.transfer(&router, &recipient, &(balance - reserved));
            }
        }
    }
```
