Audit Report

## Title
Unauthenticated `vault_publicKeyGet` request-ID squatting can block another caller's authorized secrets operation - (File: core/services/gateway/handlers/vault/handler.go)

## Summary
The Vault gateway handler tracks all in-flight requests in a single map, `h.activeRequests`, keyed only by the caller-supplied `req.ID`, shared across both the unauthenticated `MethodPublicKeyGet` path and the authorized `SecretsCreate`/`Update`/`Delete`/`List` paths. Because `MethodPublicKeyGet` skips authorization entirely and still claims a slot in this shared map, an unauthenticated attacker can occupy an arbitrary `req.ID` and cause a later, fully authorized request from a different caller with the same ID to be rejected.

## Finding Description
In `HandleJSONRPCUserMessage`, the `MethodPublicKeyGet` branch bypasses authorization ("Public key requests don't require authorization") and calls `h.newActiveRequest(req, callback)` directly when the public key isn't cached: [1](#0-0) 

For authorized methods (`SecretsCreate`/`Update`/`Delete`/`List`), the handler first calls `h.requestProcessor.ProcessRequest`, and only after authorization succeeds does it call the same `h.newActiveRequest(req, callback)`: [2](#0-1) 

`newActiveRequest` itself performs a single, global uniqueness check keyed purely on `req.ID`, with no scoping by method, caller, or authorization status: [3](#0-2) 

This confirms the reported root cause: the map and its duplicate-ID check are shared between an unauthenticated code path (`PublicKeyGet`) and authorized secret-mutation paths, with no namespacing by method or authorized owner.

I also verified there is a separate, independent anti-replay mechanism (`RequestReplayGuard` in `core/capabilities/vault/request_replay_guard.go`), used inside `ProcessRequest` for authorized requests, keyed on a request digest (not on the bare `req.ID`) — this is the source of the `"request was already authorized previously"` error seen in the `unhappy path - duplicate requestId` test. However, this replay guard only protects against literal duplicate authorized requests; it runs *before* `newActiveRequest` and does not prevent an unauthenticated `PublicKeyGet` request from separately occupying the same `req.ID` slot in `activeRequests`, since `PublicKeyGet` never goes through `ProcessRequest`/the replay guard at all. So this existing check does not mitigate the reported issue.

## Impact Explanation
This is a denial-of-service/griefing primitive against a specific request, not a fund-loss, key-exfiltration, or authorization-bypass issue: a legitimate, already-authorized `SecretsCreate`/`Update`/`Delete`/`List` request can be transiently blocked (`"request ID already exists"`) if its `req.ID` collides with one squatted via an unauthenticated `PublicKeyGet`. This does not directly map to the listed in-scope high-impact categories (auth bypass, secret exfiltration, unauthorized fund movement, allowlist bypass); it is closer to a minor availability/griefing bug whose severity is explicitly acknowledged by the report itself as bounded and likelihood-limited.

## Likelihood Explanation
Exploitation requires the attacker to predict or observe the victim's `req.ID` before the victim's request arrives, within the `RequestTimeoutSec` window. Since most real integrations use high-entropy UUIDs for `req.ID` (per the report's own reference to system-tests helpers), practical exploitation against a typical caller is low probability; it is more of a theoretical/edge-case griefing vector against callers using predictable or sequential IDs, which the report itself concedes.

## Recommendation
Scope `activeRequests` (and its duplicate-ID check) so that unauthenticated `PublicKeyGet` requests cannot collide with authorized secret-mutation requests — e.g., namespace the map key by `method` (or by authorized owner) instead of using the raw client-supplied `req.ID` alone, as recommended in the original finding.

## Proof of Concept
1. Send `{"method":"vault_publicKeyGet","id":"X"}` with no `Auth` field; per `handler.go` lines 404-420, this is accepted without authorization and inserted into `activeRequests["X"]`.
2. Before expiry (`RequestTimeoutSec`), send an authorized `{"method":"vault_secretsCreate","id":"X",...}`; authorization succeeds, but `newActiveRequest` (lines 457-472) returns `"request ID already exists: X"`, causing the authorized create-secret call to fail — this can be demonstrated with a Go unit test analogous to `TestVaultHandler_HandleJSONRPCUserMessage/unhappy_path_-_duplicate_requestId` in `handler_test.go`, but using a `MethodPublicKeyGet` request first instead of a duplicate authorized request.

```go
func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}
```
