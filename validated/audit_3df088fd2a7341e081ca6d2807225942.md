This confirms the analog: the docs explicitly promise `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" (line 125 of `docs/usage/webhooks.md`), and the handler is handed a `shop` value as the tenant identifier via `WebhookMetadata`, yet that `shop` value is never covered by the HMAC computation.

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) header values are trusted as the tenant identity without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` in `Webhooks::Registry.process` only proves that the *body bytes* were signed by a holder of `api_secret_key` [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from unauthenticated HTTP headers [3](#0-2)  and handed to the handler as the tenant/topic identity in `WebhookMetadata` without any binding to the HMAC-covered content [4](#0-3) .

### Finding Description
The identity binding broken is: `shop` (and other metadata) *authenticated* ≠ `shop` *acted on*. The HMAC only binds "this body byte-string was signed with the app's secret" — it does not bind "this body belongs to shop X, topic Y, webhook Z". An unprivileged internet user who legitimately operates their own Shopify dev/test store receives real, validly-signed webhook deliveries for their own shop (topic + body + HMAC over the body). Because the shop-domain, topic, webhook-id, and api-version headers are not part of `to_signable_string`, that same attacker can resend the identical `raw_body` + valid `hmac-sha256` header to the app's webhook endpoint while substituting arbitrary values for `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id`. `Registry.process` will pass HMAC validation (it only checks the body) and dispatch the handler with attacker-chosen `shop`/`topic`/`webhook_id` values [2](#0-1) .

Because the gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" [5](#0-4)  and instructs handler authors to key business logic off `data.shop` (the tenant) [6](#0-5) , host applications reasonably trust `shop` as an authenticated tenant identifier, when in fact only the body bytes are authenticated — not the shop attribution.

### Impact Explanation
This crosses a tenant boundary: an attacker who owns (or has captured a valid webhook delivery from) any store can forge webhook events attributed to a different, victim shop by replaying the signed body under falsified `shop`/`topic` headers, since `shop` is exactly the value the host app is documented to trust and key data storage/side-effects on. This matches the "cross-tenant access" impact category via a credential/identity-binding gap in the gem itself, rather than a host-application bug, because the gem's documented contract (`process` "verifies the request did indeed come from Shopify") implies the full metadata is authenticated when it is not.

### Likelihood Explanation
Exploitability requires the attacker to have at least one genuine signed webhook body+HMAC pair — trivially obtainable by installing the target app on their own throwaway/dev shop and triggering any topic they want to spoof (e.g., `orders/paid`, `app/uninstalled`). No secret material, TLS interception, or privileged account is required beyond normal, unprivileged app installation available to any internet user.

### Recommendation
Include the shop domain, topic, webhook id, and api version in the signable content bound by the HMAC (or otherwise independently authenticate `shop` against session/installation state before trusting it), so `Utils::HmacValidator.validate` proves the full tuple `(shop, topic, webhook_id, body)` was signed by Shopify, not merely the raw body bytes. At minimum, update the documentation to explicitly warn that `shop`/`topic`/`webhook_id` header values are not covered by the HMAC and must not be trusted as authenticated tenant identifiers without additional verification (e.g., cross-checking against the shop for which the webhook was registered).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers topic `orders/create`, capturing the legitimate delivery: `raw_body`, and header `x-shopify-hmac-sha256` (valid for that `raw_body` under the app's `api_secret_key`), plus `x-shopify-topic: orders/create`.
2. Attacker sends a POST to the app's webhook endpoint reusing the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim.myshopify.com` and/or `x-shopify-webhook-id: <arbitrary>`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers [7](#0-6) ; `Utils::HmacValidator.validate(request)` succeeds because it only recomputes the HMAC over `raw_body` [8](#0-7) .
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "orders/create", body: <attacker's body>, ...)` [9](#0-8) , causing the host app to process attacker-controlled data as if it originated from the victim shop.
