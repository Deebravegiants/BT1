### Title
Webhook cross-tenant/topic spoofing via unauthenticated headers not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts two separate HTTP headers — `shop-domain` and `topic` — that are **not** included in that signature, to decide which tenant the payload belongs to and which handler processes it.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` and `topic` accessors are derived from separate, unsigned headers: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which — per `HmacValidator#validate_signature` — only checks `verifiable_query.to_signable_string` (the raw body) against the HMAC. It then immediately uses `request.topic` (unsigned) to select the handler and `request.shop` (unsigned) to populate the tenant-identifying metadata passed to the handler: [3](#0-2) 

The equality this breaks: `shop-domain header == shop that produced the signed body` and `topic header == topic that produced the signed body`. Neither holds — only `hmac == HMAC_secret(raw_body)` is checked. Any HTTP path that lets an attacker deliver a request with a legitimately-signed body (e.g., from a real webhook the attacker's own shop received) but attacker-controlled `shopify-shop-domain` / `shopify-topic` headers, will pass `HmacValidator.validate` while misattributing the payload to a different shop and/or topic.

### Impact Explanation
Handlers keyed on `request.shop` (exposed to app code via `WebhookMetadata`) are commonly used to update per-tenant records or process sensitive mandatory topics (`shop/redact`, `customers/redact`, `customers/data_request`). Since `Registry.process` propagates the unsigned `shop` value straight into `WebhookMetadata` without any binding to the signed body, an app's webhook handler can be tricked into applying a legitimately-signed payload to the wrong tenant, or into invoking the wrong topic handler — this is a cross-tenant identity-binding break reachable purely by manipulating request headers in front of this gem's `Registry.process`/`Request` code, matching the "field acted on but not covered by the HMAC" bug pattern from the reference report (an `RCTreasury`-style value used in one place but not properly bound in another).

### Likelihood Explanation
Exploitability depends on whether headers reaching the host app's webhook endpoint can be manipulated in transit (e.g., untrusted reverse proxies, header-injection points, or any component between Shopify and the Rack app that does not strictly bind these headers to the TLS/HMAC-verified request). This is not purely theoretical inside this gem: the gem itself performs no binding between the signed content and the header-derived `shop`/`topic`, so it fails to provide the guarantee its own `HmacValidator.validate` call implies ("this request is authentic for this shop/topic"). However, whether an attacker can actually control headers presented to `Webhooks::Request.new` depends on network/deployment topology outside this gem, which limits certainty of the exploit path from an anonymous, non-privileged remote position alone.

### Recommendation
Include `shop-domain`, `topic`, `webhook-id`, and `api-version` in the HMAC-signed payload (or otherwise cryptographically bind them to the raw body) before trusting them in `Registry.process`, so that `to_signable_string` covers everything the registry subsequently relies on for tenant/topic dispatch.

### Proof of Concept
Conceptual PoC (requires a scenario where the headers can be altered in front of this gem, e.g. attacker's own shop delivers a valid webhook and headers are then substituted before reaching `Registry.process`):
1. Attacker's own dev shop triggers webhook topic `orders/create`, producing `(raw_body, hmac)` that is valid per `HmacValidator.validate`.
2. Attacker replays `(raw_body, hmac)` to the app's webhook endpoint but sets `shopify-shop-domain: victim-shop.myshopify.com` and/or `shopify-topic: customers/redact`.
3. `Registry.process` at [4](#0-3)  validates HMAC successfully (body unchanged) and dispatches `handler.handle` with `shop: "victim-shop.myshopify.com"` and/or the swapped topic's handler, even though neither field was ever authenticated.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
