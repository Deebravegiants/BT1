### Title
Accrued RAY value overflow permanently freezes an oversized market - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
The accrual engine converts aggregate scaled debt and supply into RAY-denominated values before applying the borrow-index cap. When `borrowed * borrow_index / RAY` or `supplied * supply_index / RAY` exceeds `i128::MAX`, `scaled_to_original` panics. Because every pool operation synchronizes the market before mutating it, crossing this representability boundary permanently prevents repayment, withdrawal, liquidation, index updates, and other market operations.

### Finding Description
`accrue_step` unconditionally calculates:

- `borrowed_original = scaled_to_original(borrowed, borrow_index)`
- `supplied_original = scaled_to_original(supplied, supply_index)`

in `common/src/rates/simulate.rs:60-61`.

`scaled_to_original` performs `scaled * index / RAY` through `Ray::mul`, which uses an exact `I256` intermediate but requires the final quotient to fit in `i128` (`common/src/rates/scaling.rs:14-16`, `common/src/math/fp.rs:49-52`, `common/src/math/fp_core.rs:145-175`).

This creates a dynamic ceiling:

```text
borrowed_scaled * borrow_index / RAY <= i128::MAX
supplied_scaled * supply_index / RAY <= i128::MAX
```

The configured `MAX_BORROW_INDEX_RAY` ceiling is applied only inside `update_borrow_index`, after the existing aggregate debt has already been unscaled (`common/src/rates/index.rs:13-18`). Likewise, `update_supply_index` later multiplies `supplied` by the index (`common/src/rates/index.rs:34`). Consequently, a large but individually admitted scaled position can become unrepresentable before the index reaches its nominal cap.

An unprivileged caller can trigger the state transition through controller `update_indexes(caller, assets)`, where `assets` contains the target `HubAssetKey`. The controller forwards the call to the pool (`contracts/controller/src/markets.rs:118-120`, `contracts/controller/src/external/pool.rs:109-115`), and the pool executes `interest::global_sync` for the market (`contracts/pool/src/ops/market.rs:65-71`). `global_sync` calls `accrue_step` (`contracts/pool/src/interest.rs:20-52`).

After the overflow state is reached, the same accrual-first path runs before `withdraw` and `repay`, so exits and debt reduction fail with `MathOverflow` rather than allowing the market to recover (`contracts/pool/src/ops/withdraw.rs:30-79`, `contracts/pool/src/ops/repay.rs:25-59`).

### Impact Explanation
All funds and debt operations for the affected `(hub_id, asset)` market become permanently frozen:

- suppliers cannot withdraw collateral or yield;
- borrowers cannot repay or close debt;
- liquidators cannot reduce unhealthy positions;
- index updates cannot progress;
- routes that touch the market through supply, borrow, repay, withdraw, settlement, or liquidation revert.

The failure is permanent because the stored `borrowed`, `supplied`, and index values do not decrease on their own, and every recovery operation recalculates the overflowing product before allowing a state change.

### Likelihood Explanation
Triggering the condition requires aggregate scaled balances and index growth whose product exceeds the `i128` RAY-value domain. This is a high economic threshold—approximately the documented upper range for supported assets—and generally requires a very large market, high utilization, and sustained interest accrual. It is therefore not reachable through ordinary small positions.

However, once the aggregate market state approaches the boundary, any unprivileged authorized address can call `update_indexes` with the affected `HubAssetKey` and force the overflowing accrual. No privileged role, oracle manipulation, leaked key, or malformed parameter is required.

### Recommendation
Make aggregate-value calculation and index capping representability-aware:

1. Use a saturating or widened representation for aggregate debt/supply valuation inside `accrue_step`, rather than requiring the result to fit in `i128`.
2. Enforce a dynamic share ceiling based on the current index, such as limiting `borrowed` and `supplied` to values whose index-scaled result remains representable.
3. Apply borrow-index capping before unscaling debt, and define explicit behavior when accrued debt reaches the numeric ceiling.
4. Add regression coverage that advances a near-boundary market through `update_indexes`, then verifies that at least debt repayment and supplier withdrawal remain possible.

### Proof of Concept
Conceptual sequence for an active market with an 18-decimal asset:

```text
1. Establish a large market:
   supply(hub_id, asset, principal)
   where principal is near the market's admitted cap.

2. Establish high utilization:
   borrow(account_id, ..., HubAssetKey { hub_id, asset },
          amount ≈ 98% of supplied cash)

3. Allow enough time to elapse for borrow_index growth.

4. An attacker calls:
   update_indexes(
       caller = attacker,
       assets = vec![HubAssetKey { hub_id, asset }]
   )

5. The controller invokes pool.update_indexes.
   The pool calls global_sync → accrue_step.
   accrue_step evaluates:
       borrowed * borrow_index / RAY

6. Once that quotient exceeds i128::MAX, Ray::mul panics with MathOverflow.

7. Subsequent calls fail for the same reason:
   - update_indexes(caller, same asset)
   - withdraw(... same asset ...)
   - repay(... same asset ...)
   - liquidation paths touching the market
```

The decisive condition is:

```text
borrowed_scaled * borrow_index > i128::MAX * RAY
```

or the equivalent condition for `supplied_scaled * supply_index`.
