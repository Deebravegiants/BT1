### Title
Reachable division-by-zero `unwrap()` panics in PnL/swap math permanently freeze pool operations - (File: program/src/math.rs, program/src/processor.rs)

### Summary
The external report describes a null-pointer dereference in `paddle.put_along_axis` (CVE-2023-52303) that causes a runtime crash / denial of service because an internal pointer/index is used without validating that it is non-null/in-range. The analogous bug class in this codebase (CWE-476-style "missing check before use causing abnormal termination") is the pervasive use of `.unwrap()` on `checked_div`/`checked_sub` results throughout `Calculator::calc_x_power`, `Calculator::swap_token_amount_base_in/out`, `InvariantToken::exchange_*`, and `Processor::calc_take_pnl`, none of which validate that a divisor/denominator is non-zero or that a subtraction is non-negative before unwrapping. These functions are on the hot path of `Deposit`, `Withdraw`, and swap instructions and operate on values derived from attacker-influenceable vault balances, so a transaction can be crafted whose data drives a denominator to zero and aborts, and — because pool state (`need_take_pnl_*`, `calc_pnl_x/y`) is durably stored — the same condition can recur on every subsequent call, freezing all future deposits/withdrawals/PnL calculations on that pool.

### Finding Description
`Calculator::calc_x_power` unconditionally calls `.checked_div(current_y).unwrap()`: [1](#0-0) 

`Processor::calc_take_pnl`, which is invoked from `process_deposit`, `process_withdraw`, and `process_withdrawpnl`, feeds `x1`/`y1` (normalized values derived directly from live vault token-account balances via `calc_total_without_take_pnl_no_orderbook` and `normalize_decimal_v2`) into `calc_x_power` and then divides again by `x1` without a zero-check: [2](#0-1) 

The surrounding accounting also chains multiple `.unwrap()`-guarded `checked_sub`/`checked_mul`/`checked_div` operations on pool-state-derived quantities: [3](#0-2) 

The same missing-zero-check pattern recurs in `InvariantToken::exchange_coin_to_pc` / `exchange_pc_to_coin` (dividing by `self.token_coin`/`self.token_pc`), and in `Calculator::swap_token_amount_base_in`/`swap_token_amount_base_out` (dividing by pool reserve sums/differences): [4](#0-3) [5](#0-4) 

None of `Deposit` (`process_deposit`), `Withdraw` (`process_withdraw`), or `process_withdrawpnl` validate ahead of time that `total_pc_without_take_pnl`, `total_coin_without_take_pnl`, or their normalized forms (`x1`, `y1`) are non-zero before this math executes, even though these instructions are reachable by any unprivileged liquidity provider with attacker-chosen `deposit`/`withdraw` amounts and account-supplied vault balances: [6](#0-5) [7](#0-6) 

Because `amm.state_data.need_take_pnl_pc/coin` and `target_orders.calc_pnl_x/y` are persisted on-chain and updated by these same code paths, an LP who drives the pool's uncollected-PnL accounting to a state where `total_pc_without_take_pnl` or `total_coin_without_take_pnl` reaches `0` (e.g., by fully withdrawing liquidity down to the last unit while accrued `need_take_pnl_*` consumes the remainder) causes `calc_take_pnl`'s internal division to panic. Since the panicked state (near-zero reserves with outstanding uncollected PnL) is a legitimate, reachable pool state rather than a one-off input error, subsequent `Deposit`/`Withdraw`/`process_withdrawpnl` calls on the same pool can be made to panic repeatedly, effectively freezing the pool's liquidity-management functions for all users.

### Impact Explanation
A transaction abort due to an unhandled `unwrap()` on a `None` (division-by-zero) result is the on-chain analogue of the nullptr crash in the reference advisory: the program aborts instead of returning a controlled `ProgramError`. Because the underlying pool state that triggers the panic is durable, this is not merely a single failed transaction — it can result in a **permanent denial of service on `Deposit`/`Withdraw`/`process_withdrawpnl`** for the affected pool, freezing user and LP funds inside the vaults with no reachable instruction path to safely extract them (a form of permanent fund freezing).

### Likelihood Explanation
Reaching the exact reserve state where `total_pc_without_take_pnl` or `total_coin_without_take_pnl` becomes exactly `0` while `need_take_pnl_*`/`calc_pnl_x/y` remain positive requires precise, but attacker-controllable, sequencing of deposits/withdrawals by a liquidity provider (an unprivileged actor), since withdrawal amounts and resulting vault balances are chosen by the caller within a single transaction. This is plausible but requires careful crafting of the LP-token amount / vault state, so likelihood is assessed as medium rather than trivial.

### Recommendation
- Replace all `.checked_div(...).unwrap()` and adjacent `.checked_sub(...).unwrap()` calls in `Calculator::calc_x_power`, `Calculator::swap_token_amount_base_in/out`, `InvariantToken::exchange_coin_to_pc/exchange_pc_to_coin`, and `Processor::calc_take_pnl` with explicit zero/underflow checks that return a dedicated `AmmError` (e.g., `AmmError::CalcPnlError`/`AmmError::ZeroTradingTokens`) instead of panicking.
- Add explicit guards in `process_deposit`, `process_withdraw`, and `process_withdrawpnl` to reject operations when `total_pc_without_take_pnl == 0 || total_coin_without_take_pnl == 0` (or the normalized `x1`/`y1` are zero) before calling `calc_take_pnl`.
- Add regression tests that drive pool reserves to the zero-liquidity edge case to confirm graceful error handling instead of panics.

### Proof of Concept
Conceptual sequence (requires devnet/mainnet fork validation to confirm exact numeric conditions, since exact reserve arithmetic depends on live fee/decimal configuration):
1. Create a pool via `Initialize2` with small initial liquidity and non-trivial `pc_decimals`/`coin_decimals` skew.
2. As an LP, perform a sequence of `Deposit`/`Withdraw` calls that accrues `state_data.need_take_pnl_pc`/`need_take_pnl_coin` (via normal swap fee accrual) while progressively withdrawing LP tokens, driving `amm_pc_vault.amount - need_take_pnl_pc` (i.e., `total_pc_without_take_pnl`) to exactly `0`.
3. Submit a final `Withdraw` or `process_withdrawpnl` transaction; `Calculator::calc_x_power`'s `.checked_div(current_y).unwrap()` (or the analogous division in `calc_take_pnl`) receives a zero divisor and panics, aborting the transaction.
4. Because the persisted pool state (`need_take_pnl_*`, `calc_pnl_x/y`, vault balances) remains in the triggering configuration, all subsequent `Deposit`/`Withdraw`/`process_withdrawpnl` calls on this pool panic identically, freezing further liquidity operations.

        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)

                // => amount_in = coin * pc / (coin - amount_out) - pc
                // => amount_in = (coin * pc - pc * coin + pc * amount_out) / (coin - amount_out)
                // => amount_in = (pc * amount_out) / (coin - amount_out)
                let denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_pc_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
        }
        return amount_in;
    }
