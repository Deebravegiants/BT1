### Title
Webhook Shop-Domain Header Is Not Bound by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb / lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body [1](#0-0) . The `shop` value that is then handed to the app's handler as the tenant identity comes from the `x-shopify-shop-domain` header, which is never included in the signed content [2](#0-1) .

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [3](#0-2) , and `Request#hmac` is decoded solely from the `hmac-sha256` header [4](#0-3) . `Utils::HmacValidator.validate` recomputes HMAC-SHA256 over `to_signable_string` with the shared `api_secret_key` and compares it to the received value [5](#0-4) . Because the `shop-domain` header is excluded from `to_signable_string`, the equality actually being proven is `HMAC(raw_body) == received_hmac`, not `HMAC(raw_body, shop) == received_hmac`.

`Registry.process` uses this weaker guarantee to authorize the whole request, then forwards `request.shop` unchecked to the app's handler as the webhook's originating shop: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [1](#0-0) . The library's own documentation explicitly tells integrators that `data.shop` is "The shop domain of the webhook" and shows it being used directly to key work, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)` — i.e., the gem's documented API instructs developers to trust `shop` as an authenticated tenant identifier [6](#0-5) .

Since the app's `api_secret_key` is shared across every shop that installs the app (it is not shop-specific), any merchant that installs the app can capture a validly-signed `(raw_body, hmac)` pair from a webhook Shopify delivers for their own store. That merchant can then replay the exact same body/HMAC to the shared app webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value (e.g., a victim shop's domain). `HmacValidator.validate` still succeeds, because it never inspected the header, and `Registry.process` passes the forged shop straight to the app's handler.

### Impact Explanation
This breaks the identity binding `shop_claimed_in_header == shop_that_actually_produced_signed_body`, letting one merchant inject events attributed to a different, arbitrary shop into the app's webhook processing pipeline — this is a cross-tenant confusion/spoofing primitive that can be used to poison another tenant's data, trigger unauthorized side effects keyed by `shop`, or pollute per-shop caches/state, satisfying the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on their own (attacker-controlled) shop — a normal, unprivileged action any merchant can perform — capture one legitimately delivered webhook (trivial, since it is delivered to their own endpoint or can be sniffed via any HTTP proxy they control), and then send a forged HTTP request to the app's public webhook endpoint with a different `shop-domain` header. No access token, `api_secret_key`, or privileged credential is needed.

### Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically verify that the `shop-domain` header matches the shop that the webhook subscription was registered for/expected. At minimum, `Utils::VerifiableQuery`/`Request#to_signable_string` should incorporate the shop domain (and topic) into the HMAC computation so that `HmacValidator.validate` proves both message integrity and shop provenance together, closing the gap between "bytes verified" (body only) and "bytes acted on" (body + externally-supplied shop header).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, obtaining a valid webhook delivery with body `B` and header `x-shopify-hmac-sha256: H` (a correct HMAC of `B` under the shared `api_secret_key`), per `Request#hmac`/`#to_signable_string` [7](#0-6) .
2. Attacker sends a POST to the app's public webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim.myshopify.com` instead of `attacker.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(B) == H` and returns true, since neither the shop header nor topic are covered [8](#0-7) , [9](#0-8) .
4. `handler.handle` is invoked with `WebhookMetadata(shop: "victim.myshopify.com", body: parsed(B), ...)` [10](#0-9) , causing the host application (following the gem's documented pattern of trusting `data.shop`) to process attacker-controlled data as if it originated from the victim's shop.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
