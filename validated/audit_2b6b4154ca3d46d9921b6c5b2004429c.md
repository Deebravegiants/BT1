### Title
Curve swap math rounds in the trader's favor instead of the pool's, violating the constant-product invariant every trade — ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy` and `Router._computeSell` compute swap outputs using floor (`/`) integer division when solving the constant-product invariant `k = reserveToken * reserveAsset`. Floor division on the *quoted-out* reserve necessarily rounds the *amount paid out* up, so both buyers and sellers systematically receive slightly more than the exact bonding-curve amount, at the expense of the curve's own reserves — the "maker" side of the AMM. This mirrors M-7's root cause: the whitepaper/spec-mandated rounding direction (round in favor of the protocol/maker) is violated by a raw floor-division implementation, even though the same file demonstrates elsewhere that the developers know the correct direction and implement it correctly for the overflow-capped path.

### Finding Description
In the uncapped (common) buy path: [1](#0-0) 

```solidity
function _computeBuy(address pairAddr, uint256 amountIn) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
    ...
    uint256 newReserveAsset = reserveAsset + amountInUsed;
    tokensOut = reserveToken - (k / newReserveAsset);
    ...
}
```

`k / newReserveAsset` truncates towards zero (floors). Since the true, continuous invariant-preserving new token reserve is `k / newReserveAsset` (a real number), flooring it means the computed value is `<=` the true value, so `tokensOut = reserveToken - floor(k/newReserveAsset)` is `>=` the exact invariant-preserving `tokensOut`. The buyer is systematically overpaid in tokens, and the curve's post-trade real product `(reserveToken - tokensOut) * newReserveAsset` drops below `k` — exactly the class of rounding error the whitepaper-style spec (per M-7) requires to be rounded the other way to protect the maker (here, the curve/protocol reserve).

The identical pattern exists in `_computeSell`: [2](#0-1) 

```solidity
function _computeSell(address pairAddr, uint256 amountIn) internal view returns (uint256 assetOut) {
    ...
    uint256 newReserveToken = reserveToken + amountIn;
    assetOut = reserveAsset - (k / newReserveToken);
}
```

Here `assetOut` (LT paid to the seller) is likewise rounded up, again depleting the curve's real LT reserve below what the constant-product formula would yield.

Notably, the codebase itself documents the *correct* rounding direction for the analogous overflow-cap branch of the same function: [3](#0-2) 

```solidity
/// @dev Capped: `amountInUsed` is back-calculated from the K invariant
///      (rounded up so the curve never under-charges).
```

and implements it with an explicit ceiling division: [4](#0-3) 

```solidity
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
    amountInUsed = cappedReserveAsset - reserveAsset;
}
```

This confirms the team's own stated invariant — "the curve never under-charges" — is only honored in the rare capped branch, while the ordinary uncapped buy/sell math (executed on essentially every trade) rounds the opposite way, over-paying the trader and under-charging/over-paying from the curve's reserves.

The `Pair.swap` K-invariant guard tolerates exactly this kind of dust-level slack: [5](#0-4) 

```solidity
uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();
```

The `+1` slack on each side is precisely large enough to admit the systematic, always-in-the-trader's-favor rounding error produced by `_computeBuy`/`_computeSell`, so every single buy and sell silently passes the invariant check while leaking value out of the curve.

### Impact Explanation
Every buy and every sell transaction on every bonding curve leaks a small amount of value from the curve's reserves to the trader, because the rounding direction is never in the protocol's favor as intended. This is not a one-off rounding error but a deterministic, protocol-wide directional bias baked into the core AMM math used by `Bonding.buy`/`Bonding.sell` (via `Router.buy`/`Router.sell`) for every single trade on every token, for the lifetime of each curve until graduation. An unprivileged actor can grind this repeatedly with a sequence of small buy/sell round-trips to extract reserve value across many transactions, and because the loss is systematic rather than random noise, it does not average out — it compounds unidirectionally against the curve (and, transitively, against the LP amount computed at graduation, since `tokensForLP`/`ltFromPair` are derived from the same drained reserves).

### Likelihood Explanation
The rounding direction fires on literally every trade with no special preconditions — no privileged role, no pre-seeding, no specific market state is required. Any unprivileged trader calling `Zap.buy`/`Zap.sell` (which route to `Bonding.buy`/`Bonding.sell` → `Router.buy`/`Router.sell` on-curve) triggers it. The magnitude per trade is bounded by the K-invariant `+1` slack, so it is small per-call, but the directionality is always the same, making it trivially and repeatedly exploitable by an attacker willing to submit many transactions.

### Recommendation
Round the swap-output math the same protective direction the codebase's own comment already prescribes for the capped path: use ceiling division when computing the reserve that determines how much is paid OUT, so the curve never under-charges/over-pays:

```diff
 function _computeBuy(...) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
     ...
     uint256 newReserveAsset = reserveAsset + amountInUsed;
-    tokensOut = reserveToken - (k / newReserveAsset);
+    tokensOut = reserveToken - Math.ceilDiv(k, newReserveAsset);
     ...
 }

 function _computeSell(...) internal view returns (uint256 assetOut) {
     ...
     uint256 newReserveToken = reserveToken + amountIn;
-    assetOut = reserveAsset - (k / newReserveToken);
+    assetOut = reserveAsset - Math.ceilDiv(k, newReserveToken);
 }
```
This keeps the invariant `newTokenReserve * newReserveAsset >= k` always, matching the documented "curve never under-charges" property already applied in the overflow-cap branch, and should also be mirrored in the `getAmountOut` view quote for consistency.

### Proof of Concept
1. A curve pair holds `reserveToken`, `reserveAsset` with `k = reserveToken * reserveAsset` such that `k` is not evenly divisible by `reserveAsset + amountIn` for a chosen buy size (guaranteed for essentially all reserve/amount combinations, since `k`/`reserveAsset` are generic large integers).
2. Attacker calls `Zap.buy(token, usdcAmount, 0, referrer)` with `usdcAmount` sized so the resulting LT `amountIn` produces a non-terminating `k / newReserveAsset`.
3. `Router._computeBuy` (packages/contracts/src/Router.sol:137-138) computes `tokensOut = reserveToken - floor(k / newReserveAsset)`, which is provably `>=` the exact invariant-preserving output by up to 1 wei of token.
4. `Pair.swap` (packages/contracts/src/Pair.sol:71-73) accepts the trade because the `+1` slack absorbs the shortfall — post-trade real product `newTokenReserve * newReserveAsset < k`, yet the check passes.
5. Repeating steps 2–4 across many transactions (buy then sell, or many independent buys) systematically drains dust value from the curve's reserves to the trader every time, since the rounding direction never favors the pool — reproducible deterministically against `test/Router.t.sol`'s `test_getAmountOut_constantProductHolds` style setup by comparing `tokensOut` against the true rational-number invariant solution.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {

        }
    }
