### Title
Webhook HMAC only covers the request body, letting the unauthenticated `shop-domain` header spoof tenant identity - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` value used downstream by `Registry.process` is read from an HTTP header that is never included in the signed material. This breaks the identity binding `shop_authenticated == shop_delivered_to_handler`, letting anyone who can construct/replay an HMAC-valid webhook body attach an arbitrary `shop-domain` header and have the app's handler process it under a different tenant's identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, however, is derived purely from an unauthenticated HTTP header (`shopify-shop-domain` / `x-shopify-shop-domain`): [2](#0-1) 

`Registry.process` validates the HMAC against the body only, then immediately trusts `request.shop` (the header value) to build the `WebhookMetadata` object handed to the app's `WebhookHandler`: [3](#0-2) 

`Utils::HmacValidator.validate` confirms only that `computed_signature(request.to_signable_string, secret) == request.hmac`, i.e. it authenticates the byte-string in `@raw_body`, not the `shop`, `topic`, `webhook-id`, or `api-version` headers: [4](#0-3) 

The identity binding that should hold is:
`shop_covered_by_hmac == shop_passed_to_handler`

In this implementation the left-hand side does not exist at all — no shop value is ever included in the signable string — so the equality trivially fails whenever the header disagrees with the body's true origin. Since the webhook receiver is a public HTTP endpoint controlled entirely by the host app (this gem provides no origin/IP/mTLS check), any party able to obtain one genuinely HMAC-valid `(raw_body, hmac)` pair for a webhook — e.g. a webhook delivered to their own shop, where they legitimately received the raw body and header from Shopify — can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting any other value in the `shop-domain` header. `Utils::HmacValidator.validate` still returns `true` because the signed bytes (the body) are unchanged, and `Registry.process` forwards `WebhookMetadata.new(... shop: request.shop ...)` — now containing the attacker-chosen shop — to the handler as if it were an authentic notification for that tenant.

### Impact Explanation
This is a cross-tenant identity confusion: the gem's own webhook dispatch API (`WebhookMetadata#shop`) is documented and intended to tell the host app which merchant a webhook body belongs to, but that value is not bound to the cryptographic signature that establishes authenticity. An attacker who is a legitimate merchant of shop A (which is enough access to receive real, correctly-signed webhooks for their own store) can replay their own webhook body/HMAC pair against a different `shop-domain` header value, causing the receiving application — using only the documented `ShopifyAPI::Webhooks::Registry.process`/`WebhookMetadata` API — to process attacker-controlled body content under the identity of an arbitrary/victim shop. Depending on how the host app persists or acts on `WebhookMetadata#shop` (e.g., updating per-shop records, redact flows, order/customer data), this results in cross-tenant data injection/corruption, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high because: (1) the webhook HTTP endpoint is necessarily public and reachable by anyone on the internet; (2) becoming an app installer for one's own development/test shop to obtain one legitimately-signed webhook body/HMAC pair is trivial and requires no privileged credentials, access tokens, or the app's `client_secret`; (3) HTTP headers are fully attacker-controlled in a crafted request, and this gem performs no cross-check between the header-derived `shop` and anything cryptographically bound to the body.

### Recommendation
Include the shop identity (and other trust-critical fields such as `topic`/`api_version`) in the HMAC-covered material, or otherwise verify that the shop conveyed in the webhook payload/headers corresponds to the shop for which the webhook was actually registered before handing `WebhookMetadata` to app handlers — e.g., look up the registered webhook/shop by `webhook_id` server-side, or reject/flag when the header shop cannot be corroborated with signed content. At minimum, document prominently that `Registry.process`'s `shop` field is not authenticated by the HMAC and must not be trusted for tenant-sensitive operations without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and lets Shopify deliver a genuine webhook (e.g. `orders/create`) to the app's public webhook URL. Attacker captures the exact `raw_body` and the `X-Shopify-Hmac-Sha256` header value from this legitimate delivery.
2. Attacker crafts a new HTTP POST to the same public webhook endpoint with:
   - Identical `raw_body` and `X-Shopify-Hmac-Sha256` header (unchanged, so the HMAC bytes match).
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (replaced from `attacker-shop.myshopify.com`).
3. Server calls `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` then `Registry.process(request)`.
4. `Utils::HmacValidator.validate(request)` returns `true` (only `raw_body` is checked) — see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:12-31`.
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's order data>, ...)` and invokes the app's handler with a shop identity that was never authenticated — see `lib/shopify_api/webhooks/registry.rb:188-199` and `lib/shopify_api/webhooks/request.rb:20-23`.

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
