### Title
Storage-deposit cache key collision lets attacker force a withdrawal that omits `storage_deposit`, stranding funds - ([File: packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts])

### Summary
`DirectBridge.getCachedStorageDepositValue` builds its LRU cache key by naively concatenating `contractId` and `accountId` with no separator. Because both the token (`contractId`, chosen from the withdrawal's `assetId`) and the destination account (`accountId` = `destinationAddress`) are attacker-controlled inputs to a single, shared long-lived bridge instance, an attacker can craft a withdrawal request whose concatenated key collides with a distinct, previously-cached `(token, account)` entry. This lets a stale/foreign cache value decide whether a storage deposit must be attached to the withdrawal, breaking the equality "the storage-deposit fee charged corresponds to the actual destination account's on-chain storage balance for that exact token."

### Finding Description
The cache is populated and read here: [1](#0-0) 

`key = ${contractId}${accountId}` has no delimiter, so two different pairs `(contractId_a, accountId_a)` and `(contractId_b, accountId_b)` can produce the identical string key whenever `contractId_a + accountId_a === contractId_b + accountId_b` (e.g. `"usdc.near" + "bob.near"` vs `"usdc.nearb" + "ob.near"`). Since `contractId` is derived from the caller-supplied `assetId` (any supported NEP-141 token id) and `accountId` is the caller-supplied `destinationAddress`, both halves of the key are within the calling user's control per request.

This cached value directly drives the fee computation: [2](#0-1) 

If the (colliding) cached tuple `[minStorageBalance, userStorageBalance]` falsely shows `minStorageBalance <= userStorageBalance`, `estimateWithdrawalFee` returns `storageDepositFee: 0n` for a destination account that, in reality, has no NEP-141 storage registered for that token.

That zero fee flows straight into intent construction: [3](#0-2) 

and into the primitive builder, which omits `storage_deposit` entirely whenever the passed value is `0n`: [4](#0-3) 

The resulting `ft_withdraw` intent is signed and submitted without the storage deposit the destination account actually needs. On execution, the NEP-141 `ft_transfer`/`ft_transfer_call` to an unregistered account fails on the token contract after the intents contract has already debited/settled the user's balance for the withdrawal intent, leaving funds stuck pending manual reconciliation.

### Impact Explanation
This breaks the equality between "the storage balance state validated for account X on token T" and "the storage balance state actually used to size the fee/intent for account X on token T," which is the same class of bug as CVE-2022-27782 (a security-relevant, per-(identity, resource) cached decision reused for a different (identity, resource) pair). The concrete effect is a NEAR withdrawal that reaches the chain without the required storage deposit, causing the token transfer leg to fail while the debit intent has already executed — funds stuck until an operator manually detects and remediates. This matches the High-severity category "a withdrawal stuck until manual intervention."

### Likelihood Explanation
The `DirectBridge` cache is a class-level `LRUCache` (`max: 100, ttl: 3600000`) shared across all withdrawal requests processed by one bridge instance (typical for a long-running SDK integrator service). Both key components (`contractId` from a supported-token `assetId`, and `accountId` from the caller-chosen `destinationAddress`) are attacker-influenced per call, so constructing a colliding pair only requires picking a `destinationAddress` string that makes the concatenation match an already-cached (or soon-to-be-cached) entry for a different token/account. No privileged access is required — a normal SDK caller can trigger this by issuing crafted withdrawal/fee-estimation calls.

### Recommendation
Use a delimiter-safe or structured cache key (e.g. an array/tuple key, JSON with escaping, or a fixed-width separator not valid in NEAR account IDs such as `${contractId}\u0000${accountId}`) so `(contractId, accountId)` pairs cannot collide. Apply the same review to any other place that builds cache/memoization keys via bare string concatenation of two variable, attacker-influenced identifiers.

### Proof of Concept
1. Instantiate one shared `DirectBridge` (as a long-running service would).
2. Trigger `estimateWithdrawalFee` for token `T1` and `destinationAddress = "acc.near"`, where `T1 + "acc.near"` results in the account being deemed to have sufficient storage (`minStorageBalance <= userStorageBalance`), populating the cache at key `"T1acc.near"`.
3. Trigger `estimateWithdrawalFee` for token `T2` and a crafted `destinationAddress` such that `T2 + destinationAddress === "T1acc.near"` (attacker freely chooses `destinationAddress`, and can also choose which supported token to use as `T2`/`T1`).
4. Observe the second call returns the first call's cached `[minStorageBalance, userStorageBalance]`, so `storageDepositFee` is computed as `0n` even though the real destination account has no storage registered for `T2`.
5. `createWithdrawalIntents` builds an `ft_withdraw` intent with `storage_deposit: undefined`; when relayed on-chain, the transfer to the unregistered account fails after the debit intent has executed, leaving the withdrawal stuck.

	private async getCachedStorageDepositValue(
		contractId: string,
		accountId: string,
	): Promise<[MinStorageBalance, StorageDepositBalance]> {
		const key = `${contractId}${accountId}`;
		const cached = this.storageDepositCache.get(key);
		if (cached !== undefined) {
			return cached;
		}

		const result = await Promise.all([
			getNearNep141MinStorageBalance({
				contractId: contractId,
				nearProvider: this.nearProvider,
			}),
			getNearNep141StorageBalance({
				contractId: contractId,
				accountId: accountId,
				nearProvider: this.nearProvider,
			}),
		]);

		if (result[1] >= result[0]) {
			this.storageDepositCache.set(key, result);
		}

		return result;
	}
