### Title
`describeWithdrawal()` in PoaBridge misreports withdrawal status/tx-hash when multiple withdrawals of the same asset are batched in one intent - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal()` resolves the on-chain outcome of a specific withdrawal purely by `assetId`, ignoring the caller-supplied `index`, `destinationAddress`, and `amount`. When a single signed intent batches two or more withdrawals of the same asset (e.g. two BTC withdrawals to different addresses/amounts in one transaction), each `describeWithdrawal()` call returns the *first* matching POA withdrawal record regardless of which of the batched withdrawals is actually being queried. This breaks the equality "status/txHash reported == the actual on-chain outcome for *this* withdrawal", and can make a caller/integrator believe a withdrawal to address B completed with a tx hash that in reality corresponds to the transfer sent to address A.

### Finding Description
`createWithdrawalIdentifiers()` in `packages/intents-sdk/src/core/withdrawal-watcher.ts` assigns a sequential `index` per bridge route to every withdrawal in a batch: [1](#0-0) 

For POA-bridge withdrawals, however, `describeWithdrawal()` does not use that `index` (or the `destinationAddress`/`amount` that uniquely identify the withdrawal) to disambiguate results returned by the POA status API. Instead it matches solely on `assetId`: [2](#0-1) 

The comment right above the match call even documents the limitation explicitly:
"Response list is unsorted, so we match by assetId instead of index" - i.e. the implementation is aware that ordering can't be trusted, yet still falls back to a match key (`assetId`) that is not unique when the same token is withdrawn more than once in a batch.

This exact same limitation is also called out in the sibling low-level helper used for the promise-based waiter: [3](#0-2) 

Both the direct SDK caller (`watchWithdrawal` in `withdrawal-watcher.ts`) and any external integrator polling `bridge.describeWithdrawal({..., index})` per-withdrawal expect the returned `{status, txHash}` to correspond to *that specific* withdrawal (identified by its own `destinationAddress`/`amount`), not merely to "some withdrawal of the same asset from this NEAR tx." Because `findMatchingWithdrawal` returns the *same* record for every index sharing an `assetId`, calling `describeWithdrawal()` for withdrawal #0 and #1 (same asset, different destination) in a batched intent can both resolve to the withdrawal record belonging to only one of them.

### Impact Explanation
If a user (or integrator building on top of the SDK) submits a single signed intent that batches two POA withdrawals of the same token (e.g., 0.5 BTC to address A and 0.3 BTC to address B), `watchWithdrawal()`/`describeWithdrawal()` for the *second* withdrawal identifier can report `{status:"completed", txHash: <hash-of-transfer-to-A>}` even though the transfer to B never happened yet (or happened with a different hash/amount). Any integrator that uses this status+hash to release credit, mark an invoice paid, or refund a customer would attribute the wrong destination's completion to the queried withdrawal — this is exactly the "status or hash misreport making an integrator credit or refund twice" class of High-impact issue: a caller can be told an outbound transfer to their address succeeded (with a specific real tx hash) when in fact the funds went to a different destination in the same batch, or the completion of one leg is double-counted for both legs.

### Likelihood Explanation
This does not require any privileged party to act maliciously — any legitimate user/integrator that batches ≥2 withdrawals of the same POA-bridge asset in one signed intent (a normal, supported SDK operation — nothing prevents `createWithdrawalIdentifiers` from producing multiple indices for the same bridge/asset) will trigger the ambiguous match. The bug is deterministic once such a batch exists (not a race condition), making it straightforward to reproduce whenever multiple same-asset POA withdrawals are combined.

### Recommendation
`findMatchingWithdrawal` (and the analogous logic in `waitForWithdrawalCompletion.ts`) must disambiguate withdrawals using fields that uniquely identify a specific withdrawal within a NEAR transaction — e.g., match on `(assetId, destinationAddress, amount)` tuple, or track and consume the already-used matches so each `index` maps to a distinct API record (sorting deterministically on both sides), instead of matching on `assetId` alone. Until POA's API can supply a unique per-withdrawal identifier, the SDK should refuse to return `"completed"` when more than one candidate record could plausibly correspond to the query, and instead surface an explicit ambiguity error.

### Proof of Concept
1. Sign and send a single NEAR intent containing two `ft_withdraw` intents for `nep141:btc.omft.near`: one for 50000000 sats to address `A`, one for 30000000 sats to address `B`.
2. `createWithdrawalIdentifiers()` produces `wid0 = {index:0, withdrawalParams:{destinationAddress:A, amount:50000000,...}}` and `wid1 = {index:1, withdrawalParams:{destinationAddress:B, amount:30000000,...}}`, both routed to `PoaBridge`.
3. Call `bridge.describeWithdrawal(wid1)` while the POA withdrawal-status API has already resolved the withdrawal to `A` as `COMPLETED` (with `transfer_tx_hash = "hash-A"`) but the withdrawal to `B` is still `PENDING`.
4. `findMatchingWithdrawal(response.withdrawals, "nep141:btc.omft.near")` returns the `A` record for both `wid0` and `wid1` queries (matches by `assetId` only), so `describeWithdrawal(wid1)` incorrectly returns `{status:"completed", txHash:"hash-A"}` even though funds were never sent to `B`. export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
