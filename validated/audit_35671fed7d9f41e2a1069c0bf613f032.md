### Title
Webhook HMAC does not bind the `shop` (or `topic`/`api-version`/`webhook-id`) header, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers. `Utils::HmacValidator` verifies the HMAC exclusively against that body, so the identity fields that `Registry.process` hands to the merchant's webhook handler are never covered by the signature.

### Finding Description
`Registry.process` validates a webhook purely by checking the raw body's HMAC: [1](#0-0) 

The signable string used for that validation is defined as just the raw body, never including the `shop`, `topic`, `webhook-id`, or `api-version` headers: [2](#0-1) 

`HmacValidator.validate` computes and compares the HMAC solely over `verifiable_query.to_signable_string`: [3](#0-2) 

The broken equality is:
`HMAC_valid(body) == true` is treated as equivalent to `shop_header == originating_shop`, but the gem only proves `HMAC_valid(body)`; it never proves that `shop_header` (or `topic`/`webhook_id`/`api_version`) was the value Shopify actually signed for that body. Since `body` and `hmac` are bound together by Shopify's signature but `shop-domain` is not part of that signed material, any two values can be freely recombined without invalidating the signature.

Once `HmacValidator.validate` succeeds, `Registry.process` forwards the unauthenticated `request.shop` straight into the handler's `WebhookMetadata`, so host applications that key persistence, deduplication, or authorization decisions off `data.shop` receive an attacker-controlled tenant identifier alongside a Shopify-signed body: [4](#0-3) 

### Impact Explanation
An unprivileged user who operates their own store with the app installed will legitimately receive Shopify-signed webhooks (body + HMAC) for their own shop. Because the `shop-domain` header (and `topic`/`webhook-id`) are not part of the signed material, that same (body, HMAC) pair remains valid if replayed to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. Any host application that trusts `WebhookMetadata#shop` after `Registry.process` succeeds — which is the exact value the gem hands them post-validation — can be made to process or persist attacker-supplied webhook content under another tenant's identity, i.e., cross-tenant data injection/confusion.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own legitimately-issued webhook (any topic they can trigger, e.g. by editing their own store), and (2) the ability to POST to the app's public webhook receiving endpoint with modified headers — both are within reach of an unprivileged internet user/merchant, requiring no `api_secret_key`, access token, or privileged access.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material used by `to_signable_string`, or otherwise cryptographically bind them (e.g., derive/verify `shop` from a value included in the signed payload) before passing them to `WebhookMetadata`. At minimum, document that host applications must not trust `data.shop`/`data.topic` from `WebhookMetadata` as authenticated unless separately corroborated (e.g., cross-checked against a known/expected shop for the receiving endpoint).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker resends that exact body and HMAC to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and/or a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `HmacValidator.validate` recomputes the HMAC over the (unchanged) body and it matches, so `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`. [1](#0-0) 
4. Any host application logic keyed on `data.shop` now acts on attacker-controlled data as if it originated from `victim.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
