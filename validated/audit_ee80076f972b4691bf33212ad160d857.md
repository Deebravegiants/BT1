## Title
Permissionless `CallDispatcher.dispatch()` Allows Theft of Any Residual ETH/ERC20 Left on the Shared Dispatcher — ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher` is deployed once and reused as a **shared, protocol-wide singleton** (the same address `0xE2C7e576E26E0bE7aC97c6fE925bcDAbD87c4bEd` on Ethereum, Arbitrum, Optimism, Base, BSC, Gnosis, Polygon, and Polkadot Hub) by unrelated applications: `IntentGatewayV2` and every `HyperFungibleToken`/`WrappedHyperFungibleToken`/`BridgeToken` deployment that reads the same `CALL_DISPATCHER` config value. [1](#0-0) [2](#0-1) [3](#0-2)  `CallDispatcher.dispatch()` executes fully attacker-controlled `Call{to, value, data}` items with the dispatcher itself as `msg.sender`, and has **no access control whatsoever**. [4](#0-3)  Because tokens/ETH are routinely pushed onto this shared contract's balance by legitimate flows (mint-to-dispatcher for swaps, `predispatch`/`output.call` escrow steps) and there is no dust-sweep guarantee in every caller (HFT/WHFT never sweep leftovers, unlike `IntentGatewayV2._execute`), any residual balance left on the dispatcher after one flow's transaction completes can be drained by any unrelated third party in a later transaction — the same fund-draining pattern described in the analog report (an intermediary contract that both holds transient funds and exposes a permissionless arbitrary-call primitive).

### Finding Description
`CallDispatcher.dispatch(bytes memory encoded)` decodes an attacker-supplied `Call[]` and, for each entry, performs `to.call{value: call.value}(call.data)` using the dispatcher's own balance and authority, with **no `onlyOwner`/`onlyHost`/caller check at all**: [5](#0-4) 

The contract also has an unrestricted `receive()` that accepts ETH from anyone. [6](#0-5) 

This single `CallDispatcher` instance is reused across independently-deployed, mutually untrusted apps:
- `IntentGatewayV2.placeOrder` transfers `predispatch` input assets (native value via `_sendValue`, ERC20 via `safeTransferFrom`) **directly to the dispatcher's balance** before invoking `dispatch()` on the user/solver-supplied call array. [7](#0-6) 
- `HyperFungibleToken`/`WrappedHyperFungibleToken`/`BridgeToken` `onAccept` mints or unlocks bridged tokens to a `beneficiary` that the *sender on the source chain* controls, then calls `ICallDispatcher(_dispatcher).dispatch(message.data)`. The docs explicitly instruct users to set the beneficiary to the `CallDispatcher` address itself so a subsequent swap `Call[]` can spend the freshly minted tokens: "mint to the CallDispatcher so the swap can spend the tokens." [8](#0-7) [9](#0-8) 

Unlike `IntentGatewayV2._execute`, which explicitly sweeps *any* residual balance the dispatcher holds after executing calldata back to the gateway (`"any residual token balances left on the dispatcher are swept back to this contract"`), [10](#0-9)  the HFT/WHFT `onAccept` calldata-execution path has **no equivalent sweep**: it mints tokens to the dispatcher, calls `dispatch(message.data)`, and simply returns — any tokens the source-chain sender's `Call[]` fails to fully consume (partial swap fills, rounding, an incompletely-specified approve, or a sender who forgets a sweep step) remain sitting on the dispatcher's balance indefinitely, across transactions. [9](#0-8) [11](#0-10) 

Because `dispatch()` is permissionless, any unrelated actor can, in a separate transaction, call `CallDispatcher.dispatch()` with a `Call[]` that steals whatever balance is currently sitting there — e.g. `Call({to: leftoverToken, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, IERC20(leftoverToken).balanceOf(dispatcher))})`, or for stray ETH, `Call({to: attacker, value: address(dispatcher).balance, data: ""})`. This mirrors the analog report's root cause exactly: an intermediary contract (there, `L2CrossDomainMessenger`/`L1CrossDomainMessenger`; here, `CallDispatcher`) that (1) can transiently or unintentionally hold ETH/tokens belonging to third parties, and (2) exposes a permissionless function performing an arbitrary external call, allowing anyone to redirect those held funds to themselves.

### Impact Explanation
Any ETH or ERC20 tokens left temporarily or accidentally on the shared `CallDispatcher` — from an HFT/WHFT calldata-execution flow that didn't fully consume the minted amount, from a plain accidental transfer/`receive()` deposit, or from any other user of the shared dispatcher across any of the many production apps referencing it — can be stolen outright by any attacker calling `dispatch()` directly. Given `CallDispatcher` is a cross-chain singleton reused by `IntentGatewayV2` and every deployed `HyperFungibleToken`/`WrappedHyperFungibleToken`/`BridgeToken` instance, this is a shared attack surface across the whole bridging/token/intents stack rather than an isolated per-app issue, and represents concrete, permanent, unrecoverable theft of user or protocol funds.

### Likelihood Explanation
Exploitation requires only a single permissionless call to `dispatch()` — no privileged role, no governance, no consensus forgery. The precondition (non-zero balance sitting on `CallDispatcher`) is realistic and even encouraged by the documented "mint to CallDispatcher for a swap" pattern, where any imperfect accounting in the sender-supplied `Call[]` (dust from a swap, an under-approved amount, a sender who omits a final sweep step) leaves funds on the dispatcher with no automatic recovery, unlike the `IntentGatewayV2` path which does sweep. An attacker watching mempool/chain state for a non-zero dispatcher balance can react opportunistically at any time.

### Recommendation
- Restrict `CallDispatcher.dispatch()` so it is only callable by a trusted, per-caller-scoped context — e.g., deploy a fresh, per-app (or per-request) minimal-proxy dispatcher instance instead of sharing one singleton, or add caller-authorization (`onlyAuthorizedCaller`) plus atomic sweep-back-to-caller guarantees.
- Require that any HFT/WHFT/BridgeToken `onAccept` calldata-execution path sweep 100% of the dispatcher's resulting balance for every asset touched (mirroring `IntentsBase._execute`'s residual-balance sweep) so nothing can persist on the dispatcher across transactions.
- Alternatively, make `dispatch()` require the caller to have deposited the exact funds being moved within the same call (e.g., pull funds via `transferFrom` inside `dispatch()` itself rather than relying on a pre-funded shared balance), eliminating any persistent balance for third parties to target.

### Proof of Concept
1. A user bridges tokens through `HyperFungibleToken`/`WrappedHyperFungibleToken` with `SendParams.to = CALL_DISPATCHER` and a `data` payload that approves and swaps most, but due to slippage/rounding not all, of the minted tokens (e.g., `swapExactTokensForTokens` with `amountIn < mintedAmount`, or an approval that reverts/undershoots on a fee-on-transfer token).
2. `onAccept` mints `message.amount` tokens to `CALL_DISPATCHER`, then calls `ICallDispatcher(_dispatcher).dispatch(message.data)`; the swap succeeds and leaves dust tokens on `CallDispatcher`'s balance — see `HyperFungibleToken.onAccept`. [9](#0-8) 
3. In a later, completely separate transaction, an attacker calls `CallDispatcher.dispatch(abi.encode(calls))` where `calls[0] = Call({to: leftoverToken, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, IERC20(leftoverToken).balanceOf(address(dispatcher)))})`.
4. `dispatch()` has no caller check, so the call succeeds and the entire dust balance (or any other balance sitting on the shared dispatcher from any app) is transferred to the attacker. [4](#0-3)

     * @dev Receive function to accept ETH transfers

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
