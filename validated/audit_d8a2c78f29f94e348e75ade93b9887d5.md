### Title
Missing swap deadline protection in `EvmHost` native-fee-to-feeToken conversion enables sandwich attacks - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all allow any unprivileged caller to pay protocol/relayer fees with native tokens, which the contract converts to `feeToken()` via `IUniswapV2Router02.swapETHForExactTokens`. In all three cases the `deadline` argument passed to Uniswap is `block.timestamp`, which is the exact anti-pattern described in the referenced report: it renders Uniswap's transaction-expiration protection meaningless, because whatever block eventually mines the transaction will always satisfy `deadline == block.timestamp`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
Uniswap's `deadline` parameter is meant to bound how long a signed/submitted swap request remains valid, protecting the sender from having their trade executed against a price that has moved significantly since the transaction was created and broadcast. Setting `deadline = block.timestamp` at call time defeats this purpose entirely: the check `require(deadline >= block.timestamp)` inside the router is evaluated against the timestamp of the block that eventually includes the transaction, not the timestamp at which the swap parameters (`amountOut`/`msg.value` cap) were computed off-chain by the caller. A transaction can sit in the mempool for an extended period (e.g., during gas-price spikes) and still pass the deadline check the moment it is finally mined, even though the market price of the native token relative to `feeToken()` may have moved substantially in the interim.

This is functionally identical to the root cause in the external report (`Swap.swapTokensMulti` setting `deadline = block.timestamp` when calling Uniswap's `exactInput`), just instantiated in `EvmHost`'s native-fee-to-`feeToken` conversion path rather than a reward-token-selling path. Any of the three call sites — `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` — is reachable directly by any unprivileged account sending a POST/GET dispatch or funding an existing request with `msg.value > 0`.

### Impact Explanation
Because `swapETHForExactTokens` is an exact-output swap, the fee-token amount received is fixed (`post.fee`/`get.fee`/`amount`), but the amount of native token actually consumed is variable and bounded only by `msg.value`, which callers typically set generously above the expected cost to avoid reverts. A staleness window with no deadline enforcement allows an MEV actor to manipulate the pool price around the transaction's inclusion (classic sandwich attack): pushing the effective price of `feeToken()` in terms of native token up just before the swap executes and reverting the price afterward, capturing the difference as profit. Depositors/dispatchers calling `dispatch`/`fundRequest` with native currency end up paying more native token than the fair market rate for the same fixed fee-token output, directly transferring value to the attacker at the caller's expense. Since this affects the core dispatch/fee-funding path of `EvmHost`, it can be triggered on every native-token-funded dispatch across the protocol.

### Likelihood Explanation
Any account can trigger this by simply calling `dispatch()` or `fundRequest()` with a native-token payment; no privileged role, governance action, or special conditions are required. The presence of price-sensitive AMM pools for the fee token (as configured via `_hostParams.uniswapV2`) makes this economically exploitable whenever gas markets are volatile enough to cause even a short mempool delay, which is a routine and expected occurrence on Ethereum mainnet and L2s alike.

### Recommendation
Do not use `block.timestamp` as the Uniswap `deadline`. Accept a caller-supplied deadline parameter (or a bounded default, e.g. a few minutes) for `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, and consider making the default configurable by governance/admin so it can be tuned per chain (mainnet vs. L2) as recommended in the referenced report. Apply the same fix consistently to any other internal swap helper in the codebase that hardcodes `deadline = block.timestamp` for native-to-feeToken conversions.

### Proof of Concept
1. Attacker monitors the mempool for a `dispatch(DispatchPost)` (or `dispatch(DispatchGet)`/`fundRequest`) transaction with `msg.value > 0`. [4](#0-3) 
2. Because gas price is briefly elevated, the victim's transaction stays pending; the attacker front-runs it with a swap that shifts the native-token/`feeToken()` pool price unfavorably for the victim.
3. When the victim's transaction is eventually mined, `deadline == block.timestamp` trivially passes (it always does, regardless of how stale the price assumption behind `msg.value` has become), so `swapETHForExactTokens` executes at the manipulated price, consuming more of the victim's `msg.value` than would occur at the fair price.
4. The attacker back-runs to restore the pool price and reverse their initial trade, pocketing the price difference extracted from the victim's native-token payment.

    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);

        }
