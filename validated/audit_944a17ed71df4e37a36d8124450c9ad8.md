## Title
Permissionless external DEX pool pre-creation lets an attacker seize `bonding_curve_launchpad` graduation liquidity - (File: `aptos-move/move-examples/bonding_curve_launchpad/sources/liquidity_pairs.move`)

### Summary
`bonding_curve_launchpad`'s `graduate()` function calls `router::create_pool_coin<AptosCoin>(fa_object_metadata, false)` on the external `swap` DEX and then immediately adds liquidity via `add_liquidity_coin_entry_transfer_ref`, which computes deposit amounts using `router::optimal_liquidity_amounts` based on whatever reserves exist in the pool at that moment. `router::create_pool_coin` / `router::create_pool` are `public entry` functions callable by anyone, with no check that the FA has graduated. This is the exact same custody defect described in the external report: pair/pool creation is not gated on the token's "graduated" state, so an attacker can pre-create the pool and skew its reserves before the protocol's own liquidity-seeding transaction runs. ### Finding Description
1. `swap_apt_to_fa` checks the APT threshold and, once crossed, calls `graduate()` in the same transaction: [3](#0-2) 
2. `graduate()` unconditionally calls `router::create_pool_coin<AptosCoin>(fa_object_metadata, false)` and then `add_liquidity_coin_entry_transfer_ref`, which internally calls `router::optimal_liquidity_amounts` to compute the amounts of APT/FA to deposit based on the pool's *current* reserves: [4](#0-3) 
3. `router::create_pool_coin` / `router::create_pool` are public entry functions with no access control and no check on the FA's graduation state — anyone can create the AptosCoin/FA pool ahead of time: [1](#0-0) 
4. `optimal_liquidity_amounts` derives the deposit ratio purely from `liquidity_pool::pool_reserves(pool)`, with zero protection against attacker-seeded reserves: [5](#0-4) 

Because token IDs and symbols/names used to derive the FA's object address (`get_fa_obj_address`) are known publicly as soon as `create_fa_pair` is called, an attacker can, before the bonding curve's APT threshold is crossed (or even by front-running the graduation transaction in the mempool), call `router::create_pool_coin<AptosCoin>(fa_metadata, false)` and then `router::add_liquidity_entry`/`add_liquidity_coin_entry` to seed the pool with a heavily skewed ratio (e.g., a large amount of wrapped APT and a negligible/1-unit amount of the FA, or vice versa). When `graduate()` subsequently executes `add_liquidity_coin_entry_transfer_ref`, the router computes "optimal" amounts against this attacker-controlled ratio rather than the bonding curve's actual reserve ratio, causing most of the real APT (or FA) collected by `liquidity_pairs` to be misallocated relative to the tiny counterpart amount the attacker seeded — mirroring the constant-product-manipulation exploit from the external report (`amountB = amountA * reserveB / reserveA`). Whatever surplus token is left in the pool after this skewed deposit can then be extracted by the attacker via a normal swap against the now-manipulated pool.

### Impact Explanation
This breaks the custody invariant that protocol-collected APT (accumulated from every user's bonding-curve buy transaction) is transferred proportionally into the external liquidity pool that legitimate LPs (implicitly, future holders of the graduated token) rely on for price discovery. A successful attack lets the attacker capture a large share of the aggregated APT reserves that all bonding-curve participants contributed, constituting theft of pooled value at graduation — a critical, mainnet-relevant custody violation matching the severity of the original BondingCurvePool report.

### Likelihood Explanation
The attack requires only: (1) knowledge of the FA's name/symbol (public once `create_fa_pair` executes, since `get_fa_obj_address` is a deterministic named-object seed), and (2) a normal unprivileged call to the public `swap` DEX's `router::create_pool` / `router::add_liquidity_entry` before or racing with the `graduate()` transaction. No special permissions, no governance, and no unusual gas costs are required, so likelihood is high whenever `bonding_curve_launchpad` is deployed against a public/permissionless `swap` instance (as the example and README explicitly recommend for production use).

### Recommendation
- Have `bonding_curve_launchpad::liquidity_pairs::graduate` verify that the target `swap` pool does not already exist before calling `router::create_pool_coin`, and abort (or handle gracefully) if it does, rather than blindly seeding liquidity into a pool with attacker-controlled reserves.
- Alternatively/additionally, modify `router::create_pool` in the `swap` module to restrict creation to protocol-approved callers for the specific pair, or have `bonding_curve_launchpad` create the pool for the FA/APT pair eagerly and atomically at FA-creation time (before any trading is enabled) rather than lazily at graduation, so no window exists for an attacker to front-run its creation.
- As defense in depth, `add_liquidity_coin_entry_transfer_ref`/`graduate` should pass explicit `amount_1_min`/`amount_2_min` slippage bounds computed from the bonding curve's own known reserves, rejecting the transaction if the external pool's ratio deviates from the expected bonding-curve exit price.

### Proof of Concept
1. Attacker observes `create_fa_pair(name, symbol, ...)` call to `bonding_curve_launchpad`, learning `name`/`symbol` and thus the deterministic FA object address via `get_fa_obj_address`.
2. Attacker calls `swap::router::create_pool_coin<AptosCoin>(fa_metadata_obj, false)` — permissionless, no check on FA graduation state (`aptos-move/move-examples/swap/sources/router.move:34-40`).
3. Attacker calls `swap::router::add_liquidity_entry`/`add_liquidity_coin_entry_entry` seeding the pool with a highly skewed ratio (e.g., 1e10 wrapped-APT units to 1 unit of FA), establishing `reserves_1 >> reserves_2`.
4. Trading continues on the bonding curve; once `apt_reserves` crosses `APT_LIQUIDITY_THRESHOLD`, `swap_apt_to_fa` triggers `graduate()` (`liquidity_pairs.move:320-325`).
5. `graduate()` calls `router::create_pool_coin` again — it is a no-op/aborts trivially inside `liquidity_pool::create` if idempotent, but the pool with attacker's skewed reserves persists; `add_liquidity_coin_entry_transfer_ref` then calls `optimal_liquidity_amounts` against these skewed reserves (`liquidity_pairs.move:378-412`, `router.move:172-213`), causing most of the protocol's real APT/FA to be deposited at the attacker's dictated ratio instead of the bonding curve's fair exit price.
6. Attacker swaps against the resulting mispriced pool to extract the disproportionate share of APT.

Note: I was unable to fully verify from the indexed code whether `liquidity_pool::create` (called inside `router::create_pool`) aborts outright if a pool already exists at that address, or is idempotent/no-op — the file `swap/sources/liquidity_pool.move` beyond line 180 (the `create` function body) was not available in the retrieved context. This affects whether step 5's `create_pool_coin` call inside `graduate()` reverts the whole transaction (turning this into a griefing/DoS-on-graduation issue) or silently continues (turning it into direct fund theft as described in the external report). I recommend a Devin session inspect `liquidity_pool::create`'s full body to confirm this branch before treating this as conclusively proven fund-theft versus a related griefing/DoS variant of the same root cause (unauthorized/ungated pool creation prior to graduation).

    public fun optimal_liquidity_amounts(
        token_1: Object<Metadata>,
        token_2: Object<Metadata>,
        is_stable: bool,
        amount_1_desired: u64,
        amount_2_desired: u64,
        amount_1_min: u64,
        amount_2_min: u64,
    ): (u64, u64, u64) {
        let pool = liquidity_pool::liquidity_pool(token_1, token_2, is_stable);
        let (reserves_1, reserves_2) = liquidity_pool::pool_reserves(pool);
        // Reverse the reserve numbers if token 1 and token 2 don't match the pool's token order.
        if (!liquidity_pool::is_sorted(token_1, token_2)) {
            (reserves_1, reserves_2) = (reserves_2, reserves_1);
        };
        let amount_1_desired = (amount_1_desired as u128);
        let amount_2_desired = (amount_2_desired as u128);
        let amount_1_min = (amount_1_min as u128);
        let amount_2_min = (amount_2_min as u128);
        let reserves_1 = (reserves_1 as u128);
        let reserves_2 = (reserves_2 as u128);
        let lp_token_total_supply = liquidity_pool::lp_token_supply(pool);
        let (amount_1, amount_2) = (amount_1_desired, amount_2_desired);
        let liquidity = if (lp_token_total_supply == 0) {
            math128::sqrt(amount_1 * amount_2) - (liquidity_pool::min_liquidity() as u128)
        } else if (reserves_1 > 0 && reserves_2 > 0) {
            let amount_2_optimal = math128::mul_div(amount_1_desired, reserves_2, reserves_1);
            if (amount_2 <= amount_2_desired) {
                assert!(amount_2_optimal >= amount_2_min, EINSUFFICIENT_OUTPUT_AMOUNT);
                amount_2 = amount_2_optimal;
            } else {
                amount_1 = math128::mul_div(amount_2_desired, reserves_1, reserves_2);
                assert!(amount_1 <= amount_1_desired && amount_1 >= amount_1_min, EINSUFFICIENT_OUTPUT_AMOUNT);
            };
            math128::min(
                amount_1 * lp_token_total_supply / reserves_1,
                amount_2 * lp_token_total_supply / reserves_2,
            )
        } else {
            abort EINFINITY_POOL
        };
        ((amount_1 as u64), (amount_2 as u64), (liquidity as u64))

    fun add_liquidity_coin_entry_transfer_ref<CoinType>(
        transfer_ref: &TransferRef,
        lp: &signer,
        fa_store: Object<FungibleStore>,
        token_2: Object<Metadata>,
        is_stable: bool,
        amount_1_desired: u64,
        amount_2_desired: u64,
        amount_1_min: u64,
        amount_2_min: u64,
    ) {
        // Wrap APT into a FA. Then, determine the optimal amounts for providing liquidity to the given FA - APT pair.
        let token_1 = coin_wrapper::get_wrapper<CoinType>();
        let (optimal_amount_1, optimal_amount_2, _) = router::optimal_liquidity_amounts(
            token_1,
            token_2,
            is_stable,
            amount_1_desired,
            amount_2_desired,
            amount_1_min,
            amount_2_min,
        );
        // Retrieve the APT and FA from the liquidity provider.
        // `transfer_ref` is used to avoid circular dependency during graduation. A normal transfer would require
        // visiting `bonding_curve_launchpad` to execute the custom withdraw logic. `transfer_ref` bypasses the need to
        // return to `bonding_curve_launchpad` by not executing the custom withdraw logic.
        let optimal_1 = coin::withdraw<CoinType>(lp, optimal_amount_1);
        let optimal_2 = fungible_asset::withdraw_with_ref(
            transfer_ref,
            fa_store,
            optimal_amount_2
        );
        // Place the APT and FA into the liquidity pair.
        router::add_liquidity_coin<CoinType>(lp, optimal_1, optimal_2, is_stable);
    }
