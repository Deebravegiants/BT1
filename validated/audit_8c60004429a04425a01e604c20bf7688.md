### Title
Unbounded attacker-controlled scrypt cost parameters (n/r/p) enable DoS/hang before passphrase verification - ([File: libraries/secure-container/src/index.js])

### Summary
`decrypt()` verifies a checksum that is a plain unkeyed `sha256` over `metadata || blob` [1](#0-0) , which provides no authenticity guarantee against an attacker who controls the entire file bytes (they can simply recompute a matching hash for any crafted `metadata`/`blob`). This allows an attacker-crafted `encryptedData` buffer to carry arbitrary `metadata.scrypt.n/r/p` values that flow unvalidated into `stretchPassphrase`/`scrypt` during `decryptBlobKey`, before the passphrase can ever be verified.

### Finding Description
The call sequence in `decrypt()` is: `conFile.decode` → checksum compare → `conMetadata.decode` → `conMetadata.decryptBlobKey` → `crypto.boxDecrypt` → `crypto.stretchPassphrase(scrypt)` [2](#0-1) .

The checksum verified in step 2 is computed as `sha256(metadata || blobLength || blob)` [1](#0-0) . This is not an HMAC or signature tied to any secret the attacker doesn't have — it's a deterministic hash of the data itself. Since the attacker fully controls `encryptedData` (e.g. an imported backup/file via dapp/QR/deeplink), they can set `metadata.scrypt.n`, `r`, `p` to arbitrary `UInt32BE` values and simply recompute the correct sha256 checksum over their crafted `metadata`+`blob`, so the check at index.js:46-47 passes trivially. The checksum only detects accidental corruption, not attacker tampering, and specifically does nothing to isolate/bound `scrypt` cost parameters.

`conMetadata.decode` parses `scrypt.n/r/p` directly as raw `UInt32BE` fields with no bounds checking [3](#0-2) . These attacker-controlled values are passed straight through `decryptBlobKey` → `boxDecrypt` → `stretchPassphrase` into the underlying `scrypt` call: `scrypt(passphrase, salt, { N: n, r, p, dkLen: 32 }, 'buffer')` [4](#0-3) , with no clamping or validation of `n`, `r`, `p` anywhere in `boxDecrypt`, `createScryptParams`, or `stretchPassphrase` [5](#0-4) [6](#0-5) . I was unable to inspect the `@exodus/crypto/scrypt` wrapper implementation directly (not found in the indexed codebase, likely a separate/external package or excluded from the index), so I cannot confirm with certainty whether that wrapper enforces its own `maxmem`/N ceiling before calling into the native scrypt primitive. This is a gap in verification, but based on all code reachable in `secure-container`, no such bound exists in this library's own logic.

The scrypt computation with attacker-chosen `n`/`r`/`p` occurs before the passphrase is ever checked for correctness — `boxDecrypt` derives the key from `scrypt` unconditionally and only afterward attempts AES-GCM decryption/auth-tag verification, so the expensive/memory-heavy operation always runs regardless of passphrase validity.

### Impact Explanation
An attacker who can get a victim to import a crafted backup/file (e.g., via dapp, QR code, or deeplink import flow) can force the wallet to run `scrypt` with extreme cost parameters (e.g., `N` near `2^32`), which can hang the unlock flow, exhaust device memory, or crash the wallet process — a denial-of-service against wallet unlock/availability. This matches the scoped impact described (denial of wallet unlock/availability via malicious backup import). It does not itself lead to key/secret disclosure or unauthorized signing.

### Likelihood Explanation
This requires no privileged access — only that the victim import an attacker-supplied `encryptedData` blob through any of the described input channels (backup import, QR, deeplink). Crafting the payload is straightforward: an attacker builds a valid `varstruct` file with a chosen `metadata.scrypt.{n,r,p}`, computes the (unkeyed) sha256 checksum themselves, and encodes it via `conFile.encode`. The exploit is fully reproducible and deterministic.

### Recommendation
Enforce strict upper (and lower) bounds on `metadata.scrypt.n/r/p` (and validate that `n` is a power of two and within a safe range, e.g., matching or capping at the values produced by `createScryptParams`) immediately after `conMetadata.decode`, before calling `decryptBlobKey`/`boxDecrypt`. Reject decoding if scrypt parameters fall outside an allow-listed safe range (e.g., `N <= 1<<20`, `r <= 8`, `p <= 1`), independent of the checksum check, since the checksum does not provide authenticity against an attacker who controls the whole file.

### Proof of Concept
Unit/fuzz test in `libraries/secure-container`:
1. Call `encrypt(data, { passphrase })` to get a valid `encryptedData`/`metadata` baseline.
2. Decode via `conFile.decode`, mutate `metadata.scrypt.n` (and/or `r`, `p`) to `0xFFFFFFFF` (UInt32BE max) via `conMetadata.decode`/`encode`, re-serialize with `conMetadata.serialize`.
3. Recompute `checksum = await conFile.computeChecksum(mdBuf, encBlob)` using the attacker's own crafted metadata, and re-encode via `conFile.encode` — demonstrating the checksum passes despite tampering.
4. Call `decrypt(craftedEncryptedData, passphrase)` and assert that it does not return within a bounded time budget (e.g., 2 seconds) / that memory usage explodes, showing the DoS occurs before any passphrase-correctness signal is returned.
5. Expected secure behavior: `decrypt` should throw an explicit "invalid scrypt parameters" error immediately after `conMetadata.decode`, without invoking `scrypt`.

```javascript
export async function decrypt(encryptedData, passphrase) {
  const fileObj = conFile.decode(encryptedData)

  const checksum = await conFile.computeChecksum(fileObj.metadata, fileObj.blob)
  if (!fileObj.checksum.equals(checksum))
    throw new Error('seco checksum does not match; data may be corrupted')

  const metadata = conMetadata.decode(fileObj.metadata)
  const blobKey = await conMetadata.decryptBlobKey(metadata, passphrase)
  const header = conHeader.decode(fileObj.header)
  const data = await conBlob.decrypt(fileObj.blob, metadata, blobKey)

  return { data, blobKey, metadata, header }
}
```

```javascript
export function createScryptParams(params = {}) {
  return { salt: randomBytes(32), n: 16_384, r: 8, p: 1, ...params }

// always returns 32 byte key
export async function stretchPassphrase(passphrase, { salt, n, r, p } = createScryptParams()) {
  const key = await scrypt(passphrase, salt, { N: n, r, p, dkLen: 32 }, 'buffer')
  return { key, salt }
}
```
