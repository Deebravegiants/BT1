### Title
Missing sanity/cap check before applying calc_take_pnl results permanently blocks swap/deposit/withdraw once `last_k` drifts above current pool `k` - ([File: program/src/processor.rs])

### Summary
The Sherlock report describes a missing cap check before `AddEcosystemTokensMinted`, which lets recorded minted-supply state exceed the real cap, producing a negative value later that trips a hard error (`ErrNegativeTargetEmissionPerToken`) and "compromises" the block. The analogous root cause in `raydium-amm--010` is in `Processor::calc_take_pnl`, which enforces an invariant (`pool_pc*pool_coin >= calc_pnl_x*calc_pnl_y`, i.e. current k must not fall below the stored "last k") with no tolerance/cap and no recovery path other than returning a hard error, `AmmError::CalcPnlError`. Every user-facing liquidity/swap instruction (`Deposit`, `Withdraw`, `SwapBaseIn`, `SwapBaseOut`) calls this function on the hot path, so if the stored `target_orders.calc_pnl_x/calc_pnl_y` (last k) ever exceeds the freshly computed current k due to rounding, the pool becomes permanently unusable for ordinary users.

### Finding Description
`calc_take_pnl` is invoked from every non-privileged instruction that touches the pool's reserves: `process_deposit` [1](#0-0) , `process_withdraw` (unless status is `WithdrawOnly`) [2](#0-1) , and the swap instructions.

Inside `calc_take_pnl`, the code strictly requires that the current invariant (`pool_pc_amount * pool_coin_amount`) be greater than or equal to the previously recorded `calc_pnl_x * calc_pnl_y` ("last k"); if this ever fails, it returns a hard error with no fallback and no clamping: [3](#0-2) [4](#0-3) 

After every deposit/withdraw, `target_orders.calc_pnl_x` and `calc_pnl_y` are recomputed by adding/subtracting normalized (decimal-scaled) deltas and truncated `delta_x`/`delta_y` PnL contributions: [5](#0-4) 

Because `normalize_decimal_v2`/`restore_decimal` round trips involve integer truncation (as used throughout `calc_take_pnl`, e.g. `.as_u64()` truncations on `pc_pnl_amount`/`coin_pnl_amount`), the "last k" bookkeeping value stored in `target_orders` can accumulate faster than the actual vault-derived "current k" over repeated deposit/withdraw/swap cycles, exactly the same class of defect as the Sherlock report: a monotonic accounting quantity is updated without ever being capped/reconciled against the true, bounded quantity it is supposed to track (there, `EcosystemTokensMinted` vs. `ecosystemMaxSupply`; here, `calc_pnl_x*calc_pnl_y` vs. the real pool invariant). Once the tracked value overtakes the real bound, the code path that consumes it (`GetEcosystemMintSupplyRemaining` → negative value → `ErrNegativeTargetEmissionPerToken` there; the `pool_pc_amount*pool_coin_amount >= calc_pc_amount*calc_coin_amount` check → `AmmError::CalcPnlError` here) unconditionally errors out.

### Impact Explanation
Once triggered, `calc_take_pnl` returns `Err(AmmError::CalcPnlError)` for every subsequent `Deposit`, `Withdraw`, and swap call on that pool, since all of them call it unconditionally (withdraw only skips it when the pool's status has already been set to `WithdrawOnly` by the privileged pool owner via `SetParams`). This means ordinary depositors, LPs, and swappers can be denied access to the pool's core liquidity/swap functionality — a freeze of pool operations reachable purely by normal trading activity, not requiring any privileged action, mirroring the "one block/one operation permanently compromised" impact in the original report.

### Likelihood Explanation
Likelihood depends on how quickly rounding drift between the truncated `calc_pnl_x/calc_pnl_y` bookkeeping and the real vault-derived invariant accumulates across many small deposit/withdraw/swap cycles; each individual step's truncation is at most 1 unit, but with enough transaction volume and adversarially chosen small deposit/withdraw amounts (attacker fully controls instruction data and can freely call `Deposit`/`Withdraw`/swap repeatedly with tiny amounts to maximize rounding skew), the invariant can eventually be pushed to the failing regime. I could not fully verify, within the exploration budget, the exact rounding direction of every intermediate step (`normalize_decimal_v2`, `restore_decimal`, and the fee-adjusted `pc_pnl_amount`/`coin_pnl_amount` truncations) to give a precise bound on how many transactions are required, so the exact likelihood/exploitability threshold is uncertain and would need dedicated arithmetic analysis or fuzzing to confirm the drift direction and magnitude per operation.

### Recommendation
Add a bounded/clamped reconciliation instead of a hard failure in `calc_take_pnl`: if `pool_pc_amount*pool_coin_amount < calc_pc_amount*calc_coin_amount`, either (a) skip PnL extraction for that call (treat delta as zero) and resync `calc_pnl_x`/`calc_pnl_y` to the current normalized invariant rather than erroring, or (b) clamp the "last k" comparison with a defined tolerance and recompute `calc_pnl_x`/`calc_pnl_y` from the live vault balances rather than propagating stale, potentially-drifted bookkeeping values, so ordinary user instructions can never be permanently blocked by internal PnL-tracking drift.

### Proof of Concept
Not independently reproduced; a full PoC would require constructing a sequence of small `Deposit`/`Withdraw` (or swap) instructions against a test validator/BanksClient harness to accumulate enough rounding drift in `target_orders.calc_pnl_x`/`calc_pnl_y` relative to the live vault balances until `calc_take_pnl`'s invariant check at `program/src/processor.rs:190-196` fails with `AmmError::CalcPnlError`, and then show that any subsequent unprivileged `Deposit`/`Withdraw`/swap call fails identically. This exploitation path is plausible given the code structure shown above but was not executed/verified end-to-end in this analysis.
