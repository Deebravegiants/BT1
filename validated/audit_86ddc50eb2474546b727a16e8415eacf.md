### Title
Panicking `unwrap()` in `calc_take_pnl` decimal/pnl math can permanently freeze Deposit/Withdraw for a pool - (File: program/src/processor.rs)

### Summary
`Processor::calc_take_pnl` computes pnl deltas using unguarded `.unwrap()` calls on `checked_sub` operations. The values being subtracted are derived from a decimal-normalize/restore round-trip (`Calculator::normalize_decimal_v2` / `Calculator::restore_decimal`) that only guarantees ordering in *native* decimal units, while the actual subtraction happens in the *normalized* decimal domain. When `coin_decimals != pc_decimals` (attacker/pool-creator controlled at `Initialize2` time) rounding introduced by these conversions can make the "after-pnl" values (`x2`, `y2`) exceed the pre-computed current values (`x1`, `y1`), causing `checked_sub(...).unwrap()` to panic. Because `Deposit`, `Withdraw`, and `WithdrawPnl` all invoke this same function on the same persisted `TargetOrders.calc_pnl_x/calc_pnl_y` state, once the pool state drifts into this condition every subsequent call panics identically, permanently freezing user/LP funds in the pool with no path to reset `calc_pnl_x`/`calc_pnl_y` (they are only updated on the success path of the very functions that panic).

### Finding Description
`calc_take_pnl` guards entry into the sqrt/delta computation with a check performed in **native (restored) decimal units**: [1](#0-0) 

but then computes `x2`/`y2` and the subsequent differences using the **normalized decimal** values (`x1`, `y1`, `target.calc_pnl_x`, `target.calc_pnl_y`) that were passed in as `U256`: [2](#0-1) 

`normalize_decimal_v2`/`restore_decimal` are lossy integer conversions: [3](#0-2) 

Because the guard condition is evaluated in one decimal domain (native) while the arithmetic that must not underflow is performed in another (normalized), integer truncation from `normalize_decimal_v2`/`restore_decimal` (amplified when `coin_decimals` and `pc_decimals` differ significantly, which a pool creator freely chooses via the underlying mint decimals at `Initialize2`) can make `x2 > x1` or `y2 > y1` even though the native-unit guard passed. The unchecked `.unwrap()` calls at `diff_x`/`diff_y` then panic instead of returning a `ProgramError`.

`calc_take_pnl` is reachable from all three fund-moving flows that touch `TargetOrders`:
- `process_deposit` (unprivileged LP): [4](#0-3) 
- `process_withdraw` (unprivileged LP): [5](#0-4) 
- `process_withdrawpnl` (privileged, but shares the same panicking code path): [6](#0-5) 

Since `target_orders.calc_pnl_x`/`calc_pnl_y` are only mutated on the successful (non-panicking) tail of these same functions, once the pool enters a state where the panic condition is met, **every** future `Deposit`, `Withdraw`, and `WithdrawPnl` call for that pool will deterministically panic and abort — there is no other instruction in `process()` that can reset this persisted state: [7](#0-6) 

### Impact Explanation
A panic inside a Solana program instruction aborts the transaction (all state changes revert), so a single panicking call has no direct effect. The severity here comes from the fact that the triggering condition is a function of **persisted on-chain pool state** (`TargetOrders.calc_pnl_x/calc_pnl_y` vs. current vault balances), not of the failing transaction's own inputs. Once natural trading/deposit/withdraw activity (combined with a decimals-mismatched pool) pushes the pool into this state, *all* unprivileged LPs are permanently unable to call `Deposit` or `Withdraw` against that pool, and `WithdrawPnl` is equally blocked — LP capital becomes irrecoverable through any in-scope instruction. This satisfies the "permanent freezing of user or LP funds" bar even though no direct theft occurs.

### Likelihood Explanation
Triggering requires a pool with a decimal mismatch between coin and pc mints (routine and attacker-controllable at pool-creation time since anyone can call `Initialize2` with arbitrary mints) and enough deposit/withdraw/swap activity to accumulate rounding drift between the native-unit guard and the normalized-unit arithmetic in `calc_take_pnl`. I was not able to fully derive a concrete numeric counter-example (specific decimals/amount sequence) within the available context/tools to conclusively prove the underflow is reachable in practice versus merely theoretically possible from the decimal round-trip logic; this should be validated with a focused unit/property test of `calc_take_pnl` sweeping `coin_decimals`/`pc_decimals` combinations and vault amount sequences before treating this as fully confirmed.

### Recommendation
- Replace the `.unwrap()` calls in `calc_take_pnl` (`diff_x`, `diff_y`, and the surrounding `checked_mul`/`checked_div`/`checked_add` chain) with `checked_sub(...).ok_or(AmmError::CheckedSubOverflow)?` (or equivalent), returning a normal `ProgramError` instead of panicking.
- Make the guard condition and the actual delta computation operate in the same decimal domain (either both native or both normalized) to eliminate the rounding mismatch that can make `x2 > x1` / `y2 > y1`.
- Add an explicit recovery path (e.g., an owner/permissionless instruction) that can safely re-baseline `TargetOrders.calc_pnl_x/calc_pnl_y` to the current pool state if this condition is ever detected, so a single bad calculation cannot permanently brick deposit/withdraw for a pool.

### Proof of Concept
Conceptual reproduction (not a fully verified numeric trace, see Likelihood caveat):
1. Create a pool via `Initialize2` with coin/pc mints of very different decimals (e.g., coin_decimals = 0, pc_decimals = 9), which is fully permitted by `process_initialize2`.
2. Perform a sequence of `Deposit`/`Withdraw`/swap operations that shift the coin:pc ratio while `sys_decimal_value` (fixed at pool init to `10^max(coin_decimals,pc_decimals)`) amplifies rounding error in `normalize_decimal_v2`/`restore_decimal`.
3. Call `Deposit` or `Withdraw` again; if the accumulated rounding causes `x2 > x1` or `y2 > y1` inside `calc_take_pnl`, the `checked_sub(...).unwrap()` at [8](#0-7)  panics, aborting the instruction.
4. Because `target_orders.calc_pnl_x/calc_pnl_y` were never updated (the panic occurred before the update), every subsequent `Deposit`/`Withdraw`/`WithdrawPnl` call reproduces the identical panic, permanently freezing the pool's Deposit/Withdraw functionality.

                msg!("This instruction is not supported, please use Initialize2");
                return Err(AmmError::InvalidInstruction.into());
            }
            AmmInstruction::Initialize(_init1) => {
                msg!("This instruction is not supported, please use Initialize2");
                return Err(AmmError::InvalidInstruction.into());
            }
            AmmInstruction::Initialize2(init2) => {
                Self::process_initialize2(program_id, accounts, init2)
            }
            AmmInstruction::MonitorStep(_monitor) => {
                msg!("This instruction is not supported");
                return Err(AmmError::InvalidInstruction.into());
            }
            AmmInstruction::Deposit(deposit) => {
                Self::process_deposit(program_id, accounts, deposit)
            }
            AmmInstruction::Withdraw(withdraw) => {
                Self::process_withdraw(program_id, accounts, withdraw)
            }
            AmmInstruction::MigrateToOpenBook => {
                msg!("This instruction is not supported");
                return Err(AmmError::InvalidInstruction.into());
            }
            AmmInstruction::SetParams(setparams) => {
                Self::process_set_params(program_id, accounts, setparams)
            }
            AmmInstruction::WithdrawPnl => Self::process_withdrawpnl(program_id, accounts),
            AmmInstruction::WithdrawSrm(_withdrawsrm) => {
                msg!("This instruction is not supported");
                return Err(AmmError::InvalidInstruction.into());
            }
            AmmInstruction::SwapBaseIn(swap) => {
                Self::process_swap_base_in(program_id, accounts, swap)
            }
            AmmInstruction::SwapBaseOut(swap) => {
                Self::process_swap_base_out(program_id, accounts, swap)
            }
            AmmInstruction::SimulateInfo(_simulate) => {
                msg!("This instruction is not supported");
                return Err(AmmError::InvalidInstruction.into());
            }
            AmmInstruction::AdminCancelOrders(_cancel) => {
                msg!("This instruction is not supported");
                return Err(AmmError::InvalidInstruction.into());
            }
            AmmInstruction::CreateConfigAccount => {
                Self::process_create_config(program_id, accounts)
            }
            AmmInstruction::UpdateConfigAccount(config_args) => {
                Self::process_update_config(program_id, accounts, config_args)

    pub fn normalize_decimal(val: u64, native_decimal: u64, sys_decimal_value: u64) -> u64 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**9) -> (1.23*10**6)
        //let ret:u64 = val.checked_mul(amm.sys_decimal_value).unwrap().checked_div((10 as u64).pow(native_decimal.into())).unwrap();
        let ret_mut = (U128::from(val))
            .checked_mul(sys_decimal_value.into())
            .unwrap();
        let ret = Self::to_u64(
            ret_mut
                .checked_div(U128::from(10).checked_pow(native_decimal.into()).unwrap())
                .unwrap()
                .as_u128(),
        )
        .unwrap();
        ret
    }

    pub fn restore_decimal(val: U128, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**6) -> (1.23*10**9)
        // let ret:u64 = val.checked_mul((10 as u64).pow(native_decimal.into())).unwrap().checked_div(amm.sys_decimal_value).unwrap();
        let ret_mut = val
            .checked_mul(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        let ret = ret_mut.checked_div(sys_decimal_value.into()).unwrap();
        ret
    }
