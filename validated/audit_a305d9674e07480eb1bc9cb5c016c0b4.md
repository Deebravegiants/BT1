### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook request's authenticity using an HMAC over the raw body only, but the `shop` (tenant identity) field it passes to the app's handler is read from an unauthenticated HTTP header that is never included in that HMAC computation. This breaks the equality "shop authenticated == shop bound to the verified payload," letting an attacker who legitimately receives one authentic, HMAC-valid webhook reuse (replay) it while asserting an arbitrary victim `shop` domain, which the gem forwards to the app's handler as trusted tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

The `shop` accessor, however, is derived purely from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of `to_signable_string` and therefore never covered by the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC solely against this body-only signable string: [3](#0-2) 

and then forwards `request.shop` (the unauthenticated header) straight into `WebhookMetadata`, which the host application's handler treats as the authoritative tenant identity, per the gem's own documented contract: [4](#0-3) 

Because the `client_secret`/HMAC key is a single, app-wide secret shared across every shop that installs the app (it is not per-shop), any merchant who legitimately installs the app receives real, validly-signed webhooks for their own shop (body + valid `hmac-sha256`). That attacker-merchant can capture such a payload and its valid HMAC and replay the exact same HTTP request to the app's public webhook endpoint, only changing the `x-shopify-shop-domain` header to name a different (victim) shop. `HmacValidator.validate` will still succeed because it recomputes the signature only over the untouched raw body: [5](#0-4) 

The handler then receives `data.shop == victim_shop` for a payload that was never signed with respect to that shop, which is exactly the "shop authenticated vs. shop stored/attributed as identity" binding violation called out in the rules: the byte range verified by HMAC (body only) does not include the byte range parsed as tenant identity (header).

### Impact Explanation
This crosses a tenant boundary: an unprivileged app installer (any merchant able to trigger any webhook topic for their own store, e.g. `orders/create`) can cause the app to attribute webhook data to a different, victim shop, or inject one shop's event stream into another shop's processing pipeline. Depending on how the host app uses `data.shop` (e.g., as a lookup key for session/access-token retrieval, billing, or data storage), this can lead to cross-tenant data corruption, cross-tenant data disclosure, or triggering privileged actions (job enqueue, webhook-driven side effects) against a shop that never sent that event. This matches the "cross-tenant access" Critical-impact category defined in the rules. No access token, `api_secret_key`, or credentials belonging to the victim are required — only the attacker's own legitimate webhook deliveries.

### Likelihood Explanation
Exploitation only requires the attacker to be a normal, unprivileged installer of the target app (a standard, cheap precondition for any public Shopify app) and the ability to send an arbitrary HTTP request to the app's public webhook callback URL with a modified header — no cryptographic secret is needed since the header is unauthenticated by design. The main constraint is that the replayed body content is fixed at capture time (it can't be freely rewritten without invalidating the HMAC), so the attack is strongest for topics whose body content is not itself expected to vary per shop or where mere occurrence/timing/topic-shop mismatch is damaging. Likelihood is High for any handler that trusts `data.shop` without independent verification, which is precisely the pattern the gem's own documentation recommends (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`).

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`/`webhook_id`) to the cryptographic verification, not just the header. Options:
- Extend `VerifiableQuery`/`to_signable_string` for webhooks to include the `shop-domain` header value in the signed material verified against Shopify's HMAC scheme only if Shopify supports/guarantees that (note: Shopify's real webhook HMAC is body-only, so this may require an additional application-level check), or
- Explicitly document and enforce that host applications must independently verify `request.shop` against the shop for which the topic was registered/expected before trusting it, and provide a helper in the gem (e.g., `Registry.process(request, expected_shop:)`) that rejects mismatches, rather than silently forwarding an unauthenticated header as trusted identity.
- At minimum, harden `WebhookMetadata`/`Registry.process` so the shop value is explicitly flagged as "unauthenticated" in the API surface, and add a first-class cross-check against the registry entry (i.e., which shop the topic subscription belongs to) if such association exists in the app's storage.

### Proof of Concept
1. App merchant A installs the target app and registers `orders/create` webhooks, per `docs/usage/webhooks.md` example.
2. Shopify delivers a legitimate webhook to A's endpoint:
   ```
   POST /callback/orders/create
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of raw_body with app client_secret>
   x-shopify-shop-domain: shop-a.myshopify.com
   x-shopify-webhook-id: ...
   <raw_body>
   ```
3. Merchant A (attacker) captures this exact raw request, then resends it to the same endpoint, only replacing the header:
   ```
   x-shopify-shop-domain: shop-b.myshopify.com
   ```
   leaving `raw_body` and `x-shopify-hmac-sha256` untouched.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`@raw_body` only) — verification succeeds because the body was not altered: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata` where `shop == "shop-b.myshopify.com"`, even though the payload's HMAC was never computed with respect to shop B, demonstrating the identity-binding break.

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. - `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)

      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end

end
