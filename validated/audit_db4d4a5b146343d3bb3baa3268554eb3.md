## Finding

### Title
`canGraduate` / `previewLtUntilGraduation` use an unchecked reserve subtraction that can underflow and permanently DoS buy/sell - (File: `packages/contracts/src/Bonding.sol`)

### Summary
Both graduation-trigger view functions compute "real LT raised" as a plain subtraction of the pair's stored asset reserve minus a recovered virtual reserve, with no floor/guard. If the stored `assetReserve` ever sits at or below the recovered `virtualLtReserve` (e.g. through the rounding asymmetry between the capped buy path and the uncapped sell path, or repeated buy/sell cycles that drift the invariant), the subtraction reverts under Solidity 0.8's default overflow/underflow checks. Since both functions sit on the hot path of every buy and sell, this is the exact same bug class as the referenced Uniswap-position report: an arithmetic operation that assumes a quantity is always non-negative reverts instead of allowing (or safely clamping) an edge value, permanently freezing user funds.

### Finding Description
`Bonding.canGraduate` computes: [1](#0-0) 

```
(, uint256 assetReserve) = IPair(pair).getReserves();
uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
```

and `previewLtUntilGraduation` performs the analogous subtraction: [2](#0-1) 

The recovered virtual reserve is derived once from `Pair.k() / Token.TOTAL_SUPPLY()` and is treated as a fixed floor for `assetReserve`, as documented in `docs/contracts-scope.md`: [3](#0-2) 

That invariant is not enforced anywhere in `Router.sol`. `Router._computeBuy` and `Router._computeSell` are not perfectly symmetric: the buy path has a capped/ceil-rounded branch that back-calculates `amountInUsed` from the K-invariant when a buy would exceed the real token balance, while the sell path always uses the plain constant-product formula: [4](#0-3) 

Repeated buy/sell activity that exercises this cap branch (or any accumulation of floor/ceil rounding across many trades) can drift the stored `reserve1`/`assetReserve` relative to the fixed `virtualLtReserve` recovered via `k()/TOTAL_SUPPLY`. Nothing clamps `assetReserve` to never fall to or below that recovered value.

### Impact Explanation
`canGraduate` is called from `Zap._sellInternal` on **every sell** to decide whether to route to a real sell or force graduation: [5](#0-4) 

and `previewLtUntilGraduation` is called from `Zap._executeBuy` on **every curve buy** to pre-size the LT mint: [6](#0-5) 

If the underflow condition is ever hit for a given token's pair, both of these calls revert unconditionally (Solidity 0.8 checked arithmetic), which means:
- Every subsequent `Zap.buy` for that token reverts (via `previewLtUntilGraduation`).
- Every subsequent `Zap.sell` for that token reverts (via `canGraduate`).

Since `Zap` is the sole user-facing entry point for trading a curve token, this permanently freezes all trader funds associated with that token — traders can neither buy more nor exit their position, matching the "permanently locked funds" impact class of the referenced report. This is High severity.

### Likelihood Explanation
Likelihood depends on how far the buy/sell rounding asymmetry (capped-buy ceil-rounding vs. uncapped-sell floor-rounding) can drift `assetReserve` relative to the fixed `virtualLtReserve` over a token's lifetime of trading, particularly around tokens that repeatedly approach and back off the overflow cap in `_computeBuy`. I could not fully trace `Bonding.sol`'s buy/sell wrapper functions in this session (my grep for `function buy|function sell` in `Bonding.sol` returned no matches, likely an index/matching limitation), so I cannot confirm every safeguard that might already bound this drift. The structural weakness — an unguarded subtraction assumed to be always non-negative, feeding the dual graduation trigger the contest scope explicitly calls out — is confirmed in the code shown above.

### Recommendation
- Clamp the subtraction: if `assetReserve <= virtualLtReserve`, treat `realLtRaised` as `0` instead of reverting, in both `canGraduate` and `previewLtUntilGraduation`.
- Audit `Router._computeBuy`/`_computeSell` rounding to confirm (or restore) the invariant that `assetReserve` can never fall below the launch-time virtual reserve, and add a regression/invariant test that fuzzes many buy/sell cycles including the overflow-cap branch to confirm `assetReserve >= virtualLtReserve` always holds.

### Proof of Concept
Conceptual PoC (needs on-chain/fork verification, since I could not confirm the exact drift magnitude from the indexed code alone):
1. Launch a token via `Bonding.launch`, establishing `virtualLtReserve = Pair.k() / TOTAL_SUPPLY`.
2. Drive a sequence of buys that repeatedly hit `Router._computeBuy`'s overflow-cap branch (ceil-rounded `amountInUsed`) interleaved with sells through `Router._computeSell` (floor-rounded `assetOut`), across many iterations, to accumulate rounding drift in the stored `reserve1`/`assetReserve`.
3. Once `assetReserve` drifts to ≤ `virtualLtReserve`, call `Zap.buy` or `Zap.sell` on the token; the internal call to `previewLtUntilGraduation`/`canGraduate` reverts on the `assetReserve - virtualLtReserve` (or `reserveAsset - virtualLt`) subtraction, permanently DoS-ing the token's trading through `Zap`.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

    /// @notice Tokens in → LT out.
    function sell(
        uint256 amountIn,
        address token,
        address to
    ) external onlyRole(BONDING_ROLE) returns (uint256 tokensIn, uint256 assetOut) {
        if (amountIn == 0) revert ZeroAmount();

        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        tokensIn = amountIn;

        IERC20(token).safeTransferFrom(to, pairAddr, amountIn);

        assetOut = _computeSell(pairAddr, amountIn);

        IPair(pairAddr).transferAsset(to, assetOut);

        IPair(pairAddr).swap(amountIn, 0, 0, assetOut);
    }

    function _computeSell(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 assetOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        uint256 newReserveToken = reserveToken + amountIn;
        assetOut = reserveAsset - (k / newReserveToken);
    }
