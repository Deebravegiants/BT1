### Title
Attacker-timed short-timeout POST requests cause `HandlerV2.handlePostRequests` to revert the entire relayer batch, griefing relayer gas and blocking co-batched deliveries - (File: evm/src/core/HandlerV2.sol)

### Summary
Any unprivileged application/module on a source chain can dispatch an ISMP POST request with an attacker-chosen `timeout`. On the destination chain, relayers deliver requests in batches via `IHandlerV2.handlePostRequests`, which validates every leaf in the batch (destination + timeout) **before** verifying the merkle proof and dispatching any of them. If a single request in the batch has timed out by the time the transaction lands, the whole call reverts, losing the relayer's gas and blocking delivery of every other (unrelated, legitimate) request bundled in the same batch — the same "spam cheap items with a value that drifts against a later batch-validation check, causing the whole privileged batch operation to revert" pattern as the JOJO `requestWithdraw`/`permitWithdrawRequests` report.

### Finding Description
`handlePostRequests` first loops over the entire `request.requests` array validating destination and timeout for every leaf, only reverting individually: [1](#0-0) 

```
uint256 requestsLen = request.requests.length;
...
for (uint256 i = 0; i < requestsLen; ++i) {
    PostRequestLeaf memory leaf = request.requests[i];
    // check destination
    if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
    // check time-out
    if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
    leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
}
```

This is a per-transaction `revert`, not a per-item skip — a single failing leaf reverts the entire call, before the merkle proof is even verified and before any of the batch's other (valid) requests are dispatched via `host.dispatchIncoming`: [2](#0-1) 

The documentation for this function/its `batchCall` wrapper confirms the same atomic-revert semantics are relied upon by relayer tooling: [3](#0-2) [4](#0-3) 

The relayer's tesseract implementation batches multiple pending messages into a single `IHandlerV2.batchCall`/`handlePostRequests` transaction for gas efficiency: [5](#0-4) 

The `timeout` on a POST request is fully attacker-controlled at dispatch time — any module/application can dispatch a request with an arbitrarily short `timeout` (comparable to how `requestWithdraw` amounts are attacker-controlled in the original report). Because relayers naturally batch multiple in-flight requests together to save gas (mirroring `permitWithdrawRequests` batching many `requestWithdraw` entries), an attacker can:

1. Dispatch many cheap POST requests, each with a `timeout` set just long enough to initially clear `RequestTimeout`/inclusion checks upstream on Hyperbridge, but likely to have elapsed by the time the relayer's destination-chain batch transaction is actually mined (network delay, gas auctions, MEV, or simply batching latency).
2. When the relayer assembles a batch containing these requests together with legitimate, unrelated pending deliveries and submits `handlePostRequests`, the loop hits `revert MessageTimedOut()` on the attacker's stale request and reverts the *entire* transaction — including all the legitimate requests bundled alongside it.
3. The relayer's gas for the failed batch call is wasted, and the co-batched legitimate messages are delayed/DOS'd until they're retried in a smaller batch (if the relayer's retry logic even filters out the stale request first).

This exactly mirrors the report's root cause: a value the attacker controls at submission time (`amount`/`index` there, `timeout` here) is checked once at submission but is validated again, in bulk, by an unprivileged-but-honest actor's later batch operation; drift between submission and batch execution causes the later batch check to fail and revert the whole batch rather than skipping the bad item.

### Impact Explanation
This is a gas-griefing / relayer-DOS vector reachable by any unprivileged application dispatching ISMP requests (no special permissions needed — dispatching is intentionally permissionless per protocol design). Impact:
- Relayers repeatedly waste gas on reverted `handlePostRequests`/`batchCall` transactions.
- Other users' unrelated, legitimate, time-sensitive requests co-batched with the malicious one are delayed or dropped from that attempt, potentially causing their own timeouts to be missed (a message that could have been delivered in time is now delayed past its timeout due to the forced batch failure), which can result in stuck/timed-out cross-chain messages — a route unable to deliver messages for the batching window.
- Cost of attack is cheap (dispatch a POST request with `timeout` set to expire almost immediately, similar to the $2 per `requestWithdraw` in the original report) versus the relayer's wasted gas and the cascading effect on all messages sharing that batch.

This satisfies "a route unable to deliver messages" / DOS class from the validation criteria.

### Likelihood Explanation
Likelihood is moderate-to-high in adversarial conditions:
- Dispatching a request with a short timeout requires no special privilege — any application/module on the source chain can call `dispatch(DispatchPost)` with an arbitrary `timeout`.
- Relayers are economically incentivized to batch many pending messages together (as shown in `tesseract/messaging/evm/src/tx.rs`) to amortize gas costs, which is precisely the condition that makes one bad item poison the whole batch.
- The attacker does not need to predict block timing precisely — they only need the timeout window to be tight enough that ordinary relaying latency (mempool wait, block time, occasional congestion) causes it to lapse before the batch is mined, which is a realistic, repeatable condition rather than a rare edge case.

### Recommendation
Change `handlePostRequests` (and analogous handlers) to skip/continue on a per-leaf destination/timeout failure rather than reverting the whole batch — e.g., exclude the offending leaf from the merkle-proof leaf set and emit a per-request failure event, so a single stale/malicious request cannot poison delivery of the rest of the batch. Alternatively, have relayer tooling pre-filter requests close to timeout before batching, and/or split delivery of untrusted/low-value requests from high-value legitimate ones into separate batches so an attacker's crafted timeout cannot be co-batched with unrelated messages.

### Proof of Concept
1. Attacker deploys/uses an arbitrary `IApp` module on chain A and calls `host.dispatch(DispatchPost{ dest: B, to: victimModule, body: "", timeout: T })` where `T` is chosen to be just long enough to pass any source-side checks but likely to elapse by the time a relayer's destination batch transaction for chain B is mined (e.g., `T = now + relayerAverageBatchDelay - epsilon`).
2. Repeat step 1 cheaply many times, optionally targeting whichever relayer batches are observed to include legitimate high-value requests (public mempool/hyperbridge visibility of pending deliveries allows timing this).
3. Wait for a relayer to assemble a `PostRequestMessage` batch on chain B that includes both the attacker's request and legitimate requests, then call `handlePostRequests`/`batchCall`.
4. If block inclusion is delayed past `T`, the loop's `if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();` fires on the attacker's leaf, reverting the entire transaction: [6](#0-5)  — none of the batch's requests (including the legitimate ones) are delivered, and the relayer's gas for the failed call is lost.

/// Submit a full batch of ISMP messages as a single `IHandlerV2.batchCall` transaction.
///
/// One tx replaces what would otherwise be N separate txs (one per message),
/// cutting gas overhead and nonce management complexity. Atomic: if any
/// inner call reverts, the whole transaction reverts.
pub async fn submit_batch_messages(
	client: &EvmClient,
	messages: Vec<Message>,
) -> anyhow::Result<SubmitOutcome> {
	if messages.is_empty() {
		return Ok((BTreeSet::new(), Vec::new(), Vec::new()));
	}

	let handler_addr = Address::from_slice(&client.handler().await?.0);
	let from = Address::from_slice(&client.address);
	let gas_price = fetch_gas_price(client, false).await?;
	let chain_gas_limit = get_chain_gas_limit(client.state_machine);

	let inner_calls = build_batch_inner_calls(client, &messages).await?;
	let handler_v2 = HandlerV2Instance::new(handler_addr, client.signer.clone());
	let call = handler_v2.batchCall(inner_calls);
	let gas = call.estimate_gas().await.unwrap_or_else(|_| (chain_gas_limit * 8) / 10);
	let calldata = call.calldata().clone();
	let calldata_len = calldata.len();
	let tx_request =
		build_tx_request(from, handler_addr, calldata, gas_price, gas_with_buffer(gas));
