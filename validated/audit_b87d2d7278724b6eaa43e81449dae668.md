## Title
Webhook `shop` (and `topic`/`webhook_id`) header is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking that the HMAC signature matches the raw request **body**, then blindly forwards the unauthenticated `shop-domain` header (along with `topic` and `webhook-id`) to the app's handler as if it had been verified. Because the shop identity is never bound to the bytes that are actually HMAC-verified, any merchant that legitimately installs the app can capture one of their own genuine, validly-signed webhook deliveries and replay it with a forged `x-shopify-shop-domain` header, causing the host app to process attacker-supplied data under a different tenant's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`hmac`, `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers that are not part of the signed material: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e., the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` performs this body-only check and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` as if the whole request were authenticated, forwarding them straight into the app-facing `WebhookMetadata`: [4](#0-3) 

The documented contract explicitly tells integrators that `Registry.process` "will verify the request did indeed come from Shopify and then call the specified handler," implying the entire payload (including `shop`) is authenticated: [5](#0-4) 

Because every shop that installs a given app shares the same app-level `client_secret`, any merchant (an "unprivileged" party with respect to other tenants of the same app) can install the app on their own store and receive a real webhook delivery whose HMAC is valid for that body. Since the HMAC never covers the `shop-domain` header, the attacker can replay that exact body+HMAC pair while substituting `x-shopify-shop-domain` for a victim shop. `HmacValidator.validate` will still succeed (body unchanged), and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop.

Root cause equality that is broken: **shop identity used by the handler == shop identity actually covered by the HMAC**. In this code, `request.shop` (unauthenticated bytes) ≠ `to_signable_string` (the only bytes that `validate_signature` actually checks), yet the two are conflated by `Registry.process`.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: an attacker who is a legitimate (if malicious) app installer for their own shop can forge webhook events "from" any other merchant using the same app, without ever needing the app's `client_secret`. Any host app that scopes side effects (data updates, session lookups, order/customer mutations) by `WebhookMetadata#shop` is exposed to cross-tenant data injection/corruption purely through the gem's own validation gap — this matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
High likelihood: the only requirement is the ability to install the target app on an attacker-controlled shop (a normal, permission-less merchant action) and capture one legitimate webhook delivery, then replay it with a modified shop header to the app's public webhook endpoint. No secret material, session, or privileged access is required.

### Proof of Concept
1. Attacker installs the victim app on their own store `attacker-shop.myshopify.com` and lets it deliver a legitimate webhook, e.g. `orders/create`, capturing the raw JSON body `B` and its valid header `x-shopify-hmac-sha256: H` (`H = HMAC-SHA256(client_secret, B)`).
2. Attacker resends an HTTP POST to the app's webhook endpoint with:
   - body: `B` (unchanged, so `H` still validates)
   - `x-shopify-hmac-sha256: H`
   - `x-shopify-topic: orders/create`
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `B` and succeeds: [4](#0-3) 
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and processes attacker-controlled data under the victim shop's identity.

### Recommendation
Bind the shop (and ideally topic) to the signed material instead of trusting unauthenticated headers:
- Include `shop`, `topic`, and `webhook_id` in the HMAC-signed payload (as GraphQL Admin/Shopify's newer webhook formats already support via full-header signing), or
- Have `Registry.process` cross-check `request.shop` against an independently-authenticated source (e.g., look up the session solely by the value returned from a signed claim, and refuse to trust the header-derived `shop` for anything beyond routing), or
- At minimum, document/require that consuming apps must independently re-validate `WebhookMetadata#shop` against their own session store keyed by an authenticated identifier before acting on it, and update `docs/usage/webhooks.md` to no longer imply that `Registry.process` fully authenticates the shop identity.
