### Title
TOCTOU race between `connect`/`untrust` can resurrect a revoked origin with its full trust/autoApprove privileges - ([File: features/connected-origins/module/connections.js])

### Summary
`connect()` and `untrust()` both operate on `#connectedOriginsAtom` via a non-atomic read-modify-write pattern (`#getOrigin`/`#getData` read, then a separate later `#setData`/`atom.set()` write), and the underlying atom only serializes the `set()` calls, not the reads. If `untrust(origin)` and `connect({id, origin})` race, `connect`'s write can be queued after `untrust`'s write but be based on a data snapshot taken *before* the removal, causing the just-revoked origin entry (including `trusted`/`autoApprove` flags) to be written back into `#connectedOriginsAtom` together with a fresh `activeConnections` entry.

### Finding Description
`connect` reads the origin once via `#getOrigin({ origin })` [1](#0-0) , then delegates the actual write to `#setAttributes`, which performs its own independent existence check and its own independent `#getData()` read before mapping and calling `#setData` [2](#0-1) . `untrust` similarly reads via `isTrusted`/`#getOrigin`, then `#getData()`, filters the origin out, and calls `#setData` [3](#0-2) .

The underlying in-memory atom serializes only `set()` calls via `makeConcurrent` (concurrency 1), while `get()` is unserialized and returns whatever the current in-memory value is at call time [4](#0-3) [5](#0-4) . This means write *order* is determined by when `atom.set()` is invoked (queued), not by when the corresponding read happened. Because `#setAttributes` performs two extra awaited round trips (`#getOrigin` then `#getData`) before finally calling `#setData`, there is a window in which `untrust()` can fully execute (read, filter, and issue its `set()` into the queue) before `connect()` reaches its own `#setData` call. If `connect()`'s `#getData()` snapshot was taken before `untrust`'s write landed, the entry (with its stale `trusted`/`autoApprove` fields, still intact from the read) gets merged with the new `activeConnections` and written back via `#setData` — after `untrust`'s removal is already queued/committed — reintroducing the origin into `#connectedOriginsAtom` as if it were never revoked, along with a live `activeConnections` record.

No re-validation of the origin's continued existence is performed right before the final write in `#setAttributes`; the initial `#getOrigin` check only guards against writing when the origin was *already* absent at the time of that specific call, not against concurrent removal that races the pending write.

### Impact Explanation
This is a privilege-persistence bug: an origin whose trust was explicitly revoked by the user (`untrust`) can be resurrected with its previous `trusted`/`autoApprove` attributes and an active connection, entirely from an attacker/dapp-triggered `connect` call racing with the legitimate revoke action. Since `isTrusted`/`isAutoApprove` (used to gate signing/approval flows) read directly from this same atom entry [6](#0-5) , resurrection of a `trusted: true`/`autoApprove: true` record effectively restores auto-approval privileges for an origin the user believed was disconnected/untrusted.

### Likelihood Explanation
This requires two operations to be in flight concurrently: a dapp-initiated `connect` (reachable from ordinary page/tab connection events) and a user-initiated `untrust` happening at nearly the same time. It is a genuine timing race rather than a deterministic single-call exploit, so it is not trivially reproducible on every attempt, but it is a realistic scenario (e.g. user revokes an origin's trust from settings right as/after a previously-open tab from that origin reconnects or reloads, triggering `connect`). The multi-await structure of `#setAttributes`/`#getOrigin`/`#getData` widens the race window, making it feasible under normal event-loop scheduling without any privileged access.

### Recommendation
Make the origin update atomic by removing the double read/check pattern: have `#setAttributes` (and `connect`/`disconnect`) perform a single `#getData()` read, derive both the existence check and the map from that same snapshot, and avoid any additional `#getOrigin` call between the read and the `#setData` write. Consider using the atom's supported functional `set(currentValue => newValue)` form (as seen in `enforce-rules.ts`'s setter support) so the read-modify-write happens against the atom's own internally serialized value instead of an externally captured stale snapshot, eliminating the TOCTOU window entirely.

### Proof of Concept
Unit test plan (Jest, using `connections.test.js` harness):
1. Seed `connectedOriginsAtom` with a trusted entry: `{ origin: 'exodus.com', trusted: true, autoApprove: true, activeConnections: [] }`.
2. Monkey-patch/spy `connectedOriginsAtom.get` so that the *second* call (the one inside `#setAttributes`'s `#getOrigin`/`#getData` during `connect`) returns the pre-removal snapshot, while triggering `connectedOrigins.untrust({ origin: 'exodus.com' })` to run to completion (including its `set()`) in between the first and second `get()` calls of `connect`.
3. Call `await Promise.all([connectedOrigins.untrust({ origin: 'exodus.com' }), connectedOrigins.connect({ id: 'evil-conn', origin: 'exodus.com' })])` with the interleaving forced as above.
4. Assert: `const origins = await connectedOriginsAtom.get()` — expected (correct) result is `origins` has no entry for `exodus.com`; the vulnerable behavior instead shows `origins` containing `{ origin: 'exodus.com', trusted: true, autoApprove: true, activeConnections: [{ id: 'evil-conn' }] }`, i.e. the revoked origin persisted with restored trust/autoApprove flags.

  connect = async ({ id, origin }) => {
    const value = await this.#getOrigin({ origin })

    if (!value) return

    const activeConnections = value.activeConnections || []
    const newConnection = { id, createdAt: Date.now() }
    const newConnections = uniqBy([...activeConnections, newConnection], 'id')

    await this.#setAttributes({ origin, attributes: { activeConnections: newConnections } })
  }
