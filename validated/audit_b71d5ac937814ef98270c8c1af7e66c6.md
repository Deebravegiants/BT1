### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant identity spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the `shop` (and `topic`, `webhook-id`, `api-version`) values are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then hands the handler a `shop` value that was never part of the signed payload, breaking the binding between "the shop whose secret validated this HMAC" and "the shop the handler believes sent it."

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to that body [2](#0-1) . `Registry.process` only checks `Utils::HmacValidator.validate(request)` — which recomputes HMAC over `to_signable_string` (i.e. the body) and compares it to the `hmac` header — before forwarding `request.shop` to the registered handler untouched [3](#0-2) . `HmacValidator.validate`/`validate_signature` never look at the `shop` header at all [4](#0-3) .

The equality the code implicitly assumes is:
`shop_that_produced_valid_HMAC == request.shop_header`

but the actual guarantee provided by the HMAC check is only:
`body_bytes_verified == body_bytes_the_handler_parses`

Since the same `client_secret` is shared by the app across every shop that installs it, any legitimate webhook (body + valid `hmac-sha256` header) received by shop A can be captured and replayed by that shop's own operator directly to the app's public webhook endpoint with the `shopify-shop-domain` header rewritten to shop B. The HMAC still validates (it only covers the untouched body), but `WebhookMetadata.shop` now reports shop B [5](#0-4) . Any handler that trusts `data.shop` to select which tenant's data to write/delete (a documented, expected usage pattern — e.g. mandatory `shop/redact`, `customers/redact` compliance topics) will act on the wrong tenant.

### Impact Explanation
This is a cross-tenant identity break: an attacker who merely has a legitimate account with the app (i.e., controls one shop) can make the library authenticate a message as though it originated from an arbitrary other shop, causing handler logic keyed on `shop` to run against that victim tenant. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Medium-to-High: the attacker only needs to be a normal merchant of the app to obtain one genuine, HMAC-valid webhook body/signature pair, and webhook HTTP endpoints are by design publicly reachable (no TLS interception, credentials, or privileged access required). No secret needs to be known — the attacker replays an existing valid signature. The only requirement is that the app's webhook handler branches on `shop` (a pattern the library itself documents via `WebhookMetadata.shop` and the mandatory GDPR topics).

### Recommendation
Bind `shop` (and ideally `topic`, `webhook-id`, `api-version`) into the signed material, or otherwise cryptographically tie the header-derived shop to the verified body — e.g., have `Request#to_signable_string` incorporate the shop-domain header, or have `Registry.process` cross-check `request.shop` against a shop resolved independently (such as an already-authenticated session) before dispatching to handlers, and update the library's documentation to warn that `WebhookMetadata.shop` is not itself covered by the HMAC.

### Proof of Concept
1. App installs on `shop-a.myshopify.com`, which is operated by the attacker (a legitimate user of the app).
2. Shopify sends a real webhook to the app: headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw body B>`, `x-shopify-topic: shop/redact`.
3. Attacker captures body `B` and the valid `hmac-sha256` header value (visible to them since it's delivered to their own endpoint/logs).
4. Attacker POSTs directly to the app's public webhook endpoint with the same body `B` and same `hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Request.new` parses headers/body normally [6](#0-5) ; `HmacValidator.validate` recomputes HMAC over `B` using the app's shared `client_secret` and it matches, since `B` and the signature are unmodified [7](#0-6) .
6. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: "shop/redact", shop: "victim-shop.myshopify.com", body: parsed_body, ...)` [5](#0-4) , causing the app to execute the redact/delete logic against `victim-shop.myshopify.com`'s data instead of the attacker's own shop.

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
