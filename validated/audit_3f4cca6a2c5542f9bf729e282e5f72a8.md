### Title

External rewards earned by LP collateral are permanently stranded in the pool - (File: contracts/pool/src/cache/cash.rs)

### Summary

When a user supplies an Aquarius LP token as collateral, the token is transferred to the shared pool and the user receives only internal supply shares. [1](#0-0) [2](#0-1)  The price aggregator explicitly supports valuing Aquarius LP share tokens from their underlying reserves and total shares. [3](#0-2)  However, the pool can only transfer the market's configured `asset_id`, has no reward-claim or arbitrary-token sweep path, and externally received reward tokens are not credited to suppliers or protocol revenue. [4](#0-3) 

### Finding Description

An unprivileged user reaches the affected path through `Controller::supply(caller, account_id, spoke_id, assets)` with `account_id = 0` and `assets = [(HubAssetKey { hub_id: LP_HUB_ID, asset: AQUARIUS_LP }, amount)]`. [5](#0-4)  `process_deposit` transfers the supplied asset directly from `caller` to the singleton pool address before calling `pool.supply`. [6](#0-5) [7](#0-6) 

The pool mints supply shares and increases only tracked `cash`; it does not create a side accounting bucket for external rewards. [8](#0-7)  Every outbound transfer helper constructs its token client from the market's `params.asset_id`, so a reward token different from the deposited LP token cannot be transferred out at all. [9](#0-8) 

`claim_revenue` is not a substitute: it accepts only a `HubAssetKey`, burns the market's internally tracked `revenue` shares, and pays the pool owner. [10](#0-9) [11](#0-10)  The controller then forwards only that measured market-asset receipt to the configured accumulator, not to LP suppliers. [12](#0-11) [13](#0-12) 

Consequently, rewards requiring the LP holder's authorization are unclaimable because the pool has no venue-claim entrypoint, while rewards pushed to the pool arrive as unbooked token surplus that cannot be allocated or swept. [14](#0-13) [4](#0-3) 

### Impact Explanation

LP suppliers permanently lose external yield earned while their LP tokens are custodied by the pool, even though their principal remains represented by the LP shares. [15](#0-14) [16](#0-15)  This is freezing of unclaimed yield: supplier withdrawals can return LP tokens according to internal share accounting, but neither withdrawal nor `claim_revenue` can distribute separate reward tokens received by, or claimable by, the pool. [17](#0-16) [18](#0-17) 

### Likelihood Explanation

The affected state only requires a listed Aquarius LP collateral market and a user deposit, both of which are normal reachable protocol functionality. [3](#0-2) [19](#0-18)  Any venue rewards accruing while the pool is the LP holder are affected, and the loss compounds for all LP collateral suppliers for as long as no reward-claim/distribution mechanism exists. [9](#0-8) [10](#0-9) 

### Recommendation

Add a governed reward-claim and distribution path for reward-bearing collateral, including per-market reward-token accounting and supplier pro-rata allocation. [16](#0-15)  If rewards are intentionally unsupported, prevent reward-bearing LP tokens from being listed or explicitly account for pushed rewards; otherwise add a token-address-aware rescue/distribution path rather than relying on `claim_revenue`, which can only move internally tracked revenue in the market asset. [17](#0-16) [13](#0-12) 

### Proof of Concept

1. Assume an Aquarius LP token `LP` is listed as collateral under `(LP_HUB_ID, LP)` and Alice holds `D` LP tokens.
2. Alice calls:

```rust
controller.supply(
    alice,
    0,
    LP_SPOKE_ID,
    vec![&env, (HubAssetKey { hub_id: LP_HUB_ID, asset: lp }, deposit)],
);
```

The controller transfers `deposit` LP tokens from Alice to the pool and credits Alice with internal supply shares. [20](#0-19) [2](#0-1) 

3. The Aquarius venue accrues a nonzero reward attributable to the pool's LP balance. If the venue requires the holder to claim, no pool entrypoint can perform that claim because outbound token logic is limited to the market's configured `asset_id`. [9](#0-8) 
4. If the venue allows a permissionless push of `R` reward tokens to the pool, `reward_token.balance(pool)` increases by `R`, but no market `cash`, supplier position, or `revenue` balance increases because unsolicited receipts are never passed through `credit_cash` or `accrue_revenue`. [14](#0-13) [21](#0-20) 
5. Alice's subsequent `withdraw` can only burn her supply shares and withdraw the LP market asset; calling `claim_revenue` cannot specify the reward token or a supplier recipient and pays only claimable protocol revenue to the accumulator path. [22](#0-21) [23](#0-22)
