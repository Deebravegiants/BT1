### Title
Integer-division-to-zero in `normalize_decimal_v2` reachable through swap-driven vault depletion causes unhandled panic in `calc_take_pnl`, freezing Deposit/Withdraw/WithdrawPnl - (File: `program/src/math.rs`, `program/src/processor.rs`)

### Summary
`Calculator::normalize_decimal_v2` performs an unguarded floor division (`val * sys_decimal_value / 10^native_decimal`) that can truncate a small, but strictly positive, raw token balance down to `0`. This normalized `0` is then fed as a divisor into `Calculator::calc_x_power`, which calls `.checked_div(current_y).unwrap()`. Any swap-driven reduction of a pool's vault balance to a small residual value can trigger this division-by-zero, causing the transaction to panic (abort) inside `calc_take_pnl`, which is invoked from `process_deposit`, `process_withdraw`, and `process_withdrawpnl`. This is directly analogous to the reported TensorFlow `UnravelIndex` bug class (CWE-190: integer computation issue leading to an unguarded division by zero).

### Finding Description
`normalize_decimal_v2` computes:
```rust
pub fn normalize_decimal_v2(val: u64, native_decimal: u64, sys_decimal_value: u64) -> U128 {
    let ret_mut = (U128::from(val)).checked_mul(sys_decimal_value.into()).unwrap();
    let ret = ret_mut.checked_div(U128::from(10).checked_pow(native_decimal.into()).unwrap()).unwrap();
    ret
}
``` [1](#0-0) 

For tokens with high decimal precision (e.g. 9 decimals) and the default `sys_decimal_value` of `10^6`, any raw balance `val` such that `val * sys_decimal_value < 10^native_decimal` (e.g. `val ≤ 999`) normalizes to `0`, even though the true on-chain balance is non-zero.

This normalized value (`y1` for the coin side, `x1` for the pc side) is computed in `process_deposit`, `process_withdraw`, and `process_withdrawpnl` from the *live* vault balances (after subtracting `need_take_pnl_*`): [2](#0-1) [3](#0-2) 

It is then passed into `calc_take_pnl`, which calls `Calculator::calc_x_power`:
```rust
pub fn calc_x_power(last_x: U256, last_y: U256, current_x: U256, current_y: U256) -> U256 {
    let x_power = last_x.checked_mul(last_y).unwrap().checked_mul(current_x).unwrap()
        .checked_div(current_y).unwrap();
    x_power
}
``` [4](#0-3) 
```rust
let x2_power = Calculator::calc_x_power(
    target.calc_pnl_x.into(), target.calc_pnl_y.into(), x1, y1,
);
let x2 = x2_power.integer_sqrt();
let y2 = x2.checked_mul(y1).unwrap().checked_div(x1).unwrap();
``` [5](#0-4) 

If `y1 == 0` (coin side normalized to zero), `checked_div(current_y)` returns `None`, and `.unwrap()` panics. Symmetrically, if `x1 == 0`, the `y2` computation's `.checked_div(x1).unwrap()` panics.

The swap instructions (`process_swap_base_in`, `process_swap_base_out`, and their `_v2` variants) permit driving `total_coin_without_take_pnl` (or `total_pc_without_take_pnl`) arbitrarily low, only forbidding it from reaching exactly zero:
```rust
SwapDirection::PC2Coin => {
    if swap_amount_out >= total_coin_without_take_pnl {
        return Err(AmmError::InsufficientFunds.into());
    }
    ...
}
``` [6](#0-5) 

An unprivileged swapper can therefore drain the coin (or pc) vault down to a residual raw amount (e.g., `1`) that is non-zero on-chain but normalizes to `0` in `normalize_decimal_v2` due to the decimal/sys_decimal_value mismatch, without violating any swap invariant check.

### Impact Explanation
Once the vault balance is left in this "normalizes-to-zero" state, every subsequent call to `process_deposit`, `process_withdraw`, or `process_withdrawpnl` re-derives `x1`/`y1` from the live vault balance and re-invokes `calc_take_pnl` → `calc_x_power`, which will panic and abort the transaction. This effectively freezes LP deposits, LP withdrawals, and PnL withdrawal for the pool as long as the attacker (who can hold the bulk of the pool's coin/pc liquidity outside the pool) keeps the vault balance within the vulnerable range. This is a concrete, attacker-controllable freezing of LP funds achievable from a single class of unprivileged instructions (swap), matching the "permanent freezing of user or LP funds" impact criteria.

### Likelihood Explanation
The precondition depends on token decimals and the pool's `sys_decimal_value` (commonly `10^6`), which is common for pools pairing a 9-decimal token (e.g. wrapped SOL) with a low-decimal token, or any pool where `sys_decimal_value < 10^native_decimal`. An attacker with capital sufficient to acquire nearly all coin (or pc) liquidity in the pool (which they can subsequently reclaim by swapping back) can trigger this at will using standard `SwapBaseIn`/`SwapBaseOut` instructions, with no special privileges, making this a realistically reachable, self-inflicted DoS condition.

### Recommendation
- Replace `.unwrap()` calls in `Calculator::calc_x_power` and in the `y2` computation in `calc_take_pnl` with explicit checked-division error handling (e.g. `ok_or(AmmError::CheckedDivOverflow)?`) so that a zero divisor returns a program error instead of panicking.
- Guard `normalize_decimal_v2`/`normalize_decimal` against producing `0` for a non-zero input, or explicitly special-case `x1 == 0 || y1 == 0` in `calc_take_pnl` to skip PnL computation instead of dividing.
- Consider using ceiling division or higher intermediate precision (as already done elsewhere with `U256`) to avoid precision loss when `sys_decimal_value < 10^native_decimal`.

### Proof of Concept
1. Initialize/observe a pool where `coin_decimals = 9` and `amm.sys_decimal_value = 1_000_000` (`10^6`), so `normalize_decimal_v2(val, 9, 1_000_000)` floors to `0` whenever raw `val < 1000`.
2. Attacker repeatedly submits `SwapBaseIn`/`SwapBaseOut` (PC→Coin direction) until `total_coin_without_take_pnl` (computed in `Calculator::calc_total_without_take_pnl_no_orderbook`) is driven down to a small residual value, e.g. `1`, which is permitted because the swap check only rejects `swap_amount_out >= total_coin_without_take_pnl`, not values that leave a small positive residual.
3. Any subsequent call to `process_deposit`, `process_withdraw`, or `process_withdrawpnl` computes `y1 = Calculator::normalize_decimal_v2(total_coin_without_take_pnl, amm.coin_decimals, amm.sys_decimal_value)`, which evaluates to `0`.
4. `calc_take_pnl` calls `Calculator::calc_x_power(..., current_y = y1)`, hitting `.checked_div(current_y).unwrap()` with `current_y == 0`, causing an unhandled panic and aborting the transaction — LPs cannot withdraw and no one can deposit while the pool remains in this state.
