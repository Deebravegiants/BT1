### Title
Missing lower bound on launch-time `virtualLtReserve` lets a low-value LT permanently brick `finalizeGraduation` via UniswapV2's `MINIMUM_LIQUIDITY` floor - ([File: packages/contracts/src/Bonding.sol])

### Summary
The external report is about `socket.io-parser` failing to validate a packet's shape before it is consumed downstream, causing an uncaught `TypeError` that kills the whole server process for everyone, not just the sender. The analog here is `Bonding`'s launch/graduation pipeline: it validates the *upper* bound of the LT's `exchangeRate()`-derived `virtualLtReserve` but never validates the *lower* bound, so a token launched against an LT with a sufficiently high `exchangeRate()` can compute LP-seeding amounts so small that the mandatory `pair.mint(lpLock)` call inside `_seedDirectMint` reverts on UniswapV2's `MINIMUM_LIQUIDITY` check. Because `finalizeGraduation` is the only path out of `Lifecycle.Graduating` and its inputs are cached, immutable, and never recomputed, this is a permanent, deterministic, unrecoverable revert — a total freeze of every curve buyer's LT and of the 250M LP-reserve tokens parked on `Bonding`.

### Finding Description
At launch, `_deployAndSeed` derives the curve's virtual LT reserve from the paired LT's live `exchangeRate()` and only guards against the reserve being *too large*: [1](#0-0) 

There is no symmetric check preventing `virtualLtReserve` from being extremely small (i.e., `exchangeRate()` extremely large). `ltAddress` is only checked against `IBounceFactory.ltExists`, not against any price/amount sanity bound, and it is fully attacker/creator-selected as part of the permissionless `LaunchParams`: [2](#0-1) 

When the curve fully sells out (the supply-trigger leg of `canGraduate`), the real LT raised is pinned at `ltFromPair = 3 * virtualLtReserve` by the curve math (`K = TOTAL_SUPPLY * virtualLtReserve`, and at sellout `assetReserve = K / (TOTAL_SUPPLY - curveSupply) = 4 * virtualLtReserve`). `_prepareGraduationLiquidity` then derives `tokensForLP` proportionally to `ltFromPair`: [3](#0-2) 

Both `(tokensForLP, ltFromPair)` are frozen into `pendingGraduation` in phase 1 and consumed unmodified in phase 2: [4](#0-3) 

Phase 2's happy-path/dust-preseed regime calls `pair.mint` with exactly these frozen amounts: [5](#0-4) 

Standard UniswapV2 first-mint semantics compute `liquidity = sqrt(amount0 * amount1) - MINIMUM_LIQUIDITY` and revert (`INSUFFICIENT_LIQUIDITY_MINTED`) when the product's square root doesn't exceed the fixed `MINIMUM_LIQUIDITY` (1000). If `virtualLtReserve` is small enough that `ltFromPair` and/or `tokensForLP` round down into that dust range, this `mint` call reverts unconditionally and permanently — the amounts are pinned in phase 1 and can never be recomputed or resized. `finalizeGraduation` therefore reverts on every call, forever: [6](#0-5) 

Once a token is in `Lifecycle.Graduating`, both `buy` and `sell` are blocked (`TokenIsGraduating`), and there is no admin or user path to unwind phase 1 or resize the cached `PendingGraduation`. All of the curve-raised LT (already pulled into `Bonding` via `Router.graduate` in `_prepareGraduationLiquidity`) and the 250M `LP_RESERVE` tokens are stranded on `Bonding` permanently, and every trader who held curve tokens or contributed LT to the curve loses access to their funds/tokens with no recovery mechanism (`LPLock` and `Bonding` have no rescue path for a graduation that never completes).

This is the direct Solidity analog of the reported bug class: insufficient validation of an externally-influenced input (`exchangeRate()`/LT choice) at the boundary (launch time) is never checked against the invariant actually required downstream (UniswapV2's `MINIMUM_LIQUIDITY` floor at graduation time), producing an uncaught/unhandled revert that — unlike a normal per-caller revert — permanently kills a shared, critical code path for every participant of that token, exactly as the `socket.io-parser` packet validation gap crashed the shared server process for every connected client.

### Impact Explanation
Any curve token launched against an LT whose `exchangeRate()` is high enough to shrink `virtualLtReserve` (and consequently `ltFromPair`/`tokensForLP` at sellout) below UniswapV2's `MINIMUM_LIQUIDITY` threshold becomes permanently un-graduatable. All LT deposited by every buyer on that curve, and the 250M tokens reserved for the LP, are permanently frozen in `Bonding` with no code path to retrieve them — a full, protocol-level freezing of trader/creator/LP funds for that token. This satisfies the "permanent freezing of trader, creator, or LP funds" acceptance criterion.

### Likelihood Explanation
Reachable purely by unprivileged transactions: any address can call `Zap.createToken`/`Bonding.launch` with an arbitrary `ltAddress` (subject only to `IBounceFactory.ltExists`), and any address can then buy enough on the curve to trigger the supply-sellout graduation trigger (`canGraduate`'s `tokenBalance() == 0` leg), which is exactly one of the explicitly in-scope reachable paths. The only precondition is pairing with (or the LT later drifting to, since `exchangeRate()` is live and unbounded upward) a sufficiently high-`exchangeRate()` LT — no privileged role, oracle manipulation, or off-chain component is required.

### Recommendation
Enforce a lower bound on `virtualLtReserve` (and/or on the resulting `ltFromPair`/`tokensForLP` at graduation time) sufficient to guarantee `sqrt(tokensForLP * ltFromPair) > MINIMUM_LIQUIDITY` for every possible sellout, mirroring the existing upper-bound `ExchangeRateTooLow` check in `_deployAndSeed`. Alternatively, have `_prepareGraduationLiquidity`/`_seedDirectMint` detect the dust case ahead of the `mint` call and route to a recovery/refund flow instead of leaving `finalizeGraduation` in a permanently-reverting state.

### Proof of Concept
1. Identify or wait for a BounceTech LT whose `exchangeRate()` is large enough that `virtualLtReserve = (VIRTUAL_LIQUIDITY_USD * 1e18) / exchangeRate()` is a few wei (this passes the existing `ExchangeRateTooLow` upper-bound check, which only rejects reserves that are too large).
2. Call `Zap.createToken`/`Bonding.launch` pairing the new token with that LT; `_deployAndSeed` mints the curve with this tiny `virtualLtReserve`.
3. Buy out the entire curve supply (750M tokens) via `Zap.buy`/`Bonding.buy`, driving `IPair.tokenBalance()` to `0` and satisfying the supply-trigger leg of `canGraduate`.
4. `_executeBuy` calls `_enterGraduating` → `_prepareGraduationLiquidity`, which computes `ltFromPair = 3 * virtualLtReserve` and `tokensForLP` proportionally — both landing in UniswapV2's dust range (`sqrt(tokensForLP * ltFromPair) <= 1000`). These are cached in `pendingGraduation`.
5. Call `finalizeGraduation(tokenAddress)`. `_seedUniswapV2Direct` → `_seedDirectMint` calls `pair.mint(lpLock)`, which reverts with UniswapV2's `INSUFFICIENT_LIQUIDITY_MINTED`. `finalizeGraduation` reverts every time it is retried, since the cached `pendingGraduation` values never change — the token, and every LT/token deposited into its curve, is permanently stuck.

    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }
