### Title
Webhook shop identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies the HMAC only over the raw request body, while the `shop` (tenant) identifier used by the application handler is taken from an unauthenticated header. This breaks the identity binding: `hmac_verified_bytes == raw_body` but `tenant_identity_used_by_handler == headers["shop-domain"]`, and the latter is never part of the former.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the HMAC over that signable string via `Utils::HmacValidator.validate(request)`, and — once validated — trusts `request.shop`, taken from the `shop-domain`/`x-shopify-shop-domain` header, to build the `WebhookMetadata` handed to the app's handler: [2](#0-1) [3](#0-2) 

The header used as `shop` is read straight from HTTP request headers with no cryptographic binding to the payload: [4](#0-3) 

The HMAC secret (`api_secret_key`) is shared across every merchant/shop that has installed the same app — it is not per-shop. Consequently, a valid `(raw_body, hmac)` pair captured from any one legitimate webhook delivery (e.g., for the attacker's own shop that has installed the app) remains cryptographically valid for that body regardless of which `shop-domain` header value accompanies it. The gem's design equates "HMAC-valid webhook" with "authentic for `request.shop`," but the equality that is actually enforced is:
`HMAC(raw_body, secret) == received_hmac`
not
`HMAC(raw_body ‖ shop, secret) == received_hmac`.

This mirrors the reported bug class exactly: a field acted upon by downstream logic (here, the shop that owns/receives the webhook data) is not covered by the authenticity check (the HMAC), so the two can be forged apart from one another.

### Impact Explanation
An attacker who is an unprivileged internet user but has legitimately installed the same third-party app on their own shop (or otherwise obtained one valid `(raw_body, hmac)` pair for any shop using the app) can replay that exact body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. Because `Registry.process` only checks the HMAC of the body and does not re-derive or validate the shop against anything cryptographically tied to that body, the forged request passes validation, and the handler executes business logic (e.g., processing an order, redacting/creating data, updating internal state) attributing it to the victim shop it does not actually pertain to. This is a cross-tenant integrity/confidentiality issue: data or actions intended for one tenant can be attributed to another tenant purely by altering an unauthenticated header, without needing the app's access token, refresh token, or `client_secret`.

### Likelihood Explanation
Likelihood is moderate-to-high in multi-tenant apps built on this gem: the attacker only needs to be a legitimate (even trial) installer of the target app to obtain one valid signed webhook body/HMAC pair, then can forge the header for any other shop name — no secrets, no privileged access, and no need to break HMAC/SHA-256 are required. The forgery works because the identity check (`shop`) is decoupled from the integrity check (`hmac` over `raw_body`).

### Recommendation
Bind the tenant identity into what is authenticated. Options:
- Include `shop-domain` in the HMAC-signed payload the gem verifies (i.e., change `to_signable_string` to incorporate the shop header alongside the body when computing/verifying the signature), matching Shopify's documented webhook verification, or
- Cross-check `request.shop` against a shop the app already has a stored/active session/installation for before dispatching to the handler, rejecting requests for shops unknown to the app instance, and
- Document/require that webhook handlers must not trust `shop` as tenant-authoritative unless it is independently verified against installed-shop records.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook (e.g., `orders/create`), capturing the exact `raw_body` and the `x-shopify-hmac-sha256` header Shopify sent — both valid under the app's shared `api_secret_key`.
2. Attacker resends the same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (a shop that also has the app installed).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `OpenSSL::HMAC.hexdigest(sha256, secret, raw_body)` — this still matches, since the body is unchanged: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"`, even though the payload actually originated from `attacker-shop.myshopify.com`'s webhook — cross-tenant data/action confusion, as confirmed by the handler wiring in tests: [6](#0-5)

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
