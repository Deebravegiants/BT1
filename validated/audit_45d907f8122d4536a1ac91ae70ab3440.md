### Title
Unprivileged direct LT donation to `Bonding` corrupts `protectedLT` accounting, permanently freezing curve-raised LT and starving the hostile-preseed rebalance budget - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.finalizeGraduation` distinguishes "this graduation's raised LT" from "everything else currently sitting in `Bonding`" using a single undifferentiated balance heuristic (`ltBalance - p.ltFromPair`). Any unprivileged wallet can inflate that "everything else" bucket simply by calling `IERC20(lt).transfer(address(bonding), amount)` directly on the reserve-asset LT. The contract has no way to tell that dust apart from a genuine concurrent graduation's escrowed LT, so it is permanently classified as `protectedLT` and excluded from `_sweepLTToOwner` forever — and, if the donation lands during a hostile mint-pre-seed defense, it also shrinks the corrective-swap budget (`_ltSwapInventory`), degrading the LP's opening price away from the curve-close price.

### Finding Description
`finalizeGraduation` computes:
```solidity
uint256 ltBalance = IERC20(lt).balanceOf(address(this));
uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;
``` [1](#0-0) 

The comment explicitly acknowledges this bucket is meant to protect *"a concurrent graduation on the same LT... or stray dust"* — i.e. it treats three semantically distinct "types" of LT balance (this-graduation's raised funds, another live graduation's escrowed funds, and arbitrary donated dust) as a single undifferentiated count, exactly the class of bug in the CVE report where two distinct mapping types (`GNTMAP_device_map` / `GNTMAP_host_map`) shared one type-count instead of being tracked separately, letting one type's accounting silently absorb/corrupt the other's.

Because `protectedLT` is computed purely from `balanceOf`, any wallet can inflate it at will:
```solidity
IERC20(lt).transfer(address(bonding), amount); // no auth required, LT is a normal ERC20
```
This amount becomes indistinguishable from a legitimate concurrent graduation's escrow. Two consequences follow directly from the code:

1. **Permanent freeze.** `_sweepLTToOwner(lt, protectedLT)` only sweeps balance *above* `protectedLT`:
```solidity
function _sweepLTToOwner(address lt, uint256 keep) internal {
    uint256 bal = IERC20(lt).balanceOf(address(this));
    if (bal <= keep) return;
    ...
}
``` [2](#0-1) 
The donated amount is by construction always ≤ the newly-computed `protectedLT` in every subsequent `finalizeGraduation` call on the same LT (each call re-derives `protectedLT` as "balance minus my own `ltFromPair`", and the donation is never anyone's `ltFromPair`), so it is never swept. There is no other function in `Bonding` that removes stray LT from the contract — `_sweepLTToOwner` is only ever invoked from inside `finalizeGraduation`, and `Router.graduate`/`_pairRebalance`/`_routerDepositAndDispose` only move exactly the cached, per-token amounts. The donated LT (which can include real curve-raised trader funds if it lands as unswept rebalance residue from a *previous* graduation, see next point) is stuck indefinitely.

2. **Degraded LP price during the hostile-preseed defense.** The Regime-3 rebalance budget is:
```solidity
maxSwap: _swapBudget(_ltSwapInventory(lt, protectedLT))
...
function _ltSwapInventory(address lt, uint256 protectedLT) internal view returns (uint256) {
    uint256 bal = IERC20(lt).balanceOf(address(this));
    return bal > protectedLT ? bal - protectedLT : 0;
}
``` [3](#0-2) 
An attacker who times a direct LT donation to `Bonding` to coincide with a token's Phase-2 `finalizeGraduation` (while simultaneously front-running with a hostile `pair.mint` pre-seed, as documented in `AGENTS.md`'s "HyperSwap Pre-Seed Defense" section) shrinks the corrective-swap budget available to `_pairRebalance`. A smaller budget means the swap that is supposed to drive the hostile pool back to the curve-close ratio (`_noFeeSwapInput`) is capped further below what's needed, leaving the pool further from `tokensForLP / ltFromPair` when `_routerDepositAndDispose` deposits — i.e. an LP seeded away from the curve close price, which is one of the explicitly recognized impacts for this system.

Both effects trace to the same root cause: `protectedLT` is a single balance-derived counter used to gate two logically different concerns (funds belonging to other live graduations, vs. LT that should eventually be swept as owner-bound rebalance residue), and it has no mechanism to reconcile that count against the actual set of live `pendingGraduation` entries or against a legitimate residue ledger. This mirrors XSA-224's root cause: relying on one shared count to represent two different "map types" instead of maintaining independently verifiable per-type counts.

### Impact Explanation
- Funds that should eventually be recoverable by the protocol (rebalance residue from the hostile-preseed defense, which is itself made of curve-raised trader LT that overshot the deposit) become permanently unrecoverable once even a single unrelated donation lands in `Bonding`, because every future `finalizeGraduation` on that LT re-derives the same inflated `protectedLT` and never sweeps it.
- The hostile mint-pre-seed defense (the system's own documented anti-four.meme-incident mitigation) can be partially defeated: shrinking `_ltSwapInventory`'s budget reduces how far `_pairRebalance` can correct a hostile ratio, which the contract's own invariant doc (`docs/contracts-scope.md`, Invariant #1 "Zero price gap") treats as a first-class correctness property.
- This is reachable by any unprivileged wallet with zero special role — a plain `IERC20.transfer` call to a public contract address.

### Likelihood Explanation
Medium. The freeze effect (point 1) requires no timing at all — a single stray transfer of LT into `Bonding` at any time permanently contaminates the accounting for every future graduation on that LT. The LP-price-degradation effect (point 2) additionally requires timing the donation against an in-flight hostile-preseed `finalizeGraduation`, which is a more specialized griefing scenario but costs the attacker only the price of the donated LT (which they never recover, matching the "protected" no-sweep behavior) plus gas.

### Recommendation
Replace the single `balanceOf`-derived `protectedLT` heuristic with an explicit, per-LT ledger of "amounts owed to other pending graduations" (e.g. a `mapping(address lt => uint256) outstandingGraduationEscrow` incremented in `_prepareGraduationLiquidity`/`Router.graduate` and decremented in `finalizeGraduation`), so that stray/donated LT balance is unambiguously identified and can be swept via a dedicated, always-available rescue function rather than being silently and permanently folded into "protected" funds.

### Proof of Concept
1. Launch two tokens, `TokenA` and `TokenB`, both paired against the same LT `L` (multi-LT support via `Factory`'s `ltFor` mapping).
2. Drive `TokenA` to graduation and call `Bonding.triggerGraduation(TokenA)` (Phase 1) but do **not** yet call `finalizeGraduation(TokenA)`.
3. As an unrelated wallet, call `L.transfer(address(bonding), X)` directly — any amount, no approval or role needed.
4. Call `Bonding.finalizeGraduation(TokenA)`. Observe: `ltBalance = ltFromPairA + X`; `protectedLT = X`. `_sweepLTToOwner` sweeps nothing beyond what `_seedUniswapV2Direct` consumed, so `X` remains stuck in `Bonding`.
5. Repeat step 2-4 for `TokenB` (or any future token on LT `L`) — at every subsequent `finalizeGraduation` call, `protectedLT` again equals (at least) `X`, and `X` is never swept, regardless of how many graduations occur afterward, since the heuristic has no ledger of who `X` "really" belongs to. `X` is permanently frozen in `Bonding`.
6. To additionally verify the LP-price degradation, repeat with a hostile `pair.mint` pre-seed on `TokenB`'s HyperSwap pair timed before `finalizeGraduation(TokenB)`, and diff the post-seed pool ratio against `tokensForLP/ltFromPair` with and without the attacker's donation of `X` present — the donation-present run shows a larger deviation because `_ltSwapInventory` reports a smaller `maxSwap` budget to `_pairRebalance`.

    /// @dev Send LT held by this contract above `keep` to the owner,
    ///      emitting `LTRescued`. Called at the end of
    ///      `finalizeGraduation` with `keep = protectedLT` (any escrow
    ///      that doesn't belong to this graduation), so only THIS
    ///      graduation's rebalance residue lands on the owner. No-op on
    ///      the empty-pair fast path (nothing to sweep).
    function _sweepLTToOwner(
        address lt,
        uint256 keep
    ) internal {
        uint256 bal = IERC20(lt).balanceOf(address(this));
        if (bal <= keep) return;
        uint256 amount = bal - keep;
        address recipient = owner();
        IERC20(lt).safeTransfer(recipient, amount);
        emit LTRescued(lt, recipient, amount);
    }

    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
