### Title
Webhook shop-domain header is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an incoming webhook purely from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but the HMAC signature that `HmacValidator` verifies is computed only over the raw request body. Any attacker who can obtain one valid `(body, hmac)` pair signed with the app's shared `api_secret_key` — trivially available to any merchant who has installed the app, since Shopify sends genuine webhooks to every merchant's endpoint with the same app secret — can replay that exact body/HMAC pair while substituting an arbitrary `shopify-shop-domain` header. `Utils::HmacValidator.validate` will report the request as valid, and `Webhooks::Registry.process` will hand the attacker-chosen shop to the app's handler as if the webhook genuinely originated from that shop.

### Finding Description
The binding that should hold is:
`shop_header_used_by_handler == shop_bound_into_hmac_signed_bytes`

In this gem it does not:

- `Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

- `Webhooks::Request#shop` is read straight from an attacker-controlled HTTP header, with no relationship to `to_signable_string`: [2](#0-1) 

- `Utils::HmacValidator.validate` only recomputes and compares the HMAC over `verifiable_query.to_signable_string` (i.e. the body), never touching `shop`: [3](#0-2) 

- `Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the metadata passed to the app's handler: [4](#0-3) 

Because the `api_secret_key` used to sign webhooks is shared across all shops that install a given app (it is the app's client secret, not a per-shop secret), any merchant who installs the app receives a stream of genuinely-signed `(body, hmac)` pairs for their own shop. Since the header carrying the shop identity is excluded from the signed bytes, that merchant can capture one webhook body+HMAC and resend it to the app's webhook endpoint with `shopify-shop-domain` rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds (it never inspects the header), and `Registry.process` dispatches the handler with `shop: request.shop` set to the victim's domain — a cross-tenant identity confusion entirely internal to this gem's verification logic.

This is the direct analog of the referenced report's root cause: a field that is acted upon (`_collateralToken` selecting where `amount` funds go) is not covered by the same check/guarantee that the caller believes protects the whole operation (`msg.value` sent). Here, the field acted upon (`shop`, which determines whose tenant context the payload is dispatched into) is not covered by the same HMAC guarantee that the caller (the app) believes protects the whole webhook payload.

### Impact Explanation
This allows cross-tenant access: a request whose payload/HMAC came from shop A can be relayed to make the app process it as originating from shop B. Any app whose webhook handlers key state, authorization, or data writes off `WebhookMetadata#shop` (as returned by this gem, per `handler.handle(data: WebhookMetadata.new(topic: ..., shop: request.shop, ...))`) can have another tenant's data corrupted, deleted, or overwritten by an attacker who only needs to be a legitimate installer of the same app on their own store — no access token, secret, or privileged account required. This matches the High-severity category of cross-tenant access.

### Likelihood Explanation
Likelihood is realistic though it requires the attacker to install the target app on a store they control (a normal, unprivileged action any internet user can take by installing a public app), capture one legitimate webhook delivery to their own endpoint, and replay it with a rewritten shop header against the app's public webhook endpoint. No secret material or elevated privilege is needed — only the gem's own (mis)design of `to_signable_string` excluding the shop-identifying header from the signed bytes.

### Recommendation
Bind the shop identity into the value that is HMAC-verified, or otherwise cryptographically tie the `shopify-shop-domain` header to the signed body before trusting it:
- Include the shop domain (and ideally topic/webhook-id) as part of `to_signable_string`, matching whatever Shopify actually signs, or
- After HMAC validation succeeds, independently verify the shop-domain header against an app-side registry of installed/authorized shops before dispatching to the handler, and document to consumers that `request.shop` is not covered by the HMAC and must be revalidated by the host application.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`; the app's shared `api_secret_key` is used for all installs.
2. Shopify sends the attacker a genuine webhook: body `B`, header `shopify-hmac-sha256: HMAC(secret, B)`, `shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the exact same body `B` and same `shopify-hmac-sha256` value to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) only — this matches, so validation passes: [5](#0-4) 
5. The handler is invoked with `shop: "victim-shop.myshopify.com"` even though the payload never touched that shop, giving the attacker forged webhook "evidence" attributed to the victim tenant.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
