### Title
Unprivileged attacker can execute arbitrary calls from Emporium's identity via the Emporium-Min proof path, draining Emporium's balance and standing approvals with zero accounting - (File: `contracts/CircomDataBuilder.sol`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only constrains `emporiumMessage`, `timeStamp`, and `calldataHash` — nothing about `stealthAddressStructure`, nullifiers, root hash membership, or `amountChanges`. Combined with `EmporiumUpgradeable.runAction`'s `signerAddress == address(0)` branch, which skips the EIP-712 signature check in `verifyWallet` entirely, any unprivileged EOA can submit a self-generated trivial proof and an attacker-chosen `EmporiumStack` whose `ops` execute arbitrary `call`s from Emporium's identity, with the balance-accounting loops iterating zero elements.

### Finding Description
The invariant that should hold is: *assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter`*. This is broken as follows.

`formInputForCircom` selects the minimal input set when the token array is empty: [1](#0-0) 

`formInputEmporiumMin` only feeds `emporiumMessage`, `timeStamp`, and `calldataHash` to the verifier — it proves nothing about ownership of funds, nullifiers, or the root hash, unlike `formInputNormal`/`formBasicInput` which include `rootHashHinkal`, `getSignedMessageHash`, nullifiers and out-commitments. `emporiumMessage` is just `Poseidon(messageSeed)` for a seed the attacker freely picks — a value any unprivileged actor can compute and prove knowledge of.

`performHinkalChecks` still passes for this attacker: `originalSender`/`relay` check, `getHashedCalldata` integrity check, and `dimensionsCheck` all simply require internal consistency of attacker-supplied fields (`dimensions.tokenNumber == erc20TokenAddresses.length == 0`, etc.), not proof of prior deposits: [2](#0-1) 

In `Hinkal.transact`, the min proof verifies against the appropriately-sized verifier (via `buildVerifierId`), then `_externalTransact` is invoked. Since `erc20TokenAddresses.length == 0`, no funds are pulled from Hinkal and `deltaAmountChanges` is an empty array: [3](#0-2) 

Inside `EmporiumUpgradeable.runAction`, `balancesBefore`/`balancesAfter` are computed over `circomData.erc20TokenAddresses` (empty ⇒ no-op), and `verifyWallet` is a no-op signature check when `stack.signerAddress == address(0)` (it only marks `usedMessages[emporiumMessage] = true` and returns): [4](#0-3) 

The `ops` loop then executes attacker-chosen `endpoint`/`callData`/`value` as a low-level call, with `msg.sender == Emporium` (Case 2, "Stateless Interaction"): [5](#0-4) 

Since `circomData.erc20TokenAddresses.length == 0`, the post-loop balance-accounting/UTXO-creation loop also iterates zero times, so any value moved by these ops is never checked, never charged, and never reflected in `balancesAfter`: [6](#0-5) 

Because Emporium's identity (its address) can legitimately accumulate residual ETH/ERC20 balances or hold outstanding third-party ERC20 approvals from earlier, unrelated legitimate operations (the code comment "the only case when balanceChange can be < 0, when there were some funds on emporium before the call" explicitly acknowledges Emporium is expected to carry balances across transactions), an attacker can use this unauthenticated `ops` execution to call `token.transferFrom(approver, attacker, amount)` for any allowance where Emporium is the registered spender, drain Emporium's own ETH/token balance to an attacker address, or call any other contract that trusts calls originating from Emporium's address — all while Hinkal's own final balance/slippage checks in `Hinkal.transact` are likewise skipped because `circomData.erc20TokenAddresses` is empty there too.

The "routed through HinkalWrapper" framing in the question does not actually apply: `HinkalWrapper` only wraps `prooflessDeposit`, not `transact`, so the attacker calls `Hinkal.transact` directly. This detail does not affect the validity of the underlying vulnerability.

### Impact Explanation
This allows an unprivileged attacker to execute arbitrary, unauthenticated calls from Emporium's on-chain identity, using zero balance accounting. Any funds sitting on Emporium (residual balances from prior legitimate operations, dust, or funds under a standing ERC20 approval where Emporium is the spender) can be redirected to the attacker. This is direct theft of protocol/user funds routed through Emporium — matching Critical severity ("direct theft of shielded or in-flight user funds") since Emporium routinely holds in-flight balances between the deposit and payout legs of an operation.

### Likelihood Explanation
No privileged role, no prior deposit, and no real UTXO ownership are required. The attacker only needs: (1) to generate a valid ZK proof for the trivial Min circuit, which requires only knowledge of a self-chosen `messageSeed` (fully attacker-controlled, no secret shared with anyone else), and (2) to craft an `EmporiumStack` with `signerAddress == address(0)` and arbitrary `ops`. This is repeatable in every transaction and costs only gas plus proof generation, both trivial. The bug is exploitable at any time Emporium holds any residual balance/approval, which is a normal, expected operating state per the codebase's own comments.

### Recommendation
- Do not allow the Emporium-Min path (`erc20TokenAddresses.length == 0`) to authorize execution of `stack.ops` at all, or require `stack.signerAddress != address(0)` (i.e., mandatory EIP-712 signature verification) whenever `ops.length > 0`, regardless of token array length.
- Bind `emporiumMessage`/`calldataHash` cryptographically to the actual `ops` being executed even in the Min path, so the proof cannot be trivially self-generated to authorize arbitrary calls.
- Ensure Emporium never carries a standing balance or approval across transactions, or require balance accounting (`balancesBefore`/`balancesAfter`) over the full set of tokens touched by `ops`, not just `circomData.erc20TokenAddresses`.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, and a mock ERC20.
2. Simulate a "standing approval": have a victim account call `token.approve(emporium, largeAmount)` (representing residual allowance from a prior legitimate flow), or simply fund Emporium directly with `token.transfer(emporium, amount)` to represent a residual balance.
3. As an unprivileged attacker EOA (no deposits, no UTXOs), construct `CircomData` with `externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `emporiumMessage = Poseidon(attackerChosenSeed)`, and `externalActionMetadata` encoding an `EmporiumStack{ signerAddress: address(0), ops: [{endpoint: token, invokeWallet: false, value: 0, callData: abi.encodeCall(token.transferFrom, (victim, attacker, largeAmount))}] }`.
4. Generate a locally-computed Min-circuit proof for these public inputs (`emporiumMessage`, `timeStamp`, `calldataHash`).
5. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from the attacker EOA.
6. Assert: `token.balanceOf(attacker)` increases by `largeAmount`, `token.balanceOf(victim or emporium)` decreases by `largeAmount`, while `circomData.erc20TokenAddresses.length == 0` means no slippage/balance check in `Hinkal.transact` or `EmporiumUpgradeable.runAction` ever inspected this token — i.e., assets moved != assets accounted (both sides of the equality: LHS = `largeAmount` moved via `ops`, RHS = `0` accounted in `balancesBefore`/`balancesAfter` for that token).
