### Title
Silent under-conversion of bridged token amounts when a registered ERC20's decimals are lower than the local asset's decimals - (File: modules/pallets/hyper-fungible-token/src/impls.rs)

### Summary
`convert_to_balance` and `convert_to_erc20` in `pallet-hyper-fungible-token` scale amounts between an EVM-side ERC20's `erc_decimals` and the pallet-side asset's `local_decimals` using `10u128.pow(erc_decimals.saturating_sub(local_decimals))`, applied only as a division (mint path) or multiplication (send path). `saturating_sub` silently clamps to `0` whenever `local_decimals > erc_decimals`, which drops the scaling factor entirely instead of scaling in the opposite direction.

### Finding Description
`convert_to_balance` is documented as "Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision" [1](#0-0) , and `convert_to_erc20` is the inverse, multiplying by the same `saturating_sub` exponent [2](#0-1) . This logic is correct only when `erc_decimals >= local_decimals` (as is the case for the reference `BridgeToken`, which is 18 decimals on EVM vs 12 on nexus, per its own doc comment) [3](#0-2) .

When a token is registered whose ERC20 side has *fewer* decimals than the pallet-side asset (`local_decimals > erc_decimals`), `erc_decimals.saturating_sub(local_decimals)` clamps to `0`, so `10u128.pow(0) == 1`. `convert_to_balance` then performs no division at all, and `convert_to_erc20` performs no multiplication — the raw numeric value is passed straight through unchanged instead of being scaled to line up with the target precision. This is functionally identical to the reported `USSDRebalancer` bug class: an asymmetric decimal-scaling formula that silently degenerates (there, to the wrong power of ten; here, to a no-op) for a set of valid decimal configurations, producing amounts off by orders of magnitude rather than reverting.

This conversion is used directly on the message-delivery hot path in `on_accept` (mint/transfer to beneficiary) and `on_timeout` (refund) of the ISMP module, which is reachable by any relayer delivering a proven cross-chain post request/timeout — there is no privileged actor involved in triggering the conversion itself, only in the earlier one-time configuration of `Precisions::<T>` (per-`(local_asset_id, source)` `erc_decimals`) and the local asset's own `decimals()` [4](#0-3) [5](#0-4) .

### Impact Explanation
For any registered asset pair where the local pallet asset has more decimals than its EVM ERC20 counterpart, every inbound mint/transfer via `on_accept` and every refund via `on_timeout` will credit the beneficiary with the *raw* ERC20 integer amount interpreted at the local asset's (higher) decimal precision, instead of the correctly up-scaled amount. This mints/refunds a value many orders of magnitude smaller than the amount actually escrowed/burned on the EVM side (e.g. an ERC20 with 6 decimals bridged to a local asset with 18 decimals would under-credit by 10^12x), effectively freezing the user's bridged value on this chain while the corresponding balance is locked/escrowed on the origin chain — a permanent loss/freezing-of-funds condition for the bridging user, and a protocol-level accounting break for the escrow model described in `BridgeToken.sol`'s doc comment (supply must always equal escrow) [6](#0-5) .

### Likelihood Explanation
The bug only manifests for token configurations where `local_decimals > erc_decimals` (e.g. a governance-registered custom local asset with 18 decimals paired to a 6-decimal ERC20 such as USDC on the EVM side). Whether such a configuration is actually reachable depends on `register_token`/`Precisions` setup in `lib.rs`, which was not fully verified within the tool budget available — I could not confirm whether the pallet enforces `erc_decimals >= local_decimals` at registration time. If no such validation exists, any governance-approved token registration with this decimal ordering silently triggers the bug on every subsequent mint/refund, making likelihood Medium-High once such a token is registered; if validation is enforced elsewhere, the path may be unreachable for the currently deployed `BridgeToken` but remains a latent hazard for any future token registrations using this generic pallet.

### Recommendation
Replace the single `saturating_sub`-based formula with an explicit branch that scales in the correct direction regardless of which side has more decimals, mirroring the pattern already used correctly elsewhere in the codebase (e.g. `VWAPOracle._normalizeAmount` and the SDK's `adjustDecimals`/`adjustDecimalsFloor` helpers) [7](#0-6) [8](#0-7) :
```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let scaled = if erc_decimals >= local_decimals {
        value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    };
    scaled.to_string().parse::<B>()
}
```
and symmetrically for `convert_to_erc20`. Additionally, consider rejecting/validating decimal configurations at `register_token`/`Precisions`-set time so misconfigurations fail loudly instead of silently truncating value.

### Proof of Concept
1. Governance registers a local asset `X` with `decimals() == 18` and configures `Precisions::<T>::insert(X, evm_source, 6)` (i.e., the EVM ERC20 counterpart has 6 decimals, e.g. USDC-style).
2. A user on the EVM side sends `1_000_000` raw ERC20 units (1.0 USDC, 6 decimals) via the bridge; this is escrowed on that side.
3. A relayer delivers the corresponding post request; `on_accept` computes `erc_decimals=6, local_decimals=18`, so `erc_decimals.saturating_sub(local_decimals) == 0`, and `convert_to_balance` divides by `10^0 = 1`, yielding `amount = 1_000_000` — interpreted as `1_000_000 / 10^18` of asset `X`, i.e. a dust amount instead of the intended `1_000_000 * 10^12` (1.0 token at 18 decimals) [9](#0-8) .
4. The beneficiary is credited with a value ~10^12x smaller than what was escrowed on the source chain, while the source-chain funds remain locked — a permanent value loss for the user and a broken escrow-supply invariant for the token.

export function adjustDecimals(feeInFeeToken: bigint, fromDecimals: number, toDecimals: number): bigint {
	if (fromDecimals === toDecimals) return feeInFeeToken
	if (fromDecimals < toDecimals) {
		const scaleFactor = BigInt(10 ** (toDecimals - fromDecimals))
		return feeInFeeToken * scaleFactor
	} else {
		const scaleFactor = BigInt(10 ** (fromDecimals - toDecimals))
		return (feeInFeeToken + scaleFactor - 1n) / scaleFactor
	}
}
