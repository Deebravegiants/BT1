### Title
Single global `maxOracleAge` staleness bound used for all Chainlink feeds in `SimplexPaymaster` allows severely outdated prices for short-heartbeat feeds - ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster` prices ERC-4337 gas sponsorship in stablecoins by reading two Chainlink `AggregatorV3Interface` feeds — a shared `nativeOracle` and each registered token's `tokenOracle` — and rejecting any price whose `updatedAt` is older than a single, contract-wide `maxOracleAge` value [1](#0-0) . This mirrors exactly the reported bug class: one staleness threshold applied uniformly to price feeds with materially different Chainlink heartbeat intervals, rather than a per-feed/per-token threshold.

### Finding Description
`Params.maxOracleAge` is a single `uint256` bound (capped at `MAX_ORACLE_AGE = 7 days`) that governance sets once for the whole contract [2](#0-1) [3](#0-2) . It is stored as `maxOracleAge` and used identically for the native/USD feed and for every registered token's USD feed, no matter how many tokens with differing Chainlink heartbeats are added via `RegisterToken` [4](#0-3) [5](#0-4) .

The staleness check itself is in `_getOraclePrice`, invoked from `_tokenPrice` on every pricing call (both for `getTokenPrice`/`estimateTokenCost` views and, more importantly, for the actual gas-payment prefund computed during `_validatePaymasterUserOp`/`_fetchDetails`/`_prefund` on each sponsored UserOperation):
```solidity
function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
    (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();
    if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
    if (block.timestamp - updatedAt > maxOracleAge) {
        revert StaleOraclePrice(address(oracle), updatedAt);
    }
    ...
}
``` [6](#0-5) 

Because `maxOracleAge` is one number governance-configured for the entire deployment (across 7 chains: Ethereum, Arbitrum, Base, Polygon, BSC per the docs), and each token can have a differently-heartbeated Chainlink feed, the same failure modes described in the report apply directly:
- If `maxOracleAge` is set loosely enough to accommodate a long-heartbeat feed (e.g. a token feed with a 24h+ heartbeat), a short-heartbeat feed (e.g. a native asset feed like ETH/USD or BNB/USD, heartbeat ~1h) can go many hours past its expected update cadence and still be accepted as "fresh."
- Conversely, if tuned tight for a fast feed, a legitimately-updated slow-heartbeat token feed can be wrongly rejected, causing denial of sponsorship.

The contract's own test comments acknowledge chain-dependent heartbeat variance ("BSC stablecoins ~27s, Base/Ethereum stablecoins up to 24h") [7](#0-6) , but the mitigation implemented is only a single per-deployment `maxOracleAge`, not a per-token/per-oracle threshold, so the same value is applied to `nativeOracle` and to every `TokenConfig.tokenOracle` registered on that chain [8](#0-7) .

### Impact Explanation
`_tokenPrice` directly determines how much of the stablecoin is pulled from the solver's account to cover gas (`_prefund` uses the oracle-derived rate) during every sponsored `UserOperation`. If a native-asset feed with a short heartbeat is allowed to go stale up to the same bound tuned for a slow feed, a real-world price movement (as occurred with the documented 6-hour ETH/USD Chainlink delay) can cause `_tokenPrice` to compute an exchange rate significantly divorced from the true market price. Depending on the direction of the drift, this either:
- Overcharges the solver's stablecoin balance relative to the gas actually consumed (fund loss to solver), or
- Undercharges, letting a UserOperation drain more native-equivalent value from the paymaster's treasury/EntryPoint deposit than intended (fund loss to the paymaster's treasury, which recycles fees for the whole solver fleet).

This is a "Medium" severity accounting/pricing correctness bug rather than a full unauthorized-withdrawal bug — the paymaster's underlying access controls (relayer gate, permit/permit2 bounded allowances) remain intact — but it is directly reachable by any unprivileged UserOperation sender/solver, permissionlessly, without any admin or governance compromise, matching the report's "financial losses...incorrect contract executions" characterization.

### Likelihood Explanation
Likelihood is directly tied to real-world Chainlink feed behavior and is not hypothetical: the referenced 2021 6-hour ETH/USD delay is a documented precedent for exactly this drift, and any solver simply submitting normal sponsored UserOperations (the ordinary, permissionless operating mode of Simplex/SimplexPaymaster) triggers `_getOraclePrice` on every call. No attacker action or special conditions are required beyond an oracle delay coinciding with market volatility, which is a plausible, recurring real-world event rather than an edge case requiring active exploitation.

### Recommendation
Replace the single `maxOracleAge` field with a per-oracle (or per-token) staleness threshold, analogous to the report's recommendation:
- Add a `mapping(address => uint256) private _oracleStalenessThreshold;` (or extend `TokenConfig`/`nativeOracle` config with a `stalenessThreshold` field) set at `RegisterToken`/`UpdateParams` time based on that feed's actual Chainlink heartbeat, with a sane multiplier of headroom (e.g. heartbeat × 1.5–2).
- Update `_getOraclePrice` to look up and use the oracle-specific threshold rather than the shared `maxOracleAge`.
- Retain the existing governance-gated update path (only reachable via `onAccept` from Hyperbridge governance/authorized relayer) to configure/rotate these thresholds when feeds are registered or their heartbeats change.

### Proof of Concept
1. Governance deploys `SimplexPaymaster` with `maxOracleAge` set generously (e.g. 24h) to tolerate a slow-heartbeat token feed registered via `RegisterToken` [5](#0-4) .
2. The `nativeOracle` (e.g. BNB/USD or ETH/USD, heartbeat ~1h) experiences a delay (as historically documented for ETH/USD), and `updatedAt` lags real time by, e.g., 6–20 hours while the market price has moved materially.
3. Because `block.timestamp - updatedAt <= maxOracleAge` (24h) still holds, `_getOraclePrice` returns the stale price without reverting [6](#0-5) .
4. Any solver submits a normal sponsored `UserOperation`; `_tokenPrice`/`_prefund` computes gas cost using the stale native price, over- or under-charging the stablecoin amount relative to the real-time gas cost [8](#0-7) .
5. The existing test suite only demonstrates the single-threshold check tripping when the *same* bound is breached uniformly (`testStaleOracleReverts`), and never differentiates thresholds per feed, confirming no per-oracle protection exists [9](#0-8) .

    ///      Re-registering is also the recovery path for a misbehaving oracle.
    function _registerToken(address token, AggregatorV3Interface oracle) internal {
        if (token == address(0) || address(oracle) == address(0)) revert ZeroAddress();

        bool isNew = !tokenConfigs[token].active && address(tokenConfigs[token].tokenOracle) == address(0);

        tokenConfigs[token] = TokenConfig({
            tokenOracle: oracle,
            tokenOracleDecimals: oracle.decimals(),
            tokenDecimals: IERC20Metadata(token).decimals(),
            active: true
        });

        if (isNew) {
            registeredTokens.push(token);
        }

        emit TokenRegistered(token, address(oracle));
    }

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
