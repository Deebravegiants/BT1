### Title
Simplex solver prices Uniswap V4-funded pairs off the raw spot tick, letting a flashloan-manipulated pool drain the solver's inventory - ([File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4LiquidityState.ts])

### Summary
Simplex (Hyperbridge's reference intent-gateway filler) can price a curveless trading pair directly from a Uniswap V4 pool's instantaneous `slot0` price instead of a curve, and the only manipulation defense is an optional static `referencePrice`/`maxDeviationBps` guard the operator may or may not configure. This mirrors the C4 finding on `VaderPoolV2`: an unprivileged actor can flashloan-manipulate the pool's spot price, get the solver to fill an intent order at the distorted rate, and extract solver-held assets, then reverse the manipulation.

### Finding Description
For pairs without `bidPriceCurve`/`askPriceCurve`, Simplex derives the fill rate from the live Uniswap V4 pool state rather than a curve: `resolveLegRates` → `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd`, which returns the raw mid-price computed from `sqrtPriceX96` read via `StateView.getSlot0` [1](#0-0) . The same live `slot0` read (`sqrtPriceX96`, `tick`) feeds both the position hydration/refresh path used to size LP withdrawals [2](#0-1)  and the pool object used for quoting in the mainnet test harness [3](#0-2) .

Per the docs, this "yields a single price used in both directions" and "trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote" [4](#0-3) . The only mitigation is an operator-optional, static deviation check: `referencePrice` + `maxDeviationBps`, which rejects a fill only if the quote "drifts more than `maxDeviationBps`" from a fixed reference — and the two fields "must be set together; omit both to leave the chain unguarded" [5](#0-4) . There is no TWAP, no manipulation-resistant oracle, and — per the internal AI flow notes — "no size or impact term... `checkPriceGuard` is the only defense on this path, and it checks deviation from a static reference, not execution cost" [6](#0-5) .

This is structurally identical to the reported `VaderPoolV2` bug class: a contract/service prices a swap/mint/redeem operation off manipulable, single-block reserve state (`sqrtPriceX96`/tick) rather than a time-weighted or externally-anchored price. Just as an attacker flashloan-skewed `VaderPoolV2`'s reserves to mint synths cheaply and burn them back at a favorable rate, an attacker can flashloan-swap against the same Uniswap V4 pool the solver reads, momentarily pushing its tick far from fair value, then place/fill an intent order at that instant so the solver computes `computeDirectPoolPriceUsd` from the skewed tick and hands over an inflated amount of the exotic (or stable) token relative to what the order should legitimately cost — the same instantaneous-price-oracle manipulation is possible whenever `referencePrice`/`maxDeviationBps` is left unset (which the docs explicitly allow) or set loosely enough not to catch a same-block skew before the attacker reverses their manipulating swap in the same or a following block.

### Impact Explanation
A successful attack extracts solver-controlled funds (the Uniswap V4 LP inventory backing the pair, and/or the solver's wallet balance used to fill the fraudulently favorable order) at effectively the cost of gas and swap fees for the flashloan round-trip, directly analogous to the theft of `nativeAsset` from `VaderPoolV2`. Because the solver is a first-class actor filling real cross-chain/same-chain `IntentGatewayV2` orders, this is concrete theft of funds from a component reachable by an unprivileged order placer/attacker, not merely griefing.

### Likelihood Explanation
Likelihood is contingent on deployment configuration: an operator that configures `referencePrice`/`maxDeviationBps` narrowly reduces exposure, but the documentation explicitly presents "unguarded" (both fields omitted) as a supported, valid configuration, and even with the guard set, the check is a static-deviation bound rather than a TWAP or execution-cost-aware check, so a same-block flashloan skew within the configured tolerance — or against an unguarded pair — still passes. Any Uniswap V4 pool with modest liquidity is flashloan-manipulable within one transaction, so the precondition (a pool the solver trusts for pricing) is met by design for every venue-priced pair.

### Recommendation
Do not derive fill prices for venue-priced pairs from the pool's instantaneous `slot0`/current tick. Use a manipulation-resistant reference such as a TWAP over a sufficiently long window, a Chainlink/other external oracle, or require the static `referencePrice`/`maxDeviationBps` guard to be mandatory (not optional) with a tight enough deviation bound and a same-block/flashloan detection (e.g., rejecting fills when the pool's price changed materially since the previous block). Additionally, apply an execution-cost/size-impact term to the quote so a large flashloan swap that moves the tick also increases the quoted cost, rather than only checking deviation from a stale static reference.

### Proof of Concept
1. Attacker identifies a Simplex-configured pair priced purely from a Uniswap V4 position (no `bidPriceCurve`/`askPriceCurve`), per `docs/content/developers/evm/simplex/pricing.mdx` "Pool-Based Pricing" section, ideally one where `[vault.uniswapV4]` omits `referencePrice`/`maxDeviationBps` (an explicitly supported "unguarded" configuration).
2. Attacker takes a flashloan and swaps a large amount through that same Uniswap V4 pool, moving `sqrtPriceX96`/`tick` far from fair value in the direction that inflates the exotic token's USD price (or depresses it, depending on which side benefits the attacker).
3. In the same block (or before the pool reverts to equilibrium), the attacker places/fills an `IntentGatewayV2` order that this Simplex instance is eligible to price/fill for that pair. `resolveLegRates` → `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd` reads the skewed `slot0` and returns the distorted mid, and (absent or beyond a lax `checkPriceGuard`) the solver commits to filling at that rate.
4. The solver's fill delivers an inflated amount of tokens to the attacker (or accepts too little from the attacker) relative to fair value, funded from the solver's wallet and/or its Uniswap V4 LP position withdrawal.
5. Attacker reverses the initial swap within the same transaction bundle/flashloan, restoring the pool and repaying the loan, netting the mispriced fill's value minus gas and swap fees. This can be repeated on every eligible order while the pair remains configured this way.

	async refresh(): Promise<void> {
		const client = this.clientManager.getPublicClient(this.chain)
		const chainId = chainIdFromIdentifier(this.chain)

		// Group positions by poolId to avoid duplicate pool state fetches
		const poolIds = new Set(this.tokenIdToPoolId.values())

		// Fetch slot0 + liquidity for each unique pool via StateView
		const poolStateMap = new Map<string, { sqrtPriceX96: bigint; tick: number; poolLiquidity: bigint }>()

		for (const poolId of poolIds) {
			const [slot0Result, poolLiquidity] = await Promise.all([
				client.readContract({
					address: this.stateView,
					abi: UNISWAP_V4_STATE_VIEW_ABI,
					functionName: "getSlot0",
					args: [poolId as HexString],
				}) as Promise<[bigint, number, number, number]>,
				client.readContract({
					address: this.stateView,
					abi: UNISWAP_V4_STATE_VIEW_ABI,
					functionName: "getLiquidity",
					args: [poolId as HexString],
				}) as Promise<bigint>,
			])

			poolStateMap.set(poolId, {
				sqrtPriceX96: slot0Result[0],
				tick: slot0Result[1],
				poolLiquidity,
			})
		}

		// Refresh per-position liquidity and rebuild SDK Pool objects
		for (const pos of this.positions.values()) {
			const key = pos.tokenId.toString()
			const poolId = this.tokenIdToPoolId.get(key)
			const poolState = poolId ? poolStateMap.get(poolId) : undefined
			if (!poolId || !poolState) {
				throw new Error(
					`UniswapV4 refresh: missing pool state for tokenId ${key} (poolId=${poolId ?? "undefined"})`,
				)
			}

			// Read current position liquidity
			const liquidity = (await client.readContract({
				address: pos.positionManager,
				abi: UNISWAP_V4_POSITION_MANAGER_ABI,
				functionName: "getPositionLiquidity",
				args: [pos.tokenId],
			})) as bigint

			pos.liquidity = liquidity
			const prevOnChain = this.lastOnChainLiquidity.get(key) ?? liquidity
			const decrease = prevOnChain > liquidity ? prevOnChain - liquidity : 0n
			const prevConsumed = this.consumed.get(key) ?? 0n
			const newConsumed = prevConsumed > decrease ? prevConsumed - decrease : 0n
			this.consumed.set(key, newConsumed)
			this.lastOnChainLiquidity.set(key, liquidity)
			pos.remainingLiquidity = liquidity > newConsumed ? liquidity - newConsumed : 0n
			pos.sqrtPriceX96 = poolState.sqrtPriceX96
			pos.currentTick = poolState.tick

			// Build SDK Pool (without tick data provider — we only need amount calcs)
			const currency0 = currencyFromHydratedDecimals(chainId, pos.currency0, pos.decimals0)
			const currency1 = currencyFromHydratedDecimals(chainId, pos.currency1, pos.decimals1)

			const sdkPool = new V4Pool(
				currency0,
				currency1,
				pos.fee,
				pos.tickSpacing,
				pos.hooks,
				poolState.sqrtPriceX96.toString(),
				poolState.poolLiquidity.toString(),
				poolState.tick,
			)

			this.sdkPools.set(poolId, sdkPool)

## Pool-Based Pricing

When **`[vault.uniswapV4]`** lists at least one position, cross-asset pairs without curves derive bid/ask prices from **Uniswap V4 pool state** (current tick). The pool acts as the price oracle instead of a static curve. Note this yields a **single** price used in both directions — a venue-priced pair has no bid/ask spread of its own, so its margin comes from `order.fees` alone.

With Uniswap V4 positions configured, you can **omit** `bidPriceCurve` and `askPriceCurve` on the pair. Pool pricing requires the pair's `token0` to be a USD stablecoin, and same-token pairs always need their curve. The optional **`spreadBps`** field (basis points) sets the slippage tolerance for on-chain LP redemptions; defaults to `50` (0.50%).

Uniswap V4 venue pricing uses pools that pair the exotic token with **USDC or USDT** (addresses from your chain config). When multiple positions exist for the same exotic token on a chain, the most-liquid qualifying pool's price is used.

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```
