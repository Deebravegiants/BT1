The relevant staleness bug class maps to `MasterPlan::run` in `src/plans/mod.rs`, which snapshots `operator_qr_expiration_time` from `orb.config` once at loop start (and again at `do_signup` start) and threads that stale value through `scan_initial_qr_codes`, `idle_wait_for_signup_request`, and `scan_remaining_qr_codes` for the entire duration of a signup, while a concurrent background task (`config_update` in `src/brokers/observer.rs`) overwrites `orb.config` with a freshly downloaded value roughly every `CONFIG_UPDATE_INTERVAL`.

### Title
Stale `operator_qr_expiration_time` snapshot allows operator-QR authorization window to diverge from current backend policy - (File: `src/plans/mod.rs`)

### Summary
`MasterPlan::run` and `do_signup` each read `orb.config.lock().await` once and destructure `operator_qr_expiration_time` into a local `Duration` at the very start of the signup lifecycle. This locally captured value is then passed down through several async, potentially long-running functions (`scan_initial_qr_codes`, `idle_wait_for_signup_request`/`idle_scan_user_qr_code`, `scan_remaining_qr_codes`) that decide whether a previously scanned operator QR code is still "fresh enough" to skip re-verification, purely by comparing `operator_data.timestamp.elapsed()` against that captured `Duration`.

### Finding Description
`operator_qr_expiration_time` is a backend-controlled config value [1](#0-0) , downloaded from the management backend and periodically refreshed into the shared `Arc<Mutex<Config>>` by `DefaultPlan::config_update`, which runs on a fixed interval independent of any in-progress signup [2](#0-1) .

`MasterPlan::run` reads this value once per loop iteration and threads it as a plain `Duration` argument into `scan_initial_qr_codes`, `idle_wait_for_signup_request`, and (again, re-read) into `do_signup` [3](#0-2) [4](#0-3) . That value is used purely as an in-memory comparison against `operator_data.timestamp.elapsed()` to decide whether the previously validated operator QR code can be reused without a fresh backend re-verification call, in both `scan_initial_qr_codes` [5](#0-4)  and `scan_remaining_qr_codes` [6](#0-5) .

Because the comparison is done entirely on the orb using a value captured before the (potentially minutes-long, self-serve/idle-loop-driven) signup flow began, if the backend tightens `operator_qr_expiration_time` (e.g., in response to a compromised or improperly scoped operator credential) while a signup is already underway, the orb continues enforcing the old, longer expiration window for the remainder of that signup. The operator's binding to the signup (used later to build `personal_custody_package::Credentials` and tag the enrollment with `operator_qr_code`) is decided using policy that is out of date relative to what the backend currently considers valid, with no re-validation against the backend at signup completion. This mirrors the reported bug class: a decision (validity window) computed from a config snapshot that is not guaranteed to still match backend-enforced policy by the time the transaction (signup) completes.

### Impact Explanation
If an operator QR code's authorization is later revoked/shortened by the backend (config-driven), the orb-side timestamp check can continue treating that operator binding as valid for the old, longer duration, allowing a signup to complete and be attributed to an operator identity/location that the backend would no longer consider authorized at that point in time. This is a misattributed-signup / identity-binding integrity issue rather than a data-disclosure issue.

### Likelihood Explanation
`config_update` runs unconditionally on a fixed timer (`CONFIG_UPDATE_INTERVAL`) regardless of whether a signup is in progress [2](#0-1) , and self-serve/idle flows (`idle_scan_user_qr_code`, `idle_wait_for_signup_request`) can legitimately keep the same `OperatorData` alive across multiple loop iterations and config refreshes, so the window during which the stale expiration value is used is not a narrow race — it spans the operator-to-user QR gap and any self-serve idle waiting.

### Recommendation
Re-read `orb.config.lock().await.operator_qr_expiration_time` at each point where the freshness of `operator_data.timestamp` is checked, instead of threading a single value captured at the top of `MasterPlan::run`/`do_signup` through the whole signup lifecycle, so the orb always enforces the latest backend-configured expiration policy.

### Proof of Concept
1. Operator QR is scanned and validated at `T0`, `operator_data.timestamp` set to `T0` in `scan_initial_qr_codes` [7](#0-6) .
2. `MasterPlan::run`/`do_signup` capture `operator_qr_expiration_time = OLD_LONG_VALUE` from `orb.config` at signup start [8](#0-7) .
3. Backend updates config to `operator_qr_expiration_time = SHORT_VALUE`; `config_update` overwrites `orb.config` in place mid-signup [9](#0-8) .
4. At `T0 + SHORT_VALUE < elapsed < OLD_LONG_VALUE`, `scan_remaining_qr_codes` still treats `operator_data` as fresh because it compares against the stale `OLD_LONG_VALUE` captured in step 2, letting the signup proceed and be bound to that operator without re-verification [6](#0-5) .

    fn config_update(&mut self, observer: &mut Observer) -> Result<()> {
        if self.before_config_update()? {
            match observer.config_update.as_mut().map(future::FutureExt::now_or_never) {
                Some(None) => return Ok(()),
                Some(Some(result)) => result??,
                None => {}
            }
            let config = Arc::clone(&observer.config);
            let ui = observer.ui.clone();
            observer.config_update = Some(tokio::spawn(async move {
                if let Ok(new_config) = Config::download().await {
                    *config.lock().await = new_config;
                    config.lock().await.propagate_to_ui(ui.as_ref());
                }
                Ok(())
            }));
        }
        Ok(())
    }
