### Title
Excessive memory allocation via unbounded `strings.Split` on attacker-controlled JWT/Authorization header in `VerifyRequestJWT` - (File: core/utils/jwt.go)

### Summary
`splitToken`, called at the very start of `VerifyRequestJWT`, splits the raw `tokenString` on `.` with `strings.Split(tokenString, ".")` before any length, format, or signature validation occurs. `tokenString` originates directly from the client-supplied `Authorization: Bearer <token>` HTTP header, which is not subject to the gateway's JSON body `MaxRequestBytes` limiter and is bounded only by Go's default `net/http` header size limit (1 MiB). This mirrors the Fulcio `extractIssuerURL` bug (GHSA-f83f-xpx7-ffpw): an unauthenticated client can send a token consisting mostly of `.` characters to force an O(n) allocation (with `strings.Split`'s ~16-byte-per-element constant factor) before any authentication check succeeds. [1](#0-0) 

### Finding Description
`VerifyRequestJWT` is the JWT verification routine used to authenticate unprivileged, internet-facing HTTP Trigger requests: [2](#0-1) 

It is invoked from `WorkflowMetadataHandler.Authorize`, which is called by `httpTriggerHandler.authorizeRequest` with `req.Auth` as the token, prior to any signature or format validation: [3](#0-2) [4](#0-3) 

The `req.Auth` field is populated straight from the incoming HTTP `Authorization` header in the gateway's public HTTP server, with `strings.TrimPrefix(authHeader, "Bearer ")` and no length check specific to the JWT/auth token: [5](#0-4) 

Note that `MaxRequestBytesLimiter` in `handleRequest` only bounds `r.Body` (the JSON-RPC payload), not HTTP headers: [6](#0-5) 

The HTTP server is constructed without an explicit `MaxHeaderBytes`, so it inherits Go's `net/http` default limit of ~1 MiB for the entire header block: [7](#0-6) 

Consequently, an attacker can submit an `Authorization` header up to (close to) 1 MiB filled predominantly with `.` characters. `splitToken` will call `strings.Split` on the entire string before performing the `len(parts) != 3` sanity check, causing the full O(n) allocation cost (slice of substrings plus backing array) to be paid unconditionally for every unauthenticated request — exactly the allocation-amplification pattern described in CWE-405/GHSA-f83f-xpx7-ffpw.

### Impact Explanation
This is a resource-amplification (memory/CPU) issue reachable by any unauthenticated network client hitting the internet-facing HTTP Trigger gateway endpoint (`gateway_common.MethodWorkflowExecute` path), before signature verification or workflow-owner authorization takes place. Repeated requests with large, dot-heavy `Authorization` headers can be used to inflate per-request allocations and drive up gateway node memory/CPU pressure, potentially degrading availability for legitimate DON traffic. The severity is bounded relative to Fulcio's issue because the token size is capped by Go's default `MaxHeaderBytes` (~1 MiB) rather than being fully unbounded, but the allocation cost per malicious request is still incurred prior to any authentication check succeeding, and can be repeated concurrently/at high rate to amplify impact.

### Likelihood Explanation
High likelihood of exploitability: the endpoint is internet-facing, requires no prior authentication (the malicious header is precisely what is being "authenticated"), and the vulnerable `strings.Split` call is unconditionally reached on every JWT-based HTTP Trigger request before any validation succeeds. No special conditions or races are needed — a single crafted `Authorization` header per request is sufficient, and the attack can be trivially scripted at scale.

### Recommendation
- Enforce an explicit, small maximum length check on the incoming `tokenString`/`Authorization` header (e.g., reject tokens longer than a reasonable JWT bound, on the order of a few KB) before calling `splitToken`/`strings.Split`.
- Replace the unbounded `strings.Split(tokenString, ".")` with a bounded split (e.g., `strings.SplitN(tokenString, ".", 4)` and reject if more than 3 parts result) to avoid allocating proportional to the full length of an adversarial string with many delimiters.
- Consider explicitly setting `http.Server.MaxHeaderBytes` on the gateway's public HTTP server to a tighter, application-appropriate bound rather than relying on Go's 1 MiB default.

### Proof of Concept
1. Start a Chainlink gateway node with the HTTP Trigger capability configured (`workflow_metadata_handler.go` / `http_trigger_handler.go`).
2. Send a POST request to the public gateway HTTP endpoint with a valid JSON-RPC body (`method: workflow.execute` or equivalent) and an `Authorization` header such as:
   `Authorization: Bearer ` + `strings.Repeat(".", ~900_000)` (kept just under the default 1 MiB header limit).
3. The request reaches `httpServer.handleRequest` → `gateway.ProcessRequest` → `httpTriggerHandler.authorizeRequest` → `WorkflowMetadataHandler.Authorize` → `utils.VerifyRequestJWT` → `splitToken`, which executes `strings.Split` over the ~900,000-character string, allocating a slice with ~450,000 string-header elements (16 bytes each ≈ 7.2 MB) purely from the malformed-format check, before any authentication succeeds and the request is rejected.
4. Repeating this request concurrently amplifies memory/GC pressure on the gateway node with minimal attacker resource cost, consistent with the CWE-405 pattern in the referenced Fulcio advisory.

func splitToken(tokenString string) (string, string, error) {
	parts := strings.Split(tokenString, ".")
	if len(parts) != 3 {
		return "", "", errors.New("invalid JWT format: expected 3 parts")
	}
	signedString := parts[0] + "." + parts[1]
	signature := parts[2]
	return signedString, signature, nil
}
