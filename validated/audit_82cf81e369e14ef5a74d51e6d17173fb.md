### Title
Permissionless `fillOrder` lets MEV bots/block proposers front-run and steal solver fill profit - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.fillOrder` is callable by any address whenever `_params.solverSelection` is disabled (the default), just like the Rubicon `ExclusivityOverrideLib.hasFillingRights` check that treats `exclusive == address(0)` as "anyone may fill." A solver's profitable `fillOrder` transaction — with its exact `order` and `FillOptions.outputs` amounts — is fully visible in the public mempool before inclusion, letting a MEV bot or the block proposer itself copy the calldata and submit an identical (or marginally adjusted) fill first, capturing the arbitrage/spread that the honest solver computed off-chain.

### Finding Description
`fillOrder` performs the solver-authorization check only conditionally: [1](#0-0) 

When `_params.solverSelection` is `false`, there is no exclusivity/whitelist requirement analogous to Gladius's `exclusive` field — any address satisfying `order.deadline`, `options.validUntil`, and matching `outputs[i].token`/amount can call `fillOrder` and claim the escrowed input tokens plus any solver surplus, as seen in the same-chain fill logic: [2](#0-1) 

Because a solver's `fillOrder` calldata (order + exact output amounts it is willing to provide) must be broadcast as a plain transaction to be included, it sits in the public mempool where a copy-trading MEV bot or the block producer itself can extract it and resubmit an equivalent call with higher priority fee, landing first. The original solver's transaction then reverts against `_filled[commitment] != address(0)` (`Filled()`), so the honest solver loses only gas while the front-runner walks away with the escrowed input tokens/surplus that were meant to reward the solver's off-chain sourcing work.

This is structurally identical to the `ExclusivityOverrideLib.hasFillingRights` issue: `exclusive == address(0)` permits any filler, enabling risk-free MEV extraction of the legitimate filler's expected profit.

### Impact Explanation
Solvers that source liquidity and quote competitive prices off-chain bear real capital and computation cost, expecting to be compensated with escrowed input tokens (and any surplus per `surplusShareBps`). Without exclusivity, that entire economic reward can be redirected to a MEV bot or block proposer that does zero off-chain work, purely by observing and replaying pending transactions. This directly disincentivizes solver participation (a solver-liveness/griefing risk to the intents market) and results in concrete theft of the fill reward from the party that performed the service — meeting the "concrete theft ... of funds" bar, since the escrowed tokens and surplus are diverted from the intended, economically-justified recipient to an opportunistic copy-trader.

### Likelihood Explanation
`solverSelection` is opt-in governance-set parameter and defaults to permissionless fills (`_params.solverSelection == false` unless explicitly enabled); many deployments/orders will run in this default, unprotected mode. Any mempool-observing actor (public mempool, private mempool operator, or the block proposer/builder with direct block-inclusion power) can trivially replicate a pending `fillOrder` call, since `Order` and `FillOptions` are both plain calldata with no commit-reveal or exclusivity timing. This requires no special access beyond ordinary MEV infrastructure that already exists on every EVM chain Hyperbridge integrates with.

### Recommendation
When `solverSelection` is disabled, still provide an opt-in exclusivity mechanism (e.g., a short exclusive window bound to the first solver whose bid was accepted off-chain, or requiring `select()`-style commitment even outside the coprocessor auction flow) so a legitimate filler's calldata cannot be costlessly replayed by a third party. Alternatively, document/strongly recommend that all order placers enable `solverSelection` for cross-chain and higher-value same-chain swaps, since it is the only path in the current code that binds a specific address (`_select`/`SolverAccount` transient-storage binding) to the fill.

### Proof of Concept
1. Order placer creates an order with default `Params.solverSelection = false` (permissionless mode) — see `fillOrder`'s conditional check at `evm/src/apps/IntentGatewayV2.sol:464-472`.
2. Solver `A` computes a profitable output amount and broadcasts `fillOrder(order, options)` to the public mempool.
3. A MEV bot/block proposer observes the pending transaction, copies `order` and `options` verbatim (or with output amounts equal to the required minimum, still satisfying `options.outputs[i].amount == order.output.assets[i].amount`), and submits its own `fillOrder` call with higher gas price / direct block inclusion.
4. The bot's transaction lands first, setting `_filled[commitment] = botAddress` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:56`) and receiving the escrowed input tokens.
5. Solver `A`'s original transaction reverts with `Filled()` (`evm/src/apps/IntentGatewayV2.sol:462`), losing gas and the expected profit with no compensation.
