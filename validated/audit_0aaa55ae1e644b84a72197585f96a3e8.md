## Title
Relayer fee is paid unconditionally before the corresponding action's success is verified - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract::rlp_execute` flow (analogous to LiFi's `GenericSwapFacet`/`LibSwap` pattern of firing an external call and trusting its "success" without verifying the promised outcome) dispatches the relayer's compensation ("fee") as an independent NEAR transfer promise *before* the actual EOA/ERC-20 action promise is known to succeed, and never reconciles the two.

### Finding Description
In `inner_rlp_execute`, once an Ethereum-emulated transaction is parsed into an `EOABaseTokenTransfer` or `ERC20Transfer`, the code immediately fires a standalone fee-refund promise to the relayer: [1](#0-0) 

This `env::promise_batch_create` / `env::promise_batch_action_transfer` call is **not** chained via `.then()` onto the promise that actually performs the user's intended action (`ft_transfer`, the base-token `Transfer`, or the multi-step `storage_deposit` + `ft_transfer` flow built later in the same function). It is a completely separate, fire-and-forget receipt created at parse time, before the main action's promise is even constructed.

The main action's outcome is only checked afterwards in `rlp_execute_callback`, which inspects `env::promise_result(0)` and, on failure, refunds only the `caller_deposit` (the attached NEAR deposit), not the fee that was already sent to the relayer: [2](#0-1) 

Because the fee promise and the action promise are independent receipts with no data/output dependency between them, the relayer is paid regardless of whether:
- the `ft_transfer` call on the target NEP-141 contract panics (e.g., insufficient token balance, blocked account, paused contract),
- the multi-step `storage_deposit` + `ft_transfer` promise chain fails partway through (see `nep_141_storage_balance_callback`, lines 224-269 of the same file, where `action_to_promise`/`function_call` chains can fail independently of the fee promise),
- the address-check path bans the relayer (`address_check_callback`) after the fee was already dispatched.

This mirrors the LiFi finding precisely: a value-moving action is assumed to have "succeeded" and compensation/state changes are performed without checking that the actually intended transfer of tokens took place.

### Impact Explanation
A user's NEAR fee (deducted from `context.attached_deposit`/account balance) is unconditionally paid to whichever account acts as `predecessor_account_id` (the relayer) even when the corresponding ERC-20/base-token transfer the user actually signed for fails entirely. This is an unauthorized balance change: the user pays for a service (relayer compensation for successfully relaying a transfer) that was never rendered, and only the unrelated `caller_deposit` is refunded on failure — the fee itself is never recovered. A malicious or careless relayer can trigger transactions destined to fail (e.g., targeting a token contract that will reject the transfer) purely to collect the fee with no execution risk, since the fee promise is dispatched before the outcome of the real action is known.

### Likelihood Explanation
This is reachable directly from a submitted transaction: any account (relayer) calling `rlp_execute` on a deployed `WalletContract` with an RLP-encoded Ethereum transaction that has a non-zero `max_fee_per_gas`/`gas_limit` (which is attacker-controlled input translated into `tx_fee` in `internal::parse_rlp_tx_to_action`) triggers this code path. No special privileges are required — only that the relayer holds a function-call access key or is the account owner, which is the normal operating mode of this contract.

### Recommendation
Chain the fee-refund transfer to the relayer as part of the same promise chain as the main action (e.g., attach it via `.then()` after `rlp_execute_callback` confirms `PromiseResult::Successful`), or move the fee transfer entirely into `rlp_execute_callback` conditioned on the main action's `PromiseResult` being successful, mirroring how `caller_deposit` refunds are already gated on failure.

### Proof of Concept
1. Deploy a `WalletContract` and fund it with NEAR and a NEP-141 token balance sufficient to attempt (but not complete) a transfer, e.g., token contract that reverts `ft_transfer` under some condition (blocked receiver, insufficient balance after a race, or a paused contract).
2. As the relayer, submit an RLP-encoded ERC-20 `transfer(to, value)` transaction via `rlp_execute` with `gas_price * gas_limit` set to produce a non-zero `tx_fee` (see `internal::parse_rlp_tx_to_action`, lines 54-64).
3. Ensure the underlying `ft_transfer` call will fail (e.g., target contract lacks storage registration and rejects `storage_deposit`, or token balance is insufficient).
4. Observe that `env::promise_batch_action_transfer(refund_promise, *fee)` at `lib.rs:383` already sent the fee to the relayer's account as soon as `inner_rlp_execute` ran, independent of the later `rlp_execute_callback` result.
5. Confirm via `rlp_execute_callback` that `ExecuteResponse.success == false` (transfer failed) while the relayer's account balance nonetheless increased by `fee`, and only `caller_deposit` (not the fee) is returned to the caller.
