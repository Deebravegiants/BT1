### Title
Session identity is derived directly from an unauthenticated, unsigned cookie value, enabling cross-tenant session hijacking - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` and its helper `cookie_session_id` return the raw value of the `shopify_app_session` cookie as the trusted session identifier, with no cryptographic binding (no signature, no HMAC, no verification against any Shopify-issued credential). Because session IDs are deterministic strings derived only from public information (the shop's `myshopify.com` domain and, for online sessions, the numeric user id), any party who can set this cookie value in a victim's browser (or simply supply it directly to an app that reads cookies from non-browser channels) can make the host application resolve and use another merchant's stored session/access token.

### Finding Description
`SessionUtils.cookie_session_id` trusts the cookie verbatim: [1](#0-0) 

This value flows straight out of `current_session_id` for both online and offline sessions, and — critically — even for **embedded** apps when no `shopify_id_token` is supplied, the code falls back to the same unauthenticated cookie path: [2](#0-1) 

The session-id formats returned by the gem itself are fully deterministic and computable by anyone who knows (or guesses) the target shop's domain: [3](#0-2) 

`offline_session_id(shop)` returns `"offline_#{shop}"`, and `jwt_session_id(shop, user_id)` returns `"#{shop}_#{user_id}"`. Neither value contains any secret material — the `shop` domain is by definition public (it is the merchant's own storefront address), and it is also the exact value the gem itself writes into the cookie after a legitimate OAuth flow completes: [4](#0-3) 

Because the cookie's value *is* the session id (not a random opaque token bound to the id via HMAC), and `cookie_session_id` performs no verification, this breaks the identity binding: `session id trusted by the app` ≠ `session id actually authenticated for this browser/tenant`. An attacker who can set (or fixate) this cookie to a value of the form `offline_<target-shop>.myshopify.com` — for example via cookie injection, subdomain cookie tossing, response header injection elsewhere in the stack, or simply because the host app also accepts session ids from non-cookie sources (e.g. API clients, mobile bridges) — will cause `current_session_id` to return the target shop's real session id. If the host application looks up its session store (as documented: "Store the Session object... This session object could be retrieved later to make authenticated API requests") using this id, the attacker's request is serviced using the **victim shop's access token**, i.e., cross-tenant access to that merchant's Shopify Admin API credentials.

This differs materially from every other identity check in the gem, all of which do bind the value to a cryptographic secret:
- OAuth callback `shop`/`state`/`code` are all covered by the `AuthQuery` HMAC signable string: [5](#0-4) 
- The session-token (JWT) path validates signature and binds `aud`/`shop`/`sub` cryptographically before deriving a session id: [6](#0-5) 

Only the cookie fallback path skips this binding entirely.

### Impact Explanation
This falls under session fixation / cross-tenant access to another merchant's access token, since a forged or fixated cookie causes the host application to resolve and use a different shop's stored `ShopifyAPI::Auth::Session` (and its access token) than the one the actual caller is entitled to.

### Likelihood Explanation
Exploitation requires the attacker to control or predict the cookie value presented to `current_session_id`. This is realistic in several scenarios documented as supported by the gem itself: non-embedded apps rely on cookies exclusively (`docs/getting_started.md` lines 47–52), and embedded apps fall back to cookies whenever no `shopify_id_token` is passed. No secret (`api_secret_key`, access token, etc.) is needed by the attacker — only the target shop's public `myshopify.com` domain, which the format `offline_#{shop}` or `#{shop}_#{user_id}` requires.

### Recommendation
Do not treat the raw cookie value as a trusted session identifier. Store a random opaque token in the cookie and bind it to the real session id via a server-side lookup, or protect the cookie value with an HMAC (signed using `Context.api_secret_key`) that `cookie_session_id` verifies before returning it — mirroring the HMAC/JWT verification already used for OAuth callbacks and session tokens elsewhere in the gem.

### Proof of Concept
1. Attacker learns (or already knows, since it's public) the victim's shop domain: `victim-shop.myshopify.com`.
2. Attacker computes the deterministic offline session id per the gem's own formula: `offline_victim-shop.myshopify.com` (see `lib/shopify_api/utils/session_utils.rb:63-66`).
3. Attacker sets the `shopify_app_session` cookie to this value on their own request to the host application (via cookie injection/fixation, or any interface accepting this cookie/parameter directly).
4. The host application calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` unverified (`lib/shopify_api/utils/session_utils.rb:19-37,68-71`).
5. The host app looks up its session store with this id and retrieves the victim shop's real `Session` (including access token), then services the attacker's request using the victim's Shopify Admin credentials.
