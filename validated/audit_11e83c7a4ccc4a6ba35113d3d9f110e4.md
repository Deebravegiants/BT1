### Title
Webhook shop/topic identity headers are not covered by the HMAC signature, allowing cross-tenant shop spoofing via replay - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
The gem's webhook verification (`ShopifyAPI::Utils::HmacValidator.validate`) authenticates only the raw request body of an inbound webhook. The `shop`, `topic`, `webhook_id`, and `api_version` fields — which are taken from unauthenticated HTTP headers and passed straight through to the application's handler as trusted identity data — are never included in the HMAC-signed payload. This mirrors the reported bug class: a field is acted upon (used to build `WebhookMetadata` and dispatched to the app's business logic) without being covered by the integrity check, breaking the intended binding `hmac-authenticated bytes == bytes trusted by the handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts the HMAC exclusively from the `hmac-sha256` header and defines the signable content as only the raw body: [1](#0-0) 

`Utils::HmacValidator.validate_signature` computes `HMAC-SHA256(secret, to_signable_string)` and compares it only against the body-derived signature: [2](#0-1) 

`Registry.process` then trusts `request.topic`, `request.shop`, `request.webhook_id`, and `request.api_version` — all sourced from headers that are excluded from the signable string — to build `WebhookMetadata` and dispatch it to the registered handler: [3](#0-2) [4](#0-3) 

The binding that should hold is:
`hmac_verified(raw_body) == identity_fields_trusted_by_handler(shop, topic, webhook_id)`

But the code only enforces `hmac_verified(raw_body)`, while `shop`/`topic`/`webhook_id`/`api_version` are independent, attacker-controllable header values at the HTTP layer that the gem does not bind to that body via the HMAC.

### Impact Explanation
Because `HmacValidator` never binds the `shop-domain` header to the signed content, any party capable of obtaining one valid `(raw_body, hmac)` pair — for example, a merchant who installs the app on their own shop and captures the legitimate webhook Shopify sends them (the client_secret is shared across all shops for a given app, and each shop's own inbound webhook to the app's public endpoint is trivially observable/interceptable by that shop's owner or by anyone with visibility into that HTTP request, e.g. via a shared/multi-tenant reverse proxy, logging middleware, or a compromised intermediate hop) — can replay that exact body+hmac to the app's public webhook endpoint while substituting the `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers with values belonging to a different (victim) shop. `HmacValidator.validate` will still return `true` (it re-validates only the body), and `Registry.process` will construct a `WebhookMetadata` claiming the data belongs to the victim shop, causing the host application's handler to act on attacker-controlled data under another tenant's identity — a cross-tenant data confusion/injection primitive.

This satisfies the Critical bar of "cross-tenant access": the app is made to process and potentially persist or act upon data as if it originated from a different merchant's shop, without the attacker needing that shop's access token or the app's `client_secret`.

### Likelihood Explanation
Medium-to-High. Requires: (1) the ability to install the app on at least one shop (or otherwise obtain a single valid webhook body+HMAC pair from Shopify for the correct topic), and (2) network-level ability to POST to the app's public webhook endpoint with custom headers, which is trivial since webhook endpoints are typically public unauthenticated URLs by design. No possession of the app's `client_secret` or any merchant's access token is required — only observation of one legitimately delivered webhook, since the `shop`, `topic`, and `webhook_id` headers are entirely decoupled from the signed payload.

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed payload (or otherwise cryptographically bind them to the body), so that `HmacValidator` fails if any of these fields are altered relative to what Shopify actually signed. At minimum, document and encourage callers to independently verify that `request.shop` matches an expected/registered shop for the session context before trusting `WebhookMetadata`, and consider adding a canonical signable string that concatenates body + shop + topic + webhook_id prior to HMAC computation.

### Proof of Concept
1. Install the target app on shop `attacker-shop.myshopify.com`. Configure a webhook subscription for topic `orders/create`.
2. Trigger an event in `attacker-shop` so Shopify sends a legitimate webhook POST to the app's public endpoint. Capture the full raw body and the `x-shopify-hmac-sha256` header value (e.g., via a shared logging proxy, browser dev tunnel, or by controlling the receiving infrastructure since it is the attacker's own shop's traffic to a shared endpoint).
3. Replay the exact same POST body and `x-shopify-hmac-sha256` value to the same webhook endpoint, but change:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-webhook-id: <arbitrary>`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`: [5](#0-4) 
   Since `HmacValidator.validate_signature` only hashes `request.to_signable_string` (the raw body) — see [6](#0-5)  — the validation succeeds despite the shop header being forged.
5. The handler registered for `orders/create` receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and processes/stores the attacker's order body under the victim shop's identity, demonstrating cross-tenant data confusion.
