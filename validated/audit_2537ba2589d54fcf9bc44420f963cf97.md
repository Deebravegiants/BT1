### Title
Webhook shop-domain identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then passes the unauthenticated `shopify-shop-domain` header straight to the app's handler as the tenant identity. The HMAC never covers the shop identity field, so the "shop that was cryptographically authenticated" and "the shop that is used as the tenant/session key" are not the same binding.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `shop` is read directly and unauthenticated from the `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `Utils::HmacValidator.validate` computes/compares the HMAC only against `to_signable_string` (i.e., the body) [3](#0-2) . `Registry.process` uses this single HMAC check as the sole authenticity gate and then forwards `request.shop` (the unauthenticated header) as the trusted tenant identifier to the app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) .

Because the shop-domain header is not part of the signed content, the binding `shop_authenticated == shop_used_as_tenant_key` does not hold. Anyone who can install the public app on their own store (an "unprivileged internet user" with respect to any other merchant's data) will legitimately receive Shopify-signed webhooks (body + valid `x-shopify-hmac-sha256`) for their own shop, since Shopify signs webhook bodies with the app's single shared `client_secret` across all installs. That attacker can capture one such `raw_body`/`hmac` pair and replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body against the HMAC), and the handler receives `WebhookMetadata` claiming the payload originated from the victim shop. The gem documents that `shop` is meant to identify "The shop domain of the webhook" [5](#0-4) , and the reference app usage forwards `data.shop` directly as the tenant key for background processing [6](#0-5) , so this field is expected to be trusted for tenant routing.

### Impact Explanation
This breaks the identity binding `shop_authenticated_by_hmac == shop_used_for_tenant_data`, letting a low-privilege attacker (any user who can install the public app in their own store) inject attacker-controlled webhook payloads that are attributed to a different tenant (shop) than the one whose credentials actually produced the signature. Downstream, apps that key persistence, refunds, GDPR redaction, order processing, etc., by `data.shop` (as the gem's own documentation instructs) can have their per-tenant data poisoned/confused — a cross-tenant data-integrity/cross-tenant access issue.

### Likelihood Explanation
Moderate: exploitation requires the attacker to be able to trigger at least one legitimate webhook to their own installation (trivial for any merchant/developer who installs the app) and to be able to reach the app's webhook HTTP endpoint directly (a public endpoint by design, since Shopify webhooks are unauthenticated aside from the HMAC). No access to the app's `client_secret`, access tokens, or another tenant's credentials is required.

### Recommendation
Do not trust the `shopify-shop-domain` (and other Shopify headers such as `topic`, `api-version`, `webhook-id`) unless they are cryptographically bound to the signed payload. At minimum, applications relying on this gem should independently corroborate `request.shop` against a shop they expect/registered a webhook for; the gem itself could mitigate this by incorporating the shop domain (and other identifying headers) into `to_signable_string`, or by exposing a documented warning that `shop` is unauthenticated and must not be used as a sole tenant key without additional verification (e.g., matching against the shop for which the specific webhook topic/path was registered).

### Proof of Concept
1. Attacker installs the target public app on their own shop `attacker.myshopify.com` and lets Shopify deliver a legitimate `orders/create` webhook, capturing `raw_body` and the `x-shopify-hmac-sha256` header (both valid because Shopify signs with the app's shared `client_secret`).
2. Attacker POSTs the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC [7](#0-6)  — validation succeeds.
4. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker's own order data>, ...)` [8](#0-7) , and the app processes attacker-controlled data as belonging to `victim-shop`.
