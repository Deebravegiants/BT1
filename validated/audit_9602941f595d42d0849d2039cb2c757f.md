### Title
Webhook shop/topic identity spoofing via unsigned headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw body only, while the `shop` and `topic` values used by `ShopifyAPI::Webhooks::Registry.process` to select a handler and to identify the tenant are taken from HTTP headers that are never included in the signed material. Any actor who can obtain one genuinely-signed `(raw_body, hmac)` pair for their own shop can replay it with an arbitrary `X-Shopify-Shop-Domain` and `X-Shopify-Topic` header and have it accepted as authentic, breaking the identity binding `shop authenticated == shop used to key the tenant`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` fields are read straight from headers and are never part of the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies only that the computed HMAC over `to_signable_string` (i.e. the raw body) matches the received signature — it has no knowledge of headers: [3](#0-2) 

`Registry.process` trusts the HMAC check as proof of authenticity for the entire request, then dispatches using the unauthenticated `request.topic` and forwards the unauthenticated `request.shop` straight into the data given to the app's handler: [4](#0-3) 

Because `shop` (and `topic`) are excluded from the signed payload, the equality the gem is supposed to guarantee — "the shop/topic Shopify actually sent this webhook for" == "the shop/topic the handler receives" — no longer holds. Anyone who can capture one legitimately HMAC-signed webhook body (trivially available to any merchant who installs the app on their own store and triggers an event, since Shopify signs and delivers it to their own endpoint) can resend that exact `(body, hmac)` pair with a forged `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header pointing at a victim shop, and/or a forged `X-Shopify-Topic` selecting an arbitrary registered handler. The HMAC check still passes because only the untouched body is verified.

### Impact Explanation
This is a cross-tenant identity/authentication break: the app's own webhook handler code (built per the gem's documented `WebhookMetadata#shop` contract) will process attacker-supplied body content as if it belonged to a different, victim tenant. Depending on how the host application keys its per-shop session/data store off `WebhookMetadata#shop` (which the docs instruct developers to rely on), this enables writing/overwriting data under another merchant's tenant, or invoking sensitive topic handlers (e.g. `app/uninstalled`, `shop/redact`, `customers/redact`) against a shop the attacker does not own — all without holding any credential for the victim shop. This meets the "cross-tenant access" bar.

### Likelihood Explanation
Any unprivileged internet user who can install the target app on a shop they control (a normal, unprivileged action for public apps) can generate a validly-signed webhook, capture it, and replay it with modified `shop`/`topic` headers using a plain HTTP client — no access to `api_secret_key` or any victim credential is required.

### Recommendation
Include the header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed material, or independently bind them (e.g., require the caller to additionally supply/verify the shop the webhook is destined for against the app's own known-installed-shops list) before dispatching to handlers in `Registry.process`.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`.
2. Trigger any subscribed webhook topic (e.g. `orders/create`); Shopify delivers `raw_body` + `X-Shopify-Hmac-Sha256` computed with the app's real `client_secret` to the app's endpoint.
3. Capture that exact `(raw_body, hmac)` pair.
4. Resend the same body/hmac to the app's webhook endpoint, replacing `X-Shopify-Shop-Domain: attacker.myshopify.com` with `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally change `X-Shopify-Topic` to another registered topic).
5. `Utils::HmacValidator.validate` succeeds because it only checks the untouched body; `Registry.process` invokes the handler with `shop: "victim.myshopify.com"`, causing the app to act on attacker-chosen data attributed to the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
