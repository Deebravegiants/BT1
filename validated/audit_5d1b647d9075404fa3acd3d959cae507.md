### Title
Missing effective deadline and slippage protection on native-token fee swaps in dispatch/fundRequest - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all perform an on-chain Uniswap V2 swap of the caller's native token for the protocol `feeToken` whenever `msg.value > 0`, using `deadline: block.timestamp` and no independent minimum-output check. This mirrors the reported USSD issue where a swap executed with `deadline == block.timestamp` provides no real protection against delayed/sandwiched execution, since the deadline is evaluated at mining time rather than submission time.

### Finding Description
Any unprivileged caller can trigger these swaps simply by dispatching a POST/GET request or funding a request with native token value: [1](#0-0) [2](#0-1) [3](#0-2) 

In each case, `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` is called. Passing `block.timestamp` as the deadline is functionally equivalent to having *no* deadline: the Uniswap router evaluates `deadline >= block.timestamp` at the moment the transaction is actually mined, so a transaction can sit in the mempool indefinitely (e.g., during low gas-price periods) and still pass the deadline check whenever it eventually executes — exactly the anti-pattern flagged in the referenced report ("Be advised to not set the deadline equal to `block.timestamp`... that will end up disabling the protection of the deadline parameter").

The same pattern is repeated in the fee-escrow path of the intent gateway when a solver/user funds order fees with native token: [4](#0-3) 

Because the swap is `swapETHForExactTokens` (exact-output), the transaction cannot lose more than the caller's supplied `msg.value`, but a delayed/sandwiched execution can still force the swap to consume a much larger fraction of `msg.value` than intended at submission time, since there is no independent, submission-time-bound slippage/price guarantee — only whatever `msg.value` the caller happened to send. Combined with the ineffective deadline, an adversary observing a pending dispatch/fundRequest transaction in the mempool can manipulate the underlying pool price and delay/replay execution to force a worse exchange rate.

### Impact Explanation
This affects `EvmHost.dispatch()` and `fundRequest()`, which are core, permissionless entry points for dispatching any Hyperbridge message (POST/GET) and for the intent-gateway fee escrow path. A single unprivileged transaction from any user reaches this code whenever they choose to pay dispatch fees in native token. Exploitation causes the caller/protocol to receive an unfavorable, manipulated exchange rate when converting native token to `feeToken`, resulting in economic loss to the dispatching user/app (more native token consumed than the fair-market rate would require) — a concrete, though bounded (capped at `msg.value`), fund-loss vector. This is Medium severity: it does not create unbacked mint or forged messages, but it does allow value extraction from unprivileged users via a systemic, unprotected swap pattern used on every native-fee dispatch.

### Likelihood Explanation
Likelihood is moderate-to-high: this code path executes on every `dispatch()`/`fundRequest()` call paid in native token, which per the docs is explicitly supported and encouraged for "one-off transactions, user-facing apps." MEV searchers routinely watch mempools for AMM-swap transactions with weak/no deadlines to sandwich; the `deadline: block.timestamp` pattern here is a well-known anti-pattern that provides no real submission-time guarantee.

### Recommendation
- Do not default the deadline to `block.timestamp` at execution; instead, accept a caller-supplied deadline (bound to submission time) as part of `DispatchPost`/`DispatchGet`/`fundRequest` parameters, and pass that through to the router call.
- Add an explicit, caller-supplied slippage bound (e.g., a maximum acceptable native-token amount, separate from raw `msg.value`) so the swap can revert if execution price moves unfavorably beyond the caller's tolerance, rather than silently consuming more of `msg.value`.
- Apply the same fix to the analogous native-fee swap in `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder` fee-escrow logic.

### Proof of Concept
1. Alice calls `EvmHost.dispatch(DispatchPost)` with `msg.value` covering the expected native cost to buy `post.fee` amount of `feeToken`, submitting the transaction with a normal gas price.
2. A searcher observes the pending transaction in the mempool. Because `deadline` is computed as `block.timestamp` only at execution time, the searcher can delay inclusion (or manipulate the pool state immediately before inclusion) without the transaction reverting on a deadline check.
3. The searcher sandwiches the swap, moving the WETH/feeToken pool price unfavorably. `swapETHForExactTokens` still succeeds (since it only checks `amountInMaximum <= msg.value`), consuming a much larger portion of Alice's `msg.value` than the fair-market rate would require, with only the remainder refunded.
4. Alice's dispatch is still processed, but she has paid more native token than intended, with the surplus captured by the searcher — reproducing the exact economic-loss scenario described in the referenced report.
