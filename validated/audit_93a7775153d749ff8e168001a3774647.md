This confirms the vulnerability. The docs explicitly instruct developers to trust `data.shop` as "The shop domain of the webhook" `docs/usage/webhooks.md:14` and to use it directly, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)` `docs/usage/webhooks.md:26`, while the HMAC verification in `Registry.process` only validates `Utils::HmacValidator.validate(request)` `lib/shopify_api/webhooks/registry.rb:190` which in turn signs only `request.to_signable_string` (the raw body) per `lib/shopify_api/webhooks/request.rb:36-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`. The `shop` field is read straight from an HTTP header (`shopify-shop-domain`) in `lib/shopify_api/webhooks/request.rb:20-23`, which is never included in the signed payload.

### Title
Webhook `shop` identity header is not covered by HMAC verification, enabling cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#hmac`/`Registry.process` validate the webhook's HMAC against the raw request body only. The `shop` (and `topic`, `webhook_id`, `api_version`) values are parsed from HTTP headers that are excluded from the signed payload. Because the webhook signing secret (`Context.api_secret_key`) is the app's single `client_secret` shared across every installed shop (not per-shop), any shop that has installed the app can obtain a genuine `(body, hmac)` pair from a real Shopify-delivered webhook and then replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. `HmacValidator.validate` will still pass because it only recomputes the signature over the body.

### Finding Description
`Registry.process` is the sole authenticity gate for inbound webhooks: [1](#0-0) 

It calls `Utils::HmacValidator.validate(request)`: [2](#0-1) 

The signable string used to compute/verify the signature is `Request#to_signable_string`, which returns only `@raw_body`: [3](#0-2) 

Meanwhile `shop` (the tenant identity), `topic`, `webhook_id`, and `api_version` are all read from request headers that are not part of the signed material: [4](#0-3) 

The verified body and the unverified `shop` header are then bundled together and handed to the host app's handler as if both were equally trustworthy: [5](#0-4) [6](#0-5) 

This is precisely the "field acted on but not covered by the HMAC" pattern: the equality the gem is supposed to guarantee is `hmac_signed_bytes == (body, shop, topic, webhook_id)`, but in reality it only guarantees `hmac_signed_bytes == body`. The `shop` field is trusted as an authenticated tenant identifier by the gem's own documentation and sample handler code, which explicitly forwards `data.shop` to application logic as the shop domain: [7](#0-6) 

Since Shopify webhook HMACs are computed with the app's single `client_secret` (`Context.api_secret_key`), which is identical for all shops/tenants of a given app, any shop that installs the app can legitimately trigger a real webhook delivery for itself, capture the `(raw_body, hmac)` pair, and then send a forged HTTP request directly to the app's webhook endpoint with the same body/hmac but an arbitrary `x-shopify-shop-domain` header value (e.g., a victim shop). `HmacValidator.validate` recomputes the signature only from the body and passes, so `Registry.process` invokes the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain rather than the shop that actually sent the data.

### Impact Explanation
This breaks the tenant-identity binding the gem is expected to provide to consuming applications: `verified_body == attacker_controlled_shop_identity`. Any host application that follows the gem's documented pattern of trusting `data.shop` (e.g., to select which merchant's local records to update, enqueue per-shop background jobs, or attribute webhook data to a shop) can be made to process attacker-supplied body content under a victim shop's identity — a cross-tenant data injection/confusion primitive. This satisfies the Critical bar of "cross-tenant access" since the authenticity check the gem performs does not actually authenticate the tenant field it hands to the application.

### Likelihood Explanation
Exploitation requires only that the attacker control one shop that has installed the target app (an unprivileged, ordinary attacker capability for a public Shopify app) — no access to `api_secret_key`, no TLS interception, and no social engineering is needed. The attacker legitimately receives a real webhook (valid body+hmac) for their own shop, then replays it to the app's public webhook endpoint with a modified `shop-domain` header. This is a straightforward HTTP replay/tamper, not a cryptographic attack.

### Recommendation
Bind the tenant identity to the signed material: either (a) fetch or resolve the shop from a value that is itself verified (e.g., cross-check the header `shop` against a shop embedded in the signed JSON body, since Shopify webhook payloads typically include shop/store identifying fields), or (b) document/enforce that consumers must additionally verify `shop` against their own registered webhook subscriptions/known shop list before trusting it, and consider incorporating the `shop`, `topic`, and `webhook_id` headers into the value that is HMAC-verified.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`.
2. Attacker triggers a real event (e.g., `orders/create`) causing Shopify to send a legitimately signed webhook: headers include `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid_hmac_of_body>`, and some JSON `raw_body`.
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value.
4. Attacker sends a new HTTP POST directly to the app's public webhook endpoint with the identical `raw_body`/`hmac` but `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses this into a request object; `Registry.process` calls `HmacValidator.validate`, which recomputes the HMAC solely from `raw_body` and it matches, per `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`.
6. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, per `lib/shopify_api/webhooks/registry.rb:198-199`, causing the host app to process attacker body content under the victim shop's identity.
