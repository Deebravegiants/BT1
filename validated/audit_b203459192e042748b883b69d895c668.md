### Title
Unaccounted Emporium balance changes on tokens omitted from `circomData.erc20TokenAddresses` allow permanent value stranding and theft via crafted `stack.ops` - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` only snapshots and reconciles balances for tokens listed in `circomData.erc20TokenAddresses` [1](#0-0) . Any ERC20 balance change on the Emporium contract that results from executing attacker-supplied `stack.ops` on a token **not** present in that array is neither reverted nor converted into a UTXO, and (critically) is also never protected from being moved back out, because the per-token guard loop simply never runs for that token.

### Finding Description
The claimed broken equality holds: *tokens actually gained/lost by `EmporiumUpgradeable` through `stack.ops` execution* ≠ *tokens represented in `utxoSet`/protected by the balance-diff `require`* whenever a token is absent from `circomData.erc20TokenAddresses`.

Trace:
- `runAction` takes `balancesBefore`/`balancesAfter` snapshots only for `circomData.erc20TokenAddresses` [2](#0-1) [3](#0-2) , then loops only over that same array to compute `balanceChange`, revert-guard it, and call `handleOut` [4](#0-3) .
- `stack.ops` (CASE 2 "stateless interaction") executes `op.endpoint.call{value: op.value}(op.callData)` directly from `EmporiumUpgradeable`'s own address, with the only restriction being a selector block on `callHinkalWallet`/`doSendToRelay` [5](#0-4) . Nothing constrains `op.endpoint` to be a token in `circomData.erc20TokenAddresses`, and no circuit constraint ties `op.endpoint`/`op.callData` to the declared token list — for the Min circuit (`erc20TokenAddresses.length == 0`), `formInputEmporiumMin` only feeds `emporiumMessage`, `timeStamp`, `calldataHash` as public inputs [6](#0-5) ; even for non-empty lists, `MainEVMCircuit` never constrains `op.endpoint`/`op.callData` at all (out of the ZK circuit's scope) [7](#0-6) .
- Because the omitted token is never in `balancesBefore`/`balancesAfter`, the `runAction` loop and `handleOut`'s `balanceChange <= 0` short-circuit are never evaluated for it [8](#0-7) . Consequently any ERC20 that lands on the Emporium contract via `stack.ops` (e.g., a swap's output token) but is not named in `erc20TokenAddresses` is silently retained by Emporium — no UTXO minted, no revert.
- The same omitted token is symmetrically unprotected against being moved **out**: an attacker can submit an `EmporiumOperation` whose `op.callData` is a raw `IERC20.transfer(attacker, amount)` targeting any token that Emporium happens to hold (whether stranded from a prior transaction's unlisted-token gain, or simply held transiently for other reasons) while omitting that token from their own `circomData.erc20TokenAddresses`. Since that token is absent from the tracked array, the `runAction` reconciliation loop (lines 132-151) never inspects it, so the direct transfer-out is invisible to the contract's own guard and is not reverted.
- At the `Hinkal.transact` level, the top-level balance/slippage/equation checks (lines 97-146) are likewise scoped strictly to `circomData.erc20TokenAddresses`, so they provide no additional protection for tokens the caller chooses to omit [9](#0-8) .

Note on the "sweep via naming the token" mechanic described in the question: because `handleOut` acts on a *delta* (`balancesAfter[i] - balancesBefore[i]`) measured within the sweeper's own call rather than the *absolute* Emporium balance, merely listing the stranded token in a later, unrelated `transact` does not by itself cause `handleOut` to pay out the pre-existing stranded amount (the stranded balance is already baked into that caller's `balancesBefore` baseline, so `balanceChange` for it is 0 unless the caller's own ops move it). The genuinely exploitable path is the direct `op.endpoint.call` drain described above (bypassing the guard entirely by omitting the target token from the attacker's own `erc20TokenAddresses`), which achieves the same ultimate impact — theft of Emporium-held ERC20 balance with zero accounting — and does not depend on the delta mechanic at all.

### Impact Explanation
An unprivileged attacker can (a) permanently strand another depositor's value inside `EmporiumUpgradeable` by causing `stack.ops` to produce a balance gain on a token absent from `circomData.erc20TokenAddresses` (no UTXO minted, no revert — value enters Hinkal's custody unbacked by any UTXO), and (b) directly drain any ERC20 balance sitting in the Emporium contract (whether from case (a), or from any other transient holding) via a crafted stateless `EmporiumOperation` calling `transfer` on that token while omitting it from their own declared token list, bypassing every balance/slippage guard in `runAction`. This is direct theft of shielded/in-flight user funds and matches the Critical severity bar (minting-adjacent value divergence and theft of user funds not authorized by any prover). It is repeatable against any token/amount Emporium happens to hold at the time.

### Likelihood Explanation
Preconditions: attacker needs (1) a registered Emporium `externalActionId` with a verifier for the chosen `dimensions.tokenNumber` (including 0, the "Min" circuit, which is a documented supported path in `CircomDataBuilder.formInputForCircom`), (2) knowledge that Emporium currently holds a target ERC20 balance (observable on-chain), and (3) the ability to craft an `EmporiumStack`/`EmporiumOperation` with `op.endpoint = <token>`, `op.callData = transfer(attacker, amount)`. All of this is within the attacker's own control (self-generated proof, self-crafted calldata) and does not require any privileged role, the victim's keys, or a malicious relayer. Cost is a single gas-only transaction; the technique is fully repeatable.

### Recommendation
- In `EmporiumUpgradeable.runAction`, snapshot and reconcile balances for the **union** of `circomData.erc20TokenAddresses` and every token address touched by `stack.ops` (e.g., by requiring `op.endpoint` for stateless calls to be restricted to an allow-listed set of DEX/router addresses, and by tracking any token whose balance changes during execution, not just the declared set), reverting if any untracked token balance changes.
