### Title
Webhook tenant identity (`shop`, `topic`, `webhook_id`) is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates its HMAC signature over the raw body only, while the `shop`, `topic`, and `webhook_id` fields that `Registry.process` hands to the app's webhook handler are read directly from unauthenticated HTTP headers. The documented API explicitly tells developers to trust `data.shop`/`data.topic`/`data.webhook_id` from the handler payload as the tenant identity, so any request whose body+HMAC pair the attacker can obtain (e.g. from their own installation of the same app) can be replayed with an arbitrary `shop-domain` header to impersonate a different merchant to the handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read straight from HTTP headers with no cryptographic binding to that signature: [2](#0-1) .

`Registry.process` validates only that the body matches the HMAC, then immediately forwards the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` to the developer's handler as the tenant/event identity: [3](#0-2) .

This is the same bug class as the external report: a field that is acted upon (`shop`, used as the tenant key) is not covered by the value that is cryptographically verified (`raw_body` HMAC). The gem's own documentation instructs developers to trust `data.shop` as "The shop domain of the webhook" and use it directly to key application state (e.g. `shop_domain: data.shop`), reinforcing that this field is meant to be authoritative — see `docs/usage/webhooks.md` lines 12-29.

By contrast, the OAuth callback path in this same gem does bind `shop` into the signed payload: `AuthQuery#to_signable_string` includes `shop` and `state` in the HMAC-covered string [4](#0-3) , showing the gem is capable of, and elsewhere does, bind the tenant identifier into the HMAC — but the webhook path does not.

Because the `client_secret` (and therefore the HMAC key) is shared across every shop that has installed a given app, any unprivileged user who installs the app on their own store can legitimately receive a webhook delivery, capturing a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with that app's secret. They can then replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header with a victim shop's domain. `HmacValidator.validate` will report the signature as valid, since it only checks the body bytes: [5](#0-4) . The handler then executes attacker-supplied body content under the identity of a shop the attacker does not control.

### Impact Explanation
This breaks the tenant boundary the app relies on for `Registry.process`: `shop` (attacker-controlled header) ≠ `shop` (the tenant that actually owns the signed body/event). Depending on how the app's handler uses `data.shop`/`data.body` (e.g., updating order state, revoking access on `app/uninstalled`, writing metafields, billing events), this enables cross-tenant data corruption or state manipulation attributable to a merchant who never sent the request — a cross-tenant access issue as defined in scope.

### Likelihood Explanation
Requires only: (1) installing the target app for free on an attacker-controlled development/test store to legitimately capture one valid `(body, hmac)` pair signed with the shared `client_secret`, and (2) a single unauthenticated HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header. No access token, `client_secret`, or privileged account is needed — matching the "unprivileged internet user" threat model.

### Recommendation
Bind the tenant/event identity into the signature verification step rather than trusting headers alone: after HMAC validation, cross-check `shop` (and ideally `webhook_id`, to reject duplicates/replays) against the set of shops that have an active, registered webhook subscription for that `webhook_id`/topic before invoking the handler, or require the host application to perform this check and document it prominently as mandatory. At minimum, update `docs/usage/webhooks.md` to state explicitly that `data.shop` must be verified against a known, previously-authenticated shop record (not solely trusted because the HMAC on the body passed) before use in any privileged or tenant-scoped operation.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, causing the app (using this gem) to register webhooks via `Registry.register_all`.
2. Shopify delivers a legitimate webhook, e.g. `orders/create`, to the app's endpoint with headers:
   ```
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of raw body, keyed by the app's shared client_secret>
   x-shopify-shop-domain: attacker.myshopify.com
   x-shopify-webhook-id: <id>
   ```
   The attacker records the raw body and the `x-shopify-hmac-sha256` value from this delivery (they control the endpoint or a proxy in front of it).
3. Attacker POSTs the exact same raw body and `x-shopify-hmac-sha256` value to the app's public webhook route again, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` [6](#0-5) , which succeeds because it only recomputes the HMAC over the unchanged raw body.
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)` — the app now processes attacker-supplied webhook content attributed to `victim-shop.myshopify.com` [7](#0-6) .
