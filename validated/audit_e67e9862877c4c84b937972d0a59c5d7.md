### Title
Webhook `shop` (and `topic`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop` (and `topic`) values pulled from unauthenticated HTTP headers when dispatching to the app's handler. Because the signed content and the trusted identity fields are different byte ranges, any party who can produce one valid `(body, HMAC)` pair for the app's shared `api_secret_key` can relabel that payload as coming from an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers that are never part of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` (the body) and compares it against the received HMAC: [3](#0-2) 

`Registry.process` treats a passing HMAC check as authenticating the whole request, then forwards `request.shop` and `request.topic` — which were never bound into that signature — directly into the `WebhookMetadata` struct handed to the app's handler: [4](#0-3) 

`WebhookMetadata.shop` is a plain, unauthenticated `String` field: [5](#0-4) 

This is the exact bug class called out in the rules: "a field acted on but not covered by the HMAC." The equality that should hold is `shop_bound_by_signature == shop_acted_on`, but the actual state is `shop_bound_by_signature == "" (not part of to_signable_string)` while `shop_acted_on == request.shop` (attacker-controlled header). Since the app's `api_secret_key` is shared across every shop that installs the app (it is not per-tenant), any merchant who has installed the app can capture one legitimately-signed webhook delivery (body + HMAC) sent to their own shop, then replay that identical body/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) header for a different, victim shop's domain. `Utils::HmacValidator.validate` still succeeds because the signature only ever attested to the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop.

### Impact Explanation
This breaks the tenant identity binding the gem is expected to provide to consuming apps: "this webhook body is verified AND it belongs to shop X." Any host application that uses `WebhookMetadata#shop` to key its per-shop side effects (e.g., mandatory compliance topics `shop/redact`, `customers/redact`, `customers/data_request`, or ordinary business webhooks like `orders/create`, `app/uninstalled`) can be made to apply another tenant's data-deletion, deauthorization, or business logic against a shop the attacker does not control — a cross-tenant access impact, which is listed as Critical in this scan's impact taxonomy.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-owned shop to receive one legitimate webhook delivery (a standard, low-privilege step available to any merchant/developer), and (2) the ability to send an arbitrary HTTP POST with attacker-chosen headers to the app's public webhook endpoint (webhook endpoints are internet-reachable by design). No access to `api_secret_key`, tokens, or the app owner's infrastructure is needed — the attacker leverages a signature that Shopify itself computed and delivered to them for their own shop. This fits the "unprivileged internet user" threat model in scope.

### Recommendation
Bind the identity fields into the authenticated data before trusting them: either include `shop`, `topic`, and `webhook_id` in the HMAC-signed payload (matching them against `to_signable_string`), or otherwise cryptographically bind the header values to the signature before constructing `WebhookMetadata`. At minimum, `Registry.process` should not treat body-HMAC validation as authenticating header-derived fields; document this gap prominently if header binding cannot be added, since downstream apps are likely relying on `WebhookMetadata.shop` as a verified value.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook to the app's endpoint: body `B`, header `X-Shopify-Hmac-Sha256: H` (computed by Shopify over `B` using the app's `api_secret_key`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: shop/redact`.
3. Attacker captures `(B, H)` (e.g., via their own inspectable request logging middleware, request replay tooling, or their own server-side webhook consumer).
4. Attacker sends a new HTTP POST directly to the app's public webhook endpoint with the *same* body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate` succeeds because it only recomputes the signature over `B` [3](#0-2) .
6. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: "shop/redact", shop: "victim-shop.myshopify.com", ...)` [4](#0-3) , causing the app to perform shop-scoped actions (e.g., data deletion/deauthorization) against `victim-shop.myshopify.com`, a tenant the attacker does not control.
