### Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but the HMAC signature that `Registry.process` validates is computed only over the raw request body. The header identifying which tenant (shop) the webhook belongs to is never part of the signed material, so the `shop` value handed to the application's webhook handler is unauthenticated relative to the HMAC check.

### Finding Description
`Webhooks::Registry.process` gates webhook processing on a single check: [1](#0-0) 

The HMAC validity check calls `Utils::HmacValidator.validate(request)`, which recomputes an HMAC over `request.to_signable_string` and compares it to `request.hmac`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw JSON body — never the headers: [3](#0-2) 

Meanwhile `shop` (the tenant identifier ultimately passed to the app's handler via `WebhookMetadata`) is pulled straight from the `shop-domain` header with no cryptographic binding to the signature: [4](#0-3) 

`Registry.process` then forwards this unauthenticated `shop` value straight into the handler: [5](#0-4) 

The identity binding that is broken is: `hmac_signature == HMAC(secret, body)`, but the tenant-processing code effectively assumes `hmac_signature == HMAC(secret, body, shop)`. Since the app's webhook secret is shared across every shop that has the app installed, an attacker who can install the app on their own store obtains a genuinely valid `(body, hmac)` pair signed with the same secret used for every other tenant. Nothing in this gem stops that attacker from re-submitting the same `(body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value naming a victim shop, since that header was never part of the signed content.

### Impact Explanation
This breaks the tenant/authentication boundary the HMAC is supposed to enforce: the HMAC only proves "this body was sent by Shopify for some shop using this app's secret," not "for shop X." Any application built on the documented `Webhooks::Request` / `Registry.process` API that uses `WebhookMetadata#shop` to select which tenant's data to update (the sanctioned, documented usage pattern shown in `docs/usage/webhooks.md` and exercised in `test/webhooks/registry_test.rb`) can be made to apply attacker-controlled webhook payloads under a victim shop's identity — a cross-tenant data-integrity/access violation.

### Likelihood Explanation
The attacker needs their own install of the target app (freely obtainable for any public/dev app) to harvest a validly signed `(body, hmac)` pair, and needs to be able to reach the app's public webhook endpoint directly (which is, by design, a public HTTP endpoint that must accept unauthenticated inbound requests from Shopify). No access token, `client_secret`, or privileged account is required — only normal, unprivileged use of the app as an installed merchant. This is squarely in the class of "field acted on but not covered by the HMAC" identity-binding failures called out in scope.

### Recommendation
Include the `shop` domain (and ideally `topic` and `webhook-id`) in the material bound to the HMAC check, or otherwise cryptographically/contextually bind the `shop-domain` header to the specific webhook delivery (e.g., by validating it against the shop associated with the resolved `webhook_id`/subscription, or by requiring the host app to independently verify the shop is one it has an active session/install for) before invoking the handler with that shop value. At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers/receives a real webhook (e.g. `orders/create`) which is POSTed to the app's webhook endpoint with headers:
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC of body computed with the app's shared secret>`
   - body: `{"id": 1, ...attacker-controlled order payload...}`
3. Attacker replays the identical HTTP POST to the same endpoint, keeping `body` and `x-shopify-hmac-sha256` unchanged, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged header; `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(secret, body)`, per `lib/shopify_api/webhooks/request.rb:35-43` and `lib/shopify_api/utils/hmac_validator.rb:12-31`.
5. `Registry.process` invokes the host app's handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker-controlled body>, ...)`, per `lib/shopify_api/webhooks/registry.rb:196-199` — causing the app to process attacker-controlled data under the victim shop's tenant context.
