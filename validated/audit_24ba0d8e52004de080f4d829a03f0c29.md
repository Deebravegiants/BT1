### Title
Webhook `shop`/`topic` values are unauthenticated and not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify," but the HMAC check only covers the raw HTTP body. The `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's webhook handler are parsed straight from unauthenticated HTTP headers and are never bound to the signature. This mirrors the report's root cause pattern: a check is performed on one artifact (the body bytes) while the application acts on a separate, unverified value (the `shop`/`topic` headers) that a caller fully controls.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` returns only the raw body: [1](#0-0) 

All the other identity fields the handler depends on come directly from headers, with no cryptographic binding to anything: [2](#0-1) 

`Registry.process` validates the HMAC over the body via `Utils::HmacValidator.validate(request)`, and if that passes, immediately builds `WebhookMetadata` from the same unauthenticated `request.shop`/`request.topic`, and dispatches it to the app's handler: [3](#0-2) 

`HmacValidator.validate` only proves that the given `verifiable_query.to_signable_string` (the body) was signed with `Context.api_secret_key`; it says nothing about which shop or topic that body was originally sent for: [4](#0-3) 

The gem's own documentation instructs developers to trust `data.shop` and `data.topic` as the tenant/event identity for downstream processing (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), reinforcing that these fields are expected to be trustworthy once `process` succeeds: [5](#0-4) [6](#0-5) 

The identity binding that should hold is: `shop header == shop the body was actually signed for`. Because `api_secret_key` is shared by the app across every installing shop (not per-shop), any unprivileged user who installs the app on their own shop receives genuine `(raw_body, hmac)` pairs signed with that same app-wide secret. That pair can be replayed to the app's webhook endpoint with a forged `x-shopify-shop-domain`/`x-shopify-topic` header naming a different (victim) shop or a different topic — `HmacValidator.validate` still returns `true` because it never inspects those headers, and the handler receives a `WebhookMetadata` claiming to be from the victim shop.

### Impact Explanation
This breaks tenant isolation between shops that install the same app: an attacker-controlled shop can produce webhook payloads that the app's own handler will attribute to a different shop, and/or to a different topic than what Shopify actually signed. Any host application logic that uses `data.shop` to select which tenant's job queue/data to update (exactly as shown in this gem's own docs example) can be tricked into acting on behalf of another shop — a cross-tenant access condition.

### Likelihood Explanation
Any user who can install the app on their own store (an ordinary, unprivileged Shopify merchant — no special access, tokens, or leaked secrets required) can trigger genuine webhooks to obtain a valid `(raw_body, hmac)` pair, then replay it with forged headers to the app's public webhook endpoint. No knowledge of `api_secret_key` is needed since the header fields sit entirely outside the signed content.

### Recommendation
Bind the header-derived identity fields to the signed payload, or otherwise establish shop identity independent of the unauthenticated header:
- Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC validation (this deviates from Shopify's current webhook signing scheme, so at minimum the gem/docs should stop implying that `process` verifies the full "request," including `shop`/`topic`).
- Document explicitly that `data.shop`/`data.topic` are NOT covered by the HMAC and must not be used as the sole tenant/topic determinant without additional verification (e.g., cross-checking against a shop's known/registered webhook subscription, or deduplicating/validating `webhook_id` against Shopify's Admin API before trusting `shop`).
- Consider deriving the shop from something verifiable per request (e.g., correlate `webhook_id` via an authenticated API lookup) rather than trusting the raw header value implicitly.

### Proof of Concept
1. Attacker installs the target app on their own shop, `attacker.myshopify.com` (fully within Shopify's normal, unprivileged app-install flow).
2. Shopify sends the attacker's app endpoint a legitimate webhook: `raw_body = '{"id":123}'`, header `x-shopify-hmac-sha256 = H`, where `H` is a valid HMAC-SHA256 of `raw_body` using the app's `api_secret_key` (shared across all shops using the app).
3. Attacker captures `(raw_body, H)` and POSTs it directly to the app's public webhook route, but with forged headers:
   - `x-shopify-shop-domain: victim.myshopify.com`
   - `x-shopify-topic: orders/create` (or any registered topic, regardless of what topic the body was originally for)
4. The app constructs `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` and calls `ShopifyAPI::Webhooks::Registry.process(request)`.
5. `Utils::HmacValidator.validate(request)` returns `true` (line `hmac_validator.rb:13-22`) because it only checks `raw_body` against `H`, which is genuinely valid.
6. `Registry.process` builds `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: ..., ...)` (`registry.rb:198-199`) and invokes the app's handler, which — per this gem's documented pattern — treats `data.shop` as the authoritative tenant for the update, now incorrectly attributed to `victim.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
