### Title
Zero-liquidity `finalizeGraduation` call permanently bricks a graduating token because `LPLock.recordLock` reverts on `amount == 0` with no recovery path - (File: `packages/contracts/src/Bonding.sol`, `packages/contracts/src/LPLock.sol`)

### Summary
CVE-2016-7795 is a case where an unprivileged, minimal/degenerate input (a zero-length notify message) hits an unconditional `assert`/invariant check deep in a critical system path, causing a permanent hang with no recovery. The analog here is `Bonding.finalizeGraduation`, which unconditionally forwards the LP-mint result to `LPLock.recordLock`, a one-shot function that reverts on a zero amount and offers no alternate path or admin override.

### Finding Description
`finalizeGraduation` is the permissionless phase-2 step of the two-phase graduation flow. It seeds the HyperSwap V2 pair via `_seedUniswapV2Direct`, then unconditionally calls: [1](#0-0) 

into `LPLock.recordLock(tokenAddress, lpPair, liquidity)`. `LPLock.recordLock` is a one-shot lock recorder that reverts if `amount == 0`: [2](#0-1) 

If the LP-seeding step (`_seedUniswapV2Direct`, with its documented "no LP minted yet", "pure-donation pre-seed", and rebalance/direct-mint fallback regimes) ever returns `liquidity == 0` — e.g. a hostile pre-seed sized so the proportional UniswapV2 mint formula (`min(amount0*totalSupply/reserve0, amount1*totalSupply/reserve1)`) rounds down to zero, or a curve-close position where `tokensForLP`/`ltFromPair` are tiny relative to an already-inflated attacker-seeded pair — then `LPLock.recordLock` reverts with `ZeroAmount`, and `finalizeGraduation` reverts as a whole.

Because `finalizeGraduation` is the *only* path out of `Lifecycle.Graduating` (there is no owner override, no retry-with-different-amount, and `LPLock`'s locker allowlist is explicitly add-only per the code's own comments about avoiding a "one-tx kill switch"), every subsequent call to `finalizeGraduation` for that token deterministically reverts the same way: the LP-mint math is a pure function of already-frozen `PendingGraduation` state (`tokensForLP`, `ltFromPair`) and the (attacker-controlled) pair reserves at call time, so the token is permanently stuck in `Lifecycle.Graduating`. This mirrors the CVE's bug class: a boundary/edge-case unprivileged input (a message with zero length there; a liquidity mint that resolves to zero here) hits a hard assertion/require deep in a mandatory lifecycle transition and hangs it forever with no recovery.

The commentary in `Bonding.sol` around `finalizeGraduation` and `LPLock.sol`'s locker allowlist explicitly acknowledges the risk of bricking ("a live revoke would brick every in-flight `Bonding.finalizeGraduation`... no on-chain recovery"), but the code does not appear to fully rule out the zero-liquidity revert path from a hostile pre-seed.

### Impact Explanation
If triggered, this permanently freezes all curve-raised LT and the 250M tokens parked on `Bonding` for that token's graduation — the LP can never be seeded, `LPLock.recordLock` can never succeed for that token, and traders/creator lose access to the graduated token's liquidity and fee accrual entirely. This is a permanent freezing of trader/creator/LP funds, matching the required Medium/High impact bar.

### Likelihood Explanation
Likelihood depends on whether an attacker can force the UniswapV2-style mint math in `_seedUniswapV2Direct` to output exactly `0` liquidity given `Bonding`'s hardening against hostile pre-seeds (documented "Three regimes" and the rebalance/direct-mint fallbacks). I could not fully trace `_seedUniswapV2Direct`'s complete implementation within the available context to confirm whether all rounding/edge cases are closed, so this should be treated as a plausible-but-unconfirmed edge case requiring further code review (specifically the full body of `_seedUniswapV2Direct`, `_seedRebalancing`, `_pairRebalance`, and `_seedDirectMint` in `packages/contracts/src/Bonding.sol`) to establish a concrete reachable amount/reserve combination that yields `liquidity == 0`.

### Recommendation
- Add an explicit guard in `finalizeGraduation` (or inside `_seedUniswapV2Direct`) that treats a zero-liquidity mint result as an error state with a dedicated, gracefully-handled path (e.g., emit a distinguishable event and allow retry logic, or fall back to a minimum-liquidity mint) instead of relying on `LPLock.recordLock`'s `ZeroAmount` revert to fail the whole transaction.
- Consider allowing `finalizeGraduation` to be retried with re-derived reserves/skim in the zero-liquidity case, or add a narrowly-scoped recovery path (e.g., an owner-gated rescue that can only fire once `finalizeGraduation` has provably failed N times) so a hostile pre-seed cannot permanently brick a token's graduation.

```text
    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
```
