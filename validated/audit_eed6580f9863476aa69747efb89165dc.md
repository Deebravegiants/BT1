### Title
Hyper Fungible Token pallet decimal-scaling conversion breaks (unbacked mint / permanent fund loss) whenever a bridged asset's local decimals exceed its registered EVM decimals - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s `convert_to_erc20` / `convert_to_balance` helpers only ever apply `erc_decimals.saturating_sub(local_decimals)` as the scaling exponent. This is correct only when `erc_decimals >= local_decimals`. When a registered token's local (substrate) decimals are *greater* than its registered EVM decimals, `saturating_sub` clamps to `0`, so no scaling is applied at all in either direction — silently breaking the precision conversion between chains, the same class of bug as the referenced report's "assumes 18 decimals" issue in Tokemak's `LMPStrategy`.

### Finding Description
The scaling helpers are defined as: [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256, erc_decimals: u8, local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))).to_string();
	dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions use `erc_decimals.saturating_sub(local_decimals)` as the *only* scaling exponent:
- `convert_to_erc20` (outbound, called from `send`) multiplies by `10^(erc-local)` — correct when `erc_decimals >= local_decimals`, but when `local_decimals > erc_decimals` the exponent saturates to `0`, so the raw local-precision value (already scaled at `local_decimals`) is sent verbatim to the destination chain, which is a token with fewer decimals. This inflates the minted/received amount by `10^(local_decimals - erc_decimals)`.
- `convert_to_balance` (inbound, called from `on_accept`/`on_timeout`) divides by `10^(erc-local)` — correct in the same direction, but when `local_decimals > erc_decimals` it also saturates to `0`, so the raw ERC20-precision value is credited/minted as-is at the (higher) local decimal precision, deflating the received amount by the same factor.

These helpers are used directly in the pallet's fund-moving paths: [2](#0-1) [3](#0-2) [4](#0-3) 

`send` is a `Signed`-origin extrinsic — reachable by any user — and unconditionally escrows/burns `params.amount` at the asset's local decimals, then converts it with `convert_to_erc20(amount, erc_decimals, decimals)` before dispatching a `Message` to the peer EVM contract, which mints the raw `message.amount` U256 literally: [5](#0-4) 

Nothing in `register_token`/`update_token` enforces `erc_decimals >= local_decimals`; the field is set by whatever origin the runtime configures for `CreateOrigin` and is documented as an arbitrary per-chain value: [6](#0-5) 

The only test coverage exercises the safe direction (`convert_to_erc20(SEND_AMOUNT, 18, 10)`, i.e., `erc_decimals=18 > local_decimals=10`): [7](#0-6) 

The opposite, broken direction (`local_decimals > erc_decimals`) is never tested. The bridge deployment note for `BridgeToken.sol` confirms the pallet is only validated for the `erc_decimals(18) >= local_decimals(12)` direction: [8](#0-7) 

### Impact Explanation
This is a direct token-bridge mint/burn accounting break reachable from a single signed `send()` extrinsic by any unprivileged user, once a token is registered (by governance/`CreateOrigin`) with `local_decimals > erc_decimals` for some destination chain:
- Outbound: the pallet escrows/burns the correct (small) amount locally but instructs the peer EVM `HyperFungibleToken` contract to mint an amount inflated by `10^(local_decimals - erc_decimals)` — an unbacked mint on the destination chain, i.e., counterfeit tokens with no backing escrow/burn.
- Inbound: symmetric under-crediting causes users to receive a negligible fraction of tokens actually burned/escrowed on the EVM side — a permanent, irrecoverable loss of user funds.

Either direction is a High-severity fund-safety issue: it produces either an unbacked mint (protocol insolvency, drainable by any user who triggers `send`) or permanent freezing/loss of bridged value, matching the report's bug class exactly (an unenforced decimals assumption baked into arithmetic that silently mis-scales amounts).

### Likelihood Explanation
Triggering requires only that a token be registered (via the normal `register_token`/`update_token` governance flow) with `local_decimals > erc_decimals` for some chain in the config — a legitimate and plausible configuration (e.g., an 18-decimal substrate asset bridged against a 6-decimal ERC20 representation, mirroring the report's USDC/6-decimal example). Once such a config exists, exploitation needs nothing more than a normal signed `send()` call — no privileged role, no race condition, no external dependency.

### Recommendation
Replace the one-sided `saturating_sub` scaling with a bidirectional conversion that multiplies when `local_decimals < erc_decimals` and divides when `local_decimals > erc_decimals` (mirroring the existing correct half), for both `convert_to_erc20` and `convert_to_balance`. Add test coverage for the `local_decimals > erc_decimals` direction, and consider asserting/documenting the expected relationship (or supporting both directions symmetrically) at `register_token`/`update_token` time.

### Proof of Concept
1. Governance registers token `X` with `local_decimals = 18` (e.g., pallet-assets default) and `ChainConfig { decimals: erc_decimals = 6 }` for `StateMachine::Evm(dest)`, deploying/pairing a 6-decimal `HyperFungibleToken` on `dest`.
2. Any signed user calls `send(params)` with `asset_id = X`, `amount = 1_000_000_000_000_000_000` (i.e., "1.0" token at 18 decimals). The pallet burns/escrows exactly this amount locally (correct).
3. `erc_decimals.saturating_sub(local_decimals) = 6.saturating_sub(18) = 0`, so `convert_to_erc20` computes `erc20_amount = value * 10^0 = 1_000_000_000_000_000_000` — this literal `U256` is sent as `message.amount`.
4. The EVM `HyperFungibleToken.onAccept` mints `message.amount` (`1_000_000_000_000_000_000`) directly to the beneficiary. Since the token is 6-decimal, this is `10^18 / 10^6 = 10^12` times the intended `1_000_000` (i.e., "1.0" token at 6 decimals) — a `10^12`x over-mint, entirely unbacked by the single "1.0" token burned/escrowed on the substrate side.
