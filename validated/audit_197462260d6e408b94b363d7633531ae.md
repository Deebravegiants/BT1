### Title
Vault request replay guard permanently locks a client out after transient send/authorization failures - ([File: core/capabilities/vault/authorizer.go])

### Summary
The vault gateway request-authorization pipeline records a request's digest in `RequestReplayGuard` as "seen" at authorization time, *before* the underlying secrets operation (create/update/delete) is actually executed and confirmed to the client. If any step after that point fails or the response never reaches the caller, the caller cannot resubmit the same request — it will be permanently rejected as a replay, with no way to distinguish "already succeeded" from "failed after being marked seen." This mirrors the reported bug class: a boolean/state flag ("refunded"/"seen") is set irreversibly on first attempt regardless of whether the operation fully completed, permanently blocking legitimate resubmission.

### Finding Description
`authorizer.AuthorizeRequest` calls `a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt())` immediately after the allowlist/JWT auth check succeeds, and *before* `validateSecretOwnersMatchAuthorized` and before the request is ever dispatched to `handleSecretsCreate`/`handleSecretsUpdate`/`handleSecretsDelete` in `core/services/gateway/handlers/vault/handler.go`. [1](#0-0) 

`RequestReplayGuard.CheckAndRecord` records the digest unconditionally on first sight and returns `ErrRequestAlreadySeen` on every subsequent attempt with the same digest until the entry's expiry passes: [2](#0-1) 

The comment in `GatewayVaultRequestProcessor` explicitly documents that the replay guard's dedup check happens at authorization time, ahead of the actual secret operation execution: [3](#0-2) 

Because recording happens before the create/update/delete pipeline runs (owner validation, ciphertext stamping, dispatch to `handleSecretsCreate`/etc. in `handler.go`), any failure downstream of authorization — e.g., a node-side timeout, a BFT quorum failure (`errInsufficientResponsesForQuorum`/`errQuorumUnobtainable`), a dropped gateway-to-DON connection, or the gateway process losing the in-memory `activeRequest` tracking before a response is sent back — leaves the client's secret operation in an indeterminate state that can never be retried with the same request digest. The client has no way to know if the secret was actually created/updated/deleted, and cannot force a retry, because the digest is already burned in the in-memory replay guard until its expiry (tied to `authResult.ExpiresAt()`).

This is structurally identical to the reported OpenQ bug: `refunded[_depositId] = true` is set on the first `refundDeposit()` call regardless of whether the full transfer completed, so a partial/failed refund can never be retried and funds become stuck. Here, "seen[digest] = expiresAtUnix" is set on the first authorization attempt regardless of whether the underlying secret operation (which may move/expose confidential key material) actually completes, so a partially-failed vault write can never be retried by the legitimate owner until the digest naturally expires.

### Impact Explanation
An unprivileged (but authorized/allowlisted) workflow owner whose vault write request encounters any transient failure between authorization and completion (network blip, gateway restart, DON quorum failure) is denied the ability to resubmit the identical request. Practically this can:
- Leave a `CreateSecrets`/`UpdateSecrets` operation for a critical secret (e.g., an API key or private key material used by a workflow) unconfirmed/uncommitted with no retry path, forcing the owner to mint a new digest (e.g., a fresh JWT-derived nonce) — meaning the failure mode is a availability/lockout bug rather than a fund-drain, but it is a direct, unprivileged-triggerable denial of legitimate secret management operations, analogous in root cause to the funds-lock report (irreversible state flag set before operation completion is confirmed).
- Because the replay window is tied to `authResult.ExpiresAt()` (can be minutes), a caller is fully locked out of retrying that specific request for that entire window even though the operation may never have committed.

### Likelihood Explanation
This requires only a normal, unprivileged, otherwise-authorized workflow owner sending a legitimate vault request and experiencing an ordinary transient failure (gateway/DON communication issue, quorum failure) — no malicious peer, operator privilege, or mocked-only path is needed. Given `handler.go` explicitly returns `errInsufficientResponsesForQuorum`/`errQuorumUnobtainable` as expected failure modes for gateway-to-DON aggregation, this is a realistic operational occurrence, not a contrived edge case. [4](#0-3) 

### Recommendation
Move the replay-guard "commit" (`CheckAndRecord`) to occur only after the underlying secrets operation is confirmed to have fully completed (or is durably queued for guaranteed completion), rather than at authorization time. Alternatively, record a provisional/pending marker at authorization time and roll it back (release the digest) if the downstream create/update/delete pipeline fails before completion, so the client can safely retry with the same digest.

### Proof of Concept
1. A workflow owner sends a `MethodSecretsCreate` request through the gateway with digest `D` and `expiresAt = now+60s`.
2. `authorizer.AuthorizeRequest` succeeds and calls `replayGuard.CheckAndRecord(D, expiresAt)`, which records `D` as seen. [5](#0-4) 
3. After authorization, the request is dispatched to the DON nodes; before quorum is reached the gateway loses connectivity/one or more nodes fail to respond, and `errInsufficientResponsesForQuorum` is returned to the caller without the secret actually being committed.
4. The owner retries the identical request (same digest `D`) hoping to complete the operation.
5. `replayGuard.CheckAndRecord(D, ...)` returns `ErrRequestAlreadySeen` because `D` is still in the `seen` map (not expired), so the retry is rejected with "request was already authorized previously" even though the original operation never completed — the owner is locked out of legitimate resubmission until `D`'s expiry passes. [6](#0-5)

func (a *authorizer) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	authResult, err := a.authorizeRequest(ctx, req)
	if err != nil {
		return nil, err
	}
	if authResult == nil {
		err = errors.New("auth mechanism returned nil auth result")
		a.lggr.Errorw("auth mechanism returned nil auth result", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "")
		return nil, err
	}
	if err := a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt()); err != nil {
		a.lggr.Debugw("replay guard rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "", "error", err)
		return nil, err
	}
	if ownerErr := validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner()); ownerErr != nil {
		a.lggr.Errorw("owner binding rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "hasAuth", req.Auth != "", "error", ownerErr)
		return nil, ownerErr
	}
	a.lggr.Debugw("request authorized", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "")
	return authResult, nil
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
