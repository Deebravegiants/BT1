Confirmed: `WebhookMetadata.shop` is passed directly from `request.shop` (an unauthenticated header value) to every webhook handler, while HMAC validation only covers the raw body.

### Title
Webhook shop-domain identity spoofing due to HMAC not covering the `shop` field - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/utils/hmac_validator.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied `shop-domain` header straight to the host application's webhook handler as the tenant identifier. Because the `shop` header is never part of the HMAC-signed content, an attacker who possesses any one validly-signed webhook (body + HMAC) for the shared app `client_secret` can resend it to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header, and the app will process the payload as if it belonged to a different, victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC-SHA256(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` value of the `VerifiableQuery`: [1](#0-0) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only the raw request body — the `shop`, `topic`, `webhook-id`, and `api-version` headers are excluded from the signed content: [2](#0-1) 

`Registry.process` validates only that the body's HMAC is correct, then reads `request.shop` (an unauthenticated header) and forwards it as the tenant identifier to the app-supplied handler via `WebhookMetadata`: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` field with no additional binding to the HMAC-verified body: [4](#0-3) 

The identity binding that should hold is:
`shop_verified_by_hmac == shop_delivered_to_handler`

but the actual binding enforced by the code is only:
`HMAC(secret, raw_body) == received_hmac`

with `shop` completely outside that equality. Since a single `api_secret_key`/`client_secret` is shared across **all** shops that install the same app, any merchant who installs the app on their own store legitimately receives correctly-signed webhooks (valid `raw_body` + valid HMAC, computed with the app-wide secret — not a per-shop secret). That merchant can replay the exact same `raw_body`/HMAC pair directly to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with any other installed shop's domain. `HmacValidator.validate` still succeeds because it never inspects the `shop` header, so the handler processes the payload attributing it to the victim shop chosen by the attacker.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an unprivileged merchant (one tenant of a multi-tenant app) can cause the host application to attribute webhook events (e.g. `orders/create`, `app/uninstalled`, `customers/data_request`, etc.) to a different shop of their choosing. Depending on how the host app's handler uses `data.shop` (almost universally used as the tenant/session key to look up the correct `Session`/access token and to scope database writes), this enables cross-tenant data corruption, spoofed business events, or triggering shop-scoped side effects (e.g. forcing uninstall cleanup, fake order creation, GDPR webhook mishandling) against a victim shop the attacker does not control. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any deployment that exposes the standard webhook endpoint publicly (as required by Shopify's webhook delivery model). The attacker only needs their own legitimate app installation (any merchant can install a public app) to obtain one valid signed webhook body/HMAC pair; no access to `api_secret_key`, access tokens, or the target shop's credentials is required. The replay itself is a simple unauthenticated HTTP POST with a modified header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) values into the HMAC-verified signable content, or otherwise cross-check the `shop` header against an independently-authenticated source (e.g. require the registered webhook's known shop, or include `shop` in the string that `to_signable_string` returns and validate it as part of `Utils::HmacValidator.validate`). At minimum, document and warn integrators that `WebhookMetadata#shop` is not cryptographically bound to the signed payload and must not be trusted as an authenticated tenant identifier without additional verification (e.g. matching against a shop the app has an active session for).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook delivery, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of body B, computed with the app's shared api_secret_key>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: B
   ```
2. Attacker resends the identical body `B` and identical `x-shopify-hmac-sha256` value directly to the app's public webhook endpoint, but changes the header to:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
3. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)`, which still matches the replayed `x-shopify-hmac-sha256` value (see [1](#0-0) ), so `Registry.process` proceeds.
4. `request.shop` reads `victim-shop.myshopify.com` from the (unauthenticated) header (see [5](#0-4) ) and is delivered to the app's handler in `WebhookMetadata`, causing the host application to process the event as if it originated from `victim-shop.myshopify.com`.
