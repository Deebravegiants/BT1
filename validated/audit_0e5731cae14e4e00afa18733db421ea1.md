### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity using `Utils::HmacValidator.validate(request)`, which in turn calls `request.to_signable_string` to compute the HMAC. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signature [2](#0-1) . `Registry.process` validates the HMAC and then hands `request.shop` straight to the app-supplied handler as trusted tenant identity [3](#0-2) , and the documented `WebhookHandler` contract explicitly tells integrators `shop` is "The shop domain of the webhook" [4](#0-3)  — i.e., an authenticated field.

### Finding Description
This mirrors the reported bug class: a field that is acted upon (`shop`) is not covered by the integrity check that is supposed to prove authenticity (the HMAC), so the binding `hmac_valid ⇒ shop_is_authentic` does not hold.

`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against `verifiable_query.hmac` [5](#0-4) . For OAuth's `AuthQuery`, `to_signable_string` includes `code`, `host`, `shop`, `state`, `timestamp` — so `shop` is bound to the signature there [6](#0-5) . But for `Webhooks::Request`, the same `VerifiableQuery` interface is satisfied by returning only the raw body [7](#0-6) , so the same HMAC secret/algorithm produces an identical valid signature for a given body regardless of which shop's domain header accompanies it.

Because the same `api_secret_key` is shared across all shops installed on an app (a merchant's own dev/test store included), an attacker who controls a store where the app is installed can capture a legitimately Shopify-signed `(raw_body, hmac)` pair from their own store's webhook delivery, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `Registry.process` will accept it, because `Utils::HmacValidator.validate` only checks the body, never the shop [8](#0-7) , and forward the forged shop identity plus the attacker's chosen body content to the handler as `WebhookMetadata` [9](#0-8) .

### Impact Explanation
This crosses a tenant boundary: an app built per this gem's documented contract trusts `data.shop` from `WebhookMetadata` as the authenticated identity of the shop the event pertains to, exactly as instructed in the docs example (`shop_domain: data.shop`) [10](#0-9) . An attacker who controls one legitimate install can inject arbitrary attacker-controlled JSON payloads (as long as it's a validly-formed body they previously received a real HMAC for, or any body if they can trigger events with attacker-chosen content, e.g. metafields/notes on their own store) attributed to a victim shop of their choosing. Depending on how the host application consumes `data.shop` (e.g., billing state changes, `app/uninstalled` handling, data sync), this can enable cross-tenant data corruption or state manipulation for a shop the attacker does not control.

### Likelihood Explanation
Requires only an attacker-controlled Shopify store where the target app is installed (a normal, low-privilege scenario — free trial dev stores are trivial to create) and the ability to receive one legitimately-signed webhook from Shopify. No possession of `api_secret_key`, access tokens, or the victim's credentials is required, satisfying the "unprivileged internet user" constraint.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signable payload for webhooks, or independently verify that the `shop-domain` header corresponds to a shop with an active, known session/installation before trusting it, rather than relying solely on the raw-body HMAC to vouch for header-derived identity fields.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`.
2. Attacker triggers an event (e.g., `orders/create` with a crafted `note` field) causing Shopify to send a webhook to the app's registered endpoint with a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's real `api_secret_key`.
3. Attacker intercepts/replays this exact `raw_body` + `hmac` pair via `curl`, but changes the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged shop header [11](#0-10) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC [3](#0-2) .
5. The app's handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker-controlled>)` as if Shopify authenticated that this event belongs to the victim shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
