This confirms the mechanics conclusively. The key code is in `xcm-executor`'s handling of `DepositReserveAsset`: [1](#0-0) 

When Parachain A executes `DepositReserveAsset{dest=ParachainB, xcm=[DepositReserveAsset{dest=Relay,...}]}`, the executor builds a *new* top-level message for B consisting of `[ReserveAssetDeposited(assets), ClearOrigin, ...xcm.0]` and sends it via `self_ref.send(dest, Xcm(message), ...)`. Because `message.extend(xcm.0.into_iter())` splices the nested instructions directly into the top level of the outgoing message, the attacker's inner `DepositReserveAsset{dest=Relay,...}` becomes a **top-level instruction** of the XCM that Parachain B actually executes — it is not nested inside `SetAppendix`/`SetErrorHandler`/`ExecuteWithOrigin`.

This is corroborated by the existing test/scenario patterns showing exactly this multi-hop composition already used in production code (nested `DepositReserveAsset` chains for remote-reserve transfers): [2](#0-1) [3](#0-2) 

At Parachain B, its own `Barrier` (e.g. `DenyThenTry<DenyRecursively<DenyReserveTransferToRelayChain>, ...>`) runs `DenyReserveTransferToRelayChain::deny_execution` over B's top-level instruction list via `message.matcher().match_next_inst_while`: [4](#0-3) 

Since `DepositReserveAsset{dest=Relay,...}` is a plain top-level instruction of the message B executes (not buried inside `SetAppendix`, `SetErrorHandler`, or `ExecuteWithOrigin`), the base (non-recursive) top-level scan already matches and denies it at hop B — `DenyRecursively` isn't even needed here, since that wrapper only exists to catch instructions hidden inside locally-executed nested-XCM instructions (`SetAppendix`/`SetErrorHandler`/`ExecuteWithOrigin`) per its own documentation: [5](#0-4) 

So the described bypass does not work: each hop's barrier is applied against the XCM program that hop will *locally execute*, and `DepositReserveAsset`/`InitiateReserveWithdraw`/`TransferReserveAsset` instructions always get spliced into that local top-level program when the executor constructs the onward message — they never remain "hidden" inside an opaque nested field that only the ultimate destination inspects. The barrier at Parachain B (or Parachain C, or the Relay itself) always sees the immediate `dest` field of whatever reserve-transfer instruction it is about to execute locally, and if that `dest` is the Relay Chain (`Location{parents:1, interior:Here}`), it is denied at that hop regardless of how many prior hops there were. This is exactly the scenario the existing test suite already exercises with `deny_recursively_then_try_works` and `compare_deny_filters`: [6](#0-5)
