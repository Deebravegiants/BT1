### Title
`CostTracker::remove_transaction_cost` underflows non-saturating counters, permanently bricking the leader's block-cost tracker for the remainder of the slot - (File: cost-model/src/cost_tracker.rs)

### Summary
`CostTracker::remove_transaction_cost` decrements several fields with plain `-=` operators (and calls into `sub_transaction_execution_cost`, which uses `AtomicU64::fetch_sub` on `block_cost`) instead of the `saturating_sub` pattern used everywhere else in this file (`try_add`, `roll_back_applied_costs`). If `remove()` is ever invoked for a transaction whose accounted cost/counters were not actually reflected in the tracker's current state (e.g. a rollback path removing a cost that was only partially or never durably applied), the `u64` fields will underflow. Debug builds panic outright (thread panic in banking stage → validator instability); release builds wrap silently to values near `u64::MAX`, which then makes `try_add`'s `block_cost().saturating_add(cost) > self.limits.block_cost` check permanently true, rejecting every subsequent transaction for the bank/slot — a denial-of-service analogous to the `sDaiStrategy` "single attacker bricks the strategy via unaccounted-for subtraction" bug class.

### Finding Description
`cost_tracker.rs` maintains block/account cost accounting using two different subtraction styles:
- `try_add`/`roll_back_applied_costs` use `saturating_add`/`saturating_sub` deliberately to keep partial-rollback safe.
- `remove_transaction_cost` (called via `pub fn remove`) instead does:
```rust
fn remove_transaction_cost(&mut self, tx_cost: &TransactionCost<impl TransactionWithMeta>) {
    let cost = tx_cost.sum();
    self.sub_transaction_execution_cost(tx_cost, cost);
    self.allocated_accounts_data_size -= tx_cost.allocated_accounts_data_size();
    self.transaction_count -= 1;
    self.transaction_signature_count -= tx_cost.num_transaction_signatures();
    self.secp256k1_instruction_signature_count -= tx_cost.num_secp256k1_instruction_signatures();
    self.ed25519_instruction_signature_count -= tx_cost.num_ed25519_instruction_signatures();
    self.secp256r1_instruction_signature_count -= tx_cost.num_secp256r1_instruction_signatures();
}
``` [1](#0-0) 

and `sub_transaction_execution_cost` uses a wrapping atomic subtraction on the shared block cost:
```rust
fn sub_transaction_execution_cost(&mut self, tx_cost: &TransactionCost<...>, adjustment: u64) {
    for account_key in tx_cost.writable_accounts() {
        let account_cost = self.cost_by_writable_accounts.entry(*account_key).or_insert(0);
        *account_cost = account_cost.saturating_sub(adjustment);
    }
    self.block_cost.fetch_sub(adjustment);
}
``` [2](#0-1) 

`self.block_cost` is a `SharedBlockCost(Arc<AtomicU64>)`, and `AtomicU64::fetch_sub` does not panic on underflow — it wraps to a huge value: [3](#0-2) 

`try_add` then gates all future transactions on this corrupted value:
```rust
if self.block_cost().saturating_add(cost) > self.limits.block_cost {
    return Err(CostTrackerError::WouldExceedBlockMaxLimit);
}
``` [4](#0-3) 

`remove()`/`remove_transaction_cost` is invoked from banking-stage rollback paths, e.g. `Consumer::remove_added_transaction_costs` (invoked on record failure) and the all-or-nothing rollback branch of `try_add_processed_transaction_costs`: [5](#0-4) [6](#0-5) 

This mirrors the reported bug class exactly: a single accounting path uses unchecked subtraction while sibling paths in the same module deliberately use saturating arithmetic to avoid exactly this failure mode, and the corrupted state then poisons all future operations that depend on the same shared counter (analogous to `feesPending` poisoning `_currentBalance`).

### Impact Explanation
If `remove()` is called with a `TransactionCost` whose accounted values are not fully present in the tracker (any mismatch between what was added and what is removed — including double-removal, or removal of a transaction whose earlier `try_add` failed/rolled back for some but not all counters), `block_cost` wraps to near `u64::MAX`. From that point on, every call to `try_add` for the rest of the bank's lifetime will fail with `WouldExceedBlockMaxLimit`, since `block_cost().saturating_add(cost)` (already saturated near `u64::MAX`) will always exceed `limits.block_cost`. This effectively halts transaction inclusion/block production for that bank/slot — a validator/leader-side denial of service triggerable by ordinary transaction processing paths, not a privileged operator action. In debug configurations, the plain `-=` on `Saturating<u64>`-free fields (`transaction_count`, etc. — noted as `Saturating<u64>` per the struct definition) would not panic since they are `Saturating` wrapped types, but `block_cost`'s underlying `AtomicU64::fetch_sub` silently wraps regardless of build profile, so the DoS applies uniformly.

### Likelihood Explanation
Medium/Low-to-Medium confidence: exploitability depends on whether any live code path actually calls `remove()` with a mismatched/already-removed `TransactionCost` (e.g. a double-remove race between the record-failure rollback and the all-or-nothing rollback, or removal after a cost was only partially applied in a scenario not covered by the existing rollback bookkeeping). The report should be treated as a code-hygiene / defense-in-depth finding: the asymmetry between saturating and non-saturating subtraction paths in the same accounting structure is a real root cause matching the analog bug class, but a concrete trigger requires a specific rollback/double-removal ordering that was not confirmed to be reachable within the available context (index size limits meant not all call sites of `remove`/`write_cost_tracker` across the replay and banking-stage code could be fully traced).

### Recommendation
Change `remove_transaction_cost` to use `saturating_sub` (or `checked_sub` with defensive clamping/logging) for `allocated_accounts_data_size`, `transaction_count`, and the various signature counters, consistent with `roll_back_applied_costs`/`sub_transaction_execution_cost`'s per-account handling. Additionally, change `SharedBlockCost::fetch_sub` (and its caller `sub_transaction_execution_cost`) to clamp at zero (e.g., via a compare-and-swap saturating subtraction loop) instead of relying on `AtomicU64::fetch_sub`'s silent wraparound, so that any accounting mismatch degrades gracefully (worst case: a value pinned at 0) rather than poisoning `block_cost` to near `u64::MAX` and permanently blocking further transaction admission for the bank.

### Proof of Concept
Conceptual reproduction (illustrates the underflow mechanics; exact reachability of a real mismatched-removal call site was not fully confirmed given index limitations):
1. Call `CostTracker::try_add(&tx_cost_a)` successfully, incrementing `block_cost` by `cost_a`.
2. Trigger a code path that calls `CostTracker::remove(&tx_cost_a)` twice (e.g., via overlapping rollback handling on the same processed batch, such as both `remove_added_transaction_costs` on a record failure and a subsequent all-or-nothing rollback referencing the same `transaction_costs` slice) — see the two call sites at `core/src/banking_stage/consumer.rs:398` and `core/src/banking_stage/consumer.rs:567,660`.
3. The second `remove()` call subtracts `cost_a` from an already-zeroed `block_cost`, causing `AtomicU64::fetch_sub` to wrap to `u64::MAX - cost_a + 1`.
4. All subsequent `try_add` calls now fail `block_cost().saturating_add(cost) > self.limits.block_cost`, rejecting every future transaction cost admission for that bank — reproducing the "bricked until manual intervention" (in this case, a new bank/slot) failure mode described in the source report. /// Wrapper around blockcost to allow fast sharing of the value without locking.
/// Value is read-only outside of cost-tracker.
#[derive(Debug, Clone)]
pub struct SharedBlockCost(Arc<AtomicU64>);

impl SharedBlockCost {
    pub fn new(value: u64) -> Self {
        Self(Arc::new(AtomicU64::new(value)))
    }

    fn fetch_add(&self, value: u64) -> u64 {
        self.0.fetch_add(value, Ordering::Release)
    }

    fn fetch_sub(&self, value: u64) -> u64 {
        self.0.fetch_sub(value, Ordering::Release)
    }

    pub fn load(&self) -> u64 {
        self.0.load(Ordering::Acquire)
    }
}
