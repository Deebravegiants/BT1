## Title
No check on ERC20 `transfer()` return value in `IntentGatewayV2.withdraw()`/`SweepDust` (Tron) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron deployment of `IntentGatewayV2` deliberately avoids OpenZeppelin's `SafeERC20.safeTransfer` for escrow payouts and dust sweeps, instead performing a raw low-level `.call()` with the `IERC20.transfer.selector` and only checking that the *call itself* did not revert. It never decodes and validates the boolean return value that ERC20 mandates for a successful transfer.

### Finding Description
In `withdraw()` (used both for `RedeemEscrow` fills and `RefundEscrow` cancellations) and in the `SweepDust` request handler, token payouts are performed like this: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

and the same pattern in `SweepDust`: [2](#0-1) 

`success` here only reflects whether the low-level call reverted — not whether the ERC20 `transfer` logically succeeded. Per EIP-20, a compliant token may return `false` instead of reverting when a transfer cannot be completed (e.g. insufficient balance in some non-standard TRC20/ERC20 implementations, blacklist/pausable tokens, or fee/permission gated tokens). In that case `success == true` (the call didn't revert) but the returned `bool` payload is `false`, meaning no tokens actually moved to the beneficiary. The code does not decode `returndata` to check this boolean, so the failed transfer is treated as a success.

Every other transfer-out path in the sibling `evm/src/apps/IntentGatewayV2.sol` and `evm/src/apps/intentsv2/*` contracts consistently uses `IERC20(token).safeTransferFrom(...)` (via `SafeERC20`, which does check the return value), confirming this Tron-specific `withdraw`/`SweepDust` path is the outlier that dropped the return-value check.

### Impact Explanation
`withdraw()` is reached from `onAccept()` (processing a relayed `RedeemEscrow`/`RefundEscrow` POST from a counterpart `IntentGatewayV2`) and from `onGetResponse()` (processing a relayed storage-proof response for source-chain cancellation) — both triggered by any permissionless relayer delivering a proof through Hyperbridge. Regardless of whether the underlying token transfer actually succeeds, the function unconditionally decrements the internal escrow accounting (`_orders[body.commitment][token] -= amount`) and marks the order as filled/refunded (`_filled[body.commitment] = beneficiary`). If the transfer silently fails:
- The solver/user beneficiary never receives the escrowed tokens.
- The order is nonetheless marked filled/refunded, so the escrow can never be re-claimed through the normal flow.
- Tokens remain permanently stuck in the `IntentGatewayV2` contract (their accounting entry has already been zeroed out), i.e. tokens are permanently frozen/lost from the affected party's perspective.

This is a permanent freezing/loss-of-funds bug affecting the core escrow settlement path of the intents system, satisfying High/Critical impact criteria.

### Likelihood Explanation
Triggering requires only a token used as an order's input/fee-token asset whose `transfer()` can return `false` instead of reverting (a known real-world pattern for several TRC20/ERC20-style tokens, particularly relevant given this contract specifically targets Tron's TRC20 ecosystem, which is less standardized than EVM ERC20). No privileged role is required — any user can place an order denominated in such a token, and any relayer permissionlessly delivering the settlement message will trigger the vulnerable `withdraw()` path.

### Recommendation
Use `SafeERC20.safeTransfer` (already imported and used elsewhere in the file for `safeTransferFrom`) for these payouts, or explicitly decode and check the boolean return value when calling `transfer` via low-level `.call`:
```solidity
(bool success, bytes memory data) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success || (data.length != 0 && !abi.decode(data, (bool)))) revert TransferFailed();
```

### Proof of Concept
1. Deploy a token whose `transfer()` returns `false` on failure instead of reverting (e.g., when the recipient is blacklisted, or balance/allowance checks fail without a `require`).
2. Place a cross-chain order on the source chain using this token as an input asset via `placeOrder`, escrowing tokens in `IntentGatewayV2`.
3. Have a solver fill the order on the destination chain; the destination gateway dispatches a `RedeemEscrow` POST back to the source chain.
4. A relayer delivers the POST; `onAccept()` calls `withdraw()`. The token's `transfer(beneficiary, amount)` call returns `false` (no revert) — `success == true` from the low-level call perspective.
5. `withdraw()` proceeds to decrement `_orders[commitment][token]` and mark `_filled[commitment] = beneficiary`, even though the solver's balance never changed.
6. The escrowed tokens remain permanently stuck in the `IntentGatewayV2` contract with no accounting path left to reclaim them.
