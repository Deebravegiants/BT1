Confirmed: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header without being part of the signed content [2](#0-1) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` (which checks the HMAC against `to_signable_string`, i.e. body only) and then forwards `request.shop` unchecked into `WebhookMetadata` passed to the handler [3](#0-2) .

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant shop-attribution spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body [4](#0-3) . The `shop` value that the handler receives and uses as the tenant identifier is read straight from the `X-Shopify-Shop-Domain` header [2](#0-1) , but `to_signable_string` — the data actually protected by the HMAC — only includes `@raw_body` and never the shop-domain header [1](#0-0) . This is the same bug class as the report: a field that is *acted on* (`shop`, used to attribute/route webhook data) is not *covered* by the integrity check (the HMAC), breaking the binding `hmac-authenticated body == shop asserted for processing`.

### Finding Description
The library's webhook signature scheme signs only the JSON body, using `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, raw_body)` via `HmacValidator.validate_signature` [5](#0-4) . The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are all read out-of-band from HTTP headers and are never mixed into the signed string [6](#0-5) . `Registry.process` uses `request.shop` — an unauthenticated header value — to construct the `WebhookMetadata` object handed to the app's registered handler [3](#0-2) .

Because any webhook body/HMAC pair that was legitimately generated by Shopify for **shop A** remains valid regardless of which `shop-domain` header value accompanies it (the signature check never inspects that header), an entity that can capture or replay a legitimately-signed webhook body (e.g., by controlling a shop that has this app installed, or by intercepting/observing a webhook delivery it's authorized to receive) can resend that exact body with an attacker-chosen `X-Shopify-Shop-Domain` header pointing at a *different* shop. `Registry.process` will accept it as fully valid (HMAC passes because the body is unmodified) and will invoke the app's handler with `shop:` set to the attacker-chosen victim shop [7](#0-6) .

### Impact Explanation
This breaks the identity binding "the shop asserted for a webhook == the shop that Shopify actually generated the signed payload for." A host application that uses `shop:` from `WebhookMetadata` to route the webhook body into per-tenant storage, billing, or business logic (the intended and documented usage pattern for this field) can be made to process attacker-supplied body content under a victim shop's identity — a cross-tenant data-integrity/confusion issue. This matches the Critical "cross-tenant access" impact category, since a low-privilege user (a merchant/attacker who controls any shop with the app installed, or who can capture a valid webhook delivery) can cause data attributed to another tenant.

### Likelihood Explanation
Exploitation requires the attacker to first obtain at least one validly-signed `(body, hmac)` pair — achievable by installing the app on an attacker-controlled dev/trial shop and triggering any webhook topic they want replayed (e.g. `orders/create` with attacker-controlled order content), then replaying that body against the app's webhook endpoint with a forged `shop-domain` header. This is a realistic, low-privilege, unauthenticated-relative-to-the-victim-shop attack path requiring no secrets, tokens, or victim cooperation.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed content check, e.g. by having `Request#to_signable_string` incorporate the shop-domain header (or by independently comparing `request.shop` against an expected/allow-listed shop for the session under which the webhook was registered) rather than trusting the header verbatim once only the body's HMAC has been verified.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) with an arbitrary JSON body of their choosing; Shopify signs it with the app's real `api_secret_key`, producing `(raw_body, hmac)` valid for that body.
2. Attacker replays the exact `raw_body` and `X-Shopify-Hmac-Sha256` header to the same app endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally [8](#0-7) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC from `raw_body` only and matches, since the body/HMAC pair is unmodified [4](#0-3) .
4. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop == "victim-shop.myshopify.com"`, even though the body content originated from the attacker's own shop [7](#0-6) .

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
