### Title
`InboundXcmpSuspended::try_insert` failure on `MaxInboundSuspended` exhaustion silently leaves excess channels unsuspended, degrading backpressure - (File: cumulus/pallets/xcmp-queue/src/lib.rs)

### Summary
`Pallet::on_queue_changed` suspends a sibling channel by sending a `ChannelSignal::Suspend` and recording the para in `InboundXcmpSuspended` via `try_insert`, bounded by `T::MaxInboundSuspended` [1](#0-0) . If an attacker controls enough distinct `ParaId`s to push `MaxInboundSuspended` channels past `suspend_threshold` simultaneously, subsequent channels' `try_insert` calls fail and are only logged, leaving those channels without local suspension bookkeeping even though the `Suspend` signal was successfully sent to the remote side [2](#0-1) . However, the per-channel `drop_threshold` enforcement in `enqueue_xcmp_messages` via `get_batches_footprints`/`search_best_by` is independent of `InboundXcmpSuspended` and always caps queue growth for any individual channel regardless of suspension bookkeeping state [3](#0-2) .

### Finding Description
The suspend mechanism has two independent effects when `fp.ready_pages >= suspend_threshold`: (1) `Self::send_signal(para, ChannelSignal::Suspend)` is called and (2) on success, `para` is inserted into `InboundXcmpSuspended` bookkeeping [4](#0-3) . If `try_insert` fails because `InboundXcmpSuspended` (bounded by `T::MaxInboundSuspended`) is already full, the signal was still sent (the remote side is told to stop sending), but locally the channel is not tracked as suspended, so a subsequent drop below `resume_threshold` won't trigger a `Resume` signal for it since `on_queue_changed`'s resume branch only fires for entries actually present in `suspended_channels` [5](#0-4) .

Critically, though, the actual bound on queue growth for a given channel is enforced independently in `enqueue_xcmp_messages`, which computes `get_batches_footprints(sender, xcms, drop_threshold)` and only enqueues the best batch that keeps total pages `<= drop_threshold`; any XCMs beyond that are dropped with a logged error, regardless of whether the channel is present in `InboundXcmpSuspended` [6](#0-5) . This means the `drop_threshold` cap is not gated by successful suspension bookkeeping — it is a hard-coded structural limit checked on every enqueue call, independent of `MaxInboundSuspended` exhaustion.

### Impact Explanation
The consequence of `try_insert` failure is a **backpressure signaling degradation** for excess channels: the local node loses the ability to auto-resume that channel later (since it's not tracked as suspended) and repeatedly re-sends `Suspend` signals every time `on_queue_changed` runs above `suspend_threshold`, consuming outbound bandwidth/weight for redundant signal messages. It does **not** result in unbounded queue growth or bypass of `drop_threshold`, because `enqueue_xcmp_messages` enforces the page cap unconditionally on every call for every sender, independent of the `InboundXcmpSuspended` set [6](#0-5) . Therefore the specific scoped impact claimed — "uncontrolled page growth toward/past `drop_threshold`" and "silently permits unbounded queue growth for excess channels" — is not substantiated by the code.

### Likelihood Explanation
Reaching `MaxInboundSuspended` distinct simultaneously-suspended channels requires an attacker (or many attackers) to control enough distinct `ParaId`s to flood that many channels past `suspend_threshold` in the same or overlapping blocks, which is a large-scale, resource-intensive precondition (each `ParaId` needs its own HRMP channel and enough message volume). This is plausible on a permissionless parathread/coretime model but requires substantial resources across many chains, not a single-account exploit.

### Recommendation
Decouple the remote suspend-signal state from local bookkeeping capacity: e.g., retry `try_insert` in later blocks, increase `MaxInboundSuspended` to a safe practical ceiling, or track suspended channels using a mechanism not bounded by a small fixed-size set (e.g., a `StorageMap` keyed by `ParaId` rather than `BoundedBTreeSet`) so that suspension state can never be lost due to capacity exhaustion, while independently keeping `drop_threshold` as the hard backstop it already is.

### Proof of Concept
Integration test in `cumulus/pallets/xcmp-queue/src/tests.rs`: configure a mock `T::MaxInboundSuspended = N`; call `on_queue_changed` for `N` distinct `ParaId`s each with `fp.ready_pages >= suspend_threshold`, asserting all are inserted into `InboundXcmpSuspended`; then call `on_queue_changed` for the `N+1`-th `ParaId` with the same footprint and assert (a) `try_insert` fails (channel absent from `InboundXcmpSuspended`), (b) the `Suspend` signal was still queued in `SignalMessages`/`OutboundXcmpStatus`, and (c) subsequently calling `enqueue_xcmp_messages` repeatedly for that channel never causes `OutboundXcmpMessages`/inbound page count to exceed `drop_threshold`, confirming the drop cap holds independent of the suspension-bookkeeping failure.

		sender: ParaId,
		xcms: &[BoundedSlice<'a, u8, MaxXcmpMessageLenOf<T>>],
		is_first_sender_batch: bool,
		meter: &mut WeightMeter,

		let batches_footprints =
			T::XcmpQueue::get_batches_footprints(sender, xcms.iter().copied(), drop_threshold);

		let best_batch_footprint = batches_footprints.search_best_by(|batch_info| {
			let required_weight = T::WeightInfo::enqueue_xcmp_messages(
				batches_footprints.first_page_pos.saturated_into(),
				batch_info,
				is_first_sender_batch,
			);

			match meter.can_consume(required_weight) {
				true => core::cmp::Ordering::Less,
				false => core::cmp::Ordering::Greater,
			}
		});

		meter.consume(T::WeightInfo::enqueue_xcmp_messages(
			batches_footprints.first_page_pos.saturated_into(),
			best_batch_footprint,
			is_first_sender_batch,
		));
		T::XcmpQueue::enqueue_messages(
			xcms.iter().take(best_batch_footprint.msgs_count).copied(),
			sender,
		);

			);

		}
