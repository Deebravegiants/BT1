### Title
Emporium's stateless `runAction` branch allows forging arbitrary `CircomData` against any cross-registered `IExternalActionV2` endpoint - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction`'s CASE 2 branch (stateless interaction, lines 102-113) only blacklists two `IHinkalWallet` selectors from `op.callData` and otherwise blindly forwards `op.endpoint.call{value: op.value}(op.callData)`. If `op.callData` is crafted to invoke `IExternalActionV2.runAction(forgedCircomData, forgedDeltas)` on a target action `T` that lists this Emporium instance as an `isAllowedRecipient`, `T` will execute against a completely attacker-forged `CircomData` struct that was never checked by any ZK proof, `performHinkalChecks`, or `getHashedCalldata` integrity check for its own semantics beyond raw-byte inclusion in the outer transaction's `calldataHash`.

### Finding Description
The equality that is assumed but broken: **"if `msg.sender == allowedRecipient` inside `T.runAction`, then the `CircomData` argument received has been validated by an outer ZK proof / `performHinkalChecks` for the fields `T` acts on (`originalSender`, `erc20TokenAddresses`, `externalActionMetadata`)."**

This holds for the normal path: `Hinkal._externalTransact` [1](#0-0)  calls `IExternalActionV2(...).runAction(circomData, deltaAmountChanges)` using the *exact same* `circomData` object that `hinkalHelper.performHinkalChecks` already validated (including the `calldataHash` integrity check against `CircomDataBuilder.getHashedCalldata`) [2](#0-1) , and whose fields feed the circuit's public inputs via `formInputForCircom`/`formBasicInput` [3](#0-2) .

It breaks for `EmporiumUpgradeable`'s stateless branch: `runAction` decodes an `EmporiumStack` from `circomData.externalActionData.externalActionMetadata` and, for each `op`, low-level-calls `op.endpoint.call{value: op.value}(op.callData)` with no restriction on `op.endpoint`'s type and only a selector blacklist on `op.callData` [4](#0-3) . An attacker can set `op.endpoint = T` (e.g. `DepositOnChainUtxosExternalAction`) and `op.callData = abi.encodeWithSelector(IExternalActionV2.runAction.selector, forgedCircomData, forgedDeltas)`.

Inside `T.runAction`, the only access control is `onlyAllowedRecipient`, which checks `isAllowedRecipient[msg.sender]` [5](#0-4) ; since the call originates from `EmporiumUpgradeable`, `msg.sender` is the Emporium address, which passes if `T` has registered Emporium as an allowed recipient (a plausible cross-registration for composability). Critically, `T.runAction` performs **no** independent proof/hash verification of the `circomData` it receives — it directly trusts `circomData.originalSender` and pulls tokens: `transferERC20TokenFrom(tokenAddress, userAddress, msg.sender, tokenTotal)` where `userAddress = circomData.originalSender` [6](#0-5) .

`forgedCircomData` is entirely attacker-constructed raw bytes nested inside `op.callData`, itself nested inside the outer `circomData.externalActionData.externalActionMetadata`. While the *raw bytes* of the outer `externalActionMetadata` (hence `op.callData`) are covered by `calldataHash`/`getHashedCalldata1` [7](#0-6) , this only guarantees the relay didn't tamper with the bytes the attacker's own proof committed to — it does not constrain the *semantic* content of the forged struct (e.g., that `forgedCircomData.originalSender` equals the attacker's own address, or that any nullifier/proof backs the claimed transfer). The `require(circomData.originalSender == sender ...)` check in `performHinkalChecks` [8](#0-7)  only applies to the **outer** `circomData` (Emporium's own), never to the nested forged one passed to `T`.

Exploit flow:
1. Attacker deposits/owns minimal funds and generates one legitimate proof through `Hinkal.transact`, selecting Emporium as the `externalAction`, with `externalActionMetadata` encoding an `EmporiumStack` containing one stateless `op` targeting `T`.
2. Emporium's `runAction` executes `op.endpoint.call(op.callData)`, invoking `T.runAction(forgedCircomData, forgedDeltas)` with `msg.sender = Emporium`.
3. `T`'s `onlyAllowedRecipient` passes because `Emporium` is a registered allowed recipient of `T`.
4. `T` executes `transferFrom(forgedCircomData.originalSender, Emporium, tokenTotal)`, pulling tokens from any victim address the attacker names, provided that victim has a standing ERC20 allowance to `T` (plausible since users approve `T` to use it via the normal Hinkal deposit flow).
5. Emporium's post-call balance-diff logic then mints a UTXO for the attacker for the stolen amount, or the stolen tokens simply sit in Emporium for `handleOut` to route to `msg.sender` (the attacker's Hinkal call), completing the theft.

### Impact Explanation
This is a Critical-severity finding: it enables direct theft of user funds via unauthorized `transferFrom` calls with an attacker-forged `originalSender`, executed as a call "a wallet owner or prover never authorised." The stolen amount never appears in the attacker's own proof's public inputs (the calldataHash only proves byte-integrity of the wrapper calldata, not semantic authorization of the nested call), so the exploit bypasses the intended proof-authorization model entirely. It is repeatable against any victim with standing allowance to a cross-registered action, for the cost of one minimal legitimate Hinkal transaction.

### Likelihood Explanation
The exploit strictly requires that some `IExternalActionV2` action `T` (deployed and owned by the protocol, not the attacker) lists the Emporium contract's address in its own `isAllowedRecipient` mapping via `setAllowedRecipients` [9](#0-8) . I could not find any deployment script, config, or on-chain evidence in this repo confirming that such cross-registration exists or is planned; `Emporium`'s and other actions' `allowedRecipients` are configured off-chain by contract owners at deploy/admin time and not present in the indexed contents I could inspect. Given the indexing limits of this tool, I cannot definitively confirm or rule out this precondition from the available deploy configuration — a Devin session with full filesystem access would be needed to check actual deployment scripts/addresses. Assuming the precondition holds (as the question posits, "plausible cross-registration for composability"), the attack is fully feasible for any unprivileged attacker and requires only one cheap valid Hinkal transaction plus a victim with nonzero allowance to `T`.

### Recommendation
In `EmporiumUpgradeable.runAction`'s CASE 2 branch, disallow `op.endpoint` from being any address implementing `IExternalActionV2` (e.g., maintain and check an explicit denylist/allowlist of permitted call targets and/or selectors, rather than only blacklisting two `IHinkalWallet` selectors), or require that any `IExternalActionV2.runAction` call can only be invoked through `Hinkal._externalTransact` — never via arbitrary nested calldata from another external action. More robustly, actions like `DepositOnChainUtxosExternalAction` should not trust `msg.sender` alone via `onlyAllowedRecipient`; they should independently verify that the `CircomData` they receive corresponds to a proof-checked transaction (e.g., by requiring the caller to be exactly the canonical `Hinkal` contract, not a configurable allowlist that can include composable intermediaries like Emporium).

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (with allowed recipient = Hinkal), and `DepositOnChainUtxosExternalAction` `T` (with allowed recipients = [Hinkal, Emporium] to model the cross-registration precondition).
2. Victim approves `T` for a large ERC20 allowance (as would occur from normal Hinkal usage) and holds a token balance.
3. Attacker (unprivileged) generates one legitimate small-value Hinkal proof selecting Emporium as `externalActionId`, with `externalActionMetadata` = `abi.encode(EmporiumStack)` containing a single stateless `op` where `op.endpoint = address(T)` and `op.callData = abi.encodeWithSelector(IExternalActionV2.runAction.selector, forgedCircomData, forgedDeltas)`, with `forgedCircomData.originalSender = victim` and `externalActionMetadata` (nested) encoding `utxoAmounts` equal to victim's full balance.
4. Attacker calls `Hinkal.transact(...)`.
5. Assert: victim's ERC20 balance decreased by the stolen amount and Emporium/attacker's resulting UTXO set reflects the stolen funds.
6. Assert: the outer proof's public inputs (`inputForCircom` derived from `formInputForCircom`) contain no signal encoding `forgedCircomData.originalSender` or the stolen amount — i.e., the theft occurred outside the set of values constrained by the verified circuit.
