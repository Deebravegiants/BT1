### Title
Webhook shop identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing/replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from only the raw request body, while the `shop` (tenant) identifier is read from a separate, unsigned header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts `request.shop` as the tenant to attribute the event to. Because a Shopify app's `api_secret_key` is shared across every shop that installs the app, any merchant who has installed the app can capture a valid `(raw_body, hmac)` pair from their own legitimate webhook deliveries and replay it to the app's webhook endpoint with the `shopify-shop-domain` header swapped to a victim shop, producing a request that passes HMAC validation but is misattributed to a shop the attacker does not control.

### Finding Description
The signable string used for HMAC verification is defined as only the raw body: [1](#0-0) 

The `shop` accessor, however, is derived from an entirely separate, non-signed header: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) as authenticated tenant/event identity when dispatching to the registered handler: [3](#0-2) 

This breaks the equality that should hold for a signed request: `shop verified-by-HMAC == shop acted-upon`. Here, the shop "acted upon" (passed to the app's `WebhookHandler#handle` as `data.shop`) is never part of the bytes the HMAC covers — only the body is. Since the `api_secret_key` used to compute/verify webhook HMACs is the same secret for every shop that installs a given app (it is the app's client secret, not a per-shop key), a malicious-but-legitimate merchant who has the app installed on their own store can:
1. Receive genuine webhooks to their own endpoint, obtaining valid `(raw_body, hmac)` pairs signed with the app's shared `api_secret_key` (and can shape body content to a degree by manipulating their own store's data, e.g., product/order titles).
2. Replay that exact `raw_body` + `hmac` to the app's webhook processing endpoint, but substitute the `shopify-shop-domain` header with an arbitrary victim shop's domain.
3. `HmacValidator.validate` passes (line 190) because it only checks the body bytes; `request.shop` (line 22) is accepted as-is and forwarded to the handler as the authoritative tenant identity (line 198).

### Impact Explanation
This is a cross-tenant identity confusion: the gem allows an attacker who is a legitimate merchant of the app (an unprivileged actor with respect to other tenants) to inject webhook events that the host application will process as if they originated from a different, victim shop. Any host logic keyed off `data.shop` — audit logs, per-shop state machines, order/inventory sync, GDPR-relevant handlers (e.g., `customers/redact`), billing triggers — can be spoofed for a shop the attacker does not operate, without possessing that shop's access token or any of its credentials. This matches the "cross-tenant access" criterion.

### Likelihood Explanation
Any app built with this gem processes webhooks via `Registry.process`/`HmacValidator.validate` exactly as shown; every app that has more than one merchant installed shares one `api_secret_key`, which is the normal/expected configuration for public Shopify apps. No special access, leaked secrets, or privileged accounts are required beyond installing the app as an ordinary merchant, making this practically reachable.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the signable content verified by the HMAC, or otherwise cryptographically bind the `shop` header to the signed payload before it is trusted, so `to_signable_string` in `lib/shopify_api/webhooks/request.rb` cannot diverge from the `shop` value forwarded to handlers in `lib/shopify_api/webhooks/registry.rb`.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger an event (e.g., `orders/create`) so Shopify delivers a webhook to the app's endpoint with a valid `X-Shopify-Hmac-Sha256` computed over the raw body using the app's shared `api_secret_key`.
2. Capture the raw body and its valid HMAC.
3. Send a new HTTP request to the app's webhook endpoint using the captured raw body and HMAC unchanged, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` (it only checks `raw_body` against the HMAC), and `ShopifyAPI::Webhooks::Registry.process` invokes the registered handler with `data.shop == "victim-shop.myshopify.com"`, even though the event never came from that shop.
