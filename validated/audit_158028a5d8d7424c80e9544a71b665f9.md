### Title
Missing re-initialization guard in `LockupContract::new` allows full takeover and theft of locked/vested NEAR funds - (File: `lockup/src/lib.rs`)

### Summary
The `LockupContract::new` initializer is the only `#[init]` constructor in the `core-contracts` repository that does **not** contain the `assert!(!env::state_exists(), ...)` guard that every sibling contract (`lockup-factory`, `multisig`, `multisig2`, `staking-pool`, `staking-pool-factory`, `whitelist`, `voting`) uses to prevent re-initialization. [1](#0-0) 

### Finding Description
Every other `new()` constructor in the repo begins with `assert!(!env::state_exists(), "Already initialized")` (or an equivalent), e.g.: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

`LockupContract::new`, however, has no such check — it only validates account-ID formats and vesting-schedule consistency before unconditionally overwriting `Self { owner_account_id, lockup_information, vesting_information, staking_information: None, staking_pool_whitelist_account_id, foundation_account_id }`: [6](#0-5) 

Because `near_bindgen`'s `#[init]` macro (at the SDK version used here) does not itself enforce single-use — that protection is opt-in via `env::state_exists()` — `new` remains a **public, callable-by-anyone** function for the lifetime of the contract. Since this method takes no `predecessor_account_id` check and no owner check, any unprivileged attacker can call `new` again on an already-initialized, already-funded lockup contract account and completely overwrite its state:
- Set `owner_account_id` to themselves.
- Set `vesting_schedule` to `None`, wiping out any foundation-controlled vesting/termination rights (`foundation_account_id` becomes `None`, disabling `assert_no_termination` checks permanently).
- Set `transfers_information` to `TransfersEnabled` immediately, bypassing the transfer-poll gate.
- Reset `staking_information` to `None` (forced by the constructor), clearing any staking-pool bookkeeping.

`lockup_information.lockup_amount` is recomputed from `env::account_balance()` at call time, so the attacker's fabricated lockup record legitimizes the account's current NEAR balance as "belonging" to their new configuration.

All subsequent owner-gated withdrawal paths (`transfer`, `withdraw_from_staking_pool`, `add_full_access_key`, etc.) rely solely on `self.assert_owner()` and the freshly-attacker-controlled `vesting_information`/`transfers_information` flags: [7](#0-6) 

Once the attacker becomes `owner_account_id` with `vesting_information::None` and transfers enabled, `assert_owner`, `assert_transfers_enabled`, `assert_no_staking_or_idle`, and `assert_no_termination` all pass trivially, letting the attacker drain `get_liquid_owners_balance()` — i.e., the account's real NEAR balance — to any address they choose via `transfer`.

### Impact Explanation
This maps directly to the Critical scoped impact: "Unauthorized transfer, withdrawal, spending, or release of locked, vested ... NEAR through public-call ... accounting failure reachable by an unprivileged user," and also to "Permanent freezing / irrevocable loss of user or protocol funds in lockup release, vesting termination... flows," since the legitimate owner's control, the foundation's termination rights, and any vesting/lockup schedule are permanently and irrecoverably erased by the attacker's re-initialization.

### Likelihood Explanation
The `new` method is a normal public contract method with no caller restriction and no `state_exists` guard, so any account can call it against any already-deployed `LockupContract` at any time after the atomic deploy+init transaction completes — no privileged role, front-running window, or special condition is required beyond simply knowing the lockup contract's account ID (which is derivable/observable on-chain, e.g., via `lockup-factory`'s deterministic naming scheme). This makes exploitation straightforward and highly likely wherever this contract version is deployed with funds.

### Recommendation
Add the standard re-initialization guard at the top of `LockupContract::new`:
```rust
assert!(!env::state_exists(), "The contract is already initialized");
```
consistent with every other contract in this repository (`lockup-factory`, `multisig`, `staking-pool`, `staking-pool-factory`, `whitelist`, `voting`).

### Proof of Concept
1. `lockup-factory` deploys and initializes a `LockupContract` at `lockup_account_id` with legitimate `owner_account_id`, a vesting schedule, and `foundation_account_id` set (atomic tx via `create()`). [8](#0-7) 
2. Attacker later calls `lockup_account_id.new(owner_account_id = attacker, lockup_duration = 0, transfers_information = TransfersEnabled{transfers_timestamp: 0}, vesting_schedule = None, ...)` directly — nothing prevents this since there is no `state_exists` check. [9](#0-8) 
3. The contract state is overwritten: `owner_account_id = attacker`, `vesting_information = None`, `foundation_account_id = None`, `transfers_information = TransfersEnabled`, `staking_information = None`.
4. Attacker calls `transfer(amount, attacker_receiver)`. `assert_owner()` passes (attacker is now owner), `assert_transfers_enabled()` passes, `assert_no_staking_or_idle()` passes (`staking_information` is `None`), `assert_no_termination()` passes (`vesting_information::None`), and the check `get_liquid_owners_balance().0 >= amount.0` passes against the real NEAR balance held by the account. [10](#0-9) 
5. `Promise::new(receiver_id).transfer(amount.0)` sends the locked/vested NEAR to the attacker.

    #[init]
    pub fn new(
        owner_account_id: AccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        transfers_information: TransfersInformation,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        staking_pool_whitelist_account_id: AccountId,
        foundation_account_id: Option<AccountId>,
    ) -> Self {
        assert!(
            env::is_valid_account_id(owner_account_id.as_bytes()),
            "The account ID of the owner is invalid"
        );
        assert!(
            env::is_valid_account_id(staking_pool_whitelist_account_id.as_bytes()),
            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information
        {
            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {
            None => {
                assert!(
                    foundation_account_id.is_none(),
                    "Foundation account can't be added without vesting schedule"
                );
                VestingInformation::None
            }
            Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash),
            Some(VestingScheduleOrHash::VestingSchedule(vs)) => {
                VestingInformation::VestingSchedule(vs)
            }
        };
        assert!(
            vesting_information == VestingInformation::None ||
                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),
            "Foundation account should be added for vesting schedule"
        );

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
    }
