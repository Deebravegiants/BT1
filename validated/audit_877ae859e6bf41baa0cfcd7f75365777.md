### Title
Webhook `shop-domain` (and `topic`/`webhook_id`) header is trusted for tenant routing but is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, then dispatches the webhook to the app's handler using the `shop`, `topic`, and `webhook_id` values taken from unauthenticated HTTP headers. Because the signature never binds these routing/identity fields, any party who can capture one genuine, HMAC-valid webhook delivery can replay its body+signature to the app's webhook endpoint while substituting a different `shop-domain` header, causing the app to process/act on the payload under an arbitrary shop's tenant context.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from HTTP headers, which are entirely outside the signed material: [2](#0-1) 

`Registry.process` validates the HMAC once (over the body only) and then hands the header-derived, unauthenticated `shop`/`topic`/`webhook_id` straight to the registered handler as trusted routing/tenant metadata: [3](#0-2) 

`HmacValidator.validate` confirms the signature check is scoped exactly to `to_signable_string` (i.e., the raw body) using the app's single, shared `api_secret_key` — the same secret is used to validate webhooks for every shop the app serves: [4](#0-3) 

The documented handler contract explicitly treats `data.shop` (from the unauthenticated header) as the tenant identifier the host application should act on: [5](#0-4) 

This is the same bug class as the reported issue: the code enforces an integrity check (HMAC / bonding-share accounting) over one quantity (raw body / transferred amount) while acting on a different, unverified quantity (the `shop` header / total balance) that is supposed to be equal to, but is not cryptographically bound to, the verified one. Here the broken identity equality is:

`shop used to authorize/attribute the webhook == shop covered by the HMAC signature`

This equality does not hold, because the signature covers only the JSON/body bytes, never the `shopify-shop-domain` header.

### Impact Explanation
Because the app's shared HMAC secret authenticates *content*, not *origin/tenant*, a webhook payload with a valid signature is not bound to a specific shop. If an attacker can obtain one legitimately-signed webhook (e.g., by installing the app on their own store, a normal unprivileged action, and capturing the delivery to their own endpoint/log), they can resend the identical `raw_body` + `hmac` to the app's public webhook endpoint with the `shopify-shop-domain` header rewritten to any other shop that uses the same app. `HmacValidator.validate` will still succeed (same secret, same body), and `Registry.process` will invoke the handler claiming the event belongs to the victim shop. Depending on what the host app does in its handler (common patterns include using `shop` to look up the merchant's session/access token and mutate merchant data, deprovision resources, or record consent/redaction status per the documented `data.shop`), this can result in cross-tenant data corruption, spoofed mandatory redaction/data-request webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) being applied against the wrong tenant, or state corruption keyed by the forged shop. This matches the Critical/High bar for cross-tenant access via an identity-binding gap.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install/use the target app on an attacker-controlled shop (available to any unprivileged Shopify merchant/developer who can install a public app, or via a dev store), which yields a genuinely signed webhook body/HMAC pair, and (2) the ability to POST to the app's public webhook route with a modified `shop-domain` header — no access to `api_secret_key`, tokens, or the victim's credentials is required. This is a realistic, low-effort attack path for any app that keys tenant-sensitive logic off `WebhookMetadata#shop` as instructed by the gem's own documentation.

### Recommendation
Do not treat the `shop-domain`, `topic`, or `webhook_id` headers as trusted merely because the body HMAC validates. At minimum:
- Cross-check the header-derived `shop` against the shop associated with a currently known/installed session (offline session store) before acting on the webhook, rejecting webhooks for shops that have no corresponding active installation/session, and
- Document/enforce that host apps must not use `data.shop` as an unauthenticated trust anchor, or extend `VerifiableQuery`/`Webhooks::Request` so that the identity fields the handler consumes (`shop`, `topic`, `webhook_id`) are included in (or otherwise cryptographically tied to) the verified material, e.g., by validating them against Shopify's known/registered webhook subscription for that topic+shop instead of blindly forwarding header values.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, permitted action for any merchant/developer).
2. Shopify sends a legitimate webhook (e.g. `orders/create`) to the app's endpoint with headers `x-shopify-hmac-sha256`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, and a JSON body; the attacker captures the raw body and the HMAC value from their own delivery.
3. Attacker resends an HTTP POST to the same public webhook path with the identical `raw_body` and `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`@raw_body` only) and matches the (unchanged) signature — validation passes: [6](#0-5) 
5. `Registry.process` builds `WebhookMetadata` with `shop: request.shop` = `"victim-shop.myshopify.com"` (from the forged header) and invokes the app's handler, which per the documented contract treats this as the authoritative shop for the event: [3](#0-2) 

I could not fully verify how downstream host applications typically consume `WebhookMetadata#shop` (that logic lives outside this gem, in host apps such as those built with `shopify_app`), so the concrete blast radius depends on the host app's handler implementation; the gem-level root cause — HMAC validation scoped to body only while identity fields are taken from unauthenticated headers — is confirmed directly in the cited files.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
