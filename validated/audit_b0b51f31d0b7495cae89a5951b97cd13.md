Confirmed root cause: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC exclusively over that signable string [2](#0-1) . Yet `Registry.process` reads `request.shop` (and `topic`/`webhook_id`/`api_version`) straight from unauthenticated HTTP headers and hands them to the app's handler as trusted tenant-identifying metadata [3](#0-2) [4](#0-3) .

### Title
Webhook `shop-domain` header is not covered by HMAC signature, allowing cross-tenant shop spoofing in `ShopifyAPI::Webhooks::Registry.process` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before invoking the app's webhook handler, per the gem's own documentation. In reality, the HMAC signature only authenticates the raw request body; the `x-shopify-shop-domain` (and `topic`/`webhook_id`/`api_version`) headers are never included in the signed bytes, so any value in those headers is accepted as-is and passed to the handler as trusted tenant identity.

### Finding Description
The binding that should hold is:
`bytes_verified_by_HMAC == bytes_the_handler_trusts_for_tenant_identity`

In `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from HTTP headers, which are attacker-controllable on any inbound HTTP request and are not part of the signed string: [5](#0-4) 

`HmacValidator.validate`/`validate_signature` compute and compare the HMAC solely against `verifiable_query.to_signable_string` (i.e., the body only): [2](#0-1) 

`Registry.process` performs this HMAC check, then immediately builds `WebhookMetadata` from `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version`, and hands it to the app's `handler.handle`: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` const with no cryptographic binding to the body it accompanies: [6](#0-5) 

The documentation explicitly promises the stronger guarantee that `process` "will verify the request did indeed come from Shopify," which is misleading since only the body bytes are verified, not the shop/topic association: [7](#0-6) 

Because Shopify's real webhook HMAC is computed the same way (over the raw body only, per Shopify's own webhook spec) and this gem does not additionally bind the `shop-domain` header into the verified bytes, any party who can obtain one genuinely-signed webhook body+HMAC pair for *their own* shop (trivial — install the app on an attacker-owned test shop and trigger the webhook topic) can replay that exact body/HMAC pair with a forged `x-shopify-shop-domain` header pointing at a victim shop. `Registry.process` will pass HMAC validation (it only checks the body) and dispatch to the handler with `WebhookMetadata.shop` set to the victim's domain.

### Impact Explanation
This breaks the tenant identity binding the whole webhook system relies on. Most app implementations (as shown in the gem's own doc example) use `data.shop` to select which shop's session/access token/database row to act on: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`. An attacker-controlled `shop` value combined with attacker-controlled `body` content lets them inject/attribute forged webhook data into a victim shop's tenant context — e.g., causing an app to write attacker-crafted order/product/customer data keyed to a shop the attacker doesn't own, or trigger mandatory-topic handlers (`shop/redact`, `customers/redact`, `customers/data_request`) against a victim's shop identity. This is a cross-tenant identity-binding failure reachable by any unprivileged internet user who can install the app on a shop they control (or capture one legitimate delivery) — no access token, secret, or privileged account required.

### Likelihood Explanation
Moderate-to-high. Getting one authentic body+HMAC pair only requires installing the target app on an attacker-owned shop (a normal, unprivileged action) and triggering any registered webhook topic; capturing headers/body is standard for a webhook receiver, and forging the `x-shopify-shop-domain` header on the replayed HTTP request costs nothing. The library's own documentation reinforces the false assumption that `process` fully authenticates the request's shop, making this easy to overlook by consumers of the gem.

### Recommendation
Bind the shop (and ideally topic) into the verified bytes: include `shop-domain` (and other identity-relevant headers) as part of the signable string checked by `HmacValidator`, or independently cross-check `request.shop` against an app-known, previously-registered/authenticated shop record (e.g. an active session) before trusting it — and update `to_signable_string` / `HmacValidator.validate` so `process`'s documented guarantee ("verify the request did indeed come from Shopify") actually covers the shop attribution, not just body integrity.

### Proof of Concept
1. Install the target app on an attacker-owned shop `attacker.myshopify.com`; register for topic `orders/create`.
2. Trigger the webhook; capture the raw POST body and its genuine `x-shopify-hmac-sha256` value (both are valid because the attacker's own shop legitimately triggered it).
3. Replay an HTTP POST to the app's webhook endpoint with the identical body and `x-shopify-hmac-sha256` header, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged header set; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` only checks `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and calls `handler.handle(data: metadata)` — the app processes attacker-controlled data as belonging to `victim.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
