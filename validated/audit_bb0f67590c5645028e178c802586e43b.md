### Title
Governance liquidation-curve execution can be atomically sandwiched with liquidation - (File: contracts/controller/src/config/spoke.rs)

### Summary
A ready `SetSpokeLiquidationCurve` governance operation updates the spoke-wide liquidation curve immediately when `execute` runs, while every subsequent liquidation reads that live curve rather than a per-position or activation-delayed snapshot. [1](#0-0) [2](#0-1) [3](#0-2)  An unprivileged liquidator can therefore execute a ready curve update and liquidate an already-unhealthy account in the same transaction or ledger ordering, obtaining a larger bonus that is paid from the borrower’s seized collateral. [4](#0-3) [5](#0-4) 

### Finding Description
`AdminOperation::SetSpokeLiquidationCurve` resolves to the controller’s `set_spoke_liquidation_curve` call with `spoke_id`, `target_hf_wad`, `hf_for_max_bonus_wad`, and `liquidation_bonus_factor_bps`. [6](#0-5)  The controller setter validates the new tuple and writes all three values directly into `SpokeConfig`, with no activation ledger or grace period. [2](#0-1)  Unlike stored liquidation threshold, base bonus, and fee data, the liquidation curve is loaded from the current spoke configuration each time `build_liquidation_plan` constructs a liquidation. [7](#0-6)  The curve computation increases the bonus as health factor falls through the configured target/max-bonus range and scales the increment by `liquidation_bonus_factor_bps`. [8](#0-7)  `Governance::execute` accepts an optional executor and applies the scheduled target call once the operation is ready, after which the new spoke curve is visible to later calls in the same execution context. [9](#0-8)  Permissionless `Controller::liquidate` then repays the account’s debt and seizes collateral according to the newly installed curve. [10](#0-9) [11](#0-10) 

### Impact Explanation
The borrower loses additional collateral equal to the bonus differential produced by the old and new curves, while the liquidator captures that differential as profit. [12](#0-11) [13](#0-12)  For an account already below `HF = 1`, a curve update that raises `hf_for_max_bonus_wad`, raises `liquidation_bonus_factor_bps`, or otherwise produces a higher bonus at the current HF immediately increases the collateral seized for the same debt repayment. [14](#0-13) [5](#0-4)  This satisfies theft of user funds because the extra seized collateral belongs to the liquidated borrower and is transferred or credited to the liquidator. [15](#0-14) 

### Likelihood Explanation
Exploitation requires a ready governance operation that increases the liquidation bonus applicable to a spoke and at least one account in that spoke already satisfying `health_factor < Wad::ONE`. [16](#0-15) [6](#0-5)  Those conditions are plausible during routine liquidation-parameter changes because the curve applies spoke-wide and liquidations are permissionless. [17](#0-16) [4](#0-3)  The attacker does not need to influence governance contents or oracle prices; they only need to order `execute` before their own `liquidate` call once the operation becomes executable. [9](#0-8) 

### Recommendation
Do not activate a new liquidation curve in the same state transition that makes it executable. Store `activation_ledger` or an epoch alongside `SpokeConfig` and have `LiquidationCurve::from_config` select the prior curve until the next ledger or a defined grace window. [2](#0-1) [3](#0-2)  Alternatively, stamp the curve into accounts like other liquidation parameters and refresh it through a health-factor-gated path, ensuring an already-liquidatable account cannot receive a harsher payout curve without a separate safety check. [18](#0-17)  A regression test should execute a bonus-increasing curve update and assert that a liquidation in the same transaction still uses the prior curve. [3](#0-2) 

### Proof of Concept
1. Configure a spoke with an initial valid curve and create an account whose `health_factor` is just below `Wad::ONE`. [16](#0-15) 
2. Schedule `AdminOperation::SetSpokeLiquidationCurve` with a valid curve that produces a higher bonus at that HF, such as a higher `hf_for_max_bonus_wad` or `liquidation_bonus_factor_bps`. [6](#0-5) [8](#0-7) 
3. Once the operation is ready, an attacker contract invokes `Governance::execute(None, controller, "set_spoke_liquidation_curve", args, predecessor, salt)` and then `Controller::liquidate(attacker, account_id, debt_payments, SeizeMode::Transfer)` in the same transaction or immediate transaction ordering. [9](#0-8) [19](#0-18) 
4. The liquidation plan builds `LiquidationCurve::from_config` after the setter has committed the new spoke tuple, so the bonus and seizure quantities are calculated under the updated curve. [17](#0-16) [3](#0-2) 
5. Comparing the seized collateral before and after the operation shows the attacker receives the incremental bonus while the borrower loses that additional collateral. [13](#0-12)

    /// Ramps from zero at `target` to one WAD at the max-bonus threshold.
    /// Degenerate or reversed threshold ranges return one WAD.
    fn bonus_scale(&self, env: &Env, hf: Wad, target: Wad) -> Wad {
        if target <= self.hf_for_max_bonus {
            Wad::ONE
        } else {
            target
                .checked_sub(env, hf)
                .div(env, target.checked_sub(env, self.hf_for_max_bonus))
                .min(Wad::ONE)
        }
    }
}

/// Interpolates the base-to-max bonus increment as HF falls, then applies the
/// configured factor. HF at or above `target` receives the base bonus.
pub(crate) fn calculate_linear_bonus_with_target(
    env: &Env,
    hf: Wad,
    base: Bps,
    max: Bps,
    curve: &LiquidationCurve,
    target: Wad,
) -> Bps {
    if hf >= target {
        return base;
    }
    let scale = curve.bonus_scale(env, hf, target);

    let bonus_range = max.checked_sub(env, base);
    let bonus_increment = Wad::from(bonus_range.raw()).mul(env, scale).raw();
    let scaled_increment = curve.bonus_factor.apply_to(env, bonus_increment);
    Bps::from(
        base.raw()
            .checked_add(scaled_increment)
            .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow)),
    )

/// Estimates WAD USD repayment and BPS bonus toward the target HF.
/// Caps the curve bonus to preserve HF. With a positive seizure proportion,
/// collateral below debt quotes the collateral-backed repayment
/// `min(D, floor(C / (1 + base)))` at the base bonus; otherwise a cap below
/// base quotes the full debt at the cap, floored at zero. A target-HF quote
/// that would leave positive debt below `BAD_DEBT_USD_THRESHOLD` becomes the full debt.
pub(crate) fn estimate_liquidation_amount(
    env: &Env,
    snap: &LiquidationSnapshot,
    bounds: BonusBounds,
    curve: &LiquidationCurve,
) -> (Wad, Bps) {
    let scaled_bonus = calculate_linear_bonus_with_target(
        env,
        snap.hf,
        bounds.base,
        bounds.max,
        curve,
        curve.target_hf,
    );

    let bonus = match max_hf_preserving_bonus_bps(snap) {
        None => scaled_bonus,
        Some(_) if snap.total_collateral < snap.total_debt => {
            let one_plus_base = Wad::ONE.checked_add(env, bounds.base.to_wad(env));
            let backed = snap.total_collateral.div_floor(env, one_plus_base);
            return (backed.min(snap.total_debt), bounds.base);
        }
        Some(cap) if cap < bounds.base.raw() => {
            return (snap.total_debt, Bps::from(cap.max(0)));
        }
        Some(cap) => Bps::from(scaled_bonus.raw().min(cap)),
    };

    let ideal = liquidation_at_target(env, snap, bonus, curve.target_hf);

    let remaining_debt = snap.total_debt.checked_sub(env, ideal);
    if remaining_debt > Wad::ZERO && remaining_debt < Wad::from(BAD_DEBT_USD_THRESHOLD) {
        return (snap.total_debt, bonus);
    }

    (ideal, bonus)
}

/// Refreshes the liquidation threshold, bonus, and fees together. With debt,
/// changes favoring liquidators require hypothetical health factor >= 1.05.
pub(crate) fn apply_gated_liquidation_params(
    env: &Env,
    cache: &mut Context,
    account: &Account,
    hub_asset: &HubAssetKey,
    position: &mut AccountPosition,
    effective_config: &AssetConfig,
) {
    if favors_liquidator(position, effective_config)
        && !account.debt_free()
        && !clears_min_hf(
            env,
            cache,
            account,
            hub_asset,
            position,
            effective_config.liquidation_threshold,
        )
    {
        return;
    }

    position.liquidation_threshold = effective_config.liquidation_threshold;
    position.liquidation_bonus = effective_config.liquidation_bonus;
    position.liquidation_fees = effective_config.liquidation_fees;
}
