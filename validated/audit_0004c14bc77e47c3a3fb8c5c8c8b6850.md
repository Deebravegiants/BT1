## Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
The Sui report describes a bug class where a security check validates one thing (the payload hash) while a different, unguarded value (the payload itself, reusable by anyone) is what actually drives sensitive downstream behavior — breaking the intended binding between "who is authorized" and "what is being authorized." The Ruby analog is in `ShopifyAPI::Webhooks::Request`/`Registry`: the HMAC signature verifies only the raw request body, but the `shop` value that the webhook handler trusts and acts on is taken from an unsigned HTTP header, so the two are never bound to each other.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the body or the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the HMAC only over `verifiable_query.to_signable_string` (i.e., the body) using the app's single, shop-agnostic `Context.api_secret_key`: [3](#0-2) 

`Registry.process` performs exactly this check and then unconditionally forwards `request.shop` (the unverified header) to the app's handler: [4](#0-3) 

The equality the code implicitly assumes is:

`shop authenticated by HMAC == shop attributed to the handler (request.shop)`

But what the HMAC actually proves is only:

`hmac == HMAC-SHA256(api_secret_key, raw_body)`

Since `api_secret_key` is the same for every shop that installs the app (it is the app's `client_secret`, not a per-shop secret), any party who can obtain one validly-signed webhook body/HMAC pair for the app (e.g., by installing the app on a test/attacker-controlled store, which is legitimately possible since Shopify apps are installable by any merchant) can replay that exact `raw_body` + `hmac` pair while substituting an arbitrary `shop-domain` header for a victim shop. `HmacValidator.validate` will still pass because it never inspects the header, and `Registry.process` will call the handler with `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
This breaks the tenant-authentication boundary that host apps rely on: any app built on this gem that uses `WebhookMetadata#shop` (from `Registry.process`) to route, attribute, or store data implicitly trusts that the HMAC validated the shop along with the body. It did not. An attacker with only the ability to install the app once (an unprivileged/self-service action available to any Shopify merchant) can forge webhooks that appear to originate from a different, victim shop — a cross-tenant confusion/spoofing primitive purely through this gem's own webhook-processing code path.

### Likelihood Explanation
Likelihood is high for any app that (a) is publicly installable (typical for third-party Shopify apps) and (b) uses `Registry.process`/`WebhookMetadata.shop` to key data per shop, which is the documented pattern. The attacker needs no leaked secret, no privileged account, and no host-application bug — only the ability to install the app on any shop, capture one signed webhook, and replay it with a modified `shop-domain` header.

### Recommendation
Bind the `shop` value to the signed content: e.g., include the shop domain in the HMAC-signed material (or use a per-shop signing verification that cross-checks `request.shop` against a shop the app actually has an active session/access token for) before constructing `WebhookMetadata`, rather than trusting the unauthenticated header value.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, triggering a real webhook delivery with a valid `x-shopify-hmac-sha256` for some `raw_body`.
2. Attacker captures that `raw_body` and `hmac`.
3. Attacker sends a forged request to the app's webhook endpoint with the same `raw_body`/`hmac` but `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — passes, since only `raw_body` is checked (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. The handler receives `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to process/store the payload as if it came from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
