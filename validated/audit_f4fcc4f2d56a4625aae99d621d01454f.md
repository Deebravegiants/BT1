Webhook `shop-domain` (and `topic`/`webhook-id`) headers are trusted for tenant identity without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the webhook HMAC signs the body alone. The `shop-domain`, `topic`, and `webhook-id` values are read directly from unauthenticated HTTP headers and are never part of the signed material, yet `Registry.process` treats `request.shop` as the authenticated tenant identity when dispatching to the app's handler.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `hmac`, `topic`, `shop`, `api_version`, `webhook_id` are all pulled straight from request headers with no cryptographic binding to each other: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC exclusively against `verifiable_query.to_signable_string`, i.e. the raw body: [3](#0-2) 

`Registry.process` performs that HMAC check and then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` — none of which were covered by the HMAC — to build the metadata handed to the app's own webhook handler: [4](#0-3) 

This breaks the intended identity binding `shop authenticated == shop the handler is told to act on`. The HMAC only proves "this body was signed by the app's `client_secret`"; it proves nothing about which shop the body pertains to. Because a single app's `api_secret_key`/`client_secret` is shared across every shop that installs the app (it is not per-shop), any merchant who installs the app — including an attacker running their own free/dev store — can legitimately receive a webhook with a valid HMAC over some body. The attacker can then resend that exact body+HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a victim shop's domain. The signature still validates — because it never covered the shop header — and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
Any application built on this gem that uses `data.shop` from the webhook handler callback to key persistence, cache invalidation, or trigger shop-scoped side effects (a standard, documented pattern) can be made to process attacker-supplied topic/body content under a victim tenant's identity. This is a cross-tenant confusion vulnerability rooted entirely in this gem's `Request`/`Registry` design, not a host-app documentation-ignoring issue, satisfying the Critical "cross-tenant access" bar.

### Likelihood Explanation
Exploitation only requires the attacker to install the target app on any shop they control (trivial via a free Shopify dev/partner store) and to be able to send arbitrary HTTP requests to the app's public webhook endpoint — no access token, `client_secret`, or privileged account is needed. The signature check is fully satisfied by construction, so likelihood is high wherever an app relies on `data.shop`/`request.shop` for tenant identification, which is the gem's documented usage pattern.

### Recommendation
Include `shop-domain` (and ideally `topic`/`webhook-id`/`api-version`) in the HMAC-signed material used by `Request#to_signable_string`, or otherwise cryptographically bind the shop domain to the signature (e.g., by having `HmacValidator`/`Registry.process` compute the signature over a canonical string that concatenates all header fields, not just the body) so a valid signature can only be replayed for the exact shop, topic, and webhook id it was originally issued for.

### Proof of Concept
1. Attacker creates/owns Shop A and installs the target Shopify app (any shop can install a public app).
2. Shopify sends a webhook to the app for Shop A: body `B`, header `X-Shopify-Hmac-Sha256: H` where `H = HMAC_SHA256(client_secret, B)`, `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
3. Attacker captures this request (they control the endpoint traffic path since it's their own shop's webhook) and replays it to the app's webhook endpoint, only replacing `X-Shopify-Shop-Domain` with `shop-victim.myshopify.com` (topic/body/HMAC unchanged).
4. `Utils::HmacValidator.validate` recomputes the HMAC over `to_signable_string` (`= B`) and it matches `H`, so validation succeeds per `lib/shopify_api/utils/hmac_validator.rb` lines 12-31.
5. `Registry.process` (lib/shopify_api/webhooks/registry.rb lines 188-200) builds `WebhookMetadata` with `shop: "shop-victim.myshopify.com"` and dispatches it to the app's handler, which now acts as if the (attacker-controlled) body `B` originated from the victim shop.

          received_signature = verifiable_query.hmac
