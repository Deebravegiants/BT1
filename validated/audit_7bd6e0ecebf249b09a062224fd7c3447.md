### Title
Missing slippage protection in `EvmHost`'s native-fee swap path allows sandwich attacks against `dispatch()`/`fundRequest()` callers - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` let any unprivileged caller pay the ISMP dispatch/relayer fee in native tokens. When `msg.value > 0`, each function performs an on-chain UniswapV2 `swapETHForExactTokens` call to convert the caller's ETH into the exact `feeToken()` amount required, with no caller-supplied slippage bound and a `deadline` that is always `block.timestamp`.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 

the same pattern repeats in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest()`: [3](#0-2) 

Each call sends the full `msg.value` into `IUniswapV2Router02.swapETHForExactTokens`, requesting an exact `fee`/`amount` of `feeToken()` out, with `recipient = address(this)` (the `EvmHost` contract itself). The `deadline` argument is hard-coded to `block.timestamp`, so it provides no real protection at all (it can never expire within the same transaction). More importantly, the caller has no way to bound how much of their ETH the swap is allowed to consume beyond simply not sending more than they're willing to lose — `swapETHForExactTokens` will consume up to the full `msg.value` if the pool price is bad, and only refunds unused ETH to `msg.sender` of the swap call, which is `EvmHost`, not the original transaction sender (`_msgSender()`). There is no code afterward that forwards or accounts for that leftover ETH back to the caller in any of these three functions (contrast with `IntentGatewayV2.placeOrder`, which does track `msgValue -= amounts[0]` and refunds the remainder — that safeguard is absent here).

An attacker watching the mempool can sandwich the pending `dispatch()`/`fundRequest()` transaction: front-run to push the WETH→feeToken price up (making the exact-output swap consume more ETH to obtain the same `fee` tokens), let the victim's transaction execute — consuming a larger share of the victim's `msg.value` and leaving a smaller (or zero) refund, most of which lands as arbitrage profit to the attacker's back-run trade — then restore the price. Because `EvmHost` receives any leftover ETH from the router rather than the original caller, and there is no minimum-output/maximum-input parameter under caller control other than the size of `msg.value` itself, the caller has no way to protect against this price manipulation.

### Impact Explanation
Any unprivileged user dispatching a POST/GET request or funding an existing request with native token payment is exposed to sandwich attacks that inflate the ETH cost of acquiring the required `feeToken()` amount. The victim's excess ETH is extracted as MEV/arbitrage profit instead of being refunded, and because `EvmHost` (not the caller) is the recipient of any router refund, funds are also at risk of becoming stuck/donated to the host contract with no caller-facing reclamation path. This is a direct, reachable loss-of-funds vector on a core dispatch path used to pay for every cross-chain POST/GET request and fee top-up.

### Likelihood Explanation
High. `dispatch()` and `fundRequest()` are core, permissionless entry points exercised on every native-token-funded cross-chain request — no privileged role or unusual condition is required. Any observer of the public mempool can trivially sandwich these calls using the same DEX pool that `EvmHost` swaps through.

### Recommendation
Add caller-supplied slippage protection and a genuine deadline to these swap paths:
- Let the caller pass a `maxAmountIn`/acceptable price bound instead of implicitly capping at `msg.value`, and revert if the swap would exceed it.
- After the swap, explicitly refund any unspent ETH to `_msgSender()` (not leave it in `EvmHost`), mirroring the pattern already used in `IntentGatewayV2.placeOrder`.
- Use a real, caller-supplied `deadline` (or otherwise ensure the transaction cannot be replayed/held stale) rather than hardcoding `block.timestamp`.

### Proof of Concept
1. Attacker monitors the mempool for a `dispatch(DispatchPost)` call with `msg.value > 0` and a target `post.fee` in `feeToken()`.
2. Attacker front-runs with a large swap in the same WETH/`feeToken()` pool to move the price against the victim (raising the WETH cost of the fixed `post.fee` output).
3. Victim's transaction executes `swapETHForExactTokens(post.fee, path, address(this), block.timestamp)`; because of the manipulated price, it consumes a much larger portion of `msg.value` in ETH than it would have absent manipulation, and refunds only a small amount back to `EvmHost` (not the victim).
4. Attacker back-runs to restore the pool price, capturing the price difference as profit; the victim has permanently overpaid ETH relative to fair value, and the residual refund is stuck in `EvmHost` rather than returned to them.

    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();

        }
