### Title
Unbounded loop in `AncestryChain::ancestry` allows relayer-controlled GRANDPA headers to hang block execution - ([File: modules/consensus/grandpa/primitives/src/justification.rs])

### Summary
`pallet-ismp`'s free, unsigned `handle_unsigned` extrinsic accepts a GRANDPA `ConsensusMessage` and routes it to `verify_grandpa_finality_proof`, which walks a caller-supplied set of headers (`unknown_headers`) via `AncestryChain::ancestry`. That walk loops `while current_hash != base`, following each header's `parent_hash` through a `BTreeMap` built entirely from attacker-controlled headers, with no cycle detection and no bound on iterations.

### Finding Description
`AncestryChain::ancestry` is: [1](#0-0) 

The map (`self.ancestry`) is built directly from the untrusted `votes_ancestries` / `unknown_headers` vector supplied in the proof, with no validation that the headers form an acyclic chain rooted at `base`: [2](#0-1) 

An attacker can submit two (or more) headers `A`, `B` whose `parent_hash` fields point at each other's hash (`A.parent_hash = H(B)`, `B.parent_hash = H(A)`), neither of which equals `base`. Every lookup in the `while` loop succeeds (`Some`), so `current_hash` cycles between `H(A)` and `H(B)` forever — it never becomes `Err` (that only happens when a hash is *absent* from the map) and never equals `base`.

This function is reached from `verify_grandpa_finality_proof`, called **before** the GRANDPA commit signatures are even validated: [3](#0-2) 

`verify_grandpa_finality_proof` is invoked from the GRANDPA `ConsensusClient::verify_consensus` implementation used by `pallet-ismp`, and also from `verify_parachain_headers_with_grandpa_finality_proof`: [4](#0-3) [5](#0-4) 

`pallet-ismp` dispatches consensus messages via the free, unsigned `handle_unsigned` call, which any unprivileged actor (no fee, no signature) can submit and which is also evaluated during mempool `validate_unsigned`: [6](#0-5) [7](#0-6) 

This is the same bug class as CVE-2018-11771 (CWE-835, loop with unreachable exit condition on attacker-controlled data): the loop's only two exits (`current_hash == base` or a missing map entry) can both be permanently denied by crafting a self-referential header cycle, yielding an infinite loop instead of a bounded parse/verify failure.

### Impact Explanation
Because `handle_unsigned` is unsigned/free and is evaluated both in transaction-pool `validate_unsigned` and in block execution (`execute`), a single crafted GRANDPA consensus message with a two-header parent-hash cycle causes the runtime to spin forever inside `ancestry()`. In transaction-pool validation this can stall the node's tx-pool/RPC processing for any node that tries to validate the extrinsic; if included in a block, the same infinite loop runs during block execution, exhausting the block's weight/time budget and halting import/finalization for validators, i.e., a state-machine hang / chain-halt style denial of service reachable from a single relayed message with no signature or economic cost. This satisfies the "route unable to deliver messages"/availability impact criterion.

### Likelihood Explanation
High: the only requirements are two SCALE-decodable headers whose `parent_hash` fields point at each other and are included in `unknown_headers`/`votes_ancestries`, `base` differing from both cycle hashes, and no valid signature is even required for the loop to trigger (the hang occurs before signature verification in `verify_grandpa_finality_proof`). No privileged role, no fee, no prior state is needed — any relayer able to submit `handle_unsigned` (or trigger `validate_unsigned`) can construct this.

### Recommendation
Bound the `ancestry()` walk: track visited hashes and return an error (e.g., `NotDescendent`) as soon as a hash is revisited or once the number of hops exceeds `unknown_headers.len()` (the walk can never need more hops than the number of supplied headers in a valid, acyclic chain). Alternatively, validate at construction time that `AncestryChain`'s header set forms an acyclic chain terminating outside the map (i.e., that following `parent_hash` from any header eventually leaves the map) before allowing any `ancestry()` calls.

### Proof of Concept
1. Construct header `A` with `parent_hash = H(B)` (a placeholder/precomputed hash) and header `B` with `parent_hash = H(A)`, both distinct from any real chain state and from `base`.
2. Submit a GRANDPA `FinalityProof`/`ParachainHeadersWithFinalityProof` whose `unknown_headers` contains `{A, B}`, with `target` set so `finality_proof.block == target.hash()`, and `base.number() < consensus_state.latest_height` (or arrange `from`/`target` values) so that `headers.ancestry(...)` is invoked walking into the `{A,B}` cycle before signature checks fail.
3. Wrap this in `pallet_ismp::Call::handle_unsigned { messages: [Message::Consensus(...)] }` and submit as an unsigned extrinsic / let it pass through `validate_unsigned`.
4. Observe that `AncestryChain::ancestry` never returns, hanging the calling task/block-execution indefinitely — verifiable statically from the loop body at [8](#0-7)  which has no cycle/step bound.

	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
