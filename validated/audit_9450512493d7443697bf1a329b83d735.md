### Title
`describeWithdrawal` reports `completed` for a Direct-bridge `ft_transfer_call` withdrawal even when the receiver's `ft_on_transfer` refunds the tokens - (File: `packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts`)

### Summary
`DirectBridge.describeWithdrawal` unconditionally returns `{ status: "completed", txHash: args.tx.hash }` for any Direct/NEAR withdrawal, regardless of whether the underlying `ft_withdraw` intent used `ft_transfer` or `ft_transfer_call` (i.e., whether `msg` was set). When `routeConfig.msg` is attacker/integrator-supplied, `createWithdrawIntentPrimitive` builds an `ft_withdraw` intent with `msg` set and `min_gas` deliberately omitted, causing `intents.near` to invoke `ft_transfer_call` on the token contract. If the receiving contract's `ft_on_transfer` refunds or redirects the tokens, the NEAR transaction still succeeds, so `describeWithdrawal` still reports `completed` with the same `tx.hash`, even though the tokens were not credited to `destinationAddress`.

### Finding Description
The equality the SDK implicitly claims is: *"if `describeWithdrawal` returns `completed`, then `amount` of `assetId` has been credited to `destinationAddress`."* This equality can diverge when `msg` is present.

Path:
1. `IntentsSDK.processWithdrawal` → `createNearWithdrawalRoute(msg)` sets `routeConfig.msg` to attacker/integrator-controlled data.
2. `DirectBridge.createWithdrawalIntents` (`direct-bridge.ts:110-149`) passes `args.withdrawalParams.routeConfig?.msg` straight into `createWithdrawIntentPrimitive`.
3. `createWithdrawIntentPrimitive` (`direct-bridge-utils.ts:19-61`) builds the `ft_withdraw` intent: when `msg !== undefined`, it sets `msg: params.msg` and explicitly sets `min_gas: undefined` (comment: "Only set min_gas when msg is not provided ... gas consumption is unpredictable"), only logging a warning.
4. `intents.near` executes this `ft_withdraw` by calling the token's `ft_transfer_call(receiver_id, amount, msg)`. The receiving contract's `ft_on_transfer` may return the full amount (or a partial/full refund) as its designated behavior, or otherwise redirect/refund the transferred balance back via NEP-141 `ft_resolve_transfer` — this does not fail the enclosing NEAR transaction; the transaction succeeds regardless of the semantic outcome of the transfer.
5. `DirectBridge.describeWithdrawal` (`direct-bridge.ts:334-338`) does not inspect the transaction's cross-contract call outcome, refund amount, or emitted `ft_transfer_call` resolution — it always returns `completed` with `args.tx.hash`.
6. `validateWithdrawal` (`direct-bridge.ts:154-192`) only checks address format, that destination ≠ token contract, and that an explicit account exists — it does not check whether the destination account is a "plain" account (i.e., without a `ft_on_transfer` that could refund) versus a contract that consumes `ft_transfer_call` semantics.

Existing guards do not prevent this: `supports()` only checks `assetId`/`routeConfig` shape; `compareAddresses` only rejects self-transfers to the token contract; there is no `FeeExceedsAmountError` equivalent check for post-transfer settlement; no receipt/outcome inspection exists anywhere in `DirectBridge`. Contrast this with `PoaBridge.describeWithdrawal` (`poa-bridge.ts:313-343`), which polls solver-relay withdrawal status and distinguishes `PENDING`/`COMPLETED`/other (`failed`) states based on actual settlement data — Direct bridge has no analogous verification step.

### Impact Explanation
An integrator or downstream consumer of the SDK relying on `describeWithdrawal`/`waitForWithdrawalCompletion` to determine settlement finality will see `status: "completed"` and a valid `txHash` even though the destination never actually received the funds (they were refunded to the `intents.near` account or redirected elsewhere by the receiving contract's `ft_on_transfer` logic). This is a status/hash misreport that can cause an integrator to mark a withdrawal successful and, e.g., release a matching credit off-chain, while the tokens are still held by `intents.near` (owned by whichever account executed the withdrawal) or misrouted — a "reported success without actual settlement" condition. This matches the High-severity category: "a status or hash misreport making an integrator credit or refund twice." It's repeatable per call — any withdrawal using `msg` targeting a contract account that performs a refund path will trigger this every time.

### Likelihood Explanation
Preconditions: the attacker/integrator must set `routeConfig.msg` (a documented, exposed knob on `createNearWithdrawalRoute`) and point `destinationAddress` at a NEAR account that implements `ft_on_transfer` and returns a refund/redirect for the given `msg`. No special privileges required — the `msg` field and `destinationAddress` are both attacker-controllable per the question's "attacker controls" list. Cost is a single withdrawal request through the normal SDK flow. Feasibility is high because it requires no exploitation of the intents.near contract itself, only reliance on the standard, well-known NEP-141 `ft_transfer_call`/`ft_on_transfer` refund semantics, which the code path explicitly acknowledges ("min_gas is not set... gas consumption is unpredictable") but does not account for in status reporting.

### Recommendation
`DirectBridge.describeWithdrawal` should not report `completed` purely based on `tx.hash` existing for `ft_withdraw` intents that include `msg`. It should inspect the NEAR transaction's execution outcome/receipts (e.g., the `ft_resolve_transfer` return value / the amount actually transferred vs. refunded) before reporting `completed`, or otherwise clearly report a distinct status (e.g., `pending`/`unknown`) for `ft_transfer_call`-based withdrawals until settlement can be confirmed. At minimum, surface a warning/require explicit opt-in acknowledgment when `msg` is used with Direct bridge, and document that `completed` for this route only asserts that the NEAR transaction executed, not that funds were credited.

### Proof of Concept
```ts
// direct-bridge.msg-refund.test.ts
import { DirectBridge } from "./direct-bridge";
import { createWithdrawIntentPrimitive } from "./direct-bridge-utils";

it("builds ft_transfer_call intent without min_gas when msg is set", () => {
  const intent = createWithdrawIntentPrimitive({
    assetId: "nep141:usdt.tether-token.near",
    destinationAddress: "some-contract.near",
    amount: 1000000n,
    storageDeposit: 0n,
    msg: JSON.stringify({ action: "deposit" }),
  });

  expect(intent).toMatchObject({
    intent: "ft_withdraw",
    receiver_id: "some-contract.near",
    msg: JSON.stringify({ action: "deposit" }),
  });
  // Assert the equality being violated: min_gas is undefined for ft_transfer_call
  expect((intent as any).min_gas).toBeUndefined();
});

it("describeWithdrawal reports completed regardless of ft_on_transfer refund outcome", async () => {
  const bridge = new DirectBridge({ envConfig, nearProvider });

  // Simulate: tx succeeded on-chain, but ft_on_transfer refunded 100% of tokens
  // (no on-chain outcome inspection is performed by describeWithdrawal)
  const status = await bridge.describeWithdrawal({
    landingChain: Chains.Near,
    index: 0,
    withdrawalParams: {
      assetId: "nep141:usdt.tether-token.near",
      amount: 1000000n,
      destinationAddress: "some-contract.near",
      routeConfig: { route: RouteEnum.NearWithdrawal, msg: JSON.stringify({ action: "deposit" }) },
    },
    tx: { hash: "refunded-tx-hash", accountId: "user.near" },
  });

  // Violated equality: status is "completed" even though destination balance
  // was NOT credited by `amount` (it was refunded via ft_resolve_transfer).
  expect(status).toEqual({ status: "completed", txHash: "refunded-tx-hash" });
});
```
The first assertion documents the root cause (`min_gas` omitted, `msg` forwarded verbatim). The second demonstrates that `describeWithdrawal` cannot and does not distinguish a genuine settlement from a refunded `ft_transfer_call`, confirming the misreport.
