### Title
POA Bridge withdrawal status matched only by `assetId`, causing cross-withdrawal hash/status misreport in batch withdrawals of the same token - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal()` resolves the on-chain completion status of a specific withdrawal by looking up the POA bridge's withdrawal list for the parent NEAR tx and picking the entry via `findMatchingWithdrawal`, which matches **solely on `assetId`**, ignoring `index`, `destinationAddress`, and `amount`. When a batch withdrawal (`processWithdrawal`/`waitForWithdrawalCompletion` with an array of `WithdrawalParams`) contains two or more withdrawals of the same token in the same NEAR transaction, `describeWithdrawal` for withdrawal B can return the destination `transfer_tx_hash` and "completed" status that actually belongs to withdrawal A (or vice-versa).

### Finding Description
`findMatchingWithdrawal` is defined as: [1](#0-0) 

and is invoked from `describeWithdrawal` with only the `assetId`, explicitly ignoring the withdrawal `index`: [2](#0-1) 

The SDK's batch withdrawal completion path (`waitForWithdrawalCompletion`) calls `bridge.describeWithdrawal` per withdrawal index within the same `intentTx`, relying on the bridge to disambiguate between multiple withdrawals sharing the same NEAR tx hash. For `PoaBridge`, the only inputs passed into `getWithdrawalStatusWithRetry`/`findMatchingWithdrawal` are `tx.hash` and `assetId` — `index`, `destinationAddress`, and `amount` are present on `args.withdrawalParams` but never used to disambiguate. `Array.prototype.find` returns the **first** array element whose `near_token_id` matches, and the API response is explicitly documented as unsorted: "Response list is unsorted, so we match by assetId instead of index" [3](#0-2) . If two withdrawals in the batch withdraw the same token (e.g., to two different recipients), both entries share the same `near_token_id`, so `find` will return the same matching entry (the first same-asset entry in API order) for both withdrawal indices, regardless of which one it was actually invoked for.

The same unauthenticated matching pattern exists in the sibling implementation in `internal-utils`: [4](#0-3) 

The code comment itself acknowledges the limitation ("multiple withdrawals of the same token in a single transaction are not supported"), but this is enforced only by documentation, not by a guard that rejects/throws when duplicate same-asset withdrawals are detected in a batch — the equality that should hold ("the `txHash`/`status` reported for withdrawal at index N is the one actually belonging to that N") is silently broken instead.

### Impact Explanation
This breaks the "status/hash reported must equal the on-chain outcome for that specific withdrawal" invariant. In `sdk.processWithdrawal`'s batch mode, `waitForWithdrawalCompletion` returns a `destinationTx` array aligned by index to the caller's input `withdrawalParams` array [5](#0-4) . If two withdrawals share the same token/assetId in one batch (a legitimate use case — e.g., withdrawing the same token to two different destination addresses in one call), the integrator can receive the wrong `destinationTx` hash for one of the withdrawals: it may report withdrawal-to-address-B as completed with the transaction hash that actually paid address-A, or report both as "completed" using the same single hash even though only one destination actually received funds. An integrator that credits/marks a withdrawal complete based on this misreported hash could credit or reconcile the wrong withdrawal, or mark a withdrawal "complete" for a destination that has not actually received funds while the real destination transfer is not reflected — a status misreport matching the "High" impact category (status or hash misreport making an integrator credit or refund twice).

### Likelihood Explanation
This requires no malicious actor — it is triggered purely by an ordinary user/integrator constructing a legitimate batch withdrawal (`processWithdrawal({ withdrawalParams: [...] })`) containing two or more entries with the same `assetId` (same token) routed via the POA bridge, which is an explicitly supported code path (`isBatchMode` branches throughout `sdk.ts`). The bug is deterministic given that input pattern, not a race condition or opportunistic exploit, making it reasonably likely to occur for any integrator who batches multiple same-token withdrawals.

### Recommendation
Update `findMatchingWithdrawal` (in both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) to disambiguate using additional fields available in the withdrawal record (e.g., `address`/`account_id` and `amount`) in addition to `assetId`, and to consume matched entries so the same record cannot satisfy two different indices in the same batch. At minimum, throw an explicit unsupported-batch error when multiple same-asset withdrawals are detected in one NEAR transaction, rather than silently returning a possibly wrong match.

### Proof of Concept
1. Call `sdk.processWithdrawal({ withdrawalParams: [ {assetId: "nep141:x.omft.near", amount: 100n, destinationAddress: "addrA", feeInclusive: false}, {assetId: "nep141:x.omft.near", amount: 200n, destinationAddress: "addrB", feeInclusive: false} ] })` — a batch with two withdrawals of the same POA-bridged token to different destinations.
2. Once the underlying NEAR intent transaction executes, the POA bridge indexer records two entries under the same `withdrawal_hash` (`tx.hash`), both with `near_token_id` equal to `x.omft.near`, but different `data.address`/`data.transfer_tx_hash`.
3. `waitForWithdrawalCompletion` invokes `describeWithdrawal` once per index with the same `tx.hash` and the same `assetId` for both indices.
4. `findMatchingWithdrawal` returns the **first** array element matching `assetId` for both calls (as demonstrated by the existing test `"matches withdrawal by assetId, not by index"` at [6](#0-5)  which explicitly matches by asset regardless of index), so both `withdrawalParams[0]` (destined for `addrA`) and `withdrawalParams[1]` (destined for `addrB`) resolve to the same `transfer_tx_hash`/completion status — misreporting the outcome for whichever entry is not first in the unsorted API response.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
