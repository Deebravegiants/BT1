### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only. The `shop`, `topic`, `api_version`, and `webhook_id` values — all of which are read from unauthenticated HTTP headers and passed downstream as the tenant/routing identity for the webhook — are never included in the signed payload. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` as the tenant identifier for the webhook after validating only the body's HMAC, so the "shop the signature actually vouches for" and "the shop the application acts on" are two different, independently-controlled values.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` against `verifiable_query.hmac`, so it validates body integrity/authenticity but says nothing about which shop, topic, or webhook the body belongs to: [3](#0-2) 

`Registry.process` then uses this unauthenticated `request.shop` value directly as the tenant identity handed to the host application's handler, immediately after the HMAC check passes: [4](#0-3) 

The broken identity binding is: `shop covered by the HMAC (∅, since HMAC covers only raw_body) ≠ shop used to route/attribute the webhook (request.shop, taken from an unauthenticated header)`. Any body+HMAC pair that is valid for one shop is valid, verbatim, for every possible `shop-domain`/`topic`/`webhook-id` header value, because the signature computation never sees the headers.

### Impact Explanation
An attacker who operates any endpoint reachable by Shopify webhooks (e.g. a developer of an app using this gem, or anyone who has otherwise observed a single legitimate `(raw_body, hmac)` pair for any topic/shop) can resend that exact body and HMAC to the app's webhook endpoint while freely substituting the `shop-domain`, `topic`, and `webhook-id` headers. Since `HmacValidator.validate` still returns `true` (it never inspects the headers), `Registry.process` will happily hand the handler a `WebhookMetadata` claiming the body belongs to an arbitrary different shop/topic/webhook id. Host applications built on this gem's documented flow use `request.shop`/`data.shop` as the tenant key to decide which merchant's records to update, delete, or redact (e.g. GDPR `shop/redact`, `customers/redact`, `customers/data_request` mandatory webhooks). This allows cross-tenant data corruption/misattribution driven entirely by an unauthenticated header value, meeting the Critical "cross-tenant access" bar.

### Likelihood Explanation
Exploitation requires only observing/replaying one previously-delivered, validly-signed webhook body (no `api_secret_key`, no access token, and no privileged Shopify account needed) and then submitting an HTTP POST with modified headers to the app's webhook endpoint. No cryptographic secret needs to be broken because the headers were never part of what the secret protects.

### Recommendation
Include `shop`, `topic`, and any other header-derived routing fields in the signable string used for HMAC verification (or otherwise cryptographically bind them, e.g. by validating the `shop-domain` header against the Shopify-issued webhook subscription metadata), so that a valid signature can only be replayed against the exact shop/topic/webhook it was issued for.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com`, topic `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (a valid signature of `B`).
2. Attacker resends the identical `B`/`H` to the same endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (a different, unrelated installed shop) and/or a different `x-shopify-topic`/`x-shopify-webhook-id`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `@raw_body` and succeeds: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata` attributing body `B` to `shop-b.myshopify.com`/attacker-chosen topic, even though the signature never certified that association.
