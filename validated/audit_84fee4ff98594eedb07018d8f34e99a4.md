## Analysis Result

### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop` attribute used for tenant attribution is read from a separate, unsigned HTTP header. Any tenant of a multi-tenant app that can legitimately trigger a webhook to their own shop (a normal, unprivileged capability) obtains a body+HMAC pair valid under the app's shared `api_secret_key`, and can replay it while forging the shop-domain header to impersonate any other merchant.

### Finding Description
`HmacValidator.validate` verifies a `VerifiableQuery` by computing `HMAC(secret, verifiable_query.to_signable_string)` and comparing it to `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body, never the shop domain: [2](#0-1) 

Meanwhile `shop` is parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely outside the signed material: [3](#0-2) 

`Registry.process` validates the HMAC over the body, then forwards the *unverified* `request.shop` straight into the tenant-scoped `WebhookMetadata` handed to the app's handler: [4](#0-3) 

The identity binding that should hold is: `shop attributed to the event == shop that produced the HMAC-signed body`. Because the header is never included in the signable string, this equality is never enforced by the gem — the HMAC only proves "some request signed with this app's secret produced this body," not "shop X produced this body."

### Impact Explanation
An app's `api_secret_key` is shared across every shop/tenant that installs the app. Any ordinary merchant (an unprivileged actor with respect to other tenants) can trigger a legitimate webhook to their own shop and capture the resulting `(raw_body, x-shopify-hmac-sha256)` pair — this requires no special access, secret, or token. They can then replay that exact validated body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (it never looked at the header), and `Registry.process` dispatches the payload to the handler labeled with the victim's shop, so the host application processes attacker-controlled data as if it originated from a different tenant — a cross-tenant integrity/access violation.

### Likelihood Explanation
Likelihood is high for any app relying solely on this gem's `Registry.process`/`HmacValidator` for webhook trust decisions, since obtaining a valid signed payload requires nothing more than being any existing customer of the app (no `api_secret_key`, access token, or privileged account needed) — only the intrinsic capability of installing the app and receiving one of its own webhooks.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signable material, or independently authenticate the shop-domain header against a value the gem can trust (e.g., require callers to pass the expected shop and compare it, or include the header bytes in the HMAC computation) so that `HmacValidator.validate` proves the entire tuple `(shop, topic, body)` was signed together, not the body alone.

### Proof of Concept
1. Attacker (tenant `shop-a.myshopify.com`) causes any webhook subscription to fire for their own shop, capturing `raw_body` and the resulting `X-Shopify-Hmac-Sha256` header — both fully legitimate and independently computable/obtainable because they own that shop.
2. Attacker POSTs the same `raw_body` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: shop-victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `shop-victim.myshopify.com` [3](#0-2) .
4. `Utils::HmacValidator.validate(request)` recomputes HMAC over `raw_body` only and it matches (secret is shared across tenants), so validation succeeds [5](#0-4) .
5. `Registry.process` invokes the handler with `shop: request.shop` = `shop-victim.myshopify.com`, so the host app processes forged data attributed to the victim tenant [4](#0-3) .
