### Title
Webhook shop/topic identity is not bound by the HMAC signature, allowing cross-tenant webhook impersonation - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then dispatches the handler using the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers that are never included in the signed material. Because the identity fields the handler trusts are not covered by the same binding that authenticates the request, an attacker who possesses any one genuine `(body, hmac)` pair can replay it with forged header values to make the app process a webhook as if it came from a different shop or topic.

### Finding Description
`ShopifyAPI::Webhooks::Request` derives all identity-bearing accessors from headers: [1](#0-0) 

but its `to_signable_string`, which is the only input fed into the HMAC check, returns just the raw body: [2](#0-1) 

`Registry.process` verifies the HMAC and then immediately builds `WebhookMetadata` from `request.shop`, `request.topic`, and `request.webhook_id` — none of which participated in the signature: [3](#0-2) 

`Utils::HmacValidator.validate` only ever checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`: [4](#0-3) 

The binding that should hold is:
`hmac == HMAC(secret, body ∥ shop ∥ topic)` ⇒ `handler.shop == authenticated_shop` and `handler.topic == authenticated_topic`.

What is actually enforced is only:
`hmac == HMAC(secret, body)`,

so `shop` and `topic` are accepted from unauthenticated header bytes and passed straight to `WebhookMetadata`/the handler as if they were verified. Any party who has obtained one legitimate `(raw_body, hmac)` pair — trivially available to any unprivileged user who installs the app on their own store and receives one real webhook delivery — can resend that exact body/hmac pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` and `x-shopify-topic` headers for a different tenant/topic of their choosing. The HMAC check in `HmacValidator.validate` still succeeds because it never inspects those headers, and `Registry.process` hands the handler a `WebhookMetadata` claiming an arbitrary `shop`/`topic` that the merchant-app code will treat as authenticated.

### Impact Explanation
This breaks the tenant/topic identity binding the whole webhook-processing flow depends on. A host application's webhook handler (which typically keys data lookups, order updates, or session records off `data.shop`) can be made to act on data under the identity of an arbitrary shop domain chosen by the attacker, even though the cryptographic check reports success. This is a cross-tenant confusion vulnerability: the app believes it received an authenticated event from shop/topic X while it was actually replayed by an attacker under shop/topic Y.

### Likelihood Explanation
The prerequisite — obtaining a single legitimate `(body, hmac)` webhook payload — requires no privileged credentials, secrets, or interception; any internet user can install the app on a free/dev store to receive one. Sending the modified headers to the app's public webhook endpoint (which must be internet-reachable for Shopify to deliver to it in the first place) is trivial afterward, making this a fully unprivileged, remotely exploitable path through code entirely inside this gem (`Request`, `HmacValidator`, `Registry.process`).

### Recommendation
Bind the identity headers into the material that is HMAC-verified (or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the signed body), and have `Registry.process` reject any webhook whose header-derived shop is not the expected/registered shop for the session, rather than trusting header values that were never part of the signed payload.

### Proof of Concept
1. Install the target app on any shop `attacker.myshopify.com` (unprivileged, self-service action) and capture one real webhook delivery: `raw_body = B`, header `x-shopify-hmac-sha256 = H` (valid for `B` under the app's `api_secret_key`).
2. Craft a new HTTP POST to the app's public webhook endpoint with the *same* `raw_body = B` and `x-shopify-hmac-sha256 = H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com` and `x-shopify-topic: <topic-of-choice>`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers (only presence is checked, per `lib/shopify_api/webhooks/request.rb` lines 46-59), and `Utils::HmacValidator.validate` succeeds because it only recomputes the HMAC over `B` (`lib/shopify_api/utils/hmac_validator.rb` lines 26-31).
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-200) invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: <chosen topic>, ...)`, even though the underlying signed body never came from that shop/topic.

          received_signature = verifiable_query.hmac
