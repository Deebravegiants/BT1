### Title
Deflationary/fee-on-transfer underlying tokens cause under-collateralized locking in `WrappedHyperFungibleToken.send()`, enabling escrow drain across peer chains - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken` (and its upgradeable variant) implements a lock-and-mint/unlock bridge model: `send()` locks `params.amount` of the underlying ERC20 on the source chain and dispatches an ISMP message carrying that same `params.amount`; `onAccept()` on the peer chain unconditionally releases `message.amount` of the underlying token to the beneficiary. If the configured `_underlying` token charges a transfer fee (deflationary/fee-on-transfer token), the contract actually receives less than `params.amount`, but the dispatched message and the resulting release on the peer chain still use the full, unreduced `params.amount`.

### Finding Description
In `send()`, the contract calls `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` and then immediately builds the dispatch message using the same `params.amount`, without ever checking the actual balance delta: [1](#0-0) 

Compare this to `IntentGatewayV2.sol`, which was hardened against exactly this class of bug by measuring `balanceOf` before and after every `safeTransferFrom` and mutating the escrowed/committed amount to the actually-received value: [2](#0-1) 

`WrappedHyperFungibleToken` has no equivalent measurement. The peer-chain `onAccept()` then releases the full, unreduced `message.amount` from its own token reserve: [3](#0-2) 

The same pattern (no before/after balance check on `send`, full-amount release on `onAccept`) exists in the upgradeable variant as well: [4](#0-3) 

Note this is different from `HyperFungibleToken`/`HyperFungibleTokenUpgradeable` (the pure burn/mint variant), which is immune to this class of bug because it mints/burns its own accounting-based supply rather than transferring an external, potentially fee-charging ERC20: [5](#0-4) 

### Impact Explanation
Each deployment of `WrappedHyperFungibleToken` per chain acts as an isolated lock/release pool for the underlying token, with no shared custody across chains. If a deflationary/fee-on-transfer token is configured as `_underlying` (or later becomes fee-charging via an upgrade to the token's own logic, e.g. via a fee-toggle deflationary token), every `send()` locks less than `params.amount`, yet the destination chain releases the full `params.amount`. This overstates locked funds on the destination side relative to the source-side escrow. Repeated round-trips (or configuration with an existing deflationary token) will progressively drain the local underlying-token reserve on the affected chain below what is required to honor later legitimate `onAccept` releases and `onPostRequestTimeout` refunds, permanently freezing/breaking redemption for other users' funds once the pool is exhausted — a form of unbacked release/insolvency of the bridge's escrow.

### Likelihood Explanation
This requires the owner to configure `_underlying` to a fee-on-transfer/deflationary ERC20 (via `configure()`), which is plausible since the contract is explicitly designed as a generic "wrapper for existing ERC20 tokens" and documentation doesn't restrict token types. Any unprivileged user calling the ordinary `send()` path triggers the shortfall — no special privileges are needed to trigger the underlying accounting break once such a token is configured.

### Recommendation
Mirror the fix already applied in `IntentGatewayV2.sol`: measure `IERC20(_underlying).balanceOf(address(this))` immediately before and after `safeTransferFrom` in `send()`, and use the actual received delta (not `params.amount`) when building the dispatched `Message.amount`. Apply the same fix to `WrappedHyperFungibleTokenUpgradeable`.

### Proof of Concept
1. Owner deploys `WrappedHyperFungibleToken` and calls `configure()` with `_underlying` set to a fee-on-transfer token (e.g., 1% fee per transfer) and registers a peer chain via `addChain()`.
2. User calls `send({dest, to, amount: 1000e18, ...})`. `safeTransferFrom` pulls 1000e18 but, due to the transfer fee, the contract's balance only increases by 990e18.
3. `send()` still dispatches `Message{amount: 1000e18}` to the destination chain (per `_buildDispatchPost`, `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol` lines 234-253).
4. On the destination `WrappedHyperFungibleToken` instance, `onAccept()` executes `IERC20(_underlying).safeTransfer(beneficiary, 1000e18)`, releasing 10e18 more than was ever actually locked on the source chain for this transfer.
5. Repeating this bleeds the destination-chain reserve, eventually causing later legitimate `onAccept`/`onPostRequestTimeout` calls to revert (insufficient balance) — freezing funds for other users.
