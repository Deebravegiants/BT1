The cache key itself is built by `getCachePath`, which only appends a `/multisig/{index}` segment when `multisigDataIndex !== undefined` [5](#0-4) .

### Title
Stale multisig receive address served from cache after cosigner-set changes when `multisigDataIndex` is omitted - ([File: features/address-provider/module/address-provider.js])

### Summary
`getAddress` caches multisig addresses under a key that omits the resolved `multisigDataIndex` whenever the caller does not explicitly pass one. The actual multisig data set used to derive the address is chosen dynamically inside `#getMultisigAddress` (latest entry, i.e., `multisigWallet.data.length - 1`, for multi-address assets), but this resolved index is never propagated to the cache key. As a result, the address cache conflates all "default" multisig data sets under one key, regardless of which cosigner set was actually used to derive the cached value.

### Finding Description
In `AddressProvider.getAddress` [6](#0-5) , the destructured `multisigDataIndex` from the caller's options is used directly for both the pre-derivation cache lookup (line 110) and the post-derivation cache write (line 150). When the caller omits `multisigDataIndex` (the "null" case, analogous to null basis points), `#getMultisigAddress` internally computes a concrete default index based on the *current* length of `multisigWallet.data` [1](#0-0) , but this is a local variable reassignment inside that helper — it is not returned to or reflected back in `getAddress`'s cache operations.

Consequently, `getCachePath` builds a key without any `/multisig/{index}` segment whenever the input `multisigDataIndex` is `undefined` [7](#0-6) , even though the derived address actually corresponds to a *specific* (and potentially changing) multisig data entry. If a new multisig data set is later appended (e.g. after adding/removing a cosigner or generating a new cosigner configuration for `multipleAddresses` assets), a subsequent call to `getAddress` with `multisigDataIndex` still omitted will hit the stale cache entry keyed the same way, and return the address derived from the *old* cosigner set instead of re-deriving against the new (correct) latest multisig data.

### Impact Explanation
Because Hydra is a multi-asset wallet SDK, a user relying on `getReceiveAddress`/`getDefaultAddress` for a multisig wallet account without specifying `multisigDataIndex` could be shown (and could receive funds at) an address tied to an outdated cosigner set after the multisig configuration changes. This is a direct wallet-fund-safety issue: funds sent to a stale multisig address may become inaccessible or spendable only by cosigners from the old configuration, rather than the currently intended one.

### Likelihood Explanation
This requires: (1) a multisig wallet account, (2) the `multisigDataIndex` parameter being omitted (the common/default calling pattern based on the test fixtures, e.g. `features/address-provider/__tests__/module/seed/bitcoin.test.js:784-802`), (3) `useCache: true` being used for a repeat address fetch, and (4) the underlying multisig cosigner data changing (new entry appended to `multisigWallet.data`) between calls. This is a plausible but non-trivial sequence of application-level events rather than an attacker-controlled input, since `multisigDataIndex` and multisig data updates are typically wallet-internal state, not directly attacker-supplied.

### Recommendation
Propagate the resolved `multisigDataIndex` from `#getMultisigAddress` back to `getAddress` (e.g., have it return the resolved index alongside the `Address`), and use that resolved value — not the original possibly-`undefined` value — when constructing the cache key for both the `get` and `set` calls in `getAddress`. This ensures cache entries are always keyed by the concrete multisig data index that was actually used to derive the address.

### Proof of Concept
1. Set up a multisig wallet account with one multisig data entry (`multisigWallet.data.length === 1`) for a `multipleAddresses` asset.
2. Call `addressProvider.getAddress({ ..., walletAccount: multisigWalletAccount, useCache: true })` without `multisigDataIndex`. `#getMultisigAddress` resolves `multisigDataIndex = 0` and derives address `A`. `getAddress` caches `A` under a key without any multisig index segment.
3. Append a second multisig data entry to `multisigWallet.data` (simulating a cosigner-set update), so a fresh (uncached) call would resolve `multisigDataIndex = 1` and derive a different address `B`.
4. Call `addressProvider.getAddress({ ..., walletAccount: multisigWalletAccount, useCache: true })` again, still without `multisigDataIndex`. Because the cache key is identical to step 2, the cached (stale) address `A` is returned instead of the correct current default address `B`.
