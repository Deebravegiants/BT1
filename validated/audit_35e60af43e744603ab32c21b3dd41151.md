### Title
Third-party dust `supply` force-restamps a victim account's stored LTV/LT/bonus/fee without owner authorization - (File: contracts/controller/src/risk/params.rs)

### Summary
`Controller::supply` explicitly allows third parties to top up *existing* supply positions on accounts they do not own. The supply path runs `merge_supply_leg` → `refresh_supply_risk_params`, which unconditionally overwrites the position's stored `loan_to_value` from the live spoke listing and, through `apply_gated_liquidation_params`, also overwrites `liquidation_threshold`, `liquidation_bonus`, and `liquidation_fees`. An unprivileged address can therefore modify stored risk parameters of another user's account — the same shape as the Airflow flaw where an endpoint authorized for one purpose (notes/top-up) silently mutates unrelated persisted fields (DAG-run details / the position's stamped risk tuple).

### Finding Description
- `supply(caller, account_id, spoke_id, assets)` delegates to `positions::process_supply`; per the doc comment, "Third parties may only top up existing supply positions" — no owner/delegate check is required for adding to an existing leg [1](#0-0) .
- Every supply leg refreshes the stored risk tuple: `refresh_supply_risk_params` sets `position.loan_to_value = effective_config.loan_to_value` unconditionally, and in `FullTuple` scope calls `apply_gated_liquidation_params` [2](#0-1) .
- The gate only protects liquidator-favoring changes for accounts with debt, requiring hypothetical HF ≥ 1.05 under the new LT; debt-free accounts take the new tuple unconditionally, and the LTV write is never gated [3](#0-2) .
- The victim's HF, borrow limit (`min(LTV, LT)`-weighted collateral), and liquidation terms are all computed from these *stored* position values, not the live listing — so overwriting them via a 1-wei supply directly rewrites the victim's risk profile. The dedicated `update_account_threshold` endpoint is permissionless for the same purpose, but the supply path additionally lets the attacker pick *which single asset leg* gets restamped by supplying dust to it.

### Impact Explanation
An unprivileged address can:
1. Identify a victim account with a supply position in asset X.
2. Call `supply(attacker, victim_account_id, victim_spoke_id, [(X, 1)])` to add 1 wei to X.
3. This triggers `merge_supply_leg` → `refresh_supply_risk_params`, overwriting the victim's stored LTV, LT, bonus, and fee for X to the current listing values.
4. If the listing has been tightened (lower LT, lower bonus, higher fee) since the victim's position was created, the victim's health factor and liquidation terms are immediately degraded.
5. If the victim is debt-free, the gate does not apply; if the victim has debt but the new LT is favorable to liquidators and the hypothetical HF is below 1.05, the LT is not updated — but the LTV *always* updates, and the bonus/fee update is skipped only if the gate fails, not if the LTV update alone would harm the victim.
6. The attacker can selectively restamp only the assets they choose, unlike `update_account_threshold` which refreshes all listed assets at once.

This allows theft of unclaimed yield (liquidation bonus) or temporary freezing of funds (by degrading HF to liquidatable without the victim's consent).

### Likelihood Explanation
- The supply path is explicitly documented to allow third-party top-ups, so the authorization is intentional.
- The refresh logic is also intentional: positions store their stamped tuple to survive listing changes, and the supply path refreshes them to keep them current.
- However, the combination creates an unintended side effect: a third party can force a refresh on a victim's account without the victim's authorization, and the refresh can degrade the victim's terms.
- The gate on liquidator-favoring changes is incomplete: it does not protect the LTV, and it does not protect debt-free accounts.
- An attacker needs only to know the victim's account ID and spoke ID (both are enumerable or guessable), and the victim's supply position in one asset (observable via `get_account_positions`).

### Recommendation
Restrict the supply path to owner/delegate authorization when adding to an *existing* position, or skip the risk-parameter refresh when the supply is from a third party. Alternatively, apply the HF gate to all risk-parameter updates, including LTV, and extend it to debt-free accounts if the intent is to prevent any degradation.

pub(crate) fn refresh_supply_risk_params(
    env: &Env,
    cache: &mut Context,
    account: &Account,
    hub_asset: &HubAssetKey,
    position: &mut AccountPosition,
    effective_config: &AssetConfig,
    scope: RiskRefreshScope,
) -> bool {
    let before = *position;
    position.loan_to_value = effective_config.loan_to_value;
    if scope == RiskRefreshScope::FullTuple {
        apply_gated_liquidation_params(env, cache, account, hub_asset, position, effective_config);
    }
    *position != before
}

pub(crate) fn apply_gated_liquidation_params(
    env: &Env,
    cache: &mut Context,
    account: &Account,
    hub_asset: &HubAssetKey,
    position: &mut AccountPosition,
    effective_config: &AssetConfig,
) {
    if favors_liquidator(position, effective_config)
        && !account.debt_free()
        && !clears_min_hf(
            env,
            cache,
            account,
            hub_asset,
            position,
            effective_config.liquidation_threshold,
        )
    {
        return;
    }

    position.liquidation_threshold = effective_config.liquidation_threshold;
    position.liquidation_bonus = effective_config.liquidation_bonus;
    position.liquidation_fees = effective_config.liquidation_fees;
}

/// Detects a lower threshold or fee, or a higher bonus, than the stored tuple.
fn favors_liquidator(position: &AccountPosition, effective_config: &AssetConfig) -> bool {
    effective_config.liquidation_threshold.raw() < position.liquidation_threshold.raw()
        || effective_config.liquidation_bonus.raw() > position.liquidation_bonus.raw()
        || effective_config.liquidation_fees.raw() < position.liquidation_fees.raw()
}
