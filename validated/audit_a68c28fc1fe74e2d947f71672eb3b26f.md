### Title
Unreturned-value ERC20 `.transfer()` in intent-order dust sweep can permanently strand output tokens in `CallDispatcher` - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The `IntentGatewayV2` order-fill flow sweeps residual output tokens out of the untrusted `CallDispatcher` back to the gateway by encoding a raw `IERC20.transfer.selector` call and routing it through `CallDispatcher.dispatch`. Neither the encoder (`IntentsBase._execute`) nor the executor (`CallDispatcher.dispatch`) inspects the boolean return value of `transfer` — they only check that the low-level `call` did not revert. For any ERC20 that signals failure by returning `false` instead of reverting (the exact bug class from the referenced report), the sweep call "succeeds" from `CallDispatcher`'s perspective even though no tokens moved, the `DustCollected` event is emitted for an amount that was never actually received, and the tokens remain permanently stuck inside the stateless, ownerless `CallDispatcher` contract.

### Finding Description
`IntentsBase._execute` (called from the fill path for orders carrying output calldata) builds a sweep call for every non-native output token still held by the dispatcher after postdispatch execution: [1](#0-0) 

This is dispatched through: [2](#0-1) 

`CallDispatcher.dispatch` executes each call with a plain low-level `call` and only reverts if the call itself reverts — it never decodes/validates the ERC20 boolean return value: [3](#0-2) 

Unlike the `placeOrder` predispatch-sweep path in `IntentGatewayV2.sol`, which independently re-measures `balanceOf` before/after the sweep to compute the actually-received amount (and thus tolerates a silently-failing `transfer`): [4](#0-3) 

the postdispatch dust-sweep in `_execute` has **no such balance verification**. It unconditionally emits `DustCollected(token, balance)` for the pre-transfer balance and moves on: [5](#0-4) 

If `token` is a non-standard ERC20 that returns `false` on failure instead of reverting (e.g. legacy tokens like ZRX/OMG-style implementations, or a token deliberately crafted this way by the order creator, who freely chooses the output token address in `Order.output.assets`), the `call` inside `CallDispatcher` succeeds (`success == true`), so `dispatch()` does not revert, `_execute` proceeds normally, and the gateway's accounting (`DustCollected` event / protocol bookkeeping) records tokens that were never actually transferred. The real tokens stay in `CallDispatcher`, which has no admin, no sweep, and no recovery mechanism — it is a generic, ownerless executor shared across every order. The tokens are permanently unrecoverable.

The exact same unchecked-selector pattern is used in the analogous `placeOrder`-time output-input transfer helper and mirrored again in the Tron deployment: [6](#0-5) 

but those paths at least gate on a subsequent `balanceOf`-based `dust = balance - requiredAmount` check for escrow purposes, so the impact is narrower there; the postdispatch `_execute` dust-sweep has no equivalent safety net at all.

### Impact Explanation
This is a concrete permanent-freezing-of-funds bug reachable from a normal, unprivileged order-fill flow (no governance/admin/relayer trust required beyond the standard solver/filler role). Output tokens legitimately owed to the protocol (as dust) or transiently routed through `CallDispatcher` during postdispatch calldata execution can become permanently locked in `CallDispatcher` with no recovery path, since the contract holds no owner-only withdrawal function and its balance is invisible to the gateway's escrow/dust accounting once the sweep call is (incorrectly) treated as successful.

### Likelihood Explanation
Any order creator can specify an arbitrary ERC20 as an output asset (`Order.output.assets[i].token`), including tokens with non-standard, non-reverting failure semantics. Combined with postdispatch calldata (`order.output.call`), which is a documented, normal feature of the intent gateway, triggering the vulnerable `_execute` sweep path requires nothing beyond a single order placement plus a single fill — both routine, permissionless operations. No special privilege, race condition, or unusual chain state is needed, though it does require the order to use a token with the specific non-reverting return-false failure mode.

### Recommendation
Use OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` (already used elsewhere in `IntentsBase.sol`, e.g. `_withdraw` and `_sweepDust`) instead of raw `abi.encodeWithSelector(IERC20.transfer.selector, ...)` for the dust-sweep calls, or have `CallDispatcher.dispatch` decode and validate ERC20 return data for calls targeting `transfer`/`transferFrom` selectors. Alternatively, mirror the `placeOrder` predispatch path by measuring `balanceOf` before and after the sweep and reverting (or reconciling dust accounting) if the actual balance change does not match the expected amount, rather than trusting the low-level call's success flag alone.

### Proof of Concept
1. Deploy/select an ERC20 token `T` whose `transfer` function returns `false` on failure instead of reverting (e.g., insufficient allowance/blocklist condition that the implementation swallows rather than reverts — this class of token exists in production, per the cited report).
2. Place an intent order with `Order.output.assets` including `T` and a non-empty `Order.output.call` (postdispatch calldata), per the documented calldata-execution feature.
3. A solver fills the order; `IntentsBase._execute` runs the postdispatch call via `CallDispatcher.dispatch(order.output.call)`, after which some `T` balance remains on `CallDispatcher`.
4. `_execute` builds a sweep `Call` with `abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)` and dispatches it via `ICallDispatcher(dispatcher).dispatch(abi.encode(finalCalls))`.
5. Craft/select `T` such that this particular `transfer` invocation returns `false` (e.g., destination-based restriction) without reverting. `CallDispatcher`'s `(bool success,) = to.call(...)` sees `success == true` and does not revert.
6. `DustCollected(token, balance)` is emitted and the gateway's bookkeeping assumes the funds were retrieved, while `T`'s tokens remain permanently stranded in `CallDispatcher` with no function available to recover them.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
