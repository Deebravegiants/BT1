### Title
SSRF with app credentials via unvalidated `shop` in `ShopifyAPI::Auth::Oauth.validate_auth_callback` - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the access-token request host directly from `auth_query.shop` without ever passing it through `Utils::ShopValidator.sanitize!`, unlike every other credential-exchange entry point in the gem (`client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb`, which derives `shop` from a cryptographically signed JWT `dest` claim). This breaks the intended identity binding: *the shop that Shopify's HMAC signs* should equal *the shop whose host receives the app's `client_secret`*, but the code never independently constrains the shape/domain of that value before using it to build the outbound request URI.

### Finding Description
In `lib/shopify_api/auth/oauth.rb`: [1](#0-0) 

`validate_auth_callback` only checks the HMAC signature over the query (`Utils::HmacValidator.validate(auth_query)`) and the `state` nonce. It never calls `Utils::ShopValidator.sanitize!(auth_query.shop)` — the same helper that `client_credentials.rb` and `refresh_token.rb` explicitly use before constructing a session/host: [2](#0-1) [3](#0-2) 

`auth_query.shop` is used to build `null_session = Auth::Session.new(shop: auth_query.shop)`, which is then handed to `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`. `HttpClient#initialize` derives the outbound request host directly from `session.shop` when `Context.api_host` is not configured: [4](#0-3) 

The POST body sent to that host includes the app's `client_secret` and OAuth `code`: [5](#0-4) 

The binding this breaks, expressed as an equality that must hold but isn't enforced independently of the signature check: `host-that-receives-client_secret == shop-value-Shopify-actually-authenticated-as-a-valid-*.myshopify.com-domain`. The code implicitly relies solely on `HmacValidator` to guarantee that `shop` is a legitimate value, with no defense-in-depth check that the string is actually a `myshopify.com`/`shopify.com`/`myshopify.io`/`spin.dev`/`shop.dev` host as `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` defines.

Note: `Utils::HmacValidator.validate` does cryptographically bind `shop` (it's part of `AuthQuery#to_signable_string`), which is the primary defense here. I was not able to fully establish, purely from static analysis of this gem, a request-forgery path that produces a *valid* HMAC for an attacker-chosen non-Shopify `shop` value without possession of `api_secret_key` — that would require Shopify's own signing infrastructure to be tricked, which is outside this gem's code. This weakens confidence that the missing `ShopValidator.sanitize!` call is independently exploitable to full SSRF given HMAC is otherwise intact.

### Impact Explanation
If the HMAC check could be satisfied (or bypassed) with an attacker-controlled `shop` value — e.g., through any weakness in `HmacValidator`, secret rotation edge cases, or a caller that skips/misuses the validation — the missing `ShopValidator.sanitize!` call means the gem would happily construct `https://{attacker-controlled-host}/admin/oauth/access_token` and POST the app's `client_id`, `client_secret`, and the victim's OAuth `code` to that host. That is SSRF carrying the app's `client_secret`, matching the "High — SSRF with the app's credentials" impact category. This is a defense-in-depth gap: every other OAuth-adjacent credential exchange path in this gem (`client_credentials.rb`, `refresh_token.rb`) explicitly sanitizes `shop` against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before ever building a session/host, while `validate_auth_callback` relies solely on HMAC verification for this same guarantee.

### Likelihood Explanation
Low-to-moderate as a standalone exploit today, because `Utils::HmacValidator.validate` does bind `shop` into the signed payload and no HMAC bypass was found in the reviewed code. However, likelihood should be considered non-trivial for a defense-in-depth/regression standpoint: it is inconsistent hardening across the codebase (three of four similar OAuth/token paths sanitize `shop`; this one does not), so any future change that weakens or misapplies HMAC validation (e.g., accidental old-secret fallback logic, a host application that calls `validate_auth_callback` with unauthenticated data, or a future secret-rotation bug) would immediately become a full SSRF/credential-leak vector with no secondary check to catch it.

### Recommendation
Add a `Utils::ShopValidator.sanitize!(auth_query.shop)` call at the start of `validate_auth_callback` (mirroring `client_credentials.rb`/`refresh_token.rb`), and use the sanitized value everywhere `auth_query.shop` currently is used to construct `null_session` and the final `Session.from(shop: ...)`. This ensures the shop host is independently constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` regardless of what the HMAC check does or does not guarantee, closing the defense-in-depth gap.

### Proof of Concept
Not able to produce a working end-to-end PoC within this gem's code alone: constructing a request that passes `Utils::HmacValidator.validate` for an attacker-chosen `shop` requires knowledge of `Context.api_secret_key`, which is explicitly out of scope per the rules ("anything requiring `api_secret_key` ... a privileged account"). The concrete, reviewable evidence is the code-level inconsistency:
- `validate_auth_callback` (`lib/shopify_api/auth/oauth.rb:60-82`) — no `ShopValidator` call.
- `client_credentials` (`lib/shopify_api/auth/client_credentials.rb:19-26`) — calls `Utils::ShopValidator.sanitize!(shop)`.
- `refresh_token` (`lib/shopify_api/auth/refresh_token.rb:18-25`) — calls `Utils::ShopValidator.sanitize!(shop)`.
- `token_exchange` derives shop from a JWT's `dest` claim, which is itself HMAC-signed by `JwtPayload` (`lib/shopify_api/auth/jwt_payload.rb:23-45`), providing an equivalent binding. [1](#0-0) [4](#0-3) [6](#0-5)
