### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, excluding the `X-Shopify-Shop-Domain` header from the HMAC-verified payload. `ShopifyAPI::Webhooks::Registry.process` verifies the HMAC and then unconditionally forwards `request.shop` — sourced from that unverified header — to the app's handler as the tenant identity. Any internet-reachable webhook endpoint therefore trusts a shop identifier that carries no cryptographic binding to the signature that "authenticates" the request.

### Finding Description
`Request#hmac` and `Request#to_signable_string` compute/verify the signature over `@raw_body` only: [1](#0-0) [2](#0-1) 

`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed bytes: [3](#0-2) 

`Registry.process` validates the HMAC over the request, then hands `request.shop` straight to the registered handler as the authoritative tenant for the delivered webhook body: [4](#0-3) 

The identity binding that should hold is:

`shop_that_signed(raw_body) == shop_delivered_to_handler`

Before the attacker acts, both sides are consistent because Shopify sends the genuine header alongside the genuine signed body for a given webhook subscription belonging to shop A. After the attacker's request sequence — capture a legitimate webhook (raw body + valid `hmac-sha256`) that Shopify delivered for the attacker's own store (shop A, which the attacker legitimately owns/operates), then replay the exact same body/HMAC pair to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain: shopB.myshopify.com` — the HMAC check in `HmacValidator.validate` still passes (it only checks `raw_body`), yet `request.shop` now equals shop B. `Registry.process` passes this forged `shop: request.shop` to `WebhookMetadata`, and the host handler will process/store data believed to belong to victim shop B using body content that actually originated from the attacker's own shop A.

This breaks the "shop authenticated versus shop used as tenant key" binding explicitly called out as in-scope: the signature authenticates only the bytes of `raw_body`; the shop value that determines which tenant's data gets written/updated is taken from unauthenticated header bytes.

### Impact Explanation
This is a cross-tenant integrity issue: an unprivileged user who merely owns any store where the vulnerable app is installed (no `api_secret_key`, no access token, no privileged account needed) can cause the app to process attacker-controlled webhook content under an arbitrary victim shop's identity. Depending on the handler's implementation (which typically trusts `WebhookMetadata#shop` to select the tenant record to update), this can lead to cross-tenant data corruption/injection — matching the "Critical: cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that (a) registers at least one webhook topic and exposes an HTTP endpoint reachable from the internet (the standard integration pattern documented in `docs/usage/webhooks.md`), and (b) is installed on a store the attacker controls, which is trivially available to any developer via a free development store. Capturing a legitimate webhook delivery (body + HMAC header) requires no special access — it's simply the payload Shopify already sends to the attacker's own registered endpoint.

### Recommendation
Include the tenant-identifying header (`shop-domain`) — and ideally `topic`/`webhook-id` — in the signed material verified against the HMAC, or otherwise cryptographically bind the shop value to the signed body (e.g., verify the header-provided shop against a shop separately known to be authorized for this webhook subscription/endpoint) before it is handed to `WebhookMetadata`/the handler in `Registry.process`.

### Proof of Concept
1. Attacker installs the vulnerable app on their own dev store `attacker.myshopify.com` and registers a webhook topic (e.g. `orders/create`) pointing at the app's public endpoint.
2. Shopify delivers a genuine webhook: body `B` with header `X-Shopify-Hmac-Sha256: H` (valid for `B`) and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker replays an HTTP POST to the same endpoint with the identical body `B` and `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `@raw_body` (`B`) only and it matches `H`, so the check in `Registry.process` at [5](#0-4)  passes.
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to act on attacker-controlled data under the victim shop's tenant identity.
