### Title
Webhook shop, topic, and webhook-id headers are not covered by the HMAC, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers used to route and attribute the webhook are never included in that signable string. `ShopifyAPI::Webhooks::Registry.process` trusts these unauthenticated headers to select the handler and to build the `WebhookMetadata` passed to the app's business logic. An attacker who legitimately controls one shop (and therefore legitimately receives Shopify-signed webhooks for that shop) can replay the exact same signed body while substituting the `shop-domain` header for a victim shop, and the gem will accept it as valid and hand the forged shop identity to the host application.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The header accessors `shop`, `topic`, `api_version`, and `webhook_id` are all read from unauthenticated headers and are not part of the signed payload: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` verify the HMAC strictly over `verifiable_query.to_signable_string` (the raw body), independent of any header value: [3](#0-2) 

`Registry.process` calls this HMAC validation and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to select the handler and construct the metadata delivered to the host application's webhook handler: [4](#0-3) 

Because the signature only binds the body bytes and not the header set, the equality the gem implicitly relies on — `shop that produced a valid HMAC == shop attributed to the webhook data` — does not hold. Any actor who can obtain one validly-signed webhook body (e.g., by legitimately installing the app on their own shop and receiving a real webhook) can resend that same body with a different `shopify-shop-domain` (and/or `shopify-topic`/`shopify-webhook-id`) header. `HmacValidator.validate` will still pass because it never inspects headers, and `Registry.process` will hand the forged `shop` value to the handler as if Shopify itself attested to it.

### Impact Explanation
This breaks the tenant-identity binding between "who Shopify actually signed this payload for" and "who the application believes sent it." Host applications built on this gem's webhook API generally use `WebhookMetadata#shop` to select which merchant's data to create/update/delete. An attacker can forge webhook deliveries that read as coming from a shop they do not control, using data lifted from a webhook for a shop they do control, enabling cross-tenant data injection/corruption in the host application. This matches the Critical "cross-tenant access" category since the tenant boundary (`shop`) is not authenticated by the gem's own HMAC check.

### Likelihood Explanation
Exploitation requires an attacker to be able to deliver an HTTP request to the app's webhook endpoint with attacker-controlled headers alongside a body+HMAC pair they legitimately received (e.g., from installing the app on their own store, which is trivial for any public app). No access to `api_secret_key` or any privileged credential is required — only the ability to capture one genuine webhook delivery and replay it with modified headers.

### Recommendation
Include the identity-relevant headers (`shop-domain` at minimum, plus `topic` and `webhook-id`) in the HMAC-signable string, or otherwise cryptographically bind them to the body before verification, so that `Utils::HmacValidator.validate` fails if any of these headers are altered relative to what Shopify actually signed.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `{"id": 1}}`, header `x-shopify-hmac-sha256: <valid-hmac-for-body>`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `hmac` still matches (since HMAC only covers `@raw_body`), and `shop` now returns `"victim-shop.myshopify.com"`.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)` — this succeeds because the signature check only compares the body-derived signature, per [3](#0-2) .
5. `WebhookMetadata.new(topic:, shop: request.shop, ...)` is built with `shop = "victim-shop.myshopify.com"` and passed to the host app's handler, per [4](#0-3) , causing the host app to act on victim-shop's tenant record using attacker-controlled data.
