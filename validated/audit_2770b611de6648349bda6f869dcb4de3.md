## Title
Missing shop-domain validation in `TokenExchange.exchange_token` allows the app's `client_secret` and access token to be sent to an attacker-chosen host - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
Every OAuth token-issuing flow in this gem except `TokenExchange.exchange_token` validates the `shop` value with `Utils::ShopValidator.sanitize!` before using it to build the HTTP host that receives `client_secret`. `exchange_token` instead takes the `dest` claim straight out of the JWT session token (`jwt_payload.shop`) and uses it, unsanitized, as the host to which `client_id`/`client_secret`/`subject_token` are POSTed.

### Finding Description
`ClientCredentials.client_credentials` [1](#0-0) , `RefreshToken.refresh_access_token` [2](#0-1) , and `TokenExchange.migrate_to_expiring_token` [3](#0-2)  all call `Utils::ShopValidator.sanitize!(shop)` on the caller-supplied `shop` string and only use the *validated* host (restricted to `TRUSTED_SHOPIFY_DOMAINS` such as `myshopify.com`, `myshopify.io`, `spin.dev`, etc.) [4](#0-3)  to build the outbound session and HTTP client host.

`TokenExchange.exchange_token`, however, derives the host purely from the JWT payload's `dest` claim without any such check: [5](#0-4) . `JwtPayload#shop` simply strips `"https://"` from the raw `dest` claim [6](#0-5) , and `JwtPayload#initialize` only validates the JWT signature (`aud == Context.api_key`) — it never checks that `dest`/`iss` is a trusted Shopify domain [7](#0-6) .

`dest_shop` is then used to build `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)`, which is passed to `Clients::HttpClient.new(session: shop_session, ...)`. `HttpClient` builds its request base URI directly as `"https://#{api_host || session.shop}"` [8](#0-7) , i.e. `https://#{dest_shop}`. The POST body sent to that host contains `client_id`, `client_secret` (the app's `client_secret`), and the `subject_token` (the session token itself) [9](#0-8) .

This breaks the binding: **host validated (trusted Shopify domain) vs. host that receives the `client_secret`**. Session tokens (`session_token`) are JWTs whose signature is verified against `Context.api_secret_key`, so an attacker without the secret cannot forge one outright. But session tokens are also passed through client-side/embedded-app JS and other channels; the app only checks `aud` (its own API key) and the signature, not that `dest` is confined to `TRUSTED_SHOPIFY_DOMAINS`. If a session token is ever issued/relayed with a `dest` value under attacker control (e.g., a compromised or misconfigured relay, a token issued for one merchant/environment but replayed against another host, or any place upstream that lets `dest` diverge from a real myshopify domain while still using a key the app trusts), `exchange_token` will happily POST the app's `client_secret` to that host — exactly the SSRF-with-credentials pattern the other three grant flows are explicitly hardened against via `ShopValidator.sanitize!`.

### Impact Explanation
If exploited, this results in exfiltration of the app's `client_secret` and the session token to a host chosen via the (attacker-influenceable) `dest` claim, which the gem's own consistency pattern (`ShopValidator` used everywhere else this exact host-selection happens) treats as a credential-leak/SSRF risk worth guarding against. This matches the report's underlying bug class: a privileged action (sending the client secret) is performed based on data whose scope of trust was never checked to be sufficient, unlike the sibling code path that does check it.

### Likelihood Explanation
Medium. Exploitation depends on a session token with an untrusted `dest` reaching `exchange_token` while still passing this gem's own signature/`aud` checks. This is not directly forgeable by an anonymous internet attacker without secret material, but it is a real internal inconsistency: three of four “send client_secret to `shop`” call sites enforce `ShopValidator.sanitize!`, and this one — which also handles the deprecated `shop:` parameter differently from the trusted `dest_shop` — does not, making it the most likely target if any upstream trust assumption about `dest` is violated.

### Recommendation
In `TokenExchange.exchange_token`, validate `dest_shop` with `Utils::ShopValidator.sanitize!(dest_shop)` (mirroring `client_credentials.rb`, `refresh_token.rb`, and `TokenExchange.migrate_to_expiring_token`) before constructing `shop_session`/`HttpClient`, and use the sanitized value for both the outbound request host and the resulting `Session.from(shop: ...)`.

### Proof of Concept
1. Obtain (or induce) a session token whose `dest` claim is `https://attacker.example` but which still verifies against `Context.api_secret_key` (e.g., via a compromised token-issuing path outside this gem, or a review of any upstream code that copies `dest` from unverified input into a token later validated only by signature/`aud`).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `Clients::HttpClient` is constructed with `session.shop == "attacker.example"` [8](#0-7) , and the POST containing `client_secret` is sent to `https://attacker.example/admin/oauth/access_token` instead of a verified Shopify domain [10](#0-9) .
