### Title
Excess native token sent to `EvmHost.dispatch()` for fee-swap is permanently locked in the Host instead of being refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` accept native `msg.value` and swap it for the exact required `feeToken` amount via `swapETHForExactTokens`, but never capture or forward back any leftover native ETH resulting from that swap. This mirrors the reported `LimitOrderManager.place()` bug class: surplus native value sent alongside a call is silently absorbed by the receiving contract instead of being refunded to the original depositor.

### Finding Description
Both native-fee dispatch entrypoints route the entire `msg.value` into a Uniswap V2 "exact-out" swap: [1](#0-0) 

```
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        ...
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } else if (post.fee > 0) {
        IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
    }
    ...
```

The same pattern exists in `dispatch(DispatchGet)`: [2](#0-1) 

`UniswapV2Router02.swapETHForExactTokens` only consumes `amounts[0]` (the exact amount needed to buy `post.fee`/`get.fee` fee-tokens) and refunds any unused ETH — but that refund is sent to `msg.sender` **of the router call**, which is `EvmHost` itself, not the original transaction sender (`_msgSender()`) who supplied the `msg.value`. `EvmHost.dispatch()` never reads or propagates that refund back to the caller; it is simply absorbed into the Host's native balance.

Any HyperApp built on top of `IDispatcher.dispatch()` that forwards `msg.value` directly is exposed to this: e.g. `HyperFungibleToken.send()` and `WrappedHyperFungibleToken.send()` forward the full remaining `msg.value` as the native fee: [3](#0-2) 

If the user (or an off-chain quote that becomes stale between quoting and execution) supplies more native value than the current `swapETHForExactTokens` requires, the excess is not returned to them — it stays locked in `EvmHost`.

This is directly analogous to the reported issue: `LimitOrderManager.place()` wraps the whole received ETH balance and forwards it to the pool without tracking/refunding the surplus over the amount actually consumed. Here, `EvmHost.dispatch()` forwards the whole `msg.value` into a swap and never tracks/refunds the delta between `msg.value` and the amount actually spent (`amounts[0]`) by the swap.

By contrast, other parts of the same codebase (e.g. `IntentGatewayV2.placeOrder`) correctly track `msgValue -= amounts[0]` after the swap and refund the remainder to the user: [4](#0-3) 

showing the project is aware of and normally implements this refund pattern — but `EvmHost.dispatch()`, the core, most-reachable dispatch entrypoint used by essentially every HyperApp (fungible token bridge, wrapped token, LayerZero endpoint, etc.), lacks it.

### Impact Explanation
Any unprivileged user who dispatches a cross-chain POST/GET request (via `IDispatcher.dispatch`) and slightly overestimates the native fee — which is expected in practice since fee quoting happens off-chain/pre-transaction and prices/gas can shift before the swap executes on-chain — permanently loses the surplus ETH into `EvmHost`'s balance. This is a direct, protocol-wide, unprivileged loss-of-funds vector reachable through the primary message-dispatch path (`EvmHost.dispatch`), which the ruleset explicitly names as in-scope ("EvmHost ... dispatch and delivery"). Because there is no visible sweep/withdraw mechanism for this ETH tied back to depositors, funds are effectively locked/lost to the caller, matching "permanent freezing of funds."

### Likelihood Explanation
High likelihood: any caller providing native `msg.value` for fee payment via `dispatch()` who sends even marginally more than the exact swap requirement (a common, expected scenario given price movement between fee quoting and transaction execution, or simple conservative overpayment by integrators) triggers the loss on every such call — no attacker action or special conditions are required.

### Recommendation
Track the actual amount consumed by the swap (the `amounts[0]` returned by `swapETHForExactTokens`) and refund `msg.value - amounts[0]` back to `_msgSender()` in both `dispatch(DispatchPost)` and `dispatch(DispatchGet)`, mirroring the pattern already used in `IntentGatewayV2.placeOrder`:

```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
if (msg.value > amounts[0]) {
    _sendValue(_msgSender(), msg.value - amounts[0]);
}
```

### Proof of Concept
1. User (or integrating HyperApp) calls `EvmHost.dispatch{value: X}(post)` where `post.fee` requires only `Y < X` native tokens to be swapped for the fee token (e.g., due to favorable price movement since the fee was quoted, or simple overestimation/rounding by the caller).
2. `EvmHost.dispatch` forwards the full `X` to `swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)`.
3. The router consumes only `Y` and refunds `X - Y` ETH to `msg.sender`, which in this call context is `EvmHost` (not the original user).
4. `EvmHost.dispatch` never reads or forwards this refund; `X - Y` becomes an unrecoverable addition to `EvmHost`'s native balance, while the user who paid `X` receives nothing back.
