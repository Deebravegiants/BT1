This confirms the root cause: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read straight from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header [2](#0-1) . `Registry.process` validates only the HMAC-over-body via `HmacValidator.validate(request)` and then trusts `request.shop` to build `WebhookMetadata`, which is handed directly to the app's handler as the tenant identifier [3](#0-2) . The gem's own documentation tells app authors that `data.shop` is "The shop domain of the webhook" and to use it directly (e.g. `shop_domain: data.shop`) [4](#0-3) , i.e., the gem presents this field as trustworthy/authenticated when it is not covered by the signature.

### Title
Webhook `shop` identity is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only (`to_signable_string` returns `@raw_body`), but exposes `shop` (and `topic`/`webhook_id`/`api_version`) straight from HTTP headers that are never part of the signed payload. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler. Because the header carrying the tenant identity is not bound to the HMAC-protected bytes, any party that can produce one valid `(body, hmac)` pair for a given `api_secret_key`-holding app (e.g., a merchant who installs the app on their own store and thus legitimately receives real, correctly-signed webhooks for their own shop) can replay that exact `(body, hmac)` pair to the app's shared webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. The signature still validates, and the handler will process/attribute the payload to the victim shop.

### Finding Description
The equality that should hold is: `shop bound by HMAC == shop acted upon by the handler`. Here it does not:
- Signed bytes: `to_signable_string` = `@raw_body` only [1](#0-0) .
- Trusted/acted-upon identity: `shop` comes from `shopify_header("shop-domain")`, an ordinary HTTP header supplied by whoever sends the POST request to the app's webhook endpoint [2](#0-1) .
- `HmacValidator.validate` only recomputes/compares the signature over `to_signable_string`, so it cannot detect that `shop-domain` was swapped [5](#0-4) .
- `Registry.process` gates only on that HMAC check, then forwards `request.shop` directly to the handler as the authoritative tenant identity [3](#0-2) .

Since the webhook endpoint is a plain HTTP POST route (any internet client can hit it, not just Shopify's IPs, and this gem provides no origin/IP checking), an attacker who legitimately installs the app on their own shop receives real webhooks for their shop with valid `(body, hmac)` pairs signed with the app's `api_secret_key`. They can then replay that exact request to the same endpoint, only changing the `shop-domain` header to any victim shop domain. `HmacValidator.validate` still passes because it never looks at the header, and the app processes the payload as if it came from the victim shop.

### Impact Explanation
This breaks the shop-to-payload binding that the gem's own documentation instructs app authors to rely on (`data.shop`) [6](#0-5) , enabling cross-tenant confusion: an attacker-controlled webhook body (from their own store) can be injected into another merchant's data pipeline under a forged `shop` value — e.g., forging an `app/uninstalled` event for a victim shop to trigger deprovisioning logic, or injecting fabricated order/customer data attributed to the victim tenant. This matches the "cross-tenant access" Critical impact category since a legitimate installer of the app (an unprivileged actor with respect to other merchants) can cause the app to act on/associate data with a shop they do not control, without ever needing that other shop's or the app's `client_secret`/access token.

### Likelihood Explanation
Requires only that the attacker be an app installer (any merchant can install most public/embedded apps) capable of triggering at least one webhook delivery to their own shop and capturing the raw body + `hmac-sha256` header (both are visible to the receiving app/attacker since it's their own installation), then replaying that POST with a modified `shop-domain` header to the app's public webhook URL. No secret key, access token, or privileged access is required — it is exploitable purely from the position of an unprivileged (or self-privileged-on-their-own-tenant) internet actor.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed material, or otherwise cryptographically tie the header-derived shop to the request before trusting it. Concretely, `Request#to_signable_string` should not be limited to the raw body; alternatively, `Registry.process`/`HmacValidator` should verify that the `shop-domain` header matches a shop for which the request's `hmac` was actually computed (e.g., by requiring apps to pass the expected shop and comparing it, or by having the library reject any webhook whose `shop-domain` cannot be tied to the HMAC). At minimum, document prominently that `request.shop`/`data.shop` is **not** authenticated by the HMAC and must not be trusted as a tenant boundary without additional verification (e.g., cross-checking against an existing installed-shop record before use).

### Proof of Concept
```ruby
# Attacker legitimately installs the app on their own shop "attacker.myshopify.com"
# and receives a real webhook from Shopify:
raw_body   = '{"id":1,"note":"hello"}'
real_hmac  = Base64.encode64(OpenSSL::HMAC.digest("sha256", api_secret_key, raw_body))

# Attacker replays the exact same body+hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to the victim's shop:
forged_headers = {
  "x-shopify-topic"       => "orders/create",
  "x-shopify-hmac-sha256" => real_hmac,       # still valid! only signs raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (it only checks raw_body),
#    handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))
#    is invoked, attributing attacker-controlled data to the victim shop.
```
