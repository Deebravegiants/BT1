### Title
Unchecked zero/degenerate public key in `decode_public_key` used to encrypt biometric data - (File: `src/backend/user_status.rs`)

### Summary
`decode_public_key` in `src/backend/user_status.rs` decodes a base64 string returned by the backend (and the app-provided `self_custody_public_key`) into a 32-byte `sodiumoxide::crypto::box_::PublicKey` and only validates the byte length, never checking that the value is a non-zero / non-degenerate key. This mirrors the reported `EthBridge.depositERC20To` bug class where a destination parameter (`_to`) is accepted without a zero-value check, causing assets to be "deposited" to an address that can never receive them.

### Finding Description
`decode_public_key` performs base64 decoding and a length check only: [1](#0-0) 
It is used to build every encryption key used in the signup flow — `backend_iris_public_key`, `backend_normalized_iris_public_key`, `backend_face_public_key`, `backend_tier2_public_key`, and, critically, `self_custody_user_public_key` (the key supplied via `authenticated_app_data.self_custody_public_key`): [2](#0-1) 
None of these keys are checked for being the all-zero key or another degenerate/low-order Curve25519 point before being accepted into `UserData` and subsequently `personal_custody_package::Credentials`.

These keys are then used unconditionally to seal (encrypt) the user's biometric artifacts — iris images, normalized iris images, face images, and the full tier0/tier1/tier2 personal custody packages — via `sealedbox::seal`: [3](#0-2) [4](#0-3) 

### Impact Explanation
If `self_custody_user_public_key` (or any backend key) is ever zero, degenerate, or otherwise has no known/derivable private-key counterpart — whether due to a backend bug, a malformed/replayed `authenticated_app_data` payload, or an app-side defect — the biometric package (iris, normalized iris, face images across tiers 0–2) is sealed to a key that nobody can decrypt. This is the direct analog of "depositing tokens but not being able to receive them": the Orb completes a real biometric signup, uploads a personal custody package that is unrecoverable by the legitimate user, silently and permanently. Unlike the resolved EthBridge case, there is no equivalent `require(key != 0)` guard anywhere in this decode/encrypt path.

### Likelihood Explanation
The key path is reachable by every normal signup — no special privileges are required, since `self_custody_user_public_key` originates from `authenticated_app_data` returned alongside the backend validation response and is only integrity-checked against a `user_data_hash` from the QR code (not checked for being a valid/non-zero curve point). A malformed or default-initialized key value from the backend or a buggy app integration would silently pass through undetected until the user later fails to decrypt their own data.

### Recommendation
Add explicit validation in `decode_public_key` (or immediately after decoding) rejecting all-zero and other known degenerate/low-order Curve25519 points before accepting `backend_iris_public_key`, `backend_normalized_iris_public_key`, `backend_face_public_key`, `backend_tier2_public_key`, and especially `self_custody_user_public_key`. Fail the signup validation (`return Ok(None)`), analogous to adding `require(_to != address(0))`, rather than proceeding to encrypt sensitive biometric data to an unusable key.

### Proof of Concept
1. Backend (or a compromised/misbehaving intermediary) returns `authenticated_app_data.self_custody_public_key` as base64 of 32 zero bytes.
2. `decode_public_key` successfully decodes it into `PublicKey([0u8;32])` since only the length is checked. [1](#0-0) 
3. `verify(user_data_hash)` (backend/app signature check) may still pass depending on how the hash was computed if the attacker controls the payload before hashing, or the check is bypassed via `skip-user-qr-validation` feature paths.
4. The zero key flows into `Credentials.self_custody_user_public_key` and is used to seal tier0/tier1/tier2 packages via `encrypt`, producing an unrecoverable ciphertext for the user. [5](#0-4)

fn decode_public_key(payload: &str) -> Result<PublicKey> {
    let bytes = BASE64.decode(payload.as_bytes())?;
    let bytes = <[u8; 32]>::try_from(bytes)
        .map_err(|x| eyre!("incompatible public key length: {}", x.len()))?;
    Ok(PublicKey(bytes))
}

fn encrypt<T: AsRef<[u8]>>(data: T, public_key: &PublicKey) -> Vec<u8> {
    let encrypted = sodiumoxide::crypto::sealedbox::seal(data.as_ref(), public_key);
    assert_ne!(data.as_ref(), encrypted);
    encrypted
}
