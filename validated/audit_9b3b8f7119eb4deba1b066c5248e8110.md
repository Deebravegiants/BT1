### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating only the raw request body against the HMAC signature. The `shop` identity that is handed to the application's webhook handler is read from the `x-shopify-shop-domain` header, which is never part of the signed material. This breaks the identity binding: `HMAC-verified(raw_body) != shop-domain-trusted-by-handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . `topic`, `shop`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers without being part of the signable string: [2](#0-1) .

`Utils::HmacValidator.validate` only calls `to_signable_string` to compute/compare the signature, so it verifies that the *body bytes* were signed with `Context.api_secret_key`, and says nothing about the headers: [3](#0-2) .

`Registry.process` raises only if `Utils::HmacValidator.validate(request)` fails, then immediately forwards `request.shop` (the unauthenticated header value) to the application handler as the tenant identity for the event: [4](#0-3) .

Because the HMAC only binds the *body*, and the same message body/HMAC pair is valid regardless of which shop it is claimed to belong to, an unprivileged user who legitimately receives (or can otherwise obtain) one authentic `(raw_body, x-shopify-hmac-sha256)` pair for a topic — e.g. by installing the public app on their own shop and letting Shopify deliver a real webhook to them — can resend that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and `x-shopify-webhook-id`) header with any other shop's domain. `HmacValidator.validate` will still pass because it only checks the body, and `WebhookMetadata#shop` will report the attacker-chosen tenant.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem asserts "this event body is authentic" but the host application is led to believe it also asserts "this event belongs to shop X," which it does not. Any host application that uses `data.shop` from `WebhookMetadata` to key writes/lookups (the officially recommended pattern shown in this gem's own webhook examples) can have events attributed to, or processed against, the wrong merchant/tenant — i.e., cross-tenant data confusion driven entirely by a header the gem never authenticates. This matches the Critical "cross-tenant access" impact category, since it lets one tenant's authentic message be attributed to another tenant purely by header substitution, with no dependency on `api_secret_key`, tokens, or other privileged material.

### Likelihood Explanation
Likelihood is limited by the fact that the attacker must first obtain at least one authentic `(body, hmac)` pair for the relevant topic. For a public app this is achievable by any unprivileged user simply by installing the app on their own (attacker-owned) shop and waiting for a real webhook delivery — no credentials belonging to the victim or the app owner are required, only observation of traffic the attacker itself legitimately receives. The replay itself is a single unauthenticated HTTP POST to the app's public webhook endpoint with a modified header value, which is trivial to construct once headers are inspected. This does not require the app's `client_secret`, an access token, or any privileged account.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is actually verified, or independently authenticate the shop domain, before trusting it:
- Include the shop/topic/webhook-id headers as part of `to_signable_string` computed the same way Shopify computes the HMAC (not possible unless Shopify signs headers too), **or**
- After HMAC validation, look up/confirm the delivering shop out-of-band (e.g. compare `x-shopify-webhook-id` against a value fetched from Shopify's Admin API for the session/shop the app expects, or maintain a registry of `webhook_id -> expected shop` created at registration time) rather than trusting the header verbatim, **or**
- At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a sole tenant-selection key without additional verification (e.g. matching it against an already-known, previously-authenticated shop for the installation making the request).

### Proof of Concept
1. Install the target public app on an attacker-controlled shop `attacker.myshopify.com` and enable a webhook topic (e.g. `products/create`). Shopify will deliver a webhook such as:
   ```
   POST /webhooks HTTP/1.1
   x-shopify-topic: products/create
   x-shopify-hmac-sha256: <valid-hmac-of-body>
   x-shopify-shop-domain: attacker.myshopify.com
   x-shopify-webhook-id: <id>

   {"id":1,"title":"..."}
   ```
2. Capture this exact `raw_body` and `x-shopify-hmac-sha256` value — both are attacker-visible since it was delivered to the attacker's own endpoint.
3. Replay the identical body and HMAC header to the app's webhook endpoint, but change only:
   ```
   x-shopify-shop-domain: victim.myshopify.com
   ```
4. `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only [5](#0-4)  — it matches, so the request passes validation.
5. `Registry.process` calls the handler with `WebhookMetadata.new(topic:, shop: request.shop, ...)` where `request.shop` now returns `"victim.myshopify.com"` [6](#0-5)  — the application processes the attacker's product-create event as if it originated from the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
