### Title
Webhook `shop` identifier is not covered by HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates the authenticity of an incoming webhook using only the raw request body's HMAC, but then trusts the `shop-domain` header — which is *not* part of the signed payload — as the tenant identifier passed to the host application's handler.

### Finding Description
The HMAC signature for a webhook only ever covers the raw body bytes: [1](#0-0) 

The `shop` accessor, however, is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never included in the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies exactly and only what `to_signable_string` returns: [3](#0-2) 

`Registry.process` calls this validator, and — once it passes — builds the `WebhookMetadata` handed to the application's handler using the *unauthenticated* `request.shop` value, alongside the authenticated body/topic: [4](#0-3) [5](#0-4) 

This breaks an identity binding equivalent to the one the report's bug class targets: `shop authenticated == shop used as tenant/session key`. Here, the byte range verified by HMAC (`raw_body`) is disjoint from the byte range (`shop-domain` header) that is trusted as the tenant key for dispatching the webhook to the handler.

### Impact Explanation
An attacker who can obtain any single validly-signed webhook payload for a given topic/body (e.g. from their own trial/dev shop installation of the app, or a captured request) can replay it against the app's webhook endpoint while substituting the `shop-domain` header for an arbitrary victim shop. Because the HMAC only binds the body, the signature remains valid, and `Registry.process` will pass `WebhookMetadata` claiming the payload originated from the victim shop. Any host-application handler logic that looks up sessions, orders, or state keyed by `data.shop` (as documented and expected usage of this gem) will act on forged, cross-tenant data — a cross-tenant integrity/confusion issue matching the "Critical - cross-tenant access" impact class.

### Likelihood Explanation
Exploitation only requires: (1) the attacker's own or any accessible valid webhook (easy to obtain — e.g., install the app on a free/dev shop and receive a legitimate webhook with a small/predictable body such as `{}` or a mandatory GDPR topic), and (2) the ability to send an arbitrary HTTP request to the app's public webhook endpoint with a modified `shop-domain` header. No access to `api_secret_key` or any credential is required, since the HMAC validation logic itself never inspects the header.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed/verified material, or otherwise cryptographically bind the shop domain to the payload before exposing it via `WebhookMetadata#shop`. At minimum, document that `data.shop` is unauthenticated and must not be trusted as a tenant key without additional verification (e.g., cross-checking against a known, previously-established session/shop registered for that webhook subscription).

### Proof of Concept
1. Install the app (or otherwise obtain) on `attacker-shop.myshopify.com` and receive one legitimate webhook whose raw body is small/known, e.g. `{}`. Its headers include a valid `x-shopify-hmac-sha256` computed over `{}` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Replay the exact same body `{}` and HMAC header to the app's webhook endpoint, but replace the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` = `"{}"` only — this still matches, since the header is not part of the signed content: [6](#0-5) 
4. Validation passes; `WebhookMetadata.new(... shop: request.shop ...)` is built with `shop: "victim-shop.myshopify.com"` and dispatched to the app's handler, which believes this event genuinely came from the victim's shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
