### Title

Untrusted route payload can inject arbitrary calls under the swapper’s authorization - ([File: contracts/swap-aggregator/src/venues/mod.rs](contracts/swap-aggregator/src/venues/mod.rs))

### Summary

The swap aggregator executes attacker-supplied `StrategyPayload.ops` as a compact instruction stream whose `assets` registry supplies unrestricted pool addresses. Each swap opcode dispatches to a venue adapter and invokes the payload-selected `hop.pool`. Because `execute_strategy` calls `sender.require_auth()` before executing the program, a malicious pool runs below the sender’s authorization context and can request additional token transfers from the sender. Soroban simulation records those transfers as children of the authorization tree; if that simulated tree is submitted or signed, the injected call can transfer arbitrary sender-held tokens to the attacker while the router still returns a valid swap output.

### Finding Description

`Router::execute_strategy` accepts arbitrary XDR bytes and passes the decoded `StrategyPayload` to `execute::run`. [1](#0-0) 

`execute::run` authorizes the supplied `sender` before decoding and running the route, then pulls only the declared route input into the router. [2](#0-1) 

The route is an instruction stream over caller-controlled `assets`. For a swap instruction, `idx_a` becomes `hop.pool`, while `idx_b` and `idx_c` become the input and output token contracts. [3](#0-2) 

The packed format explicitly defines each 5-byte instruction’s `idx_a` field as a pool registry index, but pool addresses come from the caller-provided `assets` vector rather than a venue allowlist or trusted registry. [4](#0-3) 

`dispatch_hop` measures the router’s input and output balances, but it places the selected pool on the call stack through the venue adapter and does not constrain what other contracts that pool calls while it executes. [5](#0-4) 

This reaches production controller strategies as well. `swap_tokens` authorizes one exact controller-to-router input transfer, calls `execute_strategy`, and checks only controller-side input/output deltas afterward. [6](#0-5)  `process_swap_collateral` permits an owner or delegate to supply the route and feeds it into that router path. [7](#0-6) 

The repository’s threat model confirms the resulting authorization-tree behavior: a payload-named pool can invoke third-party code below the caller’s authorization, and a sender-funded token transfer made by that code is recorded as a child of the caller’s authorization entry. [8](#0-7) 

### Impact Explanation

A malicious route can steal assets outside the declared route input. The injected pool can call a token contract with `transfer(victim, attacker, victim_balance)` while processing the hop. An honest simulation records that token call under the victim’s `execute_strategy` or controller-strategy authorization. If the victim or an integrating wallet accepts the resulting tree, the host authorizes the injected transfer even though it is unrelated to the requested swap.

This is theft of user funds, not merely a bad fill. The attacker can target any spendable token held by the victim, including tokens absent from the declared `token_in`, `token_out`, `total_in`, and `min_out` fields. The router’s measured-output and minimum-output checks do not inspect unrelated sender-wallet transfers.

### Likelihood Explanation

Likelihood is constrained by authorization: the attacker cannot choose an arbitrary victim and execute the route without the victim authorizing the resulting invocation tree. Exploitation therefore requires the victim to use a malicious quote/route and for the wallet, quoting service, or integration to submit the simulated authorization tree without rejecting unexpected children.

That condition is realistic for aggregator-style routes because routes are opaque XDR bytes and authorization trees are generated by simulation. The project’s own regression test demonstrates that simulation records the rogue transfer as a child invocation and that enforcing the poisoned tree moves the victim’s unrelated wallet token. [9](#0-8) [10](#0-9) 

### Recommendation

Do not let route bytes select arbitrary executable pool contracts. Bind each route to governance-approved venue pools, or precompute and validate a venue-specific pool registry before authorizing the sender. At minimum:

- Maintain per-venue pool allowlists and reject `hop.pool` values not registered for the selected `SwapVenue`.
- Validate token addresses against the selected pool’s expected token set before invoking it.
- Ensure authorization is requested only after route validation and keep payload execution outside any authorization context broader than the exact intended input transfer.
- Provide and enforce a canonical authorization-tree shape for clients: direct `execute_strategy` should contain only the input-token transfer child, while controller strategies should contain no unrelated sender-wallet token transfer.
- Treat authorization trees containing additional token transfers, approvals, or contract calls as malformed routes rather than user consent for arbitrary payload behavior.

### Proof of Concept

1. Attacker deploys `RoguePool`.
2. Attacker constructs a valid `StrategyPayload` for `execute_strategy(victim, total_in, swap_xdr)` where:
   - `assets[pool_idx] = rogue_pool`;
   - `assets[token_in_idx]` and `assets[token_out_idx]` are real tokens;
   - `ops` contains one valid swap opcode that causes a venue adapter to invoke `rogue_pool`;
   - `min_out` is positive and low enough for the route to settle.
3. `RoguePool.swap` first calls:

```rust
token::Client::new(&env, &victim_wallet_token).transfer(
    &victim,
    &attacker,
    &victim_balance,
);
```

It then arranges a positive `token_out` payment to the router so `dispatch_hop`’s measured-output checks pass.

4. Simulation records the extra `victim_wallet_token.transfer(victim, attacker, victim_balance)` as a child of the victim’s swap authorization.
5. If the victim submits/signs that recorded tree, the injected transfer executes and moves `victim_balance` to the attacker.
6. The same result is demonstrated through `controller::swap_collateral`: simulation produces a poisoned root containing the unrelated wallet-token transfer, and submitting that tree drains the victim’s wallet token while the collateral swap still succeeds. [11](#0-10)

pub(crate) fn run(env: Env, sender: Address, total_in: i128, payload: StrategyPayload) -> i128 {
    sender.require_auth();

    if total_in <= 0 {
        panic_with_error!(&env, Error::InvalidAmount);
    }

    let StrategyPayload {
        amounts,
        assets,
        ops,
    } = payload;
    let program = Program::decode(&env, &ops, assets.len(), amounts.len());

    let input_token = assets.get_unchecked(program.token_in);
    let output_token = assets.get_unchecked(program.token_out);
    let total_min_out = amounts.get_unchecked(program.min_out);
    if total_min_out <= 0 {
        panic_with_error!(&env, Error::SlippageExceeded);
    }

    let router = env.current_contract_address();
    let mut vault = Vault::new(&env);
    let mut tokens_cache: Map<Address, Vec<Address>> = Map::new(&env);

    // Credit the measured delta, not declared `total_in`: a fee-on-transfer
    // input would otherwise draw the shortfall from the fee reserve.
    let credited_in = transfer_amount_measured(
        &env,
        &input_token,
        &sender,
        &router,
        total_in,
        GenericError::AmountMustBePositive,
    );
    vault.deposit(&input_token, credited_in);

pub(crate) fn dispatch_hop(
    env: &Env,
    router: &Address,
    hop: &SwapHop,
    amount_in: i128,
    tokens_cache: &mut Map<Address, Vec<Address>>,
) -> i128 {
    let ctx = HopContext::new(env, router, hop, amount_in);
    let before_in = ctx.input_balance();
    let before_out = ctx.output_balance();

    match hop.venue {
        SwapVenue::Soroswap => soroswap::swap(&ctx),
        SwapVenue::Aquarius => aquarius::swap(&ctx, tokens_cache),
        SwapVenue::Phoenix => phoenix::swap(&ctx),
        SwapVenue::Sushi => sushi::swap(&ctx),
        SwapVenue::CometDex => comet::swap(&ctx),
    };

    let received = ctx
        .output_balance()
        .checked_sub(before_out)
        .unwrap_or_else(|| panic_with_error!(env, Error::ZeroOutput));
    if received <= 0 {
        panic_with_error!(env, Error::ZeroOutput);
    }

    let after_in = ctx.input_balance();
    let spent = before_in
        .checked_sub(after_in)
        .unwrap_or_else(|| panic_with_error!(env, Error::InvalidAmount));
    if spent != amount_in {
        panic_with_error!(env, Error::InvalidAmount);
    }

    received

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);

    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
