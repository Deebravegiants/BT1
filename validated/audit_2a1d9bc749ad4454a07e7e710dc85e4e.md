### Title
Supplying dust of an asset with a stale oracle feed permanently shields a borrower from liquidation and bad-debt cleanup - (File: contracts/controller/src/positions/liquidation/plan.rs)

### Summary
The PriceTierVesting bug class — an oracle that lags behind reality within its configured freshness envelope blocking a threshold-triggered action — maps directly onto XOXNO Lending's fail-closed valuation: any stale leg of an account's portfolio makes every valuation revert. Because `supply` stamps a brand-new position with the current config without ever reading that asset's price, an unprivileged user can add a dust-sized supply leg of an asset whose feed has gone stale, after which `liquidate`, `clean_bad_debt`, and `withdraw` all revert with `PriceFeedStale`, granting the account liquidation immunity for as long as the feed lags.

### Finding Description
`calculate_account_risk_totals` iterates every supply position and calls `cache.cached_price(&hub_asset.asset)` for each one, so a single leg whose oracle observation is older than `max_stale_seconds` poisons the whole valuation [1](#0-0) . The aggregator resolves each source with `is_stale` against its own `max_stale_seconds` and surfaces `OracleError::PriceFeedStale` from `Outcome::failure`, which strict `prices` reads turn into a hard revert [2](#0-1) . `build_liquidation_plan` unconditionally recomputes risk totals and requires `health_factor < Wad::ONE`, so the stale-leg revert aborts liquidation before the HF gate is even evaluated [3](#0-2) .

Crucially, planting the leg needs no price read: for a *new* supply position the stored `liquidation_threshold`/`liquidation_bonus`/`liquidation_fees` equal `effective_config`, `favors_liquidator` returns false, and `apply_gated_liquidation_params` skips the HF check entirely — so `supply` succeeds even while the asset's feed is stale [4](#0-3) . The in-repo harness test `audit_supply_setup_blocks_liquidation_via_stale_dust_leg` confirms exactly this: a `0.001` WBTC supply is accepted with a 1-hour-stale feed, then `try_liquidate`, `try_clean_bad_debt_by_id`, and `try_withdraw` all fail with `PRICE_FEED_STALE` until the feed refreshes [5](#0-4) .

The report's mechanism is preserved: Chainlink-style heartbeat/deviation cadence is mirrored here by per-source `max_stale_seconds` windows (production configs run 3,600 s up to 57,600 s) and by feeds that simply stop being updated (e.g., a Reflector asset losing its reporter or a RedStone feed halting) [6](#0-5) . No privileged action is needed: `supply` is an open entrypoint, and the attacker merely picks a listed spoke asset whose oracle has already lapsed — an observable on-chain condition.

### Impact Explanation
While the poisoned leg's feed is stale, the account is immune to liquidation regardless of how underwater it is: every `liquidate` call reverts before seizing anything. Interest keeps accruing on the unliquidatable debt, and `clean_bad_debt` reverts with the same `PriceFeedStale`, so the protocol cannot even write the position down — the bad debt is locked in and grows, directly producing protocol insolvency borne by suppliers. If the feed never recovers (dead provider), the freezing is permanent. This matches the accepted impact categories: protocol insolvency and (for the depositor's remaining collateral) freezing of funds.

### Likelihood Explanation
Likelihood is moderate: it requires (a) a listed asset whose oracle feed goes stale and (b) an attacker borrowing against other collateral, then adding the dust leg before their HF drops below 1 — or opportunistically, any already-underwater account adding the leg once a feed dies. Staleness windows and feed outages are normal oracle events (the exact cadence gap the source report describes); the dust leg costs only a fraction of a token plus the position. The barrier is that the attacker must time or await a stale feed on an asset listed on their spoke, and once the feed refreshes the shield evaporates and normal liquidation resumes — so the damage is bounded by the outage duration unless the feed is permanently dead.

### Recommendation
Decouple leg-planting from liquidation-blocking: either (a) require a fresh, valid price for the supplied asset whenever `supply` creates a new position on an account that carries debt (extend the existing gate so stale pricing rejects the plant), or (b) make `build_liquidation_plan` and `clean_bad_debt` treat a stale supply leg as zero-value rather than reverting — value it at 0 or skip it — so one dead feed can only under-count collateral, never immunize debt. Option (b) additionally removes the stale-feed block on `withdraw` of unrelated legs.

### Proof of Concept
1. Alice supplies USDC and borrows ETH (HF comfortably > 1).
2. WBTC's Reflector feed stops updating; its observation ages past `max_stale_seconds` (e.g., 3,600 s), which Alice observes on-chain.
3. Alice calls `supply` for a dust amount of WBTC. Because the position is new, `favors_liquidator` is false and no HF check runs — the plant succeeds despite the stale feed (`audit_supply_setup_blocks_liquidation_via_stale_dust_leg`, lines 26–35).
4. USDC price crashes; Alice's real HF falls well below 1. Liquidator calls `liquidate`, which enters `build_liquidation_plan` → `calculate_account_risk_totals` → `cached_price(WBTC)` → `prices` strict read → `Outcome::failure` returns `PriceFeedStale` → revert (test lines 51–52).
5. `clean_bad_debt` reverts identically (lines 54–55); Alice's debt accrues interest unseizable. Recovery only occurs when the WBTC feed refreshes (lines 60–69) — or never, if the provider is dead — leaving the pool holding unbacked debt.
