Unlocked `fees.getFees()` call while wallet locked bypasses lock boundary and derives receive address / fee data - ([File: features/fees/module/index.js])

### Summary
`feesApiDefinition` (`features/fees/api/index.js`) exposes the `fees` module as a public SDK/RPC surface with no `lockedAtom` gating, and `createFees` (`features/fees/module/index.js`) has no `lockedAtom` dependency at all. Unlike `addressProviderApi`'s `withWalletAccountInstance`, which explicitly checks `await lockedAtom.get()` before calling into `addressProvider`, `fees.getFees` directly injects the raw `addressProvider` module and calls `addressProvider.getReceiveAddress(...)` with no lock check, so an unprivileged dapp can call `exodus.fees.getFees()` while the wallet is locked and still get address derivation and fee computation performed.

### Finding Description
`createFees` (`features/fees/module/index.js:26-131`) depends on `addressProvider` (the module, not the API) and `walletAccountsAtom`, but not `lockedAtom`. Inside `getFees`, when no `fromAddress` is supplied, it calls: [1](#0-0) 

directly against the module-level `addressProvider.getReceiveAddress`, which is the *un-gated* module (`features/address-provider/module/address-provider.js`) — the lock enforcement (`if (await lockedAtom.get()) throw new Error('address-provider: wallet should be unlocked')`) only exists in the API wrapper `withWalletAccountInstance` in `features/address-provider/api/index.js:12-18`, which `fees` never goes through.

`feesModuleDefinition` is `public: true` [2](#0-1)  and `feesApiDefinition` simply re-exports the `fees` module verbatim with zero additional wrapping or lock check: [3](#0-2) . This contrasts directly with `addressProviderApiDefinition`, which requires `lockedAtom` as a dependency and enforces it on every wrapped method [4](#0-3) .

There is also no global lock gate at the RPC dispatch layer: `json-rpc`'s `_processCallMethod` (`libraries/json-rpc/index.js:145-173`) blindly invokes whatever method is registered via `exposeMethods`, and `sdk-rpc`'s `RPC.exposeMethods` (`libraries/sdk-rpc/src/rpc.ts:42-47`) only flattens/aggregates methods — neither performs lock checking. Enforcement is therefore expected to happen per-API, and `fees` fails to do so.

As a result, calling `rpc.fees.getFees({ assetName: 'bitcoin', walletAccount: 'exodus_0' })` while `lockedAtom` is `true` reaches `addressProvider.getReceiveAddress` unguarded, derives/returns cached or freshly-derived address data, and computes/returns fee data — all while the wallet is supposed to be locked.

### Impact Explanation
This breaks the "locked means locked" invariant: an unprivileged dapp/origin can invoke a public wallet method to trigger address derivation and information disclosure (receive address, fee computation) while the wallet is locked, which should require the wallet to be unlocked first. This is an auth/lock-boundary bypass leaking wallet account address/fee information without user unlock, matching a scoped "locked-state action bypass / unauthorized information disclosure" impact category (not full compromise, since no signing/secrets are exposed — but a genuine lock-invariant violation reachable from any dapp).

### Likelihood Explanation
Fully reachable with no privileged state: the attacker only needs the wallet in a locked state (a normal, common condition) and access to the public `exodus.fees.getFees` RPC surface, which is marked `public: true` and exposed with no auth guard. The call requires only ordinary parameters (`assetName`, `walletAccount`) that any dapp can supply. It is deterministic and repeatable.

### Recommendation
Add a `lockedAtom` dependency to `createFees` (or to `feesApiDefinition`) and check `await lockedAtom.get()` at the start of `getFees`, throwing an error (consistent with `addressProviderApi`'s `'address-provider: wallet should be unlocked'` pattern) before any address derivation or fee computation occurs. Alternatively, route `fees`'s address resolution through `addressProviderApi` (which already enforces the lock) instead of directly depending on the un-gated `addressProvider` module.

### Proof of Concept
Integration test (mirroring `sdks/headless/__tests__/address-provider.test.js:91-98`):
```js
test('should not get fees if wallet locked', async () => {
  // wallet created but never unlocked, or unlocked then locked
  await exodus.application.unlock({ passphrase })
  await exodus.application.lock() // lockedAtom = true

  const getFees = exodus.fees.getFees({
    assetName: 'bitcoin',
    walletAccount: 'exodus_0',
  })

  await expect(getFees).rejects.toThrow(/locked/i) // currently resolves instead of rejecting
})
```
Expected (secure) behavior: rejects with a lock error, analogous to `addressProvider.getAddress`/`getReceiveAddress` rejecting with `'address-provider: wallet should be unlocked'`. Current behavior: resolves successfully with fee/address data, proving the lock bypass.
