The claim doesn't hold against the actual code. `BatchedStateUpdateRefs::batch_updates` explicitly deduplicates per-key writes across versions before any `to_result_slot`/`StateSlot` conversion happens: for value write ops (`Creation`/`Modification`/`Deletion`) it unconditionally "insert[s] and overwrite[s] the previous op" [1](#0-0) . Because `PerVersionStateUpdateRefs::index` sorts each shard by `(version, key_hash)` before batching, and the batch loop then iterates in that ascending-version order, the last insert for any given key is always the highest-version op — this is the invariant the code and its own test comments are designed to guarantee [2](#0-1) .

`StateUpdateRef::to_result_slot` itself is a pure, single-entry conversion from one `BaseStateOp` at one `version` into a `StateSlot` — it never receives two entries for the same key at different versions simultaneously, so there is no code path where a lower-version `Modification` can "immediately follow" and override a higher-version `Creation` inside this function [3](#0-2) . Any duplicate-key resolution across versions happens strictly before this call, in `batch_updates`, which already enforces highest-version-wins ordering.

The existing unit tests (`test_chunk_with_checkpoint`, `test_chunk_with_no_checkpoint`) already exercise exactly the scenario described — multiple writes to the same key at different versions — and assert that the batched result contains only the highest version's value, e.g. key `"A"` written at both v1 and v2 resolves to `"A2"` at version 2 [4](#0-3) .

Additionally, this code is a generic storage-layer indexing utility over `StateKey`/`BaseStateOp` and has no direct relationship to Move's `ObjectCore.owner` field, authority checks, or any custody/authorization logic — it operates purely on already-computed write sets from executed transactions, not on unprivileged input that could bypass Move-level ownership checks. There is no unprivileged entrypoint in this file that crosses a custody boundary; the described "stale owner" scenario is not reproducible given the sort-then-overwrite semantics of `batch_updates`.
