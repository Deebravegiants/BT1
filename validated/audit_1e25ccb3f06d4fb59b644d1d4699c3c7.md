### Title
Cross-tenant webhook spoofing via shop-domain header not covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that `ShopifyAPI::Webhooks::Registry.process` hands to the host application's handler are read from unauthenticated HTTP headers.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` decodes the `hmac-sha256` header value: [1](#0-0) 

`Registry.process` validates the HMAC over that signable string (the body) and then constructs the metadata passed to the app's handler using `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — none of which are part of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` only proves that the *body* was signed by someone in possession of `Context.api_secret_key`; it says nothing about which headers accompanied that body: [3](#0-2) 

Equality that should hold but is not enforced: `hmac-authenticated(shop) == header(shop)`. In reality only `hmac-authenticated(raw_body)` is checked; `shop` (and `topic`/`webhook_id`) are trusted directly from the request headers with no cryptographic binding to the signature.

Because Shopify's webhook signing scheme intentionally signs only the payload bytes (this is the documented, expected Shopify behavior, not unique to this library), a `(raw_body, hmac)` pair generated for a legitimate delivery to one shop remains a **valid** HMAC pair no matter what `shop-domain`/`topic`/`webhook-id` headers are sent alongside it. An unprivileged internet user who owns/operates any shop that has installed the target app can:
1. Trigger a real webhook delivery to their own shop’s endpoint (e.g., by creating an order), capturing a valid `(raw_body, hmac-sha256)` pair signed with the app’s `api_secret_key`.
2. Replay that exact `raw_body` + `hmac-sha256` value to the app's webhook endpoint, but substitute the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) headers with a victim shop's domain.
3. `HmacValidator.validate` passes because the body/hmac pair is still valid; `Registry.process` then calls the host app's handler with `shop: <victim's domain>` even though the payload actually originated from — and was signed for — the attacker's own shop.

If the host application's webhook handler trusts `WebhookMetadata#shop` as the tenant key for writes/reads (the documented, intended usage pattern of this library), this breaks the shop-tenant identity binding and allows cross-tenant data confusion/injection using only the attacker's own legitimate app installation — no `access_token`, no privileged account, and no possession of the app's `client_secret` is required.

### Impact Explanation
This crosses the tenant boundary that the library is meant to enforce for webhook consumers: the `shop` value delivered to the handler is not bound to the HMAC that authenticates the request, enabling an attacker who legitimately controls one tenant (their own installed shop) to inject payloads under an arbitrary other tenant's identity into any app built on this gem's `Webhooks::Registry`. This is a cross-tenant access vulnerability (Critical bucket per the impact taxonomy), since data intended to be scoped by shop can be attributed to a victim shop by a lower-privileged attacker who never obtained the app's secret or the victim's token.

### Likelihood Explanation
Likelihood is high for an app that has installed the library in a multi-tenant SaaS setup: any developer/attacker can register their own free/dev store, install the app, receive a real signed webhook, and replay it with modified headers to the app's public webhook endpoint. No secrets, no MITM, no social engineering are required — only standard HTTP tooling.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the authenticated material, or otherwise cryptographically tie the header-derived tenant identity to the signature that `HmacValidator` checks — e.g., have `Registry.process` cross-check the delivered `shop` against a tenant/session record obtained independently (such as the session store keyed by an already-registered webhook subscription per shop) before invoking the handler, rather than trusting `request.shop` as authenticated purely because `Utils::HmacValidator.validate(request)` returned true.

### Proof of Concept
1. As shop-A (attacker-owned, legitimately installed), perform an action that triggers a webhook (e.g., `orders/create`) and capture the raw POST body and the `X-Shopify-Hmac-Sha256` header value delivered to the app's webhook endpoint — this pair is validly signed with the app's real `api_secret_key`.
2. Replay an HTTP POST to the same webhook endpoint with:
   - Body: unchanged (the captured raw body).
   - `X-Shopify-Hmac-Sha256`: unchanged (the captured value).
   - `X-Shopify-Shop-Domain`: changed to `victim-shop.myshopify.com`.
   - `X-Shopify-Topic`/`X-Shopify-Webhook-Id`: optionally changed.
3. `ShopifyAPI::Webhooks::Registry.process` (as shown in `lib/shopify_api/webhooks/registry.rb:188-200`) calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the raw body against the secret (`lib/shopify_api/utils/hmac_validator.rb:12-31`), then invokes the handler with `shop: "victim-shop.myshopify.com"` even though the data actually belongs to shop-A.

          received_signature = verifiable_query.hmac
