### Title
Webhook `shop`, `topic`, and `webhook-id` are trusted from unauthenticated headers while HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` purely from HTTP headers, but `to_signable_string` (the value HMAC-verified by `Utils::HmacValidator`) covers only the raw request body. `Registry.process` validates the HMAC and then trusts `request.shop`/`request.topic` unconditionally when dispatching to the app's webhook handler, breaking the intended binding between "bytes verified by HMAC" and "identity fields acted upon."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from headers, none of which are part of the signed payload: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., it only proves the *body bytes* were signed by someone holding the app's `api_secret_key`, not that the `shop-domain`/`topic`/`webhook-id` headers are authentic or bound to that body: [3](#0-2) 

`Registry.process` validates only this body HMAC and then immediately trusts `request.shop` and `request.topic` to build `WebhookMetadata` passed to the host app's handler: [4](#0-3) 

This is the same bug class as the external report: a validation check that "answers permissively" by verifying one set of bytes (the body) while a different, unauthenticated field (the shop/topic header) is what the application actually acts upon — breaking the equality `shop_authenticated == shop_acted_upon`.

Because `api_secret_key` (the app's `client_secret`) is a single shared secret used to sign *every* shop's webhooks for a given app (not shop-specific), any tenant that receives a legitimately-signed webhook for their own shop possesses a valid `(raw_body, hmac)` pair. Since the header fields are outside the signature, that same `(raw_body, hmac)` pair remains valid if replayed with a different `shopify-shop-domain` header value.

### Impact Explanation
An attacker who is an installed/authorized user of the multi-tenant app (i.e., a normal but malicious merchant) can capture a legitimately Shopify-signed webhook delivered to their own shop, then replay the identical body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `topic`/`webhook-id`) header with a victim shop's domain. `Registry.process` will accept it as valid (`Utils::HmacValidator.validate` passes because the body/HMAC pair is genuinely valid) and hand the host app's handler a `WebhookMetadata` claiming the event originated from the victim shop. This is a cross-tenant data/event injection: the receiving app will process attacker-controlled data attributed to a shop the attacker does not own, potentially triggering state changes, notifications, or data associated with the victim tenant — a cross-tenant boundary violation caused entirely by this gem's request/HMAC verification design.

### Likelihood Explanation
Requires only that the attacker be a legitimate (if malicious) user of a shared/multi-tenant app who receives at least one real webhook (mandatory topics like `customers/data_request` are delivered to every installed shop), and the ability to send arbitrary HTTP requests with custom headers to the app's public webhook endpoint. No secrets, TLS interception, or privileged access needed — this is reachable by any unprivileged internet user who is a customer/merchant of the same multi-tenant app.

### Recommendation
Include `shop-domain`, `topic`, and `webhook-id` in the HMAC-signed material verified by `to_signable_string` (or otherwise cryptographically bind them, e.g. via a canonical string of headers + body), so that `HmacValidator.validate` proves the *entire* set of fields the handler acts on, not just the raw body bytes.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, sharing the same `api_secret_key`.
2. Shopify delivers a mandatory webhook (e.g., `customers/data_request`) to the attacker's shop with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid hmac of body>`, and some `raw_body`.
3. Attacker captures `raw_body` and the valid `X-Shopify-Hmac-Sha256` value.
4. Attacker sends a new HTTP request to the app's webhook endpoint with the same `raw_body` and same `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses this into `shop = "victim-shop.myshopify.com"`.
6. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` — validation passes.
7. `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)` is dispatched to the app's handler as if it were a genuine event from the victim shop. [5](#0-4) [6](#0-5)
