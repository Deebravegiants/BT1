### Title
Webhook shop-domain identity spoofing via HMAC that only signs the raw body, not the shop header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating `Utils::HmacValidator.validate(request)`, whose signable content is `Request#to_signable_string`, and that method returns only `@raw_body` [1](#0-0) . The `shop` value handed to the host application's handler comes from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is never part of the signed material [2](#0-1) . `Registry.process` validates the HMAC and then constructs `WebhookMetadata` directly from `request.shop`, `request.topic`, etc., without any cross-check that these header values are consistent with what was actually signed [3](#0-2) .

### Finding Description
The equality the gem is implicitly supposed to guarantee is: `shop delivered to the handler == shop that was cryptographically authenticated`. In reality the code guarantees only: `hmac(raw_body, api_secret_key) == received_hmac`, with no binding at all to `shop`, `topic`, `webhook_id`, or `api_version`.

Because the HMAC covers only the raw body bytes [1](#0-0) , and `shop`/`topic`/etc. are read straight from attacker-controllable HTTP headers [4](#0-3) , an unprivileged internet user who at any point legitimately captures one valid `(raw_body, hmac)` pair delivered by Shopify to the app's public webhook endpoint (for example, by installing the app on their own free/dev store and observing a webhook delivery) can replay that exact body/HMAC pair to the same endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` still succeeds because it only recomputes the signature over `@raw_body` [5](#0-4) , and `Registry.process` will happily dispatch a `WebhookMetadata` claiming an arbitrary victim `shop` to the app's handler [6](#0-5) .

### Impact Explanation
Any host application handler that trusts `WebhookMetadata#shop` to select which tenant's records to create/update/delete (the documented and expected usage pattern for this gem) can be made to apply attacker-supplied webhook body content under a victim shop's identity — a cross-tenant data-integrity/confidentiality break driven entirely by a header the gem never authenticates. This satisfies the "cross-tenant access" criterion for High/Critical impact, since the identity binding between authenticated bytes and the acted-upon `shop` field is broken.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one genuine `(raw_body, hmac)` pair for the target app — achievable by installing the app on an attacker-controlled shop (a normal, unprivileged action any developer/merchant can perform) and capturing the webhook Shopify sends. No access to `api_secret_key`, access tokens, or any privileged credential is required, and the replay itself is a simple unauthenticated HTTP POST to the app's public webhook endpoint with a modified header.

### Recommendation
Bind the header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) into the signed material verified by `HmacValidator`, or otherwise cryptographically bind them to the specific delivery, so that changing any of these headers invalidates the HMAC. At minimum, document that host applications must not trust `WebhookMetadata#shop`/`topic` without independently correlating the webhook to an expected, already-known shop/session before acting on it.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and the genuine `x-shopify-hmac-sha256` value sent by Shopify.
2. Attacker sends a new HTTP POST to the app's webhook endpoint with:
   - Body: the exact captured `raw_body`
   - Header `x-shopify-hmac-sha256`: the exact captured signature
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (arbitrary victim)
   - Header `x-shopify-topic`: unchanged (e.g. `orders/create`)
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only [1](#0-0)  and it matches, so `Registry.process` proceeds.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)` [7](#0-6)  and invokes the host app's handler, which processes attacker-controlled body content attributed to the victim shop.
