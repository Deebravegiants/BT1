Confirmed root-cause candidate: `IntentsBase.sol` / `IntentGatewayV2.sol` collect `order.fees` in the fee token that is active **at placement time** (`IDispatcher(hostAddr).feeToken()`) and store only the *amount* under the `TRANSACTION_FEES` sentinel key, with no record of which token it was collected in [1](#0-0) . At settlement/refund time, `_withdraw()` releases `fees` by calling `IERC20(IDispatcher(host()).feeToken()).safeTransfer(...)` — i.e. it reads the **current** fee token, not the one that was actually escrowed [2](#0-1) .

### Title
Stale/mismatched fee-token accounting can permanently strand order fees in `IntentGatewayV2` after a host fee-token swap - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`EvmHost` allows governance to swap `feeToken` via `updateHostParams`, and only guards against the *host's own* balance being non-zero in the old token before allowing the swap [3](#0-2) . It does not, and cannot, know about balances held by downstream `IApp` integrations such as `IntentGatewayV2`. `IntentsBase._withdraw` releases `order.fees` using `IDispatcher(host()).feeToken()` read at redemption time [2](#0-1) , while the fee was collected and escrowed in whatever token was `feeToken()` at `placeOrder` time [1](#0-0) . This is exactly the bug class from the Perennial `OracleFactory` report: value is escrowed under one token identity but the withdrawal path is keyed to a live, mutable token pointer instead of the token that was actually deposited, and there is no explicit governance-level rescue path (unlike `BandwidthManager`'s `Withdrawal{token,...}` struct or `EvmHost.withdraw`'s `WithdrawParams.token` field, which both name the token explicitly to survive a fee-token swap [4](#0-3) [5](#0-4) ).

### Finding Description
1. A user calls `placeOrder` with `order.fees > 0`. The gateway reads `feeToken = IDispatcher(hostAddr).feeToken()` (call it token A) and pulls `order.fees` of token A into the gateway, recording only the amount at `_orders[commitment][TRANSACTION_FEES] = order.fees` [1](#0-0) .
2. Before the order is filled/cancelled, Hyperbridge governance rotates the host's fee token from A to B via `EvmHost.setIsmpHost`/`updateHostParams` — a legitimate, unprivileged-reachable-by-timing operation from the intent placer's perspective (the placer does not control or synchronize with this governance action, and there is no re-entrancy/atomicity between order lifetime and this parameter).
3. When the order is later filled or cancelled/refunded, `_withdraw()` is invoked with `finalize = true`. It computes `fees = _orders[commitment][TRANSACTION_FEES]` (a token-A-denominated amount) but calls `IERC20(IDispatcher(host()).feeToken())` which now resolves to token B [2](#0-1) . The contract then attempts `safeTransfer` of `fees` units of token B to the beneficiary.
4. If the gateway happens to hold ≥ `fees` of token B (e.g., from other orders' fee escrows, protocol dust, or surplus), the transfer succeeds silently — but it pays the beneficiary out of *other users'* token-B holdings, and the original token-A fee escrow is never decremented (the code deletes `_orders[commitment][TRANSACTION_FEES]` unconditionally regardless of which token is actually transferred), permanently orphaning the token-A balance in the contract with no accounting key pointing to it.
5. If the gateway does not hold enough token B, the `safeTransfer` reverts, which (depending on call site) can revert the entire settlement transaction — for `RedeemEscrow`/`onAccept()` cross-chain paths this can block finalization of an otherwise-valid escrow release, and for the `onGetResponse` cancellation path it can block refunds of the (non-fee) escrowed principal since `_withdraw` is one atomic call that also releases the principal tokens in the same function.
6. Either way, the token-A fee amount becomes permanently stuck: there is no `TRANSACTION_FEES`-token field recorded per order, no governance sweep/withdraw function equivalent to `BandwidthManager.onAccept`'s `Withdrawal{token,...}` present in `IntentGatewayV2`/`IntentsBase` to name and drain a stale fee token, and `_sweepDust`/`SweepDust` only operates on tokens explicitly named by governance after the fact with no linkage back to the specific stranded per-order accounting [6](#0-5) .

### Impact Explanation
This can result in (a) permanent freezing of the escrowed solver/relayer fee token for every order placed before a fee-token rotation and settled after it, and (b) in the revert scenario, denial of settlement/refund for the order's principal escrow bundled in the same `_withdraw` call, i.e. users' or solvers' legitimately owed principal tokens become undeliverable until governance intervenes with a bespoke fix (there is no built-in per-token, per-order rescue). This matches "permanent freezing of funds" impact criteria. Fee-token swaps are a documented, expected governance operation (see `EvmHost.updateHostParams`/`CannotChangeFeeToken` check and `BandwidthManager`'s explicit accommodation for "host occasionally swaps fee tokens"), so this is not a hypothetical, unsupported configuration.

### Likelihood Explanation
Medium. Fee-token rotation is a supported, documented, and evidently anticipated governance action across the codebase (`BandwidthManager` and `EvmHost.withdraw` both explicitly design around it), so it is realistic to occur during the lifetime of long-lived cross-chain orders (which can remain open for the full `order.deadline` window, potentially spanning governance actions). No malicious actor is required — this triggers from ordinary protocol operation (a benign governance fee-token update) intersecting with normal user order flow; the intents/order flow is reachable by any unprivileged user placing an order with `order.fees > 0`.

### Recommendation
Record the actual fee token address alongside the escrowed fee amount per order (e.g., `_orders[commitment][TRANSACTION_FEES]` amount plus a parallel `_orderFeeToken[commitment]` mapping set at `placeOrder` time), and have `_withdraw` read and transfer that recorded token rather than re-querying `IDispatcher(host()).feeToken()` at redemption time. Additionally/alternatively, follow the `BandwidthManager`/`EvmHost.withdraw` pattern and add an explicit governance-only sweep that names the stale token, decoupled from the atomic principal-release path, so a failed/mismatched fee transfer cannot block release of the underlying escrowed principal.

### Proof of Concept
1. Deploy `EvmHost` with `feeToken = TokenA`, and `IntentGatewayV2` pointed at it.
2. User calls `placeOrder(order, graffiti)` with `order.fees = 100e18`, paid in `TokenA`; gateway now holds 100 TokenA under `_orders[commitment][TRANSACTION_FEES] = 100e18` [1](#0-0) .
3. Governance calls `EvmHost.updateHostParams` (via `HostManager.onAccept`) setting `feeToken = TokenB`; this succeeds because the check only inspects `IERC20(oldFeeToken).balanceOf(address(this))` on the *host* contract, not on `IntentGatewayV2` [3](#0-2) .
4. Solver fills the order (or user cancels after deadline); settlement reaches `_withdraw(body, isRefund, true)`.
5. `_withdraw` computes `fees = 100e18` (TokenA-denominated) and executes `IERC20(TokenB).safeTransfer(beneficiary, 100e18)` [2](#0-1) . If the gateway's TokenB balance is insufficient, this reverts the whole settlement (blocking release of principal escrow bundled in the same call); if sufficient (from other orders' escrow), it pays out TokenB drawn from unrelated escrow while the 100 TokenA remains permanently stuck in the gateway with no per-order key referencing it, and no governance withdraw function exists in `IntentsBase`/`IntentGatewayV2` to recover it by token address the way `BandwidthManager.onAccept`'s `Withdrawal{token,...}` does [7](#0-6) .

    function _sweepDust(SweepDust memory req) internal {
        uint256 outputsLen = req.outputs.length;
        for (uint256 i; i < outputsLen;) {
            TokenInfo memory info = req.outputs[i];
            address token = address(uint160(uint256(info.token)));
            uint256 amount = info.amount;

                IERC20(token).safeTransfer(req.beneficiary, amount);
            }

            }

        }
