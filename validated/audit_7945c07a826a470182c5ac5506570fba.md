### Title
Cross-Tenant Webhook Spoofing via Unsigned `shop`/`topic`/`webhook-id` Headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values used for tenant identification and dispatch are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only that the body's HMAC is correct and then trusts these header-derived fields unconditionally to route the event and populate `WebhookMetadata`. Because all webhooks for an app share a single `api_secret_key`, an attacker who has legitimately received (or replayed) one validly-signed webhook body for their own shop can resubmit that same body with an arbitrary `shopify-shop-domain` header, causing the app to process the payload as belonging to a different tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from headers, none of which are included in the signed string: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.topic` for handler dispatch and `request.shop` for tenant identification, passing it straight into `WebhookMetadata`: [3](#0-2) 

The equality that should hold is: `shop covered by HMAC == shop acted upon by the handler`. Here, `shop-domain header (acted upon)` ≠ `bytes covered by HMAC (raw_body only)`. Since `HmacValidator.validate_signature` computes the digest with the single shared `Context.api_secret_key` (not a per-shop secret) using only the body: [4](#0-3) 

any request bearing a body+HMAC pair that once validated for shop A (e.g., replayed by a malicious merchant of shop A, or a body incidentally shared/guessable across shops) will also validate when the `shopify-shop-domain` header is changed to shop B, since the header is never part of the signed material. The handler code, which typically keys off `data.shop` to look up per-tenant sessions/tokens and act on that tenant's data, will then process the event under the wrong tenant identity.

### Impact Explanation
This breaks the tenant-identity binding the HMAC is supposed to enforce for webhook authenticity: the signature attests only to body integrity, not to the app-controlled tenant/topic metadata that downstream application logic actually relies on. This enables cross-tenant confusion — an attacker controlling or observing a valid webhook body for one shop can cause the receiving app to associate/process that data under an arbitrary other shop identifier, which qualifies as Critical (cross-tenant access) per the scan's impact criteria.

### Likelihood Explanation
Exploitation requires the attacker to possess one valid `(raw_body, hmac)` pair — obtainable as the merchant of their own installed shop (a fully unprivileged position relative to other tenants of the same app) — and the ability to POST to the app's public webhook endpoint with modified `shopify-shop-domain`/`x-shopify-shop-domain` headers, which is standard HTTP client capability with no credentials required beyond a normal shop installation. Likelihood is moderate-to-high depending on how strictly the host handler validates `data.shop` against expected merchant context, but the gem itself provides no protection against this header/body binding mismatch.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC-signed material (or otherwise cryptographically bind them to the payload) so that `Registry.process` can reject requests where header-derived routing/tenant fields do not match what was actually signed. At minimum, document that the HMAC only covers the raw body and that consuming applications must independently authenticate the `shop` header via other means (e.g., cross-checking against a known/expected shop for the endpoint) before trusting it for tenant-scoped operations.

### Proof of Concept
```ruby
# Attacker is a legitimate (unprivileged) merchant of shop-a.myshopify.com
# and receives a real, validly-signed webhook from Shopify:
raw_body = '{"id":123}'
valid_hmac_for_body = "<hmac captured from Shopify's real webhook call>"

# Attacker replays the same body+hmac to the app's webhook endpoint,
# but swaps the shop-domain header to a victim tenant:
headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => valid_hmac_for_body,
  "shopify-shop-domain" => "victim-shop.myshopify.com", # forged
  "shopify-webhook-id" => "attacker-chosen-id",
  "shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds because it only checks raw_body,
# and the handler receives WebhookMetadata with shop: "victim-shop.myshopify.com"
# even though the signature never covered the shop field.
``` [5](#0-4)
