### Title
Wallet Unlock Passphrase Cached Unencrypted in `chrome.storage.session` - (File: `features/application/src/modules/passphrase-cache.ts`)

### Summary
The `PassphraseCache` module persists the user's plaintext wallet unlock passphrase into a storage implementation aliased to `sessionStorage`, which is backed by `chrome.storage.session` with zero encryption. This is a stronger analog of the reported "unencrypted session data" issue: instead of non-sensitive intermediate program state, the data at risk here is the actual wallet passphrase, whose disclosure enables direct wallet unlock/compromise.

### Finding Description
When `cachePassphrase` is enabled, `features/application/src/index.ts` wires `passphraseCacheDefinition` with `storage: { namespace: 'passphrase' }` and `aliases: [{ interfaceId: 'storage', implementationId: 'sessionStorage' }]`: [1](#0-0) 

`sessionStorage` resolves to `createSessionStorage`, which is a thin wrapper over the unsafe (non-encrypting) storage adapter, falling back only to in-memory storage if `chrome.storage.session` is unavailable: [2](#0-1) 

`createSessionStorage` delegates to `createStorage` from `unsafe-storage`, which performs raw `store.get`/`store.set` calls with only an identity transform (`transformOnWrite = identity`, `transformOnRead = identity`) — i.e., no cryptographic transformation of values at all: [3](#0-2) 

The `PassphraseCache.set` method then writes the raw passphrase string directly into this storage under the `passphrase` key: [4](#0-3) 

This passphrase is written whenever the wallet is unlocked with a passphrase or the passphrase is changed: [5](#0-4) 

and it is later used to auto-unlock the wallet: [6](#0-5) 

By contrast, other Hydra storage paths that handle sensitive secrets go through explicit encryption layers, e.g. `@exodus/storage-encrypted`, which wraps a base storage with `encrypt`/`decrypt` crypto functions before persisting: [7](#0-6) 

and the browser-extension-adapters package explicitly documents `/unsafe-storage` as "no encryption built in" versus `/encrypted-storage` for sensitive data: [8](#0-7) 

The passphrase cache, however, is deliberately routed to the unencrypted `sessionStorage` implementation rather than `encrypted-storage`, meaning the wallet's unlock secret sits in plaintext in `chrome.storage.session`.

### Impact Explanation
`chrome.storage.session` in Manifest V3 extensions is process-memory-backed but is still accessible to any code executing with the extension's storage permissions (e.g., the extension's own service worker/background context, or via any future code-execution/XSS-class bug in the extension surface, or extension storage inspection via devtools with appropriate access). Unlike the zkPass report, where only "non-private, publicly derivable program state" was stored, here the disclosed value is the literal wallet unlock passphrase — possession of it, combined with access to the encrypted seed storage, allows an attacker to fully unlock and decrypt the wallet's seed, leading to direct wallet compromise and unauthorized signing capability. This crosses the "encrypted storage" and "direct wallet-compromise impact" boundaries called out in the validation rules.

### Likelihood Explanation
This code path is only active when the `cachePassphrase` feature flag is enabled by the integrating platform (e.g., browser extension builds using `passphraseCacheMaxTtl`/`cachePassphrase` config). Given that, the passphrase is cached on every unlock and every passphrase change while the feature is enabled, and remains readable in cleartext until the TTL/alarm-based clear fires. Any read access to the extension's storage layer (whether through a bug elsewhere in the same extension's privileged context, a supply-chain issue in a dependency with storage access, or forensic access to the browser profile before the session storage is cleared) yields the raw secret without needing to break any cryptography.

### Recommendation
Route the passphrase cache through the existing `@exodus/storage-encrypted` / `encrypted-storage` adapter (already used elsewhere in the codebase) instead of the raw `sessionStorage` (`unsafe-storage`) implementation, so the cached passphrase is encrypted at rest with a key not itself persisted in the same unencrypted store — mirroring how seed material is protected via `seco-storage`/`storage-encrypted`.

# @exodus/browser-extension-adapters

Storage adapters for use in browser extensions.

## /unsafe-storage

Unsafe = no encryption built in. Conforms to [`@exodus/storage-spec`](../../adapters/storage-spec).

```js
import createUnsafeStorage from '@exodus/browser-extension-adapters/unsafe-storage'

const storage = createUnsafeStorage({ store: chrome.storage.local })
// use as any other `@exodus/storage-spec` compliant interface
```

## /encrypted-storage

Returns an instance of [@exodus/storage-encrypted](../../adapters/storage-encrypted), which you must unlock with a pair of encrypt/decrypt functions before use.

```js
import createUnsafeStorage from '@exodus/browser-extension-adapters/unsafe-storage'
import createEncryptedStorage from '@exodus/browser-extension-adapters/encrypted-storage'

const unsafeStorage = createUnsafeStorage({ store: chrome.storage.local })
const encryptedStorage = createEncryptedStorage({ unsafeStorage })
// use encryptedStorage as any other `@exodus/storage-spec` compliant interface
```
