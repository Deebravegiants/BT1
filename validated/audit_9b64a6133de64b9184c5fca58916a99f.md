### Title
Webhook HMAC signature does not bind the `shop` (tenant) identity, allowing shop-domain spoofing via header substitution - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates its HMAC over the raw body only, while the `shop` value that is handed to the application's webhook handler (used as the tenant identifier) is read from the `X-Shopify-Shop-Domain` header, which is completely outside the signed content. This breaks the identity binding `shop_authenticated == shop_used_by_handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, however, is taken straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the HMAC at all: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the raw body) and compares it to the `hmac` header value — it never touches `shop`: [3](#0-2) 

`Registry.process` trusts this validation result and then forwards the attacker-controllable `request.shop` directly into `WebhookMetadata`, which is the tenant identifier the host application's handler will act on: [4](#0-3) 

This is the exact class of bug described in the reference report: a value that materially affects the operation being performed (`shop`, the tenant boundary) is not covered by the identity/authenticity check (`HMAC`) that the gem enforces on a *different* field (the body only). In the reference report, prices for actively-adjusted collateral/debt were validated for staleness while other prices/collaterals feeding into the same risk calculation were not; here, the body is authenticated but the `shop` field feeding into the same call is not authenticated at all.

Because `Digest.hexencode(Base64.decode64(shopify_header("hmac-sha256")))` is compared only against `@raw_body`, any request with a body+hmac pair that Shopify has legitimately signed for **shop A** will still pass validation if the attacker (who controls shop A, an app merchant) resends that exact body+hmac pair but swaps the `X-Shopify-Shop-Domain` header to **shop B**. The equality that should hold — "the shop whose secret validated this HMAC" == "the shop passed to the handler" — is violated because the header is never part of the signed material.

### Impact Explanation
This allows a malicious but otherwise unprivileged app merchant (shop A) to forge webhook events that the host application will process as if they originated from a different shop (shop B), since the gem's own validation provides no binding between the authenticated payload and the shop identity it will be attributed to. Depending on how the host app's handler code uses `data.shop` (e.g., to look up/update per-shop records, trigger GDPR redaction, or drive per-tenant business logic), this is a cross-tenant boundary break — the strongest applicable impact bucket for this gem (cross-tenant access) is satisfied because the SDK itself supplies no protection against this, and correctly implemented merchants relying on this library's HMAC check to authenticate the "shop" field are misled into trusting an unauthenticated value.

### Likelihood Explanation
Any real, currently-installed merchant of the app can capture a valid webhook delivery for their own shop (a normal, unprivileged action within their control) and replay the exact raw body/HMAC pair to the app's webhook endpoint with only the shop-domain header changed. No secrets, tokens, or elevated access are required — just observing one's own webhook traffic, which is trivially available to any merchant using the app.

### Recommendation
Bind the shop identity into the value that is verified. At minimum, `Utils::HmacValidator.validate` (or `Webhooks::Registry.process`) should not rely solely on the header-provided `shop`; the signable string / validation routine should incorporate the shop domain (or the caller should cross-check the header-provided shop against a shop derived from data that is actually inside the signed body, or from a known registered shop matching the specific webhook subscription) before passing it to `WebhookMetadata`. Practically: require callers to pre-associate webhook requests with a specific expected shop (e.g., validate `request.shop` against the shop for which the endpoint/subscription was registered) rather than trusting the header value implicitly once the raw-body HMAC passes.

### Proof of Concept
1. Attacker installs the app on `shop-a.myshopify.com` (legitimate, unprivileged merchant access).
2. Attacker triggers/observes a genuine webhook delivery to the app's endpoint:
   - Headers: `X-Shopify-Shop-Domain: shop-a.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, `X-Shopify-Topic: <topic>`
   - Body: `<raw_body>` (any topic whose handler logic doesn't strictly require shop-specific content, e.g., `app/uninstalled` or a minimal-body topic)
3. Attacker resends the identical `<raw_body>` and identical `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com` (a victim shop also using the app).
4. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC solely from `@raw_body` and succeeds, because the body and HMAC are unchanged and valid.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` proceeds and invokes the handler with `WebhookMetadata.new(... shop: "shop-b.myshopify.com" ...)`, even though Shopify never signed anything on behalf of `shop-b.myshopify.com`.

          received_signature = verifiable_query.hmac
