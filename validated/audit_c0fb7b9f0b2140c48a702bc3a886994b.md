### Title
Webhook `shop`/`topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches the handler using the `shop` (and `topic`) values taken from HTTP headers that are never included in that HMAC computation. Because the HMAC is computed with the app's single shared `api_secret_key` (identical for every shop that installs the app), any shop that legitimately receives a signed webhook from Shopify can replay that exact body/HMAC pair to the app's webhook endpoint while substituting a different `shopify-shop-domain` (and/or `shopify-topic`) header, and the library will accept it as authentic.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`. Its `to_signable_string` returns only the raw body: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers that are not part of the signed content: [2](#0-1) 

`Registry.process` verifies only `Utils::HmacValidator.validate(request)` (which, per the class above, checks nothing but the body) and then immediately trusts `request.topic` and `request.shop` to route and label the event: [3](#0-2) 

`HmacValidator.validate` computes the HMAC using the app-wide `Context.api_secret_key` (the same secret for all shops/tenants using this app), comparing it only against `verifiable_query.to_signable_string`, i.e. the body: [4](#0-3) 

**Identity binding broken:** `authenticated(body) == shop-that-body-was-signed-for` is assumed, but the library only proves `authenticated(body) == "signed by this app's shared secret"`. The `shop-domain` header used to build `WebhookMetadata.shop` (and consequently drive per-tenant business logic in the host app) is never bound to the HMAC, so `request.shop` can be forged independently of body integrity.

### Impact Explanation
An attacker who legitimately installs the app on their own store receives real, validly HMAC-signed webhooks from Shopify for their own shop's events. Because the signing secret is shared across every tenant of the app (not shop-specific), the attacker can replay the identical `(raw_body, hmac)` pair to the app's public webhook endpoint while forging `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) to name a victim shop. `Registry.process` will pass HMAC validation and invoke the registered handler with `WebhookMetadata` claiming the victim shop as the source, causing the host application to execute tenant-scoped business logic (e.g. data deletion, order/customer processing, GDPR redact handlers) attributed to the wrong tenant. This is a cross-tenant confusion vulnerability stemming directly from this gem's verification design.

### Likelihood Explanation
Any unprivileged user who can install the target app on any shop (including a free/trial install of their own) can capture a real signed webhook and replay it with modified headers against the app's public webhook endpoint — no access token, secret, or privileged account is required beyond normal, self-service app installation.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed content, or otherwise cryptographically bind them (e.g., require the host application to look up and compare the shop against a per-request authenticated context) before `Registry.process` dispatches to a handler. At minimum, document prominently that callers must independently verify `request.shop` against their own tenant/session store, since the HMAC check alone does not authenticate the shop or topic headers.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`; Shopify sends a real webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and some JSON body.
2. Attacker captures this request (e.g., via a network proxy they control, since it is delivered to their own configured endpoint).
3. Attacker resends the exact same body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body` — it succeeds because the body is unchanged.
5. The handler executes with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, causing the host app to act as though the event originated from the victim tenant.

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))

          received_signature = verifiable_query.hmac
