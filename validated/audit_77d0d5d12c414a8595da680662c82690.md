## Analog Found

### Title
Unchecked ERC20 `transfer()` return value in Tron `IntentGatewayV2.withdraw` permanently burns escrowed funds without paying the beneficiary - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` moves escrow accounting and token payout in `withdraw()` using a raw low-level `.call` to the token's `transfer` selector instead of OpenZeppelin's `SafeERC20.safeTransfer` (which the non-Tron `IntentsBase.sol`/`IntentGatewayV2.sol` implementations use). The code only checks that the low-level call itself did not revert, never inspecting the boolean return value that ERC20/TRC20 `transfer()` is specified to return on failure. If the token returns `false` (e.g., insufficient contract balance, blacklist, or any non-reverting failure mode) the call still reports `success == true`, so the function unconditionally decrements the escrow (`_orders[body.commitment][token] -= amount`) as though the beneficiary was paid — while they received nothing.

### Finding Description
`withdraw()` is reached from `onAccept` (cross-chain `RedeemEscrow`/`RefundEscrow` messages authenticated as coming from a registered peer gateway) and from `onGetResponse` (cancel-from-source flow) — both externally triggerable by relayers delivering otherwise-legitimate messages. [1](#0-0) [2](#0-1) 

Inside `withdraw`, the ERC20 payout path is: [3](#0-2) 

```solidity
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

`success` here reflects only whether the external call reverted, not whether `transfer()` returned `true`. Per the ERC20 standard, a compliant token may legitimately return `false` instead of reverting when a transfer cannot be completed (e.g., the gateway's on-chain balance of that token is insufficient because of prior partial fills, protocol dust accounting drift, fee-on-transfer style tokens, or any token whose `transfer()` implementation returns `false` on failure). The same unguarded pattern is reused for the accumulated transaction fee payout a few lines later: [4](#0-3) 

and again in the governance-triggered `SweepDust` handler earlier in the same file: [5](#0-4) 

By contrast, the reference (non-Tron) implementation of the same withdrawal logic in `IntentsBase.sol` uses `SafeERC20.safeTransfer`, which explicitly checks the returned boolean (and handles no-return-value tokens) and reverts on failure, precisely to avoid this class of bug: [6](#0-5) 

This is the same root-cause shape as the referenced WJLP finding: a value-transfer call whose actual success/amount is not verified against internal accounting, followed by an unconditional zeroing/decrement of that accounting, resulting in the beneficiary receiving less (here, potentially zero) than what the ledger says was paid out.

### Impact Explanation
If the underlying token's `transfer()` returns `false` rather than reverting on failure (a state ERC20/TRC20 explicitly allows), the beneficiary (solver or user) receives no tokens, yet:
- The escrow slot `_orders[body.commitment][token]` is permanently decremented, so the funds can never be reclaimed via a retry of `withdraw` (a second delivery of the same message is prevented by `_filled`/receipt replay protection at the host level, and re-authentication of the same commitment is not possible).
- `_filled[body.commitment]` is already set at function entry, marking the order as settled regardless of whether payment actually succeeded.

The net effect is a silent, permanent loss of the beneficiary's escrowed tokens — the funds remain stuck in the gateway contract with no accounting path to recover them, i.e., "permanent freezing of funds" for the affected order.

### Likelihood Explanation
This is reachable by any legitimate, unprivileged flow: a relayer delivering a valid `RedeemEscrow`/`RefundEscrow` message or GET response for an order whose escrowed token's `transfer` call returns `false` under ordinary conditions (insufficient balance from prior fee/dust rounding, a non-standard/blacklisting TRC20 token, or any token that follows the ERC20 spec's "return false" failure convention rather than "always revert"). No malicious actor or privileged role is required — a single otherwise-correct message delivery is sufficient to trigger the loss.

### Recommendation
Replace the raw `.call` + `success`-only checks in `withdraw()` (and in the `SweepDust` fee/dust payout paths) with OpenZeppelin's `SafeERC20.safeTransfer`, matching the pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol`. This validates both that the call did not revert and that any returned boolean is `true` (or that no return data is acceptable per SafeERC20's semantics), ensuring escrow accounting is only decremented when the transfer actually succeeded.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with an ERC20/TRC20 token whose `transfer()` implementation returns `false` on failure instead of reverting (permitted by the standard).
2. Place and fill/cancel an order such that, at the time `withdraw()` executes, the gateway's balance of that token is insufficient to cover `amount` (e.g., due to accumulated rounding/dust or a race with another withdrawal), but the token doesn't revert — it returns `false`.
3. `token.call(...)` returns `success == true` (the call executed without reverting) even though `transfer` internally returned `false` and moved no tokens.
4. `withdraw()` proceeds past the `if (!success) revert TransferFailed();` check, decrements `_orders[body.commitment][token] -= amount`, and emits `EscrowReleased`/`EscrowRefunded`.
5. The beneficiary's balance is unchanged, but the escrow record shows the funds as paid out and `_filled[body.commitment]` is set — the tokens are unrecoverably stuck in the gateway contract.
