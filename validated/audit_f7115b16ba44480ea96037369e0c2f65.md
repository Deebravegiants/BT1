### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity is trusted from unauthenticated HTTP headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying field `shop` (and `topic`, `webhook_id`, `api_version`) from HTTP headers, but the HMAC signature that `Registry.process` validates is computed only over the raw request body. This breaks the identity binding `authenticated(bytes) == bytes acted upon`: the bytes that are cryptographically verified (the body) are not the bytes the host application uses to decide *which shop's* access token/session/state to operate on.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers, none of which are part of the signed string: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC and, on success, unconditionally trusts `request.shop` (and the other header-derived fields) when building the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

`WebhookMetadata.shop` is a plain, unauthenticated `String` field: [5](#0-4) 

Because `OpenSSL.secure_compare(computed_signature, received_signature)` in `HmacValidator.validate_signature` only checks the body against the secret, a valid `(body, hmac)` pair computed for **any** shop remains valid no matter what `shop-domain`, `topic`, `webhook-id`, or `api-version` headers accompany it: [6](#0-5) 

This is the same bug class as the reported prototype-pollution issue: a value that flows into a security-relevant decision (there: `cycleCounter`/`txId` object keys; here: the `shop` tenant identifier) is taken directly from attacker-influenced, unauthenticated input instead of from the cryptographically verified payload.

### Impact Explanation
An attacker who controls a legitimate Shopify store (an "unprivileged internet user" with respect to the target app/merchant) can trigger real webhooks for their own shop and obtain a genuine `(raw_body, hmac)` pair signed with the target app's `client_secret`. Because the signature never covers the `shop-domain`, `topic`, or `webhook-id` headers, the attacker can POST that identical body/hmac to the victim app's webhook endpoint while substituting the `shop-domain` header for a different (victim) shop. `Registry.process` will accept the HMAC as valid and hand the handler a `WebhookMetadata` claiming the (attacker-controlled) body originated from the victim shop. Any application logic that uses `data.shop` to select the session/access-token, or that acts on the (attacker-chosen) `data.body` in the context of the victim shop, is cross-tenant compromised - the app can be tricked into applying attacker-controlled data/actions to another merchant's store/session. This matches the "cross-tenant access" Critical impact category, since a genuine identity binding (which shop this webhook truly concerns) is broken.

### Likelihood Explanation
Exploitability only requires: (1) the attacker owning any store that installs the same app (to obtain a real signed body/hmac for a topic whose body is attacker-influenceable, e.g. `orders/create`, `customers/update`), and (2) direct HTTP access to the app's public webhook endpoint to replace headers. No access token, `client_secret`, or privileged account is required, and no TLS interception is needed since the request is crafted fresh by the attacker rather than intercepted in transit.

### Recommendation
Bind the identity-relevant fields into the signed material, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the verified body (e.g., include them in the HMAC computation, or require the host application to cross-check the header-derived shop against a value embedded in the verified body/GraphQL webhook payload). At minimum, document prominently that `WebhookMetadata#shop`/`topic`/`webhook_id` are **not** authenticated by the HMAC check and must not be trusted for tenant selection without additional verification (e.g., confirming the shop has an active, previously-established session before acting).

### Proof of Concept
1. Attacker installs the target app on their own dev store `attacker.myshopify.com`.
2. Attacker triggers a webhook whose body they can influence (e.g. `orders/create` with a controlled `note`/line item), causing Shopify to POST to the app with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: H`, body `B`, where `H = HMAC_SHA256(client_secret, B)`.
3. Attacker replays their own crafted HTTP POST directly to the app's public webhook URL with the **same** body `B` and `hmac` header `H`, but changes `x-shopify-shop-domain` to `victim.myshopify.com` (and optionally spoofs `x-shopify-topic`/`x-shopify-webhook-id`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which only checks `B` against `H` — [7](#0-6)  — and succeeds.
5. The app's registered handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled B>, ...)` — [8](#0-7)  — and, if it looks up the victim's session/access token by `data.shop` to act on `data.body`, performs attacker-controlled operations under the victim's tenant context.
