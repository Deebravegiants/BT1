Webhook shop-domain/topic identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-checked signable payload from the raw request body only, while the `shop` and `topic` fields that the registry uses to route and tag the delivered data to a specific merchant are read directly from unauthenticated HTTP headers.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only [1](#0-0) . `Request#shop` and `Request#topic` are pulled straight out of the `shopify-shop-domain`/`shopify-topic` (or `x-shopify-*`) headers with no cryptographic binding to those headers [2](#0-1) . `Registry.process` validates only `Utils::HmacValidator.validate(request)`, i.e. HMAC(secret, raw_body) — it never checks that `shop`/`topic` are consistent with anything signed — and then forwards `request.shop` and `request.topic` unauthenticated into `WebhookMetadata`, which is handed to the app's webhook handler as the tenant/topic identity [3](#0-2) .

Because the webhook secret (`Context.api_secret_key`) is the same app-wide client secret used for every shop/topic delivered to that app (not per-shop), any entity capable of triggering one legitimately-signed webhook delivery for *any* shop (e.g., their own installed test shop) obtains a `(raw_body, valid hmac)` pair. Since `shop-domain` and `topic` are not part of the signed content, that same `(body, hmac)` pair remains HMAC-valid when replayed with a forged `shop-domain` header claiming to be a different, victim shop, and/or a forged `topic` header. `HmacValidator.validate` will return `true`, and the handler will receive `WebhookMetadata` claiming the payload originated from the victim shop.

This breaks the intended binding: `shop_that_produced_valid_HMAC == shop_reported_to_handler`. The equality that should hold is `hmac_valid(body) ⇒ shop_header == shop_that_generated(body)`, but here `shop_header` is fully attacker-controlled and independent of the HMAC check.

### Impact Explanation
If a host application's webhook handler trusts `WebhookMetadata#shop` (as documented/intended usage — the library's own doc and tests show handlers keying off `data.shop`) to select the tenant record to mutate, an attacker who can obtain one validly-signed webhook body (from their own shop) can forge deliveries that are attributed to any other shop's `shop-domain`, causing cross-tenant data processing (e.g., a fake `app/uninstalled`, `customers/redact`, or `orders/create` event being applied against another merchant's records). This matches the "cross-tenant access" Critical-impact category, since the identity boundary (shop tenant) enforced by this gem's HMAC check is not actually binding the shop field it hands to the handler.

### Likelihood Explanation
Exploitation requires only: (1) ability to send arbitrary HTTP requests to the app's webhook endpoint (any unprivileged internet user, since these endpoints are typically public), and (2) one legitimately HMAC-signed payload, obtainable by installing the app on an attacker-controlled development shop (a normal, unprivileged path — installing an app does not require special access) and capturing its own inbound webhook. No access token, `api_secret_key`, or privileged account is needed. Given the gem's `Request`/`Registry` API is the documented mechanism apps are told to use for webhook shop attribution, this is a defect in the gem's own binding logic, not a misuse of an undocumented API.

### Recommendation
Include `shop` and `topic` (and ideally `webhook_id`) in the HMAC-covered signable string, or otherwise cryptographically bind them (e.g., require the caller to separately verify `shop` against a known/allow-listed installed-shop list before trusting it), so that `HmacValidator.validate` fails whenever the shop/topic headers do not match what was actually signed by Shopify for that delivery.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) to capture `raw_body` and the resulting `x-shopify-hmac-sha256` header — both valid since the shared `api_secret_key` HMACs only the body.
2. Attacker replays this exact `raw_body` and `hmac` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers, `Utils::HmacValidator.validate(request)` returns `true` because the HMAC still matches `raw_body` [4](#0-3) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` [5](#0-4) , causing the host application to act on `victim-shop.myshopify.com` using attacker-controlled data.

Note: I could not locate the `WebhookMetadata` class file itself in the indexed codebase (only its usage in `registry.rb`), so exact downstream field usage by host apps could not be fully verified from this repo alone; this is based on the documented handler contract (`topic`, `shop`, `body`) visible in `registry.rb` and the webhook tests.
