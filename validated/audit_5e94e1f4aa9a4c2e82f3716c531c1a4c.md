### Title
Stale operator authorization state is reused across unrelated, unattended signups triggered by unprivileged users - ([File: src/plans/mod.rs])

### Summary
The reported GMX vulnerability describes a two-step protocol (save state → async external call → callback uses saved state) where an attacker can inject data in the gap between the two steps, causing the completion step to combine stale/attacker-influenced state with the final state incorrectly. The analogous pattern in `orb-core` is the operator/user QR-code authorization flow in `MasterPlan`: operator identity is verified and cached once (step 1), then reused — without re-verification — to authorize an arbitrary number of subsequent, unrelated signups triggered later by different unprivileged users (step 2), as long as the cache has not hit its expiration window.

### Finding Description
The `MasterPlan` caches the operator's validated identity (`OperatorData`) after a single QR-code verification, together with a `timestamp`: [1](#0-0) 

`scan_remaining_qr_codes` — invoked once per signup inside `do_signup` — reuses this cached `operator_data` as long as `operator_data.timestamp.elapsed() < operator_qr_expiration_time`, entirely skipping any fresh operator verification step: [2](#0-1) 

The default expiration window for this cached authorization is 23 hours: [3](#0-2) 

In self-serve mode without a button trigger, the top-level loop scans the operator QR-code once via `scan_initial_qr_codes` (only re-scanning if the cache has expired), and then repeatedly calls `idle_wait_for_signup_request` → `idle_scan_user_qr_code`, which loops indefinitely accepting user QR-codes from any bystander and immediately proceeding to `do_signup` under the same stale `operator_data`: [4](#0-3) [5](#0-4) 

This cached, unverified `operator_data` (the "step 1 saved state") then flows directly into the signup's attribution/authorization records — the `debug_report.operator_qr_code`, the `personal_custody_package::Credentials.operator_qr_code`, and the backend `signup_post::request` `distributorId` field — for every subsequent signup completed within the cache window: [6](#0-5) [7](#0-6) [8](#0-7) 

The `make_info_json` function used to build the signed Personal Custody Package also binds this stale, unverified `operator_qr_code.user_id` into the cryptographically-hashed operator attribution of the package, meaning the misattribution becomes part of the signed record for the signup: [9](#0-8) 

This mirrors the GMX bug's root cause precisely: state validated/saved in one step (operator identity + location, "verified" via `verify_operator_qr_code`) is silently reused across an asynchronous gap (idle waiting for arbitrary subsequent users) by a second, independent step (`do_signup`/`scan_user_qr_code`) that assumes the cached state is still authoritative for the *current* actor, without any mechanism to confirm the same operator authorized *this specific* signup.

### Impact Explanation
Because the cached operator authorization is reused for up to 23 hours by default, any unprivileged bystander can trigger and complete a full signup (in self-serve mode) that is misattributed to an operator/session that never verified or was even present for that individual signup. This breaks the intended "signup authorization"/"identity binding" guarantee that each signup is tied to a specific, freshly-verified operator session, and results in cross-signup state bleed of the operator identity across many unrelated signups performed by different, unauthorized end users during the cache window.

### Likelihood Explanation
This is trivially reachable in the self-serve deployment configuration whenever `self_serve = true` and `self_serve_button = false`: it does not require any privilege beyond walking up to an idle Orb and scanning a QR code, and it is guaranteed to occur given the intended self-serve UX (deliberately amortizing one operator scan across a long idle period).

### Recommendation
Bind operator authorization more tightly to each individual signup rather than to a long-lived cache: either require a fresh operator verification (or an explicit, cryptographically-bound consent from the cached operator session) for every individual signup, or drastically shrink `operator_qr_expiration_time` and add a per-signup liveness/consistency check between the cached `OperatorData` and the actual signup event before it is embedded into `signup_post::request` and the Personal Custody Package's signed operator attribution.

### Proof of Concept
1. Configure the Orb with `self_serve = true`, `self_serve_button = false`, and default `operator_qr_expiration_time` (23 hours).
2. An operator scans their QR code once at time T0 (`scan_initial_qr_codes` → `OperatorData { timestamp: T0 }`).
3. The operator leaves. Any unprivileged bystander at time T0 + 20 hours scans a user QR-code (`idle_scan_user_qr_code`).
4. `scan_remaining_qr_codes` finds `operator_data.timestamp.elapsed() < operator_qr_expiration_time` still true, and reuses the stale, unverified `OperatorData` for this unrelated signup.
5. The resulting `signup_post::request` and Personal Custody Package attribute this unauthorized/unattended signup to the original operator's session (`distributorId`, `operator_id` hash), even though that operator never authorized or was present for this specific signup.
