### Title
Attacker-controlled `flash_position` receiver executes arbitrary Wasm within the caller’s authorization scope and can drain unrelated wallet tokens - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
`flash_position` accepts a caller-selected `receiver`, verifies only that it is a Wasm contract, mints and forwards debt to it, and invokes its `execute_flash_position` callback. [1](#0-0)  A malicious receiver can execute arbitrary contract logic during that callback, including a token transfer from the supplied `initiator` address to an attacker. [2](#0-1)  Under Soroban authorization semantics, that nested `initiator.require_auth()` is attached to the caller’s `flash_position` authorization tree and succeeds if the simulated tree is signed.

### Finding Description
`process_flash_position` authenticates `caller`, but places no identity or code allowlist restriction on `receiver`. [3](#0-2)  The only executable check is `require_wasm_receiver`, which accepts any Wasm contract and rejects only non-Wasm executables. [4](#0-3)  The controller separately rejects the controller and pool addresses, but still permits an arbitrary attacker-deployed receiver. [5](#0-4) 

The controller transfers the measured borrowed tokens to `receiver` and then invokes `receiver.execute_flash_position`, passing `caller` as `initiator`. [6](#0-5)  Because that callback code is arbitrary, it can call `token.transfer(initiator, attacker, balance)` on any token held by the caller while also returning the collateral needed to satisfy the protocol’s post-callback accounting. [2](#0-1) 

After the callback, the controller only measures declared collateral and refund-token deltas on the controller balance, deposits declared collateral, and applies final debt/supply risk checks. [7](#0-6)  None of these checks detect an unrelated wallet-token transfer made by the callback under the caller’s signed authorization tree. [8](#0-7) 

### Impact Explanation
A victim can lose arbitrary token balances unrelated to the lending position while the protocol transaction still completes successfully and remains solvent. This is theft of user funds, not merely loss of the routed flash-position amount or temporary denial of service. The malicious receiver can extract the caller’s entire balance of any token for which the simulated authorization tree includes the nested transfer.

### Likelihood Explanation
An unprivileged attacker can deploy the receiver without any protocol role. Exploitation requires the victim to initiate `flash_position` with the malicious receiver and sign the authorization tree produced by simulation; integrations that accept receiver/payload data from external services can therefore expose users to this path. Required protocol conditions are limited to an active flash-loanable debt asset and a valid collateral declaration. [9](#0-8) 

### Recommendation
Do not let `flash_position` execute arbitrary caller-selected Wasm under the account caller’s authorization scope. Prefer a protocol-controlled receiver/executor, or governance-approve receiver implementations after review. At minimum, clients must decode the full signed authorization tree and reject any nested invocation other than the expected token transfers, but contract-level receiver allowlisting is the stronger mitigation because contract code cannot rely on wallet display behavior.

### Proof of Concept
1. The attacker deploys a Wasm receiver containing this callback logic:

```rust
// attacker-receiver/src/lib.rs
pub fn execute_flash_position(
    env: Env,
    initiator: Address,
    _account_id: u64,
    _debt_asset: Address,
    _amount: i128,
    _fee: i128,
    _amount_received: i128,
    controller: Address,
    _data: Bytes,
) {
    // Provide enough declared collateral for the lending transaction to pass.
    token::Client::new(&env, &collateral_token)
        .transfer(&env.current_contract_address(), &controller, &collateral_amount);

    // This nested initiator auth is recorded under the victim's flash_position entry.
    token::Client::new(&env, &victim_wallet_token)
        .transfer(&initiator, &attacker, &victim_wallet_balance);
}
```

2. The victim calls:

```text
controller.flash_position(
    caller = victim,
    account_id = victim_account_or_0,
    spoke_id = valid_spoke,
    mode = Multiply,
    debt = flashloanable_hub_asset,
    amount = positive_amount,
    receiver = attacker_receiver,
    data = attacker_payload,
    collaterals = [(collateral_hub_asset, collateral_amount)],
    refund_assets = [],
)
```

3. `process_flash_position` accepts the Wasm receiver, forwards the minted debt to it, and invokes `execute_flash_position`. [6](#0-5) 
4. Simulation records `victim_wallet_token.transfer(victim, attacker, balance)` as a child authorization beneath the victim’s `flash_position` call.
5. If the victim signs that tree, the nested transfer succeeds, while the declared collateral delta and final solvency checks allow the lending transaction to commit normally. [7](#0-6)

fn collect_collateral_deposits(
    env: &Env,
    controller: &Address,
    collaterals: &Vec<(HubAssetKey, i128)>,
    before: &Map<Address, i128>,
) -> Vec<(HubAssetKey, i128)> {
    let mut deposits: Vec<(HubAssetKey, i128)> = Vec::new(env);
    for (hub_asset, min_amount) in collaterals.iter() {
        let baseline = before
            .get(hub_asset.asset.clone())
            .unwrap_or_else(|| panic_with_error!(env, GenericError::InternalError));
        let delta = balance_delta_since(env, &hub_asset.asset, controller, baseline);
        assert_with_error!(
            env,
            delta >= min_amount,
            StrategyError::CollateralMinimumNotMet
        );
        if delta > 0 {
            deposits.push_back((hub_asset, delta));
        }
    }
    assert_with_error!(
        env,
        !deposits.is_empty(),
        StrategyError::CollateralMinimumNotMet
    );
    deposits
}

    assert_with_error!(
