### Title
Missing shop-domain sanitization in `Oauth.validate_auth_callback` sends `client_secret` to an attacker-influenced host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::ClientCredentials.client_credentials` and `ShopifyAPI::Auth::RefreshToken.refresh_access_token` both call `Utils::ShopValidator.sanitize!(shop)` before building the `Auth::Session` that is handed to `Clients::HttpClient`, ensuring the host that receives the request body (containing `client_id` **and** `client_secret`) is restricted to `TRUSTED_SHOPIFY_DOMAINS`. `Oauth.validate_auth_callback`, however, builds its `null_session` directly from `auth_query.shop` with no call to `ShopValidator`, so the host that the `client_secret` is POSTed to is bound only by whatever value is present in the `shop` field of the callback request.

### Finding Description
In `lib/shopify_api/auth/oauth.rb`: [1](#0-0) 

`validate_auth_callback` validates the HMAC over the query (`Utils::HmacValidator.validate(auth_query)`), then immediately does:
```ruby
null_session = Auth::Session.new(shop: auth_query.shop)
...
client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
```
`Clients::HttpClient#initialize` derives the destination host directly from `session.shop` (`@base_uri = "https://#{api_host || session.shop}"`), and the request body containing `client_id` and `Context.api_secret_key` (the app's `client_secret`) is POSTed to that host: [2](#0-1) 

Unlike this path, `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token` both call `Utils::ShopValidator.sanitize!(shop)` first, restricting the host that can ever receive the `client_secret` to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`): [3](#0-2) [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `host that receives client_secret == a value drawn from TRUSTED_SHOPIFY_DOMAINS`. For `client_credentials`/`refresh_access_token` this equality is enforced via `ShopValidator.sanitize!`. For `validate_auth_callback` it is not enforced by the gem itself; the only guard is `HmacValidator.validate`, whose `to_signable_string` merely re-serializes `code/host/shop/state/timestamp` and compares an HMAC computed with `Context.api_secret_key`: [6](#0-5) [7](#0-6) 

This HMAC check proves the `shop` string wasn't altered *after* being signed by whatever produced the callback request — but the gem does not independently constrain `auth_query.shop` to a Shopify-controlled domain. The library's documented usage pattern builds `AuthQuery` straight from the callback's raw request parameters (`request.parameters.symbolize_keys.except(...)`) without any additional shop validation step: [8](#0-7) 

### Impact Explanation
If any component upstream of `validate_auth_callback` (proxies, custom controllers, or a real OAuth-callback replay with a doctored `shop`/`hmac` pair) is able to influence the `shop` field reaching this method without an app-level check against `ShopValidator`/`TRUSTED_SHOPIFY_DOMAINS`, the gem itself provides no defense-in-depth: it will happily send the app's `client_id` and `client_secret` to that arbitrary host (SSRF carrying the app's credentials), which is exactly the class of "High" impact called out in scope ("SSRF with the app's credentials ... credential leakage"). This is inconsistent with the rest of the library, where every other flow that turns a `shop` string into an outbound request host (`ClientCredentials`, `RefreshToken`) explicitly sanitizes it first.

### Likelihood Explanation
Exploitability depends on whether the value forged by an attacker can survive the `HmacValidator.validate` check, which requires knowledge of `Context.api_secret_key` (or `old_api_secret_key`) — something an unprivileged internet user does not possess for a real OAuth callback issued by Shopify. Because the gem does not perform this validation as defense-in-depth (unlike `client_credentials`/`refresh_access_token`), any bug or looseness in how the hosting application composes/reuses `AuthQuery` (e.g., forwarding `shop` from an unauthenticated source while HMAC-validating only a subset, or reusing this method outside a genuine Shopify-signed callback) turns directly into `client_secret` exfiltration with no additional gem-level check. This is a genuine inconsistency/gap in the library's own defenses rather than a fully self-contained, gem-only exploit chain reachable purely from the network without any secret or upstream imperfection.

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop)` (mirroring `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`) before constructing `null_session` in `Oauth.validate_auth_callback`, and use the sanitized value both for the `HttpClient` session and for the resulting `Session.from(shop: ...)` call, so the host that ever receives `client_id`/`client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` regardless of what is (or isn't) verified upstream.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
