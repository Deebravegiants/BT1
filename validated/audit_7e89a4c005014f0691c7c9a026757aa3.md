### Title
POA Bridge withdrawal-status matching by `assetId` alone causes one on-chain withdrawal to be reported as "completed" for multiple different withdrawal requests in the same batch - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the status of a batch withdrawal item by matching the POA bridge API response purely on `assetId`, ignoring the requested `index`, `destinationAddress`, and `amount`. When a single intent contains two or more withdrawals of the same token (e.g., same token to two different recipients, or split amounts), `findMatchingWithdrawal` returns the *same* underlying withdrawal record for every request that shares that `assetId`, causing every corresponding promise in `createWithdrawalCompletionPromises` / `waitForWithdrawalCompletion` to report the identical `txHash` as "completed," even though only one of the requested withdrawals has actually settled on-chain.

### Finding Description
`describeWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` (lines 313-343) calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, whose implementation (lines 418-427) is:

```ts
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
``` [1](#0-0) 

The function's own comment acknowledges the defect: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported." [2](#0-1) 

`describeWithdrawal` is invoked once per withdrawal index via `createWithdrawalIdentifiers`, which assigns a distinct per-bridge `index` to each withdrawal item but does not thread that index (or the destination address) into the actual status lookup: [3](#0-2) 

`watchWithdrawal` then polls `describeWithdrawal` per item and returns `{ hash: status.txHash }` once "completed" is observed: [4](#0-3) 

`sdk.createWithdrawalCompletionPromises` fans this out per withdrawal-params entry, so a batch withdrawal `[usdc→alice, usdc→bob]` produces two independent promises, each calling `describeWithdrawal` with `assetId = "nep141:usdc..."`. If the POA API response array contains the `alice` withdrawal record (COMPLETED, `transfer_tx_hash = 0xAlice`) but the `bob` withdrawal is still `PENDING` (or not yet indexed), `Array.prototype.find` still matches the *first* entry with the same `near_token_id` for **both** calls, so `bob`'s promise also resolves as `completed` with `txHash = 0xAlice` even though Bob's funds never moved. [5](#0-4) 

This breaks the equality that a reported status/txHash must correspond to the actual on-chain outcome of that specific withdrawal request. It is functionally the same bug class as the RSK "duplicated logs" report: one underlying event (one completed withdrawal) gets reported twice, against two different logical operations, fooling a client that relies on the reported event.

### Impact Explanation
An integrator using `waitForWithdrawalCompletion` / `createWithdrawalCompletionPromises` / `processWithdrawal` for a batch containing two or more withdrawals of the *same token* would receive a false "completed" status and a transaction hash for a withdrawal that has not actually settled. If the integrator credits, releases custody, or marks an order as fulfilled based on this per-withdrawal completion signal (a common pattern per the README's "Waiting for Batch Completion" examples with `saveUsdc`/`saveBtc`), this results in **double crediting** of funds that were only sent once, or crediting a withdrawal that never happened. This matches the specified High-impact class: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This is reachable through normal SDK usage — any caller who batches multiple withdrawals of the same underlying NEP-141 asset (e.g., splitting one token withdrawal across two destination addresses, which the SDK's batch withdrawal API explicitly supports, see `sdk.processWithdrawal`/`signAndSendWithdrawalIntent` batch examples) will trigger this code path without any malicious action by any party — it's a straightforward consequence of the SDK's own supported batching feature colliding with the bridge's index-blind status-matching logic.

### Recommendation
Match withdrawal-status entries using a key that uniquely identifies each requested withdrawal (e.g., destination address, amount, and/or explicit position/index in the POA response) rather than `assetId` alone, or track and exclude already-matched response entries so each on-chain event is attributed to at most one requested withdrawal. Add regression tests covering batches with duplicate-asset withdrawals to different destinations/amounts to ensure indices are not conflated.

### Proof of Concept
1. Caller submits a batch withdrawal intent with two `ft_withdraw` items for the same token (`nep141:usdc.token.near`): one to `alice-address`, one to `bob-address`, via `sdk.signAndSendWithdrawalIntent({ withdrawalParams: [toAlice, toBob], ... })`.
2. Caller calls `sdk.createWithdrawalCompletionPromises({ withdrawalParams: [toAlice, toBob], intentTx })`.
3. The POA bridge indexer settles Alice's withdrawal first; `getWithdrawalStatus` returns `withdrawals: [{ near_token_id: "usdc.token.near", status: "COMPLETED", data: { transfer_tx_hash: "0xAliceTx" } }]` (Bob's not yet indexed).
4. Both `describeWithdrawal` calls (index 0 for Alice, index 1 for Bob) execute `findMatchingWithdrawal(withdrawals, "nep141:usdc.token.near")`, and `.find()` returns the same Alice record for both, causing `promises[1]` (Bob's withdrawal) to also resolve `{ hash: "0xAliceTx" }` as completed, even though Bob's funds have not been sent. function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
	}
