### Title
Unauthenticated `CallDispatcher.dispatch()` allows anyone to steal residual balances or plant malicious approvals on the shared dispatcher contract - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher` is a single, shared, permissionless contract reused across `IntentGatewayV2` (predispatch/postdispatch calldata execution) and the `HyperFungibleToken`/`WrappedHyperFungibleToken` cross-chain calldata execution path. Its `dispatch()` function has no access control whatsoever, so any externally owned account can call it directly with an arbitrary `Call[]` payload — exactly the "Swapper" bug class described in the external report, where a permissionless entry point lets anyone move a contract's balances or set arbitrary approvals on its behalf.

### Finding Description
`CallDispatcher.dispatch()` is declared with no modifier or caller check: [1](#0-0) 

It decodes an arbitrary `Call[]` and executes each call from the dispatcher's own context — including `to.call{value: call.value}(call.data)` to any target with any calldata. Because this function is public and unauthenticated, any address can call it directly (not only via `IntentGatewayV2` or the HFT contracts).

`CallDispatcher` is a shared singleton reused by multiple protocol flows:
- `IntentGatewayV2` sends predispatch/postdispatch assets to the dispatcher and then invokes `dispatch()` on it before sweeping remaining balances back: [2](#0-1) 
- `HyperFungibleTokenUpgradeable.onAccept` and `WrappedHyperFungibleToken.onAccept` unlock/mint tokens to the dispatcher and then call `dispatch()` with attacker-influenced `message.data` (a cross-chain sender chooses this calldata): [3](#0-2) 

Documentation confirms `CallDispatcher` deployments are canonical, long-lived, address-shared contracts across many different order/message flows: [4](#0-3) 

Because the same dispatcher instance is reused indefinitely across unrelated transactions and callers, any token or ETH balance that ends up resident on it — from dust left by fee-on-transfer tokens, rounding remainders not fully swept, a user mistakenly sending funds to the publicly known dispatcher address, or any other edge case where the atomic "transfer-in → dispatch → sweep-out" sequence fails to fully drain the contract — is directly and permanently exposed. Since `dispatch()` performs no ownership or origin check, **anyone** can call it with a crafted `Call` such as `token.transfer(attacker, balance)` to steal any leftover balance, or `token.approve(attackerSpender, type(uint256).max)` to plant a standing approval that can be exercised the moment the dispatcher next receives that token. This mirrors the reported Swapper issue precisely: an unauthenticated function lets third parties move a shared contract's balance and set arbitrary token approvals on its behalf.

### Impact Explanation
Any tokens or native ETH left on the `CallDispatcher` — even transiently, or by operator/user mistake — can be permissionlessly transferred out or pre-approved to an attacker by any address. Given `CallDispatcher` is reused by all `IntentGatewayV2` orders and all `HyperFungibleToken`/`WrappedHyperFungibleToken` cross-chain deliveries across many users, this is a shared, high-value target: a single successful exploitation can drain balances belonging to unrelated users/protocol dust, and pre-planted approvals persist across future, unrelated interactions with the same token, escalating a small leftover into an ongoing drain vector.

### Likelihood Explanation
Exploitation requires only a single unprivileged call to the public `dispatch()` function with attacker-chosen calldata — no special permissions, front-running, or governance compromise needed. The likelihood of some balance transiently residing on the dispatcher is non-trivial given fee-on-transfer tokens, non-standard ERC20 return-value behavior, and the documented practice of routing tokens/ETH through this exact address for swap/stake/lend composability.

### Recommendation
Restrict `CallDispatcher.dispatch()` (or the ability to leave any exploitable state after a call) so that it cannot be invoked by arbitrary third parties, or ensure the contract never persists any balance/approval outside a single atomic caller-initiated transaction — e.g., require the caller to be a registered/whitelisted app (`IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`), or make `dispatch()` deploy/operate through a fresh, single-use proxy per invocation so no shared, cross-transaction balance or approval state can ever exist to be stolen.

### Proof of Concept
1. Attacker calls `CallDispatcher.dispatch()` directly (bypassing `IntentGatewayV2`/HFT entirely) with `Call{to: USDC, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attackerSpender, type(uint256).max)}`. This succeeds because `dispatch()` has no access control: [1](#0-0) 
2. At any later time, a legitimate flow (e.g., an `IntentGatewayV2` predispatch order, or an `HyperFungibleToken` cross-chain delivery) transfers USDC into the same `CallDispatcher` address as part of its normal operation: [5](#0-4) 
3. If any USDC balance remains on the dispatcher after that transaction completes (dust, rounding, non-standard token behavior, or a partially-swept flow), the attacker uses the standing approval from step 1 to call `USDC.transferFrom(dispatcher, attacker, balance)` directly — no interaction with `IntentGatewayV2` or the HFT contracts required — draining the residual funds.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
