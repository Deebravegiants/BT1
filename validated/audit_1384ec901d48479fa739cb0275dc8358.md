### Title
Webhook `shop`/`topic` metadata is not covered by the HMAC signature, allowing cross-tenant/cross-topic spoofing of webhook identity - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies a webhook using an HMAC that only covers the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — which are acted upon and passed as trusted tenant/routing identity to the app's webhook handler — are read straight from unauthenticated HTTP headers. This breaks the intended identity binding `HMAC-covered bytes == data trusted by the handler`.

### Finding Description
`Request#hmac` and `Request#to_signable_string` define what is actually protected by the signature: [1](#0-0) 

`to_signable_string` returns only `@raw_body`. None of `topic`, `shop`, `api_version`, or `webhook_id` — all sourced from `shopify_header(...)` i.e. raw request headers — are included in the signable string: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` and `validate_signature` only ever hash `verifiable_query.to_signable_string` (the body) against `Context.api_secret_key`; the headers never enter the computation: [4](#0-3) 

`Registry.process` uses the *unauthenticated* `request.topic` to select a handler and the *unauthenticated* `request.shop` as the tenant identity handed to the app's handler, after only checking that the body's HMAC is valid: [5](#0-4) 

So the equality the code implicitly assumes is:
`shop/topic used by handler.handle == shop/topic that produced the HMAC-validated body`

but the actual guarantee provided by `HmacValidator.validate` is only:
`raw_body is byte-identical to what was HMAC'd with api_secret_key`

There is no cryptographic binding between the two. Because `api_secret_key` is a single per-app secret shared across every merchant who installs the app (not a per-shop secret), any merchant who installs the app can legitimately receive real webhook deliveries (body + valid HMAC) for their own shop. That attacker-merchant can then replay the exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` headers to name a different (victim) shop or a different topic. `Utils::HmacValidator.validate` still returns `true` (the body/HMAC pair is genuinely valid), and `Registry.process` will invoke the handler with `WebhookMetadata.new(topic: <attacker-chosen>, shop: <attacker-chosen>, body: <attacker's own body>, ...)`.

### Impact Explanation
If the host application (as essentially all Shopify apps do) uses `WebhookMetadata#shop` to look up the shop's session/access token/tenant data and process the payload "as" that shop, this allows a party who legitimately controls one tenant to inject/attribute webhook payloads to a different, victim tenant — a cross-tenant data-integrity/confidentiality issue (e.g., forging an `orders/create` payload from shop A but stamping it as belonging to shop B, or relabeling any topic to invoke a different handler than Shopify actually intended for that body). This matches the report's underlying bug class: an identity/routing field that is acted upon downstream but not covered by the same authentication check that gates the rest of the flow (analogous to Seaport trusting `AdvancedOrder.numerator`/`denominator` for control flow while the CONTRACT path's actual amounts come from an unchecked source, producing an on-chain/off-chain (here: verified-body vs. trusted-header) discrepancy). Severity is High given the cross-tenant nature.

### Likelihood Explanation
Any actor able to install the app on at least one shop (a normal, unprivileged action for a public/multi-tenant Shopify app) can capture one genuine `(raw_body, hmac-sha256)` pair from their own installation and replay it with forged `shop-domain`/`topic` headers, since nothing but network access to the app's public webhook endpoint is required — no access token, `client_secret`, or privileged credential is needed by the attacker to perform the replay itself.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the value that is authenticated, or independently verify `request.shop` against an application-level trust store (e.g., confirm the shop has an active, valid session/access token) before trusting `WebhookMetadata#shop`/`#topic` for routing or tenant-scoped side effects, and document this requirement prominently for consumers of `ShopifyAPI::Webhooks::Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook delivery for topic `orders/create` with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker crafts a new POST to the app's webhook endpoint with the exact same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different `X-Shopify-Topic`).
3. `ShopifyAPI::Webhooks::Request.new` parses these headers into `request.shop == "victim-shop.myshopify.com"`.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(api_secret_key, B) == H` — this passes because `B` and `H` are unmodified.
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: JSON.parse(B), ...)`, causing the host app to process attacker-supplied data under the victim shop's identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
