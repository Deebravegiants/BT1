### Title
Missing reentrancy guard on `cancelOrder` in the Tron `IntentGatewayV2` allows a TOCTOU race between escrow withdrawal and order-state finalization - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron port of `IntentGatewayV2` implements the same check-then-act order lifecycle as the audited EVM contract (`_filled[commitment]` check → external token transfer → state update), but omits the `nonReentrant` modifier that the canonical EVM contract applies to the equivalent function. This reproduces the Zulip-style race-condition bug class: a state check ("has this order/session already been consumed?") is performed, but the action that should make that check authoritative (withdrawing escrow / marking the order settled) is not atomic with respect to reentrant calls, so a second, concurrent invocation can observe the pre-update state and act on it.

### Finding Description
`evm/src/apps/IntentGatewayV2.sol` guards `cancelOrder` with `nonReentrant`: [1](#0-0) 

The Tron fork's `cancelOrder`, which implements identical business logic (`_filled[commitment]` check, same-chain withdraw, cross-chain GET dispatch, or destination-side `_filled` marking + `RefundEscrow` dispatch), is declared `public payable` with no `nonReentrant` modifier: [2](#0-1) 

The same-chain path checks `_filled[commitment] != address(0)` up front, then calls `withdraw(body, true)`, which performs the actual ERC20/native token transfer to `order.user`. Because the contract is not reentrancy-guarded, if `withdraw` sends native ETH or a token with a callback hook to `order.user` (an attacker-controlled address, since `order.user` is the caller for same-chain cancel), that callback can re-enter `cancelOrder` (or `fillOrder`) for the same commitment before any per-commitment settlement flag or escrow decrement performed inside `withdraw` has been persisted to storage from the outer call's perspective — mirroring the Zulip bug's "simultaneous access during the state transition" window that let a session survive its own revocation.

This is the same bug class validated by the project's own regression tests (`testSameChainRaceCondition_FillBeatsCancel` / `_CancelBeatsFill`) against the main EVM contract, which pass specifically because `nonReentrant` (plus the CEI-ordered `_filled` write) exists there: [3](#0-2) 

The Tron file being a separate, hand-maintained copy of the same contract (imports its own local `IntentGatewayV2.sol` interface rather than reusing the audited implementation) means the hardening applied to the canonical contract was not carried over.

### Impact Explanation
An unprivileged order owner (or a same-chain solver interacting with the destination cancel path) can exploit the missing reentrancy guard to re-enter `cancelOrder`/`fillOrder` mid-execution and drain escrowed input tokens more than once, or race a fill against a cancellation to obtain both the fill proceeds and the refund for the same order commitment on the Tron deployment. This is a concrete theft/double-spend of escrowed funds, matching the "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
Reachable by any unprivileged user placing and cancelling/filling an order with a malicious ERC20 token or a native-token receiver contract as `order.user`/beneficiary — a single-transaction attack requiring no privileged role, consensus proof, or relayer cooperation, only a crafted token/receiver contract. The precondition (Tron contract lacking `nonReentrant`) is a straightforward code-diff versus the audited EVM contract.

### Recommendation
Add the same `nonReentrant` modifier (and the associated `ReentrancyGuard`/CEI ordering already present in `evm/src/apps/IntentGatewayV2.sol`) to `cancelOrder`, `fillOrder`, and any other state-mutating external-call-bearing function in `evm/tron/contracts/apps/IntentGatewayV2.sol`, and audit the Tron fork for drift from the canonical contract more generally.

### Proof of Concept
Not directly executable within this analysis (Tron toolchain/tests not inspected), but the exploit shape mirrors the existing `testSameChainRaceCondition_*` Foundry tests: deploy the Tron `IntentGatewayV2`, place a same-chain order with `order.user` set to an attacker contract that reenters `cancelOrder` from its token `transfer`/`receive` hook, and confirm the second reentrant call succeeds in withdrawing escrow again before the outer call's bookkeeping completes — which the equivalent test on the guarded EVM contract cannot reproduce.

**Uncertainty note:** I was unable to inspect the full body of `withdraw()`/escrow-decrement bookkeeping in the Tron contract (cut off by context/iteration limits), so I cannot confirm with certainty whether per-token escrow accounting (`_orders[commitment][token]`) is zeroed before or after the external transfer in that specific file. The finding is based on the confirmed absence of `nonReentrant` on `cancelOrder` where the canonical contract has one, and the checked-then-acted `_filled` pattern is present in both. A Devin session with Tron build tooling would be needed to fully confirm exploitability with a concrete PoC transaction trace.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable {
        bytes32 commitment = keccak256(abi.encode(order));

        // order has already been filled
        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            // Same-chain: validate locally and refund immediately
            // only owner can cancel
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

            // Verify we're on the correct chain
            if (orderSource != currentChain) revert WrongChain();

            WithdrawalRequest memory body =
                WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user});

            withdraw(body, true);
