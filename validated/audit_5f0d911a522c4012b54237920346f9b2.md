### Title
Webhook `shop-domain` Header Is Not Covered by the HMAC, Allowing Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC that authenticates a webhook never covers the `shop-domain` header. Any party able to obtain one valid `(body, HMAC)` pair for the shared app secret can replay it with an arbitrary `shop-domain` header and have it accepted as coming from a different tenant.

### Finding Description
Webhook authenticity is checked with `Utils::HmacValidator.validate(request)` in `Registry.process`: [1](#0-0) 

`HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the supplied `hmac`: [2](#0-1) 

For webhooks, `to_signable_string` is defined to return only `@raw_body`: [3](#0-2) 

But the tenant identity used downstream — `request.shop`, read straight from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header — is *not* part of that signed string: [4](#0-3) 

`Registry.process` passes this unauthenticated `shop` value straight to the app's handler as the trusted tenant identifier, after only validating the HMAC of the body: [5](#0-4) 

This is exactly the bug class in the external report: a value that is acted upon (the shop) is not bound into the signature that is verified (the HMAC only covers the body). Shopify webhook signing uses the app's `client_secret`, which is the same value for every shop that installs the app — it is not per-shop. Consequently, a request with a valid HMAC only proves "some install of this app produced this body," not "this body came from shop X." Since the header carrying the shop is excluded from the signed material, an attacker who possesses one legitimate `(body, hmac)` pair (e.g., a merchant who installed the app and can trigger/capture their own shop's webhook deliveries) can resend that exact body/HMAC to the app's webhook endpoint while substituting a different `shop-domain` header. The signature check still passes, and the handler receives a spoofed `WebhookMetadata` claiming the payload originated from a shop the attacker does not control.

### Impact Explanation
This breaks the identity binding `hmac_verified_shop == shop_delivered_to_handler`, letting one tenant's low-privilege actor forge webhook events attributed to a different tenant. Any host application that relies on `WebhookMetadata#shop` (as returned by this gem) to determine which merchant/tenant the event concerns — e.g., to look up that shop's session/access token, update per-shop state, or trigger `shop/redact`/`customers/redact` type flows — can be tricked into acting on/for the wrong shop. This is a cross-tenant access issue, matching the report's Critical bucket for cross-tenant access.

### Likelihood Explanation
Reachable by an authenticated-but-unprivileged app installer (any merchant who has installed the app, which the report class treats as an "unprivileged internet user" relative to other tenants). No access to `api_secret_key`, access tokens, or any other tenant's credentials is required — only a body/HMAC pair the attacker can legitimately obtain from their own shop's webhook deliveries, plus the ability to POST to the app's public webhook endpoint (which by design accepts unauthenticated internet traffic and relies purely on this gem's HMAC check for trust).

### Recommendation
Include `shop-domain` (and ideally `topic`/`api-version`/`webhook-id`) in the signed material checked against the HMAC, or otherwise cryptographically bind the shop claim into `to_signable_string`. At minimum, document/require that consuming apps independently re-verify that `WebhookMetadata#shop` corresponds to a shop with an active install/session before trusting it, since the gem currently offers no such binding.

### Proof of Concept
1. App has two shops installed: `shop-a.myshopify.com` (attacker-controlled) and `shop-b.myshopify.com` (victim).
2. Attacker triggers a webhook event on their own shop (`shop-a`) and captures the raw POST body and its `X-Shopify-Hmac-Sha256` header — this HMAC is valid because it is computed with the app's single shared `client_secret`.
3. Attacker replays the identical body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
4. `Utils::HmacValidator.validate` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) recomputes the HMAC over `to_signable_string` (`lib/shopify_api/webhooks/request.rb:36-38`), which is only the raw body — identical to step 2 — so validation succeeds.
5. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` using the forged `shop-b.myshopify.com` header (`lib/shopify_api/webhooks/registry.rb:198`) and calls the host app's handler, which now processes an event it believes came from `shop-b` even though the payload actually originated from `shop-a`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
