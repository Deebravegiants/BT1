This confirms the vulnerability. `createWithdrawalIdentifiers` assigns index 0 and 1 for the two same-assetId withdrawals [1](#0-0) , but `findMatchingWithdrawal` ignores the `index` field entirely and returns the first array entry matching only on `assetId` [2](#0-1) , a limitation explicitly acknowledged in the code's own comment. `describeWithdrawal` passes `args.withdrawalParams.assetId` (not `args.index`) into this lookup [3](#0-2) , so both `watchWithdrawal` calls for index 0 and index 1 will converge on the same withdrawal record (whichever `Array.prototype.find` returns first) whenever two withdrawals of the same PoA token exist in a batch.

### Title
Index-blind withdrawal matching causes cross-reported txHash for duplicate-token PoA withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.findMatchingWithdrawal` matches PoA withdrawal status entries solely by `assetId`, ignoring `WithdrawalIdentifier.index`. When a single NEAR intent transaction contains two withdrawal legs of the same `assetId` to different destination addresses, `describeWithdrawal` for both legs resolves to the same underlying PoA withdrawal record, causing the same `transfer_tx_hash`/status to be reported for both legs.

### Finding Description
The claimed equality is: for `index:0` and `index:1` withdrawals of the same `assetId`, `describeWithdrawal({index:0,...}).txHash` should equal the on-chain result of withdrawal 0, and `describeWithdrawal({index:1,...}).txHash` should equal the on-chain result of withdrawal 1 (i.e., they should differ when the two destinations/amounts differ).

Tracing the path: `createWithdrawalIdentifiers` in [4](#0-3)  iterates `withdrawalParams`, and for each entry sharing the same bridge route (`RouteEnum.PoaBridge`), increments a per-route counter and assigns it as `index`, so two same-assetId withdrawals get `index: 0` and `index: 1` while `withdrawalParams` (including `destinationAddress`) differ between them.

`watchWithdrawal` calls `bridge.describeWithdrawal({...wid, logger})` [5](#0-4) . `PoaBridge.describeWithdrawal` fetches the full withdrawal list from the PoA API keyed by `args.tx.hash` (the shared NEAR tx hash for both legs) and then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, never referencing `args.index` [3](#0-2) . `findMatchingWithdrawal` uses `Array.prototype.find` to return the first array element whose `near_token_id` matches — the code comment itself states: "This means multiple withdrawals of the same token in a single transaction are not supported" [2](#0-1) .

Root cause: no per-index disambiguation exists in the matching logic, and no upstream guard (`validateWithdrawal`, `supports`, or the intents contract) rejects or reorders duplicate-assetId withdrawals within a batch. Both watchers converge on the same array entry, so both legs report identical `(status, txHash)`, even though the two withdrawals target different `destinationAddress` values and are distinct on-chain PoA transfers.

### Impact Explanation
An integrator relying on `sdk.createWithdrawalCompletionPromises` / `waitForWithdrawalCompletion` for a batch with two same-token PoA legs will receive the same `txHash` for both withdrawal indices. This causes the integrator to mark both withdrawals "completed" using a single real on-chain transfer's hash — effectively double-crediting one destination's outcome to two different logical withdrawals/users, or crediting the wrong user's transfer entirely (a status/hash misreport causing incorrect double-credit). This matches the "status or hash misreport making an integrator credit or refund twice" High-severity category (arguably Critical if integrator logic releases funds off the misreported hash for both legs, since one destination's real transfer is masked entirely).

### Likelihood Explanation
Preconditions are trivial and fully attacker/user-controlled: any ordinary user can construct a NEAR intents transaction with two PoA withdrawal legs of the same `assetId` to two different destination addresses within one `createWithdrawalCompletionPromises` call — no privileged access, no relayer/RPC compromise needed. This is 100% reproducible whenever an integrator batches same-token withdrawals, which is a normal usage pattern (e.g., splitting one balance to two recipients).

### Recommendation
Disambiguate withdrawals by more than `assetId`: match candidates by `assetId` AND `destinationAddress` (and `amount` if necessary) rather than assetId alone; if the PoA API cannot supply enough fields to disambiguate reliably, track already-consumed matches (e.g., pop matched entries from the candidate list, or require exclusivity via `amount`/`destination_address` fields per withdrawal) so that a second lookup for the same `assetId` cannot re-select an already-assigned entry. At minimum, throw explicitly when multiple unmatched candidates remain ambiguous instead of silently returning the first array element.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
