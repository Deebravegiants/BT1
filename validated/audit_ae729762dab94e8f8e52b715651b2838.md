### Title
Webhook shop-domain identity is not bound to the HMAC signature, enabling cross-tenant webhook confusion - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the `X-Shopify-Hmac-Sha256` header against the raw request **body**. The `shop-domain` header, which the host application receives as the authenticated tenant identifier for the webhook, is never included in the signed material. This breaks the identity binding `shop_that_produced_the_HMAC == shop_delivered_to_the_handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate`/`validate_signature` compute/compare the signature strictly over that signable string [2](#0-1) . The `shop`, `topic`, `api_version`, and `webhook_id` values are all pulled from unauthenticated HTTP headers [3](#0-2)  and are never mixed into the HMAC input.

`Registry.process` performs exactly one check — HMAC-over-body — and then immediately builds `WebhookMetadata` using `request.shop` (the unauthenticated header) and hands it to the app's registered handler as the trusted tenant context: [4](#0-3) 

Because a Shopify app uses a single `client_secret` to sign webhooks for *every* shop that installs it, any shop owner (an unprivileged internet user with respect to other tenants of the same app) can trigger a genuine webhook on their own store and capture a valid `(raw_body, hmac)` pair. That pair can then be replayed directly to the app's public webhook endpoint with the `shopify-shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` will still pass (the body and HMAC are untouched and were legitimately signed by the same app secret), so `Registry.process` will invoke the handler with `WebhookMetadata#shop` claiming to be the victim shop while the body content is fully attacker-controlled (from the attacker's own store data).

### Impact Explanation
This crosses a tenant boundary: the host application's webhook handler receives attacker-supplied payload data labeled as belonging to a different merchant's shop, purely because the gem's authentication step never binds the `shop` claim to the signed content. Depending on how the host app uses `WebhookMetadata#shop` (e.g., looking up sessions/access tokens, writing records, triggering shop-scoped side effects), this enables cross-tenant data injection/confusion — data that should be scoped to the victim's tenant is instead attacker-controlled.

### Likelihood Explanation
Medium-to-high: the technique requires only (1) the attacker's own legitimate installation of the target app (a normal, unprivileged action any merchant can take) to obtain one valid `(body, hmac)` pair, and (2) the ability to POST directly to the app's public webhook endpoint with a modified `shopify-shop-domain` header — no access to the app's `client_secret`, access tokens, or any other shop's credentials is required.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook_id`) header values in the HMAC-covered signable string, or otherwise cryptographically bind them to the request (e.g., derive/validate `shop` only from a value that is part of the signed payload for the specific delivery), so that spoofing the shop header invalidates the signature.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`) so Shopify delivers a genuinely HMAC-signed request to the app's public webhook endpoint; attacker records the raw body `B` and the corresponding valid `X-Shopify-Hmac-Sha256` value `H` (computed with the app's shared `client_secret`, same for all installs).
2. Attacker sends a new HTTP POST directly to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(B, client_secret) == H` — this passes [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: JSON.parse(B), ...)` [6](#0-5) , causing the host application to process attacker-controlled data as if it originated from the victim's shop.

          received_signature = verifiable_query.hmac
