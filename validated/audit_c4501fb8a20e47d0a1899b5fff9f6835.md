## Analysis

The bug class from the advisory — **validating an identifier's raw form while a downstream consumer treats an equivalent-but-differently-encoded form as the same value** — has a direct structural analog in the SDK's Bitcoin bech32 address handling.

`validateAddress` (used to accept a withdrawal destination) validates BTC bech32 addresses **case-insensitively**: `validateBtcBech32Address` explicitly folds case when checking the human-readable prefix (`decoded.prefix.toLowerCase() !== "bc"`), and the underlying bech32 decode accepts both fully-lowercase and fully-uppercase encodings of the same witness program. [1](#0-0) 

The self-transfer guard that is supposed to block a withdrawal whose destination equals the token's own custody address, however, compares Bitcoin (and Dogecoin/Litecoin/Zcash/Cardano/Aleo/Dash) addresses with **plain, case-sensitive string equality** rather than canonicalizing first: [2](#0-1) 

That comparison is invoked directly on the raw, caller-supplied `destinationAddress` in `PoaBridge.validateWithdrawal`: [3](#0-2) 

and in `HotBridge.validateWithdrawal`: [4](#0-3) 

A prior fix (changelog entry `95eca42`) confirms the SDK is aware that bech32 case-folding is real and that the on-chain/contract side only accepts lowercase bech32, but that lowercasing is applied only inside `omni-withdraw-params.ts` for the Omni Bridge route, not inside `compareAddresses`: [5](#0-4) [6](#0-5) 

### Title
Case-sensitive address comparison lets a same-address withdrawal bypass the self-transfer guard for BTC/UTXO-style destinations - (File: packages/intents-sdk/src/lib/compareAddresses.ts)

### Summary
`compareAddresses` uses raw `a === b` string equality for Bitcoin, Bitcoin Cash-legacy-fallback, Dogecoin, Litecoin, Zcash, Cardano, Aleo and Dash addresses, while `validateAddress`'s bech32 branch (used for the same addresses) accepts case-folded forms of the same address as valid. Because the "destination equals token's own address" check (`DestinationAddressMatchesTokenAddressError`) relies on `compareAddresses` without first canonicalizing case, a destination address that is byte-for-byte the same on-chain address as the token's `origin_chain_address`, but supplied in a different letter case, is treated as *not equal* and the guard silently passes.

### Finding Description
`validateBtcBech32Address` (part of `validateAddress`) decodes the address with bech32/bech32m and only lower-cases the human-readable prefix for comparison; it does not reject a fully-uppercase or reconstructed address, so both cases of the same bech32 address validate as legitimate destination addresses. `compareAddresses`, which is meant to canonicalize both sides before comparing (as it explicitly does for EVM via `getAddress`, for Aptos/Movement/Sui/Starknet via `normalizeHexAddress`, for TON/Tron via full decode, and for Stellar via `toUpperCase`), falls back to naive `a === b` for the Bitcoin-family branch. This means the equality check the code relies on to block "withdraw a token to its own custody address" is only correct if both operands already share the same case — an assumption that `validateAddress` itself does not enforce.

### Impact Explanation
If the POA/HOT bridge's `origin_chain_address` for a BTC-family token is stored/returned in one case (e.g., lowercase, as required on-chain per the `95eca42` fix) and a caller supplies the identical address in a different case as the withdrawal `destinationAddress`, `compareAddresses` returns `false`, `DestinationAddressMatchesTokenAddressError` is not thrown, and the withdrawal proceeds. The funds are then delivered to what is actually the bridge's own custody/token address rather than a genuine third-party recipient — i.e., "funds delivered to a wrong address ... with no recovery," since the destination is not a normal user-controlled wallet the withdrawal flow is designed to reach.

### Likelihood Explanation
Any caller of `PoaBridge.validateWithdrawal` / `HotBridge.validateWithdrawal` fully controls the `destinationAddress` string and can trivially re-case a known token custody bech32 address (case has no cryptographic significance in bech32) to slip past the guard. No privileged access or bridge/relayer misbehavior is required — this is purely a client-supplied string that both `validateAddress` and the eventual on-chain execution treat as equivalent to the canonical address, while the SDK's protective equality check does not.

### Recommendation
In `compareAddresses`, canonicalize Bitcoin-family (and any other bech32/base58-non-checksummed) addresses before comparing — e.g., lower-case bech32 addresses (and, ideally, re-decode/re-encode to normalize) prior to the `a === b` fallback, mirroring the canonicalization already done for EVM, TON, Tron, hex-field-element chains, and Stellar.

### Proof of Concept
1. Suppose a POA-bridge BTC-family token's `origin_chain_address` is `bc1qxyzxyz...` (lowercase, canonical on-chain form).
2. Caller requests a withdrawal with `destinationAddress = "BC1QXYZXYZ..."` (same address, uppercase).
3. `validateAddress(destinationAddress, Chains.Bitcoin)` → `true` (bech32 decode accepts uppercase; prefix check is case-folded). [7](#0-6) 
4. `compareAddresses(tokenInfo.origin_chain_address, destinationAddress, Chains.Bitcoin)` → `false` because the two strings differ byte-for-byte, even though they decode to the identical witness program. [8](#0-7) 
5. `DestinationAddressMatchesTokenAddressError` is not thrown; `validateWithdrawal` succeeds and the withdrawal is executed to the token's own custody address.

function validateBtcBech32Address(address: string): boolean {
	let decoded: { prefix: string; words: number[] };
	let isBech32m = false;

	try {
		decoded = bech32.decode(address as `${string}1${string}`);
	} catch {
		try {
			decoded = bech32m.decode(address as `${string}1${string}`);
			isBech32m = true;
		} catch {
			return false;
		}
	}

	if (decoded.prefix.toLowerCase() !== "bc") return false;

	const { words } = decoded;
	if (!words || words.length < 1) return false;

	const witnessVersion = words[0];
	if (witnessVersion === undefined || witnessVersion < 0 || witnessVersion > 16)
		return false;

	const program = bech32.fromWords(words.slice(1));
	const progLen = program.length;

	if (progLen < 2 || progLen > 40) return false;

	// v0: Bech32 only — 20 bytes (P2WPKH) or 32 bytes (P2WSH)
	if (witnessVersion === 0) {
		if (isBech32m) return false;
		return progLen === 20 || progLen === 32;
	}

	// v1: Bech32m only — 32 bytes (P2TR / Taproot)
	if (witnessVersion === 1) {
		if (!isBech32m) return false;
		return progLen === 32;
	}

	return false;
}
