### Title
Webhook `shop` identity is trusted from an unauthenticated header not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the merchant identity (`shop`) from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `Registry.process` verifies is computed only over the raw request body via `to_signable_string`. This breaks the intended binding `verified_bytes == acted_upon_identity`: the bytes that are HMAC-verified (raw body) are not the bytes that determine which merchant/tenant the event is attributed to (the `shop` header).

### Finding Description
`Registry.process` validates a webhook solely with: [1](#0-0) 
which calls `Utils::HmacValidator.validate(request)`. That validator recomputes the signature over `request.to_signable_string`: [2](#0-1) 
and `Request#to_signable_string` returns only the raw body: [3](#0-2) 
Meanwhile `Request#shop` is read straight from a header with no cryptographic binding to that body: [4](#0-3) 
and after HMAC validation succeeds, that unauthenticated `shop` value is handed to the host application as the authoritative tenant identifier via `WebhookMetadata`: [5](#0-4) [6](#0-5) 

The equality that should hold is: `shop bound by HMAC == shop acted upon by handler`. In practice: `shop verified-by-HMAC == ∅` (not covered) while `shop acted-upon = header value`, so any bytes in the `shop` header pass through to the application's tenant-scoped business logic without integrity protection, as long as the attacker can also supply a body+HMAC pair valid for the *app's* shared `client_secret` (which is identical across all shops that install the same app).

### Impact Explanation
An attacker who has installed the target app on their own store (an ordinary, unprivileged merchant/user action) can trigger a genuine webhook for their own shop, capture the valid `raw_body` + `X-Shopify-Hmac-Sha256` pair, and replay that exact body/HMAC to the same webhook endpoint while substituting a victim's `X-Shopify-Shop-Domain` value. Because the header is outside the signed content, `Utils::HmacValidator.validate` still succeeds, and `Registry.process` forwards `shop: request.shop` (the victim's domain) to the developer's `WebhookHandler#handle`. Any host application that uses `WebhookMetadata#shop` to scope lookups, credential fetches, or session context for processing the webhook (the exact pattern demonstrated in this repo's own webhook usage docs, e.g. loading a session for that shop) will act under the wrong tenant — a cross-tenant confusion primitive.

### Likelihood Explanation
Requires no privileged access beyond installing the app in one's own store (an ordinary onboarding action for any public/multi-tenant Shopify app), and no knowledge of `api_secret_key`. Exploitability additionally depends on the host application's webhook handler trusting `data.shop` for tenant-scoped actions without independently corroborating it (e.g., against the shop associated with the delivered `webhook_id`, or session state) — which is the documented usage pattern shown for this gem.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the HMAC-signable content, or otherwise cryptographically bind them to the verified request, e.g. by having `Request#to_signable_string` incorporate the shop domain, or by requiring callers to cross-check `request.shop` against a shop already associated with the specific `webhook_id`/subscription before trusting it in `WebhookMetadata`.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger any subscribed webhook topic to receive a legitimately signed request: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's `client_secret`).
2. Replay to the app's webhook endpoint with headers `X-Shopify-Topic`, `X-Shopify-Hmac-Sha256: H` (unchanged), `X-Shopify-Shop-Domain: victim.myshopify.com`, and body `B` (unchanged).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes HMAC over `B` only and matches `H`, so validation passes.
4. `handler.handle` receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` even though `victim.myshopify.com` never sent this webhook, letting the host app act on victim-tenant data/context using attacker-supplied body content.
