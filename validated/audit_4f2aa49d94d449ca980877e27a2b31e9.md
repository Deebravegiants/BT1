### Title
Unbounded `GetRequest.keys` length lets an unsigned, fee-free extrinsic force expensive per-key state-proof verification before any size/bandwidth check — (File: `modules/pallets/state-coprocessor/src/impls.rs`)

### Summary
The CVE analog is OpenSSH's `auth_password`, which ran the CPU-expensive `crypt()` hash over an attacker-supplied password of unbounded length before any length limiting, allowing a cheap request to trigger disproportionate CPU cost. The same shape exists in `pallet-state-coprocessor`'s GET-response handler: it runs a membership/non-membership trie-proof verification for every key in every `GetRequest` in a batch *before* the bandwidth gate that is supposed to meter and reject oversized/unpaid traffic, and the whole call path is reachable for free via `pallet-ismp`'s unsigned `handle_unsigned` extrinsic.

### Finding Description
`GetRequest.keys` is declared as an unbounded `Vec<Vec<u8>>` with no maximum length anywhere in the type or its (de)serialization path: [1](#0-0) 

`pallet-state-coprocessor::handle_get_requests` iterates every `GetRequest` in the batch and, for each one, calls `verify_state_proof` — a cryptographic trie-membership check — for the full `req.keys` collection, and only afterward meters the request against the bandwidth gate: [2](#0-1) 

This handler is reached through `pallet-ismp`'s unsigned `handle_unsigned` call, which is deliberately fee-free by design ("This allows users execute ISMP datagrams for free. Use with caution.") and is also fully executed inside `validate_unsigned`, i.e. during mempool validation, before the transaction is even included in a block: [3](#0-2) [4](#0-3) 

The call weight annotated on `handle_unsigned` is a static constant, not derived from the number of keys/requests in the payload: [5](#0-4) [6](#0-5) 

Unlike the analogous Ethereum consensus-verifier code (`sync-committee`, `BEEFY`) which bounds validator/committee sizes with fixed constants (`SYNC_COMMITTEE_SIZE`, `MAX_VALIDATORS_PER_COMMITTEE`, etc.): [7](#0-6) 
there is no equivalent cap on the number of storage keys a single `GetRequest` may carry, nor on the number of `GetRequest`s batched into one `GetResponseMessage`. A relayer (an unprivileged actor, since `handle_unsigned` requires only `ensure_none`) can submit a `GetResponseMessage`/`TimeoutMessage::Get` batch whose requests each carry an enormous `keys` vector; every one of those keys drives an independent expensive trie-proof verification (`verify_state_proof`) executed twice — once during `validate_unsigned` mempool validation (free, no state changes persisted) and again on dispatch — before the bandwidth gate in `impls.rs:146` gets a chance to reject the traffic for insufficient allowance.

### Impact Explanation
Because the expensive cryptographic verification runs unconditionally for every submitted key before the bandwidth/fee gate is consulted, and because `validate_unsigned` re-executes this same work for free on every node's mempool for every propagated candidate transaction, this is a real route by which an attacker can force the network's collators/validators to spend CPU proportional to attacker-chosen input size at zero cost, with no upstream cap analogous to the fixed committee-size constants used elsewhere in the codebase. This directly matches the "route unable to deliver messages" acceptance criterion: sustained submission of such oversized `GetResponseMessage`/timeout batches can degrade transaction-pool validation throughput network-wide, delaying or preventing legitimate message delivery.

### Likelihood Explanation
Reachable from a single unsigned, fee-free extrinsic (`Ismp::handle_unsigned`) that any relayer or observer of the network can submit; no special privilege, governance, or malicious-admin assumption is required. The only friction is that the caller must supply a proof that satisfies decoding and the earlier structural checks in `handle_get_requests` (proof height match, `verify_membership` of the request commitments) before reaching the per-key `verify_state_proof` loop — but crucially, an oversized `keys` array increases attacker cost only linearly (each key needs a corresponding branch in the supplied merkle/trie proof) while amplifying verifier-side CPU work by the same unbounded factor, and this is executed for free on every node during pool validation.

### Recommendation
- Enforce a hard maximum on `GetRequest.keys.len()` (and/or total encoded size) at construction/dispatch time and re-validate it in `handle_get_requests` before any proof verification runs, mirroring the fixed-size constants already used for BEEFY/sync-committee (`MAX_VALIDATORS_PER_COMMITTEE`, `SYNC_COMMITTEE_SIZE`).
- Move the bandwidth-gate check (or an equivalent cheap size-based pre-check) ahead of `verify_state_proof` in `modules/pallets/state-coprocessor/src/impls.rs`, so oversized/unpaid batches are rejected before the expensive cryptographic work is performed — the same "gate before work" fix pattern already applied to the zstd bomb in `pallet-call-decompressor`.
- Make `handle_unsigned`'s weight computation reflect the actual number of keys/requests being verified (already tracked via `message_bytes`/bandwidth accounting) rather than a static constant, so `validate_unsigned`'s free re-execution cannot be abused disproportionately.

### Proof of Concept
1. An app on a source chain dispatches (or a relayer forges, if not already length-checked at dispatch time) a `GetRequest` whose `keys: Vec<Vec<u8>>` field contains an extremely large number of entries (e.g., tens of thousands), each requiring its own trie proof.
2. The relayer submits a `Message::Request`/`GetResponseMessage` (or `TimeoutMessage::Get`) via `Ismp::handle_unsigned` carrying this oversized request set and an internally-consistent multi-proof.
3. Every full node's mempool calls `validate_unsigned`, which calls `Self::execute(messages.clone())` → `pallet_state_coprocessor::handle_get_requests`, which loops `verify_state_proof` over every key in `req.keys` for every request in the batch — all before the `BandwidthGate::try_consume` call — consuming CPU proportional to the attacker-chosen key count, for free, on every node that receives the gossiped transaction.
4. Repeating this with many such transactions (or resubmitting on failed validation) allows an attacker to impose disproportionate CPU load on transaction-pool validation across the network with negligible cost, matching the CVE-2016-6515 bug class of "unbounded attacker input driving unmetered expensive computation before any rate/size limiting."

Note: I was unable to fully confirm from the available index whether `GetRequest.keys` is length-limited earlier at the EVM `DispatchGet`/dispatch layer (gas costs on the source chain may impose a soft ceiling there), since the Solidity dispatch path is gas-metered and I could not find an explicit `MAX_KEYS`-style constant on the Substrate/ISMP core side. If such a limit exists elsewhere and was not indexed, this would reduce (but likely not eliminate, since batches can still combine many separate proven `GetRequest`s) the severity of this finding.
