Audit Report

## Title
JWT replay protection in `WorkflowMetadataHandler.Authorize()` has a check-then-act race allowing single-use JWT reuse - (File: `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`)

## Summary
`WorkflowMetadataHandler.Authorize()` checks whether a JWT `jti` has been used via `jwtCache.isReplay()` and only marks it used via `jwtCache.recordUsage()` at the end of the function, with these two operations taking separate, independent locks on the same underlying map. Two concurrent requests carrying the same JWT can both pass the replay check before either records usage, letting a single-use JWT authorize two (or more) workflow trigger executions.

## Finding Description
`Authorize()` at [1](#0-0)  verifies the JWT signature, then calls `h.jwtCache.isReplay(claims.ID)` which takes an `RLock`, checks map membership, and releases the lock [2](#0-1) . Only after unrelated authorized-key/signer checks succeed does it call `h.jwtCache.recordUsage(claims.ID)`, which takes a separate `Lock()` to insert the entry [3](#0-2) . Because the check and the record are two independent critical sections rather than one atomic check-and-set, concurrent calls to `Authorize()` with an identical `jti` can both observe "not yet used" before either records usage, defeating the intended single-use guarantee stated in the `jwtReplayCache` doc comment ("manages used JWT IDs to prevent replay attacks").

This path is reachable by any external, unprivileged caller who holds a single valid JWT, since `Authorize()` is invoked directly from `httpTriggerHandler.authorizeRequest()` on every inbound HTTP-Trigger request [4](#0-3) , before any other authorization layer that would close this race. There is no additional idempotency or dedup mechanism shown in this handler that would prevent the race.

## Impact Explanation
Exploiting the race lets a caller re-use a single-use JWT to trigger a second unauthorized workflow execution/job run for the same trigger request. This maps to the in-scope "unauthorized job run" / "gateway request impersonation" impact category, since it defeats a specific, documented anti-replay security control on an internet-facing gateway endpoint.

## Likelihood Explanation
The attacker needs only one valid, correctly signed JWT (no additional privilege) and the ability to send two requests concurrently, which is trivial for any external client (e.g., firing two parallel HTTP POSTs with the same JWT). The race window, while narrow, is a genuine, reproducible TOCTOU gap rather than a purely theoretical one, since `isReplay` and `recordUsage` are provably separate, independently-locked operations with unrelated work executed between them.

## Recommendation
Replace the separate `isReplay`/`recordUsage` calls with a single atomic `CheckAndRecord(jti string) bool` method on `jwtReplayCache` that takes the write lock once, checks for existence, and inserts the entry before releasing the lock (mirroring `RequestReplayGuard.CheckAndRecord` in `core/capabilities/vault/request_replay_guard.go`), and update `Authorize()` to use it in place of the current two-step check.

## Proof of Concept
1. Obtain one valid, signed JWT for an HTTP Trigger request with a specific `jti`.
2. Fire two concurrent requests to the gateway's HTTP Trigger endpoint using the identical JWT at nearly the same time.
3. Both requests reach `httpTriggerHandler.authorizeRequest()` → `WorkflowMetadataHandler.Authorize()` concurrently, and both call `h.jwtCache.isReplay(claims.ID)` before either calls `h.jwtCache.recordUsage(claims.ID)`.
4. Write a Go unit test that spawns two goroutines calling `Authorize()` with the same JWT/claims and asserts (via `-race` and repeated iterations, or by inserting a synchronization point between the `isReplay` check and `recordUsage` call) that both goroutines can return a non-error/authorized result for the same `jti`, confirming the single-use guarantee is violated.
