Based on my review of the webhook‑processing code, there is a genuine identity‑binding break: the webhook HMAC signature only covers the raw request body, while the `shop` value used to route/attribute the webhook is taken from an unsigned HTTP header.

### Title
Webhook `shop` identity is not bound by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` so that `Utils::HmacValidator.validate` can authenticate incoming webhooks. However, `to_signable_string` returns only the raw HTTP body, while `shop` is read from the `x-shopify-shop-domain` header, which is never part of the signed material. [1](#0-0) 

### Finding Description
`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` using the app's single, app-wide `api_secret_key`, and secure-compares it to the `hmac` value: [2](#0-1) 

For webhook requests, `to_signable_string` is `@raw_body`, i.e. the signature proves only that a given body was produced with the app's secret — it says nothing about which shop it belongs to. `Registry.process` then builds `WebhookMetadata` and dispatches to the handler using `request.shop`, which is populated purely from the `shop-domain` header, entirely outside the HMAC: [3](#0-2) [4](#0-3) 

Because `api_secret_key` is a single shared secret for the whole app (used to validate webhooks from *every* installed shop, not a per-shop key), any body+HMAC pair that is valid for shop A's webhook traffic remains a byte-for-byte valid HMAC pair no matter what `shop-domain` header accompanies it. The equality the library implicitly (and incorrectly) relies on is:

`shop authenticated by HMAC == shop used as tenant/session key`

but what is actually proven is only:

`HMAC(api_secret_key, raw_body) == received_hmac`

with `shop` completely decoupled from that proof. An attacker who is a legitimate, unprivileged merchant/tenant on any single shop that has installed the app can capture one of their own legitimately-signed webhook deliveries (body + `x-shopify-hmac-sha256`), then submit that exact body and hmac to the app's public webhook endpoint while swapping the `x-shopify-shop-domain` (or `X-Shopify-Shop-Domain`) header to a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspected the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
This breaks the tenant boundary between shops using the same installed app: a webhook attributed to shop A can be replayed as if it came from shop B, causing the host application's webhook handler to act on/for the wrong tenant (e.g. updating records, triggering side effects, or writing data keyed by `shop`) using attacker-supplied topic-relevant body content that was legitimately signed for a different store. This is cross-tenant access/data confusion achieved by an unprivileged internet user (any merchant who can install the app) without needing `api_secret_key`, an access token, or any credential belonging to the victim.

### Likelihood Explanation
Medium-to-High. It requires the attacker to install the target app on at least one shop they control (a normal unprivileged action for public apps) and to trigger/capture one legitimate webhook delivery for that shop, then replay it with a modified header — no secret material or privileged access is needed, and the header is trivially attacker-controlled once the request reaches the app's public webhook endpoint.

### Recommendation
Bind the `shop` used for routing/attribution to the authenticated material, e.g. include the `shop-domain` header (and ideally `topic`/`webhook_id`) inside `to_signable_string`, or independently verify that the shop reported in the header corresponds to a shop with an active, previously-registered session/subscription for that specific webhook `topic`/`webhook_id` before trusting `request.shop` in `Registry.process`.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) so Shopify sends a POST with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC over `B` using the app's shared `api_secret_key`) and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Capture `B` and `H`.
3. Send a new POST to the same webhook endpoint with identical body `B`, identical `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [5](#0-4)  which passes because it only checks `B` against `H`; the handler then receives `WebhookMetadata` with `shop: "victim.myshopify.com"`, causing the app to process attacker-supplied webhook content as if it belonged to the victim tenant.
