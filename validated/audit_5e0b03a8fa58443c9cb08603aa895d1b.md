## Title
Unauthenticated `market` account as PDA seed in `Initialize2` allows front‑running/squatting of the canonical AMM pool address, enabling price manipulation and theft of later depositors' funds - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` derives every core AMM account (`amm_info`, `amm_target_orders`, `amm_lp_mint`, `amm_coin_vault`, `amm_pc_vault`) deterministically from the `market_info` account key via `get_associated_address_and_bump_seed`, but never validates that `market_info` is an actual, program-owned Serum/OpenBook market. The instruction handling explicitly documents this account as unchecked filler: "Just a seed for AMM account. Can be any account." [1](#0-0)  The same applies in the 18-account legacy branch where `market_program_info`/`open_orders_info` are also explicitly unused. [2](#0-1) 

### Finding Description
`get_associated_address_and_bump_seed` computes the pool's PDAs purely from `program_id`, `market_address.to_bytes()`, and a fixed suffix seed (`AMM_ASSOCIATED_SEED`, `TARGET_ASSOCIATED_SEED`, `LP_MINT_ASSOCIATED_SEED`, `COIN_VAULT_ASSOCIATED_SEED`, `PC_VAULT_ASSOCIATED_SEED`) — this is the sole determinant of the canonical pool address for a given market. [3](#0-2) 

Because `process_initialize2` never checks that `market_info` is owned by a real market program, is a genuine Serum/OpenBook market, or is otherwise privileged, any unprivileged transaction can call `Initialize2` for a market pubkey it does not control, supplying its own `amm_coin_mint`, `amm_pc_mint`, and attacker-chosen `init_coin_amount`/`init_pc_amount`. [4](#0-3)  The accounts are created with `invoke_signed`/`system_instruction::allocate`+`assign` using PDA signer seeds derived only from `market_info.key`, so once created, `amm.status` becomes `AlreadyInUse` and any subsequent legitimate `Initialize2` call for the same market fails with `RepeatCreateAmm`/`AlreadyInUse`. [5](#0-4) [6](#0-5) 

This is the same bug class as the referenced Optimism/Wintermute exploit: a deterministically-computable, unauthenticated deployment address that a third party can preemptively occupy ("squat") before the intended owner submits their initialization transaction, seizing control of the address and its subsequent state.

The attacker controls the initial coin/pc deposit ratio entirely (subject only to the minimum-liquidity burn of `10^decimals` LP tokens), so it can set an arbitrary, heavily skewed initial price at the exact deterministic pool address that off-chain tooling/UI would compute for that market. [7](#0-6) 

### Impact Explanation
Any user or automated integrator relying on the deterministic derivation of the pool address for a known/public market pubkey (a common pattern for pool discovery) can be directed to an attacker-squatted pool. Swaps or deposits made against this squatted pool trade against an attacker-manipulated price/ratio and mint LP against attacker-controlled reserves, resulting in direct value transfer to the attacker when they later withdraw. Additionally, the legitimate project is permanently prevented from ever initializing its intended AMM for that market (`AlreadyInUse`), a permanent denial of pool creation for that market.

### Likelihood Explanation
The `Initialize2` instruction is fully permissionless — any signer can submit it with attacker-chosen `market_info`, mints, and amounts, and there is no requirement that `market_info` be owned by any market program. [8](#0-7)  An attacker only needs to know the coin/pc mint pair and market pubkey a legitimate deployer intends to use (typically public before pool creation), then race a single transaction ahead of theirs.

### Recommendation
Validate that `market_info` is owned by an approved market program (e.g., OpenBook) and represents the coin/pc mint pair being initialized, before using it as a PDA seed, or otherwise bind the AMM address derivation to values that cannot be freely chosen by an unprivileged caller (e.g., require `AmmConfig`/admin co-signature for pool creation, or check market ownership/mints against the actual DEX market layout as earlier Raydium versions did before market checks were stripped for the OpenBook migration).

### Proof of Concept
1. Attacker learns the public market pubkey `M` and mint pair `(coin_mint, pc_mint)` that a project intends to use for its AMM pool.
2. Attacker computes the deterministic PDAs `amm_info`, `amm_target_orders`, `amm_lp_mint`, `amm_coin_vault`, `amm_pc_vault` via `get_associated_address_and_bump_seed(program_id, M, seed)` — identical computation any client would use. [3](#0-2) 
3. Attacker submits `Initialize2` first, passing `M` as `market_info`, their own chosen skewed `init_coin_amount`/`init_pc_amount`, and their own wallet as `user_wallet`/LP recipient. The call succeeds since no ownership check on `market_info` exists. [9](#0-8) 
4. The legitimate project's later `Initialize2` call for the same market fails (`AlreadyInUse`/`RepeatCreateAmm`), while unsuspecting users interacting with the "official" deterministic pool address trade against the attacker-controlled reserves.
