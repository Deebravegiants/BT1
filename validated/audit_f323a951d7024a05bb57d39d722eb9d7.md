Audit Report

## Title
Missing `return` after failed OIDC email claim extraction lets `handleTokenExchange` create an authenticated session with an empty user identity - ([File: core/sessions/oidcauth/oidc.go])

## Summary
In `oidcAuthenticator.handleTokenExchange`, when `claims["email"].(string)` type assertion fails, the handler writes an HTTP 500 response but does not `return`, unlike every other error branch in the function. Execution falls through, mapping group claims to a role, inserting a new `oidc_sessions` row with `user_email = ''`, setting a valid session cookie, and finally overwriting the earlier 500 with a `200 OK` JSON success response.

## Finding Description
The vulnerable code is: [1](#0-0) . All prior error branches in the same function (`oauth2Config.Exchange`, `idToken.Claims`, `ExtractIDClaimValues`, missing `id_token`, `Verify` failure) correctly `return` after writing the error response, e.g. [2](#0-1) , but the `email` branch omits it.

Because of the missing `return`, execution proceeds to `IDClaimsToUserRole`, the `INSERT INTO oidc_sessions` with `user_email = strings.ToLower(email)` (empty string), `ginSession.Set`/`ginSession.Save()`, and the final `c.JSON(http.StatusOK, ExchangeTokenResponse{Success: true})`, overwriting the earlier `500` response: [3](#0-2) .

This session is later accepted as valid by `AuthorizedUserWithSession`, which looks up `oidc_sessions` purely by session ID and returns whatever `user_email`/`user_role` was stored without validating that the email is non-empty: [4](#0-3) . No existing middleware, role wrapper, or validation catches this — the role is still derived from real group claims via `IDClaimsToUserRole`, but the identity binding to a specific user is broken, and the client receives a live, cookie-backed session.

## Impact Explanation
This is reachable via the unauthenticated OIDC token-exchange endpoint (`handleTokenExchange`), which any client completing the OAuth2 code exchange with the node can trigger. A misconfigured or attacker-influenced IdP response (email claim missing, `null`, or non-string) causes the node to mint a valid authenticated session cookie tied to an empty-email session record, while the client-visible response ultimately reports success. This breaks the invariant that every row in `oidc_sessions` corresponds to an identifiable user, and downstream flows keyed on `email` (e.g., audit logging, or any future FindUser-by-email lookups) will operate on an empty string. The resulting session's role is still gated by legitimate group-claim mapping (`IDClaimsToUserRole` must succeed and assign a role), so it does not automatically grant admin privileges, but it does represent a session-integrity/authentication defect consistent with node API session-handling flaws in scope.

## Likelihood Explanation
Moderate: it requires the verified ID token's claims to omit `email` or provide a non-string value, which is a plausible IdP misconfiguration scenario, not a purely theoretical one, and does not require any privileged access — only that the client completes the state/code exchange. The bug is a straightforward missing `return`, and the code path is fully in the request handler, not gated by any additional check.

## Recommendation
Add the missing `return` immediately after writing the error response in the `email` claim extraction branch, matching the pattern of all other error branches:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```
Additionally, reject an empty-string `email` before persisting the session, since `oidc_sessions.user_email` should never be empty.

## Proof of Concept
1. Configure/compromise an OIDC provider so the verified ID token's claims omit `email` or return a non-string value.
2. Complete the OIDC login flow against the node (`GET` sign-in redirect → provider → `POST` to the token-exchange endpoint with matching `state`/`code`).
3. `oauth2Config.Exchange`, `idToken.Claims`, and `ExtractIDClaimValues` succeed (these only depend on the configured group/role claim, not `email`); `claims["email"].(string)` fails at [5](#0-4) .
4. Handler writes HTTP 500 but does not return, then proceeds to insert an `oidc_sessions` row with `user_email=''`, sets the session cookie, and responds `200 OK` `{"success":true}`.
5. Use the returned session cookie against any authenticated endpoint; `AuthorizedUserWithSession` returns a `User{Email: "", Role: <mapped role>}`, confirming a live session was created despite the claim-extraction failure. A Go unit test can directly invoke `handleTokenExchange` with a mock claims map lacking `email`, then assert the HTTP status/body was correctly aborted after the fix (currently it is not).
