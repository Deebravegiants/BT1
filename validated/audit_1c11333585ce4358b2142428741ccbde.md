### Title
Owner/threshold changes can permanently deadlock a timelocked multisig via unrecoverable `override_threshold` invariant violation - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`multisig_account.move` adds a `MultisigAccountTimeLock` feature (not present in upstream Aptos) that stores an `override_threshold` alongside `num_signatures_required` and `owners`. Analogous to the reported bug (an update path that changes a core value — position size/open price — without re-validating a dependent limit — TP/SL distance), `update_owner_schema()` changes `owners` and `num_signatures_required` and only partially reconciles the dependent `override_threshold` invariant, asserting unconditionally rather than adjusting it, which can make legitimate owner-management operations permanently unexecutable.

### Finding Description
`update_owner_schema` (the internal function backing `add_owners`, `remove_owners`, `swap_owners`, `update_signatures_required`, etc.) enforces, at the end of the function, that if a `MultisigAccountTimeLock` exists:
1. If `override_threshold > num_owners` (after the owner change), it is clamped down to `num_owners`.
2. Then it asserts `override_threshold.is_none() || override_threshold > num_signatures_required`. [1](#0-0) 

Unlike the clamp for the owner-count case, there is no analogous "adjust" for the `num_signatures_required` case — if changing owners/threshold via a legitimate governance proposal would make `override_threshold <= num_signatures_required` (e.g., removing owners while `num_signatures_required` is being raised, or owners shrinking such that the clamped `override_threshold` collides with `num_signatures_required`), the entire owner-management transaction (`update_owner_schema`) aborts with `EINVALID_TIMELOCK_OVERRIDE_THRESHOLD`, rather than clamping/adjusting the value the way the `TradingStorage.updateTradePosition()` bug's fix (`_limitTpDistance`/`_limitSlDistance`) re-derives dependent bounds after a state-changing update. [2](#0-1) 

The only other way to clear this invariant is `remove_timelock`, which itself must go through the same multisig execution/threshold flow and is therefore blocked by the same governance process that is now stuck. [3](#0-2) 

### Impact Explanation
If a multisig loses the ability to add/remove owners or change `num_signatures_required` because any valid combination violates the `override_threshold` invariant, custody of any resource-account-held assets (APT, coins, objects) controlled by that multisig can become permanently unrecoverable through normal governance — matching the "Permanent lock or non-recoverable loss of ... multisig-held ... value" custody-impact category. This would be High impact if confirmed, since multisig-controlled treasuries/resource accounts could be bricked.

### Likelihood Explanation
Low-to-uncertain. I could not locate or inspect the `configure_timelock`/timelock-creation entry function or the transaction-execution path that consumes `override_threshold` (e.g., whether it lets transactions bypass the timelock delay) within the available tool-call budget, so I cannot confirm: (a) whether an alternate governance path exists to reset `override_threshold` independent of `update_owner_schema`, or (b) the exact preconditions under which owners would organically end up in this locked state. Without that, I cannot fully prove the "unprivileged root cause" and "exact corrupted value" requirement to Critical/High confidence — this should be treated as a lead requiring further code review (specifically `configure_timelock`, `execute_transaction`, and any owner-swap flows), not a fully proven exploit.

### Recommendation
In `update_owner_schema`, when the invariant `override_threshold > num_signatures_required` would be violated by a legitimate owner/threshold change, clamp/adjust `override_threshold` (or `num_signatures_required` change) similarly to how `override_threshold` is already clamped against `num_owners`, rather than aborting the whole transaction. Alternatively, provide a dedicated, always-executable path (not gated by the same threshold) to disable or resize the timelock override so owner governance can never become permanently stuck.
