### Title
Fully closing a stake account after epoch reward calculation but before partitioned distribution burns its already‑computed reward - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
Agave calculates all stake rewards for an epoch in one shot at the epoch boundary and then pays them out over many subsequent blocks in a "partitioned" distribution. The reward amount for each stake account is fixed at calculation time, but the actual account is re‑looked‑up in the live `StakesCache` at pay‑out time. If a stake account (already fully deactivated, i.e. a `DeactivatedStake` type reward) is withdrawn/closed by its owner in the window between the epoch‑boundary calculation and the block where its partition is actually distributed, the account no longer exists in `StakesCache`, the lookup fails, and the reward for that account is silently burned instead of paid — the same "computed‑but‑never‑delivered because the recipient's state changed before distribution" bug class described in the external GaugeController report.

### Finding Description
Reward calculation happens once at the epoch boundary in `calculate_rewards_for_partitioning` / `calculate_stake_rewards_and_commissions`, producing a `PartitionedStakeReward` per stake account with a fixed `stake_reward` amount [1](#0-0) . Actual payout is deferred and spread across many blocks/partitions (`distribution_starting_block_height`, `REWARD_CALCULATION_NUM_BLOCKS`) via `distribute_epoch_rewards_in_partition` → `store_stake_accounts_in_partition` [2](#0-1) .

At pay-out time, `build_updated_stake_reward` re-fetches the stake account from the *current* `StakesCache` snapshot, not the one used during calculation: [3](#0-2) 

If the account is no longer present (because it was fully deactivated already and the owner submitted a `Withdraw` for the entire remaining balance, closing the account), the lookup returns `DistributionError::AccountNotFound`, and the caller reclassifies the pre-computed reward as burned rather than paid: [4](#0-3) 

The docstring on `store_stake_accounts_in_partition` explicitly assumes this cannot happen ("there should never be rewards burned") [5](#0-4) , but a stake account that is already fully deactivated (`stake_at_distribution_epoch == 0`, marked `RewardType::DeactivatedStake`) can legitimately be withdrawn down to zero and closed by its authority via the normal `Withdraw` instruction, as confirmed by the CLI integration test showing a fully-deactivated stake account can be withdrawn completely, closing it: [6](#0-5) . Nothing in the reward path prevents a user from doing so between the reward-calculation snapshot and the specific block on which their partition is processed.

### Impact Explanation
This is a value-destruction bug rather than a theft: a legitimately earned reward for the previous epoch that has already been calculated (and reserved out of the `EpochRewards` sysvar budget) is permanently forfeited/burned instead of being paid to the rightful owner, because the account happened to be closed in the multi-block window between reward calculation and that account's partition being processed. It also mutates protocol-wide accounting: `update_epoch_rewards_sysvar` is called with the burned amount included in "distributed" so the `EpochRewards` sysvar and capitalization bookkeeping treat the reward as consumed even though no one received it [7](#0-6) .

### Likelihood Explanation
Reachable by an ordinary, unprivileged staker with no special permissions: fully deactivating stake before an epoch boundary and withdrawing the entire remaining balance immediately once it becomes available is a normal, permitted user action via the stake program's `Withdraw` instruction. The only requirement is timing the withdrawal to land in the window between the epoch-boundary reward calculation and the specific block at which that account's partition is later distributed (partitioned distribution deliberately spans many blocks after the epoch boundary). Since the loss falls on the withdrawing account itself, there's no economic incentive to trigger it deliberately, which somewhat limits real-world likelihood, but it can occur unintentionally to any staker who closes out at the wrong moment, and it corrupts the "no rewards burned" invariant the distribution code assumes.

### Recommendation
Either (a) hold the fixed reward amount aside using a snapshot of the stake account's state taken at calculation time rather than re-reading the live `StakesCache` at distribution time, or (b) if the account is no longer present, redirect that reward to the withdrawal destination/authority (since it's a fully-deactivated stake being cashed out) instead of burning it, or (c) prevent full closure of a stake account whose previous-epoch reward has not yet been distributed (track "pending distribution" stake accounts and reject/queue their `Withdraw` until payout completes).

### Proof of Concept
1. Delegate stake to a vote account and let it earn credits over an epoch.
2. Deactivate the stake and wait for it to fully cool down (`effective stake == 0`).
3. At the epoch boundary, the bank computes a `PartitionedStakeReward` for this account with `RewardType::DeactivatedStake` and a non-zero `stake_reward` (see test `test_distribute_deactivated_stake_reward_with_pending_reward_adjust`, `runtime/src/bank/partitioned_epoch_rewards/distribution.rs:949-1035`), reserved out of the `EpochRewards` sysvar total.
4. Before the block where this account's partition is processed by `distribute_partitioned_epoch_rewards`, submit a `Withdraw` instruction for the full remaining balance (rent-exempt reserve + any residual lamports), closing the stake account, exactly as exercised in `test_stake_delegation_and_withdraw_all`, `cli/tests/stake.rs:480-647`.
5. When `store_stake_accounts_in_partition` later processes this account's partition index, `stakes_cache_accounts.get(&stake_pubkey)` returns `None`, `build_updated_stake_reward` returns `DistributionError::AccountNotFound`, and the reward amount is added to `stake_reward_lamports_burned` instead of being credited to any account — the previously-computed reward is destroyed.

    /// Store the rewards to AccountsDB, update reward history record and total capitalization.
    fn distribute_epoch_rewards_in_partition(
        &self,
        partition_rewards: &StartBlockHeightAndPartitionedRewards,
        partition_index: u64,
    ) {
        let pre_capitalization = self.capitalization();
        let (
            DistributionResults {
                stake_reward_lamports_minted,
                stake_reward_lamports_burned,
                block_reward_lamports_distributed,
                block_reward_lamports_burned,
                updated_stake_rewards,
            },
            store_stake_accounts_us,
        ) = measure_us!(self.store_stake_accounts_in_partition(partition_rewards, partition_index));

        // increase total capitalization by the distributed rewards
        self.capitalization
            .fetch_add(stake_reward_lamports_minted, Relaxed);

        // decrease total capitalization by burned block rewards
        self.capitalization
            .fetch_sub(block_reward_lamports_burned, Relaxed);

        // decrease distributed capital from epoch rewards sysvar
        self.update_epoch_rewards_sysvar(
            stake_reward_lamports_minted + stake_reward_lamports_burned,
            block_reward_lamports_distributed + block_reward_lamports_burned,
        );

        // update reward history for this partitioned distribution
        self.update_reward_history_in_partition(&updated_stake_rewards);

        let metrics = RewardsStoreMetrics {
            pre_capitalization,
            post_capitalization: self.capitalization(),
            total_stake_accounts_count: partition_rewards.all_stake_rewards.num_rewards(),
            total_num_partitions: partition_rewards.partition_indices.len(),
            partition_index,
            store_stake_accounts_us,
            store_stake_accounts_count: updated_stake_rewards.len(),
            distributed_rewards: stake_reward_lamports_minted,
            burned_rewards: stake_reward_lamports_burned,
            distributed_block_rewards: block_reward_lamports_distributed,
            burned_block_rewards: block_reward_lamports_burned,
        };

        report_partitioned_reward_metrics(self, metrics);
    }
