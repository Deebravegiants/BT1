### Title
Webhook shop identity spoofing via HMAC that only covers the request body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) exclusively from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `ShopifyAPI::Utils::HmacValidator` verifies only covers the raw request body. This breaks the identity binding `authenticated_bytes == acted_upon_shop`: the signature proves the body was signed with the app's secret, but it proves nothing about which shop the request claims to be from.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the signed payload: [2](#0-1) 

`HmacValidator.validate` computes and compares the signature only over `verifiable_query.to_signable_string` (i.e. the raw body): [3](#0-2) 

`Registry.process` uses this validation result as its sole authenticity gate, then trusts `request.shop` (the header) to build `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because the header is never part of the signed bytes, `bytes_verified (raw_body) != bytes_used_for_tenant_routing (shop header)`. Any internet-reachable caller who can obtain one valid `(raw_body, hmac)` pair for the app's secret (trivially available by installing the app on any test/free shop, or by observing legitimate webhook traffic sent to a shop they control) can replay that exact body+hmac to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value naming a different, victim tenant. `HmacValidator.validate` still returns `true` because it never inspected the header, and `Registry.process` forwards the attacker-chosen shop string to the handler as if it were authenticated.

### Impact Explanation
This is a cross-tenant identity-binding break: the "authenticated" shop and the shop actually acted upon by the handler are not the same value. Any app that uses `WebhookMetadata#shop` (as returned by this library) to key persistence, look up sessions, or route data updates will process/store the replayed payload under an attacker-chosen tenant identifier despite full HMAC verification passing. This satisfies the "cross-tenant access" Critical impact category — an unprivileged caller (any developer who can install the app once, even on a free/trial shop) can attribute crafted, "verified" webhook data to a shop it never came from.

### Likelihood Explanation
Likelihood is high: the webhook endpoint is public by design; a working `(body, hmac)` pair is obtainable by any actor able to install the app on at least one shop (a normal, low-privilege action) or capture one legitimate delivery; no `api_secret_key` or session hijack is needed to perform the spoof itself — only to obtain a single legitimate sample once, after which the header can be freely rewritten for replay against arbitrary victim shop identifiers.

### Recommendation
- Bind `shop` (and other routing-critical fields such as `topic`, `api_version`, `webhook_id`) into the signed content, or otherwise cryptographically tie the header value to the verified payload, before exposing `request.shop` as trusted.
- At minimum, document/enforce that consumers of `WebhookMetadata#shop` must cross-check it against an independently stored, previously-authenticated session/shop mapping (e.g., confirm the shop has an active installation with a known access token) rather than treating the header as authenticated by `HmacValidator.validate` alone.
- Consider validating that the HMAC-body relationship is unique per delivery (e.g., using `webhook-id` as a replay-detection key) to reduce the value of captured legitimate samples for replay.

### Proof of Concept
1. Attacker installs the target app on shop `attacker.myshopify.com` (or otherwise legitimately receives one webhook delivery), capturing a valid `raw_body` and its `X-Shopify-Hmac-Sha256` header value signed with the app's real secret.
2. Attacker sends a new HTTP request directly to the app's public webhook endpoint, reusing the exact same `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` [5](#0-4)  — validation succeeds.
4. `Registry.process` builds `WebhookMetadata.new(..., shop: request.shop, ...)` using the attacker-controlled header value [6](#0-5)  and passes it to the app's `handler.handle`, which now believes the signed payload originated from `victim-shop.myshopify.com`.

          received_signature = verifiable_query.hmac
