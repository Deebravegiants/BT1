### Title
Duplicate `address(0)` entries in `erc20TokenAddresses` let `msg.value` be double-counted across independent per-token balance equations, minting unbacked shielded ETH - (File: `contracts/Hinkal.sol`)

### Summary
`Hinkal.transact` computes `oldBalances`/`newBalances` once for the whole call and then validates a *separate* balance equation for every index `i` of `circomData.erc20TokenAddresses` independently. For any index where the token is `address(0)`, the code adds `msg.value` into that index's equation. Because neither `dimensionsCheck` nor `performHinkalChecks` reject duplicate token addresses, an attacker can list `address(0)` more than once, causing the same `msg.value` to be added again in the second occurrence's equation, letting the attacker mint an extra shielded ETH UTXO/`amountChange` credit that is not backed by any real ETH.

### Finding Description
The equality that should hold is: **real ETH received by the contract == exactly one term (`amountChanges[i]` or on-chain UTXO) per unique token**. Instead, the per-index loop breaks this by letting `msg.value` back two different equations.

`getBalancesForArray` snapshots balances once before and once after the external/internal action: [1](#0-0) 

The per-token check then runs for every `i` in `erc20TokenAddresses`, and for `address(0)` it re-adds `msg.value`: [2](#0-1) 

`getERC20OrETHBalance`/`getBalancesForArray` in `Transferer.sol` simply read `address(this).balance` for every `address(0)` entry, so two entries at different indices produce identical `oldBalances[i]`/`newBalances[i]` values (both equal to the same global ETH balance snapshots): [3](#0-2) 

Neither `dimensionsCheck` nor `performHinkalChecks` in `HinkalHelper.sol` enforce that `erc20TokenAddresses` contains unique entries; they only check array-length consistency across the various `CircomData` fields: [4](#0-3) [5](#0-4) 

Because `real_delta = newBalances[i] - oldBalances[i]` is identical for every duplicated `address(0)` index (it's the same global ETH balance measured at the same two points in time), both equations reduce to the same left-hand value `L = real_delta + msg.value`. The attacker then freely splits `L` across two independent right-hand sides: one index satisfies the real swap input/output (e.g., in `ExternalActionSwap.swap`, which uses `erc20TokenAddresses[0]`/`[1]` explicitly as swap input/output — [6](#0-5) ), while a second, unrelated `address(0)` entry elsewhere in the array (not touched by the swap logic at all) claims `amountChanges[i] = L` or an `onChainCreation` UTXO of value `L`, with `checkOnchainCreation` only requiring `amountChanges[i]==0` and zeroed nullifiers when `onChainCreation[i]` is true — it does not forbid a nonzero output UTXO amount for that index: [7](#0-6) 

The on-chain guard that is supposed to prevent unbacked minting — the per-index `balanceDif == amountChanges[i] + utxoAmount` check — is exactly the mechanism being abused, since it is evaluated independently per array index rather than per unique token address, and no code path deduplicates or rejects repeated `address(0)` entries before this check runs.

### Impact Explanation
An attacker can mint a shielded ETH `amountChange`/UTXO credit that is fully double-backed by a single real `msg.value` transfer, effectively creating unbacked shielded ETH value inside the protocol. This matches the Critical category: "minting shielded value without backing (protocol insolvency)." The attack requires no privileged role — any EOA calling `transact` with a crafted `erc20TokenAddresses` array (containing `address(0)` twice) and a locally generated proof matching the crafted public inputs is sufficient, and it is repeatable per transaction/deposit.

### Likelihood Explanation
Preconditions: attacker must be able to generate a valid proof for the chosen `CircomData` (their own UTXOs/circuit inputs), register a duplicate `address(0)` entry in `erc20TokenAddresses`, and route through any external action (e.g., LI.FI swap) or even the internal-transact path (`externalActionId == 0`) since the vulnerable loop in `Hinkal.transact` runs regardless of `_internalTransact`/`_externalTransact`. This requires only standard user capabilities (deposit funds, generate their own proof, call `transact`), no special privileges, and is fully reproducible for any transaction that includes two `address(0)` slots in the token dimension array.

### Recommendation
Enforce uniqueness of `erc20TokenAddresses` (particularly for `address(0)`) in `dimensionsCheck`/`performHinkalChecks` before the balance-equation loop runs, or refactor the `Hinkal.transact` balance validation to aggregate balances/`msg.value` per unique token address (deduplicated) rather than per raw array index, so that `msg.value` can only be attributed to a single accounting term across the whole transaction.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, and a `LifiExternalAction` (or a minimal `IExternalActionV2` mock) with a mock router.
2. Craft `CircomData` with `dimensions.tokenNumber = 3`: `erc20TokenAddresses = [address(0), outputToken, address(0)]`.
3. Set index 0 as the real swap input (`amountChanges[0]` matching a real inputAmount consumed by the swap, `onChainCreation[0] = false`), index 1 as the real swap output, and index 2 as a duplicate `address(0)` entry with `onChainCreation[2] = true`, `amountChanges[2] = 0`, and an off-chain/on-chain UTXO of amount equal to `msg.value` with no real corresponding nullifier/deposit.
4. Generate a matching proof (or stub `verifyProof` in a test harness) so `Hinkal.transact` accepts the crafted public inputs.
5. Call `transact{value: X}(...)`.
6. Assert: sum of minted UTXO amounts for `address(0)` (index0 UTXO + index2 UTXO, if any) exceeds the real `address(this).balance` delta plus the legitimately consumed swap amount — i.e., `mintedETHValue > actualETHReceivedByContract`, proving unbacked minting.

                block.chainid,
                hinkalAddress,
