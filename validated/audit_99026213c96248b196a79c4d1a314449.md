### Title
Unchecked `copy_from_slice` panic on attacker-influenced `from` bytes in hyper-fungible-token `on_accept` - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`hyper-fungible-token`'s `IsmpModule::on_accept` callback, reached from the fully unprivileged `pallet_ismp::Call::handle_unsigned` extrinsic, copies a variable-length, cross-chain-controlled byte string into a fixed-size `[u8; 32]` stack buffer with `copy_from_slice` without first checking that the source length is exactly 32 bytes. `copy_from_slice` panics on any length mismatch, which is exactly the same bug class as the analog `PostgreSQL` CVE (attacker-controlled length written into a fixed-size buffer without a bound check) — the difference being Rust turns the OOB write into a deterministic panic/trap instead of silent stack corruption, but the root cause (missing length validation before a fixed-size copy) is identical.

### Finding Description
In `on_accept`, when the pallet is asked to execute calldata attached to an incoming token transfer, the "unsigned" branch resolves the dispatch origin from `message.from` (a Solidity `bytes`-typed field decoded via `Message::abi_decode(&body)`), which for non-EVM sources is copied straight into a 32-byte array:

```rust
} else {
    let from_bytes = message.from.as_ref();
    if source.is_evm() {
        T::EvmToSubstrate::convert(H160::from_slice(
            &from_bytes[from_bytes.len() - 20..],
        ))
    } else {
        let mut account = [0u8; 32];
        account.copy_from_slice(from_bytes);   // <-- panics if from_bytes.len() != 32
        account.into()
    }
};
``` [1](#0-0) 

`message.from` is a Solidity `bytes` (arbitrary length) field embedded in the ABI-encoded ISMP request `body`, decoded here: [2](#0-1) 

The pallet's own codebase has already recognized and fixed the identical anti-pattern once before, in `ismp::host::StateMachine::from_str`, where a comment explicitly documents this exact bug class and its impact:

> "A malformed `SUBSTRATE-`/`TNDRMINT-` id whose byte length is not exactly 4 must return an error rather than panic. The id is copied into a `[u8; 4]`, and `copy_from_slice` traps on a length mismatch — in the runtime this is a wasm trap reachable from untrusted input (e.g. `BandwidthManager.purchase`)" [3](#0-2) 

That fix shows the maintainers treat an unchecked, attacker-reachable `copy_from_slice` panic as a serious, previously-shipped defect worth patching — but the same pattern remains present, unpatched, in `hyper-fungible-token`'s `on_accept`, which is invoked for every incoming ISMP `PostRequest` targeted at this module via the permissionless `handle_unsigned` call: [4](#0-3) 

### Impact Explanation
A runtime panic triggered inside a pallet dispatchable/module callback while processing an ISMP message traps the WASM runtime; unlike a normal `DispatchError`, this failure mode is not a graceful revert but an abort of block execution, matching the maintainers' own characterization ("wasm trap") of this bug class elsewhere in the codebase. Because `handle_unsigned` is validated via `validate_unsigned`/executed by any relayer for free, a single malformed but state-proof-valid message can repeatedly trap block execution for the affected parachain, denying delivery of this route's messages (and potentially any other message batched in the same block) until intervention — falling under "a route unable to deliver messages."

### Likelihood Explanation
Exploitability hinges on whether the length of the ABI `bytes from` field inside the request `body` is fully determined by the sender-side dispatching contract or can be influenced by an unprivileged caller of that contract (e.g., a user-controlled `bytes` parameter forwarded verbatim into `message.from`). I was not able to fully verify the EVM/Solidity-side encoder for this specific token-bridge message within the available index, so the concrete reachability of a non-32-byte `from` value could not be fully confirmed in this pass — this should be validated directly against the sending contract's encoding logic before treating this as fully exploitable. Given the codebase's own prior fix of the identical pattern (with an explicit note that it is "reachable from untrusted input"), the underlying defensive gap is real and warrants a fix regardless of the exact upstream trigger.

### Recommendation
Validate `from_bytes.len() == 32` (and `== 20` for the EVM branch, which currently also indexes unchecked with `from_bytes.len() - 20`, itself panicking on underflow for any length under 20) before constructing the fixed-size arrays, returning a proper `HftError` variant instead of panicking — mirroring the fix already applied to `StateMachine::from_str`.

### Proof of Concept
Not fully constructible without confirming the exact encoding contract on the counterparty chain; the mechanical trigger is: submit (via `handle_unsigned`, with a valid state/consensus proof) a `PostRequest` whose ABI-encoded `body` decodes to a `Message` with `to`/`from` fields of length other than 20 or 32 bytes and a non-EVM `source`, causing `account.copy_from_slice(from_bytes)` to panic during `on_accept`.
