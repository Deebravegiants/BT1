## Title
Unvalidated `message.from` length causes a panic (`from_bytes[from_bytes.len() - 20..]` / `copy_from_slice`) in `HyperFungibleToken::on_accept`, halting cross-chain message execution - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`Pallet::on_accept` in the `hyper-fungible-token` pallet decodes an attacker-influenced ABI `Message` from an incoming ISMP `PostRequest` body and, when optional calldata carries no signature, converts `message.from` into a Substrate account by indexing it with a fixed offset without first checking its length — mirroring the GPMF `GPMF_ScaledData()` pattern of trusting a length/offset derived from untrusted input before bounds-checking it.

### Finding Description
In `on_accept` [1](#0-0) , when `message.data` contains a `SubstrateCalldata` payload with no `signature`, the code computes the dispatch `origin` from `message.from`:

```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
```

`message.from` is decoded straight from the attacker-controlled request body via `Message::abi_decode(&body)` [2](#0-1)  — it is declared as `bytes from` in the Solidity `Message` struct [3](#0-2)  with no length constraint enforced anywhere before this point. Unlike `message.to`, which is explicitly length-checked (`== 32` or `== 20`, else `Err(HftError::InvalidRecipientLength)`) at [4](#0-3) , `message.from` gets no equivalent validation on this code path:
- If `source.is_evm()` and `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows (`usize` subtraction), producing a huge start index and panicking with "attempt to subtract with overflow" / a slice-index panic.
- If `source` is not EVM and `from_bytes.len() != 32`, `copy_from_slice` panics on the length mismatch.

This is directly analogous to CVE-2020-16159: a parser trusts an offset/length taken from untrusted wire data and indexes/copies before validating it fits the buffer, causing a crash during processing of the input.

The authentication check earlier (`ContractToAsset::<T>::get(source, &from)` at line 55) validates the ISMP module-address `from` field of the `PostRequest` envelope (the request's routing "from"), which is a *different* field from `message.from`, the payload field decoded from `body`. The payload-level `message.from` is fully attacker-controlled independent of that check.

### Impact Explanation
`on_accept` executes inside the consensus-critical ISMP message-dispatch path (`pallet-ismp::handle_unsigned` → module router → `HyperFungibleToken::on_accept`), reachable by any relayer submitting a message/proof for a registered source contract, no special privilege required beyond having a configured `ContractToAsset` mapping (a legitimate, expected condition for any live HFT deployment). A panic raised here during block execution/transaction validation is not a benign application-level revert — FRAME dispatchables that panic can abort the extrinsic execution non-gracefully and, depending on runtime panic configuration, can affect the whole block/import path, denying delivery of that message and potentially of the batch it is included in. This matches the "route unable to deliver messages" impact category: a relayer cannot get a well-formed cross-chain transfer with `data` payload and this `from` shape processed, and worse, a malicious/crafted counter-party contract on the source chain (or a relayer replaying a message from one) can repeatedly submit malformed `from` values to break processing of any transfer that carries executable calldata.

### Likelihood Explanation
High: any address on a connected source chain that is registered via `ContractToAsset` (i.e., any legitimate HFT peer contract, which itself may be compromised, buggy, or simply support flexible sender encodings) can emit a `PostRequest` whose ABI-encoded `Message.from` is shorter than 20/32 bytes while `Message.data` is non-empty and unsigned. No cryptographic break or governance compromise is needed — only a single relayed message.

### Recommendation
Validate `message.from` length before use, exactly as is already done for `message.to`:
```rust
let from_bytes = message.from.as_ref();
let origin = if source.is_evm() {
    if from_bytes.len() != 20 {
        Err(HftError::InvalidSenderLength(from_bytes.len()))?
    }
    T::EvmToSubstrate::convert(H160::from_slice(from_bytes))
} else {
    if from_bytes.len() != 32 {
        Err(HftError::InvalidSenderLength(from_bytes.len()))?
    }
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
};
```
Note the pallet already defines `HftError::InvalidSenderLength` and uses this exact pattern safely in `on_timeout` [5](#0-4)  — the fix should simply be mirrored into `on_accept`.

### Proof of Concept
1. Register a source-chain contract address in `ContractToAsset` (normal deployment configuration).
2. From that source chain (or by controlling/spoofing the corresponding relayed `PostRequest`), submit a `PostRequest` whose ABI-encoded body decodes to a `Message` with:
   - `to`: valid 20 or 32 bytes (passes existing check),
   - `amount`: any valid amount,
   - `data`: a SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <any allowed call> }`,
   - `from`: a byte string of length e.g. 5 (for an EVM `source`) or 10 (for a non-EVM `source`).
3. Relay/deliver this message through `pallet-ismp` so `HyperFungibleToken::on_accept` is invoked.
4. Execution reaches `&from_bytes[from_bytes.len() - 20..]` (EVM case: `5 - 20` underflows `usize`) or `account.copy_from_slice(from_bytes)` (non-EVM case: length mismatch), causing a panic during message dispatch instead of a clean `Err(...)`.
