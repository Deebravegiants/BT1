## Analysis

The reachable analog here is in `lib/shopify_api/webhooks/request.rb`, which implements `Utils::VerifiableQuery` for HMAC validation of incoming webhooks.

The identity-binding equality that should hold is:
`request.shop` (the tenant identity used by the app to attribute webhook data) == the value actually protected by `HmacValidator.validate`.

But `Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

while `shop` is read straight from an unauthenticated HTTP header, never included in the signed material: [2](#0-1) 

`Registry#process` validates the HMAC (which only covers the body) and then forwards `request.shop` — the unauthenticated header — straight to the app's handler as tenant identity: [3](#0-2) 

### Title
Webhook shop identity spoofable because `shop-domain` header is not covered by HMAC verification - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Webhooks::Request` binds its HMAC signature only to the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` attribute that `Registry.process` uses to attribute the webhook to a tenant is read directly from the `X-Shopify-Shop-Domain`/`Shopify-Shop-Domain` header, which is never included in the signed material.

### Finding Description
`HmacValidator.validate` recomputes an HMAC over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [4](#0-3) 

For webhooks, `to_signable_string` is exactly the raw body, and `hmac` is decoded from the `X-Shopify-Hmac-Sha256` header — but the `shop` value, read via `shopify_header("shop-domain")`, is not part of either. Since the body and its HMAC are independent of the shop header, any request bearing a body+HMAC pair from one legitimate webhook delivery remains "valid" per `HmacValidator.validate` regardless of what `shop-domain` header accompanies it. `Registry.process` trusts this unauthenticated header value directly as the tenant identity forwarded to the app's webhook handler: [5](#0-4) 

This breaks the equality `authenticated_shop == handler_shop`: the shop that was cryptographically bound to the payload (none, since it isn't bound at all) does not match the shop the handler is told the data belongs to.

### Impact Explanation
This crosses a tenant boundary: an unprivileged actor who can obtain (or send to themselves) one legitimately-signed webhook body/HMAC pair for their own shop can replay that exact request while substituting an arbitrary `shop-domain` header, causing the host application to process/store that body's data under a different, victim tenant's identity — a cross-tenant data-confusion/injection primitive that satisfies the "cross-tenant access" criterion.

### Likelihood Explanation
Low/Medium: this requires the ability to reach the app's webhook endpoint with a controllable `shop-domain` header while reusing a captured valid body+HMAC, which is feasible for anyone who installs the app on their own shop (getting real signed webhooks) and then replays them with a forged header against the same endpoint, since the gem itself performs no binding check between the header and the signed content.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values inside the HMAC-covered signable material, or otherwise verify the `shop-domain` header against an out-of-band authenticated value (e.g., cross-check against the shop recorded for the resolved webhook subscription) before trusting `request.shop` in `Registry.process`.

### Proof of Concept
1. Install the app on shop A and capture a genuine webhook delivery: body `B`, `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's `api_secret_key`), and header `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
2. Resend the same request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but replacing `X-Shopify-Shop-Domain` with `shop-b.myshopify.com`.
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because it only checks `B` against `H`.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` invokes the handler with `shop: "shop-b.myshopify.com"` and body `B`, causing shop A's webhook payload to be processed as if it belonged to shop B.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end
