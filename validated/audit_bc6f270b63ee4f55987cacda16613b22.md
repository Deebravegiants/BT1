Based on my research, I found a concrete analog in the `pallet-hyper-fungible-token` decimal-conversion logic that mirrors the reported bug class: unvalidated arithmetic that can silently produce a wildly inflated cross-chain transfer amount, allowing unbacked minting on the destination chain from a single user-submitted extrinsic.

### Title
Decimal-scaling underflow in `convert_to_erc20()` lets `send()` dispatch an inflated mint amount, enabling unbacked minting on the destination `HyperFungibleToken` - (File: modules/pallets/hyper-fungible-token/src/impls.rs)

### Summary
`pallet-hyper-fungible-token::send()` converts the locally-escrowed/burned amount into the ERC20-precision amount encoded in the outbound ISMP `POST` message via `convert_to_erc20()`. That helper only ever *multiplies* by `10^(erc_decimals - local_decimals)`, using `saturating_sub` to compute the exponent. When the destination ERC20's registered decimals are *fewer* than the local asset's decimals, `saturating_sub` clamps the exponent to `0` instead of the (impossible, negative) true difference, so the function silently skips the required *division*, and returns the raw, unscaled local-precision value as the ERC20 amount to mint on the destination chain — a value many orders of magnitude too large.

### Finding Description
`convert_to_erc20` is defined as: [1](#0-0) 

It is invoked in `send()` to build the cross-chain `Message.amount` field that the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract will mint or unlock: [2](#0-1) 

`erc_decimals` comes from the `Precisions` storage map (decimals of the destination ERC20 contract) and `decimals` is the local asset's decimals (native currency decimals or the `fungibles::Inspect` decimals for the asset). The correct conversion requires:
- multiplying by `10^(erc_decimals - local_decimals)` when `erc_decimals > local_decimals`, or
- dividing by `10^(local_decimals - erc_decimals)` when `local_decimals > erc_decimals`.

The implementation only ever multiplies, and uses `saturating_sub(local_decimals)` on `erc_decimals`; whenever `local_decimals > erc_decimals`, the subtraction saturates to `0`, so the multiplier becomes `10^0 = 1` and the function returns the local-precision value completely unscaled — instead of the correctly *divided-down* value. The corresponding inbound direction, `convert_to_balance`, does perform the down-scaling division correctly (`value / 10^(erc_decimals - local_decimals)`) for the opposite decimal ordering, confirming the outbound path is asymmetric/incomplete rather than intentionally one-directional: [3](#0-2) 

Nothing in `send()` validates that `erc_decimals >= decimals` before calling `convert_to_erc20`, so any token pair configured (via `register_token`/`Precisions`) with the destination ERC20 using fewer decimals than the local asset (a realistic configuration — e.g. an 18-decimal Substrate asset bridged to a 6-decimal ERC20 like USDC) will trigger this. Every ordinary user calling `send()` with such an asset produces a message whose `amount` is inflated by `10^(local_decimals - erc_decimals)`.

### Impact Explanation
The destination-chain `HyperFungibleToken.onAccept()` trusts `message.amount` from the verified POST request and mints it directly: [4](#0-3) 

Because the amount was computed by the buggy `convert_to_erc20` before dispatch, the destination chain mints an amount that can be orders of magnitude larger than what was actually escrowed/burned on the source chain, resulting in unbacked minting of the bridged asset and depegging/insolvency of the token pair, directly matching the reported bug class of unvalidated arithmetic producing over-transfer of funds.

### Likelihood Explanation
Reachable by any unprivileged user via a single signed extrinsic call to `send()` — no special privileges are required. The only precondition is that a token pair is registered (by governance/owner via `register_token`) where the destination ERC20's decimals are fewer than the local asset's decimals, which is a realistic and plausible configuration (bridging a high-decimal Substrate asset to a low-decimal stablecoin-style ERC20).

### Recommendation
Fix `convert_to_erc20` to handle both directions explicitly instead of relying on `saturating_sub`, e.g.:
```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
Add symmetric tests/assertions covering `local_decimals > erc_decimals` and `local_decimals < erc_decimals`, and consider validating decimal consistency at `register_token` time so misconfiguration is rejected rather than silently mis-scaling amounts at transfer time.

### Proof of Concept
1. Governance registers a token pair where the local asset has 18 decimals and the destination `HyperFungibleToken`'s registered `Precisions` value (`erc_decimals`) is 6 (e.g., mirroring a USDC-like ERC20).
2. A user calls `send()` with `amount = 1_000_000_000_000_000_000` (1 token, 18 decimals), which is burned/escrowed locally for 1 whole token.
3. `convert_to_erc20(1e18, erc_decimals=6, local_decimals=18)` computes `erc_decimals.saturating_sub(local_decimals) = 0`, so it returns `1e18 * 10^0 = 1e18` instead of the correct `1e18 / 10^12 = 1e6` (1 token in 6-decimal units).
4. The POST message with `amount = 1e18` is delivered to the destination `HyperFungibleToken`, which mints `1e18` units (interpreted in its own 18-decimal ERC20 representation) — 10^12 times more than the single token that was actually escrowed, resulting in massive unbacked minting.
