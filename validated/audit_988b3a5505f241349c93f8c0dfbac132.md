Found the vulnerability: in `Webhooks::Request`, the `shop` and `topic` fields used by `Registry.process` are read directly from HTTP headers and are **not included in the HMAC-signed payload**, breaking the binding `hmac-covered-bytes == data-acted-on`.

### Title
Webhook shop/topic identity spoofing via unauthenticated headers not covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates the HMAC of the body only, then dispatches the handler using the attacker-controllable `request.topic` and passes `request.shop` straight into `WebhookMetadata` given to the app's handler [3](#0-2) .

### Finding Description
The equality that should hold is: `bytes verified by HMAC == bytes acted upon (shop, topic)`. Here, the HMAC (`hmac-sha256` header) is computed over `@raw_body` only [4](#0-3) . The `shop-domain` and `topic` headers used for routing/identity are never part of the signed string, so `Utils::HmacValidator.validate(request)` returning true says nothing about the authenticity of those headers [5](#0-4) [3](#0-2) . An unprivileged internet user who can send an arbitrary HTTP request to the app's webhook endpoint containing a body from a *legitimate, previously-observed webhook for their own shop* (a valid HMAC/body pair they legitimately received) can replay it while altering the `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` headers, since neither is checked against the signed content.

### Impact Explanation
This lets a merchant/attacker who owns one shop craft a webhook delivery that `Registry.process` will accept as HMAC-valid, but with the `shop` field set to another tenant's domain and the `topic` set to a different, potentially more sensitive, registered handler than the one the body was signed for. Because `WebhookMetadata.shop` is exactly what downstream apps use to key their tenant data (per the shape of `WebhookMetadata.new(topic:, shop:, body:, ...)`), this is a cross-tenant identity confusion vector — the handler will process data or trigger side effects (e.g. `shop/redact`, `customers/data_request`) attributed to a shop the attacker doesn't control. This matches "cross-tenant access" (Critical) since the header/body identity binding required by the gem's own signature scheme is not enforced by the gem.

### Likelihood Explanation
Requires that the attacker already possesses at least one legitimately-HMAC'd webhook body/signature pair (trivially obtainable — any shop owner receives valid webhooks for their own shop) and that the receiving app relies solely on `Registry.process`/`HmacValidator.validate` (as documented) rather than independently re-validating `shop`/`topic` against out-of-band knowledge. This is a realistic misuse of the gem's own documented verification API, not a host-app oversight, since the gem's `to_signable_string` implementation is what omits `shop`/`topic` from the signed bytes.

### Recommendation
Include `shop-domain`, `topic`, and `webhook-id` in the HMAC-signable string (or otherwise cryptographically bind them to the body), so that the identity of the shop/topic is guaranteed by the same signature that authenticates the payload.

### Proof of Concept
1. Attacker's own shop (`attacker.myshopify.com`) receives a legitimate webhook: body `B`, headers `X-Shopify-Hmac-Sha256: H(B)`, `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends the same `B` and `H(B)` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com` and/or `X-Shopify-Topic: customers/data_request`.
3. `Request#initialize` accepts the headers [6](#0-5) ; `HmacValidator.validate` succeeds because it only checks `@raw_body` against `H(B)` [7](#0-6) .
4. `Registry.process` dispatches to the handler registered for `victim`/`customers/data_request` with attacker-controlled body content, having never verified that `shop` or `topic` were actually part of what Shopify signed [3](#0-2) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
