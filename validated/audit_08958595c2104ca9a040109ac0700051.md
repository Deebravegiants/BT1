### Title
Double-application of a frame's storage `Diff` to `ContractInfo` via non-consuming `apply_pending_changes_to_contract` followed by `absorb`/`finalize_own_contributions` causes over-refund of storage deposit - (File: substrate/frame/revive/src/metering/storage.rs)

### Summary
`RawMeter::apply_pending_changes_to_contract` mutates a shared `ContractInfo` using the frame's pending `Diff` so that a nested child call can see up-to-date `storage_bytes`/`storage_items`, but it deliberately does **not** reset `own_contribution` afterward [1](#0-0) . When that same parent frame is later absorbed into its caller (`RawMeter::absorb`) or finalized (`finalize_own_contributions`), the *same* `Diff` is applied to `info` a second time through `Contribution::update_contract`, because `own_contribution` still holds the full, un-consumed diff [2](#0-1) [3](#0-2) . This produces a double-subtraction of `bytes_removed`/`items_removed` from `info.storage_bytes`/`info.storage_items` and a double-refund pro-rated against an artificially shrunk denominator in `Diff::update_contract`.

### Finding Description
`Diff::update_contract` computes refunds pro-rata: `ratio = bytes_removed / info.storage_bytes` (capped at 1), multiplied by `info.storage_byte_deposit`, and then mutates `info.storage_bytes`/`storage_byte_deposit` in place [4](#0-3) . This function is designed to be called exactly once per `Diff` — one "finalization" of the frame's changes into the canonical `ContractInfo`.

The codebase provides two distinct helper methods on a nested meter for pushing pending changes into `info`:
- `bank_pending_changes` — applies the diff, records the resulting deposit as a `Charge`, and **resets** `own_contribution` back to `Contribution::Alive(Default::default())`, explicitly to prevent `finalize` from re-applying it [5](#0-4) .
- `apply_pending_changes_to_contract` — applies the diff to `info` purely so a *child frame about to be spawned* can see updated `storage_bytes`/`storage_items`/deposit fields, but explicitly discards the return value and does **not** reset `own_contribution`, per its own doc comment ("this does not consume the pending diff, allowing the meter to continue tracking changes after the nested call returns") [6](#0-5) .

The exploitable sequence is:
1. Frame A (a contract) performs storage writes/removals, accumulating `own_contribution = Contribution::Alive(diff_A)` via `RawMeter::charge` [7](#0-6) .
2. Before spawning a nested sub-call against the *same* `ContractInfo` (e.g., a self-recursive contract call, or two frames operating on the same contract's storage in sequence), the runtime calls `A.apply_pending_changes_to_contract(&mut info)`. This mutates `info.storage_bytes`, `info.storage_items`, `info.storage_byte_deposit`, `info.storage_item_deposit` according to `diff_A` — but `A.own_contribution` still equals `Contribution::Alive(diff_A)` (unchanged, unconsumed).
3. The child frame B executes against the now-updated `info`, correctly computing its own pro-rata refunds relative to the state left by step 2.
4. B returns and is absorbed into A via `A.absorb(B, contract, Some(&mut info))`, which correctly applies `diff_B` once.
5. Frame A itself eventually returns to *its* caller (root or an ancestor). At that point the caller does `caller.absorb(A, contract, Some(&mut info))`, which calls `A.own_contribution.update_contract(Some(&mut info))` — i.e., `diff_A.update_contract(info)` — **a second time**, because `own_contribution` was never reset in step 2.

The second `update_contract::<T>` call re-subtracts `bytes_removed`/`items_removed` from an `info.storage_bytes` value that has already been decremented by the same removal, and re-computes a refund ratio against this already-shrunk denominator, then refunds `Deposit::Refund` again for storage that was already refunded once. Because `Deposit::Charge`/`Deposit::Refund` amounts feed directly into `Ext::charge` → `Pallet::refund_deposit`/`charge_deposit` at `execute_postponed_deposits` [8](#0-7) [9](#0-8) , the caller/contract can be refunded more `HoldReason::StorageDepositReserve` balance than it ever actually held for that byte/item removal — violating the invariant that refunds are bounded by the deposit actually reserved.

There is no guard in `absorb`, `finalize_own_contributions`, or `Contribution::update_contract` that detects "this diff was already partially applied to `info`" — the `Contribution::Alive` vs `Contribution::Checked` state machine is the only consumption tracking mechanism, and `apply_pending_changes_to_contract` intentionally bypasses it without providing an equivalent safeguard for the *later* real finalization.

I was not able to fully verify, within the available tool budget, the exact call sites and sequencing in `substrate/frame/revive/src/exec.rs` that invoke `apply_pending_changes_to_contract` versus `bank_pending_changes` for a given frame — specifically whether the production execution path guarantees that any frame which calls `apply_pending_changes_to_contract` is *always* subsequently routed through `bank_pending_changes` (which resets `own_contribution`) rather than through the plain `absorb`/`finalize_own_contributions` path (which would double-apply). This distinction determines whether the double-application is actually reachable in the shipped contract-call dispatch flow or is prevented by call-site discipline in `exec.rs`. This is a limitation of the available index/context, not evidence that the issue is safe.

### Impact Explanation
If reachable, this allows an attacker-controlled contract (via ordinary, unprivileged `pallet_revive` call extrinsics that trigger recursive/self-referential contract calls touching the same `ContractInfo`) to cause the storage-deposit accounting to refund more `StorageDepositReserve`-held balance than was ever charged for a given storage removal, effectively minting spendable balance out of the deposit-hold mechanism. This directly violates the "user-controlled assets must remain fully backed" and "storage logic must not be bypassable by normal users" invariants.

### Likelihood Explanation
Preconditions require only: (a) a contract able to make a nested/self-referential call against the same contract's storage (an ordinary attacker-authored contract feature, not requiring any privileged origin), and (b) the runtime code path that spawns that nested frame calling `apply_pending_changes_to_contract` rather than `bank_pending_changes` before absorbing/finalizing the parent frame. Given the explicit doc comments distinguishing "consuming" vs. "non-consuming" application, and that `apply_pending_changes_to_contract` is a recently-introduced helper (per its docstring intent) alongside `bank_pending_changes`, the double-count is a plausible unit-testable bug, but confirming exploitability end-to-end requires inspecting the exact call sequence in `exec.rs`, which I could not complete in this session.

### Recommendation
- Ensure `apply_pending_changes_to_contract` is only ever used in a context where the same frame is guaranteed to be finalized afterward via `bank_pending_changes` (which resets `own_contribution`), never via plain `absorb`/`finalize_own_contributions` on the un-reset diff.
- Alternatively, have `apply_pending_changes_to_contract` track an "already partially applied" delta and have `Diff::update_contract`/`absorb` subtract only the incremental (unapplied) part of the diff when finalizing, rather than relying purely on call-site discipline.
- Add a debug assertion (mirroring the one in `bank_pending_changes`) in `absorb`/`finalize_own_contributions` that detects if `info` was already touched by this frame's diff, to fail fast in tests if the invariant is violated.

### Proof of Concept
Rust unit test in `substrate/frame/revive/src/metering/storage/tests.rs` style:
1. Construct a root meter and a `ContractInfo` with known `storage_bytes`, `storage_items`, `storage_byte_deposit`, `storage_item_deposit`.
2. Create nested frame A, call `A.charge(&diff_removing_bytes)`.
3. Call `A.apply_pending_changes_to_contract(&mut info)` (simulating spawning a child frame against the same contract).
4. Create nested frame B (child), perform some unrelated `B.charge`, then `root.absorb(B, &contract, Some(&mut info))`.
5. Finally call `root.absorb(A, &contract, Some(&mut info))` (simulating A returning to root without having gone through `bank_pending_changes`).
6. Assert: total refund amount recorded across steps 3 and 5 combined does **not** exceed `info`'s original `storage_byte_deposit`/`storage_item_deposit` (i.e., `info.storage_byte_deposit` and `info.storage_item_deposit` never go negative/saturate incorrectly, and the sum of all `Deposit::Refund` amounts charged via `E::charge` is `<=` the amount originally charged for those bytes/items).
7. Expected (bug) result: the same `bytes_removed` is refunded twice — once in step 3's mutation of `info` and once in step 5's `update_contract` call on the still-`Alive` `diff_A` — causing `info.storage_byte_deposit` to be over-reduced (potentially saturating to zero while more `Deposit::Refund` value was paid out than the original `storage_byte_deposit`), violating the assertion.

	/// Apply pending storage changes to a ContractInfo without finalizing the meter.
	///
	/// This is used before creating a nested frame to ensure the child frame can see
	/// the parent's pending storage changes when calculating refunds.
	///
	/// Unlike [`Self::finalize_own_contributions`], this does not consume the pending diff,
	/// allowing the meter to continue tracking changes after the nested call returns.
	pub fn apply_pending_changes_to_contract(&self, info: &mut ContractInfo<T>) {
		if let Contribution::Alive(diff) = &self.own_contribution {
			// Apply the diff to update the ContractInfo's storage deposit fields.
			// We don't care about the return value (the deposit amount) here,
			// we just want to update the ContractInfo so child frames can see it.
			let _ = diff.update_contract::<T>(Some(info));
		}
	}

	/// Apply the pending diff to `info` and push its deposit as a final charge, then reset
	/// `own_contribution` so finalize does not apply it a second time.
	pub fn bank_pending_changes(&mut self, contract: T::AccountId, info: &mut ContractInfo<T>) {
		if let Contribution::Alive(_) = &self.own_contribution {
			let deposit = self.own_contribution.update_contract(Some(info));
			self.own_contribution = Contribution::Alive(Default::default());
			if !deposit.is_zero() {
				self.charge_deposit(contract, deposit);
			}

				false,
				"on-stack ancestor frames have not finalized yet, so own_contribution \
				 should be Alive when banked; qed",

		}
	}
