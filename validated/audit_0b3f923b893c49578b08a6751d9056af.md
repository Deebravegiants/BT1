## Title
Webhook HMAC only signs the request body, not the shop/topic identity headers, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` binds its HMAC to the raw request body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers and are never part of the signed payload. `Registry.process` trusts these header-derived fields to route to a handler and to build `WebhookMetadata`, which is the value host applications use to identify which merchant/topic a webhook belongs to. This breaks the intended binding: `HMAC covers body` ≠ `identity fields (shop, topic) acted on by the handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from headers with no cryptographic tie to the signature: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — i.e. it only authenticates the body bytes: [3](#0-2) 

`Registry.process` then uses the unauthenticated `request.topic` and `request.shop` to select the handler and construct the `WebhookMetadata` that is delivered to the app's business logic: [4](#0-3) 

The `Context.api_secret_key` used to compute/verify the HMAC is the app's single shared secret — it is not per-shop. Any merchant who installs the app is a legitimate holder of `body,hmac` pairs for their own shop's genuine webhook deliveries (they can simply trigger an event, e.g. create an order, and observe the delivery Shopify sends to the app's registered endpoint). Because the signature covers only the body, that same `(raw_body, hmac)` pair remains valid when replayed with arbitrary `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, and `shopify-api-version` headers substituted in. `Registry.process` will accept it (`Utils::HmacValidator.validate` passes) and deliver a `WebhookMetadata` claiming to be from a different shop/topic than the one that actually produced the payload.

Equality broken: `authenticated(raw_body)` == `acted_on(shop, topic, webhook_id, api_version)` is assumed by `Registry.process`, but only `raw_body` is actually covered by the HMAC.

### Impact Explanation
This is a cross-tenant identity-spoofing primitive reachable by any unprivileged merchant with no special access: they can cause the host application to process attacker-controlled webhook bodies under an arbitrary `shop` value (any other installed shop domain) and arbitrary `topic`. Depending on how the host app uses `WebhookMetadata#shop`/`#topic` (e.g., to look up/update per-shop records, deauthorize a shop via `shop/redact`, or trigger data deletion/side effects keyed by `shop`), this allows one tenant to inject or corrupt data attributed to another tenant — a cross-tenant access violation.

### Likelihood Explanation
Likelihood is high for any app that registers more than a trivial handler set and multiple shops install it: the attacker only needs their own (unprivileged) installation to obtain one legitimately-signed `(body, hmac)` pair for a topic they control, then can freely alter the four identity headers to target any other shop domain, since none of them factor into the signature check.

### Recommendation
Include the identity-binding fields (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the HMAC-signed content, e.g. build a canonical signable string that concatenates the header values with the raw body before computing/verifying the signature, rather than signing `@raw_body` alone. Alternatively, if per-shop verification is not feasible, at minimum document that the `shop` header is unauthenticated and require host apps to independently confirm the sender shop out-of-band (e.g., via a known set of installed shops) before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers a webhook subscription, e.g. `orders/create`.
2. Attacker creates an order in their own store; Shopify delivers a webhook to the app with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, and a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's shared `api_secret_key`.
3. Attacker captures this `(raw_body, hmac)` pair (it is delivered to their own endpoint/observable via their own webhook logs or a proxy they control on their own traffic — no interception of anyone else's traffic required).
4. Attacker replays the exact same body and HMAC to the app's webhook endpoint but swaps `x-shopify-shop-domain` to `victim-shop.myshopify.com` and/or `x-shopify-topic` to another registered topic.
5. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (only checks for presence, not authenticity): [5](#0-4) ; `Utils::HmacValidator.validate` succeeds because it only checks the body signature: [6](#0-5) ; `Registry.process` dispatches to the handler with `shop: "victim-shop.myshopify.com"`: [7](#0-6) .
6. The host app's handler now believes this event originated from `victim-shop.myshopify.com`, even though it was fabricated by the unrelated attacker-controlled shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
