### Title
Direct token donations to the liquidity pool are permanently unrecoverable - (File: contracts/pool/src/lib.rs)

### Summary
An unprivileged user can transfer any token directly to a pool contract address, but the pool has no unprivileged or owner-mediated path that can return an arbitrary surplus token balance. Donated tokens are deliberately excluded from the market’s `cash` accounting, so they cannot be withdrawn through ordinary pool liquidity or claimed as revenue.

### Finding Description
The pool treats `cash` as an accounting book separate from the token contract balance, and direct donations do not increase that book. [1](#0-0)  Every pool mutator is restricted to the pool owner, normally the controller. [2](#0-1)  The outbound transfer helper can only be reached through specific market operations and only for amounts those operations calculate; it is not a general rescue function. [3](#0-2)  `claim_revenue` also cannot recover a donation because it burns claimable revenue shares, debits only booked cash, and transfers only that calculated amount to the owner. [4](#0-3) 

### Impact Explanation
Tokens sent directly to a pool become an unbooked excess physical balance. Because every withdrawal, borrow, refund, and revenue claim is bounded by market accounting rather than by `token.balance(pool)`, the donor has no reachable path to recover the funds. The result is permanent freezing of the accidentally transferred user funds absent a privileged contract upgrade.

### Likelihood Explanation
The trigger is a single mistaken direct token transfer to the pool address, reachable by any token holder without protocol privileges. This requires user error rather than an attacker-controlled exploit, but the pool accepts the transfer and provides no recovery path.

### Recommendation
Add an owner-authorized rescue entrypoint that transfers only `token.balance(pool) - aggregate_booked_cash` for a listed asset, or a more general arbitrary-token recovery path that cannot withdraw balances reserved for suppliers, debtors, revenue, or in-flight operations.

### Proof of Concept
1. Let `POOL` be the deployed `LiquidityPool` address and `TOKEN` be any Stellar asset contract.
2. An unprivileged sender executes `TOKEN.transfer(sender, POOL, amount)`.
3. The token balance of `POOL` increases by `amount`, while every affected market’s `cash`, supply shares, debt shares, and revenue shares remain unchanged. The repository’s money-flow test explicitly demonstrates this state as `token.balance(pool) == cash_market_1 + cash_market_2 + donation`. [5](#0-4) 
4. Calls to `withdraw`, `borrow`, or `claim_revenue` can only spend amounts recorded in `cash` or claimable revenue; therefore none can spend the donated surplus. [6](#0-5) [7](#0-6) 
5. There is no `sweep`, `rescue`, `recover`, or equivalent arbitrary-token withdrawal entrypoint on `LiquidityPool`, so the donation remains locked in the contract.
