## Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw body only, but the `shop` (tenant) identity that downstream code trusts to attribute the webhook is read from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header. Because the signature never binds `shop` to `body`, any actor who can obtain one valid `(body, hmac)` pair for a webhook (e.g., by installing the app on their own store and receiving a legitimate webhook there) can replay that exact body/HMAC pair while substituting a different shop domain in the header, and `Registry.process` will accept it and hand the forged tenant identity to the app's webhook handler.

## Finding Description
`Request#hmac` returns the header-provided signature and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of `to_signable_string`: [3](#0-2) 

`HmacValidator.validate` verifies exactly and only the signable string (the body) against the HMAC secret: [4](#0-3) 

`Registry.process` validates the HMAC and then trusts `request.shop` (the unauthenticated header) to build the `WebhookMetadata` handed to the app's business logic: [5](#0-4) 

This is precisely the identity-binding break called out in the prompt rules: a field ("shop") acted on by the application but not covered by the HMAC. The equality that should hold — `hmac == HMAC(secret, body ∥ shop)` — is instead only `hmac == HMAC(secret, body)`, so `shop` is free-floating relative to the signature.

## Impact Explanation
Any unprivileged internet user can install the app on a store they control (this is a normal, unprivileged action — every Shopify app allows installation by any shop owner) and thereby receive a legitimate webhook delivery: a valid `(raw_body, hmac)` pair signed with the victim app's real `api_secret_key`. The attacker can then replay that exact `raw_body`/`hmac` pair directly to the app's webhook endpoint while setting the `shopify-shop-domain` header to an arbitrary victim shop domain. `HmacValidator.validate` will still pass (it only checks the body), and `Registry.process` will dispatch a `WebhookMetadata` object carrying the attacker-chosen `shop` value with body content the attacker fully controls (within the constraints of a valid webhook payload shape for some topic they can trigger, e.g. by manipulating their own store data). Any host application that uses `data.shop` to key its per-tenant storage (the intended and documented usage pattern) will write or act on attacker-controlled data under a victim tenant's identity — this is a cross-tenant data injection / cross-tenant access primitive, satisfying the Critical severity bar in the rules ("cross-tenant access").

## Likelihood Explanation
Likelihood is high for any app that processes webhook data keyed by `shop`: the attacker only needs their own (unprivileged) install of the target app to harvest one valid signed body, no access to `api_secret_key`, access tokens, or any privileged credential is required, and the webhook endpoint is a public, unauthenticated HTTP endpoint by design.

## Recommendation
Bind the trusted identity to the signed payload instead of trusting an unauthenticated header:
- Include the shop domain (and/or topic/webhook-id) as part of the signable string used for HMAC verification, or
- Cross-check the `shop` header against the shop actually resolvable from the signed payload/topic before constructing `WebhookMetadata`, or
- At minimum, document/require host apps to independently verify that the sending shop for a topic matches a shop known to have an active installation/session before trusting `data.shop`, and consider exposing an API that returns a verified shop only when it can be tied to the signed bytes.

## Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (unprivileged, normal signup).
2. Attacker triggers a webhook delivery for a topic they control content of (e.g., by editing a product/order on their own store) and captures the raw POST body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC_SHA256(api_secret_key, B)`.
3. Attacker sends a new POST request to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses these headers/body: [6](#0-5) 
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — true, since `B` and `H` are unmodified: [7](#0-6) 
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-supplied body content, despite the signature never having authenticated that shop value.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
