### Title
`Wallet#updateSeed` allows unlocked-state bypass and injection of forged seed metadata entries without existence or lock checks - ([File: features/wallet/module/wallet.js])

### Summary
`updateSeed({seedId, label})` is exposed via `walletApi.wallet.updateSeed` and directly calls `#seedMetadataAtom.set()` without first calling `#assertWalletIsUnlocked()` (unlike every other mutating method: `addSeed`, `removeManySeeds`) and without verifying that `seedId` corresponds to a real, keychain-registered seed. An attacker with access to the wallet API surface can call `updateSeed` while the wallet is locked and with an arbitrary/forged `seedId`, injecting a phantom metadata entry into persisted `seedMetadataAtom` state.

### Finding Description
`updateSeed` in `features/wallet/module/wallet.js` is implemented as: [1](#0-0) 

Comparing to sibling mutating methods `addSeed` and `removeManySeeds`, both begin with `await this.#assertWalletIsUnlocked()`: [2](#0-1) [3](#0-2) 

`updateSeed` has no such guard, and `previous[seedId]` is spread without checking that `seedId` exists in `previous` or corresponds to a real seed tracked in `#primarySeedIdAtom` / `#getExtraSeeds()`/keychain. This method is exposed unauthenticated-within-app via `walletApi.wallet.updateSeed`, mapping 1:1 to the internal `wallet.updateSeed`: [4](#0-3) 

Since `#seedMetadataAtom` is a `public: true` `isSoleWriter` storage atom, this write path is the intended external interface for consumers of the wallet API, meaning any caller reaching `wallet.updateSeed` (e.g., a dapp/UI/RPC-bound feature that forwards user-controlled `seedId`/`label`) can inject or corrupt metadata regardless of lock state and regardless of whether `seedId` is real.

### Impact Explanation
This breaks the "locked means locked" invariant: while `wallet.isLocked() === true`, calling `updateSeed` still mutates persisted `seedMetadataAtom` state, and the injected entry is visible via `getSeedMetadata()`. While this does not directly expose keys/mnemonics or enable signing, it does inject phantom seed metadata entries not backed by any real keychain seed, and does so without requiring the unlock precondition every other similar mutator enforces — a state-integrity/cross-wallet-state-confusion issue exploitable purely through normal API usage.

### Likelihood Explanation
No special privileges are required beyond calling the existing `wallet.updateSeed` API, which is already reachable through `walletApi.wallet.updateSeed`. There's no lock check and no seedId existence validation, so the exploit is deterministic and repeatable on every call.

### Recommendation
Add `await this.#assertWalletIsUnlocked()` at the start of `updateSeed`, and validate `seedId` exists in `previous` (or corresponds to the primary seed / a real extra seed) before spreading/writing, throwing otherwise (mirroring the existing pattern used by `removeManySeeds` for primary-seed and extra-seed validation).

### Proof of Concept
```js
it('does not allow updating seed metadata while locked or for non-existent seedId', async () => {
  await wallet.create()
  // wallet is locked by default after create()
  await expect(wallet.updateSeed({ seedId: 'forged-seed-id', label: 'x' })).rejects.toThrow('locked')

  await wallet.unlock()
  await expect(wallet.updateSeed({ seedId: 'forged-seed-id', label: 'x' })).rejects.toThrow(/does not exist|not found/)

  const metadata = await seedMetadataAtom.get()
  expect(metadata).not.toHaveProperty('forged-seed-id')
})
```
Expected today: both assertions fail — `updateSeed` succeeds silently and `seedMetadataAtom` contains a `forged-seed-id` entry, confirming the bug.
