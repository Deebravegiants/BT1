### Title
Interactions-before-effects (CEI violation) in escrow withdrawal allows reentrancy from attacker-controlled token contracts before escrow accounting is finalized - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The dForce incident stemmed from performing an external native-token transfer/callback *before* internal accounting (LP burn) was finalized, letting the attacker re-enter and manipulate state while stale balances were still visible. The Tron fork of Hyperbridge's `IntentGatewayV2` contains the same anti-pattern in its escrow-release function `withdraw()`: it sends value/executes an external call to an attacker-supplied address *before* decrementing the `_orders` escrow-accounting mapping, whereas the equivalent, already-fixed logic in the primary EVM contract does the opposite (effects before interactions).

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `withdraw()` releases escrowed order inputs to a beneficiary: [1](#0-0) 

For each token in `body.tokens` it only checks `_orders[body.commitment][token] == 0` (existence, not a sufficiency check), then performs the external transfer — a raw `.call{value: amount}("")` for native tokens or a raw low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` for ERC-20s — and only *after* that call returns does it decrement `_orders[body.commitment][token] -= amount`. Because `order.inputs[i].token` is fully attacker-controlled at `placeOrder` time, an attacker can supply a malicious "token" contract as one of the escrowed inputs; that contract's fake `transfer()` implementation executes arbitrary code during the escrow release, while `_orders[body.commitment][...]` for other, not-yet-processed tokens in the same withdrawal request is still at its pre-release (stale) value.

This function is reachable by an unprivileged caller through `cancelOrder()`'s same-chain path — the order owner can cancel immediately (no deadline/expiry check on this branch) and trigger `withdraw(body, true)`: [2](#0-1) 

This is a direct structural regression relative to the fixed pattern already present elsewhere in the codebase, where `_orders[...]` is decremented *before* the external transfer: [3](#0-2) 

and where the project's own reentrancy regression tests explicitly document that fills must set `_filled` *before* any external call to prevent this exact class of bug: [4](#0-3) 

Additionally, the ERC-20 branch uses a raw `.call` and only inspects the boolean `success` flag, not the ABI-decoded return value, so a token that returns `false` without reverting is treated as a successful transfer and the escrow is still decremented — silently losing funds without ever delivering them.

### Impact Explanation
An attacker who places an order using a malicious "token" as one of the escrowed inputs gains code execution inside the gateway's own withdrawal loop while per-token escrow bookkeping for the remainder of `body.tokens` is still stale. This breaks the checks-effects-interactions invariant relied upon throughout the rest of the intents system and is a High-severity finding: it is the same bug class (state-mutating external call executed before internal accounting is settled) that enabled the dForce loss, applied to Hyperbridge's escrow-release path. Even though `_filled[commitment]` is set at the top of `withdraw()` and blocks the most direct re-entry back into `cancelOrder()` for the same commitment, the window still allows arbitrary attacker code execution against a contract whose own escrow ledger has not yet been finalized, and the unchecked low-level `.call` return-value handling can silently break accounting consistency on non-conforming tokens.

### Likelihood Explanation
Reachable directly and unprivileged from `cancelOrder()`, which the order's own creator can call for a same-chain order without any timing restriction. The only external inputs required are attacker-controlled order parameters (`order.inputs[i].token`) supplied when the attacker placed the order themselves.

### Recommendation
Refactor `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to follow the same checks-effects-interactions ordering already used in `IntentsBase.sol::_withdraw`: decrement `_orders[body.commitment][token]` before performing any native or ERC-20 transfer, and replace the raw low-level `.call` for ERC-20 transfers with `SafeERC20.safeTransfer`, which reverts on failure and validates return data correctly.

### Proof of Concept
1. Attacker calls `placeOrder` with `order.inputs = [{token: MaliciousToken, amount: X}, {token: address(0), amount: Y}]`, `order.user = attacker`, depositing `X` of `MaliciousToken` and `Y` native ETH into escrow.
2. Attacker immediately calls `cancelOrder(order, options)` on the same chain (no deadline check on this branch), which calls `withdraw(body, true)`.
3. `withdraw()` sets `_filled[commitment] = attacker`, then iterates `body.tokens`: for `MaliciousToken`, it issues `MaliciousToken.call(transfer.selector, attacker, X)` **before** decrementing `_orders[commitment][MaliciousToken]`.
4. `MaliciousToken`'s fake `transfer()` executes attacker logic while `_orders[commitment][address(0)]` (the native ETH leg) is still at its full pre-release value, demonstrating the CEI violation and the reentrancy window against a contract whose own accounting has not settled — the exact bug class flagged in the SlowMist dForce report.         address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

                ++i;
            }
        }
