### Title
Webhook Shop-Domain Spoofing via HMAC Scope Gap (Cross-Tenant Webhook Injection) - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw HTTP body only, while the shop-identifying field consumed by webhook handlers is read from an unauthenticated header. This breaks the identity binding `hmac(signed content) == hmac(content acted upon)` for the `shop` field, allowing an attacker who controls any legitimate Shopify store to replay one of their own genuine (validly-signed) webhook deliveries against the app's webhook endpoint while forging the `shop` value to point at a different, victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `Request#shop` is derived from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is not part of that signable content: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string`, i.e. the body — it never incorporates the shop-domain header: [4](#0-3) 

`Registry.process` checks only that HMAC, then forwards the unauthenticated `request.shop` straight into the app's handler: [5](#0-4) 

The equality that should hold is `hmac_covers(bytes) == bytes_acted_on`, i.e. every field that the app trusts for tenant routing (`shop`) should be covered by the HMAC. Here, `shop` is acted upon (passed to `WebhookMetadata` and thus to the consuming app's handler as the tenant identifier) but is not part of the signed bytes. `topic`, `webhook_id`, and `api_version` have the same gap, but `shop` is the most consequential since it is the tenant/identity boundary.

### Impact Explanation
Any actor who can obtain a single genuine, validly-signed webhook delivery for a shop they control (trivial — anyone can create a free Shopify development/partner store and subscribe to webhooks) can capture the `(raw_body, hmac)` pair and replay it to the target app's public webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. Because `HmacValidator.validate` only checks the body against the secret, the signature still validates, and `Registry.process` will dispatch the handler with `WebhookMetadata#shop` set to the forged victim shop domain. Any app handler that uses `data.shop` to key persistence, trigger tenant-scoped actions (e.g. `app/uninstalled` cleanup, `shop/redact`, billing state changes, cache invalidation) can be made to act against the wrong tenant using attacker-controlled data — a cross-tenant confusion/injection primitive, since the boundary the gem is expected to enforce (this webhook body + this shop, from Shopify) is not actually enforced.

### Likelihood Explanation
The prerequisite (owning a Shopify store capable of receiving one legitimate webhook of the target topic) is available to any unprivileged internet user for free, and does not require the app's `client_secret`, an access token, or any privileged account for the *victim* shop. The only engineering effort is capturing one legitimate webhook and replaying it with a modified header, which is straightforward given publicly known Shopify webhook header names.

### Recommendation
Include the shop-domain (and topic/webhook-id/api-version) header values in the HMAC-signable content, or otherwise cryptographically bind them to the request (e.g., verify the shop domain against the session/store the app expects for the given webhook subscription) before passing `request.shop` to handlers.

### Proof of Concept
```ruby
# 1. Attacker owns shop "attacker-shop.myshopify.com" and receives a legitimate
#    webhook (topic X) with body B and a valid Shopify HMAC H = HMAC-SHA256(secret, B).

raw_body = captured_body            # B, from attacker's own real webhook
valid_hmac_b64 = captured_hmac      # H, computed by Shopify over B

# 2. Attacker replays the same body+hmac to the app's endpoint,
#    but spoofs the shop-domain header to point at the victim shop.
forged_headers = {
  "x-shopify-topic"        => "app/uninstalled",   # same topic as captured
  "x-shopify-hmac-sha256"  => valid_hmac_b64,        # still valid, since HMAC only covers body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com",  # forged
  "x-shopify-webhook-id"   => "spoofed-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# 3. HMAC validation succeeds because it only checks raw_body against the secret.
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# 4. Registry.process dispatches the handler believing this event
#    originated from "victim-shop.myshopify.com".
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle receives WebhookMetadata with shop: "victim-shop.myshopify.com"
```

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
