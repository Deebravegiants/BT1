### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop` (tenant identity) is read from an unauthenticated header. `Registry.process` validates the HMAC and then dispatches to the host app's handler using that unverified `shop` value, breaking the binding `authenticated(payload) == identity(shop)`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` is derived straight from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, with no cryptographic tie to the signed body: [2](#0-1) 

`Webhooks::Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` (which calls `request.to_signable_string`, i.e. only the body) and then immediately hands the *unverified* `request.shop` to the host app's handler as the tenant identifier: [3](#0-2) 

`Utils::HmacValidator.validate_signature` confirms the comparison is solely against `verifiable_query.to_signable_string`, never incorporating headers such as the shop domain: [4](#0-3) 

Because the app's `api_secret_key` is shared across every shop that installs the app, any merchant who installs the app can trigger a legitimate webhook for their *own* shop, capture the raw body and its valid `x-shopify-hmac-sha256` value (both attacker-observable, since they own that shop and can read the webhook delivery), and then replay that exact body+HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. The HMAC check in `Registry.process` still succeeds (it only checks the body), and the handler receives `WebhookMetadata` claiming the event is for the victim shop: [5](#0-4) 

This is the exact bug class described in the report: a field that is acted upon (the shop identity used to route/attribute the webhook to a tenant) is not covered by the integrity check (HMAC), so the binding `verified-shop == acting-shop` is broken.

### Impact Explanation
An attacker who is merely a self-service app installer (i.e., not privileged, holds no access token, secret, or admin rights on the victim) can forge webhook deliveries that the host application will attribute to any other shop of their choosing. Depending on how the host app's webhook handler uses `WebhookMetadata#shop` (e.g., to look up/update per-tenant records, trigger tenant-scoped side effects, or write audit data), this enables cross-tenant data injection/confusion — the attacker controls the payload content but can direct it at an arbitrary victim tenant. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Requires the attacker to be an actual (even a free/trial) installer of the app on their own store — a low bar reachable by any unprivileged internet user via normal app installation — plus knowledge of a valid victim shop domain (public/discoverable via `*.myshopify.com`). No access token, `client_secret`, or privileged access is needed. The gem provides no mitigation (no per-shop secret, no binding of shop to signature), so exploitation is straightforward once the attacker can intercept/read their own genuine webhook deliveries and replay them with a modified header.

### Recommendation
Bind the trusted shop identity to the verified payload rather than trusting the header in isolation:
- Include the `shop-domain` header (and ideally `webhook-id`/`api-version`) in the HMAC-signable string, matching it against a value verified elsewhere (not achievable, since Shopify itself only signs the body — so instead:
- Cross-check `request.shop` against the caller's expected/registered shop for that webhook subscription (e.g., look up the shop associated with `webhook_id` via the Admin API, or require host apps to pass the expected shop and assert equality before dispatch), and document that host applications must not trust `WebhookMetadata#shop` as authenticated without such a check.
- At minimum, update documentation to explicitly warn that the `shop` field on `WebhookMetadata` is not covered by HMAC verification and must not be used as a sole tenant-selection key without an independent authorization check against the recipient's own webhook/shop mapping.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`, receiving genuine webhook deliveries (e.g., `orders/create`) signed by Shopify with the app's shared `api_secret_key`.
2. Attacker captures one such delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid, since `H = HMAC-SHA256(api_secret_key, B)`).
3. Attacker replays the exact same body `B` and header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` instead of their own domain.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation passes.
5. The registered handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled data as if it originated from the victim shop. [3](#0-2)
