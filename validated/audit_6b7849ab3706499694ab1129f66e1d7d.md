This is a strong finding: `exchange_token` in `token_exchange.rb` uses the JWT `dest` claim (via `jwt_payload.shop`) as the destination host that receives the app's `client_id`/`client_secret` in the token-exchange POST body, without ever passing it through `Utils::ShopValidator.sanitize!` — unlike the sibling method `migrate_to_expiring_token` in the same file, which does call `Utils::ShopValidator.sanitize!(shop)` before constructing the session/host [1](#0-0) . `JwtPayload#shop` only strips the `"https://"` prefix from the `dest` claim with no domain allow-listing [2](#0-1) , and `exchange_token` feeds that value directly into `Session.new(shop: dest_shop)` and then `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")`, which sends `client_id`/`client_secret` to `https://#{dest_shop}/admin/oauth/access_token` [3](#0-2) .

### Title
Token Exchange sends `client_secret` to an unvalidated host derived from the JWT `dest` claim - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the token-exchange request host from `JwtPayload#shop` (the `dest` claim of the session token) without validating that the resulting domain is a trusted Shopify domain via `Utils::ShopValidator`, unlike the parallel `migrate_to_expiring_token` method in the same module which does call `Utils::ShopValidator.sanitize!`.

### Finding Description
`JwtPayload#shop` simply does `@dest.gsub("https://", "")` with no allow-list check [2](#0-1) . `exchange_token` uses this raw value as `dest_shop` and constructs an unauthenticated `Session` (`Session.new(shop: dest_shop)`) that is then used purely as the request host by `Clients::HttpClient` [3](#0-2) . The POST body sent to that host includes `client_id` and `client_secret` in plaintext [4](#0-3) . The gem elsewhere enforces domain validation for exactly this class of host-derivation risk — `Utils::ShopValidator.sanitize!` restricts hosts to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) [5](#0-4) , and `migrate_to_expiring_token` (same file, same credential-sending pattern) calls it before building its session/host [6](#0-5) . `exchange_token` has no equivalent call.

The binding that should hold is: *host that receives `client_secret`* == *a trusted Shopify domain*. Instead the code enforces only: *host that receives `client_secret`* == *whatever string appears in the JWT `dest` claim (minus the `https://` prefix)*, which is verified for JWT-signature validity and `aud` match [7](#0-6)  but never checked to belong to a Shopify-controlled domain.

### Impact Explanation
Because the app's `client_id`/`client_secret` are POSTed to the exact string derived from the token's `dest` field, any value in `dest` — including a non-Shopify or attacker-influenced host — would receive the app's `client_secret` in the request body of an outbound HTTPS request from the host application's server, constituting SSRF-with-credentials / credential exfiltration if the `dest` claim can ever contain an untrusted value. This maps directly to the "host validated versus host that receives the `client_secret`" analog class called out in scope.

### Likelihood Explanation
The session token is JWT-signed and verified with `Context.api_secret_key`/`old_api_secret_key` and its `aud` claim is checked against `Context.api_key` [8](#0-7) [7](#0-6) , so under normal operation `dest` is Shopify-issued and trustworthy — normal App Bridge session tokens always set `dest` to a `*.myshopify.com`/`*.myshopify.io`/`spin.dev` host. I could not find a code path in this gem where an attacker without a validly-signed session token (i.e., without knowledge of `api_secret_key`) can control `dest`. Exploiting this therefore appears to require either a Shopify-side issuance anomaly or forging the token, both of which fall outside the in-scope threat model (which excludes findings that require possessing `api_secret_key`). I flag this as the closest structural analog to the report's "unchecked field trusted implicitly" pattern (missing defense-in-depth validation, inconsistent with the sibling method), but I cannot fully confirm an unprivileged-attacker-reachable path to control `dest` within the boundaries of this codebase alone.

### Recommendation
Add `dest_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)` in `exchange_token`, mirroring the validation already performed in `migrate_to_expiring_token`, so the token-exchange request (and the `client_secret` it carries) can only ever be sent to a domain in `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
Not confirmed as independently exploitable by an unprivileged internet user using only this gem's code: doing so would require producing a validly-HMAC/JWT-signed session token whose `dest` claim is a non-Shopify host, which requires `api_secret_key` — out of scope per the rules. The finding is reported as a missing-defense-in-depth inconsistency (`exchange_token` vs. `migrate_to_expiring_token`) rather than a demonstrated end-to-end exploit chain within this gem alone.
