### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant) identity that the host application uses to route and persist the webhook event is taken from an unauthenticated HTTP header. An unprivileged internet user who can obtain any one validly-signed webhook payload (e.g. a webhook delivered to their own shop on a multi-tenant app) can replay that exact body+HMAC pair while substituting the `shop-domain` header for a victim shop, and the gem will report the request as authentic for the victim tenant.

### Finding Description
`Request#to_signable_string` only returns `@raw_body`, and `Request#hmac` is read from the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header: [1](#0-0) 

`Request#shop` is read from a separate header (`shopify-shop-domain`/`x-shopify-shop-domain`) that is never included in `to_signable_string`: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` — i.e., against the body, never against the shop: [3](#0-2) 

`Registry.process` uses this same validated-but-shop-blind check, then hands `request.shop` straight to the handler as the trusted tenant identifier: [4](#0-3) 

The identity binding that should hold is:
`shop authenticated by HMAC` == `shop used as the tenant/session key (WebhookMetadata#shop)`

In this implementation that equality does not hold: the HMAC authenticates the *body*, not the *(body, shop)* pair. Any request whose body+HMAC pair is valid for *some* shop is accepted as valid for *whatever shop header* accompanies it. This is exactly the "shop authenticated versus the shop stored as a session key" identity-binding break called out in the analog rules, and it is the direct structural analog of the external report's root cause (a value that governs trust/behavior — here, tenant attribution — is not covered by the same validation that is supposed to secure the request).

### Impact Explanation
This is a cross-tenant data-injection/spoofing vector: an attacker who is a legitimate (even unprivileged) end user of the vulnerable, multi-tenant host application — e.g., a merchant that has installed the app and thus normally receives genuinely-signed webhooks for their own shop — can capture one such valid `(body, hmac)` pair and replay it against the app's webhook endpoint with the `shop-domain` header changed to any victim shop domain known to the app. Because `HmacValidator.validate` never binds the shop to the signature, `Registry.process` will pass HMAC validation and invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop, causing the host application to associate forged/attacker-controlled event data with another tenant's account. This crosses a tenant boundary using only the gem's own trust primitives (no `api_secret_key`, access token, or host-code misuse is required), matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) obtaining one legitimately-signed webhook body+HMAC (trivially available to any installed/using merchant of the target app, since webhook bodies for common topics — e.g. `app/uninstalled`, `shop/update` — are largely predictable/replayable in structure and merchants receive their own shop's real webhooks), and (2) sending a normal HTTP POST to the app's public webhook endpoint with a modified `shop-domain` header. No cryptographic secret, elevated privilege, or TLS interception is needed, making this readily reachable by an unprivileged internet user.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the HMAC verification, e.g. include the shop-domain header value in `to_signable_string`, or independently verify that `request.shop` matches an already-established, authenticated session/shop record before trusting it as the tenant key. At minimum, document prominently that `request.shop` is unauthenticated and must not be used for tenant attribution without separate verification (e.g., cross-checking against a previously stored session for that shop).

### Proof of Concept
1. Install/operate the target app as Shop A (attacker-controlled) and capture a legitimately delivered webhook request: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC-SHA256(secret, B)`).
2. Craft a new HTTP POST to the app's webhook endpoint with the identical body `B` and identical `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this successfully (shop is only checked for presence, not authenticity): [5](#0-4) 
4. `HmacValidator.validate` succeeds because it only recomputes the HMAC over `B` (`to_signable_string`), which is unchanged: [6](#0-5) 
5. `Registry.process` invokes the host's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing Shop A's captured payload to be attributed to `victim-shop.myshopify.com`: [7](#0-6)

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
