### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body. The `shop` (and `topic`/`webhook_id`) values that the library hands to the merchant's `WebhookHandler` are taken directly from unauthenticated HTTP headers and are never included in the HMAC-signed content. Because the HMAC secret (`api_secret_key`) is a single per-app secret shared across every merchant that has the app installed, an attacker who controls one legitimate install of the app can capture a valid `(body, hmac)` pair from their own webhook deliveries and replay it to the app's webhook endpoint with an arbitrary `shop` header, producing a request that passes HMAC validation while being attributed to a shop the attacker does not control.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for webhooks that method returns only the raw body: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors, however, are read straight from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC and then forwards the unauthenticated `request.shop` value straight to the app's handler as the tenant identifier: [3](#0-2) 

The identity binding that should hold is:
`HMAC-verified content == (shop, topic, body)` that the handler acts on.

What actually holds is:
`HMAC-verified content == body only`, while `shop`/`topic`/`webhook_id` are attacker-controlled headers.

Because the webhook HMAC secret is the app's single `api_secret_key`/`client_secret`, it is identical across all merchant shops that have the app installed — it is not a per-shop secret. Any user who can get the app installed on their own store (which requires no special privilege — installing a public app is an unprivileged action) receives genuine Shopify-signed webhook deliveries for their own shop. Since the signed content is only the body, and many webhook payloads have body content that is fully or partially attacker-influenced (e.g., `products/create`, `orders/create`, `customers/update`, or bodies that are simply reproducible), the attacker can construct or capture a `(raw_body, hmac)` pair and replay it directly to the app's public webhook endpoint while substituting the `shop` header for a victim shop domain the attacker does not own. `HmacValidator.validate` will still succeed because it only checks the body against the shared app secret, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event is `shop: <victim-shop>`.

### Impact Explanation
This breaks the tenant-authentication boundary the webhook HMAC is supposed to provide. Applications built on this gem key their internal state/records by the `shop` value received in `WebhookMetadata` (per the documented handler contract), so a forged `shop` header lets an attacker inject or corrupt webhook-driven state for a victim tenant, including mandatory compliance topics such as `customers/redact`, `customers/data_request`, or `shop/redact` which many apps use to trigger destructive/data-handling actions keyed only by `shop`. This is a cross-tenant integrity/confidentiality issue reachable by any unprivileged actor who can install the app once for themselves.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-owned shop (an unprivileged, self-service action for any public Shopify app), (2) triggering or receiving one legitimate webhook delivery to capture a valid `(body, hmac)` pair, and (3) POSTing that same body/HMAC to the app's public webhook endpoint with a modified `shop` header. No access to `api_secret_key`, tokens, or the victim's account is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the authenticated content before trusting them, e.g. by including the `x-shopify-shop-domain` header in the value that is HMAC-verified, or by requiring the handler/registry to cross-check the delivered `shop` against a shop that is independently known to be associated with the webhook subscription (e.g., via a `webhook_id`-to-shop lookup maintained server-side rather than trusting the header verbatim).

### Proof of Concept
1. Install the vulnerable app on attacker-owned shop `attacker.myshopify.com`; the app registers a webhook (e.g. `customers/redact`) whose handler performs shop-scoped side effects keyed on `data.shop`.
2. Shopify sends a legitimate webhook to the app's endpoint:
   - headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body B>`, `x-shopify-topic: customers/redact`
   - body: `B`
3. Attacker replays this exact request to the same public endpoint but changes only the `x-shopify-shop-domain` header to `victim.myshopify.com`, keeping body `B` and the HMAC identical.
4. `Utils::HmacValidator.validate` (see `lib/shopify_api/utils/hmac_validator.rb`) recomputes the HMAC over body `B` using the app's single `api_secret_key` and it matches, so `Registry.process` proceeds and invokes the handler with `shop: "victim.myshopify.com"`, even though `victim.myshopify.com` never sent this webhook.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
