### Title
Third-party supply dust restamps a victim's stored LTV downward, freezing withdrawals and borrows - (File: contracts/controller/src/positions/supply.rs)

### Summary
`supply` lets any authenticated caller top up an *existing* supply leg on an account it does not own (`require_third_party_existing_supply`). Every merged leg unconditionally restamps the position's stored `loan_to_value` to the current spoke listing via `merge_supply_leg` → `refresh_supply_risk_params`, with no HF gate on the LTV leg of the refresh. After governance lowers a market's LTV, an attacker can spend a dust top-up to pin the lowered LTV onto a victim's position. Because `borrow` and `withdraw` gate on LTV-weighted collateral covering debt, the forced restamp can push the victim below the collateral check and block all withdrawals and borrows — a temporary freeze of the victim's funds — while the attacker's dust is simply donated.

### Finding Description
The third-party admission check only requires that each topped-up market already exists in `account.supply_positions`:

```rust
// contracts/controller/src/positions/supply.rs:86-96
if account_id != 0
    && !account::is_owner_or_delegate(env, resolved_account_id, caller, &account.owner)
{
    for (hub_asset, _) in aggregated.iter() {
        assert_with_error!(
            env,
            account.supply_positions.contains_key(hub_asset.clone()),
            GenericError::NotAuthorized
        );
    }
}
```

The merge then restamps LTV unconditionally (only the LT/bonus/fee tuple is HF-gated):

```rust
// contracts/controller/src/risk/params.rs:34-37
position.loan_to_value = effective_config.loan_to_value;
if scope == RiskRefreshScope::FullTuple {
    apply_gated_liquidation_params(...);
}
```

`merge_supply_leg` calls `refresh_supply_risk_params` with `RiskRefreshScope::FullTuple` on every supply leg (`contracts/controller/src/positions/supply.rs:288-296`). The victim's consent is never required: any stranger can trigger the write with a minimum-amount deposit.

This mirrors the report's bug class — a permissioned-for-entry mutation endpoint that merges fresh data over an existing entity's stored state with no ownership check, bypassing the guard applied to other mutation paths (borrow/withdraw require `require_owner_or_delegate`, INV-AUTH-02).

The withdrawal/borrow gate then uses the restamped LTV: `calculate_account_risk_totals` weights collateral by the stored `loan_to_value`, and a lowered LTV shrinks `ltv_collateral` so the post-action solvency check (`InsufficientCollateral`) fails. The pinned harness test `lowering_ltv_between_borrow_and_withdraw_gates_the_withdraw_but_not_the_stamp` (`tests/test-harness/tests/controller/governance_change_between_legs.rs:24-44`) confirms the mechanics: after an LTV cut, a top-up carries the new stamp and the withdraw that previously reverted stays blocked until debt is repaid. The third-party variant is explicitly reachable — `regression_supply_skips_bonus_only_raise_below_min_hf` shows `try_supply_to_account(BOB, ALICE, ...)` succeeding (`tests/test-harness/tests/controller/security_audit.rs:151-160`).

### Impact Explanation
Temporary freezing of user funds. The victim cannot withdraw collateral or borrow until either (a) they repay enough debt to pass under the lowered LTV, (b) governance raises LTV back, or (c) a further restamp occurs. If the victim lacks funds to repay, the freeze persists; their collateral is also now exposed to liquidation as market prices move while they cannot deleverage by withdrawing. The attacker's cost is only the donated dust amount, which can be near-minimal. On HF the attack also has a subtle benefit to liquidators: while `apply_gated_liquidation_params` protects the LT tuple below HF 1.05, the LTV restamp itself is ungated and applies at any health factor.

### Likelihood Explanation
Requires a governance LTV reduction on a listed market (a routine risk action), plus one dust `supply` call by any address against any victim account holding that asset and outstanding debt near the borrow limit. Preconditions are mild: no victim interaction, no special permissions, `caller.require_auth` only. Likelihood is bounded because it needs a parameter-change trigger and only bites accounts whose LTV headroom is consumed by the cut — hence Medium rather than High.

### Recommendation
Restrict `supply` to owner-or-delegate when the leg's stored LTV would change adversely, or skip the LTV restamp for legs topped up by a non-owner (apply `restamp_listed_supply_ltv` semantics only on owner-initiated actions). Alternatively, gate the LTV decrease the same way `apply_gated_liquidation_params` gates the liquidation tuple: apply `position.loan_to_value = effective_config.loan_to_value` only when it is not lower than the stored value or the caller is owner/delegate.

### Proof of Concept
1. Alice supplies USDC and borrows ETH near the LTV limit; her USDC leg stores `loan_to_value = 7500`.
2. Governance executes `EditAssetInSpoke` lowering USDC `loan_to_value` to 5000 (an ordinary risk tightening; existing positions keep the stored stamp per design).
3. Bob calls `supply(caller: bob, account_id: alice_id, spoke_id, assets: [(USDC_key, 1)])`. `require_third_party_existing_supply` passes because the leg exists; `merge_supply_leg` restamps `loan_to_value` to 5000 (ungated) and Bob's 1 unit is credited to Alice.
4. Alice calls `withdraw(USDC, …)` → reverts `InsufficientCollateral` because `ltv_collateral` is now computed at 5000 BPS. `borrow` likewise reverts.
5. Alice remains frozen until she repays ETH or the LTV is restored; meanwhile any price decline can push her to liquidation with no ability to deleverage.
