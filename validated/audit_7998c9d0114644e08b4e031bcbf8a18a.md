### Title
Every vault "delete" (data-withdrawal) request is gated behind the same on-chain allowlist check as "create", so already-owned secrets can be temporarily locked when allowlisting fails or lags - ([File: core/capabilities/vault/allow_list_based_auth.go])

### Summary
The gateway-routed Vault pipeline requires an owner to obtain a **fresh, on-chain allowlisted digest** for every JSON-RPC method, including `MethodSecretsDelete` (the equivalent of "withdrawing"/removing already-owned data), exactly the same way it requires one for `MethodSecretsCreate`. There is no special-casing that lets an owner unconditionally delete or list secrets they already own without passing the identical allowlist/expiry gate used for writes. This mirrors the ThunderNFT `Pool.withdraw()` bug class: a delisting/whitelist check meant to gate deposits is re-applied at withdrawal time, so once the gating condition can no longer be satisfied (allowlist entry not yet propagated, expired, or never resubmitted), the owner cannot get their own data/funds out.

### Finding Description
`GatewayVaultRequestProcessor.processRequest` dispatches all four vault methods (`Create`, `Update`, `Delete`, `List`) through the same code path, and every path ends in `authorizeAndStamp`, which calls `p.authorizer.AuthorizeRequest` unconditionally before the operation is allowed to proceed: [1](#0-0) [2](#0-1) 

The default `Authorizer` wired by `NewGatewayHandler` is the on-chain, allowlist-based authorizer (`allowListBasedAuth`), which requires a request-digest entry to exist in the `WorkflowRegistry` allowlist and to not be expired: [3](#0-2) [4](#0-3) 

This check is identical regardless of whether the request is a mutating "deposit-like" action (`SecretsCreate`/`SecretsUpdate`) or a "withdrawal-like" action (`SecretsDelete`/`SecretsList`) on data the caller already owns. The digest is derived per-request (via `req.Digest()`), so a delete request needs its **own, separately allowlisted, unexpired** on-chain entry — the prior allowlisting used to create the secret does not cover deleting it: [5](#0-4) 

The authorization lookup also depends on the `workflowRegistrySyncer`'s cached view of on-chain state, polled periodically and retried for only a bounded window (10 retries × 3s): [6](#0-5) [7](#0-6) 

If the owner's new allowlist submission for the delete request has not yet propagated to a node, has expired, or otherwise fails to be found (e.g., transient chain read/sync issues), `AuthorizeRequest` returns `"request not allowlisted"` and the entire delete/list request is rejected — even though the caller is the legitimate owner of the underlying secrets and is not asking to write new data, only to remove/inspect their own: [8](#0-7) 

This is the same root-cause pattern as the ThunderNFT report: a whitelist/eligibility gate intended for controlling entry (deposit / secret creation) is reused, unmodified, to gate exit (withdrawal / secret deletion), so external state (allowlist expiry, propagation lag, on-chain gas/availability to resubmit) can transiently — or, if the owner can no longer transact on-chain — indefinitely block the user from getting their own data out of the vault.

### Impact Explanation
An owner who wants to delete secrets they already control cannot do so unless they can first successfully submit and have propagated a brand-new on-chain `AllowlistRequest` transaction for the exact delete-request digest. If the on-chain allowlist entry lags behind the syncer's poll interval, or the owner cannot immediately transact on-chain (e.g., gas issues, RPC unavailability, wallet compromise concerns prompting an urgent deletion), the owner's ability to purge or manage their own vault secrets is temporarily blocked by design, not by a data-integrity or access-control violation of someone else's data. This matches a "temporary freezing"-class impact analogous to the original report, scoped to the gateway/allowlist subsystem rather than fund custody.

### Likelihood Explanation
This triggers under normal, expected conditions: the workflow registry syncer only polls periodically and `AuthorizeRequest` retries for a fixed ~30s window before giving up, so any delay in on-chain allowlist propagation beyond that window causes deletion/listing requests to fail with "request not allowlisted." No malicious actor is required — any legitimate owner attempting a timely deletion during allowlist propagation lag, or after their allowlist entry lapses, will hit this.

### Recommendation
Do not require a fresh, request-specific on-chain allowlist entry for `SecretsDelete` (and arguably `SecretsList`) operations performed by the verified owner of the target secrets. Instead, authorize deletion/listing based on the requester's already-established, previously-verified ownership of the target `SecretIdentifier`s (as recorded when the secrets were created), independent of whether a new allowlist entry for that specific delete-request digest currently exists on-chain. This decouples "write eligibility" (controlled by the allowlist) from "the ability to remove or view your own already-stored data," preventing transient or indefinite allowlist unavailability from freezing access to owned secrets.

### Proof of Concept
1. Owner `O` creates a secret via `MethodSecretsCreate`, successfully allowlisting and authorizing that specific create-request digest (per `allow_list_based_auth.go` and `gateway_vault_request_processor.go` `processCreateSecretsRequest`).
2. Owner `O` later wants to delete that secret and submits a `MethodSecretsDelete` request. `processDeleteSecretsRequest` computes a brand-new digest for this delete request and calls `authorizeAndStamp` → `AuthorizeRequest`.
3. Because the delete request's digest was never previously allowlisted (only the create request's digest was), or because `O`'s newly-submitted allowlist transaction for the delete digest has not yet propagated to the `workflowRegistrySyncer` cache within the retry window (`allowListBasedAuthRetryCount`/`allowListBasedAuthRetryInterval`), `AuthorizeRequest` returns `errors.New("request not allowlisted")`.
4. The gateway/handler surfaces `"request not authorized: request not allowlisted"` and the delete is rejected, even though `O` is the verified owner of the secret and is not creating new state.
5. `O` must retry allowlisting on-chain and wait for propagation before being able to remove their own secret — reproducing the "temporarily locked / cannot withdraw own asset" condition from the referenced report, applied to the vault's allowlist/gateway subsystem.

func (p *GatewayVaultRequestProcessor) processDeleteSecretsRequest(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
) (*AuthorizedGatewayVaultRequest, error) {
	if req.Params == nil {
		return nil, InvalidVaultParamsError{Method: req.Method, Err: errors.New("request params must not be nil")}
	}

	var deleteReq vaultcommon.DeleteSecretsRequest
	if err := json.Unmarshal(*req.Params, &deleteReq); err != nil {
		return nil, InvalidVaultParamsError{Method: req.Method, Err: err}
	}
	if p.stripOwnerPrefixForAuth {
		deleteReq.RequestId = req.ID
		if err := marshalVaultParams(req, &deleteReq); err != nil {
			return nil, InvalidVaultParamsError{Method: req.Method, Err: err}
		}
	} else {
		deleteReq.RequestId = coalesceRequestID(deleteReq.RequestId, req.ID)
	}

	if err := p.validator.ValidateDeleteSecretsRequest(ctx, &deleteReq); err != nil {
		return nil, p.validationError(req, err)
	}

	return p.authorizeAndStamp(ctx, req, func(prefixedRequestID string) error {
		deleteReq.RequestId = prefixedRequestID
		vaultutils.ApplySecretIdentifierNamespaceDefaults(deleteReq.Ids)
		return marshalVaultParams(req, &deleteReq)
	})
}

func (p *GatewayVaultRequestProcessor) authorizeAndStamp(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
	stamp func(prefixedRequestID string) error,
) (*AuthorizedGatewayVaultRequest, error) {
	incomingOwner := ""
	if idx := strings.Index(req.ID, vaulttypes.RequestIDSeparator); idx != -1 {
		incomingOwner = req.ID[:idx]
	}

	p.lggr.Debugw("authorizing gateway vault request", "method", req.Method, "requestID", req.ID)
	authResult, err := p.authorizer.AuthorizeRequest(ctx, *req)
	if err != nil {
		authErr := fmt.Errorf("request not authorized: %w", err)
		p.lggr.Errorw("gateway vault request authorization failed", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "incomingOwner", incomingOwner, "error", authErr)
		return nil, authErr
	}

func (r *allowListBasedAuth) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	r.lggr.Debugw("AllowListBasedAuth authorizing request", "method", req.Method, "requestID", req.ID)
	requestDigest, err := req.Digest()
	if err != nil {
		r.lggr.Debugw("AllowListBasedAuth failed to create digest", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, err
	}
	requestDigestBytes, err := hex.DecodeString(requestDigest)
	if err != nil {
		r.lggr.Debugw("AllowListBasedAuth failed to decode digest", "method", req.Method, "requestID", req.ID, "requestDigest", requestDigest, "error", err)
		return nil, err
	}
	requestDigestBytes32 := [32]byte(requestDigestBytes)
	if r.workflowRegistrySyncer == nil {
		r.lggr.Errorw("AllowListBasedAuth workflowRegistrySyncer is nil", "method", req.Method, "requestID", req.ID)
		return nil, errors.New("internal error: workflowRegistrySyncer is nil")
	}
	allowlistedRequest, allowedRequestsStrs, err := r.findAllowlistedItemWithRetry(ctx, req, requestDigest, requestDigestBytes32)
	if err != nil {
		return nil, err
	}

func (r *allowListBasedAuth) findAllowlistedItemWithRetry(ctx context.Context, req jsonrpc.Request[json.RawMessage], requestDigest string, requestDigestBytes32 [32]byte) (*workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest, []string, error) {
	for attempt := 0; attempt <= r.retryCount; attempt++ {
		allowedRequests := r.workflowRegistrySyncer.GetAllowlistedRequests(ctx)
		allowedRequestsStrs := make([]string, 0, len(allowedRequests))
		for _, rr := range allowedRequests {
			allowedReqStr := fmt.Sprintf("AuthorizedOwner: %s, RequestDigest: %s, ExpiryTimestamp: %d", rr.Owner.Hex(), hex.EncodeToString(rr.RequestDigest[:]), rr.ExpiryTimestamp)
			allowedRequestsStrs = append(allowedRequestsStrs, allowedReqStr)
		}
		r.lggr.Debugw("AllowListBasedAuth loaded allowlisted requests", "method", req.Method, "requestID", req.ID, "attempt", attempt+1, "allowedRequests", allowedRequestsStrs)

		allowlistedRequest := r.fetchAllowlistedItem(allowedRequests, requestDigestBytes32)
		if allowlistedRequest != nil {
			return allowlistedRequest, allowedRequestsStrs, nil
		}
		if attempt == r.retryCount {
			return nil, allowedRequestsStrs, nil
		}

		r.lggr.Debugw("AllowListBasedAuth request digest not yet allowlisted, retrying",
			"method", req.Method,
			"requestID", req.ID,
			"digestHexStr", requestDigest,
			"attempt", attempt+1,
			"maxAttempts", r.retryCount+1,
			"retryInterval", r.retryInterval)
		if err := sleepWithContext(ctx, r.retryInterval); err != nil {
			r.lggr.Debugw("AllowListBasedAuth retry canceled", "method", req.Method, "requestID", req.ID, "error", err)
			return nil, nil, err
		}
	}

	return nil, nil, nil // unreachable: loop always returns
}
