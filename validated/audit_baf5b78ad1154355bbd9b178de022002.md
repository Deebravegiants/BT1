### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while the shop-identifying header (`shopify-shop-domain` / `x-shopify-shop-domain`) is read separately and never included in the signed bytes. `Registry.process` verifies the HMAC and then unconditionally trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler, so the binding "HMAC-verified bytes == the shop the payload is attributed to" does not hold.

### Finding Description
`Request#hmac` and `Request#to_signable_string` bind the signature strictly to `@raw_body`: [1](#0-0) [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read from separate, unsigned headers: [3](#0-2) 

`HmacValidator.validate` verifies exactly this signable string (i.e., only the raw body) against the computed HMAC: [4](#0-3) 

`Registry.process` performs this single check and then immediately trusts `request.shop`/`request.topic`/`request.webhook_id`, none of which were part of the verified bytes, to build the tenant-identifying `WebhookMetadata` passed to the app's handler: [5](#0-4) 

Identity-binding equality that should hold: `shop-header == shop covered-by-HMAC`. In this design it is instead `shop-header == arbitrary attacker-controlled value`, since the shop header sits entirely outside the signed byte range. An unprivileged attacker who is a merchant of their own shop (or otherwise obtains one legitimate `raw_body` + `hmac` pair from Shopify — trivially available to any developer/merchant testing their own store's webhooks) can:
1. Capture a genuine `(raw_body, hmac)` pair delivered for their own shop A.
2. Replay that exact body and HMAC to the victim app's webhook endpoint, substituting the `shopify-shop-domain` header with shop B's domain (any string, no ownership required).
3. `HmacValidator.validate` passes, because it only checks `raw_body` against the signature; it never inspects the `shop` header.
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic:, shop: "shopB...", body: request.parsed_body, ...))`, so the app processes attacker-supplied content (from shop A's webhook body) attributed to shop B.

Depending on how the host application keys its per-tenant data/state off `WebhookMetadata#shop` (the documented, expected usage pattern for this gem), this lets an attacker inject or mutate data under another tenant's identity — a cross-tenant access primitive rooted in this gem's own signature-scope design, not merely a downstream misuse of a documented API, since the library itself supplies `shop` to the handler as a "verified" field.

### Impact Explanation
This is a cross-tenant access vector: a party with no privileges on shop B can cause the app to execute webhook handler logic (and any resulting writes/side effects) tagged to shop B's identity, using content signed for their own shop A. This matches the "Critical - cross-tenant access" bucket, since the tenant binding relied upon by every consumer of `Registry.process`/`WebhookMetadata` is broken by design in this gem.

### Likelihood Explanation
Likelihood is high for any attacker who can install the target app on their own store (a normal, unprivileged action) and observe one legitimate webhook delivery (body + HMAC) for that store — no access to `api_secret_key`, access tokens, or the victim's credentials is required. Only the ability to POST an HTTP request with a spoofed `shop`-domain header to the app's public webhook endpoint is needed.

### Recommendation
Include the shop-identifying header (and ideally `topic`/`webhook-id`) in the HMAC-signable string, e.g. concatenate `shop-domain` with the raw body before computing/verifying the signature, or otherwise cryptographically bind the shop to the signed payload. At minimum, update `Request#to_signable_string` to incorporate `shop_domain`, and document that `WebhookMetadata#shop` is only trustworthy once such binding exists.

### Proof of Concept
```ruby
# Attacker owns shop "attacker.myshopify.com" and receives a legitimate webhook:
raw_body = '{"id":123,"malicious":"payload"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker replays the same (raw_body, hmac) pair, forging the shop header to target shop B:
headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # attacker-controlled, unsigned
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) succeeds (only raw_body is checked)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body, ...))
# The app processes attacker-crafted content attributed to "victim-shop.myshopify.com".
```
