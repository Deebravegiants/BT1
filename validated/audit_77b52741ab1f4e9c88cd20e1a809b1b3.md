Based on my investigation, I've confirmed the vulnerability pattern.

### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request **body**, while the `shop` identity used to route/act on the webhook is read from an HTTP header that is never covered by that signature.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes/compares the HMAC exclusively against that signable string [2](#0-1) . However, `Registry.process` derives the trusted "shop" identity from `request.shop`, which is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header — a value the HMAC never protects: [3](#0-2) [4](#0-3) . This `shop` value (along with `topic`, `webhook_id`, `api_version`, also header-derived and unsigned) is then passed straight into `WebhookMetadata` and handed to the app's `WebhookHandler#handle` as the trusted tenant identifier [5](#0-4) .

This is structurally the same class of bug as the referenced report: a value that is *acted upon* (the identity/state used to drive downstream logic) is not the same value that is *cryptographically bound* by the verification step (`shop` header ≠ bytes covered by HMAC). Equality that should hold — "shop authenticated == shop used for tenant attribution" — is broken because only the body is authenticated.

### Impact Explanation
An unprivileged attacker who can obtain any single valid `(raw_body, hmac)` pair — e.g., by installing the target app on their own store and capturing a legitimately delivered webhook — can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value (e.g., a victim shop). `Registry.process` will accept it, because HMAC validation never inspects the shop header, and will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop. If the host app uses `data.shop` to key merchant records, apply mutations, or route to a session (the gem's documented/intended usage), this results in cross-tenant data injection under an attacker-controlled tenant identity.

### Likelihood Explanation
Exploitability requires only a publicly reachable webhook endpoint and one previously-observed valid `(body, hmac)` pair from any shop (including the attacker's own store, which they fully control) — no access token, `client_secret`, or privileged access is needed, satisfying the unprivileged-internet-user bar.

### Recommendation
Include the shop-identifying header (and topic/webhook_id/api_version) in the value that is cryptographically bound, e.g., either fold the shop domain into the HMAC-signable string, or require the caller to independently verify `request.shop` against a value already associated with a known/authorized installation before trusting it for tenant attribution.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store and registers a webhook.
2. Attacker captures the resulting request: raw body `B` and header `shopify-hmac-sha256: H` (valid for `B` under the app's secret).
3. Attacker POSTs `B` with header `H` unchanged but `shopify-shop-domain: victim-shop.myshopify.com` to the same public webhook endpoint.
4. `Utils::HmacValidator.validate` returns `true` (only `B`/`H` checked); `Registry.process` invokes the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload never originated from Shopify for that shop.
