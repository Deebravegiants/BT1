## Analysis

The reported bug class — an atomic, all-or-nothing transfer loop over a token list that a victim cannot subset or skip, letting a single reverting/malicious token permanently block withdrawal of otherwise-good funds — has a direct analog in Hyperbridge's cross-chain Intent Gateway escrow-release path.

### Title
Unremovable malicious/reverting input token permanently blocks cross-chain escrow redemption in IntentsBase - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`_withdraw` in `IntentsBase.sol` releases every token in a `WithdrawalRequest.tokens` array in a single atomic loop with no ability for the caller to omit or retry individual tokens. For cross-chain orders, `body.tokens` is always `order.inputs` — chosen entirely by the order's creator at `placeOrder` time with no allowlist/validation — and it is echoed back verbatim into the `RedeemEscrow`/`RefundEscrow` message dispatched via Hyperbridge in `ExtrinsicIntents.sol`. If any one of those input tokens reverts on `transfer`/`safeTransfer` (a pausable token, a blacklist-capable token like USDC, or a token the order creator purposely controls), `onAccept` for that settlement message reverts every time it's delivered, permanently freezing the entire escrow — including the legitimate tokens bundled alongside the bad one — since the dispatch is created with `timeout: 0` (no timeout-based recovery path exists).

### Finding Description
In `placeOrder` (`evm/src/apps/IntentGatewayV2.sol`, tron/sdk-core mirrors), `order.inputs` is fully attacker/user-controlled — only duplicate-token checks are performed, no check on token behavior or an allowlist: [1](#0-0) 

On a cross-chain fill, the solver delivers real output value to the beneficiary on the destination chain in `_fillCrossChain`, then dispatches a `RedeemEscrow` message carrying `order.inputs` verbatim back to the source chain, with `timeout: 0` (no expiry/rescue path): [2](#0-1) [3](#0-2) 

When that message is delivered to the source chain, `onAccept` decodes the `WithdrawalRequest` and calls `_withdraw` unconditionally on `RedeemEscrow`/`RefundEscrow`: [4](#0-3) 

`_withdraw` iterates `body.tokens` (i.e., the full, unfiltered `order.inputs` list) and performs a `safeTransfer` per token with no per-token isolation (no try/catch, no ability to skip a token): [5](#0-4) 

Because the loop and the outer `onAccept` call are atomic, a single non-transferable token anywhere in `order.inputs` — a pausable token, a token subject to blacklisting (e.g., USDC-style compliance freezes on the beneficiary address), or a token the order creator specifically crafted/controls to grief a solver — causes the entire redemption/refund to revert. Since this is delivered as an ISMP request with `timeout: 0`, there is no expiry after which the escrow could instead be claimed through an alternate path; every future delivery attempt of the same message hits the same revert, so the failure is permanent, not merely transient.

The same unfiltered, atomic pattern also gates `_cancelFromSource`/`onGetResponse` refunds and the same-chain `_cancelSameChain`/partial-fill paths in `IntrinsicIntents.sol`, which build their `WithdrawalRequest.tokens` directly from `order.inputs` as well: [6](#0-5) 

### Impact Explanation
For cross-chain orders, the solver already transferred real value to the user's beneficiary on the destination chain (irreversible, separate transaction) *before* the settlement message is delivered on the source chain. If the order's escrowed input list contains even one token that becomes non-transferable (deliberately by a malicious order creator, or incidentally via a later blacklist/pause event on a previously-benign token), the solver can never redeem any of the escrowed inputs from that order — including the otherwise-good tokens bundled alongside the bad one. This is a permanent freezing of solver funds (and, symmetrically, of the user's own refund on `RefundEscrow`/cancellation), reachable by any unprivileged user simply by calling `placeOrder` with a crafted `inputs` array — no governance or privileged role is required, unlike the original DAO report where a malicious admin was needed.

### Likelihood Explanation
`order.inputs` is entirely attacker-controlled at `placeOrder` time, with no restriction beyond dedup, and a solver has no visibility mechanism to detect at fill-time whether a given input token can later be frozen/paused/blacklisted (e.g., standard patterns like USDC blacklisting, or a custom ERC20 with an owner-controlled pause). An attacker only needs to place a cross-chain order bundling one legitimate high-value input token with one token they can revert on-demand (their own deployed contract, or by triggering a blacklist against the eventual solver/beneficiary address) to permanently trap the solver's counter-value once the solver fills the order.

### Recommendation
Make `_withdraw` resilient to a single failing token instead of atomic-only: either (a) process each token transfer independently (e.g., via low-level call + per-token success bookkeeping so failures don't block release of the remaining tokens, with a separate retry/sweep mechanism for the failed token), or (b) allow the beneficiary/relayer to specify a subset of `body.tokens` to redeem per delivery (mirroring the fix pattern from the analogous report — let the receiver choose/skip tokens), or (c) validate/allowlist escrowable input tokens at `placeOrder` time to exclude tokens with owner-controlled pause/blacklist hooks. Given `timeout: 0` on these dispatches, also consider adding a governance/relayer-triggered rescue path for permanently stuck settlement messages.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 whose `transfer` the attacker can make revert on demand (e.g., an owner-controlled `paused` flag).
2. Attacker calls `placeOrder` on the source chain with `order.inputs = [ {token: USDC, amount: 10_000}, {token: EvilToken, amount: 1} ]` and a legitimate `output` (e.g., ETH) — see `evm/src/apps/IntentGatewayV2.sol` `placeOrder`.
3. A solver calls `fillOrder` on the destination chain (`ExtrinsicIntents._fillCrossChain`), transferring the required ETH output to the beneficiary and dispatching `RedeemEscrow(commitment, order.inputs, solver)` back to the source chain with `timeout: 0`.
4. Before/when the `RedeemEscrow` message is delivered, the attacker pauses `EvilToken`.
5. `onAccept` on the source chain decodes the `WithdrawalRequest` and calls `_withdraw`, which reverts on `EvilToken.safeTransfer` inside the loop — the entire 10,000 USDC + fee release to the solver reverts.
6. Because the request has `timeout: 0`, it never expires; every relayer redelivery hits the same revert. The solver's already-paid ETH is unrecoverable, and the 10,000 USDC escrow is frozen in the contract indefinitely.

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            (uint256 protocolShare, uint256 beneficiaryShare) =
                _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                _sendValue(beneficiary, beneficiaryTotal);
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        // Native dispatch fee only if the solver sent enough to cover it; else the fee token.
        uint256 nativeFee = options.nativeDispatchFee;
        if (nativeFee > msgValue) nativeFee = 0;
        msgValue -= nativeFee;
        _post(
            order,
            _body(RequestKind.RedeemEscrow, commitment, order.inputs, bytes32(uint256(uint160(msg.sender)))),
            options.relayerFee,
            nativeFee
        );

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            _sendValue(msg.sender, msgValue);
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
