### Title
Webhook shop-domain identity spoofing due to HMAC not covering the shop field - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The external report describes an unrelated Solidity DoS bug, but the underlying pattern — a field that is *acted upon* by the receiving code without being *covered by the authenticating signature* — has a direct analog in this gem's webhook processing path. `ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, while `ShopifyAPI::Webhooks::Request#shop` is read straight from an unauthenticated HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only, then trusts the unauthenticated `shop` header when dispatching to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is derived from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signed material at all: [2](#0-1) 

`Registry.process` validates the HMAC (over the body only) and then, on success, forwards `request.shop` to the app's handler as the tenant identity for the event, alongside the (HMAC-verified) body: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` only ever hash `verifiable_query.to_signable_string`, i.e. the raw body for webhooks — the `shop` header never enters the HMAC computation: [4](#0-3) 

This breaks the identity binding `hmac_verified_bytes == bytes_used_for_tenant_identification`. In equality terms:
- Before: `signable_string = raw_body` (does not include shop) and `data.shop = header["shopify-shop-domain"]` (unauthenticated).
- After a replay/relay of a legitimate body+HMAC pair (signed for shop A) with the shop-domain header rewritten to shop B: `Utils::HmacValidator.validate(request)` still returns `true` (body/HMAC pair unchanged and valid for the app's shared `api_secret_key`), yet `WebhookMetadata.shop` now equals shop B while the body content is actually shop A's event data.

Because a single Shopify app has one `api_secret_key` shared across every installed shop, HMAC validity proves only "this body was signed by Shopify for some install of this app," not "this body belongs to the shop named in this header." Any host application that uses `WebhookMetadata#shop` (as returned by `handler.handle`) to select which tenant's record to look up, update, or route to — exactly the intended and documented usage pattern — can be made to apply shop-A's payload data under shop-B's identity if the header can be manipulated between Shopify and the app (e.g., a compromised/misconfigured intermediary, a shared endpoint deployment, or any component that forwards/relays webhooks without re-deriving the header from the verified source).

### Impact Explanation
This is a cross-tenant identity-binding gap: the value used to select the tenant (`shop`) is not cryptographically bound to the payload that was actually authenticated. Any consumer of this library that trusts `WebhookMetadata#shop` to route or persist per-tenant data (the pattern shown throughout the library's own webhook docs/tests) can have shop A's data attributed to shop B, i.e. cross-tenant data confusion — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the ability to influence the `shop-domain`/`x-shopify-shop-domain` header value independently of the signed body reaching the app's webhook endpoint (e.g., through a relay, proxy misconfiguration, or any non-Shopify-terminated transport hop) — the gem does not itself validate that the header matches an HMAC-covered value, so the guarantee callers naturally expect ("if HMAC is valid, all fields on `WebhookMetadata` are trustworthy") does not hold. Likelihood depends on the deployment topology, but the gem provides no defense-in-depth for this specific field.

### Recommendation
- Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values in the HMAC-signable material used for webhook validation, or otherwise cryptographically bind them to the verified body (e.g., verify `shop` against the `dest`/`shop` claim of a co-transmitted, separately-authenticated token when available).
- At minimum, document clearly that `WebhookMetadata#shop` is not covered by the HMAC and that host applications must independently corroborate the shop identity (e.g., against their own subscription/registration records) before using it for tenant selection.

### Proof of Concept
1. Shopify sends a legitimate webhook for `shop-a.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
2. A component between Shopify and the app (relay, shared multi-tenant ingress, proxy) forwards the same body `B` and the same HMAC header, but rewrites `x-shopify-shop-domain` to `shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` from `to_signable_string` (`= B`) and matches — validation succeeds. [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic:, shop: "shop-b.myshopify.com", body: parsed(B), ...)` — the host application now believes body `B` (shop A's real data) belongs to shop B.
