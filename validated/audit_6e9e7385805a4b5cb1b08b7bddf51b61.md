### Title
Relayer consensus-delivery rewards are dropped when the first message in an executed batch is not a `Consensus` message - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`RelayerIncentives::on_executed` (the `FeeHandler` implementation used by `pallet-ismp`) only inspects the *first* message of the executed batch to recover the relayer's reward-payee signature. If that message is not a `Message::Consensus`, the function silently skips paying out rewards for the **entire batch**, even when later messages in the same batch are valid consensus messages that produced legitimate `StateMachineUpdated` events.

### Finding Description
`pallet_ismp::Pallet::execute` accepts an arbitrary `Vec<Message>` submitted in a single call, processes every message with `handle_incoming_message`, collects the resulting events, and hands the whole batch — `messages_with_weights` and `events` — to `T::FeeHandler::on_executed`: [1](#0-0) 

The batch can legitimately mix message types (consensus, request, response, timeout) in one call, since `execute` iterates and dispatches each message independently and only aggregates them afterward.

In `RelayerIncentives::on_executed`, the relayer's reward-payee account is derived solely from `messages.get(0)`: [2](#0-1) 

If that first entry is not `Message::Consensus` (or its embedded signature fails to decode/verify), `maybe_relayer_account` resolves to `None`, and the subsequent loop that pays rewards for every `IsmpEvent::StateMachineUpdated` in `events` — the `highest_per_state_machine` reward distribution — is entirely skipped: [3](#0-2) 

This is structurally the same bug class as the referenced StakeHouse finding: an `i == 0` (here, "first element of the batch") gate is used as a proxy for "does this batch contain a claimable/rewardable item," but the check only looks at position 0 rather than checking each element, so a batch whose first item does not satisfy the condition causes *all* otherwise-valid items in the batch to be denied the payout, even though the events (`StateMachineUpdated`) prove the consensus work was actually done and delivered.

### Impact Explanation
A relayer that submits a batch where the first message is not a `Consensus` message (e.g., a `Request`/`Response`/`Timeout` message batched together with one or more valid consensus messages, which is normal behavior for a relayer trying to minimize the number of separate extrinsics/transactions) loses the entire consensus-delivery reward for that batch, despite the chain state having genuinely advanced (`LastRewardedHeight` is not updated either, so the reward is not merely deferred — the corresponding block span is simply never counted, since the baseline in `calculate_reward` only ever moves forward via `LastRewardedHeight`, and the "already counted" blocks are effectively unrewardable going forward once a later batch establishes a new baseline). This causes a partial and possibly permanent loss of relayer reward funds, which the report's category explicitly covers ("relayer fee and reward accounting").

### Likelihood Explanation
This is reachable by any relayer submitting a `pallet-ismp` extrinsic that batches a non-consensus message ahead of a consensus message — a normal, unprivileged operational pattern for batching efficiency, not an attacker-controlled edge case. It requires no malicious behavior, governance action, or special privilege — an ordinary relayer batching messages in the "wrong" order (or whose signature-decode on the first message fails for any reason) triggers the loss.

### Recommendation
Do not gate the entire batch's reward distribution on `messages[0]`. Instead, scan the whole `messages` vector for `Message::Consensus` entries (or otherwise associate each `StateMachineUpdated` event with the specific consensus message and relayer that produced it) so that a valid consensus message anywhere in the batch results in its reward being paid, regardless of position.

### Proof of Concept
1. A relayer submits a single `pallet-ismp` extrinsic with `messages = [Message::Request(...), Message::Consensus(consensus_msg)]`.
2. `Pallet::execute` processes both messages successfully; `handle_incoming_message` verifies the consensus proof and emits `IsmpEvent::StateMachineUpdated` for the new height.
3. `execute` calls `T::FeeHandler::on_executed(messages_with_weights, events)` with both the Request-derived weight/message and the Consensus message, plus the `StateMachineUpdated` event.
4. In `RelayerIncentives::on_executed`, `messages.get(0)` returns the `Request` message, so the `if let Message::Consensus(..)` branch is not taken and `maybe_relayer_account` is `None`.
5. The `if let Some(relayer_account) = maybe_relayer_account` block, which contains the entire reward-payout loop over `highest_per_state_machine`, is skipped.
6. No `RelayerRewarded` event fires, no funds transfer from `TreasuryAccount` to the relayer, and `LastRewardedHeight` is not updated for that state machine's real height advance — resulting in lost reward accounting for a legitimately delivered consensus update.

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});
