## Title
Multisig timelock can be bypassed for pending transactions created before `upsert_timelock` is enabled - (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

### Summary
The multisig account module's timelock feature (`MultisigAccountTimeLock`, `upsert_timelock`/`upsert_timelock_internal`) measures elapsed time from a transaction's `creation_time_secs` rather than from the moment the timelock is activated. This is the exact bug class of the `ManagedWallet.sol` finding: a protection window (30-day timelock / owner-change timelock) that is supposed to gate a sensitive action can be satisfied using time that elapsed *before* the protection was actually in force.

### Finding Description
`can_execute_with_timelock` computes `elapsed = now_seconds() - pending_transaction.creation_time_secs` and allows execution once `elapsed >= timelock_period` [1](#0-0) . The `creation_time_secs` field is stamped when `create_transaction`/`create_transaction_with_hash` is called, independent of whether a timelock resource exists at that time [2](#0-1) .

The module's own doc comment on `upsert_timelock` acknowledges this design: enabling a timelock on a multisig account that already has one or more pending transactions in the queue does **not** grant those pending transactions the full `timelock_period` protection, because part of their "elapsed" time was already ticking before the timelock existed [3](#0-2) . The exact scenario mirrors the `ManagedWallet` bug:

1. A multisig account has no timelock configured (or a shorter one). An owner calls `create_transaction` to queue a sensitive payload (e.g. change of owners, auth-key rotation, fund transfer). `creation_time_secs` is stamped at `now_seconds()` with no timelock in force.
2. Time passes naturally (or the account waits) while this transaction sits pending — since transactions execute strictly in order, this could be a long-pending, low-priority transaction.
3. An owner (or the multisig itself, since `upsert_timelock` is only callable by the multisig account signer via a resolved multisig transaction) later calls `upsert_timelock`/`upsert_timelock_internal` to add or tighten a timelock, intending it to protect the account going forward.
4. Because `can_execute_with_timelock` uses `creation_time_secs` (set in step 1, before the timelock existed) rather than the time the timelock was activated, the already-pending transaction can become immediately executable — or need to wait far less than `timelock_period` — the moment enough approvals accumulate, defeating the newly-added protection.

This is structurally identical to the `ManagedWallet.sol` issue where `activeTimelock` could be pre-armed by sending ether before a proposal existed so that, once the proposal was later created, the 30-day clock was effectively already satisfied. Here, the "clock" (`creation_time_secs`) can likewise be started before the protective control (`MultisigAccountTimeLock`) is actually in place, letting a transaction bypass the intended waiting period once the timelock is turned on.

### Impact Explanation
If a multisig account is compromised or has malicious/colluding owners, they could queue a dangerous transaction (e.g. `add_owners`, `remove_owners`, changing `num_signatures_required`, or an arbitrary payload that drains a resource account's assets) *before* other owners impose or increase a timelock as a defensive measure. Once the timelock is added expecting to buy time to detect and react, the pre-existing pending transaction may execute with little or no additional delay, undermining the custody protection the timelock was meant to provide over owner/threshold changes and asset-moving transactions controlled by the resource account. This directly maps to "unauthorized takeover of ... multisig control" and "resource-account control ... tied to live assets," since the multisig account is itself a resource account per the module's own documentation [4](#0-3) .

### Likelihood Explanation
This is explicitly documented by the developers as a known, accepted risk ("considered an acceptable, operator-visible risk") [5](#0-4) , meaning the team is aware of it and treats it as low severity/expected behavior rather than an unpatched vulnerability. The window is bounded by the previous timelock period (or approval time if none existed), which limits — but does not eliminate — the bypass. Because this behavior is acknowledged and intentionally scoped by the team as a documented residual-risk tradeoff rather than a silent broken invariant, I am not confident this rises to an unreported, high/critical severity finding independent of the maintainers' own stated risk acceptance.

### Recommendation
If tighter guarantees are desired, `upsert_timelock_internal` could snapshot the timelock's "effective_from" timestamp and require `can_execute_with_timelock` to use `max(creation_time_secs, timelock_effective_from)` when computing elapsed time, so no pending transaction can receive credit for time that elapsed before the timelock was actually active.

### Proof of Concept
Given the acknowledged nature of this behavior in the source comments, a full PoC was not independently verified beyond tracing the code logic in `can_execute_with_timelock` and `upsert_timelock_internal`. A prospective test would:
1. Create a multisig account with no timelock, call `create_transaction`, and record time `T0`.
2. Advance a few seconds and call `upsert_timelock` with a 1-hour `timelock_period`.
3. Approve the pending transaction to reach the signature threshold.
4. Advance chain time so that `now_seconds() - T0 >= timelock_period` but `now_seconds() - (upsert_timelock call time) < timelock_period`.
5. Call `can_be_executed`/`execute` and observe it succeeds despite the timelock having been active for less than `timelock_period`.

**Note:** Because this repository's `multisig_account.move` appears to include custom, non-standard modifications (the entire timelock feature — `MultisigAccountTimeLock`, `upsert_timelock`, `override_threshold`) not present in the standard Aptos framework, and the risk is explicitly documented as accepted by the module's own comments, I was unable to fully confirm whether this constitutes a genuinely unreported, high/critical-severity custody bug versus an intentionally scoped design limitation. Given the developers' own acknowledgment, I lean toward **not** reporting this as a novel finding, but include the analysis since it is the strongest structural analog found to the external `ManagedWallet.sol` report.

```text
    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }
```
