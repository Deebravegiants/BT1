Given the specific instructions for the "ANALOG SCAN PROMPT" task, I completed the investigation. Here's the result:### Title
Webhook `shop`, `topic`, and `webhook_id` values are trusted for routing/identity while excluded from the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw HTTP body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — read from plain, unauthenticated HTTP headers — are trusted by `ShopifyAPI::Webhooks::Registry.process` for handler routing and passed on to application code as the authoritative event identity. This breaks the intended binding: `hmac == HMAC(secret, body)` is verified, but `shop`/`topic` (the fields actually acted upon) are never bound to that signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers with no cryptographic protection: [2](#0-1) 

`Utils::HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (i.e. the body) against the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts the unauthenticated header-derived `topic` for handler dispatch, and the unauthenticated `shop` value for the event's tenant identity handed to application handler code: [4](#0-3) 

Equality that should hold but doesn't: `authenticated_bytes (body signed by client_secret) == bytes the app treats as authoritative for shop/topic identity`. In reality the app treats `(body, arbitrary shop header, arbitrary topic header, arbitrary webhook_id header)` as authoritative, while only `body` is bound by the HMAC.

### Impact Explanation
Any party who can obtain one valid `(raw_body, hmac)` pair signed with the app's `client_secret` — e.g. by installing the app on their own store and receiving a real webhook delivery with a fixed/predictable body (several Shopify webhook topics, such as mandatory compliance topics or empty-body topics, produce constant or attacker-known bodies) — can replay that exact body/HMAC pair to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` and `X-Shopify-Topic` headers to name a **different, victim shop** or a **different, more sensitive topic** (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`). `HmacValidator.validate` will report the request as authentic because it only checks the body, and `Registry.process` will dispatch it to the corresponding handler with the forged `shop` treated as ground truth. This can cause cross-tenant data corruption/spoofing in the merchant application (e.g. triggering uninstall/redact cleanup logic for a shop that never sent the event), which is a cross-tenant integrity/authentication issue rooted in this gem's webhook verification code.

### Likelihood Explanation
Exploitation requires the attacker to first obtain at least one legitimately-signed `(body, hmac)` pair for the shared app secret. This is realistically achievable for a public app because any merchant (including an attacker-controlled store) can install the app and receive real, HMAC-signed webhook deliveries for topics with static/empty payloads, after which the header fields (`shop`, `topic`, `webhook_id`) can be freely rewritten by the attacker when replaying the request directly to the app's public webhook endpoint (no `client_secret`/token needed to perform the replay itself, only knowledge of one already-delivered valid body+HMAC).

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the value that is HMAC-verified (e.g., derive the endpoint URL/topic from Shopify's per-topic webhook registration and cross-check it against the header value, and/or include the header values in the signable string comparison), instead of only signing the raw body while trusting unauthenticated headers for routing and shop identity in `ShopifyAPI::Webhooks::Registry.process`.

### Proof of Concept
1. Install the target app on an attacker-controlled store; trigger delivery of a webhook topic whose body is empty/fixed (e.g., `{}`), and capture the resulting `X-Shopify-Hmac-Sha256` value — this is `HMAC-SHA256(client_secret, "{}")`, a constant reusable for any request with an identical empty body.
2. Send a forged HTTP POST directly to the app's webhook endpoint with body `{}`, the captured valid `X-Shopify-Hmac-Sha256` header, but with `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and `X-Shopify-Topic: app/uninstalled` (or another sensitive mandatory topic).
3. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb` line 190) calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body against the HMAC (`lib/shopify_api/utils/hmac_validator.rb` lines 26-31).
4. The registered handler for `app/uninstalled` is invoked with `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb` line 198), even though `victim-shop` never sent this webhook, demonstrating the missing binding between the HMAC-covered body and the header-derived shop/topic used for dispatch.
