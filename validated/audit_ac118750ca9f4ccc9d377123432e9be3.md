### Title
Stale delegate grants silently reactivate when a position NFT returns to its original owner - (File: contracts/controller/src/storage/account.rs)

### Summary
Delegate authority is stored as a `DelegateGrant` keyed only by `account_id` and stamped with `granted_by` = the owner who created it. An NFT transfer makes the old owner's grant list inert (because `get_delegates` filters on `granted_by == current_owner`), but nothing deletes or revokes it. If the NFT is ever transferred back to the original owner, the previously-granted delegates regain full spend authority over the account — including `withdraw`, `borrow`, `swap_collateral`, `multiply`, `flash_position` and `repay_debt_with_collateral` — with no fresh authorization from the owner.

### Finding Description
`get_delegates` reads `ControllerKey::Delegates(account_id)` and returns the stored delegate list only when `grant.granted_by == *owner` (account.rs:176-181). `is_owner_or_delegate` then accepts the caller if it is an active registered manager present in that list (account.rs:115-127). Because the grant entry survives transfer untouched, ownership churn acts as a passive disable/re-enable switch rather than a revocation:

- Alice owns `account_id`, calls `add_delegate` granting manager `M`.
- Alice transfers the position NFT to Bob. `granted_by == Alice != Bob`, so `M`'s grant is dormant. Bob never sees or clears it — there is no hook on the NFT `transfer` path that touches `ControllerKey::Delegates`.
- The NFT returns to Alice (sale back, OTC trade, gifting, or Bob's own `transfer`). The dormant grant now satisfies `granted_by == owner` again, so `M` is an active delegate once more without Alice ever calling `add_delegate` a second time.

The code partially acknowledges this: `remove_delegate` deletes stale grants specifically "preventing those grants from reactivating if the NFT returns to their original owner" (account.rs:224-238). But that cleanup only runs if a *new* owner explicitly calls `remove_delegate` — a permissionless call Bob has no incentive or even awareness to make, and one that reverts harmlessly-as-noop when the grant is stale. So reactivation happens by default whenever an intervening owner does nothing.

This mirrors CWE-613: a credential (the delegate grant) that should have been permanently invalidated on the ownership-change event is instead merely suspended and later honored again.

### Impact Explanation
Theft of user funds. Once reactivated, `M` can call `withdraw(caller=M, account_id, withdrawals, to=M)` and drain all collateral, or `borrow(..., to=M)` up to the LTV limit, leaving the account at the solvency boundary or saddled with maximal debt. `require_owner_or_delegate` passes because `M` is still listed in the stale grant and still marked `is_active` in `PositionManagerConfig`. Every owner/delegate-gated entrypoint is reachable: `withdraw`, `borrow`, `swap_collateral`, `swap_debt`, `multiply`, `flash_position`, `repay_debt_with_collateral`, `migrate_from_blend`. Severity is bounded by the requirement that `M` remain a governance-approved active position manager — a revoked or inactive manager cannot exploit it — which keeps this at Medium rather than High.

### Likelihood Explanation
Requires three conditions: (1) an owner who once delegated to an active manager, (2) an NFT transfer where the intermediate owner does not scrub the delegate list (no UI or flow does this; `remove_delegate` by the new owner returns `false` but does delete the stale entry only if called), and (3) the NFT returning to the original owner. Position NFTs are transferable collateral — secondary-market sales, collateral reorganization between a user's own wallets, and buy-backs are realistic flows. An attacker who is itself the stale delegate `M` can simply wait for condition (3) and then drain; no fresh signature from Alice is ever needed.

### Recommendation
Invalidate delegate grants permanently on ownership change rather than keying validity to `granted_by`. Options:

- Delete `ControllerKey::Delegates(account_id)` whenever the controller first observes a new owner for an account (e.g., stamp the last-seen owner in `AccountMeta` and clear grants when it changes), or
- Include an owner epoch/generation counter in `DelegateGrant` that increments on every observed ownership change, so grants can never outlive the epoch in which they were created.

A tombstone approach (record that a grant was revoked rather than relying on address mismatch) would also prevent reactivation while preserving the current storage layout.

### Proof of Concept
Conceptual sequence against the deployed contracts (all calls reachable by unprivileged addresses):

1. `controller.supply(caller=Alice, account_id=0, spoke_id=S, assets=[...])` → creates `account_id = N`, mints NFT `N` to Alice.
2. `controller.add_delegate(caller=Alice, account_id=N, delegate=M)` → writes `DelegateGrant{granted_by: Alice, delegates:[M]}` at `Delegates(N)` (requires `M` to be an active registered manager).
3. `position_nft.transfer(from=Alice, to=Bob, token_id=N)` → owner becomes Bob; grant dormant.
4. `position_nft.transfer(from=Bob, to=Alice, token_id=N)` → owner is Alice again; `Delegates(N)` was never deleted.
5. `controller.withdraw(caller=M, account_id=N, withdrawals=[(hub_asset, 0)], to=M)` → `is_owner_or_delegate` returns true via the stale grant; full collateral paid to `M`.
6. Optionally `controller.borrow(caller=M, account_id=N, borrows=[...], to=M)` → maximal debt drawn to `M`.

No call in steps 3-5 requires Alice's authorization after step 2, demonstrating that the delegate "session" was never truly expired.
