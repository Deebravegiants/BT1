## Title
Uniswap V4 spot-price venue pricing (`getExoticTokenPrice`/`computeDirectPoolPriceUsd`) can be manipulated within a single transaction to mis-price fills and drain the solver's own funds - (File: `sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts`)

### Summary
The Sherlock report describes `USSDRebalancer.rebalance()` deriving `USSDamount`/`DAIamount` from a Uniswap V3 pool's instantaneous token balances, which a flash loan can move within one transaction, letting an attacker force a favorable mint/sell. The analogous pattern in this codebase is `UniswapV4FundingPlanner.getExoticTokenPrice` / `computeDirectPoolPriceUsd`, which derives a fill price directly from a Uniswap V4 pool's current `sqrtPriceX96` (spot price), with no TWAP and an optional, not mandatory, deviation guard.

### Finding Description
`computeDirectPoolPriceUsd` reads `sqrtPriceX96` from the live pool state and returns it as `priceUsd` used to price the "exotic" (non-stable) token: [1](#0-0) [2](#0-1) 

This value feeds `resolveLegRates` → `referenceRate`/venue price used to size and price orders in `FXFiller`, and the only defense is `checkPriceGuard`, which compares against an operator-supplied `referencePrice`/`maxDeviationBps` pair — and that guard is explicitly **optional**, documented as leaving the chain "unguarded" when omitted: [3](#0-2) 

The flow docs confirm the price is the raw pool mid with no fee/size/impact adjustment and that `checkPriceGuard` is the only defense, checking static deviation rather than execution cost: [4](#0-3) 

A single swap in the target Uniswap V4 pool (whether financed by a flash loan, a large market order, or transient liquidity) shifts `sqrtPriceX96` for the remainder of that same block/transaction sequence in which the solver reads it. Because `getExoticTokenPrice`/`refresh()` reads live on-chain state at evaluation time with no time-weighting, an attacker can:
1. Move the pool's price via a swap on the configured V4 pool.
2. Trigger (or wait for) an order that causes the solver (FXFiller) to price/fund a venue-priced pair off that manipulated spot price, either underpricing the exotic token (solver overpays/over-delivers) or overpricing it (solver underpays, cheating the counter-party) — same root cause as `getSupplyProportion()`'s instantaneous-balance read in the report.
3. Reverse the manipulating swap, walking away with the arbitrage profit extracted from the solver's own funded fills, if `referencePrice`/`maxDeviationBps` is not configured for that chain (the documented default posture) or is configured with a loose tolerance.

### Impact Explanation
If the guard is unconfigured (an explicitly supported, documented configuration) or set loosely, an attacker can force `FXFiller` to size/fund fills at an arbitrary, manipulated price, causing the solver's UniswapV4-funded vault positions and wallet to pay out more value than they receive, or to receive less collateral than fair value — a direct value-extraction/loss-of-funds path for the solver's liquidity, analogous to the arbitrage described in the source report. This differs from the report's protocol-wide free-mint outcome (mint/redeem of a stablecoin) but is a comparable "manipulatable oracle → mispriced value transfer" class of bug reachable by any unprivileged actor who can trade against the configured pool and any user who submits an order the solver fills against that pool.

### Likelihood Explanation
The guard (`referencePrice`/`maxDeviationBps`) is optional per pair/chain and the docs explicitly describe the unguarded state as a supported configuration; when set, it only bounds against a static reference, not execution cost or manipulation via momentary price shifts within the guard's tolerance window. Any Uniswap V4 pool with modest liquidity, or one manipulable by a flash loan-financed swap, can be pushed transiently beyond fair value to bias one evaluation call. Likelihood is Medium-High for filler operators who leave the guard unset (the documented default), and lower but nonzero for operators who set a guard, since the guard only bounds absolute deviation, not the manipulation technique itself.

### Recommendation
- Require `referencePrice`/`maxDeviationBps` (or an equivalent TWAP-based check) unconditionally for any Uniswap V4-funded/priced pair rather than treating it as optional.
- Replace or supplement the raw `sqrtPriceX96` spot read in `computeDirectPoolPriceUsd` with a time-weighted average price (TWAP) over multiple blocks, since Uniswap V4 pools (like V3) support observation-based TWAPs, making single-transaction manipulation economically costly.
- Consider adding execution-cost-aware pricing (accounting for the pool's fee tier and expected slippage against order size), not just a static deviation bound.

### Proof of Concept
1. Configure a filler with a `[vault.uniswapV4]` position for an exotic/stable pair and omit `referencePrice`/`maxDeviationBps` (a valid, documented configuration per `docs/content/developers/evm/simplex/pricing.mdx`).
2. Attacker takes a large flash-loan-financed swap against the configured Uniswap V4 pool to move `sqrtPriceX96` far from the pool's typical price.
3. While the price is displaced, the attacker (or a colluding counter-party) submits/triggers an intent order that the solver's `FXFiller` prices via `getExoticTokenPrice`→`computeDirectPoolPriceUsd`, causing `sizeOrder`/`computeLegPolicyOutput` to compute an output amount based on the manipulated price.
4. The solver funds and fills the order at the bad price (draining its Uniswap V4 position/wallet unfavorably), while the attacker reverses the manipulating swap in the same block, pocketing the difference — mirroring the flash-loan `rebalance()` manipulation in the source report, but here manipulating `UniswapV4FundingPlanner`'s spot price feed instead of pool token balances.

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```

# Venue pricing (Uniswap V4 funded pairs)

Verified 2026-08-19.

```
resolveLegRates(...)
  curveless pair && token0 is a USD stable
    -> venuePriceMemo() -> getVenueUsdPrice(chain, token1)
         -> UniswapV4FundingPlanner.getExoticTokenPrice
              picks the position with the largest pool liquidity
              -> computeDirectPoolPriceUsd -> sdkPool.token0Price / token1Price
    -> checkPriceGuard(...)   reject if outside maxDeviationBps of the static reference
    -> rate = 1 / venueUsd
  otherwise -> the pair's ask/bid curve at the leg's notional
```

`computeDirectPoolPriceUsd` returns the **raw pool mid** derived from `sqrtPriceX96`. The pool's
fee tier is read and stored on the hydrated position (`pos.fee`) but never applied to the price,
and there is no size or impact term — `computeLegPolicyOutput` extends the mid linearly across the
whole priced quantity. `checkPriceGuard` is the only defense on this path, and it checks deviation
from a static reference, not execution cost. A venue-priced pair that has to swap through its own
pool to source inventory pays a fee tier it never quoted against.
