## Analog Found

### Title
Vetoing a state commitment resets `_latestStateMachineHeight` to `1`, allowing a previously‑vetoed (disabled) state commitment to be silently re‑activated by any relayer's consensus proof - (File: `evm/src/core/EvmHost.sol`)

### Summary
The XWiki bug allowed a *disabled* (revoked) account to be *re‑activated* because the system never invalidated the credential (the activation link) that had originally granted it validity. The Hyperbridge analog is `EvmHost.deleteStateMachineCommitmentInternal`, which is the function that "disables" a fraudulent `StateCommitment` after a fisherman veto. Instead of preserving the chain's true progress marker, it resets the state machine's height bookkeeping to `1`, defeating the monotonicity check that `HandlerV2.handleConsensus` relies on to reject stale/previously‑superseded commitments.

### Finding Description
When a fisherman detects a fraudulent `StateCommitment` and calls the handler‑only path that ends in `deleteStateMachineCommitmentInternal`, the function deletes the commitment and — critically — resets the height tracker: [1](#0-0) 

```solidity
function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
    ...
    delete _stateCommitments[height.stateMachineId][height.height];
    delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
    // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
    if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
        _latestStateMachineHeight[height.stateMachineId] = 1;
    }
    _vetoes[height.stateMachineId][height.height] = fisherman;
    ...
}
```

This `_latestStateMachineHeight` value is the sole gate used by `HandlerV2.handleConsensus` to decide whether an incoming intermediate state (extracted from a relayer‑submitted consensus proof) is allowed to overwrite the host's view of a state machine: [2](#0-1) 

```solidity
for (uint256 i = 0; i < intermediatesLen; i++) {
    IntermediateState memory intermediate = intermediates[i];
    uint256 latestHeight = host.latestStateMachineHeight(intermediate.stateMachineId);
    if (latestHeight != 0 && intermediate.height > latestHeight) {
        StateMachineHeight memory stateMachineHeight =
            StateMachineHeight({stateMachineId: intermediate.stateMachineId, height: intermediate.height});
        host.storeStateMachineCommitment(stateMachineHeight, intermediate.commitment);
    }
}
```

Once a veto resets `_latestStateMachineHeight` to `1`, the "must be strictly higher than everything we've ever accepted" invariant is broken: *any* future `intermediate.height > 1` for that `stateMachineId` will pass, regardless of whether it is lower than, equal to, or the very same height that was just disabled by the fisherman. The underlying BEEFY/SP1 consensus clients (`EcdsaBeefy.verify`, `SP1Beefy.verifyConsensus`) only enforce monotonicity on the **relay‑chain BEEFY commitment height** (`consensusState.latestHeight >= relay.blockNumber`), not on individual parachain state‑machine heights: [3](#0-2) [4](#0-3) 

Because the relay‑chain‑level staleness check and the per‑parachain `_latestStateMachineHeight` check are two independent gates, resetting the latter to `1` removes the only defense that would otherwise stop a relayer from re‑submitting (via any new, non‑stale BEEFY commitment) an intermediate state for the exact height that the fisherman just vetoed as fraudulent — effectively "re‑activating" state that governance/fishermen explicitly disabled, exactly mirroring how the XWiki activation token continued to be honored after the account had been administratively disabled.

### Impact Explanation
`EvmHost` state commitments are the root of trust used by `HandlerV2.handlePostRequests`, `handleGetResponses`, and timeout handlers to verify membership/non‑membership proofs of cross‑chain messages. If a vetoed (fraudulent) `StateCommitment` can be reinstated, an attacker can:
- Forge delivery of arbitrary `PostRequest`/`GetResponse` messages (state membership proofs verified against the reinstated fraudulent root), enabling unauthorized app actions, unbacked minting on token bridges relying on ISMP, or draining escrowed funds in intents/bridging contracts that trust `IHost.dispatchIncoming`.
- Defeat the entire fisherman/veto security mechanism designed to stop exactly this class of attack, since the veto's protective effect is transient rather than permanent.

This satisfies "forged message delivery / unsound state commitment" impact criteria at High severity.

### Likelihood Explanation
Exploitation requires: (1) a fraudulent state commitment to have existed and been vetoed by a fisherman at the *latest* height for that `stateMachineId`, and (2) a subsequent (non‑stale, relay‑chain‑level) consensus proof capable of including an `IntermediateState` at a height ≤ the true prior latest height (including the exact vetoed height, if the underlying parachain header/MMR proof format allows re‑proving a previously produced header). The relay‑chain‑level staleness guard makes exact proof replay of the identical BEEFY commitment impossible, but it does not prevent a *different*, newer BEEFY commitment from carrying an intermediate state whose per‑parachain height regresses relative to what was previously accepted — precisely the scenario the `intermediate.height > latestHeight` check exists to prevent, and precisely the scenario the veto's height reset breaks. Given that any relayer can call `handleConsensus` permissionlessly, and the reset condition triggers automatically whenever the vetoed height happens to be the recorded latest (the common case, since fishermen typically veto the newest fraudulent update), likelihood is Medium-to-High.

### Recommendation
On veto, do not reset `_latestStateMachineHeight[stateMachineId]` to a low sentinel (`1`). Instead:
- Maintain a separate monotonically increasing "highest height ever observed" watermark that is never decreased by a veto, and gate `storeStateMachineCommitment` on that watermark rather than on the "current" (possibly-just-deleted) latest height; or
- Track vetoed heights explicitly (the `_vetoes` mapping already records the fisherman) and have `handleConsensus`/`storeStateMachineCommitment` reject any intermediate whose height is `<=` a previously vetoed height for that `stateMachineId`, in addition to the existing `>` check.

### Proof of Concept
1. Attacker (or colluding validator subset) gets a fraudulent `StateCommitment` for `stateMachineId = X` accepted at height `H` via `handleConsensus`, making `_latestStateMachineHeight[X] == H`.
2. A fisherman detects the fraud and calls the veto path, which invokes `deleteStateMachineCommitmentInternal(height={X,H}, fisherman)`. Since `H == _latestStateMachineHeight[X]`, the height is reset: `_latestStateMachineHeight[X] = 1`.
3. Attacker (any permissionless relayer) submits a new, non‑stale BEEFY/SP1 consensus proof (satisfying the relay‑chain height check in `EcdsaBeefy.verify`/`SP1Beefy.verifyConsensus`) whose parachain header proof furnishes an `IntermediateState{stateMachineId: X, height: H, commitment: <the same fraudulent commitment>}`.
4. In `HandlerV2.handleConsensus`, the check `latestHeight != 0 && intermediate.height > latestHeight` now evaluates `1 != 0 && H > 1`, which is true, so `host.storeStateMachineCommitment({X,H}, fraudulent_commitment)` is called — reinstating the exact commitment the fisherman had just vetoed.
5. The fraudulent commitment is now usable again by `handlePostRequests`/`handleGetResponses` to forge message delivery, bypassing the veto entirely.
