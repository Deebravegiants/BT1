### Title
Webhook shop/topic identity spoofing — `shop`/`topic` headers are not covered by HMAC verification - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while `shop` (tenant identity) and `topic` are read from separate HTTP headers that are never included in the signed material. `ShopifyAPI::Webhooks::Registry.process` validates only the HMAC-over-body, then passes the unverified `shop` header straight to the app's webhook handler as the tenant identifier. Any request that carries a *valid* `(body, hmac)` pair — which an attacker can legitimately obtain by installing the same public app on their own store and triggering a webhook to themselves — can be replayed to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`) header rewritten to a victim shop, and it will still pass validation.

### Finding Description
The binding that should hold is:
`hmac_valid(request) == true` **iff** `(body, shop, topic)` as processed by the handler are exactly what Shopify signed.

Instead, the code only enforces:
`hmac_valid(request) == true` **iff** `body` matches what was signed.

Evidence:

`to_signable_string` — the only material fed into HMAC verification — returns just the raw body: [1](#0-0) 

`shop` (and `topic`) are read from separate, unauthenticated headers: [2](#0-1) 

`HmacValidator.validate` verifies exactly `to_signable_string` (the body) against the secret — nothing else: [3](#0-2) 

`Registry.process` validates HMAC, then dispatches to the handler using the *unverified* `request.shop` and `request.topic`: [4](#0-3) 

Because a single `api_secret_key` is shared across every shop that installs a given public app, an attacker only needs to be a normal merchant (unprivileged internet user) who installs the app on their own store. Any real webhook delivery they receive from Shopify for their own store is a fully valid `(body, hmac)` pair per this library's check. The attacker can then POST that exact `body` + `hmac` to the app's public webhook endpoint again, but with the `x-shopify-shop-domain` header changed to a victim shop's domain (and/or `x-shopify-topic` changed). `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` hands the handler `WebhookMetadata.new(shop: <victim-shop>, topic: <spoofed-topic>, body: <attacker's own body>)`.

### Impact Explanation
This breaks the shop/topic identity binding without any credential theft, resulting in cross-tenant confusion at the app layer: the host application's webhook handler will process attacker-supplied data (topic + body from the attacker's own installation) as if it originated from an arbitrary victim shop of the attacker's choosing. Depending on what the host app does with `WebhookMetadata#shop`/`#topic` (e.g. updating billing state, uninstall handling, order/customer data sync, GDPR/compliance webhooks), this can lead to writing or deleting data under the wrong tenant, forging `app/uninstalled` or `shop/redact` events for a victim, or other cross-tenant state corruption — this matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
High likelihood for any app built on this gem's `Webhooks::Registry`/`Request` as documented: the only prerequisite is that the attacker be a legitimate installer of the same public app (a routine, unprivileged action), plus knowledge of the app's public webhook endpoint. No leaked secrets, no TLS interception, and no privileged account are required — only crafting one HTTP POST with a rewritten `shop`/`topic` header while re-using a genuine `(body, hmac)` pair the attacker legitimately received for their own store.

### Recommendation
Include `shop` and `topic` (and any other header field the handler trusts) in the HMAC-signable string, or otherwise cryptographically bind them to the signed body, so that tampering with these headers invalidates the HMAC. At minimum, `VerifiableQuery#to_signable_string` for webhook requests should incorporate the shop domain and topic headers rather than the body alone.

### Proof of Concept
1. Attacker installs the target public app on their own store `attacker-shop.myshopify.com` (permitted, unprivileged action).
2. Attacker triggers any webhook event on their store (e.g. `products/create`), and captures the raw POST Shopify sends to the app's webhook endpoint, including headers `x-shopify-hmac-sha256: <valid-hmac>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: products/create`, and the raw body.
3. Attacker resends the exact same request to the app's public webhook endpoint, but replaces the header value:
   `x-shopify-shop-domain: victim-shop.myshopify.com`
   (optionally also rewriting `x-shopify-topic` to a different registered topic; the raw body/hmac pair is left untouched).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `raw_body` — this still matches, so validation succeeds: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, i.e. the host application processes attacker-controlled data under the victim's tenant identity.
