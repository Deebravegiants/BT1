Confirmed: `HmacValidator.validate` only checks `to_signable_string` against the HMAC, and `Webhooks::Request#to_signable_string` returns only `@raw_body`.### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant relabeling of otherwise-valid webhook payloads - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC that authenticates the webhook only covers the raw request body. `Utils::HmacValidator.validate` calls `to_signable_string`, which for `Request` returns only `@raw_body` — the `shop-domain` header is never part of what is signed.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 
and `shop` is read straight from an attacker-controllable header with no cryptographic binding to it: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and compares it to the supplied `hmac`: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The identity binding that should hold is:
`hmac == HMAC(secret, raw_body || shop)`
but the actual implementation only enforces:
`hmac == HMAC(secret, raw_body)`

Because `shop` is excluded from the signed material, any request with a genuine `(raw_body, hmac)` pair remains valid regardless of what `shop-domain` header value accompanies it. An attacker who can generate one legitimate webhook (e.g., by owning/controlling a trial or test shop that installs the target app, and thus legitimately receiving genuine webhooks with valid HMACs for their own shop) can capture that `(raw_body, hmac)` pair and resend it to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header claiming to be a different, victim shop. `HmacValidator.validate` still returns `true` (the body/HMAC pair is genuinely valid), and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` is now attacker-chosen, e.g. targeting a victim's tenant.

### Impact Explanation
This breaks tenant isolation: the app's webhook handler acts on data (e.g., `customers/redact`, `shop/redact`, order/customer data) while believing it originates from shop B, when the payload actually came from shop A, and the association is entirely attacker-controlled. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up per-shop settings, to determine which merchant's data to delete/modify, to route to per-tenant handlers), this can lead to cross-tenant data corruption, redaction of the wrong shop's data, or attribution of arbitrary payload content to any shop the attacker chooses — a cross-tenant confused-deputy condition, matching the "cross-tenant access" Critical impact category, since the credential/tenant binding (shop-domain vs. signed payload) is never verified.

### Likelihood Explanation
Any unprivileged internet user can install a trial/development app that uses this gem (or otherwise become a legitimate source of one genuine webhook), capture the raw HTTP body and the `X-Shopify-Hmac-Sha256` value for their own shop, and replay that exact body/HMAC pair to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header. No access token, `api_secret_key`, or privileged account is required — only observation of one's own legitimately-received webhook traffic, which is standard and available to any merchant.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the material that is HMAC-verified, or independently validate that the `shop-domain` header corresponds to a shop that is actually expected/registered before trusting it in `WebhookMetadata`. At minimum, document/require host applications to cross-check `request.shop` against known installed shops before acting on webhook content, since the gem's own `to_signable_string` provides no such binding.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a shop they legitimately control) and triggers a webhook event, e.g. `orders/create`.
2. Shopify sends the app a genuine webhook: raw body `B`, headers including `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` and `X-Shopify-Hmac-Sha256: H`, where `H = HMAC(secret, B)`.
3. Attacker resends an HTTP POST to the same webhook endpoint with the identical raw body `B` and identical `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` (via `Request#to_signable_string` returning only `B`) and finds it equal to `H` — validation passes. [5](#0-4) 
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's original body>, ...)`, causing the app to process attacker-controlled data under the victim shop's identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
