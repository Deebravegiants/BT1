## Finding: Unsigned cross-chain calldata execution derives dispatch origin from an unauthenticated `message.from` field

### Title
Unauthenticated `message.from` field allows dispatching arbitrary RuntimeCalls under any account's identity without a signature - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
CVE-2016-1248 is a case of an unvalidated attacker-controlled value (`filetype`/`syntax`/`keymap`) being used to select and execute unintended logic. The analogous bug class in Hyperbridge is `pallet-hyper-fungible-token`'s `on_accept` calldata-execution path: when the ABI-decoded cross-chain `Message` carries `data` but no signature, the pallet dispatches an arbitrary `RuntimeCall` with an origin derived straight from the application-level `message.from` bytes — a field that is never cryptographically authenticated by the pallet itself.

### Finding Description
`Pallet::<T>::on_accept` [1](#0-0)  only authenticates the ISMP-level `(source, from)` module pair via `ContractToAsset::<T>::get(source, &from)` — this proves the request came from a *registered HFT contract deployment*, not that the *application-level* `message.from` field inside the ABI-encoded body is trustworthy.

`message.from` is decoded separately from the body and used later, in the no-signature branch of calldata execution, directly as the dispatch origin: [2](#0-1) 

```rust
} else {
    let from_bytes = message.from.as_ref();
    if source.is_evm() {
        T::EvmToSubstrate::convert(H160::from_slice(&from_bytes[from_bytes.len() - 20..]))
    } else {
        let mut account = [0u8; 32];
        account.copy_from_slice(from_bytes);
        account.into()
    }
};
```

This account is then used to dispatch an arbitrary `RuntimeCall` decoded from `substrate_data.runtime_call`: [3](#0-2) 

The only checks performed are the message length checks (20 or 32 bytes) and `BaseCallFilter::contains`. There is no signature, no proof-of-possession, and no cryptographic binding of `message.from` to the caller who actually triggered the send on the source chain — unlike the signed branch, which does verify a signature over `(nonce, runtime_call)` against `beneficiary_bytes` [4](#0-3) .

`message.from` is populated purely by whatever the source-chain sending contract chooses to ABI-encode into the `Message.from` field, documented as "original sender (for timeout refunds)": [5](#0-4) . Nothing in the ISMP dispatch/verification pipeline (module lookup, membership proof, receipt) authenticates that this inner field actually equals the identity of the account that dispatched the message. ISMP's `handle` only guarantees the `PostRequest.from`/`source` module pair and message integrity via the commitment proof — it says nothing about arbitrary body-level sub-fields matching the real caller.

### Impact Explanation
Since the dispatch origin for arbitrary `RuntimeCall`s in the unsigned branch is taken from an unauthenticated body field rather than a value cryptographically tied to the caller (as the signed branch correctly does), any deployment/path where `message.from` can diverge from the true sender (e.g., a non-canonical or buggy peer HFT/WrappedHFT deployment, a future integrator of the documented wire format, or any code path that doesn't hard-bind `from = msg.sender`) allows a cross-chain message to trigger a `RuntimeCall::dispatch(RawOrigin::Signed(origin))` as an arbitrary substrate/EVM-derived account — a critical unauthorized-app-action / potential-theft primitive (e.g. dispatching `Balances::transfer` from a victim account, provided such calls pass `BaseCallFilter`).

### Likelihood Explanation
Exploitability is contingent on whether any reachable sender implementation can set `message.from` independently of the real caller. In the two reference EVM contracts examined, `from` is hard-coded to `abi.encodePacked(msg.sender)`, which limits the impact to self-impersonation in the canonical path. However, the receiving pallet has no independent enforcement of this invariant — the guarantee lives entirely in the sender's convention rather than in the protocol's trust boundary, which is a defense-in-depth gap consistent with the CVE-2016-1248 bug class: acting on an unvalidated field's value as an authority-bearing directive.

### Recommendation
Require a valid signature for all `RuntimeCall` dispatches originating from cross-chain calldata, or otherwise cryptographically bind `message.from` (when used as dispatch origin) to a value that the pallet itself derives/authenticates rather than trusting the encoded body — mirroring the signature-verification already implemented in the signed branch.

### Proof of Concept
Not independently verifiable without also confirming every registered/whitelisted sender implementation always sets `Message.from = msg.sender`; the reference `HyperFungibleTokenUpgradeable.sol`/`WrappedHyperFungibleToken*.sol` contracts do enforce this convention [6](#0-5) , which limits the currently demonstrable blast radius to self-targeted calls. The gap is that the pallet itself performs no such enforcement, so the guarantee is only as strong as every current and future sender's convention rather than a protocol-level invariant.
