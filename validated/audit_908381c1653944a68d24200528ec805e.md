### Title
Unvalidated mnemonic accepted by `Wallet.create()` and `Wallet.addSeed()` allows non-standard/oversized mnemonics to become unrecoverable primary or extra seeds - (File: features/wallet/module/wallet.js)

### Summary
The `@exodus/wallet` module validates mnemonic word count and BIP39 correctness only in `Wallet.import()`, via `assertMnemonic(mnemonic, this.#validMnemonicLengths)` [1](#0-0) . However `Wallet.create()` — which also accepts a caller-supplied `mnemonic` — and `Wallet.addSeed()` never call `assertMnemonic`, so they silently accept mnemonics of any length or validity and derive a seed from them with `mnemonicToSeed({ mnemonic, format: 'buffer', validate: false })` [2](#0-1) [3](#0-2) .

### Finding Description
`assertMnemonic` is the only gate that enforces the wallet's configured `validMnemonicLengths` (e.g. `[12]` or `[12, 24]`) and BIP39 checksum validity: [4](#0-3) . It is invoked exclusively from `import()`: [1](#0-0) 

`create()`, by contrast, takes an optional `mnemonic` parameter directly and passes it to `mnemonicToSeed` with `validate: false`, without any length/checksum check: [5](#0-4) 

Similarly, `addSeed()` derives and stores a seed from an arbitrary `mnemonic` with no call to `assertMnemonic`, only checking for seed-ID duplication: [3](#0-2) 

This is the same bug class as the external report: the system does not consistently enforce a single, uniformly-validated mnemonic policy across all entry points that persist a seed as the wallet's primary or extra secret. Where the external report found the *display* path (recovery-phrase view) truncates to 12 words regardless of actual mnemonic length, here the *storage* path itself is inconsistent — `import()` enforces `validMnemonicLengths`, but `create()`/`addSeed()` do not, so a seed can be created and stored under mnemonic material that would be rejected (or silently mis-handled) if the user later tried to back it up and re-`import()` it, or that is not a standards-compliant BIP39 phrase at all (e.g., wrong checksum, non-multiple-of-3 word count, or an arbitrary string).

### Impact Explanation
If any UI or SDK caller path passes a user- or externally-supplied `mnemonic` into `wallet.create()` or `wallet.addSeed()` (both are exposed through the public wallet module and, for `addSeed`, through the `application` API surface [6](#0-5) ), the resulting primary/extra seed can be built from a mnemonic that:
- fails BIP39 checksum validation (so it can't be reproduced/re-imported through the same wallet's own `import()` validation, given `assertMnemonic` would reject it), or
- has an unexpected word count outside `validMnemonicLengths`.

This directly mirrors the "wallet unrecoverable from displayed/expected backup" impact class in the report: a user could end up with a wallet whose secret material cannot be correctly reconstituted via the standard, validated `import()` flow, and any downstream UI that assumes a fixed/validated mnemonic shape (as happened in the external report's "Show recovery phrase" screen) can misrepresent or truncate it. Because it directly affects wallet-seed recoverability/backup integrity, this is a genuine wallet-compromise-adjacent issue rather than a cosmetic one.

### Likelihood Explanation
`create()` and `addSeed()` are core, always-reachable wallet operations (not mock-only) and are exposed on the public wallet API and the `application` façade, so any client code (mobile/extension "import a phrase" or "restore" flows, or third-party seed integrations via `addSeed`/`compatibilityMode`) that forwards a user-entered phrase to these methods instead of `import()` reaches the unvalidated path. The test suite itself demonstrates that `addSeed` accepts arbitrary/duplicated 12-word strings without validation beyond duplicate-seed checks [7](#0-6) , confirming there is no length/checksum guard on that path today.

### Recommendation
Route `create()` and `addSeed()` through the same `assertMnemonic(mnemonic, validMnemonicLengths)` check used by `import()` whenever a caller-supplied mnemonic is provided, so all entry points that persist a seed share one consistent, enforced mnemonic policy. At minimum, `mnemonicToSeed` calls in `create()`/`addSeed()` should use `validate: true` (or explicit `assertMnemonic`) rather than `validate: false`.

### Proof of Concept
1. `wallet.create({ mnemonic: '<24 random words with correct checksum>' })` succeeds and stores/derives a seed, even though the wallet is configured with `validMnemonicLengths: [12]`. [5](#0-4) 
2. Attempting `wallet.import({ mnemonic: '<the same 24-word phrase>' })` on this or another wallet instance with `validMnemonicLengths: [12]` throws `UnexpectedWordCount` via `assertMnemonic`. [8](#0-7) 
3. This demonstrates the primary seed created in step 1 cannot be recovered/re-imported through the wallet's own validated `import()` path, an inconsistency directly analogous to the external report's "created with more words than the recovery view/import supports" scenario.

    await this.#assertWalletIsUnlocked()

    const seed = await mnemonicToSeed({ mnemonic, format: 'buffer', validate: false })
    const seedId = await getSeedId(seed)
    if (seedId === (await this.#primarySeedIdAtom.get())) {
      throw new Error('Seed already present')
    }

    const dateCreated = this.#clock.now()
    const data = { mnemonic, seed, dateCreated, compatibilityMode }
    const seeds = await this.#getExtraSeeds()
    if (seeds.length >= this.#maxExtraSeeds) {
      throw new Error('Maximum number of seeds reached')
    }

    if (seeds.some((seed) => seed.mnemonic === mnemonic)) {
      throw new Error('Seed already present')
    }

    seeds.push(data)
    await this.#setExtraSeeds(seeds)
    await this.#seedMetadataAtom.set((previous) => ({
      ...previous,
      [seedId]: { dateCreated, label, compatibilityMode },
    }))

    return this.#keychain.addSeed(data.seed)
  }

export const assertMnemonic = async (input, validMnemonicLengths) => {
  assert(typeof input === 'string', 'The secret phrase provided is not a string')

  if (!validMnemonicLengths.includes(input.split(/\s+/gu).length)) {
    throw new NamedError({ name: 'UnexpectedWordCount' })
  }

  if (await mnemonicIsInvalid({ mnemonic: input })) {
    throw new NamedError({ name: 'InvalidPhrase' })
  }
}
