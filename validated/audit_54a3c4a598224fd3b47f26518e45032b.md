### Title
Webhook HMAC only authenticates the request body, allowing the unauthenticated `shop-domain` header to be spoofed for cross-tenant webhook injection - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking `Utils::HmacValidator.validate(request)`, which computes the signature over `request.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — none of the HTTP headers are included in the signed material. Yet the `shop` (from the `shopify-shop-domain`/`x-shopify-shop-domain` header) and `topic`/`webhook_id` values, which are used to select the handler and are forwarded as the tenant-identifying fields in `WebhookMetadata`, are taken directly from these unauthenticated headers.

### Finding Description
The identity binding that should hold is:
`HMAC-verified bytes == bytes that determine the tenant (shop) context delivered to the app`

In `lib/shopify_api/webhooks/request.rb`:
```ruby
def to_signable_string
  @raw_body
end
```
only the body is included in the signable string used by `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`). Meanwhile:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
```
reads `shop` purely from a header, with no cryptographic binding to the signed body. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) checks only `HmacValidator.validate(request)` and then immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)`, handing the unauthenticated `shop` value straight to the host application's handler.

Because HMAC(body) does not depend on the headers, any request whose body byte-for-byte matches a body that was legitimately signed by Shopify for the app's `client_secret` (e.g., one the attacker triggered for their own store, or any body an attacker can otherwise get signed/observed) will pass HMAC validation regardless of what `shop-domain`, `topic`, or `webhook_id` headers are sent alongside it. An attacker who controls the delivery of the HTTP request to the app's webhook endpoint (e.g., can replay or forge HTTP headers while keeping the exact signed body) can therefore present a genuinely-signed payload under an arbitrary spoofed `shop` (and `topic`/`webhook_id`), causing the host app to process/store data under another tenant's identity — a break of the shop-authenticated vs. shop-used-downstream binding described in the audit hint.

### Impact Explanation
This falls under the Critical bucket "cross-tenant access": the gem hands the host application a `shop` value in `WebhookMetadata` that carries no cryptographic guarantee of matching the actually-signed content, letting a bad actor with control of the outer HTTP request (headers) attribute Shopify-signed webhook data to any target shop it chooses, subject only to producing a matching signed body.

### Likelihood Explanation
Moderate: exploitation requires the attacker to be able to influence the transport-level headers of a request reaching the app before/at the point `Webhooks::Request` is constructed, while the raw body and its HMAC remain a validly-signed pair (e.g., attacker's own shop triggers a genuine webhook, and the attacker relays/replays the exact body+hmac to the endpoint with a different `shop-domain`/`topic` header, which the gem does nothing to prevent). The gem is the trust boundary that is supposed to bind `shop` to a verified request but does not.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material verified by `HmacValidator`, or otherwise cryptographically bind them to the body before trusting `request.shop`/`request.topic` in `Registry.process` and `WebhookMetadata`.

### Proof of Concept
1. Register an app and topic handler with `Registry.add_registration`.
2. Obtain a genuinely Shopify-signed webhook payload for shop A (`raw_body`, `x-shopify-hmac-sha256`).
3. Construct a new `Webhooks::Request.new(raw_body: <same raw_body>, headers: {..., "x-shopify-shop-domain" => "shop-b.myshopify.com", ...})` — same body/hmac, different shop header.
4. Call `Registry.process(request)`; `HmacValidator.validate` passes because it only checks the body, and the handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` even though the payload was never signed for shop B.
