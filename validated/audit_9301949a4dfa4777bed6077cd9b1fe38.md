### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook shop-spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-signing only the raw request body (`to_signable_string` returns `@raw_body`), while `shop` (and `topic`, `webhook_id`, `api_version`) are read directly from unauthenticated HTTP headers (`x-shopify-shop-domain` / `shopify-shop-domain`) and passed straight into `WebhookMetadata` and business logic without being bound to the HMAC.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` field [1](#0-0) . For webhooks, `to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop` is derived from the `shop-domain` header, entirely outside the signed material [3](#0-2) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the topic handler with `request.shop` as the tenant identifier: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) .

The identity binding broken is:
`shop_authenticated_by_hmac(raw_body) == shop_used_for_tenant_routing(header)` — these are not equal because the header is never part of the signed content.

An unprivileged actor who legitimately controls their own shop (e.g., installs the target app on a test/free store, or captures any webhook payload+HMAC combination sent to their endpoint) possesses a *valid* `(raw_body, hmac)` pair signed with the app's real `client_secret` — because Shopify itself computed and delivered that HMAC for their own shop's event. Since the header carrying `shop` is unauthenticated, the attacker can resend that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still passes (it only checks the body), and `Registry.process` will happily dispatch the handler with `shop: "victim-shop.myshopify.com"` attached to data that actually originated from the attacker's own shop.

### Impact Explanation
This crosses a tenant boundary: an app relying on this gem's webhook `shop` field to select the session/tenant record (a documented, intended usage pattern — see `WebhookMetadata` and the registry's `handle` call) can be made to apply the attacker's fabricated/attacker-controlled body under a victim shop's identity. Depending on the webhook topic, this can drive cross-tenant data corruption or unauthorized actions attributed to a different merchant's account/session — a cross-tenant access impact under the Critical category. The attack requires no secret material beyond one legitimate webhook delivery to a shop the attacker controls, which is trivially obtainable by installing the app themselves.

### Likelihood Explanation
Likelihood is High/Practical: any developer/tester can install the target Shopify app on a store they control and receive a genuine, correctly-signed webhook to replay against the app's endpoint with only the shop-domain header swapped. No brute forcing, credential theft, or privileged access is required — only a normal, unprivileged merchant relationship with the app.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-signed material, or otherwise cryptographically tie the shop identity to the signed body (e.g., include the shop domain in the canonical string that is HMAC-verified, consistent with how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop` in its signed payload [5](#0-4) ). At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted for tenant routing without independent verification (e.g., cross-checking against a known/expected shop for the session).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the delivered request: headers `x-shopify-topic`, `x-shopify-hmac-sha256`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, and raw JSON body `B`.
2. Attacker sends a new HTTP request to the app's webhook endpoint with the **same** `x-shopify-hmac-sha256` and body `B`, but with `x-shopify-shop-domain` header replaced by `victim-shop.myshopify.com`.
3. The app calls `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: headers)` then `Registry.process(request)`.
4. `HmacValidator.validate` succeeds because `to_signable_string` only checks `B` against the secret [2](#0-1) .
5. `Registry.process` dispatches `handler.handle(data: WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...))` [4](#0-3)  — the handler now believes attacker-controlled data belongs to the victim tenant.

        end
