### Title
Webhook `shop` identity is trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop` (tenant) identifier is read from an unsigned HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant context passed to the app's handler, without that value ever being covered by the signature. Since a Shopify app's webhook signing secret (`Context.api_secret_key`) is shared across all shops that install the app rather than being shop-specific, any merchant who has installed the app can replay a genuinely-signed webhook body with a forged `shop-domain` header naming a different (victim) shop, causing the host app to process the event under the wrong tenant.

### Finding Description
The identity binding that should hold is:

`shop authenticated by the HMAC == shop used as tenant context by the handler`

but the actual implementation breaks this equality.

`Webhooks::Request#to_signable_string` only returns the raw body: [1](#0-0) 

`Webhooks::Request#shop` is read straight from an attacker-controllable header, entirely outside of what is signed: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` compute and compare HMAC over `verifiable_query.to_signable_string` (i.e. the raw body) using `Context.api_secret_key`, a secret that is the same for every shop that installs a given app, not scoped per-shop: [3](#0-2) 

`Registry.process` validates the HMAC and, immediately after, forwards `request.shop` — the unauthenticated header value — as the tenant identity to the webhook handler: [4](#0-3) 

Because the shared client secret lets any installed merchant produce a validly-signed webhook body (by simply receiving a real webhook delivery for their own store), and because the `shop` header carrying tenant identity is not part of the signed material, an attacker can take a legitimately-signed `(raw_body, hmac)` pair issued to their own shop and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to point at a victim shop. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` dispatches the handler believing the event belongs to the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: the app's webhook handler executes under the assumption that `request.shop` is trustworthy Shopify-asserted tenant context (as documented in `docs/usage/webhooks.md`, where `Registry.process` is fed directly from request headers), but that field carries no cryptographic binding to the signed payload. Depending on how a host app implements its webhook handlers (e.g. selecting a session/access token by `shop`, or handling mandatory GDPR topics like `customers/redact` / `shop/redact`), this can lead to actions or data being attributed to the wrong merchant, i.e. cross-tenant access — a Critical-severity impact per the specified impact taxonomy.

### Likelihood Explanation
Likelihood is realistic for an "unprivileged internet user" who is simply a merchant that has installed the target app (no special privileges beyond normal installation): they naturally receive real webhook deliveries with valid `(body, hmac)` pairs for their own shop, and can freely replay that exact HTTP body/HMAC pair to the app's public webhook endpoint while substituting the `shop-domain` header. No possession of `api_secret_key` or any other tenant's credentials is required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed material, or otherwise cryptographically bind `request.shop` to the verified payload before it is handed to handlers — e.g., verify that the `shop` header matches a shop-scoped secret, or require the host application to independently corroborate `shop` against a known/installed-shop list before trusting it as tenant context in `Registry.process`.

### Proof of Concept
1. Merchant A installs the app and triggers a webhook event on their own store (e.g. `orders/create`), capturing the raw request body `B` and the resulting `X-Shopify-Hmac-Sha256` header `H` (valid because it is signed with the app's shared `client_secret`).
2. Merchant A sends a forged HTTP POST to the app's webhook endpoint with:
   - Body: `B` (unmodified)
   - Header `X-Shopify-Hmac-Sha256`: `H` (unmodified, still valid since only `B` is signed)
   - Header `X-Shopify-Shop-Domain`: `victim-shop.myshopify.com` (changed)
3. The host app constructs `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` and calls `ShopifyAPI::Webhooks::Registry.process(request)`.
4. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `B` against `H`.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, causing the app to process Merchant A's forged event as if it originated from the victim shop.
