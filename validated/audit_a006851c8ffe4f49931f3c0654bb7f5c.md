### Title
Unmetered Computational Cost in `pallet_state_coprocessor::handle_unsigned` Enables Free Resource-Exhaustion via Oversized `GetRequestsWithProof` Batches - ([File: modules/pallets/state-coprocessor/src/lib.rs])

### Summary
`pallet_state_coprocessor::Pallet::handle_unsigned` is dispatched as an unsigned, fee-less extrinsic (`ensure_none`) with a fixed, content-independent weight of `DbWeight::get().reads_writes(1, 2)`. The message body, `GetRequestsWithProof`, carries an unbounded `Vec<GetRequest>` and each `GetRequest` carries an unbounded `keys: Vec<Vec<u8>>`. `handle_get_requests` iterates every request and, for each, performs full storage-trie proof verification (decoding and walking a Merkle-Patricia trie, cloning proof data) before any bandwidth accounting occurs. This mirrors the CVE-2019-12420 pattern: a single crafted "message" (here, a crafted unsigned extrinsic/proof batch) drives the node to perform work far exceeding the resource cost the fee/weight model assumes, at zero cost to the submitter.

### Finding Description
`GetRequestsWithProof` is decoded from an unsigned extrinsic anyone can submit: [1](#0-0) 

The dispatchable is registered with a fixed weight that does not scale with `requests.len()` or the number of keys inside each request: [2](#0-1) 

`handle_get_requests` then loops over every `GetRequest` in the batch and, per request, calls `verify_state_proof`, which decodes the supplied trie proof and rebuilds a `TrieDB` to look up every key — real cryptographic/computational work proportional to `requests.len() * avg(keys.len())` and to the size of the attacker-supplied proof blob: [3](#0-2) 

The per-app bandwidth metering — the only mechanism that limits how much data an app can push through this path — is explicitly applied *after* proof verification has already run, as the code comments state: [4](#0-3) 

Neither `GetRequest.keys` nor the request batch itself is bounded anywhere in the wire type or dispatch path: [5](#0-4) 

The `validate_unsigned` implementation for this pallet performs the same unbounded verification work again during mempool validation, before the transaction is even included in a block, and does not reject on request/key count: [6](#0-5) 

Because `pallet-ismp`/`pallet-state-coprocessor` treat these as unsigned, free-of-transaction-fee calls (a documented design choice — "all cross-chain messages received are executed for free as unsigned transactions"), the only anti-spam guard is the weight-based `ValidTransaction` and the fixed `#[pallet::weight]` annotation, neither of which scales with the actual verification cost incurred. An attacker (a "message dispatcher"/relayer with no special privilege — anyone can submit `handle_unsigned` extrinsics with self-fabricated `GetRequest` batches and arbitrarily large/garbage trie proof blobs, since the requests only need to reference an unknown/timed-out request to eventually fail, but not before the expensive proof-decoding/trie-walk work is done) can repeatedly submit oversized batches to burn Hyperbridge collator/validator CPU time cheaply relative to the actual cost imposed, without paying gas/fees proportional to that cost.

### Impact Explanation
This is a computational resource-exhaustion vector reachable from a single unsigned, unprivileged, dispatched extrinsic (analogous to a "crafted message" in the SpamAssassin CVE). Repeated submission can degrade block production / transaction-pool validation throughput for the Hyperbridge relay chain, constituting a denial-of-service against the message-delivery route (a route unable to deliver messages) rather than a low/no-impact issue, since it targets the core cross-chain message-processing pipeline used by every relayer and application on the network.

### Likelihood Explanation
Likelihood is high for an adversary willing to spend engineering effort: the attack requires only crafting `GetRequestsWithProof` messages with many requests/keys and large (even garbage, since decoding failure only occurs after significant work) trie-proof blobs, and submitting them as unsigned transactions — a capability available to any network participant, with no relayer allowlist or fee gate blocking it.

### Recommendation
- Make the extrinsic weight for `pallet_state_coprocessor::handle_unsigned` (and the equivalent `pallet_ismp::handle_unsigned`) a function of the actual decoded message size: number of requests, total number of keys, and size of the proof blob, rather than a fixed constant.
- Enforce hard upper bounds on `GetRequestsWithProof::requests.len()` and per-request `GetRequest::keys.len()` (and total proof byte size) at the very start of `handle_get_requests` and in `validate_unsigned`, before any trie decoding/verification is attempted.
- Move (or duplicate a cheap pre-check version of) the bandwidth-gate accounting to run before proof verification, so unmetered work cannot be performed ahead of the gate rejecting the batch.

### Proof of Concept
1. Craft a `GetRequestsWithProof` where `requests` contains many `GetRequest`s, each with a large `keys: Vec<Vec<u8>>` (e.g., thousands of 52-byte keys), and `response.proof` containing a large but syntactically valid (or partially valid) SCALE-encoded `StateMachineProof` with numerous trie nodes.
2. Submit this as `pallet_state_coprocessor::Call::handle_unsigned { message }` via an unsigned transaction, as done in [7](#0-6) .
3. Observe that `validate_unsigned`/`handle_get_requests` performs full `TrieDBBuilder` construction and per-key lookups for the entire batch (see `verify_state_proof` in `modules/ismp/state-machines/substrate/src/lib.rs:240-281`) before any size- or bandwidth-based rejection, while the dispatchable's declared weight remains the fixed `reads_writes(1, 2)`.
4. Repeating this with maximally sized batches within the extrinsic length limit demonstrates computational cost far exceeding the weight fee charged, at zero net cost to the submitter (unsigned, free dispatch).

	impl<T: Config> ValidateUnsigned for Pallet<T>
	where
		T::AccountId: AsRef<[u8]>,
		<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		<T as pallet_ismp::Config>::Balance: Into<u128>,
	{
		type Call = Call<T>;

		// empty pre-dispatch so we don't modify storage
		fn pre_dispatch(_call: &Self::Call) -> Result<(), TransactionValidityError> {
			Ok(())
		}

		fn validate_unsigned(_source: TransactionSource, call: &Self::Call) -> TransactionValidity {
			let Call::handle_unsigned { message } = call else {
				return Err(TransactionValidityError::Invalid(InvalidTransaction::Call));
			};

			if let Err(err) = Self::handle_get_requests(message.clone()) {
				log::error!(target: "ismp", "{:?}", err);
				return Err(TransactionValidityError::Invalid(InvalidTransaction::Call));
			}

			let mut messages = message
				.requests
				.iter()
				.map(|get| hash_request::<<T as Config>::IsmpHost>(&Request::Get(get.clone())))
				.collect::<Vec<_>>();
			messages.sort();

			// this is so we can reject duplicate batches at the mempool level
			let msg_hash = sp_io::hashing::keccak_256(&messages.encode()).to_vec();

			Ok(ValidTransaction {
				priority: 100,
				requires: vec![],
				provides: vec![msg_hash],
				longevity: 25,
				propagate: true,
			})
		}
	}
