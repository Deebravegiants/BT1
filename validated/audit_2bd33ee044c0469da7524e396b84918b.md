### Title
Webhook `shop-domain` header is trusted for tenant identification without being bound to the HMAC signature, enabling cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands the handler a `WebhookMetadata` struct whose `shop` field is read from the unauthenticated `x-shopify-shop-domain` HTTP header. The HMAC never covers the shop identity, so any valid `(raw_body, hmac)` pair can be replayed with an arbitrary `shop` header and will still pass validation, letting an attacker who controls one legitimate app installation cause the host app to process webhook data under a different tenant's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e. the body) and compares it with the received `hmac`: [3](#0-2) 

`Registry.process` gates on that body-only HMAC check and then constructs `WebhookMetadata` using `request.shop`—the unauthenticated header value—as the tenant identifier passed to the app's handler: [4](#0-3) 

The identity binding that should hold is:
`shop_bound_by_hmac == shop_used_by_handler`

but the gem actually implements:
`hmac_verifies(body) AND shop_used_by_handler = header["shop-domain"]` (unbound)

Because the `shop` value is never covered by the signature, the two sides diverge whenever the header is altered independently of the body — which is exactly the "field acted on but not covered by the HMAC" pattern.

### Impact Explanation
An attacker who is a legitimate merchant of the same multi-tenant app receives real webhook deliveries from Shopify addressed to their own shop, each with a valid `(raw_body, hmac)` pair signed with the app's shared `client_secret`. Because the shop identity is not part of the signed payload, the attacker can resend that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting `x-shopify-shop-domain` for a victim shop. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` forwards `shop: request.shop` (the attacker-controlled victim value) to the app's `WebhookHandler#handle`. Any host app that uses `data.shop` to select which tenant's record to update (a documented, intended usage pattern per this gem's own docs) will act on the wrong tenant — e.g. applying the attacker's own webhook payload (or a captured mandatory `customers/redact`/`shop/redact` payload) against a different shop's stored data. This crosses a tenant boundary using only the identity binding gap in this gem, matching the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Likelihood is bounded by the precondition that the attacker must be able to obtain at least one valid `(body, hmac)` pair for the shared app secret — trivially available to any merchant who installs the app themselves (an unprivileged, self-service action requiring no special access, credentials, or social engineering). From there, forging the header is a simple unauthenticated HTTP request to the app's own webhook callback endpoint; no `api_secret_key`, access token, or admin role is required.

### Recommendation
Bind the shop identity to the authenticated bytes: include the `shop` (and ideally `topic`/`api-version`) in the HMAC signable string, or otherwise cryptographically bind the header to the request before trusting it as a tenant key. At minimum, `ShopifyAPI::Webhooks::Request#to_signable_string` should not diverge from the fields exposed to handlers as tenant identifiers, and the gem's documentation should explicitly warn implementers that `data.shop` is not authenticated by the HMAC check performed by `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook delivery, e.g. body `{"id":123}` with header `x-shopify-hmac-sha256: <valid-hmac-for-body>` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the identical request to the app's registered webhook endpoint but changes only `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (the unchanged body) and succeeds: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: {"id":123}, ...)` and processes the attacker's payload as if it belonged to `victim.myshopify.com`: [6](#0-5)
