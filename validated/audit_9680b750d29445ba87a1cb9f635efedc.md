### Title
Webhook `shop`, `topic`, `webhook_id` and `api_version` headers are not covered by HMAC verification, allowing cross-tenant header spoofing on an otherwise validly-signed webhook - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts several other header-derived fields — most importantly `shop` — that are never included in the signed material. This breaks the intended identity binding: `hmac_valid(body) == true` is treated as proof that `(shop, topic, webhook_id, api_version)` are also authentic, when in fact only `body` is authenticated.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines the signable string as the raw body only: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read from separate, unsigned HTTP headers: [2](#0-1) 

`Registry.process` verifies only the HMAC of the body, and then forwards `request.shop` (and the other header-derived fields) straight into `WebhookMetadata`, which is handed to the app's webhook handler as the trusted tenant identity for the event: [3](#0-2) [4](#0-3) 

Because `HmacValidator.validate` only proves that the *body* bytes are unmodified from what was HMAC'd with `Context.api_secret_key`: [5](#0-4) 

the equality the library implicitly promises to the host application — `hmac_valid(request) == true` implies `request.shop == the tenant that generated this payload` — does not hold. The `shop` (and `topic`/`webhook_id`) fields are "acted on but not covered by the HMAC," exactly the class of binding failure called out in the analog rules. Any party capable of submitting a POST to the app's webhook endpoint with a body/HMAC pair (e.g., replaying a webhook payload legitimately received for their own shop, since HMAC-only bodies for common Shopify topics can be near-identical or attacker-shaped in some payload fields) can attach an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header value while keeping the body's HMAC valid, since the header is never part of `to_signable_string`.

### Impact Explanation
This is a cross-tenant identity confusion at the library's trust boundary: the one piece of data (`shop`) that host applications rely on to route/attribute webhook data to a tenant is not bound to the cryptographic proof of authenticity. In a multi-tenant app this can lead to a merchant's data being written against another merchant's session/shop (cross-tenant data corruption or disclosure), since `WebhookMetadata#shop` is the only tenant identifier the gem hands to the `WebhookHandler#handle` callback and it carries no origin guarantee beyond "some entity that could produce this raw body." This matches the report's underlying theme — an operation is trusted/executed based on an unauthenticated or under-authenticated identity field.

### Likelihood Explanation
Requires only unprivileged network access to the app's publicly reachable webhook endpoint plus a legitimately-obtained (body, hmac) pair — e.g., from the attacker's own installed/trial shop, or from any previously observed webhook delivery (webhooks are sent over HTTPS but the endpoint is a normal internet-exposed URL, and header manipulation via direct HTTP tooling is trivial once any valid body/hmac pair is known). No access to `api_secret_key`, access tokens, or the merchant's session is required, so this is within scope as an unprivileged-internet-user analog.

### Recommendation
Bind the tenant/topic identity to the HMAC-protected material: include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or otherwise verify them against a value derived from the authenticated body/channel), or require the host application to independently confirm the `shop` header against a known/expected value (e.g., a per-webhook shared secret to shop mapping) rather than trusting it implicitly once `HmacValidator.validate` passes.

### Proof of Concept
1. Attacker has a legitimate raw webhook body and its valid `x-shopify-hmac-sha256` value (e.g., from their own free-trial shop's `orders/create` webhook, or any previously captured Shopify webhook delivery).
2. Attacker POSTs the same `raw_body` and the same `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and, if desired, a different `x-shopify-topic`/`x-shopify-webhook-id`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body` — it passes.
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built using the attacker-supplied `shop`/`topic` header values and delivered to the app's `WebhookHandler#handle`, causing the host app to process/attribute the webhook payload against `victim-shop.myshopify.com` despite the payload never having been signed for that shop.           raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
