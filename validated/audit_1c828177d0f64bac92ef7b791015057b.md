### Title
Saturating scaled-cap conversion silently disables the spoke supply/borrow cap when `cap * RAY / index` exceeds `i128` - ([File: contracts/controller/src/spoke_usage.rs])

### Summary
`enforce_spoke_cap` converts the asset-unit cap into RAY-scaled units with `calculate_scaled_cap`, which deliberately *saturates* to `i128::MAX` instead of reverting when `cap_ray * RAY / index` overflows. Because the comparison is `next_scaled <= cap_scaled`, a saturated `cap_scaled = i128::MAX` makes the cap check vacuously true: any unprivileged caller can exceed the configured spoke supply/borrow cap through `supply` / `borrow` whenever the index is small enough relative to `RAY`. This mirrors CVE-2015-7854's class — a crafted oversized numeric input bypassing a bounds check due to overflow during conversion.

### Finding Description
`common/src/rates/scaling.rs:26-33` computes the scaled cap as:

```rust
pub fn calculate_scaled_cap(env: &Env, cap: i128, decimals: u32, index: Ray) -> Ray {
    Ray::from(fp_core::mul_div_floor_saturating(
        env, Ray::from_asset(env, cap, decimals).raw(), RAY, index.raw(),
    ))
}
```

`mul_div_floor_saturating` (`common/src/math/fp_core.rs:180-201`) returns `i128::MAX` on overflow rather than panicking. `enforce_spoke_cap` (`contracts/controller/src/spoke_usage.rs:144-157`) then asserts `next_scaled <= cap_scaled`, so a saturated cap is never exceeded.

`require_cap_within_asset_domain` (`common/src/validation.rs:61-70`) only bounds `cap * 10^(27-d) ≤ i128::MAX`; it does not bound `cap_ray * RAY / index`. Whenever `index < RAY` — e.g. after a bad-debt supply-index write-down floors the supply index (`SUPPLY_INDEX_FLOOR_RAW` is referenced in `common/tests/rates/scaling.rs`) — the product `cap_ray * RAY` can exceed `i128::MAX` even though `cap_ray` itself fits, because `RAY / index > 1`. For caps near `max_cap_for_decimals(d)`, overflow begins as soon as `index < RAY` by roughly a factor `i128::MAX / cap_ray`, which is on the order of a few percent of RAY for realistic caps. The saturating path is reachable for any spoke asset whose cap was configured near the domain maximum and whose index has drifted below `RAY`; the code comments explicitly state the design "fails open rather than trapping an entry path."

### Impact Explanation
Once `cap_scaled` saturates, `enforce_spoke_cap` admits arbitrarily large `delta_scaled`. An unprivileged attacker calling `controller.supply` can push the spoke's tracked `supplied_scaled_ray` far beyond the governance-configured cap, minting supply shares uncapped collateral. With collateral LTV applied to that oversized position, `borrow`/`multiply`/`flash_position` can draw more from the hub pool than risk parameters intended, producing protocol insolvency / theft of user funds when the position is unwound or liquidated at unfavorable terms. The cap exists precisely to bound per-spoke exposure; the saturated conversion removes that bound entirely rather than failing closed.

### Likelihood Explanation
Reachable by a single unprivileged address via `supply` (or `borrow` for the borrow side) once `index < RAY` and `cap_ray * RAY > i128::MAX`. Supply indexes can be written below `RAY` by bad-debt write-downs (dust cleanup / `clean_bad_debt`), and caps near `max_cap_for_decimals` make the overflow band wide. No privileged action is required at attack time; the precondition depends only on stored index/cap state.

### Recommendation
Replace `mul_div_floor_saturating` in `calculate_scaled_cap` with the reverting `mul_div_floor` (raise `MathOverflow`), or clamp the comparison by checking `next_scaled <= cap_scaled` **and** `unscale(next_scaled, index, decimals) <= cap` on the asset side. Alternatively, validate at listing that `cap_ray * RAY / min_possible_index` fits `i128` (i.e., bound caps against `SUPPLY_INDEX_FLOOR_RAW`, not just `RAY_DECIMALS` scaling).

### Proof of Concept
1. Governance lists an asset with `supply_cap = max_cap_for_decimals(d)` (permitted by `require_cap_within_asset_domain`).
2. Bad-debt cleanup writes the spoke supply index below `RAY` (e.g. to `SUPPLY_INDEX_FLOOR_RAW`).
3. Attacker calls `controller.supply(spoke, asset, amount)` with `amount` exceeding `supply_cap`.
4. `enforce_spoke_cap` computes `cap_scaled = mul_div_floor_saturating(cap_ray, RAY, index)` → `cap_ray * RAY` overflows `i128` → `cap_scaled = i128::MAX` → `assert next_scaled <= cap_scaled` passes for any `next_scaled`.
5. The over-cap supply mints shares; attacker borrows against the oversized collateral.

Caveat: I verified the saturation path and the cap-comparison logic, but did not fully confirm within available context that stored supply indexes reach values low enough for realistic caps to trigger the overflow; if all caps are configured far below `max_cap_for_decimals` and the index floor stays close to `RAY`, the overflow band may be unreachable in practice.
