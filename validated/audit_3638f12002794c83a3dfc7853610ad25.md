### Title
Webhook HMAC only signs the raw body; `shop`, `topic`, `webhook_id`, and `api_version` are unauthenticated and can be forged - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook exclusively via `Utils::HmacValidator.validate(request)`, which only signs `request.to_signable_string`. In `Request`, `to_signable_string` returns solely `@raw_body`; every other identity-bearing field the handler consumes — `shop`, `topic`, `webhook_id`, `api_version` — is read straight from HTTP headers that are never part of the signed material.

### Finding Description
`Utils::HmacValidator.validate` computes an HMAC over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [1](#0-0) 

For webhook requests, `to_signable_string` is defined to be just the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` come from separate, unsigned headers: [2](#0-1) 

`Registry.process` performs the HMAC check, then immediately uses the unauthenticated `request.topic` for handler dispatch and `request.shop` for the metadata handed to the application's handler: [3](#0-2) 

The equality this HMAC is supposed to enforce is: `hmac == HMAC(secret, entire_authenticated_request)`. In practice it only enforces `hmac == HMAC(secret, raw_body)`. Any `(raw_body, hmac)` pair that was ever valid for *any* shop/topic (e.g., one the attacker obtained by installing the app on their own store, or from any other webhook delivery visible to them) remains valid forever with `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, and `x-shopify-api-version` replaced arbitrarily, since none of those headers feed into `to_signable_string`. This breaks the binding "the shop/topic acted on == the shop/topic the signature attests to."

### Impact Explanation
An unprivileged internet user who can reach the app's public webhook endpoint (a normal HTTP route, as documented) and who has captured a single legitimate `(raw_body, hmac)` pair — trivially obtainable by installing the target app on their own store and letting Shopify deliver one webhook to them — can replay that exact body+signature while substituting the `shop-domain` header for a victim shop, and/or the `topic`/`webhook_id` headers for a different topic. `HmacValidator.validate` still returns `true` because only the body is checked, so `Registry.process` will call the merchant's registered handler with `WebhookMetadata` claiming the body came from the victim shop / a different topic than it actually did. Any host application logic that trusts `WebhookMetadata#shop` or `#topic` to scope database writes, fulfil orders, or select which tenant's data/session to act on will now execute cross-tenant, attacker-influenced business logic — this is a tenant-identity-binding bypass with cross-tenant impact.

### Likelihood Explanation
Requires the attacker to have obtained at least one valid `(body, hmac)` pair, which is straightforward: install the app for free/trial on an attacker-controlled shop, capture the resulting webhook delivery, then replay it against the same public endpoint with forged shop/topic headers. No credentials, `api_secret_key`, or access tokens are needed.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the signable material for webhook requests, or otherwise cryptographically bind them to the body before dispatch — e.g., extend `Request#to_signable_string` to concatenate these header values with the raw body (in a canonical, unambiguous encoding) so `HmacValidator` authenticates the full identity tuple, not just the payload bytes.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers for a webhook topic the app handles (e.g. `orders/create`). Shopify delivers a webhook with a valid `x-shopify-hmac-sha256` computed over the JSON body.
2. Attacker captures `raw_body` and `hmac` from this legitimate delivery.
3. Attacker POSTs to the app's public webhook endpoint with the *same* `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or a different `x-shopify-topic`/`x-shopify-webhook-id`).
4. `ShopifyAPI::Webhooks::Registry.process` builds `Request` from these headers/body; `HmacValidator.validate` passes because `to_signable_string` only checks `raw_body`, which is unchanged and correctly signed.
5. The app's handler is invoked with `WebhookMetadata.new(topic: <attacker-chosen>, shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)`, causing the host app to act as if this data originated from the victim tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
