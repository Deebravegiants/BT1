Audit Report

## Title
Missing slippage protection (`amount_out_min = None`) in `swap_and_burn` allows front-running/sandwich attacks on tip-asset-to-Ether swaps - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

## Summary
`Pallet::swap_and_burn` in the `snowbridge-pallet-system-frontend` pallet swaps a caller-supplied tip asset into Ether via `T::Swap::swap_exact_tokens_for_tokens` but hardcodes `amount_out_min` to `None`, disabling the slippage-floor check that `pallet-asset-conversion` otherwise enforces. This function is reachable by any signed account through the public `add_tip` extrinsic, which passes an arbitrary attacker-supplied `Asset` (id + amount) directly into the swap path.

## Finding Description
`swap_and_burn` calls `T::Swap::swap_exact_tokens_for_tokens(..., None, ...)`, explicitly disabling the minimum-output guard: [1](#0-0) 

This is reached from `swap_fee_asset_and_burn`, which is invoked by the `add_tip` extrinsic — a call open to any `ensure_signed` origin, with a fully caller-controlled `asset` (fee asset id and amount): [2](#0-1) [3](#0-2) 

In `pallet-asset-conversion`, `do_swap_exact_tokens_for_tokens` only enforces the minimum-output check when `amount_out_min` is `Some`; when `None`, no floor is applied and the swap proceeds at whatever price the pool currently offers: [4](#0-3) 

Pools in `pallet-asset-conversion` are permissionlessly created via `do_create_pool`, with the initial price ratio fully determined by whoever adds the first liquidity, and reserves are otherwise vulnerable to within-block sandwich manipulation absent a min-out guard: [5](#0-4) 

The exploit path is concrete and reachable by an unprivileged user: (1) attacker observes a pending `add_tip` extrinsic for a tip asset with no or thin liquidity against Ether, (2) attacker pre-creates/skews the pool or sandwiches the swap within the same block, (3) the victim's `swap_and_burn` call executes at the manipulated price with zero protection since `amount_out_min` is hardcoded `None`, (4) the resulting near-worthless `ether_gained` is burned/teleported, destroying the value of the tip and degrading the relayer incentive it was meant to fund.

## Impact Explanation
An attacker-manipulated or newly-created skewed pool can drive the Ether amount received from the swap arbitrarily close to zero, causing the user's tip asset to be effectively destroyed with negligible resulting Ether burned/teleported for the cross-chain relayer reward. This is an in-scope Substrate/Snowbridge pallet defect — a broken accounting/pricing assumption in production dispatchable code, not a node/relayer/governance-only issue, and directly affects any unprivileged user calling `add_tip`.

## Likelihood Explanation
The attack is triggerable by any signed account without special privileges, since `add_tip` takes an arbitrary `Asset` and is not gated by an allowlist of tip assets in the pallet itself. Feasibility depends on the tip asset not already being Ether and either (a) no pool existing yet for asset/Ether (attacker front-runs pool creation with a skewed ratio) or (b) an existing pool with insufficient liquidity to resist single-block sandwich manipulation — both realistic conditions for less-common or newly-registered tip assets.

## Recommendation
Compute a reasonable `amount_out_min` (e.g., via `QuotePrice::quote_price_exact_tokens_for_tokens` with an acceptable tolerance, or an oracle-derived bound) before calling `swap_exact_tokens_for_tokens` in `swap_and_burn`, and pass `Some(min_out)` instead of hardcoding `None`, so the swap reverts if pool pricing deviates beyond an acceptable threshold.

## Proof of Concept
1. Attacker monitors the tx pool for a pending `add_tip(message_id, asset)` call where `asset` is a token with no or thin liquidity paired against Ether in `pallet-asset-conversion`.
2. Attacker front-runs by calling `create_pool`/`add_liquidity` to establish or skew the `asset`/Ether pool ratio drastically in the attacker's favor.
3. The victim's `add_tip` executes, invoking `swap_fee_asset_and_burn` → `swap_and_burn` → `swap_exact_tokens_for_tokens(..., None, ...)`, receiving near-zero Ether at the manipulated rate (confirmed by the code at `bridges/snowbridge/pallets/system-frontend/src/lib.rs` lines 301-308 and the unguarded path in `substrate/frame/asset-conversion/src/lib.rs` lines 987-1002).
4. Attacker reverses the pool skew (removes liquidity/swaps back) to extract the value taken from the victim's tip.

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}
