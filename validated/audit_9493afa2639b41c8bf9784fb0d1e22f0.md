### Title
POA Bridge withdrawal status/txHash misreported when a batch contains multiple withdrawals of the same asset - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves a withdrawal's on-chain status/txHash by matching only on `assetId`, ignoring `destinationAddress`, `amount`, and batch `index`. When a batch (`WithdrawalParams[]`) contains two or more withdrawals of the same token, the SDK reports the *same* status/txHash for all of them, regardless of which one actually settled.

### Finding Description
`findMatchingWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` picks the first entry in the (unsorted) API response array whose `near_token_id` matches the requested `assetId`: [1](#0-0) 

This is invoked from `describeWithdrawal`, which returns that single matched withdrawal's `status`/`txHash` as the result for the given `WithdrawalIdentifier`: [2](#0-1) 

The code comment itself acknowledges the flaw: "multiple withdrawals of the same token in a single transaction are not supported" [3](#0-2) . In the batch/orchestrated path (`sdk.ts`'s `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises`), each withdrawal in a batch gets its own `WithdrawalIdentifier` (including `index`) via `createWithdrawalIdentifiers`, but `PoaBridge.describeWithdrawal` never consults `index` — it only reuses `assetId` for matching. If a caller submits, in one batch, two withdrawals of the same `assetId` (e.g., same token, two different destination addresses/amounts — a completely normal, unprivileged usage pattern, not requiring any malicious actor), both `describeWithdrawal` calls query the same underlying tx status list and both resolve to whichever single entry `Array.prototype.find` returns first for that `assetId`.

The equality this breaks: "status reported == the on-chain outcome for *this specific* withdrawal." Instead, the reported status/txHash can belong to a *different* withdrawal within the same batch.

### Impact Explanation
If withdrawal #1 (say, sent to address A) has settled but withdrawal #2 (same asset, sent to address B) has not, an integrator awaiting completion of #2 can be told `{status: "completed", txHash: <hash belonging to #1's transfer>}`. This is a "status or hash misreport making an integrator credit or refund twice" scenario (per the High severity bucket): the integrator may treat withdrawal #2 as delivered to B when the funds actually never left for B (or landed for A), potentially double-crediting or releasing downstream funds prematurely. Conversely it can also cause withdrawal #1 to be reported "pending" indefinitely if the found entry happens to correspond to #2's still-pending record, causing operational/stuck-funds effects.

### Likelihood Explanation
Triggering this only requires an ordinary caller building a batch of `WithdrawalParams[]` that includes two entries with the same `assetId` (e.g., withdrawing the same token to two different addresses in one call) — a supported, documented SDK batch feature, not privileged or adversarial. Given POA bridge is one of the actively used bridges (`.omft.near` NEP-141 tokens) and batch withdrawal APIs (`waitForWithdrawalCompletion`, `createWithdrawalCompletionPromises`) exist precisely to support multi-withdrawal batches, this is readily reachable in normal integrator usage.

### Recommendation
`findMatchingWithdrawal` must disambiguate withdrawals with identical `assetId` using additional fields returned by the POA status API (e.g., destination address/memo and/or amount) in combination with `index`-based ordering, or the POA bridge API must be extended to return a per-withdrawal correlation id that the SDK can match against. Until such disambiguation is added, the SDK should either reject/flag batches containing duplicate-`assetId` POA withdrawals, or explicitly document and surface this limitation as an error rather than silently returning a possibly-wrong status for one of the withdrawals.

### Proof of Concept
1. Caller submits `sdk.processWithdrawal({ withdrawalParams: [ {assetId: "nep141:usdc.omft.near", amount: 100n, destinationAddress: "0xA...", feeInclusive:false}, {assetId: "nep141:usdc.omft.near", amount: 200n, destinationAddress: "0xB...", feeInclusive:false} ] })`, producing a single NEAR tx with two POA `ft_withdraw` intents.
2. The POA bridge backend processes withdrawal to `0xA` first and settles it while withdrawal to `0xB` is still pending.
3. SDK calls `describeWithdrawal` for index 1 (destined for `0xB`). `getWithdrawalStatusWithRetry` returns both withdrawal records (unsorted); `findMatchingWithdrawal(withdrawals, "nep141:usdc.omft.near")` returns whichever record appears first in the array — potentially the completed one destined for `0xA`.
4. The caller/integrator sees `{status: "completed", txHash: <0xA's tx>}` for what it believes is the `0xB` withdrawal, and credits/acts on withdrawal #2 as if it were delivered, while in reality `0xB`'s transfer may still be pending or may go to a different result entirely.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
