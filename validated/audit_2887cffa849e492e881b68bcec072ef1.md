### Title
Webhook shop/topic/webhook_id/api_version headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, then dispatches the handler using the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers — none of which are included in the HMAC-signed payload. This breaks the identity binding `shop authenticated == shop the data is attributed to`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from attacker-controllable HTTP headers, independent of the HMAC: [2](#0-1) 

`Registry.process` validates only the body's HMAC and then trusts these unauthenticated header-derived fields to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

Because every shop that installs the same app shares the same `client_secret` for HMAC signing (this is how Shopify webhook HMACs work — the secret is per-app, not per-shop), any merchant who legitimately installs the app receives real webhooks with a body and HMAC signed by that shared secret. That merchant (an "unprivileged internet user" relative to other tenants of the same app) can capture their own valid `(raw_body, hmac)` pair and replay it to the app's public webhook endpoint while forging the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, and `shopify-api-version` headers to any values they choose (including another tenant's shop domain). `Utils::HmacValidator.validate(request)` will still pass because it only checks the raw body against the shared secret: [4](#0-3) 

The equality that should hold is: `shop the HMAC authorizes == shop the handler attributes the payload to`. In this design, the left side is undefined (HMAC covers only body bytes) while the right side is attacker-supplied header data, so the binding is broken.

### Impact Explanation
A malicious tenant of a multi-tenant app can forge webhook events that appear to originate from a different, victim shop, by replaying their own genuinely-signed webhook body with spoofed identity headers. Depending on what the host app's webhook handler does with `shop` (e.g., look up/update a merchant record, trigger data sync, or write attacker-controlled body content attributed to the victim's shop), this results in cross-tenant data corruption/confusion — data ostensibly from one merchant's store being processed and stored against another merchant's store record. This matches the "cross-tenant access" Critical impact criterion.

### Likelihood Explanation
Requires only that the attacker be a legitimate (even free/trial) installer of the target app — a low bar, matching "unprivileged internet user" — and knowledge of the target shop's `.myshopify.com` domain (typically public/derivable). No access to the app's `client_secret`, access tokens, or the victim's credentials is needed; the attacker only needs one genuine webhook delivery to their own shop to replay with modified headers.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the material that is verified, or otherwise cross-check the header-derived `shop` against a trusted, out-of-band value (e.g., the shop for which the specific webhook subscription was registered) before dispatching to handlers. At minimum, document prominently that `request.shop`/`topic`/etc. are unauthenticated and must not be trusted as tenant identity without additional verification (e.g., correlating against the app's own webhook registration records instead of trusting the header verbatim).

### Proof of Concept
1. App `X` is installed by attacker's own shop `attacker.myshopify.com` and by victim shop `victim.myshopify.com`, both webhooks signed with the same app `client_secret`.
2. Shopify delivers a genuine webhook to attacker for their own shop: body `B`, header `shopify-hmac-sha256: H` (valid HMAC of `B`), header `shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the identical `POST` to the app's shared webhook endpoint, keeping body `B` and header `shopify-hmac-sha256: H` unchanged, but sets `shopify-shop-domain: victim.myshopify.com` (and optionally forges `shopify-topic`/`shopify-webhook-id`).
4. `Utils::HmacValidator.validate(request)` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) succeeds because it only checks `B` against `H`.
5. `handler.handle` receives `shop: "victim.myshopify.com"` with attacker-controlled body `B`, causing the app to process/store the attacker's data as if it came from the victim's shop.
