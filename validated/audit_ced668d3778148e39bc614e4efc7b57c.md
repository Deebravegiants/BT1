Confirmed: `CallDispatcher` at [1](#0-0)  is a single shared, stateless-relay contract with no access control on `dispatch()` — anyone can call it, and its `receive()` accepts arbitrary ETH/token deposits from any caller. It is passed as `_params.dispatcher`, the same address for every order on a given `IntentGatewayV2` deployment.

### Title
Balance-delta escrow sizing in `IntentGatewayV2.placeOrder` predispatch path trusts whatever balance sits on the shared `CallDispatcher`, allowing donation-inflated/free escrow credit - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder`'s predispatch branch sizes each escrowed input by reading the *balance* of the shared `CallDispatcher` contract before and after sweeping it to the gateway, rather than verifying the value actually originated from that specific caller's predispatch assets in that transaction [2](#0-1) . This mirrors the root cause of the Projekt incident: a permissionless code path that sizes a credited value from a balance snapshot/delta on a shared account, rather than from a verified, attributable transfer, letting a party count value it didn't itself deposit.

### Finding Description
In the non-predispatch path, `placeOrder` correctly measures the delta immediately around its own `safeTransferFrom` call, so nothing else can intervene [3](#0-2) .

In the predispatch path, however:
1. `_params.dispatcher` is `CallDispatcher`, a permissionless, unauthenticated relay whose `dispatch()` can be called by *anyone*, and whose `receive()` accepts value from anyone [4](#0-3) .
2. `placeOrder` snapshots `balancesBefore[i]` as `IERC20(token).balanceOf(dispatcher)` (or `address(this).balance` for native), *after* the predispatch call has already executed [5](#0-4) .
3. It then sweeps the *entire* current balance of `dispatcher` for that token to the gateway (`IERC20.transfer.selector, address(this), balance`), and computes `received` as the delta versus a gateway-side "before" snapshot [6](#0-5) .
4. Because `dispatcher` is a single well-known, shared, and permissionless address (not a per-order/per-caller escrow), any value sitting there for a given token — whether from a front-run "donation" by an unrelated party, residual dust from a previous order's incompletely-swept predispatch, or unrelated calls — is available to be counted as "received" for whoever calls `placeOrder` with matching `order.inputs[i].token` and `requiredAmount` next.
5. The code does check `balance < requiredAmount → revert`, and if `received > order.inputs[i].amount` it treats the excess as protocol dust rather than crediting the caller — but it does **not** verify that the received balance was produced by *this caller's own* predispatch assets/call in *this* transaction. A caller whose own predispatch call produces zero or partial value for a token, but who arrives after value has landed on `dispatcher` for any reason, can have that pre-existing balance silently absorbed into their own order's escrow up to `requiredAmount`, without having paid for it via `predispatch.assets`.

This is structurally the same defect as `trackPurchase` in the external report: sizing a credited/escrowed amount from a balance snapshot on a shared account, rather than from a verified transfer tied to the specific caller/action.

### Impact Explanation
If exploited, an attacker can escrow tokens in `IntentGatewayV2` that were not genuinely funded by their own predispatch assets, while the commitment/escrow bookkeeping (`_orders[commitment][token]`) records the full `requiredAmount` as backed. When a solver later fills the order and the escrow-release path pays out the recorded amount, the gateway can be paying out value it never actually received from that order's placer — a direct loss to the protocol/other users whose funds happen to be commingled in gateway/dispatcher balances, and a route to mint escrow credit "for free." This satisfies the "concrete theft ... of funds" acceptance bar via a single `placeOrder` extrinsic-equivalent transaction, reachable by any unprivileged token bridger/order placer.

### Likelihood Explanation
Medium. It requires either (a) another party's tokens to transiently sit on the shared, permissionless `CallDispatcher` (e.g., front-running/donation, since `dispatch()` and `receive()` are open to anyone), or (b) residual balance left by an earlier predispatch call that didn't fully consume/sweep the dispatcher's holdings for that token. Both are plausible given `CallDispatcher` is a single, unauthenticated, cross-order shared contract; no privileged action is needed to trigger it.

### Recommendation
Do not size escrow from a balance snapshot/delta on the shared `CallDispatcher`. Instead:
- Use a fresh, per-call/per-order `CallDispatcher` instance (e.g., deploy ephemeral via CREATE2/CREATE per `placeOrder` call), or
- Have the predispatch call return/report the exact amount it produced and require the gateway to pull exactly that amount via `transferFrom`-style accounting instead of sweeping "whatever remains," or
- At minimum, snapshot `balancesBefore[i]` *before* the predispatch call executes (not after), and revert if `dispatcher`'s pre-call balance for that token/asset is non-zero, so cross-order/cross-caller residue can never be attributed to the current caller.

### Proof of Concept
1. Attacker (or an unrelated party) sends `X` units of token `T` directly to the known `CallDispatcher` address via a plain `transfer()`, or leaves `T` there via a prior `placeOrder` predispatch call that intentionally under-consumes it.
2. Attacker calls `placeOrder` with `order.predispatch.assets` containing zero or minimal real value in `T`, and `order.predispatch.call` a no-op (as already demonstrated feasible by `testPlaceOrder_FeeOnTransferToken_Predispatch`'s empty-calls pattern) [7](#0-6) .
3. Attacker sets `order.inputs[i] = {token: T, amount: X}` for the same `X` already sitting on `dispatcher`.
4. `placeOrder`'s predispatch branch reads `balance = IERC20(T).balanceOf(dispatcher)` (which is `X`, not funded by the attacker in this tx), passes the `balance < requiredAmount` check, sweeps `X` to the gateway, and records `order.inputs[i].amount = X` — crediting the attacker's order with `X` of escrow they never paid [8](#0-7) .

Note: I was not able to fully trace every downstream consumer of `_orders[commitment][token]` (e.g., the exact withdraw/fill accounting) in this session due to tool-call limits; a Devin session with full repo access should verify the end-to-end payout path from `_orders` to solver withdrawal to confirm the exact loss magnitude and any existing mitigations not surfaced by the index.

     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

    /// @notice Fee-on-transfer through the predispatch path: escrow reflects actual received.
    function testPlaceOrder_FeeOnTransferToken_Predispatch() public {
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% transfer fee
        fot.mint(user, 10000 * 1e18);

        uint256 predispatchAmount = 1000 * 1e18;
        // After transferring to dispatcher: 1% fee = dispatcher receives 990
        uint256 dispatcherReceived = predispatchAmount - (predispatchAmount * 100) / 10000;
        // After dispatcher transfers to gateway: another 1% fee = gateway receives ~980.1
        uint256 gatewayReceived = dispatcherReceived - (dispatcherReceived * 100) / 10000;

        // Predispatch: send FOT to dispatcher, the "call" is a no-op (empty calls array)
        TokenInfo[] memory predispatchAssets = new TokenInfo[](1);
        predispatchAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: predispatchAmount});

        // The predispatch call is an empty Call[] dispatch (no-op, tokens just sit on dispatcher)
        Call[] memory emptyCalls = new Call[](0);
        bytes memory predispatchCall = abi.encode(emptyCalls);

        // Inputs: expect the FOT that lands on dispatcher after predispatch
        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: dispatcherReceived});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 500 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: predispatchAssets, call: predispatchCall}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), predispatchAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received (double fee-on-transfer)
        assertEq(fot.balanceOf(address(intentGateway)), gatewayReceived, "Gateway should hold double-taxed amount");

        // Reconstruct commitment
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = gatewayReceived; // mutated to actual received
        bytes32 commitment = keccak256(abi.encode(order));

        assertEq(
            intentGateway._orders(commitment, address(fot)),
            gatewayReceived,
            "Escrow should match actual received after double transfer fee"
        );
    }
