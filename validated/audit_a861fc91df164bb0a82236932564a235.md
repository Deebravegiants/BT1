### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify," but the HMAC verification performed by `Utils::HmacValidator` only covers the raw request body, not the `shop-domain` header. Any party who can obtain one genuinely-signed webhook (e.g., by installing the app on a shop they control) can replay that exact body/HMAC pair while substituting a different `shop-domain` header, and the library will accept it as an authentic webhook for the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [1](#0-0) 

The HMAC signable content, however, is defined as only the raw body: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the signature purely over `to_signable_string` (the raw body) against the `hmac` header: [3](#0-2) 

`Registry.process` performs this HMAC check and then, on success, forwards `request.shop` — the unauthenticated header value — directly to the app's handler as the trusted tenant identifier: [4](#0-3) 

This breaks an identity binding the library implicitly promises to the host application: `shop header verified by HMAC == shop attributed to the webhook data`. In reality, `hmac verified` only equals `body bytes unmodified`; the `shop` value is never part of what's authenticated. The gem's own documentation reinforces the false guarantee, stating that `Registry.process` "will verify the request did indeed come from Shopify": [5](#0-4) 

and that handlers can trust `data.shop` as "The shop domain of the webhook": [6](#0-5) 

### Impact Explanation
An attacker who has (or creates) any shop with the target app installed receives genuinely Shopify-signed webhooks for their own shop (valid `raw_body` + valid `hmac`, since Shopify signs with the app's own `client_secret`, which the attacker never needs to know). Because the `shop-domain` header is excluded from the signed bytes, the attacker can replay that identical body/HMAC pair to the app's public webhook endpoint while swapping in an arbitrary victim `shop-domain` (any `*.myshopify.com` value, not necessarily one that installed the app). `HmacValidator.validate` still succeeds because the body is unchanged, and `Registry.process` dispatches the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain. Any host application that uses `data.shop` to route or attribute the webhook body to a tenant (exactly as the library's own docs example does — `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will process attacker-controlled data (orders, products, customer records, GDPR redact payloads, etc.) under a victim tenant's identity. This is a cross-tenant data-integrity/confusion issue reachable by an unprivileged internet user with no access token or secret required.

### Likelihood Explanation
The prerequisite — installing the app on a store the attacker controls, or capturing one legitimate webhook — is trivial for free/dev stores, and the webhook endpoint is by design a public, unauthenticated HTTP endpoint. No credentials, TLS interception, or privileged access are needed; only knowledge of the target app's public webhook URL and one authentic webhook capture.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed payload, or otherwise independently authenticate the `shop` value (e.g., only accept it if it matches a known/authorized shop with an active, registered webhook subscription for that topic) before forwarding it to the handler. At minimum, update `Utils::HmacValidator`/`Webhooks::Request` so `to_signable_string` binds header-derived fields it exposes as trusted identity to the same signature that gates authenticity.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (or any store they control) and triggers a webhook (e.g., `orders/create`), capturing the raw POST body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (computed by Shopify over `B` with the app's secret).
2. Attacker sends a new POST to the app's public webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request object whose `shop` returns `"victim-shop.myshopify.com"` while `to_signable_string` still returns `B`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` and compares to `H` — this succeeds because `B` and `H` are unchanged.
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-supplied webhook content as if it belonged to `victim-shop.myshopify.com`.
