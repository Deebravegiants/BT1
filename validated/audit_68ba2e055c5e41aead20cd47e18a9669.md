Confirmed: the `AuthQuery#to_signable_string` correctly binds `shop` and `host` into the HMAC (`lib/shopify_api/auth/oauth/auth_query.rb` lines 33-43), but the webhook `Request#to_signable_string` binds only `@raw_body`, deliberately excluding the `shop` header from `lib/shopify_api/utils/hmac_validator.rb`'s HMAC computation.

### Title
Webhook `shop` identity is not bound by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` authenticates *only* the body bytes with the app's shared `client_secret`. The `shop-domain` header — the field the registry then uses to identify which tenant a webhook belongs to — is never included in the signed material.

### Finding Description
The equality the library should enforce is: `shop bound in the verified HMAC == shop the handler acts on`. Instead:

- `Request#hmac` reads `x-shopify-hmac-sha256` and `Request#shop` reads `x-shopify-shop-domain` independently as plain headers [1](#0-0) .
- `Request#to_signable_string` returns `@raw_body` only, with no shop/topic/webhook-id binding [2](#0-1) .
- `HmacValidator.validate_signature` computes the HMAC exclusively over `verifiable_query.to_signable_string` [3](#0-2) .
- `Registry.process` trusts this validation and then builds `WebhookMetadata` directly from the unauthenticated `request.shop` header, handing it to the app's handler as the tenant identifier [4](#0-3) .

This is the exact pattern the OAuth callback path avoids: `Auth::Oauth::AuthQuery#to_signable_string` explicitly folds `shop` (and `host`) into the signed string before HMAC verification [5](#0-4) , so the equality "shop verified by HMAC == shop used to build the session" holds for OAuth but not for webhooks — an inconsistency between two sibling `VerifiableQuery` implementations in the same gem, mirroring the "inconsistent binding logic between two similar code paths" bug class.

Because the same `client_secret` HMAC key is shared across every shop that installs the app, and the signed material is only the JSON body, any party who can obtain one valid `(body, hmac)` pair for their own shop can replay the identical body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain, and `Utils::HmacValidator.validate` will still return `true`.

### Impact Explanation
An unprivileged party that installs the app on a shop they control (or otherwise obtains a legitimate webhook delivery) can trigger any webhook topic on their own shop, capture the resulting `(raw_body, hmac)` pair, then replay it to the app's public webhook endpoint with a forged `shop-domain` header naming a different, victim tenant. The library reports the request as validly signed and hands the host application a `WebhookMetadata` object whose `shop` is attacker-controlled but whose HMAC-verified authenticity the host application will reasonably trust. Any host application that uses `WebhookMetadata#shop` to select the tenant record to create/update/delete (the documented and expected usage pattern, see `docs/usage/webhooks.md`) is exposed to cross-tenant data injection or corruption without needing any credential belonging to the victim shop. This meets the Critical bar of cross-tenant access via an authentication/identity-binding gap in the gem's own webhook verification path.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target app on any shop (development stores are free and self-serve, or a merchant with a legitimate but adversarial intent), (2) the ability to trigger a webhook of the desired topic on that shop, and (3) the ability to send an arbitrary HTTP POST with custom headers to the app's public webhook endpoint (no credentials required). No secret material, token, or privileged access to Shopify's platform is needed — this is a purely unprivileged-internet-user attack once step 1 is satisfied.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed material verified for webhooks, or otherwise cryptographically tie the verified body to the claimed shop before constructing `WebhookMetadata`. Concretely:
- Change `Request#to_signable_string` to include the `shop` (and `topic`) alongside `@raw_body` in a way compatible with Shopify's signing scheme, or
- Have `Registry.process` cross-check `request.shop` against an application-supplied allow-list/session store keyed by the previously verified `shop` before dispatching to `handler.handle`, so a body legitimately signed for shop A cannot be attributed to shop B.
- At minimum, document prominently that `WebhookMetadata#shop` is NOT authenticated by the HMAC check and must not be used as the sole tenant-identity input without additional verification (e.g., confirming an active session/install record exists for that shop before trusting the payload).

### Proof of Concept
```ruby
# Attacker controls "attacker-shop.myshopify.com" (a real, self-installed shop)
# and legitimately receives a webhook for it:
raw_body = '{"id": 1, "note": "legit order on attacker shop"}'
hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# Attacker now POSTs the *same* body+hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to a victim shop it does NOT control:
forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => hmac,                       # unchanged, still valid
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id"   => "attacker-controlled-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes validation because shop is never part of the signed content:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process happily dispatches to the handler with the forged shop:
ShopifyAPI::Webhooks::Registry.process(request)
# handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker's data, ...)
```
