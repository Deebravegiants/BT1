<title>Webhook shop-domain header not covered by HMAC signature allows cross-tenant webhook spoofing</title>

### Summary
The webhook signature verification in `ShopifyAPI::Webhooks::Request` only binds the HMAC to the raw request body, not to the `shop-domain` header. Because the HMAC secret (`Context.api_secret_key`, the app's client secret) is shared across all shops that install the app, any unprivileged party who operates their own Shopify store can generate a validly-signed webhook payload and then submit it to the app's webhook endpoint while spoofing the `x-shopify-shop-domain`/`shopify-shop-domain` header to name a different, victim shop. The registry accepts it as authentic and dispatches it to the app's handler tagged with the attacker-chosen shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the `shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to the signed content: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. the body only) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` only checks that this body-only HMAC is valid, then builds `WebhookMetadata` using `request.shop` — the unauthenticated header value — and dispatches it to the app's handler: [4](#0-3) 

`WebhookMetadata.shop` is exactly the value the app is expected to use as the tenant identifier for the event (per the gem's own documentation, apps key their processing on `data.shop`, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [5](#0-4) 

The equality that should hold is: `shop bound by the HMAC signature == shop the handler attributes the event to`. Because the signed bytes are just the raw JSON body, that equality does not hold — the `shop` field is fully attacker-controlled while the HMAC still validates, since the app's secret used to sign a webhook is the same `client_secret` regardless of which shop originates it. A merchant/attacker with their own installed instance of the app can obtain a legitimately-signed `(body, hmac)` pair from their own store's webhook deliveries, then replay that pair to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still returns `true` (it never looks at `shop`), so `Registry.process` treats the forged event as authentic and calls the app's handler with `WebhookMetadata#shop` set to the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook authenticity: the HMAC is meant to prove "this event genuinely originates from Shopify for this shop," but it only proves "this body was signed with the app's shared secret" — it says nothing about which shop the event is for. Any app that uses `data.shop` (as documented) to key business logic — e.g. crediting/canceling orders, marking `app/uninstalled`, processing `customers/data_request` or `shop/redact` GDPR webhooks, updating per-shop billing state — can be made to act on a victim shop's identity using attacker-supplied data. This is a cross-tenant integrity issue reachable by any unprivileged party who can install the app on their own store (a normal, unprivileged path) and does not require the victim's access token, session, or `client_secret`.

### Likelihood Explanation
Likelihood is moderate-to-high in apps that expose a public webhook endpoint (as instructed by the gem's own docs) and trust `data.shop` for attribution, which is the documented and expected usage pattern. The attacker only needs their own legitimate install of the target app (any store can install a public app) to harvest a valid `(body, hmac)` pair, and standard HTTP tooling to replay it with a modified header — no secrets, tokens, or elevated access required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the signed material verified against Shopify, or otherwise cryptographically bind `request.shop` to the HMAC before trusting it — e.g. reject/flag when the signed body's shop-context (if present, such as an order's `shop_id` you can cross-check via API) diverges from the header-asserted shop, or document prominently that `data.shop` must not be trusted for authorization decisions without an independent verification (such as looking up an existing session for that shop and confirming the webhook was actually registered for it). At minimum, the docs and `Registry.process` should make it explicit that `shop` is unauthenticated header data, not a value covered by webhook signature verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify deliver a normal webhook, e.g. `orders/create`, to the app's registered endpoint. Attacker captures the raw request: body `B`, and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared `client_secret`), and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker crafts a new POST to the app's webhook endpoint with the *same* body `B` and *same* `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request object; `ShopifyAPI::Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`, so `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) does not raise `InvalidWebhookError`.
4. `Registry.process` dispatches to the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: JSON.parse(B), ...)`, causing the app to process attacker-controlled order/webhook data as if it belonged to `victim.myshopify.com`.
