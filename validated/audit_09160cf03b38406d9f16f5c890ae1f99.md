## Title
Webhook shop identity spoofing — the `shop` (tenant) field is processed but not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity of an inbound webhook exclusively from the `X-Shopify-Shop-Domain` HTTP header, while the HMAC that authenticates the request only covers the raw request body. Because the same `api_secret_key` is used to authenticate webhooks for every shop that has installed the app, any unprivileged internet user who can install the app on their own store (a normal, unprivileged action) can obtain a body + valid HMAC pair, then replay that pair directly to the app's public webhook endpoint while swapping the `shop-domain` header to name an arbitrary victim shop. The signature check still passes because the header is never part of the signed content, so the handler executes with attacker-controlled body content attributed to a victim tenant.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop` is read straight from an untrusted header, with no cryptographic binding to the body/HMAC: [2](#0-1) 

`HmacValidator.validate` computes and compares the signature purely against `verifiable_query.to_signable_string` (i.e., the body), never incorporating the shop header: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`) to build the metadata handed to the app's handler, with no further cross-check that the shop matches the entity that legitimately produced the signed body: [4](#0-3) 

Equality that should hold but doesn't: `shop_that_produced_valid_HMAC(body, api_secret_key) == shop_attributed_to_request (request.shop)`. Since `api_secret_key` is shared across all merchants of the app, and the HMAC never binds to the shop header, any holder of one valid `(body, hmac)` pair (trivially obtainable by installing the app on any store and triggering any webhook topic) can present that pair with an arbitrary `shop-domain` header and have it accepted as belonging to that other shop.

### Impact Explanation
This breaks the tenant/shop identity binding for all inbound webhooks: an attacker can make the app process attacker-chosen body content while causing app logic to attribute it to a victim shop of the attacker's choosing (cross-tenant confusion). Depending on how the host application uses `WebhookMetadata#shop` (e.g., to look up that shop's stored access token/session and perform authenticated actions on the victim's behalf, or to write attacker data into the victim's tenant-scoped records), this can result in cross-tenant data corruption or actions being executed against a shop using forged event data — matching the "cross-tenant access" bar (Critical) since the fundamental HMAC-to-tenant binding never exists.

### Likelihood Explanation
High for any host application that trusts `WebhookMetadata#shop` for tenant-scoped state changes; the only precondition is that the attacker can install the app on a shop they control (typically low or no privilege bar, e.g. dev/partner test stores) and know/guess the victim's `myshopify.com` domain, which is often public.

### Recommendation
Bind the shop identity into the authenticated material used for signature verification (or otherwise cryptographically verify that the `shop-domain` header matches the shop for which the body's HMAC was legitimately produced), for example by rejecting/flagging webhook requests when the resolved shop for the topic/registration doesn't correspond to a shop known to be equal to the one that produced the signature, or by requiring callers to independently confirm the shop is one they have an active session for before trusting `WebhookMetadata#shop` for any privileged action.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged action available to anyone).
2. Attacker triggers a real webhook (e.g. `orders/create`) with attacker-chosen body content (order notes, custom attributes, etc.) on their own shop; Shopify computes and sends a legitimate `X-Shopify-Hmac-Sha256` for the exact raw body using the app's single `api_secret_key`.
3. Attacker captures `{raw_body, hmac}` from this legitimate delivery.
4. Attacker sends an HTTP POST directly to the app's public webhook endpoint with the same `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `HmacValidator.validate` passes because it only checks the body against the secret (`lib/shopify_api/utils/hmac_validator.rb:26-31`), and `Registry.process` proceeds to call the app's handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: attacker_controlled_body ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the victim shop never produced this event.
