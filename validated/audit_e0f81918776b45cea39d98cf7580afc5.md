### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the HMAC signature over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by the handler are read directly from unauthenticated HTTP headers. This breaks the identity binding: `hmac_valid(body) == true` does not imply `shop_header == shop_that_Shopify_actually_sent_this_for`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` reads the `hmac-sha256` header: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled straight from headers via `shopify_header`, none of which are part of the signed payload: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., the body/HMAC pair) before dispatching to the handler with `request.shop` used as the tenant identifier: [3](#0-2) 

`HmacValidator.validate` calls `validate_signature`, which signs/verifies `verifiable_query.to_signable_string` (the body only for webhooks) against the `hmac` field — it never incorporates the `shop`, `topic`, or `webhook_id` headers into the signed material: [4](#0-3) 

The gem's own documentation tells integrators that `Registry.process` "will verify the request did indeed come from Shopify" and that the resulting `data.shop` is "The shop domain of the webhook," implying the shop value is trustworthy once HMAC validation passes: [5](#0-4) [6](#0-5) 

This is the same bug class as the referenced report: a value that is *acted upon* (here, the tenant-identifying `shop` field routed to the handler) is not covered by the cryptographic check that is supposed to establish trust (here, the webhook HMAC), even though the API's documentation implies otherwise.

### Impact Explanation
Any party who can obtain one genuine `(raw_body, hmac)` pair for a webhook delivered to the app — e.g. by installing the app on their own store and triggering a webhook (a normal, unprivileged action for any merchant) — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header with an arbitrary victim shop domain. `HmacValidator.validate` still returns `true` because it only checks the body against the HMAC, so `Registry.process` will happily dispatch the (attacker-controlled) body to the handler tagged as coming from the victim shop (`WebhookMetadata#shop`). Any app that uses `data.shop` to select which tenant's data to update (a documented, intended usage pattern) can be made to write, delete, or otherwise process attacker-supplied data under a victim tenant's identity — a cross-tenant data integrity/confidentiality violation.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the attacker to first obtain a legitimately signed `(body, hmac)` pair, which is trivial for anyone who can install the app on a shop they control (a standard, unprivileged action within the Shopify app ecosystem) and does not require the app's `client_secret`, an access token, or any other privileged credential. The only extra step is sending a raw HTTP request to the app's public webhook endpoint with a modified `shop-domain` header, which is fully within reach of an unprivileged internet user.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values to the HMAC-verified payload rather than trusting the corresponding headers independently. At minimum, `Request#to_signable_string` should incorporate the `shop-domain` (and `topic`) header value so that any tampering invalidates the HMAC, or `Registry.process` should independently authenticate the shop (e.g., by requiring the caller to supply the expected shop separately and comparing it, or validating the shop domain against `ShopValidator` and cross-checking against a known/registered install for that webhook subscription).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook, capturing the raw body `B` and the valid header `shopify-hmac-sha256: H` (HMAC of `B` with the app's `client_secret`).
2. Attacker sends a new HTTP request to the app's webhook endpoint with the same raw body `B`, the same `shopify-hmac-sha256: H`, but headers rewritten to:
   ```
   shopify-shop-domain: victim-shop.myshopify.com
   shopify-topic: orders/create
   shopify-webhook-id: <any>
   ```
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed and passed to `ShopifyAPI::Webhooks::Registry.process`.
4. `Utils::HmacValidator.validate(request)` returns `true` since it only recomputes the HMAC over `B` and it matches `H`.
5. The registered handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the app to process attacker-controlled data as if it belonged to `victim-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
