### Title
Solver bids on IntentGateway deployments predating `FillOptions.validUntil` can be held indefinitely and exercised only when the rate moves against the solver - ([File: `evm/src/apps/IntentGatewayV2.sol`], legacy implementation tracked in [`sdk/packages/sdk/src/protocols/intents/fillOrderCodec.ts`])

### Summary
An order placer who holds the `order.session` key can retain a solver's signed `fillOrder` bid indefinitely and choose to execute it (via `select()` + `fillOrder()`) at whatever future block is most advantageous to the placer, since the fixed-price commitment carries no expiry on gateway deployments that predate the `validUntil` field. This is the same bug class as the OngoingBounty report: a counterparty with unilateral control over *when* to accept an already-signed commitment can wait for the market to move against the other unprivileged party before "cashing in," at no cost to themselves.

### Finding Description
In the current `IntentGatewayV2.sol`, `fillOrder` enforces `options.validUntil` as a hard ceiling on how long a solver's quoted price stands: [1](#0-0) 

This field was added specifically because, before it existed, `order.deadline` is chosen entirely by the placer with no upper bound, retracting a bid on Hyperbridge has no effect on the destination chain, and the placer (holding the session key) could sit on a signed, still-valid bid and only execute it once the solver's quoted price had become unfavorable to the solver: [2](#0-1) 

The struct-level documentation on the fixed version states this explicitly as the exploited property being closed: [3](#0-2) 

Critically, this fix is not universally deployed. Because `fillOrder` gained a new field, its selector changed, and both the pre-fix (v1, `0x5cfb1ea5`) and post-fix (v2, `0xa5470064`) shapes remain live on the network simultaneously — the SDK explicitly tracks which chains/implementations still run the vulnerable v1 shape: [4](#0-3) 

On any such chain, a solver's signed `UserOperation` — bound only by `order.deadline` (placer-controlled, unbounded) — is fully executable by the order placer at any block up to that deadline. The Simplex filler code explicitly warns operators of this residual exposure rather than blocking it, because there is "nowhere to put" the bound on the legacy selector: [5](#0-4) 

The mechanics of solver selection (`select()` binding a `msg.sender`/`order.session` pair via transient storage, verified in `fillOrder`) do not constrain *when* the placer chooses to submit the winning bid — only *which* solver is authorized: [6](#0-5) 

### Impact Explanation
On any IntentGateway deployment still running the pre-`validUntil` implementation, the order placer holds a free, unbounded-duration option on the solver's quoted price. A solver commits liquidity by signing a `UserOperation` with fixed output amounts; if the exchange rate later moves in the placer's favor (i.e., against the solver), the placer executes the stale bid and forces the solver to deliver output tokens at the now-unfavorable rate — a direct financial loss to the solver, mirroring exactly how an OngoingBounty owner could decrease `payout` and force a stale contributor claim to settle at worse terms. This is a real, uncompensated wealth transfer from solver to order placer, reachable by any ordinary (unprivileged) user placing an intent order — no protocol admin or governance action is required.

### Likelihood Explanation
Likelihood is high wherever the legacy gateway implementation is still live, since exploiting it requires nothing more than: (1) placing a normal order, (2) collecting solver bids as intended by the protocol, and (3) simply waiting before calling `select`/`fillOrder` until the price has moved favorably — all standard, permitted interactions with no special access. The protocol's own SDK and filler code acknowledge and warn about this exact gap rather than being able to close it on-chain for un-upgraded deployments.

### Recommendation
Ensure `FillOptions.validUntil` enforcement (as already implemented in the v2 `fillOrder`) is deployed to every chain before onboarding solver liquidity there; until upgraded, treat `CHAINS_WITHOUT_VALID_UNTIL`/`LEGACY_FILL_OPTIONS_IMPLEMENTATIONS` chains as unsafe for solver bidding, or have solvers refuse to sign bids on those deployments entirely rather than merely logging a warning.

### Proof of Concept
1. On a chain still running the legacy `IntentGatewayV2` implementation (pre-`validUntil`), a user places an order with `order.session` set to a session key they control, and `order.deadline` set far in the future.
2. A solver observes the order and signs a `UserOperation` (via `SolverAccount`) committing to fill it at the current favorable exchange rate, using the legacy `fillOrder(Order, (relayerFee, nativeDispatchFee, outputs))` selector (`0x5cfb1ea5`) — no `validUntil` field exists to bound it.
3. The order placer withholds calling `select()`/submitting the bundler operation.
4. The market price moves against the solver over subsequent blocks (still within `order.deadline`).
5. The placer signs the `SelectSolver` EIP-712 message now, appends it to the solver's original (stale) signed `UserOperation`, and submits it to the bundler.
6. `fillOrder` executes successfully — there is no `validUntil` check on this implementation — forcing the solver to deliver output tokens at the original, now-unfavorable, rate. The placer captures the difference at the solver's expense, with no on-chain mechanism to prevent or compensate for it.
