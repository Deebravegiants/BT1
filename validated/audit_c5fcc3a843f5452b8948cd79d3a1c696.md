### Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by the HMAC, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while `shop`, `topic`, `api_version`, and `webhook_id` are taken verbatim from unauthenticated HTTP headers. `Utils::HmacValidator.validate` only proves that the body bytes match a valid signature computed with the app's single, shop-independent `api_secret_key` — it says nothing about which shop that body belongs to. Any attacker who can obtain one genuine, validly-signed webhook body (trivially achievable by installing the app on their own store, since the app's secret is shared across all shops) can replay that exact body with a forged `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`webhook-id`) header pointing at a victim shop. The signature still validates, and `Registry.process` dispatches the handler with the attacker-controlled body attributed to the victim's shop.

### Finding Description
`to_signable_string` for webhook requests is defined as just the raw body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors read directly from headers that are never included in that signable string: [2](#0-1) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (the body) using the app-wide `Context.api_secret_key`/`old_api_secret_key` — the same secret for every shop that has installed the app: [3](#0-2) 

`Registry.process` gates only on this body-HMAC check, then dispatches the handler using the unauthenticated `request.shop`/`request.topic`/`request.webhook_id` values: [4](#0-3) 

The binding that is broken is: **shop the HMAC actually authenticates (none — it only authenticates body bytes under a shared secret) ≠ shop attributed to the delivered event (`request.shop`, taken from an unauthenticated header)**. Because the secret is shared across all shops using the app, any shop that has installed the app can generate a validly-signed body (e.g., via a benign webhook it itself triggers), then replay that identical body+HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header value for a different, victim shop. The signature check in `HmacValidator.validate` passes since the body is unchanged, and the handler processes the forged event as if it originated from the victim tenant.

### Impact Explanation
This is a cross-tenant identity confusion in the webhook trust boundary: an unprivileged app-installer (attacker who merely installs the app on their own shop) can cause the host application's webhook handling logic to execute with a victim shop's identity attached to attacker-chosen body content and topic. Depending on how the host app's webhook handlers use `WebhookMetadata#shop` (e.g., billing state changes, GDPR/customer-data topics, `app/uninstalled` bookkeeping, cache invalidation, or triggering per-shop side effects), this enables cross-tenant access/manipulation of another merchant's application state — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Reachable by any unprivileged internet user who can install the target Shopify app on their own store (a normal, non-privileged action for any Shopify merchant) and can send HTTP requests to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only a legitimately-delivered webhook body/HMAC pair from their own tenant, which the gem does nothing to bind to a specific shop.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) headers in the HMAC-signable string computed by `Webhooks::Request#to_signable_string`, or otherwise cryptographically bind the shop identity to the signed payload (e.g., verify the header-derived shop against a per-shop secret/session before trusting `request.shop` in `Registry.process`).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`; app's webhook endpoint receives a legitimate delivery:
   - Body: `{"id":123}`
   - Headers: `X-Shopify-Hmac-Sha256: <valid hmac of body>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`
2. Attacker captures this body+HMAC pair (it is delivered to their own endpoint, so they have full access to it).
3. Attacker resends an HTTP POST to the app's webhook endpoint with the identical body and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over the (unchanged) body using the app's shared secret and it matches, so validation succeeds.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the registered handler with `shop: "victim-shop.myshopify.com"`, causing the host application to process attacker-controlled data attributed to the victim tenant.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
