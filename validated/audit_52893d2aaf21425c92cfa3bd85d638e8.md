### Title
Webhook `shop`, `topic`, and `webhook_id` identity fields are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the shop, topic, and webhook-id used to route and attribute the webhook are read from HTTP headers that are excluded from the signature. `Registry.process` validates the HMAC and then trusts these header-derived values as authenticated tenant identity, breaking the binding between "bytes verified" and "identity acted on."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are all pulled from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`), none of which participate in the signable string: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` only re-computes and compares the HMAC over `verifiable_query.to_signable_string` (the raw body): [4](#0-3) 

`Registry.process` validates the HMAC once, then constructs `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id` directly from the unauthenticated headers, treating them as if they had been verified alongside the body: [5](#0-4) 

The identity binding that should hold is: `shop-domain header == shop bound inside the HMAC-signed payload`. Because the header is outside the signed bytes, this equality is never checked — the gem verifies the body's integrity but attributes that body to whatever shop value the caller supplies in the header, independent of the signature.

### Impact Explanation
Any caller able to reach the app's webhook endpoint (which is a public HTTP endpoint, by design) can pair a body/HMAC pair that is valid under the app's real secret (obtained from any legitimately-delivered webhook, e.g., one sent to the attacker's own shop after installing the app) with an arbitrary `shopify-shop-domain` header value. `Registry.process` will accept the HMAC as valid (it only checks body bytes) and dispatch the handler with `shop` set to the attacker-chosen value. Any host application logic that uses `WebhookMetadata#shop` to select which merchant's session/data record to update is thereby fed attacker-controlled tenant identity alongside genuinely-signed body content, enabling cross-tenant data confusion/injection without ever needing the app's `client_secret` or an access token.

### Likelihood Explanation
Medium: it requires the attacker to possess at least one legitimately-signed webhook body (achievable simply by installing the target app on their own shop and receiving any webhook), and requires the host application to key merchant-side effects off `WebhookMetadata#shop`/`#topic`/`#webhook_id` rather than by re-deriving shop identity from data embedded and signed inside the JSON body. This is a common pattern for apps consuming this gem's webhook API, since the gem's own documented interface (`WebhookMetadata`) exposes these header values as if they were verified.

### Recommendation
Include the `shop-domain`, `topic`, and `webhook-id` headers in the HMAC-signable string (or otherwise cryptographically bind them to the body) so that `HmacValidator.validate` fails if any of these values are altered relative to what Shopify actually signed, restoring the equality `verified bytes == identity acted upon`.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; receive a legitimate webhook `POST` with body `B` and header `x-shopify-hmac-sha256: H` (valid because Shopify signed `B` with the app's real secret) and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Replay the exact same body `B` and HMAC header `H` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the headers/body and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `OpenSSL.secure_compare(compute_signature(B, secret), H)` — this passes because `B` and `H` are unchanged. [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker's own body content, even though Shopify never signed that shop/body combination — any host-side logic trusting `data.shop` for tenant attribution is compromised.
