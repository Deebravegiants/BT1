### Title
Webhook `shop-domain` Header Is Trusted for Tenant Routing Without Being Covered by the HMAC Signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (i.e. `shop-domain`) header used to route the webhook payload to a specific merchant/tenant handler is read from an unauthenticated HTTP header and never included in the signed data.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Webhooks::Registry.process` validates the webhook solely via `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` and thus only ever hashes the body bytes [2](#0-1) [3](#0-2) . Meanwhile `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header with no cryptographic binding to the HMAC-covered body [4](#0-3) . After the HMAC check passes, `Registry.process` forwards `request.shop` unchanged into `WebhookMetadata` and dispatches it to the host application's webhook handler, which typically uses this value to select the tenant/shop record to act on [2](#0-1) .

This breaks the intended identity binding: `hmac-verified-bytes == raw_body` but `shop-used-for-tenant-routing == unauthenticated header`. The library never asserts `hmac-verified-bytes` also covers `shop`. Because the header is not part of the signed payload, its value can be swapped independently of the HMAC digest.

### Impact Explanation
If the gem's HTTP transport surface (or any component that forwards the raw body/headers to `Webhooks::Request.new`) allows an attacker to submit or replay a request with a body/HMAC pair that was legitimately produced by Shopify for the attacker's own shop, but with a substituted `shop-domain` header pointing to a victim shop, `Registry.process` will pass HMAC validation (since it never checks the header) and hand the attacker-controlled `shop` value to the handler as if it were authentic. Depending on how the host app's webhook handler keys off `WebhookMetadata#shop` (e.g., to look up per-tenant settings, credentials, or trigger tenant-scoped side effects), this is a cross-tenant identity-confusion primitive — the exact "field acted on but not covered by the HMAC" class called out in the report's rules.

### Likelihood Explanation
This requires the attacker to control (or replay) a body+HMAC pair — normally only Shopify can produce a valid HMAC without the shared secret, since HMAC verification uses `Context.api_secret_key` [5](#0-4) . However, the specific weakness — that `shop-domain` is excluded from the signed bytes — is a genuine, unconditional design gap in this gem's own verification logic, independent of whether the app happens to be multi-tenant enough for an attacker to supply a legitimately-signed webhook for one shop and relabel it for another (e.g., a malicious merchant installing the app on their own shop, capturing a legitimately HMAC-signed webhook body/HMAC pair from Shopify for their own store, and replaying it with a different `shop-domain` header value against the app's webhook endpoint). No leaked secret or privileged access is required for this specific step; the attacker only needs to be a legitimate merchant with the app installed on their own shop to obtain one valid (body, hmac) pair to relabel.

### Recommendation
Bind `shop` (and ideally `topic`, `webhook_id`, `api_version`) into the value verified by the HMAC, or independently verify the `shop-domain` header against a source of truth (e.g., only accept shops for which the app holds an active session/access token) before dispatching to handlers. At minimum, document that `WebhookMetadata#shop` is not covered by the Shopify HMAC and must be independently validated by host applications before being trusted for tenant-scoped actions.

### Proof of Concept
1. App has installed on `attacker-shop.myshopify.com` and legitimately receives a real webhook from Shopify: body `B`, header `shopify-hmac-sha256: H` (valid HMAC over `B` with the app's `client_secret`), and header `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same `B` and `H` to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac-sha256: H...})` is constructed; `to_signable_string` returns `B`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` and compares to `H` — this matches because `shop` was never part of the signed data [6](#0-5) .
5. `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` fires with `shop: "victim-shop.myshopify.com"` [7](#0-6) , even though the payload actually originated for `attacker-shop.myshopify.com`.
